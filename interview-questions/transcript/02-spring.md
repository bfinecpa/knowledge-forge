# 2. Spring / Spring Boot — 문답 기록

## 기본 ⭐

### [Q1] IoC와 DI란, 왜 사용하나 — **중**

**본질문 답변 요지**: "의존성 주입과 의존성 역전이다." (약어 풀이만 — IoC를 '의존성 역전'으로 오답, 제어의 역전으로 교정함. DIP와 혼동)

**꼬리질문 1-1**: 역전되는 것은 정확히 무엇? 무엇이 누구에게 넘어가나? 이득은?
- 답변: 클래스가 연결되는 제어를 직접 했는데 이제 스프링이 자동으로 해준다. 이득은 연결 제어를 내가 안 하고 비즈니스 로직에 집중. (제어 이양은 정확, 이득은 편의성 서사에 머묾)

**꼬리질문 1-2**: OrderService가 내부에서 `new PgPaymentClient()` 직접 생성 — 단위 테스트 시? DI였다면?
- 답변: 단위 테스트에 PgPaymentClient가 포함되어 테스트가 안 돌아간다. 실제 외부 API를 찌르기 때문. DI 구조면 실제로 찌르지 않고 찌른 것처럼(목) 사용 가능. (테스트 가능성 도달 — 정확)
- 면접관 보충: new = 구현체가 코드에 박제(강결합). 주입 = 인터페이스에만 의존해 교체 가능(느슨한 결합). 테스트 용이성은 이 결합도 낮춤의 대표 증상.

**메모**: IoC/DIP 용어 혼동으로 출발. 시나리오를 주면 테스트 가능성까지 정확히 도달하지만, "왜 쓰나"를 스스로 결합도·테스트 관점으로 여는 힘은 아직. rationale 기준(테스트 가능성·결합도 자발 설명) 절반 충족.

### [Q2] Bean 생명주기 / singleton / 상태 위험 — **중**

**본질문 답변 요지**: 컨테이너 생성 시 함께 생성, 컨테이너가 죽을 때 같이 죽는다. singleton=컨테이너 안에 1개만 생성. 1개라 여러 요청(스레드)이 상태값 공유하면 장애. (큰 그림·싱글턴 계약·위험 전부 정확 — 위험은 1장 Q22에서 이미 검증된 바)

**꼬리질문 2-1**: 의존성 주입 완료 시점의 초기화(캐시 예열 등)와 종료 시 자원 정리는 어디에?
- 답변: 어노테이션이 있는데 까먹었다.
- 면접관 보충: `@PostConstruct`(생성+주입 완료 후 1회) / `@PreDestroy`(컨테이너 종료 시). 세밀 생명주기 = 인스턴스화 → 의존성 주입 → @PostConstruct → 사용 → @PreDestroy → 소멸. 생성자에서 초기화하면 안 되는 이유 = (필드 주입 시) 의존성 미주입 상태 + AOP 프록시 미적용 시점.

**메모**: 큰 그림과 싱글턴 계약은 확실, 훅 이름은 "존재는 아는데 이름 망각" — 1장부터 반복되는 어휘 층 패턴. 실무에서 @PostConstruct를 직접 쓸 일이 있었는지 의문.

### [Q3] 생성자 주입 권장 이유 (필드 주입 대비) — **중**

**본질문 답변 요지**: 순환 참조를 미리(기동 시점에) 알 수 있다. 주입 전후로 로직을 넣을 수 있다. (순환참조 조기발견 정확. 두 번째 포인트는 모호. 불변성·테스트 용이성 자발 언급 없음)

**꼬리질문 3-1**: 왜 생성자 주입은 순환 참조를 기동 시점에 잡고 필드 주입은 못 잡나? 컨테이너 내부 차이는?
- 답변: 생성자는 빈 생성 시 연결된 객체도 함께 생성해야 해서 순환이면 반복 생성으로 오류. 필드 주입은 객체 생성 후 연결하는 방식이라 못 잡는다. (핵심 메커니즘 — 생성 시점 의존성 요구 vs 생성 후 채움 — 정확)
- 면접관 보충: 무한 반복이 아니라 스프링이 "생성 중인 빈" 목록을 추적하다 재등장 시 `BeanCurrentlyInCreationException`. 필드 주입은 조기 참조(3단계 캐시)로 순환을 우회해 기동이 성공해버림.

**꼬리질문 3-2**: 필드 주입 클래스를 스프링 없이 순수 단위 테스트할 때의 불편은? (테스트 용이성 유도)
- 답변: 생성자 주입이면 목을 만들어 생성자로 주입하면 되는데 필드 주입은 불가능하다. (방향 정확, 최소한의 답 — 리플렉션/@InjectMocks 우회나 "컴파일 타임에 의존성이 드러난다" 확장 없음)

**메모**: 메커니즘 이해는 기본⭐ 기준 탄탄. 그러나 rationale의 권장 근거 3축(순환참조/불변성 final/테스트 용이성) 중 자발적으로 나온 건 순환참조뿐 — 테스트는 유도해야 나왔고 **불변성(final 필드, NPE 예방)은 끝까지 미언급**. 1~2장 반복 패턴(시나리오 주면 도달, 자발 확장 부족) 지속.

### [Q4] @Component/@Service/@Repository/@Controller 차이 — **중**

**본질문 답변 요지**: 셋 다 까보면 @Component가 있다(메타 애너테이션 구조 인지 — 소스를 직접 확인해본 흔적). "계층 인지를 위한 차이일 뿐" — rationale이 노리는 바로 그 절반짜리 통념.

**꼬리질문 4-1**: 반론 — 넷 중 실제 런타임 동작이 달라지는 것이 있다. 무엇이고 무슨 동작?
- 답변: @Repository 지목은 정확했으나 근거 오답("ORM으로 DB와 연결해주는 것 같다")

**꼬리질문 4-2**: (힌트: 기술마다 예외 타입이 제각각 — SQLException/Hibernate 예외/몽고 예외) @Repository가 그 예외들에 무엇을 해주나? 서비스 계층에 왜 이득?
- 답변: "스프링 공통 예외로 변환해주는 것 같다" (힌트 받고 도달, 정확. 단 '왜 이득인지'는 미답)
- 면접관 보충: `DataAccessException` 계층으로 변환(예: 중복 키 → `DuplicateKeyException`). 이득 = 서비스 계층이 영속성 기술의 예외 타입에 의존하지 않음 → 기술 교체 시 catch 블록 불변, 런타임 예외라 선언 강제도 없음. @Controller도 기능적 차이 있음(DispatcherServlet의 핸들러 탐지 대상).

**메모**: 메타 애너테이션 구조를 소스로 확인해본 건 플러스. 그러나 예외 변환은 강한 힌트를 줘야 도달했고 추측 어투("~것 같다"). '장식 vs 기능' 구분 정밀함은 아직 — rationale 기준 미달이지만 힌트 후 방향은 정확히 잡음.

### [Q5] Spring MVC 요청 처리 흐름 — **중**

**본질문 답변 요지**: DS가 요청을 받으면 "리졸버"에게 일치하는 컨트롤러를 찾게 하고, 찾으면 실행시킨다. (골격은 맞으나 HandlerMapping을 '리졸버'로 부름 — 용어 부정확. HandlerAdapter·응답 경로(ViewResolver/@ResponseBody) 전부 누락)

**꼬리질문 5-1** (rationale 시나리오 변환 — 디버깅): POST JSON이 400인데 컨트롤러 첫 줄 브레이크포인트에 안 걸림. DS와 컨트롤러 사이 어디서 무슨 일? JSON→DTO 변환은 누가 언제?
- 답변: 누가 하는지는 모르겠으나 그 사이에 JSON→DTO 매핑 단계가 있을 것으로 판단, 거기서 에러 가능. 인터셉터나 필터에서도 장애 가능. (단계 추론은 정확 — rationale이 노리는 "어느 단계에서 죽었나" 감각은 있음. 컴포넌트 이름은 전무)
- 면접관 보충: HandlerAdapter가 메서드 호출 전 ArgumentResolver→HttpMessageConverter(Jackson)로 바디 역직렬화 + @Valid 검증 — 여기서 실패하면 컨트롤러 진입 전 400. 필터는 DS보다도 앞(서블릿 컨테이너 레벨). 응답 경로: @ResponseBody면 ViewResolver 대신 MessageConverter가 직렬화.

**메모**: 1~2장 패턴 그대로 — 단계·메커니즘 추론은 되는데 컴포넌트 어휘(HandlerMapping/Adapter/HttpMessageConverter/ArgumentResolver)가 없음. 디버깅 감각(컨트롤러 전 단계에서 죽었다는 판단)은 실무형으로 합격점.

### [Q6] Filter vs Interceptor 차이·용도 — **중**

**본질문 답변 요지**: Filter는 스프링 컨테이너 들어오기 전, Interceptor는 컨테이너 안에서 요청 앞단. (위치 구분의 골격은 맞음. Interceptor의 preHandle/postHandle/afterCompletion 3훅, 핸들러 정보 접근 가능 등 용도 차이는 미언급)

**꼬리질문 6-1** (rationale 시나리오 변환 — 관측 사각지대): trace id를 MDC에 심는 로깅을 어디에? 인증 실패 401도 찍혀야 함.
- 답변: 필터. 단 근거에서 "Spring Security 인증은 스프링 컨테이너 안에서 한다"고 오답 — Security가 필터 체인에서 동작함을 모름. (결론은 맞았으나 근거가 우연)

**꼬리질문 6-2**: Security도 필터라고 교정 후 — trace 필터가 Security 필터보다 뒤에 등록되면? 순서 보장은?
- 답변: 401에 trace id가 안 찍힌다(정확). 순서는 "정해서 넣으면 된다"(모호).

**꼬리질문 6-3**: 구체적으로 스프링 부트에서 필터 순서를 어떻게 지정? Security 체인보다 앞에 두려면?
- 답변: "코드상에서 설정할 수 있는 것 아니냐, 그 뒤 체인에 security가 적용되게 하면 된다" — 메커니즘 이름 없음.
- 면접관 보충: `FilterRegistrationBean.setOrder(n)` 또는 필터 빈에 `@Order`/`Ordered` 구현. Spring Security 체인은 `DelegatingFilterProxy`→`FilterChainProxy`(springSecurityFilterChain)로 서블릿 필터 체인에 하나의 필터로 끼어들며 기본 order는 `SecurityProperties.DEFAULT_FILTER_ORDER = -100` — 그보다 작은 값이면 앞. trace/MDC 필터는 `OncePerRequestFilter` 상속이 관례(포워드 시 중복 실행 방지).

**메모**: 결과 예측(401 관측 사각지대)은 유도하면 정확히 도달 — rationale이 노리는 "어느 계층에 넣을지" 감각의 절반은 있음. 그러나 (1) Security=필터 체인이라는 구조를 몰랐고 (2) 순서 지정 메커니즘(@Order/FilterRegistrationBean/-100)이 전무. Q5와 동일 패턴: 단계 감각 있음, 컴포넌트·설정 어휘 없음. IAM(인증/인가) 도메인 종사자로서 Security 필터 체인 무지는 아픈 지점 — 3장 이후 Security 섹션에서 재검증 필요.

### [Q7] @Transactional 기본 동작 / 롤백 조건 — **중** (상 경계)

**본질문 답변 요지**: 프록시 클래스가 메서드 실행 전 트랜잭션 시작, 리턴 후 커밋. unchecked 예외에서만 롤백. (프록시 메커니즘 + unchecked 기본값 — 기본⭐ 기준 정확하고 간결. 섹션 내 최초로 어휘까지 갖춘 답변)

**꼬리질문 7-1** (rationale 시나리오 — 정합성 사고): order()가 내부 빈 decrease()(둘 다 @Transactional 기본 전파)의 RuntimeException을 try-catch 후 정상 리턴 — 커밋되나?
- 답변: "내부에서 이미 롤백 설정을 on 해놓았기 때문에 전파되어 결국 롤백된다" — rollback-only 마킹 개념 자발 도달 (정확)

**꼬리질문 7-2**: 호출자는 뭘 받나? 조용한 롤백인가?
- 답변: 트랜잭션 롤백 관련 에러 발생 (정확 — `UnexpectedRollbackException` 이름은 미언급)

**꼬리질문 7-3**: "실패 시 대체 로직 + order()는 정상 커밋" 요구사항 — 어떻게 설계? 트레이드오프는?
- 답변: noRollbackFor 사용, 또는 @Transactional을 뗀다. (트레이드오프 없음, **REQUIRES_NEW 미언급**)
- 면접관 보충: 정석은 `decrease()`에 `propagation = REQUIRES_NEW` — 별도 물리 트랜잭션이라 실패 시 자기만 롤백, order는 깨끗하게 커밋. 트레이드오프 = 커넥션 2개 동시 점유(풀 고갈 주의), 이후 order가 롤백돼도 decrease 커밋은 안 되돌아감. 후보의 두 방법은 공통 함정: decrease가 예외 전에 쓴 데이터가 공유 트랜잭션에 남은 채 커밋됨(반쯤 커밋 정합성 사고 — rationale이 노리는 바로 그 지점). 가장 깔끔한 대안은 decrease 내부에서 잡아 실패를 리턴값으로 표현.

**메모**: 개념·함정·결과(rollback-only 전파→커밋 시점 예외)를 유도 없이 자발 도달 — 이 섹션 최고 수행. 다만 설계 결정 단계에서 전파 속성(REQUIRES_NEW) 어휘 부재 + 제안한 수정안의 부분 쓰기 잔존 결함을 인지 못함 + 트레이드오프 요청에 무응답. "동작 모델은 정확, 설계 대안 레퍼토리는 얕음" 패턴.

### [Q8] Spring Boot Auto Configuration 동작 — **하**

**본질문 답변 요지**: "잘 모르겠다." (즉답 포기 — 꼬리질문 없이 종료)

- 면접관 보충(핵심만): `@SpringBootApplication` 안의 `@EnableAutoConfiguration`이 시작점. 스타터 jar들의 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 목록에서 자동 구성 후보 클래스들을 읽고, 각 후보의 `@ConditionalOnClass`(클래스패스에 있나) / `@ConditionalOnMissingBean`(사용자가 직접 등록 안 했나) 등 **조건 평가**를 통과한 것만 빈으로 등록. 그래서 의존성만 추가하면 DataSource·ObjectMapper가 "알아서" 생기고, 내가 같은 타입 빈을 등록하면 자동 구성이 물러난다(사용자 우선).

**메모**: 매일 쓰는 부트 기능의 원리를 전혀 모름. "왜 설정 없이 도는지"를 설명 못 하면 자동 구성이 안 먹을 때(조건 불충족, 빈 충돌) 디버깅 불가. 재도전 필수.

### [Q9] application.yml profile 활용 — **중**

**본질문 답변 요지**: 환경별로 실행하고 환경별 yml을 읽게 한다. (한 줄 개념 — 활성화 방법, 파일 구조, 우선순위 등 구체 없음)

**꼬리질문 9-1** (rationale 시나리오 — 운영 사고 방어): 프로파일 지정을 깜빡하고 운영 장비에서 기동하면? "운영이 엉뚱한 설정으로 붙는" 사고를 구조적으로 막으려면?

**꼬리질문 9-2** (힌트: 사고 전제는 기본 yml에 로컬 DB 정보가 있다는 것): 기본 yml에서 뭘 빼고 어디로 옮기면?

### [Q10] AOP 동작 원리 (JDK Dynamic Proxy vs CGLIB) — **하**

**본질문 답변 요지**: 프록시 객체가 전작업→메인 메서드 호출→후작업→리턴 (감싸기 골격 정확). JDK vs CGLIB 차이는 "프록시를 언제 만드는지"로 오답 추측.

**꼬리질문 10-1** (추론 유도): 프록시는 원본과 "같은 타입인 척"해야 한다 — 자바에서 같은 타입인 척하는 두 가지 방법은?
- 답변: "인터페이스냐 추상 클래스냐" (절반 — 인터페이스는 맞음, 상속 개념에는 접근했으나 추상 클래스로 한정)
- 교정: JDK Proxy = 인터페이스 구현, CGLIB = 구체 클래스를 런타임 상속(바이트코드 자식 클래스 생성)

**꼬리질문 10-2**: CGLIB이 상속 기반이라면 프록시가 안 만들어지거나 부가 기능이 안 걸리는 경우는? (final 유도)
- 답변 1: "이미 상속을 받은 클래스인 경우" (오답 — 프록시가 대상을 상속하므로 무관)
- 힌트(상속/오버라이드 금지 키워드) 후 답변 2: 같은 주장 반복 → 재차 되물은 뒤 "final이 붙은 클래스?"로 도달 (힌트 2회 후 도달)

**꼬리질문 10-3**: final이 클래스에 붙었을 때 vs 메서드에 붙었을 때 각각 무슨 일? 어느 쪽이 악질인가?
- 답변: "잘 모르겠다"
- 면접관 보충: `final` 클래스 = 상속 불가 → 프록시 생성 실패(기동 에러). `final` 메서드 = 프록시는 생성되나 오버라이드 불가 → **그 메서드만 조용히 부가 기능 미적용**(@Transactional 붙였는데 트랜잭션 없이 실행 — 가장 악질적인 유형). private 메서드도 동일하게 미적용. 부트 기본값은 CGLIB(proxyTargetClass=true), 인터페이스 없는 빈도 프록시 가능하게 하기 위함.

**메모**: 프록시 감싸기 큰 그림만 있고 두 방식의 정체(인터페이스 구현 vs 상속)를 몰랐음. 강한 힌트(금지 키워드)에도 final 미도달 — 상속 제약(final)과 프록시 한계를 연결하는 사고가 없음. rationale(127)이 노리는 "붙였는데 동작 안 함을 이해하는 기반" 미달. 다음 질문(자기 호출)과 연계 재검증.

### [Q11] 자기 호출 시 @Transactional 미적용 이유 / 해결 — **상**

**본질문 답변 요지**: "같은 클래스 메서드라면 이미 프록시 없이 원본에 들어와 있는 상태라 프록시 객체를 사용할 수 없다" — 메커니즘 정확(즉답, 힌트 없음). 해결책: "메서드를 다른 클래스(빈)로 분리해 그걸 쓰게 한다" — 정석 도달.

**꼬리질문 11-1** (rationale — 코드 리뷰로 잡는 능력): 에러 없이 조용히 도는 버그 — 리뷰에서 어떤 패턴을 보면 의심? 잡아본 경험은?
- 답변: "public 메서드 내부에서 자신의 다른 public 메서드를 호출하는지 확인" (방향 맞음, 조건 부정확 / 경험담은 무응답)

**꼬리질문 11-2**: 정확히 어떤 조건일 때 버그? 같은 이유로 미적용되는 다른 애너테이션은?
- 답변: "내부 호출 + 호출당하는 메서드에 트랜잭션 애너테이션" (정확) → "내가 만든 애너테이션 + Aspect 구현한 것도 똑같다" (**커스텀 AOP로 일반화 — 프록시 모델을 원리로 이해한 신호**. 단 @Cacheable/@Async 같은 대표 내장 애너테이션 이름은 미언급)
- 면접관 보충: 대표적으로 @Cacheable(내부 호출 시 캐시 미적용), @Async(동기로 실행됨), @Retryable, 메서드 시큐리티(@PreAuthorize). 지양하는 해결책 = self-injection(자기 자신 주입)과 AopContext.currentProxy(exposeProxy) — 동작은 하나 설계 냄새.

**메모**: 이 섹션 최고 수행. 원리·해결책 즉답 + 커스텀 Aspect로의 일반화까지. 유의: 직전에 요청으로 작성된 @Transactional knowledge 문서에 자기 호출 절이 포함되어 있어 학습 직후 효과일 수 있음 — 시차를 두고 재확인 가치. 경험담(실제 잡아본 사례)은 끝내 안 나옴.

### [Q12] 전파: REQUIRED vs REQUIRES_NEW 차이·실무 사례 — **상**

**본질문 답변 요지**: REQUIRED = 기존 트랜잭션 있으면 합류, REQUIRES_NEW = 무조건 새 트랜잭션 (정확). 활용은 "기존 데이터와 상관없이 롤백해야 하는 상황"으로 다소 추상적.

**꼬리질문 12-1**: 구체적 업무 시나리오는? 어떤 성격의 데이터가 본 처리와 운명 분리되어야 하나?
- 답변: **"로그인 실패해도 실패 사유는 저장해야 할 때"** — 자기 도메인(IAM)에서 나온 정확한 사례. 본 트랜잭션 롤백과 무관하게 감사/이력은 남아야 함 = REQUIRES_NEW 정석 용례.

**꼬리질문 12-2** (역방향 메커니즘): REQUIRES_NEW 안쪽 예외를 바깥이 안 잡으면? "분리됐으니 바깥 무사"가 맞나?
- 답변: "바깥도 예외가 던져지기 때문에 롤백된다" (정확 — 트랜잭션 분리 ≠ 예외 격리)

**메모**: Q7에서 학습한 내용의 연장선이긴 하나, 실무 사례를 자기 도메인에서 즉시 꺼낸 것과 예외 전파/트랜잭션 분리를 혼동하지 않은 것은 진짜 이해의 신호. 트레이드오프(커넥션 2개 점유)는 Q7에서 보충된 바 있어 재확인 생략.

### [Q13] @Transactional(readOnly = true)의 실제 최적화 — **하**

**본질문 답변 요지**: "정확하게 모르겠다" (즉답 포기 — 꼬리질문 없이 종료. knowledge 문서 작성 요청)

- 면접관 보충(핵심만): 실효의 핵심은 하이버네이트 — 플러시 모드 MANUAL로 커밋 시 flush 생략 + 더티 체킹용 스냅샷 유지 부담 제거(대량 조회 시 메모리/CPU 절약). JDBC 드라이버에는 setReadOnly 힌트(드라이버/DB별 상이). 리더/리플리카 분리 환경에서는 리플리카 라우팅 근거. 단 쓰기를 "막아주는" 안전장치가 아니라 힌트 — 변경이 조용히 무시될 수 있음.

**메모**: readOnly를 관례로 붙여왔을 텐데 "왜"는 모름 — Auto Configuration과 같은 유형(매일 쓰는 것의 원리 공백). 재도전 대상.

### [Q14] 트랜잭션 격리 수준 4가지 / 이상 현상 — **하**

**본질문 답변 요지**: "잘 모르겠다" (즉답 포기 — 꼬리질문 없이 종료. knowledge 문서 작성 요청)

- 면접관 보충(핵심만): READ UNCOMMITTED(dirty read 허용) → READ COMMITTED(non-repeatable read 가능) → REPEATABLE READ(phantom read 가능) → SERIALIZABLE. dirty = 커밋 안 된 걸 읽음, non-repeatable = 같은 행 두 번 읽었는데 값이 다름(UPDATE), phantom = 같은 조건 재조회 시 행 개수가 다름(INSERT). MySQL InnoDB 기본은 REPEATABLE READ(MVCC+갭 락으로 phantom 상당 부분 차단), PostgreSQL/Oracle은 READ COMMITTED.

**메모**: DB 기초 대구멍. "같은 트랜잭션에서 두 번 읽었는데 값이 달라요" 류 버그 리포트를 추적할 수 없는 상태. 4장(RDB/SQL) 섹션에서 정면 재검증 예정 — 재도전 필수.

### [Q15] @Async 동작 원리와 주의점 — **중**

**본질문 답변 요지**: 프록시로 새 스레드에서 실행 / 요청 많으면 풀 부족→대기 길어지고 다른 스레드에 영향 / 예외가 조용히 묻히므로 잡아서 처리해야 함. (세 관점을 자발적으로 모두 스케치 — 프록시 학습이 이어지고 있음)

**꼬리질문 15-1**: 예외가 항상 묻히나? 리턴 타입에 따른 예외의 운명은?
- 답변: "void가 아니면 받을 수 있지 않아?" (방향 맞음 — Future/CompletableFuture에 담겨 get()/join() 시점에 수령. 단 확인 안 하면 똑같이 묻힘, void는 AsyncUncaughtExceptionHandler행 — 보충으로 정리)

**꼬리질문 15-2** (시나리오): 부트 기본 설정에서 동시 처리가 8개에서 안 늘어남 — 왜? (힌트: core/max/queue)
- 답변: "기본값이 8로 보인다, 더 늘릴 수 있어 보인다" (core=8은 인지, **큐 무제한 함정 미도달**)
- 면접관 보충: ThreadPoolTaskExecutor는 **큐가 가득 차야** core를 넘어 max까지 스레드를 늘리는데, 부트 기본 queue-capacity가 사실상 무제한(Integer.MAX_VALUE) → 큐가 영원히 안 차서 스레드가 8개에서 고정, 작업은 큐에 쌓여 지연/OOM 위험. max-size만 늘려도 소용없고 queue-capacity를 함께 제한해야 함. 추가 주의점: 새 스레드에는 트랜잭션·SecurityContext·MDC가 전파되지 않음(TaskDecorator로 복사).

**메모**: 세 관점 자발 스케치는 좋았으나 각 깊이 1단계에서 멈춤 — 예외는 유도로 도달, 풀 메커니즘(큐→max 순서)은 미도달. "써봤지만 설정을 튜닝해본 적은 없는" 수준의 전형적 프로필.

### [Q16] Spring Event / @TransactionalEventListener — **상**

**본질문 답변 요지**: 활용 경험 있음. @TransactionalEventListener는 "커밋 후 로직 수행"에 유용. (한 줄이지만 정확)

**꼬리질문 16-1** (경험 검증): 어떤 기능에서 무엇의 결합을 끊었나? 왜 직접 호출이 아니라 이벤트였나?
- 답변: **설정 변경 → 커밋 후 Redis의 사용자 토큰 blocking** (IAM 실무). 이유: "설정 변경이 커밋된 후에 캐시 값이 수정되어야 하므로" — 외부 저장소(Redis)는 트랜잭션 미참여 → 커밋 확정 후 반영이라는 AFTER_COMMIT 정석 근거. 진짜 경험으로 판정.

**꼬리질문 16-2** (실패 경로): AFTER_COMMIT 리스너의 Redis 블로킹이 실패하면? DB엔 차단 설정이 커밋됐는데 토큰은 살아있는 보안 불일치 — 방어는?
- 답변: ① **토큰 30분 리프레시 주기가 불일치의 상한 — 스펙으로 수용** (bounded risk 의사결정, 시니어다운 답) ② retry ③ 예외 잡고 DB 롤백 직접 수행

**꼬리질문 16-3** (반론): 커밋 확정 후엔 롤백이 없다 — ③이 실제로 의미해야 하는 것과 허점은?
- 답변: "커밋 이후 다시 쿼리를 날리고 다시 커밋" — **보상 트랜잭션** 개념에 도달(용어는 미사용). 허점 분석은 미도달.
- 면접관 보충: 허점 = (a) 원 커밋~보상 커밋 사이 다른 트랜잭션이 "차단됨" 상태를 읽었을 수 있음 (b) 보상 쓰기 자체도 실패 가능(무한 후퇴 — 그래서 retry+상한+모니터링 조합이 현실해) (c) AFTER_COMMIT 리스너에서 DB 쓰기는 기본으로는 커밋 안 되는 함정(이미 끝난 트랜잭션에 편승) — REQUIRES_NEW 필요. phase 어휘: BEFORE_COMMIT/AFTER_COMMIT(기본)/AFTER_ROLLBACK/AFTER_COMPLETION.

**메모**: 자기 도메인의 실제 설계 + 실패 경로에 3개 대안 + TTL 상한 수용이라는 스펙 레벨 판단 — 이 섹션에서 경험의 진위가 가장 확실히 드러난 스레드. 부족한 건 어휘(보상 트랜잭션, phase 이름)와 허점 분석의 끝단.

### [Q17] Bean 순환 참조 원인과 해결 — **중**

**본질문 답변 요지**: 원인 = 의존성 주입 체인이 자기 자신으로 되돌아오는 경우 (정확). 해결 = 새 상위 클래스를 만들어 순환 당사자들을 참조시키고 다른 클래스는 상위를 사용 (구조 개선 — 추출로 의존 방향 정리, A→B→A를 C→A,C→B로. 정석을 우회책보다 먼저 꺼냄).

**꼬리질문 17-1**: 스프링 장치만으로 기동을 통과시키는 우회 방법은? 순환은 설계 관점에서 무슨 신호?
- 답변: "우회 방법은 모르겠다. 순환참조 발생은 클래스 설계가 잘못됐다는 신호" (설계 본능은 있으나 얇음, 우회 장치 어휘 전무)
- 면접관 보충: 우회 = `@Lazy`(프록시를 꽂아 실제 주입을 첫 사용 시점으로 지연), setter/필드 주입(생성 후 채움이라 기동 통과 — Q3의 3단계 캐시), `spring.main.allow-circular-references=true`(부트 2.6+부터 기본 금지라 이 플래그가 필요). 전부 기동만 통과시키는 미봉책. "잘못된 설계"의 정체 = 순환하는 두 클래스가 **숨은 제3의 책임을 나눠 가진 것** — 그래서 해결이 그 책임의 추출(C)이 됨. 이벤트로 결합 끊기(Q16 연계)도 대안.

**메모**: 설계 우선 본능(구조 개선을 먼저)은 플러스 — 세션 전반의 패턴("방향은 알고 어휘·메커니즘이 없음")이 여기서도. @Lazy 존재 자체를 모르는 건 우회책 유혹을 겪어본 적이 없다는 뜻이기도.

### [Q18] RestTemplate / WebClient / RestClient 차이·선택 기준 — **하**

**본질문 답변 요지**: "비동기, api 요청 옵션 차이 아니야?" (뭉뚱그림)

**꼬리질문 18-1**: 셋 중 어느 게 동기/비동기? 새 프로젝트라면 뭘 고르나?
- 답변: "이건 그냥 AI한테 물어보면 되는 것 아니냐" (푸시백 — 절반은 유효하나 판단 기준 제시 없이 꺼낸 카드)

**꼬리질문 18-1 수정** (AI 시대 판단형으로 변환): AI가 "최신이니 WebClient"를 권했고 팀원이 평범한 MVC(톰캣) 앱에 도입하려 함 — 리뷰어로서 승인? 판단에 뭘 알아야?
- 답변: "우선 WebClient에 대해 알아야 한다" (동어반복 — 실행 모델 지식 전무 확인)
- 면접관 보충: RestTemplate=동기·유지보수 모드 / WebClient=논블로킹·리액티브(MVC에서 block()이면 이점 없이 복잡도만) / RestClient=6.1+ 동기+모던 API, 사실상 후계자. 판단 기준 = **실행 모델이 앱 스택과 맞는가** — AI는 "무엇이 최신인지"는 알아도 "우리 앱의 스레드 모델"은 모름.

**메모**: HTTP 클라이언트 3종의 위치조차 없음 — 외부 API 연동 경험이 얕거나 RestTemplate만 관성으로 써온 프로필. "AI한테 물으면 된다" 푸시백은 판단 기준을 보여준 뒤에 꺼냈으면 유효한 카드였음 — 태도 코칭 제공. 재도전 대상.

### [Q19] @ControllerAdvice 전역 예외 처리 / 에러 응답 표준화 — **중**

**본질문 답변 요지**: ControllerAdvice에서 예외를 잡고, 커스텀 에러 응답 클래스를 만들어 항상 그걸로 리턴 (골격 정확).

**꼬리질문 19-1**: 에러 응답 클래스에 담을 필드 / 절대 담으면 안 되는 것?
- 답변: 에러코드 + 사용자 메시지 + 메시지 인자. 금지 = 개인정보. (방향 맞음. 스택트레이스/내부 구현 상세(클래스명·SQL·경로) = 정보 노출 취약점은 보충으로 채움)

**꼬리질문 19-2** (운영 연결): 고객이 가진 건 에러 화면뿐 — 수백만 줄 로그에서 그 요청을 찾으려면 응답에 뭐가 더 필요? (Q6 trace id 연결 유도)
- 답변: "사용자 아이디를 담고 ControllerAdvice에서 로그를 찍어야" — **trace id 미도달** (명시적 연결 힌트에도). 사용자 ID는 사용자까지만 좁히고 요청 단위 특정 불가 + 본인이 말한 개인정보 금지와 긴장.
- 면접관 보충: 정답은 **trace id를 에러 응답에 포함** — 고객이 문의에 그 값을 첨부하면 로그에서 요청 단위로 즉시 특정(Q6 필터→MDC의 열매). ControllerAdvice 로깅은 좋은 포인트 — 비즈니스 예외 warn / 시스템 예외 error+알람으로 레벨 구분, 마지막 안전망(Exception.class) 필수. 표준화 어휘로 ProblemDetail(RFC 7807, 스프링 6) 존재도 언급 가치.

**[사후 논쟁 — 후보자 발의]** "traceId를 응답에 담을 필요 없다" 논제로 토론 요청.
- 후보자 논거: ① 고객이 그 값을 전달해줄 리 없음 ② 전달 안 되면 무의미 ③ 최우선은 사용자 ID를 에러 로그에 찍고, 그 로그에 연결된 traceId로 흐름 추적 (= 무용론이 아니라 "서버 로그 피벗" 포지션으로 정교화됨)
- 면접관 반례 ①(B2B 문의 주체는 IT 관리자, ref 코드 UX 실제 작동): "관리자가 아닐 수도 있고 에러 UI에 항상 노출은 과하다"로 방어 — UX 트레이드오프 논거, 부분 타당
- 면접관 반례 ②(로그인 실패엔 사용자 ID가 없다): **"로그인 시도 자체에서 아이디를 추출 가능 — 로그인 아이디만으로 특정 가능"**으로 방어 — 도메인 사실 기반의 유효한 반박 (실패 로그인도 시도된 식별자를 로그에 남김)
- 남는 엣지(면접관 정리): 식별자 자체가 없는 요청(바디 파싱 실패, 게이트웨이 레벨 에러, 변조된 토큰), 동일 사용자 반복 시도 중 특정 문제. 결론 = 두 전략은 경쟁이 아니라 보완 — 식별자 피벗이 주 경로, 응답 ref id는 식별자 없는 케이스의 저비용 폴백. 문의 채널 특성으로 선택하는 트레이드오프.

**메모**: 실무 골격(Advice+표준 응답+코드/메시지)은 있음. trace id 연결은 처음엔 미도달였으나, **사후 토론에서 도메인 사실(로그인 시도 아이디 추출)로 반례를 방어하는 모습은 세션 통틀어 가장 시니어다운 순간** — 자기 주장을 근거로 지키는 힘 확인. 평가는 중 유지하되 토론 태도는 확실한 플러스.

### [Q20] @Cacheable 동작 원리와 함정 — **중** (하 경계)

**본질문 답변 요지**: 프록시가 캐시 조회, 있으면 캐시 반환/없으면 로직 실행 (원리 정확). 함정 ① "정밀한 옵션이 안 된다 — 미스 시 DB 조회 후 캐시 저장 후 반환이 안 된다" (**오답 — 그게 기본 동작**) ② 자기 호출 미적용 (정확 — 프록시 일반화 유지).

**꼬리질문 20-1** (반론): 미스→실행→저장→반환이 기본 동작인데? 무슨 상황을 말한 건가?
- 답변: "그럼 캐시에 저장하지 않고 바로 리턴하는 게 안 되는 것이다" (**재오답** — condition/unless가 정확히 그 용도. unless="#result == null", sync=true 등 속성 미인지)

**꼬리질문 20-2**: null 리턴은 캐시되나? 각각의 문제는? / TTL은 어디서 설정?
- 답변: "잘 모르겠다"
- 면접관 보충: null 캐싱 = "없음"이 TTL 동안 고정 vs 미캐싱 = 없는 키 반복 조회가 DB 관통(cache penetration). **TTL은 @Cacheable 속성에 없음** — 추상화가 만료를 다루지 않아 구현체 설정(RedisCacheConfiguration.entryTtl, Caffeine expireAfterWrite)에서. 키 설계: 기본 SimpleKeyGenerator(파라미터 조합), 멀티테넌트에서 테넌트 ID 누락 시 타사 데이터 유출.

**메모**: 원리+자기 호출은 프록시 학습의 일반화로 커버. 그러나 "안 된다"고 두 번 확신한 것이 둘 다 되는 기능이었음 — **모르는 것을 한계로 단정하는 습관**이 이 스레드에서 노출(못 써본 속성 = 없는 기능). null/TTL/키 설계 전부 공백. @Cacheable을 애너테이션 한 줄로만 써본 프로필.

### [Q21] Bean Validation vs 도메인 검증 역할 분담 — **상**

**본질문 답변 요지**: 형식/구문(null·공백)은 애너테이션, 설정·상태 의존 비즈니스 규칙(예: "비밀번호 3글자 연속 중복 금지 설정이 on인 경우" — IAM 실무 사례) + 커스텀 에러 응답 필요 시 도메인 검증. 중복은 "검증 주체 룰"로 방지. (분담 기준 명확 + 자기 도메인 예시)

**꼬리질문 21-1** (경계 사례): 이메일 중복 검사는 어느 계층? 검증 통과한 두 요청이 동시에 오면? 최종 방어선은?
- 답변: DB 조회 필요 + 비즈니스 스펙 → 도메인 검증. 동시 요청은 "마지막 DB 유니크 설정으로 하나가 탈락" (정확 — 검증은 확률 감소, 제약은 보장이라는 층위 구분)

**꼬리질문 21-2** (조합): 탈락한 요청의 제약 위반 예외를 어떻게 "이미 사용 중인 이메일" 응답으로?
- 답변: "DB 저장 로직이 있는 부분에서 잡아 커스텀 예외로 변경 후 던진다" (정확 — 저장 계층에서 번역 → ControllerAdvice가 표준 응답 렌더. Q4 예외 변환 + Q19 전역 처리의 조합)
- 면접관 보충: 잡는 대상의 이름 — DataIntegrityViolationException/DuplicateKeyException(@Repository 예외 변환의 산물).

**메모**: 중급 12문항의 마무리로 좋은 수행. 분담 기준·심층 방어(defense in depth)·예외 번역 흐름을 자기 언어로 조합. 예외 타입 이름 부재는 세션 공통 패턴이나 구조 이해는 확실.

### [Q22] 트랜잭션 안의 외부 API 호출 — **상**

**본질문 답변 요지**: 커넥션을 문 채 외부 호출 → 커넥션 소비 → 다른 요청이 커넥션 대기 (정확). 설계 변경: 트랜잭션 진입 전에 API를 먼저 호출 (1차 해법 정확).

**꼬리질문 22-1** (연쇄 시뮬레이션: 결제사 3초 지연, 풀 10, 톰캣 200, 20req/s): 커넥션 레벨 연쇄 정확 — 결제 요청이 풀 독점(60 동시 필요 vs 10), 나머지 API 대기→타임아웃.
**꼬리질문 22-2** (힌트: 대기 중 무엇을 쥐고 있나): DB 무관 기능까지 죽는 이유 = 커넥션 대기 요청들이 톰캣 스레드를 물고 있어 스레드 풀 고갈 (정확 — 연쇄 완성. 헬스체크 사망→LB 제외까지 보충)
**꼬리질문 22-3** (API 먼저 방식의 잔여 위험: API 성공 후 DB 롤백): ① 롤백 시 결제 취소 API 호출 ② 커밋 먼저 후 API, 실패 시 역방향 보상 — 양방향 보상 패턴 (Q16 개념 이식)
**꼬리질문 22-4** (보상 직전 서버 사망/보상 실패): **"결제 시도·결과를 우리 DB에 저장 + 매일 배치로 재요청하는 보완 시스템"** — 내구성 있는 상태 기록 + 대사(reconciliation) 골격 자발 도달 (사가 상태 기록의 실질)
**꼬리질문 22-5** (그 기록을 본 트랜잭션 안에 INSERT하면?): "스프링 이벤트처럼 커밋 후 적용" — **오답**. AFTER_COMMIT은 롤백 시 실행되지 않고, 시도 기록은 API 호출 **전에** 미리 내구화(write-ahead)돼야 함. 정답 = **REQUIRES_NEW 별도 트랜잭션** (Q12 로그인 실패 이력과 동일 패턴): "시도" 상태로 선커밋 → API 호출 → 상태 갱신, 배치는 "시도" 상태로 방치된 레코드를 대사.

**메모**: ⭐⭐⭐ 첫 문항에서 연쇄 시뮬레이션(단계마다 넛지는 필요했으나 추론은 본인 것), 양방향 보상, 내구 기록+대사까지 — 장애 사고력의 골격은 실제로 있음. 마지막 함정(REQUIRES_NEW vs AFTER_COMMIT의 용도 구분 — 롤백에도 살아남아야 하는 기록)은 미도달: 학습한 도구들의 적용 조건을 아직 혼용함.

### [Q23] 커밋 후 이벤트 발행 보장 (Transactional Outbox) — **중** (상 경계)

**본질문 답변 요지**: 커밋 후 발행 + "발행함과 동시에 DB에 발행 기록" + 소비측 처리 기록. (**이중 쓰기 결함** — 발행과 기록이 별개 시스템이라 원자성 없음, 커밋~발행 사이 사망 시 재시도 트리거 부재)

**꼬리질문 23-1** (①커밋~②발행 사이 사망 — 무엇이 재시도를 트리거? "발행 필요" 기록은 어느 트랜잭션에?): "1번(비즈니스 트랜잭션)에서 이벤트 발행 필요를 저장해야 한다" — **같은 트랜잭션 원자 기록 = Outbox 핵심** 도달 (Q22 write-ahead 힌트 활용)

**꼬리질문 23-2** (발행 주체는? 발행 완료 표시 직전 사망 시 소비자에 필요한 것은?):
- 1: "발행 대기를 작성한 주체가 발행" — **미완**. 작성 주체(요청 스레드)가 죽으면 재시도 주체가 없음 — 정답은 **별도 릴레이**(폴러/스케줄러가 미발행 레코드 스캔, 또는 CDC/Debezium). 작성자 즉시 발행은 지연 최적화일 뿐, 안전망은 릴레이.
- 2: "재기동하면 다시 발행 → 소비자는 이미 처리했는지 데이터로 보관" — **정확** (at-least-once → 멱등 소비자 자발 도달)

**메모**: Q16(AFTER_COMMIT 실패 경로)→Q22(내구 기록+대사)→Q23(outbox) 3연전으로 개념이 점증적으로 쌓이는 게 보임. 같은-트랜잭션 원자 기록은 힌트로, 멱등 소비자는 자발로. 남은 구멍 = **릴레이의 존재 이유**(발행의 책임을 요청 스레드에서 떼어내는 것). "Transactional Outbox/at-least-once/멱등성" 용어 세트 장착 필요.

### [Q24] 트랜잭션 동기화(TransactionSynchronizationManager)와 커넥션 바인딩 — **중**

**본질문 답변 요지**: "쓰레드가 커넥션을 갖고 있고 그 하나를 계속 사용" — 방향은 맞으나 내부 메커니즘(리소스 맵, DataSourceUtils 경유 획득)은 설명 못 함.

**꼬리질문 24-1** (@Async/CompletableFuture로 다른 스레드에서 DB 작업 시 트랜잭션 참여?): "참여 못 한다, 커넥션이 ThreadLocal에 있기 때문" — **ThreadLocal 바인딩 자발 도달**. 단 "ThreadLocal을 물려주면 가능하다"는 위험한 주장 덧붙임.
**꼬리질문 24-2** (물려줘서 두 스레드가 같은 커넥션을 쓰면 안전한가?): "원 스레드 종료 시 커넥션이 반환되는데 다른 스레드가 계속 사용해 문제" — 라이프사이클 위험은 자발 도출. 미언급: 풀이 그 커넥션을 **제3의 요청에 재대여**해 두 트랜잭션이 섞이는 것, JDBC Connection 자체가 비스레드세이프라 애초에 깨진 설계라는 점.
**꼬리질문 24-3** (@Async 안에서 DB 쓰기 필요 시 정석 + 원 트랜잭션과의 정합성?): "새 트랜잭션 분리" 정답. 정합성은 "저장 전 원 데이터 커밋 여부 조회" — **레이스 있는 답** (조회 시점에 커밋 전이면 유실).
**꼬리질문 24-4** (그 레이스는? 커밋 이후에만 시작을 보장하는 장치?): "커밋 이후 실행하도록 한다" — 방향만, 장치명 미제시.
**꼬리질문 24-5** (구체적 어노테이션/API?): "**@TransactionalEventListener의 AFTER_COMMIT**" — 정답 (Q16·Q23 학습이 안착된 증거).

**메모**: ThreadLocal 바인딩과 비동기 경계의 단절은 자기 것이 됐고, AFTER_COMMIT으로의 수렴도 이번엔 스스로 해냄(3연전 학습 효과). 그러나 본질문의 출제 의도인 **내부 구조**(TransactionSynchronizationManager의 리소스 맵에 DataSource→ConnectionHolder 바인딩, DataSourceUtils.getConnection이 그걸 먼저 조회, JdbcTemplate/JPA가 같은 커넥션을 공유하게 되는 원리)는 미도달. "물려주면 가능" 같은 발상이 나온 것도 커넥션 공유의 위험(비스레드세이프, 풀 재대여)이 체화되지 않은 신호.

### [Q25] 톰캣 스레드풀 / HikariCP 크기 산정 — **중**

**본질문 답변 요지**: "코어 수 기반 + I/O 바운드 vs CPU 바운드 구분" — 축은 맞으나 계산 없음.

**꼬리질문 25-1** (구체 조건: 4코어, 응답 100ms 중 DB 점유 50ms, 목표 500 TPS — 각각 몇?): 스레드=코어수 4에서 출발 → DB 점유가 절반이니 2배(8) → 여유분 +2 → 스레드 10/커넥션 10. **단위 오류**(4스레드×100ms를 240 TPS로 계산, 실제 40 TPS). 스레드가 100ms 내내 CPU를 쓴다는 전제.
**꼬리질문 25-2** (검산 + 100ms 중 스레드는 뭘 하나 + 동시 진행 요청 수는?): **동시 50개 자발 도달(Little's law 핵심 획득)**. 그러나 "DB 대기 50ms 동안 스레드가 다른 요청을 처리한다"는 **논블로킹 모델 혼입 오개념** → 톰캣 25/커넥션 50으로 **거꾸로 배정**. "4코어=커널 스레드 4개인데 톰캣 스레드 25개가 가능한가?"라고 코어-스레드 관계 혼란을 솔직히 자백.
**꼬리질문 25-3** (힌트 2개: 블로킹 JDBC 스레드는 대기 중 아무것도 못 함 / 코어 수는 '동시 실행' 제한이지 '존재 가능 스레드 수' 제한 아님 — 다시 배정): "요청이 스레드를 100ms 잡음→50개, 커넥션을 50ms 잡음→25개" — **정확** (톰캣 50 / Hikari 25).

**메모**: rationale이 거르려는 "코어 수 앵커" 답변으로 출발 — 블로킹 서블릿 모델에서 스레드가 대기 시간 내내 묶인다는 사실, 코어 수는 CPU 동시 실행 상한일 뿐이라는 사실이 체화 안 됨(WebFlux식 서사와 혼재). 반면 유도하자 Little's law(동시수 = TPS × 체류시간)에 스스로 도달했고, 힌트 후 점유 시간 비례 배정을 정확히 해냄 — 계산 골격을 이번에 획득. 모범답 보충: 톰캣 = TPS×전체 응답시간(50)+여유, Hikari = TPS×커넥션 점유시간(25), 코어 수는 CPU 바운드 구간과 컨텍스트 스위칭 비용의 상한으로만 작용, 최종 숫자는 부하 테스트·메트릭(active threads, connection acquire wait)으로 검증.

### [Q26] HikariCP 커넥션 고갈 — 원인 후보와 진단 — **중** (하 경계)

**본질문 답변 요지**: 원인 후보 2개 — 커넥션 물고 CPU 집약 작업 / 커넥션 물고 외부 API 호출("오래 점유" 계열만). 대책 = 로직 재배치로 순수 DB 작업에만 커넥션 사용. 누수·느린 쿼리·풀 크기 부족 등 다른 후보와 "확인 방법"의 구체 수단 없음.

**꼬리질문 26-1** (장애 진행 중, 코드 전에 뭘 보고 점유자를 특정? 앱/DB 양쪽 도구·메트릭·명령): "트레이스 분석으로 오래 물고 있는 것 확인, DB에서는 느린 쿼리 확인" — 방향만 (APM 트레이스·슬로우 쿼리 로그 수준. 스레드 덤프, 풀 메트릭, PROCESSLIST 등 미언급)
**꼬리질문 26-2** (조건 변형: 느린 쿼리 없음·DB 한가·active=max에서 안 내려옴·대기만 누적 — 무슨 상황? 잡아내는 HikariCP 기능은?): 앞의 답 반복("트랜잭션 잡고 I/O/CPU 작업") — **누수(미반환) 개념 미도달**, leakDetectionThreshold 모름.

**메모**: Q22에서 학습한 "트랜잭션 내 외부 호출" 원인은 자기 것이 됐으나, 이 질문의 본령인 **감별 진단 방법론**(원인 후보 매트릭스 → 각각의 배제 수단)이 없음. 특히 "오래 점유"와 "아예 미반환(누수)"을 구분 못 함 — 쿼리가 빠른데 active가 안 내려오는 시나리오를 줘도 같은 답 반복. 모범답 보충: 후보 4계열 ① 풀 크기 부족(트래픽 증가 — 풀 메트릭 추이로 확인) ② 느린 쿼리·락 대기(슬로우 쿼리 로그, SHOW PROCESSLIST/pg_stat_activity) ③ 트랜잭션 내 외부 호출·CPU 작업(APM 트레이스 스팬) ④ **커넥션 누수**(수동 getConnection 후 close 누락 등 — `leakDetectionThreshold`로 미반환 커넥션의 획득 스택트레이스 로깅, 스레드 덤프로 잡은 스레드의 블록 지점 확인, DB의 idle in transaction). 진단은 "메트릭으로 계열 좁히기 → 계열별 배제"의 순서.

### [Q27] WebFlux vs MVC 스레딩 모델 / WebFlux가 독이 되는 경우 — **하**

**본질문 답변 요지**: "WebFlux=비동기 처리용, MVC=동기+트랜잭션용, 동기 수행이 필요하면 WebFlux가 독" — 용도 라벨만, 스레딩 모델 설명 없음.

**꼬리질문 27-1** (Netty는 스레드 몇 개? 적은 수로 어떻게 수만 동시 요청? DB 대기 50ms 동안 스레드는?): "정확하게 모르겠다" — 즉답 포기.

- 면접관 보충(핵심만): MVC=thread-per-request(대기=점유, 톰캣 200=동시 상한) / WebFlux(Netty)=이벤트 루프 스레드 ≈ 코어 수, 논블로킹 I/O로 대기=반납(콜백 등록 후 다음 이벤트 처리). 독이 되는 조건 = 이벤트 루프 위 블로킹 호출(JDBC — 4개 중 1개 막힘의 폭발 반경), CPU 바운드, 팀 학습·디버깅 비용. Q25의 "대기 중 스레드가 다른 요청 처리" 오개념이 사실 WebFlux 모델이었다는 연결 고리 제시.

**메모**: Q25에서 두 모델을 섞어 쓰던 것과 일관된 구멍 — 블로킹/논블로킹 스레딩 모델의 구분이 아직 어휘·메커니즘 수준에서 없음. rationale 기준(튜토리얼 수준 vs 운영 수준)에서 튜토리얼 이하. knowledge 문서(webflux-vs-mvc-threading-model.md)로 정리, 재도전 필수.

### [Q28] Graceful shutdown / 무중단 배포 — **중**

**본질문 답변 요지**: "톰캣 셧다운 옵션을 graceful로 + 배포 시 구버전을 LB에서 제외" — 앱/인프라 두 축의 골격은 정답, 구체 메커니즘 없음.

**꼬리질문 28-1** (SIGTERM 수신 시 내부 동작 — 신규/진행 중/무한정?): "새 요청은 안 들어오(는 것 아닌가), 진행 중은 마저 처리, 오래 걸리면 정해진 시간에 강제 종료" — 3요소 모두 방향 정확 (`timeout-per-shutdown-phase` 어휘는 없음)
**꼬리질문 28-2** (LB가 아직 트래픽을 보내는데 앱이 거부 시작하는 레이스 — "LB 제외 먼저, SIGTERM 나중" 순서를 어떻게 보장?): "잘 모르겠다" — 즉답 포기.

- 면접관 보충(핵심만): LB 제외는 비동기 전파 → 패턴 = ① 트래픽 차단 신호 ② 전파 대기 ③ SIGTERM. K8s는 엔드포인트 제거와 SIGTERM이 동시·비동기 진행이 함정 — preStop sleep 10~15s + terminationGracePeriodSeconds > (preStop+graceful timeout). VM+LB는 디레지스터→connection draining 대기→SIGTERM. 역할 분담: 앱 graceful=이미 들어온 요청 보호 / 인프라=새 요청 차단 / 배포 절차=순서 보장.

**메모**: 두 축을 자발적으로 짚은 건 이 주제를 문제로 인식해본 흔적(rationale 절반 충족). 그러나 변별 지점인 **순서 조율(레이스)**은 미도달 — "배포 때마다 소량 에러"의 진범을 특정 못 함. knowledge 문서(graceful-shutdown-zero-downtime-deploy.md) 정리.

- 면접관 보충(핵심만): FilterChainProxy의 순서 있는 필터 목록 — SecurityContextHolderFilter(복원) → 인증 필터들(credential 추출→AuthenticationManager 위임→성공 시 SecurityContextHolder(ThreadLocal)에 저장) → ExceptionTranslationFilter → **AuthorizationFilter(인가, 맨 끝)**. 커스텀 토큰 필터 = addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class), 이유 = 인가 판정 전 SecurityContext 채움. 암기 3문장: "인증은 중간(컨텍스트 저장), 인가는 맨 끝, 커스텀은 addFilterBefore".

**메모**: Q6(Security=필터 체인 무지)과 동일 계열 구멍 — IAM 종사자로서 최우선 보완 대상. 섹션 26(인증/인가/세션)에서 재검증 예정. knowledge 문서(spring-security-filter-chain-authentication.md) 에이전트 위임.

### [Q32] 애플리케이션 시작 시간 급증 — 추적과 개선 — **하**

**본질문 답변 요지**: "부트 로그를 살펴보고 AI한테 문제 분석해달라고 한다."

**꼬리질문 32-1** (로그에서 구체적으로 뭘 보나? 1분 침묵 구간의 내부는 어떻게 확인?): "AI한테 원인부터 찾아보라고 시킨다, 왜 멈춰있는지도 물어본다" — **본인 진단 모델 부재**, 전 과정 AI 위임. 침묵 구간에 스레드 덤프라는 발상 없음.

- 면접관 보충(핵심만): ① 로그 = 타임스탬프 간격으로 단계 특정 ② 침묵 구간 = 기동 중 jstack으로 main 스레드 블록 지점(DB/DNS/외부 API) ③ Actuator startup + BufferingApplicationStartup 빈 단위 타임라인 ④ 흔한 범인(기동 시 외부 대기, @PostConstruct 예열, JPA 초기화, flyway, 스캔 확대)과 개선(@Lazy·비동기화·ApplicationReadyEvent 이후 예열). AI에겐 "스레드 덤프와 타임라인을 떠서 주며" 물어야 시니어 답변.

**메모**: Q26(진단 방법론 부재)과 같은 계열 — "무엇을 떠야(수집해야) 하는지"의 레퍼토리(스레드 덤프·타임스탬프·계측)가 없음. AI 위임 답변은 24장(AI 도구 활용)에서 다시 짚을 태도 신호이기도. knowledge 문서(slow-application-startup-diagnosis.md) 에이전트 위임.

### [Q33] 반복 인증 사용자 조회 제거 (인터셉터 + ArgumentResolver) — **중** (상 경계)

**본질문 답변 요지**: "인터셉터에서 처리한다. 인터셉터는 스프링 컨테이너 내부라 빈을 쓸 수 있다" — 절반 정답, 선택 근거는 부정확(필터도 빈 등록 시 주입 가능. 진짜 강점은 핸들러 정보 접근·URL 패턴 유연성).

**꼬리질문 33-1** (@AuthUser LoginUser 파라미터로 바로 받으려면 어떤 확장 지점?): "ArgumentResolver" — 정답 (유도 후)
**꼬리질문 33-2** (인터셉터→리졸버 전달 통로는?): "ThreadLocal" — 유효 (SecurityContextHolder가 정확히 이 구조 — 오늘 학습 안착 증거)

- 면접관 보충: request.setAttribute가 더 단순한 통로(NativeWebRequest에서 꺼냄, 생명주기 자동). ThreadLocal이면 afterCompletion에서 반드시 remove() — 톰캣 스레드 재사용으로 다른 사용자 정보 오염(IAM 치명). Security 있으면 @AuthenticationPrincipal이 정석.

**메모**: 구조(검증은 앞단, 주입은 리졸버, 전달은 컨텍스트)를 유도 하에 완성. ThreadLocal 연결은 플러스, 뒤처리(remove) 자발 언급 없음은 마이너스. knowledge 문서(custom-argument-resolver-auth-user.md) 에이전트 위임.

### [Q34] @Scheduled 실행 스레드 / 지연 전파와 대책 — **하**

**본질문 답변 요지**: "잘 모르겠다" — 즉답 포기.

- 면접관 보충(핵심만): 기본 ThreadPoolTaskScheduler 풀 크기 1(scheduling-1) — 모든 작업이 단일 스레드 공유, 한 작업 지연이 전체를 밀어냄. 대책 = pool.size 확장 / @Async로 트리거·실행 분리 / 작업군별 스케줄러 분리. 파생 = 중복 실행 문제(fixedDelay vs fixedRate), 다중 인스턴스는 ShedLock.

**메모**: "기본 스레드 1개 → 한 작업 지연이 전체를 민다" 한 문장이 핵심. knowledge 문서(scheduled-tasks-threading.md) 에이전트 위임. 재도전 대상.

### [Q35] AI 생성 코드의 트랜잭션 리뷰 체크리스트 — **상**

**본질문 답변 요지**: ① 자기 호출 트랜잭션(프록시 미적용) ② 트랜잭션 내 I/O·CPU 작업 ③ REQUIRES_NEW 남용 ④ 로직의 위치 판정(트랜잭션 내부/외부/커밋 후) ⑤ 외부 로직의 보상 로직 존재 — 5항목 자발 나열. **세션 학습(Q7·Q22~24·Q26)이 체크리스트로 응집**, REQUIRES_NEW를 이번엔 스스로 꺼냄.

**꼬리질문 35-1** (빠진 2가지 — 예외 처리 관점? 조회 메서드 관점?): ① "rollback 설정이 이미 true여서 마지막에 에러 터지는지 확인"(rollback-only→커밋 시점 예외 — Q7 회수 정확) ② "readOnly 옵션 확인" — 둘 다 정답.

**메모**: 섹션 마무리 질문에서 최고 수행 — 개별 문항에서 힌트로 얻은 것들이 리뷰 관점으로 종합됨. 이 체크리스트 자체가 rationale이 원하는 "AI 시대의 시니어 감리 능력"의 골격. readOnly는 이름만 확인된 상태(중급에서 메커니즘 즉답 포기했던 항목)라 재도전은 유지.
