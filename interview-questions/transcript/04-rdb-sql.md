## 기본 ⭐

### [기본 Q1] 인덱스는 어떻게 동작하나요? B+Tree 구조를 설명해주세요.

**답변 요지**
> "정확하게 기억이 나지 않지만 키 값을 바탕으로 트리 형태를 단순 이진 트리가 아니라 하나의 노드에 여러 노드가 연결된 형태이다."

다분기(multi-way) 트리라는 형태만 짚고, B+Tree의 정의적 특징(리프 전용 데이터, 리프 연결 리스트)은 언급 없음.

**꼬리질문**

1. **"한 노드에 자식이 여러 개 달리는 구조가 이진 트리에 비해 무엇을 벌어주나요? 왜 굳이 그렇게 만들었을까요?"**
   - 답변: "한 노드에 키가 많으면 트리 높이가 낮아져서 디스크 접근 횟수가 줄어든다."
   - 평가: 정확. fan-out → 트리 높이 → 디스크 I/O 횟수라는 인과를 자력으로 연결.

2. **"이름이 B-Tree가 아니라 B+Tree입니다. `+`가 붙으면서 달라지는 게 뭔가요? 실제 레코드 값은 트리의 어디에 있고, 그 구조가 어떤 쿼리에서 이득을 주나요?"**
   - 답변: "리프 노드에만 있던 데이터가 중간 노드에도 데이터 있을 수 있도록 변경한 것으로 기억하고 이에 트리의 크기가 줄어든 것으로 알고 있다."
   - **오답 — 방향이 반대.** B-Tree가 중간 노드에도 데이터를 두는 쪽, B+Tree가 리프 전용.
   - 면접관 보충: B+Tree는 데이터를 리프에만 두고 중간 노드는 길잡이 키만 갖는다 → 중간 노드가 가벼워져 한 페이지에 키를 더 많이 담고 트리가 더 낮아진다. 리프끼리는 양방향 연결.

3. **"리프끼리 연결돼 있다는 성질이 결정적으로 유리해지는 쿼리 유형은? 반대로 전혀 도움이 안 되는 쿼리는?"**
   - 답변: "범위 쿼리가 도움이 된다. 텍스트 검색 쿼리는 도움이 안된다."
   - 평가: 정확. 힌트 없이 양쪽을 다 짚음. (범위 조회·`ORDER BY` ↔ 선행 와일드카드 `LIKE '%kw%'`)

4. **"팀원이 '이 조회가 느리니 컬럼 A에 인덱스 하나 걸어주세요'라고 요청했습니다. '일단 걸자'고 하기 전에 무엇을 따져보시나요? 인덱스를 하나 더 다는 대가는?"**
   - 답변: "우선 A 컬럼이 자주 바뀌는 대상인지 확인해야 한다. 조회보다 더 자주 바뀌는 컬럼이라면 바꿀 때마다 index를 업데이트하는 부하가 있다."
   - 평가: 쓰기 비용 축을 자력으로 제시. 다만 대가를 "쓰기 부하" 하나로만 봄(저장 공간, 옵티마이저 혼선, DDL 시점 리스크는 미언급).

5. **"A는 거의 안 바뀌는 값이었습니다. 그럼 걸어도 될까요? 그래도 안 걸거나 다르게 거는 게 나은 경우는?"**
   - 답변: "우선 조회할 때 오로지 A 컬럼을 바탕으로 조회하는 것인지도 확인한다. 즉 인덱스를 걸고 이 인덱스를 타는지 확인해야 한다. 조회 시 여러 컬럼으로부터 데이터를 조회한다면 복합 인덱스를 넣어야 한다."
   - 평가: **복합 인덱스 축과 "실제로 타는지 확인"(EXPLAIN 검증)을 스스로 제시** — 좋은 반응. 그러나 **선택도(카디널리티) 축과 기존 인덱스와의 중복 축이 끝까지 나오지 않음.**

**면접관 피드백 / 모범 답변 핵심 포인트**
- B+Tree = ① 다분기(한 페이지에 키 여러 개) → 낮은 높이 → 적은 디스크 접근 ② **데이터는 리프에만**, 중간 노드는 길잡이 키만 ③ **리프 양방향 연결** → 범위 스캔·정렬 획득.
- 인덱스 추가 판단 체크리스트(4축): **쓰기 빈도**(후보자 자력) / **선택도·카디널리티**(누락) / **기존 인덱스와의 중복 — 복합 인덱스 선두 컬럼 규칙**(부분 도달) / **EXPLAIN으로 실제 사용 검증**(자력).
- 특히 `(A, B)` 복합 인덱스가 이미 있으면 **A 단독 인덱스는 대개 불필요**하다는 선두 컬럼 규칙이 실무에서 인덱스 개수를 줄이는 핵심 근거.

**평가: 중**

**메모**
- 본질문 자체(B+Tree 구조)는 부정확했고 `+`의 의미를 정확히 반대로 알고 있었다. 기본⭐에서 이 정도 오차는 이후 커버링 인덱스·복합 인덱스 순서 문항에서 그대로 발목을 잡는다.
- 반면 꼬리질문 1·3·4·5는 힌트 없이 방향을 잡았다. **추론 능력은 있는데 구조 지식의 바닥이 얕은 전형.** 암기가 아니라 그림 한 장(3층 B+Tree 그림)으로 고정할 필요.
- 3장 횡단 약점 ②(트레이드오프 양면 조립)는 Q1에서 **부분 개선** — 대가를 먼저 말하고 판단 기준을 이어 붙였다. 다만 여전히 한 축씩 순차로 나오고, 압박 없이 스스로 3~4축을 한 호흡에 펼치지는 못했다.

### [기본 Q2] 인덱스를 걸었는데도 풀스캔이 발생하는 경우는 어떤 경우인가요?

**답변 요지**
> "인덱스를 타지 않는 경우이다."

**동어반복** — 질문을 되돌려준 답변. 이 문항의 본질(머릿속에 원인 목록이 있는가)에 전혀 답하지 못한 출발.

**꼬리질문**

1. **`email`에 인덱스가 있을 때 `WHERE email = 'a@b.com'`(A) vs `WHERE LOWER(email) = 'a@b.com'`(B) 중 못 타는 쪽과 이유는?**
   - 답변: "B가 인덱스를 못 탄다. 이유는 기존 데이터의 lower한 처리가 인덱스에 되어있지 않기 때문이다."
   - 평가: **정확.** 암기가 아니라 "인덱스에는 원본 값이 저장·정렬돼 있다"는 구조에서 도출한 답. Q1에서 구조를 틀렸던 것에 비하면 여기서는 구조적 추론이 작동했다.

2. **"함수를 전혀 씌우지 않았는데도 못 타는 경우를 떠오르는 대로 나열해보세요."**
   - 답변: "`like '%search%'` 이 경우 타지 못한다."
   - 평가: 맞지만 **한 개뿐**이고, 그마저 Q1에서 이미 나왔던 항목의 재등장. 타입 불일치·선두 컬럼 미사용·`OR`·부정 조건·낮은 선택도가 전부 누락.

3. **"조건식이 멀쩡한데도 옵티마이저가 일부러 풀스캔을 고르는 경우는?"**
   - 답변: "풀스캔이 비용이 싼 경우이다."
   - 평가: 방향은 맞음. 옵티마이저가 비용 기반으로 선택한다는 사실 자체는 인지.

4. **"왜 풀스캔이 더 쌀 수 있나요? 원하는 행만 골라 읽는 게 전체를 다 읽는 것보다 비싸지는 이유는?"**
   - 답변: **"잘 모르겠다."**
   - 면접관 보충: 세컨더리 인덱스 조회는 2단계 — ① 인덱스에서 조건에 맞는 항목을 찾아 **PK를 얻고** ② 그 PK로 **실제 행을 다시 찾아 읽는다**(북마크 룩업). ②가 디스크에 흩어진 **랜덤 I/O**. 대상 행이 전체의 일정 비율(대략 20~30%)을 넘으면 흩어진 랜덤 I/O 수만 번보다 **순차 풀스캔이 싸다.** → `WHERE status = 'ACTIVE'` 같은 낮은 선택도 컬럼이 인덱스가 있어도 무시당하는 이유.

**면접관 피드백 / 모범 답변 핵심 포인트**
- 원인 목록을 외우지 말고 **"인덱스는 원본 값의 정렬"이라는 한 문장에서 각 항목이 왜 깨지는지 도출**할 것.
- 필수 목록 6종:
  1. **컬럼에 함수·연산 적용** (`LOWER(email)`, `DATE(created_at)`, `col + 1`)
  2. **타입 불일치로 인한 암묵적 형변환** — `VARCHAR` 컬럼에 숫자를 비교하면 **컬럼 쪽**이 변환돼 ①과 동일해짐
  3. **선행 와일드카드** `LIKE '%kw%'` — 시작점을 못 잡음
  4. **복합 인덱스 선두 컬럼 미사용** (leftmost prefix 위반)
  5. **`OR` 조건 / 부정 조건**(`!=`, `NOT IN`) — 범위가 갈라지거나 전 구간이 대상
  6. **낮은 선택도** — 옵티마이저가 비용 계산 끝에 **일부러** 풀스캔 선택
- 1~5는 "구조상 못 타는" 경우, 6은 "탈 수 있는데 안 타는" 경우. **이 두 부류를 구분해 말하는 것 자체가 변별점.**

**평가: 하**

**메모**
- 첫 답변이 동어반복이었다는 점이 가장 큰 감점. rationale이 말하는 이 문항의 가치("이 목록이 머리에 있는 사람은 슬로 쿼리를 5분 만에 고치고, 없는 사람은 '인덱스 있는데 왜 느리지'에서 멈춘다")에 정면으로 미달.
- 다만 꼬리질문 1의 이유 설명은 정확했다. **지식의 문제라기보다 "떠올려 나열하는 인출(retrieval) 훈련"이 안 된 상태.** 원인 목록을 6종 체크리스트로 고정할 것.
- **랜덤 I/O vs 순차 I/O라는 비용 모델이 통째로 비어 있다.** 이건 Q3(클러스터드/세컨더리), 중급 커버링 인덱스, 깊은 페이지네이션까지 전부를 떠받치는 축이라 여기서 반드시 메워야 한다.
- Q1에서 누락됐던 **선택도** 축이 Q2에서도 자력으로 나오지 않음 — **2회 연속 누락**.

**기록 무결성**: 이 스레드 진행 중 후보자가 작성하지 않은 메시지 2건이 사용자 입력으로 도착했다(꼬리질문 2·4 시점). 후보자가 즉시 부인해 기록·평가에서 제외했다. 세션 #6, 3장 고난이도 Q4에 이은 **세 번째 발생**.

### [기본 Q3] 클러스터드 인덱스와 논클러스터드(세컨더리) 인덱스의 차이는? (InnoDB 기준)

**답변 요지**
> "클러스터드 인덱스는 PK 기준이고 인덱스로부터 완전한 row 데이터를 얻을 수 있다. 논클러스터드 인덱스는 사용자가 정의한 컬럼으로 만들어 리프 노드에서 PK를 얻는다. 조회 시 클러스터드는 바로 응답하지만, 논클러스터드는 PK를 얻고 다시 클러스터드 인덱스를 조회해 로우 데이터를 얻는다."

**구조 완전 정답** — 리프의 내용물(row 데이터 vs PK), 2차 탐색(북마크 룩업)까지 자력으로. 4장 세 문항 중 가장 좋은 출발.

**꼬리질문**

1. **"세컨더리 리프에 물리 주소를 넣으면 2차 탐색 없이 더 빠를 텐데, 왜 PK를 넣는 설계를 택했나? 이 구조 때문에 PK 설계에서 조심할 점은?"**
   - 전반부 답변: "물리 주소를 넣으면 물리 주소가 변경될 때 인덱스도 모두 다시 변경되는 문제가 생긴다." — **자력 정답.** 논리 포인터의 이유를 정확히 도출.
   - 후반부는 무응답 → 재질문하자 "정확히는 모르겠지만 PK를 매우 여러 컬럼으로 지정하면 안 될 것 같다." — 방향(PK 크기)만, 확신·근거 없음.

2. **"100바이트 복합 PK + 세컨더리 인덱스 5개면 정확히 무슨 일이 벌어지고, 왜 성능 문제인가?"**
   - 답변: "세컨더리 인덱스의 조합되는 데이터마다 100바이트를 더해가니 메모리에 부하가 생긴다. 데이터 생성 시마다 인덱스를 생성하며 많은 메모리를 잡아먹는다."
   - 평가: PK가 모든 세컨더리 엔트리에 복제된다는 연결은 해냄. 그러나 **"메모리 부하"라는 뭉뚱그린 표현에서 멈춤** — 페이지당 엔트리 수↓ → 버퍼 풀 적재율↓ → 디스크 I/O↑라는 비용 사슬은 못 짚음. Q2의 랜덤 I/O 비용 모델 공백과 일관된 패턴.

3. **"동료가 '규모 유추 방지를 위해 PK를 UUID(v4)로 하자'고 제안. INSERT가 몰릴 때 무슨 일이 벌어지고, 어떻게 답하겠나?"** (클러스터드 인덱스 = PK 순 물리 정렬이라는 힌트 제공)
   - 답변: "차례대로 저장하는 게 아니라 디스크의 각 위치를 왔다갔다 하면서 저장하게 되어 성능 이슈. 나라면 랜덤은 아니고 **스노우플레이크를 적용**해서 유추도 어렵게 하자고 한다."
   - 평가: 랜덤 삽입 지점 분산까지는 정확. **페이지 분할이라는 이름과 그 비용(쪼개기·단편화·버퍼 풀 캐시 미스)은 없음.** 반면 **Snowflake 대안은 자력 — 시간순 정렬성과 유추 방지를 동시에 잡는 실전 판단으로, 이 스레드의 백미.**

**면접관 피드백 / 모범 답변 핵심 포인트**
- InnoDB에서 테이블 = 클러스터드 인덱스 그 자체(PK 순서로 물리 정렬된 B+Tree, 리프가 곧 행 데이터). 세컨더리 인덱스 리프에는 **PK가 논리 포인터로** 들어간다 — 페이지 분할로 행이 이동해도 세컨더리 인덱스를 고칠 필요가 없게 하기 위해.
- 이 구조에서 도출되는 **PK 설계 2원칙**: ① **작게** — PK는 모든 세컨더리 인덱스 엔트리에 복제되므로, PK 크기 = 전체 인덱스 크기의 곱셈 계수. 커지면 페이지당 엔트리 수↓ → 버퍼 풀에 덜 올라감 → 디스크 I/O↑ ② **단조 증가** — 순차 삽입은 마지막 페이지에 append만 하지만, 랜덤 PK는 아무 페이지나 열어 **페이지 분할**을 일으키고 단편화 + 인덱스 전체가 워킹셋이 되어 버퍼 풀을 오염시킨다.
- 규모 유추 방지가 요건이면 UUID v4가 아니라 **시간 순 정렬성이 있는 ID**(Snowflake, UUID v7)로 — 후보자가 자력으로 도달.

**평가: 중** (상에 가까운 중)

**메모**
- 본질문을 4장 들어 처음으로 완전 정답으로 출발했고, 논리 포인터의 이유·Snowflake 대안 등 **추론과 실전 판단이 살아 있는 스레드**였다.
- 상을 못 준 이유: ① PK 설계 주의점이 스스로 안 나오고 재질문 후 방향만 나옴 ② 비용을 말할 때마다 "메모리 부하", "왔다갔다 해서 성능 이슈"처럼 **뭉뚱그린 표현에서 멈춤** — 페이지 분할·버퍼 풀 적재율·랜덤 I/O라는 이름과 사슬로 말하지 못함(Q1·Q2·Q3 **3회 연속** 같은 지점).
- 이 문항의 구조 지식은 Q2 면접관 보충(북마크 룩업)의 학습 효과일 가능성이 있음 — 커버링 인덱스(중급)에서 자력 재현되는지 확인할 것.

### [기본 Q4] 정규화와 반정규화란? 반정규화를 선택하는 기준은?

**답변 요지**
> "정규화는 테이블끼리 데이터 중복 없이 원본 데이터만 갖는 구조. 반정규화는 같은 데이터를 중복으로 갖거나 연산해서 갖는 것. 선택 기준은 조회 시 여러 테이블을 조회하게 되는 경우 성능을 올리기 위해."

개념 방향 정확 — 중복 컬럼과 연산(집계) 컬럼 **두 형태를 모두 인지**. 그러나 기준을 조회 성능(편익)만으로 서술, **대가(갱신 정합성) 축 무언급** — 3장 횡단 약점 ②(트레이드오프 양면 조립) 재발.

**꼬리질문**

1. **"게시글 목록의 `posts.comment_count` 반정규화 — 지불한 대가와 관리 방법은?"**
   - 답변: "댓글 추가마다 컬럼도 함께 수정. 같은 트랜잭션으로 묶여 카운트가 에러 나면 댓글도 롤백되는 비용. 달리고 지워질 때 원자적 연산으로 유지."
   - 평가: 쓰기 동반 갱신·트랜잭션 결합 비용·원자적 UPDATE까지 자력. 3장 고난이도 Q1(동시성 갱신, 평가 상)의 학습 효과가 이식된 모습.

2. **"초당 수백 개 댓글이 달리는 인기 글이 되면 이 구조에서 무슨 일이?"**
   - 첫 답변: "성능 저하가 일어난다. 응답시간이 오래 걸리고 다른 요청도 문제가 생긴다." — **뭉뚱그린 비용 서술 4회째**(Q1~Q4 연속).
   - "수백 트랜잭션이 같은 posts 행 하나를 UPDATE" 힌트 후: "락 경합이 일어난다." — **이름만 도달.** 락 경합→사실상 직렬화→트랜잭션 장기화→커넥션 풀 고갈이라는 사슬은 면접관이 보충. (3장 고난이도 Q1에서 커넥션 풀 보호 논리를 자력으로 폈던 것과 대조 — 지식은 있는데 인출이 힌트에 의존)

3. **"원자적 UPDATE로 다 묶어도 1년 뒤 comment_count가 실제와 어긋날 수 있다. 왜, 그리고 장기적으로 어떻게 유지하나?"**
   - 답변: "DB상 묶여 있는 게 아니므로 로직상 오류가 있으면 달라질 수 있다. 유지하려면 정합성을 맞추는 배치를 주기적으로 돌려야 한다."
   - 평가: **양쪽 다 자력 정답.** 불변식이 DB 제약이 아니라 애플리케이션 관례에 사는 한 어긋난다는 본질 + **보정 배치라는 안전망을 힌트 없이 제시** — 3장 횡단 약점 ①(안전망을 코드로 고정, 7회 반복)에서 처음 나온 자력 개선 신호.

**면접관 피드백 / 모범 답변 핵심 포인트**
- 정규화 = "하나의 사실은 한 곳에만" — 중복을 없애 수정 이상(update anomaly)을 구조적으로 차단. 반정규화 = **조회 패턴에 맞춰 의도적으로 중복·연산 값을 허용하고, 그 대가(갱신 정합성)를 관리하는 결정.** 정의에 "대가 관리"까지 넣어야 완성.
- 선택 기준 4축: ① 읽기:쓰기 비율(읽기 압도적) ② 조인·집계 비용이 **실측으로** 병목 ③ 그 전에 인덱스·커버링 인덱스·캐시로 해결 안 되는지 먼저 ④ 대가를 지불할 준비 — 동기 트랜잭션+원자적 UPDATE(핫 로우면 경합 대비), 보정 배치.
- 핫 로우 사슬: **락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파.** 이름으로 말할 것.
- (가산점) 주문 테이블의 상품명 스냅샷처럼 **동기화하면 안 되는 중복**(역사적 사실 보존)과 동기화해야 하는 중복의 구분.

**평가: 중**

**메모**
- rationale의 변별점("중복을 허용하고 대가를 관리해본 사람인가")에 부분 부합 — 트랜잭션 결합, 원자적 UPDATE, 보정 배치까지 관리 수단이 나왔다. 다만 본질문에서 편익만 말하고 대가는 꼬리질문이 끌어내야 했다.
- **개선 신호**: 안전망(보정 배치) 자력 제시는 3장 내내 없던 반응. 반면 **비용 사슬에 이름 붙이기는 4문항 연속 같은 지점에서 걸림** — 이번 장의 최우선 교정 대상 확정.

### [기본 Q5] 트랜잭션의 ACID를 설명해주세요.

**답변 요지**
> (약어 자체를 기억 못해 "ACID가 각각 무슨 단어인지 알 수 있을까?"라고 단어를 요청 → 네 단어 제공 후)
> "원자성: 트랜잭션으로 묶여 있다면 쿼리 실행 도중에 누군가 끼어들 수 없다 / 일관성: 같은 쿼리라면 같은 결과 / 격리성: 다른 트랜잭션의 영향을 받지 않고 독립적 / 지속성: 과거와 미래 트랜잭션의 결과가 동일해야"

**4개 정의 중 격리성만 방향 정답.** 원자성은 격리성과 혼동, 일관성·지속성은 오답. 기본⭐ 중의 기본에서 약어 인출 실패 + 정의 3/4 오류로 출발.

**꼬리질문**

1. **"A계좌 차감 성공 → B계좌 입금 직전 서버 다운. 재시작 후 A는 어떤 상태여야 하고, 어느 글자인가?"**
   - 답변: "차감 전 상태여야 한다. 원자성이다." — **즉답 정답.** 개념은 있고 정의 언어만 어긋났음을 확인.

2. **"커밋 완료 응답 직후 전원 차단. 남아야 하나? 어느 글자? 테이블 파일에 아직 안 쓰였을 수도 있는데 무슨 수로 보장하나?"**
   - 답변: "남아 있어야 한다. 지속성이다. 메모리 내용을 로컬 파일로 갖고 있는 방식을 쓰든 어떻게든 갖고 있어야 한다."
   - 평가: 글자 매핑 정답, "커밋 전에 디스크 어딘가에 남겨야 한다"는 감까지. redo log/WAL 이름은 없음(면접관 제공).

3. **"왜 커밋 때 테이블 파일을 바로 안 고치고 로그 파일에 먼저 쓰나? (I/O 비용 힌트 제공)"**
   - 답변: "실제 테이블 파일을 고치는 작업은 I/O 작업이므로 로그를 갖고 있는 것보다 오래 걸리기 때문."
   - **로그 쓰기도 똑같이 디스크 I/O라는 인식이 없음 — 랜덤 I/O vs 순차 I/O 구분 부재 5회째.** 면접관 보충: 테이블 반영 = 흩어진 페이지 랜덤 쓰기 / 로그 = 파일 끝 순차 append → 커밋 순간엔 싼 순차 쓰기만, 비싼 랜덤 쓰기는 나중에 모아서.

4. **"일관성이 깨진 상태란 계좌이체 예에서 구체적으로 어떤 상태인가?"**
   - 답변: **"잘 모르겠다."**
   - 면접관 보충: 이체 후 두 계좌 총합에서 10만원 증발 / 잔액 음수 제약 뚫림 — "트랜잭션 전후로 시스템의 규칙(불변식·제약)이 항상 지켜진다"가 일관성.

**면접관 피드백 / 모범 답변 핵심 포인트**
- 글자마다 **한 줄 정의 + 메커니즘 하나**로 고정할 것:
  - **A(원자성)**: 전부 반영 or 전부 취소, 중간 상태 없음 — 구현: **undo log**(되돌리기용 기록)
  - **C(일관성)**: 트랜잭션 전후로 불변식·제약 유지(총합 불변, 잔액 ≥ 0) — DB 제약 + 애플리케이션의 공동 책임
  - **I(격리성)**: 동시 트랜잭션이 서로의 중간 상태를 보지 않음 — 구현: **락 + MVCC**
  - **D(지속성)**: 커밋 응답 후에는 전원이 나가도 보존 — 구현: **redo log(WAL)** — 커밋 시점엔 순차 append만, 랜덤 페이지 쓰기는 나중에
- "원자성 = 끼어들 수 없다"는 격리성의 언어다. 원자성은 **동시성이 아니라 실패**에 대한 보장.

**평가: 하**

**메모**
- 시나리오를 주면 A·D를 즉답으로 맞힌다 — **개념의 씨앗은 있는데 용어·정의·메커니즘이 전혀 조직화되어 있지 않은 상태.** Q2와 같은 패턴(인출 실패)이나, ACID는 기본 중의 기본이라 감점 폭이 더 크다.
- **랜덤 vs 순차 I/O 구분 부재가 5회째** — 이번엔 "로그 쓰기는 I/O가 아니다"라는 인식 수준까지 드러남. redo log가 존재하는 이유 자체가 이 구분이므로, 이 축을 메우면 D의 메커니즘까지 한 번에 잡힌다.
- 격리성이 유일하게 방향이 맞았던 것은 3장(JPA 동시성)에서 락·동시성을 다뤄본 경험 덕으로 보임. MVCC(중급 예정)에서 검증될 것.

### [기본 Q6] JOIN의 종류(INNER, LEFT, ...)와 실행 방식(NL, Hash, Sort-merge)을 설명해주세요.

**답변 요지**
> "INNER JOIN은 두 테이블에서 서로 데이터가 있는 것들만 조인, LEFT JOIN은 한쪽에 있는 모든 데이터를 바탕으로 조인." (종류는 기본 수준 정답 — NULL 채움·RIGHT/FULL은 언급 없음)
> 실행 방식 재촉구에는 **"다 모른다."**

**꼬리질문** (자바 코드로 제1원리 도출 유도)

1. **"List<Order> 10만 × List<User> 1만을 순수 자바로 조인한다면 가장 단순한 방법은?"**
   - 답변: "Order를 순회하면서 User를 순회해서 찾는다." — 이중 루프 = **Nested Loop을 자력 도출.**

2. **"리뷰에서 지적받을 그 코드, 어떻게 고치고 뭘 대가로 빨라지나?"**
   - 답변: "한쪽을 Map에 넣고 다른 쪽을 순회하며 찾는다. **메모리를 대가로 빨라진다.**" — **Hash 조인 자력 도출 + 트레이드오프 양면을 한 호흡에**(3장 약점 ②의 두 번째 개선 신호). 단 Map을 큰 쪽(Order 10만)으로 만든다고 함.

3. **"DB라면 어느 쪽을 해시 테이블로 만드나?"**
   - 답변: "메모리 한계를 확인하고 한계 내에서 가능한 큰 쪽을 선택할 것 같다." — **오답.** "큰 쪽을 해시로 만들수록 이득"이라는 오개념. 정답: **항상 작은 쪽**(build side). 프로브 비용은 어느 방향이든 양쪽 한 번씩 순회로 동일하고, 차이는 해시 테이블의 메모리 점유(+스필 위험)뿐 — 큰 쪽을 해시로 만들면 얻는 것 없이 메모리만 더 쓴다.

**면접관 피드백 / 모범 답변 핵심 포인트**
- **NL 조인** = 이중 루프. 단 DB는 안쪽 루프를 통순회하지 않고 **조인 키 인덱스로 탐색** — MySQL의 기본 조인 방식이라 "드라이빙(바깥) 테이블을 작게, 안쪽 테이블 조인 키에 인덱스"가 튜닝의 기본 문법.
- **Hash 조인** = 작은 쪽으로 해시 테이블 build, 큰 쪽으로 probe. 등호 조인 전용. 인덱스 없는 대량 조인에 강함.
- **Sort-merge** = 양쪽을 조인 키로 정렬 후 지퍼처럼 병합. 이미 정렬된(인덱스 순) 입력이면 강함.
- LEFT JOIN에서 매칭 없는 쪽 컬럼은 **NULL로 채워진다.** LEFT를 써야 할 곳에 INNER를 쓰면 **행이 조용히 사라진다** — 에러가 아니라 누락이라 리뷰에서 잡아야 하는 버그(rationale의 핵심 축).

**평가: 중** (하에 가까운 중)

**메모**
- "다 모른다"로 시작했지만 자바로 재구성하자 NL·Hash를 모두 자력 도출 — **이미 아는 것(이중 루프, HashMap)의 DB 이름을 모르는 상태**였다. 실전 면접에서 "다 모른다"는 절반 포기는 치명적: "제가 자바로 짠다면 이중 루프인데, DB도 비슷하게…"처럼 아는 것에서 출발하는 태도 전환이 필요.
- "메모리를 대가로"가 즉답으로 나온 것은 Q4 보정 배치에 이은 개선 신호. 다만 빌드 사이드 오답은 "비용이 어디서 나는가"를 끝까지 추적하지 않는 습관(뭉뚱그림)과 같은 뿌리로 보임.
- 실행 계획에서 조인을 읽는 능력(rationale 축)은 현재 0 — 중급 EXPLAIN 문항에서 재검증 예정.

### [기본 Q7] `WHERE`절과 `HAVING`절의 차이는?

**답변 요지**
> "WHERE은 FROM절에서 해당되는 데이터에 조건을 추가하는 것이고, HAVING절은 GROUP화된 데이터에 조건을 추가하는 것이다."

**정답.** 집계 전 행 필터 vs 집계 후 그룹 필터.

**꼬리질문**

1. **"'연봉 5000 이상 직원만으로 부서별 평균'(①) vs '부서별 평균이 5000 이상인 부서'(②) — 조건 위치와, 바꿔 쓰면 숫자가 어떻게 잘못 나오나?"**
   - 절 배치는 즉답 정답(①WHERE ②HAVING). 바꿔 쓸 때의 결과 설명은 뭉개짐("요청 2는 요청 1처럼 나온다") — 의미 교환을 말하려던 것으로 보이나 숫자가 달라진다는 핵심이 언어화되지 않음.

2. **"개발팀 A=3000·B=7000 미니 데이터로 ①과 ②의 개발팀 평균을 직접 계산해보라."**
   - 답변: "요청 1은 7000만원, 요청 2는 5000만원." — **둘 다 정확.** 경계값(5000 ≥ 5000 포함) 처리까지 맞음.

**면접관 피드백 / 모범 답변 핵심 포인트**
- 같은 테이블, 같은 "5000"이라는 조건인데 결과 숫자가 7000 vs 5000으로 갈린다 — rationale이 말하는 "집계 전/후 구분 실패 → 틀린 숫자 → 틀린 비즈니스 판단"의 실체.
- 실행 순서로 고정할 것: **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY.** WHERE는 집계에 들어갈 재료를 거르고, HAVING은 집계 결과를 거른다.
- (성능 보너스) 같은 조건이라면 WHERE에 — 집계 전에 행을 줄이고 인덱스를 탈 수 있다. HAVING은 일단 전부 그룹핑한 뒤에 거른다.

**평가: 상** (4장 첫 상)

**메모**
- 개념·배치·숫자 추적 모두 자력. 유일한 흠은 FU1에서 구체 데이터 없이 말로 설명할 때 뭉개진 것 — 지식이 아니라 **언어화 습관**의 문제로, 이번 장 내내 반복되는 패턴("사슬로 말하기")과 같은 뿌리.

## 기본 ⭐ 소구간 총평 (7문항 완료 ✅ — 상 1 · 중 4 · 하 2)

- **패턴이 명확하다**: 구조·개념의 뼈대와 추론 능력은 있는데, ① **용어·목록·약어의 인출(retrieval)이 자주 실패**하고(Q2 원인 목록, Q5 ACID, Q6 실행 방식 — "다 모른다" 포함) ② **비용·장애를 이름 붙은 사슬로 언어화하지 못한다**(Q1~Q5 5회: "메모리 부하"·"왔다갔다"·"성능 저하"·"로그는 I/O가 아니다").
- **개선 신호 2건**: Q4 보정 배치 자력(3장 약점 ① 첫 개선), Q6 "메모리를 대가로" 즉답(약점 ② 개선). 시나리오·코드로 재구성해주면 A·D 매핑(Q5), NL·Hash 도출(Q6), 숫자 추적(Q7)처럼 성공률이 급등한다.
- **중급 진입 전 최우선 복습**: 랜덤 vs 순차 I/O 비용 모델(북마크 룩업·WAL·페이지 분할이 전부 이 축 위에 있다) → 그 다음 ACID 4줄 매핑, 풀스캔 원인 6종, 조인 3방식 이름.
- 중급에서 재검증할 것: 선택도 축(Q1·Q2 연속 누락 — 복합 인덱스 문항에서), 북마크 룩업 자력 재현(커버링 인덱스 문항에서), EXPLAIN에서 조인 읽기(Q6 축).

## 약점 노트 (평가 "중" 이하 — 재도전 대상)

- [ ] **[기본 Q1] B+Tree 구조** — `B-Tree vs B+Tree`의 차이를 반대로 기억. 리프 전용 데이터 / 리프 연결 리스트 / 중간 노드는 길잡이 키. 그림으로 고정할 것.
- [ ] **[기본 Q1] 인덱스 추가 판단의 선택도(카디널리티) 축** — 끝까지 언급 없음. "값 종류가 적은 컬럼(상태값·성별)은 단독 인덱스가 무의미"까지.
- [ ] **[기본 Q1] 기존 인덱스와의 중복 판단** — 복합 인덱스 **선두 컬럼 규칙**. `(A,B)`가 있으면 `A` 단독 인덱스는 불필요.
- [ ] **[기본 Q2] 풀스캔 원인 6종 체크리스트 인출** — 함수·연산 / 타입 불일치 / 선행 와일드카드 / 선두 컬럼 미사용 / `OR`·부정 조건 / 낮은 선택도. **"구조상 못 탄다"와 "탈 수 있는데 안 탄다"를 구분해 말하기.**
- [ ] **[기본 Q2] 랜덤 I/O vs 순차 I/O 비용 모델** — 세컨더리 인덱스의 2단계 조회(북마크 룩업)와 손익분기(대략 20~30%). **Q3·커버링 인덱스·깊은 페이지네이션의 공통 토대라 최우선.**
- [ ] **선택도(카디널리티) 축 — Q1·Q2 2회 연속 누락.** 인덱스 관련 어떤 질문에서든 자력으로 꺼낼 수 있을 때까지.
- [ ] **[기본 Q3] PK 설계 2원칙을 구조에서 도출하기** — ① 작게(모든 세컨더리 인덱스에 복제 → 페이지당 엔트리↓ → 버퍼 풀 적재율↓ → I/O↑) ② 단조 증가(랜덤 PK → 페이지 분할·단편화·버퍼 풀 오염). "메모리 부하" 같은 뭉뚱그린 표현 대신 **비용 사슬을 이름으로** 말하기.
- [ ] **비용·장애를 정밀한 사슬로 서술하는 습관 — Q1~Q5 5회 연속 같은 지점에서 멈춤.** I/O 쪽(페이지 분할/버퍼 풀/**랜덤 vs 순차 I/O — Q5에선 "로그 쓰기는 I/O가 아니다" 수준까지 노출**)과 동시성 쪽(락 경합→직렬화→트랜잭션 장기화→커넥션 풀 고갈) 모두 **이름 붙은 사슬**로 말할 수 있을 때까지. 4장 최우선 교정 대상. redo log의 존재 이유(순차 append가 싸다)를 이해하면 D 메커니즘까지 한 번에 잡힌다.
- [ ] **[기본 Q4] 반정규화 정의·기준에 대가 축 포함하기** — "조회 성능을 위해"에서 멈추지 말고 "의도적 중복 + 갱신 정합성 관리"까지 한 호흡에(3장 횡단 약점 ② 재발). 선택 기준 4축: 읽기:쓰기 비율 / 실측 병목 / 인덱스·캐시 선행 검토 / 대가 지불 준비.
- [ ] **[기본 Q5] ACID — 글자별 "한 줄 정의 + 메커니즘 하나" 매핑 통암기 수준으로 고정** — A=전부 or 전무(undo log) / C=불변식 유지(제약+애플리케이션) / I=중간 상태 안 보임(락+MVCC) / D=커밋 후 불멸(redo log/WAL). 약어 인출 실패 + 정의 3/4 오류였다. **원자성을 "끼어들 수 없다"로 말하지 않기(그건 격리성).**
- [ ] **[기본 Q5] 일관성 개념 자체** — "같은 쿼리 같은 결과"가 아니라 "트랜잭션 전후 시스템 규칙(총합 불변·잔액 ≥ 0)이 유지". 시나리오를 줘도 "잘 모르겠다"였던 유일한 글자.
- [ ] **[기본 Q6] 조인 실행 방식 3종을 DB 용어로 인출하기** — NL(이중 루프 + 안쪽은 인덱스 탐색, MySQL 기본) / Hash(작은 쪽 build·큰 쪽 probe, 등호 전용) / Sort-merge(정렬 후 병합). 자바 코드로는 도출했으니 **이름 ↔ 코드 그림 연결**만 고정하면 됨.
- [ ] **[기본 Q6] Hash 조인 빌드 사이드 = 항상 작은 쪽** — "큰 쪽을 해시로"라는 오개념 교정. 프로브 비용은 방향 무관, 차이는 해시 테이블 메모리뿐.
- [ ] **"다 모른다"로 절반을 포기하는 답변 태도** — 아는 것(자바 코드)에서 출발해 추론을 보여주는 전환. 실전 면접에서 치명적.
