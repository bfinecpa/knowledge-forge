### [Q1] JVM 메모리 구조 (Heap/Stack/Metaspace), 객체 생성 위치 — **상**

**본질문 답변 요지**: Heap=객체 데이터, Stack=지역변수/파라미터, Metaspace=클래스 데이터/메서드/전역 메타. (정확)

**꼬리질문 1-1**: `User user = new User()` 시 변수와 객체 위치, 멀티스레드 시 Stack/Heap 취급?
- 답변: Heap엔 객체 데이터, 이를 가리키는 주소값은 Stack. 각 스레드는 자기 Stack에 주소 저장, Heap엔 객체 생성. (정확 — 참조 vs 객체 실체, 스레드별 스택 이해)

**꼬리질문 1-2**: Heap 안정한데 Metaspace 우상향(배포 안 함), 무엇을 의심? OOM 시 영역별 대응 차이?
- 답변: 클래스로더 참조 유지, 클래스 객체 계속 참조/사용, 동적 프록시 클래스 계속 생성, 리플렉션 클래스 양산. (Metaspace 누수 원인 정확 즉답 — 우수)

**꼬리질문 1-3**: Heap OOM vs Metaspace OOM 구분법? Metaspace 누수라면 힙 덤프가 도움 되나?
- 답변: Heap 모니터링해서 Heap 일정한데 OOM이면 Metaspace 의심. 힙 덤프로는 못 찾는다. (구분 방향 OK, 힙 덤프 판단은 부정확)

**꼬리질문 1-4 (반론)**: OOM 에러 메시지 문구로 구분되지 않나? 힙 덤프엔 클래스로더/클래스 객체도 포함되는데 정말 못 찾나?
- 답변: 에러 문구는 본 적 없어 모름 — "AI한테 물어보면 되는 것 아닌가". 힙 덤프로 클래스로더/클래스 객체 통해 범인 좁힐 수는 있다고 정정. (기술적으론 정정 성공, 태도 관찰됨)
- 면접관 보충: OOM 문구 판별기 — `Java heap space`/`Metaspace`/`GC overhead limit exceeded`/`unable to create new native thread`. 장애 대응은 초 단위 → 즉시 판독력 필요.

**메모**: Heap/Stack/Metaspace·참조vs객체·스레드별 스택 정확. Metaspace 누수 원인 즉답 우수. OOM 에러 문구는 모름(AI에 물어보면 된다는 태도) — 장애 시 즉시 판독력 보완 필요.

### [Q2] GC 동작 원리 / Young·Old 분리 이유 — **상**

**본질문 답변 요지**: GC root부터 참조 추적해 미참조 데이터 sweep 후 compact. Young=짧은 주기 GC/단명 객체, Old=장수 객체 → weak generational hypothesis 기반 효율화. (정확)

**꼬리질문 2-1**: Young 내부 구조와 승격(promotion) 기준? Eden/Survivor 흐름으로.
- 답변: Young = Eden 1 + Survivor 2. 시간 기반 또는 Young 메모리 참으로 승격. Eden→Survivor→Old. (구조 OK, 승격 기준 '시간'은 오인 → age 카운터로 정정)

**꼬리질문 2-2**: 왜 Survivor가 2개(S0,S1)인가? 1개면 안 되나? Minor GC 시 객체 이동으로 설명.
- 답변(+역질문): (역질문) minor GC 카운트 기준이면 트래픽 몰릴 때 짧은 시간에 minor GC 많이 일어나 원래 정리될 게 살아남아 승격되나? / Survivor 2개는 minor GC 잦으니 sweep-compact보다 copy 후 정리가 효율적이라서.
- 면접관 답: (1) 정확한 직관 = 조기 승격(premature promotion), Survivor 오버플로 또는 age 카운터 급증 → Old 적재 → Full GC 유발("트래픽 피크마다 응답 튐" 시나리오). (2) copy는 생존 소수만 복사+compaction 공짜, 2개인 결정적 이유는 항상 To를 비워둬 복사 대상 확보(ping-pong 스왑). 1개면 복사 공간 없음.

**메모**: mark-sweep-compact·weak generational hypothesis 정확. 조기 승격을 스스로 추론해 역질문(인상적). 승격 기준을 '시간'으로 오인(→age 카운터), Survivor 2개 이유는 힌트 후 도달.

### [Q3] equals()/hashCode() 동시 재정의 이유 — **상**

**본질문 답변 요지**: 둘 다 정의해야 HashSet/HashMap에서 정확히 중복 제거, 하나만 하면 중복 발생. (방향 OK, 얕음)

**꼬리질문 3-1**: hashCode만 재정의 vs equals만 재정의 각각 put→get 시 버킷 찾기/비교 과정과 버그?
- 답변: hashCode만 → 같은 버킷에 논리적 동일 데이터 중복. equals만 → 다른 버킷에 흩어져 중복. (핵심 두 모드 파악)

**꼬리질문 3-2**: equals만 재정의 상태에서 put(new User("A"),100) 후 get(new User("A"))는? 조회 순서와 연결.
- 답변: 데이터 없다(null) 반환. 버킷 찾았는데 그 버킷에 equals 매칭 데이터 없음, 저장 버킷이 다르기 때문. (2단계 조회 정확)

**메모**: 처음엔 '중복' 수준으로 얕음. 힌트 후 버킷먼저→equals비교 2단계 조회, put성공/get=null 증상 정확히 도달.

### [Q4] String 불변성 / StringBuilder — **중**

**본질문 답변 요지**: String pool 캐시 + 멀티스레드 안전 위해 불변. StringBuilder는 멀티스레드 공유 시 사용. (불변 이유 OK, StringBuilder 정반대 오해)

**꼬리질문 4-1**: StringBuilder가 thread-safe한가? StringBuffer와 차이? StringBuilder 원래 용도?
- 답변: 잘 모르겠다.
- 면접관 보충: StringBuilder=thread-safe X(빠름), StringBuffer=synchronized(느림). StringBuilder 진짜 이유=가변 버퍼, String 불변이라 루프 += 시 매번 새 객체 O(n²)→StringBuilder는 char배열 재사용 O(n). 단일스레드 반복조립=StringBuilder.

**메모**: 불변 이유(String pool+스레드안전) 정확. StringBuilder 목적을 정반대(멀티스레드 공유)로 오해, 반복연결 O(n²) 동기 모름. StringBuffer/synchronized 몰랐음.

### [Q5] Checked vs Unchecked 예외 / 선택 기준 — **상**

**본질문 답변 요지**: Checked=컴파일 시점, Unchecked=런타임. Checked는 잡아서 처리 필요할 때, Unchecked는 던져도 될 때. (방향 OK, 두번째 살짝 모호)

**꼬리질문 5-1**: 왜 실무는 커스텀 예외를 Unchecked로 선호? catch(Exception e){} 위험성?
- 답변: 사용자에게 에러 노출 목적(→살짝 빗나감). Checked는 기본값 처리 필요 시. Unchecked만 스프링 트랜잭션 롤백 대상. 예외 삼킴은 조용히 중요 예외 묻혀 위험. (롤백·삼킴 정확 자답)

**꼬리질문 5-2**: 트랜잭션 중 Checked 예외인데 반드시 롤백 원하면?
- 답변: Checked 잡아 로깅 등 처리 후 Unchecked로 던진다. (유효 — 예외 변환)
- 면접관 보충: 예외 변환 정석 OK. 또는 @Transactional(rollbackFor=...). 둘 다 맞음.
- (부가) '시그니처 오염/결합도 회피' 설명: Checked는 throws가 중간 계층 시그니처 전파·오염, 하위 예외 변경이 상위 연쇄 수정 유발(결합). 처리는 최상단 한 곳인데 중간이 다 알 필요 없음.

**메모**: 컴파일/런타임 강제 구분. Unchecked만 기본 롤백·예외삼킴 위험 정확 자답. Checked→Unchecked 변환으로 롤백 유도. Unchecked 선호이유는 살짝 빗나감(사용자 노출→실제는 시그니처오염/결합도).

### [Q6] 인터페이스 vs 추상 클래스, 각각 언제 사용? — **중**

**본질문 답변 요지**: 인터페이스=기능 추상화 목적, 추상클래스=위계 확실할 때 클래스 추상화. 인터페이스는 다중 구현 가능, 추상클래스는 필드 보유 가능. (개념 정확)

**꼬리질문 6-1 (시나리오)**: SSO/IdP 1곳→3곳(Google/Azure AD/SAML) 확장 시 인터페이스·추상클래스 어떻게? 경계 어디, 공통로직 어디, 트레이드오프?
- 답변: 외부인증 추상화 인터페이스 만들고 3개 클래스가 구현. (뼈대만, 공통로직/트레이드오프 미답)

**꼬리질문 6-2**: 공통 흐름(토큰검증→클레임 매핑→프로비저닝)을 (a)추상클래스에 담을지 (b)합성으로 분리할지? 트레이드오프?
- 답변: b(합성). 추후 공통로직 변경 시 쉽게 변경 가능. (선택 옳으나 근거 얕음)

**꼬리질문 6-3**: (a) 템플릿 메서드 방식이 IdP 3→10곳 늘 때 구체적으로 뭐가 불편? 합성이 어떻게 피하나?
- 답변: 잘 모르겠다.
- 면접관 보충: 상속 방식 단점=단일상속 제약/부모-자식 경직 결합(부모 변경이 10자식 영향)/변형 축 다수 시 조합 폭발. 합성=공통흐름 협력객체, 다른 부분만 인터페이스 주입 → 다중상속 문제無/공통 한곳 수정/변형 독립조합. "상속보다 합성" 원칙.

**메모**: 개념구분 정확. 확장 시나리오에서 합성 택한 본능 옳음. but 트레이드오프 근거(상속 경직성·단일상속·변형폭발) 못 댐, 결론만.

### [Q7] final (클래스/메서드/변수) 각각의 의미 — **상**

**본질문 답변 요지**: 클래스=상속 불가, 메서드=오버라이드 불가, 변수=변경 불가. (정확)

**꼬리질문 7-1**: `final List<String> list = new ArrayList<>()` 에서 list.add("x") 되나? final이 막는 게 정확히 뭔가?
- 답변: 된다. final은 재할당을 막지 데이터 변경은 못 막음. 진짜 불변은 immutable 컬렉션(List.of/unmodifiableList) 필요. Kotlin은 val/var로 구분. (정확 + 스스로 확장)

**메모**: final=참조 재할당만 막음, 컬렉션 내부 변경 가능 정확. Kotlin val/var까지 스스로 확장.

### [Q8] Java 8+ (Stream/Optional/람다) 실무 활용 경험 — **중**

**본질문 답변 요지**: Stream으로 List를 선언형 처리. Optional은 리턴이 null일 수 있음을 인지시키려 사용. 람다는 함수형 메서드를 파라미터로 넘길 때. (용도 이해 정확)

**꼬리질문 8-1**: Stream이 독이 되는 경우? forEach 안 외부상태 변경 / map 안 DB조회 문제·개선, 차라리 for문 나은 상황?
- 답변: 잘 모르겠다. continue 써야 하는 경우는 for문이 낫다. (continue/break 분별 OK, 남용 사례는 못 댐)
- 면접관 보충: forEach 외부상태 변경→병렬 경쟁조건(collect/reduce로 대체), map내 DB조회→N+1·지연평가로 은폐(batch 조회).
- 후보자 역질문(우수): (1)"부수효과 없음이 왜 전제?"→지연평가/재배열/병렬의 자유를 위해 순수함수 가정, JavaDoc의 non-interfering/stateless/side-effect-free. (2)"N+1은 for문도 문제 아닌가?"→정확한 지적. N+1은 스트림 고유 아님, 루프 안 I/O가 본질. 스트림은 지연평가로 발견만 더 어려움.

**메모**: 용도 이해 정확, continue→for문 분별 OK. but Stream 남용 사례·대안 못 댐. 역질문 우수(전제 왜/N+1 반문 — 정확한 지적).

## 중급 ⭐⭐

### [Q10] G1 GC vs ZGC, latency 민감 서비스 선택 — **상**

**본질문 답변 요지**: G1=최대 STW 지정 가능, ZGC=STW 최소화. latency 민감→ZGC. 이유: throughput 조금 낮추는 대신 STW 매우 짧게→최대 응답시간 감소. (정확)

**꼬리질문 10-1**: ZGC가 힙 커져도 STW sub-ms 유지하는 기법은? 메커니즘으로.
- 답변: mark/복사 대부분 앱 실행 중 concurrent. 이름은 모르나 마킹 2단계(이번 GC 확인 여부 / 참조 주소 매칭 여부). 참조 조회 시 마킹 확인, 잘못된 주소면 정확한 주소로 수정 후 조회. STW는 GC root 조회·최종 동기화만. (사실상 정확)
- 면접관 보충: 그게 colored pointers(포인터 비트에 마킹 메타) + load barrier(읽는 순간 색 검사, relocated면 remap 후 조회). 이름만 몰랐지 원리 정확.

**꼬리질문 10-2 (조건 변형)**: ZGC가 항상 정답? 밤 대용량 배치라면? ZGC가 뭘 대가로 지불?
- 답변: ZGC는 조회마다 마킹 체크+수정하므로 부하 분산→처리량 하락. 배치는 G1으로 가끔 지연 감수하고 처리량 올리는 게 낫다. (정확)
- 면접관 보충: load barrier의 per-access 비용→throughput 하락. 순수 처리량이면 Parallel GC도. ZGC는 메모리 오버헤드도 큼.

**메모**: colored pointer+load barrier를 이름 없이 스스로 재구성(인상적). 조건 배치로 바꾸자 처리량 트레이드오프로 정확히 반전.

### [Q11] GC 튜닝 경험 / Full GC 빈발 추적 순서 — **상**

**본질문 답변 요지**: GC 튜닝 경험 없음. Full GC 빈발 시나리오: (1)static 미비움 누적 (2)ThreadLocal 미비움 (3)요청량 대비 young 작아 강제 승격 (4)장수 데이터가 old 상시 점유. 접근: 영역별 메모리 사용량 추이 → 힙 덤프로 내용 확인.

**꼬리질문 11-1**: 힙 덤프 전, 누수 vs 트래픽 할당압력 구분? 배포이력·GC로그 활용?
- 답변: 요청량과 메모리 추이 대조. 요청량 일정+GC 증가+메모리 우상향→누수. 요청량과 함께 GC 잦음→트래픽. (상관관계 방법론 정확)

**꼬리질문 11-2**: (1)누수 의심 시 배포이력 활용? (2)GC 로그의 heap-after-GC 추이에서 누수 결정적 시그니처는?
- 답변: (1)메모리 증가 시점 범위 추출→그 범위 배포이력 확인→메모리 건드는 로직 들어갔는지. (2)Full GC 돌았음에도 old 사용량 크면 누수 판단.
- 면접관 보충: (2)정밀화 — "old가 크다"만으론 정상적 큰 작업집합일 수도. 결정적 시그니처는 연속 Full GC들의 바닥(회수 직후 old)이 계단식 우상향.

**메모**: 직접 튜닝 경험 無이나 원인후보 체계적. 누수vs트래픽 상관관계로 가름, 배포이력 시간범위 대조. heap-after-GC 바닥상승 시그니처는 힌트 후. 튜닝 파라미터 관점 약함.

### [Q12] HashMap 내부 동작(충돌/리사이징/트리화) — **중** (상에 근접)

**본질문 답변 요지**: 버킷 안에 리스트, 길어지면 RB트리. hashCode로 버킷 결정. 리사이징은 기억 안 남. 트리화는 6개 이상(오인 — 정답 8).

**꼬리질문 12-1**: load factor(0.75)와 엮여 언제 리사이징 트리거? 버킷 개수 변화? 왜 비싼가?
- 답변: 64버킷 중 75% 이상 차면 2배 리사이징. (트리거·2배 정확)

**꼬리질문 12-2**: 리사이징 왜 비싼가(엔트리에 무슨 일)? 1만 건 미리 알면 어떻게 생성?
- 답변: 기존 데이터를 늘어난 해시만큼 재계산해 옮겨야 해서. 1만 건 넣을 구조로 초기 크기 지정. (rehash O(n) + 초기용량 최적화 정확)

**꼬리질문 12-3**: new HashMap<>(10000)이면 충분? load factor 0.75면 1만번째 전에 무슨 일? 초기 용량 얼마?
- 답변: 초기 용량 13500 정도. 그래야 0.75 안 넘김. (정확 — load factor로 나눠 잡는 통찰)
- 면접관 보충: 트리화는 버킷 배열 용량 64 이상일 때만, 미만이면 트리화 대신 리사이징(작은 맵 트리 오버헤드 회피).

**메모**: 시작 흔들림(리사이징 망각, 트리화 임계 6으로 오인→8). but 힌트 후 rehash 비용·초기용량÷load factor(13500)까지 정확 도달. 회복력·통찰 좋음. 핵심 메커니즘이 손끝에 있진 않음.

### [Q13] ConcurrentHashMap thread-safe 보장 / synchronizedMap 차이 — **중**

**본질문 답변 요지**: 내부에 락 거는 구조. synchronized가 코드상 있음. 무엇이 다른지는 모르겠다.
- 면접관 보충: synchronizedMap=맵 전체 단일 락(전면 경합). CHM=버킷(노드) 단위 락(Java8+ 버킷 헤드 synchronized+CAS), 다른 버킷은 안 막힘·읽기 대체로 무락.

**꼬리질문 13-1 (핵심)**: CHM 써도 `if(!containsKey) put()`은 왜 버그? 어떻게 고치나?
- 답변: 검사 시점과 넣는 시점이 원자적이지 않다. 원자적 함수 쓰거나 두 메서드를 원자적으로 묶기(synchronized). (착각 간파 정확)
- 면접관 보충: 외부 synchronized는 CHM 이점을 죽임. 정석은 putIfAbsent/computeIfAbsent 등 CHM 원자 메서드.

**메모**: 복합연산 비원자성(TOCTOU) 착각을 스스로 간파·원자메서드 치환 방향 정확(질문 핵심). but 내부 메커니즘(버킷락+CAS)·synchronizedMap(전체 단일락) 차이는 모름.

### [Q14] volatile — 가시성 vs 원자성 — **상**

**본질문 답변 요지**: 가시성=CPU 캐시에 두고 메모리 반영 지연으로 다른 스레드가 옛 값 보는 문제 방지, 항상 메모리에 쓰도록 보장. 원자성=한 스레드 작업 중 다른 스레드 끼어들지 못함. (정의 정확)

**꼬리질문 14-1**: volatile int count의 count++가 왜 여전히 유실되나? volatile이 왜 못 막나? 고치려면?
- 답변: count++는 읽기+연산+쓰기 복합. volatile은 읽기/쓰기 가시성만 보장, 나머지 원자성 못 보장. (정확)

**꼬리질문 14-2**: 제대로 고치려면?
- 답변: AtomicInteger 또는 synchronized로 감싸기. (정확)
- 면접관 보충: AtomicInteger=CAS 기반 무락 원자증가, synchronized=락 상호배제.

**메모**: 개념 정확, read-modify-write 복합성 정확 간파, 해결책 명확. 코드리뷰서 동시성 버그 잡을 수준.

### [Q15] JMM happens-before 관계 — **하**

**본질문 답변 요지**: 잘 모르겠다. (미접촉)
- 면접관 보충: A의 결과가 B에게 반드시 보이도록 보장되는 순서 관계. 컴파일러/CPU 재배열·캐시 때문에 멀티스레드 가시성이 저절로 보장 안 됨 → 그 보장 규칙 집합. 성립 예: synchronized unlock→lock, volatile 쓰기→읽기, thread.start()→스레드내부, 스레드내부→join(). 효용=동시성 정확성을 규칙으로 논증.

**메모**: 미접촉. volatile 이해했으니 "volatile 쓰기→읽기 happens-before"로 연결해 학습 권장.

### [Q16] ThreadLocal 용도 / 스레드풀 위험 — **상**

**본질문 답변 요지**: 스레드가 작업 중 스레드별로 보관해야 할 값에 사용. 스레드풀은 스레드가 사라지지 않고 반납되므로 안 비우면 계속 보관 → 메모리 문제. (정확)

**꼬리질문 16-1**: 메모리 말고, 이전 요청이 인증 정보를 안 비우고 반납하면 다음 요청은?
- 답변: 다음 사용자가 다른 사용자의 정보를 볼 수 있다. (힌트 한 번에 보안 위험 도달)
- 면접관 보충: 정보 유출 보안 사고. 요청 종료 지점(필터/인터셉터 finally)에서 반드시 remove().

**메모**: 용도·누수 정확, 힌트 한 번에 보안 위험 도달. 보안 위험 자발적 상기는 아직.

### [Q17] parallelStream 함부로 쓰면 안 되는 이유 — **하**

**본질문 답변 요지**: 잘 모르겠다. (미접촉)
- 면접관 보충: 모든 parallelStream이 JVM 전역 **공용 ForkJoinPool.commonPool** 하나를 나눠 씀(기본 크기=코어수-1). ① 웹 요청 처리 중 쓰면 한 기능의 무거운 병렬 작업이 공용 풀을 점유 → 다른 기능/요청까지 전부 굶음(장애 전파). ② 풀 스레드에서 블로킹 I/O 하면 코어수-1개 스레드가 전부 대기 → 서비스 전체 병렬 작업 정지. ③ 작은 컬렉션은 분할·병합 오버헤드가 이득을 초과. 쓰려면 전용 풀에 submit하거나 CPU-bound 대량 데이터 + 배치 등 격리된 맥락에서만.

**메모**: 미접촉. "편해 보이는 API 뒤의 숨은 공유 자원" 감각이 핵심 — ThreadLocal(스레드 재사용)을 이해한 만큼 commonPool(스레드 공유)로 연결해 학습 권장.

### [Q18] 제네릭 타입 소거 / PECS — **하**

**본질문 답변 요지**: 잘 모르겠다. (미접촉)
- 면접관 보충: 제네릭은 **컴파일 타임 전용 검사 장치** — 컴파일 후 바이트코드에서 타입 파라미터가 지워짐(`List<String>`도 `List<Integer>`도 런타임엔 그냥 `List`). 실무 제약: ① `obj instanceof List<String>` 불가 ② `new T()`, `new T[]` 불가 ③ 직렬화 라이브러리(Jackson 등)가 `List<User>`를 역직렬화할 때 타입을 몰라 `TypeReference`/`ParameterizedTypeReference` 같은 우회가 필요한 이유. PECS: Producer(꺼내 읽기만)=`? extends T`, Consumer(넣기만)=`? super T` — 공통 모듈 API 시그니처 유연성 설계 기준.

**메모**: 미접촉. 실무 접점(Jackson TypeReference를 써본 적 있다면 "왜 그게 필요한가"부터)으로 연결해 학습 권장. 2연속 미접촉(Q17~18) — 중급 후반부는 접촉면이 얇은 영역.

### [Q19] Optional 필드/파라미터 금지 이유·올바른 범위 — **중**

**본질문 답변 요지**: 쓰나 안 쓰나 null 검사하는 건 똑같다. 함수 리턴할 때만 쓰면 된다. 해당 함수가 null을 리턴할 수 있음을 호출자가 인지하게 하는 용도. (핵심 정확 — 반환 전용 + 부재 시그널)

**꼬리질문 19-1**: Optional<String> 필드가 가질 수 있는 상태는 몇 가지? 의도하지 않은 상태는?
- 답변: 잘 모르겠다.
- 면접관 보충: **3가지** — ① `null`(Optional 자체가 null) ② `Optional.empty()` ③ `Optional.of(x)`. ①이 의도하지 않은 상태: "null을 없애려던 도구가 자기 자신이 null이 되는" 이중 부재 문제 → 결국 Optional에 또 null 검사를 하게 돼 목적 자체가 붕괴. 부가로 Serializable 미구현이라 직렬화되는 엔티티/DTO 필드에 못 씀.

**메모**: 사용 규칙(반환 전용·시그널)은 정확히 체득 — 관용구 수준은 통과. 그러나 "왜"의 마지막 층(이중 부재, 3-state)은 미도달. 규칙을 알고 지키지만 근거를 남에게 논증하는 단계는 아직.

### [Q20] try-with-resources / 자원 누수 패턴 — **중**

**본질문 답변 요지**: 자원을 해제하지 않는 문제. try-catch에서 catch 중 에러가 나면 해제 누락, 또는 finally에서 에러가 난 경우. (방향 맞음, 다소 모호 — 전형 패턴을 코드 수준으로 특정하진 못함)
- 면접관 보충: 전형 패턴 ① close()가 finally 밖(try 본문 끝)에 있어 예외 시 건너뜀 ② finally에서 다중 자원 정리 시 첫 close()가 예외 던지면 나머지 누락 ③ finally의 예외가 try의 원래 예외를 삼킴(마스킹) — try-with-resources는 역순 자동 close + suppressed exception으로 원래 예외 보존.

**꼬리질문 20-1**: 커넥션 close 누락 배포 → 배포 직후 증상? 언제 장애?
- 답변: 커넥션 풀 고갈 → 무한 대기 장애. (종착점 정확. "배포 직후엔 멀쩡, 트래픽/누수 경로 빈도에 따라 지연 발화"라는 시간 축은 직접 언급 안 함)

**꼬리질문 20-2**: 수백 개 쿼리 지점 중 누수 지점을 어떻게 찾나?
- 답변: 잘 모르겠다.
- 면접관 보충: ① HikariCP `leakDetectionThreshold` — 임계 초과 보유 시 **빌린 시점의 스택트레이스**를 로그로 출력(누수 지점 직격) ② DB 쪽 `SHOW PROCESSLIST`/`pg_stat_activity`로 오래 물린 커넥션의 마지막 쿼리 확인 ③ 스레드 덤프로 커넥션 대기 중 스레드 확인 ④ 풀 메트릭(active 지속 증가) 모니터링.

**메모**: 장애의 종착점(풀 고갈)은 즉답 — 운영 감각 유지. 그러나 진단 도구·추적 절차 미접촉. "터진다"까지는 알고 "어디서 새는지 찾는" 단계가 빈 곳. leakDetectionThreshold 하나만 알아도 실전 대응이 달라짐.

### [Q21] 방어적 복사 / 내부 컬렉션 노출 — **중**

**본질문 답변 요지**: (정의를 반대로) "주소를 가리키는 변수만 복사하는 것"이라 정의. 단 문제 현상은 정확 — getter로 컬렉션 반환 후 외부에서 수정/추가/삭제하면 원본에 바로 반영.

**꼬리질문 21-1**: 방금 정의는 문제를 일으키는 쪽 아닌가? 재정의 + 막는 방법?
- 답변: (즉시 자가 교정) 방어적 복사 = 깊은 복사로 이 문제를 막는 것. 새 List를 만들고, 원시타입은 그대로/참조타입은 새로 생성해서 넣는다. (교정 정확, 단 기준이 원시/참조로 부정확)

**꼬리질문 21-2**: List<String>이면? String도 참조 타입인데 전부 새로 생성?
- 답변: String은 애초에 불변이라 상관없다. (정확 — 기준=가변/불변 스스로 도달)

**꼬리질문 21-3**: 수만 개 컬렉션, 복사 없이 외부 수정을 막는 방법과 함정은?
- 답변: 잘 모르겠다.
- 면접관 보충: `Collections.unmodifiableList(list)` — O(1) 래퍼 뷰, 수정 시도 시 UnsupportedOperationException. **함정 = 복사가 아니라 뷰**라서 원본이 내부에서 바뀌면 밖에서 그대로 투과되어 보임(스냅샷 아님). 진짜 불변 스냅샷이 필요하면 `List.copyOf()`(Java 10+, O(n) 복사지만 완전 독립). Kotlin의 List 인터페이스도 read-only일 뿐 backing이 가변이면 같은 문제.

**메모**: 문제 현상(참조 공유로 캡슐화 붕괴)은 명확히 이해, 정의를 반대로 말했다가 지적 한 번에 자가 교정 — 개념 골격은 있음. String 불변 연결로 가변/불변 기준까지 스스로 도달한 건 좋음. 표준 도구(unmodifiableList/copyOf) 미접촉이 감점.

### [Q22] static SimpleDateFormat 공유 (공유 가변 상태 리뷰) — **상**

**본질문 진행**: SDF 자체는 미접촉 — 대신 역질문("SDF는 상태 보관 필드가 있나, 행위만 하나?")으로 판단 기준을 먼저 세움. 유도("static 공유가 문제 되려면 어느 쪽?") 후 추론: "공유가 되려면 행위만 하는 클래스여야 한다. 포맷 패턴을 생성자로 받아 들고 있으니 데이터를 갖고 있는 것 같다" → 상태 보유라 공유 위험 결론 도달.
- 면접관 보충: 패턴뿐 아니라 format/parse **도중의 중간 계산값**을 내부 Calendar 필드에 쓰는 작업대 구조 — 공유하면 두 스레드가 같은 작업대 사용.

**꼬리질문 22-1**: 동시 format() 호출 시 증상? 왜 테스트를 전부 통과하나?
- 답변: 중간 계산값이 오염돼 의도치 않은 데이터를 읽으며 로직 진행. 테스트는 보통 단일 스레드라 재현 안 됨. (정확)
- 면접관 보충: 값이 조용히 섞이거나(다른 요청의 날짜) 간헐 파싱 예외.

**꼬리질문 22-2**: 같은 유형(공유 가변 상태) 함정을 Spring 앱 어디서 점검?
- 답변: 싱글턴 객체의 필드 데이터를 확인. (Spring에서의 핵심 지점 정확 — 싱글턴 빈의 가변 인스턴스 필드)
- 면접관 보충: + 가변 static 필드 전수, non-thread-safe 유틸(DecimalFormat, Calendar) 공유, 동기화 없는 HashMap 캐시. 해결책: DateTimeFormatter(불변·thread-safe)로 교체, 또는 ThreadLocal/지역 변수화.

**메모**: 이 스레드가 후보자의 최대 강점을 보여줌 — 모르는 클래스를 만나자 "상태 유무"라는 판단 기준부터 세우는 역질문, 시그니처 관찰로 추론, 증상·테스트 통과 이유·싱글턴 빈 일반화까지 유형으로 사고. 함정을 목록이 아니라 유형으로 아는 리뷰어의 사고 방식. DateTimeFormatter 대체재는 미언급.

### [Q23] OOM 힙 덤프 분석 과정 — **중**

**본질문 답변 요지**: ① 힙 사용량·요청량 상관 관찰 → 요청량 증가 동반이면 순수 자원 부족, 요청량 그대로면 누수 의심 ② 코드에서 자원 미해제·static 누적 구조부터 점검 ③ 판단 불가 시 힙 덤프 ④ 어떤 객체가 많은지·누가 붙잡는지 확인. (절차 합리적 — 트래픽vs누수 판별 우선, 덤프는 최후 수단)

**꼬리질문 23-1**: 운영 중 덤프 뜨면 무슨 일? 어떻게 확보?
- 답변: STW가 발생해 멈춘다. OOM 나면 어차피 죽으니 그때 뜨도록 미리 설정한다. (정확 — `-XX:+HeapDumpOnOutOfMemoryError`. 경험 진위 판별 지점 통과)

**꼬리질문 23-2**: 덤프 히스토그램 1위 byte[], 2위 String — byte[]가 범인?
- 답변: 왜 byte[]가 많은지, 누가 참조하고 있는지를 봐야 한다. (방향 정확 — 히스토그램 상위는 항상 byte[]/char[]/String, 보유자 추적 필요)

**꼬리질문 23-3**: shallow size vs retained size? 왜 retained 기준 정렬?
- 답변: 잘 모르겠다.
- 면접관 보충: shallow=객체 자신의 크기, retained=**그 객체가 GC되면 함께 해제되는 총량**(지배하는 서브그래프 전체). 누수 분석은 "보유 책임"을 찾는 일이므로 retained 기준 — 예: HashMap 자체는 48바이트(shallow)지만 retained 3GB면 그게 범인. MAT의 dominator tree·Leak Suspects·path to GC roots가 이 관점의 도구.

**메모**: 운영 절차(판별→코드→덤프)와 현실 제약(STW, 사전 설정)은 실전 감각 확실 — rationale의 경험 판별 지점은 통과. 그러나 분석 단계의 도구 어휘(retained/dominator/GC root path)가 전무 — 덤프를 실제로 열어 범인을 찾아본 경험은 없거나 얕음. "확보까지는 상, 분석부터는 하"라 종합 중.

### [Q24] 스레드 덤프 데드락 / 4조건 / 예방 — **하**

**본질문 답변 요지**: 덤프를 뜨면 마지막에 락을 정리해서 알려준다(정확 — jstack "Found one Java-level deadlock" 자동 탐지). 4가지 조건은 모른다.

**꼬리질문 24-1**: A: 락1→락2, B: 락2→락1 — 코드 레벨 원천 차단 규칙? 순서 통제 불가 시 차선책?
- 답변: 잘 모르겠다.
- 면접관 보충: ① **락 획득 순서 전역 고정**(모두 락1→락2로만) — 순환 대기가 구조적으로 불가능해짐 ② 순서 통제 불가 시 `ReentrantLock.tryLock(timeout)` — 못 잡으면 포기·해제·재시도로 무한 대기 제거. 4조건 = 상호배제·점유대기·비선점·순환대기, 예방 = 이 중 하나만 깨면 됨(순서 고정=순환대기 제거, tryLock=점유대기 제거). synchronized는 타임아웃이 없어 이 차선책이 불가능한 것도 ReentrantLock 선택 이유 중 하나.

**메모**: 탐지(덤프 자동 정리)는 실무형으로 알고 있으나 4조건·예방 전략 미접촉. "재시작으로 덮으면 반복된다"는 rationale 관점에서 순환을 끊는 설계 규칙이 빈 곳. 데드락 예방은 DB 락(같은 행을 다른 순서로 UPDATE)에도 동일 유형이라 학습 가치 높음.

### [Q25] JIT 동작이 성능에 미치는 영향 — **상**

**본질문 답변 요지**: 처음엔 인터프리터, 자주 쓰는 것은 부분 컴파일, 더 자주 쓰면 큰 범위로 컴파일(계층형 컴파일 골격 정확). 따라서 시작 직후 워밍업 존재. 성능 측정도 워밍업 후에야 정확. (rationale의 두 축 — 배포 직후 latency·측정 오염 — 모두 자발적 도달)

**꼬리질문 25-1**: 무중단 배포, 새 인스턴스 LB 투입 직후 latency 스파이크 완화?
- 답변: K8s에서 readiness probe 통과 전에 예열 요청을 날려 클래스 로딩(·JIT)을 미리 유도. (정확, 실무 정석)
- 면접관 보충: + LB slow start(투입 초기 트래픽 점진 램프업).

**꼬리질문 25-2**: 탈최적화 — 왜 컴파일한 코드를 버리나? (추론 허용)
- 답변: 다형성으로 인해 컴파일 시점의 행동과 현재 요청의 행동이 달라지는 경우. (추론으로 정답 도달 — 낙관적 타입 가정 붕괴)
- 면접관 보충: JIT은 프로파일 기반 낙관적 최적화(단형 호출 지점 인라이닝 등)를 하고, 새 서브타입 등장·새 클래스 로딩으로 가정이 깨지면 되돌린 후 재수집. C1(빠른 컴파일)/C2(공격적 최적화) 계층 명칭.

**메모**: 이름(C1/C2)은 몰라도 모델은 정확 — 워밍업·측정 오염·예열 배포·탈최적화 원인(다형성 가정 붕괴)까지 추론 도달. static SDF에 이어 "원리에서 추론하는" 강점 재확인.

### [Q26] synchronized / ReentrantLock / StampedLock / CAS 선택 기준 — **상**

**본질문 답변 요지**: synchronized=기본 락 / ReentrantLock=타임아웃·인터럽트 등 옵션 / StampedLock=조회 많을 때 낙관적 락 / Atomic=단일 변수. (4개 도구 포지션 전부 정확·간결)

**꼬리질문 26-1**: 수십 스레드 초당 수백만 증가 카운터에 AtomicLong — 왜 기대만큼 안 빠른가?
- 답변: CAS가 변경 적용 시 원래 조회한 값과 일치하는지 확인하는데 극한 경합에선 항상 달라져 있어 계속 재시도 루프가 돈다. (정확 — 락은 없지만 진행도 없는 공회전)

**꼬리질문 26-2**: 재시도 폭증을 구조적으로 피하는 설계 아이디어? (클래스명 몰라도 됨)
- 답변: 스레드마다 각자의 카운터를 두고 조회할 때 합산한다. (LongAdder의 설계를 스스로 도출 — 쓰기 경합 분산+읽기 시 집계)
- 면접관 보충: = `LongAdder`(셀 배열 분산, sum()). 쓰기 초고빈도·읽기 저빈도 카운터의 정석. 정확한 스냅샷이 필요하면(sum은 약한 일관성) AtomicLong 유지라는 트레이드오프.

**메모**: 도구 분류·CAS 실패 메커니즘·해결 설계까지 전부 자력 — 동시성 파트(Q13 ConcurrentHashMap, Q14 volatile+AtomicInteger)와 일관되게 강함. rationale의 "경합도·읽기/쓰기 비율 기반 트레이드오프 판단" 충족.

### [Q27] False sharing — **상**

**본질문 답변 요지**: (용어 자체는 미접촉, "캐시가 메모리를 읽는 단위" 힌트 제공) "CPU가 캐시 라인 단위로 읽어서 서로 무효화시키는 것 같다" — 힌트 한 개로 현상의 메커니즘 전체를 즉시 재구성.
- 면접관 보충: 서로 다른 스레드가 서로 다른 변수를 써도 같은 캐시 라인(64B)에 있으면 한쪽 쓰기가 상대 코어의 라인 전체를 무효화 — 논리적 비공유·물리적 공유라서 "false".

**꼬리질문 27-1**: 회피는?
- 답변: 패딩을 붙인다. (정확)
- 면접관 보충: JDK는 `@Contended`(LongAdder 셀에 실제 적용). 프로파일러에 잘 안 잡히는 병목이라 고빈도 집계·이벤트 처리에서 아는 사람만 잡는 유형.

**메모**: 용어는 몰랐지만(하드웨어 층 직접 경험은 없다는 신호) 힌트 하나로 현상→원인→처방 전부 도출. ZGC colored pointer 재구성(세션1)과 같은 패턴 — 지식의 폭보다 재구성 능력이 강점.

### [Q28] Virtual Thread / pinning — **상**

**본질문 답변 요지**: 기존 모델=OS 스레드와 JVM 스레드 강결합(1:1). 가상 스레드=OS 스레드 위 캐리어, 그 위에 가상 스레드. 물러날 때 콜 스택·실행 위치를 힙에 저장, 재마운트 시 복원해 멈춘 지점부터 재개. JNI는 스택을 정확히 캡처 못해 고정. synchronized는 OS 스레드와 강결합("커널 연결 명령어" — 부정확)이라 그 안에서 I/O 블로킹 시 캐리어를 놔주지 않는 것이 pinning. (모델 상세 정확, 최고 수준 답변)
- 면접관 교정: synchronized pinning의 원인은 커널 명령이 아니라 **모니터 소유권이 캐리어 기준으로 기록**되어 언마운트 시 락 의미가 깨지기 때문. JDK 24(JEP 491)부터 대부분 해소.

**꼬리질문 28-1**: Spring MVC+JPA에 가상 스레드 켜기 전 점검?
- 답변: DB 커넥션 고갈 확인. (핵심 — 면접관 프레임 보충: 톰캣 스레드 수 = 암묵적 동시성 상한이 사라져, 스레드 수로 동시성 제어하던 가정 전부 붕괴. 세마포어 등 명시적 제한 필요)

**꼬리질문 28-2**: ThreadLocal 많이 쓰는 코드베이스라면? (재사용 위험의 반대 방향)
- 답변: 가상 스레드는 재사용이 없어 스레드마다 ThreadLocal 복사본이 생겨 메모리 폭발. (정확)
- 면접관 보충: 비싼 객체를 ThreadLocal에 캐시하던 패턴도 무의미해짐. 대체재 = ScopedValue(JDK 21+).

**메모**: 1장 전체에서 가장 완성도 높은 본질문 답변 — 마운트 모델·스택 힙 저장·JNI까지 스스로 서술. 도입 판단(rationale 의도)도 커넥션 풀·ThreadLocal 양쪽 모두 정확. 신기술을 하이프가 아니라 제약으로 보는 습관 확인. synchronized 원인의 부정확만 옥에 티.

### [Q30] Integer 캐싱과 == 비교 — **중**

**본질문 답변 요지**: Integer는 -128~127 범위를 캐싱해 그 안에서는 같은 객체를 반환하기 때문. (메커니즘 정확)

**꼬리질문 30-1**: 왜 특히 위험한 유형인가? (발견 시점 관점)
- 답변: 범위를 벗어나는 Integer를 비교하는 경우가 있을 것이다. (트리거 재진술 — "테스트 통과형 잠복 버그"라는 유형화까지는 미도달)
- 면접관 보충: 테스트는 작은 값(1, 2, 100)으로 쓰니 전부 통과 → 운영에서 ID가 127을 넘는 순간부터만 조용히 false. static SDF와 같은 "테스트가 못 잡는 유형". 박싱 타입 비교는 무조건 equals() 또는 언박싱.

**메모**: 캐싱 메커니즘은 정확. 다만 위험의 유형화(왜 테스트를 통과하고 잠복하는가)는 유도에도 미도달 — Q22에선 스스로 해냈던 사고라 아쉬움.

### [Q31] Strong/Soft/Weak 참조, WeakHashMap — **하**

**본질문 답변 요지**: 잘 모르겠다. (미접촉)
- 면접관 보충: Strong=일반 참조, 있는 한 GC 불가. Soft=메모리 부족할 때만 회수(메모리 민감 캐시). Weak=다음 GC에서 바로 회수(강한 참조가 없다면). WeakHashMap=키를 약참조로 보유 — 키 객체가 밖에서 더는 안 쓰이면 엔트리가 자동 제거되는 맵. 용도=객체에 부가 정보를 매달되 생명주기를 따라가게(리스너·메타데이터 캐시). 일반 HashMap 캐시는 키가 살아있는 한 영원히 누수라는 대비가 핵심.

**메모**: 미접촉. OOM/누수 학습(힙 덤프 노트)과 묶어서 보면 좋음 — "캐시가 누수가 되는 경계"라는 관점.

### [Q32] BigDecimal equals vs compareTo — **하**

**본질문 답변 요지**: 잘 모르겠다. (미접촉)
- 면접관 보충: `equals`는 값+**scale**까지 비교 — `new BigDecimal("1.0").equals(new BigDecimal("1.00"))` → **false**. `compareTo`는 수치만 — `compareTo(...) == 0` → true. 버그: DB가 1.00으로 돌려주고 코드가 1.0을 만들면 equals 기반 금액 비교·HashSet/HashMap 포함 검사가 조용히 어긋남. 금액 수치 비교는 반드시 `compareTo() == 0`.

**메모**: 미접촉. Integer 캐싱(Q30)과 묶이는 유형 — "같아 보이는 값의 동등성 함정, 테스트 통과형". 금액 다루는 도메인이면 우선 학습.

## 📌 이 섹션 약점 노트 (재도전 대상)

- [ ] 기본 > JVM 메모리 — OOM 에러 문구별 영역 판별(Java heap space / Metaspace / GC overhead limit / native thread) 즉시 인지
- [ ] 기본 > StringBuilder/StringBuffer — StringBuilder는 thread-safe X(빠름), StringBuffer는 synchronized(느림). StringBuilder 진짜 목적=가변 버퍼로 반복연결 O(n²)→O(n)
- [ ] 기본 > 인터페이스vs추상클래스 — 상속(템플릿메서드) 단점(단일상속/경직결합/변형폭발) vs 합성 이점, "상속보다 합성" 근거 설명
- [ ] 기본 > Stream 남용 — forEach 부수효과(병렬 경쟁조건), map내 I/O(N+1은 공통 문제지만 지연평가로 은폐), 대안=collect/reduce·batch조회
- [ ] 기본 > enum 고급 패턴 — 전략 메서드 enum, 상태전이 enum(canMoveTo). if-else 산탄 제거·컴파일러 강제
- [ ] 중급 > HashMap — 트리화 임계 8(복귀 6)·용량 64 조건, 리사이징 트리거(용량×0.75)·2배 확장 즉시 상기
- [ ] 중급 > ConcurrentHashMap — 내부 메커니즘(버킷단위 락+CAS, 읽기 무락) vs synchronizedMap(맵 전체 단일 락) 차이
- [ ] 중급 > happens-before — 정의·필요성(재배열/캐시)·성립 규칙(synchronized/volatile/start·join). volatile과 연결
- [ ] 중급 > parallelStream — 공용 ForkJoinPool.commonPool 공유(코어수-1), 웹 요청 처리서 장애 전파·블로킹 I/O로 풀 고갈. 대안=전용 풀 격리
- [ ] 중급 > 타입 소거/PECS — 제네릭=컴파일 타임 전용(런타임 소거), instanceof/new T 불가, Jackson TypeReference 필요 이유. PECS(Producer extends/Consumer super)
- [ ] 중급 > Optional 필드 3-state — null/empty/of 3가지 상태, "null 없애려는 도구가 자신이 null" 이중 부재 논증. Serializable 미구현
- [ ] 중급 > 커넥션 누수 진단 — HikariCP leakDetectionThreshold(빌린 스택트레이스 로그), pg_stat_activity/PROCESSLIST, 풀 active 메트릭. suppressed exception(예외 마스킹 해결)도 함께
- [ ] 중급 > 컬렉션 불변 노출 도구 — unmodifiableList(O(1) 뷰, 원본 변경 투과 함정) vs List.copyOf(O(n) 독립 스냅샷) 구분
- [ ] 고난이도 > 힙 덤프 분석 어휘 — shallow vs retained(GC 시 함께 해제되는 총량=보유 책임), dominator tree, path to GC roots. MAT로 한 번 직접 열어볼 것
- [ ] 고난이도 > 데드락 — 4조건(상호배제·점유대기·비선점·순환대기), 예방=하나만 깨기: 락 순서 전역 고정(순환대기), tryLock 타임아웃(점유대기). DB 락에도 동일 유형
- [ ] +α > Integer 캐싱 위험 유형화 — 작은 값 테스트 통과→운영 큰 값에서만 발현하는 잠복 버그(SDF와 동일 유형). 박싱 비교=equals()
- [ ] +α > 참조 3종/WeakHashMap — Soft(메모리 부족 시 회수=캐시), Weak(다음 GC 회수), WeakHashMap=키 생명주기 따라가는 맵(리스너/메타데이터). HashMap 캐시=영원한 누수 대비
- [ ] +α > BigDecimal — equals=값+scale(1.0≠1.00), compareTo=수치만. 금액 비교는 compareTo()==0, HashSet 포함 검사 함정
- 태도 관찰: "문구 나오면 AI한테 물어보면 되지 않나" — 장애 대응의 즉각 판독 중요성 재확인 필요. 단, 역질문(전제 왜/N+1 반문)은 사고력 좋음.
