# 3. JPA / ORM — 문답 기록

## 기본 ⭐

### [Q1] JPA를 사용하는 이유 / MyBatis와의 차이 — **중**

**본질문 답변 요지**: "DB와 연결되는 데이터를 보다 객체스럽게 사용하기 위함. MyBatis는 SQL을 쓰기 때문에 DB에 저장되는 클래스가 DB와의 연결강도가 높아지지만, JPA는 그 연결강도를 줄일 수 있다." (방향은 맞으나 '객체스럽게'·'결합도'가 모두 미정의 상태)

**꼬리질문 1-1**: 운영 테이블에 컬럼 1개 추가 + 조회 조건 1개 추가 시, MyBatis/JPA 각각 손으로 고칠 지점은? 그게 결합도 차이의 실체인가?
- 답변: MyBatis는 맵핑 파일 수정 + 연결 클래스 수정. JPA는 객체에 필드 추가만. 조회 조건은 MyBatis는 쿼리 수정, JPA는 인터페이스 메서드 명만 수정. (수정 지점 비교는 정확하나 '편의성' 층에 머묾)

**꼬리질문 1-2**: 선택적 조건 6개(이름·이메일·가입일 범위·상태·조직·마지막 로그인) 조합 검색 화면 — 메서드 이름 방식으로 되나? 실제로 어떻게 처리했나?
- 답변: 만들 수 없다. JPQL 또는 QueryDSL을 사용해서 처리했다. (한계선 즉시 인정 — 좋음)

**꼬리질문 1-3 (반론)**: QueryDSL/JPQL을 쓰는 순간 조회 쿼리를 직접 설계하는 셈인데, 그러면 "결합도 감소" 이점은 유지되나? QueryDSL 조회 코드와 MyBatis 조회 코드의 차이는?
- 답변: QueryDSL은 컴파일 시점 타입 체크와 엔티티 기반이라 차이가 있다. MyBatis는 순수 쿼리다. (여기서 멈춤 — QueryDSL vs MyBatis 차이일 뿐, JPA vs MyBatis의 결합도 층으로 올리지 못함)

**꼬리질문 1-4**: 반대로 MyBatis를 골라야 한다고 판단하는 상황은? 실제 프로젝트는 무엇을 썼고 누가 어떤 근거로 정했나?
- 답변: 간단한 CRUD가 별로 없고 복잡한 서브쿼리가 존재하며 쿼리 최적화가 자주 필요한 경우 MyBatis가 유리하다. 실제 프로젝트는 JPA를 사용했고, 근거는 빠른 개발과 간단한 CRUD가 많은 유형의 서비스여서. (선택 기준 축은 정확. 단, 결정 주체는 답 없음 — 스택 논의 참여 경험은 아닌 것으로 판단)

**면접관 보충**:
- **결합도의 실체 3층** — ① 방언/벤더 종속(JPA는 Dialect가 SQL 생성 vs MyBatis는 SQL 문법이 코드에 박제) ② SQL 자체가 애플리케이션에 없어 스키마 변경이 XML 전수 검사로 번지지 않음 ③ **도메인 로직을 엔티티 안에 둘 수 있음** — MyBatis의 VO는 결과셋 그릇이라 로직이 서비스로 새어나감. 여기가 "객체스럽게"의 진짜 값.
- **JPA의 대가** — 쿼리가 코드에 안 보여 의도치 않은 쿼리(N+1, 불필요 UPDATE)가 조용히 나감 → 쿼리 로그 상시 확인 습관이 필수. MyBatis의 최대 장점은 쿼리가 눈에 보이는 것.
- **실무의 현실적 답은 병용** — 쓰기는 ORM(변경 감지·객체 그래프), 통계·리포트·대량 조회는 MyBatis/native. "쓰기는 ORM, 읽기는 SQL"이 대용량 서비스의 흔한 구도.

**메모**: 개념 방향은 맞고 도구 한계선 인정도 빠르지만, 답변 전체가 **"JPA는 편하다" 단면 서사**. 트레이드오프의 아픈 쪽(JPA의 대가)을 한 번도 자발 언급하지 않은 것이 이 평가의 핵심 사유 — 1·2장에서 반복된 "트레이드오프 근거 서술 약함" 패턴의 연장. 반론을 받았을 때 논점을 한 층 올리는 힘(타입 체크 → 벤더 종속·도메인 모델)이 아직 부족.

### [Q2] 영속성 컨텍스트 / 1차 캐시 / 쓰기 지연 / 변경 감지 — **중**

**본질문 답변 요지**: "하나의 트랜잭션에 속한 엔티티 데이터를 메모리에 보관하는 것. 1차 캐시는 조회 시 메모리에서 꺼내 쓰는 것. 쓰기 지연은 트랜잭션 끝나기 직전에 한 번에 쓰기 쿼리를 날리는 것. 변경 감지는 스냅샷을 갖고 있다가 트랜잭션 끝나기 전 비교해서 UPDATE를 만드는 것." (네 개념 모두 방향 정확. 다만 "변경된 데이터를 분리해서 갖고 있다"는 표현은 모델이 흐릿함 — 실제로는 엔티티 인스턴스 자체가 변경되고 스냅샷은 로드 시점 복사본)

**꼬리질문 2-1**: 조회 전용 화면에서 엔티티 1,000건을 읽고 아무것도 수정하지 않았다. 커밋 시점에 애플리케이션이 하는 일이 있나? 비용은 어디서 발생하나?
- 답변: "1,000건이 영속성 컨텍스트에 올라가고, 커밋 시점에 정리한다. 비용은 메모리와 GC이지 않을까." (스냅샷 메모리는 짚었으나 **flush 시 전건 비교라는 CPU 비용에 미도달**)

**꼬리질문 2-2 (힌트 제공)**: 스냅샷은 언제 만들어지나? 1,000건이면 비교가 몇 번 일어나나? 수정하지 않은 엔티티도 비교 대상인가?
- (후보자 역질문: "readOnly 옵션인가 default인가?" → 기본 설정으로 답함. 조건을 스스로 확인하려 한 점은 좋음)
- 답변: "조회 시점에 스냅샷 생성, 커밋 시점에 스냅샷과 현재 데이터를 비교. 1,000건 비교가 일어난다. 수정하지 않은 엔티티도 대상이다. **수정 여부는 비교하고 나서야 알기 때문.** readOnly=true면 스냅샷을 생성하지 않는다." (정확 + readOnly의 효과를 자발 언급 — 이 스레드의 최고점)

**꼬리질문 2-3**: 조회성 API인데 `updated_at`이 갱신되고 감사 로그에 UPDATE가 남는다는 운영 문의. 원인을 어디부터 좁히나? 유사 경험은?
- 답변: "조회성 API에 엔티티 필드를 업데이트하는 메서드를 쓰는지 확인한다." (첫 단계로는 타당하나 그 이상 확장 없음. **경험 질문에는 응답 없음 → 실제 진단 경험 부재로 판단**)

**꼬리질문 2-4**: 수정 메서드가 전수 조사에서 정말 없었는데도 매 조회마다 UPDATE가 나간다. 무엇이 남았나?
- 답변: "변경 감지 비교에 equals/hashCode를 쓴다면 그 문제 아닐까." (추측. 기본 필드 dirty checking은 엔티티 equals/hashCode를 쓰지 않고 Hibernate 타입별 비교기를 씀)

**꼬리질문 2-5 (힌트 제공)**: 자바 필드 타입과 DB 컬럼 타입이 1:1로 안 맞는 경우 — `char(1)`↔String, `NUMBER`↔BigDecimal, 컬렉션 필드. 하나 골라 왜 "변경됨"으로 판정되는지 설명해보라.
- 답변: "잘 모르겠다."

**면접관 보충**:
- **영속성 컨텍스트의 정체는 4가지 저장소** — ① 1차 캐시(`@Id` → 엔티티 인스턴스 맵) ② 스냅샷 저장소(로드 시점 필드값 복사본) ③ 쓰기 지연 SQL 저장소 ④ 그 결과로 얻는 **동일성 보장**(같은 트랜잭션에서 같은 id 조회 시 `==`가 참). 1차 캐시는 성능 캐시가 아니라 **동일성·정합성 장치**다 — 범위가 트랜잭션이라 히트율에 기대는 설계는 잘못.
- **flush의 실제 비용** — 스냅샷 때문에 엔티티 메모리가 사실상 2배, 그리고 flush마다 `O(관리 엔티티 수 × 필드 수)` 비교. 조회 전용은 `@Transactional(readOnly=true)`(Hibernate 세션 read-only → 스냅샷 생략 + FlushMode.MANUAL) 또는 **DTO 프로젝션**(애초에 영속성 컨텍스트에 안 올림).
- **flush 실행 순서는 코드 순서가 아니다** — INSERT → UPDATE → DELETE 고정. "DELETE 먼저 하고 INSERT 했는데 유니크 제약 위반"이 여기서 나온다(중급 문항에서 다시 다룸).
- **기본 UPDATE는 전 컬럼 UPDATE** — 변경된 컬럼만 나가지 않는다. `@DynamicUpdate`로 바꿀 수 있으나 매번 SQL을 새로 만들어 구문 캐시 이점을 잃는 트레이드오프.
- **"안 시킨 UPDATE"의 실제 단골 원인** — ① **BigDecimal scale 불일치**(`1.10` vs `1.1`은 `equals` 기준 다름) ② **컬렉션 재할당**(`setItems(new ArrayList<>(...))` → 관리 컬렉션 교체로 보고 전체 DELETE+INSERT) ③ **AttributeConverter의 왕복 비대칭**(Y/N↔Boolean에서 null↔false) ④ **시간 타입 정밀도**(DB는 초, 자바는 나노초) ⑤ **OSIV 켜짐 상태에서 컨트롤러/DTO 변환 중 setter 호출** → 다음 트랜잭션 진입 시 유령 UPDATE. `updated_at`은 dirty일 때만 갱신되므로 **원인이 아니라 결과**다.
- **진단 도구** — `org.hibernate.SQL` + 바인딩 파라미터 로깅(p6spy/datasource-proxy), `SessionFactory` Statistics의 `entityUpdateCount`, 그리고 결정적 한 방: **flush 이벤트 리스너에서 스택트레이스를 찍어 어느 코드가 dirty를 만들었는지 역추적**.

**메모**: 개념 4종의 설명은 정확하고, `readOnly=true`의 스냅샷 생략을 스스로 꺼낸 것은 기본⭐ 기준 상급. 그러나 rationale의 핵심 검증 지점 — "이상 동작이 났을 때 속수무책인가" — 에서 막혔다. flush 비용을 힌트 없이 못 짚었고, 유령 UPDATE 진단은 첫 단계 이후 확장이 없었으며 **경험 질문에 응답 자체가 없었다**(Q1의 "실제 결정 주체 답 없음"과 같은 패턴 — 운영 중 이상 동작을 직접 추적해본 이력이 얇은 것으로 보임). 개념 층은 상, 진단·경험 층은 하 → 종합 **중**.

### [Q3] 즉시 로딩(EAGER) vs 지연 로딩(LAZY), 기본 전략 — **중**

**본질문 답변 요지**: "즉시 로딩은 연관 엔티티를 조회 시 함께 불러오는 것, 지연 로딩은 사용할 때 불러오는 것. 프로젝트 기본 전략은 지연 로딩. 이유는 연관 엔티티를 바로 사용하는 곳보다 사용하지 않는 곳이 더 많아서." (정의·선택 정확. 근거는 "낭비 회피" 한 축에 머묾 — EAGER의 구조적 위험 미언급)

**꼬리질문 3-1**: 지연 로딩을 기본으로 관철하려면 코드에서 실제로 무엇을 해야 하나? JPA 명세의 연관관계별 기본값은? 그 기본값이 왜 그렇게 정해졌다고 보나?
- 답변: "연관관계 매핑 시 LAZY 옵션을 명시해야 한다. 1대1은 즉시 로딩, **다대1이나 1대다는 지연 로딩이 기본값.** 이유는 1대1은 즉시 로딩 가능성이 높고 다대1·1대다는 낮아서가 아닐까." (`@OneToOne` EAGER ✓, `@OneToMany` LAZY ✓, **`@ManyToOne`을 LAZY로 오답** — 실무에서 가장 많이 쓰는 연관의 기본값을 틀림)

**꼬리질문 3-2 (반론)**: `@ManyToOne`이 지연 로딩 기본값이라고 확신하나? 명세가 기본값을 가르는 축은 "즉시 로딩 가능성"이 아니라 단일 값 연관(to-one) vs 컬렉션 연관(to-many)이다. 다시 생각해보라.
- 답변: "다대1은 내가 '다'고 연관된 데이터가 '1'이라 하나밖에 없어 즉시 로딩이 기본값이다." (**자기 교정 성공.** 힌트를 받고 명세의 논리를 스스로 재구성 — 이 스레드의 가점 요소)

**꼬리질문 3-3 (반론)**: "EAGER면 조인 한 번에 다 가져오니 효율적 아닌가?" `em.find()`는 실제로 조인이 나간다. 그런데 같은 엔티티를 JPQL(`select o from Order o`)로 조회하면 EAGER `@ManyToOne`이 조인으로 나가나?
- 답변: "이때는 join으로 나가지 않는다." (**즉답 정확** — 쿼리 로그를 실제로 본 사람의 답으로 판단)

**꼬리질문 3-4**: 그럼 무슨 쿼리가 나가나? 왜 조인으로 안 나가나?
- 답변: "작성한 쿼리대로 나간다. 이유는 정확히는 모르겠지만 JPA 설정 상 JPQL로 join을 명시하지 않는 이상 조인으로 안 나간다." (관찰은 정확하나 **메커니즘 미도달**. "설정"이 아니라 JPQL 번역 원리라는 점을 놓침)

**꼬리질문 3-5**: JPQL이 그대로 SQL로 나갔는데 EAGER 연관은 즉시 로딩이어야 한다. 그 연관 엔티티는 어떻게 채워지나? 결과가 100건이면 총 쿼리 수는?
- 답변: "설마 n+1로 나가나?" (유도 끝에 도달. 자발적 연결은 아니었음)

**면접관 보충**:
- **LAZY의 실체는 프록시** — Hibernate가 바이트코드로 만든 하위 클래스 인스턴스를 필드에 넣어두고 실제 접근 순간 초기화 쿼리를 날린다. 트랜잭션 밖 접근 → `LazyInitializationException`.
- **기본값 정리** — `@ManyToOne`·`@OneToOne` = **EAGER**, `@OneToMany`·`@ManyToMany` = LAZY. 가르는 축은 단일 값 연관 vs 컬렉션 연관(크기 예측 불가). 결론: **to-one은 전부 손으로 `fetch = LAZY`를 명시해야 한다.**
- **JPQL에서 EAGER가 N+1이 되는 메커니즘** — JPQL은 작성한 대로 SQL로 번역되고 **글로벌 fetch 전략은 이 번역에 개입하지 않는다.** 번역된 SQL 실행 후 Hibernate가 EAGER 계약을 지키려고 조회된 행마다 연관을 추가 쿼리로 채운다 → 1 + N. 위험한 건 **`find()`는 조인이 나가므로 단건 테스트에서 안 보이고 목록 API에서만 터진다**는 비대칭성.
- **EAGER 금지의 나머지 두 근거** — ① **연쇄 전파**: Order→Member→Team이 전부 EAGER면 조인 depth가 누적돼 엔티티 하나 조회에 테이블 10개가 붙는다 ② **결정적으로, 쿼리 단위로 끌 수 없다.** LAZY를 fetch join으로 켜는 건 쉬운데 EAGER를 특정 쿼리에서만 끄는 건 불가능하다. **기본값은 되돌릴 수 있는 방향으로 둔다** — 후보자의 "안 쓰는 곳이 더 많아서"보다 한 층 위의 근거.
- **정답 조합** — LAZY 전역 기본 + 필요한 지점에서 명시적 fetch(fetch join / `@EntityGraph` / `@BatchSize` / DTO 프로젝션). LAZY의 대가(LazyInitializationException, N+1)를 아는 상태에서의 선택이어야 한다.
- **함정** — `@OneToOne`의 주인이 아닌 쪽(`mappedBy`)은 LAZY를 걸어도 걸리지 않는다. FK가 상대 테이블에 있어 연관이 null인지 알 수 없으므로 프록시를 만들 수 없고 즉시 쿼리가 나간다.

**메모**: Q1·Q2에서 반복된 "트레이드오프 한쪽만 서술" 패턴이 여기서도 나왔다 — LAZY를 고른 근거가 "낭비 회피"뿐이고, EAGER의 구조적 위험(쿼리 단위 제어 불가, JPQL 비대칭)은 유도해야 나왔다. 다만 **이 스레드에서 처음으로 자기 교정이 나왔다**(꼬리 3-2) — 반론을 받고 논점을 스스로 다시 세운 첫 사례로, Q1에서 지적했던 "반론 시 논점을 한 층 올리는 힘 부족"이 개선될 여지를 보였다. "JPQL에서는 조인이 안 나간다"를 즉답한 것도 실제 쿼리 로그 관찰 경험의 근거로 본다 — Q2의 진단 경험 부재 평가를 일부 상향할 재료.

### [Q4] N+1 문제란? 해결책은? — **중**

**본질문 답변 요지**: "한 번의 쿼리에 연관된 데이터의 추가 쿼리가 발생하는 것. 엔티티를 List로 조회했는데 각 엔티티의 연관 데이터를 조회하느라 List 개수만큼 쿼리가 나가는 것. 해결은 join으로 한 번에 가져오거나, 추가 쿼리에서 모든 데이터를 가져와 애플리케이션에서 조합한다." (정의 정확. 두 번째 해결책은 batch fetch / 별도 조회 후 조합을 이름 없이 원리로 설명 — 좋음)

**꼬리질문 4-1**: N+1은 코드만 봐서는 안 보이고 개발 데이터로는 멀쩡하다. 운영에 나가기 전에 어떻게 발견하나? 실제 프로젝트에서 둔 장치는?
- 답변: "테스트용 데이터를 1,000개 이상 넣어 성능 테스트를 하고, 쿼리 로그로 확인할 수 있다." (**둘 다 사람이 눈으로 보는 방식.** "실제 프로젝트에서 둔 장치"에는 답 없음)

**꼬리질문 4-2**: 팀 10명·주당 PR 50개. 신입이 컬렉션을 루프에서 만지는 코드를 올렸고 리뷰어는 놓쳤다. 사람의 주의력에 의존하지 않고 자동으로 막는 장치를 만들 수 있나?
- 답변: "잘 모르겠다."

**면접관 보충**:
- **N의 정체** — 추가 SELECT는 "결과 행 수"만큼이 아니라 **1차 캐시에 없는 서로 다른 연관 id 수**만큼 나간다. 그래서 **건수만 늘린 테스트 데이터로는 재현되지 않는다**(회원 1~2명이면 100건 조회해도 1+1). 픽스처는 건수가 아니라 **카디널리티**로 설계해야 한다 — 후보자의 "1,000건 넣고 성능 테스트"가 실패하는 이유.
- **해결책 4종과 선택 기준** — ① **fetch join**: 조인 한 방. 컬렉션 fetch join + 페이징 불가(메모리 페이징), 컬렉션 둘 이상 fetch join 불가(카테시안 곱) ② **`@EntityGraph`**: 선언적 fetch join, 한계 동일 ③ **`hibernate.default_batch_fetch_size` / `@BatchSize`**: N개 개별 쿼리를 `IN (...)`으로 묶어 `1 + ceil(N/size)`. **페이징과 공존 가능**해서 전역 100~1000이 실무 정석 안전망 ④ **DTO 프로젝션 / 두 번 조회 후 조합**: 조회 전용 화면의 정답. → 기준: **컬렉션+페이징이면 fetch join 금지 → batch fetch size**, to-one 여럿이면 fetch join, 조회 전용이면 DTO.
- **자동 탐지 장치(이 질문의 핵심 관문)** — ① **테스트에서 쿼리 수 단정**: `Statistics.getPrepareStatementCount()`를 전후로 재서 `assertEquals`. N+1이 생기면 테스트가 깨진다 ② 사실상 표준 라이브러리 `com.vladmihalcea:db-util`의 `SQLStatementCountValidator.assertSelectCount(n)` ③ 개발/스테이징 프로파일에 **요청 단위 쿼리 카운터** + 임계치 초과 시 WARN + 스택트레이스 ④ ArchUnit으로 `FetchType.EAGER` 금지 룰 고정 ⑤ APM·슬로우 쿼리 로그는 **사후 발견**이라 예방 장치가 아님.
- **사고의 전환** — N+1은 성능 문제가 아니라 **회귀(regression)**다. 한 번 고쳐도 다음 PR에서 재발하므로 사람이 아니라 **테스트로 고정**해야 한다.

**메모**: 정의와 해결책은 기본⭐ 기준 충분하고, 특히 "추가 쿼리에서 모든 데이터를 가져와 조합"을 용어 없이 원리로 설명한 것은 실제로 써본 흔적이다. 그러나 rationale이 이 문항으로 재려던 것 — **"운영 전에 어떻게 발견하는가"** — 에서 정확히 막혔다. "성능 테스트 + 로그 확인"은 사람 의존이고, 자동 가드에는 "잘 모르겠다". Q2의 "진단 도구·경험 부재"와 **동일한 공백의 재확인**: 이 후보자는 개념과 해결책은 알지만 **품질을 시스템으로 고정해본 경험이 없다**. 3장 전체에서 가장 일관된 약점이므로 다음 세션 재도전 최우선 대상.

### [Q5] `merge`와 dirty checking의 차이 — **하**

(후보자 역질문: "정확히 어떤 merge인가?" → `EntityManager.merge()`, 즉 Spring Data `save()`에 준영속 엔티티를 넘겼을 때 호출되는 그것으로 특정해줌)

**본질문 답변 요지**: "**정확히는 모르지만** merge는 새롭게 데이터를 생성해서 스냅샷과 기존 데이터를 대조하는 과정이 없다." (개념 미정립을 스스로 인정. "새 인스턴스를 만든다"는 관찰은 정확 — merge의 반환값이 새 영속 인스턴스이고 넘긴 객체는 준영속으로 남는다는 핵심을 부분적으로 짚음. 다만 "스냅샷 대조가 없다"는 틀림 — merge도 SELECT로 영속화한 뒤 결국 dirty checking을 탄다)

**꼬리질문 5-1**: 회원 엔티티 필드 10개, 수정 화면은 이름·전화번호 2개만 전송. `new Member()`에 id+이름+전화번호만 채우고 `save()` 호출. DB에 무슨 일이 벌어지나?
- (후보자 역질문: "수정 요청인가?" → 그렇다, 해당 id의 회원이 DB에 존재하고 나머지 8필드에 정상 값이 있다고 명시)
- 답변: "**id가 있는데 같은 id로 다시 저장 요청하면 당연히 에러가 난다. id 중복 에러 발생.**" (**정반대 오답.** Spring Data `save()`가 id 유무로 `persist`/`merge`를 가른다는 것을 모름 — 매일 쓰는 API의 분기)

**꼬리질문 5-2 (교정 후)**: 에러가 나지 않는다. merge 경로이므로 SELECT 후 UPDATE가 나간다. 그 UPDATE의 SET 절에는 어떤 컬럼과 값이 들어가나?
- 답변: "전체 컬럼이 들어가고, 내가 넣은 값이 있으면 해당 값으로, 안 넣은 값은 null로 저장한다." (**정확.** 경로를 알려준 직후에는 귀결을 스스로 도출)

**꼬리질문 5-3**: 이 코드를 어떻게 고치겠나? 실무에서 merge를 써야 하는 경우가 있나?
- 답변: "member를 우선 조회하고 setter로 수정 후 dirty checking을 쓸 것이다. merge를 써야 하는 경우는 기존 값을 모두 바꿔야 할 때다." (**수정 방법은 정확.** merge의 용도는 절반 — 재부착 시나리오를 못 짚음)

**면접관 보충**:
- **merge의 동작 5단계** — ① id로 1차 캐시 조회 → 없으면 **DB SELECT** ② DB에도 없으면 새 엔티티 생성 → INSERT 경로 ③ 조회된 영속 엔티티에 **넘어온 객체의 모든 필드를 복사** ④ **그 영속 엔티티를 반환**(넘긴 객체는 끝까지 준영속) ⑤ flush 시 변경 감지가 UPDATE 생성.
- **차이의 한 문장** — 변경 감지는 "무엇이 바뀌었는지"를 스냅샷으로 **계산**한다. merge는 "무엇이 바뀌었는지 모르니 **전부 덮는다**". merge도 결국 변경 감지를 타지만 **덮어쓰기가 끝난 상태**로 타므로 null까지 변경으로 잡힌다. → 후보자의 "스냅샷 대조가 없다"를 여기서 교정.
- **두 번째 버그 유형: 반환값 무시** — `repository.save(member)` 이후 `member`를 만져도 아무 일도 없다(준영속). "수정이 반영 안 된다"는 문의는 대개 이것.
- **정답 패턴** — 조회 후 영속 상태에서 필요한 필드만 변경. 한 겹 더: `member.changeContact(name, phone)` 같은 **도메인 메서드로 감싸 변경 가능 범위를 타입으로 고정**한다(setter를 열어두면 다음 사람이 또 전체를 만진다).
- **merge가 정당한 자리는 거의 없다** — 세션·캐시에 보관했던 엔티티, 원격 호출로 통째로 받은 엔티티의 **재부착** 정도. "값을 전부 바꿔야 할 때"조차 DTO로 받아 필드별 적용이 안전한 이유: **merge는 "클라이언트가 안 보낸 필드"와 "null로 지우라고 보낸 필드"를 구분할 수 없다** — PATCH 시맨틱 구현에서 이 구분이 곧 요구사항.
- **부수 비용** — merge는 항상 SELECT가 선행된다. 대량 수정에서 조회가 배로 붙는다.

**메모**: 이 스레드가 3장에서 가장 낮다. 주목할 점은 **올바른 코드 패턴은 알지만 그 이유를 모른다**는 구조 — 관례로 정답을 써왔다는 뜻이고, 이는 rationale이 이 문항으로 정확히 재려던 것("미묘하지만 사고 유형이 명확한 지식")에 걸렸다. `save()`의 persist/merge 분기를 모르는 것은 기본⭐ 기준으로도 결함이다. 다만 경로를 한 번 알려주자 전체 컬럼 null 덮어쓰기를 즉시 도출했으므로 **이해력 문제가 아니라 학습 공백**으로 판단 — 문서 학습으로 빠르게 메워질 유형. 역질문 두 번("어떤 merge인가", "수정 요청인가")은 조건을 확정하려는 좋은 습관으로, Q2에서도 나온 일관된 강점.

### [Q6] 연관관계의 주인(owner), `mappedBy`는 왜 필요한가 — **상**

**본질문 답변 요지**: "연관관계의 아이디를 갖고 있는 클래스가 주인이다. `mappedBy`는 주인이 아닌 엔티티가 연관관계를 갖기 위함이다." (주인의 정의 정확 = FK를 가진 쪽)

**꼬리질문 6-1**: `Member.team`이 주인(`@JoinColumn(team_id)`), `Team.members`는 `@OneToMany(mappedBy="team")`. `team.getMembers().add(member)`만 하고 커밋하면 DB의 `team_id`는?
- 답변: "null로 저장된다. 주인이 아니라서 FK 갱신이 안 된다." (**즉답 정확** — rationale이 지목한 "신입 단골 이슈"를 바로 짚음)

**꼬리질문 6-2**: 왜 JPA는 굳이 주인 개념을 두고 한쪽만 FK를 관리하게 했나? 양쪽 다 관리하게 두면 안 되는 이유는?
- 답변: "양쪽 다 관리하면 어느 쪽 값을 따라야 할지 모호해져서." (**정확** — 객체 참조 2개 vs FK 1개의 비대칭에서 기준이 필요하다는 설계 의도를 짚음)

**꼬리질문 6-3**: 양방향/단방향은 어떻게 결정하나? 양방향으로 둔 연관이 있었다면 이유는?
- 답변: "보통 단방향으로 푼다. 양방향을 잘 사용하지 않는다." (선택은 옳으나 **근거 서술 없음**)

**꼬리질문 6-4**: 단방향이면 팀 상세 화면의 소속 멤버 목록은 어떻게 조회했나? 양방향으로 가야 하면 반드시 해야 하는 일은?
- 답변: "팀 id로 멤버를 조회한다. 양방향을 쓴다면 무조건 주인을 골라야 하고, 주인이 아닌 곳에서 데이터를 업데이트할 때는 주인도 같이 업데이트하도록 해야 한다." (**둘 다 정확.** 대안 조회 경로 + 연관관계 편의 메서드의 필요성을 용어 없이 원리로 서술)

**면접관 보충**:
- 주인은 항상 **다(N)쪽**이다. `@ManyToOne`이 주인, `@OneToMany`가 `mappedBy`. `mappedBy`의 의미는 **"나는 주인이 아니고 상대의 이 필드가 FK를 관리한다" = 읽기 전용 선언**.
- **연관관계 편의 메서드의 진짜 이유는 DB가 아니라 1차 캐시다** — 주인만 세팅하면 DB의 FK는 정확히 갱신된다. 그런데 같은 트랜잭션에서 `team.getMembers()`를 다시 읽으면 **이미 로딩된 컬렉션이 1차 캐시에 있어 갱신 전 상태로 보인다.** "DB는 맞는데 화면은 틀린" 현상의 출처. 즉 편의 메서드는 영속화용이 아니라 **객체 그래프 일관성용**이다. ← 후보자가 도달하지 못한 유일한 층.
- **양방향의 대가** — 편의 메서드 유지 부담, **무한 순환 참조**(JSON 직렬화·`toString`·`equals`에서 스택 오버플로), 테스트에서 양쪽 정합성 관리.
- **단방향 우선의 근거** — 조회 요구는 대부분 리포지토리 쿼리로 해결된다(후보자의 `findByTeamId`). 양방향이 정당한 자리는 **연관을 함께 저장·삭제하는 Aggregate 경계 안**, 즉 cascade가 의미를 갖는 곳뿐. 판단 축은 "조회 편의"가 아니라 **"생명주기를 공유하는가"**.
- **함정** — `@OneToMany`를 `mappedBy` 없이 `@JoinColumn`으로 단방향 매핑하면 동작하지만 **INSERT 후 FK를 채우는 UPDATE가 별도로 나간다.**

**메모**: 3장 첫 **상**. 네 개 꼬리질문 전부 힌트 없이 정확히 답했고, 특히 6-2(설계 의도)와 6-4(대안 조회 + 편의 메서드)는 매핑을 손으로 다뤄본 근거로 본다. 남은 약점은 **일관된 서술 습관** — "보통 단방향으로 푼다"에서 근거를 붙이지 않는다. Q1·Q3에서도 같은 패턴(선택은 맞고 근거는 한 줄). 지식보다 **답변 구성 훈련**의 문제이므로 knowledge 문서보다 실전 반복으로 교정할 영역.

### [Q7] `LazyInitializationException`의 원인과 해결책의 트레이드오프 — **중** (상에 가까움)

**본질문 답변 요지**: "트랜잭션이 끝난 후 지연 로딩된 데이터에 접근해서 발생한다. 해결은 ① 트랜잭션 범위를 넓히거나(커넥션을 길게 가지고 감) ② 다시 트랜잭션을 열어 재조회하거나(커넥션 재사용 비용) ③ 즉시 로딩으로 바꾼다(메모리 비용)." (**이 세션 최초로 해결책마다 비용을 자발적으로 병기** — Q1~Q6에서 반복 지적된 "트레이드오프 한쪽만 서술" 패턴이 여기서 깨졌다. 단 fetch join·`@EntityGraph` 누락)

**꼬리질문 7-1**: 즉시 로딩을 해결책으로 들었는데 앞서 EAGER의 문제를 직접 말했다. 지금 스스로 어떻게 평가하나? 그리고 빠진 실무 표준 해결책이 있다.
- 답변: "무조건 필요하다면 즉시 로딩 말고 DTO로 조회해서 가져오는 게 좋다고 생각한다. **즉시 로딩으로 바꾸면 기존 로직에도 영향을 미칠 수 있어 위험하다.**" (**우수한 자기 교정.** "예외는 한 지점에서 났는데 처방은 전역에 적용된다"는 범위 불일치 논리를 스스로 세움 — 이 문항의 핵심 판단)

**꼬리질문 7-2**: Spring Boot 프로젝트에서 이 예외를 실제로 자주 봤나? 자주 안 봤다면 왜 안 났을까?
- 답변: "자주 봤다. `@Transactional`이 붙지 않은 곳에서 연관관계 데이터를 사용하려다 발생했다. 자주 보지 않았으면 매 요청마다 트랜잭션 범위를 길게 잡은 것이다." (경험 서술은 구체적. 다만 "안 나는 이유"를 트랜잭션 범위로만 설명 — **OSIV 미언급**)

**꼬리질문 7-3**: Spring Boot에 기본 on인 설정 하나가 컨트롤러의 지연 로딩을 통과시킨다. 그 설정을 아나? 켜져 있는데도 예외를 자주 봤다면 어떤 상황이었나?
- 답변: "잘 모르겠다."

**면접관 보충**:
- **원인의 정확한 표현** — "트랜잭션이 끝나서"가 아니라 **`EntityManager`(세션)가 닫혀서**다. 이 구분이 중요한 이유가 곧 OSIV — **트랜잭션은 끝났는데 `EntityManager`는 열려 있는** 상태를 만드는 장치이기 때문.
- **OSIV(`spring.jpa.open-in-view`)는 Spring Boot 기본 `true`** — 트랜잭션은 서비스에서 끝나지만 `EntityManager`를 응답 완료까지 열어둔다. 그래서 컨트롤러의 지연 로딩이 통과한다. 대가는 **커넥션을 요청 전체 동안 붙잡는 것** → 트래픽 증가 시 커넥션 풀 고갈. 시작 시 경고 로그가 뜨는 이유. 대용량 서비스는 끄고, 끄면 이 예외가 드러나므로 fetch join·DTO로 정면 대응한다.
- **OSIV가 켜져 있어도 예외가 나는 자리** — 테스트 코드(웹 요청 스코프 없음), `@Async`·스케줄러·별도 스레드, 배치, 응답 직렬화 이후, 엔티티를 캐시에 담아 재사용할 때. 후보자가 "자주 봤다"고 한 상황이 아마 이쪽.
- **해결책 4종의 계층별 성격** — ① **fetch join / `@EntityGraph`**: 지점별 처방, 가장 표준(후보자가 끝까지 누락) ② **트랜잭션 안에서 DTO 변환**: 근본적, 엔티티가 계층을 넘지 않게 함 ③ **트랜잭션 범위 확대**: 커넥션 보유 시간 증가로 대용량에서 금지 ④ **EAGER·OSIV**: 전역 설정으로 덮는 증상 은폐.
- **관통하는 원칙** — **해결책의 범위를 문제의 범위에 맞춘다.** 한 화면에서 났으면 그 쿼리에서 fetch join, 계층 경계 문제면 DTO. 전역 스위치는 문제를 옮기는 것.

**메모**: 서술 품질이 이 세션 최고. 특히 7-1의 자기 교정은 **면접관이 반론을 제기하지 않았는데도** 스스로 앞선 답변과의 모순을 인정하고 더 나은 대안으로 갈아탄 것으로, Q1 메모의 "반론 시 논점을 한 층 올리는 힘 부족"이 실질적으로 개선된 증거다(Q6의 자기 교정에 이어 두 번째). 남은 공백은 **지식의 구멍 두 개**(fetch join을 해결책 목록에 못 넣음 — Q4에서 언급했는데도 연결 실패 / OSIV 완전 미인지)이지 사고력 문제가 아니다. OSIV는 중급⭐⭐에 단독 문항이 있으므로 그때 재검증.

### [중급 Q1] fetch join과 페이징을 함께 쓸 때의 문제와 해결책 — **중**

**본질문 답변 요지**: 즉답 못 하고 **힌트 요청** — "fetch join은 join이고 페이징은 offset/limit인데 문제가 어떻게 발생하나?" (join의 **행 증폭**과 페이징 단위의 불일치를 연결하지 못한 상태에서 출발)

**힌트 제공**: Post 1건에 Comment 10개, `join fetch p.comments`를 페이지 크기 10으로 조회 — 반환 행 수와 원하는 Post 수가 같은가? `limit 10`을 그대로 붙이면 몇 건의 Post를 받나?
- 답변: "**실제로는 1건의 POST를 받는다.**" 해결책으로 "join한 상태에서 post id만 distinct로 페이징 조회 → 그 id로 다시 조회"를 제시. (**힌트 하나로 행 증폭 메커니즘을 스스로 도출.** 제시한 해법은 실무의 2-쿼리 분리 패턴 그대로 — 방향 정확)

**꼬리질문 1-1**: 하이버네이트는 이 SQL에 `limit`을 실제로 붙이나? 안 붙인다면 무엇을 하나? 그때 찍히는 경고 로그를 본 적 있나?
- 답변: "잘 모르겠다. 로그도 모르겠다." (**핵심 공백 1** — 실패가 어떤 모습으로 드러나는지를 모름)

**꼬리질문 1-2**: 그 2-쿼리 패턴을 하이버네이트가 설정 한 줄로 대신해주는 기능이 있다. 무엇인가? 켰을 때 쿼리 모양은?
- 답변: "잘 모르겠다." (**핵심 공백 2** — `default_batch_fetch_size` 미인지)

**꼬리질문 1-3**: fetch join + 페이징이 항상 문제는 아니다. 어떤 연관관계는 `limit`이 그냥 붙는다. 어느 쪽이고 왜인가?
- 답변: "**1대1 같은 경우는 괜찮다. post당 1건이면 의도한 대로 post를 조회할 수 있기 때문**이다." (정확. 자신이 세운 행 증폭 논리를 그대로 역방향 적용 — 추론력 확인. `@ManyToOne`까지 일반화하진 못했으나 판별 축은 잡음)

**꼬리질문 1-4 (설계)**: 게시글 목록 20건/페이지, 작성자 닉네임(`@ManyToOne`)과 태그 목록(`@OneToMany`, 3~5개) 필요. 쿼리를 어떻게 구성하고 몇 번 나가나?
- 답변: "post와 member 조인해 페이징 적용 후 조회 → 조회한 post_id로 태그 목록 한 번에 조회 → 애플리케이션에서 합쳐 응답. **총 2번.**" (**실무 정답.** ToOne은 조인에 포함, 컬렉션은 분리 — 도구 이름을 몰라도 설계는 도출)

**면접관 보충**:
- **하이버네이트의 실제 동작** — `limit`을 **붙이지 않는다**. 결과 정합성을 지키려 조건에 맞는 **전체를 힙에 올린 뒤 애플리케이션에서 잘라낸다**. 경고: `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory`. **쿼리는 성공하고 결과도 맞고 로그 한 줄만 남은 채 운영에서 OOM** — 이 문항이 검사하는 "지금은 되는데 나중에 터지는" 유형의 전형.
- **위험이 숨는 이유** — 개발/스테이징의 적은 데이터에서는 증상이 0이다. 사전 신호는 `HHH000104` 하나뿐이므로 **경고 로그를 실패로 승격**시키는 습관이 방어선.
- **문제의 정확한 범위** — `fetch join` 자체가 아니라 **컬렉션(ToMany) fetch join + 페이징**. ToOne(`@ManyToOne`·`@OneToOne`)은 행이 불어나지 않아 `limit`이 안전하게 부착된다.
- **해법 3종** — ① **ToOne은 fetch join으로 함께 조회**(조인해도 행 수 불변) ② **컬렉션은 `default_batch_fetch_size`(또는 `@BatchSize`)** — LAZY로 두고 접근 시 `where post_id in (?, ?, …)`로 묶어 `1 + N` → `1 + ceil(N/size)`. 후보자의 2-쿼리 수동 패턴을 프레임워크가 대신하는 것 ③ **조회 전용 화면은 애초에 DTO 프로젝션**.

**메모**: **추론력과 도구 인지가 뚜렷이 갈린 문항.** 힌트 하나를 받은 뒤로는 메커니즘 도출(1건만 온다) → 판별 기준 수립(1:1은 안전) → 설계 도출(2쿼리)까지 전부 스스로 해냈고, 마지막 설계 답변은 정답과 동일하다. 반면 "무엇을 아는가"를 묻는 두 질문(`HHH000104`, `default_batch_fetch_size`)은 연속 미답. 기본⭐ 소구간 총평의 약점 ①(**품질을 시스템으로 고정해본 경험 없음**)이 또 재현됐다 — Q2 유령 UPDATE 진단, Q4 N+1 자동 탐지에 이어 세 번째로, **"장애를 사전에 알아채는 장치"를 묻는 질문에서 일관되게 막힌다.** 사고력이 아니라 **운영 관측 경험의 부재**가 이 사람의 실제 병목임이 이제 확정적이다.

### [중급 Q2] OSIV 트레이드오프와 대용량 트래픽에서의 설정 — **중**

**본질문 답변 요지**: 즉답 못 하고 **힌트 요청** — "OSIV가 무엇인지 힌트를 줄 수 있나?" (**기본⭐ Q7 보충에서 이미 다룬 항목인데 재인출 실패.** 이 문항이 Q7의 재검증 문항이었음)

**힌트 제공**: 이름 그대로 뷰 렌더링 시점까지 `EntityManager`를 열어둔다. `spring.jpa.open-in-view` 기본값 `true`. 트랜잭션은 서비스에서 끝나도 `EntityManager`는 응답까지 살아 있어 컨트롤러의 지연 로딩이 통과한다. → "그 상태를 유지하려면 무엇을 계속 붙잡아야 하나?"
- 답변: "**요청 끝까지 DB 커넥션을 갖고 있는 것.** 커넥션이 부족해지면 응답이 느려지고 타임아웃 나서 에러가 전파된다. 대용량 트래픽에서는 꺼야 한다. 트랜잭션 범위 내에서 영속성 컨텍스트를 사용하도록 해야 한다." (**메커니즘만 주어지면 인과를 끝까지 완성한다** — 커넥션 점유 → 풀 고갈 → 타임아웃 → 전파. Q1과 동일한 패턴)

**꼬리질문 2-1**: 질문은 트레이드오프를 물었는데 한쪽 면만 말했다. **끄면 공짜인가?** 껐을 때 개발자가 치르는 대가는? 그리고 끄는 게 일방적으로 옳다면 스프링 부트는 왜 기본값을 `true`로 두나?
- 답변: "끄면 트랜잭션 범위에서만 커넥션을 갖고 있는다. 껐을 때는 **트랜잭션 범위 밖에서 영속성 컨텍스트를 통한 JPA 이점을 얻지 못한다.** 따라서 JPA 로직 작성 시 트랜잭션 내부에 있는지 확인이 필요하다. 기본값 `true`인 이유는 대용량 트래픽을 고려한 게 아니라 **에러가 최대한 나지 않도록 방어적으로 설정**한 것으로 생각한다." (**양면 서술 성립.** 기본값 해석도 타당 — 프레임워크의 방어적 기본값이라는 프레임을 스스로 세움. 단 지적을 받은 뒤에야 나옴)

**꼬리질문 2-2 (시나리오)**: OSIV가 켜진 전제로 3년치 코드가 쌓인 운영 서비스. 커넥션 풀 고갈이 실제 발생해 끄기로 결정. `false`로 배포하면 무슨 일이 벌어지나? **그 사고를 배포 전에 막으려면 무엇을 하겠나? 3년치 코드 중 어디가 터질지 어떻게 찾겠나?**
- 답변: "트랜잭션 범위 밖에서 지연 로딩으로 통한 데이터 조회가 있는지 확인해야 한다." (**방향만 있고 방법이 없음** — 이 문항의 핵심을 비껴감)

**꼬리질문 2-3**: 컨트롤러와 DTO 변환 코드가 수백 개다. **구체적으로 어떻게** 확인하나? 전수 눈으로 읽나? 다 읽었다 쳐도 **놓친 게 없다는 걸 무엇으로 보장하나?**
- 답변: "엔티티 기준으로 **지연 로딩 데이터를 get하는 메서드 사용처만 확인**하면 된다." (탐색 범위를 좁히는 발상 자체는 합리적. 그러나 **정적 검색의 한계를 못 봄** — 보장 수단에 대한 답은 없음)

**꼬리질문 2-4 (반론)**: 컨트롤러가 `Order` 엔티티를 그대로 반환하고 `@OneToMany(LAZY) items`가 있다. **코드 어디에도 `getItems()` 호출이 없어 사용처 검색에 안 걸린다.** 그런데 끄고 배포하면 터진다. 왜인가?
- 답변: "**JSON으로 직렬화할 때 터진다.**" (**즉답, 정확.** Jackson이 리플렉션으로 게터를 호출한다는 것을 알고 있음)

**면접관 보충**:
- **켰을 때가 특히 치명적인 조건** — 컨트롤러·응답 단계에 **외부 API 호출** 같은 느린 I/O가 있으면 커넥션이 **아무 일도 하지 않으면서** 그 시간만큼 점유된다. 풀 20개에 300ms 외부 호출이면 처리량이 무너진다. "커넥션을 오래 잡는다"보다 **"놀고 있는 커넥션을 잡는다"** 가 문제의 정확한 표현.
- **껐을 때의 진짜 의미는 불편이 아니라 설계 강제** — "엔티티는 트랜잭션 밖으로 나가지 않는다"를 프레임워크가 강제한다. 그 결과 fetch join·DTO 변환을 명시적으로 쓰게 된다. 중급 Q5(엔티티 직접 노출 금지)와 같은 원칙의 다른 얼굴.
- **전환 순서** — 끄고 나서 터지는 걸 줍는 게 아니다. ① **컨트롤러가 엔티티를 반환하지 않도록 DTO 경계를 먼저 세운다** → ② 서비스 트랜잭션 안에서 변환을 끝낸다 → ③ **마지막에 끈다**.
- **보장 수단** — `open-in-view=false` 프로파일로 **전체 컨트롤러 통합 테스트**를 돌려 `LazyInitializationException`을 표면화시킨다(통합 테스트 커버리지 = 안전망). **ArchUnit**으로 "컨트롤러 반환 타입에 엔티티 금지" 룰을 걸어 재발까지 차단. 정적 검색은 직렬화·`toString`·프록시 경유를 못 잡으므로 보장 수단이 될 수 없다.

**메모**: **Q1과 완전히 같은 프로필이 반복됐다.** ① 도구·설정의 이름을 묻는 지점에서 막히고(OSIV 자체를 재차 모름 — Q7 보충에서 이미 설명한 항목이라 **인출 실패가 더 뼈아프다**) ② 메커니즘만 손에 쥐면 인과 전개는 정확하며 ③ 반론에는 즉답한다(직렬화). 그리고 ④ **"배포 전에 어떻게 보장하나"에서 또 멈췄다 — 3장에서 네 번째다**(유령 UPDATE 진단 / N+1 자동 탐지 / `HHH000104` / OSIV 전환 검증). 이 사람의 병목은 지식량도 사고력도 아니라 **"안전망을 코드로 고정한 경험"의 완전한 부재**로 확정. 다음 세션부터는 이 축을 별도 훈련 대상으로 다뤄야 한다. 한편 트레이드오프 양면 서술은 **지적을 받으면 즉시 채운다** — 자발성만 남은 문제.

### [중급 Q3] 낙관적 락(`@Version`) vs 비관적 락 — 차이와 선택 기준 — **중 (상에 근접)**

**본질문 답변 요지**: "낙관적 락은 **락이 거의 걸리지 않는 상황**에서, 비관적 락은 **락이 자주 발생하는 상황**에서 쓴다. 낙관적 락은 업데이트할 때 기존 값을 조회하고 **업데이트 직전에 다시 조회해서 값이 같은지 확인 후** 업데이트하는 방식, 비관적 락은 **조회부터 락을 잡아서** 실행한다." (**선택 기준(충돌 빈도)은 정확.** 그러나 낙관적 락의 동작 모델이 **check-then-act로 잘못 형성**돼 있음 — 실제로는 별도 SELECT 없이 UPDATE 한 문장의 조건절로 처리)

**꼬리질문 3-1 (반론)**: "확인하는 순간과 업데이트하는 순간 사이"에 다른 트랜잭션이 끼어들면? 그 확인은 무엇을 보장하나? 틈이 없으려면 실제 UPDATE 문이 어떻게 생겨야 하나?
- 답변: "그럼 데이터가 그대로 업데이트되어서 의도대로 되지 않는 것으로 안다. **틈이 없으려면 비관적 락을 사용**하는 것으로 안다." (**자신의 모델 안에서는 논리적으로 옳은 결론.** 모델이 틀려서 "낙관적 락은 근본적으로 안전하지 않다"는 오결론에 도달 — 이해의 바닥 확인)

**꼬리질문 3-2 (힌트)**: 틈이 생기는 건 확인과 갱신이 두 문장이기 때문이다. **확인을 UPDATE 문 안에 집어넣으면?** `@Version` 엔티티 수정 시 하이버네이트가 실제 날리는 UPDATE는? 충돌은 무엇을 보고 감지하나?
- 답변: "SQL 한 문장 안에서 일어나면 끼어들 틈이 없다. **version 필드를 붙여 업데이트 시 where 절에 해당 버전을 넣고, 업데이트 실패하면 다시 버전 조회 후 로직 실행 후 업데이트**하도록 한다." (**힌트 하나로 정확히 재구성.** 재시도 흐름까지 스스로 포함)

**꼬리질문 3-3 (시나리오)**: 한정판 재고 차감, **초당 500건이 전부 같은 `product` 로우 하나**를 친다. 낙관적 락 + 재시도를 걸면? 비관적 락으로 바꾸면 해결되나?
- 답변: "500건이 계속 쌓이고 **그중 1개만 통과하고 다시 499건이 로직을 실행해서 스레드 부담이 커진다.** 비관적 락을 쓰면 499건이 block되어 스레드 부담이 덜어진다. 단 **요청 시 스레드를 계속 들고 있어서 가상 스레드를 이용해야 한다.**" (**재시도 폭풍을 정확히 예측.** 블로킹과의 대비도 정확. 가상 스레드까지 끌어온 것은 2장 학습의 전이)

**꼬리질문 3-4 (반론)**: 가상 스레드로 스레드는 싸졌다. 그런데 대기 중인 499건이 붙잡은 게 스레드뿐인가? `SELECT ... FOR UPDATE` 상태로 대기 중이고 **커넥션 풀이 20개**라면? 가상 스레드가 이 문제를 해결하나?
- 답변: "**커넥션 풀이 모두 고갈되어서 해결을 못한다.** 해결하려면 JPA 비관적 락이 아닌 **Redis 분산 락**을 사용하는 것이 좋다." (**즉답, 정확.** 직전 Q2(OSIV)의 커넥션 점유 논리를 다른 맥락에 전이시킴 — 학습 전이 확인)

**꼬리질문 3-5**: Redis 분산 락도 500건이 줄 서는 건 똑같다. **기다리게 하지 않고** 푸는 방법은? 힌트 — 읽고/계산하고/쓰는 3단계가 정말 필요한가?
- 답변: "**이해가 안 간다. 어떻게 되었든 기다려야 한다. 기다리는 곳이 바뀔 뿐 값을 1개씩 차감해야 하므로 어느 한곳에서는 기다려야 한다.**" (**타당한 반론.** 같은 로우인 이상 직렬화는 불가피하다는 직관 자체는 옳다. 놓친 것은 "기다림의 유무"가 아니라 **"임계 구간의 길이"** 라는 축)

**면접관 보충**:
- **낙관적 락은 락이 아니다** — 아무것도 잠그지 않는다. `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`의 **영향 행 수 0**으로 충돌을 **사후 감지**할 뿐이다(`OptimisticLockException`). "충돌하지 않을 것"에 베팅하고 틀리면 예외를 받는 구조. 후보자의 check-then-act 모델과의 결정적 차이는 **별도 SELECT가 없다**는 점.
- **재시도는 반드시 새 트랜잭션·새 영속성 컨텍스트에서** — 같은 트랜잭션에서 재시도하면 1차 캐시에 옛 버전 엔티티가 남아 영원히 실패한다. (후보자가 "다시 버전 조회 후"라고 한 것은 방향은 맞으나 영속성 컨텍스트 초기화까지는 미언급)
- **선택 기준 = 충돌 빈도 × 재시도 비용** — 드물면 낙관적(평시 오버헤드 0), 잦으면 비관적(재시도 폭풍 회피). 단 **비관적 락은 커넥션을 락 대기 시간만큼 점유**하므로 고TPS에서는 이것도 답이 아니다.
- **3-5의 답 — 락을 애플리케이션에서 DB 한 문장 안으로 밀어 넣는다**: `UPDATE product SET stock = stock - 1 WHERE id = ? AND stock >= 1`. 기존 구조의 락 보유 구간은 `SELECT` → 값 전송 → 자바 계산 → `UPDATE` 전송(네트워크 왕복 2회, **수 ms**)인 반면, 한 문장이면 **수 μs**. 직렬화는 여전하지만 **임계 구간이 ~1000배 짧아져** 500 TPS가 소화된다. 게다가 `affected rows = 0`이면 곧 "재고 없음"이라 **재시도 자체가 불필요**(즉시 품절 응답). → 고난이도⭐⭐⭐ 전용 문항에서 4종(낙관/비관/원자적 UPDATE/분산 락) 비교로 재확인 예정.

**메모**: **3장 전체에서 가장 좋은 스레드.** 반론을 받을 때마다 한 단계씩 정확히 올라갔다 — 재시도 폭풍 → 블로킹 → 스레드 점유 → 가상 스레드 → **커넥션 풀 고갈** → 분산 락. **네 번 연속으로 "다음에 짚어야 할 것"을 스스로 짚었고**, 마지막엔 반론까지 제기했다. 기본⭐ Q1 메모의 "반론 시 논점을 한 층 올리는 힘 부족"은 이제 완전히 해소된 것으로 판단한다. 특히 3-4에서 **직전 문항(OSIV)의 커넥션 점유 논리를 자발적으로 전이**시킨 것이 인상적 — 세션 내 학습이 즉시 작동한다는 증거.
반면 감점 사유는 단 하나, **`@Version`의 실제 동작을 몰랐다는 것**(중급 필수 지식). 이 패턴 역시 3장 내내 동일하다 — **판단력 ≫ 도구·메커니즘 지식**. Q1(HHH·batch fetch), Q2(OSIV 정의), Q3(@Version 동작) 모두 "무엇을 아는가"에서만 걸렸고 "어떻게 판단하는가"에서는 걸린 적이 없다. **학습 처방은 명확: 개념 이해가 아니라 도구·설정·API의 실제 동작을 사실 단위로 채우는 것.**

### [중급 Q4] 벌크 연산(`@Modifying`) 후 영속성 컨텍스트 처리 — **중 (하에 근접)**

**본질문 답변 요지**: "벌크 연산을 실행하면 **영속성 컨텍스트는 한번에 처리하지 않을까?**" (**질문의 전제인 `@Modifying`을 모르는 상태.** 벌크 연산이 영속성 컨텍스트를 **우회**한다는 핵심을 정반대로 이해 — "한번에 처리한다"는 곧 컨텍스트를 거친다는 뜻)

**꼬리질문 4-1 (시나리오)**: 같은 트랜잭션에서 `findById`로 `stock=100`을 로드 → `@Modifying update Product p set p.stock = 0` 실행 → `p.getStock()`은 무엇이 찍히나? 그 시점 **DB 값**은?
- 답변: "**100이 찍힌다. 그리고 그 시점 DB 값도 100이다.**" (**전자는 정답, 후자는 오답.** 1차 캐시가 안 바뀐다는 건 맞혔으나 **벌크 연산이 쓰기 지연 대상이 아니라 즉시 DB로 나간다**는 것을 모름 → 실제 DB는 이미 `0`)

**면접관 정정**: 벌크 연산은 영속성 컨텍스트를 거치지 않고 DB로 직행한다. 오히려 JPQL 실행 **직전에 flush가 먼저** 일어나고 그 다음 UPDATE가 즉시 나간다. 1차 캐시의 `p`는 그 사실을 모른 채 옛 값을 유지 → **DB 0 / 메모리 100 불일치**.

**꼬리질문 4-2**: 그 불일치 상태에서 `p.setName("신상품")` 한 줄을 추가하고 커밋하면? DB의 `stock`은 최종 얼마가 되나?
- 답변: "**100이 되지 않을까?**" (**정답.** 확신은 없으나 dirty checking이 벌크 결과를 덮어쓴다는 결론에 도달)

**꼬리질문 4-3**: 이상하지 않나 — `name`만 바꿨는데 왜 `stock`까지 되돌아가나? **커밋 시점에 하이버네이트가 만드는 UPDATE 문**으로 설명하라.
- 답변: "커밋 시점에 하이버네이트가 **기존 스냅샷과 현재 상태값을 비교 후** 업데이트문을 작성하기 때문이다. **업데이트문에는 모든 필드가 들어간다.**" (**정확.** 기본⭐ Q2 보충에서 다룬 전 컬럼 UPDATE를 정확히 인출 — 이전 학습이 작동한 사례)

**꼬리질문 4-4**: 실무에서 이 사고를 어떻게 막나? `@Modifying`에 이를 위한 옵션이 있다. 무엇이고 각각 언제 동작하나? 모르면 옵션 없이 막는 방법이라도.
- 답변: "**우선 `@Modifying`이 무엇인지 왜 쓰는지도 모르겠다.** 따라서 옵션도 모르겠다. 옵션 없이 논리적으로 생각했을 때는 **`EntityManager`를 clear하고 다시 조회하면 될 것 같다.**" (**어노테이션을 모르는 채로 정답 처방을 논리만으로 도출** — `clearAutomatically = true`가 정확히 그것. Q1~Q3과 완전히 동일한 프로필)

**면접관 보충**:
- **`@Modifying`의 정체** — "이건 조회가 아니라 변경 쿼리다"라는 표시. 붙이지 않으면 Spring Data JPA가 `getResultList()`로 실행하려다 예외. 붙이면 `executeUpdate()`로 나간다.
- **옵션 두 개는 방향이 반대다** — `flushAutomatically = true`는 쿼리 **실행 전** flush(아직 DB에 안 나간 변경분을 벌크 연산에 **반영**), `clearAutomatically = true`는 쿼리 **실행 후** clear(낡은 1차 캐시를 **폐기**). 후보자가 도출한 것은 후자.
- **그러나 `clearAutomatically`는 안전장치가 아니다** — 영속성 컨텍스트를 **통째로** 비우므로 같은 트랜잭션에서 수정 중이던 **다른 엔티티의 변경분도 flush 없이 소실**된다. clear 이후 기존 참조는 전부 준영속이 되어 지연 로딩도 터진다.
- **진짜 처방은 옵션이 아니라 배치** — 벌크 연산은 **트랜잭션의 맨 끝에 두거나 별도 트랜잭션으로 분리**한다. 원칙: **"영속성 컨텍스트를 우회하는 연산과 영속성 컨텍스트에 의존하는 연산을 같은 트랜잭션에 섞지 않는다."**

**메모**: **Q1~Q3의 프로필이 네 번째로 정확히 재현됐다** — 도구 이름(`@Modifying`)과 사실(벌크의 즉시 실행·우회 성격)에서 걸리고, 시나리오를 코드로 깔아주면 그 뒤로는 한 번도 틀리지 않는다(4-2 덮어쓰기 예측 → 4-3 메커니즘 정확 → 4-4 정답 처방 도출). 특히 4-3에서 **기본⭐ Q2 보충의 "전 컬럼 UPDATE"를 정확히 인출**한 것은 학습 정착의 증거.
다만 이 문항의 rationale은 "**증상이 괴상해서 원인을 모르면 며칠을 헤맨다 — 겪었거나 원리를 아는 사람만 즉답한다**"이다. 후보자는 즉답하지 못했고, **코드를 눈앞에 깔아줘야만 보였다.** 실무에서 이 증상("DB는 바뀌었는데 조회는 옛날 값" 또는 "벌크 결과가 사라짐")을 만나면 원인을 짐작조차 못 할 상태. 평가를 상향할 수 없는 이유가 여기 있다.

### [중급 Q5] 엔티티를 API 응답으로 직접 노출하면 안 되는 이유 — **중 (상에 근접)**

**본질문 답변 요지**: "엔티티를 직렬화할 때 **lazy 로딩 시 오류가 날 가능성이 높다.** 오류는 **OSIV가 false인 상황**에서 발생한다." (**이유를 하나만, 그것도 가장 좁은 기술적 사고로 답함.** 직전 Q2 학습의 전이라는 점은 긍정적이나, 이 문항이 요구하는 결합도·보안·순환참조는 전무)

**꼬리질문 5-1 (반론)**: "우리는 OSIV를 켜두니 그 오류는 안 난다, 그럼 엔티티를 그대로 반환해도 되나?" 다른 이유는? 그리고 OSIV를 켜서 예외가 안 나는 그 상황은 정말 안전한가 — 지연 로딩이 "성공"할 때 직렬화기는 무엇을 하고 있나?
- 답변: "사용자 응답 데이터에 다른 데이터도 추가로 넣어야 하는데 **이때마다 테이블 수정과 엔티티 수정을 하면 유지보수가 어렵다.** 즉 **DTO로 분리해서 의존성을 낮춰야** 한다." (**결합도 층 도달.** 단 두 번째 물음(직렬화기의 동작)은 건너뜀)

**꼬리질문 5-2**: (코드 제시 — `Order`에 LAZY `member`, `items`, `OrderItem`에는 역방향 `order`) Jackson이 `items` 게터를 만나면? 응답 하나에 쿼리가 몇 번? `OrderItem`에서 다시 `order`를 만나면?
- 답변: "**items를 만나면 N+1 문제가 터진다. 그리고 순환참조 문제가 발생한다.**" (**둘 다 즉답, 정확**)

**꼬리질문 5-3 (반론)**: 동료 제안 — "`OrderItem.order`에 `@JsonIgnore` 붙이면 순환참조 막히고 `member`에도 붙이면 지연 로딩도 안 탄다. DTO보다 간단하지 않나?" 받아들이겠나? 반대한다면 근거는?
- 답변: "**그럼 사용자 화면에 필요한 데이터가 다른 엔티티를 필요로 하고, 이 엔티티가 Order와는 전혀 연관관계가 없는 데이터라면?**" (**유도하지 않은 논거를 스스로 제시.** 엔티티 구조와 화면 요구가 애초에 다른 축이라는 지적 — DTO의 가장 근본적 정당화. 이 스레드 최고의 답변)

**꼬리질문 5-4**: `@JsonIgnore` 자체의 구멍 — 관리자 API는 `member` 실명·연락처가 **필수**, 사용자 API는 **절대 노출 금지**. `@JsonIgnore`로 둘을 동시에 만족시킬 수 있나?
- 답변: "**만족시킬 수 없다.**" (즉답, 정확. 어노테이션이 엔티티에 박히는 전역 스위치라는 성질을 이해)

**면접관 보충** (후보자가 끝까지 언급하지 않은 두 축):
- **보안 — 실수의 방향이 반대다.** 엔티티 직접 노출은 **opt-out** 구조라, 누군가 엔티티에 `internalMemo`·`settlementRate` 필드를 추가하는 순간 **응답 코드를 아무도 건드리지 않았는데 그 필드가 API로 새어 나간다.** DTO는 **opt-in**이라 명시한 것만 나간다 — 사고가 나려면 누군가 의도적으로 코드를 써야 한다. **이것이 실무에서 가장 자주 인용되는 논거.**
- **요청 방향은 더 위험하다** — `@RequestBody Member member`로 받으면 클라이언트가 `role: "ADMIN"`, `point: 999999`를 실어 보내 덮어쓸 수 있다(mass assignment). 서버 코드 어디에도 허용한 줄이 없는데도.
- **`@JsonIgnore`·`@JsonView`의 진짜 문제** — 동작 여부가 아니라 **엔티티에 표현 계층 관심사를 새겨 넣는다**는 것. 그 순간 엔티티는 도메인 모델이 아니라 **응답 템플릿**이 된다.
- **OSIV가 켜진 상태에서 예외가 안 나는 것은 더 나쁘다** — 예외 대신 직렬화기가 연관을 타고 들어가며 쿼리를 계속 날린다. 실패가 조용해질 뿐 비용은 늘어난다. 중급 Q2와 같은 원칙의 다른 얼굴.

**메모**: **지식의 양은 충분한데 자발적 전개가 안 되는 패턴이 새로운 형태로 재현됐다.** 5-2·5-4는 즉답이었고 5-3에서는 **유도하지 않은 독창적 논거**까지 나왔다 — 즉 알고 있다. 그런데 본질문에는 **이유를 하나만, 그것도 가장 좁은 것 하나**를 대고 멈췄다. 기본⭐ 소구간 총평의 약점 ②("선택은 맞고 근거는 한 줄")가 "이유는 알고 근거는 하나만"으로 변주된 것. 이 문항은 rationale상 **"계층 경계를 지키는 규율의 리트머스"** 인데, 규율이 몸에 밴 사람은 묻지 않아도 결합도·직렬화·보안을 한 호흡에 나열한다. 거기서 갈렸다.
한편 **직전 문항(OSIV)의 학습을 곧바로 끌어온 것**은 Q3의 커넥션 전이에 이어 두 번째 — 세션 내 학습 전이는 확실히 작동한다. 다만 이번엔 **그 전이가 시야를 좁히는 방향으로 작용**했다(가장 최근에 배운 것 하나로 답을 마감). 훈련 포인트: **"이유를 대라"는 질문에는 반드시 3층으로 답하는 습관**(기술적 사고 → 설계·결합도 → 보안·운영).

### [중급 Q6] QueryDSL 동적 쿼리 구성 경험 — **중**

**본질문**: 기본⭐ Q1에서 "선택적 조건 6개 조합 검색은 메서드 이름 방식으로 못 만들어 QueryDSL로 처리했다"고 한 발언을 근거로, 그 동적 쿼리를 실제로 어떻게 구성했는지 요구.
**답변 요지**: "**enum을 통해서 타입을 만들고, enum이 요청으로부터 들어왔는지로 분기해서 조건들을 where절에 추가**했다." (방향은 맞으나 코드 수준 서술이 아님)

**꼬리질문 6-1**: 구체적으로 `BooleanBuilder builder = new BooleanBuilder(); if (cond.getName() != null) builder.and(...)` 형태였나? 그리고 QueryDSL에서 `where()`에 `null`을 넘기면 어떻게 되나?
- 답변: "**맞다 위처럼 사용했다.**" (실제 사용 방식 확인 — **경험은 진짜**. 단 두 번째 물음은 미응답)

**꼬리질문 6-2**: `query.where(user.name.eq(name), null, user.age.gt(20))` — 예외가 나나, 조건이 무시되나, 결과가 0건이 되나?
- 답변: "**null을 넘겨본 적이 없어서 잘 모르겠다.**" (**핵심 공백.** 이 성질을 모르기 때문에 `BooleanBuilder` + `if`에 머물렀음)

**꼬리질문 6-3**: `BooleanBuilder` 방식의 함정 — 사용자가 검색 조건을 하나도 입력하지 않고 조회하면 어떤 쿼리가 나가나? 겪어봤나?
- 답변: "그냥 조회 쿼리만 나가지 않을까 싶다." (맞음 — `where`가 통째로 사라짐. 다만 **위험으로 인식하는 기색이 없음**)

**꼬리질문 6-4**: 그 테이블에 500만 건이 있고 페이징이 안 걸려 있다면? 어떻게 막겠나?
- 답변: "**OOM이 발생한다. 페이징 처리를 넣거나 최소 조건을 강제**하도록 해야 한다." (정확)

**후보자의 반론**: "이해가 안 간다. **페이징 쿼리와 BooleanBuilder를 분리해서 사용하면 무조건 페이징 처리가 되는 것으로 알고 있다.**"
- **면접관 인정**: 타당한 반론. 리포지토리 메서드가 항상 `Pageable`을 받아 `offset`/`limit`을 적용하는 구조라면 조건이 없어도 한 페이지 분량만 나가므로 OOM은 구조적으로 발생하지 않는다. 면접관이 깐 전제가 후보자의 실제 구조에 해당하지 않음을 인정하고 한 단계 더 진행.

**꼬리질문 6-5**: 페이징을 강제해 20건만 가져온다. 그런데 `Page<User>`를 반환해 "총 500만 건 중 1페이지"를 표시해야 한다면 — 쿼리가 몇 번 나가나? 조건이 하나도 없을 때 그 추가 쿼리는 무엇을 하나?
- 답변: "**2번 나간다. 모든 데이터를 조회한다.**" (**정확.** content 쿼리 + count 쿼리, 조건 없는 count는 500만 건 풀스캔)

**면접관 보충**:
- **`where(null)`은 조용히 무시된다** — 이것이 QueryDSL 동적 쿼리의 핵심 장치. 그래서 조건마다 `BooleanExpression`을 반환하는 메서드로 쪼개고 `where(nameEq(x), statusEq(y), ...)`로 나열하면 **`if`가 전부 사라진다**.
- **진짜 이점은 `if` 제거가 아니라 조합 가능성** — `nameEq(x).and(statusIn(y))`처럼 조건을 **합성·재사용**할 수 있다. `BooleanBuilder`에는 없는 성질.
- **선택 기준** — 단순 AND 나열이면 메서드 분리, `OR` 중첩처럼 구조가 복잡하면 `BooleanBuilder`. 대체재가 아니라 용도가 다르다.
- **count 쿼리는 최적화 대상** — `PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne)`는 **첫 페이지에 다 담히거나 마지막 페이지일 때 count 쿼리를 생략**한다. count 쿼리에서는 fetch join·불필요한 join을 제거해야 한다(세는 데 필요 없음).
- **더 근본적으로는** 조건 없는 전체 검색을 **애초에 허용하지 않는 설계**(필수 조건 하나 강제, 기본 기간 조건 자동 주입)가 대용량 검색 화면의 표준.

**메모**: **오늘 처음으로 "안전망" 축에서 긍정 신호가 나왔다.** 6-4 이후의 반론("페이징을 분리해서 쓰면 무조건 적용된다")은 문제를 **개별 케이스가 아니라 구조로 막아본 사람의 답변**이다. 3장 내내 지적된 횡단 약점(장애를 사전에 보장하는 장치의 부재)에 대한 첫 반증 사례이므로 기록해 둔다 — 다만 그 구조를 **후보자가 설계했는지 팀 컨벤션을 따른 것인지는 확인하지 못했다.** 다음 세션에서 확인 가치 있음.
공백은 여전히 같은 자리다 — **도구의 관용구를 모른다**(`where(null)` 무시). 이 하나 때문에 QueryDSL의 절반만 쓰고 있었다. Q1(batch fetch size), Q2(OSIV), Q3(`@Version` 동작), Q4(`@Modifying`)에 이어 **다섯 번째로 "무엇을 아는가"에서만 걸렸다.** 반면 판단(6-4 OOM·페이징 강제, 6-5 count 정체)은 전부 정확. 3장 전체를 관통하는 결론이 이제 흔들림 없다: **사고력 상급 / 도구 지식 하급.**

### [중급 Q7] 복합 유니크 제약 + 동시 INSERT — **중**

**본질문**: `(user_id, coupon_id)` 복합 유니크 제약이 걸린 쿠폰 발급 테이블에 같은 사용자의 발급 요청이 동시에 들어올 때, JPA 레벨에서 어떤 문제가 생기고 어떻게 대응하겠는가?
**답변 요지**: "정확히 모르겠지만 추론하자면 — **영속성 컨텍스트에서도 유니크 제약을 검사해야 하므로 유니크에 포함된 컬럼 데이터를 가져와서 비교하지 않을까** 싶다. 그리고 생성 시 락을 잡고 insert해서 **DB 커넥션 부족**까지 진행될 것 같다. 응답 시간이 길어지고 애플리케이션 전반에 에러가 전파된다." (**전제 자체가 틀림** — JPA는 유니크 검사도, 락 획득도 하지 않는다. 다만 "커넥션 고갈 → 장애 전파"라는 파급 서술은 습관적으로 나옴)

**꼬리질문 7-1**: JPA/Hibernate가 `persist` 시 실제로 SELECT를 날려 유니크 중복을 확인하나? (힌트: 1차 캐시는 무엇을 키로 관리하나?)
- 답변: "**id를 key로 관리한다. 그럼 영속성 컨텍스트에서는 관리 안 하고 바로 쿼리를 보내나?**" (**힌트 한 줄로 즉시 자기 전제를 뒤집음** — 인출 실패였을 뿐 지식은 있었다)

**꼬리질문 7-2**: `if (existsByUserIdAndCouponId(...)) throw ...; save(...)` 코드에 동시 요청 둘이 들어오면 언제 깨지나? 시간 순서로.
- 답변: "**두 스레드 모두 if문이 false이고 save 로직을 타고 나서 둘 중 하나는 unique 에러가 던져진다.**" (**정확.** check-then-act 붕괴를 즉답)

**꼬리질문 7-3**: (a) 분산 락/비관적 락으로 동시 진입 차단 vs (b) 유니크 제약 예외를 잡아 처리 — 어느 쪽을 기본으로? 근거는?
- 답변: "**우선 비즈니스 조건을 살펴봐야 한다. 쿠폰 중복 발급이 자주 발생하는 일인지 확인**해야 한다. 자주 발생하지 않으면 (b), 자주 발생하면 (a)를 선택해서 굳이 DB 커넥션을 사용하지 않도록." (**충돌 빈도라는 정확한 판단 축.** 락은 항상 비용을 내고 예외 처리는 충돌할 때만 낸다는 구조를 스스로 잡음)

**꼬리질문 7-4**: `@Transactional` 안에서 `DataIntegrityViolationException`을 catch하고 `IssueLog`를 저장한 뒤 정상 종료시켰는데, 메서드가 끝날 때 예외가 터진다. 왜?
- 답변: "커넥션을 물고 있는 상태에서 DB가 에러를 냈는데 catch한 곳에서 다시 save를 하려 해서 **이 save는 적용이 안 될 것**으로 예상한다. **정상 처리하려면 새로운 트랜잭션을 통해 저장**하도록 해야 하지 않나 싶다." (**메커니즘 이름은 모르나 결론과 처방에 스스로 도달**)

**꼬리질문 7-5**: 락으로 동시 진입을 확실히 막았다면 DB 복합 유니크 제약은 빼도 되나?
- 답변: "**빼면 안 된다. DB는 레디스 락이 아니더라도 최후의 보루 역할을 진행할 수 있기 때문**이다." (정확)

**면접관 보충**:
- **JPA는 방어선이 아니다** — 1차 캐시는 `@Id` 키 Map이라 유니크 컬럼 조합은 애초에 관여 대상이 아니다. `persist`는 쓰기 지연 저장소에 INSERT를 쌓을 뿐이고, 검증은 전적으로 DB 몫. flush 시점에 DB가 `ConstraintViolationException` → Spring이 `DataIntegrityViolationException`으로 변환.
- **애플리케이션 사전 검사는 UX용이지 정합성 보장 수단이 아니다** — `exists` → `save` 사이의 틈에서 반드시 깨진다. 친절한 에러 메시지를 위해 남기되, 정합성은 DB 제약이 책임진다.
- **예외를 잡아도 트랜잭션은 못 살린다 — `rollback-only` 마킹** — 제약 위반 시 Hibernate 세션이 오염 상태로 간주되고 Spring 트랜잭션에 rollback-only 플래그가 찍힌다. catch해도 커밋 시점에 **`UnexpectedRollbackException`**이 터지고 안에서 한 후속 저장까지 함께 롤백된다. 처방: `REQUIRES_NEW`로 분리하거나, 예외를 트랜잭션 밖(파사드 계층)에서 잡는다.
- **락을 써도 유니크 제약은 남긴다** — Redis 락은 **TTL 만료, 네트워크 분단, 노드 장애, 배포 중 락 키 변경**에서 뚫리고, 무엇보다 **배치·수동 SQL 같은 락을 안 거치는 경로**를 전혀 커버하지 못한다. DB 제약만이 모든 진입 경로를 덮는다.
- **원자적 upsert라는 제3의 선택지** — `INSERT ... ON DUPLICATE KEY IGNORE`(MySQL) / `ON CONFLICT DO NOTHING`(PostgreSQL)을 네이티브 쿼리로 쓰면 예외 자체가 발생하지 않는다. 단 영속성 컨텍스트를 우회하므로 이후 조회 시 주의(벌크 연산과 같은 성질).

**메모**: **3장에서 처음으로 "모르는 영역을 추론으로 건너간" 문항.** 시작 전제가 통째로 틀렸는데(JPA가 유니크를 검사한다, 락을 잡는다) **힌트 한 줄에 스스로 뒤집고** 7-2부터 7-5까지 전부 정확하게 답했다. 인출 실패였을 뿐 재료는 있었다는 뜻 — Q6까지 반복된 "도구 지식 하급"과는 결이 다르다.
특히 **7-3의 판단 축(충돌 빈도)과 7-4의 처방(새 트랜잭션 분리)은 유도 없이 나왔다.** 7-5의 "최후의 보루"까지 포함하면 **이 문항의 rationale 의도(DB 제약을 최후 방어선으로 쓰는 설계 습관)는 충족**했다. 그럼에도 **중**인 이유는 두 가지: ① 본질문 첫 답이 사실 오류였고 ② **회원가입·쿠폰·좋아요에서 반드시 마주쳤을 상황인데 실제 겪은 사례가 끝까지 나오지 않았다.** 6-4의 페이징 반론처럼 경험 근거가 붙었다면 상이었다.
직전 Q6 메모의 "사고력 상급 / 도구 지식 하급"이 여기서 더 선명해졌다 — **추론으로 메울 수 있는 공백(이번)과 메울 수 없는 공백(`where(null)`, `@Modifying`)이 갈린다.** 후자만 암기로 채우면 된다는 것이 3장의 학습 처방이다.

### [중급 Q8] flush 시점과 쓰기 지연 SQL 실행 순서 — **중**

**본질문**: 영속성 컨텍스트의 flush는 언제 일어나나? 쓰기 지연 SQL의 실행 순서가 코드 순서와 달라서 생기는 문제(유니크 제약, 데드락)를 겪어봤나?
**답변 요지**: "**영속성 컨텍스트 flush는 트랜잭션이 끝나기 전에 실행된다.** 코드에 쓴 순서대로 나가지 않아서 생기는 문제는 **겪어보지 못했다.**" (시점 1개만 — auto-flush와 명시 호출 누락. 순서 문제는 경험 없음)

**꼬리질문 8-1**: `save(new Member("kim"))` 직후 같은 트랜잭션에서 `findByName("kim")`을 호출하면 `size()`가 0인가 1인가? 이유는?
- 답변: "**1이다. 데이터를 조회할 때 flush를 하고 다시 DB 조회를 한다.**" (**정확.** JPQL auto-flush를 유도 없이 설명)

**꼬리질문 8-2**: 그럼 같은 트랜잭션에서 `findById(1L)`은? 이때도 flush가 일어나나?
- 답변: "**1차 캐시에 있으면 flush 안 하고 바로 반환할 것 같다. 없으면 flush하고 조회할 것 같다.**" (**앞은 맞고 뒤는 틀림** — 1차 캐시에 없어도 `em.find()`는 auto-flush 검사 경로를 타지 않는다)

**꼬리질문 8-3**: `email`에 유니크 제약이 있는 테이블에서 `delete(기존행)` 후 `save(같은 email 새 행)` — 코드는 지우고 넣는데 유니크 위반이 난다. 왜?
- 답변: "**추론하자면 delete 쿼리가 save 쿼리보다 늦게 나가서이다.**" (**경험이 없는데 추론으로 정확히 도달**)

**꼬리질문 8-4**: 어떻게 고치겠나? 그리고 이 유형은 테스트에서 잘 안 잡히고 운영에서 터지는데, 배포 전에 발견할 방법이 있나?
- 답변: "**delete 하고 의도적으로 flush 로직 추가하면 된다.** 미리 발견하는 방법은 **사람들이 직접 보는 것 외에 시스템적으로 막는 것은 잘 모르겠다.**" (처방은 정확 / **안전망은 또 공백**)

**면접관 보충**:
- **flush 3시점** — ① 트랜잭션 커밋 직전 ② **JPQL·Criteria·네이티브 쿼리 실행 직전(auto-flush)** — 미반영 변경분 때문에 쿼리 결과가 틀리는 것을 막으려고 ③ `em.flush()` 명시. `FlushModeType.COMMIT`으로 ②를 끌 수 있으나 "저장했는데 조회에 안 나오는" 버그를 자초하는 셈이라 거의 안 쓴다.
- **`findById`가 다른 이유** — auto-flush는 "이 쿼리가 건드리는 **query space**에 미반영 변경이 있나"를 판정해 결정하는데, `em.find()`는 PK 조회라 그 판정 경로 자체를 타지 않는다. 그래서 `findByName`은 flush를 부르고 `findById`는 안 부르는 **비대칭**이 생긴다.
- **실행 순서는 Hibernate가 고정해 둔 규칙** — `ActionQueue`의 타입별 고정 순서: `orphanRemoval → INSERT → UPDATE → 컬렉션 삭제 → 컬렉션 갱신 → 컬렉션 생성 → DELETE`. **DELETE가 항상 맨 마지막.** 이유는 ① FK 제약 위반을 줄이려는 의도 ② **같은 종류를 몰아야 JDBC batch가 먹히기** 때문. 그래서 "지우고 넣기"가 실제로는 "넣고 지우기"가 된다.
- **처방 3종(좋은 순서대로)** — ① **애초에 DELETE+INSERT를 안 한다**. 이 예시는 `member.changeEmail(email)` UPDATE 한 줄이면 끝난다. `flush()` 끼워 넣기는 증상 대응 ② 구조상 불가피하면 `em.flush()`로 경계 명시(후보자 답) ③ soft delete 환경이면 유니크 제약에 삭제 플래그/시각을 포함해 제약 자체를 분리.
- **데드락은 같은 원리의 더 나쁜 얼굴** — 여러 건을 한 트랜잭션에서 UPDATE할 때 처리 순서가 컬렉션 순회 순서에 따라 트랜잭션마다 달라지면 서로 반대 순서로 락을 잡아 데드락. 처방은 **엔티티를 항상 같은 기준(보통 PK)으로 정렬한 뒤 처리**. flush 순서와 달리 **Hibernate가 지켜주지 않으므로 코드로 고정**해야 한다.
- **배포 전에 잡는 방법(8-4의 공백)** — ① **실제 SQL 순서를 눈으로 확인**: `p6spy`/`datasource-proxy`로 바인딩값까지 찍고 쓰기 로직 테스트에서 로그 확인 ② **`@DataJpaTest`로는 못 잡는다** — 테스트가 롤백되면 커밋 시점 flush에서 나는 문제를 통과시킨다. `@Commit` 또는 `TestTransaction`으로 실제 커밋을 일으켜야 한다 ③ **H2가 아니라 Testcontainers로 실제 DB** — 유니크 제약·데드락 동작은 벤더마다 다르다. "H2에서 통과하고 MySQL에서 터지는" 대표 유형.

**메모**: **Q7과 똑같은 모양의 반복.** 경험이 없다고 선언한 순간(8-3)에도 **추론만으로 정확한 원인(DELETE가 뒤로 밀림)에 도달**했고 처방까지 맞췄다. 사고력은 이제 의심의 여지가 없다.
공백의 성격이 두 갈래로 확실히 분리된다: ① **사실 지식** — flush 시점을 하나만 알고 있었고, `findById`/`findByName` 비대칭을 몰랐으며, 순서가 **Hibernate가 정한 `ActionQueue` 고정 규칙**이라는 것을 몰랐다(그래서 "왜 하필 DELETE가 뒤인가"를 설명하지 못했다). ② **안전망** — 8-4에서 **"사람이 직접 보는 것 외에는 모르겠다"**. 3장에서 **여섯 번째 동일 지점**(유령 UPDATE 진단 / N+1 자동 탐지 / `HHH000104` / OSIV 전환 검증 / 동시성 테스트 / 이번).
Q6의 페이징 반론이 유일한 긍정 신호였는데, 그것도 **이미 갖춰진 구조를 서술한 것**이지 **본인이 안전망을 설계한 사례는 3장 내내 한 번도 나오지 않았다.** 이제 이 축은 개별 문항의 약점이 아니라 **후보자의 작업 방식 자체의 공백**으로 봐야 한다 — "문제를 만나면 잘 푼다. 그러나 문제가 오기 전에 잡는 장치를 만드는 습관은 없다." 4장으로 넘어가기 전 이 도구 상자(쿼리 수 단정, p6spy, `@Commit`, Testcontainers, ArchUnit)를 한 번에 익히는 것을 강력히 권고.

### [중급 Q9] `findById` vs `getReferenceById` — **상**

**본질문**: 두 메서드의 차이는? 프록시 반환이 유용한 경우는 언제인가?
**답변 요지**: "**`findById`는 객체를 DB로부터 영속성 컨텍스트로 가져온다. `getReferenceById`는 id만 들고 있는 객체를 영속성 컨텍스트로 가져온다.** 프록시로 반환받는 게 유용한 경우는 **필드 데이터가 필요 없고 연관관계에서 id값만 필요한 경우**이다." (**군더더기 없이 정확.** 유용한 경우까지 즉답)

**꼬리질문 9-1**: `createOrder`에서 `findById` → `getReferenceById`로 바꾸면 SQL이 어떻게 달라지나? 실무에서 이 치환을 해본 적 있나?
- 답변: "**`getReferenceById`는 SELECT 없이 INSERT만 나간다.** 이런 치환을 한 적이 없다. 우선 `findById`를 사용한 건 **실제로 있는 데이터인지 검사를 하는 내용도 갖고 있기 때문**이다." (SQL 차이 정확 / **경험은 없으나 자기 선택의 근거를 스스로 제시** — 단순 선호가 아니라 트레이드오프 인지)

**꼬리질문 9-2**: `getReferenceById(999L)`인데 999번이 DB에 없으면? 예외가 난다면 언제·어디서?
- 답변: "**결과를 이용해서 다시 데이터를 저장하거나 조회할 때 에러가 난다.**" (정확 — 프록시 초기화 시점의 지연 실패)

**꼬리질문 9-3**: 그 예시는 FK만 쓰므로 프록시 초기화가 없고, FK 제약이 있으면 INSERT 시점에 DB가 막아준다. Q7에서 "DB를 최후 방어선으로"라고 했으니 같은 논리로 `getReferenceById`가 낫지 않나?
- 답변: "**원인 지점과 발현 지점이 달라진다는 것은 에러를 분석하는 데 힘들다는 의미로, 굳이 `getReferenceById`를 사용할 이유가 없다.**" (**프록시의 대가를 한 문장으로 정확히 요약.** 면접관의 유도성 반론에 흔들리지 않고 자기 기준 유지)

**꼬리질문 9-4**: 조건 변형 — CSV 10만 건 배치 적재. `findById`면 회원 조회 SELECT가 10만 번. 그래도 쓸 이유가 없나? 쓴다면 "에러 분석 어려움"은 어떻게 다루겠나?
- 답변: "**배치라면 `getReferenceById`를 쓰고 없는 id는 미리 한 번에 검증하겠다.**" (**이번 문항의 백미.** 유도 없이 교과서적 정답 — `IN` 절 일괄 존재 검증 후 프록시로 SELECT 제거. 원칙 고수 → 전제 변화 감지 → 재판단의 흐름이 깨끗함)

**면접관 보충**:
- **`deleteById`도 같은 낭비를 한다** — 내부적으로 `findById`로 SELECT 후 DELETE. `delete(getReferenceById(id))`로 SELECT 생략 가능(없는 id면 `EmptyResultDataAccessException`).
- **트랜잭션 밖 프록시 초기화는 `EntityNotFoundException`이 아니라 `LazyInitializationException`** — OSIV를 끈 환경(중급 Q2)에서 `getReferenceById` 결과를 컨트롤러로 넘기면 이게 터진다. 같은 실수인데 예외 이름이 달라 혼동되는 지점.
- **프록시는 `instanceof`·`getClass()`를 배신한다** — `Member$HibernateProxy`라 `getClass() == Member.class`가 false. 엔티티 `equals`에서 `getClass()` 비교를 쓰면 프록시와 실제 엔티티가 다르게 판정된다(+α의 `equals`/`hashCode` 문항으로 연결).
- **배치의 진짜 병목은 그다음** — SELECT 10만 번을 없애도 INSERT 10만 번이 남는다. `IDENTITY` 전략이면 JDBC batch가 무력화되므로 `SEQUENCE`나 JdbcTemplate 벌크로 내려가야 한다(고난이도 Q2 예고).
- **선택의 축은 "존재 검증을 어디서 하느냐"** — 단건 API는 `findById`로 즉시·명확하게, 대량 처리는 `IN` 절 일괄 검증 후 `getReferenceById`로 SELECT 제거.

**메모**: **3장에서 두 번째 "상".** 그리고 **성격이 지금까지와 완전히 다르다** — Q7·Q8은 "추론으로 정답에 도달했으나 사실 지식이 비어" 중이었는데, 이번엔 **사실 오류가 단 하나도 없었고 힌트도 필요 없었다.**
결정적인 것은 9-3 → 9-4의 흐름이다. 9-3에서 면접관이 **Q7의 "DB를 최후 방어선으로"를 무기로 유도성 반론**을 폈는데 **끌려가지 않고 "발현 지점이 멀어지면 분석이 어렵다"는 자기 기준으로 방어**했고, 9-4에서 전제(단건 → 10만 건)가 바뀌자 **즉시 판단을 갈아타면서도 원래 우려(존재 검증)를 버리지 않고 `IN` 절 일괄 검증으로 옮겨 담았다.** 이건 암기로 나오지 않는다.
**흥미로운 대비**: 이 문항도 경험은 없다("치환을 한 적이 없다"). 그런데 Q7·Q8과 달리 감점 요인이 되지 않았다 — 차이는 **자기 선택에 근거가 있었느냐**다. Q7·Q8은 "안 겪어봤다"로 끝났고, 여기서는 "안 써봤다, 왜냐하면 findById가 존재 검증까지 해주기 때문"이었다. **후보자에게 줄 교훈: 경험이 없을 때 "안 해봤습니다"에서 멈추지 말고 "안 한 이유"를 대라.** 3장 전체 총평에 반영할 것.

### [중급 Q10] 상속 관계 매핑 전략(SINGLE_TABLE / JOINED / TABLE_PER_CLASS)의 트레이드오프와 선택 기준 — **중**

**본질문**: 세 전략의 트레이드오프와, 실제로 하나를 골라야 할 때의 선택 기준은?
**답변 요지**: "**상속 관계 매핑 전략 3가지를 사용해본 적이 없다.**" (경험 없음을 즉시 선언 → 면접관이 시나리오로 전환)

**꼬리질문 10-1**: 시나리오 — `Payment` 부모 + `CardPayment`(카드번호·할부개월) / `BankTransferPayment`(계좌·은행코드) / `PointPayment` 세 자식, 결제수단은 계속 늘어날 예정. 조회는 "단건 상세"와 "기간별 목록(페이징)"이 대부분. **단일 테이블에 다 몰기 vs 부모+자식 테이블 조인** 중 어느 쪽? 택하지 않은 쪽에서 무엇을 포기하나?
- **후보자의 되질문**: "**단건·목록 조회 시 노출되어야 하는 데이터는 Payment 데이터뿐인가?**" (**이번 문항의 최고 신호.** 상속 매핑 선택은 조회 패턴이 결정하므로, 답하기 전에 이걸 물은 것 자체가 정답 방향)
- 면접관 조건 보강: 목록=공통 필드만(호출량 지배적, 페이징 20건) / 단건 상세=자식 고유 필드까지 전부
- 답변: "**자식 테이블로 쪼개고 조인(JOINED)을 쓰겠다.** 하나의 테이블이면 nullable하면서 각 row에 필요 없는 컬럼을 갖고 있어 **데이터가 집약적이지 않다**. 목록은 **부모 테이블만**, 단건은 **하나의 row에 join**하면 된다. 그리고 **추후 결제가 더 늘어나면 계속 컬럼을 추가할 수도 없다.**" (세 축 중 **무결성·확장성**을 스스로 짚음 / **택한 쪽의 비용은 미언급**)

**꼬리질문 10-2** (조건 변형): 운영 6개월 뒤 "목록에도 카드면 할부개월, 계좌이체면 은행명을 보여달라"는 요구가 온다. 하루 수십만 건 호출되는 페이징 화면. JOINED에서 **어떤 SQL이 나가고** 무슨 문제가 생기나?
- 답변: "**목록 20건 조회할 때 자식 테이블 3개를 join해야 한다. 그리고 결제 방식이 늘어날수록 join도 늘어난다.**" (정확 / `LEFT OUTER JOIN`이라는 형태와 "조인 폭이 커지면 문제의 성질이 옵티마이저 오판으로 바뀐다"는 지점까지는 못 감)

**꼬리질문 10-3** (반론): 그렇다면 조회 트래픽이 지배적이니 애초에 SINGLE_TABLE이 맞았다고 반박할 수 있다. 대신 `card_number`·`bank_code`에 **NOT NULL을 걸 수 없는 무결성 구멍**은 어떻게 방어하나?
- 답변: "**애플리케이션 레벨에서 검증하고 DB에는 CHECK 제약을 걸겠다.**" (**모범 답안.** Q7·Q8에서 보인 "DB를 최후 방어선으로" 기준이 여기서도 일관되게 작동)

**꼬리질문 10-4**: 세 번째 전략 `TABLE_PER_CLASS`는 왜 실무에서 거의 권장되지 않나?
- 답변: "**공통 컬럼 조회 시 자식 테이블들을 UNION ALL 해야 한다.**" (핵심 정확)

**면접관 보충**:
- **선택 기준은 두 축으로 압축된다** — ① **자식 고유 컬럼의 양** ② **다형성 조회(부모 타입 조회)의 빈도**. 자식 컬럼이 적고 부모 타입 조회가 지배적 → `SINGLE_TABLE`(조인 0, 대가는 nullable + 테이블 비대). 자식 컬럼이 많고 무결성이 중요하며 목록에서 자식 필드가 불필요 → `JOINED`.
- **JOINED가 지불하는 대가(10-1의 공백)** — 상세 조회마다 조인 1회, **부모 타입 조회 시 자식 전체에 `LEFT OUTER JOIN`**, INSERT가 테이블 2개로 나뉨(쓰기 비용·트랜잭션 길이 증가). 결제수단이 15종이 되면 outer join 15개짜리 쿼리가 되고, 이때부터는 **조인 비용이 아니라 옵티마이저가 실행계획을 잘못 잡는 문제**로 성질이 바뀐다.
- **`TABLE_PER_CLASS`의 두 번째 결격 사유** — `UNION ALL` 외에 **`IDENTITY` 전략을 쓸 수 없다**(자식 테이블마다 독립 auto_increment면 ID가 충돌 → `SEQUENCE`/`TABLE` 필요). 부모 타입 조회를 아예 안 하는 경우에만 후보.
- **`@DiscriminatorColumn`** — `SINGLE_TABLE`은 필수(없으면 기본 `DTYPE`), `JOINED`는 선택. 값을 클래스명 대신 `@DiscriminatorValue("CARD")`처럼 명시해야 클래스 리네임이 데이터와 어긋나지 않는다.
- **이 결정은 되돌리기가 가장 비싼 축에 속한다** — 전략 변경 = 데이터 마이그레이션. 그래서 "지금 자식이 3개"가 아니라 **"3년 뒤 자식이 몇 개이고, 목록 화면이 자식 필드를 요구할 것인가"** 를 기준으로 정한다.
- **상속을 테이블로 내리지 않는 선택지** — `@MappedSuperclass`(공통 컬럼만 상속, 다형성 조회 포기), 또는 **컴포지션 + JSON 컬럼**으로 자식 고유 속성을 담기(스키마 변경 없이 결제수단 추가, 대가는 해당 속성으로 검색·제약 불가).

**메모**: 평가는 **중**이지만 **성격이 Q5·Q7과 다르다** — 여기서는 **사실 오류가 없었고**, 경험이 전무한 영역에서 시나리오만으로 실무 정답(JOINED)에 도달했다. 특히 **10-1에서 답하기 전에 "목록·단건에 어떤 데이터가 노출되는가"를 되물은 것**이 압권 — 상속 매핑의 선택 변수를 정확히 알고 요구사항을 확정하러 간 행동이다. 10-3의 "애플리케이션 검증 + CHECK 제약"도 3장 내내 일관된 자기 기준(DB를 최후 방어선)의 재적용이었다.
감점 사유는 단 하나, **"택한 쪽이 지불하는 비용"을 유도 없이 꺼내지 못한 것**이다. 10-1에서 SINGLE_TABLE의 단점만 나열하고 JOINED의 조인 비용은 면접관이 10-2로 밀어야 나왔다. **이는 Q7("이유를 3층으로 대라")과 정확히 같은 서술 습관 문제** — 트레이드오프 질문에 **한쪽 면만 말하고 멈추는** 패턴이 3장에서 반복된다. 결론은 지식 공백이 아니라 **답변 구조의 문제**이므로, "선택 = 얻는 것 + 포기하는 것"을 한 호흡에 말하는 훈련만으로 교정 가능하다.
**긍정 신호 누적**: Q9(경험 없음 + 근거 제시 → 상), Q10(경험 없음 + 요구사항 확정 후 판단 → 중상). Q9 메모의 교훈("안 한 이유를 대라")이 이번엔 "**모르면 조건을 물어라**"로 확장됐다 — 두 문항 연속으로 경험 공백을 사고력으로 메우는 방식이 안정화되고 있다.

### [중급 Q11] 조회 전용 화면에 엔티티 대신 DTO 프로젝션을 쓰는 이유와 방법 — **중**

**본질문**: 조회 전용 화면(상품 목록, 주문 내역)에서 엔티티 대신 DTO로 직접 프로젝션하는 이유는? 어떤 방법으로 구현하나?
**답변 요지**: "**화면에 보여지는 데이터로 엔티티를 보여주면 화면이 달라졌을 때 엔티티를 수정해야 하는 문제가 발생한다. 화면 때문에 DB를 수정할 수는 없다.**" (**질문의 초점을 벗어남** — 이것은 중급 Q5(엔티티 직접 노출)의 답변 축. 이 문항은 **조회 비용**을 묻는 것)

**꼬리질문 11-2** (반론): `@Transactional(readOnly = true)`를 걸면 Hibernate가 스냅샷을 만들지 않고 변경 감지도 건너뛴다. 그러면 **A + readOnly로 충분한가?** 그래도 B가 나은 부분은?
- 답변: "**영속성 컨텍스트에 올려놓는 것도 비용이다.**" (정확 — 1차 캐시 적재라는 남은 항목을 집어냄. 유도성 반론에 끌려가지 않음)

**꼬리질문 11-3**: 메모리가 아니라 **실제 나가는 SQL**을 A/B로 비교하면? (상품 테이블에 `description` TEXT, `detail_html`이 있고 목록에는 상품명·가격·썸네일만 필요)
- 답변: "**엔티티는 불필요한 컬럼도 조회하지만 DTO는 필요한 컬럼만 조회할 수 있다.**" (정확 — 두 축 중 나머지 하나. 단, 힌트를 준 뒤에 나옴)

**꼬리질문 11-4** (방법): QueryDSL로 그 목록 조회를 DTO로 가져오는 코드를 어떻게 쓰나? **DTO 매핑 지점**을 구체적으로.
- 답변: "**`Projections.constructor`로 DTO 생성자에 매핑한다.**" (정확하되 최소 답변 — 다른 방식·선택 기준은 미언급)

**꼬리질문 11-5**: `Projections.constructor(...)`인데 누가 DTO 생성자의 `String name, String thumbnailUrl` **순서를 바꿨다**. 컴파일은 통과하나? 위험을 줄이는 방법은?
- 답변: "**컴파일은 통과한다. `@QueryProjection`을 쓰면 컴파일 시점에 잡힌다.**" (전반부 정확 / **후반부는 과대평가** — `@QueryProjection`도 **같은 타입의 순서 교체는 못 잡는다**. 생성자 시그니처 `(String, String)`은 그대로이므로. 잡아주는 것은 **파라미터 개수 오류와 타입 불일치**)

**면접관 보충**:
- **순서 교체를 원천 차단하는 것은 이름 기반 매핑** — `Projections.fields` / `Projections.bean`은 프로퍼티 **이름**으로 꽂으므로 순서가 변수 자체가 아니다. Spring Data **인터페이스 프로젝션**(`interface ProductListView { String getName(); }`)도 이름 기반 + 필요 컬럼만 SELECT + 코드가 가장 짧다. 선택 기준: 단순 조회는 인터페이스 프로젝션, 복잡한 동적 조건·집계는 QueryDSL `@QueryProjection`.
- **`readOnly = true`가 없애는 것 / 남기는 것** — 없어짐: 스냅샷, 변경 감지. 남음: ① **1차 캐시 적재**(후보자 답) ② `select *`로 인한 불필요 컬럼·네트워크 전송 ③ **지연 로딩 프록시**(뒤에서 누가 건드리면 쿼리 폭발). 따라서 `readOnly`는 DTO 프로젝션의 **대체가 아니라 병행 수단**(replica 라우팅 스위치로도 쓰이므로 조회 전용 메서드엔 어차피 붙인다 → 고난이도 Q4로 연결).
- **DTO 프로젝션이 포기하는 것(이번 문항 최대 공백)** — ① **1:N 컬렉션을 조인해 담으면 행이 중복**되어 DTO 하나로 안 떨어진다 → 루트만 페이징 조회 후 자식은 `in` 절 2차 쿼리 + 애플리케이션 그룹핑(중급 Q1의 `default_batch_fetch_size`와 같은 구조) ② 반환 DTO는 **영속 객체가 아니라 변경 감지가 안 된다** → 수정 목적 조회에는 사용 불가 ③ 화면 수만큼 DTO 클래스가 증식.
- **구현 방법 4종** — JPQL `select new com.x.Dto(...)`(패키지 전체 경로 필요, 생성자만), QueryDSL `Projections.constructor/fields/bean` + `@QueryProjection`, Spring Data 인터페이스 프로젝션(중첩 프로젝션도 가능), 네이티브 쿼리 + `@SqlResultSetMapping`(마지막 수단).
- **판단 기준 한 문장** — "이 조회의 목적이 **변경**이면 엔티티, **표시**면 DTO." 12장 CQRS의 출발점.

**메모**: 개별 사실은 거의 다 맞혔는데 평가가 **중**인 이유는 두 가지다.
① **첫 답변이 질문의 초점을 벗어났다.** Q5(엔티티 직접 노출)와 Q11(DTO 프로젝션)은 결론이 비슷해 보여도 근거의 층이 다른데, 후보자는 결합도 축으로 답하고 멈췄다. **"결론이 같으면 근거도 같다"고 여기는 경향** — 실제로는 Q5는 계층 경계, Q11은 조회 비용이다.
② **3장에서 세 번째로 반복된 "한쪽 면만 말하고 멈춤"**(Q7 이유 3층 / Q10 택한 전략의 비용 / 이번 3층). 이번엔 특히 선명하다 — 이유가 결합도·영속성 컨텍스트 비용·조회 컬럼 세 층인데 **면접관이 세 번 밀어야 하나씩 나왔다.** 각각을 정확히 알고 있었으므로 지식 공백이 아니라 **답변 구조의 습관**이다. 이제 이 축은 Q10 메모와 합쳐 별도 약점 항목으로 승격한다.
**정밀도 오류 1건**: `@QueryProjection`의 보호 범위 과대평가(동일 타입 순서 교체는 못 잡음). 도구가 무엇을 **못** 막는지까지 아는 것이 시니어 변별 지점이라는 점에서, ①②와 같은 뿌리(한쪽 면만 보기)로 읽힌다.
**긍정 신호**: 11-2의 `readOnly` 반론은 Q9의 9-3과 같은 모양의 승리다 — 면접관이 "그럼 필요 없지 않나"로 유도했을 때 **남은 비용 항목을 정확히 지목**했다. 유도성 반론 방어는 이제 안정적이다.

### [중급 Q12] 루프 건별 `findById` PR 리뷰 코멘트 — **중**

**본질문**: `List<Long> orderIds`를 루프 돌며 건별 `findById(...).orElseThrow(...)`로 조회하는 PR. 관리자 화면에서 몇 건만 쓰이고 지금 규모에선 충분히 빠르며 테스트도 통과. 동료는 "성능 문제 없다"고 한다. **어떤 리뷰 코멘트를 남기겠나? 실제로 쓸 문장 그대로.**
**답변 요지**: "**선택한 주문이 많아질수록 많은 쿼리가 날아간다. `IN` 절을 사용하고 요청한 주문 수와 결과 수를 비교해서 에러를 내리던가 응답을 주는 것이 더 효율적이다.**" (지적 + 대안 + **`orElseThrow`의 존재 검증을 개수 비교로 이관** — Q9의 배치 판단과 같은 논리를 힌트 없이 재사용 / 단, "실제 코멘트 문장"을 요청했는데 **사실 진술만**)

**꼬리질문 12-1** (조건 변형): `IN` 절로 고쳤는데 6개월 뒤 **정산 배치**가 이 메서드를 재사용해 `orderIds`가 **10만 건**으로 들어온다. `in (?, ?, … ×100000)`이 나가면 무슨 일이 벌어지나?
- 답변: "**이것도 문제가 된다. 한 번의 조회에 10만 건을 조회하는 것은 너무 무겁다. 100개씩 쪼개서 100번 보내도록 하는 것이 낫다.**" (청킹을 스스로 도출 / **실패 모드는 "무겁다"에서 멈춤** — DB별 한계·실행계획 캐시 오염·1차 캐시 적재 모두 미언급)

**꼬리질문 12-2** (전달 방식·rationale 핵심): 동료가 "관리자가 체크박스로 고르는 거라 많아도 20~30건이다. `IN` 절 청킹까지 넣는 건 오버엔지니어링이고 코드도 복잡해진다. 실제로 문제가 생기면 그때 고치면 되지 않나?"라고 반박한다. **approve 하겠나?**
- 답변: "**`IN` 절까지는 승인하고 청킹은 추후에 적용.**" (**타당한 판단** — 모든 지적을 blocking으로 만들지 않고 무엇을 지금 요구할지 선을 그음. 단, 근거를 YAGNI로 명시하거나 미룬 위험의 처리 방법을 함께 내지는 않음)

**꼬리질문 12-3** (횡단 약점 7번째 검증): 청킹을 미룬다면 **그 6개월 뒤의 사고를 무엇이 막아주나?** 리뷰 코멘트에 "나중에 하자"고 적는 것 말고, **사람의 기억·선의에 의존하지 않는** 방법이 있나?
- 답변: "**TODO 주석을 사용할 것이다.**" (**또 사람에게 맡김** — 3장 일곱 번째 동일 지점)

**꼬리질문 12-4** (힌트 제공): TODO는 읽는 사람에게만 작동한다. 배치 개발자는 시그니처만 보고 호출한다. 지금 이 메서드는 **10만 건이 들어와도 일단 실행된다** — **코드가 스스로 거부하게** 만들 방법은?
- 답변: "**로직상으로 개수를 제한하도록 한다.**" (힌트 후 정답 방향 도달 — 입력 크기 상한 검증)

**면접관 보충**:
- **"지금 규모에선 빠릅니다"의 정확한 반박은 성능이 아니라 계약이다** — 이 메서드는 "입력 개수에 비례해 쿼리를 발생시키는" API가 됐고, **비용이 호출자에 따라 결정되는 구조 자체가 결함**이다. 그래서 호출자가 바뀌는 순간(배치 재사용) 터진다. **성능 논쟁을 설계 논쟁으로 옮겨야** 동료를 설득할 수 있다.
- **좋은 리뷰 코멘트의 4조각** — ① 무엇이 문제인지 ② **언제 터지는지(조건)** ③ 대안 코드 ④ **blocking인지 아닌지**. ②가 빠지면 "지금 문제 없는데요"를 막을 수 없다. ④를 명시하면 리뷰가 마비되지 않는다.
- **10만 건 `IN`의 실제 실패 모드** — Oracle은 `IN` 항목 1000개 초과 시 에러, PostgreSQL은 바인드 파라미터 개수 상한(65535), MySQL은 패킷 크기 제한. 더 은밀한 것은 **파라미터 개수가 매번 달라지면 SQL 문자열도 달라져 실행계획 캐시가 오염**되는 것(Hibernate `in_clause_parameter_padding`이 개수를 2의 거듭제곱으로 맞춰 완화). 그리고 `readOnly`여도 **엔티티 10만 개가 1차 캐시에 쌓여 힙을 밀어낸다**(중급 Q11에서 후보자가 지목한 그 비용).
- **미루기로 한 결정도 코드로 못 박는다** — `if (ids.size() > MAX) throw ...` 한 줄 + 그 상한을 검증하는 테스트. 배치 개발자는 주석을 안 읽어도 **실행 즉시 실패**하고, 그 시점에 청킹이냐 배치 전용 경로냐를 결정하게 된다. **TODO는 소망이고, 상한 검증은 장치다.**
- **쿼리 수 단정으로 CI에 넘긴다** — `SQLStatementCountValidator.assertSelectCount(1)`. 3장 내내 반복된 도구 상자가 여기서도 답.
- **`findAllById(ids)`** — Spring Data가 이미 `IN` 절 조회를 제공한다. QueryDSL을 직접 쓸 필요도 없다.
- **배치가 정말 10만 건이면 청킹도 답이 아니다** — id 목록을 받는 API 자체가 잘못이고 **커서·범위 기반 조회**(`where id > ? order by id limit 1000`)로 가야 한다. 청킹은 관리자 화면용 API를 배치에 억지로 쓰는 것을 연장하는 처방이다.

**메모**: 이 문항은 **후보자의 강점과 약점이 한 화면에 같이 보이는 축소판**이다.
**강점**: 본질문에서 힌트 없이 지적·대안·존재 검증 이관을 한 번에 냈고(Q9 사고의 재사용), 12-1에서 청킹을 스스로 도출했고, 12-2에서 **오버엔지니어링 반박에 굴복하지도 과잉 방어하지도 않고 blocking/non-blocking을 나눴다.** 이 판단은 실제 팀에서 바로 쓸 수 있는 수준이다.
**약점**: 12-3에서 **TODO 주석**. 3장에서 **일곱 번째**(유령 UPDATE 진단 / N+1 자동 탐지 / `HHH000104` / OSIV 전환 검증 / 동시성 재현 테스트 / SQL 실행 순서 사전 발견 / 이번). 특히 이번은 **면접관이 "사람의 기억에 의존하지 않는 방법"이라고 조건을 명시했는데도** TODO가 나왔다는 점에서, 도구를 몰라서가 아니라 **"코드로 강제한다"는 사고 자체가 레퍼토리에 없다**는 것이 확정됐다. 힌트("코드가 스스로 거부하게")를 받자 즉시 도달했으므로 **개념 난이도 문제가 아니라 습관 문제** — 4장 진입 전 도구 상자 학습의 우선순위를 최상위로 올린다.
또한 "실제 코멘트 문장 그대로"라는 요구를 사실 진술로 답한 것은 Q11의 "이유 3층을 못 쌓음"과 같은 뿌리 — **아는 것을 상대가 납득할 형태로 조립하는 단계**가 약하다. 지식 축적은 충분하므로, 3장 이후의 훈련 초점은 **지식이 아니라 서술·강제 장치** 두 축이다.

## 중급 ⭐⭐ 완료 — 소구간 총평 (12문항)

**평가 분포**: 상 2(Q6 연관관계 주인은 기본⭐, 중급에서는 Q9 `findById`/`getReferenceById`) · 중 9 · 하 0 (기본⭐ 구간의 Q5 merge가 유일한 "하")

**확정된 강점**
1. **경험이 없는 영역에서도 추론으로 정답에 도달한다.** Q8(flush 순서), Q10(상속 매핑), Q11(DTO 프로젝션) 모두 "안 써봤다"로 시작했으나 시나리오를 주면 실무 정답에 닿았다. Q10에서는 답하기 전에 **조회 패턴을 되물어 요구사항을 확정**했다 — 선택 변수를 알고 있다는 증거.
2. **유도성 반론에 흔들리지 않는다.** Q9의 9-3(DB 최후 방어선 논리로 유도), Q11의 11-2(`readOnly`면 충분하지 않나), Q12의 12-2(오버엔지니어링 반박) — 세 번 모두 자기 기준으로 방어했고, 전제가 바뀌면(Q9 9-4) 즉시 판단을 갈아탔다.
3. **자기 선택에 근거가 있다.** "안 해봤다"에서 멈추지 않고 "안 한 이유"를 댄다(Q9의 `findById` 선호 = 존재 검증). Q12의 blocking/non-blocking 구분도 같은 성격.

**확정된 약점 (2축, 둘 다 지식이 아니라 습관)**
1. **안전망을 코드로 고정하지 않는다 — 7회 반복.** 정점은 Q12의 TODO 주석("사람의 기억에 의존하지 않는 방법"을 명시적으로 물었는데도). 힌트 한 번에 도달하므로 개념 난이도 문제가 아니다. → 약점 노트 최상위 항목.
2. **트레이드오프·근거를 한 호흡에 양면으로 조립하지 못한다 — 3회 반복**(Q7 이유 3층 / Q10 택한 전략의 비용 / Q11 이유 3층). Q12의 "실제 코멘트 문장"을 사실 진술로 답한 것도 같은 뿌리. **아는 것을 상대가 납득할 형태로 조립하는 단계**가 약하다.

**다음 구간 권고**: 고난이도 ⭐⭐⭐로 진행. 4문항 모두(동시성 4가지 비교 / 대량 INSERT / 여러 Aggregate / replica 라우팅) **트레이드오프 서술이 곧 평가 대상**이므로, 위 약점 2번이 바로 시험된다. 특히 첫 문항은 "정답 없는 문제에서 비교표를 말로 그리는 능력"을 보는 것이니, **선택 → 얻는 것 → 포기하는 것 → 감당 가능한 이유** 4단 구조를 의식적으로 연습하며 답할 것.

### [고난이도 Q1] 동시성 갱신을 낙관적 락 / 비관적 락 / 원자적 UPDATE / 분산 락으로 풀 때의 트레이드오프 — **상**

**본질문**: 재고 차감·포인트 차감 같은 동시성 갱신 문제를 ① 낙관적 락(`@Version`) ② 비관적 락(`select ... for update`) ③ 원자적 UPDATE(`update ... set qty = qty - 1 where id = ? and qty >= 1`) ④ 분산 락(Redis) 각각으로 풀 때의 트레이드오프를 비교하고, 어떤 상황에서 무엇을 고를지 말하라.
**답변 요지**: "**낙관적 락**은 동시 요청 시 성공한 1개를 제외하고 계산과 DB 반영을 모두 다시 하여 자원 낭비. **비관적 락**은 하나씩만 반영되지만 다른 요청이 스레드와 커넥션을 잡고 있어 자원 낭비. **원자적 UPDATE**는 DB에 락을 전가해 DB단에서 하나씩 처리하지만 이 또한 대기해야 하므로 스레드·커넥션 모두 소모. **분산 락**은 Redis로 애플리케이션 단에서 락을 잡으므로 **스레드만 소모**. 나라면 **동시성이 얼마나 발생하느냐**에 따라 선택 — 거의 없으면 낙관적 락, 많으면 분산 락으로 DB에 영향을 주지 않도록." (**이번 세션 최고 답변.** 네 방식을 **"무슨 자원을 소모하는가"라는 단일 축으로 꿰어** 비교하고 선택 기준까지 한 호흡에 — 3장 내내 지적한 조립 문제가 실제로 교정된 첫 사례)

**꼬리질문 1-1**: ②와 ③을 거의 같은 등급으로 묶었는데, **DB가 그 행의 락을 실제로 붙잡고 있는 시간**을 비교하면? (두 코드 제시)
- 답변: "**비관적 락은 `findByIdForUpdate`부터 커밋할 때까지, 원자적 UPDATE는 `repo.decrease(id)` 이 순간에만. 붙잡고 있는 시간은 원자적 UPDATE가 훨씬 짧다.**" (정확 — 락 구간에 **애플리케이션 왕복이 포함되느냐**가 결정적 차이라는 핵심을 짚음)

**꼬리질문 1-2** (반론): 임계 구간이 가장 짧은 게 원자적 UPDATE라면 **충돌이 많을수록 오히려 그쪽이 유리**해야 하지 않나? 그리고 분산 락을 걸어도 UPDATE는 그대로 DB로 나가는데 "DB에 영향을 주지 않는다"는 게 정확히 무엇인가?
- 답변: "**DB 커넥션에 영향을 주지 않는다는 말이다.** 임계 구간이 짧더라도 요청이 순간에 많이 들어오면 커넥션을 물고 있을 수밖에 없고, 이는 **다른 API에 영향을 줄 수밖에 없다.**" (**정교한 방어.** 락을 트랜잭션 밖에서 잡으면 대기 비용이 커넥션 풀 밖으로 밀려난다 — 분산 락의 실제 존재 이유 중 하나이고 교과서보다 운영에 가까운 논리. 면접관의 반론에 굴복하지 않고 자기 논거를 정확히 좁혔다)

**꼬리질문 1-3** (실패 경로): 재고 100개 선착순인데 ① 락을 잡은 스레드가 GC 정지·네트워크 지연으로 **TTL 3초를 넘겨** 그 사이 락이 만료돼 다른 요청이 같은 락을 잡거나 ② Redis 노드가 순간 장애. 재고는 어떻게 되나? 그래도 음수로 안 내려가게 하려면?
- 답변: "**락이 풀려서 재고가 음수가 된다. 이때는 내부적으로 원자적 UPDATE를 최후의 보루로 삼는 것이 좋다.**" (**정확.** 3장 내내 유지해온 "DB를 최후 방어선으로" 기준을 분산 락 환경에 그대로 적용)

**꼬리질문 1-4** (양면 서술 요구): 원자적 UPDATE가 그렇게 좋다면 왜 **모든** 재고·포인트 갱신을 그것으로만 처리하지 않나? 이 방식이 **포기하는 것**은?
- 답변: "**커넥션 외에는 잘 모르겠다.**" (**막힘 — 이번 문항 유일한 감점**)
- **힌트**: 이 `update ... set qty = qty - 1`은 중급 Q4에서 다룬 **벌크 연산과 같은 성질**의 쿼리다. JPA 관점에서 무슨 일이 벌어지나?
- 답변: "**DB 데이터랑 영속성 데이터가 다를 수 있다.**" (힌트 후 즉시 도달)

**꼬리질문 1-5**: 충돌이 드물어 낙관적 락을 쓰면 `OptimisticLockException` 재시도가 필요하다. `@Transactional` 메서드 **안에서** `for` 루프로 감싸 `saveAndFlush` + `catch` 재시도하는 코드를 제시 — 문제가 있나?
- 답변: "**커밋할 때 트랜잭션 롤백에 체크되어 있어서 오류가 난다.**" (**즉답.** 중급 Q7(유니크 제약) 약점 노트에 "채울 것"으로 적어둔 `rollback-only` 마킹이 실제로 인출됨)

**면접관 보충**:
- **재시도 코드의 두 번째 문제(후보자 미언급)** — `rollback-only`를 피해 트랜잭션을 밖으로 빼더라도, **같은 영속성 컨텍스트를 쓰면 `findById`가 1차 캐시에서 옛 `version`을 그대로 돌려준다.** 그러면 재시도는 몇 번을 돌아도 같은 값으로 실패한다. **재시도는 새 트랜잭션 + 새 영속성 컨텍스트에서**(`@Retryable` + `REQUIRES_NEW`, 또는 트랜잭션 경계 밖 루프).
- **선택의 기본값은 "임계 구간에 무엇이 들어가는가"** — 읽고·계산하고·쓰는 과정이 **SQL 한 문장으로 압축되면 원자적 UPDATE가 기본값**. 낙관적 락은 여러 필드를 읽어 애플리케이션에서 계산해야 하고 충돌이 드물 때. 비관적 락은 계산이 복잡하고 충돌이 잦아 재시도 비용이 클 때. **분산 락은 임계 구간에 DB 밖 자원이 포함될 때**(외부 PG 호출, 여러 DB에 걸친 갱신, 멀티 인스턴스 스케줄러).
- **Redis 분산 락은 정합성 보증 장치가 아니라 부하 최적화 장치** — TTL 만료·노드 장애·GC 정지로 언제든 두 스레드가 동시에 임계 구간에 들어갈 수 있다(Redlock 논쟁의 핵심). **정합성의 최종 보증은 항상 DB**: `where qty >= 1` 조건 + **`CHECK (qty >= 0)` 제약**을 함께 걸면 어떤 경로로 뚫려도 재고는 음수가 되지 않는다.
- **원자적 UPDATE가 포기하는 것(1-4의 공백)** — ① **영속성 컨텍스트 우회**(중급 Q4와 동일한 1차 캐시 불일치. 같은 트랜잭션에서 그 엔티티를 다시 읽으면 옛 값) ② **도메인 로직이 엔티티가 아니라 SQL로 새어나간다**(할인 정책·등급별 차감량 같은 규칙을 쿼리에 넣기 시작하면 테스트·재사용이 어려워짐) ③ 여러 필드를 함께 갱신하거나 조건이 복잡해지면 표현력이 급격히 떨어진다.
- **트래픽이 극단적이면 네 가지 모두 답이 아닐 수 있다** — 선착순 이벤트는 DB를 때리지 않고 **Redis `DECR`로 수량을 선점**한 뒤 당첨자만 비동기로 확정한다. 이때 Redis는 락이 아니라 **카운터**로 쓰이며, 최종 확정은 여전히 DB 제약이 지킨다.

**메모**: **3장 세 번째 "상"이자, 지적받은 습관이 교정된 것을 확인한 첫 사례.** 본질문에서 네 방식을 **단일 축(자원 소모)으로 꿰고 선택 기준까지 한 호흡에** 냈다 — 직전 구간 총평에서 최우선 약점으로 적은 "트레이드오프를 양면으로 조립하기"가 바로 다음 문항에서 개선됐다. 면접관의 지적이 즉시 반영되는 학습 속도.
**1-2가 이번 문항의 백미** — 면접관이 "임계 구간이 짧으면 원자적 UPDATE가 유리하지 않나 / 분산 락도 UPDATE는 나가지 않나"로 양쪽에서 밀었는데, **논거를 '커넥션 풀 보호'로 정확히 좁혀** 방어했다. 이는 암기가 아니라 커넥션 풀 고갈을 이해하고 있어야 나오는 답이며, 중급 Q2(OSIV)에서 비어 있던 "놀고 있는 커넥션 점유"의 개념이 여기서 자기 언어로 작동했다.
**약점 노트 항목 2개가 실제로 인출됐다** — 1-3의 "DB를 최후 보루로"(Q7 계열), 1-5의 `rollback-only` 마킹(Q7 약점 노트에 "채울 것"으로 명시했던 항목). **복습이 작동하고 있다는 증거**이므로 약점 노트 운용을 유지한다.
**남은 공백은 하나** — 1-4에서 "가장 좋아 보이는 선택지의 대가"를 묻자 막혔다. 양면 서술이 **자기가 고른 것**에 대해서는 나오는데(본질문), **면접관이 좋다고 인정해준 것**에 대해서는 아직 반사적으로 안 나온다. 다음 문항들에서 같은 패턴을 한 번 더 확인할 것.

### [고난이도 Q2] 대량 INSERT의 JPA 한계와 JDBC batch 우회 (IDENTITY 문제 포함) — **중**

**본질문**: 매일 새벽 정산 내역 **100만 건**을 `for (dto : dtos) settlementRepository.save(...)`로 적재하는 배치가 2시간 넘게 걸린다. 왜 느리고 어떻게 개선하겠나?
**답변 요지**: "**100만 건 쿼리가 나가기 때문이다. 벌크 쿼리로 수정해야 한다.**" (원인 진단은 맞으나 매우 짧고 처방이 없음)

**꼬리질문 2-1**: "벌크 쿼리로 수정"을 구체화하라. 이 코드에서 **정확히 무엇을 바꾸면** INSERT 100만 번이 줄어드나?
- 답변: "**JPQL로 변경 후 페이징으로 쿼리당 몇 개의 데이터를 넣을지 분리해야 한다.**" (**오답** — JPQL에는 INSERT 문이 없다(`insert into ... select` 제외). 면접관이 사실 교정 후 방향 제시)

**꼬리질문 2-2** (방향 제시): Hibernate에는 여러 INSERT를 **JDBC 레벨에서 하나로 묶어 보내는 기능**이 있다. 이걸 켜는 설정은? 켜면 SQL이 어떻게 나가나?
- 답변: "**`hibernate.jdbc.batch_size` 설정하면 insert가 묶여서 나간다.**" (정확)

**꼬리질문 2-3** (이 문항의 핵심): PK가 `@GeneratedValue(strategy = IDENTITY)`(MySQL auto_increment)면 `batch_size`를 아무리 키워도 **INSERT가 전혀 묶이지 않는다.** 왜?
- 답변: "**auto_increment라 INSERT 하기 전엔 id를 알 수 없어서.**" (**정확 — 이 문항에서 가장 중요한 지점.** 식별자를 모르면 1차 캐시에 넣을 수 없으므로 `persist` 시점에 즉시 INSERT를 날려 생성 키를 받아와야 하고, 그래서 쓰기 지연 자체가 성립하지 않는다)

**꼬리질문 2-4**: DB가 MySQL이라 시퀀스 오브젝트가 없다. 100만 건 적재를 어떻게 처리하겠나?
- 답변: "**다른 곳에서 id를 관리하도록 한다. Redis `INCR` 등.**" (분산 ID 생성으로는 유효한 선택지이나 **이 배치 하나 때문에 인프라 의존이 생김**. 표준 우회로는 미언급)

**꼬리질문 2-5** (조건 제한): **인프라를 새로 추가하지 않고** 애플리케이션과 MySQL만으로 빠르게 만들려면?
- 답변: "**JPA를 사용하지 않고 바로 DB에 넣는 방법을 사용한다.**" (`JdbcTemplate.batchUpdate` 경로 — 정확한 방향)

**꼬리질문 2-6** (메커니즘 확인): `JdbcTemplate`으로 내려가면 테이블은 그대로 `auto_increment`인데 배치가 잘 동작한다. **JPA에서 문제였던 것이 왜 여기서는 문제가 안 되나?**
- 답변: "**JDBC는 영속성 컨텍스트가 없으니 id를 몰라도 된다.**" (**정확.** 원인을 알기 때문에 우회로가 통하는 이유까지 설명할 수 있는 것 — 암기와 이해를 가르는 지점)

**면접관 보충**:
- **느린 이유는 두 갈래인데 후보자는 한쪽만 봤다** — ① 쿼리 왕복 100만 번 ② **영속성 컨텍스트에 엔티티 100만 개 + 스냅샷이 그대로 누적**. 힙이 밀리고 GC가 돌며, `flush`마다 변경 감지 비교 대상이 계속 늘어나 **뒤로 갈수록 느려진다**. 그래서 배치에서는 **일정 건수마다 `flush()` + `clear()`** 가 필수(기본⭐ Q2의 스냅샷 비용이 여기서 실제 장애로 나타난다).
- **JPA를 유지한 채 푸는 표준 경로(2-4의 공백)** — ID 전략을 `IDENTITY` → **`SEQUENCE`**(MySQL이면 Hibernate `TABLE` 제너레이터) + **`allocationSize`를 크게**. 채번을 한 번에 여러 개 미리 받아오므로 INSERT를 미룰 수 있고 배치가 살아난다. **`JdbcTemplate`으로 내려가는 것은 그다음 카드**이지 첫 카드가 아니다.
- **개선 순서** — ① ID 전략 교체 ② `hibernate.jdbc.batch_size` + **`order_inserts`/`order_updates`**(같은 테이블끼리 모여야 묶인다) ③ 배치 크기마다 `flush()`+`clear()` ④ 그래도 부족하면 `JdbcTemplate.batchUpdate` 또는 `LOAD DATA INFILE`.
- **MySQL에서 반드시 확인할 것** — JDBC URL의 **`rewriteBatchedStatements=true`**. 없으면 Hibernate가 묶어도 **드라이버가 결국 문장을 하나씩 보낸다.** 설정을 켜놓고 "왜 안 빨라지지"로 헤매는 대표 지점이며, **Hibernate 로그로는 확인되지 않는다**(로그에는 묶인 것처럼 보인다) — 실제 전송을 봐야 한다.
- **100만 건을 트랜잭션 하나로 처리하지 않는다** — undo 로그와 락이 계속 커지고 중간 실패 시 전부 롤백. **청크 단위 커밋**(Spring Batch chunk) + **멱등성 확보**(정산 내역이면 (정산일자, 거래ID) 유니크 키 + `insert ignore`/upsert)로 어디서 끊겨도 재실행 가능하게 만든다.

**메모**: 직전 Q1(상)과 대비된다. **메커니즘 질문에는 강하고(2-3, 2-6 모두 자력 정답) 처방 레퍼토리는 얇다.** 원인을 알면 우회로의 이유까지 설명하지만, "그 상황에서 실무자가 실제로 밟는 순서"는 갖고 있지 않다 — 2-1에서 JPQL로 잘못 갔고, 2-4에서 표준 해법(`SEQUENCE`/`allocationSize`) 대신 Redis 채번으로 점프했으며, 2-5에서도 "JPA를 버린다"로 바로 갔다. **JPA 안에서 단계적으로 조여가는 카드가 없다.**
또 하나: **영속성 컨텍스트 누적(OOM)을 언급하지 못했다.** 중급 Q11에서 "1차 캐시 적재 자체가 비용"이라고 정확히 말했던 사람이, 100만 건 배치에서는 그 축을 떠올리지 못했다 — **알고 있는 개념을 새 상황에 옮겨 붙이는 연결이 아직 자동이 아니다.** Q1에서는 그 연결이 훌륭히 작동했으므로(커넥션 풀 이해 → 분산 락 방어), 문항별 편차로 본다.
`rewriteBatchedStatements`는 "로그로는 확인되지 않는다"는 성격 때문에 **횡단 약점(관측·안전망)** 과 같은 계열이다 — 약점 노트의 도구 상자 항목에 이 사례를 추가한다.

### [고난이도 Q3] 한 트랜잭션에서 여러 Aggregate를 수정하는 문제와 도메인 이벤트 분리 — **중**

**본질문**: `@Transactional completeOrder()`가 주문 상태 변경 → 재고 차감 → 포인트 적립 → 쿠폰 사용 → **완료 메일 발송**을 한 트랜잭션에서 수행한다. 이 구조의 문제는?
**답변 요지**: "**`getItems`를 하게 된 경우 여러 번의 쿼리가 날아간다. 나중에 N+1 문제로 성능 이슈가 생길 수 있다.**" (**초점 이탈** — N+1은 fetch join 하나로 끝나는 국소 문제. 이 문항은 트랜잭션 경계)

**꼬리질문 3-1** (초점 교정): 이 메서드가 도는 동안 **커넥션과 행 락은 언제부터 언제까지** 잡혀 있나? 특히 마지막 줄 메일 발송을 감안하면?
- **후보자의 되질문**: "**`for update`를 사용하는 곳이 있는지 안 알려줬다.**" (**좋은 습관** — Q10에서 조회 패턴을 되물은 것과 같은 태도)
- 답변: "**만약 행 락을 잡았다면 메일 발송 끝날 때까지 갖고 있다. 메일 API라면 응답 올 때까지 락을 잡고 있다.**" (정확)
- **면접관 교정**: 명시적 락이 없어도 **`UPDATE` 문 자체가 대상 행에 배타 락을 걸고 커밋/롤백까지 유지**한다(InnoDB 기본 동작). `select ... for update`는 그 락을 SELECT 시점에 **미리** 잡는 것일 뿐. 그래서 명시적 락이 하나도 없어도 커밋이 늦어지면 락 점유가 그대로 길어진다.

**꼬리질문 3-2**: 메일 발송을 `@Async`로 뺐다. 그런데 뒤이어 `couponService.use()`에서 예외가 나 **트랜잭션이 롤백**됐다. 무슨 일이 벌어지나? 어떻게 막나?
- 답변: "**롤백되었지만 메일은 발송된다. 메일 발송을 커밋 후 진행으로 옮긴다. 스프링 이벤트를 사용하면 된다.**" (정확 — `@TransactionalEventListener(phase = AFTER_COMMIT)`)

**꼬리질문 3-3**: 재고·포인트·쿠폰은 여전히 한 트랜잭션 안이다. 이것들도 분리해야 하나? **무엇을 남기고 무엇을 뺄지 판단 기준은?**
- 답변: "**단순 DB 변경 작업이면 사실 트랜잭션을 분리할 필요가 없다. 오히려 분리할수록 추후 디버깅이 번거로워진다.** 즉 트랜잭션을 잡고 **block되는 상태가 있는지** 확인해야 한다. 아니라면 함께 있는 것이 유지보수할 때 편하다." (**실무적으로 타당하고, 대가(디버깅 난이도)를 스스로 붙였다 — 양면 서술이 자발적으로 나온 두 번째 사례**)

**꼬리질문 3-4** (조건 변형): 주문 완료가 **초당 수천 건**이고, 같은 시각 관리자 정산 배치가 **재고와 포인트를 반대 순서로** 갱신한다. 블로킹 I/O는 하나도 없고 전부 단순 DB 변경이다. 무슨 일이 벌어지나?
- 답변: "**배타 락으로 인해 커넥션을 들고 있는 시간이 오래 걸리고 다른 API까지 영향을 미칠 수 있다. 이렇게 되면 포인트 차감은 트랜잭션 밖으로 분리하는 것이 좋다.**" (커넥션 확산 축은 정확하나 **"반대 순서"라는 조건을 깔았는데도 데드락을 못 짚음**)
- **힌트**: 주문은 재고→포인트, 배치는 포인트→재고 순으로 잡는다. 서로 상대가 쥔 락을 기다리면 단순 대기로 끝나나?
- 답변: "**아 데드락이 발생한다. 재고 데이터 수정하고 포인트 수정할 때 락으로 대기하고, 배치는 포인트는 수정했지만 재고를 기다린다.**" (힌트 후 즉시 정확히 서술)

**꼬리질문 3-5**: 포인트 적립을 도메인 이벤트로 분리했다. 주문은 커밋됐는데 그 직후 **서버 재시작 또는 포인트 서비스 예외**로 적립이 실패했다. 주문은 완료됐는데 포인트는 없다. 어떻게 다루겠나?
- 답변: "**주문 도메인에 포인트가 쌓였는지 체크하는 데이터를 갖고 있으면 된다.**" (방향 정답 — 사실상 Outbox 패턴의 축소판. 다만 재처리 주체와 멱등성은 미언급)

**면접관 보충**:
- **트랜잭션 경계는 네 가지 경계를 동시에 긋는다** — **정합성 경계 = 락 경합 범위 = 실패 파급 범위 = 커넥션 점유 시간.** 여러 Aggregate를 한 트랜잭션에 넣는 것은 이 넷을 한꺼번에 키우는 결정이며, DDD의 **"트랜잭션 하나에 Aggregate 하나"** 원칙의 근거가 이것이다.
- **분리 기준을 하나 더**(3-3의 보완) — "블로킹 여부"에 더해 **"이 작업이 실패했을 때 주문 자체를 취소해야 하는가"**. 재고 차감은 실패하면 주문이 성립할 수 없으니 같은 트랜잭션에 남기고, 포인트·쿠폰·메일은 나중에 보정 가능하니 이벤트로 뺀다. **경계를 정하는 것은 성능이 아니라 정합성 요구 수준이다.**
- **Outbox 패턴**(3-5의 완성형) — 후보자의 "주문에 적립 여부 플래그"에 두 가지가 더 필요하다: ① **누가 그 플래그를 보고 재처리하는가**(미처리 건을 긁는 주기 배치 또는 재시도 큐) ② **재처리가 중복 적립을 만들지 않도록 멱등성**(적립 이력에 주문ID 유니크 제약). 정석은 **이벤트 자체를 같은 트랜잭션에서 outbox 테이블에 INSERT**해 "주문 커밋 = 이벤트 저장"을 원자적으로 만들고, 별도 프로세스가 그 테이블을 읽어 발행하는 것.
- **`@TransactionalEventListener(AFTER_COMMIT)`의 함정** — 그 리스너 안에서 DB를 변경하려면 **`REQUIRES_NEW`로 새 트랜잭션**을 열어야 한다. 원 트랜잭션은 이미 끝났으므로 그냥 쓰면 조용히 반영되지 않는다.
- **데드락 예방의 정석** — 락 획득 순서를 **전역으로 고정**한다. 여러 행을 갱신할 때 **항상 PK 오름차순으로 정렬한 뒤 처리**하면 순서 역전 자체가 사라진다. **Hibernate가 지켜주지 않으므로 코드로 고정**해야 한다(중급 Q8 보충과 동일한 처방).

**메모**: **본질문 초점 이탈이 또 나왔다** — Q11(DTO 프로젝션에서 Q5 축으로 답함)에 이은 두 번째. 패턴이 분명하다: **"이 구조의 문제는?"처럼 열린 질문을 받으면 가장 최근에 학습한 성능 주제(N+1)로 먼저 간다.** 열린 질문에서는 **구조 → 경계 → 성능** 순으로 큰 것부터 훑는 습관이 필요하다.
반면 **유도 후의 정확도는 높았다**. 3-1의 되질문, 3-2의 즉답(`@Async` 롤백 함정), 3-3의 자발적 양면 서술은 모두 우수하다. 특히 3-3은 "분리가 항상 옳다"는 교과서적 답을 하지 않고 **모놀리스의 현실(디버깅 비용)을 근거로 반대편을 세운** 답이라 오히려 시니어에 가깝다.
**데드락은 여전히 공백** — 중급 Q8 보충에서 다룬 축인데 조건을 다 깔아줘도 스스로 도달하지 못했다. **락 순서 역전은 "알면 즉시 보이고 모르면 영원히 안 보이는" 유형**이므로 약점 노트에 단독 항목으로 유지한다.
3-5의 답은 방향이 정확했고 이름만 몰랐을 뿐이다(Outbox). **패턴 이름을 몰라도 필요한 구조를 스스로 설계해내는** 것은 3장 내내 반복 확인된 이 후보자의 강점이다.

### [고난이도 Q4] read replica 라우팅과 replication lag — **중**

**본질문**: 쓰기용 마스터 1대 + 읽기용 리플리카 2대로 나눴다. 매번 코드에서 지정하지 않고 **`@Transactional(readOnly = true)` 기준으로 자동 라우팅**을 구현하려면?
**답변 요지**: "**DB 조회할 때 readOnly를 보고 DB를 선택하도록 하면 된다.**" (방향은 맞으나 구현 장치 없음)

**꼬리질문 4-1**: 스프링에서 "readOnly를 보고 DB를 고르는" 지점이 **정확히 어디**인가? 어떤 장치를 쓰나?
- 답변: "**정확하게 모르겠다. 하지만 찾아볼 수 있다.**" (**모름 — 인정 후 넘어감.** 아는 척하지 않은 것 자체는 긍정 신호)
- 면접관이 `AbstractRoutingDataSource` + `determineCurrentLookupKey()` + `TransactionSynchronizationManager.isCurrentTransactionReadOnly()`만 짚어주고 진행

**꼬리질문 4-2**: "게시글을 등록했는데 목록에 없고, 새로고침하면 나타난다"는 제보. 무슨 일이며 어떻게 다루나?
- 답변: "**쓰기 DB와 읽기 DB가 분리되어 있어 동기화 전에 읽기 DB로부터 데이터를 조회해서 그렇다. 해결책으로는 쓸 때 응답을 줄 것 같다.**" (원인 정확 / 처방은 **쓰기 응답에 결과를 담아 재조회 자체를 없애기** — lag을 우회하는 대신 **문제 상황을 만들지 않는** 접근이라 실무적으로 견고. 다만 목록 전체·타인 데이터 화면에는 적용 불가)

**꼬리질문 4-3** (조건 변형): 그 처방은 개발자가 매번 판단해야 하고, 누락된 화면은 지연이 커지는 순간 조용히 깨진다. 평소 50ms인 지연이 **새벽 배치 때 5초**까지 벌어진다면 애플리케이션은 어떻게 알아채고 무엇을 해야 하나?
- **후보자의 되질문**: "**lag이 무엇인지 모르겠다. 리플리카 지연은 동기화 지연을 의미하는가?**" (용어 확인 — 아는 척하지 않음)
- 답변: "**리플리카 지연을 애플리케이션 자체에서 알 수는 없을 것이다. 그럼 DB를 모니터링하는 무엇인가가 필요하고, 모니터링으로부터 접근 DB를 수정할 수 있어야 한다.**" (**대응 구조는 정확** — 리플리카 헬스체크 기반 동적 라우팅 제외가 바로 이 모양 / 다만 "애플리케이션이 알 수 없다"는 전제는 틀림)

**면접관 보충**:
- **구현의 핵심 함정 — `LazyConnectionDataSourceProxy`** — `AbstractRoutingDataSource`만 붙이면 대개 동작하지 않는다. 스프링은 **트랜잭션 시작 시점에 커넥션을 먼저 획득**하는데 그때는 아직 `readOnly` 정보가 반영되기 전이라 항상 같은 DB로 간다. `LazyConnectionDataSourceProxy`로 감싸 **실제 쿼리가 나가는 순간까지 커넥션 획득을 미뤄야** 라우팅이 걸린다. "리플리카로 안 가는데요"의 대표 원인.
- **`@Transactional`이 없는 조회는 라우팅을 못 탄다** — 트랜잭션 밖이면 readOnly 정보 자체가 없다. 조회 메서드에 `@Transactional(readOnly = true)`를 붙이는 규율이 필요하고 **ArchUnit 룰로 강제** 가능(중급 Q2 OSIV 전환 검증과 같은 도구).
- **애플리케이션은 지연을 알 수 있다(4-3의 오해 교정)** — ① 리플리카에 주기적으로 `SHOW REPLICA STATUS`를 조회해 `Seconds_Behind_Source`를 읽거나 ② 더 정확한 **하트비트 테이블**(마스터에 1초마다 현재 시각 기록 → 리플리카에서 읽어 현재 시각과의 차이 계산). 이 값이 실제 지연이며 헬스체크 지표가 된다.
- **읽기 일관성은 층으로 쌓는다** — ① 쓰기 응답으로 재조회 제거(후보자 답) ② **쓴 직후 몇 초간 그 사용자의 요청만 마스터로**(세션에 마지막 쓰기 시각 기록 — read-your-writes를 전역 성능 손해 없이 만족시키는 표준 기법) ③ 정합성 필수 조회만 명시적 마스터 강제 ④ 지연이 임계치를 넘으면 해당 리플리카를 라우팅 풀에서 제외.
- **리플리카를 다 빼면 마스터가 그 부하를 다 받는다** — 제외 로직에는 반드시 상한과 폴백 설계(조회 제한, 캐시 응답 허용)가 함께 있어야 한다.

**메모**: 이 문항은 **경험이 없는 영역에서 후보자의 기본 태도가 어떻게 작동하는지**를 보여준다. 4-1에서 모른다고 인정하고, 4-3에서 용어를 되물었으며, 그럼에도 **대응 구조(모니터링 → 라우팅 제어)는 스스로 도출**했다. Q10(상속 매핑)·Q3(트랜잭션 경계)에서와 같은 패턴 — **설계 감각은 있고 도구 이름이 없다.**
4-2의 "쓸 때 응답을 준다"는 답은 특히 좋다. 교과서적 답(마스터 강제 조회)보다 **문제를 만들지 않는 쪽**을 먼저 떠올렸고, 이는 Q12의 "입력 상한으로 애초에 막기"와 같은 사고 방향이다.
**주의(기록 무결성)**: 이 문항 진행 중 후보자가 작성하지 않은 메시지 2건이 사용자 입력으로 도착했다(입력 채널 문제로 추정). 해당 내용("정합성이 중요한 부분은 write DB에서 조회" / "리플리카가 응답을 줄 수 있는지 파악해 막는다")은 **후보자 답변이 아니므로 위 기록과 평가에서 제외**했다.

## 알면 좋은 +α

### [+α Q1] `CascadeType.REMOVE`와 `orphanRemoval`의 차이, 사고 위험 — **하**

**본질문**: `Post` 1:N `Attachment`에서 `cascade = CascadeType.REMOVE`와 `orphanRemoval = true`의 차이는? 각각의 사고 위험은?
**답변**: "**정확하게 모르겠다.**" (미답 — 면접관이 핵심만 짚고 다음으로 진행)

**면접관 보충(핵심만)**:
- **`CascadeType.REMOVE`는 "부모가 삭제될 때" 자식도 함께 삭제**한다. 트리거는 **부모의 `remove()` 한 가지뿐**.
- **`orphanRemoval = true`는 거기에 더해 "부모와의 연결이 끊긴 순간" 자식을 삭제**한다. `post.getAttachments().remove(a)` 한 줄이면 그 자식 행이 DELETE된다 — **컬렉션에서 빼는 행위가 곧 삭제 명령**이 되는 것이 결정적 차이.
- **사고 위험 ①(`orphanRemoval`)** — `attachments.clear()`나 **컬렉션 통째 재할당**(`this.attachments = newList`)이 **전건 DELETE**가 된다. "목록을 갈아끼우려던" 코드가 데이터 삭제가 되는 유형이며, 기본⭐ Q2에서 다룬 "안 시킨 UPDATE"의 삭제판이다.
- **사고 위험 ②(`CascadeType.REMOVE`)** — 자식이 **다른 엔티티와도 공유되는 참조**일 때 부모 삭제가 공유 자원을 지운다. `CascadeType.ALL`에 REMOVE가 포함되어 있어 **의도치 않게 켜지는 경우가 대부분**이다.
- **공통 위험** — 자식 수만큼 DELETE가 개별로 나간다(100건이면 DELETE 100번). 대량이면 벌크 DELETE로 내려가야 하는데, 그러면 영속성 컨텍스트 불일치(중급 Q4)가 따라온다.
- **판단 기준** — 자식이 **부모 없이는 존재 의미가 없는 종속 관계**(주문-주문상품, 게시글-첨부)일 때만 켠다. 공유되거나 독립적으로 조회되는 엔티티에는 켜지 않는다. 그리고 **`CascadeType.ALL`을 습관적으로 쓰지 않는다.**

**메모**: 미답. 3장에서 두 번째 "하"(첫 번째는 기본⭐ Q5 merge). 다만 성격이 다르다 — merge는 **잘못 알고 있었던** 것이고 이번은 **아예 안 써본** 영역이다. `cascade`/`orphanRemoval`은 편의 기능이라 모르고 지나가기 쉬운데, **사고가 나면 데이터 유실**이라 위험 등급은 높다. 약점 노트 최우선으로 올린다.

### [+α Q2] 엔티티의 `equals`/`hashCode` — 프록시와 id 생성 시점 문제 — **중**

**본질문**: `Set<Member>`에 넣은 미저장 엔티티를 `save()` 한 뒤 `members.contains(member)`가 `false`가 된다. 왜인가?
**답변 요지**: "**id가 null일 때 hashCode와 저장 후 hashCode가 달라져서.**" (즉답 — `HashSet`은 넣을 때의 버킷을 기억하는데 해시값이 바뀌면 엉뚱한 버킷을 뒤진다)

**꼬리질문 2-1**: `equals`/`hashCode`를 어떻게 구현해야 이 문제가 안 생기나? 특히 `hashCode`는 무엇을 기준으로?
- 답변: "**`equals`와 `hashCode`를 id값이 아닌 다른 필드들의 값으로 구현해야 한다.**" (자연키 기반 — 불변 자연키가 있으면 유효한 답)

**꼬리질문 2-2** (조건 변형): `name`·`email`·`phone` 셋 다 사용자가 마이페이지에서 변경할 수 있다. 이 필드로 `hashCode`를 만들면? **변하지 않는 자연 키가 아예 없는 엔티티**라면 무엇을 기준으로?
- 답변: "**변경은 가능하더라도 필드를 `final`로 해서 무조건 새로운 객체를 생성하도록 해야 한다. 그럼 이 필드들로 hashCode를 만들어도 상관없다.**" (**엔티티에는 성립하지 않는 답** — 값 객체(VO)의 논리를 엔티티에 적용)
- **면접관 교정**: ① 엔티티는 **DB의 한 행에 대응**하므로 이름이 바뀌어도 같은 회원이고, 새 객체로 갈아치우면 **다른 행**이 된다 ② **변경 감지 자체가 필드가 바뀌는 것을 전제**로 동작하므로 `final`이면 JPA의 기본 동작이 성립하지 않는다. 엔티티는 **"식별자는 고정되고 내용은 변하는"** 객체다.

**꼬리질문 2-3** (힌트 제공): 그 조건에서 `hashCode()`는 무엇을 반환해야 규약을 지키나? 힌트 — **"항상 같은 값을 유지한다"** 만 만족하면 된다.
- 답변: "**id 이외에는 잘 모르겠다.**" (**막힘** — 면접관이 정답 제시: **상수 반환**(`return 31;` 또는 `getClass().hashCode()`). 버킷이 하나가 되지만 엔티티를 대량으로 `Set`에 넣는 일은 드물어 감수한다)

**꼬리질문 2-4**: `equals`에서 `getClass() != o.getClass()` 비교가 깨지는 상황은? (Q9의 `getReferenceById`와 같은 눈으로 보라는 단서 제공)
- 답변: "**프록시 객체일 때 깨진다.**" (**정확** — `Member$HibernateProxy`는 `Member.class`와 다르다. 지연 로딩된 연관 엔티티도 동일)

**면접관 보충**:
- **`equals`는 `getClass()`가 아니라 `instanceof`로** 비교하면 프록시도 통과한다. Hibernate 환경이면 `Hibernate.getClass(o)`가 프록시를 벗겨 실제 클래스를 돌려준다.
- **id 비교는 `id != null && id.equals(...)`** 형태로. 저장 전(id null)이면 항상 `false`가 되어 **서로 다른 미저장 객체가 같다고 판정되는 사고**를 막고, 자기 자신은 맨 앞의 `this == o`가 잡는다.
- **프록시의 id는 필드 직접 접근이 아니라 getter로 읽어야 한다** — `o.id`로 접근하면 프록시의 필드는 비어 있어 `null`이 나온다. `o.getId()`여야 값이 나온다. `equals` 구현에서 실제로 자주 터지는 함정.
- **가장 확실한 처방은 엔티티를 `Set`·`Map` 키로 쓰지 않는 것.** 연관관계 컬렉션도 특별한 이유가 없으면 `List`로 매핑한다.
- **실무 최대 함정은 Lombok** — 엔티티에 `@Data`/`@EqualsAndHashCode`를 붙이면 **모든 필드 기반**으로 생성되어 이 사고를 그대로 만들고, `equals` 호출이 **지연 로딩 연관을 전부 초기화**해 쿼리 폭탄이 된다. 엔티티에는 붙이지 않는다.

**메모**: **개념 전이가 이번엔 작동했다** — 2-4에서 Q9(프록시)의 지식을 다른 맥락으로 즉시 옮겨 붙였다. 고난이도 Q2에서 "1차 캐시 적재 비용"을 배치 상황에 못 옮겼던 것과 대비되는데, 차이는 **면접관이 연결 단서를 준 것**이다("Q9와 같은 눈으로"). 즉 연결 능력은 있고 **트리거를 스스로 찾는 것**이 약하다.
2-2의 오답은 **틀렸다기보다 대상을 착각한 것**이다 — 불변 + 새 객체 생성은 **값 객체(VO)에는 정확한 처방**이다. 엔티티와 VO의 성질 차이(식별자 고정 vs 값 전체가 정체성)를 명시적으로 구분해본 적이 없다는 신호이며, 이는 DDD 기초 개념이라 4장 이후 도메인 설계 문항에서 재확인할 가치가 있다.
1장 `equals`/`hashCode` 규약 문항과 연결해 복습할 것 — rationale이 말한 "1장의 equals 규약이 JPA라는 구체 환경에서 어떻게 꼬이는지"가 정확히 이 문항이다.

### [+α Q3] Soft delete와 유니크 제약·연관관계 조회 — **중**

**본질문**: `member(email UNIQUE, deleted)` 구조에서 "탈퇴했다가 재가입하려는데 이미 사용 중인 이메일이라고 나온다"는 CS. 왜 그렇고 어떻게 해결하나?
**답변 요지**: "**탈퇴 시 email에 의미 없는 상수를 붙인다.**" (이메일 변형 — 실무에서 쓰이는 기법)

**꼬리질문 3-1**: 같은 사람이 가입-탈퇴를 두 번 반복하면 `hong@a.com_deleted`가 두 개가 된다. 무슨 일이 벌어지고 어떻게 바꾸나?
- 답변: "**임의의 랜덤값을 삽입하도록 해야 한다.**" (정확)

**꼬리질문 3-2**: 그 방식은 **원본 이메일이 사라진다**(재가입 이력 연결 불가, 감사 요구). 이메일 값은 그대로 두고 **제약 쪽을 바꿔** 푸는 방법은?
- 답변: "**삭제 여부를 나타내는 컬럼과 복합 유니크로 지정하면 될 것 같다.**" (방향 정확)

**꼬리질문 3-3**: `deleted`가 boolean이면 `(email, false)` 하나와 `(email, true)` 하나까지는 공존한다. **두 번째 탈퇴**에서는?
- 답변: "**다시 충돌한다.**" (즉답)

**꼬리질문 3-4**: 그럼 `deleted`를 무엇으로 바꾸면 사라지나?
- 답변: "**삭제 여부 컬럼을 삭제 일시로 변경한다**" + "**int로 바꾸고 하나씩 더하는 방식?**" (둘 다 실무에서 쓰이는 해법)
- **면접관 보충**: `deleted_at`을 쓰면 **활성 행은 `NULL`** 인데, MySQL은 유니크 제약에서 **`NULL`끼리 서로 다르다고 취급**하므로 `UNIQUE(email, deleted_at)`은 **활성 회원이 같은 이메일로 여러 명 존재하는 것을 막지 못한다**는 새 구멍이 생긴다.
- **후보자의 반격**: "**`UNIQUE(email, deleted_at)`는 마우스 두 번 클릭으로는 못 막는 것 아닌가? `deleted_at`이 초 단위라면 못 막을 것 같다.**" (**이번 문항의 백미** — 면접관이 제시한 해법의 **정밀도 허점을 스스로 지적**했고, 그 문제는 **본인이 앞서 낸 랜덤값·순번 정수가 이미 해결**한다. 받은 답을 검증 없이 수용하지 않는 태도)

**꼬리질문 3-5** (질문의 나머지 절반): `Post` 1:N `Comment`에서 댓글도 soft delete인데 `post.getComments()`에 **삭제된 댓글까지 딸려 온다.** 왜 그렇고 어떻게 처리하나?
- 답변: "**`getComments()`를 할 때는 soft delete를 보지 못한다. soft delete를 볼 수 있도록 제공하는 JPA 기능이 있으면 사용하고, 아니면 따로 조회 로직 만들어서 사용한다.**" (현상은 맞으나 **메커니즘 설명이 얕고 도구 이름을 모름**)

**면접관 보충**:
- **딸려오는 이유** — JPA는 컬렉션을 채울 때 **FK만 보고 자식 행을 전부 가져온다.** soft delete는 애플리케이션이 정한 규약일 뿐, DB에도 JPA에도 "이 행은 삭제된 것"이라는 개념이 없다.
- **도구** — Hibernate의 **`@SQLRestriction("deleted = false")`**(구버전 `@Where`)를 엔티티나 컬렉션 필드에 붙이면 그 대상을 조회하는 **모든 쿼리에 조건이 자동으로 붙는다.** 짝이 되는 **`@SQLDelete(sql = "update comment set deleted = true where id = ?")`** 로 `delete` 호출을 UPDATE로 바꾸면 세트가 완성된다.
- **그 대가는 "끌 수 없다"** — 조건이 전역으로 붙으므로 **삭제된 데이터를 봐야 하는 관리자 화면·통계에서 우회할 방법이 없다.** 네이티브 쿼리나 별도 조회 경로가 필요하다. 중급 Q5에서 다룬 `@JsonIgnore`의 전역성과 정확히 같은 성격의 함정.
- **유니크 해법은 DB에 따라 갈린다** — PostgreSQL은 **부분 유니크 인덱스** 하나로 끝난다(`CREATE UNIQUE INDEX ... ON member(email) WHERE deleted = false`). 활성 행에만 제약이 걸리므로 이메일 변형도 복합 유니크도 불필요. **MySQL에는 이 기능이 없어서** 앞서 논의한 우회로들이 필요한 것이다.
- **soft delete 자체의 대가** — 모든 조회에 조건이 붙으니 **복합 인덱스 선두에 `deleted`를 넣어야** 하고, 데이터는 계속 쌓이며, 집계에서 조건 하나 빠뜨리면 숫자가 틀린다. 규모가 커지면 **삭제된 행을 아카이브 테이블로 옮기는 쪽**이 낫다 — 유니크 제약·조회 조건·인덱스 문제가 한꺼번에 사라진다.

**메모**: **유도에 대한 반응 속도가 이 문항에서 가장 좋았다** — 3-1~3-4에서 밀 때마다 정확히 한 칸씩 전진했고 모든 답이 실무 해법이었다. 그리고 3-4 이후 **면접관 답변의 허점을 되받은 것**은 이 세션 전체에서 처음 나온 행동이다(그동안은 면접관의 반론을 방어하기만 했다). 지식이 자리 잡히면 검증으로 넘어간다는 신호.
공백은 일관되게 **도구 이름**이다 — `@SQLRestriction`/`@SQLDelete`, 부분 유니크 인덱스. 3장 전체를 관통하는 패턴("설계 감각은 있고 도구 이름이 없다")이 +α 구간에서도 그대로 반복됐다. **4장 이후에는 개념 학습보다 "이 상황에서 쓰는 표준 도구의 이름" 목록화가 학습 효율이 훨씬 높다.**

### [+α Q4] JPA Auditing의 동작과 벌크 연산에서의 누락 — **중**

**본질문**: `BaseEntity`에 `@EntityListeners(AuditingEntityListener.class)` + `@CreatedDate`/`@LastModifiedDate`/`@LastModifiedBy`를 적용해 잘 동작하는데, **휴면 전환 벌크 UPDATE로 바뀐 10만 건은 `updatedAt`이 예전 값 그대로**다. 왜이며 어떻게 처리하나?
**답변 요지**: "**정확히는 모르지만 추론하자면 `@EntityListeners`는 영속성 컨텍스트에 있는 엔티티만 해당되는 로직이다. 따라서 배치로 업데이트하면 영속성 컨텍스트를 타지 않기 때문에 업데이트가 안 되는 것이다.**" (**메커니즘 정확 — 3장에서 다섯 번째 "경험 없음 + 추론으로 정답"**) + "**JPA로 업데이트할 때 `batch.size` 옵션을 통해서 진행하면 된다.**" (**처방은 오답** — `hibernate.jdbc.batch_size`는 SQL 문장을 JDBC 레벨에서 묶어 보내는 옵션이지 값을 채우는 기능이 아니며, 이 벌크 UPDATE는 이미 한 문장이라 묶을 것도 없다)

**꼬리질문 4-1**: 벌크 UPDATE를 그대로 유지하면서 `updatedAt`을 제대로 남기려면?
- 답변: "**업데이트 문에 추가한다.**" (정확 — `set m.status = 'DORMANT', m.updatedAt = :now`)

**꼬리질문 4-2** (설계·규율): 개인정보 처리 이력을 **감사받아야 하는** 서비스라면, "JPA Auditing은 벌크·네이티브에서 조용히 빠진다"는 성질을 팀 차원에서 어떻게 관리하겠나?
- 답변: "**벌크 연산 시 auditing을 실제로 삽입하는지 테스트 코드로 막는다.**" (**이 세션에서 가장 의미 있는 답변.** 3장 내내 7회 지적한 "안전망을 코드로 고정" 축에서 **처음으로 유도 없이 나온 답**)

**면접관 보충**:
- **Auditing의 동작 경로** — `AuditingEntityListener`가 **`@PrePersist`/`@PreUpdate` 콜백**에서 값을 채운다. 즉 **영속성 컨텍스트의 생명주기 이벤트에 얹혀 있다.** 그 경로를 타지 않는 것(벌크 JPQL, 네이티브 쿼리, `JdbcTemplate`)은 전부 조용히 빠진다.
- **`@LastModifiedBy`도 같이 빠진다** — SET 절에 `m.updatedBy = 'BATCH_DORMANT'`처럼 주체를 명시해야 한다. 덧붙여 `AuditorAware`는 보통 SecurityContext에서 사용자를 꺼내는데 **배치 스레드에는 그것이 없어 `null`이 되는** 함정이 따라온다.
- **규정 감사가 걸린 데이터면 애플리케이션 레벨 auditing은 신뢰 경계가 약하다** — ① **Hibernate Envers**로 별도 리비전 테이블에 이력을 남기거나 ② **DB 트리거**로 내린다. 다만 **Envers도 벌크 연산에서는 똑같이 빠진다** — "자동으로 되는 것"의 동작 경로를 알아야 안 되는 경우를 예측할 수 있다는 것이 이 문항의 요지.
- **실무 규칙 두 갈래** — 감사 대상 엔티티에는 **벌크 연산 금지**(ArchUnit 룰 또는 리뷰 규칙), 또는 벌크가 불가피하면 **이력 테이블에 직접 남기는 경로를 함께** 만든다.

**메모**: 처방에서 **도구의 역할을 혼동**했다(고난이도 Q2에서 배운 `batch_size`를 엉뚱한 문제에 적용). 이는 3장 전체의 약점 "도구 이름이 없다"의 변종 — 이름을 새로 알게 되면 **적용 범위를 함께 고정하지 않아** 오적용이 생긴다. **도구를 익힐 때 "무엇을 해결하는가"와 "무엇은 해결하지 못하는가"를 세트로 외울 것.**
반면 4-2는 기록할 가치가 크다. **7회 지적한 축에서 처음으로 자발적 안전망 답변**이 나왔다. 같은 세션 안에서 지적이 반영되는 이 후보자의 학습 속도가 여기서도 확인된다.

## 3장 JPA/ORM 전체 총평 — 27문항 완료

**평가 분포**: 상 3(기본 연관관계 주인 / 중급 `findById` vs `getReferenceById` / 고난이도 동시성 4가지) · 중 22 · 하 2(기본 merge, +α cascade·orphanRemoval)

**구간별**: 기본⭐ 7문항(상 1·중 5·하 1) / 중급⭐⭐ 12문항(상 1·중 11) / 고난이도⭐⭐⭐ 4문항(상 1·중 3) / +α 4문항(중 3·하 1)

### 강점 — 가르쳐서 되는 것이 아니다
1. **추론으로 메커니즘에 도달한다.** "경험이 없다"고 선언한 문항에서 반복적으로 정답에 닿았다 — flush 순서(DELETE가 뒤로 밀림), 상속 매핑(JOINED 도출), IDENTITY가 배치를 무력화하는 이유, `JdbcTemplate`이 통하는 이유, Auditing 누락. **최소 다섯 번.**
2. **유도성 반론에 흔들리지 않는다.** `getReferenceById`(9-3), `readOnly`(11-2), 오버엔지니어링(12-2), 커넥션 풀(고1-2) — 네 번 모두 자기 논거로 방어했고 전제가 바뀌면 즉시 판단을 갈아탔다(9-4). **마지막 +α Q3에서는 면접관 답변의 허점을 되받았다**(`deleted_at` 정밀도) — 방어에서 검증으로 넘어간 신호.
3. **모르는 것을 모른다고 하고, 전제를 되묻는다.** `for update` 여부, `lag` 정의, 조회 패턴, merge의 종류 — 아는 척으로 시간을 끌지 않는다.
4. **자기 선택에 근거가 있다.** "안 해봤다"에서 멈추지 않고 "안 한 이유"를 댄다.

### 약점 — 전부 습관이지 지능이 아니다
1. **(최대) 도구 이름이 없다.** 3장 전체를 관통한 단일 패턴이다 — `@Modifying`, `@BatchSize`/`default_batch_fetch_size`, `where(null)`의 성질, `SEQUENCE`+`allocationSize`, `rewriteBatchedStatements`, `AbstractRoutingDataSource`/`LazyConnectionDataSourceProxy`, `@SQLRestriction`/`@SQLDelete`, 부분 유니크 인덱스, `hashCode` 상수 관례. **상황 판단은 되는데 손이 잡는 도구가 없다.** → 4장부터는 개념 학습보다 **"이 상황 → 이 도구" 목록화**가 효율이 훨씬 높다. 그리고 **도구마다 "해결하지 못하는 것"을 함께** 고정할 것(+α Q4의 `batch_size` 오적용).
2. **안전망을 코드로 고정하는 습관 — 7회 지적, 마지막에 자발적 답변 출현.** 중급 Q12의 TODO 주석이 최저점이었고, +α Q4에서 유도 없이 "테스트로 막는다"가 나왔다. **개선 진행 중으로 판정.**
3. **트레이드오프 양면 서술 — 3회 지적 후 고난이도 구간에서 교정 완료.** 동시성 4가지 비교(고1), 트랜잭션 분리의 대가(고3-3) 모두 자발적.
4. **열린 질문에서 초점 이탈 — 2회**(중급 Q11, 고난이도 Q3). 익숙한 축(N+1·결합도)으로 먼저 간다. → **구조 → 경계 → 성능** 순으로 훑는 습관.
5. **아는 개념을 새 상황으로 옮기는 트리거가 약하다.** 중급 Q11에서 "1차 캐시 적재가 비용"이라 답한 사람이 고난이도 Q2의 100만 건 배치에서 그 축을 못 떠올렸다. 반대로 단서를 주면(+α Q2의 "Q9와 같은 눈으로") 즉시 연결한다. **연결 능력은 있고 트리거를 스스로 찾는 것이 약하다.**

### 가장 중요한 관찰
**지적받은 약점이 같은 세션 안에서 교정된다**(약점 3은 완료, 약점 2는 진행 중). 이 학습 속도가 최대 자산이며, 남은 최대 약점(도구 이름)도 **목록만 제공하면 빠르게 메워질 성질**이다.

### 4장 진입 전 권고
- 약점 노트의 **도구 상자 항목을 한 번에 훑을 것**(쿼리 수 단정, p6spy, `@Commit`, Testcontainers, ArchUnit, `CountDownLatch` 동시성 테스트).
- **엔티티 vs 값 객체(VO)의 구분**(+α Q2의 오답)은 DDD 기초이므로 도메인 설계 문항에서 재확인 대상.
- 4장은 DB를 최후 방어선으로 삼는 감각이 유리하게 작용하는 장이다 — 3장에서 그 감각은 반복 확인됐다.

## 약점 노트 (재도전 대상)

- [ ] **(최우선·횡단)** **"이 상황 → 이 도구" 목록화** — 3장 전체를 관통한 **최대 약점**. 상황 판단은 되는데 손이 잡는 도구가 없다. 한 번에 외울 목록: `@Modifying`(+`clearAutomatically`/`flushAutomatically`) · `@BatchSize`/`default_batch_fetch_size` · QueryDSL `where(null)`은 무시된다 + `PageableExecutionUtils` · `SEQUENCE`+`allocationSize`(MySQL은 `TABLE`) · `order_inserts`/`order_updates` · **`rewriteBatchedStatements=true`**(로그로는 확인 불가) · `AbstractRoutingDataSource`+**`LazyConnectionDataSourceProxy`** · `@SQLRestriction`(구 `@Where`)+`@SQLDelete`, Hibernate 6.4 `@SoftDelete` · **부분 유니크 인덱스**(PostgreSQL 전용) · `hashCode` 상수 관례 + `Hibernate.getClass()` · `@TransactionalEventListener(AFTER_COMMIT)`+`REQUIRES_NEW` · Outbox · Envers. **각 도구마다 "해결하지 못하는 것"을 반드시 함께 고정할 것**(+α Q4에서 `batch_size`를 감사 필드 문제에 오적용).
- [ ] +α > JPA Auditing — 메커니즘(영속성 컨텍스트 생명주기 콜백 `@PrePersist`/`@PreUpdate`에 얹혀 있음)은 추론으로 맞혔으므로 **처방과 주변 사실만**: ① 벌크에서는 **SET 절에 `updatedAt`·`updatedBy`를 직접** 넣는다 ② `AuditorAware`는 **배치 스레드에 SecurityContext가 없어 `null`** 이 된다 ③ **Envers도 벌크에서는 똑같이 빠진다** ④ 규정 감사가 걸리면 DB 트리거 또는 이력 테이블 직접 기록 + **감사 대상 엔티티 벌크 금지 규칙**(ArchUnit).
- [ ] +α > Soft delete — 유니크 해법의 단계(이메일 변형+랜덤 → 복합 유니크+**순번/타임스탬프** → **부분 유니크 인덱스**(PostgreSQL) → 아카이브 테이블 분리)는 유도 시 전부 도출했으므로 **도구 이름과 DB별 차이만**: ① **`@SQLRestriction`+`@SQLDelete`** 세트와 그 대가(**전역이라 관리자 화면에서 끌 수 없다** — `@JsonIgnore` 전역성과 동형) ② MySQL은 `UNIQUE(email, deleted_at)`에서 **활성 행의 `NULL`끼리 서로 다르게 취급**되어 활성 중복을 못 막는다(sentinel 값·순번으로 회피) ③ soft delete의 상시 비용(복합 인덱스 선두에 `deleted`, 집계 오염, 데이터 누적).
- [ ] +α > 엔티티 `equals`/`hashCode` — 원인(해시값 변화)과 프록시 문제는 자력 정답. 채울 것: ① **엔티티 vs 값 객체(VO)** — "불변 + 새 객체 생성"은 **VO에는 정답, 엔티티에는 불가**(새 행이 됨 + 변경 감지가 필드 변경을 전제) ② **`hashCode` 상수 반환**이 정석(규약은 "항상 같은 값"만 요구) ③ `equals`는 `getClass()`가 아니라 **`instanceof`/`Hibernate.getClass()`**, id 비교는 **`id != null &&`**, 프록시의 id는 **필드가 아니라 getter로** ④ 근본 처방은 **엔티티를 `Set`·`Map` 키로 쓰지 않기**(컬렉션은 `List` 매핑) ⑤ **엔티티에 Lombok `@Data`/`@EqualsAndHashCode` 금지**(모든 필드 기반 + 지연 로딩 전부 초기화).
- [ ] **(최우선)** +α > `CascadeType.REMOVE` vs `orphanRemoval` — **미답**. 핵심 한 문장부터: **REMOVE는 "부모가 삭제될 때"만, `orphanRemoval`은 거기에 더해 "부모와의 연결이 끊긴 순간"에도 삭제**(`getAttachments().remove(a)` 한 줄이 DELETE). 사고 유형 2종: ① `clear()`·**컬렉션 재할당**이 전건 DELETE ② `CascadeType.ALL`에 REMOVE가 포함되어 **의도치 않게 켜지고**, 공유 참조 자식까지 지움. + 자식 수만큼 DELETE가 개별로 나가는 성능 문제와 벌크 DELETE로 내려갈 때의 컨텍스트 불일치(중급 Q4 연결). **판단 기준**: 자식이 부모 없이 존재 의미가 없는 종속 관계일 때만, `CascadeType.ALL`을 습관적으로 쓰지 않기.
- [ ] **(최우선·횡단)** **트레이드오프를 한 호흡에 양면으로 말하는 훈련** — 3장에서 **세 번 반복된 서술 습관**(Q7 "이유를 3층으로" / Q10 택한 전략의 비용 미언급 / Q11 이유 3층을 면접관이 세 번 밀어서 하나씩). **지식 공백이 아니라 답변 구조의 문제**라 교정 비용이 가장 낮고 효과가 가장 크다. 훈련 포맷: ① "왜 X인가" 질문에는 **기술적 사고 → 설계·결합도 → 보안·운영/비용** 3층으로 답한다 ② "A와 B 중 무엇을 고르나"에는 **"A를 고른다. 얻는 것은 …, 대신 포기하는 것은 …, 그 대가를 감당할 수 있는 이유는 …"** 를 한 문장 안에 넣는다 ③ 도구를 제시할 때는 **그 도구가 못 막는 것**까지 붙인다(Q11의 `@QueryProjection`은 개수·타입은 잡지만 동일 타입 순서 교체는 못 잡음). **관련 항목**: 아래 "상속 매핑 전략", "DTO 프로젝션", "엔티티 직접 노출".
- [ ] 중급 > 조회 전용 DTO 프로젝션 — 개별 사실은 거의 다 맞힘(스냅샷·1차 캐시 적재·필요 컬럼만·`Projections.constructor`·`@QueryProjection`). 채울 것: ① **Q5와 Q11의 근거 층 구분** — Q5(엔티티 직접 노출)=계층 경계·보안, Q11(DTO 프로젝션)=**조회 비용**. 결론이 비슷해도 근거가 다르다 ② **`readOnly=true`가 남기는 것 3가지**(1차 캐시 적재 / `select *` 불필요 컬럼·전송 / 지연 로딩 프록시) → `readOnly`는 대체가 아니라 병행 수단 ③ **`@QueryProjection`의 한계** = 개수·타입은 잡지만 **동일 타입 순서 교체는 못 잡음**. 순서를 원천 차단하는 건 **이름 기반 매핑**(`Projections.fields`/`bean`, Spring Data **인터페이스 프로젝션**) ④ **DTO 프로젝션이 포기하는 것**(1:N 조인 시 행 중복 → 루트 페이징 + `in` 절 2차 쿼리 + 그룹핑 / 변경 감지 불가 → 수정 목적엔 사용 불가 / DTO 클래스 증식) ⑤ **구현 4종과 선택 기준**(JPQL `new`, QueryDSL, 인터페이스 프로젝션, 네이티브+`@SqlResultSetMapping`) ⑥ 판단 기준 한 문장: **"변경이 목적이면 엔티티, 표시가 목적이면 DTO"**(12장 CQRS의 출발점).
- [ ] 중급 > 상속 매핑 전략 — 판단은 이미 정확(JOINED 도출, CHECK 제약, `UNION ALL`). 채울 것: ① **택한 쪽의 대가를 같은 호흡에 말하기** — JOINED = 상세마다 조인 1회 + **부모 타입 조회 시 자식 전체 `LEFT OUTER JOIN`** + INSERT가 테이블 2개로 분할. 자식 15종이면 outer join 15개 → **옵티마이저 오판 문제로 성질 변화** ② **선택 기준 두 축**(자식 고유 컬럼의 양 / 다형성 조회 빈도) ③ **`TABLE_PER_CLASS`의 두 번째 결격 사유 = `IDENTITY` 사용 불가**(자식별 auto_increment ID 충돌) ④ **`@DiscriminatorColumn`/`@DiscriminatorValue`** 명시 이유(클래스 리네임 내구성) ⑤ **테이블로 안 내리는 선택지**(`@MappedSuperclass`, 컴포지션+JSON 컬럼과 그 대가) ⑥ **전략 변경 = 데이터 마이그레이션**이라 초기 결정 기준은 "3년 뒤 자식 수와 목록 화면 요구". **횡단 교훈: 트레이드오프 질문에 한쪽 면만 말하고 멈추는 습관**(Q7과 동일 패턴) — "얻는 것 + 포기하는 것"을 한 문장에.
- [ ] 중급 > flush 시점과 쓰기 지연 SQL 실행 순서 — 추론·처방은 정확했으므로 **사실만 채우면 됨**: ① **flush 3시점**(커밋 직전 / **JPQL·Criteria·네이티브 실행 직전 auto-flush** / `em.flush()` 명시) + `FlushModeType.COMMIT`으로 끌 수 있으나 안 쓰는 이유 ② **`findById`는 flush를 유발하지 않는다** — auto-flush는 query space 판정 기반이고 `em.find()`는 그 경로를 안 탄다(1차 캐시 유무와 무관) ③ **`ActionQueue` 고정 순서**(`orphanRemoval → INSERT → UPDATE → 컬렉션 3종 → DELETE`, **DELETE가 항상 마지막**)와 **그 이유**(FK 위반 회피 + JDBC batch 효율) ④ **데드락 축** — 처리 순서가 트랜잭션마다 달라지면 락 순서 역전, 처방은 **PK 정렬 후 처리**(Hibernate가 안 지켜주므로 코드로 고정) ⑤ 최선의 처방은 `flush()`가 아니라 **DELETE+INSERT를 UPDATE로 바꾸는 것**.
- [ ] 중급 > 복합 유니크 제약 + 동시 INSERT — 판단(충돌 빈도로 락/예외 선택, DB를 최후 방어선으로 유지)은 이미 상급. 채울 것은 **사실 3개**: ① **JPA는 유니크를 검사하지 않는다**(1차 캐시=`@Id` 키 Map, `persist`는 쓰기 지연 적재만, 검증은 flush 시점의 DB) ② **`rollback-only` 마킹** — 제약 위반 후 예외를 catch해도 커밋 시 `UnexpectedRollbackException`, 후속 저장까지 롤백 → `REQUIRES_NEW` 분리 또는 트랜잭션 밖에서 catch ③ **원자적 upsert**(`ON DUPLICATE KEY IGNORE` / `ON CONFLICT DO NOTHING`)로 예외 자체를 없애는 선택지. + **락이 뚫리는 구체적 경로**(TTL 만료·네트워크 분단·노드 장애·배포 중 키 변경·**락을 안 거치는 배치/수동 SQL**)를 근거로 댈 수 있을 것.
- [ ] **(최우선·횡단)** **안전망을 코드로 고정하는 훈련** — 3장 전체에서 **여섯 번 막힌 축**(유령 UPDATE 진단 / N+1 자동 탐지 / `HHH000104` / OSIV 전환 검증 / 동시성 재현 테스트 / SQL 실행 순서 사전 발견). 이제 개별 문항의 약점이 아니라 **작업 방식 자체의 공백**으로 본다 — "문제를 만나면 잘 푼다. 그러나 문제가 오기 전에 잡는 장치를 만드는 습관은 없다." 공통 처방(**한 번에 익힐 도구 상자**): **쿼리 수 단정 테스트**(`SQLStatementCountValidator`, `Statistics.getPrepareStatementCount()`), **실제 SQL·바인딩값 관측**(`p6spy`/`datasource-proxy`), **경고 로그를 실패로 승격**, **ArchUnit 구조 룰**(EAGER 금지, 컨트롤러 엔티티 반환 금지), **프로파일을 바꾼 통합 테스트로 잠재 예외 표면화**, **`@DataJpaTest`의 롤백이 커밋 시점 문제를 숨긴다 → `@Commit`/`TestTransaction`**, **H2 대신 Testcontainers로 실제 DB**(유니크 제약·데드락은 벤더마다 다름), **`CountDownLatch` 동시성 재현 테스트**.
- [ ] **(최우선)** 중급 > 벌크 연산과 영속성 컨텍스트 — **`@Modifying`의 존재 자체를 모름**부터 채울 것("조회가 아니라 변경 쿼리"라는 표시, 없으면 예외, 있으면 `executeUpdate()`). + **벌크 연산은 영속성 컨텍스트를 우회해 즉시 DB로 나간다**(쓰기 지연 대상 아님, 오히려 실행 직전 flush 선행) → **DB와 1차 캐시의 불일치**가 이 문항의 전부. + **옵션 2종의 반대 방향**(`flushAutomatically`=실행 전 반영 / `clearAutomatically`=실행 후 폐기) + **`clearAutomatically`의 부작용**(컨텍스트 통째 비움 → 다른 엔티티 변경분 소실, 준영속화) + **진짜 처방은 배치**(벌크는 트랜잭션 끝 또는 별도 트랜잭션). **증상으로부터 원인을 떠올리는 훈련**이 핵심 — "DB는 바뀌었는데 조회는 옛날 값" / "벌크 결과가 조용히 사라짐"을 트리거로 기억할 것.
- [ ] 중급 > 엔티티 직접 노출 금지 — 개별 지식은 이미 있음(N+1·순환참조·결합도·`@JsonIgnore`의 전역성 모두 즉답). 비어 있는 것은 **보안 축 두 개**: ① **opt-out vs opt-in** — 엔티티 노출은 새 필드가 추가되면 응답 코드를 안 건드려도 자동 유출, DTO는 명시한 것만 나감 ② **요청 방향의 mass assignment**(`@RequestBody`로 엔티티를 받으면 `role`·`point`를 클라이언트가 덮어씀). + **`@JsonIgnore`의 진짜 문제는 동작이 아니라 엔티티가 응답 템플릿이 되는 것.** **훈련 포인트: "이유를 대라"에 3층으로 답하기**(기술적 사고 → 설계·결합도 → 보안·운영) — 이 문항은 하나만 대고 멈춘 것이 유일한 감점 사유였다.
- [ ] 중급 > QueryDSL 동적 쿼리 — **`where(null)`은 조용히 무시된다**는 성질 하나가 공백의 전부. 이를 알면 `BooleanExpression` 반환 메서드로 조건을 쪼개고 `where(nameEq(x), statusEq(y), …)`로 나열해 **`if`가 사라지고 조건을 합성·재사용**할 수 있다(`nameEq(x).and(statusIn(y))`) — `BooleanBuilder`에는 없는 성질. + **선택 기준**(단순 AND 나열 → 메서드 분리 / OR 중첩 → `BooleanBuilder`) + **count 쿼리 최적화**(`PageableExecutionUtils.getPage(...)`로 첫·마지막 페이지에서 count 생략, count 쿼리에서 join 제거) + **조건 없는 전체 검색을 애초에 막는 설계**(필수 조건 강제, 기본 기간 주입).
- [ ] 중급 > 낙관적 락 vs 비관적 락 — **`@Version`의 실제 동작을 사실로 고정**: 별도 SELECT 없이 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?` 한 문장, **영향 행 수 0 = 충돌**, `OptimisticLockException`. **"낙관적 락은 락이 아니다(사후 감지)"** 를 한 문장으로. + **재시도는 새 트랜잭션·새 영속성 컨텍스트에서**(1차 캐시에 옛 버전이 남으면 영원히 실패) + **비관적 락의 숨은 대가는 커넥션 점유** + **임계 구간 길이라는 축**(원자적 UPDATE로 ms → μs). 판단력은 이미 상급이므로 **메커니즘 사실만 채우면 상**.
- [ ] **(최우선)** 중급 > OSIV — **OSIV의 정의 자체를 재차 인출 실패**(기본⭐ Q7 보충에서 이미 학습한 항목) → `spring.jpa.open-in-view=true`가 기본이고 트랜잭션 종료 후에도 `EntityManager`를 응답까지 연다는 한 문장을 확실히 고정. + **"놀고 있는 커넥션을 점유한다"는 문제의 정확한 표현**(컨트롤러 단 외부 API 호출이 있을 때 치명적) + **껐을 때는 불편이 아니라 설계 강제**(엔티티가 트랜잭션 밖으로 못 나감) + **안전한 전환 순서**(DTO 경계 수립 → 트랜잭션 내 변환 → 마지막에 끄기) + **보장 수단**(`open-in-view=false` 프로파일 통합 테스트, ArchUnit 룰). 정적 검색이 직렬화·`toString`·프록시를 못 잡는다는 것도 함께.
- [ ] **(최우선)** 중급 > fetch join + 페이징 — **`HHH000104` 경고와 메모리 페이징 동작**(limit을 붙이지 않고 전량 로딩 후 애플리케이션에서 절단 → 데이터 증가 시 OOM, 사전 신호는 이 경고 한 줄뿐) + **`default_batch_fetch_size` / `@BatchSize`**(컬렉션은 LAZY로 두고 `in (…)` 묶음 조회, `1+N` → `1+ceil(N/size)`) + **문제 범위의 정확한 한정**(컬렉션 fetch join일 때만. ToOne은 안전) + **해법 3종의 선택 기준**(ToOne은 fetch join / 컬렉션은 batch fetch / 조회 전용은 DTO). 설계는 이미 도출 가능하므로 **도구 이름과 관측 신호만 메우면 상**.
- [ ] **(최우선)** 기본 > merge vs dirty checking — **`save()`의 persist/merge 분기**(id 유무로 갈림, 중복 에러가 아니라 조용한 UPDATE) + **merge 5단계**(SELECT → 전 필드 복사 → 새 영속 인스턴스 반환 → flush 시 dirty checking) + **차이의 한 문장**("계산" vs "전부 덮기") + **반환값 무시 버그** + **merge가 PATCH를 구현할 수 없는 이유**(안 보낸 필드 vs null로 지우라는 필드 구분 불가) + 정당한 용도는 재부착뿐.
- [ ] **(최우선)** 기본 > N+1 — **자동 탐지 장치**(테스트에서 `Statistics.getPrepareStatementCount()` 단정, `SQLStatementCountValidator.assertSelectCount`, 요청 단위 쿼리 카운터 + 임계치 경고, ArchUnit EAGER 금지 룰) + **N의 정체는 결과 행 수가 아니라 미해결 연관 id 수**(픽스처는 건수 아니라 카디널리티) + **해결책 선택 기준**(컬렉션+페이징 → batch fetch size, to-one 여럿 → fetch join, 조회 전용 → DTO). "N+1은 회귀이므로 테스트로 고정한다"는 프레임 체득.
- [ ] 기본 > EAGER vs LAZY — **연관관계별 기본값 암기**(`@ManyToOne`·`@OneToOne`=EAGER / to-many=LAZY, 가르는 축은 단일 값 vs 컬렉션) + **JPQL에서 EAGER가 N+1이 되는 메커니즘**(JPQL은 그대로 번역, 글로벌 fetch 전략은 번역에 개입하지 않음 → 행마다 추가 쿼리. `find()`는 조인이라 단건 테스트에서 안 보이는 비대칭) + **EAGER 금지의 진짜 근거**(쿼리 단위로 끌 수 없다 = 되돌릴 수 없는 기본값). `@OneToOne(mappedBy)`의 LAZY 미작동도 함께.
- [ ] 기본 > 영속성 컨텍스트 — **flush의 실제 비용**(스냅샷 메모리 2배 + `O(엔티티×필드)` 비교, readOnly/DTO 프로젝션으로 회피)과 **"안 시킨 UPDATE" 진단 경로**(BigDecimal scale, 컬렉션 재할당, 컨버터 왕복 비대칭, 시간 정밀도, OSIV+setter → 진단은 바인딩 SQL 로그·Statistics·flush 리스너 스택트레이스). flush 순서 고정(INSERT→UPDATE→DELETE)과 전 컬럼 UPDATE도 함께.
- [ ] 기본 > JPA vs MyBatis — **결합도의 실체 3층**(방언/벤더 종속, SQL 부재로 스키마 변경 파급 축소, 도메인 로직을 엔티티에 둘 수 있음) + **JPA의 대가**(쿼리 비가시성→N+1·불필요 UPDATE, 쿼리 로그 습관) + **병용 구도**(쓰기 ORM / 읽기 SQL)를 스스로 꺼내기. 트레이드오프 양면 서술 훈련.
