# 3. JPA / ORM — 문답 기록

## 기본 ⭐

### [Q1] JPA를 사용하는 이유 / MyBatis와의 차이 — **중**

**본질문 답변 요지**: "DB와 연결되는 데이터를 보다 객체스럽게 사용하기 위함. MyBatis는 SQL을 쓰기 때문에 DB에 저장되는 클래스가 DB와의 연결강도가 높아지지만, JPA는 그 연결강도를 줄일 수 있다." (방향은 맞으나 '객체스럽게'·'결합도'가 모두 미정의 상태)

**꼬리질문 1-1**: 운영 테이블에 컬럼 1개 추가 + 조회 조건 1개 추가 시, MyBatis/JPA 각각 손으로 고칠 지점은? 그게 결합도 차이의 실체인가?
- 답변: MyBatis는 맵핑 파일 수정 + 연결 클래스 수정. JPA는 객체에 필드 추가만. 조회 조건은 MyBatis는 쿼리 수정, JPA는 인터페이스 메서드 명만 수정. (수정 지점 비교는 정확하나 '편의성' 층에 머묾)

**꼬리질문 1-2**: 선택적 조건 6개(이름·이메일·가입일 범위·상태·조직·마지막 로그인) 조합 검색 화면 — 메서드 이름 방식으로 되나? 실제로 어떻게 처리했나?
- 답변: 만들 수 없다. JPQL 또는 QueryDSL을 사용해서 처리했다. (한계선 즉시 인정 — 좋음)

**꼬리질문 1-3 (반론)**: QueryDSL/JPQL을 쓰는 순간 조회 쿼리를 직접 설계하는 셈인데, 그러면 "결합도 감소" 이점은 유지되나? QueryDSL 조회 코드와 MyBatis 조회 코드의 차이는?
- 답변: QueryDSL은 컴파일 시점 타입 체크와 엔티티 기반이라 차이가 있다. MyBatis는 순수 쿼리다. (여기서 멈춤 — QueryDSL vs MyBatis 차이일 뿐, JPA vs MyBatis의 결합도 층으로 올리지 못함)

**꼬리질문 1-4**: 반대로 MyBatis를 골라야 한다고 판단하는 상황은? 실제 프로젝트는 무엇을 썼고 누가 어떤 근거로 정했나?
- 답변: 간단한 CRUD가 별로 없고 복잡한 서브쿼리가 존재하며 쿼리 최적화가 자주 필요한 경우 MyBatis가 유리하다. 실제 프로젝트는 JPA를 사용했고, 근거는 빠른 개발과 간단한 CRUD가 많은 유형의 서비스여서. (선택 기준 축은 정확. 단, 결정 주체는 답 없음 — 스택 논의 참여 경험은 아닌 것으로 판단)

**면접관 보충**:
- **결합도의 실체 3층** — ① 방언/벤더 종속(JPA는 Dialect가 SQL 생성 vs MyBatis는 SQL 문법이 코드에 박제) ② SQL 자체가 애플리케이션에 없어 스키마 변경이 XML 전수 검사로 번지지 않음 ③ **도메인 로직을 엔티티 안에 둘 수 있음** — MyBatis의 VO는 결과셋 그릇이라 로직이 서비스로 새어나감. 여기가 "객체스럽게"의 진짜 값.
- **JPA의 대가** — 쿼리가 코드에 안 보여 의도치 않은 쿼리(N+1, 불필요 UPDATE)가 조용히 나감 → 쿼리 로그 상시 확인 습관이 필수. MyBatis의 최대 장점은 쿼리가 눈에 보이는 것.
- **실무의 현실적 답은 병용** — 쓰기는 ORM(변경 감지·객체 그래프), 통계·리포트·대량 조회는 MyBatis/native. "쓰기는 ORM, 읽기는 SQL"이 대용량 서비스의 흔한 구도.

**메모**: 개념 방향은 맞고 도구 한계선 인정도 빠르지만, 답변 전체가 **"JPA는 편하다" 단면 서사**. 트레이드오프의 아픈 쪽(JPA의 대가)을 한 번도 자발 언급하지 않은 것이 이 평가의 핵심 사유 — 1·2장에서 반복된 "트레이드오프 근거 서술 약함" 패턴의 연장. 반론을 받았을 때 논점을 한 층 올리는 힘(타입 체크 → 벤더 종속·도메인 모델)이 아직 부족.

### [Q2] 영속성 컨텍스트 / 1차 캐시 / 쓰기 지연 / 변경 감지 — **중**

**본질문 답변 요지**: "하나의 트랜잭션에 속한 엔티티 데이터를 메모리에 보관하는 것. 1차 캐시는 조회 시 메모리에서 꺼내 쓰는 것. 쓰기 지연은 트랜잭션 끝나기 직전에 한 번에 쓰기 쿼리를 날리는 것. 변경 감지는 스냅샷을 갖고 있다가 트랜잭션 끝나기 전 비교해서 UPDATE를 만드는 것." (네 개념 모두 방향 정확. 다만 "변경된 데이터를 분리해서 갖고 있다"는 표현은 모델이 흐릿함 — 실제로는 엔티티 인스턴스 자체가 변경되고 스냅샷은 로드 시점 복사본)

**꼬리질문 2-1**: 조회 전용 화면에서 엔티티 1,000건을 읽고 아무것도 수정하지 않았다. 커밋 시점에 애플리케이션이 하는 일이 있나? 비용은 어디서 발생하나?
- 답변: "1,000건이 영속성 컨텍스트에 올라가고, 커밋 시점에 정리한다. 비용은 메모리와 GC이지 않을까." (스냅샷 메모리는 짚었으나 **flush 시 전건 비교라는 CPU 비용에 미도달**)

**꼬리질문 2-2 (힌트 제공)**: 스냅샷은 언제 만들어지나? 1,000건이면 비교가 몇 번 일어나나? 수정하지 않은 엔티티도 비교 대상인가?
- (후보자 역질문: "readOnly 옵션인가 default인가?" → 기본 설정으로 답함. 조건을 스스로 확인하려 한 점은 좋음)
- 답변: "조회 시점에 스냅샷 생성, 커밋 시점에 스냅샷과 현재 데이터를 비교. 1,000건 비교가 일어난다. 수정하지 않은 엔티티도 대상이다. **수정 여부는 비교하고 나서야 알기 때문.** readOnly=true면 스냅샷을 생성하지 않는다." (정확 + readOnly의 효과를 자발 언급 — 이 스레드의 최고점)

**꼬리질문 2-3**: 조회성 API인데 `updated_at`이 갱신되고 감사 로그에 UPDATE가 남는다는 운영 문의. 원인을 어디부터 좁히나? 유사 경험은?
- 답변: "조회성 API에 엔티티 필드를 업데이트하는 메서드를 쓰는지 확인한다." (첫 단계로는 타당하나 그 이상 확장 없음. **경험 질문에는 응답 없음 → 실제 진단 경험 부재로 판단**)

**꼬리질문 2-4**: 수정 메서드가 전수 조사에서 정말 없었는데도 매 조회마다 UPDATE가 나간다. 무엇이 남았나?
- 답변: "변경 감지 비교에 equals/hashCode를 쓴다면 그 문제 아닐까." (추측. 기본 필드 dirty checking은 엔티티 equals/hashCode를 쓰지 않고 Hibernate 타입별 비교기를 씀)

**꼬리질문 2-5 (힌트 제공)**: 자바 필드 타입과 DB 컬럼 타입이 1:1로 안 맞는 경우 — `char(1)`↔String, `NUMBER`↔BigDecimal, 컬렉션 필드. 하나 골라 왜 "변경됨"으로 판정되는지 설명해보라.
- 답변: "잘 모르겠다."

**면접관 보충**:
- **영속성 컨텍스트의 정체는 4가지 저장소** — ① 1차 캐시(`@Id` → 엔티티 인스턴스 맵) ② 스냅샷 저장소(로드 시점 필드값 복사본) ③ 쓰기 지연 SQL 저장소 ④ 그 결과로 얻는 **동일성 보장**(같은 트랜잭션에서 같은 id 조회 시 `==`가 참). 1차 캐시는 성능 캐시가 아니라 **동일성·정합성 장치**다 — 범위가 트랜잭션이라 히트율에 기대는 설계는 잘못.
- **flush의 실제 비용** — 스냅샷 때문에 엔티티 메모리가 사실상 2배, 그리고 flush마다 `O(관리 엔티티 수 × 필드 수)` 비교. 조회 전용은 `@Transactional(readOnly=true)`(Hibernate 세션 read-only → 스냅샷 생략 + FlushMode.MANUAL) 또는 **DTO 프로젝션**(애초에 영속성 컨텍스트에 안 올림).
- **flush 실행 순서는 코드 순서가 아니다** — INSERT → UPDATE → DELETE 고정. "DELETE 먼저 하고 INSERT 했는데 유니크 제약 위반"이 여기서 나온다(중급 문항에서 다시 다룸).
- **기본 UPDATE는 전 컬럼 UPDATE** — 변경된 컬럼만 나가지 않는다. `@DynamicUpdate`로 바꿀 수 있으나 매번 SQL을 새로 만들어 구문 캐시 이점을 잃는 트레이드오프.
- **"안 시킨 UPDATE"의 실제 단골 원인** — ① **BigDecimal scale 불일치**(`1.10` vs `1.1`은 `equals` 기준 다름) ② **컬렉션 재할당**(`setItems(new ArrayList<>(...))` → 관리 컬렉션 교체로 보고 전체 DELETE+INSERT) ③ **AttributeConverter의 왕복 비대칭**(Y/N↔Boolean에서 null↔false) ④ **시간 타입 정밀도**(DB는 초, 자바는 나노초) ⑤ **OSIV 켜짐 상태에서 컨트롤러/DTO 변환 중 setter 호출** → 다음 트랜잭션 진입 시 유령 UPDATE. `updated_at`은 dirty일 때만 갱신되므로 **원인이 아니라 결과**다.
- **진단 도구** — `org.hibernate.SQL` + 바인딩 파라미터 로깅(p6spy/datasource-proxy), `SessionFactory` Statistics의 `entityUpdateCount`, 그리고 결정적 한 방: **flush 이벤트 리스너에서 스택트레이스를 찍어 어느 코드가 dirty를 만들었는지 역추적**.

**메모**: 개념 4종의 설명은 정확하고, `readOnly=true`의 스냅샷 생략을 스스로 꺼낸 것은 기본⭐ 기준 상급. 그러나 rationale의 핵심 검증 지점 — "이상 동작이 났을 때 속수무책인가" — 에서 막혔다. flush 비용을 힌트 없이 못 짚었고, 유령 UPDATE 진단은 첫 단계 이후 확장이 없었으며 **경험 질문에 응답 자체가 없었다**(Q1의 "실제 결정 주체 답 없음"과 같은 패턴 — 운영 중 이상 동작을 직접 추적해본 이력이 얇은 것으로 보임). 개념 층은 상, 진단·경험 층은 하 → 종합 **중**.

### [Q3] 즉시 로딩(EAGER) vs 지연 로딩(LAZY), 기본 전략 — **중**

**본질문 답변 요지**: "즉시 로딩은 연관 엔티티를 조회 시 함께 불러오는 것, 지연 로딩은 사용할 때 불러오는 것. 프로젝트 기본 전략은 지연 로딩. 이유는 연관 엔티티를 바로 사용하는 곳보다 사용하지 않는 곳이 더 많아서." (정의·선택 정확. 근거는 "낭비 회피" 한 축에 머묾 — EAGER의 구조적 위험 미언급)

**꼬리질문 3-1**: 지연 로딩을 기본으로 관철하려면 코드에서 실제로 무엇을 해야 하나? JPA 명세의 연관관계별 기본값은? 그 기본값이 왜 그렇게 정해졌다고 보나?
- 답변: "연관관계 매핑 시 LAZY 옵션을 명시해야 한다. 1대1은 즉시 로딩, **다대1이나 1대다는 지연 로딩이 기본값.** 이유는 1대1은 즉시 로딩 가능성이 높고 다대1·1대다는 낮아서가 아닐까." (`@OneToOne` EAGER ✓, `@OneToMany` LAZY ✓, **`@ManyToOne`을 LAZY로 오답** — 실무에서 가장 많이 쓰는 연관의 기본값을 틀림)

**꼬리질문 3-2 (반론)**: `@ManyToOne`이 지연 로딩 기본값이라고 확신하나? 명세가 기본값을 가르는 축은 "즉시 로딩 가능성"이 아니라 단일 값 연관(to-one) vs 컬렉션 연관(to-many)이다. 다시 생각해보라.
- 답변: "다대1은 내가 '다'고 연관된 데이터가 '1'이라 하나밖에 없어 즉시 로딩이 기본값이다." (**자기 교정 성공.** 힌트를 받고 명세의 논리를 스스로 재구성 — 이 스레드의 가점 요소)

**꼬리질문 3-3 (반론)**: "EAGER면 조인 한 번에 다 가져오니 효율적 아닌가?" `em.find()`는 실제로 조인이 나간다. 그런데 같은 엔티티를 JPQL(`select o from Order o`)로 조회하면 EAGER `@ManyToOne`이 조인으로 나가나?
- 답변: "이때는 join으로 나가지 않는다." (**즉답 정확** — 쿼리 로그를 실제로 본 사람의 답으로 판단)

**꼬리질문 3-4**: 그럼 무슨 쿼리가 나가나? 왜 조인으로 안 나가나?
- 답변: "작성한 쿼리대로 나간다. 이유는 정확히는 모르겠지만 JPA 설정 상 JPQL로 join을 명시하지 않는 이상 조인으로 안 나간다." (관찰은 정확하나 **메커니즘 미도달**. "설정"이 아니라 JPQL 번역 원리라는 점을 놓침)

**꼬리질문 3-5**: JPQL이 그대로 SQL로 나갔는데 EAGER 연관은 즉시 로딩이어야 한다. 그 연관 엔티티는 어떻게 채워지나? 결과가 100건이면 총 쿼리 수는?
- 답변: "설마 n+1로 나가나?" (유도 끝에 도달. 자발적 연결은 아니었음)

**면접관 보충**:
- **LAZY의 실체는 프록시** — Hibernate가 바이트코드로 만든 하위 클래스 인스턴스를 필드에 넣어두고 실제 접근 순간 초기화 쿼리를 날린다. 트랜잭션 밖 접근 → `LazyInitializationException`.
- **기본값 정리** — `@ManyToOne`·`@OneToOne` = **EAGER**, `@OneToMany`·`@ManyToMany` = LAZY. 가르는 축은 단일 값 연관 vs 컬렉션 연관(크기 예측 불가). 결론: **to-one은 전부 손으로 `fetch = LAZY`를 명시해야 한다.**
- **JPQL에서 EAGER가 N+1이 되는 메커니즘** — JPQL은 작성한 대로 SQL로 번역되고 **글로벌 fetch 전략은 이 번역에 개입하지 않는다.** 번역된 SQL 실행 후 Hibernate가 EAGER 계약을 지키려고 조회된 행마다 연관을 추가 쿼리로 채운다 → 1 + N. 위험한 건 **`find()`는 조인이 나가므로 단건 테스트에서 안 보이고 목록 API에서만 터진다**는 비대칭성.
- **EAGER 금지의 나머지 두 근거** — ① **연쇄 전파**: Order→Member→Team이 전부 EAGER면 조인 depth가 누적돼 엔티티 하나 조회에 테이블 10개가 붙는다 ② **결정적으로, 쿼리 단위로 끌 수 없다.** LAZY를 fetch join으로 켜는 건 쉬운데 EAGER를 특정 쿼리에서만 끄는 건 불가능하다. **기본값은 되돌릴 수 있는 방향으로 둔다** — 후보자의 "안 쓰는 곳이 더 많아서"보다 한 층 위의 근거.
- **정답 조합** — LAZY 전역 기본 + 필요한 지점에서 명시적 fetch(fetch join / `@EntityGraph` / `@BatchSize` / DTO 프로젝션). LAZY의 대가(LazyInitializationException, N+1)를 아는 상태에서의 선택이어야 한다.
- **함정** — `@OneToOne`의 주인이 아닌 쪽(`mappedBy`)은 LAZY를 걸어도 걸리지 않는다. FK가 상대 테이블에 있어 연관이 null인지 알 수 없으므로 프록시를 만들 수 없고 즉시 쿼리가 나간다.

**메모**: Q1·Q2에서 반복된 "트레이드오프 한쪽만 서술" 패턴이 여기서도 나왔다 — LAZY를 고른 근거가 "낭비 회피"뿐이고, EAGER의 구조적 위험(쿼리 단위 제어 불가, JPQL 비대칭)은 유도해야 나왔다. 다만 **이 스레드에서 처음으로 자기 교정이 나왔다**(꼬리 3-2) — 반론을 받고 논점을 스스로 다시 세운 첫 사례로, Q1에서 지적했던 "반론 시 논점을 한 층 올리는 힘 부족"이 개선될 여지를 보였다. "JPQL에서는 조인이 안 나간다"를 즉답한 것도 실제 쿼리 로그 관찰 경험의 근거로 본다 — Q2의 진단 경험 부재 평가를 일부 상향할 재료.

### [Q4] N+1 문제란? 해결책은? — **중**

**본질문 답변 요지**: "한 번의 쿼리에 연관된 데이터의 추가 쿼리가 발생하는 것. 엔티티를 List로 조회했는데 각 엔티티의 연관 데이터를 조회하느라 List 개수만큼 쿼리가 나가는 것. 해결은 join으로 한 번에 가져오거나, 추가 쿼리에서 모든 데이터를 가져와 애플리케이션에서 조합한다." (정의 정확. 두 번째 해결책은 batch fetch / 별도 조회 후 조합을 이름 없이 원리로 설명 — 좋음)

**꼬리질문 4-1**: N+1은 코드만 봐서는 안 보이고 개발 데이터로는 멀쩡하다. 운영에 나가기 전에 어떻게 발견하나? 실제 프로젝트에서 둔 장치는?
- 답변: "테스트용 데이터를 1,000개 이상 넣어 성능 테스트를 하고, 쿼리 로그로 확인할 수 있다." (**둘 다 사람이 눈으로 보는 방식.** "실제 프로젝트에서 둔 장치"에는 답 없음)

**꼬리질문 4-2**: 팀 10명·주당 PR 50개. 신입이 컬렉션을 루프에서 만지는 코드를 올렸고 리뷰어는 놓쳤다. 사람의 주의력에 의존하지 않고 자동으로 막는 장치를 만들 수 있나?
- 답변: "잘 모르겠다."

**면접관 보충**:
- **N의 정체** — 추가 SELECT는 "결과 행 수"만큼이 아니라 **1차 캐시에 없는 서로 다른 연관 id 수**만큼 나간다. 그래서 **건수만 늘린 테스트 데이터로는 재현되지 않는다**(회원 1~2명이면 100건 조회해도 1+1). 픽스처는 건수가 아니라 **카디널리티**로 설계해야 한다 — 후보자의 "1,000건 넣고 성능 테스트"가 실패하는 이유.
- **해결책 4종과 선택 기준** — ① **fetch join**: 조인 한 방. 컬렉션 fetch join + 페이징 불가(메모리 페이징), 컬렉션 둘 이상 fetch join 불가(카테시안 곱) ② **`@EntityGraph`**: 선언적 fetch join, 한계 동일 ③ **`hibernate.default_batch_fetch_size` / `@BatchSize`**: N개 개별 쿼리를 `IN (...)`으로 묶어 `1 + ceil(N/size)`. **페이징과 공존 가능**해서 전역 100~1000이 실무 정석 안전망 ④ **DTO 프로젝션 / 두 번 조회 후 조합**: 조회 전용 화면의 정답. → 기준: **컬렉션+페이징이면 fetch join 금지 → batch fetch size**, to-one 여럿이면 fetch join, 조회 전용이면 DTO.
- **자동 탐지 장치(이 질문의 핵심 관문)** — ① **테스트에서 쿼리 수 단정**: `Statistics.getPrepareStatementCount()`를 전후로 재서 `assertEquals`. N+1이 생기면 테스트가 깨진다 ② 사실상 표준 라이브러리 `com.vladmihalcea:db-util`의 `SQLStatementCountValidator.assertSelectCount(n)` ③ 개발/스테이징 프로파일에 **요청 단위 쿼리 카운터** + 임계치 초과 시 WARN + 스택트레이스 ④ ArchUnit으로 `FetchType.EAGER` 금지 룰 고정 ⑤ APM·슬로우 쿼리 로그는 **사후 발견**이라 예방 장치가 아님.
- **사고의 전환** — N+1은 성능 문제가 아니라 **회귀(regression)**다. 한 번 고쳐도 다음 PR에서 재발하므로 사람이 아니라 **테스트로 고정**해야 한다.

**메모**: 정의와 해결책은 기본⭐ 기준 충분하고, 특히 "추가 쿼리에서 모든 데이터를 가져와 조합"을 용어 없이 원리로 설명한 것은 실제로 써본 흔적이다. 그러나 rationale이 이 문항으로 재려던 것 — **"운영 전에 어떻게 발견하는가"** — 에서 정확히 막혔다. "성능 테스트 + 로그 확인"은 사람 의존이고, 자동 가드에는 "잘 모르겠다". Q2의 "진단 도구·경험 부재"와 **동일한 공백의 재확인**: 이 후보자는 개념과 해결책은 알지만 **품질을 시스템으로 고정해본 경험이 없다**. 3장 전체에서 가장 일관된 약점이므로 다음 세션 재도전 최우선 대상.

### [Q5] `merge`와 dirty checking의 차이 — **하**

(후보자 역질문: "정확히 어떤 merge인가?" → `EntityManager.merge()`, 즉 Spring Data `save()`에 준영속 엔티티를 넘겼을 때 호출되는 그것으로 특정해줌)

**본질문 답변 요지**: "**정확히는 모르지만** merge는 새롭게 데이터를 생성해서 스냅샷과 기존 데이터를 대조하는 과정이 없다." (개념 미정립을 스스로 인정. "새 인스턴스를 만든다"는 관찰은 정확 — merge의 반환값이 새 영속 인스턴스이고 넘긴 객체는 준영속으로 남는다는 핵심을 부분적으로 짚음. 다만 "스냅샷 대조가 없다"는 틀림 — merge도 SELECT로 영속화한 뒤 결국 dirty checking을 탄다)

**꼬리질문 5-1**: 회원 엔티티 필드 10개, 수정 화면은 이름·전화번호 2개만 전송. `new Member()`에 id+이름+전화번호만 채우고 `save()` 호출. DB에 무슨 일이 벌어지나?
- (후보자 역질문: "수정 요청인가?" → 그렇다, 해당 id의 회원이 DB에 존재하고 나머지 8필드에 정상 값이 있다고 명시)
- 답변: "**id가 있는데 같은 id로 다시 저장 요청하면 당연히 에러가 난다. id 중복 에러 발생.**" (**정반대 오답.** Spring Data `save()`가 id 유무로 `persist`/`merge`를 가른다는 것을 모름 — 매일 쓰는 API의 분기)

**꼬리질문 5-2 (교정 후)**: 에러가 나지 않는다. merge 경로이므로 SELECT 후 UPDATE가 나간다. 그 UPDATE의 SET 절에는 어떤 컬럼과 값이 들어가나?
- 답변: "전체 컬럼이 들어가고, 내가 넣은 값이 있으면 해당 값으로, 안 넣은 값은 null로 저장한다." (**정확.** 경로를 알려준 직후에는 귀결을 스스로 도출)

**꼬리질문 5-3**: 이 코드를 어떻게 고치겠나? 실무에서 merge를 써야 하는 경우가 있나?
- 답변: "member를 우선 조회하고 setter로 수정 후 dirty checking을 쓸 것이다. merge를 써야 하는 경우는 기존 값을 모두 바꿔야 할 때다." (**수정 방법은 정확.** merge의 용도는 절반 — 재부착 시나리오를 못 짚음)

**면접관 보충**:
- **merge의 동작 5단계** — ① id로 1차 캐시 조회 → 없으면 **DB SELECT** ② DB에도 없으면 새 엔티티 생성 → INSERT 경로 ③ 조회된 영속 엔티티에 **넘어온 객체의 모든 필드를 복사** ④ **그 영속 엔티티를 반환**(넘긴 객체는 끝까지 준영속) ⑤ flush 시 변경 감지가 UPDATE 생성.
- **차이의 한 문장** — 변경 감지는 "무엇이 바뀌었는지"를 스냅샷으로 **계산**한다. merge는 "무엇이 바뀌었는지 모르니 **전부 덮는다**". merge도 결국 변경 감지를 타지만 **덮어쓰기가 끝난 상태**로 타므로 null까지 변경으로 잡힌다. → 후보자의 "스냅샷 대조가 없다"를 여기서 교정.
- **두 번째 버그 유형: 반환값 무시** — `repository.save(member)` 이후 `member`를 만져도 아무 일도 없다(준영속). "수정이 반영 안 된다"는 문의는 대개 이것.
- **정답 패턴** — 조회 후 영속 상태에서 필요한 필드만 변경. 한 겹 더: `member.changeContact(name, phone)` 같은 **도메인 메서드로 감싸 변경 가능 범위를 타입으로 고정**한다(setter를 열어두면 다음 사람이 또 전체를 만진다).
- **merge가 정당한 자리는 거의 없다** — 세션·캐시에 보관했던 엔티티, 원격 호출로 통째로 받은 엔티티의 **재부착** 정도. "값을 전부 바꿔야 할 때"조차 DTO로 받아 필드별 적용이 안전한 이유: **merge는 "클라이언트가 안 보낸 필드"와 "null로 지우라고 보낸 필드"를 구분할 수 없다** — PATCH 시맨틱 구현에서 이 구분이 곧 요구사항.
- **부수 비용** — merge는 항상 SELECT가 선행된다. 대량 수정에서 조회가 배로 붙는다.

**메모**: 이 스레드가 3장에서 가장 낮다. 주목할 점은 **올바른 코드 패턴은 알지만 그 이유를 모른다**는 구조 — 관례로 정답을 써왔다는 뜻이고, 이는 rationale이 이 문항으로 정확히 재려던 것("미묘하지만 사고 유형이 명확한 지식")에 걸렸다. `save()`의 persist/merge 분기를 모르는 것은 기본⭐ 기준으로도 결함이다. 다만 경로를 한 번 알려주자 전체 컬럼 null 덮어쓰기를 즉시 도출했으므로 **이해력 문제가 아니라 학습 공백**으로 판단 — 문서 학습으로 빠르게 메워질 유형. 역질문 두 번("어떤 merge인가", "수정 요청인가")은 조건을 확정하려는 좋은 습관으로, Q2에서도 나온 일관된 강점.

### [Q6] 연관관계의 주인(owner), `mappedBy`는 왜 필요한가 — **상**

**본질문 답변 요지**: "연관관계의 아이디를 갖고 있는 클래스가 주인이다. `mappedBy`는 주인이 아닌 엔티티가 연관관계를 갖기 위함이다." (주인의 정의 정확 = FK를 가진 쪽)

**꼬리질문 6-1**: `Member.team`이 주인(`@JoinColumn(team_id)`), `Team.members`는 `@OneToMany(mappedBy="team")`. `team.getMembers().add(member)`만 하고 커밋하면 DB의 `team_id`는?
- 답변: "null로 저장된다. 주인이 아니라서 FK 갱신이 안 된다." (**즉답 정확** — rationale이 지목한 "신입 단골 이슈"를 바로 짚음)

**꼬리질문 6-2**: 왜 JPA는 굳이 주인 개념을 두고 한쪽만 FK를 관리하게 했나? 양쪽 다 관리하게 두면 안 되는 이유는?
- 답변: "양쪽 다 관리하면 어느 쪽 값을 따라야 할지 모호해져서." (**정확** — 객체 참조 2개 vs FK 1개의 비대칭에서 기준이 필요하다는 설계 의도를 짚음)

**꼬리질문 6-3**: 양방향/단방향은 어떻게 결정하나? 양방향으로 둔 연관이 있었다면 이유는?
- 답변: "보통 단방향으로 푼다. 양방향을 잘 사용하지 않는다." (선택은 옳으나 **근거 서술 없음**)

**꼬리질문 6-4**: 단방향이면 팀 상세 화면의 소속 멤버 목록은 어떻게 조회했나? 양방향으로 가야 하면 반드시 해야 하는 일은?
- 답변: "팀 id로 멤버를 조회한다. 양방향을 쓴다면 무조건 주인을 골라야 하고, 주인이 아닌 곳에서 데이터를 업데이트할 때는 주인도 같이 업데이트하도록 해야 한다." (**둘 다 정확.** 대안 조회 경로 + 연관관계 편의 메서드의 필요성을 용어 없이 원리로 서술)

**면접관 보충**:
- 주인은 항상 **다(N)쪽**이다. `@ManyToOne`이 주인, `@OneToMany`가 `mappedBy`. `mappedBy`의 의미는 **"나는 주인이 아니고 상대의 이 필드가 FK를 관리한다" = 읽기 전용 선언**.
- **연관관계 편의 메서드의 진짜 이유는 DB가 아니라 1차 캐시다** — 주인만 세팅하면 DB의 FK는 정확히 갱신된다. 그런데 같은 트랜잭션에서 `team.getMembers()`를 다시 읽으면 **이미 로딩된 컬렉션이 1차 캐시에 있어 갱신 전 상태로 보인다.** "DB는 맞는데 화면은 틀린" 현상의 출처. 즉 편의 메서드는 영속화용이 아니라 **객체 그래프 일관성용**이다. ← 후보자가 도달하지 못한 유일한 층.
- **양방향의 대가** — 편의 메서드 유지 부담, **무한 순환 참조**(JSON 직렬화·`toString`·`equals`에서 스택 오버플로), 테스트에서 양쪽 정합성 관리.
- **단방향 우선의 근거** — 조회 요구는 대부분 리포지토리 쿼리로 해결된다(후보자의 `findByTeamId`). 양방향이 정당한 자리는 **연관을 함께 저장·삭제하는 Aggregate 경계 안**, 즉 cascade가 의미를 갖는 곳뿐. 판단 축은 "조회 편의"가 아니라 **"생명주기를 공유하는가"**.
- **함정** — `@OneToMany`를 `mappedBy` 없이 `@JoinColumn`으로 단방향 매핑하면 동작하지만 **INSERT 후 FK를 채우는 UPDATE가 별도로 나간다.**

**메모**: 3장 첫 **상**. 네 개 꼬리질문 전부 힌트 없이 정확히 답했고, 특히 6-2(설계 의도)와 6-4(대안 조회 + 편의 메서드)는 매핑을 손으로 다뤄본 근거로 본다. 남은 약점은 **일관된 서술 습관** — "보통 단방향으로 푼다"에서 근거를 붙이지 않는다. Q1·Q3에서도 같은 패턴(선택은 맞고 근거는 한 줄). 지식보다 **답변 구성 훈련**의 문제이므로 knowledge 문서보다 실전 반복으로 교정할 영역.

### [Q7] `LazyInitializationException`의 원인과 해결책의 트레이드오프 — **중** (상에 가까움)

**본질문 답변 요지**: "트랜잭션이 끝난 후 지연 로딩된 데이터에 접근해서 발생한다. 해결은 ① 트랜잭션 범위를 넓히거나(커넥션을 길게 가지고 감) ② 다시 트랜잭션을 열어 재조회하거나(커넥션 재사용 비용) ③ 즉시 로딩으로 바꾼다(메모리 비용)." (**이 세션 최초로 해결책마다 비용을 자발적으로 병기** — Q1~Q6에서 반복 지적된 "트레이드오프 한쪽만 서술" 패턴이 여기서 깨졌다. 단 fetch join·`@EntityGraph` 누락)

**꼬리질문 7-1**: 즉시 로딩을 해결책으로 들었는데 앞서 EAGER의 문제를 직접 말했다. 지금 스스로 어떻게 평가하나? 그리고 빠진 실무 표준 해결책이 있다.
- 답변: "무조건 필요하다면 즉시 로딩 말고 DTO로 조회해서 가져오는 게 좋다고 생각한다. **즉시 로딩으로 바꾸면 기존 로직에도 영향을 미칠 수 있어 위험하다.**" (**우수한 자기 교정.** "예외는 한 지점에서 났는데 처방은 전역에 적용된다"는 범위 불일치 논리를 스스로 세움 — 이 문항의 핵심 판단)

**꼬리질문 7-2**: Spring Boot 프로젝트에서 이 예외를 실제로 자주 봤나? 자주 안 봤다면 왜 안 났을까?
- 답변: "자주 봤다. `@Transactional`이 붙지 않은 곳에서 연관관계 데이터를 사용하려다 발생했다. 자주 보지 않았으면 매 요청마다 트랜잭션 범위를 길게 잡은 것이다." (경험 서술은 구체적. 다만 "안 나는 이유"를 트랜잭션 범위로만 설명 — **OSIV 미언급**)

**꼬리질문 7-3**: Spring Boot에 기본 on인 설정 하나가 컨트롤러의 지연 로딩을 통과시킨다. 그 설정을 아나? 켜져 있는데도 예외를 자주 봤다면 어떤 상황이었나?
- 답변: "잘 모르겠다."

**면접관 보충**:
- **원인의 정확한 표현** — "트랜잭션이 끝나서"가 아니라 **`EntityManager`(세션)가 닫혀서**다. 이 구분이 중요한 이유가 곧 OSIV — **트랜잭션은 끝났는데 `EntityManager`는 열려 있는** 상태를 만드는 장치이기 때문.
- **OSIV(`spring.jpa.open-in-view`)는 Spring Boot 기본 `true`** — 트랜잭션은 서비스에서 끝나지만 `EntityManager`를 응답 완료까지 열어둔다. 그래서 컨트롤러의 지연 로딩이 통과한다. 대가는 **커넥션을 요청 전체 동안 붙잡는 것** → 트래픽 증가 시 커넥션 풀 고갈. 시작 시 경고 로그가 뜨는 이유. 대용량 서비스는 끄고, 끄면 이 예외가 드러나므로 fetch join·DTO로 정면 대응한다.
- **OSIV가 켜져 있어도 예외가 나는 자리** — 테스트 코드(웹 요청 스코프 없음), `@Async`·스케줄러·별도 스레드, 배치, 응답 직렬화 이후, 엔티티를 캐시에 담아 재사용할 때. 후보자가 "자주 봤다"고 한 상황이 아마 이쪽.
- **해결책 4종의 계층별 성격** — ① **fetch join / `@EntityGraph`**: 지점별 처방, 가장 표준(후보자가 끝까지 누락) ② **트랜잭션 안에서 DTO 변환**: 근본적, 엔티티가 계층을 넘지 않게 함 ③ **트랜잭션 범위 확대**: 커넥션 보유 시간 증가로 대용량에서 금지 ④ **EAGER·OSIV**: 전역 설정으로 덮는 증상 은폐.
- **관통하는 원칙** — **해결책의 범위를 문제의 범위에 맞춘다.** 한 화면에서 났으면 그 쿼리에서 fetch join, 계층 경계 문제면 DTO. 전역 스위치는 문제를 옮기는 것.

**메모**: 서술 품질이 이 세션 최고. 특히 7-1의 자기 교정은 **면접관이 반론을 제기하지 않았는데도** 스스로 앞선 답변과의 모순을 인정하고 더 나은 대안으로 갈아탄 것으로, Q1 메모의 "반론 시 논점을 한 층 올리는 힘 부족"이 실질적으로 개선된 증거다(Q6의 자기 교정에 이어 두 번째). 남은 공백은 **지식의 구멍 두 개**(fetch join을 해결책 목록에 못 넣음 — Q4에서 언급했는데도 연결 실패 / OSIV 완전 미인지)이지 사고력 문제가 아니다. OSIV는 중급⭐⭐에 단독 문항이 있으므로 그때 재검증.

### [중급 Q1] fetch join과 페이징을 함께 쓸 때의 문제와 해결책 — **중**

**본질문 답변 요지**: 즉답 못 하고 **힌트 요청** — "fetch join은 join이고 페이징은 offset/limit인데 문제가 어떻게 발생하나?" (join의 **행 증폭**과 페이징 단위의 불일치를 연결하지 못한 상태에서 출발)

**힌트 제공**: Post 1건에 Comment 10개, `join fetch p.comments`를 페이지 크기 10으로 조회 — 반환 행 수와 원하는 Post 수가 같은가? `limit 10`을 그대로 붙이면 몇 건의 Post를 받나?
- 답변: "**실제로는 1건의 POST를 받는다.**" 해결책으로 "join한 상태에서 post id만 distinct로 페이징 조회 → 그 id로 다시 조회"를 제시. (**힌트 하나로 행 증폭 메커니즘을 스스로 도출.** 제시한 해법은 실무의 2-쿼리 분리 패턴 그대로 — 방향 정확)

**꼬리질문 1-1**: 하이버네이트는 이 SQL에 `limit`을 실제로 붙이나? 안 붙인다면 무엇을 하나? 그때 찍히는 경고 로그를 본 적 있나?
- 답변: "잘 모르겠다. 로그도 모르겠다." (**핵심 공백 1** — 실패가 어떤 모습으로 드러나는지를 모름)

**꼬리질문 1-2**: 그 2-쿼리 패턴을 하이버네이트가 설정 한 줄로 대신해주는 기능이 있다. 무엇인가? 켰을 때 쿼리 모양은?
- 답변: "잘 모르겠다." (**핵심 공백 2** — `default_batch_fetch_size` 미인지)

**꼬리질문 1-3**: fetch join + 페이징이 항상 문제는 아니다. 어떤 연관관계는 `limit`이 그냥 붙는다. 어느 쪽이고 왜인가?
- 답변: "**1대1 같은 경우는 괜찮다. post당 1건이면 의도한 대로 post를 조회할 수 있기 때문**이다." (정확. 자신이 세운 행 증폭 논리를 그대로 역방향 적용 — 추론력 확인. `@ManyToOne`까지 일반화하진 못했으나 판별 축은 잡음)

**꼬리질문 1-4 (설계)**: 게시글 목록 20건/페이지, 작성자 닉네임(`@ManyToOne`)과 태그 목록(`@OneToMany`, 3~5개) 필요. 쿼리를 어떻게 구성하고 몇 번 나가나?
- 답변: "post와 member 조인해 페이징 적용 후 조회 → 조회한 post_id로 태그 목록 한 번에 조회 → 애플리케이션에서 합쳐 응답. **총 2번.**" (**실무 정답.** ToOne은 조인에 포함, 컬렉션은 분리 — 도구 이름을 몰라도 설계는 도출)

**면접관 보충**:
- **하이버네이트의 실제 동작** — `limit`을 **붙이지 않는다**. 결과 정합성을 지키려 조건에 맞는 **전체를 힙에 올린 뒤 애플리케이션에서 잘라낸다**. 경고: `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory`. **쿼리는 성공하고 결과도 맞고 로그 한 줄만 남은 채 운영에서 OOM** — 이 문항이 검사하는 "지금은 되는데 나중에 터지는" 유형의 전형.
- **위험이 숨는 이유** — 개발/스테이징의 적은 데이터에서는 증상이 0이다. 사전 신호는 `HHH000104` 하나뿐이므로 **경고 로그를 실패로 승격**시키는 습관이 방어선.
- **문제의 정확한 범위** — `fetch join` 자체가 아니라 **컬렉션(ToMany) fetch join + 페이징**. ToOne(`@ManyToOne`·`@OneToOne`)은 행이 불어나지 않아 `limit`이 안전하게 부착된다.
- **해법 3종** — ① **ToOne은 fetch join으로 함께 조회**(조인해도 행 수 불변) ② **컬렉션은 `default_batch_fetch_size`(또는 `@BatchSize`)** — LAZY로 두고 접근 시 `where post_id in (?, ?, …)`로 묶어 `1 + N` → `1 + ceil(N/size)`. 후보자의 2-쿼리 수동 패턴을 프레임워크가 대신하는 것 ③ **조회 전용 화면은 애초에 DTO 프로젝션**.

**메모**: **추론력과 도구 인지가 뚜렷이 갈린 문항.** 힌트 하나를 받은 뒤로는 메커니즘 도출(1건만 온다) → 판별 기준 수립(1:1은 안전) → 설계 도출(2쿼리)까지 전부 스스로 해냈고, 마지막 설계 답변은 정답과 동일하다. 반면 "무엇을 아는가"를 묻는 두 질문(`HHH000104`, `default_batch_fetch_size`)은 연속 미답. 기본⭐ 소구간 총평의 약점 ①(**품질을 시스템으로 고정해본 경험 없음**)이 또 재현됐다 — Q2 유령 UPDATE 진단, Q4 N+1 자동 탐지에 이어 세 번째로, **"장애를 사전에 알아채는 장치"를 묻는 질문에서 일관되게 막힌다.** 사고력이 아니라 **운영 관측 경험의 부재**가 이 사람의 실제 병목임이 이제 확정적이다.

### [중급 Q2] OSIV 트레이드오프와 대용량 트래픽에서의 설정 — **중**

**본질문 답변 요지**: 즉답 못 하고 **힌트 요청** — "OSIV가 무엇인지 힌트를 줄 수 있나?" (**기본⭐ Q7 보충에서 이미 다룬 항목인데 재인출 실패.** 이 문항이 Q7의 재검증 문항이었음)

**힌트 제공**: 이름 그대로 뷰 렌더링 시점까지 `EntityManager`를 열어둔다. `spring.jpa.open-in-view` 기본값 `true`. 트랜잭션은 서비스에서 끝나도 `EntityManager`는 응답까지 살아 있어 컨트롤러의 지연 로딩이 통과한다. → "그 상태를 유지하려면 무엇을 계속 붙잡아야 하나?"
- 답변: "**요청 끝까지 DB 커넥션을 갖고 있는 것.** 커넥션이 부족해지면 응답이 느려지고 타임아웃 나서 에러가 전파된다. 대용량 트래픽에서는 꺼야 한다. 트랜잭션 범위 내에서 영속성 컨텍스트를 사용하도록 해야 한다." (**메커니즘만 주어지면 인과를 끝까지 완성한다** — 커넥션 점유 → 풀 고갈 → 타임아웃 → 전파. Q1과 동일한 패턴)

**꼬리질문 2-1**: 질문은 트레이드오프를 물었는데 한쪽 면만 말했다. **끄면 공짜인가?** 껐을 때 개발자가 치르는 대가는? 그리고 끄는 게 일방적으로 옳다면 스프링 부트는 왜 기본값을 `true`로 두나?
- 답변: "끄면 트랜잭션 범위에서만 커넥션을 갖고 있는다. 껐을 때는 **트랜잭션 범위 밖에서 영속성 컨텍스트를 통한 JPA 이점을 얻지 못한다.** 따라서 JPA 로직 작성 시 트랜잭션 내부에 있는지 확인이 필요하다. 기본값 `true`인 이유는 대용량 트래픽을 고려한 게 아니라 **에러가 최대한 나지 않도록 방어적으로 설정**한 것으로 생각한다." (**양면 서술 성립.** 기본값 해석도 타당 — 프레임워크의 방어적 기본값이라는 프레임을 스스로 세움. 단 지적을 받은 뒤에야 나옴)

**꼬리질문 2-2 (시나리오)**: OSIV가 켜진 전제로 3년치 코드가 쌓인 운영 서비스. 커넥션 풀 고갈이 실제 발생해 끄기로 결정. `false`로 배포하면 무슨 일이 벌어지나? **그 사고를 배포 전에 막으려면 무엇을 하겠나? 3년치 코드 중 어디가 터질지 어떻게 찾겠나?**
- 답변: "트랜잭션 범위 밖에서 지연 로딩으로 통한 데이터 조회가 있는지 확인해야 한다." (**방향만 있고 방법이 없음** — 이 문항의 핵심을 비껴감)

**꼬리질문 2-3**: 컨트롤러와 DTO 변환 코드가 수백 개다. **구체적으로 어떻게** 확인하나? 전수 눈으로 읽나? 다 읽었다 쳐도 **놓친 게 없다는 걸 무엇으로 보장하나?**
- 답변: "엔티티 기준으로 **지연 로딩 데이터를 get하는 메서드 사용처만 확인**하면 된다." (탐색 범위를 좁히는 발상 자체는 합리적. 그러나 **정적 검색의 한계를 못 봄** — 보장 수단에 대한 답은 없음)

**꼬리질문 2-4 (반론)**: 컨트롤러가 `Order` 엔티티를 그대로 반환하고 `@OneToMany(LAZY) items`가 있다. **코드 어디에도 `getItems()` 호출이 없어 사용처 검색에 안 걸린다.** 그런데 끄고 배포하면 터진다. 왜인가?
- 답변: "**JSON으로 직렬화할 때 터진다.**" (**즉답, 정확.** Jackson이 리플렉션으로 게터를 호출한다는 것을 알고 있음)

**면접관 보충**:
- **켰을 때가 특히 치명적인 조건** — 컨트롤러·응답 단계에 **외부 API 호출** 같은 느린 I/O가 있으면 커넥션이 **아무 일도 하지 않으면서** 그 시간만큼 점유된다. 풀 20개에 300ms 외부 호출이면 처리량이 무너진다. "커넥션을 오래 잡는다"보다 **"놀고 있는 커넥션을 잡는다"** 가 문제의 정확한 표현.
- **껐을 때의 진짜 의미는 불편이 아니라 설계 강제** — "엔티티는 트랜잭션 밖으로 나가지 않는다"를 프레임워크가 강제한다. 그 결과 fetch join·DTO 변환을 명시적으로 쓰게 된다. 중급 Q5(엔티티 직접 노출 금지)와 같은 원칙의 다른 얼굴.
- **전환 순서** — 끄고 나서 터지는 걸 줍는 게 아니다. ① **컨트롤러가 엔티티를 반환하지 않도록 DTO 경계를 먼저 세운다** → ② 서비스 트랜잭션 안에서 변환을 끝낸다 → ③ **마지막에 끈다**.
- **보장 수단** — `open-in-view=false` 프로파일로 **전체 컨트롤러 통합 테스트**를 돌려 `LazyInitializationException`을 표면화시킨다(통합 테스트 커버리지 = 안전망). **ArchUnit**으로 "컨트롤러 반환 타입에 엔티티 금지" 룰을 걸어 재발까지 차단. 정적 검색은 직렬화·`toString`·프록시 경유를 못 잡으므로 보장 수단이 될 수 없다.

**메모**: **Q1과 완전히 같은 프로필이 반복됐다.** ① 도구·설정의 이름을 묻는 지점에서 막히고(OSIV 자체를 재차 모름 — Q7 보충에서 이미 설명한 항목이라 **인출 실패가 더 뼈아프다**) ② 메커니즘만 손에 쥐면 인과 전개는 정확하며 ③ 반론에는 즉답한다(직렬화). 그리고 ④ **"배포 전에 어떻게 보장하나"에서 또 멈췄다 — 3장에서 네 번째다**(유령 UPDATE 진단 / N+1 자동 탐지 / `HHH000104` / OSIV 전환 검증). 이 사람의 병목은 지식량도 사고력도 아니라 **"안전망을 코드로 고정한 경험"의 완전한 부재**로 확정. 다음 세션부터는 이 축을 별도 훈련 대상으로 다뤄야 한다. 한편 트레이드오프 양면 서술은 **지적을 받으면 즉시 채운다** — 자발성만 남은 문제.

### [중급 Q3] 낙관적 락(`@Version`) vs 비관적 락 — 차이와 선택 기준 — **중 (상에 근접)**

**본질문 답변 요지**: "낙관적 락은 **락이 거의 걸리지 않는 상황**에서, 비관적 락은 **락이 자주 발생하는 상황**에서 쓴다. 낙관적 락은 업데이트할 때 기존 값을 조회하고 **업데이트 직전에 다시 조회해서 값이 같은지 확인 후** 업데이트하는 방식, 비관적 락은 **조회부터 락을 잡아서** 실행한다." (**선택 기준(충돌 빈도)은 정확.** 그러나 낙관적 락의 동작 모델이 **check-then-act로 잘못 형성**돼 있음 — 실제로는 별도 SELECT 없이 UPDATE 한 문장의 조건절로 처리)

**꼬리질문 3-1 (반론)**: "확인하는 순간과 업데이트하는 순간 사이"에 다른 트랜잭션이 끼어들면? 그 확인은 무엇을 보장하나? 틈이 없으려면 실제 UPDATE 문이 어떻게 생겨야 하나?
- 답변: "그럼 데이터가 그대로 업데이트되어서 의도대로 되지 않는 것으로 안다. **틈이 없으려면 비관적 락을 사용**하는 것으로 안다." (**자신의 모델 안에서는 논리적으로 옳은 결론.** 모델이 틀려서 "낙관적 락은 근본적으로 안전하지 않다"는 오결론에 도달 — 이해의 바닥 확인)

**꼬리질문 3-2 (힌트)**: 틈이 생기는 건 확인과 갱신이 두 문장이기 때문이다. **확인을 UPDATE 문 안에 집어넣으면?** `@Version` 엔티티 수정 시 하이버네이트가 실제 날리는 UPDATE는? 충돌은 무엇을 보고 감지하나?
- 답변: "SQL 한 문장 안에서 일어나면 끼어들 틈이 없다. **version 필드를 붙여 업데이트 시 where 절에 해당 버전을 넣고, 업데이트 실패하면 다시 버전 조회 후 로직 실행 후 업데이트**하도록 한다." (**힌트 하나로 정확히 재구성.** 재시도 흐름까지 스스로 포함)

**꼬리질문 3-3 (시나리오)**: 한정판 재고 차감, **초당 500건이 전부 같은 `product` 로우 하나**를 친다. 낙관적 락 + 재시도를 걸면? 비관적 락으로 바꾸면 해결되나?
- 답변: "500건이 계속 쌓이고 **그중 1개만 통과하고 다시 499건이 로직을 실행해서 스레드 부담이 커진다.** 비관적 락을 쓰면 499건이 block되어 스레드 부담이 덜어진다. 단 **요청 시 스레드를 계속 들고 있어서 가상 스레드를 이용해야 한다.**" (**재시도 폭풍을 정확히 예측.** 블로킹과의 대비도 정확. 가상 스레드까지 끌어온 것은 2장 학습의 전이)

**꼬리질문 3-4 (반론)**: 가상 스레드로 스레드는 싸졌다. 그런데 대기 중인 499건이 붙잡은 게 스레드뿐인가? `SELECT ... FOR UPDATE` 상태로 대기 중이고 **커넥션 풀이 20개**라면? 가상 스레드가 이 문제를 해결하나?
- 답변: "**커넥션 풀이 모두 고갈되어서 해결을 못한다.** 해결하려면 JPA 비관적 락이 아닌 **Redis 분산 락**을 사용하는 것이 좋다." (**즉답, 정확.** 직전 Q2(OSIV)의 커넥션 점유 논리를 다른 맥락에 전이시킴 — 학습 전이 확인)

**꼬리질문 3-5**: Redis 분산 락도 500건이 줄 서는 건 똑같다. **기다리게 하지 않고** 푸는 방법은? 힌트 — 읽고/계산하고/쓰는 3단계가 정말 필요한가?
- 답변: "**이해가 안 간다. 어떻게 되었든 기다려야 한다. 기다리는 곳이 바뀔 뿐 값을 1개씩 차감해야 하므로 어느 한곳에서는 기다려야 한다.**" (**타당한 반론.** 같은 로우인 이상 직렬화는 불가피하다는 직관 자체는 옳다. 놓친 것은 "기다림의 유무"가 아니라 **"임계 구간의 길이"** 라는 축)

**면접관 보충**:
- **낙관적 락은 락이 아니다** — 아무것도 잠그지 않는다. `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`의 **영향 행 수 0**으로 충돌을 **사후 감지**할 뿐이다(`OptimisticLockException`). "충돌하지 않을 것"에 베팅하고 틀리면 예외를 받는 구조. 후보자의 check-then-act 모델과의 결정적 차이는 **별도 SELECT가 없다**는 점.
- **재시도는 반드시 새 트랜잭션·새 영속성 컨텍스트에서** — 같은 트랜잭션에서 재시도하면 1차 캐시에 옛 버전 엔티티가 남아 영원히 실패한다. (후보자가 "다시 버전 조회 후"라고 한 것은 방향은 맞으나 영속성 컨텍스트 초기화까지는 미언급)
- **선택 기준 = 충돌 빈도 × 재시도 비용** — 드물면 낙관적(평시 오버헤드 0), 잦으면 비관적(재시도 폭풍 회피). 단 **비관적 락은 커넥션을 락 대기 시간만큼 점유**하므로 고TPS에서는 이것도 답이 아니다.
- **3-5의 답 — 락을 애플리케이션에서 DB 한 문장 안으로 밀어 넣는다**: `UPDATE product SET stock = stock - 1 WHERE id = ? AND stock >= 1`. 기존 구조의 락 보유 구간은 `SELECT` → 값 전송 → 자바 계산 → `UPDATE` 전송(네트워크 왕복 2회, **수 ms**)인 반면, 한 문장이면 **수 μs**. 직렬화는 여전하지만 **임계 구간이 ~1000배 짧아져** 500 TPS가 소화된다. 게다가 `affected rows = 0`이면 곧 "재고 없음"이라 **재시도 자체가 불필요**(즉시 품절 응답). → 고난이도⭐⭐⭐ 전용 문항에서 4종(낙관/비관/원자적 UPDATE/분산 락) 비교로 재확인 예정.

**메모**: **3장 전체에서 가장 좋은 스레드.** 반론을 받을 때마다 한 단계씩 정확히 올라갔다 — 재시도 폭풍 → 블로킹 → 스레드 점유 → 가상 스레드 → **커넥션 풀 고갈** → 분산 락. **네 번 연속으로 "다음에 짚어야 할 것"을 스스로 짚었고**, 마지막엔 반론까지 제기했다. 기본⭐ Q1 메모의 "반론 시 논점을 한 층 올리는 힘 부족"은 이제 완전히 해소된 것으로 판단한다. 특히 3-4에서 **직전 문항(OSIV)의 커넥션 점유 논리를 자발적으로 전이**시킨 것이 인상적 — 세션 내 학습이 즉시 작동한다는 증거.
반면 감점 사유는 단 하나, **`@Version`의 실제 동작을 몰랐다는 것**(중급 필수 지식). 이 패턴 역시 3장 내내 동일하다 — **판단력 ≫ 도구·메커니즘 지식**. Q1(HHH·batch fetch), Q2(OSIV 정의), Q3(@Version 동작) 모두 "무엇을 아는가"에서만 걸렸고 "어떻게 판단하는가"에서는 걸린 적이 없다. **학습 처방은 명확: 개념 이해가 아니라 도구·설정·API의 실제 동작을 사실 단위로 채우는 것.**

### [중급 Q4] 벌크 연산(`@Modifying`) 후 영속성 컨텍스트 처리 — **중 (하에 근접)**

**본질문 답변 요지**: "벌크 연산을 실행하면 **영속성 컨텍스트는 한번에 처리하지 않을까?**" (**질문의 전제인 `@Modifying`을 모르는 상태.** 벌크 연산이 영속성 컨텍스트를 **우회**한다는 핵심을 정반대로 이해 — "한번에 처리한다"는 곧 컨텍스트를 거친다는 뜻)

**꼬리질문 4-1 (시나리오)**: 같은 트랜잭션에서 `findById`로 `stock=100`을 로드 → `@Modifying update Product p set p.stock = 0` 실행 → `p.getStock()`은 무엇이 찍히나? 그 시점 **DB 값**은?
- 답변: "**100이 찍힌다. 그리고 그 시점 DB 값도 100이다.**" (**전자는 정답, 후자는 오답.** 1차 캐시가 안 바뀐다는 건 맞혔으나 **벌크 연산이 쓰기 지연 대상이 아니라 즉시 DB로 나간다**는 것을 모름 → 실제 DB는 이미 `0`)

**면접관 정정**: 벌크 연산은 영속성 컨텍스트를 거치지 않고 DB로 직행한다. 오히려 JPQL 실행 **직전에 flush가 먼저** 일어나고 그 다음 UPDATE가 즉시 나간다. 1차 캐시의 `p`는 그 사실을 모른 채 옛 값을 유지 → **DB 0 / 메모리 100 불일치**.

**꼬리질문 4-2**: 그 불일치 상태에서 `p.setName("신상품")` 한 줄을 추가하고 커밋하면? DB의 `stock`은 최종 얼마가 되나?
- 답변: "**100이 되지 않을까?**" (**정답.** 확신은 없으나 dirty checking이 벌크 결과를 덮어쓴다는 결론에 도달)

**꼬리질문 4-3**: 이상하지 않나 — `name`만 바꿨는데 왜 `stock`까지 되돌아가나? **커밋 시점에 하이버네이트가 만드는 UPDATE 문**으로 설명하라.
- 답변: "커밋 시점에 하이버네이트가 **기존 스냅샷과 현재 상태값을 비교 후** 업데이트문을 작성하기 때문이다. **업데이트문에는 모든 필드가 들어간다.**" (**정확.** 기본⭐ Q2 보충에서 다룬 전 컬럼 UPDATE를 정확히 인출 — 이전 학습이 작동한 사례)

**꼬리질문 4-4**: 실무에서 이 사고를 어떻게 막나? `@Modifying`에 이를 위한 옵션이 있다. 무엇이고 각각 언제 동작하나? 모르면 옵션 없이 막는 방법이라도.
- 답변: "**우선 `@Modifying`이 무엇인지 왜 쓰는지도 모르겠다.** 따라서 옵션도 모르겠다. 옵션 없이 논리적으로 생각했을 때는 **`EntityManager`를 clear하고 다시 조회하면 될 것 같다.**" (**어노테이션을 모르는 채로 정답 처방을 논리만으로 도출** — `clearAutomatically = true`가 정확히 그것. Q1~Q3과 완전히 동일한 프로필)

**면접관 보충**:
- **`@Modifying`의 정체** — "이건 조회가 아니라 변경 쿼리다"라는 표시. 붙이지 않으면 Spring Data JPA가 `getResultList()`로 실행하려다 예외. 붙이면 `executeUpdate()`로 나간다.
- **옵션 두 개는 방향이 반대다** — `flushAutomatically = true`는 쿼리 **실행 전** flush(아직 DB에 안 나간 변경분을 벌크 연산에 **반영**), `clearAutomatically = true`는 쿼리 **실행 후** clear(낡은 1차 캐시를 **폐기**). 후보자가 도출한 것은 후자.
- **그러나 `clearAutomatically`는 안전장치가 아니다** — 영속성 컨텍스트를 **통째로** 비우므로 같은 트랜잭션에서 수정 중이던 **다른 엔티티의 변경분도 flush 없이 소실**된다. clear 이후 기존 참조는 전부 준영속이 되어 지연 로딩도 터진다.
- **진짜 처방은 옵션이 아니라 배치** — 벌크 연산은 **트랜잭션의 맨 끝에 두거나 별도 트랜잭션으로 분리**한다. 원칙: **"영속성 컨텍스트를 우회하는 연산과 영속성 컨텍스트에 의존하는 연산을 같은 트랜잭션에 섞지 않는다."**

**메모**: **Q1~Q3의 프로필이 네 번째로 정확히 재현됐다** — 도구 이름(`@Modifying`)과 사실(벌크의 즉시 실행·우회 성격)에서 걸리고, 시나리오를 코드로 깔아주면 그 뒤로는 한 번도 틀리지 않는다(4-2 덮어쓰기 예측 → 4-3 메커니즘 정확 → 4-4 정답 처방 도출). 특히 4-3에서 **기본⭐ Q2 보충의 "전 컬럼 UPDATE"를 정확히 인출**한 것은 학습 정착의 증거.
다만 이 문항의 rationale은 "**증상이 괴상해서 원인을 모르면 며칠을 헤맨다 — 겪었거나 원리를 아는 사람만 즉답한다**"이다. 후보자는 즉답하지 못했고, **코드를 눈앞에 깔아줘야만 보였다.** 실무에서 이 증상("DB는 바뀌었는데 조회는 옛날 값" 또는 "벌크 결과가 사라짐")을 만나면 원인을 짐작조차 못 할 상태. 평가를 상향할 수 없는 이유가 여기 있다.

### [중급 Q5] 엔티티를 API 응답으로 직접 노출하면 안 되는 이유 — **중 (상에 근접)**

**본질문 답변 요지**: "엔티티를 직렬화할 때 **lazy 로딩 시 오류가 날 가능성이 높다.** 오류는 **OSIV가 false인 상황**에서 발생한다." (**이유를 하나만, 그것도 가장 좁은 기술적 사고로 답함.** 직전 Q2 학습의 전이라는 점은 긍정적이나, 이 문항이 요구하는 결합도·보안·순환참조는 전무)

**꼬리질문 5-1 (반론)**: "우리는 OSIV를 켜두니 그 오류는 안 난다, 그럼 엔티티를 그대로 반환해도 되나?" 다른 이유는? 그리고 OSIV를 켜서 예외가 안 나는 그 상황은 정말 안전한가 — 지연 로딩이 "성공"할 때 직렬화기는 무엇을 하고 있나?
- 답변: "사용자 응답 데이터에 다른 데이터도 추가로 넣어야 하는데 **이때마다 테이블 수정과 엔티티 수정을 하면 유지보수가 어렵다.** 즉 **DTO로 분리해서 의존성을 낮춰야** 한다." (**결합도 층 도달.** 단 두 번째 물음(직렬화기의 동작)은 건너뜀)

**꼬리질문 5-2**: (코드 제시 — `Order`에 LAZY `member`, `items`, `OrderItem`에는 역방향 `order`) Jackson이 `items` 게터를 만나면? 응답 하나에 쿼리가 몇 번? `OrderItem`에서 다시 `order`를 만나면?
- 답변: "**items를 만나면 N+1 문제가 터진다. 그리고 순환참조 문제가 발생한다.**" (**둘 다 즉답, 정확**)

**꼬리질문 5-3 (반론)**: 동료 제안 — "`OrderItem.order`에 `@JsonIgnore` 붙이면 순환참조 막히고 `member`에도 붙이면 지연 로딩도 안 탄다. DTO보다 간단하지 않나?" 받아들이겠나? 반대한다면 근거는?
- 답변: "**그럼 사용자 화면에 필요한 데이터가 다른 엔티티를 필요로 하고, 이 엔티티가 Order와는 전혀 연관관계가 없는 데이터라면?**" (**유도하지 않은 논거를 스스로 제시.** 엔티티 구조와 화면 요구가 애초에 다른 축이라는 지적 — DTO의 가장 근본적 정당화. 이 스레드 최고의 답변)

**꼬리질문 5-4**: `@JsonIgnore` 자체의 구멍 — 관리자 API는 `member` 실명·연락처가 **필수**, 사용자 API는 **절대 노출 금지**. `@JsonIgnore`로 둘을 동시에 만족시킬 수 있나?
- 답변: "**만족시킬 수 없다.**" (즉답, 정확. 어노테이션이 엔티티에 박히는 전역 스위치라는 성질을 이해)

**면접관 보충** (후보자가 끝까지 언급하지 않은 두 축):
- **보안 — 실수의 방향이 반대다.** 엔티티 직접 노출은 **opt-out** 구조라, 누군가 엔티티에 `internalMemo`·`settlementRate` 필드를 추가하는 순간 **응답 코드를 아무도 건드리지 않았는데 그 필드가 API로 새어 나간다.** DTO는 **opt-in**이라 명시한 것만 나간다 — 사고가 나려면 누군가 의도적으로 코드를 써야 한다. **이것이 실무에서 가장 자주 인용되는 논거.**
- **요청 방향은 더 위험하다** — `@RequestBody Member member`로 받으면 클라이언트가 `role: "ADMIN"`, `point: 999999`를 실어 보내 덮어쓸 수 있다(mass assignment). 서버 코드 어디에도 허용한 줄이 없는데도.
- **`@JsonIgnore`·`@JsonView`의 진짜 문제** — 동작 여부가 아니라 **엔티티에 표현 계층 관심사를 새겨 넣는다**는 것. 그 순간 엔티티는 도메인 모델이 아니라 **응답 템플릿**이 된다.
- **OSIV가 켜진 상태에서 예외가 안 나는 것은 더 나쁘다** — 예외 대신 직렬화기가 연관을 타고 들어가며 쿼리를 계속 날린다. 실패가 조용해질 뿐 비용은 늘어난다. 중급 Q2와 같은 원칙의 다른 얼굴.

**메모**: **지식의 양은 충분한데 자발적 전개가 안 되는 패턴이 새로운 형태로 재현됐다.** 5-2·5-4는 즉답이었고 5-3에서는 **유도하지 않은 독창적 논거**까지 나왔다 — 즉 알고 있다. 그런데 본질문에는 **이유를 하나만, 그것도 가장 좁은 것 하나**를 대고 멈췄다. 기본⭐ 소구간 총평의 약점 ②("선택은 맞고 근거는 한 줄")가 "이유는 알고 근거는 하나만"으로 변주된 것. 이 문항은 rationale상 **"계층 경계를 지키는 규율의 리트머스"** 인데, 규율이 몸에 밴 사람은 묻지 않아도 결합도·직렬화·보안을 한 호흡에 나열한다. 거기서 갈렸다.
한편 **직전 문항(OSIV)의 학습을 곧바로 끌어온 것**은 Q3의 커넥션 전이에 이어 두 번째 — 세션 내 학습 전이는 확실히 작동한다. 다만 이번엔 **그 전이가 시야를 좁히는 방향으로 작용**했다(가장 최근에 배운 것 하나로 답을 마감). 훈련 포인트: **"이유를 대라"는 질문에는 반드시 3층으로 답하는 습관**(기술적 사고 → 설계·결합도 → 보안·운영).

### [중급 Q6] QueryDSL 동적 쿼리 구성 경험 — **중**

**본질문**: 기본⭐ Q1에서 "선택적 조건 6개 조합 검색은 메서드 이름 방식으로 못 만들어 QueryDSL로 처리했다"고 한 발언을 근거로, 그 동적 쿼리를 실제로 어떻게 구성했는지 요구.
**답변 요지**: "**enum을 통해서 타입을 만들고, enum이 요청으로부터 들어왔는지로 분기해서 조건들을 where절에 추가**했다." (방향은 맞으나 코드 수준 서술이 아님)

**꼬리질문 6-1**: 구체적으로 `BooleanBuilder builder = new BooleanBuilder(); if (cond.getName() != null) builder.and(...)` 형태였나? 그리고 QueryDSL에서 `where()`에 `null`을 넘기면 어떻게 되나?
- 답변: "**맞다 위처럼 사용했다.**" (실제 사용 방식 확인 — **경험은 진짜**. 단 두 번째 물음은 미응답)

**꼬리질문 6-2**: `query.where(user.name.eq(name), null, user.age.gt(20))` — 예외가 나나, 조건이 무시되나, 결과가 0건이 되나?
- 답변: "**null을 넘겨본 적이 없어서 잘 모르겠다.**" (**핵심 공백.** 이 성질을 모르기 때문에 `BooleanBuilder` + `if`에 머물렀음)

**꼬리질문 6-3**: `BooleanBuilder` 방식의 함정 — 사용자가 검색 조건을 하나도 입력하지 않고 조회하면 어떤 쿼리가 나가나? 겪어봤나?
- 답변: "그냥 조회 쿼리만 나가지 않을까 싶다." (맞음 — `where`가 통째로 사라짐. 다만 **위험으로 인식하는 기색이 없음**)

**꼬리질문 6-4**: 그 테이블에 500만 건이 있고 페이징이 안 걸려 있다면? 어떻게 막겠나?
- 답변: "**OOM이 발생한다. 페이징 처리를 넣거나 최소 조건을 강제**하도록 해야 한다." (정확)

**후보자의 반론**: "이해가 안 간다. **페이징 쿼리와 BooleanBuilder를 분리해서 사용하면 무조건 페이징 처리가 되는 것으로 알고 있다.**"
- **면접관 인정**: 타당한 반론. 리포지토리 메서드가 항상 `Pageable`을 받아 `offset`/`limit`을 적용하는 구조라면 조건이 없어도 한 페이지 분량만 나가므로 OOM은 구조적으로 발생하지 않는다. 면접관이 깐 전제가 후보자의 실제 구조에 해당하지 않음을 인정하고 한 단계 더 진행.

**꼬리질문 6-5**: 페이징을 강제해 20건만 가져온다. 그런데 `Page<User>`를 반환해 "총 500만 건 중 1페이지"를 표시해야 한다면 — 쿼리가 몇 번 나가나? 조건이 하나도 없을 때 그 추가 쿼리는 무엇을 하나?
- 답변: "**2번 나간다. 모든 데이터를 조회한다.**" (**정확.** content 쿼리 + count 쿼리, 조건 없는 count는 500만 건 풀스캔)

**면접관 보충**:
- **`where(null)`은 조용히 무시된다** — 이것이 QueryDSL 동적 쿼리의 핵심 장치. 그래서 조건마다 `BooleanExpression`을 반환하는 메서드로 쪼개고 `where(nameEq(x), statusEq(y), ...)`로 나열하면 **`if`가 전부 사라진다**.
- **진짜 이점은 `if` 제거가 아니라 조합 가능성** — `nameEq(x).and(statusIn(y))`처럼 조건을 **합성·재사용**할 수 있다. `BooleanBuilder`에는 없는 성질.
- **선택 기준** — 단순 AND 나열이면 메서드 분리, `OR` 중첩처럼 구조가 복잡하면 `BooleanBuilder`. 대체재가 아니라 용도가 다르다.
- **count 쿼리는 최적화 대상** — `PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne)`는 **첫 페이지에 다 담히거나 마지막 페이지일 때 count 쿼리를 생략**한다. count 쿼리에서는 fetch join·불필요한 join을 제거해야 한다(세는 데 필요 없음).
- **더 근본적으로는** 조건 없는 전체 검색을 **애초에 허용하지 않는 설계**(필수 조건 하나 강제, 기본 기간 조건 자동 주입)가 대용량 검색 화면의 표준.

**메모**: **오늘 처음으로 "안전망" 축에서 긍정 신호가 나왔다.** 6-4 이후의 반론("페이징을 분리해서 쓰면 무조건 적용된다")은 문제를 **개별 케이스가 아니라 구조로 막아본 사람의 답변**이다. 3장 내내 지적된 횡단 약점(장애를 사전에 보장하는 장치의 부재)에 대한 첫 반증 사례이므로 기록해 둔다 — 다만 그 구조를 **후보자가 설계했는지 팀 컨벤션을 따른 것인지는 확인하지 못했다.** 다음 세션에서 확인 가치 있음.
공백은 여전히 같은 자리다 — **도구의 관용구를 모른다**(`where(null)` 무시). 이 하나 때문에 QueryDSL의 절반만 쓰고 있었다. Q1(batch fetch size), Q2(OSIV), Q3(`@Version` 동작), Q4(`@Modifying`)에 이어 **다섯 번째로 "무엇을 아는가"에서만 걸렸다.** 반면 판단(6-4 OOM·페이징 강제, 6-5 count 정체)은 전부 정확. 3장 전체를 관통하는 결론이 이제 흔들림 없다: **사고력 상급 / 도구 지식 하급.**

## 약점 노트 (재도전 대상)

- [ ] **(최우선·횡단)** **안전망을 코드로 고정하는 훈련** — 3장 전체에서 네 번 연속 막힌 축(유령 UPDATE 진단 / N+1 자동 탐지 / `HHH000104` / OSIV 전환 검증). 공통 처방: **쿼리 수 단정 테스트**(`SQLStatementCountValidator`, `Statistics.getPrepareStatementCount()`), **경고 로그를 실패로 승격**, **ArchUnit 구조 룰**(EAGER 금지, 컨트롤러 엔티티 반환 금지), **프로파일을 바꾼 통합 테스트로 잠재 예외 표면화**. 개별 문항이 아니라 **이 도구 상자 자체를 한 번에 익히는 것**이 효율적.
- [ ] **(최우선)** 중급 > 벌크 연산과 영속성 컨텍스트 — **`@Modifying`의 존재 자체를 모름**부터 채울 것("조회가 아니라 변경 쿼리"라는 표시, 없으면 예외, 있으면 `executeUpdate()`). + **벌크 연산은 영속성 컨텍스트를 우회해 즉시 DB로 나간다**(쓰기 지연 대상 아님, 오히려 실행 직전 flush 선행) → **DB와 1차 캐시의 불일치**가 이 문항의 전부. + **옵션 2종의 반대 방향**(`flushAutomatically`=실행 전 반영 / `clearAutomatically`=실행 후 폐기) + **`clearAutomatically`의 부작용**(컨텍스트 통째 비움 → 다른 엔티티 변경분 소실, 준영속화) + **진짜 처방은 배치**(벌크는 트랜잭션 끝 또는 별도 트랜잭션). **증상으로부터 원인을 떠올리는 훈련**이 핵심 — "DB는 바뀌었는데 조회는 옛날 값" / "벌크 결과가 조용히 사라짐"을 트리거로 기억할 것.
- [ ] 중급 > 엔티티 직접 노출 금지 — 개별 지식은 이미 있음(N+1·순환참조·결합도·`@JsonIgnore`의 전역성 모두 즉답). 비어 있는 것은 **보안 축 두 개**: ① **opt-out vs opt-in** — 엔티티 노출은 새 필드가 추가되면 응답 코드를 안 건드려도 자동 유출, DTO는 명시한 것만 나감 ② **요청 방향의 mass assignment**(`@RequestBody`로 엔티티를 받으면 `role`·`point`를 클라이언트가 덮어씀). + **`@JsonIgnore`의 진짜 문제는 동작이 아니라 엔티티가 응답 템플릿이 되는 것.** **훈련 포인트: "이유를 대라"에 3층으로 답하기**(기술적 사고 → 설계·결합도 → 보안·운영) — 이 문항은 하나만 대고 멈춘 것이 유일한 감점 사유였다.
- [ ] 중급 > QueryDSL 동적 쿼리 — **`where(null)`은 조용히 무시된다**는 성질 하나가 공백의 전부. 이를 알면 `BooleanExpression` 반환 메서드로 조건을 쪼개고 `where(nameEq(x), statusEq(y), …)`로 나열해 **`if`가 사라지고 조건을 합성·재사용**할 수 있다(`nameEq(x).and(statusIn(y))`) — `BooleanBuilder`에는 없는 성질. + **선택 기준**(단순 AND 나열 → 메서드 분리 / OR 중첩 → `BooleanBuilder`) + **count 쿼리 최적화**(`PageableExecutionUtils.getPage(...)`로 첫·마지막 페이지에서 count 생략, count 쿼리에서 join 제거) + **조건 없는 전체 검색을 애초에 막는 설계**(필수 조건 강제, 기본 기간 주입).
- [ ] 중급 > 낙관적 락 vs 비관적 락 — **`@Version`의 실제 동작을 사실로 고정**: 별도 SELECT 없이 `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?` 한 문장, **영향 행 수 0 = 충돌**, `OptimisticLockException`. **"낙관적 락은 락이 아니다(사후 감지)"** 를 한 문장으로. + **재시도는 새 트랜잭션·새 영속성 컨텍스트에서**(1차 캐시에 옛 버전이 남으면 영원히 실패) + **비관적 락의 숨은 대가는 커넥션 점유** + **임계 구간 길이라는 축**(원자적 UPDATE로 ms → μs). 판단력은 이미 상급이므로 **메커니즘 사실만 채우면 상**.
- [ ] **(최우선)** 중급 > OSIV — **OSIV의 정의 자체를 재차 인출 실패**(기본⭐ Q7 보충에서 이미 학습한 항목) → `spring.jpa.open-in-view=true`가 기본이고 트랜잭션 종료 후에도 `EntityManager`를 응답까지 연다는 한 문장을 확실히 고정. + **"놀고 있는 커넥션을 점유한다"는 문제의 정확한 표현**(컨트롤러 단 외부 API 호출이 있을 때 치명적) + **껐을 때는 불편이 아니라 설계 강제**(엔티티가 트랜잭션 밖으로 못 나감) + **안전한 전환 순서**(DTO 경계 수립 → 트랜잭션 내 변환 → 마지막에 끄기) + **보장 수단**(`open-in-view=false` 프로파일 통합 테스트, ArchUnit 룰). 정적 검색이 직렬화·`toString`·프록시를 못 잡는다는 것도 함께.
- [ ] **(최우선)** 중급 > fetch join + 페이징 — **`HHH000104` 경고와 메모리 페이징 동작**(limit을 붙이지 않고 전량 로딩 후 애플리케이션에서 절단 → 데이터 증가 시 OOM, 사전 신호는 이 경고 한 줄뿐) + **`default_batch_fetch_size` / `@BatchSize`**(컬렉션은 LAZY로 두고 `in (…)` 묶음 조회, `1+N` → `1+ceil(N/size)`) + **문제 범위의 정확한 한정**(컬렉션 fetch join일 때만. ToOne은 안전) + **해법 3종의 선택 기준**(ToOne은 fetch join / 컬렉션은 batch fetch / 조회 전용은 DTO). 설계는 이미 도출 가능하므로 **도구 이름과 관측 신호만 메우면 상**.
- [ ] **(최우선)** 기본 > merge vs dirty checking — **`save()`의 persist/merge 분기**(id 유무로 갈림, 중복 에러가 아니라 조용한 UPDATE) + **merge 5단계**(SELECT → 전 필드 복사 → 새 영속 인스턴스 반환 → flush 시 dirty checking) + **차이의 한 문장**("계산" vs "전부 덮기") + **반환값 무시 버그** + **merge가 PATCH를 구현할 수 없는 이유**(안 보낸 필드 vs null로 지우라는 필드 구분 불가) + 정당한 용도는 재부착뿐.
- [ ] **(최우선)** 기본 > N+1 — **자동 탐지 장치**(테스트에서 `Statistics.getPrepareStatementCount()` 단정, `SQLStatementCountValidator.assertSelectCount`, 요청 단위 쿼리 카운터 + 임계치 경고, ArchUnit EAGER 금지 룰) + **N의 정체는 결과 행 수가 아니라 미해결 연관 id 수**(픽스처는 건수 아니라 카디널리티) + **해결책 선택 기준**(컬렉션+페이징 → batch fetch size, to-one 여럿 → fetch join, 조회 전용 → DTO). "N+1은 회귀이므로 테스트로 고정한다"는 프레임 체득.
- [ ] 기본 > EAGER vs LAZY — **연관관계별 기본값 암기**(`@ManyToOne`·`@OneToOne`=EAGER / to-many=LAZY, 가르는 축은 단일 값 vs 컬렉션) + **JPQL에서 EAGER가 N+1이 되는 메커니즘**(JPQL은 그대로 번역, 글로벌 fetch 전략은 번역에 개입하지 않음 → 행마다 추가 쿼리. `find()`는 조인이라 단건 테스트에서 안 보이는 비대칭) + **EAGER 금지의 진짜 근거**(쿼리 단위로 끌 수 없다 = 되돌릴 수 없는 기본값). `@OneToOne(mappedBy)`의 LAZY 미작동도 함께.
- [ ] 기본 > 영속성 컨텍스트 — **flush의 실제 비용**(스냅샷 메모리 2배 + `O(엔티티×필드)` 비교, readOnly/DTO 프로젝션으로 회피)과 **"안 시킨 UPDATE" 진단 경로**(BigDecimal scale, 컬렉션 재할당, 컨버터 왕복 비대칭, 시간 정밀도, OSIV+setter → 진단은 바인딩 SQL 로그·Statistics·flush 리스너 스택트레이스). flush 순서 고정(INSERT→UPDATE→DELETE)과 전 컬럼 UPDATE도 함께.
- [ ] 기본 > JPA vs MyBatis — **결합도의 실체 3층**(방언/벤더 종속, SQL 부재로 스키마 변경 파급 축소, 도메인 로직을 엔티티에 둘 수 있음) + **JPA의 대가**(쿼리 비가시성→N+1·불필요 UPDATE, 쿼리 로그 습관) + **병용 구도**(쓰기 ORM / 읽기 SQL)를 스스로 꺼내기. 트레이드오프 양면 서술 훈련.
