# 10. 결제 / 정합성 (도메인 심화)

## 기본 ⭐

- 결제 흐름(요청 → 승인 → 완료)을 설계할 때 상태 관리는 어떻게 하나요?
- PG사 연동 시 기본적으로 고려해야 할 것들은? (타임아웃, 중복 방지, 검증)
- 웹훅(callback) 수신 처리 시 주의할 점은? (검증, 멱등성, 순서)

## 중급 ⭐⭐

- 결제 요청 후 PG 응답이 타임아웃됐습니다. 결제가 됐는지 안 됐는지 모르는 상태 — 어떻게 처리하나요?
- 포인트/캐시 차감과 콘텐츠 이용권 지급을 하나의 흐름에서 처리할 때 정합성을 어떻게 보장하나요?
- 결제 취소/부분 취소/환불의 상태 머신을 설계해보세요.
- 이중 지급/이중 차감을 막기 위한 방어선을 계층별로 나열해주세요. (UI → API → DB 제약)
- 정산/대사(reconciliation) 배치는 왜 필요하고 어떻게 설계하나요?
- AI가 생성한 "포인트 이체" 코드가 테스트를 전부 통과했습니다. 머지 전에 무엇을 어떤 순서로 검증하나요?

## 고난이도 ⭐⭐⭐

- 분산 환경에서 "잔액 차감 + 주문 생성 + 이용권 지급"이 서로 다른 서비스에 있을 때 트랜잭션을 어떻게 설계하나요? (Saga, 보상, 멱등성)
- 금액 계산에서 부동소수점을 쓰면 안 되는 이유와 통화/환율(글로벌 서비스)을 다루는 설계 원칙은?
- 프로모션(할인+쿠폰+포인트 복합 적용) 금액 배분과 부분 환불 시 역산 문제를 어떻게 설계하나요?
- 결제 데이터의 감사(audit) 요구사항 — 이벤트 소싱이나 append-only 설계가 유리한 이유는?

## 알면 좋은 +α

- 망취소(net cancellation)란 무엇이고 언제 필요한가요?
- 가상계좌처럼 승인이 비동기로 완료되는 결제 수단은 상태 설계가 어떻게 달라지나요?
- 부정 결제(도난 카드, 어뷰징) 탐지는 어느 계층에서 하나요? 오탐(정상 고객 차단)과의 균형은 어떻게 잡나요?
- 웹훅을 발신하는 쪽은 어떻게 설계하나요? (서명, 재시도와 백오프, 순서 역전, 수신측 장애 시 격리)
- 대사 배치가 실제로 불일치를 찾아낸 경험이 있나요? 원인은 무엇이었고, 그 뒤 무엇을 바꿨나요?
