# 9. REST API 설계

## 기본 ⭐

- RESTful API의 설계 원칙을 설명해주세요. 리소스 네이밍 규칙은?
- PUT과 PATCH의 차이는?
- API 버저닝 전략(URI, 헤더)의 장단점은?
- 페이지네이션 API를 설계할 때 offset 기반과 커서 기반의 차이는?
- API 에러 응답 바디는 어떻게 표준화하나요?

## 중급 ⭐⭐

- 결제 API에서 중복 요청(더블 클릭, 네트워크 재시도)을 어떻게 방지하나요? (멱등성 키 설계)
- 목록 조회 + 상세 N건 조회로 인한 API 호출 폭증(chatty API)을 어떻게 개선하나요?
- 하위 호환성을 깨지 않고 API를 변경하는 원칙은? 깨야만 할 때의 마이그레이션 절차는?
- 외부 파트너사에 제공하는 API(콘텐츠 연동)와 내부 API 설계의 차이점은? (인증, rate limit, 문서화, SLA)
- 긴 작업(예: 대량 다운로드 생성)을 REST로 어떻게 표현하나요? (202 + polling, callback)
- REST vs GraphQL vs gRPC — 어떤 기준으로 선택하나요?

## 고난이도 ⭐⭐⭐

- 낙관적 동시성 제어를 API 레벨에서 어떻게 표현하나요? (ETag, If-Match, 409 vs 412)
- 여러 마이크로서비스를 조합해 응답하는 API(BFF/aggregation)의 부분 실패를 어떻게 설계하나요?
- API 게이트웨이에서 처리할 것과 각 서비스에서 처리할 것의 경계를 어떻게 나누나요?

## 알면 좋은 +α

- API 문서와 실제 구현의 불일치를 어떻게 방지하나요? (Swagger 어노테이션 vs Spring REST Docs)
- 여러 건을 한 번에 처리하는 벌크 API에서 일부만 실패하면 응답을 어떻게 설계하나요?
- 목록 조회 API의 필터·정렬·검색 파라미터는 어떻게 설계하나요? 허용 정렬 키를 제한해야 하는 이유는?
- API 응답의 날짜/시간 포맷은 어떻게 규약하나요? (ISO 8601, 타임존 표기, epoch) 규약이 없으면 어떤 사고가 나나요?
