# 배포 없이 DB CPU만 올랐다 — "변경 없음"은 전제가 아니라 첫 번째 검증 대상이다

> 핵심 관전 포인트: **"배포 안 했다"는 코드가 안 바뀌었다는 말이지 시스템이
> 안 바뀌었다는 말이 아니다. DB는 배포 없이도 매일 변한다 — 데이터 증가·분포
> 변화, 통계 갱신에 따른 실행 계획 변경, 인접 배치·타 팀 잡, 트래픽 구성
> 변화·크롤러, 외부사 변경(웹훅 폭주), 인프라 작업(파라미터·페일오버·리플리카
> 소실), 캐시 만료·무효화, 긴 트랜잭션. 그래서 첫 행동은 원인을 찍는 것이
> 아니라 ① "변경 없음"이라는 전제를 **변경 타임라인**(배포·스키마·배치·인프라
> 이벤트·플래그·외부 공지·트래픽을 한 화면에)으로 검증하고, ② 후보를
> **언제부터**(CPU 곡선의 변곡점 시각과 모양) → **무엇이**(변곡점 전후의 top
> SQL digest 비교 — 새로 나타난 쿼리 / 횟수 급증 / 건당 비용 급증의 세 갈래)
> → **왜**(그 쿼리의 실행 계획을 베이스라인과 대조, 발신자 추적) 순으로
> 좁힌다. "CPU**만**"이라는 증상도 단서다 — CPU는 DB가 메모리 안의 행을 많이
> 읽고 비교·정렬하고 있다는 뜻이고, 디스크 병목이면 iowait, 락 대기면
> `Threads_running`만 오르고 CPU는 낮다. 이 검증이 사람의 기억이 아니라
> 시스템(변경 어노테이션, digest 스냅샷 잡, 실행 계획 베이스라인)에 고정돼
> 있어야 다음 장애 때도 같은 속도로 답이 나온다.**

## 0. 질문 + 의도

**질문**: "배포도 없었는데 어제부터 DB CPU만 올랐습니다. "변경이 없다"는
전제를 어떻게 검증하고, 원인 후보를 어떻게 좁혀가나요?"

**출제 의도**: 의도 2(장애 상황 판단)의 대표 형식. "배포 안 했는데요"는 코드
변경만 본 말이고, 시스템은 데이터 증가·통계 갱신·인접 배치·외부사 변경·인프라
작업으로 매일 변한다. "변경 없음"이라는 전제 자체를 의심하고 **변경의 정의를
넓혀** 조사하는지 — 진단의 첫 갈림길에서 방향을 잡는 능력을 본다. 즉 이
질문은 MySQL 지식 시험이 아니라 ⑴ 전제를 검증하는 습관, ⑵ 후보 목록을
빠짐없이 인출하는 능력, ⑶ 각 후보가 왜 하필 CPU로 나타나는지를 자원 단위로
설명하는 능력, ⑷ 그 절차가 사람 기억이 아니라 시스템에 있는지를 한 번에 본다.

> 진단 문서로서의 위치: [02-spring의 기동 지연 진단](../02-spring/32-slow-application-startup-diagnosis.md)이
> "시간축 먼저 → 침묵 구간은 다른 도구로"의 방법론이었다면, 이 문서는 같은
> 방법론을 DB에 적용한다 — 다만 여기서는 "무엇이 바뀌었는가"를 확인하는 단계가
> 앞에 하나 더 붙는다. 실행 계획이 바뀌는 메커니즘 자체는
> [실행 계획 급변 문서](./31-execution-plan-sudden-change.md)로 분리하고
> 여기서는 후보 중 하나로만 다룬다.

## 1. 첫 갈림길 — "변경 없음"은 전제가 아니라 검증 대상이다

### 1-1. "배포 안 했다"가 실제로 뜻하는 것

"배포 없음"은 **우리 팀이 이 서비스의 코드를 어제 이후 올리지 않았다**는
사실 하나다. 그 문장이 배제하지 못하는 것:

- 코드는 같아도 **코드가 처리하는 데이터**가 다르다 (행 수, 값 분포, 특정
  고객의 데이터 크기).
- 코드는 같아도 **옵티마이저가 고른 길**이 다를 수 있다 (통계 갱신).
- 코드는 같아도 **코드를 부르는 쪽**이 다르다 (트래픽 구성, 크롤러, 외부사
  웹훅, 타 팀 배치).
- 코드는 같아도 **코드가 도는 바닥**이 다르다 (파라미터, 페일오버, 리플리카
  소실, 패치).
- 코드는 같아도 **코드가 타는 경로**가 다르다 (feature flag, 원격 설정, A/B
  비율 — 배포 없이 동작이 바뀌는 공식 통로).
- 코드는 같아도 **앞단의 방패**가 다르다 (캐시 히트율).

그래서 "변경이 없다"는 결론이 아니라 **가설**이고, 검증 방법은 사람에게 "어제
뭐 하셨어요?"라고 묻는 것이 아니라 §4의 변경 타임라인을 여는 것이다. 사람의
기억은 자기 팀 배포까지만 미치고, 위 여섯 줄은 대부분 우리 팀 밖에서 일어난다.

### 1-2. 변경의 정의를 넓힌 후보 목록 — 체크리스트 (암기 카드)

면접에서 이 표를 순서대로 말할 수 있으면 "목록 인출"은 통과다. 각 줄이 왜
CPU로 이어지는지는 §2에서 사슬로 편다.

| # | 후보 | 첫 확인 지점 | CPU로 이어지는 사슬 한 줄 |
|---|---|---|---|
| 0 | 배포 아닌 코드 경로 변경 (플래그·원격 설정·A/B) | 플래그 변경 이력, config 저장소 커밋 | 새 경로의 쿼리가 켜짐 → 새 digest 등장 |
| 1 | 데이터 증가·분포 변화 | 테이블 행 수·크기 추이, 특정 키의 행 수 | 같은 계획으로 읽는 행 수 증가 → `rows_examined` ↑ |
| 2 | 통계 갱신 → 실행 계획 변경 | `EXPLAIN` vs 베이스라인, `rows` 추정 vs 실측 | 인덱스 대신 풀스캔·조인 순서 역전 → 행 수 폭증 |
| 3 | 인접 배치·크론·타 팀 잡 | 배치 메타 테이블, 크론 로그, `PROCESSLIST`의 user/host | 대량 스캔·집계 → CPU + 버퍼 풀 오염의 2차 피해 |
| 4 | 트래픽 구성 변화·크롤러·특정 사용자 | 엔드포인트별 RPS, UA·IP 분포, 페이지 번호 분포 | 총량은 같아도 비싼 쿼리 비중 ↑ |
| 5 | 외부사 변경 (웹훅 폭주·재전송 루프) | 웹훅 수신 건수, 외부사 공지·상태 페이지 | 이벤트당 조회+갱신 → 쿼리 수 ↑ |
| 6 | 인프라 작업 (파라미터·페일오버·리플리카 소실·패치) | 클라우드 이벤트 로그, 파라미터 변경 이력, 감사 로그 | 읽기가 프라이머리로 몰림 / 콜드 버퍼 풀 / 옵티마이저 동작 변화 |
| 7 | 캐시 무효화·만료 | 캐시 히트율, Redis 재시작·evict 지표 | 미스 → 원본 쿼리 폭증 |
| 8 | 락·긴 트랜잭션 | `innodb_trx`의 오래된 `trx_started`, History list length | undo 체인 순회 비용 → 모든 조회의 CPU ↑ (락 대기 자체는 CPU가 아님) |

외우는 요령: **"코드는 같은데 무엇이 다른가"를 여섯 방향(데이터·계획·호출자·
바닥·경로·방패)으로 돌리면 이 표가 재생된다.** 표를 통째로 외우는 것보다
§1-1의 여섯 줄에서 도출하는 편이 면접장에서 안전하다.

### 1-3. 증상 읽기 — "CPU만"이 이미 후보를 반으로 가른다

메커니즘 사슬의 첫 관문은 여기다. "DB가 느리다"가 아니라 **"DB CPU가
올랐다"**는 정보량이 큰 증상이다. DB 서버의 CPU는 무슨 일에 쓰이는가 — 버퍼 풀
안의 페이지에서 행을 찾고, 조건과 비교하고, 정렬하고, 조인 버퍼를 채우고,
해시를 만들고, MVCC 버전 체인을 따라가고, 결과를 직렬화해 보내는 데 쓰인다.
전부 **메모리 안에서 일어나는 계산**이다. 반대로 디스크에서 페이지를 기다리는
시간과 락을 기다리는 시간은 CPU를 쓰지 않는다.

| 증상 | 병목의 위치 | 판별 지표 (전후 비교) |
|---|---|---|
| user CPU ↑, `Threads_running` ↑ | 계산 — 읽는 행 수·쿼리 수·건당 연산 증가 | `Innodb_rows_read`/s, `Handler_read_rnd_next`, digest의 `SUM_ROWS_EXAMINED`, `Sort_rows`, `Created_tmp_tables` |
| iowait ↑, user CPU 낮음 | 디스크 — 버퍼 풀 밖 페이지 대기 | `Innodb_buffer_pool_reads`(물리) / `Innodb_buffer_pool_read_requests`(논리) 비율, 디스크 큐 깊이 |
| CPU 낮음, `Threads_running` ↑ | 대기 — 락 또는 외부 | `Innodb_row_lock_waits`·`Innodb_row_lock_time`, `PROCESSLIST` State의 `Waiting for …` |
| CPU 낮음, 앱 쪽 커넥션 획득 대기 ↑ | DB 밖 — 풀 크기·앱 스레드 | HikariCP pending 지표 ([connection-count 문서 §4](./15-connection-count-vs-throughput.md)) |

여기서 나오는 추론 세 가지:

1. **"CPU만 올랐다"면 디스크 병목이 아니라 계산 병목이다.** 흔히 헷갈리는
   사슬 — "데이터가 늘어 버퍼 풀을 넘쳤다 → 디스크 I/O" — 는 iowait로
   나타나지 user CPU로 나타나지 않는다. 물론 CPU 사용률 지표가
   user·system·iowait를 합산해 보여주는 대시보드라면 먼저 분해부터 해야
   한다(OS `top`, RDS Enhanced Monitoring의 `cpuUtilization.user/wait`).
   분해 결과 wait가 주범이면 후보의 무게가 데이터 증가·콜드 버퍼 풀 쪽으로,
   user가 주범이면 실행 계획·쿼리 수·긴 트랜잭션 쪽으로 이동한다.
2. **"DB CPU만" — 앱 서버 CPU는 그대로라면** 요청 총량이 늘어난 것이
   아니다(총량이 늘면 앱 CPU도 같이 오른다). 남는 것은 ⑴ 쿼리당 비용이
   올랐거나(계획·데이터·긴 트랜잭션), ⑵ 앱을 거치지 않는 발신자가
   있거나(배치·타 팀·수동 세션·리플리카 폴백), ⑶ 앱은 기다리기만 하는
   패턴(캐시 미스로 DB 호출 수만 증가)이다.
3. **락 대기는 CPU를 올리지 않는다.** "락 경합 때문에 CPU가 올랐다"는 사슬이
   틀린 이유다. 락은 후보 목록에 있지만 그 경로는 "락" 자체가 아니라 "긴
   트랜잭션 → undo 누적 → 버전 체인 순회"라는 다른 사슬로 CPU에 닿는다(§2-8).

## 2. 각 후보가 CPU로 나타나는 메커니즘 사슬

"원인 후보를 안다"와 "그 후보가 왜 CPU로 나타나는지 안다"는 다른 수준이다.
각 후보를 **변한 것 → DB 안에서 늘어난 일 → 그 일이 소비하는 자원** 세 마디로
끊어 말한다.

### 2-0. 배포 아닌 코드 경로 변경 — 플래그·원격 설정·A/B 비율

**변한 것**: 누군가 어제 feature flag를 켰거나, 원격 설정(config server)에서
페이지 크기·조회 기간·정렬 옵션을 바꿨거나, A/B 비율을 10%→50%로 올렸다.
배포 이력에는 아무것도 없다.
**늘어난 일**: 새 경로의 쿼리가 실행되기 시작하거나(digest에 어제부터
`FIRST_SEEN`인 쿼리가 나타난다), 기존 쿼리의 파라미터가 비싼 값으로
바뀐다(조회 기간 7일→90일).
**자원**: 새 쿼리가 인덱스를 못 타면 행 수 폭증 → CPU. 파라미터 변경이면
같은 digest의 `avg rows examined`만 오른다.
**확인**: 플래그 시스템의 변경 이력, config 저장소 커밋 로그 — 이 둘이 변경
타임라인(§4-1)에 안 들어가 있으면 "배포 없음"은 영원히 검증되지 않는다.

### 2-1. 데이터 증가·분포 변화

**변한 것**: 행 수가 임계를 넘었거나, 특정 키의 행 수가 튀었거나(한 대형
고객이 어제 주문 10만 건을 넣었다), 값 분포가 바뀌었다(`status='PENDING'`
비율이 1%→30%).
**늘어난 일**: 실행 계획은 그대로인데 **같은 계획이 읽는 행 수**가 늘어난다.
`WHERE user_id = ?`가 `ref`로 인덱스를 타도, 그 user의 행이 100건에서 10만
건이 되면 검사 행 수는 1,000배다. 범위 조건(`created_at > 어제`)은 하루
유입량에 정비례한다.
**자원**: 읽는 행이 버퍼 풀 안에 있으면 **CPU**(페이지 내 탐색·비교), 넘치면
**iowait**. 그리고 데이터 증가는 **임계를 넘는 순간 계단식**으로 비용이 튄다 —
정렬 대상이 `sort_buffer_size`를 넘으면 디스크 정렬(`Sort_merge_passes` ↑),
임시 테이블이 메모리 한도를 넘으면 디스크 임시 테이블(`Created_tmp_disk_tables`
↑). "어제부터 갑자기"가 완만한 증가와 양립하는 이유가 이 임계들이다.
**확인**: 테이블 행 수·크기 추이(§4-3의 일별 스냅샷), digest에서 호출 수는
같은데 `SUM_ROWS_EXAMINED/COUNT_STAR`만 오른 쿼리, 그 쿼리의 파라미터별 대상
행 수.

### 2-2. 통계 갱신 → 실행 계획 변경

**변한 것**: 옵티마이저가 보는 통계. InnoDB는 테이블 행의 일정 비율(기본 약
10%)이 바뀌면 통계를 자동 재수집하고, 그 통계는 **일부 페이지를 샘플링**해
만든다. 어제 대량 적재·삭제·상태 일괄 갱신이 있었다면 재수집이 돌았고, 샘플이
운 나쁘게 편향되면 "이 조건은 절반을 걸러낸다"에서 "거의 안 걸러낸다"로 추정이
뒤집힌다.
**늘어난 일**: 추정이 뒤집히면 옵티마이저는 **정직하게** 다른 길을 고른다 —
인덱스 대신 풀스캔, 조인 드라이빙 테이블 역전, 다른 인덱스 선택. 쿼리
텍스트는 한 글자도 안 바뀌었는데 읽는 행 수가 자릿수로 뛴다.
**자원**: 풀스캔은 순차 I/O라 디스크 관점에서는 싸지만([index-not-used-full-scan
§4](./02-index-not-used-full-scan.md)), 테이블이 버퍼 풀에 올라와 있다면 **행마다
조건을 비교하는 CPU**가 그대로 남는다. "CPU만 올랐다"에 가장 잘 맞는 후보 중
하나가 이것이다.
**확인**: 그 digest의 현재 `EXPLAIN`을 베이스라인(§4-3)과 대조. `rows` 추정과
실측이 자릿수로 다르면 통계가 범인 — 응급 처방은 `ANALYZE TABLE`. 메커니즘의
나머지(히스토그램, 샘플 페이지 수, 옵티마이저 힌트로 고정할 때의 대가)는
[실행 계획 급변 문서](./31-execution-plan-sudden-change.md)와
[explain 문서의 꼬리질문 1](./10-explain-and-slow-query-process.md)에 맡긴다.

### 2-3. 인접 배치·크론·타 팀 잡

**변한 것**: 새 잡이 등록됐거나, 기존 잡의 시간이 옮겨져 피크와 겹치거나,
잡의 처리량이 커졌거나(월말·이벤트), 타 팀이 같은 DB에 리포트 쿼리를 붙였다.
우리 배포 이력에는 없다 — 그 팀의 배포 이력에 있다.
**늘어난 일**: 배치는 본성상 **대량 스캔·집계·정렬**이다. 운영 쿼리 1만 건
분량의 행을 쿼리 한 개가 읽는다.
**자원**: 스캔·집계·정렬 자체가 CPU다. 그리고 **2차 피해** — 대량 스캔이 버퍼
풀의 뜨거운 페이지를 밀어내면(InnoDB에 완화 장치가 있어도 완전히 막지는
못한다) 배치가 끝난 뒤에도 운영 쿼리가 디스크를 다시 읽어야 해서 iowait가
뒤따른다. "배치는 새벽 3시에 끝났는데 아침까지 느렸다"의 정체다. (가산점 포인트)
**확인**: 배치 메타 테이블(Spring Batch의 `BATCH_JOB_EXECUTION`의
`START_TIME`/`END_TIME`), 크론 로그, `SHOW FULL PROCESSLIST`의 `User`/`Host` —
DB 계정을 서비스별로 분리해 두었다면 발신자가 한눈에 보이고, 전부 하나의
계정을 쓰고 있다면 이 단계에서 막힌다(§4-4). 리포트·통계 쿼리를 운영 DB에서
떼어내는 구조적 해법은 [dashboard-stats 문서](./21-dashboard-stats-oltp-olap-separation.md)의
영역이다.

### 2-4. 트래픽 구성 변화·크롤러·특정 사용자

**변한 것**: 총 RPS는 어제와 같은데 **구성**이 다르다 — 검색·필터 페이지
비중이 올랐거나, 크롤러가 목록 API를 깊은 페이지까지 훑고 있거나, 특정
사용자(대형 고객, 어뷰저, 사내 스크립트)가 대량 조회를 돌리고 있다.
**늘어난 일**: 엔드포인트마다 쿼리 비용이 10~1,000배 다르다. `LIMIT 100000, 20`은
20건을 주려고 10만 건을 읽는다([deep-pagination 문서](./13-deep-pagination-offset-vs-cursor.md)).
비싼 엔드포인트 비중이 5%→20%가 되면 총 RPS가 같아도 DB 일은 몇 배다.
**자원**: 읽는 행 수 증가 → CPU. 앱 CPU는 크게 안 오른다(앱은 20건만
직렬화한다) — "DB CPU만"과 잘 맞는다.
**확인**: 엔드포인트별 RPS와 p95, UA·IP별 요청 수, 페이지 번호 분포, 사용자별
호출 순위. APM이 있으면 "어느 엔드포인트의 DB 시간 합계가 어제 대비 가장
늘었나"가 한 번에 나온다.

### 2-5. 외부사 변경 — 웹훅 폭주·재전송 루프

**변한 것**: 결제사·물류사·메신저 등 외부 시스템이 배포했다. 이벤트 형식이
바뀌어 우리 쪽 처리가 실패 → 상대가 재전송 → 또 실패의 루프, 혹은 상대의 장애
복구로 밀렸던 이벤트가 한꺼번에 밀려온다.
**늘어난 일**: 웹훅 하나가 "주문 조회 + 상태 갱신 + 이력 INSERT" 세 쿼리라면
수신 건수에 정비례해 쿼리 수가 는다. 멱등 처리가 되어 있어도 **멱등 확인
조회**는 실행된다.
**자원**: 쿼리 수 증가형 CPU. 여기에 외부 API 응답 지연이 트랜잭션 안에 들어
있으면 §2-8의 긴 트랜잭션 사슬이 겹친다.
**확인**: 웹훅 수신 건수·실패율 그래프, 외부사 공지·상태 페이지·변경 알림 메일
— 이 채널이 변경 타임라인에 구독돼 있지 않으면 "외부사는 변경 없다"도
검증되지 않은 가설이다.

### 2-6. 인프라 작업 — 파라미터·페일오버·리플리카 소실·패치

**변한 것**: 운영팀이나 관리형 서비스가 우리 모르게 무언가를 했다. 대표 네 가지:

- **파라미터 그룹 변경**: 버퍼 풀 크기 축소(메모리 재배분), `optimizer_switch`
  변경, 정렬·임시 테이블 버퍼 축소 — 즉시 또는 재시작 후 적용.
- **페일오버·재시작**: 새 인스턴스의 **버퍼 풀은 비어 있다**(콜드 캐시). 처음
  몇 시간은 iowait가 오르고, 워밍이 끝나면 회복한다. 스탠바이가 다른
  사양이었다면 회복하지 않는다.
- **리플리카 소실**: 리플리카가 죽거나 복제 지연으로 라우팅에서 빠지면 **읽기
  트래픽 전부가 프라이머리로 온다.** 앱은 오류 없이 폴백하므로 아무도 모르고,
  프라이머리 CPU만 두 배가 된다(§5 사례). 일부 관리형 서비스는 리더가 없으면
  리더 엔드포인트를 라이터로 향하게 한다.
- **자동 마이너 패치**: 옵티마이저 동작이 미세하게 바뀌어 특정 쿼리의 계획이
  달라질 수 있다.

**자원**: 리플리카 소실은 쿼리 수 증가형 CPU, 콜드 버퍼 풀은 iowait, 파라미터
축소는 디스크 정렬·임시 테이블 증가로 CPU+I/O 혼합.
**확인**: 클라우드 이벤트 로그(RDS 이벤트: failover, configuration change,
maintenance), 파라미터 그룹 변경 이력, 감사 로그(CloudTrail의
`ModifyDBInstance`·`ModifyDBParameterGroup`·`RebootDBInstance`), 리플리카
상태·지연 지표. `SHOW GLOBAL STATUS LIKE 'Uptime'`이 하루보다 짧으면 어제 무슨
일이 있었던 것이다.

### 2-7. 캐시 무효화·만료

**변한 것**: Redis가 재시작됐거나(유지보수·OOM), 메모리 상한에 닿아 evict가
돌거나, 캐시 키 버전이 바뀌었거나, 같은 TTL로 적재된 키들이 **같은 시각에 일괄
만료**되기 시작했다(어제 예열 배치가 돈 뒤 24시간마다 동시 만료 — cache
stampede).
**늘어난 일**: 미스마다 원본 쿼리. 히트율 95%→70%면 DB로 오는 쿼리는 5%→30%,
즉 **6배**다. 앱은 캐시 대신 DB를 기다릴 뿐이라 앱 CPU는 거의 그대로다.
**자원**: 쿼리 수 증가형 CPU. 원본 쿼리가 비싼 집계였다면(캐시하는 이유가
그것이다) 건당 비용도 크다.
**확인**: 캐시 히트율 그래프의 어제 변곡점, Redis `evicted_keys`·`used_memory`·
재시작 시각, 앱 로그의 캐시 연결 오류. 재발 방지의 TTL 지터·확률적 조기 갱신은
5장 캐싱 문서의 영역이라 여기서는 후보로만 둔다.

### 2-8. 락·긴 트랜잭션 — 락 대기는 CPU가 아니고, 긴 트랜잭션은 CPU다

이 후보는 §1-3의 자원 매핑을 정확히 말하는지 보는 시험 문제다.

**락 대기**는 스레드가 잠들어 있는 상태다. `Threads_running`은 오르고 응답은
느려지지만 **CPU는 오르지 않는다.** "락 때문에 CPU가 올랐다"는 사슬이 끊겨
있다.

**긴 트랜잭션**은 다르다. 배치·수동 세션·외부 호출을 품은 트랜잭션 하나가
어제부터 열려 있으면, InnoDB의 purge가 그 트랜잭션이 볼 수도 있는 undo를
지우지 못한다 → History list length가 자란다 → 갱신이 잦은 행의 **버전 체인이
길어진다** → 그 행을 읽는 **모든** 쿼리가 자기 시점에 맞는 버전을 찾아 체인을
순회한다. 이 순회는 메모리 안의 포인터 추적이라 **순수 CPU**다. 잠긴 행이
아니라 무관한 조회까지 느려지고, 트랜잭션을 닫는 순간 회복된다. 사슬 전체는
[mvcc-innodb §3](./11-mvcc-innodb.md)에, 긴 트랜잭션을 만드는 코드 패턴과 짧게
유지하는 방법은 [long-transaction 문서](./16-long-transaction-harm-and-shortening.md)에
있다.

**확인**: `information_schema.innodb_trx`에서 `trx_started`가 오래된 행(누가
열었나 — `trx_mysql_thread_id`로 `PROCESSLIST`와 조인), `SHOW ENGINE INNODB
STATUS`의 `History list length` 추이(평소 수준 대비 수십·수백 배로 자라
있으면 확정), 앱 쪽 HikariCP의 커넥션 장기 점유 로그.

## 3. 좁혀가는 절차 — 언제부터 → 무엇이 → 왜

후보 목록이 아홉 줄이라도 전부를 순서대로 확인하지는 않는다. 세 단계가 각각
후보를 걸러낸다: **시간축이 절반을 지우고, digest 비교가 남은 것을 세 갈래로
가르고, 마지막에 하나를 확정한다.**

### 3-1. 언제부터 — 변곡점의 시각과 모양

CPU 그래프를 열어 세 가지를 읽는다. 이 단계에서는 아직 DB에 접속하지 않는다.

**⑴ 변곡점의 시각을 분 단위로.** "어제부터"가 아니라 "어제 14:17부터"여야
다음 단계에서 그 시각 전후를 비교할 수 있다.

**⑵ 곡선의 모양.**

- **계단형**(몇 분 안에 35%→80%로 뛰고 유지): 그 시각에 **이벤트**가 있었다.
  배치 시작, 플래그 토글, 파라미터 적용, 페일오버, 리플리카 이탈, 통계
  재수집, 캐시 일괄 만료. 후보 0·2·3·6·7이 남는다.
- **완만한 우상향**(며칠에 걸쳐 오르다 어제 임계를 넘음): **누적**이다. 데이터
  증가, 트래픽 증가, History list length 누적. 후보 1·4·8이 남는다.
- **주기형**(매일 같은 시각 스파이크, 어제부터 진폭이 커짐): 스케줄이 있다.
  크론·배치·동시 만료 TTL. 후보 3·7.
- **톱니형**(오르내리며 점점 상승): 재시도 루프나 큐 적체 — 후보 5.

**⑶ 같은 시간축에 변경 타임라인을 겹친다.** 배포 이력, 스키마 마이그레이션
기록(`flyway_schema_history`의 `installed_on`), 배치 실행 기록, 플래그 변경,
클라우드 이벤트, 외부사 공지, 트래픽·캐시 히트율 그래프를 **같은 화면의
세로선**으로 놓고 변곡점과 일치하는 것을 찾는다. 일치하는 세로선이 있으면
그것이 첫 번째 가설이고, 없으면 "관측되지 않는 변경"(통계 재수집, 데이터 임계
통과, 외부사)으로 무게가 옮겨간다. 이 화면이 없으면 각 팀 채널에 물어보며
반나절을 쓴다 — 그래서 §4-1이 안전망이다.

> 기동 지연 진단에서 "로그 타임스탬프 간격으로 구간을 먼저 특정"하던 것과 같은
> 원리다. 시간축을 먼저 확정하지 않고 DB에 들어가 `PROCESSLIST`부터 보는 것은
> 침묵 구간을 로그로 읽으려는 것과 같다.

### 3-2. 무엇이 — 변곡점 전후의 top SQL digest 비교

이제 DB에 들어간다. 볼 것은 "지금 느린 쿼리"가 아니라 **"변곡점 전과 후에
달라진 쿼리"**다. `performance_schema.events_statements_summary_by_digest`는
쿼리를 파라미터를 지운 패턴(digest)별로 호출 수·총 시간·검사 행 수를
누적하는데([explain 문서 §4-1](./10-explain-and-slow-query-process.md)),
**누적값**이라 그냥 조회하면 어제와 오늘이 섞인다. 그래서 스냅샷(§4-2)의
디프를 본다. 스냅샷이 없다면 차선으로 현재 값을 덤프한 뒤 `TRUNCATE`하고 10분
뒤 다시 읽어 "현재 구간"만이라도 확보한다.

디프에서 상위 쿼리를 **세 갈래**로 분류한다. 이 분류가 후보를 반으로 가른다.

| 갈래 | digest에서 보이는 모양 | 남는 후보 |
|---|---|---|
| A. 새로 나타난 쿼리 | `FIRST_SEEN`이 변곡점 이후 | 0 플래그 · 3 새 배치·타 팀 · 5 외부사 |
| B. 횟수가 급증한 쿼리 | `COUNT_STAR` ↑, 건당 시간·행 수는 그대로 | 4 트래픽 구성 · 5 웹훅 · 6 리플리카 폴백 · 7 캐시 미스 |
| C. 건당 비용이 급증한 쿼리 | `COUNT_STAR` 같음, `SUM_ROWS_EXAMINED/COUNT_STAR`·평균 시간 ↑ | 1 데이터 · 2 실행 계획 · 8 긴 트랜잭션(전 쿼리에 고루) |

```sql
-- 변곡점 전(스냅샷 s1)과 후(스냅샷 s2)의 디프 — 총 소요 시간 증가분 순
SELECT s2.digest_text,
       s2.count_star        - s1.count_star                    AS calls_delta,             -- B 갈래 판별
       (s2.sum_timer_wait   - s1.sum_timer_wait) / 1e12        AS sec_delta,
       (s2.sum_rows_examined - s1.sum_rows_examined)
         / NULLIF(s2.count_star - s1.count_star, 0)            AS rows_examined_per_call,  -- C 갈래 판별
       s2.first_seen                                           -- A 갈래 판별
FROM   ops.digest_snapshot s2
LEFT JOIN ops.digest_snapshot s1
       ON s1.digest = s2.digest AND s1.taken_at = '2026-08-30 14:00:00'
WHERE  s2.taken_at = '2026-08-30 15:00:00'
ORDER  BY sec_delta DESC
LIMIT  10;
```

읽는 법 — C 갈래인데 **모든** 쿼리의 건당 시간이 조금씩 올랐으면 개별 쿼리
문제가 아니라 전역 원인(긴 트랜잭션, 버퍼 풀 축소, 콜드 캐시, 인스턴스
사양)이고, **특정** 쿼리 하나만 자릿수로 뛰었으면 그 쿼리의 계획 또는
데이터다. B 갈래면 다음 질문은 "누가 부르나" — `SHOW FULL PROCESSLIST` 또는
`sys.session`의 `user`·`host`·`db`로 발신자를 세고, 앱이면 APM의 엔드포인트별
호출 수로 내려간다.

이 단계에서 함께 떠 두는 것: 상태 카운터 전후 비교(`Innodb_rows_read`,
`Handler_read_rnd_next`, `Created_tmp_disk_tables`, `Sort_merge_passes`,
`Threads_running`), `innodb_trx`의 오래된 트랜잭션, `Uptime`. 관리형 서비스라면
Performance Insights의 "wait event별 DB load"가 §1-3의 자원 매핑을 그래프로
대신해 준다. (가산점 포인트)

### 3-3. 왜 — 하나로 확정한다

갈래별로 마지막 확인이 다르다.

**C 갈래·특정 쿼리**: 그 쿼리의 `EXPLAIN`을 지금 뜨고 **베이스라인**(§4-3에
어제 저장된 계획)과 나란히 놓는다. `type`·`key`·`rows`가 달라졌으면 실행 계획
변경(후보 2) — `EXPLAIN ANALYZE`의 실측 행 수와 추정이 자릿수로 다르면 통계가
원인이고, `ANALYZE TABLE` 후 계획이 돌아오면 확정. 계획은 같은데 실측 행 수만
늘었으면 데이터(후보 1) — 그 파라미터의 대상 행 수와 테이블 크기 추이를 본다.

**C 갈래·전 쿼리**: `innodb_trx`의 오래된 트랜잭션과 History list length(후보
8), `Uptime`과 이벤트 로그(후보 6 페일오버·파라미터), 버퍼 풀 물리 읽기
비율(콜드 캐시).

**B 갈래**: 발신자가 앱이면 엔드포인트→UA·IP·사용자 순으로(후보 4), 웹훅
핸들러면 수신 건수와 외부사 상태(후보 5), 캐시 조회 뒤의 원본 쿼리면
히트율(후보 7), 리플리카에서 오던 읽기 쿼리가 프라이머리에 나타났으면
라우팅(후보 6).

**A 갈래**: 쿼리 텍스트가 어느 코드·어느 잡의 것인지 — 발신 계정·호스트,
플래그 변경 이력, 타 팀 배포 이력.

확정의 기준은 하나다: **"이것을 되돌리면(끄면·닫으면·재수집하면) CPU가
내려간다"를 재현하거나, 최소한 시각·크기가 정량적으로 맞는다.** 원인 쿼리의
총 소요 시간 증가분이 CPU 증가분과 크기가 비슷해야 한다. 크기가 안 맞으면
원인이 하나가 아니거나 다른 것이다.

### 3-4. 응급 조치와 그 대가 — 양면으로 말한다

원인을 확정하기 전이라도 CPU가 90%라면 무언가 해야 한다. 조치마다 **얻는 것과
잃는 것**을 한 호흡에 붙인다. 그리고 어떤 조치든 **먼저 증거를
보존**한다(`PROCESSLIST` 덤프, digest 스냅샷, `innodb_trx`, `SHOW ENGINE INNODB
STATUS`) — 조치가 성공하면 증거도 사라진다.

| 조치 | 얻는 것 | 잃는 것 |
|---|---|---|
| 원인 세션 `KILL` | 즉시 부하 제거 | 큰 갱신이었다면 **롤백이 실행만큼 오래** 걸리고 그동안 부하는 계속. 배치라면 재실행 계획 필요 |
| 배치·크론 일시 중지 | 즉시 부하 제거 | 그 배치의 SLA(정산·리포트 지연), 밀린 처리량이 재개 시 몰림 |
| `ANALYZE TABLE` | 통계 원인이면 계획이 즉시 복귀 | 원인이 통계가 아니면 무효. 샘플이 다시 편향될 수 있어 근본 대책은 아님 |
| 인덱스 힌트·옵티마이저 힌트 | 특정 쿼리의 계획을 고정 | 데이터가 바뀌어도 계획이 안 바뀌는 **경직**. 코드 배포가 필요 |
| 캐시 TTL 연장·예열 | 미스형이면 DB 호출 수 즉시 감소 | 데이터 신선도 저하, 예열 자체가 DB 부하 |
| 특정 발신자 rate limit·차단 | 크롤러·어뷰저형이면 즉시 효과 | 정상 사용자 오탐, 외부사면 계약 문제 |
| 리플리카 추가·읽기 분리 | 프라이머리 CPU를 구조적으로 나눔 | 복제 지연에 따른 stale read, 비용, 라우팅 코드 |
| 인스턴스 스케일업 | 근본 원인 무관하게 여유 확보 | 재시작·페일오버를 동반하면 **콜드 버퍼 풀로 일시 악화**, 비용, 원인을 덮어 재발 |

"스케일업하면 되죠"가 왜 부족한 답인지 — 원인을 덮을 뿐 아니라 재시작을
동반하면 몇 시간 동안 더 나빠질 수 있고, 데이터 증가·트래픽 구성처럼 계속
커지는 원인이면 다음 달에 같은 자리로 돌아온다. 응급 조치는 "시간을
산다"이지 "해결"이 아니다.

## 4. 안전망 고정 — 검증을 사람의 기억에서 시스템으로

§3의 절차가 훌륭해도 그 입력(변경 타임라인, 전후 스냅샷, 베이스라인)이
**미리** 쌓여 있지 않으면 장애 당일에는 쓸 수 없다. "다음에는 이렇게 하자"를
사람이 기억하는 대신 잡과 파이프라인이 기억하게 만드는 네 가지.

### 4-1. 변경 타임라인 — 모든 변경을 하나의 어노테이션 스트림으로

```yaml
# ❌ before: 장애 당일 각 채널에 묻는다
#   "어제 배포하신 분?" / "인프라팀, 어제 뭐 하셨어요?" / "배치 새로 등록된 거 있나요?"
#   → 답이 오는 데 반나절, 오지 않는 답(외부사·플래그·통계 재수집)은 영원히 공백

# ✅ after: 변경을 만드는 모든 통로가 같은 어노테이션 저장소에 이벤트를 남기고,
#           대시보드가 세로선으로 겹쳐 그린다
# 1) 배포 파이프라인 마지막 스텝
- name: annotate-deploy
  run: |
    curl -X POST "$GRAFANA/api/annotations" -H "Authorization: Bearer $TOKEN" \
      -d "{\"tags\":[\"deploy\",\"order-api\"],\"text\":\"$GIT_SHA by $ACTOR\"}"
# 2) 스키마 마이그레이션: flyway_schema_history / DATABASECHANGELOG 를 주기 수집 → 같은 저장소
# 3) 배치: BATCH_JOB_EXECUTION 의 START_TIME/END_TIME 을 주기 수집 → 같은 저장소 (잡 이름 태그)
# 4) 인프라: 클라우드 이벤트(failover·parameter change·maintenance) 구독 → 같은 저장소
# 5) 플래그·원격 설정: 변경 웹훅 → 같은 저장소
# 6) 외부사: 상태 페이지·변경 공지 RSS/웹훅 → 같은 저장소 (태그 vendor:pg)
```

핵심은 도구가 아니라 원칙이다 — **변경을 만들 수 있는 통로마다 "기록을 남기는
것"이 통로의 일부**여야 한다. 사람이 "기록해야지"라고 기억하는 통로가 하나라도
남아 있으면 그 통로가 다음 장애의 원인이 된다.

### 4-2. digest 스냅샷 잡 — "어제와 오늘"을 비교 가능하게

```sql
-- ❌ before: 장애 당일 누적 테이블을 그냥 읽는다
--            → 어제 정상 구간까지 합산돼 급증한 쿼리가 묻힌다
SELECT digest_text, count_star, sum_timer_wait
FROM performance_schema.events_statements_summary_by_digest
ORDER BY sum_timer_wait DESC LIMIT 10;

-- ✅ after: 주기(예: 10분)로 스냅샷을 남기고 §3-2 디프 쿼리로 구간 비교
CREATE TABLE ops.digest_snapshot (
  taken_at                    DATETIME        NOT NULL,
  digest                      VARCHAR(64)     NOT NULL,
  digest_text                 LONGTEXT,
  count_star                  BIGINT UNSIGNED,
  sum_timer_wait              BIGINT UNSIGNED,
  sum_rows_examined           BIGINT UNSIGNED,
  sum_rows_sent               BIGINT UNSIGNED,
  sum_created_tmp_disk_tables BIGINT UNSIGNED,
  first_seen                  TIMESTAMP(6),
  PRIMARY KEY (taken_at, digest)
);
-- 이벤트 스케줄러 또는 외부 크론에서:
INSERT INTO ops.digest_snapshot
SELECT NOW(), DIGEST, DIGEST_TEXT, COUNT_STAR, SUM_TIMER_WAIT,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT, SUM_CREATED_TMP_DISK_TABLES, FIRST_SEEN
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'order';   -- 보존 기간은 별도 정리 잡으로 관리
```

알아둘 성질 세 가지: ⑴ 누적값은 **DB 재시작 시 초기화**된다 — 스냅샷 디프가
음수면 그 사이 재시작이 있었다는 뜻이고, 그 자체가 후보 6의 단서다. ⑵ digest
테이블에는 **행 수 상한**이 있어 상한을 넘은 새 패턴은 `DIGEST`가 `NULL`인 한
행에 뭉쳐 집계된다 — 그 행이 급증하면 "새 쿼리 패턴이 대량으로 생겼다"는
신호(ORM이 `IN (?, ?, ?, …)` 길이별로 다른 digest를 만드는 경우가 흔한 원인).
⑶ 관리형 서비스의 Performance Insights나 `pt-query-digest` 일일 리포트가 이
잡을 대신할 수 있다 — 무엇이든 "전후 비교가 가능한 형태로 남는가"가 기준이다.

### 4-3. 실행 계획 베이스라인 + 테이블 크기 스냅샷

```bash
# ✅ 매일 새벽 (의사 코드): 총 비용 상위 N개 digest의 대표 쿼리를 EXPLAIN FORMAT=JSON 으로
#    저장하고 전일과 diff. 비용 숫자는 매일 조금씩 달라지므로 access_type·key·rows 만 추출해 비교
for q in "${TOP_QUERIES[@]}"; do
  mysql -e "EXPLAIN FORMAT=JSON $q" \
    | jq '.. | objects | select(has("access_type")) | {table: .table_name, access_type, key, rows: .rows_examined_per_scan}' \
    > "plans/$(date +%F)/$(echo -n "$q" | sha1sum | cut -c1-12).json"
done
diff -rq "plans/$(date -v-1d +%F)" "plans/$(date +%F)" \
  | grep differ && notify "#db-alerts" "실행 계획 변경 감지 — 목록 첨부"
```

MySQL에는 계획을 고정하는 내장 베이스라인 기능이 없으므로 **"바뀌었다"를
사람이 아니라 잡이 발견**하게 하는 것이 현실적 목표다. §3-3에서 "베이스라인과
대조"가 가능한 것은 이 잡이 어제 계획을 남겨 두었기 때문이다. 같은 잡에
`information_schema.tables`의 `table_rows`·`data_length`·`index_length`를
일별로 적재해 두면 후보 1(데이터 증가)의 "어제 임계를 넘었나"가 그래프로
보인다. CI 단계에서의 `EXPLAIN` 단정은 [explain 문서 §4-4 층 2](./10-explain-and-slow-query-process.md)와
같은 도구다.

### 4-4. 증상 → 자원 지표 알람 세트, 그리고 발신자 식별

§1-3의 표를 알람으로 옮긴다: `Threads_running`(실행 중 스레드 급증),
`Innodb_rows_read`/s(읽는 행 수 급증 — CPU의 선행 지표), 버퍼 풀 물리 읽기
비율(콜드 캐시·버퍼 풀 초과), History list length(긴 트랜잭션), 캐시 히트율,
리플리카 지연·상태, `Created_tmp_disk_tables`/s. CPU 알람 하나만 있으면
"올랐다"는 알지만 "무엇이"는 모른다 — 지표를 자원별로 나눠 두면 알람 조합이
§1-3의 판별을 대신한다.

그리고 **DB 계정을 발신자별로 분리**한다 — 서비스별 계정, 배치 전용 계정,
사람 전용 계정. §3-2의 "누가 부르나"가 `PROCESSLIST` 한 번으로 끝나느냐,
커넥션 IP를 역추적하느냐가 여기서 갈린다.

## 5. 실무 사례 — 리플리카가 조용히 사라진 날

**증상**: 화요일 아침 알람. 프라이머리 CPU가 월요일 14:17부터 38%→81%로
**계단형** 상승 후 유지. 앱 서버 CPU·RPS는 평소와 같음. 배포 파이프라인 이력:
마지막 배포는 금요일.

**① 언제부터**: 변곡점 14:17, 계단형 → 이벤트형 후보(0·2·3·6·7)로 압축. 변경
타임라인을 겹치니 14:16에 클라우드 이벤트 세로선 — "read replica: instance
restarted (maintenance)". 배포·플래그·배치·마이그레이션 세로선은 없음. 첫
가설: 후보 6.

**② 무엇이**: digest 스냅샷 14:00 vs 15:00 디프. 상위 8개가 전부 **B 갈래** —
`SELECT … FROM episode WHERE series_id = ?`, `SELECT … FROM comment WHERE
episode_id = ? ORDER BY id DESC LIMIT ?` 등 읽기 전용 쿼리의 `COUNT_STAR`가
프라이머리에서 2.1배, 건당 시간·행 수는 동일. 새 쿼리(A)도, 건당 비용
급증(C)도 없음. `PROCESSLIST`의 발신 계정은 평소 리플리카에 붙던 `webtoon_ro`
— 프라이머리에 나타나 있음. 리플리카 지표: 14:16 이후 커넥션 0.

**③ 왜**: 리플리카가 유지보수로 재시작 → 복제 재동기화에 시간이 걸리며 지연이
임계를 넘음 → 앱의 라우팅 데이터소스가 "리플리카 비정상"으로 판정하고
**조용히 프라이머리로 폴백** → 리플리카는 복구됐지만 앱 쪽 헬스체크가
재편입을 시도하지 않는 구현이라 폴백 상태가 유지됨. 크기 검증: 읽기 쿼리 총
소요 시간 증가분이 CPU 증가분과 비례.

**응급 조치와 대가**: 앱 인스턴스 롤링 재시작으로 라우팅 초기화(수 분의 배포와
같은 위험, 그러나 코드 변경 없음) vs 리플리카 추가(수십 분, 비용). 전자를
택하고 5분 내 CPU 복귀.

**안전망으로 고정한 것**: ⑴ 폴백은 **시끄럽게** — 라우팅 데이터소스가
프라이머리로 폴백하는 순간 메트릭과 알람. 조용한 폴백은 가용성을 지키는 대신
장애를 숨긴다는 트레이드오프가 있었고, 가용성은 유지하되 알람을 붙이는 쪽으로
양면을 취함. ⑵ 리플리카 재편입을 주기 헬스체크로 자동화. ⑶ 클라우드 이벤트가
변경 타임라인에 이미 들어와 있었기에 ①이 5분에 끝났음을 회고에 기록 — 없었다면
"인프라팀 어제 뭐 하셨어요?"에서 시작했을 것.

```java
// ❌ before: 조용한 폴백 — 가용성은 지키지만 아무도 모른다
@Override
protected Object determineCurrentLookupKey() {
    if (isReadOnlyTx() && replicaHealthy) return "replica";
    return "primary";                       // 폴백 사실이 어디에도 남지 않는다
}

// ✅ after: 폴백은 유지하되 관측 가능하게, 그리고 재편입을 시도한다
@Override
protected Object determineCurrentLookupKey() {
    if (isReadOnlyTx()) {
        if (replicaHealth.isHealthy()) return "replica";
        fallbackCounter.increment();        // 메트릭 → 알람 (지속 1분이면 페이지)
        replicaHealth.scheduleRecheck();    // 복구 시 자동 재편입
    }
    return "primary";
}
```

같은 절차를 후보 2(통계 갱신)에 적용한 사례는 C 갈래·특정 쿼리로 시작해
`EXPLAIN` 대조 → `ANALYZE TABLE`로 끝나는데, 그 사례와 재발 방지(히스토그램·
배치 후 통계 재수집 스텝)는 [실행 계획 급변 문서](./31-execution-plan-sudden-change.md)에서
이어진다.

## 6. 꼬리질문 대비 포인트

### "CPU는 올랐는데 slow query log에는 아무것도 안 잡힙니다. 왜 그럴 수 있고, 어디를 보나요?"

slow query log는 **건당 실행 시간**이 `long_query_time`을 넘는 쿼리만
기록한다. CPU를 올리는 가장 흔한 패턴 — 건당 20ms인 쿼리가 초당 5,000번(캐시
미스, 크롤러, N+1, 리플리카 폴백) — 은 한 건도 임계를 안 넘는다. 그래서 §3-2의
B 갈래는 slow log가 아니라 digest의 `COUNT_STAR × 평균 시간`으로만 보인다.
보조로 `long_query_time`을 0에 가깝게 낮추되 `min_examined_row_limit`으로
"많이 읽은 것만" 남기거나 `log_queries_not_using_indexes`를 켜면 "빠르지만
많이 읽는" 쿼리를 잡을 수 있지만, 로그량이 급증해 디스크와 I/O를 먹는다는
대가가 있다. 결론: "slow log에 없다"는 "느린 쿼리가 없다"가 아니라 "건당은
빠르다"는 정보이고, 그 자체가 B 갈래를 가리키는 단서다.

### "CPU 상승, I/O 대기, 락 대기를 지표만으로 어떻게 구분하나요?"

§1-3의 표를 말로 풀면 된다. user CPU와 `Threads_running`이 함께 오르면
**계산**(읽는 행 수·쿼리 수·정렬). user CPU는 낮은데 iowait와
`Innodb_buffer_pool_reads`(물리 읽기)가 오르면 **디스크**(버퍼 풀 초과, 콜드
캐시, 대량 스캔의 오염). CPU도 iowait도 낮은데 `Threads_running`과
`Innodb_row_lock_waits`가 오르고 `PROCESSLIST` State가 `Waiting for …`면
**락**. 셋 다 낮은데 앱만 느리면 DB 밖(커넥션 풀, 네트워크, 앱 스레드). 이
구분이 되어야 "CPU가 올랐으니 인덱스를 보자"와 "iowait가 올랐으니 버퍼 풀과
배치를 보자"가 갈린다 — 같은 "DB가 느리다"에서 정반대의 첫 행동이 나온다.

### "원인을 찾기 전에 당장 CPU를 내려야 한다면 무엇을 하고, 그 대가는 무엇인가요?" (시니어 변별 포인트)

순서가 답이다. ⑴ **증거 보존** — `PROCESSLIST`·`innodb_trx`·digest 스냅샷·`SHOW
ENGINE INNODB STATUS`를 파일로 뜬다. 조치가 성공하면 증거는 사라지고 재발
방지가 불가능해진다. ⑵ **가역적이고 국소적인 조치부터** — 발신자가 특정되면
그 배치 중지·그 IP 제한, 오래된 트랜잭션이면 `KILL`(단, 큰 갱신의 롤백은
실행만큼 오래 걸려 부하가 이어질 수 있음), 계획 문제로 보이면 `ANALYZE TABLE`.
⑶ **전역 조치는 마지막** — 스케일업은 재시작·페일오버를 동반하면 콜드 버퍼
풀로 몇 시간 더 나빠질 수 있고, 원인을 덮어 다음 달 같은 자리로 돌아온다. 각
조치의 대가는 §3-4 표 그대로. 면접관이 듣고 싶은 문장은 "응급 조치는 시간을
사는 것이고, 무엇을 샀는지와 무엇을 지불했는지를 회고에 적는다"이다.

### "performance_schema는 누적값인데 '어제와 오늘'을 어떻게 비교하나요? 운영 DB에서 켜두는 비용은요?" (시니어 변별 포인트)

누적값은 그 자체로는 구간 비교가 안 되므로 **주기 스냅샷의 디프**(§4-2)나
관리형 서비스의 Performance Insights, `pt-query-digest` 일일 리포트처럼
**"전후"가 남는 형태**가 필요하다. 없을 때의 차선은 현재 값을 덤프한 뒤
`TRUNCATE`하고 일정 시간 뒤 다시 읽어 현재 구간만 확보하는 것 — 단 이 순간
과거는 영구히 사라지므로 덤프가 먼저다. 성질로는 재시작 시 초기화(디프가
음수면 재시작 단서)와 digest 행 수 상한(`NULL` digest 행의 급증 = 새 패턴
폭증) 두 가지를 알아야 한다. 비용은 트레이드오프다: statement 단위 계측은
일반적으로 감수할 만한 오버헤드지만, 모든 instrument·consumer를 켜면 부하가
눈에 띄게 늘고, 반대로 아예 끄면 §3-2 전체를 잃는다. "기본 statement digest는
켜 두고, 더 세밀한 계측은 장애 시 잠깐 켠다"가 균형점이다.

### "'변경 없음'을 사람에게 묻지 않고 확인하려면 팀에 무엇이 갖춰져 있어야 하나요?" (시니어 변별 포인트)

§4를 우선순위로 답한다. ⑴ **변경 타임라인** — 배포·스키마·배치·플래그·인프라
이벤트·외부사 공지가 한 저장소에 어노테이션으로 들어오고 대시보드에
세로선으로 겹쳐 보이는 것. 이것이 없으면 §3-1이 성립하지 않는다. ⑵ **digest
스냅샷 잡** — 전후 비교의 재료. ⑶ **실행 계획·테이블 크기 일별 스냅샷** —
"관측되지 않는 변경"(통계·데이터 임계)을 관측 가능하게 만드는 것. ⑷ **발신자
식별** — 서비스·배치·사람별 DB 계정 분리. 그리고 이 네 가지는 기능 개발이
아니라 **다음 장애의 진단 시간을 반나절에서 5분으로 줄이는 투자**라는
프레임으로 팀을 설득한다 — 시니어 변별은 도구 목록이 아니라 "이 투자가 언제
회수되는가"를 말할 수 있는지에 있다.

## 한 줄 요약

"배포 없음"은 코드가 안 바뀌었다는 말일 뿐이라 시스템의 변경(데이터·계획·
호출자·바닥·경로·방패)을 변경 타임라인으로 먼저 검증하고, 좁히기는
**언제부터**(변곡점의 시각과 모양) → **무엇이**(전후 digest 비교를 새
쿼리·횟수 급증·건당 비용 급증 세 갈래로) → **왜**(계획 베이스라인 대조·발신자
추적)의 순서로 — "CPU만"은 계산 병목이라 디스크(iowait)·락(`Threads_running`만)과
구분되고, 이 절차의 입력(타임라인·스냅샷·베이스라인)은 장애 전에 시스템이 쌓아
두어야 장애 당일에 쓸 수 있다.
