# 복합 인덱스 컬럼 순서 — "카디널리티 높은 컬럼 먼저"는 1순위 규칙이 아니라 3순위 기준이다

> 핵심 관전 포인트: **복합 인덱스 `(A, B, C)`는 "A로 정렬하고, A가 같은
> 것끼리만 B로, B까지 같은 것끼리만 C로" 정렬된 **하나의 트리**다. 그래서
> 컬럼 순서는 "플래너가 리프에서 **얼마나 좁은 연속 구간 하나**를 찍을 수
> 있는가"를 결정한다. 순서 결정 원칙은 셋 — ① **등호(`=`) 조건 컬럼을 앞에,
> 범위 조건(`>`, `<`, `BETWEEN`, `LIKE 'x%'`)은 맨 뒤에** (범위 뒤 컬럼은
> 정렬이 깨져 탐색 조건으로 못 쓴다) ② **등호 컬럼끼리는 "더 많은 쿼리가
> 접두사로 재사용하는 컬럼"을 앞에**, 그 다음에야 카디널리티 높은 쪽을 앞에
> ③ 범위·정렬 컬럼 뒤에는 커버링용 컬럼. **카디널리티는 ②의 타이브레이커**일
> 뿐이고, "이 인덱스를 탈지 말지"는 개별 컬럼이 아니라 **컬럼 조합의
> 선택도**(랜덤 vs 순차 I/O 손익분기)가 정한다. 순서가 틀리면 뒤 컬럼 조건이
> 구간을 못 좁혀 **스캔 폭이 자릿수로 커지는데** — PostgreSQL 계획에는
> 강등된 조건도 멀쩡히 `Index Cond`로 찍혀서 **겉으로는 구분이 안 된다.
> 판별 도구는 계획 텍스트가 아니라 `EXPLAIN (ANALYZE, BUFFERS)`의 읽은
> 페이지 수다.**

## 0. 질문 + 의도

**질문**: "복합 인덱스의 컬럼 순서는 어떤 기준으로 정하나요? 카디널리티와의
관계는?"

관련 질문:
"커버링 인덱스란? 어떤 상황에서 효과가 큰가요?"
"ORDER BY가 인덱스를 타는 조건은? 정렬(Sort)은 언제 발생하고 왜 문제가 되나요?"

**출제 의도**: rationale의 표현 그대로 — "인덱스를 **'거는' 것과 '설계하는'
것의 차이**가 여기서 갈린다. 등호 조건 먼저·범위 조건 뒤 같은 원칙을 **쿼리
패턴에서 도출**할 수 있어야, 테이블당 인덱스 수를 늘리지 않으면서 여러 쿼리를
커버하는 설계가 가능하다." 즉 "카디널리티 높은 컬럼을 앞에"라는 격언을 외웠는지가
아니라, **쿼리 조건을 등호/범위/정렬로 분류해 순서를 스스로 조립하고, 그 순서가
I/O 비용으로 어떻게 번지는지**를 말할 수 있는지를 본다. 앞 문항들이 "구조를
아는가"([B+Tree](01-index-and-bplus-tree.md)) → "구조로 현상을 설명하는가"
([풀스캔 원인 6종](02-index-not-used-full-scan.md))였다면, 이 문항은 **"구조로
설계하는가"**다.

> 이 문서는 기본 Q1·Q2에서 **두 번 연속 비어 있던 축 — 선택도(카디널리티)와
> 복합 인덱스 선두 컬럼 규칙** — 을 정면으로 다룬다. 앞 문서들에서 "선두 컬럼이
> 빠지면 인덱스가 없는 것과 같다"(leftmost prefix)까지는 정리됐으니, 여기서는
> **"그럼 선두에 무엇을 둘 것인가"**부터 시작한다.

## 1. 한 문장 원리 — 복합 인덱스는 "사전 안의 사전"이다

```text
(status, created_at) 인덱스의 리프 — status로 정렬, status가 같은 것끼리만 created_at 정렬
  ┌ DONE ──────────────────────┐┌ FAILED ───────────┐┌ PAID ──────────────────────────┐
  │ 08-01 │ 08-01 │ 08-02 │ ...││ 07-30 │ 08-01 │...││ 08-01 │ 08-01 │ 08-02 │ 08-02 │...│
  └────────────────────────────┘└───────────────────┘└────────────────────────────────┘
  → "status = 'FAILED' AND created_at >= 08-01" : FAILED 칸으로 점프 → 그 안에서
    08-01 지점을 찍고 오른쪽 끝까지. ★ 연속 구간 하나 ★

(created_at, status) 인덱스의 리프 — created_at으로 정렬, 같은 시각끼리만 status 정렬
  ┌ 07-30 ─┐┌ 08-01 ───────────────────────────┐┌ 08-02 ───────────────────┐
  │ FAILED ││ DONE │ DONE │ FAILED │ PAID │ PAID││ DONE │ PAID │ PAID │ ... │
  └────────┘└──────────────────────────────────┘└──────────────────────────┘
  → 같은 조건: 08-01 지점부터 오른쪽 끝까지 **전부** 훑으며 FAILED만 골라낸다.
    FAILED가 어디 있을지 미리 알 수 없다 — 시각마다 흩어져 있으므로.
```

전화번호부가 "성 → 이름" 순인 것과 같다. 성이 같은 사람들 안에서만 이름이
정렬돼 있지, 책 전체가 이름순은 아니다. 이 한 문장에서 순서 원칙이 전부 나온다:

> **앞 컬럼의 값이 하나로 고정돼야, 그 안에서 뒤 컬럼의 정렬이 살아 있다.**

앞 컬럼이 **등호**(`status = 'FAILED'`)면 값이 하나로 고정된다 → 뒤 컬럼
정렬이 살아 있다 → 뒤 컬럼으로도 구간을 좁힐 수 있다.
앞 컬럼이 **범위**(`created_at >= 08-01`)면 값이 여러 개에 걸친다 → 각 값마다
뒤 컬럼 정렬이 따로 논다 → 뒤 컬럼은 구간을 좁히는 데 못 쓰고, 훑으면서
**걸러내는** 데만 쓴다.

### 1-1. 용어 고정 — "접두사"와 "재사용"

**접두사(prefix)** = 인덱스 컬럼 목록의 **왼쪽부터 끊기지 않고 이어지는
조각**.

```text
(user_id, status, created_at) 인덱스의 접두사는 딱 셋:
  (user_id) ✅   (user_id, status) ✅   (user_id, status, created_at) ✅

접두사가 아닌 것 — 왼쪽이 빠졌거나 중간이 끊겼다:
  (status) ❌   (created_at) ❌   (status, created_at) ❌   (user_id, created_at) ❌
```

왼쪽부터만인 이유는 위 그림 그대로다 — 뒤 컬럼의 정렬은 **앞 컬럼이 고정된
안에서만** 살아 있으므로, 앞 컬럼 조건이 빠지면 구간을 찍을 수 없다. 그래서
**인덱스 1개는 사실상 "접두사 개수만큼의 인덱스"**다.
`(user_id, status, created_at)` 하나가 `(user_id)` 인덱스, `(user_id,
status)` 인덱스 노릇까지 겸한다.

**재사용** = 여러 쿼리가 이 접두사들을 **나눠 쓰게** 만드는 것. 인덱스는
개수만큼 쓰기(INSERT/UPDATE) 비용이 붙으므로, 선두 컬럼을 잘 고르면 인덱스
하나로 여러 쿼리를 태울 수 있다 — 2-2의 순서 결정 기준이 바로 이것이다.

> **접두사 재사용 vs 카디널리티, 관계 한 줄 (암기)** — **접두사 재사용은
> "이 인덱스를 몇 개의 쿼리가 탈 수 있나"(커버 범위)를 정하고, 카디널리티는
> "그 접두사로 탔을 때 얼마나 좁혀지나"(효율)를 정한다.** 커버 범위가 먼저고,
> 둘 다 탈 수 있어 우열이 안 갈릴 때 효율로 타이브레이크한다.

*(PostgreSQL 각주: PG의 복합 B-tree는 선두 컬럼 조건이 없어도 "인덱스 전체를
훑는 식으로" 쓸 수는 있다 — 하지만 구간을 못 좁히므로 플래너가 대개 Seq
Scan을 고른다. "못 탄다"가 아니라 "타 봐야 손해"라 결론은 같다.)*

## 2. 순서 결정 3원칙 — "등 · 범 · 정 · 커"로 외운다

조건을 세 바구니로 나눈 뒤 순서대로 배치한다. 암기용 네 글자:
**등**호 → **범**위 → **정**렬 → **커**버링.

| 순위 | 원칙 | 왜 |
|---|---|---|
| ① | **등호 조건 컬럼을 앞에, 범위 조건은 맨 뒤(하나만)** | 범위 뒤 컬럼은 정렬이 깨져 탐색에 못 쓴다 |
| ② | **등호 컬럼끼리는 "접두사 재사용" 우선, 그다음 카디널리티** | 같은 쿼리 안에서는 등호끼리 순서를 바꿔도 최종 구간이 같다 |
| ③ | **범위/정렬 컬럼 뒤에 커버링용 컬럼** | 탐색엔 못 쓰지만 힙 방문(북마크 룩업)을 없앤다 |

### 2-1. 원칙 ① — 등호 먼저, 범위는 맨 뒤: 비용 사슬로 말하기

여기가 후보자가 "성능 저하"·"느려짐"에서 멈추던 지점이다. 이름을 붙여 사슬로
말한다. 먼저 용어 셋 —

- **액세스 조건(access predicate)**: 인덱스 트리를 내려가 **시작점·끝점을
  찍는 데** 쓰이는 조건. 스캔 폭을 실제로 줄인다.
- **인덱스 내 검사(in-index filter)**: 구간은 못 좁히지만, 훑는 **인덱스
  엔트리 단계에서** 하나씩 검사해 걸러내는 조건. 힙 방문은 막아 주지만 스캔
  폭은 못 줄인다. **PostgreSQL 계획에서는 이것도 액세스 조건과 함께
  `Index Cond:`에 찍힌다** — 겉으로 구분이 안 되는 이유.
- **필터 조건(`Filter:`)**: 인덱스에 없는 컬럼의 조건. **힙에서 행을 가져온
  뒤에야** 검사해 버린다 — 버릴 행에 힙 랜덤 I/O를 이미 지불한 상태.
  `Rows Removed by Filter: N`이 그 낭비의 계산서다.

```sql
-- 쿼리: 최근 1시간 안에 실패한 주문을 모아 알림을 보내는 배치
SELECT id, user_id, amount
FROM orders
WHERE status = 'FAILED'
  AND created_at >= now() - interval '1 hour';

-- ❌ before: "created_at이 카디널리티가 훨씬 높으니 앞에" 라고 정한 순서
CREATE INDEX idx_orders_created_status ON orders (created_at, status);
-- EXPLAIN (ANALYZE, BUFFERS)
--  Index Scan using idx_orders_created_status on orders
--    Index Cond: ((created_at >= …) AND (status = 'FAILED'))
--    (actual rows=3000)              ← 결과 행 수는 after와 똑같다!
--    Buffers: shared hit=1873        ← 1시간치 30만 엔트리를 훑은 흔적
-- status가 Index Cond에 찍혀 있지만 구간을 좁히지 못했다 — 30만 엔트리를
-- 훑으며 인덱스 안에서 하나씩 걸러 3천 건만 남긴 것. 스캔 폭 100배.

-- ✅ after: 등호(status) 먼저, 범위(created_at) 뒤
CREATE INDEX idx_orders_status_created ON orders (status, created_at);
-- EXPLAIN (ANALYZE, BUFFERS)
--  Index Scan using idx_orders_status_created on orders
--    Index Cond: ((status = 'FAILED') AND (created_at >= …))
--    (actual rows=3000)
--    Buffers: shared hit=42          ← FAILED 칸 안의 1시간치 구간만
```

**함정 — 두 계획의 텍스트가 사실상 같다.** `Index Cond`도, `actual rows`도
같다. PostgreSQL은 인덱스 컬럼에 대한 조건을 구간을 좁히든 못 좁히든 전부
`Index Cond`에 찍기 때문이다(못 좁히는 키는 인덱스 안에서 검사 — MySQL이
ICP라고 따로 부르는 동작이 PG에는 기본 내장). 그래서 **강등 여부는 계획
텍스트가 아니라 ① 인덱스 정의의 선두 컬럼과 조건의 등호/범위를 대조하거나
② `BUFFERS`의 읽은 페이지 수로** 판별한다 — 위 예시에서 1873 vs 42.

**순서가 틀렸을 때 비용 사슬 — 5고리 (암기)**

> 순서 오류 → ① 뒤 컬럼 조건이 **액세스 조건에서 "인덱스 내 검사"로 강등**
> (계획엔 둘 다 `Index Cond` — 겉으로 안 보인다) → ② 인덱스 **스캔 구간
> 폭↑** (리프 페이지를 자릿수로 더 읽는다 — 리프는 연결 리스트라 순차
> 읽기이므로 이것만은 그나마 싸다) → ③ 인덱스 안에서 걸러진 엔트리는 힙
> 방문 없이 버려지니 여기까진 버티지만, **조건 컬럼이 인덱스에 없으면**
> (`Filter`) 버릴 행에도 **힙 랜덤 I/O를 먼저** 지불한다
> (`Rows Removed by Filter`가 그 계산서) → ④ 그 인덱스·힙 페이지들이
> **shared buffers를 채워** 정작 필요한 페이지를 밀어낸다(오염) →
> ⑤ 다른 쿼리의 캐시 미스↑.

②와 ③의 차이가 곧 [Q2 문서 §4](02-index-not-used-full-scan.md)의 **순차 vs
랜덤 I/O**다. 30만 엔트리를 순차로 훑는 것(②)보다 그중 수만 건에 대해 흩어진
힙 페이지를 찌르는 것(③)이 훨씬 비싸다. 그래서 걸러낼 조건은 최소한
인덱스 안에는 있어야(③ 방어) 하고, 애초에 구간을 좁히는 것(②까지 방어)이
설계다.

**(가산점 포인트) 같은 실수가 MySQL(InnoDB)에서는 락 사고로도 번진다 —
PG와의 대조.** InnoDB는 `UPDATE … WHERE status = 'FAILED' AND created_at
>= ?` 같은 쿼리에서 **훑은 인덱스 레코드에 락을 건다** — 스캔 폭 100배 =
락 범위 100배 → 같은 구간을 만지는 트랜잭션 대기 → 커넥션 풀 고갈.
**PostgreSQL은 훑은 행이 아니라 실제로 수정하는(또는 `FOR UPDATE`로
반환되는) 행에만 락을 건다** — 스캔 폭이 락 범위로 직결되진 않는다. 대신
PG에서 스캔 폭 실수는 **트랜잭션 장기화**로 번진다: 그만큼 락 보유 시간이
길어지고, 오래 열린 트랜잭션은 VACUUM이 죽은 튜플을 치우지 못하게 막아
(블로트) 무관한 테이블 성능까지 끌어내린다. "인덱스 순서 실수"가 성능
문제를 넘어 운영 사고가 되는 경로다.

### 2-2. 원칙 ② — 등호 컬럼끼리: 접두사 재사용이 먼저, 카디널리티는 그다음

같은 쿼리 안에서 등호 컬럼끼리는 **순서를 바꿔도 최종 구간이 같다.**
`user_id = 100 AND status = 'PAID'`는 `(user_id, status)`든 `(status, user_id)`든
결국 "user 100의 PAID 칸"이라는 **동일한 리프 구간**에 도달한다. 카디널리티
격언이 여기서 무력한 이유다. 그럼 무엇으로 정하나 — **이 인덱스의 접두사만
쓰는 다른 쿼리들**이다.

```sql
-- 이 테이블을 치는 뜨거운 쿼리 셋
-- (a) 내 주문 중 상태별 목록: WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20
-- (b) 내 주문 전체 최근순  : WHERE user_id = ?                ORDER BY created_at DESC LIMIT 20
-- (c) 실패 주문 알림 배치  : WHERE status = 'FAILED' AND created_at >= ?

-- ❌ before: "status가 등호니까 아무 데나" → (status, user_id, created_at)
CREATE INDEX idx_orders_status_user_created ON orders (status, user_id, created_at);
--   (a) ✅ 완전 커버 — 등호 둘 다 액세스 조건, created_at 정렬까지
--   (b) ❌ 선두 status 조건이 없다 → 구간을 못 찍어 플래너가 버린다(Seq Scan행)
--   (c) △ status까지만 구간, created_at은 인덱스 내 검사로 강등(스캔 폭 = FAILED 전체)

-- ✅ after: 접두사 재사용 기준 — (a)(b)가 공유하는 user_id를 선두로
CREATE INDEX idx_orders_user_status_created ON orders (user_id, status, created_at);
--   (a) ✅ 완전 커버 (before와 동일한 구간)
--   (b) ✅ user_id 접두사로 탄다 (정렬은 §6 꼬리질문 3 참고)
--   (c) ❌ 이건 어차피 선두가 status여야 하므로 별도 인덱스 (status, created_at)
--          — status 단독은 카디널리티 3이라 무의미해 보이지만, FAILED가 전체의 1%면
--            "희귀 값만 조회하는" 쿼리엔 유효하다 (§3-3 편중 분포, §6의 부분 인덱스)
```

카디널리티가 실제로 개입하는 순간은 **"앞 컬럼만 쓰는 쿼리가 있을 때"**다.
`(user_id, status, …)`의 접두사 `user_id`만 쓰면 사용자 한 명 분(수십 건)으로
좁혀지지만, `(status, user_id, …)`의 접두사 `status`만 쓰면 전체의 절반이
걸려 플래너가 인덱스를 버린다. 즉 **카디널리티 높은 컬럼을 앞에 두는
이유는 "그 컬럼만으로도 인덱스가 쓸모 있게" 하기 위해서**이지, 등호 둘을
다 쓰는 쿼리를 위해서가 아니다.

### 2-3. 원칙 ③ — 범위·정렬 뒤에 오는 컬럼: 탐색용이 아니라 제거용

범위 컬럼 뒤에 붙는 컬럼은 구간을 좁히지 못한다. 그래도 붙이는 이유는 둘이다.

- **정렬 제거**: 등호 컬럼들 바로 뒤에 `ORDER BY` 컬럼을 두면 인덱스 순서가
  곧 정렬 순서라 계획에서 **`Sort` 노드가 사라진다**. 특히 `LIMIT 20`이
  붙으면 **구간의 앞 20개만 읽고 멈춘다.** 반면 `Sort`가 남으면 조건에 맞는
  행을 **전부** 읽은 뒤에야 정렬한다 — `LIMIT`이 있으면 PG는
  `Sort Method: top-N heapsort`로 정렬 메모리는 20건 몫만 쓰지만, **매칭 행
  전수를 읽는 비용은 그대로**다. `LIMIT` 없이 대량이면 `external merge
  Disk:`(디스크 정렬)까지 간다. **범위 컬럼 = 정렬 컬럼**(`created_at >= ?
  ORDER BY created_at`)이면 이상적 — 범위이자 정렬이라 둘 다 인덱스로
  처리된다.
- **커버링**: `SELECT`가 필요로 하는 컬럼까지 인덱스가 들고 있으면 힙 방문
  (북마크 룩업) 자체가 사라진다 — 계획에 **`Index Only Scan`**으로 찍힌다.
  PG는 이 용도의 전용 문법이 있다: **`INCLUDE`(PG 11+)** — `CREATE INDEX …
  ON orders (status, created_at) INCLUDE (amount)`처럼 **탐색에는 안 쓰고
  리프에만 얹는** 컬럼을 선언한다. 키 컬럼으로 붙이는 것보다 내부 노드가
  좁아지고, 유니크 인덱스에도 덧붙일 수 있다. 단 `Index Only Scan`의 효과는
  **visibility map(VACUUM 상태)에 달려 있다** — 다음 문항
  "커버링 인덱스"(09)에서 다룬다.

```sql
-- (a) WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20

-- ❌ (user_id, status)만 있을 때
--   Index Scan (user 100·PAID 행 전부)
--    → Sort  Sort Method: top-N heapsort    ← 전부 읽고 정렬 후 20개
-- ✅ (user_id, status, created_at)
--   Index Scan Backward using … + Limit     ← Sort 노드 없음.
--                                              구간 끝에서 역방향으로 20개 읽고 종료
--   (PG는 인덱스를 역방향으로도 읽고, 컬럼별 방향을 준 인덱스
--    (a ASC, b DESC)도 만들 수 있어 혼합 정렬도 인덱스로 처리할 수 있다)
```

### 2-4. 무엇이 "범위"로 취급되는가 (암기)

원칙 ①을 적용하려면 이 분류가 즉시 나와야 한다.

- **등호처럼 동작**: `=`, `IS NULL`, 그리고 `IN (…)` — 단 `IN`은 값 개수만큼
  **구간이 여러 개로 갈라진다.** 뒤 컬럼을 탐색에 쓸 수는 있지만, 뒤 컬럼
  기준 `ORDER BY`는 갈라진 구간을 병합해야 해서 대개 `Sort`가 남는다.
  (PG 17에서 `IN` 배열 처리가 한 번의 스캔으로 개선돼 정렬이 살아남는 경우가
  생겼지만, 기본기는 "갈라지면 정렬이 필요하다"로 두는 게 안전하다.)
- **범위**: `>`, `>=`, `<`, `<=`, `BETWEEN`, `LIKE 'kim%'`(선행 문자 고정)
- **사실상 전 구간(범위 중 최악)**: `!=`, `NOT IN`, `IS NOT NULL`, `NOT LIKE`
- **아예 못 씀**: `LIKE '%kim%'`, 컬럼에 함수·연산, 타입 불일치 —
  [풀스캔 원인 6종](02-index-not-used-full-scan.md) 참고

## 3. 카디널리티와의 관계 — 오해 둘, 개입 지점 둘

용어부터 고정한다([Q2 문서 §4-3](02-index-not-used-full-scan.md)의 정의 그대로).
**카디널리티** = 그 컬럼에 서로 다른 값이 몇 개인가(컬럼의 성질) —
`user_id`는 100만 종(높음), `status`는 3종(낮음), `is_deleted`는 2종(최악).
**선택도** = 이 조건이 전체 행을 몇 %로 좁히는가(조건의 성질). 카디널리티가
낮으면 대개 선택도도 낮지만, **편중 분포에서는 갈라진다**(3-3).

### 3-1. 오해 ① "카디널리티 높은 컬럼을 무조건 앞에"

틀린 이유 두 가지. ⑴ 그 컬럼이 **범위 조건**이면 카디널리티가 아무리 높아도
뒤로 가야 한다 — 2-1의 before가 정확히 이 실수다(`created_at`은 카디널리티
최상위지만 범위라서 앞에 두는 순간 `status`가 인덱스 내 검사로 강등됐다).
⑵ 등호 컬럼끼리라면 순서를 바꿔도 **같은 쿼리의 최종 구간은 동일**하다 — 2-2.
정확한 순위는 **등호/범위 구분(1순위) → 접두사 재사용(2순위) → 카디널리티
(3순위)**다.

### 3-2. 오해 ② "카디널리티 낮은 컬럼은 복합 인덱스 안에서도 쓸모없다"

단독 인덱스로는 무의미한 `status`(값 3종)가 **복합 안에서는 구간을 쪼개는
칸막이**가 된다. `(user_id, status, created_at)`에서 `status`는 user 한 명의
주문 50건을 PAID 10건으로 좁히는 일을 한다. **조합의 선택도는 (독립이라면)
각 컬럼 선택도의 곱**이다 — user_id로 1/100만 × status로 1/5 = 1/500만.
"인덱스를 탈지 말지"(랜덤 vs 순차 I/O 손익분기)를 정하는 것은 이 **조합의
선택도**이지, 개별 컬럼의 카디널리티가 아니다.

### 3-3. 개입 지점 ① — 편중 분포: 카디널리티 숫자만 보면 속는다

`status`의 카디널리티(고유값 수)가 3이라는 숫자는 "각 값이 33%씩"이라는
인상을 주지만, 실제 분포가 PAID 90% / DONE 9% / FAILED 1%라면
**`status = 'FAILED'`의 선택도는 1%로 충분히 좋다.** 사람이 카디널리티만
보고 "status는 인덱스 무의미"라고 판단하면 (c) 배치 쿼리를 풀스캔으로
방치하게 된다.

```sql
-- ❌ 카디널리티 숫자로 판단
SELECT n_distinct FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
--   3   → "무의미하네" (오판)

-- ✅ 분포로 판단 — PG 통계는 분포까지 들고 있다 (이 조회가 습관이 돼야 한다)
SELECT most_common_vals, most_common_freqs FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';
--   {PAID,DONE,FAILED} / {0.90,0.09,0.01}  → FAILED 조회는 1%, 인덱스 유효
--   (pg_stats는 ANALYZE 표본 기반 — 낡았다 싶으면 ANALYZE orders 먼저)
```

플래너 쪽은 이 **MCV(최빈값 목록)·히스토그램**으로 추정하므로 편중을 대체로
잡아낸다 — 표본이 모자라 못 잡으면 `ALTER TABLE … ALTER COLUMN … SET
STATISTICS`(또는 `default_statistics_target`)로 표본을 키운다. 속는 쪽은
플래너가 아니라 **카디널리티 숫자 하나로 설계 판단을 내리는 사람**이다.

### 3-4. 개입 지점 ② — 접두사만 쓰는 쿼리의 효율

2-2에서 본 대로다. 등호 컬럼 A, B가 있고 "A만 쓰는 쿼리"와 "B만 쓰는 쿼리"가
둘 다 있어 접두사 재사용으로 우열이 안 갈릴 때, **카디널리티 높은 쪽을 앞에**
둔다 — 접두사만으로도 구간이 좁아져 인덱스가 실제로 쓰이도록. 카디널리티가
낮은 쪽을 앞에 두면 그 접두사 쿼리는 플래너가 인덱스를 버린다.

**(가산점 포인트)** **skip scan** — 선두 컬럼이 조건에 없어도 선두 고유값이
아주 적을 때 값마다 뒤 컬럼 구간을 따로 탐색해 주는 최적화. **PostgreSQL은
18부터** 지원한다(MySQL은 8.0부터). 그 이전 버전에서는 재귀 CTE로 흉내 내는
수공업(loose scan 패턴)뿐이었다. "카디널리티 낮은 컬럼을 앞에 두면 접두사
규칙을 우회할 수 있다"는 뜻이지만, 고유값 수만큼 탐색을 반복하므로 **선두
카디널리티가 한 자릿수일 때만** 의미 있는 예외다. 설계 원칙을 대체하지
않는다.

### 3-5. 카디널리티 관계 — 한 장 요약 (암기)

| 질문 | 답 |
|---|---|
| 카디널리티가 컬럼 **순서**를 정하나? | 3순위. 등호/범위 → 접두사 재사용 → 그다음 |
| 카디널리티가 "인덱스를 **탈지**"를 정하나? | 개별 컬럼이 아니라 **조합의 선택도**가 정한다 (Q2 손익분기) |
| 낮은 카디널리티 컬럼은 버리나? | 단독은 무의미, 복합 안에서는 **칸막이**. 편중 분포면 단독도 유효 |
| 접두사 재사용과의 관계는? | 재사용 = **커버 범위**(2순위), 카디널리티 = **접두사 효율**(3순위 타이브레이커) |
| 무엇을 보고 판단하나? | `n_distinct` 숫자가 아니라 **`most_common_vals/freqs` 분포**(또는 `GROUP BY`) |

## 4. 트레이드오프 — 한 호흡에 양면으로

순서를 정하는 각 결정에는 대가가 붙어 있다. 편익만 말하면 반쪽이다.

| 결정 | 얻는 것 | 내주는 것 |
|---|---|---|
| 정렬·커버링용 컬럼을 뒤에 더 붙인다 | `Sort` 제거, 힙 방문 제거 | 엔트리 폭↑ → 페이지당 엔트리↓ → **버퍼 적재율↓**([Q3 문서 §2-1](03-clustered-vs-secondary-index.md)의 사슬); 그 컬럼이 자주 바뀌면 **HOT 탈락으로 쓰기 증폭**(아래) |
| 기존 인덱스의 순서를 바꾼다 | 대상 쿼리 최적 | 그 인덱스의 접두사에 기대던 **다른 쿼리가 조용히 풀스캔으로 전락** — 에러가 아니라 지연으로 나타나서 늦게 발견된다 |
| 넓은 인덱스 하나로 여러 쿼리 커버 | 인덱스 수↓ → DML당 갱신 트리 수↓, 버퍼 경쟁↓ | 각 쿼리는 차선(어떤 쿼리는 `Sort` 감수), 순서 변경 시 영향 범위↑ |
| 쿼리별 좁은 인덱스 여럿 | 각 쿼리 최적 | DML마다 트리 N개 갱신, 공간, 후보가 많아져 **플래너 선택 실패 확률↑** |
| 범위 조건이 둘일 때 하나만 인덱스 범위로 | 더 좁히는 범위로 스캔 폭 최소화 | 다른 범위는 인덱스 내 검사 → 그만큼 초과 스캔 |

특히 첫 줄 — **자주 바뀌는 컬럼을 인덱스에 넣는 대가**는 PostgreSQL에서 한 겹
더 무겁다. PG의 UPDATE는 행을 제자리에서 고치지 않고 **새 버전 튜플을
만드는데**, 바뀐 컬럼이 **어떤 인덱스에도 안 들어 있으면** 같은 힙 페이지
안에서 **HOT(Heap-Only Tuple) 업데이트**로 처리돼 인덱스를 하나도 안 건드린다.
그런데 `status`를 인덱스에 넣는 순간, status를 바꾸는 모든 UPDATE가 HOT에서
탈락한다 — **그 인덱스만이 아니라 그 테이블의 모든 인덱스에 새 엔트리를
꽂는다.** 주문 하나가 상태를 다섯 번 바꾸면 인덱스가 5개인 테이블에서 인덱스
쓰기 25번이다. "조회가 빨라진다"만 말하고 이걸 빠뜨리면 트레이드오프 서술이
아니다.

## 5. 안전망 — 순서 규칙을 사람의 기억이 아니라 코드·설정에 박는다

"등호 먼저, 범위 뒤"를 리뷰어가 기억해 주기를 바라는 것이 가장 약한 안전망이다.
고정할 곳은 넷이다.

**⑴ 이름에 순서를 박는다.** 인덱스 이름이 컬럼 순서를 그대로 드러내면,
마이그레이션 PR에서 이름만 보고도 "범위 컬럼이 앞에 있네"를 잡을 수 있다.

```sql
-- ❌ 순서가 안 보이는 이름 — 리뷰어가 정의문을 열어봐야 안다
CREATE INDEX idx_orders_1 ON orders (created_at, status);

-- ✅ 이름 = 컬럼 순서
CREATE INDEX idx_orders_status_created_at ON orders (status, created_at);
```

**⑵ 실행 계획을 테스트로 단정한다.** 주의 — PG에는 MySQL `used_key_parts`
같은 "어느 컬럼까지 구간을 좁혔나" 필드가 **없다**(강등된 키도 `Index Cond`에
찍히므로 계획 텍스트로는 순서 실수를 못 잡는다). 그래서 단정할 것은 두 가지 —
① 의도한 **인덱스 이름**, ② `BUFFERS`의 **읽은 블록 수**(순서가 뒤집히면
자릿수로 튄다).

```java
@Test
void 실패주문_알림쿼리는_status_created_인덱스로_좁은_구간만_읽는다() throws Exception {
    // given: 실전 규모의 데이터 + 통계 갱신 (아래 주의 참고)
    seedOrders(200_000);
    jdbcTemplate.execute("ANALYZE orders");

    // when
    String plan = jdbcTemplate.queryForObject(
        "EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) "
      + "SELECT id, user_id, amount FROM orders "
      + "WHERE status = 'FAILED' AND created_at >= ?",
        String.class, LocalDateTime.now().minusHours(1));
    JsonNode p = objectMapper.readTree(plan).at("/0/Plan");

    // then ①: 의도한 인덱스를 탄다
    assertThat(p.at("/Index Name").asText()).isEqualTo("idx_orders_status_created_at");
    // then ②: 읽은 블록이 "좁은 구간" 수준 — (created_at, status)로 뒤집히면 수천으로 튄다
    int blocks = p.at("/Shared Hit Blocks").asInt() + p.at("/Shared Read Blocks").asInt();
    assertThat(blocks).isLessThan(200);   // 임계값은 실측 후 여유 있게
}
```

> **주의 — 이 테스트에도 대가가 있다.** 실행 계획은 **데이터 양과 통계에 따라
> 바뀐다.** 행이 수백 건뿐인 테스트 DB에서는 플래너가 인덱스 대신 Seq Scan을
> 고르는 게 정상이라 테스트가 거짓 실패한다. 그래서 실전 규모의 시드 +
> `ANALYZE`가 필요하고, 그만큼 테스트가 무거워진다. 모든 쿼리에 걸지
> 말고 **테이블 규모가 크고 순서 실수가 곧 장애인 쿼리 몇 개**에만 건다.
> (Testcontainers로 PostgreSQL을 띄우는 구성은 3장 문서들 참고.)

**⑶ 중복·미사용 인덱스를 사람이 기억하지 않는다.** `(A, B)`를 만들면서 기존
`(A)`를 지우는 걸 잊는 일은 반드시 생긴다. PG는 MySQL `sys` 스키마 같은 기성
뷰가 없어 카탈로그를 직접 조회한다 — 배치나 대시보드에 걸어 둔다.

```sql
-- 미사용: 통계 수집 이후 한 번도 안 쓰인 인덱스 (pg_stat_reset 시점 주의)
SELECT indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE relname = 'orders' AND idx_scan = 0;

-- 접두사에 흡수되는(중복) 인덱스: a의 컬럼 목록이 b의 접두사인 쌍
SELECT a.indexrelid::regclass AS redundant, b.indexrelid::regclass AS covering
FROM pg_index a
JOIN pg_index b ON a.indrelid = b.indrelid AND a.indexrelid <> b.indexrelid
WHERE a.indrelid = 'orders'::regclass
  AND b.indkey::text LIKE a.indkey::text || ' %';
-- (단순 비교 버전 — 부분 인덱스(WHERE 절)·연산자 클래스가 다르면 중복이 아니니 따로 확인)
```

**⑷ 느린 쿼리를 계획째로 자동 수집한다.** `log_min_duration_statement`를
낮게 잡으면 느린 쿼리가 로그에 남고, **`auto_explain`** 확장을 켜면
(`auto_explain.log_min_duration`, `log_buffers = on`) 그 쿼리의 **실제 실행
계획 + Buffers까지** 같이 남는다 — 순서 실수로 스캔 폭이 늘어난 쿼리는 "읽은
블록 대비 반환 행이 적은" 형태로 잡힌다. 상시 감시는 `pg_stat_statements`로
`shared_blks_read`·`mean_exec_time` 상위 쿼리를 본다. 운영에서 "느려요"가
오기 전에 설정이 먼저 알려주는 구조다.

## 6. 꼬리질문 대비 포인트

### "카디널리티 높은 컬럼을 앞에 두라고 배웠는데, 틀린 건가요?"

반쯤 맞다 — **3순위 기준으로는 맞고, 1순위로 쓰면 틀린다.** 1순위는
등호/범위 구분이다: 범위 조건 컬럼은 카디널리티가 최상위여도 뒤로 가야 한다
(`created_at`을 앞에 둔 순간 `status`가 구간을 못 좁히는 인덱스 내 검사로
강등돼 스캔 폭이 100배가 된 예). 2순위는 접두사 재사용 — 등호 컬럼끼리는
같은 쿼리에서 순서를 바꿔도 최종 구간이 같으므로, "이 인덱스의 앞부분만
쓰는 다른 쿼리"가 무엇인지가 순서를 정한다. 카디널리티는 그래도 우열이 안
갈릴 때, **접두사만으로도 구간이 좁아지도록** 높은 쪽을 앞에 두는
타이브레이커다.

### "범위 조건이 두 개(`created_at` 기간 + `amount >= ?`)면 어떻게 하나요?"

인덱스는 **범위를 하나만 액세스 조건으로** 쓴다 — 첫 범위 뒤는 정렬이
깨지므로 두 번째 범위는 구간을 못 좁힌다. 그래서 둘 중 **더 좁히는 범위**(또는
`ORDER BY`에 쓰이는 범위)를 인덱스의 범위 컬럼으로 두고, 나머지는 그 뒤에
붙인다 — 뒤에 붙이면 적어도 **인덱스 안에서 걸러져 힙 방문 전에 버려진다**
(계획엔 똑같이 `Index Cond`로 찍힌다). 한 단계 위의 답은 **요건을 되물어
고정 조건인지 확인하는 것** — "금액 1만 원 이상"이 사실상 고정된 기준이면
PG는 **부분 인덱스**가 정석이다: `CREATE INDEX … ON orders (status,
created_at) WHERE amount >= 10000`. 인덱스 자체가 그 조건의 행만 담으므로
두 번째 범위가 사라지고 인덱스도 작아진다. (플래그 컬럼·생성 컬럼은 부분
인덱스를 못 쓸 때의 차선.) 다만 조건이 정말 고정인지, 쿼리의 WHERE가 인덱스
WHERE를 포함하는지(포함해야 플래너가 쓴다)를 확인하고 간다.

### "`(user_id, status, created_at)`가 있는데 `WHERE user_id = ? ORDER BY created_at DESC LIMIT 20`이 정렬을 합니다. 왜죠? 어떻게 하죠?"

가운데 `status`가 조건에 없어서다. user 100의 구간 안에서 `created_at`은
**status별로 따로** 정렬돼 있지(DONE 칸의 시간순, PAID 칸의 시간순…) 전체가
시간순이 아니다. 선택지는 넷이고 각각 대가가 있다. ⑴ 사용자당 행이 수십 건이면
`Sort`(top-N heapsort) 비용이 미미할 수 있다 — **실측하고 수용**.
⑵ `(user_id, created_at)`을 따로 만든다 — 이 쿼리는 최적, 대가는 인덱스
하나 몫의 쓰기·공간. ⑶ 쿼리에 `status IN (모든 값)`을 넣어도 구간이 값
수만큼 갈라져 병합 정렬이 필요하므로 `Sort`는 대개 안 사라진다.
⑷ 순서를 `(user_id, created_at, status)`로 바꾸면 이 쿼리는 해결되지만,
`user_id + status + 정렬` 쿼리에서 `status`가 구간을 못 좁히게 된다 —
**어느 쿼리가 더 뜨거운지**를 `pg_stat_statements`로 측정해 결정한다.

### "인덱스 하나를 넓게(4~5컬럼) 만들어 여러 쿼리를 커버하는 것과 쿼리별로 좁은 인덱스를 여러 개 두는 것, 기준은?" (시니어 변별 포인트)

양면을 먼저 편다. 넓은 하나는 **DML당 갱신하는 트리 수와 버퍼 경쟁을
줄이지만**, 각 쿼리는 차선이 되고 순서를 바꿀 때 영향 범위가 커진다. 좁은
여럿은 **각 쿼리가 최적이지만** 쓰기 증폭·공간·플래너 선택 혼선을 낸다.
기준은 셋 — ① **읽기:쓰기 비율**(쓰기가 무거운 테이블일수록 넓은 하나로
합친다) ② **접두사 공유 여부**(쿼리들이 같은 등호 컬럼으로 시작하지 않으면
넓혀도 못 커버하므로 애초에 선택지가 아니다) ③ **포함 컬럼의 변경 빈도**
(자주 바뀌는 컬럼이 인덱스에 들어가면 그 컬럼을 바꾸는 UPDATE가 HOT에서
탈락해 **모든 인덱스가** 쓰기 부담을 진다 — §4). 그리고 결정보다 중요한 건
**"각 인덱스가 어떤 쿼리를 위해 존재하는지"를 표로 남기는 것** — 이게
없으면 다음 사람이 순서를 바꾸다 다른 쿼리를 깨뜨린다.

### "순서를 잘 잡았는데 어느 날부터 플래너가 그 인덱스를 안 탑니다" (가산점 포인트)

순서는 안 바뀌었어도 **조합의 선택도**는 바뀐다. 후보 셋을 순서대로 본다.
① **데이터 분포 변화** — FAILED가 1%였다가 외부사 장애로 40%가 되면
`status = 'FAILED'` 구간이 손익분기를 넘어 Seq Scan이 정답이 된다(플래너가
맞다). ② **통계가 낡음** — 대량 적재·삭제 후 추정 행 수가 어긋나면
`ANALYZE`로 갱신([Q2 문서 §5-2](02-index-not-used-full-scan.md)). autovacuum의
analyze 임계가 큰 테이블에서 둔한 것도 흔한 원인 —
`autovacuum_analyze_scale_factor`를 테이블 단위로 낮춘다. ③ **새로 추가된
인덱스가 후보로 경쟁** — 누군가 비슷한 인덱스를 만들어 플래너가 그쪽을
고르기 시작한 경우, §5-⑶의 중복 인덱스 쿼리로 확인한다. PG에는 `FORCE
INDEX` 같은 힌트가 기본으로 없다 — 진단은 세션에서 `SET enable_seqscan =
off`로 가설을 검증하는 데까지만 쓰고, 정말 강제가 필요하면 `pg_hint_plan`
확장이 최후 수단이다. 쓰면 "왜 플래너를 못 믿었는지"를 주석과 이슈로 남긴다.

### "MySQL로 물어보면 답이 달라지는 부분은?" (경험 대조)

네 지점이다. ① **강등이 계획에 보이는 방식** — MySQL은 `key_len`(어느
컬럼까지 액세스인지)과 `Extra: Using index condition`(ICP)으로 강등이
드러나지만, PG는 강등된 키도 `Index Cond`에 찍혀 **텍스트로는 안 보이고
`BUFFERS`로 판별**한다. ② **커버링 문법** — MySQL은 커버링 컬럼도 키 컬럼으로
붙이는 수밖에 없지만 PG는 `INCLUDE`가 따로 있고, 대신 `Index Only Scan`이
visibility map(VACUUM)에 좌우된다. ③ **자주 바뀌는 컬럼의 대가** — InnoDB는
해당 인덱스에서만 삭제+삽입이 일어나지만, PG는 HOT 탈락으로 **모든 인덱스**에
새 엔트리를 꽂는다. ④ **skip scan** — MySQL 8.0 / PG 18. 이 넷을 짚으면
"격언 암기"가 아니라 "저장 구조에서 도출"로 들린다.

## 한 줄 요약

**복합 인덱스는 "앞 컬럼 값이 하나로 고정돼야 뒤 컬럼 정렬이 살아 있는"
사전 안의 사전이므로, 순서는 등호 → 범위(하나, 맨 뒤) → 정렬 → 커버링
순으로 배치하고, 등호 컬럼끼리는 접두사 재사용(커버 범위) → 카디널리티
(접두사 효율) 순으로 정한다. 카디널리티는 순서의 3순위 기준일 뿐이며
"인덱스를 탈지"는 개별 컬럼이 아닌 조합의 선택도가 정한다. 순서가 틀리면
뒤 컬럼이 구간을 못 좁혀 스캔 폭이 자릿수로 커지는데, PostgreSQL 계획에는
강등된 조건도 `Index Cond`로 찍혀 겉으로 안 보인다 — `EXPLAIN (ANALYZE,
BUFFERS)`의 읽은 블록 수로 판별하고, 규칙은 인덱스 이름·블록 수 단정
테스트·카탈로그 조회·auto_explain에 박아 둔다.**
