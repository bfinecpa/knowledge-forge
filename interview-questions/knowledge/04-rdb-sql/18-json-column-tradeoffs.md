# RDB의 JSON 컬럼 — "귀찮아서 jsonb"와 "비정형이라 jsonb"를 가르는 규율

> 핵심 관전 포인트: **JSON 컬럼(PostgreSQL에서는 `jsonb`)은 "행마다 모양이 다른 데이터를 DDL 없이 담는 자유"를 사는 대신, RDB가 컬럼에 공짜로 얹어 주던 네 가지 — ① 인덱스(값의 정렬된 사본) ② 타입·제약(DB가 지키는 불변식) ③ 좁은 갱신(바뀐 만큼만 쓰기) ④ 통계(플래너가 행 수를 맞출 근거) — 를 반납하는 거래다. PostgreSQL은 ①을 표현식 인덱스·GIN으로 상당 부분 되찾게 해 주지만 "미리 정한 키"만 빠르고, ③은 MVCC 위에서 오히려 더 비싸다 — 키 하나를 바꿔도 문서 전체가 새 튜플 버전으로 다시 쓰이고 (TOAST 청크까지) WAL·죽은 튜플로 번진다. ④는 우회가 가장 늦게 오는 손실이다 — 플래너는 문서 안 키의 분포를 모르므로 추정 행 수가 상수가 되고, 그 쿼리가 조인의 한 축이면 조인 방식과 순서까지 통째로 어긋난다. 그래서 판별은 취향이 아니라 네 질문이다: ⑴ 그 안의 값이 WHERE·JOIN·GROUP BY·ORDER BY의 대상인가 ⑵ 스키마가 행마다 진짜 다른가(모든 행이 같은 키를 가지면 컬럼을 JSON에 숨긴 것) ⑶ 쓰기 후 부분 수정이 잦은가 ⑷ DB가 지켜야 할 불변식인가. 하나라도 "예"면 컬럼(또는 별도 테이블), 넷 다 "아니오"인 데이터 — 외부 원문 보존, 희소(sparse) 속성, 통째로 읽고 쓰는 문서 — 가 jsonb의 자리다. 쓰기로 했다면 안전망을 함께 든다: 조회 조건이 된 키는 표현식 인덱스(또는 STORED 생성 컬럼)로 승격, `CHECK` + jsonb 연산자(또는 DTO)로 스키마 검증, 버전 필드로 세대 관리. 그리고 스키마 진화의 정체를 정직하게 말한다 — jsonb는 마이그레이션을 없앤 것이 아니라 DB의 DDL 한 번을 애플리케이션 읽기 코드의 영구 분기로 옮긴 것이다.**

> 표기: 이 문서에서 "PG사"·"결제 PG"는 결제 게이트웨이(Payment Gateway)를 뜻한다. PostgreSQL은 줄이지 않고 항상 풀어 쓴다.

## 0. 질문 + 의도

**질문**: "RDB의 JSON 컬럼은 언제 쓰고 언제 피하나요? 인덱싱과 스키마 진화 관점의 트레이드오프는?"

**출제 의도**: 스키마 유연성의 편의와 **그 대가(인덱싱 제약, 타입 안전 상실, 조회 최적화 어려움)** 를 아는지. "정규화가 귀찮아서 JSON"과 "진짜 비정형 속성이라 JSON"을 구분하는 **설계 규율의 표본**이다. 즉 jsonb 연산자 문법이 아니라 — 편익과 대가를 양면으로 조립하고, 그 대가가 "왜" 생기는지를 저장 구조(힙 튜플·TOAST·MVCC)의 메커니즘으로 말하며, 쓰기로 했을 때 어떤 안전망을 함께 설계하는지를 본다. PostgreSQL은 `jsonb`·GIN·표현식 인덱스·jsonpath까지 도구가 유난히 풍부해서 "되니까 쓴다"의 유혹이 크다 — **도구가 있다는 것과 써야 한다는 것은 다르다**는 판단이 이 문항의 핵심이다. 반정규화 문항([정규화 vs 반정규화](./04-normalization-vs-denormalization.md))과 같은 뿌리 — "중복을 두는 결정"이 아니라 "구조를 포기하는 결정"의 버전이다.

> 읽는 순서를 미리 알려 둔다. §1은 **무엇을 반납하는가**를 다섯 갈래로 쪼갠다 — 반납 목록을 먼저 손에 쥐어야 §2의 판별 질문이 암기가 아니라 도출이 된다. §2는 그 반납 목록을 네 개의 예/아니오 질문으로 접어 실무 리뷰에서 바로 쓸 수 있게 만든다. §3은 "그래도 jsonb를 골랐을 때" 반납한 것 중 무엇을 얼마나 되사올 수 있는지(표현식 인덱스·GIN)와, 되살 수 없는 것(스키마 진화 비용)을 어떻게 관리하는지를 다룬다.

## 1. 개념 — jsonb 컬럼은 무엇을 반납하고 무엇을 사는가

### 1-1. 전제 — `json`과 `jsonb`는 이름만 닮은 다른 타입이다

이 문서의 모든 서술은 "어느 타입 이야기인가"에 따라 참·거짓이 갈린다. 그래서 여기부터 갈라 둔다. PostgreSQL에는 JSON을 담는 타입이 **둘**이고, 둘은 저장 방식이 근본적으로 다르다.

**`json`은 입력받은 텍스트를 그대로 저장한다.** INSERT 시점에 하는 일은 "이게 문법적으로 올바른 JSON인가"를 한 번 검사하는 것뿐이고, 검사가 끝나면 받은 문자열을 한 바이트도 손대지 않고 그대로 넣는다. 공백도, 키를 쓴 순서도, 같은 키가 두 번 나온 것도 전부 남는다. 대신 나중에 `doc->>'name'`으로 값을 꺼낼 때마다 **저장된 텍스트를 처음부터 다시 파싱**해야 한다. 저장은 싸고 읽기는 비싼 구조다.

**`jsonb`는 입력을 파싱해서 이진(binary) 구조로 바꿔 저장한다.** 이름의 `b`가 binary다. INSERT 시점에 파싱·정규화 비용을 한 번 치르는 대신, 저장된 형태 자체가 이미 "키 → 값"의 탐색 가능한 구조라서 값을 꺼낼 때 다시 파싱하지 않는다. 저장이 비싸고 읽기가 싼 구조다. 그리고 이 "이진 구조로 저장한다"가 뒤따르는 모든 기능의 전제다 — 문서 안을 구조로 이해하고 있어야 `@>`(포함) 같은 연산자를 만들 수 있고, 인덱스에 키·값을 꺼내 넣을 수도 있다.

| 항목 | `json` | `jsonb` |
|---|---|---|
| 저장 형태 | 입력 텍스트 **그대로** | 파싱된 **이진 구조** |
| 저장 시 비용 | 문법 검사만 (싸다) | 파싱 + 정규화 (비싸다) |
| 값을 꺼낼 때 | 접근할 때마다 **다시 파싱** | 파싱 없이 키 탐색 |
| 공백·들여쓰기 | 보존 | 제거 |
| 키 순서 | 입력한 순서 그대로 보존 | **정렬해서 저장** (길이순 → 사전순). 꺼내 보면 넣은 순서와 다르다 |
| 중복 키 | 전부 보존 (`->>`는 마지막 것을 준다) | **마지막 값만 남기고 나머지는 버린다** |
| 연산자 | `->`, `->>`, `#>`, `#>>` 정도 | 위 전부 + `@>`, `<@`, `?`, `?|`, `?&`, `||`, `-`, jsonpath(`@?`, `@@`) |
| 인덱스 | GIN 불가. 표현식 B-tree만 겨우 | GIN(`jsonb_ops`/`jsonb_path_ops`), 표현식 인덱스 전부 가능 |
| 동등 비교(`=`) | 불가 (텍스트로 캐스트해야 함) | 가능 (구조가 정규화돼 있어서) |
| 자리 | "바이트 그대로 보존"이 요구인 원문 증거 | 그 외 전부 |

정규화가 실제로 무엇을 바꾸는지는 한 번 넣었다 꺼내 보면 바로 보인다.

```sql
-- 같은 입력을 두 타입에 넣고 그대로 꺼내 본다
SELECT '{"b": 1,  "a": 2, "a": 3}'::json  AS as_json,
       '{"b": 1,  "a": 2, "a": 3}'::jsonb AS as_jsonb;

--   as_json                     |  as_jsonb
--  ---------------------------- + -------------------
--   {"b": 1,  "a": 2, "a": 3}   |  {"a": 3, "b": 1}
--
-- json  : 공백 두 칸도, 중복된 "a"도, b가 먼저 온 순서도 그대로다.
-- jsonb : 공백이 사라지고, 키가 정렬되고, 중복 "a"는 마지막 값 3만 남았다.
--         "받은 그대로"가 요구였다면 이 시점에 이미 요구를 어긴 것이다.
```

**실무의 기본 선택은 `jsonb`다.** 조회·인덱싱·연산자가 전부 jsonb 쪽에만 있으므로, "JSON 컬럼을 쓴다"는 말은 거의 항상 jsonb를 뜻한다. `json`이 맞는 자리는 딱 하나 — **"입력 바이트를 그대로 보존하는 것 자체가 요구사항"**일 때다. 결제 PG 응답 원문처럼 나중에 분쟁이 났을 때 "그때 상대가 정확히 뭐라고 응답했는가"를 증거로 내야 하는 데이터가 여기 해당한다(§2-3의 (b)). 그런 컬럼은 어차피 조회 조건으로 쓰지 않으므로 `json`의 "읽을 때마다 파싱" 비용도 문제가 되지 않는다.

아래 본문에서 그냥 "JSON 컬럼"이라고 쓰면 **jsonb**를 뜻한다. `json`을 말할 때는 그때마다 명시한다.

### 1-2. 컬럼이 공짜로 주던 것들 — 그리고 각각이 없으면 나는 사고

비유부터. 정식 컬럼은 **서류 양식의 인쇄된 칸**이다. 칸이 정해져 있으니 접수처는 그 칸 기준으로 **색인**(인덱스)을 만들 수 있고, 칸의 **형식**(숫자만, 빈칸 금지, 다른 서류의 번호와 대조)을 접수 시점에 검사하며, 칸 하나만 **고쳐 쓸** 수 있고, 칸마다 "이 값이 대략 몇 건"이라는 **장부**(통계)를 갖는다. 그리고 칸에는 **이름이 인쇄되어 있어서** 없는 칸에 적으려 하면 적을 자리가 없다.

JSON 컬럼은 양식 비고란에 **붙여 둔 메모지**다. 무엇이든 적을 수 있지만 — 접수처는 메모지 안의 내용으로 색인을 만들지 않고, 내용을 검사하지도 않으며, 한 글자를 고치려면 메모지를 새로 써서 다시 붙여야 하고, 메모지 안에 무엇이 몇 건 적혀 있는지 세지 않으며, 메모지에는 인쇄된 칸 이름이 없으니 이름을 잘못 써도 아무도 모른다.

이제 비유를 걷어내고 하나씩 이름을 붙인다. 아래 표의 오른쪽 칸 — **"없으면 무슨 사고가 나는가"** — 가 이 문서의 실질이다. 면접에서 "인덱스가 잘 안 된다", "타입이 없다"라고 결과만 말하는 것과, 사고까지 이어 말하는 것이 이 질문의 첫 변별점이다.

| 컬럼이면 공짜로 오는 것 | jsonb 안에서는 | 없으면 나는 사고 |
|---|---|---|
| **인덱스** — 값이 정렬된 사본에 들어간다 | 없음 (우회 필요) | 조건 검색이 Seq Scan + 행마다 파싱. 300만 행이면 1.8초짜리 조회가 목록 API에 박힌다 (1-3) |
| **통계** — 플래너가 "이 값이 몇 건"을 안다 | 없음 (내부 키 분포를 수집하지 않음) | 추정 행 수가 **상수**가 되어 조인 방식·순서가 통째로 뒤집힌다. 단독 쿼리보다 **조인에서 훨씬 크게 터진다** (1-4) |
| **좁은 갱신** — 바뀐 칸만큼만 다시 쓴다 | 없음 (문서 전체 재기록) | 키 하나 바꾸는 UPDATE가 100KB를 다시 쓰고 WAL·죽은 튜플로 번진다. 락 보유 시간도 같이 늘어난다 (1-5) |
| **타입 검사** — `numeric` 칸에 문자열이 못 들어온다 | 없음 (문법만 검사) | 숫자와 문자열이 한 키에 섞이고, 어느 날 `"1,000"` 한 건 때문에 집계 쿼리 전체가 `ERROR`로 죽는다 (1-6) |
| **`NOT NULL` · `CHECK`** — 필수값·범위를 DB가 강제 | 없음 | 필수 키가 빠진 문서가 조용히 들어오고, 읽는 코드가 `NullPointerException`으로 처음 알게 된다 (1-6) |
| **`FOREIGN KEY`** — 없는 행을 가리킬 수 없다 | 없음 (jsonb 내부 값에는 FK를 못 건다) | 삭제된 작가를 가리키는 `{"author_id": 42}`가 검출 수단 없이 쌓인다 (1-6) |
| **`UNIQUE`** — 중복을 DB가 막는다 | 없음 (문서 전체에는 걸 수 있으나 내부 키에는 불가) | 같은 SKU가 두 행에 들어가고, 발견은 정산 대사에서 된다 (1-6) |
| **이름** — 없는 컬럼에 쓰면 즉시 에러 | 없음 (아무 키나 만들어진다) | `prcie`라고 오타 낸 키가 조용히 저장되고, 조회는 예외 없이 그 행을 빼고 센다 (1-7) |

이 목록을 다섯 갈래의 "비용 사슬"로 묶으면 아래 다섯 소절이 된다. 사슬이라고 부르는 이유는, 각 항목이 "기능이 하나 없다"에서 끝나지 않고 **다음 고리로 번지기 때문**이다.

### 1-3. 반납 ① 인덱스 — 값이 정렬된 사본에 없어서 Seq Scan

[인덱스가 있는데 풀스캔](./02-index-not-used-full-scan.md) 문서의 한 문장을 다시 가져온다 — **인덱스란 인덱스 컬럼의 값과 그 행의 위치(TID)를 함께 담아 그 값 기준으로 정렬해 둔 별도의 사본**이다. 탐색이 빠른 이유는 오직 "찾는 값이 이미 정렬된 사본 안에 있어서"다. 정렬돼 있으니 이진 탐색으로 시작점을 찍고, 필요한 만큼만 옆으로 이어 읽으면 끝난다.

여기서 결정적인 사실 하나. **JSON 컬럼의 내부 키는 플래너 입장에서 컬럼이 아니다.** DB가 카탈로그(`pg_attribute`)에서 아는 것은 "이 테이블에 `attrs`라는 이름의 jsonb 컬럼이 하나 있다"까지이고, 그 문서 안의 `genre`라는 키는 **스키마에 존재하지 않는다.** 데이터일 뿐 구조가 아니다. 그러니 사슬은 이렇게 간다.

```text
⑴ 정렬 사본에 값이 없다
   B-tree 인덱스는 "컬럼 값 + TID"를 정렬해 담는다. attrs->>'genre'는 컬럼이 아니므로
   어떤 인덱스의 정렬 기준에도 들어 있지 않다.
   (jsonb 컬럼 자체에 B-tree를 걸 수는 있다. 그러나 그것은 "문서 전체"를 하나의 값으로
    보고 정렬한 것이라, attrs = '{"genre":"스릴러", ...}' 처럼 문서 전체가 정확히
    일치하는 조건에만 쓰이고 내부 키 조건에는 아무 쓸모가 없다.)
      ↓
⑵ 탐색 불가 → 전 행 읽기
   정렬 기준이 없으니 트리를 타고 내려갈 시작점을 찍을 수 없다. 유일한 방법은
   모든 행을 처음부터 끝까지 읽는 Seq Scan이다.
   (테이블이 크면 Gather 아래 Parallel Seq Scan으로 나오지만, 전 페이지를 읽는다는
    사실은 같다. 병렬은 시간을 나눌 뿐 일의 총량을 줄이지 않는다.)
      ↓
⑶ 행마다 파싱 CPU가 붙는다
   읽기만 하는 게 아니다. 행마다 jsonb를 열어 genre 키를 찾고, 값을 텍스트로 꺼내
   비교해야 한다. 일반 컬럼 Seq Scan은 정해진 오프셋의 값을 바로 비교하지만,
   jsonb Seq Scan은 I/O + 키 탐색·변환의 이중 비용이다.
   계획에는 Filter: 와 Rows Removed by Filter 로 찍힌다.
      ↓
⑷ 큰 문서일수록 읽을 페이지도 많다
   문서가 행을 뚱뚱하게 만들어 페이지(8KB)당 행 수가 줄고, 대략 2KB를 넘는 값은
   TOAST(The Oversized-Attribute Storage Technique)로 압축돼 별도 테이블에 청크로
   밀려난다. genre 하나 보려고 그 청크들을 모아 압축을 풀어 문서 전체(쓰지도 않을
   다른 키 수십 개 포함)를 메모리로 끌어온다.
      ↓
⑸ 통계가 없어 추정도 틀린다  →  이 고리는 1-4에서 따로 다룬다
```

구조적으로는 "컬럼에 함수를 씌운 조건"(위 문서의 3-1)과 같은 부류다 — `attrs->>'genre'`는 연산자(함수) 적용의 극단형이고, 가공 전 원본 값만 정렬해 둔 사본이 가공 후 값을 알 리 없다.

```sql
-- before: JSON 내부 키로 조건 검색 (에피소드 300만 건)
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title
  FROM episodes
 WHERE format_attrs->>'genre' = '스릴러';

 Seq Scan on episodes  (cost=0.00..105604.00 rows=15000 width=40)
                       (actual time=0.412..1874.903 rows=9120 loops=1)
   Filter: ((format_attrs ->> 'genre'::text) = '스릴러'::text)
   Rows Removed by Filter: 2990880
   Buffers: shared hit=2112 read=58392
 Planning Time: 0.09 ms
 Execution Time: 1876.1 ms
-- 인덱스가 "안 쓰인" 게 아니라 애초에 후보조차 없다: 300만 행 전부 읽고(⑵)
-- 행마다 jsonb를 열어 비교했다(⑶ — Rows Removed by Filter 299만).
-- 읽은 버퍼 2,112 + 58,392 = 60,504 페이지 ≈ 473MB를 훑고 9,120건을 골랐다.
-- rows=15000 은 데이터를 보고 낸 추정이 아니라 상수 선택도(0.5%)다 —
-- 300만 x 0.005 = 15,000. 실제 비율이 0.3%든 30%든 똑같이 15000으로 찍힌다(1-4).
```

우회(표현식 인덱스·GIN)는 §3에서 다루지만, 원리는 한 줄로 요약된다 — **값을 정렬 사본 안에 "존재하게" 만들어야 한다.**

### 1-4. 반납 ② 통계 — 플래너가 행 수를 모르면 조인 방식이 통째로 어긋난다

이 고리는 셋 중 가장 늦게 눈에 띄고 가장 크게 터진다. 그래서 따로 뗀다.

먼저 전제. PostgreSQL의 플래너는 규칙표를 보고 실행 방법을 고르는 것이 아니라 **비용을 추정해서 가장 싼 계획을 고른다.** 그 추정의 재료가 **통계**다. `ANALYZE`가 테이블을 표본 추출해 컬럼마다 "값이 몇 종류인가(`n_distinct`)", "가장 흔한 값과 그 빈도는(`most_common_vals`/`most_common_freqs`)", "값이 어떻게 퍼져 있나(히스토그램)"를 `pg_statistic`에 적어 둔다(사람이 보는 뷰는 `pg_stats`). `WHERE genre = '스릴러'`가 몇 건을 남길지를 플래너가 아는 것은 이 통계 덕이다.

**jsonb 컬럼에도 통계는 있다. 그러나 "문서 전체를 하나의 값으로 본" 통계다.** `pg_stats`에서 `attrs` 행을 조회하면 문서 전체의 `n_distinct`와 most common values가 나온다. 그런데 문서 전체가 통째로 똑같은 행이 몇 개나 되겠는가 — 사실상 전부 유일하다. 우리가 알고 싶은 것은 "`attrs->>'genre'`가 '스릴러'인 행이 몇 건인가"인데, **그 분포는 어디에도 수집돼 있지 않다.**

통계가 없을 때 플래너가 하는 일은 포기가 아니라 **상수 대입**이다. `text = text` 형태의 등호 조건에 대해 아무 정보가 없으면 선택도를 0.005(0.5%)로 가정한다. 그래서 위 계획의 `rows=15000`이 나왔다 — 300만 × 0.005다. 이 값은 데이터를 한 번도 안 보고 나온 숫자라서, 실제가 0.3%든 30%든 똑같이 15,000이다.

단독 쿼리라면 이 오차가 큰 사고를 내지 않는다. 어차피 Seq Scan 말고 고를 것이 없기 때문이다. **문제는 이 쿼리가 조인의 한 축일 때 터진다.** 조인 방식 선택이 전적으로 "양쪽이 몇 건인가"에 달려 있기 때문이다. 세 방식을 짧게 짚고 간다.

- **Nested Loop**: 바깥 결과 한 건마다 안쪽을 한 번씩 조회한다. 바깥이 **적을 때** 압도적으로 싸고, 많으면 그 횟수만큼 비용이 곱해진다.
- **Hash Join**: 한쪽을 통째로 읽어 메모리에 해시 테이블을 만들고, 다른 쪽을 흘려보내며 맞춰 본다. 양쪽이 **클 때** 유리하고, 해시로 만드는 쪽이 `work_mem`을 넘으면 디스크로 흘러넘친다.
- **Merge Join**: 양쪽을 정렬해 놓고 지퍼처럼 맞춰 나간다. 이미 정렬돼 있거나 결과가 아주 클 때 후보다.

이제 추정이 틀렸을 때 무슨 일이 벌어지는지를 두 방향으로 본다.

```text
[방향 A] 실제보다 적게 추정했다 — rows=15,000 추정 / 실제 900,000

  플래너의 생각: "바깥이 1.5만 건뿐이네. Nested Loop로 안쪽 인덱스를 1.5만 번
                  찍는 게 제일 싸겠다."
  실제로 일어난 일: 안쪽 인덱스 조회가 90만 번 실행된다.

    Nested Loop  (actual rows=900000 loops=1)
      ->  Seq Scan on episodes  (rows=15000)  (actual rows=900000)   <- 60배 빗나감
      ->  Index Scan on series  (rows=1)      (actual loops=900000)  <- 여기서 폭발

  한 번에 0.05ms인 인덱스 조회도 90만 번이면 45초다. 계획 자체는 "인덱스를 타는"
  멀쩡한 모양이라, 계획 텍스트만 보고는 무엇이 잘못됐는지 알기 어렵다.
  단서는 오직 estimated rows와 actual rows의 자릿수 차이뿐이다.

[방향 B] 실제보다 많게 추정했다 — rows=15,000 추정 / 실제 40

  플래너의 생각: "1.5만 건이면 Nested Loop는 비싸다. 반대편 테이블을 통째로 읽어
                  해시 테이블을 만들자."
  실제로 일어난 일: 40건 처리하자고 수백만 행짜리 테이블을 전부 읽어 해시로 쌓는다.
                    work_mem을 넘으면 디스크로 흘러넘쳐(Batches > 1) 더 느려진다.

  결론: 오차의 방향이 어느 쪽이든 계획이 뒤집힌다. 그리고 이 오차는 데이터가
        늘어날수록 커지는 게 아니라, 데이터 분포가 바뀔 때마다 무작위로 커진다.
```

한 문장으로 압축하면 — **컬럼이면 플래너가 "몇 건인지"를 알고 계획을 세우지만, jsonb 내부 키는 플래너에게 안개다. 안개 속에서는 경로 선택이 운에 맡겨진다.**

진단은 간단하다. `EXPLAIN ANALYZE`에서 **추정 rows와 actual rows가 자릿수로 어긋나는 노드**를 찾으면 된다. 그 노드가 jsonb 표현식 조건을 달고 있으면 이 사슬이다.

```sql
-- jsonb 컬럼의 통계에 무엇이 들어 있는지 직접 확인해 본다
SELECT attname, n_distinct, null_frac, avg_width
  FROM pg_stats
 WHERE tablename = 'episodes' AND attname = 'format_attrs';
-- attname      | n_distinct | null_frac | avg_width
-- format_attrs |         -1 |         0 |       412
--
-- n_distinct = -1 은 "행마다 전부 다른 값"이라는 뜻이다. 문서 전체를 하나의 값으로
-- 봤으니 당연하다. 여기 어디에도 "genre 키의 값 분포"는 없다 — 그래서 상수 추정이다.
```

이 손실만은 §3-1의 표현식 인덱스가 **부수 효과로 되돌려 준다.** 표현식 인덱스를 만들면 `ANALYZE`가 그 식의 결과에 대한 통계까지 수집하기 때문이다. 통계만 따로 원하면 인덱스 없이 `CREATE STATISTICS`로 만들 수도 있다. 이 점이 PostgreSQL에서 표현식 인덱스가 단순한 "검색 가속" 이상인 이유다.

### 1-5. 반납 ③ 좁은 갱신 — 키 하나 고쳐도 문서 전체가 새 튜플로 다시 쓰인다

전제부터. PostgreSQL에서는 어떤 컬럼이든 UPDATE가 **제자리 덮어쓰기가 아니다.** 옛 튜플(행의 한 버전)의 헤더에 "이 XID가 지웠다"는 뜻으로 `xmax`를 찍고, 바뀐 값이 담긴 **새 튜플 버전을 힙에 삽입**한다([MVCC](./11-mvcc-postgresql.md)). 옛 버전은 그 자리에 남아 있다가 VACUUM이 회수할 때 사라진다.

그러면 정당한 반문이 하나 나온다 — **"컬럼이든 jsonb든 어차피 새 튜플인데 뭐가 다른가?"** 좋은 질문이고, 답은 **쓰는 양**과 **인덱스** 두 가지다.

| | 정식 컬럼 갱신 (`view_count = view_count + 1`) | jsonb 내부 키 갱신 (`jsonb_set(attrs, '{view_count}', ...)`) |
|---|---|---|
| 새 튜플에 담기는 양 | 행 폭만큼 (수십~수백 바이트) | **문서 전체** (10KB면 10KB, 100KB면 100KB) |
| 안 바뀐 큰 값 | TOAST에 나가 있으면 **포인터만 복사**, 청크는 손 안 댐 | 문서 전체가 새로 만들어지므로 **새 TOAST 청크 세트**를 다시 쓴다 |
| 인덱스 | 인덱스된 컬럼이 아니면 HOT 업데이트 → **인덱스 갱신 0회** | `attrs`에 GIN·표현식 인덱스가 있으면 HOT이 깨져 **테이블의 모든 인덱스**에 새 엔트리 |
| WAL | 새 튜플 크기만큼 | 새 튜플 + TOAST 청크 전부. 그대로 레플리카까지 흘러간다 |
| 죽은 튜플 | 행 폭만큼 | 문서 크기만큼. VACUUM이 치울 때까지 공간을 차지한다 |

여기 나온 **HOT**을 한 문장으로 정의하고 간다. HOT(Heap-Only Tuple) 업데이트란 "바뀐 컬럼이 어떤 인덱스에도 들어 있지 않고, 새 버전을 같은 페이지에 놓을 자리가 있을 때" PostgreSQL이 **인덱스를 하나도 건드리지 않고** 새 버전을 놓는 최적화다. 인덱스는 여전히 옛 튜플의 주소를 가리키고, 힙 페이지 안의 포인터 사슬이 최신 버전으로 안내한다. 인덱스가 5개인 테이블에서 HOT이 되느냐 마느냐는 **UPDATE 한 번의 쓰기가 1회냐 6회냐**를 가른다.

그래서 jsonb 내부 키 갱신의 실제 순서는 이렇다.

```text
UPDATE ... SET attrs = jsonb_set(attrs, '{view_count}', ...) WHERE id = $1

 ⑴ 읽기      저장된 문서 전체를 읽는다. TOAST에 나가 있으면 청크를 모아 압축을 푼다.
 ⑵ 만들기    메모리에서 값 하나를 바꾼 "새 문서 전체"를 만든다. jsonb_set은 제자리
              수정이 아니라 새 jsonb 값을 반환하는 함수다.
 ⑶ 쓰기      그 새 문서를 새 튜플에 담아 힙에 쓴다. 2KB를 넘으면 다시 압축해
              새 TOAST 청크 세트로 나간다.
 ⑷ WAL       ⑶ 전부가 WAL에 실린다. 스트리밍 복제라면 그대로 레플리카로 흘러간다.
 ⑸ 남기기    옛 튜플과 옛 TOAST 청크는 죽은 튜플로 남아 VACUUM을 기다린다.
 ⑹ 인덱스    attrs에 GIN이나 표현식 인덱스가 걸려 있으면 "인덱스된 컬럼이 바뀐" 것이라
              HOT이 깨진다 → 그 테이블의 모든 인덱스에 새 엔트리. GIN은 pending list까지.
```

문서가 100KB면 숫자 하나 바꾸려고 100KB를 다시 쓰고, 100KB가 WAL로 레플리카까지 흘러가고, 100KB짜리 죽은 튜플이 bloat로 남는다. 그동안 잡고 있는 **행 락 보유 시간**도 그만큼 늘어난다 — 락 보유 시간은 같은 행에 몰리는 UPDATE의 초당 처리량 상한을 직접 결정하므로([핫 로우](./23-high-frequency-counter-hot-row.md)), 이 사슬은 조용히 동시성 상한까지 갉아먹는다.

이 사슬에서 바로 도출되는 금지 사항이 하나 있다 — **JSON 안에 카운터를 넣지 마라.** 가장 잦은 쓰기를 가장 비싼 방식으로 하는 최악의 조합이다.

```sql
-- before: JSON 안의 조회수 — 조회 1건마다 문서 전체가 새 튜플로 재기록
UPDATE episodes
   SET format_attrs = jsonb_set(format_attrs, '{view_count}',
                                to_jsonb((format_attrs->>'view_count')::bigint + 1))
 WHERE id = $1;
-- 읽기 → 새 문서 생성 → 새 튜플(+ 새 TOAST 청크) → WAL → 죽은 튜플.
-- 문서에 썸네일 URL 목록, 태그, 번역 상태 같은 다른 키가 클수록 "조회수 +1"의 비용이 커진다.
-- 즉 비용이 바꾸는 값의 크기가 아니라 "옆에 뭐가 같이 들어 있는가"에 비례한다.

-- after: 카운터는 컬럼 — 좁은 새 튜플, TOAST 무관, HOT 가능
UPDATE episodes SET view_count = view_count + 1 WHERE id = $1;
-- (물론 초고빈도 카운터는 컬럼이어도 핫 로우 문제가 남는다 —
--  그건 별도 문서(./23-high-frequency-counter-hot-row.md)의 사슬이다.
--  JSON은 거기에 "문서 전체 재기록"을 한 겹 더 얹을 뿐이다.)
```

이 비용은 추측이 아니라 관찰할 수 있다.

```sql
-- ① HOT 비율과 죽은 튜플 — 사슬이 돌고 있는지
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct,
       n_live_tup, n_dead_tup
  FROM pg_stat_user_tables WHERE relname = 'episodes';
-- hot_pct가 낮고 n_dead_tup이 빠르게 쌓이면 이 사슬이다.

-- ② 문서 크기 — 한 번의 갱신이 얼마를 다시 쓰는지
SELECT pg_size_pretty(avg(pg_column_size(format_attrs))::bigint) AS avg_doc
  FROM episodes TABLESAMPLE SYSTEM (1);

-- ③ TOAST 몫 — 문서가 별도 테이블로 얼마나 밀려나 있는지
SELECT pg_size_pretty(pg_table_size('episodes'))     AS total,
       pg_size_pretty(pg_relation_size('episodes'))  AS heap_only,
       pg_size_pretty(pg_table_size('episodes')
                      - pg_relation_size('episodes')) AS toast_and_fsm;
```

### 1-6. 반납 ④ 타입·제약 — 불변식이 DB에서 애플리케이션 관례로 내려간다

`price numeric(12,2) NOT NULL`, `FOREIGN KEY (product_id)`, `UNIQUE (sku)` — 정식 컬럼의 제약은 **DB가 지킨다.** 여기서 "DB가 지킨다"는 말의 무게를 정확히 새겨야 한다. 어떤 코드 경로로 들어오든, 어떤 배치가 넣든, 운영자가 psql에서 직접 넣든 뚫리지 않는다는 뜻이다. 애플리케이션 검증은 "그 코드를 통과한 데이터"만 지키지만, DB 제약은 **그 테이블에 들어오는 모든 데이터**를 지킨다.

jsonb 컬럼에는 이 검사가 하나도 없다. DB가 보장하는 것은 "문법적으로 올바른 JSON인가"뿐이다.

```sql
-- 세 행 모두 "유효한 JSON"이라 INSERT가 전부 성공한다
INSERT INTO products (attrs) VALUES ('{"price": 1000}');      -- 숫자
INSERT INTO products (attrs) VALUES ('{"price": "1000"}');    -- 문자열
INSERT INTO products (attrs) VALUES ('{"prcie": 1000}');      -- 오타 키

-- 그리고 조회는 조용히 틀리거나, 시끄럽게 죽는다
SELECT count(*) FROM products WHERE (attrs->>'price')::numeric > 500;
-- 숫자 1000    → 텍스트 '1000' → 캐스트 성공 → 포함
-- 문자열 "1000" → 텍스트 '1000' → 캐스트 성공 → 포함 (타입이 달라도 조용히 섞인다)
-- 오타 행       → 키 없음 → NULL → 제외 → 아무 에러 없이 2건이 답으로 나온다
--
-- 그리고 누군가 '{"price": "1,000"}' 을 넣는 순간, 이 쿼리는 그 한 행 때문에
-- ERROR: invalid input syntax for type numeric 로 통째로 실패한다.
-- 어제까지 잘 돌던 대시보드가 오늘 죽는데, 배포는 없었다.

-- 섞여 있다는 사실은 이렇게 사후에야 드러난다
SELECT jsonb_typeof(attrs->'price') AS t, count(*) FROM products GROUP BY 1;
--  t      | count
--  number |  81234
--  string |    417   <- 언제부터 들어왔는지 아무도 모른다
--  (null) |      3   <- 키 자체가 없는 행
```

[정규화 문서 2-3](./04-normalization-vs-denormalization.md)의 결론을 그대로 가져온다 — **불변식이 DB 제약이 아니라 애플리케이션 관례에 살면, 그 관례를 모르는 새 코드 경로·DB 직접 수정에 뚫린다.** 반정규화 컬럼은 불변식 "하나"를 관례로 내려보냈지만, jsonb 컬럼은 **그 안의 모든 필드에 대해 그것을 기본값으로 만든다.** 차이가 정도가 아니라 범위다.

여기에 두 가지가 더 얹힌다.

**참조 무결성 부재.** `{"author_id": 42}`가 삭제된 작가를 가리켜도 DB는 모른다. FK가 있었다면 작가 삭제 시점에 `ERROR: update or delete on table "authors" violates foreign key constraint`로 막혔을 일이, jsonb에서는 아무 일도 일어나지 않는다. 고아(orphan) 참조가 **검출 수단 없이** 쌓이고, 발견은 보통 "작가 이름이 안 나온다"는 CS 문의로 온다. 되짚어 세려면 `jsonb_array_elements`로 전 행을 전개해 대조하는 배치를 따로 만들어야 한다.

**NULL의 세 얼굴.** SQL `NULL`(컬럼 자체가 비었다), JSON `null`(키는 있고 값이 null), 키 부재(키 자체가 없다)가 서로 다른 의미로 공존한다. 컬럼이었다면 상태는 "값이 있다 / NULL이다" 둘뿐이었는데 셋이 된 것이다. PostgreSQL 연산자는 이 셋을 다르게 본다.

```sql
-- 같은 "값이 없다"를 세 연산자가 다르게 본다
WITH t(doc) AS (VALUES ('{"k": null}'::jsonb), ('{}'::jsonb), ('{"k": 1}'::jsonb))
SELECT doc,
       doc->>'k'          AS arrow_text,   -- text  : JSON null과 키 부재를 둘 다 SQL NULL로 뭉갠다
       doc->'k'           AS arrow_jsonb,  -- jsonb : JSON null은 'null', 키 부재는 SQL NULL — 구분된다
       doc ? 'k'          AS has_key       -- bool  : 값과 무관하게 키 존재만 본다
  FROM t;
--  doc          | arrow_text | arrow_jsonb | has_key
--  {"k": null}  | (NULL)     | null        | t
--  {}           | (NULL)     | (NULL)      | f
--  {"k": 1}     | 1          | 1           | t
--
-- "값을 명시적으로 비운 것"과 "아직 그 필드가 없던 옛 세대 문서"를 구분해야 하는데,
-- ->> 만 쓰면 둘이 똑같이 NULL로 보인다. 집계와 마이그레이션이 여기서 어긋난다.
```

### 1-7. 반납 ⑤ 이름 — 컬럼명 오타를 아무도 잡아주지 않는다

앞의 넷보다 사소해 보이지만 실무에서 가장 자주 물리는 것이 이것이다. **컬럼은 이름이 스키마에 등록돼 있다.** `INSERT INTO products (prcie) VALUES (1000)`은 `ERROR: column "prcie" of relation "products" does not exist`로 즉시 죽는다. 오타가 프로덕션에 도달할 수 없다.

jsonb에서는 오타가 **새 키를 만드는 정상 동작**이다. 문법적으로 올바른 JSON이니 아무 문제가 없다. 그래서 다음 세 가지가 조용히 벌어진다.

- **쓰기는 성공한다.** 그 행에는 `prcie` 키가 생겼고 `price` 키는 없다.
- **읽기는 예외 없이 그 행을 뺀다.** `attrs->>'price'`가 `NULL`이라 `WHERE (attrs->>'price')::numeric > 500`에서 조용히 제외된다. 에러가 없으니 아무도 모른다.
- **발견은 집계가 어긋난 뒤에 온다.** "500원 넘는 상품이 어제보다 왜 줄었지?"에서 시작해 `jsonb_object_keys`로 키 목록을 세어 봐야 나온다.

이 손실은 §3-6의 `CHECK` 제약으로 **부분적으로만** 되살 수 있다. "이 키들은 반드시 있어야 한다"(`?&`)는 강제할 수 있지만, "이 키들 말고는 있으면 안 된다"까지 강제하려면 허용 키 목록을 CHECK 안에 적어야 하고 그러면 사실상 컬럼 정의를 CHECK로 재현하는 셈이 된다. 그 지점에 도달했다면 답은 이미 나온 것이다 — **컬럼으로 만들어라.**

```sql
-- 오타 키를 사후에 찾아내는 쿼리 — 정기적으로 돌려야 한다는 사실 자체가 대가다
SELECT k, count(*) AS rows
  FROM products, LATERAL jsonb_object_keys(attrs) AS k
 GROUP BY k
 ORDER BY rows;
--  k       | rows
--  prcie   |    3   <- 소수 등장 키가 오타 후보다
--  color   |  812
--  price   | 81651
```

### 1-8. 그럼에도 사는 것 — 정확히 네 가지

대가를 다 말했으니 편익도 정확히 말해야 양면이 조립된다. 반납만 나열하면 "그럼 절대 쓰지 말라는 거냐"가 되고, 그건 답이 아니다. JSON 컬럼이 사는 것은 정확히 다음 넷이다.

1. **희소(sparse) 속성**: 행마다 키 집합이 진짜 다를 때, NULL투성이 컬럼 수십 개나 EAV(Entity-Attribute-Value, 속성을 행으로 늘어놓는 별도 테이블) 없이 담는다. EAV는 조회할 때마다 여러 행을 피벗해야 해서 쿼리가 급격히 복잡해지는데, jsonb는 그 복잡도를 한 컬럼으로 접는다.
2. **DDL 없는 필드 추가**: 수억 건 테이블에 `ALTER TABLE ... ADD COLUMN`을 내는 리스크([무중단 DDL](./14-online-ddl-zero-downtime-schema-change.md))를 피한다 — 단, 이 자유의 청구서는 §3-5에서 온다. 공짜로 사라진 것이 아니라 청구지가 바뀐 것이다.
3. **외부 원문의 무손실 보존**: 스키마의 주인이 우리가 아닌 데이터(결제 PG 응답, 웹훅 페이로드)를 그대로 둔다. "바이트 그대로"가 요구면 `json`(또는 `text`)이다 — jsonb는 키 순서·공백·중복 키를 정규화한다(1-1).
4. **문서 단위 접근**: 항상 통째로 읽고 통째로 쓰는 부속 데이터를 조인 없이 한 번에 가져온다. 이 경우엔 사슬 ③(문서 전체 재기록)이 대가가 아니다 — 어차피 전체를 다시 쓸 참이었기 때문이다.

**얻는 것이 이 넷 중 하나가 아니면 JSON을 쓸 이유가 없다.** "테이블 하나 더 만들기 귀찮아서"는 이 목록에 없다.

## 2. 판별 체크리스트 — "귀찮아서"와 "비정형이라"를 가르는 네 질문

### 2-1. 네 질문

§1의 반납 목록을 실무에서 3분 안에 쓸 수 있는 형태로 접으면 네 개의 예/아니오 질문이 된다. 각 질문은 §1의 사슬 하나와 정확히 짝을 이룬다 — 그래서 답을 외울 필요가 없고, 사슬을 기억하면 질문이 도출된다.

| 질문 | "예"라면 | 근거 사슬 |
|---|---|---|
| ⑴ 그 안의 값이 WHERE·JOIN·GROUP BY·ORDER BY 에 등장하는가? | 컬럼 | 반납 ①·② — 조건 검색·집계는 정렬 사본과 통계가 둘 다 필요하다 |
| ⑵ 모든 행이 (거의) 같은 키 집합을 갖는가? | 컬럼 | 스키마가 균일하면 JSON은 컬럼을 문서 안에 숨긴 것일 뿐이다 |
| ⑶ 쓰기 후 부분 수정이 잦은가? (카운터·상태·수정 가능한 항목) | 컬럼 | 반납 ③ — 문서 전체가 새 튜플로 재기록된다 |
| ⑷ 다른 테이블을 참조하거나 UNIQUE·NOT NULL·타입 보장이 필요한가? | 컬럼 / 별도 테이블 | 반납 ④·⑤ — DB가 지켜야 할 불변식과 이름 |

**하나라도 "예"면 컬럼(또는 별도 테이블)이다.** 넷 다 "아니오"인 데이터만 JSON 후보다.

이 표가 곧 "정규화가 귀찮아서 JSON"의 정체이기도 하다 — ⑴~⑷에 "예"인 데이터인데 테이블을 만들기 싫어서 JSON에 넣은 것. 그것은 반정규화(대가를 알고 관리하는 의도적 중복)도 아니고, **정규화 실패의 새 포장**이다. 반정규화는 "정규화를 알고 나서 일부러 어기는 것"이고, 이것은 "정규화를 안 하고 티가 안 나게 덮은 것"이다.

⑵에 실무적 판정법 하나 — 논쟁하지 말고 **데이터에 물어본다.** 테이블에서 문서를 표본으로 뽑아 키 집합을 세면 1초 만에 결론이 난다.

```sql
SELECT k, count(*) AS rows
  FROM (SELECT jsonb_object_keys(attrs) AS k
          FROM products TABLESAMPLE SYSTEM (1)) s   -- 페이지 기준 1% 표본
 GROUP BY k ORDER BY 2 DESC;
-- 거의 모든 행에 나오는 키가 있으면 그 키들은 컬럼이었어야 한다(⑵ 예).
-- 키 집합이 진짜로 제각각이면 희소 속성이 맞다.
-- 덤: 아주 소수의 행에만 있는 키는 1-7의 오타 후보다.
```

### 2-2. 목록으로 인출한다 — JSON이 맞는 경우 5 / 피해야 할 경우 5

면접에서 "경우에 따라 다르다"로 끝내지 말고 목록을 그대로 꺼낸다. 판단 기준을 안다는 것과 사례를 인출할 수 있다는 것은 다른 능력이고, 뒤쪽이 실무 경험을 드러낸다.

**JSON이 맞는 경우**

1. **외부 시스템 원문 보존** — 결제 PG 응답, 웹훅 페이로드, 외부 API 응답. 스키마의 주인이 우리가 아니고, write-once(한 번 쓰고 안 고침)이며, 감사·분쟁 대응용이다.
2. **행마다 키가 다른 희소 속성** — 상품 카테고리별 규격, 콘텐츠 형식별 메타데이터. 컬럼으로 펼치면 NULL이 대부분인 컬럼 수십 개가 된다.
3. **통째로 읽고 통째로 쓰는 문서** — 사용자 설정(preferences), 에디터 레이아웃 상태. 항상 전체를 로드하고 전체를 저장하며, 조건 검색이 없다.
4. **감사·이력 스냅샷** — "그 시점에 이 객체가 어떤 모양이었나"를 통째로 남기는 변경 이력. 조회는 PK나 시각 컬럼으로 하고 문서는 그냥 보여 준다.
5. **아직 형태가 굳지 않은 실험 속성** — 단, "굳는 순간 승격한다"는 출구 규칙(§3-6)이 함께 있을 때만.

**JSON을 피해야 할 경우**

1. **조회 조건·정렬·집계 대상** — `WHERE`·`ORDER BY`·`GROUP BY`에 오르는 값. 반납 ①. 특히 **조인의 축**이 되는 값은 통계 부재(반납 ②)로 계획까지 망친다.
2. **다른 테이블과의 관계** — 주문의 상품 목록, 글의 태그처럼 반대 방향 조회("이 상품이 포함된 주문", "이 태그의 글")가 필요한 1:N. 별도 테이블이다.
3. **모든 행이 같은 키를 갖는 균일 데이터** — 그냥 컬럼이다.
4. **잦은 부분 갱신, 특히 큰 문서의** — 카운터, 상태값, 재고. 반납 ③. 문서가 클수록(TOAST) 한 번의 갱신이 비싸진다.
5. **DB가 지켜야 할 불변식이 있는 값** — 금액, 식별자, 필수값, 유일값. 반납 ④.

### 2-3. 도메인에 대 보기 — 세 사례와 반례 하나

**(a) 웹툰 에피소드 메타데이터 — 공통은 컬럼, 형식별 희소 속성만 JSON**

```sql
-- before: "메타데이터는 다 JSON에" — 조회 조건까지 문서 안에 넣었다
CREATE TABLE episodes (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    meta  jsonb   -- {"title":..., "no":12, "published_at":..., "is_free":true,
                  --  "genre":"로맨스", "cut_count":48, "bgm_track":"..."}
);
-- 목록 화면: WHERE (meta->>'is_free')::boolean ORDER BY meta->>'published_at'
-- → 반납 ① 그대로(Seq Scan + Sort). 게다가 회차 번호 UNIQUE도, 공개일 NOT NULL도 못 건다.
-- → published_at을 텍스트로 정렬하므로 '2026-9-1' 같은 값이 섞이면 정렬 순서까지 틀린다.

-- after: 모든 에피소드가 갖는 것 + 조회 조건은 컬럼, 형식별 속성만 JSON
CREATE TABLE episodes (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    series_id     bigint      NOT NULL REFERENCES series(id), -- "시리즈의 에피소드 목록" 조회 + 참조 무결성
    episode_no    int         NOT NULL,                       -- UNIQUE(series_id, episode_no)로 중복 회차 차단
    title         text        NOT NULL,
    published_at  timestamptz NOT NULL,                       -- 정렬·범위 조건 → 타입이 있어야 정렬이 맞는다
    is_free       boolean     NOT NULL,                       -- 목록 필터 조건
    view_count    bigint      NOT NULL DEFAULT 0,             -- 잦은 갱신 → 반납 ③을 피한다
    format_attrs  jsonb       NOT NULL DEFAULT '{}',          -- 형식별 희소 속성만:
    --   컷툰:   {"cut_count":48, "swipe_hint":true}
    --   효과툰: {"bgm_track":"...", "vibration_points":[...]}
    --   일반:   {}
    UNIQUE (series_id, episode_no)
);
CREATE INDEX idx_episodes_series_published ON episodes (series_id, published_at DESC);
```

판별 흐름을 소리 내어 말하면 이렇게 된다 — "제목·회차·공개일·무료여부는 모든 행에 있고(⑵ 예) 목록의 필터·정렬 조건이라(⑴ 예) 컬럼. 조회수는 잦은 갱신(⑶ 예) 컬럼. 컷 수·BGM 트랙은 형식마다 있거나 없고(⑵ 아니오), 조회 조건이 아니며(⑴ 아니오), 등록 후 거의 안 바뀌고(⑶ 아니오), 참조·유일 제약이 없다(⑷ 아니오) — JSON."

**(b) 결제 PG 원문 응답 — 원문은 JSON으로 보존, 조회 키는 컬럼으로 추출**

```sql
-- before: 응답 통째로만 저장 — 나중에 "승인번호로 찾아 주세요"가 오면 Seq Scan
CREATE TABLE payment_approvals (
    id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    gateway_response jsonb NOT NULL
);

-- after: 이중 저장 — 원문(무손실·write-once) + 조회용 컬럼(추출·인덱스·제약)
CREATE TABLE payment_approvals (
    id               bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id         bigint        NOT NULL REFERENCES orders(id), -- 주문 → 결제 조회
    gateway_name     text          NOT NULL,
    gateway_tid      text          NOT NULL,   -- PG사 거래 ID: 대사·환불 조회 키
    approval_no      text,                     -- 승인번호: CS 검색 키
    approved_amount  numeric(12,2) NOT NULL,   -- 금액: 정산 집계·정합성 검증 → 타입이 반드시 필요
    status           text          NOT NULL,   -- 상태: 필터 + 갱신 대상
    gateway_response json          NOT NULL,   -- 원문 바이트 그대로. 절대 수정하지 않는다
    UNIQUE (gateway_name, gateway_tid)         -- 같은 거래가 두 번 기록되는 사고를 DB가 막는다
);
CREATE INDEX idx_payment_approvals_approval_no ON payment_approvals (approval_no);
```

핵심은 **"원문 보존"과 "조회"를 같은 컬럼에 시키지 않는 것**이다. 두 요구는 성격이 다르다.

원문은 PG사가 스키마의 주인이고, 필드가 언제 늘어날지 모르며, 분쟁 시 "그때 PG사가 정확히 뭐라고 응답했나"의 증거다. 그래서 JSON이 맞다 — 그리고 "정확히"가 요구이므로 정규화하는 `jsonb`가 아니라 **원문 텍스트를 보존하는 `json`**이다(1-1). jsonb에 넣으면 키 순서가 바뀌고 공백이 사라져서, 나중에 "PG사가 보낸 응답과 우리가 저장한 것이 바이트 단위로 같다"를 주장할 수 없다. 조회하지 않을 컬럼이니 `json`의 "읽을 때마다 파싱" 비용은 문제가 되지 않는다.

반면 우리가 조회·집계·정합성 검증에 쓰는 값(거래 ID, 승인번호, 금액, 상태)은 **우리 도메인의 컬럼**이다. 저장 시 한 번 추출해 두 곳에 쓴다. 이것은 중복이지만, 원문은 write-once라 어긋날 갱신 경로가 없어 [정규화 문서의 "스냅샷"](./04-normalization-vs-denormalization.md)과 같은 성격(동기화 대상이 아닌 중복)이다.

**(c) 사용자 설정 — 통째로 읽고 쓰는 문서, 단 "집계 대상"은 빼낸다**

```sql
CREATE TABLE user_preferences (
    user_id          bigint      PRIMARY KEY REFERENCES users(id),
    marketing_opt_in boolean     NOT NULL,  -- 법적 근거 + 발송 대상 추출(WHERE) → 컬럼
    schema_version   int         NOT NULL,  -- §3-5의 세대 관리
    prefs            jsonb       NOT NULL,  -- {"theme":"dark","reader":{"direction":"vertical",
    updated_at       timestamptz NOT NULL   --  "auto_scroll_speed":3}, "notif":{...}}
);
```

테마·뷰어 방향·자동 스크롤 속도는 클라이언트 버전마다 키가 늘고, 항상 설정 화면에서 통째로 읽어 통째로 저장하며, 조건 검색이 없다 — JSON이 맞다. 특히 반납 ③(문서 전체 재기록)이 여기서는 대가가 아니다. 어차피 전체를 다시 쓸 참이었고, 문서도 작아 TOAST로 나가지 않기 때문이다.

그러나 "마케팅 수신 동의자에게 발송"은 `WHERE` 조건이고 법적 기록이라(⑴·⑷ 예) 컬럼으로 빼낸다. 그리고 "다크 모드 사용자 비율"을 대시보드에 띄우자는 요구가 오면? 집계 대상이 됐으니(⑴ 예) 승격하거나, 설정 변경 이벤트를 따로 적재해 거기서 센다 — jsonb Seq Scan 집계를 운영 DB에 매일 돌리는 선택지는 없다.

**(d) 반례 — 주문의 상품 목록을 JSON 배열로**

```sql
-- 안티패턴: orders.items jsonb = [{"product_id":7,"qty":2,"price":1000}, ...]
-- 필요한 조회를 네 질문에 대 보면 전부 "예"다:
--   "상품 7이 포함된 주문"    → WHERE 대상 (⑴)   — GIN @> 로 되긴 하지만 통계는 여전히 없다
--   "상품별 판매량 집계"      → GROUP BY 대상 (⑴) — jsonb_array_elements 전개 후 집계, 매번 전 행
--   "product_id 유효성"       → FK (⑷)           — jsonb 안의 값에는 FK를 못 건다
--   "부분 취소 시 qty 감소"   → 부분 갱신 (⑶)     — 배열 원소 하나 고치려고 문서 전체 재기록
--   모든 주문이 같은 키 구조   → 균일 (⑵)
-- 답: order_items 테이블. 이건 비정형이 아니라 1:N이다.
```

이 반례가 "정규화가 귀찮아서 JSON"의 전형이다. 주문 항목은 형태가 불규칙해서가 아니라 **테이블을 하나 더 만들기 싫어서** JSON에 들어간다. PostgreSQL에서는 "GIN 걸면 되잖아요"가 따라붙는데 — 되는 것은 ⑴의 검색 하나뿐이고, FK·부분 갱신·집계·통계는 그대로 남는다. 도구가 있다는 것과 써야 한다는 것은 다르다.

## 3. 인덱싱 우회와 스키마 진화 — 그리고 함께 들어야 할 안전망

### 3-1. 표현식 인덱스 — 값을 정렬 사본 안에 "존재하게" 만든다

반납 ①의 원인이 "값이 정렬 사본에 없다"였으니, 우회는 그 값을 **사본에 넣는 것**이다.

PostgreSQL의 1순위 도구는 **표현식 인덱스**(expression index)다. 일반 인덱스가 "이 컬럼의 값으로 정렬한 사본을 만들어라"라면, 표현식 인덱스는 **"이 식을 모든 행에 대해 계산한 결과값으로 정렬한 사본을 만들어라"**다. 인덱스 리프에는 식의 결과가 **물질화**(계산해서 실제로 저장)되어 정렬된다. 테이블 행은 한 바이트도 바뀌지 않는다 — 사본만 새로 생긴다.

```sql
-- 표현식 인덱스로 승격 — 테이블 재작성 없음, CONCURRENTLY면 쓰기도 안 막음
CREATE INDEX CONCURRENTLY idx_episodes_genre
    ON episodes ((format_attrs->>'genre'));
--                ^ 괄호가 두 겹인 것에 주의. 안쪽은 식, 바깥쪽은 인덱스 컬럼 목록의 괄호다.
ANALYZE episodes;   -- 통계까지 걷으려면 반드시 필요하다 (아래 ②)

-- 이제 같은 식을 쓴 조건은 인덱스를 탄다
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM episodes WHERE format_attrs->>'genre' = '스릴러';

 Bitmap Heap Scan on episodes  (cost=178.63..24211.40 rows=9030 width=40)
                               (actual time=2.310..41.877 rows=9120 loops=1)
   Recheck Cond: ((format_attrs ->> 'genre'::text) = '스릴러'::text)
   Heap Blocks: exact=8714
   Buffers: shared hit=8746
   ->  Bitmap Index Scan on idx_episodes_genre  (cost=0.00..176.37 rows=9030 width=0)
                                                (actual time=1.402..1.403 rows=9120 loops=1)
         Index Cond: ((format_attrs ->> 'genre'::text) = '스릴러'::text)
         Buffers: shared hit=32
 Planning Time: 0.21 ms
 Execution Time: 42.6 ms
-- 읽은 블록 60,504 → 8,746 (인덱스 32 + 힙 8,714). 실행 시간 1,876ms → 43ms.
-- 그리고 rows=9030 — 상수 15,000이 아니라 실제(9,120)에 붙은 추정이다(아래 ②).
```

세 가지를 함께 말하면 원리를 이해했다는 신호다.

**① 식 일치 조건 — 이 우회의 가장 흔한 함정.** 플래너는 쿼리의 식이 인덱스 정의의 식과 **같은 형태**일 때만 인덱스를 매칭한다. "같은 형태"의 판정은 사람의 눈이 아니라 파싱된 식 트리 기준이라, 연산자·캐스트·결과 타입이 하나라도 다르면 매칭되지 않는다. 그리고 매칭에 실패해도 **에러가 나지 않는다** — 그냥 조용히 Seq Scan으로 돌아간다.

```sql
-- 인덱스는 numeric으로 캐스트한 식으로 만들었다
CREATE INDEX idx_products_price ON products (((attrs->>'price')::numeric));

-- 타는 조건: 인덱스 정의와 식이 정확히 같다
SELECT * FROM products WHERE (attrs->>'price')::numeric > 500;   -- Index Scan

-- 안 타는 조건들 — 전부 에러 없이 Seq Scan으로 돌아간다
SELECT * FROM products WHERE attrs->>'price' > '500';            -- text 비교. 식이 다르다
                                                                 -- 게다가 '90' > '500'이 참이라 결과도 틀린다
SELECT * FROM products WHERE (attrs->'price')::numeric > 500;    -- -> vs ->> : 다른 연산자
SELECT * FROM products WHERE (attrs->>'price')::float8 > 500;    -- 캐스트 타입이 다르다
SELECT * FROM products WHERE (attrs#>>'{price}')::numeric > 500;  -- #>> vs ->> : 결과는 같지만 식이 다르다
```

그래서 실무 규율은 **"이 식을 한 곳에만 적는다"**다. 리포지토리의 상수 문자열로 고정하거나, 아예 뷰(또는 §3-6의 생성 컬럼)를 만들어 애플리케이션이 식을 직접 쓰지 못하게 한다. 사람이 매번 손으로 적으면 언젠가 누군가 `#>>`를 쓰고, 그날 그 API만 조용히 1.8초가 된다.

**② 통계까지 따라온다 (가산점 포인트).** 표현식 인덱스가 있으면 `ANALYZE`가 **그 식의 결과에 대한 통계**를 함께 수집한다. 반납 ②(상수 선택도)가 이 순간 풀린다 — 위 계획에서 추정이 15,000에서 9,030으로 바뀐 이유다. 이것이 표현식 인덱스가 단순한 검색 가속이 아닌 이유이고, **조인의 축이 되는 jsonb 키에는 검색 속도보다 이쪽이 더 중요할 때도 있다.**

```sql
-- 인덱스 없이 통계만 원한다면 (인덱스 유지 비용을 안 내고 계획만 고치고 싶을 때)
CREATE STATISTICS stx_episodes_genre ON ((format_attrs->>'genre')) FROM episodes;
ANALYZE episodes;

-- 수집됐는지는 pg_stats에서 확인한다 (표현식 인덱스의 통계는 인덱스 이름으로 잡힌다)
SELECT most_common_vals, most_common_freqs
  FROM pg_stats WHERE tablename = 'idx_episodes_genre';
```

**③ 타입 고정 — 그리고 인덱스가 데이터 품질 검사기가 된다.** `((attrs->>'price')::numeric)` 인덱스는 생성 시 **모든 행에 대해 식을 계산**한다. 그래서 한 행이라도 `"1,000"`이 들어 있으면 `CREATE INDEX` 자체가 `ERROR: invalid input syntax for type numeric`로 실패한다. 이건 불편이 아니라 **공짜 데이터 검증**이다 — 반납 ④가 인덱스 생성 시점에 터져 주는 것이고, 프로덕션 조회가 터지기 전에 알게 된다. 동시에 이 장면은 우회의 한계도 보여 준다 — **우회는 반납 ①·②만 되사고, ③·④·⑤는 그대로 남는다.**

두 가지 변형이 더 있다.

**부분 인덱스와의 결합.** `CREATE INDEX ... ON episodes ((format_attrs->>'genre')) WHERE format_attrs ? 'genre'` — 그 키가 없는 행을 인덱스에서 아예 빼서 크기를 줄인다. 희소 속성일수록 효과가 크다(키가 10%의 행에만 있으면 인덱스도 10% 크기다). 단, 쿼리에도 같은 `WHERE` 조건이 들어 있어야 플래너가 "이 부분 인덱스로 답을 다 낼 수 있다"고 판단한다.

**생성 컬럼(STORED) + 일반 인덱스.** `ALTER TABLE episodes ADD COLUMN genre text GENERATED ALWAYS AS (format_attrs->>'genre') STORED` — 식의 결과를 아예 **정식 컬럼으로 만든다.** 정식 컬럼 이름으로 조회하니 ①의 식 일치 함정이 사라지고, 일반 인덱스·통계·`NOT NULL`·`CHECK`가 다 붙는다. 대신 값이 **행에도 저장**되어 테이블이 커지고, 기존 테이블에 추가하면 **테이블 재작성**(`ACCESS EXCLUSIVE` 잠금, [무중단 DDL](./14-online-ddl-zero-downtime-schema-change.md))이다. 큰 테이블에는 표현식 인덱스가 먼저이고, 생성 컬럼은 **"이 키는 이제 사실상 컬럼이다"라고 선언할 때**의 도구다.

> MySQL 대조: MySQL은 JSON 컬럼 자체에도, JSON 식에도 인덱스를 직접 걸지 못해 **생성 컬럼(`GENERATED ALWAYS AS (...) VIRTUAL`) + 인덱스**가 정석이다. VIRTUAL은 행에 값을 저장하지 않고 인덱스에만 물질화되며 추가가 메타데이터 변경만이라 싸다 — PostgreSQL에서 그 자리를 맡는 것이 표현식 인덱스다. 반대로 PostgreSQL의 생성 컬럼은 STORED만 있어 추가 시 테이블 재작성이라는 점이 다르다.

### 3-2. GIN — 키를 미리 정하지 않고 문서 안을 역색인한다 (가산점 포인트)

표현식 인덱스로 안 되는 경우가 있다. `tags: ["로맨스", "학원", "완결"]`처럼 **배열 원소가 조건**이 되는 경우다. 행 하나에 값이 여러 개라서, "정렬된 사본의 한 자리"에 넣을 수가 없다. 어느 태그를 그 자리에 넣을 것인가?

이때의 도구가 **GIN**(Generalized Inverted Index)이다. 이름의 inverted(역)가 핵심이다. B-tree가 "행 → 그 행의 값"을 정렬해 두는 것이라면, GIN은 **"값(키/원소) → 그 값을 가진 행들의 목록"**을 담는다. 책 뒤의 찾아보기(색인)와 같은 구조다 — 단어 하나에 그 단어가 나오는 페이지 번호들이 줄줄이 달려 있다. 그래서 한 행에 값이 여러 개여도 문제가 없다. 값마다 그 행 번호를 달아 두면 그만이다.

jsonb 컬럼 전체에 GIN을 걸면 문서 안의 **모든 키와 값**이 색인되므로, 어떤 키를 조회할지 **미리 정하지 않고도** 포함 검색이 된다. 이것이 표현식 인덱스와 갈리는 결정적 차이다.

```sql
CREATE INDEX CONCURRENTLY idx_episodes_attrs_gin
    ON episodes USING gin (format_attrs);              -- 연산자 클래스 기본값은 jsonb_ops

EXPLAIN (ANALYZE, BUFFERS)
SELECT id FROM episodes WHERE format_attrs @> '{"tags": ["완결"]}';
--                                          ^ @> 는 "왼쪽 문서가 오른쪽 문서를 포함하는가"

 Bitmap Heap Scan on episodes  (cost=412.08..38620.55 rows=3000 width=8)
                               (actual time=18.204..210.331 rows=51238 loops=1)
   Recheck Cond: (format_attrs @> '{"tags": ["완결"]}'::jsonb)
   Heap Blocks: exact=30112
   ->  Bitmap Index Scan on idx_episodes_attrs_gin  (cost=0.00..411.33 rows=3000 width=0)
                                                    (actual time=12.871..12.872 rows=51238 loops=1)
         Index Cond: (format_attrs @> '{"tags": ["완결"]}'::jsonb)
-- GIN은 항상 Bitmap 스캔으로 나온다: 인덱스에서 TID를 모아 비트맵을 만든 뒤 힙을
-- 페이지 순서대로 훑기 때문이다. Recheck Cond가 붙는 것도 정상이다 —
-- 비트맵이 페이지 단위로 흐려지면(lossy) 그 페이지의 행을 다시 검사해야 한다.
-- rows=3000은 또 상수 선택도다 — GIN은 통계를 만들어 주지 않는다(반납 ②는 안 풀린다).
```

**GIN이 지원하는 것과 못 하는 것**을 정확히 갈라 말할 수 있어야 한다. 여기가 이 소절의 핵심이다.

| | `jsonb_ops` (기본) | `jsonb_path_ops` |
|---|---|---|
| 색인하는 것 | 문서 안의 **모든 키와 모든 값**을 각각 별도 엔트리로 | **경로+값을 합친 해시** 하나만 |
| `@>` (포함) | 가능 | 가능 |
| jsonpath `@?` / `@@` | 가능 | 가능 |
| `?` (키 존재), `?|`, `?&` | 가능 | **불가** — 값 없이 키만으로는 찾을 수 없다 |
| 인덱스 크기 | 크다 (엔트리 수 = 키 수 + 값 수) | 작다 (엔트리 수 = 리프 경로 수) |
| `@>` 검색 속도 | 보통 (흔한 키 때문에 후보가 넓게 잡힌다) | 빠르다 (경로+값이 한 덩어리라 후보가 좁다) |
| 고르는 기준 | `?`로 키 존재를 물어야 한다면 이쪽 | 포함 검색만 한다면 이쪽 |

**어느 쪽이든 GIN이 못 하는 것**은 따로 못 박아 둔다. 역색인에는 **순서가 없기 때문이다.**

- **범위 조건 불가** — `attrs->>'price' > 500`, `BETWEEN`, `<`, `>`. 색인이 "값 → 행 목록"이라 값들 사이의 대소 관계가 구조에 없다. 범위를 원하면 표현식 B-tree다.
- **정렬 불가** — `ORDER BY attrs->>'published_at'`. 같은 이유다.
- **접두사 검색 불가** — `LIKE '스릴%'` 류. (문자열 안을 찾는 것은 `pg_trgm` 확장의 GIN이 별도로 맡는다.)
- **통계 없음** — 반납 ②는 GIN으로 풀리지 않는다. 추정은 여전히 상수다.

**대가**도 같은 호흡으로 말한다.

- **인덱스가 크다.** `jsonb_ops`는 문서 안의 모든 키와 모든 값을 엔트리로 만든다. 키가 20개인 문서라면 행 하나가 인덱스에 수십 개의 엔트리를 만드는 셈이다. 문서 내용에 따라 인덱스가 테이블 크기에 근접하거나 넘어서는 경우도 드물지 않다.
- **쓰기 비용이 높다.** INSERT/UPDATE 한 번이 키 수만큼의 엔트리를 만든다. 기본 설정(`fastupdate = on`)에서는 이 엔트리를 바로 트리에 넣지 않고 **pending list**라는 임시 목록에 모아 두었다가 나중에 병합한다. 쓰기는 싸지지만, 병합 전까지는 **읽기가 트리와 pending list를 둘 다 훑어야** 해서 조회가 느려진다. 병합은 VACUUM이나 pending list가 `gin_pending_list_limit`을 넘을 때 일어나는데, 그 순간 그 쿼리가 병합 비용을 뒤집어쓴다.
- **HOT이 깨진다.** `attrs`에 GIN이 있는 순간 그 컬럼을 바꾸는 모든 UPDATE가 "인덱스된 컬럼이 바뀐" 것이 되어 비-HOT이 된다(반납 ③). 즉 GIN을 거는 결정은 검색만의 결정이 아니라 **쓰기 비용의 결정**이다.

**범위를 좁혀 크기를 줄이는 방법**도 있다. 문서 전체가 아니라 실제로 검색하는 서브 문서에만 걸면 된다.

```sql
-- 문서 전체가 아니라 tags 배열만 색인 — 엔트리 수가 자릿수로 줄어든다
CREATE INDEX CONCURRENTLY idx_episodes_tags_gin
    ON episodes USING gin ((format_attrs->'tags') jsonb_path_ops);

-- 인덱스가 실제로 얼마나 큰지는 재 보면 된다. 세 방식을 나란히 재서 고른다.
SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size
  FROM pg_class
 WHERE relname IN ('episodes',
                   'idx_episodes_genre',       -- 표현식 B-tree: 키 하나만 뽑아 정렬 → 가장 작다
                   'idx_episodes_tags_gin',    -- 범위를 좁힌 path_ops GIN
                   'idx_episodes_attrs_gin')   -- 문서 전체 jsonb_ops GIN → 가장 크다
 ORDER BY pg_relation_size(oid) DESC;
-- 크기 순서는 데이터에 따라 달라지므로 외우지 말고 이 쿼리로 직접 재라.
-- 다만 "표현식 B-tree < path_ops GIN < 문서 전체 jsonb_ops GIN"이라는 순서 자체는
-- 엔트리 개수 정의에서 나오는 것이라 거의 항상 성립한다.
```

> MySQL 대조: 배열 원소 색인은 **멀티밸류 인덱스** — `CREATE INDEX ... ((CAST(attrs->'$.tags' AS CHAR(30) ARRAY)))`로 만들고 `MEMBER OF`, `JSON_CONTAINS`, `JSON_OVERLAPS`가 탄다. 단 "미리 정한 배열 하나"만 색인한다는 점에서 표현식 인덱스의 배열판이지, 키를 안 정해도 되는 GIN 같은 도구는 없다.

### 3-3. 우회의 한계 — 결국 "미리 정한 키"만 빠르다

우회를 말한 다음에는 반드시 한계를 붙인다. 여기서 답변의 깊이가 갈린다.

표현식 인덱스도 생성 컬럼도 **어떤 키를 색인할지 미리 정해야** 한다. 그런데 "미리 정해진, 모든 행이 갖는, 조회 조건인 키"는 — §2-1의 표로 돌아가면 — ⑴과 ⑵에 모두 "예"인 키다. 즉 **정의상 컬럼이었어야 하는 것**이다. 그래서 우회의 정직한 적용 범위는 아주 좁다.

> 문서의 **대부분이 진짜 비정형**이고, 그중 **한두 키만** 뒤늦게 조회 조건이 됐을 때 — 문서를 깨지 않고 그 키만 꺼내 색인하는 도구.

이 범위를 넘어서는 신호가 있다. **조회 키가 하나둘 늘어 표현식 인덱스가 다섯 개가 됐다면**, 그것은 우회가 아니라 "컬럼이어야 했던 것을 뒤늦게, 그리고 더 비싼 방식으로 컬럼으로 만들고 있는 것"이다. 인덱스 다섯 개의 유지 비용을 내면서 타입 검사도 제약도 없는 상태를 유지하고 있는 셈이니 양쪽 다 손해다. 그 시점엔 JSON에서 빼내 정식 컬럼으로 승격하는 게 맞다.

GIN처럼 키를 안 정하는 방식은 그 자유만큼 값을 치른다 — 인덱스 크기, 쓰기 비용, 비-HOT, 그리고 범위·정렬 조건에는 무력하고 통계는 여전히 없다. 정리하면 이렇다.

| 되사온 것 | 표현식 인덱스 | GIN |
|---|---|---|
| 반납 ① 인덱스 | 되산다 (미리 정한 키 한정, 범위·정렬 포함) | 되산다 (임의 키 포함 검색 한정, 범위·정렬 불가) |
| 반납 ② 통계 | **되산다** (`ANALYZE`가 식의 통계 수집) | 못 산다 (추정은 계속 상수) |
| 반납 ③ 좁은 갱신 | 못 산다. 오히려 **비-HOT을 유발해 악화**시킨다 | 못 산다. 악화 폭이 더 크다 (pending list까지) |
| 반납 ④ 타입·제약 | 못 산다 (단, 인덱스 생성이 타입 검사기 역할은 한다) | 못 산다 |
| 반납 ⑤ 이름 | 못 산다 | 못 산다 |

**공짜 우회는 없다.** 표를 한 줄로 요약하면 — 우회는 읽기를 되사올 뿐, 쓰기와 불변식은 되사오지 못한다.

### 3-4. 스키마 진화 — 마이그레이션이 없어진 게 아니라 코드로 옮겨간 것

§1-8의 편익 ②(DDL 없는 필드 추가)의 청구서가 여기서 온다. jsonb를 고르는 가장 흔한 명분이 "나중에 스키마가 바뀔 것 같아서"인데, 이 명분을 정확히 해부해야 한다.

컬럼과 JSON의 스키마 변경을 나란히 놓으면 차이가 보인다.

| | 정식 컬럼 (PostgreSQL) | JSON 필드 |
|---|---|---|
| 필드 추가 | `ADD COLUMN ... DEFAULT` 1회 — 상수 기본값이면 카탈로그만 고쳐 즉시 끝. **모든 행이 그 순간 같은 형태**가 된다 | 새로 쓰는 문서부터 키가 생긴다. **옛 행은 키가 없는 채로 영구 공존** |
| 필드 이름 변경 | `RENAME COLUMN` 1회 (카탈로그만 바뀐다) | 전 행 UPDATE(행마다 문서 전체 재기록, 반납 ③) 또는 **영원한 이중 읽기** |
| 타입 변경 | `ALTER COLUMN ... TYPE ... USING (...)` — DB가 변환·검증하고, 한 행이라도 실패하면 DDL 전체가 롤백된다 | 아무도 검증하지 않는다. 옛 타입 행과 새 타입 행이 섞인다 |
| 필드 삭제 | `DROP COLUMN` 1회 | `doc - 'key'` 전 행 UPDATE, 또는 그냥 방치(읽는 코드가 계속 무시) |
| 비용의 위치 | **DDL 시점에 한 번** (잠금·재작성 — 무중단 DDL이 어려운 이유) | **모든 읽기 코드에, 영원히** |

즉 JSON은 스키마 변경 비용을 **없앤 것이 아니다.** "DB의 DDL 한 번"에서 **"애플리케이션의 모든 읽기 경로, 무기한"**으로 옮긴 것이다. 배포마다 형태가 다른 세대(generation)의 행이 쌓이고, 읽는 코드는 지금껏 존재한 **모든 세대를 이해해야** 한다.

말로만 하면 와닿지 않으니 코드로 본다. 사용자 설정에서 "다크 모드 여부"를 세 번 리팩터링한 흔한 시나리오다.

```java
// 세대 v0 (2024): {"darkMode": true}              — boolean
// 세대 v1 (2025): {"theme": "dark"}               — 3값 enum으로 확장 (system 추가)
// 세대 v2 (2026): {"display": {"theme": "dark"}}  — 관련 설정을 묶으면서 한 단계 내림

// 컬럼이었다면 읽는 코드는 이렇다. 마이그레이션 한 번으로 모든 행이 같은 모양이 됐으므로
// 읽는 쪽에는 분기가 없다.
String theme = row.getString("theme");
```

```java
// jsonb라면 읽는 코드가 이렇게 된다. 세대가 데이터에 섞여 있으므로 코드가 전부 처리한다.
String theme(JsonNode prefs) {
    // v2: 가장 최신 형태부터 본다
    if (prefs.path("display").has("theme")) {
        return prefs.get("display").get("theme").asText();
    }
    // v1: 한 단계 위에 있던 시절
    if (prefs.has("theme")) {
        return prefs.get("theme").asText();
    }
    // v0: boolean이던 시절. true/false를 새 어휘로 번역한다
    if (prefs.has("darkMode")) {
        return prefs.get("darkMode").asBoolean() ? "dark" : "light";
    }
    // 세 세대 어디에도 없는 행 — 설정을 한 번도 저장하지 않은 사용자다
    return "system";
}
```

이 코드에서 봐야 할 것은 분기 자체가 아니라 **이 분기를 언제 지울 수 있는가**다. 답은 "v0·v1 형태의 행이 테이블에서 완전히 사라진 뒤"이고, 문제는 **그 시점을 알 방법이 기본적으로 없다**는 것이다. 그래서 이 분기는 대개 지워지지 않는다. 3년 뒤 신규 입사자가 `darkMode`가 뭔지 물어보고, 아무도 지워도 되는지 확신하지 못해 그대로 남는다.

그리고 이 분기는 한 곳에만 있는 것이 아니다. 설정을 읽는 곳이 웹 API, 앱 API, 배치, 어드민 네 군데면 네 곳 모두에 있어야 하고, 한 곳이라도 빠뜨리면 그 경로에서만 다크 모드가 안 먹는다. **컬럼이었다면 존재하지 않았을 버그 종류가 통째로 새로 생긴 것이다.**

여기서 두 가지 결론이 나온다. 첫째, **세대를 셀 수 있어야 한다** — 그래야 분기를 지울 시점을 판단할 수 있다. 둘째, **새 세대로 옮기는 작업을 누군가는 해야 한다** — 자동으로 사라지지 않는다. 이 둘을 담당하는 것이 다음 소절의 안전망 ①이다.

### 3-5. 안전망 ① 버전 필드 — 세대를 세고, 점진적으로 옮긴다

`schema_version`은 각 문서가 **어느 세대인지 스스로 표시**하게 하는 정수 컬럼이다. jsonb 안이 아니라 정식 컬럼으로 두는 것이 중요하다 — 이 값으로 세고 필터해야 하므로 ⑴에 "예"이기 때문이다.

이 컬럼이 있으면 앞 소절의 두 문제가 풀린다.

```sql
-- ① 세대를 셀 수 있다 — "그 분기를 지워도 되나?"에 숫자로 답한다
SELECT schema_version, count(*) FROM user_preferences GROUP BY 1 ORDER BY 1;
--  schema_version | count
--               0 |    412      <- 아직 남아 있다. v0 분기는 못 지운다
--               1 |  38102
--               2 | 2914883
-- 412가 0이 되는 날 v0 분기를 지우는 PR을 올린다. 추측이 아니라 조회 결과로 결정한다.
```

```java
// ② 읽기 시 업캐스팅 + 쓰기는 항상 최신 세대 — 점진 마이그레이션
public UserPreferences read(long userId) {
    var row = repo.findById(userId).orElseThrow();
    // 세대별로 다른 DTO로 역직렬화한 뒤 현재 모델로 끌어올린다(upcast).
    // 분기가 "어느 필드가 있나"를 추측하는 대신 "이 행은 몇 세대인가"를 읽으므로,
    // 3-4의 has() 사슬보다 의도가 명확하고 세대가 늘어도 사슬이 깊어지지 않는다.
    return switch (row.schemaVersion()) {
        case 0 -> upcastV0(mapper.readValue(row.prefs(), PrefsV0.class));
        case 1 -> upcastV1(mapper.readValue(row.prefs(), PrefsV1.class));
        case 2 -> mapper.readValue(row.prefs(), PrefsV2.class);
        // 모르는 세대를 만나면 조용히 기본값을 주지 않고 터뜨린다. 롤백된 배포가
        // 미래 세대의 문서를 읽는 상황을 무시하면 설정이 조용히 초기화된다.
        default -> throw new UnsupportedSchemaVersionException(row.schemaVersion());
    };
}

// 쓰기는 언제나 최신 세대로만 한다. 그래서 사용자가 설정을 한 번 저장할 때마다
// 그 행이 v2로 올라간다 — "읽기 시 점진 마이그레이션"이다.
// 활동이 없는 계정은 영원히 v0로 남으므로, 남은 잔여분은 야간 배치로 훑어 올린다.
public void save(long userId, UserPreferences prefs) {
    repo.upsert(userId, CURRENT_SCHEMA_VERSION, mapper.writeValueAsString(prefs));
}
```

```sql
-- ③ 잔여분 배치 — PK 범위로 잘라 짧은 트랜잭션 여러 번으로 돌린다.
--    한 문장으로 412만 건을 돌리면 그 자체가 긴 트랜잭션이 되어 VACUUM을 막는다.
UPDATE user_preferences
   SET prefs = jsonb_build_object('display',
                   jsonb_build_object('theme',
                       CASE WHEN (prefs->>'darkMode')::boolean THEN 'dark' ELSE 'light' END))
             || (prefs - 'darkMode'),
       schema_version = 2
 WHERE schema_version = 0
   AND user_id IN (SELECT user_id FROM user_preferences
                    WHERE schema_version = 0 ORDER BY user_id LIMIT 1000);
-- 행마다 문서 전체 재기록이므로(반납 ③) 대용량이면 이 배치 자체가 WAL·bloat·VACUUM
-- 부하 작업이다. 트래픽이 낮은 시간에, 배치 사이에 간격을 두고 돌린다.
```

**버전 필드가 없으면 "지금 어떤 세대가 몇 건 남았는지"조차 셀 수 없다.** 세지 못하면 옮길 수도, 분기를 지울 수도 없다. 그래서 이것이 안전망 목록의 첫 줄이다.

### 3-6. 안전망 ② DB 층 스키마 검증, ③ 승격 규율

**안전망 ② — 검증은 DB 층에 두는 것이 우선이다.** 이유는 반납 ④와 정확히 같다. 애플리케이션 DTO 검증은 그 코드를 통과한 쓰기만 지키지만, **psql 직접 수정과 아직 만들어지지 않은 새 코드 경로까지 막는 것은 DB 제약뿐**이다.

PostgreSQL에는 JSON Schema 문서를 통째로 검사하는 함수가 **내장돼 있지 않다**(`pg_jsonschema` 같은 확장은 있다). 대신 `CHECK` 안에 `jsonb_typeof`·`?&`·`->>` + `IN`을 조합하면 필수 키, enum, 타입, 범위를 DB가 지키게 만들 수 있다.

```sql
-- before: 검증도 버전도 없는 jsonb — 무엇이 들어 있는지 아무도 보장하지 못한다
CREATE TABLE user_preferences (
    user_id bigint PRIMARY KEY,
    prefs   jsonb  NOT NULL
);

-- after: 안전망 ① 버전 필드 + ② DB 층 스키마 검증
CREATE TABLE user_preferences (
    user_id        bigint PRIMARY KEY,
    schema_version int    NOT NULL DEFAULT 2,
    prefs          jsonb  NOT NULL,
    CONSTRAINT chk_prefs_shape CHECK (
        jsonb_typeof(prefs) = 'object'                                 -- 배열이나 스칼라가 들어오는 것부터 막는다
        AND prefs ?& array['theme', 'reader']                          -- 필수 키: 둘 다 있어야 한다
        AND prefs->>'theme' IN ('light', 'dark', 'system')             -- enum: 오타 값을 막는다
        AND jsonb_typeof(prefs->'reader') = 'object'                   -- 중첩 객체의 타입까지 본다
        AND prefs->'reader'->>'direction' IN ('vertical', 'horizontal')
        AND (
            NOT (prefs->'reader' ? 'auto_scroll_speed')                -- 선택 키: 없어도 되고,
            OR (jsonb_typeof(prefs->'reader'->'auto_scroll_speed') = 'number'  -- 있으면 숫자여야 하고,
                AND (prefs->'reader'->>'auto_scroll_speed')::numeric BETWEEN 1 AND 5)  -- 범위도 맞아야 한다
        )
    )
);
-- 이제 {"theme": 3}도, {"reader": {}}도, psql에서 직접 넣어도 INSERT가 실패한다.
-- 불변식이 애플리케이션 관례에서 다시 DB 제약으로 올라왔다(반납 ④의 부분 회복).
-- "부분"인 이유: 여기 안 적은 키는 여전히 아무거나 들어올 수 있다(반납 ⑤는 안 풀린다).

-- 이미 데이터가 있는 큰 테이블에 붙일 때는 두 단계로 나눈다.
-- 한 번에 붙이면 전 행 검증 동안 테이블을 잠근다.
ALTER TABLE user_preferences
      ADD CONSTRAINT chk_prefs_shape CHECK (...) NOT VALID;   -- 새 쓰기부터만 검사. 즉시 끝난다
-- (여기서 위반 행을 조회해 배치로 정리한 뒤)
ALTER TABLE user_preferences VALIDATE CONSTRAINT chk_prefs_shape;  -- 쓰기를 막지 않고 기존 행 검증
```

`CHECK`가 따라가기 어려울 만큼 스키마가 자주 바뀐다면, 최소한 애플리케이션 DTO + Bean Validation으로 **쓰기 경로를 하나로 단일화**한다. 둘 중 하나는 반드시 있어야 한다 — 둘 다 없으면 그 컬럼은 아무도 모양을 모르는 채로 몇 년 자란다.

```java
// 애플리케이션 층 검증 — DB 층과 이중으로 건다
public record PrefsV2(
        @NotNull @Pattern(regexp = "light|dark|system") String theme,
        @NotNull @Valid Reader reader) {

    public record Reader(
            @NotNull @Pattern(regexp = "vertical|horizontal") String direction,
            @Min(1) @Max(5) Integer autoScrollSpeed) {}   // null 허용 = 선택 키
}
// 매핑 메모: Hibernate 6은 @JdbcTypeCode(SqlTypes.JSON)으로 jsonb 컬럼에 바로 매핑된다.
//            pgjdbc로 문자열을 직접 넣을 땐 SQL 쪽에서 $1::jsonb로 캐스트해야 타입이 맞는다.
```

**안전망 ③ — 승격 규율.** 팀 규칙으로 문서화한다: **"JSON 안의 키가 조회 조건·집계·정렬 대상이 되는 순간 컬럼(또는 표현식 인덱스, 또는 별도 테이블)으로 승격한다."**

이것이 안전망인 이유는, jsonb의 실패가 대개 **한 번의 잘못된 결정이 아니라 수정하지 않은 채 흘려보낸 시간**에서 오기 때문이다. 처음 넣을 때는 정말로 비정형이었는데, 6개월 뒤 기획이 "이걸로 필터링하고 싶다"고 하고, 그때 "일단 되니까" 두면 그대로 굳는다. 출구 규칙이 없는 JSON은 "임시"라는 이름으로 영구화된다.

규율을 실제로 작동시키려면 **점검 시점**을 정해 둔다. jsonb 키가 `WHERE`에 등장하는 PR은 리뷰에서 승격 여부를 묻고, 분기마다 §2-1의 표본 쿼리로 키 분포를 다시 재서 "거의 모든 행에 있는 키"를 찾아낸다. 그 키가 발견되면 이미 컬럼이었어야 하는 것이다.

## 4. 꼬리질문 대비 포인트

### "jsonb 안의 값으로 WHERE를 걸면 왜 느린가요? 어떻게 우회하나요?"

사슬로 답한다 — B-tree는 **컬럼 값을 정렬해 둔 사본**인데 jsonb 내부 키는 컬럼이 아니라 **어떤 사본에도 값이 없다** → 탐색 불가 → **Seq Scan** → 행마다 **jsonb 키 탐색 후 비교**(I/O + CPU 이중 비용, `Rows Removed by Filter`) → 큰 문서일수록 TOAST 청크까지 → 게다가 **내부 키 통계가 없어** 추정 rows가 상수(등호 조건이면 0.5%)라 조인 계획까지 틀어진다.

우회의 원리는 하나다 — **값을 사본에 존재하게 만들기.** **표현식 인덱스** `((attrs->>'genre'))`를 걸면 인덱스 리프에 값이 물질화되고, `ANALYZE`가 그 식의 통계까지 만들어 줘서 추정도 같이 고쳐진다(`CONCURRENTLY`면 테이블 재작성도 쓰기 차단도 없다). 배열 원소나 임의 키 포함 검색이면 **GIN**(`jsonb_ops`/`jsonb_path_ops`, `@>`)인데 이쪽은 통계를 안 만들어 주고 범위·정렬에도 못 쓴다.

그리고 한계를 붙인다 — 우회는 미리 정한 키만 빠르게 하므로, 조회 키가 늘어 표현식 인덱스가 다섯 개가 됐다면 그건 컬럼이어야 했던 것이다.

### "jsonb 안의 키 하나만 바꾸는 UPDATE는 싸지 않나요? PostgreSQL은 어차피 새 튜플이잖아요."

좋은 반문이고, 답은 **"새 튜플인 건 같지만 쓰는 양과 인덱스가 다르다"**다.

컬럼 하나를 바꾼 새 튜플은 행 폭만큼이고, 안 바뀐 TOAST 값은 **포인터만 복사**되며, 인덱스된 컬럼이 아니면 HOT이라 인덱스를 하나도 안 건드린다. jsonb 내부 키 하나를 바꾸면 `jsonb_set`이 **새 문서 전체**를 만들고 → 새 튜플 + **새 TOAST 청크 전부** → 그 전부가 **WAL**(레플리카로도) → 옛 문서 전체가 **죽은 튜플**로 VACUUM 대기다. 재기록량이 바꾼 값의 크기가 아니라 **문서 전체 크기**에 비례한다. 여기에 GIN이나 표현식 인덱스가 걸려 있으면 비-HOT이라 **테이블의 모든 인덱스**에 새 엔트리까지 붙는다.

그래서 **jsonb 안에 카운터·상태 같은 잦은 부분 갱신 대상을 두지 않는다** — 가장 잦은 쓰기를 가장 비싼 방식으로 하는 조합이다. 반대로 통째로 읽고 통째로 쓰는 작은 문서(사용자 설정)는 어차피 전체 재기록이라 이 비용이 문제가 안 된다 — 그래서 그쪽이 jsonb에 맞는 것이다. 관찰은 `pg_stat_user_tables`의 `n_tup_hot_upd / n_tup_upd` 비율과 `n_dead_tup`으로 한다.

### "1년 뒤 jsonb 안의 필드 이름을 바꿔야 합니다. 컬럼이면 RENAME 한 번인데, JSON은 뭐가 다른가요?"

컬럼은 카탈로그 한 번으로 **모든 행이 즉시 같은 형태**가 되지만, JSON은 DDL이 없는 대신 **옛 형태의 행이 영구 공존**한다. 선택지는 둘뿐이다.

(a) **전 행 UPDATE** — `SET doc = (doc - 'old') || jsonb_build_object('new', doc->'old') WHERE doc ? 'old'`를 PK 범위로 잘라 배치 실행한다. 행마다 문서 전체 재기록이라 대용량이면 그 배치 자체가 WAL·bloat·VACUUM 부하 작업이다. (b) **영원한 이중 읽기** — 읽기 코드가 옛 이름과 새 이름을 둘 다 이해한다. 그리고 그 분기는 옛 형태 행이 0건이 됐다는 것을 확인하기 전까지 지울 수 없는데, `schema_version`이 없으면 확인할 방법이 없어서 사실상 영구화된다.

즉 JSON은 스키마 변경 비용을 없앤 게 아니라 **DB의 DDL 한 번 → 애플리케이션의 모든 읽기 경로, 무기한**으로 옮긴 것이다. 게다가 읽는 곳이 웹·앱·배치·어드민 네 군데면 네 곳 모두에 분기가 있어야 하고, 한 곳을 빠뜨리면 그 경로에서만 조용히 값이 안 나온다 — 컬럼이었다면 존재할 수 없는 버그다.

감당하는 장치는 **`schema_version` 필드**(세대 표시 → 읽기 시 업캐스팅 → 쓰기는 항상 최신 세대 → 잔여분 배치 마이그레이션 → 0건이 되면 분기 삭제)와 **스키마 검증**(`CHECK` + jsonb 연산자, 기존 테이블엔 `NOT VALID` → `VALIDATE`)이다.

### "주니어가 '상품 속성은 카테고리마다 달라서 attrs jsonb에 다 넣겠다'는 PR을 올렸습니다. 어떤 질문을 던지시겠어요?"

체크리스트를 질문으로 바꾼다.

⑴ "이 속성들 중 **검색 필터·정렬·집계**에 쓰이는 게 있나요?" — 가격·브랜드·색상처럼 필터가 되는 것은 컬럼(또는 표현식 인덱스). ⑵ "**모든 상품이 갖는** 키가 있나요?" — 있으면 그건 컬럼이다. 논쟁하지 말고 `jsonb_object_keys` 표본 쿼리로 세어 보자고 한다. ⑶ "등록 후 **자주 바뀌는** 값이 있나요?" — 재고·판매 상태는 컬럼. ⑷ "다른 테이블을 **참조**하거나 **유일·필수**여야 하는 값이 있나요?" — 브랜드 ID·SKU는 컬럼/FK.

넷을 통과한 진짜 희소 속성(의류의 소재·세탁법, 가전의 소비전력)만 jsonb다. 그리고 두 가지를 더 요구한다 — **검증**(어떤 키·타입이 허용되는지 `CHECK` 또는 DTO)과 **승격 규칙**("필터가 되는 순간 컬럼으로").

"GIN 걸면 검색은 되는데요"가 오면 — 검색 하나는 되지만 FK·부분 갱신·통계·정렬·오타 검출은 그대로라고 짚는다. 이 질문 세트가 곧 "귀찮아서"와 "비정형이라"를 가르는 리뷰 기준이다.

### "결제 PG 원문 응답을 jsonb로만 저장했는데, CS팀에서 '승인번호로 검색'을 요구합니다. 어떻게 하시겠어요? 그리고 처음부터 어떻게 설계했어야 하나요?" (시니어 변별 포인트)

**지금**: 승인번호는 조회 키가 됐으니(⑴ 예) 승격한다. 가장 싼 경로는 **표현식 인덱스** — `CREATE INDEX CONCURRENTLY ... ON payment_approvals ((gateway_response->>'approvalNo'))`. 기존 행을 다시 쓰지 않고, 테이블 재작성도 없으며, `CONCURRENTLY`라 쓰기도 막지 않는다(단 트랜잭션 밖에서 실행해야 하고, 실패하면 INVALID 인덱스가 남으므로 지우고 재시도한다). 단 PG사마다 응답 필드명이 다르면 `COALESCE(resp->>'approvalNo', resp->>'approval_no')` 식이 되어 §3-1 ①의 식 일치가 깨지기 쉬우므로, 그 경우엔 nullable 정식 컬럼을 추가하고(상수 기본값 없는 nullable 추가는 카탈로그 변경만이라 싸다) 배치로 채운 뒤 일반 인덱스를 건다.

**처음부터**: **이중 저장**이 정답이었다. 원문 `gateway_response`는 write-once 무손실 보존(스키마의 주인이 PG사이고, 분쟁 시 증거)이라 JSON이 맞고, "받은 그대로"가 요구이므로 정규화하는 `jsonb`가 아니라 **`json`**(또는 `text`)으로. jsonb에 넣으면 키 순서와 공백이 바뀌어 "바이트 단위로 같다"를 주장할 수 없다는 것까지 말하면 1-1을 이해한 것이다. **우리가 조회·집계·정합성 검증에 쓰는 값**(거래 ID, 승인번호, 금액, 상태)은 저장 시점에 추출해 정식 컬럼으로 둔다.

트레이드오프를 양면으로 말하면 — 대가는 "같은 값이 두 곳에 있는 중복"이지만, 원문은 갱신 경로가 없어 어긋날 수 없는 **스냅샷 성격의 중복**이라 동기화 장치가 필요 없다. 편익은 조회 키가 인덱스를 타고, 금액에 `numeric NOT NULL`, 거래 ID에 `UNIQUE`를 걸어 **불변식을 DB로 되돌린다**는 것이다. "JSON이냐 컬럼이냐"의 이분법이 아니라 **"원문 보존과 조회는 다른 요구이고, 다른 컬럼(그리고 다른 타입)이 맡는다"**까지 가면 이 질문에서 변별된다.

### "MySQL로 물어보면 답이 달라지는 부분은?" (경험 대조)

판별 규율(네 질문·안전망)은 같고, 도구와 비용 구조 다섯 지점이 다르다.

① **타입과 문법** — MySQL은 `JSON` 타입 하나(내부적으로 바이너리)이고 경로를 `->>'$.genre'`처럼 JSON path 문자열로 쓴다. PostgreSQL은 `json`/`jsonb` 둘이고 `->>'genre'`·`#>>'{a,b}'`·`@>`·`?` 연산자에 jsonpath가 따로 있다. "원문 바이트 보존"을 원할 때 PostgreSQL은 `json`이라는 선택지가 있지만 MySQL은 `text`로 내려가야 한다.

② **인덱스 도구** — MySQL은 JSON 컬럼에도 JSON 식에도 인덱스를 직접 못 걸어 VIRTUAL 생성 컬럼 + 인덱스가 정석이고(메타데이터 변경만이라 추가가 싸다), 배열은 멀티밸류 인덱스다. PostgreSQL은 표현식 인덱스(+ 표현식 통계)와, 키를 미리 정하지 않는 GIN이 있다 — 대신 STORED 생성 컬럼 추가는 테이블 재작성이다.

③ **부분 갱신** — MySQL 8.0은 `JSON_SET`/`JSON_REPLACE`/`JSON_REMOVE`가 크기가 늘지 않는 등 조건을 만족하면 **제자리 부분 갱신**을 하고 binlog에도 부분 갱신 로그를 남길 수 있다(조건이 까다로워 설계 가정으로 삼을 수는 없지만). PostgreSQL은 MVCC라 예외 없이 **문서 전체가 새 튜플**이고 TOAST 청크까지 다시 쓴다 — 반납 ③이 더 무겁다.

④ **스키마 검증** — MySQL은 `JSON_SCHEMA_VALID`로 JSON Schema를 `CHECK`에 바로 넣을 수 있지만, PostgreSQL은 내장 함수가 없어 `CHECK` + jsonb 연산자 조합이거나 확장(`pg_jsonschema`)이다.

⑤ **통계** — 둘 다 내부 키의 통계가 없어 추정이 상수인 것은 같지만, PostgreSQL은 표현식 인덱스(또는 `CREATE STATISTICS`)가 그 식의 통계를 만들어 준다는 출구가 있다.

이 다섯을 짚으면 "jsonb 문법을 안다"가 아니라 "저장 구조에서 비용을 도출한다"로 들린다.

## 한 줄 요약

**jsonb 컬럼은 행마다 다른 데이터를 DDL 없이 담는 자유를 사는 대신 인덱스(정렬 사본에 값이 없어 Seq Scan + 행마다 키 탐색)·통계(내부 키 분포를 모르니 추정이 상수가 되어 조인 방식까지 뒤집힌다)·좁은 갱신(키 하나 바꿔도 문서 전체가 새 튜플 + TOAST + WAL + 죽은 튜플)·타입/제약(불변식이 DB에서 앱 관례로 강등되고 오타 키도 조용히 저장된다)을 반납하는 거래이므로, "조회·집계 대상인가 / 모든 행이 같은 키인가 / 부분 갱신이 잦은가 / DB가 지킬 불변식인가"에 하나라도 "예"면 컬럼이고, 넷 다 "아니오"인 외부 원문(바이트 보존이 요구면 정규화하지 않는 `json`)·희소 속성·통째로 읽고 쓰는 문서만 jsonb에 둔다. 쓰기로 했다면 조회 조건이 된 키는 표현식 인덱스(`CONCURRENTLY`, 통계까지 따라온다)나 GIN(포함 검색만, 범위·정렬·통계는 못 산다)으로 승격하고, `CHECK` + jsonb 연산자(또는 DTO)로 검증하며, `schema_version`으로 세대를 세어 분기를 지울 시점을 판단하는 안전망을 함께 든다. 스키마 진화의 정체를 정직하게 말하는 것이 이 문항의 마지막 관문이다 — jsonb는 마이그레이션을 없앤 것이 아니라 DB의 DDL 한 번을 애플리케이션 읽기 코드의 영구 분기로 옮긴 것이고, PostgreSQL은 도구가 풍부해서 "되니까 쓴다"의 유혹이 큰데 되는 것과 써야 하는 것은 다르다.**
