# `LIKE '%kw%'`와 검색 전환 기준 — 인덱스는 "왼쪽부터 정렬된 사전"이라 중간 일치는 시작점이 없다

> 핵심 관전 포인트: **B+Tree 인덱스는 문자열을 **첫 글자부터** 정렬해 둔
> 사전이다. `LIKE '나무%'`는 "나무"로 시작하는 첫 장을 펼쳐 **연속 구간
> 하나**만 읽으면 되지만, `LIKE '%나무%'`는 첫 글자를 모르니 **트리를 내려갈
> 시작점을 찍을 수 없다** — 사전에서 "…나무"로 끝나는 단어를 찾으려면 첫
> 장부터 끝 장까지 넘겨야 하는 것과 같다. 그래서 풀스캔이고, 비용은 **행 수에
> 선형**이다: 전 행 순차 읽기 + 행마다 문자열 패턴 매칭(CPU) + filesort, 이게
> QPS만큼 곱해져 커넥션 점유 시간이 늘고 풀이 마르면 검색과 무관한 기능까지
> 번진다. 대응은 세 층위 — ① **LIKE 안에서 버티기**(접두 일치로 요구 협상 /
> 역방향 생성 컬럼 / 정규화 생성 컬럼 / 자체 n-gram 토큰 테이블 / 선행 필터로
> 스캔 폭 축소) ② **풀텍스트 인덱스**(InnoDB FULLTEXT + ngram 파서 —
> **역색인**으로 "중간 일치"를 "토큰 등호 조회"로 바꾼다. 대가: 색인 크기,
> 쓰기 비용, 형태소 분석 부재, 필터·정렬 결합 약함) ③ **검색 엔진
> (Elasticsearch)** — 형태소·오타·동의어·관련도·패싯·부하 격리가 필요할 때.
> 대가: 운영할 클러스터 하나, RDB와의 **동기화와 최종 일관성**, 장애 도메인
> 추가. 전환 판단은 감이 아니라 **데이터량 · QPS · 일치 유형 · 정확도 요구 ·
> 필터/정렬 결합 · 신선도 · 격리** 체크리스트로 하고, "무엇이 넘으면 다음
> 층위로 간다"를 팀 문서(ADR)에 숫자로 박아 둔다.**

## 0. 질문 + 의도

**질문**: "`LIKE '%keyword%'` 검색이 인덱스를 못 타는 이유는? 풀텍스트
인덱스와 검색 엔진(Elasticsearch) 전환은 어떤 기준으로 판단하나요?"

관련 질문:
"인덱스를 걸었는데도 풀스캔이 발생하는 경우는 어떤 경우인가요?" (원인 ③으로
LIKE가 등장 — [풀스캔 원인 6종](02-index-not-used-full-scan.md) 3-3절)
"Elasticsearch를 검색에 사용할 때 RDB와의 동기화는 어떻게 하나요? 색인 지연은
어떻게 다루나요?" (12장 NoSQL — `questions/12-nosql.md`)

**출제 의도**: rationale의 표현 그대로 — "중간 일치 검색이 **인덱스 구조상
불가능함**을 알고, **풀텍스트 인덱스로 버틸 수 있는 규모**와 **검색 엔진
도입(운영 비용, 동기화 문제 — 12장)의 문턱**을 판단하는지 — **'검색 기능
추가해주세요'라는 흔한 요구의 숨은 비용을 산정하는 능력**이다." 즉 "LIKE는
인덱스 못 탐"이라는 사실 확인이 아니라, 기획자가 툭 던진 한 줄 요구를 받았을 때
**세 층위(LIKE 우회 / 풀텍스트 / 검색 엔진)의 비용과 한계를 양쪽 다 놓고
어디서 멈출지 결정하는 판단 과정**을 말할 수 있는지 본다.

> 이 문서는 모의면접 **전** 학습용이다. 4장 기본 구간에서 반복 확인된 횡단
> 약점 네 가지를 해당 지점마다 명시적으로 겨냥한다 —
> **① 비용을 "메커니즘 사슬"로**(1-3절: 시작점을 못 잡는 원리 → 풀스캔이
> 데이터 증가에 선형인 사슬), **② 트레이드오프 양면**(3-4절·4-2절: 풀텍스트와
> 검색 엔진 각각의 대가), **③ 안전망을 팀 기준으로 고정**(5절: 숨은 비용
> 체크리스트와 전환 트리거를 문서·도구에 박기), **④ 목록 인출**(2절 "LIKE로
> 버티는 우회 5가지", 4-1절 "전환 신호 5가지"를 번호 붙은 목록으로).
> `LIKE '%kw%'`가 풀스캔 원인 중 하나라는 사실은 이미
> [풀스캔 원인 6종](02-index-not-used-full-scan.md)에 있으니 여기서는 반복하지 않고
> **원리의 깊이와 전환 판단**에 지면을 쓴다.

## 1. 원리 — 왜 "시작점"이 없는가

### 1-1. 인덱스는 사전이다: 첫 글자부터 정렬돼 있다

[인덱스와 B+Tree](01-index-and-bplus-tree.md)에서 정리했듯 B+Tree의 리프는
**인덱스 컬럼 값 기준으로 정렬된 연결 리스트**다. 문자열 컬럼이면 그 정렬
기준은 **첫 글자, 같으면 둘째 글자, …** — 사전과 정확히 같다.

```text
idx_webtoons_title 의 리프 (title 기준 정렬)
  … │ 나 혼자만 레벨업 │ 나무 위의 집 │ 나무늘보 일기 │ 나쁜 남자 │ … │ 사과나무 아래 │ … │ 헬로 나무 │ …
      ▲ '나' 구간 시작                   ▲ '나' 구간 끝

LIKE '나무%'  →  루트에서 '나무'로 내려가 ★ 시작점 ★ 을 찍고, '나무'가 아닌 값이
                 나올 때까지 오른쪽으로 → [나무 위의 집, 나무늘보 일기] 연속 구간 하나.

LIKE '%나무%' →  '나무'가 들어간 제목은 '나…'에도, '사…'에도, '헬…'에도 흩어져 있다.
                 어느 글자로 시작하는지 모르니 루트에서 내려갈 방향이 없다.
                 = 시작점을 찍을 수 없다 = 리프 전체를 처음부터 끝까지 훑는다.
```

**사전 비유**: "나무로 시작하는 단어"는 ㄴ 항목을 펴고 '나무' 페이지로 바로
간다. 그런데 **"…나무로 끝나는 단어"**(사과나무, 소나무, 참나무)는? 사전은 끝
글자로 정렬돼 있지 않으니 **첫 장부터 끝 장까지 한 단어씩 확인**하는 수밖에
없다. 국어사전에 "역순 사전"(단어를 뒤집어 정렬한 사전)이 따로 존재하는 이유가
바로 이것이고, 2절의 "역방향 컬럼" 우회는 그 역순 사전을 DB에 만드는 것이다.

### 1-2. 정확히 말하면 "인덱스를 못 쓴다"가 아니라 "인덱스로 **탐색(seek)** 을 못 한다"

면접에서 한 단계 정밀하게 말할 지점이다. `LIKE '%kw%'`도 **인덱스를 읽을 수는
있다**. 조회 컬럼이 인덱스 안에 다 있으면(커버링) 옵티마이저는 테이블 대신
**인덱스 전체를 순차로 훑는** 쪽을 고른다 — `EXPLAIN`에 `type: index`,
`Extra: Using where; Using index`로 나온다.

```sql
-- title 인덱스가 있고 SELECT 컬럼이 id, title 뿐이면
SELECT id, title FROM webtoons WHERE title LIKE '%나무%';
-- type: index  ← "인덱스 풀스캔". 테이블(모든 컬럼)보다 작은 사본을 훑으니
--               테이블 풀스캔(type: ALL)보다 싸긴 하다. 하지만 여전히 N에 선형.
```

즉 **"타냐 못 타냐"가 아니라 "seek(시작점 찍고 구간만 읽기)이냐 scan(전부
읽기)이냐"** 가 본질이고, `%kw%`는 seek이 구조적으로 불가능하다. 커버링으로
얻는 건 **상수배 개선**이지 **선형을 로그로 바꾸는 개선이 아니다**. 데이터가
10배 되면 여전히 10배 느려진다.

### 1-3. 비용 사슬 — 풀스캔은 데이터 증가에 **선형**이다

> **약점 ① 겨냥** — "느려진다", "부하가 온다"에서 멈추지 말고 **이름 붙은
> 사슬**로 말한다. 특히 "왜 지금은 안 느린데 나중에 장애가 되는가"를 선형성으로
> 설명할 수 있어야 한다.

```text
LIKE '%kw%' 한 번의 비용 (행 수 N)
  ① 리프/데이터 페이지 전부 읽기     — 순차 I/O. 페이지 수 ∝ N.
     (버퍼 풀에 다 올라가 있으면 메모리 스캔, 넘치면 디스크)
  ② 행마다 문자열 패턴 매칭          — CPU. (평균 문자열 길이) × N.
  ③ 통과한 행을 정렬                 — filesort. 인덱스 정렬 순서를 못 쓴다
     (시작점 없이 훑었으니 결과가 view_count 순일 리 없다)
  ④ LIMIT 20이어도 ①~③은 끝까지     — 상위 20개를 알려면 전부 봐야 한다
  ──────────────────────────────────────────────────────────────
  한 건당 응답 시간 ∝ N
  × QPS  ⇒  동시에 점유되는 커넥션 수 ∝ N × QPS       (리틀의 법칙)
  ⇒ 커넥션 풀 고갈 → 검색과 무관한 결제·조회수 갱신·에피소드 조회가 커넥션 대기
  ⇒ 장애 반경이 "검색 느림"에서 "서비스 전체 지연"으로 확산
  부수 효과: 큰 테이블 풀스캔이 버퍼 풀의 자주 쓰는 페이지를 밀어낸다(오염)
  → 다른 쿼리의 캐시 적중률↓ → 디스크 I/O↑ (InnoDB는 midpoint 삽입으로
    완화하지만 반복 풀스캔 앞에선 완전하지 않다)
```

**"지금은 빠른데요?"의 함정**: 작품 테이블이 5천 건이면 페이지 수십 장, 전부
버퍼 풀 안이라 `%kw%`도 수 ms다. 문제는 이 비용이 **N에 선형**이라 **조용히
자란다**는 것이다. 5천 건에서 5ms면 50만 건에서 500ms, 5천만 건(댓글·에피소드
규모)에서 50초다. 그리고 그 사이 어느 날 — 배포도 없이 — 임계를 넘는다. 이게
4장 뒤쪽 "배포 없었는데 DB CPU가 올랐다" 문항의 전형적 정답 중 하나(**데이터
증가 자체가 변경**)다. 검색 기능의 진짜 비용은 **오늘의 응답 시간이 아니라
기울기**로 산정해야 한다.

커넥션 점유 → 풀 고갈 사슬의 자세한 메커니즘은
[커넥션 수와 처리량](15-connection-count-vs-throughput.md)에 있다.

### 1-4. 그럼 `LIKE 'kw%'`는 왜 타는가 — 그리고 그마저 안 타는 세 경우

접두 일치는 옵티마이저가 **범위 조건**으로 바꿔 처리한다:
`title LIKE '나무%'` ≡ `title >= '나무' AND title < ('나무' 접두사의 상한값)`.
시작점과 끝점이 있으니 seek 후 연속 구간 하나 — `type: range`.

다만 접두 일치도 다음 셋 중 하나면 못 탄다. 전부
[풀스캔 원인 6종](02-index-not-used-full-scan.md)에서 도출되는 것들이다:

```sql
-- ❌ ①번 원인(컬럼에 함수): 대소문자 무시하려고 LOWER를 씌움 → 원본 값이 정렬된 인덱스와 무관
SELECT * FROM webtoons WHERE LOWER(title) LIKE 'solo%';
-- ✅ 대소문자 무시 콜레이션(_ci)이면 함수 없이도 무시된다. 아니면 정규화 생성 컬럼(2절)
SELECT * FROM webtoons WHERE title LIKE 'solo%';

-- ❌ ⑥번 원인(낮은 선택도): '가%'가 전체 30%면 옵티마이저가 풀스캔을 고른다 — 옳은 판단(부류 B)
SELECT * FROM webtoons WHERE title LIKE '가%';

-- ❌ 코드는 접두처럼 보이는데 실행은 중간 일치: 사용자 입력에 %가 섞여 들어옴
--    keyword = "%나무" → 'title LIKE ?' 바인딩 값이 '%나무%'가 된다
String kw = request.getKeyword();               // "%나무"
query.setParameter("kw", kw + "%");             // → '%나무%'  ← 접두 일치가 깨짐
// ✅ %, _ 를 이스케이프하거나 제거하고 바인딩한다 (LIKE 와일드카드 인젝션 방지)
```

## 2. 층위 ① — LIKE 안에서 버티는 우회 5가지 (목록으로 인출)

> **약점 ④ 겨냥** — "풀텍스트나 ES로 가야죠"로 바로 점프하면 **중간 선택지가
> 없는 사람**으로 보인다. 도구를 바꾸기 전에 RDB 안에서 할 수 있는 다섯
> 가지를 **번호로** 꺼내고, 각각 "어떤 요구까지 커버하고 무엇을 못 하는지"를
> 붙인다. 기억 고리: **협상 · 역순 · 정규화 · 토큰 · 선행필터**.

| # | 우회 | 커버하는 요구 | 대가 / 한계 |
|---|---|---|---|
| ① | **요구를 접두 일치로 협상** | 자동완성, "작품명이 ~로 시작" | UX 변경을 기획과 합의해야 함 |
| ② | **역방향 생성 컬럼** | 접미 일치(`%나무`) | 컬럼·인덱스 하나 추가, 중간 일치는 여전히 불가 |
| ③ | **정규화 생성 컬럼** | 공백·대소문자·특수문자 무시한 접두 일치 | 앱과 DB의 정규화 규칙을 일치시켜야 함 |
| ④ | **자체 n-gram 토큰 테이블** | 중간 일치 | 쓰기 시 토큰 재생성, 저장량 수 배, 직접 만든 역색인 = 풀텍스트의 수제판 |
| ⑤ | **선행 필터로 스캔 폭 축소** | 필터 조건이 붙는 중간 일치 | 필터가 좁을 때만 의미, 전역 검색엔 무력 |

### 2-1. 요구를 접두 일치로 바꾼다 — 가장 싼 해법은 요구를 바꾸는 것

"작품 검색"이라는 요구의 실제 UX가 **검색창에 타이핑하면 후보가 뜨는 자동완성**
이라면, 그건 접두 일치로 충분한 경우가 많다. 기획자에게 "중간 글자로도 찾아야
하나요?"를 **먼저 묻는 것**이 백엔드의 일이다. rationale이 말하는 "요구의 숨은
비용을 산정"의 첫 단계가 바로 **요구를 되묻기**다.

```sql
-- ✅ 자동완성: 접두 일치 + 인기순은 (title) 인덱스로 seek 후 상위 N만
SELECT id, title FROM webtoons
WHERE title LIKE '나무%'
ORDER BY view_count DESC
LIMIT 10;
-- 구간이 좁으면 filesort 비용도 작다. 구간이 넓은 한 글자 접두(‘가%’)는 최소 2글자부터 검색하도록 UX에서 막는다.
```

### 2-2. 역방향 생성 컬럼 — 역순 사전을 만든다

접미 일치(`%나무`: "…나무"로 끝나는 작품)가 진짜 요구라면 **뒤집어 저장한
컬럼**에 인덱스를 건다. MySQL의 생성 컬럼(generated column)을 쓰면 애플리케이션
코드 수정 없이 DB가 값을 유지한다.

```sql
-- ✅ 역순 사전
ALTER TABLE webtoons
  ADD COLUMN title_rev VARCHAR(200) AS (REVERSE(title)) STORED,
  ADD INDEX idx_webtoons_title_rev (title_rev);

-- "…나무"로 끝나는 작품 = 뒤집으면 "무나…"로 시작하는 작품 → 접두 일치
SELECT id, title FROM webtoons
WHERE title_rev LIKE CONCAT(REVERSE('나무'), '%');   -- '무나%'
```

한계는 명확하다 — **접두와 접미는 되지만 중간은 여전히 안 된다.** 그리고
`STORED`라 쓰기마다 한 번 더 계산해 저장하고, 인덱스도 하나 더 유지한다(쓰기
비용). 접미 검색 요구 자체가 드물어서 실무 빈도는 낮지만, "구조적 한계를
구조로 우회한다"는 사고를 보여주기엔 좋은 예다.

### 2-3. 정규화 생성 컬럼 — 함수를 WHERE가 아니라 컬럼 쪽에 미리 적용한다

"나 혼자만 레벨업"을 "나혼자만"으로 쳐도 나와야 한다, 영문 대소문자는 무시해야
한다 같은 요구는 **검색 시점에 함수를 씌우면**(1-4절 ❌) 인덱스가 죽는다.
대신 **저장 시점에 정규화한 값을 별도 컬럼에 두고** 거기에 인덱스를 건다 —
원인 ①(컬럼에 함수)의 정석 해법을 검색에 적용한 것이다.

```sql
-- ✅ 공백 제거 + 소문자화한 검색용 컬럼
ALTER TABLE webtoons
  ADD COLUMN title_norm VARCHAR(200) AS (LOWER(REPLACE(title, ' ', ''))) STORED,
  ADD INDEX idx_webtoons_title_norm (title_norm);

-- 앱에서도 같은 규칙으로 정규화한 뒤 접두 검색
SELECT id, title FROM webtoons WHERE title_norm LIKE '나혼자만%';
```

**대가**: 정규화 규칙이 DB(생성 컬럼 식)와 애플리케이션(검색어 전처리) **두
곳에 존재**한다. 한쪽만 바꾸면 조용히 검색이 안 된다 — 규칙을 한 곳(예: DB
식)에만 두고 앱은 `SELECT`로 그 식을 재사용하거나, 통합 테스트에 "정규화 규칙
일치"를 박아 둔다(5절).

### 2-4. 자체 n-gram 토큰 테이블 — 역색인을 손으로 만든다

중간 일치가 꼭 필요한데 풀텍스트 기능을 쓸 수 없는 환경(권한, DB 종류, 파서
제약)이라면, **제목을 2글자 조각(bigram)으로 쪼개 별도 테이블에 저장**하고
검색어도 같은 방식으로 쪼개 **등호 조회의 교집합**으로 찾는다. 이것이 3절
풀텍스트 인덱스가 내부에서 하는 일의 축소판이라 원리 이해에도 좋다.

```sql
-- ✅ 토큰 테이블: token 기준 정렬(PK) → 등호 조회는 seek
CREATE TABLE webtoon_title_tokens (
  token      CHAR(2) NOT NULL,      -- 2글자 조각
  webtoon_id BIGINT  NOT NULL,
  PRIMARY KEY (token, webtoon_id)
);
-- "사과나무 아래"(id=7) 저장 시 → ('사과',7) ('과나',7) ('나무',7) ('무아',7)* ('아래',7)
--   * 공백 처리 규칙은 정규화 컬럼과 마찬가지로 한 곳에 고정

-- 검색어 "과나무" → 토큰 '과나', '나무' 를 모두 가진 작품
SELECT webtoon_id
FROM webtoon_title_tokens
WHERE token IN ('과나', '나무')            -- 두 개의 짧은 등호 구간 (seek)
GROUP BY webtoon_id
HAVING COUNT(DISTINCT token) = 2;          -- 집계 후 필터 = HAVING (07-where-vs-having.md)
```

**대가를 양면으로**: (+) 중간 일치가 seek이 된다, 어떤 RDB에서도 된다.
(−) 제목 한 번 바꾸면 토큰 행을 지우고 다시 넣어야 한다 — 이걸 **같은
트랜잭션에서** 하지 않으면 검색 결과와 실제 제목이 어긋난다(반정규화의 갱신
정합성 문제와 같은 뿌리). 저장량은 제목 길이만큼 행이 생겨 **수 배**. 그리고
bigram 교집합은 **순서를 보장하지 않는다** — '과나'와 '나무'를 둘 다 가졌지만
"나무과나"인 제목도 매치되므로, 후보 id로 원본 행을 읽어 `LIKE '%과나무%'`로
**2차 검증**해야 한다(후보가 이미 좁으니 이 LIKE는 싸다). 이 정도 손이 가기
시작하면 "풀텍스트 인덱스가 이걸 대신 해 준다"로 넘어갈 시점이다.

### 2-5. 선행 필터로 스캔 폭을 줄인다 — LIKE를 액세스 조건이 아니라 필터 조건으로 격하

검색이 항상 **다른 좁은 조건과 함께** 온다면(장르 페이지 안에서 검색, 특정
작가의 작품 중 검색), 그 조건을 선두로 한 복합 인덱스로 **구간을 먼저
좁히고** 그 안에서 LIKE는 필터로만 쓴다. [복합 인덱스 컬럼 순서](08-composite-index-column-order.md)의
"뒤 컬럼은 탐색용이 아니라 제거용" 원칙 그대로다.

```sql
CREATE INDEX idx_webtoons_author_title ON webtoons (author_id, title);

-- ✅ author_id 등호로 seek → 그 작가의 작품 수십 건 안에서만 LIKE 평가
SELECT id, title FROM webtoons
WHERE author_id = 1024 AND title LIKE '%나무%';
-- type: ref, key: idx_webtoons_author_title, Extra: Using index condition
```

한계: **전역 검색에는 무력하다.** `genre = 'ROMANCE'`처럼 전체의 30%를 남기는
필터는 스캔 폭을 별로 줄이지 못한다. "필터가 충분히 좁을 때만" 이라는 조건을
반드시 붙여 말한다.

## 3. 층위 ② — 풀텍스트 인덱스: 중간 일치를 "토큰 등호 조회"로 바꾼다

### 3-1. 역색인(inverted index) — 책 뒤의 "찾아보기"

B+Tree가 "값 → 행"을 값 순서로 정렬한 사전이라면, 역색인은 **"단어 → 그 단어가
나오는 문서 목록"** 이다. 책 뒤 찾아보기 페이지에서 "나무 …… 12, 87, 203쪽"을
보고 바로 그 쪽으로 가는 것. 문서를 **미리 단어(토큰)로 쪼개** 저장해 두므로,
검색어가 문서 **어느 위치에 있든** 토큰 하나를 등호로 찾으면 된다 — **"중간
일치"라는 문제 자체가 사라진다.**

```text
문서                              역색인 (토큰 → 문서 id 목록)
 1: 나무 위의 집                   나무 → [1, 2, 7]
 2: 나무늘보 일기                  위의 → [1]
 7: 사과나무 아래                  늘보 → [2]        ← 토큰을 어떻게 자르느냐(파서)가 품질을 정한다
                                   사과 → [7]
```

핵심은 **"토큰을 어떻게 자르느냐"(파서/분석기)가 검색 품질의 전부**라는 점이고,
한국어에서 이게 문제가 된다(3-3절).

### 3-2. InnoDB FULLTEXT 사용법

```sql
-- ✅ 풀텍스트 인덱스 (한국어라면 ngram 파서 필수 — 3-3절)
ALTER TABLE webtoons
  ADD FULLTEXT INDEX ft_webtoons_title_author (title, author_name) WITH PARSER ngram;

-- 자연어 모드: 토큰 중 하나라도 맞으면 매치, 관련도 점수순
SELECT id, title, author_name,
       MATCH(title, author_name) AGAINST('사과나무' IN NATURAL LANGUAGE MODE) AS score
FROM webtoons
WHERE MATCH(title, author_name) AGAINST('사과나무' IN NATURAL LANGUAGE MODE)
ORDER BY score DESC
LIMIT 20;

-- 불리언 모드: +필수 -제외 *접두 "구문" 연산자. ngram 파서에서는 검색어가 구문 검색으로 바뀐다
SELECT id, title
FROM webtoons
WHERE MATCH(title, author_name) AGAINST('+사과나무 -완결' IN BOOLEAN MODE);
```

`EXPLAIN`에는 `type: fulltext`, `key: ft_webtoons_title_author`로 나온다.
`LIKE '%사과나무%'`가 N에 선형이었다면 이건 **토큰 '사과나무'(ngram이면 '사과',
'과나', '나무')의 문서 목록 길이에 비례**한다 — 전체 N이 아니라 **해당 토큰이
든 문서 수**다.

### 3-3. 한국어 문제와 ngram 파서

InnoDB의 **기본 파서는 공백·구두점으로 단어를 자른다.** 영어처럼 띄어쓰기가
단어 경계인 언어를 전제한 것이라 한국어에서 두 가지가 깨진다:

1. **조사·어미가 붙는다** — "나무를", "나무가", "나무에서"가 전부 **다른
   토큰**이다. "나무"로 검색하면 하나도 안 걸린다.
2. **띄어쓰기가 없는 제목** — "나혼자만레벨업"은 토큰 하나다. "레벨업"으로
   못 찾는다.

그래서 한국어(중국어·일본어도)는 **ngram 파서**를 쓴다. 의미 단위와 무관하게
**글자를 n개씩 겹쳐 자른다**(`ngram_token_size` 기본 2). "사과나무" → '사과',
'과나', '나무'. 검색어도 같은 방식으로 잘라 찾으니 **어디서 잘렸든 중간 일치가
된다.** ngram 파서는 자기 토큰 크기를 쓰므로 일반 파서의 최소 토큰 길이
설정(`innodb_ft_min_token_size`)에 걸리지 않는다.

**ngram의 한계도 같은 호흡으로 말한다**:

- **의미를 모른다** — '과나' 같은 무의미 토큰도 전부 색인한다 → **색인 크기가
  텍스트 길이에 비례해 크게 불어난다**(형태소 분석 대비 수 배).
- **자연어 모드는 노이즈가 크다** — "사과나무" 검색이 '사과', '과나', '나무' 중
  **하나라도** 든 문서를 매치해 "나무늘보 일기", "사과 농장"이 딸려 온다.
  관련도 점수로 위로 올리긴 하지만 "정확히 사과나무가 든 것만"은 **불리언
  모드**(ngram에서는 구문 검색으로 변환)로 써야 한다.
- **형태소 분석이 없다** — "달리기"와 "달렸다"를 같은 단어로 묶지 못한다.
  동의어("웹툰"↔"만화"), 오타("나무우"), 초성 검색(ㄴㅁ)은 아예 영역 밖이다.
- **관련도 계산이 단순하다** — TF-IDF 계열 점수뿐이고, "인기 작품을 위로",
  "최근 작품에 가중치" 같은 **부스팅을 조합할 수단이 없다**(ORDER BY로
  덧붙이면 관련도 정렬이 깨진다).

### 3-4. 풀텍스트 인덱스의 대가 — 쓰기·크기·결합

> **약점 ② 겨냥** — "풀텍스트 인덱스를 쓰면 됩니다"로 끝내면 한쪽 면만 본
> 것이다. 얻는 것(중간 일치가 토큰 조회로)과 **치르는 것 네 가지**를 한
> 호흡에 붙인다.

1. **쓰기 비용** — 행 하나 INSERT/UPDATE에 토큰 수만큼 역색인 항목이 생긴다.
   InnoDB는 이를 메모리 캐시에 모았다가 보조 테이블로 내려쓰고, **트랜잭션
   커밋 시점에 토큰화**한다 — 같은 트랜잭션 안에서 방금 넣은 행을 `MATCH`로
   찾으면 안 보인다. 삭제도 즉시 지우지 않고 "삭제됨" 목록에 표시했다가
   나중에 정리(`OPTIMIZE TABLE`)하므로, 갱신이 잦은 테이블은 **색인이 점점
   비대해진다**. (가산점 포인트)
2. **크기** — ngram이면 특히. 제목 20자에 bigram 19개, 작가명·줄거리까지 넣으면
   원본보다 색인이 커지는 경우가 흔하다 → 버퍼 풀 경쟁.
3. **필터·정렬과의 결합이 약하다** — 한 테이블 조회에서 옵티마이저는 **인덱스
   하나**를 고른다. `MATCH … AND genre = ? ORDER BY view_count DESC`는
   풀텍스트로 후보를 뽑은 뒤 `genre`는 필터, `view_count`는 filesort다. 후보가
   수십만이면 여기서 다시 느려진다.

   ```sql
   -- 검색 + 장르 필터 + 인기순: 풀텍스트 인덱스 하나로 후보 → 나머지는 필터·정렬
   SELECT id, title FROM webtoons
   WHERE MATCH(title) AGAINST('나무' IN BOOLEAN MODE) AND genre = 'ROMANCE'
   ORDER BY view_count DESC LIMIT 20;
   -- 후보('나무' 포함)가 많을수록 filesort 비용↑ — 이게 4절 "전환 신호 ③"이다
   ```
4. **조인 결과에는 못 건다** — FULLTEXT는 **테이블 단위**다. "작품명 + 작가명 +
   태그(별도 테이블) + 줄거리"를 한 번에 검색하려면 검색용 반정규화 컬럼을
   만들어 거기에 걸어야 하고, 그 순간 갱신 정합성 문제가 따라온다.

### 3-5. 풀텍스트로 "버틸 수 있는" 조건 — 어디까지인가

수치는 하드웨어·데이터 형태에 따라 달라 **팀이 실측해야** 하지만, 정성적 경계는
분명하다:

| 조건 | 풀텍스트로 버팀 | 검색 엔진 신호 |
|---|---|---|
| 대상 | 단일 테이블, 짧은 필드(제목·이름) | 여러 테이블·긴 본문·태그 결합 |
| 일치 | 키워드 포함 여부 | 형태소·오타·동의어·초성·자동완성 품질 |
| 결합 | 필터 없거나 아주 좁음 | 필터 + 정렬 + 패싯(장르별 건수) 동시 |
| 규모 | 실측 p99가 목표 안 | 후보 집합이 커져 filesort가 지배 |
| 신선도 | 커밋 즉시 반영이 필요 | 수 초 지연 허용 가능 |
| 격리 | 검색 트래픽이 OLTP에 묻힘 | 검색 스파이크가 OLTP를 밀어냄 |

웹툰 플랫폼의 **작품명·작가명 검색**은 왼쪽 열에 대체로 들어간다 — 짧은 필드,
단일 테이블, 수만~수십만 건. 그래서 **첫 선택은 FULLTEXT ngram**이고, 오른쪽
열 조건이 **하나라도 필수 요구로 들어오는 순간**이 전환점이다.

## 4. 층위 ③ — 검색 엔진(Elasticsearch) 전환

### 4-1. 전환을 미는 신호 5가지 (목록으로 인출)

> **약점 ④ 겨냥** — "규모가 커지면 ES"는 판단 기준이 아니다. 아래 다섯 중
> 어느 것이 요구로 들어왔는지를 **번호로** 짚는다. 기억 고리: **품질 · 결합 ·
> 범위 · 규모 · 격리**.

1. **검색 품질 요구** — 형태소 분석(한국어 `nori` 분석기: "달렸다"→"달리다"),
   동의어, 오타 허용(fuzziness), 초성 검색(커스텀 분석기), 자동완성
   (`edge_ngram`), 관련도 튜닝(BM25 + 인기·최신 부스팅). RDB 풀텍스트는 이
   중 어느 것도 제대로 못 한다. **가장 흔한 전환 사유.**
2. **필터·정렬·집계의 결합** — "나무 검색 결과를 로맨스만, 인기순으로,
   장르별 건수(패싯)와 함께" — 역색인 + 컬럼 저장 + 집계가 한 엔진의 본업이다.
   RDB는 인덱스 하나 + filesort로 버틴다(3-4절 ③).
3. **검색 범위가 여러 소스** — 작품명·작가명·태그·줄거리·에피소드 제목을 한
   검색창에서. RDB는 조인 위에 FULLTEXT를 못 건다. 검색 엔진은 애초에
   **검색용으로 반정규화한 문서**를 받는 구조라 자연스럽다.
4. **규모** — 실측에서 풀텍스트 p99가 목표를 넘고, 후보 집합 크기 때문에
   filesort가 지배적일 때. 신호 ①~③ 없이 규모만으로 가는 경우는 생각보다
   드물다 — 규모만 문제면 3-5절 왼쪽 열 안에서 인덱스·캐시로 더 버틸 수 있다.
5. **부하 격리** — 검색 트래픽(이벤트·푸시 직후 스파이크, 크롤러)이 결제·조회수
   갱신과 **같은 DB의 버퍼 풀·CPU·커넥션을 잠식**한다. 검색을 별도 시스템으로
   떼어내면 검색이 죽어도 결제는 산다 — 4장 "통계 조회의 분리" 문항과 같은
   논리(기능은 다른데 자원은 공유).

### 4-2. 전환의 대가 5가지 — 양면으로

> **약점 ② 겨냥** — 신호 다섯을 말했으면 대가 다섯을 **같은 호흡에** 붙인다.
> "ES 쓰면 다 해결"은 운영을 안 해 본 사람의 말이다.

1. **운영할 시스템이 하나 는다** — 클러스터(노드·샤드·레플리카 설계), JVM 힙과
   GC, 디스크 워터마크, 버전 업그레이드, 모니터링·알람, 그리고 **담당자**.
   매니지드 서비스(Elastic Cloud, OpenSearch Service)로 일부를 돈으로 바꿀 수
   있지만 매핑 설계·재색인·용량 계획은 남는다.
2. **데이터 동기화와 최종 일관성** — RDB에 커밋된 것이 ES에 **언제** 반영되는가.
   - **이중 쓰기 금지**: 애플리케이션이 RDB와 ES에 각각 쓰면 한쪽만 성공하는
     순간 영구 불일치. RDB 트랜잭션은 ES를 롤백해 주지 않는다.
   - 정석은 **RDB 커밋을 사실의 원천으로 두고 그 변경을 흘려보내는 것** —
     같은 트랜잭션에 Outbox 행을 넣고 별도 프로세스가 색인하거나, binlog를
     CDC(Debezium 등)로 읽어 색인한다.
   - 그 결과 **작품 등록 직후 몇 초간 검색에 안 나온다**(파이프라인 지연 +
     ES의 refresh 주기). 기획에 "검색 반영은 최대 N초 지연"을 **명시적으로
     합의**해야 하고, 등록 화면에서 "검색 반영 중" 같은 UX가 필요할 수 있다.
   - **삭제·비공개**도 지연된다 — 검색엔 나오는데 클릭하면 404. 검색 결과
     id로 RDB 상태를 한 번 더 확인(후처리 필터)하거나 지연을 UX로 흡수한다.
   - 매핑 변경·파서 교체 때는 **전량 재색인**(새 인덱스에 다시 넣고 alias
     스왑)이 필요하다. 이 절차가 없으면 분석기 하나 못 바꾼다.
3. **장애 도메인이 추가된다** — ES 클러스터가 red가 되면 검색이 죽는다. "검색은
   비핵심이니 비활성화" / "RDB 풀텍스트로 축소 검색 폴백" / "인기 작품 목록으로
   대체" 중 무엇으로 degrade할지 **미리** 정해 두고 회로 차단기로 연결해야
   한다. 폴백이 없으면 격리(신호 ⑤)로 얻은 것을 도로 잃는다.
4. **사실의 원천이 둘로 보인다** — ES는 **파생 데이터**다. "언제든 RDB에서
   전량 재구축할 수 있다"가 성립해야 하고, 그 재구축 스크립트가 **주기적으로
   돌아가는지**가 팀의 성숙도다. 이 주제는 12장(`questions/12-nosql.md`,
   "RDB·Redis·ES 공존 시 source of truth")에서 다시 나온다.
5. **트랜잭션과 정합성 모델이 다르다** — ES 검색 결과는 RDB 격리 수준의 보호를
   받지 않는다. 검색 결과로 뭔가를 **결정**(결제·권한)하면 안 되고, 검색은
   "후보를 찾는" 용도로 제한하고 최종 판단은 RDB에서 한다는 경계를 코드에
   둔다.

### 4-3. 구조 한 장 — RDB가 원천, ES는 파생

```text
[작품 등록/수정 트랜잭션]
   │ 같은 트랜잭션
   ├──▶ webtoons 테이블            ← source of truth (RDB)
   └──▶ outbox 테이블 ──(폴링 or CDC)──▶ 인덱서 ──▶ Elasticsearch  ← 파생 데이터, 재구축 가능
                                                          ▲
[검색 API] ── 질의(형태소·오타·필터·정렬·패싯) ───────────────┘
        └── 결과 id 목록 → (필요 시) RDB에서 삭제·비공개 상태 재확인 → 응답
[ES 장애] ── 회로 차단 ──▶ 폴백(FULLTEXT 축소 검색 / 인기 목록 / 검색 비활성)
```

### 4-4. 중간 선택지 (가산점 포인트)

- **매니지드 검색 서비스**: 운영 대가 ①의 일부를 비용으로 전환. 동기화·폴백
  대가는 그대로다.
- **경량 검색 엔진**(Meilisearch, Typesense 등): 단일 노드로 오타·자동완성·
  패싯이 되고 운영이 가볍다. 규모·집계 요구가 작을 때 ES와 FULLTEXT 사이의
  선택지가 된다.
- **읽기 레플리카에 FULLTEXT**: 격리(신호 ⑤)만 문제라면 검색 쿼리를
  레플리카로 보내는 것으로 OLTP 보호는 된다. 품질(신호 ①)은 못 푼다.

## 5. 판단 절차 — "검색 기능 추가해주세요"의 숨은 비용을 산정하는 팀 체크리스트

> **약점 ③ 겨냥** — 판단 기준을 "그때그때 감으로"가 아니라 **팀 문서와
> 도구에 고정**한다. 사람의 기억에 의존하지 않는 형태여야 한다.

### 5-1. 요구를 받으면 먼저 채우는 8칸

| # | 질문 | 답이 가리키는 층위 |
|---|---|---|
| 1 | **데이터량** — 지금 몇 건, 1년 뒤 몇 건? (기울기) | 선형 비용이 언제 임계를 넘는가 |
| 2 | **QPS** — 평시/피크, 전체 트래픽 대비 비중 | 커넥션 점유 = N × QPS |
| 3 | **일치 유형** — 접두 / 접미 / 중간 / 형태소 / 오타 / 초성 | 접두면 ①, 중간이면 ②, 형태소·오타면 ③ |
| 4 | **품질 요구** — 관련도 순위, 동의어, 인기 반영 | 있으면 ③ |
| 5 | **결합 조건** — 필터(장르·연재상태·성인) / 정렬(인기·최신) / 집계(패싯) | 둘 이상 동시면 ③ 신호 |
| 6 | **대상 범위** — 필드 몇 개, 테이블 몇 개, 조인 필요? | 여러 테이블이면 ③ 신호 |
| 7 | **신선도** — 등록 후 몇 초 안에 검색돼야 하나 | 즉시면 ①②, 수 초 허용이면 ③ 가능 |
| 8 | **격리·가용성** — 검색 부하가 OLTP를 밀어내면 안 되나, 검색 장애 시 폴백은 | 격리 필수면 ③(또는 레플리카) |

### 5-2. 결정 트리 3단계

```text
1) 접두 일치로 협상 가능한가? (자동완성 UX면 대부분 가능)
   → YES: 일반 인덱스 + LIKE 'kw%' (+ 정규화 생성 컬럼). 끝.
   → NO ↓
2) 단일 테이블 · 짧은 필드 · 키워드 포함 여부만 · 결합 조건 가벼움 · 실측 p99 OK?
   → YES: InnoDB FULLTEXT + ngram. ADR에 "③으로 가는 트리거"를 숫자로 적는다.
   → NO ↓
3) 형태소/오타/동의어/관련도/패싯/다중 소스/격리 중 하나라도 필수
   → 검색 엔진. 매니지드·경량 엔진부터 검토. 동기화 방식·지연 합의·폴백을 설계 문서에.
```

### 5-3. 안전망을 고정하는 방법 — 문서·코드·알람

- **ADR(설계 결정 기록)에 전환 트리거를 숫자로** — "현재 FULLTEXT ngram. 검색
  p99 > 300ms가 1주 지속 / 요구에 형태소·오타 추가 / 검색 대상 테이블 2개 이상
  → ES 검토 착수". 숫자는 팀이 정하되, **정하지 않은 채로 두지 않는 것**이
  핵심이다. 그래야 "언제 갈지"를 두고 매번 감정 싸움을 안 한다.
- **코드 리뷰 규칙 + 자동 검출** — "선행 `%` LIKE는 검색 전용 포트(`SearchPort`)
  밖에서 금지". 사람 눈만 믿지 말고 통합 테스트에서 DataSource 프록시(p6spy 등)로
  실행 SQL을 잡아 `LIKE '%` 패턴이 나오면 테스트를 실패시킨다.
- **풀스캔 감시 알람** — 슬로 쿼리 로그 + `sys.statements_with_full_table_scans`
  / `Select_scan` 상태 변수 추이. 데이터가 자라 임계를 넘는 날을 **배포 없이도**
  잡아낸다.
- **부하 테스트 시나리오에 "검색 × 데이터 N배"** — 현재 데이터로만 테스트하면
  선형 비용은 절대 안 잡힌다. 1년 뒤 예상 건수를 채운 환경에서 검색 QPS를 건다.
- **정규화 규칙·토큰 규칙 일치 테스트** — 생성 컬럼 식과 앱 전처리, 토큰
  테이블과 원본이 어긋나지 않는지 검증하는 테스트를 CI에 둔다.
- **ES 도입 시 재구축 스크립트를 정기 실행** — "언제든 RDB에서 다시 만들 수
  있다"를 말이 아니라 주기 작업으로 증명한다.

## 6. 실무 사례 — 웹툰 플랫폼 작품명·작가명 검색의 3단계

### 단계 1: `LIKE '%kw%'`로 시작, 조용히 자라는 비용

```java
// ❌ 출시 초기 — 작품 3천 건. 잘 돌아간다. 문제는 이 코드가 "N에 선형인 비용"을 심는다는 것
@Query("SELECT w FROM Webtoon w WHERE w.title LIKE %:keyword% OR w.authorName LIKE %:keyword% " +
       "ORDER BY w.viewCount DESC")
List<Webtoon> search(@Param("keyword") String keyword, Pageable pageable);
// EXPLAIN: type=ALL, rows=3000, Extra=Using where; Using filesort
```

이 코드가 위험한 진짜 이유는 두 가지다. 첫째, 이 패턴을 본 동료가 **댓글·
에피소드 테이블에도 복사**한다 — 거기는 N이 수천만이다. 둘째, `OR`로 두 컬럼을
묶어 선행 필터(2-5절)조차 못 붙는다. 검색 QPS가 오르던 어느 이벤트 날, 배포도
없이 커넥션 풀이 마르고 **결제 API까지 타임아웃**이 났다 — 1-3절의 사슬 그대로.

### 단계 2: FULLTEXT ngram + 자동완성은 접두 인덱스

```java
// ✅ 검색 요구를 둘로 쪼갠다: 자동완성(접두) / 결과 검색(중간 일치)
public interface WebtoonSearchRepository extends JpaRepository<Webtoon, Long> {

    // 자동완성: 접두 일치 → title 인덱스 seek. 2글자 미만은 컨트롤러에서 거른다
    @Query("SELECT w FROM Webtoon w WHERE w.title LIKE :prefix% ORDER BY w.viewCount DESC")
    List<Webtoon> autocomplete(@Param("prefix") String prefix, Pageable pageable);

    // 결과 검색: FULLTEXT ngram, 불리언 모드(구문 검색으로 노이즈 억제)
    @Query(value = """
        SELECT * FROM webtoons
        WHERE MATCH(title, author_name) AGAINST(:keyword IN BOOLEAN MODE)
          AND status = 'ONGOING'
        ORDER BY view_count DESC
        LIMIT :size
        """, nativeQuery = true)
    List<Webtoon> searchFullText(@Param("keyword") String keyword, @Param("size") int size);
}
```

ADR에 적은 전환 트리거: "① 검색 p99 > 300ms 지속 ② 태그·줄거리 검색 요구
③ 오타·초성 요구 ④ 장르 패싯 요구". 이 시점의 검색은 **단일 테이블·짧은 필드
·수만 건**이라 3-5절 왼쪽 열 안이다.

### 단계 3: "태그로도, 줄거리로도, 오타 나도 찾게" — 검색 엔진

요구가 ②③④를 한꺼번에 밟았다. 이제 RDB 안에서는 답이 없다 — 여러 테이블(태그),
형태소·오타(품질), 패싯(집계). 검색을 **포트 뒤로 격리**하고 ES 어댑터를 붙인다.

```java
// ✅ 검색을 포트로 격리 — 구현(FULLTEXT / ES)을 바꿔도 호출부는 모른다. 폴백도 여기서
public interface WebtoonSearchPort {
    SearchResult search(SearchQuery query);   // 키워드 + 필터 + 정렬 + 패싯 요청
}

@Component
class ElasticsearchWebtoonSearchAdapter implements WebtoonSearchPort {
    private final ElasticsearchClient es;
    private final WebtoonSearchPort fallback;   // FULLTEXT 축소 검색 어댑터
    private final CircuitBreaker breaker;

    @Override
    public SearchResult search(SearchQuery q) {
        // nori + edge_ngram + fuzziness + 장르 패싯은 es.search 안에서. 차단기가 열리면 즉시 폴백으로
        return Try.ofSupplier(breaker.decorateSupplier(() -> es.search(q)))
                  .recover(ex -> fallback.search(q.withoutFacets()))   // ES 장애 시 degrade (패싯 없이)
                  .get();
    }
}
```

```text
색인 파이프라인: webtoons/tags/authors 변경 → outbox → 인덱서 → ES 문서(작품명·작가명·태그·줄거리 반정규화)
합의한 지연: "등록 후 최대 10초 내 검색 반영" (기획 문서에 명시)
후처리: 검색 결과 id로 RDB status 재확인 → 비공개·삭제 작품 제거
재구축: 매주 새벽 전량 재색인 → alias 스왑 (분석기 변경 리허설 겸용)
```

**대가로 실제 치른 것**: 검색 팀 1명 상시, 클러스터 비용, 등록 직후 "검색에
안 나와요" 문의 → UX 안내 추가, 분석기 교체 때 전량 재색인 2시간. 이 목록을
**전환 전에** 산정해 보고했기 때문에 "왜 이렇게 오래 걸리냐"가 아니라 "예상
범위"로 받아들여졌다 — rationale이 말하는 **숨은 비용 산정**의 실제 모습이다.

## 7. 꼬리질문 대비 포인트

### "`LIKE '나무%'`는 인덱스를 탄다고 했는데, 항상 타나요?"

아니다. 셋을 짚는다. ① **컬럼에 함수를 씌우면** 못 탄다 — 대소문자 무시용
`LOWER(title) LIKE`가 전형. 대소문자 무시 콜레이션(`_ci`)이나 정규화 생성
컬럼으로 함수를 컬럼 쪽에 미리 적용한다. ② **선택도가 낮으면** 옵티마이저가
일부러 안 탄다 — `LIKE '가%'`가 전체의 30%면 랜덤 I/O 북마크 룩업보다 순차
풀스캔이 싸다(부류 B, 옳은 판단). 그래서 자동완성은 최소 2글자부터 받는다.
③ **사용자 입력에 `%`·`_`가 섞이면** 코드는 접두처럼 보여도 실행은 중간
일치가 된다 — 와일드카드를 이스케이프하거나 제거한 뒤 바인딩한다. 이 셋 모두
[풀스캔 원인 6종](02-index-not-used-full-scan.md)의 ①·⑥과 입력 검증에서 도출된다.

### "InnoDB FULLTEXT로 한국어 검색이 제대로 되나요? 어디까지 되고 어디서 막히나요?"

기본 파서는 공백 기준이라 조사·어미가 붙는 한국어("나무를"≠"나무")와 띄어쓰기
없는 제목에서 깨진다. **ngram 파서**로 글자를 2개씩 겹쳐 잘라 색인하면 중간
일치와 조사 문제는 풀린다. 막히는 지점은 넷 — **형태소를 모른다**("달렸다"↔
"달리다" 불가), **의미 없는 토큰까지 색인해 크기가 크게 는다**, **자연어
모드는 토큰 하나만 맞아도 매치해 노이즈가 크다**(불리언 모드의 구문 검색으로
억제), **관련도가 TF-IDF 계열 하나뿐이라 인기·최신 부스팅을 못 섞는다**. 작품명·
작가명처럼 짧은 필드의 "포함 여부" 검색까지는 충분하고, 오타·동의어·초성·
부스팅이 요구로 들어오면 검색 엔진 신호다.

### "ES를 도입하면 RDB와의 데이터 불일치는 어떻게 다루나요?" (시니어 변별 포인트)

먼저 **불일치는 없앨 수 없고 관리하는 것**이라고 전제한다. 원칙 넷: ① **이중
쓰기 금지** — RDB 트랜잭션은 ES를 롤백해 주지 않으니 앱이 두 곳에 직접 쓰면
영구 불일치가 생긴다. ② **RDB 커밋을 원천으로, 변경을 흘려보낸다** — 같은
트랜잭션의 Outbox 행 또는 binlog CDC를 인덱서가 소비. 실패해도 재시도로
따라잡는다(최종 일관성). ③ **지연을 기획과 합의**한다 — "등록 후 최대 N초",
등록 화면 UX, 삭제·비공개 작품이 검색에 남는 창은 검색 결과 id로 RDB 상태를
재확인하는 후처리로 막는다. ④ **전량 재구축 절차를 정기 실행**한다 — 매핑
변경·분석기 교체·유실 복구 모두 이 절차 하나로 수렴하고, "언제든 RDB에서 다시
만들 수 있다"를 주기 작업으로 증명한다. 이 넷 중 ①②가 없으면 언젠가 "검색엔
있는데 DB엔 없는 작품"을 손으로 지우게 된다. 12장 "source of truth" 문항과
같은 뿌리다.

### "ES 클러스터가 죽으면 검색은 어떻게 하나요? 그럼 격리한 의미가 있나요?" (시니어 변별 포인트)

격리로 얻은 건 **"검색이 죽어도 결제는 산다"**이지 "검색이 안 죽는다"가
아니다. 그래서 검색 경로에 **degrade 계층**을 미리 설계한다: 회로 차단기로 ES
호출을 끊고 → (a) RDB FULLTEXT 축소 검색(패싯·오타 없이 키워드만) (b) 인기
작품 목록으로 대체 (c) 검색 UI 비활성 + 안내, 중 서비스 성격에 맞는 것으로
떨어진다. 폴백 (a)를 유지하려면 **FULLTEXT 인덱스를 ES 도입 후에도 지우지
않는다**는 결정이 따라오고, 그 쓰기 비용은 폴백의 가격이다. 이 "장애 도메인
추가 → 폴백 설계 → 폴백 유지 비용"까지가 전환 대가의 한 묶음이고, ES
자체의 가용성은 레플리카 샤드·다중 AZ·매니지드로 올린다.

### "`LIKE '%나무%'`인데 EXPLAIN에 `type: index`, `Using index`가 나옵니다. 인덱스를 탄 건가요?" (가산점 포인트)

**인덱스 풀스캔**이다 — 탐색(seek)이 아니라 테이블 대신 인덱스 사본을 처음부터
끝까지 훑은 것. 조회 컬럼이 인덱스에 다 들어 있어(커버링) 옵티마이저가 "더
작은 쪽을 훑자"고 고른 결과다. 테이블 풀스캔(`type: ALL`)보다 읽는 페이지가
적으니 빠르긴 하지만 **비용은 여전히 N에 선형**이고, 데이터가 10배면 10배
느려진다. `type`이 `range`/`ref`가 아니라 `index`면 "인덱스를 읽긴 했으나
시작점은 못 찍었다"로 읽는다. 이 구분을 못 하면 "인덱스 탔는데 왜 느리죠"에서
멈춘다.

## 한 줄 요약

**B+Tree 인덱스는 첫 글자부터 정렬된 사전이라 `LIKE '%kw%'`는 트리를 내려갈
시작점을 찍을 수 없어(seek 불가) 전부 훑고, 그 비용은 행 수에 선형이라 QPS와
곱해져 커넥션 풀을 말리며 조용히 자란다. 대응은 세 층위 — 요구 협상·역순/
정규화 생성 컬럼·자체 토큰 테이블·선행 필터로 LIKE 안에서 버티기 → 역색인으로
중간 일치를 토큰 등호 조회로 바꾸는 FULLTEXT ngram(대가: 쓰기·크기·형태소
부재·결합 약함) → 형태소·오타·패싯·다중 소스·격리가 필수일 때 검색 엔진(대가:
운영 클러스터, 동기화와 최종 일관성, 장애 도메인 추가). 전환은 데이터량·QPS·
일치 유형·품질·결합·범위·신선도·격리 8칸을 채워 판단하고, 그 트리거를 ADR에
숫자로 박아 둔다.**
