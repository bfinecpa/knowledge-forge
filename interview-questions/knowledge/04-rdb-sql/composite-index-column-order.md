# 복합 인덱스 컬럼 순서 — "카디널리티 높은 컬럼 먼저"는 1순위 규칙이 아니라 3순위 기준이다

> 핵심 관전 포인트: **복합 인덱스 `(A, B, C)`는 "A로 정렬하고, A가 같은
> 것끼리만 B로, B까지 같은 것끼리만 C로" 정렬된 **하나의 트리**다. 그래서
> 컬럼 순서는 "옵티마이저가 리프에서 **얼마나 좁은 연속 구간 하나**를 찍을 수
> 있는가"를 결정한다. 순서 결정 원칙은 셋 — ① **등호(`=`) 조건 컬럼을 앞에,
> 범위 조건(`>`, `<`, `BETWEEN`, `LIKE 'x%'`)은 맨 뒤에** (범위 뒤 컬럼은
> 정렬이 깨져 탐색 조건으로 못 쓴다) ② **등호 컬럼끼리는 "더 많은 쿼리가
> 접두사로 재사용하는 컬럼"을 앞에**, 그 다음에야 카디널리티 높은 쪽을 앞에
> ③ 범위·정렬 컬럼 뒤에는 커버링용 컬럼. **카디널리티는 ②의 타이브레이커**일
> 뿐이고, "이 인덱스를 탈지 말지"는 개별 컬럼이 아니라 **컬럼 조합의
> 선택도**(랜덤 vs 순차 I/O 손익분기)가 정한다. 순서가 틀리면 뒤 컬럼 조건이
> **액세스 조건에서 필터 조건으로 강등 → 스캔 구간 폭↑ → 버릴 행에도 북마크
> 룩업(랜덤 I/O) → 버퍼 풀 오염**, 비용은 이 사슬로 말한다.**

## 0. 질문 + 의도

**질문**: "복합 인덱스의 컬럼 순서는 어떤 기준으로 정하나요? 카디널리티와의
관계는?"

관련 질문:
"커버링 인덱스란? 어떤 상황에서 효과가 큰가요?"
"ORDER BY가 인덱스를 타는 조건은? filesort는 언제 발생하고 왜 문제가 되나요?"

**출제 의도**: rationale의 표현 그대로 — "인덱스를 **'거는' 것과 '설계하는'
것의 차이**가 여기서 갈린다. 등호 조건 먼저·범위 조건 뒤 같은 원칙을 **쿼리
패턴에서 도출**할 수 있어야, 테이블당 인덱스 수를 늘리지 않으면서 여러 쿼리를
커버하는 설계가 가능하다." 즉 "카디널리티 높은 컬럼을 앞에"라는 격언을 외웠는지가
아니라, **쿼리 조건을 등호/범위/정렬로 분류해 순서를 스스로 조립하고, 그 순서가
I/O 비용으로 어떻게 번지는지**를 말할 수 있는지를 본다. 앞 문항들이 "구조를
아는가"([B+Tree](index-and-bplus-tree.md)) → "구조로 현상을 설명하는가"
([풀스캔 원인 6종](index-not-used-full-scan.md))였다면, 이 문항은 **"구조로
설계하는가"**다.

> 이 문서는 기본 Q1·Q2에서 **두 번 연속 비어 있던 축 — 선택도(카디널리티)와
> 복합 인덱스 선두 컬럼 규칙** — 을 정면으로 다룬다. 앞 문서들에서 "선두 컬럼이
> 빠지면 인덱스가 없는 것과 같다"(leftmost prefix)까지는 정리됐으니, 여기서는
> **"그럼 선두에 무엇을 둘 것인가"**부터 시작한다.

## 1. 한 문장 원리 — 복합 인덱스는 "사전 안의 사전"이다

```text
(status, created_at) 인덱스의 리프 — status로 정렬, status가 같은 것끼리만 created_at 정렬
  ┌ DONE ──────────────────────┐┌ FAILED ───────────┐┌ PAID ──────────────────────────┐
  │ 08-01 │ 08-01 │ 08-02 │ ...││ 07-30 │ 08-01 │...││ 08-01 │ 08-01 │ 08-02 │ 08-02 │...│
  └────────────────────────────┘└───────────────────┘└────────────────────────────────┘
  → "status = 'FAILED' AND created_at >= 08-01" : FAILED 칸으로 점프 → 그 안에서
    08-01 지점을 찍고 오른쪽 끝까지. ★ 연속 구간 하나 ★

(created_at, status) 인덱스의 리프 — created_at으로 정렬, 같은 시각끼리만 status 정렬
  ┌ 07-30 ─┐┌ 08-01 ───────────────────────────┐┌ 08-02 ───────────────────┐
  │ FAILED ││ DONE │ DONE │ FAILED │ PAID │ PAID││ DONE │ PAID │ PAID │ ... │
  └────────┘└──────────────────────────────────┘└──────────────────────────┘
  → 같은 조건: 08-01 지점부터 오른쪽 끝까지 **전부** 훑으며 FAILED만 골라낸다.
    FAILED가 어디 있을지 미리 알 수 없다 — 시각마다 흩어져 있으므로.
```

전화번호부가 "성 → 이름" 순인 것과 같다. 성이 같은 사람들 안에서만 이름이
정렬돼 있지, 책 전체가 이름순은 아니다. 이 한 문장에서 순서 원칙이 전부 나온다:

> **앞 컬럼의 값이 하나로 고정돼야, 그 안에서 뒤 컬럼의 정렬이 살아 있다.**

앞 컬럼이 **등호**(`status = 'FAILED'`)면 값이 하나로 고정된다 → 뒤 컬럼
정렬이 살아 있다 → 뒤 컬럼으로도 구간을 좁힐 수 있다.
앞 컬럼이 **범위**(`created_at >= 08-01`)면 값이 여러 개에 걸친다 → 각 값마다
뒤 컬럼 정렬이 따로 논다 → 뒤 컬럼은 구간을 좁히는 데 못 쓰고, 훑으면서
**걸러내는** 데만 쓴다.

## 2. 순서 결정 3원칙 — "등 · 범 · 정 · 커"로 외운다

조건을 세 바구니로 나눈 뒤 순서대로 배치한다. 암기용 네 글자:
**등**호 → **범**위 → **정**렬 → **커**버링.

| 순위 | 원칙 | 왜 |
|---|---|---|
| ① | **등호 조건 컬럼을 앞에, 범위 조건은 맨 뒤(하나만)** | 범위 뒤 컬럼은 정렬이 깨져 탐색에 못 쓴다 |
| ② | **등호 컬럼끼리는 "접두사 재사용" 우선, 그다음 카디널리티** | 같은 쿼리 안에서는 등호끼리 순서를 바꿔도 최종 구간이 같다 |
| ③ | **범위/정렬 컬럼 뒤에 커버링용 컬럼** | 탐색엔 못 쓰지만 북마크 룩업을 없앤다 |

### 2-1. 원칙 ① — 등호 먼저, 범위는 맨 뒤: 비용 사슬로 말하기

여기가 후보자가 "성능 저하"·"느려짐"에서 멈추던 지점이다. 이름을 붙여 사슬로
말한다. 먼저 용어 둘 —

- **액세스 조건(access predicate)**: 인덱스 트리를 내려가 **시작점·끝점을
  찍는 데** 쓰이는 조건. `EXPLAIN`의 `key_len`이 몇 컬럼 몫인지로 드러난다.
- **필터 조건(filter predicate)**: 구간을 좁히지 못하고, 훑은 엔트리/행을
  하나씩 검사해 **버리는 데만** 쓰이는 조건. `Extra`의 `Using index condition`
  (인덱스 단계에서 거름 = ICP) 또는 `Using where`(행을 가져온 뒤 거름)로 드러난다.

```sql
-- 쿼리: 최근 1시간 안에 실패한 주문을 모아 알림을 보내는 배치
SELECT id, user_id, amount
FROM orders
WHERE status = 'FAILED'
  AND created_at >= NOW() - INTERVAL 1 HOUR;

-- ❌ before: "created_at이 카디널리티가 훨씬 높으니 앞에" 라고 정한 순서
CREATE INDEX idx_orders_created_status ON orders (created_at, status);
-- EXPLAIN
--   type   : range
--   key    : idx_orders_created_status
--   key_len: created_at 한 컬럼 몫           ← status는 액세스 조건이 아니다
--   rows   : 300000                          ← 1시간치 주문 전체
--   Extra  : Using index condition           ← status는 훑으면서 거르는 필터
-- 1시간치 30만 엔트리를 다 훑고 그중 FAILED 3천 건만 남긴다. 스캔 폭 100배.

-- ✅ after: 등호(status) 먼저, 범위(created_at) 뒤
CREATE INDEX idx_orders_status_created ON orders (status, created_at);
-- EXPLAIN
--   type   : range
--   key    : idx_orders_status_created
--   key_len: status + created_at 두 컬럼 몫   ← 둘 다 액세스 조건
--   rows   : 3000                            ← FAILED 칸 안에서 1시간치만
--   Extra  : Using where
```

**순서가 틀렸을 때 비용 사슬 — 5고리 (암기)**

> 순서 오류 → ① 뒤 컬럼 조건이 **액세스 조건에서 필터 조건으로 강등** →
> ② 인덱스 **스캔 구간 폭↑** (리프 페이지를 더 많이 읽는다 — 리프는 연결
> 리스트라 순차 읽기이므로 이것만은 그나마 싸다) → ③ 필터에 걸러질 행까지
> **북마크 룩업**을 한다 (ICP가 인덱스 단계에서 걸러주면 이 고리는 줄지만,
> ICP를 못 쓰는 조건이면 행마다 클러스터드 인덱스를 다시 탄다) → ④ PK가
> 흩어져 있으니 **랜덤 I/O↑** — **결국 버릴 행에 가장 비싼 I/O를 지불**한다
> → ⑤ 그 페이지들이 **버퍼 풀을 채워** 정작 필요한 페이지를 밀어낸다(오염)
> → 다른 쿼리의 캐시 미스↑.

②와 ④의 차이가 곧 [Q2 문서 §4](index-not-used-full-scan.md)의 **순차 vs 랜덤
I/O**다. 30만 엔트리를 순차로 훑는 것(②)보다 그중 수만 건에 대해 흩어진
페이지를 찌르는 것(④)이 훨씬 비싸다. 그래서 ICP가 있어도 ②는 남고, ICP가
없으면 ④가 터진다.

**(가산점 포인트) 같은 사슬이 락으로도 번진다.** 이 쿼리가 `SELECT`가 아니라
`UPDATE orders SET status = 'NOTIFIED' WHERE status = 'FAILED' AND created_at >= ?`
였다면 — InnoDB는 **훑은 인덱스 레코드에 락을 건다.** 스캔 폭 100배 = 락
범위 100배 → 같은 구간을 만지는 다른 트랜잭션 **대기** → 트랜잭션 장기화 →
**커넥션 풀 고갈** → 무관한 API까지 타임아웃. "인덱스 순서 실수"가 성능
문제를 넘어 동시성 사고가 되는 경로이고, 중급 "`SELECT ... FOR UPDATE`의 락
범위" 문항의 입구다.

### 2-2. 원칙 ② — 등호 컬럼끼리: 접두사 재사용이 먼저, 카디널리티는 그다음

같은 쿼리 안에서 등호 컬럼끼리는 **순서를 바꿔도 최종 구간이 같다.**
`user_id = 100 AND status = 'PAID'`는 `(user_id, status)`든 `(status, user_id)`든
결국 "user 100의 PAID 칸"이라는 **동일한 리프 구간**에 도달한다. 카디널리티
격언이 여기서 무력한 이유다. 그럼 무엇으로 정하나 — **이 인덱스의 접두사만
쓰는 다른 쿼리들**이다.

```sql
-- 이 테이블을 치는 뜨거운 쿼리 셋
-- (a) 내 주문 중 상태별 목록: WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20
-- (b) 내 주문 전체 최근순  : WHERE user_id = ?                ORDER BY created_at DESC LIMIT 20
-- (c) 실패 주문 알림 배치  : WHERE status = 'FAILED' AND created_at >= ?

-- ❌ before: "status가 등호니까 아무 데나" → (status, user_id, created_at)
CREATE INDEX idx_orders_status_user_created ON orders (status, user_id, created_at);
--   (a) ✅ 완전 커버 — 등호 둘 다 액세스 조건, created_at 정렬까지
--   (b) ❌ 선두 status 없음 → 이 인덱스를 못 탄다 → 풀스캔 또는 다른 인덱스
--   (c) △ status까지만 액세스, user_id가 비어 created_at은 필터로 강등

-- ✅ after: 접두사 재사용 기준 — (a)(b)가 공유하는 user_id를 선두로
CREATE INDEX idx_orders_user_status_created ON orders (user_id, status, created_at);
--   (a) ✅ 완전 커버 (before와 동일한 구간)
--   (b) ✅ user_id 접두사로 탄다 (정렬은 §4 꼬리질문 3 참고)
--   (c) ❌ 이건 어차피 선두가 status여야 하므로 별도 인덱스 (status, created_at)
--          — status 단독은 카디널리티 3이라 무의미해 보이지만, FAILED가 전체의 1%면
--            "희귀 값만 조회하는" 쿼리엔 유효하다 (§3-3 편중 분포)
```

카디널리티가 실제로 개입하는 순간은 **"앞 컬럼만 쓰는 쿼리가 있을 때"**다.
`(user_id, status, …)`의 접두사 `user_id`만 쓰면 사용자 한 명 분(수십 건)으로
좁혀지지만, `(status, user_id, …)`의 접두사 `status`만 쓰면 전체의 절반이
걸려 옵티마이저가 인덱스를 버린다. 즉 **카디널리티 높은 컬럼을 앞에 두는
이유는 "그 컬럼만으로도 인덱스가 쓸모 있게" 하기 위해서**이지, 등호 둘을
다 쓰는 쿼리를 위해서가 아니다.

### 2-3. 원칙 ③ — 범위·정렬 뒤에 오는 컬럼: 탐색용이 아니라 제거용

범위 컬럼 뒤에 붙는 컬럼은 구간을 좁히지 못한다. 그래도 붙이는 이유는 둘이다.

- **정렬 제거**: 등호 컬럼들 바로 뒤에 `ORDER BY` 컬럼을 두면 인덱스 순서가
  곧 정렬 순서라 `filesort`가 사라진다. 특히 `LIMIT 20`이 붙으면 **구간의
  앞 20개만 읽고 멈춘다.** 반면 filesort는 조건에 맞는 행을 **전부** 모아
  정렬한 뒤에야 20개를 자른다 — 비용이 `LIMIT`이 아니라 **매칭 행 수에
  비례**하고, 정렬 버퍼를 넘치면 임시 파일(디스크 쓰기)까지 간다.
  **범위 컬럼 = 정렬 컬럼**(`created_at >= ? ORDER BY created_at`)이면 이상적 —
  범위이자 정렬이라 둘 다 인덱스로 처리된다.
- **커버링**: `SELECT`가 필요로 하는 컬럼을 맨 뒤에 붙이면 북마크 룩업
  자체가 사라진다(`Extra: Using index`). 위 사슬의 ③·④ 고리를 통째로
  제거하는 것 — 다음 문항 "커버링 인덱스"에서 다룬다.

```sql
-- (a) WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20

-- ❌ (user_id, status)만 있을 때
--   Extra: Using where; Using filesort   ← user 100·PAID 행 전부 모아 정렬 후 20개
-- ✅ (user_id, status, created_at)
--   Extra: Using where                   ← 구간 끝에서 역방향으로 20개 읽고 종료
--   (MySQL은 인덱스를 역방향으로도 읽으며, 8.0부터는 내림차순 인덱스도 만들 수 있어
--    ORDER BY a ASC, b DESC 같은 혼합 정렬도 인덱스로 처리할 수 있다)
```

### 2-4. 무엇이 "범위"로 취급되는가 (암기)

원칙 ①을 적용하려면 이 분류가 즉시 나와야 한다.

- **등호처럼 동작**: `=`, `IS NULL`, 그리고 `IN (…)` — 단 `IN`은 값 개수만큼
  **구간이 여러 개로 갈라진다.** 뒤 컬럼을 탐색에 쓸 수는 있지만, 뒤 컬럼
  기준 `ORDER BY`는 갈라진 구간을 병합해야 해서 대개 filesort가 남는다.
- **범위**: `>`, `>=`, `<`, `<=`, `BETWEEN`, `LIKE 'kim%'`(선행 문자 고정)
- **사실상 전 구간(범위 중 최악)**: `!=`, `NOT IN`, `IS NOT NULL`, `NOT LIKE`
- **아예 못 씀**: `LIKE '%kim%'`, 컬럼에 함수·연산, 타입 불일치 —
  [풀스캔 원인 6종](index-not-used-full-scan.md) 참고

## 3. 카디널리티와의 관계 — 오해 둘, 개입 지점 둘

용어부터 고정한다([Q2 문서 §4-3](index-not-used-full-scan.md)의 정의 그대로).
**카디널리티** = 그 컬럼에 서로 다른 값이 몇 개인가(컬럼의 성질).
**선택도** = 이 조건이 전체 행을 몇 %로 좁히는가(조건의 성질). 카디널리티가
낮으면 대개 선택도도 낮지만, **편중 분포에서는 갈라진다**(3-3).

### 3-1. 오해 ① "카디널리티 높은 컬럼을 무조건 앞에"

틀린 이유 두 가지. ⑴ 그 컬럼이 **범위 조건**이면 카디널리티가 아무리 높아도
뒤로 가야 한다 — 2-1의 before가 정확히 이 실수다(`created_at`은 카디널리티
최상위지만 범위라서 앞에 두는 순간 `status`가 필터로 강등됐다). ⑵ 등호
컬럼끼리라면 순서를 바꿔도 **같은 쿼리의 최종 구간은 동일**하다 — 2-2.
정확한 순위는 **등호/범위 구분(1순위) → 접두사 재사용(2순위) → 카디널리티
(3순위)**다.

### 3-2. 오해 ② "카디널리티 낮은 컬럼은 복합 인덱스 안에서도 쓸모없다"

단독 인덱스로는 무의미한 `status`(값 3종)가 **복합 안에서는 구간을 쪼개는
칸막이**가 된다. `(user_id, status, created_at)`에서 `status`는 user 한 명의
주문 50건을 PAID 10건으로 좁히는 일을 한다. **조합의 선택도는 (독립이라면)
각 컬럼 선택도의 곱**이다 — user_id로 1/100만 × status로 1/5 = 1/500만.
"인덱스를 탈지 말지"(랜덤 vs 순차 I/O 손익분기)를 정하는 것은 이 **조합의
선택도**이지, 개별 컬럼의 카디널리티가 아니다.

### 3-3. 개입 지점 ① — 편중 분포: 카디널리티 숫자만 보면 속는다

`SHOW INDEX`의 `Cardinality`는 **접두사별 고유값 개수의 추정치(평균)**다.
`status`의 카디널리티가 3이라는 숫자는 "각 값이 33%씩"이라는 인상을 주지만,
실제 분포가 PAID 90% / DONE 9% / FAILED 1%라면 **`status = 'FAILED'`의
선택도는 1%로 충분히 좋다.** 사람이 카디널리티만 보고 "status는 인덱스
무의미"라고 판단하면 (c) 배치 쿼리를 풀스캔으로 방치하게 된다.

```sql
-- ❌ 카디널리티 숫자로 판단
SHOW INDEX FROM orders;   -- status: Cardinality 3  → "무의미하네" (오판)

-- ✅ 분포로 판단 — 이 한 줄이 습관이 돼야 한다
SELECT status, COUNT(*) FROM orders GROUP BY status;
--   PAID 900000 / DONE 90000 / FAILED 10000  → FAILED 조회는 1%, 인덱스 유효
```

옵티마이저 쪽은 인덱스가 있는 컬럼의 등호·범위 조건에 대해 **실제 인덱스를
찔러보는 추정(index dive)**을 하므로 편중을 대체로 잡아낸다. 속는 쪽은
옵티마이저가 아니라 **카디널리티 숫자 하나로 설계 판단을 내리는 사람**이다.

### 3-4. 개입 지점 ② — 접두사만 쓰는 쿼리의 효율

2-2에서 본 대로다. 등호 컬럼 A, B가 있고 "A만 쓰는 쿼리"와 "B만 쓰는 쿼리"가
둘 다 있어 접두사 재사용으로 우열이 안 갈릴 때, **카디널리티 높은 쪽을 앞에**
둔다 — 접두사만으로도 구간이 좁아져 인덱스가 실제로 쓰이도록. 카디널리티가
낮은 쪽을 앞에 두면 그 접두사 쿼리는 옵티마이저가 인덱스를 버린다.

**(가산점 포인트)** MySQL 8.0의 **skip scan**은 선두 컬럼이 조건에 없어도
선두 컬럼의 고유값이 아주 적을 때 값마다 뒤 컬럼 구간을 따로 탐색해 준다.
"카디널리티 낮은 컬럼을 앞에 두면 접두사 규칙을 우회할 수 있다"는 뜻이지만,
고유값 수만큼 탐색을 반복하므로 **선두 카디널리티가 한 자릿수일 때만** 의미
있는 예외다. 설계 원칙을 대체하지 않는다.

### 3-5. 카디널리티 관계 — 한 장 요약 (암기)

| 질문 | 답 |
|---|---|
| 카디널리티가 컬럼 **순서**를 정하나? | 3순위. 등호/범위 → 접두사 재사용 → 그다음 |
| 카디널리티가 "인덱스를 **탈지**"를 정하나? | 개별 컬럼이 아니라 **조합의 선택도**가 정한다 (Q2 손익분기) |
| 낮은 카디널리티 컬럼은 버리나? | 단독은 무의미, 복합 안에서는 **칸막이**. 편중 분포면 단독도 유효 |
| 무엇을 보고 판단하나? | `Cardinality` 숫자가 아니라 **`GROUP BY` 분포** |

## 4. 트레이드오프 — 한 호흡에 양면으로

순서를 정하는 각 결정에는 대가가 붙어 있다. 편익만 말하면 반쪽이다.

| 결정 | 얻는 것 | 내주는 것 |
|---|---|---|
| 정렬·커버링용 컬럼을 뒤에 더 붙인다 | filesort 제거, 북마크 룩업 제거 | 엔트리 폭↑ → 페이지당 엔트리↓ → **버퍼 풀 적재율↓**([Q3 문서 §2-1](clustered-vs-secondary-index.md)의 사슬); 그 컬럼이 자주 바뀌면(`status` 전이) **UPDATE마다 인덱스 엔트리를 지우고 다시 꽂는** 쓰기 증폭 |
| 기존 인덱스의 순서를 바꾼다 | 대상 쿼리 최적 | 그 인덱스의 접두사에 기대던 **다른 쿼리가 조용히 풀스캔으로 전락** — 에러가 아니라 지연으로 나타나서 늦게 발견된다 |
| 넓은 인덱스 하나로 여러 쿼리 커버 | 인덱스 수↓ → DML당 갱신 트리 수↓, 버퍼 풀 경쟁↓ | 각 쿼리는 차선(어떤 쿼리는 filesort 감수), 순서 변경 시 영향 범위↑ |
| 쿼리별 좁은 인덱스 여럿 | 각 쿼리 최적 | DML마다 트리 N개 갱신, 공간, 후보가 많아져 **옵티마이저 선택 실패 확률↑** |
| 범위 조건이 둘일 때 하나만 인덱스 범위로 | 더 좁히는 범위로 스캔 폭 최소화 | 다른 범위는 필터 → 그만큼 초과 스캔 + 북마크 룩업 |

특히 첫 줄 — **자주 바뀌는 컬럼을 인덱스에 넣는 대가**는 놓치기 쉽다.
세컨더리 인덱스는 값 순서로 정렬돼 있으므로 `status`가 `PAID → DONE`으로
바뀌면 엔트리가 PAID 칸에서 DONE 칸으로 **이동**해야 한다(삭제 + 삽입).
주문 하나가 상태를 다섯 번 바꾸면 그 인덱스에 쓰기 열 번이다. "조회가
빨라진다"만 말하고 이걸 빠뜨리면 트레이드오프 서술이 아니다.

## 5. 안전망 — 순서 규칙을 사람의 기억이 아니라 코드·설정에 박는다

"등호 먼저, 범위 뒤"를 리뷰어가 기억해 주기를 바라는 것이 가장 약한 안전망이다.
고정할 곳은 넷이다.

**⑴ 이름에 순서를 박는다.** 인덱스 이름이 컬럼 순서를 그대로 드러내면,
마이그레이션 PR에서 이름만 보고도 "범위 컬럼이 앞에 있네"를 잡을 수 있다.

```sql
-- ❌ 순서가 안 보이는 이름 — 리뷰어가 정의문을 열어봐야 안다
CREATE INDEX idx_orders_1 ON orders (created_at, status);

-- ✅ 이름 = 컬럼 순서
CREATE INDEX idx_orders_status_created_at ON orders (status, created_at);
```

**⑵ 실행 계획을 테스트로 단정한다.** `EXPLAIN FORMAT=JSON`의 `used_key_parts`는
**어느 컬럼까지 액세스 조건으로 쓰였는지**를 배열로 준다. "범위 컬럼까지
탔는가"를 사람이 눈으로 보는 대신 테스트가 본다.

```java
@Test
void 실패주문_알림쿼리는_status_created_인덱스를_범위컬럼까지_탄다() throws Exception {
    // given: 실전 규모의 데이터 + 통계 갱신 (아래 주의 참고)
    seedOrders(200_000);
    jdbcTemplate.execute("ANALYZE TABLE orders");

    // when
    String plan = jdbcTemplate.queryForObject(
        "EXPLAIN FORMAT=JSON SELECT id, user_id, amount FROM orders "
      + "WHERE status = 'FAILED' AND created_at >= ?",
        String.class, LocalDateTime.now().minusHours(1));
    JsonNode table = objectMapper.readTree(plan).at("/query_block/table");

    // then: 의도한 인덱스를, 범위 컬럼(created_at)까지 액세스 조건으로 사용
    assertThat(table.get("key").asText()).isEqualTo("idx_orders_status_created_at");
    assertThat(table.get("used_key_parts"))
        .extracting(JsonNode::asText)
        .containsExactly("status", "created_at");   // 순서가 뒤집히면 여기서 깨진다
}
```

> **주의 — 이 테스트에도 대가가 있다.** 실행 계획은 **데이터 양과 통계에 따라
> 바뀐다.** 행이 수백 건뿐인 테스트 DB에서는 옵티마이저가 인덱스 대신 풀스캔을
> 고르는 게 정상이라 테스트가 거짓 실패한다. 그래서 실전 규모의 시드 +
> `ANALYZE TABLE`이 필요하고, 그만큼 테스트가 무거워진다. 모든 쿼리에 걸지
> 말고 **테이블 규모가 크고 순서 실수가 곧 장애인 쿼리 몇 개**에만 건다.
> (Testcontainers로 MySQL을 띄우는 구성은 3장 문서들 참고.)

**⑶ 중복·미사용 인덱스를 사람이 기억하지 않는다.** `(A, B)`를 만들면서 기존
`(A)`를 지우는 걸 잊는 일은 반드시 생긴다. MySQL `sys` 스키마의 뷰를 배치나
대시보드로 주기 조회한다.

```sql
SELECT * FROM sys.schema_redundant_indexes WHERE table_name  = 'orders';  -- 접두사에 흡수되는 인덱스
SELECT * FROM sys.schema_unused_indexes    WHERE object_name = 'orders';  -- 재시작 후 한 번도 안 쓰인 인덱스
```

**⑷ 슬로 쿼리 로그를 켜 두고 `key_len`·`filtered`를 본다.** `long_query_time`을
낮게 잡아 두면, 순서 실수로 스캔 폭이 늘어난 쿼리는 `rows`가 크고 `filtered`가
낮은(훑은 것 대비 남은 것이 적은) 형태로 잡힌다. 운영에서 "느려요"가 오기 전에
설정이 먼저 알려주는 구조다.

## 6. 꼬리질문 대비 포인트

### "카디널리티 높은 컬럼을 앞에 두라고 배웠는데, 틀린 건가요?"

반쯤 맞다 — **3순위 기준으로는 맞고, 1순위로 쓰면 틀린다.** 1순위는
등호/범위 구분이다: 범위 조건 컬럼은 카디널리티가 최상위여도 뒤로 가야 한다
(`created_at`을 앞에 둔 순간 `status`가 필터로 강등돼 스캔 폭이 100배가 된
예). 2순위는 접두사 재사용 — 등호 컬럼끼리는 같은 쿼리에서 순서를 바꿔도
최종 구간이 같으므로, "이 인덱스의 앞부분만 쓰는 다른 쿼리"가 무엇인지가
순서를 정한다. 카디널리티는 그래도 우열이 안 갈릴 때, **접두사만으로도 구간이
좁아지도록** 높은 쪽을 앞에 두는 타이브레이커다.

### "범위 조건이 두 개(`created_at` 기간 + `amount >= ?`)면 어떻게 하나요?"

인덱스는 **범위를 하나만 액세스 조건으로** 쓴다 — 첫 범위 뒤는 정렬이
깨지므로 두 번째 범위는 필터가 된다. 그래서 둘 중 **더 좁히는 범위**(또는
`ORDER BY`에 쓰이는 범위)를 인덱스의 범위 컬럼으로 두고, 나머지는 그 뒤에
붙여 ICP 필터로 처리한다(뒤에 붙이면 적어도 북마크 룩업 전에 걸러진다).
한 단계 위의 답은 **요건을 되물어 하나를 등호로 바꿀 수 있는지** 보는 것 —
"금액 1만 원 이상"이 사실상 고정된 기준이면 `is_high_amount` 같은 플래그(또는
생성 컬럼)를 등호로 쓸 수 있다. 다만 그건 스키마 변경과 쓰기 비용을 지불하는
결정이므로, 두 번째 범위의 필터 비용을 **실측**한 뒤에 간다.

### "`(user_id, status, created_at)`가 있는데 `WHERE user_id = ? ORDER BY created_at DESC LIMIT 20`이 filesort를 합니다. 왜죠? 어떻게 하죠?"

가운데 `status`가 조건에 없어서다. user 100의 구간 안에서 `created_at`은
**status별로 따로** 정렬돼 있지(DONE 칸의 시간순, PAID 칸의 시간순…) 전체가
시간순이 아니다. 선택지는 넷이고 각각 대가가 있다. ⑴ 사용자당 행이 수십 건이면
filesort 비용이 미미할 수 있다 — **실측하고 수용**. ⑵ `(user_id, created_at)`을
따로 만든다 — 이 쿼리는 최적, 대가는 인덱스 하나 몫의 쓰기·공간.
⑶ 쿼리에 `status IN (모든 값)`을 넣어도 구간이 값 수만큼 갈라져 병합 정렬이
필요하므로 filesort는 대개 안 사라진다. ⑷ 순서를 `(user_id, created_at, status)`로
바꾸면 이 쿼리는 해결되지만, `user_id + status + 정렬` 쿼리에서 `status`가
필터로 강등된다 — **어느 쿼리가 더 뜨거운지**를 슬로 로그로 측정해 결정한다.

### "인덱스 하나를 넓게(4~5컬럼) 만들어 여러 쿼리를 커버하는 것과 쿼리별로 좁은 인덱스를 여러 개 두는 것, 기준은?" (시니어 변별 포인트)

양면을 먼저 편다. 넓은 하나는 **DML당 갱신하는 트리 수와 버퍼 풀 경쟁을
줄이지만**, 각 쿼리는 차선이 되고 순서를 바꿀 때 영향 범위가 커진다. 좁은
여럿은 **각 쿼리가 최적이지만** 쓰기 증폭·공간·옵티마이저 선택 혼선을 낸다.
기준은 셋 — ① **읽기:쓰기 비율**(쓰기가 무거운 테이블일수록 넓은 하나로
합친다) ② **접두사 공유 여부**(쿼리들이 같은 등호 컬럼으로 시작하지 않으면
넓혀도 못 커버하므로 애초에 선택지가 아니다) ③ **포함 컬럼의 변경 빈도**
(자주 바뀌는 컬럼을 넓은 인덱스에 넣으면 그 인덱스 전체가 쓰기 부담을 진다).
그리고 결정보다 중요한 건 **"각 인덱스가 어떤 쿼리를 위해 존재하는지"를 표로
남기는 것** — 이게 없으면 다음 사람이 순서를 바꾸다 다른 쿼리를 깨뜨린다.

### "순서를 잘 잡았는데 어느 날부터 옵티마이저가 그 인덱스를 안 탑니다" (가산점 포인트)

순서는 안 바뀌었어도 **조합의 선택도**는 바뀐다. 후보 셋을 순서대로 본다.
① **데이터 분포 변화** — FAILED가 1%였다가 외부사 장애로 40%가 되면
`status = 'FAILED'` 구간이 손익분기를 넘어 풀스캔이 정답이 된다(옵티마이저가
맞다). ② **통계가 낡음** — 대량 적재·삭제 후 `rows` 추정이 어긋나면
`ANALYZE TABLE`로 갱신([Q2 문서 §5-2](index-not-used-full-scan.md)).
③ **새로 추가된 인덱스가 후보로 경쟁** — 누군가 비슷한 인덱스를 만들어
옵티마이저가 그쪽을 고르기 시작한 경우, `sys.schema_redundant_indexes`로
확인한다. 힌트(`FORCE INDEX`)는 이 셋을 다 확인한 뒤의 최후 수단이고, 쓰면
"왜 옵티마이저를 못 믿었는지"를 주석과 이슈로 남긴다.

## 한 줄 요약

**복합 인덱스는 "앞 컬럼 값이 하나로 고정돼야 뒤 컬럼 정렬이 살아 있는"
사전 안의 사전이므로, 순서는 등호 → 범위(하나, 맨 뒤) → 정렬 → 커버링
순으로 배치하고, 등호 컬럼끼리는 접두사 재사용 → 카디널리티 순으로 정한다.
카디널리티는 순서의 3순위 기준일 뿐이며 "인덱스를 탈지"는 개별 컬럼이 아닌
조합의 선택도가 정한다. 순서가 틀리면 조건이 액세스에서 필터로 강등 →
스캔 폭↑ → 버릴 행에 북마크 룩업(랜덤 I/O) → 버퍼 풀 오염 — 이 사슬로
비용을 말하고, 규칙은 인덱스 이름·플랜 단정 테스트·`sys` 뷰에 박아 둔다.**
