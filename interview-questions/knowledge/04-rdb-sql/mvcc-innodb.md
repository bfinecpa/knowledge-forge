# MVCC와 InnoDB 구현 — "읽기는 왜 락을 안 잡는가"를 숨은 컬럼·undo 체인·Read View로 답한다

> 핵심 관전 포인트: **MVCC(다중 버전 동시성 제어)는 "읽는 쪽이 락을 잡는
> 대신, 자기 시점에 맞는 과거 버전을 본다"는 격리(I) 구현 방식이다. 그래서
> 읽기는 쓰기를 막지 않고 쓰기는 읽기를 막지 않지만, 쓰기끼리는 여전히
> 락이다. InnoDB는 이를 세 부품으로 구현한다 — ① 행마다 숨은 컬럼
> `DB_TRX_ID`(마지막으로 바꾼 트랜잭션)·`DB_ROLL_PTR`(이전 버전이 있는 undo
> 위치), ② 이전 값들을 연결 리스트로 쌓아 두는 **undo 로그 = 버전 체인**,
> ③ 조회 시점에 "어떤 트랜잭션까지 보이는가"를 찍어 두는 **Read View**.
> Read View를 문장마다 새로 만들면 READ COMMITTED, 트랜잭션의 첫 읽기 때
> 한 번만 만들면 REPEATABLE READ — 격리 수준 차이는 이 생성 시점 하나다.
> 비용은 트랜잭션 길이에 비례한다: 오래된 Read View 하나가 살아 있으면
> purge가 그 뒤의 undo를 못 지우고 → 버전 체인이 길어져 → 무관한
> 트랜잭션의 조회까지 행마다 체인을 순회하느라 느려진다.**

---

## 0. 질문 + 의도

**질문**: "MVCC란 무엇인가요? InnoDB에서 어떻게 구현되어 있나요?"

**출제 의도**: "읽기는 왜 락을 안 잡는가"를 이해해야 격리 수준, 락 경합,
undo 폭증(긴 트랜잭션의 해악) 같은 운영 이슈가 **전부 연결**된다. RDB 내부
이해의 허리에 해당하는 개념이다. 즉 이 질문은 MVCC 정의 암기가 아니라 —
[격리 수준 4단계](./transaction-isolation-levels.md)가 내부적으로 무엇이
다른 건지, [ACID의 I](./transaction-acid.md)가 무슨 장치로 구현되는지,
"트랜잭션은 짧게"라는 격언의 근거가 무엇인지를 **하나의 메커니즘으로 꿰어
말할 수 있는지**를 본다. 여기가 뚫리면 다음 문항(갭 락·데드락, 긴
트랜잭션의 해악)이 전부 이 문서의 응용 문제가 된다.

> 이 문서는 [transaction-acid.md](./transaction-acid.md)(I = 락 + MVCC,
> undo = A의 도구)와 [transaction-isolation-levels.md](./transaction-isolation-levels.md)
> (RC/RR의 차이, InnoDB RR이 phantom을 막는 이유)를 전제로, 그 두 문서가
> "MVCC"라는 단어로 뭉뚱그려 넘긴 내부를 연다.

## 1. 개념 — MVCC는 "락 대신 과거 버전을 보여주는" 격리 구현 방식

### 1-1. 락만으로 격리하면 무엇이 문제인가

격리성(I)의 요구는 "동시 트랜잭션이 서로의 중간 상태를 보지 않는다"다.
가장 단순한 구현은 **읽을 때도 락을 잡는 것**이다 — 내가 읽는 행은 남이 못
고치고(공유 락), 남이 고치는 중인 행은 내가 못 읽는다(배타 락에 막힘).
정확하긴 한데 비용이 치명적이다:

- 통계 쿼리 하나가 10만 행을 읽는 동안 그 10만 행에 대한 UPDATE가 전부
  대기한다 — **읽기가 쓰기를 막는다.**
- 주문 한 건을 갱신 중이면 그 주문을 보려는 조회가 전부 대기한다 —
  **쓰기가 읽기를 막는다.**

웹 서비스 트래픽은 읽기가 압도적이다. 읽기마다 락이면 동시성이 죽는다.

### 1-2. MVCC의 아이디어 — 행을 덮어쓰지 말고 버전을 남긴다

MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)는 발상을
바꾼다. **UPDATE가 행을 덮어쓰더라도 이전 값을 어딘가에 남겨 두면, 읽는
쪽은 락을 기다릴 필요 없이 "자기 시점에 맞는 버전"을 골라 읽으면 된다.**

비유하면 — 문서를 한 부만 두고 "편집 중이니 읽지 마세요" 팻말을 거는 대신
(락), 편집할 때마다 이전 판을 서랍에 보관하고 읽는 사람에게는 "당신이
들어온 시각 기준 최신 판"을 건네는 것이다(MVCC). 편집자와 독자가 서로를
기다리지 않는다.

이로부터 MVCC의 성질이 한 문장으로 정리된다 — **"읽기는 쓰기를 막지 않고,
쓰기는 읽기를 막지 않는다. 단, 쓰기끼리는 여전히 락이다."** 마지막 절이
중요하다. 같은 행을 두 트랜잭션이 동시에 UPDATE하는 충돌은 버전을 아무리
쌓아도 해결되지 않는다 — 누가 먼저 쓸지 정해야 하고 그건 락의 일이다.
MVCC는 격리성의 **읽기 절반**을 맡고, 나머지 쓰기 절반은 락이 맡는다.

### 1-3. ACID와 연결 — I의 두 축, 그리고 undo의 겸직

[ACID 문서](./transaction-acid.md)에서 I(격리성)의 메커니즘을 "락 + MVCC"로
적었다. 이제 그 뜻이 정확해진다:

- **I = 락(쓰기-쓰기 충돌 직렬화) + MVCC(읽기-쓰기 비차단)**
- 그리고 MVCC가 "이전 버전"을 보관하는 장소가 바로 **undo 로그**다.

여기서 undo 로그가 **두 글자를 겸직**한다는 점을 짚어야 한다. ACID
문서에서 undo는 A(원자성)의 도구였다 — 변경 **전** 값을 적어 두었다가
롤백 때 거꾸로 적용한다. 그런데 "변경 전 값"은 정확히 MVCC가 다른
트랜잭션에게 보여 줘야 하는 "과거 버전"이기도 하다. 같은 장부 하나가
**롤백용(A)** 이자 **과거 버전 제공용(I)** 이다. 이 겸직 때문에 뒤에서
볼 "undo 누적"은 A의 비용(롤백이 오래 걸림)과 I의 비용(조회가 느려짐)을
**동시에** 청구한다.

## 2. InnoDB 구현 — 세 부품: 숨은 컬럼 · undo 버전 체인 · Read View

### 2-1. 숨은 컬럼 3개 (암기 목록)

InnoDB는 사용자가 정의한 컬럼 외에 모든 클러스터드 인덱스 레코드(= 실제
행)에 시스템 컬럼을 붙인다:

| 숨은 컬럼 | 크기 | 뜻 |
|---|---|---|
| `DB_TRX_ID` | 6바이트 | 이 행을 **마지막으로 INSERT/UPDATE/DELETE-mark한 트랜잭션의 ID** |
| `DB_ROLL_PTR` | 7바이트 | 이 행의 **직전 버전이 기록된 undo 로그 레코드를 가리키는 포인터**(롤백 포인터) |
| `DB_ROW_ID` | 6바이트 | PK도, NOT NULL UNIQUE도 없는 테이블에서만 붙는 **자동 증가 행 ID**(클러스터드 인덱스 키 대용) |

MVCC의 주역은 앞의 둘이다. `DB_TRX_ID`는 "이 버전을 누가 만들었나", `DB_ROLL_PTR`은
"이 버전 이전엔 뭐였나"에 답한다. 트랜잭션 ID는 **쓰기 트랜잭션이 시작될 때
단조 증가로 발급**되므로, ID의 크기 비교가 곧 시간 순서 비교다 — Read View
판정이 숫자 비교만으로 가능한 이유다.

### 2-2. undo 로그 = 버전 체인

`UPDATE`가 일어날 때 InnoDB가 하는 일을 순서대로 놓으면 버전 체인이 저절로
그려진다:

1. 현재 행의 값(과 현재 `DB_TRX_ID`, `DB_ROLL_PTR`)을 **undo 로그 레코드로
   복사**한다.
2. 행을 새 값으로 **제자리에서 덮어쓴다**(in-place). `DB_TRX_ID`에 내
   트랜잭션 ID, `DB_ROLL_PTR`에 방금 만든 undo 레코드 위치를 적는다.
3. 방금 만든 undo 레코드 안에는 **그 이전 버전을 가리키는 롤 포인터**가
   그대로 들어 있다 — 그래서 undo 레코드들이 **연결 리스트**를 이룬다.

```text
[클러스터드 인덱스의 현재 행]
  id=1  stock=7   DB_TRX_ID=120  DB_ROLL_PTR ─┐
                                              ▼
                     [undo]  stock=8  TRX_ID=115  ROLL_PTR ─┐
                                                           ▼
                                        [undo]  stock=9  TRX_ID=101  ROLL_PTR ─┐
                                                                               ▼
                                                           [undo]  stock=10  TRX_ID=90  (끝)

  ← 최신                      버전 체인 (roll pointer를 따라 과거로)                  오래된 →
```

**행 하나에 버전이 여러 개 존재하되, 테이블(클러스터드 인덱스)에는 항상 최신
하나만 있고 나머지는 undo에 사슬로 매달려 있다.** 이것이 InnoDB MVCC의
저장 구조다.

undo 로그는 용도가 둘로 나뉜다 (가산점 포인트):

- **insert undo** — INSERT를 되돌리는 정보. 롤백에만 필요하고 다른
  트랜잭션이 "과거 버전"으로 볼 일이 없으므로(INSERT 전엔 행이 없었다)
  **커밋 즉시 폐기**된다.
- **update undo** — UPDATE/DELETE의 이전 값. 롤백(A)에도 쓰이지만
  **다른 트랜잭션의 일관된 읽기(I)에도 쓰이므로**, 커밋했다고 바로 못
  지운다. "이 버전을 봐야 하는 Read View가 하나도 없다"가 확인될 때까지
  보존되고, 그 정리를 **purge**라는 백그라운드 작업이 맡는다(3절).

DELETE도 마찬가지다. InnoDB의 DELETE는 행을 물리적으로 지우지 않고
**delete-mark(삭제 표시) 비트만 켠다** — 아직 그 행을 봐야 할 Read View가
있을 수 있기 때문이다. 실제 제거는 역시 purge의 몫이다.

### 2-3. Read View (암기 목록) — "내 눈에 보이는 트랜잭션의 경계"

버전 체인이 "재료"라면, Read View는 "어느 버전을 고를지 정하는 기준"이다.
일관된 읽기(consistent read)를 시작하는 순간 InnoDB는 **그 시점에 어떤
트랜잭션이 아직 안 끝났는지**를 스냅샷으로 찍어 둔다. 구성 요소는 넷이다:

| 구성 요소 | 소스 상의 이름 | 뜻 |
|---|---|---|
| **활성 트랜잭션 ID 목록** | `m_ids` | Read View 생성 시점에 시작됐지만 아직 커밋/롤백 안 된 쓰기 트랜잭션들 |
| **하한선** | `m_up_limit_id` | 활성 목록 중 **최솟값**. 이보다 작은 ID는 전부 이미 끝난 트랜잭션 → **무조건 보임** |
| **상한선** | `m_low_limit_id` | 생성 시점에 **다음에 발급될 ID**(= 현재 최대 ID + 1). 이 이상은 내 스냅샷 이후 시작 → **무조건 안 보임** |
| **자기 트랜잭션 ID** | `m_creator_trx_id` | 내가 만든 변경은 커밋 전이라도 나에게는 보여야 하므로 따로 기억 |

> 소스의 이름이 직관과 반대다 — `up_limit`이 **하한**(low water mark),
> `low_limit`이 **상한**(high water mark)이다. 면접에서는 "하한선 = 활성
> 중 최소 ID, 상한선 = 다음 발급 ID"라는 뜻으로 말하면 충분하다.

이 넷으로 **어떤 버전의 `DB_TRX_ID`가 나에게 보이는가**를 판정하는 규칙은
4단계다 (순서대로 적용):

1. `trx_id == 자기 ID` → **보임** (내가 바꾼 건 나에게 보인다)
2. `trx_id < 하한선` → **보임** (내가 스냅샷 찍기 전에 이미 끝난 트랜잭션)
3. `trx_id ≥ 상한선` → **안 보임** (내 스냅샷 이후에 시작한 트랜잭션)
4. 그 사이 값이면 **활성 목록에 있으면 안 보임**(찍을 당시 진행 중이었으니,
   그 후 커밋됐더라도 내 스냅샷엔 없다), **없으면 보임**(찍기 전에 이미
   커밋된 트랜잭션)

4번이 핵심이다. "하한선과 상한선 사이"는 ID가 발급된 순서와 커밋 순서가
다를 수 있는 구간이라, 목록을 직접 확인해야 한다. 이 규칙 덕분에 **"내가
스냅샷을 찍은 순간 커밋되어 있던 세상"**이 정확히 재구성된다.

### 2-4. 한 행을 읽는 절차 — 판정 → 체인 순회

일반 SELECT가 행 하나를 만났을 때:

```text
1. 클러스터드 인덱스의 현재 행을 본다. DB_TRX_ID를 Read View로 판정.
   └ 보임 → 이 버전을 결과로 반환. 끝.
   └ 안 보임 → 2로
2. DB_ROLL_PTR을 따라 undo 레코드로 가서 직전 버전을 재구성한다.
   그 버전의 TRX_ID를 다시 판정.
   └ 보임 → 반환
   └ 안 보임 → 다시 ROLL_PTR을 따라 더 과거로 … (반복)
3. 체인 끝까지 갔는데도 보이는 버전이 없다
   → 내 스냅샷 시점엔 이 행이 존재하지 않았던 것 → 결과에서 제외
```

**락은 어디에도 없다.** 남이 지금 그 행을 UPDATE 중이어도(배타 락을 잡고
있어도) 나는 undo에서 이전 버전을 꺼내 읽으면 된다. 이것이 "읽기가 락을 안
잡는" 정확한 이유다.

그리고 이 절차에 **비용의 씨앗**이 보인다 — 2번 반복 횟수는 **버전 체인의
길이**다. 체인이 짧으면 공짜에 가깝고, 길면 행 하나 읽는 데 undo 페이지를
여러 번 뒤진다. 3절의 사슬이 여기서 출발한다.

### 2-5. 격리 수준별 Read View 생성 시점 (암기) — 차이는 "언제 찍느냐" 하나

| 격리 수준 | 일반 SELECT의 동작 |
|---|---|
| READ UNCOMMITTED | Read View 안 만듦. 클러스터드 인덱스의 **현재 행을 그대로** 읽음 → 미커밋 값도 보임(dirty read) |
| **READ COMMITTED** | **문장(statement)마다 새 Read View** → 매 SELECT가 그 순간 커밋된 최신을 봄 → non-repeatable read 발생 |
| **REPEATABLE READ** | **트랜잭션의 첫 일관된 읽기 때 한 번 만들고 끝까지 재사용** → 같은 스냅샷을 계속 봄 → non-repeatable read·phantom 방지 |
| SERIALIZABLE | 일반 SELECT도 공유 락을 잡는 잠금 읽기로 바뀜(MVCC 스냅샷을 쓰지 않음) |

**RC와 RR의 내부 차이는 코드 몇 줄 — "Read View를 문장마다 새로 만드느냐,
트랜잭션당 한 번 만드느냐"다.** 격리 수준 문서에서 "RR은 첫 읽기 시점의
스냅샷을 유지한다"고 한 문장의 실체가 이것이다.

주의할 디테일 두 가지 (가산점 포인트):

- RR의 Read View는 `BEGIN` 시점이 아니라 **첫 일관된 읽기(SELECT)를
  실행하는 순간** 만들어진다. `BEGIN` 후 한참 있다가 첫 SELECT를 하면
  스냅샷은 그 SELECT 시점이다. `START TRANSACTION WITH CONSISTENT SNAPSHOT`
  을 쓰면 즉시 만들어진다.
- **스냅샷 읽기 vs 현재 읽기(잠금 읽기)**: Read View를 쓰는 건 **일반
  SELECT뿐**이다. `SELECT ... FOR UPDATE / FOR SHARE`, `UPDATE`, `DELETE`는
  격리 수준과 무관하게 **항상 최신 커밋 버전을 읽고 락을 잡는다**(공식
  용어는 locking read, 흔히 current read라고도 부른다). 격리 수준 문서에서
  "일반 SELECT와 잠금 읽기를 섞으면 phantom처럼 보인다"고 한 이유가 이
  둘이 서로 다른 세상을 보기 때문이다.

이 디테일에서 자연스럽게 나오는 실무 함정 하나 — RR에서 내 SELECT는
과거 스냅샷을 보는데 내 UPDATE는 최신 행에 적용된다. "SELECT로 재고 10개
확인 → `UPDATE SET stock = 9`"는 그 사이 남이 재고를 3으로 줄였어도 9로
덮어쓴다(갱신 유실). 꼬리질문 4에서 다룬다.

## 3. 비용 — "긴 트랜잭션 → undo 누적 → purge 지연 → 조회 저하" 사슬

이 절이 이 문서가 가장 겨냥하는 지점이다. "긴 트랜잭션은 안 좋다"가 아니라
**어떤 부품이 어떤 순서로 막혀서 누구의 무엇이 느려지는지**를 이름 붙여
말해야 한다.

### 3-1. purge는 무엇을 하는가

purge는 InnoDB의 백그라운드 스레드로, 두 가지를 치운다:

- 더 이상 어떤 Read View도 필요로 하지 않는 **update undo 레코드**를 폐기
- delete-mark만 켜져 있던 행과 그 **인덱스 엔트리를 물리적으로 제거**

"더 이상 필요 없다"의 판정 기준은 단순하다 — **현재 살아 있는 가장 오래된
Read View**가 그 버전을 볼 가능성이 없으면 지운다. 바꿔 말하면 **가장
오래된 Read View 하나가 purge의 진도를 결정한다.** 커밋됐지만 아직 purge되지
않은 undo의 목록이 **history list**이고, 그 길이가 `SHOW ENGINE INNODB
STATUS`에 찍히는 **History list length**다 — MVCC 건강의 대표 지표다.

### 3-2. 사슬 — 이름 붙여서 순서대로

```text
① 트랜잭션 하나가 오래 열려 있다 (RR이면 첫 SELECT 이후 Read View 보유)
      ↓
② purge가 그 Read View 이후의 update undo를 하나도 지우지 못한다
   — "가장 오래된 Read View가 볼 수도 있는 버전"이라서. 이 트랜잭션이
     그 테이블을 안 보더라도 무관하다. Read View는 테이블 단위가 아니다.
      ↓
③ History list length가 계속 증가, undo 테이블스페이스가 팽창한다
      ↓
④ 자주 갱신되는 행(핫 로우)의 버전 체인이 수십·수백 개로 길어진다
      ↓
⑤ 그 행을 읽는 "다른 모든" 트랜잭션이 행마다 체인을 순회한다
   — undo 페이지를 버퍼 풀로 끌어올리며(I/O), 버전을 재구성하며(CPU).
     범인이 아닌 짧은 조회들까지 느려진다. 버퍼 풀은 undo 페이지로
     오염돼 정작 데이터 페이지의 적중률이 떨어진다.
      ↓
⑥ delete-mark 행이 물리 삭제되지 않아 인덱스에 유령 엔트리가 쌓인다
   — 범위 스캔·COUNT가 "이미 지운 행"까지 읽고 걸러낸다. 테이블은
     비어 가는데 조회는 느려지는 역설이 여기서 난다.
      ↓
⑦ 마침내 긴 트랜잭션이 끝나면 밀린 purge가 한꺼번에 돌아 I/O 스파이크.
   롤백으로 끝나면 자기 undo를 역순으로 전부 적용하느라 롤백 자체가
   또 오래 걸린다 (A의 비용 — 1-3절의 겸직)
```

이 사슬의 각 단계를 이름으로 부를 수 있어야 한다 — **Read View 보유 →
purge 정지 → history list 증가 → 버전 체인 길이 증가 → 체인 순회 비용
(무관 트랜잭션 전파) → 유령 인덱스 엔트리 → 종료 시 purge 폭주.** "조회가
느려진다"에서 멈추면 결과만 말한 것이고, "왜 무관한 조회까지"에 답하려면
②와 ⑤가 있어야 한다.

핵심 통찰을 한 문장으로 — **MVCC의 청구서는 트랜잭션이 "무엇을 했는가"가
아니라 "얼마나 오래 열려 있었는가"에 비례하고, 그 청구서를 받는 건 그
트랜잭션이 아니라 남들이다.**

### 3-3. 세컨더리 인덱스와 MVCC — 커버링 인덱스가 조용히 무력화되는 순간 (가산점 포인트)

`DB_TRX_ID`는 **클러스터드 인덱스 레코드에만** 있다. 세컨더리 인덱스
엔트리에는 없다. 그럼 세컨더리 인덱스만 읽어서 끝내는 커버링 인덱스 조회는
버전 판정을 어떻게 하나?

InnoDB는 **인덱스 페이지 단위로 `PAGE_MAX_TRX_ID`**(그 페이지를 마지막으로
수정한 트랜잭션 ID)를 갖고 있다. 이 값이 내 Read View의 하한선보다
작으면 "이 페이지의 엔트리는 전부 내가 봐도 되는 것"이라 인덱스만으로
끝낸다. 그런데 **최근에 누군가 그 페이지를 건드렸으면**(또는 엔트리가
delete-mark 상태면) 판정이 불가능해서 **클러스터드 인덱스로 내려가
`DB_TRX_ID`를 확인**한다 — 커버링 인덱스로 설계했는데 갱신이 잦은 구간에서
북마크 룩업(랜덤 I/O)이 되살아나는 것이다. "커버링 인덱스인데 왜 느리지"의
숨은 원인 하나가 MVCC다.

### 3-4. 실무에서 사슬 ①을 만드는 전형적인 코드

가장 흔한 범인은 **트랜잭션 안의 외부 호출**이다. 락 점유·커넥션 풀 고갈
관점의 피해는 [ACID 문서의 "긴 트랜잭션" 꼬리질문](./transaction-acid.md)에서
다뤘고, 여기서는 **MVCC 관점**의 피해를 붙인다 — 이 코드가 도는 동안 DB
전체의 purge가 멈춘다.

```java
// ❌ before: 트랜잭션 안에서 외부 PG 호출
@Transactional
public void settle(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    // ↑ RR이라면 여기서 Read View 생성 — 이 순간부터 purge가 이 시점에 묶인다

    PgResult result = pgClient.capture(order);
    // ↑ 외부 HTTP. 평소 300ms, PG 장애 시 30초 타임아웃 × 재시도.
    //   그동안 이 트랜잭션은 "살아 있는 가장 오래된 Read View"가 되어
    //   DB의 모든 테이블에 대한 undo 정리를 막는다. 커넥션도 점유.

    order.markPaid(result);
}   // 커밋 → 그제야 Read View 해제 → 밀린 purge 폭주
```

```java
// ✅ after: 읽기 트랜잭션 / 외부 호출 / 쓰기 트랜잭션을 분리
public void settle(Long orderId) {
    OrderSnapshot snapshot = orderTxService.loadForSettlement(orderId);
    // ↑ 짧은 @Transactional(readOnly = true) — 수 ms 안에 Read View 생성·해제

    PgResult result = pgClient.capture(snapshot);
    // ↑ 트랜잭션 밖. 30초가 걸려도 DB는 아무것도 붙들지 않는다.

    orderTxService.markPaid(orderId, result);
    // ↑ 별도의 짧은 @Transactional — 상태 검증(이미 처리됐는지) 후 갱신
}
// orderTxService는 별도 빈이어야 @Transactional 프록시가 적용된다(자기 호출 함정)
```

두 번째 범인은 **사람이 연 콘솔 트랜잭션**이다 — `SET autocommit = 0` 상태의
DB 클라이언트에서 `SELECT` 한 번 날리고 창을 켜 둔 채 퇴근하면, 그
세션이 밤새 "가장 오래된 Read View"가 된다. 코드 리뷰로는 절대 못 잡는
유형이라 4-2절의 DB 쪽 안전망이 필요하다.

## 4. 트레이드오프 양면 조립 + 안전망 고정

### 4-1. MVCC의 양면 — 한 호흡으로

"MVCC는 읽기 성능이 좋다"까지만 말하면 절반이다. 얻는 것과 내는 것을 같은
문장에 넣는다.

| 축 | 얻는 것 | 내는 것 |
|---|---|---|
| 읽기 | 락 없이 일관된 스냅샷 — 읽기와 쓰기가 서로 안 막힘 | 행마다 버전 판정 + 체인 순회(CPU·undo 페이지 I/O) |
| 쓰기 | 읽기에 막히지 않음 | 모든 UPDATE/DELETE가 undo를 추가로 기록(쓰기 증폭); 쓰기끼리는 여전히 락 |
| 저장 공간 | — | undo 누적, delete-mark 유령 엔트리, purge 백그라운드 부하 |
| 정합성 | 긴 리포트도 일관된 결과를 봄 | 스냅샷은 "과거"다 — 판단(check-then-act)에 쓰면 갱신 유실 위험 |

조립한 문장: **"MVCC는 읽기 락을 없애 읽기-쓰기 비차단을 얻는 대신, 그
대가를 undo 공간·버전 체인 순회·purge 부하로 치른다. 그리고 그 청구서는
트랜잭션 길이에 비례해 커지고, 범인이 아닌 트랜잭션들에게 배달된다."**
이 문장이 그대로 "그래서 트랜잭션은 짧게"의 근거가 된다.

한 겹 더 (시니어 변별): 이 트레이드오프는 **읽기 위주 OLTP 워크로드에
최적화된 선택**이다. 쓰기 비중이 압도적이거나 같은 행을 초고빈도로
갱신하는 워크로드(카운터, 재고)에서는 버전 체인이 빨리 길어지고 쓰기끼리
락 직렬화가 병목이라 MVCC의 강점이 거의 안 보인다 — 그런 구간은 원자적
UPDATE·버퍼링·배치 반영으로 설계를 바꾸는 것이 답이지 격리 수준을 만지는
게 아니다.

### 4-2. 안전망 — 기억이 아니라 시스템이 잡게 한다

"트랜잭션을 짧게 유지하자"는 규칙을 사람의 기억에 맡기면 반드시 뚫린다.
DB 쪽과 애플리케이션 쪽에 **각각** 고정한다.

**DB 쪽 — 지금 누가 purge를 막고 있는지 즉시 찾는 쿼리**

```sql
-- ① 열려 있는 트랜잭션, 오래된 순. trx_query가 NULL인데 age가 크면
--    "쿼리는 안 돌고 트랜잭션만 열어 둔" 전형적 범인 (외부 호출 대기, 콘솔 방치)
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec,
       trx_mysql_thread_id, trx_rows_locked, trx_query
  FROM information_schema.INNODB_TRX
 ORDER BY trx_started
 LIMIT 10;

-- ② purge 대기 중인 undo 양 (History list length)
SELECT COUNT FROM information_schema.INNODB_METRICS
 WHERE NAME = 'trx_rseg_history_len';
-- 또는 SHOW ENGINE INNODB STATUS\G 의 TRANSACTIONS 절 "History list length"
```

- **②를 모니터링 지표로 수집해 임계치 알림**을 건다. 평소 수준 대비 급증이
  곧 "어딘가에 긴 트랜잭션이 생겼다"는 신호이며, 조회가 느려지기 **전에**
  잡을 수 있는 유일한 선행 지표다.
- 알림이 오면 ①로 범인 스레드를 특정하고 `KILL <thread_id>`. 운영 정책으로
  "N분 이상 열린 idle 트랜잭션은 자동 종료"를 도구(예: `pt-kill`류)로
  고정하는 팀도 많다 — 사람이 새벽에 깨서 죽이는 구조는 안전망이 아니다.
- `innodb_undo_log_truncate`로 팽창한 undo 테이블스페이스를 자동으로
  줄이게 둔다. 단 이건 사후 정리이지 사슬 ①을 막는 게 아니다.

**애플리케이션 쪽 — 긴 트랜잭션을 만들 수 없게**

```java
// 1) 트랜잭션 시간 상한을 코드에 박는다
@Transactional(timeout = 3)   // 초 단위. 초과 시 다음 JDBC 호출/커밋 시점에 예외
public void markPaid(Long orderId, PgResult result) { ... }
// 주의: 외부 HTTP 대기 중에는 아무것도 확인되지 않는다 — 결국 호출 자체를
//       밖으로 빼는 게 근본. timeout은 "빼먹은 곳"을 드러내는 2차 안전망이다.

// 2) 구조로 금지 — @Transactional 클래스가 외부 클라이언트를 의존하지 못하게 (ArchUnit)
@ArchTest
static final ArchRule transactional_services_do_not_call_external_clients =
    noClasses()
        .that().areAnnotatedWith(Transactional.class)
        .should().dependOnClassesThat().resideInAnyPackage("..client..", "..external..")
        .because("트랜잭션 안의 외부 호출은 커넥션 점유와 purge 정지를 동시에 일으킨다");
```

```yaml
# 3) 커넥션 장기 점유를 로그로 노출 (HikariCP) — 긴 트랜잭션은 반드시 긴 커넥션 점유를 동반한다
spring:
  datasource:
    hikari:
      leak-detection-threshold: 5000   # ms. 초과 점유 시 스택 트레이스 경고
```

이 세 겹은 역할이 다르다 — ArchUnit은 **만들지 못하게**(빌드 실패),
timeout은 **만들어졌으면 끊게**, leak detection은 **어디서 만들어졌는지
스택으로 알려주게**. "트랜잭션은 짧게"라는 격언이 팀에서 실제로 지켜지는
건 이 셋이 CI와 운영에 박혀 있을 때다.

## 5. 꼬리질문 대비 포인트

### "MVCC가 있는데 왜 락이 여전히 필요한가요?"

MVCC가 없애는 건 **읽기-쓰기 사이의 대기**뿐이다. 두 트랜잭션이 같은 행을
동시에 UPDATE하는 **쓰기-쓰기 충돌**은 버전을 아무리 쌓아도 "누구 것이
최종인가"를 정할 수 없어 배타 락으로 직렬화한다. 또 `UPDATE`·`DELETE`·
`SELECT ... FOR UPDATE` 같은 잠금 읽기는 스냅샷이 아니라 **최신 버전을 읽고
락을 잡는다** — 스냅샷을 근거로 갱신하면 갱신 유실이 나기 때문이다. 마지막으로
RR에서 "아직 없는 행"의 INSERT를 막는 건 MVCC가 못 하는 일이라 **갭 락**이
맡는다(다음 문항). 정리하면 — 읽기 절반은 MVCC, 쓰기 절반과 범위 보호는 락.

### "READ COMMITTED와 REPEATABLE READ의 차이를 InnoDB 내부 동작으로 설명해 보세요."

숨은 컬럼도 undo 체인도 똑같다. 차이는 **Read View를 언제 만드느냐** 하나다.
RC는 **문장마다 새 Read View**를 만들어 매 SELECT가 그 순간 커밋된 최신을
보고, RR은 **트랜잭션의 첫 일관된 읽기 때 한 번 만들어 끝까지 재사용**한다.
그래서 RC에서는 두 SELECT 사이에 남이 커밋하면 값이 바뀌고(non-repeatable
read), RR에서는 같은 스냅샷을 보니 안 바뀐다. 덧붙이면 RR의 Read View는
`BEGIN`이 아니라 첫 SELECT 시점에 만들어지고, 잠금 읽기는 두 수준 모두
스냅샷을 쓰지 않는다. 운영 관점으로 한 줄 더 — RC는 Read View 수명이 문장
단위라 **긴 트랜잭션이 purge를 막는 정도가 훨씬 약하다.** 배치·통계성 긴
조회를 RC로 내리는 판단의 근거가 이것이다.

### "긴 트랜잭션 하나가 왜 그것과 무관한 다른 조회까지 느리게 만드나요? 어떻게 확인하죠?"

메커니즘 사슬로 답한다. ① 긴 트랜잭션이 Read View를 보유한다 → ② purge는
"가장 오래된 Read View가 볼 수도 있는 버전"을 지울 수 없어 그 이후의
update undo를 전부 보존한다 — **Read View는 테이블 단위가 아니라 DB
전체에 걸린다**, 그래서 무관한 테이블도 영향권이다 → ③ History list
length 증가 → ④ 자주 갱신되는 행의 버전 체인이 길어진다 → ⑤ 그 행을
읽는 모든 트랜잭션이 **행마다 체인을 순회**하며 undo 페이지 I/O와 CPU를
쓴다 → ⑥ delete-mark 행이 인덱스에 유령으로 남아 범위 스캔이 더 읽는다.
확인은 `INNODB_METRICS`의 `trx_rseg_history_len`(또는 `SHOW ENGINE INNODB
STATUS`의 History list length) 급증으로 감지하고, `information_schema.INNODB_TRX`를
`trx_started` 순으로 정렬해 **쿼리는 없는데 오래 열린** 트랜잭션을 특정한다.
재발 방지는 지표 알림 + 장기 idle 트랜잭션 자동 종료 + 코드 쪽 ArchUnit·timeout.

### "REPEATABLE READ에서 SELECT로 재고 10개를 확인하고 UPDATE로 9를 썼는데 재고가 꼬였습니다. 왜 그렇고, 어떻게 고치나요?" (시니어 변별 포인트)

**스냅샷 읽기와 현재 읽기가 다른 세상을 보기 때문**이다. 일반 SELECT는
Read View 기준 과거 스냅샷(10)을 보여 주지만, UPDATE는 격리 수준과 무관하게
**최신 커밋 행**에 적용된다. 그 사이 다른 트랜잭션들이 재고를 3까지 줄여
커밋했어도 내 SELECT는 여전히 10이라 하고, 내 `SET stock = 9`는 최신 행을
9로 덮어쓴다 — 갱신 유실이다. 격리 수준을 올려서 풀 문제가 아니다
(SERIALIZABLE은 전역 비용, [격리 수준 문서](./transaction-isolation-levels.md)
4절). 고치는 법은 "판단의 근거가 되는 읽기는 현재 읽기로"다: ① 가장 싼
건 읽기 자체를 없애는 **원자적 UPDATE** — `UPDATE item SET stock = stock - 1
WHERE id = ? AND stock >= 1`, affected rows 0이면 재고 부족. ② 차감 전후로
검증 로직이 필요하면 `SELECT ... FOR UPDATE`로 **최신을 읽으면서 잠근다.**
③ 충돌이 드물면 버전 컬럼 기반 낙관적 락 + 재시도. 핵심 문장은 —
**"MVCC의 스냅샷은 보고용이고, 결정용 읽기는 잠금 읽기여야 한다."**

### "PostgreSQL의 MVCC와 InnoDB의 MVCC는 어떻게 다른가요?" (가산점 포인트)

**과거 버전을 어디에 두느냐**가 다르다. InnoDB는 테이블(클러스터드
인덱스)에 최신 버전 하나만 두고 과거 버전을 **undo 로그**에 사슬로 매단다.
PostgreSQL은 UPDATE를 "새 튜플 INSERT + 옛 튜플에 만료 표시"로 처리해
**과거 버전이 테이블 힙 안에 그대로 남는다**(각 튜플이 xmin/xmax로 생성·
만료 트랜잭션을 기록). 그래서 비용의 모양이 다르다 — InnoDB는 undo 팽창과
체인 순회, PostgreSQL은 **테이블·인덱스 자체의 비대화(bloat)** 와 그걸 치우는
VACUUM 부하, 그리고 인덱스 컬럼이 안 바뀌어도 새 튜플을 가리켜야 하는
인덱스 쓰기 증폭(HOT 최적화로 일부 완화). 공통점은 **긴 트랜잭션이 정리
작업(purge / VACUUM)을 막아 남들을 느리게 한다**는 것 — 어느 DB든 "트랜잭션은
짧게"의 근거는 같다. 이 비교를 할 수 있으면 MVCC를 특정 DB의 기능이 아니라
설계 선택으로 이해하고 있다는 신호가 된다.

## 한 줄 요약

**MVCC는 "읽는 쪽이 락 대신 자기 시점의 과거 버전을 보는" 격리(I) 구현으로,
InnoDB는 행의 숨은 컬럼 `DB_TRX_ID`·`DB_ROLL_PTR`, undo 로그로 이어진
버전 체인, 그리고 "어떤 트랜잭션까지 보이는가"를 찍은 Read View(활성 목록·
하한선·상한선·자기 ID)로 구현한다 — Read View를 문장마다 만들면 RC,
트랜잭션당 한 번이면 RR이고, 잠금 읽기는 스냅샷이 아닌 최신을 읽는다.
읽기-쓰기 비차단을 얻는 대가는 undo 공간·체인 순회·purge 부하이며, 이
청구서는 트랜잭션 길이에 비례해 커져 "긴 트랜잭션 → purge 정지 → history
list 증가 → 체인 길어짐 → 무관한 조회까지 행마다 체인 순회"라는 사슬로
남들에게 배달된다. 그래서 History list length를 지표로 걸고, 외부 호출을
트랜잭션 밖으로 빼는 규칙을 ArchUnit·timeout·leak detection으로 고정한다.**
