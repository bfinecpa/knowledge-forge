# DB 커넥션 수와 처리량 — 커넥션은 "처리 능력"이 아니라 "줄 서는 자리"이고, PostgreSQL에서는 그 자리 하나가 프로세스 하나다

> 핵심 관전 포인트: **커넥션을 늘리면 처리량은 어느 지점까지만 오르고,
> 그 뒤로는 평평해지다가 오히려 떨어진다. DB가 실제로 동시에 일할 수
> 있는 양은 커넥션 수가 아니라 DB 서버의 CPU 코어 수와 디스크 병렬성이
> 정하기 때문이다. PostgreSQL은 한 겹이 더 얹힌다 — **커넥션 하나가
> 스레드가 아니라 fork된 백엔드 프로세스 하나**라서 놀고 있는 커넥션도
> 메모리와 스냅샷 비용을 먹는다. 한계를 넘긴 커넥션은 일을 더 시키는 게
> 아니라 경합을 더 만든다 — ① CPU 컨텍스트 스위칭과 스냅샷 비용 ② 디스크
> I/O 큐 적체와 순차 I/O의 랜덤화 ③ 락 경합과 열린 트랜잭션이 멈춰 세우는
> VACUUM ④ 프로세스 메모리의 OS 캐시 잠식과 LWLock 경합, 이 네 사슬이
> 쿼리 하나하나를 느리게 만들어 총처리량을 깎는다. 그래서 "느리니까
> 커넥션을 늘리자"(`max_connections`를 올리자)는 처방은 병목 위치(앱
> 스레드 풀 → 커넥션 풀 → DB CPU → 디스크 I/O → 락 대기)를
> `pg_stat_activity`의 state·wait_event 분포로 확인한 뒤에만 유효하고, 풀
> 크기는 경험식으로 출발해 부하 테스트와 메트릭으로 고정하며, 앱
> 인스턴스가 많거나 유동적이면 **PgBouncer(transaction pooling)** 로 DB
> 프로세스 수를 앱 커넥션 수와 분리한다.**

---

## 0. 질문 + 의도

**질문**: "DB 커넥션 수와 처리량(throughput)의 관계 — 커넥션을 늘리면
항상 빨라지나요?"

**출제 의도**: "느리니까 커넥션을 늘리자"는 직관이 왜 역효과인지(경합 증가)를
아는지 확인한다. 더 깊게는 **병목의 위치를 확인하지 않은 처방이 얼마나
위험한지에 대한 감각**을 검사하는 질문이다 — 커넥션 풀 크기는 설정 한 줄이라
누구나 만질 수 있는데, 그 한 줄이 DB 전체를 무너뜨릴 수 있다는 걸 아는
사람과 모르는 사람의 운영 태도가 다르다. PostgreSQL에서는 커넥션이 곧
DB 서버의 **프로세스**라, 앱 풀 크기 × 인스턴스 수가 그대로 DB의 프로세스
수·메모리·`max_connections` 한계에 부딪힌다 — 그 한 줄의 파급이 한층 크다.

> 이 문서는 사전 학습용이다. 4장 기본 구간에서 반복된 공백 — 비용을
> "성능 저하", "부하 증가" 같은 뭉뚱그린 표현이 아니라 **이름 붙은 메커니즘
> 사슬**로 말하기, 특히 **랜덤 vs 순차 I/O** 축 — 을 이 질문에서 메우는
> 것이 1차 목표다. 2장에서 다룬 풀 크기 산정(Little's law)과 고갈 진단은
> 반복하지 않고 링크로 대신한다:
> [`../02-spring/25-thread-pool-connection-pool-sizing.md`](../02-spring/25-thread-pool-connection-pool-sizing.md),
> [`../02-spring/26-hikaricp-connection-pool-exhaustion.md`](../02-spring/26-hikaricp-connection-pool-exhaustion.md).
> 여기서는 **DB 서버 내부에서 무슨 일이 벌어지는가**에 집중한다 — 그리고
> PostgreSQL의 프로세스 모델이 그 "내부"를 어떻게 다르게 만드는지를 본다.

## 1. 큰 그림 — 처리량 곡선은 오르다가 꺾인다

커넥션 수(= DB에 동시에 들어와 있는 요청 수)를 가로축, 초당 처리 건수를
세로축으로 그리면 거의 모든 DB에서 같은 모양이 나온다.

```text
처리량(TPS)
  ▲
  │            ┌───────┐  ← ② 포화: 늘려도 그대로
  │         ┌──┘       └──┐
  │      ┌──┘             └───┐   ← ③ 붕괴: 늘릴수록 떨어진다
  │   ┌──┘                    └────
  │ ┌─┘  ← ① 선형 증가 구간
  │─┘
  └──────────────────────────────────▶ 동시 커넥션 수
        (코어 수 근처)
```

- **① 선형 구간**: 커넥션이 코어 수보다 적으면 CPU가 놀고 있다. 커넥션을
  늘리는 만큼 처리량이 는다. "커넥션을 늘리면 빨라진다"는 직관은 **이
  구간의 경험**이다.
- **② 포화 구간**: DB의 CPU와 디스크가 이미 쉬지 않고 일한다. 커넥션을
  더 넣어도 처리량은 그대로 — 새로 들어온 요청은 DB 안에서 **대기**할 뿐이다.
- **③ 붕괴 구간**: 대기하는 요청 자체가 비용을 만든다(2절의 네 사슬).
  쿼리 하나의 실행 시간이 늘어나고, 그 결과 총처리량이 **오히려 떨어진다.**

비유하면 **은행 창구(코어)는 8개인데 번호표(커넥션)를 500장 뿌린 상황**이다.
번호표를 더 뿌린다고 창구가 늘지 않는다. 오히려 대기 손님이 로비를
가득 채워 직원 이동을 방해하고(컨텍스트 스위칭), 서류 보관함 앞에서 서로
부딪히고(shared buffers·OS 캐시 경합), 같은 계좌를 처리하려고 서로
기다린다(락 경합). PostgreSQL에서는 번호표 한 장마다 **직원 한 명이 대기
손님 옆에 붙어 서 있는** 셈이라(커넥션 = 프로세스) 로비가 더 빨리 찬다.

핵심 문장: **커넥션은 "DB가 동시에 처리할 수 있는 능력"이 아니라 "DB
앞에 동시에 서 있을 수 있는 자리 수"다.** 능력의 상한은 DB 서버의
CPU 코어 수와 디스크 병렬성이 정한다.

이 모양을 수식으로 만든 것이 Gunther의 **USL(Universal Scalability Law)**
이다 — 공유 자원을 두고 줄 서는 **경합(contention)** 항이 ②의 포화를,
실행 단위끼리 상태를 맞추는 **일관성 유지(coherency)** 항이 ③의 붕괴를
만든다. "왜 평평해지는 데서 안 끝나고 떨어지기까지 하나요?"의 답이다
(가산점 포인트).

### PostgreSQL은 커넥션마다 프로세스를 하나씩 fork한다

이 곡선이 왜 생기는지, 그리고 왜 PostgreSQL에서 더 일찍 꺾이는지를
이해하려면 DB가 커넥션을 어떻게 다루는지 알아야 한다.

```text
클라이언트 TCP 접속
  → postmaster(부모 프로세스)가 fork()  →  백엔드 프로세스 1개 (이 커넥션 전담)
  → 인증(SCRAM 등) → 세션 파라미터 설정 → 첫 쿼리들이 카탈로그 캐시를 데운다
  ─────────────────────────────────────────────────────────────────────────
  커넥션 500개  =  DB 서버 안에 백엔드 프로세스 500개가 살아 있다
  그중 CPU 위에서 도는 건 코어 수만큼뿐, 나머지는 어딘가에서 대기 중
```

- **프로세스마다 전용 메모리가 붙는다.** 카탈로그 캐시(relcache/syscache),
  계획 캐시, 실행 중에는 `work_mem`(정렬·해시 **노드마다**, 기본 4MB). idle
  상태에서도 수 MB, 넓은 스키마를 두루 만진 백엔드는 수십 MB. 이 메모리는
  **공유되지 않는다** — 같은 테이블 정보를 500개 프로세스가 각자 들고 있다.
- **생성 비용이 크다.** fork + 인증 + 캐시 워밍. 스레드 생성과 자릿수가
  다르다 → 풀이 미리 만들어 **재사용**하는 것이 한층 중요하다(5-3의
  `minimum-idle = maximum-pool-size`).
- **상한 `max_connections`(기본 100)는 재시작 값이다.** 프로세스 배열·락
  테이블 같은 공유 메모리 크기가 이 값으로 시작 시 정해진다.
  `superuser_reserved_connections`(기본 3)는 관리자 몫.
- **idle 커넥션도 공짜가 아니다.** READ COMMITTED는 **문장마다** 스냅샷을
  찍고, 스냅샷은 "진행 중인 트랜잭션 목록"이라 **모든 백엔드를 훑어서**
  만든다(프로세스 배열). 백엔드가 1,000개면 스냅샷 하나의 비용이 그에
  비례한다 — 노는 커넥션이 일하는 커넥션의 문장마다 세금을 매기는 구조
  (PG 14에서 크게 완화, 0은 아님). **idle in transaction**이면 `backend_xmin`
  까지 쥐고 VACUUM을 막는다(사슬 C).

> MySQL 대조: MySQL은 커넥션당 **스레드** 하나이고 thread cache로
> 재사용한다. 프로세스보다 가볍고, InnoDB의 read view는 진행 중인
> 트랜잭션 목록만 복사하므로 idle 커넥션 수의 영향을 거의 받지 않는다.
> 그래서 커넥션 수천 개를 붙여 두는 운영이 흔하다. "커넥션 많아도
> 괜찮던데요"는 대개 MySQL 경험이다 — 그 감각을 PG에 그대로 옮기면
> 사고가 난다.

## 2. 역효과의 메커니즘 사슬 — "경합 증가"를 네 개의 이름으로 쪼개기

> 겨냥하는 공백: 지금까지 비용을 말할 때마다 "성능 저하", "메모리 부하",
> "부하 증가"에서 멈췄다. 면접관이 "커넥션을 늘리면 왜 역효과인가요?"라고
> 물을 때 "경합이 늘어서요"는 **답의 제목**일 뿐이다. 아래 네 사슬을
> 각각 **이름 → 원인 → 결과**의 화살표로 말할 수 있어야 한다.

```text
커넥션 수 ↑ (= DB 안의 백엔드 프로세스 ↑)
   │
   ├─ A. CPU: 실행 가능 프로세스 > 코어 수 → 컨텍스트 스위칭 ↑, 캐시 오염
   │         + 문장마다 찍는 스냅샷 비용이 백엔드 수에 비례해 ↑
   ├─ B. 디스크: I/O 큐 적체 + 순차 접근이 랜덤으로 뒤섞임 → IOPS 정체·하락
   │         + 커밋마다 WAL fsync — 커넥션을 늘려도 fsync 처리량은 안 는다
   ├─ C. 락: 동시 트랜잭션 ↑ → 같은 행 충돌 확률 ↑ → 대기 → 트랜잭션 길어짐 → 더 많은 대기
   │         + 열린 트랜잭션이 backend_xmin을 쥐어 VACUUM 정지 → 죽은 튜플 ↑ → B·D로
   └─ D. 메모리: 프로세스 메모리 ↑ → OS 페이지 캐시 몫 ↓ + 워킹셋 합 > 캐시 → 히트율 ↓ → B로
                 + LWLock(BufferMapping·LockManager·ProcArrayLock·WALWrite) 경합 → 스핀으로 CPU 낭비
   │
   ▼
쿼리 1건의 실행 시간 ↑  →  초당 처리 건수 ↓  +  p99 응답시간 ↑
```

### 사슬 A — CPU 컨텍스트 스위칭, 그리고 스냅샷

- 코어가 8개인데 실행하려는 프로세스가 200개면, OS는 수 ms 단위로 코어를
  돌려가며 태운다(시분할). 프로세스를 바꿔 태울 때마다 **레지스터·스택
  상태를 저장/복원**하고, 방금 전 프로세스가 데워둔 **CPU 캐시(L1/L2)가
  다른 프로세스의 데이터로 덮인다**(캐시 오염). 프로세스 전환은 주소
  공간까지 바뀌므로 스레드 전환보다 무겁다.
- 이 비용은 "쿼리 실행"이 아닌 "쿼리 사이를 오가는" 데 쓰이는 CPU다. 즉
  같은 CPU 100%인데 **실제 쿼리 처리에 쓰인 몫이 줄어든다.**
- **PG만의 추가 항 — 스냅샷.** 문장마다 프로세스 배열을 훑고, 트랜잭션이
  끝날 때마다 그 배열을 갱신한다. 이를 지키는 `ProcArrayLock`(LWLock)에서
  백엔드가 많을수록 문장들이 줄을 선다 — 커넥션 수백 개에서 처리량이
  꺾이는 PG 특유의 현상(PG 14에서 완화).
- **병렬 쿼리 워커도 프로세스다.** `max_parallel_workers_per_gather`(기본
  2)가 켜진 쿼리 하나는 CPU 경쟁자 셋이다. 커넥션 200개가 각각 병렬
  스캔을 돌리면 코어 8개를 두고 600개가 다툰다.
- 시그니처: `vmstat`의 `cs`(context switch/초)가 폭증하고 `r`(run queue)이
  코어 수를 크게 넘는데, `pg_stat_activity`에서 `state = 'active'`이면서
  `wait_event`가 NULL인(= CPU 위에서 실행 중인) 백엔드 수가 코어 수의
  몇 배인데도 처리량은 안 오른다. `wait_event = 'ProcArrayLock'`이
  보이면 스냅샷 경합이다.

I/O 대기 중인 프로세스는 CPU를 안 쓰므로 컨텍스트 스위칭 비용이 없다고
생각하기 쉬운데, 커넥션이 많으면 **깨어나는 프로세스도 그만큼 많다** —
I/O가 끝날 때마다 깨어나 run queue에 줄을 서고, 그 줄이 코어 수보다 길면
다시 시분할 비용이 든다.

### 사슬 B — 디스크 I/O 큐, 순차 I/O의 랜덤화, 그리고 WAL fsync

> 겨냥하는 공백: **랜덤 vs 순차 I/O 비용 모델** — 기본 구간에서 5회 연속
> 비어 있던 축이다. 힙 페치(Q2)·페이지 분할(Q3)·WAL(Q5)이 전부 이 축
> 위에 있었고, 여기서는 "왜 디스크가 병목일 때 동시성을 올리는 게
> 무의미하거나 해로운가"로 같은 축이 다시 등장한다.

먼저 비용 모델 자체를 한 번 더 고정한다.

- **순차 I/O**: 디스크의 연속된 블록을 쭉 읽는다. HDD라면 헤드를 한 번
  놓고 플래터가 도는 대로 읽기만 하면 된다. 매우 싸다.
- **랜덤 I/O**: 매 블록마다 다른 위치로 헤드를 옮긴다(seek, 밀리초 단위).
  HDD에서 순차와 랜덤의 처리량 차이는 **자릿수가 다르다.** SSD는 seek가
  없어 격차가 크게 줄지만, 여전히 "한 번에 크게 읽기"가 "작게 여러 번"보다
  싸고, 컨트롤러가 동시에 처리할 수 있는 요청 수(큐 깊이)에 상한이 있다.
  (플래너의 `random_page_cost` 4.0 vs `seq_page_cost` 1.0이 이 격차다.)

이제 커넥션을 늘렸을 때 디스크에서 벌어지는 일 세 가지:

**(1) 큐만 길어진다 — IOPS는 고정**

디스크가 초당 처리할 수 있는 I/O 수(IOPS)는 장치가 정한 상수다. 이미
`iostat`의 `%util`이 100%에 붙어 있다면, 커넥션을 늘려 I/O 요청자를 늘려도
**초당 처리되는 I/O 수는 1도 안 는다.** 요청은 디스크 큐에 쌓이고
`await`(요청당 평균 대기+처리 시간)만 길어진다. 각 쿼리는 그만큼 느려지고,
느려진 쿼리는 커넥션을 더 오래 물고, 앱 풀도 따라서 마른다.

**(2) 순차가 랜덤으로 뒤섞인다 — IOPS가 오히려 떨어진다**

이게 더 중요한 포인트다. 커넥션 하나가 `Seq Scan`으로 큰 테이블을 읽거나
`Bitmap Heap Scan`이 TID를 정렬해 힙을 순서대로 찍을 때, **그 쿼리 하나만
보면 접근은 순차적**이다. 그런데 이런 쿼리 50개가 동시에 돌면, 디스크가
받는 요청 스트림은 50개 쿼리의 요청이 **번갈아 섞인 것**이 된다.

```text
쿼리 1 혼자:   블록 100, 101, 102, 103, 104 ...        ← 순차 (헤드 이동 거의 없음)
쿼리 2 혼자:   블록 9000, 9001, 9002, 9003 ...          ← 순차

둘이 동시에:   100, 9000, 101, 9001, 102, 9002 ...      ← 디스크 입장에선 랜덤
               (매 요청마다 헤드가 100번대 ↔ 9000번대를 왕복)
```

각 쿼리는 순차 스캔을 하고 있다고 믿지만, 디스크는 매 요청마다 seek를
한다. 동시성이 올라갈수록 **디스크가 실제로 뽑아내는 처리량이 순차 수준에서
랜덤 수준으로 떨어진다.** 그래서 디스크가 병목인 시스템에서는 동시 커넥션을
늘리는 것이 "무의미"를 넘어 "해롭다". 반대로 커넥션을 줄이면 각 스캔이
순차성을 회복해 **총 디스크 처리량이 오른다** — 6절 사례의 물리적 근거
중 하나다. (OS와 디스크 컨트롤러가 요청을 재정렬해 완화해 주긴 하지만,
요청자 수가 많을수록 재정렬로 살릴 수 있는 순차성 자체가 줄어든다.)

SSD·클라우드 블록 스토리지에서는 seek 비용이 없으니 (2)는 약해지고 (1)이
주로 남는다. 다만 클라우드 볼륨은 **IOPS 자체가 상품 스펙으로 상한이
걸려 있어** (1)이 더 일찍, 더 딱딱하게 온다.

**(3) 쓰기라면 상한은 WAL fsync다**

커밋은 WAL을 fsync한 뒤에야 응답한다. 동시 커밋이 많으면 한 번의 flush에
여러 트랜잭션의 WAL을 묶어 쓰지만(그룹 커밋), **fsync 처리량 자체는
커넥션을 늘린다고 늘지 않는다.** 쓰기 워크로드의 TPS 상한이 코어 수가
아니라 WAL 장치의 fsync 속도인 이유다. 시그니처는 `wait_event`의
`WALSync`/`WALWrite`(IO)와 `LWLock:WALWrite`.

함정 하나 — **PG의 "read"는 디스크 읽기가 아닐 수 있다.**
`pg_stat_database.blks_read`나 `EXPLAIN (BUFFERS)`의 `shared read`는
`shared_buffers` 미스일 뿐, OS 페이지 캐시에서 왔는지 디스크에서 왔는지는
구분하지 않는다. `track_io_timing = on`의 `blk_read_time`(읽기당
마이크로초면 OS 캐시, 밀리초면 디스크)이나 `iostat`으로 확인하고,
`pg_stat_io`(PG 16+)면 백엔드 종류별로 분해된다.

### 사슬 C — 락 경합, 그리고 열린 트랜잭션이 멈춰 세우는 VACUUM

- 동시에 진행 중인 트랜잭션이 많아지면, 같은 행(또는 같은 유니크 키)을
  잡으려는 **충돌 확률이 조합적으로** 는다(트랜잭션 n개면 쌍은 n(n-1)/2개).
  PG의 행 락은 튜플 헤더 `xmax`에 기록되고, 충돌한 쪽은 그 트랜잭션이
  끝나기를 기다린다(`wait_event = transactionid`).
- 충돌한 트랜잭션은 락을 기다리고, **기다리는 동안 자기 커넥션(프로세스)·
  자기가 이미 잡은 락·자기 스냅샷(`backend_xmin`)을 전부 쥐고 있다.** 즉
  트랜잭션이 길어진다.
- 트랜잭션이 길어지면 락 점유 시간이 늘고, 그만큼 뒤에 오는 트랜잭션이
  더 오래 기다린다 — **대기 → 장기화 → 더 많은 대기**의 되먹임.
- 핫 로우(재고 1건, 카운터 1행)가 있다면 처리량은 결국 **그 행을 잠그고
  푸는 속도로 직렬화**된다. 커넥션 500개든 5개든 그 행은 한 번에 하나씩만
  갱신되므로, 500개는 처리량을 못 올리고 대기열과 데드락 검사 비용
  (`deadlock_timeout` 1초를 넘긴 대기마다 대기 그래프 검사)만 만든다. PG는
  갱신마다 새 튜플 버전을 만들므로 핫 로우는 죽은 튜플까지 쌓는다 —
  [`23-high-frequency-counter-hot-row.md`](23-high-frequency-counter-hot-row.md).
- **PG 고유의 되먹임 — VACUUM.** 대기 중이거나 `idle in transaction`인
  트랜잭션은 `backend_xmin`을 잡고 있어, 그 시점 이후 생긴 죽은 튜플을
  VACUUM이 치우지 못한다. 죽은 튜플이 쌓이면(bloat) 같은 결과를 내려고
  읽어야 하는 페이지가 늘고, `Index Only Scan`은 힙 페치로 퇴화하며,
  사슬 B·D로 되돌아간다. 커넥션이 많을수록 "누군가 하나는 오래 열어 두고
  있을" 확률이 커진다는 것이 문제다 —
  [`16-long-transaction-harm-and-shortening.md`](16-long-transaction-harm-and-shortening.md),
  [`11-mvcc-postgresql.md`](11-mvcc-postgresql.md).
- 시그니처: `pg_stat_activity`에서 `wait_event_type = 'Lock'`(`transactionid`,
  `tuple`) 다수, `pg_locks`의 `granted = false`, `pg_blocking_pids(pid)`로
  누가 막는지, `log_lock_waits = on`이면 `deadlock_timeout`을 넘긴 대기가
  서버 로그에, `state = 'idle in transaction'`이 `now() - xact_start`로
  오래된 것들.

여기서 2장의 고갈 문서와 연결된다: 락 대기로 트랜잭션이 길어지면
커넥션 점유 시간이 늘고, 앱 풀이 마르고, 톰캣 스레드까지 마른다. 락
경합은 **DB 내부 현상이지만 장애는 앱 전체에서 터진다.**

> MySQL 대조: InnoDB는 갭 락·넥스트 키 락이 있어 "같은 행"뿐 아니라
> "같은 범위"에서도 충돌하므로, 동시성이 오를 때 락 경합이 더 가파르게
> 늘 수 있다. 반면 옛 버전을 언두 로그에 두므로 롱 트랜잭션의 대가가
> "VACUUM 정지·bloat"가 아니라 "언두 증가·history list length"로 나타난다.

### 사슬 D — 메모리 배분과 내부 자원(LWLock) 경합

PG의 메모리는 세 층이고, 커넥션 수가 건드리는 층이 정해져 있다.

```text
[ shared_buffers ]        ← 시작 시 고정(기본 128MB). 커넥션이 늘어도 줄지 않는다
[ OS 페이지 캐시 ]        ← 나머지 RAM. 이중 캐시의 2층. 플래너는 effective_cache_size로 크기를 짐작
[ 백엔드 프로세스 × N ]   ← 각각 수 MB + 카탈로그 캐시 + (실행 중) work_mem × 노드 수 × (1 + 병렬 워커)
                            + temp_buffers, VACUUM·인덱스 생성 시 maintenance_work_mem(기본 64MB)
```

- **메모리 배분**: 커넥션 × 프로세스 메모리가 RAM에서 빠져나가면
  **`shared_buffers`가 아니라 OS 페이지 캐시가 얇아진다.** 2층 캐시가
  줄면 `shared_buffers` 미스가 곧 디스크 읽기가 된다 → 사슬 B. `work_mem`을
  전역으로 올리면 안 되는 이유가 여기서 나온다 — 노드당 값이라
  `max_connections × 노드 수 × 병렬 워커`로 부풀 수 있다.
- **넘치면 전체 장애다.** swap이 시작되면 성능이 전면 붕괴하고, Linux
  OOM killer가 백엔드 **하나**를 죽이면 postmaster는 공유 메모리 오염
  가능성 때문에 **모든 백엔드를 끊고 크래시 복구를 돈다.** 커넥션 하나의
  메모리 사고가 DB 전체 재시작이 되는 경로다(PG 문서가
  `vm.overcommit_memory = 2`를 권하는 이유).
- **워킹셋 초과**: 동시에 도는 쿼리가 많아지면 그들이 만지는 페이지의
  합(워킹셋)이 커진다. 합이 `shared_buffers` + OS 캐시를 넘는 순간 **캐시
  히트율이 떨어지고 디스크 읽기가 늘어** 사슬 B로 되돌아간다. 커넥션
  50개일 땐 메모리에서 다 처리되던 쿼리들이 200개가 되면 디스크를 때리기
  시작하는 현상이 이것이다.
- **내부 래치 = LWLock.** 버퍼 해시 테이블, 락 테이블, 프로세스 배열,
  WAL 버퍼, 트랜잭션 ID 발급 같은 내부 자료구조는 짧은 락(LWLock·스핀락)
  으로 보호된다. `pg_stat_activity`에 `wait_event_type = 'LWLock'`으로
  이름까지 찍힌다 — `BufferMapping`(버퍼 찾기), `LockManager`(백엔드당
  fast-path 슬롯을 넘긴 락이 공유 락 테이블로 갈 때), `ProcArrayLock`
  (스냅샷·트랜잭션 종료), `WALInsert`/`WALWrite`, `XidGen`. 짧은 락이지만
  대기자가 많으면 줄이 생기고, 대기 방식이 스핀이라 **CPU를 쓰면서
  기다리는** 낭비가 는다.
- **PG에는 DB 안에서 동시 실행 수를 제한하는 손잡이가 없다**(가산점
  포인트). 들어온 커넥션은 전부 프로세스가 되어 전부 CPU를 다툰다. 그래서
  동시성 상한은 **반드시 DB 밖에서**(앱 풀 크기, PgBouncer의
  `default_pool_size`) 걸어야 한다 — PgBouncer가 PG 생태계에서 사실상
  필수가 된 이유 중 하나다.

> MySQL 대조: 버퍼 풀이 단일 캐시라(`innodb_buffer_pool_size`를 RAM의
> 대부분에 주고 대개 O_DIRECT로 OS 캐시를 우회) "세션 메모리가 버퍼 풀
> 몫을 잠식"이 직접 계산이 되고, `innodb_thread_concurrency`로 DB 스스로
> 내부 동시 실행 상한을 걸 수 있다. PG에는 그 손잡이가 없다.

### 네 사슬을 한 문장으로

"커넥션을 늘리면 DB 안의 백엔드 프로세스가 늘고, 그것이 **CPU에선
컨텍스트 스위칭과 스냅샷 비용, 디스크에선 큐 적체와 순차 I/O의 랜덤화,
트랜잭션 사이에선 락 경합과 VACUUM 정지, 메모리에선 OS 캐시 잠식과
LWLock 경합**을 일으켜 쿼리 하나하나가 느려지고 총처리량이 떨어진다."

이 한 문장을 말한 뒤 면접관이 어느 사슬을 파고들어도 한 단계씩 더
내려갈 수 있으면 이 질문은 통과다.

## 3. 트레이드오프 양면 — 커넥션을 늘리는 것이 맞는 경우와 틀린 경우

> 겨냥하는 공백: 트레이드오프를 **한 호흡에 양면으로** 조립하기. "늘리면
> 안 된다"로 끝내면 반쪽이다. 늘리는 것이 정답인 조건과 오답인 조건을
> 같은 문장 안에서 대비시킨다.

| 상황 | 커넥션 늘리기의 효과 | 판단 |
|---|---|---|
| DB CPU 여유(예: 40%), 디스크 여유, `Lock` 대기 없음, 앱 `pending` 발생 | 처리량 선형 증가 (곡선 ① 구간) | **늘리는 게 맞다** |
| DB CPU 포화(`active` 백엔드 ≫ 코어), 앱 `pending` 발생 | 처리량 그대로, DB 응답시간 ↑ (② 구간) | 늘려도 소용없음 — 점유 시간 단축·쿼리 튜닝 |
| 디스크 `%util` 100%, `await` 상승, `wait_event_type = 'IO'` 다수 | IOPS 정체 + 순차 I/O 랜덤화로 처리량 ↓ (③ 구간) | **줄이는 게 맞다** — 인덱스·캐시·I/O 줄이기 |
| `wait_event_type = 'Lock'` 다수, `idle in transaction` 다수 | 충돌 확률 ↑, 트랜잭션 장기화, VACUUM 정지 | 줄이거나, 락 범위·트랜잭션 길이 축소 |
| DB 여유 있는데 앱 `pending`도 없음 | 아무 효과 없음 | 병목이 다른 곳(앱 CPU, 외부 API) |

표를 양면 문장으로 조립하면:

> "커넥션을 늘리면 **DB가 놀고 있을 때는** 놀던 코어를 채워 처리량이
> 오르지만, **DB가 이미 포화일 때는** 대기 줄을 DB 내부로 옮겨 컨텍스트
> 스위칭·I/O 랜덤화·락 경합만 키워 처리량이 떨어진다. 그래서 늘리기 전에
> DB 쪽 지표로 어느 구간에 있는지부터 확인한다."

덧붙일 양면 하나 더 — **대기의 위치**. 커넥션을 줄이면 앱 쪽 풀에서
대기(`pending`)가 생긴다. 이건 나빠진 게 아니라 **대기를 DB 내부(비싼 대기:
프로세스·CPU·락·`backend_xmin`을 쥔 채 기다림)에서 앱 풀(싼 대기: 스레드가
park만 하고 DB 자원은 전혀 안 씀)로 옮긴 것**이다. 총 대기 시간이 같아도
DB는 최적 동시성으로 돌아 처리량이 오르고, 그 덕에 대기 총량도 줄어드는
경우가 대부분이다. 다만 앱 쪽 대기가 톰캣 스레드를 묶어 스레드 풀 고갈로
번지지 않도록 `connection-timeout`을 짧게 두고 빨리 실패시키는 안전장치가
함께 필요하다(고갈 문서 5절).

### `max_connections`를 올리는 것은 처방이 아니다

`FATAL: sorry, too many clients already`(SQLSTATE 53300)가 뜨면 가장 먼저
손이 가는 곳이 `max_connections`다. 올리면 에러는 사라진다 — 그리고 문제는
커진다.

- **자리를 늘린 것이지 창구를 늘린 게 아니다.** 상한은 코어와 디스크가
  정한다. 자리가 늘면 대기자가 DB 안(비싼 대기)에 더 많이 들어올 뿐이다.
- **프로세스 메모리가 그만큼 는다.** 500 → 2,000이면 OS 페이지 캐시가
  그만큼 얇아지고, 피크에 OOM killer가 백엔드를 죽이면 전체 재시작이다
  (사슬 D).
- **O(N) 자료구조의 N을 키운다.** 스냅샷 계산, 락 테이블, 프로세스 배열
  갱신 — 연결만 돼 있어도 내는 비용이 커진다(사슬 A).
- **재시작이 필요하다.** 장애 중에 바로 바꿀 수 있는 값도 아니다.
- 에러의 진짜 뜻은 "**앱 풀 합계 설계가 DB 한계를 넘었다**"다. 처방은
  ① 인스턴스 수 × 풀 크기를 다시 계산하고(5-1) ② 그 곱을 앱 토폴로지와
  분리하려면 PgBouncer를 둔다(5-4). `max_connections`는 "풀 합계 +
  autovacuum 워커(기본 3) + 복제·관리·배치 접속 + 예약분"이 들어갈 만큼만
  잡는 **상한선**이지 튜닝 손잡이가 아니다.

## 4. 병목 위치 확인 순서 — 처방 전 진단 체크리스트

> 겨냥하는 공백: **목록 인출**. 장애 중에 "어디가 병목인지 어떻게 확인하나요?"
> 를 받으면 아래 다섯 단계를 **순서대로, 각 단계의 확인 지표와 함께**
> 꺼낼 수 있어야 한다. 순서에 의미가 있다 — 요청이 흐르는 방향(앱 → DB →
> 디스크)을 따라가며, 앞 단계가 병목이 아님을 확인한 뒤 다음으로 내려간다.

```text
요청 → [1] 앱 스레드 풀 → [2] 커넥션 풀 (→ PgBouncer) → [3] DB CPU → [4] 디스크 I/O → [5] 락 대기
```

| 단계 | 확인 지표 | 병목일 때의 시그니처 | 처방 방향 |
|---|---|---|---|
| [1] 앱 스레드 풀 | `tomcat.threads.busy` vs max, 앱 CPU | busy가 max에 붙고 DB는 한가 | 스레드 수 재산정, 앱 CPU 병목 확인 |
| [2] 커넥션 풀 | `hikaricp.connections.active/pending`, `acquire` 시간; PgBouncer면 `SHOW POOLS`의 `cl_waiting`·`maxwait` | active = max, pending > 0, acquire 시간 ↑ | **여기서 멈추지 말 것** — [3]~[5]로 내려가 "왜 커넥션이 안 돌아오는지" 확인 |
| [3] DB CPU | DB 호스트 CPU, `pg_stat_activity`의 `active` 수(wait_event NULL), `vmstat cs/r` | CPU 90%↑, active ≫ 코어, cs 폭증, `LWLock:ProcArrayLock` | 커넥션 줄이기 + 쿼리 CPU 비용 튜닝 |
| [4] 디스크 I/O | `iostat %util/await/r/s`, `pg_stat_database.blks_hit/blks_read`, `blk_read_time`, `wait_event_type = 'IO'` | %util 100%, await ↑, 히트율 ↓, `DataFileRead` 대기 다수 | 커넥션 줄이기 + 인덱스·커버링·캐시 확대 |
| [5] 락 대기 | `wait_event_type = 'Lock'`, `pg_locks`, `pg_blocking_pids()`, `idle in transaction` 수와 나이 | 락 대기 수·시간 ↑, `transactionid` 대기 다수, 오래된 idle in transaction | 트랜잭션 짧게, 락 범위 축소, 핫 로우 분산, `idle_in_transaction_session_timeout` |

각 단계의 읽는 법:

- **[1] → [2]**: 앱 스레드가 놀고 있는데 커넥션 pending이 있다면 문제는
  DB 쪽이다. 반대로 스레드가 꽉 찼는데 커넥션은 여유면 DB와 무관한
  병목(외부 API, 앱 CPU)이다.
- **[2]에서 멈추는 것이 가장 흔한 실수.** `pending`이 보이면 "커넥션이
  부족하다"로 읽고 늘리고 싶어진다. 하지만 pending은 **커넥션이 안 돌아오고
  있다**는 뜻이지 **커넥션 개수가 모자란다**는 뜻이 아니다. 안 돌아오는
  이유가 [3]~[5] 중 어디인지 확인하기 전에는 처방을 내리지 않는다.
  PgBouncer의 `cl_waiting`도 같은 신호가 한 단계 뒤에서 보이는 것이다.
- **[3] vs [4] 구분**: DB CPU가 높고 디스크가 한가하면 CPU 바운드(정렬·조인·
  함수 연산이 무거운 쿼리, 또는 스냅샷·LWLock 경합), CPU는 낮은데
  `iowait`·`%util`이 높으면 I/O 바운드(캐시 미스, `Seq Scan`). 처방이 다르다
  — 전자는 쿼리 연산량, 후자는 읽는 페이지 수를 줄인다. **`wait_event`
  분포 하나로 둘이 갈린다** — NULL이 많으면 CPU, `IO`가 많으면 디스크.
- **[5]는 CPU도 디스크도 한가한데 느릴 때** 의심한다. 자원은 놀고 있는데
  트랜잭션들이 서로를 기다리는 상태다. 이때 커넥션을 늘리면 대기자만 는다.
  PG에서는 여기에 **`idle in transaction`을 반드시 같이 본다** — 락을 쥔
  채 앱이 외부 API를 기다리는 커넥션이 대기열의 머리인 경우가 많다.

```sql
-- [3]~[5] PostgreSQL: 백엔드가 지금 무엇을 하고 있는지 한 번에 — 이 쿼리 하나가 출발점
SELECT state, wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY 1, 2, 3
ORDER BY 4 DESC;
-- 읽는 법:
--   active + wait_event_type NULL           → CPU 위에서 실행 중. 코어 수를 크게 넘으면 [3]
--   active + IO (DataFileRead, WALSync…)    → 디스크 대기 [4]
--   active + Lock (transactionid, tuple)    → 락 대기 [5]
--   active + LWLock (BufferMapping, LockManager, ProcArrayLock, WALWrite) → 내부 래치 경합 (사슬 D)
--   idle                                    → 풀이 쥐고만 있는 커넥션. 프로세스·메모리·스냅샷 비용만 낸다
--   idle in transaction + Client:ClientRead → 앱이 트랜잭션을 열어 두고 딴 일 중. 락·backend_xmin을 쥐고 있다
--   ※ active 합계 = "실행 중인 수", 전체 합계 = "붙어 있는 수". 둘은 다르다 — 이 차이가 이 문서 전체다

-- [4] 캐시 히트율 — 단, "read"는 shared_buffers 미스일 뿐 OS 캐시에서 왔을 수 있다
SELECT datname,
       round(100.0 * blks_hit / nullif(blks_hit + blks_read, 0), 2) AS hit_pct,
       blk_read_time            -- track_io_timing = on 일 때만 채워진다. 이게 커야 진짜 디스크
FROM pg_stat_database
WHERE datname = current_database();

-- [5] 지금 누가 누구를 막고 있는가 + 오래 열린 트랜잭션
SELECT pid, state, now() - xact_start AS tx_age, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by, left(query, 60) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0
   OR state = 'idle in transaction'
ORDER BY tx_age DESC;
```

> MySQL 대조: 같은 진단이 `SHOW GLOBAL STATUS LIKE 'Threads_running'`(실행
> 중 스레드 — `Threads_connected`와 다르다), `Innodb_buffer_pool_read%`(버퍼
> 풀 히트율), `sys.innodb_lock_waits`(락 대기 쌍)로 이뤄진다. `SHOW
> PROCESSLIST`의 상태 문자열이 PG의 `wait_event` 자리다.

이 체크리스트의 존재 이유는 "커넥션을 늘릴까 줄일까"가 아니다. **어느
자원이 포화인지 알기 전에는 어떤 처방도 도박**이라는 것 — 출제 의도가
말하는 "병목 위치를 확인하지 않은 처방의 위험"이 정확히 이것이다.

## 5. 풀 크기를 고정하는 방법 — 경험식으로 출발, 측정으로 확정, 알람으로 유지, 풀러로 분리

> 겨냥하는 공백: **안전망 고정**. 풀 크기를 "감으로 50" 또는 "공식 대로 17"로
> 정하고 끝내는 게 아니라, 부하 테스트로 곡선의 꺾이는 지점을 찾고 메트릭
> 알람으로 이탈을 감지하는 체계까지 말한다. PG에서는 여기에 **앱 커넥션
> 수와 DB 프로세스 수를 분리하는 층(PgBouncer)**이 하나 더 붙는다.

### 5-1. 경험식 — HikariCP 위키의 출발점

HikariCP 위키(About Pool Sizing)가 제시하는 식:

```text
connections = (DB 서버 코어 수 × 2) + 유효 스핀들 수
```

- 이 식은 **경험식(rule of thumb)이지 정리(theorem)가 아니다.** 위키
  스스로도 "출발점"이라고 못 박는다.
- 왜 이런 형태인가 — 항이 곧 1~2절의 내용이다:
  - **코어 수**: 동시에 CPU 위에서 돌 수 있는 쿼리의 상한(사슬 A).
  - **× 2**: 한 백엔드가 디스크 I/O를 기다리는 동안 다른 백엔드가 CPU를
    쓰게 하려는 겹치기(overlap) 여유. I/O 대기 비율이 높을수록 이 계수는
    더 커도 되고, 데이터가 전부 메모리에 있으면 1에 가까워도 된다.
  - **유효 스핀들 수**: 독립적으로 I/O를 동시에 처리할 수 있는 디스크 수
    (사슬 B의 디스크 병렬성). 스핀들 수만큼은 동시에 I/O를 걸어도 서로
    큐를 만들지 않는다는 뜻이다.
- 한계: SSD·NVMe·클라우드 볼륨에는 "스핀들"이라는 물리 단위가 없다. 큐
  깊이·IOPS 상한을 대신 넣어야 하는데 정확한 환산은 없다. 따라서 이 식은
  **자릿수를 잡는 용도**로만 쓰고, 최종 숫자는 반드시 측정으로 정한다.
- 앱 인스턴스가 N대면 DB에는 **N × 풀 크기**개의 백엔드 프로세스가 뜬다.
  공식이 주는 숫자는 **DB 전체 기준**이므로 인스턴스 수로 나눠야 한다.
  오토스케일링으로 앱이 10대에서 30대가 되면 DB 프로세스도 3배 — 계산에
  넣지 않으면 피크에 붕괴 구간으로 밀려나고 `max_connections`를 넘겨 53300
  에러가 섞여 나온다. **이 곱셈을 앱 토폴로지에서 떼어 내는 것이 5-4다.**

### 5-2. 부하 테스트 — 곡선의 꺾이는 지점을 직접 그린다

```text
절차
1. 실제와 비슷한 쿼리 믹스·데이터 크기로 부하 도구(k6, Gatling 등) 준비
2. 풀 크기를 단계적으로 바꿔가며(예: 5 → 10 → 20 → 40 → 80) 같은 부하를 건다
3. 각 단계에서 기록: TPS, p50/p99 응답시간, DB CPU, iostat %util,
   pg_stat_activity의 state·wait_event 분포(active 수, Lock·IO·LWLock 대기 수)
4. TPS가 더 이상 오르지 않는 지점(포화)과 p99가 급격히 나빠지는 지점(붕괴)을 찾는다
5. 포화 지점보다 약간 아래를 채택 — 여유는 커넥션 수가 아니라 응답시간에 둔다
```

- 측정 없이 "일단 크게 잡아두면 안전하겠지"가 가장 위험하다. 큰 풀은
  평소엔 조용하다가 **트래픽 피크에 DB를 붕괴 구간으로 밀어 넣는** 시한폭탄이다.
- 반대로 너무 작으면 앱 pending이 상시 발생한다. 이때는 풀을 키우기 전에
  **커넥션 점유 시간**(트랜잭션 안의 외부 호출, 느린 쿼리)부터 줄인다 —
  같은 TPS를 더 작은 풀로 감당하는 게 언제나 DB에 이롭다.

### 5-3. 메트릭과 알람 — 결정을 코드로 고정한다

```yaml
# ❌ before — "느리다"는 보고에 감으로 늘린 설정
spring:
  datasource:
    url: jdbc:postgresql://db:5432/app
    hikari:
      maximum-pool-size: 200        # 근거 없음. 인스턴스 10대면 PG 백엔드 프로세스 2,000개
      connection-timeout: 30000     # 30초 대기 → 톰캣 스레드까지 30초씩 묶임
```

```yaml
# ✅ after — 측정으로 정한 크기 + 빨리 실패 + 관측 가능
spring:
  datasource:
    url: jdbc:postgresql://db:5432/app   # PgBouncer를 두면 6432 포트로 (5-4)
    hikari:
      maximum-pool-size: 12         # 부하 테스트에서 TPS 포화 지점(DB 8코어, 인스턴스 10대 → DB 전체 120)
      minimum-idle: 12              # 고정 크기 — PG는 커넥션 생성이 fork라 피크에 만들면 그 자체가 부하
      connection-timeout: 3000      # 3초 안에 못 받으면 실패 — 대기 줄이 스레드 풀로 전이되는 걸 차단
      leak-detection-threshold: 30000
management:
  metrics:
    enable:
      hikaricp: true                # hikaricp.connections.{active,idle,pending,acquire,usage,timeout}
```

DB 쪽에도 같은 취지의 안전장치를 건다 — 앱이 놓친 점유를 DB가 끊어 준다.

```sql
-- 롤 단위 기본값으로 박아 둔다 (세션 SET은 PgBouncer transaction 모드에서 못 믿는다 — 5-4)
ALTER ROLE app_rw SET idle_in_transaction_session_timeout = '30s';  -- 트랜잭션 열고 노는 커넥션 강제 종료
ALTER ROLE app_rw SET statement_timeout = '5s';                     -- 폭주 쿼리 상한 (배치 롤은 따로)
ALTER ROLE app_rw SET lock_timeout = '3s';                          -- 락 대기 상한
-- idle_session_timeout(PG 14+)은 idle 자체를 끊는 값 — 앱 풀이 관리하는 커넥션에는 보통 안 건다
```

알람으로 걸어둘 것(임계값은 부하 테스트에서 본 정상 범위 기준):

- `hikaricp.connections.pending` — 0보다 큰 상태가 지속되면 "커넥션이 안
  돌아온다". 4절 체크리스트의 시작 신호.
- `hikaricp.connections.acquire`(획득 대기 시간 p99) — 커넥션을 받기까지
  기다린 시간. 응답시간 악화의 선행 지표.
- `hikaricp.connections.usage`(점유 시간 p99) — 커넥션을 물고 있는 시간.
  이게 늘면 풀 크기가 아니라 **점유 시간이 문제**다.
- `hikaricp.connections.timeout` — 획득 실패 건수. 0이 아니면 이미 사용자
  영향.
- DB 쪽: `pg_stat_activity`의 `active` 수가 코어 수의 배수를 넘는 지속
  시간, `idle in transaction` 수와 최대 나이, `Lock`·`LWLock` 대기 수,
  `pg_stat_database.blks_read` 증가율, `numbackends`가 `max_connections`에
  붙는 비율. **앱 pending과 DB 지표를 같은 대시보드에 나란히** 두어야
  "pending이 뜨는데 DB CPU는 포화인가 여유인가"를 한눈에 읽고 4절의
  처방 방향을 즉시 고를 수 있다.

풀 크기 결정 근거(테스트 날짜·부하 조건·채택 이유)는 설정 파일 주석이나
운영 위키에 남긴다. 반년 뒤 다른 사람이 "느리니까 늘리자"를 반복하지
않게 하는 것까지가 안전망이다.

### 5-4. PgBouncer — 앱 커넥션 수와 DB 프로세스 수를 분리한다

앱 인스턴스가 10대에서 40대로 늘면 풀 크기를 안 바꿔도 DB 프로세스는
4배가 된다. 앱 쪽에서 아무리 잘 나눠도 "인스턴스 수 × 풀 크기"는 결국 앱
배포 토폴로지에 종속된다. PG 생태계의 답은 **DB 바로 앞에 풀러를 하나 더
두는 것**이다.

```text
앱 40대 × HikariCP 10  =  클라이언트 커넥션 400개    ← 싼 쪽: PgBouncer에겐 커넥션 하나가 소켓 하나
                                │
                          [ PgBouncer ]  pool_mode = transaction
                                │
                          서버 커넥션 40개  =  PostgreSQL 백엔드 프로세스 40개   ← 비싼 쪽
```

**세 가지 풀링 모드** — 서버 커넥션을 클라이언트에게서 언제 돌려받느냐의
차이다. `session`은 접속을 끊을 때(앱이 이미 풀을 쓰면 1:1이라 이득이
없다), `statement`는 문장마다(다중 문장 트랜잭션 불가, 특수 용도),
**`transaction`은 트랜잭션이 끝날 때마다** — 앱 커넥션 400개 중 어느
순간에 실제로 트랜잭션 안에 있는 것은 소수이므로 그 소수만 서버 커넥션
40개를 나눠 쓴다. 앱 커넥션의 대부분이 언제나 idle이기에 성립하는
곱셈이고, 실무 표준이다.

```ini
; pgbouncer.ini — 핵심만 (인증 설정은 생략)
[databases]
app = host=10.0.0.5 port=5432 dbname=app

[pgbouncer]
listen_port = 6432
pool_mode = transaction
max_client_conn = 2000        ; 앱 쪽에서 붙을 수 있는 소켓 수 — 싼 쪽이라 넉넉히
default_pool_size = 40        ; (DB, 유저) 쌍마다 실제로 여는 서버 커넥션 = PG 프로세스 수 — 5-1·5-2로 정한 값
query_wait_timeout = 3        ; 서버 커넥션을 이 시간 안에 못 받으면 실패 — HikariCP connection-timeout과 같은 역할
max_prepared_statements = 200 ; 1.21+ — transaction 모드에서 프로토콜 준비문을 추적 (아래 함정)
```

**transaction pooling의 제약 — "다음 트랜잭션도 같은 서버 커넥션일 것"
이라는 가정이 전부 깨진다.** 세션에 붙는 상태는 서버 커넥션에 남고,
클라이언트는 다음 트랜잭션에서 다른 서버 커넥션을 받는다.

| 깨지는 것 | 왜 | 대신 |
|---|---|---|
| 세션 `SET`(`SET search_path`, `SET work_mem` …) | 다음 트랜잭션은 다른 서버 커넥션에서 돈다 | `SET LOCAL`(트랜잭션 범위) 또는 `ALTER ROLE … SET`(롤 기본값) |
| 세션 advisory lock(`pg_advisory_lock`) | 락은 서버 커넥션에 남고 클라이언트는 떠난다 | `pg_advisory_xact_lock`(트랜잭션 종료 시 자동 해제) |
| `LISTEN`/`NOTIFY` 수신 | 알림은 서버 커넥션으로 온다 | 직결 커넥션 하나를 따로 둔다 |
| 임시 테이블, `WITH HOLD` 커서 | 세션에 붙어 있다 | 트랜잭션 안에서만 쓰거나 별도의 session 모드 풀 |
| SQL `PREPARE`/`DEALLOCATE` | 이름이 서버 커넥션에 남는다 | 드라이버의 프로토콜 준비문은 1.21+에서 풀러가 추적 |

```java
// ❌ before — transaction pooling 뒤에서 조용히 깨지는 코드들
jdbc.execute("SET search_path TO tenant_42");     // 다음 트랜잭션은 다른 서버 커넥션 → 남의 스키마 또는 public
jdbc.execute("SELECT pg_advisory_lock(12345)");   // 락은 서버 커넥션 A에 남고, 해제 호출은 커넥션 B로 감 → 영구 락
```

```java
// ✅ after — 모든 상태를 트랜잭션 범위 안에 가둔다
@Transactional
public void doTenantWork() {
    jdbc.execute("SET LOCAL search_path TO tenant_42");   // 이 트랜잭션이 끝나면 자동 복원
    jdbc.execute("SELECT pg_advisory_xact_lock(12345)");   // 커밋/롤백 시 자동 해제 — 같은 서버 커넥션 안에서 끝난다
}
```

**pgjdbc 준비문 함정(가산점 포인트).** pgjdbc는 같은 `PreparedStatement`를
5회(`prepareThreshold` 기본값) 실행하면 서버 측 준비문(`S_1`)으로 전환한다.
예전 transaction 모드에서는 이 이름이 서버 커넥션 A에만 있어, 다음 실행이
커넥션 B로 가면 `ERROR: prepared statement "S_1" does not exist`가 터졌다.
우회는 `prepareThreshold=0`(계획 캐시 포기)이었고, PgBouncer 1.21부터
`max_prepared_statements`로 풀러가 준비문을 추적해 주면서 해소됐다. 이걸
모르고 PgBouncer를 끼우면 배포 직후 이 에러가 폭발한다.

**HikariCP는 그대로 둔다.** TCP 재사용, 앱 안의 대기 큐와
`connection-timeout`, 누수 감지, 메트릭은 앱 풀의 일이다. 역할 분담은
**HikariCP = 인스턴스 하나 안의 동시성과 대기 정책, PgBouncer = DB 앞의
프로세스 총량 통제.** HikariCP 풀은 여전히 작게 — "PgBouncer 앞이라
커넥션이 싸졌으니 크게"로 가면 대기가 `cl_waiting`으로 자리만 옮긴다.

**PgBouncer 자체의 한계.** 단일 스레드 이벤트 루프라 인스턴스 하나의 처리량
상한이 있고(부하가 크면 `so_reuseport`로 여러 프로세스), 단일 장애점이
되지 않도록 2대 이상 둔다. 관측은 `SHOW POOLS`(`cl_active`, `cl_waiting`,
`sv_active`, `sv_idle`, `maxwait`) — `cl_waiting`이 지속되면 "서버 커넥션이
안 돌아온다"는 뜻으로 4절의 [2]와 같은 자리다. 클라우드면 **RDS Proxy**가
같은 역할을 한다(단, 세션 상태를 바꾸는 순간 서버 커넥션을 그 클라이언트에
고정(pinning)해 멀티플렉싱 효과가 사라지므로 위 제약표는 그대로 유효하다).

**페일오버·재시작 때의 커넥션 폭주.** 프라이머리가 바뀌면 모든 앱
인스턴스의 풀이 **동시에** 재접속한다 — 40대 × 10 = 400개의 fork + 인증 +
캐시 워밍이 한꺼번에 몰려 새 프라이머리가 첫 수십 초를 접속 처리에만 쓰고,
`max_connections`를 넘기면 53300 에러가 섞여 나온다. PgBouncer가 앞에
있으면 DB에 다시 붙는 것은 서버 커넥션 40개뿐이고 앱 400개는 PgBouncer에
줄을 선다 — 폭주를 흡수하는 완충재다. 페일오버 뒤 앱 동작 전반은
[`28-db-failover-application-behavior.md`](28-db-failover-application-behavior.md).

## 6. 실제 사례 — 풀을 줄였더니 빨라졌다

HikariCP 위키가 인용하는 Oracle 성능팀의 시연이 이 현상의 대표 사례다.
수천 개 수준(약 2,000개)이던 커넥션 풀을 100개 미만으로 줄이자 쿼리
응답시간이 수십 배 빨라지고 처리량이 올랐다. 하드웨어도 쿼리도 그대로였다.

이 결과를 "신기한 일"이 아니라 **구조적으로** 설명할 수 있어야 한다.
아래는 같은 구조를 PostgreSQL 위에 옮긴 전형적 시나리오다(예시 수치).

```text
[증상] 피크 시간 API p99 2초. 앱 로그에 "Connection is not available, request timed out" 간헐 발생.
[첫 처방] "커넥션이 모자라구나" → maximum-pool-size 30 → 100
         (인스턴스 10대 → PG 백엔드 프로세스 300 → 1,000. max_connections도 500 → 1,200으로 올려 맞춤)
[결과] 타임아웃 로그는 줄었는데 p99가 2초 → 5초로 악화. DB CPU 100%. 새벽 배치 시간에 OOM으로 PG 전체 재시작 1회.
```

늘렸는데 왜 나빠졌는가 — 1~2절로 읽으면:

- DB는 8코어. 커넥션 300일 때 이미 `pg_stat_activity`의 `active`가 수십
  개로 코어를 넘어 **포화 구간**에 있었다. 앱의 타임아웃은 "커넥션 부족"이
  아니라 "DB가 느려서 커넥션이 안 돌아옴"의 신호였다.
- 1,000개로 늘리자 DB 안의 백엔드가 3배가 됐다. 사슬 A로 컨텍스트 스위칭과
  1,000개 백엔드를 훑는 스냅샷 비용이 얹혀 CPU 100% 중 쿼리 실행 몫이
  줄었다. 사슬 D로 프로세스 700개분의 메모리가 OS 페이지 캐시를 밀어내
  `shared_buffers` 미스가 곧 디스크 읽기가 됐고(`LWLock:BufferMapping`
  등장), 사슬 B로 그 읽기들이 뒤섞여 랜덤화됐다. 같은 행을 갱신하는
  UPDATE는 사슬 C로 대기열이 3배가 됐고, 대기 중인 트랜잭션들이
  `backend_xmin`을 쥐어 autovacuum이 뒤처지며 죽은 튜플이 쌓였다. OOM
  재시작은 프로세스 메모리를 빼고 `max_connections`만 올린 대가였다.
- 타임아웃 로그가 줄어든 건 **앱에서의 대기가 DB 안으로 옮겨갔기** 때문이다.
  대기가 사라진 게 아니라 **더 비싼 곳에서 대기**하게 됐다.

```text
[진단] 4절 순서로: 톰캣 스레드 여유 → Hikari pending 다수 → DB CPU 100%
       pg_stat_activity: active ≈ 150 (코어 8) — wait_event NULL 60, LWLock:BufferMapping 30,
                         IO:DataFileRead 25, Lock:transactionid 20 / idle in transaction 40 (xact_age 수십 초)
       vmstat cs 폭증, pg_stat_database.blks_read 급증, n_dead_tup 증가·last_autovacuum 지연
[두 번째 처방] maximum-pool-size 100 → 8 (DB 전체 80), connection-timeout 3초,
             idle_in_transaction_session_timeout = 30s, 후속으로 PgBouncer 도입
[결과] active ≈ 12~16, DB CPU 75%, p99 5초 → 300ms, TPS 상승. LWLock·IO 대기 거의 소멸.
       앱 pending은 간헐 발생하지만 acquire p99 수십 ms 수준.
```

줄였는데 왜 좋아졌는가:

- DB 안의 백엔드가 코어 수 근처로 내려오자 **컨텍스트 스위칭과 스냅샷
  비용이 사라지고 CPU가 온전히 쿼리에 쓰였다.** 같은 CPU 75%가 이전
  100%보다 더 많은 쿼리를 처리한다.
- 프로세스 메모리가 돌아오고 동시 쿼리의 워킹셋이 `shared_buffers` + OS
  캐시 안에 들어오면서 **히트율이 회복**됐고, 줄어든 디스크 읽기는 서로
  덜 섞여 **순차성을 되찾았다.**
- 동시 트랜잭션이 줄어 **락 충돌 확률이 떨어지고** 트랜잭션이 짧아졌으며,
  `backend_xmin`이 빨리 풀려 autovacuum이 따라잡았다.
- 그 결과 쿼리 1건의 실행 시간이 크게 줄었고, 커넥션이 빨리 돌아오니
  **80개로도 1,000개일 때보다 많은 요청을 처리**했다. 대기는 앱 풀에서
  잠깐(park) 발생할 뿐 DB 자원은 소모하지 않는다.

이 사례의 교훈을 한 문장으로: **"대기 줄은 어디에든 생긴다. 그 줄을 DB
안(비싼 대기 — PG에서는 프로세스 하나가 통째로 서서 기다린다)에 세울
것인가, DB 앞의 앱 풀·PgBouncer(싼 대기)에 세울 것인가가 풀 크기 결정의
본질이다."** 작은 풀은 DB를 최적 동시성으로 돌리기 위한 **의도적인
관문(throttle)** 이다.

남은 pending을 더 줄이고 싶다면 풀을 키우는 게 아니라 **점유 시간을
줄인다** — 트랜잭션 안의 외부 호출 제거, 느린 쿼리 튜닝, 읽기 트래픽의
레플리카 분리. 이 방향은 2장 산정 문서의 Little's law(동시수 = TPS ×
점유 시간)가 그대로 말해 준다.

## 7. 꼬리질문 대비 포인트

### "그럼 커넥션을 늘리는 게 정답인 경우는 언제인가요?"

DB가 **놀고 있을 때**다. 구체적으로 DB CPU 여유, 디스크 `%util` 여유,
`pg_stat_activity`에 `Lock` 대기 없음 — 이 세 가지가 동시에 만족되는데 앱
쪽 `hikaricp.connections.pending`이 발생하면, 커넥션이 DB의 처리 능력보다
적어서 코어가 비는 상태다(1절 곡선의 ① 구간). 이때는 늘리면 처리량이
선형으로 오른다. 반대로 셋 중 하나라도 포화면 늘리는 것은 대기 줄을 DB
내부로 옮기는 것일 뿐이다. "늘려도 되는가"는 앱 메트릭이 아니라 **DB
메트릭이 결정**한다는 것이 답의 핵심이다. 늘리기로 했다면 인스턴스 수를
곱한 합계가 `max_connections`에서 autovacuum·복제·관리 몫을 뺀 안에
들어가는지까지 확인한다.

### "디스크가 병목인 상황에서 커넥션을 늘리면 정확히 무슨 일이 일어나나요?"

두 가지다. 첫째, 디스크의 IOPS는 장치가 정한 상수라 요청자를 늘려도
초당 처리되는 I/O는 안 늘고 큐(`await`)만 길어진다. 둘째, 더 나쁜 쪽인데,
각 쿼리가 혼자서는 순차적으로 읽더라도 여러 쿼리의 요청이 디스크에
번갈아 도착하면 디스크 입장에서는 **랜덤 접근**이 된다. HDD라면 매 요청마다
seek가 발생해 총 처리량이 순차 수준에서 랜덤 수준으로 떨어진다 — 자릿수가
다른 하락이다. 그래서 디스크 병목에서 동시성 증가는 무의미를 넘어 유해하고,
오히려 커넥션을 줄여 각 스캔의 순차성을 되찾는 것이 총 디스크 처리량을
올린다. SSD·클라우드 볼륨은 seek가 없어 두 번째 효과는 약하지만, IOPS
상한이 상품 스펙으로 딱딱하게 걸려 있어 첫 번째 효과는 더 일찍 온다.
PG에서 이 상태는 `wait_event_type = 'IO'`(`DataFileRead`)가 `active`
백엔드의 다수를 차지하는 것으로 보이고, 쓰기 워크로드라면 `WALSync`가
같은 자리에 선다 — 커밋 처리량의 상한은 WAL fsync 속도다.

### "풀을 줄였더니 앱에서 커넥션 획득 대기가 늘었습니다. 잘못 조정한 건가요?" (시니어 변별 포인트)

대기가 **어디로 옮겨갔는지**를 먼저 본다. 풀을 줄이기 전에는 요청이 DB
내부에서 프로세스·CPU·락·`backend_xmin`을 쥔 채 기다렸고(비싼 대기), 줄인
뒤에는 앱 풀에서 스레드가 park된 채 기다린다(싼 대기 — DB 자원 소모 0).
판단 기준은 대기 발생 여부가 아니라 **최종 처리량과 p99 응답시간**이다.
둘이 좋아졌다면 조정은 옳다 — 대기가 눈에 보이는 위치로 옮겨왔을 뿐이다.
남은 대기를 줄이고 싶다면 풀을 도로 키우는 게 아니라 **점유 시간**을
줄인다(트랜잭션 밖으로 외부 호출 빼기, 느린 쿼리 튜닝, 읽기 레플리카 분리).
단, 앱 쪽 대기가 톰캣 스레드를 오래 묶어 스레드 풀 고갈로 번지지 않도록
`connection-timeout`을 짧게 두고 빨리 실패시키는 안전장치를 같이 건다.
"대기 총량"이 아니라 "대기의 위치와 비용"으로 답하면 시니어 답변이다.

### "HikariCP 공식(코어 × 2 + 스핀들)을 그대로 쓰면 되지 않나요?"

경험식이라 **자릿수를 잡는 용도**로만 쓴다. 항의 의미는 분명하다 — 코어
수는 CPU 병렬성 상한, ×2는 I/O 대기 동안 다른 백엔드가 CPU를 쓰는 겹치기
여유, 스핀들 수는 디스크 병렬성. 하지만 SSD·NVMe·클라우드 볼륨에는
스핀들이라는 물리 단위가 없고, I/O 대기 비율이 워크로드마다 달라 ×2가
맞는지도 알 수 없다. 그래서 공식으로 출발점(예: 8코어 → 20 전후)을 잡고,
부하 테스트에서 풀 크기를 단계적으로 바꿔가며 TPS 포화 지점과 p99 붕괴
지점을 직접 그려 채택한다. 인스턴스 N대의 합이 DB 기준 숫자라는 것,
오토스케일링 최대 대수까지 곱해 봐야 한다는 것도 공식이 말해 주지 않는
부분이다.

### "커넥션이 idle이면 비용이 없는 것 아닌가요? `max_connections`를 넉넉히 올려 두면 안 되나요?" (가산점 포인트)

PostgreSQL에서는 idle도 비용이다. 세 겹 — ① **메모리**: idle 커넥션도
프로세스라 수 MB~수십 MB를 각자 쥐고, 그 합은 OS 페이지 캐시에서
빠져나간다. ② **스냅샷**: 문장마다 프로세스 배열 전체를 훑으므로 idle
백엔드 900개는 일하는 100개의 모든 문장에 세금을 매긴다(PG 14에서 완화).
③ **idle in transaction이면 훨씬 나쁘다**: `backend_xmin`을 쥐어 VACUUM을
막고 락을 보유한다. 그래서 `max_connections`는 상한선이지 튜닝 손잡이가
아니고(3절), 커넥션이 정말 많이 필요하면 답은 **PgBouncer의 transaction
pooling**으로 앱 커넥션 수와 DB 프로세스 수를 떼어 놓는 것이다.

### "PgBouncer를 앞에 두면 HikariCP는 빼도 되나요? transaction pooling에서 깨지는 건 뭔가요?" (시니어 변별 포인트)

빼지 않는다 — 역할이 다르다. HikariCP는 **인스턴스 하나 안**의 동시성과
대기 정책(TCP 재사용, `connection-timeout`, 누수 감지, 메트릭), PgBouncer는
**DB 앞**의 프로세스 총량 통제다. 둘 다 두되 HikariCP는 여전히 작게.
transaction pooling에서 깨지는 것은 "다음 트랜잭션도 같은 서버 커넥션"이라는
가정에 기댄 모든 세션 상태 — 세션 `SET`(→ `SET LOCAL`/`ALTER ROLE … SET`),
세션 advisory lock(→ `pg_advisory_xact_lock`), `LISTEN`(→ 직결 커넥션),
임시 테이블·`WITH HOLD` 커서, 그리고 pgjdbc의 서버 준비문(`prepared
statement "S_1" does not exist` — 1.21+의 `max_prepared_statements`로 해소).
덧붙이면 PgBouncer는 단일 스레드라 처리량 상한이 있고 단일 장애점이므로
2대 이상, 페일오버 때는 앱 수백 개의 재접속 폭주를 DB 대신 받아 주는
완충재이기도 하다.

### "MySQL로 물어보면 답이 달라지는 부분은?" (경험 대조)

네 지점이다. ① **커넥션의 실체** — MySQL은 스레드(thread cache로 재사용),
PG는 fork된 프로세스. 그래서 MySQL은 커넥션 수천 개를 붙여 두는 운영이
흔하지만 PG는 수백 개에서 스냅샷·메모리 비용으로 꺾이고, 외부 풀러
(PgBouncer)가 사실상 필수다. ② **idle의 비용** — InnoDB의 read view는
진행 중인 트랜잭션만 보므로 idle 커넥션이 거의 공짜에 가깝지만, PG는
프로세스 배열을 훑는 스냅샷과 프로세스 메모리 때문에 idle도 세금을 낸다.
③ **DB 내부 동시성 상한** — MySQL은 `innodb_thread_concurrency`로 DB
스스로 동시 실행 수를 억제할 수 있지만 PG에는 그 손잡이가 없어 상한을
반드시 DB 밖(앱 풀·PgBouncer)에서 걸어야 한다. ④ **롱 트랜잭션의 대가와
캐시 구조** — MySQL은 언두 증가와 단일 버퍼 풀 잠식으로, PG는 VACUUM
정지(bloat)와 OS 페이지 캐시 잠식(+ OOM 시 전체 재시작)으로 나타난다.
이 넷을 짚으면 "커넥션은 자리일 뿐"이라는 원리는 같되 **PG에서 왜 그
자리가 더 비싼지**를 구조로 말하는 답이 된다.

## 한 줄 요약

커넥션은 DB의 처리 능력이 아니라 DB 앞의 자리 수이고 PostgreSQL에서는 그
자리 하나가 프로세스 하나라서, 코어와 디스크가 정한 상한을 넘긴 커넥션은
**컨텍스트 스위칭과 스냅샷 비용·I/O 큐 적체와 순차 I/O의 랜덤화·락 경합과
VACUUM 정지·OS 캐시 잠식과 LWLock 경합**을 더 만들어 처리량을 깎는다 —
그래서 늘리기 전에 앱 스레드 풀 → 커넥션 풀 → DB CPU → 디스크 I/O → 락
대기 순으로 `pg_stat_activity`의 state·wait_event 분포를 읽어 병목을
확인하고, 풀 크기는 경험식 → 부하 테스트 → 메트릭 알람으로 고정하며,
대기 줄은 DB 안(비싼 대기)이 아니라 앱 풀과 PgBouncer(싼 대기)에 세우고,
`max_connections`는 튜닝 손잡이가 아니라 상한선으로만 다룬다.
