# 정규화 vs 반정규화 — "조회 성능을 위해"에서 멈추면 반쪽짜리 정의다

> 핵심 관전 포인트: **정규화는 "하나의 사실은 한 곳에만" — 중복을 없애 수정 이상(update anomaly)을 구조적으로 차단하는 설계다. 반정규화는 조회 패턴에 맞춰 의도적으로 중복·연산 값을 허용하고, 그 대가(갱신 정합성)를 관리하는 결정이다 — "대가 관리"까지 말해야 정의가 완성된다. 선택 기준은 4축: ① 읽기:쓰기 비율 ② 실측된 조인·집계 병목 ③ 인덱스·Index Only Scan·캐시 선행 검토 ④ 대가 지불 준비. PostgreSQL은 generated column·트리거·materialized view로 관리 장치 일부를 DB 안으로 끌어올 수 있지만, 다른 테이블을 세는 집계 컬럼은 어느 도구로도 FK 같은 선언적 제약이 되지 못한다 — 보정 배치가 끝까지 남는 이유다. 그리고 핫 로우의 비용은 "성능 저하"라는 뭉뚱그린 말 대신 락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파라는 이름 붙은 사슬로 말한다 — PostgreSQL에서는 UPDATE마다 쌓이는 죽은 튜플(bloat)이 그 위에 한 겹 더 얹힌다.**

---

## 0. 질문 + 의도

**질문**: "정규화와 반정규화란? 반정규화를 선택하는 기준은?"

**출제 의도**: 교과서 정규화만 아는 사람과 **"조회 패턴에 맞춰 의도적으로 중복을 허용하고 그 대가(갱신 정합성)를 관리"해본 사람**을 구분한다. 대용량 조회 시스템은 반정규화 없이 성립하지 않는다. 즉 정규형 번호의 암기가 아니라 — 편익(조회 성능)과 대가(갱신 정합성)를 **양면으로 조립**해서, 언제 어떤 관리 장치와 함께 중복을 들여오는지의 실무 판단을 본다.

## 1. 개념 — 정규화는 수정 이상의 구조적 차단, 반정규화는 대가를 아는 의도적 중복

### 1-1. 먼저 "수정 이상"이 무엇인지 — 실제 데이터로 보기

정규화를 설명할 때 가장 먼저 나오는 말이 **수정 이상(update anomaly)** 인데, 이 말이 정의 없이 지나가면 그 뒤가 전부 뜬다. 그러니 데이터부터 본다.

**수정 이상**이란 **같은 사실이 여러 행에 중복 저장돼 있을 때, 그중 일부만 고쳐서 데이터가 서로 모순되는 상태**를 말한다. "이상(anomaly)"은 "정상적인 연산(UPDATE 한 번)을 했는데 데이터가 비정상이 되는 현상"이라는 뜻이다.

직원 테이블 하나에 부서 정보까지 같이 넣은 설계를 보자.

```text
employees  (부서 정보를 직원 행에 함께 담은 설계)

 id | name   | dept_name | dept_phone
----+--------+-----------+-------------
  1 | 김하늘 | 개발1팀   | 02-100-0001
  2 | 이바다 | 개발1팀   | 02-100-0001      ← "개발1팀의 대표번호는 02-100-0001"이라는
  3 | 박구름 | 개발1팀   | 02-100-0001         하나의 사실이 직원 수만큼 복제돼 있다
  4 | 최나무 | 디자인팀  | 02-100-0002
```

여기서 개발1팀 대표번호가 바뀌어 UPDATE를 하는데, 조건을 잘못 걸었거나 배치가 중간에 끊겨 **한 행만 반영**됐다고 하자.

```sql
UPDATE employees SET dept_phone = '02-100-0009' WHERE id = 1;   -- 한 행만 갱신됐다
```

```text
 id | name   | dept_name | dept_phone
----+--------+-----------+-------------
  1 | 김하늘 | 개발1팀   | 02-100-0009   ← 새 번호
  2 | 이바다 | 개발1팀   | 02-100-0001   ← 옛 번호
  3 | 박구름 | 개발1팀   | 02-100-0001   ← 옛 번호

"개발1팀 대표번호가 뭐죠?"  →  DB가 두 가지 답을 내놓는다. 어느 쪽이 맞는지 DB는 모른다.
```

**이 상태가 수정 이상이다.** 문법 오류도, 제약 위반도 아니다. DB는 아무 불평 없이 이 모순을 받아들이고 계속 서비스한다. 그래서 이런 데이터는 **몇 달 뒤 리포트가 이상하다는 신고로 발견**되고, 그때는 어느 값이 진실인지 되짚을 방법이 없다.

### 1-2. 같은 뿌리의 다른 얼굴 — 삽입 이상과 삭제 이상

수정 이상만 있는 게 아니다. 위와 **똑같은 테이블 하나**에서 나머지 둘도 그대로 나온다.

**삽입 이상(insertion anomaly)** — 아직 직원이 배정되지 않은 신설 '플랫폼팀'을 등록하고 싶다. 그런데 부서 정보를 담을 자리가 `employees` 행 안에만 있으므로, **직원이 없으면 부서를 등록할 방법이 없다.** 억지로 넣으려면 `name`이 비어 있는 유령 직원 행을 만들어야 한다 — 존재하지 않는 직원 한 명이 데이터에 끼어드는 것이다.

```text
 id | name   | dept_name  | dept_phone
----+--------+------------+-------------
  9 | (NULL) | 플랫폼팀   | 02-100-0003   ← 부서를 등록하려고 만든 가짜 직원 행
```

**삭제 이상(deletion anomaly)** — 디자인팀의 유일한 직원 최나무(id=4)가 퇴사해 그 행을 지운다. 그러면 **"디자인팀이라는 부서가 있고 대표번호는 02-100-0002"라는 사실까지 함께 사라진다.** 지우려던 것은 직원 한 명인데 부서가 같이 증발한 것이다.

셋의 뿌리는 하나다 — **서로 독립적인 두 사실(직원 / 부서)이 한 행에 묶여 있어서, 한쪽을 다루는 연산이 다른 쪽을 건드린다.**

### 1-3. 정규화 = "하나의 사실은 한 곳에만"

정규화의 본질은 규칙 목록(1NF, 2NF, ...)이 아니라 하나의 원칙이다 — **하나의 사실(fact)은 데이터베이스에서 정확히 한 곳에만 존재해야 한다.**

같은 사실이 여러 곳에 흩어져 있으면 수정할 때 전부 찾아 고쳐야 하고, 하나라도 놓치면 1-1에서 본 **"같은 질문에 DB가 두 가지 답을 하는" 상태**가 된다. 정규화는 이것을 코드 리뷰나 개발자의 주의력이 아니라 **테이블 구조 자체로 차단**한다. "고칠 곳이 한 곳뿐이면, 일부만 고쳐서 어긋날 방법이 애초에 없다"는 것이 차단의 원리다.

```sql
-- before: "부서 이름"이라는 하나의 사실이 직원 수만큼 복제됨
CREATE TABLE employees (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       text NOT NULL,
    dept_name  text,           -- '개발1팀'이 소속 직원 300행에 흩어져 있다
    dept_phone text            -- 대표번호도 마찬가지로 300벌
);
-- 부서 이름이 바뀌면? UPDATE employees SET dept_name = ... WHERE dept_name = ...
-- 조건을 잘못 쓰거나 일부 행만 갱신되면 → 한 부서에 두 이름 (수정 이상)
-- 직원이 없는 부서는 등록 자체가 불가 (삽입 이상)
-- 마지막 직원을 지우면 부서까지 사라짐 (삭제 이상)

-- after: 부서라는 사실은 departments에 딱 한 곳
CREATE TABLE departments (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  text NOT NULL,        -- '개발1팀'은 여기 한 행에만 존재
    phone text
);
CREATE TABLE employees (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name    text NOT NULL,
    dept_id bigint NOT NULL REFERENCES departments (id)  -- 복제 대신 참조(FK)
);
CREATE INDEX ON employees (dept_id);  -- PG는 FK 컬럼 인덱스를 자동으로 만들지 않는다
-- 부서 이름 변경 = departments 한 행 UPDATE. 어긋날 "다른 곳"이 구조적으로 없다.
-- 직원 없는 부서도 등록 가능. 마지막 직원을 지워도 부서는 남는다.
```

비유하면 — 회사 규정을 각 팀이 복사해 갖는 것(정규화 전)과, 원본은 사내 위키 한 페이지에만 두고 각 팀은 링크만 갖는 것(정규화)의 차이다. 복사본 체제에서는 개정 때마다 전 팀을 돌며 바꿔야 하고, 한 팀이라도 옛 버전을 들고 있으면 사고가 난다.

### 1-4. 정규형은 암기 목록이 아니라 "이 단계가 무엇을 막는가"의 체크리스트다

정규형을 1NF·2NF·3NF라는 **번호로 외우면 면접에서 아무 쓸모가 없다.** 각 단계는 "위반하면 어떤 이상이 생기는가"로 읽어야 판단에 쓰인다. 세 단계를 그 관점으로 정리한다.

**1NF (제1정규형) — 한 칸에는 값 하나.**

한 컬럼에 값을 여러 개 욱여넣지 않는 상태다. `phone` 칸에 `'010-1111,010-2222'`처럼 쉼표로 이어 붙이거나, `phone1`·`phone2`·`phone3`처럼 반복 컬럼을 만드는 것이 위반이다.

이 단계가 막는 것: **값 하나만 고치거나 지우는 연산이 불가능해지는 상태.** 두 번째 번호만 바꾸려면 문자열을 잘라 붙이는 코드를 짜야 하고, 실수하면 나머지 번호까지 날아간다. 검색도 `LIKE '%010-2222%'`가 되어 인덱스를 못 탄다. 즉 1NF 위반은 **그 값을 DB의 1급 시민 자리에서 끌어내리는** 일이다.

PostgreSQL은 배열과 `jsonb`를 지원해서 이 선을 넘기가 유난히 쉽다. 넘는 순간 그 안의 값은 타입 제약·FK·통계·일반 인덱스의 대상에서 벗어난다는 것을 알고 넘어야 한다([RDB의 JSON 컬럼](18-json-column-tradeoffs.md)).

**2NF (제2정규형) — 복합 PK의 "일부"에만 딸린 컬럼이 없을 것.**

PK가 여러 컬럼으로 이루어졌을 때, 어떤 컬럼이 PK 전체가 아니라 그중 일부만으로 결정된다면 위반이다(부분 함수 종속).

```text
[2NF 위반] order_items(order_id, product_id) PK, qty, order_date
    (order_id, product_id) → qty          정상: 이 주문의 이 상품을 몇 개 샀는지
    order_id 하나만으로 → order_date      위반: 주문일은 상품과 무관하게 주문만으로 정해진다

  결과: 한 주문에 품목이 10개면 order_date가 10벌 복제된다
        → 주문일을 정정할 때 10행을 다 고쳐야 하고, 일부만 고치면 한 주문에 두 날짜
```

이 단계가 막는 것: **PK의 일부에만 딸린 사실이 "나머지 부분의 개수만큼" 복제되는 수정 이상.** 처방은 그 컬럼을 자기 자리(여기서는 `orders` 테이블)로 올려보내는 것이다.

**3NF (제3정규형) — PK가 아닌 컬럼이 다른 비-PK 컬럼에 딸리지 않을 것.**

1-1의 `employees` 표가 정확히 이 위반이다.

```text
[3NF 위반] employees(id PK, name, dept_name, dept_phone)
    id → dept_name              직원이 정해지면 소속 부서가 정해진다
    dept_name → dept_phone      부서가 정해지면 대표번호가 정해진다
    따라서 id → dept_phone 은 dept_name을 "거쳐 가는" 종속이다 (이행적 종속)

  결과: dept_phone은 부서의 속성인데 직원 테이블에 살고 있다
        → 부서 수만큼이 아니라 직원 수만큼 복제된다 → 1-1의 수정 이상

[3NF]  departments(id PK, name, phone) / employees(id PK, name, dept_id FK)
    dept_phone은 departments 한 행에만 존재 → 고칠 곳이 하나뿐 → 어긋날 방법이 없다
```

이 단계가 막는 것: **"A가 정해지면 B, B가 정해지면 C"의 사슬에서 C가 A의 테이블에 눌러앉아 복제되는 수정 이상.**

실무의 기본선은 여기까지다. 그 위(BCNF, 4NF)는 후보 키가 여러 개 겹치는 특수한 모양에서 등장하는데, 목적은 똑같다 — **"고칠 곳을 하나로 만들어 이상을 구조적으로 없앤다."** 정규형 번호를 외우는 대신 이 목적을 쥐고 있으면, 처음 보는 스키마에서도 "이 컬럼은 무엇이 정해지면 정해지는가"를 물어 위반을 찾아낼 수 있다.

### 1-5. 반정규화의 두 형태 — 중복 컬럼과 연산(집계) 컬럼

반정규화가 들여오는 중복은 크게 두 형태다.

- **중복 컬럼**: 다른 테이블의 값을 조인 없이 읽으려고 복사해 둔다. 예 — `comments.author_name`(원본은 `users.name`).
- **연산(집계) 컬럼**: 매번 COUNT/SUM 하는 대신 결과를 컬럼에 유지한다. 예 — `posts.comment_count`(원본은 `comments`의 행 수).

두 형태 모두 원리는 같다. **정규화가 금지한 "같은 사실의 복제"를 조회 패턴을 위해 일부러 되돌리는 것.** 즉 반정규화는 1-4의 정규형을 의도적으로 위반하는 행위이고, 그래서 1-1에서 본 수정 이상의 위험을 스스로 불러들이는 일이다.

### 1-6. 정의를 완성하는 나머지 반쪽 — "의도적" + "대가 관리"

여기가 이 문서의 첫 번째 핵심이다. 반정규화를 "조회 성능을 위해 중복을 두는 것"까지만 말하면 **편익만 말한 반쪽 정의**다. 완성된 정의는 이렇다.

> 반정규화 = 조회 패턴에 맞춰 **의도적으로** 중복·연산 값을 허용하고, **그 대가(갱신 정합성)를 관리 장치와 함께 지불하는 결정.**

두 단어가 정의의 자격 요건이다.

- **"의도적"**: 설계를 몰라서 중복이 생긴 것은 반정규화가 아니라 그냥 정규화 실패다. 반정규화는 정규화된 설계를 **알고서** 되돌리는 결정이고, 어떤 사실을 어디에 복제했는지가 문서와 코드에 드러나야 한다.
- **"대가 관리"**: 중복을 두는 순간 "원본과 사본이 어긋날 수 있다"는 부채가 생긴다. 이 부채를 갚는 장치(같은 트랜잭션, 원자적 UPDATE, 보정 배치 — 2장)가 함께 설계되지 않은 중복은 결정이 아니라 방치다.

면접에서 이 질문의 변별점은 정확히 여기다 — **편익과 대가를 한 호흡에 말하는가.** "조회가 빨라진다"에서 끊기면 트레이드오프의 한 면만 본 것이고, "대신 갱신 정합성이라는 대가가 생기며 이를 이렇게 관리한다"까지 이어져야 양면이 조립된 답이다.

## 2. 선택 기준 4축 — 그리고 comment_count의 3단 관리 장치

### 2-1. 반정규화를 선택하는 기준 4축

| 축 | 질문 | 통과 조건 |
|---|---|---|
| ① 읽기:쓰기 비율 | 이 데이터, 읽기가 압도적인가? | 사본은 읽을 때 이득, 쓸 때 비용이다. 쓰기가 잦으면 대가만 키운다 |
| ② 실측 병목 | 조인·집계 비용이 **측정으로** 확인된 병목인가? | "느릴 것 같아서"는 근거가 아니다. `EXPLAIN (ANALYZE, BUFFERS)`·`pg_stat_statements`로 확인 |
| ③ 선행 검토 | 인덱스·커버링(Index Only Scan)·쿼리 형태·캐시로 먼저 해결되지 않는가? | 반정규화는 스키마를 바꾸는 비가역에 가까운 수단 — 더 싼 수단부터 |
| ④ 대가 지불 준비 | 갱신 정합성 관리 장치를 설계했는가? | 같은 트랜잭션 + 원자적 UPDATE(+ 핫 로우 경합 대비) + 보정 배치 |

④가 빠진 반정규화 제안은 "대출로 뭘 살지"만 정하고 상환 계획이 없는 것과 같다.

그리고 ③의 순서가 중요하다 — 인덱스는 되돌리기 쉽고 캐시는 DB 스키마를 건드리지 않지만, 반정규화 컬럼은 **모든 쓰기 경로가 그 컬럼을 함께 갱신해야 하는 영구적 의무**를 만든다. 가장 비싼 수단을 가장 마지막에 꺼낸다.

### 2-2. before — 정규화 그대로의 집계 조인

게시글 목록 20건을 보여줄 때마다 댓글 수를 세는 상황이다.

```sql
-- before: 정규화 그대로 — 목록 한 페이지에 집계 조인
SELECT p.id, p.title, count(c.id) AS comment_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id          -- PK로 묶으면 p.title은 함수 종속으로 인정돼 GROUP BY에 안 써도 된다
ORDER BY p.created_at DESC
LIMIT 20;
-- 목록 20건을 위해 그 글들에 달린 댓글 수만큼 행을 만나 집계한다.
-- 계획을 보면 Limit 아래의 집계 노드는 posts 전체를, 조인 노드는 comments
-- 전체를 훑는다(actual rows가 20이 아니다).
-- 트래픽이 큰 목록 화면이라면 이 비용이 실측 병목으로 잡힐 수 있다.
```

②실측으로 병목을 확인하고 ③인덱스·캐시로는 부족하다는 판단이 끝났다면, 그때 `posts.comment_count` 연산 컬럼을 도입한다. 단, **관리 장치 3단을 함께 설계**한다.

### 2-3. after — `posts.comment_count`와 3단 관리 장치

#### 3단이 각각 무엇을 막는가, 그리고 왜 그 순서인가

먼저 순서의 논리부터 잡는다. 3단은 "겹겹이 쌓은 같은 방어"가 아니라 **서로 다른 세 가지 실패 원인에 각각 대응하는 세 장치**다. 하나가 다른 하나를 대신하지 못하기 때문에 셋 다 필요하다.

| 단계 | 장치 | 대응하는 실패 원인 | 이 장치가 못 막는 것 |
|---|---|---|---|
| ① | **같은 트랜잭션** | 한 요청 안에서 두 쓰기가 갈라지는 것 — 댓글은 들어갔는데 카운트는 안 오른 채 커밋 | 여러 요청이 겹칠 때의 덮어쓰기, 애초에 이 트랜잭션을 안 거치는 경로 |
| ② | **원자적 UPDATE** | 여러 요청이 겹칠 때의 lost update — 둘이 같은 값을 읽고 같은 값을 써서 하나가 사라짐 | 아예 UPDATE 문을 실행하지 않는 경로 |
| ③ | **주기적 보정 배치** | 앞의 두 규약을 모르는 경로가 만든 드리프트 — 새 코드, 콘솔 직접 수정 | 실시간 정확성(보정 주기만큼은 늦다) |

읽는 순서는 **"단일 요청의 원자성 → 동시 요청의 격리 → 코드 밖에서 오는 변경"** 이다. 앞의 둘은 **예방**이고 셋째는 **복구**다. 앞의 둘로 막을 수 있는 것을 셋째에 미루면 데이터가 상시로 어긋난 채 굴러가고, 셋째를 생략하면 "예방이 완벽하다"는 전제 위에 서는 것인데 그 전제는 2-4절에서 무너진다.

#### 장치별 코드

```sql
-- after: 반정규화 + 3단 관리 장치
ALTER TABLE posts ADD COLUMN comment_count integer NOT NULL DEFAULT 0;
-- 상수 DEFAULT의 컬럼 추가는 테이블을 다시 쓰지 않고 카탈로그만 바꾼다(PG 11+).
-- 다만 ACCESS EXCLUSIVE 잠금은 잡으므로 SET lock_timeout = '2s' 와 함께 실행한다.

-- 장치 ① 같은 트랜잭션: 원본(댓글)과 사본(카운트)의 운명을 묶는다
BEGIN;
INSERT INTO comments (post_id, author_id, body) VALUES ($1, $2, $3);
UPDATE posts SET comment_count = comment_count + 1 WHERE id = $1;
COMMIT;
-- 카운트 갱신이 실패하면 댓글 INSERT도 함께 롤백 — 어긋난 채 커밋되는
-- 경로를 트랜잭션이 막는다. (대가: 댓글 쓰기가 posts 갱신 비용까지 짊어짐)

-- 장치 ② 원자적 UPDATE: 값을 읽어와 더하지 않는다
UPDATE posts SET comment_count = comment_count + 1 WHERE id = $1;
-- "SELECT로 읽고 → 애플리케이션에서 +1 → UPDATE"로 쪼개면, 두 요청이
-- 같은 값을 읽고 같은 값을 쓰는 lost update가 난다. DB가 행 락을 잡고
-- 현재 값 위에서 더하게 하는 위 형태여야 동시 요청에도 안 샌다.
-- (PG의 READ COMMITTED는 앞선 UPDATE의 커밋을 기다린 뒤 그 행의 최신
--  버전을 다시 읽어 그 위에 +1 한다 — 그래서 위 한 문장이면 안 샌다.)

-- 장치 ③ 주기적 보정 배치: 어긋남을 전제로 한 안전망
UPDATE posts p
SET    comment_count = c.cnt
FROM  (SELECT p2.id, count(c2.id) AS cnt
       FROM posts p2 LEFT JOIN comments c2 ON c2.post_id = p2.id
       GROUP BY p2.id) c
WHERE  c.id = p.id
  AND  p.comment_count IS DISTINCT FROM c.cnt;   -- 이미 맞는 행은 건드리지 않는다
-- PG의 UPDATE는 값이 같아도 새 튜플 버전을 쓴다(죽은 튜플 + WAL + 인덱스
-- 갱신 가능성). 위 가드가 없으면 보정 배치가 posts 전체를 매번 다시 쓰는 셈이다.
-- (실전에서는 전체가 아니라 최근 변경분·표본 검증 위주로 돈다)
```

애플리케이션 쪽에서는 ①과 ②가 이렇게 만난다.

```java
@Transactional  // 장치 ① — 두 쓰기를 하나의 커밋 단위로 묶는다
public void addComment(Long postId, Long authorId, String body) {
    commentRepository.save(new Comment(postId, authorId, body));
    // 장치 ② — 엔티티를 읽어 setCommentCount(+1) 하지 않는다.
    // 읽고-더하고-쓰면 동시 요청 둘이 같은 값을 읽어 하나의 증가가 사라진다.
    postRepository.incrementCommentCount(postId);
}

// Repository — DB가 현재 값 위에서 더하게 한다
@Modifying(clearAutomatically = true)  // 벌크 UPDATE는 영속성 컨텍스트를 우회하므로
@Query("update Post p set p.commentCount = p.commentCount + 1 where p.id = :id")
int incrementCommentCount(@Param("id") Long id);
```

### 2-4. 다 묶어도 왜 어긋나나 — 불변식이 DB 제약이 아니라 애플리케이션 관례에 산다

장치 ①②를 다 갖춰도 1년 뒤 `comment_count`는 실제와 어긋날 수 있다. 이유는 하나로 요약된다 — **"comment_count = comments의 행 수"라는 불변식이 DB 제약이 아니라 애플리케이션의 관례로만 존재하기 때문.**

FK나 UNIQUE 제약은 DB가 지키므로 어떤 코드 경로로 들어와도 뚫리지 않는다. 반면 이 불변식은 "댓글을 건드리는 모든 코드가 카운트도 함께 갱신하기로 한 약속"일 뿐이라, 약속을 모르는 경로가 하나만 생겨도 뚫린다.

- **새 코드 경로**: 신입이 만든 관리자용 댓글 일괄 삭제 API가 카운트 갱신을 빼먹는다. 컴파일도 테스트도 통과한다.
- **DB 직접 수정**: 운영 이슈로 콘솔에서 `DELETE FROM comments ...`를 직접 실행 — 애플리케이션의 약속은 애초에 거치지 않는다.
- **경로 비대칭**: 작성 경로는 +1을 하는데, 나중에 추가된 "블라인드 처리" 경로는 카운트를 어떻게 할지 정의조차 안 돼 있다.

그래서 장치 ③(보정 배치)은 "버그가 있으면 돌리는 것"이 아니라 **어긋남을 전제로 처음부터 설계에 포함하는 안전망**이다. 드리프트는 막는 게 아니라 "주기적으로 0으로 되돌리는" 대상이다.

### 2-5. PostgreSQL이 주는 반정규화 도구 — 관례를 DB 안으로 얼마나 옮길 수 있나

2-4의 결론은 "불변식이 애플리케이션 관례에 산다"였다. PostgreSQL에는 이 관례를 DB 쪽으로 옮겨 주는 도구가 몇 개 있는데, **각각 옮겨 주는 범위가 다르다.** 무엇을 DB가 대신 져 주고 무엇이 여전히 내 몫인지가 선택 기준이다.

| 도구 | DB가 대신 져 주는 것 | 여전히 내 몫 |
|---|---|---|
| generated column `GENERATED ALWAYS AS (...) STORED` (PG 12+) | 같은 행 안의 연산 값 계산·저장 — 어긋날 경로 자체가 없다 | 다른 테이블을 참조하는 식은 불가 → `comment_count`에는 못 쓴다 |
| 트리거 (`AFTER INSERT OR DELETE ON comments`) | 콘솔 DELETE·새 코드 경로까지 모든 쓰기가 카운트 갱신을 거친다 | 절차적 코드라 우회 가능(트리거 비활성화, `session_replication_role = replica`), 핫 로우 비용은 그대로 |
| materialized view + `REFRESH MATERIALIZED VIEW CONCURRENTLY` | 집계 결과를 통째로 스냅샷 — 쓰기 경로를 안 건드린다 | 신선도가 REFRESH 주기에 묶임, CONCURRENTLY는 유니크 인덱스 필수, 매번 전체 재계산 |
| `jsonb`·배열에 자식 데이터 내장 | 1:N 조인을 없앤다 | 부분 갱신 없음 — 원소 하나 바꿔도 값 전체를 새 튜플로 재기록 |

```sql
-- 같은 행 안의 연산 값이면 generated column — 드리프트가 구조적으로 불가능
ALTER TABLE order_items
    ADD COLUMN amount numeric GENERATED ALWAYS AS (qty * unit_price) STORED;

-- 다른 테이블을 세는 값이면 트리거로 "관례"를 DB 안으로 — 단, 선언적 제약은 아니다
CREATE FUNCTION bump_comment_count() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        UPDATE posts SET comment_count = comment_count + 1 WHERE id = NEW.post_id;
    ELSIF TG_OP = 'DELETE' THEN
        UPDATE posts SET comment_count = comment_count - 1 WHERE id = OLD.post_id;
    END IF;
    RETURN NULL;   -- AFTER 트리거의 반환값은 무시된다 (댓글의 post_id 변경 처리는 생략)
END $$;
CREATE TRIGGER trg_comment_count
AFTER INSERT OR DELETE ON comments
FOR EACH ROW EXECUTE FUNCTION bump_comment_count();
```

**트리거를 고를 때 함께 드는 대가**를 명시해 둔다. ① 갱신 로직이 애플리케이션 코드 밖으로 나가므로 `git grep comment_count`로는 안 잡히고, 트랜잭션이 왜 느린지 추적할 때 계획에도 잘 안 드러난다. ② 대량 적재 성능 때문에 트리거를 꺼 두는 순간 그 구간은 그대로 뚫린다. ③ 행 단위 트리거라 댓글 1만 건을 한 문장으로 INSERT해도 UPDATE가 1만 번 발생한다 — 3장의 핫 로우 사슬을 오히려 키운다.

기준은 하나로 정리된다 — **사본이 가리키는 원본이 같은 행 안에 있으면 generated column, 다른 테이블이면 트리거 또는 앱 트랜잭션 + 보정 배치, "잠시 후"로 느슨해도 되면 materialized view.** 트리거는 2-4의 구멍 중 "DB 직접 수정"과 "새 코드 경로"를 막아 주지만, 로직이 앱 코드 밖에 숨고 대량 적재 때 꺼 두는 순간 다시 뚫린다.

어느 도구를 써도 **다른 테이블을 세는 집계 컬럼은 FK·UNIQUE 같은 선언적 제약이 되지 못하므로**, 장치 ③(보정 배치)은 도구 선택과 무관하게 끝까지 남는다.

## 3. 핫 로우 — "성능 저하"가 아니라 이름 붙은 사슬로 말하기

초당 수백 개 댓글이 달리는 인기 글에서 2-3의 구조가 무슨 일을 겪는지 물었을 때, "성능이 저하되고 다른 요청도 문제가 생긴다"는 답과 아래 사슬을 이름으로 짚는 답은 전혀 다른 평가를 받는다.

이 주제 자체를 깊이 다루는 문서는 같은 장의 [초고빈도 카운터와 핫 로우](23-high-frequency-counter-hot-row.md)다. 여기서는 **반정규화의 대가라는 맥락에 필요한 만큼만** 짚는다.

### 3-1. 사슬을 단계 도식으로

모든 댓글 트랜잭션이 `UPDATE posts ... WHERE id = 인기글` — **같은 행 하나**를 갱신한다. 이런 행을 **핫 로우(hot row)** 라 부른다. 그 다음은 필연의 연쇄인데, 갈래가 둘이다.

```text
             같은 행 하나에 UPDATE가 몰린다  (posts.id = 인기글)
                              │
        ┌─────────────────────┴──────────────────────┐
        │ [A] 동시성 축                               │ [B] 저장 축 (PostgreSQL)
        ↓                                            ↓
 ⑴ 행 잠금 대기                              UPDATE는 제자리 수정이 아니라
    UPDATE는 그 행의 배타 락을 잡고            새 튜플 버전 삽입이다
    커밋까지 놓지 않는다                              ↓
        ↓                                     그 페이지에 죽은 튜플이 초당 수백 개씩 쌓인다
 ⑵ 사실상 직렬화                                      ↓
    락은 한 번에 하나만 통과시킨다              페이지의 여유 공간이 마른다
    수백 개 "동시" 요청이 한 줄로 선다                 ↓
    서버를 늘려도 소용없다                       HOT 업데이트가 깨진다
        ↓                                            ↓
 ⑶ 트랜잭션 장기화                            comment_count에 인덱스가 없어도
    대기 시간만큼 수명이 늘고,                  다른 인덱스들에 새 엔트리가 꽂힌다
    자기 락도 그만큼 오래 쥔다                          ↓
        ↓                                     autovacuum이 갱신 속도를 못 따라잡는다
 ⑷ 커넥션 점유                                        ↓
    기다리는 동안에도 DB 커넥션을 놓지 않는다    테이블·인덱스 bloat → 조회까지 느려진다
        ↓
 ⑸ 커넥션 풀 고갈
    풀 크기는 유한하다
        ↓
 ⑹ 전 서비스 지연
    풀은 서비스 공용이므로 로그인·결제 등
    무관한 요청까지 커넥션을 못 얻고 타임아웃된다
```

[A]축의 고리를 문장으로 한 번 더 풀면 이렇다.

> **⑴ 락 경합(lock contention)**: UPDATE는 그 행의 배타적 행 락을 잡고, 락은 커밋 때까지 유지된다. 초당 수백 트랜잭션이 같은 행 락 하나를 두고 줄을 선다.
>
> **⑵ 사실상 직렬화(serialization)**: 락은 한 번에 하나만 통과시키므로, 수백 개의 "동시" 요청이 실제로는 **한 줄로 서서 차례로** 처리된다. 서버를 아무리 늘려도 소용없다 — 병목은 CPU가 아니라 행 하나다.
>
> **⑶ 트랜잭션 장기화**: 줄 뒤쪽 트랜잭션은 락 대기 시간만큼 전체 수명이 늘어난다. 그리고 각 트랜잭션이 잡은 자신의 락도 그만큼 오래 유지되므로 뒤에 선 트랜잭션의 대기는 더 길어진다 — 대기가 대기를 키운다.
>
> **⑷⑸ 커넥션 점유와 풀 고갈**: 락을 기다리는 트랜잭션은 그동안 **DB 커넥션을 쥔 채로** 기다린다. 풀 크기는 유한하므로, 장기화된 트랜잭션들이 커넥션을 점유하면 풀이 바닥난다.
>
> **⑹ 전 서비스 전파**: 커넥션 풀은 서비스 전체가 공유한다. 인기 글 댓글과 무관한 요청 — 로그인, 결제, 다른 글 조회 — 도 커넥션을 못 얻어 대기·타임아웃된다. **행 하나의 경합이 서비스 전체의 장애가 된다.**

비유하면 — 계산대가 백 개인 마트(서버·커넥션)에서 특정 상품 하나의 재고 장부(핫 로우)를 계산 때마다 반드시 고쳐야 하는데, 그 장부에 펜이 하나뿐인 상황이다. 계산대가 아무리 많아도 모든 계산원이 펜 하나를 기다리며 계산대를 점유하고, 그 상품과 무관한 손님까지 빈 계산대가 없어 줄을 선다.

### 3-2. [B]축 보충 — PostgreSQL에서는 죽은 튜플과 VACUUM이 한 겹 더 얹힌다

행 락은 별도의 락 테이블이 아니라 튜플 헤더의 `xmax`에 기록되므로 락 개수 제한이나 에스컬레이션은 없지만, 줄 서기 자체는 똑같이 일어난다 — `pg_stat_activity`에 `wait_event_type = 'Lock'`, `wait_event = 'transactionid'`인 세션이 쌓이는 것으로 보인다.

그리고 PostgreSQL은 UPDATE를 제자리에서 고치지 않고 **새 튜플 버전을 삽입**하므로, 초당 수백 번 갱신되는 행 하나는 그 페이지에 죽은 튜플을 수백 개씩 남긴다. `comment_count`에 인덱스가 없으면 HOT 업데이트로 인덱스 갱신은 피하지만 페이지 여유 공간이 금세 바닥나고, 그 순간부터는 HOT이 깨져 다른 인덱스들까지 갱신된다. autovacuum이 이 속도를 따라잡지 못하면 bloat이 [A]축 위에 한 겹 더 얹힌다. 관찰은 `pg_stat_user_tables`의 `n_tup_upd` 대 `n_tup_hot_upd`, 그리고 `n_dead_tup`으로 한다.

### 3-3. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

| 뭉뚱그린 표현 | 이름 | 사슬로 말하면 |
|---|---|---|
| "성능이 저하된다" | **락 경합 + 사실상 직렬화** | 같은 행 락에 수백 트랜잭션이 줄 서서 동시성이 1로 붕괴 — 서버 증설로 해결 불가 |
| "다른 요청도 문제가 생긴다" | **커넥션 풀 고갈 + 전파** | 락 대기 트랜잭션이 커넥션을 쥔 채 장기화 → 풀 소진 → 무관한 요청까지 타임아웃 |
| "DB가 좀 무거워졌다" | **죽은 튜플 + VACUUM 추격 실패** | UPDATE마다 새 튜플 버전 → 페이지 여유 소진 → HOT 깨짐 → 인덱스 갱신 → bloat → 조회까지 느려짐 |

사슬의 힘은 **처방이 사슬의 고리에서 나온다**는 데 있다. "성능 저하"에서는 아무 처방도 안 나오지만, 고리를 짚으면 고리별 개입 지점이 보인다 — 경합 자체를 줄이거나(⑴), 락 보유 시간을 줄이거나(⑶), 풀을 보호하거나(⑸).

### 3-4. 처방 스케치 — 경합을 행에서 떼어내기

핫 로우의 근본 원인은 "쓰기 지점이 행 하나로 수렴"이므로, 처방은 수렴을 푸는 방향이다. 전략별 대가와 유실 창까지 따지는 상세는 [초고빈도 카운터와 핫 로우](23-high-frequency-counter-hot-row.md)에 있고, 여기서는 반정규화 결정을 내릴 때 함께 떠올려야 할 선택지만 나열한다.

- **비동기 집계**: 댓글 트랜잭션에서 카운트 UPDATE를 빼고, 이벤트를 쌓아 모아서(배치로 묶어) 반영한다. 모아 둔 N건을 `+ N` 한 번의 UPDATE로 반영하면 락을 잡는 횟수도 새 튜플 버전도 1/N이 된다. 정합성이 "즉시"에서 "잠시 후"로 느슨해지는 대가를 치른다.
- **카운터 분산(sharded counter)**: 카운터를 N개 행으로 쪼개 무작위로 하나에 +1 하고, 읽을 때 SUM 한다. 락 경합이 1/N로 준다. 대신 읽기가 N행 집계가 되고 그 컬럼으로 정렬·인덱스를 쓸 수 없다.
- **외부 카운터**: Redis 같은 인메모리 카운터에 증가시키고 주기적으로 DB에 반영한다. DB 쓰기가 극적으로 줄지만 반영 주기만큼의 유실 창과 이중 소스 관리가 생긴다.
- **락 보유 시간 줄이기**: 트랜잭션 안에서 **UPDATE를 커밋 직전(마지막 문장)에** 두면 락을 쥐는 구간이 짧아진다(⑶ 고리에 대한 개입).
- **PostgreSQL 물리 설계 위생**: `posts`의 `fillfactor`를 낮춰 HOT 업데이트 여지를 넓힌다. 새 버전이 같은 페이지 안에서 소화되면 인덱스 갱신과 bloat 확산이 준다. 그리고 카운터 컬럼에는 인덱스를 걸지 않는다.

그리고 결정의 순서를 잊지 않는다 — **이 카운터가 "정확해야 하는 숫자"인지 "대략 맞으면 되는 숫자"인지가 먼저다.** 조회수는 뒤쪽이라 비동기·외부 카운터가 성립하지만, 결제 잔액이나 재고는 앞쪽이라 같은 처방을 쓰면 안 된다.

## 4. 꼬리질문 대비 포인트

### "posts.comment_count 반정규화 — 무엇을 대가로 지불했고 어떻게 관리하나요?"

대가: **갱신 정합성.** 댓글이라는 원본과 카운트라는 사본이 어긋날 수 있는 부채가 생기고, 모든 댓글 쓰기 경로가 카운트 갱신 의무를 영구히 짊어진다.

관리 장치 3단 — ① **같은 트랜잭션**으로 묶어 한쪽만 반영된 채 커밋되는 경로 차단(대신 댓글 쓰기가 posts 갱신 실패 시 함께 롤백되는 결합 비용), ② **원자적 UPDATE**(`SET comment_count = comment_count + 1`)로 읽고-더하고-쓰는 lost update 차단, ③ **주기적 보정 배치**로 그래도 새는 드리프트를 되돌리는 안전망. 셋이 각각 다른 실패 원인(단일 요청의 원자성 / 동시 요청의 격리 / 코드 밖 변경)에 대응한다는 것까지 붙이면 "대가를 관리해본 사람"의 답이 된다.

### "초당 수백 개 댓글이 달리는 인기 글이 되면 이 구조에서 무슨 일이 벌어지나요?"

사슬을 이름으로 완주한다 — 모든 트랜잭션이 같은 posts 행을 UPDATE하는 **핫 로우**가 되고, **락 경합** → 락은 한 번에 하나만 통과시키므로 **사실상 직렬화**(서버 증설 무효) → 락 대기로 **트랜잭션 장기화** → 대기 중에도 커넥션을 쥐고 있으므로 **커넥션 풀 고갈** → 풀은 서비스 공용이라 무관한 요청까지 타임아웃되는 **전 서비스 전파.**

PostgreSQL이면 두 번째 축을 덧붙인다 — UPDATE마다 **새 튜플 버전**이 쌓여 페이지 여유가 마르고, HOT이 깨지면 다른 인덱스까지 갱신되며, autovacuum이 못 따라잡아 bloat이 남는다.

이어서 처방을 고리에 연결한다 — 쓰기 수렴을 푸는 비동기 집계·카운터 분산·외부 카운터, 락 보유 시간을 줄이는 UPDATE 위치 조정, `fillfactor` 조정. **"성능 저하"라고 답하는 순간 이 질문의 목적(비용을 사슬로 말하는가)에서 탈락한다.**

### "같은 트랜잭션 + 원자적 UPDATE로 다 묶어도 1년 뒤 어긋날 수 있다 — 왜, 그리고 장기적으로 어떻게 유지하나요?"

**불변식이 DB 제약이 아니라 애플리케이션 관례에 살기 때문.** FK처럼 DB가 지키는 규칙은 어떤 경로로 와도 뚫리지 않지만, "댓글을 건드리면 카운트도 갱신한다"는 코드의 약속일 뿐이라 — 약속을 모르는 새 코드 경로(일괄 삭제 API), 애플리케이션을 거치지 않는 DB 직접 수정, 정의가 누락된 신규 상태(블라인드 처리)가 뚫는다.

장기 유지는 **드리프트를 전제로 한 주기적 보정 배치**(원본 기준 재계산)가 답이며, 이것은 버그 대응이 아니라 설계에 처음부터 포함되는 안전망이다. 트리거로 관례를 DB 안으로 옮기면 "직접 수정"과 "새 코드 경로"는 막히지만, 트리거를 꺼 두는 대량 적재 구간이 다시 구멍이 되므로 보정 배치는 여전히 남는다.

### "반정규화를 하기 전에 먼저 검토해야 할 것은 무엇인가요?"

순서가 답이다.

① **실측** — `EXPLAIN (ANALYZE, BUFFERS)`와 `pg_stat_statements`로 조인·집계가 진짜 병목인지 확인한다("느릴 것 같아서"는 근거가 아니다).

② **더 싼 수단 먼저** — 인덱스 추가(`comments(post_id)` 인덱스만 있어도 `count(*)`는 `Index Only Scan`으로 센다 — VACUUM이 visibility map을 신선하게 유지한다는 전제에서), 쿼리 형태 변경(목록 20건을 먼저 자르고 그 20건만 상관 서브쿼리로 세면 집계 범위가 전체에서 20건으로 준다), 애플리케이션·캐시 계층(자주 읽는 목록이면 캐시 적중이 집계 자체를 없앤다). 인덱스는 되돌리기 쉽고 캐시는 스키마를 안 건드리는 반면, 반정규화 컬럼은 **모든 쓰기 경로에 영구적 갱신 의무**를 새기는 가장 비싼 수단이므로 마지막에 꺼낸다.

③ 그래도 필요하면 **대가 지불 준비(관리 장치 3단)와 함께** 도입한다.

### "주문 테이블에 상품명·가격을 복사해 두는 것도 반정규화인가요? 상품명이 바뀌면 동기화 배치를 돌려야 하나요?" (시니어 변별 포인트 · 가산점 포인트)

함정 질문이다 — **동기화하면 안 되는 중복**이 존재한다.

`orders.product_name`과 `orders.price`는 "지금의 상품 정보"의 사본이 아니라 **"주문 시점에 무엇을 얼마에 샀는가"라는 역사적 사실의 스냅샷**이다. 상품명이 바뀌거나 가격이 인상됐다고 과거 주문의 값을 동기화하면 영수증·정산·환불 근거가 파괴된다 — 여기서는 **원본과 어긋나는 것이 정합성**이다.

즉 중복을 보면 먼저 물어야 한다: "이 사본이 가리키는 사실이 **현재의 사실**(comment_count — 어긋나면 오류, 동기화 장치 필요)인가, **과거 시점의 사실**(주문 스냅샷 — 동기화가 오히려 오류)인가." 이 구분 없이 "중복은 다 동기화"로 접근하면 반정규화와 스냅샷을 같은 것으로 취급하는 것이고, 구분해서 말하면 중복의 의미론까지 설계해본 사람으로 변별된다.

### "MySQL로 물어보면 답이 달라지는 부분은?" (경험 대조)

네 지점이다.

① **카운터 UPDATE의 저장 비용** — InnoDB는 행을 제자리에서 고치고 옛 값을 언두 로그로 빼내지만, PostgreSQL은 새 튜플 버전을 삽입하고 옛 버전을 죽은 튜플로 남긴다. 락 직렬화 사슬은 둘 다 같지만 PostgreSQL은 그 위에 bloat과 VACUUM 추격이 한 겹 더 있다.

② **같은 값으로의 UPDATE** — MySQL은 값이 안 바뀌면 행을 건드리지 않지만, PostgreSQL은 값이 같아도 새 버전을 쓴다. 그래서 보정 배치의 `IS DISTINCT FROM` 가드가 PostgreSQL에서는 선택이 아니라 필수다.

③ **문법** — 보정 배치는 PostgreSQL이 `UPDATE ... FROM`, MySQL이 `UPDATE ... JOIN`이고, MySQL의 `SET p.col = ...`처럼 SET에 테이블 한정자를 붙이면 PostgreSQL은 에러다.

④ **도구** — materialized view는 PostgreSQL에만 있고(MySQL은 집계 테이블 + 배치를 직접 짠다), JSON 부분 갱신은 반대로 MySQL 8.0에만 있다(PostgreSQL `jsonb`는 값 전체 재기록). 컬럼 추가는 PostgreSQL 11+가 상수 DEFAULT를 카탈로그만 바꾸고 MySQL 8.0은 `ALGORITHM=INSTANT`로 같은 효과를 내는데, PostgreSQL은 ACCESS EXCLUSIVE 대기열이 뒤의 SELECT까지 세우므로 `lock_timeout`이 붙어야 한다.

## 한 줄 요약

**정규화는 "하나의 사실은 한 곳에만"으로 수정 이상(중복된 사실 중 일부만 고쳐 DB가 두 가지 답을 하게 되는 상태)을 구조적으로 차단하고, 반정규화는 조회 패턴을 위해 의도적으로 중복·연산 값을 두되 그 대가(갱신 정합성)를 관리 장치와 함께 지불하는 결정이다. 관리 장치 3단은 서로 다른 실패 원인에 각각 대응한다 — 같은 트랜잭션(단일 요청의 원자성) + 원자적 UPDATE(동시 요청의 격리) + 보정 배치(코드 밖에서 오는 변경). 선택 기준은 읽기:쓰기 비율 · 실측 병목 · 인덱스/캐시 선행 검토 · 대가 지불 준비의 4축이고, PostgreSQL의 generated column·트리거·materialized view는 관리 장치 일부를 DB 안으로 옮겨 주되 보정 배치를 없애 주지는 않는다. 핫 로우의 비용은 락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파라는 이름 붙은 사슬로 말하고, PG에서는 UPDATE마다 쌓이는 죽은 튜플(bloat)이 그 위에 얹힌다.**
