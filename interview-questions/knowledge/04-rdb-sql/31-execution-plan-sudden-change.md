# 실행 계획의 갑작스러운 변경 — 플래너는 "통계를 입력받는 함수"다, 입력이 바뀌면 출력이 바뀐다

> 핵심 관전 포인트: **PostgreSQL 플래너는 쿼리를 "계산"하는 계산기가 아니라, 통계·확장 통계·파라미터 값·비용 상수를 입력으로 받아 후보 계획들의 비용을 비교하는 함수다. 코드도 쿼리도 안 바꿨는데 계획이 바뀌었다면 셋 중 하나다 — ① 입력이 바뀜(autoanalyze, 통계 노후, n_distinct 오추정, MCV 목록 교체, **파라미터 값을 안 보기로 한 제네릭 계획 전환**), ② 후보가 바뀜(인덱스 추가·삭제·INVALID), ③ 함수가 바뀜(GUC 변경, 메이저 업그레이드 — **`pg_upgrade`는 통계를 안 옮긴다**). PostgreSQL에는 **index dive도, 힌트 문법도, INVISIBLE 인덱스도 없다.** 그래서 통계가 유일한 진실이고 대응 순서가 강제로 고정된다 — **`ANALYZE` → statistics target 상향 → `CREATE STATISTICS` → 비용 파라미터 국소 교정 → 부분·복합 인덱스로 후보 단일화 → 최후에 `pg_hint_plan`.** 진단도 사다리다: 느려진 시각 특정 → `pg_stat_statements`의 "건당 읽은 블록" 비교 → `auto_explain` 로그의 계획 diff → `last_autoanalyze`·`pg_stats` 확인 → 분포 확인. **확장을 깔아야 계획을 고정할 수 있다는 사실 자체가 "그건 최후 수단"이라는 설계 메시지다.**

---

## 0. 질문 + 의도

**질문**: "잘 돌던 쿼리의 실행 계획이 어느 날 갑자기 바뀌어 느려졌습니다. 가능한 원인과 대응은?"

관련 질문: "배포도 없었는데 어제부터 DB CPU만 올랐습니다. '변경이 없다'는 전제를 어떻게 검증하고, 원인 후보를 어떻게 좁혀가나요?" (같은 장 중급 문항 — [별도 문서](./22-db-cpu-spike-without-deployment.md). 그쪽은 "변경 없음"이라는 전제를 의심하며 **원인 전체를 넓게** 훑고, 이 문서는 그중 가장 흔한 한 갈래인 **"실행 계획이 바뀌었다"를 깊게** 판다.)

**출제 의도**: rationale의 표현 그대로 — "'코드도 쿼리도 안 바꿨는데 느려졌다'의 단골 원인(통계 정보 갱신, 데이터 분포 변화). **DB를 정적인 계산기가 아니라 상태에 따라 판단이 바뀌는 시스템으로 이해하는지** — 힌트로 고정하는 것의 트레이드오프까지 가면 상급이다."

즉 이 문항이 재는 것은 두 층이다. 아래층은 **모델**이다 — "같은 SQL을 넣으면 같은 계획이 나온다"는 계산기 모델을 버리고, "플래너는 통계라는 입력으로 비용을 계산하는 함수라서 입력이 바뀌면 출력이 바뀐다"는 모델을 갖고 있는가. 이 모델이 있어야 원인 후보가 목록으로 인출되고 진단 순서가 논리적으로 나온다. 위층은 **판단**이다 — 계획을 고정하는 수단이 "문제 해결"이 아니라 "플래너의 판단 기능을 끄는 것"임을 알고 그 대가와 기한을 붙여 쓰는가. **PG에서는 이 위층이 특히 선명하다** — "고정한다"는 선택지 자체가 확장 설치라는 문턱 뒤에 있어, 대응이 자연히 "입력을 바로잡는다"에서 출발한다.

이 문서는 모의면접 **전** 학습용이고, 후보자의 횡단 약점 네 가지를 겨냥한다 — ① 인과를 "메커니즘 사슬"로 서술하기(§1·§2), ② 대응책의 대가를 한 호흡에 양면으로(§3-3·§3-4), ③ 안전망을 코드·설정·잡으로 고정하기(§3-5~§3-9), ④ "원인 후보 N종"과 "대응 사다리"를 목록으로 인출하기(§2-6·§3-1).

**이 문서가 다루지 않는 것.** `EXPLAIN` 출력의 노드를 읽는 법(`cost`·`rows`·`width`·`actual time`·`loops`·`Buffers`가 각각 무엇인지, 트리를 어느 방향으로 읽는지)은 [실행 계획 읽기와 느린 쿼리 개선 프로세스](10-explain-and-slow-query-process.md) §1에 전부 있다. 여기서는 그것을 **아는 상태**를 전제하고, "왜 플래너가 인덱스를 일부러 버리는가"의 비용 모델은 [인덱스를 걸었는데도 풀스캔](02-index-not-used-full-scan.md) §4에 맡긴다. 이 문서가 얹는 것은 딱 하나다 — **"어제까지 옳던 판단이 오늘 왜 바뀌는가."**

## 1. 모델 — 플래너는 함수다: 계획 = f(후보 집합, 입력)

### 1-1. 계산기 모델을 버린다 — 이 문서의 지도

먼저 머릿속 모델을 교체한다. 계산기는 `2 + 3`을 넣으면 언제나 `5`다. 같은 입력에 같은 출력이 나오는 것이 계산기의 정의다. **플래너는 계산기가 아니다.** 같은 SQL을 넣어도 오늘과 어제의 출력이 다를 수 있고, 그건 고장이 아니라 설계다.

플래너를 함수로 보면 이렇게 생겼다.

```text
                        계획 = f( 후보 집합 , 입력 )

  ┌─ 후보 집합 ────────────────┐        ┌─ 입력 ─────────────────────────────────────────┐
  │ 이 SQL을 실행할 수 있는     │        │ ① 영속 통계                                     │
  │ "물리적 방법"들의 목록      │        │    pg_class : reltuples, relpages, relallvisible│
  │                            │        │    pg_stats : n_distinct, most_common_vals/freqs│
  │ · 어느 인덱스를 쓸까        │        │               histogram_bounds, correlation,    │
  │ · Seq / Index / Index Only │        │               null_frac                         │
  │   / Bitmap 중 어느 스캔     │        │    → ANALYZE 가 채운다                          │
  │ · Nested Loop / Hash /     │        │                                                 │
  │   Merge 중 어느 조인        │        │ ② 확장 통계 (CREATE STATISTICS)                 │
  │ · 조인 순서                 │        │    ndistinct / dependencies / mcv               │
  │ · 병렬로 나눌까             │        │    → 만들지 않으면 "컬럼끼리 서로 독립"이라 가정  │
  └──────────┬─────────────────┘        │                                                 │
             │                          │ ③ 쿼리에 들어온 값                               │
             │                          │    커스텀 계획 → 실제 값으로 선택도 계산          │
             ▼                          │    제네릭 계획 → 값을 안 보고 평균 선택도로 계산   │
  ┌────────────────────────────┐        │                                                 │
  │  후보마다 "예상 비용"을      │◀───────┤ ④ 비용 상수·스위치 (GUC)                        │
  │  계산해서 가장 싼 것을 고른다 │        │    seq_page_cost 1.0, random_page_cost 4.0,     │
  │       비용 = g(입력)        │        │    cpu_tuple_cost, effective_cache_size,        │
  └──────────┬─────────────────┘        │    work_mem, enable_*, jit, 병렬 설정            │
             │                          └─────────────────────────────────────────────────┘
             ▼
        실행 계획 (EXPLAIN 이 보여 주는 것)
```

이 그림에서 곧바로 나오는 결론이 이 문서의 전부다.

> **코드도 쿼리도 안 바꿨는데 출력(계획)이 바뀌었다.** 함수의 출력이 바뀌는 경우는 셋뿐이다 — **입력이 바뀌었거나, 후보 집합이 바뀌었거나, 함수 자체가 바뀌었거나.**

그래서 "실행 계획이 왜 바뀌었나요"라는 질문은 자동으로 세 개의 질문으로 쪼개진다.

| 질문 | 무엇을 확인하나 | §2-6의 원인 |
|---|---|---|
| **입력이 바뀌었나?** | `last_autoanalyze` 시각, `pg_stats`의 값, 파라미터를 보고 있나 | ①②③④⑤⑥⑨⑩ |
| **후보 집합이 바뀌었나?** | 인덱스 목록 diff, `pg_index.indisvalid` | ⑦ |
| **함수 자체가 바뀌었나?** | `pg_settings` diff, `version()` | ⑧ |

§2-6의 원인 10종은 전부 이 세 칸 중 하나에 들어간다. **목록을 외우는 게 아니라 이 세 칸에서 꺼내는 것**이고, 그래서 면접장에서 긴장해도 인출된다.

> **내비게이션 비유**
> 같은 집에서 같은 회사로 가는데 어느 날 내비가 다른 길을 안내한다. 지도(쿼리)는 그대로다. 바뀐 것은 교통정보(통계)다. 교통정보가 갱신되면 안내가 바뀌는 건 정상이고, 대개 더 나은 길이다. 문제는 교통정보가 **낡았거나**(통계가 현실과 어긋남), **표본이 적어 엉뚱하게 잡혔거나**(샘플링 오차), **"목적지를 안 물어보고 평균적인 통근자 기준으로" 짜였을 때**(제네릭 계획)다. "내비가 미쳤다"가 아니라 "내비가 무슨 정보를 보고 그렇게 판단했나"를 묻는 것이 진단의 시작이다.

### 1-2. 입력 ① 영속 통계 — 통계란 무엇이고, 실제로 무엇이 들어 있나

**통계(statistics)란 무엇인가부터 정의한다.** 플래너는 "이 조건에 몇 행이나 맞을까"를 알아야 비용을 계산할 수 있는데, 매번 테이블을 세어 보면 그 자체가 쿼리 한 번 값이다. 그래서 **테이블 전체를 세지 않고도 그 답을 추정할 수 있도록, 미리 표본으로 떠 둔 요약**이 통계다. 여론조사가 국민 전체에게 안 묻고 1,000명 표본으로 지지율을 추정하는 것과 정확히 같은 구조다.

이 요약을 만드는 명령이 `ANALYZE`다. 테이블에서 무작위 표본을 뽑아 분포를 요약해 시스템 카탈로그 `pg_statistic`에 저장하고, 사람이 읽는 뷰가 `pg_stats`다. 크기 정보는 `pg_class`에 있고, autovacuum이 백그라운드에서 이 일을 대신 돌려 준다(autoanalyze).

```sql
-- 크기 + "전부 가시"로 표시된 페이지 수(Index Only Scan 비용의 입력)
SELECT relname, reltuples::bigint, relpages, relallvisible
FROM pg_class WHERE relname = 'orders';

-- 언제 통계를 떴나 + 그 뒤로 몇 행이 바뀌었나 (autoanalyze 임계 추적의 핵심)
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables WHERE relname = 'orders';

-- 컬럼 단위 분포 — 세로로 펼쳐 보는 것이 읽기 쉽다(psql 에서 \x on)
SELECT attname, null_frac, n_distinct, correlation,
       most_common_vals, most_common_freqs, histogram_bounds
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';
```

**실제 값을 한 컬럼만 눈으로 보자.** `orders.status`는 값이 세 개뿐인 컬럼이다.

```text
attname            | status
null_frac          | 0
n_distinct         | 3
most_common_vals   | {PAID,PENDING,FAILED}
most_common_freqs  | {0.9703,0.0201,0.0096}
histogram_bounds   | (없음)              ← 값이 세 개뿐이라 전부 MCV 에 들어갔다. 남는 값이 없으니 히스토그램도 없다
correlation        | 0.213
```

이 여덟 줄로 플래너가 하는 일은 이렇다. `WHERE status = 'FAILED'`가 들어오면 MCV 목록에서 `FAILED`를 찾아 빈도 **0.0096**을 꺼내고, `reltuples`가 1,500만이면 **1,500만 × 0.0096 = 144,000행**이 걸린다고 추정한다. 이 추정 하나에서 "인덱스를 탈까 전부 읽을까"가 갈린다.

같은 방식으로 `user_id`를 보면 이렇게 나온다. 이 컬럼이 §2-1 사고의 현장이다.

```text
attname            | user_id
null_frac          | 0
n_distinct         | 16685                ← 실제 서로 다른 사용자는 100만 명이 넘는다. 60배 과소 추정.
                                          ← 고카디널리티 컬럼에서 PostgreSQL 이 늘 이렇게 낮게 잡는다(1-7)
most_common_vals   | {70001,70002, ... }  ← 주문이 몰린 가맹점 계정 100개
most_common_freqs  | {0.125,0.061, ... }
histogram_bounds   | {1,10432,20981, ... } ← MCV 에 못 든 나머지 값들의 범위 분포
correlation        | 0.031                ← user_id 순서와 힙의 물리 순서는 거의 무관
```

각 칸이 어디에 쓰이는지가 핵심이다.

| 통계 칸 | 하는 일 | 이 칸이 흔들리면 |
|---|---|---|
| `reltuples` / `relpages` | "전부 읽으면 얼마"(Seq Scan 비용)의 밑변 | 테이블이 자란 것만으로 계획이 바뀐다(원인 ⑨) |
| `n_distinct` | **MCV에 없는 값**의 등호 선택도를 준다 | 등호 조건 하나의 추정이 자릿수로 틀린다(원인 ③) |
| `most_common_vals` / `most_common_freqs`(MCV) | 자주 나오는 값과 그 비율. **목록 크기가 statistics target에 비례**한다 | 값이 목록에 들어오거나 밀려나면 그 값의 추정이 불연속하게 점프한다(원인 ⑤) |
| `histogram_bounds` | MCV에 못 든 값들의 범위 분포 → `created_at >= ?` 같은 범위 조건의 선택도 | 새로 적재된 구간이 히스토그램 밖이면 "거의 안 걸린다"고 본다(원인 ②) |
| `correlation` | 컬럼 값 순서와 힙의 물리 순서의 상관계수(-1~1). 1에 가까우면 인덱스 순서로 읽어도 힙 접근이 사실상 순차 | 랜덤 I/O 가정이 세지거나 약해진다 |
| `relallvisible` | visibility map에서 "전부 가시"인 페이지 수 | **Index Only Scan의 비용 추정에 직접 들어간다**(원인 ⑩) |

**등호 조건의 선택도를 정하는 규칙은 세 갈래**이고, 이 세 갈래를 구분하는 것이 §2 전체의 열쇠다.

```text
  WHERE col = ? 의 선택도

  ⑴ 값이 상수이고 MCV 목록에 있다
       → 그 값의 most_common_freqs 를 그대로 쓴다.  (가장 정확하다)

  ⑵ 값이 상수인데 MCV 목록에 없다
       → (1 - MCV 빈도 합 - null_frac) / (n_distinct - MCV 개수)
       → "MCV 가 안 먹은 나머지 확률을, 나머지 값들이 똑같이 나눠 갖는다"는 가정.
          그 값이 실제로는 나머지 중 유난히 큰 값이면 여기서 크게 틀린다.

  ⑶ 값을 아예 모른다 (제네릭 계획, §1-4)
       → 1 / n_distinct.  단 MCV 최빈값의 빈도를 넘지는 않게 상한을 건다.
       → "평균적인 값 하나가 걸린다"는 가정.
```

⑴에서 ⑵로 넘어가는 순간(= 어떤 값이 MCV에서 밀려나는 순간) 추정이 **연속적으로 조금 변하는 게 아니라 계단처럼 점프한다.** §2-1의 사고가 정확히 이 계단이다.

### 1-3. 입력 ② 확장 통계 — "컬럼들이 서로 독립"이라는 기본 가정

기본 통계는 **컬럼 하나씩만** 안다. 그래서 조건이 여럿이면 플래너는 **선택도를 곱한다.** 확률에서 독립사건의 동시 확률을 곱하는 것과 같은 계산이고, 그 "독립"이라는 전제가 여기 숨어 있다.

```text
  city = '서울'      선택도 0.20    (전체의 20%)
  zipcode = '06236'  선택도 0.001   (전체의 0.1%)
  --------------------------------------------------
  둘 다 참일 확률(플래너의 가정) = 0.20 × 0.001 = 0.0002 = 0.02%
  1,000만 건이면 추정 2,000행

  그런데 06236 은 애초에 서울에만 있는 우편번호다.
  "서울이면서 06236" = "06236" 과 같은 집합 → 실제 0.1% = 10,000행
  → 10,000 ÷ 2,000 = 5배 과소 추정
```

과소 추정은 Nested Loop·Index Scan 쪽으로 계획을 밀고, 실제 행이 그보다 훨씬 많으면 그 계획이 자릿수로 느려진다. 이 곱셈 가정을 깨는 도구가 확장 통계다.

```sql
CREATE STATISTICS stat_orders_city_zip (dependencies, ndistinct, mcv)
  ON city, zipcode FROM orders;
ANALYZE orders;                              -- 만들고 나서 ANALYZE 를 해야 비로소 채워진다
```

**중요한 함정 — 확장 통계는 "만들지 않으면 없다".** 즉 상관관계가 강한 컬럼 조합은 기본적으로 **항상 오추정 상태**이고, 데이터가 자라 그 오차의 절대량이 임계를 넘는 날 계획이 뒤집힌다. "어제까지 괜찮았는데"의 흔한 정체다.

### 1-4. 입력 ③ 쿼리에 들어온 값 — 커스텀 계획과 제네릭 계획

이 절이 PostgreSQL 고유의 사고를 만드는 자리다. 결론("여섯 번째 실행부터 느려진다")을 먼저 말하면 마법처럼 들리므로, 다섯 단계를 순서대로 밟는다.

**⑴ 준비문(prepared statement)이 무엇인가.**

준비문은 **SQL 문장을 서버에 한 번 등록해 두고, 그 뒤로는 값만 바꿔 실행하는 것**이다. 값이 들어갈 자리는 `$1`, `$2` 같은 자리표시자(placeholder)로 남겨 둔다.

```sql
PREPARE p(bigint) AS SELECT * FROM orders WHERE user_id = $1 ORDER BY id DESC LIMIT 20;
EXECUTE p(42);        -- 값만 바꿔 여러 번
EXECUTE p(7001);
```

JDBC의 `PreparedStatement`가 바로 이것이고, 자바 진영에서는 "SQL 인젝션을 막으려고" 쓰는 것으로 배우지만 서버 쪽 이유는 다르다 — **파싱과 계획 수립을 아끼려고** 쓴다.

**⑵ 매번 계획을 짜는 것은 비싸다 — 그래서 재사용하고 싶다.**

`EXPLAIN` 출력 맨 아래에 찍히는 `Planning Time`이 그 비용이다. 조인이 여럿인 쿼리는 계획 수립에 수 ms가 들 수 있는데, 실행이 0.5ms인 짧은 쿼리를 초당 수천 번 돌리면 **계획 수립이 실행보다 비싸진다.** 그러니 한 번 짠 계획을 재사용하고 싶은 동기가 생긴다.

**⑶ 그런데 값에 따라 최적 계획이 달라진다 — 딜레마.**

`user_id = 42`(주문 8건)와 `user_id = 7001`(대형 가맹점, 주문 150만 건)은 같은 SQL이지만 최적 계획이 다르다. 앞은 인덱스로 8건 집어 오는 게 맞고, 뒤는 전혀 다른 계획이 맞다. **계획을 재사용하려면 값을 안 볼 수밖에 없고, 값을 안 보면 최적이 아닐 수 있다.** 이것이 딜레마다.

**⑷ PostgreSQL의 타협.** 이 딜레마를 이렇게 절충한다.

| 그 준비문의 계획 수립 회차 | 서버가 하는 일 | 쓰이는 계획 |
|---|---|---|
| 1~5회 | 매번 들어온 **실제 값**으로 계획을 세우고, 그 비용을 누적한다 | **커스텀 계획**(custom plan) |
| 6회째 | 커스텀 다섯 번의 **평균 비용**을 계산한다. 그리고 **값을 모르는 채로** 계획을 한 번 만들어(제네릭 계획) 그 추정 비용과 비교한다 | 아래 판정에 따라 |
| 판정 | **제네릭의 추정 비용 < 커스텀 평균 비용** → 이후 제네릭을 재사용<br>그렇지 않으면 → 계속 커스텀 | 고정 |

**⑸ 그래서 "여섯 번째 실행부터 느려진다"**는 증상이 나온다.

주의할 점 하나 — 회차를 세는 주체가 둘이다. **pgjdbc는 같은 `PreparedStatement`를 5회 실행해야 비로소 서버 준비문으로 전환한다**(`prepareThreshold` 기본 5). 그전까지는 이름 없는(unnamed) 문장이라 서버가 매번 값을 보고 새로 계획한다. 그러니 애플리케이션 관점에서는 "열 번쯤 실행한 뒤"에 바뀌고, 서버 관점에서는 정확히 "여섯 번째 계획 수립"에서 바뀐다. psql에서 `PREPARE`/`EXECUTE`로 직접 재현하면 딱 여섯 번째다.

**여기서 반드시 짚어야 할 것 — 채택 조건의 방향이다.** 제네릭 계획은 "커스텀보다 싸 **보일 때만**" 채택된다. 그러므로 사고는 이렇게 난다.

```text
  제네릭이 채택되는 조건 : 제네릭의 "추정" 비용 < 커스텀 다섯 번의 "추정" 평균

  → 제네릭이 평균 선택도(1/n_distinct)로 계산한 결과가 실제 값보다 "적은 행"으로 나올 때
    = 우리가 실제로 조회하는 값이 평균보다 훨씬 흔한 값일 때
    → 플래너는 "몇 행 안 걸리네"라고 믿고 인덱스 스캔·Nested Loop 같은 계획을 고른다
    → 그 계획이 싸 보이므로 채택된다
    → 실행하면 몇십만~몇백만 행을 그 계획으로 처리한다 → 폭주

  반대로 실제 값이 평균보다 희귀하면 제네릭은 "많이 걸린다"고 과대 추정해
  Seq Scan 같은 비싼 계획을 만들고, 그건 커스텀 평균보다 비싸므로 애초에 채택되지 않는다.
  → 이 경우엔 사고가 안 난다.
```

즉 **제네릭 계획 사고의 피해자는 "우리 서비스에서 유난히 흔한 값만 조회하는 화면"**이다 — 대형 가맹점 전용 정산 화면, 특정 테넌트만 보는 관리 화면 같은 것들. §2-2가 그 사례다.

증상의 지문도 독특하다. **애플리케이션을 재시작하면 잠깐 빨라졌다가 다시 느려진다.** 커넥션이 새로 나면 준비문 캐시가 비어 다시 커스텀 계획부터 시작하기 때문이다. HikariCP `maxLifetime`으로 커넥션이 주기적으로 교체되는 환경이면 **몇십 분 주기로 빨라졌다 느려졌다** 하는 모양으로도 온다.

확인과 통제 수단은 셋이다.

```sql
-- ⑴ 파라미터를 채우지 않고 제네릭 계획을 그대로 본다 (PG 16+)
EXPLAIN (GENERIC_PLAN)
SELECT * FROM orders WHERE user_id = $1 ORDER BY id DESC LIMIT 20;

-- ⑵ 손으로 재현한다 — 여섯 번째 EXECUTE 에서 계획이 바뀌는 것을 눈으로 본다
PREPARE p(bigint) AS SELECT * FROM orders WHERE user_id = $1 ORDER BY id DESC LIMIT 20;
EXPLAIN EXECUTE p(7001);   -- 1~5회는 커스텀 계획, 6회째부터 제네릭인지 확인

-- ⑶ 통제: 이 세션/롤/DB 에서는 항상 값을 보고 계획하게 한다 (= 제네릭 전환을 끈다)
SET plan_cache_mode = force_custom_plan;                       -- 지금 세션만(검증용)
ALTER ROLE app_user SET plan_cache_mode = force_custom_plan;   -- 이 앱 롤만. 새 커넥션부터
ALTER DATABASE shop SET plan_cache_mode = force_custom_plan;   -- 더 넓게
-- 반대로 force_generic_plan 은 "항상 제네릭" — 계획 수립 비용을 아껴야 하는 특수한 경우에만
```

> **MySQL 대조**: MySQL은 실행할 때마다 실제 값으로 다시 최적화하므로 이 제네릭 계획 함정이 **없다.** 대신 "같은 SQL이 값에 따라 다른 계획을 갖는 것이 정상"이라는 다른 얼굴로 온다 — 주문 8건인 사용자와 150만 건인 대형 가맹점은 같은 SQL, 다른 최적 계획이다. 즉 스큐(편중)라는 뿌리는 같고 증상만 다르다: MySQL은 "특정 값에서만 느리다", PostgreSQL은 "여섯 번째 실행부터 모든 값에서 느리다".

### 1-5. 입력 ④ 비용 상수와 스위치 — 함수의 계수

플래너의 산술에 들어가는 계수들은 GUC(Grand Unified Configuration, PostgreSQL의 설정 파라미터)다.

- `seq_page_cost`(1.0) / `random_page_cost`(4.0) — **랜덤 대 순차의 비율**이 인덱스 스캔과 Seq Scan의 손익분기를 정한다. 회전 디스크 시절의 4.0을 SSD에서 그대로 두면 플래너가 인덱스를 과소평가한다(1.1 근처로 낮추는 것이 통례).
- `effective_cache_size` — "이 정도는 캐시에 있겠지"의 짐작값. 크게 잡을수록 반복 인덱스 접근을 싸게 본다. `cpu_tuple_cost` 계열은 행·연산자당 CPU 비용이다.
- `work_mem`(+ `hash_mem_multiplier`) — 해시·정렬이 메모리에 들어가는지. 이 값이 바뀌면 Hash Join ↔ Merge Join, quicksort ↔ external merge가 갈린다.
- `enable_seqscan` 류 스위치 — **운영 설정이 아니라 가설 검증 도구다**(§2-5).
- `jit`와 그 비용 임계 — 짧고 자주 도는 쿼리에 JIT가 붙으면 컴파일 시간이 실행 시간을 압도할 수 있다. 병렬 설정(`max_parallel_workers_per_gather` 등)은 테이블이 임계 크기를 넘으면 Parallel Seq Scan을 **후보에 추가**한다.

**(가산점 포인트) GUC는 계층적이다.** 전역(postgresql.conf) → DB(`ALTER DATABASE`) → 롤(`ALTER ROLE`) → 세션(`SET`) → 트랜잭션(`SET LOCAL`) 순으로 좁혀 덮어쓸 수 있다 — **"전역을 바꾸지 않고 이 앱 롤에서만" 비용 파라미터를 교정**할 수 있고, §3-3 카드 4가 이 성질 위에 서 있다.

**(가산점 포인트) PostgreSQL 플래너는 "지금 캐시에 뭐가 올라와 있는지"를 보지 않는다.** `effective_cache_size`는 정적인 짐작값일 뿐이다. 그래서 **"재시작 직후 계획이 달라졌다"는 PostgreSQL에서는 성립하지 않는다** — 재시작 후 느린 것은 같은 계획이 캐시 미스로 디스크를 읽는 것이고 `BUFFERS`의 `shared read`가 그것을 증명한다.

> **MySQL 대조**: MySQL 8의 비용 모델은 "이 인덱스가 버퍼 풀에 얼마나 올라와 있나" 추정치를 참고하므로 재시작·failover 직후와 예열 뒤의 **계획 자체가** 다를 수 있다. PostgreSQL에는 그 입력이 없어 위의 구분이 더 깔끔하게 떨어진다.

### 1-6. 후보 집합 — 무엇이 "후보"인가

입력 넷을 봤으니 함수의 다른 인자인 후보 집합도 한 줄 정의한다. **후보 집합은 "이 SQL을 실행할 수 있는 물리적 방법들의 목록"**이다. 인덱스를 하나 만들면 후보가 늘고, 지우면 준다. 테이블이 임계 크기를 넘으면 병렬 계획이 후보에 추가되고, `CREATE INDEX CONCURRENTLY`가 실패해 `INVALID` 상태로 남은 인덱스는 **디스크에 존재하고 쓰기 비용도 내지만 후보에는 안 들어간다.**

여기서 §3-4의 근본 대응이 나온다 — **후보가 하나뿐이면 통계가 어떻게 흔들려도 계획은 안 흔들린다.** 입력을 정확하게 만드는 것보다 후보를 줄이는 쪽이 근본적인 이유다.

### 1-7. PostgreSQL에는 index dive가 없다 — 이 문서 전체의 전제

**index dive란 무엇인가.** MySQL은 `WHERE user_id = 42`처럼 **상수 조건**이 걸리면 통계를 믿지 않고, 계획을 세우는 그 시점에 **그 인덱스의 해당 범위에 실제로 들어가 대략 몇 행인지 세어 본다.** 인덱스 안으로 "잠수한다(dive)"는 이름이 여기서 나왔다. 그래서 MySQL에서는 단일 등호·범위 조건이 통계가 낡아도 비교적 정확하다.

**PostgreSQL은 그러지 않는다.** 상수 조건이든 파라미터든 선택도는 **오직 `pg_stats`의 MCV·히스토그램·n_distinct에서** 계산되고, 실측하러 인덱스에 들어가는 단계가 아예 없다. 플래너가 보는 것은 표본으로 뜬 요약 하나뿐이다.

```text
  MySQL          WHERE user_id = 42  →  통계로 1차 추정
                                     →  그 인덱스의 42 구간에 실제로 들어가 행 수를 센다 (index dive)
                                     →  훨씬 정확한 수를 얻는다

  PostgreSQL     WHERE user_id = 42  →  pg_stats 만 본다. 끝.
                                     →  통계가 낡았거나 표본이 편중됐으면 그대로 틀린다
```

이 한 문장에서 PostgreSQL 운영의 결론 세 개가 곧바로 나온다.

1. **통계가 낡으면 가장 단순한 등호 조건도 틀린다.** 대량 적재 직후가 특히 위험하다 — MySQL이었다면 dive가 새 데이터를 즉시 보지만, PostgreSQL은 `ANALYZE`가 돌기 전까지 옛 세계를 믿는다.
2. **그래서 `ANALYZE`가 1순위 대응이다.** 어떤 원인이든 통계 갱신을 먼저 해서 "입력이 낡은 건 아니다"를 배제하고 시작한다.
3. **분포가 급변해도 통계가 안 돌면 계획은 안 바뀐다.** 분포 변화가 계획을 바꾸려면 **반드시 그 사이에 ANALYZE가 있었다** — 진단에서 `last_autoanalyze` 시각이 결정적 단서가 되는 이유다.

### 1-8. 이 모델이 주는 첫 번째 결론

> **"실행 계획이 바뀌었다"는 결과이지 원인이 아니다.** 진단은 "어느 입력이, 언제, 왜 바뀌었나"를 찾는 일이고, 대응은 "그 입력을 바로잡을 것인가(`ANALYZE`·statistics target·확장 통계), 값을 다시 보게 할 것인가(`plan_cache_mode`), 후보를 줄여 흔들릴 여지를 없앨 것인가(인덱스 설계), 함수를 우회할 것인가(`pg_hint_plan`)"의 선택이다. 이 문장을 첫 답변으로 말하면 "정적인 계산기가 아니라 상태에 따라 판단이 바뀌는 시스템"이라는 이해가 첫머리에서 드러난다.

## 2. 동작·판별 — 사고 두 개를 숫자로, 그리고 원인 후보 10종

후보자의 최대 약점은 "통계가 바뀌어서 느려졌다"에서 멈추는 것이다. 그 사이의 칸을 숫자로 채운다.

**상황 고정.** `orders` 1,200만 건. 인덱스는 `orders_pkey(id)`와 `idx_orders_user(user_id)` 둘. 사용자 구성은 편중돼 있다 — **가맹점(입점 판매자) 계정 5,000개가 900만 건**을 갖고 있고(평균 1,800건, 최대 150만 건), **일반 사용자 100만 명이 300만 건**을 갖는다(평균 3건). 주문 목록 API의 쿼리는 이것 하나다.

```sql
SELECT * FROM orders WHERE user_id = $1 ORDER BY id DESC LIMIT 20;
```

플래너 앞에 놓인 **후보는 둘**이다. 이 둘의 이름을 A·B로 고정하고 문서 끝까지 쓴다.

```text
계획 A: idx_orders_user 로 이 사용자의 행을 전부 모아 → 힙에서 읽고 → id 로 정렬 → 앞 20건
        비용 ∝ (이 사용자의 "예상" 행 수) × (힙 랜덤 접근 비용) + 정렬 비용
        → 예상 행 수가 적을수록 싸다.

계획 B: orders_pkey 를 뒤에서부터 훑으며(id DESC 순서 그대로) user_id 로 거른다
        → 20건 모이면 Limit 이 중단시킨다. 정렬 노드가 아예 없다.
        비용 ∝ (전체 스캔 비용) × 20 / (이 사용자의 "예상" 행 수)
        → 예상 행 수가 많을수록(= 매치가 촘촘할수록) 싸다.

두 계획의 방향이 정반대다. 그래서 "예상 행 수" 하나가 뒤집히면 계획도 뒤집힌다.
그리고 그 예상 행 수를 정하는 것이 §1-2의 세 갈래 규칙이다.
```

아래 비용 숫자는 PostgreSQL 기본 비용 상수(`seq_page_cost` 1.0, `random_page_cost` 4.0, `cpu_tuple_cost` 0.01, `cpu_index_tuple_cost` 0.005, `cpu_operator_cost` 0.0025)와 페이지당 52행·인덱스 페이지당 367엔트리를 가정해 손으로 계산한 값이다. 실제 출력과 소수점까지 같지는 않지만 **대소 관계와 자릿수는 이대로**이고, 어느 쪽이 이기는지가 이 절의 전부다.

### 2-1. 사고 ① — 새벽 배치 한 번이 계획을 뒤집는 여섯 칸

**피해자는 가맹점 X**다. 주문 8만 건을 가진 중견 가맹점이고, 전체 1,200만 건의 0.667%를 차지해 `most_common_vals` 목록의 끝자락(100번째)에 실려 있다. 그래서 지금까지 플래너는 X의 행 수를 **정확히** 알고 있었다.

**평소(베이스라인).** X는 MCV에 있으므로 §1-2의 규칙 ⑴이 적용된다 — 빈도 0.006667을 그대로 써서 예상 행 수 = 1,200만 × 0.006667 = **80,000행**. 실제도 80,000행이니 추정이 맞다.

```text
  계획 B의 비용 = (전체 후방 스캔 571,559) × 20 / 80,000 = 142.89   → Limit cost 0.56..143.45
  계획 A의 비용 = 힙 랜덤 접근 80,000회 + 80,000행 정렬            → Limit cost 281,314.36
  → B가 A보다 1,961배 싸다. B 선택. 그리고 B가 실제로 옳다.
    20건을 모으려면 20 ÷ 0.006667 = 3,000행만 훑으면 된다.
```

```text
 Limit  (cost=0.56..143.45 rows=20 width=124) (actual time=0.09..3.91 rows=20 loops=1)
   ->  Index Scan Backward using orders_pkey on orders o
         (cost=0.56..571559.42 rows=80000 width=124) (actual rows=20 loops=1)
         Filter: (user_id = 70100)
         Rows Removed by Filter: 2981                  <- 3,000행쯤 훑고 20건을 채웠다. 정상.
         Buffers: shared hit=64
 Execution Time: 3.95 ms
```

**그날 밤 무슨 일이 있었나.** 신규 이관 가맹점 20곳의 과거 주문 **300만 건**이 새벽 배치로 들어왔다. 각 가맹점이 15만 건씩이다. 그 뒤 여섯 칸이 도미노처럼 넘어간다.

| # | 칸 | 배치 전 | 배치 후 | 무엇이 이 변화를 일으켰나 |
|---|---|---|---|---|
| 1 | **행 수** | 1,200만 | **1,500만** | 배치가 300만 건 INSERT |
| 2 | **autoanalyze 발동** | — | `n_mod_since_analyze` 300만 > 임계 **1,200,050** | 임계 = `autovacuum_analyze_threshold` 50 + `autovacuum_analyze_scale_factor` 0.1 × 1,200만 |
| 3 | **표본과 MCV 목록** | MCV 100칸 = 기존 상위 가맹점 100곳(X가 100번째) | MCV 100칸 중 **20칸을 신규 가맹점(각 1.0%)이 차지** → 하위 20곳이 밀려남. **X가 그중 하나** | ANALYZE가 표본 3만 행(= 300 × `default_statistics_target` 100)을 새로 떠서 목록을 다시 짬. **목록 크기는 100으로 고정**이라 들어오면 누군가는 나간다 |
| 4 | **X의 선택도 규칙** | 규칙 ⑴ — MCV 빈도 **0.006667** | 규칙 ⑵ — **(1 − 0.65) / (13,788 − 100) = 2.557e-05** | X가 MCV에서 빠져 "나머지 균등 분배" 대상이 됨. 0.65는 MCV 100개의 빈도 합, 13,788은 `n_distinct` 추정값, 100은 MCV 개수 |
| 5 | **추정 행 수** | 80,000 (실제와 일치) | 1,500만 × 2.557e-05 = **384** (실제 80,000 → **208배 과소**) | 규칙 ⑵의 "나머지 값들은 다 비슷하겠지"라는 가정이 X에게만 크게 틀림 |
| 6 | **선택된 계획** | **B** (cost 143.45) | **A** (cost 1,565.27). B는 이제 37,211로 보인다 | 예상 행 수가 384로 줄자 A의 비용이 (384행 × 랜덤 힙 접근 4.02) + 인덱스 접근 ≈ 1,549로 떨어지고, B의 비용은 714,449 × 20/384 = 37,211로 올랐다 — **방향이 정반대인 두 비용이 교차했다** |

계산을 한 줄씩 따라가면 이렇다.

```text
 4번 칸  선택도 = (1 - MCV 빈도 합 - null 비율) / (n_distinct - MCV 개수)
                = (1 - 0.65 - 0) / (13,788 - 100)
                = 0.35 / 13,688
                = 2.5570e-05

 5번 칸  추정 행 수 = 1,500만 × 2.5570e-05 = 383.6 → 384행
         실제       = 80,000행
         오차       = 80,000 / 384 = 208배 과소 추정

 6번 칸  계획 A 비용 ≈ 384행 × (랜덤 힙 접근 4.0 + CPU 0.015) + 정렬  ≈ 1,565
         계획 B 비용 ≈ 714,449 × 20 / 384                            ≈ 37,211
         → A 가 24배 싸 보인다. A 선택.
```

```text
 Limit  (cost=1565.22..1565.27 rows=20 width=124) (actual time=2401.7..2401.8 rows=20 loops=1)
   ->  Sort  (cost=1565.22..1566.18 rows=384 width=124) (actual rows=20 loops=1)
         Sort Key: id DESC
         Sort Method: external merge  Disk: 9736kB     <- 80,000행 × 124B = 9.5MB > work_mem 4MB
         ->  Index Scan using idx_orders_user on orders o
               (cost=0.43..1548.74 rows=384 width=124) (actual rows=80000 loops=1)
               Index Cond: (user_id = 70100)
               Buffers: shared hit=12043 read=56218    <- 힙 랜덤 접근 8만 회
 Execution Time: 2401.9 ms
```

p95 4ms → 2.4초, DB CPU 급등. **배포는 없었다.** 실제로 바뀐 것은 데이터 300만 건, ANALYZE 1회, 계획 1회다.

**계획 변경의 지문 세 개가 여기 그대로 있다.**

- ⑴ `rows=384`(추정)과 `actual rows=80000`(실제)의 자릿수 차이 — **입력이 틀렸다는 직접 증거**.
- ⑵ `Sort Method: external merge Disk:` — 384행이 걸릴 줄 알고 짠 계획에 8만 행이 들어오니 `work_mem`을 넘겨 디스크로 흘렀다. `pg_stat_statements`의 `temp_blks_written`으로도 잡힌다.
- ⑶ `Buffers`의 `read` 급증 — 힙 랜덤 접근이 8만 회다. 이 "훑은 양 대비 반환량"의 붕괴가 §3-2 2단계에서 **건당 읽은 블록 수**로 나타난다.

**이 사고를 §1-1의 세 칸에 넣어 보면**: 입력이 바뀐 경우이고, 그중에서도 **원인 ①(autoanalyze가 돌았다)이 방아쇠, 원인 ⑤(MCV 목록 교체)가 총알**이다. 방아쇠만 말하면 "ANALYZE가 문제였다"는 틀린 결론(→ autoanalyze를 끄자)으로 가고, 총알까지 말해야 올바른 처방(→ statistics target을 올려 MCV 목록을 넓히거나, 후보를 하나로 만들자)이 나온다.

### 2-2. 사고 ② — 여섯 번째 실행부터 느려진다: 제네릭 계획 전환

같은 테이블(배치 뒤 1,500만 건), 다른 화면이다. **가맹점 정산 상세 화면**이고, 이 화면은 **최대 가맹점 M(주문 150만 건, 전체의 10%)만** 조회한다. MCV 1위 값이다.

```sql
SELECT status, count(*), sum(amount)
FROM orders
WHERE user_id = $1
GROUP BY status;
```

1. 애플리케이션이 이 쿼리를 같은 커넥션에서 다섯 번 실행했다. **pgjdbc가 서버 준비문으로 전환**한다(`prepareThreshold` 기본 5).
2. 서버는 처음 다섯 번을 **커스텀 계획**으로 세운다. `$1 = M`은 MCV 1위라 빈도 0.10을 그대로 써서 **추정 150만 행**. 150만 행을 힙에서 읽어야 하니 랜덤 접근 대신 **Bitmap Heap Scan**(인덱스에서 위치를 모아 블록 순서로 정렬한 뒤 순차에 가깝게 읽는 방식)을 고른다.

   ```text
    HashAggregate  (cost=339159.98..339160.01 rows=3 width=48) (actual time=1783.2..1783.2 rows=3 loops=1)
      Group Key: status
      ->  Bitmap Heap Scan on orders  (cost=23852.00..331659.98 rows=1500000 width=20)
            Recheck Cond: (user_id = 7001)
            Heap Blocks: exact=287257                 <- 블록 순서로 정리해 읽는다
            ->  Bitmap Index Scan on idx_orders_user  (cost=0.00..23852.00 rows=1500000 width=0)
                  Index Cond: (user_id = 7001)
    Execution Time: 1783.4 ms
   ```

   (참고로 Seq Scan은 475,962로 계산되므로 비트맵이 이긴다.)

3. 커스텀 다섯 번의 평균 비용 **339,160**이 기록된 뒤, 서버가 **제네릭 계획**을 한 번 만들어 비교한다. 제네릭은 `$1`이 무엇인지 모르므로 §1-2의 규칙 ⑶을 쓴다 — `1 / n_distinct` = 1 / 13,788 → **추정 1,088행**.

   ```text
    HashAggregate  (cost=4376.86..4376.89 rows=3 width=48) (actual time=24106.8..24106.8 rows=3 loops=1)
      Group Key: status
      ->  Index Scan using idx_orders_user on orders  (cost=0.43..4371.42 rows=1088 width=20)
            Index Cond: (user_id = $1)                (actual rows=1500000 loops=1)
    Execution Time: 24107.1 ms
   ```

4. **제네릭 4,377 < 커스텀 평균 339,160 → 제네릭이 채택된다.** 1,088행이면 비트맵을 만들 것 없이 그냥 인덱스로 하나씩 집어 오는 게 싸다는 계산이고, 그 계산은 **1,088행이라는 전제 아래서는 옳다.**
5. **여섯 번째 실행부터 24초.** 실제로는 150만 행을 하나씩 랜덤 힙 접근으로 집어 오고 있다. 비트맵이 287,257 블록을 정리해서 읽던 일을, 150만 번 흩어져 읽는 것으로 바꿔 버린 것이다.
6. 담당자가 앱을 재시작한다 → 준비문 캐시가 비어 다시 커스텀 계획 → **1.8초로 회복** → 몇 분 뒤 다시 24초. "재시작하면 낫는다"가 진단을 오히려 방해한다(사람들은 메모리·커넥션 누수를 의심한다).

**이 사고가 §1-4의 방향 규칙을 그대로 보여 준다.** 화면이 조회하는 값(M, 10%)이 **평균(1/13,788 ≈ 0.007%)보다 1,400배 흔한 값**이라서, 제네릭 계획이 "몇 행 안 걸린다"고 과소 추정했고, 그래서 **싸 보였고, 그래서 채택됐다.** 만약 이 화면이 희귀한 값만 조회했다면 제네릭은 과대 추정으로 비싼 계획을 만들었을 것이고, 비싸므로 애초에 채택되지 않았을 것이다 — 사고가 안 난다.

**결정적 지문 세 개.** ⑴ 재시작·커넥션 교체 뒤 회복했다 재발한다. ⑵ 리터럴을 박아 psql에서 직접 실행하면 **빠르다** — "DB에서 돌리면 빠른데 앱에서만 느리다"는 전형적 보고가 이것이다. ⑶ 편중 컬럼(테넌트 ID, 가맹점 ID, `status`, `type`)이 파라미터 자리에 있고, **그 화면이 유난히 흔한 값만 본다.**

> 조인이 끼면 같은 과소 추정이 **Nested Loop 폭주**로 나타난다 — 안쪽 노드의 `loops=1500000`이 그 지문이다. 얼굴만 다르고 뿌리는 같다(제네릭 계획의 과소 추정).

[나쁜 답] "통계가 갱신돼서 플래너가 다른 인덱스를 타게 됐고, 그래서 느려졌습니다."
   → 왜 갱신됐는지, 갱신되면 무엇이 바뀌는지, 그게 왜 다른 계획으로 이어지는지,
     왜 그게 느린지가 전부 비어 있다. 네 칸이 비었으므로 "하" 답변이다.

[좋은 답 — 사고 ①]

[좋은 답 — 사고 ②]

### 2-4. 이 두 사례가 가르치는 네 가지

**첫째, ANALYZE 자체는 정상 동작이다.** 문제는 "재계산"이 아니라 **"재계산 결과가 특정 값에게만 나빠질 수 있다"**는 것이다. 사고 ①에서 새 통계는 전체적으로 더 정확해졌다 — 신규 가맹점 20곳의 추정은 정확해졌고, 밀려난 20곳만 나빠졌다. 그래서 대응이 "autoanalyze를 끄자"가 아니라 "목록을 넓히거나(statistics target) 후보를 줄이자"로 간다(§3-4).

**둘째, 플래너는 "평균적인 값"을 가정한다.** MCV에 못 든 값들은 전부 똑같이 생겼다고 보고, 제네릭 계획은 아예 "평균 하나로 모든 값을 처리하겠다"고 결정한다. 편중된 컬럼에서는 **"플래너가 옳은 값"과 "틀린 값"이 동시에 존재**하고, 그래서 "쿼리가 느리다"가 아니라 **"이 값에서만 느리다"**로 증상이 온다.

**셋째, 후보가 둘이었기 때문에 뒤집힐 수 있었다.** §2의 쿼리에 `(user_id, id)` 복합 인덱스가 있었다면 후보 하나가 WHERE·ORDER BY·LIMIT을 동시에 만족해, 계획 B가 이길 수 있는 통계값이 아예 존재하지 않는다. 사고 ②도 `(user_id)` 위에 필요한 컬럼을 얹은 커버링 인덱스가 있으면 커스텀이든 제네릭이든 같은 인덱스를 고른다. **흔들릴 여지를 없애는 것이 근본 대응**이다(§3-4의 1번).

**넷째, PostgreSQL에는 "지금 데이터를 실측하는 안전장치"가 없다**(§1-7). 대신 통계를 정밀하게 만드는 손잡이(statistics target, 확장 통계, `n_distinct` 고정)가 열려 있다 — **그 손잡이를 쓰는 것이 PostgreSQL 운영자의 일이다.**

### 2-5. 두 후보의 비용을 나란히 보는 법 (가산점 포인트)

`EXPLAIN`은 "고른 것"만 보여준다. "무엇과 비교해서 골랐는지"를 PostgreSQL에서 보는 정석은 **후보를 하나씩 막아 각 계획의 총비용을 뽑아 비교하는 것**이다.

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 70100 ORDER BY id DESC LIMIT 20;
--  Limit  (cost=1565.22..1565.27 rows=20 ...)   ← 지금 고른 계획 A 의 비용 1,565

BEGIN;                                 -- SET LOCAL 이라 이 트랜잭션에서만 적용되고 ROLLBACK 이면 원복
SET LOCAL enable_indexscan = off;      -- idx_orders_user 를 쓰는 A 를 막아 B 를 보게 한다
SET LOCAL enable_indexonlyscan = off;
EXPLAIN SELECT * FROM orders WHERE user_id = 70100 ORDER BY id DESC LIMIT 20;
--  Limit -> Bitmap Heap Scan ... 또는 Seq Scan ...  (cost=... .. 37211.43)   ← B 계열의 비용
ROLLBACK;
```

"A가 1,565, B가 37,211이면 24배 차이"처럼 **두 후보의 비용 간격이 얼마인지**를 알면, 그 쿼리가 다음 ANALYZE에서 또 뒤집힐 후보인지 판단할 수 있다. 간격이 두 배 남짓이면 통계가 조금만 흔들려도 뒤집힌다. 반대로 실제 실행 시간은 A가 압도적으로 느린데 비용은 A가 싸다면 **비용 모델의 입력이 틀렸다는 확진**이다 — 사고 ①이 정확히 그 상태다.

베이스라인에 이 비용도 남겨 두면(§3-5) "왜 뒤집혔나"가 아니라 "뒤집힐 뻔했다"를 미리 안다. 주의: `enable_*`를 끄는 것은 그 노드의 비용에 큰 상수를 더하는 것이지 금지가 아니고, **가설 검증 도구이지 운영 설정이 아니다.**

> **MySQL 대조**: MySQL은 `optimizer_trace`가 후보별 `cost`·`chosen`을 JSON으로 한 번에 준다. PostgreSQL에는 내장 트레이스가 없어 위처럼 **후보를 하나씩 막아 재는 방식**이 표준이다. 대신 PostgreSQL은 노드별 실제 읽은 블록까지 주므로 "왜 골랐나"는 약하고 "고른 게 실제로 어땠나"는 강하다.

### 2-6. 원인 후보 10종 — 세 칸에서 꺼내는 인출 목록

§1-1의 세 질문(입력이 바뀌었나 / 후보가 바뀌었나 / 함수가 바뀌었나)에 걸어서 외운다. 표는 인출용이고 설명은 아래 각 항목에 있다.

| # | 원인 | 바뀐 칸 | 전형적 트리거 | 첫 확인 지점 |
|---|---|---|---|---|
| ① | autoanalyze로 통계 갱신 | 입력(통계) | 변경 행이 임계(기본 10%) 초과 | `last_autoanalyze` |
| ② | 통계가 낡음 | 입력(통계) | 대량 적재 직후, 임계 미달인 큰 테이블 | `n_mod_since_analyze` |
| ③ | `n_distinct` 오추정 | 입력(통계) | 값이 뭉쳐 저장되는 컬럼, 배치 이관분 | `pg_stats.n_distinct` vs `COUNT(DISTINCT)` |
| ④ | **제네릭 계획 전환** | 입력(값을 안 봄) | 준비문 6번째 계획 수립부터, 재시작하면 회복 | `EXPLAIN (GENERIC_PLAN)` |
| ⑤ | 데이터 분포 변화 · **MCV 목록 교체** | 입력(통계) | FAILED 급증, 특정 값의 MCV 진입/이탈 | `most_common_vals`, 값별 건수 추이 |
| ⑥ | 컬럼 상관관계 미반영 | 입력(통계 모델) | AND 조건 여럿 → 선택도 곱셈 붕괴 | 추정 vs 실제 rows, `pg_statistic_ext` |
| ⑦ | 인덱스 추가·삭제·INVALID | 후보 집합 | 남이 만든 유사 인덱스, CIC 실패 잔존 | `pg_index.indisvalid`, `idx_scan` |
| ⑧ | GUC 변경 / 메이저 업그레이드 | 함수 | `work_mem`·`random_page_cost`·`jit`, **`pg_upgrade` 후 ANALYZE 누락** | `pg_settings` diff, `version()` |
| ⑨ | 테이블 크기 임계 통과 | 입력(크기) | 자연 증가로 Seq Scan·병렬 선호 | `pg_class.relpages` 추이 |
| ⑩ | visibility map 노후 (가산점) | 입력(가시성) | 롱 트랜잭션 → Index Only Scan 퇴화 | `relallvisible`, `Heap Fetches` |

#### ①② autoanalyze가 돌았거나, 반대로 안 돌았거나

변경 행 수(`n_mod_since_analyze`)가 `autovacuum_analyze_threshold`(기본 50) + `autovacuum_analyze_scale_factor`(기본 0.1) × 추정 행 수를 넘으면 autovacuum 워커가 다음 순회에서 ANALYZE를 돌린다. 배치가 끝난 시각과 일치하지도 않고 기본 설정으로는 로그에도 안 남아서 **"배포도 배치도 끝난 지 한참인데 갑자기"**라는 인상을 준다(①). §2-1의 사고가 이 방아쇠에서 출발했다.

반대편도 같은 임계에서 나온다 — 임계가 **비율**이라 1억 건 테이블은 1,000만 행이 바뀌어야 돈다(0.1 × 1억). 그 사이 적재된 새 데이터는 **통계에 아예 존재하지 않고**, 플래너는 `created_at >= '어제'`를 히스토그램 밖 값으로 보고 "거의 안 걸린다"고 추정한다 → 과도한 Nested Loop·인덱스 스캔(②). **PostgreSQL에는 index dive가 없으므로**(§1-7) 이 오차를 실행 시점에 바로잡을 장치가 없다.

```sql
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze,
       (SELECT reltuples::bigint FROM pg_class c WHERE c.oid = relid) AS reltuples
FROM pg_stat_user_tables WHERE relname = 'orders';
-- last_autoanalyze 가 느려진 시각 직전 → ①
-- n_mod_since_analyze 가 크고 last_analyze 가 오래됨 → ②
```

**(가산점 포인트)** `log_autovacuum_min_duration`을 켜 두면 autovacuum·autoanalyze 실행이 서버 로그에 남는다 — 사후에 "그 시각에 정말 돌았나"를 확인할 유일한 기록이라 운영 기본값으로 켜 두는 게 낫다.

#### ③ n_distinct 오추정 — "돌았다"가 아니라 "다르게 나왔다"가 문제

표본 3만 행은 1,200만 건 테이블의 0.25%다. PostgreSQL은 이 표본에서 본 서로 다른 값의 개수를 전체로 외삽하는데, **고카디널리티 컬럼에서는 구조적으로 낮게 잡힌다** — §1-2 예시에서 실제 100만 명 이상인 `user_id`가 16,685로 나온 것이 그 얼굴이다. 값이 **뭉쳐서 저장되는 컬럼**일수록 어느 행을 맞히느냐에 따라 추정이 더 크게 흔들린다. 증상은 **"아무것도 안 했는데 며칠에 한 번씩 계획이 왔다 갔다 한다"**이다.

```sql
SELECT attname, n_distinct, null_frac, correlation
FROM pg_stats WHERE tablename = 'orders' AND attname = 'user_id';
--  n_distinct 가 양수면 그 값 자체, 음수면 행 수 대비 비율(-0.1 = 행 수의 10%)
SELECT COUNT(DISTINCT user_id) FROM orders;   -- 레플리카에서. 자릿수가 다르면 ③ 확정
```

`n_distinct`는 §1-2 규칙 ⑵·⑶의 분모다. 분모가 흔들리면 **MCV에 없는 모든 값의 추정이 함께 흔들린다** — 한 값의 문제가 아니라 컬럼 전체의 문제라는 점이 ③의 특징이다.

**PostgreSQL의 손잡이 둘**: `ALTER COLUMN user_id SET STATISTICS 1000`(이 컬럼만 표본·MCV 목록 크기를 키운다), 그리고 값 개수가 안정적이라면 `SET (n_distinct = -0.1)`로 **추정치를 아예 고정**(§3-4에서 대가와 함께).

#### ④ 제네릭 계획 전환 — PostgreSQL에서 가장 자주 만나는 "갑자기"

§2-2의 사슬 그대로이고, 이 원인만 진단 진입점이 다르다 — **통계는 멀쩡하고 `last_autoanalyze`도 조용한데 계획만 바뀐다.** 입력 중에서 "쿼리에 들어온 값"만 바뀐(정확히는 "안 보게 된") 경우이기 때문이다.

판별은 §2-2의 지문 세 개, 확진은 `EXPLAIN (GENERIC_PLAN)`(PG 16+)이나 `PREPARE` + 여섯 번의 `EXPLAIN EXECUTE`. **(가산점 포인트)** `track_planning = on`을 켜면 `pg_stat_statements`에 `plans`가 수집된다(PG 13+) — `calls`는 느는데 `plans`가 거의 안 늘면 계획을 재사용 중이라는 간접 신호다.

#### ⑤ 데이터 분포 변화 — 플래너가 "옳게" 바꾼 경우일 수 있다

`status = 'FAILED'`가 1%일 때는 인덱스가 정답이고 40%일 때는 Seq Scan이 정답이다. 외부 결제사 장애로 실패 주문이 쏟아지고 그 뒤 ANALYZE가 돌면 `most_common_freqs`가 갱신되고 플래너는 Seq Scan으로 바꾼다. 이때 계획 전환은 **오판이 아니라 정확한 판단**이고, 느려진 것은 **"실패 주문 전부를 읽어야 하는 쿼리"가 된 요구 자체** 때문이다.

구분법은 추정 `rows`와 `actual rows`의 거리 — 가까우면 플래너가 옳고, 대응은 쿼리·요구의 변경(기간 조건, 아카이빙, **부분 인덱스**, 파티셔닝)이다. 손익분기 자체는 [인덱스를 걸었는데도 풀스캔](02-index-not-used-full-scan.md) §4-3에 있다.

**PostgreSQL 특유의 미묘함 — MCV 목록은 크기가 유한하다.** 목록 칸 수는 `statistics target`(기본 100)이 정하고, 새 값이 들어오면 누군가는 밀려난다. 어떤 값이 MCV에 들어오거나 밀려 빠지는 순간, 그 값의 선택도 계산이 §1-2 규칙 ⑴에서 규칙 ⑵로 **불연속하게** 바뀐다. **"어제까지 잘 되던 특정 값만 갑자기"의 정체가 이것인 경우가 많고, §2-1의 사고가 정확히 이것이다.** 처방은 statistics target 상향(= MCV 목록 확대)이다.

#### ⑥ 컬럼 상관관계 — 확장 통계를 안 만들었으면 항상 틀리고 있다

§1-3 그대로 — 조건이 둘 이상 AND로 걸리는 쿼리에서 추정 rows가 실제보다 자릿수로 작으면 이 칸을 의심한다. `CREATE STATISTICS`는 만든 뒤 `ANALYZE`를 해야 채워지고, **테이블 하나 안의 컬럼들에만** 적용된다(조인 양쪽의 상관은 못 잡는다).

#### ⑦ 인덱스 추가·삭제·INVALID — 후보 집합이 바뀜

옆 팀이 리포트 쿼리를 위해 `idx_orders_created_status`를 추가했더니 내 쿼리의 플래너가 그쪽을 고르기 시작하는 경우. 인덱스는 **추가만으로 다른 쿼리의 계획을 바꿀 수 있다.** 반대로 "안 쓰는 것 같아서" 지운 인덱스가 특정 값에서만 쓰이던 것이라 그 값이 들어올 때 무너지기도 한다.

**PostgreSQL 고유의 함정 하나**: `CREATE INDEX CONCURRENTLY`가 실패하면 **`INVALID` 상태의 인덱스가 남는다** — 쓰기 비용은 다 내면서 플래너의 후보에는 안 들어간다. "인덱스가 분명히 있는데 안 탄다"의 단골이다.

```sql
SELECT i.indexrelid::regclass AS index_name, pg_get_indexdef(i.indexrelid) AS def,
       i.indisvalid, s.idx_scan
FROM pg_index i JOIN pg_stat_user_indexes s ON s.indexrelid = i.indexrelid
WHERE i.indrelid = 'orders'::regclass ORDER BY s.idx_scan;
-- indisvalid = false → CIC 실패 잔존(DROP 후 재시도) / idx_scan = 0 → 미사용 후보
```

**인덱스 bloat**도 이 칸이다. 인덱스가 부풀면 `relpages`가 커져 인덱스 스캔 비용이 올라가고 어느 지점에서 Seq Scan에 진다 — 처방은 `REINDEX CONCURRENTLY`.

#### ⑧ GUC 변경과 메이저 업그레이드 — 함수가 바뀜

`work_mem`, `random_page_cost`, `effective_cache_size`, `jit`, 병렬 설정, `default_statistics_target`. 누군가 "다른 문제를 고치려고" 만진 파라미터의 영향이 내 쿼리에 왔다. `pg_settings`의 정기 스냅샷 diff로 잡는다 — `WHERE source NOT IN ('default','override')`가 "기본값에서 벗어난 것들"을 준다.

**메이저 업그레이드는 두 겹으로 위험하다.** ⑴ 플래너 자체가 바뀐다 — 새 노드(`Memoize`, `Incremental Sort` 등)가 후보에 추가되고 비용 계산이 개선된다. 대개는 좋아지지만 개별 쿼리는 나빠질 수 있다. ⑵ **더 흔하고 더 치명적인 쪽: `pg_upgrade`는 옵티마이저 통계를 새 클러스터로 옮기지 않는다.** 업그레이드 직후의 DB는 **통계가 텅 빈 상태**라 플래너가 기본 추정치로 계획을 세운다 — 모든 쿼리의 계획이 동시에 이상해지고, 그 정체는 "새 버전이 나쁘다"가 아니라 "통계가 없다"이다. 그래서 절차의 마지막 줄은 반드시 통계 재수집이고, 서비스를 빨리 열어야 하면 정밀도를 단계적으로 올리는 방식을 쓴다.

```bash
vacuumdb --all --analyze-in-stages   # 낮은 정밀도로 전체를 빠르게 훑고 점점 정밀하게 반복
# (--analyze 로 한 번에 돌리면 정확하지만 그동안 통계가 계속 비어 있다)
```

#### ⑨⑩ 아무 사건 없이 넘어가는 두 임계 (⑩은 가산점)

**⑨ 테이블 크기.** 테이블이 커지면 어느 지점에서 인덱스 스캔의 힙 랜덤 접근 비용이 Seq Scan을 넘어서고, 또 어느 크기를 넘으면 **Parallel Seq Scan이 후보에 추가**된다. 이 전환은 배치도 배포도 없이 **데이터가 자란 것만으로** 일어난다 — `pg_class.relpages` 추이를 베이스라인에 남겨 두면 "그날 임계를 넘었다"가 보인다.

**⑩ visibility map 노후.** Index Only Scan의 비용 추정에는 `relallvisible / relpages` 비율이 들어간다. 롱 트랜잭션이 `backend_xmin`으로 VACUUM을 막거나 autovacuum이 밀리면 "전부 가시" 페이지 비율이 떨어지고 → 예상 힙 접근이 늘어 비용이 올라가고 → **다른 계획으로 전환**된다. 전환되지 않더라도 `Heap Fetches`가 폭증해 같은 계획이 느려진다. 이 갈래는 [롱 트랜잭션의 해악](16-long-transaction-harm-and-shortening.md)과 [커버링 인덱스](09-covering-index.md)로 이어진다.

### 2-7. 계획은 안 바뀌었는데 그렇게 보이는 것들 — 이 문서 밖

락 대기(`wait_event_type = 'Lock'`), 캐시 냉각(같은 계획인데 `shared read` 급증), bloat로 같은 계획이 더 많은 블록을 읽는 것, `work_mem` 초과 스필(`external merge Disk`, `Batches > 1`), N+1 호출 수 증가. 이것들은 **같은 계획, 다른 실행 비용**이다.

진단 2단계(§3-2)에서 **계획 텍스트가 동일**하다면 계획 변경이 아니므로 이 문서를 덮고 ["변경 없음" 검증 문서](./22-db-cpu-spike-without-deployment.md)로 돌아간다.

## 3. 대응 · 안전망

### 3-1. 대응 사다리 — 진단 → 즉시 완화 → 근본 대응

순서가 있는 이유: 진단 없이 완화하면 무엇을 되돌려야 할지 모르고, 완화 없이 근본 대응만 하면 장애 시간이 길어지고, 근본 대응 없이 완화만 하면 다음 ANALYZE에 또 뒤집힌다. **PostgreSQL에서는 이 순서가 강제된다** — 힌트 문법이 없어 "일단 고정하고 나중에 본다"는 지름길이 막혀 있기 때문이다.

```text
① ANALYZE                     — 입력이 낡은 건 아닌지 먼저 배제 (가장 싸고 되돌릴 것도 없다)
② statistics target 상향       — 입력의 "정밀도"를 올린다 (컬럼 단위, MCV 목록도 함께 넓어진다)
③ CREATE STATISTICS           — 입력의 "모델"을 고친다 (컬럼 간 독립 가정을 깬다)
④ 비용 파라미터 국소 교정      — 함수의 계수를 하드웨어 현실에 맞춘다 (롤/세션 범위로)
⑤ 부분 인덱스 · 복합 인덱스    — 후보를 하나로 만들어 흔들릴 여지 자체를 없앤다
⑥ pg_hint_plan               — 응급. 확장 설치가 전제라는 사실 자체가 "최후"라는 뜻이다
   (원인 ④ 제네릭 계획이면 ①보다 먼저 plan_cache_mode = force_custom_plan)
```

### 3-2. 진단 5단계 — 순서 고정

**1단계. 느려진 시각을 특정한다.** APM에서 p95가 꺾인 분 단위 시각, `log_min_duration_statement` 로그에 그 쿼리가 **처음 등장한** 시각, `pg_stat_statements` 스냅샷의 구간 diff. 그 시각 위에 배포·배치·`last_autoanalyze`·GUC 변경·인덱스 DDL·**애플리케이션 재시작**의 타임라인을 겹친다. "갑자기"는 대개 이 겹치기에서 이미 반쯤 풀린다.

**2단계. "계획이 바뀐 게 맞는지"부터 확정한다.** 계획 변경의 지문은 **건당 읽은 블록은 뛰는데 건당 반환 행은 그대로**라는 것이다 — 같은 결과를 내기 위해 훨씬 많이 읽고 있다는 뜻이다.

```sql
-- pg_stat_statements 는 누적이므로 "구간"을 보려면 스냅샷 diff 가 필요하다(§3-6)
SELECT left(query, 80) AS q, calls,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       round((shared_blks_hit + shared_blks_read)::numeric / NULLIF(calls, 0), 1) AS blocks_per_call,
       round(rows::numeric / NULLIF(calls, 0), 1) AS rows_per_call,
       temp_blks_written                              -- 정렬·해시가 디스크로 흘렀나(사고 ①의 지문 ⑵)
FROM pg_stat_statements WHERE query LIKE '%FROM orders%'
ORDER BY total_exec_time DESC LIMIT 10;
```

`blocks_per_call`이 자릿수로 뛰었는데 `rows_per_call`은 그대로면 계획 변경(또는 원인 ⑤의 분포 급변)이고, `blocks_per_call`도 그대로인데 느려졌으면 §2-7이다.

> **MySQL 대조**: MySQL은 digest 테이블의 `SUM_ROWS_EXAMINED`로 "훑은 행 수"를 직접 볼 수 있다. PostgreSQL의 `pg_stat_statements`에는 그 칸이 없고 `rows`는 **반환 행 수**다. 그래서 PostgreSQL에서 "얼마나 헛일했나"의 대용치는 **읽은 블록 수**이고, 정확한 훑은 행 수는 개별 쿼리를 `EXPLAIN (ANALYZE)`로 재현해 `Rows Removed by Filter`에서 읽는다([실행 계획 읽기](10-explain-and-slow-query-process.md) §2).

**3단계. 계획을 현재 vs 과거로 diff한다.** PostgreSQL에서 가장 확실한 방법은 **`auto_explain` 로그**다 — 과거의 실제 계획이 텍스트로 남아 있으므로 "어제 02:00의 계획"과 "오늘 09:00의 계획"을 그대로 비교할 수 있다.

```conf
# postgresql.conf — 상시로 켜 두는 것을 권한다 (§3-7)
shared_preload_libraries = 'pg_stat_statements,auto_explain'
auto_explain.log_min_duration = '500ms'
auto_explain.log_analyze = on       # 실측치까지 (오버헤드 있음 — 임계를 넉넉히)
auto_explain.log_buffers = on
```

로그가 없으면 지금 계획을 뜨고 베이스라인(§3-5)과 비교한다. **`EXPLAIN`에 넣는 값은 실제로 느린 값**이어야 한다 — `pg_stat_statements`는 파라미터를 `$1`로 정규화하므로 실제 값은 로그에서 얻는다. 사고 ①처럼 "특정 값에서만" 느린 경우에 대표값으로 뜨면 아무것도 안 보인다. 그리고 **원인 ④가 의심되면 `EXPLAIN (GENERIC_PLAN)`도 같이 뜬다** — psql에서 리터럴로 뜬 계획은 커스텀 계획이라 앱이 실제로 쓰는 계획과 다를 수 있다.

**4단계. 통계를 확인한다.** `pg_stat_user_tables`의 `last_analyze`/`last_autoanalyze`/`n_mod_since_analyze`가 1단계의 시각과 어떻게 겹치는지 보고(→ ①②), `pg_stats`의 `n_distinct`를 레플리카의 실제 `COUNT(DISTINCT ...)`와 대조하고(→ ③), **문제의 값이 `most_common_vals`에 있는지 없는지**를 확인한다(→ ⑤). 마지막 항목이 사고 ①을 잡는 결정적 확인이다.

```sql
-- 문제의 값이 MCV 목록에 있나 — 있으면 규칙 ⑴(정확), 없으면 규칙 ⑵(나머지 균등 분배)
SELECT 70100 = ANY(most_common_vals::text::bigint[]) AS in_mcv,
       n_distinct, array_length(most_common_vals, 1) AS n_mcv,
       (SELECT sum(f) FROM unnest(most_common_freqs) f) AS sum_common
FROM pg_stats WHERE tablename = 'orders' AND attname = 'user_id';
```

**5단계. 후보와 함수를 확인한다.** 인덱스 목록·`indisvalid` diff(원인 ⑦), `pg_settings` diff·`version()`(원인 ⑧), `relpages`·`relallvisible` 추이(원인 ⑨⑩). 여기까지 오면 원인은 10종 중 하나로 특정된다.

```text
증상 → 원인 빠른 매핑
- last_autoanalyze 가 느려진 시각 직전 + 문제의 값이 MCV 에서 빠졌다     → ① + ⑤ (사고 ①)
- 앱 재시작하면 회복 / psql 에선 빠름 / 흔한 값만 보는 화면              → ④ (사고 ②)
- last_analyze 는 오래됐고 n_mod_since_analyze 가 큼                    → ② (통계 노후)
- n_distinct 가 실제와 자릿수 차이, 계획이 며칠에 한 번씩 오락가락        → ③
- 추정 ≈ 실측인데 느림, 값별 건수가 급변                                 → ⑤ (플래너가 옳다)
- AND 조건 여럿, 추정 rows 가 실제보다 자릿수로 작음                     → ⑥ (확장 통계 부재)
- 인덱스 목록 diff 에 새 항목 / indisvalid = false                      → ⑦
- pg_settings diff / 업그레이드 직후 통계 텅 빔                         → ⑧
- 아무 사건 없이 서서히, relpages 임계 통과, Parallel Seq Scan 등장      → ⑨
- Heap Fetches 폭증, relallvisible 하락, 롱 트랜잭션 존재                → ⑩
```

### 3-3. 즉시 완화 — 카드 5장, 각각 대가와 함께

장애 중이라면 근본 대응(DDL·배포)을 기다릴 수 없다. 카드는 **원인에 맞춰** 뽑고 대가를 같이 말한다. 다섯 장을 먼저 같은 네 칸으로 세워 두고, 각각을 아래에서 서술한다.

| 카드 | 무엇을 얻나 | 무엇을 내주나 | 언제까지만 쓰나 | 어떻게 만료를 강제하나 |
|---|---|---|---|---|
| **1. `ANALYZE`** | 배포 없이 통계를 지금 데이터에 맞춘다. 원인 ①②③⑤⑧의 첫 수 | 표본 I/O, 계획 캐시 무효화로 잠깐 계획 수립이 몰림, 원인 ③이면 다음 autoanalyze에 또 흔들림 | **만료 개념이 없다** — 유일하게 영구히 둬도 되는 카드 | 불필요. 대신 **같은 테이블에 두 번째 ANALYZE를 하고 있다면** 카드 3으로 올라가라는 신호 |
| **2. `plan_cache_mode = force_custom_plan`** | 값을 다시 보게 만들어 원인 ④를 즉시 원복 | 매 실행 계획 수립 비용, 범위가 쿼리 단위가 아니라 롤/DB 단위 | 근본 대응(경로 분리·커버링 인덱스)이 배포될 때까지 | `ALTER ROLE`은 코드가 아니라 DB에 남으므로 **마이그레이션 파일로만 적용**하고 §3-9의 베이스라인이 `pg_settings` 스냅샷으로 감시 |
| **3. statistics target 상향 + 재수집** | 표본과 MCV 목록이 커져 추정 흔들림이 줄고 원인 ③⑤가 완화 | ANALYZE I/O 증가, MCV 목록을 훑는 만큼 계획 수립 시간 증가 | **영구 설정이 정상** — 문제 컬럼에 남겨 둔다 | 마이그레이션 파일에 이유 주석과 함께 남긴다 |
| **4. 비용 파라미터 국소 교정** | 함수의 계수를 하드웨어 현실에 맞춘다. 원인 ⑧ | 그 롤/DB의 **모든 쿼리** 계획에 영향 | SSD 교정처럼 "현실을 반영한" 것이면 영구, 특정 쿼리를 살리려는 것이면 임시 | 바꾼 뒤 §3-5 베이스라인 잡을 돌려 diff를 확인하는 것이 절차. 임시면 PLAN-PIN 주석 + §3-9 린트 |
| **5. `pg_hint_plan`** | 즉시·확실·그 쿼리만 | 확장 의존, 데이터 변화 추종 불가, 물리 정보가 코드에 결합, 업그레이드 혜택 제외, 원인 은폐 | **반드시 기한부** — 근본 대응 배포까지 | 힌트 옆에 `PLAN-PIN:` 주석으로 이슈 번호·이유·만료일. §3-9의 CI 린트가 만료를 검사해 빌드를 깬다 |

**카드 1. `ANALYZE` — 원인 ①②③⑤⑧일 때, 가장 싼 첫 수.**

```sql
ANALYZE orders;                       -- 테이블 전체
ANALYZE orders (user_id, status);     -- 컬럼을 지정하면 그 컬럼만 떠서 더 빠르다
```

얻는 것: 코드 변경·배포 없이 통계를 지금 데이터에 맞춘다. **PostgreSQL의 `ANALYZE`는 `SHARE UPDATE EXCLUSIVE` 잠금이라 읽기·쓰기를 막지 않는다** — 같은 테이블의 VACUUM/ANALYZE, `CREATE INDEX CONCURRENTLY`, 일부 `ALTER TABLE`과만 충돌한다.

내는 것 셋 — ⑴ **표본 I/O**, ⑵ **계획 캐시 무효화**로 잠깐 계획 수립 비용이 몰린다, ⑶ 원인이 ③이라면 **이번엔 좋은 표본이 잡혀도 다음 autoanalyze에 또 흔들린다.** 같은 테이블에서 ANALYZE를 두 번째 하고 있다면 카드 3으로 가야 한다는 신호다.

> **MySQL 대조**: `ANALYZE TABLE`은 테이블 정의 캐시를 비우므로 그 테이블을 오래 잡고 있는 쿼리가 있으면 **뒤이어 들어오는 쿼리들이 줄을 서는 flush 대기**가 생기고, 기본적으로 binlog에 기록돼 레플리카에서도 같이 돈다. PostgreSQL에는 이 두 위험이 없다 — 잠금이 약하고, 물리 복제에서는 통계 자체가 WAL로 복제되므로 레플리카에서 따로 돌릴 필요도 없다(standby는 읽기 전용이라 돌릴 수도 없다).

**카드 2. `plan_cache_mode = force_custom_plan` — 원인 ④일 때, PostgreSQL 고유의 원복 카드.**

```sql
-- 범위를 좁혀 적용한다 (GUC 계층 — §1-5)
ALTER ROLE app_user SET plan_cache_mode = force_custom_plan;   -- 이 앱 롤만. 새 커넥션부터 적용
ALTER DATABASE shop SET plan_cache_mode = force_custom_plan;   -- 더 넓게
SET plan_cache_mode = force_custom_plan;                       -- 지금 세션만(검증용)
```

얻는 것: 값을 다시 보게 만들어 **즉시 원상 복구**된다. 코드 배포도 DDL도 없다.

내는 것 셋 — ⑴ **매 실행 계획 수립 비용**(준비문의 존재 이유였던 계획 재사용을 포기하는 것이라, 짧고 초당 수천 번 도는 쿼리에서는 계획 수립 CPU가 무시 못 할 비용이 된다), ⑵ **범위가 쿼리 단위가 아니다** — 롤/DB에 걸면 그 롤의 모든 준비문이 영향을 받으므로, 근본 대응이 서면 되돌리는 것이 맞다, ⑶ **원인을 덮는다** — 진짜 문제는 "이 화면이 유난히 흔한 값만 조회한다"는 것이고, 그건 경로 분리나 인덱스 설계로 푸는 편이 낫다(§3-4의 2·6번).

애플리케이션 쪽 대안도 같이 안다 — pgjdbc의 `prepareThreshold`로 서버 준비문 전환 시점을 늦추거나 아예 쓰지 않게 할 수 있다(`prepareThreshold=0`). 대가는 같은 방향이다.

**카드 3. statistics target 상향 + 재수집 — 원인 ③⑤일 때.**

```sql
ALTER TABLE orders ALTER COLUMN user_id SET STATISTICS 1000;  -- 메타데이터 변경이라 즉시 끝난다
ANALYZE orders (user_id);                                     -- 새 설정으로 바로 재수집
```

얻는 것: 표본이 `300 × 1000` = 30만 행으로 늘고 **MCV 목록도 100칸에서 1,000칸으로 늘어난다.** 사고 ①처럼 "MCV에서 밀려나 규칙 ⑵로 떨어진" 값이 다시 목록 안으로 들어올 여지가 생기고, `n_distinct` 추정의 흔들림 폭도 줄어든다 — 원인 ③과 ⑤를 동시에 완화하는 유일한 카드다.

내는 것: ANALYZE가 그만큼 더 읽고, **계획 수립 시간이 늘어난다**(플래너가 MCV 목록을 훑는 비용이 목록 길이에 비례한다). 전역 `default_statistics_target`을 올리는 것보다 **문제 컬럼만 올리는 쪽**이 거의 항상 옳다.

**카드 4. 비용 파라미터·스위치의 국소 교정 — 원인 ⑧일 때.**

```sql
ALTER DATABASE shop SET random_page_cost = 1.1;   -- SSD 인데 기본 4.0 이라 인덱스를 과소평가할 때
ALTER ROLE batch_user SET work_mem = '64MB';      -- 배치 롤에서만 정렬·해시 메모리를 키운다
BEGIN; SET LOCAL jit = off; SELECT ...; COMMIT;   -- 짧은 쿼리에 JIT 가 붙어 느려진 경우, 그 트랜잭션만
```

얻는 것: **PostgreSQL의 GUC 계층 덕분에 전역을 건드리지 않고 영향 범위를 좁힐 수 있다** — MySQL 대비 PostgreSQL의 실질적 강점이다.

내는 것: ⑴ 그래도 "쿼리 하나"보다는 넓다, ⑵ 비용 상수는 **모든 쿼리의 계획에 영향**을 주므로 하나를 고치면서 다른 쿼리를 나쁘게 만들 수 있다 — 바꾼 뒤 베이스라인 잡(§3-5)을 돌려 diff를 확인하는 것이 절차여야 한다, ⑶ `enable_seqscan = off` 류는 **여기 들어오면 안 된다**(§2-5의 가설 검증 도구이지 운영 설정이 아니다).

**카드 5. `pg_hint_plan` — 최후의 지혈대.**

PostgreSQL에는 힌트 문법이 **없다.** 계획을 강제하려면 `pg_hint_plan` 확장을 설치해야 하고, 이 문턱 자체가 설계 메시지다 — "여기까지 왔다면 먼저 통계를 의심하라".

```sql
-- 나쁜 예 — 이유도 기한도 없이 물리 인덱스 이름을 박는다. 3년 뒤 아무도 못 지운다
/*+ IndexScan(o idx_orders_user) */ SELECT * FROM orders o WHERE o.user_id = $1 ...;

-- 좋은 예 — 이유·이슈·만료일을 함께. "왜 플래너를 못 믿었는지"를 남긴다
/*+ IndexScan(o idx_orders_user) */
-- PLAN-PIN: 2026-08-31 autoanalyze 후 가맹점 X 가 MCV 에서 밀려 추정 384행(실제 8만)이 됐다(ISSUE-1234).
--           복합 인덱스 (user_id, id) 배포 후 제거. 만료 2026-09-14
SELECT * FROM orders o WHERE o.user_id = $1 ORDER BY o.id DESC LIMIT 20;

-- 더 나은 선택: 계획을 고정하는 대신 "추정치만 고쳐 주는" 힌트
--   플래너의 판단 기능은 살려 두고 틀린 입력만 바로잡는 것이라 대가가 작다
/*+ Rows(o #80000) */ SELECT * FROM orders o WHERE o.user_id = $1 ORDER BY o.id DESC LIMIT 20;
```

얻는 것: 즉시, 확실히, 그 쿼리만.

내는 것 다섯 가지 — ⑴ **확장 의존**: 설치·유지가 필요하고 관리형 서비스에 따라 지원 여부가 갈린다. ⑵ **데이터가 바뀌어도 계획이 못 따라간다**: 오늘 옳은 인덱스가 내년에는 틀린 인덱스가 되는데 힌트는 그 판단 기능을 꺼버린 것이다. ⑶ **코드에 물리 정보가 결합된다**: 인덱스 이름 변경·삭제가 애플리케이션 변경이 된다. ⑷ **업그레이드의 혜택에서 그 쿼리만 제외된다.** ⑸ **원인을 덮는다**: 통계·인덱스 설계의 진짜 문제는 남아 다른 쿼리에서 재발한다.

그래서 힌트는 **이슈 번호와 만료일이 붙은 지혈대**이고, 만료를 사람이 기억하지 않도록 §3-9의 린트가 지킨다. rationale이 말한 "힌트로 고정하는 것의 트레이드오프까지 가면 상급"이 정확히 이 다섯 줄이다.

**한 가지 더 — PostgreSQL에는 인덱스를 "후보에서만 빼는" 스위치가 없다.** 원인 ⑦의 가설 검증은 `BEGIN; DROP INDEX ...; EXPLAIN ...; ROLLBACK;`으로 한다 — PostgreSQL은 **DDL이 트랜잭션에 포함**되므로 "지웠다 되돌리는" 검증이 가능하다(가산점 포인트). 단 `DROP INDEX`는 `ACCESS EXCLUSIVE` 잠금이라 **트래픽이 있는 운영에서 이 몇 초가 대기열을 만들어 사고가 된다** — `SET LOCAL lock_timeout = '2s'`를 같이 걸고 가능하면 스냅샷 복제본에서 한다.

> **MySQL 대조**: MySQL 8은 `ALTER INDEX ... INVISIBLE`로 **메타데이터만 바꿔 즉시·가역적으로** 인덱스를 후보에서 뺄 수 있어 "지우기 전 일주일은 INVISIBLE로 둔다"는 안전 규칙이 성립한다. PostgreSQL에는 이 기능이 없어 인덱스 삭제가 **비가역적 결정**이 되고(되돌리려면 `CREATE INDEX CONCURRENTLY` 2회 스캔), 그래서 `idx_scan`을 오래 관찰해 근거를 쌓는 일이 더 중요해진다.

### 3-4. 근본 대응 — 흔들릴 여지를 없앤다

**1. 복합 인덱스로 후보를 하나로 만든다 — 최우선.** §2의 쿼리에 `(user_id, id)`를 두면 "이 사용자의 행을 id 순서로 읽는다"는 후보 하나가 WHERE·ORDER BY·LIMIT을 전부 만족하고 정렬 노드가 사라진다. 계획 B가 이길 수 있는 통계값이 존재하지 않으므로 **통계가 어떻게 흔들려도 계획이 안 흔들린다.**

```sql
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id, id);
-- PostgreSQL 은 B-tree 를 역방향으로도 읽으므로 (user_id, id DESC) 로 만들 필요가 없다
-- → Index Scan Backward using idx_orders_user_id 로 찍히고 Sort 노드가 사라진다
```

순서 원칙(등호 → 범위 → 정렬 → 커버링)은 [복합 인덱스 컬럼 순서](08-composite-index-column-order.md) §2, `INCLUDE` 확장은 [커버링 인덱스](09-covering-index.md).

내는 것: 인덱스 하나만큼의 쓰기·공간 비용(PostgreSQL에서는 인덱스 컬럼이 바뀌는 UPDATE가 **HOT에서 탈락해 모든 인덱스에 새 엔트리를 꽂는다**는 추가 대가), 대형 테이블 DDL의 절차 비용([무중단 DDL](14-online-ddl-zero-downtime-schema-change.md)), 기존 `idx_orders_user`가 접두사로 중복되므로 관찰 후 정리.

**2. 부분 인덱스 — 원인 ⑤의 근본 처방이자 PostgreSQL의 무기. 단 제네릭 계획과는 궁합이 나쁘다.**

```sql
-- 관리자 화면이 보는 것은 전체의 1%뿐이다. 그 1%만 담는 인덱스를 만든다
CREATE INDEX CONCURRENTLY idx_orders_failed_created
  ON orders (created_at DESC) WHERE status = 'FAILED';
```

얻는 것: 인덱스가 전체의 1% 크기라 그 조건의 조회가 압도적으로 싸지고, `status`의 분포가 흔들려도 이 쿼리의 계획은 안 흔들린다.

내는 것: **쿼리의 WHERE가 인덱스의 WHERE를 포함한다는 것을 플래너가 증명할 수 있어야만** 쓴다. 여기서 중요한 제약이 나온다 — **`status = $1`처럼 파라미터로 오면 `$1 = 'FAILED'`임을 증명할 수 없어 이 인덱스를 못 쓴다.** 그러니 **부분 인덱스는 원인 ④(제네릭 계획)의 해결책이 아니다.** 쓰려면 **그 화면만 리터럴을 박은 전용 쿼리로 분리**해야 하고, 분리하는 순간 그 쿼리는 준비문 파라미터가 아니게 되므로 **원인 ④도 함께 사라진다.** 즉 처방은 "부분 인덱스"가 아니라 **"경로 분리 + 부분 인덱스"** 한 묶음이다.

**3. 확장 통계 — 원인 ⑥.** §1-3의 `CREATE STATISTICS`. 얻는 것: 컬럼 독립 가정을 깨서 AND 조건의 추정이 현실에 붙는다. 내는 것: **직접 만들어야 하고 어느 조합이 상관관계가 있는지는 사람이 판단해야 한다**(추정 vs 실제 rows가 자릿수로 벌어지는 쿼리에서 역산한다), ANALYZE·계획 수립 비용이 늘고, 테이블 하나 안의 컬럼에만 적용되어 조인 양쪽의 상관은 못 잡는다.

**4. 통계 정밀도 정책을 테이블에 박는다 — 원인 ①②③⑤.**

```sql
-- 큰 테이블은 비율 임계가 너무 멀다 → 이 테이블만 임계를 낮춘다
ALTER TABLE orders SET (autovacuum_analyze_scale_factor = 0.02,
                        autovacuum_analyze_threshold    = 5000);

-- 편중 컬럼은 정밀도를 올린다 — MCV 목록이 100칸에서 1,000칸으로 늘어
-- 사고 ①처럼 "밀려나서" 생기는 추정 붕괴가 구조적으로 줄어든다
ALTER TABLE orders ALTER COLUMN user_id SET STATISTICS 1000;

-- 값 개수가 실제로 안정적인 컬럼은 추정치를 고정해 흔들림을 원천 차단한다
ALTER TABLE orders ALTER COLUMN user_id SET (n_distinct = -0.1);
ANALYZE orders;
```

얻는 것: 사고 ①의 원인(MCV 목록 교체 + `n_distinct` 흔들림)이 구조적으로 줄어든다.

내는 것: ⑴ 임계를 낮추면 **autoanalyze가 더 자주 돌아** 그 자체가 I/O 부하다, ⑵ `n_distinct` 고정은 **가장 위험한 손잡이**로, 데이터 성격이 바뀌어도 플래너는 영구히 그 값을 믿으므로 이유와 재검토 시점을 마이그레이션 파일에 남기고 §3-5의 베이스라인 잡이 감시하게 한다.

**5. 대량 적재·업그레이드 절차에 ANALYZE를 코드로 박는다 — 원인 ②⑧.** 배치의 마지막 Step(§3-8), `pg_upgrade` 직후의 `vacuumdb --all --analyze-in-stages`(원인 ⑧). "잊지 말자"가 아니라 **잡 정의와 런북 스크립트에 들어가야 한다.**

**6. 스큐 파라미터의 경로 분리 — 원인 ④⑤.** 사고 ②처럼 **한 화면이 유난히 흔한 값만 조회한다면**, 그 화면을 별도 쿼리로 분리한다(리터럴을 박거나, 키셋 커서로 바꾸거나, 별도 집계 테이블을 두거나). 그러면 그 화면의 계획이 다른 값들의 평균에 끌려다니지 않는다. 내는 것: 코드 경로가 둘이 되고 "누가 대형인가"의 기준을 유지해야 한다.

| 대응 | 얻는 것 | 내는 것 | 언제 |
|---|---|---|---|
| `ANALYZE` | 즉시, 무해, 배포 없음 | 다음 autoanalyze에 또 흔들릴 수 있음 | 무조건 첫 수 |
| `force_custom_plan` | 제네릭 계획 즉시 원복 | 매 실행 계획 수립 비용, 범위가 롤/DB 단위 | 원인 ④ |
| statistics target 상향 | 추정 안정, **MCV 목록 확대** | ANALYZE I/O, 계획 수립 시간 | 같은 테이블 ANALYZE 2회째, MCV 이탈이 원인일 때 |
| `CREATE STATISTICS` | 컬럼 독립 가정 해소 | 사람이 조합 선정, 테이블 내부만 | AND 조건 추정이 자릿수로 틀릴 때 |
| 비용 파라미터 국소 교정 | 하드웨어 현실 반영 | 그 롤/DB의 모든 계획에 영향 | SSD인데 기본값 그대로일 때 |
| 복합 인덱스 | 통계와 무관하게 안정 | 쓰기·HOT 탈락·DDL 절차 | 거의 항상 1순위 근본 대응 |
| 부분 인덱스 + 경로 분리 | 그 화면만 안정화, 원인 ④도 동시 제거 | 코드 경로 분기, 리터럴 쿼리 관리 | 특정 화면이 편중된 값만 볼 때 |
| `n_distinct` 고정 | 흔들림 원천 차단 | 데이터 성격 변화에 영구히 눈감음 | 값 개수가 확실히 안정적일 때만 |
| `pg_hint_plan` | 즉시·확실·쿼리 단위 | 확장 의존·추종 불가·결합·원인 은폐 | 지혈대, 만료일 필수 |

### 3-5. 안전망 ① — EXPLAIN 베이스라인 잡: 운영 통계로, 정기적으로, diff

여기서부터가 "사람의 기억 밖으로" 옮기는 작업이다. 이 주제는 특히 그렇다 — **계획 변경은 배포 없이 일어나므로 배포 파이프라인이 못 잡는다.** 잡는 것은 정기 잡과 알람뿐이다. 다섯 층을 둔다.

[실행 계획 읽기](10-explain-and-slow-query-process.md) §4-4의 "EXPLAIN 단정 테스트"는 CI에서 **시드 데이터**로 돌아 **코드 변경**이 만드는 회귀를 잡는데, 이 문서의 원인은 데이터·통계가 만드는 회귀라 그것으로는 안 잡힌다. 한 층이 더 필요하다 — **운영 레플리카에서, 운영 통계로, 매일 뜨는 베이스라인.**

```bash
# explain-baseline.sh — 핵심 쿼리 계획을 운영 레플리카에서 뜨고 커밋된 베이스라인과 비교
BASE=db/explain-baseline; WORK=$(mktemp -d); changed=0
for q in db/critical-queries/*.sql; do    # 파일 1개 = 쿼리 1개. 파라미터는 대표값·최악값 두 벌
  name=$(basename "$q" .sql)
  psql -X -A -t -h "$REPLICA_HOST" -d shop -c "EXPLAIN (FORMAT JSON, SETTINGS) $(cat "$q")" \
    | jq -S '[.. | objects | select(has("Node Type"))
              | {node: ."Node Type", rel: ."Relation Name",
                 idx: ."Index Name", cond: ."Index Cond"}]' > "$WORK/$name.json"
  diff "$BASE/$name.json" "$WORK/$name.json" || { echo "PLAN CHANGED: $name"; changed=1; }
done
exit $changed        # 0이 아니면 알람 채널로. 승인된 변경이면 베이스라인 JSON 을 PR 로 갱신
```

노드 종류·인덱스 이름·`Index Cond`는 엄격 비교하고, `Total Cost`와 `Plan Rows`는 따로 기록해 "3배 이상 변동"을 경고로 둔다(ANALYZE만으로도 조금씩 움직이므로 엄격 비교하면 소음이 된다). `SETTINGS`를 켜면 **기본값에서 벗어난 GUC가 계획과 함께 기록**되므로 원인 ⑧의 증거가 베이스라인 안에 남는다.

**이 잡이 하는 일은 "느려지기 전에" 계획 전환을 알리는 것**이다 — 새벽 2시 autoanalyze 뒤 6시 잡이 diff를 내면 출근 전에 안다. **PostgreSQL에는 Oracle의 SQL Plan Baseline이나 SQL Server Query Store 같은 계획 고정·회귀 감지 기능이 없으므로**, 이 "우리가 기록한 베이스라인"이 그 역할을 대신한다.

사고 ①을 잡으려면 **파라미터를 "대표값"만 넣으면 안 된다** — 대표값(일반 사용자)은 계획이 안 바뀌었고, 밀려난 가맹점 X에서만 바뀌었기 때문이다. 그래서 쿼리 파일마다 **대표값과 최악값(가장 행이 많은 값) 두 벌**을 넣는다. 원인 ④까지 잡으려면 파라미터 쿼리는 `EXPLAIN (GENERIC_PLAN)` 판도 같이 떠서 비교한다.

### 3-6. 안전망 ② — pg_stat_statements 스냅샷과 비율 알람

"건당 블록"의 급변을 기계가 본다.

```sql
-- ops.pgss_snapshot(snapshot_at, queryid, query, calls, total_exec_time, rows,
--                   shared_blks_hit, shared_blks_read)  PK(snapshot_at, queryid)
-- 매시 적재 (pg_cron 또는 외부 크론)
INSERT INTO ops.pgss_snapshot
SELECT now(), queryid, left(query, 500), calls, total_exec_time, rows,
       shared_blks_hit, shared_blks_read
FROM pg_stat_statements WHERE queryid IS NOT NULL;

-- 직전 구간 대비 "건당 읽은 블록"과 "건당 반환 행"을 나란히 — 앞만 뛰면 계획 변경
SELECT c.queryid, left(c.query, 80) AS q,
       (c.shared_blks_hit + c.shared_blks_read - p.shared_blks_hit - p.shared_blks_read)
         / NULLIF(c.calls - p.calls, 0)                 AS blocks_per_call_now,
       (c.rows - p.rows) / NULLIF(c.calls - p.calls, 0) AS rows_per_call_now
FROM ops.pgss_snapshot c
JOIN ops.pgss_snapshot p
  ON p.queryid = c.queryid AND p.snapshot_at = c.snapshot_at - interval '1 hour'
WHERE c.snapshot_at = (SELECT max(snapshot_at) FROM ops.pgss_snapshot)
  AND c.calls > p.calls
ORDER BY 3 DESC;
-- (7일 중앙값 대비 5배 같은 임계는 같은 테이블에서 윈도우 집계로 붙인다)
```

postgres_exporter + Prometheus로 만들면 알람 규칙이 YAML 파일이 된다. 어느 쪽이든 **"건당 읽은 블록이 갑자기 100배인데 반환 행은 그대로"라는 알람이 계획 변경의 가장 이른 신호**다. 주의 — `pg_stat_statements`는 누적이고 `pg_stat_statements.max`를 넘으면 오래된 항목이 밀려나므로, 스냅샷 테이블이 사실상의 시계열 원본이 된다.

### 3-7. 안전망 ③ — auto_explain 상시 + "신규 느린 쿼리 등장" 알람

계획이 뒤집힌 쿼리는 어제까지 느린 쿼리 로그에 없다가 오늘 처음 나타난다. `log_min_duration_statement` 임계와 "분당 건수" 알람에 더해, **`auto_explain`을 상시로 켜 두는 것**이 이 문서의 핵심 장치다 — 사고가 났을 때 "그때의 계획"이 로그에 남아 있어야 §3-2의 3단계가 성립한다.

pgBadger 같은 도구로 일일 리포트를 만들고 **어제 리포트에 없던 정규화 쿼리**를 따로 표시한다. 총량 알람은 묻히지만 "신규 등장"은 안 묻힌다. `log_analyze = on`은 계측 오버헤드를 얹으므로 `log_min_duration`을 넉넉히 잡고 `sample_rate`로 표본만 남긴다.

### 3-8. 안전망 ④ — 배치의 마지막 단계를 `ANALYZE`로 코드화

§2-1의 사고는 "배치가 끝나고 autovacuum이 알아서" 통계를 뜬 데서 났다. 대량 적재 배치가 **스스로 통계를 갱신하고 끝나면** ANALYZE 시각이 배치 시각으로 고정되고, 표본 오차가 있더라도 배치 직후 베이스라인 잡(§3-5)이 그것을 본다.

```java
// before — 런북에 "이관 배치 뒤에는 DBA 에게 ANALYZE 요청"이라고 적어 두는 방식.
//   통계는 autovacuum 에 맡겨지고, 언제 어떤 표본으로 뜰지 아무도 모르며, 런북은 아무도 안 읽는다.

// after — 적재 Step 뒤에 통계 갱신 Step 을 잡 정의에 박는다.
//   "잡은 성공했는데 통계는 낡은" 상태가 아예 존재할 수 없게 만드는 것이 목적이다.
@Bean
public Job merchantMigrationJob(JobRepository repo, Step loadOrdersStep, Step analyzeOrdersStep) {
    return new JobBuilder("merchantMigrationJob", repo)
            .start(loadOrdersStep)
            .next(analyzeOrdersStep)      // 마지막 단계 = 통계 갱신. 실패하면 잡 실패로 드러난다
            .build();
}

@Bean
public Step analyzeOrdersStep(JobRepository repo, PlatformTransactionManager tm, JdbcTemplate jdbc) {
    // ANALYZE 는 SHARE UPDATE EXCLUSIVE 라 읽기·쓰기를 막지 않는다 — 서비스 중에 돌려도 된다.
    // 물리 복제 레플리카는 통계도 WAL 로 복제되므로 프라이머리에서만 돌리면 된다.
    // 대량 삭제가 섞였다면 VACUUM (ANALYZE) 로 죽은 튜플 회수까지 함께.
    return new StepBuilder("analyzeOrdersStep", repo)
            .tasklet((c, ctx) -> { jdbc.execute("ANALYZE orders"); return RepeatStatus.FINISHED; }, tm)
            .build();
}
```

적용 기준을 규칙으로 적어 둔다: **"한 번에 테이블 행 수의 수 % 이상을 넣거나 지우는 잡은 마지막 Step이 ANALYZE다."** PR 템플릿의 체크 항목이 된다. 같은 규칙의 짝이 **업그레이드 런북**이다 — `pg_upgrade` 절차서의 마지막 줄은 `vacuumdb --all --analyze-in-stages`이고, 이 줄이 빠진 절차서는 반려한다.

### 3-9. 안전망 ⑤ — 계획 고정 레지스트리 린트: 지혈대의 만료를 기계가 본다

§3-3 카드 5의 "만료일"은 사람이 기억하면 안 지켜진다. PostgreSQL의 감시 대상은 둘이다 — `pg_hint_plan` 힌트 주석과, 코드에서 세션 GUC를 덮어쓰는 자리.

```bash
# ci/lint-plan-pins.sh — 계획 고정 자리에 PLAN-PIN(이슈·만료일)이 없거나 만료됐으면 빌드를 깬다
status=0
while IFS=: read -r file line _; do
  ctx=$(sed -n "$((line > 3 ? line - 3 : 1)),$((line + 3))p" "$file")
  expiry=$(grep -oE "PLAN-PIN:.*만료 [0-9]{4}-[0-9]{2}-[0-9]{2}" <<< "$ctx" | grep -oE "[0-9-]{10}$" || true)
  if [ -z "$expiry" ]; then echo "$file:$line PLAN-PIN(이슈·만료일)이 없다"; status=1
  elif [[ "$expiry" < "$(date +%F)" ]]; then echo "$file:$line PLAN-PIN 만료($expiry)"; status=1; fi
done < <(grep -rnE "/\*\+ *(IndexScan|SeqScan|NestLoop|HashJoin|MergeJoin|Rows|Set)|SET (LOCAL )?(enable_[a-z]+|plan_cache_mode|random_page_cost|jit) *=" src/ db/ || true)
exit $status
```

한 층 더 — **`SET (n_distinct = ...)`이나 `ALTER ROLE ... SET ...`은 코드가 아니라 DB에 남는 고정**이라 grep으로 안 잡힌다. 마이그레이션 파일로만 적용하도록 규약을 정하고, §3-5의 베이스라인 잡이 `pg_settings`·`reloptions` 스냅샷을 함께 떠서 "코드에 없는 고정"을 diff로 드러내게 한다.

이 다섯 층이 있으면 사고는 이렇게 흘러간다 — 새벽 2시 배치가 끝나며 스스로 ANALYZE(§3-8) → 6시 베이스라인 잡이 `Index Scan Backward → Index Scan + Sort` diff를 알림(§3-5) → 담당자가 `ANALYZE`·`plan_cache_mode`로 즉시 완화(§3-3) → 복합 인덱스를 `CREATE INDEX CONCURRENTLY`로 배포(§3-4) → 2주 뒤 린트가 만료를 알려 임시 고정 제거(§3-9). **사용자는 느려진 것을 모른다.**

## 4. 꼬리질문 대비 포인트

### "계획을 고정해 버리면 끝 아닌가요? 왜 최후 수단이라고 하죠?" (시니어 변별 포인트)

**PostgreSQL에는 애초에 힌트 문법이 없다 — 그 사실 자체가 답의 절반이다.** 계획을 강제하려면 `pg_hint_plan` 확장을 설치해야 하고, 그건 "여기까지 왔다면 먼저 통계를 의심하라"는 설계 메시지다.

원리로 말하면 **힌트는 문제를 푸는 게 아니라 플래너의 판단 기능을 끄는 것**이다. 플래너가 오늘 틀렸다고 내년에도 틀리리라는 보장이 없는데, 힌트는 "오늘의 정답"을 영구 고정한다. 대가를 한 호흡에 — ⑴ 확장 설치·유지라는 운영 부담, ⑵ 분포가 바뀌어도 계획이 못 따라간다, ⑶ 인덱스 이름이라는 물리 정보가 코드에 결합된다, ⑷ 업그레이드로 플래너가 좋아져도 그 쿼리만 과거에 묶인다, ⑸ 증상을 덮어 진짜 원인이 다른 쿼리에서 재발한다.

그래서 순서는 **`ANALYZE` → statistics target·`CREATE STATISTICS` → 비용 파라미터 국소 교정 → 복합·부분 인덱스로 후보 단일화 → 그래도 안 되면 `pg_hint_plan`**이고, 쓴다면 **이슈 번호·이유·만료일을 붙이고 린트가 만료를 잡게** 한다. 한 단계 더 나은 답은 계획을 통째로 고정하는 대신 **`/*+ Rows(...) */`처럼 추정치만 고쳐 주는 힌트** — 플래너의 판단은 살려 두고 틀린 입력만 바로잡는 것이라 대가가 작다. "장애 중이라면 먼저 고정하고 나중에 정리하겠다"도 맞는 답이다 — 단, "나중"을 기계가 기억하게 하는 장치까지 말해야 상급이다.

### "플래너가 '틀린' 게 아니라 '맞게' 바꾼 경우는 어떻게 구분하나요?"

**`EXPLAIN (ANALYZE, BUFFERS)`로 추정과 실측의 거리를 잰다.** 새 계획의 추정 `rows`와 `actual rows`가 가까우면 플래너는 지금 데이터를 정확히 보고 있고 계획 전환은 옳다 — `status = 'FAILED'`가 1%에서 40%가 된 뒤의 Seq Scan은 정답이다. 이때 느린 것은 계획 탓이 아니라 **"실패 주문 전부를 읽는 쿼리"가 된 요구** 탓이므로, 대응은 쿼리·요구의 변경(기간 조건 강제, 아카이빙, 부분 인덱스, 파티셔닝)이다.

반대로 추정과 실측이 자릿수로 어긋나면 입력이 틀린 것이고, 그때는 `ANALYZE` → statistics target → `CREATE STATISTICS` 순서다. **PostgreSQL에서 함께 봐야 할 칸이 둘 더 있다** — `Rows Removed by Filter`(헛일의 크기)와 `Buffers`(실제 I/O). "플래너가 이상하다"는 말은 이 측정 전에는 할 수 없다.

### "autovacuum의 ANALYZE를 꺼버리면 안정적이지 않나요?"

**안정은 얻지만 낡음의 책임을 전부 떠안는다.** `autovacuum_enabled = false`로 두면 계획은 내가 ANALYZE할 때만 바뀌지만 대가가 셋이다. ⑴ 데이터가 10배로 자라도 통계는 그대로라 "낡은 통계로 인한 오판"이 영구화된다. ⑵ **PostgreSQL에서는 특히 위험한데, autovacuum을 끄면 ANALYZE만이 아니라 VACUUM까지 멈춘다** — bloat가 늘고 visibility map이 낡아 Index Only Scan이 퇴화하며, 최악의 경우 XID wraparound 위험까지 간다. ⑶ 예약 ANALYZE 잡이 실패하면 아무도 모른다.

그래서 PostgreSQL의 올바른 선택은 "끈다"가 아니라 **임계를 테이블 단위로 조정**(`autovacuum_analyze_scale_factor = 0.02`)이다. "재계산이 문제"가 아니라 **"재계산의 표본과 시점이 문제"**이므로, 표본은 statistics target으로 키우고(MCV 목록도 함께 넓어진다) 시점은 임계와 배치 끝 ANALYZE로 당긴다.

### "같은 쿼리인데 앱에서만 느리고 psql에선 빠릅니다. 재시작하면 잠깐 낫고요."

**PostgreSQL 준비문의 제네릭 계획 전환이다 — PostgreSQL 면접에서 이 답을 아는지가 갈림길이다.**

사슬로 말한다: pgjdbc가 같은 문장 5회 뒤 서버 준비문으로 전환하고, 서버는 커스텀 계획 다섯 번의 평균 비용과 제네릭 계획 비용을 비교해 **제네릭이 더 싸 보이면** 그쪽으로 고정한다. 제네릭 계획은 `$1`을 모르므로 `1 / n_distinct`(평균 선택도)를 쓰는데, **이 화면이 실제로 조회하는 값이 평균보다 훨씬 흔한 값이면** 플래너는 "몇 행 안 걸린다"고 믿고 인덱스 스캔·Nested Loop를 고른다 → 싸 보이므로 채택된다 → 실행하면 몇십만 행을 그 계획으로 처리한다.

psql에서 리터럴로 실행하면 커스텀 계획이라 빠르고, 앱을 재시작하면 준비문 캐시가 비어 잠깐 회복됐다가 여섯 번째 계획 수립부터 다시 느려진다. 확진은 **`EXPLAIN (GENERIC_PLAN)`(PG 16+)** 또는 `PREPARE` 후 여섯 번의 `EXPLAIN EXECUTE`.

즉시 완화는 `force_custom_plan`을 롤 단위로(대가: 매 실행 계획 수립 비용) 또는 pgjdbc `prepareThreshold=0`. 근본 대응은 **그 화면의 경로를 분리하는 것**(리터럴 쿼리, 별도 집계 테이블, 키셋 커서)과 **커버링·복합 인덱스로 후보를 하나로 만들어 커스텀이든 제네릭이든 같은 계획이 나오게 하는 것**이다. 여기서 흔한 오답 하나를 피해야 한다 — **부분 인덱스는 이 문제의 해결책이 아니다.** `status = $1`처럼 파라미터로 오면 플래너가 `$1 = 'FAILED'`임을 증명할 수 없어 부분 인덱스를 아예 후보에 넣지 못하기 때문이다. 부분 인덱스를 쓰려면 먼저 리터럴로 경로를 분리해야 하고, 분리하는 순간 제네릭 계획 문제도 같이 사라진다.

**(가산점 포인트)** `track_planning`을 켜면 `calls`는 느는데 `plans`가 안 느는 것으로 계획 재사용을 간접 확인할 수 있다.

### "메이저 업그레이드 전후로 실행 계획 변경을 어떻게 미리 잡나요?" (시니어 변별 포인트)

**두 가지를 분리해서 말해야 한다 — "플래너가 바뀌는 것"과 "통계가 사라지는 것".** 후자가 훨씬 흔하고 치명적이다: **`pg_upgrade`는 옵티마이저 통계를 새 클러스터로 옮기지 않는다.** 업그레이드 직후의 DB는 통계가 빈 상태라 모든 쿼리의 계획이 동시에 이상해지고, 사람들은 "새 버전이 나쁘다"고 오진한다. 그래서 절차의 마지막 줄은 반드시 `vacuumdb --all --analyze-in-stages`다.

전자(플래너 변경)의 절차는 ⑴ `pg_stat_statements` 상위 N개와 핵심 쿼리 목록을 뽑고, ⑵ 운영 스냅샷 스테이징을 새 버전으로 올린 뒤 **`ANALYZE`로 통계를 맞추고**(빼면 비교가 무의미하다), ⑶ 두 버전의 계획을 §3-5의 스크립트로 diff하고, ⑷ 바뀐 것은 실측해 좋아진 것과 나빠진 것을 나눈다. 나빠진 쿼리는 미리 인덱스를 손보거나 롤 단위 GUC를 브리지로 둔다.

한 호흡으로 — "업그레이드의 이득을 받되, 통계 재수집을 절차에 못 박고, 계획 diff로 손해 볼 쿼리를 미리 특정해 리스크를 좁힌다."

### "MySQL로 물어보면 답이 달라지는 부분은?" (경험 대조)

다섯 지점이다.

① **index dive의 유무** — MySQL은 상수 조건이면 인덱스 범위에 실제로 들어가 행 수를 세므로 통계가 낡아도 단순 조건은 비교적 정확하지만, PostgreSQL은 **오직 `pg_stats`만** 본다. 그래서 PostgreSQL에서는 "대량 적재 직후 ANALYZE"가 선택이 아니라 절차이고, 진단의 첫 수도 `ANALYZE`로 고정된다.

② **제네릭 계획** — PostgreSQL은 준비문 다섯 번 뒤 값을 안 보는 계획으로 고정될 수 있어 "여섯 번째부터 느려진다"가 생기지만, MySQL은 매 실행 재최적화라 이 함정이 없다. 대신 MySQL은 특정 값에서만 느린 형태로 온다 — 뿌리는 같은 스큐다.

③ **계획을 고정하는 수단** — MySQL은 `FORCE INDEX`·옵티마이저 힌트·`SET_VAR`가 문법에 있고 `INVISIBLE`로 인덱스를 즉시·가역적으로 후보에서 뺄 수 있지만, PostgreSQL은 힌트가 확장이고 INVISIBLE이 없어 인덱스 삭제가 비가역 결정이 된다. 대신 PostgreSQL은 **GUC를 전역/DB/롤/세션/트랜잭션 계층으로 좁혀 덮을 수 있다.**

④ **후보 비교를 보는 법** — MySQL은 `optimizer_trace`가 후보별 비용을 주지만, PostgreSQL은 `enable_*`를 하나씩 꺼서 재는 수동 방식이다(대신 PostgreSQL은 노드별 실제 블록을 준다).

⑤ **통계 수집의 단위** — MySQL은 인덱스별 카디널리티를 20페이지 표본으로 뜨고 히스토그램은 수동 갱신이지만, PostgreSQL은 컬럼별 MCV·히스토그램·correlation을 기본 통계로 갖고 autoanalyze가 갱신하며 컬럼 간 상관은 `CREATE STATISTICS`로 따로 만든다.

이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "차이를 원리로 이해했다"로 들린다.

## 한 줄 요약

**PostgreSQL 플래너는 통계·확장 통계·파라미터 값·비용 상수를 입력받아 후보 계획의 비용을 비교하는 함수라서, 코드도 쿼리도 안 바꿨는데 계획이 바뀌었다면 입력이 바뀌었거나(autoanalyze·통계 노후·n_distinct 오추정·MCV 목록 교체·**제네릭 계획 전환**), 후보가 바뀌었거나(인덱스 추가·삭제·INVALID), 함수가 바뀐 것(GUC·메이저 업그레이드 — **`pg_upgrade`는 통계를 안 옮긴다**)이다. 등호 조건의 추정은 세 갈래로 갈리는데 — 값이 MCV에 있으면 정확한 빈도, 없으면 "나머지 균등 분배", 값을 아예 모르면 `1/n_distinct` — **값 하나가 MCV 목록에서 밀려나는 순간 추정이 계단처럼 점프하는 것**이 "어제까지 잘 되던 특정 값만 갑자기"의 정체이고, **제네릭 계획은 자기 추정이 커스텀 평균보다 싸 보일 때만 채택되므로 사고의 피해자는 늘 "평균보다 훨씬 흔한 값만 조회하는 화면"**이다. PostgreSQL에는 index dive도, 힌트 문법도, INVISIBLE 인덱스도 없으므로 통계가 유일한 진실이고 대응 순서가 강제로 고정된다 — `ANALYZE` → statistics target → `CREATE STATISTICS` → 비용 파라미터 국소 교정 → 부분·복합 인덱스로 후보 단일화 → 최후에 `pg_hint_plan`(원인이 제네릭 계획이면 그 앞에 `force_custom_plan`). 진단은 느려진 시각 → 건당 읽은 블록 비교 → `auto_explain` 로그의 계획 diff → `last_autoanalyze`·`pg_stats`·**문제의 값이 MCV에 있는지** 확인 순서이며, 배포 없이 일어나는 변경이므로 EXPLAIN 베이스라인 잡(대표값과 최악값 두 벌로)·pg_stat_statements 스냅샷 알람·배치 끝 ANALYZE·업그레이드 런북의 `vacuumdb --analyze-in-stages`를 기계에 맡겨야 사용자보다 먼저 안다.**
