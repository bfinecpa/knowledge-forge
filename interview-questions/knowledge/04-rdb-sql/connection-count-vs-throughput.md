# DB 커넥션 수와 처리량 — 커넥션은 "처리 능력"이 아니라 "줄 서는 자리"다

> 핵심 관전 포인트: **커넥션을 늘리면 처리량은 어느 지점까지만 오르고,
> 그 뒤로는 평평해지다가 오히려 떨어진다. DB가 실제로 동시에 일할 수
> 있는 양은 커넥션 수가 아니라 DB 서버의 CPU 코어 수와 디스크 병렬성이
> 정하기 때문이다. 그 한계를 넘긴 커넥션은 일을 더 시키는 게 아니라
> 경합을 더 만든다 — ① CPU 컨텍스트 스위칭 ② 디스크 I/O 큐 적체와
> 순차 I/O의 랜덤화 ③ 락 경합 ④ 버퍼 풀·내부 뮤텍스 경합, 이 네 사슬이
> 쿼리 하나하나를 느리게 만들어 총처리량을 깎는다. 그래서 "느리니까
> 커넥션을 늘리자"는 처방은 병목 위치(앱 스레드 풀 → 커넥션 풀 → DB CPU
> → 디스크 I/O → 락 대기)를 확인한 뒤에만 유효하고, 풀 크기는 경험식으로
> 출발해 부하 테스트와 active/pending/acquire-time 메트릭으로 고정한다.**

---

## 0. 질문 + 의도

**질문**: "DB 커넥션 수와 처리량(throughput)의 관계 — 커넥션을 늘리면
항상 빨라지나요?"

**출제 의도**: "느리니까 커넥션을 늘리자"는 직관이 왜 역효과인지(경합 증가)를
아는지 확인한다. 더 깊게는 **병목의 위치를 확인하지 않은 처방이 얼마나
위험한지에 대한 감각**을 검사하는 질문이다 — 커넥션 풀 크기는 설정 한 줄이라
누구나 만질 수 있는데, 그 한 줄이 DB 전체를 무너뜨릴 수 있다는 걸 아는
사람과 모르는 사람의 운영 태도가 다르다.

> 이 문서는 사전 학습용이다. 4장 기본 구간에서 반복된 공백 — 비용을
> "성능 저하", "부하 증가" 같은 뭉뚱그린 표현이 아니라 **이름 붙은 메커니즘
> 사슬**로 말하기, 특히 **랜덤 vs 순차 I/O** 축 — 을 이 질문에서 메우는
> 것이 1차 목표다. 2장에서 다룬 풀 크기 산정(Little's law)과 고갈 진단은
> 반복하지 않고 링크로 대신한다:
> [`../02-spring/thread-pool-connection-pool-sizing.md`](../02-spring/thread-pool-connection-pool-sizing.md),
> [`../02-spring/hikaricp-connection-pool-exhaustion.md`](../02-spring/hikaricp-connection-pool-exhaustion.md).
> 여기서는 **DB 서버 내부에서 무슨 일이 벌어지는가**에 집중한다.

## 1. 큰 그림 — 처리량 곡선은 오르다가 꺾인다

커넥션 수(= DB에 동시에 들어와 있는 요청 수)를 가로축, 초당 처리 건수를
세로축으로 그리면 거의 모든 DB에서 같은 모양이 나온다.

```text
처리량(TPS)
  ▲
  │            ┌───────┐  ← ② 포화: 늘려도 그대로
  │         ┌──┘       └──┐
  │      ┌──┘             └───┐   ← ③ 붕괴: 늘릴수록 떨어진다
  │   ┌──┘                    └────
  │ ┌─┘  ← ① 선형 증가 구간
  │─┘
  └──────────────────────────────────▶ 동시 커넥션 수
        (코어 수 근처)
```

- **① 선형 구간**: 커넥션이 코어 수보다 적으면 CPU가 놀고 있다. 커넥션을
  늘리는 만큼 처리량이 는다. "커넥션을 늘리면 빨라진다"는 직관은 **이
  구간의 경험**이다.
- **② 포화 구간**: DB의 CPU와 디스크가 이미 쉬지 않고 일한다. 커넥션을
  더 넣어도 처리량은 그대로 — 새로 들어온 요청은 DB 안에서 **대기**할 뿐이다.
- **③ 붕괴 구간**: 대기하는 요청 자체가 비용을 만든다(2절의 네 사슬).
  쿼리 하나의 실행 시간이 늘어나고, 그 결과 총처리량이 **오히려 떨어진다.**

비유하면 **은행 창구(코어)는 8개인데 번호표(커넥션)를 500장 뿌린 상황**이다.
번호표를 더 뿌린다고 창구가 늘지 않는다. 오히려 대기 손님이 로비를
가득 채워 직원 이동을 방해하고(컨텍스트 스위칭), 서류 보관함 앞에서 서로
부딪히고(버퍼 풀 경합), 같은 계좌를 처리하려고 서로 기다린다(락 경합).

핵심 문장: **커넥션은 "DB가 동시에 처리할 수 있는 능력"이 아니라 "DB
앞에 동시에 서 있을 수 있는 자리 수"다.** 능력의 상한은 DB 서버의
CPU 코어 수와 디스크 병렬성이 정한다.

### DB는 커넥션마다 실행 단위를 하나씩 붙인다

이 곡선이 왜 생기는지 이해하려면 DB가 커넥션을 어떻게 다루는지 알아야 한다.

- **MySQL**: 커넥션 하나당 서버 **스레드** 하나. 쿼리가 오면 그 스레드가
  실행한다.
- **PostgreSQL**: 커넥션 하나당 **백엔드 프로세스** 하나(fork). 스레드보다
  훨씬 무겁다 — 프로세스마다 독립 메모리, 캐시된 카탈로그 등을 따로 가진다.

즉 커넥션 500개 = DB 서버 안에 실행 단위 500개가 살아 있다는 뜻이다.
이 500개 중 실제로 CPU 위에서 도는 건 코어 수만큼뿐이고, 나머지는
어딘가에서 **대기 중**이다. 어디서 어떻게 대기하느냐가 2절의 내용이다.

## 2. 역효과의 메커니즘 사슬 — "경합 증가"를 네 개의 이름으로 쪼개기

> 겨냥하는 공백: 지금까지 비용을 말할 때마다 "성능 저하", "메모리 부하",
> "부하 증가"에서 멈췄다. 면접관이 "커넥션을 늘리면 왜 역효과인가요?"라고
> 물을 때 "경합이 늘어서요"는 **답의 제목**일 뿐이다. 아래 네 사슬을
> 각각 **이름 → 원인 → 결과**의 화살표로 말할 수 있어야 한다.

```text
커넥션 수 ↑ (= DB 안의 동시 실행 단위 ↑)
   │
   ├─ A. CPU: 실행 가능 스레드 > 코어 수 → 컨텍스트 스위칭 ↑, 캐시 오염
   ├─ B. 디스크: I/O 큐 적체 + 순차 접근이 랜덤으로 뒤섞임 → IOPS 정체·하락
   ├─ C. 락: 동시 트랜잭션 ↑ → 같은 행/갭 충돌 확률 ↑ → 대기 → 트랜잭션 길어짐 → 더 많은 대기
   └─ D. 메모리: 세션 메모리 ↑ → 버퍼 풀 몫 ↓ + 워킹셋 합 > 버퍼 풀 → 히트율 ↓ → B로 되돌아감
                                          + 내부 뮤텍스/래치 경합 → 스핀으로 CPU 낭비
   │
   ▼
쿼리 1건의 실행 시간 ↑  →  초당 처리 건수 ↓  +  p99 응답시간 ↑
```

### 사슬 A — CPU 컨텍스트 스위칭

- 코어가 8개인데 실행하려는 스레드가 200개면, OS는 수 ms 단위로 코어를
  돌려가며 태운다(시분할). 스레드를 바꿔 태울 때마다 **레지스터·스택 상태를
  저장/복원**하고, 방금 전 스레드가 데워둔 **CPU 캐시(L1/L2)가 다른 스레드의
  데이터로 덮인다**(캐시 오염).
- 이 비용은 "쿼리 실행"이 아닌 "쿼리 사이를 오가는" 데 쓰이는 CPU다. 즉
  같은 CPU 100%인데 **실제 쿼리 처리에 쓰인 몫이 줄어든다.**
- DB 쪽 시그니처: `vmstat`의 `cs`(context switch/초)가 폭증하고 `r`(run queue)이
  코어 수를 크게 넘는데, MySQL `Threads_running`은 수백인데 처리량은 안 오른다.

I/O 대기 중인 스레드는 CPU를 안 쓰므로 컨텍스트 스위칭 비용이 없다고
생각하기 쉬운데, 커넥션이 많으면 **깨어나는 스레드도 그만큼 많다** —
I/O가 끝날 때마다 깨어나 run queue에 줄을 서고, 그 줄이 코어 수보다 길면
다시 시분할 비용이 든다.

### 사슬 B — 디스크 I/O 큐, 그리고 순차 I/O의 랜덤화

> 겨냥하는 공백: **랜덤 vs 순차 I/O 비용 모델** — 기본 구간에서 5회 연속
> 비어 있던 축이다. 북마크 룩업(Q2)·페이지 분할(Q3)·redo log(Q5)가 전부
> 이 축 위에 있었고, 여기서는 "왜 디스크가 병목일 때 동시성을 올리는 게
> 무의미하거나 해로운가"로 같은 축이 다시 등장한다.

먼저 비용 모델 자체를 한 번 더 고정한다.

- **순차 I/O**: 디스크의 연속된 블록을 쭉 읽는다. HDD라면 헤드를 한 번
  놓고 플래터가 도는 대로 읽기만 하면 된다. 매우 싸다.
- **랜덤 I/O**: 매 블록마다 다른 위치로 헤드를 옮긴다(seek, 밀리초 단위).
  HDD에서 순차와 랜덤의 처리량 차이는 **자릿수가 다르다.** SSD는 seek가
  없어 격차가 크게 줄지만, 여전히 "한 번에 크게 읽기"가 "작게 여러 번"보다
  싸고, 컨트롤러가 동시에 처리할 수 있는 요청 수(큐 깊이)에 상한이 있다.

이제 커넥션을 늘렸을 때 디스크에서 벌어지는 일 두 가지:

**(1) 큐만 길어진다 — IOPS는 고정**

디스크가 초당 처리할 수 있는 I/O 수(IOPS)는 장치가 정한 상수다. 이미
`iostat`의 `%util`이 100%에 붙어 있다면, 커넥션을 늘려 I/O 요청자를 늘려도
**초당 처리되는 I/O 수는 1도 안 는다.** 요청은 디스크 큐에 쌓이고
`await`(요청당 평균 대기+처리 시간)만 길어진다. 각 쿼리는 그만큼 느려지고,
느려진 쿼리는 커넥션을 더 오래 물고, 앱 풀도 따라서 마른다.

**(2) 순차가 랜덤으로 뒤섞인다 — IOPS가 오히려 떨어진다**

이게 더 중요한 포인트다. 커넥션 하나가 인덱스 리프를 따라가거나 큰 테이블을
스캔할 때, **그 쿼리 하나만 보면 접근은 순차적**이다. 그런데 이런 쿼리
50개가 동시에 돌면, 디스크가 받는 요청 스트림은 50개 쿼리의 요청이
**번갈아 섞인 것**이 된다.

```text
쿼리 1 혼자:   블록 100, 101, 102, 103, 104 ...        ← 순차 (헤드 이동 거의 없음)
쿼리 2 혼자:   블록 9000, 9001, 9002, 9003 ...          ← 순차

둘이 동시에:   100, 9000, 101, 9001, 102, 9002 ...      ← 디스크 입장에선 랜덤
               (매 요청마다 헤드가 100번대 ↔ 9000번대를 왕복)
```

각 쿼리는 순차 스캔을 하고 있다고 믿지만, 디스크는 매 요청마다 seek를
한다. 동시성이 올라갈수록 **디스크가 실제로 뽑아내는 처리량이 순차 수준에서
랜덤 수준으로 떨어진다.** 그래서 디스크가 병목인 시스템에서는 동시 커넥션을
늘리는 것이 "무의미"를 넘어 "해롭다". 반대로 커넥션을 줄이면 각 스캔이
순차성을 회복해 **총 디스크 처리량이 오른다** — 6절 사례의 물리적 근거
중 하나다. (OS와 디스크 컨트롤러가 요청을 재정렬해 완화해 주긴 하지만,
요청자 수가 많을수록 재정렬로 살릴 수 있는 순차성 자체가 줄어든다.)

SSD·클라우드 블록 스토리지에서는 seek 비용이 없으니 (2)는 약해지고 (1)이
주로 남는다. 다만 클라우드 볼륨은 **IOPS 자체가 상품 스펙으로 상한이
걸려 있어** (1)이 더 일찍, 더 딱딱하게 온다.

### 사슬 C — 락 경합

- 동시에 진행 중인 트랜잭션이 많아지면, 같은 행이나 같은 갭을 잡으려는
  **충돌 확률이 조합적으로** 는다(트랜잭션 n개면 쌍은 n(n-1)/2개).
- 충돌한 트랜잭션은 락을 기다리고, **기다리는 동안 자기 커넥션·자기가
  이미 잡은 락·undo 스냅샷을 전부 쥐고 있다.** 즉 트랜잭션이 길어진다.
- 트랜잭션이 길어지면 락 점유 시간이 늘고, 그만큼 뒤에 오는 트랜잭션이
  더 오래 기다린다 — **대기 → 장기화 → 더 많은 대기**의 되먹임.
- 핫 로우(재고 1건, 카운터 1행)가 있다면 처리량은 결국 **그 행을 잠그고
  푸는 속도로 직렬화**된다. 커넥션 500개든 5개든 그 행은 한 번에 하나씩만
  갱신되므로, 500개는 처리량을 못 올리고 대기열과 데드락 검사 비용만 만든다.
- 시그니처: MySQL `Innodb_row_lock_waits`·`Innodb_row_lock_time_avg` 상승,
  `SHOW PROCESSLIST`에 `Waiting for lock`/`updating` 상태 다수,
  PostgreSQL `pg_stat_activity`의 `wait_event_type = 'Lock'` 다수.

여기서 2장의 고갈 문서와 연결된다: 락 대기로 트랜잭션이 길어지면
커넥션 점유 시간이 늘고, 앱 풀이 마르고, 톰캣 스레드까지 마른다. 락
경합은 **DB 내부 현상이지만 장애는 앱 전체에서 터진다.**

### 사슬 D — 버퍼 풀·내부 자원 경합

- **메모리 배분**: 커넥션(세션)마다 정렬 버퍼·조인 버퍼·임시 테이블 같은
  **세션 전용 메모리**가 붙는다. 커넥션 수 × 세션 메모리만큼 DB 서버의
  RAM이 빠져나가고, 그만큼 **버퍼 풀(데이터 페이지 캐시)에 줄 수 있는
  몫이 줄어든다.** PostgreSQL은 프로세스 단위라 이 비용이 더 크다.
- **워킹셋 초과**: 동시에 도는 쿼리가 많아지면 그들이 만지는 페이지의
  합(워킹셋)이 커진다. 합이 버퍼 풀 크기를 넘는 순간 **캐시 히트율이
  떨어지고 디스크 읽기가 늘어** 사슬 B로 되돌아간다. 커넥션 50개일 땐
  메모리에서 다 처리되던 쿼리들이 200개가 되면 디스크를 때리기 시작하는
  현상이 이것이다.
- **내부 뮤텍스/래치**: 버퍼 풀 페이지 목록, 로그 버퍼, 트랜잭션 ID 발급,
  락 테이블 같은 DB 내부 자료구조는 짧은 락(뮤텍스·래치)으로 보호된다.
  동시 스레드가 많아지면 이 짧은 락에서도 줄이 생기고, 대기 방식이
  스핀(짧게 CPU를 돌며 재시도)이라 **CPU를 쓰면서 기다리는** 낭비가 는다.
  MySQL이 `innodb_thread_concurrency` 같은 내부 동시 실행 상한 옵션을
  가지고 있는 이유가 바로 이 경합을 DB 스스로 억제하기 위해서다(가산점 포인트).

### 네 사슬을 한 문장으로

"커넥션을 늘리면 DB 안의 동시 실행 단위가 늘고, 그것이 **CPU에선
컨텍스트 스위칭, 디스크에선 큐 적체와 순차 I/O의 랜덤화, 트랜잭션
사이에선 락 경합, 메모리에선 버퍼 풀 몫 감소와 히트율 하락**을 일으켜
쿼리 하나하나가 느려지고 총처리량이 떨어진다."

이 한 문장을 말한 뒤 면접관이 어느 사슬을 파고들어도 한 단계씩 더
내려갈 수 있으면 이 질문은 통과다.

## 3. 트레이드오프 양면 — 커넥션을 늘리는 것이 맞는 경우와 틀린 경우

> 겨냥하는 공백: 트레이드오프를 **한 호흡에 양면으로** 조립하기. "늘리면
> 안 된다"로 끝내면 반쪽이다. 늘리는 것이 정답인 조건과 오답인 조건을
> 같은 문장 안에서 대비시킨다.

| 상황 | 커넥션 늘리기의 효과 | 판단 |
|---|---|---|
| DB CPU 여유(예: 40%), 디스크 여유, 락 대기 없음, 앱 `pending` 발생 | 처리량 선형 증가 (곡선 ① 구간) | **늘리는 게 맞다** |
| DB CPU 포화, 앱 `pending` 발생 | 처리량 그대로, DB 응답시간 ↑ (② 구간) | 늘려도 소용없음 — 점유 시간 단축·쿼리 튜닝 |
| 디스크 `%util` 100%, `await` 상승 | IOPS 정체 + 순차 I/O 랜덤화로 처리량 ↓ (③ 구간) | **줄이는 게 맞다** — 인덱스·버퍼 풀·I/O 줄이기 |
| 락 대기 지표 상승 | 충돌 확률 ↑, 트랜잭션 장기화 | 줄이거나, 락 범위·트랜잭션 길이 축소 |
| DB 여유 있는데 앱 `pending`도 없음 | 아무 효과 없음 | 병목이 다른 곳(앱 CPU, 외부 API) |

표를 양면 문장으로 조립하면:

> "커넥션을 늘리면 **DB가 놀고 있을 때는** 놀던 코어를 채워 처리량이
> 오르지만, **DB가 이미 포화일 때는** 대기 줄을 DB 내부로 옮겨 컨텍스트
> 스위칭·I/O 랜덤화·락 경합만 키워 처리량이 떨어진다. 그래서 늘리기 전에
> DB 쪽 지표로 어느 구간에 있는지부터 확인한다."

덧붙일 양면 하나 더 — **대기의 위치**. 커넥션을 줄이면 앱 쪽 풀에서
대기(`pending`)가 생긴다. 이건 나빠진 게 아니라 **대기를 DB 내부(비싼 대기:
CPU·락·버퍼를 쥔 채 기다림)에서 앱 풀(싼 대기: 스레드가 park만 하고 DB
자원은 전혀 안 씀)로 옮긴 것**이다. 총 대기 시간이 같아도 DB는 최적
동시성으로 돌아 처리량이 오르고, 그 덕에 대기 총량도 줄어드는 경우가
대부분이다. 다만 앱 쪽 대기가 톰캣 스레드를 묶어 스레드 풀 고갈로 번지지
않도록 `connection-timeout`을 짧게 두고 빨리 실패시키는 안전장치가 함께
필요하다(고갈 문서 5절).

## 4. 병목 위치 확인 순서 — 처방 전 진단 체크리스트

> 겨냥하는 공백: **목록 인출**. 장애 중에 "어디가 병목인지 어떻게 확인하나요?"
> 를 받으면 아래 다섯 단계를 **순서대로, 각 단계의 확인 지표와 함께**
> 꺼낼 수 있어야 한다. 순서에 의미가 있다 — 요청이 흐르는 방향(앱 → DB →
> 디스크)을 따라가며, 앞 단계가 병목이 아님을 확인한 뒤 다음으로 내려간다.

```text
요청 → [1] 앱 스레드 풀 → [2] 커넥션 풀 → [3] DB CPU → [4] 디스크 I/O → [5] 락 대기
```

| 단계 | 확인 지표 | 병목일 때의 시그니처 | 처방 방향 |
|---|---|---|---|
| [1] 앱 스레드 풀 | `tomcat.threads.busy` vs max, 앱 CPU | busy가 max에 붙고 DB는 한가 | 스레드 수 재산정, 앱 CPU 병목 확인 |
| [2] 커넥션 풀 | `hikaricp.connections.active/pending`, `acquire` 시간 | active = max, pending > 0, acquire 시간 ↑ | **여기서 멈추지 말 것** — [3]~[5]로 내려가 "왜 커넥션이 안 돌아오는지" 확인 |
| [3] DB CPU | DB 호스트 CPU, `Threads_running`, `vmstat cs/r` | CPU 90%↑, Threads_running ≫ 코어, cs 폭증 | 커넥션 줄이기 + 쿼리 CPU 비용 튜닝 |
| [4] 디스크 I/O | `iostat %util/await/r/s`, 버퍼 풀 히트율 | %util 100%, await ↑, 히트율 ↓ | 커넥션 줄이기 + 인덱스·커버링·버퍼 풀 확대 |
| [5] 락 대기 | `Innodb_row_lock_waits`, `sys.innodb_lock_waits`, PG `wait_event_type=Lock` | 락 대기 수·시간 ↑, PROCESSLIST에 대기 다수 | 트랜잭션 짧게, 락 범위 축소, 핫 로우 분산 |

각 단계의 읽는 법:

- **[1] → [2]**: 앱 스레드가 놀고 있는데 커넥션 pending이 있다면 문제는
  DB 쪽이다. 반대로 스레드가 꽉 찼는데 커넥션은 여유면 DB와 무관한
  병목(외부 API, 앱 CPU)이다.
- **[2]에서 멈추는 것이 가장 흔한 실수.** `pending`이 보이면 "커넥션이
  부족하다"로 읽고 늘리고 싶어진다. 하지만 pending은 **커넥션이 안 돌아오고
  있다**는 뜻이지 **커넥션 개수가 모자란다**는 뜻이 아니다. 안 돌아오는
  이유가 [3]~[5] 중 어디인지 확인하기 전에는 처방을 내리지 않는다.
- **[3] vs [4] 구분**: DB CPU가 높고 디스크가 한가하면 CPU 바운드(정렬·조인·
  함수 연산이 무거운 쿼리), CPU는 낮은데 `iowait`·`%util`이 높으면 I/O
  바운드(버퍼 풀 미스, 풀스캔). 처방이 다르다 — 전자는 쿼리 연산량, 후자는
  읽는 페이지 수를 줄인다.
- **[5]는 CPU도 디스크도 한가한데 느릴 때** 의심한다. 자원은 놀고 있는데
  트랜잭션들이 서로를 기다리는 상태다. 이때 커넥션을 늘리면 대기자만 는다.

```sql
-- [3] MySQL: 실제로 실행 중인 스레드 수 (커넥션 수와 다르다)
SHOW GLOBAL STATUS LIKE 'Threads_running';    -- 코어 수의 몇 배면 CPU 경합 의심
SHOW GLOBAL STATUS LIKE 'Threads_connected';  -- 이건 그냥 붙어 있는 수

-- [4] MySQL: 버퍼 풀 히트율 — reads(디스크) / read_requests(논리)
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';

-- [5] MySQL: 지금 누가 누구를 기다리는가
SELECT * FROM sys.innodb_lock_waits;

-- [3]~[5] PostgreSQL: 세션별로 무엇을 기다리는지 한 번에
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE state = 'active'
GROUP BY 1, 2 ORDER BY 3 DESC;
-- wait_event_type이 NULL이면 CPU 실행 중, 'IO'면 디스크, 'Lock'이면 락, 'LWLock'이면 내부 래치
```

이 체크리스트의 존재 이유는 "커넥션을 늘릴까 줄일까"가 아니다. **어느
자원이 포화인지 알기 전에는 어떤 처방도 도박**이라는 것 — 출제 의도가
말하는 "병목 위치를 확인하지 않은 처방의 위험"이 정확히 이것이다.

## 5. 풀 크기를 고정하는 방법 — 경험식으로 출발, 측정으로 확정, 알람으로 유지

> 겨냥하는 공백: **안전망 고정**. 풀 크기를 "감으로 50" 또는 "공식 대로 17"로
> 정하고 끝내는 게 아니라, 부하 테스트로 곡선의 꺾이는 지점을 찾고 메트릭
> 알람으로 이탈을 감지하는 체계까지 말한다.

### 5-1. 경험식 — HikariCP 위키의 출발점

HikariCP 위키(About Pool Sizing)가 제시하는 식:

```text
connections = (DB 서버 코어 수 × 2) + 유효 스핀들 수
```

- 이 식은 **경험식(rule of thumb)이지 정리(theorem)가 아니다.** 위키
  스스로도 "출발점"이라고 못 박는다.
- 왜 이런 형태인가 — 항이 곧 1~2절의 내용이다:
  - **코어 수**: 동시에 CPU 위에서 돌 수 있는 쿼리의 상한(사슬 A).
  - **× 2**: 한 스레드가 디스크 I/O를 기다리는 동안 다른 스레드가 CPU를
    쓰게 하려는 겹치기(overlap) 여유. I/O 대기 비율이 높을수록 이 계수는
    더 커도 되고, 데이터가 전부 메모리에 있으면 1에 가까워도 된다.
  - **유효 스핀들 수**: 독립적으로 I/O를 동시에 처리할 수 있는 디스크 수
    (사슬 B의 디스크 병렬성). 스핀들 수만큼은 동시에 I/O를 걸어도 서로
    큐를 만들지 않는다는 뜻이다.
- 한계: SSD·NVMe·클라우드 볼륨에는 "스핀들"이라는 물리 단위가 없다. 큐
  깊이·IOPS 상한을 대신 넣어야 하는데 정확한 환산은 없다. 따라서 이 식은
  **자릿수를 잡는 용도**로만 쓰고, 최종 숫자는 반드시 측정으로 정한다.
- 앱 인스턴스가 N대면 DB에는 **N × 풀 크기**가 꽂힌다. 공식이 주는 숫자는
  **DB 전체 기준**이므로 인스턴스 수로 나눠야 한다. 오토스케일링으로 앱이
  10대에서 30대가 되면 DB 커넥션도 3배가 된다는 걸 계산에 넣지 않으면
  트래픽 피크에 DB가 붕괴 구간으로 밀려난다.

### 5-2. 부하 테스트 — 곡선의 꺾이는 지점을 직접 그린다

```text
절차
1. 실제와 비슷한 쿼리 믹스·데이터 크기로 부하 도구(k6, Gatling 등) 준비
2. 풀 크기를 단계적으로 바꿔가며(예: 5 → 10 → 20 → 40 → 80) 같은 부하를 건다
3. 각 단계에서 기록: TPS, p50/p99 응답시간, DB CPU, iostat %util, 락 대기 수
4. TPS가 더 이상 오르지 않는 지점(포화)과 p99가 급격히 나빠지는 지점(붕괴)을 찾는다
5. 포화 지점보다 약간 아래를 채택 — 여유는 커넥션 수가 아니라 응답시간에 둔다
```

- 측정 없이 "일단 크게 잡아두면 안전하겠지"가 가장 위험하다. 큰 풀은
  평소엔 조용하다가 **트래픽 피크에 DB를 붕괴 구간으로 밀어 넣는** 시한폭탄이다.
- 반대로 너무 작으면 앱 pending이 상시 발생한다. 이때는 풀을 키우기 전에
  **커넥션 점유 시간**(트랜잭션 안의 외부 호출, 느린 쿼리)부터 줄인다 —
  같은 TPS를 더 작은 풀로 감당하는 게 언제나 DB에 이롭다.

### 5-3. 메트릭과 알람 — 결정을 코드로 고정한다

```yaml
# before — "느리다"는 보고에 감으로 늘린 설정
spring:
  datasource:
    hikari:
      maximum-pool-size: 200        # 근거 없음. 인스턴스 10대면 DB에 2,000개
      connection-timeout: 30000     # 30초 대기 → 톰캣 스레드까지 30초씩 묶임
```

```yaml
# after — 측정으로 정한 크기 + 빨리 실패 + 관측 가능
spring:
  datasource:
    hikari:
      maximum-pool-size: 12         # 부하 테스트에서 TPS 포화 지점(DB 8코어, 인스턴스 10대 → DB 전체 120)
      minimum-idle: 12              # 피크에 커넥션 생성 비용을 치르지 않도록 고정 크기
      connection-timeout: 3000      # 3초 안에 못 받으면 실패 — 대기 줄이 스레드 풀로 전이되는 걸 차단
      leak-detection-threshold: 30000
management:
  metrics:
    enable:
      hikaricp: true                # hikaricp.connections.{active,idle,pending,acquire,usage,timeout}
```

알람으로 걸어둘 것(임계값은 부하 테스트에서 본 정상 범위 기준):

- `hikaricp.connections.pending` — 0보다 큰 상태가 지속되면 "커넥션이 안
  돌아온다". 4절 체크리스트의 시작 신호.
- `hikaricp.connections.acquire`(획득 대기 시간 p99) — 커넥션을 받기까지
  기다린 시간. 응답시간 악화의 선행 지표.
- `hikaricp.connections.usage`(점유 시간 p99) — 커넥션을 물고 있는 시간.
  이게 늘면 풀 크기가 아니라 **점유 시간이 문제**다.
- `hikaricp.connections.timeout` — 획득 실패 건수. 0이 아니면 이미 사용자
  영향.
- DB 쪽: `Threads_running`이 코어 수의 배수를 넘는 지속 시간, 락 대기
  시간, 버퍼 풀 히트율 하락. **앱 pending과 DB 지표를 같은 대시보드에
  나란히** 두어야 "pending이 뜨는데 DB CPU는 포화인가 여유인가"를 한눈에
  읽고 4절의 처방 방향을 즉시 고를 수 있다.

풀 크기 결정 근거(테스트 날짜·부하 조건·채택 이유)는 설정 파일 주석이나
운영 위키에 남긴다. 반년 뒤 다른 사람이 "느리니까 늘리자"를 반복하지
않게 하는 것까지가 안전망이다.

## 6. 실제 사례 — 풀을 줄였더니 빨라졌다

HikariCP 위키가 인용하는 Oracle 성능팀의 시연이 이 현상의 대표 사례다.
수천 개 수준(약 2,000개)이던 커넥션 풀을 100개 미만으로 줄이자 쿼리
응답시간이 수십 배 빨라지고 처리량이 올랐다. 하드웨어도 쿼리도 그대로였다.

이 결과를 "신기한 일"이 아니라 **구조적으로** 설명할 수 있어야 한다.
아래는 같은 구조를 가진 전형적 시나리오다(예시 수치).

```text
[증상] 피크 시간 API p99 2초. 앱 로그에 "Connection is not available" 간헐 발생.
[첫 처방] "커넥션이 모자라구나" → maximum-pool-size 30 → 100 (인스턴스 10대 → DB 커넥션 300 → 1,000)
[결과] 타임아웃 로그는 줄었는데 p99가 2초 → 5초로 악화. DB CPU 100%.
```

늘렸는데 왜 나빠졌는가 — 1~2절로 읽으면:

- DB는 8코어. 커넥션 300일 때 이미 `Threads_running`이 수십 개로 코어를
  넘어 **포화 구간**에 있었다. 앱의 타임아웃은 "커넥션 부족"이 아니라
  "DB가 느려서 커넥션이 안 돌아옴"의 신호였다.
- 1,000개로 늘리자 DB 안의 대기자가 3배가 됐다. 사슬 A로 컨텍스트 스위칭이
  폭증해 CPU 100% 중 쿼리 실행에 쓰이는 몫이 줄었고, 사슬 D로 세션 메모리가
  버퍼 풀을 잠식하고 동시 쿼리의 워킹셋이 버퍼 풀을 넘어 히트율이 떨어졌으며,
  사슬 B로 디스크 읽기가 늘고 그 읽기들이 서로 뒤섞여 랜덤화됐다. 락이 걸리는
  UPDATE는 사슬 C로 대기열이 3배가 됐다.
- 타임아웃 로그가 줄어든 건 **앱에서의 대기가 DB 안으로 옮겨갔기** 때문이다.
  대기가 사라진 게 아니라 **더 비싼 곳에서 대기**하게 됐다.

```text
[진단] 4절 순서로: 톰캣 스레드 여유 → Hikari pending 다수 → DB CPU 100%,
       Threads_running ≈ 150 (코어 8), vmstat cs 폭증, 버퍼 풀 히트율 하락, 락 대기 상승
[두 번째 처방] maximum-pool-size 100 → 8 (DB 전체 80), connection-timeout 3초
[결과] Threads_running ≈ 12~16, DB CPU 75%, p99 5초 → 300ms, TPS 상승.
       앱 pending은 간헐 발생하지만 acquire p99 수십 ms 수준.
```

줄였는데 왜 좋아졌는가:

- DB 안의 동시 실행 단위가 코어 수 근처로 내려오자 **컨텍스트 스위칭이
  사라지고 CPU가 온전히 쿼리에 쓰였다.** 같은 CPU 75%가 이전 100%보다 더
  많은 쿼리를 처리한다.
- 동시 쿼리의 워킹셋이 버퍼 풀 안에 들어오면서 **히트율이 회복**됐고,
  줄어든 디스크 읽기는 서로 덜 섞여 **순차성을 되찾았다.**
- 동시 트랜잭션이 줄어 **락 충돌 확률이 떨어지고** 트랜잭션이 짧아졌다.
- 그 결과 쿼리 1건의 실행 시간이 크게 줄었고, 커넥션이 빨리 돌아오니
  **80개로도 1,000개일 때보다 많은 요청을 처리**했다. 대기는 앱 풀에서
  잠깐(park) 발생할 뿐 DB 자원은 소모하지 않는다.

이 사례의 교훈을 한 문장으로: **"대기 줄은 어디에든 생긴다. 그 줄을 DB
안(비싼 대기)에 세울 것인가, DB 앞의 앱 풀(싼 대기)에 세울 것인가가
풀 크기 결정의 본질이다."** 작은 풀은 DB를 최적 동시성으로 돌리기 위한
**의도적인 관문(throttle)** 이다.

남은 pending을 더 줄이고 싶다면 풀을 키우는 게 아니라 **점유 시간을
줄인다** — 트랜잭션 안의 외부 호출 제거, 느린 쿼리 튜닝, 읽기 트래픽의
레플리카 분리. 이 방향은 2장 산정 문서의 Little's law(동시수 = TPS ×
점유 시간)가 그대로 말해 준다.

## 7. 꼬리질문 대비 포인트

### "그럼 커넥션을 늘리는 게 정답인 경우는 언제인가요?"

DB가 **놀고 있을 때**다. 구체적으로 DB CPU 여유, 디스크 `%util` 여유,
락 대기 없음 — 이 세 가지가 동시에 만족되는데 앱 쪽 `hikaricp.connections.pending`
이 발생하면, 커넥션이 DB의 처리 능력보다 적어서 코어가 비는 상태다(1절
곡선의 ① 구간). 이때는 늘리면 처리량이 선형으로 오른다. 반대로 셋 중
하나라도 포화면 늘리는 것은 대기 줄을 DB 내부로 옮기는 것일 뿐이다.
"늘려도 되는가"는 앱 메트릭이 아니라 **DB 메트릭이 결정**한다는 것이
답의 핵심이다.

### "디스크가 병목인 상황에서 커넥션을 늘리면 정확히 무슨 일이 일어나나요?"

두 가지다. 첫째, 디스크의 IOPS는 장치가 정한 상수라 요청자를 늘려도
초당 처리되는 I/O는 안 늘고 큐(`await`)만 길어진다. 둘째, 더 나쁜 쪽인데,
각 쿼리가 혼자서는 순차적으로 읽더라도 여러 쿼리의 요청이 디스크에
번갈아 도착하면 디스크 입장에서는 **랜덤 접근**이 된다. HDD라면 매 요청마다
seek가 발생해 총 처리량이 순차 수준에서 랜덤 수준으로 떨어진다 — 자릿수가
다른 하락이다. 그래서 디스크 병목에서 동시성 증가는 무의미를 넘어 유해하고,
오히려 커넥션을 줄여 각 스캔의 순차성을 되찾는 것이 총 디스크 처리량을
올린다. SSD·클라우드 볼륨은 seek가 없어 두 번째 효과는 약하지만, IOPS
상한이 상품 스펙으로 딱딱하게 걸려 있어 첫 번째 효과는 더 일찍 온다.

### "풀을 줄였더니 앱에서 커넥션 획득 대기가 늘었습니다. 잘못 조정한 건가요?" (시니어 변별 포인트)

대기가 **어디로 옮겨갔는지**를 먼저 본다. 풀을 줄이기 전에는 요청이 DB
내부에서 CPU·락·버퍼 풀을 쥔 채 기다렸고(비싼 대기), 줄인 뒤에는 앱 풀에서
스레드가 park된 채 기다린다(싼 대기 — DB 자원 소모 0). 판단 기준은 대기
발생 여부가 아니라 **최종 처리량과 p99 응답시간**이다. 둘이 좋아졌다면
조정은 옳다 — 대기가 눈에 보이는 위치로 옮겨왔을 뿐이다. 남은 대기를
줄이고 싶다면 풀을 도로 키우는 게 아니라 **점유 시간**을 줄인다(트랜잭션
밖으로 외부 호출 빼기, 느린 쿼리 튜닝, 읽기 레플리카 분리). 단, 앱 쪽
대기가 톰캣 스레드를 오래 묶어 스레드 풀 고갈로 번지지 않도록
`connection-timeout`을 짧게 두고 빨리 실패시키는 안전장치를 같이 건다.
"대기 총량"이 아니라 "대기의 위치와 비용"으로 답하면 시니어 답변이다.

### "HikariCP 공식(코어 × 2 + 스핀들)을 그대로 쓰면 되지 않나요?"

경험식이라 **자릿수를 잡는 용도**로만 쓴다. 항의 의미는 분명하다 — 코어
수는 CPU 병렬성 상한, ×2는 I/O 대기 동안 다른 스레드가 CPU를 쓰는 겹치기
여유, 스핀들 수는 디스크 병렬성. 하지만 SSD·NVMe·클라우드 볼륨에는
스핀들이라는 물리 단위가 없고, I/O 대기 비율이 워크로드마다 달라 ×2가
맞는지도 알 수 없다. 그래서 공식으로 출발점(예: 8코어 → 20 전후)을 잡고,
부하 테스트에서 풀 크기를 단계적으로 바꿔가며 TPS 포화 지점과 p99 붕괴
지점을 직접 그려 채택한다. 인스턴스 N대의 합이 DB 기준 숫자라는 것,
오토스케일링 최대 대수까지 곱해 봐야 한다는 것도 공식이 말해 주지 않는
부분이다.

### "MySQL과 PostgreSQL에서 커넥션의 비용이 다른가요? 앱이 오토스케일링되면요?" (가산점 포인트)

다르다. MySQL은 커넥션당 **스레드**, PostgreSQL은 커넥션당 **프로세스**
(fork)라 PG 쪽이 메모리·생성 비용이 훨씬 크고, 그래서 PG 생태계에서는
**PgBouncer** 같은 외부 커넥션 풀러를 DB 앞에 두는 것이 사실상 표준이다.
오토스케일링은 이 문제를 증폭한다 — 앱이 10대에서 40대로 늘면 풀 크기를
안 바꿔도 DB 커넥션은 4배가 되어 붕괴 구간으로 밀려나고, 스케일 아웃이
오히려 DB 장애를 만든다. 대책은 두 방향이다: ① 앱 풀 크기를 **최대 인스턴스
수 기준**으로 나눠 잡기 ② DB 앞에 **프록시/풀러**(PgBouncer, ProxySQL,
클라우드의 RDS Proxy 류)를 두어 앱 커넥션 수와 무관하게 DB 커넥션 총량을
고정하기. 후자는 "DB 동시성의 상한을 DB 바로 앞에서 한 곳으로 통제"하는
구조라 인스턴스 수가 유동적인 환경에서 특히 유효하다.

## 한 줄 요약

커넥션은 DB의 처리 능력이 아니라 DB 앞의 자리 수라서, 코어와 디스크가
정한 상한을 넘긴 커넥션은 일을 더 시키는 게 아니라 **컨텍스트 스위칭·I/O
큐 적체와 순차 I/O의 랜덤화·락 경합·버퍼 풀 경합**을 더 만들어 처리량을
깎는다 — 그래서 늘리기 전에 앱 스레드 풀 → 커넥션 풀 → DB CPU → 디스크
I/O → 락 대기 순으로 병목 위치를 확인하고, 풀 크기는 경험식으로 출발해
부하 테스트로 포화 지점을 찾은 뒤 active/pending/acquire 메트릭 알람으로
고정하며, 대기 줄은 DB 안(비싼 대기)이 아니라 앱 풀(싼 대기)에 세운다.
