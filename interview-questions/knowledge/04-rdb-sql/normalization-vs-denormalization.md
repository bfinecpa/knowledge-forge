# 정규화 vs 반정규화 — "조회 성능을 위해"에서 멈추면 반쪽짜리 정의다

> 핵심 관전 포인트: **정규화는 "하나의 사실은 한 곳에만" — 중복을 없애
> 수정 이상(update anomaly)을 구조적으로 차단하는 설계다. 반정규화는
> 조회 패턴에 맞춰 의도적으로 중복·연산 값을 허용하고, 그 대가(갱신
> 정합성)를 관리하는 결정이다 — "대가 관리"까지 말해야 정의가 완성된다.
> 선택 기준은 4축: ① 읽기:쓰기 비율 ② 실측된 조인·집계 병목 ③ 인덱스·
> 커버링 인덱스·캐시 선행 검토 ④ 대가 지불 준비. 그리고 핫 로우의 비용은
> "성능 저하"라는 뭉뚱그린 말 대신 락 경합 → 사실상 직렬화 → 트랜잭션
> 장기화 → 커넥션 풀 고갈 → 전 서비스 전파라는 이름 붙은 사슬로 말한다.**

---

## 0. 질문 + 의도

**질문**: "정규화와 반정규화란? 반정규화를 선택하는 기준은?"

**출제 의도**: 교과서 정규화만 아는 사람과 **"조회 패턴에 맞춰 의도적으로
중복을 허용하고 그 대가(갱신 정합성)를 관리"해본 사람**을 구분한다.
대용량 조회 시스템은 반정규화 없이 성립하지 않는다. 즉 정규형 번호의
암기가 아니라 — 편익(조회 성능)과 대가(갱신 정합성)를 **양면으로
조립**해서, 언제 어떤 관리 장치와 함께 중복을 들여오는지의 실무 판단을
본다.

---

## 1. 개념 — 정규화는 수정 이상의 구조적 차단, 반정규화는 대가를 아는 의도적 중복

### 1-1. 정규화 = "하나의 사실은 한 곳에만"

정규화의 본질은 규칙 목록(1NF, 2NF, ...)이 아니라 하나의 원칙이다 —
**하나의 사실(fact)은 데이터베이스에서 정확히 한 곳에만 존재해야 한다.**
같은 사실이 여러 곳에 흩어져 있으면, 수정할 때 전부 찾아 고쳐야 하고
하나라도 놓치면 **"같은 질문에 DB가 두 가지 답을 하는" 상태**가 된다.
이것이 수정 이상(update anomaly)이고, 정규화는 이것을 코드 리뷰나 개발자
주의력이 아니라 **테이블 구조 자체로 차단**한다.

```sql
-- ❌ before: "부서 이름"이라는 하나의 사실이 직원 수만큼 복제됨
CREATE TABLE employees (
    id        BIGINT PRIMARY KEY,
    name      VARCHAR(50),
    dept_name VARCHAR(50)   -- '개발1팀'이 소속 직원 300행에 흩어져 있다
);
-- 부서 이름이 바뀌면? UPDATE employees SET dept_name = ... WHERE dept_name = ...
-- 조건을 잘못 쓰거나 일부 행만 갱신되면 → 한 부서에 두 이름 (update anomaly)

-- ✅ after: 부서 이름은 departments에 딱 한 곳
CREATE TABLE departments (
    id   BIGINT PRIMARY KEY,
    name VARCHAR(50)         -- '개발1팀'은 여기 한 행에만 존재
);
CREATE TABLE employees (
    id      BIGINT PRIMARY KEY,
    name    VARCHAR(50),
    dept_id BIGINT           -- 사실을 복제하지 않고 참조(FK)만 든다
);
-- 부서 이름 변경 = 한 행 UPDATE. 어긋날 "다른 곳"이 구조적으로 없다.
```

비유하면 — 회사 규정을 각 팀이 복사해 갖는 것(정규화 전)과, 원본은
사내 위키 한 페이지에만 두고 각 팀은 링크만 갖는 것(정규화)의 차이다.
복사본 체제에서는 개정 때마다 전 팀을 돌며 바꿔야 하고, 한 팀이라도
옛 버전을 들고 있으면 사고가 난다.

### 1-2. 반정규화의 두 형태 — 중복 컬럼과 연산(집계) 컬럼

반정규화가 들여오는 중복은 크게 두 형태다.

- **중복 컬럼**: 다른 테이블의 값을 조인 없이 읽으려고 복사해 둔다.
  예 — `comments.author_name`(원본은 `users.name`).
- **연산(집계) 컬럼**: 매번 COUNT/SUM 하는 대신 결과를 컬럼에 유지한다.
  예 — `posts.comment_count`(원본은 `comments`의 행 수).

두 형태 모두 원리는 같다. **정규화가 금지한 "같은 사실의 복제"를 조회
패턴을 위해 일부러 되돌리는 것.**

### 1-3. 정의를 완성하는 나머지 반쪽 — "의도적" + "대가 관리"

여기가 이 문서의 첫 번째 핵심이다. 반정규화를 "조회 성능을 위해 중복을
두는 것"까지만 말하면 **편익만 말한 반쪽 정의**다. 완성된 정의는:

> 반정규화 = 조회 패턴에 맞춰 **의도적으로** 중복·연산 값을 허용하고,
> **그 대가(갱신 정합성)를 관리 장치와 함께 지불하는 결정.**

두 단어가 정의의 자격 요건이다.

- **"의도적"**: 설계를 몰라서 중복이 생긴 것은 반정규화가 아니라 그냥
  정규화 실패다. 반정규화는 정규화된 설계를 **알고서** 되돌리는 결정이고,
  어떤 사실을 어디에 복제했는지가 문서와 코드에 드러나야 한다.
- **"대가 관리"**: 중복을 두는 순간 "원본과 사본이 어긋날 수 있다"는
  부채가 생긴다. 이 부채를 갚는 장치(동기 갱신, 원자적 UPDATE, 보정
  배치 — 2장)가 함께 설계되지 않은 중복은 결정이 아니라 방치다.

면접에서 이 질문의 변별점은 정확히 여기다 — **편익과 대가를 한 호흡에
말하는가.** "조회가 빨라진다"에서 끊기면 트레이드오프의 한 면만 본
것이고, "대신 갱신 정합성이라는 대가가 생기며 이를 이렇게 관리한다"까지
이어져야 양면이 조립된 답이다.

## 2. 선택 기준 4축 — 그리고 comment_count의 3단 관리 장치

### 2-1. 반정규화를 선택하는 기준 4축

| 축 | 질문 | 통과 조건 |
|---|---|---|
| ① 읽기:쓰기 비율 | 이 데이터, 읽기가 압도적인가? | 사본은 읽을 때 이득, 쓸 때 비용이다. 쓰기가 잦으면 대가만 키운다 |
| ② 실측 병목 | 조인·집계 비용이 **측정으로** 확인된 병목인가? | "느릴 것 같아서"는 근거가 아니다. 실행 계획·슬로 쿼리로 확인 |
| ③ 선행 검토 | 인덱스·커버링 인덱스·캐시로 먼저 해결되지 않는가? | 반정규화는 스키마를 바꾸는 비가역에 가까운 수단 — 더 싼 수단부터 |
| ④ 대가 지불 준비 | 갱신 정합성 관리 장치를 설계했는가? | 동기 트랜잭션 + 원자적 UPDATE(+ 핫 로우 경합 대비) + 보정 배치 |

④가 빠진 반정규화 제안은 "대출로 뭘 살지"만 정하고 상환 계획이 없는
것과 같다. 그리고 ③의 순서가 중요하다 — 인덱스는 되돌리기 쉽고 캐시는
DB 스키마를 건드리지 않지만, 반정규화 컬럼은 **모든 쓰기 경로가 그
컬럼을 함께 갱신해야 하는 영구적 의무**를 만든다. 가장 비싼 수단을
가장 마지막에 꺼낸다.

### 2-2. before / after — `posts.comment_count`와 3단 관리 장치

게시글 목록 20건을 보여줄 때마다 댓글 수를 세는 상황.

```sql
-- ❌ before: 정규화 그대로 — 목록 한 페이지에 집계 조인
SELECT p.id, p.title, COUNT(c.id) AS comment_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.title
ORDER BY p.created_at DESC
LIMIT 20;
-- 목록 20건을 위해 그 글들에 달린 댓글 수만큼 행을 만나 집계한다.
-- 트래픽이 큰 목록 화면이라면 이 비용이 실측 병목으로 잡힐 수 있다.
```

②실측으로 병목 확인, ③인덱스·캐시로 부족 판단이 끝났다면 —
`posts.comment_count` 연산 컬럼을 두되, **관리 장치 3단을 함께 설계**한다.

```sql
-- ✅ after: 반정규화 + 3단 관리 장치
ALTER TABLE posts ADD COLUMN comment_count INT NOT NULL DEFAULT 0;

-- 장치 ① 같은 트랜잭션: 원본(댓글)과 사본(카운트)의 운명을 묶는다
BEGIN;
INSERT INTO comments (post_id, author_id, body) VALUES (?, ?, ?);
UPDATE posts SET comment_count = comment_count + 1 WHERE id = ?;
COMMIT;
-- 카운트 갱신이 실패하면 댓글 INSERT도 함께 롤백 — 어긋난 채 커밋되는
-- 경로를 트랜잭션이 막는다. (대가: 댓글 쓰기가 posts 갱신 비용까지 짊어짐)

-- 장치 ② 원자적 UPDATE: 값을 읽어와 더하지 않는다
UPDATE posts SET comment_count = comment_count + 1 WHERE id = ?;
-- "SELECT로 읽고 → 애플리케이션에서 +1 → UPDATE"로 쪼개면, 두 요청이
-- 같은 값을 읽고 같은 값을 쓰는 lost update가 난다. DB가 행 락을 잡고
-- 현재 값 위에서 더하게 하는 위 형태여야 동시 요청에도 안 샌다.

-- 장치 ③ 주기적 보정 배치: 어긋남을 전제로 한 안전망
UPDATE posts p
SET p.comment_count = (
    SELECT COUNT(*) FROM comments c WHERE c.post_id = p.id
);
-- (실전에서는 전체가 아니라 최근 변경분·표본 검증 위주로 돈다)
```

### 2-3. 다 묶어도 왜 어긋나나 — 불변식이 DB 제약이 아니라 애플리케이션 관례에 산다

장치 ①②를 다 갖춰도 1년 뒤 `comment_count`는 실제와 어긋날 수 있다.
이유는 하나로 요약된다 — **"comment_count = comments의 행 수"라는
불변식이 DB 제약이 아니라 애플리케이션의 관례로만 존재하기 때문.**

FK나 UNIQUE 제약은 DB가 지키므로 어떤 코드 경로로 들어와도 뚫리지
않는다. 반면 이 불변식은 "댓글을 건드리는 모든 코드가 카운트도 함께
갱신하기로 한 약속"일 뿐이라, 약속을 모르는 경로가 하나만 생겨도 뚫린다.

- **새 코드 경로**: 신입이 만든 관리자용 댓글 일괄 삭제 API가 카운트
  갱신을 빼먹는다. 컴파일도 테스트도 통과한다.
- **DB 직접 수정**: 운영 이슈로 콘솔에서 `DELETE FROM comments ...`를
  직접 실행 — 애플리케이션의 약속은 애초에 거치지 않는다.
- **경로 비대칭**: 작성 경로는 +1을 하는데, 나중에 추가된 "블라인드
  처리" 경로는 카운트를 어떻게 할지 정의조차 안 돼 있다.

그래서 장치 ③(보정 배치)은 "버그가 있으면 돌리는 것"이 아니라 **어긋남을
전제로 처음부터 설계에 포함하는 안전망**이다. 드리프트는 막는 게 아니라
"주기적으로 0으로 되돌리는" 대상이다.

## 3. 핫 로우 — "성능 저하"가 아니라 이름 붙은 사슬로 말하기

이 절이 이 문서의 심장이다. 초당 수백 개 댓글이 달리는 인기 글에서
2-2의 구조가 무슨 일을 겪는지 물었을 때, "성능이 저하되고 다른 요청도
문제가 생긴다"는 답과 아래 사슬을 이름으로 짚는 답은 전혀 다른 평가를
받는다.

### 3-1. 사슬 — 락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파

모든 댓글 트랜잭션이 `UPDATE posts ... WHERE id = 인기글` — **같은 행
하나**를 갱신한다. 이런 행을 **핫 로우(hot row)** 라 부른다. 그 다음은
필연의 연쇄다.

> **⑴ 락 경합(lock contention)**: UPDATE는 그 행의 배타적 행 락을 잡고,
> 락은 커밋 때까지 유지된다. 초당 수백 트랜잭션이 같은 행 락 하나를
> 두고 줄을 선다.
>
> **⑵ 사실상 직렬화(serialization)**: 락은 한 번에 하나만 통과시키므로,
> 수백 개의 "동시" 요청이 실제로는 **한 줄로 서서 차례로** 처리된다.
> 서버를 아무리 늘려도 소용없다 — 병목은 CPU가 아니라 행 하나다.
>
> **⑶ 트랜잭션 장기화**: 줄 뒤쪽 트랜잭션은 락 대기 시간만큼 전체 수명이
> 늘어난다. 그리고 각 트랜잭션이 잡은 자신의 락도 그만큼 오래 유지되므로
> 뒤에 선 트랜잭션의 대기는 더 길어진다 — 대기가 대기를 키운다.
>
> **⑷ 커넥션 풀 고갈**: 락을 기다리는 트랜잭션은 그동안 **DB 커넥션을
> 쥔 채로** 기다린다. 풀 크기는 유한하므로, 장기화된 트랜잭션들이
> 커넥션을 점유하면 풀이 바닥난다.
>
> **⑸ 전 서비스 전파**: 커넥션 풀은 서비스 전체가 공유한다. 인기 글
> 댓글과 무관한 요청 — 로그인, 결제, 다른 글 조회 — 도 커넥션을 못 얻어
> 대기·타임아웃된다. **행 하나의 경합이 서비스 전체의 장애가 된다.**

비유하면 — 계산대가 백 개인 마트(서버·커넥션)에서 특정 상품 하나의
재고 장부(핫 로우)를 계산 때마다 반드시 고쳐야 하는데, 그 장부에 펜이
하나뿐인 상황이다. 계산대가 아무리 많아도 모든 계산원이 펜 하나를
기다리며 계산대를 점유하고, 그 상품과 무관한 손님까지 빈 계산대가 없어
줄을 선다.

### 3-2. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

| 뭉뚱그린 표현 | 이름 | 사슬로 말하면 |
|---|---|---|
| "성능이 저하된다" | **락 경합 + 사실상 직렬화** | 같은 행 락에 수백 트랜잭션이 줄 서서 동시성이 1로 붕괴 — 서버 증설로 해결 불가 |
| "다른 요청도 문제가 생긴다" | **커넥션 풀 고갈 + 전파** | 락 대기 트랜잭션이 커넥션을 쥔 채 장기화 → 풀 소진 → 무관한 요청까지 타임아웃 |

사슬의 힘은 **처방이 사슬의 고리에서 나온다**는 데 있다. "성능 저하"
에서는 아무 처방도 안 나오지만, 고리를 짚으면 고리별 개입 지점이 보인다
— 경합 자체를 줄이거나(⑴), 락 보유 시간을 줄이거나(⑶), 풀을 보호하거나
(⑷).

### 3-3. 처방 스케치 — 경합을 행에서 떼어내기

핫 로우의 근본 원인은 "쓰기 지점이 행 하나로 수렴"이므로, 처방은 수렴을
푸는 방향이다. (상세는 꼬리질문 2)

- **비동기 집계**: 댓글 트랜잭션에서 카운트 UPDATE를 빼고, 이벤트를
  쌓아 모아서(배치로 묶어) 반영. 정합성이 "즉시"에서 "잠시 후"로
  느슨해지는 대가를 치른다.
- **카운터 분산(sharded counter)**: 카운터를 N개 행으로 쪼개 무작위로
  하나에 +1, 읽을 때 SUM. 락 경합이 1/N로.
- **외부 카운터**: Redis 같은 인메모리 카운터에 증가시키고 주기적으로
  DB에 반영.
- 최소한의 완화로, 트랜잭션 안에서 **UPDATE를 커밋 직전(마지막 문장)에**
  두면 락 보유 시간이 줄어든다(⑶ 고리에 대한 개입).

## 4. 꼬리질문 대비 포인트

### "posts.comment_count 반정규화 — 무엇을 대가로 지불했고 어떻게 관리하나요?"

대가: **갱신 정합성.** 댓글이라는 원본과 카운트라는 사본이 어긋날 수
있는 부채가 생기고, 모든 댓글 쓰기 경로가 카운트 갱신 의무를 영구히
짊어진다. 관리 장치 3단 — ① **같은 트랜잭션**으로 묶어 한쪽만 반영된 채
커밋되는 경로 차단(대신 댓글 쓰기가 posts 갱신 실패 시 함께 롤백되는
결합 비용), ② **원자적 UPDATE**(`SET comment_count = comment_count + 1`)
로 읽고-더하고-쓰는 lost update 차단, ③ **주기적 보정 배치**로 그래도
새는 드리프트를 되돌리는 안전망. 셋을 한 호흡에 말하면 "대가를 관리해본
사람"의 답이 된다.

### "초당 수백 개 댓글이 달리는 인기 글이 되면 이 구조에서 무슨 일이 벌어지나요?"

사슬을 이름으로 완주한다 — 모든 트랜잭션이 같은 posts 행을 UPDATE하는
**핫 로우**가 되고, **락 경합** → 락은 한 번에 하나만 통과시키므로
**사실상 직렬화**(서버 증설 무효) → 락 대기로 **트랜잭션 장기화** →
대기 중에도 커넥션을 쥐고 있으므로 **커넥션 풀 고갈** → 풀은 서비스
공용이라 무관한 요청까지 타임아웃되는 **전 서비스 전파.** 이어서 처방을
고리에 연결한다 — 쓰기 수렴을 푸는 비동기 집계·카운터 분산·외부 카운터,
락 보유 시간을 줄이는 UPDATE 위치 조정. **"성능 저하"라고 답하는 순간
이 질문의 목적(비용을 사슬로 말하는가)에서 탈락한다.**

### "같은 트랜잭션 + 원자적 UPDATE로 다 묶어도 1년 뒤 어긋날 수 있다 — 왜, 그리고 장기적으로 어떻게 유지하나요?"

**불변식이 DB 제약이 아니라 애플리케이션 관례에 살기 때문.** FK처럼
DB가 지키는 규칙은 어떤 경로로 와도 뚫리지 않지만, "댓글을 건드리면
카운트도 갱신한다"는 코드의 약속일 뿐이라 — 약속을 모르는 새 코드
경로(일괄 삭제 API), 애플리케이션을 거치지 않는 DB 직접 수정, 정의가
누락된 신규 상태(블라인드 처리)가 뚫는다. 장기 유지는 **드리프트를
전제로 한 주기적 보정 배치**(원본 기준 재계산)가 답이며, 이것은 버그
대응이 아니라 설계에 처음부터 포함되는 안전망이다.

### "반정규화를 하기 전에 먼저 검토해야 할 것은 무엇인가요?"

순서가 답이다. ① **실측** — 실행 계획과 슬로 쿼리로 조인·집계가 진짜
병목인지 확인("느릴 것 같아서"는 근거가 아니다). ② **더 싼 수단 먼저**
— 인덱스 추가, 커버링 인덱스(조인·집계 대상 컬럼을 인덱스에 포함해
테이블 접근 제거), 애플리케이션·캐시 계층(자주 읽는 목록이면 캐시 적중이
집계 자체를 없앤다). 인덱스는 되돌리기 쉽고 캐시는 스키마를 안 건드리는
반면, 반정규화 컬럼은 **모든 쓰기 경로에 영구적 갱신 의무**를 새기는
가장 비싼 수단이므로 마지막에 꺼낸다. ③ 그래도 필요하면 **대가 지불
준비(관리 장치 3단)와 함께** 도입한다.

### "주문 테이블에 상품명·가격을 복사해 두는 것도 반정규화인가요? 상품명이 바뀌면 동기화 배치를 돌려야 하나요?" (시니어 변별 포인트 · 가산점 포인트)

함정 질문이다 — **동기화하면 안 되는 중복**이 존재한다. `orders.product_name`,
`orders.price`는 "지금의 상품 정보"의 사본이 아니라 **"주문 시점에
무엇을 얼마에 샀는가"라는 역사적 사실의 스냅샷**이다. 상품명이 바뀌거나
가격이 인상됐다고 과거 주문의 값을 동기화하면 영수증·정산·환불 근거가
파괴된다 — 여기서는 **원본과 어긋나는 것이 정합성**이다. 즉 중복을 보면
먼저 물어야 한다: "이 사본이 가리키는 사실이 **현재의 사실**(comment_count
— 어긋나면 오류, 동기화 장치 필요)인가, **과거 시점의 사실**(주문 스냅샷
— 동기화가 오히려 오류)인가." 이 구분 없이 "중복은 다 동기화"로 접근하면
반정규화와 스냅샷을 같은 것으로 취급하는 것이고, 구분해서 말하면 중복의
의미론까지 설계해본 사람으로 변별된다.

## 한 줄 요약

**정규화는 "하나의 사실은 한 곳에만"으로 수정 이상을 구조적으로 차단하고,
반정규화는 조회 패턴을 위해 의도적으로 중복·연산 값을 두되 그 대가(갱신
정합성)를 관리 장치(같은 트랜잭션 + 원자적 UPDATE + 보정 배치)와 함께
지불하는 결정이다. 선택 기준은 읽기:쓰기 비율 · 실측 병목 · 인덱스/캐시
선행 검토 · 대가 지불 준비의 4축이고, 핫 로우의 비용은 락 경합 → 사실상
직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파라는 이름 붙은
사슬로 말한다.**
