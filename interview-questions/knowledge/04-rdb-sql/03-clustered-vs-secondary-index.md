# 클러스터드 vs 세컨더리 인덱스 — PostgreSQL은 힙 + 전부 세컨더리, 그래도 PK 설계 2원칙은 살아남는다

> 핵심 관전 포인트: **PostgreSQL에는 클러스터드 인덱스가 없다. 테이블은 정렬 없는 힙(heap)이고, PK를 포함한 모든 인덱스가 리프에 행의 물리 주소 TID(블록 번호 + 오프셋, 6바이트)를 담아 힙을 직접 가리키는 세컨더리다. InnoDB의 전제(테이블 = PK B+Tree, 세컨더리 리프 = PK 복제, 2단계 북마크 룩업)는 통째로 뒤집히는데 — PK 설계 2원칙은 살아남는다. ① 작게: 세컨더리에 PK가 복제되는 곱셈은 없지만 **FK 컬럼·FK 인덱스·조인 키**에는 PK가 그대로 들어간다. ② 단조 증가: 힙은 랜덤 PK에 무관하지만 **PK B-tree의 무작위 삽입**은 페이지 분할 · 캐시 미스 · `full_page_writes` WAL 증폭을 그대로 일으킨다. 여기에 PG만의 셋째 비용 — **비-HOT UPDATE는 새 TID를 만들어 모든 인덱스를 갱신한다** — 가 붙는다. 비용은 "메모리 부하" 같은 뭉뚱그린 말 대신 페이지 분할 · shared_buffers 적재율 · 랜덤 I/O · WAL 증폭이라는 이름과 인과 사슬로 말해야 한다. 이름을 붙이는 순간 반박도 검증도 가능한 엔지니어링이 된다.**

## 0. 질문 + 의도

**질문**: "클러스터드 인덱스와 논클러스터드(세컨더리) 인덱스의 차이는? (InnoDB 기준)"

**PostgreSQL 기준 재해석**: "PostgreSQL의 힙 구조와 InnoDB의 클러스터드 구조는 어떻게 다르고, 그 차이가 PK 설계와 UPDATE 비용에 어떤 영향을 주는가?"

**출제 의도**: 저장 구조가 PK 선택을 어떻게 결정하는지 — InnoDB에서는 "세컨더리 인덱스가 PK를 품는 구조"에서, PostgreSQL에서는 "힙 + TID 포인터 + MVCC의 새 튜플" 구조에서 — UUID PK가 왜(그리고 **어디까지**) 문제인지가 여기서 나온다. **테이블 설계 첫 단추의 근거**를 확인한다. "리프에 뭐가 들었는지"의 암기가 아니라, 그 구조로부터 "PK는 어떻게 설계해야 하는가"를 스스로 도출할 수 있는지, 그리고 "PG니까 UUID 써도 된다"는 반쪽 명제를 어디서 잘라 말할 수 있는지를 본다.

## 1. 구조 — 클러스터드 인덱스가 있는 세계와 없는 세계

### 1-1. 먼저 클러스터드 인덱스가 무엇인지부터

이 문서의 출발점은 "PostgreSQL에는 클러스터드 인덱스가 없다"는 사실이다. 그런데 **없다는 말은 있는 쪽을 알아야 정보가 된다.** 그래서 있는 쪽부터 본다.

**클러스터드 인덱스(clustered index)** 는 **인덱스의 리프에 행 자체가 들어 있는 구조**, 즉 "테이블이 곧 하나의 인덱스"인 저장 방식이다. 이름의 유래는 "키 값이 가까운 행들이 디스크에서도 한 덩어리로 뭉쳐(cluster) 있다"는 성질이다. MySQL/InnoDB가 이 방식을 쓴다 — 테이블은 PK 순으로 정렬된 B+Tree 하나이고, 리프 페이지를 왼쪽부터 읽으면 그게 곧 PK 순 전체 스캔이다.

여기서 두 가지가 따라 나온다. 첫째, **PK로 조회하면 트리 하나만 타면 끝**이다. 리프에 도착한 순간 행 전체가 거기 있으니 더 갈 곳이 없다. 둘째, **PK가 아닌 인덱스(세컨더리 인덱스)의 리프에는 행이 없다.** 행은 클러스터드 쪽에만 있으니, 세컨더리는 "그 행을 클러스터드에서 어떻게 찾는지"를 적어 둘 수밖에 없고, 그 적어 두는 값이 **PK 값**이다. 그래서 세컨더리로 조회하면 트리를 두 번 탄다 — 세컨더리에서 PK를 얻고, 그 PK로 클러스터드 트리를 루트부터 다시 내려간다. 이 2단계를 **북마크 룩업(bookmark lookup)** 이라 부른다.

**PostgreSQL은 이 구조를 쓰지 않는다.** 테이블은 **힙(heap)** — 정렬 없이 행을 쌓아 두는 파일 — 이고, 인덱스는 전부 별도의 B-tree이며 리프에는 행이 아니라 **값과 행의 물리 주소**만 들어간다. 두 구조를 나란히 놓으면 이렇다.

```text
[A] 클러스터드 인덱스가 있는 구조 (MySQL InnoDB)
    테이블 = PK 순으로 정렬된 B+Tree 하나. 리프 = 행 전체.

    users (= PK B+Tree 그 자체)
      브랜치:  │ 1 │ 5 │ 9 │
      리프:    │ 1, a@x.com, 서울 │ 2, b@y.com, 부산 │ → │ 5, e@x.com, 대전 │ 7, c@z.com, 광주 │
                 └ 리프를 왼쪽부터 이어 읽으면 그것이 곧 PK 순 전체 스캔

    idx_users_email (세컨더리)
      리프:    │ 'c@z.com' │ PK=7 │      ← 행 주소가 아니라 PK "값"을 적어 둔다
                              └── 행을 보려면 PK B+Tree를 루트부터 다시 탐색 (북마크 룩업, 2단계)

[B] 힙 구조 (PostgreSQL)
    테이블 = 정렬 없는 힙 파일. 행은 도착 순으로 빈자리에 쌓인다.

    users (힙 파일)
      블록 0:    [슬롯1 → 1, a@x.com, 서울] [슬롯2 → 2, b@y.com, 부산]
      블록 1042: [슬롯7 → 7, c@z.com, 광주]

    users_pkey (id B-tree)                idx_users_email (email B-tree)
      리프: │ 1 │ (0,1)    │                 리프: │ 'a@x.com' │ (0,1)    │
            │ 2 │ (0,2)    │                       │ 'b@y.com' │ (0,2)    │
            │ 7 │ (1042,7) │                       │ 'c@z.com' │ (1042,7) │
              └────────── 둘 다 똑같이 (값, 물리 주소)로 힙을 직접 가리킨다 ──────────┘
```

[B]를 보면 **PK 인덱스와 email 인덱스의 생김새가 완전히 같다.** 둘 다 "값 + 힙의 주소"이고, 어느 쪽도 행을 품고 있지 않다. 그래서 PostgreSQL에서는 "클러스터드 인덱스 vs 세컨더리 인덱스"라는 **구분 자체가 성립하지 않는다** — 굳이 InnoDB의 어휘로 옮기면 **PK 인덱스를 포함해 전부 세컨더리**다. PostgreSQL 문서에서 "세컨더리 인덱스"라는 말이 사실상 "인덱스"와 동의어처럼 쓰이는 이유가 이것이다.

### 1-2. 힙, 라인 포인터, 그리고 삽입 위치를 정하는 것

PostgreSQL의 테이블 파일은 **8KB 페이지(블록)의 나열**이다. 행(튜플)은 정렬 없이, 빈 공간이 있는 페이지에 들어간다.

어느 페이지에 빈 공간이 있는지는 **Free Space Map(FSM)** — 테이블마다 딸려 있는 "페이지별 남은 공간 요약본" — 이 알려주고, 새로 붙는 행은 대개 파일 끝 쪽 페이지에 쌓인다. 여기서 이 문서 전체를 관통하는 한 줄이 나온다: **INSERT 위치를 정하는 것은 PK 값이 아니라 FSM이다.** 이 한 줄이 2-3절의 결론을 절반쯤 미리 말해 준다 — PK가 아무리 무작위여도 힙은 흔들리지 않는다.

페이지 안에서 행은 **라인 포인터(line pointer, item identifier)** 라는 4바이트 슬롯 배열을 통해 가리켜진다. 페이지 머리에 "1번 슬롯은 이 페이지의 몇 바이트 지점, 2번 슬롯은 몇 바이트 지점" 하는 목차가 있고, 실제 행 데이터는 페이지 뒤쪽부터 채워지는 구조다. 슬롯이라는 한 겹을 두는 이유는 **페이지 안에서 행이 움직여도 바깥에서 쓰는 주소는 안 바뀌게** 하기 위해서다.

### 1-3. `ctid` — 행의 물리 주소, 그리고 이 문서의 핵심 어휘

행의 주소는 **TID(tuple identifier) = (블록 번호 4바이트, 라인 포인터 번호 2바이트) = 6바이트**다. 시스템 컬럼 `ctid`로 직접 볼 수 있다. "몇 번째 페이지의 몇 번째 슬롯"이라는 뜻이므로, **책의 '173쪽 7번째 줄'에 해당하는 물리 좌표**라고 생각하면 된다.

```sql
SELECT ctid, id, email FROM users LIMIT 3;
--   ctid    | id | email
--  (0,1)    |  1 | a@x.com      -- 0번 블록의 1번 라인 포인터
--  (0,2)    |  2 | b@y.com
--  (1042,7) |  7 | c@z.com      -- 1042번 블록의 7번 라인 포인터
```

**모든 인덱스의 리프 엔트리는 (키, TID)다.** PK 인덱스(`users_pkey`)도 예외가 아니다. 리프에 행 전체가 들어가는 인덱스도, 다른 인덱스의 키가 복제되는 인덱스도 없다.

**여기서 반드시 붙여야 할 성질 하나 — `ctid`는 불변 식별자가 아니다.** PostgreSQL의 UPDATE는 행을 제자리에서 고치지 않는다. **새 튜플 버전을 힙에 삽입하고**(그러므로 **새 `ctid`**), 옛 튜플에는 "이 트랜잭션이 지웠음" 표시만 남긴다. 같은 논리적 행인데 UPDATE 한 번에 물리 주소가 바뀌는 것이다.

```sql
SELECT ctid, id, nickname FROM users WHERE id = 7;
--   ctid    | id | nickname
--  (1042,7) |  7 | 오리

UPDATE users SET nickname = '거위' WHERE id = 7;

SELECT ctid, id, nickname FROM users WHERE id = 7;
--   ctid    | id | nickname
--  (1042,9) |  7 | 거위        -- 같은 행인데 ctid가 바뀌었다 (새 튜플 버전)
```

그러면 곤란한 일이 생긴다. **모든 인덱스가 옛 TID를 가리키고 있기 때문**이다. 새 버전을 찾아가게 하려면 원칙적으로 **인덱스마다 (키, 새 TID) 엔트리를 하나씩 더 꽂아야** 한다 — 어떤 컬럼을 고쳤는지와 **무관하게, 인덱스 N개 전부에**. 인덱스가 8개인 테이블에서 `updated_at` 하나만 고쳤는데 인덱스 쓰기가 8건 발생하는 것이다. **"인덱스가 많으면 UPDATE가 비싸진다"는 흔한 말의 정확한 메커니즘이 이것**이다.

이 대가를 피하는 예외 장치가 **HOT(Heap-Only Tuple, "힙 안에서만 사는 튜플")** 이다. 조건 둘 — ① **인덱스가 걸린 컬럼이 하나도 안 바뀌었고** ② 옛 튜플과 **같은 힙 페이지에 새 버전을 넣을 여유 공간**이 있으면 — 새 튜플을 같은 페이지에 넣고 옛 슬롯에서 새 슬롯으로 **페이지 안 체인**만 건다. 인덱스는 여전히 옛 TID를 가리키지만 체인을 따라가면 최신 버전에 도달하므로, **인덱스 갱신이 전부 생략**된다. "힙 안에서만 존재하고 인덱스에는 흔적을 남기지 않는 튜플"이라 이런 이름이 붙었다.

```text
비-HOT UPDATE  (인덱스 컬럼이 바뀌었거나, 같은 페이지에 여유가 없음)
  힙: 블록 1042 [슬롯7 → 옛 버전(삭제 표시)]      블록 2077 [슬롯3 → 새 버전]
  인덱스 8개 전부: (키, (2077,3)) 엔트리 삽입      ← 인덱스 쓰기 8건

HOT UPDATE     (인덱스 컬럼 불변 + 같은 페이지에 여유 있음)
  힙: 블록 1042 [슬롯7 → 옛 버전] ──페이지 안 체인──→ [슬롯9 → 새 버전]
  인덱스: 손대지 않음  ← 여전히 (1042,7)을 가리키고, 체인을 따라가면 최신 버전
```

자세한 설계 지침은 2-5절에서 다룬다. 여기서 기억할 것은 **`ctid`는 UPDATE로 바뀐다**는 한 줄과, 그 한 줄이 곧 PostgreSQL 인덱스 유지 비용의 뿌리라는 것이다.

### 1-4. 조회 경로 — 인덱스 → TID → 힙 페치 (북마크 룩업의 PG 판)

`WHERE email = 'c@z.com'`은 ① `idx_users_email`을 루트에서 리프까지 내려가 `(1042,7)`을 얻고 ② 1042번 블록의 7번 슬롯을 읽는다. InnoDB의 2단계처럼 "다른 트리를 처음부터 다시 탐색"하는 게 아니라 **주소를 보고 한 번에 점프**한다. 이 두 번째 단계를 **힙 페치(heap fetch)** 라 부른다.

대신 대칭적인 대가가 있다 — **PK로 조회해도 힙 페치는 똑같이 붙는다.** InnoDB에서 PK 조회는 리프가 곧 행이라 페치가 없지만, PostgreSQL에서는 PK 인덱스도 주소만 갖고 있으므로 힙을 한 번 더 읽어야 한다.

```text
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE email = 'c@z.com';

 Index Scan using idx_users_email on users  (cost=0.43..8.45 rows=1 width=120)
                                             (actual rows=1 loops=1)
   Index Cond: (email = 'c@z.com'::text)
   Buffers: shared hit=4          -- 인덱스 3장(루트→브랜치→리프) + 힙 1장
```

힙 페치가 항상 따라붙기 때문에 PostgreSQL은 이를 줄이는 장치를 둘 갖고 있다.

- **Bitmap Heap Scan**: 조건에 맞는 TID를 먼저 다 모은 뒤 **블록 번호 순으로 정렬해서** 힙을 방문한다. 같은 페이지를 여러 번 오가지 않고 한 번에 처리하므로 랜덤 접근이 순차에 가까워진다. 인덱스가 수천 건 이상을 돌려줄 때 플래너가 이 방식을 고른다.
- **Index Only Scan**: 필요한 컬럼이 전부 인덱스 안에 있고, 그 힙 페이지가 **visibility map**(페이지 단위로 "이 페이지의 모든 튜플이 모든 트랜잭션에 보인다"를 표시해 둔 비트맵)에 "모두 가시"로 찍혀 있으면 **힙을 아예 안 읽는다**. 계획의 `Heap Fetches: N`이 그 예외가 몇 번 발생했는지다. 자세한 것은 [커버링 인덱스](09-covering-index.md) 문서를 참고.

### 1-5. 왜 논리 포인터(PK)가 아니라 물리 주소(TID)인가

InnoDB가 세컨더리 리프에 (행 주소가 아니라) PK를 넣는 이유는 **"클러스터드 인덱스가 정렬을 유지하느라 행을 물리적으로 옮기기 때문"** 이다. 페이지가 가득 차 분할되면 행 절반이 새 페이지로 이사한다. 그때 물리 주소를 적어 둔 세컨더리가 있다면 전부 고쳐야 하는데, PK 값을 적어 뒀다면 고칠 것이 없다.

PostgreSQL의 힙은 정렬을 유지하지 않으니 **행이 저절로 이동하는 일이 없다.** 옮길 일이 없으면 주소를 직접 적어도 깨지지 않는다 — 그래서 TID다.

책의 찾아보기 비유로 옮기면 — InnoDB는 개정판에서 쪽수가 밀릴 것을 알기에 "4.2절"이라는 **논리 포인터**를 적었고, PostgreSQL은 **글을 절대 옮기지 않는 책**이라 "173쪽 7번째 줄"이라는 **물리 주소**를 적어도 된다. 다만 PostgreSQL의 책에는 규칙이 하나 더 있다 — "고칠 때 그 자리에 덧쓰지 않고 **새 자리에 새로 쓴 뒤 옛 글에 취소선을 긋는다**". 그러면 찾아보기에 새 줄이 하나 더 필요해진다. 이것이 1-3절에서 본 PostgreSQL의 UPDATE 비용이고, 취소선 그은 옛 글을 지우는 것이 VACUUM이다([MVCC 문서](11-mvcc-postgresql.md)).

| | PostgreSQL (힙) | MySQL InnoDB (클러스터드) |
|---|---|---|
| 테이블 자체 | 정렬 없는 힙 페이지 나열 (8KB) | PK 순 정렬 B+Tree, 리프 = 행 (16KB) |
| PK 인덱스 리프 | (PK 값, **TID**) | 행 전체 |
| 세컨더리 리프 | (키, **TID**) | (키, **PK 값**) |
| 세컨더리 조회 | 인덱스 → TID로 힙 점프 (1회) | 세컨더리 → PK 트리 재탐색 (2회, 북마크 룩업) |
| PK 조회 | 인덱스 → 힙 페치 | 트리 하나로 끝 |
| 행 이동 | 없음 (UPDATE = 새 튜플 = 새 TID) | 페이지 분할 시 이동 (PK 불변이라 세컨더리 무영향) |
| 갱신 시 인덱스 | 비-HOT이면 **모든** 인덱스에 새 엔트리 | 바뀐 컬럼의 인덱스만 |

> MySQL 대조: InnoDB는 "테이블 = 클러스터드 B+Tree"라 테이블당 정확히 하나이고, PK가 없으면 첫 NOT NULL UNIQUE 인덱스를, 그것도 없으면 6바이트 숨은 row id를 클러스터드 축으로 삼는다. 읽기 한 단계를 내주고 쓰기 안정성을 산 설계다. SQL Server는 테이블마다 클러스터드/힙을 고른다. 즉 "클러스터드 테이블"은 RDB의 보편이 아니라 **엔진의 설계 선택**이다.

### 1-6. 그럼 PostgreSQL에서 "물리 순서"는 무슨 뜻인가

PostgreSQL은 힙의 순서를 **보장하지 않지만 관찰은 한다.**

`ANALYZE`가 컬럼마다 `pg_stats.correlation`을 계산한다. 이 값은 −1에서 1 사이로, **그 컬럼의 값 순서와 힙의 물리 순서가 얼마나 일치하는지**를 나타낸다. 플래너는 이 값으로 Index Scan의 힙 접근을 "순차에 가까움(비용 낮음)"에서 "완전 랜덤(`random_page_cost`)" 사이 어디쯤으로 추정한다. 시간 순으로 쌓이는 `bigint IDENTITY`나 `created_at`은 1 근처, 무작위 UUID 컬럼은 0 근처다.

순서를 강제로 맞추는 명령도 있다 — `CLUSTER orders USING orders_pkey;`는 힙을 그 인덱스 순으로 **1회 재작성**한다. 다만 세 가지 제약이 붙는다: ACCESS EXCLUSIVE 잠금이라 읽기까지 막히고, 이후 삽입되는 행은 다시 무질서해지며, 순서를 유지하는 메커니즘이 없다. 이름이 `CLUSTER`라서 오해하기 쉬운데 **"PostgreSQL의 클러스터드 인덱스"가 아니라 "한 번 정렬해 두기"** 다(무중단으로 하려면 `pg_repack --order-by`).

그래서 PostgreSQL에서 "정렬된 물리 순서"의 효과는 명령이 아니라 조합으로 얻는다 — 삽입 순서가 곧 조회 순서가 되게 키를 설계해 correlation을 높게 유지하고, 힙 접근 자체를 없애는 커버링 인덱스 + Index Only Scan을 쓰고, 시계열 데이터면 파티셔닝에 초소형 **BRIN**(페이지 범위마다 최솟값·최댓값만 기록하는 인덱스 — correlation이 높을 때만 쓸모가 있다)을 얹는다.

## 2. 비용에 이름 붙이기 — 페이지 분할 · shared_buffers 적재율 · 랜덤 I/O · 워킹셋 · WAL

이 절이 이 문서의 심장이다. 구조가 바뀌었으니 PK 설계 2원칙을 **PostgreSQL 구조에서 다시 도출**해야 하고, 그 비용을 뭉뚱그리지 않고 **이름 → 사슬**로 말할 수 있어야 한다.

면접에서 "메모리에 부하가 생긴다"와 "페이지당 엔트리 수가 줄어 shared_buffers 적재율이 떨어지고 캐시 미스가 디스크 I/O로 번진다"는 전혀 다른 평가를 받는다. 앞의 문장은 확인할 방법이 없지만, 뒤의 문장은 고리마다 반박할 수도 있고 `EXPLAIN (ANALYZE, BUFFERS)`로 검증할 수도 있다. **이름을 붙이는 순간 엔지니어링이 된다**는 것이 이 절의 방법론이다.

### 2-1. 등장인물 다섯 — 이름, 정의, 그리고 왜 그것이 비용인가

먼저 다섯 이름을 그 자리에서 정의해 둔다. 각각 "무엇인가" 한 문장과 "왜 그것이 비용인가" 한 문장이다.

#### (1) shared_buffers — PostgreSQL이 디스크 페이지를 담아 두는 공유 메모리 캐시

**무엇인가**: PostgreSQL 프로세스들이 함께 쓰는 고정 크기 메모리 영역으로, 디스크에서 읽어 온 8KB 페이지를 여기에 담아 둔다(기본값 128MB, 운영에서는 대개 RAM의 1/4 안팎으로 키운다). 그 뒤에 **OS 페이지 캐시**를 한 겹 더 쓰는 이중 캐시 구조라, 플래너에게는 `effective_cache_size`로 "둘을 합치면 이 정도는 캐시에 있다"고 알려준다.

**왜 비용인가**: 원하는 페이지가 여기 있으면 `EXPLAIN (ANALYZE, BUFFERS)`에 `shared hit`으로 찍히고 메모리 접근으로 끝나지만, 없으면 `shared read` — 즉 **디스크 I/O**다. 둘의 지연 차이는 자릿수 단위다.

**"적재율"이란**: 이 캐시에 **실제 행(엔트리)이 몇 건 담기느냐는 밀도**를 뜻한다. 여기가 핵심인데 — **shared_buffers는 "몇 GB"로 고정이지 "몇 행"으로 고정이 아니다.** 엔트리가 비대해지면 같은 데이터를 담는 데 페이지가 더 많이 필요해지고, 같은 메모리에 들어가는 행의 수가 준다.

#### (2) 워킹셋(working set) — 실제로 자주 손대는 데이터의 크기

**무엇인가**: 어떤 부하를 처리하는 동안 **실제로 접근하는 페이지들의 집합**, 그리고 그 크기. OS 가상 메모리 이론에서 온 개념으로, "이 부하를 감당하려면 메모리에 최소 얼마가 올라와 있어야 하는가"를 뜻한다. 캐시가 **공급**이라면 워킹셋은 **수요**다.

**왜 비용인가**: 둘의 대소가 성능을 가르는데, **경계를 넘는 순간 성능이 선형이 아니라 계단식으로 무너진다.** 데이터는 매일 조금씩 늘었을 뿐인데 워킹셋이 캐시를 넘어선 그날 갑자기 붕괴한다 — "어제까지 멀쩡했는데" 장애의 상당수가 이 지점이다.

```text
인덱스 200MB (캐시 2GB) → 워킹셋 다 들어감 → INSERT 5,000/s
인덱스 1.5GB            → 아직 들어감      → INSERT 4,800/s
인덱스 2.5GB            → 못 들어감        → INSERT   300/s   ← 절벽 (예시 수치)
```

PK 설계가 워킹셋을 얼마나 좌우하는지가 2-3절의 요지다. 같은 1,000만 행 `orders`라도 **INSERT 한 건이 손대는 페이지**를 세어 보면 이렇게 갈린다.

| | 힙 | PK B-tree |
|---|---|---|
| `bigint IDENTITY` | FSM이 가리키는 끝 페이지 1~2장 | 맨 오른쪽 리프 1장 + 경로 브랜치 2~3장, 합쳐 약 **30KB** |
| UUID v4 | 똑같이 끝 페이지 1~2장 (**PK와 무관**) | 삽입 지점이 트리 전역에 흩어져 **리프 전체 약 400MB**(5만 장) |

힙 쪽은 같고 PK 인덱스 쪽만 **만 배 이상** 벌어진다. "다음 INSERT가 어느 리프로 갈지 예측할 수 없으니 어느 리프든 메모리에 있어야 한다"가 곧 **"모든 리프가 워킹셋"** 이라는 말이다. 이 표에는 아직 FK 인덱스(`order_items.order_id` 등)가 빠져 있다 — 그것들도 uuid면 같은 일이 한 벌씩 더 생긴다.

#### (3) 페이지 분할(page split) — 가득 찬 B-tree 페이지를 둘로 쪼개는 작업

**무엇인가**: B-tree 페이지에 새 엔트리를 넣어야 하는데 자리가 없으면, 페이지를 둘로 쪼개 절반을 새 페이지(파일 끝 또는 재활용된 페이지)로 옮기고, 부모 노드에 "여기서 갈린다"는 새 분리 키를 올린다.

**왜 비용인가**: 세 갈래다. ① 쪼개고 옮기고 부모를 고치는 작업 자체의 비용. ② 쪼갠 결과 **반쯤 빈 페이지가 둘** 생긴다 — 같은 엔트리 수를 담는 데 페이지가 더 필요해지는 **인덱스 bloat**(부풀기)이고, 이는 곧 (1)의 적재율 하락이다. ③ 새 페이지는 파일 끝에 붙으므로 **논리 순서와 물리 순서가 어긋난다**.

PostgreSQL B-tree 리프의 fillfactor 기본값은 90인데, 여기에 중요한 비대칭이 있다 — **맨 오른쪽 끝에 붙는 삽입**은 페이지를 90%까지만 채우고 오른쪽에 새 페이지를 이어 붙이는 "이어 붙이기"이고, **중간에 끼워 넣는 삽입**만 진짜 반반 분할이다. 이 비대칭이 2-3절의 원칙 ②를 만든다.

#### (4) 랜덤 I/O — 디스크의 흩어진 위치를 오가는 접근

**무엇인가**: 인접한 블록을 이어서 읽는 순차 I/O와 달리, 매번 다른 위치로 건너뛰며 읽고 쓰는 접근 패턴.

**왜 비용인가**: 같은 바이트 수를 읽어도 훨씬 느리다. 플래너가 이 차이를 모델링한 값이 `random_page_cost`(기본 4.0) 대 `seq_page_cost`(기본 1.0)이다. B-tree 범위 스캔은 리프의 좌우 링크를 따라가는데, 페이지 분할로 리프의 논리 순서와 파일상 물리 순서가 어긋나 있으면 이 순차 스캔이 랜덤 I/O로 전락한다.

#### (5) WAL과 full_page_writes — 변경을 먼저 적어 두는 로그, 그리고 페이지 통째 기록

**무엇인가**: WAL(Write-Ahead Log)은 "데이터 파일을 고치기 전에 무엇을 고칠지 먼저 로그에 적는다"는 내구성 장치다. 여기에 PostgreSQL 고유의 규칙이 하나 붙는다 — **체크포인트 이후 어떤 페이지를 처음 건드릴 때는 변경분이 아니라 8KB 페이지 전체 이미지(FPI, full page image)를 통째로 WAL에 쓴다**(`full_page_writes`, 기본 on).

**왜 그런 규칙이 있는가**: OS가 8KB 페이지를 디스크에 쓰는 도중 전원이 나가면 페이지가 반만 기록된 채 찢어질 수 있는데(torn page), 그런 페이지에는 "몇 바이트를 이렇게 고쳐라"는 변경분 로그를 적용해 봐야 복구가 안 된다. 그래서 체크포인트 후 첫 변경 때는 성한 페이지 전체를 로그에 박아 둔다.

**왜 비용인가**: 같은 페이지를 계속 건드리면 FPI는 한 번이지만, **매번 다른 페이지를 건드리면 매번 FPI**다. INSERT 한 건마다 8KB가 WAL에 실린다는 뜻이고, 이는 WAL 볼륨 증가 → 체크포인트 I/O 증가 → 스트리밍 복제 지연 → 아카이브 비용 증가로 번진다. InnoDB 설명에는 없던 PostgreSQL 고유의 비용 항목이다(MySQL 대조: InnoDB는 같은 찢어진 페이지 문제를 doublewrite buffer로 풀어서, 리두 로그가 페이지 단위로 부풀지는 않는다).

### 2-2. 원칙 ① 작게 — 곱셈 계수는 사라진 게 아니라 자리를 옮겼다

#### 먼저 용어 — 엔트리(entry)란

사슬의 첫 고리가 "엔트리"라 이것부터 고정한다. B-tree 노드 하나가 곧 **8KB 페이지 한 장**이고, **엔트리는 그 페이지 안에 기록된 한 건의 레코드**, 즉 "행 하나에 대응하는 한 줄"이다.

| 위치 | 엔트리 하나에 들어있는 것 |
|---|---|
| **힙 페이지** | 라인 포인터 4B + 튜플 헤더 24B + 행 데이터 (모든 컬럼) |
| **B-tree 리프** (PK든 세컨더리든) | 라인 포인터 4B + 인덱스 튜플 헤더 8B(**TID 6B 포함**) + 키 값 |
| B-tree 브랜치 | 분리 키(피벗, 자식을 가르는 데 필요한 접두 부분만) + 자식 블록 번호 |

`idx_users_email`의 리프 페이지 한 장(8KB)은 페이지 헤더 24B + 라인 포인터 배열 + `│ 헤더 8B(TID (1042,7)) │ "c@z.com" │` 같은 인덱스 튜플 수백 개 + 특수 영역 16B(좌우 리프 링크·레벨)로 채워진다.

정리하면 **엔트리 = 키 값 + TID(헤더에 포함) + 라인 포인터**다. 여기 어디에도 PK 값이 없다. `users.id`가 `bigint`든 `uuid`든 **이 페이지의 엔트리 크기는 1바이트도 달라지지 않는다.** InnoDB의 "PK는 (행 수) × (세컨더리 인덱스 수)만큼 곱해지는 계수"라는 명제는 PostgreSQL에서 **성립하지 않는다.**

> MySQL 대조: InnoDB 세컨더리 리프 엔트리는 (키, PK)라 PK가 100바이트면 인덱스 5개 × 1,000만 행에 `92B × 1,000만 × 5 ≈ 4.6GB`가 얹힌다. PostgreSQL 면접에서 이 계산을 그대로 말하면 InnoDB 지식을 PostgreSQL에 오적용한 것이다.

#### 그래서 "작게"는 폐기인가 — 아니다, PK가 들어가는 자리가 세 군데 남는다

**① PK 인덱스 자체.** 리프 엔트리가 (PK 값, TID)라 PK가 크면 그만큼 비대해진다. 여긴 곱셈 없이 1배다.

**② FK 컬럼과 FK 인덱스 — 여기가 새 곱셈 계수다.** `order_items.order_id`, `payments.order_id`, `shipments.order_id`처럼 자식 테이블마다 부모의 PK 값이 **힙 컬럼으로 한 벌**, **FK 인덱스 엔트리로 한 벌** 더 들어간다. PostgreSQL은 FK 컬럼에 인덱스를 **자동 생성하지 않지만**, 없으면 부모 행을 DELETE하거나 키를 UPDATE할 때마다 자식 테이블 전체를 훑어야 하므로 사실상 필수다.

즉 곱셈 계수가 "세컨더리 인덱스 개수"에서 **"자식 테이블(FK) 개수 × 자식 행 수"** 로 자리를 옮긴 것이지 사라진 게 아니다. 그리고 자식 행은 보통 부모보다 훨씬 많다(주문 1건에 품목 여러 건).

**③ 조인 키 비교와 해시 테이블.** `Nested Loop`의 `Index Cond` 비교, 해시 조인이 `work_mem` 안에 만드는 해시 테이블 — 8바이트 정수와 100바이트 복합 키는 CPU 비용이 다르고, 해시 테이블이 커지면 `Batches > 1`로 디스크에 쏟아지는 시점이 빨라진다.

#### 페이지당 엔트리 수가 주는 건 그냥 나눗셈이다

이유는 단순하다 — **페이지가 8KB로 고정이기 때문**이다. 늘어나지 않는 상자에 더 큰 물건을 넣으면 개수가 주는 것과 같다.

```text
페이지당 엔트리 수 ≈ (8,192 − 페이지 헤더 24 − 특수 영역 16) × fillfactor ÷ 엔트리 크기
                   ≈ 8,152 × 0.9 ÷ 엔트리 크기 ≈ 7,300바이트 ÷ 엔트리 크기
```

`order_items.order_id`의 FK 인덱스에서 **인덱스 컬럼은 그대로 두고 키 타입만 바꾼** 세 경우를 계산해 보면(8바이트 정렬 패딩은 무시한 근사):

| | `bigint` (8B) | `uuid` (16B) | 복합 PK (100B) |
|---|---|---|---|
| 엔트리 하나 | 4 + 8 + **8** = **20B** | 4 + 8 + **16** = **28B** | 4 + 8 + **100** = **112B** |
| **페이지당 엔트리 수** | 약 **366개** | 약 **262개** | 약 **65개** |

**컬럼 구성은 그대로인데 키 타입만 바뀌었을 뿐인데 페이지당 수용량이 72%, 18%로 깎였다.** 자식 행 5,000만 건 기준으로 나머지가 자동으로 따라온다.

```text
① 페이지당 엔트리 감소     366개 → 262개 → 65개
② FK 인덱스 페이지 수 증가  13.7만 장(약 1.1GB) → 19.1만 장(약 1.5GB) → 77만 장(약 6GB)
   (+ 힙에도 FK 컬럼이 8B → 16B → 100B로 5,000만 벌: +400MB / +4.6GB)
③ shared_buffers 적재율 하락
   shared_buffers 2GB = 페이지 262,144장
     bigint: 262,144 × 366 ≈ 9,600만 엔트리 상주
     uuid  : 262,144 × 262 ≈ 6,900만 엔트리 상주
     └ 메모리는 똑같은데 캐시되는 행이 28% 줄었다
④ 캐시 미스 증가 → 디스크 I/O 증가 (Buffers: shared read 증가)
```

핵심은 ③이다. **shared_buffers는 "몇 GB"로 고정이지 "몇 행"으로 고정이 아니다.** 엔트리가 뚱뚱해지면 같은 메모리에 담기는 **행의 수**가 줄고, 어제까지 메모리에서 끝나던 조회가 오늘은 디스크를 때리기 시작한다.

(보정 하나: PostgreSQL 13부터 B-tree는 같은 키에 딸린 TID들을 posting list로 묶는 **중복 제거(deduplication)** 를 하므로, FK 인덱스처럼 중복 키가 많은 인덱스는 실제 크기가 위 숫자보다 작아진다. 그래도 키 크기의 차이는 남고 사슬의 방향은 그대로다.)

> PK가 크다 → 자식 테이블의 FK 컬럼·FK 인덱스 엔트리가 비대해진다(자식 테이블 수만큼) → 8KB 페이지 하나에 들어가는 엔트리 수가 줄어든다 → 같은 데이터를 담는 데 페이지가 더 많이 필요하다(트리 높이도 올라갈 수 있다) → **고정 크기인 shared_buffers에 담기는 "행의 수"(적재율)가 떨어진다** → 같은 쿼리를 쳐도 캐시 미스가 늘어난다 → **캐시 미스는 곧 디스크 I/O다.**

"메모리 부하"라는 말은 이 사슬 전체를 한 단어로 뭉갠 것이다. 면접에서는 고리를 하나씩 짚어 말한다.

#### 브랜치 노드는 어떻게 되나 — 유일성은 TID가 만들고, 무게는 가볍다

**InnoDB가 브랜치에도 PK를 붙이는 이유는 트리 탐색의 유일성**이었다. 중복 값이 허용되는 세컨더리 인덱스에서 특정 엔트리 하나를 집으러 내려가려면 분기 키가 유일해야 하기 때문이다. PostgreSQL은 같은 문제를 **TID로 푼다.** B-tree 엔트리는 (키, TID) 순으로 정렬되고(PostgreSQL 12부터 힙 TID가 정렬 키의 마지막 컬럼처럼 취급된다), 브랜치의 분리 키(피벗)는 자식을 가르는 데 필요한 접두 부분만 남기고 잘라내므로(suffix truncation) 리프 엔트리보다 오히려 작다.

**얼마나 아픈가 — 세 경로의 무게가 전혀 다르다.** 여기를 뭉뚱그리면 "트리 높이가 올라간다"를 주장의 중심에 세우는 실수를 하게 된다.

| | 경로 | 무게 | 이유 |
|---|---|---|---|
| ⑴ | 브랜치가 차지하는 **공간** | **무시 가능** | fan-out이 수십~수백이라 브랜치는 전체 페이지의 수 % 이하 — 1,000만 행 bigint 인덱스에서 리프 2.7만 장에 브랜치 100장 안팎 |
| ⑵ | **트리 높이** | 부차적 | 오를 수 있지만 **계단식이고 값이 싸다** — 1,000만 행에서 bigint는 3단, 100B PK는 4단 |
| ⑶ | **리프 페이지 수 = shared_buffers 적재율** | **주범** | 매끄럽게, 항상, 비례해서 나빠진다. 위의 ①~④ 사슬이 이것이다 |

**브랜치 레벨은 페이지 수가 워낙 적어 사실상 항상 shared_buffers에 상주한다.** 그래서 트리 한 단이 늘어난 비용은 대개 "디스크 I/O 한 번"이 아니라 "메모리 접근 한 번"이고, 높이는 로그 함수라서 어지간해선 안 오른다.

정리하면 **PK 크기가 성능을 때리는 경로의 순위는 ⑶ ≫ ⑵ > ⑴이다.** ⑶을 주장으로 세우고 ⑵는 "상위 레벨은 캐시에 상주하니 부차적"이라고 덧붙이는 게 정확한 그림이며, 셋을 동급으로 나열하면 무게 차이를 모르는 것으로 읽힌다.

### 2-3. 원칙 ② 단조 증가 — 힙은 무관하지만 PK B-tree는 그대로 앓는다

여기가 PostgreSQL에서 **가장 자주 틀리는 지점**이다. "PostgreSQL은 힙이니까 UUID PK가 테이블을 흩뜨리지 않는다"는 맞다. 그런데 거기서 "그러니 UUID v4 PK는 PostgreSQL에서 문제없다"로 건너뛰면 틀린다. **삽입 위치를 값이 결정하는 구조가 하나 남아 있기 때문이다 — PK B-tree, 그리고 그 값을 받는 FK 인덱스들.**

두 층을 나눠 본다.

- **힙**: 새 행은 FSM이 가리키는 빈 공간(대개 파일 끝)에 들어간다. PK가 `bigint`든 `uuid`든 **힙 쪽 워킹셋은 끝 페이지 몇 장으로 같다.** 여기까지는 "PostgreSQL은 랜덤 PK에 강하다"가 맞다.
- **PK B-tree**: 삽입 위치를 **키 값이 결정한다.** 여기서 두 갈래로 갈린다.

**단조 증가 PK**(`bigint GENERATED ALWAYS AS IDENTITY`)에서는 새 엔트리가 항상 맨 오른쪽 리프로 간다. 그 페이지가 fillfactor(90%)까지 차면 오른쪽에 새 페이지를 이어 붙일 뿐이다(최근 버전은 이 리프를 기억해 두고 루트부터의 탐색조차 건너뛴다). 손대는 페이지가 늘 "맨 끝 한 장"이라 shared_buffers에 항상 있고, 파일에도 순차로 쌓인다.

**랜덤 PK**(UUID v4)에서는 삽입 지점이 **트리 전역에 흩어진다.** 대상 리프가 이미 가득 차 있으면 **페이지 분할**이 일어난다 — 반반으로 쪼개고, 새 페이지를 파일 끝에 붙이고, 부모에 새 분리 키를 올린다. 그 결과가 네 갈래로 번진다.

> ⑴ 분할 비용 자체 + 반쯤 빈 페이지들(**인덱스 bloat**) → 같은 엔트리 수에 페이지 수가 늘고 → 적재율이 떨어진다. (유일한 무작위 키라 PostgreSQL 13의 중복 제거도 도움이 안 된다.)
>
> ⑵ 새 페이지는 파일 끝에 붙으므로 **논리 순서(리프의 좌우 링크)와 물리 순서가 어긋난다** → 리프 링크를 따라가는 범위 스캔이 순차 I/O에서 **랜덤 I/O로 전락**한다.
>
> ⑶ 삽입 지점이 전역에 흩어지므로 **인덱스의 모든 리프가 워킹셋**이 된다. 캐시가 인덱스 전체를 못 담으면 INSERT 한 건마다 대상 리프를 디스크에서 **읽어와야** 쓸 수 있다 — 쓰기가 읽기 I/O를 유발하는 역설이고, 이걸 **캐시 오염**이라 부른다.
>
> ⑷ **WAL 증폭(PostgreSQL 고유)**: 매 INSERT가 체크포인트 이후 처음 건드리는 리프일 확률이 높으니 `full_page_writes` 규칙에 따라 **INSERT 한 건에 8KB 페이지 이미지 하나씩** WAL에 실린다. 단조 증가라면 같은 리프를 수백 번 건드리는 동안 FPI는 한 번이다. WAL 볼륨 증가 → 체크포인트 I/O 증가 → 스트리밍 복제 지연 → 아카이브 비용 증가. `EXPLAIN (ANALYZE, WAL)`의 `WAL: fpi=`와 `pg_stat_wal`(PostgreSQL 14+)의 `wal_fpi`로 관찰한다.

접수창구 비유 — 서류 **원본은 상자에 도착 순으로 쌓는다**(힙: PK와 무관). 문제는 **번호별 색인 카드철**(PK B-tree)이다. 번호표 순서로 카드를 **맨 뒤에 끼우는 것**(단조 증가)과, 이미 꽉 찬 카드철 **중간을 벌려 끼우려고 카드철을 쪼개는 것**(랜덤)의 차이다. 그리고 쪼갠 카드철은 매번 복사기(WAL)에 한 장 통째로 올라간다.

> MySQL 대조: InnoDB에서는 이 모든 일이 **테이블 그 자체**(클러스터드 리프 = 행 전체, 16KB)에서 일어난다. 피해 규모가 "PK 인덱스 크기"가 아니라 "테이블 크기"라 랜덤 PK가 PostgreSQL보다 훨씬 치명적이다. "UUID PK가 나쁘다"의 강도는 엔진마다 다르다 — PostgreSQL은 덜 아프지만 안 아픈 게 아니다.

### 2-4. before / after — PK 설계로 보는 두 원칙

```sql
-- before: 랜덤 PK, 그리고 FK 인덱스 누락
CREATE TABLE orders (
    id  uuid PRIMARY KEY DEFAULT gen_random_uuid(),   -- v4: 16바이트 + 무작위 순서
    ...
);
CREATE TABLE order_items (
    order_id uuid NOT NULL REFERENCES orders(id),     -- FK 컬럼에 16바이트 한 벌 더, 인덱스 없음
    ...
);
-- ① orders_pkey: 매 INSERT가 트리 전역의 아무 리프나 열어 분할 → 인덱스 bloat +
--    전 리프가 워킹셋 → INSERT가 읽기 I/O를 유발 + FPI로 WAL 증폭
-- ② FK 인덱스 없음(PostgreSQL은 자동 생성하지 않는다) → 부모 DELETE마다 order_items 전체 Seq Scan
-- ③ 인덱스를 만들어도 그 FK 인덱스 역시 uuid 무작위 삽입 — 같은 병을 한 벌 더 앓는다

-- after: 작고 단조 증가하는 PK + 외부 노출용 식별자 분리 + FK 인덱스
CREATE TABLE orders (
    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- 8바이트, 항상 맨 오른쪽에 append
    public_id uuid NOT NULL DEFAULT gen_random_uuid() UNIQUE,  -- 외부 노출용은 세컨더리 유니크로
    ...
);
CREATE TABLE order_items (
    order_id bigint NOT NULL REFERENCES orders(id),
    ...
);
CREATE INDEX idx_order_items_order_id ON order_items (order_id);
-- 내부 조인·FK·FK 인덱스는 전부 8바이트 순차 키로 가볍게 가고, 외부에는 유추 불가능한
-- public_id만 노출한다. 무작위 삽입 비용은 public_id 유니크 인덱스 하나만 감당한다.
```

**(가산점 포인트)** "PK를 UUID로 할까"라는 논쟁 자체를 우회하는 이 **내부 PK / 외부 식별자 분리** 패턴이 실무의 기본형이다. 무작위 삽입 비용은 `public_id` 유니크 인덱스 한 개가 감당하고, FK와 조인 키는 전부 8바이트 순차 키로 간다. UUID를 쓸 거면 반드시 네이티브 `uuid` 타입(16바이트)으로 담는다 — `text`나 `char(36)`에 담으면 36바이트 이상을 차지하고 비교도 문자열 비교가 된다.

### 2-5. PostgreSQL만의 세 번째 비용 — 비-HOT UPDATE는 모든 인덱스를 갱신한다

1-3절에서 메커니즘은 이미 봤다. 여기서는 **설계 지침**으로 옮긴다. InnoDB 기준 문서에는 없던 항목이고, PostgreSQL 면접에서는 PK 설계와 같은 무게로 물어보는 주제다.

**① 인덱스 하나를 추가하는 비용은 "그 인덱스를 유지하는 비용"만이 아니다.** 그 컬럼을 UPDATE하는 순간 HOT 조건 ①이 깨져 **다른 모든 인덱스까지** 갱신된다. 자주 바뀌는 컬럼(`updated_at`, 카운터, 상태 값)에 인덱스를 거는 결정은 이 비용을 알고 해야 한다.

**② 갱신이 잦은 테이블은 테이블 `fillfactor`를 낮춘다.** 힙의 기본값은 100(꽉 채움)인데, 이러면 HOT 조건 ②(같은 페이지의 여유 공간)를 만족할 수가 없다. 70~80으로 낮춰 새 버전이 들어갈 자리를 미리 비워 둔다. 다만 이미 꽉 찬 페이지에는 소급되지 않는다.

**③ 관찰은 `pg_stat_user_tables`의 `n_tup_upd` 대비 `n_tup_hot_upd`로 한다.** UPDATE가 많은데 HOT 비율이 낮은 테이블이 인덱스 bloat와 VACUUM 부담의 진원지다.

그리고 **PK 설계와 만나는 지점**이 있다. PK 값 자체를 UPDATE하는 설계(자연 키를 PK로 쓰는 경우)는 비-HOT이 확정이고 FK cascade까지 끌고 온다. "PK는 불변이어야 한다"는 원칙이 PostgreSQL에서는 HOT 때문에 한 번 더 무게를 얻는다.

> MySQL 대조: InnoDB는 행을 **제자리에서 갱신**하고 옛 버전은 언두 로그로 보낸다. 세컨더리 인덱스는 **바뀐 컬럼의 인덱스만** 삭제 표시 + 삽입한다. "인덱스 8개 테이블에서 컬럼 하나 UPDATE"의 비용을 결정하는 요인이 두 엔진에서 정반대다 — PostgreSQL은 HOT 여부가, InnoDB는 그 컬럼에 인덱스가 걸렸는지가 결정한다.

### 2-6. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

| 뭉뚱그린 표현 | 이름 | 사슬로 말하면 |
|---|---|---|
| "메모리에 부하가 생긴다" | **shared_buffers 적재율** | 큰 PK → 자식 테이블의 FK 컬럼·FK 인덱스 엔트리 비대(자식 수만큼) → 8KB 페이지당 엔트리 감소 → shared_buffers에 담기는 행 수 감소 → 캐시 미스 증가 → 디스크 I/O 증가 |
| "왔다갔다 해서 성능 이슈" | **페이지 분할 + 랜덤 I/O + WAL 증폭** | 랜덤 PK → PK B-tree 삽입 지점 전역 분산(힙은 무관) → 가득 찬 리프 쪼개기 → 인덱스 bloat + 전 리프가 워킹셋 → 캐시 오염 → INSERT마다 디스크 읽기 + 페이지마다 FPI → WAL·복제 지연 증가 |
| "UPDATE가 느려요" | **비-HOT 갱신 = 전 인덱스 갱신** | 인덱스 컬럼 변경 또는 페이지 여유 없음 → 새 TID → 인덱스 N개 전부 삽입 → 인덱스 bloat → VACUUM 부담 증가 → Index Only Scan의 `Heap Fetches` 증가 |

## 3. 실무 사례 — "규모 유추 방지를 위해 PK를 UUID로 하자"는 제안

### 3-1. 요건은 정당하다, 그리고 "PG니까 괜찮다"는 반론은 반쪽이다

연속 번호 PK를 외부에 노출하면 경쟁사가 "주문 번호가 하루에 얼마나 늘어나는지"로 규모를 유추할 수 있다. 요건 자체는 정당하고, 이걸 "기우"라고 잘라내는 답은 좋지 않다.

그러면 팀에서 "우리는 PostgreSQL이니까 InnoDB의 UUID 문제는 해당 없다"는 반론이 따라붙는다. **반쯤 맞다** — 힙에 대해서는 맞고, PK B-tree·FK 인덱스·WAL에 대해서는 틀리다(2-3절의 ⑴~⑷). 이 문장을 정확히 잘라 말하는 것이 이 사례에서 가져갈 한 마디다.

### 3-2. MySQL에서 비싼 이유와 PostgreSQL에서 비싼 이유는 다르다

여기를 뭉뚱그리면 "UUID는 나쁘다"는 미신이 되고, 반대로 뭉뚱그린 반론에 부딪히면 논거를 못 댄다. 두 엔진의 이유를 나눠서 정리한다.

| | MySQL / InnoDB에서의 대가 | PostgreSQL에서의 대가 |
|---|---|---|
| 주된 이유 | **행 자체가 PK 순으로 물리 정렬**되므로, 무작위 PK는 테이블(= 클러스터드 B+Tree) 중간을 계속 벌려 페이지 분할을 일으킨다 | 힙은 무관하다. 대신 **PK 인덱스 B-tree의 삽입 지역성**이 무너진다 |
| 피해 규모 | **테이블 크기** 전체 | **PK 인덱스 + FK 인덱스** 크기 |
| 세컨더리 인덱스 | 리프에 PK가 복제돼 인덱스 개수만큼 곱해진다 | 리프가 (키, TID)라 **영향 없다** |

PostgreSQL에서 UUID v4 PK가 지불하는 진짜 대가는 셋이다.

**① PK 인덱스 B-tree의 삽입 지역성 상실.** 무작위 키는 트리 전역에 흩어져 꽂히므로 가득 찬 리프를 계속 쪼갠다 — 페이지 분할과 캐시 미스가 늘어난다.

**② 인덱스가 커져 워킹셋이 부풀고 shared_buffers 적재율이 떨어진다.** 키가 8바이트에서 16바이트로 늘면 페이지당 엔트리가 366개에서 262개로 줄고(2-2절), bloat까지 겹치면 인덱스 크기가 더 늘어난다. 게다가 삽입 지점이 예측 불가라 **인덱스 전체가 워킹셋**이 된다.

**③ WAL 기록량 증가.** 매 INSERT가 새 페이지를 처음 건드리므로 `full_page_writes`로 건당 8KB FPI가 실린다. 복제 지연과 아카이브 비용까지 번진다.

**MySQL을 인용할 때는 MySQL이라고 명시하고 섞지 않는다.** "UUID PK를 쓰면 행이 물리적으로 흩어져 테이블이 조각난다"는 문장은 InnoDB에서는 맞고 PostgreSQL에서는 틀린 말이라, 그냥 말하면 오답이 된다.

### 3-3. 대안 — "유추 불가능"과 "무작위 삽입 순서"를 분리한다

핵심 통찰은 이것이다. **요건이 요구하는 건 "유추 불가능"이지 "무작위 삽입 순서"가 아니다.** UUID v4는 두 성질을 한 몸으로 팔고 있을 뿐이고, 랜덤성은 힙에는 무해해도 B-tree에는 최악의 성질이다. 두 성질을 분리하는 대안이 둘 있다.

**(가) 시간 순 정렬성이 있는 ID로 바꾼다.** **UUID v7**은 타임스탬프가 앞쪽에 오는 UUID다 — v4와 같은 16바이트 `uuid` 타입에 담기면서 삽입은 맨 오른쪽 리프에 가깝게 꽂힌다(PostgreSQL 18부터 `uuidv7()` 내장, 그 전에는 애플리케이션에서 생성). **Snowflake ID**는 64비트에 타임스탬프를 상위 비트로 넣는 방식이라 `bigint`에 그대로 들어간다. 둘 다 값 자체는 유추 불가능하면서 B-tree에는 append에 가깝게 꽂힌다.

**대가**: **생성 시각이 값에 드러난다.** 값을 디코딩하면 언제 만들어진 행인지 알 수 있고, 두 ID의 시각 차이도 계산된다. "총량·증가율 유추 방지"가 요건이면 이걸로 충분하지만, "생성 시각조차 숨겨야 한다"가 요건이면 부적합하다. 또 UUID v7은 16바이트라 8바이트 `bigint`보다는 여전히 무겁다.

**(나) 별도의 공개용 식별자 컬럼을 둔다** (2-4절의 after). 내부 PK는 `bigint IDENTITY`로 두고, 외부에는 `public_id uuid ... UNIQUE`만 노출한다.

**대가**: 무작위 삽입 비용이 사라지는 게 아니라 **`public_id` 유니크 인덱스 하나로 격리**되는 것이다. 그 인덱스는 여전히 페이지 분할과 FPI를 겪는다. 다만 FK와 조인 키는 전부 8바이트 순차 키로 가므로, 자식 테이블 수만큼 곱해지던 비용은 없어진다. 추가로 "외부에는 `public_id`, 내부에는 `id`"라는 규칙을 API 계층에서 지켜야 하는 운영 부담이 생긴다.

요건을 한 단계 쪼개서 어느 성질이 진짜 필요한지 되묻는 것 — 이게 시니어의 답변 태도다.

## 4. 꼬리질문 대비 포인트

### "PG는 왜 인덱스 리프에 PK가 아니라 물리 주소(TID)를 넣나요? 행이 옮겨지면 어떻게 하나요?"

힙은 정렬을 유지하지 않으므로 **행이 저절로 이동하는 일이 없다.** InnoDB가 논리 포인터(PK)를 택한 이유(페이지 분할로 행이 옮겨짐)가 PostgreSQL에는 없으니, 물리 주소를 적어 **트리 재탐색 없이 한 번에 점프**하는 쪽을 택했다.

행이 "옮겨지는" 유일한 경우는 UPDATE인데, PostgreSQL은 옮기는 게 아니라 **새 버전을 새 TID에 쓰고 옛 버전에 삭제 표시**를 한다 — 그래서 인덱스마다 새 엔트리를 꽂아야 하고(비-HOT), 그걸 피하는 장치가 HOT이다. `VACUUM FULL`이나 `CLUSTER`처럼 힙을 통째로 다시 쓰는 작업은 인덱스도 전부 재구축한다.

완결된 답은 트레이드오프 양쪽을 함께 말하는 것이다 — **PostgreSQL: 읽기 1단계 + 쓰기 시 전 인덱스 갱신 부담(HOT으로 완화), InnoDB: 읽기 2단계 + 쓰기 안정.** 가산점: PostgreSQL 인덱스 엔트리에는 버전 가시성 정보가 없어 옛 버전의 엔트리도 남는다 — 이것이 Index Only Scan이 visibility map을 확인해야 하는 이유이자, VACUUM이 힙뿐 아니라 인덱스도 청소하는 이유다.

### "100바이트 복합 PK에 세컨더리 인덱스가 5개면, PG에서는 정확히 무슨 일이 벌어지나요?"

함정 질문이다. InnoDB라면 "5개 인덱스 × 1,000만 행에 92B씩 복제"가 정답이지만, **PostgreSQL의 세컨더리 인덱스 5개는 PK 크기에 영향받지 않는다**(리프가 (키, TID)이므로).

대신 비용이 나는 자리를 짚는다. ① PK 인덱스 자체가 엔트리 112B라 페이지당 65개 — bigint의 1/5.6 밀도다. ② **자식 테이블마다** FK 컬럼 100B(힙) + FK 인덱스 엔트리 112B가 붙는다 — 자식 행 5,000만이면 힙 +4.6GB, FK 인덱스 약 6GB. ③ 조인과 해시 테이블에서 100바이트 비교. ④ 복합 PK 컬럼 중 하나라도 UPDATE되면 비-HOT + FK cascade.

처방은 복합 키를 **UNIQUE 제약으로 내리고** `bigint GENERATED ALWAYS AS IDENTITY` 대리 키를 PK로 세우는 것 — 결론은 InnoDB와 같다. 결론은 같은데 **이유의 위치가 다르다**는 걸 보여주면 "두 엔진을 원리로 구분한다"로 들린다.

### "UUID v4를 PK로 쓴 테이블에 INSERT가 몰리면 PG에서는 무슨 일이 벌어지나요?"

두 층으로 나눠 답한다.

**힙**: 아무 일도 없다 — FSM이 가리키는 끝 페이지에 순서대로 쌓인다.

**PK B-tree(그리고 그 값을 받는 FK 인덱스들)**: 삽입 지점이 전역에 흩어진다 → 가득 찬 리프마다 **페이지 분할** → 반쯤 빈 리프가 쌓이는 **인덱스 bloat** → **모든 리프가 워킹셋**이 되어 캐시가 못 담는 순간부터 INSERT 한 건마다 리프를 디스크에서 읽어온다(쓰기가 읽기 I/O를 유발) → 매 INSERT가 다른 페이지를 건드리니 `full_page_writes`로 **WAL이 건당 8KB씩 증폭**돼 체크포인트와 복제 지연으로 번진다.

관찰 수단: `pgstattuple` 확장의 `pgstatindex()`가 주는 `avg_leaf_density`(리프 평균 적재율), `pg_stat_wal.wal_fpi`, `EXPLAIN (ANALYZE, WAL)`. 대안은 UUID v7 / Snowflake / 내부 PK와 외부 식별자 분리다. **왜 IDENTITY는 안 그런가**를 물으면 — 삽입 위치를 키 값이 결정하는 B-tree에서 단조 증가는 "맨 오른쪽 한 장"만 만지지만 랜덤은 "아무 장이나" 만지기 때문이다.

### "PK를 안 만들면 PG는 어떻게 하나요?" (가산점 포인트)

**아무것도 안 한다.** InnoDB는 테이블이 곧 클러스터드 인덱스라 PK가 없으면 NOT NULL UNIQUE 인덱스를 승격하거나 6바이트 숨은 row id라도 만들지만, PostgreSQL의 힙은 PK 없이도 완전히 성립한다 — 숨은 대리 키를 만들지 않는다. `ctid`가 있긴 하지만 **불변 식별자가 아니다**(UPDATE로 바뀌고, VACUUM이 슬롯을 재사용한다).

그래서 PK 없는 테이블의 대가는 성능이 아니라 **운영 기능 쪽**에서 온다. ① **논리 복제**에서 `REPLICA IDENTITY`가 없어 UPDATE/DELETE가 에러가 난다(`cannot update table ... does not have a replica identity`). ② `INSERT ... ON CONFLICT`의 충돌 대상이 없어 UPSERT를 못 쓴다. ③ 중복 행 제거를 `ctid`로 골라 지우는 수공업으로 해야 하고, ORM 매핑도 안 된다.

결론은 InnoDB와 같되 이유가 반대다 — **"InnoDB는 어차피 만들어지니 의도적으로 설계하라", "PostgreSQL은 안 만들면 정말 없으니 반드시 만들어라."**

### "MySQL로 물어보면 답이 달라지는 부분은?" (경험 대조)

다섯 지점이다.

① **리프에 든 것** — InnoDB는 클러스터드 리프 = 행 전체, 세컨더리 리프 = PK 값. PostgreSQL은 모든 리프가 (키, TID)라 "클러스터드 vs 세컨더리" 구분 자체가 없다.

② **곱셈 계수의 위치** — InnoDB는 세컨더리 인덱스 개수만큼 PK가 복제되고, PostgreSQL은 세컨더리에는 영향 없이 **자식 테이블의 FK 컬럼·FK 인덱스**로 자리를 옮긴다(그리고 PostgreSQL은 FK 인덱스를 자동 생성하지 않는다).

③ **랜덤 PK의 피해 범위** — InnoDB는 테이블 자체가 흩어지지만, PostgreSQL은 힙은 무관하고 **PK B-tree + FK 인덱스 + WAL FPI**가 앓는다. 덜 아프지만 안 아픈 게 아니다.

④ **UPDATE 비용의 방향** — InnoDB는 제자리 갱신 + 바뀐 컬럼의 인덱스만, PostgreSQL은 새 TID + 비-HOT이면 **모든** 인덱스.

⑤ **PK가 없을 때** — InnoDB는 숨은 row id를 강제로 만들고, PostgreSQL은 정말 없다(대가는 논리 복제·UPSERT·ORM).

덤으로, InnoDB는 세컨더리에 PK가 공짜로 들어 있어 PK 컬럼이 자동으로 커버링되지만 PostgreSQL은 `INCLUDE`로 명시해야 한다. 이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "저장 구조에서 도출했다"로 들린다.

## 한 줄 요약

**PostgreSQL에는 클러스터드 인덱스가 없다 — 테이블은 정렬 없는 힙이고, PK를 포함한 모든 인덱스는 리프에 (키, TID)를 담아 힙을 직접 가리키는 세컨더리이며, 조회는 인덱스 → TID → 힙 페치 1단계다. 그런데도 PK 설계 2원칙은 살아남는다 — ① 작게(세컨더리 복제 곱셈은 없지만 **자식 테이블의 FK 컬럼·FK 인덱스·조인 키**에 PK가 들어가 페이지당 엔트리가 줄고 → shared_buffers 적재율이 떨어지고 → 디스크 I/O가 는다), ② 단조 증가(힙은 무관하지만 **PK B-tree의 무작위 삽입**이 페이지 분할 → 인덱스 bloat + 캐시 오염 + `full_page_writes` WAL 증폭을 부른다). 여기에 PG만의 셋째 비용, **비-HOT UPDATE = 새 TID = 모든 인덱스 갱신**(HOT과 fillfactor로 완화)이 붙는다. 비용은 뭉뚱그리지 말고 이 이름들의 사슬로 말한다.**
