# 트랜잭션 ACID — 글자마다 "한 줄 정의 + 메커니즘 하나"로 고정한다

> 핵심 관전 포인트: **ACID는 암기 항목이 아니라 글자마다 "한 줄 정의 +
> 그것을 구현하는 메커니즘 하나"를 묶어서 말하는 문제다. A(원자성) =
> 전부 반영 or 전부 취소, 중간 상태 없음 — PostgreSQL에서는 MVCC 튜플
> 버전 + `pg_xact`(커밋 로그)의 취소 표시, undo 로그는 **없다** /
> C(일관성) = 트랜잭션 전후로 시스템의 불변식·제약이 유지 —
> DB 제약 + 애플리케이션의 공동 책임 / I(격리성) = 동시 트랜잭션이 서로의
> 중간 상태를 보지 않음 — MVCC 스냅샷 + 행 락 / D(지속성) = 커밋 응답
> 후엔 전원이 나가도 보존 — WAL + 커밋 시 fsync. 특히 두 가지를 틀리지
> 말 것: ① "끼어들 수 없다"는 격리성의 언어다 — 원자성은 동시성이 아니라
> 실패에 대한 보장. ② 로그 쓰기도 똑같은 디스크 I/O다 — 다만 파일 끝
> 순차 append라서 싸고, 흩어진 페이지의 랜덤 쓰기는 체크포인트 때 모아서
> 한다. 이게 WAL이 존재하는 이유다.**

---

## 0. 질문 + 의도

**질문**: "트랜잭션의 ACID를 설명해주세요."

**출제 의도**: 개념 암기가 아니라, 이후 꼬리 질문("그럼 커밋 순간 서버가
죽으면 D는 어떻게 보장되나요")의 **발판**. 각 글자를 실제 메커니즘(WAL,
MVCC 튜플 버전과 `pg_xact`, 스냅샷/행 락)과 연결하는지로 깊이를 잰다. 즉
"네 단어를 외웠는가"가 아니라, 각 글자가 **무엇으로부터 무엇을
지키는지**(실패로부터? 동시성으로부터? 장애로부터?)와 **DB가 그걸 무슨
장치로 구현하는지**를 짝지어 말할 수 있는지를 본다. 여기서 짝이 맞으면
격리 수준·MVCC(중급), WAL·체크포인트·VACUUM 내부(중급)로 자연스럽게
이어진다.

## 1. 개념 — 네 글자를 "한 줄 정의 + 메커니즘 하나"로 고정

트랜잭션은 **여러 개의 작업을 하나의 논리적 단위로 묶은 것**이다.
계좌이체가 표준 예시인 이유 — "A 차감"과 "B 입금"이라는 두 UPDATE는
따로 보면 각각 멀쩡하지만, **둘 중 하나만 실행된 세상은 존재해선 안
되기** 때문이다. ACID는 이 "하나의 단위"라는 약속을 네 방향에서
지키는 성질들이다.

| 글자 | 한 줄 정의 | 무엇으로부터 지키나 | PostgreSQL의 메커니즘 |
|---|---|---|---|
| **A** 원자성(Atomicity) | 전부 반영 or 전부 취소 — 중간 상태 없음 | **실패**(에러·크래시) | MVCC 튜플 버전 + `pg_xact` 취소 표시 (뒷정리는 VACUUM) |
| **C** 일관성(Consistency) | 트랜잭션 전후로 불변식·제약이 항상 유지 | **규칙 위반** | 제약(CHECK·UNIQUE·FK·EXCLUDE) + 애플리케이션 (공동 책임) |
| **I** 격리성(Isolation) | 동시 트랜잭션이 서로의 중간 상태를 보지 않음 | **동시성** | MVCC 스냅샷 + 행 락 (기본 READ COMMITTED) |
| **D** 지속성(Durability) | 커밋 응답 후엔 전원이 나가도 보존 | **장애**(전원 차단·크래시) | WAL + 커밋 시 fsync |

> MySQL 대조: InnoDB라면 A 칸이 **undo 로그**, D 칸이 **redo 로그(+ binlog)**
> 다 — PG에는 undo 로그가 **없다**(2-2절).

비유로 고정하면 —

- **A**: 계약서에 양쪽이 서명하거나, 아무도 안 하거나. "한쪽만 서명된
  계약서"라는 물건은 세상에 존재하지 않는다.
- **C**: 복식부기 장부. 어떤 거래를 적든 차변과 대변의 총합은 맞아야
  한다. 거래(트랜잭션)가 장부의 **규칙**을 깨면 그 거래 자체가 무효다.
- **I**: 각자 회의실에서 작업하고, 문서가 완성되기 전에는 서로의
  초안을 들여다보지 않는다.
- **D**: 연필이 아니라 잉크로 쓴 서명. 정전이 나도 종이에 남는다.

### 1-1. A와 I를 절대 섞지 말 것 — "끼어들 수 없다"는 격리성의 언어다

가장 흔한 혼동이자 이 문서가 첫 번째로 교정하는 지점. 원자성을
"트랜잭션 실행 도중 누군가 끼어들 수 없다"로 설명하면 틀린다 —
**"끼어든다"는 동시성의 언어이고, 동시성을 다루는 글자는 I(격리성)**다.

두 글자는 지키는 대상 자체가 다르다:

- **원자성이 상대하는 적은 "실패"다.** 다른 트랜잭션이 하나도 없는,
  나 혼자 쓰는 DB에서도 원자성은 필요하다 — UPDATE 두 개 중 첫 번째만
  실행되고 서버가 죽으면? 에러가 나서 두 번째를 실행 못 하면? 이때
  "절반만 반영된 세상"을 없애는 것이 원자성이다.
- **격리성이 상대하는 적은 "동시성"이다.** 크래시가 절대 없는 완벽한
  서버라도, 두 트랜잭션이 같은 계좌를 동시에 만지면 서로의 **중간
  상태**(차감은 됐는데 입금은 아직인 순간)를 볼 위험이 생긴다. 이걸
  차단하는 것이 격리성이다.

한 문장 테스트로 구분한다 — **"혼자 쓰는 DB에서도 문제가 되면 A,
둘 이상이 써야 문제가 되면 I."**

### 1-2. C는 층위가 다르다 — "같은 쿼리 같은 결과"가 아니다

두 번째 교정 지점. 일관성은 "같은 쿼리를 날리면 같은 결과가 나온다"가
**아니다**(그건 굳이 분류하면 격리 수준의 반복 읽기 이야기에 가깝다).

일관성의 정의는 이것이다 — **트랜잭션이 시작되기 전에 성립하던 시스템의
규칙(불변식·제약)이, 트랜잭션이 끝난 후에도 여전히 성립한다.**

계좌이체로 말하면 규칙은 두 가지다:

1. **총합 불변**: 이체는 돈을 옮기는 것이지 만들거나 없애는 게 아니다.
   A+B의 총합은 이체 전후로 같아야 한다.
2. **잔액 ≥ 0**: 어떤 순간에도 계좌 잔액은 음수가 될 수 없다(마이너스
   통장이 아니라면).

**일관성이 깨진 상태란**: 10만원을 이체했는데 A에서는 빠졌고 B에는 안
들어와서 **두 계좌 총합에서 10만원이 증발한 상태**, 또는 잔액 5만원인
계좌에서 10만원이 빠져나가 **잔액이 -5만원이 된 상태**다. 각 행만 보면
멀쩡한 숫자지만, 시스템 전체의 규칙이 무너져 있다.

#### 흔한 오해 ① — 일관성은 컬럼 타입/스키마 얘기가 아니다

"규칙이 유지된다"를 **"컬럼 타입이 바뀌지 않는다"** 로 읽으면 완전히 다른
층위로 간다. 둘은 이렇게 갈린다.

| | 무엇에 대한 것 | 누가 바꾸나 | 트랜잭션과의 관계 |
|---|---|---|---|
| **컬럼 타입** | 스키마(구조) | `ALTER TABLE` (DDL) | 트랜잭션이 건드리는 대상이 아니다 |
| **일관성(C)** | 데이터 값(상태) | `INSERT`/`UPDATE`/`DELETE` (DML) | 트랜잭션 전후로 규칙이 유지돼야 한다 |

반례 하나면 충분하다.

```text
balance bigint      ← 타입 선언은 그대로. 아무도 스키마를 안 건드렸다.

A: -50000           ← bigint로서 100% 유효한 값. 타입 위반이 아니다.
                    ← 그런데 "잔액 ≥ 0" 규칙 위반 = 일관성 파괴
```

`-50000`은 `bigint`가 담을 수 있는 지극히 정상적인 값이다. **타입은
"어떤 값이 담길 수 있는가"의 문제고, 일관성은 "지금 담긴 값들이 업무
규칙에 맞는가"의 문제**다. 타입 검사를 전부 통과해도 일관성은 얼마든지
깨진다.

#### 흔한 오해 ② — 일관성은 "언제나"가 아니라 "경계에서" 성립한다

규칙이 트랜잭션 **도중에는 반드시 깨진다**는 것도 같이 알아야 한다.

```text
                      A잔액   B잔액   총합
트랜잭션 시작 전        50만    30만    80만   ← 규칙 성립 ✅
  ↓ UPDATE A -10만
    (트랜잭션 도중)     40만    30만    70만   ← 규칙 위반 ❌ 10만원 증발!
  ↓ UPDATE B +10만
트랜잭션 종료 후        40만    40만    80만   ← 규칙 복구 ✅
```

두 UPDATE를 물리적으로 동시에 실행할 수는 없으니 **총합이 안 맞는 순간은
반드시 존재한다.** 일관성이 요구하는 건 "항상 성립"이 아니라 **시작 전과
커밋 후라는 두 경계에서만 성립**이다.

그럼 깨져 있는 그 순간은 누가 감당하나 — **격리성(I)이 그 중간 상태를
남에게 보이지 않게 가려주고, 원자성(A)이 실패했을 때 그 상태로 멈추지
않게 되돌린다.** C가 다른 세 글자와 층위가 다르다는 말의 실체가 이것이다.
**A·I·D는 메커니즘이고, C는 그것들이 떠받치는 목표다.** (PG의 `DEFERRABLE
INITIALLY DEFERRED` 제약이 이 "경계에서만"을 문법으로 옮긴 것 — 문장마다가
아니라 **커밋 순간에** 검사한다.)

이 글자만 유일하게 **DB 혼자 다 지켜줄 수 없다**는 점이 특징인데,
3절에서 자세히 다룬다.

## 2. 동작 — 계좌이체 한 건으로 네 글자를 관통한다

### 2-1. before / after — 트랜잭션이 없으면 무슨 일이 벌어지나

```sql
-- ❌ before: 트랜잭션 없이 UPDATE 두 방 (자동 커밋 모드)
UPDATE account SET balance = balance - 100000 WHERE id = 'A';
-- ← 여기서 서버 다운 / 애플리케이션 예외 / 네트워크 단절이 나면?
UPDATE account SET balance = balance + 100000 WHERE id = 'B';

-- 결과: A에서 10만원이 빠졌는데 B에는 안 들어옴.
-- "절반만 실행된 세상"이 그대로 남는다 = 원자성 없음
-- → 총합에서 10만원 증발 = 일관성 파괴로 번짐
```

```sql
-- ✅ after: 하나의 트랜잭션으로 묶는다
BEGIN;

UPDATE account SET balance = balance - 100000 WHERE id = 'A';
UPDATE account SET balance = balance + 100000 WHERE id = 'B';

COMMIT;
-- 중간 어디서 실패하든 ROLLBACK — pg_xact에 "취소" 표시 하나로 끝(2-2절).
-- 바깥 세상에는 "둘 다 반영" 아니면 "아무 일도 없었음" 두 상태만 존재.
```

이 한 건의 이체 위에 네 글자가 각각 **언제** 작동하는지를 붙이면
정의가 저절로 복원된다:

- **A가 작동하는 순간**: 첫 UPDATE 후, 둘째 UPDATE 전에 서버가 죽었다.
  재시작한 DB는 WAL을 재생하지만 이 트랜잭션의 **커밋 기록이 없으므로**
  그것이 만든 "40만원" 버전은 아무에게도 보이지 않고, "50만원" 옛 버전은
  지워진 적이 없으니 **되돌릴 것도 없다.** A 잔액은 원래대로.
- **D가 작동하는 순간**: `COMMIT` 성공 응답을 클라이언트가 받은 **직후**
  전원이 나갔다. 재시작해도 이체 결과는 남아 있어야 한다 — **WAL**
  덕분에 남는다(2-3절).
- **I가 작동하는 순간**: 이체가 진행되는 도중 다른 트랜잭션이 A와 B의
  잔액을 조회했다. "차감만 되고 입금은 안 된" 중간 상태를 보여주면 안
  된다 — 조회하는 쪽은 자기 **스냅샷** 기준으로 커밋된 옛 버전을 읽고,
  같은 행을 갱신하려는 쪽은 **행 락**에 걸려 커밋까지 기다린다.
- **C가 확인되는 순간**: 커밋 전후로 총합 불변·잔액 ≥ 0이라는 규칙이
  유지됐는가. A·I·D라는 도구 + 제약 + 애플리케이션 로직이 합작한
  **결과**로서 지켜진다.

### 2-2. PostgreSQL에는 undo 로그가 없다 — A는 "덧붙이기 + 취소 도장"

교과서(정확히는 InnoDB)의 그림은 변경 **전** 값을 적는 undo 로그(A)와
변경 **후** 값을 적는 redo 로그(D), 장부 두 권이다. PostgreSQL은 **WAL 한
권**뿐이고 "되돌리기 장부"가 없다. 없어도 되는 이유는 저장 구조에 있다.

**① 행을 제자리에서 고치지 않는다.** UPDATE는 옛 튜플을 덮어쓰지 않고
**새 튜플 버전을 페이지에 덧붙이며**, 옛 튜플에는 "누가 지웠는지"만
표시한다. 튜플 헤더마다 만든 트랜잭션 ID(`xmin`)와 지운 ID(`xmax`)가
박혀 있다.

```text
UPDATE account SET balance = 400000 WHERE id = 'A';   -- 내 트랜잭션 ID = 1001

힙 페이지 안 (같은 페이지에 두 버전이 공존):
  [옛 버전] balance = 500000   xmin =  980   xmax = 1001  ← "1001이 지움" 표시만
  [새 버전] balance = 400000   xmin = 1001   xmax =    0  ← 새로 덧붙임
```

INSERT = `xmin`, DELETE = `xmax`, UPDATE = 둘 다. **옛 값은 어디로도
옮겨지지 않는다** — "원상복구할 것"이 처음부터 없다.

**② 롤백 = `pg_xact`에 도장 하나.** 트랜잭션 상태(진행 중/커밋/취소)는
`pg_xact`(옛 이름 CLOG)라는 **트랜잭션 ID당 2비트짜리 상태표**에 적힌다.
`ROLLBACK`은 1001번 칸에 "취소" 도장을 찍으면 끝 — 튜플을 하나도 안
건드리니 **갱신한 행이 1건이든 1억 건이든 O(1)** 이다. 이후 읽기는
`xmin`/`xmax`와 이 표를 대조해 "1001은 취소 → 새 버전은 없는 셈, 옛
버전은 산 셈"으로 판정한다.

**③ 뒷정리는 VACUUM.** 취소된 트랜잭션이 남긴 새 버전, 커밋된
UPDATE/DELETE가 남긴 옛 버전은 **죽은 튜플**로 페이지에 남고
VACUUM(autovacuum)이 회수한다. 즉 PG는 **롤백 비용을 그 자리에서 내지
않고 VACUUM에 외상으로 넘긴다**(4절).

**④ 크래시 복구도 REDO뿐.** 마지막 체크포인트 이후의 WAL을 재생해
페이지를 크래시 직전 상태로 만들면 끝. 커밋 레코드가 없는 트랜잭션의
튜플은 그냥 안 보인다. **미커밋분을 되돌리는 UNDO 단계가 없으므로**
거대한 미커밋 배치가 돌던 중 죽어도 복구가 그만큼 길어지지 않는다.

`SAVEPOINT` 이후는 자기 ID를 받는 **서브트랜잭션**이라 `ROLLBACK TO
SAVEPOINT`도 그 ID에만 도장을 찍는다.

| | PostgreSQL | MySQL(InnoDB) — 대조 |
|---|---|---|
| 갱신 방식 | 새 버전 덧붙이기 — 옛 버전은 같은 페이지에 그대로 | 제자리(in-place) 갱신 — 옛 값은 undo 로그(언두 세그먼트)로 |
| 롤백 | `pg_xact`에 취소 표시, O(1) | undo 로그 역재생, 갱신량에 비례 |
| 크래시 복구 | WAL REDO만 | redo 재적용 → 미커밋분 undo의 2단계 |
| 옛 버전 청소 | VACUUM(autovacuum) | 퍼지 스레드 (밀린 양 = history list length) |
| 로그 | WAL 하나(복구·복제·PITR·논리 디코딩 공용) | redo 로그 + binlog 두 벌 |

### 2-3. WAL이 존재하는 이유 — 로그 쓰기도 디스크 I/O다, 다만 싸다

이 문서가 세 번째로 교정하는 지점. "테이블 파일을 고치는 건 I/O라서
느리고, 로그는 그냥 갖고 있으면 되니까 빠르다"는 설명은 틀렸다.
**로그 쓰기도 똑같이 디스크에 쓰는 I/O다.** 메모리에만 갖고 있으면
전원이 나가는 순간 같이 증발하므로 D를 보장할 수 없다 — 커밋 시점에
로그는 반드시 디스크까지 내려가야 한다(fsync).

그럼 왜 굳이 로그에 먼저 쓰나? **같은 디스크 쓰기라도 접근 패턴이
다르기 때문이다.** (이 랜덤 vs 순차 비용 모델은 Q2의 인덱스 손익분기,
Q3의 페이지 분할과 정확히 같은 축이다.)

- **테이블(데이터 페이지)에 직접 반영** = 이번 트랜잭션이 건드린 행들이
  들어 있는 8KB 페이지들은 디스크 여기저기에 **흩어져** 있다. 커밋마다
  이걸 다 쓰려면 흩어진 위치를 오가는 **랜덤 쓰기** — 비싸다.
- **로그에 기록** = WAL은 순서대로 이어지는 세그먼트 파일이고, 쓰기는
  항상 **파일 끝에 이어붙이기(순차 append)** 다. 한 방향으로만 쓴다 —
  같은 디스크 I/O지만 훨씬 싸다.

그래서 전략이 **WAL(Write-Ahead Logging, 로그 선행 기입)** 이다:

> 커밋 순간에는 **싼 순차 쓰기(WAL에 커밋 레코드 append + fsync)만**
> 하고 응답한다. 변경된 데이터 페이지는 `shared_buffers`에 더티 상태로
> 두었다가, 나중에 **비싼 랜덤 쓰기를 모아서**(체크포인트,
> `checkpoint_timeout` 기본 5분 또는 WAL 누적량 기준) 천천히 반영한다.
> 그 사이에 죽어도 WAL이 디스크에 있으니 D는 깨지지 않는다. "선행"의
> 뜻은 **어떤 페이지도 그것을 바꾼 WAL 레코드보다 먼저 디스크에 쓰이지
> 않는다**는 순서 규칙 — 그래서 복구가 REDO만으로 끝난다.

PG의 손잡이 셋 (가산점 포인트) — **`synchronous_commit`**(`off`·`local`·
`on`(기본)·`remote_write`·`remote_apply`): 커밋 응답 전 WAL을 어디까지
기다릴지. **`off`면 응답 뒤 짧은 창에 "커밋했다고 응답한 트랜잭션"이
사라질 수 있다**(순서는 지켜져 데이터가 깨지진 않는다) — 유실을 감수하는
트랜잭션에만 `SET LOCAL`로. **`full_page_writes`**: 체크포인트 후 첫 변경
페이지는 8KB 전체를 WAL에 써 torn page를 막는다(체크포인트 직후 WAL 급증의
원인). 그리고 이 **WAL 하나가** 복구·복제·PITR·CDC를 다 한다.

한 줄로 — **"로그도 디스크 쓰기다. 다만 순차 append라 싸고, 비싼 랜덤
쓰기는 체크포인트로 미뤄 모아서 한다."** 이 문장이 나오면 WAL의 존재
이유를 이해한 것이고, 안 나오면 외운 것이다.

### 2-4. I는 "읽기는 스냅샷, 쓰기는 행 락"

각 트랜잭션(기본 READ COMMITTED에서는 각 **문장**)이 **스냅샷**을 들고
`xmin`/`xmax`에 비추어 볼 버전을 고르므로 **읽기와 쓰기는 서로 막지 않고**,
쓰기 대 쓰기 충돌만 **행 락**(튜플 헤더 `xmax`)이 직렬화한다 — "MVCC가
기본, 락은 쓰기 충돌에만"이 PG의 무게다([격리 수준](transaction-isolation-levels.md)·
[MVCC](11-mvcc-postgresql.md)). **(가산점 포인트)** PG는 **DDL도 트랜잭션
안**(`ALTER TABLE`을 롤백 가능, `CREATE INDEX CONCURRENTLY` 등은 예외)이고
`PREPARE TRANSACTION`으로 **2단계 커밋**을 내장한다.

## 3. 실무 사례 — 일관성은 누가 지키나: DB와 애플리케이션의 공동 책임

C가 네 글자 중 유일하게 "DB가 알아서" 다 못 해주는 글자다. 규칙에는
두 부류가 있기 때문이다.

**① DB가 선언적으로 강제할 수 있는 규칙** — 스키마에 박아둘 수 있다:

```sql
-- ❌ before: "잔액은 음수가 될 수 없다"를 애플리케이션 코드만 믿는다
CREATE TABLE account (
    id      varchar(20) PRIMARY KEY,
    balance bigint NOT NULL
);
-- 코드에서 if (balance >= amount) 검사를 하더라도 —
-- 검사와 차감 사이에 다른 요청이 끼어들면(동시성) 음수 잔액이 뚫린다.
-- 검사를 빼먹은 신규 API 하나만 있어도 뚫린다.

-- ✅ after: 최후의 방어선을 DB 제약으로 선언
CREATE TABLE account (
    id      varchar(20) PRIMARY KEY,
    balance bigint NOT NULL,
    CONSTRAINT chk_balance_non_negative CHECK (balance >= 0)
);
-- 어떤 경로로 UPDATE가 들어와도, 잔액을 음수로 만드는 트랜잭션은
-- DB가 ERROR 23514 (check_violation)를 내고 거부 → 롤백
-- (A가 C를 지키는 도구로 동원된다).
```

NOT NULL, UNIQUE, FK, CHECK(PG는 "예약 시간대가 겹칠 수 없다" 같은 행 간
배타 조건용 **`EXCLUDE`**까지)가 이 부류다. **어떤 코드 경로로 들어와도
우회 불가능**하다는 것이 애플리케이션 검증에 없는 강점이다.

**② DB에 선언할 수 없는 비즈니스 규칙** — "이체 총합은 불변이어야
한다", "VIP 등급은 연 구매액 천만원 이상만 가능하다" 같은 규칙은 CHECK
한 줄로 표현이 안 된다.

**왜 안 되나 — `CHECK`는 자기 행 안에서 판정 가능한 것만 검사한다.**

```sql
-- ✅ 가능: 이 행의 balance만 보면 참/거짓이 결정된다
CHECK (balance >= 0)

-- ❌ 불가능: 판정하려면 테이블 전체를 봐야 한다
ALTER TABLE account ADD CONSTRAINT chk_total
    CHECK ((SELECT sum(balance) FROM account) = 10000000);
--   → ERROR: cannot use subquery in check constraint
--   여러 행에 걸친 규칙은 표현 자체가 안 된다.
```

SQL 표준에는 이 자리를 위한 `CREATE ASSERTION`(테이블 전체·여러 테이블에
걸친 제약)이 정의돼 있지만 **PostgreSQL을 포함해 실제 DB가 거의 구현하지
않았다.** 모든 쓰기 때마다 테이블 전체를 재검증해야 해서 비용이 감당이
안 되기 때문이다. 그래서 총합 불변 같은 규칙은 **애플리케이션 코드가
규칙의 구현체**가 된다.

```java
// 총합 불변은 여기서 지켜진다. DB는 이 규칙의 존재조차 모른다.
@Transactional
public void transfer(String from, String to, long amount) {
    accountRepo.withdraw(from, amount);   // 같은 amount를
    accountRepo.deposit(to, amount);      // 양쪽에 쓴다 ← 이게 규칙의 구현체
}
```

앞서 1-2절에서 본 계좌이체의 규칙 두 개가 정확히 이 선을 따라 갈린다 —
**"잔액 ≥ 0"은 ①(DB가 지켜준다), "총합 불변"은 ②(애플리케이션이
지켜야 한다).** 같은 "일관성"이라는 말 안에 성격이 다른 둘이 섞여 있는
셈이고, 이 구분을 짚는 것이 이 절의 핵심이다.

②는 **애플리케이션이 트랜잭션 안에서 지켜야** 하고, DB는 그 코드가 절반만
실행되지 않게(A), 동시 실행에 찢기지 않게(I) **도구를 제공**할 뿐이다.

그래서 정확한 문장은 이렇다 — **"DB는 자신이 아는 제약을 강제하고
A·I·D라는 도구를 제공한다. 그 도구 위에서 비즈니스 불변식까지 지켜
'일관된 상태 → 일관된 상태'로 옮기는 최종 책임은 애플리케이션과 DB의
공동 책임이다."** (가산점 포인트) 일관성을 이렇게 "공동 책임"으로
설명하면, ACID를 DB 기능 목록이 아니라 시스템 설계의 언어로 쓰고 있다는
신호가 된다.

**(가산점 포인트)** 네 글자가 이후 어떤 질문의 발판인지 지도를 갖고
있으면 꼬리질문이 두렵지 않다 — **I** → 격리 수준과 MVCC 스냅샷(중급),
**D** → WAL·체크포인트·`synchronous_commit`, **A** → `pg_xact`와
VACUUM, 그리고 **긴 트랜잭션이 왜 위험한가**(중급,
[16번 문서](16-long-transaction-harm-and-shortening.md))로 이어진다.

## 4. 꼬리질문 대비 포인트

### "커밋 완료 응답 직후 전원이 나갔습니다. 데이터는 남아 있어야 하나요? 테이블 파일엔 아직 안 쓰였을 수도 있는데 무슨 수로 보장하죠?"

남아 있어야 한다 — 그게 D(지속성)의 정의다. "커밋 성공"이라는 응답은
**"이제 무슨 일이 있어도 이 결과는 보존된다"는 약속**이기 때문이다.
보장 수단은 WAL: 커밋 시점에 커밋 레코드를 **WAL 파일 끝에 순차
append하고 fsync로 디스크까지 내려보낸 뒤에야** 성공을 응답한다
(`synchronous_commit = on`). 테이블 파일(데이터 페이지)에는 아직 반영
전이어도 상관없다 — 재시작한 DB가 마지막 체크포인트부터 WAL을 읽어
**커밋된 변경을 다시 적용(REDO)** 하기 때문이다. 요점은 "메모리 어딘가에
갖고 있다"가 아니라 **"응답 전에 디스크의 WAL에 내려갔다"**는 것.

### "로그 쓰기도 어차피 디스크 쓰기잖아요. 그런데 왜 테이블 파일을 바로 고치는 것보다 빠르다는 거죠?"

맞다, **로그 쓰기도 똑같은 디스크 I/O다** — 이걸 인정하는 데서 답이
시작된다. 차이는 접근 패턴이다. 트랜잭션이 건드린 행들은 디스크
여기저기 흩어진 8KB 페이지에 있어서 직접 반영은 **랜덤 쓰기**이고, WAL은
파일 끝에 **순차 append**라 같은 양을 써도 훨씬 싸다. 그래서 커밋
순간엔 싼 순차 쓰기만 하고, 비싼 랜덤 쓰기는 `shared_buffers`의 더티
페이지로 모아뒀다가 체크포인트 때 배치로 처리한다. "로그는 I/O가
아니라서 빠르다"라고 답하면 즉시 감점 — 로그가 디스크에 안 내려가면 D
자체가 성립하지 않는다.

### "일관성이 깨진 상태란 계좌이체에서 구체적으로 어떤 상태인가요? DB가 혼자 다 지켜줄 수 있나요?"

구체적으로 두 가지 — ① 이체 후 **두 계좌 총합에서 이체액만큼 증발**한
상태(차감만 반영), ② **잔액이 음수**가 된 상태(제약 뚫림). "같은 쿼리
같은 결과"는 일관성의 정의가 아니다. 그리고 DB 혼자는 못 지킨다 —
NOT NULL·UNIQUE·FK·CHECK(PG는 `EXCLUDE`까지)처럼 **선언 가능한 제약은
DB가 강제**하지만, "총합 불변" 같은 비즈니스 불변식은 CHECK에 서브쿼리를
쓸 수 없어 선언할 방법이 없고 **애플리케이션이 트랜잭션(A·I라는 도구)
안에서 지켜야** 한다. "DB 제약 + 애플리케이션의 공동 책임"이라는
문장까지 나와야 완결된 답이다.

### "PostgreSQL에는 undo 로그가 없다던데, 그럼 롤백과 크래시 후 미커밋 정리는 어떻게 하나요?"

**되돌릴 것이 없도록 설계돼 있어서다.** PG는 행을 제자리에서 고치지 않고
새 튜플 버전을 덧붙이며 옛 버전은 같은 페이지에 그대로 둔다. 그래서
롤백은 `pg_xact`에 "취소" 표시 하나를 찍는 O(1) 작업이고, 이후 읽기가
`xmin`/`xmax`와 그 표를 대조해 취소된 버전을 없는 셈 친다. 크래시 후도
같다 — WAL을 REDO하면 커밋 레코드가 없는 트랜잭션의 튜플은 그냥 안 보이고
**UNDO 단계 자체가 없다.** 체크포인트가 미커밋 변경을 먼저 디스크에
내렸더라도 그건 "덮어쓴 옛 값"이 아니라 "미커밋 ID의 새 버전"이라 되돌릴
필요가 없다. 대가는 나중에 VACUUM이 낸다 — **"롤백이 싼 대신 청소가
비싸다"** 가 PG의 A를 한 문장으로 요약한 것이다.

### "긴 트랜잭션이 왜 위험한가요? ACID의 언어로 설명해보세요." (시니어 변별 포인트)

각 글자의 메커니즘이 **전부 "트랜잭션이 살아 있는 동안" 자원을 붙들고
있기** 때문이다. ① **A/MVCC의 외상이 쌓인다** — PG는 롤백용 undo를 쌓지는
않지만, 이 트랜잭션의 스냅샷이 살아 있는 한(`pg_stat_activity.backend_xmin`)
그 뒤에 죽은 튜플은 **어느 테이블에서도** VACUUM이 회수하지 못한다 →
테이블·인덱스 bloat, 극단적으로는 트랜잭션 ID(32비트) freeze가 밀려
wraparound 방지 VACUUM이 강제로 돈다. ② **I의 락·스냅샷이 오래 유지된다**
— 행 락은 커밋까지 안 풀리니 경합이 번지고, DDL이 오면 ACCESS EXCLUSIVE
대기열 뒤로 **모든 SELECT까지** 줄을 선다. ③ 커넥션까지 오래 점유하면(PG는
커넥션 = 프로세스라 더 비싸다) **락 경합 → 대기 → 트랜잭션 장기화 →
커넥션 풀 고갈** 사슬로 번진다(`state = 'idle in transaction'`이 단골).
그래서 실무 수칙이 "트랜잭션은 짧게, 외부 API 호출은 트랜잭션 밖으로,
`idle_in_transaction_session_timeout`"이다. ACID의 네 글자를 보장 목록이
아니라 **비용의 원천**으로도 읽을 수 있는지가 시니어 변별점이다.

### "MySQL로 물어보면 답이 달라지는 부분은?" (경험 대조)

네 지점이다. ① **A와 롱 트랜잭션의 대가** — InnoDB는 제자리 갱신 + undo
로그라 롤백이 갱신량에 비례하고 대가는 undo 누적(history list length),
PG는 덧붙이기 + `pg_xact` 표시라 롤백은 O(1)이고 대가는 VACUUM 방해로
인한 bloat·wraparound다. ② **크래시 복구** — InnoDB는 redo 재적용 후 미커밋분 undo의 2단계, PG는
REDO 한 단계. ③ **로그 개수** — InnoDB는 redo 로그와 복제·PITR용 binlog가
따로라 둘 사이 2PC가 필요하고, PG는 WAL 하나로 복구·복제·PITR·CDC를 다
한다. ④ **DDL과 기본 격리 수준** — MySQL은 DDL이 암묵 커밋으로 트랜잭션을
끊고 기본이 REPEATABLE READ, PG는 DDL도 롤백 가능하고 기본이 READ
COMMITTED. 이 넷이 나오면 "저장 구조 차이에서 도출했다"로 들린다.

## 한 줄 요약

**ACID는 글자마다 "한 줄 정의 + 메커니즘"으로 말한다 — A: 전부 반영
or 전부 취소, 실패에 대한 보장(PG는 undo 로그 없이 MVCC 버전 + `pg_xact`
취소 표시, 청소는 VACUUM) / C: 트랜잭션
전후 불변식 유지 — 총합 불변·잔액 ≥ 0, DB 제약과 애플리케이션의 공동
책임 / I: 동시 트랜잭션이 중간 상태를 못 본다, 동시성에 대한 보장(MVCC
스냅샷 + 행 락) / D: 커밋 응답 후엔 전원이 나가도 보존(WAL + fsync,
크래시 복구는 REDO뿐). "끼어들 수 없다"는 격리성의 언어이고, 로그도
똑같은 디스크 I/O지만 순차 append라 싸기에 커밋 순간엔 WAL만 쓰고 비싼
랜덤 쓰기는 체크포인트로 미뤄 모아서 한다.**
