# 운영 DB의 FK 제약 논쟁 — "안 건다"가 관행이 된 이유와, 포기한 방어선을 무엇으로 메우는가

> 핵심 관전 포인트: **FK는 "가리키는 곳이 반드시 있다"를 DB가 어떤 경로로
> 들어와도 강제하는 최후 방어선이다. 그 대가로 DB는 자식 INSERT마다 부모
> 행에 공유(S) 락을 잡아 커밋까지 쥐고, 부모 DELETE마다 자식 테이블을
> 검사한다. 대규모 팀이 FK를 빼는 이유는 이 검사가 만드는 사슬 —
> 핫 부모 행의 S 락 ↔ X 락 경합과 데드락, 대량 적재·아카이빙의 순서 제약,
> gh-ost가 FK 테이블을 아예 못 다루는 것, 샤딩·서비스 분리에서 FK가 성립
> 불가한 것, CASCADE의 보이지 않는 폭발 — 이고, 솔직히는 "대규모 회사의
> 관행이 그대로 전파된" 몫도 크다. 그런데 빼는 순간 잃는 것도 정면으로
> 말해야 한다: 어떤 경로(콘솔·배치·신규 코드)로 와도 뚫리지 않는 유일한
> 검사, 고아 행이 조용히 쌓이지 않는다는 보장, 스키마 자체가 문서인 상태,
> 그리고 MySQL이 FK와 함께 자동으로 만들어주던 인덱스. 내 견해는 "기본값은
> 건다 — 빼는 것은 조건(쓰기 TPS·핫 부모·마이그레이션 빈도·분산 계획·데이터
> 민감도·팀 규율)이 확인된 예외이고, 빼는 순간 앱 레벨 존재 검증 + 소프트
> 삭제 + FK 컬럼 인덱스 강제 + 고아 행 탐지 배치와 알람 + 소프트 참조
> 규약·스키마 문서화 (+ 테스트 환경에서만 FK 켜기)가 한 세트로 따라와야
> 한다"이다. 대체 체계를 운영할 준비 없이 FK만 빼는 것은 결정이 아니라
> 방치다.**

## 0. 질문 + 의도

**질문**: "운영 DB에서 FK 제약을 걸지 않는 팀이 많은 이유는 무엇이고,
본인의 견해는? FK 없이 정합성은 어떻게 지키나요?"

**출제 의도**: 대용량 환경에서 FK가 만드는 비용(락 전파, 마이그레이션
제약, 샤딩 불가)과 FK를 포기했을 때 잃는 최후 방어선을 **양쪽 다** 말할
수 있는지 — 교과서 규범("참조 무결성은 DB가 지킨다")과 실무 관행("운영
DB엔 FK 안 건다")이 충돌하는 지점에서 **"우리 서비스의 조건"으로 결론을
내는 사고**를 본다. 앱 레벨 검증 + 배치 정합성 점검으로 대체하는 체계까지
말하면 상급이다.

즉 이 문항은 "FK 찬성/반대"를 묻는 것이 아니다. 채점 지점은 세 층이다 —
⑴ 비용을 "느려진다"가 아니라 **메커니즘으로** 말하는가 ⑵ 잃는 것을
**회피하지 않고 정면으로** 말한 뒤 조건으로 결론 내는가 ⑶ 포기한 방어선을
**사람의 주의력이 아닌 체계로** 대체하는가.

> 이 문서는 후보자의 횡단 약점 4가지를 겨냥해 구성했다 — ① FK의 비용을
> **이름 붙은 메커니즘 사슬**로 말하기(2장) ② 잃는 것까지 **양면으로
> 조립**하고 "우리 서비스의 조건"으로 결론 내기(3장·5장) ③ 포기한
> 방어선을 **코드·잡·규약으로 고정**하기(4장) ④ "안 거는 이유 N가지 /
> 잃는 것 N가지 / 대체 체계 N가지"를 **목록으로 인출**하기(각 장 첫머리).

> 연결 문서: FK가 걸린 테이블에서 gh-ost가 왜 빠지는지는
> [무중단 스키마 변경](14-online-ddl-zero-downtime-schema-change.md) §3,
> "정합성이 DB 제약이 아니라 앱 관례에 살면 왜 새는지"는
> [정규화 vs 반정규화](04-normalization-vs-denormalization.md) §2-3,
> soft delete가 FK를 무의미하게 만드는 지점은
> [Soft delete와 유니크·연관관계](../03-jpa-orm/26-soft-delete-unique-and-associations.md) §6-3,
> JPA cascade와 DB `ON DELETE CASCADE`의 차이는
> [CascadeType.REMOVE와 orphanRemoval](../03-jpa-orm/24-cascade-remove-vs-orphan-removal.md) §7,
> "참조는 둘, FK는 하나"의 매핑 기초는
> [연관관계의 주인과 mappedBy](../03-jpa-orm/06-association-owner-and-mappedby.md)에 있다.

## 1. FK가 하는 일 — 무엇을 지키고, 그 대가로 DB가 매번 무엇을 하는가

### 1-1. 참조 무결성 = "가리키는 곳이 반드시 있다"

외래 키(FK, foreign key) 제약은 한 문장이다 — **자식 행의 참조 컬럼 값은
부모 테이블에 반드시 존재하는 키여야 한다.** `comments.post_id = 42`라면
`posts.id = 42`가 있어야 하고, 그 행을 지우려면 먼저 댓글을 처리해야
한다. 이 성질을 참조 무결성(referential integrity)이라 부르고, 이것이
깨진 자식 행 — 부모 없는 자식 — 을 **고아 행(orphan row)** 이라 한다.

비유하면 FK는 건물 출입구의 경비원이다. 어떤 문으로 들어오든(앱 코드,
배치, 운영자의 콘솔 `DELETE`, 마이그레이션 스크립트) 신분증(부모 존재)을
확인한다. 경비원을 없애면 출입은 빨라지고 이삿짐(대량 적재)도 편해지지만,
그때부터 "누가 들어왔는지"는 각 부서(코드 경로)가 알아서 확인해야 한다.

### 1-2. 검사가 일어나는 네 순간 — 그리고 각 순간에 DB가 잡는 것

FK를 "느리다"고 뭉뚱그리지 않으려면, **언제 검사가 일어나고 그때 무엇을
잡는지**부터 고정해야 한다. InnoDB 기준이다.

| 순간 | DB가 하는 일 | 잡는 락 |
|---|---|---|
| ① 자식 INSERT | 부모 PK(또는 유니크 키)에서 참조 값을 찾는다 | **부모 행에 공유(S) 레코드 락** — 커밋까지 유지 |
| ② 자식의 FK 컬럼 UPDATE | 새 부모 값을 ①처럼 찾는다 | 새 부모 행에 S 락 |
| ③ 부모 DELETE | 자식 테이블의 FK 인덱스에서 참조하는 자식이 있는지 훑는다 | 훑은 **자식 레코드에 S 락** (+ RC에서도 갭 락) |
| ④ 부모 PK UPDATE | ③과 같다 (실무에선 드묾) | ③과 같다 |

두 가지가 중요하다.

- **InnoDB는 FK 검사를 즉시 한다** — 트랜잭션 커밋 시점으로 미루지
  않는다. (PostgreSQL은 `DEFERRABLE INITIALLY DEFERRED`로 커밋까지 미룰
  수 있다 — 상호 참조 행을 한 트랜잭션에서 넣을 때 쓴다.)
- **검사 때 잡은 S 락은 트랜잭션이 끝날 때까지 유지된다.** "검사"는
  한순간이지만 "락"은 트랜잭션 수명만큼 산다. 2-1의 사슬은 여기서
  출발한다. 그리고 [갭 락 문서](12-gap-lock-next-key-lock-deadlock.md) §2-2에
  적었듯 **READ COMMITTED로 낮춰도 FK 검사의 갭 락은 남는다.**

검사 자체의 CPU 비용은 작다 — 부모 PK 한 번 찾기(클러스터드 인덱스 탐색
한 번)다. **FK 비용의 실체는 "찾기"가 아니라 "찾은 뒤 쥐고 있는 락"과
운영상의 제약**이다. 이 구분을 못 하면 "FK는 느려서 뺐다"는 말이 근거
없는 관행 반복으로 들린다.

## 2. FK를 걸지 않는 이유 7가지 — 각각을 메커니즘 사슬로

목록부터 인출한다. 면접에서는 이 순서로 말한다.

> **FK를 안 거는 이유 7가지**
> ① 락 전파 — 자식 INSERT의 S 락이 핫 부모의 X 락과 경합·데드락
> ② 부모 DELETE의 자식 검사 비용 — 인덱스가 없으면 풀스캔
> ③ 대량 적재·마이그레이션·아카이빙의 순서 제약
> ④ online DDL 도구의 제약 — gh-ost는 FK 테이블 불가, `ADD FOREIGN KEY`는 COPY
> ⑤ 샤딩·파티셔닝·서비스 분리에서 FK 성립 불가
> ⑥ CASCADE의 예측 불가 폭발
> ⑦ (솔직한 이유) 관행의 전파 — 성능은 사후 정당화인 경우가 많다

### 2-1. ① 락 전파 — 자식 INSERT → 부모 행 S 락 → 핫 부모의 X 락과 경합 → 데드락

가장 중요한 사슬이고, [정규화 문서](04-normalization-vs-denormalization.md)의
`posts.comment_count` 예제와 정확히 맞물린다.

> **⑴ 자식 INSERT가 부모 행에 S 락**: `INSERT INTO comments (post_id=42)`는
> FK 검사로 `posts.id=42` 행에 공유 락을 잡고 커밋까지 쥔다.
>
> **⑵ 부모가 핫하면 X 락과 경합**: 같은 트랜잭션에서, 혹은 다른 트랜잭션이
> `UPDATE posts SET comment_count = comment_count + 1 WHERE id = 42`를
> 치면 배타(X) 락이 필요하다. X는 S와 호환되지 않으므로 **다른 트랜잭션이
> 쥔 S 락이 풀릴 때까지 대기**한다.
>
> **⑶ 대기의 교차 = 데드락**: 두 트랜잭션이 각각 "INSERT 자식 → UPDATE
> 부모" 순서면 서로의 S 락을 기다리며 교착한다.
>
> **⑷ 대기 전파**: 데드락이 아니어도, 인기 글에 초당 수백 댓글이 붙으면
> 부모 행 하나의 락 큐에 모든 댓글 트랜잭션이 걸린다 → 트랜잭션 장기화 →
> 커넥션 풀 고갈 → 무관한 API까지 전파 — 정규화 문서 §3의 사슬이 **FK가
> 있으면 한 단계 더 일찍, S 락 단계에서** 시작된다.

시간순으로 보면 이렇다.

```sql
-- ❌ before: FK 있음 + "자식 INSERT → 부모 UPDATE" 순서 (흔한 코드 순서)
-- T1                                        -- T2
BEGIN;                                       BEGIN;
INSERT INTO comments (post_id, body)         INSERT INTO comments (post_id, body)
VALUES (42, 'a');                            VALUES (42, 'b');
-- FK 검사 → posts.id=42 에 S 락 (T1)        -- FK 검사 → posts.id=42 에 S 락 (T2)
--                                           -- S ↔ S 는 호환 → 둘 다 통과
UPDATE posts SET comment_count = comment_count + 1
WHERE id = 42;
-- X 락 필요 → T2 의 S 락 때문에 대기          UPDATE posts SET comment_count = comment_count + 1
                                             WHERE id = 42;
                                             -- X 락 필요 → T1 의 S 락 때문에 대기
-- ⇒ 데드락. InnoDB 가 한쪽을 롤백한다.
-- ERROR 1213 (40001): Deadlock found when trying to get lock
```

```sql
-- ✅ after-1: FK 유지 + 순서 반전 — 부모 X 락을 먼저 잡는다
BEGIN;
UPDATE posts SET comment_count = comment_count + 1 WHERE id = 42;  -- X 락 선점
INSERT INTO comments (post_id, body) VALUES (42, 'a');             -- 자기 X 위의 FK 검사는 통과
COMMIT;
-- 데드락은 사라진다. 대신 X 락을 트랜잭션 처음부터 쥐므로 락 보유 시간이
-- 길어진다 — 정규화 문서가 권한 "UPDATE 를 커밋 직전에"와 정면충돌한다.
-- FK 가 있는 한 "락 짧게"와 "데드락 회피" 중 하나를 고르게 된다.

-- ✅ after-2: FK 제거 — S 락 자체가 안 생기므로 순서 제약이 사라진다
--   (대신 3장에서 잃는 것을 4장의 체계로 메워야 한다)
```

이 예제가 이 문서에서 가장 자주 써먹을 무기다. "FK는 락 때문에 뺐다"를
**"자식 INSERT의 S 락이 핫 부모 UPDATE의 X 락과 교차해 데드락이 나고,
회피하려면 X를 먼저 잡아 락 보유 시간을 늘려야 하는 딜레마가 생긴다"**
로 바꿔 말하는 순간 평가가 달라진다.

### 2-2. ② 부모 DELETE의 자식 검사 — 인덱스가 없으면 자식 테이블 풀스캔

부모 행을 지우면 DB는 "이 부모를 가리키는 자식이 있나"를 자식 테이블에서
찾아야 한다. 자식의 FK 컬럼에 인덱스가 있으면 탐색 한 번, 없으면 **자식
테이블 전체 스캔**이다. 자식이 수억 건이면 부모 한 행 삭제가 수십 초짜리
풀스캔이 되고, 그동안 훑은 레코드에 S 락이 걸린다.

여기서 엔진이 갈린다.

- **MySQL(InnoDB)**: FK를 만들 때 자식 FK 컬럼에 **인덱스가 없으면
  자동으로 만든다.** 그래서 ②의 풀스캔은 MySQL에서는 거의 겪지 않는다 —
  대신 이 자동 생성이 3-4절의 함정을 만든다.
- **PostgreSQL**: 자식 FK 컬럼에 인덱스를 **자동으로 만들지 않는다.**
  `ON DELETE`가 걸린 부모를 지웠는데 자식 시퀀셜 스캔이 나가는 것이
  PostgreSQL FK 성능 문제의 단골이다.

즉 ②는 "FK를 빼는 이유"라기보다 "FK 컬럼 인덱스를 빠뜨리면 생기는
문제"에 가깝다. 이 구분을 아는 것이 변별점이다.

### 2-3. ③ 대량 적재·마이그레이션·아카이빙의 순서 제약

FK가 있으면 데이터 이동에 **순서**가 생긴다.

- **적재**: 부모 → 자식 순서로만 넣을 수 있다. 수억 건을 병렬로 붓는
  적재 파이프라인에서 이 순서는 병렬성을 죽인다. 그래서 흔히
  `SET foreign_key_checks = 0`으로 끄고 붓는데 — **다시 1로 켜도 이미
  들어간 데이터는 검사하지 않는다.** 즉 "적재 중엔 어차피 FK를 끈다"는
  현실이, "그럼 평소에도 없는 것과 무엇이 다른가"라는 질문으로 이어진다.
- **아카이빙**: 오래된 부모 행을 아카이브 테이블로 옮기려면 자식을 먼저
  옮기거나 지워야 한다. 자식이 여러 테이블에 흩어져 있으면 아카이빙
  잡이 FK 그래프 전체를 알아야 한다.
- **테이블 교체·복구**: 백업에서 테이블 하나만 되살리거나, 스왑 방식으로
  교체하는 작업에서 FK가 다른 테이블을 물고 있으면 순서·잠금 창이 생긴다.

### 2-4. ④ online DDL 도구의 제약 — gh-ost는 FK 테이블을 아예 못 다룬다

[무중단 스키마 변경 문서](14-online-ddl-zero-downtime-schema-change.md) §3에서
정리한 대로:

- **gh-ost**: 대상 테이블이 FK의 부모든 자식이든 **지원하지 않는다**
  (하드 리밋). FK가 있는 스키마에서는 선택지에서 빠진다.
- **pt-online-schema-change**: `--alter-foreign-keys-method`로
  `rebuild_constraints`(자식 테이블들에 ALTER — 자식이 크면 또 하나의
  대공사) 또는 `drop_swap`(테이블이 잠깐 존재하지 않는 창)을 골라야 한다.
- **네이티브 online DDL**: `ADD FOREIGN KEY`는 `foreign_key_checks=1`이면
  **COPY 알고리즘**(쓰기 차단, 디스크 2배)이다. INPLACE로 하려면 검사를
  끄고 걸어야 하는데, 그러면 기존 데이터의 위반을 검사하지 않는다.

즉 "수억 건 테이블을 자주 바꾸는 팀"에게 FK는 **도구 선택지를 절반
이하로 줄이는 제약**이다. 이것이 대규모 팀이 FK를 빼는 가장 실질적인
이유 중 하나이고, "성능"보다 훨씬 설득력 있는 근거다.

### 2-5. ⑤ 샤딩·파티셔닝·서비스 분리 — FK가 성립 불가한 지형

FK는 **같은 DB 인스턴스 안의 두 테이블** 사이에서만 성립한다.

- **샤딩**: `comments`가 `user_id`로 샤딩되고 `posts`가 `post_id`로
  샤딩되면 부모와 자식이 다른 서버에 있다. 검사할 대상이 물리적으로
  다른 곳에 있으니 FK 자체가 정의될 수 없다.
  ([샤딩 문서](24-sharding-timing-shard-key-and-cross-shard.md) — 크로스
  샤드 조인이 사라지는 것과 같은 뿌리다.) 샤딩 미들웨어·분산 DB 계층
  중 상당수가 FK를 지원하지 않거나 뒤늦게 제한적으로 지원하는 이유다.
- **파티셔닝**: MySQL의 파티션 테이블은 FK를 지원하지 않는다.
  파티셔닝을 도입하는 순간 그 테이블의 FK는 걷어내야 한다.
- **서비스 분리(MSA)**: 주문 서비스의 `orders.member_id`가 회원 서비스의
  `members.id`를 가리키지만 DB가 다르다. 여기서 참조는 **DB가 아니라
  계약(API·이벤트)으로만 지켜진다** — 4-5절의 소프트 참조 규약이 유일한
  선택지다.

"언젠가 샤딩·분리할 것"이라면 FK에 기대 짠 코드(삭제 순서를 FK에 맡기기,
cascade)는 그때 전부 다시 짜야 한다. 그래서 **처음부터 FK 없는 규율로
가는 팀**이 생긴다.

### 2-6. ⑥ CASCADE의 예측 불가 폭발

`ON DELETE CASCADE`는 부모 한 행 DELETE가 자식 → 손자 → 증손자로 번진다.

- **범위가 코드에 안 보인다.** `DELETE FROM posts WHERE id = 42` 한 줄이
  댓글·첨부·알림·통계 행 수만 건을 지우는데, 코드 리뷰어는 그 한 줄만
  본다. [cascade 문서](../03-jpa-orm/24-cascade-remove-vs-orphan-removal.md)
  §7에서 "JPA cascade는 코드에 파급이 보이고, DB cascade는 안 보인다"고
  정리한 그 지점이다.
- **MySQL에서 캐스케이드된 삭제는 트리거를 발동시키지 않는다.** 감사
  로그 트리거가 있어도 연쇄 삭제분은 기록되지 않는다.
- **중첩 깊이 제한**이 있어 깊은 그래프에서는 에러로 실패한다.
- **락과 시간이 예측 불가**다. 부모 한 행 삭제가 자식 수십만 건의 X
  락으로 확장되고, 그 트랜잭션은 그만큼 길어진다 — 장기 트랜잭션의 해악
  ([long-transaction 문서](16-long-transaction-harm-and-shortening.md))이 한
  문장에서 시작된다.

그래서 FK를 쓰더라도 `CASCADE`는 안 쓰고 `RESTRICT`만 쓰는 팀이 많고,
"어차피 RESTRICT만 쓸 거면 앱에서 막는 것과 무엇이 다른가"가 FK 제거의
또 다른 논거가 된다.

### 2-7. ⑦ 솔직한 이유 — 관행의 전파

위 여섯이 다 해당되는 팀은 사실 많지 않다. 그런데 "운영 DB엔 FK 안
건다"는 규칙은 훨씬 넓게 퍼져 있다. 이유는 **대규모 서비스 회사의 DBA
컨벤션이 "정답"으로 전파**되었기 때문이다 — 그 회사들은 ①~⑥을 실제로
겪었지만, 컨벤션만 가져온 팀은 겪지 않은 문제를 피하려고 방어선을
버린다. 이걸 인정하고 말하는 것이 오히려 신뢰를 준다: **"성능 때문에
뺐다"는 대개 사후 정당화이고, 실제 결정 요인은 운영 유연성(③④)과 분산
계획(⑤)이다.** 우리 팀이 그 조건에 해당하는지가 5장의 판단 기준이다.

## 3. FK를 포기하면 잃는 것 4가지 — 정면으로

여기가 트레이드오프의 반대편이고, 후보자가 가장 자주 건너뛰는 면이다.
2장만 말하고 끝내면 "관행을 외운 사람", 3장까지 말해야 "결정을 내릴 수
있는 사람"이다.

> **FK를 빼면 잃는 것 4가지**
> ① 최후 방어선 — 어떤 경로로 와도 뚫리지 않는 유일한 검사
> ② 고아 행이 쌓이지 않는다는 보장 — 증상은 몇 달 뒤에 엉뚱한 곳에서
> ③ 스키마의 문서 역할 — ERD·관계 추론·신규 입사자의 지도
> ④ (MySQL) FK가 자동으로 만들어주던 인덱스 — 가장 흔한 함정

### 3-1. ① 최후 방어선 — 불변식이 DB 제약에서 앱 관례로 내려온다

[정규화 문서](04-normalization-vs-denormalization.md) §2-3의 문장을 그대로
가져온다 — **"FK나 UNIQUE 제약은 DB가 지키므로 어떤 코드 경로로 들어와도
뚫리지 않는다. 반면 앱의 약속은 약속을 모르는 경로가 하나만 생겨도
뚫린다."** FK를 빼는 것은 참조 무결성을 정확히 그 "앱의 약속" 등급으로
강등시키는 일이다.

뚫는 경로는 늘 같은 세 종류다.

- **새 코드 경로**: 신입이 만든 관리자 일괄 삭제 API가 자식 처리를
  빼먹는다. 컴파일도 테스트도 통과한다.
- **앱을 거치지 않는 경로**: 장애 대응 중 콘솔에서 `DELETE FROM posts
  WHERE ...`. 데이터 보정 스크립트. ETL 역적재.
- **경로 비대칭**: 생성 경로는 부모를 확인하는데, 나중에 추가된 "계정
  병합" 경로는 참조를 옮기는 걸 잊는다.

FK가 있으면 이 셋이 전부 **에러로 즉시 드러난다.** 없으면 전부 **조용히
성공**한다. 이 차이가 최후 방어선의 뜻이다.

### 3-2. ② 고아 행 — 조용히 쌓이고, 증상은 엉뚱한 곳에서 터진다

고아 행의 무서움은 생길 때가 아니라 **발견될 때**다.

- 부모를 조인해 화면을 그리는 코드가 `null`을 만나 NPE — 그런데 원인
  행은 석 달 전 배치가 만들었다.
- INNER JOIN 통계에서 고아 행이 빠져 매출 집계가 조용히 작다. 아무도
  모른다.
- 개인정보 삭제 요청으로 회원을 지웠는데, 그 회원의 주소가 담긴 자식
  행이 남아 있다 — 이건 버그가 아니라 컴플라이언스 사고다.
- 고아를 뒤늦게 발견해 지우려는데 "이 행이 정말 고아인지, 부모가 다른
  경로로 옮겨진 건지"를 판별할 근거가 없다.

FK는 이 모든 것을 **생성 시점에 0건으로** 유지한다. 대체 체계(4-4절)는
"발견 시점"을 몇 시간 단위로 당기는 것이지 0건을 보장하지 못한다 —
이 차이를 알고 받아들이는 것이 결정이다.

### 3-3. ③ 스키마의 문서 역할

FK가 있는 스키마는 그 자체로 ERD다. DB 도구가 관계를 그려주고, 신규
입사자가 `SHOW CREATE TABLE`만으로 "이 테이블은 누구를 가리키나"를 안다.
FK가 없으면 `member_id`가 `members.id`인지 `legacy_members.member_no`인지
**컬럼 이름과 부족의 기억**으로만 남는다. 테이블이 200개를 넘으면 이
지식은 반드시 유실되고, 4-5절의 문서화 규약이 그 자리를 메워야 한다.

### 3-4. ④ 자동 인덱스의 소멸 — MySQL에서 가장 흔한 함정

2-2절에서 말한 대로 MySQL은 FK를 걸면 자식 FK 컬럼에 인덱스를 자동으로
만든다. FK를 안 거는 팀은 **이 인덱스를 손으로 만들어야 한다는 사실을
자주 잊는다.** 결과는 —

```sql
-- FK 없이 만든 자식 테이블. member_id 에 인덱스가 없다.
CREATE TABLE orders (
    id         BIGINT PRIMARY KEY,
    member_id  BIGINT NOT NULL,   -- 논리적 FK. 그런데 인덱스는? 없다.
    amount     DECIMAL(19, 2)
);

-- 가장 흔한 조회가 풀스캔이 된다
SELECT * FROM orders WHERE member_id = ?;      -- type: ALL
-- 회원 삭제 전 "주문 있나" 검사도 풀스캔
SELECT 1 FROM orders WHERE member_id = ? LIMIT 1;
```

"FK를 뺐더니 느려졌다"의 상당수가 FK가 아니라 **함께 사라진 인덱스**
때문이다. 4-3절에서 이걸 사람 기억이 아니라 린트로 막는다.

## 4. FK 없이 정합성을 지키는 체계 7가지 — 안전망을 코드·잡·규약으로 고정

FK를 빼기로 했다면 아래 일곱은 **선택이 아니라 세트**다. 하나라도 빠지면
3장의 손실을 그대로 떠안는다.

> **대체 체계 7가지**
> ① 앱 레벨 존재 검증 — 그리고 레이스 조건의 보정
> ② 삭제는 소프트 삭제/아카이브로 — 부모가 안 사라지면 고아가 안 생긴다
> ③ FK 컬럼 인덱스 강제 — 마이그레이션 린트로
> ④ 고아 행 탐지 배치 + 알람 — 발견 지연을 시간 단위로
> ⑤ 소프트 참조 규약 + 스키마 문서화 — 이름·COMMENT·ERD 도구
> ⑥ 테스트/스테이징에서만 FK 켜기 — 버그를 운영 전에 드러내는 선택지
> ⑦ JPA에서 매핑과 물리 제약을 분리 — `NO_CONSTRAINT`와 `ddl-auto`

### 4-1. ① 앱 레벨 존재 검증 — 도메인 서비스가 경비원이 된다

```java
// ❌ before: FK 도 없고 검증도 없다 — 존재하지 않는 postId 가 그대로 저장된다
@Transactional
public Long addComment(Long postId, String body) {
    Comment comment = new Comment(postId, body);
    return commentRepository.save(comment).getId();   // 고아 행 생성 경로
}
```

```java
// ✅ after: 부모 존재(그리고 삭제되지 않음)를 같은 트랜잭션에서 확인한다
@Transactional
public Long addComment(Long postId, String body) {
    Post post = postRepository.findActiveById(postId)        // deleted = false 조건 포함
        .orElseThrow(() -> new PostNotFoundException(postId));
    Comment comment = new Comment(post.getId(), body);
    return commentRepository.save(comment).getId();
}
```

검증은 **도메인 서비스 한 곳**에 둔다. 컨트롤러·배치·관리자 API가 각자
검증하면 3-1의 "경로 비대칭"이 그대로 재현된다. 자식 생성 진입점을
하나로 모으는 것 자체가 안전망이다.

**레이스 조건을 정직하게 말한다.** 위 코드에도 구멍이 있다 —
`findActiveById`와 `save` 사이에 다른 트랜잭션이 부모를 **물리 삭제**하면
고아가 생긴다. FK의 S 락이 하던 일이 정확히 이 틈을 막는 것이었다.
보정 선택지는 셋이고, 각각 대가가 있다.

- **부모를 물리 삭제하지 않는다(4-2)** → 틈 자체가 사라진다. 대부분의
  팀이 실제로 택하는 답이다.
- **`SELECT ... FOR SHARE`로 부모를 읽는다** → FK가 잡던 S 락을 손으로
  잡는 것이다. 정합성은 FK 수준이 되지만 **2-1의 락 경합도 그대로
  돌아온다.** 즉 "FK를 빼고 FOR SHARE를 넣는" 것은 아무것도 얻지 못한
  것 — 돈이 걸린 극소수 경로에만 쓴다.
- **틈을 인정하고 4-4의 배치가 잡게 한다** → 가장 흔한 현실적 답.
  "0건 보장"이 아니라 "N시간 내 발견"이라는 등급으로 내려온 것을
  인지하고 말한다.

삭제 쪽도 같다.

```java
// ❌ before: "자식 있나" 확인 후 삭제 — 확인과 삭제 사이에 자식이 들어오면 고아
@Transactional
public void deletePost(Long postId) {
    if (commentRepository.existsByPostId(postId)) {
        throw new PostHasCommentsException(postId);
    }
    postRepository.deleteById(postId);   // 물리 삭제. 이 사이에 addComment 가 끼면 고아
}
```

```java
// ✅ after: 물리 삭제 대신 soft delete — 자식이 가리키는 행이 사라지지 않는다
@Transactional
public void deletePost(Long postId) {
    Post post = postRepository.findActiveById(postId)
        .orElseThrow(() -> new PostNotFoundException(postId));
    post.markDeleted(clock.now());       // UPDATE posts SET deleted_at = ? WHERE id = ?
    // 자식 정책은 명시적으로: 댓글도 함께 soft delete 할지, 남길지 — 도메인 규칙으로
    commentRepository.softDeleteAllByPostId(postId);
}
```

### 4-2. ② 삭제는 소프트 삭제/아카이브로 — 고아가 생기는 조건을 없앤다

고아 행은 "부모가 사라질 때" 생긴다. 부모가 사라지지 않으면 — 즉
`deleted_at`만 찍히면 — **참조 무결성은 FK 없이도 물리적으로 깨질 수
없다.** FK를 빼는 팀이 거의 예외 없이 soft delete를 함께 택하는 이유다.

대신 두 가지를 짊어진다. 첫째,
[soft delete 문서](../03-jpa-orm/26-soft-delete-unique-and-associations.md)
§6-3에서 본 대로 **"삭제된 부모를 가리키는 살아 있는 자식"이라는 논리적
고아**가 새로 생기고, 이건 FK가 있어도 못 막는다 — "부모가 soft delete될
때 자식은 어떻게 할 것인가"를 도메인 규칙으로 정해야 한다. 둘째, 데이터가
계속 쌓이므로 언젠가 **아카이브 테이블로 이동**해야 하는데, 그 이동이
2-3절의 순서 제약을 다시 만난다 — 다만 FK가 없으므로 자식·부모를 독립적
으로 옮길 수 있고, 이때 "옮긴 뒤 고아가 없는지"를 4-4의 배치가 검증한다.

### 4-3. ③ FK 컬럼 인덱스 강제 — 사람 기억이 아니라 린트로

3-4의 함정은 "인덱스 잊지 말자"로 막히지 않는다. **CI에서 스키마를 훑어
`*_id` 컬럼에 인덱스가 없으면 빌드를 깨뜨린다.** 마이그레이션이 적용된
테스트 DB(Testcontainers)에서 아래 쿼리가 한 행이라도 돌려주면 실패.

```sql
-- MySQL: 이름이 *_id 로 끝나는데 어떤 인덱스의 선두 컬럼도 아닌 컬럼
SELECT c.table_name, c.column_name
FROM information_schema.columns c
LEFT JOIN information_schema.statistics s
       ON s.table_schema = c.table_schema
      AND s.table_name   = c.table_name
      AND s.column_name  = c.column_name
      AND s.seq_in_index = 1                 -- 선두 컬럼일 때만 인정
WHERE c.table_schema = DATABASE()
  AND c.column_name LIKE '%\_id'
  AND c.column_name <> 'id'
  AND s.index_name IS NULL;
```

```java
// 테스트로 고정 — 새 테이블·새 컬럼이 들어와도 사람이 기억할 필요가 없다
@Test
void everyLogicalFkColumnIsIndexed() {
    List<String> missing = jdbcTemplate.queryForList(MISSING_FK_INDEX_SQL, String.class);
    assertThat(missing)
        .as("논리적 FK 컬럼에 인덱스가 없다 — 마이그레이션에 CREATE INDEX 를 추가하라")
        .isEmpty();
}
```

예외(일부러 인덱스를 안 두는 컬럼)는 허용 목록 테이블로 관리한다.
"허용 목록에 넣으려면 PR에 이유를 적어야 한다"가 곧 리뷰 게이트가 된다.

### 4-4. ④ 고아 행 탐지 배치 + 알람 — 발견 지연을 시간 단위로 묶는다

FK가 "생성 시점 0건"을 보장했다면, 배치는 **"N시간 안에 발견하고 사람을
부른다"** 를 보장한다. 정규화 문서의 "보정 배치"와 같은 성격 — 어긋남을
전제로 한 안전망이다.

```sql
-- 고아 탐지의 기본형: 부모가 없는 자식
SELECT c.id, c.post_id, c.created_at
FROM comments c
LEFT JOIN posts p ON p.id = c.post_id
WHERE p.id IS NULL
  AND c.created_at < NOW() - INTERVAL 10 MINUTE   -- ① 유예 창: 진행 중 트랜잭션·복제 지연 제외
  AND c.id BETWEEN ? AND ?                        -- ② PK 범위로 청크 — 대형 테이블 풀스캔 금지
LIMIT 1000;

-- soft delete 를 쓰는 팀은 "논리적 고아"도 함께 본다
SELECT c.id, c.post_id
FROM comments c
JOIN posts p ON p.id = c.post_id
WHERE p.deleted_at IS NOT NULL
  AND c.deleted_at IS NULL                        -- 부모는 삭제됐는데 자식은 살아 있다
  AND c.id BETWEEN ? AND ?;
```

운영 규칙까지 세트다.

- **주기**: 핵심 관계(주문–회원, 결제–주문)는 시간 단위, 나머지는 일
  단위. 배치 자체가 부하가 되면 안 되므로 복제본에서, 청크로, 야간에.
- **결과 처리**: 0건이 아니면 **알람**(Slack·페이저) → 자동 삭제가 아니라
  **격리 테이블로 이동 + 원인 경로 추적**. 자동 삭제는 "부모가 다른
  경로로 옮겨진 정상 데이터"를 지울 수 있다.
- **지표화**: 고아 건수를 시계열 지표로 남기면 "어느 배포 이후 늘었다"가
  보인다 — 3-1의 "새 코드 경로"를 잡는 유일한 방법이다.
- **커버리지 목록**: 어떤 관계를 검사하는지 목록으로 관리하고, 새
  `*_id` 컬럼이 생기면 4-3의 린트가 "탐지 목록에도 추가했나"를 함께 묻게
  한다.

```java
@Scheduled(cron = "0 15 * * * *")                  // 매시 15분
public void detectOrphanComments() {
    long count = orphanScanner.scanInChunks("comments", "post_id", "posts", "id");
    orphanGauge.set("comments.post_id", count);    // 시계열 지표
    if (count > 0) {
        alert.page("orphan rows detected: comments.post_id -> posts.id = " + count);
    }
}
```

### 4-5. ⑤ 소프트 참조 규약 + 스키마 문서화 — 잃어버린 "문서로서의 스키마"를 되찾기

**소프트 참조(soft reference) 규약**: 물리 FK 대신 팀이 지키는 이름·타입
규칙이다.

- 참조 컬럼은 `<부모단수>_id`, 타입은 부모 PK와 동일(BIGINT ↔ BIGINT).
  타입이 다르면 조인에서 암묵적 형변환으로 인덱스를 못 탄다
  ([풀스캔 원인 문서](02-index-not-used-full-scan.md)).
- 컬럼 `COMMENT`에 대상을 명시한다 — 도구가 읽고 사람이 읽는다.
- 서비스 경계를 넘는 참조(주문 → 회원 서비스)는 코드에서도
  `@ManyToOne Member`가 아니라 **`Long memberId`** 로 둔다. "여기는 DB가
  지켜주지 않는 참조"임이 타입에서 드러난다.

```sql
CREATE TABLE orders (
    id         BIGINT PRIMARY KEY,
    member_id  BIGINT NOT NULL COMMENT 'FK(logical) -> members.id, 회원 서비스 소유',
    KEY idx_orders_member_id (member_id)         -- 4-3: 손으로 만든다
) COMMENT = '주문. FK 미사용 — 고아 탐지 배치 orphan-check.orders 참조';
```

**ERD 도구**: 물리 FK가 없어도 이름 규약을 근거로 관계를 추론해 그려주는
도구(SchemaSpy의 implied relationship, dbdocs 류의 선언형 스키마)를 CI에
붙여 문서를 자동 생성한다. 손으로 그린 ERD는 반드시 낡는다.

### 4-6. ⑥ 테스트·스테이징에서만 FK 켜기 — 선택지와 그 대가 (가산점 포인트)

운영에는 FK가 없지만 **테스트 DB에는 FK를 건다.** 그러면 4-1의 검증을
빠뜨린 새 코드 경로가 통합 테스트에서 FK 위반 예외로 **즉시 드러난다.**

```sql
-- src/test/resources/db/testonly/R__fk_constraints.sql  (테스트 프로파일에서만 적용)
ALTER TABLE comments ADD CONSTRAINT fk_comments_post
    FOREIGN KEY (post_id) REFERENCES posts(id);
ALTER TABLE orders ADD CONSTRAINT fk_orders_member
    FOREIGN KEY (member_id) REFERENCES members(id);
```

```yaml
# application-test.yml — Flyway 위치에 테스트 전용 디렉토리를 추가
spring:
  flyway:
    locations: classpath:db/migration, classpath:db/testonly
```

대가를 같이 말해야 한다. ⑴ **테스트와 운영의 락 동작이 달라진다** —
2-1의 데드락은 테스트에서만 나고 운영에선 안 나거나 그 반대다. ⑵ 테스트
픽스처 정리(`TRUNCATE`) 순서가 FK에 묶여 귀찮아진다. ⑶ 스테이징에 FK를
두면 운영 데이터를 복제해 넣을 때 기존 고아 때문에 적재가 실패한다 —
그 실패가 오히려 고아를 발견하는 계기가 되기도 한다. 이 선택지는 "FK를
빼도 개발 단계의 방어선은 유지하고 싶다"는 팀에 잘 맞는다.

### 4-7. ⑦ JPA — 객체 매핑과 물리 제약은 별개다

JPA의 `@ManyToOne`은 **객체 참조를 어떻게 로딩할지**에 대한 선언이고,
DB의 FK 제약과는 독립이다. 그런데 Hibernate가 DDL을 생성하면(`ddl-auto`)
`@JoinColumn`마다 **FK 제약을 기본으로 만든다.** 여기서 두 가지 사고가
난다.

```java
// ❌ before: 팀 규칙은 "운영 DB 에 FK 없음"인데, 매핑은 FK 를 만든다
@Entity
public class Comment {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "post_id")            // ddl-auto=create/update 면 FK 제약이 생성된다
    private Post post;
}
// 사고 ①: 로컬·테스트는 ddl-auto 로 FK 있는 스키마, 운영은 Flyway 로 FK 없는 스키마
//         → "테스트에선 예외, 운영에선 조용히 고아"가 반대로도 일어난다
// 사고 ②: 어느 날 누가 운영에 ddl-auto=update 를 켰다 → 수억 건 테이블에
//         ADD FOREIGN KEY = COPY 알고리즘 → 쓰기 차단 (online DDL 문서 §2)
```

```java
// ✅ after: 매핑은 유지하되 "물리 FK 를 만들지 마라"를 명시한다
@Entity
public class Comment {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(
        name = "post_id",
        foreignKey = @ForeignKey(ConstraintMode.NO_CONSTRAINT)   // DDL 생성 시 FK 제약 생략
    )
    private Post post;
}

// 서비스 경계를 넘거나 애초에 객체 그래프가 필요 없는 참조는 ID 만 든다 (4-5 소프트 참조)
@Entity
public class Order {
    @Column(name = "member_id", nullable = false)
    private Long memberId;                   // 타입 자체가 "DB 가 지켜주지 않는 참조"라고 말한다
}
```

```yaml
# 운영: 스키마는 마이그레이션 도구가 소유한다. Hibernate 는 DDL 을 만들지 않는다.
spring:
  jpa:
    hibernate:
      ddl-auto: none        # validate 도 가능하지만, validate 는 테이블·컬럼·타입만 보고
                            # FK 유무는 검사하지 않는다 — "FK 없는 운영 스키마"를 잡아주지 않는다
```

`NO_CONSTRAINT`로 물리 FK가 없어도 `@ManyToOne` 지연 로딩·조인은 그대로
동작한다. 단, **부모가 없는 자식을 로딩하면 프록시 초기화 시점에
`EntityNotFoundException`** 이 난다 — 고아 행이 있는 운영 DB에서 JPA가
먼저 비명을 지르는 지점이고, 4-4 배치가 있으면 그 전에 잡힌다.

## 5. 본인의 견해 — "우리 서비스의 조건"으로 결론 내기

### 5-1. 판단 기준 6축

"FK 건다/안 건다"는 팀의 신념이 아니라 아래 여섯 축의 답으로 정해진다.

| 축 | 질문 | FK 유지 쪽 | FK 제거 쪽 |
|---|---|---|---|
| ① 쓰기 부하·핫 부모 | 자식 INSERT가 집중되는 부모 행이 있는가(인기 글, 이벤트 상품) | 없다 | 있다 → 2-1 사슬 |
| ② 스키마 변경 빈도·크기 | 수억 건 테이블을 분기마다 바꾸는가 | 아니다 | 그렇다 → gh-ost 필요 |
| ③ 분산 계획 | 샤딩·파티셔닝·서비스 분리가 로드맵에 있는가 | 없다 | 있다 → 어차피 불가 |
| ④ 삭제 정책 | 부모를 물리 삭제하는가 | 그렇다 → FK가 막아줘야 | soft delete → 고아 조건 자체가 없음 |
| ⑤ 데이터 민감도 | 돈·법적 근거·개인정보인가 | 그렇다 → 방어선 필요 | 로그·집계·파생 데이터 |
| ⑥ 팀 규율·도구 | 4장의 체계를 운영할 배치 인프라·CI 린트·리뷰 문화가 있는가 | 없다 → 빼면 방치 | 있다 |

⑥이 결정적이다. **①~⑤가 전부 "제거"를 가리켜도 ⑥이 없으면 빼지
않는다.** 대체 체계 없이 FK만 빼는 것은 트레이드오프가 아니라 손실만
받아들인 것이기 때문이다.

### 5-2. 결론은 세 갈래다 — 그리고 기본값은 "건다"

**내 견해: 기본값은 FK를 건다. 빼는 것은 위 조건이 확인된 예외이며,
빼는 순간 4장의 일곱 가지가 세트로 따라온다.**

- **걸어라** — 단일 DB, 중간 이하 쓰기 부하, 작은 팀, 물리 삭제가 있는
  도메인. 이 조건에서 FK의 비용(부모 PK 탐색 한 번 + 드문 S 락)은
  4장 체계의 운영 비용보다 훨씬 싸다. "대규모 회사가 안 건다더라"는
  이 팀에 해당하지 않는 근거다. 단 `CASCADE`는 쓰지 않고 `RESTRICT`로
  두어 파급을 코드에 드러낸다.
- **선택적으로 걸어라** — 대부분의 중규모 서비스가 여기다. 원장성
  관계(결제 → 주문, 정산 → 결제, 권한 → 회원)에는 FK를 유지하고,
  고빈도·로그성 자식(알림, 조회 이력, 이벤트 로그)과 핫 부모를 가진
  관계(댓글 → 인기 글)에는 빼고 4장 체계를 붙인다. 서비스 경계를 넘는
  참조는 무조건 소프트 참조다. "테이블마다 판단한다"가 가장 성숙한 답이다.
- **빼라** — 샤딩·파티셔닝이 이미 있거나 확정, gh-ost 없이는 운영이 안
  되는 테이블 크기, 적재 파이프라인이 병렬로 붓는 구조, 그리고 4장을
  이미 운영하고 있는 팀. 이 팀은 FK를 빼는 것이 아니라 **FK가 하던 일을
  다른 자리(앱·배치·CI)에서 하고 있는 것**이다.

### 5-3. 면접에서 말하는 순서

> "FK를 빼는 팀이 많은 이유는 일곱 가지로 정리할 수 있는데, 핵심은 세
> 가지입니다. 첫째 락 — 자식 INSERT가 부모 행에 S 락을 커밋까지 쥐기
> 때문에, 핫 부모의 UPDATE X 락과 교차해 데드락이 나고 회피하려면 X를
> 먼저 잡아 락 보유 시간을 늘려야 하는 딜레마가 생깁니다. 둘째 운영 —
> 대량 적재·아카이빙에 순서가 강제되고, gh-ost는 FK 테이블을 아예 못
> 다루며, `ADD FOREIGN KEY`는 COPY입니다. 셋째 지형 — 샤딩·파티셔닝·
> 서비스 분리에선 FK가 정의 자체가 안 됩니다. 솔직히는 대규모 회사의
> 관행이 전파된 몫도 큽니다.
>
> 대신 잃는 것도 분명합니다. 어떤 경로로 와도 뚫리지 않는 최후 방어선,
> 고아 행이 0건이라는 보장, 스키마가 곧 문서인 상태, 그리고 MySQL이
> 자동으로 만들던 FK 컬럼 인덱스입니다.
>
> 제 견해는 기본값은 건다, 입니다. 빼는 것은 쓰기 부하·핫 부모·
> 마이그레이션 빈도·분산 계획·데이터 민감도·팀 규율을 확인한 예외이고,
> 빼는 순간 앱 레벨 존재 검증, 소프트 삭제, FK 컬럼 인덱스 CI 린트,
> 고아 탐지 배치와 알람, 소프트 참조 규약과 문서화, 그리고 테스트
> 환경에서만 FK를 켜는 것까지 세트로 갑니다. 현실적으론 테이블마다
> 판단해서 원장성 관계엔 걸고, 고빈도·로그성 관계와 서비스 경계를
> 넘는 참조엔 빼는 구성이 가장 많습니다."

## 6. 꼬리질문 대비 포인트

### "FK가 락을 잡는다고 했는데, 정확히 어떤 락이 어디에 걸리고 왜 데드락이 나나요?"

자식 `INSERT`는 FK 검사를 위해 **부모 행에 공유(S) 레코드 락**을 잡고
커밋까지 유지한다. 두 트랜잭션이 같은 부모(인기 글)에 댓글을 넣으면 둘
다 S를 쥔다(S끼리는 호환). 이어서 각자 `UPDATE posts SET comment_count
= comment_count + 1`로 **배타(X) 락**을 요구하면 상대의 S 때문에 서로
대기 — 데드락이다. 회피하려면 UPDATE(X)를 INSERT보다 먼저 두어 X를
선점해야 하는데, 그러면 X를 트랜잭션 처음부터 쥐어 락 보유 시간이
늘어난다. 덧붙여 **READ COMMITTED로 낮춰도 FK 검사의 갭 락은 남는다**는
것까지 말하면 InnoDB 락을 이해한 사람으로 들린다.

### "앱에서 부모 존재를 확인하고 INSERT하면 FK와 같은 것 아닌가요?"

같지 않다 — 두 가지가 빠진다. ⑴ **레이스 조건**: 확인과 INSERT 사이에
다른 트랜잭션이 부모를 물리 삭제하면 고아가 생긴다. FK의 S 락이 정확히
이 틈을 막던 장치다. 손으로 같은 수준을 만들려면 `SELECT ... FOR SHARE`
인데, 그러면 FK의 락 경합이 그대로 돌아오므로 얻는 게 없다. 현실적
답은 부모를 물리 삭제하지 않는 것(soft delete)으로 틈 자체를 없애고,
남는 구멍은 고아 탐지 배치가 "N시간 내 발견"으로 커버하는 것 — 즉
보장 등급이 "생성 시 0건"에서 "발견 지연 N시간"으로 내려왔음을 인지하고
말한다. ⑵ **경로 커버리지**: 앱 검증은 앱을 거치는 경로만 지킨다. 콘솔
DELETE, 보정 스크립트, 검증을 빠뜨린 새 API는 못 막는다. 그래서 검증
진입점을 도메인 서비스 한 곳으로 모으고, 테스트 환경에선 FK를 켜서 새
경로의 누락을 조기에 잡는 선택지를 붙인다.

### "FK를 안 걸었을 때 팀이 가장 흔히 놓치는 게 뭔가요?"

**인덱스다.** MySQL은 FK를 걸면 자식 FK 컬럼에 인덱스를 자동으로
만드는데, FK를 안 걸면 그 인덱스도 없다. `WHERE member_id = ?`와 "삭제
전 자식 존재 확인"이 풀스캔이 되고, "FK 뺐더니 느려졌다"의 상당수가
이것이다. 처방은 "잊지 말자"가 아니라 **CI 린트** — 테스트 DB의
`information_schema`를 훑어 `*_id` 컬럼 중 어떤 인덱스의 선두도 아닌
컬럼이 있으면 빌드를 깨뜨린다. 두 번째로 자주 놓치는 것은 **고아 탐지
배치의 커버리지 목록** — 새 참조 컬럼이 생겼는데 탐지 목록에 안 들어가
있는 관계다.

### "MSA로 분리된 서비스 간 참조는 어떻게 정합성을 지키나요?"

DB가 다르므로 FK는 선택지에 없고, 참조는 **계약**으로만 지켜진다.
⑴ 코드에서는 `@ManyToOne Member`가 아니라 `Long memberId`로 든다 —
"DB가 지켜주지 않는 참조"임이 타입에 드러난다. ⑵ 생성 시 상대 서비스에
존재를 묻거나(동기 API — 결합·지연 대가), 상대 서비스가 발행한
이벤트로 만든 **로컬 사본**(회원 요약 테이블)을 참조한다(최종적 일관성
대가). ⑶ 상대가 삭제되면 이벤트로 통보받아 로컬 자식을 처리한다 —
이벤트 유실을 전제로 **주기적 대사(reconciliation) 배치**가 두 서비스의
ID 집합을 맞춰 본다. 즉 단일 DB의 "고아 탐지 배치"가 서비스 간에서는
"대사 배치"가 되고, 이것은 ["결제됐는데 주문이 없다" 정합성 사고](27-payment-succeeded-order-missing-incident.md)의
Outbox·대사와 같은 도구 상자다.

### "그럼 나중에 FK를 다시 걸 수 있나요? 이미 고아가 있으면요?" (시니어 변별 포인트)

걸 수는 있지만 **두 가지가 앞을 막는다.** ⑴ 기존 고아: FK 추가는 기존
데이터를 검사하므로 고아가 한 행이라도 있으면 실패한다. 먼저 4-4의
탐지 쿼리로 고아를 찾아 격리·정리해야 하고, 이것이 몇 주짜리 데이터
정비 프로젝트가 되곤 한다. `foreign_key_checks = 0`으로 검사를 끄고
걸면 통과는 하지만 **위반 데이터가 그대로 남은 채 FK만 생긴다** —
방어선이 아니라 거짓 안심이다. ⑵ DDL 비용: MySQL에서 `ADD FOREIGN
KEY`는 검사를 켠 상태면 COPY 알고리즘이라 쓰기 차단·디스크 2배이고,
gh-ost는 못 쓴다. PostgreSQL이라면 `ADD CONSTRAINT ... NOT VALID`로
새 쓰기부터 검사를 시작하고 `VALIDATE CONSTRAINT`를 나중에 돌려 긴
락을 피할 수 있다. 결론 — "FK는 나중에 걸면 된다"는 말은 사실상
거짓에 가깝고, **FK는 처음에 걸든가 처음부터 대체 체계로 가든가** 둘 중
하나다. 이것이 비가역에 가까운 결정임을 아는 것이 시니어의 답이다.

### "결제·정산처럼 돈이 걸린 테이블도 FK를 빼나요?" (시니어 변별 포인트)

여기서 "우리 팀은 FK 안 겁니다"로 일괄 답하면 탈락이다. 판단 축
⑤(데이터 민감도)가 다른 축을 누른다 — **원장성 관계(결제 → 주문, 정산
→ 결제)는 고아 한 건이 곧 돈의 불일치**이고, "N시간 내 발견"이 아니라
"생성 시 0건"이 필요하다. 이 관계는 쓰기가 폭주하는 핫 부모도 아니고
(주문 하나에 결제 몇 건), 샤딩하더라도 주문과 결제는 같은 샤드 키로
같은 샤드에 두는 것이 정석이므로 FK 제거의 이유 ①⑤가 해당되지 않는다.
따라서 **원장성 관계에는 FK를 유지하고, 그 위에 고아 탐지가 아니라
금액 대사 배치를 얹는다.** 같은 시스템 안에서도 알림·이력 테이블은
FK를 빼는 — "테이블마다 판단"이 이 질문의 정답 형태다.

## 한 줄 요약

**FK는 "가리키는 곳이 반드시 있다"를 어떤 경로로 와도 강제하는 최후
방어선이고, 그 대가는 자식 INSERT마다 부모 행에 커밋까지 쥐는 S 락(핫
부모의 X 락과 교차해 데드락) · 적재·아카이빙의 순서 제약 · gh-ost
불가와 `ADD FOREIGN KEY`의 COPY · 샤딩·분리에서의 성립 불가 · CASCADE의
보이지 않는 폭발이다. 빼면 최후 방어선·고아 0건 보장·문서로서의
스키마·자동 인덱스를 잃으므로, 기본값은 걸고 빼는 것은 조건(쓰기
부하·마이그레이션 빈도·분산 계획·삭제 정책·데이터 민감도·팀 규율)이
확인된 예외로 다루며, 빼는 순간 앱 레벨 존재 검증 + 소프트 삭제 + FK
컬럼 인덱스 린트 + 고아 탐지 배치와 알람 + 소프트 참조 규약·문서화 +
테스트 환경 FK + JPA `NO_CONSTRAINT`가 한 세트로 따라와야 한다 — 대체
체계 없이 FK만 빼는 것은 결정이 아니라 방치다.**
