# 커버링 인덱스 — 북마크 룩업을 0으로 만드는 대신 인덱스 폭·쓰기·취약성을 치른다

> 핵심 관전 포인트: **커버링 인덱스는 쿼리가 필요로 하는 모든 컬럼
> (SELECT 목록 · WHERE · ORDER BY · 조인 키)이 세컨더리 인덱스 안에 들어
> 있어서, 리프에서 PK를 꺼내 클러스터드 인덱스를 다시 타는 2단계(북마크
> 룩업)가 통째로 사라진 상태다. 빠른 이유는 "테이블에 안 가서"가 아니라 —
> 북마크 룩업은 **행 1건마다 PK 순으로 흩어진 페이지를 한 장씩 찌르는
> 랜덤 I/O**인데, 커버링은 그것을 **좁은 리프 페이지 몇 장을 연결 리스트
> 따라 이어 읽는 순차 I/O**로 바꾸기 때문이다. 효과가 큰 조건은 "대상
> 행이 많고 · 필요한 컬럼이 좁고 · 자주 불리는" 쿼리(목록·랭킹·COUNT·
> 페이징)이고, 그 대가는 **인덱스 폭 증가(버퍼 풀 적재율↓) · 포함 컬럼이
> UPDATE될 때마다의 쓰기 증폭 · SELECT에 컬럼 하나만 추가해도 조용히
> 깨지는 취약성**이다. EXPLAIN에서 `Extra: Using index`가 커버링이고,
> `Using index condition`은 룩업 횟수만 줄이는 ICP라 다른 것이다.**

---

## 0. 질문 + 의도

**질문**: "커버링 인덱스란? 어떤 상황에서 효과가 큰가요?"

**출제 의도**: 랭킹·목록 조회 같은 고빈도 쿼리를 디스크 접근 없이
처리하는 핵심 기법. 아는 사람은 같은 하드웨어에서 몇 배의 처리량을 뽑는다.
즉 "인덱스만 읽고 끝난다"는 정의의 암기가 아니라, **왜 몇 배인지를 I/O
비용 모델(랜덤 vs 순차)로 설명**할 수 있는지, 그리고 그 몇 배를 위해
**무엇을 지불하는지**(인덱스 폭·쓰기·취약성)를 함께 말해 "언제 쓰고
언제 쓰지 않는지"를 스스로 판단하는지를 본다.

> 이 문서는 [인덱스와 B+Tree](01-index-and-bplus-tree.md) §4(리프에 무엇이
> 드는가), [클러스터드 vs 세컨더리 인덱스](03-clustered-vs-secondary-index.md)
> §1(북마크 룩업의 구조), [인덱스가 있는데 풀스캔](02-index-not-used-full-scan.md)
> §4(랜덤 vs 순차 I/O 손익분기)를 전제로 한 단계 더 들어간다. 세 문서의
> 공통 축 — **"세컨더리 조회는 2단계이고, 2단계는 랜덤 I/O다"** — 가
> 흔들리면 이 문서도 같이 흔들리니 먼저 그 한 줄을 고정하고 읽는다.

## 1. 개념 — "인덱스만 읽고 끝난다"가 정확히 어느 단계를 없애는가

### 1-1. 정의: 세 군데의 컬럼이 전부 인덱스 안에 있어야 한다

세컨더리 인덱스의 리프 엔트리는 `(인덱스 컬럼들, PK)`다. 쿼리가 쓰는
컬럼이 **이 엔트리 안에서 전부 해결되면** DB는 PK를 들고 클러스터드
인덱스로 내려갈 이유가 없다. 이 상태의 인덱스를 그 쿼리에 대한 **커버링
인덱스**라 부른다. "커버링"은 인덱스의 종류가 아니라 **인덱스와 쿼리의
관계**다 — 같은 인덱스가 어떤 쿼리에는 커버링이고 다른 쿼리에는 아니다.

체크할 곳은 세 군데다.

- **SELECT 목록**의 컬럼
- **WHERE**(조인이면 ON 조건까지)의 컬럼
- **ORDER BY / GROUP BY**의 컬럼

InnoDB에서는 여기에 공짜 한 줄이 붙는다 — **PK 컬럼은 모든 세컨더리
리프에 이미 들어 있으므로, 인덱스 정의에 안 써도 커버된다.** `(user_id)`
인덱스 하나로 `SELECT id FROM orders WHERE user_id = ?`는 이미 커버링이다.
(가산점 포인트 — 이 성질이 §6의 "지연 조인" 기법의 근거다.)

```text
세컨더리 인덱스 idx(user_id, created_at)     리프 엔트리 = (user_id, created_at, PK)

 리프: │(7, 08-01, PK=8231)│(7, 08-02, PK=4)│(7, 08-03, PK=99120)│(7, 08-04, PK=577)│ …
              │                  │                   │                  │
 ── SELECT * … : 행마다 PK를 들고 아래로 ▼ (북마크 룩업 × 대상 행 수)
              ▼                  ▼                   ▼                  ▼
 클러스터드:  [… PK=8231 …]   [PK=4 …]        [… PK=99120 …]      [… PK=577 …]
              ↑ 인덱스에서는 이웃인 네 행이, 테이블(PK 순)에서는 서로 먼 페이지에 있다

 ── SELECT id, created_at … : 리프에서 답이 다 나왔다. 여기서 끝. 아래로 내려가지 않는다.
```

### 1-2. 비용 사슬 — "왔다갔다"를 I/O 단위로 분해한다

이 절이 이 문서의 심장이다. "테이블까지 안 가서 빠르다", "왔다갔다 안
해서 빠르다"는 결론만 말한 것이지 비용을 말한 게 아니다. 면접에서는
**어느 고리가 끊겼는지**를 이름을 붙여 말해야 한다.

먼저 커버링이 **아닐 때** 무슨 일이 벌어지는지를 사슬로 놓는다.

> ⑴ 필요한 컬럼이 인덱스 밖에 있다 → ⑵ 리프에서 얻은 PK로 **클러스터드
> B+Tree를 행마다 한 번씩 재탐색**한다(트리 높이만큼 페이지를 거치는데,
> 루트·브랜치는 캐시돼 있어도 **리프는 행마다 다른 페이지**다) → ⑶ 세컨더리
> 인덱스는 `(user_id, created_at)` 순으로 정렬돼 있지만 클러스터드는
> **PK 순**이라, 인덱스에서 이웃한 두 엔트리의 행은 테이블에서 **서로 먼
> 페이지**에 있다 → ⑷ 그러므로 룩업 1건 = 흩어진 페이지 1장을 따로 요청
> = **랜덤 I/O 1회** → ⑸ 대상이 N행이면 랜덤 I/O N회이고, 그 N장은 테이블
> 전역에 퍼져 있어 **버퍼 풀 워킹셋이 테이블 전체**가 된다 → ⑹ 버퍼 풀에
> 없는 페이지 비율만큼 **디스크 랜덤 읽기**가 발생하고, 처리량은 초당
> 처리 가능한 랜덤 I/O 수에 묶인다.

그리고 **랜덤 I/O가 순차 I/O보다 왜 비싼지**를 세 축으로 고정한다. 이
축이 비어 있으면 위 사슬의 ⑷~⑹이 전부 "그냥 느리다"로 뭉개진다.

- **요청 단위**: 랜덤은 16KB 페이지 1장마다 I/O 요청 1건이다. 순차는
  이어진 페이지를 **큰 묶음으로 한 번에 요청**하고, InnoDB는 연속 접근을
  감지하면 다음 묶음(익스텐트)을 **미리 읽기(read-ahead)** 로 올려둔다.
  랜덤 접근에는 미리 읽기가 작동하지 않는다.
- **매체**: HDD는 요청마다 헤드 이동 + 회전 대기가 붙어 차이가 수십 배다.
  SSD는 그 기계적 대기는 없지만 **요청 1건당 고정 오버헤드**(커널·드라이버·
  컨트롤러 경로)와 미리 읽기 불가는 그대로라, 차이가 **줄어들 뿐 사라지지
  않는다.** "SSD니까 랜덤도 괜찮다"는 절반만 맞다.
- **캐시**: 순차는 좁은 범위의 페이지만 만지므로 버퍼 풀 히트율이 높고,
  랜덤은 워킹셋이 넓어 미스율이 높다. 즉 랜덤 I/O는 **디스크 비용이자
  캐시 비용**이다.

이제 커버링이 하는 일은 한 문장이다 — **사슬의 ⑴을 끊는다.** 필요한
컬럼이 전부 인덱스 안에 있으니 ⑵의 재탐색이 없고, 따라서 ⑶~⑹이
통째로 사라진다. 남는 것은 세컨더리 **리프를 연결 리스트 따라 옆으로
읽는 것**뿐인데, 리프는 정렬 순서로 이어져 있고(순차) 엔트리가 좁아
페이지 1장에 수백 건이 들어간다. **N행을 읽는 데 페이지 N장(랜덤)이 아니라
N/수백 장(순차)** — 이 비율이 "몇 배"의 출처다.

숫자 감각으로 세 사례를 잡아둔다(자릿수 감각용이지 정확한 상수가 아니다).

| 쿼리 | 커버링이 아닐 때 | 커버링일 때 |
|---|---|---|
| 내 주문 목록 `LIMIT 20` | 리프 1장 + **랜덤 룩업 20회** | 리프 1장 |
| 랭킹 TOP 100 | 리프 1~2장 + **랜덤 룩업 100회** | 리프 1~2장 |
| `COUNT(*) WHERE status='ACTIVE'` (90만 행) | 룩업 90만 회 → 옵티마이저가 포기하고 **테이블 100만 행 풀스캔** | 좁은 인덱스 리프 수천 장 **순차** |

세 번째 줄이 중요하다. 대상이 많아 인덱스가 버려지던 쿼리(풀스캔 문서
§4의 손익분기)도, **커버링이면 인덱스 풀스캔(`type: index`)이 테이블
풀스캔보다 싸다** — 인덱스가 테이블보다 훨씬 좁기 때문이다. 커버링은
"룩업을 없앤다"에서 끝나지 않고 **손익분기 자체를 옮긴다.**

### 1-3. 말하기 훈련 — 뭉뚱그린 표현을 이름 붙은 사슬로 교체

| 뭉뚱그린 표현 | 이름 | 사슬로 말하면 |
|---|---|---|
| "테이블까지 안 가서 빠르다" | **북마크 룩업 제거** | 필요한 컬럼이 인덱스 안 → PK 재탐색 0회 → 행마다 흩어진 페이지를 찌르던 랜덤 I/O N회가 → 좁은 리프 페이지 N/수백 장의 순차 읽기로 |
| "왔다갔다 해서 느리다" | **랜덤 I/O + 워킹셋 확대** | 세컨더리 정렬 ≠ PK 정렬 → 이웃 엔트리의 행이 먼 페이지 → 요청 1건당 페이지 1장 → 미리 읽기 무용 → 워킹셋 = 테이블 전체 → 버퍼 풀 미스 → 디스크 랜덤 읽기 |

## 2. 동작 — 어떤 상황에서 효과가 큰가, EXPLAIN에서 어떻게 확인하나

### 2-1. 효과 공식과 암기 목록 5종

효과의 크기는 공식 하나로 어림된다.

> **효과 ≈ (절감되는 룩업 횟수) × (룩업 1회의 랜덤 I/O 비용) × (호출
> 빈도) − (인덱스 폭 증가로 늘어난 비용)**

앞의 세 항이 크고 마지막 항이 작을수록 효과가 크다. 그래서 효과가 큰
상황 목록은 이 공식의 항을 하나씩 키우는 조건들이다. **암기 목록 — 효과
큰 상황 5종**:

1. **대상 행이 많다** — 범위 조회, 낮은 선택도 조건. 룩업 횟수 N 자체가
   크다. 극단에서는 인덱스 풀스캔이 테이블 풀스캔을 이긴다(§1-2).
2. **필요한 컬럼이 좁다** — 목록 카드·랭킹 행처럼 2~4개의 짧은 컬럼만
   쓴다. 인덱스 폭 증가 항이 작다.
3. **호출 빈도가 높다** — 메인 목록 API, 랭킹 보드, 홈 화면. 출제 의도의
   "같은 하드웨어에서 몇 배"는 여기서 실현된다.
4. **세기만 한다** — `COUNT` / `EXISTS` / `SUM(amount)` 같은 집계, 또는
   조인에서 **조인 키와 필터 컬럼만 필요한 드리븐 테이블**. 행의 나머지가
   애초에 필요 없다.
5. **정렬·페이징을 인덱스에서 끝낸다** — `ORDER BY … LIMIT`, 깊은
   페이지네이션의 지연 조인(§6). 정렬 컬럼까지 인덱스에 있어야 커버링과
   `filesort` 제거가 동시에 성립한다.

반대로 **효과가 작거나 없는 상황**도 같은 공식에서 나온다 — PK 단건
조회(클러스터드 리프가 이미 행이라 룩업이 없다), `SELECT *`나 TEXT/BLOB
포함(커버 자체가 불가), 대상 행이 1~2건(절감 룩업이 1~2회), 쓰기가
지배적인 테이블(마지막 항이 앞을 잡아먹는다).

### 2-2. before / after — 목록 조회 한 건으로

```sql
-- orders (id BIGINT PK, user_id, status, created_at, amount, memo TEXT, …)
-- 화면: "내 주문 목록" — 카드에 id, created_at, amount 세 컬럼만 표시

-- ❌ before: 탐색용 인덱스 + SELECT *
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);

EXPLAIN SELECT * FROM orders
WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20;
-- type: ref   key: idx_orders_user_created   rows: 20
-- Extra: Backward index scan      ← 정렬은 인덱스가 해결했지만 "Using index"가 없다
--                                     = 20행 각각 PK로 클러스터드 재탐색(랜덤 룩업 20회)

-- ✅ after: 화면이 쓰는 amount를 인덱스 끝에 "실어" 커버링으로 만든다.
--    id(PK)는 세컨더리 리프에 이미 있으니 적지 않는다.
--    접두사가 같은 기존 인덱스는 추가가 아니라 교체(중복 인덱스 방지).
DROP INDEX idx_orders_user_created ON orders;
CREATE INDEX idx_orders_user_created_cover ON orders (user_id, created_at, amount);

EXPLAIN SELECT id, created_at, amount FROM orders
WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20;
-- type: ref   key: idx_orders_user_created_cover   rows: 20
-- Extra: Using index (DESC라 Backward index scan도 함께)   ← 룩업 0회, 리프 1~2장으로 끝
```

`amount`는 조건에도 정렬에도 안 쓰인다. **인덱스 뒤쪽 컬럼은 탐색에는
기여하지 않아도 리프에 실려 있기만 하면 커버링에 기여한다** — 이걸
"실어 나르는(payload) 컬럼"이라고 생각하면 설계할 때 헷갈리지 않는다.
앞쪽은 **찾기 위한** 컬럼(등호 → 범위/정렬 순), 뒤쪽은 **나르기 위한**
컬럼이다.

### 2-3. EXPLAIN `Extra` 3종 — `Using index` ≠ `Using index condition`

이 둘을 섞어 말하면 "커버링을 이해했다"는 주장이 바로 무너진다. **암기
목록 — Extra 3종**:

| Extra | 뜻 | 북마크 룩업 |
|---|---|---|
| `Using index` | **커버링** — 인덱스만 읽고 끝, 테이블 접근 없음 | **0회** |
| `Using index condition` | **ICP(Index Condition Pushdown)** — 인덱스 컬럼으로 된 조건을 스토리지 엔진이 **룩업 전에** 인덱스 엔트리에서 평가해, 탈락한 행의 룩업을 건너뜀 | **줄어듦**(통과한 행만) |
| `Using where` | 룩업으로 행을 가져온 **뒤** 서버 층에서 조건 평가 | 전부 |

ICP가 왜 존재하는지를 예로 잡는다.

```sql
CREATE INDEX idx_users_last_first ON users (last_name, first_name);

SELECT * FROM users WHERE last_name = 'Kim' AND first_name LIKE '%수%';
-- last_name = 'Kim'      → 인덱스 탐색에 쓰인다(ref)
-- first_name LIKE '%수%' → 선행 와일드카드라 탐색에는 못 쓴다. 하지만 값은 인덱스 리프에 있다.

-- ICP 없음: 'Kim' 전부를 룩업해 행을 가져온 뒤 first_name을 검사      → Extra: Using where
-- ICP 있음: 리프의 first_name 값으로 먼저 거르고, 통과한 행만 룩업     → Extra: Using index condition
--   룩업 횟수: (Kim 전체) → (Kim 중 '수' 포함). 크게 줄지만 0은 아니다.
```

구분을 한 문장으로 — **`Using index`는 테이블 접근이 없다, `Using index
condition`은 테이블 접근 횟수를 인덱스에서 미리 걸러 줄인다.** 커버링이
성립하면 룩업이 없으니 ICP가 등장할 자리도 없다 — `Using index`만 뜬다.
ICP는 "커버링을 못 만들었을 때 룩업을 덜 하게 해주는 차선"이라고 위치를
잡아두면 둘이 섞이지 않는다.

`type` 칸도 같이 읽어야 한다. `Using index`가 떠도 `type: index`면
**인덱스를 처음부터 끝까지 읽는 인덱스 풀스캔**이다. 테이블 풀스캔보다는
싸지만 "좁힌 뒤 커버링"(`ref`/`range` + `Using index`)과는 다르므로,
좋은 신호인지 아닌지는 `rows`와 함께 판단한다.

### 2-4. (가산점 포인트) 다른 DB는 — PostgreSQL의 Index Only Scan과 `INCLUDE`

- **PostgreSQL**은 힙 테이블이고 MVCC 가시성 정보가 힙 튜플에 있다. 그래서
  인덱스만 읽어서는 "이 행이 내 트랜잭션에 보이는가"를 알 수 없고,
  **visibility map**에 "이 페이지의 튜플은 전부 가시"로 표시된 페이지만
  힙 방문을 생략한다. VACUUM이 밀리면 Index Only Scan 계획이 잡혀도
  `EXPLAIN ANALYZE`의 `Heap Fetches`가 치솟아 사실상 커버링 효과가 사라진다.
  "커버링 인덱스를 만들었는데 안 빨라요"의 PostgreSQL판 원인이다.
- PostgreSQL과 SQL Server에는 **`INCLUDE (col)`** 이 있다 — 탐색 키가
  아닌 컬럼을 **리프에만** 실어 커버링을 만든다. 키 길이와 정렬 순서에
  영향을 주지 않는다. **MySQL에는 없다.** 그래서 MySQL은 나르기용 컬럼도
  키에 직접 붙여야 하고, 그만큼 키 길이 상한(§3-4)과 정렬·비교 비용을
  함께 짊어진다.

## 3. 대가 — 트레이드오프를 한 호흡에: 폭 · 쓰기 · 취약 · 상한

편익만 말하면 반쪽 답이다. 커버링 인덱스는 **읽기의 랜덤 I/O**를 **인덱스
폭 + 쓰기 비용 + 유지보수 취약성**으로 바꾸는 거래이고, 면접관은 후자를
말하는지 반드시 본다. **암기 목록 — 대가 4종**은 "폭·쓰기·취약·상한"이다.

### 3-1. 폭 — 넓어진 인덱스는 커버링의 이득 일부를 스스로 갉아먹는다

> 나르기용 컬럼을 붙인다 → 리프 엔트리가 커진다 → 16KB 페이지당 엔트리
> 수↓ → 같은 행 수를 담는 리프 페이지 수↑(트리 높이가 오를 수도) → 같은
> 범위를 읽는 데 페이지가 더 필요하고 → **버퍼 풀 적재율↓** → 이 인덱스가
> 다른 인덱스·테이블 페이지를 밀어낸다.

[클러스터드 문서 §2-1](03-clustered-vs-secondary-index.md)의 "PK는 곱셈
계수"와 같은 사슬이다. 그래서 원칙은 **필요한 컬럼만, 짧은 타입만**이다.
`VARCHAR(255)` 제목이나 `DECIMAL(20,4)` 여러 개를 "혹시 쓸지 모르니"
싣는 순간 §1-2의 "N/수백 장"이 "N/수십 장"으로 줄어들고 이득이 반감된다.

### 3-2. 쓰기 — 실은 컬럼이 UPDATE되는 순간 그 인덱스도 갱신 대상이 된다

인덱스에 없던 컬럼은 UPDATE해도 인덱스가 움직이지 않았다. 커버링을 위해
그 컬럼을 실은 순간부터는 다르다.

> 실은 컬럼이 UPDATE된다 → InnoDB는 세컨더리 엔트리를 제자리 수정하지
> 않고 **옛 엔트리 삭제 표시 + 새 엔트리 삽입**으로 처리한다 → 인덱스
> 페이지 쓰기 + undo/redo 기록이 늘어난다 → 갱신이 잦은 컬럼이면 그 UPDATE
> 경로 전체가 느려지고, 쓰기가 몰리는 시간대에 락 점유 시간까지 늘어난다.

```sql
-- ❌ before: "화면에 다 보이니까" 자주 바뀌는 컬럼까지 실었다
CREATE INDEX idx_orders_user_cover ON orders (user_id, created_at, amount, status, updated_at);
-- status는 주문 상태 전이마다, updated_at은 모든 UPDATE마다 바뀐다
-- → 주문 한 건의 상태가 바뀔 때마다 이 인덱스 엔트리가 삭제+삽입된다
-- → 읽기에서 번 랜덤 I/O를 쓰기의 인덱스 갱신으로 도로 지불

-- ✅ after: 생성 후 거의 안 바뀌는 컬럼만 싣고, 자주 바뀌는 컬럼은 화면 요구를 재협상하거나
--    (목록엔 상태를 안 보여주고 상세에서 본다) 별도 조회로 뺀다
CREATE INDEX idx_orders_user_cover ON orders (user_id, created_at, amount);
```

판단 기준을 한 줄로 — **"이 컬럼은 행이 만들어진 뒤 몇 번 바뀌는가?"**
거의 안 바뀌면 싣고, 자주 바뀌면 싣지 않는다. 그 경계가 이 인덱스의
손익분기다.

### 3-3. 취약 — SELECT에 컬럼 하나 추가하면 에러 없이 조용히 깨진다

가장 실무적인 대가다. 커버링은 **인덱스와 쿼리의 관계**라서(§1-1), 쿼리
쪽이 바뀌면 인덱스는 그대로여도 관계가 깨진다.

> 기획이 카드에 `status` 뱃지를 추가한다 → DTO에 필드 하나 추가 → SELECT
> 목록에 `status`가 들어간다 → `Using index`가 사라지고 20행 룩업이
> 부활한다 → 목록 20건이면 티도 안 나지만, 같은 인덱스를 커버링으로 믿고
> 있던 **랭킹·집계 쿼리는 절벽**을 맞는다 → 에러도 경고도 없다. p99
> 지연 그래프만 조용히 올라간다.

JPA는 이 취약성을 구조적으로 안고 있다 — 엔티티를 조회하면 **모든 컬럼을
SELECT**하므로 엔티티 조회는 절대 커버링이 되지 않는다. 커버링을 쓰려면
DTO 프로젝션이 필수이고, 그래서 안전망(§4)이 필요하다.

### 3-4. 상한과 중복 — 키 길이 제한, 접두사 인덱스, 기존 인덱스와의 교체

- **키 길이 상한**: InnoDB 인덱스 키에는 길이 상한이 있다(DYNAMIC 행
  포맷 기준 3072바이트). TEXT/BLOB은 실을 수 없고, 긴 VARCHAR 여러 개를
  실으면 상한에 걸린다. **접두사 인덱스**(`title(30)`)는 값의 일부만
  가지므로 그 컬럼을 SELECT하는 쿼리는 커버할 수 없다.
- **중복 인덱스**: `(user_id, created_at)`가 있는데 `(user_id, created_at,
  amount)`를 **추가**하면 왼쪽 접두사가 같은 중복이다. 교체가 맞지만,
  교체 전에 기존 인덱스를 쓰던 다른 쿼리가 무엇인지 확인해야 한다
  ([B+Tree 문서 §3 축 3](01-index-and-bplus-tree.md)). 대형 테이블에서는
  DDL 자체가 부하이자 복제 지연 요인이라는 점도 같이 말한다.

### 3-5. 한 호흡 템플릿

면접에서 편익과 대가를 **한 문장 안에** 넣는 연습용 문장이다. 이 문장이
입에서 그대로 나오면 약점 ②(편익만 서술)는 이 문항에서 재발하지 않는다.

> "커버링 인덱스는 **읽기에서 북마크 룩업 N회, 즉 랜덤 I/O N회를 0으로
> 만들어** 몇 배의 처리량을 얻는 대신, **폭**(엔트리 비대 → 버퍼 풀
> 적재율↓)·**쓰기**(실은 컬럼 UPDATE마다 인덱스 갱신)·**취약성**(SELECT에
> 컬럼 하나 추가로 조용히 무효)을 치릅니다. 그래서 '많이 읽고, 좁게
> 쓰고, 자주 불리는' 쿼리에, 거의 안 바뀌는 컬럼만 실어 제한적으로 씁니다."

## 4. 안전망 — 커버링이 깨지는 것을 사람이 아니라 코드·테스트·설정이 잡게

§3-3의 "조용히 깨짐"은 PR 설명이나 위키, 담당자의 기억으로는 막을 수
없다. 컬럼을 추가하는 사람은 6개월 뒤의 다른 사람이고, 그 사람은 이
인덱스의 존재를 모른다. 그래서 네 겹으로 고정한다. **암기 목록 — 안전망
4종: 프로젝션 · 실행 계획 테스트 · 마이그레이션 주석 · rows_examined
알림.**

### 4-1. 코드 — DTO 프로젝션으로 SELECT 목록을 타입에 고정한다

```java
// ❌ before: 엔티티 조회 — 모든 컬럼을 SELECT하므로 어떤 인덱스로도 커버 불가
List<Order> findByUserIdOrderByCreatedAtDesc(Long userId, Pageable pageable);
// → SELECT o.id, o.user_id, o.status, o.created_at, o.amount, o.memo, … FROM orders o …

// ✅ after: 닫힌 인터페이스 프로젝션 — 여기 선언한 getter만 SELECT 된다
public interface OrderCard {
    Long getId();
    LocalDateTime getCreatedAt();
    BigDecimal getAmount();
}
List<OrderCard> findByUserIdOrderByCreatedAtDesc(Long userId, Pageable pageable);
// → SELECT o.id, o.created_at, o.amount FROM orders o WHERE o.user_id = ? ORDER BY o.created_at DESC LIMIT ?
//   idx_orders_user_created_cover(user_id, created_at, amount)에 정확히 덮인다
```

(`@Query("select new …OrderCard(o.id, o.createdAt, o.amount) …")`의
클래스 기반 DTO나 QueryDSL `Projections.constructor`도 같은 효과다.)
핵심은 **프로젝션 타입이 곧 SELECT 목록의 계약**이라는 것 — 컬럼을
추가하려면 이 타입을 고쳐야 하고, 그 diff가 리뷰에 드러난다. 인덱스
정의와 1:1로 대응하는 코드상의 지점이 생긴다.

### 4-2. 테스트 — 실행 계획을 단정하는 통합 테스트

프로젝션을 고쳐도 사람이 "이거 커버링 깨지는데?"를 떠올려야 한다면 아직
기억 의존이다. 실행 계획 자체를 테스트가 단정하게 한다.

```java
@Test  // Testcontainers MySQL 위에서 실행. 데이터는 수백 건 정도 적재해 둔다.
void 주문목록_조회는_커버링_인덱스를_탄다() {
    // JPA가 실제로 내보내는 SQL(p6spy 로그에서 확보)을 그대로 EXPLAIN 한다
    String plan = jdbcTemplate.queryForObject(
        "EXPLAIN FORMAT=JSON SELECT o.id, o.created_at, o.amount FROM orders o " +
        "WHERE o.user_id = 7 ORDER BY o.created_at DESC LIMIT 20", String.class);

    assertThat(plan).contains("\"key\": \"idx_orders_user_created_cover\"");
    assertThat(plan).contains("\"using_index\": true");   // ← 커버링이 깨지면 여기서 빨간불
}
```

주의 두 가지. ⑴ 단정은 `key`와 `using_index`처럼 **구조적으로 결정되는
값**에 한정한다 — `rows`나 비용 수치는 통계에 따라 흔들려 테스트가
불안정해진다. ⑵ EXPLAIN 대상 SQL은 손으로 쓴 것이 아니라 **JPA가 실제로
내보낸 문장**이어야 한다(p6spy·datasource-proxy 로그로 확보). 손으로
쓴 SQL이 통과해도 실제 쿼리가 다르면 테스트는 거짓 안심을 준다.

### 4-3. 설정 — 마이그레이션 파일에 인덱스의 존재 이유를 박는다

인덱스 정의는 Flyway/Liquibase 마이그레이션이라는 **코드**로 관리되므로,
"이 인덱스가 누구를 위해 존재하는지"를 그 파일 안에 남길 수 있다.

```sql
-- V37__orders_user_created_cover.sql
-- [COVERING] OrderCard 프로젝션(id, created_at, amount) 전용 커버링 인덱스.
--   앞 2컬럼 = 탐색·정렬용, amount = 나르기용.
--   OrderCard에 컬럼을 추가하면 커버링이 깨진다 → OrderCoveringIndexTest가 실패한다.
--   자주 바뀌는 컬럼(status, updated_at)은 의도적으로 제외(§3-2).
CREATE INDEX idx_orders_user_created_cover ON orders (user_id, created_at, amount);
```

이름 규약도 설정의 일부다 — `_cover` 접미사를 붙여 두면 리뷰어가 이름만
보고 "나르기용 컬럼이 실린 인덱스"임을 알고, `SHOW INDEX` 결과에서도
"왜 amount가 여기 있지? 지워도 되나?"라는 오판을 막는다.

### 4-4. 운영 — `rows_examined` 비율 알림, 마지막 그물

앞의 세 겹을 다 뚫고 배포된 뒤에도 에러는 나지 않는다. 그래서 관측이
마지막 그물이다. slow query log나 `performance_schema`의 쿼리 다이제스트
통계에서 **해당 쿼리의 `rows_examined / rows_sent` 비율**이나 p99 지연이
기준선 대비 튀면 알림이 오게 둔다. 커버링이 깨지면 읽는 행 수는 그대로여도
페이지 접근 수가 뛰므로 지연 그래프에 먼저 나타난다. 반대 방향의 점검도
같이 — `sys.schema_unused_indexes`에 `_cover` 인덱스가 올라오면 쿼리 쪽이
바뀌어 더는 안 쓰이는 것이니 정리 대상이다.

## 5. 암기 카드 — 네 개의 목록을 한 장에

면접 직전에 이 카드만 훑는다. 목록이 인출되지 않으면 사슬도 트레이드오프도
꺼낼 수 없다.

- **효과 큰 상황 5종**: ① 대상 행이 많다 ② 필요한 컬럼이 좁다 ③ 자주
  불린다 ④ 세기만 한다(COUNT/EXISTS/집계/조인 키) ⑤ 정렬·페이징을 인덱스에서
  끝낸다 → 기억 열쇠 **"많이 · 좁게 · 자주 · 세기 · 정렬"**
- **Extra 3종**: `Using index`(커버링, 룩업 0) / `Using index condition`
  (ICP, 룩업 감소) / `Using where`(룩업 후 필터) — 그리고 `type: index`는
  인덱스 **풀스캔**임을 잊지 말 것
- **대가 4종**: **폭**(버퍼 풀 적재율↓) · **쓰기**(실은 컬럼 UPDATE마다
  삭제+삽입) · **취약**(SELECT 컬럼 추가로 조용히 무효) · **상한**(키 길이,
  접두사 인덱스 불가, 중복 인덱스 교체)
- **안전망 4종**: DTO **프로젝션** · EXPLAIN **단정 테스트** · 마이그레이션
  **주석 + `_cover` 규약** · **`rows_examined` 알림**
- **비용 사슬 한 줄**: 컬럼이 인덱스 밖 → PK로 클러스터드 재탐색(행마다)
  → 세컨더리 순서 ≠ PK 순서 → 페이지 1장당 요청 1건 = 랜덤 I/O → 워킹셋 =
  테이블 전체 → 버퍼 풀 미스 → 디스크 랜덤 읽기. 커버링은 첫 고리를 끊는다.

## 6. 꼬리질문 대비 포인트

### "커버링 인덱스가 왜 빠른지, '테이블에 안 가서' 말고 I/O 단위로 설명해보세요."

세컨더리 인덱스 조회는 2단계다. 1단계는 리프를 연결 리스트로 훑는
순차 읽기라 싸고, 2단계는 리프에서 얻은 PK로 클러스터드 인덱스를 **행마다
재탐색**하는 것이다. 세컨더리는 자기 컬럼 순, 클러스터드는 PK 순으로
정렬돼 있어 **인덱스에서 이웃한 행이 테이블에서는 먼 페이지**에 있고,
그래서 2단계는 **페이지 1장당 요청 1건인 랜덤 I/O**다 — 미리 읽기가
안 걸리고, 워킹셋이 테이블 전체로 퍼져 버퍼 풀 미스도 늘어난다. 커버링은
필요한 컬럼이 전부 인덱스에 있어 **2단계 자체가 없다.** 대상 N행에 대해
"랜덤 페이지 N장"이 "좁은 리프 N/수백 장 순차"로 바뀌는 것이 몇 배의
정체다. **SSD에서도** 요청당 고정 오버헤드와 미리 읽기 부재 때문에 차이는
줄어들 뿐 사라지지 않는다는 한 마디를 붙이면 비용 모델을 이해했다는
신호가 된다.

### "`Using index`와 `Using index condition`은 뭐가 다른가요?"

`Using index`는 **커버링** — 쿼리가 쓰는 컬럼이 전부 인덱스에 있어
테이블 접근이 0회다. `Using index condition`은 **ICP** — 인덱스 컬럼으로
된 조건 중 탐색에는 못 쓰는 것(범위 뒤 컬럼, 선행 와일드카드 LIKE 등)을
스토리지 엔진이 **룩업 전에 인덱스 엔트리에서 평가**해, 탈락한 행의
룩업을 건너뛴다. 즉 전자는 테이블 접근을 **없애고**, 후자는 테이블 접근
**횟수를 줄인다.** 커버링이 성립하면 룩업이 없으니 ICP가 나올 자리가
없고 `Using index`만 뜬다. 예시로 `(last_name, first_name)` 인덱스에
`last_name = 'Kim' AND first_name LIKE '%수%'`를 들면 — `SELECT *`면 ICP,
`SELECT id, first_name`이면 커버링이라는 대비까지 말한다.

### "JPA 엔티티 조회는 `SELECT *`인데, 그러면 커버링 인덱스를 못 쓰나요?"

엔티티 조회로는 못 쓴다 — 모든 컬럼을 SELECT하므로 어떤 인덱스로도
덮이지 않는다. 방법은 둘이다. ⑴ **DTO 프로젝션**(인터페이스 프로젝션,
`select new`, QueryDSL `Projections`)으로 SELECT 목록을 필요한 컬럼만으로
고정한다. ⑵ 행 전체가 정말 필요하면 **지연 조인(deferred join)** — 커버링
인덱스로 **PK만 먼저** 뽑고, 살아남은 PK로만 행을 가져온다.

```sql
SELECT o.*
FROM orders o
JOIN (SELECT id FROM orders                      -- id(PK)는 세컨더리 리프에 있으므로
      WHERE user_id = 7                          -- (user_id, created_at)만으로 커버링
      ORDER BY created_at DESC
      LIMIT 20 OFFSET 100000) t ON o.id = t.id;  -- 버리는 10만 건에는 룩업이 없고,
                                                 -- 살아남은 20건만 PK로 룩업
```

깊은 페이지네이션에서 `OFFSET`이 버리는 행에 대해서도 룩업을 다 하던
비용을 없애는 표준 기법이고, JPA에서는 "PK 목록 조회 → `findAllById`"
2단계로 같은 효과를 낸다. (가산점 포인트 — 이 기법이 성립하는 근거가
바로 "InnoDB 세컨더리 리프에는 PK가 공짜로 들어 있다"는 §1-1이다.)

### "커버링 인덱스는 항상 이득인가요? 만들지 말아야 할 때는 언제죠?" (시니어 변별 포인트)

아니다. 이득은 `절감 룩업 횟수 × 랜덤 I/O 비용 × 호출 빈도 − 인덱스 폭
비용`이므로, 앞이 작거나 뒤가 크면 손해다. 만들지 말아야 할 때는 —
⑴ **실을 컬럼이 자주 UPDATE될 때**: 실은 순간부터 그 UPDATE마다 세컨더리
엔트리 삭제+삽입이 붙어, 읽기에서 번 것을 쓰기에서 도로 낸다.
⑵ **컬럼이 넓거나 많을 때**: 엔트리 비대 → 페이지당 엔트리↓ → 버퍼 풀
적재율↓로 다른 인덱스까지 밀어내고, TEXT/BLOB이나 키 길이 상한에 걸리면
애초에 불가. ⑶ **호출이 드물거나 대상이 1~2건일 때**: 절감분이 없다.
⑷ **쿼리 모양이 자주 바뀌는 화면일 때**: 컬럼 추가로 조용히 깨지는
취약성을 감당할 안전망(프로젝션 고정 + EXPLAIN 테스트)이 없다면 만들지
않는 게 낫다. 즉 답은 "많이·좁게·자주 읽히고, 거의 안 바뀌는 컬럼만
싣고, 깨짐을 테스트가 잡아주는 조건에서만 만든다"이고, 그 판단 근거를
**EXPLAIN 전후 비교와 실제 지연 측정**으로 남기는 것까지가 세트다.

### "`SELECT COUNT(*) FROM orders`가 PK가 아니라 엉뚱한 세컨더리 인덱스를 타던데, 왜 그런가요?" (가산점 포인트)

`COUNT(*)`는 어떤 컬럼 값도 필요 없어 **모든 인덱스가 그 쿼리에 대해
커버링**이다. 그러면 남는 기준은 "어느 트리가 가장 좁아서 페이지 수가
적은가"뿐이고, InnoDB는 조건 없는 `COUNT(*)`를 **가장 작은 세컨더리
인덱스**를 훑어 처리한다 — 클러스터드 인덱스는 리프가 행 전체라 가장
넓기 때문이다. 이 현상을 설명할 수 있으면 "커버링 = 필요한 컬럼이
인덱스 안"이라는 정의를 극한(필요한 컬럼이 0개)까지 밀어 이해했다는
뜻이다. 덧붙여 PostgreSQL이라면 같은 Index Only Scan이라도 **visibility
map이 갱신돼 있어야** 힙 방문을 생략하므로, VACUUM 상태에 따라 같은
계획이 빠르기도 느리기도 하다는 점까지 말하면 저장 엔진별 차이를 안다는
신호가 된다.

## 한 줄 요약

**커버링 인덱스는 쿼리가 쓰는 모든 컬럼이 세컨더리 인덱스 안에 있어
북마크 룩업 — 행마다 PK 순으로 흩어진 페이지를 찌르는 랜덤 I/O — 이
0회가 된 상태이고, 그 랜덤 N장이 좁은 리프 N/수백 장의 순차 읽기로 바뀌는
것이 "몇 배"의 정체다. 효과는 "많이·좁게·자주·세기·정렬" 쿼리에서 크고,
대가는 폭(버퍼 풀 적재율↓)·쓰기(실은 컬럼 UPDATE마다 갱신)·취약(컬럼
추가로 조용히 깨짐)·상한이며, 그 깨짐은 사람의 기억이 아니라 프로젝션 ·
EXPLAIN 단정 테스트 · 마이그레이션 주석 · `rows_examined` 알림이 잡게
한다. `Using index`는 커버링, `Using index condition`은 룩업을 줄일 뿐인
ICP다.**
