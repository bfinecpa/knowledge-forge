# 초고빈도 카운터와 핫 로우 — PostgreSQL에서는 "행 하나에 줄 서기"에 "죽은 튜플 폭증"이 겹친다

> 핵심 관전 포인트: **조회수 +1을 조회 트랜잭션 안에서 같은 행에 UPDATE하면, 그 행의 락(PostgreSQL에서는 튜플 헤더 `xmax`에 기록되는 XID)이 커밋까지 유지되므로 수천 개의 "동시" 요청이 한 줄로 서서 직렬화된다 — 그 행의 초당 갱신 상한은 정확히 `1 / 락 보유 시간`이고, 서버를 늘려도 이 벽은 1밀리미터도 안 움직인다. 게다가 PostgreSQL에는 락 대기 기본 타임아웃이 없어(`lock_timeout` 기본 0) 줄은 끊기지 않고 자란다. 줄 선 트랜잭션은 커넥션(= OS 프로세스 하나)을 쥔 채 기다리므로 풀이 고갈되고, 조회수와 무관한 로그인·결제 API까지 커넥션을 못 얻어 장애가 된다. 그리고 PostgreSQL에서는 락 뒤에 두 번째 사슬이 따라온다 — UPDATE는 제자리 수정이 아니라 새 튜플 버전을 만드는 일이라, 초당 수천 번 갱신되는 행 하나가 죽은 튜플을 그 페이지에 쌓고, 페이지 여유가 마르면 HOT(인덱스를 안 건드리는 업데이트)이 깨져 모든 인덱스에 새 엔트리가 꽂히며, autovacuum은 이 속도를 따라잡지 못해 블로트가 남고 결국 읽기까지 느려진다. 설계의 출발점은 기술이 아니라 도메인 판단이다 — 갈림길은 딱 하나, "이 숫자는 얼마나 정확해야 하는가". 재고·잔액처럼 정확해야 하는 숫자는 원자적 UPDATE와 DB 제약이 최종 보증이어야 하고 버퍼링은 선택지에서 빠진다. 웹툰 조회수처럼 대략 맞으면 되는 숫자는 쓰기 지점을 행에서 떼어낸다 — 행 샤딩, 배치 집계, Redis `INCR` 버퍼 + 주기 반영. 그리고 유실을 "허용"했다면 반드시 유실을 "측정"해야 한다 — 멱등한 flush, 원천 로그 대비 대사(reconciliation) 배치, 드리프트 알람까지가 한 세트다.**

## 0. 질문 + 의도

**질문**: "웹툰 에피소드 조회수 같은 초고빈도 카운터 갱신을 RDB에 직접 하면 어떤 문제가 있나요? 어떻게 설계하겠습니까?"

**출제 의도**: rationale은 이렇게 적고 있다 — "같은 행 UPDATE의 락 직렬화라는 병목을 인식하고, 버퍼링·배치 반영·근사치 허용 같은 완화책과 그 대가(실시간성, 유실 가능성)를 비즈니스와 협상하는 능력. 웹툰 조회수는 정확히 이 문제라 도메인 적합성 검증이기도 하다." 즉 이 문항은 세 가지를 동시에 잰다. ① 문제를 "성능 저하"가 아니라 **이름 붙은 메커니즘 사슬**로 말할 수 있는가 ② 완화책 하나하나의 **대가를 같은 호흡에** 붙일 수 있는가 ③ "이 숫자는 얼마나 정확해야 하는가"라는 **도메인 판단**에서 설계를 출발시키는가. 고난이도 문항은 트레이드오프 서술 자체가 채점 대상이라, 완화책을 나열만 하고 대가를 안 붙이면 중급 답변으로 내려간다. 여기에 PostgreSQL을 쓰고 있다면 한 축이 더 붙는다 — **"같은 문제가 이 엔진에서는 왜 더 나쁜가"**를 저장 구조(MVCC·HOT·VACUUM)에서 도출할 수 있는가.

> 이 문서는 사전 학습용이다. 4장 기본 Q4에서 핫 로우 질문에 "성능 저하"로 뭉뚱그린 뒤 힌트를 받고서야 "락 경합"이라는 **이름 하나에만 도달**했고, 락 경합 이후의 사슬은 면접관이 보충했다. 그래서 이 문서는 §1에서 **락 경합 "다음"에 무슨 일이 이어지는지**를 두 갈래(동시성 사슬 / 쓰기 증폭 사슬)로 가장 자세히 다루고, §2에서 **"이 숫자는 얼마나 정확해야 하는가"라는 갈림길을 먼저 세운 뒤** 갈래별 처방을 배치하며, §3에서 "유실 허용"을 "유실 측정"으로 닫는 안전망을 코드로 보여 준다.

> 다른 문서와의 경계. [`04-normalization-vs-denormalization.md`](04-normalization-vs-denormalization.md)와 [`11-mvcc-postgresql.md`](11-mvcc-postgresql.md)는 핫 로우 사슬을 짧게 언급하며 이 문서를 가리킨다 — 여기가 그 주제의 본거지다. 반대로 낙관적 락·비관적 락·재시도 같은 **애플리케이션 쪽 동시성 선택지**는 3장 [`20-concurrency-update-four-approaches.md`](../03-jpa-orm/20-concurrency-update-four-approaches.md)가 맡으므로 여기서는 반복하지 않고 참조만 한다. 이 문서의 초점은 **DB 안에서 벌어지는 사슬**과 **카운터 자체의 설계**다.

## 1. 문제 — 같은 행 UPDATE 하나가 어떻게 전 서비스 장애가 되나

### 1-1. before — 조회 API 안의 `@Transactional` + 더티 체킹

가장 흔한 첫 구현이다. 에피소드를 읽어서 응답을 만들고, 그 김에 조회수도 1 올린다. 코드만 보면 흠잡을 데가 없다.

```java
// before — 조회 트랜잭션이 곧 쓰기 트랜잭션이다
@Service
@RequiredArgsConstructor
public class EpisodeService {

    private final EpisodeRepository episodeRepository;

    @Transactional                                   // ① 쓰기 트랜잭션 — 커넥션(= PostgreSQL 백엔드 프로세스)을 빌린다
    public EpisodeResponse view(Long episodeId) {
        Episode episode = episodeRepository.findById(episodeId).orElseThrow();  // ② SELECT (스냅샷 읽기)
        episode.increaseViewCount();                 // ③ 자바에서 view_count = 읽은 값 + 1
        return EpisodeResponse.from(episode);        // ④ 이미지 URL 목록 등 응답 조립 (지연 로딩이 끼면 더 길어진다)
    }   // ⑤ 커밋 직전 flush → UPDATE episode SET view_count = $1, ... WHERE id = $2
        //    → 옛 튜플 xmax에 내 XID 기록(= 행 락) + 새 튜플 버전 삽입 → WAL 기록
        //    → 커밋(WAL fsync) → 락 해제
}
```

이 코드에는 성격이 다른 문제가 **세 겹**으로 겹쳐 있다. 셋을 구분하지 못하면 "원자적 UPDATE로 바꿨으니 해결"이라는 오답으로 간다.

**첫째, lost update(갱신 손실).** 용어부터 정의한다. lost update란 두 트랜잭션이 같은 값을 읽고 각자 계산해서 쓸 때, 나중에 쓴 쪽이 앞선 쪽의 갱신을 덮어써서 그 증가분이 사라지는 현상이다. 위 코드에서 ②는 스냅샷을 읽고 ③은 자바에서 더한다. 같은 순간 100을 읽은 두 트랜잭션이 각각 101을 쓴다 — 두 번 조회했는데 조회수는 1만 늘었다. **락은 "덮어쓰는 순서"만 정해 줄 뿐 "네가 읽은 값이 이미 낡았다"는 사실은 알려 주지 않는다.** 그래서 아무 예외도 안 난다.

> PostgreSQL 기본 격리 수준인 READ COMMITTED에서 위와 같이 조용히 사라진다. REPEATABLE READ 이상이면 두 번째 트랜잭션이 조용히 덮어쓰는 대신 `ERROR: 40001 could not serialize access due to concurrent update`로 터진다 — 값은 지켜지지만 재시도 코드가 없으면 요청이 실패한다. 즉 격리 수준을 올리는 것은 "문제를 없애는" 게 아니라 "문제를 조용한 손실에서 시끄러운 실패로 바꾸는" 선택이다.

**둘째, 조회 트랜잭션이 쓰기 트랜잭션이 된다.** 쓰기가 섞였으므로 `readOnly = true`를 붙일 수 없고, 붙일 수 없으니 리드 리플리카(hot standby)로 라우팅할 수 없다([리드 리플리카 라우팅](../03-jpa-orm/23-read-replica-routing-and-lag.md)). 스탠바이는 읽기 전용이라 쓰기 트랜잭션을 아예 못 받기 때문이다. **조회수 한 줄 때문에 모든 에피소드 조회가 프라이머리로 몰리고, 읽기 분산 구조 전체가 무력화된다.**

**셋째, 핫 로우(hot row).** 신작 공개 직후에는 특정 에피소드 하나에 조회가 집중된다. 수천 개 요청이 전부 **같은 행 하나**를 UPDATE한다. 셋 중 장애를 만드는 것은 이것이고, 아래에서 두 갈래로 쪼갠다.

### 1-2. 사슬 A — 동시성: 행 락 하나에서 무관한 API 장애까지

"락 경합"은 사슬의 **첫 고리 이름**이지 설명이 아니다. 고리를 하나씩 끊어서 말할 수 있어야 한다.

```text
⑴ 같은 행 UPDATE
   모든 요청이 episode.id = 신작 1화, 단 하나의 행을 갱신한다.
      ↓
⑵ 행 락 직렬화
   PostgreSQL의 UPDATE는 옛 튜플 헤더의 xmax에 자기 XID를 적는다 — 이것이 곧 행 락이다.
   별도의 락 테이블이 아니라 데이터 자체에 적으므로, "잠글 행이 너무 많아서 락을
   테이블 단위로 승격한다"는 락 에스컬레이션이 PostgreSQL에는 없다.
   뒤에 온 트랜잭션은 그 xmax가 가리키는 XID가 끝나기를 기다린다.
     - pg_locks          : transactionid 락
     - pg_stat_activity  : wait_event_type = 'Lock', wait_event = 'transactionid'
   한 번에 하나만 통과하므로 그 행에 대한 동시성이 1로 붕괴한다.
      ↓
⑶ 락 대기 큐 적체 — PostgreSQL에는 자동 안전판이 없다
   벽을 넘는 요청은 그대로 줄을 선다. PostgreSQL은 락 대기에 기본 타임아웃이 없다
   (lock_timeout 기본 0 = 무한 대기). MySQL/InnoDB의 innodb_lock_wait_timeout 같은
   "50초 지나면 실패" 안전판이 없으므로, 명시적으로 설정하기 전까지 요청은
   실패하지도 않고 끝없이 기다린다 — 실패가 없으니 더 위험하다.
   deadlock_timeout(기본 1초)은 "데드락인지 검사하는 시점"일 뿐 대기 상한이 아니다.
   log_lock_waits = on 이면 그 시점을 넘긴 대기가 서버 로그에 남는다.
      ↓
⑷ 트랜잭션 지연 — 대기가 대기를 키운다
   줄 뒤의 트랜잭션은 앞선 전원의 락 보유 시간을 합친 만큼 늦어진다.
   그리고 자기가 잡은 다른 락도 그만큼 오래 쥔다. 지연이 지연을 낳는다.
   덤으로 이 오래 열린 트랜잭션들이 VACUUM을 막아 사슬 B를 악화시킨다(⑻).
      ↓
⑸ 커넥션 점유 — 여기가 "행 하나"와 "서비스 전체"를 잇는 다리다
   락을 기다리는 트랜잭션은 DB 커넥션을 "쥔 채로" 기다린다. PostgreSQL에서
   커넥션 하나는 OS 프로세스 하나이므로, 대기 중인 백엔드 프로세스가 메모리를
   차지한 채 아무 일도 안 하며 풀의 한 자리를 막는다.
      ↓
⑹ 커넥션 풀 고갈
   풀 크기(예: 20)만큼의 트랜잭션이 전부 같은 행을 기다리면 풀은 "일은 안 하는데
   꽉 찬" 상태가 된다. HikariCP의 getConnection()이 connection-timeout(기본 30초)까지
   대기하다 SQLTransientConnectionException 으로 터진다.
   "풀을 키우자"도 답이 아니다 — max_connections 기본값은 100이고, 프로세스 모델이라
   커넥션을 늘리면 메모리와 스냅샷 경합이 같이 늘어난다(→ 15-connection-count-vs-throughput.md).
      ↓
⑺ 무관한 API 장애 (전파)
   커넥션 풀은 서비스 전체가 공유한다. 로그인, 결제, 다른 웹툰 목록 조회 —
   조회수와 아무 상관없는 요청이 커넥션을 못 얻어 타임아웃된다.
   톰캣 스레드까지 커넥션 대기에 묶이면 헬스체크마저 실패해 인스턴스가 교체되기 시작하고,
   교체된 인스턴스가 다시 같은 행에 몰려들어 상황이 반복된다.
      ↓
⑻ (PostgreSQL 추가 고리) VACUUM 방해 → 블로트
   길어진 트랜잭션들이 각자 backend_xmin(자기가 아직 볼 수 있어야 하는 가장 오래된 XID)을
   잡고 있으면, autovacuum은 그 시점 이후의 죽은 튜플을 회수하지 못한다.
   사슬 B가 만든 죽은 튜플이 치워지지 않고 쌓인다.
```

⑵에서 ⑺까지를 한 문장으로 묶으면 — **행 하나의 락이 서비스 전체의 동시성을 1로 만든다.** 병목이 CPU도 디스크도 아니고 "행 하나"라서 인프라 증설이 통하지 않는다는 점이 이 사슬의 핵심이다.

⑸ 이후는 4장 [`15-connection-count-vs-throughput.md`](15-connection-count-vs-throughput.md)와 2장 [`26-hikaricp-connection-pool-exhaustion.md`](../02-spring/26-hikaricp-connection-pool-exhaustion.md)에서 다룬 "대기 줄이 DB 안에 서면 비싸다"의 정확히 그 상황이다.

> **MySQL 대조:** InnoDB도 ⑵~⑺의 골격은 같지만 두 가지가 다르다. ① InnoDB는 `innodb_lock_wait_timeout`(기본 50초)이 있어 무한 대기가 자동으로 끊기는 반면, PostgreSQL은 `lock_timeout`을 직접 걸어야 한다. ② InnoDB의 락은 메모리의 락 테이블 구조라 대상 행이 많으면 관리 비용이 붙지만, PostgreSQL은 락을 튜플 헤더에 적으므로 행 수 자체는 문제가 안 된다 — 대신 그 "적는 행위"가 곧 새 튜플 버전이라 사슬 B가 무거워진다.

### 1-3. 벽의 높이를 직접 계산한다 — 왜 서버를 늘려도 안 되는가

사슬 A의 ⑵를 숫자로 만들어야 "성능 저하"에서 "상한이 얼마"로 넘어간다. 계산은 한 줄이다.

```text
  그 행의 초당 갱신 상한  ≈  1 ÷ (한 트랜잭션이 그 행의 락을 쥐고 있는 시간)
```

왜 이 공식이 성립하는가. **행 락은 UPDATE를 실행하는 순간 잡히고, 트랜잭션이 커밋(또는 롤백)될 때 풀린다.** 그 사이에는 누구도 그 행을 갱신하지 못한다. 그러니 그 행의 갱신은 "락 보유 시간"을 한 칸으로 하는 컨베이어 벨트 위를 지나가는 셈이고, 1초 동안 벨트를 지나갈 수 있는 개수는 `1초 ÷ 한 칸의 길이`다.

그러면 락 보유 시간은 무엇으로 이루어지는가. 여기가 실무에서 중요한 부분이다.

| 구성 요소 | 대략의 크기 | 설명 |
|---|---|---|
| UPDATE 실행 자체 | 수십 마이크로초 | 힙 페이지에 새 튜플을 쓰는 메모리 작업. 가장 싸다 |
| 커밋 시 WAL fsync | 0.1ms(로컬 NVMe) ~ 5ms(네트워크 스토리지) | 보통 여기가 지배적이다 |
| 앱과 DB 사이 네트워크 왕복 | 왕복당 0.2~0.5ms (같은 AZ 기준) | UPDATE 문에 한 번, COMMIT에 한 번 |
| **UPDATE 이후 트랜잭션 안에서 하는 모든 일** | 제한 없음 | 응답 조립, 지연 로딩 추가 쿼리, 외부 API 호출. **전부 락 보유 시간에 들어간다** |

마지막 줄이 1-1의 before 코드가 나쁜 진짜 이유다. `episode.increaseViewCount()`가 만든 UPDATE는 커밋 직전에 flush되긴 하지만, 더티 체킹 방식에서는 flush 시점이 프레임워크 손에 있어 통제하기 어렵고, 무엇보다 **트랜잭션을 길게 잡는 습관 자체가 락 보유 시간을 늘린다.**

숫자를 대입해 보면 벽의 높이가 보인다.

| 락 보유 시간 | 그 행의 초당 갱신 상한 | 어떤 상황인가 |
|---|---|---|
| 0.5ms | **2,000건/초** | UPDATE 한 문장만 던지고 즉시 커밋, 로컬 NVMe |
| 2ms | **500건/초** | 일반적인 매니지드 PostgreSQL + 네트워크 왕복 포함 |
| 10ms | **100건/초** | UPDATE 뒤에 응답 조립·지연 로딩이 남아 있는 트랜잭션 |
| 100ms | **10건/초** | UPDATE 뒤에 외부 API 호출이 들어간 트랜잭션 |

(계산은 그대로다. `1 ÷ 0.0005초 = 2,000`, `1 ÷ 0.002초 = 500`, `1 ÷ 0.01초 = 100`, `1 ÷ 0.1초 = 10`.)

**이 벽이 왜 서버 증설로 안 뚫리는지**를 이어서 말해야 한다. 앱 서버를 10대에서 100대로 늘리면 DB에 도착하는 요청은 10배가 되지만, 그 요청들이 통과해야 하는 문은 여전히 **행 하나의 락 하나**다. 문의 폭이 안 늘어나므로 처리량은 그대로고, 늘어난 것은 문 앞에 선 줄의 길이뿐이다. 병목이 자원(CPU·디스크·네트워크)이 아니라 **직렬화 지점**일 때 수평 확장이 무력한 것이 이 사슬의 본질이다.

줄이 길어지면 어떻게 되는지도 숫자로 이어 본다. 락 보유 2ms(상한 500건/초)인 상황에 초당 5,000건이 들어온다고 하자.

```text
 초당 도착 5,000건        초당 통과 500건       →  초당 4,500건이 어딘가에서 밀린다
        │                        │
        └──────────┬─────────────┘
                   ↓
  그런데 "줄"은 두 군데에 선다. 이걸 구분하는 것이 진단의 핵심이다.

  [줄 1] DB 안의 락 대기 줄
     커넥션을 이미 얻은 트랜잭션만 여기 설 수 있다. 풀 크기가 20이면 최대 20개.
     20번째 요청의 대기 시간 = 앞선 19개의 락 보유 시간 합 = 19 x 2ms ≈ 38ms.
     여기까지는 "조금 느린" 정도다.

  [줄 2] 커넥션 풀 대기 줄  ←  실제 장애는 여기서 난다
     풀 20개가 전부 [줄 1]에 들어가 있으므로, 나머지 요청은 커넥션 자체를 못 얻는다.
     그리고 이 줄에는 조회수 요청만 서는 게 아니다.
     로그인도, 결제도, 상품 목록도 같은 풀을 쓰므로 전부 여기 선다.
     HikariCP connection-timeout 30초를 다 기다린 뒤 예외로 터진다.
     그 30초 동안 톰캣 스레드도 한 자리씩 묶여 있으므로, 스레드 풀도 같이 마른다.

  결론: "조회수 UPDATE가 커넥션 풀 20개를 전부 점유한다"는 한 문장이
        행 하나의 문제와 전 서비스 장애를 잇는 다리다.
```

### 1-4. 사슬 B — 쓰기 증폭: PostgreSQL의 UPDATE는 "고치기"가 아니라 "다시 쓰기"다

락이 없다고 가정해도 — 예를 들어 샤딩 카운터로 경합을 완전히 나눴다고 해도 — 남는 비용이 있다. 이 갈래를 따로 세우는 이유가 그것이다.

전제부터. "조회수 +1"은 논리적으로 8바이트 하나를 고치는 일이다. 그러나 PostgreSQL에서 UPDATE는 **제자리 수정이 아니다.** 옛 튜플에 `xmax`를 찍어 "이 XID가 지웠다"고 표시하고, 바뀐 값이 담긴 **새 튜플 버전을 삽입**한다([MVCC](11-mvcc-postgresql.md)). 옛 버전은 별도 공간이 아니라 **같은 힙 페이지 안에 그대로 남아** VACUUM을 기다린다. 이 한 문장에서 아래 고리가 전부 나온다.

```text
UPDATE episode SET view_count = view_count + 1 WHERE id = $1   (초당 N번)
  │
  ├─ ⓐ 죽은 튜플 폭증
  │     갱신 한 번 = 죽은 튜플 하나. 초당 5,000건이면 그 행이 사는 8KB 페이지에
  │     초당 5,000개의 옛 버전이 쌓인다. 옛 버전은 MySQL의 언두 세그먼트 같은
  │     별도 공간이 아니라 힙 페이지 안에 그대로 남는다.
  │
  ├─ ⓑ HOT이냐 아니냐가 비용을 가른다
  │     HOT(Heap-Only Tuple) 업데이트 = "인덱스를 하나도 안 건드리는 업데이트".
  │     성립 조건은 둘: ① 바뀌는 컬럼이 어떤 인덱스에도 들어 있지 않을 것
  │                     ② 같은 페이지에 새 버전을 놓을 자리가 있을 것.
  │     성립하면 인덱스는 여전히 옛 튜플을 가리키고, 페이지 안의 포인터 사슬이
  │     최신 버전으로 안내한다 — 인덱스 쓰기 0회.
  │     조건이 깨지면 새 튜플이 다른 TID(물리 주소)를 받으므로 그 테이블의
  │     모든 인덱스에 새 엔트리를 꽂는다 — 인덱스 5개면 갱신 한 번에 쓰기 5번,
  │     초당 5,000건이면 초당 25,000번이다.
  │
  ├─ ⓒ 페이지 여유 소진
  │     힙의 기본 fillfactor는 100이라 페이지에 남는 자리가 별로 없다.
  │     HOT 프루닝(그 페이지를 지나가는 쿼리가 죽은 튜플 자리를 회수하는 동작)이
  │     따라와 주면 같은 페이지 안에서 계속 돌 수 있지만, 갱신 속도가 프루닝을
  │     넘어서면 새 버전이 다른 페이지로 밀려나고 그 순간 HOT이 깨진다(→ ⓑ).
  │
  ├─ ⓓ VACUUM 추격 실패
  │     죽은 튜플을 실제로 회수하는 것은 autovacuum인데 구조적으로 느리다.
  │       ① 테이블당 한 번에 워커 하나  ② 주기적으로 깨어나 시작
  │       ③ vacuum_cost_delay 로 I/O를 스로틀
  │     그래서 "초당 수천 개 생산"을 따라잡지 못한다. 게다가 사슬 A ⑻처럼
  │     오래 열린 트랜잭션이 하나만 있어도 회수 자체가 금지된다.
  │     결과는 테이블 블로트: 논리적으로 1행인데 물리적으로 수십~수백 페이지.
  │
  ├─ ⓔ WAL
  │     변경마다 WAL 레코드를 쓰고 커밋마다 fsync 한다. 순차 쓰기라 싸지만
  │     "커밋 횟수 = fsync 횟수"다. 그룹 커밋이 여러 트랜잭션의 fsync를 묶어 주지만,
  │     같은 행은 직렬이라 같은 순간에 커밋할 상대가 없어 묶일 여지도 없다.
  │     full_page_writes 때문에 체크포인트 직후 첫 갱신에서는 그 페이지 전체(8KB)가
  │     통째로 WAL에 실린다.
  │
  ├─ ⓕ 인덱스 블로트
  │     ⓑ에서 비-HOT이 되면 인덱스에도 죽은 엔트리가 쌓인다.
  │     "인기순 정렬"용으로 view_count에 인덱스를 걸어뒀다면 매 갱신이 비-HOT 확정이다.
  │     인덱스 공간은 VACUUM이 "재사용 가능"하게 만들 뿐 파일 크기가 줄지는 않아,
  │     회복하려면 REINDEX CONCURRENTLY 가 필요하다.
  │
  ├─ ⓖ 읽기까지 느려진다
  │     블로트된 페이지 = 같은 행 하나를 읽는 데 더 많은 페이지를 읽는다는 뜻이다.
  │     visibility map(전부 보이는 페이지를 표시해 둔 비트맵)이 계속 더러워져
  │     다른 쿼리의 Index Only Scan이 힙 페치로 퇴화한다(Heap Fetches 증가).
  │
  └─ ⓗ 복제 지연
        스트리밍 복제는 standby가 WAL을 단일 프로세스로 순차 재생한다.
        같은 페이지를 반복 갱신하는 부하는 병렬화할 여지 자체가 없다
        → 지연 누적 → 리플리카에서 읽는 다른 화면이 낡은 데이터를 본다.
        반대로 hot_standby_feedback = on 이면 standby의 롱 쿼리가 프라이머리의
        VACUUM을 막아 ⓓ의 블로트를 프라이머리로 되돌린다.
```

**PostgreSQL에서 이 사슬이 더 나쁜 이유를 한 문장으로** 말하면 이렇다. MySQL/InnoDB는 행을 제자리에서 고치고 옛 이미지를 언두 세그먼트에 따로 두므로 "테이블 자체"는 부풀지 않지만, PostgreSQL은 옛 버전이 **테이블 안에 남기 때문에 핫 로우가 곧 테이블 블로트다.**

그 대신 PostgreSQL에는 MySQL/InnoDB에 없는 완충 장치가 하나 있다 — **HOT 업데이트**다. 그래서 "카운터 컬럼에 인덱스를 걸지 않고, `fillfactor`를 낮춰 페이지에 여유를 준다"는 PostgreSQL 전용 손잡이가 생기고, 이것이 §2-3의 공통 위생 첫 줄로 등장한다.

> **MySQL 대조:** InnoDB에서 같은 자리에 있던 고리는 ⓐ 언두 로그 체인 증가(긴 조회 트랜잭션이 있으면 purge가 못 지워 버전 체인 순회 비용 증가), ⓑ redo 로그 fsync, ⓒ binlog 이벤트(`sync_binlog=1`이면 또 fsync), ⓓ 세컨더리 인덱스 엔트리 delete-mark + 재삽입이다. 이름과 위치가 다를 뿐 "커밋 횟수가 곧 비용"이라는 결론은 같고, **테이블이 부푸느냐(PostgreSQL) 언두가 부푸느냐(InnoDB)**가 갈린다.

이 갈래를 따로 세운 것이 중요한 이유는, **§2의 전략을 평가하는 기준**이 되기 때문이다.

| 전략 | 사슬 A (경합) | 사슬 B (쓰기·죽은 튜플 총량) |
|---|---|---|
| 원자적 UPDATE | 락 보유 시간만 조금 줄임 | 그대로 |
| 행 샤딩 카운터 | **1/N로 완화** | **한 고리도 안 줄어든다** |
| Redis 버퍼 + 주기 반영 | **거의 소멸** | **거의 소멸** |

이 차이를 말할 수 있으면 "전략을 아는 것"에서 "전략의 비용 구조를 아는 것"으로 올라간다.

### 1-5. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

| 뭉뚱그린 표현 | 사슬로 말하면 |
|---|---|
| "성능이 저하된다" | 같은 행 락(`xmax`)에 직렬화 → 초당 상한 = 1 / 락 보유 시간 → 서버 증설 무효 |
| "락 경합이 일어난다" | 락 대기 큐 적체(`lock_timeout` 기본 무한) → 지연 → **커넥션을 쥔 채 대기** → 풀 고갈 |
| "다른 요청도 느려진다" | 풀은 전 서비스 공유 → 로그인·결제까지 커넥션 획득 타임아웃 → 전파 |
| "DB에 부하가 간다" | UPDATE마다 새 튜플 버전 → 죽은 튜플 → HOT 탈락 시 모든 인덱스 갱신 → VACUUM 추격 실패 → 블로트 → 읽기까지 느려짐 |

면접에서 "락 경합"까지 말했다면 그 다음 문장은 반드시 **"그 락을 기다리는 트랜잭션이 커넥션을 쥐고 있어서"**여야 한다. 이 한 문장이 행 하나의 문제와 서비스 전체 장애를 잇는 다리다. PostgreSQL이라면 한 문장 더 — **"게다가 그 UPDATE 하나하나가 죽은 튜플을 만들어서"**가 사슬 B의 입구다.

### 1-6. 원자적 UPDATE로 바꾸면? — 정확성은 잡히고 경합은 남는다

3장 [`20-concurrency-update-four-approaches.md`](../03-jpa-orm/20-concurrency-update-four-approaches.md)의 결론대로, "읽고 계산하고 쓰기"를 SQL 한 문장으로 압축할 수 있으면 원자적 UPDATE가 기본값이다. 여기서도 첫 번째 개선은 그것이다.

```java
// 개선 1단계 — lost update 제거. 그러나 핫 로우 사슬은 그대로다
public interface EpisodeRepository extends JpaRepository<Episode, Long> {
    @Modifying(clearAutomatically = true)   // 벌크 UPDATE는 영속성 컨텍스트를 우회하므로,
                                            // 같은 트랜잭션에 남아 있는 낡은 엔티티를 비운다
    @Query("update Episode e set e.viewCount = e.viewCount + 1 where e.id = :id")
    int increaseViewCount(@Param("id") Long id);
}
```

얻는 것은 두 가지다. 첫째, 값을 자바로 가져와 계산하지 않고 **DB가 현재 값 기준으로 더하므로** lost update가 사라진다. 둘째, SELECT 후 자바 계산 단계가 없어 **락 보유 시간이 짧아진다** — 1-3의 표에서 아래 칸에서 위 칸으로 올라가는 것이라 상한 자체는 조금 올라간다.

> **(가산점 포인트) 왜 PostgreSQL에서 이게 안전한가.** READ COMMITTED에서 UPDATE가 이미 잠긴 행을 만나면, 앞 트랜잭션이 끝나기를 기다렸다가 **그 최신 버전으로 조건과 식을 다시 평가한다.** 이 동작에 EvalPlanQual이라는 이름이 붙어 있다. 그래서 `view_count = view_count + 1`은 대기 후 "갱신된 값 + 1"이 되어 증가분이 사라지지 않는다. 반대로 REPEATABLE READ 이상에서는 재평가 대신 `40001`로 abort하므로, 격리 수준을 올려 둔 서비스라면 **재시도 코드가 없는 원자적 UPDATE는 오히려 실패한다.** "원자적 UPDATE는 어디서나 안전하다"가 아니라 "격리 수준에 따라 안전한 방식이 다르다"가 정확한 서술이다.

그러나 초당 수천 요청이 **여전히 같은 행의 락을 순서대로 잡는다.** 사슬 A의 ⑵~⑻과 사슬 B는 한 고리도 사라지지 않는다. "원자적 UPDATE로 해결했다"고 답하면 **lost update와 핫 로우를 구분하지 못하는 것**으로 읽힌다. 원자적 UPDATE는 **위생**이지 **처방**이 아니다.

### 1-7. 진단 — 핫 로우가 실제로 있는지 확인하는 세 쿼리

"느리다"에서 "이 행이 핫하다"로 넘어가려면 숫자가 있어야 한다. 그리고 §2-9에서 말하겠지만, **측정 없이 버퍼링을 도입하면 과설계다.** 그래서 진단이 설계보다 앞에 온다.

```sql
-- ① 지금 누가 누구를 막고 있나 (핫 로우라면 blocking_pid 하나에 수십 개가 매달린다)
SELECT pid, state, wait_event_type, wait_event,
       pg_blocking_pids(pid) AS blocked_by,      -- 나를 막고 있는 프로세스 목록
       now() - xact_start AS tx_age, left(query, 60) AS q
  FROM pg_stat_activity
 WHERE wait_event_type = 'Lock'
 ORDER BY tx_age DESC;
-- wait_event = 'transactionid' 가 줄줄이 보이면 "같은 행을 기다리는 중"이다.
-- blocked_by 열의 값이 전부 같은 pid 하나를 가리키면 그것이 핫 로우의 서명이다.

-- ② HOT 비율 — 갱신 대비 HOT 갱신이 낮으면 매 UPDATE가 모든 인덱스를 건드리고 있다
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct,
       n_live_tup, n_dead_tup, last_autovacuum
  FROM pg_stat_user_tables
 WHERE relname = 'episode';
-- hot_pct 가 낮다(예: 10% 미만) → 카운터 컬럼에 인덱스가 걸렸거나 페이지 여유가 없다.
-- n_dead_tup 이 n_live_tup 을 자릿수로 넘는다 → VACUUM이 추격에 실패하고 있다.

-- ③ 블로트 감각 — 행 몇 개짜리 테이블이 왜 이렇게 큰가
SELECT pg_size_pretty(pg_table_size('episode'))   AS heap,
       pg_size_pretty(pg_indexes_size('episode')) AS idx,
       (SELECT reltuples::bigint FROM pg_class WHERE oid = 'episode'::regclass) AS est_rows;
-- 예상 행 수 대비 heap 크기가 자릿수로 크면 블로트다.
```

②의 `hot_pct`와 `n_dead_tup`가 이 문서의 사슬 B를 그대로 계량한 숫자다. "핫 로우 문제인 것 같다"가 아니라 이 세 값을 들고 말하면 진단이 된다.

## 2. 설계 — 판단 기준부터: 이 숫자는 얼마나 정확해야 하는가

### 2-1. 먼저 갈라야 할 질문 — 기술 선택보다 앞에 있는 것

전략 목록부터 꺼내는 답변은 대개 감점된다. 같은 "카운터 갱신"인데도 **처방이 정반대로 갈리는 갈림길**이 앞에 있기 때문이다. 그 갈림길을 세우지 않고 Redis를 꺼내면, 면접관이 "그럼 잔액도 그렇게 하시겠어요?"로 즉시 무너뜨릴 수 있다.

갈림길을 만드는 축은 셋이다 — **정확도, 실시간성, 비용.** 셋을 동시에 최대로 가질 수는 없고, 어느 것을 얼마나 양보할지는 엔지니어가 혼자 정하는 게 아니라 **비즈니스와 협상**하는 것이다. 이 협상을 해 봤는지가 rationale이 말하는 "도메인 적합성 검증"이다.

세 축을 실제로 판단할 때 던지는 질문은 이렇게 생겼다.

- **틀려도 되는가.** 조회수가 1,000,352인지 1,000,340인지는 독자도 작가도 구분하지 못한다. 반면 잔액이 12원 비면 사고다. **유실을 허용할 수 없으면 버퍼링은 선택지에서 통째로 빠진다.**
- **늦어도 되는가.** 조회수는 1분 뒤에 반영돼도 아무도 모른다. 재고는 "지금 살 수 있는가"라서 지연이 곧 오버셀(재고보다 많이 파는 사고)이다.
- **DB가 지켜야 할 불변식이 있는가.** `잔액 >= 0`, `재고 >= 0` 같은 조건은 애플리케이션 관례가 아니라 DB 제약이 지켜야 한다. 이런 값은 진실이 DB 밖에 있으면 안 된다.
- **누가 대가를 지는가.** 유실·지연을 허용한 숫자는 "정확하지 않을 수 있다"는 사실을 비즈니스가 알고 승인해야 한다. 정산·수익 배분에 조회수가 쓰인다면 이야기가 달라진다 — 그때는 "화면에 보여 주는 조회수"와 "정산용 조회수"를 **분리**해서, 후자는 원천 로그에서 배치로 정확히 재계산한다.

이 질문들을 실제 숫자에 대 보면 표가 나온다.

| 숫자 | 정확도 요구 | 실시간성 요구 | 쓰기 양상 | 갈래 |
|---|---|---|---|---|
| 웹툰 조회수 | 근사 허용 — 0.1% 유실을 아무도 못 느낀다 | 분 단위면 충분 | 초고빈도, 특정 행 집중 | **B (대략)** |
| 좋아요 수 | 합계는 근사, "내가 눌렀는지"는 정확 | 개인 상태 즉시, 합계 지연 OK | 고빈도 | 개인 상태는 A, 합계는 B |
| 재고 | 정확 — `qty >= 0` 불변식 | 즉시 | 이벤트성 집중 | **A (정확)** |
| 결제 잔액 | 정확, 유실 0, 감사 추적 | 즉시 | 계정별로 분산 — 핫 로우 자체가 드묾 | **A (정확)** |

### 2-2. 갈림길 도식 — 갈래마다 처방이 완전히 다르다

```text
                   "이 숫자는 얼마나 정확해야 하는가?"
                                │
        ┌───────────────────────┴────────────────────────┐
        ↓                                                ↓
  [갈래 A] 정확해야 한다                        [갈래 B] 대략 맞으면 된다
  재고 · 잔액 · 쿠폰 수량                        조회수 · 좋아요 합계 · 노출수
  "1이 틀리면 사고"                              "0.1% 틀려도 아무도 모른다"
        │                                                │
        │ 원칙: 진실은 언제나 DB 안에 있고,               │ 원칙: 쓰기 지점을 그 행에서
        │       불변식은 DB 제약이 최종 보증한다.          │       떼어내 총량을 줄인다.
        ↓                                                ↓
  ① 원자적 UPDATE (읽고-계산-쓰기를 한 문장으로)     ① 행 샤딩 카운터
  ② CHECK 제약으로 불변식을 DB에 못 박기               (N행으로 쪼개 쓰고, 읽을 때 SUM)
  ③ 조건부 UPDATE + 영향 행 수로 실패 감지          ② 배치 집계
     (WHERE qty >= :n → 0행이면 재고 부족)             (append-only 로그에 INSERT →
  ④ 경합이 극단이면 Redis DECR "선점 게이트"           주기 배치가 GROUP BY로 집계)
     — 단 최종 확정은 여전히 DB 제약               ③ Redis INCR 버퍼 + 주기 반영
                                                     (DB 쓰기를 수천분의 1로)
        │                                                │
        │ 버퍼링 금지. 진실이 DB 밖으로 나가는            │ 유실 창이 생긴다.
        │ 순간 불변식을 지킬 방법이 사라진다.              │ → 그래서 §3의 "측정"이 필수다.
        ↓                                                ↓
  대가: 경합은 남는다. 처리량 상한을            대가: 유실 · 지연 · 이중 소스 ·
        받아들이고 도메인을 쪼개거나                    인프라 의존 · 코드 복잡도
        대기열로 흡수한다.
```

**두 갈래가 공유하는 것은 §2-3의 위생뿐이고, 그 위는 갈라진다.** 이 그림을 먼저 그리고 시작하는 것이 이 문항의 골격이다.

### 2-3. 어느 갈래든 먼저 하는 공통 위생 세 가지

갈래를 정하기 전에도 무조건 하는 것이 셋 있다. 셋 다 비용이 거의 0이라 "할지 말지"를 고민할 대상이 아니다.

**위생 ① 물리 설계 (PostgreSQL 전용).** 사슬 B의 ⓑ·ⓒ를 직접 겨눈다. 카운터 컬럼이 **어떤 인덱스에도 들어 있지 않으면** 그 UPDATE는 HOT 후보가 되고, 페이지에 새 버전을 놓을 자리만 있으면 **인덱스를 하나도 안 건드린다.** 자리를 마련하는 손잡이가 `fillfactor`다 — 페이지를 몇 %까지만 채울지 정하는 설정으로, 기본 100(꽉 채움)을 낮추면 갱신용 여백이 남는다.

```sql
-- 카운터를 별도 테이블로 떼어내고, 갱신 여백을 준다
CREATE TABLE episode_view_count (
    episode_id bigint      PRIMARY KEY REFERENCES episode(id),
    cnt        bigint      NOT NULL DEFAULT 0,
    updated_at timestamptz NOT NULL DEFAULT now()
) WITH (fillfactor = 70);          -- 페이지의 30%를 "새 버전이 들어갈 자리"로 비워 둔다

-- 기존 테이블에 적용하려면: 설정은 즉시 반영되지만 효과는 이후 갱신부터다
ALTER TABLE episode SET (fillfactor = 70);
-- 이미 꽉 찬 페이지에는 소급되지 않는다. 즉시 반영하려면 VACUUM FULL 또는 pg_repack —
-- 둘 다 무거우므로 트래픽이 낮을 때. 특히 VACUUM FULL은 ACCESS EXCLUSIVE 잠금이라
-- 그 시간 동안 읽기조차 막힌다.

-- 이 테이블만 autovacuum을 공격적으로 (테이블 단위 설정)
ALTER TABLE episode_view_count SET (
    autovacuum_vacuum_scale_factor = 0.01,   -- 기본 0.2(=20%) → 1%만 죽어도 청소를 시작한다
    autovacuum_vacuum_threshold    = 50      -- 작은 테이블이라 비율만으로는 잘 안 걸린다
);
```

**카운터 컬럼을 별도 테이블로 떼어내는 것 자체가 PostgreSQL에서는 이득**이라는 점도 함께 말할 수 있어야 한다. 이유는 새 튜플에 복사되는 양이다. `episode` 본체는 제목·썸네일 URL·설명 같은 것이 붙은 넓은 행이라, 조회수 하나를 올릴 때마다 **그 큰 행 전체가 새 버전으로 복사된다.** 반면 `(episode_id, cnt, updated_at)`만 있는 좁은 테이블은 복사할 바이트가 적고, 페이지당 튜플 수가 많아 HOT이 살아남기도 쉽다. 대가는 조회 시 조인 하나다. 얻는 것과 내는 것이 이렇게 뚜렷한 반정규화 판단은 [`04-normalization-vs-denormalization.md`](04-normalization-vs-denormalization.md)의 연장선이다.

**위생 ② 원자적 UPDATE.** 1-6에서 다룬 그대로다. lost update를 없애고 락 보유 시간을 줄인다. 처방이 아니라 위생이므로, 이것만 하고 끝내면 안 된다는 점도 함께 기억한다.

**위생 ③ UPDATE를 조회 트랜잭션에서 분리.** 조회는 `@Transactional(readOnly = true)`로 리플리카에서 읽고, 카운터 UPDATE는 **응답을 보낸 뒤** 별도의 짧은 트랜잭션으로 보낸다. 조회 API가 쓰기에서 해방되는 것만으로 리플리카 라우팅이 되살아나고, 락 보유 시간이 "UPDATE 한 문장 + 커밋"으로 최소화된다.

```java
// 주의: REQUIRES_NEW로 "같은 요청 안에서" 분리하면 오히려 나빠진다
@Transactional                                   // 바깥 트랜잭션이 커넥션 1개를 쥐고 있는데
public EpisodeResponse view(Long id) {
    var episode = repo.findById(id).orElseThrow();
    counterService.increase(id);                 // 여기서 REQUIRES_NEW면 커넥션 1개를 더 쥔다
    return EpisodeResponse.from(episode);        // → 요청당 커넥션 2개 → 풀 고갈이 두 배 빨라진다
}
// 분리하려면 "바깥 트랜잭션이 끝난 뒤"에 해야 한다.
// 예: @TransactionalEventListener(phase = AFTER_COMMIT) 또는 응답 후 비동기 처리.
```

단, 위생 ③은 UPDATE 자체를 없애지 않는다. **초당 UPDATE 횟수는 그대로**이므로 핫 로우 사슬은 여전히 살아 있다. 그래서 갈래별 처방이 필요하다.

### 2-4. 갈래 A — "정확해야 하는 숫자": 진실은 DB 안에 있어야 한다

재고, 잔액, 쿠폰 잔여 수량처럼 **1이 틀리면 사고인 숫자**다. 이 갈래의 원칙은 한 줄이다 — **불변식의 최종 보증은 DB 제약이 하고, 진실은 DB 밖으로 나가지 않는다.**

왜 그런가. 불변식(`재고 >= 0`)이 애플리케이션 코드에만 살면, 그 코드를 거치지 않는 경로 — 새로 만든 배치, 어드민 화면, 운영자의 psql — 가 하나만 생겨도 뚫린다. 반면 `CHECK` 제약은 **그 테이블에 들어오는 모든 쓰기**를 막는다.

```sql
CREATE TABLE stock (
    product_id bigint PRIMARY KEY,
    qty        int    NOT NULL,
    CONSTRAINT chk_stock_non_negative CHECK (qty >= 0)   -- 이 줄이 최종 방어선이다
);

-- 차감: 원자적 UPDATE + 조건. 두 가지가 동시에 필요하다.
UPDATE stock
   SET qty = qty - $2
 WHERE product_id = $1
   AND qty >= $2;          -- ① 조건: 재고가 부족하면 아예 갱신하지 않는다
-- 애플리케이션은 "영향받은 행 수"로 성공/실패를 판별한다.
--   1행 → 차감 성공
--   0행 → 재고 부족. 예외를 던져 주문을 거절한다.
-- ② CHECK 제약: 혹시 WHERE 조건을 빠뜨린 코드 경로가 생겨도 여기서 막힌다.
--    조건이 있는데 CHECK를 또 두는 이유가 이것이다 — 하나는 흐름 제어, 하나는 최종 보증.
```

이 갈래에서 **하면 안 되는 것**을 명확히 말하는 것이 변별점이다.

- **Redis 버퍼링 금지.** 갱신을 Redis에 모았다가 나중에 DB에 반영하는 순간, "지금 재고가 몇인가"의 진실이 DB 밖에 생긴다. Redis가 죽으면 **돈이 사라지는 유실 창**이 열리고, `CHECK` 제약은 자기가 모르는 델타에 대해 아무것도 지켜 주지 못한다.
- **`synchronous_commit = off` 금지.** 커밋 응답을 준 뒤 WAL fsync를 미루는 설정이라 커밋 처리량은 올라가지만, 크래시 시 **커밋했다고 응답한 트랜잭션이 사라진다.** 그건 조회수에서나 협상 가능한 성질이다.
- **행 샤딩도 원칙적으로는 못 쓴다.** 이유는 §2-7 끝에서 따로 다룬다 — 유실이 문제가 아니라 **불변식이 합계에 걸려 있기 때문**이다.

그럼 갈래 A에서 경합은 어떻게 하나. 정직한 답은 **"경합은 남는다"**이고, 그 위에서 할 수 있는 일은 셋이다.

1. **락 보유 시간을 최소화한다.** 1-3의 표에서 아래 칸으로 내려가는 요인(트랜잭션 안의 외부 API 호출, 지연 로딩, 응답 조립)을 전부 트랜잭션 밖으로 뺀다. 100ms를 2ms로 줄이면 상한이 10건/초에서 500건/초로 **50배** 올라간다. 이것이 갈래 A에서 가장 효과가 큰 조치다.
2. **경합 지점 자체를 도메인으로 쪼갠다.** 재고를 창고별·색상별로 나누면 행이 여러 개가 되어 자연스럽게 경합이 분산된다. 이것은 기술적 샤딩이 아니라 도메인 모델링이고, 합계 불변식이 각 행 안에서 닫히므로 §2-7의 문제가 생기지 않는다.
3. **극단적인 이벤트성 집중은 앞단에서 흡수한다.** 초당 5만 건짜리 선착순 쿠폰이라면 Redis `DECR`로 **선점 게이트**를 세운다 — Redis가 "n번째까지만 통과"를 결정하고, 통과한 요청만 DB로 내려보내 확정한다. 여기서 Redis의 역할이 **버퍼가 아니라 게이트**라는 점이 결정적이다. 진실은 여전히 DB에 있고, Redis는 DB에 도달하는 요청 수를 줄일 뿐이다. 상세는 3장 [`20-concurrency-update-four-approaches.md`](../03-jpa-orm/20-concurrency-update-four-approaches.md)가 다룬다.

> **(가산점 포인트) 잔액을 잠글 때는 `FOR UPDATE`가 아니라 `FOR NO KEY UPDATE`.** `SELECT ... FOR UPDATE`는 그 행의 키(PK·유니크 컬럼)까지 바뀔 수 있다는 전제의 강한 락이라, 자식 테이블에 FK가 걸린 행을 INSERT하려는 트랜잭션이 요구하는 `KEY SHARE` 락과 충돌한다. 잔액처럼 **키가 아닌 컬럼만 바꾸는 갱신**이면 `FOR NO KEY UPDATE`가 맞고, 그러면 FK 삽입과 나란히 진행된다. 자세한 락 모드 비교는 [`19-select-for-update-lock-scope.md`](19-select-for-update-lock-scope.md)에 있다.

### 2-5. 갈래 B — "대략 맞으면 되는 숫자": 쓰기 지점을 행에서 떼어낸다

조회수, 좋아요 합계, 노출수처럼 **0.1%가 틀려도 아무도 감지하지 못하는 숫자**다. 이 갈래의 원칙도 한 줄이다 — **정확도를 조금 팔아서 "같은 행에 도달하는 쓰기 횟수" 자체를 줄인다.**

방향은 셋이고, 셋 다 "쓰기 지점을 행에서 떼어낸다"는 같은 아이디어의 변형이다.

- **공간으로 떼어내기 (행 샤딩).** 행 하나를 N개 행으로 쪼갠다. 쓰기가 N개 지점으로 흩어지므로 경합이 1/N이 된다. 외부 인프라가 필요 없고 **유실이 0**이라는 것이 최대 장점이고, 쓰기 총량은 그대로라는 것이 최대 단점이다. (§2-7)
- **시간으로 떼어내기 (버퍼 + 주기 반영).** 증가분을 어딘가에 모아 두었다가 N초에 한 번 합쳐서 반영한다. 모으는 곳이 Redis면 전략 4, 앱 메모리면 전략 5, Kafka면 전략 6이다. **쓰기 총량 자체가 줄어들므로 사슬 A와 B를 동시에 없앤다**는 것이 최대 장점이고, **유실 창**이 생긴다는 것이 대가다. (§2-8)
- **모양을 바꾸기 (append 후 집계).** UPDATE 대신 INSERT만 하고, 집계는 나중에 배치가 한다. INSERT는 같은 행을 건드리지 않으므로 락도 없고, **죽은 튜플도 만들지 않는다**(INSERT는 옛 버전을 남기지 않는다). 대신 테이블이 빠르게 커진다. (§2-6의 6번)

세 방향을 하나로 이으면 이렇다. **행 샤딩은 경합만 줄이고, 버퍼링은 총량까지 줄이며, append는 UPDATE를 INSERT로 바꾼다.** 어느 것을 고를지는 "지금 아픈 게 경합인가, 쓰기 총량인가"에 달렸고, 그 판별은 §1-7의 세 쿼리가 해 준다.

### 2-6. 완화 전략 총람 — 얻는 것 / 내는 것

목록으로 인출할 수 있어야 한다. 전략 이름만이 아니라 **대가 열을 같이** 외운다. "갈래" 열이 §2-2의 그림과 이어진다.

| # | 전략 | 얻는 것 | 내는 것 | 유실 가능성 | 갈래 / 적합 |
|---|---|---|---|---|---|
| 0 | **(PostgreSQL 전용) 물리 설계 위생**: 카운터 컬럼에 인덱스를 두지 않고 `fillfactor`를 낮춘다 | HOT 유지 → 인덱스 갱신 0회, 페이지 안에서 공간 재사용 | 테이블 크기 증가(여백), 그 컬럼으로 정렬·인덱스 조회 포기 | 0 | 공통 위생 — 항상 |
| 1 | 원자적 UPDATE | lost update 제거, 락 보유 시간 단축 | 경합 사슬 A·B 그대로 | 0 | 공통 위생 — 항상 |
| 2 | UPDATE를 조회 트랜잭션에서 분리 | 조회는 `readOnly` → 리플리카로, 락 보유 최소 | 커밋 수·죽은 튜플 생성량은 동일 | 0 | 공통 위생 — 항상 |
| 3 | 행 샤딩 카운터 (N행) | 경합 1/N, 외부 인프라 없이 DB만으로 해결 | 읽기 N행 SUM, 정렬·인덱스 불가, **쓰기·죽은 튜플 총량 동일**, 합계 불변식 불가 | 0 | B (그리고 불변식 없는 A) |
| 4 | Redis `INCR` 버퍼 + 주기 배치 반영 | DB 쓰기 수백~수천분의 1, 락 0, 조회는 read-only | 유실 창(주기 × TPS), Redis 의존, 이중 소스, flush 멱등성 숙제 | 주기 × 초당 증가량 | **B — 조회수의 정답** |
| 5 | 앱 로컬 버퍼(`LongAdder`) + 주기 반영 | 네트워크 왕복 0 | 인스턴스 다운·배포마다 유실, 인스턴스별 합산 필요 | 4보다 큼 | B — 로그성 지표, 4의 앞단 |
| 6 | 이벤트 스트림 / append-only 집계 | 내구성, 재처리 가능, 다른 소비자(추천·정산) 공유 | 지연, at-least-once 중복 처리, 인프라 복잡도 | 거의 0 (내구) | B — 집계가 다목적일 때 |
| 7 | 근사 자료구조 (HyperLogLog) | 메모리 상수 (유니크 방문자) | 오차 존재, 정확한 값은 영원히 없음 | 해당 없음 | B — UV, 유니크 조회자 |
| 8 | 표시 계층 캐시 | 읽기 부하 감소 | 표시 지연 | 해당 없음 | 다른 전략과 병행 |

0~2번은 §2-3에서 다뤘고 3번은 §2-7, 4번은 §2-8에서 코드로 내린다. 나머지를 짧게 풀면 이렇다.

**5 — 앱 로컬 버퍼.** 4의 앞단에 `LongAdder`를 두고 몇 초에 한 번 Redis로 몰아 보내면 네트워크 왕복까지 줄일 수 있다. 그러나 인스턴스가 죽거나 배포로 내려가면 메모리의 델타가 통째로 사라진다 — **유실 창이 4보다 넓다.** graceful shutdown에서 마지막 flush를 보장하는 코드가 필요하고, 그것도 `kill -9`에는 무력하다. 조회수처럼 유실을 넓게 허용하는 곳이 아니면 쓰지 않는다.

**6 — 이벤트 스트림 / append-only 집계.** 조회 한 건을 이벤트로 발행하고, 컨슈머가 시간 창 단위로 집계해 DB에 반영한다. 4와 비교한 차이는 **내구성과 재처리 가능성**이다 — 브로커에 남아 있으니 컨슈머가 죽어도 유실이 없고, 집계 로직에 버그가 있어도 되감아 다시 계산할 수 있으며, 같은 이벤트를 추천·정산·통계가 함께 소비한다. 대가는 지연(브로커 → 컨슈머 → 집계 창 → 반영), at-least-once 전달이라 **중복 반영을 막는 멱등성 설계**가 필수라는 점, 그리고 브로커 운영 비용이다. 조회수 하나를 위해 Kafka를 새로 들이지는 않지만, 조회 로그가 이미 스트림으로 흐르는 조직이라면 자연스러운 선택이다.

DB만으로 하는 같은 계열의 변형도 있다. 조회를 **append-only 테이블에 INSERT만 하고**, 주기 배치가 `GROUP BY`로 집계해 카운터에 반영하는 방식이다. INSERT는 옛 버전을 남기지 않으므로 **죽은 튜플을 만들지 않는다**는 것이 핵심 이점이다. 날짜로 RANGE 파티션을 잘라 두면 집계가 끝난 파티션을 통째로 `DROP`할 수 있어 대량 DELETE의 블로트도 피한다([대량 삭제와 파티셔닝](25-mass-delete-archiving-and-partitioning.md)). 그리고 이 원천 테이블이 §3의 대사(reconciliation) 기준이 되어 준다는 부수 효과가 크다.

**7 — 근사 자료구조.** "이 에피소드를 본 유니크 독자 수"처럼 중복을 제거해야 하는 카운트는, 정확히 세려면 독자 ID 집합을 통째로 들고 있어야 한다. HyperLogLog(`PFADD`/`PFCOUNT`)는 키당 12KB 안팎의 고정 메모리로 표준 오차 1% 미만의 근사치를 준다. PostgreSQL에도 같은 자료구조를 제공하는 확장(`postgresql-hll`)이 있어 집계 테이블에 스케치를 저장할 수 있다. 정확한 값은 영원히 얻을 수 없다는 것이 대가인데, 조회수 도메인에서는 그 대가가 거의 0이다. (가산점 포인트)

**8 — 표시 캐시.** 쓰기 문제와 별개로, 조회수를 보여 주는 읽기 자체도 캐시한다. 4를 쓰면 Redis에 이미 최신 델타가 있으므로 "DB 기준값 + 미반영 델타"를 조합하거나, 그냥 분 단위 갱신값을 보여 준다.

### 2-7. 행 샤딩 카운터 — 완성 SQL과 샤드 수를 정하는 근거

1장 [`27-longadder-false-sharing.md`](../01-java-kotlin/27-longadder-false-sharing.md)에서 본 **"쓰기는 셀별로 분산, 읽기는 합산"**의 DB 판이다. `LongAdder`가 CAS 경합 지점을 Cell 배열로 쪼갰듯, 행 하나를 N개 행으로 쪼갠다.

```sql
-- 스키마: (엔티티, 샤드 번호)가 PK. 같은 에피소드의 샤드들이 PK 접두사로 붙어 있어
--         읽을 때 인덱스 범위 스캔 한 번으로 N행을 모을 수 있다.
CREATE TABLE counter_shards (
    post_id  bigint   NOT NULL REFERENCES post(id) ON DELETE CASCADE,
    shard_no smallint NOT NULL,                    -- 0 .. N-1
    cnt      bigint   NOT NULL DEFAULT 0,
    PRIMARY KEY (post_id, shard_no)
) WITH (fillfactor = 70);                          -- 위생 ①을 같이 적용한다
-- cnt에는 인덱스를 걸지 않는다. 걸면 매 UPDATE가 비-HOT이 되어 사슬 B가 되살아난다.

-- 쓰기 준비: 게시물 생성 시 샤드 행을 미리 만들어 둔다.
-- 이걸 안 하면 첫 UPDATE가 "0행 갱신"으로 조용히 실패한다 — 흔한 버그다.
INSERT INTO counter_shards (post_id, shard_no)
SELECT $1, generate_series(0, 15);

-- 쓰기: 무작위 샤드 하나에 +1. 경합이 1/16이 된다.
UPDATE counter_shards
   SET cnt = cnt + 1
 WHERE post_id = $1 AND shard_no = $2;             -- $2 = 애플리케이션이 고른 0~15

-- 미리 만들어 두지 않는 구조라면 UPSERT로 "없으면 만들고 있으면 더한다"
INSERT INTO counter_shards (post_id, shard_no, cnt)
VALUES ($1, $2, 1)
ON CONFLICT (post_id, shard_no)
DO UPDATE SET cnt = counter_shards.cnt + 1;

-- 읽기 ①: 한 게시물의 총합. PK 접두사로 16행만 읽는다.
SELECT coalesce(sum(cnt), 0) AS total
  FROM counter_shards
 WHERE post_id = $1;

-- 읽기 ②: 목록 화면 — 여러 게시물의 총합을 한 번에.
--         읽는 행 수가 (게시물 수 x N)으로 곱해진다는 것이 이 전략의 대가다.
SELECT post_id, sum(cnt) AS total
  FROM counter_shards
 WHERE post_id = ANY($1::bigint[])
 GROUP BY post_id;
```

**샤드 수 N을 정하는 근거**를 말할 수 있어야 한다. 감이 아니라 계산이다.

```text
  필요한 N  ≥  목표 초당 갱신량  ÷  행 하나의 초당 상한(= 1 / 락 보유 시간)

  예) 목표 5,000건/초, 락 보유 2ms → 행 하나의 상한 500건/초
      N ≥ 5,000 ÷ 500 = 10
      → 여유를 두어 16으로 잡는다.

  주의: 무작위 분배는 완벽히 균등하지 않다. 순간적으로 한 샤드에 몰릴 수 있으므로
        계산값에 2배 정도 여유를 두는 것이 실무 감각이다.
```

N을 무한정 키우지 못하는 이유가 **읽기 비용**이다. 여기가 이 전략의 트레이드오프 핵심이다.

- **읽기가 N배가 된다.** 총합을 낼 때마다 N행을 읽어 더해야 한다. 한 건 조회면 16행이라 무시할 만하지만, **목록 화면에서 게시물 100개의 조회수를 보여 준다면 1,600행**이다. 읽기가 잦은 서비스일수록 N을 작게 잡아야 한다.
- **정렬·인덱스가 불가능해진다.** "인기순 정렬"을 하려면 `ORDER BY cnt`가 필요한데, 실제 값이 N행에 흩어져 있으므로 인덱스를 걸 대상 자체가 없다. 정렬이 필요하면 별도의 요약 테이블이나 Redis Sorted Set을 따로 둬야 한다.
- **쓰기 총량은 그대로다.** 사슬 A(경합)는 1/N이 되지만 **사슬 B는 한 고리도 안 줄어든다.** 초당 5,000 UPDATE는 여전히 초당 5,000개의 죽은 튜플이고 5,000번의 커밋·WAL fsync다. PostgreSQL 특유의 단서를 하나 붙이면 — 샤드 16행이 같은 페이지에 몰려 있으면 **죽은 튜플 압력도 그 페이지 하나에 그대로 몰린다.**
- **N을 바꾸는 비용은 방향에 따라 다르다.** 늘리는 것은 쉽다 — 어차피 총합을 `SUM`으로 내므로 새로 추가한 샤드가 0에서 시작해도 합계는 계속 맞는다. 줄이는 것은 값을 옮겨야 한다 — 없앨 샤드의 `cnt`를 남길 샤드에 더한 뒤 삭제해야 하고, 그 사이에 들어오는 쓰기와 경쟁하지 않도록 잠금이나 중단 창이 필요하다.

**샤드를 고르는 방법**도 선택지가 있다.

- **무작위(`random()`)**: 가장 균등하다. 카운터라 "같은 요청이 재시도되면 다른 샤드로 간다"는 것이 문제가 되지 않는다.
- **앱 인스턴스나 커넥션 ID 해시**: 같은 인스턴스는 항상 같은 샤드를 쓰게 만든다. 인스턴스 수가 N보다 적거나 비슷하면 **인스턴스끼리 아예 안 부딪히게** 만들 수 있어 무작위보다 낫다. 대신 인스턴스별 트래픽이 고르지 않으면 샤드도 불균등해진다.

**그리고 갈래 A에서 이 전략을 못 쓰는 이유.** 유실이 0이니 정확성은 문제가 아니다. 문제는 **불변식이 합계에 걸려 있다는 것**이다. `재고 >= 0`을 지키려면 "지금 총합이 얼마인지"를 알고 차감해야 하는데, 총합이 N행에 흩어져 있으면 `CHECK (cnt >= 0)`는 각 샤드가 음수가 아닌 것만 보장할 뿐 **총합을 보장하지 못한다.** 총합을 원자적으로 확인하려면 N행을 전부 잠가야 하는데, 그러면 경합을 나눈 의미가 사라진다. 즉 **샤딩은 "합계에 불변식이 없는 순수한 누적 카운터"에만 쓴다.**

### 2-8. after — 웹툰 조회수: Redis 버퍼 + 멱등 flush

갈래 B의 전략 4를 코드로 내린다. 조회수는 이 문서의 문항이 지정한 도메인이고, 표의 첫 줄(근사 허용 · 분 단위면 충분 · 초고빈도 집중)에 정확히 해당한다.

먼저 원리. `INCR`/`HINCRBY`는 Redis가 **단일 스레드로 명령을 하나씩 실행**하므로 락 없이 원자적이고, 메모리 연산이라 초당 수십만 건을 받는다. N초마다 누적된 델타를 읽어 DB에 `cnt = cnt + Δ`로 **한 번** 반영하면, 초당 5,000건의 UPDATE가 **1분에 한 번의 UPDATE(에피소드당 1행)**로 줄어든다.

배율을 계산해 보면 이 전략이 왜 압도적인지 보인다. 에피소드 하나에 대해 1분간 발생하는 DB UPDATE가 `5,000 × 60 = 300,000`번에서 **1번**이 된다 — **1/300,000**이다. 그리고 이 감소는 사슬 A와 B에 동시에 작용한다. 락도, 죽은 튜플도, WAL도, 복제 지연도 같은 배율로 줄어든다. 사슬 B가 함께 사라지는 것이 PostgreSQL에서 이 전략이 특히 잘 듣는 이유다.

부품은 셋이다 — **요청 경로의 버퍼**, **주기 flush**, **flush의 멱등성 장치**.

```java
// after ① 요청 경로 — 조회는 read-only, 카운트는 DB 트랜잭션 밖 자원에
@Service
@RequiredArgsConstructor
public class EpisodeService {

    private final EpisodeRepository episodeRepository;
    private final ViewCountBuffer viewCountBuffer;

    @Transactional(readOnly = true)                 // 리플리카로 라우팅 가능, 락 없음, 죽은 튜플 0
    public EpisodeResponse view(Long episodeId) {
        Episode episode = episodeRepository.findById(episodeId).orElseThrow();
        viewCountBuffer.increment(episodeId);       // Redis HINCRBY — 실패해도 조회는 성공한다
        return EpisodeResponse.from(episode);
    }
}

@Component
@RequiredArgsConstructor
public class ViewCountBuffer {

    private final StringRedisTemplate redis;
    private final MeterRegistry meterRegistry;
    private final Clock clock;

    /** 1분 단위 버킷 키. 버킷을 시간으로 닫아야 flush 대상이 "더 이상 안 바뀌는 키"가 된다 */
    static String bucketKey(long bucket) {
        return "ep:views:" + bucket;
    }

    static long currentBucket(Instant now) {
        return now.getEpochSecond() / 60;           // 60초를 한 버킷으로
    }

    public void increment(Long episodeId) {
        try {
            redis.opsForHash().increment(
                bucketKey(currentBucket(clock.instant())), episodeId.toString(), 1);
        } catch (DataAccessException e) {
            // fail-open: 조회수 1건을 포기하고 조회 API는 살린다.
            // 대신 "포기했다"는 사실을 반드시 센다 — 세지 않으면 §3의 측정이 불가능하다.
            meterRegistry.counter("viewcount.buffer.failure").increment();
        }
    }
}
```

포인트는 세 가지다.

**① 조회 트랜잭션에서 쓰기가 완전히 빠졌다.** 락도, 새 튜플 버전도, WAL도, 리플리카 라우팅 제약도 사라진다. 1-1의 세 문제 중 둘이 여기서 동시에 해결된다.

**② Redis 호출은 fail-open이다.** 카운터 인프라 장애가 콘텐츠 조회 장애로 번지면 본말이 전도된다. 다만 fail-open은 "조용히 무시"가 아니다 — 포기한 건수를 세지 않으면 §3의 안전망이 성립하지 않는다.

**③ 키를 시간 버킷으로 나눈다.** 이것이 이 설계에서 가장 놓치기 쉬운 부분이다. 만약 키가 `ep:views` 하나뿐이라면, flush가 `HGETALL`로 읽고 `DEL`로 지우는 사이에 들어온 증가분이 **읽히지도 못한 채 삭제된다.** 키를 분 단위로 나누면 "지금 쓰고 있는 키"와 "flush할 키"가 물리적으로 다른 키가 되어 이 경쟁이 원천적으로 사라진다.

```java
// after ② 주기 flush — 이미 닫힌 버킷만, 멱등하게
@Component
@RequiredArgsConstructor
public class ViewCountFlusher {

    private final StringRedisTemplate redis;
    private final JdbcTemplate jdbc;
    private final TransactionTemplate tx;
    private final Clock clock;

    private static final int LOOKBACK_BUCKETS = 10;   // 장애로 밀린 버킷도 따라잡는다

    @Scheduled(fixedDelay = 10_000)
    public void flush() {
        long current = ViewCountBuffer.currentBucket(clock.instant());
        // current-1은 "방금 닫힌" 버킷이다. 59.999초에 버킷 번호를 계산한 요청의 HINCRBY가
        // 00.001초에 도착할 수 있으므로 한 칸 더 비워 current-2까지만 flush한다.
        for (long bucket = current - LOOKBACK_BUCKETS; bucket <= current - 2; bucket++) {
            flushBucket(bucket);
        }
    }

    void flushBucket(long bucket) {
        String key = ViewCountBuffer.bucketKey(bucket);
        Map<Object, Object> deltas = redis.opsForHash().entries(key);
        if (deltas.isEmpty()) return;

        Boolean applied = tx.execute(status -> {
            // 멱등성의 핵심: "이 버킷은 반영했다"는 기록을 카운터 UPDATE와 같은 트랜잭션에
            // PK로 남긴다. PostgreSQL에서는 예외를 던지지 않는
            // ON CONFLICT DO NOTHING + RETURNING 이 정석이다 (아래 주의 참고).
            Long claimed = jdbc.query(
                """
                insert into view_count_flush_log (bucket, total_delta, applied_at)
                values (?, ?, now())
                on conflict (bucket) do nothing
                returning bucket
                """,
                rs -> rs.next() ? rs.getLong(1) : null,
                bucket, totalOf(deltas));

            if (claimed == null) return false;   // 다른 인스턴스가 먼저 했거나, 지난 실행이 커밋 직후 죽었다

            // 델타를 episode_id 오름차순으로 정렬해 배치로 보낸다.
            // 동시에 도는 배치끼리 행 잠금 순서가 같아져 데드락이 나지 않는다.
            jdbc.batchUpdate(
                "update episode_view_count set cnt = cnt + ?, updated_at = now() where episode_id = ?",
                deltas.entrySet().stream()
                    .map(e -> new Object[]{ Long.parseLong((String) e.getValue()),
                                            Long.parseLong((String) e.getKey()) })
                    .sorted(Comparator.comparingLong(a -> (Long) a[1]))
                    .toList());
            return true;
        });

        // 커밋 뒤에 삭제한다. 여기서 죽어도 다음 실행은 flush_log PK에 막혀
        // 이중 반영이 불가능하고 삭제만 하고 지나간다.
        redis.delete(key);
    }
}
```

```sql
create table view_count_flush_log (
    bucket      bigint      primary key,   -- "이 버킷은 반영 완료"의 표식. 같은 버킷은 두 번 못 들어온다
    total_delta bigint      not null,      -- §3 대사 배치가 원천 로그와 비교할 때 쓴다
    applied_at  timestamptz not null
);
```

> **(가산점 포인트) PostgreSQL에서 유니크 충돌을 예외로 받으면 안 되는 이유.** PostgreSQL은 트랜잭션 안에서 에러가 하나라도 나면 **그 트랜잭션 전체가 abort 상태**가 되어, 이후 명령이 전부 `current transaction is aborted, commands ignored until end of transaction block`으로 거부된다. 즉 `DuplicateKeyException`을 잡아서 "그럼 다른 걸 하자"가 성립하지 않는다 — 계속하려면 `SAVEPOINT`(스프링에서는 `@Transactional(propagation = NESTED)`)로 서브트랜잭션을 열어야 한다. 그래서 PostgreSQL에서는 **애초에 예외를 만들지 않는** `ON CONFLICT DO NOTHING ... RETURNING`이 정석이다. 반환 행이 있으면 내가 선점한 것, 없으면 이미 누가 했다는 뜻이라 분기까지 한 문장에서 끝난다. (동시 실행이면 뒤에 온 쪽이 앞 트랜잭션의 커밋을 기다린 뒤 0행을 받는다.)

**대량 반영이라면 한 문장으로 (선택).** 에피소드가 수만 개면 배치 왕복 대신 배열을 하나 보내는 편이 낫다. 카운터 행이 없을 수도 있는 구조면 UPSERT가 그대로 병합식이 된다.

```sql
-- 델타 배열 두 개를 파라미터로 — 왕복 1회
insert into episode_view_count (episode_id, cnt, updated_at)
select id, delta, now()
from   unnest($1::bigint[], $2::bigint[]) as d(id, delta)
order  by id                                   -- 잠금 순서 고정 → 데드락 방지
on conflict (episode_id)
do update set cnt = episode_view_count.cnt + excluded.cnt,
              updated_at = now();
```

주의 둘. ① **한 문장 안에 같은 키가 두 번 있으면** `ON CONFLICT DO UPDATE command cannot affect row a second time` 에러가 난다 — 보내기 전에 `episode_id`로 집계해 중복을 없애야 한다. ② `DO UPDATE`는 값이 결과적으로 같아도 **새 튜플 버전을 만든다** — 델타가 0인 행은 애초에 보내지 않거나 조건으로 걸러야 무의미한 블로트가 안 생긴다. JDBC 배치를 그대로 쓸 거라면 pgjdbc의 `reWriteBatchedInserts=true`가 INSERT 배치를 다중 VALUES 한 문장으로 재작성해 왕복을 줄여 준다.

이 flush가 **왜 멱등한지**를 순서대로 말할 수 있어야 한다. 멱등(idempotent)이란 "몇 번 실행해도 결과가 한 번 실행한 것과 같다"는 성질이고, 배치가 재시도되거나 여러 인스턴스에서 동시에 도는 환경에서는 이것이 정합성의 전부다.

- **반영 여부의 기록이 반영 자체와 같은 트랜잭션에 있다.** flush_log INSERT와 카운터 UPDATE가 함께 커밋되거나 함께 롤백된다. "UPDATE는 됐는데 기록이 안 됐다"는 상태가 **존재할 수 없다.**
- **`bucket`이 PK다.** 인스턴스 3대가 동시에 같은 버킷을 집어도 삽입에 성공하는 것은 한 대뿐이다 — 나머지는 첫 번째의 커밋을 기다렸다가 `RETURNING`에서 0행을 받고 물러난다. **DB의 유니크 제약이 조정자**다([유니크 제약과 동시 INSERT](../03-jpa-orm/14-unique-constraint-concurrent-insert.md)와 같은 원리). ShedLock을 얹으면 헛수고(불필요한 `HGETALL`)를 줄일 수 있지만 **정합성은 ShedLock이 아니라 PK가 지킨다** — 분산 락은 최적화 장치라는 3장의 결론이 여기서도 그대로다. (PostgreSQL만의 대안으로 `pg_try_advisory_xact_lock(bucket)`을 앞에 두면 헛수고를 DB 안에서 줄일 수 있는데, 이것도 최적화이지 정합성 장치가 아니다.)
- **Redis 키 삭제는 커밋 뒤다.** 커밋과 삭제 사이에 프로세스가 죽으면 다음 실행이 같은 델타를 다시 읽지만, flush_log PK에 막혀 반영은 건너뛰고 삭제만 한다. 반대로 삭제를 먼저 하고 커밋 전에 죽으면 **델타가 영원히 사라진다** — 순서를 바꾸면 안 되는 이유다.
- **버킷 마감 유예.** `current - 2`까지만 flush하는 이유는 위 코드 주석대로 경계 직전의 지각 쓰기 때문이다. 1분의 유예를 두면 실질적으로 지각 쓰기가 없다. 유예를 넘긴 지각 쓰기는 이론상 유실인데, 이것까지 "유실 상한"에 포함해 말하면 된다.

### 2-9. 이 설계가 내는 대가 — 반드시 같은 호흡으로

after를 말한 뒤 대가를 붙이지 않으면 고난이도 문항에서 감점이다. 이 설계의 대가는 넷이다.

**① 유실 창이 있다.** Redis가 죽거나 데이터를 잃으면 **아직 flush되지 않은 버킷**이 사라진다. 중요한 것은 이 상한을 **계산할 수 있다**는 점이다. 계산해 두면 "얼마나 잃을 수 있는지 모른다"가 "최악 N건까지 잃을 수 있다"로 바뀌고, 그래야 비즈니스와 협상이 된다.

```text
  최악의 유실 = (버킷 길이) + (마감 유예) + (스케줄 지연)  x  초당 증가량

  위 설정에 대입하면:
    버킷 길이   60초   조회 한 건이 버킷 맨 앞에 들어왔다면 그 버킷이 닫힐 때까지 60초를 머문다
    마감 유예   60초   current-2까지만 flush하므로 닫힌 뒤 한 버킷을 더 기다린다
    스케줄 지연 최대 10초  fixedDelay = 10초이므로 대상이 된 직후 최대 10초를 더 기다린다
  ─────────────────────────────────────────────────────────
    합계 130초 = 약 2분 10초

  초당 5,000건이 들어오는 에피소드라면  130 x 5,000 = 650,000건이 최악의 유실이다.
```

이 숫자를 말하고, 그 숫자를 **비즈니스가 승인했는지**가 협상의 실체다. 상한을 줄이는 손잡이는 세 개이고 전부 다른 것과 교환된다.

| 손잡이 | 줄어드는 것 | 대신 내는 것 |
|---|---|---|
| flush 주기·버킷 길이 단축 | 유실 창이 비례해서 줄어든다 | DB 쓰기 횟수가 그만큼 늘어난다 (전략의 이득을 되돌리는 방향) |
| Redis AOF `everysec` | 재시작 시 유실이 1초 이내로 | 디스크 쓰기 부하, 약간의 지연 |
| Redis 복제 + 자동 페일오버 | 노드 하나가 죽어도 델타가 남는다 | 인프라 비용, 비동기 복제라 유실이 0은 아니다 |

그리고 하지 말아야 할 것 하나 — **DB 쪽에서 `synchronous_commit`을 꺼서 커밋을 싸게 만드는 것은 답이 아니다.** 그건 유실 창을 Redis에서 DB로 옮기는 것이지 없애는 게 아니고, 같은 DB를 쓰는 다른 도메인(주문·결제)까지 유실 위험에 넣는다.

**② 실시간성이 떨어진다.** DB의 `cnt`는 최대 2분쯤 낡아 있다. 화면에 "방금 내가 본 것"이 즉시 +1로 보여야 한다면 DB 값이 아니라 "DB 값 + Redis 미반영 델타"를 조합하거나 Redis에 총계 키를 따로 유지해야 하고, 그러면 **진실의 원천이 둘**이 된다. 이중 소스는 반드시 어긋나므로 §3의 대사가 따라와야 한다.

**③ Redis가 장애 지점에 추가된다.** fail-open으로 조회 API는 지켰지만 카운터는 Redis 가용성에 종속된다. Redis 장애 = 그 시간 동안 조회수 0. 이걸 알람 없이 지나가면 "지난주 화요일 오후 조회수가 왜 비었죠"라는 질문을 몇 달 뒤에 받는다.

**④ 코드가 늘어난다.** before는 한 줄이었다. after는 버퍼, 스케줄러, flush_log 테이블, 멱등성 규칙, 모니터링, 회귀 테스트가 생겼다. 이 복잡도를 감당할 만큼 트래픽이 실제로 핫 로우를 만드는지 — **측정 없이 도입하면 과설계다.** 초당 수십 건이면 §2-3의 공통 위생 셋으로 충분하다. 판단 근거는 §1-7의 세 쿼리다.

## 3. 안전망 — 유실을 "허용"했으면 유실을 "측정"한다

### 3-1. 왜 측정이 설계의 일부인가

"조회수는 대략 맞으면 된다"는 말과 "얼마나 틀렸는지 모른다"는 말은 완전히 다르다. 앞의 것은 **허용 오차를 정한 설계**이고, 뒤의 것은 그냥 **관리되지 않는 상태**다. 둘을 가르는 것이 측정이다.

측정이 없으면 어떤 일이 벌어지는지 구체적으로 그려 보면 필요성이 분명해진다. 어느 날 배포로 스케줄러 빈이 등록되지 않아 flush가 멈춘다. 조회 API는 멀쩡하고, Redis는 델타를 계속 쌓고, 에러 로그도 없다. **아무도 모른다.** LOOKBACK 범위를 넘어간 버킷은 영원히 반영되지 않고, 하루 뒤 누군가 "조회수가 안 오르는 것 같은데"라고 말할 때 비로소 발견된다. 그때는 이미 하루치가 사라졌고, 원천 로그가 없으면 복구도 불가능하다.

그래서 안전망을 **세 층**으로 깐다. 층마다 잡아내는 사고의 종류가 다르다.

| 층 | 무엇을 잡나 | 주기 |
|---|---|---|
| 실시간 지표 + 알람 (§3-3) | flush가 멈췄다, Redis가 죽었다, 누가 인덱스를 걸었다 | 초~분 |
| 대사(reconciliation) 배치 (§3-2) | 조용히 누적된 드리프트, 원천과의 차이 | 일 |
| 회귀 테스트 (§3-4) | 멱등성 규칙이 코드 변경으로 깨졌다 | 커밋마다 |

### 3-2. 대사(reconciliation) 배치 — 원천 대비 드리프트를 숫자로

대사(對査, reconciliation)란 **서로 다른 두 기록을 맞대어 차이를 찾는 것**이다. 회계에서 은행 잔고와 장부를 맞춰 보는 그 작업이고, 여기서는 "실제로 일어난 조회 수"와 "카운터에 반영된 수"를 맞댄다.

전제가 하나 필요하다 — **원천(source of truth)이 따로 있어야 한다.** 웹툰 서비스에는 보통 조회 로그가 추천·정산·통계를 위해 append-only 테이블(RANGE 파티션)이나 스트림으로 남아 있다. 그것이 원천이다. 카운터는 그 원천의 **요약본**이고, 대사는 요약본이 원본과 얼마나 벌어졌는지를 재는 일이다.

```sql
-- 어제 하루의 드리프트를 에피소드별로 잰다
with actual as (
    -- 원천 로그로 센 "실제 일어난" 조회 수
    select episode_id, count(*) as actual_cnt
    from   episode_view_log                       -- viewed_at 기준 RANGE 파티션 테이블
    where  viewed_at >= date_trunc('day', now()) - interval '1 day'
      and  viewed_at <  date_trunc('day', now())  -- 상수 범위 조건이어야 파티션 프루닝이 걸린다
    group  by episode_id
),
applied as (
    -- flush 배치가 DB에 반영한 델타 합 (flush_log의 버킷 범위로 자른다)
    select episode_id, sum(delta) as applied_cnt
    from   view_count_flush_detail                -- flush 시 에피소드별 델타를 남겨 두면 여기서 쓴다
    where  bucket between $1 and $2
    group  by episode_id
)
select a.episode_id,
       a.actual_cnt,
       coalesce(p.applied_cnt, 0)                                as applied_cnt,
       a.actual_cnt - coalesce(p.applied_cnt, 0)                 as drift,
       (a.actual_cnt - coalesce(p.applied_cnt, 0))::numeric
           / a.actual_cnt                                        as drift_ratio
from   actual a
left   join applied p on p.episode_id = a.episode_id
where  abs(a.actual_cnt - coalesce(p.applied_cnt, 0))::numeric
           / a.actual_cnt > 0.01;                                -- 1% 초과만 뽑는다
```

> **함정 (PostgreSQL):** `bigint / bigint`는 **정수 나눗셈**이라 `drift / actual_cnt`가 거의 항상 0으로 나온다. 예를 들어 `5 / 1000`은 0.005가 아니라 **0**이다. "드리프트가 없다"는 착시가 정확히 여기서 나온다. 위처럼 `::numeric`(또는 `::float8`)으로 캐스팅해야 비율이 나온다. 대사 쿼리를 처음 짤 때 실제로 자주 밟는 지뢰다.

에피소드별 델타 상세를 남기지 않았다면, `view_count_flush_log.total_delta`의 일별 합과 원천 로그의 일별 총합만이라도 비교한다. **전체 드리프트 비율 하나만 있어도** "flush가 멈췄다", "Redis가 30분 죽었다" 같은 사고를 잡기에는 충분하다.

원천 로그가 아예 없다면 대사는 불가능하다. 그때는 §3-3의 관측 지표(버퍼 실패 건수, 미반영 버킷 수)가 **유일한** 안전망이라는 사실을 인정하고 말해야 한다 — 그리고 그 사실 자체가 "원천 로그를 남길지"를 재검토할 근거가 된다.

**정정(correction)은 신중하게.** 드리프트가 크면 배치가 카운터를 고치게 되는데, 절대값을 그대로 덮어쓰는 `set cnt = actual`은 위험하다. 그 순간에도 flush가 델타를 더하고 있어서 **정정과 flush가 경쟁하기 때문**이다. 정정이 읽은 값과 쓰는 값 사이에 들어온 flush의 델타가 통째로 날아간다. 안전한 형태는 둘이다.

1. **기준점 방식**: "기준 버킷 B까지의 재계산값 + B 이후 flush_log에 기록된 델타"를 더해서 쓴다. 경쟁하는 구간이 없다.
2. **중단 방식**: 정정 시간 동안 flush를 플래그로 멈추고 진행한 뒤 재개한다. 단순하지만 그동안 델타가 Redis에 쌓이므로 유예 시간을 짧게 잡아야 한다.

정정을 자동화할지 사람이 승인하게 할지도 비즈니스와 정한다. 조회수라면 자동화해도 되지만, 정산에 쓰이는 숫자라면 승인 절차를 두는 편이 낫다.

### 3-3. 메트릭과 알람 — 결정을 코드로 고정

| 지표 | 의미 | 알람 기준 예 |
|---|---|---|
| `viewcount.buffer.failure` | fail-open으로 포기한 증가분 | 분당 N건 초과 (= Redis가 불안정하다) |
| `viewcount.flush.lag` | 가장 오래된 미반영 버킷의 나이 | 5분 초과 (= flush가 멈췄다) |
| `viewcount.flush.pending_keys` | Redis에 남아 있는 버킷 키 수 | LOOKBACK 초과 (= 따라잡지 못한다) |
| `viewcount.flush.skipped` | flush_log 선점 실패로 건너뛴 횟수 | 지속 발생 시 스케줄러 중복 실행 점검 |
| `viewcount.drift_ratio` | 일 대사 결과 | 1% 초과 |
| `pg_stat_user_tables.n_dead_tup` (카운터 테이블) | 사슬 B가 되살아났는지 | 라이브 대비 자릿수 초과 |
| `n_tup_hot_upd / n_tup_upd` (카운터 테이블) | HOT 비율 — 인덱스가 몰래 추가됐는지 | 급락 시 |

마지막 두 줄이 PostgreSQL을 쓸 때 추가되는 감시 축이다. 특히 `hot_pct` 급락은 **"누군가 인기순 정렬 때문에 카운터 컬럼에 인덱스를 걸었다"**는 사건을 거의 확실하게 알려 준다 — 코드 리뷰에서 놓쳐도 지표가 잡는다. 이것이 "설계 의도를 지표로 고정한다"의 좋은 예다. 문서에 "카운터 컬럼에 인덱스를 걸지 마시오"라고 적어 두는 것보다, 걸리는 순간 알람이 울리게 만드는 편이 훨씬 오래 간다.

```java
// flush 지연을 시스템이 감시하게 만든다 — "누가 확인하겠지"를 없애는 코드
@Scheduled(fixedDelay = 30_000)
public void reportFlushLag() {
    long current = ViewCountBuffer.currentBucket(clock.instant());
    // 아직 Redis에 남아 있는(= 아직 반영 안 된) 가장 오래된 버킷을 찾는다
    long oldestPending = LongStream.rangeClosed(current - LOOKBACK_BUCKETS, current - 2)
        .filter(b -> Boolean.TRUE.equals(redis.hasKey(ViewCountBuffer.bucketKey(b))))
        .findFirst().orElse(current);
    // 값이 계속 커지면 flush가 멈췄거나 따라잡지 못하고 있다는 뜻이다
    meterRegistry.gauge("viewcount.flush.lag.minutes", current - oldestPending);
}
```

### 3-4. 테스트 — 멱등성을 회귀 테스트로 고정

"flush를 두 번 호출해도 한 번만 반영된다"는 규칙은 코드 리뷰가 아니라 **테스트가 지켜야 한다.** 리뷰는 사람이 하고 사람은 잊지만, 테스트는 매 커밋마다 같은 것을 검사한다.

Testcontainers로 **실제 PostgreSQL을 띄운다.** `ON CONFLICT`의 동작과 "에러 하나로 트랜잭션 전체가 abort된다"는 규칙은 H2로 재현되지 않으므로, 인메모리 DB로 테스트하면 정작 지켜야 할 규칙을 검사하지 못한다.

```java
@Test
void 같은_버킷을_두_번_flush해도_한_번만_반영된다() {
    long bucket = 1_000L;
    redis.opsForHash().increment(ViewCountBuffer.bucketKey(bucket), "42", 7);

    flusher.flushBucket(bucket);
    // 커밋 직후 죽어서 Redis 키 삭제가 안 된 상황을 재현한다
    redis.opsForHash().increment(ViewCountBuffer.bucketKey(bucket), "42", 7);
    flusher.flushBucket(bucket);

    assertThat(jdbc.queryForObject(
            "select cnt from episode_view_count where episode_id = 42", Long.class))
        .isEqualTo(7L);   // 14가 아니다 — flush_log PK가 두 번째 반영을 막았다
}

@Test
void 인스턴스_두_대가_같은_버킷을_동시에_flush해도_한_번만_반영된다() throws Exception {
    long bucket = 2_000L;
    redis.opsForHash().increment(ViewCountBuffer.bucketKey(bucket), "42", 5);

    // 두 스레드를 같은 순간에 출발시켜 "동시에 집었을 때"를 재현한다
    CountDownLatch ready = new CountDownLatch(2);
    CountDownLatch go = new CountDownLatch(1);
    Runnable worker = () -> { ready.countDown(); await(go); flusher.flushBucket(bucket); };
    var pool = Executors.newFixedThreadPool(2);
    pool.submit(worker); pool.submit(worker);
    ready.await(); go.countDown();
    pool.shutdown(); pool.awaitTermination(10, TimeUnit.SECONDS);

    assertThat(jdbc.queryForObject(
            "select cnt from episode_view_count where episode_id = 42", Long.class))
        .isEqualTo(5L);   // 10이 아니다 — 한 대만 선점에 성공했다
}
```

## 4. 꼬리질문 대비 포인트

### "원자적 UPDATE(`cnt = cnt + 1`)로 바꾸면 해결되는 것 아닌가요?"

두 문제를 분리해서 답한다.

원자적 UPDATE가 해결하는 것은 **lost update**다 — 읽은 값에 의존하지 않고, PostgreSQL의 READ COMMITTED는 앞 트랜잭션을 기다린 뒤 **최신 버전으로 식을 다시 평가**(EvalPlanQual)하므로 증가분이 사라지지 않는다. SELECT 후 자바 계산이 없어 락 보유 시간도 짧아진다.

그러나 **핫 로우는 그대로**다. 초당 수천 요청이 여전히 같은 행의 락을 순서대로 잡으므로 그 행의 초당 상한은 여전히 `1 / 락 보유 시간`이고, 락 대기 → 커넥션 점유 → 풀 고갈 → 전파 사슬도, 갱신마다 새 튜플 버전이 생겨 VACUUM이 추격에 실패하는 쓰기 증폭도 한 고리도 안 사라진다.

원자적 UPDATE는 "정확성 위생"이고 핫 로우 처방은 "쓰기 지점을 행에서 떼어내는 것"이라 **층이 다르다.** 그래서 답은 "그것부터 하고, PostgreSQL이면 `fillfactor`·인덱스 정리까지 하고, 그 위에 갈래에 맞는 처방을 얹는다"다.

### "Redis로 버퍼링하면 조회수가 유실될 수 있잖아요. 얼마나, 그리고 괜찮은가요?"

"괜찮다"가 아니라 **상한을 숫자로** 말한다.

유실 창은 `(버킷 길이 + 마감 유예 + 스케줄 지연) × 초당 증가량`이고, 유실이 실제로 일어나는 조건은 두 가지다 — Redis 장애·재시작으로 미반영 버킷을 잃는 경우, 그리고 fail-open으로 포기한 증가분. 1분 버킷 + 1분 유예 + 10초 주기면 **최악 약 2분 10초치**이고, 초당 5,000건인 에피소드라면 약 65만 건이다.

그 다음 문장은 도메인 판단이다 — 웹툰 조회수는 화면 표시용이라 이 손실을 아무도 감지하지 못하고, 정산에 쓰이는 숫자라면 원천 로그에서 배치로 정확히 재계산하는 **별도 경로**를 둔다. 같은 "조회수"라도 용도가 둘이면 숫자도 둘이어야 한다.

그리고 "허용"으로 끝내지 않는다 — 대사 배치가 매일 원천 대비 드리프트를 재고, 1%를 넘으면 알람이 울리며, `buffer.failure`와 `flush.lag` 지표가 유실이 실제로 일어나는 순간을 잡는다. 유실 상한을 낮추고 싶으면 주기 단축·AOF·복제라는 손잡이가 있고 각각 DB 쓰기·디스크·인프라 비용과 교환된다는 것까지 붙이면 완성이다.

### "flush 배치가 인스턴스 3대에서 동시에 돌거나, 반영 도중 죽으면 어떻게 되나요?" (시니어 변별 포인트)

멱등성을 세 층으로 답한다.

① **반영 기록과 반영이 같은 트랜잭션**이다 — `view_count_flush_log(bucket PK)` 삽입과 카운터 UPDATE가 함께 커밋되므로 "반영은 됐는데 기록이 없다"는 상태가 없다.

② **PK가 조정자**다 — 3대가 같은 버킷을 집어도 삽입에 성공하는 것은 한 대뿐이고, 나머지는 첫 번째의 커밋을 기다렸다가 빈손으로 물러난다. 여기서 PostgreSQL 디테일 하나 — `DuplicateKeyException`을 잡는 방식은 **PostgreSQL에서 위험하다.** 트랜잭션 안에서 에러가 나면 그 트랜잭션 전체가 abort 상태가 되어 뒤이은 명령이 전부 거부되므로, 계속 진행하려면 `SAVEPOINT`(스프링 `NESTED`)가 필요하다. 그래서 예외를 아예 만들지 않는 `INSERT ... ON CONFLICT DO NOTHING ... RETURNING`으로 선점 여부를 행 유무로 받는다. ShedLock이나 advisory lock은 헛수고를 줄이는 최적화이지 정합성 장치가 아니다.

③ **Redis 삭제는 커밋 뒤**다 — 커밋과 삭제 사이에 죽으면 다음 실행이 같은 델타를 다시 읽지만 PK에 막혀 건너뛰고 삭제만 한다. 순서를 뒤집어 삭제를 먼저 하면 커밋 전 장애에서 델타가 영구 유실된다.

이 세 층을 회귀 테스트(같은 버킷 2회 flush → 1회 반영, 2스레드 동시 flush → 1회 반영)로 고정해 두었다고까지 말하면, 안전망을 사람의 기억이 아니라 시스템에 두는 습관이 드러난다.

### "그럼 결제 잔액이나 재고도 같은 방식으로 Redis에 모았다 반영하면 되지 않나요?" (시니어 변별 포인트)

안 된다 — 그리고 **이유를 도메인 축으로** 말한다.

이 설계가 성립하는 전제는 "틀려도 되고 늦어도 된다"인데, 잔액은 유실 0·즉시 반영·감사 추적이 요구되고 `잔액 >= 0` 같은 불변식은 DB 제약이 지켜야 한다. Redis에 버퍼링하는 순간 **진실이 DB 밖으로 나가고**, `CHECK` 제약은 자기가 모르는 델타를 지켜 줄 수 없으며, Redis 장애 시 "돈이 사라지는" 유실 창이 생긴다.

게다가 쓰기 양상도 다르다. 잔액은 계정별로 분산돼 있어 핫 로우 자체가 드물다. 재고는 이벤트성으로 집중되지만 정확해야 하므로 **원자적 UPDATE + 조건(`WHERE qty >= :n`) + `CHECK` 제약**이 기본이고, 초당 5만 같은 극단에서는 Redis `DECR`로 **선점**하되 최종 확정은 여전히 DB 제약이 하는 구조로 간다(3장 [`20-concurrency-update-four-approaches.md`](../03-jpa-orm/20-concurrency-update-four-approaches.md)).

행 샤딩도 갈래 A에는 못 쓴다는 점을 덧붙이면 깊이가 드러난다 — 유실이 0인데도 못 쓰는 이유는 **불변식이 합계에 걸려 있기 때문**이다. 총합이 N행에 흩어져 있으면 `CHECK (cnt >= 0)`가 총합의 음수를 막지 못하고, 총합을 원자적으로 확인하려면 N행을 전부 잠가야 해서 경합을 나눈 의미가 사라진다.

PostgreSQL 특유의 덧붙임 두 개 — 잔액을 잠글 때는 `FOR UPDATE`가 아니라 **`FOR NO KEY UPDATE`**가 맞다(키가 아닌 컬럼만 바꾸는 갱신이라, 자식 테이블의 FK 삽입이 요구하는 `KEY SHARE` 락과 충돌하지 않는다). 그리고 결제 DB에서 `synchronous_commit = off`는 금지다 — 커밋 응답 후 유실 창이 생기는데, 그건 조회수에서나 협상 가능한 성질이다.

즉 같은 Redis라도 조회수에서는 **버퍼**(진실은 나중에 DB로), 재고에서는 **선점 게이트**(진실은 즉시 DB에)로 역할이 다르다. 이 구분을 못 하면 도구를 알고 도메인은 모르는 것으로 읽힌다.

### "'인기순' 정렬을 위해 `cnt`에 인덱스를 걸어두면 어떻게 되나요?" (가산점 포인트)

PostgreSQL에서는 **이 한 줄이 사슬 B의 스위치**다.

카운터 컬럼이 인덱스에 들어가는 순간 그 컬럼을 바꾸는 모든 UPDATE가 **HOT에서 탈락**하고, 새 튜플이 새 TID를 받으므로 그 테이블의 **모든 인덱스**에 새 엔트리가 꽂힌다 — 인덱스가 5개면 갱신 한 번에 인덱스 쓰기 5번, 초당 5,000건이면 초당 25,000번이다. 쌓인 죽은 엔트리는 VACUUM이 재사용 가능하게 만들 뿐 파일을 줄이지는 않아 인덱스 블로트가 남고, 회복하려면 `REINDEX CONCURRENTLY`가 필요하다. `pg_stat_user_tables`의 `n_tup_hot_upd / n_tup_upd` 비율 급락으로 바로 잡힌다.

게다가 "인기순"은 대개 최근 기간 기준이라 **누적 조회수 인덱스로는 답도 안 나온다.** 요구를 제대로 들으면 필요한 것은 "최근 7일 조회수 순위"인데 인덱스는 "전체 누적"을 정렬하고 있다.

처방은 정렬을 카운터 행에서 떼어내는 것이다. 버퍼링으로 DB UPDATE가 분당 1회로 줄면 인덱스 갱신도 분당 1회라 견딜 만하고, 더 정석은 인기 순위를 Redis Sorted Set(`ZINCRBY`)이나 주기 집계 테이블(원하면 그 위에 materialized view + `REFRESH MATERIALIZED VIEW CONCURRENTLY`)로 따로 관리해 **카운터 테이블에는 인덱스를 아예 두지 않는 것**이다. 행 샤딩 카운터를 골랐다면 정렬 자체가 불가능해진다는 대가도 여기서 다시 등장한다.

### "MySQL로 물어보면 답이 달라지는 부분은?" (경험 대조)

네 지점이다.

① **쓰기 증폭의 모양** — MySQL/InnoDB는 행을 제자리에서 고치고 옛 이미지를 언두 세그먼트에 두므로 테이블 자체는 안 부푼다(대신 언두가 자라고, purge가 밀리면 그 행을 읽을 때 버전 체인을 순회한다). PostgreSQL은 옛 버전이 힙에 남아 **핫 로우 = 테이블 블로트**다.

② **HOT이라는 완충 장치** — PostgreSQL에는 "인덱스를 안 건드리는 업데이트"라는 개념과 `fillfactor` 손잡이가 있어 "카운터 컬럼에 인덱스를 걸지 않는다"가 곧 성능 설계가 된다. MySQL/InnoDB에서는 그 결정이 이 정도로 결정적이지 않다.

③ **대기 안전판** — MySQL/InnoDB는 `innodb_lock_wait_timeout` 50초가 기본으로 줄을 끊어 주지만, PostgreSQL은 `lock_timeout` 기본이 0(무한)이라 직접 걸어야 한다.

④ **로그 구조** — MySQL/InnoDB는 redo + binlog 두 벌을 쓰고 복제도 binlog 기반이라 행 단위 병렬 적용 여지가 있는 반면, PostgreSQL은 WAL 하나이고 물리 복제 재생은 standby의 단일 프로세스라 같은 페이지 연타는 병렬화 여지가 없다.

이 넷을 짚으면 "핫 로우는 나쁘다"가 아니라 "이 엔진에서 왜 이렇게 나쁜가"를 말한 것이 된다. 반대로 갈림길(정확해야 하는 숫자인가 아닌가)과 완화 전략의 목록은 엔진과 무관하게 같다는 점도 함께 말하면 좋다.

## 한 줄 요약

**초고빈도 카운터를 RDB 행 하나에 직접 UPDATE하면 그 행의 락(PostgreSQL에서는 튜플 헤더 `xmax`)이 모든 요청을 직렬화해 초당 상한을 `1 / 락 보유 시간`에 묶고(락 보유 2ms면 초당 500건이 벽이며 서버를 늘려도 안 움직인다), PostgreSQL에는 락 대기 기본 타임아웃이 없어 줄이 끊기지도 않으며, 락을 기다리는 트랜잭션이 커넥션(= 프로세스)을 쥔 채 풀을 고갈시켜 무관한 API까지 무너뜨린다 — 그 뒤로 PostgreSQL 고유의 사슬이 붙는다. UPDATE마다 새 튜플 버전이 생겨 죽은 튜플이 페이지에 쌓이고, 페이지 여유가 마르거나 카운터 컬럼에 인덱스가 있으면 HOT이 깨져 모든 인덱스가 갱신되며, autovacuum은 이 속도를 못 따라가 블로트가 남아 읽기까지 느려진다. 그래서 설계는 기술이 아니라 **"이 숫자는 얼마나 정확해야 하는가"**라는 갈림길에서 시작한다 — 재고·잔액처럼 정확해야 하는 숫자는 원자적 UPDATE + 조건 + `CHECK` 제약이 최종 보증이고 버퍼링도 행 샤딩도 쓰지 않으며(불변식이 합계에 걸려 있어서), 조회수처럼 대략 맞으면 되는 숫자는 인덱스 제거와 `fillfactor` 낮추기를 위생으로 깔고 쓰기 지점을 행에서 떼어낸다(행 샤딩으로 경합만, 또는 Redis `INCR` 버퍼 + 시간 버킷 + `ON CONFLICT DO NOTHING RETURNING` 멱등 flush로 쓰기 총량까지 1/300,000). 그리고 유실을 허용했다면 상한을 숫자로 말하고(1분 버킷 + 1분 유예 + 10초 주기 = 최악 약 2분 10초치), 대사 배치와 드리프트 알람과 멱등성 회귀 테스트로 그 상한을 시스템이 감시하게 만든다.**
