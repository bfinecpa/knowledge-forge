# 이벤트 스키마 진화와 호환성 — 발행자와 소비자가 따로 배포되는 세계의 계약 관리

> 핵심 관전 포인트: **이벤트 스키마는 발행자와 소비자 사이의 계약이고,
> 양쪽은 다른 팀이 다른 배포 주기로 운영한다. 그래서 스키마 변경은 항상
> "구버전과 신버전이 공존하는 기간"을 전제로 설계해야 한다.
> backward compatibility는 새 스키마로 읽는 쪽이 옛 데이터를 읽을 수 있는 것
> (컨슈머를 먼저 배포 가능), forward는 옛 스키마의 컨슈머가 새 데이터를
> 읽을 수 있는 것(프로듀서를 먼저 배포 가능)이다. Schema Registry는 이
> 호환성 규칙을 스키마 등록 시점에 강제해서, 계약을 깨는 변경이 운영에
> 도달하기 전에 차단한다. 실무 원칙은 단순하다 — 필드 추가는 기본값과
> 함께, 삭제·이름 변경·타입 변경은 금지하거나 다단계(expand-contract)로.**

---

## 0. 질문 + 의도

**질문**: "이벤트 스키마가 변경될 때(스키마 진화) 호환성을 어떻게 관리하나요? (Schema Registry, forward/backward compatibility)"

**출제 의도**: 이벤트는 발행자와 소비자가 다른 팀·다른 배포 주기라서,
스키마 변경 하나가 남의 서비스를 깬다. REST API의 하위 호환성 개념을
비동기 세계로 확장해 사고할 수 있는지 — 즉 "내 변경이 언제 누구를
깨뜨리는가"를 배포 순서와 함께 추론하는 능력을 본다.

## 1. 왜 동기 API보다 어려운 문제인가

REST API의 하위 호환성과 비슷해 보이지만, 이벤트에는 두 가지가 더 붙는다.

1. **과거 데이터가 토픽에 남아 있다.** Kafka는 로그 기반이라
   리텐션 기간 내 옛 스키마로 쓰인 메시지가 그대로 저장돼 있다.
   컨슈머가 장애 복구나 재처리(replay)로 오프셋을 되감으면
   **몇 주 전 스키마의 메시지**를 지금의 코드로 읽어야 한다.
   동기 API에는 없는 "과거와의 호환성"이 생기는 것이다.
2. **배포 순서를 통제할 수 없다.** 발행자와 소비자가 다른 팀이면
   "프로듀서와 컨슈머를 동시에 배포"는 불가능하다. 어느 쪽이 먼저
   올라가도 안전한 방향을 스키마 변경 시점에 정해야 한다.

```java
// 발행 측이 가볍게 rename 한 줄을 배포한 순간 —
// Before
{ "orderId": 123, "userId": 45, "amount": 10000 }
// After (userId → memberId 로 이름 변경)
{ "orderId": 123, "memberId": 45, "amount": 10000 }

// 소비 측 코드는 그대로다
Long userId = event.getUserId();   // null 또는 역직렬화 실패
// → 다른 팀 서비스에서 NPE·DLQ 적재 폭증. 발행 팀은 원인을 모른다.
```

이 사고의 본질은 코드 버그가 아니라 **계약 관리의 부재**다.

## 2. backward vs forward — 방향을 정확히 구분하기

호환성 방향은 면접에서 가장 자주 헷갈리는 지점이다.
**"누구를 먼저 배포할 수 있는가"**로 기억하면 안 헷갈린다.

| 모드 | 정의 | 먼저 배포 가능한 쪽 | 허용되는 변경 |
|---|---|---|---|
| **Backward** | 새 스키마(읽는 쪽)가 **옛 데이터**를 읽을 수 있음 | 컨슈머 먼저 | 필드 삭제, 기본값 있는 필드 추가 |
| **Forward** | 옛 스키마(읽는 쪽)가 **새 데이터**를 읽을 수 있음 | 프로듀서 먼저 | 필드 추가, 기본값 있는 필드 삭제 |
| **Full** | 양방향 모두 | 어느 쪽이든 | 기본값 있는 필드의 추가/삭제만 |

풀어서 설명하면:

- **Backward compatible**: 컨슈머를 새 버전으로 올려도 토픽에 남아 있는
  옛 메시지를 읽을 수 있다. 예: 새 스키마에 `couponId` 필드를
  **기본값과 함께** 추가하면, 옛 메시지에 그 필드가 없어도 기본값으로
  채워 읽는다. **replay가 있는 Kafka 세계에서 기본으로 요구되는 방향**이다
  (과거 데이터를 항상 읽을 수 있어야 하므로).
- **Forward compatible**: 프로듀서가 새 스키마로 먼저 발행해도 아직
  구버전인 컨슈머가 깨지지 않는다. 예: 새 필드가 추가돼도 옛 컨슈머는
  모르는 필드를 무시하고 읽는다. 컨슈머 팀이 여럿이라 업그레이드 시점을
  통제 못 할 때 중요한 방향이다.
- 각 모드에는 **transitive 변형**이 있다 — 직전 버전 하나가 아니라
  **역대 모든 버전**과 호환을 요구한다. 리텐션이 길거나 compacted topic처럼
  아주 오래된 메시지가 남는 토픽이면 transitive가 안전하다. (가산점 포인트)

## 3. Schema Registry — 계약을 사람 리뷰가 아니라 시스템이 지키게

Schema Registry는 스키마의 중앙 저장소 + **호환성 게이트키퍼**다.
동작 방식:

1. 프로듀서가 직렬화할 때 스키마를 레지스트리에 등록/조회하고,
   메시지에는 스키마 전체가 아니라 **스키마 ID(몇 바이트)**만 실어 보낸다.
2. 컨슈머는 메시지의 스키마 ID로 레지스트리에서 스키마를 받아
   (로컬 캐시) 역직렬화한다. 페이로드 크기 부담 없이 스키마가 관리된다.
3. **핵심**: 토픽(subject)별로 호환성 모드(BACKWARD 등)를 설정해 두면,
   규칙을 위반하는 새 스키마는 **등록 자체가 거부**된다.
   `userId` rename 같은 변경이 운영에 도달하기 전에 막히는 것이다.

```text
Before: 스키마가 각 서비스 코드에만 존재
  → 변경이 깨뜨리는지 여부를 사람 리뷰와 운에 의존
After: Schema Registry + 호환성 모드 BACKWARD
  → 깨는 변경은 등록 거부 → CI 단계(빌드 시 호환성 검사 플러그인)에서
    이미 실패 → 운영 사고가 컴파일 에러 수준으로 앞당겨짐
```

직렬화 포맷은 Avro·Protobuf·JSON Schema를 지원하는데, Avro/Protobuf는
기본값·필드 번호 같은 진화 규칙이 포맷 자체에 내장돼 있어 레지스트리와
궁합이 좋다.

### 실무 변경 수칙 (expand-contract)

이름 변경·타입 변경처럼 호환 불가능한 변경은 **한 번에 하지 말고
여러 단계로 늘렸다 줄인다**:

```text
목표: userId(Long) → memberId(String) 로 교체

1단계(expand): memberId 필드를 기본값과 함께 추가, 프로듀서는
   userId와 memberId를 둘 다 채워 발행 (dual-write)
2단계(migrate): 모든 컨슈머가 memberId를 읽도록 순차 배포
   (배포 순서 자유 — 두 필드가 다 있으므로)
3단계(contract): 모든 컨슈머 전환 확인 후 userId 발행 중단·필드 제거
   (replay 범위를 고려해 리텐션 기간 이상 기다린 뒤 제거하면 안전)
```

## 4. 꼬리질문 대비 포인트

### "호환성 모드는 어떤 걸 기본으로 두나요? 왜요?"

**BACKWARD를 기본**으로 두는 경우가 일반적이다(Confluent 레지스트리의
기본값이기도 하다). 이유는 Kafka의 본질이 로그이기 때문 — 컨슈머는
언제든 과거 오프셋으로 되감아 **옛 스키마의 메시지를 읽을 수 있어야**
한다. 이는 곧 "새 코드가 옛 데이터를 읽는" backward 방향이다.
컨슈머 팀이 많아 업그레이드를 강제할 수 없는 조직이라면 FORWARD 또는
FULL을 검토하고, 리텐션이 긴 토픽은 transitive를 붙인다.

### "Schema Registry 없이 JSON을 쓰는 팀은 어떻게 관리하나요?"

레지스트리가 없어도 원칙은 같고, 강제 수단을 다른 곳에 둔다:

- **관용적 소비자(tolerant reader)**: 모르는 필드는 무시하고, 없는 필드는
  기본값 처리 (`FAIL_ON_UNKNOWN_PROPERTIES=false` 등). 이것만으로
  "필드 추가"가 안전해진다.
- **변경 수칙을 규약화**: 추가만 허용, 삭제·rename·타입 변경 금지,
  불가피하면 expand-contract.
- **스키마를 코드로 공유**: 이벤트 스키마 파일(JSON Schema, proto)을
  별도 저장소에 두고, CI에서 이전 버전과의 호환성 diff 검사 또는
  발행자-소비자 간 계약 테스트(CDC 테스트)를 돌린다.

핵심은 "사람이 조심한다"가 아니라 **깨는 변경이 자동으로 실패하는
장치가 어딘가에 있어야 한다**는 것이다.

### "필드의 타입을 꼭 바꿔야 한다면요?"

타입 변경은 어떤 호환성 모드에서도 대부분 불가라서, 위의
**expand-contract**로 푼다 — 새 이름의 새 필드를 추가하고, 이중 발행
기간을 거쳐, 전 소비자 전환 후 옛 필드를 제거. 제거 시점은
**리텐션/replay 가능 범위**까지 고려해서 잡는다. 급하다고 in-place로
바꾸면 그 순간부터 토픽 안에 두 가지 타입의 메시지가 섞인다.

### "스키마 호환성만 지키면 안전한가요?" (시니어 변별 포인트)

아니다. 레지스트리가 지켜주는 것은 **구조적 호환**뿐이고,
**의미(semantic) 변경은 통과시킨다.** 예: `amount` 필드를 "원 단위"에서
"전체 금액 → 할인 적용 후 금액"으로 의미만 바꾸면 스키마는 동일하지만
모든 소비자의 계산이 틀어진다. 의미가 바뀌는 변경은:

- 새 필드명으로 추가하거나(`amountAfterDiscount`),
- 아예 **새 이벤트 타입/버전 토픽**(`order-events.v2`)으로 분리하고
  소비자를 점진 이전시킨다. 토픽 버저닝은 이전 기간 동안 이중 발행과
  소비자 마이그레이션 추적 비용이 들지만, 계약이 크게 갈라질 때는
  섞어 쓰는 것보다 안전하다.

여기에 "스키마 진화는 fat event일수록 부담이 커진다 — 페이로드에 담긴
필드 전부가 계약이므로, 이벤트를 얇게 유지하는 것 자체가 호환성 관리
비용을 줄인다"까지 연결하면 설계 관점의 답이 된다. (가산점 포인트)

## 한 줄 요약

이벤트 스키마는 서로 배포 시점을 통제할 수 없는 팀들 사이의 계약이므로,
"어느 쪽을 먼저 배포해도, 그리고 과거 메시지를 replay해도 안 깨지는가"를
기준으로 backward/forward 호환을 정하고 — 그 규칙을 사람의 조심성이
아니라 Schema Registry(또는 CI의 호환성 검사)가 등록 시점에 강제하게
만드는 것이 스키마 진화 관리의 본질이다.
