# Kafka vs RabbitMQ — 로그 기반과 큐 기반, 구조 차이가 요구사항 선택으로 이어지는 길

> 핵심 관전 포인트: **근본 차이는 저장 모델이다. Kafka는 append-only
> 로그 — 메시지를 소비해도 삭제되지 않고 보존 기간 동안 남아 있어
> 컨슈머가 오프셋만 움직이며 읽고, 되감아 재소비(replay)할 수 있다.
> RabbitMQ는 전통적 큐 — 메시지를 컨슈머에게 밀어주고(ack 받으면 삭제)
> 라우팅·메시지 단위 제어에 강하다. 그래서 "재처리와 다수 독립
> 소비자가 필요한 이벤트 스트림"이면 Kafka, "복잡한 라우팅과 메시지
> 단위 처리가 필요한 작업 큐"면 RabbitMQ — 기능 목록 암기가 아니라
> 요구사항→구조 매핑으로 답하는 것이 핵심이다.**

---

## 0. 질문 + 의도

**질문**: "Kafka와 RabbitMQ(전통적 MQ)의 차이는?"

**출제 의도**: 로그 기반(재소비 가능) vs 큐 기반(소비 후 삭제)의 구조
차이가 "재처리가 필요한가"라는 요구사항과 어떻게 연결되는지 —
요구사항→기술 매핑 능력을 본다.

## 1. 근본 차이 — 메시지가 소비 후 어떻게 되는가

### RabbitMQ: 큐 — 소비하면 사라진다

우편함 모델이다. 브로커가 메시지를 컨슈머에게 **밀어주고(push)**,
컨슈머가 처리 확인(ack)을 보내면 브로커가 그 메시지를 **삭제**한다.
"이 메시지를 누가 처리했는가"를 브로커가 메시지 단위로 관리한다.

### Kafka: 로그 — 소비해도 남는다

CCTV 녹화 테이프 모델이다. 메시지는 파티션이라는 append-only 로그에
기록되어 **소비 여부와 무관하게 보존 기간 동안 남는다.** 컨슈머는
자기가 어디까지 읽었는지(오프셋)만 관리하며 **직접 당겨간다(pull).**
브로커는 "누가 읽었는지"에 관심이 없다 — 그래서:

- 여러 컨슈머 그룹이 **같은 데이터를 각자 독립적으로** 소비할 수 있고
- 오프셋을 되감아 과거 메시지를 **재소비(replay)**할 수 있다

이 한 가지 구조 차이에서 아래 기능 차이가 대부분 파생된다.

## 2. 구조 차이가 만드는 실무 차이

| 축         | Kafka (로그)                  | RabbitMQ (큐)                  |
|-----------|-----------------------------|-------------------------------|
| 소비 후 메시지  | 보존 기간까지 유지 → 재소비 가능         | ack 시 삭제 → 재소비 불가             |
| 전달 방식     | 컨슈머가 pull                   | 브로커가 push                     |
| 소비 진도 관리  | 컨슈머(그룹)의 오프셋                | 브로커가 메시지 단위 ack 추적            |
| 라우팅       | 단순 (토픽/파티션 키)               | 강력 (exchange: direct/topic/fanout 등) |
| 순서 보장     | 파티션 내 보장                    | 큐 단위, 단 재큐잉·다중 컨슈머 시 흔들림      |
| 실패 처리 단위  | 오프셋 (연속 진도)                 | 메시지 개별 (nack, 개별 재큐잉)         |
| 대표 강점     | 대용량 처리량, 스트림, 다수 독립 소비자     | 유연한 라우팅, 메시지 단위 제어, 지연/우선순위/TTL |

### 라우팅 — 브로커가 똑똑한가, 컨슈머가 똑똑한가

RabbitMQ는 **브로커가 똑똑하다.** exchange가 라우팅 키·패턴·헤더로
메시지를 적절한 큐에 분배한다 — "결제 실패 메시지만 이 큐로" 같은
조건 분배를 브로커 설정으로 푼다. Kafka는 **브로커는 단순하고
컨슈머가 똑똑하다.** 브로커는 로그에 쓰고 읽어줄 뿐, 필터링·분기는
컨슈머가 (또는 토픽을 나눠서) 해결한다. 이 단순함이 Kafka의 높은
처리량의 배경이기도 하다.

### 실패 처리 — 개별 ack vs 오프셋

RabbitMQ는 메시지 하나만 nack(거부)해서 재큐잉하거나 DLX(데드레터
exchange)로 보낼 수 있다 — **메시지 단위 재시도가 자연스럽다.**
Kafka는 오프셋이라는 "연속된 진도"만 있어서 중간의 한 건만 건너뛰는
개념이 없다. 실패한 메시지를 계속 붙잡으면 그 파티션 전체가 막히는
poison pill 문제가 생기므로 재시도 토픽/DLQ 토픽을 **직접 설계**해야
한다.

## 3. 요구사항 → 선택 매핑 (면접의 승부처)

기능 나열이 아니라 "우리 요구사항이 무엇인가"에서 출발한다.

**Kafka가 맞는 경우** — "데이터를 여러 곳에서, 여러 번 읽어야 한다":

- 하나의 이벤트를 여러 팀/서비스가 **독립적으로 구독** (주문 이벤트를
  알림·적립·정산·데이터 분석이 각자 소비)
- 컨슈머 버그로 잘못 처리한 데이터를 **되감아 재처리(replay)**해야 함
- 대용량 스트림 처리, 로그/메트릭 수집처럼 **처리량이 최우선**
- 이벤트를 "시스템의 사실 기록(로그)"으로 남겨 나중에 새 소비자가
  과거부터 읽게 하고 싶은 경우

**RabbitMQ가 맞는 경우** — "작업을 한 번 배달하고 끝내면 된다":

- 워커에게 작업을 분배하는 **작업 큐** (이미지 변환, 메일 발송)
- 라우팅 조건이 복잡 (수신자·유형별 분기 배달)
- **지연 메시지, 우선순위, 메시지별 TTL** 같은 메시지 단위 제어가 필요
- 메시지량이 크지 않고 브로커 운영을 가볍게 가져가고 싶은 경우

```text
판단 한 줄 정리:
"이 데이터를 나중에 다시 읽을 일이 있는가? 소비자가 늘어날 것인가?"
 → Yes: Kafka (로그)   → No, 배달하고 끝: RabbitMQ (큐)
```

## 4. 꼬리질문 대비 포인트

### "Kafka는 왜 그렇게 처리량이 높은가요?"

- 파티션 로그에 **순차 쓰기** — 디스크는 랜덤 I/O에 약하지만 순차
  I/O에는 매우 빠르다
- 메시지를 **배치**로 묶어 쓰고 읽음 (네트워크·디스크 왕복 절감)
- OS 페이지 캐시 활용, 브로커가 메시지 단위 상태(누가 ack했는지)를
  추적하지 않는 **단순한 브로커 설계**
- 파티션으로 **수평 확장** — 처리량이 필요하면 파티션과 브로커를 늘림

### "RabbitMQ로는 재처리가 정말 불가능한가요?"

기본 큐 모델에서는 ack된 메시지가 삭제되므로 불가능하다. 우회하려면
발행 시점에 별도 저장소에 복사해 두거나 재발행을 요청해야 한다.
다만 최근 RabbitMQ도 로그 기반의 스트림 기능을 추가해 경계가 흐려지고
있다 — "설계 기원이 다르고, 각자의 본진(라우팅 vs 스트림)에서 여전히
강하다"고 정리하면 균형 잡힌 답이 된다 (가산점 포인트).

### "메시지 하나가 계속 실패하면 두 시스템은 각각 어떻게 되나요?" (시니어 변별 포인트)

RabbitMQ는 그 메시지만 nack → DLX로 격리하면 **다른 메시지는 영향이
없다.** Kafka는 오프셋이 연속 진도라서 실패한 메시지 앞에서 커밋을
멈추면 **그 파티션의 뒤 메시지 전부가 막힌다(poison pill).** 그래서
Kafka에서는 "몇 회 재시도 후 실패 건을 DLQ 토픽으로 옮기고 오프셋은
전진"시키는 설계를 컨슈머에 직접 넣어야 한다. 이 차이를 아는 것이
"실패 경로까지 설계해 본 사람"의 표식이다.

### "순서 보장은 어느 쪽이 강한가요?"

Kafka는 **파티션 안에서 구조적으로 보장**된다 — 같은 키는 같은
파티션에 append 순서대로 쌓이고 그 순서로 읽힌다. RabbitMQ는 큐
자체는 FIFO지만, 컨슈머 여러 대가 붙거나 실패한 메시지가 재큐잉되면
처리 순서가 쉽게 흔들린다. "키 기반 순서 보장이 요구사항이면 Kafka의
파티션 키가 자연스러운 해법"이라고 연결하면 좋다.

### "그래서 지금 우리 서비스에는 뭘 고르실 건가요?"

정답을 하나 찍는 게 아니라 판단 기준을 말한다: "이벤트를 여러
소비자가 구독하고 재처리 가능성이 있으면 Kafka, 단순 작업 분배와
메시지 단위 제어(지연·우선순위)가 핵심이면 RabbitMQ를 고르겠다.
그리고 이미 팀이 운영 경험을 가진 브로커가 있다면 그 운영 역량도
비용 항목에 넣겠다"까지 말하면 도입 결정의 양면을 보는 사람으로
보인다.

---

## 한 줄 요약

Kafka는 "소비해도 남는 로그"라 재소비·다수 독립 구독·대용량 스트림에
강하고, RabbitMQ는 "배달하면 사라지는 큐"라 라우팅·메시지 단위 제어가
필요한 작업 분배에 강하다 — **"이 데이터를 다시 읽을 일이 있는가"라는
요구사항이 두 구조 중 하나를 가리킨다.**
