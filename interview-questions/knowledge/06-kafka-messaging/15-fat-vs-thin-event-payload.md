# Fat event vs Thin event — 페이로드 설계가 1년 뒤의 결합도와 장애 모드를 결정한다

> 핵심 관전 포인트: **이벤트 페이로드는 발행자의 내부 구현이 아니라
> 모든 컨슈머가 의존하는 공개 계약이다 — 한번 소비자들이 붙으면
> 사실상 비가역이라, 이 선택은 API 설계급의 무게를 가진다.
> fat event(전체 상태 동봉)는 소비자가 역조회 없이 자립하게 해주지만,
> 스키마가 전 소비자와의 결합점이 되고 개인정보가 브로커 리텐션
> 기간만큼 복제·전파된다. thin event(ID만)는 계약이 얇아 진화가 쉽지만,
> 소비자마다 발행자 API를 되부르며(조회 부하 N배) 이벤트로 끊었던
> 가용성 의존이 되살아나고, "조회 시점 상태 ≠ 이벤트 시점 상태"라는
> 시점 불일치가 생긴다. 1년 뒤 이 결정이 좌우하는 것은 세 가지 —
> 스키마 변경의 파급 범위, 발행자가 죽었을 때의 장애 모드,
> 대량 재처리(replay)가 가능한가다.**

---

## 0. 질문 + 의도

**질문**: "이벤트 페이로드에 전체 상태를 담을까(fat event), ID만
담을까(thin event)? 이 결정이 1년 뒤 시스템의 무엇을 좌우하나요?"

**출제 의도**: 비가역 설계 결정의 이벤트 설계 판. 페이로드 형태는 모든
컨슈머가 의존하는 계약이라 나중에 바꾸면 전 소비자가 흔들린다. fat은
소비자 자립(역조회 불필요) 대신 스키마 결합·개인정보 전파, thin은
느슨함 대신 조회 부하·시점 불일치 — 초기 결정 하나가 1년 뒤의 결합도와
장애 모드를 결정함을 아는지 본다.

## 1. 두 방식의 정체 — 통지인가, 상태 운반인가

같은 "주문 완료" 이벤트도 두 가지로 만들 수 있다:

```json
// thin event (notification event): "무슨 일이 있었다"는 통지만
{
  "eventType": "OrderCompleted",
  "orderId": 1234,
  "occurredAt": "..."
}

// fat event (event-carried state transfer): 상태를 통째로 운반
{
  "eventType": "OrderCompleted",
  "orderId": 1234,
  "occurredAt": "...",
  "userId": 88,
  "userEmail": "a@b.com",
  "items": [ { "productId": 7, "qty": 2, "price": 12000 } ],
  "totalAmount": 24000,
  "shippingAddress": "서울시 ..."
}
```

- **thin**: 소비자는 "주문 1234가 완료됐다"만 알고, 내용이 필요하면
  주문 서비스 API를 **되불러 조회**한다.
- **fat**: 이벤트 안에 필요한 상태가 다 있어 소비자가 **역조회 없이
  자립**한다. 소비자가 자기 DB에 복제본을 쌓아두는 패턴(event-carried
  state transfer)의 기반이다.

핵심 인식: **이 JSON의 모양은 발행자 마음대로 바꿀 수 있는 내부 구현이
아니다.** 소비자가 3팀 붙는 순간 이 스키마는 REST API 응답 스펙과 같은
공개 계약이 되고, 필드 하나 빼는 것도 전 소비자와의 협상이 된다.
그래서 "1년 뒤"를 묻는 것이다 — 지금은 어느 쪽이든 돌아가지만, 1년 뒤
바꾸려면 이미 늦다.

## 2. 1년 뒤 좌우되는 것 ① — 결합도: 무엇에 묶이는가

둘 다 결합이 생긴다. **어디에 묶일지를 고르는 문제**다.

**fat = 스키마 결합.** 이벤트에 담긴 모든 필드가 잠재적 의존점이다.
주문 서비스가 `shippingAddress`의 구조를 바꾸고 싶어도, 어느 소비자가
그 필드를 파싱하는지 전수 조사 전에는 못 바꾼다. 필드가 많을수록
결합 표면적이 넓어진다 — "혹시 몰라서 다 넣은" 필드 하나하나가 1년 뒤
변경을 막는 족쇄가 된다. 그래서 fat을 선택하면 Schema Registry와
호환성 규칙(하위/상위 호환) 같은 스키마 거버넌스가 사실상 필수
동반 투자다.

**thin = 가용성·API 결합.** 스키마는 ID뿐이라 거의 안 바뀌지만,
모든 소비자가 발행자의 조회 API에 런타임 의존한다. 이벤트로
비동기화해서 끊어냈던 "발행자가 살아있어야 한다"는 의존이 **뒷문으로
되살아나는 것**이다. 소비자가 5팀이면 이벤트 1건당 조회 5번 — 발행
트래픽이 조회 트래픽을 N배로 증폭시킨다.

## 3. 1년 뒤 좌우되는 것 ② — 장애 모드와 재처리

**발행자가 죽었을 때.** fat 소비자는 브로커만 살아있으면 계속 소비한다
(필요한 상태가 이벤트 안에 있으므로). thin 소비자는 조회가 실패하므로
같이 멈춘다 — 또는 재시도가 쌓여 발행자 복구 직후 조회 폭탄으로 2차
장애를 만든다. "이벤트 기반으로 격리했다"고 믿었던 장애 전파 경로가
thin에서는 살아있다.

**대량 재처리(replay)할 때.** 장애 복구로 지난 이벤트 100만 건을
재소비하는 상황 — fat이면 브로커에서 읽기만 하면 된다. thin이면
**발행자 API에 100만 건의 조회**가 발사된다. 재처리 자체가 발행자를
쓰러뜨리는 2차 장애가 되고, 결국 "재처리는 심야에 스로틀 걸고"라는
운영 제약이 생긴다. 재처리 가능성이 아키텍처의 전제라면(이벤트 소싱,
소비자 DB 재구축) 이 차이는 결정적이다.

**시점 불일치 — thin의 조용한 버그.** thin 소비자가 조회하는 것은
"이벤트 시점의 상태"가 아니라 **"조회 시점의 최신 상태"**다:

```
주문 상태가 빠르게 두 번 바뀜: 결제완료 → 배송중

이벤트: [OrderPaid(1234)]  [OrderShipped(1234)]  가 연달아 도착
소비자: OrderPaid를 받고 조회 → 이미 "배송중"이 읽힌다
        OrderShipped를 받고 조회 → 또 "배송중"

→ "결제완료" 상태는 어느 조회에도 잡히지 않았다.
  "결제완료 시점에 재고를 차감"하는 로직이라면 조용히 어긋난다.
```

중간 상태가 소비자에게 영영 보이지 않는 것 — 이벤트 폭주 시에만
간헐적으로 드러나서 원인 추적이 매우 어려운 유형이다. fat은 이벤트에
그 시점의 상태가 박제되어 있으므로 이 문제가 없다.

## 4. fat의 어두운 면 — 개인정보가 리텐션만큼 전파된다

fat의 대가는 스키마 결합만이 아니다. 페이로드에 이메일·주소·전화번호를
담는 순간:

- **브로커 리텐션 기간 동안 삭제할 수 없다.** Kafka 로그는 개별 레코드
  삭제가 안 되는 append-only 구조다. "회원 탈퇴 시 개인정보 즉시 삭제"
  요구와 정면 충돌한다.
- **다운스트림으로 무한 복제된다.** 소비자들이 자기 DB에 복제본을
  쌓으면, "우리 회사에서 이 사용자의 이메일이 저장된 곳"의 목록이
  이벤트를 구독한 팀 수만큼 늘어난다. 삭제 요청이 오면 그 전부를
  추적해야 한다.

방어선: 개인정보 필드는 페이로드에서 빼고 ID/토큰만 싣기(그 부분만
thin으로), 또는 사용자별 키로 암호화해 싣고 삭제 요청 시 키를 파기해
사실상 읽기 불능으로 만드는 crypto-shredding(가산점 포인트).
"fat으로 간다"는 결정에는 데이터 거버넌스 비용이 딸려온다는 것을
아는지가 시니어 변별 지점이다.

## 5. 실무의 답 — 이분법이 아니라 스펙트럼에서 자리 잡기

실무 답안은 "fat이냐 thin이냐"가 아니라 **기준을 갖고 중간 어딘가에
자리 잡는 것**이다.

- **하이브리드가 기본값.** ID + 대부분의 소비자가 공통으로 필요로 하는
  안정적인 핵심 필드(상태, 금액, 발생 시각) + 이번에 바뀐 필드만.
  "혹시 몰라서" 넣는 필드가 곧 미래의 결합이므로, 실제 소비자 요구가
  확인된 필드만 승격시킨다.
- **경계에 따라 다르게.** 같은 도메인 안(바운디드 컨텍스트 내부)의
  이벤트는 fat이어도 스키마 협상 비용이 낮다. 팀·도메인을 넘는
  통합 이벤트는 계약 변경 비용이 크므로 얇고 안정적으로 — "내부는
  두껍게, 외부 공개는 얇게"가 흔한 배치다.
- **선택 기준 체크리스트**: 소비자가 몇 팀이고 뭘 필요로 하나 /
  발행자가 소비자들의 조회 부하를 감당할 수 있나 / 재처리가 아키텍처의
  전제인가 / "이벤트 시점 상태"가 필요한 소비자가 있나 / 페이로드에
  개인정보가 섞이나.

## 6. 꼬리질문 대비 포인트

### "thin 이벤트인데 '이벤트 시점의 상태'가 필요한 소비자가 있다면?"

세 가지 경로가 있다. ① 그 소비자가 필요로 하는 시점 데이터만 이벤트에
승격시킨다(하이브리드) — 가장 흔한 답. ② 이벤트에 버전/시퀀스 번호를
싣고 발행자가 버전별 조회를 제공한다 — 발행자에 이력 저장 부담이
생긴다. ③ 요구가 전반적이면 그 이벤트는 fat이 맞는 것이다. "thin으로
정했으니 끝"이 아니라 소비자 요구가 설계를 되먹이는 구조로 답한다.

### "fat 이벤트의 스키마는 어떻게 안 깨지게 진화시키나?"

스키마를 코드 밖의 계약으로 관리한다 — Schema Registry에 등록하고
호환성 규칙을 강제한다. 실무 관용 규칙은 "필드 추가는 기본값과 함께,
삭제·타입 변경·의미 변경은 금지"다. 지키기 어려운 변경이 필요하면 새
버전 토픽(또는 새 이벤트 타입)을 나란히 발행하고 소비자를 순차
이전시킨다. 요컨대 REST API 하위 호환성 원칙을 비동기 세계로 확장한
것이다.

### "대량 replay 상황에서 두 방식은 어떻게 다르게 무너지나?"

fat은 브로커 읽기 + 소비자 처리 능력만이 제약이라 소비자 쪽 격리만
하면 된다. thin은 재처리 건수만큼의 조회가 발행자 API로 향한다 —
100만 건 replay가 발행자에 100만 조회를 쏘는 2차 장애 유발기가 된다.
thin으로 갈 거면 재처리 시나리오에서의 조회 스로틀링, 발행자 조회
전용 replica, 또는 "재처리용은 스냅샷에서 읽기" 같은 대비까지 설계에
포함돼야 한다.

### "이벤트에 개인정보를 실으면 안 되는 이유와, 실어야 한다면?" (시니어 변별 포인트)

Kafka 로그는 레코드 단위 삭제가 안 되므로 리텐션 동안 개인정보가
지워지지 않고, 소비자 DB로 복제되는 순간 삭제 요청 시 추적 범위가
구독 팀 수만큼 늘어난다. 실어야 한다면: 개인정보 필드만 ID 참조로
빼거나(부분 thin), 사용자별 키로 암호화 후 삭제 요청 시 키를 파기하는
crypto-shredding으로 "지울 수 없는 로그"를 "읽을 수 없는 로그"로
바꾼다. 페이로드 설계를 데이터 거버넌스 문제로 연결하는 것 자체가
변별 포인트다.

### "이미 thin으로 1년 운영했는데 조회 부하가 한계다 — 어떻게 전환하나?"

계약 변경이므로 빅뱅은 불가능하다. 기존 thin 이벤트는 그대로 두고
필드를 **추가**하는 방식으로 살찌운다(추가는 하위 호환) — 소비자들이
조회를 필드 참조로 하나씩 바꾸고, 전 소비자 이전이 확인되면 조회 API
의존을 끊는다. 반대 방향(fat→thin)은 필드 제거라서 더 어렵다 — 이
비대칭("살찌우기는 호환, 빼기는 파괴")이 처음에 얇게 시작하는 근거가
된다는 것까지 말하면 좋다.

## 한 줄 요약

이벤트 페이로드는 전 소비자가 의존하는 공개 계약이라 사실상 비가역이고,
fat은 소비자 자립·재처리 자유를 주는 대신 스키마 결합과 개인정보
전파를, thin은 얇은 계약을 주는 대신 조회 부하·발행자 가용성 재결합·
시점 불일치를 남긴다 — 1년 뒤의 스키마 변경 파급, 장애 전파 경로,
replay 가능성이 이 결정 하나에 걸려 있으므로, "ID + 검증된 핵심 필드"의
하이브리드에서 시작해 소비자 요구로 승격시키는 것이 실무의 답이다.
