# 컨슈머 리밸런싱 — 배포할 때마다 "알림이 두 번 가요"가 생기는 이유

> 핵심 관전 포인트: **리밸런싱은 컨슈머 그룹의 멤버 구성이나 구독
> 대상(파티션)이 바뀔 때 — 컨슈머의 합류/이탈/사망 판정, 파티션 증설 —
> 파티션 소유권을 다시 나누는 과정이다. 이때 처리 중이던 메시지는
> 회수되지 않는다: 컨슈머는 손에 든 메시지를 계속 처리하지만, 그 결과를
> 커밋하기 전에 파티션 주인이 바뀌면 새 주인은 "마지막으로 커밋된
> 오프셋"부터 다시 읽는다. 즉 리밸런싱의 대가는 유실이 아니라
> **중복 처리**이고(처리 후 커밋 기준), 배포 때마다 이 과정이 일어나므로
> 컨슈머는 반드시 멱등하게 만들어야 한다.**

---

## 0. 질문 + 의도

**질문**: "컨슈머 리밸런싱은 언제 발생하고, 처리 중이던 메시지는
어떻게 되나요?"

**출제 의도**: 배포할 때마다 중복 처리가 발생하는 이유의 정체를
아는지 본다. 리밸런싱을 모르면 "가끔 알림이 두 번 가요"라는 버그
리포트를 영원히 미제로 남긴다 — 리밸런싱의 발생 조건과 그 순간
in-flight 메시지의 운명(커밋 여부에 따른 중복/유실)을 연결해서
설명할 수 있는지가 관전 포인트다.

## 1. 리밸런싱이란 — 작업대 재배정

파티션은 같은 그룹 안에서 컨슈머 하나가 전담한다. 그런데 그 "누가
어느 파티션을 맡는가"라는 배정표는 고정이 아니다. **그룹의 멤버
구성이나 파티션 구성이 바뀌면 배정표를 다시 짜야 하고, 이 재배정
과정이 리밸런싱이다.** 그룹 코디네이터(브로커 중 하나)가 진행을
주관하고, 그룹 리더(컨슈머 중 하나)가 새 배정안을 계산한다.

발생 조건은 세 갈래로 정리하면 깔끔하다.

1. **멤버가 늘 때** — 새 컨슈머 합류 (스케일 아웃, 배포로 새 인스턴스
   기동).
2. **멤버가 줄 때** — 컨슈머의 정상 종료(그룹 탈퇴 통보), 또는 죽었다고
   **판정**될 때. 판정 기준은 두 가지다: 하트비트가 끊겨 세션 타임아웃
   초과(프로세스 사망·네트워크 단절·긴 GC), 또는 `poll()` 호출 간격이
   너무 길어 "살아 있지만 일을 못 한다"고 간주될 때. 이 두 타임아웃의
   구분은 별도 문서(22번, `max.poll.interval.ms` vs
   `session.timeout.ms`)에서 다룬다.
3. **구독 대상이 바뀔 때** — 토픽의 파티션 증설, 패턴 구독 중 새 토픽
   생성 등.

핵심 통찰: **배포 = 종료 + 기동이므로 리밸런싱이 최소 두 번은
일어난다.** 롤링 배포로 인스턴스 5대를 순차 교체하면 리밸런싱이
연쇄적으로 발생한다. "리밸런싱은 장애 상황"이 아니라 **일상 운영의
일부**라는 인식이 이 주제의 출발점이다.

## 2. 처리 중이던 메시지의 운명 — 회수가 아니라 재전달

리밸런싱이 나도 컨슈머 손에 있던 메시지를 Kafka가 뺏어가지는 않는다.
Kafka는 메시지를 "전달했다가 회수"하는 모델이 아니라, **컨슈머가
어디까지 읽었는지(오프셋 커밋)만 기록하는 모델**이기 때문이다.
따라서 운명을 결정하는 것은 단 하나 — **파티션을 잃는 순간, 처리한
데까지 커밋이 되어 있었는가.**

```text
파티션 P0: [... 100, 101, 102, 103 ...]
C1이 100~102를 폴링해 101까지 처리 완료, 커밋은 100까지만 된 상태
   ↓ 리밸런싱 발생, P0이 C2로 이동
C2는 "마지막 커밋 = 100"을 보고 101부터 다시 읽음
   → 101은 C1도 처리했고 C2도 처리한다 = 중복 처리
```

- **처리 후 커밋(일반적인 수동 커밋)**: 커밋 안 된 구간이 재전달된다 →
  **중복**. at-least-once의 본질이다.
- **처리 전 커밋(자동 커밋의 타이밍에 따라)**: 커밋은 됐는데 처리를
  못 끝낸 메시지는 새 주인이 건너뛴다 → **유실**.

그래서 결론은 명확하다. 리밸런싱이 존재하는 한 "정확히 한 번만
처리됨"을 컨슈머 배정만으로 보장할 수 없고, **중복을 정상 상황으로
받아들이는 멱등 컨슈머**가 전제되어야 한다.

이전 주인이 커밋을 시도하면 어떻게 될까? 파티션 소유권이 이미
넘어갔다면 커밋은 거부된다(`CommitFailedException`). 낡은 세대의
컨슈머가 커밋해서 새 주인의 진행 상황을 덮어쓰는 사고를 막기 위해,
그룹은 리밸런싱 때마다 **세대 번호(generation)** 를 올리고 이전 세대의
커밋을 거절한다 (가산점 포인트).

## 3. 리밸런싱의 비용과 완화 — eager vs cooperative, 정적 멤버십

전통적인(eager) 리밸런싱은 **stop-the-world**다: 그룹 전원이 자기
파티션을 전부 내려놓고, 재배정이 끝날 때까지 그룹 전체의 소비가
멈춘다. 파티션 하나가 이동하는 상황인데 나머지 멤버까지 일손을 놓는
것이 문제였고, 이를 개선한 것이 **협력적(cooperative, incremental)
리밸런싱**이다 — 실제로 이동해야 하는 파티션만 내려놓고 나머지는
계속 소비한다.

배포 시나리오에서 쓸 수 있는 완화 수단들:

```java
// 1) 정상 종료(graceful shutdown): close()가 그룹 탈퇴를 즉시 통보해
//    타임아웃 대기 없이 빠른 리밸런싱을 유도하고, 종료 전 커밋 기회를 준다.
Runtime.getRuntime().addShutdownHook(new Thread(consumer::wakeup));

// 2) 파티션을 내려놓기 직전에 처리분 커밋 — 중복 구간 최소화
consumer.subscribe(topics, new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> parts) {
        consumer.commitSync(currentProcessedOffsets);  // 처리 완료분만
    }
    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> parts) { }
});
```

- **정적 멤버십(static membership)**: `group.instance.id`를 지정하면
  컨슈머가 재시작해도 "같은 멤버가 돌아왔다"고 인식해, 세션 타임아웃
  안에 복귀하는 한 리밸런싱 자체를 생략한다. 재배포·재시작이 잦은
  환경에서 배포발 리밸런싱을 크게 줄인다 (가산점 포인트).
- Spring Kafka를 쓰면 컨테이너가 정상 종료 시 커밋과 그룹 탈퇴를
  처리해 주지만, **처리 로직이 멱등해야 한다는 요구는 사라지지
  않는다** — 어떤 완화책도 중복을 0으로 만들지는 못한다.

## 4. 꼬리질문 대비 포인트

### "리밸런싱 동안 메시지 소비는 완전히 멈추나요?"

프로토콜에 따라 다르다. eager 방식은 그룹 전원이 모든 파티션을
내려놓으므로 재배정이 끝날 때까지 그룹 전체가 멈춘다. cooperative
방식은 소유자가 바뀌는 파티션만 잠시 멈추고 나머지는 계속 소비한다.
"그래서 리밸런싱 프로토콜 설정이 소비 중단 시간(availability)에 직접
영향을 준다"까지 연결하면 좋다.

### "배포할 때마다 생기는 리밸런싱을 줄이는 방법은?"

세 가지 축으로 답한다. ① **정적 멤버십**으로 재시작을 멤버 교체가
아닌 복귀로 인식시킨다(재시작 시간 < 세션 타임아웃이 전제). ②
**cooperative 리밸런싱**으로 이동 범위를 최소화한다. ③ **정상
종료**를 보장해 죽은 것으로 판정될 때까지 기다리는 지연을 없애고,
`onPartitionsRevoked`에서 처리분을 커밋해 중복 구간을 줄인다.

### "중복 처리를 아예 없앨 수는 없나요?"

컨슈머 배정과 커밋 메커니즘만으로는 불가능하다. "처리"와 "커밋"이
서로 다른 시스템(내 DB vs Kafka)에 대한 두 개의 쓰기이기 때문에, 그
사이 어디서든 끊기면 중복 또는 유실 중 하나가 남는다. 실무 표준은
at-least-once + **멱등 컨슈머**(처리 이력 기반 중복 제거)이고,
Kafka 트랜잭션 기반 exactly-once는 Kafka 안에서 읽고 Kafka로 쓰는
파이프라인(스트림 처리)으로 범위가 제한된다.

### "onPartitionsRevoked에서는 무엇을 해야 하나요?"

내려놓는 파티션에 대해 **처리를 완료한 오프셋까지 동기 커밋**하는
것이 핵심이다(처리 중인 것까지 커밋하면 유실로 바뀐다). 그 외에
파티션 단위로 들고 있던 로컬 상태(버퍼, 캐시, 집계 중간값)가 있다면
플러시하거나 폐기한다. 이 콜백은 리밸런싱 절차 중에 호출되므로 오래
걸리는 작업을 넣으면 그룹 전체의 리밸런싱을 지연시킨다는 점도 짚으면
좋다.

### "리밸런싱이 잦으면 시스템에 어떤 비용이 생기나요?" (시니어 변별 포인트)

세 겹의 비용이다. ① **소비 중단** — 그 시간만큼 랙이 쌓이고, 실시간성
요구가 있는 파이프라인(알림, 정산)은 체감 지연이 된다. ② **중복
버스트** — 리밸런싱마다 커밋 안 된 구간이 재처리되므로, 다운스트림
(DB, 외부 API)에 중복 쓰기 부하가 몰린다. ③ **연쇄 위험** — 리밸런싱
후 밀린 랙을 따라잡느라 처리 시간이 길어지면 또 쫓겨나 다시
리밸런싱이 나는 악순환(rebalance storm)으로 번질 수 있다. 잦은
리밸런싱은 증상이지 원인이 아니므로, "왜 멤버가 자꾸 바뀌는가"를
타임아웃 설정과 처리 시간 관점에서 추적해야 한다(22번 문서).

## 한 줄 요약

리밸런싱은 그룹 멤버·파티션 구성이 바뀔 때마다 일어나는 소유권
재배정이고(배포마다 반드시 일어난다), 처리 중이던 메시지는 회수되지
않는 대신 **커밋 안 된 구간이 새 주인에게 재전달되어 중복 처리**된다
— 그래서 Kafka 컨슈머의 기본 소양은 리밸런싱 회피가 아니라
**멱등한 처리 로직**이다.
