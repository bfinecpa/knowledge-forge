# 컨슈머 재시도와 DLQ 설계 — 실패 메시지 하나가 파티션 전체를 막지 않게

> 핵심 관전 포인트: **파티션은 한 줄로 선 대기열이라, 실패한 메시지
> 하나를 붙잡고 무한 재시도하면 그 뒤의 모든 메시지가 멈춘다(poison
> pill). 그래서 실패 처리의 뼈대는 "실패를 분류하고, 회복 가능한
> 것만 제한된 횟수로 재시도하고, 끝내 안 되는 것은 DLQ로 치워 흐름을
> 살리는 것"이다. 재시도는 순서를 지키는 블로킹 방식과 순서를
> 포기하는 재시도 토픽 방식 중 도메인 요구에 맞춰 고르고, DLQ는
> 버리는 곳이 아니라 원인 분석과 재투입까지 이어지는 운영 절차의
> 시작점으로 설계한다.**

---

## 0. 질문 + 의도

**질문**: "컨슈머가 메시지 처리에 실패하면 어떻게 하나요?
재시도/DLQ(Dead Letter Queue) 설계를 설명해주세요."

**출제 의도**: 실패 메시지 하나가 파티션 전체를 막는 poison pill
문제를 아는지 확인한다. "실패하면 어떻게 되나"를 설계하지 않은
컨슈머는 반드시 운영에서 그 대가를 치른다 — 실패 경로를 미리
설계하는 습관이 있는 개발자인지 가리는 질문이다.

## 1. 왜 문제인가 — 파티션은 한 줄 대기열이다

Kafka 컨슈머는 파티션 안의 메시지를 **오프셋 순서대로 한 줄로**
읽는다. 큐 앞사람이 계산을 못 끝내면 뒷줄 전체가 멈추는 계산대와
같은 구조다. 그래서 "실패한 메시지를 어떻게 할 것인가"라는 질문은
사실 "이 계산대의 줄을 계속 흐르게 할 것인가"라는 질문이다.

가장 흔한 두 가지 잘못된 극단이 있다.

```java
// ❌ 극단 1: 예외를 삼키고 넘어간다 — 조용한 유실
@KafkaListener(topics = "orders")
public void consume(OrderEvent event) {
    try {
        orderService.process(event);
    } catch (Exception e) {
        log.error("처리 실패", e);   // 로그만 남기고 다음 메시지로
    }                                 // → 실패 메시지는 영영 사라진다
}

// ❌ 극단 2: 성공할 때까지 무한 재시도 — poison pill
@KafkaListener(topics = "orders")
public void consume(OrderEvent event) {
    while (true) {
        try {
            orderService.process(event);
            break;
        } catch (Exception e) {
            sleep(1000);   // 영구적 실패(잘못된 데이터)라면 영원히 반복
        }                  // → 이 파티션의 뒤 메시지 전부가 멈춘다
    }
}
```

극단 1은 데이터 유실이고, 극단 2는 **poison pill**(독약 알약) —
처리 불가능한 메시지 하나가 파티션 소비 전체를 중독시키는 상황이다.
게다가 극단 2는 `max.poll.interval.ms`(poll 사이 최대 허용 간격)를
초과해 브로커가 이 컨슈머를 죽었다고 판단, 리밸런싱까지 유발한다.
리밸런싱 후 다른 컨슈머가 같은 메시지를 받아 또 막히므로 **컨슈머
그룹 전체가 재시도-리밸런싱 루프에 갇힌다.**

### 실패의 분류가 설계의 출발점

모든 실패를 같게 다루면 안 된다. 두 부류로 나눈다.

- **일시적(transient) 실패**: DB 커넥션 고갈, 외부 API 타임아웃,
  락 경합 — 시간이 지나면 성공할 수 있다. → **재시도 대상**
- **영구적(permanent) 실패**: 역직렬화 실패(스키마 불일치), 검증
  실패(필수 필드 누락), NPE 같은 코드 버그 — 100번 재시도해도
  100번 실패한다. → **즉시 DLQ 대상**

영구적 실패를 재시도하는 것은 시간 낭비를 넘어 파티션 지연을
늘리는 해악이다. 이 분류를 예외 타입으로 코드에 박아두는 것이
실패 경로 설계의 첫 단추다.

## 2. 재시도 설계 — 순서를 지킬 것인가, 흐름을 지킬 것인가

### 2-1. 블로킹 재시도 (in-place retry)

같은 파티션 자리에서 백오프(재시도 간격을 점점 늘리는 것)를 두고
몇 번 재시도한 뒤, 초과하면 DLQ로 보내는 방식. Spring Kafka의
`DefaultErrorHandler`가 이 모델이다.

```java
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    // 실패 시 원본 토픽명 + ".DLT" 토픽으로 발행하는 복구기
    var recoverer = new DeadLetterPublishingRecoverer(template);

    // 1초 간격으로 최대 3회 재시도 후 recoverer(DLQ 발행) 실행
    var handler = new DefaultErrorHandler(recoverer,
            new FixedBackOff(1000L, 3));

    // 영구적 실패는 재시도 없이 즉시 DLQ로
    handler.addNotRetryableExceptions(
            DeserializationException.class,
            ValidationException.class);
    return handler;
}
```

- 장점: **파티션 내 순서가 유지된다.** 재시도가 끝날 때까지 뒤
  메시지를 읽지 않으므로, 같은 키의 이벤트가 순서대로 처리된다.
- 단점: 재시도하는 동안 그 파티션이 멈춘다. 재시도 횟수 × 백오프
  합계가 `max.poll.interval.ms`를 넘지 않게 계산해야 한다 —
  넘으면 리밸런싱이 터진다.

### 2-2. 논블로킹 재시도 (재시도 토픽 방식)

실패한 메시지를 별도 **재시도 토픽**(`orders.retry.5s`,
`orders.retry.1m` 같은 지연 단계별 토픽)으로 옮겨 발행하고, 원본
파티션은 즉시 다음 메시지로 넘어가는 방식. 재시도 토픽의 전용
컨슈머가 지연 후 다시 처리를 시도하고, 최종 실패하면 DLQ로 보낸다.
Spring Kafka는 `@RetryableTopic`으로 이 계층을 자동 생성해준다.

```java
@RetryableTopic(
        attempts = "4",                       // 원본 1회 + 재시도 3회
        backoff = @Backoff(delay = 5000, multiplier = 3.0),
        dltTopicSuffix = ".dlt")
@KafkaListener(topics = "orders")
public void consume(OrderEvent event) {
    orderService.process(event);   // 실패 시 재시도 토픽으로 자동 발행
}
```

- 장점: 실패 메시지가 본선 흐름을 막지 않는다. 긴 백오프(수 분
  단위)도 파티션 정지 없이 걸 수 있다.
- 단점: **키 순서가 깨진다.** 사용자 A의 "주소 변경" 이벤트가
  재시도 토픽으로 빠진 사이, 뒤에 온 A의 "주문 생성"이 먼저
  처리될 수 있다. 순서가 계약인 도메인에서는 이 방식이 정합성
  버그가 된다.

### 선택 기준

- **순서가 중요한 도메인**(잔액 변동, 상태 전이): 블로킹 재시도 +
  짧은 백오프. 순서를 지키는 대신 지연을 감수한다.
- **건별 독립 처리 도메인**(알림 발송, 로그 적재): 재시도 토픽.
  흐름을 지키는 대신 순서를 포기한다.

"어느 쪽이 정답"이 아니라 **무엇을 포기할지 도메인이 결정한다**고
답하는 것이 포인트다.

## 3. DLQ 설계 — 버리는 곳이 아니라 병원이다

DLQ는 실패 메시지의 종착역이 아니다. 쓰레기통처럼 운영하면 "DLQ에
30만 건이 쌓여 있는데 아무도 모르는" 상태가 된다. 세 가지를 설계에
포함해야 DLQ가 기능한다.

**(1) 진단 정보를 함께 담는다.** 원본 메시지만 복사하면 나중에
원인을 알 수 없다. Kafka 헤더에 원본 토픽·파티션·오프셋, 예외
클래스와 메시지, 실패 시각, 재시도 횟수를 실어 보낸다
(`DeadLetterPublishingRecoverer`가 기본으로 넣어주는 정보들이다).

**(2) 유입을 감시하고 알린다.** DLQ에 메시지가 들어오는 것 자체가
장애 신호다. DLQ 토픽의 적재량(또는 DLQ 컨슈머 랙)에 알림을 걸어,
"실패가 발생했다"를 사람이 즉시 알게 한다. 알림 없는 DLQ는
존재하지 않는 것과 같다.

**(3) 재투입(re-drive) 절차를 미리 만든다.** 원인을 고친 뒤(코드
배포, 외부 시스템 복구, 데이터 보정) DLQ의 메시지를 원본 토픽
또는 전용 재처리 경로로 다시 흘려보내는 도구/절차가 있어야 한다.
이때 본 처리와 중복될 수 있으므로 **컨슈머의 멱등성이 전제**다
— 같은 메시지를 두 번 처리해도 결과가 한 번과 같아야 한다.

비유하면 DLQ는 병원이다 — 줄을 막는 환자를 일단 대기열에서 빼내
(흐름 유지), 차트를 붙여(진단 헤더), 치료 후 일상에 복귀시킨다
(재투입). 시체 안치소처럼 운영하는 순간 데이터 유실과 같아진다.

(가산점 포인트: DLQ 재투입 시 "실패 당시의 코드"가 아니라 "수정된
현재 코드"로 처리되므로, 스키마가 그 사이 진화했다면 구버전
메시지를 현재 컨슈머가 읽을 수 있는지 — 하위 호환성 — 를 먼저
확인해야 한다고 짚으면 좋다.)

## 4. 꼬리질문 대비 포인트

### "재시도 횟수 제한 없이 성공할 때까지 재시도하면 안 되나?"

영구적 실패(잘못된 페이로드, 코드 버그)는 몇 번을 해도 실패하므로
무한 재시도는 poison pill이 된다 — 그 파티션의 뒤 메시지 전체가
멈추고, 처리 시간이 `max.poll.interval.ms`를 넘으면 브로커가
컨슈머를 그룹에서 제외해 리밸런싱이 발생한다. 재할당받은 다른
컨슈머도 같은 메시지에서 막히므로 그룹 전체가 리밸런싱 루프에
빠진다. 재시도는 반드시 "횟수 제한 + 초과 시 DLQ"와 세트다.

### "재시도 토픽 방식을 쓰면 무엇을 잃나?" (시니어 변별 포인트)

같은 키의 순서 보장을 잃는다. 실패 메시지가 재시도 토픽으로 빠진
사이 원본 파티션의 후속 이벤트가 먼저 처리되므로, "상태 변경 →
후속 처리"처럼 순서가 정합성의 전제인 도메인에서는 논블로킹
재시도가 곧 버그다. 대응은 (1) 순서 민감 도메인은 블로킹 재시도로
가거나, (2) 재시도 중인 키의 후속 메시지를 컨슈머가 감지해 함께
보류/재시도 경로로 보내는 키 단위 순서 유지 로직을 얹는 것인데,
(2)는 구현 복잡도가 커서 "그 복잡도를 감수할 만큼 논블로킹이
필요한가"부터 되묻는 게 실무 판단이다. 트레이드오프를 도메인
요구로 환원해 답하는 것이 변별 포인트.

### "어떤 예외는 재시도하고 어떤 예외는 바로 DLQ로 보내나?"

기준은 "시간이 지나면 결과가 달라지는가"다. 타임아웃·커넥션 실패·
락 경합은 일시적이라 재시도 가치가 있고, 역직렬화 실패·검증 실패·
NPE는 영구적이라 재시도가 무의미하므로 즉시 DLQ로 보낸다. 코드로는
예외 타입을 분리해 에러 핸들러에 등록한다(Spring Kafka
`addNotRetryableExceptions`). 이 분류를 안 하면 영구 실패 메시지가
재시도 횟수만큼 파티션을 붙잡아 지연을 키운다.

### "재시도하면 중복 처리가 생길 수 있지 않나?"

생긴다 — 처리는 성공했는데 오프셋 커밋 전에 실패한 경우 재시도가
곧 중복이고, DLQ 재투입도 중복 가능성이 있다. Kafka의 기본 세계관이
at-least-once(최소 한 번 전달, 중복 허용)이므로 재시도/DLQ 설계는
**멱등 컨슈머를 전제로 성립**한다. 이벤트 고유 키로 처리 이력을
기록해 두 번째 처리를 건너뛰는 방식이 대표적이다. "재시도 설계와
멱등성 설계는 한 몸"이라고 묶어 답하면 좋다.

### "DLQ에 쌓인 메시지는 실제로 어떻게 운영하나?"

들어오는 즉시 알림 → 헤더의 예외 정보로 원인 분류(코드 버그 /
외부 장애 / 데이터 오류) → 원인 수정 → 재투입 도구로 원본 처리
경로에 다시 투입 → 재투입 후 DLQ 비움 확인, 순서의 운영 루프를
만든다. 데이터 오류처럼 재처리가 불가능한 건은 비즈니스 부서와
협의해 수동 보정하거나 폐기를 결정하고 그 근거를 남긴다. "DLQ에
넣는 것"이 아니라 "DLQ에서 꺼내는 것"까지가 설계라는 답이 핵심이다.

## 한 줄 요약

파티션은 한 줄 대기열이라 실패 메시지 하나를 무한 재시도하면 뒤
전체가 멈추므로, 실패를 일시적/영구적으로 분류해 일시적 실패만
제한 횟수로 재시도(순서가 중요하면 블로킹, 흐름이 중요하면 재시도
토픽)하고 나머지는 진단 헤더를 붙여 DLQ로 치운 뒤 — 알림·원인
분석·재투입까지 이어지는 운영 루프를 멱등 컨슈머 위에 세우는 것이
재시도/DLQ 설계의 전부다.
