# 대량 이벤트 재처리(replay)와 실시간 격리 — 복구 작업이 2차 장애가 되지 않게

> 핵심 관전 포인트: **Kafka는 로그라서 과거 이벤트를 다시 읽는 것
> 자체는 쉽다 — 어려운 것은 100만 건 replay가 실시간 처리를 밀어내
> 2차 장애를 내지 않게 하는 것이다. 격리할 축은 세 개: (1) 소비
> 경로 — 기존 그룹의 오프셋을 되감지 말고 별도 컨슈머 그룹·별도
> 인스턴스로 읽는다, (2) 다운스트림 — DB·외부 API의 여유 용량만큼만
> 처리율을 제한한다, (3) 부수효과 — replay 표식을 달아 알림 재발송
> 같은 사용자 영향 동작을 차단하고, 전체를 멱등 처리 위에서
> 돌린다.**

---

## 0. 질문 + 의도

**질문**: "대량 이벤트 재처리(replay)가 필요한 상황에서 실시간
처리와 격리하는 방법은?"

**출제 의도**: 장애 복구로 100만 건을 replay할 때 실시간
트래픽까지 밀리게 하면 2차 장애다. 복구 작업 자체의 안전성을
설계하는, 한 단계 위의 운영 사고를 갖췄는지 확인한다.

## 1. replay는 왜 필요하고, 왜 위험한가

Kafka가 큐(소비하면 삭제)가 아니라 **로그(리텐션 기간 동안 보존,
오프셋만 되돌리면 재소비 가능)**라는 점이 replay의 근거다. 필요한
순간은 명확하다 — 컨슈머 버그로 3시간치 이벤트를 잘못 처리했거나,
다운스트림 장애 중 [스킵했던 구간](16-consumer-lag-diagnosis-and-resolution.md)을
복구하거나, 새 서비스/새 읽기 모델에 과거 이벤트를 부어 초기
상태를 만들 때다.

위험도 명확하다. replay는 평시 유입과 **비교가 안 되는 밀도**의
트래픽이다 — 3시간에 걸쳐 쌓인 100만 건을 몇 분 만에 읽어낼 수
있고, 이것이 세 곳을 짓누른다.

- **컨슈머 처리 용량**: 실시간 이벤트와 같은 경로로 흐르면 실시간
  처리가 뒤로 밀린다 — "복구하느라 지금 들어오는 주문이 30분
  밀리는" 2차 장애.
- **다운스트림**: 컨슈머가 쓰는 DB, 호출하는 외부 API가 replay
  물량을 그대로 맞는다. 평시 초당 100건 설계된 DB에 초당 5,000건이
  꽂히면 replay가 아니라 자체 DDoS다.
- **부수효과**: 이벤트 처리에 딸린 사용자 영향 동작 — 100만 건을
  다시 처리하면 100만 건의 푸시 알림이 다시 나간다. 데이터는
  복구됐는데 고객 신뢰가 장애 난다.

그래서 이 질문의 답은 "오프셋을 되감으면 됩니다"가 아니라 **세
축의 격리 설계**여야 한다.

## 2. 격리 설계 — 세 개의 축

### 2-1. 소비 경로 격리: 별도 그룹, 별도 인스턴스

가장 흔한 실수가 **기존 컨슈머 그룹의 오프셋을 과거로 리셋**하는
것이다.

```bash
# ❌ 실시간 그룹을 통째로 되감는다
kafka-consumer-groups.sh --group order-consumer \
  --topic orders --reset-offsets --to-datetime 2026-08-31T02:00:00.000 \
  --execute
# → 실시간 처리까지 3시간 전으로 되돌아간다.
#   최신 이벤트는 100만 건 뒤에 줄을 서고(실시간 지연),
#   이미 정상 처리된 구간 전체가 다시 처리된다(전량 중복).
```

정상 구간까지 재처리되고 최신 이벤트가 밀리므로 복구가 아니라
장애 확대다. 올바른 방향은 **replay 전용 컨슈머 그룹**을 새로
만들어 원하는 지점부터 읽게 하는 것 — 오프셋은 그룹별로 독립
저장되므로 실시간 그룹은 아무 영향을 받지 않는다.

```bash
# ✅ replay 전용 그룹을 만들어 그 그룹의 오프셋만 과거로 지정
kafka-consumer-groups.sh --group order-replay-20260831 \
  --topic orders --reset-offsets --to-datetime 2026-08-31T02:00:00.000 \
  --execute
# 실시간 그룹(order-consumer)의 오프셋은 그대로다.
```

그리고 이 그룹을 **기존 실시간 인스턴스가 아니라 별도로 띄운
replay 전용 애플리케이션(또는 배치 잡)**이 소비하게 한다. 같은
프로세스에 두 리스너를 얹으면 CPU·스레드 풀·DB 커넥션 풀을 실시간
처리와 나눠 쓰게 되어 프로세스 수준 격리가 깨진다. 별도 배포면
replay 쪽만 스케일 조절·일시정지·강제 종료할 수 있어 운영 통제권도
생긴다.

변형으로, 재처리 대상만 골라내야 하거나(특정 구간·특정 조건)
가공이 필요하면 **원본에서 추출해 별도 replay 토픽에 복사한 뒤 그
토픽을 소비**하는 방법도 있다. 원본 토픽의 소비 흐름과 물리적으로
분리되고, 재처리 범위가 토픽 자체로 명시되는 장점이 있다.

### 2-2. 다운스트림 격리: 처리율 제한

소비 경로를 분리해도 **다운스트림은 하나다** — replay 컨슈머와
실시간 컨슈머가 같은 DB에 쓴다. 격리의 실질은 여기서 결정된다.

- replay 컨슈머에 **처리율 제한(rate limit)**을 건다. 기준은 "내가
  내고 싶은 속도"가 아니라 **다운스트림의 여유 용량** — 평시 부하
  계측으로 DB가 초당 1,000건을 소화하고 실시간이 300건을 쓰고
  있다면, 안전 마진을 두고 replay에 초당 300~500건만 허용하는
  식이다.

```java
// replay 컨슈머 — 다운스트림 여유 용량만큼만 흘린다
private final RateLimiter rateLimiter = RateLimiter.create(300.0); // 초당 300건

@KafkaListener(topics = "orders", groupId = "order-replay-20260831",
               containerFactory = "replayContainerFactory")
public void replay(OrderEvent event) {
    rateLimiter.acquire();          // 처리율 제한 — 실시간 트래픽 보호
    orderService.reprocess(event);
}
```

- **시간대 선택**도 격리 수단이다 — 트래픽이 낮은 새벽에 돌리면
  같은 처리율로도 실시간 영향이 준다.
- replay 중 **다운스트림 지표(DB 응답 시간, 실시간 컨슈머의 랙)에
  알림을 걸어 두고**, 임계 초과 시 replay를 일시정지하는 스위치를
  준비한다. "밟는 것"보다 "멈출 수 있는 것"이 복구 작업의 안전
  요건이다.

(가산점 포인트: 브로커 관점의 부하도 있다 — 최신 데이터는 OS
페이지 캐시에서 읽히지만 오래된 세그먼트는 디스크에서 읽어야
하므로, 대량 replay는 브로커 디스크 I/O를 키우고 캐시를 오염시켜
같은 브로커의 다른 토픽 소비까지 느리게 할 수 있다. 처리율 제한이
브로커 보호이기도 하다는 것까지 말하면 좋다.)

### 2-3. 부수효과 격리: replay 표식과 멱등성

재처리는 "데이터를 다시 맞추는 것"이지 "그때의 모든 동작을
재연하는 것"이 아니다. 알림 발송, 이메일, 외부 시스템 통지 같은
**한 번만 일어나야 하는 부수효과**는 replay 경로에서 차단해야 한다.

```java
public void reprocess(OrderEvent event) {
    orderRepository.upsert(event);        // ✅ 상태 복구는 수행

    if (!replayContext.isReplay()) {      // replay 표식 확인
        notificationClient.sendPush(event); // ❌ 알림은 replay에서 차단
    }
}
```

표식은 이벤트 헤더에 `replay=true`를 싣거나, replay 전용 소비
경로(별도 리스너/토픽)라는 사실 자체로 구분한다. 그리고 replay
구간이 정상 처리 구간과 겹칠 수 있으므로(스킵 경계의 모호함,
at-least-once 중복) **전 과정이 멱등 처리를 전제**로 한다 — 같은
이벤트를 두 번 반영해도 결과가 같아야 replay를 "겹치게, 넉넉하게"
돌릴 수 있고, 그래야 경계를 정밀하게 맞추느라 유실을 감수하는
일이 없어진다.

## 3. 실무 시나리오 — 컨슈머 버그로 3시간치를 재처리

새벽 배포된 컨슈머 버그로 02:00~05:00 이벤트가 잘못 반영됐다고
하자. 절차는 격리 설계의 실행 순서가 된다.

1. **버그 수정 배포** — 실시간 흐름부터 정상화한다. replay는 그
   다음이다.
2. **재처리 범위 확정** — 타임스탬프 기준 오프셋 조회로 02:00
   시점의 파티션별 시작 오프셋을 구한다. 경계는 넉넉히 잡는다
   (멱등하므로 겹쳐도 안전).
3. **replay 전용 그룹 + 전용 인스턴스 기동** — 처리율 제한과
   replay 표식(알림 차단)을 켠 상태로.
4. **감시하며 진행** — 실시간 컨슈머 랙과 DB 지표를 보며, 임계
   초과 시 일시정지. 완료 예상 시간(건수 ÷ 처리율)을 공유한다.
5. **완료 검증 후 철거** — 대상 구간 처리 완료를 확인하고 replay
   그룹·인스턴스를 제거한다. 일회성 그룹 이름에 날짜를 박아
   (order-replay-20260831) 남은 그룹이 좀비가 되지 않게 한다.

여기서 "리텐션이 이미 지나 원본이 브로커에 없으면 replay 자체가
불가능하다"는 전제 조건도 짚을 수 있어야 한다 — 그래서 재처리
요구가 있는 토픽은 리텐션을 복구 소요 시간보다 길게 잡거나, 장기
보관소(오브젝트 스토리지 싱크)를 따로 둔다.

## 4. 꼬리질문 대비 포인트

### "그냥 기존 컨슈머 그룹의 오프셋을 과거로 리셋하면 안 되나?"

안 된다. 오프셋은 그룹 단위라 실시간 처리까지 통째로 되감긴다 —
최신 이벤트가 재처리 물량 뒤에 줄을 서서 실시간 지연이 생기고,
이미 정상 처리된 구간 전체가 중복 처리된다. 게다가 리셋은 그룹의
모든 컨슈머를 내린 상태에서만 가능해 그 순간 실시간 소비가
중단된다. "오프셋 리셋은 그룹 전체에 대한 수술"이므로, 수술은
실시간 그룹이 아니라 새로 만든 replay 그룹에 하는 것이 원칙이다.

### "replay 중 중복 처리는 어떻게 막나?"

막는 게 아니라 **무해하게 만든다**. replay 경계는 정밀하게 맞추기
어렵고(스킵 시점의 모호함, at-least-once 재전달) 정밀하게 맞추려다
좁게 잡으면 유실이 난다. 그래서 이벤트 고유 키로 처리 이력을 두고
두 번째 반영을 건너뛰는 멱등 컨슈머를 전제로, 경계를 넉넉히 겹치게
잡는 것이 실무 방식이다. "중복 방지가 아니라 중복 허용 설계"라고
프레임을 바꿔 답하면 좋다.

### "replay 처리율은 어떻게 정하나?" (시니어 변별 포인트)

"replay를 빨리 끝내고 싶은 속도"가 아니라 **다운스트림의 여유
용량에서 역산**한다. DB·외부 API의 평시 처리량과 실시간 트래픽
점유분을 계측해 남는 용량의 일부(안전 마진 포함)만 replay에
배정하고, 그 처리율로 완료 시간(건수 ÷ 처리율)을 계산해 "이
속도면 4시간 걸린다"를 이해관계자와 합의한다. 완료 시간이 허용
불가면 off-peak 시간대 실행이나 다운스트림 임시 증설을 조합한다.
속도-안전 트레이드오프를 수치로 협상하는 태도가 변별 포인트다.

### "재처리하고 싶은데 리텐션이 지나 브로커에 이벤트가 없다면?"

replay는 리텐션 안에서만 성립하므로 그때는 다른 원천이 필요하다 —
(1) 토픽을 오브젝트 스토리지로 싱크해 둔 장기 보관소에서 읽어
재발행, (2) Outbox 테이블이나 원천 DB에서 이벤트를 재구성해 발행,
(3) 애초에 재처리 요구가 있는 토픽은 리텐션을 복구 리드타임(장애
인지~복구 착수)보다 길게 설계. "리텐션은 스토리지 비용 설정이
아니라 복구 가능 기간의 설계"라는 관점으로 답하면 좋다.

### "새 서비스에 과거 이벤트 전체를 부어 초기화하는 경우도 같은 방식인가?"

격리 원칙(별도 그룹·처리율 제한·부수효과 차단)은 같지만 성격이
다르다 — 장애 복구가 아니라 계획된 대량 적재이므로, 처음부터
오프셋 earliest로 읽는 신규 그룹이면 되고 시간 여유가 있어 처리율을
더 보수적으로 잡을 수 있다. 이 용도가 상시적이라면 키별 최신값만
남기는 log compaction 토픽이 전체 히스토리 replay보다 초기화에
적합할 수 있다는 것까지 얹으면 가산점 포인트다.

## 한 줄 요약

Kafka가 로그라서 되읽기 자체는 쉽지만, 대량 replay의 본질은 복구
작업이 2차 장애가 되지 않게 하는 격리 설계다 — 기존 그룹을 되감는
대신 별도 컨슈머 그룹·별도 인스턴스로 소비 경로를 분리하고,
다운스트림 여유 용량에서 역산한 처리율 제한으로 실시간 트래픽을
보호하며, replay 표식으로 알림 같은 부수효과를 차단한 채 멱등 처리
위에서 경계를 넉넉히 겹쳐 돌리는 것이 정석이다.
