# Outbox + CDC — binlog를 이벤트 소스로: Kafka 발행 보장의 완성

> 핵심 관전 포인트: **DB와 Kafka는 한 트랜잭션으로 묶을 수 없으므로
> (이중 쓰기 문제), 이벤트를 비즈니스 변경과 같은 트랜잭션으로 outbox
> 테이블에 기록하고 별도 경로로 발행한다. CDC는 그 발행 경로를 DB
> 트랜잭션 로그(binlog) 테일링으로 구현한 것 — Debezium 같은 커넥터가
> outbox INSERT를 로그에서 감지해 Kafka로 흘린다. 커밋이 binlog에
> 남는 순간 발행이 예약된 것과 같아서 유실이 없고, 폴링과 달리 DB
> 부하·지연이 거의 없다. 보장은 전 구간 at-least-once — 커넥터
> 재시작 시 중복 발행이 가능하므로 멱등 컨슈머가 세트이고, 순서는
> binlog의 커밋 순서 + aggregate ID 파티션 키로 지킨다.**

---

## 0. 질문 + 의도

**질문**: "Kafka로 이벤트를 발행하는 서비스에서 \"DB 커밋은 됐는데
발행이 실패\"하는 문제를 어떻게 해결하나요? (Transactional Outbox + CDC)"

**출제 의도**: DB와 메시지 브로커라는 두 시스템에 걸친 원자성 문제의
표준 해법을 아는지 본다. 이 패턴의 필요성을 스스로 설명할 수 있으면
분산 정합성의 핵심을 이해한 것이다.

> 이중 쓰기 문제의 구조, AFTER_COMMIT의 한계, outbox 테이블·폴링
> 릴레이의 Spring 구현은 `02-spring/23-transactional-outbox-pattern.md`에
> 정리되어 있다. 이 문서는 **Kafka 관점 — CDC 연계, 발행 보장 체인,
> 순서와 중복** — 에 집중한다.

## 1. 문제 요약 — 커밋과 발행 사이엔 항상 틈이 있다

```java
// before: 커밋 후 발행 — 이 두 줄 사이 어디서든 죽을 수 있다
@Transactional
public void completeOrder(Long id) { ... }   // ① DB 커밋

kafkaTemplate.send("order-completed", event); // ② 발행 — ①과 ② 사이
                                              //    크래시/브로커 장애 → 이벤트 증발
```

커밋 → 발행이면 유실, 발행 → 커밋이면 거짓 이벤트. 순서 조정으로는
못 풀고, **원자성의 단위를 DB 하나로 모아야** 한다. 그래서 이벤트를
비즈니스 변경과 **같은 로컬 트랜잭션**으로 outbox 테이블에 INSERT한다
— 여기까지가 Outbox이고, 남은 문제는 "outbox에 쌓인 레코드를 누가,
어떻게 Kafka로 옮기느냐"다. 그 답이 폴링 또는 CDC다.

## 2. CDC — 폴링 대신 DB의 트랜잭션 로그를 구독한다

CDC(Change Data Capture)는 DB에 SELECT를 날리는 대신 **DB가 이미
쓰고 있는 트랜잭션 로그(MySQL binlog, PostgreSQL WAL)를 읽어 변경을
감지**하는 방식이다. Debezium이 대표 구현으로, Kafka Connect의 소스
커넥터로 동작한다:

```text
[App] --같은 TX--> [DB: 주문 UPDATE + outbox INSERT] --커밋--> [binlog에 기록]
                                                                    |
                              [Debezium 커넥터] <-- binlog 테일링 ---+
                                     |
                                     v  (outbox 레코드를 이벤트로 변환)
                              [Kafka: order-completed 토픽] --> [컨슈머]
```

DB 입장에서 Debezium은 **복제(replication) 클라이언트 하나가 더 붙은
것**과 같다. 레플리카가 binlog를 받아 자기 데이터를 갱신하듯,
Debezium은 binlog를 받아 Kafka로 흘린다. 이 관점이 서면 CDC의 성질이
자연스럽게 따라온다:

- **유실 없음**: 커밋이 binlog에 기록되는 것 자체가 DB 내구성의
  일부다. binlog에 남은 이상 커넥터가 (지금이든 재시작 후든) 반드시
  읽는다 — "커밋됐는데 발행 안 됨"이 구조적으로 사라진다.
- **DB 부하·지연 최소**: 폴링처럼 주기적 SELECT가 없다. binlog는
  순차 읽기라 부담이 적고, 커밋 → 발행 지연이 폴링 주기가 아니라
  로그 전파 속도(보통 밀리초 단위)로 줄어든다.
- **애플리케이션 코드에서 릴레이가 사라짐**: 스케줄러·SKIP LOCKED·
  발행 마킹 코드가 전부 인프라(커넥터)로 이동한다.

대가는 운영 부담이다 — Kafka Connect 클러스터와 Debezium 커넥터라는
새 구성요소의 배포·모니터링·장애 대응이 생긴다. 이벤트가 적고 몇 초
지연이 허용되면 폴링으로 시작하고, 규모가 커지면 CDC로 진화시키는
경로가 일반적이다.

### Outbox Event Router — 테이블 변경을 "이벤트"로 바꾸는 조각

Debezium이 기본으로 내보내는 건 "outbox 테이블의 행이 이렇게
바뀌었다"는 **테이블 변경 메시지**라서, 그대로 쓰면 컨슈머가 CDC
내부 포맷에 결합된다. Debezium의 outbox event router(SMT,
메시지 변환기)를 걸면:

- outbox 행의 `payload` 컬럼만 꺼내 이벤트 본문으로 만들고,
- `aggregate_type`으로 목적지 토픽을 라우팅하고 (예: ORDER →
  `order-events`),
- `aggregate_id`를 **메시지 키**로 실어 파티션 키가 되게 한다.

컨슈머는 CDC의 존재를 모른 채 평범한 도메인 이벤트를 받는다 —
"인프라 선택이 소비자 계약에 새어나가지 않게 한다"는 점을 언급하면
좋다. (가산점 포인트)

## 3. 발행 보장 체인 — 어디까지가 보장이고 어디부터가 내 몫인가

"Outbox + CDC를 쓰면 끝"이 아니라, 구간별로 보장 수단이 다르다는
것을 체인으로 설명할 수 있어야 한다:

| 구간 | 유실 방지 수단 | 중복 발생 지점 |
|---|---|---|
| 앱 → DB(outbox) | 로컬 트랜잭션 원자성 | 없음 (롤백되면 이벤트도 없음) |
| DB → Debezium | binlog 내구성 + 커넥터 오프셋 관리 | **커넥터 재시작 시 재발행** |
| Debezium → Kafka | Connect 내부 프로듀서 acks=all | ack 유실 시 재전송 |
| Kafka → 컨슈머 | 처리 후 오프셋 커밋 | 커밋 전 리밸런싱/장애 시 재처리 |

Debezium은 "binlog의 어디까지 읽어 Kafka에 넘겼는지"를 오프셋으로
저장하는데, **발행과 오프셋 저장이 원자적이지 않다** — 발행 후
오프셋 저장 전에 커넥터가 죽으면 재시작 후 같은 구간을 다시 읽어
**같은 이벤트가 한 번 더 발행**된다. 즉 전 구간의 보장은
at-least-once다. 그래서 결론은 언제나 같다:

```java
// 컨슈머: outbox 이벤트 ID 기반 멱등 처리 — CDC를 써도 이건 생략 불가
@KafkaListener(topics = "order-events")
@Transactional
public void consume(OutboxMessage msg) {
    if (!processedEventRepository.tryInsert(msg.eventId())) return; // 중복 스킵
    settlementService.settle(msg.payload());
    // 처리 이력 INSERT와 비즈니스 처리를 같은 TX로 → 소비 측 원자성
}
```

**생산 측(Outbox+CDC)은 유실 방지, 소비 측(멱등 컨슈머)은 중복
제거** — 이 역할 분담까지 말해야 완결된 답변이다.

## 4. 순서와 운영 — CDC라서 좋아지는 것, CDC라서 챙길 것

### 순서: binlog가 곧 커밋 순서다

폴링 릴레이를 멀티 인스턴스로 띄우면 같은 aggregate의 이벤트를 서로
다른 인스턴스가 집어 순서가 흔들릴 수 있었다. CDC는 이 문제가 구조적으로
없다 — binlog는 커밋 순서대로 기록된 단일 스트림이고, 한 테이블은
커넥터의 한 태스크가 순차로 읽는다. 여기에 outbox router가
`aggregate_id`를 메시지 키로 실어주므로 **같은 주문의 이벤트는 같은
파티션에 커밋 순서대로** 쌓인다. "커밋 순서 → binlog 순서 → 파티션
내 순서"로 이어지는 사슬을 설명할 수 있으면 좋다.

### outbox 테이블 정리: INSERT 직후 DELETE해도 된다

폴링 방식은 발행 여부를 status로 마킹하고 PUBLISHED를 주기적으로
지워야 했지만, CDC는 **binlog에서 읽으므로 테이블에 행이 남아 있을
필요가 없다**. INSERT와 DELETE를 같은 트랜잭션에서 해도 INSERT가
binlog에 남아 있어 이벤트는 정상 발행된다(커넥터가 DELETE 변경은
무시하도록 설정). outbox 테이블이 사실상 항상 비어 있게 되어 비대화
문제가 사라진다. (가산점 포인트)

### 챙겨야 할 운영 포인트

- **커넥터 생존 모니터링**: 커넥터가 죽으면 발행이 조용히 멈춘다 —
  에러가 앱 로그에 안 나오는 장애다. Connect 태스크 상태와 "커넥터가
  읽은 binlog 위치 vs DB의 현재 위치" 격차(랙)에 알람을 건다.
- **binlog 보존 기간**: 커넥터가 죽어 있는 시간이 binlog 보존
  기간을 넘기면 읽을 로그가 지워져 유실이 난다. 보존 기간을 장애
  대응 시간보다 넉넉히 잡아야 한다.
- **스키마 변경 주의**: outbox 테이블의 컬럼 구조는 커넥터 설정과
  결합돼 있다. payload 안에 이벤트 버전 필드를 두고, 테이블 DDL은
  커넥터 영향 검토 후 진행한다.

## 5. 꼬리질문 대비 포인트

### "폴링 릴레이 대신 CDC를 선택하는 기준은?"

트레이드오프 축은 지연·DB 부하·운영 복잡도다. 폴링은 스케줄러와
DB만으로 끝나 도입이 쉽지만 주기만큼 지연되고 주기적 SELECT가 DB를
때린다. CDC는 지연이 밀리초급이고 DB 부하가 거의 없지만 Kafka
Connect + Debezium이라는 인프라 운영이 새로 생긴다. 이벤트 빈도가
낮고 몇 초 지연이 허용되면 폴링, 이벤트가 많고 지연 요구가 빡빡하며
커넥터를 운영할 역량(모니터링 체계 포함)이 있으면 CDC — "우리 팀이
그 인프라를 감시·복구할 수 있는가"까지 판단 기준에 넣는다.

### "Debezium이 재시작하면 이벤트가 중복 발행되지 않나요?"

된다 — 그리고 그게 정상 동작이다. 커넥터는 Kafka 발행과 자신의
binlog 오프셋 저장을 원자적으로 못 하므로, 발행 후 오프셋 저장 전에
죽으면 재시작 시 같은 구간을 재발행한다. Outbox + CDC의 보장은
exactly-once가 아니라 at-least-once이고, 중복 제거는 소비 측 몫이다:
outbox 이벤트의 고유 ID를 처리 이력 테이블에 유니크 제약으로
INSERT해 이미 있으면 스킵하는 멱등 컨슈머를 세트로 구현한다.

### "이벤트 순서는 어떻게 보장되나요? 폴링 릴레이와 차이는?"

binlog는 커밋 순서의 단일 스트림이고 outbox 테이블은 커넥터 태스크
하나가 순차로 읽으므로, 발행 순서가 커밋 순서와 일치한다. 여기에
aggregate_id를 메시지 키로 실으면 같은 aggregate의 이벤트가 같은
파티션에 순서대로 쌓인다. 폴링 릴레이는 멀티 인스턴스일 때 같은
aggregate의 이벤트를 다른 인스턴스가 나눠 집으면 발행 순서가 흔들릴
수 있어 SKIP LOCKED·단일 릴레이 같은 추가 장치가 필요했다 — CDC는
이 문제를 구조로 없앤다.

### "커넥터가 며칠 죽어 있었는데 그 사이 binlog가 만료·삭제됐다면?" (시니어 변별 포인트)

읽을 로그가 사라졌으므로 그 구간의 이벤트는 CDC 경로로는 복구
불가다 — CDC의 유실 방지 보장은 "binlog가 남아 있는 동안"이라는
전제 위에 있다. 예방이 우선이다: binlog 보존 기간을 장애 감지 +
대응 시간보다 넉넉하게 잡고, 커넥터 다운·랙 증가에 알람을 걸어
보존 기간 안에 복구한다. 그래도 뚫렸다면 outbox(또는 원본 테이블)
데이터로 재발행하는 복구 배치가 필요한데, INSERT 직후 DELETE
전략을 쓰고 있었다면 outbox에도 데이터가 없으므로 원본 도메인
테이블 기준 재구성이 된다 — 이런 최악 시나리오까지 고려해 "즉시
DELETE 대신 짧은 보존 후 삭제"를 선택하는 팀도 있다. 보장의 전제
조건과 그 전제가 깨졌을 때의 복구 경로까지 말하는 것이 시니어
답변이다.

### "그냥 Kafka 트랜잭션(transactional producer)으로 DB 커밋과 묶으면 안 되나요?"

Kafka 트랜잭션은 "여러 파티션·토픽에 걸친 발행 + 컨슈머 오프셋
커밋"을 원자적으로 묶는 기능, 즉 **Kafka 세계 안의 원자성**이다.
외부 DB의 트랜잭션과는 묶이지 않으므로 이중 쓰기 문제를 못 푼다.
DB와 브로커를 아우르는 분산 트랜잭션(2PC)은 Kafka가 지원하지 않고
지원하더라도 가용성·성능 비용이 커서, 실무 표준은 로컬 트랜잭션
하나로 원자성을 모으는 Outbox다.

## 한 줄 요약

커밋과 발행 사이의 틈은 코드로 못 막는다 — 이벤트를 같은 트랜잭션으로
outbox에 남기고, CDC(Debezium)가 binlog를 테일링해 Kafka로 흘리면
"binlog에 남은 커밋은 반드시 발행된다"가 성립하며, 남는 중복
(at-least-once)은 멱등 컨슈머로, 순서는 binlog 커밋 순서 +
aggregate ID 파티션 키로 지켜 발행 보장을 완성한다.
