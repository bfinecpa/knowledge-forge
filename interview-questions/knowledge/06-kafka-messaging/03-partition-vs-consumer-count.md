# 파티션과 컨슈머 수의 관계 — 스케일 아웃의 상한은 토픽을 만들 때 이미 정해진다

> 핵심 관전 포인트: **하나의 컨슈머 그룹 안에서 파티션 1개는 정확히
> 컨슈머 1개에만 할당된다(반대로 컨슈머 1개는 여러 파티션을 맡을 수 있다).
> 따라서 그룹의 병렬 처리 상한 = 파티션 수이고, 파티션보다 많은 컨슈머는
> 아무 파티션도 배정받지 못한 채 유휴(idle) 상태로 논다.
> "컨슈머를 늘렸는데 처리량이 안 늘어요"의 정체가 바로 이것이며,
> 스케일 아웃의 최대치는 운영 중이 아니라 토픽 생성 시점(파티션 수 결정)에
> 이미 정해진다.**

---

## 0. 질문 + 의도

**질문**: "파티션과 컨슈머 수의 관계는? 컨슈머를 파티션보다 많이 띄우면
어떻게 되나요?"

**출제 의도**: "컨슈머를 늘렸는데 처리량이 안 늘어요"라는 실제 상황의
원인을 아는지 확인한다. 스케일 아웃의 상한이 설계 시점(파티션 수)에
결정된다는 것을 알아야 처음부터 파티션 수를 맞게 잡을 수 있다 —
운영 중에 컨슈머만 늘리며 헛수고하는 사람과, 설계 단계에서 상한을
계산하는 사람을 가르는 질문이다.

## 1. 기본 규칙 — "한 작업대에는 한 명만"

비유부터: 파티션은 **작업대**, 컨슈머 그룹은 **작업조**다.
Kafka의 규칙은 단순하다 — **같은 작업조 안에서, 한 작업대는
반드시 한 명이 전담한다.** 한 명이 여러 작업대를 오가며 맡을 수는 있어도,
두 명이 한 작업대를 같이 쓰는 일은 없다.

파티션 3개짜리 토픽을 예로 들면:

```text
컨슈머 1개:  C1 → [P0, P1, P2]           # 혼자 3개 전담
컨슈머 2개:  C1 → [P0, P1], C2 → [P2]    # 나눠 가짐 (편중 발생 가능)
컨슈머 3개:  C1 → [P0], C2 → [P1], C3 → [P2]   # 1:1, 병렬성 최대
컨슈머 4개:  C1 → [P0], C2 → [P1], C3 → [P2], C4 → (없음)  # C4는 유휴
```

왜 이런 규칙을 두었을까? 두 가지 이유다.

1. **순서 보장**: 파티션은 Kafka에서 순서가 보장되는 유일한 단위다.
   두 컨슈머가 한 파티션을 나눠 읽으면 처리 순서가 뒤섞인다.
2. **오프셋 관리의 단순함**: "이 파티션을 어디까지 읽었는가"(오프셋
   커밋)를 파티션당 주인 하나가 관리하니 경합 없이 단순해진다.

즉 파티션은 **순서 보장의 단위이면서 동시에 병렬성의 단위**다.
이 이중성이 Kafka 이해의 출발점이다.

## 2. 컨슈머를 파티션보다 많이 띄우면 — 에러가 아니라 침묵

파티션 3개 토픽에 컨슈머 4개를 띄워도 **에러는 나지 않는다.**
4번째 컨슈머는 그룹 가입까지는 정상적으로 하지만, 파티션을 하나도
배정받지 못하고 조용히 논다. 로그에 경고 한 줄 없이 CPU만 차지하는
경우가 많아서, "인스턴스를 5대로 늘렸는데 왜 랙이 안 줄지?"라는
상황이 벌어진다.

```text
# Before: 파티션 3개인데 컨슈머 6대로 스케일 아웃
#   → 3대만 일하고 3대는 유휴. 처리량 변화 없음. 비용만 2배.

# After: 처리량 상한을 올리려면 선택지는 둘 중 하나
#   1) 파티션 수 자체를 늘린다 (부작용 있음 — 아래 꼬리질문 참고)
#   2) 컨슈머 1대의 처리 속도를 올린다 (배치 폴링, 내부 병렬화)
```

Spring Kafka에서도 같은 함정이 있다. `concurrency` 설정은
"리스너 컨테이너가 내부에 몇 개의 컨슈머(스레드)를 만들지"인데,
이 역시 파티션 수를 넘으면 초과분은 논다.

```java
// Before: 파티션 3개 토픽에 concurrency 10 — 7개 스레드는 유휴
@KafkaListener(topics = "order-events", concurrency = "10")
public void handle(OrderEvent event) { ... }

// After: 파티션 수 이하로. 인스턴스 수 × concurrency ≤ 파티션 수
@KafkaListener(topics = "order-events", concurrency = "3")
public void handle(OrderEvent event) { ... }
```

인스턴스가 여러 대라면 **(인스턴스 수 × concurrency)의 총합**이
그룹의 컨슈머 수라는 점도 놓치기 쉽다. 3대 × concurrency 3 = 컨슈머
9개이므로, 파티션이 9개는 되어야 전부 일한다.

## 3. 실무 맥락 — 상한은 설계 시점에 결정된다

이 질문이 진짜 묻는 것은 "그래서 파티션 수를 언제, 어떻게 정하느냐"다.

- **컨슈머 스케일 아웃은 파티션 수라는 천장 아래에서만 유효하다.**
  트래픽이 늘 때 컨슈머 추가는 몇 분이면 되지만, 그 천장(파티션 수)을
  올리는 일은 별개의 운영 작업이고 부작용이 있다.
- 그래서 토픽 생성 시 **"목표 처리량 ÷ 컨슈머 1대의 처리량 + 성장
  여유"**로 파티션 수를 산정한다 (가산점 포인트 — 산정 공식을 먼저
  말하면 설계 경험이 드러난다).
- 다만 "그럼 처음부터 1000개로 잡자"도 답이 아니다. 파티션이 많을수록
  브로커의 메타데이터·복제 부담, 리밸런싱 시간, 장애 복구 시간이
  늘어난다. 상한과 비용 사이의 **계산된 타협**이 정답이다.

유휴 컨슈머가 항상 낭비인 것도 아니다. 파티션 수와 같은 수의 컨슈머에
+1대를 **대기(standby)** 용도로 두면, 컨슈머 한 대가 죽었을 때 새
인스턴스 기동을 기다리지 않고 즉시 이어받을 수 있다. 다만 이어받는
과정 자체는 리밸런싱이므로 무중단은 아니다.

## 4. 꼬리질문 대비 포인트

### "반대로 컨슈머가 파티션보다 적으면 어떻게 되나요?"

한 컨슈머가 여러 파티션을 맡는다. 동작에는 문제가 없지만 두 가지를
살펴야 한다. 첫째, 그 컨슈머가 처리량 병목이 되어 랙이 쌓일 수 있다.
둘째, 할당 전략에 따라 파티션이 고르게 분배되지 않을 수 있다 —
컨슈머 2개에 파티션 3개면 한쪽이 2개를 맡아 부하가 기운다.

### "왜 같은 그룹의 두 컨슈머가 한 파티션을 같이 읽으면 안 되나요?"

파티션 안에서의 순서 보장과 오프셋 커밋 모델이 깨지기 때문이다.
둘이 같은 파티션을 읽으면 어떤 메시지를 누가 처리했는지, 오프셋을
어디까지 커밋해야 하는지 조율하는 분산 합의 문제가 생긴다. Kafka는
이 문제를 "파티션당 주인은 하나"라는 규칙으로 아예 없애버렸다.
단, 이 제약은 **같은 그룹 안에서만**이다. 서로 다른 컨슈머 그룹은
같은 파티션을 각자의 오프셋으로 독립적으로 읽는다 — 하나의 주문
이벤트를 알림 서비스 그룹과 정산 서비스 그룹이 각각 소비하는 구조가
가능한 이유다.

### "처리량이 부족하면 파티션을 늘리면 되는 것 아닌가요?" (시니어 변별 포인트)

"늘리면 되지"가 아니라 부작용을 먼저 말해야 한다. 파티션을 늘리면
**키 → 파티션 매핑이 바뀐다.** 같은 사용자 ID의 이벤트가 증설 전에는
P1으로, 증설 후에는 P4로 가면서 **키 기반 순서 보장이 그 경계에서
깨진다.** 순서에 의존하는 컨슈머가 있다면 이는 정합성 사고다.
또 파티션 수는 줄일 수 없는 단방향 결정이다. 그래서 실무 순서는:
① 컨슈머 1대의 처리 속도 개선(배치 크기, 다운스트림 최적화, 내부
병렬화)을 먼저 시도하고, ② 그래도 부족하면 순서 의존성을 확인한 뒤
파티션 증설을 계획한다.

### "유휴 컨슈머는 무조건 제거해야 하나요?"

비용 관점에선 제거가 맞지만, 의도적으로 두는 경우가 있다 — 장애 대비
핫 스탠바이. 컨슈머 한 대가 죽으면 유휴 컨슈머가 리밸런싱을 통해
그 파티션을 즉시 이어받으므로, 새 인스턴스가 뜨는 시간만큼의 처리
공백을 줄인다. "낭비 vs 가용성 버퍼"의 트레이드오프로 답하면 좋다.

### "여러 토픽을 하나의 그룹으로 구독하면 할당은 어떻게 되나요?" (가산점 포인트)

할당 전략(assignor)에 따라 다르다. 기본 계열인 range 방식은 토픽별로
파티션을 정렬해 앞 컨슈머부터 배정하기 때문에, 토픽이 여러 개면
**각 토픽의 0번 파티션들이 전부 첫 컨슈머에게 몰리는 편중**이 생길 수
있다. round-robin이나 sticky 계열은 전체 파티션을 섞어 고르게
분배한다. sticky/cooperative-sticky는 여기에 더해 리밸런싱 때 기존
할당을 최대한 유지해 이동 비용을 줄인다 — 할당 전략 이름까지 나오면
운영 경험이 드러난다.

## 한 줄 요약

같은 그룹 안에서 파티션 하나의 주인은 컨슈머 하나뿐이므로 **병렬성의
상한 = 파티션 수**이고, 파티션보다 많은 컨슈머는 에러 없이 조용히
논다 — 그래서 처리량의 천장은 컨슈머를 늘리는 운영 시점이 아니라
파티션 수를 정하는 **설계 시점에 이미 결정된다.**
