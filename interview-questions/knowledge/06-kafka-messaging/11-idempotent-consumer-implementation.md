# 멱등 컨슈머 구현 — 중복은 예외가 아니라 정상 동작이다

> 핵심 관전 포인트: **at-least-once 세계에서 중복 수신은 버그가 아니라
> 스펙이다 — 커밋 전 크래시, 리밸런스, 프로듀서 재발행, 대량 재처리
> 어디서든 온다. 멱등 컨슈머는 같은 메시지를 두 번 처리해도 결과가 한
> 번과 같게 만드는 것으로, 구현은 두 축이다: ① 연산 자체를 멱등하게
> 설계(절대값 세팅, UPSERT, 상태 기계 조건부 전이) — 가능하면 최선.
> ② 처리 이력 기반 중복 제거 — 프로듀서가 발급한 이벤트 ID를 멱등 키로,
> 이력 테이블(unique 제약)과 비즈니스 변경을 **같은 DB 트랜잭션**으로
> 묶는다. 키 선정·저장소·원자성, 이 세 디테일이 구현의 성패를 가른다.**

---

## 0. 질문 + 의도

**질문**: "멱등 컨슈머(idempotent consumer)를 어떻게 구현하나요?"

**출제 의도**: at-least-once 세계에서 중복은 예외가 아니라 정상
동작이다. 처리 이력 기반 중복 제거의 구현 디테일(키 선정, 저장소,
원자성)까지 들어가는지로 실전 경험을 가린다 — "중복 체크하면 된다"
수준과 "체크와 반영이 원자적이지 않으면 레이스에서 뚫린다"를 아는
수준의 차이를 보는 질문이다.

## 1. 왜 중복이 "정상"인가 — 도착 경로부터

멱등 처리가 방어해야 할 중복은 한 곳에서 오지 않는다:

- **컨슈머 쪽**: 처리 완료 후 오프셋 커밋 전에 크래시·리밸런스 →
  같은 메시지 재수신 (05번 문서). 배포할 때마다 리밸런스가 일어나므로
  이건 "배포 = 중복 발생 가능 이벤트"라는 뜻이다.
- **프로듀서 쪽**: 앱 레벨 재시도·재기동 후 재발행 — 멱등 프로듀서
  설정으로도 못 막는 비즈니스 레벨 중복 (07번 문서).
- **운영 쪽**: 장애 복구를 위한 오프셋 되감기, 대량 이벤트 재처리
  (replay). 이때는 과거 메시지 전체가 "합법적으로" 다시 온다.

경로가 이렇게 많으니 "중복이 오면 어떡하지"가 아니라 **"중복은
반드시 온다"를 전제로 컨슈머를 설계**하는 것이 출발점이다.

## 2. 전략 1 — 연산 자체를 멱등하게 (가능하면 최선)

별도 인프라 없이, 두 번 실행해도 결과가 같은 연산으로 바꿀 수 있는지
먼저 본다.

### 상대 연산 → 절대 상태 세팅

```java
// before: 상대 연산 — 두 번 오면 두 번 적립된다
@KafkaListener(topics = "point-events")
public void handle(PointEvent event) {
    member.addPoint(event.amount());   // point += amount ❌
}

// after: 이벤트에 결과 상태를 실어 절대값으로 세팅
public void handle(PointEvent event) {
    member.setPoint(event.totalPoint());  // point = totalPoint ✅
    // 같은 이벤트가 몇 번 와도 같은 값 — 자연 멱등
}
```

(단, 절대값 방식은 이벤트 **순서**가 지켜질 때만 안전하다 — 파티션 키
설계와 엮이는 지점.)

### INSERT → UPSERT

"있으면 갱신, 없으면 삽입"을 DB가 원자적으로 처리하게 한다
(`INSERT ... ON CONFLICT DO UPDATE`, MySQL의
`INSERT ... ON DUPLICATE KEY UPDATE` 등). 같은 키의 재수신은 같은 행을
같은 값으로 덮을 뿐이다.

### 상태 기계 — 조건부 전이

```sql
-- "결제완료 → 배송준비" 전이: 현재 상태를 조건에 박는다
UPDATE orders SET status = 'PREPARING'
 WHERE id = :orderId AND status = 'PAID';
-- 첫 처리: 1 row 갱신. 중복 처리: 이미 PREPARING이라 0 row → 무시하고 ack
```

갱신된 행 수가 0이면 "이미 처리됨"으로 보고 조용히 넘어간다. 도메인이
상태 기계로 모델링되는 경우(주문, 정산, 구독) 가장 자연스러운 멱등이다.

## 3. 전략 2 — 처리 이력 기반 중복 제거 (범용 해법)

"이메일 발송", "포인트 적립(총액을 못 싣는 경우)"처럼 연산을 멱등하게
못 바꾸는 경우의 범용 패턴. 여기서 출제 의도가 짚는 3대 디테일이 나온다.

### 3-1. 키 선정 — 무엇으로 "같은 메시지"를 판별하나

정석은 **프로듀서가 발급한 이벤트 고유 ID**(UUID 등, Outbox 패턴이라면
outbox 행의 PK)를 페이로드나 헤더에 싣는 것이다. 소비 쪽에서 뭘 조합해
만드는 것보다, **이벤트가 태어날 때 신분증을 쥐여주는** 쪽이 확실하다.

`토픽-파티션-오프셋` 조합은 쓰지 않는 것이 좋다 — 토픽 재생성,
다른 토픽으로의 재발행, 미러링 환경에서 같은 비즈니스 이벤트에 다른
좌표가 붙어 중복 판별이 뚫린다. 위치 기반 키가 아니라 **비즈니스 의미
기반 키**가 원칙이다.

### 3-2. 저장소와 원자성 — 이력과 비즈니스 변경을 한 트랜잭션에

```java
// before: 체크와 반영이 분리 — 두 군데서 깨진다
public void handle(OrderEvent event) {
    if (redis.exists(event.eventId())) return;  // ① 체크
    orderRepository.save(toOrder(event));       // ② 반영 (DB)
    redis.set(event.eventId(), "done");         // ③ 기록 (Redis)
}
// ②와 ③ 사이 크래시 → 이력 없음 → 재수신 시 ② 재실행 = 중복
// ①을 통과한 두 요청이 동시에 ②로 진입하는 레이스도 그대로 열려 있다
```

```java
// after: 이력 INSERT와 비즈니스 변경을 같은 DB 트랜잭션으로
@Transactional
public void handle(OrderEvent event) {
    try {
        processedEventRepository.insert(event.eventId());
        // ↑ processed_event.event_id 에 UNIQUE 제약
    } catch (DuplicateKeyException e) {
        return;   // 이미 처리된 이벤트 — 조용히 ack
    }
    orderRepository.save(toOrder(event));
}
// 트랜잭션이 원자성을 보장: 이력과 반영은 함께 커밋되거나 함께 롤백된다.
// 중간에 죽어도 "이력만 있고 처리는 안 된" 어긋난 상태가 안 생긴다.
```

이 패턴의 핵심 두 가지:

- **같은 DB, 같은 트랜잭션.** 이력 저장소가 비즈니스 DB와 분리되는
  순간(위 before의 Redis) 둘 사이의 원자성이 사라지고, 크래시 타이밍에
  따라 유실("이력 있음 + 처리 안 됨") 또는 중복("처리됨 + 이력 없음")이
  생긴다.
- **UNIQUE 제약이 최후 방어선.** "SELECT로 있는지 보고 없으면
  INSERT"는 동시성에서 뚫린다(꼬리질문 참고). 중복 판정은 DB가
  원자적으로 하게 한다.

Redis `SETNX` 같은 외부 저장소 필터는 빠른 사전 차단(1차 필터)으로는
유용하지만, 원자성이 없으므로 **단독 방어선이 아니라 보조 수단**으로만
쓴다 — 최종 방어는 항상 DB unique 제약.

### 3-3. 이력 보관 기간 — 무한히 쌓을 수는 없다

processed_event는 계속 자란다. 보관 기간은 "중복이 도달할 수 있는 최대
시간 창"보다 길게 잡는다 — 재시도 정책의 최대 지연, 예상 컨슈머 랙,
운영상 replay가 커버하는 범위를 합쳐 산정하고, 그보다 오래된 이력은
배치로 정리한다(시간 기준 파티셔닝이 삭제를 싸게 만든다). 이 창을
넘는 대규모 replay는 이력 정리와 충돌하므로 별도 절차(격리 컨슈머,
사전 공지)로 다룬다 — 여기까지 말하면 운영을 해 본 티가 난다
(가산점 포인트).

## 4. 트랜잭션 밖의 부수효과 — 멱등의 사각지대

이메일 발송, 푸시, 외부 API 호출은 DB 트랜잭션으로 감쌀 수 없다.
"이력 커밋은 됐는데 발송 API 호출 직후 응답을 못 받고 죽음 → 재수신은
이력에 걸려 skip → 그런데 발송은 됐나 안 됐나?" 같은 회색지대가 남는다.
대응은 두 가지다:

- **수신 측 멱등 키 전달**: 외부 API가 idempotency key를 지원하면
  이벤트 ID를 그대로 넘겨 중복 흡수를 상대 경계로 위임한다.
- **기록과 실행의 분리**: 트랜잭션 안에서는 "발송 예약" 행만 기록하고,
  실제 발송은 그 행을 읽는 별도 워커가 수행 — 발행 측 Outbox 패턴을
  소비 측에 다시 적용한 구조다.

## 5. 꼬리질문 대비 포인트

### "멱등 키는 뭘로 잡나? 파티션-오프셋을 쓰면 안 되나?"

프로듀서가 이벤트 생성 시점에 발급한 고유 ID가 정석이다. 파티션-오프셋은
브로커상의 "위치"일 뿐이라, 토픽 재생성·재발행·미러링·replay 대상 토픽
변경에서 같은 비즈니스 이벤트에 다른 좌표가 붙어 중복 판별이 뚫린다.
반대로 이벤트 ID는 메시지가 어디를 거쳐 오든 불변이다. Outbox 패턴을
쓴다면 outbox 행 PK가 자연스러운 이벤트 ID가 된다 — 발행 경로와 멱등
키 체계가 한 번에 정리되는 조합이다 (가산점 포인트).

### "unique 제약 없이 SELECT로 존재 확인 후 INSERT 하면 안 되나?" (시니어 변별 포인트)

동시성에서 깨진다. check-then-act 사이에 다른 처리가 끼어들 수 있기
때문 — 같은 이벤트를 든 두 스레드(또는 두 컨슈머 인스턴스)가 동시에
SELECT하면 둘 다 "없음"을 보고 둘 다 처리한다. "파티션 하나는 컨슈머
하나가 소비하는데 동시 처리가 되나?"까지 파고들면: 된다 — 긴 GC나
처리 지연으로 `max.poll.interval.ms`를 넘긴 컨슈머는 그룹에서 제외되어
파티션이 다른 인스턴스로 넘어가는데, **원래 컨슈머는 자기가 쫓겨난 줄
모르고 하던 처리를 계속 끝낸다**(좀비 컨슈머). 이 순간 같은 메시지를
두 인스턴스가 처리 중이다. 그래서 애플리케이션 레벨 체크가 아니라 DB가
원자적으로 판정하는 unique 제약이 최후 방어선이어야 한다.

### "처리 이력 테이블이 무한히 커지는 문제는 어떻게 하나?"

보관 기간을 "중복이 도달 가능한 최대 창"(재시도 최대 지연 + 예상 랙 +
통상 replay 범위) 이상으로 설계하고, 그보다 오래된 행을 배치
삭제한다 — 시간 기준 테이블 파티셔닝이면 파티션 드롭으로 삭제 비용이
거의 없다. 핵심은 "얼마나 보관하나"에 정답 숫자가 있는 게 아니라,
**중복 도달 창이라는 근거에서 기간을 도출**하고 그 창을 넘는 replay는
별도 절차로 격리한다는 논리 구조를 보여주는 것이다.

### "이메일 발송처럼 롤백 불가능한 부수효과는 어떻게 멱등하게 하나?"

DB 트랜잭션 안에 넣을 수 없으므로 두 가지로 푼다. 외부 시스템이
idempotency key를 받으면 이벤트 ID를 전달해 중복 흡수를 그쪽 경계에
위임하고, 그게 안 되면 트랜잭션 안에서는 "발송 예약" 기록까지만 하고
실제 발송은 예약 행을 소비하는 별도 워커로 분리한다(소비 측 outbox).
"부수효과는 트랜잭션의 원자성 밖"이라는 한계를 먼저 인정하고 경계를
옮기는 답이 정확한 답이다.

### "멱등 컨슈머를 만들었으면 exactly-once 설정은 필요 없나?"

역할이 다르다. 멱등 프로듀서·트랜잭션은 Kafka 경계 안(재시도 중복,
Kafka 간 파이프라인)의 중복을 줄여 멱등 컨슈머가 처리할 중복의 양을
줄여주고, 멱등 컨슈머는 그걸로 못 막는 비즈니스 레벨 중복(앱 재발행,
replay, 좀비 컨슈머)까지 막는 최종 방어선이다. 인프라 설정으로 중복
빈도를 낮추고, 애플리케이션 멱등으로 정확성을 보장하는 **이중 구조**로
답하면 07번 질문(전달 의미론)과의 연결까지 보여줄 수 있다.

## 한 줄 요약

멱등 컨슈머는 "중복은 반드시 온다"는 at-least-once의 전제를 받아들이고,
가능하면 연산 자체를 멱등하게(절대값·UPSERT·조건부 전이), 안 되면
프로듀서 발급 이벤트 ID를 unique 제약 걸린 이력 테이블에 비즈니스
변경과 **같은 트랜잭션**으로 기록해 — 키 선정, 저장소, 원자성이라는 세
디테일로 exactly-once 효과를 애플리케이션 레벨에서 완성하는 패턴이다.
