# 멱등 컨슈머 구현 — 중복은 예외가 아니라 정상 동작이다

> 핵심 관전 포인트: **멱등성은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"이고, at-least-once 세계에서 중복 수신은 버그가 아니라 스펙이다 — 커밋 전 크래시, 리밸런스, 프로듀서 재발행, 대량 재처리 어디서든 온다. 구현은 두 축이다: ① 연산 자체를 멱등하게 설계(절대값 세팅, UPSERT, 상태 기계 조건부 전이) — 가능하면 최선. ② 처리 이력 기반 중복 제거 — 프로듀서가 발급한 이벤트 ID를 멱등 키로, 이력 테이블(유니크 제약)과 비즈니스 변경을 **같은 DB 트랜잭션**으로 묶는다. 키는 메시지가 담고 있는 비즈니스적 사실에 붙어야지 파티션-오프셋 같은 위치에 붙으면 안 되고, 중복 판정은 애플리케이션의 SELECT가 아니라 DB의 유니크 제약 + `ON CONFLICT DO NOTHING`이 원자적으로 해야 하며, 이력은 최소한 토픽의 리텐션 기간보다 길게 보관해야 한다. 키 선정·원자성·보관 기간, 이 세 디테일이 구현의 성패를 가른다.**

---

## 0. 질문 + 의도

**질문**: "멱등 컨슈머(idempotent consumer)를 어떻게 구현하나요?"

**출제 의도**: at-least-once 세계에서 중복은 예외가 아니라 정상 동작이다. 처리 이력 기반 중복 제거의 구현 디테일(키 선정, 저장소, 원자성)까지 들어가는지로 실전 경험을 가린다 — "중복 체크하면 된다" 수준과 "체크와 반영이 원자적이지 않으면 레이스에서 뚫린다"를 아는 수준의 차이를 보는 질문이다.

## 1. 멱등성이 무엇이고, 왜 중복이 "정상"인가

### 1-1. 멱등성 — 몇 번 눌러도 결과가 같다

먼저 용어부터 정확히 잡는다. **멱등성(idempotency)은 같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질**이다.

수학에서 온 말이다. 어떤 함수 f에 대해 `f(f(x)) = f(x)`가 성립하면 그 함수를 멱등하다고 부른다. 한 번 적용한 결과에 또 적용해도 값이 안 바뀐다는 뜻이다. "멱(冪)"은 거듭제곱, "등(等)"은 같다 — 거듭 적용해도 같다는 뜻의 조어다.

**엘리베이터 버튼**이 딱 맞는 비유다. 층 버튼을 한 번 누르나 다섯 번 누르나 엘리베이터는 그 층에 한 번 온다. 버튼은 "호출을 하나 추가한다"가 아니라 "이 층이 호출된 상태로 만든다"를 하기 때문이다.

반대로 멱등하지 않은 것도 보자. 은행 창구에서 "만 원 입금해 주세요"를 세 번 말하면 삼만 원이 들어간다. 이건 "잔액을 만 원 늘려라"라는 **상대적 변경**이라 반복하면 결과가 달라진다.

이 대비가 2절 전체의 뼈대가 된다. **멱등하게 만든다는 것은 "얼마만큼 바꿔라"를 "이 상태가 되게 하라"로 바꾸는 일**이다.

### 1-2. 중복은 어디서 오는가

멱등 처리가 방어해야 할 중복은 한 곳에서 오지 않는다.

- **컨슈머 쪽**: 처리 완료 후 오프셋 커밋 전에 크래시하거나 리밸런스가 일어나면 같은 메시지를 다시 받는다(`05-offset-commit-and-auto-commit-risk.md`). 여기서 중요한 건 리밸런스가 장애 상황에서만 일어나는 게 아니라는 점이다 — **배포할 때마다 컨슈머 인스턴스가 내려갔다 올라오면서 리밸런스가 일어난다.** 즉 "배포 = 중복 발생 가능 이벤트"다.
- **프로듀서 쪽**: 애플리케이션 레벨의 재시도, 재기동 후 재발행 등으로 같은 비즈니스 이벤트가 두 번 발행될 수 있다. 이건 `enable.idempotence=true`(멱등 프로듀서)로도 못 막는다 — 멱등 프로듀서는 "한 번의 send가 네트워크 재시도로 두 번 저장되는 것"만 막지, 애플리케이션이 의도적으로 두 번 send한 것은 서로 다른 메시지로 본다(`07-delivery-semantics-and-exactly-once-reality.md`).
- **운영 쪽**: 장애 복구를 위한 오프셋 되감기, 대량 이벤트 재처리(replay). 이때는 과거 메시지 전체가 **"합법적으로" 다시 온다.** 아무것도 고장 나지 않았는데 중복이 쏟아지는 경우다.

경로가 이렇게 많으니 "중복이 오면 어떡하지"가 아니라 **"중복은 반드시 온다"를 전제로 컨슈머를 설계**하는 것이 출발점이다.

한 가지 더. Kafka의 기본 보장은 **at-least-once(최소 한 번)**다. "적어도 한 번은 도착시킨다"는 약속이지 "정확히 한 번"이 아니다. 그리고 이 선택은 실수가 아니라 의도된 것이다 — 유실을 막으려면 "확실하지 않으면 다시 보낸다"가 유일한 전략이고, 그 대가가 중복이기 때문이다. **중복은 유실을 막은 대가로 받아들인 부작용**이고, 그 부작용을 소비 측에서 흡수하는 장치가 멱등 컨슈머다.

## 2. 전략 1 — 연산 자체를 멱등하게 (가능하면 최선)

별도 인프라 없이, 두 번 실행해도 결과가 같은 연산으로 바꿀 수 있는지 먼저 본다. 이 전략이 성립하면 이력 테이블도, 유니크 제약도, 정리 배치도 필요 없다. **가장 싼 해법이므로 항상 먼저 검토한다.**

### 2-1. 상대 연산을 절대 상태 세팅으로 바꾼다

1-1의 은행 비유가 그대로 코드가 된다.

```java
// before: 상대 연산 — "얼마만큼 늘려라"라서 두 번 오면 두 번 적립된다
@KafkaListener(topics = "point-events")
public void handle(PointEvent event) {
    member.addPoint(event.amount());   // point = point + amount
}

// after: 이벤트에 "적립 후의 총액"을 실어 보내 절대값으로 세팅한다
public void handle(PointEvent event) {
    member.setPoint(event.totalPoint());  // point = totalPoint
    // 같은 이벤트가 몇 번 와도 최종 상태가 같다 — 연산 자체가 멱등해졌다
}
```

바뀐 것은 컨슈머 코드만이 아니다. **이벤트의 스키마가 바뀌었다.** 프로듀서가 `amount`(변화량)만 싣던 것을 `totalPoint`(결과 상태)까지 싣도록 바꿔야 한다. 즉 이 전략은 컨슈머 혼자 결정할 수 없고 **이벤트 설계 단계에서 합의돼야 하는 것**이다.

그리고 대가가 하나 있다. 절대값 방식은 이벤트 **순서**가 지켜질 때만 안전하다. 100점 → 150점 → 200점 순으로 발행된 이벤트가 150점이 마지막에 도착하면 최종 상태가 150점으로 잘못 굳는다. 그래서 이 전략은 **같은 회원의 이벤트가 같은 파티션에 들어가도록 파티션 키를 설계하는 것**과 세트다(`06-message-ordering-partition-key.md`). Kafka는 파티션 안에서만 순서를 보장하기 때문이다.

### 2-2. INSERT를 UPSERT로 바꾼다

"없으면 삽입, 있으면 갱신"을 애플리케이션에서 분기하지 말고 **DB가 한 문장으로 원자적으로 처리하게** 한다.

```sql
-- PostgreSQL: 같은 키로 다시 들어오면 같은 값으로 덮어쓸 뿐이다
INSERT INTO order_summary (order_id, status, total_amount, updated_at)
VALUES (:orderId, :status, :amount, now())
ON CONFLICT (order_id)
DO UPDATE SET status       = EXCLUDED.status,
              total_amount = EXCLUDED.total_amount,
              updated_at   = now();
```

`ON CONFLICT (order_id)`는 "order_id의 유니크 제약에 걸리면"이라는 뜻이고, `EXCLUDED`는 "삽입하려다 막힌 그 행"을 가리키는 특수 별칭이다. 즉 이 한 문장이 "넣어 보고, 이미 있으면 새 값으로 갱신해라"를 뜻한다. (MySQL이라면 `INSERT ... ON DUPLICATE KEY UPDATE`가 같은 역할을 한다.)

같은 키의 재수신은 같은 행을 같은 값으로 덮을 뿐이므로, 몇 번을 받아도 최종 상태가 같다.

### 2-3. 상태 기계 — 현재 상태를 조건에 박는다

도메인이 상태 전이로 모델링돼 있으면(주문, 정산, 구독) 가장 자연스러운 멱등 방식이 이것이다.

```sql
-- "결제완료 -> 배송준비" 전이: 출발 상태를 WHERE 조건에 박는다
UPDATE orders
   SET status = 'PREPARING'
 WHERE id = :orderId
   AND status = 'PAID';
-- 첫 처리:   status가 PAID이므로 1행 갱신
-- 중복 처리: 이미 PREPARING이라 조건 불일치 -> 0행 갱신
```

갱신된 행 수가 0이면 **"이미 처리됨"으로 보고 예외 없이 조용히 넘어간 뒤 오프셋을 커밋**한다. 여기서 예외를 던지면 안 된다 — 중복은 오류가 아니라 정상적으로 예상되는 상황이고, 예외를 던지면 컨슈머가 같은 메시지를 무한 재시도하며 파티션이 멈춘다.

이 방식의 부수 효과 하나. `AND status = 'PAID'`는 중복 방어인 동시에 **잘못된 순서의 전이를 막는 방어**이기도 하다. 아직 PENDING인 주문에 배송준비 이벤트가 먼저 도착해도 0행 갱신으로 튕겨 나간다. 중복 방어와 순서 방어를 한 줄이 동시에 해 주는 셈이다.

### 2-4. 이 전략이 안 통하는 경우

전략 1은 언제나 최선이지만 언제나 가능하지는 않다.

- **결과 상태를 이벤트에 실을 수 없는 경우.** 프로듀서가 총액을 모르거나, 여러 이벤트가 합산돼야 최종 값이 나오는 경우다.
- **행이 아니라 사건을 남기는 경우.** 포인트 원장, 감사 로그처럼 "적립 내역이 한 줄 추가되는 것" 자체가 요구사항이면 덮어쓸 대상이 없다.
- **부수효과가 있는 경우.** 이메일 발송, 푸시, 외부 결제 API 호출은 애초에 DB 상태가 아니라 바깥 세계를 바꾸는 일이라 "덮어쓴다"는 개념이 없다.

이때 필요한 것이 전략 2다.

## 3. 전략 2 — 처리 이력 기반 중복 제거 (범용 해법)

발상은 단순하다. **"이 이벤트 처리했음"을 어딘가에 기록해 두고, 다음에 같은 이벤트가 오면 기록을 보고 건너뛴다.** 그런데 출제 의도가 짚는 것처럼 이 단순한 발상은 세 개의 디테일에서 전부 뚫릴 수 있다.

### 3-1. 키 선정 — 무엇으로 "같은 메시지"를 판별하나

정석은 **프로듀서가 이벤트를 만들 때 발급한 고유 ID**(UUID 등, Outbox 패턴이라면 outbox 행의 PK)를 페이로드나 헤더에 실어 보내는 것이다. 소비 쪽에서 이것저것 조합해 만드는 것보다, **이벤트가 태어날 때 신분증을 쥐여주는** 쪽이 확실하다.

그리고 여기서 자주 나오는 오답이 **`토픽-파티션-오프셋` 조합을 키로 쓰는 것**이다. 메시지마다 유일한 값처럼 보이니 그럴듯한데, 실제로는 세 방향으로 뚫린다.

**(1) 같은 좌표가 다른 메시지에 재사용된다.** 오프셋은 파티션 안에서 0부터 매겨지는 일련번호다. 토픽을 삭제하고 다시 만들면 오프셋도 0부터 다시 시작하므로, `(주문토픽, 파티션0, 오프셋 517)`이 예전의 완전히 다른 메시지를 가리키게 된다. 이력 테이블에 그 키가 남아 있으면 **새 메시지가 "이미 처리됨"으로 오인돼 통째로 버려진다.** 유실이다.

**(2) 파티션을 늘리면 같은 이벤트의 좌표가 바뀐다.** Kafka는 메시지 키의 해시를 파티션 수로 나눈 나머지로 파티션을 정하므로, 파티션 수가 3에서 6으로 바뀌면 같은 주문의 이벤트가 다른 파티션으로 간다(`17-partition-increase-side-effects.md`). 좌표가 달라졌으니 이력이 안 걸린다.

**(3) replay하면 같은 이벤트가 다른 좌표로 다시 온다.** 대량 재처리를 위해 이벤트를 다른 토픽으로 복사해 흘리거나 미러링 클러스터를 거치면, 같은 비즈니스 이벤트에 완전히 다른 `(토픽, 파티션, 오프셋)`이 붙는다. 이력에 없는 키니까 **중복으로 인식되지 않고 그대로 두 번 처리된다.**

세 경우가 말하는 바는 하나로 모인다. **파티션-오프셋은 "그 메시지가 어디에 놓여 있는가"라는 위치 정보이지, "그 메시지가 무엇인가"라는 정체 정보가 아니다.** 위치는 인프라 사정으로 바뀌지만 정체는 안 바뀐다.

**멱등 키는 메시지가 담고 있는 비즈니스적 사실에 붙어야지, 그 메시지가 놓인 자리에 붙으면 안 된다.** 이 원리 한 줄이 이 절의 결론이다.

이력 테이블은 이렇게 잡는다.

```sql
CREATE TABLE processed_event (
    event_id       uuid        NOT NULL,
    consumer_group varchar(100) NOT NULL,
    processed_at   timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (event_id, consumer_group)
);
-- consumer_group을 키에 넣는 이유: 같은 토픽을 정산 컨슈머와 알림 컨슈머가
-- 각자 소비하는데 이력 테이블을 공유하면, 정산이 먼저 처리한 이벤트를
-- 알림 쪽이 "이미 처리됨"으로 오인해 건너뛴다. 소비 주체별로 이력이 따로여야 한다.

-- 오래된 이력 정리(3-3)를 위한 인덱스
CREATE INDEX idx_processed_event_at ON processed_event (processed_at);
```

### 3-2. 원자성 — 두 겹의 원자성이 필요하다

여기가 출제 의도의 심장부다. 이력 기반 중복 제거는 **서로 다른 두 종류의 원자성**을 동시에 요구하는데, 하나만 챙기고 다른 하나를 빠뜨리는 답이 흔하다.

#### (가) 확인과 선점의 원자성 — "SELECT 후 INSERT"는 왜 새는가

가장 자연스러워 보이는 구현이 이것이다.

```java
// before: check-then-act — 확인과 선점 사이에 틈이 있다
public void handle(OrderEvent event) {
    if (processedEventRepository.exists(event.eventId())) return;  // ① 확인
    orderRepository.save(toOrder(event));                          // ② 처리
    processedEventRepository.insert(event.eventId());              // ③ 기록
}
```

같은 이벤트를 든 두 스레드(또는 두 컨슈머 인스턴스)가 동시에 들어오면 이렇게 된다.

```
시각   인스턴스 A                                인스턴스 B
----   ---------------------------------------   ---------------------------------------
t0     SELECT ... WHERE event_id = 'E-1'
       -> 0건. "아직 처리 안 됐네"
t1                                               SELECT ... WHERE event_id = 'E-1'
                                                 -> 0건. "아직 처리 안 됐네"
t2     주문 생성 (비즈니스 처리)
t3     INSERT INTO processed_event ...
t4                                               주문 생성 (비즈니스 처리)   <- 중복!
t5                                               INSERT INTO processed_event ...
```

t0의 확인과 t3의 기록 사이에 **B가 통째로 끼어들 수 있는 틈**이 열려 있다. 이것을 **check-then-act 문제**라고 부른다 — 확인한 순간의 사실이 행동하는 순간에는 이미 옛날 얘기가 되어 있는 것이다.

여기서 흔한 오해를 하나 짚어야 한다. **"메서드에 `@Transactional`을 붙이면 해결되지 않나?"** — 안 된다. 기본 격리 수준인 READ COMMITTED에서 B의 SELECT는 **A가 아직 커밋하지 않은 INSERT를 볼 수 없다.** 트랜잭션이 하는 일은 "내 변경을 한 덩어리로 커밋/롤백하는 것"이지 "남이 끼어드는 것을 막는 것"이 아니다. 격리 수준을 SERIALIZABLE까지 올리면 막히지만, 그 대가로 처리량이 크게 떨어지고 직렬화 실패 재시도 로직을 따로 짜야 한다.

또 하나. **"파티션 하나는 컨슈머 하나가 소비하는데 애초에 동시 처리가 되나?"**도 흔한 반문인데, 된다. 자세한 시나리오는 4절 꼬리질문에 있다.

**해법은 확인과 선점을 한 문장으로 합치는 것**이다.

```java
// after: 유니크 제약 + ON CONFLICT DO NOTHING — 확인과 선점이 DB 안에서 한 번에 일어난다
@Transactional
public void handle(OrderEvent event) {
    int inserted = processedEventRepository.insertIfAbsent(
            event.eventId(), consumerGroup);
    // insertIfAbsent가 실행하는 SQL:
    //   INSERT INTO processed_event (event_id, consumer_group)
    //   VALUES (:eventId, :group)
    //   ON CONFLICT (event_id, consumer_group) DO NOTHING;
    // 반환값은 삽입된 행 수 — 1이면 내가 처음, 0이면 이미 누가 처리했다는 뜻이다.

    if (inserted == 0) return;   // 중복 — 예외 없이 조용히 넘어가고 오프셋 커밋

    orderRepository.save(toOrder(event));
}
```

**왜 이건 안전한가.** 유니크 제약이 걸린 키에 두 트랜잭션이 동시에 INSERT를 시도하면, PostgreSQL은 인덱스 레벨에서 **뒤에 온 쪽을 앞선 쪽이 커밋하거나 롤백할 때까지 대기시킨다.** 앞선 쪽이 커밋하면 뒤에 온 쪽은 충돌을 확인하고 `DO NOTHING`으로 0행을 반환한다. 즉 **"이미 있는지 확인하는 일"과 "없으면 내가 자리를 차지하는 일"이 DB 엔진 안에서 쪼갤 수 없는 한 동작으로 일어난다.** 위 타임라인의 t0~t3 같은 틈이 애초에 존재하지 않는다.

`ON CONFLICT DO NOTHING` 대신 그냥 INSERT를 날리고 `DuplicateKeyException`을 잡는 방식도 안전성은 같다. 다만 PostgreSQL에서는 제약 위반이 나면 **그 트랜잭션 전체가 중단 상태(aborted)가 되어** 이후 쿼리가 전부 거부되므로, 예외를 잡아서 같은 트랜잭션 안에서 뭔가를 더 하려면 세이브포인트가 필요하다. `ON CONFLICT`는 애초에 예외를 만들지 않으므로 이 문제가 없다 — **PostgreSQL에서는 `ON CONFLICT`가 더 깔끔한 선택**이다.

#### (나) 이력과 비즈니스 변경의 원자성 — 반드시 같은 트랜잭션

두 번째 원자성은 다른 이야기다. **이력 기록과 비즈니스 변경이 함께 커밋되거나 함께 롤백돼야 한다.**

왜 그런지는 어긋나는 두 경우를 보면 안다.

**경우 1: 이력만 커밋되고 비즈니스 변경이 롤백됐다.** 다음에 같은 메시지가 다시 와도 이력에 걸려 skip된다. **그 메시지는 영영 처리되지 않는다.** 중복을 막으려던 장치가 유실을 만든 것이고, 더 나쁜 건 아무도 이 사실을 모른다는 점이다 — 시스템은 정상 동작했다고 믿는다.

**경우 2: 비즈니스 변경만 커밋되고 이력이 롤백됐다.** 다음에 같은 메시지가 오면 이력이 없으니 통과해서 **또 처리한다.** 중복이다.

즉 둘 중 어느 쪽으로 어긋나도 이 패턴의 존재 이유 자체가 무너진다. 그래서 반드시 하나의 트랜잭션이어야 한다.

```java
// before: 체크와 반영이 서로 다른 시스템에 흩어져 있다 — 두 군데서 깨진다
public void handle(OrderEvent event) {
    if (redis.exists(event.eventId())) return;  // ① 체크 (Redis)
    orderRepository.save(toOrder(event));       // ② 반영 (PostgreSQL)
    redis.set(event.eventId(), "done");         // ③ 기록 (Redis)
}
// ②와 ③ 사이 크래시 -> 이력 없음 -> 재수신 시 ② 재실행 = 중복 (경우 2)
// ①을 통과한 두 요청이 동시에 ②로 진입하는 레이스도 그대로 열려 있다 (가)
```

이 코드가 고칠 수 없는 이유는 순서를 바꾸는 문제가 아니다. **Redis와 PostgreSQL은 서로 다른 시스템이라 애초에 한 트랜잭션으로 묶을 수 없다.** `@Transactional`은 하나의 DataSource가 관리하는 커넥션 안에서만 원자성을 만들어 준다. 다른 시스템에 대한 쓰기는 그 트랜잭션 바깥이므로, 롤백돼도 되돌아오지 않고 커밋 직전에 죽으면 남지 않는다.

이걸 "이중 쓰기(dual write) 문제"라고 부른다. 서로 다른 두 시스템에 써야 하는데 그 둘을 원자적으로 묶을 방법이 없는 상황이다. 발행 측에서 이 문제를 푸는 것이 Outbox 패턴이고(`12-transactional-outbox-cdc-kafka.md`), 소비 측에서 이 문제를 회피하는 방법은 훨씬 간단하다 — **이력을 비즈니스 DB와 같은 DB에 두면 된다.** 그러면 이중 쓰기가 아니라 한 트랜잭션 안의 두 쓰기가 된다.

그렇다고 Redis가 쓸모없는 것은 아니다. Redis `SETNX` 같은 외부 저장소 필터는 **빠른 사전 차단(1차 필터)**으로 유용하다 — replay로 이미 처리된 이벤트 수백만 건이 밀려올 때 DB까지 안 가고 걸러내면 DB 부하가 크게 준다. 다만 원자성이 없으므로 **단독 방어선이 아니라 보조 수단**이다. 최종 방어는 항상 DB 유니크 제약이어야 한다.

정리하면 이 패턴의 핵심은 두 문장이다.

- **같은 DB, 같은 트랜잭션** — 이력과 비즈니스 변경이 함께 커밋되거나 함께 롤백되게 한다.
- **유니크 제약이 최후 방어선** — 중복 판정을 애플리케이션의 SELECT가 아니라 DB가 원자적으로 하게 한다.

### 3-3. 이력 보관 기간 — 무한히 쌓을 수는 없다

`processed_event`는 처리한 이벤트 수만큼 계속 자란다. 언젠가는 지워야 하는데, **"얼마나 보관하나"에는 근거가 있어야 한다.**

**바닥선은 명확하다. 최소한 토픽의 리텐션 기간보다 길어야 한다.**

이유를 보자. Kafka 토픽은 `retention.ms`(기본 7일 = 604,800,000ms) 동안 메시지를 보관하고, 그 안에서는 오프셋을 되감아 언제든 다시 읽을 수 있다. 그런데 이력을 3일만 보관하고 있다면 이런 일이 벌어진다.

```
토픽 리텐션 7일  |=========================================|  (7일 전 ~ 지금)
이력 보관   3일                          |=================|  (3일 전 ~ 지금)
                 |<----- 사각지대 4일 ---->|

장애 복구를 위해 5일 전 오프셋으로 되감으면?
 - 5일 전 ~ 3일 전 구간의 메시지: 토픽에는 남아 있어 다시 온다.
   그런데 이력은 이미 지워졌다 -> 중복 판정 실패 -> 전부 재처리된다.
```

**즉 이력 보관 기간이 리텐션보다 짧으면, replay 할 수 있는 범위 안에 멱등성이 보장되지 않는 구멍이 생긴다.** 되감기가 가능한 구간 전체를 이력이 덮고 있어야 논리가 닫힌다.

리텐션은 어디까지나 하한이고, 실제 기간은 **"중복이 도달할 수 있는 최대 시간 창"**을 기준으로 산정한다. 이 창을 이루는 요소가 셋이다.

- 재시도 정책의 최대 지연 — DLQ로 보내기 전 재시도를 며칠에 걸쳐 하는 설계라면 그만큼 늦게 같은 메시지가 온다.
- 예상 컨슈머 랙 — 컨슈머가 며칠 밀렸다가 따라잡는 경우.
- 운영상 replay가 커버하는 범위 — 실제로 되감기를 하는 최대 폭.

이 셋 중 가장 긴 값과 토픽 리텐션을 비교해 더 긴 쪽을 기준으로 잡고, 여기에 여유를 얹는다.

정리 방법은 **시간 기준 파티셔닝**이 압도적으로 싸다.

```sql
-- 월별 레인지 파티셔닝: 오래된 이력을 DELETE가 아니라 파티션 통째로 버린다
CREATE TABLE processed_event (
    event_id       uuid         NOT NULL,
    consumer_group varchar(100) NOT NULL,
    processed_at   timestamptz  NOT NULL DEFAULT now(),
    PRIMARY KEY (event_id, consumer_group, processed_at)
) PARTITION BY RANGE (processed_at);

CREATE TABLE processed_event_2026_09 PARTITION OF processed_event
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

왜 이게 싼지가 PostgreSQL에서는 특히 분명하다. `DELETE FROM processed_event WHERE processed_at < ...`은 수천만 행에 **죽은 튜플(dead tuple)**을 만들고, 그 공간은 VACUUM이 돌기 전까지 회수되지 않는다. 지웠는데 테이블 크기는 그대로거나 오히려 부푸는 것이다. 반면 파티션은 `DROP TABLE processed_event_2026_09` 한 줄이면 **파일 자체가 사라진다** — 죽은 튜플도, VACUUM 부담도 없다.

마지막으로, 이 창을 넘어서는 대규모 replay는 이력 정리와 정면으로 충돌한다. 이때는 임기응변으로 이력 보관 기간을 늘리는 것이 아니라, **격리된 컨슈머 그룹으로 별도 환경에서 돌리거나 사전 공지 후 정리 배치를 멈추는 등의 별도 절차**로 다룬다(`19-bulk-replay-isolation.md`). 여기까지 말하면 운영을 해 본 티가 난다. (가산점 포인트)

### 3-4. 트랜잭션 밖의 부수효과 — 멱등의 사각지대

이메일 발송, 푸시 알림, 외부 API 호출은 DB 트랜잭션으로 감쌀 수 없다. 3-2에서 본 이중 쓰기 문제가 여기서 다시 나타난다 — **트랜잭션을 롤백해도 이미 나간 이메일은 회수되지 않는다.**

구체적으로 어떤 회색지대가 생기는지 보자.

```
t0  트랜잭션 시작
t1  processed_event INSERT (성공)
t2  이메일 발송 API 호출 -> 메일 서버는 정상 접수했다
t3  ★ 응답을 받기 직전 컨슈머 프로세스가 죽는다 -> 트랜잭션 롤백
t4  재수신: 이력이 롤백됐으므로 통과 -> 이메일을 또 보낸다   <- 중복 발송

또는 t1과 t2의 순서를 바꾸면:
t1  이메일 발송 API 호출 (성공)
t2  ★ processed_event INSERT 직전 크래시
t3  재수신: 이력 없음 -> 또 보낸다                          <- 역시 중복 발송
```

순서를 어떻게 바꿔도 "보냈는지 안 보냈는지 모르는" 구간이 남는다. 트랜잭션의 원자성이 API 호출까지 미치지 못하기 때문이다. **대응은 이 한계를 인정하고 경계를 옮기는 것**이고, 세 가지 방법이 있다.

**(1) 수신 측에 멱등 키를 넘긴다.** 외부 API가 `Idempotency-Key` 헤더를 지원하면(결제 게이트웨이 대부분이 지원한다) 이벤트 ID를 그대로 넘긴다. 그러면 같은 키로 두 번 호출해도 상대 시스템이 한 번만 실행하고 두 번째는 첫 번째의 결과를 그대로 돌려준다. **중복 흡수 책임을 상대 경계로 위임**하는 것이고, 가능하면 이게 제일 깔끔하다.

**(2) 발송 이력을 먼저 기록하고 조건부로 발송한다.** 상대가 멱등 키를 안 받으면 우리 쪽에서 기록을 남긴다.

```java
@Transactional
public void handle(OrderEvent event) {
    if (processedEventRepository.insertIfAbsent(event.eventId(), group) == 0) return;

    orderRepository.save(toOrder(event));

    // 발송 "예약"만 트랜잭션 안에 기록한다. 실제 발송은 하지 않는다.
    // 이 행이 커밋되면 "보내야 한다"는 사실이 확정되고,
    // 롤백되면 "보낼 일 자체가 없었다"가 된다 — 원자성이 성립한다.
    emailOutboxRepository.save(EmailOutbox.pending(event.eventId(), event.email()));
}
```

**(3) 발송 자체를 별도 이벤트로 분리한다.** (2)를 한 단계 더 밀면 이렇게 된다 — 컨슈머는 "주문 확정" 처리만 하고 `order.confirmed` 이벤트를 발행하며, 이메일 발송은 그 이벤트를 구독하는 **별도의 컨슈머**가 맡는다. 그 컨슈머도 자기 이력 테이블로 멱등 처리를 하고, 발송 실패는 그쪽의 재시도·DLQ 정책으로 다룬다.

(2)와 (3)의 공통 구조를 짚어 두면 이해가 굳는다. **둘 다 "기록"과 "실행"을 분리해서, 기록만 트랜잭션 안에 넣고 실행은 그 기록을 읽는 별도 워커에게 넘기는 방식**이다. 이건 발행 측의 Outbox 패턴을 소비 측에 그대로 다시 적용한 것이다. 그리고 이 구조에서도 완전한 exactly-once는 안 된다 — 워커가 발송 후 상태 갱신 전에 죽으면 한 번 더 보낸다. **다만 "보냈는지 모르는 상태"가 "보낸 기록은 확실히 있고 중복 가능성만 남은 상태"로 줄어든다.** 부수효과 영역에서 할 수 있는 최선은 대체로 여기까지다.

## 4. 꼬리질문 대비 포인트

### "멱등 키는 뭘로 잡나? 파티션-오프셋을 쓰면 안 되나?"

프로듀서가 이벤트 생성 시점에 발급한 고유 ID가 정석이다.

파티션-오프셋은 브로커상의 **"위치"일 뿐 "정체"가 아니다.** 토픽 재생성으로 오프셋이 0부터 다시 매겨지면 같은 좌표가 전혀 다른 메시지에 재사용되어 새 메시지가 "이미 처리됨"으로 버려지고, 파티션 증설이나 다른 토픽으로의 재발행·미러링·replay에서는 같은 비즈니스 이벤트에 다른 좌표가 붙어 중복 판별이 아예 안 걸린다. **한쪽으로는 유실, 다른 쪽으로는 중복 — 양방향으로 뚫린다.**

반대로 이벤트 ID는 메시지가 어디를 거쳐 오든 불변이다. 원리로 말하면 **키는 메시지가 담고 있는 비즈니스적 사실에 붙어야지 그 메시지가 놓인 위치에 붙으면 안 된다.**

Outbox 패턴을 쓴다면 outbox 행의 PK가 자연스러운 이벤트 ID가 된다 — 발행 경로와 멱등 키 체계가 한 번에 정리되는 조합이다. (가산점 포인트)

### "unique 제약 없이 SELECT로 존재 확인 후 INSERT 하면 안 되나?" (시니어 변별 포인트)

동시성에서 깨진다. **check-then-act 사이에 다른 처리가 끼어들 수 있기 때문**이다 — 같은 이벤트를 든 두 스레드가 동시에 SELECT하면 둘 다 "없음"을 보고 둘 다 처리한다(3-2의 타임라인).

여기서 반드시 나오는 반문이 **"파티션 하나는 컨슈머 하나가 소비하는데 동시 처리가 되나?"**인데, 된다. 시나리오는 이렇다.

```
t0   인스턴스 A가 파티션 0의 메시지 E-1을 poll해서 처리를 시작한다
t1   A에서 긴 GC 또는 외부 API 지연이 발생해 처리가 길어진다
t2   A가 max.poll.interval.ms를 넘겨 poll을 못 하자,
     브로커는 A가 죽었다고 판단하고 그룹에서 제외한다
t3   리밸런스로 파티션 0이 인스턴스 B에게 넘어간다
t4   B가 (A가 오프셋을 커밋하지 못했으므로) E-1을 처음부터 다시 받아 처리한다
t5   ★ 이 순간 A는 자기가 쫓겨난 줄 모르고 t0에 시작한 처리를 계속 끝낸다
     -> 같은 메시지 E-1을 두 인스턴스가 동시에 처리 중이다
```

t5의 A를 **좀비 컨슈머(zombie consumer)**라고 부른다. 자기가 이미 그룹에서 쫓겨났다는 사실을 모른 채 살아 움직이기 때문이다(`22-max-poll-interval-vs-session-timeout.md`).

그래서 결론은 **애플리케이션 레벨 체크로는 원리적으로 못 막는다**는 것이다. 어느 인스턴스의 메모리에서 무슨 판단을 하든, 두 프로세스가 각자 판단하는 이상 틈은 생긴다. 유일하게 신뢰할 수 있는 심판은 **두 요청이 반드시 거쳐 가는 단일 지점인 DB**이고, 그래서 유니크 제약 + `ON CONFLICT DO NOTHING`이 최후 방어선이어야 한다.

### "처리 이력 테이블이 무한히 커지는 문제는 어떻게 하나?"

보관 기간을 근거를 갖고 정하고, 그보다 오래된 행을 정리한다.

**바닥선은 토픽의 리텐션 기간이다.** 되감아 다시 읽을 수 있는 구간 전체를 이력이 덮고 있어야 하고, 이력이 그보다 짧으면 replay 시 이미 지운 구간에서 중복 처리가 뚫린다. 그 위에 "중복이 도달 가능한 최대 창"(재시도 최대 지연 + 예상 컨슈머 랙 + 통상 replay 범위)을 얹어 산정한다.

정리는 시간 기준 레인지 파티셔닝으로 한다. PostgreSQL에서 대량 `DELETE`는 죽은 튜플을 만들어 VACUUM이 돌기 전까지 공간이 회수되지 않지만, 파티션 드롭은 파일이 통째로 사라져 비용이 거의 없다.

핵심은 "얼마나 보관하나"에 정답 숫자가 있는 게 아니라, **중복 도달 창과 토픽 리텐션이라는 근거에서 기간을 도출**하고 그 창을 넘는 replay는 별도 절차로 격리한다는 논리 구조를 보여주는 것이다.

### "이메일 발송처럼 롤백 불가능한 부수효과는 어떻게 멱등하게 하나?"

DB 트랜잭션 안에 넣을 수 없다는 한계를 먼저 인정하고, **경계를 옮겨서** 푼다.

첫째, 외부 시스템이 `Idempotency-Key`를 받으면 이벤트 ID를 그대로 전달해 **중복 흡수를 그쪽 경계로 위임**한다.

둘째, 그게 안 되면 **기록과 실행을 분리**한다 — 트랜잭션 안에서는 "발송 예약" 행만 남기고, 실제 발송은 그 행을 읽는 별도 워커가 수행한 뒤 상태를 SENT로 바꾼다. 소비 측에 다시 적용한 Outbox 구조다.

셋째, 한 걸음 더 나가면 **발송 자체를 별도 이벤트로 떼어내** 전용 컨슈머가 자기 이력 테이블로 멱등 처리하게 한다. 발송 실패의 재시도·DLQ 정책도 그쪽에 격리된다.

솔직하게 덧붙일 것이 하나 있다. 이 방법들도 완전한 exactly-once는 아니다 — 워커가 발송 후 상태 갱신 전에 죽으면 한 번 더 보낸다. **"보냈는지 모르는 상태"를 "중복 가능성만 남은 상태"로 줄이는 것**이 부수효과 영역에서의 최선이고, 그 한계를 정확히 말하는 것이 좋은 답이다.

### "멱등 컨슈머를 만들었으면 exactly-once 설정은 필요 없나?"

역할이 다르다. 대체 관계가 아니라 층이 다른 두 장치다.

**멱등 프로듀서와 Kafka 트랜잭션은 Kafka 경계 안의 중복을 줄인다** — 프로듀서 재시도로 인한 중복, Kafka에서 읽어 Kafka로 쓰는 파이프라인의 중복이 대상이다. 이 층의 역할은 멱등 컨슈머가 처리해야 할 중복의 **양을 줄이는 것**이다.

**멱등 컨슈머는 그걸로 못 막는 비즈니스 레벨 중복까지 막는 최종 방어선**이다 — 애플리케이션의 재발행, 운영상의 replay, 좀비 컨슈머가 여기 해당한다. 이 층의 역할은 **정확성을 보장하는 것**이다.

즉 **인프라 설정으로 중복 빈도를 낮추고, 애플리케이션 멱등으로 정확성을 보장하는 이중 구조**다. 그리고 어느 하나만 있으면 부족하다 — 인프라 설정만 있으면 replay에서 뚫리고, 애플리케이션 멱등만 있으면 불필요한 중복 트래픽을 전부 DB로 받아내야 한다. 여기까지 답하면 `07-delivery-semantics-and-exactly-once-reality.md`와의 연결까지 보여줄 수 있다.

---

## 한 줄 요약

멱등 컨슈머는 "중복은 반드시 온다"는 at-least-once의 전제를 받아들이고, 가능하면 연산 자체를 멱등하게(절대값·UPSERT·조건부 전이) 바꾸고, 안 되면 프로듀서가 발급한 이벤트 ID를 — 파티션-오프셋 같은 위치가 아니라 비즈니스적 정체를 가리키는 키를 — 유니크 제약 걸린 이력 테이블에 `ON CONFLICT DO NOTHING`으로 넣어 확인과 선점을 원자적으로 만들고, 그 이력을 비즈니스 변경과 **같은 트랜잭션**으로 묶으며, 이력은 최소한 토픽 리텐션보다 길게 보관해 — 키 선정, 원자성, 보관 기간이라는 세 디테일로 exactly-once 효과를 애플리케이션 레벨에서 완성하는 패턴이다.
