# max.poll.interval.ms vs session.timeout.ms — 컨슈머가 쫓겨나는 두 가지 이유의 구분

> 핵심 관전 포인트: **컨슈머의 생존 판정은 두 갈래로 나뉜다.
> `session.timeout.ms`는 백그라운드 하트비트 스레드가 브로커(그룹
> 코디네이터)에 보내는 심장박동이 끊겼는지 보는 값 — "프로세스가 살아
> 있는가"의 판정이고, `max.poll.interval.ms`는 `poll()` 호출 사이의
> 간격이 너무 길어졌는지 보는 값 — "살아는 있는데 일이 너무 느린 것
> 아닌가"의 판정이다. 리밸런싱이 반복될 때 이 둘 중 어느 쪽에 걸려
> 쫓겨났는지를 로그로 먼저 가르는 것이 진단의 첫 걸음이다 —
> 하트비트 단절이면 인프라/GC 문제, poll 간격 초과면 처리 지연 문제로
> 수사 방향이 완전히 달라진다.**

---

## 0. 질문 + 의도

**질문**: "`max.poll.interval.ms`와 `session.timeout.ms`의 차이는?
리밸런싱이 반복될 때 무엇부터 확인하나요?"

**출제 의도**: "컨슈머가 자꾸 쫓겨나며 리밸런싱이 반복되는" 실무 단골
장애의 원인 분기(처리가 느림 vs 하트비트 끊김)를 할 수 있는지 본다.
두 타임아웃의 구분이 곧 진단 능력이다 — 구분을 못 하면 엉뚱한 설정을
키우며 장애를 연장하고, 구분하면 로그 한 줄로 수사 방향을 잡는다.

## 1. 왜 생존 판정이 두 개인가 — 심장박동과 작업 진척은 다르다

옛날 Kafka 컨슈머는 하트비트를 `poll()` 안에서 보냈다. 그래서 메시지
처리가 오래 걸리면(= poll을 못 부르면) 하트비트도 끊겨서, "일이
느린 것"과 "죽은 것"을 구분할 수 없었다. 처리가 긴 컨슈머를 살리려고
타임아웃을 키우면 진짜 죽은 컨슈머의 감지도 그만큼 늦어지는 딜레마.

그래서 하트비트가 **별도 백그라운드 스레드**로 분리되면서 판정이
두 갈래가 됐다.

- **`session.timeout.ms` — "심장이 뛰는가"**: 하트비트 스레드가
  `heartbeat.interval.ms` 주기로 코디네이터에 신호를 보낸다. 이 신호가
  `session.timeout.ms` 동안 안 오면 브로커가 "죽었다"고 판정하고
  리밸런싱을 시작한다. 걸리는 원인: 프로세스 크래시, 네트워크 단절,
  **모든 스레드를 멈추는 긴 GC(stop-the-world)**, 컨테이너 강제 종료.
- **`max.poll.interval.ms` — "일이 진척되는가"**: 마지막 `poll()`
  호출로부터 이 시간이 지나도록 다음 `poll()`이 없으면, "하트비트는
  오지만 소비가 멈춘 상태"로 간주해 그룹에서 내보낸다(컨슈머 스스로
  탈퇴를 통보한다). 걸리는 원인: 한 번 폴링한 배치의 **처리가 너무
  오래 걸림** — 느린 다운스트림(DB, 외부 API), 너무 큰 배치, 처리
  스레드의 교착/무한 루프.

비유하면 `session.timeout.ms`는 **심박 모니터**, `max.poll.interval.ms`는
**작업 일지 검사**다. 심박이 뛰어도 일지가 몇 시간째 비어 있으면
그 작업자에게서 일을 회수하는 것이다.

```text
컨슈머 프로세스
├── 하트비트 스레드 ──(heartbeat.interval.ms 주기)──▶ 코디네이터
│        └─ 끊기면 session.timeout.ms 후 사망 판정   ← "죽었나?"
└── 폴링/처리 스레드 ── poll() → 처리 → poll() → ...
         └─ 간격이 max.poll.interval.ms 넘으면 탈퇴   ← "느린가?"
```

기억할 관계식: 한 사이클의 최대 처리 시간은 대략
**폴링당 레코드 수(`max.poll.records`) × 레코드당 처리 시간**이고,
이것이 `max.poll.interval.ms`를 넘으면 안 된다. 레코드당 1초 걸리는
작업을 500건씩 폴링하면 한 바퀴에 500초 — 기본 한도(5분)를 넘어
쫓겨난다.

## 2. 리밸런싱 반복 장애 — 확인 순서

"컨슈머가 자꾸 쫓겨나고 리밸런싱이 반복된다"는 신고가 오면, 설정을
만지기 전에 **어느 타임아웃에 걸렸는지부터** 가른다.

**① 로그에서 축출 사유를 확인한다.** 두 경우는 로그 메시지가 다르다.

- poll 간격 초과: 컨슈머 로그에 "poll 간격을 초과해 그룹을
  떠난다(consumer poll timeout has expired)" 계열 경고 —
  `max.poll.interval.ms` 위반. **처리 지연 수사로.**
- 하트비트 단절: 브로커/코디네이터 쪽에 세션 만료로 멤버 제거 기록,
  컨슈머 쪽은 사망 직전이라 로그가 없거나 끊겨 있음 —
  `session.timeout.ms` 위반. **프로세스/인프라 수사로.**

**② poll 간격 초과라면 — "무엇이 느려졌나".**

- 레코드당 처리 시간 × `max.poll.records`를 계산해 한도와 비교한다.
- 최근에 느려진 것이라면 다운스트림부터: DB 슬로우 쿼리, 외부 API
  응답 지연, 커넥션 풀 고갈. 특정 메시지에서만 멈춘다면 poison pill
  (처리 불가능한 메시지가 파티션을 막는 것) 여부를 본다.
- 대응: `max.poll.records` 축소(한 바퀴를 가볍게), 외부 호출에 타임아웃
  설정, 처리 로직 최적화. `max.poll.interval.ms` 증가는 근본 원인을
  못 고칠 때의 완충이지 1순위가 아니다.

**③ 하트비트 단절이라면 — "프로세스에 무슨 일이".**

- GC 로그에서 긴 stop-the-world 발생 여부 (하트비트 스레드도 GC 중엔
  멈춘다), OOM 킬·파드 재시작 이력, CPU 스로틀링, 네트워크 이슈.
- 대응: 힙/GC 튜닝, 리소스 한도 조정, 불안정한 인프라 교체. 재시작이
  잦은 환경이면 정적 멤버십(`group.instance.id`)으로 복귀를 리밸런싱
  없이 처리하는 것도 검토한다.

**④ 악순환(rebalance storm) 여부를 본다.** 리밸런싱으로 밀린 랙을
따라잡느라 배치가 무거워지고 → 처리가 더 느려져 또 쫓겨나고 → 다시
리밸런싱… 이 소용돌이에 들어갔다면 원인 수리와 별개로 **고리를 먼저
끊는다**: `max.poll.records`를 줄여 한 바퀴를 짧게 만들거나, 문제
컨슈머를 잠시 내리고 안정화 후 재투입한다.

```properties
# Before: 무거운 배치 + 빠듯한 한도 — 처리 급증 시 축출 반복
max.poll.records=500
max.poll.interval.ms=300000   # 5분 (기본값)

# After: 한 바퀴를 가볍게 — 축출 없이 같은 처리량을 여러 바퀴로 나눔
max.poll.records=100          # 폴링당 처리량을 줄여 poll 간격 단축
max.poll.interval.ms=600000   # 정당하게 긴 작업이면 한도도 현실화
# + 외부 호출에 타임아웃: 다운스트림 지연이 poll 간격을 잡아먹지 않게
```

## 3. 꼬리질문 대비 포인트

### "heartbeat.interval.ms는 두 설정과 어떤 관계인가요?"

하트비트를 **보내는 주기**다. `session.timeout.ms`는 그 신호가 끊겼다고
**판정하는 한도**이므로 항상 주기 < 한도여야 하고, 관례상 한도의 1/3
이하로 잡는다 — 한 번의 유실이나 지연으로 바로 사망 판정이 나지 않고
몇 번의 재시도 기회가 생기게 하기 위해서다. 정리하면: 보내는 주기
(`heartbeat.interval.ms`) → 죽음 판정(`session.timeout.ms`) → 게으름
판정(`max.poll.interval.ms`)의 3층 구조다.

### "max.poll.interval.ms를 아주 크게 잡으면 문제가 없어지지 않나요?" (시니어 변별 포인트)

축출은 없어지지만 **감지도 없어진다.** 처리 스레드가 교착이나 무한
루프에 빠져도(하트비트 스레드는 멀쩡히 뛰므로 세션 타임아웃엔 안
걸린다) 그 컨슈머는 파티션을 움켜쥔 채 한도 시간만큼 아무것도
소비하지 않는다 — 그동안 해당 파티션의 랙은 계속 쌓인다. 즉 이 값은
"장애 감지 속도 vs 정상적인 긴 처리의 허용" 사이의 다이얼이다.
정당하게 긴 작업이라면 값을 키우기보다 배치를 줄이거나, 무거운 작업을
별도 워커로 넘기고 컨슈머는 빠르게 poll 루프를 도는 구조가 낫다.

### "처리 시간이 원래 긴 메시지(수 분짜리 작업)는 어떻게 다루나요?"

세 가지 접근이 있다. ① `max.poll.records`를 극단적으로 줄이고
`max.poll.interval.ms`를 현실적인 값으로 — 가장 단순하지만 처리량
한계. ② 컨슈머는 메시지를 받아 작업 큐/워커 스레드에 넘기고 즉시
poll 루프로 복귀 — 처리량은 좋지만 **오프셋 커밋을 워커 완료와 동기화
하지 않으면 유실**이 생기므로 커밋 관리가 어려워진다. ③ 긴 작업은
별도 시스템(배치, 작업 큐)으로 위임하고 Kafka에는 트리거만 흘리기 —
설계 차원의 회피. "poll 루프는 빠르게 유지한다"가 공통 원칙이다.

### "session.timeout.ms를 줄이면 장애 감지가 빨라지니 좋은 것 아닌가요?"

빠른 감지와 오탐은 트레이드오프다. 너무 짧으면 일시적 네트워크 지연,
짧은 GC에도 사망 판정이 나서 **불필요한 리밸런싱이 늘어난다** — 잦은
리밸런싱의 비용(소비 중단, 중복 버스트)이 빠른 감지의 이득을 넘어설
수 있다. 반대로 너무 길면 죽은 컨슈머의 파티션이 그 시간 동안
방치된다. 배포·재시작 시간, GC 특성, 네트워크 품질을 근거로 정하는
값이지 무조건 줄이는 값이 아니다.

### "두 타임아웃 모두 정상인데도 리밸런싱이 반복된다면?" (가산점 포인트)

멤버 축출 말고도 리밸런싱 트리거는 있다 — 새 멤버의 합류다.
오토스케일러가 컨슈머를 계속 늘렸다 줄였다 하거나, 크래시 루프에
빠진 파드가 재시작하며 매번 새 멤버로 합류하거나(정적 멤버십이 없을
때), 배포 파이프라인이 잦게 도는 경우다. 즉 "누가 쫓겨났나"뿐 아니라
"누가 자꾸 들어오나"도 봐야 한다. 그룹의 멤버 목록 변화 이력과 배포
이력을 겹쳐 보면 답이 나온다.

---

## 한 줄 요약

`session.timeout.ms`는 하트비트로 "죽었는가"를, `max.poll.interval.ms`는
poll 간격으로 "일이 멈췄는가"를 판정하는 서로 다른 생존 검사다 —
리밸런싱이 반복되면 **로그에서 어느 쪽에 걸려 쫓겨났는지부터 갈라야**
처리 지연 수사(다운스트림·배치 크기)로 갈지, 인프라 수사(GC·리소스·
네트워크)로 갈지가 정해진다.
