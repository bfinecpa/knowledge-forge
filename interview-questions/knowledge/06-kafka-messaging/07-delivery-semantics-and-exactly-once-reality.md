# 전달 의미론 — "정확히 한 번"은 어디까지가 진짜인가

> 핵심 관전 포인트: **전달 의미론은 "장애가 났을 때 메시지가 몇 번 처리되는가"에 대한 계약이다. 보내는 쪽은 응답이 안 왔을 때 "못 갔다"인지 "갔는데 응답만 유실됐다"인지 구별할 수 없고, 그래서 선택지는 재전송(중복 감수)과 포기(유실 감수) 둘뿐이다 — at-most-once는 유실을, at-least-once는 중복을 감수하고, exactly-once는 둘 다 없애겠다는 약속이지만 그 약속에는 경계가 있다. Kafka의 exactly-once는 멱등 프로듀서(프로듀서 ID + 시퀀스 번호로 재전송 중복을 브로커가 걸러냄)와 트랜잭션(여러 파티션 쓰기 + 컨슈머 오프셋 커밋을 한 원자 단위로 묶음)의 조합이라, "Kafka에서 읽어 Kafka에 쓰는" 파이프라인 안에서만 성립하고 컨슈머가 PostgreSQL에 쓰거나 외부 API를 부르는 순간 경계 밖이라 깨진다. 그래서 실무 정답은 exactly-once delivery를 좇는 게 아니라 at-least-once + 멱등 처리로 exactly-once "효과"를 만드는 것이다.**

---

## 0. 질문 + 의도

**질문**: "at-least-once, at-most-once, exactly-once 전달 의미론을 설명해주세요. 실무에서 exactly-once는 현실적인가요?"

**출제 의도**: "정확히 한 번"이 공짜가 아니며 대부분 at-least-once + 멱등 처리로 푼다는 실무 감각을 확인한다. 벤더 마케팅 용어("exactly-once 지원!")와 실제 보장 범위를 구분하는 비판적 시각 — 문서의 보장 문구를 그대로 믿지 않고 "어느 경계 안에서의 보장인가"를 따져 묻는 습관이 있는지를 본다.

## 1. 세 가지 의미론 — 왜 하필 이 셋뿐인가

### 1-1. 전제 지식 — 응답이 안 오면 무슨 일이 벌어졌는지 알 수 없다

세 의미론을 외우기 전에, **왜 애초에 "정확히 한 번"이 어려운가**를 먼저 깔아야 한다. 이걸 건너뛰면 세 이름이 그냥 암기 대상이 된다.

메시지를 네트워크로 보내는 쪽 입장에서 생각해 보자. 메시지를 보냈는데 응답이 안 왔다. 이때 실제로 벌어진 일은 두 가지 중 하나다.

```
[보내는 쪽]                              [받는 쪽]
    |
    | ──── 메시지 ────────X (여기서 유실)          (가) 못 받았다
    |
    | ──── 메시지 ─────────────────────>  받아서 저장까지 마침
    |                                      |
    | <────────── 응답 ────X (여기서 유실)  |     (나) 받았다
    |
    v
  "응답이 안 왔다"  ← 보내는 쪽이 관측한 사실은 이것뿐이다
```

**보내는 쪽이 손에 쥔 정보는 "응답이 안 왔다" 하나뿐이고, 그것만으로는 (가)와 (나)를 구별할 방법이 없다.** 받는 쪽 로그를 볼 수도 없고, 물어보는 것 자체가 또 하나의 네트워크 요청이라 그 요청도 똑같이 유실될 수 있다.

구별할 수 없으면 행동은 두 가지뿐이다.

```
                  "응답이 안 왔다"
                        |
          ┌─────────────┴─────────────┐
          |                           |
     다시 보낸다                   포기한다
          |                           |
   (나)였다면 → 중복             (가)였다면 → 유실
   (가)였다면 → 정상             (나)였다면 → 정상
          |                           |
    at-least-once               at-most-once
```

**세 가지 의미론은 이 갈림길에 붙인 이름이다.** 새로운 기술 세 개가 아니라, "무엇을 감수할지"를 고른 결과에 이름을 붙인 것이다. 그리고 exactly-once는 이 갈림 자체를 없애겠다는 세 번째 주장인데, 전송 계층만으로는 만들 수 없다 — 그래서 뒤에서 볼 여러 장치가 필요해진다.

### 1-2. 세 이름의 정의

- **at-most-once(최대 한 번)**: 메시지가 0회 또는 1회 처리된다. 재전송하지 않으므로 중복은 절대 없지만, 유실은 있을 수 있다.
- **at-least-once(최소 한 번)**: 메시지가 1회 이상 처리된다. 확인될 때까지 재전송하므로 유실은 없지만, 중복은 있을 수 있다.
- **exactly-once(정확히 한 번)**: 메시지가 딱 1회 처리된다. 유실도 중복도 없다.

정상 상황에서는 **세 의미론 모두 메시지가 한 번씩 처리된다.** 차이는 **장애와 재시도가 끼어들었을 때** 비로소 드러난다. 그래서 개발 환경에서는 셋이 구별되지 않고, 운영에서 처음 차이가 나타난다.

| 의미론 | 보장 | 감수하는 것 | 어울리는 데이터 |
|---|---|---|---|
| at-most-once | 최대 한 번 (0 또는 1회) | 유실 | 메트릭, 위치 업데이트 |
| at-least-once | 최소 한 번 (1회 이상) | 중복 | 대부분의 비즈니스 이벤트 |
| exactly-once | 정확히 한 번 | 비용·범위 제약 | Kafka 내 스트림 처리 |

표의 세 번째 열이 핵심이다. **유실과 중복 중 하나는 반드시 골라야 한다.** 둘 다 피하는 제3의 길은 전송 계층에는 없다. exactly-once가 "비용·범위 제약"을 감수한다고 적힌 이유가 여기 있다 — 그것은 전송 계층 바깥에 추가 장치를 붙여서 만들어내는 것이고, 그 장치가 미치는 범위 밖에서는 다시 무너진다.

### 1-3. 비유 — 등기우편과 일반우편

**일반우편**이 at-most-once다. 부치면 끝이고, 도착 여부를 확인하지 않는다. 우체국에서 분실되면 그걸로 사라진다. 대신 싸고 빠르다.

**등기우편에 "도착 확인이 안 오면 다시 부친다"는 규칙을 더한 것**이 at-least-once다. 편지는 반드시 도착하지만, 도착 확인서가 오는 길에 분실되면 같은 편지를 한 번 더 부치게 된다. 받는 사람은 같은 편지를 두 통 받는다.

그리고 받는 사람이 **봉투에 적힌 일련번호를 확인해 "이미 처리한 번호면 무시한다"**는 규칙을 세우면, 두 통이 와도 결과는 한 통 받은 것과 같아진다. 이것이 뒤에서 볼 **멱등 처리**이고, 실무의 exactly-once는 사실상 이 형태다. 우편 시스템을 완벽하게 만드는 것이 아니라, 받는 사람 쪽에서 중복을 흡수하는 것이다.

## 2. 의미론은 한 곳에서 정해지지 않는다 — 구간별 합성

"우리 시스템은 at-least-once입니다"라는 말은 사실 **두 구간에 대한 주장**이다. 메시지는 프로듀서에서 브로커로 한 번, 브로커에서 컨슈머로 한 번, 총 두 번의 네트워크 구간을 건넌다.

```
[프로듀서] ──구간 1──> [브로커(파티션 로그)] ──구간 2──> [컨슈머]
              ^                                    ^
              |                                    |
       acks, retries,                        오프셋 커밋 시점이
       enable.idempotence가                  이 구간의 의미론을 정한다
       이 구간의 의미론을 정한다
```

**전체 의미론은 두 구간 중 약한 쪽을 따라간다.** 한 구간이라도 유실 구조면 전체는 at-most-once로 떨어진다. 프로듀서를 아무리 튼튼하게 설정해도 컨슈머가 처리 전에 오프셋을 커밋해 버리면 전체는 유실 가능한 시스템이다.

### 2-1. 프로듀서 → 브로커 구간

이 구간의 의미론을 정하는 설정은 두 개다. 먼저 `acks`부터 짚자.

**`acks`는 "브로커의 몇 명이 받았다고 해야 성공으로 칠 것인가"를 정하는 값이다.** Kafka의 파티션은 리더 한 대와 팔로워 여러 대로 복제되는데, `acks=0`은 응답을 아예 기다리지 않고, `acks=1`은 리더만 받으면 성공, `acks=all`은 동기화 대상 복제본 전부가 받아야 성공이다. (내구성 관점의 상세는 10번 문서에서 다룬다.)

이제 구간별 의미론을 보자.

- **`acks=0` + 재시도 없음**: 보내고 확인하지 않는다. 유실을 알아챌 방법조차 없으니 **at-most-once**다.
- **`acks=all` + `retries` 설정**: 확인될 때까지 재전송하므로 유실은 막는다. 그런데 1-1에서 본 그 상황이 여기서 그대로 벌어진다 — **"브로커는 받아서 로그에 썼는데 응답만 유실 → 프로듀서가 재전송"**이면 브로커 로그에 **같은 메시지가 두 번 저장**된다. 그래서 **at-least-once**다.
- **`enable.idempotence=true`(멱등 프로듀서)**: 바로 위의 "재전송으로 인한 브로커 내 중복 저장"을 없앤다. 아래에서 자세히 본다.

#### `enable.idempotence`가 정확히 무엇을 막는가

먼저 동작 원리다. **프로듀서에 고유 ID(PID, producer id)를 부여하고, 파티션별로 보내는 메시지 묶음마다 1씩 증가하는 시퀀스 번호를 붙인다.** 브로커는 파티션마다 "이 PID로부터 마지막으로 받은 시퀀스 번호"를 기억해 두고, 이미 받은 번호가 다시 오면 **로그에 쓰지 않고 성공 응답만 돌려준다.**

```
프로듀서(PID=7)                        브로커 파티션 P0
                                       (PID 7의 마지막 seq = 40)
  seq=41 [주문 생성] ────────────────>  seq 41 저장. 마지막 seq = 41로 갱신
                     <────X 응답 유실
  (응답이 없다 → 재전송)
  seq=41 [주문 생성] ────────────────>  "41은 이미 받았다"
                                        → 저장하지 않고 성공 응답만 반환
                     <──── 성공 ─────
  결과: 로그에는 주문 생성이 한 번만 남았고,
        프로듀서는 성공 응답을 받아 다음으로 넘어갔다
```

이 장치의 값을 정확히 짚자. 멱등 프로듀서가 없으면 "유실을 막으려면 재전송해야 하고, 재전송하면 중복이 생긴다"는 1-1의 딜레마를 프로듀서 구간에서 그대로 안게 된다. 멱등 프로듀서는 **재전송은 마음껏 하되 중복 저장은 브로커가 걸러내게** 해서, 이 구간에 한해 딜레마를 해소한다.

그런데 **막지 못하는 것**이 있다. 이 경계를 헷갈리면 "멱등 프로듀서를 켰으니 중복은 끝났다"는 잘못된 결론에 도달한다.

```
[막지 못하는 경우 1] 애플리케이션이 같은 내용을 두 번 발행한다
  seq=41 [주문 8471 생성] ───> 저장 (seq 41)
  seq=42 [주문 8471 생성] ───> 저장 (seq 42)
  → 시퀀스 번호가 다르므로 브로커에겐 서로 다른 두 메시지다.
    내용이 같은지는 브로커가 알 바 아니다. 그대로 두 건 저장된다.

[막지 못하는 경우 2] 프로세스가 재시작한다
  구 프로세스: PID=7,  seq=41 [주문 8471 생성] ───> 저장
  (크래시 후 재기동, 같은 이벤트를 다시 발행)
  새 프로세스: PID=8,  seq=0  [주문 8471 생성] ───> 저장
  → PID가 다르면 중복 판정의 비교 대상 자체가 아니다. 그대로 두 건 저장된다.
```

한 줄로 정리하면 이렇다. **`enable.idempotence`가 막는 것은 "프로듀서 클라이언트가 자기 판단으로 재시도해서 생긴 브로커 측 중복 저장"이고, 막지 못하는 것은 "애플리케이션 코드가 같은 내용을 두 번 발행하는 것"이다.** 전자는 전송 계층의 중복, 후자는 비즈니스 레벨의 중복이다. 이 둘을 구분해 말하는 것이 이 주제에서 가장 자주 나오는 변별 포인트다.

참고로 Kafka 3.0부터 프로듀서의 기본값이 `enable.idempotence=true`, `acks=all`로 바뀌었다. 즉 요즘 기본 설정은 "프로듀서 구간은 유실 없음 + 재전송 중복 없음"에서 출발한다.

### 2-2. 브로커 → 컨슈머 구간

이 구간의 의미론은 **오프셋 커밋 시점**이 정한다(05번 문서에서 상세히 다룬다).

**오프셋**은 컨슈머가 "이 파티션을 어디까지 읽었는지"를 나타내는 숫자이고, **커밋**은 그 숫자를 Kafka에 기록해 두는 행위다. 컨슈머가 죽었다가 살아나면 커밋된 오프셋부터 다시 읽기 시작한다. 그래서 "처리와 커밋 중 무엇을 먼저 하는가"가 이 구간의 운명을 가른다.

```
[처리 전 커밋]  커밋 ──> 처리
                       ^
                       └ 여기서 죽으면: 커밋은 됐는데 처리는 안 됐다
                         → 재시작해도 이 메시지를 다시 안 받는다 = 유실
                         = at-most-once 성향

[처리 후 커밋]  처리 ──> 커밋
                       ^
                       └ 여기서 죽으면: 처리는 됐는데 커밋은 안 됐다
                         → 재시작하면 이 메시지를 다시 받는다 = 중복
                         = at-least-once
```

실무 정석은 **처리 후 커밋**이다. 중복은 멱등 처리로 흡수할 수 있지만 유실은 흡수할 방법이 없기 때문이다. 없어진 데이터를 되살리는 코드는 쓸 수 없다.

### 2-3. 합성 결과

흔한 실무 구성 — `acks=all` + 멱등 프로듀서 + 처리 후 커밋 — 의 최종 의미론은 이렇게 나온다.

```
구간 1 (프로듀서→브로커):  유실 없음, 재전송 중복 없음   → at-least-once (사실상 정확히 1회)
구간 2 (브로커→컨슈머):    유실 없음, 중복 가능          → at-least-once
                                    |
                        약한 쪽을 따라간다
                                    v
                    전체:  at-least-once
```

**유실은 없지만 컨슈머 입장에서 중복 수신은 언제든 가능하다.** 이것이 대부분의 Kafka 시스템이 실제로 서 있는 자리이고, 그래서 "컨슈머는 멱등하게 만든다"가 기본기가 된다.

## 3. Kafka의 exactly-once — 무엇이고, 어디까지인가

### 3-1. 두 장치의 조합

Kafka가 제공하는 exactly-once(EOS, exactly-once semantics)는 두 장치의 조합이다.

- **멱등 프로듀서**: 2-1에서 본 대로, 재시도로 인한 브로커 내 중복 저장을 제거한다. 단 보장 범위는 **프로듀서 세션·파티션 단위**다 — 애플리케이션이 재기동 후 같은 메시지를 다시 `send()`하는 것까지 막아주지는 못한다.
- **트랜잭션**: 여러 파티션에 대한 쓰기 + **컨슈머 오프셋 커밋**을 하나의 원자 단위로 묶는다.

두 번째가 이 절의 본론이다.

### 3-2. Kafka 트랜잭션의 실체

트랜잭션이라는 말이 나오면 DB의 `@Transactional`을 떠올리기 쉬운데, Kafka 트랜잭션이 원자적으로 묶는 대상은 다르다. **"여러 토픽·파티션에 대한 쓰기"와 "입력 오프셋의 커밋"이다.**

먼저 `transactional.id`부터. **`transactional.id`는 프로듀서에 붙이는 사람 이름 같은 것으로, 프로세스가 재시작해도 유지되는 식별자다.** 앞에서 본 PID는 세션마다 새로 발급되지만, `transactional.id`가 있으면 새 세션이 시작될 때 Kafka가 "아, 예전의 그 프로듀서구나"를 알아본다. 그래서 재시작 전에 열려 있던 미완결 트랜잭션을 정리하고, **낡은 세션이 뒤늦게 쓰기를 시도하면 거절**할 수 있다(좀비 차단).

동작 흐름은 이렇다.

```java
// 애플리케이션 기동 시 한 번: transactional.id로 신원을 등록하고,
// 이전 세션이 남긴 미완결 트랜잭션을 정리한다.
producer.initTransactions();

while (true) {
    ConsumerRecords<K, V> records = consumer.poll(Duration.ofMillis(200));

    producer.beginTransaction();
    try {
        for (var record : records) {
            // 처리 결과를 출력 토픽에 쓴다. 여러 토픽·파티션에 써도
            // 아래 commitTransaction() 전까지는 아무도 못 본다.
            producer.send(new ProducerRecord<>("orders-aggregated", transform(record)));
        }

        // 핵심은 이 줄이다. 입력 오프셋 커밋을 컨슈머가 아니라
        // 프로듀서를 통해 트랜잭션 안에서 한다. 그래야 "출력 쓰기"와
        // "입력을 어디까지 읽었나"가 함께 확정되거나 함께 무효가 된다.
        producer.sendOffsetsToTransaction(offsetsOf(records), consumer.groupMetadata());

        producer.commitTransaction();
    } catch (Exception e) {
        // 중단하면 출력 쓰기도, 오프셋 커밋도 없던 일이 된다.
        // 재시작하면 같은 입력을 다시 읽어 처음부터 처리한다.
        producer.abortTransaction();
    }
}
```

`sendOffsetsToTransaction`이 이 구조의 심장이다. **오프셋 커밋까지 트랜잭션에 넣었기 때문에 "읽기-처리-쓰기"가 원자적이 된다.** 오프셋 커밋을 컨슈머가 따로 했다면, "출력은 썼는데 오프셋 커밋은 실패" 또는 "오프셋은 커밋했는데 출력 쓰기는 실패"라는 어긋남이 다시 생긴다.

커밋하면 브로커는 관련된 각 파티션 로그 끝에 **트랜잭션 마커**를 기록한다. 마커는 실제 데이터가 아니라 "여기까지의 이 트랜잭션은 커밋됨(또는 중단됨)"이라고 알리는 제어용 표식이다.

읽는 쪽도 설정이 필요하다. **`isolation.level=read_committed`**로 두어야 컨슈머가 커밋되지 않은 트랜잭션의 메시지를 건너뛴다. 기본값인 `read_uncommitted`는 마커를 무시하고 로그에 있는 것을 전부 읽으므로, 중단될 트랜잭션의 메시지까지 읽어버린다.

여기서 **안정 오프셋(LSO, last stable offset)** 개념이 나온다. **파티션 로그에서 "그 지점 앞에는 아직 결말이 안 난 트랜잭션이 하나도 없는" 위치**를 가리킨다.

```
파티션 로그:  ... [T1:m1] [T1:m2] [T1 커밋마커] [T2:m3] [T2:m4] ...
                                                ^
                                                |
                                        안정 오프셋(LSO)
                                        여기까지는 미결 트랜잭션이 없다

  read_committed 컨슈머는 LSO를 넘어서 읽지 않는다.
  T2가 커밋되거나 중단되어야 LSO가 앞으로 나아간다.
```

이 그림이 실무적으로 의미하는 바가 하나 있다. **트랜잭션이 열린 채 오래 끌면 그 뒤의 메시지들도 read_committed 컨슈머에게 보이지 않는다.** 즉 트랜잭션 크기와 지연은 소비 지연으로 직결된다. 프로듀서가 트랜잭션을 열어두고 죽어버린 경우에도 `transaction.timeout.ms`로 강제 종료될 때까지 LSO가 멈춰 있다.

### 3-3. 이 조합이 성립하는 무대

두 장치가 함께 성립하는 무대는 **"Kafka에서 읽어 → 처리하고 → Kafka에 쓰는"** 파이프라인이다.

```
[입력 토픽] ──> [처리] ──> [출력 토픽]
     ^                          ^
     |                          |
   오프셋 커밋              메시지 쓰기
     └────── 한 트랜잭션 ────────┘
```

입력 오프셋 커밋과 출력 메시지 쓰기가 같은 트랜잭션이므로, 중간에 죽으면 오프셋도 롤백되어 재처리되고 출력도 롤백되어 중복 발행이 없다. Kafka Streams가 설정 하나(`processing.guarantee=exactly_once_v2`)로 이 모드를 제공하는 것도, **읽기 쪽과 쓰기 쪽이 모두 Kafka라서** 한 시스템의 트랜잭션으로 전부 감쌀 수 있기 때문이다.

### 3-4. 경계 밖으로 나가는 순간 깨진다

현실의 컨슈머는 Kafka에만 쓰지 않는다. 대부분 DB에 쓴다. 그 순간 어떤 일이 벌어지는지 구체적으로 보자.

```java
@KafkaListener(topics = "order-events")
public void handle(OrderEvent event) {
    // ① PostgreSQL에 INSERT하고 커밋한다. 이건 PostgreSQL의 트랜잭션이다.
    orderRepository.save(toOrder(event));

    // ② 리스너가 정상 리턴하면 그때 컨테이너가 오프셋을 커밋한다.
    //    이건 Kafka에 남기는 별개의 기록이다.
}
```

①과 ② 사이에서 크래시하면 어떻게 되는가.

```
t0  ① PostgreSQL: INSERT INTO orders ... ; COMMIT;
    → 주문 한 건이 DB에 확정됐다. 되돌릴 수 없다.

t1  ★ 프로세스 크래시 (또는 리밸런싱으로 파티션을 빼앗김)

t2  ② 오프셋 커밋은 일어나지 않았다.
    → Kafka가 아는 마지막 커밋 지점은 이 메시지 이전이다.

t3  재시작 → 커밋된 오프셋부터 다시 읽음 → 같은 OrderEvent를 다시 수신

t4  ① 다시 실행 → orders 테이블에 같은 주문이 두 건이 된다
```

여기서 "그럼 Kafka 트랜잭션으로 묶으면 되지 않나?"라는 생각이 자연스럽게 나온다. 안 된다. **Kafka 트랜잭션이 감쌀 수 있는 것은 Kafka의 것뿐이다.**

```
   ┌──── Kafka 트랜잭션이 감쌀 수 있는 범위 ─────┐
   │   Kafka 토픽 쓰기      컨슈머 오프셋 커밋    │
   └────────────────────────────────────────────┘

        PostgreSQL INSERT     ← 밖이다
        외부 PG사 결제 API     ← 밖이다
        Redis 캐시 갱신        ← 밖이다
```

트랜잭션으로 오프셋 커밋을 아무리 안전하게 만들어도, **DB 커밋은 그 트랜잭션 안에 들어올 수 없으므로** "DB는 커밋됐는데 오프셋 커밋은 실패"라는 어긋남은 그대로 남는다.

왜 그런 일반해가 없는지도 한 줄로 답할 수 있어야 한다. 두 독립 시스템에 걸친 원자적 확정은 **분산 합의 문제**라서, "메시지를 정확히 한 번 전달받았음을 양쪽이 동시에 확신하는" 일반해는 존재하지 않는다. 불확실한 채널 위에서 두 참여자가 완전한 합의에 도달할 수 없다는 **두 장군 문제**와 같은 구조다 (가산점 포인트). 1-1에서 본 "응답이 안 왔을 때 구별할 수 없다"가 바로 이 문제의 최소 형태다.

### 3-5. 그래서 정확한 표현은 이렇다

**exactly-once "delivery"는 시스템 경계를 넘는 순간 불가능하고, 가능한 것은 exactly-once "processing 효과"다.**

전달은 at-least-once로 두되, **같은 메시지를 두 번 받아도 결과가 한 번 처리한 것과 같도록 처리 쪽을 멱등하게** 만드는 것이다. 여기서 **멱등성(idempotency)**은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"을 말한다.

위의 깨진 코드를 멱등하게 고치면 이렇게 된다.

```java
@KafkaListener(topics = "order-events")
@Transactional   // PostgreSQL 트랜잭션. Kafka 트랜잭션이 아니다.
public void handle(OrderEvent event) {
    // 이벤트마다 프로듀서가 발급한 고유 ID(eventId)를 유니크 키로 삼는다.
    // "이미 처리했나?"를 조회로 확인하지 않고 곧바로 INSERT를 시도하는 이유는,
    // 조회와 INSERT 사이의 틈에 같은 이벤트의 두 번째 처리가 끼어들 수 있어서다.
    // 유니크 제약과 결합하면 확인과 선점이 DB 안에서 한 번에 원자적으로 일어난다.
    int inserted = processedEventRepository.insertIfAbsent(event.eventId());

    // 0이면 이미 처리된 이벤트다. 조용히 리턴하면 오프셋만 커밋되고 끝난다.
    // 예외를 던지면 안 된다 — 중복 수신은 오류가 아니라 정상적으로
    // 예상되는 상황이고, 예외를 던지면 재시도 루프에 빠진다.
    if (inserted == 0) return;

    orderRepository.save(toOrder(event));
    // 처리 이력 INSERT와 실제 업무 쓰기가 같은 PostgreSQL 트랜잭션이라
    // "이력만 남고 주문은 없는" 어긋남이 생기지 않는다.
}
```

```sql
CREATE TABLE processed_event (
    event_id     uuid        PRIMARY KEY,   -- 중복 판정의 기준
    processed_at timestamptz NOT NULL DEFAULT now()
);
-- insertIfAbsent는 INSERT ... ON CONFLICT (event_id) DO NOTHING 이다.
-- 충돌 시 예외 없이 0행 삽입으로 끝나므로 분기가 단순해진다.
```

구현 상세는 11번 문서에서 다룬다. 여기서 핵심은 **exactly-once가 인프라 설정이 아니라 처리 로직의 성질로 달성된다**는 방향 전환이다.

### 3-6. 실무 감각 — 데이터별로 의미론을 고른다

모든 데이터에 같은 보장을 걸 필요는 없다. 데이터의 가치에 보장 수준을 맞춘다.

**로그·메트릭·실시간 위치**는 한두 건 유실이 중복 처리 비용보다 싸다. at-most-once 성향 설정(`acks=0~1`, 가벼운 커밋)으로 처리량을 산다. 초 단위 메트릭은 한 점이 빠져도 그래프가 유효하고, 차량 위치는 최신값만 의미가 있어 과거 값 재전송이 오히려 노이즈다.

**주문·결제·정산 등 비즈니스 이벤트**는 유실이 불가하다. at-least-once + 멱등 컨슈머가 표준 조합이다. 여기서 유실을 허용하면 돈이 사라지거나 생겨난다.

**Kafka 안에서 끝나는 스트림 집계**(예: 이벤트 → 집계 → 다른 토픽)는 EOS가 실제로 유효한 영역이다. 다만 트랜잭션 코디네이션 비용으로 지연·처리량 손해가 있으므로, 집계 정확성이 그 비용을 정당화할 때 쓴다. 3-2에서 본 LSO 때문에 read_committed 컨슈머의 체감 지연이 트랜잭션 주기만큼 늘어난다는 점도 계산에 넣어야 한다.

정리하면, **"exactly-once 지원"이라는 문구를 보면 "어느 경계 안에서?"를 묻는 것** — 이것이 이 질문이 확인하려는 비판적 시각이다.

## 4. 꼬리질문 대비 포인트

### "enable.idempotence는 무엇을 막고, 무엇을 못 막나?"

**막는 것**: 프로듀서 클라이언트 내부의 **재시도**로 같은 배치가 브로커에 두 번 저장되는 것. 프로듀서 ID(PID) + 파티션별 시퀀스 번호로 브로커가 "이미 받은 시퀀스"를 감지해 저장 없이 성공 응답만 돌려준다.

**못 막는 것**: 애플리케이션 레벨의 중복 — 코드가 `send()`를 두 번 부르거나, 재기동한 프로세스가 같은 비즈니스 이벤트를 다시 발행하는 경우. 새 프로세스는 새 프로듀서 세션이라 새 PID를 받으므로, 브로커 입장에선 아예 다른 프로듀서가 보낸 다른 메시지다.

즉 **"전송 계층의 중복"과 "비즈니스 레벨의 중복"을 구분해서 답하는 것**이 포인트다. 전자는 설정으로 해결되고 후자는 멱등 키 설계로 해결된다.

### "Kafka 트랜잭션으로 DB 쓰기까지 묶을 수는 없나?"

없다. Kafka 트랜잭션의 원자성 범위는 **Kafka 토픽 쓰기와 컨슈머 오프셋 커밋까지**다.

DB와 Kafka에 걸친 정합성은 방향별로 다른 패턴을 쓴다.

- **발행 측**(DB 커밋과 이벤트 발행의 원자성): Transactional Outbox + CDC. 보낼 메시지를 같은 DB의 outbox 테이블에 INSERT해 업무 데이터 변경과 발행 예약을 한 트랜잭션으로 묶고, 별도 프로세스가 그 테이블을 읽어 Kafka로 발행한다(12번 문서).
- **소비 측**(이벤트 수신과 DB 반영의 중복 제거): 멱등 컨슈머. 3-5의 `processed_event` 방식이다(11번 문서).

**"양쪽을 한 트랜잭션으로" 대신 "각 경계에서 각자의 패턴으로"**가 분산 시스템의 표준 접근이라고 답하면 된다.

### "결제 시스템에서 '정확히 한 번 결제'를 요구받으면 어떻게 설계하나?" (시니어 변별 포인트)

전달 계층에 exactly-once를 요구하지 않고 **도메인 계층에서 멱등성으로 달성**한다.

결제 이벤트에 프로듀서가 발급한 고유 ID(멱등 키)를 싣고, 컨슈머는 처리 이력과 결제 반영을 같은 DB 트랜잭션으로 묶어 같은 키의 두 번째 처리를 무시한다. PG 같은 외부 결제사 호출에는 그쪽이 제공하는 idempotency key를 전달해 외부 경계에서도 중복을 흡수한다.

즉 "정확히 한 번 결제"는 인프라 설정이 아니라 **멱등 키가 이벤트 생성부터 외부 호출까지 관통하는 설계**로 만드는 것이다. 요구사항을 전달 보장 문제가 아니라 멱등성 설계 문제로 번역하는 답변이 시니어 답변이다.

### "at-most-once를 일부러 선택하는 경우가 실제로 있나?"

있다. **유실 비용 < 중복·재처리 비용**인 데이터가 그렇다.

- 초 단위 메트릭 — 한 점이 빠져도 그래프는 유효하다.
- 차량·배달원 위치 — 최신값만 의미가 있고, 과거 값 재전송은 오히려 노이즈다.
- 대량 로그 샘플링 — 애초에 전수가 목적이 아니다.

이런 데이터에 at-least-once 인프라 비용(재시도, 멱등 처리, 커밋 관리)을 쓰는 건 과설계다. **"모든 데이터가 같은 보장을 받을 필요는 없다 — 데이터의 가치에 보장 수준을 맞춘다"**가 답의 골격이다.

## 한 줄 요약

전달 의미론은 "응답이 안 왔을 때 재전송할 것인가"라는 갈림길에서 유실과 중복 중 무엇을 감수할지 고른 결과에 붙인 이름이고, Kafka의 exactly-once는 멱등 프로듀서(재전송 중복 제거)와 트랜잭션(파티션 쓰기 + 오프셋 커밋의 원자적 묶음)으로 Kafka 경계 안(읽기-처리-쓰기)에서만 성립하는 보장이므로 — PostgreSQL과 외부 API가 있는 현실 시스템의 정답은 exactly-once delivery를 좇는 것이 아니라 at-least-once + 멱등 처리로 exactly-once 효과를 만드는 것이다.
