# 전달 의미론 — "정확히 한 번"은 어디까지가 진짜인가

> 핵심 관전 포인트: **전달 의미론은 "장애가 났을 때 메시지가 몇 번
> 처리되는가"에 대한 계약이다. at-most-once는 유실을, at-least-once는
> 중복을 감수하고, exactly-once는 둘 다 없애겠다는 약속이지만 — Kafka의
> exactly-once는 트랜잭션으로 "Kafka 안에서의 읽기-처리-쓰기"에만
> 성립하고, 컨슈머가 DB에 쓰거나 외부 API를 부르는 순간 경계 밖이라
> 깨진다. 그래서 실무 정답은 exactly-once delivery를 좇는 게 아니라
> at-least-once + 멱등 처리로 exactly-once "효과"를 만드는 것이다.**

---

## 0. 질문 + 의도

**질문**: "at-least-once, at-most-once, exactly-once 전달 의미론을
설명해주세요. 실무에서 exactly-once는 현실적인가요?"

**출제 의도**: "정확히 한 번"이 공짜가 아니며 대부분 at-least-once +
멱등 처리로 푼다는 실무 감각을 확인한다. 벤더 마케팅 용어("exactly-once
지원!")와 실제 보장 범위를 구분하는 비판적 시각 — 문서의 보장 문구를
그대로 믿지 않고 "어느 경계 안에서의 보장인가"를 따져 묻는 습관이
있는지를 본다.

## 1. 세 가지 의미론 — 장애 시 무엇을 감수하는가

정상 상황에서는 세 의미론 모두 메시지가 한 번씩 처리된다. 차이는
**장애·재시도가 끼어들었을 때** 드러난다.

| 의미론 | 보장 | 감수하는 것 | 어울리는 데이터 |
|---|---|---|---|
| at-most-once | 최대 한 번 (0 또는 1회) | 유실 | 메트릭, 위치 업데이트 |
| at-least-once | 최소 한 번 (1회 이상) | 중복 | 대부분의 비즈니스 이벤트 |
| exactly-once | 정확히 한 번 | 비용·범위 제약 | Kafka 내 스트림 처리 |

핵심 통찰: **유실과 중복 중 하나는 반드시 골라야 한다.** 네트워크에서
"보냈는데 응답이 안 왔다"는 상황은 상대가 못 받은 것일 수도, 받았는데
응답만 유실된 것일 수도 있다. 이때 재전송하지 않으면 유실 가능성을
(at-most-once), 재전송하면 중복 가능성을(at-least-once) 안는 것이고,
둘 다 피하는 제3의 길은 전송 계층에는 없다.

## 2. 의미론은 한 곳에서 정해지지 않는다 — 구간별 합성

"우리 시스템은 at-least-once"라고 말하려면 프로듀서→브로커,
브로커→컨슈머 두 구간이 모두 그 보장을 지켜야 한다. 한 구간이라도
유실 구조면 전체는 at-most-once로 떨어진다.

### 2-1. 프로듀서 → 브로커 구간

- `acks=0` + 재시도 없음: 보내고 확인 안 함 → 유실 가능 = at-most-once
- `acks=all` + `retries` 설정: 확인될 때까지 재전송 → 유실은 막지만,
  "브로커는 받았는데 응답만 유실 → 재전송"으로 **브로커에 같은 메시지가
  두 번 저장**될 수 있다 = at-least-once
- `enable.idempotence=true`(멱등 프로듀서): 프로듀서마다 ID(PID)와
  메시지 시퀀스 번호를 붙여, 브로커가 재전송된 중복을 감지하고
  버린다 → **재시도로 인한 브로커 내 중복 저장**이 사라진다.

### 2-2. 브로커 → 컨슈머 구간

이 구간의 의미론은 **오프셋 커밋 시점**이 정한다(05번 문서 상세).
처리 전 커밋이면 유실 가능(at-most-once 성향), 처리 후 커밋이면 중복
가능(at-least-once). 실무 정석인 "처리 후 커밋"을 택하면 이 구간은
at-least-once다.

정리하면, 흔한 실무 구성(acks=all + 멱등 프로듀서 + 처리 후 커밋)의
최종 의미론은 **at-least-once**다. 유실은 없지만 컨슈머 입장에서 중복
수신은 언제든 가능하다.

## 3. Kafka의 exactly-once — 무엇이고, 어디까지인가

Kafka가 제공하는 exactly-once(EOS)는 두 장치의 조합이다.

- **멱등 프로듀서**: 위에서 본 대로, 재시도로 인한 브로커 내 중복
  저장을 제거한다. 단, 보장 범위는 프로듀서 세션·파티션 단위다 —
  애플리케이션이 재기동 후 같은 메시지를 다시 `send()`하는 것까지
  막아주지는 못한다.
- **트랜잭션**: 여러 파티션에 대한 쓰기 + **컨슈머 오프셋 커밋**을
  하나의 원자 단위로 묶는다. 실패하면 전부 없던 일이 되고,
  `read_committed` 컨슈머는 커밋 완료된 트랜잭션의 메시지만 읽는다.

이 조합이 성립하는 무대가 **"Kafka에서 읽어 → 처리하고 → Kafka에
쓰는"** 파이프라인이다. 입력 오프셋 커밋과 출력 메시지 쓰기가 같은
트랜잭션이므로, 중간에 죽으면 오프셋도 롤백되어 재처리되고, 출력도
롤백되어 중복 발행이 없다. Kafka Streams가 설정 하나로 이 모드를
제공하는 것도 읽기-쓰기 양쪽이 모두 Kafka라서 가능한 것이다.

### 3-1. 경계 밖으로 나가는 순간 깨진다

```java
@KafkaListener(topics = "order-events")
public void handle(OrderEvent event) {
    orderRepository.save(toOrder(event));   // ① DB에 쓰기 (DB 트랜잭션)
    // ② 리스너 리턴 후 오프셋 커밋 (Kafka 쪽 기록)
}
// ①과 ② 사이에서 크래시하면? DB에는 저장됐는데 오프셋 커밋은 안 됨
// → 재시작 후 같은 이벤트 재수신 → save가 다시 실행됨 = 중복
```

DB 커밋과 오프셋 커밋은 서로 다른 시스템의 서로 다른 기록이다. Kafka
트랜잭션은 Kafka의 토픽과 오프셋만 원자적으로 묶을 뿐, **외부 DB나
HTTP 호출을 그 트랜잭션 안에 넣을 수 없다.** 두 독립 시스템에 걸친
원자적 확정은 분산 합의 문제라서, "메시지를 정확히 한 번 전달받았음을
양쪽이 동시에 확신하는" 일반해는 존재하지 않는다(불확실한 채널 위에서
두 참여자가 완전한 합의에 도달할 수 없다는 두 장군 문제와 같은 구조 —
가산점 포인트).

그래서 정확한 표현은 이렇다: **exactly-once "delivery"는 시스템 경계를
넘는 순간 불가능하고, 가능한 것은 exactly-once "processing 효과"** —
전달은 at-least-once로 두되, 같은 메시지를 두 번 받아도 결과가 한 번
처리한 것과 같도록 처리 쪽을 멱등하게 만드는 것이다(구현은 11번 문서).

## 4. 실무 감각 — 데이터별로 의미론을 고른다

- **로그·메트릭·실시간 위치**: 한두 건 유실이 중복 처리 비용보다 싸다.
  at-most-once 성향 설정(acks=0~1, 가벼운 커밋)으로 처리량을 산다.
- **주문·결제·정산 등 비즈니스 이벤트**: 유실 불가. at-least-once +
  멱등 컨슈머가 표준 조합.
- **Kafka 안에서 끝나는 스트림 집계**(예: 이벤트 → 집계 → 다른 토픽):
  EOS가 실제로 유효한 영역. 단 트랜잭션 코디네이션 비용으로 지연·처리량
  손해가 있으므로, 집계 정확성이 그 비용을 정당화할 때 쓴다.

"exactly-once 지원"이라는 문구를 보면 **"어느 경계 안에서?"**를 묻는
것 — 이것이 이 질문이 확인하려는 비판적 시각이다.

## 5. 꼬리질문 대비 포인트

### "enable.idempotence는 무엇을 막고, 무엇을 못 막나?"

막는 것: 프로듀서 내부 **재시도**로 같은 배치가 브로커에 두 번 저장되는
것. 프로듀서 ID + 시퀀스 번호로 브로커가 "이미 받은 시퀀스"를 감지해
버린다. 못 막는 것: 애플리케이션 레벨의 중복 — 코드가 `send()`를 두 번
부르거나, 재기동한 프로세스가 같은 비즈니스 이벤트를 다시 발행하는 경우.
새 프로세스는 새 프로듀서 세션이라 브로커 입장에선 다른 메시지다. 즉
"전송 계층의 중복"과 "비즈니스 레벨의 중복"을 구분해서 답하는 것이
포인트다.

### "Kafka 트랜잭션으로 DB 쓰기까지 묶을 수는 없나?"

없다. Kafka 트랜잭션의 원자성 범위는 Kafka 토픽 쓰기와 컨슈머 오프셋
커밋까지다. DB와 Kafka에 걸친 정합성은 방향별로 다른 패턴을 쓴다 —
**발행 측**(DB 커밋과 이벤트 발행의 원자성)은 Transactional Outbox +
CDC, **소비 측**(이벤트 수신과 DB 반영의 중복 제거)은 멱등 컨슈머.
"양쪽을 한 트랜잭션으로" 대신 "각 경계에서 각자의 패턴으로"가 분산
시스템의 표준 접근이라고 답하면 된다.

### "결제 시스템에서 '정확히 한 번 결제'를 요구받으면 어떻게 설계하나?" (시니어 변별 포인트)

전달 계층에 exactly-once를 요구하지 않고 **도메인 계층에서 멱등성으로
달성**한다. 결제 이벤트에 프로듀서가 발급한 고유 ID(멱등 키)를 싣고,
컨슈머는 처리 이력과 결제 반영을 같은 DB 트랜잭션으로 묶어 같은 키의
두 번째 처리를 무시한다. PG 같은 외부 결제사 호출에는 그쪽이 제공하는
idempotency key를 전달해 외부 경계에서도 중복을 흡수한다. 즉 "정확히
한 번 결제"는 인프라 설정이 아니라 멱등 키가 이벤트 생성부터 외부
호출까지 관통하는 설계로 만드는 것 — 요구사항을 전달 보장 문제가 아니라
멱등성 설계 문제로 번역하는 답변이 시니어 답변이다.

### "at-most-once를 일부러 선택하는 경우가 실제로 있나?"

있다. 유실 비용 < 중복·재처리 비용인 데이터: 초 단위 메트릭(한 점
빠져도 그래프는 유효), 차량·배달원 위치(최신값만 의미 있고 과거 값
재전송은 오히려 노이즈), 대량 로그 샘플링. 이런 데이터에 at-least-once
인프라 비용(재시도, 멱등 처리, 커밋 관리)을 쓰는 건 과설계다. "모든
데이터가 같은 보장을 받을 필요는 없다 — 데이터의 가치에 보장 수준을
맞춘다"가 답의 골격이다.

## 한 줄 요약

전달 의미론은 장애 시 유실과 중복 중 무엇을 감수할지의 계약이고,
Kafka의 exactly-once는 Kafka 경계 안(읽기-처리-쓰기)에서만 성립하는
보장이므로 — DB와 외부 API가 있는 현실 시스템의 정답은 exactly-once
delivery를 좇는 것이 아니라 at-least-once + 멱등 처리로 exactly-once
효과를 만드는 것이다.
