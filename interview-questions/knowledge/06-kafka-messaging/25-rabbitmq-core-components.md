# RabbitMQ 기본 구성요소 — Exchange, Queue, Binding, Routing Key가 만드는 메시지의 경로

> 핵심 관전 포인트: **RabbitMQ의 핵심은 "발행하는 곳과 쌓이는 곳이 분리되어 있다"는 것이다. 프로듀서는 큐에 직접 넣지 않고 exchange(교환대)에 보내며, exchange는 메시지를 저장하지 않고 바인딩 규칙에 따라 큐로 배분만 한다. 컨슈머는 exchange가 아니라 큐에 붙는다. 이 분리 덕분에 "결제 실패 이벤트를 알림 큐와 보정 큐에 동시에" 같은 분배를 애플리케이션 코드 없이 브로커 설정으로 바꿀 수 있다. 대신 대가가 있다 — 어느 바인딩에도 걸리지 않은 메시지는 조용히 버려진다. 발행은 성공했는데 아무도 못 받는 무응답 장애가 여기서 나오고, 그래서 실무에서는 `mandatory` 플래그 + return 콜백이나 alternate exchange로 "갈 곳 없는 메시지"를 반드시 잡아둔다.**

---

## 0. 질문 + 의도

**질문**: "RabbitMQ의 기본 구성요소(Exchange, Queue, Binding, Routing Key)와 메시지가 흐르는 경로를 설명해주세요. 어느 큐에도 라우팅되지 못한 메시지는 어떻게 되나요?"

**출제 의도**: Kafka의 "토픽에 넣으면 컨슈머가 가져간다"와 달리 RabbitMQ는 발행 지점(exchange)과 저장 지점(queue)이 분리되어 있고 그 사이를 바인딩이 잇는다. 이 분리를 이해하지 못하면 "발행은 성공했는데 아무도 못 받는" 무응답 장애의 원인을 영원히 못 찾는다. 매일 쓰는 도구의 데이터 흐름을 그림으로 그릴 수 있는지, 그리고 그 그림에서 실패 지점을 짚어낼 수 있는지를 본다.

## 1. 전체 그림 — 부품 넷과 그 사이의 관계

### 1-1. 한 장으로 보는 구조

먼저 전체 경로를 눈에 넣고 시작하자. 각 부품이 무엇인지는 바로 아래에서 하나씩 정의한다.

```
[프로듀서]
    |
    | ① publish(exchange 이름, 라우팅 키, 메시지)
    v
+-------------------------------------------+
|  Virtual Host (vhost) — 논리적 격리 공간    |
|                                           |
|  [Exchange]  ← 저장하지 않는다. 배분만 한다  |
|      |                                    |
|      | ② 바인딩 규칙과 라우팅 키를 대조     |
|      |                                    |
|      +--(바인딩 키 "payment.*")--> [알림 큐]   --+
|      +--(바인딩 키 "payment.failed")-> [보정 큐] --+
|      +--(바인딩 키 "order.*")----> [주문 큐]      |
|                                                  |
+--------------------------------------------------+
                                                   |
                                        ③ 브로커가 컨슈머에게 push
                                                   v
                                          [알림 워커] [보정 워커]
```

Kafka를 먼저 배운 사람이 여기서 가장 헷갈리는 지점은 **"프로듀서가 큐 이름을 모른다"**는 것이다. Kafka에서는 프로듀서가 `orders` 토픽에 보내고 컨슈머도 `orders` 토픽에서 읽으므로 양쪽이 같은 이름을 공유한다. RabbitMQ에서 프로듀서가 아는 것은 exchange 이름과 라우팅 키뿐이고, 큐가 몇 개인지 이름이 무엇인지는 모른다. **큐를 만들고 바인딩을 거는 것은 소비하는 쪽의 책임**이다.

이 한 가지 차이가 확장성의 방향을 결정한다. 새 서비스가 결제 이벤트를 받고 싶으면, 자기 큐를 만들고 바인딩만 걸면 된다 — 프로듀서는 자기에게 소비자가 하나 늘었다는 사실조차 모른다.

### 1-2. Exchange — 저장하지 않는 분류 창구

**Exchange(익스체인지, 교환대)**는 프로듀서가 메시지를 보내는 지점이다. 이름이 "교환대"인 이유가 그대로 역할이다 — **받아서 넘길 뿐, 쌓아두지 않는다.**

우체국의 분류 창구를 생각하면 된다. 창구는 편지를 보관하지 않는다. 주소를 보고 어느 우편함으로 갈지만 정하고 즉시 넘긴다. 편지가 실제로 머무는 곳은 우편함(큐)이다.

여기서 초심자가 가장 자주 하는 오해를 미리 깨자. **exchange에는 메시지가 "들어 있지" 않다.** 관리 콘솔에서 exchange를 눌러도 메시지 목록이 나오지 않는 이유가 이것이다. 조회할 대상이 없다. 배분이 끝나면 exchange의 일은 끝난 것이고, 배분할 큐가 없었다면 메시지는 그 자리에서 사라진다.

### 1-3. Queue — 메시지가 실제로 머무는 곳

**Queue(큐)**는 메시지가 쌓여 컨슈머를 기다리는 저장소다. 컨슈머는 exchange가 아니라 **큐에 붙는다.**

큐는 기본적으로 FIFO(먼저 들어온 것이 먼저 나가는 구조)이며, 브로커가 메시지를 컨슈머에게 밀어주고(push) 처리 확인(ack)을 받으면 **그 메시지를 삭제한다.** 소비하면 사라진다는 이 성질이 Kafka와 갈리는 가장 근본적인 지점이다 — Kafka의 파티션은 로그 파일이라 읽어도 남지만, RabbitMQ의 큐는 우편함이라 꺼내면 빈다.

큐를 선언할 때 정하는 속성 중 실무에서 매번 마주치는 것은 셋이다.

- **durable**: 브로커가 재시작해도 큐 정의(그리고 그 안의 persistent 메시지)가 살아남는지. 끄면 브로커 재시작과 함께 큐 자체가 사라진다.
- **exclusive**: 선언한 커넥션만 쓸 수 있고 커넥션이 끊기면 큐가 삭제된다. RPC 응답용 임시 큐 같은 데 쓴다.
- **auto-delete**: 마지막 컨슈머가 떨어지면 큐가 삭제된다.

운영 서비스의 업무 큐는 사실상 항상 `durable=true, exclusive=false, auto-delete=false`다. 나머지 조합은 임시 큐를 위한 것이다.

### 1-4. Binding과 Routing Key — 규칙과 라벨

이제 exchange와 큐를 잇는 부분이다. 둘은 이름이 비슷해서 자주 섞이는데, **누가 붙이는가**로 구분하면 헷갈리지 않는다.

**Routing Key(라우팅 키)**는 **프로듀서가 메시지에 붙이는 문자열 라벨**이다. `payment.failed`, `order.kr.created` 처럼 점으로 구분한 단어열을 쓰는 것이 관례다. 편지 봉투에 적은 주소라고 보면 된다.

**Binding(바인딩)**은 **"이 exchange의 메시지를 저 큐로 보낸다"는 연결 선언**이며, 그 선언에 붙는 조건을 **바인딩 키(binding key)**라고 한다. 우편함에 붙여둔 "이 주소로 오는 편지는 여기로" 라는 안내판이다.

정리하면 이렇다.

| 이름 | 붙이는 주체 | 정체 | 비유 |
|---|---|---|---|
| 라우팅 키 | 프로듀서 (메시지마다) | 메시지에 붙은 주소 라벨 | 봉투에 쓴 주소 |
| 바인딩 키 | 소비하는 쪽 (큐 설정 시 1회) | 그 주소를 받아줄 조건 | 우편함의 안내판 |

exchange가 하는 일은 이 둘을 대조하는 것뿐이다. 대조 방식이 곧 exchange 타입이며, 그 이야기는 별도 문서(`26-rabbitmq-exchange-types-routing.md`)에서 자세히 다룬다. 여기서는 **"라우팅 키와 바인딩 키를 맞춰본다"**는 골격만 잡고 간다.

### 1-5. Virtual Host — 그림 바깥을 감싸는 격리 공간

**Virtual Host(vhost)**는 exchange·큐·바인딩·권한이 담기는 **논리적 격리 공간**이다. DB의 스키마나 Kubernetes의 네임스페이스와 같은 개념이다.

vhost가 다르면 이름이 같아도 완전히 다른 객체다. `/prod`의 `order.events` exchange와 `/stage`의 `order.events` exchange는 서로 아무 관계가 없다. 사용자 권한도 vhost 단위로 부여하므로, 한 클러스터를 여러 팀이 나눠 쓸 때의 기본 분리 단위가 된다.

접속 문자열에 vhost가 들어간다는 점이 실무에서 자주 무는 지점이다. `amqp://user:pass@host:5672/prod` 의 마지막 `/prod`가 vhost 이름인데, 이걸 빠뜨리면 기본 vhost인 `/`에 붙어 "큐가 없다"거나 "권한이 없다"는 오류를 만난다.

### 1-6. Connection과 Channel — 그림에는 안 보이지만 반드시 아는 것

마지막 부품은 구조도에 그려지지 않지만 실무 장애의 단골이다.

**Connection(커넥션)**은 애플리케이션과 브로커 사이의 **TCP 연결**이다. 연결을 맺는 데 TCP 핸드셰이크와 인증이 필요하므로 비싸다.

**Channel(채널)**은 그 하나의 TCP 연결 안에서 다중화되는 **가벼운 가상 연결**이다. 실제 명령(발행, 소비, 큐 선언, ack)은 모두 채널 위에서 오간다.

왜 이런 2단 구조인가? 스레드 100개가 각각 TCP 연결을 맺으면 브로커의 소켓과 메모리가 금방 바닥난다. 그래서 **커넥션은 소수로 유지하고, 그 위에 채널을 여러 개 얹어 쓴다.** 고속도로 하나에 차선을 여러 개 긋는 것과 같다.

여기서 반드시 기억할 규칙이 하나 있다. **채널은 스레드 안전하지 않다.** 여러 스레드가 한 채널을 공유해 발행하면 프레임이 섞여 깨진다. 스레드마다 채널을 따로 쓰거나, Spring AMQP의 `RabbitTemplate`처럼 내부적으로 채널 풀을 관리해주는 추상화를 쓰는 것이 정석이다.

```java
// 잘못된 코드 — 채널 하나를 여러 스레드가 공유
Channel channel = connection.createChannel();
executor.submit(() -> channel.basicPublish(...)); // 스레드 A
executor.submit(() -> channel.basicPublish(...)); // 스레드 B
// 두 스레드의 프레임이 뒤섞이면 채널이 예외와 함께 닫히고,
// 그 채널로 발행 중이던 메시지는 전송 여부조차 불확실해진다.

// 올바른 코드 — 커넥션은 공유, 채널은 스레드/작업 단위로
executor.submit(() -> {
    try (Channel ch = connection.createChannel()) { // 채널은 싸다. 매번 열어도 된다
        ch.basicPublish(...);
    }
});
```

## 2. 메시지가 흐르는 경로를 단계로 따라가기

### 2-1. 발행에서 삭제까지

한 건의 메시지가 겪는 일을 시간순으로 따라가면 이렇다. 각 단계마다 실패할 수 있고, 그 실패가 무엇을 뜻하는지가 핵심이다.

```
① 프로듀서가 채널에서 publish(exchange="order.events",
                             routingKey="payment.failed", body=...)
        |
        v
② exchange가 바인딩 목록을 훑어 라우팅 키와 대조
        |
        +-- 매칭된 큐가 0개 --> 메시지 폐기 (기본 동작. 2-3에서 다룸)
        |
        v
③ 매칭된 각 큐에 메시지를 "한 통씩" 넣는다
   (큐가 3개 매칭되면 사본 3개. 브로커 내부적으로는 본문을 공유하지만,
    소비 관점에서는 각 큐가 독립된 한 통을 갖는다)
        |
        v
④ 큐가 컨슈머에게 push (prefetch 한도 안에서)
        |
        v
⑤ 컨슈머가 처리 후 ack
        |
        +-- ack        --> 큐에서 삭제. 끝.
        +-- nack/reject --> requeue=true면 큐로 복귀, false면 폐기 또는 DLX로
        +-- 응답 없이 커넥션 끊김 --> 큐로 자동 복귀 (redelivered 플래그가 붙는다)
```

③번의 "큐가 3개면 사본 3개"가 Kafka와 크게 다른 지점이다. Kafka는 데이터를 한 벌만 저장하고 컨슈머 그룹마다 오프셋(읽은 위치를 가리키는 숫자)만 따로 들고 있다. RabbitMQ는 큐마다 실제로 메시지가 들어가므로, 소비자가 늘어나면 브로커가 안고 있는 메시지 총량도 늘어난다. **소비자 10개면 적체도 10배로 쌓인다**는 뜻이라 용량 산정에서 반드시 고려해야 한다.

⑤번의 마지막 줄도 중요하다. **컨슈머 프로세스가 죽으면 ack 안 된 메시지는 자동으로 큐로 돌아온다.** 이것이 RabbitMQ의 기본 안전망이며, `redelivered=true` 플래그가 붙어 돌아오므로 컨슈머는 "이건 이전에 한 번 받았던 것"이라는 힌트를 얻는다. 다만 그 힌트는 힌트일 뿐이다 — 이전 시도가 어디까지 진행됐는지는 알려주지 않으므로, 중복 처리 방지는 여전히 애플리케이션의 몫이다.

### 2-2. 같은 큐에 컨슈머가 여럿이면 — 경쟁 소비자

큐 하나에 컨슈머 여러 대를 붙이면 메시지는 **나눠서** 배달된다. 같은 메시지가 두 컨슈머에게 가지 않는다. 이 구조를 경쟁 소비자(competing consumers) 패턴이라고 부르며, 워커를 늘려 처리량을 올리는 기본 수단이다.

```
                       +--> [워커 1]  (메시지 1, 4, 7 ...)
[주문 큐] --- push ---> +--> [워커 2]  (메시지 2, 5, 8 ...)
                       +--> [워커 3]  (메시지 3, 6, 9 ...)
```

Kafka의 컨슈머 그룹과 목적은 같지만 **제약이 정반대**다. Kafka는 파티션 수가 컨슈머 수의 상한이라 파티션 3개인 토픽에 컨슈머 4대를 띄우면 한 대는 논다. RabbitMQ에는 그런 상한이 없다 — **큐 하나에 컨슈머 100대를 붙여도 모두 일한다.** 워커를 늘리는 것만으로 처리량이 선형에 가깝게 늘어나는 것이 RabbitMQ의 강점이다.

대신 대가가 있다. 컨슈머가 여러 대면 **처리 순서가 보장되지 않는다.** 큐에서 나가는 순서는 FIFO여도, 워커 3대가 각자 다른 속도로 처리하므로 완료 순서는 뒤섞인다. 순서 이야기는 `30-rabbitmq-message-ordering.md`에서 따로 다룬다.

### 2-3. 갈 곳 없는 메시지 — 조용한 유실의 진원지

이제 이 질문의 승부처다. **어느 바인딩에도 매칭되지 않은 메시지는 브로커가 그냥 버린다.** 예외도, 로그도, 알림도 없다.

더 나쁜 것은 **프로듀서 입장에서는 발행이 성공으로 보인다**는 점이다. publisher confirms(발행 확인)를 켜도 마찬가지다. confirm은 "브로커가 메시지를 받아 라우팅 처리를 마쳤다"는 뜻이지 "어떤 큐에 들어갔다"는 뜻이 아니기 때문이다. 라우팅 대상이 0개여도 브로커는 할 일을 다 한 것이므로 정상 confirm을 돌려준다.

그래서 이런 장애가 만들어진다.

```
라우팅 키 오타:  "payment.faild"  (바인딩은 "payment.failed")
    -> exchange에서 매칭 0개
    -> 메시지 폐기
    -> 프로듀서는 정상 발행 로그를 남김
    -> 컨슈머 큐는 비어 있고 에러도 없음
    -> "알림이 안 갔어요" 리포트가 며칠 뒤에 올라옴
```

막는 방법은 둘이다.

**첫째, `mandatory` 플래그 + return 콜백.** 발행 시 mandatory를 켜면, 라우팅 대상이 없는 메시지를 브로커가 버리지 않고 **프로듀서에게 되돌려준다.** 프로듀서는 return 콜백에서 이를 받아 로그·알람·별도 저장을 할 수 있다.

```java
// 잘못된 코드 — 발행하고 끝. 라우팅 실패가 보이지 않는다
rabbitTemplate.convertAndSend("order.events", "payment.faild", event);

// 올바른 코드 — 갈 곳 없는 메시지를 되받아 처리한다
@Bean
RabbitTemplate rabbitTemplate(ConnectionFactory cf) {
    RabbitTemplate t = new RabbitTemplate(cf);
    t.setMandatory(true); // 라우팅 실패 시 폐기하지 말고 되돌려 달라는 요청
    t.setReturnsCallback(returned -> {
        // 여기 들어왔다는 것 자체가 설정 오류(오타/바인딩 누락)라는 신호다.
        // 조용히 넘기지 말고 알람으로 올린다.
        log.error("라우팅 실패: exchange={}, routingKey={}, reply={}",
                  returned.getExchange(), returned.getRoutingKey(), returned.getReplyText());
        unroutableStore.save(returned.getMessage()); // 재발행할 수 있게 보관
    });
    return t;
}
```

**둘째, Alternate Exchange(대체 익스체인지).** exchange를 선언할 때 `alternate-exchange` 인자를 주면, 라우팅에 실패한 메시지가 **버려지는 대신 그 대체 exchange로 넘어간다.** 보통 fanout 타입의 대체 exchange를 만들고 거기에 `unroutable` 큐를 하나 물려둔다.

```java
// exchange 선언 시 대체 목적지를 지정한다
@Bean
TopicExchange orderEvents() {
    return ExchangeBuilder.topicExchange("order.events")
            .durable(true)
            .alternate("order.events.unroutable") // 갈 곳 없으면 여기로
            .build();
}
// order.events.unroutable(fanout)에 큐를 하나 묶어두면,
// 라우팅 실패 메시지가 그 큐에 쌓인다. 큐 깊이 알람만 걸면
// 설정 오류를 배포 직후에 발견할 수 있다.
```

둘의 차이는 **누가 책임지느냐**다. mandatory는 프로듀서 애플리케이션이 되받아 처리하므로 프로듀서가 살아 있어야 하고 코드가 필요하다. alternate exchange는 브로커 설정만으로 동작하며 프로듀서가 죽어도 메시지가 남는다. **운영에서는 alternate exchange를 기본으로 깔고, 중요한 발행 경로에만 mandatory를 추가로 켜는 조합**이 안전하다. (가산점 포인트)

## 3. 실무 사례 — 무응답 장애 추적

### 3-1. 증상과 오진

신규 정산 서비스를 배포한 뒤 "정산 알림이 안 온다"는 리포트가 올라왔다고 하자. 흔한 오진 순서는 이렇다.

1. 컨슈머 로그를 본다 → 에러가 없다. 아예 아무것도 안 찍혀 있다.
2. 컨슈머가 안 떴나 확인한다 → 정상 기동, 큐에 연결됨.
3. 프로듀서 로그를 본다 → "이벤트 발행 완료" 가 정상적으로 찍혀 있다.
4. "그럼 브로커가 먹었네" 라며 브로커 로그를 뒤진다 → 아무것도 없다.

여기서 막히는 이유는 **라우팅 실패가 어디에도 기록되지 않기 때문**이다. 프로듀서는 성공했고, 컨슈머는 받은 게 없고, 브로커는 정상 동작했다. 세 곳 모두 정상이므로 로그 기반 추적이 통하지 않는다.

### 3-2. 확인 순서

이럴 때는 로그가 아니라 **브로커의 현재 상태**를 봐야 한다. 순서는 이렇다.

1. **큐가 존재하는가.** `rabbitmqctl list_queues name messages consumers` — 큐 자체가 없다면 컨슈머 쪽 선언이 실행되지 않았거나 vhost가 다르다.
2. **바인딩이 걸려 있는가.** `rabbitmqctl list_bindings` — 큐는 있는데 바인딩이 없으면 메시지는 절대 도달하지 않는다.
3. **바인딩 키와 프로듀서의 라우팅 키가 실제로 매칭되는가.** 관리 콘솔의 exchange 상세 화면에는 라우팅 키를 입력해 어느 큐로 갈지 시험해보는 기능이 있다. 눈으로 비교하는 것보다 이 시험이 빠르고 정확하다.
4. **exchange의 in/out 지표를 본다.** 관리 콘솔의 exchange 화면에서 들어온 메시지 수와 나간 메시지 수가 벌어져 있으면 그 차이가 곧 폐기된 양이다.

4번이 이 장애의 결정적 증거다. **들어온 것보다 나간 것이 적으면 그 차이만큼 버려졌다는 뜻**이고, 이 지표 하나로 "브로커까지는 왔고 라우팅에서 죽었다"가 확정된다.

### 3-3. 재발 방지

원인을 찾았다면 오타를 고치는 것으로 끝내지 말고 구조를 바꿔야 한다. 같은 실수는 반드시 다시 난다.

- **라우팅 키를 문자열 리터럴로 흩뿌리지 않는다.** 상수 클래스나 enum으로 모아 컴파일 타임에 오타가 걸리게 한다.
- **alternate exchange + unroutable 큐를 기본 인프라로 깐다.** 그리고 그 큐의 깊이가 0보다 커지면 알람이 울리게 한다. 그러면 다음 오타는 배포 5분 뒤에 발견된다.
- **큐·바인딩 선언을 컨슈머 애플리케이션 기동 시점에 코드로 수행한다.** Spring AMQP는 `Queue`, `Binding` 빈을 선언해두면 기동 시 자동으로 생성한다. 콘솔에서 수동으로 만든 바인딩은 클러스터를 재구축하는 순간 사라진다.

```java
// 큐와 바인딩을 코드로 선언 — 인프라가 재구축돼도 기동만 하면 복구된다
@Bean Queue settlementNotifyQueue() {
    return QueueBuilder.durable("settlement.notify")
            .deadLetterExchange("settlement.dlx") // 실패 경로도 같이 선언
            .build();
}
@Bean Binding settlementNotifyBinding(Queue settlementNotifyQueue, TopicExchange orderEvents) {
    return BindingBuilder.bind(settlementNotifyQueue)
            .to(orderEvents)
            .with(RoutingKeys.SETTLEMENT_COMPLETED); // 리터럴 대신 상수
}
```

## 4. 꼬리질문 대비 포인트

### "Exchange를 안 쓰고 큐에 바로 보낼 수는 없나요?"

AMQP에는 exchange를 거치지 않는 경로가 없다. 다만 **기본 익스체인지(default exchange)**라는 편법이 있다. 이름이 빈 문자열(`""`)인 direct 타입 exchange로, 브로커에 있는 **모든 큐가 자기 이름을 바인딩 키로 삼아 자동으로 바인딩되어 있다.**

그래서 `publish(exchange="", routingKey="my.queue")` 라고 쓰면 `my.queue`라는 이름의 큐로 바로 들어간다. 큐에 직접 보내는 것처럼 보이지만 실제로는 기본 exchange를 통과한 것이다.

간단한 작업 큐에는 편하지만, 프로듀서가 큐 이름을 직접 알아야 하므로 **프로듀서와 컨슈머가 강하게 묶인다.** 나중에 소비자를 하나 더 붙이려면 프로듀서 코드를 고쳐야 한다. 그래서 이벤트성 발행에는 쓰지 않고, 명시적인 exchange를 두는 것이 정석이다.

### "메시지가 여러 큐에 들어가면 브로커 메모리에 사본이 여러 개 생기나요?"

브로커는 메시지 본문을 내부적으로 공유해 저장하므로 본문이 그대로 N배가 되지는 않는다. 하지만 **큐마다 별도의 엔트리와 인덱스, 그리고 각자의 상태(전달됨/미확인)가 생긴다.** 그리고 결정적으로 **소비 진행이 큐마다 독립적**이라, 컨슈머 하나가 느리면 그 큐만 계속 쌓인다.

Kafka와의 차이를 이 문장으로 요약하면 좋다. **Kafka에서 느린 컨슈머는 자기 오프셋만 뒤처지지만, RabbitMQ에서 느린 컨슈머는 브로커에 실제 메시지를 쌓는다.** 그래서 RabbitMQ 클러스터의 용량 산정은 "이벤트 발생량 × 소비자 수 × 최악의 적체 시간"으로 잡아야 한다.

### "큐 이름과 라우팅 키를 어떻게 설계하는 게 좋나요?" (시니어 변별 포인트)

원칙 하나로 정리된다. **라우팅 키는 "무슨 일이 일어났는가"(사실), 큐 이름은 "누가 무엇을 하는가"(용도)로 짓는다.**

```
라우팅 키:  order.payment.failed        <- 도메인.대상.사건 (과거형)
큐 이름:    notification.payment-failed  <- 소비 주체.용도
           settlement.payment-failed
```

라우팅 키를 `notification.send` 처럼 **명령형**으로 지으면 그 순간 프로듀서가 소비자를 알게 된다. 알림 말고 정산도 그 이벤트를 원하게 되는 날, 라우팅 키가 의미와 맞지 않게 되고 결국 프로듀서를 고치게 된다. **사실을 발행하고 해석은 소비자에게 맡기는 것**이 이벤트 기반 설계의 기본이며, 라우팅 키 작명이 그 원칙을 지키는 첫 관문이다.

계층 순서도 중요하다. topic exchange의 패턴 매칭은 앞에서부터 단어를 맞추므로, **넓은 범주를 앞에 두어야 `order.#` 같은 유용한 구독이 가능해진다.** `failed.payment.order` 처럼 뒤집으면 "주문 도메인 전체 구독"을 표현할 방법이 없어진다.

### "vhost는 언제 나누나요?"

기준은 **권한과 장애 격리를 함께 나눠야 하는가**다. 팀이 다르고 권한을 분리해야 하면 vhost를 나눈다. 다만 vhost는 논리적 격리일 뿐 **자원 격리가 아니라는 점**을 알아야 한다. 같은 클러스터를 쓰므로 한 vhost가 메모리를 다 쓰면 브로커 전역 alarm이 걸려 **다른 vhost의 프로듀서까지 멈춘다.**

즉 "테스트 트래픽 때문에 운영이 죽는 것"을 막고 싶다면 vhost 분리로는 부족하고 클러스터를 나눠야 한다. 이 구분을 말할 수 있으면 격리 수준을 정확히 이해하고 있는 것이다.

### "Kafka의 토픽은 RabbitMQ의 무엇에 대응하나요?"

정확히 대응하는 것이 없다는 것이 정답이고, 굳이 나누면 **역할이 둘로 쪼개진다.**

| Kafka 토픽의 역할 | RabbitMQ의 대응 |
|---|---|
| 프로듀서가 지정하는 발행 대상 | Exchange |
| 메시지가 저장되고 컨슈머가 읽는 곳 | Queue |
| 소비자 그룹별 독립 소비 | 소비자마다 별도 큐 + 바인딩 |

이 표가 두 도구의 성격 차이를 압축한다. Kafka는 **저장소 하나를 여러 소비자가 각자의 위치로 읽는** 모델이고, RabbitMQ는 **소비자마다 자기 우편함을 갖는** 모델이다. 그래서 Kafka는 소비자가 늘어도 저장량이 그대로지만 RabbitMQ는 늘어난다. 반대로 RabbitMQ는 소비자마다 다른 필터(바인딩 키)를 걸 수 있지만 Kafka는 전부 받아 컨슈머가 걸러야 한다.

## 한 줄 요약

RabbitMQ는 **exchange(배분)와 queue(저장)를 분리하고 binding으로 잇는** 구조라서 프로듀서를 건드리지 않고 소비자를 늘릴 수 있지만, 그 대가로 **어느 바인딩에도 걸리지 않은 메시지가 조용히 사라지므로** alternate exchange와 mandatory + return 콜백으로 "갈 곳 없는 메시지"를 반드시 붙잡아 두어야 한다.
