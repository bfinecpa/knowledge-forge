# 컨슈머 한 대의 처리량 올리기 — 병렬화가 오프셋 커밋의 전제를 깨는 지점

> 핵심 관전 포인트: **파티션 증설은 키 순서를 깨고 되돌리기 어려운 카드라,
> 그 전에 컨슈머 한 대를 최적화한다. 방법은 두 축 — ① 배치 폴링에 맞춰
> 처리도 배치로(건별 I/O를 묶기), ② 폴링 스레드와 처리 스레드를 분리하는
> 내부 병렬화. 그런데 병렬화하는 순간 "poll한 순서 = 처리 완료 순서"라는
> 오프셋 커밋의 전제가 깨진다. 오프셋 커밋은 "이 지점 이전은 전부
> 처리됐다"는 선언이므로, 완료 순서가 뒤섞인 상태에서 최신 오프셋을
> 커밋하면 아직 처리 중이던 메시지가 유실된다. 해법은 자동 커밋을 끄고
> 파티션별로 "연속으로 완료된 구간의 끝"까지만 수동 커밋하는 것 —
> 처리량과 전달 보장의 트레이드오프를 컨슈머 구현 레벨에서 다루는 게
> 이 질문의 본론이다.**

---

## 0. 질문 + 의도

**질문**: "파티션을 늘리지 않고 컨슈머 한 대의 처리량을 높이는 방법은?
(배치 폴링, 컨슈머 내부 병렬화) 이때 오프셋 커밋은 어떻게 다뤄야 하나요?"

**출제 의도**: 배치 폴링·내부 병렬화로 처리량을 올릴 때 커밋 시점이
어긋나면 유실이나 중복이 생긴다. "병렬화가 전달 보장을 깨는 지점"을
인식하는지 — 처리량과 정확성의 트레이드오프를 컨슈머 구현 레벨에서
다뤄봤는지 확인한다.

## 1. 왜 파티션 증설이 첫 카드가 아닌가

"처리가 밀리면 파티션 늘리고 컨슈머 늘리면 되지"가 직관이지만,
파티션 증설은 공짜가 아니다:

- **키 순서가 깨진다.** 파티션 수가 바뀌면 `hash(key) % 파티션수`의
  결과가 달라져, 같은 키의 메시지가 증설 전후로 다른 파티션에 실린다.
  "사용자별 순서 보장"이 그 경계에서 무너진다.
- **줄일 수 없다.** Kafka는 파티션 수를 늘릴 수만 있고 줄일 수 없다 —
  사실상 비가역 결정이다.
- **브로커 부담이 늘어난다.** 파티션마다 메타데이터·복제·파일 핸들이
  붙는다.

그래서 순서가 있다: **먼저 컨슈머 한 대가 낼 수 있는 처리량을
끝까지 끌어올리고, 그래도 부족할 때 파티션 증설을 검토한다.**
그리고 그 전에 확인할 것 — 병목이 정말 컨슈머인가? 처리 시간의
대부분이 다운스트림(DB insert, 외부 API)이라면 컨슈머를 아무리
병렬화해도 다운스트림이 상한이다.

## 2. 축 ① 배치 폴링 — 가져오는 건 이미 배치, 문제는 처리다

오해부터 바로잡으면: `poll()`은 원래 한 건씩이 아니라 **한 번에 여러
건(최대 `max.poll.records`)을 가져온다.** 배치 폴링 자체는 기본
동작이다. 처리량이 안 나오는 진짜 원인은 대부분 "배치로 받아놓고
**한 건씩 처리**"하는 쪽이다.

```java
// ❌ before: 배치로 받아서 건별로 I/O — 500건이면 DB 왕복 500번
ConsumerRecords<String, OrderEvent> records = consumer.poll(timeout);
for (ConsumerRecord<String, OrderEvent> record : records) {
    orderRepository.save(toEntity(record.value())); // 건별 insert
}
consumer.commitSync();
```

```java
// ✅ after: 처리도 배치로 — DB 왕복 1번 (JDBC batch / bulk insert)
ConsumerRecords<String, OrderEvent> records = consumer.poll(timeout);
List<OrderEntity> entities = new ArrayList<>();
for (ConsumerRecord<String, OrderEvent> record : records) {
    entities.add(toEntity(record.value()));
}
orderRepository.batchInsert(entities); // 묶음 처리
consumer.commitSync(); // 배치 전체 성공 후에만 커밋
```

배치 처리에서의 커밋 규칙은 단순하다: **배치 전체가 성공한 뒤에만
커밋한다.** 중간까지 처리하고 커밋하면, 커밋 지점 이후의 실패분을
어디까지 처리했는지 아무도 모르게 된다.

두 가지 따라오는 이슈:

- **부분 실패 = 중복 재처리.** 배치 중 한 건이 실패해 커밋을 안 하면,
  재시작 시 배치 전체를 다시 받는다 — 이미 성공했던 건들이 중복
  처리된다. 그래서 배치 처리는 **멱등 컨슈머**(처리 이력 기반 중복
  제거)와 세트다.
- **배치를 키울수록 리밸런싱 위험.** `max.poll.records`를 키우면 한
  배치의 처리 시간이 길어지고, `max.poll.interval.ms` 안에 다음
  poll()을 못 하면 브로커가 "이 컨슈머 죽었다"고 판단해 리밸런싱을
  일으킨다. 배치 크기는 "처리 시간 × 여유 배수 < max.poll.interval.ms"
  안에서 잡는다.

폴링 효율 쪽 다이얼로는 `fetch.min.bytes`/`fetch.max.wait.ms`(브로커가
데이터를 모아서 응답하게 해 네트워크 왕복을 줄임)도 있다 — 처리량과
지연의 트레이드오프 다이얼이라는 것까지 언급하면 가산점.

## 3. 축 ② 컨슈머 내부 병렬화 — 폴링 스레드와 워커 풀의 분리

배치로 묶어도 처리 자체가 느리면(외부 API 호출 등 I/O 대기가 길면)
**한 컨슈머 안에서 처리를 병렬화**한다. 전제 지식: `KafkaConsumer`
객체는 **스레드 세이프하지 않다.** 여러 스레드가 같은 consumer로
poll() 하면 안 되고, 구조는 이렇게 갈라진다:

```
[폴링 스레드 1개] --poll()--> 레코드들
        |
        +--> [워커 풀 N개] 가 나눠서 처리
        |
        +--> 완료 오프셋 취합 --> 폴링 스레드가 커밋
```

```java
// 뼈대: 폴링은 한 스레드, 처리는 워커 풀
while (running) {
    ConsumerRecords<String, Event> records = consumer.poll(timeout);
    for (ConsumerRecord<String, Event> record : records) {
        // 키 해시로 워커를 고정 → 같은 키는 같은 워커 = 키 순서 유지
        int worker = Math.abs(record.key().hashCode()) % workerCount;
        workers[worker].submit(() -> process(record));
    }
    // 커밋은 여기서 "안전한 지점"까지만 — 4절에서 설명
}
```

핵심 설계 포인트 두 가지:

- **키 순서를 지키려면 키 → 워커 고정 라우팅.** 무작위로 워커 풀에
  뿌리면 같은 사용자의 이벤트 두 건이 다른 스레드에서 역전될 수 있다.
  파티션이 키 순서를 지켜줬듯, 컨슈머 안에서는 "키 해시 % 워커 수"로
  같은 키를 같은 워커에 보내 순서를 유지한다.
- **spring-kafka의 `concurrency` 설정과는 다른 층위다.** concurrency는
  "컨슈머 인스턴스를 여러 개 띄우는 것"이라 파티션 수가 상한이다
  (파티션보다 많은 컨슈머는 논다). 여기서 말하는 내부 병렬화는 **파티션
  1개를 여러 스레드가 나눠 처리**하는 것 — 파티션 수의 상한을 넘어서는
  방법이고, 그래서 오프셋 커밋 문제가 새로 생긴다. Confluent의
  parallel-consumer 같은 라이브러리가 이 패턴(키 단위 병렬화 + 안전한
  오프셋 관리)을 구현해 둔 것까지 알면 가산점.

## 4. 오프셋 커밋 — 병렬화가 깨뜨리는 전제와 복구법 (이 질문의 본론)

오프셋 커밋의 의미부터: 커밋은 "몇 번을 처리했다"가 아니라 **"이 오프셋
이전은 전부 처리됐으니, 재시작하면 여기부터 읽어라"**라는 선언이다.
순차 처리에서는 "마지막으로 처리한 오프셋 = 그 이전 전부 완료"가
자동으로 성립했다. **병렬화는 이 전제를 깬다.**

### 사고 시나리오

파티션에서 오프셋 100, 101, 102를 poll해서 워커 3개에 뿌렸다.
101, 102는 끝났는데 100이 아직 처리 중이다. 이때:

- **"가장 최근에 완료된 102를 커밋"하면** → 컨슈머가 죽고 재시작하는
  순간 103부터 읽는다. **100은 처리도 안 됐는데 건너뛰어진다 — 유실.**
- **자동 커밋(enable.auto.commit=true)을 켜둔 채라면** 더 나쁘다.
  자동 커밋은 poll() 호출 시점에 "직전 poll로 가져간 것들은 처리됐겠지"
  라고 가정하고 커밋한다. 워커에 던져놓고 바로 다음 poll을 도는 구조에서는
  **처리가 시작도 안 된 메시지가 커밋된다.**

### 해법: 연속 완료 구간까지만 커밋

```java
// ❌ before: 완료된 것 중 최대 오프셋을 커밋 — 구멍(100)을 건너뛴다
completedOffsets = {101, 102};   // 100은 아직 처리 중
consumer.commitSync(Map.of(partition, new OffsetAndMetadata(103)));
// 재시작하면 100이 영원히 유실된다

// ✅ after: 파티션별 완료 오프셋을 취합해 "연속 구간의 끝"까지만 커밋
// 완료: {101, 102}, 미완료: {100} → 커밋할 수 있는 지점 없음 (대기)
// 100 완료 → 연속 구간이 100~102 → OffsetAndMetadata(103) 커밋
```

구현 골자는 파티션별 오프셋 트래커다: 워커가 처리를 마치면 완료
오프셋을 보고하고, 폴링 스레드는 **낮은 오프셋부터 끊김 없이 이어진
구간의 끝 + 1**만 커밋한다(커밋 오프셋은 "다음에 읽을 위치"이므로 +1).
중간에 구멍이 있으면 그 앞에서 멈춘다.

이 구조의 필연적 따름 정리 — **실패한 메시지를 방치하면 커밋이 영원히
멈춘다.** 오프셋 100이 계속 실패 상태면 101 이후가 아무리 완료돼도
커밋 지점이 전진하지 못하고, 컨슈머가 재시작하는 순간 전부 재처리된다.
그래서 재시도 상한 + DLQ(실패 메시지를 별도 토픽으로 격리하고 "처리
완료"로 마킹해 커밋을 전진시킴)가 병렬 컨슈머의 필수 부품이 된다.
poison pill 하나가 파티션을 막는 문제의 병렬화 버전인 셈이다.

### 그래도 남는 것: at-least-once + 멱등

연속 구간 커밋을 완벽히 해도, "처리 완료 ~ 커밋 사이"에 죽으면 그
구간은 재처리된다 — **유실은 막아도 중복은 남는다(at-least-once).**
그래서 최종 방어선은 멱등 컨슈머다. "병렬화 → 수동 커밋 → 연속 구간
커밋 → 그래도 중복은 남으니 멱등 처리"까지 한 호흡으로 말하면
이 질문은 끝난다.

## 5. 꼬리질문 대비 포인트

### "자동 커밋을 켠 채로 워커 풀에 처리를 넘기면 정확히 무슨 일이 생기나?"

자동 커밋은 poll() 호출 시점에 이전 poll로 가져간 오프셋을 커밋한다 —
"가져갔으면 처리됐겠지"라는 가정이다. 워커에 submit만 하고 다음 poll을
도는 구조에서는 처리가 끝나지 않은(시작도 안 했을 수 있는) 메시지가
커밋되고, 그 상태에서 컨슈머가 죽으면 재시작 시 그 메시지들을
건너뛴다 — 유실이다. 내부 병렬화의 첫 번째 전제는
`enable.auto.commit=false`.

### "워커 풀로 병렬화하면 키 순서는 어떻게 지키나?"

키 해시로 워커를 고정한다(`hash(key) % 워커 수`). 같은 키의 메시지는
항상 같은 워커의 큐에 들어가 순차 처리되므로 키 내부 순서가 유지되고,
서로 다른 키끼리만 병렬이 된다. 파티션이 브로커 레벨에서 하던
"키 단위 순서 보장 + 키 간 병렬"을 컨슈머 내부에서 한 단계 더
재현하는 것이다.

### "배치 크기를 키웠더니 리밸런싱이 반복된다 — 왜?"

한 배치의 처리 시간이 `max.poll.interval.ms`를 넘으면 브로커
코디네이터가 컨슈머를 그룹에서 제외하고 리밸런싱을 일으킨다. 재조인한
컨슈머가 또 큰 배치를 물고 또 초과하면 리밸런싱이 무한 반복된다.
해법은 배치 축소(`max.poll.records` 감소), 처리 최적화, 또는
`max.poll.interval.ms` 상향 — 단 상향은 진짜 죽은 컨슈머의 감지도
늦춘다는 트레이드오프를 함께 말해야 한다.

### "commitSync와 commitAsync는 어떻게 골라 쓰나?"

commitSync는 커밋 완료(또는 실패)를 확인할 때까지 블로킹하고 재시도도
해주지만 그만큼 처리 루프를 세운다. commitAsync는 논블로킹이라 루프
처리량을 지키지만 실패 시 자동 재시도가 없다(순서 역전 위험 때문).
실무 관용구는 "평상시 루프에서는 commitAsync, 종료/리밸런스 직전에는
commitSync로 마지막 오프셋을 확실히 박는" 조합이다. 커밋은
at-least-once 전제에서 '중복 범위를 줄이는 장치'이지 유실/중복을
없애는 장치가 아니라는 것도 같이.

### "그렇게까지 했는데도 안 따라잡으면? 파티션 증설 판단 기준은?" (시니어 변별 포인트)

먼저 병목 위치를 확정한다 — 컨슈머 CPU가 상한이면 내부 병렬화의 여지가
남았는지, 다운스트림(DB·외부 API)이 상한이면 파티션을 늘려도 다운스트림
부하만 커질 뿐 처리량은 안 는다(이 경우 다운스트림 증설·배치화가 먼저).
진짜 컨슈머 인스턴스 수의 상한(=파티션 수)에 막힌 것이 확인되면 그때
증설하되, 키 재배치로 증설 시점 전후의 키 순서가 깨진다는 것과 줄일 수
없다는 비가역성을 알고 실행한다 — 순서에 민감한 토픽이면 트래픽이 빠진
시간대 + 컨슈머 드레인 후 증설 같은 운영 절차까지 언급하면 시니어 답변.

## 한 줄 요약

파티션 증설은 비가역이라 컨슈머 한 대를 먼저 쥐어짜는 게 순서고, 그
방법은 배치 처리(건별 I/O를 묶기)와 폴링/처리 스레드 분리(키 고정
라우팅으로 순서 유지)인데 — 병렬화하는 순간 "커밋 = 이 이전은 전부
처리됨"이라는 전제가 깨지므로, 자동 커밋을 끄고 연속 완료 구간까지만
수동 커밋하며, 그래도 남는 중복은 멱등 컨슈머로 받는 것까지가 한
세트다.
