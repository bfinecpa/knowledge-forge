# 컨슈머 한 대의 처리량 올리기 — 병렬화가 오프셋 커밋의 전제를 깨는 지점

> 핵심 관전 포인트: **파티션 증설은 키 순서를 깨고 되돌리기 어려운 카드라, 그 전에 컨슈머 한 대를 최적화한다. 방법은 두 축 — ① 배치 폴링에 맞춰 처리도 배치로(건별 I/O를 묶기), ② 폴링 스레드와 처리 스레드를 분리하는 내부 병렬화. 그런데 병렬화하는 순간 "poll한 순서 = 처리 완료 순서"라는 오프셋 커밋의 전제가 깨진다. 오프셋 커밋은 "이 지점 이전은 전부 처리됐다"는 선언이므로, 완료 순서가 뒤섞인 상태에서 최신 오프셋을 커밋하면 아직 처리 중이던 메시지가 유실된다. 해법은 자동 커밋을 끄고 파티션별로 "연속으로 완료된 구간의 끝"까지만 수동 커밋하는 것 — 처리량과 전달 보장의 트레이드오프를 컨슈머 구현 레벨에서 다루는 게 이 질문의 본론이다.**

---

## 0. 질문 + 의도

**질문**: "파티션을 늘리지 않고 컨슈머 한 대의 처리량을 높이는 방법은? (배치 폴링, 컨슈머 내부 병렬화) 이때 오프셋 커밋은 어떻게 다뤄야 하나요?"

**출제 의도**: 배치 폴링·내부 병렬화로 처리량을 올릴 때 커밋 시점이 어긋나면 유실이나 중복이 생긴다. "병렬화가 전달 보장을 깨는 지점"을 인식하는지 — 처리량과 정확성의 트레이드오프를 컨슈머 구현 레벨에서 다뤄봤는지 확인한다.

## 1. 왜 파티션 증설이 첫 카드가 아닌가

"처리가 밀리면 파티션 늘리고 컨슈머 늘리면 되지"가 가장 먼저 떠오르는 직관이다. 실제로 컨슈머 그룹에서 **파티션 하나는 최대 한 컨슈머에게만 할당**되므로, 컨슈머 대수를 늘리려면 파티션이 그만큼 있어야 한다는 것도 맞다.

문제는 파티션 증설이 공짜가 아니라는 점이다. 대가가 셋이다.

**키 순서가 깨진다.** Kafka는 키가 있는 메시지의 목적지를 `해시(키) % 파티션 수`로 정한다. 파티션 수가 바뀌면 **분모가 바뀌므로 같은 키의 목적지가 달라진다.** 그런데 증설이 기존 데이터를 재배치해 주지는 않으므로, 같은 키의 옛 메시지는 옛 파티션에 남고 새 메시지는 새 파티션으로 간다. 두 파티션은 서로 다른 컨슈머가 읽으니 앞뒤 관계가 정의되지 않는다. "사용자별 순서 보장"이 증설 경계에서 영구적인 구멍을 갖게 된다.

**줄일 수 없다.** Kafka는 파티션 수 축소를 아예 지원하지 않는다. 올리는 API는 있고 내리는 API는 없다. 되돌리려면 새 토픽을 만들어 프로듀서·컨슈머를 전부 옮기는 마이그레이션밖에 없다 — 사실상 비가역 결정이다.

**브로커 부담이 늘어난다.** 파티션마다 로그 세그먼트 파일과 인덱스 파일이 열려 있고, 복제 팩터만큼 복제 스트림이 돌고, 브로커 장애 시 리더 선출 대상이 된다. 놀고 있는 파티션도 관리 비용은 낸다. (상세: `13-partition-count-sizing.md`)

그래서 순서가 있다. **먼저 컨슈머 한 대가 낼 수 있는 처리량을 끝까지 끌어올리고, 그래도 부족할 때 파티션 증설을 검토한다.** 컨슈머 최적화는 되돌릴 수 있고 파티션 증설은 되돌릴 수 없으니, 되돌릴 수 있는 카드를 먼저 쓰는 것이다.

그리고 그 전에 하나 더 확인해야 한다. **병목이 정말 컨슈머인가?** 처리 시간의 대부분이 다운스트림(DB INSERT, 외부 API 호출)에서 나온다면, 컨슈머를 아무리 병렬화해도 다운스트림이 상한이다. 컨슈머 스레드를 10배로 늘려 DB에 요청을 10배로 쏘면 DB가 먼저 넘어질 뿐이다. 이 경우엔 다운스트림 증설이나 배치화가 먼저다.

## 2. 두 축 — 배치 처리와 내부 병렬화

### 2-1. 축 하나 — 가져오는 건 이미 배치, 문제는 처리다

오해부터 바로잡자. `poll()`은 원래 메시지를 한 건씩 가져오지 않는다. **한 번 호출하면 최대 `max.poll.records`개까지 한꺼번에 가져온다.** 즉 "배치 폴링"은 별도로 켜야 하는 기능이 아니라 기본 동작이다.

그렇다면 처리량이 안 나오는 진짜 원인은 어디인가. 대부분 **배치로 받아 놓고 for 루프를 돌며 한 건씩 처리하는** 쪽이다. 네트워크로 가져오는 구간은 이미 묶여 있는데, 처리 구간에서 다시 낱개로 풀어 버리는 것이다.

```java
// Before: 배치로 받아서 건별로 I/O를 친다
ConsumerRecords<String, OrderEvent> records = consumer.poll(timeout);
for (ConsumerRecord<String, OrderEvent> record : records) {
    // save()가 한 번 불릴 때마다 INSERT 한 문장이 나가고
    // 그때마다 애플리케이션 -> DB -> 애플리케이션 왕복이 한 번 발생한다.
    // 500건을 받았다면 왕복 500번이다.
    orderRepository.save(toEntity(record.value()));
}
consumer.commitSync();
```

왕복 한 번의 비용은 SQL 실행 시간만이 아니다. 네트워크 지연, 파싱, 트랜잭션 오버헤드가 매번 붙는다. 한 번에 1ms라 쳐도 500번이면 500ms다. 이 구간을 줄이는 것이 배치 처리다.

```java
// After: 처리도 배치로 묶는다 — 왕복 500번이 1번이 된다
ConsumerRecords<String, OrderEvent> records = consumer.poll(timeout);

List<OrderEntity> entities = new ArrayList<>();
for (ConsumerRecord<String, OrderEvent> record : records) {
    entities.add(toEntity(record.value()));   // 여기서는 DB를 건드리지 않는다
}

// 모아 둔 것을 한 문장으로 보낸다. 왕복이 1회로 줄어든다.
orderRepository.batchInsert(entities);

consumer.commitSync();  // 배치 전체가 성공한 뒤에만 커밋한다
```

`batchInsert`가 실제로 만드는 SQL은 PostgreSQL 기준으로 이렇게 생겼다.

```sql
-- 다건 INSERT: VALUES 절에 여러 행을 이어 붙여 한 문장으로 보낸다
INSERT INTO orders (order_id, user_id, amount, created_at)
VALUES (1001, 88, 24000, now()),
       (1002, 91, 15000, now()),
       (1003, 88,  8000, now());
```

중복 재처리까지 감안한다면(뒤에서 볼 at-least-once 때문에 반드시 감안해야 한다) `ON CONFLICT`를 붙인 UPSERT로 쓴다.

```sql
-- ON CONFLICT: 유니크 제약에 걸리는 행은 조용히 넘어간다.
-- 같은 배치가 두 번 처리돼도 결과가 같아지므로 멱등해진다.
INSERT INTO orders (order_id, user_id, amount, created_at)
VALUES (1001, 88, 24000, now()),
       (1002, 91, 15000, now())
ON CONFLICT (order_id) DO NOTHING;
```

왕복 횟수를 세어 보면 차이가 분명하다.

```text
poll() 한 번에 500건을 받았을 때

  건별 INSERT   : DB 왕복 500회
  다건 INSERT 1문장 : DB 왕복 1회        -> 500배 감소
  100행씩 잘라 5문장 : DB 왕복 5회        -> 100배 감소
```

실무에서는 VALUES 절이 지나치게 길어지면 파싱 비용과 메모리가 부담되므로 100~1,000행 단위로 잘라 보내는 경우가 많다. 그래도 500회가 5회가 되는 것이므로 효과는 충분하다.

**배치 처리에서의 커밋 규칙은 단순하다. 배치 전체가 성공한 뒤에만 커밋한다.** 중간까지 처리하고 커밋해 버리면, 나중에 실패했을 때 "어디까지 처리됐는지"를 아무도 모르게 된다.

여기서 따라오는 이슈가 둘 있다.

**부분 실패는 중복 재처리를 부른다.** 배치 500건 중 한 건이 실패해서 커밋을 안 하면, 재시작 시 **배치 전체를 다시 받는다.** 이미 성공했던 499건이 다시 처리된다는 뜻이다. 그래서 배치 처리는 **멱등 컨슈머**(같은 메시지를 여러 번 처리해도 결과가 한 번 처리한 것과 같아지는 컨슈머)와 세트다. 위의 `ON CONFLICT DO NOTHING`이 바로 그 장치다.

**배치를 키울수록 리밸런싱 위험이 커진다.** `max.poll.records`를 키우면 한 배치의 처리 시간이 길어진다. 그런데 Kafka는 컨슈머가 살아 있는지를 **다음 `poll()`이 제때 오는지**로 판단한다. 처리에 오래 걸려 `max.poll.interval.ms` 안에 다음 poll을 못 하면 브로커가 "이 컨슈머 죽었다"고 보고 그룹에서 빼낸 뒤 리밸런싱을 일으킨다. 배치 크기는 `한 배치 처리 시간 × 여유 배수 < max.poll.interval.ms`를 만족하는 범위에서 잡는다.

폴링 효율 쪽 다이얼로는 `fetch.min.bytes`와 `fetch.max.wait.ms`도 있다. 브로커가 요청받은 즉시 응답하지 않고 **데이터가 지정한 크기만큼 모일 때까지(또는 지정한 시간까지) 기다렸다가 한 번에 응답**하게 해서 네트워크 왕복을 줄이는 설정이다. 데이터를 모으는 만큼 지연은 늘어나므로, 처리량과 지연의 트레이드오프 다이얼이라는 점까지 언급하면 가산점.

### 2-2. 축 둘 — 폴링 스레드와 워커 풀의 분리

배치로 묶어도 처리 자체가 느린 경우가 있다. 외부 API 호출처럼 **CPU는 놀고 I/O 대기만 긴** 작업이 대표적이다. 이럴 때는 한 컨슈머 안에서 처리를 병렬화한다.

전제 지식이 하나 필요하다. **`KafkaConsumer` 객체는 스레드 세이프하지 않다.** 여러 스레드가 같은 consumer 인스턴스로 `poll()`을 호출하면 안 된다(예외적으로 `wakeup()`만 다른 스레드에서 호출할 수 있다). 그래서 구조가 이렇게 갈라진다.

```text
[폴링 스레드 1개]  --poll()-->  레코드 500건
        |
        |  (consumer를 만지는 것은 이 스레드뿐)
        |
        +--> [워커 풀 N개] 가 나눠서 처리
        |
        +--> 워커들이 "몇 번 오프셋 끝냈다"고 보고
        |
        +--> 폴링 스레드가 그 보고를 취합해 커밋
```

**consumer를 만지는 것은 폴링 스레드 하나뿐**이고, 워커는 처리만 하고 결과를 보고한다. 커밋도 반드시 폴링 스레드가 한다.

```java
// 뼈대: 폴링은 한 스레드, 처리는 워커 풀
while (running) {
    ConsumerRecords<String, Event> records = consumer.poll(timeout);

    for (ConsumerRecord<String, Event> record : records) {
        // 키 해시로 워커를 고정한다. 같은 키는 언제나 같은 워커의 큐로 들어가
        // 그 워커 안에서 순차 처리되므로 키 내부 순서가 유지된다.
        int worker = Math.abs(record.key().hashCode()) % workerCount;
        workers[worker].submit(() -> process(record));
    }

    // 커밋은 여기서 "안전한 지점"까지만 한다 — 3절의 본론이다.
}
```

이 구조에서 반드시 짚어야 할 설계 포인트가 셋이다.

**(1) 키 순서를 지키려면 키를 워커에 고정 배정한다.** 레코드를 워커 풀에 아무렇게나 던지면 같은 사용자의 이벤트 두 건이 서로 다른 스레드에서 처리되어 역전될 수 있다. "결제완료"보다 "배송시작"이 먼저 끝나 버리는 식이다.

그래서 `키 해시 % 워커 수`로 워커를 고정한다. 같은 키는 언제나 같은 워커의 큐에 줄을 서므로 그 안에서는 넣은 순서대로 처리되고, **서로 다른 키끼리만 병렬**이 된다. 파티션이 브로커 레벨에서 하던 "키 단위 순서 보장 + 키 간 병렬"을 컨슈머 내부에서 한 단계 더 재현하는 셈이다.

대가도 있다. **워커별 부하가 불균등해진다.** 해시가 균등해도 키마다 트래픽이 다르면 특정 워커에 일이 몰린다.

```text
워커 4개, 키를 해시로 고정 배정

  W0: user-1001(초당 800건), user-1005(초당 20건)   <- 포화
  W1: user-1002(초당 30건)                           <- 한산
  W2: user-1003(초당 25건)                           <- 한산
  W3: user-1004(초당 15건)                           <- 한산

  W0의 큐만 계속 자란다. 나머지 워커는 놀지만 도와줄 수 없다
  — 도와주는 순간 user-1001의 순서가 깨지기 때문이다.
```

**순서 보장과 부하 균등은 근본적으로 맞바꾸는 관계**다. 순서를 포기할 수 있는 키가 있다면 그것만 무작위 배정으로 돌리는 절충도 가능하다.

**(2) 폴링 스레드가 워커 풀보다 빠르면 큐가 무한정 쌓인다.** 이게 놓치기 쉬운 지점이다. 폴링 스레드는 `submit()`만 하고 바로 다음 `poll()`을 돌기 때문에, **워커가 처리하는 속도보다 빠르게 계속 레코드를 밀어 넣는다.** 워커 큐는 메모리에 있으므로 결국 OOM으로 프로세스가 죽는다.

대응은 **백프레셔(backpressure)** — 하류가 감당 못 할 때 상류에 "잠깐 멈춰"라고 신호를 보내는 것 — 이고, Kafka에서는 `pause()`와 `resume()`으로 구현한다.

```java
while (running) {
    ConsumerRecords<String, Event> records = consumer.poll(timeout);
    for (ConsumerRecord<String, Event> record : records) {
        int worker = Math.abs(record.key().hashCode()) % workerCount;
        workers[worker].submit(() -> process(record));
    }

    // 미처리 건수가 상한을 넘으면 해당 파티션의 폴링을 멈춘다.
    // pause() 이후에도 poll()은 계속 호출해야 한다 — poll()이 하트비트를
    // 보내는 통로이므로, poll을 멈추면 브로커가 컨슈머를 죽은 것으로 보고
    // 리밸런싱을 일으킨다. pause 상태의 poll()은 레코드를 0건 반환하면서
    // 하트비트만 유지해 준다.
    if (inFlightCount() > MAX_IN_FLIGHT) {
        consumer.pause(consumer.assignment());
    } else if (!consumer.paused().isEmpty()) {
        consumer.resume(consumer.paused());  // 큐가 빠지면 다시 받는다
    }

    commitContiguousCompleted();  // 3절
}
```

**`pause()`를 걸어도 `poll()` 호출은 계속해야 한다**는 점이 핵심이다. `poll()`이 하트비트를 실어 보내는 통로이기 때문에, 폴링 루프 자체를 멈추면 브로커는 컨슈머가 죽은 줄 안다.

**(3) spring-kafka의 `concurrency` 설정과는 다른 층위다.** `concurrency`는 **리스너 컨테이너 안에 컨슈머 인스턴스를 여러 개 띄우는 것**이라 파티션 수가 상한이다(파티션보다 많은 컨슈머는 논다). 여기서 말하는 내부 병렬화는 **파티션 하나를 여러 스레드가 나눠 처리**하는 것이므로 파티션 수의 상한을 넘어선다. 그리고 넘어서기 때문에 **오프셋 커밋 문제가 새로 생긴다** — 이게 3절이다.

Confluent의 parallel-consumer 같은 라이브러리가 이 패턴(키 단위 병렬화 + 안전한 오프셋 관리)을 이미 구현해 둔 것까지 알면 가산점이다. 직접 구현하기 전에 검토할 선택지다.

## 3. 병렬화가 깨뜨리는 전제와 복구법 (이 질문의 본론)

### 3-1. 전제 지식 — 오프셋은 체크리스트가 아니라 북마크 하나다

여기서 반드시 먼저 깔아야 할 것이 있다. **오프셋 커밋이 정확히 무엇을 기록하는가**이다.

컨슈머 그룹은 파티션마다 **숫자 하나**를 저장한다. 그게 전부다. "어느 메시지를 처리했고 어느 메시지를 안 했는지"를 하나하나 표시하는 체크리스트가 아니라, **책갈피 하나**다.

```text
[체크리스트라면 이렇게 표현할 수 있을 것이다 — 하지만 이런 건 없다]
  100 [완료]  101 [완료]  102 [완료]  103 [ ]  104 [완료]  105 [완료]

[실제로 저장되는 것은 이것뿐이다]
  파티션 P0 -> 103
```

숫자 하나로 표현할 수 있는 의미는 하나뿐이다. **"이 지점 이전은 전부 처리됐으니, 재시작하면 여기부터 읽어라."** 커밋 오프셋이 103이면 "102번까지는 전부 끝났고 다음은 103번부터"라는 뜻이다(그래서 커밋값은 마지막 처리 오프셋이 아니라 **다음에 읽을 위치**, 즉 +1이다).

여기서 결정적인 한계가 나온다. **중간에 구멍이 있으면 표현할 방법이 없다.** "100, 101, 102, 104, 105는 끝났는데 103만 안 끝났다"를 숫자 하나로 적을 수는 없다.

순차 처리에서는 이 한계가 드러나지 않았다. 한 건씩 순서대로 처리하면 "마지막으로 처리한 오프셋 = 그 이전 전부 완료"가 자동으로 성립하기 때문이다. 구멍이 생길 수가 없었다.

**병렬화는 정확히 이 전제를 깬다.** 여러 워커가 동시에 처리하면 완료 순서가 뒤섞이고, 중간에 구멍이 뚫린다. 그러면 북마크 하나로는 진실을 적을 수가 없다. **이것이 이 질문의 근본 원인이다.**

### 3-2. 사고 시나리오 — 최신 완료 오프셋을 커밋하면

파티션에서 오프셋 100, 101, 102를 poll해 워커 3개에 뿌렸다. 101과 102는 끝났는데 100이 아직 처리 중이다.

**"가장 최근에 완료된 102를 커밋"하면** 커밋값은 103이 된다. 그 직후 컨슈머가 죽으면 재시작 시 103부터 읽는다. **100은 처리도 안 끝났는데 영원히 건너뛰어진다 — 유실이다.** 그리고 이 유실은 조용하다. 에러 로그도 안 남고, 나중에 데이터를 대조해 보기 전에는 아무도 모른다.

**자동 커밋(`enable.auto.commit=true`)을 켜둔 채라면 더 나쁘다.** 자동 커밋은 `poll()` 호출 시점에, 설정된 간격이 지났으면 **"직전 poll로 가져간 것들은 처리됐겠지"라고 가정하고** 커밋한다. 순차 처리 루프에서는 그 가정이 대체로 맞았다. 하지만 워커에 `submit()`만 하고 바로 다음 poll을 도는 구조에서는 **처리가 시작도 안 된 메시지가 커밋된다.**

**그래서 내부 병렬화의 첫 번째 전제는 `enable.auto.commit=false`다.** 예외가 없다.

### 3-3. 해법 — 연속 완료 구간의 끝까지만 커밋한다

북마크 하나로 표현할 수 있는 진실은 "여기까지는 구멍 없이 전부 끝났다"뿐이다. 그러면 답도 하나로 정해진다. **낮은 오프셋부터 끊김 없이 이어진 구간의 끝까지만 커밋한다.**

구체적으로 보자. 오프셋 100~109를 워커 풀에 나눠 줬고, 지금 상태가 이렇다.

```text
오프셋:   100   101   102   103   104   105   106   107   108   109
상태:      완    완    완   진행중  완    완    대기  대기  대기  대기
                              ^
                              |
                        여기가 구멍이다

연속 완료 구간:  [100][101][102]  <- 여기서 끊긴다
                                ^
                     커밋 가능한 마지막 지점 = 102
                     실제 커밋값 = 103 (다음에 읽을 위치)

104, 105는 끝났지만 커밋에 포함시킬 수 없다.
커밋값을 106으로 올리는 순간 그 선언의 의미는
"105 이전은 전부 처리됐다"가 되는데, 103이 그 안에서 거짓이 된다.
```

**104와 105가 끝났는데도 커밋하면 안 되는 이유**를 정확히 말할 수 있어야 한다. 오프셋 커밋은 개별 메시지에 대한 완료 표시가 아니라 **"이 지점 이전은 전부 처리됐다"는 구간 선언**이기 때문이다. 106을 커밋하면 103도 함께 "처리됨"으로 선언해 버리는 것이고, 그 상태에서 컨슈머가 죽으면 103은 다시 읽히지 않는다.

103이 끝나면 그때 구멍이 메워지고 커밋 지점이 한 번에 전진한다.

```text
103 완료 직후

오프셋:   100   101   102   103   104   105   106   107   108   109
상태:      완    완    완    완    완    완   진행중 대기  대기  대기

연속 완료 구간:  [100][101][102][103][104][105]
                                              ^
                          커밋 가능한 마지막 지점 = 105
                          실제 커밋값 = 106
```

한 칸이 아니라 세 칸(102 → 105)이 한꺼번에 전진했다. 밀려 있던 완료분이 구멍이 메워지는 순간 함께 반영되기 때문이다.

코드로 대비하면 이렇다.

```java
// Before: 완료된 것 중 최대 오프셋을 커밋한다 — 구멍(100)을 건너뛴다
Set<Long> completed = Set.of(101L, 102L);       // 100은 아직 처리 중
long maxCompleted = Collections.max(completed);  // 102
consumer.commitSync(Map.of(partition, new OffsetAndMetadata(maxCompleted + 1)));
// 커밋값 103. 여기서 죽으면 100은 영원히 유실된다.
```

```java
// After: 파티션별로 "연속 구간의 끝"을 계산해 그 다음 위치만 커밋한다
// completed: 워커들이 완료를 보고해 쌓아 둔 오프셋 집합
// nextExpected: 이번 파티션에서 아직 커밋되지 않은 가장 낮은 오프셋

long cursor = nextExpected;                  // 예: 100
while (completed.contains(cursor)) {         // 구멍을 만날 때까지만 전진
    completed.remove(cursor);                // 반영된 것은 집합에서 비운다
    cursor++;
}

// cursor는 "아직 안 끝난 첫 오프셋" = 다음에 읽어야 할 위치가 된다.
// 100이 미완이면 cursor는 100 그대로여서 커밋할 것이 없다.
if (cursor > nextExpected) {
    consumer.commitSync(Map.of(partition, new OffsetAndMetadata(cursor)));
    nextExpected = cursor;
}
```

워커가 처리를 마치면 `completed`에 자기 오프셋을 넣고, **폴링 스레드만이** 이 루프를 돌려 커밋한다(consumer는 스레드 세이프하지 않으므로). 구멍을 만나면 그 앞에서 멈추는 것이 전부다.

### 3-4. 따름 정리 — 실패한 메시지를 방치하면 커밋이 영원히 멈춘다

위 구조에는 필연적인 부작용이 하나 딸려 온다. **오프셋 100이 계속 실패 상태로 남아 있으면, 101 이후가 아무리 완료돼도 커밋 지점이 100 앞에서 전진하지 못한다.**

```text
오프셋 100이 영구 실패 (역직렬화 에러, 잘못된 데이터 등)

  100 [실패]  101 [완] 102 [완] ... 5000 [완]
   ^
   커밋 지점은 여기서 못 움직인다

  -> 컨슈머가 재시작하면 100부터 다시 읽는다
  -> 이미 처리한 4,900건이 전부 재처리된다
  -> 그리고 100은 또 실패하므로 같은 일이 반복된다
```

그래서 **재시도 상한과 DLQ(dead letter queue)가 병렬 컨슈머의 필수 부품**이 된다. DLQ는 처리에 반복 실패한 메시지를 별도 토픽으로 격리해 두는 곳이다. 핵심은 격리 자체가 아니라 **격리한 뒤 그 오프셋을 "처리 완료"로 마킹해 커밋을 전진시키는 것**이다. 그래야 구멍이 메워지고 뒤의 4,900건이 커밋된다.

이것은 잘 알려진 **poison pill**(한 건의 독약 메시지가 파티션 전체의 소비를 막는 문제)의 병렬화 버전이다. 순차 처리에서는 그 한 건에서 루프가 멈추고, 병렬 처리에서는 루프는 계속 도는데 **커밋만 멈춘다.** 증상이 다르게 보여서 원인 파악이 더 어렵다.

### 3-5. 그래도 남는 것 — at-least-once와 멱등 처리

연속 구간 커밋을 완벽하게 구현해도 사라지지 않는 문제가 있다. **처리 완료와 커밋 사이에 죽으면 그 구간은 재처리된다.**

```text
t0  오프셋 100~105 처리 완료
t1  커밋 직전에 프로세스가 죽는다
t2  재시작 -> 마지막 커밋값이 100이었다면 100부터 다시 읽는다
    -> 100~105가 두 번 처리된다
```

처리와 커밋은 서로 다른 시스템에 대한 두 개의 쓰기라 원자적으로 묶을 수 없다. 그래서 **유실은 막아도 중복은 남는다.** 이것이 Kafka의 기본 전달 보장인 **at-least-once**(최소 한 번은 도착한다, 하지만 정확히 한 번은 아니다)의 실체다.

최종 방어선은 **멱등 컨슈머**다. 2-1의 `ON CONFLICT DO NOTHING`이나, 처리 이력 테이블에 메시지 ID를 유니크 제약으로 걸어 두 번째 시도를 흡수하는 방식이다.

**"병렬화 → 자동 커밋 끄기 → 연속 구간까지만 수동 커밋 → 그래도 남는 중복은 멱등 처리"**까지 한 호흡으로 말하면 이 질문은 끝난다.

## 4. 꼬리질문 대비 포인트

### "자동 커밋을 켠 채로 워커 풀에 처리를 넘기면 정확히 무슨 일이 생기나?"

자동 커밋은 `poll()` 호출 시점에, 커밋 간격이 지났으면 **직전 poll로 가져간 오프셋을 커밋한다.** 근거는 "가져갔으면 처리됐겠지"라는 가정 하나다.

순차 처리 루프에서는 이 가정이 대체로 맞다. 다음 poll에 도달했다는 것은 이전 배치를 다 돌았다는 뜻이니까. 그런데 워커에 `submit()`만 하고 바로 다음 poll을 도는 구조에서는 **처리가 끝나지 않은 — 시작조차 안 했을 수 있는 — 메시지가 커밋된다.** 그 상태에서 컨슈머가 죽으면 재시작 시 그 메시지들을 건너뛴다. 유실이다.

그래서 내부 병렬화의 첫 번째 전제는 `enable.auto.commit=false`다.

### "워커 풀로 병렬화하면 키 순서는 어떻게 지키나?"

**키 해시로 워커를 고정 배정한다**(`hash(key) % 워커 수`). 같은 키의 메시지는 언제나 같은 워커의 큐에 들어가 순차 처리되므로 키 내부 순서가 유지되고, 서로 다른 키끼리만 병렬이 된다. 파티션이 브로커 레벨에서 하던 "키 단위 순서 보장 + 키 간 병렬"을 컨슈머 내부에서 한 단계 더 재현하는 것이다.

대가는 **워커별 부하 불균등**이다. 뜨거운 키가 배정된 워커만 포화되고 나머지는 놀 수 있는데, 놀고 있는 워커가 도와줄 수 없다 — 도와주는 순간 순서가 깨진다. 순서 보장과 부하 균등이 맞바꾸는 관계라는 점을 함께 말하면 좋다.

### "폴링이 워커보다 빨라서 메모리가 터지면?"

`pause()`와 `resume()`으로 백프레셔를 건다. 미처리 건수가 상한을 넘으면 `consumer.pause(assignment)`로 해당 파티션의 데이터 수신을 멈추고, 큐가 빠지면 `resume()`으로 재개한다.

핵심은 **`pause()` 상태에서도 `poll()` 호출은 계속해야 한다**는 것이다. `poll()`이 브로커에 하트비트를 보내는 통로이기 때문에, 폴링 루프 자체를 멈추면 브로커가 컨슈머를 죽은 것으로 판단해 리밸런싱을 일으킨다. pause 상태의 `poll()`은 레코드를 0건 반환하면서 하트비트만 유지해 준다. **"멈춘다"가 "poll을 안 부른다"가 아니라는 것**이 이 API의 요점이다.

### "배치 크기를 키웠더니 리밸런싱이 반복된다 — 왜?"

한 배치의 처리 시간이 `max.poll.interval.ms`를 넘으면, 브로커의 그룹 코디네이터가 그 컨슈머를 죽은 것으로 보고 그룹에서 제외한 뒤 리밸런싱을 일으킨다. 재조인한 컨슈머가 또 큰 배치를 물고 또 초과하면 **리밸런싱이 무한 반복**되고, 그동안 실제 처리량은 0에 가까워진다.

해법은 셋이다. `max.poll.records`를 줄여 배치를 작게 만들거나, 처리 자체를 최적화하거나, `max.poll.interval.ms`를 올린다. 단 마지막 선택지는 **진짜로 죽은 컨슈머를 감지하는 시간도 함께 늘린다**는 트레이드오프를 같이 말해야 한다.

### "commitSync와 commitAsync는 어떻게 골라 쓰나?"

`commitSync`는 커밋 완료(또는 실패)를 확인할 때까지 블로킹하고 실패 시 재시도도 해 주지만, 그만큼 처리 루프를 세운다. `commitAsync`는 논블로킹이라 루프 처리량을 지키지만 **실패해도 자동 재시도를 하지 않는다.** 재시도를 안 하는 이유가 중요하다 — 늦게 재시도한 예전 커밋이 나중에 성공한 최신 커밋을 덮어써 오프셋이 뒤로 되돌아가는 사고를 막기 위해서다.

실무 관용구는 **평상시 루프에서는 `commitAsync`, 종료 직전이나 리밸런스 직전에는 `commitSync`로 마지막 오프셋을 확실히 박는** 조합이다.

그리고 한 가지 더 — 커밋은 at-least-once 전제에서 **중복 범위를 줄이는 장치**이지 유실이나 중복을 없애는 장치가 아니다. 커밋을 자주 하면 재처리 구간이 짧아질 뿐, 재처리 자체는 사라지지 않는다.

### "그렇게까지 했는데도 안 따라잡으면? 파티션 증설 판단 기준은?" (시니어 변별 포인트)

**먼저 병목 위치를 확정한다.** 이 순서를 건너뛰면 파티션을 늘려도 아무것도 나아지지 않는다.

- **컨슈머 CPU가 상한이라면** 내부 병렬화나 배치화의 여지가 남았는지 먼저 본다.
- **다운스트림(DB, 외부 API)이 상한이라면** 파티션을 늘려도 다운스트림에 가는 부하만 커질 뿐 처리량은 안 는다. 오히려 DB를 먼저 넘어뜨릴 수 있다. 이 경우엔 다운스트림 증설이나 배치화가 먼저다.
- **컨슈머 인스턴스 수의 상한(= 파티션 수)에 막힌 것이 확인되면** 그때 증설한다.

증설을 실행할 때는 **키 순서가 증설 경계에서 깨진다는 것과 되돌릴 수 없다는 것**을 알고 한다. 순서에 민감한 토픽이면 운영 절차까지 설계한다 — 트래픽이 빠진 시간대를 고르고, 컨슈머를 드레인해 기존 파티션의 메시지를 다 소비한 뒤 증설하면 "옛 파티션에 옛 메시지가 남아 있는" 상태 자체를 없앨 수 있다. 여기까지 말하면 시니어 답변이다.

> **RabbitMQ에서의 대응**: 파티션 수 같은 상한이 없어 워커 증설이 1순위이고, prefetch·리스너 동시성·배치가 그다음이다. `33-rabbitmq-consumer-throughput-prefetch.md`에서 다룬다.

## 한 줄 요약

파티션 증설은 비가역이라 컨슈머 한 대를 먼저 쥐어짜는 게 순서고, 그 방법은 배치 처리(건별 왕복 500회를 다건 INSERT 1회로)와 폴링/처리 스레드 분리(키 고정 라우팅으로 순서 유지, `pause()`로 백프레셔)인데 — 병렬화하는 순간 "오프셋은 개별 완료 표시가 아니라 이 지점 이전 전부가 끝났다는 북마크 하나"라는 전제가 깨지므로, 자동 커밋을 끄고 구멍을 만나면 멈추는 연속 완료 구간까지만 수동 커밋하며(그래서 DLQ로 실패 건을 치워 커밋을 전진시켜야 하고), 그래도 남는 중복은 멱등 컨슈머로 받는 것까지가 한 세트다.
