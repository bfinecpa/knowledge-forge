# 메시지 큐 도입 이유 — 동기 호출 대비 얻는 것과 잃는 것

> 핵심 관전 포인트: **메시지 큐는 시스템 간 결합을 시간·장애·처리량
> 세 축에서 끊어준다 — 호출자는 응답을 기다리지 않고(시간),
> 수신자가 죽어 있어도 요청이 사라지지 않으며(장애), 트래픽 폭증을
> 큐가 버퍼로 흡수한다(처리량). 대신 즉시 정합성을 포기하고
> 최종 일관성을 받아들여야 하며, 요청 흐름 추적이 어려워지고,
> 실패 처리(재시도·중복·유실)를 직접 설계해야 하는 복잡도를 떠안는다.
> "비동기라 좋다"가 아니라 이 트레이드오프를 저울질해서 도입을
> 결정하는 것이 핵심이다.**

---

## 0. 질문 + 의도

**질문**: "메시지 큐를 도입하는 이유는? 동기 호출 대비 장단점은?"

**출제 의도**: "비동기로 하면 좋다"가 아니라 잃는 것(즉시 정합성, 흐름
추적 난이도, 실패 처리 복잡도)을 함께 말하는지 본다. 도입 결정의 양면을
보는 습관은 모든 아키텍처 논의의 입장권이다.

## 1. 동기 호출의 세 가지 한계 — 왜 큐를 생각하게 되는가

주문 완료 후 알림 발송·적립금 지급·통계 집계를 모두 동기로 호출하는
전형적인 코드를 보자.

```java
// Before: 전부 동기 호출 — 세 가지 문제가 숨어 있다
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    notificationClient.send(order);   // 문제 1: 알림 서버가 느리면 주문도 느려짐 (지연 전파)
    pointClient.accumulate(order);    // 문제 2: 적립금 서버가 죽으면 주문 자체가 실패 (장애 전파)
    statsClient.record(order);        // 문제 3: 주문 스파이크가 그대로 하위 시스템을 강타 (부하 전파)
}
```

동기 호출은 호출자와 수신자를 세 축에서 묶어버린다.

- **시간 결합**: 응답이 올 때까지 스레드가 대기한다. 하위 시스템의
  지연이 그대로 내 응답 시간에 더해진다 (지연의 합산).
- **가용성 결합**: 수신자가 죽으면 나도 실패한다. 주문의 성공이
  "알림 서버의 생존"에 의존할 이유가 없는데도 그렇게 된다.
- **처리량 결합**: 내가 받는 트래픽 스파이크가 완충 없이 하위
  시스템으로 흘러간다. 가장 약한 시스템이 전체의 상한이 된다.

## 2. 메시지 큐가 끊어주는 것 — 도입 이유 4가지

```java
// After: 이벤트 발행 — 주문은 주문만 책임진다
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    eventPublisher.publish(new OrderPlacedEvent(order.getId()));
    // 알림·적립금·통계는 각자 이 이벤트를 구독해서 처리
    // 주문 응답 시간 = 주문 저장 + 발행 시간뿐
}
```

1. **비동기화 (응답 시간 단축)** — 핵심 작업(주문 저장)만 끝내고 즉시
   응답한다. 부가 작업의 지연이 사용자 응답 시간에서 빠진다.
2. **장애 격리 (버퍼링)** — 알림 서버가 10분 죽어 있어도 메시지는
   큐에 쌓여 있다가 복구 후 처리된다. 요청이 "사라지지 않고 기다리는"
   것이 큐의 본질이다. 비유하면 전화(동기 — 상대가 안 받으면 실패)와
   문자(비동기 — 상대가 나중에 확인)의 차이다.
3. **피크 흡수 (부하 평탄화)** — 초당 1만 건이 몰려도 컨슈머는 자기
   속도(초당 1천 건)로 꺼내 처리한다. 스파이크가 큐 길이로 변환될 뿐
   하위 시스템은 일정한 부하만 받는다.
4. **결합도 감소 (발행-구독 확장)** — 주문 서비스는 "누가 이 이벤트를
   쓰는지" 모른다. 나중에 추천 시스템이 추가돼도 주문 코드는 한 줄도
   바뀌지 않는다 (컨슈머만 추가).

## 3. 잃는 것 — 이걸 말해야 합격 답변이 된다

### ① 즉시 정합성 → 최종 일관성

주문 직후 사용자가 적립금 페이지를 열면 **아직 적립 전일 수 있다.**
"언젠가는 맞아진다(eventually consistent)"는 보장뿐이다. "구매했는데
이용권이 안 보여요" 같은 문의가 곧 이 선택의 대가이며, 몇 초까지
허용 가능한지 기획과 협상해야 하는 제품 문제가 된다.

### ② 흐름 추적 난이도

동기 호출은 스택 트레이스 하나로 전 과정이 보이지만, 큐를 거치면
호출 흐름이 물리적으로 끊긴다. "주문은 됐는데 알림이 안 갔다"를
추적하려면 상관관계 ID(correlation ID)를 이벤트에 심고 분산 추적을
갖춰야 한다 — 관측 인프라 비용이 추가된다.

### ③ 실패 처리 복잡도

동기 호출은 실패하면 즉시 예외로 알 수 있고 호출자가 그 자리에서
대응한다. 비동기에서는:

- **유실**: 발행 실패, 브로커 장애, 커밋 시점 문제로 메시지가 사라질 수 있다.
- **중복**: 재시도 과정에서 같은 메시지가 두 번 처리될 수 있다
  → 컨슈머를 멱등하게 만들어야 한다.
- **재시도·DLQ**: 계속 실패하는 메시지(poison pill)가 뒤 메시지를
  막지 않도록 별도 설계가 필요하다.

즉 **동기에서는 공짜였던 "실패의 즉시 인지와 전파"를 직접 구현**해야 한다.

### ④ 운영 인프라 부담

브로커라는 새 인프라의 운영(모니터링, 랙 감시, 용량, 장애 대응)이
추가된다. 트래픽이 작고 호출 관계가 단순하면 동기 호출 + 타임아웃이
더 싼 선택일 수 있다.

### 요약 비교

| 축      | 동기 호출            | 메시지 큐              |
|--------|------------------|--------------------|
| 정합성    | 즉시 (강한 일관성 쪽)    | 최종 일관성             |
| 응답 시간  | 하위 지연이 합산됨       | 핵심 작업만큼만           |
| 장애 영향  | 수신자 장애 = 내 장애    | 큐가 격리 (쌓였다 처리)     |
| 실패 인지  | 즉시 예외            | 지연 감지 — 직접 설계 필요   |
| 추적     | 스택 트레이스로 한눈에     | 상관관계 ID·분산 추적 필요   |

## 4. 꼬리질문 대비 포인트

### "그럼 모든 호출을 비동기로 바꾸면 되지 않나요?"

아니다. **응답 결과가 다음 진행의 전제인 호출은 동기여야 한다.**
결제 승인처럼 "성공/실패를 알아야 주문 확정 여부가 갈리는" 호출을
비동기로 빼면 사용자에게 "아마 될 거예요"라고 답하는 셈이다.
기준은 "이 작업의 결과 없이 응답해도 되는가" — 알림·적립·집계처럼
부가적인(핵심 트랜잭션 밖의) 작업이 비동기화의 대상이다.

### "타임아웃 + 서킷 브레이커로도 장애 전파는 막을 수 있지 않나요?" (시니어 변별 포인트)

막는 건 맞지만 **의미가 다르다.** 서킷 브레이커는 "하위가 죽었으니
그 작업을 포기(fail-fast)"하는 것이고, 큐는 "하위가 죽었어도 작업을
보존했다가 나중에 반드시 수행"하는 것이다. 즉 작업을 **버려도 되면**
동기 + 서킷 브레이커로 충분하고, **버리면 안 되면**(적립금 지급 등)
큐가 필요하다. 요구사항이 결정하는 것이지 어느 쪽이 우월한 게 아니라고
답하면 균형 잡힌 인상을 준다.

### "DB 커밋은 됐는데 이벤트 발행이 실패하면요?"

DB와 브로커는 서로 다른 시스템이라 하나의 트랜잭션으로 묶이지 않는다.
표준 해법은 **Transactional Outbox** — 이벤트를 같은 DB 트랜잭션으로
outbox 테이블에 함께 저장하고, 별도 프로세스(폴링 또는 CDC)가 그
테이블을 읽어 브로커로 발행한다. DB 커밋이 성공했다면 이벤트도 반드시
발행된다는 원자성을 확보하는 패턴이다 (가산점 포인트).

### "메시지가 중복 처리되면 어떻게 하나요?"

대부분의 브로커 사용은 at-least-once(최소 한 번) 전달이라 **중복은
예외가 아니라 정상 동작**이다. 컨슈머를 멱등하게 만든다 — 이벤트에
고유 ID를 부여하고 처리 이력 테이블에 유니크 제약으로 기록해, 이미
처리한 ID면 건너뛴다. "exactly-once는 공짜가 아니고, 실무는
at-least-once + 멱등 컨슈머로 푼다"까지 말하면 가산점 포인트.

### "도입하지 말아야 할 때는 언제인가요?"

- 결과를 즉시 알아야 하는 호출 (조회, 결제 승인)
- 트래픽이 작고 호출 관계가 1:1로 단순한 경우 — 브로커 운영 비용이
  이득보다 큼
- 팀에 비동기 실패 처리(멱등·DLQ·랙 모니터링)를 설계·운영할 여력이
  없는 경우 — 유실이 나도 원인을 모르는 시스템이 된다

---

## 한 줄 요약

메시지 큐는 시간·장애·처리량의 결합을 끊어 **응답 속도, 장애 격리,
피크 흡수, 확장성**을 얻는 대신, **즉시 정합성·흐름 추적·단순한 실패
처리**를 내주는 거래다 — "작업을 버리면 안 되는가, 결과를 즉시 알아야
하는가"라는 요구사항이 도입 여부를 결정한다.
