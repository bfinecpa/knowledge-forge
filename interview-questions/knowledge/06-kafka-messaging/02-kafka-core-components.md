# Kafka 기본 구성요소 — Broker, Topic, Partition, Consumer Group의 역할과 관계

> 핵심 관전 포인트: **Broker는 메시지를 저장·전달하는 서버(여럿이 모여
> 클러스터), Topic은 메시지를 종류별로 나누는 논리적 채널, Partition은
> 토픽을 물리적으로 쪼갠 append-only 로그로 — 파티션 안에서만 순서가
> 보장되고 파티션 수가 곧 병렬 처리의 상한이라는 이중성을 가진다.
> Consumer Group은 파티션들을 나눠 갖고 소비하는 협업 단위로, 같은
> 그룹 안에서 한 파티션은 한 컨슈머만 읽는다. 이 네 개념, 특히
> "파티션 = 순서 보장 단위이자 병렬성 단위"가 이후 모든 Kafka 논의의
> 어휘가 된다.**

---

## 0. 질문 + 의도

**질문**: "Kafka의 기본 구성요소(Broker, Topic, Partition, Consumer
Group)를 설명해주세요."

**출제 의도**: 이후 모든 논의(순서, 병렬성, 재처리)의 어휘를 갖췄는지
확인하는 질문. 특히 파티션이 "순서 보장 단위이자 병렬성 단위"라는
이중성을 짚는지가 이해도의 척도다.

## 1. 전체 그림 — 메시지 하나의 여정

```
Producer ──▶ [ Broker 클러스터 ]                    ┌ Consumer A-1 ┐
             Topic "order-events"                   │              │ Consumer
             ├─ Partition 0: [m0][m1][m2]... ──────▶│ Consumer A-2 │ Group A
             ├─ Partition 1: [m0][m1]...     ──────▶│              │ (적립금 서비스)
             └─ Partition 2: [m0][m1][m2]... ──────▶└ Consumer A-3 ┘
                                             └────▶ Consumer Group B (알림 서비스, 전 파티션 소비)
```

프로듀서가 토픽에 메시지를 발행하면, 메시지는 토픽의 여러 파티션 중
하나에 **덧붙여지고(append)**, 컨슈머 그룹들이 각자의 진도(오프셋)로
읽어간다. 우체국 비유로: Broker는 우체국 건물, Topic은 수신함 종류,
Partition은 같은 종류의 수신함을 여러 칸으로 나눈 것, Consumer Group은
칸을 나눠 맡아 비우는 작업조다.

## 2. 구성요소별 역할

### Broker — 저장하고 전달하는 서버

메시지를 디스크에 저장하고 프로듀서/컨슈머의 요청을 처리하는 Kafka
서버 프로세스다. 보통 3대 이상이 **클러스터**를 이루고, 각 파티션의
데이터가 여러 브로커에 **복제(replication)**되어 한 대가 죽어도
데이터가 유지된다. 파티션마다 읽기/쓰기를 담당하는 **리더** 브로커가
있고 나머지는 **팔로워**로 복제만 받는다 — 리더가 죽으면 팔로워 중
하나가 리더로 승격된다 (가산점 포인트).

### Topic — 메시지의 논리적 분류 채널

`order-events`, `payment-events`처럼 메시지를 종류별로 구분하는
이름이다. RDB의 테이블에 비유할 수 있는 **논리적** 단위이고, 실제
저장은 아래의 파티션 단위로 이뤄진다.

### Partition — 토픽을 쪼갠 append-only 로그 (핵심)

토픽을 물리적으로 나눈 조각으로, 각 파티션은 **끝에만 추가되는
로그 파일**이다. 메시지는 파티션 안에서 **오프셋(offset)**이라는
순번을 갖는다. 두 가지 성질이 파티션의 정체성이다:

- **순서 보장 단위**: 한 파티션 안에서는 쓴 순서대로 읽힌다.
  파티션이 다르면 순서 보장이 없다. "토픽 전체의 순서"라는 것은
  존재하지 않는다 (파티션이 1개일 때만 예외).
- **병렬성 단위**: 같은 그룹 안에서 한 파티션은 한 컨슈머만 읽으므로,
  **파티션 수 = 그 그룹이 낼 수 있는 최대 병렬도**다.

메시지가 어느 파티션으로 갈지는 **메시지 키의 해시**로 결정된다
(키가 없으면 파티션에 분산). 같은 키는 항상 같은 파티션으로 가므로,
`userId`를 키로 주면 "같은 사용자의 이벤트는 순서대로"가 보장된다.

또 하나 중요한 점: 큐와 달리 **읽어도 메시지가 삭제되지 않는다.**
설정된 보존 기간 동안 로그에 남아 있고, 컨슈머는 자기 오프셋만
움직인다 — 그래서 오프셋을 되감아 **재소비(replay)**가 가능하다.

### Consumer Group — 파티션을 나눠 갖는 소비 협업 단위

같은 `group.id`를 가진 컨슈머들의 집합이다. 그룹 안에서 파티션들이
컨슈머들에게 **배타적으로 분배**된다 — 파티션 3개에 컨슈머 3대면
1개씩 맡는다. 그룹은 파티션별로 "어디까지 읽었는지"(**커밋된
오프셋**)를 브로커에 기록해 두고, 컨슈머가 죽거나 추가되면 파티션을
다시 분배하는 **리밸런싱**이 일어난다.

그룹이 다르면 서로 독립적으로 전체 메시지를 읽는다. 이것이 발행-구독의
핵심이다: 적립금 서비스(그룹 A)와 알림 서비스(그룹 B)가 같은
`order-events`를 각자 처음부터 끝까지 소비한다.

## 3. 실무 감각 — 이 구조가 코드에 미치는 영향

```java
// Before: 키 없이 발행 — 파티션에 분산되어 사용자별 순서가 깨질 수 있음
kafkaTemplate.send("order-events", event);
// 같은 사용자의 "주문 → 취소"가 다른 파티션에 실려
// "취소 → 주문" 순서로 소비될 수 있다

// After: userId를 키로 발행 — 같은 사용자는 항상 같은 파티션 → 순서 보장
kafkaTemplate.send("order-events", event.getUserId(), event);
```

```yaml
# 같은 그룹 = 나눠 처리(작업 분담), 다른 그룹 = 각자 전체 소비(방송)
spring:
  kafka:
    consumer:
      group-id: point-service   # 적립금 서비스 인스턴스 3대가 이 그룹으로 파티션을 나눠 가짐
```

- 처리량을 올리려고 컨슈머 인스턴스를 늘려도 **파티션 수를 넘으면
  잉여 인스턴스는 논다.** 확장의 상한이 토픽 생성 시점에 정해진다.
- 파티션을 나중에 늘리면 키 해싱 결과가 바뀌어 **기존 키의 순서
  보장이 그 시점에 끊긴다** — 파티션 수 결정이 비가역에 가까운 이유다.

## 4. 꼬리질문 대비 포인트

### "파티션 3개인 토픽에 컨슈머 5대를 띄우면 어떻게 되나요?"

같은 그룹이라면 3대만 파티션을 배정받고 **2대는 유휴(idle) 상태**로
논다. 한 파티션을 두 컨슈머가 나눠 읽는 일은 없다 (그룹 내에서
파티션은 배타적 소유). 유휴 컨슈머는 낭비지만, 기존 컨슈머가 죽었을 때
리밸런싱으로 즉시 이어받는 대기조 역할은 한다.

### "메시지는 어떤 파티션으로 가나요? 순서 보장이 필요하면?"

키가 있으면 `hash(key) % 파티션 수`로 결정되어 같은 키는 항상 같은
파티션으로 간다. 키가 없으면 파티션들에 분산된다. "특정 사용자의
이벤트 순서 보장"은 `userId`를 키로 지정해서 푼다. 대가도 말해야
한다 — 특정 키에 트래픽이 몰리면(핫 키) 그 파티션만 병목이 되는
**키 편중** 문제가 생긴다 (가산점 포인트).

### "같은 토픽을 두 서비스가 각자 소비하려면 어떻게 하나요?"

**다른 `group.id`를 쓰면 된다.** 그룹별로 오프셋이 독립 관리되므로
각 서비스가 전체 메시지를 자기 진도로 소비한다. 반대로 같은 그룹으로
묶으면 "나눠서 처리"(부하 분산)가 된다 — 같은 그룹 = 작업 분담,
다른 그룹 = 방송이라는 구분이 컨슈머 설계의 첫 단추다.

### "브로커 한 대가 죽으면 메시지는 유실되나요?"

복제 계수(replication factor)를 2 이상으로 잡았다면 다른 브로커의
팔로워 복제본이 있으므로 유실되지 않고, 팔로워가 리더로 승격되어
서비스가 계속된다. 단 프로듀서의 `acks` 설정이 복제 완료까지
기다리지 않는 값이면(예: `acks=1`) 리더만 받고 죽는 순간의 메시지는
유실될 수 있다 — 내구성은 복제 계수와 `acks`의 조합으로 결정된다
(가산점 포인트).

### "파티션 수는 처음에 어떻게 잡아야 하나요?" (시니어 변별 포인트)

**목표 처리량 ÷ 컨슈머 1대의 처리량 + 성장 여유**로 산정한다.
나중에 늘리면 키 해싱이 바뀌어 순서 보장이 깨지고, 처음부터 과하게
잡으면 브로커의 메타데이터·복제 부담과 리밸런싱 시간이 늘어난다.
"부족하면 늘리면 되지"가 아니라 **거의 비가역인 설정이므로 설계
시점에 계산해야 한다**는 인식을 보여주는 것이 포인트다.

---

## 한 줄 요약

Broker(저장 서버) 위에 Topic(논리 채널)이 있고, Topic은
Partition(순서 보장 단위이자 병렬성 단위인 append-only 로그)으로
쪼개지며, Consumer Group이 그 파티션들을 배타적으로 나눠 갖고 각자의
오프셋으로 읽는다 — **순서는 파티션 키로, 병렬도는 파티션 수로,
독립 소비는 그룹으로** 푼다는 것이 Kafka 설계의 문법이다.
