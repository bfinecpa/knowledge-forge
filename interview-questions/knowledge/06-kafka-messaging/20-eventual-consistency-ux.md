# 최종 일관성과 UX — "결제했는데 왜 안 보여요"를 다루는 법

> 핵심 관전 포인트: **이벤트 기반 아키텍처에서 쓰기와 그 결과가 조회에
> 반영되는 시점 사이의 지연은 버그가 아니라 설계의 속성이다. 따라서
> 대응도 두 축으로 간다. 기술 축 — 사용자가 자기 행동의 결과는 즉시
> 보게 만드는 read-your-own-writes(응답에 결과 포함, 쓰기 경로 조회
> 라우팅, 버전 토큰)와, "처리중"이라는 정직한 중간 상태를 도메인과
> 화면에 도입하는 것. 제품 축 — "몇 초까지 허용 가능한가"를 기획과
> 협상해 SLA로 못 박고, 컨슈머 랙을 그 SLA 기준으로 모니터링하는 것.
> 그리고 돈·권한처럼 즉시성이 필수인 구간은 애초에 동기 범위에 남긴다.**

---

## 0. 질문 + 의도

**질문**: "이벤트 기반 아키텍처에서 최종 일관성(eventual consistency)으로 인한 UX 문제를 어떻게 다루나요?"

**출제 의도**: "구매했는데 이용권이 아직 안 보여요"를 기술 문제이자
제품 문제로 다루는지 본다. 기획자와 "몇 초까지 허용 가능한가"를
협상하는 역할까지 백엔드의 일임을 아는 사람인지 — 즉 아키텍처 선택의
대가가 사용자 화면에 어떻게 나타나는지를 끝까지 추적하는 시야를 확인한다.

## 1. 왜 생기는가 — 지연은 아키텍처의 청구서다

전형적인 흐름을 보면 지연이 어디서 쌓이는지 보인다.

```text
[결제 서비스] 결제 승인 + DB 커밋
   → (outbox 폴링/CDC) 이벤트 발행
   → [Kafka] 파티션 적재
   → [이용권 서비스] 컨슈머가 poll → 처리 → 이용권 테이블 커밋
   → 사용자가 "내 이용권" 화면 조회
```

평상시에는 이 전체가 수백 ms라 아무도 모른다. 문제는:

- **컨슈머 랙이 쌓이는 순간** 지연이 초 → 분 단위로 늘어난다.
  이때 "이용권이 안 보여요" CS가 몰려온다.
- 사용자는 아키텍처를 모른다. **자기가 방금 한 행동의 결과가 안 보이면
  실패로 인식**하고 — 새로고침 연타, 재구매 시도(중복 결제 위험),
  CS 문의로 이어진다.

즉 최종 일관성 자체를 없앨 수는 없고(그게 비동기를 택한 이유이므로),
**"사용자가 그 지연을 실패로 오인하지 않게"** 만드는 것이 과제다.

## 2. 기술 축 ① — read-your-own-writes: 내 행동의 결과는 내가 즉시 본다

전체 시스템의 강한 일관성은 포기해도, **"방금 쓴 본인"에게만큼은
즉시 보이게** 하는 보장이다. 사용자 불만의 대부분은 남의 데이터가 아니라
자기 행동의 결과가 안 보일 때 나오기 때문에, 이것만으로 체감 문제의
대부분이 사라진다. 구현 선택지:

```java
// Before: 쓰기는 명령만 던지고, 화면은 이벤트로 갱신되는 조회 모델만 본다
POST /purchases → 202 Accepted (본문 없음)
GET  /my/passes → 아직 컨슈머가 처리 전이라 빈 목록   // "안 보여요"

// After 1: 쓰기 응답에 결과를 담아 클라이언트가 화면을 직접 갱신
POST /purchases → 200 { "passId": 7, "status": "ACTIVE", ... }
// 클라이언트는 응답으로 받은 이용권을 목록에 즉시 추가(낙관적 UI).
// 조회 모델이 따라잡기 전까지의 공백을 클라이언트 상태가 메운다.
```

- **After 2 — 쓰기 경로로 조회 라우팅**: 쓰기 직후 일정 시간(또는 세션
  단위)은 그 사용자의 조회를 조회 모델이 아니라 **원본(쓰기) 저장소**로
  보낸다. CQRS에서 흔한 절충.
- **After 3 — 버전/타임스탬프 토큰**: 쓰기 응답으로 버전 토큰을 주고,
  이후 조회 요청에 실어 보내면 서버는 조회 모델이 그 버전 이상으로
  따라잡았는지 확인하고, 아직이면 잠깐 대기하거나 원본을 조회한다.
  구현 비용이 있지만 멀티 디바이스에서도 성립한다. (가산점 포인트)

## 3. 기술 축 ② — "처리중"이라는 정직한 상태 + 완료 통지

read-your-own-writes로도 안 되는 경우가 있다 — 처리 자체가 비동기 저편에서
끝나야 결과가 존재하는 경우(외부 결제망 확정, 배송 접수 등). 이때는
**거짓 완료 대신 중간 상태를 도메인에 도입**한다.

```text
Before: 화면이 즉시 "구매 완료!"를 보여줌
  → 뒤에서 실패하면 완료라던 것이 사라짐 — 최악의 UX (신뢰 붕괴)

After: PENDING(처리중) 상태를 정식 도메인 상태로 추가
  → 화면: "구매 처리 중입니다" + 완료되면 갱신
  → 실패하면 "결제에 실패했습니다 (재시도)"로 정직하게 전이
```

완료 시점 전달 방법은 상황에 맞게: 웹소켓/SSE push, 짧은 폴링,
푸시 알림("이용권이 지급되었어요"). 포인트는 **비동기라는 사실을 숨기지
말고, 진행 상황을 보여주는 UX로 바꾸는 것**이다. 은행 이체가 "처리중"을
보여주는 것과 같은 원리다.

또 하나의 선긋기 — **모든 것을 비동기로 하지 않는다**:

- 돈이 오가는 확정, 권한 부여처럼 **다음 화면이 그 결과에 의존하는 것**은
  동기 커밋 범위(같은 트랜잭션 또는 동기 API 호출)에 남긴다.
- 알림, 통계 적재, 추천 갱신처럼 **늦어도 아무도 안 다치는 것**만
  이벤트로 뺀다. "무엇을 비동기로 뺄 수 있는가"의 판단 기준 자체가
  UX 허용치다.

## 4. 제품 축 — 허용 지연을 협상하고, 그 숫자로 모니터링한다

시니어가 갈리는 지점은 여기다. 최종 일관성의 지연 허용치는
엔지니어가 혼자 정하는 값이 아니라 **제품 결정**이다.

1. **기획과 SLA 협상**: "이용권 지급이 결제 후 몇 초까지 늦어도
   되는가?" — 3초라면 read-your-own-writes로 충분하고, 0초여야 한다면
   그 구간은 동기로 설계해야 한다. 이 질문을 백엔드가 먼저 던지는 것이
   아키텍처 결정의 순서다.
2. **SLA 기준의 모니터링**: 컨슈머 랙을 "메시지 수"가 아니라
   **시간(가장 오래된 미처리 메시지의 나이)**으로 환산해 SLA 초과 시
   알림을 건다. "랙 1만 건"은 판단이 안 되지만 "지급 지연 40초"는
   즉시 대응 판단이 된다.
3. **장애 시 강등(degradation) UX 준비**: 랙이 SLA를 크게 넘는 상황에서
   보여줄 배너("현재 지급이 지연되고 있습니다"), CS 대응 문구,
   중복 구매 방지 가드(처리중 상태에서 구매 버튼 비활성화)를
   미리 만들어 둔다. 지연은 반드시 오므로, 그날의 UX를 설계해 두는 것까지가
   이벤트 기반 아키텍처의 운영이다.

## 5. 꼬리질문 대비 포인트

### "read-your-own-writes를 구체적으로 어떻게 구현했나요/하겠나요?"

세 가지 중 시스템 형태에 맞는 것을 고른다 — ① 쓰기 응답에 결과를 담아
클라이언트가 화면 상태를 직접 갱신(가장 싸고 대부분 충분),
② 쓰기 직후 그 사용자의 조회를 원본 저장소로 라우팅(서버에서 보장,
클라이언트 수정 불필요), ③ 쓰기 버전 토큰으로 조회 모델의 따라잡음을
확인(멀티 디바이스까지 성립, 구현 비용 최대). "본인 것만 즉시 보이면
되고 남의 화면은 몇 초 늦어도 된다"는 요구 분해가 답의 핵심이다.

### "그럴 거면 그냥 동기로 하면 되지 않나요?"

부분적으로 맞는 지적이라 선긋기로 답한다 — 결과에 다음 행동이 의존하는
핵심 경로(결제 확정, 권한 부여)는 동기로 남기고, 지연이 허용되는 부가
경로만 비동기로 뺀다. 전부 동기로 묶으면 가용성·처리량·서비스 간 결합의
비용을 도로 내는 것이고, 전부 비동기로 빼면 UX 비용을 낸다.
**경계를 어디에 긋느냐가 설계 판단**이고, 그 기준이 바로 "이 결과는
몇 초까지 늦어도 되는가"다.

### "허용 지연 시간은 누가 어떻게 정하나요?" (시니어 변별 포인트)

백엔드가 단독으로 정하는 값이 아니다. 흐름별로 "안 보이면 사용자가
무엇을 하는가"(재구매? 이탈? 무시?)를 기획·CS와 함께 따져 도메인별로
차등을 둔다 — 결제/권한은 초 단위 이하, 알림·통계는 분 단위 허용, 등.
정한 숫자는 문서로 끝나는 게 아니라 **컨슈머 랙 알림 임계값과 강등 UX
발동 조건**으로 연결돼야 산다. "허용치를 정의한 적이 없는 시스템은
지연이 나도 장애인지 아닌지조차 판단할 수 없다"까지 말하면
운영 관점이 완성된다.

### "완료를 폴링으로 확인시키면 조회가 폭주하지 않나요?"

폴링을 쓴다면 지수 백오프 + 최대 횟수를 클라이언트에 강제하고,
서버는 그 조회를 가벼운 상태 확인 API(캐시 가능)로 분리한다.
규모가 커지면 SSE/웹소켓 push나 모바일 푸시로 전환해 "완료를 서버가
알려주는" 구조로 바꾼다. 어느 쪽이든 처리중 상태의 존재가 전제다 —
상태가 없으면 클라이언트는 무엇을 폴링할지조차 없다.

---

## 한 줄 요약

최종 일관성의 UX 문제는 지연을 없애는 게 아니라 — 자기 행동의 결과는
즉시 보이게 하고(read-your-own-writes), 나머지는 "처리중"이라는 정직한
상태로 보여주고, "몇 초까지 괜찮은가"를 제품 결정으로 합의해 그 숫자로
랙을 감시하는 것 — 즉 **지연을 사용자가 실패로 오인하지 않게 설계하는
일**이다.
