# 오프셋 커밋과 자동 커밋의 위험 — 커밋 시점이 유실과 중복을 가른다

> 핵심 관전 포인트: **오프셋 커밋은 컨슈머 그룹이 "이 파티션을 어디까지
> 읽었다"를 브로커에 기록하는 책갈피 행위다. 재시작·리밸런스 때 이
> 책갈피부터 다시 읽는다. 자동 커밋(enable.auto.commit=true)의 위험은
> 커밋이 "처리 완료"가 아니라 "시간 주기"로 일어난다는 것 — 처리가 끝나기
> 전에 커밋되면 크래시 시 그 메시지는 영영 다시 오지 않고(유실), 처리는
> 끝났는데 커밋 전에 죽으면 다시 와서 두 번 처리된다(중복). 그래서 실무
> 정석은 수동 커밋으로 "처리 후 커밋"을 보장하고, 그 대가인 중복은 멱등
> 처리로 방어하는 것이다.**

---

## 0. 질문 + 의도

**질문**: "오프셋 커밋이란? 자동 커밋의 위험은?"

**출제 의도**: 처리 전 커밋(유실) vs 처리 후 커밋(중복)이라는 선택이
존재함 자체를 아는지 확인한다. 이 선택을 의식하지 않고 기본값으로
운영하는 시스템은 유실이 나도 원인을 모른다 — "가끔 이벤트가
사라져요"라는 버그 리포트 앞에서 커밋 시점부터 의심할 수 있는 사람인지를
가리는 질문이다.

## 1. 오프셋 커밋이란 — 컨슈머 그룹의 책갈피

파티션 안의 메시지에는 0부터 증가하는 위치 번호(**오프셋**)가 붙는다.
컨슈머는 메시지를 읽어가도 브로커에서 메시지가 지워지지 않기 때문에
(전통 MQ와의 결정적 차이), "어디까지 읽었는지"는 컨슈머 쪽이 기억해야
한다. 이 기억을 브로커에 기록하는 행위가 **오프셋 커밋**이다.

- 커밋된 오프셋은 브로커 내부 토픽 `__consumer_offsets`에
  `(컨슈머 그룹, 토픽, 파티션) → 다음에 읽을 오프셋` 형태로 저장된다.
- 컨슈머가 살아서 도는 동안에는 메모리 안의 현재 위치(position)로
  계속 읽어나가므로 커밋이 없어도 진행에는 문제가 없다.
- 커밋이 힘을 발휘하는 순간은 **재시작과 리밸런스**다. 파티션을 새로
  할당받은 컨슈머는 커밋된 오프셋부터 읽기 시작한다.

책 비유: 책(파티션)은 그대로 있고, 책갈피(커밋된 오프셋)만 그룹 단위로
꽂아둔다. 책갈피를 실제 읽은 곳보다 앞에 꽂으면 그 사이는 다시 읽고(중복),
뒤에 꽂으면 그 사이를 건너뛴다(유실). **커밋 시점 문제의 전부가 이
비유 안에 있다.**

## 2. 자동 커밋의 동작 — "처리 완료"가 아니라 "시간 주기"로 커밋한다

`enable.auto.commit=true`(기본값)이면 컨슈머는
`auto.commit.interval.ms` 주기가 지난 뒤의 `poll()` 호출 시점에,
**직전 poll()이 반환했던 마지막 오프셋**을 조용히 커밋한다.

문제의 본질은 이것이다: **자동 커밋은 애플리케이션이 메시지를 실제로
처리했는지 전혀 모른다.** 커밋 조건이 "처리 성공"이 아니라 "시간이
지났고 poll이 또 불렸다"이기 때문에, 커밋과 처리의 순서가 코드 구조에
따라 어긋난다.

### 2-1. 중복 시나리오 — 처리는 됐는데 커밋 전에 죽음

```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(timeout);
    for (var record : records) {
        process(record);          // 300건 처리 완료
    }
    // 다음 poll()에서 커밋될 예정이었는데, 여기서 크래시/리밸런스 발생
}
// → 커밋은 마지막 커밋 주기 시점에 멈춰 있음
// → 재시작한 컨슈머는 이미 처리한 300건을 다시 받는다 = 중복 처리
```

동기 처리 루프에서는 커밋이 항상 "직전 배치 처리 완료 후"(다음 poll
시점)에 일어나므로 유실은 없고 중복만 생긴다. 중복 폭은 마지막 커밋
이후 처리한 만큼 — 커밋 주기가 길수록 커진다.

### 2-2. 유실 시나리오 — 처리가 안 됐는데 커밋됨 (더 위험)

```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(timeout);
    for (var record : records) {
        executor.submit(() -> process(record));  // ① 스레드풀에 던지고
    }
    // ② 바로 다음 poll()로 진행 → 자동 커밋 발동
    //    아직 처리 중(또는 실패)인 레코드의 오프셋까지 커밋됨
}
// → 여기서 크래시하면, 처리 못 한 메시지는 커밋 뒤편에 있으므로
//   재시작해도 다시 오지 않는다 = 조용한 유실
```

유실은 두 가지 코드 구조에서 나온다:

- **처리를 다른 스레드에 넘기고 루프는 계속 도는 구조** — poll은
  빨리 돌고, 커밋은 처리 완료를 앞질러 간다.
- **예외를 삼키고 루프가 계속 도는 구조** — 처리 실패한 레코드가
  있어도 다음 poll에서 그 오프셋까지 커밋된다. 로그에 에러 한 줄
  남고 메시지는 사라진다.

중복은 로그·정산에서 두 번 보이니까 발견이라도 되는데, 유실은
**아무 흔적 없이 조용히 사라진다.** "이 선택을 의식하지 않고 기본값으로
운영하는 시스템은 유실이 나도 원인을 모른다"는 말이 정확히 이 지점이다.

## 3. 수동 커밋 — 커밋 시점을 코드가 통제한다

정석은 자동 커밋을 끄고, **처리가 끝난 뒤에** 명시적으로 커밋하는 것이다.

```java
// enable.auto.commit=false
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(timeout);
    for (var record : records) {
        process(record);       // ① 먼저 처리
    }
    consumer.commitSync();     // ② 처리 성공 후 커밋
}
// 처리 후 커밋 = 커밋 전에 죽으면 다시 받는다 → 유실 없음, 중복 가능
// = at-least-once. 중복은 멱등 컨슈머로 방어한다(11번 문서).
```

- `commitSync()`: 커밋 성공/실패를 확인할 때까지 블로킹하고, 일시
  오류면 재시도한다. 느리지만 확실하다.
- `commitAsync()`: 논블로킹으로 커밋 요청만 보낸다. 빠르지만 실패해도
  재시도하지 않는다 — 재시도하면 나중 커밋이 먼저 도착한 뒤 이전
  커밋이 덮어써서 오프셋이 뒤로 가는 역전이 생길 수 있어서다.
- 실무 패턴 (가산점 포인트): **평상시 루프에서는 commitAsync로 지연을
  줄이고, 종료·리밸런스 직전(finally 블록, `onPartitionsRevoked`)에는
  commitSync로 마지막 오프셋을 확실히 남긴다.** async 커밋 하나가
  실패해도 다음 커밋이 더 큰 오프셋으로 덮어주므로 평시에는 문제가
  안 되고, "마지막 커밋"만 확실하면 되기 때문이다.

Spring Kafka를 쓴다면: 컨테이너의 `AckMode` 기본값(BATCH)은 리스너가
정상 리턴한 뒤 커밋하는 방식이라 **프레임워크가 "처리 후 커밋"을 이미
구현해 둔 것**이다. 즉 Spring Kafka의 기본 동작은 순수 클라이언트의
자동 커밋과 다르며 at-least-once에 가깝다. `MANUAL`/`MANUAL_IMMEDIATE`로
바꾸면 리스너 코드가 `Acknowledgment.acknowledge()`를 부르는 시점까지
직접 통제할 수 있다.

## 4. 커밋 시점 = 전달 보장의 선택

커밋 시점을 정하는 것은 결국 장애 시 무엇을 감수할지 정하는 것이다:

| 커밋 시점 | 장애 시 결과 | 성향 |
|---|---|---|
| 처리 **전** 커밋 (자동 커밋의 유실 구조) | 못 다시 받음 → 유실 | at-most-once |
| 처리 **후** 커밋 (수동 커밋 정석) | 다시 받음 → 중복 | at-least-once |

"유실 없음 + 중복 없음"을 커밋 시점만으로 만들 수는 없다. 그래서 실무
결론은 **처리 후 커밋으로 유실을 막고, 중복은 멱등 처리로 흡수**하는
것이다. 전달 의미론 전체 그림은 07번 문서, 멱등 구현은 11번 문서에서
다룬다.

## 5. 꼬리질문 대비 포인트

### "커밋을 아예 안 하면 어떻게 되나?"

실행 중에는 아무 문제가 없어 보인다. 컨슈머는 메모리 안의 position으로
계속 읽어나가기 때문이다. 문제는 재시작·리밸런스 시점 — 커밋된 오프셋이
없으면 `auto.offset.reset` 설정을 따른다. `earliest`면 파티션 처음부터
전량 재처리(중복 폭탄), `latest`(기본값)면 재시작 사이에 쌓인 메시지를
전부 건너뛴다(유실). 즉 커밋은 "지금 읽기"가 아니라 "다음에 어디서
이어받을지"를 위한 장치라는 걸 짚으면 이해도가 드러난다.

### "commitSync와 commitAsync의 차이는? 실무에선 뭘 쓰나?"

sync는 브로커 응답까지 블로킹 + 일시 오류 재시도, async는 논블로킹 +
재시도 없음. async가 재시도하지 않는 이유는 오프셋 커밋의 순서 역전
(늦게 보낸 큰 오프셋이 먼저 커밋되고, 재시도된 작은 오프셋이 그걸
덮어쓰는) 을 막기 위해서다. 실무 패턴은 루프에서 async, 종료와
`onPartitionsRevoked`에서 sync — 평시 커밋 하나쯤 실패해도 다음 커밋이
덮어주지만, 파티션을 내놓기 직전의 마지막 커밋은 확실해야 리밸런스 후
중복 폭이 최소화되기 때문이다.

### "자동 커밋이라도 동기 루프면 유실은 없는 것 아닌가?"

맞다 — 커밋이 다음 poll 시점에 일어나므로 동기 루프에서는 "직전 배치
처리 완료 후 커밋"이 되어 사실상 at-least-once다. 이걸 아는지가 정확한
이해의 척도다. 다만 그 안전은 코드 구조가 우연히 만들어준 것이지 보장이
아니다: 처리를 스레드풀에 넘기거나, 예외를 삼키고 루프를 계속 돌리는
순간 유실 구조로 바뀐다. 즉 위험의 본질은 "자동 커밋 자체"가 아니라
**커밋 시점을 코드가 통제하지 못한다는 것** — 그래서 처리 방식이
바뀌어도 보장이 유지되도록 수동 커밋으로 시점을 명시하는 것이 정석이다,
라고 답하면 원리로 답하는 인상을 준다.

### "배치로 받아서 컨슈머 내부에서 병렬 처리하면 커밋은 어떻게 다루나?" (시니어 변별 포인트)

병렬화하는 순간 "배치의 마지막 오프셋 커밋"은 위험해진다. 뒤쪽 오프셋
레코드가 먼저 끝나고 앞쪽이 아직 처리 중일 때 마지막 오프셋을 커밋하면,
크래시 시 앞쪽 미처리 레코드가 유실된다. 원칙은 **"연속으로 처리 완료된
가장 낮은 오프셋까지만" 커밋**하는 것이다 — 처리 완료 오프셋들을
추적하다가 앞에서부터 끊김 없이 이어진 지점(예: 1,2,3 완료 + 5 완료,
4 미완료 → 3까지만 커밋)을 계산해 커밋한다. 파티션별로 순서를 유지하는
executor를 쓰면 파티션 단위 순차성이 남아 이 관리가 단순해진다.
"병렬화가 처리량을 올리는 대신 커밋 관리 복잡도를 사는 것"이라는
트레이드오프를 말할 수 있으면 컨슈머 구현 레벨을 다뤄본 사람이다.

## 한 줄 요약

오프셋 커밋은 컨슈머 그룹의 책갈피이고, 자동 커밋의 위험은 그 책갈피를
"처리 완료"가 아니라 "시간 주기"로 꽂는다는 것이다 — 책갈피가 실제 읽은
곳보다 앞서면 유실, 뒤처지면 중복이며, 실무 정석은 처리 후 수동 커밋으로
유실을 막고 그 대가인 중복을 멱등 처리로 흡수하는 것이다.
