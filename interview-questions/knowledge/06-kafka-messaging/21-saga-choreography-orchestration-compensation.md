# Saga 패턴 — choreography vs orchestration, 그리고 보상의 함정

> 핵심 관전 포인트: **Saga는 여러 서비스에 걸친 작업을 하나의 분산
> 트랜잭션으로 묶는 대신, 서비스별 로컬 트랜잭션의 연쇄로 진행하고
> 중간에 실패하면 이미 커밋된 단계들을 보상 트랜잭션으로 되돌리는
> 패턴이다. choreography는 중앙 지휘자 없이 각 서비스가 이벤트를 구독해
> 스스로 반응하는 방식 — 결합은 낮지만 전체 흐름이 코드 어디에도 없다.
> orchestration은 오케스트레이터가 순서와 보상을 지휘하는 방식 — 흐름이
> 한눈에 보이지만 중앙 컴포넌트가 생긴다. 그리고 보상은 rollback이
> 아니라 "반대 방향의 새로운 비즈니스 행위"라서 — 보상 자체가 실패할 수
> 있고, 멱등해야 하고, 보상이 아예 불가능한 동작(이미 발송된 알림)이
> 존재한다는 것까지 설계에 넣어야 한다.**

---

## 0. 질문 + 의도

**질문**: "Saga 패턴(choreography vs orchestration)을 비교하고, 보상 트랜잭션 설계 시 주의점을 설명해주세요."

**출제 의도**: 분산 트랜잭션의 실무 대안을 아는 것에 더해, 보상의
함정(보상 자체의 실패, 보상 불가능한 동작 — 이미 발송된 알림)까지
짚는지 본다. 해법의 한계를 아는 것이 진짜 이해의 증거다.

## 1. 왜 필요한가 — 분산 트랜잭션(2PC)이 답이 아닌 이유

주문 하나가 여러 서비스를 거친다고 하자:
**주문 생성 → 결제 승인 → 재고 차감 → 배송 접수.**
각 서비스는 자기 DB를 가지므로, 이 넷을 하나의 ACID 트랜잭션으로 묶을
수 없다. 고전적 답인 2PC(two-phase commit)는 실무에서 거의 못 쓴다:

- **블로킹**: prepare 후 코디네이터 응답을 기다리는 동안 모든 참여자가
  락을 쥔 채 멈춘다. 참여자 하나만 느려도 전체가 그 속도가 된다.
- **코디네이터가 단일 장애점**: 코디네이터가 죽으면 참여자들은
  커밋도 롤백도 못 하는 in-doubt 상태로 남는다.
- 애초에 Kafka나 대부분의 최신 저장소·외부 API는 XA(분산 트랜잭션
  프로토콜)에 참여하지 않는다.

Saga는 접근을 뒤집는다 — **원자성을 포기하고, 각 단계를 즉시 커밋되는
로컬 트랜잭션으로 진행하되, 실패 시 "이미 커밋된 것들을 의미적으로
되돌리는" 보상 트랜잭션을 준비해 둔다.**

```text
정상:  주문 생성 → 결제 승인 → 재고 차감 → 배송 접수 ✓
실패:  주문 생성 → 결제 승인 → 재고 차감 ✗ (품절)
보상:            ← 결제 취소(환불) ← 주문 실패 처리
       (커밋 완료된 단계를 역순으로 되돌린다)
```

## 2. choreography vs orchestration — 지휘자 없는 춤 vs 지휘자 있는 오케스트라

### Choreography (안무) — 이벤트 구독으로 각자 반응

중앙 조정자가 없다. 각 서비스가 앞 단계의 이벤트를 구독해서
자기 일을 하고 다음 이벤트를 발행한다.

```text
주문 서비스: OrderCreated 발행
결제 서비스: OrderCreated 구독 → 결제 → PaymentCompleted 발행
재고 서비스: PaymentCompleted 구독 → 차감 → StockReserved 발행
             (실패 시 StockReservationFailed 발행)
결제 서비스: StockReservationFailed 구독 → 환불 (보상)
주문 서비스: StockReservationFailed 구독 → 주문 실패 처리 (보상)
```

### Orchestration (지휘) — 오케스트레이터가 순서·보상을 관리

오케스트레이터(별도 컴포넌트 또는 주문 서비스 내 saga 관리 모듈)가
각 서비스에 커맨드를 보내고 응답을 받아 다음 단계 또는 보상을 결정한다.

```text
오케스트레이터: 결제해라 → [결제 서비스] → 완료
오케스트레이터: 재고 차감해라 → [재고 서비스] → 실패!
오케스트레이터: (saga 상태를 보고) 결제 취소해라 → [결제 서비스]
오케스트레이터: 주문 실패 처리 → 종료
```

### 비교와 선택 기준

| 관점 | Choreography | Orchestration |
|---|---|---|
| 전체 흐름 파악 | 어디에도 없음 — 이벤트 구독 관계를 다 뒤져야 보임 | 오케스트레이터 코드 한 곳에 있음 |
| 결합도 | 낮음 — 서로 이벤트만 알면 됨 | 오케스트레이터가 모든 참여자를 앎 |
| 단계 추가/변경 | 구독만 추가하면 되지만, 영향 범위 파악이 어려움 | 오케스트레이터 수정으로 명시적 |
| 실패/보상 로직 | 각 서비스에 분산 — 누락되기 쉬움 | 한곳에서 관리 — 상태 추적·타임아웃 걸기 쉬움 |
| 추가 컴포넌트 | 없음 | 오케스트레이터(상태 저장 포함) 필요 |
| 위험 요소 | 순환 구독, 암묵적 흐름, "이 이벤트 지우면 뭐가 깨지지?" | 오케스트레이터에 비즈니스 로직 집중·비대화 |

선택 기준을 한 줄로: **참여 서비스 2~3개에 흐름이 직선이면
choreography로 가볍게, 단계가 많거나 조건 분기·타임아웃·보상 조합이
복잡하면 orchestration.** choreography로 시작한 saga가 커지면서
"전체 그림을 아는 사람이 아무도 없는" 상태가 되는 것이 실무에서 가장
흔한 실패 경로다.

## 3. 보상 트랜잭션 설계 시 주의점 — 여기가 진짜 시험대

### ① 보상은 rollback이 아니라 새로운 비즈니스 행위다

DB rollback은 "없었던 일"로 만들지만, 보상은 이미 커밋되고 외부에
노출된 결과를 **반대 방향의 새 트랜잭션**으로 상쇄하는 것이다.
결제 취소는 결제가 없었던 게 아니라 "결제 후 환불"이라는 새 이력이다.
따라서 보상도 정식 비즈니스 로직으로 — 이력, 정산, 알림까지 —
설계해야 한다.

### ② 보상 자체가 실패할 수 있다

환불 API가 그 순간 죽어 있으면? 보상 실패를 그냥 버리면 **돈은 받고
물건은 안 주는** 상태로 영구히 남는다.

```text
Before: 보상 호출 1회 → 실패 시 로그만 남기고 종료   // 정합성 구멍
After:  보상은 재시도 큐로 — 성공할 때까지 재시도(멱등 전제)
        + N회 초과 시 수동 개입 큐 적재 + 운영 알림
        // 보상의 실패 경로까지 설계해야 saga가 완성된다
```

### ③ 멱등성 — 보상이 두 번 실행돼도 안전해야 한다

이벤트는 at-least-once로 전달되고, 재시도도 있으므로 **같은 보상이
중복 실행되는 것은 정상 상황**이다. 환불이 두 번 나가면 그게 새 장애다.
sagaId(또는 주문 ID) 기준 처리 이력으로 중복을 걸러 멱등하게 만든다.

### ④ 보상 불가능한 동작이 있다 — 실행 순서로 푼다

이미 발송된 이메일·푸시 알림, 외부사에 전송된 확정 통보는 되돌릴 수
없다. 해법은 보상이 아니라 **단계 배치 순서**다:

- 실패 가능성이 있는 단계(결제, 재고)를 앞에 두고,
- **되돌릴 수 없는 단계(알림 발송, 외부 확정 통보)는 saga의 마지막**,
  즉 더 이상 실패로 인한 보상이 없을 위치에 둔다.
- 이때 "이 단계 이후로는 보상 없이 앞으로만 간다"는 분기점을
  **피벗(pivot) 트랜잭션**이라 부른다. 피벗 이후의 단계는 실패하면
  보상이 아니라 **성공할 때까지 재시도**로 설계한다(재시도 가능
  단계만 피벗 뒤에 배치). (가산점 포인트)

### ⑤ 격리성이 없다 — 중간 상태가 노출된다

Saga의 각 단계는 즉시 커밋되므로, 다른 요청이 **아직 완주하지 못한
saga의 중간 상태를 읽고 행동할 수 있다**(예: 결제 완료됐지만 재고
실패로 곧 취소될 주문을 "결제 완료"로 보고 포인트 적립).
대응은 **semantic lock** — 확정 전 상태를 `PENDING` 같은 명시적 상태로
표시하고, 다른 로직이 PENDING 상태를 확정치로 취급하지 않게 한다.
확정 상태 전이는 saga 완료 시점에만 일어난다.

### ⑥ saga에도 실행 상태와 타임아웃이 필요하다

응답이 영원히 안 오는 단계가 있으면 saga는 미완주로 표류한다.
saga 인스턴스별 상태(어느 단계까지 갔는지)를 저장소에 영속화하고,
단계별 타임아웃 초과 시 보상 또는 알림으로 전이시킨다.
orchestration이 유리한 이유 중 하나가 이 상태 관리가 자연스럽다는 점이다.

## 4. 꼬리질문 대비 포인트

### "choreography에서 전체 흐름이 안 보이는 문제는 어떻게 보완하나요?"

correlation ID(sagaId)를 모든 이벤트에 실어 분산 추적으로 한 saga의
여정을 조회 가능하게 하고, 이벤트 스키마·구독 관계를 문서/카탈로그로
관리한다. 다만 이는 관측을 돕는 것이지 흐름을 한곳에 모으지는 못한다 —
분기·보상 조합이 계속 늘어나면 orchestration으로 전환하는 것이 정답인
시점이 온다. "보완하다가 한계가 오면 패턴을 바꾼다"까지 말하는 것이
균형 잡힌 답이다.

### "오케스트레이터가 죽으면 saga는 어떻게 되나요?"

오케스트레이터를 무상태로 만들고 **saga 상태를 DB에 영속화**하는 것이
전제다 — 각 단계 전이를 상태 저장과 함께 커밋하면, 재기동 후 미완주
saga를 읽어 이어서 진행하거나 타임아웃 보상으로 전이할 수 있다.
상태가 메모리에만 있는 오케스트레이터는 재배포 한 번에 표류 saga를
양산한다. 커맨드 발행과 상태 저장의 원자성은 결국 outbox 패턴으로
푼다는 점을 연결하면 좋다. (가산점 포인트)

### "2PC를 쓰면 안 되는 건가요? Saga가 항상 우월한가요?" (시니어 변별 포인트)

항상은 아니다. Saga는 원자성과 격리성을 포기하는 대가로 가용성과 낮은
결합을 얻는 선택이다 — 중간 상태 노출, 보상 로직 개발·테스트 비용,
운영 복잡도(표류 saga 추적)가 전부 청구서로 돌아온다. 참여자가 모두
같은 DB라면 그냥 로컬 트랜잭션 하나로 묶는 게 정답이고, 강한 정합성이
필수인데 참여자가 XA를 지원하는 폐쇄적 환경이면 2PC도 선택지다.
"서비스가 분리돼 있고, 중간 상태를 도메인이 허용할 수 있을 때 Saga를
쓴다"는 적용 조건을 말하는 것이 해법 나열보다 중요하다.

### "보상 트랜잭션과 재시도는 어떻게 구분해서 쓰나요?"

실패의 종류로 가른다 — 일시적 실패(타임아웃, 일시 장애)는 **재시도**로
같은 방향을 계속 밀고, 비즈니스적 거절(품절, 한도 초과)은 재시도해도
결과가 같으므로 **보상**으로 방향을 뒤집는다. 이 구분이 없으면 품절을
무한 재시도하거나, 순간 타임아웃에 멀쩡한 결제를 환불하는 일이 생긴다.
피벗 이후 단계는 보상이 없으므로 재시도 가능한 실패만 오도록
설계돼 있어야 한다는 점과 이어진다.

## 한 줄 요약

Saga는 분산 트랜잭션 대신 "로컬 트랜잭션의 연쇄 + 실패 시 역순 보상"으로
가는 패턴이고 — 흐름이 단순하면 이벤트 구독(choreography), 복잡하면 중앙
지휘(orchestration)를 택하되 — 보상은 rollback이 아닌 새 비즈니스 행위라서
**보상의 실패·중복·불가능(비가역 단계는 맨 뒤로)까지 설계해야 비로소
완성된다.**
