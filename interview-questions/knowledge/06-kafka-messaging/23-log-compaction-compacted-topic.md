# Log Compaction — 시간이 아니라 "키별 최신값"으로 보존하는 토픽

> 핵심 관전 포인트: **일반 토픽의 리텐션은 "오래된 것부터 지운다"
> (시간/크기 기준)이지만, compacted topic은 "같은 키의 옛 값을
> 지우고 키별 최신값은 영구 보존"한다. 토픽이 이벤트 이력이 아니라
> 키-값 테이블의 스냅샷처럼 동작하게 되는 것 — 새 컨슈머가 처음부터
> 읽으면 전체 최신 상태를 복원할 수 있다. 그래서 컨슈머 오프셋 저장
> (__consumer_offsets), Kafka Streams 상태 저장소의 changelog, CDC
> 스냅샷 토픽, 설정·엔티티 최신 상태 배포처럼 "이력은 필요 없고
> 현재 상태가 필요한" 용도에 맞는다. 단 compaction은 백그라운드에서
> 지연 수행되므로 키당 정확히 1건이 아니라 "최소한 최신값은 있다"는
> 보장이고, 삭제는 null 값(tombstone)으로 표현한다.**

---

## 0. 질문 + 의도

**질문**: "Log compaction(compacted topic)이란? 어떤 용도에 적합한가요?"

**출제 의도**: 리텐션(시간 기반 삭제)과 다른 "키별 최신값 보존"
모델을 아는지 본다. 상태 스냅샷·CDC 토픽의 기반으로, Kafka를 큐가
아니라 로그 저장소로 이해하는 깊이의 표본이다.

## 1. 두 가지 청소 정책 — delete는 "언제까지", compact는 "무엇의 최신만"

Kafka 토픽은 무한히 쌓을 수 없으니 청소 정책(`cleanup.policy`)이
있고, 두 모델의 질문 자체가 다르다:

| 정책 | 지우는 기준 | 남는 것 | 토픽의 성격 |
|---|---|---|---|
| `delete` (기본) | 시간/크기 초과분 (`retention.ms` 등) | 최근 N일치 전부 | **이벤트 이력** (무슨 일이 있었나) |
| `compact` | 같은 키의 구버전 | **키별 최신 레코드** | **상태 스냅샷** (지금 값이 뭔가) |

비유하면 delete는 CCTV 녹화본(7일 지나면 덮어씀), compact는
전화번호부(사람별로 최신 번호만 유지, 옛 번호는 버림)다.

```text
compaction 전 (키:값):   user1:서울  user2:부산  user1:대전  user3:인천  user1:부산
compaction 후:                        user2:부산              user3:인천  user1:부산
                          → user1의 옛 값(서울, 대전)만 제거. 각 키의 최신값은 보존.
                          → 남은 레코드의 오프셋·순서는 그대로 유지된다.
```

핵심 성질: **새 컨슈머가 오프셋 0부터 끝까지 읽으면 모든 키의 최신
상태를 얻는다.** 시간이 아무리 지나도 최신값은 지워지지 않으므로,
토픽 자체가 "재생하면 복원되는 키-값 데이터베이스"가 된다. 이 지점이
"Kafka는 큐가 아니라 로그 저장소"라는 관점의 표본이다.

## 2. 동작 방식 — 백그라운드 청소라서 생기는 성질들

compaction은 쓰기 경로에서 즉시 일어나는 게 아니라, 브로커의
**로그 클리너 스레드가 백그라운드에서 세그먼트를 다시 쓰는** 작업이다.
여기서 실무적으로 중요한 성질들이 나온다:

- **키당 1건 보장이 아니다**: 활성 세그먼트(지금 쓰고 있는 파일)는
  compaction 대상이 아니고, 클리너는 중복 비율(dirty ratio)이
  기준을 넘어야 돈다. 즉 **컨슈머는 같은 키를 여러 번 볼 수 있다** —
  보장은 "최소한 각 키의 최신값은 남아 있다"이지 "최신값만 있다"가
  아니다. 컨슈머는 순서대로 읽으며 같은 키를 덮어쓰는(last-write-wins)
  방식으로 소비해야 한다.
- **키가 필수다**: 키가 없으면 "같은 키의 구버전"이라는 개념 자체가
  성립하지 않는다. compacted topic에는 반드시 의미 있는 키(사용자
  ID, 엔티티 ID)를 실어야 한다.
- **삭제는 tombstone으로**: "이 키를 지워라"는 **값이 null인
  레코드**로 표현한다. compaction이 tombstone 이전의 값들을 제거하고,
  tombstone 자체도 일정 시간(`delete.retention.ms`) 보존 후 제거된다
  — 바로 지우면, 아직 읽는 중인 컨슈머가 "삭제됐다"는 사실 자체를
  놓치기 때문이다. (가산점 포인트)
- `min.compaction.lag.ms`로 "쓰인 지 얼마 안 된 레코드는 compaction
  보류"를 걸 수 있다 — 컨슈머가 중간 상태 변화까지 봐야 하는 경우
  최소 관찰 시간을 확보하는 용도. (가산점 포인트)

## 3. 어디에 적합한가 — "이력이 아니라 현재 상태"가 필요한 곳

판단 기준은 하나다: **컨슈머가 원하는 게 "무슨 일이 있었나"(이력)인가,
"지금 값이 뭔가"(상태)인가.** 후자면 compacted topic이 맞다.

- **`__consumer_offsets`** — Kafka 자신이 컨슈머 그룹의 커밋 오프셋을
  compacted topic에 저장한다. 필요한 건 그룹·파티션별 "마지막 커밋
  오프셋"뿐, 커밋 이력 전체가 아니다 — compaction의 원조 사용처.
- **Kafka Streams 상태 저장소의 changelog** — 로컬 상태(집계값 등)의
  변경을 compacted topic에 백업해 두고, 인스턴스 장애 시 재생해서
  상태를 복원한다. 이력이 아니라 복원이 목적이므로 키별 최신값이면
  충분하다.
- **CDC 테이블 스냅샷 토픽** — Debezium 등으로 DB 테이블을 Kafka에
  미러링할 때, 행(PK)별 최신 상태만 있으면 새 소비 시스템이 토픽
  재생만으로 테이블 전체를 복제할 수 있다.
- **설정·마스터 데이터 배포** — 상품 정보, 환율, 기능 플래그처럼
  여러 서비스가 로컬 캐시로 들고 있어야 하는 데이터. 서비스가 새로
  뜰 때 토픽을 처음부터 읽어 캐시를 웜업하고, 이후 변경분만 반영한다
  — "전체 로드 API + 변경 이벤트"의 두 경로를 토픽 하나로 통합하는
  효과.

반대로 **부적합한 곳**: 주문 이벤트 이력·감사 로그처럼 모든 발생
사실이 의미 있는 데이터(compaction이 중간 이력을 지워버린다), 키가
없는 스트림(클릭 로그), "같은 키의 새 값이 옛 값을 대체한다"고 볼
수 없는 데이터. 이런 곳에 compact를 걸면 **데이터 유실 사고**가 된다
— 청소 정책은 데이터의 의미론을 따라 골라야 한다.

## 4. 꼬리질문 대비 포인트

### "compacted topic을 읽으면 키당 딱 1건만 오나요?"

아니다. 활성 세그먼트는 compaction 대상이 아니고 클리너도 지연·비율
기준으로 돌기 때문에, 아직 정리 안 된 구간에는 같은 키의 레코드가
여러 개 남아 있다. 보장은 "각 키의 최신값이 반드시 있다"까지다.
따라서 컨슈머는 같은 키를 여러 번 받는 것을 전제로, 순서대로 읽으며
마지막 값으로 덮어쓰는 방식(사실상 멱등한 upsert)으로 소비해야 한다.
이 성질을 아는지가 "문서만 읽었나, 써봤나"의 갈림길이다.

### "compacted topic에서 키를 삭제하려면 어떻게 하나요? tombstone은 왜 바로 안 지워지나요?"

값이 null인 레코드(tombstone)를 그 키로 발행한다. compaction이
그 키의 이전 값들을 제거하고 tombstone만 남긴 뒤,
`delete.retention.ms`가 지나면 tombstone도 지운다. 유예를 두는 이유:
토픽을 처음부터 읽는 중인 컨슈머가 있을 때 tombstone이 너무 일찍
사라지면 그 컨슈머는 "키가 삭제됐다"는 사실을 영영 모른 채 옛 값을
살아 있는 상태로 복원해 버린다. 삭제라는 사건 자체를 일정 시간
전파해야 하는 것이다.

### "일반 토픽(retention 길게)으로도 상태 복원이 되는데 왜 compact가 필요한가요?" (시니어 변별 포인트)

두 가지가 다르다. 첫째 비용 — 일반 토픽으로 상태를 복원하려면 전체
변경 이력을 무한 보존해야 해서 저장 용량과 복원 시간이 이력에
비례해 계속 자란다. compacted topic은 크기가 "키 개수 × 레코드
크기"로 수렴해 복원 시간이 상태 크기에 비례한다. 둘째 보장 — 일반
토픽은 retention이 지난 초기 이력이 지워지는 순간 "처음부터 재생하면
전체 상태"라는 성질이 깨진다. 즉 이력이 필요하면 delete 토픽, 상태
복원이 목적이면 compact 토픽 — 목적이 다르면 정책이 다르다. 둘 다
필요하면 이벤트 이력 토픽과 스냅샷용 compacted topic을 분리 운영하는
설계를 언급하면 좋다.

### "compaction 중 오프셋이나 순서가 바뀌지 않나요?"

바뀌지 않는다. compaction은 레코드를 제거만 할 뿐 재배열하지
않으므로 남은 레코드의 오프셋과 상대 순서는 그대로다. 오프셋이 듬성듬성
비게 될 뿐이고, 컨슈머가 지워진 오프셋을 요청하면 그다음 유효한
레코드부터 받는다. "파티션 내 순서 보장"이라는 Kafka의 기본 계약은
compacted topic에서도 유지된다.

### "compaction이 계속 밀리면(클리너가 못 따라가면) 어떤 문제가 생기고 무엇을 보나요?"

정리 안 된 중복 구간이 길어져 디스크 사용량이 늘고, 상태 복원을
위해 처음부터 읽는 컨슈머의 재생 시간이 길어진다. 클리너 스레드
수, `min.cleanable.dirty.ratio`(이 비율을 넘어야 청소 시작 — 낮추면
더 자주 청소하는 대신 I/O 비용 증가), 세그먼트 크기 설정을 점검하고,
브로커의 클리너 관련 지표(미정리 비율, 클리너 동작 여부)를 본다.
클리너가 오류로 멈춰 있는 장애는 조용히 진행되므로 디스크 증가
추세에 알람을 걸어두는 게 실무 포인트다.

---

## 한 줄 요약

log compaction은 "오래된 것 삭제"가 아니라 "같은 키의 구버전 삭제"로,
토픽을 재생하면 전체 최신 상태가 복원되는 키-값 스냅샷으로 만드는
정책이다 — 컨슈머 오프셋·Streams changelog·CDC 스냅샷·설정 배포처럼
이력이 아니라 현재 상태가 필요한 곳에 쓰되, 키당 1건이 아니라 "최신값
보존" 보장이라는 점과 tombstone 삭제 의미론까지 알아야 실전에서 쓸 수
있다.
