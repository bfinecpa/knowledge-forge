# Log Compaction — 시간이 아니라 "키별 최신값"으로 보존하는 토픽

> 핵심 관전 포인트: **일반 토픽의 리텐션은 "오래된 것부터 지운다"(시간/크기 기준)이지만, compacted topic은 "같은 키의 옛 값을 지우고 키별 최신값은 계속 보존"한다. 그래서 토픽이 이벤트 이력이 아니라 키-값 테이블의 스냅샷처럼 동작하고, 새 컨슈머가 처음부터 읽기만 하면 전체 최신 상태가 복원된다 — 컨슈머 오프셋 저장소(`__consumer_offsets`), Kafka Streams 상태 저장소의 changelog, CDC 스냅샷 토픽, 설정·마스터 데이터 배포처럼 "이력은 필요 없고 현재 상태가 필요한" 용도가 여기에 맞는다. 다만 청소는 백그라운드에서 비동기로 돌고 로그의 맨 끝(활성 세그먼트)은 아예 대상이 아니므로 보장은 "키당 정확히 1건"이 아니라 **"최신값은 반드시 남아 있고, 옛 값이 몇 개 더 보일 수 있다"**이다. 따라서 컨슈머는 같은 키를 여러 번 받아도 마지막 값으로 덮어쓰는 멱등한 방식으로 소비해야 하고, 삭제는 값이 null인 레코드(tombstone)로 표현하되 그 tombstone도 일정 기간은 남겨 둬야 나중에 붙는 컨슈머가 삭제 사실을 알 수 있다.**

---

## 0. 질문 + 의도

**질문**: "Log compaction(compacted topic)이란? 어떤 용도에 적합한가요?"

**출제 의도**: 리텐션(시간 기반 삭제)과 다른 "키별 최신값 보존" 모델을 아는지 본다. 상태 스냅샷·CDC 토픽의 기반으로, Kafka를 큐가 아니라 로그 저장소로 이해하는 깊이의 표본이다.

## 1. 두 가지 청소 정책 — delete는 "언제까지", compact는 "무엇의 최신만"

### 1-1. 전제 지식 — 파티션은 append-only 로그이고, 세그먼트 파일로 쪼개져 있다

compaction을 이해하려면 Kafka가 데이터를 어떻게 들고 있는지부터 알아야 한다.

파티션은 **append-only 로그**다. 끝에 덧붙이기만 하고 중간을 고치지 않는 파일이라는 뜻이다. 각 레코드에는 0부터 하나씩 증가하는 위치 번호가 붙고, 이 번호가 **오프셋(offset)**이다.

그런데 파티션이 파일 하나로 무한히 커지면 관리가 불가능하다. 그래서 Kafka는 파티션을 **세그먼트(segment)**라는 여러 개의 파일로 잘라 저장한다. 일정 크기나 시간에 도달하면 현재 파일을 닫고 새 파일을 연다. 지금 프로듀서가 쓰고 있는 마지막 세그먼트를 **활성 세그먼트(active segment)**라고 부른다.

이 구조가 중요한 이유는, **Kafka의 청소가 "레코드 하나 지우기"가 아니라 "세그먼트 파일 단위의 작업"**이기 때문이다. 2절에서 볼 compaction의 실무적 성질 대부분이 여기서 나온다.

로그를 무한히 쌓을 수는 없으므로 토픽에는 청소 정책(`cleanup.policy`)이 있다. 그리고 두 정책은 **던지는 질문 자체가 다르다.**

| 정책 | 지우는 기준 | 남는 것 | 토픽의 성격 |
|---|---|---|---|
| `delete` (기본) | 시간/크기 초과분 (`retention.ms` 등) | 최근 N일치 전부 | **이벤트 이력** (무슨 일이 있었나) |
| `compact` | 같은 키의 구버전 | **키별 최신 레코드** | **상태 스냅샷** (지금 값이 뭔가) |

`delete`는 **"언제까지 보관할까"**를 묻는다. 7일이 지났으면 그 안에 무슨 값이 들었든 지운다. `compact`는 **"무엇의 최신값만 남길까"**를 묻는다. 아무리 오래됐어도 그 키의 최신값이면 남기고, 방금 쓴 것이라도 같은 키의 더 새 값이 있으면 지운다. **시간이 기준이 아니라 키가 기준**이라는 것이 전환점이다.

### 1-2. 비유와 동작 예시

`delete`는 **CCTV 녹화본**이다. 7일 지나면 앞부터 덮어쓴다. 무슨 장면이 찍혔는지는 상관없고 오직 시간이 기준이다.

`compact`는 **전화번호부**다. 사람마다 최신 번호 하나만 유지하고 옛 번호는 버린다. 5년 전에 등록한 번호라도 그 사람의 현재 번호면 남고, 어제 적었더라도 오늘 바뀌었으면 지운다.

실제로 어떤 레코드가 사라지는지 오프셋과 함께 보면 이렇다.

```
compaction 전
  offset:  0          1          2          3          4
  키:값:   user1:서울  user2:부산  user1:대전  user3:인천  user1:부산

compaction 후
  offset:  -          1          -          3          4
  키:값:              user2:부산             user3:인천  user1:부산

  → user1의 옛 값(offset 0의 서울, offset 2의 대전)만 제거됐다.
     각 키의 최신값(user1:부산, user2:부산, user3:인천)은 보존된다.
```

### 1-3. 오프셋은 유지되고 구멍이 생긴다

위 도식에서 놓치면 안 되는 성질이 하나 있다. **레코드가 지워져도 남은 레코드의 오프셋 번호는 바뀌지 않는다.**

compaction 후에 남은 세 건이 0, 1, 2로 다시 번호를 받지 않는다. 원래 갖고 있던 1, 3, 4를 그대로 유지한다. 그래서 이 로그를 순서대로 읽으면 오프셋이 **1, 3, 4처럼 듬성듬성 건너뛴다.** 지워진 자리는 그냥 구멍으로 남는다.

이게 왜 문제가 되지 않는지를 설명할 수 있어야 한다. **오프셋은 "이 파티션 안에서의 위치"를 가리키는 번호일 뿐, 연속성을 약속한 적이 없다.** 컨슈머는 "오프셋 2번을 주세요"라고 요청하지 않는다. "오프셋 2 이후의 것들을 주세요"라고 요청하고, 브로커는 그 지점 이후로 **실제로 존재하는 다음 레코드**부터 돌려준다. 지워진 오프셋을 요청해도 오류가 나지 않고 그다음 유효한 레코드로 넘어간다.

그리고 **순서는 절대 바뀌지 않는다.** compaction은 레코드를 제거만 할 뿐 재배열하지 않는다. 그래서 "파티션 안에서 쓰인 순서대로 읽힌다"는 Kafka의 기본 계약은 compacted topic에서도 그대로 유지된다. 이것이 뒤에서 볼 "마지막 값으로 덮어쓰면 된다"는 소비 전략의 근거가 된다 — 순서가 보장되니 **나중에 읽은 값이 곧 더 새로운 값**이다.

### 1-4. 그래서 토픽이 데이터베이스가 된다

여기까지 오면 compacted topic의 핵심 성질이 나온다. **새 컨슈머가 오프셋 0부터 끝까지 읽으면 모든 키의 최신 상태를 얻는다.**

시간이 아무리 지나도 최신값은 지워지지 않으므로, 토픽 자체가 **"재생하면 복원되는 키-값 데이터베이스"**가 된다. 일반 토픽이었다면 리텐션이 지난 초기 이력이 사라지는 순간 이 성질이 깨진다 — 처음 등록된 뒤 한 번도 안 바뀐 키의 값은 초기 이력에만 있으니, 그 구간이 지워지면 재생해도 그 키를 복원할 수 없다.

**"Kafka는 큐가 아니라 로그 저장소"**라는 관점의 가장 선명한 표본이 이 지점이다. 큐는 읽으면 비지만, 이 토픽은 읽어도 남고 심지어 그것으로 상태를 복원한다.

## 2. 동작 방식 — 백그라운드 청소라서 생기는 성질들

### 2-1. 로그 클리너 — 언제, 무엇을 청소하는가

compaction은 프로듀서가 쓰는 순간 일어나지 않는다. 브로커의 **로그 클리너(log cleaner) 스레드**가 백그라운드에서 세그먼트 파일들을 읽어 **새 파일로 다시 쓰는** 작업이다. 같은 키의 옛 레코드를 빼고 다시 쓴 뒤 옛 파일을 교체하는 식이다.

이 "비동기로 따로 돈다"는 사실에서 실무적으로 가장 중요한 성질이 나온다. 로그를 세 구간으로 나눠 보면 명확해진다.

```
파티션의 로그 (왼쪽이 오래된 것, 오른쪽이 최신)

 ◀────────── 클리너의 작업 대상 ──────────▶│◀── 활성 세그먼트 ──▶
 ┌─────────────────┬──────────────────────┐┌───────────────────┐
 │   clean 구간     │     dirty 구간       ││  지금 쓰이는 파일  │
 │                 │                      ││                   │
 │ 이미 청소됨      │ 청소된 적 없는       ││ 프로듀서가 여기에  │
 │ 키당 1건만 남음  │ 새 레코드들          ││ append 하는 중     │
 │                 │ 같은 키가 여러 번     ││ 같은 키가 여러 번  │
 │                 │ 있을 수 있다          ││ 있을 수 있다       │
 └─────────────────┴──────────────────────┘└───────────────────┘
                    └─ dirty 비율이 기준을    └─ 절대 청소 대상이
                       넘어야 클리너가 돈다      되지 않는다
```

**활성 세그먼트는 compaction 대상이 아니다.** 지금 프로듀서가 쓰고 있는 파일을 클리너가 동시에 다시 쓰면 충돌이 나기 때문이다. 그래서 로그의 맨 끝부분은 언제나 청소되지 않은 상태로 남아 있다.

**클리너는 "지저분한 정도"가 기준을 넘어야 돈다.** 여기서 지저분한 정도가 **dirty ratio** — 전체 대비 아직 청소 안 된 구간의 비율이다. 이 비율이 `min.cleanable.dirty.ratio`를 넘어야 청소가 시작된다. 매번 도는 게 아니라 청소할 값어치가 생겼을 때 도는 것이다. 매 레코드마다 파일을 다시 쓰면 디스크 I/O가 감당이 안 되므로 당연한 설계다.

### 2-2. 그래서 "키당 정확히 1건"이 아니다 — 이 문서의 급소

두 성질을 합치면 결론이 나온다. **컨슈머가 읽는 시점에 같은 키의 옛 값이 아직 남아 있을 수 있다.**

활성 세그먼트에 있는 것은 아예 청소된 적이 없고, dirty 구간에 있는 것은 기준을 넘지 않아 아직 청소되지 않았다. 방금 같은 키로 다섯 번을 썼다면 그 다섯 건이 전부 그대로 읽힐 수 있다.

그러므로 정확한 보장은 이렇게 말해야 한다.

```
[틀린 표현] compacted topic에는 키당 1건만 있다
[맞는 표현] 각 키의 최신값은 반드시 남아 있다.
            그 앞에 옛 값이 몇 개 더 보일 수 있고, 몇 개일지는 정해져 있지 않다.
```

보장되는 것은 **하한(최신값은 있다)**이지 상한(그것만 있다)이 아니다. 이 차이가 문서만 읽은 사람과 써 본 사람을 가른다.

### 2-3. 컨슈머는 멱등하게 — 마지막 값으로 덮어쓰기

보장이 저러하므로 **컨슈머는 같은 키를 여러 번 받아도 문제가 없는 방식으로 처리해야 한다.** 여기서 **멱등(idempotent)**은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"을 말한다.

compacted topic의 소비에서 멱등한 방식은 명확하다. **순서대로 읽으면서 같은 키를 만나면 마지막 값으로 덮어쓴다(last-write-wins).** 1-3에서 본 순서 보장이 이걸 가능하게 한다 — 나중에 읽은 것이 더 새로운 값임이 보장되므로, 그냥 덮어쓰기만 하면 끝에 도달했을 때 남는 것이 최신값이다.

```java
// Before: "키당 1건"이라고 믿고 짠 코드 — 같은 키가 두 번 오면 깨진다
@KafkaListener(topics = "user-region", groupId = "region-cache")
public void onMessage(ConsumerRecord<String, String> record) {
    if (cache.containsKey(record.key())) {
        // "compacted니까 키당 1건일 텐데 왜 또 오지?" 하고 예외를 던지거나
        // 무시해 버린다. 무시하면 옛 값을 붙잡고 최신값을 버리게 된다.
        throw new IllegalStateException("중복 키: " + record.key());
    }
    cache.put(record.key(), record.value());
}

// After: 여러 번 와도 결과가 같다 — 마지막 값이 이긴다
@KafkaListener(topics = "user-region", groupId = "region-cache")
public void onMessage(ConsumerRecord<String, String> record) {
    if (record.value() == null) {
        // 값이 null인 레코드(tombstone)는 "이 키는 삭제됐다"는 뜻이다.
        // 값으로 null을 저장하는 게 아니라 항목 자체를 없애야 한다.
        cache.remove(record.key());
        return;
    }
    // 순서가 보장되므로 나중에 읽은 값이 더 새 값이다.
    // 같은 키가 세 번 와도 마지막 것만 남으니 결과는 한 번 온 것과 같다.
    cache.put(record.key(), record.value());
}
```

DB에 반영하는 경우도 원리가 같다. INSERT가 아니라 **upsert**로 쓴다.

```sql
-- PostgreSQL: 같은 키가 여러 번 와도 결과가 같다
INSERT INTO user_region (user_id, region, updated_at)
VALUES (:userId, :region, now())
ON CONFLICT (user_id)
DO UPDATE SET region = EXCLUDED.region, updated_at = now();
```

### 2-4. 키가 없으면 성립하지 않는다

**compacted topic에는 반드시 의미 있는 키가 있어야 한다.** 키가 없으면 "같은 키의 구버전"이라는 개념 자체가 성립하지 않기 때문이다.

키는 사용자 ID, 엔티티 ID처럼 **"이 레코드가 무엇의 상태를 나타내는가"를 식별하는 값**이어야 한다. 키를 안 실으면(null 키) 청소할 근거가 없고, 키를 아무렇게나 실으면(예: 랜덤 UUID) 모든 레코드가 서로 다른 키가 되어 아무것도 지워지지 않는다 — 정책만 걸었을 뿐 사실상 무한 보존 토픽이 된다.

### 2-5. 삭제는 tombstone으로 — 그리고 왜 바로 지우면 안 되는가

키를 지우고 싶을 때는 어떻게 하는가. compacted topic에서는 "지운다"는 명령이 없다. 로그는 append-only이므로 **지웠다는 사실을 새 레코드로 덧붙이는** 수밖에 없다.

그 레코드가 **tombstone(툼스톤, 묘비)**이다. **값이 null인 레코드**로, "이 키는 삭제됐다"를 나타낸다. 묘비라는 이름 그대로 **"여기 있던 것이 지워졌다"는 표식**이다 — 시신은 없지만 누가 여기 있었고 지금은 없다는 사실을 알려 주는 돌이다.

```
프로듀서: send(key="user1", value=null)   ← 이것이 tombstone

로그:  ... user1:서울 ... user1:대전 ... user1:null
                                          ↑
       compaction이 돌면 앞의 user1 값들이 제거되고 tombstone만 남는다
       그다음 delete.retention.ms가 지나면 tombstone도 제거된다
```

여기서 반드시 짚어야 할 질문이 나온다. **tombstone은 왜 바로 지우지 않고 일정 기간 남겨 두는가.**

앞의 값들을 다 지웠으니 tombstone도 같이 지워도 될 것 같다. 그런데 그러면 안 되는 이유가 있다. **지금 오프라인인 컨슈머 때문이다.**

```
t0  user1의 값이 로그에 있다.  컨슈머 X는 이미 읽어서 캐시에 user1=서울을 갖고 있다.
t1  컨슈머 X가 다운된다. (배포, 장애, 아직 안 뜬 신규 인스턴스)
t2  tombstone 발행 — user1 삭제.
t3  compaction이 돌아 user1의 옛 값들을 제거하고 tombstone만 남긴다.
t4  ★ 여기서 tombstone까지 즉시 지워 버리면?
t5  컨슈머 X가 복귀해 로그를 읽는다.
    → user1에 관한 레코드가 로그 어디에도 없다.
    → "삭제됐다"는 정보를 영영 받지 못하고, 캐시의 user1=서울을 그대로 들고 있다.
    → 삭제된 사용자가 이 서비스에서만 영원히 살아 있게 된다.
```

**삭제는 "값이 없는 상태"가 아니라 "삭제됐다는 사건"이고, 그 사건도 전파되어야 한다.** 그래서 tombstone은 `delete.retention.ms` 동안 로그에 남아 있다가 제거된다. 이 값은 사실상 **"컨슈머가 이만큼은 밀려 있어도 삭제 사실을 놓치지 않는다"고 보장하는 시간**이다. 오프라인 상태가 이 시간을 넘긴 컨슈머는 캐시를 통째로 버리고 처음부터 다시 읽어야 안전하다. (가산점 포인트)

### 2-6. 중간 상태를 봐야 하는 컨슈머를 위한 유예

반대 방향의 요구도 있다. **컨슈머가 값의 중간 변화까지 봐야 하는 경우**다. 예를 들어 "주문 상태가 PAID를 거쳐 SHIPPED가 됐다"를 전부 봐야 하는 컨슈머에게, compaction이 PAID를 지워 버리고 SHIPPED만 남기면 중간 단계를 놓친다.

이를 위해 `min.compaction.lag.ms`로 **"쓰인 지 얼마 안 된 레코드는 compaction을 보류"**시킬 수 있다. 최소 관찰 시간을 확보하는 용도다 — 그 시간 안에 붙어 읽는 컨슈머는 중간 상태를 볼 수 있다. (가산점 포인트)

다만 이건 완충 장치이지 보장이 아니다. **이력이 진짜로 필요하면 애초에 compact를 걸면 안 된다**(3-5).

## 3. 어디에 적합한가 — "이력이 아니라 현재 상태"가 필요한 곳

판단 기준은 하나다. **컨슈머가 원하는 게 "무슨 일이 있었나"(이력)인가, "지금 값이 뭔가"(상태)인가.** 후자라면 compacted topic이 맞다.

### 3-1. `__consumer_offsets` — compaction의 원조 사용처

가장 좋은 예가 Kafka 자신이다. 컨슈머 그룹이 "이 파티션을 어디까지 읽었다"를 기록하는 **오프셋 커밋**은 브로커의 별도 메타데이터 저장소가 아니라 **`__consumer_offsets`라는 Kafka 내부 토픽**에 발행된다(자세한 것은 `05-offset-commit-and-auto-commit-risk.md`).

그런데 이 토픽에 필요한 것이 무엇인지 생각해 보자. **`(컨슈머 그룹, 토픽, 파티션)` 조합마다 "마지막으로 커밋한 위치" 하나면 된다.** "이 그룹이 지난 한 달간 커밋해 온 오프셋의 전체 이력"은 아무도 필요로 하지 않는다.

그리고 커밋은 매우 자주 일어난다. 컨슈머 하나가 초당 몇 번씩 커밋하면 그 이력은 순식간에 거대해진다. **필요한 건 마지막 값 하나인데 쌓이는 건 무한한 이력**인 상황 — compaction이 정확히 이걸 위해 만들어진 도구다.

```
키:   (그룹 G, topic-A, 파티션 0)
값:   다음에 읽을 오프셋

로그: ...(G,A,0):100  (G,A,0):150  (G,A,0):200  ...
      compaction 후 → (G,A,0):200 만 남는다
```

브로커가 재시작해도 이 토픽을 재생하면 모든 그룹의 마지막 커밋 위치가 복원된다. **1-4에서 말한 "재생하면 복원되는 키-값 데이터베이스"가 Kafka 내부에서 실제로 이렇게 쓰이고 있다.**

### 3-2. Kafka Streams 상태 저장소의 changelog

Kafka Streams는 집계값 같은 로컬 상태를 인스턴스의 디스크에 들고 처리한다. 그 인스턴스가 죽으면 로컬 상태도 함께 사라지므로, **상태의 변경을 compacted topic에 백업**해 둔다. 이 백업 토픽을 changelog라고 부른다.

인스턴스 장애 시 새 인스턴스가 changelog를 재생해 상태를 복원한다. 목적이 **이력 조회가 아니라 복원**이므로 키별 최신값이면 충분하다.

### 3-3. CDC 테이블 스냅샷 토픽

Debezium 같은 도구로 DB 테이블을 Kafka에 미러링할 때, 행(기본 키)별 최신 상태만 있으면 새로 붙는 소비 시스템이 **토픽 재생만으로 테이블 전체를 복제**할 수 있다. DB에 직접 전체 스캔 쿼리를 날리지 않고도 초기 적재가 되는 것이다.

### 3-4. 설정·마스터 데이터 배포

상품 정보, 환율, 기능 플래그처럼 **여러 서비스가 로컬 캐시로 들고 있어야 하는 데이터**가 여기 해당한다.

서비스가 새로 뜰 때 토픽을 처음부터 읽어 캐시를 웜업하고, 이후에는 도착하는 변경분만 반영한다. **"전체 로드 API + 변경 이벤트 구독"이라는 두 개의 경로를 토픽 하나로 통합하는 효과**가 있다. 초기 적재와 증분 갱신이 같은 코드 경로가 되므로 둘 사이의 불일치(전체 로드와 첫 이벤트 사이에 놓친 변경)도 사라진다.

### 3-5. 부적합한 곳 — 여기에 걸면 데이터 유실 사고다

반대로 compact를 걸면 안 되는 곳이 있다.

- **주문 이벤트 이력, 감사 로그** — 모든 발생 사실이 각각 의미를 갖는 데이터다. compaction이 중간 이력을 지워 버린다. "결제 승인 → 취소 → 재승인"의 중간 단계가 사라지면 감사 자체가 불가능해진다.
- **키가 없는 스트림** — 클릭 로그처럼 키를 붙일 대상이 없는 데이터(2-4).
- **"같은 키의 새 값이 옛 값을 대체한다"고 볼 수 없는 데이터** — 예를 들어 사용자별 포인트 적립 이벤트는 같은 키로 여러 건이 오지만 뒤엣것이 앞엣것을 대체하는 게 아니라 **누적**된다. 여기에 compact를 걸면 마지막 적립만 남고 나머지가 증발한다.

**청소 정책은 데이터의 의미론을 따라 골라야 한다.** compact를 잘못 건 토픽은 조용히 데이터를 지우면서도 아무 오류를 내지 않기 때문에, 사고를 발견하는 시점이 한참 뒤가 된다.

## 4. 꼬리질문 대비 포인트

### "compacted topic을 읽으면 키당 딱 1건만 오나요?"

**아니다.** 이 질문에 "네"라고 답하면 안 된다.

이유는 둘이다(2-1). **활성 세그먼트는 compaction 대상이 아니고**, 클리너도 dirty 비율 기준을 넘어야 도는 **지연 작업**이다. 그래서 아직 정리 안 된 구간에는 같은 키의 레코드가 여러 개 남아 있다.

보장은 **"각 키의 최신값이 반드시 있다"**까지다. 하한만 보장하고 상한은 보장하지 않는다.

따라서 컨슈머는 **같은 키를 여러 번 받는 것을 전제로**, 순서대로 읽으며 마지막 값으로 덮어쓰는 방식(사실상 멱등한 upsert)으로 소비해야 한다. 이 성질을 아는지가 **"문서만 읽었나, 써 봤나"의 갈림길**이다.

### "compacted topic에서 키를 삭제하려면 어떻게 하나요? tombstone은 왜 바로 안 지워지나요?"

**값이 null인 레코드(tombstone)를 그 키로 발행한다.** compaction이 그 키의 이전 값들을 제거하고 tombstone만 남긴 뒤, `delete.retention.ms`가 지나면 tombstone도 지운다.

유예를 두는 이유는 **지금 오프라인이거나 뒤처져 있는 컨슈머** 때문이다(2-5). tombstone이 너무 일찍 사라지면 나중에 붙어 로그를 읽는 컨슈머는 그 키에 관한 레코드를 아예 못 보게 되고, **"삭제됐다"는 사실을 영영 모른 채 자기 캐시의 옛 값을 살아 있는 상태로 유지**해 버린다.

한 문장으로 정리하면 이렇다. **삭제는 "값이 없는 상태"가 아니라 "삭제됐다는 사건"이고, 사건인 이상 일정 시간 전파되어야 한다.**

### "일반 토픽(retention 길게)으로도 상태 복원이 되는데 왜 compact가 필요한가요?" (시니어 변별 포인트)

**된다는 것부터 인정하고 시작한다.** 리텐션을 무한으로 잡은 일반 토픽을 처음부터 재생하면 상태는 복원된다. 이건 맞는 말이다.

문제는 **필요한 것과 읽어야 하는 것의 불일치**다. 상태 복원에 필요한 것은 **최신값뿐인데**, 일반 토픽에서는 그 최신값에 도달하기 위해 **전체 이력을 다 읽어야 한다.** 그래서 저장 용량과 복원 시간이 **이력의 길이에 비례해** 자란다. 반면 compaction은 읽어야 할 양을 **키 개수 수준으로 묶어 준다** — 상태의 크기에 비례하게 만드는 것이다.

숫자를 넣으면 격차가 분명해진다. 키가 100만 개이고 각 키가 평균 100번 바뀌어 변경 이력이 총 1억 건, 레코드 하나가 200바이트라고 하자.

| | 일반 토픽 (무한 리텐션) | compacted topic |
|---|---|---|
| 저장된 레코드 수 | 1억 건 | 약 100만 건 (키 개수로 수렴) |
| 저장 용량 | 1억 × 200B = **20GB** | 100만 × 200B = **200MB** |
| 재생 시간 (5만 건/초 가정) | 2,000초 = **약 33분** | 20초 |

**100배 차이**이고, 이 배수는 곧 **키당 평균 변경 횟수**다. 키가 자주 바뀌는 데이터일수록 격차가 벌어진다. 인스턴스가 뜰 때마다 33분을 기다려야 하는 시스템은 배포도, 오토스케일링도, 장애 복구도 성립하지 않는다.

**둘째 차이는 보장이다.** 일반 토픽은 리텐션이 유한한 순간 **"처음부터 재생하면 전체 상태"라는 성질 자체가 깨진다**(1-4). 한 번 등록되고 안 바뀐 키의 값은 초기 이력에만 있으므로, 그 구간이 리텐션으로 지워지면 재생해도 복원되지 않는다. 그렇다고 무한 리텐션으로 두면 위 표의 20GB가 계속 자란다 — **압박이 사라지는 게 아니라 다른 축으로 옮겨갈 뿐이다.**

정리하면 **이력이 필요하면 delete 토픽, 상태 복원이 목적이면 compact 토픽** — 목적이 다르면 정책이 다르다. 둘 다 필요하다면 **이벤트 이력 토픽과 스냅샷용 compacted topic을 분리 운영**하는 설계를 언급하면 좋다.

### "compaction 중 오프셋이나 순서가 바뀌지 않나요?"

**바뀌지 않는다.** compaction은 레코드를 제거만 할 뿐 재배열하지 않으므로, 남은 레코드의 오프셋 번호와 상대 순서는 그대로다.

달라지는 것은 하나뿐이다. **오프셋이 듬성듬성 비게 된다**(1-3). 0, 1, 2, 3, 4가 아니라 1, 3, 4처럼 건너뛴다.

이것이 문제가 되지 않는 이유는 **오프셋이 위치를 가리키는 번호일 뿐 연속성을 약속한 값이 아니기 때문**이다. 컨슈머가 지워진 오프셋을 요청하면 오류가 아니라 **그다음 유효한 레코드**부터 받는다. 그리고 "파티션 내 순서 보장"이라는 Kafka의 기본 계약은 compacted topic에서도 유지된다 — 이 보장이 있어야 "마지막 값으로 덮어쓰기"가 최신값 복원과 같은 뜻이 된다.

### "compaction이 계속 밀리면(클리너가 못 따라가면) 어떤 문제가 생기고 무엇을 보나요?"

**증상**부터 말한다. 정리 안 된 dirty 구간이 계속 길어져 **디스크 사용량이 예상보다 크게 늘고**, 상태 복원을 위해 처음부터 읽는 컨슈머의 **재생 시간이 길어진다.** 앞의 표에서 본 "200MB / 20초"의 이점이 점점 사라져 일반 토픽 쪽 수치로 되돌아가는 것이다.

**점검 대상**은 셋이다. 클리너 스레드 수, `min.cleanable.dirty.ratio`(이 비율을 넘어야 청소를 시작한다 — 낮추면 더 자주 청소하는 대신 디스크 I/O 비용이 늘어난다), 그리고 세그먼트 크기 설정이다. 세그먼트가 너무 크면 활성 세그먼트가 오래 닫히지 않아 청소 대상에 들어가는 시점 자체가 늦어진다.

**확인 방법**은 브로커가 노출하는 **로그 클리너 관련 지표** — 미정리 비율과 클리너가 실제로 돌고 있는지 — 를 보는 것이다.

실무 포인트를 하나 얹으면 좋다. **클리너 스레드가 오류로 멈춰 버리는 장애는 조용히 진행된다.** 프로듀서도 컨슈머도 아무 오류를 못 느끼고, 디스크가 찰 때까지 아무도 모른다. 그래서 클리너 지표 자체를 보는 것과 별개로 **디스크 사용량 증가 추세에 알람을 걸어 두는 것**이 실질적인 방어선이 된다.

## 한 줄 요약

log compaction은 "오래된 것 삭제"가 아니라 "같은 키의 구버전 삭제"로, 토픽을 재생하면 전체 최신 상태가 복원되는 키-값 스냅샷으로 만드는 정책이다 — 컨슈머 오프셋(`__consumer_offsets`)·Streams changelog·CDC 스냅샷·설정 배포처럼 이력이 아니라 현재 상태가 필요한 곳에 쓰되, 청소가 백그라운드로 돌고 활성 세그먼트는 대상이 아니므로 보장은 "키당 1건"이 아니라 **"최신값은 반드시 있고 옛 값이 더 보일 수 있다"**여서 컨슈머를 last-write-wins로 멱등하게 짜야 하고, 삭제는 tombstone(값이 null인 레코드)으로 표현하되 뒤처진 컨슈머가 삭제 사실을 받을 수 있도록 일정 기간 남겨 둔다는 것까지 알아야 실전에서 쓸 수 있다.
