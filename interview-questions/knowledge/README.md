## 서술 기준 — 시니어의 깊이를 주니어에게 설명한다

**독자**: 3년차 백엔드 개발자. Spring·JPA로 CRUD API는 능숙하게 만들지만 결제·분산 시스템은 처음이고, `@Transactional`은 붙여봤어도 격리 수준이나 락은 깊이 모른다.

**깊이는 낮추지 않는다.** 시니어가 실무에서 부딪히는 실패 시나리오, 트레이드오프, 운영 대응을 그대로 다룬다. 내용을 빼서 쉽게 만드는 것이 아니라 **설명을 더해서** 쉽게 만든다.

**설명 규칙**

- 새 용어는 등장하는 그 자리에서 한 문장으로 정의하고, 가능하면 왜 그런 이름인지까지 덧붙인다. 영문 병기는 정의를 대신하지 못한다.
- 결론("돈 도메인에선 오케스트레이션이 유리하다") 앞에, 선택지가 왜 그것들뿐인지를 먼저 설명한다.
- 한 문단에 새 개념 하나. 여러 개념을 쉼표로 나열해 압축하지 않는다.
- 개념을 꺼내기 전에 전제 지식을 짧게 보충한다. 예: 분산 트랜잭션을 말하기 전에 "단일 DB 트랜잭션이 왜 여기선 안 통하는지" 한 문단.
- 비유는 개념 도입 직후에 둔다.
- 코드 주석도 같은 기준으로 쓴다 — "왜 이 줄이 필요한가"를 설명한다.
- 상태 전이, 타임라인, 계층 구조, 계산 과정은 문장으로만 쓰지 않는다. 텍스트 다이어그램이나 표로 한 번 더 보여준다.

**분량과 줄바꿈은 규칙이 아니다.** 분량은 목표가 아니라 결과다 — 위 규칙을 지키는 데 필요한 만큼 쓰고, 특정 KB를 채우려 문장을 늘리지 않는다. 줄바꿈도 가독성 기준으로 한다. 고정 폭 하드랩(72자 등)을 강제하지 않으며, 문장을 잘라 줄을 맞추는 대신 문단을 짧게 끊어 읽기 쉽게 만든다.

## 문서 형식

- 파일명: `QQ-주제-kebab-case.md` — `QQ`는 해당 질문이 questions 섹션 파일에서 몇 번째 항목인지(2자리, 주석 처리된 항목 제외, 위→아래 순). 예: `32-bigdecimal-equals-compareto.md`. 질문지에 없는 질문(출처 없음)은 번호 없이 주제 슬러그만 쓴다 (예: `transaction-isolation-levels.md`).
- 상단에 `> 핵심 관전 포인트:` 인용 블록 — 면접에서 첫 답변으로 말할 요약
- 본문은 번호 섹션, before/after 코드 예시, 꼬리질문 대비 포인트 포함
- 마지막에 "한 줄 요약" 섹션
