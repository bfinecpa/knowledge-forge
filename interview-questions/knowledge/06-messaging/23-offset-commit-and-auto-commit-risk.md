# 오프셋 커밋과 자동 커밋의 위험 — 커밋 시점이 유실과 중복을 가른다

> 핵심 관전 포인트: **오프셋 커밋은 컨슈머 그룹이 "이 파티션을 어디까지 읽었다"를 브로커에 기록하는 책갈피 행위다. 기록되는 곳은 `__consumer_offsets`라는 Kafka 내부 토픽이라, 커밋도 결국 메시지 발행이고 그래서 브로커가 재시작해도 남는다. 자동 커밋(`enable.auto.commit=true`)의 위험은 이 책갈피가 "처리 완료"가 아니라 **`poll()`을 부르는 시점**에 꽂힌다는 것이다 — 다음 poll을 부르는 행위 자체가 "앞 배치는 다 처리했다"는 선언으로 취급되므로, 실제로는 아직 처리 중인데 커밋되면 크래시 시 그 메시지는 영영 다시 오지 않고(유실), 처리는 끝났는데 커밋 전에 죽으면 다시 와서 두 번 처리된다(중복). 그리고 이 둘은 대등하지 않다 — 중복은 흔적을 남기는 탐지 가능한 문제지만 유실은 사라졌다는 사실조차 남기지 않는 탐지 불가능한 문제다. 그래서 실무 정석은 수동 커밋으로 "처리 후 커밋"을 보장해 유실을 중복으로 바꾸고, 그 대가인 중복은 멱등 처리로 흡수하는 것이다.**

---

## 0. 질문 + 의도

**질문**: "오프셋 커밋이란? 자동 커밋의 위험은?"

**출제 의도**: 처리 전 커밋(유실) vs 처리 후 커밋(중복)이라는 선택이 존재함 자체를 아는지 확인한다. 이 선택을 의식하지 않고 기본값으로 운영하는 시스템은 유실이 나도 원인을 모른다 — "가끔 이벤트가 사라져요"라는 버그 리포트 앞에서 커밋 시점부터 의심할 수 있는 사람인지를 가리는 질문이다.

## 1. 오프셋 커밋이란 — 책갈피와 저장 위치

### 1-1. 왜 진도를 컨슈머가 기억해야 하는가

파티션 안의 메시지에는 0부터 하나씩 증가하는 위치 번호가 붙는다. 이 번호가 **오프셋(offset)**이다. 파티션이 append-only 로그(끝에 덧붙이기만 하는 파일)이므로, 오프셋은 그 파일 안에서 몇 번째 줄인지를 가리키는 줄 번호에 가깝다.

전통적인 MQ에서는 컨슈머가 메시지를 처리하고 확인(ack)을 보내면 브로커가 그 메시지를 지운다. 그래서 브로커의 큐에 남아 있는 것이 곧 "아직 안 한 일"이고, 진도를 따로 기억할 필요가 없다.

**Kafka는 읽어가도 메시지를 지우지 않는다.** 보존 기간 동안 로그에 그대로 남아 있다. 이것이 여러 컨슈머 그룹이 같은 데이터를 각자 읽을 수 있게 해주는 장점이지만, 동시에 **"어디까지 읽었는지"를 아무도 대신 기억해 주지 않는다**는 뜻이기도 하다. 그 기억은 컨슈머 쪽 책임이 된다.

이 기억을 브로커에 기록해 두는 행위가 **오프셋 커밋(offset commit)**이다.

### 1-2. 커밋된 오프셋은 어디에 저장되는가

여기가 자주 비어 있는 지식이다. 커밋된 오프셋은 브로커의 특별한 메타데이터 저장소가 아니라, **`__consumer_offsets`라는 Kafka 내부 토픽**에 저장된다.

이름 앞의 밑줄 두 개(`__`)는 **Kafka가 자기 용도로 쓰는 내부 토픽이라는 관례**다. 사용자가 만든 토픽과 이름이 부딪히지 않게 하고, 도구들이 목록에서 걸러낼 수 있게 하는 표시다.

저장 형태는 이렇다.

```
키:   (컨슈머 그룹 ID, 토픽 이름, 파티션 번호)
값:   다음에 읽을 오프셋 + 부가 정보
```

여기서 두 가지가 따라온다.

**첫째, 커밋은 결국 메시지 발행이다.** 컨슈머가 "그룹 G의 topic-A 파티션 0을 200까지 읽었다"고 커밋하면, 그것은 `__consumer_offsets` 토픽에 한 건을 발행하는 일이다. 그래서 커밋도 다른 발행과 마찬가지로 **네트워크 왕복이 필요하고, 실패할 수 있고, 복제본에 기록된다.** 3-2에서 `commitSync`가 왜 느린지, `commitAsync`가 왜 실패할 수 있는지의 근거가 여기다.

**둘째, 토픽에 저장되므로 브로커가 재시작해도 남는다.** 커밋 정보는 브로커 메모리의 휘발성 상태가 아니라 디스크의 로그이고, 복제까지 된다. 컨슈머가 죽어도, 브로커가 죽었다 살아나도, 그 책갈피는 그 자리에 있다.

이 토픽은 같은 키에 대해 최신 값만 남기는 **compaction**(같은 키의 오래된 값은 정리하고 마지막 값만 남기는 로그 정리 방식)이 걸려 있어, 그룹·토픽·파티션 조합마다 마지막 커밋 위치가 유지된다. (compaction 자체는 `36-log-compaction-compacted-topic.md`)

정리하면 이렇다.

- 커밋된 오프셋은 브로커 내부 토픽 `__consumer_offsets`에 `(컨슈머 그룹, 토픽, 파티션) → 다음에 읽을 오프셋` 형태로 저장된다.
- 컨슈머가 살아서 도는 동안에는 메모리 안의 현재 위치(position)로 계속 읽어나가므로 커밋이 없어도 진행에는 문제가 없다.
- 커밋이 힘을 발휘하는 순간은 **재시작과 리밸런스**다. 파티션을 새로 할당받은 컨슈머는 커밋된 오프셋부터 읽기 시작한다.

세 번째 항목이 핵심이다. **커밋은 "지금 읽기"를 위한 장치가 아니라 "다음에 누가 어디서 이어받을지"를 위한 장치다.**

### 1-3. 책갈피 비유 — 이 질문의 전부가 여기 있다

책(파티션)은 그대로 있고, 책갈피(커밋된 오프셋)만 그룹 단위로 꽂아둔다. 책을 읽어도 페이지가 사라지지 않으니 책갈피가 유일한 진도 표시다.

```
파티션(책):  [100][101][102][103][104][105][106] ...
                                ^
                          책갈피(커밋된 오프셋 = 103)
                          "다음에 103부터 읽어라"

실제로 읽고 처리한 곳이 105인데 책갈피가 103에 있으면
  -> 재시작 시 103, 104를 다시 읽는다 = 중복

실제로 처리한 곳이 103인데 책갈피가 106에 있으면
  -> 104, 105를 영영 안 읽는다 = 유실
```

**책갈피를 실제 읽은 곳보다 앞에 꽂으면 그 사이는 다시 읽고(중복), 뒤에 꽂으면 그 사이를 건너뛴다(유실).** 커밋 시점 문제의 전부가 이 비유 안에 있다.

## 2. 자동 커밋의 동작과 두 사고 시나리오

### 2-1. 자동 커밋은 정확히 언제 일어나는가

여기를 두루뭉술하게 알면 뒤의 인과가 전부 어긋난다. "시간 주기로 알아서 커밋된다"는 설명은 절반만 맞다.

`enable.auto.commit=true`(기본값)일 때, 커밋을 수행하는 주체는 **뒤에서 도는 별도의 타이머 스레드가 아니다.** **`poll()`을 호출하는 그 스레드 자신**이다.

컨슈머는 `poll()`이 불릴 때마다 이렇게 한다.

1. "지난번 커밋으로부터 `auto.commit.interval.ms`가 지났나?"를 확인한다.
2. 지났으면 **직전 `poll()`이 반환했던 레코드의 마지막 오프셋 다음**까지 커밋한다.
3. 그러고 나서 새 레코드를 가져와 반환한다.

타임라인으로 겹쳐 그리면 이렇다.

```
시간 ---------------------------------------------------------------->

  poll#1                          poll#2                          poll#3
    |                               |                               |
    | (1) 커밋 조건 확인             | (1) 지난 커밋 이후 간격 경과?  | (1) 간격 확인
    |     (첫 호출이라 커밋 없음)    | (2) 지났으면 "200부터 읽을     | (2) 조건 맞으면
    | (2) 레코드 100~199 반환        |     차례"라고 커밋 <-- ★       |     "300부터"라고 커밋
    v                               | (3) 레코드 200~299 반환        | (3) 300~399 반환
                                    |                               |
  [애플리케이션이 100~199를 처리]    v
    ^                          [200~299를 처리]
    |
    +-- 이 구간에서 죽으면 커밋 전이므로
        재시작 후 100부터 다시 = 중복

  ★ 커밋 판단은 오직 poll() 호출 시점에만 일어난다.
    그리고 그때 커밋되는 범위는 "직전 poll이 넘겨준 것 전부"다.
    애플리케이션이 그것을 실제로 처리했는지는 아무도 확인하지 않는다.
```

여기서 두 가지 사실이 나온다.

**첫째, poll을 안 부르면 커밋도 안 일어난다.** 자동 커밋은 시계에 실려 움직이는 것이 아니라 **poll 호출에 실려** 움직인다. 처리가 길어져 poll을 오래 안 부르면 그동안 커밋도 없다.

**둘째 — 그리고 이것이 진짜 위험의 근원인데 — 커밋되는 범위는 "직전 poll이 반환한 것 전부"다.** 그중 몇 건을 처리했는지, 처리하다 예외가 났는지는 판단에 들어가지 않는다. **다음 poll을 부르는 행위 자체가 "앞의 배치는 다 처리했다"는 선언으로 취급된다.**

문제의 본질을 한 문장으로 쓰면 이렇다. **자동 커밋은 애플리케이션이 메시지를 실제로 처리했는지 전혀 모른다.** 커밋 조건이 "처리 성공"이 아니라 "간격이 지났고 poll이 또 불렸다"이기 때문에, 커밋과 처리의 순서가 **코드 구조에 따라** 어긋난다.

그래서 유실 시나리오를 "타이머가 제멋대로 커밋해서"로 이해하면 틀린다. **유실의 방아쇠는 내 루프 안에 있다** — 내가 다음 poll을 부르는 그 줄이다.

### 2-2. 중복 시나리오 — 처리는 됐는데 커밋 전에 죽음

```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(timeout);
    for (var record : records) {
        process(record);          // 300건 처리 완료
    }
    // 다음 poll()에서 커밋될 예정이었는데, 여기서 크래시/리밸런스 발생
}
// → 커밋은 마지막 커밋 주기 시점에 멈춰 있음
// → 재시작한 컨슈머는 이미 처리한 300건을 다시 받는다 = 중복 처리
```

이 코드는 **처리를 다 끝낸 뒤에야 다음 poll로 넘어간다.** 그러니 커밋은 항상 "직전 배치 처리 완료 후"(다음 poll 시점)에 일어난다. 즉 이 구조에서는 **유실은 없고 중복만 생긴다.**

중복 폭은 **마지막 커밋 이후 처리한 만큼**이다. 커밋 주기가 길수록 그 사이 처리한 건수가 많아지므로 중복 폭도 커진다.

### 2-3. 유실 시나리오 — 처리가 안 됐는데 커밋됨 (더 위험)

```java
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(timeout);
    for (var record : records) {
        executor.submit(() -> process(record));  // ① 스레드풀에 던지고
    }
    // ② 바로 다음 poll()로 진행 → 자동 커밋 발동
    //    아직 처리 중(또는 실패)인 레코드의 오프셋까지 커밋됨
}
// → 여기서 크래시하면, 처리 못 한 메시지는 커밋 뒤편에 있으므로
//   재시작해도 다시 오지 않는다 = 조용한 유실
```

2-1의 타임라인에 이 코드를 얹으면 왜 유실인지가 보인다.

```
poll#1 : 레코드 100~199 반환
   |
   +-- executor.submit() x 100
       워커 큐에 쌓아 놓기만 하고 즉시 리턴한다.
       실제 처리는 아직 아무것도 안 끝났다.
   |
poll#2 : "200부터 읽을 차례"라고 커밋   <-- ★ 여기가 사고
   |     (100~199를 다 처리한 것으로 간주됨)
   |
   +-- 이 순간 프로세스가 죽으면
       재시작한 컨슈머는 커밋된 200부터 읽는다
       -> 워커 큐에 앉아 있다가 함께 사라진 100~199 구간은
          영영 다시 오지 않는다
```

유실은 두 가지 코드 구조에서 나온다.

**처리를 다른 스레드에 넘기고 루프는 계속 도는 구조.** poll은 빨리 돌고, 커밋은 처리 완료를 앞질러 간다. 위 코드가 정확히 이 경우다.

**예외를 삼키고 루프가 계속 도는 구조.** `try { process(record); } catch (Exception e) { log.error(...); }`처럼 실패를 잡아먹으면, 처리 실패한 레코드가 있어도 루프는 끝까지 돌고 다음 poll에서 그 오프셋까지 커밋된다. **로그에 에러 한 줄 남고 메시지는 사라진다.**

두 번째가 특히 함정인 이유는, 예외를 잡아서 로그를 남기는 것이 보통은 "견고한 코드"의 습관이기 때문이다. 여기서는 그 습관이 정확히 유실 장치가 된다.

### 2-4. 유실이 중복보다 위험한 이유 — 탐지 가능한 문제와 탐지 불가능한 문제

"둘 다 나쁜 것 아닌가"로 넘어가면 이 질문의 핵심을 놓친다. **둘은 대등하지 않다.** 가르는 축은 심각도가 아니라 **탐지 가능성**이다.

| | 중복 | 유실 |
|---|---|---|
| 데이터에 남는 흔적 | 같은 결과가 두 번 (원장 두 줄, 메일 두 통) | 없음 |
| 발견 경로 | 유니크 제약 위반, 정산 불일치, 사용자 문의 | 원본과 대조할 때만 |
| 사후 복구 | 중복분을 찾아 취소·정정 | 원본 위치를 알면 재발행, 모르면 불가 |
| 사전 방어 | 멱등 처리로 흡수 가능 | 커밋 시점을 옮기는 것 외에 없음 |

**중복은 탐지 가능한 문제다.** 무언가가 두 번 일어났다는 것은 데이터에 흔적을 남긴다. 원장에 같은 주문이 두 줄, 사용자에게 같은 메일이 두 통, 유니크 제약이 걸려 있으면 예외 로그. **찾을 실마리가 반드시 남는다.**

**유실은 탐지 불가능한 문제다.** 없어진 메시지는 없어졌다는 사실조차 남기지 않는다. 카운터가 하나 안 올라간 것이 아니라 **애초에 그런 이벤트가 있었다는 정보가 이 시스템 어디에도 없는** 상태다.

이 비대칭을 정확히 짚으려면 이렇게 물어보면 된다. **"이벤트 987654가 처리되지 않았다"는 것을 어떻게 알아낼 것인가?** 그것을 알려면 그 이벤트가 존재했다는 사실을 다른 곳에서 알고 있어야 하는데, 컨슈머 입장에서 그 정보의 유일한 출처가 **방금 사라진 그 메시지**다. 자기 존재를 증명해 줄 유일한 증거와 함께 사라지는 것이다.

발견되는 경로가 있긴 하다. 원본 시스템의 건수와 우리 쪽 처리 건수를 맞춰보는 **대사(reconciliation)** 배치다. 그런데 대사는 보통 하루 단위로 돌고, 그 시점에는 이미 며칠이 지나 있으며, 사라진 메시지의 내용이 무엇이었는지는 원본을 다시 뒤져야 알 수 있다. **탐지에 별도의 인프라가 필요하다는 것 자체가 유실의 비용이다.**

그래서 설계 원칙이 이렇게 정해진다. **탐지 불가능한 문제를 탐지 가능한 문제로 바꾼다.**

처리 후 커밋을 택하면 유실이 중복으로 바뀐다. 문제가 없어지는 게 아니라 **다룰 수 있는 형태로 바뀌는** 것이다. 그리고 중복에는 멱등 처리라는 정해진 해법이 있다(`04-idempotent-consumer-implementation.md`).

"이 선택을 의식하지 않고 기본값으로 운영하는 시스템은 유실이 나도 원인을 모른다"는 출제 의도의 문장이 정확히 이 지점을 가리킨다.

## 3. 수동 커밋과 커밋 시점 = 전달 보장의 선택

### 3-1. 처리 후 커밋 — 시점을 코드가 통제한다

정석은 자동 커밋을 끄고, **처리가 끝난 뒤에** 명시적으로 커밋하는 것이다.

```java
// enable.auto.commit=false
while (true) {
    ConsumerRecords<String, String> records = consumer.poll(timeout);
    for (var record : records) {
        process(record);       // ① 먼저 처리
    }
    consumer.commitSync();     // ② 처리 성공 후 커밋
}
// 처리 후 커밋 = 커밋 전에 죽으면 다시 받는다 → 유실 없음, 중복 가능
// = at-least-once. 중복은 멱등 컨슈머로 방어한다(04번 문서).
```

바뀐 것은 딱 하나 — **커밋 시점의 결정권이 컨슈머 라이브러리에서 내 코드로 넘어왔다.** 자동 커밋에서는 "poll이 불렸다"가 커밋 조건이었지만, 여기서는 "for 루프가 예외 없이 끝났다"가 커밋 조건이다.

이 차이가 값을 하는 순간은 **처리 방식이 바뀔 때**다. 나중에 누군가 처리를 스레드풀로 옮기더라도, 커밋 줄이 명시적으로 거기 있으니 "이 커밋이 무엇을 보장하는가"를 다시 생각하게 된다. 자동 커밋에서는 그 질문이 코드 어디에도 드러나지 않는다.

### 3-2. commitSync vs commitAsync — 그리고 실무 조합

1-2에서 본 대로 커밋은 브로커로 나가는 요청이다. 그러니 "응답을 기다릴 것인가"라는 선택이 생긴다.

**`commitSync()`** 는 커밋 성공/실패를 확인할 때까지 **블로킹**하고, 일시적 오류면 내부적으로 재시도한다. 느리지만 확실하다. 브로커 왕복 시간만큼 루프가 멈추므로, 배치마다 부르면 그만큼 처리량이 깎인다.

**`commitAsync()`** 는 **논블로킹**으로 커밋 요청만 보내고 즉시 다음으로 넘어간다. 빠르지만 **실패해도 재시도하지 않는다.**

재시도하지 않는 이유가 중요하다. **재시도하면 오프셋이 뒤로 갈 수 있기 때문이다.**

```
t0  commitAsync(200 커밋) 발송  -> 일시 오류로 실패
t1  commitAsync(300 커밋) 발송  -> 성공.  커밋된 오프셋 = 300
t2  만약 t0의 200을 재시도했다면 -> 성공.  커밋된 오프셋 = 200  <-- 뒤로 감
t3  여기서 크래시
    -> 재시작 컨슈머는 200부터 읽는다
    -> 이미 처리한 200~299를 통째로 다시 처리 = 불필요한 중복
```

**늦게 보낸 큰 오프셋이 먼저 커밋되고, 재시도된 작은 오프셋이 그것을 덮어쓰는 역전**을 막으려고 아예 재시도를 하지 않는 설계다.

그런데 여기서 자연스럽게 실무 조합이 나온다.

**평상시에는 비동기, 컨슈머를 닫기 직전과 리밸런싱 직전에는 동기.** (가산점 포인트)

왜 이 조합인가. **비동기 커밋은 실패해도 다음 커밋이 덮어쓰므로 평소에는 괜찮다.** 오프셋 200 커밋이 실패해도 다음 루프에서 300을 커밋하면 진도는 회복된다. 잃는 것은 없다.

**그런데 마지막 커밋은 덮어쓸 다음이 없다.** 컨슈머가 종료되거나 파티션을 남에게 넘기는 순간의 커밋이 실패하면, 그 실패를 만회할 다음 커밋이 영영 오지 않는다. 그 구간은 다음 컨슈머가 통째로 다시 읽게 된다.

```java
try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(timeout);
        for (var record : records) {
            process(record);
        }
        // 평시: 논블로킹이라 브로커 왕복을 기다리지 않는다 = 처리량 유지.
        // 이 커밋 하나가 실패해도 다음 루프의 커밋이 더 큰 오프셋으로
        // 덮어쓰므로 진도가 회복된다.
        consumer.commitAsync();
    }
} finally {
    try {
        // 마지막 커밋에는 "덮어쓸 다음 커밋"이 없다.
        // 여기서 실패하면 그 구간은 재시작 후 통째로 중복 처리된다.
        // 그래서 여기서만 블로킹하며 확실히 성공시킨다.
        consumer.commitSync();
    } finally {
        consumer.close();
    }
}
```

리밸런싱 직전도 같은 논리다. 리밸런스로 파티션을 다른 컨슈머에게 넘기면 **그 파티션에 대한 나의 마지막 커밋**이 되므로, `ConsumerRebalanceListener`의 `onPartitionsRevoked`에서 `commitSync`를 부른다. 여기서 커밋을 빠뜨리면 파티션을 넘겨받은 컨슈머가 내가 이미 처리한 구간부터 다시 읽는다 — 리밸런스 때마다 중복이 터지는 흔한 원인이다.

정리하면 판단 기준은 하나다. **"이 커밋이 실패했을 때 만회해 줄 다음 커밋이 있는가."** 있으면 async, 없으면 sync다.

### 3-3. Spring Kafka를 쓴다면

컨테이너의 `AckMode` 기본값(BATCH)은 **리스너가 정상 리턴한 뒤 커밋하는 방식**이다. 즉 **프레임워크가 "처리 후 커밋"을 이미 구현해 둔 것**이다.

그래서 Spring Kafka의 기본 동작은 순수 클라이언트의 자동 커밋과 다르며 **at-least-once에 가깝다.** `@KafkaListener`만 붙여 쓰는 코드가 대체로 유실 없이 도는 이유가 여기 있다.

다만 **리스너 안에서 처리를 비동기로 넘기면 그 보장이 그대로 깨진다.** 리스너가 `executor.submit()`만 하고 즉시 리턴하면, 프레임워크 입장에서는 "정상 리턴 = 처리 완료"이므로 커밋한다. 2-3의 유실 구조가 프레임워크 위에서 그대로 재현되는 것이다. **보장의 근거가 "리스너의 정상 리턴"이라는 것을 알고 있어야 이 함정을 피한다.**

`MANUAL`/`MANUAL_IMMEDIATE`로 바꾸면 리스너 코드가 `Acknowledgment.acknowledge()`를 부르는 시점까지 직접 통제할 수 있다.

### 3-4. 커밋 시점 = 전달 보장의 선택

커밋 시점을 정하는 것은 결국 **장애 시 무엇을 감수할지** 정하는 것이다.

| 커밋 시점 | 장애 시 결과 | 성향 |
|---|---|---|
| 처리 **전** 커밋 (자동 커밋의 유실 구조) | 못 다시 받음 → 유실 | at-most-once |
| 처리 **후** 커밋 (수동 커밋 정석) | 다시 받음 → 중복 | at-least-once |

**at-most-once**는 "많아야 한 번" — 두 번 오지는 않지만 아예 안 올 수 있다는 뜻이다. **at-least-once**는 "적어도 한 번" — 반드시 오지만 두 번 이상 올 수 있다는 뜻이다.

**"유실 없음 + 중복 없음"을 커밋 시점만으로 만들 수는 없다.** 처리와 커밋은 서로 다른 두 시스템(내 애플리케이션과 브로커)에서 일어나는 별개의 쓰기이고, 두 쓰기 사이에는 반드시 틈이 있다. 그 틈에서 죽으면 둘 중 하나는 어긋난다. 커밋을 앞에 두면 유실 쪽으로, 뒤에 두면 중복 쪽으로 어긋날 뿐이다.

그래서 실무 결론은 **처리 후 커밋으로 유실을 막고, 중복은 멱등 처리로 흡수**하는 것이다. 2-4의 표현으로 다시 쓰면, **탐지 불가능한 문제를 탐지 가능한 문제로 바꾼 뒤 정해진 해법을 적용하는 것**이다.

전달 의미론 전체 그림은 `03-delivery-semantics-and-exactly-once-reality.md`, 멱등 구현은 `04-idempotent-consumer-implementation.md`에서 다룬다.

## 4. 꼬리질문 대비 포인트

### "커밋을 아예 안 하면 어떻게 되나?"

실행 중에는 아무 문제가 없어 보인다. 컨슈머는 메모리 안의 position으로 계속 읽어나가기 때문이다. 이것이 함정이다 — 개발 중에는 증상이 안 나온다.

문제는 재시작·리밸런스 시점이다. 커밋된 오프셋이 없으면 컨슈머는 **어디서부터 읽을지 알 수 없고**, 그때 `auto.offset.reset` 설정을 따른다.

- `earliest` — 파티션에 남아 있는 가장 오래된 메시지부터 전량 재처리한다. **중복 폭탄**이다.
- `latest`(기본값) — 지금 시점 이후에 들어오는 메시지부터 읽는다. **재시작 사이에 쌓인 메시지를 전부 건너뛴다 = 유실.**

즉 커밋은 "지금 읽기"가 아니라 **"다음에 어디서 이어받을지"**를 위한 장치라는 걸 짚으면 이해도가 드러난다.

한 가지 덧붙이면 좋은 것이 있다. **이 설정은 커밋된 오프셋이 없을 때만 쓰인다.** 커밋이 하나라도 있으면 무시된다. 그래서 "장애 났을 때 `earliest`로 바꿔서 다시 읽자"는 시도가 아무 효과가 없는 경우가 자주 생긴다 — 커밋이 이미 있기 때문이다. 그때는 오프셋을 직접 되감아야 한다.

### "commitSync와 commitAsync의 차이는? 실무에선 뭘 쓰나?"

sync는 브로커 응답까지 블로킹 + 일시 오류 재시도, async는 논블로킹 + 재시도 없음이다.

async가 재시도하지 않는 이유는 **오프셋 커밋의 순서 역전**을 막기 위해서다 — 늦게 보낸 큰 오프셋이 먼저 커밋되고, 재시도된 작은 오프셋이 그걸 덮어쓰면 커밋 위치가 뒤로 간다(3-2 타임라인).

실무 패턴은 **루프에서 async, 종료와 `onPartitionsRevoked`에서 sync**다. 근거를 한 문장으로 말할 수 있어야 한다. **"평시 커밋은 실패해도 다음 커밋이 덮어주지만, 마지막 커밋은 덮어쓸 다음이 없다."**

파티션을 내놓기 직전의 마지막 커밋이 확실해야 리밸런스 후 중복 폭이 최소화된다.

### "자동 커밋이라도 동기 루프면 유실은 없는 것 아닌가?"

맞다 — 커밋이 다음 poll 시점에 일어나므로, 처리를 다 끝내고 다음 poll로 가는 동기 루프에서는 **"직전 배치 처리 완료 후 커밋"**이 되어 사실상 at-least-once다. 이걸 아는지가 정확한 이해의 척도다.

다만 그 안전은 **코드 구조가 우연히 만들어준 것이지 보장이 아니다.** 처리를 스레드풀에 넘기거나, 예외를 삼키고 루프를 계속 돌리는 순간 유실 구조로 바뀐다(2-3). 그리고 그 변경을 하는 사람은 대개 "커밋 시점을 바꾸고 있다"는 자각이 없다 — 코드 어디에도 커밋이라는 단어가 안 보이기 때문이다.

즉 위험의 본질은 "자동 커밋 자체"가 아니라 **커밋 시점을 코드가 통제하지 못한다는 것**이다. 그래서 처리 방식이 바뀌어도 보장이 유지되도록 수동 커밋으로 시점을 명시하는 것이 정석이다, 라고 답하면 원리로 답하는 인상을 준다.

### "배치로 받아서 컨슈머 내부에서 병렬 처리하면 커밋은 어떻게 다루나?" (시니어 변별 포인트)

병렬화하는 순간 **"배치의 마지막 오프셋 커밋"은 위험해진다.** 뒤쪽 오프셋 레코드가 먼저 끝나고 앞쪽이 아직 처리 중일 때 마지막 오프셋을 커밋하면, 크래시 시 앞쪽 미처리 레코드가 유실된다.

원칙은 **"연속으로 처리 완료된 가장 낮은 오프셋까지만" 커밋**하는 것이다.

```
처리 완료 상태:  1(완료) 2(완료) 3(완료) 4(진행중) 5(완료)

  잘못된 커밋: 5까지 커밋
    -> 크래시 시 4는 미처리인데 커밋 뒤편에 있어 영영 유실

  올바른 커밋: 3까지만 커밋
    -> 앞에서부터 끊김 없이 이어진 마지막 지점이 3이다
    -> 크래시 시 4, 5를 다시 받는다 (5는 중복이지만 멱등으로 흡수)
```

즉 처리 완료 오프셋들을 추적하다가 **앞에서부터 빈틈 없이 이어진 지점**을 계산해 커밋한다. 5가 완료됐어도 4가 비어 있으면 5까지 커밋할 수 없다 — 오프셋은 하나의 숫자라 "4만 빼고"를 표현할 수 없기 때문이다(이것이 `02-kafka-vs-rabbitmq.md`에서 본 오프셋 모델의 성질이다).

파티션별로 순서를 유지하는 executor를 쓰면 파티션 단위 순차성이 남아 이 관리가 단순해진다.

**"병렬화가 처리량을 올리는 대신 커밋 관리 복잡도를 사는 것"**이라는 트레이드오프를 말할 수 있으면 컨슈머 구현 레벨을 다뤄본 사람이다. (깊은 논의: `30-single-consumer-throughput-and-offset-commit.md`)

> **RabbitMQ에서의 대응**: 오프셋 대신 메시지 단위 ack을 쓴다. auto-ack의 위험과 prefetch(QoS)의 역할, 그리고 "연속 진도"와 "메시지별 상태"라는 두 모델의 차이는 `12-rabbitmq-ack-nack-prefetch.md`에서 다룬다.

## 한 줄 요약

오프셋 커밋은 컨슈머 그룹의 책갈피를 `__consumer_offsets` 내부 토픽에 발행해 두는 행위이고, 자동 커밋의 위험은 그 책갈피가 "처리 완료"가 아니라 **다음 `poll()`을 부르는 시점**에 "앞 배치는 다 했다"는 선언으로 꽂힌다는 것이다 — 책갈피가 실제 읽은 곳보다 앞서면 유실, 뒤처지면 중복이며, 유실은 흔적조차 남지 않는 탐지 불가능한 문제이므로 실무 정석은 처리 후 수동 커밋으로 유실을 탐지 가능한 중복으로 바꾸고 그 중복을 멱등 처리로 흡수하는 것이다.
