# 컨슈머 재시도와 DLQ 설계 — 실패 메시지 하나가 파티션 전체를 막지 않게

> 핵심 관전 포인트: **파티션은 한 줄로 선 대기열이라, 실패한 메시지 하나를 붙잡고 무한 재시도하면 그 뒤의 모든 메시지가 멈춘다(poison pill). 그래서 실패 처리의 뼈대는 "실패를 분류하고, 회복 가능한 것만 제한된 횟수로 재시도하고, 끝내 안 되는 것은 DLQ로 치워 흐름을 살리는 것"이다. 재시도는 순서를 지키는 블로킹 방식과 순서를 포기하는 재시도 토픽 방식 중 도메인 요구에 맞춰 고르되, 블로킹 재시도는 그 대기 시간이 `max.poll.interval.ms`를 넘기면 컨슈머가 죽은 것으로 판정돼 리밸런싱이 터진다는 함정을 계산에 넣어야 한다. DLQ는 버리는 곳이 아니라 진단 정보·유입 알림·재투입 절차까지 이어지는 운영 절차의 시작점으로 설계한다.**

---

## 0. 질문 + 의도

**질문**: "컨슈머가 메시지 처리에 실패하면 어떻게 하나요? 재시도/DLQ(Dead Letter Queue) 설계를 설명해주세요."

**출제 의도**: 실패 메시지 하나가 파티션 전체를 막는 poison pill 문제를 아는지 확인한다. "실패하면 어떻게 되나"를 설계하지 않은 컨슈머는 반드시 운영에서 그 대가를 치른다 — 실패 경로를 미리 설계하는 습관이 있는 개발자인지 가리는 질문이다.

## 1. 왜 문제인가 — 파티션은 한 줄 대기열이다

### 1-1. 전제 지식 — 컨슈머는 파티션마다 오프셋 하나만 들고 있다

Kafka 컨슈머가 파티션에서 메시지를 읽는 방식을 정확히 알아야 이 문제가 보인다.

컨슈머는 파티션마다 **"어디까지 읽었는가"를 나타내는 숫자 하나**만 들고 있다. 이 숫자가 **오프셋(offset)**이다. 메시지를 처리하고 오프셋을 앞으로 밀고, 다시 처리하고 밀고를 반복한다. **"3번은 실패했지만 4번은 성공했다"를 따로 표시할 자리가 없다.** 진행 상태를 나타낼 수 있는 것은 숫자 하나뿐이기 때문이다.

그래서 3번에서 막히면 이런 그림이 된다.

```
파티션 P0 (브로커에 저장된 로그)

  오프셋:    1        2        3        4        5        6
           [완료]   [완료]   [독약]   [정상]   [정상]   [정상]
                              ^
                              |
                     컨슈머의 오프셋 포인터가 여기서 멈춘다
                     3번을 성공시키지 못하면 앞으로 밀 수가 없다

  → 4, 5, 6번은 브로커에 멀쩡히 저장되어 있는데도 아무도 읽어가지 못한다.
    컨슈머를 아무리 늘려도 소용없다 — 한 파티션은 그룹 안에서
    컨슈머 하나가 전담하므로, 다른 컨슈머가 대신 4번을 가져갈 수 없다.
```

이것을 **선두 차단(head-of-line blocking)**이라고 부른다. 큐 앞사람이 계산을 못 끝내면 뒷줄 전체가 멈추는 계산대와 같은 구조다. 그래서 "실패한 메시지를 어떻게 할 것인가"라는 질문은 사실 **"이 계산대의 줄을 계속 흐르게 할 것인가"**라는 질문이다.

### 1-2. poison pill — 왜 "독약"인가

**poison pill**은 "삼키면 죽는 독약"이라는 뜻이다. 이름 그대로다 — **컨슈머가 그 메시지를 처리하려 할 때마다 실패해서, 결국 파이프라인 전체를 마비시키는 메시지**를 가리킨다.

이름이 잘 붙은 이유는 증상이 정확히 중독이기 때문이다. 컨슈머는 살아 있고 CPU도 돌고 있는데, 파티션 소비만 조용히 멈춰 있다. 랙(아직 소비하지 못한 메시지 수)만 계속 쌓인다. 로그에는 같은 예외가 초당 수십 번씩 반복되는데, 그 로그가 너무 많아 오히려 눈에 안 띈다.

더 나쁜 것은 **전염된다**는 점이다. 뒤에서 자세히 보겠지만, 무한 재시도는 브로커가 이 컨슈머를 죽었다고 판정하게 만들고, 그러면 파티션이 다른 컨슈머로 넘어가고, 그 컨슈머도 같은 독약을 삼켜 똑같이 마비된다. 결국 **컨슈머 그룹 전체가 재시도-리밸런싱 루프에 갇힌다.**

### 1-3. 이 문제가 RabbitMQ에는 없다

구조가 원인이라는 것을 보여주는 가장 좋은 대조가 RabbitMQ다.

**Kafka는 로그(log) 기반이다.** 메시지는 파티션에 순서대로 쌓인 채 남아 있고, 컨슈머는 "어디까지 읽었다"는 오프셋 하나만 움직인다. 메시지를 개별적으로 "처리 완료" 표시할 수 없다.

**RabbitMQ는 큐(queue) 기반이다.** 메시지를 컨슈머에게 밀어주고, 컨슈머가 **메시지 단위로 ack(처리 완료) 또는 nack(처리 실패)**을 돌려준다. ack를 받은 메시지는 큐에서 삭제된다.

```
[Kafka] 오프셋 포인터 하나 = 한 줄 대기열
  ... [3 실패] [4] [5] [6] ...
        ^
        └ 여기서 못 넘어가면 4, 5, 6도 못 읽는다

[RabbitMQ] 메시지마다 개별 ack/nack
  [3] nack → 큐로 되돌리거나 dead-letter exchange로 보낸다
  [4] ack  → 삭제, 처리 완료
  [5] ack  → 삭제, 처리 완료
  → 3번이 막혀도 4, 5는 그대로 흘러간다
```

**즉 poison pill로 인한 선두 차단은 Kafka의 버그가 아니라 로그 기반 모델의 대가다.** Kafka는 그 대가를 치르는 대신 재소비(replay) 가능성과 높은 처리량을 얻었다(02번 문서). 이 트레이드오프를 말할 수 있으면 "Kafka를 쓸 줄 안다"가 아니라 "Kafka가 왜 그렇게 생겼는지 안다"가 된다.

### 1-4. 흔한 두 가지 잘못된 극단

구조를 알았으니 잘못된 대응을 보자. 실무에서 가장 자주 보는 두 극단이다.

```java
// 잘못된 극단 1: 예외를 삼키고 넘어간다 — 조용한 유실
@KafkaListener(topics = "orders")
public void consume(OrderEvent event) {
    try {
        orderService.process(event);
    } catch (Exception e) {
        log.error("처리 실패", e);   // 로그만 남기고 다음 메시지로 넘어간다
    }                                 // 예외가 리스너 밖으로 안 나가므로
}                                     // 컨테이너는 성공으로 보고 오프셋을 커밋한다
                                      // → 실패 메시지는 영영 사라진다

// 잘못된 극단 2: 성공할 때까지 무한 재시도 — poison pill
@KafkaListener(topics = "orders")
public void consume(OrderEvent event) {
    while (true) {
        try {
            orderService.process(event);
            break;
        } catch (Exception e) {
            sleep(1000);   // 영구적 실패(잘못된 데이터)라면 영원히 반복된다
        }                  // → 이 파티션의 뒤 메시지 전부가 멈춘다
    }
}
```

**극단 1의 진짜 문제는 로그를 남겼다는 것이 아니라, 오프셋이 커밋된다는 것이다.** 예외를 잡아 삼키면 리스너는 정상 종료한 것처럼 보이므로 컨테이너가 오프셋을 앞으로 민다. 그 메시지는 다시 읽을 수 없다. 데이터 유실이고, 유실됐다는 사실조차 로그 파일 안에만 남는다.

**극단 2는 poison pill 그 자체다.** 그리고 여기에 한 겹의 재앙이 더 있다 — `max.poll.interval.ms`(같은 컨슈머가 `poll()`을 다시 부르기까지 허용되는 최대 간격) 초과다. 이건 2-1에서 도식으로 자세히 본다.

### 1-5. 실패의 분류가 설계의 출발점

모든 실패를 같게 다루면 안 된다. 기준은 하나다 — **"시간이 지나면 결과가 달라지는가."**

- **일시적(transient) 실패**: DB 커넥션 풀 고갈, 외부 API 타임아웃, 락 경합. 지금은 실패했지만 잠시 후에는 성공할 수 있다. **재시도 대상**이다.
- **영구적(permanent) 실패**: 역직렬화 실패(메시지 스키마가 컨슈머가 아는 구조와 다름), 검증 실패(필수 필드 누락), NPE 같은 코드 버그. **100번 재시도해도 100번 실패한다.** 즉시 **DLQ 대상**이다.

영구적 실패를 재시도하는 것은 단순한 시간 낭비가 아니다. 재시도하는 동안 파티션이 멈춰 있으므로 **뒤에 줄 선 정상 메시지들의 지연을 늘리는 해악**이다. 성공 가능성이 0인 일에 파티션을 점유시키는 셈이다.

이 분류를 **예외 타입으로 코드에 박아두는 것**이 실패 경로 설계의 첫 단추다. 다음 절의 `addNotRetryableExceptions`가 바로 그 자리다.

## 2. 재시도 설계 — 순서를 지킬 것인가, 흐름을 지킬 것인가

재시도 방식은 두 가지다. 그리고 이 둘은 **정확히 반대되는 것을 포기한다.** 하나는 흐름을 포기하고 순서를 지키며, 다른 하나는 순서를 포기하고 흐름을 지킨다.

### 2-1. 블로킹 재시도 (in-place retry)

**같은 파티션 자리에서, 같은 컨슈머 스레드가 백오프를 두고 몇 번 재시도한 뒤, 횟수를 초과하면 DLQ로 보내는 방식**이다. 여기서 **백오프(backoff)**는 재시도 사이에 두는 대기 시간으로, 보통 실패가 거듭될수록 간격을 늘린다(이미 힘들어하는 상대 시스템에 재시도 폭풍을 얹지 않기 위해서다).

Spring Kafka의 `DefaultErrorHandler`가 이 모델이다.

```java
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    // 재시도를 다 소진했을 때 실행할 "복구기".
    // 기본 동작은 원본 토픽명 + ".DLT" 토픽으로 실패 메시지를 발행하는 것이다.
    var recoverer = new DeadLetterPublishingRecoverer(template);

    // 1초 간격으로 최대 3회 재시도하고, 그래도 실패하면 recoverer를 부른다.
    // 이 숫자들이 아래에서 볼 max.poll.interval.ms 계산의 입력값이 된다.
    var handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 3));

    // 1-5의 분류를 코드에 박는 자리다. 여기 등록된 예외는 재시도를 건너뛰고
    // 곧바로 recoverer(DLQ 발행)로 간다 — 성공 가능성이 0이므로
    // 파티션을 3초간 점유할 이유가 없다.
    handler.addNotRetryableExceptions(
            DeserializationException.class,
            ValidationException.class);
    return handler;
}
```

**장점은 파티션 내 순서가 유지된다는 것이다.** 재시도가 끝날 때까지 뒤 메시지를 읽지 않으므로, 같은 키의 이벤트가 발행된 순서대로 처리된다.

**단점은 재시도하는 동안 그 파티션이 멈춘다는 것이다.** 그리고 여기에 반드시 알아야 할 함정이 하나 더 있다.

#### 숨은 함정 — 재시도가 컨슈머 생존 판정과 충돌한다

블로킹 재시도는 **컨슈머 스레드가 `sleep`하면서 기다린다.** 그 말은 그동안 **`poll()`을 부르지 못한다**는 뜻이다.

그런데 Kafka 브로커는 컨슈머가 살아 있는지를 두 가지로 판정하는데, 그중 하나가 **`max.poll.interval.ms` — `poll()` 호출 사이의 최대 허용 간격**이다(다른 하나인 `session.timeout.ms`와의 구분은 35번 문서에서 다룬다). 이 간격을 넘기면 브로커는 **"살아는 있는데 일을 진척시키지 못하는 컨슈머"**로 보고 그룹에서 쫓아낸다.

즉 **재시도 전략이 컨슈머 생존 판정과 정면으로 충돌한다.**

```
컨슈머 스레드 (한 개다. 이게 핵심이다)

  poll() ──> [최대 500건 수신]
               |
               ├─ 1번째 레코드 처리 실패
               │    ├ 1초 대기 (sleep)   ← 이 동안 poll()을 못 부른다
               │    ├ 재시도 실패 → 1초 대기
               │    ├ 재시도 실패 → 1초 대기
               │    └ 재시도 실패 → DLQ 발행         (누적 3초)
               ├─ 2번째 레코드도 실패 → 같은 과정     (누적 6초)
               ├─ 3번째 ...                          (누적 9초)
               ...
               └─ 100번째 레코드까지 실패하면        (누적 300초 = 5분)
                                                      ^
                          max.poll.interval.ms 기본값 300000ms에 도달

  브로커: "이 컨슈머가 5분째 poll을 안 한다. 죽은 걸로 친다."
            |
            v
  리밸런싱 발생 → 이 컨슈머의 파티션이 다른 컨슈머에게 넘어간다
            |
            v
  새 주인은 마지막으로 커밋된 오프셋부터 읽는다
  → 재시도하던 그 메시지를 처음부터 다시 받아 다시 재시도한다
```

**재시도하려다 파티션을 빼앗기고, 다른 컨슈머가 같은 메시지를 처음부터 다시 받는 상황**이다. 그리고 새 컨슈머도 같은 이유로 쫓겨나므로 이것이 반복된다.

숫자로 확인해 보면 여유가 생각보다 없다. `max.poll.records` 기본값은 500이고, 한 번의 `poll()`이 가져온 500건이 전부 실패한다면 순수 대기 시간만 500 × 3초 = **1500초, 25분**이다. `max.poll.interval.ms` 기본값 5분의 다섯 배다. 실패가 100건만 몰려도 이미 5분에 도달한다.

그래서 블로킹 재시도를 쓸 때의 규칙은 이렇다.

**재시도 횟수 × 백오프 합계 × 한 배치의 최대 실패 건수 < `max.poll.interval.ms`**

이 부등식을 만족시키는 방법은 세 가지다. 재시도 횟수와 백오프를 줄이거나, `max.poll.records`를 줄여 한 배치의 크기를 제한하거나, `max.poll.interval.ms`를 늘리는 것이다. 다만 세 번째는 공짜가 아니다 — 이 값을 늘리면 **진짜로 죽은 컨슈머를 감지하는 시간도 그만큼 늘어난다.**

### 2-2. 논블로킹 재시도 (재시도 토픽 방식)

**실패한 메시지를 원본 토픽에서 즉시 커밋해 치우고, 별도의 재시도 토픽으로 발행한 뒤, 그 토픽의 전용 컨슈머가 지연 후 다시 처리하는 방식**이다.

핵심은 **"원본 파티션에서는 즉시 커밋하고 넘어간다"**는 점이다. 실패했는데 커밋한다는 것이 처음엔 이상하게 들리지만, **메시지가 사라지는 게 아니라 다른 토픽으로 옮겨 갔기 때문에** 유실이 아니다. 원본 파티션 입장에서는 그 메시지에 대한 일이 끝난 것이다.

재시도 토픽은 **대기 시간별로 계단식으로** 만든다.

```
orders (원본 토픽)
  |
  |  처리 실패 → 원본에서는 즉시 오프셋 커밋 (파티션이 안 막힌다)
  |             → 재시도 토픽으로 발행
  v
orders-retry-0   전용 컨슈머가 5초 대기 후 재처리 ──실패──┐
                                                          v
orders-retry-1   전용 컨슈머가 15초 대기 후 재처리 ──실패──┐
                                                          v
orders-retry-2   전용 컨슈머가 45초 대기 후 재처리 ──실패──┐
                                                          v
orders-dlt       사람이 보는 종착지 (DLQ)

  총 65초를 기다려도 원본 파티션은 단 한 순간도 멈추지 않았다.
```

Spring Kafka는 `@RetryableTopic`으로 이 계층을 자동 생성해준다.

```java
@RetryableTopic(
        attempts = "4",                                    // 원본 1회 + 재시도 3회
        backoff = @Backoff(delay = 5000, multiplier = 3.0), // 5초 → 15초 → 45초
        dltTopicSuffix = ".dlt")
@KafkaListener(topics = "orders")
public void consume(OrderEvent event) {
    orderService.process(event);
    // 예외가 나면 프레임워크가 재시도 토픽으로 자동 발행하고,
    // 원본 파티션의 오프셋은 곧바로 커밋된다.
    // 재시도 단계별 토픽(orders-retry-0, -1, -2)과 DLT는 자동 생성된다.
}
```

지연 시간이 5초 → 15초 → 45초로 늘어나는 것은 `multiplier = 3.0` 때문이다. 5000 × 3 = 15000, 15000 × 3 = 45000이고 총합은 65초다. 블로킹 방식이었다면 이 65초 동안 파티션이 통째로 멈춰 있었을 것이고, 이미 `max.poll.interval.ms` 계산에 심각한 압박이 된다. **긴 백오프를 걸 수 있다는 것이 이 방식의 가장 큰 실익이다.**

#### 이 방식이 잃는 것 — 원본 순서

공짜는 아니다. **원본 토픽의 순서 보장을 포기한다.**

실패한 메시지가 재시도 토픽으로 빠져나가 나중에 처리되므로, **그 뒤에 있던 메시지들이 먼저 처리된다.**

```
원본 토픽에 도착한 순서 (모두 같은 사용자 A의 이벤트)
  오프셋 10: A의 "주소 변경"     ← 외부 API 타임아웃으로 실패
  오프셋 11: A의 "주문 생성"
  오프셋 12: A의 "주문 결제"

실제 처리 순서
  t0   오프셋 10 실패 → orders-retry-0으로 발행, 원본 커밋
  t1   오프셋 11 "주문 생성" 처리    ← 먼저 처리됐다
  t2   오프셋 12 "주문 결제" 처리    ← 먼저 처리됐다
  t5   재시도 토픽에서 "주소 변경" 처리  ← 5초 뒤에야 처리됐다

  → 새 주소로 배송돼야 할 주문이 옛 주소로 나갔다.
```

**순서가 계약인 도메인에서는 이 방식이 곧 정합성 버그다.** 잔액 변동("입금 → 출금"이 뒤집히면 잔액 부족 오류), 상태 전이("결제 완료 → 배송 시작"이 뒤집히면 미결제 배송) 같은 도메인이 그렇다.

### 2-3. 선택 기준

- **순서가 중요한 도메인**(잔액 변동, 상태 전이): **블로킹 재시도 + 짧은 백오프**. 순서를 지키는 대신 지연을 감수한다. 백오프를 짧게 두는 이유는 2-1의 부등식 때문이다.
- **건별 독립 처리 도메인**(알림 발송, 로그 적재, 검색 색인 갱신): **재시도 토픽**. 흐름을 지키는 대신 순서를 포기한다. 어차피 각 건이 서로 독립적이라 순서가 의미 없다.

**"어느 쪽이 정답"이 아니라 "무엇을 포기할지를 도메인이 결정한다"**고 답하는 것이 포인트다. 두 방식의 이름을 아는 것은 지식이고, 어느 쪽을 포기할지 도메인 요구로 환원해 말하는 것이 설계다.

## 3. DLQ 설계 — 버리는 곳이 아니라 병원이다

**DLQ(Dead Letter Queue)**는 끝내 처리하지 못한 메시지를 모아두는 별도의 토픽이다. "죽은 편지 보관함"이라는 이름은 수취인 불명으로 배달하지 못한 우편물을 모아두는 우체국의 부서에서 왔다.

DLQ는 실패 메시지의 **종착역이 아니다.** 쓰레기통처럼 운영하면 "DLQ에 30만 건이 쌓여 있는데 아무도 모르는" 상태가 된다. 그 순간 DLQ는 유실과 같아진다 — 데이터가 어딘가에 있긴 하지만 아무도 꺼내지 않으므로 없는 것과 다르지 않다.

세 가지를 설계에 포함해야 DLQ가 기능한다.

### 3-1. 진단 정보를 함께 담는다

원본 메시지만 복사하면 나중에 원인을 알 수 없다. **"이 메시지가 왜 여기 있는가"에 답할 수 있어야** 재투입 판단이 가능하다. 그래서 다음을 Kafka 헤더에 함께 실어 보낸다.

| 담을 것 | 왜 필요한가 |
|---|---|
| 원본 메시지 본문 | 재투입할 때 그대로 다시 보내야 한다 |
| 실패 예외 클래스와 메시지 | 원인 분류(코드 버그 / 외부 장애 / 데이터 오류)의 1차 근거 |
| 스택 트레이스 | 코드 어느 줄에서 터졌는지 — 버그 수정의 출발점 |
| 재시도 횟수 | "몇 번 해보고 포기했나" — 일시 장애였는지 판단 |
| 원본 토픽·파티션·오프셋 | 원본 로그에서 앞뒤 메시지를 찾아볼 좌표 |
| 최초 실패 시각 | 다른 시스템의 장애 시각과 대조 |

`DeadLetterPublishingRecoverer`는 이 정보들을 기본으로 헤더에 넣어준다 — `KafkaHeaders.DLT_ORIGINAL_TOPIC`, `DLT_ORIGINAL_PARTITION`, `DLT_ORIGINAL_OFFSET`, `DLT_ORIGINAL_TIMESTAMP`, `DLT_EXCEPTION_FQCN`, `DLT_EXCEPTION_MESSAGE`, `DLT_EXCEPTION_STACKTRACE` 같은 것들이다.

실무에서 한 가지 함정이 있다. **기본 동작은 원본과 같은 파티션 번호로 DLT에 발행하는 것**이라, DLT의 파티션 수가 원본보다 적으면 존재하지 않는 파티션으로 보내려다 실패한다. 목적지 결정 함수를 직접 주면 피할 수 있다.

```java
var recoverer = new DeadLetterPublishingRecoverer(template,
        // 파티션 번호를 음수로 두면 원본 파티션 번호를 그대로 쓰지 않고
        // Kafka가 알아서 파티션을 고르게 한다. DLT의 파티션 수가
        // 원본보다 적어도 안전하다.
        (record, ex) -> new TopicPartition(record.topic() + ".DLT", -1));
```

### 3-2. 유입 자체를 알람으로 건다

**DLQ에 메시지가 들어오는 것 자체가 장애 신호다.** 이건 "쌓인 양이 많아지면 알린다"가 아니라 **"한 건이라도 들어오면 알린다"**에 가깝다. DLQ는 정상 상황에서 비어 있어야 하는 토픽이기 때문이다.

거는 방법은 두 가지다.

- **DLQ 토픽의 초당 유입량**에 알람을 건다. 0보다 크면 알린다.
- **DLQ 토픽의 컨슈머 랙**에 알람을 건다. DLQ를 읽는 운영용 컨슈머를 하나 두고, 그 랙이 0이 아니면 "처리되지 않은 실패 메시지가 있다"는 뜻이다.

**알림 없는 DLQ는 존재하지 않는 것과 같다.** 실패가 발생했다는 사실을 사람이 즉시 알지 못하면, DLQ는 그저 데이터가 조용히 쌓이는 곳이 된다. 재시도·DLQ 설계에서 이 항목이 빠지는 것이 가장 흔한 실수다.

### 3-3. 재투입(re-drive) 절차를 미리 만든다

원인을 고친 뒤 DLQ의 메시지를 다시 처리해야 한다. 방법은 원인의 종류에 따라 둘로 갈린다.

**(가) 코드나 외부 시스템이 문제였던 경우 — DLQ에서 그대로 다시 소비한다.** 코드를 고쳐 배포하거나 외부 시스템이 복구된 뒤, DLQ를 읽어 원본 처리 로직으로 흘려보내는 전용 컨슈머를 잠시 켠다. 메시지 내용은 손댈 필요가 없다.

**(나) 메시지 내용 자체가 문제였던 경우 — 수정해서 원본 토픽으로 다시 발행한다.** 필수 필드가 빠졌거나 값이 잘못된 경우다. 이때는 사람이 내용을 보정한 뒤 원본 토픽에 새로 발행한다.

어느 쪽이든 **컨슈머의 멱등성이 전제**다. 재투입한 메시지가 사실은 이미 부분적으로 처리됐을 수 있고(예: DB에는 저장됐는데 후속 API 호출에서 실패해 DLQ로 갔다), 재투입 도구가 중복 발행할 수도 있다. **같은 메시지를 두 번 처리해도 결과가 한 번과 같아야** 재투입이 안전한 작업이 된다.

운영 루프 전체를 그리면 이렇다.

```
DLQ 유입 ──> 알림 발송 ──> 헤더의 예외 정보로 원인 분류
                                    |
              ┌─────────────────────┼─────────────────────┐
              v                     v                     v
         코드 버그              외부 장애            데이터 오류
              |                     |                     |
         수정 후 배포          복구 확인             수동 보정 또는
              |                     |               비즈니스 협의 후 폐기
              └─────────┬───────────┘                     |
                        v                                 v
                DLQ에서 재소비                    근거를 남기고 종결
                        |
                        v
                DLQ 비움 확인 (랙 0 복귀)
```

비유하면 **DLQ는 병원이다** — 줄을 막는 환자를 일단 대기열에서 빼내(흐름 유지), 차트를 붙이고(진단 헤더), 치료 후 일상에 복귀시킨다(재투입). 시체 안치소처럼 운영하는 순간 데이터 유실과 같아진다.

(가산점 포인트: DLQ 재투입 시 메시지는 "실패 당시의 코드"가 아니라 **"수정된 현재 코드"로 처리된다.** 그 사이 스키마가 진화했다면 구버전 메시지를 현재 컨슈머가 읽을 수 있는지 — 하위 호환성 — 를 먼저 확인해야 한다고 짚으면 좋다. 특히 DLQ에 며칠씩 묵은 메시지가 있다면 실제로 자주 문제가 된다. 06번 문서 참고.)

## 4. 꼬리질문 대비 포인트

### "재시도 횟수 제한 없이 성공할 때까지 재시도하면 안 되나?"

영구적 실패(잘못된 페이로드, 코드 버그)는 몇 번을 해도 실패하므로 무한 재시도는 poison pill이 된다.

연쇄는 이렇게 이어진다. **그 파티션의 뒤 메시지 전체가 멈추고 → 재시도 대기 시간이 `max.poll.interval.ms`를 넘으면 브로커가 컨슈머를 그룹에서 제외해 리밸런싱이 발생하고 → 재할당받은 다른 컨슈머도 같은 메시지에서 막히므로 → 그룹 전체가 리밸런싱 루프에 빠진다.**

**재시도는 반드시 "횟수 제한 + 초과 시 DLQ"와 세트다.** 끝이 없는 재시도는 재시도가 아니라 장애다.

### "재시도 토픽 방식을 쓰면 무엇을 잃나?" (시니어 변별 포인트)

**같은 키의 순서 보장을 잃는다.** 실패 메시지가 재시도 토픽으로 빠진 사이 원본 파티션의 후속 이벤트가 먼저 처리되므로, "상태 변경 → 후속 처리"처럼 순서가 정합성의 전제인 도메인에서는 논블로킹 재시도가 곧 버그다.

대응은 두 가지다.

1. **순서 민감 도메인은 블로킹 재시도로 간다.** 지연을 감수하고 순서를 지킨다.
2. **키 단위 순서 유지 로직을 얹는다.** 재시도 중인 키를 컨슈머가 기억해 두었다가, 그 키의 후속 메시지가 오면 함께 보류하거나 같은 재시도 경로로 보낸다.

다만 2번은 구현 복잡도가 크다 — 재시도 중인 키 목록을 어디에 둘 것인지, 컨슈머가 재시작하면 그 목록은 어떻게 되는지, 보류된 메시지가 쌓이면 결국 파티션이 막히는 것 아닌지까지 답해야 한다. 그래서 **"그 복잡도를 감수할 만큼 논블로킹이 필요한가"부터 되묻는 것**이 실무 판단이다. 트레이드오프를 도메인 요구로 환원해 답하는 것이 변별 포인트다.

### "어떤 예외는 재시도하고 어떤 예외는 바로 DLQ로 보내나?"

기준은 **"시간이 지나면 결과가 달라지는가"**다.

타임아웃·커넥션 실패·락 경합은 일시적이라 재시도 가치가 있고, 역직렬화 실패·검증 실패·NPE는 영구적이라 재시도가 무의미하므로 즉시 DLQ로 보낸다.

코드로는 예외 타입을 분리해 에러 핸들러에 등록한다(Spring Kafka의 `addNotRetryableExceptions`). 이 분류를 안 하면 **영구 실패 메시지가 재시도 횟수만큼 파티션을 붙잡아** 정상 메시지들의 지연을 키운다. 2-1에서 본 대로 그 지연이 `max.poll.interval.ms` 압박으로도 이어진다.

### "재시도하면 중복 처리가 생길 수 있지 않나?"

생긴다. 경로가 둘이다.

- **처리는 성공했는데 오프셋 커밋 전에 실패한 경우** — 재시도가 곧 중복이다.
- **DLQ 재투입** — 이미 일부 처리된 메시지를 다시 흘려보내는 것이므로 중복 가능성이 있다.

Kafka의 기본 세계관이 **at-least-once**(최소 한 번 전달, 중복 허용)이므로 재시도/DLQ 설계는 **멱등 컨슈머를 전제로 성립**한다. 이벤트 고유 키로 처리 이력을 기록해 두 번째 처리를 건너뛰는 방식이 대표적이다(04번 문서).

**"재시도 설계와 멱등성 설계는 한 몸"**이라고 묶어 답하면 좋다. 멱등하지 않은 컨슈머에 재시도를 붙이는 것은 중복 처리를 늘리는 장치를 다는 것과 같다.

### "DLQ에 쌓인 메시지는 실제로 어떻게 운영하나?"

3-3의 운영 루프를 순서대로 말하면 된다.

**들어오는 즉시 알림 → 헤더의 예외 정보로 원인 분류(코드 버그 / 외부 장애 / 데이터 오류) → 원인 수정 → 재투입 도구로 원본 처리 경로에 다시 투입 → 재투입 후 DLQ 비움 확인.**

데이터 오류처럼 재처리가 불가능한 건은 비즈니스 부서와 협의해 수동 보정하거나 폐기를 결정하고, **그 근거를 반드시 남긴다.** 나중에 "이 데이터는 왜 없나"라는 질문이 반드시 온다.

**"DLQ에 넣는 것"이 아니라 "DLQ에서 꺼내는 것"까지가 설계**라는 답이 핵심이다.

> **RabbitMQ에서의 대응**: 재시도 토픽 대신 `x-dead-letter-exchange`와 TTL 대기 큐를 엮어 브로커가 타이머 역할을 한다. requeue 무한 루프라는 고유 함정을 포함해 `14-rabbitmq-retry-dlx-dlq.md`에서 다룬다.

## 한 줄 요약

파티션은 오프셋 하나로만 진행 상태를 표현하는 한 줄 대기열이라 실패 메시지 하나를 무한 재시도하면 뒤 전체가 멈추고(poison pill) 대기 시간이 `max.poll.interval.ms`를 넘겨 리밸런싱까지 부르므로, 실패를 일시적/영구적으로 분류해 일시적 실패만 제한 횟수로 재시도(순서가 중요하면 블로킹, 흐름이 중요하면 재시도 토픽)하고 나머지는 진단 헤더를 붙여 DLQ로 치운 뒤 — 유입 알림·원인 분류·재투입까지 이어지는 운영 루프를 멱등 컨슈머 위에 세우는 것이 재시도/DLQ 설계의 전부다.
