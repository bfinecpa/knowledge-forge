# 최종 일관성과 UX — "결제했는데 왜 안 보여요"를 다루는 법

> 핵심 관전 포인트: **이벤트 기반 아키텍처에서 쓰기와 그 결과가 조회에 반영되는 시점 사이의 지연은 버그가 아니라 설계의 속성이다. 따라서 대응도 두 축으로 간다. 기술 축 — 사용자가 자기 행동의 결과는 즉시 보게 만드는 read-your-own-writes(응답에 결과 포함, 쓰기 경로 조회 라우팅, 버전 토큰)와, "처리중"이라는 정직한 중간 상태를 도메인과 화면에 도입하는 것. 제품 축 — "몇 초까지 허용 가능한가"를 기획과 협상해 SLA로 못 박고, 컨슈머 랙을 그 SLA 기준으로 모니터링하는 것. 그리고 돈·권한처럼 즉시성이 필수인 구간은 애초에 동기 범위에 남긴다.**

---

## 0. 질문 + 의도

**질문**: "이벤트 기반 아키텍처에서 최종 일관성(eventual consistency)으로 인한 UX 문제를 어떻게 다루나요?"

**출제 의도**: "구매했는데 이용권이 아직 안 보여요"를 기술 문제이자 제품 문제로 다루는지 본다. 기획자와 "몇 초까지 허용 가능한가"를 협상하는 역할까지 백엔드의 일임을 아는 사람인지 — 즉 아키텍처 선택의 대가가 사용자 화면에 어떻게 나타나는지를 끝까지 추적하는 시야를 확인한다.

## 1. 왜 생기는가 — 지연은 아키텍처의 청구서다

### 1-1. 전제 지식 — "일관성"이라는 말이 뜻하는 것

먼저 용어부터 정리하고 들어가자. 이 문서의 모든 논의가 이 두 단어의 차이 위에 서 있다.

**강한 일관성(strong consistency)**은 "쓰기가 완료된 직후, 누가 어디서 읽어도 그 새 값이 보인다"는 보장이다. 단일 DB에 `COMMIT`하고 바로 `SELECT`하면 방금 쓴 값이 나오는 것, 이게 우리가 익숙한 세계다.

**최종 일관성(eventual consistency)**은 "언젠가는 모든 읽기 경로가 같은 값으로 수렴한다"는 보장이다. eventual은 "결국"이라는 뜻이다. 즉 **수렴한다는 것은 약속하지만 언제 수렴하는지는 약속하지 않는다.** 이름 자체가 시간 보장의 부재를 드러내고 있다.

여기서 중요한 것은, 최종 일관성이 우리가 실수로 떠안은 것이 아니라 **선택한 대가**라는 점이다. 결제 서비스와 이용권 서비스를 분리하고 그 사이를 Kafka로 이었을 때 우리가 산 것은 가용성(한쪽이 죽어도 다른 쪽이 산다), 처리량(각자 자기 속도로 처리한다), 낮은 결합(서로의 API를 직접 호출하지 않는다)이다. 지연은 그 물건값이다.

그래서 "지연을 없애자"는 방향은 애초에 성립하지 않는다. 지연을 없애려면 비동기를 되돌려야 하고, 그러면 산 것을 도로 반납하는 것이다. 과제는 **지연을 없애는 것이 아니라 지연을 사용자가 실패로 오인하지 않게 만드는 것**이다.

### 1-2. 지연이 어디서 쌓이는가

전형적인 흐름을 단계별로 펼쳐 보면 지연이 어디에 붙는지 보인다.

```text
[결제 서비스] 결제 승인 + DB 커밋
   -> (outbox 폴링/CDC) 이벤트 발행
   -> [Kafka] 파티션 적재
   -> [이용권 서비스] 컨슈머가 poll -> 처리 -> 이용권 테이블 커밋
   -> 사용자가 "내 이용권" 화면 조회
```

각 화살표가 지연 한 조각씩이다.

| 구간 | 무엇 때문에 걸리는가 | 평상시 |
|---|---|---|
| 커밋 -> 발행 | 릴레이의 폴링 주기, 또는 CDC 반영 지연 | 수십 ms |
| 발행 -> 적재 | 프로듀서 배치·네트워크·`acks` 대기 | 수 ms |
| 적재 -> poll | 컨슈머의 poll 주기, 백로그(랙) | 수십 ms |
| poll -> 커밋 | 컨슈머 처리 시간, 다운스트림 호출 | 수십~수백 ms |

평상시에는 전체가 수백 ms라 아무도 눈치채지 못한다. 화면을 갱신하는 사이에 이미 끝나 있기 때문이다.

문제는 **컨슈머 랙이 쌓이는 순간**이다. 랙은 "브로커에는 도착했는데 아직 처리하지 못한 메시지"를 말한다. 처리 속도가 유입 속도보다 낮아지면 이 백로그가 계속 자라고, 그러면 위 표의 "적재 -> poll" 한 칸이 수십 ms에서 수십 초, 수 분으로 늘어난다. 나머지 구간은 그대로인데 이 한 칸만 커지는 것이다. 랙의 진단과 해소는 같은 장의 `31-consumer-lag-diagnosis-and-resolution.md`에서 따로 다룬다.

그리고 이때가 정확히 "이용권이 안 보여요" CS가 몰려오는 시점이다.

### 1-3. 사용자는 지연을 실패로 읽는다

사용자는 아키텍처를 모른다. Kafka도 컨슈머도 랙도 모른다. 사용자가 아는 것은 하나다 — **"돈을 냈는데 화면에 아무것도 없다."**

그리고 사람은 그 상황에서 예측 가능한 세 가지 행동을 한다.

첫째, **새로고침을 연타한다.** 이게 왜 나쁜가. 지연이 나는 순간은 시스템이 이미 힘들어하는 순간인데, 바로 그 순간에 조회 트래픽이 몇 배로 뛴다. 아픈 시스템을 더 때리는 되먹임이 생긴다.

둘째, **다시 산다.** 이것이 가장 위험하다. 첫 결제는 성공했고 지급만 늦은 것인데 사용자는 실패로 판단하고 재구매를 누른다. 중복 결제 방지 가드가 없으면 그대로 두 번 결제된다.

셋째, **CS에 문의한다.** 상담원은 "지금 처리 중입니다"라고 말할 근거가 화면에 없다. 시스템이 중간 상태를 표현하지 못하면 상담 대응도 불가능하다.

세 행동 모두 근본 원인이 같다. **시스템이 "지금 진행 중"이라는 사실을 사용자에게 전달할 방법을 갖고 있지 않다.** 이 문서의 나머지는 그 방법을 기술 축과 제품 축으로 나눠 만드는 이야기다.

## 2. 기술 축 — 내 결과는 즉시, 나머지는 정직하게

### 2-1. read-your-own-writes — 자기가 쓴 것은 자기가 즉시 읽는다

#### 무엇을 보장한다는 말인가

**read-your-own-writes(RYOW)**는 "한 사용자가 방금 쓴 데이터는, 그 사용자 자신이 곧바로 읽었을 때 반드시 보인다"는 보장이다. 우리말로 옮기면 "자기가 쓴 것은 자기가 읽는다"다.

주의해서 볼 것은 **보장하지 않는 것**이다. RYOW는 그 값이 **다른 사용자에게** 언제 보이는지는 전혀 약속하지 않는다. 내가 산 이용권이 내 화면에는 즉시 보이지만, 옆 사람의 통계 대시보드에는 30초 뒤에 반영돼도 RYOW는 지켜진 것이다.

이 "보장 범위를 한 사람으로 좁힌 것"이 RYOW의 전부이자 핵심이다. **최종 일관성 전체를 포기하지 않으면서, 사용자 한 명의 체감만 즉시 일관되게 만드는 절충**인 것이다.

#### 왜 이 절충이 훨씬 싼가

강한 일관성과 비교하면 값 차이가 분명해진다.

강한 일관성을 만들려면 **모든 조회 경로가 항상 최신을 봐야 한다.** 실무에서 이것은 조회 모델(캐시, 읽기 전용 레플리카, CQRS의 read model)을 못 쓴다는 뜻이거나, 쓸 거면 동기 복제로 묶어 쓰기 응답이 복제 완료까지 기다린다는 뜻이다. 어느 쪽이든 조회 모델을 둔 이유 자체가 사라진다.

RYOW는 **방금 쓴 그 사용자의 조회에만** 특별 취급을 한다. 대상이 얼마나 적은지 숫자로 감을 잡아보자. 쓰기가 초당 100건이고 특별 취급 창을 5초로 잡으면, 어느 순간에도 대상자는 최대 100 x 5 = 500명이다. 전체 조회가 초당 10,000건이라면 그중 특별 취급이 필요한 몫은 극히 일부다. **나머지 절대다수의 조회는 여전히 값싼 조회 모델이 받는다.**

그리고 앞서 봤듯 사용자 불만은 대부분 남의 데이터가 아니라 **자기 행동의 결과**가 안 보일 때 나온다. 그러니 값의 극히 일부만 내고 체감 문제의 대부분을 없애는 셈이다. 이것이 RYOW가 최종 일관성 시스템의 기본 처방인 이유다.

#### 구현 1 — 쓰기 응답에 결과를 담는다

가장 싸고, 그래서 가장 먼저 시도할 방법이다.

```java
// Before: 쓰기는 명령만 던지고, 화면은 이벤트로 갱신되는 조회 모델만 본다
POST /purchases -> 202 Accepted (본문 없음)
GET  /my/passes -> 아직 컨슈머가 처리 전이라 빈 목록   // "안 보여요"

// After 1: 쓰기 응답에 결과를 담아 클라이언트가 화면을 직접 갱신
POST /purchases -> 200 { "passId": 7, "status": "ACTIVE", ... }
// 클라이언트는 응답으로 받은 이용권을 목록에 즉시 추가(낙관적 UI).
// 조회 모델이 따라잡기 전까지의 공백을 클라이언트 상태가 메운다.
```

이 방식의 정체를 정확히 이해하는 것이 중요하다. **서버가 일관성을 보장하는 것이 아니라, 클라이언트가 자기 메모리에 들고 있는 값으로 공백을 메우는 것**이다. 조회 모델은 여전히 뒤처져 있고, 화면만 앞서 있다.

그래서 통하는 상황과 안 통하는 상황이 명확히 갈린다.

**통하는 상황**은 쓰기 직후 같은 화면에서 결과를 보여줄 때다. 구매 버튼을 누른 그 화면에서 "이용권 1장 추가됨"을 그리는 경우.

**안 통하는 상황**은 그 화면을 벗어나는 순간 전부다. 사용자가 다른 탭으로 갔다가 돌아오면 클라이언트는 서버에서 목록을 다시 받아오고, 그 목록에는 아직 이용권이 없다. 새로고침해도 없다. 폰으로 열어도 없다. **클라이언트 메모리에만 있던 보장이라 메모리가 날아가면 같이 날아간다.**

즉 구현 1은 "그 순간 그 화면"만 덮는다. 그것만으로 충분한 서비스도 많지만, 충분하지 않다면 다음으로 간다.

#### 구현 2 — 쓰기 경로로 조회를 라우팅한다

**방금 쓴 사용자의 조회만 조회 모델이 아니라 원본(쓰기) 저장소로 보낸다.** 서버가 보장하므로 화면을 이동하든 새로고침하든 성립한다.

```text
[일반 사용자의 조회]  GET /my/passes -> 조회 모델(레플리카/read model)
[방금 쓴 사용자의 조회] GET /my/passes -> 원본 DB(쓰기 저장소)
                                          ^ 여기만 예외 취급
```

여기서 진짜 설계 문제는 "원본으로 보낸다"가 아니라 **"이 사용자가 방금 썼다는 것을 서버가 어떻게 아는가"**다. 라우팅 판단 근거를 어디에 두느냐가 이 방식의 전부다.

근거는 결국 "이 사용자의 마지막 쓰기 시각"이고, 그것을 둘 곳은 두 군데다.

**(가) 쿠키에 둔다.** 쓰기 응답에서 `Set-Cookie: lastWriteAt=...`을 내려주면 클라이언트가 이후 모든 요청에 자동으로 실어 보낸다. 서버는 무상태를 유지할 수 있고 추가 저장소도 필요 없다. 대신 **클라이언트가 조작할 수 있다** — 누구나 쿠키를 심어 모든 조회를 원본으로 보낼 수 있고, 그것은 곧 조회 모델을 우회해 원본 DB에 부하를 거는 통로가 된다. 그리고 쿠키를 안 쓰는 진입 경로(서버 간 호출, 일부 네이티브 앱 클라이언트)에서는 아예 안 통한다.

**(나) 서버 쪽 세션 저장소(예: Redis)에 둔다.** 쓰기가 끝나면 `ryow:{userId}`에 TTL을 걸어 기록하고, 조회 때 그 키의 존재 여부로 판단한다. 조작이 불가능하고 TTL 만료가 자동으로 특별 취급을 해제해 준다. 대신 **조회마다 Redis 조회가 한 번 더 붙는다.**

```java
// After 2: 쓰기 직후 그 사용자의 조회만 원본으로 보낸다
@PostMapping("/purchases")
public PurchaseResponse purchase(@AuthenticationPrincipal Long userId, ...) {
    PurchaseResponse res = purchaseService.purchase(userId, ...);
    // TTL = 허용 지연 SLA와 같은 값으로 잡는다(3절). SLA가 5초라면
    // 5초 뒤에는 조회 모델이 따라잡았을 것이라고 보는 것이다.
    redis.setex("ryow:" + userId, Duration.ofSeconds(5), "1");
    return res;
}

@GetMapping("/my/passes")
public List<PassView> myPasses(@AuthenticationPrincipal Long userId) {
    // 이 사용자가 최근에 썼는가? 그렇다면 뒤처진 조회 모델 대신
    // 반드시 최신인 원본을 읽게 한다.
    boolean recentlyWrote = redis.hasKey("ryow:" + userId);
    return recentlyWrote
        ? passQuery.fromPrimary(userId)   // 원본(쓰기) 저장소
        : passQuery.fromReplica(userId);  // 조회 모델
}
```

TTL 값이 그냥 아무 숫자가 아니라는 점을 짚어두자. **TTL은 곧 "우리가 약속한 허용 지연"이다.** 3절에서 기획과 합의할 그 숫자가 여기 그대로 들어간다. TTL을 길게 잡을수록 보장은 두터워지지만 원본으로 새는 트래픽이 늘어난다 — 조회 부하를 원본에서 떼어내려고 조회 모델을 만들었는데 그것을 다시 붙이는 것이므로, TTL은 "필요한 만큼만 짧게"가 원칙이다.

**안 통하는 상황**도 있다. 사용자를 식별할 수 없는 비로그인 경로에서는 "누가 방금 썼는지"를 특정할 수 없다. 그리고 원본 저장소가 그 추가 부하를 감당할 수 있다는 전제가 필요하다.

#### 구현 3 — 버전 토큰으로 "이 버전 이상"을 요구한다 (가산점 포인트)

가장 정확하고 가장 비싸다.

발상은 이렇다. 쓰기 응답에 **"이 쓰기가 만들어낸 버전"**을 담아 클라이언트에 준다. 클라이언트는 이후 조회 요청에 그 토큰을 실어 보내면서 사실상 이렇게 요구한다 — **"나는 이 버전 이상이 반영된 결과만 받겠다."** 서버는 조회 모델이 그 버전에 도달했는지 확인하고, 아직이면 두 가지 중 하나를 한다.

- **잠깐 기다린다.** 짧은 시간(예: 수백 ms) 안에 조회 모델이 따라잡으면 그때 응답한다.
- **원본으로 우회한다.** 기다리지 않고 최신이 확실한 원본을 읽는다.

버전이 무엇이 되는가가 Kafka 문맥에서는 자연스럽게 정해진다. 쓰기 응답에 **그 이벤트가 적재된 파티션과 오프셋**을 담고, 조회 서비스는 자기 컨슈머가 그 파티션을 어디까지 처리했는지와 비교하면 된다.

```text
[쓰기]  POST /purchases
        -> 200 { "passId": 7, "readToken": "passes-3:184920" }
                                            토픽-파티션 : 오프셋

[조회]  GET /my/passes   X-Read-Token: passes-3:184920
        서버: 이용권 조회 모델의 파티션 3 처리 지점은 지금 184915다.
              184920에 아직 못 미쳤다.
              -> (a) 200ms 대기 후 재확인, 또는 (b) 원본 조회로 우회
```

이 방식의 값은 **어떤 진입 경로에서도 성립한다**는 데 있다. 토큰이 클라이언트 손에 있으므로 새로고침해도, 앱을 껐다 켜도, 다른 기기에 토큰을 넘겨도 보장이 따라간다. 구현 1처럼 화면 하나에 묶이지 않고, 구현 2처럼 서버가 사용자를 식별해야만 하는 것도 아니다.

비용은 세 군데서 발생한다. **조회 API 계약이 바뀐다** — 모든 조회가 토큰 파라미터를 받아야 한다. **조회 서비스가 자기 진행 지점을 밖으로 노출해야 한다** — 내부 구현이던 것이 API 계약의 일부가 된다. 그리고 **대기 방식을 쓰면 요청 스레드를 그동안 점유한다** — 대기 상한을 반드시 두고, 넘으면 원본 우회나 "처리중" 응답으로 빠져야 한다.

**안 통하는 상황**은 토큰을 전달할 수 없는 진입 경로다. 메일 링크를 눌러 바로 들어온 화면이나 서버 사이드 렌더링의 첫 진입에는 토큰이 없다. 그때는 토큰 없는 요청을 그냥 조회 모델로 보내고, 대신 "처리중" 상태(2-2)가 화면을 지키게 한다.

#### 세 방식 정리

| | 보장 범위 | 구현 비용 | 깨지는 지점 |
|---|---|---|---|
| 1. 응답에 결과 포함 | 그 화면, 그 순간 | 가장 낮음 | 화면 이동·새로고침·다른 기기 |
| 2. 쓰기 경로 라우팅 | 그 사용자의 모든 조회 | 중간 (판단 근거 저장소 필요) | 비로그인 경로, 원본 부하 |
| 3. 버전 토큰 | 토큰을 든 모든 요청 | 가장 높음 (조회 API 계약 변경) | 토큰 없는 진입 경로 |

셋은 배타적이지 않다. **1을 기본으로 깔고, 부족한 흐름에만 2를 얹고, 정확성이 정말 필요한 소수 흐름에 3을 쓰는** 조합이 현실적이다.

### 2-2. "처리중"은 화면 문구가 아니라 도메인 상태다

#### 상태가 모델에 없으면 화면은 그것을 그릴 수 없다

RYOW로 안 되는 경우가 있다. **처리 자체가 비동기 저편에서 끝나야 결과가 존재하는 경우**다 — 외부 결제망의 승인 확정, 배송 접수, 외부 정산 API 응답 같은 것들. 이때는 서버가 원본을 읽어도 보여줄 것이 아직 없다. 결과가 아예 만들어지지 않았기 때문이다.

여기서 흔히 나오는 대응이 "화면에 '처리 중입니다'라고 띄우자"인데, **이것은 프런트엔드 문구 작업이 아니다.** 왜 그런지 도메인 모델 쪽에서 보자.

```java
// Before: 주문 상태에 중간 상태가 없다
public enum OrderStatus {
    COMPLETED,   // 완료
    CANCELLED    // 취소
}
```

이 모델에서 조회 API가 표현할 수 있는 세계는 두 가지뿐이다 — **"그런 주문은 없다"**와 **"완료된 주문이다"**. 결제는 승인됐지만 후속 처리가 아직인 그 몇 초 동안, 서버가 정직하게 답할 수 있는 말이 이 둘 중에는 없다.

그래서 서버는 "없다"고 답하고, 화면은 그 응답을 그대로 그려 "구매 내역이 없습니다"를 띄운다. **"결제했는데 왜 안 보여요"는 UI 버그가 아니라 도메인 모델에 중간 상태가 없다는 사실의 표면화다.**

```java
// After: 중간 상태를 정식 도메인 상태로 승격한다
public enum OrderStatus {
    PENDING,     // 결제는 승인됐고 후속 처리(이용권 지급)가 진행 중
    COMPLETED,   // 후속 처리까지 끝나 확정됨
    FAILED       // 후속 처리가 확정 실패 — 사용자에게 재시도를 안내
}
```

이제 서버는 세 번째 답을 갖게 됐다. 그리고 이 한 줄의 enum 추가가 아래 것들을 전부 가능하게 만든다.

```text
Before: 화면이 즉시 "구매 완료!"를 보여줌
  -> 뒤에서 실패하면 완료라던 것이 사라짐 — 최악의 UX (신뢰 붕괴)

After: PENDING(처리중) 상태를 정식 도메인 상태로 추가
  -> 화면: "구매 처리 중입니다" + 완료되면 갱신
  -> 실패하면 "결제에 실패했습니다 (재시도)"로 정직하게 전이
```

상태 전이를 도식으로 보면 이렇다.

```text
        결제 승인
            |
            v
        [PENDING] ------ 이용권 지급 완료 ------> [COMPLETED]
         "처리중"                                    "완료"
            |
            +------- 지급 확정 실패 -------------> [FAILED]
            |                                     "실패 (재시도)"
            +------- 타임아웃(SLA 초과) ----------> 강등 UX + 운영 알림
```

**거짓 완료(화면이 먼저 "완료"라고 말하고 뒤에서 실패하는 것)가 왜 최악인가**도 이 그림에서 읽힌다. `PENDING`이 없으면 화면은 `COMPLETED`를 미리 그릴 수밖에 없고, 그 뒤에 실패하면 사용자는 **완료라고 봤던 것이 사라지는** 경험을 한다. "늦게 나오는 것"은 기다림이지만 "있다가 없어지는 것"은 신뢰 붕괴다. 둘의 무게는 전혀 다르다.

#### 같은 처방이 다른 문서에서도 나온다 — 의미적 잠금

이 처방에는 이름이 있다. **의미적 잠금(semantic lock)** — DB 락처럼 물리적으로 접근을 막는 것이 아니라, **데이터에 "아직 확정 아님"이라는 표식을 붙여 확정처럼 취급되지 않게 하는** 기법이라 "의미적"이라고 부른다.

같은 발상이 세 자리에서 나온다는 것을 연결해 두면 답이 훨씬 단단해진다.

- `10-payment-consistency/10-distributed-saga-compensation-idempotency.md`: Saga에는 격리성이 없어 중간 상태가 노출되므로, 주문을 `PENDING`으로, 이용권을 `INACTIVE`로 만들어 확정처럼 보이지 않게 한다.
- 같은 장의 `08-saga-choreography-orchestration-compensation.md`: 완주하지 못한 Saga의 중간 상태를 다른 로직이 확정치로 오독하지 않게 막는다.
- 이 문서: 후속 처리가 끝나기 전의 주문을 사용자 화면에 "처리중"으로 정직하게 보여준다.

셋 다 **"확정 전 데이터를 상태값으로 표시해 둔다"**는 하나의 처방이고, 대상만 다르다(다른 서비스의 로직 / 같은 시스템의 다른 코드 / 사용자의 눈).

그리고 `PENDING`이 있어야 비로소 **중복 구매 가드**가 성립한다. "이 사용자에게 이 상품의 `PENDING` 주문이 있으면 새 구매를 막는다"는 규칙은 `PENDING`이라는 상태가 모델에 존재해야만 쓸 수 있는 문장이다. 1-3에서 본 "다시 산다"는 위험한 행동이 여기서 차단된다.

#### 완료를 어떻게 알릴 것인가 — 세 방법의 대가

`PENDING`을 만들었으면 이제 "언제 끝났는지"를 사용자에게 전해야 한다. 방법은 셋이고, 각각 다른 대가를 낸다.

**(1) 폴링 — 클라이언트가 주기적으로 물어본다.** 가장 단순하고 어디서나 동작한다. 대가는 조회량이고, 이건 반드시 숫자로 계산해서 판단해야 한다.

**대기 사용자 수 x (1 / 폴링 주기) = 초당 추가 조회수**다. 대기 1만 명이 2초마다 폴링하면 10,000 / 2 = **초당 5,000 조회**다. 1분이면 30만 회다.

이 숫자에서 진짜 무서운 대목은 크기 자체가 아니라 **타이밍**이다. 대기자가 1만 명까지 쌓이는 상황은 곧 컨슈머 랙이 커진 상황이고, 그것은 시스템이 이미 힘들어하는 상황이다. **가장 아플 때 조회가 최대가 되는 구조**인 것이다. 1-3에서 본 "새로고침 연타"를 우리가 코드로 자동화해 준 셈이라고 봐도 된다.

그래서 폴링을 쓴다면 최소한 이 셋을 건다.

- **지수 백오프**: 1, 2, 4, 8, 16, 32초로 간격을 늘린다. 6회로 63초를 덮으면서 조회는 6번뿐이다. 고정 2초로 63초를 덮으려면 약 31회다.
- **최대 횟수 상한**: 무한 폴링을 클라이언트가 못 하게 강제하고, 상한을 넘으면 "완료되면 알림을 보내드립니다"로 전환한다.
- **경량 상태 확인 API 분리**: 이용권 목록 전체를 다시 내려주지 말고 `{ "status": "PENDING" }` 한 줄만 답하는 전용 엔드포인트를 만들고 짧은 TTL 캐시를 붙인다. 같은 5,000 QPS라도 비용이 자릿수 단위로 달라진다.

**(2) SSE(Server-Sent Events) — 서버가 밀어준다.** SSE는 HTTP 연결을 열어둔 채 서버에서 클라이언트로 한 방향으로 이벤트를 흘려보내는 방식이다. 완료 통지에 정확히 맞는 모양이다 — 클라이언트는 받기만 하면 되니까.

대가는 **연결 유지 비용**이다. 대기 1만 명이면 동시 연결 1만 개가 열려 있고, 그동안 서버·로드밸런서·프록시의 커넥션 슬롯을 점유한다. 프록시의 idle timeout에 끊기지 않도록 주기적 keep-alive 이벤트를 보내야 하고, 커넥션 상한도 손봐야 한다.

덜 알려진 대가가 하나 더 있다. **여러 인스턴스로 뜬 서버에서는 "그 사용자의 연결을 들고 있는 인스턴스"에만 알림이 도달해야 한다.** 완료 이벤트를 받은 인스턴스가 그 사용자의 연결을 갖고 있으리라는 보장이 없으므로, 이벤트를 전 인스턴스에 퍼뜨리는 장치(예: Redis pub/sub)가 하나 더 필요해진다. 폴링에는 없던 문제다.

**(3) 웹소켓 — 양방향 상시 연결.** 완료 통지라는 용도만 놓고 보면 **과하다.** 클라이언트가 서버로 보낼 것이 없는데 양방향 채널을 여는 것이기 때문이다. SSE의 대가를 전부 그대로 내면서 프로토콜 업그레이드, 연결 중 인증 갱신, 재연결 처리 같은 운영 부담이 더 붙는다. 채팅처럼 원래 양방향이 필요한 기능이 이미 웹소켓을 쓰고 있다면 거기에 얹는 것은 합리적이지만, 완료 통지 하나 때문에 새로 도입할 이유는 없다.

**(4) 푸시 알림**은 위 셋과 성격이 다르다. **앱을 떠난 사용자에게 닿는 유일한 수단**이다. 대신 도달이 보장되지 않고(OS 권한, 네트워크, 지연) 즉시성도 약하다. 그래서 화면 갱신을 대체하는 것이 아니라 **보완**한다 — 화면에 있는 동안은 폴링이나 SSE가, 떠난 뒤에는 푸시가 맡는 식이다.

| | 조회 부하 | 연결 자원 | 앱 떠난 뒤 | 적합한 규모 |
|---|---|---|---|---|
| 폴링 | 대기자 수에 비례해 증가 | 없음 | 안 됨 | 대기자가 적을 때 |
| SSE | 없음 | 동시 연결 수만큼 | 안 됨 | 대기자가 많고 실시간이 중요할 때 |
| 웹소켓 | 없음 | 동시 연결 + 운영 부담 | 안 됨 | 이미 웹소켓을 쓰고 있을 때 |
| 푸시 알림 | 없음 | 없음 | 됨 | 지연이 길어질 수 있을 때 |

어느 쪽을 고르든 전제는 하나로 같다. **`PENDING` 상태가 존재해야 한다.** 상태가 없으면 클라이언트는 무엇을 폴링할지도, 서버는 무엇의 완료를 통지할지도 정할 수 없다.

### 2-3. 선긋기 — 모든 것을 비동기로 하지 않는다

지금까지가 "비동기로 뺀 것을 어떻게 감당하는가"였다면, 그 앞에 던져야 할 질문이 있다. **애초에 무엇을 비동기로 뺄 것인가.**

기준은 하나다. **다음 화면이 그 결과에 의존하는가.**

- **의존한다면 동기 범위에 남긴다.** 돈이 오가는 확정, 권한 부여 같은 것들이다. 같은 트랜잭션 안에 두거나 동기 API 호출로 끝낸다. 여기를 비동기로 빼면 위에서 만든 모든 장치(RYOW, `PENDING`, 완료 통지, 강등 UX)를 다 만들고도 사용자는 여전히 기다린다.
- **의존하지 않는다면 이벤트로 뺀다.** 알림 발송, 통계 적재, 추천 갱신처럼 **늦어도 아무도 안 다치는 것**들이다.

여기서 한 걸음 더 나가면 이 문서의 두 축이 만난다. **"무엇을 비동기로 뺄 수 있는가"의 판단 기준 자체가 UX 허용치다.** 즉 비동기/동기 경계는 순수한 기술 결정이 아니라 제품 결정이고, 그래서 다음 절이 필요하다.

## 3. 제품 축 — 허용 지연을 협상하고, 그 숫자로 감시한다

시니어가 갈리는 지점은 여기다. 최종 일관성의 지연 허용치는 엔지니어가 혼자 정하는 값이 아니라 **제품 결정**이다.

### 3-1. 기획과 SLA를 협상한다

던져야 할 질문은 한 문장이다. **"이용권 지급이 결제 후 몇 초까지 늦어도 되는가?"**

답에 따라 설계가 갈린다. **3초라면** RYOW로 충분하다 — 그 사용자 화면만 즉시 채워주고 조회 모델은 뒤에서 따라잡게 두면 된다. **0초여야 한다면** 그 구간은 비동기로 뺄 수 없다는 뜻이고, 동기 커밋 범위에 남겨야 한다.

즉 **이 질문의 답이 2-3의 경계선을 긋는다.** 그래서 이 질문은 아키텍처를 다 만든 뒤 확인 삼아 묻는 것이 아니라, 아키텍처를 정하기 전에 백엔드가 먼저 던져야 하는 질문이다. **이 순서를 말할 수 있는지가 변별 지점이다.**

협상은 서비스 전체에 하나의 숫자를 정하는 방식이 아니라 **흐름별로** 한다. 판단 근거는 "결과가 안 보이면 사용자가 무엇을 하는가"다.

| 흐름 | 안 보이면 사용자가 하는 행동 | 허용 지연 |
|---|---|---|
| 결제 -> 이용권 지급 | 재구매 시도(중복 결제 위험), CS 문의 | 초 단위 이하 |
| 주문 -> 배송 상태 갱신 | 새로고침, 잠시 후 다시 봄 | 수십 초 |
| 구매 -> 추천 목록 반영 | 아무것도 안 함 (인지조차 못 함) | 분 단위 |
| 활동 -> 통계 대시보드 | 아무것도 안 함 | 시간 단위 |

이 표가 말하는 것은 **지연의 비용이 흐름마다 다르다**는 것이다. 중복 결제로 이어지는 지연과 아무도 모르는 지연에 같은 기준을 적용할 이유가 없다.

### 3-2. 합의한 숫자가 그대로 모니터링 임계값이 된다

여기가 이 문서에서 가장 실질적인 연결이다. **기획과 합의한 SLA 숫자는 문서에 적히고 끝나는 것이 아니라, 컨슈머 랙 알람의 임계값으로 그대로 들어간다.**

그러려면 랙을 **개수가 아니라 시간으로** 봐야 한다. 왜 개수로는 판단이 안 되는지 계산해 보면 바로 드러난다.

```text
랙 10,000건, 컨슈머 처리율 5,000 msg/s -> 10000 / 5000 =   2초 지연  (정상)
랙 10,000건, 컨슈머 처리율   100 msg/s -> 10000 /  100 = 100초 지연  (장애)
```

**같은 "랙 1만 건"이 한쪽에서는 정상이고 다른 쪽에서는 장애다.** 개수만 보고는 어느 쪽인지 알 수 없다. 그래서 임계값을 개수로 잡으면 처리율이 바뀔 때마다 임계값을 다시 정해야 하고, 알람은 늑대소년이 된다.

시간으로 환산하면 그럴 일이 없다. 랙을 **"가장 오래된 미처리 메시지의 나이"**(브로커 적재 시각과 현재 시각의 차)로 재면, 그 값은 곧 "지금 이 순간 지급이 몇 초 늦고 있는가"다. **"랙 1만 건"은 판단이 안 되지만 "지급 지연 40초"는 즉시 대응 판단이 된다.**

그리고 이 숫자를 무엇과 비교할 것인가 — **3-1에서 합의한 SLA와 비교한다.**

```text
[협상 결과]  이용권 지급 SLA = 5초

[그대로 임계값이 된다]
  지급 지연 >  5초 (SLA 초과)  -> 경고 알람, 온콜 확인
  지급 지연 > 15초 (SLA x 3)   -> 심각 알람, 강등 UX 배너 발동
  지급 지연 > 60초             -> CS 사전 공지, 구매 버튼 가드 강화

[같은 숫자가 코드에도 들어간다]
  2-1 구현 2의 Redis TTL = 5초
  2-2 PENDING 타임아웃 전이 기준 = 5초
```

**제품 합의가 곧 모니터링 임계값이고, 동시에 코드의 상수다.** 세 자리에 같은 숫자가 들어간다는 것이 이 설계의 핵심이다. 반대로 말하면, **허용치를 정의한 적이 없는 시스템은 지연이 나도 그것이 장애인지 아닌지조차 판단할 수 없다.** 알람을 걸 기준이 없기 때문이다.

랙을 어떻게 재고 어떤 원인으로 분기해 진단하는지는 같은 장의 `31-consumer-lag-diagnosis-and-resolution.md`에서 다룬다. 이 문서의 몫은 **그 알람의 임계값이 어디서 오는가**에 답하는 것이다.

### 3-3. 지연은 반드시 오므로, 그날의 UX를 미리 만들어 둔다

마지막 한 조각은 **강등(degradation) UX**다. 랙이 SLA를 크게 넘는 상황이 오면 보여줄 것들을 미리 준비해 두는 것이다.

- **배너**: "현재 이용권 지급이 지연되고 있습니다. 결제는 정상 처리되었습니다." 두 번째 문장이 특히 중요하다 — 1-3의 "다시 산다"를 막는 문장이 이것이다.
- **CS 대응 문구**: 상담원이 볼 수 있는 주문 상태(`PENDING` + 경과 시간)와 안내 스크립트.
- **중복 구매 가드**: `PENDING` 상태인 동안 같은 상품의 구매 버튼을 비활성화하고, 서버에서도 차단한다. 클라이언트 비활성화만으로는 부족하다 — API를 직접 부르는 경로가 남기 때문이다.

이 배너를 장애가 터진 날 급하게 만들면 늦다. 그래서 **강등 UX는 기능 개발 시점에 함께 만드는 산출물**이지 장애 대응 절차가 아니다. 지연은 반드시 오고, 그날의 화면까지 설계해 두는 것이 이벤트 기반 아키텍처의 운영이다.

## 4. 꼬리질문 대비 포인트

### "read-your-own-writes를 구체적으로 어떻게 구현했나요/하겠나요?"

세 가지 중 시스템 형태에 맞는 것을 고른다.

1. **쓰기 응답에 결과를 담아 클라이언트가 화면 상태를 직접 갱신** — 가장 싸고 대부분 충분하다. 단, 화면을 벗어나면 보장이 사라진다는 한계를 함께 말해야 한다.
2. **쓰기 직후 그 사용자의 조회를 원본 저장소로 라우팅** — 서버가 보장하므로 클라이언트 수정이 필요 없다. 관건은 "최근에 썼다"는 판단 근거를 어디에 두느냐(쿠키는 무상태지만 조작 가능, 서버 세션은 안전하지만 조회 1회 추가)이고, TTL은 SLA와 같은 값으로 잡는다.
3. **버전 토큰으로 조회 모델의 따라잡음을 확인** — 어떤 진입 경로에서도 성립하지만 조회 API 계약이 바뀌고 조회 서비스가 자기 진행 지점을 노출해야 한다. 구현 비용이 가장 크다.

답의 핵심은 기법 나열이 아니라 **요구의 분해**다. **"본인 것만 즉시 보이면 되고 남의 화면은 몇 초 늦어도 된다"**는 분해를 먼저 말하면, 세 기법이 왜 전부 "한 사용자만 특별 취급"이라는 같은 모양인지가 설명된다.

### "그럴 거면 그냥 동기로 하면 되지 않나요?"

부분적으로 맞는 지적이라 **선긋기**로 답한다.

결과에 다음 행동이 의존하는 핵심 경로(결제 확정, 권한 부여)는 동기로 남기고, 지연이 허용되는 부가 경로만 비동기로 뺀다. 전부 동기로 묶으면 가용성과 처리량, 서비스 간 결합의 비용을 도로 내는 것이고, 전부 비동기로 빼면 UX 비용을 낸다.

**경계를 어디에 긋느냐가 설계 판단**이고, 그 기준이 바로 "이 결과는 몇 초까지 늦어도 되는가"다. 즉 이 꼬리질문의 답은 다음 질문의 답과 같은 뿌리에서 나온다.

### "허용 지연 시간은 누가 어떻게 정하나요?" (시니어 변별 포인트)

백엔드가 단독으로 정하는 값이 아니다.

흐름별로 **"안 보이면 사용자가 무엇을 하는가"**(재구매? 이탈? 무시?)를 기획·CS와 함께 따져 도메인별로 차등을 둔다 — 결제·권한은 초 단위 이하, 알림·통계는 분 단위 허용, 같은 식이다.

그리고 이 답의 진짜 무게는 뒷부분에 있다. **정한 숫자는 문서로 끝나는 게 아니라 컨슈머 랙 알림 임계값과 강등 UX 발동 조건으로 연결돼야 산다.** SLA 5초는 곧 "랙 나이 5초 초과 시 경고", "15초 초과 시 강등 배너", 그리고 RYOW 라우팅의 TTL 5초다. 같은 숫자가 협상 테이블과 알람 설정과 코드 상수에 동시에 들어간다.

마무리는 이 문장이 좋다. **"허용치를 정의한 적이 없는 시스템은 지연이 나도 그것이 장애인지 아닌지조차 판단할 수 없다."** 여기까지 말하면 운영 관점이 완성된다.

### "완료를 폴링으로 확인시키면 조회가 폭주하지 않나요?"

**폭주한다.** 그러니 숫자로 인정하고 시작하는 것이 좋다 — **대기 1만 명이 2초마다 폴링하면 초당 5,000 조회**이고, 1분이면 30만 회다. 더 나쁜 것은 그 부하가 **시스템이 가장 아플 때(랙이 쌓여 대기자가 많은 때) 최대가 된다**는 점이다.

그래서 폴링을 쓴다면 세 가지를 건다.

- **지수 백오프 + 최대 횟수를 클라이언트에 강제한다.** 1, 2, 4, 8, 16, 32초면 6회로 63초를 덮는다(고정 2초로 같은 시간을 덮으면 약 31회다).
- **경량 상태 확인 API로 분리하고 짧은 TTL 캐시를 붙인다.** 목록 전체를 다시 내려주는 조회와 `{ "status": "PENDING" }` 한 줄을 내려주는 조회는 비용이 자릿수 단위로 다르다.
- **상한을 넘으면 통지 방식으로 전환한다.** "완료되면 알려드릴게요"로 바꾸고 푸시로 넘긴다.

규모가 더 커지면 SSE나 웹소켓 push로 **"완료를 서버가 알려주는"** 구조로 바꾼다. 이때 대가가 조회량에서 **연결 유지 비용**으로 옮겨 간다는 점을 짚으면 좋다 — 동시 연결 1만 개, 프록시 idle timeout 대응, 그리고 여러 인스턴스 중 그 사용자의 연결을 들고 있는 인스턴스에만 이벤트를 보내기 위한 브로드캐스트 장치가 필요해진다. 공짜로 좋아지는 것이 아니라 **비용의 종류가 바뀌는 것**이다.

어느 쪽이든 **처리중 상태의 존재가 전제다.** 상태가 없으면 클라이언트는 무엇을 폴링할지조차 없다.

## 한 줄 요약

최종 일관성의 UX 문제는 지연을 없애는 게 아니라 — 자기 행동의 결과는 즉시 보이게 하고(read-your-own-writes), 나머지는 "처리중"이라는 정직한 도메인 상태로 보여주고, "몇 초까지 괜찮은가"를 제품 결정으로 합의해 그 숫자를 그대로 랙 알람 임계값과 코드 상수로 쓰는 것 — 즉 **지연을 사용자가 실패로 오인하지 않게 설계하는 일**이다.
