# 지연 메시지와 스케줄링 — TTL+DLX, delayed message 플러그인, 그리고 Kafka로는 왜 어려운가

> 핵심 관전 포인트: **"30분 뒤 미결제 주문 자동 취소", "3일 뒤 만료 알림" 같은 요구는 큐로 푸는 것이 자연스러워 보이지만, 큐에는 원래 시간 개념이 없다. 큐는 들어온 순서대로 즉시 내보낸다. 그래서 RabbitMQ에서는 우회가 필요하고 방법이 셋이다 — ① 컨슈머 없는 큐에 TTL을 걸어 만료되면 DLX로 흘리는 대기 큐 방식(브로커 기본 기능만으로 되지만 지연 시간마다 큐를 따로 만들어야 한다), ② `x-delayed-message` 플러그인으로 메시지마다 지연을 지정하는 방식(유연하지만 대량·장기 지연에 약하다), ③ DB에 예약 행을 넣고 스케줄러가 시각이 되면 발행하는 방식(가장 무겁지만 취소·조회·변경이 가능한 유일한 방법). 그리고 결정적 판단 기준이 하나 있다 — 예약을 취소해야 하는가. 브로커에 넣은 지연 메시지는 되돌릴 수 없다. 사용자가 5분 만에 결제하면 30분 뒤 취소 메시지는 이미 날아가고 있고, 그때 할 수 있는 것은 소비 시점에 "아직 유효한가"를 다시 확인하는 것뿐이다.**

---

## 0. 질문 + 의도

**질문**: "RabbitMQ에서 지연 메시지·스케줄링을 어떻게 구현하나요? (TTL + DLX vs delayed message exchange 플러그인) 같은 요구를 Kafka로 풀면 왜 어려운가요?"

**출제 의도**: "5분 뒤 재시도", "3일 뒤 만료 알림" 같은 흔한 요구를 브로커 기능으로 푸는 법을 아는지 본다. TTL+DLX의 head-of-line 함정까지 짚으면 실제로 구현해본 사람이다. 같은 요구가 Kafka에서 왜 어려운지 대비할 수 있으면 도구 선택의 근거를 갖춘 것이다.

## 1. 전제 — 큐에는 시간이 없다

### 1-1. 무엇이 문제인가

메시지 큐의 기본 계약은 "넣으면 컨슈머가 곧 가져간다"이다. 큐는 **가능한 한 빨리** 메시지를 내보내려 한다. "이건 30분 뒤에 주세요"라는 지시를 받을 자리가 애초에 없다.

그런데 실무 요구에는 시간이 자주 끼어든다.

- 미결제 주문을 **30분 뒤** 자동 취소
- 이용권 만료 **3일 전** 알림
- 실패한 결제를 **5분 뒤** 재시도
- 리뷰 요청을 배송 완료 **7일 뒤** 발송
- 장바구니 이탈 사용자에게 **1시간 뒤** 리마인드

이 요구들은 성격이 조금씩 다르고, 그 차이가 해법을 가른다. **지연 시간의 길이**와 **취소 가능성**이 핵심 변수다.

### 1-2. 세 가지 접근과 비교

먼저 전체 지도를 놓고 시작한다.

| | TTL + DLX 대기 큐 | delayed message 플러그인 | DB + 스케줄러 |
|---|---|---|---|
| 추가 설치 | 불필요 (기본 기능) | 플러그인 필요 | 불필요 |
| 지연 지정 | 큐 단위 (고정값) | 메시지 단위 (자유) | 자유 |
| 적합한 길이 | 초~분 | 초~분 | 분~일 이상 |
| 대량 예약 | 큐가 버퍼라 견딤 | **약함** | 강함 |
| 취소·변경 | 불가 | 불가 | **가능** |
| 조회 | 어려움 | 어려움 | **쉬움 (SQL)** |
| 정확도 | 낮음 (큐 앞머리 의존) | 보통 | 폴링 주기에 좌우 |

**"취소·조회가 필요하면 DB"**라는 한 줄이 이 표의 핵심이다. 나머지는 편의성의 문제지만 취소는 기능의 유무 문제다.

## 2. 세 가지 구현 방법 — 타이머를 누가 들고 있는가

세 방법을 하나씩 보기 전에 축을 하나 세워두면 나머지가 전부 그 위에 얹힌다. 축은 **"시간을 재는 일을 브로커에 맡기는가, 애플리케이션이 직접 지는가"**다.

TTL + DLX 대기 큐에서는 큐의 TTL 만료가 곧 타이머이므로 시간을 재는 일이 전적으로 브로커의 몫이다. 애플리케이션은 지연 종류마다 큐를 미리 선언해 두는 일만 진다. 플러그인 방식도 시간을 재는 주체는 브로커(정확히는 exchange)지만, 지연 값을 메시지마다 받는다는 점이 다르다. 애플리케이션이 "얼마나 뒤에"를 그때그때 정할 수 있는 대신, 지연 중인 메시지 전부를 exchange가 안고 있어야 하므로 부담은 오히려 브로커 쪽으로 더 쏠린다. DB + 스케줄러는 반대편 끝이다. 브로커는 타이머 역할을 전혀 하지 않고, 예약 시각을 기록하고 때가 됐는지 확인하는 일 전부를 애플리케이션이 진다.

이 축이 중요한 이유는 **여기서 취소 가능성이 곧바로 따라 나오기 때문**이다. 브로커가 시간을 들고 있으면 예약은 브로커 내부의 불투명한 상태가 되어 우리가 손댈 수단이 없다. 반대로 애플리케이션이 시간을 들고 있으면 예약은 우리 테이블의 한 행 — 조회하고 수정하고 지울 수 있는 평범한 데이터 — 가 된다. 1-2 표의 "취소·변경" 행이 왜 그렇게 갈리는지가 여기서 나오고, 3절에서 다룰 "취소할 수 없다는 문제"도 여기서 시작된다.

### 2-1. 방법 ① — TTL + DLX 대기 큐

#### 원리

RabbitMQ는 **메시지 TTL이 만료되면 그 메시지를 dead letter로 처리**한다. 큐에 `x-dead-letter-exchange`가 설정되어 있으면 그리로 흘러간다.

이 두 성질을 엮으면 타이머가 된다. **컨슈머가 없는 큐에 TTL을 걸어두면, 메시지는 아무에게도 배달되지 않고 그 자리에서 TTL이 다하기를 기다린다. 만료되는 순간 DLX를 통해 진짜 목적지로 이동한다.**

```
[발행]
   |
   v
[대기 큐: order.cancel.wait]
   - x-message-ttl: 1800000  (30분)
   - 컨슈머 없음  <- 이게 핵심. 아무도 안 가져가므로 만료까지 머문다
   - x-dead-letter-exchange: order.exchange
   - x-dead-letter-routing-key: order.cancel
   |
   | 30분 뒤 TTL 만료 -> dead letter 처리
   v
[order.exchange] --> [실행 큐: order.cancel] --> [취소 워커]
```

#### 구현

```java
// 대기 큐 — 컨슈머를 붙이지 않는다
@Bean Queue cancelWaitQueue() {
    return QueueBuilder.durable("order.cancel.wait")
            .ttl(30 * 60 * 1000)                       // 이 큐의 모든 메시지는 30분 뒤 만료
            .deadLetterExchange("order.exchange")      // 만료되면 여기로
            .deadLetterRoutingKey("order.cancel")      // 실행 큐로 라우팅
            .build();
}

// 실행 큐 — 여기에만 컨슈머를 붙인다
@Bean Queue cancelQueue() { return QueueBuilder.durable("order.cancel").build(); }

@Bean Binding cancelBinding(TopicExchange orderExchange) {
    return BindingBuilder.bind(cancelQueue()).to(orderExchange).with("order.cancel");
}

// 예약: 대기 큐에 직접 넣는다 (기본 exchange 사용)
public void scheduleCancel(Long orderId) {
    rabbitTemplate.convertAndSend("", "order.cancel.wait", new CancelCommand(orderId));
}
```

#### 반드시 알아야 할 함정 — head-of-line blocking

여기서 실무자와 책으로 배운 사람이 갈린다.

**RabbitMQ는 큐의 맨 앞 메시지만 만료 여부를 검사한다.** 뒤쪽 메시지는 앞의 것이 나가야 검사 대상이 된다. 큐 단위 TTL(`x-message-ttl`)이면 모든 메시지의 수명이 같으므로 앞의 것이 항상 먼저 만료되어 문제가 없다.

그런데 **메시지 단위 TTL(`expiration` 속성)로 서로 다른 지연을 주면 무너진다.**

```
대기 큐 (메시지마다 다른 TTL)

  [앞] TTL 30분 | TTL 5초 | TTL 5초 [뒤]
        ^^^^^^^
        이게 만료될 때까지 뒤의 5초짜리들은 검사조차 안 된다
        -> 5초짜리가 30분을 기다린다
```

그래서 규칙이 하나 나온다. **대기 큐 하나에는 같은 지연 시간만 담는다.** 5초·30초·5분이 필요하면 대기 큐를 세 개 만든다.

```java
@Bean Queue wait5s()  { return delayQueue("wait.5s",  5_000); }
@Bean Queue wait30s() { return delayQueue("wait.30s", 30_000); }
@Bean Queue wait5m()  { return delayQueue("wait.5m",  300_000); }
```

지연 값이 몇 종류로 고정되어 있으면(재시도 백오프처럼) 이 방식이 잘 맞는다. **사용자마다 임의의 시각을 예약해야 한다면 큐를 무한정 만들 수 없으므로 이 방식은 부적합하다.**

#### 장단점

**장점**: 플러그인 없이 기본 기능만으로 된다. 대기 큐도 그냥 큐이므로 **대량으로 쌓여도 큐의 일반적 특성(디스크로 내려감)이 그대로 적용**된다. 브로커 재시작에도 살아남는다(durable + persistent).

**단점**: 지연 종류마다 큐가 필요하다. 정확도가 높지 않다(만료 검사가 큐 앞머리에서만 일어나므로 부하 상황에서 늦어질 수 있다). 그리고 **예약을 취소할 수 없다.**

### 2-2. 방법 ② — delayed message exchange 플러그인

#### 원리

`rabbitmq_delayed_message_exchange` 플러그인을 설치하면 `x-delayed-message`라는 새 exchange 타입을 쓸 수 있다. 이 exchange에 보낸 메시지는 **바로 라우팅되지 않고 exchange가 붙들고 있다가, 지정한 지연이 지나면 그때 라우팅한다.**

지연은 메시지 헤더 `x-delay`에 밀리초로 넣는다.

```java
// exchange 선언 — 내부적으로 어떤 라우팅을 흉내 낼지도 지정한다
@Bean CustomExchange delayedExchange() {
    Map<String, Object> args = new HashMap<>();
    args.put("x-delayed-type", "topic");   // 지연 후에는 topic처럼 라우팅
    return new CustomExchange("order.delayed", "x-delayed-message", true, false, args);
}

// 발행 — 메시지마다 다른 지연을 줄 수 있다
public void scheduleCancel(Long orderId, Duration delay) {
    rabbitTemplate.convertAndSend("order.delayed", "order.cancel",
        new CancelCommand(orderId),
        message -> {
            message.getMessageProperties()
                   .setHeader("x-delay", delay.toMillis());  // 이 메시지만의 지연
            return message;
        });
}
```

**메시지마다 지연을 자유롭게 줄 수 있다는 것**이 TTL 방식 대비 결정적 이점이다. 대기 큐를 종류별로 만들 필요가 없다.

#### 한계 — 언제 쓰면 안 되는가

플러그인은 편하지만 **범용 스케줄러가 아니다.** 다음 경우에는 피해야 한다.

**대량의 지연 메시지.** 지연 중인 메시지는 exchange가 자체 저장소에 들고 있다. 수십만~수백만 건이 동시에 대기하는 상황은 이 구조가 상정한 사용처가 아니다. 큐와 달리 일반적인 큐 관리 기능(디스크로 내리기, 길이 제한)이 그대로 적용되지 않는다.

**아주 긴 지연.** 며칠~몇 달짜리 예약을 브로커에 쌓아두는 것은 좋은 설계가 아니다. 그동안 브로커를 업그레이드하거나 재구축하면 그 예약들의 운명이 불투명해진다.

**고가용성이 필요한 경우.** 지연 중인 메시지의 복제·이관이 일반 큐만큼 매끄럽지 않다. 클러스터 구성과 버전에 따라 동작이 다를 수 있으므로 **쓰기 전에 반드시 자기 환경에서 노드 장애 시나리오를 시험해야 한다.**

**운영 정책.** 커뮤니티 플러그인이므로 매니지드 서비스에서는 설치가 불가능할 수 있다. 클라우드 관리형 RabbitMQ를 쓴다면 지원 여부부터 확인해야 한다.

#### 적합한 자리

**초~분 단위의 짧은 지연, 그리고 동시 대기 건수가 크지 않은 경우**다. 재시도 백오프, 몇 분 뒤 리마인드, 짧은 유예 후 처리 같은 것들이다.

이 범위 안에서는 TTL 대기 큐보다 훨씬 쓰기 편하다. 큐를 종류별로 만들 필요가 없고, 지연 값이 코드에서 그때그때 결정될 수 있다.

### 2-3. 방법 ③ — DB + 스케줄러

#### 언제 이것이 정답인가

앞의 두 방법에는 공통된 근본 한계가 있다. **브로커에 넣은 지연 메시지는 취소할 수도, 조회할 수도, 변경할 수도 없다.**

그런데 실무 요구는 대개 이렇게 생겼다.

- "결제하면 30분 뒤 취소 예약을 **없애야** 한다"
- "예약된 알림이 지금 몇 건인지 **보고 싶다**"
- "발송 시각을 **바꿔야** 한다"
- "이 사용자의 예약을 전부 **지워야** 한다" (탈퇴)

셋 다 브로커로는 불가능하고, **DB라면 전부 SQL 한 줄**이다.

#### 구조

```sql
CREATE TABLE scheduled_task (
    id            BIGSERIAL PRIMARY KEY,
    task_type     VARCHAR(50)  NOT NULL,   -- ORDER_CANCEL, EXPIRY_NOTIFY ...
    payload       JSONB        NOT NULL,
    execute_at    TIMESTAMPTZ  NOT NULL,   -- 실행 예정 시각
    status        VARCHAR(20)  NOT NULL,   -- PENDING, PUBLISHED, CANCELLED
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 스케줄러가 매번 때리는 쿼리이므로 인덱스가 필수다
CREATE INDEX idx_scheduled_task_due
    ON scheduled_task (execute_at)
    WHERE status = 'PENDING';
```

```java
@Scheduled(fixedDelay = 10_000)   // 10초마다 — 이 주기가 정확도의 상한이다
@Transactional
public void publishDueTasks() {
    List<ScheduledTask> due = repository.findDueTasks(
            Instant.now(), PageRequest.of(0, 500));   // 한 번에 처리할 상한을 둔다

    for (ScheduledTask task : due) {
        rabbitTemplate.convertAndSend(
                task.exchange(), task.routingKey(), task.payload());
        task.markPublished();
    }
}

// 취소는 그냥 UPDATE 한 줄
public void cancelScheduledCancel(Long orderId) {
    repository.cancelPending("ORDER_CANCEL", orderId);
}
```

여러 인스턴스가 동시에 도는 환경이라면 **같은 행을 두 인스턴스가 집어가지 않게** 해야 한다. `SELECT ... FOR UPDATE SKIP LOCKED`로 행을 잠그고 가져오는 방식이 가장 간단하다.

#### 대가

**정확도가 폴링 주기에 묶인다.** 10초마다 돌면 최대 10초 늦는다. 초 단위 정밀도가 필요하면 주기를 줄여야 하고, 그만큼 DB에 쿼리가 늘어난다.

**DB 부하가 생긴다.** 예약이 수백만 건이면 인덱스 설계와 파티셔닝이 필요하다.

**컴포넌트가 하나 늘어난다.** 스케줄러가 죽으면 예약이 전부 밀린다. 감시 대상이 하나 더 생긴다.

그럼에도 **취소·조회·변경이 필요한 순간 이 방식 외에 선택지가 없다.** 그리고 **긴 지연(시간~일)에는 이것이 유일하게 건전한 답**이다.

### 2-4. 조합이 실전 답인 경우가 많다

둘을 섞는 것이 실제로는 가장 흔하다.

```
긴 지연(3일 뒤 알림)   -> DB 스케줄러가 관리
      |
      | 실행 시각이 되면 발행
      v
   RabbitMQ 큐  -> 워커가 실제 발송 처리
      |
      | 발송 실패 시
      v
짧은 지연(5분 뒤 재시도) -> TTL 대기 큐
```

**"언제 실행할지"는 DB가 관리하고, "실행을 어떻게 분산 처리할지"는 큐가 관리한다.** 각자 잘하는 일을 맡기는 구조이며, 면접에서 이 그림을 그리면 도구의 역할을 정확히 이해했다는 인상을 준다.

## 3. 세 방법이 공통으로 못 하는 것, 그리고 Kafka와의 대비

여기까지가 구현 방법이다. 이제 세 방법을 모두 손에 쥔 상태에서 남는 두 가지를 본다.

하나는 **브로커에 시간을 맡기는 두 방법(①②)이 공통으로 못 하는 일** — 예약 취소 — 이다. 2절에서 세운 축의 직접적인 결과이고, 사정상 DB 방식으로 갈 수 없을 때 그 제약을 어떻게 견디는지가 실무의 답이 된다.

다른 하나는 **같은 요구를 Kafka로 가져가면 왜 더 어려워지는가**다. 앞의 것이 RabbitMQ 안에서 감수해야 할 한계라면, 이쪽은 애초에 어느 브로커를 고를지의 근거다. 두 이야기를 나란히 두면 "이 방법들의 한계는 여기까지지만, 그럼에도 다른 도구보다는 낫다"는 판단이 한 줄로 이어진다.

### 3-1. 취소할 수 없다는 문제 — 소비 시점 유효성 검사

#### 상황

30분 뒤 주문 취소를 예약했는데 사용자가 5분 만에 결제했다. 예약된 메시지는 이미 브로커 안에 있고 되돌릴 수 없다.

25분 뒤 그 메시지가 도착하면 워커는 **이미 결제된 주문을 취소하려 든다.**

#### 해법 — 실행할 때 다시 확인한다

브로커에서 취소할 수 없다면, **소비 시점에 "이 명령이 아직 유효한가"를 확인**하면 된다.

```java
// 잘못된 코드 — 메시지가 왔으니 실행한다
@RabbitListener(queues = "order.cancel")
public void handle(CancelCommand cmd) {
    orderService.cancel(cmd.getOrderId());   // 이미 결제된 주문도 취소해버린다
}

// 올바른 코드 — 실행 직전에 현재 상태를 확인한다
@RabbitListener(queues = "order.cancel")
public void handle(CancelCommand cmd) {
    Order order = orderRepository.findById(cmd.getOrderId()).orElse(null);
    if (order == null) return;                  // 이미 삭제됨

    if (order.getStatus() != OrderStatus.PENDING_PAYMENT) {
        // 예약할 때는 미결제였지만 그 사이 상태가 바뀌었다.
        // 이 명령은 유효기간이 지난 것이므로 조용히 버린다.
        log.debug("취소 예약 무효화: orderId={}, 현재 상태={}",
                  cmd.getOrderId(), order.getStatus());
        return;
    }
    orderService.cancel(cmd.getOrderId());
}
```

이 패턴에는 이름이 있다. **지연 메시지는 "명령"이 아니라 "확인 요청"으로 취급하라.** 메시지의 뜻이 "취소하라"가 아니라 "취소해야 하는지 확인하라"가 되면, 취소 불가라는 제약이 문제가 되지 않는다.

여기에 한 가지 더 보태면 완전해진다. **예약 시점의 상태 버전을 메시지에 담고, 소비 시점에 비교한다.** 상태 값만 보면 "결제 → 취소 → 다시 주문"처럼 같은 상태로 돌아온 경우를 구분하지 못하기 때문이다.

```java
// 예약할 때의 버전을 함께 담는다
new CancelCommand(orderId, order.getVersion());

// 소비할 때 비교 — 그 사이 상태가 한 번이라도 바뀌었으면 무효
if (order.getVersion() != cmd.getVersionAtSchedule()) return;
```

**"브로커에서 취소가 안 되므로 소비 시점 검증으로 대체한다"**는 이 설계는 지연 메시지를 실제로 운영해본 사람의 답이다. (가산점 포인트)

### 3-2. Kafka로는 왜 어려운가

#### 구조적 이유

Kafka의 파티션은 **순서가 고정된 로그**이고, 컨슈머는 오프셋을 순서대로 전진시키며 읽는다. 여기에 "이 레코드는 30분 뒤에 처리"라는 개념을 넣을 자리가 없다.

```
파티션:  [0][1][2][3][4][5]
              ^
         3을 30분 뒤에 처리하고 싶다.
         그런데 4, 5를 먼저 처리하면 오프셋이 5로 가고,
         그러면 3은 영영 다시 읽히지 않는다.
```

**오프셋이 "여기까지 처리했다"는 단일 숫자라서, 중간 하나를 건너뛰고 나중에 돌아오는 것을 표현할 수 없다.** RabbitMQ는 메시지마다 상태를 갖기 때문에 이 문제가 없다.

#### Kafka에서 쓰는 우회

**단계별 지연 토픽.** `retry-5s`, `retry-1m`, `retry-10m` 같은 토픽을 만들고, 각 토픽의 컨슈머가 **레코드의 타임스탬프를 보고 아직 시간이 안 됐으면 처리를 멈춘다.** 구체적으로는 컨슈머가 `pause()`로 파티션 소비를 일시 중지하고 정해진 시간이 지난 뒤 `resume()`한다. 지연 시간이 토픽마다 고정되어 있으므로 **파티션 앞머리 레코드가 준비되면 그 뒤도 준비된 상태**라는 성질을 이용한다.

RabbitMQ의 TTL 대기 큐와 발상이 같지만, **지연을 브로커가 아니라 컨슈머가 직접 관리해야 한다**는 점이 다르다. 컨슈머가 재시작하면 pause 상태가 사라지고 처음부터 다시 판단해야 하며, `max.poll.interval.ms`를 넘기지 않도록 주의해야 한다(오래 멈춰 있으면 그룹에서 쫓겨나 리밸런싱이 일어난다).

**외부 스케줄러.** 결국 DB나 별도 스케줄러를 두는 방식으로 가는 경우가 많다. 이 경우 Kafka는 "실행 시점의 전달 수단"일 뿐이고 지연 관리는 밖에서 한다.

#### 정리 — 도구 선택의 근거로 쓰기

이 대비는 면접에서 **"왜 RabbitMQ를 쓰는가"의 좋은 근거**가 된다.

**"지연·스케줄링이 요구사항에 많다면 RabbitMQ 쪽이 훨씬 자연스럽습니다. TTL과 DLX를 엮어 브로커가 타이머 역할을 해주고, 플러그인을 쓰면 메시지 단위 지연도 됩니다. Kafka는 로그의 순차성 때문에 컨슈머가 직접 pause/resume으로 지연을 관리해야 하고, `max.poll.interval.ms`까지 함께 신경 써야 합니다."**

반대로 **재처리(replay)가 필요하면 Kafka가 압도적**이라는 점을 함께 말하면 균형 잡힌 답이 된다.

## 4. 꼬리질문 대비 포인트

### "TTL 대기 큐에서 지연 정확도는 얼마나 되나요?"

**정확한 타이머가 아니다**라고 답해야 한다. 이유는 둘이다.

**첫째, 만료 검사는 큐 앞머리에서 일어난다.** 앞의 메시지가 나가야 뒤의 것이 검사된다. 큐 단위 TTL이면 순서가 맞아 문제가 적지만, 브로커가 바쁘면 검사가 늦어질 수 있다.

**둘째, 만료 후 라우팅과 배달에도 시간이 든다.** dead letter 처리 → DLX 라우팅 → 실행 큐 적재 → 컨슈머 배달의 단계를 거친다.

그래서 **초 단위 정확도를 요구하는 곳(경매 마감, 예약 발송 시각 준수)에는 부적합**하다. 그런 요구에는 DB + 짧은 주기 스케줄러가 낫고, 정말 초 단위가 중요하면 실행 시각을 미리 계산해 여유를 두는 설계가 필요하다.

### "지연 메시지가 수십만 건 쌓이면 어떻게 되나요?"

방식마다 다르다.

**TTL 대기 큐**는 그냥 큐이므로 일반적인 적체와 같은 문제를 겪는다 — 브로커 메모리를 쓰고, 임계치를 넘기면 alarm이 걸려 발행이 막힌다. 다만 큐의 저장 최적화(긴 큐를 디스크로 내리는 동작)가 적용되므로 어느 정도는 견딘다.

**플러그인**은 exchange 자체가 지연 중인 메시지를 들고 있으므로, 대량 상황에 대한 대비가 큐만큼 되어 있지 않다. **대량 예약에는 쓰지 않는 것이 안전하다.**

**DB 스케줄러**는 수백만 건도 인덱스만 맞으면 견딘다. 애초에 대량 데이터를 다루라고 만든 것이 DB다.

**"대량이면 DB"**가 여기서도 답이다.

### "예약을 취소해야 하는 요구가 있으면 어떻게 하나요?" (시니어 변별 포인트)

두 갈래로 답한다.

**첫째, 취소가 자주 일어나고 정확해야 하면 DB 스케줄러를 쓴다.** 브로커에는 애초에 취소 기능이 없으므로 우회가 아니라 도구 선택의 문제다.

**둘째, 브로커 방식을 유지해야 한다면 소비 시점 검증으로 대체한다.** 3-1에서 본 대로 메시지를 "명령"이 아니라 "확인 요청"으로 다루고, 상태와 버전을 비교해 무효한 것은 조용히 버린다.

여기에 한 가지 실무 관점을 덧붙이면 좋다. **무효 메시지가 쌓이면 자원 낭비**라는 점이다. 취소율이 높은 업무(예: 미결제 취소 예약 중 90%가 결제로 무효화됨)라면, 브로커에 90%의 쓸모없는 메시지를 넣고 있는 셈이다. 이 비율이 높으면 **DB 방식으로 옮기는 것이 자원 면에서도 유리**하다. 취소율을 지표로 보고 판단한다는 관점이 변별력이 있다.

### "그냥 스프링의 `@Scheduled`로 주기적으로 DB를 스캔하면 안 되나요?"

되고, 오히려 많은 경우 그것이 정답이다. 다만 **분산 환경에서 주의할 점**이 있다.

**첫째, 인스턴스가 여러 대면 중복 실행된다.** 같은 스케줄러가 3대에서 동시에 돌면 같은 예약을 3번 처리한다. `SELECT ... FOR UPDATE SKIP LOCKED`로 행 단위 잠금을 걸거나, 분산 락(Redis 등)으로 한 대만 돌게 해야 한다.

**둘째, 한 번에 처리할 양에 상한을 둔다.** 스케줄러가 한동안 멈췄다 재개되면 밀린 예약이 한꺼번에 쏟아진다. 상한 없이 처리하면 그 순간 다운스트림이 죽는다.

**셋째, 실행과 발행을 분리한다.** 스케줄러는 "시각이 됐다"만 판단하고 실제 작업은 큐에 넘긴다. 스케줄러가 직접 무거운 작업을 하면 한 건이 오래 걸릴 때 뒤의 예약이 전부 밀린다. **스케줄러는 트리거, 큐는 실행**이라는 역할 분리가 핵심이다.

### "지연 메시지가 중복 실행되면 어떻게 되나요?"

일반 메시지와 같은 문제이고 같은 해법이다 — **멱등 처리**. 다만 지연 메시지에는 고유한 위험이 하나 더 있다.

**같은 예약이 여러 번 등록되는 경우**다. 주문 생성 이벤트를 컨슈머가 두 번 처리하면 취소 예약이 두 건 걸린다. 30분 뒤 취소 명령이 두 번 오고, 두 번째는 이미 취소된 주문을 또 취소하려 한다.

그래서 **예약 등록 자체도 멱등**이어야 한다. DB 방식이라면 `(task_type, reference_id)`에 유니크 제약을 걸면 끝난다. 브로커 방식이라면 예약 등록 시점에 중복을 막을 수단이 없으므로, **소비 시점 검증에 의존할 수밖에 없다.** 이것 역시 DB 방식의 이점이다.

## 한 줄 요약

큐에는 시간 개념이 없으므로 지연은 우회로 만든다 — **짧고 종류가 고정된 지연은 TTL+DLX 대기 큐, 짧지만 값이 자유로운 지연은 delayed message 플러그인, 길거나 취소·조회가 필요하면 DB 스케줄러**이며, 브로커에 넣은 예약은 되돌릴 수 없으므로 지연 메시지는 항상 **"명령"이 아니라 "지금도 유효한지 확인하라는 요청"**으로 설계해야 한다.
