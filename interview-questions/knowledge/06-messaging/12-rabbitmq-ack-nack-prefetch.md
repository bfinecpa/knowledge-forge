# ack/nack과 prefetch(QoS) — RabbitMQ의 전달 보장 다이얼, 그리고 Kafka 오프셋과의 결정적 차이

> 핵심 관전 포인트: **ack는 "이 메시지를 처리 완료했으니 지워도 된다"는 컨슈머의 신고이고, prefetch는 "ack 안 한 메시지를 최대 몇 개까지 미리 받아둘 것인가"의 한도다. 둘의 조합이 유실·중복·처리량을 동시에 결정한다. auto-ack(자동 확인)은 브로커가 메시지를 보내는 즉시 지우므로, 컨슈머가 처리 중에 죽으면 그 메시지들은 흔적 없이 사라진다 — 게다가 prefetch 한도도 무력화되어 브로커가 컨슈머 메모리에 메시지를 무한정 밀어넣는다. Kafka와의 결정적 차이는 RabbitMQ는 메시지 단위로 상태를 추적하므로 순서를 건너뛴 ack이 가능하다는 것이다. Kafka의 오프셋은 "여기까지 처리했다"는 숫자 하나라 중간 한 건이 막히면 뒤가 전부 막히지만, RabbitMQ는 5번이 실패해도 6·7번을 먼저 ack할 수 있다. 이 차이가 실패 처리 설계 전체를 갈라놓는다.**

---

## 0. 질문 + 의도

**질문**: "RabbitMQ의 ack/nack과 prefetch(QoS)는 각각 무엇을 결정하나요? auto-ack의 위험은? (Kafka의 오프셋 커밋과 비교해서 설명해주세요)"

**출제 의도**: Kafka의 오프셋 커밋에 대응하는 RabbitMQ의 전달 보장 다이얼을 아는지 본다. auto-ack이 왜 유실이고 prefetch가 왜 처리량과 공정성을 동시에 좌우하는지 — 기본값으로 운영하다 장애를 겪어봤는지, 그리고 "메시지 단위 추적"과 "연속 진도"라는 두 모델의 차이를 구조적으로 설명할 수 있는지를 가린다.

## 1. 전제 — 브로커는 무엇을 알고 있어야 하는가

### 1-1. 문제의 출발점

브로커가 메시지를 컨슈머에게 보냈다. 이제 그 메시지를 지워도 되는가?

지우면 안 된다. 컨슈머가 처리 중에 죽을 수 있고, 그러면 메시지가 영영 사라진다. 그렇다고 안 지우면 큐가 무한정 커진다. 그래서 **"처리가 끝났다"는 신호를 받고 나서 지워야** 하고, 그 신호가 **ack(acknowledgement, 확인 응답)**다.

여기서 브로커가 안고 가야 할 상태가 생긴다. 메시지마다 지금 어느 단계인지 알고 있어야 한다.

```
[Ready]  아직 아무에게도 안 보냄
   |
   | 컨슈머에게 전달(deliver)
   v
[Unacked]  보냈고, ack을 기다리는 중  <- 브로커 메모리에 남아 있다
   |
   +-- ack        --> 삭제. 끝
   +-- nack/reject --> 큐로 복귀하거나(requeue) 폐기/DLX로
   +-- 채널·커넥션 끊김 --> 자동으로 [Ready]로 복귀 (redelivered 플래그 부착)
```

관리 콘솔의 큐 화면에 `Ready`와 `Unacked`가 따로 나오는 이유가 이것이다. **Unacked가 계속 높다면 컨슈머가 받아만 놓고 처리를 못 끝내고 있다는 뜻**이며, 이 지표 하나로 "컨슈머가 느리다"와 "컨슈머가 멈췄다"를 구분할 수 있다.

### 1-2. Kafka는 이 상태를 갖지 않는다

Kafka 브로커는 위 상태 전이를 **아예 관리하지 않는다.** 컨슈머가 어디까지 읽었는지를 나타내는 숫자, 곧 **오프셋** 하나만 컨슈머 그룹이 스스로 기록한다.

```
Kafka 파티션:  [0][1][2][3][4][5][6][7][8] ...
                             ^
                        커밋된 오프셋 = 5
                        "0~4는 처리 끝. 5부터 다시 읽으면 됨"
```

이 모델은 **연속적**이다. "5번은 실패했지만 6·7번은 처리했다"를 표현할 방법이 없다. 오프셋을 7로 올리면 5번이 처리된 것으로 간주되고, 5에 머무르면 6·7을 다시 읽게 된다.

RabbitMQ는 메시지마다 상태를 들고 있으므로 그 표현이 가능하다.

```
RabbitMQ 큐:  delivery tag 5 -> nack (DLQ로)
              delivery tag 6 -> ack  (완료)
              delivery tag 7 -> ack  (완료)
              세 건이 서로 독립적이다
```

**이 한 가지 차이에서 두 도구의 실패 처리 설계가 전부 갈라진다.** Kafka는 한 건이 막히면 뒤가 전부 막히므로(poison pill) 재시도 토픽 같은 우회로를 반드시 설계해야 하지만, RabbitMQ는 실패한 한 건만 떼어내 DLQ로 보내고 나머지는 흘려보낼 수 있다.

대신 RabbitMQ가 치르는 대가도 이 지점에 있다. **메시지마다 상태를 갱신해야 하므로** 브로커가 하는 일이 많고, 그래서 순수 처리량에서는 Kafka에 못 미친다.

### 1-3. delivery tag — 메시지를 가리키는 번호

ack을 보내려면 "어느 메시지"인지 지목해야 한다. 그 지목에 쓰는 것이 **delivery tag(전달 태그)**다.

중요한 성질이 둘 있다.

**채널 단위로 매겨지는 번호다.** 같은 큐라도 채널이 다르면 태그 공간이 다르다. 그래서 **다른 채널에서 받은 메시지를 이 채널에서 ack하면 오류**가 되고, 채널이 닫히면 그 채널의 unacked 메시지는 전부 큐로 돌아간다.

**단조 증가한다.** 그래서 `multiple=true` 옵션으로 "이 태그까지 전부 ack"이라는 일괄 확인이 가능하다. 배치 처리에서 왕복을 줄이는 수단이지만, 중간에 실패한 건이 섞여 있으면 그것까지 완료로 처리해버리므로 주의해야 한다.

## 2. ack의 세 가지 모드와 그 대가

### 2-1. auto-ack — 보내는 순간 지운다

`basic.consume(autoAck=true)`로 소비하면 브로커는 **메시지를 컨슈머에게 보내는 즉시 삭제**한다. Spring AMQP의 `AcknowledgeMode.NONE`이 여기에 해당한다.

이름이 오해를 부른다. "자동으로 ack 해준다"가 아니라 **"ack이라는 절차 자체가 없다"**에 가깝다. 브로커는 전송을 곧 완료로 간주한다.

위험은 둘이고, 두 번째가 덜 알려져 있다.

**첫째, 유실.** 컨슈머가 메시지를 받은 뒤 처리 중에 죽으면 그 메시지는 브로커에 없다. 재전달도 없다. 배포로 파드를 내리는 것만으로도 처리 중이던 건이 사라진다.

**둘째, prefetch 무력화.** auto-ack 모드에서는 unacked 메시지라는 개념이 없으므로 **prefetch 한도가 적용되지 않는다.** 브로커는 컨슈머가 받아갈 수 있는 만큼 계속 밀어넣고, 컨슈머 프로세스의 힙에 메시지가 쌓여 OOM으로 죽는다. 그리고 죽는 순간 그 안에 있던 수천 건이 전부 사라진다. 첫 번째 위험이 두 번째와 만나 피해가 증폭된다.

그래서 auto-ack이 정당한 경우는 하나뿐이다. **잃어도 되는 메시지, 그리고 컨슈머가 절대 밀리지 않는 경우** — 실시간 지표 스트림이나 로그 tail 같은 것들이다. 업무 처리에는 쓰지 않는다.

### 2-2. manual ack — 처리 후 직접 확인

컨슈머가 처리를 마친 뒤 `basic.ack`을 명시적으로 보낸다. 안전한 기본값이며, 여기서 중요한 것은 **ack을 보내는 시점**이다.

```java
// 잘못된 코드 — 받자마자 ack
@RabbitListener(queues = "payment.done", ackMode = "MANUAL")
public void handle(Message msg, Channel channel,
                   @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    channel.basicAck(tag, false); // 먼저 ack -> 브로커에서 즉시 삭제
    settlementService.settle(parse(msg)); // 여기서 예외가 나면? 메시지는 이미 없다
}

// 올바른 코드 — 처리가 끝난 뒤 ack
@RabbitListener(queues = "payment.done", ackMode = "MANUAL")
public void handle(Message msg, Channel channel,
                   @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    try {
        settlementService.settle(parse(msg)); // DB 커밋까지 완료
        channel.basicAck(tag, false);         // 그 다음에 완료 신고
    } catch (RetryableException e) {
        // 일시적 실패: 큐로 되돌려 재시도 (단, 무한 루프 주의 — 3-2 참고)
        channel.basicNack(tag, false, true);
    } catch (Exception e) {
        // 영구적 실패: 되돌리지 말고 DLX로 보낸다
        channel.basicNack(tag, false, false);
    }
}
```

처리 후 ack이 정답인 이유는 **선택지가 유실이냐 중복이냐 둘뿐이기 때문**이다. 처리 전에 ack하면 처리 실패 시 유실이고, 처리 후에 ack하면 ack 직전에 죽었을 때 중복이다. **중복은 멱등 처리로 막을 수 있지만 유실은 되돌릴 방법이 없다.** 그래서 실무는 예외 없이 "처리 후 ack + 멱등 컨슈머" 조합을 택한다. Kafka에서 "처리 후 커밋"을 택하는 것과 완전히 같은 논리다.

### 2-3. Spring AMQP의 AUTO 모드 — 이름에 속지 말 것

Spring AMQP에는 모드가 셋 있고, 이름 때문에 가장 많이 오해받는다.

| Spring 설정 | 실제 동작 | AMQP 수준 |
|---|---|---|
| `AcknowledgeMode.NONE` | ack 절차 없음. 전송 즉시 삭제 | auto-ack (위험) |
| `AcknowledgeMode.AUTO` (기본값) | **리스너 메서드가 정상 리턴하면 프레임워크가 ack, 예외를 던지면 nack** | manual ack |
| `AcknowledgeMode.MANUAL` | 개발자가 직접 `basicAck` 호출 | manual ack |

즉 **Spring의 `AUTO`는 AMQP의 auto-ack이 아니라 "프레임워크가 대신 눌러주는 manual ack"**이다. 안전한 기본값이며, 대부분의 경우 이걸 쓰면 된다.

`MANUAL`이 필요한 경우는 제한적이다. 여러 메시지를 모아 한 번에 ack하고 싶거나(`multiple=true`), 리스너 메서드 밖(비동기 콜백 등)에서 완료 시점이 결정될 때다. 필요 없는데 `MANUAL`로 두면 **ack을 빠뜨리는 실수**가 생기고, 그 메시지는 컨슈머가 살아 있는 한 영원히 Unacked에 남아 큐를 막는다.

## 3. prefetch(QoS) — 미리 받아두는 양

### 3-1. 왜 필요한가 — 없으면 어떻게 되는가

prefetch를 설정하지 않으면(제한 없음) 브로커는 **큐에 있는 메시지를 컨슈머에게 되는 대로 밀어넣는다.** 컨슈머가 처리 중이든 말든 계속 보낸다.

여기서 두 가지 문제가 동시에 생긴다.

**메모리 문제.** 큐에 10만 건이 있고 컨슈머 하나가 붙으면, 그 10만 건이 전부 컨슈머 프로세스로 흘러 들어간다.

**공정성 문제.** 워커 3대를 띄웠는데 처음 붙은 워커가 메시지를 다 가져가 버리면, 나중에 붙은 워커는 놀고 첫 워커만 몇 시간을 처리한다. **워커를 늘렸는데 처리량이 안 늘어나는** 전형적인 증상이다.

`basic.qos(prefetch_count=N)`은 이 문제를 한 문장으로 푼다. **"unacked 메시지가 N개가 되면 더 보내지 마라."**

```
prefetch = 1 인 경우
  워커1: [메시지1 처리중]     <- ack 전까지 다음 메시지 안 옴
  워커2: [메시지2 처리중]
  워커3: [메시지3 처리중]
  -> 먼저 끝낸 워커가 다음 것을 가져간다. 완벽한 부하 분산.

prefetch = 100 인 경우
  워커1: [처리중] + 대기열 99건 보유
  워커2: [처리중] + 대기열 99건 보유
  워커3: 붙었지만 남은 게 없어 놀 수도 있다
  -> 왕복이 줄어 처리량은 높지만, 분배가 불균등해질 수 있다.
```

### 3-2. 값을 어떻게 정하는가

트레이드오프가 명확하다. **작으면 공정하지만 왕복 대기가 생기고, 크면 빠르지만 편중되고 메모리를 먹는다.**

판단 기준은 **메시지 하나의 처리 시간**이다.

- **처리가 오래 걸리는 작업**(수백 ms~수 초: 외부 API 호출, 결제, 파일 처리) → **prefetch를 작게(1~5).** 처리 시간에 비해 네트워크 왕복은 무시할 수준이므로 공정한 분배가 훨씬 중요하다. 큰 값을 주면 한 워커가 오래 걸리는 작업 100건을 쥐고 있는 동안 다른 워커가 노는 최악의 상황이 나온다.
- **처리가 매우 빠른 작업**(수 ms 이하: 인메모리 변환, 로그 적재) → **prefetch를 크게(수백).** 이때는 왕복 지연이 처리 시간을 압도하므로 미리 받아두는 것이 이득이다.

두 번째로 볼 것은 **메모리**다. prefetch × 컨슈머 수 × 평균 메시지 크기가 컨슈머 프로세스가 안고 있을 수 있는 최대치다. 메시지가 1MB인데 prefetch를 500으로 주면 500MB를 쥐게 된다.

```java
// Spring Boot 설정 — 작업 성격에 맞춰 컨테이너별로 다르게 준다
@Bean("slowJobContainerFactory")
SimpleRabbitListenerContainerFactory slowJobFactory(ConnectionFactory cf) {
    var f = new SimpleRabbitListenerContainerFactory();
    f.setConnectionFactory(cf);
    f.setPrefetchCount(2);   // 건당 수 초 걸리는 작업: 공정 분배 우선
    f.setConcurrentConsumers(4);
    return f;
}
// application.yml 전역 기본값
// spring.rabbitmq.listener.simple.prefetch: 20
```

**"기본값이 얼마인가"보다 "왜 이 값인가"를 말할 수 있는 것이 중요하다.** 면접에서도 숫자를 외워 말하는 것보다 "처리 시간이 길면 작게, 짧으면 크게 잡고, 메모리 상한을 함께 계산합니다"라고 근거를 말하는 편이 낫다.

### 3-3. prefetch와 순서 — 놓치기 쉬운 부작용

prefetch를 키우면 **재시도 시 순서가 더 크게 흐트러진다.**

컨슈머가 10건을 미리 받아 순서대로 처리하다가 3번째에서 실패해 requeue하면, 그 메시지는 **큐의 맨 뒤로 가는 것이 아니라 큐 앞쪽으로 돌아간다.** 하지만 컨슈머는 이미 4~10번을 손에 쥐고 있으므로 그것들을 먼저 처리한다. 결과적으로 3번이 4~10번보다 늦게 처리된다.

**"prefetch를 키우면 처리량이 오르지만, 실패가 섞이는 순간 순서가 무너진다"**는 인과를 아는 것이 시니어 신호다. (가산점 포인트) 순서가 중요한 큐라면 prefetch를 1로 두고 컨슈머도 하나만 두어야 한다. 자세한 내용은 `15-rabbitmq-message-ordering.md`에서 다룬다.

## 4. 실무 사고 — requeue 무한 루프

### 4-1. 증상

배포 직후 CPU가 100%로 튀었는데 처리량은 0이다. 큐 깊이는 그대로이고, 컨슈머 로그에는 같은 에러가 초당 수천 줄씩 쏟아진다.

### 4-2. 원인

컨슈머가 처리에 실패해 메시지를 큐로 되돌리고(requeue), 큐가 곧바로 다시 배달하고, 또 실패하고, 또 되돌리는 순환이다. **실패 원인이 그 메시지 자체에 있으므로(파싱 불가, 필수 필드 누락) 몇 번을 재시도해도 결과가 같다.**

```
[컨슈머] 수신 -> 파싱 실패 -> nack(requeue=true)
    ^                                |
    +--------- 즉시 재배달 -----------+
   지연 없음. 초당 수천 회 반복. CPU 100%.
```

여기서 결정적인 함정은 **Spring AMQP의 기본값이 requeue=true**라는 것이다(`spring.rabbitmq.listener.simple.default-requeue-rejected`의 기본값이 true). 리스너에서 예외를 던지면 프레임워크가 자동으로 requeue하므로, **아무 설정도 하지 않은 상태에서 파싱 불가 메시지 하나가 들어오면 즉시 이 루프에 빠진다.**

### 4-3. 대응

```yaml
# 1) 되돌리지 않도록 기본값을 바꾼다 — 실패 시 DLX로 넘어간다
spring:
  rabbitmq:
    listener:
      simple:
        default-requeue-rejected: false
        retry:
          enabled: true          # 컨슈머 내부에서 제한된 횟수만 재시도
          max-attempts: 3
          initial-interval: 1s
          multiplier: 2          # 1s -> 2s -> 4s 백오프
```

```java
// 2) 예외 종류로 갈라 판단한다 — 되돌릴 가치가 있는 실패인가
try {
    handler.handle(event);
    channel.basicAck(tag, false);
} catch (TransientException e) {
    // DB 커넥션 끊김, 외부 API 타임아웃 -> 시간이 지나면 성공할 수 있다
    channel.basicNack(tag, false, true);
} catch (Exception e) {
    // 파싱 실패, 유효성 위반 -> 몇 번을 해도 같다. 즉시 격리한다
    channel.basicNack(tag, false, false); // DLX로 이동
}
```

`AmqpRejectAndDontRequeueException`을 던지면 Spring이 requeue 없이 거부하므로, 예외 타입만으로 같은 분기를 표현할 수도 있다.

**핵심 원칙은 "즉시 무한 재시도는 재시도가 아니라 장애"**라는 것이다. 재시도에는 반드시 **횟수 상한**과 **지연(백오프)**이 있어야 하고, 상한을 넘으면 **DLQ로 격리**해야 한다. 이 설계는 `14-rabbitmq-retry-dlx-dlq.md`에서 전개한다.

## 5. 꼬리질문 대비 포인트

### "ack을 보내기 전에 컨슈머가 죽으면 메시지는 어떻게 되나요?"

브로커가 **커넥션·채널이 끊긴 것을 감지하는 즉시** 그 채널의 unacked 메시지를 전부 큐로 되돌린다. Kafka처럼 세션 타임아웃을 기다릴 필요 없이, TCP 연결이 끊기면 바로 알 수 있기 때문이다.

되돌아온 메시지에는 `redelivered=true` 플래그가 붙는다. 다만 이 플래그는 "전에 한 번 배달된 적 있음"만 알려줄 뿐 **이전 시도가 어디까지 진행됐는지는 알려주지 않는다.** DB 커밋까지 끝내고 ack 직전에 죽었을 수도 있다. 그래서 **중복 처리 방지는 여전히 애플리케이션 책임**이며, 처리 이력 테이블에 이벤트 ID를 유니크 제약으로 저장하는 멱등 처리가 필요하다.

### "prefetch를 1로 두면 처리량이 많이 떨어지나요?"

떨어지는 정도는 **처리 시간과 왕복 지연의 비율**로 결정된다.

처리에 500ms 걸리는 작업이라면, 왕복 1ms는 0.2%의 손해다 — 무시해도 된다. 반대로 처리에 1ms 걸리는 작업이라면 왕복 1ms는 처리량을 절반으로 깎는다.

그래서 답은 "떨어진다/안 떨어진다"가 아니라 **"내 작업의 처리 시간이 왕복 지연보다 충분히 긴가"**다. 그리고 처리량이 부족하면 prefetch를 키우기 전에 **컨슈머 수를 늘리는 것**이 먼저다 — 그쪽이 공정성을 잃지 않으면서 확장된다.

### "Kafka의 오프셋 커밋과 비교하면 무엇이 더 나은가요?" (시니어 변별 포인트)

우열이 아니라 **다른 문제를 푸는 다른 모델**이라고 답해야 한다.

| | RabbitMQ (메시지 단위 ack) | Kafka (오프셋) |
|---|---|---|
| 추적 단위 | 메시지 하나하나 | 파티션별 위치 숫자 하나 |
| 순서 건너뛴 완료 | 가능 (5 실패, 6·7 완료) | 불가능 |
| poison pill 문제 | 없음 (한 건만 격리) | 있음 (뒤가 전부 막힘) |
| 브로커 부담 | 메시지마다 상태 갱신 | 거의 없음 |
| 재처리(replay) | 불가 (ack하면 삭제) | 가능 (오프셋 되감기) |

핵심 문장은 이렇다. **"RabbitMQ는 브로커가 상태를 안고 있어서 실패한 한 건만 떼어낼 수 있고, Kafka는 브로커가 상태를 안 갖는 대신 처리량과 재처리를 얻었다."**

여기에 실무 판단을 덧붙이면 좋다. 실패 격리가 자연스럽다는 것은 **작업 큐**에 유리하고, 재처리가 된다는 것은 **이벤트 스트림**에 유리하다.

### "`multiple=true`로 일괄 ack하면 무엇을 조심해야 하나요?"

`basicAck(tag=100, multiple=true)`는 **그 채널에서 아직 ack 안 된 태그 100 이하를 전부 완료 처리**한다. 왕복이 줄어 처리량에 유리하다.

위험은 **처리하지 않은 것까지 완료로 만들 수 있다**는 점이다. 예를 들어 95번이 실패해 나중에 처리하려고 남겨뒀는데 100번을 일괄 ack하면 95번도 함께 사라진다.

그래서 일괄 ack은 **"이 배치는 전부 성공했다"가 확정된 뒤에만** 쓴다. 부분 실패가 있으면 성공한 것만 개별 ack하고 실패한 것은 따로 nack해야 한다. Kafka에서 배치 처리 후 오프셋을 커밋할 때 "실패 건이 섞이면 어디까지 커밋할 것인가"를 고민하는 것과 똑같은 문제다.

### "Unacked 수가 계속 높은데 CPU도 안 쓰고 있습니다. 무엇을 의심하나요?"

**컨슈머가 무언가를 기다리며 멈춰 있다**는 신호다. 순서대로 의심한다.

1. **외부 호출 블로킹.** 타임아웃 없는 HTTP 호출이나 DB 락 대기. 스레드 덤프를 뜨면 즉시 보인다.
2. **ack 누락 버그.** `MANUAL` 모드인데 특정 분기에서 `basicAck`을 호출하지 않는 경로가 있는 경우. 그 메시지는 컨슈머가 살아 있는 한 영원히 Unacked에 남는다.
3. **prefetch만 크고 처리 스레드가 부족한 경우.** 100건을 받아뒀지만 처리 스레드가 1개면 나머지 99건은 그냥 대기 상태로 잡혀 있다. 이건 버그는 아니지만, 그 99건이 **다른 워커에게 갈 수 있었던 일감**이라는 점에서 손해다.

3번은 특히 "워커를 늘렸는데 왜 안 빨라지죠"의 숨은 원인이다. prefetch를 낮추면 즉시 개선된다.

---

## 한 줄 요약

ack은 유실과 중복의 경계를 정하고 prefetch는 처리량과 공정성의 균형을 정한다 — **처리 후 ack + 멱등 처리 + 작업 시간에 맞춘 prefetch**가 안전한 기본형이며, RabbitMQ가 Kafka와 근본적으로 다른 점은 **메시지 단위로 상태를 추적하므로 실패한 한 건만 떼어내 격리할 수 있다는 것**이다.
