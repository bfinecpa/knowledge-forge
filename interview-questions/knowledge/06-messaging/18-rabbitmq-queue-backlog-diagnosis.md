# RabbitMQ 큐 적체 진단과 해소 — 랙과 달리 "브로커가 먼저 무너진다"

> 핵심 관전 포인트: **Kafka의 컨슈머 랙과 RabbitMQ의 큐 적체는 증상이 근본적으로 다르다. Kafka에서 컨슈머가 밀리는 것은 "오프셋이 뒤처진 것"일 뿐 브로커는 아무 부담도 지지 않는다 — 데이터는 어차피 디스크에 있었고 리텐션 기간까지 그대로 있다. RabbitMQ에서 큐가 쌓이는 것은 브로커의 메모리와 디스크가 실제로 차오르는 것이다. 그래서 임계치를 넘으면 브로커가 자기 보호를 위해 모든 프로듀서를 블로킹한다(메모리·디스크 alarm). 컨슈머가 느린 문제가 발행 API의 응답 지연으로 번지고, 결국 사용자 요청 처리까지 멈춘다. 컨슈머 장애가 서비스 전체 장애로 번지는 경로가 존재한다는 것이 RabbitMQ 적체의 본질이며, 진단은 항상 `Ready`/`Unacked` 두 숫자의 조합과 `publish rate` vs `ack rate` 비교에서 시작한다.**

---

## 0. 질문 + 의도

**질문**: "RabbitMQ 큐에 메시지가 계속 쌓일 때(적체) 원인 진단과 해소를 단계적으로 설명해주세요. (flow control, 메모리/디스크 alarm, lazy queue — Kafka 컨슈머 랙 대응과 비교)"

**출제 의도**: Kafka의 컨슈머 랙에 대응하는 문항이지만 증상이 다르다. RabbitMQ는 큐가 쌓이면 메모리·디스크 alarm과 flow control로 프로듀서를 막아 서비스 전체가 멈추는 방향으로 무너진다. "적체가 왜 발행 지연 장애로 번지는가"라는 인과를 설명할 수 있는지, 그리고 진행 중인 장애에서 단기 완화와 근본 대책을 분리해 말하는지를 본다.

## 1. 전제 — 적체가 왜 Kafka보다 위험한가

### 1-1. 저장 모델의 차이가 만드는 결과

Kafka는 **처음부터 디스크 로그**다. 메시지는 발행 시점에 파일에 append되고, 컨슈머가 읽든 안 읽든 리텐션 기간 동안 그대로 있다. 컨슈머가 하루 밀려도 브로커에게는 아무 변화가 없다 — 어차피 디스크에 있던 것을 컨슈머가 늦게 읽을 뿐이다.

RabbitMQ는 **기본적으로 메모리 큐**다. 큐가 짧으면 메시지가 디스크를 거의 거치지 않고 메모리에서 흘러간다. 이것이 낮은 지연의 비결이지만, **컨슈머가 멈추면 그 메시지들이 전부 브로커 메모리에 눌러앉는다.**

```
Kafka:    프로듀서 --> [디스크 로그] --> 컨슈머
                       컨슈머가 밀려도 브로커 부담 없음

RabbitMQ: 프로듀서 --> [메모리 큐] --> 컨슈머
                       컨슈머가 밀리면 여기가 부푼다
                       -> 임계치 초과 -> 브로커가 프로듀서를 막는다
```

### 1-2. 브로커의 자기 보호 — alarm과 flow control

RabbitMQ는 자기가 죽지 않기 위한 방어 장치를 갖고 있고, 그 방어가 **프로듀서를 멈추는 방식**으로 작동한다.

**메모리 alarm.** 브로커가 쓰는 메모리가 임계치(기본값은 시스템 메모리의 일정 비율)를 넘으면 alarm이 켜지고, **모든 발행 커넥션이 블로킹된다.** 클라이언트는 `connection.blocked` 알림을 받고, 이후 발행 호출이 응답 없이 멈춘다.

**디스크 여유 공간 alarm.** 디스크 여유가 임계치 아래로 떨어져도 같은 일이 벌어진다. persistent 메시지를 더 쓸 수 없으니 발행을 막는 것이다.

**flow control.** 브로커 내부적으로도 크레딧 기반 제어가 있어, 소비가 느린 경로로 메시지가 밀려들면 그 앞단(발행 채널)의 속도를 늦춘다. alarm처럼 완전히 막는 것은 아니지만 발행 지연이 눈에 띄게 늘어난다.

### 1-3. 그래서 무슨 일이 벌어지는가

여기서 이 문서의 핵심 인과가 나온다.

```
① 컨슈머가 느려지거나 멈춘다 (다운스트림 장애, 배포 실수, 버그)
      |
② 큐가 쌓인다
      |
③ 브로커 메모리 사용량이 임계치를 넘는다
      |
④ 메모리 alarm -> 모든 프로듀서 블로킹
      |
⑤ 발행을 호출하던 API 스레드가 멈춘다
      |
⑥ 톰캣 스레드 풀 고갈 -> 사용자 요청 전체가 응답 없음
      |
⑦ "알림 워커 하나가 죽었는데 주문 API가 통째로 멈췄다"
```

**컨슈머 하나의 문제가 서비스 전체 장애로 번지는 경로**가 이것이다. Kafka에서는 이 경로가 없다 — 컨슈머가 밀려도 프로듀서는 아무 영향을 받지 않는다.

그래서 RabbitMQ 운영에서 **큐 깊이는 "컨슈머가 얼마나 밀렸는가" 지표가 아니라 "브로커가 얼마나 위험한가" 지표**로 봐야 한다. 이 관점 전환을 말할 수 있는 것이 이 질문의 핵심이다.

**미리 알아둘 방어 수단**: 프로듀서 쪽 커넥션 팩토리에 타임아웃을 걸고, 블로킹 상태를 감지해 **발행을 포기하고 요청을 빠르게 실패시키는** 처리를 넣어두면 ⑤~⑦로 번지는 것을 막을 수 있다. Spring AMQP에는 블로킹 시 발행을 일정 시간 뒤 실패시키는 설정(`setConnectionFactoryPublisherBlockedTimeout` 계열)이 있으므로, **무한 대기가 되지 않게 상한을 두는 것**이 기본이다.

## 2. 진단 — 두 숫자의 조합으로 원인이 갈린다

### 2-1. 봐야 할 지표

관리 콘솔이나 `rabbitmqctl list_queues`에서 얻는 값들이다.

| 지표 | 의미 |
|---|---|
| `messages_ready` | 아직 아무에게도 배달 안 된 메시지 수 |
| `messages_unacknowledged` | 배달됐지만 ack을 못 받은 수 |
| `consumers` | 붙어 있는 컨슈머 수 |
| publish rate | 초당 유입량 |
| deliver rate | 초당 배달량 |
| ack rate | 초당 처리 완료량 |

**`Ready`와 `Unacked`의 조합**이 1차 분기를 만든다.

```
Ready 높음 + Unacked = 0        -> 배달 자체가 안 되고 있다
Ready 높음 + Unacked = prefetch 상한 -> 배달은 되는데 처리가 느리다
Ready 낮음 + Unacked 높음        -> 컨슈머가 붙잡고 있다 (블로킹 의심)
deliver rate >> ack rate        -> 재배달 루프 (requeue 무한 반복)
publish rate 급증               -> 유입 폭증 (컨슈머 문제가 아님)
```

### 2-2. 진단 순서

**1단계: 컨슈머가 붙어 있는가.**

```bash
rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers
```

`consumers = 0`이면 컨슈머 문제가 아니라 **연결 문제**다. 애플리케이션이 죽었거나, 큐 이름이 바뀌었거나, 배포 중 리스너가 시작되지 않았다. 이 경우 컨슈머를 튜닝해봐야 소용이 없다.

**2단계: 배달은 되는데 느린 것인가.**

`Unacked`가 prefetch × 컨슈머 수에 딱 붙어 있다면, 컨슈머가 받을 만큼 받아놓고 처리를 못 끝내고 있다는 뜻이다. 원인은 컨슈머 안이 아니라 **거의 항상 다운스트림**이다.

- DB 슬로우 쿼리나 락 대기
- 외부 API 지연 (타임아웃 설정이 없으면 무한정 잡힌다)
- GC 정지 시간 증가

컨슈머 애플리케이션의 스레드 덤프를 한 번 뜨면 대부분 즉시 보인다. **"어디서 멈춰 있는가"를 추측하지 말고 덤프로 확인하는 것**이 가장 빠르다.

**3단계: 처리 중인데 완료가 안 되는 것인가.**

`deliver rate`는 높은데 `ack rate`가 낮으면 **재배달 루프**다. 실패한 메시지를 지연 없이 requeue하고 있다는 신호이며, CPU는 높은데 처리량이 0인 특징적 증상이 함께 나타난다. 대응은 `14-rabbitmq-retry-dlx-dlq.md`에 있다.

**4단계: 유입이 늘어난 것인가.**

`publish rate`가 평소보다 크게 높으면 컨슈머는 정상이고 **트래픽이 폭증한 것**이다. 이때 컨슈머를 튜닝하는 것은 방향이 틀렸고, 컨슈머를 늘리거나 유입을 조절해야 한다.

**5단계: 브로커가 이미 방어에 들어갔는가.**

```bash
rabbitmqctl status | grep -A5 alarms       # 켜져 있는 alarm 확인
rabbitmqctl list_connections name state    # blocked / blocking 상태 확인
```

alarm이 켜져 있다면 이미 1-3의 ④단계에 도달한 것이다. **이 경우 최우선 조치는 컨슈머 튜닝이 아니라 alarm 해제**다 — 프로듀서가 막혀 있는 동안 서비스 전체가 멈춰 있기 때문이다.

## 3. 해소 — 단기 완화와 근본 대책을 나눈다

### 3-1. 지금 당장 (분 단위)

목표는 **브로커의 압력을 낮춰 프로듀서 블로킹을 푸는 것**이다.

**컨슈머를 늘린다.** RabbitMQ는 Kafka와 달리 **파티션 수 같은 상한이 없다.** 큐 하나에 컨슈머를 몇 대든 더 붙일 수 있으므로, 워커 파드를 늘리는 것이 가장 즉효다. 이것이 Kafka 대비 RabbitMQ의 명확한 운영상 이점이다.

**prefetch를 조정한다.** 컨슈머를 늘렸는데도 안 빨라진다면 prefetch가 커서 기존 컨슈머가 메시지를 다 쥐고 있을 수 있다. 값을 낮추면 새로 붙은 컨슈머에게 일감이 분배된다.

**급하지 않은 큐의 유입을 끊는다.** 브로커 전체가 위험한 상황에서는 우선순위가 낮은 큐의 바인딩을 임시로 제거해 유입을 막는 것이 합리적이다. 알림·통계성 이벤트를 잠시 포기하고 결제 흐름을 살리는 판단이다.

**디스크 alarm이면 공간부터 확보한다.** 로그 파일 정리나 볼륨 확장이 컨슈머 튜닝보다 훨씬 빠르다.

### 3-2. 며칠 안 (구조 완화)

**큐를 나눈다.** 한 큐에 여러 종류의 작업이 섞여 있으면 느린 작업이 빠른 작업을 막는다. 무거운 작업을 별도 큐로 분리하고 워커도 따로 두면, 한쪽이 밀려도 다른 쪽은 정상 처리된다. **큐 분리는 격리 수단**이라는 관점이 중요하다.

**큐 길이 상한을 건다.** `x-max-length` 또는 `x-max-length-bytes`로 상한을 두면 **적체가 브로커 전체를 위협하는 상황 자체를 막는다.** 상한 초과 시 동작은 `x-overflow`로 정한다.

| `x-overflow` | 동작 | 적합한 경우 |
|---|---|---|
| `drop-head` | 가장 오래된 메시지를 버린다 | 최신 값만 의미 있는 지표성 데이터 |
| `reject-publish` | 새 발행을 거부한다 (프로듀서가 오류를 받음) | 유실보다 발행 실패가 나은 경우 |
| `reject-publish-dlx` | 거부하면서 DLX로 보낸다 | 거부된 것도 나중에 처리해야 하는 경우 |

**핵심은 "무한히 쌓이게 두지 않는 것"**이다. 상한이 없으면 브로커가 죽는 방향으로 가고, 상한이 있으면 그 큐만 아프고 나머지는 산다. **장애를 국소화하는 설계**다.

**긴 큐를 디스크로 내린다.** classic 큐에는 메시지를 가능한 한 디스크에 두는 lazy 모드가 있었다. 최신 버전에서는 classic 큐의 저장 방식이 개선되어 긴 큐를 자동으로 디스크로 내리는 동작이 기본에 가까워졌으므로, **쓰는 버전에서 이 설정이 여전히 의미가 있는지 확인**해야 한다. 어느 쪽이든 원리는 같다 — **메모리 압력을 낮추는 대신 처리 지연을 감수한다.**

### 3-3. 근본 대책 (설계)

**컨슈머 처리량 자체를 올린다.** 배치 처리, 커넥션 풀 조정, 불필요한 동기 호출 제거. 자세한 내용은 `16-rabbitmq-consumer-throughput-prefetch.md`에서 다룬다.

**프로듀서 쪽 배압(backpressure)을 설계한다.** 브로커가 막아서 API가 멈추는 것이 아니라, **애플리케이션이 스스로 판단해 빠르게 실패**하게 만든다. 발행에 타임아웃을 두고, 실패하면 요청을 거절하거나 대체 경로(DB에 적재 후 나중에 발행)로 흘린다.

**이벤트 발행 자체를 줄인다.** 같은 이벤트를 여러 큐에 복제하고 있다면, 정말 그 소비자들이 다 필요한지 검토한다. RabbitMQ는 큐마다 실물 메시지가 쌓이므로 **소비자 수가 곧 저장 부담**이다.

**감시 지표를 바꾼다.** 큐 깊이만 보지 말고 **"현재 적체를 소진하는 데 걸리는 시간"**을 지표로 만든다. `messages_ready ÷ ack rate` = 예상 소진 시간이며, 이 값이 SLA를 넘기면 알람을 건다. 깊이 1만 건이 정상인 큐도 있고 100건이 비상인 큐도 있으므로, **절대값보다 시간 환산이 훨씬 유용하다.** (가산점 포인트)

## 4. 실무 사례 — 알림 워커 하나가 주문 API를 멈춘 건

### 4-1. 상황

외부 푸시 서비스가 응답 지연에 빠졌다. 알림 컨슈머는 타임아웃 설정 없이 그 API를 호출하고 있었다.

```
14:10  푸시 API 지연 시작 (응답 30초 이상)
14:12  알림 큐 Unacked 가 prefetch 상한에 붙음, Ready 증가 시작
14:25  브로커 메모리 사용량 임계치 도달 -> 메모리 alarm ON
14:25  모든 프로듀서 커넥션 blocked
14:26  주문 API 응답 없음 -> 톰캣 스레드 풀 고갈
14:27  전면 장애
```

### 4-2. 무엇이 잘못됐나

기술적 원인은 하나지만 설계 결함은 셋이다.

**첫째, 컨슈머에 타임아웃이 없었다.** 외부 호출에 타임아웃이 없으면 그 스레드는 영원히 잡힌다. 이것이 모든 것의 출발점이다.

**둘째, 큐에 길이 상한이 없었다.** 알림 큐가 무한정 쌓일 수 있었고, 그래서 브로커 전체를 위협하는 수준까지 갔다.

**셋째, 프로듀서에 발행 타임아웃이 없었다.** 브로커가 블로킹했을 때 API 스레드가 무한 대기했다. 알림 발행이 실패해도 주문은 처리되어야 하는데, 그 구분이 코드에 없었다.

**중요한 것은 "알림이 안 간 것"이 아니라 "알림 때문에 주문을 못 받은 것"**이다. 중요도가 낮은 기능이 중요도가 높은 기능을 죽였다.

### 4-3. 대응

```java
// 1) 컨슈머: 외부 호출에 반드시 타임아웃
RestClient pushClient = RestClient.builder()
        .requestFactory(clientHttpRequestFactory(
                Duration.ofSeconds(2),   // 연결
                Duration.ofSeconds(3)))  // 응답 — 이게 없으면 스레드가 영원히 잡힌다
        .build();
```

```java
// 2) 큐: 길이 상한 + 초과 시 DLX로 흘려 브로커를 지킨다
@Bean Queue notifyQueue() {
    return QueueBuilder.durable("notify.push")
            .maxLength(100_000)                      // 이 이상은 쌓지 않는다
            .overflow(QueueBuilder.Overflow.rejectPublishDlx)
            .deadLetterExchange("notify.overflow.dlx")
            .build();
}
```

```java
// 3) 프로듀서: 알림 발행 실패가 주문을 막지 않게 격리
try {
    notificationPublisher.publish(event);   // 내부적으로 짧은 타임아웃
} catch (AmqpException e) {
    // 알림은 부가 기능이다. 실패해도 주문 처리는 계속한다.
    // 대신 outbox에 남겨 나중에 재발행한다.
    failedNotificationOutbox.save(event);
    log.warn("알림 발행 실패, outbox로 이월: {}", event.getId());
}
```

**핵심 교훈은 "중요도가 다른 흐름은 격리해야 한다"**는 것이다. 알림 큐와 결제 큐가 같은 브로커의 같은 메모리를 공유하는 한, 알림의 장애는 언제든 결제로 번질 수 있다. 정말 중요한 흐름이라면 **브로커(또는 클러스터)를 분리하는 것**까지 검토해야 한다. vhost 분리로는 부족하다 — vhost는 논리적 격리일 뿐 메모리 alarm은 브로커 전역이기 때문이다.

## 5. 꼬리질문 대비 포인트

### "Kafka 컨슈머 랙 대응과 무엇이 다른가요?"

**진단 흐름은 비슷하고 위험도와 해소 수단이 다르다.**

| | Kafka 랙 | RabbitMQ 적체 |
|---|---|---|
| 브로커 부담 | 거의 없음 (원래 디스크에 있던 데이터) | 메모리·디스크가 실제로 참 |
| 최악의 결말 | 리텐션 초과로 미처리 데이터 유실 | **프로듀서 블로킹 → 서비스 전면 장애** |
| 컨슈머 증설 상한 | 파티션 수 (넘으면 논다) | **없음 (몇 대든 더 붙는다)** |
| 급할 때의 조치 | 파티션 증설은 즉시 불가 → 컨슈머 내부 병렬화 | 워커 증설이 즉시 효과 |

두 문장으로 요약하면 이렇다. **Kafka는 밀려도 브로커가 안전하지만 컨슈머를 파티션 수 이상으로 늘릴 수 없어 즉각적인 확장 수단이 제한된다. RabbitMQ는 컨슈머를 무제한 늘릴 수 있어 확장은 쉽지만, 밀리는 동안 브로커 자체가 위험해져 시간 여유가 없다.**

### "메모리 alarm이 걸렸습니다. 지금 무엇부터 하나요?"

**프로듀서가 막혀 있으므로 시간이 없다는 것**을 전제로 답해야 한다.

1. **어느 큐가 메모리를 먹고 있는지 확인한다.** `rabbitmqctl list_queues name messages memory --sort memory` 로 상위 큐를 찾는다.
2. **그 큐의 컨슈머 상태를 본다.** 컨슈머가 0이면 애플리케이션을 살리는 것이 최우선이다.
3. **당장 살릴 수 없다면 유입을 끊는다.** 그 큐의 바인딩을 임시 제거하면 새 메시지가 안 들어온다. 이미 쌓인 것은 남지만 더 나빠지지는 않는다.
4. **중요도가 낮은 큐라면 비우는 것도 선택지다.** `rabbitmqctl purge_queue`는 되돌릴 수 없으므로 마지막 수단이지만, **알림 큐 하나를 버려 결제를 살리는 판단**이 필요한 순간이 실제로 있다.
5. **임시로 임계치를 올리는 것은 신중해야 한다.** 브로커가 OOM으로 죽으면 훨씬 나빠진다.

**"무엇을 버릴지 미리 정해두는 것"**이 이 답의 핵심이다. 장애 중에 "이 큐 비워도 되나요?"를 물어볼 시간은 없다. 큐마다 중요도 등급을 사전에 문서화해두는 것이 운영 성숙도다.

### "적체가 반복되는데 컨슈머를 계속 늘리는 게 맞나요?" (시니어 변별 포인트)

아니다. 컨슈머 증설은 **컨슈머가 병목일 때만** 효과가 있다.

병목이 다운스트림(DB, 외부 API)이라면 컨슈머를 늘리는 것은 **그 다운스트림에 더 많은 부하를 보내는 것**이다. DB 커넥션 풀이 20인데 컨슈머를 50대로 늘리면 30대는 커넥션을 기다리며 놀고, DB는 더 느려진다. **증상이 악화된다.**

그래서 순서는 이렇다.

1. **병목이 어디인지 먼저 확정한다.** 컨슈머 스레드 덤프를 뜬다. 대부분 스레드가 DB 대기 중이면 병목은 DB다.
2. **병목이 컨슈머 자신이면** 증설한다.
3. **병목이 다운스트림이면** 그쪽을 고친다 — 쿼리 튜닝, 인덱스, 배치화, 캐시.
4. **다운스트림을 못 고치면** 컨슈머 수를 오히려 **제한**하고, 유입 쪽을 조절한다. 처리할 수 없는 속도로 받아봐야 큐만 쌓인다.

4번을 말할 수 있으면 좋다. **"처리량을 올릴 수 없으면 유입을 줄이는 것이 다음 선택지"**라는 판단은 부하 제어를 이해한 사람의 답이다.

### "큐 깊이 알람의 임계치는 어떻게 잡나요?"

절대값으로 잡으면 큐마다 다시 정해야 하고 트래픽이 변하면 무의미해진다. **시간으로 환산하는 것**이 낫다.

```
예상 소진 시간 = messages_ready / ack rate
```

이 값이 업무상 허용 지연(예: 알림은 5분, 정산은 1시간)을 넘으면 알람을 건다. 이 방식의 이점은 셋이다. 트래픽이 늘어도 임계치를 다시 안 잡아도 되고, 컨슈머가 느려지면 같은 깊이에서도 알람이 울리며, **기획자와 "몇 분까지 허용되는가"를 협의한 결과를 그대로 지표로 옮길 수 있다.**

여기에 **증가 추세**를 함께 본다. 깊이가 일정하면 처리량과 유입량이 균형을 이룬 것이고, 계속 증가하면 소진 시간이 무한대로 발산하는 중이다. **추세가 절대값보다 먼저 알람을 울려야 한다.**

### "적체된 메시지가 이미 유효기간이 지난 경우는 어떻게 하나요?"

실무에서 자주 있는 상황이다. 30분 밀린 큐에 "결제 완료 알림"이 쌓여 있다면, 이제 와서 보내는 것이 오히려 이상할 수 있다.

이때 쓰는 것이 **메시지 TTL**이다. 큐에 `x-message-ttl`을 걸면 지정 시간이 지난 메시지가 자동으로 만료되어 사라지거나(DLX가 있으면 그쪽으로) 간다.

```java
@Bean Queue realtimeNotifyQueue() {
    return QueueBuilder.durable("notify.realtime")
            .ttl(300_000)                              // 5분 지난 알림은 의미 없다
            .deadLetterExchange("notify.expired.dlx")  // 버리지 말고 집계는 한다
            .build();
}
```

이 설계의 이점은 **적체가 자동으로 해소된다**는 것이다. 컨슈머가 회복되면 유효한 메시지부터 처리하게 되고, 만료된 것들은 이미 빠져 있다. 다만 **어떤 메시지가 만료되어도 되는지는 업무 판단**이다. 결제 원장 이벤트에 TTL을 걸면 정합성이 깨진다. **실시간성이 가치의 전부인 메시지에만** 적용해야 한다.

## 한 줄 요약

RabbitMQ의 적체는 Kafka의 랙과 달리 **브로커의 메모리를 실제로 채워 프로듀서를 블로킹하고 서비스 전면 장애로 번지므로**, `Ready`/`Unacked` 조합으로 원인을 빠르게 가르고(컨슈머 부재 / 처리 지연 / 재배달 루프 / 유입 폭증), 단기로는 워커 증설과 유입 차단으로 압력을 낮춘 뒤, 근본적으로는 **큐 길이 상한과 중요도별 큐 격리**로 "한 큐의 적체가 브로커 전체를 위협하지 않는" 구조를 만들어야 한다.
