# 메시지 큐 도입 이유 — 동기 호출 대비 얻는 것과 잃는 것

> 핵심 관전 포인트: **메시지 큐는 시스템 간 결합을 시간·장애·처리량 세 축에서 끊어준다 — 호출자는 응답을 기다리지 않고(시간), 수신자가 죽어 있어도 요청이 큐에 보관되며(장애), 트래픽 폭증을 큐가 버퍼로 흡수한다(처리량). 대신 즉시 정합성을 포기하고 최종 일관성("지금은 어긋나 있어도 언젠가는 같아진다")을 받아들여야 하며, 요청 흐름이 스택 트레이스에서 끊겨 추적이 어려워지고, 동기에서는 공짜였던 실패 처리(유실·중복·재시도·DLQ)를 직접 설계해야 하는 복잡도를 떠안는다. "비동기라 좋다"가 아니라 이 트레이드오프를 저울질해서 도입을 결정하는 것이 핵심이고, 판단 기준은 두 개다 — 이 작업을 버려도 되는가, 결과를 즉시 알아야 하는가.**

---

## 0. 질문 + 의도

**질문**: "메시지 큐를 도입하는 이유는? 동기 호출 대비 장단점은?"

**출제 의도**: "비동기로 하면 좋다"가 아니라 잃는 것(즉시 정합성, 흐름 추적 난이도, 실패 처리 복잡도)을 함께 말하는지 본다. 도입 결정의 양면을 보는 습관은 모든 아키텍처 논의의 입장권이다.

## 1. 동기 호출의 세 가지 한계 — 왜 큐를 생각하게 되는가

### 1-0. 전제 지식 — "동기 호출"이 서버 안에서 실제로 하는 일

먼저 용어부터 못박자. **동기(synchronous) 호출**은 내가 상대를 부른 뒤 **응답이 돌아올 때까지 그 자리에서 기다리는** 방식이다. 어원 그대로 "같은 시간(syn-chronos)에 함께 있어야" 성립한다 — 부르는 쪽과 받는 쪽이 동시에 살아 있어야 한다.

이 "기다린다"가 서버 안에서 무엇을 뜻하는지가 중요하다. Spring MVC로 만든 API는 요청 하나를 톰캣 스레드 하나가 잡고 처리한다. 그 스레드가 `restTemplate.postForObject(...)`를 호출하면, 스레드는 소켓에서 응답 바이트가 올 때까지 커널에 의해 재워진다. CPU를 쓰지도 않고, 다른 요청을 처리하지도 못한 채 **자리만 차지한다.**

즉 동기 호출에서 하위 시스템의 응답 시간은 단순히 "느린 것"이 아니라 **내 서버의 스레드를 그만큼 붙잡아 두는 비용**이다. 이 사실이 뒤에 나오는 세 가지 한계의 공통 뿌리다.

주문 완료 후 알림 발송·적립금 지급·통계 집계를 모두 동기로 호출하는 전형적인 코드를 보자.

```java
// Before: 전부 동기 호출 — 세 가지 문제가 숨어 있다
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    notificationClient.send(order);   // 문제 1: 알림 서버가 느리면 주문도 느려짐 (지연 전파)
    pointClient.accumulate(order);    // 문제 2: 적립금 서버가 죽으면 주문 자체가 실패 (장애 전파)
    statsClient.record(order);        // 문제 3: 주문 스파이크가 그대로 하위 시스템을 강타 (부하 전파)
}
```

이 코드가 나쁜 이유는 예외 처리가 없어서가 아니다. **주문의 성공 여부와 응답 속도가 알림·적립금·통계 세 시스템 전부의 건강 상태에 묶여 있다**는 구조 자체가 문제다. 이 묶임을 **결합(coupling)**이라 부르고, 축이 셋이다.

### 1-1. 한계 ① 시간 결합 — 지연이 합산된다

**시간 결합**은 내 응답 시간이 하위 시스템들의 응답 시간을 그대로 더한 값이 된다는 뜻이다. 순서대로 기다리므로 산수 그대로 합이다.

```
[동기 — 지연의 합산]
사용자 요청
  |
  |--[주문 저장 30ms]--[알림 200ms]--[적립금 150ms]--[통계 120ms]--> 응답
  |
  <------------------------ 사용자가 기다리는 시간 500ms ------------------------>

  주문에 정말 필요한 일은 앞의 30ms뿐인데, 나머지 470ms를 사용자가 함께 기다린다.
```

여기서 끝이 아니다. 하위 하나가 느려지면 **내 서버의 처리 용량 자체가 무너진다.** 이유는 1-0에서 본 스레드 점유다.

동시에 붙잡히는 스레드 수는 **리틀의 법칙(Little's Law)** — "시스템 안에 동시에 머무는 개수 = 도착률 × 머무는 시간" — 으로 계산할 수 있다. 초당 1,000건이 들어오고 한 건이 0.2초 머문다면 동시에 살아 있는 요청은 1,000 × 0.2 = 200개다.

| 알림 서버 상태 | 요청 하나의 체류 시간 | 동시에 붙잡히는 스레드 |
|---|---|---|
| 정상 | 0.05초 | 50개 |
| 조금 느려짐 | 0.2초 | 200개 |
| 많이 느려짐 | 2초 | 2,000개 |

톰캣의 스레드 풀 크기가 200이라면, 알림 서버가 0.2초를 넘어가는 순간부터 풀이 가득 찬다. 그러면 **알림과 아무 상관 없는 조회 API 요청까지 스레드를 못 얻어 대기열에서 굶는다.** 알림 서버 한 대의 지연이 서비스 전면 지연으로 번지는 경로가 이것이다.

### 1-2. 한계 ② 가용성 결합 — 장애가 호출 사슬을 거슬러 올라온다

**가용성 결합**은 수신자가 죽으면 호출자도 함께 실패한다는 뜻이다. 주문의 성공이 "알림 서버의 생존"에 의존할 논리적 이유가 없는데도 코드 구조상 그렇게 된다.

더 무서운 것은 이 장애가 **한 단계에서 멈추지 않는다**는 점이다. A가 B를 부르고 B가 C를 부르는 사슬에서 C가 느려지면 어떻게 되는지 시간축으로 따라가 보자.

```
[장애가 거슬러 올라오는 과정 — A → B → C 호출 사슬]

t0   C(정산 서버)의 DB에 슬로우 쿼리가 걸려 응답이 10초로 늘어난다.
        C: 응답 10초

t1   B(적립금 서버)의 스레드들이 C의 응답을 기다리며 하나씩 잠든다.
        B: [스레드1 대기중] [스레드2 대기중] ... 초당 유입만큼 계속 쌓인다

t2   B의 스레드 풀이 가득 찬다. 새 요청은 큐에서 대기하거나 거절된다.
        B: 풀 200/200 포화 → 응답 시간이 10초를 넘어 무한정 늘어남

t3   A(주문 서버)의 스레드들이 이번엔 B의 응답을 기다리며 잠든다.
        A: [스레드1 대기중] [스레드2 대기중] ...

t4   A의 스레드 풀도 가득 찬다.
        A: 풀 200/200 포화 → 주문 API 전체가 응답 불가

t5   결과: C 한 대의 슬로우 쿼리로 A의 모든 API가 죽는다.
        C와 전혀 무관한 "주문 조회" 요청도 스레드를 못 얻어 실패한다.
```

이것을 **연쇄 장애(cascading failure)**라고 부른다. 핵심은 **장애가 호출 방향(A→B→C)의 반대로, 즉 거슬러 올라오면서 전파된다**는 것이다. 그리고 전파의 매개는 에러가 아니라 **스레드**다. 아직 아무도 예외를 던지지 않았는데도 시스템이 멈춘다는 점이 특히 진단을 어렵게 만든다.

### 1-3. 한계 ③ 처리량 결합 — 스파이크가 완충 없이 흘러간다

**처리량 결합**은 내가 받는 트래픽 모양이 그대로 하위 시스템의 트래픽 모양이 된다는 뜻이다. 동기 호출은 요청 하나가 들어오는 즉시 하위 호출 하나를 만들어 내므로, 중간에 완충 장치가 없다.

```
[동기 — 스파이크가 그대로 통과한다]

주문 유입          ▁▁▁▁▁█████████▁▁▁▁▁     피크 1,000건/s
                              |
                   (완충 장치가 없다. 들어온 만큼 즉시 호출한다)
                              v
통계 서버 부하      ▁▁▁▁▁█████████▁▁▁▁▁     피크 1,000건/s 그대로 도달
                              |
                   통계 서버의 처리 한계는 300건/s
                              v
                   초과분 700건/s는 타임아웃·에러가 되고
                   그 실패가 1-2의 경로로 주문까지 올라온다
```

여기서 나오는 결론이 중요하다. **가장 약한 시스템의 처리 한계가 전체의 상한이 된다.** 주문 서버가 초당 1만 건을 감당할 수 있어도, 동기로 물려 있는 통계 서버가 300건/s가 한계면 전체 시스템은 300건/s 근처에서 무너진다.

그렇다고 통계 서버를 피크에 맞춰 증설하는 것도 낭비다. 하루 중 대부분은 100건/s만 들어오는데 순간 피크 1,000건/s를 위해 상시 서버를 3배로 띄워야 하기 때문이다.

## 2. 메시지 큐가 끊어주는 것 — 도입 이유 4가지

### 2-0. 전제 지식 — 메시지 큐가 무엇인가

**메시지 큐(message queue)**는 보내는 쪽과 받는 쪽 사이에 끼어 **메시지를 대신 보관해 주는 중간 저장소**다. 등장인물이 셋이다.

- **프로듀서(producer, 생산자)**: 메시지를 만들어 큐에 넣는 쪽. 위 예에서는 주문 서비스다.
- **브로커(broker, 중개자)**: 메시지를 받아 저장하고 있다가 요청이 오면 내주는 서버. Kafka, RabbitMQ 같은 것이 여기 해당한다.
- **컨슈머(consumer, 소비자)**: 큐에서 메시지를 꺼내 처리하는 쪽. 알림·적립금·통계 서비스다.

구조상 딱 한 가지가 바뀌었을 뿐인데 1절의 세 한계가 전부 풀린다. **프로듀서가 컨슈머를 직접 부르지 않고, 브로커에 메시지를 놓고 돌아선다는 것.** 브로커에 넣는 순간 프로듀서의 일은 끝난다.

```
[Before — 동기]                      [After — 큐]

주문 ──호출──> 알림                  주문 ──넣기──> [브로커] ──꺼내기──> 알림
     ──호출──> 적립금                                       ──꺼내기──> 적립금
     ──호출──> 통계                                         ──꺼내기──> 통계
     ^                                    ^
     |                                    |
 주문이 셋의 응답을                   주문은 브로커에만 의존한다.
 전부 기다린다.                       셋이 언제 처리하는지 모르고, 알 필요도 없다.
```

코드로는 이렇게 바뀐다.

```java
// After: 이벤트 발행 — 주문은 주문만 책임진다
@Transactional
public void placeOrder(Order order) {
    orderRepository.save(order);
    // publish는 브로커에 메시지를 넣기만 한다. 알림·적립금·통계가
    // 그 메시지를 언제 처리하는지 이 코드는 알지 못하고, 알 필요도 없다.
    eventPublisher.publish(new OrderPlacedEvent(order.getId()));
    // 주문 응답 시간 = 주문 저장 + 발행 시간뿐
}
```

여기서 얻는 것이 넷이다.

### 2-1. 얻는 것 ① 비동기화 — 응답 시간이 핵심 작업만큼으로 줄어든다

핵심 작업(주문 저장)만 끝내고 즉시 응답하므로, 부가 작업의 지연이 사용자 응답 시간에서 빠진다. 1-1의 타임라인과 나란히 놓으면 차이가 분명하다.

```
[동기]  |--[주문 30ms]--[알림 200ms]--[적립금 150ms]--[통계 120ms]--> 응답  (500ms)

[큐]    |--[주문 30ms]--[발행 5ms]--> 응답  (35ms)
                            |
                            +--> (이후 알림·적립금·통계가 각자 자기 속도로 처리)
```

응답 시간이 500ms에서 35ms로 줄었다. 그리고 1-1에서 본 스레드 산수도 같이 좋아진다 — 체류 시간이 0.5초에서 0.035초로 줄었으므로, 같은 초당 1,000건 유입에서 동시 점유 스레드가 500개에서 35개로 떨어진다. **응답 시간 단축은 곧 처리 용량 증대**라는 것이 리틀의 법칙이 말해 주는 바다.

### 2-2. 얻는 것 ② 장애 격리 — 요청이 사라지지 않고 기다린다

알림 서버가 10분 죽어 있어도 메시지는 브로커에 쌓여 있다가 복구 후 처리된다. **요청이 "사라지지 않고 기다리는" 것이 큐의 본질이다.**

비유하면 **전화와 문자의 차이**다. 전화(동기)는 상대가 지금 받아야 성립하고, 안 받으면 그 통화는 실패로 끝난다. 문자(비동기)는 상대의 휴대폰이 꺼져 있어도 보내지고, 켜지는 순간 도착한다. 보내는 사람은 상대가 언제 확인하는지 신경 쓰지 않는다.

그리고 이것이 1-2의 연쇄 장애를 원천에서 끊는다. 주문 서버의 스레드는 브로커에 넣는 5ms만 쓰고 즉시 반환되므로, 알림 서버가 아무리 느려도 **주문 서버의 스레드는 단 한 개도 그 때문에 묶이지 않는다.** 전파의 매개였던 스레드 점유가 사라진 것이다.

### 2-3. 얻는 것 ③ 피크 흡수 — 큐가 완충 탱크가 된다

이 항목은 수치로 봐야 감이 온다. 1-3의 상황을 그대로 가져오자. 주문 이벤트가 피크에 초당 1,000건 발생하고, 통계 컨슈머의 처리 능력은 초당 300건이며, 피크는 10분간 지속된다.

```
[큐에 쌓이는 속도]
  유입 1,000건/s  -  처리 300건/s  =  순증 700건/s

[10분(600초) 피크 동안 누적되는 양]
  700건/s × 600초 = 420,000건

[피크 후 소진 — 평상시 유입이 100건/s로 돌아왔다고 하면]
  소진 속도 = 처리 300건/s - 유입 100건/s = 200건/s
  420,000건 ÷ 200건/s = 2,100초 = 35분

[결과]
  피크 10분 동안 큐 길이가 42만까지 부풀었다가,
  이후 35분에 걸쳐 천천히 0으로 돌아온다.
  통계 서버는 그동안 내내 자기 속도 300건/s만 처리했다 — 한 번도 과부하가 아니었다.
```

이 계산에서 봐야 할 것은 **큐 길이라는 숫자로 시간차가 저장된다**는 점이다. 스파이크가 사라진 게 아니라 **모양이 바뀌었다** — 세로로 높던 봉우리가 가로로 긴 평지가 됐다. 이것을 **부하 평탄화(load leveling)**라고 부른다.

그런데 왜 동기 호출로는 이게 불가능한가. 답은 한 줄이다. **요청은 기다려 주지 않기 때문이다.** 동기 호출에서 초과분 700건/s를 "일단 붙잡아 두려면" 그 700건에 해당하는 스레드와 커넥션을 계속 살려 둬야 하고, 그 700건을 보낸 사용자들은 브라우저 앞에서 응답을 기다리고 있어야 한다. 30초쯤 지나면 타임아웃이 나거나 사용자가 새로고침을 누른다. 즉 **동기 호출에서 "기다림"의 비용은 살아 있는 자원(스레드·커넥션·사용자의 인내심)으로 지불**되는데, 이 자원들은 42만 건 규모로는 존재하지 않는다.

큐는 그 기다림을 **디스크에 적힌 데이터**로 바꾼다. 42만 건의 메시지는 그냥 디스크에 누워 있는 바이트일 뿐이고, 아무 스레드도 소모하지 않으며, 아무도 초조해하지 않는다. 자원의 성격을 바꾼 것이 큐의 진짜 기여다.

여기에 부수 효과가 하나 더 있다. 통계 서버를 피크 1,000건/s에 맞춰 증설할 필요가 없어진다. 평균 부하에 맞춰 300건/s짜리로 두고, 피크는 큐 길이로 받아 낸다. **용량 산정 기준이 "피크"에서 "평균 + 허용 지연"으로 바뀌는 것**이 비용 면의 실익이다.

### 2-4. 얻는 것 ④ 결합도 감소 — 발행-구독으로 확장이 열린다

주문 서비스는 "누가 이 이벤트를 쓰는지" 모른다. 알 필요도 없다. 이 구조를 **발행-구독(publish-subscribe, pub/sub)**이라 부른다 — 발행하는 쪽은 주제(토픽)에 대고 던지고, 관심 있는 쪽이 각자 구독해 가져간다.

여기서 오는 실익은 **변경의 범위**다. 나중에 추천 시스템이 "주문이 일어나면 취향 프로필을 갱신하고 싶다"고 요청해 왔다고 하자.

- 동기 구조라면: 주문 서비스 코드에 `recommendClient.update(order)` 한 줄을 추가하고, 테스트하고, 배포한다. 주문이라는 **가장 위험한 코드**를 부가 기능 때문에 건드리는 것이다.
- 큐 구조라면: 추천 팀이 컨슈머를 하나 띄우고 `order-events`를 구독하면 끝난다. **주문 코드는 한 줄도 바뀌지 않는다.**

이 차이는 조직 규모가 커질수록 커진다. 주문 서비스가 하위 시스템 10개를 직접 호출하는 코드는 새 시스템이 붙을 때마다 수정되고, 그 수정 하나하나가 결제 흐름의 회귀 위험이 된다.

## 3. 잃는 것 — 이걸 말해야 합격 답변이 된다

2절까지만 말하면 "비동기 좋다"에서 멈춘 답변이다. 면접이 실제로 보려는 것은 여기부터다.

### 3-1. 잃는 것 ① 즉시 정합성이 최종 일관성으로 내려간다

용어부터 정확히 세우자. 이 두 단어의 차이가 이 절 전체의 뼈대다.

**즉시(강한) 정합성(strong consistency)**은 **쓰기가 성공한 순간부터 누가 어디서 읽어도 그 새 값이 보인다**는 보장이다. 단일 DB 트랜잭션이 커밋되면 그 다음 조회는 반드시 새 값을 본다 — 우리가 평소 당연하게 여기는 그 상태다.

**최종 일관성(eventual consistency)**은 보장의 수준을 한 단계 낮춘 것이다. **지금 이 순간에는 시스템들의 상태가 서로 어긋나 있을 수 있지만, 새 변경이 더 들어오지 않는다면 시간이 지나 결국은 같아진다**는 보장이다. 이름 그대로 "eventually(결국에는)" 맞아진다는 뜻이지 "always(언제나)" 맞다는 뜻이 아니다.

```
[즉시 정합성 — 동기 호출]
t0  주문 저장 커밋 + 적립금 반영 커밋   (같은 호출 안에서 끝났다)
t1  사용자가 적립금 조회  ->  반영된 값이 보인다.  어긋나는 구간이 없다.

[최종 일관성 — 큐]
t0  주문 저장 커밋 + 이벤트 발행       (여기까지가 사용자 응답)
t1  사용자가 적립금 조회  ->  ★ 아직 반영 전. 어긋나 있다.
t2  컨슈머가 이벤트를 꺼내 적립금 반영
t3  사용자가 다시 조회  ->  이제 보인다.  결국 같아졌다.

     t1 ~ t2 사이의 이 구간이 "일관성 창(inconsistency window)"이고,
     이 구간의 존재를 받아들이는 것이 최종 일관성이다.
```

**중요한 것은 이 어긋남이 사용자 눈에 구체적인 증상으로 나타난다**는 점이다. 추상적인 이론 문제가 아니다.

- "주문했는데 주문 목록에 아직 안 보여요"
- "결제는 됐다는데 이용권이 없어요"
- "적립금이 안 들어왔어요" (10초 뒤에 다시 보면 들어와 있다)

그래서 이것은 결국 **제품 문제**가 된다. 몇 초까지 어긋나 있어도 되는지를 기획과 협상해야 하고, 그 시간 동안 화면에 무엇을 보여줄지("처리 중입니다") 정해야 하며, CS가 이 문의를 어떻게 응대할지 사전에 합의해야 한다. 엔지니어링 선택이 CS 티켓 수로 청구되는 구조다.

같은 디렉토리의 `07-eventual-consistency-ux.md`가 이 사용자 경험 설계를 따로 다룬다.

### 3-2. 잃는 것 ② 흐름 추적 난이도

동기 호출은 스택 트레이스 하나로 전 과정이 보인다. `placeOrder`가 `notificationClient.send`를 불렀고 거기서 예외가 났다는 사실이 한 화면에 다 나온다. **호출 관계가 스택이라는 자료구조에 그대로 기록되어 있기 때문**이다.

큐를 거치면 이 연결이 물리적으로 끊긴다. 프로듀서의 스택은 `publish`에서 끝나고, 컨슈머의 스택은 `poll`에서 시작한다. 둘 사이에는 아무 코드 연결이 없다. "주문은 됐는데 알림이 안 갔다"를 추적하려면 **두 개의 서로 다른 서버, 서로 다른 시각의 로그를 사람이 손으로 이어 붙여야** 한다.

대응은 **상관관계 ID(correlation ID)**다. 요청이 시작될 때 고유 ID를 하나 만들어 이벤트 메시지 헤더에 실어 보내고, 컨슈머는 그 ID를 자기 로그에 찍는다. 그러면 ID 하나로 검색해 전 구간의 로그를 모을 수 있다.

```java
// 발행 시: 이 요청을 식별하는 ID를 메시지 헤더에 실어 보낸다.
// 페이로드가 아니라 헤더에 두는 이유는, 이 값이 비즈니스 데이터가 아니라
// 관측용 메타데이터이고 컨슈머가 역직렬화하기 전에 읽어야 하기 때문이다.
Message<OrderPlacedEvent> message = MessageBuilder
        .withPayload(new OrderPlacedEvent(order.getId()))
        .setHeader("X-Correlation-Id", MDC.get("correlationId"))
        .setHeader(KafkaHeaders.TOPIC, "order-events")
        .build();
kafkaTemplate.send(message);

// 소비 시: 헤더에서 꺼내 MDC(로깅 문맥)에 넣는다.
// 이렇게 해두면 이 컨슈머 스레드가 찍는 모든 로그 줄에 자동으로 ID가 붙어,
// 프로듀서 쪽 로그와 같은 ID로 검색해 이어 붙일 수 있다.
@KafkaListener(topics = "order-events")
public void handle(OrderPlacedEvent event,
                   @Header("X-Correlation-Id") String correlationId) {
    MDC.put("correlationId", correlationId);
    try {
        pointService.accumulate(event.orderId());
    } finally {
        MDC.clear();   // 스레드가 풀로 반납되므로 반드시 지운다. 안 지우면 다음 메시지 로그에 남는다.
    }
}
```

여기에 더해 분산 추적 시스템(Zipkin, Jaeger 같은 것)을 붙이면 구간별 소요 시간까지 시각화된다. 요점은 이것이 **공짜가 아니라는 것** — 동기 구조에서는 언어와 런타임이 공짜로 주던 추적성을, 비동기에서는 인프라를 지어서 사야 한다.

### 3-3. 잃는 것 ③ 실패 처리 복잡도

동기 호출은 실패하면 즉시 예외가 올라오고 호출자가 그 자리에서 대응한다. 재시도할지, 사용자에게 에러를 보여줄지, 트랜잭션을 롤백할지를 **결정할 주체가 명확히 그 자리에 있다.**

비동기에서는 그 주체가 사라진다. 프로듀서는 이미 응답하고 떠났고, 컨슈머가 실패했을 때 "누구에게 알릴 것인가"가 자명하지 않다. 그래서 아래 세 가지를 직접 설계해야 한다.

**(1) 유실.** 메시지가 사라질 수 있는 지점이 여럿이다. 발행 자체가 실패할 수 있고(브로커 장애, 네트워크), 브로커가 받았지만 디스크에 안전하게 쓰기 전에 죽을 수 있고, 컨슈머가 메시지를 받은 뒤 처리 전에 "다 읽었다"고 표시(오프셋 커밋)해 버리면 그 메시지는 영원히 다시 오지 않는다. 각각의 방어가 다른 문서로 이어진다 — 발행 쪽은 `27-producer-acks-durability.md`, 소비 쪽은 `23-offset-commit-and-auto-commit-risk.md`다.

**(2) 중복.** 유실을 막으려고 재시도를 켜면 이번엔 중복이 생긴다. 컨슈머가 처리를 끝내고 오프셋 커밋 직전에 죽으면, 재시작 후 같은 메시지를 다시 받는다. 그래서 컨슈머는 **멱등(idempotent)**해야 한다 — 같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질이다. `04-idempotent-consumer-implementation.md`가 구현을 다룬다.

**(3) 재시도와 DLQ.** 특정 메시지가 계속 실패하면(형식이 깨졌다거나, 참조하는 데이터가 없다거나) 그 메시지가 뒤 메시지들을 막아 세운다. 이런 메시지를 **poison pill(독이 든 알약)**이라 부른다 — 삼키면 컨슈머가 계속 쓰러진다는 뜻이다. 몇 번 재시도한 뒤 **DLQ(Dead Letter Queue, 처리 실패 메시지를 따로 모아 두는 별도 큐)**로 옮겨 흐름을 막지 않게 해야 한다. `25-consumer-retry-dlq-design.md`가 이 설계를 다룬다.

한 문장으로 압축하면 이렇다. **동기에서는 공짜였던 "실패의 즉시 인지와 전파"를 직접 구현해야 한다.**

### 3-4. 잃는 것 ④ 운영 인프라 부담

브로커는 새로운 인프라다. 그리고 새 인프라에는 새 운영 업무가 따라온다.

- **랙(lag) 감시**: 랙은 "브로커에 쌓인 최신 오프셋 - 컨슈머가 처리한 오프셋", 즉 **밀린 메시지 수**다. 이 숫자가 계속 늘고 있다면 컨슈머가 유입을 못 따라가고 있다는 뜻이고, 방치하면 3-1의 일관성 창이 몇 초가 아니라 몇 시간이 된다.
- **용량 관리**: 디스크가 차면 브로커가 쓰기를 거부한다. 보존 기간과 디스크 여유를 함께 봐야 한다.
- **장애 대응**: 브로커 자체가 죽었을 때의 복구 절차, 복제 설정, 리더 재선출 상황을 이해하고 있어야 한다.

그래서 트래픽이 작고 호출 관계가 단순하면 **동기 호출 + 타임아웃이 더 싼 선택일 수 있다.** 큐가 주는 이익보다 브로커 운영 비용이 클 수 있다는 이 판단이, 도입 여부를 묻는 질문의 진짜 답에 가깝다.

### 3-5. 요약 비교

| 축 | 동기 호출 | 메시지 큐 |
|---|---|---|
| 정합성 | 즉시 (강한 일관성 쪽) | 최종 일관성 |
| 응답 시간 | 하위 지연이 합산됨 | 핵심 작업만큼만 |
| 장애 영향 | 수신자 장애 = 내 장애 | 큐가 격리 (쌓였다 처리) |
| 실패 인지 | 즉시 예외 | 지연 감지 — 직접 설계 필요 |
| 추적 | 스택 트레이스로 한눈에 | 상관관계 ID·분산 추적 필요 |

표는 요약일 뿐이고, 면접에서 말해야 하는 것은 표 밖의 문장이다. **큐는 "결합을 끊는 대가로 즉시성과 단순함을 판다"**는 거래이고, 그 거래가 유리한지는 요구사항이 결정한다.

## 4. 꼬리질문 대비 포인트

### "그럼 모든 호출을 비동기로 바꾸면 되지 않나요?"

아니다. **응답 결과가 다음 진행의 전제인 호출은 동기여야 한다.**

결제 승인이 대표적이다. 승인 성공/실패를 알아야 주문을 확정할지 말지가 갈리는데, 이것을 비동기로 빼면 사용자에게 "아마 될 거예요"라고 답하는 셈이 된다. 재고 확인도 마찬가지다 — 재고가 없는데 주문을 받아 놓고 나중에 취소 안내를 보내는 것은 대부분의 비즈니스에서 받아들여지지 않는다.

판단 기준은 한 문장이다. **"이 작업의 결과 없이 사용자에게 응답해도 되는가?"** 알림·적립·집계처럼 핵심 트랜잭션 밖의 부가 작업이 비동기화의 대상이고, 결과가 응답 내용을 바꾸는 작업은 동기로 남는다.

### "타임아웃 + 서킷 브레이커로도 장애 전파는 막을 수 있지 않나요?" (시니어 변별 포인트)

막는 건 맞다. 하지만 **막는 방식의 의미가 다르다.** 이 차이를 축으로 세울 수 있느냐가 변별 포인트다.

먼저 용어를 정확히. **서킷 브레이커(circuit breaker, 회로 차단기)**는 하위 호출의 실패율을 세고 있다가 임계를 넘으면 **회로를 열어 이후 호출을 아예 시도하지 않고 즉시 실패시키는** 장치다. 전기 회로의 두꺼비집에서 온 이름이다 — 과전류가 흐르면 차단해 집 전체가 타는 것을 막는다.

이제 두 해법을 나란히 놓으면 축이 보인다.

```
[서킷 브레이커 — "빠르게 실패시키기(fail fast)"]
알림 서버 죽음 -> 회로 열림 -> 알림 호출을 즉시 포기하고 주문만 성공 응답
  결과: 주문 서버는 살았다. 그런데 ★ 그 알림 요청은 이 세상에서 사라졌다.
        나중에 알림 서버가 살아나도 그 알림은 영영 안 간다.

[큐 — "나중에 처리하기(defer)"]
알림 서버 죽음 -> 메시지는 브로커에 그대로 쌓임 -> 주문은 성공 응답
  결과: 주문 서버도 살았고, ★ 알림 요청도 보존됐다.
        알림 서버가 살아나는 순간 밀린 것부터 순서대로 처리된다.
```

둘 다 **장애 전파는 막는다.** 갈리는 지점은 **"요청 자체를 어떻게 하느냐"**다. 서킷 브레이커는 버리고, 큐는 보관한다.

따라서 선택 기준은 이것이다. **그 작업을 버려도 되면 동기 + 서킷 브레이커로 충분하고, 버리면 안 되면 큐가 필요하다.**

- 버려도 되는 것: 추천 목록 조회 실패 시 기본 목록 보여주기, 실시간 배지 카운트, 조회수 집계 일부
- 버리면 안 되는 것: 적립금 지급, 정산 데이터 기록, 결제 완료 알림, 이용권 발급

그리고 둘은 배타적이지 않다. 실무에서는 **프로듀서가 브로커에 발행하는 그 호출 자체에도 타임아웃과 서킷 브레이커를 건다.** 브로커가 죽었을 때 발행에서 스레드가 묶이면 결국 1-2의 연쇄 장애가 재현되기 때문이다. "요구사항이 결정하는 것이지 어느 쪽이 우월한 게 아니다"까지 답하면 균형 잡힌 인상을 준다.

### "DB 커밋은 됐는데 이벤트 발행이 실패하면요?"

**DB와 브로커는 서로 다른 시스템이라 하나의 트랜잭션으로 묶이지 않는다.** 이것을 **이중 쓰기(dual write) 문제**라고 부른다 — 한 논리적 작업을 위해 두 시스템에 각각 써야 하는데, 그 둘을 원자적으로 묶을 방법이 없는 상황이다.

어긋나는 방향이 둘이고 증상이 다르다.

```
[방향 A] DB 커밋 성공 -> 발행 실패
  주문은 저장됐는데 적립금 이벤트가 없다.
  -> 사용자는 주문했는데 적립금이 영영 안 들어온다. 아무도 모른다.

[방향 B] 발행 성공 -> DB 커밋 롤백
  적립금은 지급됐는데 주문은 없다.
  -> 존재하지 않는 주문에 대한 적립금이 나갔다.
```

발행을 트랜잭션 안에 넣든 밖에 넣든 이 둘 중 하나의 위험은 남는다. 코드를 옮겨서 해결되는 문제가 아니라는 점이 핵심이다.

표준 해법은 **트랜잭셔널 아웃박스(Transactional Outbox)**다. 이벤트를 브로커로 바로 쏘는 대신 **같은 DB의 `outbox` 테이블에 INSERT**한다. 그러면 주문 INSERT와 이벤트 INSERT가 **같은 트랜잭션 안의 두 쓰기**가 되어 함께 커밋되거나 함께 롤백된다. 이중 쓰기가 단일 쓰기로 바뀐 것이다. 실제 발행은 별도 프로세스가 그 테이블을 폴링하거나 DB 복제 로그(PostgreSQL이라면 WAL)를 CDC로 구독해 처리한다.

같은 디렉토리의 `28-transactional-outbox-cdc-kafka.md`가 이 패턴을 깊게 다룬다. 여기서는 "이중 쓰기 문제이고, 아웃박스로 단일 쓰기로 바꿔 푼다"까지 말하면 충분하다 (가산점 포인트).

### "메시지가 중복 처리되면 어떻게 하나요?"

대부분의 브로커 사용은 **at-least-once(최소 한 번) 전달**이다. "적어도 한 번은 도착한다"는 보장이지 "정확히 한 번"이 아니다. 유실을 막으려면 확신이 없을 때 다시 보내야 하고, 다시 보내면 중복이 생긴다 — **유실과 중복은 맞바꾸는 관계**다.

그래서 **중복은 예외가 아니라 정상 동작**이라는 전제에서 출발한다. 컨슈머를 멱등하게 만든다 — 이벤트에 고유 ID를 부여하고 처리 이력 테이블에 유니크 제약으로 기록해, 이미 처리한 ID면 건너뛴다.

```sql
-- 처리 이력 테이블. event_id에 PK를 걸어 두 번째 INSERT가 DB 수준에서 막히게 한다.
-- 애플리케이션에서 "이미 있나?" 조회 후 INSERT 하는 방식은
-- 두 스레드가 조회를 나란히 통과할 수 있어 안전하지 않다.
CREATE TABLE processed_event (
    event_id     uuid        PRIMARY KEY,
    processed_at timestamptz NOT NULL DEFAULT now()
);
```

```java
@KafkaListener(topics = "order-events")
@Transactional
public void handle(OrderPlacedEvent event) {
    // INSERT를 먼저 시도한다(INSERT-first). 조회 후 INSERT가 아니라 INSERT로 선점하는 이유는
    // 확인과 선점이 DB 안에서 한 번에 원자적으로 일어나야 하기 때문이다.
    int inserted = processedEventRepository.insertIfAbsent(event.eventId());
    // ON CONFLICT (event_id) DO NOTHING 이므로 이미 있으면 0이 돌아온다.
    if (inserted == 0) return;   // 이미 처리한 이벤트다. 조용히 종료 — 예외를 던지면 무한 재시도가 된다.

    pointService.accumulate(event.orderId());
}
```

"exactly-once는 공짜가 아니고, 실무는 at-least-once + 멱등 컨슈머로 푼다"까지 말하면 가산점 포인트다. Kafka에도 트랜잭션 기능이 있지만 그것은 Kafka 안에서 읽고 쓰는 경로에 한정되고, 외부 DB나 외부 API 호출까지 포함한 진짜 exactly-once는 아니다. `03-delivery-semantics-and-exactly-once-reality.md`가 이 경계를 다룬다.

### "도입하지 말아야 할 때는 언제인가요?"

세 가지다. 각각 이유가 다르다.

**(1) 결과를 즉시 알아야 하는 호출.** 조회, 결제 승인, 재고 확인처럼 응답 내용이 그 결과에 달려 있는 호출이다. 비동기로 빼면 사용자에게 확정을 줄 수 없다.

**(2) 트래픽이 작고 호출 관계가 1:1로 단순한 경우.** 큐가 주는 이익(피크 흡수, 다대다 확장)이 애초에 필요 없는 상황인데 브로커 운영 비용만 든다. 초당 몇 건짜리 내부 시스템 두 대 사이라면 동기 호출 + 타임아웃 + 재시도가 훨씬 싸고 단순하다.

**(3) 팀에 비동기 실패 처리를 설계·운영할 여력이 없는 경우.** 이것이 가장 실질적인 기준이다. 멱등 컨슈머, DLQ, 랙 모니터링을 갖추지 않고 큐만 도입하면 **유실이 나도 아무도 모르는 시스템**이 된다. 동기 호출은 실패하면 최소한 에러 로그와 500 응답이 남지만, 비동기는 조용히 사라진다. 관측 체계 없는 비동기화는 장애를 없애는 게 아니라 **보이지 않게 만드는 것**이다.

## 한 줄 요약

메시지 큐는 시간·장애·처리량의 결합을 끊어 **응답 속도, 장애 격리, 피크 흡수, 확장성**을 얻는 대신, **즉시 정합성·흐름 추적·단순한 실패 처리**를 내주는 거래다 — "작업을 버리면 안 되는가, 결과를 즉시 알아야 하는가"라는 요구사항이 도입 여부를 결정한다.
