# 파티션 증설의 부작용 — "늘리면 되지"가 정합성 사고가 되는 이유

> 핵심 관전 포인트: **파티션을 늘리면 기본 파티셔너의 `해시(키) % 파티션 수`에서 분모가 바뀌어 같은 키의 메시지가 증설 전과 다른 파티션으로 가기 시작한다. 옛 파티션에 남아 있는 그 키의 미소비 메시지와 새 파티션에 쌓이는 메시지 사이에는 순서 관계가 정의되지 않으므로, 증설 시점을 걸치는 구간에서 키 기반 순서가 깨진다. 여기서 핵심은 **그 구간이 언제 닫히는가**인데, 답은 리텐션이 아니라 **옛 파티션의 잔여분이 전부 소비될 때(그 파티션의 랙이 0이 될 때)**다 — 그래서 "드레인 후 증설"이 안전한 것이다. 순서 말고도 컨슈머 리밸런싱으로 인한 일시 중단과 중복 처리, 프로듀서마다 메타데이터 캐시 갱신 시점이 달라 같은 키가 두 파티션에 동시에 쌓이는 혼재 구간, compacted 토픽에서 옛 값이 다른 파티션에 남아 컴팩션이 지워주지 못하는 문제, 스트림 조인의 co-partitioning 파괴라는 파급이 따라온다. 순서가 중요한 토픽이라면 랙을 0으로 드레인한 뒤 증설하거나 새 토픽을 만들어 마이그레이션하는 것이 안전하고, 근본적으로는 설계 시점 산정으로 증설 자체를 회피한다.**

---

## 0. 질문 + 의도

**질문**: "파티션 수를 늘리면 어떤 부작용이 있나요? 키 기반 순서는 어떻게 되나요?"

**출제 의도**: "늘리면 되지"라는 쉬워 보이는 운영 작업이 키 재배치로 순서 보장을 깨는 것을 아는지 확인한다. 운영 작업의 숨은 파급을 미리 검토하는 습관이 없으면 단순 확장 작업이 정합성 사고가 된다.

## 1. 순서가 깨지는 구간 — 언제 시작해서, 언제 닫히는가

### 1-1. 메커니즘은 한 줄이다 — 분모가 바뀐다

기본 파티셔너는 키를 직렬화한 바이트에 murmur2 해시를 적용하고, 그 값을 양수로 만든 뒤 파티션 수로 나눈 나머지를 목적지로 쓴다.

```text
목적지 파티션 = (murmur2(직렬화된 키) & 0x7fffffff) % 파티션 수
```

파티션 수를 늘리면 **이 나눗셈의 분모가 바뀌므로** 같은 키의 목적지 파티션이 달라진다.

```text
파티션 3개 -> 4개 증설, 키 "user-42"의 해시가 6이라 하면

증설 전: 6 % 3 = 0  -> P0으로 감
증설 후: 6 % 4 = 2  -> P2로 감
```

실제 해시값으로 계산해 보면 이동은 예외가 아니라 다수다 — `29-partition-count-sizing.md`의 1-4에서 `user-1001`~`user-1008` 여덟 개 키의 실제 murmur2 값을 넣어 3개에서 4개로 늘렸을 때 **다섯 개의 목적지가 바뀌는 것**을 표로 확인했다. 왜 순서가 깨지는지의 산술적 근거는 그쪽에 있으니, 이 문서는 **그 사실을 전제로 "그래서 무슨 일이 나고, 어떻게 안전하게 늘릴 것인가"**에 집중한다.

여기서 반드시 짚어야 할 것은 하나다. **증설은 기존 데이터를 재배치하지 않는다.** 이미 P0에 쓰인 메시지를 P2로 옮겨주는 동작은 없다. 옛 메시지는 옛 파티션에 그대로 있고, 새 메시지만 새 목적지로 간다. 문제는 전부 여기서 나온다.

### 1-2. 진짜 질문은 "언제까지 위험한가"다

"파티션 증설이 순서를 깬다"는 말만으로는 운영 판단을 못 한다. 필요한 것은 **위험 구간의 시작과 끝**이다. 시작은 자명하다 — 증설하는 순간이다. 끝이 이 문서의 핵심이다.

키 `user-42`의 이벤트로 타임라인을 그려 보자.

```text
                증설                          P0에 남아 있던 그 키의
                 |                            잔여분이 전부 소비된 순간
   ──────────────┼──────────────────────────────────┼──────────────>  시간
                 |<========= 위험 구간 =============>|
                 |     (순서 역전이 가능한 기간)      |

  [증설 전에 발행]  P0 :  가입   프로필수정         <- 아직 미소비 (랙이 있다)
  [증설 후에 발행]  P2 :                     탈퇴   <- 새 이벤트는 여기로

  위험 구간 안에서 P0 담당 컨슈머와 P2 담당 컨슈머는 서로 다른 프로세스이고,
  둘의 진도는 완전히 독립이다. 파티션 사이에는 앞뒤 관계가 정의되지 않는다.

    P0 담당 컨슈머 : 랙 8만 건. "가입", "프로필수정"이 아직 큐에서 대기 중
    P2 담당 컨슈머 : 한가함.    "탈퇴"를 즉시 처리

  실제 처리 순서 = 탈퇴 -> 가입 -> 프로필수정        <- 순서 역전
  -> "탈퇴한 회원이 다시 살아나는" 정합성 사고

  그런데 P0의 잔여분이 모두 소비되고 나면, 이 키의 미처리 메시지는
  P2에만 존재한다. 순서 관계가 다시 한 파티션 안으로 모이므로
  P2 안에서의 오프셋 순서가 곧 처리 순서가 된다. 위험 구간이 닫힌다.
```

**즉 위험 구간의 끝은 "옛 파티션에 남아 있던 그 키의 미소비 메시지가 전부 소비되는 시점"이다.** 이것은 곧 그 파티션의 **랙이 0이 되는 시점**이다.

이 인과가 3절 전략 1("드레인 후 증설")의 근거 전체다. 위험 구간의 길이가 "증설 시점의 랙"으로 결정된다면, **증설 전에 랙을 0으로 만들어 두면 위험 구간의 길이가 0**이 된다. 순서 문제를 "대응"하는 것이 아니라 **성립하지 않게 만드는** 것이다.

한 가지 정밀한 단서를 붙이면 좋다. 엄밀히 말하면 기준은 파티션 전체의 랙이 아니라 **"그 키의" 미소비 메시지**다. P0에 다른 키의 메시지가 잔뜩 남아 있어도 `user-42`의 잔여분만 없으면 `user-42`는 이미 안전하다. 다만 운영 중에 "어느 키가 아직 남았는지"를 알아낼 방법이 없으므로, 실무의 판정 기준은 **파티션 랙 0**이 된다. 이론적 기준과 실무적 기준이 다르다는 것까지 말할 수 있으면 좋다.

### 1-3. 왜 "리텐션 기간 동안"이 오답인가

이 질문에 "리텐션 기간 동안 위험하다"고 답하는 경우가 흔한데, **소비와 보관을 혼동한 것**이다.

**리텐션(retention)**은 브로커가 로그를 디스크에 얼마나 오래 보관하는가의 설정이다. 컨슈머가 이미 처리한 메시지도 리텐션이 지나기 전까지는 로그에 남아 있다. 그런데 **이미 소비 완료한 메시지는 컨슈머가 다시 읽지 않으므로 순서에 아무 영향이 없다.** 커밋 오프셋이 이미 그 앞을 지나갔기 때문이다.

```text
                      무엇을 재는가                    증설 위험 구간과의 관계
리텐션    브로커가 로그를 보관하는 기간              무관.
                                                    소비 완료분은 다시 읽히지 않는다.
랙        옛 파티션에 남은 미소비 메시지 수          이것이 0이 되면 위험 구간이 닫힌다.
```

역으로, 리텐션이 7일이어도 컨슈머가 실시간으로 따라오고 있으면 위험 구간은 몇 초로 끝난다. 반대로 리텐션이 1일이어도 컨슈머가 20시간 밀려 있으면 위험 구간은 20시간이다. **위험 구간을 결정하는 것은 보관 정책이 아니라 소비 진도다.**

### 1-4. 그래서 위험 구간의 길이는 증설 직전의 랙이 정한다

이 결론을 숫자로 만들어 두면 증설 계획을 세울 때 바로 쓸 수 있다. 랙이 0이 되기까지 걸리는 시간은 `31-consumer-lag-diagnosis-and-resolution.md`의 환산 공식과 같다.

```text
위험 구간의 길이 ≈ 증설 시점의 (그 파티션) 랙 ÷ 처리율

[사례] 증설 직전 P0의 랙이 600,000건, 컨슈머 처리율 1,000건/s

  600,000 ÷ 1,000 = 600초 = 10분
  -> 증설 후 약 10분 동안 이 키의 순서 역전이 가능하다.
```

검산하면 600,000 ÷ 1,000 = 600초이고 600 ÷ 60 = 10분이다.

이 계산이 실무에서 하는 일은 두 가지다. **하나, 증설 시점을 고르는 근거가 된다** — 랙이 상시 밀려 있는 시간대가 아니라 랙이 바닥인 새벽에 하면 위험 구간이 몇 초로 줄어든다. **둘, 위험 구간 동안 무엇을 감수하는지를 사업 측에 설명할 수 있다** — "10분간 회원 상태 이벤트의 순서가 역전될 수 있습니다"는 판단 가능한 정보지만 "순서가 좀 깨질 수 있습니다"는 아니다.

## 2. 순서 말고도 있는 부작용들

증설의 파급은 순서 하나가 아니다. 네 가지가 더 있고, 이 중 셋은 순서 요구가 없는 토픽에도 해당한다.

### 2-1. ① 컨슈머 그룹 리밸런싱 — 일시 중단과 중복 처리

컨슈머들도 프로듀서처럼 토픽 메타데이터를 캐시해 두고 주기적으로 갱신한다. 갱신 과정에서 **파티션이 늘어난 것을 감지하면, 늘어난 파티션을 누가 맡을지 정하기 위해 그룹 전체의 리밸런싱**이 일어난다.

**리밸런싱(rebalancing)**은 컨슈머 그룹 안에서 파티션 할당을 다시 계산해 반영하는 절차다. 여기에 두 가지 대가가 붙는다.

**일시적인 소비 중단.** 할당을 재계산하고 각 컨슈머에 반영하는 동안 그룹의 소비가 멈춘다. 파티션 수와 컨슈머 수가 많을수록 이 시간이 길어진다.

**중복 처리.** 재할당 직전에 처리는 끝났지만 아직 커밋하지 못한 메시지가 있으면, 그 파티션을 새로 넘겨받은 컨슈머가 커밋 오프셋부터 다시 읽으므로 **같은 메시지를 한 번 더 처리한다.** 즉 파티션 증설은 순서 문제뿐 아니라 **중복 처리도 유발할 수 있다.** 컨슈머가 멱등하지 않다면(같은 메시지를 두 번 처리해도 결과가 한 번 처리한 것과 같지 않다면) 여기서도 사고가 난다. (리밸런싱과 처리 중 메시지: `26-consumer-rebalancing-and-in-flight-messages.md`, 멱등 컨슈머: `04-idempotent-consumer-implementation.md`)

그래서 순서 요구가 전혀 없는 토픽이라도 **증설은 트래픽이 낮은 시간대에** 한다. 리밸런싱 자체의 비용은 피할 수 없기 때문이다.

### 2-2. ② 프로듀서 메타데이터 갱신 시차 — 같은 키가 두 파티션에 동시에 쌓인다

프로듀서는 메시지를 보낼 때마다 브로커에 "이 토픽 파티션이 몇 개야?"를 묻지 않는다. 그러면 매 전송마다 왕복이 하나 더 붙어 처리량이 감당이 안 된다. 대신 **토픽 메타데이터**(파티션 목록과 각 파티션의 리더 브로커가 누구인지)를 **로컬에 캐시**해 두고 주기적으로만 갱신한다.

갱신 주기는 `metadata.max.age.ms`가 정하고 **기본값은 5분**이다. (전송 실패나 리더 변경을 감지하면 그보다 일찍 갱신하기도 한다.) 문제는 각 프로듀서 인스턴스가 **서로 다른 시각에 시작됐으므로 갱신 시점도 제각각**이라는 점이다.

```text
증설 시각을 t0라 하자. 프로듀서 3대의 캐시 갱신 시점은 서로 무관하다.

  t0 ─────────────────────────────────────────────> 최대 5분 후
  프로듀서 A : [파티션 3개로 알고 있음]──갱신(t0+20초)──[4개]
  프로듀서 B : [파티션 3개로 알고 있음]──────────갱신(t0+3분)──[4개]
  프로듀서 C : [파티션 3개로 알고 있음]───────────────갱신(t0+4분40초)──[4개]

  t0 + 1분 시점에 세 프로듀서가 각각 키 "user-42"를 보내면
    A (갱신 완료) -> 6 % 4 = 2 -> P2
    B (갱신 전)   -> 6 % 3 = 0 -> P0
    C (갱신 전)   -> 6 % 3 = 0 -> P0

  같은 키의 "새" 메시지가 P0과 P2에 동시에 쌓인다.
```

이것이 왜 별개의 부작용인가. 1-2의 위험 구간은 "옛 메시지 대 새 메시지"의 경합이었다. 여기서는 **새 메시지끼리도 두 파티션으로 갈린다.** 결과적으로 증설 후에는 위험 구간이 두 겹으로 쌓인다.

```text
(a) 옛 파티션의 잔여분이 소비될 때까지        -> 랙이 0이 되면 닫힌다 (1-2)
(b) 모든 프로듀서의 메타데이터가 갱신될 때까지 -> 최대 metadata.max.age.ms만큼 (기본 5분)
```

(b) 때문에 "증설 후 옛 메시지만 다 처리하면 끝"이라고 단정할 수 없다. (b) 구간에 P0으로 새로 들어간 메시지가 또 잔여분이 되기 때문이다. **발행을 멈추지 않는 한 혼재 구간을 완전히 없앨 수는 없다** — 전략 1이 "프로듀서 발행 중지"부터 시작하는 이유가 여기에도 있다.

### 2-3. ③ compacted 토픽의 낡은 값 잔존 (가산점 포인트)

먼저 전제를 깔자. **로그 컴팩션(log compaction)**은 토픽의 정리 정책 중 하나로, "오래된 것을 지운다"(시간 기반 리텐션) 대신 **"같은 키의 옛 값을 지우고 키별 최신 값 하나만 남긴다"**는 청소 방식이다. 이 토픽을 처음부터 끝까지 읽으면 키별 최신 상태의 스냅샷이 복원되므로, 상태 저장소나 CDC 결과 토픽처럼 **"현재 상태"를 담는 용도**에 쓴다. (상세: `36-log-compaction-compacted-topic.md`)

여기서 결정적인 사실이 하나 있다. **컴팩션은 파티션 단위로 일어난다.** 브로커가 P0의 로그를 청소할 때는 P0 안에서만 같은 키를 찾아 옛 값을 지운다. P2에 그 키의 더 새로운 값이 있는지는 보지 않는다. 볼 필요가 없었기 때문이다 — 증설 전에는 같은 키가 **언제나 같은 파티션**에 있었다.

증설이 바로 그 전제를 깬다.

```text
키 user-42의 등급 이벤트. 파티션 3개 -> 4개로 증설.

[증설 전]  P0 : (user-42, 등급=SILVER)     <- 당시의 최신값
[증설]
[증설 후]  P2 : (user-42, 등급=GOLD)       <- 새 값은 P2로 간다

컴팩션이 돌면 어떻게 되는가?

  P0 청소 : P0 안에 user-42의 값이 하나뿐 -> 지울 대상이 없다. SILVER 생존.
  P2 청소 : P2 안에 user-42의 값이 하나뿐 -> 지울 대상이 없다. GOLD 생존.

  두 값은 서로 다른 파티션에 있으므로 컴팩션이 서로를 지워주지 못한다.
  -> 옛 값 SILVER가 로그에 "영원히" 남는다.
     (P0에는 이 키의 새 메시지가 다시는 오지 않으므로 갱신될 기회도 없다.)
```

그래서 이 토픽으로 상태를 복원하면 이런 일이 생긴다.

```text
복원 컨슈머가 토픽 전체를 처음부터 읽는다.

  P0에서 (user-42, SILVER)를 읽는다
  P2에서 (user-42, GOLD)를 읽는다

  파티션 사이에는 앞뒤 관계가 정의되지 않으므로 읽는 순서를 보장할 수 없다.
  SILVER를 나중에 읽으면 GOLD를 덮어쓴다 -> 등급이 조용히 강등된다.
```

**키 하나에 값이 둘 보이고, 어느 쪽이 최신인지 로그 구조만으로는 판정할 수 없다.** 오프셋으로 비교할 수도 없다 — 오프셋은 파티션마다 독립적으로 매겨지는 번호라 P0의 오프셋 500과 P2의 오프셋 3은 크기를 비교할 수 있는 값이 아니다.

그래서 **상태 스냅샷이나 CDC 용도의 compacted 토픽은 사실상 증설 불가**로 취급하는 것이 안전하다. 파티션을 늘려야 한다면 새 토픽을 만들어 전체 상태를 다시 발행하는 방식(전략 2)을 쓴다.

### 2-4. ④ 스트림 처리의 co-partitioning 파괴 (가산점 포인트)

**co-partitioning(공동 파티셔닝)이 무엇인지부터 정의하자.** 두 토픽을 키로 조인한다는 것은 "양쪽 토픽에서 같은 키를 가진 레코드를 짝지어 처리한다"는 뜻이다. 그런데 Kafka Streams 같은 스트림 처리 엔진은 이 조인을 **각 태스크가 자기가 맡은 파티션 번호 안에서 로컬로** 수행한다. 태스크 2번은 `orders`의 P2와 `payments`의 P2만 들고 있고 다른 파티션은 쳐다보지 않는다. 그래야 네트워크를 건너 데이터를 뒤섞는 과정 없이 로컬 메모리·디스크에서 조인이 끝나기 때문이다.

이 구조가 성립하려면 전제가 필요하다. **같은 키가 양쪽 토픽에서 같은 번호의 파티션에 들어가 있어야 한다.** 이 성질을 co-partitioning이라 부른다. 그리고 목적지가 `해시(키) % 파티션 수`이므로, 이 성질이 성립하려면 **양쪽의 파티션 수가 같아야** 한다(그리고 같은 파티셔너를 써야 한다).

실제 해시값으로 그려 보면 이렇다.

```text
[정상 — orders와 payments가 둘 다 파티션 4개]

  키 user-1001 (murmur2 해시 = 1,095,147,730)
     orders   : 1,095,147,730 % 4 = 2  ->  orders-P2
     payments : 1,095,147,730 % 4 = 2  ->  payments-P2
                                             ^ 번호가 같다

  조인 태스크 2 : [orders-P2] + [payments-P2]
                  -> 같은 키가 한 태스크 안에서 만난다. 조인 성립.

[깨짐 — orders만 6개로 증설]

  키 user-1001
     orders   : 1,095,147,730 % 6 = 4  ->  orders-P4
     payments : 1,095,147,730 % 4 = 2  ->  payments-P2
                                             ^ 번호가 다르다

  조인 태스크 4 : [orders-P4] + [payments-P4]
                  -> payments-P4에는 user-1001이 없다. 짝을 못 찾는다.
                  -> 조인 결과가 비어 버린다.
```

`1,095,147,730 % 4 = 2`이고 `1,095,147,730 % 6 = 4`인 것은 직접 계산해 확인한 값이다.

드러나는 방식이 두 가지라는 점을 알아 두면 좋다. **Kafka Streams는 조인 대상 토픽들의 파티션 수 불일치를 토폴로지 시작 시점에 검증**하므로, 이 경우 애플리케이션이 아예 뜨지 않는 형태로 즉시 드러난다. 반면 **각 컨슈머가 자기 파티션 안의 로컬 상태로 직접 매칭하도록 손으로 구현한 조인**은 아무 예외도 던지지 않고 **결과만 조용히 비어 간다.** 후자가 훨씬 위험하다 — 며칠 뒤 "매칭률이 떨어졌다"는 지표로 발견된다.

같은 이유로 **키 단위 로컬 상태를 들고 있는 컨슈머**도 깨진다. "이 키는 항상 내 파티션으로 온다"는 가정 위에서 파티션별 로컬 캐시에 키별 누적 상태를 쌓아 두었다면, 증설로 그 키가 다른 파티션으로 옮겨 간 순간 **새 담당 컨슈머는 그 키의 누적 상태를 전혀 모른 채 0부터 시작한다.** 옛 담당 컨슈머의 캐시에는 다시 갱신되지 않는 유령 상태가 남는다.

## 3. 그래서 어떻게 늘리나 — 안전한 증설 절차

### 3-1. 증설 전에 답해야 할 네 가지

증설 결정 전에 이 토픽에 대해 네 개의 질문에 답한다. 2절의 부작용들이 각각 이 질문에 대응한다.

```text
① 이 토픽의 컨슈머가 키 기반 순서에 의존하는가?   -> 예 라면 1절의 위험 구간이 실재한다
② 이 토픽은 compacted 토픽인가?                  -> 예 라면 2-3. 사실상 증설 불가
③ 이 토픽이 다른 토픽과 키로 조인되는가?          -> 예 라면 2-4. 짝 토픽도 같이 늘려야 한다
④ 컨슈머가 키 단위 로컬 상태를 들고 있는가?       -> 예 라면 2-4 후반. 상태 재구축 계획 필요
```

**네 답이 모두 "아니오"인 토픽**(대표적으로 로그, 메트릭, 순서 무관 알림)은 **그냥 늘려도 된다.** 남는 고려사항은 리밸런싱 타이밍뿐이므로, 트래픽이 낮은 시간대를 고르면 끝이다. 이 경우까지 겁을 내면 정당한 확장을 못 한다.

**하나라도 "예"라면** 아래 전략 중 하나를 쓴다. 그 전에, 증설이 정말 필요한지부터 확인한다 — 컨슈머 단일 처리량 개선으로 해결되는 경우가 많고, 그쪽은 되돌릴 수 있는 카드다(4절 첫 번째 꼬리질문).

### 3-2. 전략 1 — 드레인 후 증설 (발행을 멈출 수 있을 때)

```text
1. 프로듀서 발행 중지 (또는 발행량이 0인 점검 시간대를 고른다)
2. 컨슈머 랙이 전 파티션 0이 될 때까지 대기   <- 옛 파티션에 잔여분이 없어진다
3. 파티션 증설
4. 발행 재개
```

**왜 안전한가.** 1-2에서 위험 구간의 끝이 "옛 파티션의 잔여분이 소비되는 시점"이라는 것을 확인했다. 2단계에서 그 잔여분을 미리 0으로 만들었으므로, **증설 시점에 이미 위험 구간의 길이가 0**이다. 순서 문제를 대응하는 것이 아니라 **성립하지 않게** 만든 것이다.

그리고 1단계의 발행 중지는 2-2의 메타데이터 시차 문제까지 함께 처리한다. 발행이 멈춰 있는 동안 프로듀서를 재시작하거나 캐시 갱신 주기(기본 5분) 이상을 기다린 뒤 재개하면, 재개 시점에 모든 프로듀서가 이미 새 파티션 수를 알고 있게 만들 수 있다.

2단계의 확인은 이렇게 한다.

```bash
kafka-consumer-groups.sh --bootstrap-server broker:9092 \
  --group order-consumer --describe
# 모든 파티션의 LAG이 0인지 확인한다.
#
# 놓치기 쉬운 것: 이 토픽을 읽는 컨슈머 그룹이 여러 개일 수 있다.
# 한 그룹의 랙이 0이어도 다른 그룹은 밀려 있을 수 있고,
# 그 그룹에게는 위험 구간이 그대로 열려 있다.
# --list로 그룹 목록을 먼저 뽑아 전부 확인해야 한다.
kafka-consumer-groups.sh --bootstrap-server broker:9092 --list
```

**전제와 한계.** 발행을 멈출 수 있어야 하고, 랙 0을 확인할 수 있어야 한다. 24시간 트래픽이 들어오는 토픽에는 쓸 수 없고, 그때는 전략 2로 간다.

### 3-3. 전략 2 — 새 토픽으로 마이그레이션 (무중단이 필요할 때)

원하는 파티션 수로 새 토픽을 만들고 트래픽을 옮긴다. 순서가 중요하다.

```text
1. 원하는 파티션 수로 새 토픽 orders.v2를 만든다.

2. 컨슈머를 "orders + orders.v2 양쪽 구독"으로 먼저 배포한다.
   <- 순서 주의: 프로듀서를 먼저 옮기면 새 토픽에 쌓이는데 아무도 안 읽는 구간이 생긴다.
      읽는 쪽을 먼저 준비하고 쓰는 쪽을 나중에 옮긴다.

3. 프로듀서를 orders.v2로 전환한다.

4. 구 토픽 orders의 랙이 0이 될 때까지 기다린다.

5. 컨슈머에서 구 토픽 구독을 제거하고, 구 토픽을 삭제한다.
```

**파티션 수를 "줄일" 때도 이 방법뿐이다.** Kafka는 파티션 축소 API를 제공하지 않으므로, 축소는 언제나 새 토픽 마이그레이션이다.

여기에 정직하게 짚어야 할 한계가 있다. **3단계와 4단계 사이에도 같은 키의 옛 메시지(구 토픽)와 새 메시지(신 토픽)가 공존한다.** 두 토픽 사이에도 순서 관계는 없으므로, 이 구간에서는 여전히 순서 역전이 가능하다. 즉 이 전략은 **무중단을 얻는 대신 순서 안전을 완전히 사지는 못한다.**

순서까지 지키려면 한 단계를 더 넣는다. 컨슈머가 신 토픽을 구독하되, **구 토픽의 랙이 0이 되기 전에는 신 토픽의 메시지를 처리하지 않도록 잡아 둔다.** Kafka Consumer의 `pause()`로 특정 파티션의 소비를 일시 정지시켰다가 조건이 만족되면 `resume()`하는 방식이다. 무중단과 순서를 둘 다 얻지만, 그 대가로 컨슈머 코드에 전환 전용 로직이 들어가고 전환이 끝난 뒤 그것을 걷어내는 작업이 따라붙는다.

### 3-4. 전략 3 — 애초에 겪지 않기

가장 좋은 대응은 지금까지 나온 어떤 절차도 아니고 **설계 시점의 산정**이다.

`29-partition-count-sizing.md`가 그 산정법을 다룬다. 골자는 `필요 파티션 수 = ceil(피크 처리량 ÷ 컨슈머 1대의 처리량) × 성장 여유 배수`이고, 여기서 **순서 요구가 있는 토픽은 여유 배수를 후하게(2~3배) 잡는다**는 것이 이 문서와 이어지는 지점이다.

왜 후하게 잡아야 하는지를 이 문서의 언어로 다시 말하면 이렇다. **두 비용의 성격이 다르기 때문이다.**

- 파티션을 여유 있게 잡는 비용은 **상시로 조금씩 내는 요금**이다 — 브로커의 파일 핸들과 메타데이터, 복제 스레드, 리더 선출 시간, 프로듀서 배칭 효율 저하. 매일 조금씩 손해지만 예측 가능하고, 언제든 클러스터를 키워 흡수할 수 있다.
- 증설의 비용은 **한 번에 크게 치르는, 되돌릴 수 없는 손실**이다 — 위험 구간 동안 발생한 정합성 사고는 사후에 되돌릴 수 없고, compacted 토픽이라면 잘못된 상태가 영구히 남는다.

**예측 가능한 상시 요금과 되돌릴 수 없는 일회성 손실 중에서는 전자를 택하는 것이 합리적이다.** 그래서 순서 요구가 있는 토픽에서 파티션 과잉 산정은 낭비가 아니라 보험료다.

## 4. 꼬리질문 대비 포인트

### "증설 없이 처리량을 올릴 수는 없나요?"

증설을 검토하기 전에 볼 카드들이 있다. 순서대로 **컨슈머 단일 처리량 개선**이다 — 배치 폴링과 배치 쓰기로 다운스트림 왕복 줄이기, DB 슬로우 쿼리·커넥션 풀 등 다운스트림 최적화, 컨슈머 프로세스 안에서 키 단위로 나눈 워커 스레드 병렬화.

**순서를 강조해서 말하는 것이 중요하다.** 컨슈머 최적화는 마음에 안 들면 되돌릴 수 있는 카드이고, 파티션 증설은 되돌릴 수 없는 카드다. **되돌릴 수 있는 카드를 먼저 쓴다.** 게다가 컨슈머 1대의 처리량이 두 배가 되면 필요 파티션 수 자체가 절반이 되므로, 최적화가 증설 필요성을 없애 버리는 경우도 흔하다.

파티션 증설은 컨슈머 처리량 개선으로 안 될 때의 카드이고, 순서 요구가 있다면 그때도 2절의 부작용 검토가 선행되어야 한다.

### "순서가 깨지는 기간은 정확히 언제까지인가요?"

증설 시점부터 **컨슈머가 옛 파티션에 남아 있던 해당 키의 메시지를 모두 처리할 때까지**다(1-2). 곧 **그 파티션의 랙이 0이 되는 시점**이고, 길이는 `증설 시점의 랙 ÷ 처리율`로 어림할 수 있다. 랙이 0 근처로 유지되는 토픽이라면 위험 구간이 몇 초로 끝나고, 랙이 상시 밀려 있는 토픽일수록 역전 가능 구간이 길다.

**"리텐션 기간 동안"이라고 답하면 소비와 보관을 혼동한 것이다**(1-3). 리텐션은 브로커가 로그를 얼마나 오래 들고 있느냐이고, 이미 소비 완료한 옛 메시지는 로그에 남아 있어도 다시 읽히지 않으므로 순서에 영향이 없다.

여기에 2-2를 덧붙이면 답이 완성된다. 위험 구간은 사실 두 겹이다 — **옛 잔여분이 소비될 때까지**와, **모든 프로듀서의 메타데이터 캐시가 갱신될 때까지**(기본 5분)다. 후자 구간에는 새 메시지조차 두 파티션으로 갈리므로 새 잔여분이 계속 만들어진다.

### "커스텀 파티셔너로 기존 키의 매핑을 고정하면 안 되나요?"

**커스텀 파티셔너**는 Kafka의 `Partitioner` 인터페이스를 구현해 목적지 파티션을 직접 계산하도록 바꾸는 것이다. 기존 키를 옛 분모로 계속 보내면 목적지가 안 바뀌므로 순서가 지켜진다는 발상이고, 아이디어 자체는 성립한다.

```java
// 기존 키는 옛 분모(3)로 고정하고, 신규 키만 늘어난 파티션까지 쓰게 하는 절충안
public class LegacyPinningPartitioner implements Partitioner {

    private static final int OLD_PARTITION_COUNT = 3;

    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                         Object value, byte[] valueBytes, Cluster cluster) {
        int hash = Utils.toPositive(Utils.murmur2(keyBytes));

        // 증설 이전부터 존재하던 키는 옛 분모로 계속 라우팅한다.
        // 목적지가 그대로이므로 이 키의 순서 관계는 한 파티션 안에 유지된다.
        if (legacyKeys.contains(key)) {
            return hash % OLD_PARTITION_COUNT;
        }
        // 신규 키만 늘어난 파티션 수를 분모로 쓴다.
        return hash % cluster.partitionCountForTopic(topic);
    }
}
```

문제는 두 가지다.

**첫째, 증설의 목적이 무색해진다.** 기존 키들은 새로 만든 파티션을 영영 활용하지 못한다. 트래픽의 90%가 기존 키에서 나온다면 파티션을 3개에서 4개로 늘려도 실제 부하 분산은 거의 개선되지 않는다. **부하를 나누려고 늘렸는데 나눠지지 않는다.**

**둘째, 운영 부채가 남는다.** 위 코드의 `legacyKeys`는 어디서 관리하는가? 모든 프로듀서 인스턴스가 같은 집합을 봐야 하고, 그 집합은 시간이 지날수록 커진다. 그리고 몇 달 뒤 이 코드를 보는 사람은 왜 분모가 두 개인지 알 수 없다. **파티셔너에 상태와 규칙이 들어간 순간, 운영자가 그 규칙을 계속 기억해야 하는 부채가 된다.**

일반적으로는 **새 토픽 마이그레이션(전략 2)이 더 깔끔하다.** 전환이 끝나면 특별한 규칙이 아무것도 남지 않기 때문이다.

### "파티션을 줄이는 것은요?"

**Kafka가 지원하지 않는다.** 기술적 판단 이전에 API 자체가 없다.

이유는 두 파티션을 합칠 때 답할 수 없는 질문이 바로 생기기 때문이다 — **P0의 오프셋 100과 P1의 오프셋 100 중 어느 쪽이 먼저인가?** 오프셋은 파티션마다 독립적으로 매겨지는 번호라 서로 비교할 수 있는 값이 아니고, 시간 순서로 섞으려 해도 각 파티션 안의 원래 순서와 충돌한다. 게다가 합치는 순간 키 라우팅 결과도 전부 바뀐다.

축소가 필요하면 **새 토픽 마이그레이션이 유일한 방법**이다(전략 2). (관련: `29-partition-count-sizing.md`의 "왜 파티션 수를 줄일 수는 없나요?")

### "그럼에도 증설을 받아들일 수 있는 경우는요?" (시니어 변별 포인트)

**컨슈머가 순서 역전에 견디도록 설계돼 있다면 증설은 안전하다.** 판단 기준을 토픽 설정이 아니라 컨슈머 쪽으로 옮기는 것이 이 답의 핵심이다.

가장 흔한 방법은 **이벤트에 버전이나 발생 시각을 실어, 자기 상태보다 최신일 때만 반영하는 컨슈머**를 만드는 것이다.

```java
// 순서 역전에 견디는 컨슈머 — 증설이 무해해지는 조건
@Transactional
public void apply(UserEvent event) {
    User user = userRepository.findByIdForUpdate(event.userId());

    // 이 이벤트가 이미 반영한 것보다 옛것이면 조용히 버린다.
    // 파티션이 갈려 "탈퇴"가 "가입"보다 먼저 도착하더라도,
    // 뒤늦게 도착한 옛 이벤트가 최신 상태를 덮어쓰는 일이 없다.
    if (event.version() <= user.getVersion()) {
        return;
    }
    user.applyAndBumpVersion(event);
}
```

여기서 `version`이 무엇이어야 하는지가 실무 포인트다. **Kafka 오프셋은 쓸 수 없다** — 파티션마다 독립적으로 매겨지는 번호라 P0의 500과 P2의 3을 비교할 수 없기 때문이다. 발생 시각도 서버 간 시계 오차가 있으면 위험하다. 가능하면 **원천 DB가 채번한 단조 증가 버전 컬럼**을 이벤트에 실어 보낸다.

다만 이 방어가 모든 이벤트에 통하는 것은 아니다. 세 종류로 갈린다.

- **누적 연산 이벤트**(포인트 +100, -50) — 더하기는 순서를 바꿔도 결과가 같으므로 애초에 안전하다.
- **덮어쓰기 이벤트**(등급 = GOLD, 주소 = ...) — 위 버전 가드로 방어된다.
- **상태 머신 이벤트**(주문 생성 -> 취소) — 가장 어렵다. "취소"가 "생성"보다 먼저 오면 취소할 대상이 없으므로 버릴 수도 반영할 수도 없고, 선행 이벤트가 올 때까지 **보관했다가 나중에 적용하는 버퍼링**이 필요하다. 이건 컨슈머에 상당한 복잡도를 더한다.

정리하면 **판단 기준은 "이 토픽의 컨슈머들이 순서에 의존하는가"**이고, 장기적으로는 순서 의존 자체를 줄이는 설계가 증설 자유도를 되찾는 근본 대응이다. **"증설 가능 여부는 토픽 설정이 아니라 컨슈머의 계약이 결정한다"**고 정리하면 설계 관점을 보여줄 수 있다.

## 한 줄 요약

파티션 증설은 `해시(키) % 파티션 수`의 분모를 바꿔 같은 키를 다른 파티션으로 보내기 시작하므로 옛 파티션의 잔여분을 따라잡을 때까지(리텐션이 아니라 랙이 0이 될 때까지) 키 순서가 깨지고, 그 위에 리밸런싱으로 인한 중단·중복, 프로듀서 메타데이터 갱신 시차로 인한 혼재 구간, compacted 토픽에서 다른 파티션에 남아 컴팩션이 지워주지 못하는 옛 값, 스트림 조인의 co-partitioning 파괴가 겹친다 — 그래서 순서가 중요한 토픽은 드레인 후 증설이나 새 토픽 마이그레이션으로 다루고, 근본적으로는 산정 단계의 여유(`29-partition-count-sizing.md`)와 순서 의존을 줄인 컨슈머 설계로 이 문제 자체를 회피하는 것이 정답이다.
