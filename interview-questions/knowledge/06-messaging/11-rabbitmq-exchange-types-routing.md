# Exchange 타입과 라우팅 설계 — 분기를 코드에 둘 것인가, 브로커에 둘 것인가

> 핵심 관전 포인트: **exchange 타입은 "라우팅 키를 어떻게 대조할 것인가"의 네 가지 답이다. direct는 완전 일치, fanout은 대조 없이 전부, topic은 점으로 끊은 패턴 매칭, headers는 키·값 조합 매칭. 실무에서는 topic 하나로 나머지를 거의 다 흉내 낼 수 있어서 처음부터 topic exchange를 두는 것이 기본 선택이다 — fanout으로 시작하면 나중에 "이 소비자는 결제 실패만 받고 싶다"는 요구가 왔을 때 exchange를 새로 만들고 프로듀서를 고쳐야 하지만, topic이면 바인딩만 추가하면 된다. 그리고 "한 이벤트를 여러 서비스가 각자 받는" 요구는 exchange 타입의 문제가 아니라 큐를 서비스마다 따로 두느냐 공유하느냐의 문제다. 이 둘을 구분하지 못하면 두 서비스가 한 큐를 나눠 먹으면서 각자 절반씩만 처리하는 사고가 난다.**

---

## 0. 질문 + 의도

**질문**: "Exchange 타입(direct/fanout/topic/headers)의 차이와 선택 기준은? 하나의 이벤트를 여러 서비스가 각자 받아야 한다면 어떻게 설계하나요?"

**출제 의도**: 분기 조건을 애플리케이션 if 문으로 풀 것인가 브로커 설정으로 풀 것인가의 선택을 아는지 본다. 이 선택은 "새 소비자가 붙을 때 기존 코드를 고쳐야 하는가"라는 확장성 질문으로 직결된다. 인프라가 이미 제공하는 기능을 알고 코드를 아끼는 감각, 그리고 경쟁 소비자와 팬아웃을 혼동하지 않는 정확성을 확인한다.

## 1. 전제 — 왜 exchange 타입이라는 것이 존재하는가

### 1-1. 분기는 어디선가 반드시 일어난다

주문 도메인에서 이벤트가 세 종류 나온다고 하자: `주문 생성`, `결제 완료`, `결제 실패`. 그리고 소비자가 셋 있다.

- 알림 서비스: 결제 관련 이벤트 전부 필요
- 정산 서비스: 결제 완료만 필요
- 보정 배치: 결제 실패만 필요

"어떤 메시지를 누가 받을지" 결정하는 일은 어디선가 반드시 일어나야 한다. 자리는 셋뿐이다.

```
① 프로듀서가 결정          ② 브로커가 결정          ③ 컨슈머가 결정
   if (실패) send(보정큐)      exchange + 바인딩        전부 받고 나서
   if (완료) send(정산큐)                              if (내 것 아니면) skip
   ...
```

①은 프로듀서가 모든 소비자를 알아야 한다. 소비자가 하나 늘 때마다 프로듀서를 고치고 배포해야 하므로 이벤트 기반 아키텍처의 이점이 사라진다.

③은 Kafka가 택한 길이다. 브로커는 단순하게 두고 컨슈머가 다 받아서 거른다. 브로커 부하는 낮지만 **필요 없는 메시지까지 네트워크로 흘려보내고 컨슈머가 역직렬화한 뒤 버린다.**

②가 RabbitMQ가 택한 길이고, **exchange 타입은 그 "브로커가 결정하는 방식"의 종류**다. 타입이 넷인 것은 대조 방식이 넷이라는 뜻일 뿐이다.

### 1-2. 대조의 재료 — 라우팅 키와 헤더

exchange가 판단에 쓸 수 있는 재료는 둘뿐이다.

**라우팅 키**는 프로듀서가 메시지에 붙이는 문자열 하나다. direct·fanout·topic이 이것을 본다(fanout은 보지 않기로 한 것이지만).

**헤더**는 메시지에 딸린 키·값 맵이다. headers 타입만 이것을 본다.

메시지 본문(payload)은 **어떤 exchange도 들여다보지 않는다.** "금액이 10만 원 이상인 주문만 이 큐로" 같은 라우팅은 브로커가 해줄 수 없다. 그런 분기가 필요하면 프로듀서가 그 정보를 라우팅 키나 헤더로 끌어올려야 한다. 이 제약을 아는 것이 라우팅 설계의 출발점이다.

## 2. 네 가지 타입

### 2-1. direct — 완전 일치

라우팅 키와 바인딩 키가 **문자열로 정확히 같을 때만** 배달한다.

```
[direct exchange]
  메시지 라우팅 키: "payment.failed"

  바인딩 키 "payment.failed" 인 큐  --> 배달 O
  바인딩 키 "payment.done"   인 큐  --> 배달 X
  바인딩 키 "payment"        인 큐  --> 배달 X (부분 일치는 없다)
```

가장 단순하고 가장 빠르다. 작업 유형이 몇 개로 고정되어 있고 늘어날 일이 없는 작업 큐에 적합하다 — 예를 들어 이미지 리사이즈 워커를 `thumbnail`, `webp`, `original` 세 종류로 나누는 경우.

한 가지 자주 놓치는 사실이 있다. **같은 큐에 바인딩 키를 여러 개 걸 수 있다.** direct도 이 방법으로 "여러 종류를 한 큐가 받게" 만들 수 있다.

```java
// 알림 큐가 완료와 실패를 모두 받게 하려면 바인딩을 두 개 건다
@Bean Binding b1(Queue notify, DirectExchange ex) {
    return BindingBuilder.bind(notify).to(ex).with("payment.done");
}
@Bean Binding b2(Queue notify, DirectExchange ex) {
    return BindingBuilder.bind(notify).to(ex).with("payment.failed");
}
// 종류가 늘 때마다 바인딩을 추가해야 한다 -> 이 시점이 topic으로 갈아탈 신호
```

### 2-2. fanout — 대조하지 않고 전부

라우팅 키를 **아예 보지 않고** 바인딩된 모든 큐에 복사본을 넣는다.

```
[fanout exchange]
  라우팅 키가 무엇이든 (빈 문자열이어도)
     --> 큐 A, 큐 B, 큐 C 전부에 한 통씩
```

"이 이벤트는 관심 있는 모두에게"라는 방송(broadcast)을 표현한다. 캐시 무효화 신호처럼 **모든 인스턴스가 받아야 하는 알림**에 잘 맞는다.

다만 실무에서 fanout을 첫 선택으로 두는 것은 대개 성급하다. 이유는 **필터를 나중에 추가할 수 없기 때문**이다. 처음엔 모두가 전부 받아도 괜찮았지만, 소비자가 늘면 "나는 이 중 일부만 필요하다"는 요구가 반드시 생긴다. fanout에는 그 표현이 없으므로 exchange를 새로 만들고 프로듀서의 발행 대상을 바꿔야 한다 — 즉 프로듀서 배포가 필요해진다.

**topic exchange에 `#` 패턴으로 바인딩하면 fanout과 같은 동작을 얻는다.** 그러면서 나중에 필터가 필요한 소비자만 자기 바인딩 키를 좁히면 된다. 이것이 "처음부터 topic"을 권하는 실질적 이유다.

### 2-3. topic — 패턴 매칭

라우팅 키를 **점(`.`)으로 끊은 단어열**로 보고 패턴을 맞춘다. 와일드카드는 둘이다.

- `*` : **정확히 한 단어**를 대체한다
- `#` : **0개 이상의 단어**를 대체한다

```
라우팅 키: "order.kr.payment.failed"   (단어 4개)

패턴 "order.#"                  --> 일치 (# 가 뒤 3단어를 덮는다)
패턴 "order.*.payment.failed"   --> 일치 (* 가 kr 하나를 덮는다)
패턴 "#.failed"                 --> 일치
패턴 "order.*"                  --> 불일치 (* 는 한 단어뿐, kr.payment.failed 를 못 덮는다)
패턴 "order.us.#"               --> 불일치
패턴 "#"                        --> 일치 (모든 메시지. fanout과 동일한 효과)
```

`*`와 `#`의 차이가 실무에서 가장 자주 무는 지점이다. `order.*`가 `order.kr.created`를 못 잡는다는 사실을 모르고 바인딩을 걸면, 3-4에서 볼 "일부 이벤트만 조용히 안 오는" 장애가 된다.

topic이 강력한 이유는 **라우팅 키를 계층으로 설계하면 소비자가 자기 관심 범위를 스스로 정할 수 있기 때문**이다.

```
라우팅 키 규약:  <도메인>.<국가>.<대상>.<사건>

알림 서비스   : "order.*.payment.*"        (모든 국가의 결제 이벤트 전부)
한국 정산     : "order.kr.payment.done"    (한국 결제 완료만)
글로벌 모니터 : "order.#"                   (주문 도메인 전부)
```

여기서 소비자가 하나 늘어도 **프로듀서는 아무것도 모른다.** 새 큐를 만들고 원하는 패턴으로 바인딩하면 끝이다. 이것이 "브로커가 똑똑하다"의 실질적 이득이다.

### 2-4. headers — 키·값 조합 매칭

라우팅 키 대신 **메시지 헤더의 키·값 조합**으로 매칭한다. 바인딩에 `x-match` 인자를 주어 `all`(모든 조건 일치, AND)인지 `any`(하나라도 일치, OR)인지 정한다.

```
메시지 헤더: { "type": "payment", "region": "kr", "priority": "high" }

바인딩 { x-match: all, type: payment, region: kr }   --> 일치 (둘 다 맞음)
바인딩 { x-match: all, type: payment, region: us }   --> 불일치
바인딩 { x-match: any, region: us,    priority: high } --> 일치 (priority 하나 맞음)
```

topic으로 표현하기 어려운 **직교하는 조건들의 조합**을 다룰 때 쓴다. 라우팅 키는 문자열 하나라서 차원이 늘어나면 순서를 정해야 하는데(국가가 먼저냐 대상이 먼저냐), 헤더는 순서가 없으므로 그 고민이 사라진다.

그럼에도 실무에서 headers를 보기 드문 이유는 셋이다. **문자열 하나를 비교하는 것보다 맵을 비교하는 쪽이 느리고**, 관리 콘솔이나 CLI로 바인딩을 눈으로 확인하기 불편하며, 대부분의 도메인은 계층으로 정리하면 topic으로 충분하기 때문이다. **"topic으로 표현하려니 라우팅 키 순서를 정할 수 없다"는 실제 문제를 겪은 뒤에** 도입하는 것이 맞다.

### 2-5. 선택 기준 정리

| 상황 | 선택 |
|---|---|
| 고정된 소수의 작업 유형, 늘어날 일 없음 | direct |
| 모두가 전부 받는 방송 (캐시 무효화 등) | fanout, 또는 topic + `#` |
| 소비자마다 관심 범위가 다르고 앞으로 늘어남 | **topic (기본 선택)** |
| 순서 없는 조건들의 AND/OR 조합이 필요 | headers |

면접에서 이 표를 그대로 읊는 것보다, **"저는 특별한 이유가 없으면 topic으로 시작합니다. 나중에 필터가 필요해졌을 때 프로듀서를 안 고쳐도 되기 때문입니다"**라고 판단 근거를 먼저 말하는 편이 낫다.

## 3. "여러 서비스가 각자 받는" 설계 — 이 질문의 진짜 승부처

2절에서 본 exchange 타입은 이 요구의 절반만 답한다. 나머지 절반은 **큐를 몇 개 두느냐**와 **각 큐를 어떤 바인딩 키로 매다느냐**다. 이 둘이 어긋나면 exchange 타입을 아무리 잘 골라도 메시지는 엉뚱한 곳으로 가거나 아무 데도 가지 않는다.

그래서 이 절은 네 걸음으로 간다. 큐를 잘못 나눴을 때 벌어지는 일(3-1), 같은 문제를 Kafka는 어떻게 푸는지(3-2), 그 큐와 바인딩을 누가 소유하고 선언하는지(3-3), 그리고 **큐는 제대로 나눴는데 바인딩 키를 잘못 잡아 이벤트가 통째로 사라진 실제 사고(3-4)**다. 마지막 것이 이 절에 붙는 이유는 분명하다 — 큐를 서비스마다 정확히 나눠도, 그 큐에 매단 패턴이 메시지를 못 잡으면 결과는 "큐를 안 만든 것"과 똑같기 때문이다.

### 3-1. 흔한 사고 — 큐 하나를 두 서비스가 나눠 먹기

이 질문에서 가장 많이 나오는 오답이 **"fanout exchange를 쓰면 됩니다"**로 끝나는 것이다. 절반만 맞다. 결정적인 부분은 exchange 타입이 아니라 **큐를 몇 개 두느냐**다.

알림 서비스와 정산 서비스가 같은 이벤트를 받아야 하는데, 큐를 하나만 두고 둘 다 그 큐에 붙였다고 하자.

```
                              +--> [알림 서비스]  메시지 1, 3, 5 ...
[exchange] --> [공용 큐] ---> |
                              +--> [정산 서비스]  메시지 2, 4, 6 ...
```

큐 하나에 붙은 컨슈머들은 **경쟁 소비자**가 되어 메시지를 나눠 갖는다. 그 결과 **알림은 절반만 가고 정산도 절반만 된다.** 게다가 두 서비스가 서로 다른 메시지를 처리하므로 로그만 봐서는 "가끔 알림이 안 간다"로 보이고, 원인을 찾기가 대단히 어렵다.

정답은 **서비스마다 자기 큐를 갖는 것**이다.

```
                +--(바인딩)--> [알림 큐]   --> [알림 서비스 인스턴스 1..N]
[topic exchange]|
                +--(바인딩)--> [정산 큐]   --> [정산 서비스 인스턴스 1..N]
```

이제 두 큐에 각각 한 통씩 들어가므로 두 서비스가 모든 이벤트를 받는다. 그리고 각 큐 안에서는 **같은 서비스의 인스턴스들끼리** 경쟁 소비자가 되어 처리량을 나눠 갖는다.

정리하면 규칙은 이렇다.

- **큐 하나 = 논리적 소비자 하나(= 하나의 서비스/역할).** 그 큐에 붙는 여러 프로세스는 같은 역할의 복제본이다.
- **다른 역할이면 큐를 나눈다.** 같은 큐를 공유하는 순간 메시지가 쪼개진다.

### 3-2. Kafka의 컨슈머 그룹과 대응시키기

이 구조는 Kafka의 컨슈머 그룹과 정확히 같은 문제를 다른 방식으로 푼 것이다. 대응이 명확해서 면접에서 말하기 좋다.

| 목적 | Kafka | RabbitMQ |
|---|---|---|
| 같은 역할끼리 나눠 처리 | 같은 `group.id` | 같은 큐에 여러 컨슈머 |
| 다른 역할이 각자 전부 받기 | 다른 `group.id` | **큐를 따로 만들고 각자 바인딩** |
| 소비자 추가 비용 | 그룹 하나 추가 (저장량 불변) | 큐 추가 (저장량 증가) |

마지막 행이 중요한 차이다. Kafka는 그룹을 하나 더 만들어도 데이터가 한 벌 그대로지만, RabbitMQ는 큐가 늘면 **브로커에 실제로 메시지가 한 벌 더 쌓인다.** 소비자가 10개면 적체도 10배다. 그래서 RabbitMQ에서 소비자를 늘릴 때는 브로커 용량을 함께 계산해야 한다.

### 3-3. 큐 선언은 소비하는 쪽이 한다

한 가지 더. **큐와 바인딩은 소비하는 서비스가 자기 기동 시점에 선언하는 것이 원칙**이다.

프로듀서 쪽 코드나 인프라 저장소에 모든 소비자의 큐를 모아두면, 소비자가 추가될 때마다 남의 저장소에 PR을 보내야 한다. 그 순간 "프로듀서를 안 건드려도 된다"는 이점이 사라진다.

```java
// 정산 서비스 안에 두는 선언 — 이 서비스만 알면 되는 정보다
@Configuration
class SettlementQueueConfig {

    // exchange는 이미 있다고 가정하고 durable=true로 "선언"만 한다.
    // 같은 속성으로 선언하면 멱등하게 통과하므로, 소비자가 exchange를
    // 먼저 기동해도 문제가 없다.
    @Bean TopicExchange orderEvents() {
        return ExchangeBuilder.topicExchange("order.events").durable(true).build();
    }

    @Bean Queue settlementQueue() {
        return QueueBuilder.durable("settlement.payment-done")
                .deadLetterExchange("settlement.dlx")
                .build();
    }

    @Bean Binding settlementBinding() {
        // 이 서비스가 무엇에 관심 있는지를 이 한 줄이 선언한다
        return BindingBuilder.bind(settlementQueue())
                .to(orderEvents())
                .with("order.*.payment.done");
    }
}
```

주의할 점이 하나 있다. **이미 존재하는 큐/exchange를 다른 속성으로 선언하면 채널이 예외와 함께 닫힌다.** 예를 들어 누군가 콘솔에서 `durable=false`로 만들어둔 큐를 코드가 `durable=true`로 선언하면 기동이 실패한다. 이런 사고를 막으려면 **큐 정의를 콘솔에서 손으로 만들지 않는 규율**이 필요하다.

### 3-4. 실무 사례 — `*` 하나 때문에 국가별 이벤트가 사라진 건

앞의 세 항목은 "큐를 나누고 각자 바인딩하면 된다"까지를 말했다. 그런데 그 바인딩 키는 라우팅 키 규약에 얹혀 있고, **규약이 바뀌면 멀쩡하던 바인딩이 한순간에 아무것도 못 잡는 상태가 된다.** 다음이 그 일이 실제로 벌어진 건이다.

#### 상황

글로벌 서비스에서 라우팅 키 규약을 `order.<사건>` 에서 `order.<국가>.<사건>` 으로 확장했다. 국가별 처리가 필요해졌기 때문이다.

프로듀서는 규약대로 바꿔 배포했다.

```java
// 이전: "order.created"
// 이후: "order.kr.created", "order.us.created", ...
rabbitTemplate.convertAndSend("order.events", "order." + country + ".created", event);
```

알림 서비스의 바인딩은 `order.*` 였다. 이전 규약에서는 `order.created`를 정확히 잡았다. 그런데 배포 이후 알림이 한 건도 가지 않았다.

#### 원인

`*`는 **정확히 한 단어**다. `order.*`는 `order.created`(2단어)를 잡지만 `order.kr.created`(3단어)는 잡지 못한다. 단어가 하나 늘어난 순간 모든 바인딩이 무효가 된 것이다.

그리고 이 실패는 `10-rabbitmq-core-components.md`에서 본 대로 **조용하다.** 매칭되는 큐가 0개가 되었으므로 브로커는 메시지를 그냥 버렸고, 프로듀서는 정상 발행 로그를 남겼다. 큐도 컨슈머도 정상이고 에러 로그도 없는데 알림만 안 가는 상태 — 3-1의 "절반만 처리되는" 사고보다 오히려 찾기 어렵다.

#### 교훈

**라우팅 키의 단어 수를 바꾸는 것은 스키마 변경이다.** 필드를 추가하는 것과 같은 무게로 다뤄야 한다.

- 계층을 추가할 계획이 조금이라도 있으면 **바인딩을 처음부터 `#`로 여유 있게 잡는다.** `order.#`는 단어가 몇 개로 늘어도 계속 잡는다.
- 규약을 바꿀 때는 **프로듀서가 한동안 양쪽 라우팅 키로 모두 발행**하게 하고(이중 발행), 소비자 바인딩이 전부 이전된 것을 확인한 뒤 옛 발행을 제거한다. 이벤트 스키마 진화에서 쓰는 것과 같은 전개 순서다.
- alternate exchange + unroutable 큐를 깔아두었다면 **배포 직후 그 큐가 차오르는 것으로 즉시 알아챌 수 있었다.** 라우팅 규약을 바꾸는 배포일수록 이 안전망의 값이 크다.

## 4. 꼬리질문 대비 포인트

### "topic exchange는 direct보다 느리지 않나요?"

패턴 매칭이므로 완전 일치보다 계산이 더 든다. 다만 RabbitMQ는 topic 바인딩을 트라이(trie, 단어 단위로 갈라지는 트리) 구조로 색인해 매칭하므로, 바인딩이 많아져도 선형 탐색처럼 느려지지는 않는다.

실무에서 라우팅 방식이 병목이 되는 경우는 거의 없다. **병목은 거의 항상 디스크 I/O(persistent 메시지 기록), 네트워크, 또는 컨슈머의 처리 속도**에서 나온다. "혹시 느릴까 봐 direct를 쓴다"는 성능 근거 없는 조기 최적화이며, 그 대가로 확장성을 잃는다.

### "exchange를 exchange에 바인딩할 수도 있나요?"

가능하다. exchange-to-exchange 바인딩이라고 하며, 큐에 바인딩하듯 exchange를 다른 exchange에 묶는다.

쓸모가 분명한 경우가 있다. **팀별로 exchange를 두고 상위에 회사 공통 exchange를 두는 구조**를 만들면, 각 팀은 자기 exchange만 알면 되고 전사 감사 로그 수집기는 상위 exchange에 한 번만 붙으면 된다.

다만 단계가 늘수록 **"이 메시지가 왜 여기 왔지"를 추적하기 어려워진다.** 라우팅 경로가 눈에 안 보이는 구조는 장애 시 비용이 크므로, 2단계를 넘기지 않는 선에서 쓰는 것이 좋다. **"쓸 수는 있지만 추적 비용 때문에 깊이를 제한한다"까지 말하면 기능을 아는 것을 넘어 운영을 고려한 답이 된다.** (가산점 포인트)

### "라우팅을 브로커에 두면 브로커가 SPOF(단일 장애점)가 되지 않나요?" (시니어 변별 포인트)

라우팅 규칙을 브로커에 두는 것과 브로커가 SPOF인 것은 별개다. 브로커는 라우팅을 안 해도 이미 경로 위에 있다.

진짜 지적할 만한 대가는 **설정이 코드 저장소 밖에 존재하게 된다**는 점이다. 바인딩을 콘솔에서 손으로 만들면 어디에도 이력이 남지 않고, 클러스터를 재구축하면 사라지며, 스테이징과 운영이 조용히 달라진다. 이것이 실제로 사고를 만드는 지점이다.

그래서 대응은 **선언을 코드로 두는 것**이다. 애플리케이션 기동 시 큐·바인딩을 선언하게 하거나, `definitions.json`을 형상 관리하고 배포 파이프라인에서 적용한다. **"브로커에 로직을 두되, 그 로직의 정의는 코드로 관리한다"**가 정답이다.

### "라우팅 키에 담을 수 없는 조건(금액, 사용자 등급)으로 분기하려면요?"

세 가지 길이 있고 각각 대가가 다르다.

**첫째, 프로듀서가 그 판단을 라우팅 키로 끌어올린다.** `order.kr.high-value.created` 처럼. 브로커가 걸러주므로 가장 효율적이지만, **판단 기준(10만 원)이 프로듀서에 박힌다.** 기준이 바뀌면 프로듀서를 배포해야 한다.

**둘째, 헤더로 올리고 headers exchange를 쓴다.** 라우팅 키 문자열 설계를 건드리지 않아도 되지만 여전히 프로듀서가 값을 넣어야 한다.

**셋째, 컨슈머가 받아서 거른다.** 가장 유연하고(기준 변경이 컨슈머 배포로 끝난다) 프로듀서가 소비자를 전혀 모른다. 대신 필요 없는 메시지까지 전송·역직렬화한다.

기준은 **"거르고 나면 얼마나 남는가"**다. 100건 중 1건만 필요한데 컨슈머가 거르면 99%가 낭비다 — 이때는 라우팅으로 올린다. 100건 중 80건이 필요하면 컨슈머에서 거르는 편이 낫다. 그리고 **분기 기준이 자주 바뀌는 비즈니스 규칙이면 컨슈머 쪽에 두는 것**이 배포 단위를 작게 유지한다.

### "이벤트마다 exchange를 따로 만드는 것과 하나의 exchange에 라우팅 키로 구분하는 것 중 무엇이 낫나요?"

**도메인 단위로 exchange 하나, 이벤트 종류는 라우팅 키로 구분**하는 것이 기본이다.

exchange를 이벤트마다 만들면 소비자가 여러 이벤트를 받고 싶을 때 바인딩을 exchange 개수만큼 걸어야 하고, `order.#` 같은 "도메인 전체 구독"을 표현할 수 없다. 무엇보다 **새 이벤트 종류가 생길 때마다 새 exchange를 만들어야 하므로** 프로듀서 설정과 소비자 설정이 동시에 바뀐다.

exchange를 나누는 것이 맞는 경우는 **격리 경계가 다를 때**다. 팀이 다르고 권한을 분리해야 하거나, 트래픽 특성이 극단적으로 달라(초당 수만 건의 로그성 이벤트 vs 하루 수백 건의 결제 이벤트) 서로 영향을 주지 않아야 할 때는 나눈다. 이때도 기준은 이벤트 종류가 아니라 **운영 경계**다.

---

## 한 줄 요약

exchange 타입은 라우팅 키를 대조하는 네 가지 방식일 뿐이고, 실무 기본값은 **나중에 필터를 좁힐 여지를 남기는 topic**이다. 그리고 "여러 서비스가 각자 받는" 요구는 exchange 타입이 아니라 **서비스마다 큐를 따로 두는 것**으로 푼다 — 큐를 공유하는 순간 두 서비스가 메시지를 절반씩 나눠 먹는다.
