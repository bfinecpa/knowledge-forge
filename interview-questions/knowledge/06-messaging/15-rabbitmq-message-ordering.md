# RabbitMQ의 순서 보장 — "큐는 FIFO"가 실제로 성립하는 조건과 그것을 깨는 것들

> 핵심 관전 포인트: **"큐니까 FIFO"는 아주 좁은 조건에서만 참이다. 정확히는 큐 하나, 컨슈머 하나, prefetch 1, requeue 없음, 우선순위 없음일 때만 발행 순서 = 처리 순서가 성립한다. 이 중 하나만 어겨도 순서가 흔들린다 — 컨슈머를 2대로 늘리는 순간 처리 완료 순서가 뒤섞이고, 실패한 메시지를 requeue하면 그 메시지는 이미 다른 컨슈머가 처리 중인 뒤 메시지보다 늦어지며, prefetch를 키우면 컨슈머 손안에서 순서가 재배열된다. 그리고 발행 쪽에도 조건이 있다 — 순서 보장은 같은 채널로 발행한 메시지들 사이에서만 성립한다. 실무 해법은 순서를 지키려 애쓰는 쪽(Single Active Consumer, consistent hash exchange로 키별 큐 분리)과 순서에 의존하지 않게 만드는 쪽(이벤트에 버전을 넣고 오래된 것은 무시)으로 갈리며, 후자가 압도적으로 견고하다. Kafka의 파티션 키 순서 보장도 정확히 같은 대가를 치른다.**

---

## 0. 질문 + 의도

**질문**: "RabbitMQ에서 메시지 순서는 어디까지 보장되나요? 무엇이 순서를 깨뜨리나요? (Kafka의 파티션 단위 순서와 비교)"

**출제 의도**: "큐는 FIFO니까 순서가 지켜진다"는 오해를 깨는 문항이다. 재큐잉·다중 컨슈머·prefetch·우선순위가 각각 어떻게 순서를 흔드는지 짚는지로, 보장의 전제 조건까지 읽는 습관을 본다. 그리고 순서를 지키는 비용을 알고, 순서에 의존하지 않는 설계를 대안으로 제시할 수 있는지가 변별점이다.

## 1. 전제 — "순서"가 무엇을 뜻하는지부터 나눈다

### 1-1. 세 개의 다른 순서

순서 이야기가 엉키는 이유는 **서로 다른 세 지점의 순서를 하나로 뭉뚱그리기 때문**이다.

```
① 발행 순서    프로듀서가 send()를 호출한 순서
② 큐 안의 순서  브로커의 큐에 줄 서 있는 순서
③ 처리 순서    컨슈머가 실제로 비즈니스 로직을 끝낸 순서
```

RabbitMQ가 구조적으로 보장하는 것은 **②까지**다. 한 채널에서 발행한 메시지들은 큐에 발행 순서대로 들어간다.

우리가 실제로 원하는 것은 **③**이다. "결제 완료가 결제 취소보다 먼저 처리되어야 한다"는 요구는 처리 순서에 대한 것이다.

그리고 **②에서 ③으로 넘어가는 구간에 보장이 없다.** 이 구간에서 순서가 깨지는 방식이 이 문서의 본론이다.

### 1-2. 발행 쪽에도 조건이 있다

②조차 무조건은 아니다. **순서는 같은 채널 안에서만 보장된다.**

```
스레드 A (채널 1): send(주문생성) --> 큐
스레드 B (채널 2): send(주문취소) --> 큐
   두 채널의 상대적 도착 순서는 정해져 있지 않다.
   취소가 생성보다 먼저 큐에 들어갈 수 있다.
```

Spring AMQP의 `RabbitTemplate`은 내부적으로 채널을 캐시해 재사용하므로, **서로 다른 스레드에서 발행하면 서로 다른 채널을 쓸 수 있다.** 즉 애플리케이션이 멀티스레드로 발행하는 순간 발행 순서 자체가 보장되지 않는다.

이 사실이 중요한 이유는, **순서가 깨졌을 때 컨슈머만 의심하다 시간을 버리기 때문**이다. 조사 순서는 항상 "발행 쪽에서 이미 뒤집혔는가"부터다.

## 2. 순서를 깨뜨리는 다섯 가지

### 2-1. 컨슈머가 여럿 (가장 흔한 원인)

큐 하나에 컨슈머 여러 대를 붙이면 메시지는 나눠서 배달된다. 배달 자체는 큐 순서대로지만, **각 컨슈머의 처리 시간이 다르므로 완료 순서가 뒤섞인다.**

```
큐:  [1][2][3]

워커1 <- 1  (처리 500ms)
워커2 <- 2  (처리 10ms)   -> 2가 먼저 끝난다
워커3 <- 3  (처리 10ms)   -> 3이 그 다음

실제 처리 완료 순서: 2, 3, 1
```

주문 생성(1) → 주문 수정(2) → 주문 취소(3)였다면, 수정과 취소가 생성보다 먼저 처리되어 "존재하지 않는 주문을 수정" 오류가 난다.

**이것은 버그가 아니라 경쟁 소비자 패턴의 정의 그 자체다.** 처리량을 위해 병렬화한 이상 순서는 포기한 것이다.

### 2-2. requeue — 되돌린 메시지의 위치

`basic.nack(requeue=true)`로 되돌린 메시지는 **큐의 원래 자리 근처로 돌아간다**(맨 뒤가 아니다). 그런데 그 사이 뒤쪽 메시지들은 이미 다른 컨슈머에게 배달되어 처리 중이다.

```
시각 t0:  큐 [1][2][3],  워커1 <- 1,  워커2 <- 2
시각 t1:  워커1이 1 실패 -> requeue.  워커2는 2를 처리 중
시각 t2:  워커1 <- 1 (재배달).  워커2는 이미 2를 끝냄
결과:     2가 1보다 먼저 처리됨
```

**재시도가 순서를 깨는 것은 피할 수 없다.** 지연 재시도(TTL 대기 큐)를 쓰면 더 크게 벌어진다 — 5초 뒤에 돌아오므로 그 사이 수백 건이 앞질러 간다.

### 2-3. prefetch — 컨슈머 손안에서의 재배열

prefetch를 크게 잡으면 컨슈머가 여러 건을 미리 받아둔다. 컨슈머가 이것을 **여러 스레드로 나눠 처리하면** 그 안에서 순서가 뒤집힌다.

단일 스레드로 순차 처리한다면 컨슈머 손안에서는 순서가 유지된다. 하지만 **실패가 섞이는 순간** 이야기가 달라진다. 3번을 requeue했는데 4~10번을 이미 손에 쥐고 있으므로, 그것들을 먼저 처리한 뒤에야 3번이 재배달된다.

### 2-4. 우선순위 큐

`x-max-priority`를 설정한 큐는 **우선순위가 높은 메시지를 먼저 내보낸다.** 순서를 의도적으로 뒤집는 기능이므로 당연히 FIFO가 아니다.

주의할 점은 **이미 컨슈머에게 전달된(unacked) 메시지에는 소급 적용되지 않는다**는 것이다. prefetch가 크면 낮은 우선순위 메시지 100건이 이미 컨슈머 손에 가 있고, 그 뒤에 도착한 긴급 메시지는 그것들이 다 처리된 뒤에야 간다. **우선순위 큐를 쓰려면 prefetch를 작게 잡아야 의미가 있다.** (가산점 포인트)

### 2-5. 여러 큐로 갈라진 경우

fanout이나 topic으로 한 이벤트가 여러 큐에 들어가면, **큐마다 소비 속도가 달라 서비스 간 처리 시점이 어긋난다.** 각 큐 안의 순서는 지켜져도 시스템 전체로 보면 "알림은 이미 갔는데 정산은 아직"인 상태가 생긴다.

이건 순서 문제라기보다 **최종 일관성** 문제지만, 장애 리포트에는 "순서가 이상하다"로 들어온다. 원인 분류를 정확히 하는 것이 대응의 출발점이다.

### 2-6. 정리 — 순서가 성립하는 조건

거꾸로 뒤집으면 조건이 명확해진다.

| 조건 | 어기면 |
|---|---|
| 같은 채널에서 발행 | 발행 순서부터 뒤집힘 |
| 큐 하나 | 큐 간 진도 차이 |
| 컨슈머 하나 | 완료 순서 뒤섞임 |
| prefetch = 1 | 실패 시 재배열 |
| 재시도 없음(또는 블로킹 재시도) | 재시도한 건이 뒤로 밀림 |
| 우선순위 미사용 | 의도적 역전 |

**이 조건을 다 만족시키면 처리량은 컨슈머 한 대의 단일 스레드 성능으로 고정된다.** 순서 보장의 진짜 비용이 이것이다.

## 3. 순서가 필요할 때의 세 가지 해법

### 3-1. 해법 A — Single Active Consumer

큐에 `x-single-active-consumer`를 설정하면, **컨슈머가 여러 대 붙어 있어도 한 번에 한 대에게만 메시지를 준다.** 나머지는 대기하다가 활성 컨슈머가 죽으면 그중 하나가 승계한다.

```java
@Bean Queue orderQueue() {
    return QueueBuilder.durable("order.sequence")
            .singleActiveConsumer()   // 한 번에 한 컨슈머만 활성
            .build();
}
```

이것이 주는 것은 **순서 + 가용성**이다. 컨슈머를 여러 대 띄워두되(장애 시 자동 승계) 실제 소비는 한 대만 한다. "인스턴스를 하나만 띄운다"는 순진한 방법과 달리, 그 하나가 죽어도 서비스가 멈추지 않는다.

주는 만큼 잃는 것도 명확하다. **처리량이 컨슈머 한 대로 고정된다.** 워커를 100대 띄워도 99대는 논다.

### 3-2. 해법 B — 키별로 큐를 나눈다 (Kafka의 파티션과 같은 발상)

전체 순서가 필요한 경우는 드물다. 대부분 필요한 것은 **"같은 주문 안에서의 순서"**다. 서로 다른 주문끼리는 뒤섞여도 상관없다.

그렇다면 **주문 ID로 갈라 각 그룹은 한 컨슈머가 순서대로 처리**하면 된다. 이것이 정확히 Kafka의 파티션 키가 하는 일이다.

RabbitMQ에서는 `rabbitmq_consistent_hash_exchange` 플러그인으로 구현한다. 라우팅 키(또는 헤더)를 해시해 **여러 큐 중 하나로 결정적으로 배분**하는 exchange다.

```
                        해시(주문ID) % 큐 수
[consistent hash exchange] --> [큐 0] --> 워커 A  (주문 1, 4, 7 ...)
                           --> [큐 1] --> 워커 B  (주문 2, 5, 8 ...)
                           --> [큐 2] --> 워커 C  (주문 3, 6, 9 ...)

같은 주문 ID는 항상 같은 큐로 -> 그 큐 안에서 순서 유지
서로 다른 주문은 병렬 처리 -> 처리량 확보
```

Kafka와 대응이 정확해서 면접에서 말하기 좋다.

| | Kafka | RabbitMQ |
|---|---|---|
| 순서 단위 | 파티션 | 큐 |
| 배분 방법 | 파티션 키 해시 | consistent hash exchange |
| 병렬성 상한 | 파티션 수 | 큐 수 |
| 키 편중 시 | 특정 파티션 병목 | 특정 큐 병목 |
| 단위 수 변경 | 어렵다 (키 재배치로 순서 붕괴) | 어렵다 (같은 이유) |

**대가도 같다.** 특정 키에 트래픽이 몰리면(대형 가맹점 하나가 전체의 30%) 그 큐만 밀리고, 큐 수를 나중에 바꾸면 해시 결과가 달라져 **같은 키가 다른 큐로 가면서 순서가 깨진다.** Kafka에서 파티션을 늘릴 때 겪는 문제와 동일하다.

### 3-3. 해법 C — 순서에 의존하지 않게 만든다 (가장 견고함)

앞의 둘은 순서를 지키기 위해 처리량이나 운영 복잡도를 낸다. 세 번째 길은 **순서가 뒤집혀도 결과가 옳도록 만드는 것**이다.

핵심은 **이벤트에 버전(또는 논리적 시각)을 넣고, 소비자가 자기가 이미 반영한 버전과 비교하는 것**이다.

```java
// 잘못된 코드 — 도착 순서를 그대로 믿는다
public void handle(OrderStatusChanged event) {
    Order order = orderRepository.findById(event.getOrderId()).orElseThrow();
    order.setStatus(event.getStatus());  // 오래된 이벤트가 늦게 오면 상태가 되돌아간다
    orderRepository.save(order);
}

// 올바른 코드 — 더 오래된 이벤트는 무시한다
public void handle(OrderStatusChanged event) {
    Order order = orderRepository.findById(event.getOrderId()).orElseThrow();
    if (event.getVersion() <= order.getAppliedVersion()) {
        // 이미 더 최신 상태를 반영했다. 이 이벤트는 늦게 도착한 과거다
        log.debug("오래된 이벤트 무시: orderId={}, eventVer={}, appliedVer={}",
                  event.getOrderId(), event.getVersion(), order.getAppliedVersion());
        return;
    }
    order.setStatus(event.getStatus());
    order.setAppliedVersion(event.getVersion());  // 반영한 버전을 기록
    orderRepository.save(order);
}
```

이 방식이 강력한 이유는 **순서가 깨지는 모든 경로를 한 번에 막기 때문**이다. 컨슈머가 몇 대든, 재시도가 몇 번이든, 네트워크가 어떻게 흔들리든 결과가 같다. 브로커 설정에 의존하지 않으므로 RabbitMQ에서 Kafka로 옮겨도 그대로 동작한다.

**"순서를 보장받는 것"과 "순서에 무관하게 만드는 것" 중 후자를 먼저 검토하는 것이 분산 시스템 설계의 기본기**이며, 면접에서 이 순서로 말하면 강하다.

버전을 만들 방법이 마땅치 않은 경우도 대안이 있다.

- **상태 전이 규칙으로 막는다.** `CANCELLED` 상태에서 `PAID`로 가는 전이를 도메인 규칙으로 금지하면, 순서가 뒤집혀 늦게 온 결제 완료 이벤트가 자연스럽게 무시된다.
- **thin event로 바꾼다.** 이벤트에 ID만 담고 컨슈머가 현재 상태를 조회하면, 어떤 순서로 처리해도 최종 상태가 같아진다. 대신 조회 부하와 시점 불일치가 생긴다.

## 4. 실무 사례 — "취소된 주문이 다시 결제 완료로 바뀝니다"

### 4-1. 증상

주문 취소 후 몇 초 지나 상태가 `PAID`로 되돌아가는 건이 하루 몇 건씩 발생했다. 재현이 안 되고 로그상 오류도 없다.

### 4-2. 추적

이벤트 두 건의 처리 시각을 대조한 것이 실마리였다.

```
14:02:31.100  order.paid      발행
14:02:31.850  order.cancelled 발행
14:02:31.870  order.cancelled 처리 완료  <- 먼저 끝났다
14:02:32.400  order.paid      처리 완료  <- 나중에 끝나며 상태를 덮어씀
```

원인은 둘이 겹친 것이었다.

- 컨슈머가 4대였다. `paid`와 `cancelled`가 서로 다른 워커에게 갔다.
- `paid` 처리에는 외부 PG 조회가 있어 수백 ms가 걸렸고, `cancelled`는 DB 갱신뿐이라 빨랐다.

즉 **처리 시간 차이가 발행 간격(750ms)보다 컸다.** 순서가 뒤집힐 조건이 갖춰져 있었고, 트래픽이 몰릴 때만 재현되니 평소엔 안 보였다.

### 4-3. 대응

단기 대응으로 컨슈머를 1대로 줄이는 안이 나왔지만 처리량이 부족해 불가능했다. 최종적으로는 **해법 C**를 택했다.

- 이벤트에 `sequence`(주문 단위로 증가하는 번호)를 추가했다.
- 주문 테이블에 `applied_sequence` 컬럼을 두고, 이벤트 처리 시 비교해 오래된 것은 무시했다.
- 무시된 건수를 지표로 남겨 **순서 역전이 얼마나 자주 일어나는지** 관측 가능하게 만들었다.

이 지표가 뜻밖에 유용했다. 배포 직후나 다운스트림이 느려질 때 역전 건수가 튀는 것이 보였고, **성능 저하의 선행 지표** 역할을 했다.

**"순서를 지키게 만드는 것"이 아니라 "순서가 깨져도 안전하게 만들고, 깨진 횟수를 관측한다"**가 이 사례의 교훈이다.

## 5. 꼬리질문 대비 포인트

### "컨슈머를 1대로 줄이면 순서가 보장되나요?"

거의 보장되지만 완전하지는 않다. 남는 구멍이 셋이다.

**첫째, 발행 쪽.** 프로듀서가 멀티스레드로 발행하면 큐에 들어가는 순서부터 뒤집힌다.

**둘째, 재시도.** 실패한 건을 지연 재시도로 빼면 그 건이 뒤로 밀린다. 순서를 지키려면 **그 자리에서 성공할 때까지 막고 있어야**(블로킹 재시도) 하는데, 그러면 poison 메시지 하나가 큐 전체를 막는다.

**셋째, 컨슈머 내부 병렬화.** 리스너가 메시지를 받아 스레드 풀에 던지면 컨슈머가 1대여도 순서가 깨진다.

그리고 무엇보다 **컨슈머 1대는 가용성이 없다.** 그래서 실무에서는 컨슈머를 여러 대 띄우되 Single Active Consumer로 하나만 활성화하는 방식을 쓴다.

### "Kafka는 파티션 안에서 순서가 보장된다는데, RabbitMQ보다 유리한 것 아닌가요?"

보장의 층위가 다를 뿐 실질은 비슷하다.

Kafka가 보장하는 것은 **파티션 안의 저장 순서와 배달 순서**다. RabbitMQ의 "큐 안의 순서"와 같은 수준이다. 그리고 **처리 순서**는 Kafka도 보장하지 않는다 — 컨슈머가 poll한 레코드를 스레드 풀로 넘기면 똑같이 뒤섞인다.

차이가 있다면 **Kafka는 파티션 단위 순서를 유지하면서 병렬화하는 구조가 기본 내장**이라는 점이다. RabbitMQ에서 같은 것을 하려면 consistent hash exchange 플러그인이 필요하다.

반대로 RabbitMQ가 유리한 지점도 있다. **실패한 한 건을 떼어내도 뒤가 안 막힌다.** Kafka에서 순서를 지키려면 실패한 건에서 멈춰야 하고, 안 멈추려면 재시도 토픽으로 빼야 하는데 그 순간 순서가 깨진다. 결국 **"순서와 흐름 중 하나를 포기해야 한다"는 딜레마는 양쪽 모두 동일**하다.

### "그럼 순서 보장은 아예 포기하는 게 맞나요?" (시니어 변별 포인트)

포기가 아니라 **요구를 정확히 좁히는 것**이 맞다. 질문을 이 순서로 던진다.

1. **정말 순서가 필요한가, 아니면 최종 상태만 맞으면 되는가?** 대부분은 후자다. 그렇다면 버전 기반 무시로 끝난다.
2. **전체 순서인가, 특정 키 안의 순서인가?** 거의 항상 후자다. 그렇다면 키별 큐 분리로 병렬성을 유지한 채 해결된다.
3. **그 키의 트래픽이 한 컨슈머로 감당되는가?** 안 되면 순서 요구 자체를 재검토해야 한다 — 이 지점에서는 기술이 아니라 도메인 설계 문제다.

이 세 질문을 순서대로 던지는 것 자체가 답이다. **"순서를 보장해달라"는 요구를 그대로 받아 구현하면 처리량을 잃고, 요구를 분해하면 대부분 훨씬 싼 해법이 나온다.**

### "우선순위 큐를 쓰면 급한 메시지를 먼저 처리할 수 있나요?"

가능하지만 함정이 둘이다.

**첫째, prefetch가 크면 무력화된다.** 이미 컨슈머에게 전달된 메시지에는 우선순위가 소급 적용되지 않는다. prefetch 100이면 낮은 우선순위 100건이 먼저 처리된 뒤에야 긴급 메시지가 간다. **우선순위 큐를 쓸 때는 prefetch를 작게 잡아야 한다.**

**둘째, 낮은 우선순위의 기아(starvation).** 높은 우선순위가 계속 들어오면 낮은 것은 영영 처리되지 않는다.

그래서 실무에서는 **우선순위 큐보다 큐 자체를 나누는 것**을 더 자주 쓴다. `payment.urgent`와 `payment.normal`을 만들고 워커 비율을 다르게 배치하면, 급한 것이 빨리 처리되면서도 일반 건이 굶지 않는다. 자원 배분을 눈에 보이게 만든다는 점도 장점이다.

### "메시지에 순번을 넣었는데 중간이 비어 있으면(유실 의심) 어떻게 하나요?"

**갭 감지(gap detection)**라고 부르는 기법이고, 순번을 넣은 김에 얻는 부가 이득이다.

컨슈머가 마지막으로 본 순번을 키별로 기억해두고, 다음 메시지의 순번이 +1이 아니면 갭을 기록한다. 다만 **갭이 곧 유실은 아니다.** 순서가 뒤집혀 나중에 도착할 수도 있으므로, 일정 시간(예: 5분) 기다린 뒤에도 안 오면 그때 유실로 판정한다.

여기서 중요한 판단이 있다. **갭을 발견했을 때 멈출 것인가, 계속 갈 것인가.** 순서가 절대적인 도메인(원장 기록)이라면 멈추고 알람을 올린다. 그렇지 않다면 기록만 하고 계속 처리하는 편이 낫다 — 멈추면 유실 한 건이 전체 정지로 번진다.

---

## 한 줄 요약

RabbitMQ의 FIFO는 **큐 하나·컨슈머 하나·prefetch 1·재시도 없음**이라는 좁은 조건에서만 성립하고, 그 조건을 다 지키면 처리량이 컨슈머 한 대로 고정된다 — 실무의 정답은 **키별로 큐를 갈라 순서 단위를 좁히거나(Kafka 파티션과 같은 발상), 이벤트에 버전을 넣어 순서가 뒤집혀도 결과가 옳게 만드는 것**이다.
