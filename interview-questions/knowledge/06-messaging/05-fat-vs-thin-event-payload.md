# Fat event vs Thin event — 페이로드 설계가 1년 뒤의 결합도와 장애 모드를 결정한다

> 핵심 관전 포인트: **이벤트 페이로드는 발행자의 내부 구현이 아니라 모든 컨슈머가 의존하는 공개 계약이다 — 한번 소비자들이 붙으면 사실상 비가역이라, 이 선택은 API 설계급의 무게를 가진다. fat event(전체 상태 동봉)는 소비자가 역조회 없이 자립하게 해주지만, 스키마가 전 소비자와의 결합점이 되고 개인정보가 브로커 리텐션 기간만큼 복제·전파된다. thin event(ID만)는 계약이 얇아 진화가 쉽지만, 소비자마다 발행자 API를 되부르며(조회 부하 N배) 이벤트로 끊었던 가용성 의존이 되살아나고, "조회 시점 상태 ≠ 이벤트 시점 상태"라는 시점 불일치가 생긴다. 1년 뒤 이 결정이 좌우하는 것은 세 가지 — 스키마 변경의 파급 범위, 발행자가 죽었을 때의 장애 모드, 대량 재처리(replay)가 가능한가다.**

---

## 0. 질문 + 의도

**질문**: "이벤트 페이로드에 전체 상태를 담을까(fat event), ID만 담을까(thin event)? 이 결정이 1년 뒤 시스템의 무엇을 좌우하나요?"

**출제 의도**: 비가역 설계 결정의 이벤트 설계 판. 페이로드 형태는 모든 컨슈머가 의존하는 계약이라 나중에 바꾸면 전 소비자가 흔들린다. fat은 소비자 자립(역조회 불필요) 대신 스키마 결합·개인정보 전파, thin은 느슨함 대신 조회 부하·시점 불일치 — 초기 결정 하나가 1년 뒤의 결합도와 장애 모드를 결정함을 아는지 본다.

## 1. 두 방식의 정체와 이벤트가 계약인 이유

### 1-1. 같은 사건, 두 가지 페이로드

"주문이 완료됐다"는 똑같은 사건을 두 가지 모양으로 발행할 수 있다.

```json
// thin event: "무슨 일이 있었다"는 사실과 식별자만
{
  "eventType": "OrderCompleted",
  "orderId": 1234,
  "occurredAt": "..."
}

// fat event: 소비자가 필요로 할 상태를 함께 실어 보낸다
{
  "eventType": "OrderCompleted",
  "orderId": 1234,
  "occurredAt": "...",
  "userId": 88,
  "userEmail": "a@b.com",
  "items": [ { "productId": 7, "qty": 2, "price": 12000 } ],
  "totalAmount": 24000,
  "shippingAddress": "서울시 ..."
}
```

정의를 또렷하게 하면 이렇다.

**thin event는 "무슨 일이 일어났다"는 사실과 식별자만 보내고, 상세는 소비자가 되물어보게 하는 방식이다.** 위 JSON을 받은 소비자는 "주문 1234가 완료됐다"는 것만 알고, 내용이 필요하면 주문 서비스의 조회 API를 **되불러야** 한다.

**fat event는 소비자가 필요로 할 상태를 이벤트에 함께 실어 보내는 방식이다.** 소비자는 이벤트만 읽고 자기 일을 끝낼 수 있다 — **역조회 없이 자립**한다. 소비자가 이 데이터를 자기 DB에 복제본으로 쌓아 두는 패턴의 기반이기도 하다.

### 1-2. 통지인가, 상태 전송인가

이 둘을 다른 이름으로 부르면 구분이 훨씬 선명해진다.

**thin은 통지(notification)다.** 문자 메시지로 "택배가 도착했습니다"를 받는 것과 같다. 내용을 알려면 문을 열어 봐야 한다. 통지는 "확인해 보라"는 신호일 뿐 정보 자체가 아니다.

**fat은 상태 전송(event-carried state transfer)이다.** 택배 상자를 통째로 문 앞에 놓고 가는 것이다. 열어 보면 필요한 게 다 들어 있다.

이 이름을 쓰면 트레이드오프가 자동으로 따라 나온다. 통지는 가볍고 계약이 얇지만 **받은 쪽이 확인하러 가야 한다.** 상태 전송은 받은 쪽이 편하지만 **상자 안에 무엇이 들어 있어야 하는지를 미리 합의해야 하고**, 그 합의를 바꾸기가 어렵다.

### 1-3. 이 JSON이 왜 "공개 계약"인가 — REST API와 다른 점

여기가 이 문서의 축이다. **이 JSON의 모양은 발행자가 마음대로 바꿀 수 있는 내부 구현이 아니다.**

REST API를 생각해 보자. 응답 스펙을 바꾸려면 호출자와 협의해야 한다는 것은 누구나 안다. 그런데 이벤트에는 REST API보다 **한 단계 더 나쁜 성질**이 있다.

**구독에는 발행자의 동의가 필요 없다.** 어떤 팀이 우리 토픽을 소비하고 싶으면, 자기 쪽에 컨슈머 그룹 하나를 만들어 붙이면 끝이다. 우리에게 요청하지도, 알리지도 않는다. Kafka는 그렇게 설계돼 있고, 그게 이벤트 기반 아키텍처의 장점이기도 하다 — 발행자를 건드리지 않고 소비자를 늘릴 수 있다.

그 장점의 이면이 이것이다. **발행자는 누가 구독하고 있는지 알 수 없다.**

```text
[REST API]
  누가 부르는지 알 수 있는가?  -> 액세스 로그, API 키, 게이트웨이 통계로 파악 가능
  필드를 빼면?                 -> 호출자 목록을 뽑아 공지하고 협의할 수 있다

[이벤트]
  누가 구독하는지 알 수 있는가? -> 컨슈머 그룹 목록은 조회할 수 있지만,
                                  그 그룹이 어느 필드를 파싱하는지는 알 수 없다
  필드를 빼면?                 -> 어디가 깨질지 모른다.
                                  깨진 사실도 그쪽 팀이 알려 줘야 안다
```

**호출자 목록조차 파악하기 어렵다는 것 — 이것이 이벤트 계약의 특수성이다.** 필드 하나를 빼는 순간 어느 소비자의 어느 코드가 `NullPointerException`을 내는지 발행자는 알 방법이 없고, 그 사실은 그 팀이 장애를 겪고 나서야 우리에게 도달한다.

그래서 이벤트 페이로드는 **사실상 비가역**이다. 소비자가 3팀 붙는 순간 이 스키마는 REST API 응답 스펙과 같은, 아니 그보다 더 뻣뻣한 공개 계약이 된다.

**그래서 "1년 뒤"를 묻는 것이다.** 지금은 fat이든 thin이든 잘 돌아간다. 차이가 드러나는 것은 소비자가 늘고, 스키마를 바꿔야 하고, 발행자가 장애를 겪고, 대량 재처리를 해야 하는 시점이다. 그리고 그때는 이미 바꾸기 늦다.

## 2. 1년 뒤 좌우되는 것

### 2-1. 결합도 — 무엇에 묶이는가

먼저 오해를 걷어내자. **둘 중 하나가 결합이 없는 게 아니다.** 둘 다 결합이 생긴다. **어디에 묶일지를 고르는 문제**다.

**fat은 스키마에 묶인다.** 이벤트에 담긴 모든 필드가 잠재적 의존점이다. 주문 서비스가 `shippingAddress`를 문자열에서 구조체로 바꾸고 싶어도, 그 필드를 파싱하는 소비자가 있는지 전수 조사하기 전에는 못 바꾼다. 그리고 1-3에서 봤듯 전수 조사가 어렵다.

**필드가 많을수록 결합 표면적이 넓어진다.** "혹시 몰라서 다 넣은" 필드 하나하나가 1년 뒤 변경을 막는 족쇄가 된다. 지금은 아무도 안 쓰는 필드처럼 보여도, 1년 뒤에는 어느 팀이 그걸 파싱하고 있을지 모른다.

그래서 fat을 선택하면 **스키마 거버넌스가 사실상 필수 동반 투자**가 된다. Schema Registry(스키마를 코드 밖의 중앙 저장소에 등록하고 버전을 관리하는 서비스)에 스키마를 올리고, 호환성 규칙 — 하위 호환(옛 소비자가 새 이벤트를 읽을 수 있는가), 상위 호환(새 소비자가 옛 이벤트를 읽을 수 있는가) — 을 강제해야 한다. fat은 페이로드만 두꺼운 게 아니라 **딸려 오는 인프라도 두껍다.**

**thin은 발행자의 가용성과 조회 API에 묶인다.** 스키마는 ID뿐이라 거의 안 바뀐다. 대신 **모든 소비자가 발행자의 조회 API에 런타임으로 의존한다.**

이게 왜 아픈지가 핵심이다. 애초에 이벤트로 비동기화한 이유가 무엇이었나? **"발행자가 살아 있어야 소비자가 일할 수 있다"는 동기 호출의 의존을 끊으려는 것**이었다. 그런데 thin은 그 의존을 **뒷문으로 되살린다.** 앞문(동기 호출)으로 나간 의존이 뒷문(역조회)으로 들어온다.

부하 증폭도 그냥 넘길 수 없는 크기다. 숫자로 보자.

```text
소비자가 5팀, 이벤트 1건당 각 팀이 조회 1회

  이벤트 1건       -> 발행자 조회 API 호출 5회
  초당 1,000건     -> 초당 5,000회 조회
  소비자가 10팀이 되면 -> 초당 10,000회 조회
```

검산하면 1,000 × 5 = 5,000이 맞고, 소비자가 10팀이면 1,000 × 10 = 10,000이다. **발행 트래픽은 그대로인데 조회 트래픽만 소비자 팀 수에 비례해 늘어난다.** 그리고 이 증가는 발행자가 통제할 수 없다 — 새 팀이 구독을 시작하면 발행자에게 알리지 않고도 조회 부하가 20% 늘어난다.

여기서 결합의 성격이 드러난다. **발행자가 죽으면 소비자들도 처리를 못 한다.** 조회가 실패하니 이벤트를 받아도 할 수 있는 일이 없다. 이벤트로 끊었다고 믿었던 가용성 의존이 그대로 살아 있는 것이다.

### 2-2. 장애 모드와 재처리

1년 뒤 반드시 겪게 될 세 가지 상황에서 두 방식이 어떻게 다르게 무너지는지를 본다.

**상황 1 — 발행자가 죽었을 때.**

fat 소비자는 브로커만 살아 있으면 계속 소비한다. 필요한 상태가 이벤트 안에 있으므로 발행자가 없어도 자기 일을 끝낸다.

thin 소비자는 조회가 실패하므로 같이 멈춘다. 그리고 더 나쁜 시나리오가 있다 — **재시도가 쌓였다가 발행자 복구 직후 한꺼번에 터지는 것**이다. 멈춰 있던 몇 분 동안 밀린 이벤트가 컨슈머 랙으로 쌓이고, 발행자가 살아나는 순간 모든 소비자가 밀린 만큼의 조회를 동시에 쏜다. 겨우 일어난 발행자가 조회 폭탄에 다시 쓰러진다. **"이벤트 기반으로 격리했다"고 믿었던 장애 전파 경로가 thin에서는 살아 있는 정도가 아니라 증폭기 역할을 한다.**

**상황 2 — 대량 재처리(replay)할 때.**

장애를 복구하느라 지난 이벤트 100만 건을 다시 소비해야 하는 상황이다. Kafka는 오프셋을 되돌리면 과거 이벤트를 다시 읽을 수 있으므로, 이런 복구가 가능하다는 것 자체가 이벤트 기반 아키텍처의 큰 장점이다.

fat이면 브로커에서 읽기만 하면 된다. 제약은 소비자 자신의 처리 능력뿐이다.

thin이면 **발행자 API에 100만 건의 조회가 발사된다.** 소비자가 5팀이면 500만 건이다(100만 × 5 = 500만). 게다가 재처리는 평소 속도가 아니라 최대 속도로 돈다 — 밀린 것을 따라잡으려는 것이므로. **재처리 자체가 발행자를 쓰러뜨리는 2차 장애**가 된다.

결국 "재처리는 심야에, 스로틀 걸고, 한 팀씩"이라는 운영 제약이 붙는다. 재처리 가능성이 아키텍처의 전제라면(이벤트 소싱, 소비자 DB 재구축) 이 차이는 결정적이다.

**상황 3 — 시점 불일치. thin의 조용한 버그.**

이게 가장 찾기 어려운 문제다. **thin 소비자가 조회로 얻는 것은 "이벤트가 발생한 시점의 상태"가 아니라 "조회를 실행한 시점의 최신 상태"다.** 이벤트와 조회 사이에는 시간이 흐른다.

주문이 생성됐다가 곧바로 취소된 경우를 타임라인으로 보자.

```text
t0   주문 1234 생성       DB 상태: CREATED
t0   OrderCreated(1234) 이벤트 발행
t1   사용자가 주문 취소    DB 상태: CANCELLED
t2   소비자가 OrderCreated(1234)를 수신
t2   소비자가 주문 1234를 조회  ->  돌아오는 값은 CANCELLED

  소비자가 마주하는 것:
  "생성 이벤트를 받았는데 조회하니 취소 상태"라는 모순
```

소비자 코드는 대개 이런 모순을 예상하고 짜여 있지 않다. "OrderCreated를 받으면 재고를 차감한다"는 로직이라면, 취소된 주문의 재고를 차감하거나, 상태 검증에 걸려 조용히 아무것도 안 하거나 — 어느 쪽이든 의도와 다르다.

상태가 빠르게 연달아 바뀌는 경우엔 **중간 상태가 아예 관측되지 않는다.**

```text
주문 상태가 빠르게 두 번 바뀜: 결제완료 -> 배송중

이벤트: [OrderPaid(1234)]  [OrderShipped(1234)]  가 연달아 도착
소비자: OrderPaid를 받고 조회 -> 이미 "배송중"이 읽힌다
        OrderShipped를 받고 조회 -> 또 "배송중"

-> "결제완료" 상태는 어느 조회에도 잡히지 않았다.
   "결제완료 시점에 재고를 차감"하는 로직이라면 조용히 어긋난다.
```

**대량 재처리에서는 이 문제가 특히 심각해진다.** 과거 이벤트를 재생하는데 조회는 언제나 현재 상태를 주기 때문이다.

```text
[재처리 시나리오]
  3개월 전의 OrderCreated 이벤트 100만 건을 재생

  이벤트가 말하는 것: "3개월 전 이 주문이 생성됐다"
  조회가 돌려주는 것: "오늘 이 주문의 상태"  (배송완료, 반품, 취소...)

  -> 3개월 치 이벤트를 재생했는데 결과는 전부 "오늘 상태" 기준으로 만들어진다.
     시간축이 통째로 뭉개진다.
```

즉 thin에서는 **"과거 시점의 사실을 복원하는 재처리"가 원리적으로 불가능하다.** fat은 이벤트에 그 시점의 상태가 박제되어 있으므로 이 문제가 없다. 이벤트를 다시 읽으면 그때의 세계가 그대로 돌아온다.

이 유형의 버그가 무서운 이유는 **평소에는 안 드러난다**는 점이다. 이벤트와 조회 사이 간격이 짧고 상태가 안 바뀌면 아무 문제가 없다. 이벤트가 폭주해 소비가 밀릴 때, 즉 **가장 바쁠 때만 간헐적으로** 어긋난다. 재현이 어렵고 원인 추적은 더 어렵다.

### 2-3. 개인정보 전파 — fat의 어두운 면

fat의 대가는 스키마 결합만이 아니다. 페이로드에 이메일·주소·전화번호를 담는 순간 **개인정보가 통제하기 어려운 방식으로 퍼진다.**

무엇이 문제인지 두 갈래로 나눠 보자.

**(1) 브로커의 리텐션 기간 동안 남는다.** Kafka의 로그는 뒤에만 덧붙이는 append-only 구조다. **개별 레코드를 골라 지우는 API가 없다.** 로그가 사라지는 것은 리텐션(보관 기간) 설정에 따라 오래된 세그먼트가 통째로 삭제될 때뿐이다. 리텐션이 7일이면 개인정보가 7일간 브로커에 남고, 30일이면 30일간 남는다. "회원 탈퇴 시 개인정보를 즉시 삭제한다"는 요구와 정면으로 충돌한다.

**(2) 모든 컨슈머의 로그·DB·로컬 캐시로 복제된다.** 이쪽이 훨씬 넓은 문제다. 이벤트를 받은 소비자들이 그 데이터로 무엇을 하는지 발행자는 통제할 수 없다.

```text
발행자가 이메일을 담은 OrderCompleted를 발행한다

  -> Kafka 브로커        : 리텐션 기간 동안 보관
  -> 소비자 A            : 자기 DB에 복제본 저장
  -> 소비자 B            : 처리 로그에 페이로드 전문 기록
  -> 소비자 C            : 로컬 캐시에 적재
  -> 소비자 D            : 다시 가공해 자기 토픽으로 재발행 (2차 확산)

이 사용자의 이메일이 저장된 곳의 목록 =
  원본 DB + 브로커 + 구독 팀 수만큼의 저장소 + 그 팀들의 다운스트림
```

**삭제 요청이 들어와도 원본 DB만 지워서는 회수되지 않는다.** 우리 DB에서 이메일을 지웠는데 소비자 세 팀의 DB에는 그대로 남아 있는 상태가 된다. 그리고 발행자는 1-3에서 본 이유로 **누가 구독하는지도 정확히 모른다** — 지워야 할 목록조차 못 만든다.

대응은 두 가지다.

**민감 정보는 ID만 싣고 조회하게 한다.** 이벤트에는 `userId`만 넣고, 이메일이 정말 필요한 소비자는 별도의 통제된 조회 경로로 가져가게 하는 것이다. **전체를 thin으로 만드는 게 아니라 민감 필드만 thin으로 만드는 부분 적용**이다. 이러면 개인정보가 브로커와 여러 소비자 DB에 복제되는 경로가 끊긴다.

**crypto-shredding.** 개인정보 필드를 사용자별로 다른 키로 암호화해서 싣고, 키는 별도의 안전한 저장소에 보관한다. 삭제 요청이 오면 **그 사용자의 키를 파기한다.** 그러면 브로커와 모든 소비자에 남은 암호문은 어디에 있든 복호화할 수 없는 바이트 덩어리가 된다. **"지울 수 없는 로그"를 "읽을 수 없는 로그"로 바꾸는 것**이 이 기법의 요지다. 다만 키 저장소 관리, 키 파기 절차, 아직 복호화가 필요한 정상 소비자와의 조율 같은 운영 부담이 새로 생긴다. (가산점 포인트)

**"fat으로 간다"는 결정에는 데이터 거버넌스 비용이 딸려 온다**는 것을 아는지가 시니어 변별 지점이다.

## 3. 실무의 답 — 이분법이 아니라 스펙트럼에서 자리 잡기

실무 답안은 "fat이냐 thin이냐"를 고르는 것이 아니다. 둘은 양 끝점이고, **기준을 갖고 그 사이 어딘가에 자리 잡는 것**이 답이다.

**하이브리드가 기본값이다.** 구체적으로는 ID + 대부분의 소비자가 공통으로 필요로 하는 안정적인 핵심 필드(상태, 금액, 발생 시각) + 이번에 바뀐 필드다.

여기서 중요한 판단 기준은 **"혹시 몰라서"를 금지하는 것**이다. 2-1에서 봤듯 지금 넣는 필드 하나하나가 1년 뒤의 결합이 된다. 실제 소비자 요구가 확인된 필드만 승격시킨다. **"필요하면 나중에 추가한다"가 가능하다는 것이 이 원칙의 근거**다 — 필드 추가는 하위 호환이지만 제거는 파괴적 변경이기 때문이다(4절 마지막 꼬리질문).

**경계에 따라 다르게 잡는다.** 같은 도메인 안(바운디드 컨텍스트 내부)의 이벤트는 소비자가 우리 팀이거나 가까운 팀이라 스키마 협상 비용이 낮다. fat이어도 감당된다. 반면 팀과 도메인을 넘는 통합 이벤트는 계약 변경 비용이 크므로 얇고 안정적으로 간다. **"내부는 두껍게, 외부 공개는 얇게"**가 흔한 배치다.

**선택 기준 체크리스트.** 결정할 때 실제로 물어볼 질문들이다.

- 소비자가 몇 팀이고 각각 무엇을 필요로 하나?
- 발행자가 소비자들의 조회 부하를 감당할 수 있나? (2-1의 N배 계산을 실제 숫자로 해 본다)
- 재처리가 아키텍처의 전제인가? (전제라면 thin은 위험하다)
- "이벤트 시점의 상태"가 필요한 소비자가 있나? (있다면 thin으로는 못 준다)
- 페이로드에 개인정보가 섞이나? (섞인다면 그 필드만 분리한다)

## 4. 꼬리질문 대비 포인트

### "thin 이벤트인데 '이벤트 시점의 상태'가 필요한 소비자가 있다면?"

경로가 셋이다.

**① 그 소비자가 필요로 하는 시점 데이터만 이벤트에 승격시킨다(하이브리드).** 가장 흔하고 대체로 옳은 답이다. 전부를 fat으로 바꾸는 게 아니라 필요한 필드 하나만 추가하는 것이고, 추가는 하위 호환이므로 기존 소비자를 깨지 않는다.

**② 이벤트에 버전/시퀀스 번호를 싣고 발행자가 버전별 조회를 제공한다.** "주문 1234의 버전 7 상태를 달라"는 조회를 받는 것이다. 정확하지만 발행자에 **이력 저장 부담**이 새로 생긴다 — 과거 모든 버전을 보관해야 한다.

**③ 요구가 전반적이면 그 이벤트는 애초에 fat이 맞는 것이다.** 한 소비자만 시점 데이터가 필요하면 ①이지만, 대부분이 필요하다면 설계 판단 자체가 틀렸다는 신호다.

"thin으로 정했으니 끝"이 아니라 **소비자 요구가 설계를 되먹이는 구조**로 답하는 것이 요점이다.

### "fat 이벤트의 스키마는 어떻게 안 깨지게 진화시키나?"

**스키마를 코드 밖의 계약으로 관리한다.** Schema Registry에 스키마를 등록하고 호환성 규칙을 강제해, 규칙을 어기는 스키마는 아예 등록되지 않게 만든다. 사람의 주의력에 맡기지 않고 도구가 막게 하는 것이 핵심이다.

실무 관용 규칙은 **"필드 추가는 기본값과 함께, 삭제·타입 변경·의미 변경은 금지"**다. 기본값을 요구하는 이유는, 새 필드를 모르는 옛 소비자가 그 이벤트를 읽어도 문제없이 역직렬화되게 하기 위해서다.

**의미 변경 금지**를 특히 짚으면 좋다. 필드 이름과 타입은 그대로인데 값의 의미만 바꾸는 것(예: `amount`를 세전에서 세후로) — 이건 스키마 검사를 통과하면서도 모든 소비자를 조용히 망가뜨린다. **도구가 못 잡는 유형의 파괴적 변경**이다.

지키기 어려운 변경이 필요하면 **새 버전 토픽(또는 새 이벤트 타입)을 나란히 발행하고 소비자를 순차 이전**시킨다. 요컨대 REST API의 하위 호환성 원칙을 비동기 세계로 확장한 것이다.

### "대량 replay 상황에서 두 방식은 어떻게 다르게 무너지나?"

fat은 브로커 읽기와 소비자 자신의 처리 능력만이 제약이다. 소비자 쪽만 격리하면 된다.

thin은 재처리 건수만큼의 조회가 발행자 API로 향한다. **100만 건 replay가 발행자에 100만 조회를 쏘는 2차 장애 유발기**가 되고, 소비자가 5팀이면 500만 조회다. 게다가 2-2에서 본 시점 불일치 때문에, 무사히 돌았다 해도 **결과가 "과거 시점 복원"이 아니라 "오늘 상태 기준"으로 만들어진다.**

thin으로 갈 거라면 재처리 시나리오의 대비까지 설계에 포함돼야 한다 — 조회 스로틀링, 발행자 조회 전용 replica 분리, 또는 "재처리용은 실시간 API가 아니라 스냅샷에서 읽기" 같은 우회로다.

### "이벤트에 개인정보를 실으면 안 되는 이유와, 실어야 한다면?" (시니어 변별 포인트)

이유는 둘이다. **Kafka 로그는 레코드 단위 삭제가 안 되므로 리텐션 기간 동안 개인정보가 지워지지 않는다.** 그리고 **소비자 DB·로그·캐시로 복제되는 순간 삭제 요청 시 추적해야 할 범위가 구독 팀 수만큼 늘어난다** — 발행자는 구독 목록조차 정확히 모르므로 지울 대상 목록을 만들 수도 없다.

실어야 한다면 대응은 둘이다. **개인정보 필드만 ID 참조로 빼거나(부분 thin)**, **사용자별 키로 암호화해 싣고 삭제 요청 시 그 키를 파기하는 crypto-shredding**으로 "지울 수 없는 로그"를 "읽을 수 없는 로그"로 바꾼다.

**페이로드 설계를 데이터 거버넌스 문제로 연결하는 것 자체가 변별 포인트**다. 대부분은 이 질문을 성능·결합도 문제로만 본다.

### "이미 thin으로 1년 운영했는데 조회 부하가 한계다 — 어떻게 전환하나?"

계약 변경이므로 빅뱅은 불가능하다. 순서는 이렇다.

기존 thin 이벤트는 그대로 두고 **필드를 추가하는 방식으로 살찌운다.** 추가는 하위 호환이므로 옛 소비자는 아무 영향을 안 받는다. 그다음 소비자들이 각자 조회를 이벤트 필드 참조로 하나씩 바꾸고, **전 소비자 이전이 확인되면** 그때 조회 API 의존을 끊는다.

반대 방향(fat → thin)은 훨씬 어렵다. 필드 제거는 파괴적 변경이라 소비자 전수를 확인해야 하는데, 1-3에서 본 대로 전수 확인이 어렵다.

이 **비대칭**을 짚는 것이 답의 마무리다. **"살찌우기는 호환, 빼기는 파괴"** — 그래서 확신이 없을 때는 얇게 시작하는 것이 안전하고, 3절의 "혹시 몰라서 넣지 않는다" 원칙도 여기서 나온다.

## 한 줄 요약

이벤트 페이로드는 발행자가 구독자 목록조차 알 수 없는 상태로 전 소비자가 의존하는 공개 계약이라 사실상 비가역이고, fat(상태 전송)은 소비자 자립·재처리 자유를 주는 대신 스키마 결합과 개인정보의 리텐션·다운스트림 전파를, thin(통지)은 얇은 계약을 주는 대신 소비자 수만큼의 조회 부하·발행자 가용성 재결합·"이벤트 시점이 아닌 조회 시점 상태"라는 시점 불일치를 남긴다 — 1년 뒤의 스키마 변경 파급, 장애 전파 경로, replay 가능성이 이 결정 하나에 걸려 있으므로, "ID + 검증된 핵심 필드"의 하이브리드에서 시작해 소비자 요구가 확인된 필드만 승격시키는 것이 실무의 답이다.
