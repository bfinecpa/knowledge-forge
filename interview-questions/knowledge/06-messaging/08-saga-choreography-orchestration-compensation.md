# Saga 패턴 — choreography vs orchestration, 그리고 보상의 함정

> 핵심 관전 포인트: **Saga는 여러 서비스에 걸친 작업을 하나의 분산 트랜잭션으로 묶는 대신, 서비스별 로컬 트랜잭션의 연쇄로 진행하고 중간에 실패하면 이미 커밋된 단계들을 보상 트랜잭션으로 되돌리는 패턴이다. choreography(안무)는 중앙 지휘자 없이 각 서비스가 이벤트를 구독해 스스로 반응하는 방식 — 결합은 낮지만 전체 흐름이 코드 어디에도 없고 토픽 구독 관계도에만 존재한다. orchestration(지휘)은 오케스트레이터가 순서와 보상을 지휘하는 방식 — 흐름이 한눈에 보이지만 중앙 컴포넌트가 생기고, 그 컴포넌트의 상태 전이와 커맨드 발행을 아웃박스로 묶어야 한다. 그리고 보상은 rollback이 아니라 "반대 방향의 새로운 비즈니스 행위"라서 — 보상 자체가 실패할 수 있고, 보상 커맨드도 at-least-once로 오므로 보상이 멱등해야 하고, 보상이 아예 불가능한 동작(이미 발송된 알림)은 실행 순서로 풀어야 한다는 것까지 설계에 넣어야 한다.**

---

## 0. 질문 + 의도

**질문**: "Saga 패턴(choreography vs orchestration)을 비교하고, 보상 트랜잭션 설계 시 주의점을 설명해주세요."

**출제 의도**: 분산 트랜잭션의 실무 대안을 아는 것에 더해, 보상의 함정(보상 자체의 실패, 보상 불가능한 동작 — 이미 발송된 알림)까지 짚는지 본다. 해법의 한계를 아는 것이 진짜 이해의 증거다.

> 이 문서는 **Saga를 Kafka/메시징 관점에서** 다룬다. 같은 패턴을 결제 도메인의 요구(돈이 붕 뜨는 상황, 대사, 수동 개입 큐) 관점에서 더 깊게 파고드는 문서가 따로 있다 — `10-payment-consistency/10-distributed-saga-compensation-idempotency.md`. 2PC 배제 근거나 멱등성 키 전파 같은 공통 토대는 이 문서에서도 답할 수 있게 짚되 간결히 가고, **이벤트 구독으로 Saga를 구현할 때만 생기는 문제**(순환 구독, 흐름의 부재, 파티션 키와 단계 순서, at-least-once와 보상)에 무게를 싣는다.

## 1. 왜 필요한가 — 분산 트랜잭션(2PC)이 답이 아닌 이유

### 1-1. 전제 지식 — 각자 DB를 가지면 롤백 버튼이 사라진다

주문 하나가 여러 서비스를 거친다고 하자: **주문 생성 -> 결제 승인 -> 재고 차감 -> 배송 접수.**

`@Transactional`이 여러 SQL을 "전부 성공 아니면 전부 없던 일"로 묶어줄 수 있는 이유는, **하나의 DB 엔진이 자기 데이터에 대해** 변경 전 값을 갖고 있다가 `ROLLBACK` 신호에 되돌려 주기 때문이다. 롤백은 DB가 제공하는 기능이지 공중에 떠 있는 능력이 아니다.

각 서비스가 자기 PostgreSQL을 가지면 이 전제가 무너진다. 결제 서비스가 `COMMIT`을 끝낸 순간 그 승인은 **그쪽 DB에서 이미 확정된 과거**다. 나중에 재고 차감이 실패했다고 해서 남의 DB에 "아까 그거 롤백해"라고 보낼 수 있는 표준 명령은 존재하지 않는다.

그래서 분산 환경의 실패 처리는 **"되돌리기"가 아니라 "반대 방향의 새 작업으로 메우기"**가 된다. 이 전환이 Saga의 출발점이다.

### 1-2. 고전적 답인 2PC가 실무에서 배제되는 이유

**2PC(two-phase commit, 2단계 커밋)**는 **코디네이터(coordinator, 조정자)**라는 중앙 심판을 두고 두 단계로 진행하는 방식이다. 1단계에서 코디네이터가 참여자 전원에게 "준비됐나?"를 묻고, 참여자는 자기 몫을 실행하되 **커밋하지 않고 잠금을 쥔 채** "예"라고 답한다. 2단계에서 전원이 "예"였으면 "커밋하라"를, 하나라도 아니면 "중단하라"를 전파한다.

이론상 분산 원자성이 성립한다. 그런데 실무에서는 거의 못 쓴다.

- **블로킹**: prepare 후 코디네이터 응답을 기다리는 동안 모든 참여자가 락을 쥔 채 멈춘다. 참여자 하나만 느려도 전체가 그 속도가 된다.
- **코디네이터가 단일 장애점**: 코디네이터가 죽으면 참여자들은 커밋도 롤백도 못 하는 in-doubt 상태로 남는다. 잠금을 쥔 채로다 — **한 지점의 장애가 전 시스템의 잠금 정체로 번진다.**
- 애초에 Kafka나 대부분의 최신 저장소·외부 API는 XA(분산 트랜잭션 프로토콜)에 참여하지 않는다. XA는 prepare와 commit을 나눠 받을 수 있는 자원만 참가할 수 있는 표준인데, 현대적 아키텍처의 구성 요소 상당수가 **참가 자격 자체가 없다.**

세 근거를 더 자세히 풀어 놓은 곳은 `10-payment-consistency/10-distributed-saga-compensation-idempotency.md`의 1-2절이다.

Saga는 접근을 뒤집는다 — **원자성을 포기하고, 각 단계를 즉시 커밋되는 로컬 트랜잭션으로 진행하되, 실패 시 "이미 커밋된 것들을 의미적으로 되돌리는" 보상 트랜잭션을 준비해 둔다.** 원자성을 공간(동시에 전원이 커밋)이 아니라 시간축(순서대로 진행하고 실패하면 되감기)으로 푸는 것이다.

```text
정상:  주문 생성 -> 결제 승인 -> 재고 차감 -> 배송 접수   (완주)
실패:  주문 생성 -> 결제 승인 -> 재고 차감 (품절로 실패)
보상:            <- 결제 취소(환불) <- 주문 실패 처리
       (커밋 완료된 단계를 역순으로 되돌린다)
```

보상이 **역순**인 이유는 의존 관계 때문이다. 주문이 있어야 그 주문에 대한 결제가 성립하므로, 되돌릴 때는 안쪽(나중 단계)부터 푼다. 그리고 **실패한 단계 자신은 보상하지 않는다** — 커밋되지 않았으니 되돌릴 것이 없다.

## 2. choreography vs orchestration — 지휘자 없는 춤 vs 지휘자 있는 오케스트라

### 2-1. 왜 선택지가 이 둘뿐인가

Saga를 구현하려면 반드시 답해야 하는 질문이 하나 있다. **"주문 생성이 끝났다는 것을 누가 알고, 누가 결제를 시작시키는가?"**

이 질문의 답은 논리적으로 두 개뿐이다. **다음 단계를 맡은 서비스가 스스로 알아채고 시작하거나**, **중앙의 누군가가 알려주고 시작시키거나.** 이 갈림이 그대로 두 방식이 된다. 세 번째 답은 없다.

### 2-2. Choreography (안무) — 이벤트 구독으로 각자 반응

이름부터 보자. **choreography는 무용의 "안무"**다. 무대 위 무용수들에게는 지휘자가 없다. 각자 음악을 듣고 서로의 동작을 보면서 자기 차례에 움직인다. 전체 안무는 리허설을 통해 각자의 몸에 나뉘어 들어가 있을 뿐, 무대 위 어느 한 사람이 들고 있지 않다.

Saga의 choreography가 정확히 그렇다. 중앙 조정자가 없다. 각 서비스가 앞 단계의 이벤트를 구독해서 자기 일을 하고 다음 이벤트를 발행한다.

```text
주문 서비스: OrderCreated 발행
결제 서비스: OrderCreated 구독 -> 결제 -> PaymentCompleted 발행
재고 서비스: PaymentCompleted 구독 -> 차감 -> StockReserved 발행
             (실패 시 StockReservationFailed 발행)
결제 서비스: StockReservationFailed 구독 -> 환불 (보상)
주문 서비스: StockReservationFailed 구독 -> 주문 실패 처리 (보상)
```

메시지 흐름을 토픽 관점에서 그리면 이렇게 된다. 화살표가 전부 "발행 -> 구독"이고, 중앙이 없다.

```text
  [주문 서비스] --발행--> (order.created)
                              |
                            구독
                              v
                        [결제 서비스] --발행--> (payment.completed)
                                                    |
                                                  구독
                                                    v
                                              [재고 서비스]
                                                    |
                                              실패 시 발행
                                                    v
                                        (stock.reservation.failed)
                                             |            |
                                           구독          구독
                                             v            v
                                    [결제 서비스]   [주문 서비스]
                                      환불(보상)     실패 처리(보상)
```

### 2-3. Orchestration (지휘) — 오케스트레이터가 순서·보상을 관리

**orchestration은 오케스트라의 "지휘"**다. 지휘자가 악보 전체를 들고 있고, 현악 파트에 신호를 주고, 그다음 관악 파트에 신호를 준다. 각 연주자는 자기 파트만 알면 되고 전체 곡의 진행은 지휘자만 안다.

오케스트레이터(별도 컴포넌트 또는 주문 서비스 내 saga 관리 모듈)가 각 서비스에 커맨드를 보내고 응답을 받아 다음 단계 또는 보상을 결정한다.

```text
오케스트레이터: 결제해라 -> [결제 서비스] -> 완료
오케스트레이터: 재고 차감해라 -> [재고 서비스] -> 실패!
오케스트레이터: (saga 상태를 보고) 결제 취소해라 -> [결제 서비스]
오케스트레이터: 주문 실패 처리 -> 종료
```

메시지 흐름을 그리면 choreography와 모양이 확연히 다르다. 모든 화살표가 중앙을 지난다.

```text
                    [오케스트레이터]  (saga 상태 테이블 보유)
                      |   ^   |   ^   |   ^
             커맨드   |   |   |   |   |   |   응답 이벤트
                      v   |   v   |   v   |
              [결제 서비스] [재고 서비스] [배송 서비스]

  흐름이 오케스트레이터의 상태 머신 코드 한 곳에 전부 적혀 있다.
  참여 서비스끼리는 서로를 모른다.
```

**핵심 대비**는 이것이다. choreography에서 각 서비스는 **서로를 안다**(정확히는 서로의 이벤트를 안다) 대신 전체를 모른다. orchestration에서 각 서비스는 **서로를 모른다** 대신 오케스트레이터가 전체를 안다.

### 2-4. 비교와 선택 기준

| 관점 | Choreography | Orchestration |
|---|---|---|
| 전체 흐름 파악 | 어디에도 없음 — 이벤트 구독 관계를 다 뒤져야 보임 | 오케스트레이터 코드 한 곳에 있음 |
| 결합도 | 낮음 — 서로 이벤트만 알면 됨 | 오케스트레이터가 모든 참여자를 앎 |
| 단계 추가/변경 | 구독만 추가하면 되지만, 영향 범위 파악이 어려움 | 오케스트레이터 수정으로 명시적 |
| 실패/보상 로직 | 각 서비스에 분산 — 누락되기 쉬움 | 한곳에서 관리 — 상태 추적·타임아웃 걸기 쉬움 |
| 추가 컴포넌트 | 없음 | 오케스트레이터(상태 저장 포함) 필요 |
| 위험 요소 | 순환 구독, 암묵적 흐름, "이 이벤트 지우면 뭐가 깨지지?" | 오케스트레이터에 비즈니스 로직 집중·비대화 |

선택 기준을 한 줄로: **참여 서비스 2~3개에 흐름이 직선이면 choreography로 가볍게, 단계가 많거나 조건 분기·타임아웃·보상 조합이 복잡하면 orchestration.**

그리고 실무에서 가장 흔한 실패 경로를 하나 알고 있으면 좋다. **choreography로 시작한 saga가 커지면서 "전체 그림을 아는 사람이 아무도 없는" 상태가 되는 것**이다. 단계가 3개일 때는 구독 관계가 머릿속에 들어오지만, 8개가 되고 분기와 보상이 얽히면 아무도 전체를 그릴 수 없게 된다. 그런데 각 단계는 여전히 "구독 하나 추가"라는 작은 변경으로 늘어나기 때문에, **커지는 과정에서 아무도 브레이크를 밟지 않는다.**

### 2-5. Kafka로 구현할 때만 생기는 문제들

여기부터가 이 문서의 고유 영역이다. 위의 비교는 패턴 차원의 이야기이고, 실제로 Kafka 위에 얹는 순간 몇 가지 문제가 더 붙는다.

#### (1) 코레오그래피의 순환 구독 — 사이클이 토픽 그래프에 생긴다

choreography의 보상 경로를 다시 보자. 재고 실패 이벤트를 **결제 서비스가 구독**해서 환불한다. 그런데 결제 서비스는 원래 `order.created`를 구독해서 결제하는 서비스다. 즉 결제 서비스는 이제 두 토픽을 구독하고, 그중 하나는 자기보다 **뒤 단계**의 서비스가 발행한 것이다.

```text
  (order.created) -> [결제] -> (payment.completed) -> [재고]
                        ^                                |
                        |                                v
                        +----- (stock.reservation.failed)
                              뒤 단계가 앞 단계를 다시 깨운다
```

화살표가 앞으로만 가지 않고 되돌아온다. **토픽과 서비스로 그린 그래프에 사이클이 생긴 것**이다. 이 자체가 곧 버그는 아니지만 두 가지가 어려워진다.

첫째, **무한 루프가 실제로 만들어질 수 있다.** 환불 처리 결과로 `payment.refunded`를 발행하고 그것을 다시 누군가 구독해 또 이벤트를 발행하는 식으로 연쇄가 이어지면, 어느 지점에서 앞의 토픽으로 되돌아가 순환이 닫힐 수 있다. 단계마다 다른 팀이 구독을 추가하는 환경에서는 **아무도 전체 그래프를 보지 않기 때문에** 닫히는 순간을 알아채기 어렵다.

둘째, **보상인지 정방향인지가 이벤트만 봐서는 구분되지 않는다.** 결제 서비스 입장에서 들어오는 메시지는 그냥 "구독한 토픽의 레코드"이고, 지금 진행 중인 saga가 정방향인지 되감는 중인지는 페이로드를 뜯어봐야 안다. orchestration에서는 이것이 상태 머신의 현재 상태로 명확한데, choreography에서는 각 서비스가 각자 추론해야 한다.

방어책은 **모든 이벤트에 sagaId(correlation ID)와 단계 번호를 싣고, 각 컨슈머가 "지금 이 saga가 어느 방향인지"를 자기 처리 이력으로 판단하게** 만드는 것이다. 다만 이것은 방어이지 해결이 아니다 — 사이클 자체는 남는다.

#### (2) 흐름이 코드가 아니라 토픽 관계도에만 존재한다

choreography에서 "이 토픽을 없애면 뭐가 깨지지?"라는 질문에 답해 보자.

코드 검색으로는 답이 안 나온다. 발행하는 쪽 코드에는 토픽 이름만 있고, 구독하는 쪽은 **다른 저장소의 다른 서비스**에 있기 때문이다. 결국 답을 얻으려면 브로커에 물어봐야 한다.

```bash
# 이 토픽을 지금 누가 소비하고 있는가 — 코드가 아니라 브로커에게 묻는다
kafka-consumer-groups.sh --bootstrap-server broker:9092 --list
kafka-consumer-groups.sh --bootstrap-server broker:9092 \
  --group inventory-saga --describe
```

즉 **Saga의 흐름도가 소스 코드가 아니라 런타임 구독 관계에 존재한다.** 이것이 표에서 "전체 흐름 파악: 어디에도 없음"이라고 쓴 것의 실체다. 그리고 그 관계는 코드 리뷰에도 안 잡히고, 컴파일 에러로도 안 나오며, 배포 순서에 따라 조용히 깨진다.

orchestration에서는 같은 질문이 "오케스트레이터의 상태 머신 코드를 읽는다"로 끝난다. 이 차이가 운영 부담의 대부분을 만든다.

#### (3) 오케스트레이터의 커맨드 발행에는 아웃박스가 필요하다

오케스트레이터가 매 단계에 하는 일은 두 가지다 — ① 자기 DB의 saga 상태를 전이시키고, ② 다음 서비스에 커맨드를 발행한다.

이 둘이 어긋나면 어떻게 되는지 보면 왜 문제인지 안다.

- **전이만 커밋되고 발행 전에 죽으면**: 상태는 `STOCK_REQUESTED`인데 재고 차감 커맨드는 아무도 못 받았다. saga가 조용히 멈춰 표류한다.
- **발행은 됐는데 전이가 롤백되면**: 재고 서비스는 차감을 했는데 오케스트레이터는 아직 이전 단계라고 알고 있다. 나중에 커맨드를 또 보내거나 잘못된 보상을 태운다.

그런데 **PostgreSQL 쓰기와 Kafka 발행은 서로 다른 시스템이라 한 트랜잭션으로 묶을 수 없다.** 이것을 **이중 쓰기(dual write) 문제**라고 부른다.

해법이 **트랜잭셔널 아웃박스**다. 아웃박스(outbox)는 말 그대로 "보낼 편지함"이다. 커맨드를 Kafka로 바로 쏘는 대신 **같은 DB의 outbox 테이블에 INSERT**해 두면, saga 상태 전이와 발행 예약이 **같은 트랜잭션 안의 두 쓰기**가 되어 함께 커밋되거나 함께 롤백된다. 실제 발행은 릴레이(relay)라는 별도 프로세스가 outbox를 읽어(폴링 또는 WAL 기반 CDC) 처리한다.

```text
[오케스트레이터]
  |  BEGIN
  |    UPDATE saga_instance SET step='STOCK_REQUESTED' ...
  |    INSERT INTO outbox (topic='stock.commands', payload=...)
  |  COMMIT   <- 상태 전이와 발행 예약이 함께 남거나 함께 없다
  v
[outbox 테이블] <--- 릴레이가 폴링/CDC로 읽어 발행
                        |
                        v
                    [Kafka] ---> [재고 서비스]
```

여기서 짚어야 할 것은 **choreography라고 이 문제가 없는 것이 아니다**라는 점이다. 각 참여 서비스도 "자기 로컬 트랜잭션 커밋 + 다음 이벤트 발행"이라는 똑같은 이중 쓰기를 하고 있다. 오히려 **choreography에서는 그 아웃박스를 모든 참여 서비스가 각자 갖춰야** 하고, 한 서비스라도 빠뜨리면 그 지점에서 saga가 끊긴다. orchestration은 최소한 "중앙 한 곳은 반드시 갖춰야 한다"가 명확하다.

아웃박스와 CDC의 구현 세부는 같은 장의 `28-transactional-outbox-cdc-kafka.md`에서 다룬다.

#### (4) 보상 커맨드도 at-least-once로 온다

Kafka의 기본 전달 보장은 **at-least-once(최소 1회)**다. "적어도 한 번은 도착한다"는 약속이지 "정확히 한 번"이 아니다.

왜 그런지 구체적으로 보자. 컨슈머는 "어디까지 읽었는지"를 오프셋(offset)이라는 숫자로 기록한다. 메시지를 처리한 뒤 오프셋을 커밋해야 다음부터 그 메시지를 안 받는데, **처리와 오프셋 커밋 사이에 죽으면** 재시작 후 같은 메시지를 다시 받는다. 리밸런싱 중에도 같은 일이 생긴다.

이 사실이 보상에 던지는 의미가 중요하다. **보상 커맨드 역시 Kafka를 타고 오므로, 보상도 두 번 실행될 수 있다.** 정방향 단계만 멱등하게 만들고 보상은 잊는 것이 흔한 누락인데, **환불이 두 번 나가는 것은 재고가 두 번 차감되는 것보다 대체로 더 아프다.**

그래서 규칙은 이렇게 정리된다. **정방향 단계와 보상 단계 모두, 예외 없이 전부 멱등해야 한다.** 구체적인 구현은 3절 ③에서 다룬다. 전달 의미론 자체는 `03-delivery-semantics-and-exactly-once-reality.md`, 멱등 컨슈머 구현은 `04-idempotent-consumer-implementation.md`에 있다.

#### (5) 단계의 순서는 파티션 키로 지킨다

Kafka는 **하나의 파티션 안에서만** 메시지 순서를 보장한다. 파티션이 여럿이면 파티션 사이의 순서는 보장하지 않는다. 어느 파티션에 들어갈지는 메시지 키의 해시로 정해지고, 키가 없으면(null) 라운드로빈으로 흩뿌려진다.

Saga에 이것이 왜 치명적인지 보자. 같은 주문에 대한 커맨드가 키 없이 발행되면 서로 다른 파티션에 들어갈 수 있고, 그러면 **발행 순서와 소비 순서가 뒤집힐 수 있다.**

```text
[키를 안 준 경우 — 위험]
  payment.deduct  (order=8471) -> 파티션 0
  payment.refund  (order=8471) -> 파티션 2   (다른 파티션!)

  파티션 0의 컨슈머와 파티션 2의 컨슈머는 서로의 진도를 모른다.
  -> 환불이 결제보다 먼저 소비될 수 있다.
  -> "결제 이력이 없는데 환불하라"는 요청이 되어 거부되고,
     뒤늦게 결제만 성사되어 돈이 그대로 빠져나간다.

[sagaId(=orderId)를 키로 준 경우 — 안전]
  producer.send(new ProducerRecord<>("payment.commands",
      String.valueOf(orderId),   // <- 파티션 키
      command));

  order=8471의 모든 커맨드 -> 같은 해시 -> 같은 파티션 -> 발행 순서대로 소비
  order=8472는 다른 파티션일 수 있다 -> 서로 간 순서는 무관하므로 문제없다
```

**키는 sagaId(실무에서는 대개 orderId)로 잡는다.** 순서를 지켜야 하는 단위가 정확히 "하나의 saga 인스턴스"이기 때문이다. userId를 키로 쓰면 순서는 지켜지지만 헤비 유저가 있는 서비스에서 특정 파티션에 쏠린다.

그런데 여기에 **반드시 알아야 할 한계**가 둘 있다.

**첫째, 순서 보장은 같은 토픽 안에서만이다.** saga의 각 단계가 `payment.commands`, `stock.commands`, `shipping.commands`처럼 서로 다른 토픽으로 나간다면, 같은 키를 줘도 **토픽이 다르면 순서 보장은 아예 없다.** 각 토픽의 컨슈머가 독립적으로 돌기 때문이다.

**둘째, 컨슈머가 병렬로 처리하면 파티션 순서가 무너진다.** poll로 받은 레코드를 스레드 풀에 던지는 순간, 브로커가 지켜준 순서는 애플리케이션 안에서 사라진다.

그래서 결론은 **"파티션 키만 믿지 않는다"**이다. 파티션 키는 같은 토픽 안 같은 saga의 순서를 지키는 도구이고, 그 바깥은 **상태 머신 가드**가 지킨다.

```java
// 오케스트레이터의 응답 이벤트 핸들러 — 순서가 뒤집혀 와도 안전하다
@Transactional
public void onPaymentCompleted(PaymentCompleted event) {
    // FOR UPDATE로 saga 행을 잠근다. 같은 saga의 이벤트 둘이 동시에
    // 도착해도 한 번에 하나씩만 상태를 전이시키기 위해서다.
    Saga saga = sagaRepository.findByOrderIdForUpdate(event.orderId());

    // 상태 머신 가드: "지금 상태에서 유효한 이벤트인가"만 받아들인다.
    // 중복 배달이거나 순서가 뒤집혀 늦게 도착한 이벤트는 여기서 걸린다.
    // 예외를 던지지 않고 return하는 이유 — 중복 배달은 오류가 아니라
    // at-least-once에서 정상적으로 예상되는 상황이다. 예외를 던지면
    // 컨슈머가 같은 메시지를 무한 재시도하며 파티션을 막는다.
    if (saga.step() != Step.PAYMENT_REQUESTED) return;

    saga.moveTo(Step.STOCK_REQUESTED);
    outbox.save(Command.of("stock.commands", event.orderId()));  // (3) 아웃박스
}
```

파티션 키에 대한 더 자세한 논의는 같은 장의 `24-message-ordering-partition-key.md`에 있다.

## 3. 보상 트랜잭션 설계 시 주의점 — 여기가 진짜 시험대

### ① 보상은 rollback이 아니라 새로운 비즈니스 행위다

DB rollback은 "없었던 일"로 만들지만, 보상은 이미 커밋되고 외부에 노출된 결과를 **반대 방향의 새 트랜잭션**으로 상쇄하는 것이다. 결제 취소는 결제가 없었던 게 아니라 "결제 후 환불"이라는 새 이력이다.

회계와 같다. 잘못된 분개를 지우개로 지우지 않고 **반대 분개를 한 줄 더 적는다.** 원장에는 두 줄이 다 남고, 합계만 0이 된다.

따라서 보상도 정식 비즈니스 로직으로 — 이력, 정산, 알림까지 — 설계해야 한다. 실무에서 이것이 잊히면 "환불은 됐는데 정산 데이터에는 결제만 잡혀 있다" 같은 불일치가 나온다.

### ② 보상 자체가 실패할 수 있다

환불 API가 그 순간 죽어 있으면? 보상 실패를 그냥 버리면 **돈은 받고 물건은 안 주는** 상태로 영구히 남는다. 그리고 아무도 그 사실을 모른다.

```text
Before: 보상 호출 1회 -> 실패 시 로그만 남기고 종료   // 정합성 구멍
After:  보상은 재시도 큐로 — 성공할 때까지 재시도(멱등 전제)
        + N회 초과 시 수동 개입 큐 적재 + 운영 알림
        // 보상의 실패 경로까지 설계해야 saga가 완성된다
```

Kafka 위에서는 이 "재시도 큐"가 사실상 공짜로 온다. **보상 커맨드가 아웃박스에 커밋되어 Kafka에 발행되고 나면 그 메시지는 사라지지 않는다.** 컨슈머가 죽어 있으면 오프셋이 진행되지 않을 뿐이고, 복구되면 그 지점부터 다시 처리된다. 이것이 "보상을 HTTP 동기 호출로 하지 않는" 실질적인 이유다 — 동기 호출은 실패하면 그 순간 사라지지만, 발행된 메시지는 남는다.

다만 무한 재시도는 답이 아니다. 재시도 사이에 **지수 백오프**(1, 2, 4, 8초처럼 간격을 늘려 가는 방식)를 두어 이미 힘들어하는 상대 시스템에 재시도 폭풍을 얹지 않고, 한도(예: 5회)를 넘기면 **수동 개입 큐** — 운영자가 보는 보정 대기 테이블 — 에 적재하고 알림을 쏜다.

**자동 복구가 실패하는 것 자체는 막을 수 없지만, 실패했다는 사실이 아무 데도 기록되지 않는 것은 설계 결함이다.** 수동 개입 큐의 구체적인 스키마와 운영은 `10-payment-consistency/10-distributed-saga-compensation-idempotency.md`의 3절 사례 1에 있다.

### ③ 멱등성 — 보상이 두 번 실행돼도 안전해야 한다

**멱등성(idempotency)**은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"이다.

2-5 (4)에서 봤듯 이벤트는 at-least-once로 전달되고 재시도도 있으므로, **같은 보상이 중복 실행되는 것은 예외가 아니라 정상 상황**이다. 환불이 두 번 나가면 그게 새 장애다.

방어는 **sagaId(또는 주문 ID) 기준 처리 이력**으로 한다. 그런데 "이미 처리했나?"를 조회로 확인하고 없으면 INSERT하는 방식은 안 된다 — 조회와 INSERT 사이의 틈에 다른 요청이 끼어들 수 있기 때문이다. **유니크 제약을 걸고 INSERT를 먼저 시도**해야 확인과 선점이 DB 안에서 한 번에 원자적으로 일어난다.

```sql
-- 한 주문에 결제 1건, 환불 1건까지만 허용한다.
-- entry_type을 키에 포함하지 않으면 "결제가 이미 있다"는 이유로
-- 환불이 거부된다 — 성격이 다른 쓰기는 키로 구분해야 한다.
ALTER TABLE payment_ledger
    ADD CONSTRAINT uq_payment_ledger UNIQUE (order_id, entry_type);
```

```java
// 결제 서비스: 환불(보상) 커맨드 핸들러
@Transactional
public RefundResult handle(RefundCommand cmd) {
    // ON CONFLICT (order_id, entry_type) DO NOTHING.
    // 이미 환불 기록이 있으면 아무 일도 일어나지 않고 0을 반환한다.
    int inserted = ledgerRepository.insertRefundIfAbsent(
        cmd.orderId(), cmd.amount());

    // 여기서 에러를 응답하면 오케스트레이터가 "보상 실패"로 오판해
    // 재시도를 반복하거나 수동 개입 큐에 정상 건을 쌓는다.
    // "이미 처리됨"은 실패가 아니라 성공이다.
    return RefundResult.success(cmd.orderId());
}
```

이 **"이미 처리됨 = 성공 응답"** 규칙이 왜 중요한지 한 번 더 짚자. 참여자 전원이 멱등하고 이 규칙을 지켜야 오케스트레이터가 **"확신이 없으면 그냥 재전송한다"**는 단순한 복구 전략을 쓸 수 있다. 그렇지 않으면 재전송할 때마다 "이미 했나 안 했나"를 확인하는 조회 API와 분기 로직이 필요해지고 상태 공간이 폭발한다.

멱등성 키는 **오케스트레이터(또는 saga 시작점)가 한 번 만들어 모든 커맨드에 실어 끝까지 같은 값으로 전파**해야 한다. 참여자가 각자 키를 만들면 재전송 때마다 새 키가 붙어 중복 탐지가 원천적으로 불가능해진다.

### ④ 보상 불가능한 동작이 있다 — 실행 순서로 푼다

이미 발송된 이메일·푸시 알림, 외부사에 전송된 확정 통보는 되돌릴 수 없다. 보낸 메일을 회수하는 API는 없다.

해법은 보상이 아니라 **단계 배치 순서**다. 발상이 단순해서 오히려 넘어가기 쉬운데, 정확히 말하면 이렇다. **되돌릴 수 없는 동작을 saga의 가장 마지막에 두면, 그 앞 단계가 전부 성공한 뒤에만 실행되므로 애초에 보상할 일이 생기지 않는다.**

```text
[나쁜 배치 — 알림이 중간에 있다]
  주문 생성 -> 알림 발송 -> 결제 승인 -> 재고 차감(실패!)
                  ^                          |
                  |                          v
              보상 불가!  <----------- 여기서 되감아야 하는데
              메일은 이미 나갔다        알림을 되돌릴 방법이 없다

[좋은 배치 — 되돌릴 수 없는 것을 끝으로 민다]
  주문 생성 -> 결제 승인 -> 재고 차감 -> [피벗] -> 배송 접수 -> 알림 발송
  <---- 실패 가능·보상 가능 구간 ---->          <-- 실패해도 재시도만 -->

  재고 차감까지 전부 성공했다는 것은
  = 되감을 이유가 더 이상 없다는 뜻이고,
  = 그 뒤의 알림 발송은 보상 대상이 될 일이 없다.
```

이때 **"이 단계 이후로는 보상 없이 앞으로만 간다"는 분기점**을 **피벗(pivot) 트랜잭션**이라 부른다. 피벗은 저울의 받침점이라는 뜻으로, 그 지점을 넘으면 saga가 되돌아갈 수 없고 완주 방향으로만 기운다는 의미다.

피벗 이후의 단계는 실패하면 **보상이 아니라 성공할 때까지 재시도**로 설계한다. 그러므로 **피벗 뒤에는 재시도로 반드시 성공할 수 있는 단계만 배치해야 한다.** 품절처럼 재시도해도 결과가 같은 비즈니스적 거절이 피벗 뒤에 오면 saga가 영원히 끝나지 않는다. (가산점 포인트)

#### 마지막에 둘 수 없다면 — 비가역을 가역으로 바꾼다

문제는 모든 비가역 동작을 맨 뒤로 밀 수 있는 것은 아니라는 점이다. 예를 들어 외부 정산 시스템에 확정 통보를 보내야 그쪽에서 배송 승인이 떨어지고, 배송 승인이 있어야 다음 단계가 진행되는 경우가 있다. 순서를 바꿀 수 없다.

이때의 답은 **되돌릴 수 없는 동작을 되돌릴 수 있는 형태로 바꾸는 것**이다. 세 가지 방법이 있다.

**(가) 즉시 실행을 예약 실행으로 바꾼다.** 이메일을 지금 보내는 대신 "N분 뒤 발송"으로 예약한다. saga가 그 안에 완주하면 예약대로 나가고, 실패하면 **예약을 취소**한다. 취소는 가능한 동작이므로 보상이 성립한다.

```text
Before: sendEmail(...)              // 나간 순간 끝, 보상 불가
After:  scheduleEmail(..., delay);  // 예약 — 취소 가능
        보상: cancelScheduledEmail(sagaId);
```

여기서 **N을 얼마로 잡느냐가 설계 판단**이다. N은 saga의 최대 완주 시간보다 커야 한다 — 그보다 짧으면 saga가 아직 진행 중인데 메일이 나가버린다. 반대로 너무 길면 사용자가 정상 케이스에서 알림을 늦게 받는다. 즉 **비가역 동작의 지연을 UX 비용으로 지불하고 보상 가능성을 사는 것**이다.

**(나) 한 번의 확정을 두 단계로 쪼갠다.** 외부 API가 "가승인(authorize) 후 확정(capture)" 형태를 지원하면, saga 중간에는 가승인만 하고 확정은 완주 시점에 한다. 가승인은 취소(void)가 가능하므로 보상이 성립한다. 카드 결제가 정확히 이 구조이고, 그래서 결제를 saga 중간에 둘 수 있는 것이다. 외부 시스템이 이 형태를 지원하지 않으면 협의해서 만들어야 하는 항목이다.

**(다) 비가역 동작을 saga 밖으로 뺀다.** 알림 발송을 saga의 한 단계로 넣지 말고, **saga 완주 이벤트를 구독하는 별도 컨슈머**가 처리하게 한다.

```text
[오케스트레이터] --완주 시 발행--> (order.completed)
                                        |
                                      구독
                                        v
                                  [알림 서비스]
                                  메일·푸시 발송

  발송은 saga가 이미 끝난 뒤에만 일어난다.
  -> 구조적으로 보상 대상이 아니다.
  -> 발송 실패는 saga의 문제가 아니라 알림 서비스 자체의 재시도 문제가 된다.
```

이것이 Kafka 문맥에서 가장 자연스러운 답이다. **완주 이벤트를 발행하고 후속 작업을 구독으로 떼어내면, "saga의 마지막 단계"조차 아니게 되므로 순서 배치를 고민할 필요 자체가 사라진다.** 07번 문서(`07-eventual-consistency-ux.md`)의 "늦어도 아무도 안 다치는 것만 이벤트로 뺀다"는 기준과 정확히 같은 판단이다.

### ⑤ 격리성이 없다 — 중간 상태가 노출된다

Saga의 각 단계는 즉시 커밋되므로, 다른 요청이 **아직 완주하지 못한 saga의 중간 상태를 읽고 행동할 수 있다.** 예를 들어 결제는 완료됐지만 재고 실패로 곧 취소될 주문을 다른 로직이 "결제 완료"로 보고 포인트를 적립해 버리는 식이다.

이것이 단일 트랜잭션과의 가장 큰 차이다. 단일 트랜잭션에서는 커밋 전까지 다른 트랜잭션이 중간 상태를 볼 수 없지만, saga에는 ACID의 **I(Isolation, 격리성)가 없다.**

대응은 **의미적 잠금(semantic lock)**이다. DB 락처럼 물리적으로 접근을 막는 것이 아니라, **데이터에 "아직 확정 아님" 표식을 붙여 확정처럼 취급되지 않게 하는** 기법이라 "의미적"이라고 부른다. 확정 전 상태를 `PENDING` 같은 명시적 상태로 표시하고, 다른 로직이 `PENDING`을 확정치로 취급하지 않게 한다. 확정 상태 전이는 saga 완료 시점에만 일어난다.

여기서 **같은 배치의 두 문서가 만난다.**

- `07-eventual-consistency-ux.md`의 "처리중 상태를 도메인에 넣는다"는 처방이 정확히 이것이다. 그 문서는 **사용자의 눈**에 중간 상태가 확정처럼 보이는 문제를 다루고, 이 절은 **다른 코드**가 중간 상태를 확정으로 오독하는 문제를 다룬다. 대상이 다를 뿐 처방은 하나다 — `PENDING`을 정식 도메인 상태로 만든다.
- `10-payment-consistency/10-distributed-saga-compensation-idempotency.md`의 2-6절은 여기서 한 걸음 더 나간다. 이용권을 지급 즉시 활성화하지 않고 `INACTIVE`로 넣어 두라는 것인데, 이유가 중요하다. 즉시 활성화하면 나중에 보상할 때 **이미 소비된 권리를 회수**해야 하고 그것은 불가능하다. `INACTIVE`로 두면 보상은 그냥 상태를 `REVOKED`로 바꾸는 일이 된다.

즉 **의미적 잠금은 격리성 부재의 대응이면서 동시에 ④의 "보상 불능"을 예방하는 장치이기도 하다.** 중간 상태를 감춰 두면, 그 사이 아무도 그것을 소비하지 못하므로 되돌릴 수 있는 상태가 유지된다. 두 논점이 하나의 설계로 만난다.

### ⑥ saga에도 실행 상태와 타임아웃이 필요하다

응답이 영원히 안 오는 단계가 있으면 saga는 미완주로 표류한다. 그런데 Kafka는 "이 커맨드가 처리됐는지"를 알려주지 않는다 — 발행은 성공했고, 소비 여부는 컨슈머 그룹의 오프셋에만 남으며, 처리 결과는 응답 이벤트가 와야 안다. 응답이 안 오면 **아무 일도 일어나지 않는 채로 조용히 멈춘다.**

그래서 saga 인스턴스별 상태(어느 단계까지 갔는지)를 저장소에 영속화하고, 단계별 타임아웃 초과 시 보상 또는 알림으로 전이시킨다.

```sql
CREATE TABLE saga_instance (
    saga_id     bigserial    PRIMARY KEY,
    order_id    bigint       NOT NULL UNIQUE,  -- 주문당 saga 1개를 DB가 보장
    step        varchar(30)  NOT NULL,
    retry_count int          NOT NULL DEFAULT 0,
    updated_at  timestamptz  NOT NULL DEFAULT now()
);
-- (step, updated_at) 인덱스는 "오래 멈춰 있는 saga" 스캔을 위한 것이다.
CREATE INDEX idx_saga_stuck ON saga_instance (step, updated_at);
```

```sql
-- 3분 이상 같은 단계에 머물러 있는 saga를 찾아 커맨드를 재전송한다.
-- 참여자가 ③대로 멱등하므로 "이미 처리됐는지" 확인할 필요 없이 그냥 다시 보낸다.
SELECT saga_id, order_id, step, retry_count
  FROM saga_instance
 WHERE step IN ('PAYMENT_REQUESTED', 'STOCK_REQUESTED', 'COMPENSATING')
   AND updated_at < now() - interval '3 minutes'
 ORDER BY updated_at
 LIMIT 200;
```

여기에 함정이 하나 있다. **"실패 응답"과 "무응답"은 다르다.** 명시적 실패 응답은 "확실히 안 됐다"는 사실이지만, 무응답은 **결과 불명**이다. 무응답을 실패로 간주해 보상을 태웠는데 뒤늦게 성공 응답이 도착할 수 있다.

```text
t0   STOCK_REQUESTED, 재고 차감 커맨드 발행
t1   재고 서비스는 실제로 차감을 완료 (응답 이벤트가 지연됨)
t2   타임아웃 -> COMPENSATING 전이, 결제 취소 커맨드 발행
t3   환불 완료 -> COMPENSATED
t4   뒤늦은 StockReserved 이벤트 도착
     -> 재고는 차감된 채인데 결제는 취소된 상태
```

그래서 **"성공 이벤트가 `COMPENSATING`/`COMPENSATED` 상태에 도착하는 경우"까지 상태 머신에 자리를 만들어** 추가 보상(재고 복원)을 태워야 한다. 늦게 도착한 이벤트에도 갈 곳을 마련해 두는 것이 교과서 saga와 실무 saga의 차이다.

orchestration이 유리한 이유 중 하나가 이 상태 관리가 자연스럽다는 점이다. choreography에서 같은 것을 하려면 "누가 타임아웃을 감시하는가"부터가 문제가 된다 — 각 서비스가 자기가 발행한 이벤트에 대한 응답을 스스로 감시해야 하고, 그 감시 로직이 서비스마다 흩어진다.

## 4. 꼬리질문 대비 포인트

### "choreography에서 전체 흐름이 안 보이는 문제는 어떻게 보완하나요?"

correlation ID(sagaId)를 모든 이벤트에 실어 분산 추적으로 한 saga의 여정을 조회 가능하게 하고, 이벤트 스키마·구독 관계를 문서나 카탈로그로 관리한다. Kafka 환경이라면 컨슈머 그룹 목록으로 "이 토픽을 누가 구독하는가"를 역추적하는 운영 절차까지 갖춰 둔다(2-5 (2)).

다만 **이는 관측을 돕는 것이지 흐름을 한곳에 모으지는 못한다.** 흐름은 여전히 런타임 구독 관계에만 존재하고, 추적 도구는 "이미 일어난 일"을 보여줄 뿐 "앞으로 어떻게 흘러갈지"를 보여주지 못한다.

그래서 분기·보상 조합이 계속 늘어나면 **orchestration으로 전환하는 것이 정답인 시점이 온다.** "보완하다가 한계가 오면 패턴을 바꾼다"까지 말하는 것이 균형 잡힌 답이다.

결정적인 반론을 하나 더 얹으면 좋다. **choreography에서 흐름 추적을 제대로 하려면 모든 이벤트를 모아 여정을 재구성하는 저장소를 따로 지어야 하는데, 그게 사실상의 오케스트레이터다.** 결합도를 줄인 대신 관측 인프라를 하나 더 짓게 되는 셈이다.

### "오케스트레이터가 죽으면 saga는 어떻게 되나요?"

답의 뼈대는 **"상태가 어디에 있었느냐"**로 갈린다.

**상태가 메모리에만 있었다면 흐름이 그대로 사라진다.** "결제까지는 했고 재고에서 실패했다"는 사실이 프로세스와 함께 소멸하므로, 누구도 이어받을 수 없다. 표류하는 saga는 아무 로그도 남기지 않고 그냥 멈춰 있다 — 사용자는 돈만 나간 채 물건을 못 받고, 우리는 그런 건이 몇 개인지조차 모른다. **재배포 한 번에 표류 saga를 양산하는 구조**다.

**상태가 DB에 있으면 다른 인스턴스가 테이블을 보고 이어받는다.** 오케스트레이터 자체는 무상태로 만들고 saga 상태만 영속화하는 것이 전제다. 각 단계 전이를 상태 저장과 함께 커밋해 두면, 재기동 후 미완주 saga를 읽어 이어서 진행하거나 타임아웃 보상으로 전이할 수 있다(⑥의 스캔 쿼리).

**이것이 saga 상태를 영속화하는 이유다.** "상태를 DB에 넣는다"는 것이 단순한 저장이 아니라 **"이 흐름의 소유권을 프로세스에서 떼어내 DB로 옮긴다"**는 뜻임을 말할 수 있어야 한다. 소유권이 DB에 있으면 프로세스는 대체 가능한 일꾼이 되고, 몇 대가 죽든 남은 인스턴스나 스케줄러가 대장을 보고 일을 이어간다.

여기에 두 가지를 덧붙이면 답이 완성된다.

**(1) 커맨드 발행과 상태 저장의 원자성은 결국 outbox 패턴으로 푼다**(2-5 (3)). 상태만 저장하고 커맨드 발행 직전에 죽으면 saga는 여전히 멈추기 때문에, 영속화만으로는 부족하고 둘을 한 트랜잭션에 묶어야 한다. (가산점 포인트)

**(2) 이어받은 인스턴스는 "커맨드가 이미 처리됐는지" 확인하지 않고 그냥 재전송한다.** 참여자가 멱등하므로 이미 처리됐으면 "처리됨" 성공 응답이 다시 오고, 미처리였으면 이번에 처리된다. 어느 쪽이든 saga는 전진한다. 확인 후 분기하는 방식보다 상태 공간이 훨씬 작다.

### "2PC를 쓰면 안 되는 건가요? Saga가 항상 우월한가요?" (시니어 변별 포인트)

항상은 아니다.

Saga는 **원자성과 격리성을 포기하는 대가로 가용성과 낮은 결합을 얻는 선택**이다 — 중간 상태 노출, 보상 로직 개발·테스트 비용, 운영 복잡도(표류 saga 추적)가 전부 청구서로 돌아온다. 여기에 Kafka 위에서는 아웃박스, 릴레이, 멱등 처리 테이블, 타임아웃 스캐너까지 딸려 온다.

그래서 순서를 밝히는 것이 중요하다. **분산 트랜잭션이 필요 없게 서비스 경계를 다시 긋는 것이 첫 번째 답이다.** 참여자가 모두 같은 DB라면 그냥 로컬 트랜잭션 하나로 묶는 게 정답이고, 그게 saga보다 백 배 단순하다. 실제로 "마이크로서비스로 쪼갰더니 saga가 필요해졌다"는 상황의 상당수는 경계를 잘못 그은 결과다 — 한 트랜잭션으로 묶여야 하는 데이터는 대체로 같은 서비스에 있어야 한다.

그리고 강한 정합성이 필수인데 참여자가 XA를 지원하는 폐쇄적 환경이면 **2PC도 선택지다.** 사내 시스템 몇 대가 전부 같은 벤더의 DB를 쓰는 경우 같은 상황이다.

**"서비스가 분리돼 있고, 중간 상태를 도메인이 허용할 수 있을 때 saga를 쓴다"**는 적용 조건을 말하는 것이 해법 나열보다 중요하다. 특히 뒷부분 — 중간 상태를 도메인이 허용할 수 있어야 한다는 조건 — 이 ⑤와 이어진다.

### "보상 트랜잭션과 재시도는 어떻게 구분해서 쓰나요?"

**실패의 종류로 가른다.**

- **일시적 실패**(타임아웃, 커넥션 끊김, 상대 서비스 배포 중 5xx)는 **재시도**로 같은 방향을 계속 민다. 조건이 달라지면 성공할 수 있는 실패이기 때문이다.
- **비즈니스적 거절**(품절, 한도 초과, 자격 미달)은 재시도해도 결과가 같으므로 **보상**으로 방향을 뒤집는다.

이 구분이 없으면 두 방향으로 사고가 난다. 품절을 무한 재시도하며 파티션을 막거나, 순간 타임아웃에 멀쩡한 결제를 환불한다. 후자가 특히 아프다 — 결제는 성사됐는데 우리가 오판해서 환불한 것이므로, 사용자는 물건도 못 받고 우리는 수수료만 잃는다.

Kafka 컨슈머에서는 이 구분이 **예외 타입 설계**로 나타난다. 재시도 가능한 실패는 예외를 던져 컨슈머의 재시도·DLQ 경로를 타게 하고, 비즈니스적 거절은 예외가 아니라 **실패 응답 이벤트를 정상 발행**해 오케스트레이터가 보상 전이를 하게 한다. 비즈니스 거절을 예외로 던지면 컨슈머가 무한 재시도에 빠진다.

마지막으로 ④와 연결하면 좋다. **피벗 이후 단계는 보상이 없으므로, 재시도 가능한 실패만 오도록 설계돼 있어야 한다.** 즉 "재시도 vs 보상" 구분은 단계 배치를 정할 때 이미 반영돼야 하는 판단이지, 런타임에 그때그때 정하는 것이 아니다.

## 한 줄 요약

Saga는 분산 트랜잭션 대신 "로컬 트랜잭션의 연쇄 + 실패 시 역순 보상"으로 가는 패턴이고 — 흐름이 단순하면 이벤트 구독(choreography, 안무), 복잡하면 중앙 지휘(orchestration)를 택하되, Kafka 위에서는 커맨드 발행을 아웃박스로 묶고 sagaId를 파티션 키로 써서 단계 순서를 지키며 — 보상은 rollback이 아닌 새 비즈니스 행위라서 **보상의 실패·중복(보상도 at-least-once로 온다)·불가능(비가역 단계는 맨 뒤로, 안 되면 가역 형태로 바꾸거나 saga 밖으로)까지 설계해야 비로소 완성된다.**
