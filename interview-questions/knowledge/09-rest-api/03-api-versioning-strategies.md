# API 버저닝 전략 — URI vs 헤더, "미래의 변경"을 지금 설계하는 일

> 핵심 관전 포인트: **버저닝을 말하려면 먼저 "언제 버전을 올리는가"의 기준인 **파괴적 변경(breaking change)** — 기존 클라이언트 코드를 한 줄도 고치지 않은 채로 새 서버와 통신했을 때 동작이 깨지는 변경 — 을 정의해야 한다. 응답에 필드를 더하는 것이 안전한 이유는 대부분의 JSON 역직렬화기가 모르는 필드를 그냥 무시하기 때문이고, 필드를 빼는 것이 위험한 이유는 있어야 할 값이 사라지면 그 자리에서 NPE나 파싱 실패로 죽기 때문이다 — 즉 안전/위험의 근거는 서버가 아니라 **소비자 쪽 파서의 동작**에 있다. 이 파괴적 변경을 흡수하는 방법이 "기존 계약(v1)은 그대로 두고 새 계약(v2)을 나란히 제공"하는 버저닝이고, 버전을 요청의 어디에 적느냐에 따라 경로·헤더·쿼리 세 방식으로 갈린다. URI 방식(`/v1/orders`)이 캐시·로그·라우팅에 유리한 이유는 명확하다 — HTTP 캐시의 기본 키가 메서드+URL이고 프록시·CDN·게이트웨이는 애초에 경로를 보고 판단하는 장비라서, 버전이 경로에 있으면 그 장비들이 우리 앱을 전혀 몰라도 버전을 구분할 수 있다. 헤더 방식(`Accept: application/vnd.myapp.v2+json`)은 HTTP의 콘텐츠 협상 — 클라이언트가 "나는 이런 형태의 표현을 원한다"고 말하고 서버가 그중 하나를 골라 주는 기본 장치 — 를 버전 선택에 재사용하는 것이라 URI가 순수하게 유지되지만, 브라우저 주소창으로 테스트할 수 없고 캐시가 `Vary: Accept`를 정확히 다뤄야 버전 섞임 사고를 피한다. 그리고 진짜 난도는 만드는 쪽이 아니라 없애는 쪽에 있다 — v2 출시 → `Deprecation` 헤더 고지 → 버전별 사용량 계측 → `Sunset` 헤더로 종료 일시 확정 → brownout(짧게 일부러 끊어 남은 소비자를 깨우는 리허설) → 410 Gone 종료라는 폐기 타임라인과 그 근거가 되는 사전 계약이 v2를 낼 때 함께 준비돼 있어야 한다. 최고의 버저닝은 하위 호환 변경만으로 진화시켜 **버전을 올릴 일 자체를 줄이는 것**이다.**

---

## 0. 질문 + 의도

**질문**: "API 버저닝 전략(URI, 헤더)의 장단점은?"

**출제 의도**: 버저닝은 "미래의 변경"을 지금 설계하는 일이다. 전략 없이 시작한 API가 v2를 내야 할 때 겪는 고통을 아는지 — 미래 비용을 앞당겨 사고하는 습관을 본다. 방식 비교 암기가 아니라, 왜 버전이 필요해지고 어떻게 하면 덜 필요해지는지까지 말하는 후보자가 변별된다.

## 1. 왜 버저닝인가 — 내 배포가 남의 앱을 깨는 구조

### 1-1. 전제 — 서버와 클라이언트는 같이 배포되지 않는다

사내 서비스를 혼자 만들 때는 API를 바꾸는 일이 어렵지 않다. 서버를 고치고 클라이언트를 고쳐 같이 배포하면 끝이다. 버저닝이 문제가 되는 지점은 **그 "같이"가 성립하지 않는 순간**이다.

API는 배포하는 순간 소비자(모바일 앱, 파트너사, 타 팀)와의 **계약**이 된다. 문제는 소비자를 내가 통제할 수 없다는 것 — 특히 모바일 앱은 사용자가 업데이트를 안 하면 **1년 전 버전이 여전히 살아서 내 API를 호출한다.**

그러니까 어느 시점의 실제 상황은 이렇게 생겼다.

```text
                        [ 오늘의 서버 (한 벌) ]
                                 ▲
        ┌────────────┬───────────┼───────────┬─────────────┐
        │            │           │           │             │
   웹 프론트     iOS 최신판   iOS 8개월 전판  안드 1년 전판  파트너사 배치
   (내일 배포)   (심사 통과)  (업데이트 안 함) (업데이트 안 함) (담당자 퇴사)
        │            │           │           │             │
     통제 가능     통제 가능    통제 불가     통제 불가      연락도 안 됨
```

서버는 한 벌인데 그 서버와 대화하는 클라이언트는 **여러 세대가 동시에 살아 있다.** 그리고 오른쪽으로 갈수록 내가 손댈 수 없다. 이 그림이 버저닝이라는 주제의 전제 전부다.

여기서 이 문제의 고약한 성질이 나온다. **깨지는 것은 내 서비스가 아니라 남의 서비스다.** 내 대시보드에는 5xx가 안 찍히고, 파트너사 CS나 앱스토어 리뷰로 며칠 뒤에 돌아온다. 내가 즉시 알아채는 장애보다 오히려 위험한 이유다.

### 1-2. 파괴적 변경(breaking change)이란 정확히 무엇인가

이 문서 전체가 "언제 버전을 올리는가"를 다루는데, 그 판단 기준을 먼저 정의하지 않으면 나머지가 전부 감으로 흐른다.

**파괴적 변경(breaking change)이란, 기존 클라이언트가 자기 코드를 한 줄도 고치지 않은 채 새 서버와 통신했을 때 동작이 깨지는 변경이다.** 이름 그대로 "무언가를 깨뜨리는(breaking) 변경"인데, 깨지는 대상이 **내 서버가 아니라 남의 클라이언트**라는 점이 핵심이다. 반대로 소비자가 아무것도 모른 채 그대로 돌아가면 **하위 호환 변경(non-breaking)**이다.

- **하위 호환 변경(non-breaking)**: 응답에 필드 추가, 새 엔드포인트 추가, 선택적 요청 파라미터 추가. → 기존 클라이언트는 모르는 필드를 무시하면 되므로 **버전 없이 그냥 배포한다.**
- **파괴적 변경(breaking)**: 필드 삭제/이름 변경/타입 변경, 필수 파라미터 추가, URL 구조 변경, 에러 포맷 변경. → 기존 클라이언트가 즉시 깨진다. **이때가 버저닝이 필요한 순간이다.**

### 1-3. 왜 추가는 안전하고 삭제는 위험한가 — 근거는 소비자 쪽 파서에 있다

위 분류를 외우지 말고 근거를 이해해야 응용이 된다. 근거는 서버가 아니라 **클라이언트의 JSON 파서가 모르는 필드와 없는 필드를 각각 어떻게 다루는가**에 있다.

**모르는 필드가 하나 더 왔을 때**, 대부분의 역직렬화기는 그냥 버린다. Java의 Jackson으로 `{"id":1,"name":"김","tier":"GOLD"}`를 `record OrderDto(Long id, String name)`으로 읽으면 `tier`는 매핑할 자리가 없으므로 무시된다. 그래서 **응답 필드 추가는 소비자가 아무것도 안 해도 통과한다.**

한 가지 단서는 붙는다. Jackson 자체의 기본값은 모르는 필드를 만나면 예외를 던지는 쪽(`DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES`가 켜짐)이고, Spring Boot가 자동 구성하는 `ObjectMapper`에서 그 옵션을 꺼 주기 때문에 무시가 기본처럼 보이는 것이다. 즉 "추가는 안전"은 **소비자가 관대한 파싱을 한다는 규약 위에서만** 성립한다. 그래서 API 문서에 "모르는 필드가 오면 무시하라"를 명시적으로 적어 두는 것이 계약의 일부다(이 규약을 **tolerant reader**, 관대한 읽기 쪽이라고 부른다).

**있어야 할 필드가 사라졌을 때**는 이야기가 다르다. 없는 필드는 무시할 수 없다 — 그 자리를 채울 값이 없기 때문이다. 언어마다 죽는 방식이 다를 뿐 전부 죽는다.

```java
// 서버가 응답에서 discountAmount 를 제거했다. 클라이언트 코드는 그대로다.

// ① Java 참조 타입: 값이 null 로 들어오고, 쓰는 순간 NullPointerException
Integer discount = res.getDiscountAmount();   // null
int total = price - discount;                 // 언박싱하는 이 줄에서 NPE

// ② Java 기본 타입: 예외는 없지만 0 이 들어가 조용히 금액이 틀어진다 (더 나쁘다)
int discount2 = res.getDiscountAmount();      // 0 — 아무도 모르는 계산 오류

// ③ Kotlin 의 non-null 타입, Swift 의 Codable 비옵셔널:
//    필드가 없으면 역직렬화 단계에서 실패한다 — 응답 전체를 못 읽는다
```

정리하면 이렇다. **모르는 필드는 버릴 수 있지만, 없는 필드는 만들어 낼 수 없다.** 이 비대칭이 "추가는 자유, 삭제는 버전 인상 또는 긴 폐기 절차"라는 규칙의 전부다.

변경 종류별 판정표와 "깨야만 할 때"의 expand → migrate → contract 절차는 이 장의 짝 문서인 [08-backward-compatible-api-changes.md](08-backward-compatible-api-changes.md)가 본격적으로 다룬다. 이 문서는 **그 판정에서 "파괴적"이 나왔을 때 어떤 장치로 흡수하는가**에 집중한다.

### 1-4. 버저닝은 파괴적 변경을 "나란히 두기"로 흡수한다

파괴적 변경을 배포해야 하는데 소비자를 통제할 수 없다면, 남은 방법은 하나뿐이다. **기존 계약을 그대로 살려 둔 채 새 계약을 그 옆에 하나 더 세우는 것.**

버저닝은 정확히 그 장치다. v1은 어제와 똑같이 동작하고, 준비된 소비자만 v2로 옮겨 온다. 옮겨 오는 시점은 소비자가 자기 사정에 맞춰 정한다.

비유하면 **도로를 폐쇄하고 새로 까는 게 아니라, 새 도로를 옆에 놓고 기존 도로는 안내판을 붙여 서서히 폐쇄하는 것**이다. 이 비유에서 "안내판"과 "서서히"에 해당하는 것이 3절의 폐기 정책이고, 그쪽이 실제로 더 어렵다.

## 2. 전략별 장단점 — URI, 헤더, 쿼리 파라미터

### 2-1. 세 방식이 갈리는 자리 — 버전을 요청의 어디에 적을 것인가

방식을 세 개 외우기 전에, 왜 선택지가 하필 그 셋인지를 먼저 보면 비교가 쉬워진다.

HTTP 요청은 크게 세 부분으로 되어 있다. **요청 라인**(메서드 + 경로 + 쿼리 문자열), **헤더**, **본문**이다. 버전이라는 정보를 서버에 전달하려면 이 셋 중 어딘가에 적는 수밖에 없다.

```text
GET /v1/orders/42?fields=id,total HTTP/1.1     ← ① 경로   ② 쿼리 문자열
Host: api.example.com
Accept: application/vnd.myapp.v2+json          ← ③ 헤더
X-API-Version: 2                               ← ③ 헤더 (커스텀)

(본문)                                          ← 조회 요청에는 없다
```

본문은 후보에서 빠진다. 목록·상세 조회는 `GET`이고 `GET` 요청에 본문을 싣는 것은 사실상 통하지 않기 때문이다. 그래서 남는 자리가 **경로 / 쿼리 / 헤더** 셋이고, 그것이 그대로 세 가지 버저닝 방식이 된다.

여기서 방향을 하나 잡아두면 뒤의 장단점이 전부 따라 나온다. **경로와 쿼리는 URL의 일부라서 중간 장비가 그냥 볼 수 있고, 헤더는 URL 바깥이라 중간 장비가 따로 읽어 줘야 한다.**

### 2-2. URI 경로 버저닝 — `/v1/orders`

```http
GET /v1/orders/42
GET /v2/orders/42
```

**장점**

- **명시적이고 눈에 보인다**: URL만 봐도 어떤 계약인지 안다. 브라우저·curl로 바로 테스트되고, 접근 로그만으로 "v1을 아직 누가 쓰는지" 집계할 수 있다 — **폐기(deprecation) 운영이 쉬워진다.**
- **라우팅이 쉽다**: 게이트웨이/로드밸런서가 경로 prefix만 보고 v1은 구서버, v2는 신서버로 보내는 식의 분리 배포가 간단하다.
- **캐시 친화적**: URL이 다르면 다른 캐시 키다. 중간 캐시(CDN 포함)가 버전을 섞어 응답할 위험이 없다.

여기서 앞의 두 장점("캐시·로그·라우팅에 유리하다")이 **왜** 성립하는지가 이 방식을 고르는 실제 근거이므로 한 겹 더 들어가자. 근거는 하나로 모인다 — **URL은 우리 애플리케이션 바깥의 장비들도 이미 읽고 있는 값이라는 것.**

**캐시부터.** HTTP 캐시가 저장된 사본을 찾을 때 쓰는 기본 키는 **요청 메서드 + URL**이다. 즉 URL이 다르면 캐시 입장에서는 애초에 다른 물건이고, 별도 설정 없이 v1 응답과 v2 응답이 서로 다른 칸에 들어간다. 반대로 URL이 같으면 캐시는 둘을 같은 물건으로 보고, 뒤에 오는 사람에게 앞사람의 버전을 그대로 내줄 수 있다.

**라우팅도 같은 이유다.** 프록시·CDN·API 게이트웨이는 원래부터 **경로를 보고 목적지를 정하는 장비**다. 버전이 경로에 있으면 이 장비들이 우리 애플리케이션 코드를 전혀 몰라도 버전을 구분할 수 있다.

```nginx
# 게이트웨이가 우리 앱의 도메인 로직을 하나도 모른 채로 버전을 분리한다.
# 아는 것은 "경로 앞부분이 /v1 이냐 /v2 이냐" 뿐이다.
location /v1/ { proxy_pass http://orders-v1-pool; }   # 유지보수만 하는 구버전 풀
location /v2/ { proxy_pass http://orders-v2-pool; }   # 신규 배포가 나가는 신버전 풀
```

이 분리가 실제로 값을 하는 순간은 배포 사고 때다. v2 배포가 잘못돼도 **v1 풀은 건드리지 않았으므로 구버전 앱 사용자에게는 아무 일도 일어나지 않는다.** 버전이 헤더에만 있으면 두 버전이 같은 프로세스 안에서 분기되므로 이런 물리적 격리가 불가능하다.

**로그도 같다.** 액세스 로그는 기본적으로 요청 라인(메서드 + URL)을 남긴다. 그래서 아무 설정도 하지 않은 상태에서 이미 버전별 호출량 집계가 가능하다.

```text
# 어느 웹서버·CDN이든 기본 액세스 로그에 이미 들어 있는 값만으로 집계가 된다
10.0.3.11 - - [01/Sep/2026:10:22:03] "GET /v1/orders/42 HTTP/1.1" 200
10.0.3.42 - - [01/Sep/2026:10:22:04] "GET /v2/orders/42 HTTP/1.1" 200
                    ↑ 여기 v1/v2 가 이미 찍혀 있다 → 3절의 "잔여 호출자 집계"가 공짜
```

**단점**

- **"같은 자원인데 URI가 두 개"**: REST 관점에서 URI는 자원의 식별자인데, 42번 주문이 `/v1/orders/42`와 `/v2/orders/42` 두 정체성을 갖게 된다. 자원을 가리켜 저장해둔 링크가 버전에 묶인다.
- 버전이 계약 전체에 걸리므로, 한 리소스만 바뀌어도 **v2로 전체 표면적이 복제**되는 경향이 생긴다(코드/문서 유지 비용).

### 2-3. 헤더 버저닝 — 콘텐츠 협상을 버전 선택에 재사용한다

```http
# 미디어 타입(콘텐츠 협상) 방식
GET /orders/42
Accept: application/vnd.myapp.v2+json

# 커스텀 헤더 방식
GET /orders/42
X-API-Version: 2
```

#### 먼저 콘텐츠 협상(content negotiation)이 무엇인가

이 방식을 "정석"이라고 부르는 근거가 콘텐츠 협상인데, 정작 그게 뭔지 모르면 근거가 근거로 들리지 않는다. 먼저 정의하고 가자.

**콘텐츠 협상은 클라이언트가 요청 헤더로 "나는 이런 형태의 표현을 원한다"고 말하고, 서버가 자기가 낼 수 있는 표현 중 하나를 골라 응답하는 HTTP의 기본 장치다.** "협상"이라는 이름은 한쪽이 일방적으로 정하는 게 아니라 클라이언트의 희망과 서버의 능력을 맞춰 본다는 뜻이다.

전제로 용어 하나가 필요하다. HTTP에는 **자원(resource)**과 **표현(representation)**이라는 구분이 있다. 자원은 "42번 주문"이라는 대상 자체이고, 표현은 그 대상을 실제 바이트로 옮긴 결과 — JSON일 수도, XML일 수도, 한국어일 수도, 영어일 수도 있다. **자원 하나에 표현은 여럿일 수 있다**는 것이 콘텐츠 협상의 출발점이다.

이미 매일 쓰고 있는 장치이기도 하다.

| 요청 헤더 | 클라이언트가 말하는 것 | 서버가 고르는 것 |
|---|---|---|
| `Accept: application/json` | "JSON으로 주세요" | 표현의 **형식** |
| `Accept-Language: ko-KR` | "한국어로 주세요" | 표현의 **언어** |
| `Accept-Encoding: gzip` | "압축해서 보내도 됩니다" | 표현의 **인코딩** |

**미디어 타입 버저닝은 이 장치를 버전 선택에 그대로 재사용하는 것이다.** "JSON 형식의 표현을 주세요"라고 말할 수 있다면 "v2 형식의 표현을 주세요"라고도 말할 수 있지 않겠느냐는 발상이다. 42번 주문이라는 **자원은 하나이고, v1 응답과 v2 응답은 그 자원의 서로 다른 표현**이라고 보면 개념이 딱 맞아떨어진다. URI는 자원을 가리키고 헤더는 표현을 고른다 — 이것이 "정석"이라고 불리는 이유다.

미디어 타입 문자열도 뜯어보면 규칙이 있다.

```text
application / vnd.myapp.v2 + json
     │            │    │       │
     │            │    │       └─ 구조 접미사: "실제 문법은 JSON이다"
     │            │    │           → 표준 JSON 파서로 그냥 읽을 수 있다는 신호
     │            │    └─ 버전
     │            └─ vnd = vendor(공급자). "이 조직이 자기 용도로 정의한 타입"이라는 표준 접두사
     └─ 최상위 타입
```

#### 장점

- **URI가 순수하게 유지된다**: 자원의 식별자(URI)와 표현의 버전(헤더)이 분리된다 — HTTP의 콘텐츠 협상(content negotiation) 메커니즘을 정석대로 쓰는 방식.
- 자원을 가리키는 링크가 버전과 무관하게 안정적이다. 채팅으로 공유한 `/orders/42`가 몇 년 뒤에도 유효하다.

#### 단점

- **눈에 안 보인다**: 브라우저 주소창으로 테스트 불가, curl에 헤더를 매번 붙여야 하고, 장애 조사 때 접근 로그의 URL만으로는 어떤 버전이 호출됐는지 모른다(헤더 로깅을 별도로 심어야 한다).
- **캐시가 까다롭다**: 같은 URL에 버전별로 다른 응답이 나가므로 중간 캐시에 `Vary: Accept` 같은 지시를 정확히 줘야 하고, 이를 무시하는 캐시 계층이 있으면 **버전이 섞인 응답 사고**가 난다.
- 파트너사 개발자 온보딩 비용이 크다 — "헤더 빼먹음"이 흔한 문의 유형이 된다.

#### `Vary`가 무엇이고 왜 여기서 필수인가

두 번째 단점이 이 방식의 실질적인 위험이므로 장치까지 짚어 두자.

앞에서 본 대로 캐시의 기본 키는 **메서드 + URL**이다. 그런데 헤더 버저닝에서는 URL이 `/orders/42` 하나뿐이고 응답만 v1·v2로 갈린다. 캐시 입장에서는 **같은 물건인데 내용이 두 가지**인 상황이다.

**`Vary`는 서버가 캐시에게 "이 응답은 URL만으로 식별하지 마라. 다음 요청 헤더의 값도 캐시 키에 포함시켜라"라고 알려주는 응답 헤더다.** 이름 그대로 "이 헤더 값에 따라 응답이 달라진다(vary)"는 선언이다.

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.myapp.v2+json
Vary: Accept
# 캐시 키 = (GET, /orders/42, Accept 헤더 값)
# → v1 을 요청한 사람과 v2 를 요청한 사람이 서로 다른 칸에 저장된다
```

빠뜨리면 나는 사고는 구체적이다.

```text
t=0  구버전 앱(A)이 Accept: ...v1+json 으로 /orders/42 요청
     캐시에 없음 → 오리진 호출 → v1 응답을 받아 저장
     Vary 가 없으므로 캐시 키 = (GET, /orders/42)  ← 버전이 키에 없다

t=1  신버전 앱(B)이 Accept: ...v2+json 으로 같은 URL 요청
     캐시: "키가 같네" → 저장해 둔 v1 응답을 그대로 내준다
     B 는 v2 스키마를 기대하고 파싱하다 실패한다
     → 오리진에는 아무 로그도 안 남는다. 캐시가 응답했으니까.
```

여기서 재현이 안 되는 버그의 조건이 다 갖춰진다. **오리진에는 흔적이 없고, 캐시 사본이 만료되면 저절로 사라진다.** URI 버저닝에서는 이 사고가 구조적으로 불가능하다는 점이 앞 절 "캐시 친화적"의 실제 의미다.

### 2-4. 쿼리 파라미터 버저닝 — `/orders/42?version=2`

URI 방식과 헤더 방식의 중간이다. URL의 일부라서 눈에 보이고 테스트가 쉽지만, "버전 파라미터를 빠뜨리면 어느 버전인가"라는 기본값 문제가 있고 자원 식별과 표현 선택이 뒤섞여 어느 쪽 장점도 온전히 갖지 못한다.

기본값 문제를 조금 더 보면 왜 애매한지 드러난다. `?version=`이 없는 요청에 v1을 주면 **무버전 URL이 사실상 영구적인 v1 별칭**이 되어 4절 마지막 질문과 같은 상황이 되고, 최신 버전을 주면 **파라미터를 빠뜨린 구버전 클라이언트가 어느 날 갑자기 깨진다.** 어느 쪽도 좋지 않다.

캐시 관점에서도 어중간하다. 쿼리 문자열은 URL의 일부이므로 원칙적으로 캐시 키에 포함되지만, 중간 장비에 따라 특정 쿼리 파라미터를 캐시 키에서 제외하도록 설정돼 있는 경우가 있어(추적용 파라미터를 제거하려는 흔한 설정) URI 방식만큼 안심할 수 없다. 실무에서는 앞의 두 방식보다 드물다.

### 2-5. 비교 요약과 실무 선택

| 기준 | URI 방식 | 헤더 방식 |
|---|---|---|
| 가시성(테스트·로그·디버깅) | 좋음 — 액세스 로그에 이미 찍힘 | 나쁨 (별도 로깅 필요) |
| 라우팅/배포 분리 | 쉬움 — 경로 prefix로 풀 분리 | 게이트웨이가 헤더 해석 필요 |
| 캐시 안전성 | 좋음 (URL=캐시 키) | `Vary` 관리 필요 — 실패 시 버전 섞임 |
| REST 순수성(자원 식별) | 어색함 (자원 URI가 버전에 묶임) | 좋음 |
| 소비자 사용 난이도 | 낮음 | 높음 (헤더 누락 문의) |

**실무 선택**: 외부에 공개하거나 파트너가 소비하는 API는 대부분 **URI 방식**을 택한다 — 이론적 순수성보다 가시성·운영 편의·소비자 접근성이 주는 이득이 크기 때문이다. "정답은 URI"가 아니라 "소비자가 누구이고 운영에서 무엇이 중요한지로 고른다"고 말하는 것이 핵심이다.

판단 기준을 한 문장으로 정리하면 이렇다. **소비자를 통제할 수 없을수록 URI 방식으로 기운다.** 소비자를 통제할 수 없다는 것은 곧 폐기 운영이 어렵다는 뜻이고, 폐기 운영의 재료가 되는 "누가 아직 v1을 쓰는가"를 URI 방식은 공짜로 준다.

## 3. 실무 운영 — 버전은 만드는 것보다 없애는 게 어렵다

### 3-1. v1이 안 죽는 세 가지 이유

전략 없이 시작한 API가 v2를 내야 할 때 겪는 고통은 대략 이렇다.

1. v2를 냈지만 v1 트래픽이 줄지 않는다 — 어떤 클라이언트가 v1을 쓰는지 **집계 수단이 없다.**
2. v1·v2 두 벌의 코드/문서/테스트를 무기한 유지한다 — 버그를 두 번 고친다.
3. v1을 내리자 업데이트 안 한 구버전 앱과 연락 안 되는 파트너사가 깨진다 — 장애 문의로 되돌아온다.

세 항목이 각각 별개의 실패처럼 보이지만 원인은 하나다. **v2를 낼 때 "언제 어떤 근거로 v1을 내릴 것인가"를 같이 정하지 않았다는 것.** 그 순간부터 v1 종료는 기술 문제가 아니라 매번 새로 해야 하는 협상이 되고, 협상은 대체로 미뤄진다.

그래서 버저닝 전략에는 **폐기 정책이 함께 설계**되어야 한다.

- **버전별 사용량 계측**: 처음부터 버전·클라이언트 식별자별 호출량을 대시보드로 본다. "v1 잔여 호출자 톱10"을 뽑을 수 있어야 폐기가 가능하다.
- **폐기 공지 체계**: 문서·공지에 더해 응답 헤더로 기계가 읽을 수 있는 신호(`Deprecation`, `Sunset` 헤더)를 실어준다. (가산점 포인트)
- **지원 버전 수 상한**: "동시 지원은 최대 2개 버전, 신버전 공개 후 N개월 뒤 구버전 종료" 같은 규칙을 계약(문서)에 미리 명시한다 — 폐기 근거를 사후 협상이 아니라 사전 계약으로 만든다.

### 3-2. 폐기 타임라인 — 종료는 이벤트가 아니라 절차다

말로만 하면 "공지하고 내린다"로 뭉개지므로 시간축에 놓고 보자. 아래는 신버전 공개 후 6개월 뒤 종료를 계약해 둔 경우의 표준 진행이다.

```text
[T+0개월] v2 공개 — v1 과 v2 를 나란히 운영 시작
   │        ▸ 이 시점에 종료 예정일을 문서에 못 박는다 (사후 협상 → 사전 계약)
   │        ▸ v1 응답에 Deprecation 헤더를 붙이기 시작 (기계가 읽는 고지)
   ▼
[T+1개월] 사용량 계측 — 버전 × 클라이언트 식별자별 호출량 대시보드
   │        ▸ "v1 잔여 호출자 톱10" 이 나와야 다음 단계로 갈 수 있다
   │        ▸ 여기서 트래픽의 정체가 안 보이면 이후 절차가 전부 막힌다
   ▼
[T+3개월] Sunset 헤더로 종료 일시를 확정 고지 + 상위 호출자에게 개별 연락
   │        ▸ 자동 고지(헤더)와 사람 대 사람 연락은 둘 다 필요하다
   ▼
[T+5개월] brownout ① — 종료 4주 전, 평일 낮 5분간 v1 을 410 으로 응답
   │        ▸ 공지를 아무도 안 읽은 소비자를 "가벼운 장애"로 깨우는 절차
   │        ▸ 여기서 처음 문의가 들어오는 소비자가 반드시 나온다
   ▼
[T+5.5개월] brownout ② — 종료 3일 전, 1시간
   │        ▸ 1차 후에도 트래픽이 남아 있으면 강도를 올린다
   ▼
[T+6개월] v1 종료 — 410 Gone 고정 응답으로 전환 (404 가 아니다)
   │        ▸ 라우팅은 살려둔 채 응답만 바꾼다 → 되돌리기가 즉시 가능
   ▼
[T+9개월] v1 코드·라우팅·문서 제거
            ▸ 되돌릴 일이 없다고 확인된 뒤에 지운다
```

이 타임라인에서 눈여겨볼 설계가 둘이다.

**첫째, 종료를 두 단계로 쪼갰다.** T+6개월의 "410 응답으로 전환"과 T+9개월의 "코드 제거"는 다른 일이다. 앞 단계는 설정 한 줄로 되돌릴 수 있지만 뒤 단계는 되돌리려면 배포가 필요하다. **되돌리기 비용이 다른 두 작업을 같은 날 하지 않는 것**이 운영의 기본기다.

**둘째, 404가 아니라 410을 쓴다.** 404 Not Found는 "그런 거 없다"라서 경로를 잘못 썼는지 API가 없어졌는지 구분이 안 된다. **410 Gone은 "여기 있었는데 의도적으로 없앴고 다시 안 돌아온다"**는 뜻이라, 받는 쪽이 즉시 원인을 안다. 본문에 대체 경로와 문서 링크를 담아 주면 더 좋다.

### 3-3. `Deprecation`과 `Sunset` — 기계가 읽는 폐기 고지

블로그 공지와 이메일은 사람이 읽어야 도달한다. 그런데 3-1의 세 번째 실패 — "연락 안 되는 파트너사" — 는 정확히 **사람이 안 읽는 경로**에서 터진다. 그래서 응답 자체에 폐기 정보를 실어 소비자의 **코드나 모니터링이** 읽을 수 있게 만드는 표준 헤더가 있다.

**`Deprecation` 헤더는 "이 엔드포인트가 언제부로 폐기(deprecated)됐는가"를 담는다.** 폐기됐다는 것은 아직 동작하지만 더는 권장되지 않고 곧 없어진다는 뜻이다. RFC 9745로 표준화되면서 값은 구조화 필드의 날짜 형식 — `@` 뒤에 유닉스 초 타임스탬프 — 이 됐다. 값이 미래면 "그날부터 폐기 예정", 과거면 "그날부터 이미 폐기됨"이다.

**`Sunset` 헤더는 "이 엔드포인트가 언제 응답을 멈추는가"를 담는다**(RFC 8594). 이름은 해가 지는 시각이라는 뜻이고, 값은 HTTP 날짜 형식의 절대 시각이다. `Deprecation`이 "권장하지 않게 된 시점"이라면 `Sunset`은 "죽는 시점"이라 **`Sunset`은 항상 `Deprecation`보다 뒤여야 한다**(RFC 9745가 명시한 제약이다).

```http
HTTP/1.1 200 OK
Content-Type: application/json

Deprecation: @1798761599
# 2026-12-31 23:59:59 UTC 부터 폐기 상태. 구조화 필드의 날짜라 '@' 접두사가 붙는다.

Sunset: Wed, 31 Mar 2027 23:59:59 GMT
# 이 시각에 응답이 멈춘다. Deprecation 보다 반드시 뒤여야 한다.

Link: <https://api.example.com/docs/deprecations/orders-v1>; rel="deprecation"
# rel="deprecation" — 사람이 읽을 폐기 안내 문서 (RFC 9745)

Link: <https://api.example.com/v2/orders/42>; rel="successor-version"
# rel="successor-version" — 이 자원의 다음 버전이 어디인지 (RFC 5829)
```

한 가지 현실적인 주의가 있다. `Deprecation`은 표준이 되기 전 초안 단계에서 오래 쓰여 왔고, 그 시절 형태인 `Deprecation: true`나 HTTP 날짜 문자열을 그대로 내려주는 서비스가 아직 많다(GitHub가 그 예다). **받는 쪽을 만들 때는 여러 형태를 관대하게 해석하고, 내려주는 쪽은 현행 표준 형태를 쓰되 문서에 형식을 명시**하는 것이 안전하다.

이 헤더들의 실질적인 가치는 **소비자 쪽에서 자동화가 가능해진다**는 데 있다. 클라이언트가 응답에서 `Sunset`을 발견하면 로그에 경고를 남기거나 사내 알림을 쏘게 만들어 둘 수 있고, 그러면 "공지 메일을 아무도 안 읽었다"는 문제가 구조적으로 줄어든다.

### 3-4. brownout — 짧게 일부러 끊어 남은 소비자를 깨운다

고지를 다 해도 트래픽이 안 빠지는 소비자가 반드시 남는다. 담당자가 바뀌었거나, 배치 스크립트를 아무도 안 보고 있거나, 그냥 안 읽은 경우다. 이들에게 도달하는 마지막 수단이 brownout이다.

**brownout은 종료 전에 짧은 시간 동안 일부러 해당 버전의 응답을 끊어, 남아 있는 소비자가 "장애"로 인지하게 만드는 기법이다.** 이름은 전력 용어에서 왔다. blackout(정전)이 완전히 꺼지는 것이라면 **brownout은 전압이 떨어져 조명이 어두워지는 부분적 정전**이다. 완전히 끄지 않고 잠깐만 어둡게 한다는 뉘앙스가 그대로 옮겨 왔다.

효과의 원리가 재미있다. **공지는 안 읽어도 장애 알림은 읽는다.** 아무도 보지 않던 배치 스크립트도 실패하면 누군가에게 알림이 가고, 그때 비로소 "우리가 아직 v1을 쓰고 있었구나"가 발견된다.

실행에는 규칙이 붙는다.

- **예고한다.** 기습이 아니다. "몇 월 며칠 몇 시부터 5분간 v1이 410을 반환합니다"를 미리 공지한다. 목적은 놀래키는 것이 아니라 **연락 경로를 여는 것**이다.
- **업무 시간에 한다.** 새벽에 하면 아무도 못 보고 지나간다. 상대 담당자가 깨어 있는 시간이어야 문의가 들어온다.
- **짧게, 그리고 점점 길게.** 4주 전 5분 → 3일 전 1시간처럼 강도를 올린다.
- **중단 스위치를 준비한다.** 예상보다 큰 영향이 나오면 즉시 되돌릴 수 있어야 한다. 설정 값 하나로 끄고 켜지도록 만든다.
- **결제·정산처럼 실패가 곧 금전 손실인 경로는 제외**하거나 별도 협의를 거친다. brownout은 압박 수단이지 사고 유발 장치가 아니다.

### 3-5. 그리고 시니어의 결론 — 최고의 버저닝은 버전을 안 올리는 것이다

3-2부터 3-4까지가 전부 **버전 하나를 없애는 데 드는 비용**이었다는 점을 다시 보자. 6개월의 타임라인, 계측 인프라, 개별 연락, brownout 리허설, 그동안의 이중 유지보수. 이 비용을 안 내는 유일한 방법은 **애초에 버전을 안 올리는 것**이다.

그래서 실제 실력은 파괴적 변경을 피하는 설계에서 드러난다.

- 응답 필드를 **삭제하는 대신 새 필드를 병행 제공**하고, 구 필드는 사용량이 0으로 수렴한 뒤에 뺀다(1-3의 비대칭을 이용하는 것이다 — 추가는 공짜고 삭제만 비싸다).
- 클라이언트에게 **tolerant reader 규약**을 문서로 명시한다. "모르는 필드는 무시하라"가 계약에 있어야 필드 추가가 진짜로 안전해진다.
- 버전 인상은 정말 계약을 갈아엎어야 하는 마지막 수단으로 아껴둔다.

## 4. 꼬리질문 대비 포인트

### "필드 추가는 왜 안전하고, 삭제는 왜 위험한가요?"

소비자 관점에서 보면 된다. 기존 클라이언트는 자기가 아는 필드만 읽으므로 **모르는 필드가 추가돼도 무시하면 그만**이다. 실제로 Jackson 같은 역직렬화기는 매핑할 자리가 없는 필드를 그냥 버린다(단, 클라이언트가 "모르는 필드가 오면 실패"하는 엄격 파싱을 하지 않는다는 규약이 필요하다 — Jackson 자체 기본값은 예외를 던지는 쪽이고 Spring Boot가 그 옵션을 꺼 준다).

반대로 삭제·이름 변경은 그 필드를 읽던 코드가 즉시 깨진다. **없는 값은 무시할 수 없기 때문**이다. Java 참조 타입이면 null이 들어와 쓰는 순간 NPE, 기본 타입이면 0이 들어가 조용히 계산이 틀어지고, Kotlin의 non-null 타입이나 Swift의 비옵셔널 프로퍼티면 역직렬화 자체가 실패해 응답을 통째로 못 읽는다. 특히 강제 업데이트가 불가능한 모바일 앱은 깨진 채로 남는다.

그래서 계약 변경의 기본기는 "추가는 자유, 삭제는 버전 인상 또는 긴 폐기 절차"다.

### "v2를 냈는데 v1을 언제, 어떻게 내리나요?"

(3장의 폐기 정책이 답의 골격) ① 버전별 사용량을 계측해 잔여 호출자를 식별하고, ② 문서 공지 + `Deprecation`/`Sunset` 헤더로 기한을 알리고, ③ 사전에 계약된 지원 기간이 지나면 단계적으로 내린다(예: brownout → 410 Gone 응답 → 완전 제거). 핵심은 "내릴 수 있는 근거(사전 계약)와 수단(계측)을 v2를 낼 때 함께 준비한다"는 것.

한 단계 더 들어가면 **되돌리기 비용이 다른 작업을 분리한다**는 원칙을 덧붙일 수 있다. "410으로 전환"은 설정으로 즉시 되돌아가지만 "코드 제거"는 배포가 필요하므로, 둘을 같은 날 하지 않고 몇 달 간격을 둔다.

기간의 감을 물으면 공개 API의 실제 사례를 대면 된다. GitHub은 새 REST API 버전을 낸 뒤 **이전 버전을 최소 24개월 더 지원**한다고 문서에 못 박아 두고, 지원이 끝난 버전을 지정한 요청에는 400을 돌려준다. 사내 서비스라면 이보다 훨씬 짧아도 되지만, **기간을 사전에 문서화한다는 성질**은 같다.

### "버전은 API 전체에 붙이나요, 리소스(엔드포인트)별로 붙이나요?"

- **전역 버전**(`/v1/...` 전체): 소비자가 이해하기 쉽고 문서가 단순하다. 대신 리소스 하나 바뀌어도 전체가 v2로 복제되는 비용.
- **리소스별 버전**(`/orders` 만 v2): 변경 범위가 작지만, "이 API는 지금 어떤 버전 조합이 유효한가"를 소비자가 추적해야 해서 혼란이 크다.
- 외부 공개 API는 전역 버전이 무난하고, 내부 API는 리소스별로 느슨하게 가져가기도 한다 — **소비자가 누구냐에 따라 갈리는 결정**이라고 답하면 된다.

여기서 한 겹 더 들어가면 좋다. 실제로 큰 서비스들이 지키는 것은 "전역이냐 리소스별이냐"가 아니라 더 밑에 있는 기준 하나다. **소비자가 "지금 내가 어느 계약 위에 있는가"를 언제나 확실히 알 수 있어야 한다.**

이 기준으로 보면 서로 달라 보이는 사례들이 한 줄로 정리된다.

| 서비스 | 버전을 어디에 | 소비자가 자기 버전을 아는 방법 |
|---|---|---|
| Stripe | 날짜 버전. 계정에 고정되고 요청별로 `Stripe-Version` 헤더로 덮어쓴다 | 대시보드에 고정 버전이 항상 표시되고, 요청 하나에는 버전이 하나만 적용된다 |
| GitHub REST | 날짜 버전을 `X-GitHub-Api-Version` 헤더로 | 헤더를 안 보내면 지정된 기본 버전으로 고정 — "모르는 사이에 바뀜"이 없다 |
| Kubernetes | 그룹 + 버전이 경로에 (`/apis/apps/v1/...`) | 리소스별로 버전이 다르지만 **모든 요청 경로에 버전이 박혀 있어** 헷갈릴 수 없다 |

Kubernetes가 특히 좋은 반례다. 리소스 그룹마다 버전이 제각각인데도 혼란이 크지 않은 이유는, 버전이 **경로에 항상 명시돼 있어 어느 요청을 보든 자기 버전이 눈에 보이기 때문**이다. 반대로 리소스별 버전이 위험해지는 것은 "어떤 엔드포인트는 버전이 붙고 어떤 건 안 붙어서, 소비자가 조합표를 외워야 하는" 형태로 갈 때다.

그러니 답의 결론은 이렇게 맺는다. **"리소스별 버전을 쓰더라도, 버전이 요청마다 명시적으로 드러나 소비자가 추측하지 않아도 되는 형태여야 한다."**

### "URI 버저닝이 REST 원칙 위반이라는 비판에 어떻게 답하시겠어요?" (시니어 변별 포인트)

비판의 요지는 "URI는 자원의 식별자인데 버전이 끼면 같은 자원이 여러 식별자를 갖는다"는 것이고, 이론적으로 타당하다. 2-3에서 본 자원/표현 구분으로 말하면 **v1 응답과 v2 응답은 같은 자원의 다른 표현일 뿐인데, 표현의 차이를 자원의 식별자에 새겨 넣은 셈**이다.

하지만 설계는 원칙 준수가 아니라 트레이드오프 선택이다 — 나는 **운영 가시성(로그로 버전 사용량 집계), 폐기 운영 가능성, 소비자 접근성**이 URI 순수성보다 실무 가치가 크다고 판단해 URI 방식을 고른다.

그 판단의 근거를 구체적으로 말할 수 있으면 좋다. **URI 방식이 주는 것은 전부 "우리 애플리케이션 바깥의 장비도 버전을 읽을 수 있다"는 한 가지 성질에서 나온다** — 액세스 로그가 그냥 남기는 URL이 곧 사용량 계측 데이터가 되고, 게이트웨이가 경로만 보고 버전별 풀을 분리하며, 캐시가 `Vary` 설정 없이도 버전을 섞지 않는다. 3절의 폐기 운영이 계측 위에 서 있는 이상 이 성질은 이론적 순수성과 맞바꿀 만하다.

대신 그 비용(자원 정체성 분열)을 알고 고르는 것과 모르고 고르는 것은 다르며, 내부 서비스 간 API처럼 소비자를 통제할 수 있고 게이트웨이가 헤더 라우팅을 잘 지원하는 환경이라면 헤더 방식도 유효한 선택지로 검토한다.

### "버저닝 없이 시작한 API에 나중에 버전을 붙일 수 있나요?"

붙일 수 있지만 비용이 크다 — 무버전 URI(`/orders`) 자체가 이미 계약이라, `/v2/orders`를 내는 순간 기존 경로를 "암묵적 v1"로 영구 유지하거나 마이그레이션을 강제해야 한다.

여기서 진짜 문제는 코드가 아니라 **뒤엉킨 이름**이다. `/orders`가 사실상 v1인데 이름에는 그 사실이 없으므로, 신규 소비자는 `/orders`와 `/v2/orders` 중 무엇이 최신인지 문서를 봐야만 알 수 있고, 나중에 v3이 나오면 `/orders`가 어느 세대인지 아무도 기억하지 못한다.

그래서 **공개 시점에 버전 자리(`/v1`)를 미리 잡아두는 것**이 정석이다. "지금은 v2 계획이 없어도 v1 prefix를 붙인다"는 결정 자체가 미래 비용을 앞당겨 사고하는 습관의 예시다. 비용은 경로에 세 글자를 더하는 것뿐인데, 안 붙였을 때 나중에 치르는 값은 위와 같다. (가산점 포인트)

## 한 줄 요약

버저닝은 "기존 클라이언트 코드를 고치지 않으면 깨지는 변경"인 파괴적 변경으로부터 소비자를 지키는 장치이고(추가가 안전한 이유는 파서가 모르는 필드를 버리기 때문, 삭제가 위험한 이유는 없는 값을 만들어 낼 수 없기 때문), URI 방식은 URL이 곧 캐시 키·라우팅 기준·로그 필드라서 우리 앱 바깥의 장비까지 버전을 읽을 수 있어 폐기 운영에 강하고 헤더 방식은 콘텐츠 협상을 재사용해 URI 순수성을 지키는 대신 `Vary` 관리와 가시성 부재라는 보이지 않는 비용을 낸다 — 그리고 진짜 실력은 하위 호환 변경만으로 API를 진화시켜 **버전을 올릴 일 자체를 줄이고**, 버전을 낼 때는 계측·`Deprecation`/`Sunset` 고지·brownout·410 종료로 이어지는 폐기 타임라인까지 함께 설계하는 데 있다.
