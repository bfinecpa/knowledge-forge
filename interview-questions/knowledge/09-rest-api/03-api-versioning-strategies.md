# API 버저닝 전략 — URI vs 헤더, "미래의 변경"을 지금 설계하는 일

> 핵심 관전 포인트: **API 버저닝은 하위 호환을 깨는 변경(breaking
> change)이 생겼을 때 기존 클라이언트를 깨뜨리지 않고 새 계약을
> 내놓는 장치다. URI 방식(`/v1/orders`)은 눈에 보이고 라우팅·캐시·
> 로그 분석이 쉬워 실무에서 가장 널리 쓰이지만 "같은 자원이 버전마다
> 다른 URI를 갖는" 어색함이 있고, 헤더 방식(`Accept` 미디어 타입 등)은
> URI를 순수하게 유지하지만 눈에 안 보여 테스트·디버깅·캐싱이
> 번거롭다. 그리고 최고의 버저닝 전략은 **버전을 올릴 일 자체를
> 줄이는 것** — 필드 추가 같은 하위 호환 변경만으로 API를 진화시키는
> 설계다.**

---

## 0. 질문 + 의도

**질문**: "API 버저닝 전략(URI, 헤더)의 장단점은?"

**출제 의도**: 버저닝은 "미래의 변경"을 지금 설계하는 일이다. 전략 없이
시작한 API가 v2를 내야 할 때 겪는 고통을 아는지 — 미래 비용을 앞당겨
사고하는 습관을 본다. 방식 비교 암기가 아니라, 왜 버전이 필요해지고
어떻게 하면 덜 필요해지는지까지 말하는 후보자가 변별된다.

## 1. 왜 버저닝인가 — 내 배포가 남의 앱을 깨는 구조

API는 배포하는 순간 소비자(모바일 앱, 파트너사, 타 팀)와의
**계약**이 된다. 문제는 소비자를 내가 통제할 수 없다는 것 —
특히 모바일 앱은 사용자가 업데이트를 안 하면 **1년 전 버전이
여전히 살아서 내 API를 호출한다.**

그래서 변경을 두 종류로 구분하는 감각이 먼저다:

- **하위 호환 변경(non-breaking)**: 응답에 필드 추가, 새 엔드포인트
  추가, 선택적 요청 파라미터 추가. → 기존 클라이언트는 모르는 필드를
  무시하면 되므로 **버전 없이 그냥 배포한다.**
- **파괴적 변경(breaking)**: 필드 삭제/이름 변경/타입 변경, 필수
  파라미터 추가, URL 구조 변경, 에러 포맷 변경. → 기존 클라이언트가
  즉시 깨진다. **이때가 버저닝이 필요한 순간이다.**

버저닝은 이 파괴적 변경을 "기존 계약(v1)은 그대로 두고 새 계약(v2)을
나란히 제공"하는 방식으로 흡수한다. 비유하면 **도로를 폐쇄하고 새로
까는 게 아니라, 새 도로를 옆에 놓고 기존 도로는 안내판을 붙여 서서히
폐쇄하는 것**이다.

## 2. 전략별 장단점 — URI, 헤더, 쿼리 파라미터

### ① URI 경로 버저닝 — `/v1/orders`

```http
GET /v1/orders/42
GET /v2/orders/42
```

**장점**

- **명시적이고 눈에 보인다**: URL만 봐도 어떤 계약인지 안다.
  브라우저·curl로 바로 테스트되고, 접근 로그만으로 "v1을 아직 누가
  쓰는지" 집계할 수 있다 — **폐기(deprecation) 운영이 쉬워진다.**
- **라우팅이 쉽다**: 게이트웨이/로드밸런서가 경로 prefix만 보고
  v1은 구서버, v2는 신서버로 보내는 식의 분리 배포가 간단하다.
- **캐시 친화적**: URL이 다르면 다른 캐시 키다. 중간 캐시(CDN 포함)가
  버전을 섞어 응답할 위험이 없다.

**단점**

- **"같은 자원인데 URI가 두 개"**: REST 관점에서 URI는 자원의
  식별자인데, 42번 주문이 `/v1/orders/42`와 `/v2/orders/42` 두
  정체성을 갖게 된다. 자원을 가리켜 저장해둔 링크가 버전에 묶인다.
- 버전이 계약 전체에 걸리므로, 한 리소스만 바뀌어도 **v2로 전체
  표면적이 복제**되는 경향이 생긴다(코드/문서 유지 비용).

### ② 헤더 버저닝 — `Accept` 미디어 타입 또는 커스텀 헤더

```http
# 미디어 타입(콘텐츠 협상) 방식
GET /orders/42
Accept: application/vnd.myapp.v2+json

# 커스텀 헤더 방식
GET /orders/42
X-API-Version: 2
```

**장점**

- **URI가 순수하게 유지된다**: 자원의 식별자(URI)와 표현의 버전
  (헤더)이 분리된다 — HTTP의 콘텐츠 협상(content negotiation)
  메커니즘을 정석대로 쓰는 방식.
- 자원을 가리키는 링크가 버전과 무관하게 안정적이다.

**단점**

- **눈에 안 보인다**: 브라우저 주소창으로 테스트 불가, curl에
  헤더를 매번 붙여야 하고, 장애 조사 때 접근 로그의 URL만으로는
  어떤 버전이 호출됐는지 모른다(헤더 로깅을 별도로 심어야 한다).
- **캐시가 까다롭다**: 같은 URL에 버전별로 다른 응답이 나가므로
  중간 캐시에 `Vary: Accept` 같은 지시를 정확히 줘야 하고,
  이를 무시하는 캐시 계층이 있으면 **버전이 섞인 응답 사고**가 난다.
- 파트너사 개발자 온보딩 비용이 크다 — "헤더 빼먹음"이 흔한
  문의 유형이 된다.

### ③ 쿼리 파라미터 버저닝 — `/orders/42?version=2`

URI 방식과 헤더 방식의 중간. 눈에 보이고 테스트가 쉽지만,
"버전 파라미터를 빠뜨리면 어느 버전인가"라는 기본값 문제가 있고
자원 식별과 표현 선택이 뒤섞여 어느 쪽 장점도 온전히 갖지 못한다.
실무에서는 앞의 두 방식보다 드물다.

### 비교 요약

| 기준 | URI 방식 | 헤더 방식 |
|---|---|---|
| 가시성(테스트·로그·디버깅) | 좋음 | 나쁨 (별도 로깅 필요) |
| 라우팅/배포 분리 | 쉬움 | 게이트웨이가 헤더 해석 필요 |
| 캐시 안전성 | 좋음 (URL=캐시 키) | `Vary` 관리 필요 |
| REST 순수성(자원 식별) | 어색함 (자원 URI가 버전에 묶임) | 좋음 |
| 소비자 사용 난이도 | 낮음 | 높음 (헤더 누락 문의) |

**실무 선택**: 외부에 공개하거나 파트너가 소비하는 API는 대부분
**URI 방식**을 택한다 — 이론적 순수성보다 가시성·운영 편의·소비자
접근성이 주는 이득이 크기 때문이다. "정답은 URI"가 아니라
"소비자가 누구이고 운영에서 무엇이 중요한지로 고른다"고 말하는 것이
핵심이다.

## 3. 실무 운영 — 버전은 만드는 것보다 없애는 게 어렵다

전략 없이 시작한 API가 v2를 내야 할 때 겪는 고통은 대략 이렇다:

1. v2를 냈지만 v1 트래픽이 줄지 않는다 — 어떤 클라이언트가 v1을
   쓰는지 **집계 수단이 없다.**
2. v1·v2 두 벌의 코드/문서/테스트를 무기한 유지한다 — 버그를 두 번
   고친다.
3. v1을 내리자 업데이트 안 한 구버전 앱과 연락 안 되는 파트너사가
   깨진다 — 장애 문의로 되돌아온다.

그래서 버저닝 전략에는 **폐기 정책이 함께 설계**되어야 한다:

- **버전별 사용량 계측**: 처음부터 버전·클라이언트 식별자별 호출량을
  대시보드로 본다. "v1 잔여 호출자 톱10"을 뽑을 수 있어야 폐기가
  가능하다.
- **폐기 공지 체계**: 문서·공지에 더해 응답 헤더로 기계가 읽을 수 있는
  신호(`Deprecation`, `Sunset` 헤더)를 실어준다. (가산점 포인트)
- **지원 버전 수 상한**: "동시 지원은 최대 2개 버전, 신버전 공개 후
  N개월 뒤 구버전 종료" 같은 규칙을 계약(문서)에 미리 명시한다 —
  폐기 근거를 사후 협상이 아니라 사전 계약으로 만든다.

그리고 시니어의 결론: **최고의 버저닝은 버전을 안 올리는 것이다.**
필드 추가처럼 하위 호환 변경만으로 진화할 수 있게 설계하고
(응답 필드 삭제 대신 신규 필드 병행 제공, 클라이언트에는 "모르는
필드는 무시하라"는 tolerant reader 규약), 버전 인상은 정말 계약을
갈아엎어야 하는 마지막 수단으로 아껴둔다.

## 4. 꼬리질문 대비 포인트

### "필드 추가는 왜 안전하고, 삭제는 왜 위험한가요?"

소비자 관점에서 보면 된다. 기존 클라이언트는 자기가 아는 필드만
읽으므로 **모르는 필드가 추가돼도 무시하면 그만**이다(단, 클라이언트가
"모르는 필드가 오면 실패"하는 엄격 파싱을 하지 않는다는 규약 필요).
반대로 삭제·이름 변경은 그 필드를 읽던 코드가 즉시 깨진다 — 특히
강제 업데이트가 불가능한 모바일 앱은 깨진 채로 남는다. 그래서 계약
변경의 기본기는 "추가는 자유, 삭제는 버전 인상 또는 긴 폐기 절차"다.

### "v2를 냈는데 v1을 언제, 어떻게 내리나요?"

(3장의 폐기 정책이 답의 골격) ① 버전별 사용량을 계측해 잔여
호출자를 식별하고, ② 문서 공지 + `Deprecation`/`Sunset` 헤더로
기한을 알리고, ③ 사전에 계약된 지원 기간이 지나면 단계적으로 내린다
(예: 410 Gone 응답 → 완전 제거). 핵심은 "내릴 수 있는 근거(사전
계약)와 수단(계측)을 v2를 낼 때 함께 준비한다"는 것.

### "버전은 API 전체에 붙이나요, 리소스(엔드포인트)별로 붙이나요?"

- **전역 버전**(`/v1/...` 전체): 소비자가 이해하기 쉽고 문서가
  단순하다. 대신 리소스 하나 바뀌어도 전체가 v2로 복제되는 비용.
- **리소스별 버전**(`/orders` 만 v2): 변경 범위가 작지만, "이 API는
  지금 어떤 버전 조합이 유효한가"를 소비자가 추적해야 해서 혼란이
  크다.
- 외부 공개 API는 전역 버전이 무난하고, 내부 API는 리소스별로
  느슨하게 가져가기도 한다 — **소비자가 누구냐에 따라 갈리는 결정**
  이라고 답하면 된다.

### "URI 버저닝이 REST 원칙 위반이라는 비판에 어떻게 답하시겠어요?" (시니어 변별 포인트)

비판의 요지는 "URI는 자원의 식별자인데 버전이 끼면 같은 자원이 여러
식별자를 갖는다"는 것이고, 이론적으로 타당하다. 하지만 설계는 원칙
준수가 아니라 트레이드오프 선택이다 — 나는 **운영 가시성(로그로 버전
사용량 집계), 폐기 운영 가능성, 소비자 접근성**이 URI 순수성보다
실무 가치가 크다고 판단해 URI 방식을 고른다. 대신 그 비용(자원
정체성 분열)을 알고 고르는 것과 모르고 고르는 것은 다르며, 내부
서비스 간 API처럼 소비자를 통제할 수 있고 게이트웨이가 헤더 라우팅을
잘 지원하는 환경이라면 헤더 방식도 유효한 선택지로 검토한다.

### "버저닝 없이 시작한 API에 나중에 버전을 붙일 수 있나요?"

붙일 수 있지만 비용이 크다 — 무버전 URI(`/orders`) 자체가 이미
계약이라, `/v2/orders`를 내는 순간 기존 경로를 "암묵적 v1"로
영구 유지하거나 마이그레이션을 강제해야 한다. 그래서 **공개 시점에
버전 자리(`/v1`)를 미리 잡아두는 것**이 정석이다. "지금은 v2 계획이
없어도 v1 prefix를 붙인다"는 결정 자체가 미래 비용을 앞당겨 사고하는
습관의 예시다. (가산점 포인트)

## 한 줄 요약

버저닝은 파괴적 변경으로부터 기존 소비자를 지키는 장치로, URI 방식은
가시성·라우팅·캐시·폐기 운영에 강해 실무 표준에 가깝고 헤더 방식은
URI 순수성을 지키는 대신 보이지 않는 비용을 낸다 — 그리고 진짜 실력은
하위 호환 변경만으로 API를 진화시켜 **버전을 올릴 일 자체를 줄이고**,
버전을 낼 때는 폐기 정책(계측·공지·기한)까지 함께 설계하는 데 있다.
