# PUT vs PATCH — 전체 교체와 부분 수정, 그리고 "안 보낸 필드가 null로 덮이는" 사고

> 핵심 관전 포인트: **PUT은 "보낸 표현으로 자원 전체를 교체(replace)"하는 메서드고, PATCH는 "보낸 내용만 부분 수정(partial update)"하는 메서드다. 이때 '메서드의 의미'는 내가 정하는 것이 아니라 HTTP 명세가 미리 정해둔 것이고(이것을 시맨틱이라고 부른다), 그 약속을 믿고 캐시·프록시·재시도 라이브러리·상대 팀 클라이언트가 움직이기 때문에 서버가 마음대로 어기면 사고는 내 코드 밖에서 난다. 가장 실질적인 차이는 멱등성이다 — PUT은 본문에 최종 상태가 통째로 담겨 있어 몇 번을 보내도 결과가 같으므로 "응답을 못 받았을 때 그냥 재시도해도 되는" 메서드지만, PATCH는 명세가 멱등을 약속하지 않으므로 자동 재시도 대상이 아니다. 이 구분이 흐려지면 실무에서 "클라이언트가 안 보낸 필드가 null로 덮여 데이터가 유실되는" 사고가 API 계약 수준에서 발생한다 — 부분 수정을 PUT으로 받거나, PATCH에서 '필드를 아예 안 보냄'과 '필드에 null을 보냄'을 구분하지 못하는 구현이 그 범인이다. 이 3-way 구분을 살리는 선택지가 `JsonNullable` 래퍼, JSON Merge Patch(RFC 7386), JSON Patch(RFC 6902) 셋이며, 어느 쪽을 고르든 팀 컨벤션으로 못박아 API 문서에 명시하는 것까지가 계약을 다루는 태도다.**

---

## 0. 질문 + 의도

**질문**: "PUT과 PATCH의 차이는?"

**출제 의도**: 전체 교체와 부분 수정의 구분이 흐리면 "안 보낸 필드가 null로 덮이는" 데이터 유실이 API 계약 수준에서 발생한다. HTTP 메서드의 시맨틱(의미 약속)을 지키는 규율이 있는지 보는 표본 검사다 — 이 구분을 아는 사람은 다른 계약(상태 코드, 멱등성)도 지킬 확률이 높다.

## 1. 시맨틱 차이 — 교체(replace) vs 수정(modify)

### 1-1. "시맨틱"이 무엇이고, 왜 서버 마음대로 어기면 안 되는가

이 문서 전체에서 "시맨틱"이라는 말이 계속 나오므로 먼저 정의하고 가자.

**시맨틱(semantics)은 문법(syntax)의 반대말로 "의미"를 뜻한다.** HTTP 메서드의 시맨틱이란, **그 메서드를 쓴 요청이 서버에게 무엇을 시키는 것인지를 HTTP 명세(RFC 9110)가 미리 정해둔 의미**를 말한다. `PUT`이라는 세 글자가 문법이라면, "이 URI의 자원을 본문 내용으로 교체하라"가 시맨틱이다.

중요한 것은 이 의미를 **내가 정하는 게 아니라는 점**이다. `@PutMapping`이 붙은 메서드 안에서 무슨 코드를 쓰든 프레임워크는 막지 않지만, 그렇다고 PUT의 의미가 내가 짠 코드로 바뀌지는 않는다. 세상은 여전히 명세에 적힌 의미로 그 요청을 해석한다.

그러면 "세상"은 구체적으로 누구인가. 이 약속을 참으로 믿고 동작하는 것들의 목록이 곧 답이다.

- **재시도 라이브러리와 API 게이트웨이**는 "PUT은 멱등이니 타임아웃 나면 다시 보내도 된다, PATCH는 아니다"를 기본 정책으로 삼는다. 내 PATCH 구현이 우연히 멱등하다는 사실을 이들은 알 방법이 없다.
- **중간 캐시**는 PUT·PATCH·DELETE·POST 요청이 지나가면 그 URI에 저장해둔 응답을 무효화한다. 메서드 이름만 보고 "이 자원이 바뀌었겠구나"를 판단하는 것이다.
- **클라이언트를 만드는 사람**은 문서를 다 읽지 않는다. `PUT /users/42`를 보면 "전체를 보내야겠네"라고 이해하고 구현한다. 이 이해가 서버 구현과 어긋나면 그 지점이 그대로 버그가 된다.

그래서 **시맨틱 위반의 대가는 대체로 내 서버 로그가 아니라 내가 통제하지 못하는 바깥에서 나타난다.** 이것이 "메서드 의미를 지키는 것은 취향이 아니라 규율"인 이유다.

### 1-2. PUT과 PATCH가 각각 약속하는 것

두 메서드의 차이는 "몇 개 필드를 보내느냐"가 아니라 **서버가 요청 본문을 무엇으로 해석하겠다고 약속하느냐**다. 같은 `{"email": "new@ex.com"}` 본문이라도 메서드가 무엇이냐에 따라 뜻이 정반대가 된다.

**PUT `/users/42`** 는 "이 본문이 42번 사용자의 **완전한 최신 상태**다. 기존 걸 버리고 이걸로 갈아끼워라"라는 뜻이다. 그러므로 **본문에 없는 필드는 "없애라"는 뜻**이 된다.

**PATCH `/users/42`** 는 "이 본문에 **적힌 것만** 바꿔라"라는 뜻이다. 그러므로 **본문에 없는 필드는 "건드리지 마라"는 뜻**이 된다.

비유하면 PUT은 **문서 전체를 새 파일로 덮어쓰기**, PATCH는 **문서에 수정 지시서(변경분)만 전달하기**다. 새 파일로 덮어쓸 때는 파일에 없는 문단이 사라지는 것이 당연하고, 수정 지시서를 보낼 때는 지시서에 없는 문단이 남는 것이 당연하다. 둘 다 맞는 동작인데 전제가 다를 뿐이다.

```http
# 사용자 자원의 현재 상태
# {"name": "김철수", "email": "kim@ex.com", "phone": "010-1111-2222"}

# PUT — 전체 교체: phone을 안 보냈으므로 phone은 "제거하라"는 의미다
PUT /users/42
{"name": "김철수", "email": "new@ex.com"}
# 결과: {"name": "김철수", "email": "new@ex.com", "phone": null}

# PATCH — 부분 수정: 보낸 email만 바뀌고 나머지는 그대로 유지된다
PATCH /users/42
{"email": "new@ex.com"}
# 결과: {"name": "김철수", "email": "new@ex.com", "phone": "010-1111-2222"}
```

### 1-3. 멱등성 — 실무 질문은 "재시도해도 되는가"다

**멱등(idempotent)** 은 "같은 요청을 1번 보내든 N번 보내든 서버의 최종 상태가 같다"는 성질이다. 낯선 한자어인 멱등(冪等)은 수학에서 왔다 — **거듭 적용해도 결과가 더 이상 변하지 않는 연산**, 즉 `f(f(x)) = f(x)`를 뜻한다. 절댓값이 딱 그렇다. `abs(-3)`도 3이고 `abs(abs(-3))`도 3이라 몇 번을 씌워도 값이 그대로다.

여기까지는 정의일 뿐이고, 이 개념이 실무에서 왜 중요한지는 **질문을 바꿔 던져야** 드러난다. 실무에서 우리가 진짜 답해야 하는 질문은 이것이다.

**"요청은 보냈는데 응답을 못 받았다. 다시 보내도 되는가?"**

이 상황은 분산 환경에서 가장 흔하고 가장 곤란하다. 서버가 에러를 돌려주는 것은 오히려 다행이다 — 무엇이 잘못됐는지 알려주니까. 진짜 곤란한 것은 **아무 응답도 못 받은 상태**다.

```
[클라이언트가 아는 것과 모르는 것]

  아는 것   : "내가 요청을 보냈고, 응답이 안 왔다"
  모르는 것 : "서버가 그 요청을 처리했는가?"

  가능한 세계가 셋인데 구분할 방법이 없다.
    ① 요청이 서버에 도달조차 못 했다       → 미처리
    ② 도달해서 처리됐는데 응답이 유실됐다   → 처리됨
    ③ 지금 서버가 처리하는 중이다          → 곧 처리됨
```

이 불확실성 앞에서 클라이언트가 할 수 있는 선택은 둘뿐이다 — **포기하거나, 다시 보내거나.** 그런데 다시 보냈다가 실제로는 ②였다면 같은 작업이 두 번 실행된다.

**멱등성이 정확히 이 갈림에서 답을 준다.** 요청이 멱등하면 ②였더라도 한 번 더 보낸 결과가 같으므로 "모르는 채로 그냥 다시 보내도" 안전하다. 즉 **멱등성은 "재시도해도 되는가"라는 질문의 다른 이름**이다.

두 메서드를 이 기준으로 보자.

**PUT은 멱등하다.** 근거는 "본문에 최종 상태가 통째로 담겨 있기 때문"이다. "42번 사용자를 이 내용으로 만들어라"는 명령은 **목적지를 절대 좌표로 지정**한 것과 같아서, 몇 번을 실행해도 같은 자리에 도착한다. 그래서 네트워크 오류로 응답을 못 받은 클라이언트가 **안심하고 재시도할 수 있다.**

**PATCH는 멱등이 보장되지 않는다.** PATCH는 "부분 수정"이라는 틀만 정하고 **수정 내용의 성질은 정하지 않기** 때문이다. 본문 두 개를 나란히 보면 왜 그런지 한눈에 들어온다.

```
[멱등한 PATCH — 절대값을 지정한다]
  PATCH /users/42   {"email": "new@ex.com"}
  1회 후 new@ex.com,  2회 후 new@ex.com,  3회 후 new@ex.com   → 최종 상태 동일

[멱등하지 않은 PATCH — 상대 연산을 지정한다]
  PATCH /users/42   {"op": "increment", "field": "point", "by": 100}
  1회 후 +100,       2회 후 +200,        3회 후 +300           → 최종 상태가 달라진다
```

즉 **"PATCH는 절대 멱등이 아니다"는 틀린 설명**이고, **"구현이 멱등일 수는 있지만 클라이언트와 인프라가 멱등이라고 가정해서는 안 되는 메서드"**가 정확한 설명이다. 명세가 약속하지 않았으므로 중간 장비나 클라이언트 라이브러리는 PATCH를 자동 재시도 대상으로 취급하지 않는다.

메서드별 안전성·멱등성 전체 표와 더 깊은 논의는 [8장 04번 문서](../08-network-http/04-http-method-idempotency-and-safety.md)와 [01번 문서](01-restful-design-principles-resource-naming.md)의 1-3에 있다.

## 2. 실무 사고 시나리오 — "안 보낸 필드가 null로 덮였어요"

### 2-1. 사고 재현

가장 흔한 사고는 **부분 수정 화면을 PUT(또는 PUT처럼 동작하는 구현)으로 처리**할 때 난다.

시나리오는 이렇다. 회원 정보에 `name`, `email`, `marketingAgreed`(마케팅 수신 동의)가 있다. 앱의 "이메일 변경" 화면은 이메일 입력칸 하나뿐이라 `email`만 보낸다.

```java
// Before: 부분 수정 요청을 전체 교체처럼 처리 — 데이터 유실
@PutMapping("/users/{id}")
public void update(@PathVariable Long id, @RequestBody UserUpdateRequest req) {
    User user = userRepository.findById(id).orElseThrow();
    // 요청 본문에 없던 필드는 DTO에서 null(또는 false)로 남아 있는데,
    // 아래 세 줄은 그 값을 그대로 엔티티에 덮어쓴다.
    user.setName(req.getName());                       // null로 덮임
    user.setMarketingAgreed(req.getMarketingAgreed()); // null 또는 false로 덮임
    user.setEmail(req.getEmail());
}
```

이메일만 바꿨는데 **이름이 사라지고 마케팅 동의가 풀린다.** 이런 버그는 컴파일 에러도, 런타임 예외도 없이 조용히 데이터를 갉아먹다가 **"동의한 적 있는데 왜 해제됐냐"는 CS로 발견된다.** 그때는 이미 며칠치 데이터가 덮여 있고, 원본이 없으니 복구도 어렵다.

원인은 코드가 아니라 **계약 위반**이다. 클라이언트는 부분 수정(PATCH 시맨틱)을 기대했는데 서버는 전체 교체(PUT 시맨틱)로 처리했다.

### 2-2. 왜 null이 되는가 — 역직렬화가 하는 일

위 코드가 왜 그렇게 동작하는지 한 단계 아래를 보자.

**역직렬화(deserialization)는 네트워크로 도착한 JSON 문자열을 Java 객체로 되돌리는 과정이다.** 반대 방향, 즉 Java 객체를 JSON 문자열로 바꾸는 것이 직렬화(serialization)다. Spring에서는 `@RequestBody`가 붙는 순간 Jackson 라이브러리가 이 일을 대신해 준다.

여기서 핵심은 **Jackson이 "JSON에 없는 키"를 만났을 때 하는 일이 "아무것도 안 하는 것"**이라는 점이다. 그 필드에는 값을 세팅하지 않고 지나가므로, 필드는 **자바가 객체를 만들 때 넣어둔 기본값 그대로** 남는다.

```
요청 본문:  {"email": "new@ex.com"}

  Jackson이 UserUpdateRequest 객체를 만든 직후의 상태
    name            = null    (참조 타입의 기본값)
    email           = null
    marketingAgreed = null    (Boolean 래퍼) 또는 false (boolean 원시 타입)

  JSON에 있는 키만 채운다
    email = "new@ex.com"      ← 이것만 세팅됨
    나머지는 기본값 그대로 남는다
```

그리고 이 기본값이 그대로 엔티티에 복사된다. **DTO 입장에서 "안 보낸 필드"와 "null을 보낸 필드"가 완전히 같은 모습**이 되는 것인데, 이 문제가 3절의 주제다.

`marketingAgreed`를 `Boolean`(래퍼)이 아니라 `boolean`(원시 타입)으로 선언했다면 상황은 더 나쁘다. 기본값이 `null`이 아니라 `false`라서, DB의 `NOT NULL` 제약에도 안 걸리고 **조용히 "동의 해제"로 저장된다.** null로 덮이면 제약 위반으로 터지기라도 하지만, `false`는 정상적인 값처럼 보이기 때문에 아무 신호도 남지 않는다.

### 2-3. After — 부분 수정은 PATCH로 받고 "보낸 필드만" 반영한다

```java
// After: 부분 수정은 PATCH로 받고, null이 아닌 필드만 반영한다
@PatchMapping("/users/{id}")
public void patch(@PathVariable Long id, @RequestBody UserPatchRequest req) {
    User user = userRepository.findById(id).orElseThrow();
    // null 체크가 곧 "이 필드가 요청에 실려 왔는가"의 판정 역할을 한다.
    // 실려 오지 않은 필드는 건드리지 않으므로 기존 값이 보존된다.
    if (req.getName() != null) user.setName(req.getName());
    if (req.getEmail() != null) user.setEmail(req.getEmail());
    if (req.getMarketingAgreed() != null) {
        user.setMarketingAgreed(req.getMarketingAgreed());
    }
}
```

메서드를 PATCH로 바꾼 것과 `if (… != null)`을 넣은 것은 **한 세트**다. 둘 중 하나만 하면 여전히 이름과 동작이 어긋난다. 그리고 이 구현에도 남은 구멍이 있는데, 그것이 3절이다.

### 2-4. 반대 방향의 규율 — "친절한 PUT"이 계약을 무너뜨린다

여기까지 읽으면 "그럼 PUT에서도 null이면 건너뛰게 하면 되지 않나?"라는 생각이 든다. 안 된다. 그렇게 만든 PUT은 **이름만 PUT인 PATCH**다.

**PUT을 제공한다면 클라이언트는 항상 전체 표현을 보내야 하고, 서버는 빠진 필드를 "유지"가 아니라 "제거/초기화"로 처리해야 PUT이다.** 빠진 필드를 적당히 유지해주는 "친절한 PUT"은 당장은 사고를 막아주는 것처럼 보이지만, 더 나쁜 결과를 만든다.

이유는 **클라이언트가 필드를 지울 방법이 사라지기 때문**이다. 사용자가 전화번호 입력칸을 비우고 저장했다고 하자. 클라이언트는 `phone`을 빼고 보내거나 `null`로 보낼 텐데, 친절한 PUT은 둘 다 "유지"로 처리해 버린다. **사용자 화면에는 지워졌는데 서버에는 그대로 남는다.** 그리고 이때부터 클라이언트마다 해석이 갈라진다 — 어떤 팀은 빈 문자열 `""`을 보내 지우려 하고, 어떤 팀은 별도 삭제 API를 요구한다. 계약이 무너지는 것이 이 지점이다.

### 2-5. PUT의 또 다른 대가 — lost update

전체 교체에는 사고 하나가 더 딸려 온다. 이것이 4절의 "무조건 PATCH가 좋은가" 꼬리질문과 12번 문서로 이어지는 다리이므로 여기서 정의해 둔다.

**lost update(갱신 유실)는 두 사람이 같은 자원을 각자 읽어 각자 수정한 뒤 저장했을 때, 나중에 저장한 쪽이 앞사람의 수정을 덮어써 앞사람의 변경이 흔적 없이 사라지는 현상이다.** 이름 그대로 갱신이 유실된다. 에러도, 경고도, 로그도 남지 않는다는 것이 이 현상의 무서운 점이다.

관리자 두 명이 같은 주문 화면을 열어 각각 다른 필드를 고치는 상황을 타임라인으로 보자.

```
시각   관리자 A                        관리자 B                       서버의 주문 42
────────────────────────────────────────────────────────────────────────────────────
 t0    GET /orders/42                                                 메모="" · 배송지=서울
       → 메모="" · 배송지=서울
 t1                                    GET /orders/42                 메모="" · 배송지=서울
                                       → 메모="" · 배송지=서울
 t2    화면에서 메모를 "선물포장"으로
 t3                                    화면에서 배송지를 "부산"으로
 t4    PUT /orders/42
       {메모:"선물포장", 배송지:"서울"}                                메모=선물포장 · 배송지=서울
 t5                                    PUT /orders/42
                                       {메모:"", 배송지:"부산"}        메모="" · 배송지=부산
                                                                              ↑
                                              t4에 A가 쓴 "선물포장"이 사라졌다.
                                              B는 t1에 읽은 낡은 메모("")를 그대로 되보냈기 때문이다.
```

B는 배송지만 고쳤다고 생각하지만, PUT의 시맨틱상 **B가 보낸 본문 전체가 자원의 최종 상태**다. B의 본문에 담긴 메모는 t1 시점의 낡은 값이므로, 그 값이 A의 수정을 덮어쓴다.

**PATCH는 이 문제를 줄여준다.** B가 `{"배송지": "부산"}`만 보내면 메모는 손대지 않으므로 A의 수정이 살아남는다. 하지만 **없애지는 못한다** — 두 사람이 같은 필드를 고치면 여전히 나중에 저장한 쪽이 이긴다.

**근본 해결은 메서드 선택이 아니라 조건부 요청이다.** 서버가 GET 응답에 자원의 버전 지문인 `ETag`를 실어주고, 클라이언트는 수정 요청에 `If-Match: <그 ETag>`를 붙인다. 서버는 현재 버전과 대조해 다르면 요청을 실행하지 않고 `412 Precondition Failed`를 돌려준다. 즉 **"내가 본 그 버전이 아직 그대로일 때만 저장해라"**를 계약으로 강제하는 것이다. 자세한 내용은 [12번 문서](12-etag-if-match-optimistic-concurrency.md)에서 다룬다.

## 3. PATCH 구현의 함정 — "안 보냄"과 "null로 지워라"의 구분

### 3-1. 세 가지 의미가 두 가지로 뭉개진다

2-3의 After 코드에도 남은 구멍이 있다. `if (req.getX() != null)` 방식은 **"필드를 아예 안 보냈다"와 "필드를 null로 지워달라"를 구분하지 못한다.**

JSON 쪽에서는 이 셋이 분명히 다른 표현이다.

```json
{"phone": "010-9999-8888"}   // phone을 이 값으로 변경해라
{"phone": null}              // phone을 지워라 (null로 설정해라)
{}                           // phone은 건드리지 마라
```

그런데 2-2에서 봤듯이 Jackson은 "키가 없으면 아무것도 안 한다". 그래서 평범한 DTO로 받으면 뒤의 두 경우가 **똑같이 `phone == null`**이 되어 구분이 사라진다.

| JSON 본문 | 클라이언트의 의도 | 평범한 DTO로 역직렬화한 결과 | 서버가 구분 가능한가 |
|---|---|---|---|
| `{"phone": "010-9999-8888"}` | 이 값으로 변경 | `req.phone` = `"010-9999-8888"` | 가능 |
| `{"phone": null}` | 지워라 (null로 설정) | `req.phone` = `null` | **불가** — 아래와 똑같아진다 |
| `{}` (키 자체가 없음) | 건드리지 마라 | `req.phone` = `null` | **불가** — 위와 똑같아진다 |

결과적으로 `if (req.getPhone() != null)` 구현은 **"지워라"를 언제나 "건드리지 마라"로 해석한다.** 사용자가 전화번호를 비우고 저장하면 화면에서는 지워졌는데 서버에는 그대로 남는다. 2-4의 "친절한 PUT"과 정확히 같은 증상이 PATCH에서도 나는 것이다.

이 문제는 **nullable 필드가 하나라도 있는 순간** 생긴다. 반대로 모든 필드가 `NOT NULL`이고 "지우기"가 애초에 없는 API라면 평범한 DTO로도 충분하다. 그래서 설계 단계에서 먼저 물어야 할 질문은 **"이 자원에 지울 수 있는 필드가 있는가"**다.

선택지는 세 가지이고, 셋은 요청 본문의 모양부터 다르다.

### 3-2. 선택지 ① `JsonNullable` 래퍼 필드

**무엇인가.** 필드 타입을 값 자체가 아니라 **래퍼**로 감싸서, "값이 실려 왔는가"와 "실려 온 값이 null인가"를 **별개의 두 정보로 분리해 담는** 방법이다. 대표적인 구현이 OpenAPI Generator가 쓰는 `org.openapitools.jackson.nullable.JsonNullable`이다.

**어떻게 생겼나.** 요청 본문의 모양은 **하나도 바뀌지 않는다.** 서버 DTO의 타입만 바뀐다.

```java
public class UserPatchRequest {
    // JsonNullable은 상태를 셋으로 구분한다.
    //   undefined()      : 요청 본문에 이 키가 없었다        → 건드리지 마라
    //   of(null)         : 키가 있었고 값이 null이었다        → 지워라
    //   of("010-...")    : 키가 있었고 값이 있었다            → 이 값으로 바꿔라
    // 초기값을 undefined()로 둬야 "안 보냄"이 기본 상태가 된다.
    private JsonNullable<String> phone = JsonNullable.undefined();

    public JsonNullable<String> getPhone() { return phone; }
}
```

```java
// isPresent()는 "값이 null인가"가 아니라 "키가 본문에 있었는가"를 묻는다.
// 그래서 명시적으로 보낸 null도 통과하고, 아래 get()이 null을 돌려준다.
if (req.getPhone().isPresent()) {
    user.setPhone(req.getPhone().get());   // null이면 그대로 null로 설정 = 지우기
}
```

쓰려면 Jackson에 `JsonNullableModule`을 등록해야 한다. 그리고 `Optional`로 대신하려는 시도는 권하지 않는다 — 기본 설정에서 명시적 null은 `Optional.empty()`가 되고 키가 없으면 **필드 자체가 `null`**로 남아서, "필드가 null이면 안 보낸 것, `Optional.empty()`면 null을 보낸 것"이라는 헷갈리는 3상태가 된다. 의도를 이름으로 드러내는 `JsonNullable` 쪽이 읽기 쉽다.

**언제 고르나.** **기존 JSON 계약(본문 모양)을 전혀 바꾸지 않고 3-way 구분만 살리고 싶을 때**다. 클라이언트는 하던 대로 `{"phone": null}`을 보내면 되고, 서버 DTO의 타입만 바뀌므로 도입 비용이 가장 낮다. 필드가 몇 개 안 되는 일반적인 CRUD API에서는 이 선택이 가장 현실적이다.

### 3-3. 선택지 ② JSON Merge Patch (RFC 7386)

**무엇인가.** **"null = 제거, 키 없음 = 유지"라는 해석 규칙 자체를 표준 문서로 못박은 포맷**이다. 위의 `JsonNullable`이 "우리 서버는 이렇게 해석하기로 했다"는 팀 내부의 약속이라면, Merge Patch는 **RFC 번호가 붙은 공용 약속**이다. 그래서 클라이언트에게 "우리는 RFC 7386을 따른다"는 한 줄로 해석 규칙 전체를 전달할 수 있다.

**어떻게 생겼나.** 본문 모양은 평범한 JSON과 똑같고, `Content-Type`이 달라진다.

```http
PATCH /users/42
Content-Type: application/merge-patch+json

{"email": "new@ex.com", "phone": null}
# 해석: email은 이 값으로 바꾸고, phone은 제거하고, 나머지 필드는 그대로 둔다
```

구현은 DTO로 받지 않고 **JSON 트리(맵)로 받아 키의 존재 여부를 직접 검사**하는 방식이 된다. Jackson에는 이 병합을 그대로 해주는 기능이 있다.

```java
@PatchMapping(path = "/users/{id}", consumes = "application/merge-patch+json")
public void patch(@PathVariable Long id, @RequestBody JsonNode patch) throws IOException {
    User user = userRepository.findById(id).orElseThrow();

    // 엔티티에 직접 병합하지 않는다. 클라이언트가 role이나 balance처럼
    // 수정하면 안 되는 필드를 본문에 끼워 넣어도 그대로 반영되기 때문이다.
    // 수정 허용 필드만 담은 뷰 객체에 먼저 병합해 화이트리스트 역할을 시킨다.
    UserPatchView view = mapper.convertValue(user, UserPatchView.class);

    // readerForUpdating은 patch에 실제로 존재하는 키만 view에 덮어쓴다.
    // 없는 키는 건드리지 않고, null인 키는 null로 설정한다 — 곧 Merge Patch 시맨틱이다.
    mapper.readerForUpdating(view).readValue(patch);

    validator.validate(view);   // 병합 후에 검증해야 최종 상태를 검사하게 된다
    user.applyFrom(view);
}
```

**한계도 알고 골라야 한다.** null에 "제거"라는 의미를 부여했으므로 **필드를 진짜 null 값으로 설정하는 것과 제거를 구분할 수 없고**, 배열은 원소별 병합이 아니라 **통째로 교체**된다. 태그 목록에서 한 개만 빼고 싶어도 전체 배열을 다시 보내야 한다.

**언제 고르나.** 자원이 **문서에 가까운 형태**(중첩 객체가 있고 부분 갱신이 잦은)이고, 해석 규칙을 표준으로 못박아 여러 클라이언트에 동일하게 전달하고 싶을 때다.

### 3-4. 선택지 ③ JSON Patch (RFC 6902)

**무엇인가.** 본문을 "바뀐 상태"가 아니라 **"수행할 연산의 목록"**으로 보내는 포맷이다. 앞의 둘이 "결과를 그려서 보내는" 방식이라면, 이쪽은 **"수정 지시서를 명령문으로 적어 보내는"** 방식이다.

**어떻게 생겼나.** 본문이 객체가 아니라 **연산 객체의 배열**이라 모양부터 완전히 다르다.

```http
PATCH /users/42
Content-Type: application/json-patch+json

[
  {"op": "replace", "path": "/email", "value": "new@ex.com"},
  {"op": "remove",  "path": "/phone"},
  {"op": "add",     "path": "/tags/-", "value": "vip"},
  {"op": "test",    "path": "/version", "value": 7}
]
```

`op`에는 `add`·`remove`·`replace`·`move`·`copy`·`test` 여섯 가지가 있고, `path`는 JSON Pointer(RFC 6901)라는 표기법으로 문서 안의 위치를 가리킨다(`/tags/-`는 배열의 끝을 뜻한다). 연산은 **적힌 순서대로 적용**되고, 하나라도 실패하면 **전체를 적용하지 않는 것**이 규칙이라 요청 단위의 원자성이 있다.

앞의 두 방식이 못 하던 일이 여기서 가능해진다. **배열의 특정 원소만 추가·삭제·이동할 수 있고**, `test` 연산으로 **"이 필드가 이 값일 때만 적용해라"라는 조건**을 요청 안에 담을 수 있다. `test`는 2-5의 lost update 대응을 본문 수준에서 흉내 내는 셈인데, HTTP 계층의 표준 수단은 어디까지나 `If-Match`이므로 그쪽을 우선한다.

**대가는 클라이언트 비용이다.** 클라이언트가 "무엇을 바꿀지"가 아니라 "어떤 연산을 어떤 경로에 적용할지"를 조립해야 하고, 서버도 별도 라이브러리(`jakarta.json`의 `Json.createPatch`, 또는 `com.github.java-json-tools:json-patch`)를 물어야 한다. 사람이 눈으로 읽기도 앞의 둘보다 어렵다.

**언제 고르나.** **배열 원소 단위 편집이 필요하거나**, 협업 편집·감사 로그처럼 **"무엇을 어떻게 바꿨는지"를 연산 단위로 기록하고 재생해야 할 때**다. 일반적인 회원 정보 수정에는 과하다.

### 3-5. 무엇을 고를 것인가

| 방식 | 표현할 수 있는 것 | 요청 본문 모양 | 클라이언트 비용 | 언제 고르나 |
|---|---|---|---|---|
| 평범한 DTO + null 체크 | 값 설정만 | `{"email":"..."}` | 없음 | nullable 필드가 없고 "지우기"가 필요 없는 API |
| `JsonNullable` 래퍼 | 값 설정 + 명시적 제거 | 위와 동일 (본문 안 바뀜) | 없음 | 기존 계약을 유지하며 3-way만 살릴 때 — 가장 현실적 |
| JSON Merge Patch | 값 설정 + 제거 + 중첩 객체 병합 | `{"phone": null}` + 전용 Content-Type | 낮음 | 문서형 자원, 해석 규칙을 표준으로 못박고 싶을 때 |
| JSON Patch | 위 전부 + 배열 원소 조작·이동·조건부 | `[{"op":"remove","path":"/phone"}]` | 높음 | 배열 편집, 연산 단위 기록·재생이 필요할 때 |

실무에서는 **"nullable 필드가 있는 PATCH는 이 구분 문제를 반드시 설계 단계에서 짚고, 어떤 시맨틱을 택했는지(예: Merge Patch)를 API 문서에 명시한다"**까지 말하면 계약을 다루는 태도가 드러난다. 어느 것을 고르느냐보다 **고른 것을 문서에 적어 클라이언트가 추측하지 않게 만드는 것**이 핵심이다. (가산점 포인트)

## 4. 꼬리질문 대비 포인트

### "PUT은 멱등한데 POST는 왜 멱등하지 않나요?"

**차이는 "누가 URI를 정하는가"에서 온다.**

`POST /orders`는 "컬렉션에 새 자원을 추가하라"는 요청이고, **만들어질 자원의 URI를 서버가 정한다.** 그래서 호출할 때마다 서로 다른 새 자원이 생긴다 — 두 번 보내면 주문이 2건이다. 반면 `PUT /orders/42`는 **URI가 이미 42로 못박혀 있고** "그 자리를 이 상태로 만들어라"는 요청이므로, 몇 번을 반복해도 최종 상태가 같다.

이 차이는 실무에서 **재시도 정책**으로 직결된다. 타임아웃이 났을 때 PUT은 그냥 재시도해도 되지만, POST 재시도는 곧 중복 생성이다. 그래서 결제·주문처럼 **꼭 재시도가 필요한데 본질적으로 비멱등인** 작업에는 서버가 멱등성을 직접 부여하는 장치가 필요하다 — 클라이언트가 시도마다 고유 키를 만들어 보내고 서버가 그 키로 중복을 흡수하는 **멱등성 키**다. 자세한 설계는 [06번 문서](06-idempotency-key-design.md)에 있다.

### "값을 지정하는 PATCH는 사실상 멱등인데, 왜 '멱등이 아니다'라고 하나요?"

**멱등성은 개별 요청의 우연한 성질이 아니라 메서드 단위의 계약**이기 때문이다.

HTTP 명세가 PATCH에 멱등을 약속하지 않았으므로, 프록시·클라이언트 라이브러리·재시도 미들웨어는 **"PATCH는 재시도하면 위험할 수 있다"를 전제로** 동작한다. 이들은 내 PATCH 핸들러의 코드를 읽어볼 수 없다. 내 PATCH가 우연히 멱등이더라도 그건 **명세가 아니라 구현 사정**이므로 바깥에서는 알 방법이 없는 것이다.

그래서 "재시도해도 안전하다"를 **계약으로 보장받고 싶다면** 두 가지 길뿐이다. 전체 교체가 가능한 상황이면 PUT을 쓰고, 그럴 수 없으면 멱등성 키를 도입해 서버가 직접 중복을 흡수한다.

### "PUT으로 자원 생성도 가능한가요?"

가능하다 — 단, **클라이언트가 URI(식별자)를 결정할 수 있을 때**다.

`PUT /users/42/profile-image`처럼 **자원의 자리가 미리 정해져 있는 경우**, 그 자리에 아직 아무것도 없으면 만들고 이미 있으면 갈아끼우면 된다. 이렇게 **없으면 insert, 있으면 update로 동작하는 것을 upsert 시맨틱**이라고 부른다(update + insert의 합성어다). 응답은 새로 만들었으면 `201 Created`, 기존 것을 교체했으면 `200 OK`나 `204 No Content`로 구분해 준다.

반면 서버가 ID를 발급하는 일반적인 생성(`/orders`에 새 주문 추가)은 **클라이언트가 URI를 모르므로 PUT을 쓸 수 없고** POST를 쓴다. 굳이 PUT으로 하고 싶다면 클라이언트가 UUID를 만들어 `PUT /orders/{uuid}`로 보내는 설계도 가능한데, 이 경우 **재시도가 안전해진다는 이점**이 따라온다 — 같은 UUID로 다시 보내도 같은 자리를 덮어쓸 뿐이라 주문이 두 건 생기지 않는다.

### "그럼 수정 API는 무조건 PATCH로 만드는 게 좋은가요?" (시니어 변별 포인트)

트레이드오프가 있다.

**PUT의 강점**은 시맨틱이 단순하고(보낸 것이 곧 최종 상태) 멱등이라 재시도가 안전하다는 것이다. 서버 구현도 조건 분기 없이 통째로 덮어쓰면 끝이라 단순하다. "설정 저장"처럼 **클라이언트가 항상 전체 상태를 들고 있는 화면**에는 PUT이 오히려 깔끔하다.

**PATCH의 강점**은 부분 수정 화면이 여러 개일 때 각 화면이 자기 필드만 보내면 된다는 것이다. 그리고 2-5에서 봤듯이 **서로 다른 필드를 고치는 동시 요청끼리 덮어쓰지 않는다** — PUT 둘이 교차하면 한쪽 수정이 통째로 증발하는 lost update가 나지만, PATCH는 각자 자기 필드만 건드리므로 그 경우가 줄어든다.

**나의 기준은 "클라이언트가 전체 표현을 신뢰성 있게 갖고 있는가"다.** 갖고 있으면 PUT, 화면이 쪼개져 있거나 필드가 많아 클라이언트가 일부만 아는 상태면 PATCH.

여기에 한 줄을 더 얹으면 판단이 완성된다. **어느 쪽이든 동시 수정이 진짜 문제라면 메서드 선택으로는 풀리지 않는다.** PATCH는 lost update의 발생 범위를 줄일 뿐 없애지 못하므로, 같은 필드를 동시에 고치는 경우까지 막으려면 `ETag`/`If-Match` 기반의 낙관적 동시성 제어로 가야 한다([12번 문서](12-etag-if-match-optimistic-concurrency.md)).

### "@PatchMapping만 붙이면 부분 수정이 되는 건가요?"

안 된다. **애너테이션은 라우팅만 담당하고, 부분 수정 시맨틱은 전적으로 구현 책임**이다. `@PatchMapping`이 하는 일은 "PATCH 메서드로 이 경로에 들어온 요청을 이 자바 메서드로 보내라"가 전부다. 그 안에서 무슨 짓을 하는지는 검사하지 않는다.

```java
// 이름만 PATCH인 PUT — 애너테이션은 PATCH인데 동작은 전체 교체다.
// 2-1의 null 덮어쓰기 사고가 그대로 재현된다.
@PatchMapping("/users/{id}")
public void fakePatch(@PathVariable Long id, @RequestBody UserRequest req) {
    User user = userRepository.findById(id).orElseThrow();
    user.setName(req.getName());     // 안 보낸 필드가 null로 덮인다
    user.setEmail(req.getEmail());
}

// 이름만 PUT인 PATCH — 애너테이션은 PUT인데 동작은 부분 수정이다.
// 클라이언트는 "전체를 보내야 한다"고 이해했는데 서버는 빠진 필드를 유지한다.
// 그래서 클라이언트가 필드를 지울 방법이 사라진다(2-4).
@PutMapping("/users/{id}")
public void fakePut(@PathVariable Long id, @RequestBody UserRequest req) {
    User user = userRepository.findById(id).orElseThrow();
    if (req.getName() != null) user.setName(req.getName());
    if (req.getEmail() != null) user.setEmail(req.getEmail());
}
```

**메서드 이름과 실제 동작이 어긋난 API가 계약 사고의 진원지다.** 클라이언트 개발자는 코드를 볼 수 없고 메서드 이름만 보고 자기 구현을 만들기 때문이다.

덧붙여 클라이언트 쪽에도 함정이 하나 있다. `RestTemplate`의 기본 요청 팩토리인 `SimpleClientHttpRequestFactory`는 JDK의 `HttpURLConnection`을 쓰는데, 이 클래스가 허용하는 메서드 목록에 **PATCH가 없어** 호출하면 `ProtocolException`이 난다. Apache HttpClient 기반 팩토리로 바꾸거나, `java.net.http.HttpClient`를 쓰는 `RestClient`·`WebClient`를 쓰면 해결된다. "PATCH를 붙였는데 안 된다"는 문의의 상당수가 서버가 아니라 여기서 나온다.

## 한 줄 요약

PUT은 "본문이 곧 자원의 완전한 최종 상태"인 전체 교체(멱등 — 응답을 못 받아도 재시도 가능), PATCH는 "보낸 것만 바꾸는" 부분 수정(멱등 비보장 — 자동 재시도 대상이 아님)이며, 이 시맨틱이 흐려지는 순간 "안 보낸 필드가 null로 덮이는" 데이터 유실이 계약 수준에서 발생한다 — 그래서 부분 수정은 PATCH로 받고, nullable 필드가 있다면 '안 보냄'과 'null 보냄'을 구분하는 수단(`JsonNullable`·Merge Patch·JSON Patch)을 고른 뒤 그 선택을 문서에 명시하며, 동시 수정으로 인한 lost update는 메서드가 아니라 `ETag`/`If-Match`로 푸는 것까지가 이 질문의 완성형이다.
