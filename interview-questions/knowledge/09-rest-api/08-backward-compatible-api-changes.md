# 하위 호환 API 변경 — 내 배포가 남의 앱을 깨지 않게 하는 계약 관리

> 핵심 관전 포인트: **공개된 API는 계약이므로, 변경은 "소비자가 모르는 사이에
> 일어나도 아무 일도 없는 변경(호환)"과 "소비자가 반드시 대응해야 하는
> 변경(파괴적)"으로 나눠 관리한다. 호환 변경의 대원칙은 "추가는 안전,
> 삭제·의미 변경은 위험" — 응답 필드 추가와 선택적 요청 파라미터 추가만
> 허용하고, 필드 삭제·이름 변경·타입 변경·필수화는 전부 파괴적 변경으로
> 취급한다. 깨야만 할 때는 expand(새것 추가·병행 제공) →
> migrate(소비자 이전, Deprecation 고지 + 사용량 모니터링) →
> contract(아무도 안 쓰는 것 확인 후 제거)의 3단계 절차를 밟는다.**

---

## 0. 질문 + 의도

**질문**: "하위 호환성을 깨지 않고 API를 변경하는 원칙은? 깨야만 할 때의
마이그레이션 절차는?"

**출제 의도**: 내 배포가 남의 앱을 깨는 구조(특히 강제 업데이트가 불가능한
모바일)에서 일해봤는지를 본다. "필드 삭제는 왜 위험하고 추가는 왜 안전한가"를
서버 편의가 아니라 **소비자(클라이언트) 관점**에서 설명할 수 있는지가 관건이다.

> 이벤트/메시지 스키마의 호환성(backward/forward, Schema Registry)은
> `06-kafka-messaging/18-schema-evolution-compatibility.md` 참고.
> 이 문서는 **동기 REST API의 요청/응답 계약** 관점에 집중한다.

## 1. 왜 "하위 호환"이 문제가 되는가 — 배포 주기가 다른 세계

서버와 클라이언트는 **같이 배포되지 않는다.** 서버는 오늘 바꿔도,

- 웹 프론트는 다음 주에 배포되고,
- 모바일 앱은 심사 후 배포되며, 배포돼도 **사용자가 업데이트를 안 하면
  구버전이 몇 달씩 살아 있다.**
- 외부 파트너사는 아예 내 통제 밖이다.

즉 "서버의 지금 버전"과 "클라이언트의 과거 버전"이 항상 동시에 대화하고
있다. **하위 호환 = 옛날 클라이언트가 새 서버와 통신해도 깨지지 않는 성질**이고,
이걸 깨는 배포는 내 장애가 아니라 **남의 장애**를 만든다 — 그래서 더 위험하다
(내 대시보드에는 에러가 안 찍히고, 파트너사 CS로 먼저 터진다).

## 2. 호환/파괴 변경 분류표 — "추가는 안전, 삭제·의미 변경은 위험"

핵심 규칙은 방향으로 기억한다.

| 변경 | 응답(서버→클라) | 요청(클라→서버) |
|---|---|---|
| 필드 **추가** | 안전 (모르는 필드는 무시됨) | **선택적**이면 안전, **필수**면 파괴적 |
| 필드 **삭제** | **파괴적** (읽던 쪽이 깨짐) | 안전 (서버가 안 읽으면 그만) |
| 필드 **이름 변경** | 파괴적 (삭제+추가와 동일) | 파괴적 |
| **타입/포맷 변경** (숫자→문자열, 날짜 포맷) | 파괴적 | 파괴적 |
| **의미 변경** (같은 필드, 다른 뜻·단위) | **가장 위험한 파괴적 변경** — 스키마 검증도 못 잡는다 | 동일 |
| enum에 **새 값 추가** | 조건부 — 클라가 unknown 값을 처리 못 하면 파괴적 | 안전 |
| 필수였던 응답 필드를 **nullable로** | 파괴적 | — |
| 에러 상태코드/에러코드 체계 변경 | 파괴적 (클라이언트 분기 로직이 깨짐) | — |
| URL·HTTP 메서드 변경 | 파괴적 | 파괴적 |

왜 "응답 필드 추가"는 안전한가 — 대부분의 역직렬화기(Jackson 등)와
클라이언트 코드는 **모르는 필드를 무시**하기 때문이다. 반대로 "응답 필드
삭제"는 그 필드를 읽어 화면에 뿌리던 코드가 null/파싱 에러로 깨진다.
소비자가 무엇을 읽고 있는지 서버는 알 수 없으므로, **한 번 내보낸 응답
필드는 소비자 전수 확인 전까지 내 마음대로 없앨 수 없다** — 이게 "API는
장기 계약"이라는 말의 실체다.

```java
// Before: 파괴적 변경 — 필드 이름을 "정리"하고 싶어서 바꿈
public record OrderResponse(
    Long id,
    String price   // "10000" → 이걸 amount로 바꾸면 옛 클라이언트가 전부 깨짐
) {}

// After: expand — 새 필드를 추가하고 옛 필드를 당분간 병행 제공
public record OrderResponse(
    Long id,
    @Deprecated String price,   // 유지 (Deprecation 고지 후 사용량 0 확인되면 제거)
    Long amount                  // 새 계약: 숫자 타입 + 명확한 이름
) {}
```

요청 방향의 함정 하나 — **선택 파라미터를 필수로 바꾸는 것**도 파괴적 변경이다.
어제까지 안 보내도 되던 값을 오늘부터 400으로 거부하면, 코드를 한 줄도 안 바꾼
클라이언트가 깨진다.

### 방어적 소비 원칙 — Tolerant Reader (가산점 포인트)

호환성은 제공자만의 책임이 아니다. 소비자 쪽도 **"아는 것만 읽고, 모르는 것은
무시한다"**(Tolerant Reader 패턴)를 지켜야 한다. 예: 역직렬화 시 unknown
필드에 fail하도록 설정(`FAIL_ON_UNKNOWN_PROPERTIES=true`)해 두면, 제공자가
규칙대로 "안전한 필드 추가"만 해도 내 쪽이 깨진다. enum도 마찬가지 —
모르는 값이 오면 예외 대신 `UNKNOWN`으로 받아들이는 기본값을 둔다.

## 3. 깨야만 할 때 — expand → migrate → contract 3단계

이름 변경, 타입 변경, 리소스 구조 개편처럼 파괴적 변경이 불가피하면
**한 번에 바꾸지 않고 겹침 구간을 만든다.**

### ① expand — 옛것을 유지한 채 새것을 추가

- 필드 수준: 새 필드 추가 + 옛 필드 병행 제공 (위 코드 예시).
- 엔드포인트 수준: `/v2/orders` 같은 새 버전을 추가하고 v1은 그대로 둔다.
  이 단계에서 옛 클라이언트는 **아무 변화도 느끼지 못해야 한다.**

### ② migrate — 소비자를 이전시키고, 이전됐는지 측정한다

- **고지**: 변경 로그·파트너 공지로 "무엇이, 언제까지, 왜" 바뀌는지 알린다.
  응답에 `Deprecation` 헤더와 종료 시점을 알리는 `Sunset` 헤더를 실어
  기계적으로도 알린다.
- **측정**: 고지만으로는 절대 안 옮긴다. 옛 필드/옛 버전 호출을
  **호출자별로 로깅·집계**해서 (게이트웨이 액세스 로그, API 키·User-Agent
  기준) "아직 v1을 쓰는 소비자가 누구인지" 명단을 만들고 직접 연락한다.

```java
// 마이그레이션 기간: 옛 엔드포인트에 deprecation 신호 + 사용 추적
@GetMapping("/v1/orders/{id}")
public OrderResponseV1 getOrderV1(@PathVariable Long id,
                                  @RequestHeader(value = "User-Agent", required = false) String ua) {
    deprecationMetrics.count("orders-v1", ua);   // 누가 아직 쓰는지 집계
    return orderV1Adapter.from(orderService.find(id));  // 내부는 신모델, 경계에서 v1로 변환
}
// 응답 헤더: Deprecation: true / Sunset: <종료 예정 시점> / Link: <v2 문서>
```

- 내부 구현은 하나로 통일하고, **v1은 얇은 어댑터(변환 계층)로만 유지**하는
  게 유지비를 줄이는 요령이다. v1/v2 로직을 각각 구현하면 겹침 구간 동안
  버그가 두 배로 난다.

### ③ contract — 사용량 0을 확인하고 제거

- 사용량이 0이거나, 남은 소비자와 합의된 시점이 지나면 옛 필드/버전을 제거한다.
- 제거 직전에 바로 삭제하지 않고 **일시 차단(410 Gone) 후 되돌릴 수 있는
  기간**을 두면, 놓친 소비자를 낮은 비용으로 발견할 수 있다 (가산점 포인트).

## 4. 꼬리질문 대비 포인트

### "호환성이 깨지는 걸 배포 전에 어떻게 잡나요?"

사람 리뷰만으로는 못 잡는다. 체계로 잡는다:

1. **OpenAPI 스펙 diff 검사** — CI에서 이전 버전 스펙과 비교해 "필드 삭제,
   타입 변경, 필수화" 같은 파괴적 변경을 자동 검출해 빌드를 실패시킨다.
2. **소비자 주도 계약 테스트(CDC)** — 소비자가 "내가 이 필드를 이렇게 쓴다"를
   계약으로 등록하고(Pact, Spring Cloud Contract), 제공자 빌드에서 그 계약을
   검증한다. "누가 뭘 읽는지 모른다" 문제를 정면으로 해결하는 방법.
3. 스냅샷/직렬화 테스트 — 응답 JSON을 고정해 두고 달라지면 실패.

### "필드의 '의미'가 바뀌는 건 스펙 diff로도 못 잡지 않나요?"

맞다, 그래서 가장 위험하다. 예: `amount`가 "원 단위"에서 "부가세 포함
원 단위"로 바뀌면 스키마는 동일한데 모든 클라이언트의 금액 표시가 틀어진다.
의미 변경은 **호환 변경으로 위장한 파괴적 변경**이므로, 같은 필드의 의미를
바꾸지 말고 **새 이름의 필드를 추가**하는 것이 원칙이다
(`amountWithTax` 추가 → 마이그레이션 → `amount` 정리).

### "API 버저닝을 하면 되는데 왜 이렇게까지 필드 수준을 관리하나요?" (시니어 변별 포인트)

버저닝은 만능이 아니라 **최후 수단**이다. 버전을 올릴 때마다:

- 겹침 기간 동안 서버는 v1/v2를 **둘 다 운영**해야 하고(코드·테스트·모니터링
  이중화), 소비자는 아무 이득 없이 이전 작업을 해야 한다.
- 이전을 강제할 수단이 없는 외부 소비자 때문에 v1이 몇 년씩 살아남는 일이
  흔하다.

그래서 성숙한 팀의 전략은 "필드 수준의 호환 변경(추가)으로 최대한 버티고,
파괴적 변경은 모아서 드물게, 마이그레이션 절차와 함께"다. 버전 번호는 계약
관리의 시작이 아니라 **호환 유지에 실패했을 때 지불하는 비용**이라고 답하면
설계 감각을 보여줄 수 있다.

### "모바일 앱처럼 강제 업데이트가 안 되는 소비자는 어떻게 하나요?"

- 앱에 **최소 지원 버전 체크**(기동 시 서버에 버전 확인 → 강제/권장 업데이트
  안내)를 처음부터 심어 두는 게 근본 대책이다. 이게 없으면 사실상 sunset이
  불가능하다.
- 없다면: 구버전 트래픽이 자연 감소 곡선을 그릴 때까지 어댑터를 유지하고,
  잔존율 기준(예: 전체 트래픽의 일정 비율 미만)을 정해 종료를 의사결정한다.

### "Deprecation 고지는 어디에, 어떻게 남기나요?"

세 채널을 병행한다 — ① 문서/변경 로그(사람용), ② 응답 헤더
`Deprecation`·`Sunset`·대체 리소스를 가리키는 `Link`(기계용, 게이트웨이에서
일괄 부착 가능), ③ 사용량 기반 직접 연락(옛 버전을 실제로 호출 중인
소비자 명단). 고지 기간은 소비자의 배포 주기보다 길어야 의미가 있다 —
외부 파트너라면 계약서에 명시된 사전 고지 기간을 따른다.

## 한 줄 요약

공개 API의 변경은 "추가는 안전, 삭제·의미 변경은 파괴적"이라는 규칙으로
분류해 호환 변경만 자유롭게 배포하고, 파괴적 변경이 불가피하면
**expand(병행 제공) → migrate(고지 + 사용량 측정으로 이전 확인) →
contract(사용 0 확인 후 제거)**의 겹침 구간 절차로 — 내 배포가 남의 앱을
깨지 않게 하는 것이 API 제공자의 기본기다.
