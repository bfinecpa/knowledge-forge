# 하위 호환 API 변경 — 내 배포가 남의 앱을 깨지 않게 하는 계약 관리

> 핵심 관전 포인트: **서버와 클라이언트는 같이 배포되지 않는다 — 앱스토어 심사가 있고, 심사를 통과해도 사용자가 업데이트를 안 누르며, 그래서 몇 달에서 몇 년 전 버전의 앱이 지금 이 순간에도 내 서버를 부르고 있다. 하위 호환은 그래서 선택이 아니라 제약이다. 변경은 "소비자가 몰라도 아무 일도 없는 변경(호환)"과 "소비자가 반드시 대응해야 하는 변경(파괴적)"으로 나눠 관리하고, 대원칙은 "추가는 안전, 삭제·의미 변경은 위험"이다. 다만 **"추가는 안전"은 무조건이 아니라 조건부 명제**다 — 안전한 이유는 받는 쪽 역직렬화기가 모르는 필드를 무시하도록 설정돼 있기 때문이고, 그건 자동이 아니다(Jackson 단독 기본값은 모르는 필드를 만나면 예외를 던진다). 그래서 제공자의 규칙과 소비자의 **Tolerant Reader**(아는 것만 읽고, 모르는 필드는 무시하고, 모르는 enum 값에도 죽지 않는다)가 짝으로 성립해야 하며, 특히 enum에 값 하나를 더하는 것은 필드 추가가 아닌데도 구버전 앱을 파싱 단계에서 죽일 수 있는 반직관적 파괴다. 깨야만 할 때는 expand(둘 다 지원해 넓힌다) → migrate(소비자를 옮기고 옮겨졌는지 측정한다) → contract(옛것을 제거해 좁힌다)의 3단계를 밟는데, 여기서 진짜 어려운 곳은 측정이다 — 요청은 서버 로그에 남지만 **응답 필드를 누가 읽는지는 서버가 원리적으로 알 수 없어서**, 소비자 단위 호출량 집계와 brownout 같은 우회 수단이 필요하다.**

---

## 0. 질문 + 의도

**질문**: "하위 호환성을 깨지 않고 API를 변경하는 원칙은? 깨야만 할 때의 마이그레이션 절차는?"

**출제 의도**: 내 배포가 남의 앱을 깨는 구조(특히 강제 업데이트가 불가능한 모바일)에서 일해봤는지를 본다. "필드 삭제는 왜 위험하고 추가는 왜 안전한가"를 서버 편의가 아니라 **소비자(클라이언트) 관점**에서 설명할 수 있는지가 관건이다.

> 이 문서는 **동기 REST API의 요청/응답 계약**에 집중한다. 버전 번호를 어디에 붙일지(URI 대 헤더)와 폐기 운영은 `03-api-versioning-strategies.md`, 이벤트/메시지 스키마의 호환성(backward/forward, Schema Registry)은 `06-messaging/06-schema-evolution-compatibility.md`에서 다룬다.

## 1. 왜 "하위 호환"이 문제가 되는가 — 배포 주기가 다른 세계

### 1-1. 서버는 오늘 배포한다, 앱은 그렇지 않다

결론부터 말하기 전에 현실을 먼저 깔아야 이 문서의 모든 규칙이 이해된다. 질문은 이것이다. **왜 서버는 오늘 고칠 수 있는데 모바일 앱은 못 고치는가.**

서버 배포는 우리 손 안에 있다. 빌드하고, 배포하고, 문제가 있으면 롤백한다. 몇 분이면 전 사용자가 새 코드를 쓴다.

모바일 앱은 그 사이에 관문이 셋 있다.

**첫째, 앱스토어 심사가 있다.** 우리가 오늘 앱을 고쳐도 스토어에 올라가는 것은 심사를 통과한 뒤다. 리젝되면 고쳐서 다시 제출하고 다시 기다린다. "긴급 수정"이라는 개념이 서버만큼 빠르게 작동하지 않는다.

**둘째, 배포는 곧 설치가 아니다.** 스토어에 새 버전이 올라간다고 사용자 폰의 앱이 바뀌는 게 아니다. 자동 업데이트를 꺼둔 사용자, Wi-Fi에서만 업데이트하도록 설정한 사용자, 저장 공간이 부족한 사용자, 그냥 업데이트 알림을 무시하는 사용자가 있다.

**셋째, 그래서 구버전이 오래 살아남는다.** 버전별 트래픽 대시보드를 켜 보면 대체로 이런 모양이 나온다 — 출시 직후 며칠 만에 상당수가 올라오고, 몇 주 안에 대부분이 따라오지만, **마지막 몇 퍼센트가 몇 달에서 몇 년씩 꼬리를 끈다.** 그 꼬리가 사라지지 않는 이유는 그 폰들이 아직 살아서 앱을 쓰고 있기 때문이다.

여기에 통제 밖의 소비자가 더해진다.

```text
[내 서버]  오늘 배포한 최신 버전  ─── 하나뿐이다

    ▲   ▲   ▲   ▲
    │   │   │   │
    │   │   │   └── 외부 파트너사 시스템 — 아예 내 통제 밖. 그쪽 개발 일정에 달렸다
    │   │   └────── 3개월 전 버전 앱 — 업데이트 안 한 사용자들
    │   └────────── 지난주 버전 앱 — 대부분의 사용자
    └────────────── 웹 프론트 — 다음 배포 때 같이 나간다

옛 클라이언트들은 "지금" 살아서 "지금의 서버"와 대화하고 있다.
```

이 그림이 핵심이다. **서버는 하나인데 클라이언트는 여러 시대가 동시에 존재한다.** 그리고 그 시대들을 내가 정리할 수 없다.

### 1-2. 그래서 하위 호환은 선택이 아니라 제약이다

**하위 호환(backward compatibility)이란 "옛날 클라이언트가 새 서버와 통신해도 깨지지 않는 성질"**이다. "뒤(backward)"는 시간 축의 뒤, 즉 과거 버전을 가리킨다. 새 서버가 과거 방향으로 호환된다는 뜻이다.

1-1의 현실 때문에 이건 "지키면 좋은 미덕"이 아니라 **작업의 전제 조건**이다. 옛 클라이언트를 정리할 수단이 없으므로, 옛 클라이언트가 계속 동작하게 만드는 것 외에 다른 선택지가 없다.

그리고 이 규칙을 어겼을 때의 벌이 특이하다. **내 장애가 아니라 남의 장애가 된다.**

| | 보통의 장애 | 하위 호환을 깬 배포 |
|---|---|---|
| 어디서 터지나 | 내 서버 | 남의 앱, 남의 시스템 |
| 내 대시보드 | 5xx 급증, 알람 발화 | **전부 초록색** (서버는 200을 잘 주고 있다) |
| 어떻게 알게 되나 | 알람 | 파트너사 CS, 앱 리뷰, 며칠 뒤의 문의 |
| 롤백으로 해결되나 | 대체로 된다 | 서버는 되돌려도, 그사이 깨진 화면을 본 사용자는 되돌릴 수 없다 |

서버는 정상 응답 200을 주고 있는데 그 응답을 받은 앱이 파싱에 실패해 흰 화면을 띄우는 상황을 상상하면 된다. **내 관측 범위 밖에서 조용히 터지기 때문에 더 위험하다.**

### 1-3. 용어 정리 — 호환 변경과 파괴적 변경

변경을 두 종류로 나누는 감각이 이 문서의 뼈대다. 용어는 `03-api-versioning-strategies.md`와 맞춘다.

- **호환 변경(non-breaking change)**: 소비자가 코드를 한 줄도 안 바꿔도 계속 동작하는 변경. 응답 필드 추가, 새 엔드포인트 추가, 선택적 요청 파라미터 추가가 여기 속한다. **버전을 올리지 않고 그냥 배포한다.**
- **파괴적 변경(breaking change)**: 소비자가 코드를 고쳐야만 동작하는 변경. 필드 삭제, 이름 변경, 타입 변경, 필수 파라미터 추가가 여기 속한다. **소비자를 옮기는 절차(3장) 없이는 배포할 수 없다.**

이 구분이 왜 중요한가 하면, **호환 변경만으로 API를 진화시킬 수 있으면 버전을 올릴 일 자체가 없어지기 때문**이다. 버전 번호는 계약 관리의 시작이 아니라 **호환 유지에 실패했을 때 지불하는 비용**이다.

## 2. 무엇이 안전하고 무엇이 위험한가 — 분류표와 그 메커니즘

### 2-1. 분류표 — 방향으로 기억한다

핵심 규칙은 **"추가는 안전, 삭제·의미 변경은 위험"**인데, 여기에 방향(응답이냐 요청이냐)이 곱해진다. 응답은 서버가 주고 클라이언트가 읽는 방향이고, 요청은 클라이언트가 주고 서버가 읽는 방향이다.

| 변경 | 응답(서버→클라) | 요청(클라→서버) |
|---|---|---|
| 필드 **추가** | 안전 — 단, 소비자가 모르는 필드를 무시할 때만 (2-2) | **선택적**이면 안전, **필수**면 파괴적 (2-6) |
| 필드 **삭제** | **파괴적** — 읽던 쪽이 null 또는 파싱 에러로 깨진다 | 안전 — 서버가 안 읽으면 그만 |
| 필드 **이름 변경** | 파괴적 (삭제 + 추가와 동일하다) | 파괴적 |
| **타입/포맷 변경** (숫자→문자열, 날짜 포맷) | 파괴적 | 파괴적 |
| **의미 변경** (같은 필드, 다른 뜻·단위) | **가장 위험한 파괴적 변경** — 스키마 검증도 못 잡는다 (4장) | 동일 |
| enum에 **새 값 추가** | 조건부 파괴적 — 소비자가 모르는 값을 처리 못 하면 죽는다 (2-4) | 안전 |
| 숫자 **값의 범위 확대** (id가 32비트를 넘어감) | 조건부 파괴적 — 좁은 타입으로 파싱하던 쪽이 깨진다 (2-4) | 조건부 |
| 필수였던 응답 필드를 **nullable로** | 파괴적 — non-null로 매핑하던 쪽이 NPE 또는 역직렬화 실패 | — |
| 에러 상태 코드·에러 코드 체계 변경 | 파괴적 — 클라이언트 분기 로직이 깨진다 | — |
| URL·HTTP 메서드 변경 | 파괴적 | 파괴적 |
| 새 엔드포인트 추가 | 안전 — 아무도 아직 안 부른다 | 안전 |
| JSON 필드 **순서** 변경 | 안전 — JSON 객체의 키 순서에는 의미가 없다 | 안전 |

표는 결론이고, 중요한 것은 **왜 그런가**다. 아래 네 절이 그 메커니즘이다.

### 2-2. "추가는 안전"의 진짜 이유 — 모르는 필드를 무시하는 것은 자동이 아니다

응답에 필드를 하나 더 넣었을 때 옛 클라이언트가 안 깨지는 이유는 무엇인가. **그 클라이언트의 JSON 역직렬화기(JSON 문자열을 객체로 바꿔주는 라이브러리)가 자기가 모르는 필드를 만나면 조용히 무시하도록 설정돼 있기 때문**이다.

여기서 반드시 알아야 할 사실이 있다. **그 설정은 자동이 아니고, 라이브러리마다 기본값이 다르다.**

Java 진영에서 가장 많이 쓰는 Jackson을 보자.

```java
// Jackson 단독 기본값 — 모르는 필드를 만나면 예외를 던진다
ObjectMapper mapper = new ObjectMapper();
mapper.readValue(json, OrderResponse.class);
// 서버가 응답에 "couponId" 필드를 하나 추가했을 뿐인데
// → UnrecognizedPropertyException 발생 (DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES 가 기본 true)
// "안전한 필드 추가"가 이 소비자에게는 전혀 안전하지 않다.

// Tolerant Reader 로 만드는 설정 — 모르는 필드는 무시한다
mapper.disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);

// DTO 하나에만 걸고 싶다면 클래스 애노테이션으로도 된다
@JsonIgnoreProperties(ignoreUnknown = true)
public record OrderResponse(Long id, Long amount) {}
```

**Spring Boot는 자동 구성한 `ObjectMapper`에서 이 옵션을 꺼둔다.** 그래서 Spring Boot 애플리케이션끼리 통신하는 환경에서는 "필드 추가는 안전"이 대체로 성립하고, 이 사실이 널리 통용되는 이유이기도 하다.

문제는 그 밖의 경우다. 소비자가 `new ObjectMapper()`를 직접 만들어 쓰거나, 다른 언어의 엄격한 파서를 쓰면 성립하지 않는다.

| 소비자 환경 | 모르는 필드 기본 동작 |
|---|---|
| Jackson 단독 (`new ObjectMapper()`) | 예외 — 엄격 |
| Spring Boot 자동 구성 Jackson | 무시 — 관대 |
| Kotlin `kotlinx.serialization` | 예외 — 엄격 (`ignoreUnknownKeys = true`를 켜야 관대해진다) |
| Go `encoding/json` | 무시 — 관대 |
| Swift `Codable` | 무시 — 관대 |
| JSON Schema 검증에서 `additionalProperties: false` | 검증 실패 — 엄격 |

정리하면 이렇다. **"응답 필드 추가는 안전"은 제공자 혼자 성립시킬 수 있는 명제가 아니라, 소비자 쪽 설정에 의존하는 조건부 명제다.** 그래서 이 규칙은 소비자 쪽의 원칙(2-5 Tolerant Reader)과 짝으로만 완성된다. 파트너사에 API를 열 때 "모르는 필드는 무시하도록 파싱하십시오"를 **문서의 첫 페이지에 계약으로 적어 두는** 이유가 여기 있다.

### 2-3. "삭제는 위험"의 진짜 이유 — 서버는 누가 읽는지 모른다

반대로 응답 필드를 없애면, 그 필드를 읽어 화면에 뿌리던 코드가 깨진다. 값이 `null`로 들어와 NPE가 나거나, 필수로 선언된 필드가 없다며 역직렬화 자체가 실패한다.

그런데 진짜 어려운 점은 깨진다는 사실이 아니라 **깨질지 아닐지를 미리 알 수 없다는 것**이다.

```text
요청 방향 — 서버가 볼 수 있다
  클라이언트 ── GET /v1/orders?legacyFlag=true ──▶ [서버]
                                                    액세스 로그에 남는다
                                                    "누가, 어떤 경로를, 어떤 파라미터로 불렀는가"

응답 방향 — 서버가 볼 수 없다
  [서버] ── { "id":1, "price":"10000", "amount":10000 } ──▶ 클라이언트
                                                              price 를 읽었는가?
                                                              무시했는가?
                                                              ← 서버는 알 방법이 없다
```

**이 비대칭이 이 문서에서 가장 중요한 구조다.** 요청은 서버를 통과하므로 전부 관측되지만, 응답 필드를 읽는 행위는 소비자 프로세스 안에서 일어나므로 네트워크에 아무 흔적을 남기지 않는다.

그래서 **한 번 내보낸 응답 필드는 소비자 전수 확인 전까지 내 마음대로 없앨 수 없다.** "API는 장기 계약"이라는 말의 실체가 이것이고, 3-3에서 이 비대칭을 어떻게 우회하는지가 이 문서의 실무 핵심이다.

여기서 파생되는 실천 규칙도 하나 나온다. **필드 추가는 싸 보이지만 제거는 비싸다.** 넣기는 자유고 빼기는 절차라는 비대칭이 있으므로, 판단의 무게는 넣을 때 실어야 한다. "일단 넣어두고 나중에 정리하지"가 성립하지 않는 세계다.

### 2-4. 값의 추가도 파괴적일 수 있다 — enum과 숫자 범위

여기가 반직관적인 대목이다. **필드를 하나도 건드리지 않고 값만 새로 내보내도 구버전 소비자가 죽을 수 있다.**

가장 흔한 사례가 **enum**이다. 주문 상태에 부분 환불이 생겨서 `PARTIALLY_REFUNDED`라는 값을 추가했다고 하자. 스키마상 `status`는 여전히 문자열 하나이고 필드는 추가도 삭제도 되지 않았다. 그런데 그 값을 모르는 구버전 앱은 **화면을 그리기도 전에 파싱 단계에서 죽는다.**

```java
// Before: 서버가 enum 에 값 하나를 추가하면 응답 전체를 못 읽는다
public enum OrderStatus { PAID, SHIPPED, DELIVERED, REFUNDED }

public record OrderResponse(Long id, OrderStatus status) {}

// 서버가 {"id":1, "status":"PARTIALLY_REFUNDED"} 를 내려보내는 순간
// → Jackson 이 InvalidFormatException 을 던진다
// → Spring 의 RestTemplate/WebClient 는 이를 HttpMessageNotReadableException 등으로 감싼다
// 주목할 점: status 필드 하나 때문에 id 를 포함한 응답 전체가 못 읽힌다.
//            "모르는 값은 그냥 못 그린다" 가 아니라 "아무것도 못 그린다" 가 된다.
```

```java
// After: 모르는 값이 와도 파싱이 살아남게 만든다
public enum OrderStatus {
    PAID, SHIPPED, DELIVERED, REFUNDED,
    @JsonEnumDefaultValue UNKNOWN   // 모르는 값은 전부 여기로 떨어진다
}

// 애노테이션만으로는 동작하지 않는다. 이 기능 플래그를 켜야
// Jackson 이 @JsonEnumDefaultValue 가 붙은 상수를 실제로 사용한다.
mapper.enable(DeserializationFeature.READ_UNKNOWN_ENUM_VALUES_USING_DEFAULT_VALUE);

// 기본값 상수를 두기 싫다면 null 로 받는 선택지도 있다.
// 단, null 이면 이후 분기에서 NPE 를 조심해야 하므로 기본값 쪽이 대체로 안전하다.
// mapper.enable(DeserializationFeature.READ_UNKNOWN_ENUM_VALUES_AS_NULL);
```

파싱이 살아남는 것으로 끝이 아니다. **화면 코드에도 기본 분기가 있어야 완성된다.**

```java
// 모르는 상태가 와도 화면이 그려지도록 default 분기를 반드시 둔다
String label = switch (order.status()) {
    case PAID      -> "결제 완료";
    case SHIPPED   -> "배송 중";
    case DELIVERED -> "배송 완료";
    case REFUNDED  -> "환불 완료";
    default        -> "처리 중";   // UNKNOWN 포함 — 미래의 값도 여기로 온다
};
```

같은 종류의 함정이 **숫자 값의 범위**에도 있다. 필드 타입은 그대로 정수인데 id가 21억(32비트 부호 있는 정수의 상한)을 넘어가는 순간, 그 값을 32비트로 파싱하던 소비자가 오버플로로 깨진다. JavaScript는 더 일찍 깨진다 — `Number`가 정확히 표현할 수 있는 정수는 2의 53승까지라서, 그보다 큰 id는 조용히 값이 어긋난다. **큰 id를 문자열로 내보내는 API 관행**이 여기서 나왔다.

**교훈은 하나다. 계약은 스키마만이 아니라 "그 필드에 어떤 값이 올 수 있는가"까지 포함한다.** enum에 값을 추가하는 것은 스키마 변경이 아니지만 계약 변경이고, 그래서 다른 파괴적 변경과 같은 무게로 다뤄야 한다.

### 2-5. Tolerant Reader — 받는 쪽이 관대하게 읽는다 (가산점 포인트)

여기까지 오면 결론이 하나로 모인다. **호환성은 제공자만의 책임이 아니다.** 제공자가 규칙을 다 지켜도 소비자가 엄격하게 읽으면 깨지고, 소비자가 관대하게 읽으면 제공자의 작은 실수를 흡수할 수 있다.

**Tolerant Reader(관대한 독자)**는 그 소비자 쪽 원칙의 이름이다. "받는 쪽이 관대하게 읽는다"는 뜻이고, 이름만 알면 아무 소용이 없으므로 **세 가지 구체적인 행동**으로 풀어야 한다.

**① 내가 아는 필드만 꺼내 쓴다.** 응답 전체를 내 DTO 구조와 1:1로 맞추려 들지 않는다. 필요한 필드만 선언하고 나머지는 신경 쓰지 않는다.

**② 모르는 필드는 무시한다.** 2-2의 `FAIL_ON_UNKNOWN_PROPERTIES=false` 또는 `@JsonIgnoreProperties(ignoreUnknown = true)`가 이것이다. 이 설정이 없으면 제공자의 안전한 필드 추가가 내 쪽 장애가 된다.

**③ 모르는 값이 와도 죽지 않고 기본 분기로 떨어진다.** 2-4의 enum 처리다. 파싱 단계에서 살아남고, 화면 분기에서도 `default`로 흡수한다.

셋을 한 문장으로 묶으면 이렇다. **"내가 이해하지 못하는 것 때문에 내가 이해하는 것까지 잃지 않는다."** 2-4의 코드에서 `status` 하나 때문에 `id`까지 못 읽게 됐던 것이 정확히 그 반대 상황이다.

이 원칙이 반대 방향(제공자)으로도 짝이 있다. 보내는 쪽은 엄격하게, 받는 쪽은 관대하게 — 네트워크 프로토콜 설계의 오래된 격언인 **견고성 원칙(robustness principle)**이 그대로 API 계약에 적용된 것이다. 면접에서 이 연결까지 말하면 원칙의 뿌리를 아는 답이 된다.

### 2-6. 요청 방향의 함정 — 선택 파라미터를 필수로 바꾸기

응답 쪽 이야기를 많이 했으니 요청 쪽 함정도 하나 짚는다. **선택 파라미터를 필수로 바꾸는 것도 파괴적 변경이다.**

어제까지 안 보내도 되던 값을 오늘부터 400으로 거절하면, **코드를 한 줄도 안 바꾼 클라이언트가 깨진다.** 필드를 지우지도 이름을 바꾸지도 않았는데 깨지므로, 변경 리뷰에서 놓치기 쉽다.

```java
// Before: 새 필수 파라미터를 추가 — 옛 클라이언트가 즉시 400 을 받는다
public record OrderCreateRequest(
    Long productId,
    Integer quantity,
    @NotNull String channel   // 오늘부터 필수 → 이 값을 모르는 옛 앱은 전부 실패
) {}

// After: 선택으로 받고 서버가 기본값을 채운다
public record OrderCreateRequest(
    Long productId,
    Integer quantity,
    String channel            // 선택. null 이면 서버가 "UNKNOWN" 으로 채운다
) {}
// 필수화가 정말 필요하다면 3장의 절차를 밟는다 —
// 먼저 선택으로 열어두고, 소비자가 다 보내기 시작한 것을 측정으로 확인한 뒤 필수로 조인다.
```

## 3. 깨야만 할 때 — expand → migrate → contract 3단계

### 3-1. 이름의 유래와 전체 타임라인

이름 변경, 타입 변경, 리소스 구조 개편처럼 파괴적 변경이 불가피할 때가 온다. 그때의 원칙은 하나다. **한 번에 바꾸지 않고, 옛것과 새것이 함께 사는 겹침 구간을 만든다.**

절차 이름은 그 모양에서 왔다. **넓혔다가(expand) → 옮기고(migrate) → 좁힌다(contract).** 계약의 표면적을 일시적으로 넓혀 옛것과 새것을 둘 다 지원하고, 소비자를 새것으로 옮기고, 아무도 안 쓰는 옛것을 걷어내 다시 좁히는 것이다. **DB 스키마 마이그레이션에서 온 관용어**로, 컬럼 이름을 바꿀 때 새 컬럼을 추가해 스키마를 넓히고, 데이터와 코드를 옮기고, 옛 컬럼을 지워 좁히는 그 절차와 완전히 같은 형태다.

`price`(문자열)를 `amount`(숫자)로 바꾸는 예로 시간 축을 펼치면 이렇다.

```text
시간 ──────────────────────────────────────────────────────────────────▶

              ① expand              ② migrate              ③ contract
            새것을 추가한다        소비자를 옮긴다         옛것을 제거한다

서버가       { "price": "10000",   { "price": "10000",    { "amount": 10000 }
내보내는       "amount": 10000 }     "amount": 10000 }
응답                                + Deprecation 헤더
                                    + Sunset 헤더

구버전 앱    price 를 읽는다        price 를 읽는다         price 가 없다
(옛 계약)    ✓ 정상 동작            ✓ 정상 동작             ✗ 깨진다
                                                           ↑ 그래서 이 시점 이전에
                                                             사용량 0 을 확인해야 한다

신버전 앱    아직 배포 전            amount 를 읽는다        amount 를 읽는다
(새 계약)                          ✓ 정상 동작             ✓ 정상 동작

우리가       새 필드를 추가만        옛 필드/옛 버전의       남은 소비자가 없음을
하는 일      한다 (아무도            사용량을 소비자별로     확인하고 제거한다
             영향받지 않는다)        센다 ──▶ 0 에 수렴?
```

그림에서 읽어야 할 것은 **가운데 구간의 길이가 우리가 정하는 값이 아니라는 점**이다. ①과 ③은 우리가 배포하면 끝나지만, ②는 남의 배포 주기와 사용자의 업데이트 속도가 정한다. 1-1의 현실 그대로다. **겹침 구간은 소비자의 배포 주기보다 길어야 의미가 있다.**

### 3-2. ① expand — 옛것을 유지한 채 새것을 추가한다

이 단계의 성공 기준은 하나다. **옛 클라이언트가 아무 변화도 느끼지 못해야 한다.** 즉 이 단계는 순수한 호환 변경(1-3)만으로 이뤄진다.

```java
// Before: 파괴적 변경 — 필드 이름과 타입을 "정리"하고 싶어서 그냥 바꿔버린다
public record OrderResponse(
    Long id,
    String price   // 이걸 amount(숫자) 로 바꾸면 price 를 읽던 옛 클라이언트가 전부 깨진다
) {}

// After(expand): 새 필드를 추가하고 옛 필드를 당분간 병행 제공한다
public record OrderResponse(
    Long id,
    @Deprecated String price,   // 유지. 사용량 0 이 확인되면 ③ contract 에서 제거한다
    Long amount                 // 새 계약: 숫자 타입 + 명확한 이름
) {
    // 두 필드가 어긋나면 소비자마다 다른 값을 보게 되므로,
    // 하나의 원본에서 둘을 파생시켜 항상 같은 값이 되도록 보장한다.
    public static OrderResponse from(Order order) {
        long amount = order.getAmount();
        return new OrderResponse(order.getId(), String.valueOf(amount), amount);
    }
}
```

주석에 적은 것이 이 단계의 숨은 함정이다. **병행 제공 기간에 두 필드가 서로 다른 값을 갖게 되면 겹침 구간이 오히려 사고를 만든다.** 옛 필드는 새 필드에서 파생시키고, 절대 따로 계산하지 않는다.

엔드포인트 수준의 expand도 같은 원리다. `/v2/orders`를 추가하되 `/v1/orders`는 그대로 둔다. 그리고 **내부 구현은 하나로 통일하고 v1은 얇은 어댑터(변환 계층)로만 유지**한다 — v1과 v2의 로직을 각각 구현하면 겹침 구간 내내 같은 버그를 두 번 고치게 된다.

### 3-3. ② migrate — 소비자를 옮기고, 옮겨졌는지 측정한다

이 단계가 3단계 중 유일하게 어렵고, 그래서 실무 실력이 드러나는 곳이다. 두 가지 일을 한다.

**고지(告知)는 쉬운 쪽이다.** 세 채널을 병행한다.

| 채널 | 대상 | 수단 |
|---|---|---|
| 문서·변경 로그·파트너 공지 | 사람 | "무엇이, 언제까지, 왜" 바뀌는지 |
| 응답 헤더 | 기계 | `Deprecation`, `Sunset`, 대체 리소스를 가리키는 `Link` |
| 직접 연락 | 아직 안 옮긴 특정 소비자 | 아래 측정으로 뽑은 명단 |

```http
HTTP/1.1 200 OK
Deprecation: true
Sunset: Wed, 31 Dec 2026 23:59:59 GMT
Link: <https://docs.example.com/migration/v2>; rel="deprecation"
```

`Sunset` 헤더는 "이 자원이 언제 응답하지 않게 되는가"를 HTTP 날짜로 알리는 표준 헤더다(RFC 8594). 게이트웨이에서 옛 경로에 일괄로 붙일 수 있어 서비스 코드를 안 건드려도 된다는 점이 실무 이점이다.

위 예시의 `Deprecation: true`는 표준화 이전 초안 시절의 형태다. 표준(RFC 9745)이 정한 값은 폐기 시점을 담는 날짜(`Deprecation: @1798761599`)이지만, 초안 형태가 이미 널리 퍼져 있어 둘 다 실무에서 보인다. 두 형식의 차이와 어느 쪽을 쓸지는 `03-api-versioning-strategies.md`에서 다룬다.

**측정이 어려운 쪽이고, 여기가 이 문서의 실무 핵심이다.** 고지만으로는 아무도 안 옮긴다는 것이 먼저 알아야 할 현실이고, 그래서 "옮겨졌는가"를 숫자로 확인해야 한다.

그런데 2-3에서 본 비대칭이 여기서 발목을 잡는다. **응답에 필드를 넣어주는 쪽이라 서버는 그 필드를 누가 읽는지 원리적으로 알 수 없다.** 그래서 측정은 직접 세는 대신 우회한다. 네 가지 수단이 있고, 위쪽이 쉽고 아래로 갈수록 강력하다.

**(1) 요청 쪽에 남는 것을 센다.** 옛 **엔드포인트**(`/v1/orders`)나 옛 **파라미터** 사용량은 액세스 로그에 그대로 남으므로 정확히 셀 수 있다. **그래서 파괴적 변경을 필드 수준이 아니라 엔드포인트 수준으로 표현하면 측정이 쉬워진다** — 이것이 버저닝의 실용적 가치 중 하나다.

**(2) 소비자를 식별해 호출량을 나눠 센다.** "총 호출량 1,000건"은 쓸모가 없고, "누가 부르는가"가 있어야 연락할 수 있다. 식별 축은 셋이다.

- **API 키·파트너 id**: 외부 소비자에게 가장 확실하다. 발급 단위가 곧 연락 단위다.
- **클라이언트 버전 헤더**: 앱이 `X-App-Version: 3.2.1`을 보내게 해두면 버전별 트래픽 곡선을 그릴 수 있다. **이걸 처음부터 심어두는 것이 사후에 할 수 있는 어떤 조치보다 강력하다.**
- **User-Agent**: 위 둘이 없을 때의 차선책이다. 위조되기 쉽고 형식이 제각각이라 집계가 지저분하다.

```java
// 마이그레이션 기간: 옛 엔드포인트에 deprecation 신호를 붙이고 호출자를 집계한다
@GetMapping("/v1/orders/{id}")
public OrderResponseV1 getOrderV1(
        @PathVariable Long id,
        @RequestHeader(value = "X-App-Version", required = false) String appVersion,
        @RequestHeader(value = "User-Agent", required = false) String ua) {

    // 총량이 아니라 "누가" 를 함께 태그해야 연락할 명단이 나온다.
    deprecationMetrics.count("orders-v1", appVersion, ua);

    // 내부는 신모델 하나로 통일하고, 경계에서만 v1 형태로 변환한다.
    // v1/v2 로직을 각각 구현하면 겹침 구간 내내 버그를 두 번 고치게 된다.
    return orderV1Adapter.from(orderService.find(id));
}
```

**(3) 소비자 주도 계약 테스트(CDC)를 깔아둔다.** 소비자가 "나는 이 응답의 이 필드를 이렇게 쓴다"를 계약으로 등록하고(Pact, Spring Cloud Contract), 제공자 빌드가 그 계약을 검증하는 방식이다. **"누가 뭘 읽는지 모른다"는 문제를 정면으로 해결하는 유일한 방법**이지만, 소비자가 협조해야 하고 미리 깔아둬야 한다는 전제가 있다. 사내 서비스 간에는 현실적이고, 불특정 다수의 외부 소비자에게는 적용하기 어렵다.

**(4) brownout — 짧게 일부러 끊어보고 누가 항의하는지 본다.** 위 셋으로도 확신이 안 설 때 쓰는 마지막 수단이다. 이름은 정전을 뜻하는 blackout이 아니라 **전압만 낮추는 brownout**에서 왔다 — 완전히 내리는 게 아니라 잠깐 흐리게 만들어 본다는 뜻이다.

- 방법: 정해진 짧은 시간 동안 옛 필드를 `null`로 비우거나, 옛 엔드포인트를 `410 Gone`으로 응답한다.
- 신호: 그 시간대에 문의가 오거나, 특정 앱 버전의 크래시율이 튀거나, 파트너 시스템의 에러가 늘면 **그쪽이 아직 읽고 있었다는 증거**다.
- 안전 규칙 넷: **예고하고**(언제 몇 분간 할지 미리 공지), **짧게**(수 분 단위), **트래픽 일부에만**(전체를 끊지 않는다), **즉시 되돌릴 수 있게**(피처 플래그로 켜고 끈다).
- 돈이나 안전에 직결되는 API에는 쓰지 않는다. 측정을 위해 실제 사고를 내는 셈이 되기 때문이다.

### 3-4. ③ contract — 사용량 0을 확인하고 제거한다

마지막 단계의 조건은 둘 중 하나다. **사용량이 0이거나, 남은 소비자와 합의된 종료 시점이 지났거나.** 후자가 필요한 이유는 연락이 닿지 않는 소비자가 항상 남기 때문이고, 그래서 종료 근거를 **사후 협상이 아니라 사전 계약**(문서에 명시한 지원 기간)으로 만들어 두는 것이 중요하다.

제거는 한 번에 하지 않는다. **바로 삭제하기 전에 되돌릴 수 있는 차단 기간을 둔다.** (가산점 포인트)

```text
사용량 0 확인
   │
   ▼
[1단계] 410 Gone 으로 응답 — 코드는 아직 살아 있고, 되돌리려면 설정 하나만 바꾸면 된다
   │     이 기간에 문의가 오면 즉시 되살린다 = 놓친 소비자를 싸게 발견하는 장치
   │
   │  (문제 없이 지나가면)
   ▼
[2단계] 코드·테스트·문서에서 실제 제거
```

`410 Gone`을 쓰는 이유는 상태 코드가 의미를 정확히 전달하기 때문이다. `404 Not Found`는 "여기 없다(일시적일 수도 있다)"이지만, **`410 Gone`은 "여기 있었지만 영구히 사라졌다"**는 뜻이라 소비자가 재시도할 대상이 아님을 알 수 있다.

## 4. 꼬리질문 대비 포인트

### "호환성이 깨지는 걸 배포 전에 어떻게 잡나요?"

사람 리뷰만으로는 못 잡는다는 것부터 인정하고 시작한다. 필드 하나 이름 바꾸는 PR은 리뷰에서 "좋네요"를 받기 쉽다 — 그게 남의 앱을 깬다는 사실이 코드에는 안 적혀 있기 때문이다. 그래서 체계로 잡는다.

**① OpenAPI 스펙 diff 검사.** CI에서 이전 버전의 스펙과 비교해 "필드 삭제, 타입 변경, 필수화" 같은 파괴적 변경을 자동 검출하고 빌드를 실패시킨다. 가장 싸고 효과가 큰 방어선이다.

**② 소비자 주도 계약 테스트(CDC).** 3-3의 (3)이다. 스펙 diff가 "규칙 위반"을 잡는다면, CDC는 "실제로 누가 무엇을 쓰는지"를 잡는다.

**③ 스냅샷/직렬화 테스트.** 응답 JSON을 파일로 고정해 두고 달라지면 실패시킨다. 의도한 변경이면 스냅샷을 갱신하는데, **그 갱신 diff가 리뷰에 뜬다는 것 자체가 가치**다 — "이 응답이 바뀝니다"가 리뷰어 눈앞에 놓인다.

세 층의 역할이 다르다는 것까지 말하면 정리가 깔끔하다. **스펙 diff는 규칙을, CDC는 실제 소비를, 스냅샷은 변경의 가시성을 지킨다.**

### "필드의 '의미'가 바뀌는 건 스펙 diff로도 못 잡지 않나요?"

맞다. 그래서 가장 위험하다.

구체적인 예가 설득력을 만든다. **주문 응답의 `amount`가 "세금 포함 금액"에서 "세금 별도 금액"으로 바뀌었다고 하자.** 필드 이름도 그대로, 타입도 그대로 `Long`, JSON 스키마도 완전히 동일하다. 스펙 diff는 아무 변화가 없다고 보고하고 CI는 통과한다.

그런데 그 값을 화면에 뿌리던 모든 클라이언트가 **틀린 금액을 조용히 표시한다.** 예외도 안 나고 에러 로그도 없다. 사용자가 결제 금액과 화면 금액이 다르다고 신고할 때까지 아무도 모른다. 계산에 쓰던 소비자라면 그사이 잘못된 값이 남의 DB에 쌓인다.

**이런 변경은 호환 변경으로 위장한 파괴적 변경**이다. 그래서 규칙은 이렇게 닫는다. **타입이 아니라 의미가 바뀌면 반드시 새 필드로 만든다.**

```text
잘못된 방법: amount 의 의미만 바꾼다
  { "amount": 10000 }   (세금 포함)  →  { "amount": 9091 }   (세금 별도)
  스키마 동일, 아무도 못 잡음, 전 소비자가 조용히 틀린 값을 본다

올바른 방법: 3장의 절차를 그대로 태운다
  expand   → { "amount": 10000, "amountExcludingTax": 9091 }   둘 다 제공
  migrate  → 소비자를 amountExcludingTax 로 이전, 사용량 측정
  contract → 합의된 시점에 amount 정리 (또는 amount 는 세금 포함 의미로 영구 유지)
```

의미 변경은 **이름으로 드러내는 것이 최선의 방어**라는 결론까지 붙이면 좋다. `amount`처럼 모호한 이름 대신 `amountIncludingTax`처럼 의미를 이름에 박아두면, 애초에 "같은 필드의 뜻만 바꾸자"는 유혹이 생기지 않는다.

### "API 버저닝을 하면 되는데 왜 이렇게까지 필드 수준을 관리하나요?" (시니어 변별 포인트)

버저닝은 만능이 아니라 **최후 수단**이라는 것이 답의 골자다. 버전을 올릴 때마다 치르는 비용이 있다.

**첫째, 겹침 기간 동안 서버가 v1과 v2를 둘 다 운영한다.** 코드도 테스트도 모니터링도 문서도 이중화된다. 3-2에서 본 어댑터 전략으로 줄일 수는 있어도 0이 되지는 않는다.

**둘째, 소비자는 아무 이득 없이 이전 작업을 한다.** 새 기능이 생긴 것도 아닌데 코드를 고치라는 요청이라, 우선순위가 밀리는 것이 당연하다. 특히 외부 파트너에게는 **우리 사정 때문에 그쪽 개발 리소스를 쓰라는 요구**다.

**셋째, 이전을 강제할 수단이 없어 v1이 몇 년씩 살아남는다.** 1-1의 꼬리가 여기서 다시 나온다.

그래서 성숙한 팀의 전략은 이렇다. **필드 수준의 호환 변경(추가)으로 최대한 버티고, 파괴적 변경은 모아서 드물게, 마이그레이션 절차와 함께 낸다.** 파괴적 변경을 하나씩 낼 때마다 버전을 올리면 v5, v6이 쌓이므로, 여러 개를 모아 한 번에 처리하는 것이 소비자의 이전 비용도 줄인다.

정리 문장은 이것이다. **버전 번호는 계약 관리의 시작이 아니라 호환 유지에 실패했을 때 지불하는 비용이다.** (버저닝 방식 자체의 비교는 `03-api-versioning-strategies.md`)

### "모바일 앱처럼 강제 업데이트가 안 되는 소비자는 어떻게 하나요?"

**근본 대책은 앱에 최소 지원 버전 체크를 처음부터 심어두는 것**이다. 앱 기동 시 서버에 "내 버전은 3.2.1인데 아직 써도 되나"를 묻고, 서버가 강제 업데이트·권장 업데이트·정상 중 하나를 답하는 구조다.

이게 왜 근본 대책인가 하면, **이 장치가 없으면 sunset이 사실상 불가능하기 때문**이다. 옛 앱을 종료시킬 수단이 없으니 어댑터를 영원히 유지하는 것 외에 방법이 없다. 그리고 이 장치는 나중에 넣을 수 없다 — 지금 심어도 지금 이후 버전부터만 동작하고, 이미 나가 있는 옛 앱에는 적용되지 않는다. **초기 설계에 넣어야만 하는 몇 안 되는 항목** 중 하나다.

이미 그 장치가 없다면 선택지는 둘이다. ① 구버전 트래픽이 자연 감소할 때까지 어댑터를 유지하고, **잔존율 기준을 미리 정해**(예: 전체 트래픽의 일정 비율 미만이 되면 종료) 의사결정을 감으로 하지 않는다. ② 앱 안에서 서버가 그리는 화면(웹뷰나 서버 주도 UI)을 쓰는 영역이라면 그쪽으로 옮겨 클라이언트 배포 없이 고칠 수 있게 만든다.

### "Deprecation 고지는 어디에, 어떻게 남기나요?"

3-3의 표가 답의 골격이다. 세 채널을 병행한다 — **문서·변경 로그(사람용)**, **응답 헤더 `Deprecation`·`Sunset`·`Link`(기계용, 게이트웨이에서 일괄 부착 가능)**, **사용량 기반 직접 연락(실제로 옛것을 호출 중인 소비자 명단)**.

여기에 두 가지를 덧붙이면 답이 완성된다.

**고지 기간은 소비자의 배포 주기보다 길어야 의미가 있다.** 3-1의 타임라인에서 겹침 구간의 길이를 우리가 정하지 못하는 이유가 이것이다. 모바일 앱이 소비자라면 "심사 + 배포 + 사용자 업데이트 확산"까지가 한 주기이고, 외부 파트너라면 계약서에 명시된 사전 고지 기간을 따른다.

**그리고 고지는 측정과 짝일 때만 작동한다.** 공지만 띄우고 사용량을 안 보면 "알렸으니 됐다"고 착각한 채 종료일을 맞게 되고, 그날 남의 시스템이 깨진다. **고지는 이전을 부탁하는 것이고, 측정은 이전이 실제로 일어났는지 확인하는 것**이라 서로를 대체하지 않는다.

## 한 줄 요약

서버는 하나인데 클라이언트는 여러 시대가 동시에 살아 있는 구조(앱스토어 심사·업데이트 안 하는 사용자·통제 밖 파트너) 때문에 하위 호환은 미덕이 아니라 제약이고, 변경은 "추가는 안전, 삭제·의미 변경은 파괴적"으로 분류하되 **"추가는 안전"이 소비자의 역직렬화 설정에 기대는 조건부 명제**임을 알고 Tolerant Reader(모르는 필드 무시, 모르는 enum 값은 기본 분기)를 짝으로 요구해야 하며 — enum 값 추가처럼 스키마가 그대로인 변경도 구버전을 죽일 수 있다 — 파괴적 변경이 불가피하면 expand(병행 제공) → migrate(고지 + 소비자 단위 사용량 측정, 필요하면 brownout) → contract(사용량 0 확인 후 410을 거쳐 제거)의 겹침 구간 절차를 밟는데, 응답 필드를 누가 읽는지는 서버가 원리적으로 알 수 없다는 비대칭 때문에 **측정 수단을 미리 심어두는 것**이 이 절차 전체의 성패를 가른다.
