# 벌크 API의 부분 실패 응답 설계 — 성공/실패 이분법을 넘는 응답 모델

> 핵심 관전 포인트: **첫 결정은 기술이 아니라 도메인 질문이다 — 이 묶음이 원자적(전부 성공 아니면 전부 취소, 중간 상태가 남지 않음)이어야 하는가, 부분 성공을 허용하는가. 원자적이면 전체를 한 트랜잭션으로 묶고 일반 에러 응답 하나로 끝나지만, 묶음이 클수록 트랜잭션이 길어지고 1건 때문에 99건이 계속 반려되는 처리량 문제를 떠안는다. 부분 성공이면 응답이 "항목별 결과 배열"로 바뀐다 — 클라이언트가 항목마다 부여한 식별자로 매칭하고(배열 인덱스에 의존하면 서버가 중복 제거·재정렬·병렬 처리를 하는 순간 대응이 어긋난다), 항목마다 성공/실패와 표준 에러 code를 담고, 전체 HTTP status는 200으로 준다. 200인 이유가 이 문제의 채점 포인트다 — 4xx를 주면 클라이언트 HTTP 라이브러리와 게이트웨이의 공통 재시도 로직이 **바디를 열어보지 않고** 상태 코드 숫자만으로 전체 실패로 판정해 요청 전체를 재시도하고, 이미 성공한 97건이 중복 처리된다. 대신 요청 수준의 실패(바디 파싱 불가, 인증 실패, 건수 초과)는 항목별 결과 이전의 문제이므로 4xx가 맞다 — "요청 수준은 status, 항목 수준은 바디"로 층을 나누는 것이 계약의 골격이다. 그리고 실패 항목만 골라 재시도할 수 있도록 항목 에러에 재시도 가능 여부를 드러내고, itemId를 항목별 멱등성 키로 삼아 이미 성공한 항목의 재전송이 저장된 결과의 재생으로 흡수되게 만드는 것까지가 계약이다 — 이 결정이 클라이언트의 재시도 코드 구조를 결정한다.**

---

## 0. 질문 + 의도

**질문**: "여러 건을 한 번에 처리하는 벌크 API에서 일부만 실패하면 응답을 어떻게 설계하나요?"

**출제 의도**: 100건 중 3건 실패 시 전체 롤백인지 부분 성공인지는 클라이언트의 재시도 설계까지 바꾸는 계약 결정이다. 성공/실패 이분법을 넘어 응답 모델을 설계하는지 확인한다.

## 1. 첫 번째 설계 결정 — 원자성은 도메인이 정한다

### 1-1. 전제 — 원자성이 무엇인가

이 절의 주인공이 되는 단어부터 정의하고 시작한다.

**원자성(atomicity)은 "전부 성공하거나 전부 없던 일이 되거나, 그 중간 상태가 남지 않는 성질"이다.** 이름은 "더 이상 쪼갤 수 없는 알갱이(atom)"에서 왔다. 안에 여러 단계가 들어 있어도 바깥에서 보면 하나의 알갱이처럼 통째로 일어나거나 통째로 안 일어난다는 뜻이다.

이미 써 본 적이 있는 개념이다. **트랜잭션의 성질을 부르는 ACID의 A가 바로 이 원자성이고, `@Transactional`을 붙였을 때 얻는 것이 그것이다.** 메서드 안에서 INSERT를 세 번 하다가 두 번째에서 예외가 나면 첫 번째 INSERT도 남지 않는다. 세 개의 쓰기가 하나의 알갱이로 묶였기 때문이다.

벌크 API의 첫 질문은 그 알갱이의 크기를 어디까지로 볼 것인가다. **요청에 담긴 100건 전체가 하나의 알갱이인가, 아니면 100개의 알갱이가 한 봉투에 담겨 온 것인가.** 답이 갈리는 순간 응답 모델 전체가 갈린다.

### 1-2. 두 갈래 — 원자적 묶음과 부분 성공 묶음

"일부 실패 시 어떻게 응답하나"보다 앞선 질문이 있다. **일부 실패라는 상태를 허용할 것인가.** 이건 기술 선택이 아니라 업무 요구다.

**원자적이어야 하는 묶음**부터 보자. 계좌 이체의 출금과 입금, 회계 분개의 차변과 대변처럼 **묶음 전체가 하나의 의미 단위**인 경우다. 출금만 되고 입금이 안 된 중간 상태는 업무적으로 존재해서는 안 되는 상태다. 한 건이라도 실패하면 전체를 되돌려야 한다.

이때 서버는 전체를 한 트랜잭션으로 처리하고, 실패하면 **일반 에러 응답 하나**(어느 항목이 원인인지를 덧붙여)로 답하면 된다. **응답 모델이 단순해지는 것이 이 선택의 이득**이다 — 소비자 입장에서도 "성공했나?"에 예/아니오로 답할 수 있으니 분기가 하나다.

**부분 성공이 자연스러운 묶음**은 성격이 다르다. 대량 사용자 초대, 상품 100건 태그 일괄 지정, 메시지 벌크 발송처럼 **항목이 서로 독립적**인 경우다. 3번 사용자의 이메일 형식이 틀렸다고 해서 나머지 97명의 초대를 취소할 이유가 전혀 없다. "성공한 97건은 살리고 실패한 3건만 알려달라"가 소비자가 원하는 것이고, 여기서부터 응답 모델 설계가 시작된다(이하 이 문서의 본론).

**면접에서 이 갈림길을 먼저 말하는 것이 중요하다.** 부분 성공 응답 스키마는 "부분 성공을 허용하기로 결정한 다음"의 이야기이므로, 바로 스키마부터 그리기 시작하면 결정 하나를 건너뛴 답이 된다.

### 1-3. 원자성은 공짜가 아니다

원자적 묶음 쪽을 고를 때 함께 떠안는 대가가 둘 있다. 이걸 알고 고르는 것과 모르고 고르는 것이 다르다.

**하나, 묶음이 클수록 트랜잭션이 길어진다.** 100건을 한 트랜잭션으로 묶으면 그 트랜잭션은 100건이 다 끝날 때까지 열려 있고, 그동안 잡은 행 잠금도 계속 유지된다. 잠금 유지 시간이 길어지면 같은 행을 건드리는 다른 요청들이 줄줄이 대기하고, 트랜잭션 자체가 타임아웃에 걸릴 위험도 커진다.

**둘, 1건의 반복 실패가 전체 배치를 영구 반려시킨다.** 100건 중 3번 항목의 데이터가 잘못돼 있으면, 그 3번이 고쳐질 때까지 나머지 99건은 **몇 번을 재전송해도 계속 반려된다.** 소비자가 할 수 있는 일은 실패 원인을 추측해 항목을 하나씩 빼 보는 것뿐이다.

그래서 현실적 절충이 나온다. **원자성이 꼭 필요한 최소 단위로 묶음을 쪼개고, 그 사이는 부분 성공으로 둔다.** 이체 100건을 보낸다면 "출금+입금" 쌍 하나가 원자 단위이고, 100개의 쌍 사이에는 원자성이 필요 없다. 그러면 응답은 "쌍 100개 중 97쌍 성공"이라는 부분 성공 모델이 된다.

## 2. 부분 성공 응답 스키마와 상태 코드

### 2-1. 응답은 항목별 결과의 목록이 된다

부분 성공을 허용하는 순간, "성공했나요?"라는 단일 질문에 대한 단일 답은 성립하지 않는다. **응답은 항목별 결과의 목록이 되어야 한다.**

```jsonc
// before: 요약만 주는 응답 — 어느 3건인지 몰라 재시도가 불가능하다
{ "success": false, "message": "100건 중 3건 실패" }
```

이 응답을 받은 소비자가 할 수 있는 일이 무엇인지 생각해 보면 문제가 분명해진다. 실패한 3건이 어느 것인지 모르므로 고칠 수도 없고, 실패한 것만 다시 보낼 수도 없다. **남은 선택지는 100건 전체를 다시 보내는 것뿐이고, 그러면 이미 성공한 97건이 중복 처리된다.** 요약만 주는 응답은 소비자를 가장 위험한 선택지로 몬다.

```jsonc
// after: 항목별 결과 + 요약 — 실패 항목만 골라 재시도할 수 있다
// POST /users/bulk-invite  요청:
{
  "items": [
    { "itemId": "req-001", "email": "a@example.com" },  // itemId: 클라이언트가 부여한다
    { "itemId": "req-002", "email": "b@example" },
    { "itemId": "req-003", "email": "c@example.com" }
  ]
}

// 응답 (HTTP 200):
{
  "summary": { "total": 3, "succeeded": 2, "failed": 1 },
  "results": [
    { "itemId": "req-001", "status": "SUCCESS", "userId": 501 },
    { "itemId": "req-002", "status": "FAILED",
      "code": "USER-002", "message": "이메일 형식이 아닙니다" },
    { "itemId": "req-003", "status": "SUCCESS", "userId": 502 }
  ]
}
```

이 응답이 갖춰야 할 요소가 셋이고, 하나씩 따로 볼 값이 있다 — 매칭 키(2-2), 항목별 에러의 모양(2-3), 요약(2-4)이다.

### 2-2. 매칭 키 — 배열 인덱스는 어떻게 깨지는가

응답의 결과 하나가 요청의 어느 항목에 대한 답인지를 소비자가 알아내야 한다. 가장 손쉬운 방법은 **배열 인덱스**다 — "요청의 n번째 항목에 대한 답이 응답의 n번째 결과"라고 약속하는 것이다.

이 약속의 문제는 어디에도 적혀 있지 않다는 데 있다. 응답 JSON 어디에도 "이건 3번째 항목의 결과입니다"라는 정보가 없고, 순서라는 **암묵적 계약**만 있다. 그리고 암묵적 계약은 서버가 그 사실을 잊는 순간 조용히 깨진다.

구체적으로 어떤 변경이 이 대응을 깨는지 나열해 보면, 전부 서버 입장에서는 지극히 정상적인 개선이라는 것이 보인다.

```java
// 요청 100건이 들어왔다. 아래 넷 중 하나라도 하면 인덱스 대응이 깨진다.

// ① 중복 제거 — 같은 이메일이 두 번 들어왔으니 하나로 합친다
List<Item> targets = items.stream().distinct().toList();
// 요청은 100건인데 결과는 98건. 99번째부터 전부 한 칸씩 밀린다.

// ② 유효성 검사에서 걸린 항목을 앞으로 모은다 — "에러부터 보여주자"
List<Result> results = new ArrayList<>();
results.addAll(invalidItems.stream().map(Result::validationFailed).toList());
results.addAll(processed);
// 개수는 100건 그대로인데 순서가 완전히 뒤바뀐다. 개수가 맞아서 더 위험하다.

// ③ 병렬 처리 후 완료 순서로 결과를 담는다 — 처리량을 4배로 올렸다
items.parallelStream().forEach(item -> results.add(process(item)));
// 완료 순서는 비결정적이다. 같은 요청을 두 번 보내면 결과 순서가 다를 수도 있다.

// ④ 실패 항목을 재시도 큐로 빼고 성공분만 즉시 응답한다
// 요청 100건, 응답 97건.
```

②번이 특히 위험하다. **개수가 100건 그대로라서 클라이언트가 어긋남을 감지할 방법이 없다.** 개수가 다르면 최소한 "뭔가 이상하다"는 방어 코드에라도 걸리는데, 순서만 바뀐 경우는 조용히 잘못된 화면을 그린다. 3번 사용자의 화면에 7번 사용자의 에러가 뜨는 식이다.

그래서 **클라이언트가 항목마다 식별자를 부여하고 응답이 그 식별자를 되돌려주는 방식**이 명시적이고 안전하다. 위 네 가지 변경을 아무리 해도 `itemId`가 결과에 실려 있으면 대응이 깨지지 않는다.

```jsonc
// 서버가 순서를 바꾸든 개수를 줄이든, itemId가 있으면 매칭이 성립한다
{ "itemId": "req-042", "status": "FAILED", "code": "USER-002" }
```

이 식별자는 뒤에서 **항목별 멱등성 키로도 재활용된다**(3-2). 매칭을 위해 도입한 필드가 재시도 안전성까지 떠받치게 되는 것이 이 설계의 좋은 점이다.

### 2-3. 항목별 에러는 단건 API와 같은 에러 스키마로

항목 하나가 실패했을 때 그 실패를 무슨 모양으로 담을 것인가. 답은 **새로 만들지 말고 이미 있는 표준 에러 스키마를 그대로 쓰는 것**이다.

이 저장소의 표준 에러 응답(`05-error-response-body-standardization.md`)은 이렇게 생겼다 — 기계 판독용 `code`, 사람용 `message`, 검증 실패 상세 `errors[]`, 추적 진입점 `traceId`. 항목 실패도 정확히 같은 필드 구성으로 담는다.

```jsonc
// 단건 API가 실패했을 때의 응답 바디 (05번 문서의 표준 스키마)
{
  "code": "USER-002",
  "message": "이메일 형식이 아닙니다",
  "errors": [ { "field": "email", "reason": "이메일 형식이 아닙니다" } ],
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}

// 벌크 API의 항목 실패 — 매칭 키와 상태만 얹고 나머지는 위와 같은 모양이다
{
  "itemId": "req-002",
  "status": "FAILED",
  "code": "USER-002",
  "message": "이메일 형식이 아닙니다",
  "errors": [ { "field": "email", "reason": "이메일 형식이 아닙니다" } ]
}
```

**같은 모양으로 맞추는 이유는 소비자의 코드 재사용이다.** 소비자는 이미 단건 API용 에러 처리 로직을 갖고 있다 — `code`로 분기해 화면을 정하고, 모르는 코드는 status 기반으로 폴백하고, `errors[]`의 `field`를 보고 폼의 해당 칸에 빨간 줄을 긋는 코드다. 항목 에러가 같은 모양이면 그 함수를 항목 하나하나에 그대로 돌려 쓸 수 있다.

반대로 벌크 API만 `{"reason": "..."}` 같은 다른 모양을 쓰면, 소비자는 같은 실패를 두 가지 방식으로 처리하는 코드를 갖게 된다. **에러 스키마 표준화의 목적이 "파서를 한 번만 짜게 하는 것"이었는데, 벌크에서 그 원칙이 깨지면 표준화가 절반만 성립한 상태가 된다.**

`traceId`처럼 요청 전체에 하나뿐인 값은 항목마다 반복할 필요 없이 응답 최상위에 한 번 두면 된다.

### 2-4. 요약(summary) 필드

응답에 요약을 함께 주는 이유는 **소비자의 대다수가 "전부 성공했는지"만 궁금하기 때문**이다.

```jsonc
"summary": { "total": 100, "succeeded": 97, "failed": 3 }
```

요약이 없으면 소비자는 "전부 성공했는가"를 알기 위해 결과 100건을 전부 순회하며 세어야 한다. 그리고 그 순회 코드는 모든 소비자가 각자 짜게 된다. 서버가 이미 알고 있는 숫자이므로 그냥 실어 주는 편이 낫다.

실용적인 효과가 하나 더 있다. **`failed`가 0인지 아닌지로 최상단 분기가 가능해지므로, 정상 경로에서는 결과 배열을 아예 안 열어봐도 된다.** 100건 중 100건이 성공하는 것이 압도적 다수인 API에서는 이 분기 하나가 소비자 코드를 상당히 단순하게 만든다.

### 2-5. 부분 실패는 왜 200인가 — 4xx가 만드는 인과 사슬

**여기가 이 문제의 채점 포인트다.** "3건이 실패했으니 400이 맞지 않나"는 직관이 왜 위험한지를, 결과가 아니라 인과로 설명할 수 있어야 한다.

전제 하나를 먼저 깔아야 한다. **HTTP 상태 코드는 우리 API를 직접 쓰는 클라이언트 코드만 읽는 것이 아니다.** 요청과 응답이 지나가는 길목의 여러 층 — HTTP 클라이언트 라이브러리, API 게이트웨이, 리버스 프록시, APM — 이 전부 이 숫자를 읽고 자기 동작을 결정한다. **그리고 이들은 바디를 열어보지 않는다.** 우리 응답 바디의 키 이름을 모르고 알 필요도 없으며, 상태 코드 숫자 하나만 본다(이 이중 축 이야기는 `05-error-response-body-standardization.md` 2-1과 2-2가 자세히 다룬다).

이 전제 위에서 4xx를 주면 무슨 일이 벌어지는지 사슬로 펴 보면 이렇다.

```
[서버]  100건 중 97건 처리 완료, 3건 실패
   │    "실패가 섞여 있으니 400이 정직하지" 라고 판단한다
   ▼
[응답]  HTTP 400 Bad Request
        바디: { summary: {succeeded: 97, failed: 3}, results: [ ...100건... ] }
        ★ "97건은 성공했다"는 사실은 오직 바디 안에만 있다
   │
   ▼
[중간 층]  클라이언트 HTTP 라이브러리 / API 게이트웨이 / 리버스 프록시
   │
   │    ★★ 이 층은 바디를 열어보지 않는다 ★★
   │       - 재시도 정책, 서킷 브레이커, 에러율 지표가 전부 상태 코드 숫자에만 걸려 있다
   │       - 바디를 파싱하려면 우리 API의 스키마를 알아야 하는데, 이들은 모른다
   ▼
[판정]  "이 요청은 실패했다"
        97건이 성공했다는 정보는 이 층에 도달하지 못하고 버려진다
   │
   ▼
[동작]  공통 재시도 로직이 요청 전체를 다시 보낸다 — 100건 그대로
   │
   ▼
[서버]  같은 100건을 다시 처리한다
   │
   ▼
[결과]  ★ 이미 성공한 97건이 두 번 처리된다
        초대 메일 2통, 포인트 2배 지급, 태그 중복 부착
```

**이 사슬의 핵심 고리는 "바디를 안 열어본다"이다.** 여기가 끊기기 때문에 그 뒤가 전부 잘못된다. 서버는 바디에 정확한 정보를 다 담았고 거짓말한 것도 없는데, 그 정보를 읽을 수 없는 층이 판단을 내려버리는 것이다.

부작용은 재시도만이 아니다. **성공분이 유실된 것처럼 보이는 문제**도 함께 온다. 클라이언트 애플리케이션 코드에도 대개 "HTTP 에러면 공통 에러 핸들러로 보낸다"는 인터셉터가 있고, 그 핸들러는 바디를 성공 응답 파서로 넘기지 않는다. 그래서 화면에는 "요청에 실패했습니다"만 뜨고, 실제로는 97명이 초대된 상태가 된다.

그래서 관례는 이렇게 정리된다. **"요청 자체는 정상 접수·처리되었고 결과가 항목별로 다르다"는 의미로 200을 주고, 항목별 성패는 바디에 담는다.** 200이 뜻하는 것은 "모든 항목이 성공했다"가 아니라 **"이 요청을 우리가 제대로 받아 끝까지 처리했다"**이다.

같은 논리로, **전 건이 실패해도 200 + 전부 FAILED가 일관적이다.** 처리 자체는 정상적으로 끝났기 때문이다. "실패가 절반을 넘으면 status를 바꾼다" 같은 혼합 규칙은 소비자 분기를 복잡하게 만들 뿐이고, 임계값을 넘나드는 요청마다 클라이언트의 처리 경로가 달라지는 불안정한 계약이 된다.

### 2-6. 207 Multi-Status와 206 Partial Content

상태 코드 목록을 뒤지다 보면 이 상황에 맞아 보이는 코드가 둘 나온다. 둘 다 정확히 짚어야 한다.

**207 Multi-Status**는 WebDAV 명세(RFC 4918)에서 정의된 코드로, **"여러 리소스에 대한 결과를 한 응답에 담는다"**는 뜻이다. WebDAV는 HTTP를 파일 시스템처럼 쓰기 위한 확장이라 "이 폴더 아래 파일 전부를 옮겨라" 같은 요청이 자연스럽고, 그때 파일마다 결과가 다를 수 있어서 이 코드가 만들어졌다. **의미상으로는 벌크 API의 부분 실패와 정확히 같은 상황이다.**

문제는 인지도다. **일반 REST 생태계에서 이 코드를 아는 클라이언트 라이브러리·게이트웨이·모니터링 도구가 드물다.** 다행히 207은 2xx 계열이라 대부분의 도구가 "성공"으로 분류하므로 2-5의 재시도 사슬 문제는 생기지 않는다. 다만 특별 취급을 기대할 수 없으므로 얻는 것도 별로 없다 — 결국 소비자가 바디를 열어봐야 하는 것은 200일 때와 같다.

**쓴다면 "우리 API에서 207은 항목별 결과를 확인하라는 뜻"임을 문서에 명시해야 한다.** 표준 코드조차 계약 없이는 안전하지 않다는 것이 여기서 얻을 교훈이다. 같은 결론이 조합 API의 부분 실패를 다루는 `13-aggregation-api-partial-failure-contract.md`에도 나오는데, 그 문서는 "섹션별 성패"를, 이 문서는 "항목별 성패"를 다룰 뿐 코드 선택의 근거는 동일하다.

**206 Partial Content**는 이름 때문에 자주 오해받는다. 짚고 넘어갈 값이 있다.

**206의 "부분"은 결과의 일부가 아니라 자원의 일부 바이트 구간을 뜻한다.** 이 코드는 **Range 요청 전용**이다 — 클라이언트가 `Range: bytes=1000-1999` 같은 헤더로 "이 파일의 1000번째부터 1999번째 바이트만 달라"고 요청했을 때, 서버가 "요청한 구간만 보낸다"는 뜻으로 돌려주는 코드다. 동영상을 중간부터 재생할 때, 끊긴 다운로드를 이어받을 때 쓰인다.

**"항목 100개 중 97개만 성공했다"와는 아무 관계가 없다.** 벌크 응답에 206을 쓰면 Range를 이해하는 중간 장비가 `Content-Range` 헤더를 찾다가 없어서 혼란스러워할 수 있고, 얻는 것은 하나도 없다.

### 2-7. 요청 수준 실패와 항목 수준 실패를 층으로 나눈다

2-5에서 "부분 실패에 4xx를 주면 안 된다"고 했지만, **4xx가 맞는 경우는 따로 있다.** 이 구분을 못 하면 "벌크 API는 무조건 200"이라는 잘못된 규칙이 된다.

기준은 **그 실패가 항목별 결과를 만들기 전에 일어났는가**다.

| 실패의 층 | 예 | 항목별 결과가 존재하는가 | 응답 |
|---|---|---|---|
| 요청 수준 | 바디 JSON 파싱 불가 | 아니오 — 어떤 항목이 있는지도 모른다 | 400 + 표준 에러 바디 |
| 요청 수준 | 인증·인가 실패 | 아니오 — 처리를 시작하지 않았다 | 401 / 403 |
| 요청 수준 | 허용 건수 초과 (3-4) | 아니오 — 접수를 거절했다 | 400 (또는 413) + 한도를 알리는 에러 code |
| 항목 수준 | 3번 항목의 이메일 형식 오류 | 예 — 100건의 결과가 있다 | 200 + results 배열 |
| 항목 수준 | 7번 항목 저장 중 일시 오류 | 예 | 200 + results 배열 |

**"요청 수준의 실패는 4xx, 항목 수준의 실패는 200 + results"로 층을 나누는 것이 계약의 골격이다.** 이렇게 나누면 소비자의 코드도 두 층으로 깔끔하게 갈린다 — HTTP 에러면 요청 자체를 고쳐서 다시 보내야 하고, 200이면 바디를 열어 항목별로 처리하면 된다.

## 3. 재시도 설계 — 응답 모델이 멱등성을 요구한다

부분 성공 계약의 진짜 어려움은 응답 그 자체가 아니라 **그다음 동작**에 있다. 소비자는 응답을 받고 나서 실패한 3건만 골라 다시 보내게 되는데, 그 재시도가 안전하게 성립하려면 응답 모델이 몇 가지를 더 갖춰야 한다.

### 3-1. 재시도 가능 여부를 항목 에러에 담는다

실패한 3건을 그대로 다시 보내면 되는가. 실패의 종류에 따라 다르다.

- **"이메일 형식이 아닙니다"**: 데이터를 고치지 않는 한 몇 번을 다시 보내도 똑같이 실패한다. **비재시도성**이다. 이건 사용자에게 노출해 고치게 해야 할 문제다.
- **"일시적 저장 실패"**: 잠시 후 다시 보내면 성공할 수 있다. **재시도성**이다. 사람 개입 없이 자동 재시도 대상으로 삼아도 된다.

이 구분이 응답에 드러나지 않으면 소비자는 실패 3건 전부를 같은 방식으로 다룰 수밖에 없다. 전부 자동 재시도하면 형식 오류 항목을 영원히 반복 전송하게 되고, 전부 사용자에게 노출하면 자동으로 회복될 수 있었던 항목까지 사람 손을 타게 된다.

드러내는 방법은 둘이다. **항목별 에러 code 체계 자체에 그 구분이 드러나게 하거나**(검증 실패 계열과 일시 오류 계열의 접두사를 나눈다), **`retryable: true/false` 필드를 따로 두거나**다. 어느 쪽이든 목적은 하나 — **소비자가 재시도 대상을 사람 판단 없이 기계적으로 고를 수 있게 하는 것**이다.

운영 관점의 부산물도 있다. 항목 실패 중 서버 오류 비율은 서버 상태를 보여주는 지표라 집계·알람 대상이지만, 입력 오류 비율은 소비자의 데이터 품질 문제라 알람으로 울리면 노이즈다. **구분이 없으면 이 둘이 한 지표에 섞여 알람이 무의미해진다.**

### 3-2. 항목 처리는 멱등해야 한다 — itemId를 항목별 멱등성 키로

재시도 설계에서 가장 중요한 대목이다.

먼저 상황을 정확히 그려야 한다. 소비자가 항상 "실패한 3건만" 골라 보내는 것은 아니다. **응답을 아예 못 받는 경우**가 있기 때문이다. 서버가 100건을 다 처리하고 응답을 쓰는 도중에 연결이 끊기면, 클라이언트가 아는 것은 "응답을 못 받았다"뿐이다. 몇 건이 처리됐는지, 아니 하나라도 처리됐는지조차 모른다.

이 불확실성은 원리적으로 해소할 수 없다(`06-idempotency-key-design.md` 1-2). 그래서 클라이언트의 유일한 선택지는 **요청 전체를 그대로 재전송하는 것**이 되고, 그 순간 이미 성공한 97건이 두 번 처리될 위험이 생긴다.

해법은 06번 문서의 설계를 항목 단위로 축소해 적용하는 것이다. **요청의 `itemId`를 항목별 멱등성 키로 삼는다.** 06번의 두 핵심 개념을 그대로 가져온다.

- **선점 후 처리**: "이미 처리했나?"를 조회로 확인하고 없으면 처리하는 것이 아니라, **유니크 제약이 걸린 키를 먼저 꽂아 보고 꽂혔으면 내가 처음**이라고 판정한다. 검사와 선점이 SQL 한 문장에서 원자적으로 끝나므로 동시에 도착한 두 요청이 나란히 통과하는 틈이 없다.
- **재생(replay)**: 이미 처리된 키로 다시 온 요청에는 처리를 다시 하지 않고 **저장해 둔 최초 결과를 그대로 돌려준다.** 실패를 알리는 것이 아니라 성공했을 때와 같은 답을 주는 것이 핵심이다 — 그래야 소비자가 "1번 보낸 것과 2번 보낸 것"을 구분할 수 없게 된다.

전체를 재전송했을 때 실제로 무슨 일이 벌어지는지 타임라인으로 보면 이렇다.

| 시각 | 클라이언트 | 서버 | 실제 부수효과 (초대 메일) |
|---|---|---|---|
| t0 | 100건 전송 (`req-001` ~ `req-100`) | 접수 | |
| t1 | 대기 | 97건 처리 성공, 3건 실패 판정. 성공한 97개 `itemId`를 결과와 함께 저장 | 97통 발송 |
| t2 | 대기 | 응답을 쓰던 중 연결이 끊긴다 | |
| t3 | 결과 불명 — 100건을 그대로 재전송 | 접수 | |
| t4 | 대기 | `req-001`~`req-097`: 이미 처리된 키 → **처리하지 않고 저장된 결과를 재생** | 0통 (중복 없음) |
| t5 | 대기 | `req-098`~`req-100`: 처리된 적 없는 키 → 이번에 처리 | 성공분만 추가 발송 |
| t6 | 100건 전체 결과 수신 | 응답 | **누적 100통, 중복 0통** |

t4가 이 설계의 전부다. **97건이 "이미 처리됨"으로 조용히 흡수되고, 소비자는 그 사실을 알 필요조차 없다.** 응답에는 t1에서 성공했던 것과 똑같은 결과가 담겨 나가므로, 소비자 코드에는 "재전송이었다"는 분기 자체가 필요 없다.

여기서 반드시 정해야 하는 세부가 하나 있다. **`itemId`가 어느 범위에서 유일해야 하는가**다. 요청 하나 안에서만 유일하면 안 된다 — 어제 보낸 배치의 `req-001`과 오늘 보낸 배치의 `req-001`이 다른 사람인데 같은 키가 되어, 오늘의 초대가 어제 결과의 재생으로 삼켜진다. 06번 문서가 키 스코프를 `(user_id, idempotency_key)`로 잡았던 것과 같은 문제다.

선택지는 둘이고, **어느 쪽이든 계약 문서에 적어야 계약이 된다.**

- **`itemId` 자체를 소비자 단위로 유일한 값(UUID 등)으로 요구한다.** 서버 구현이 단순하다. 대신 "요청마다 새 값을 만들지 말고, 같은 항목의 재전송에는 같은 값을 유지하라"까지 계약에 적어야 한다.
- **요청 수준의 배치 키를 따로 받고 `(배치 키, itemId)`를 복합 키로 쓴다.** 그러면 `itemId`는 배치 안에서만 유일하면 되므로 소비자 부담이 적다. 대신 재전송할 때 배치 키도 같이 유지해야 한다.

멱등성 레코드의 보관 기간(TTL)도 같은 이유로 계약이다. **보관 기간이 지난 뒤에 도착한 재전송은 처음 보는 키로 처리되므로 그대로 중복이 된다** — TTL은 성능 파라미터가 아니라 안전 파라미터라는 06번 2-7의 결론이 여기에도 그대로 적용된다.

### 3-3. 처리 순서와 독립성을 계약에 적는다

응답 모델만큼이나 자주 빠지는 계약 항목이 있다. **항목 간 순서를 보장하는가, 앞 항목의 실패가 뒤 항목 처리에 영향을 주는가.**

소비자는 이걸 모르면 잘못된 가정 위에서 요청을 만든다. 예를 들어 "1번 항목에서 그룹을 만들고 2번 항목에서 그 그룹에 사용자를 넣는" 요청을 보내는 소비자가 있을 수 있다. 서버가 병렬로 처리한다면 이 요청은 대부분 실패하고, 가끔 우연히 성공한다 — **가장 나쁜 종류의 버그다.**

부분 성공 모델과 자연스럽게 짝을 이루는 계약은 이것이다. **"각 항목은 독립적으로 처리되며 순서는 보장하지 않는다."** 항목이 서로 독립적이라는 것이 애초에 부분 성공을 선택한 근거였으므로(1-2), 순서 보장을 약속하지 않는 것이 일관적이다. 그리고 순서를 보장하지 않는다고 명시해야 2-2의 병렬 처리 같은 최적화를 나중에 자유롭게 넣을 수 있다.

### 3-4. 건수 한도 — 근거를 수치로 검산한다

벌크 API에는 **요청당 최대 건수**를 계약에 명시한다. 무제한이면 페이로드 크기·처리 시간·트랜잭션 길이가 전부 소비자 손에 좌우되고, 타임아웃과 부분 실패 확률만 커지기 때문이다.

문제는 그 한도를 어떻게 정하느냐다. "1,000건쯤이면 되겠지"는 근거가 아니다. **근거는 곱셈 하나로 나온다 — 건당 처리 시간 × 한도가 이 요청의 실질 타임아웃 상한 안에 들어와야 한다.**

여기서 "실질 타임아웃 상한"이 무엇인지가 중요하다. 요청 하나는 클라이언트 SDK, CDN, 로드밸런서, Nginx, 앱이라는 여러 층을 지나고 **각 층이 자기 대기 상한을 들고 있으므로 그중 가장 짧은 값이 이 요청의 실질 상한**이다. 잘 정렬된 스택에서도 그 값은 10초 안팎이다(`08-network-http/13-nginx-tomcat-timeout-buffer-mismatch.md`의 정렬 예시 기준으로 앱 자체 가드가 10초, 그 안쪽 최악 처리 시간이 8초다).

이 기준으로 흔한 설정을 검산해 보자.

| 항목 | 값 | 근거 |
|---|---|---|
| 건당 처리 시간 (p99) | 20ms | 운영 관측값 |
| 계약에 적힌 최대 건수 | 1,000건 | 감으로 정한 값 |
| 직렬 처리 최악 시간 | **20초** | 20ms × 1,000건 = 20,000ms |
| 이 요청의 실질 타임아웃 상한 | 8~10초 | 정렬된 계층 스택의 가장 짧은 값 |
| 판정 | **이미 깨져 있다** | 20초 > 10초 — 상한의 2배 |

**1,000건이라는 한도는 이미 지켜질 수 없는 값이다.** 최악의 경우 이 요청은 반드시 중간 층에서 끊기고, 그러면 클라이언트는 결과를 못 받아 전체를 재전송하며, 그 재전송이 또 20초짜리라 또 끊긴다. **한도를 둔 목적이 타임아웃 방지였는데 그 한도 자체가 타임아웃을 보장하는 값인 것이다.**

역산해서 지켜질 수 있는 한도를 구하면 이렇다.

| 방식 | 계산 | 허용 건수 |
|---|---|---|
| 직렬 처리, 응답 예산 8초 | 8,000ms ÷ 20ms | **400건** |
| 직렬 처리, 예산의 절반을 여유로 남김 | 400 ÷ 2 | **200건** |
| 4레인 병렬 처리, 응답 예산 8초 | 20,000ms ÷ 4 = 5,000ms → 8초 안에 들어옴 | 1,000건 |

세 번째 줄이 흥미롭다. **병렬 처리로 한도를 유지하는 선택지도 있지만 공짜가 아니다.** 요청 하나가 DB 커넥션 4개를 동시에 잡으므로 동시 벌크 요청 수만큼 커넥션 소모가 배로 늘고, 무엇보다 **완료 순서가 비결정적이 되어 2-2에서 본 배열 인덱스 매칭이 깨진다.** 병렬화를 하려면 `itemId` 매칭이 먼저 있어야 한다는 뜻이다.

한도를 넘는 요청은 **요청 수준의 실패로 거절한다**(2-7). 그리고 거절만 하면 소비자가 막히므로 대안을 계약에 함께 적는다 — **여러 요청으로 나누어 보내거나, 한도를 크게 넘는 작업이라면 비동기 모델로 넘긴다.**

비동기 모델이란 요청을 즉시 처리하지 않고 `202 Accepted`로 접수증만 돌려준 뒤 작업 자체를 리소스로 승격시켜, 클라이언트가 그 URI를 폴링해 진행 상태와 결과를 받아가는 구조다(`10-long-running-operations-202-polling-callback.md`). **10만 건 일괄 처리처럼 애초에 HTTP 응답 시간 안에 들어올 수 없는 작업은 벌크 API의 한도를 조절할 문제가 아니라 모델을 바꿔야 할 문제**라는 것이 이 계산의 결론이다.

페이로드 크기도 함께 본다. 항목 하나가 200바이트라면 1,000건은 약 200KB다. 이 자체는 큰 값이 아니지만, 게이트웨이·프록시·서버에 각각 요청 본문 크기 한도가 걸려 있으므로 **건수 한도와 본문 크기 한도 중 먼저 걸리는 쪽이 실질 한도**가 된다. 둘 다 문서에 적어야 소비자가 미리 나눠 보낼 수 있다.

### 3-5. 실무에서 이 패턴이 보이는 곳 (가산점 포인트)

"성공 응답 안에 실패가 들어 있는" 모양은 처음엔 어색하지만, **항목 독립적인 벌크 처리의 표준 형태**다. 대형 API들이 이미 같은 결론에 도달해 있다는 것을 사례로 들면 설득력이 붙는다.

**Elasticsearch `_bulk` API.** 색인·수정·삭제 요청 여러 건을 한 번에 보내는 API인데, 응답이 정확히 이 문서의 모양이다.

```jsonc
// POST /_bulk 응답 — HTTP 상태 코드는 200이다
{
  "took": 30,
  "errors": true,          // 요약 플래그: 실패가 하나라도 있으면 true
  "items": [               // 항목별 결과 배열 — 요청 순서와 같은 순서로 담긴다
    { "index": { "_id": "1", "status": 201, "result": "created" } },
    { "index": { "_id": "2", "status": 400,
                 "error": { "type": "...", "reason": "..." } } }
  ]
}
```

세 가지를 짚을 만하다. **첫째, 개별 항목이 실패해도 HTTP 상태 코드는 200이다** — 2-5의 결론과 같다. **둘째, `errors` 불리언이 2-4의 요약 필드 역할을 한다** — 전수 순회 없이 최상단 분기가 가능하다. **셋째, 항목마다 HTTP 상태 코드와 같은 형태의 `status`를 담는다** — 항목 결과를 단건 API의 결과와 같은 어휘로 표현한 것이라 2-3의 "항목별 에러는 단건 API와 같은 스키마로"와 같은 발상이다. 참고로 ES는 요청당 건수 상한을 못 박기보다 **요청 크기와 노드 부담을 기준으로 조정하라고 안내**한다.

**AWS SQS `SendMessageBatch`.** 메시지 여러 건을 한 번에 큐에 넣는 API다.

- 요청의 각 엔트리에 **클라이언트가 부여한 `Id`**가 붙고, 그 값은 배치 안에서 유일해야 한다. 2-2의 `itemId`가 이것이다.
- 응답은 **`Successful`과 `Failed` 두 목록으로 나뉘고**, 각 엔트리가 자기 `Id`를 달고 돌아온다. 실패 엔트리에는 에러 `Code`와 `Message`, 그리고 **`SenderFault` 불리언**이 담긴다.
- `SenderFault`가 3-1과 정확히 같은 정보다 — **실패의 책임이 보낸 쪽에 있는지(그러면 요청을 고치기 전엔 재시도가 무의미하다) 서비스 쪽에 있는지(그러면 재시도로 회복될 수 있다)**를 기계가 판단할 수 있게 해 준다.
- 그리고 이 API는 **요청당 최대 10건**이라는 한도를 명시한다. 3-4에서 본 "건수 한도는 계약에 적는다"의 실물이다.

**결과를 두 목록으로 나누는 SQS 방식과 하나의 배열에 담는 방식의 차이**도 언급할 만하다. 두 목록으로 나누면 소비자가 실패분을 골라내는 필터링이 필요 없어 재시도 코드가 짧아지고, 하나의 배열은 요청 순서와의 대응이 남아 있어 화면에 그대로 늘어놓기 좋다. **어느 쪽이든 "매칭 키가 결과에 실려 있다"는 것이 본질이고, 배열이냐 두 목록이냐는 그 위의 취향이다.**

## 4. 꼬리질문 대비 포인트

### "부분 성공일 때 HTTP 상태코드는 뭘로 주나? 207을 써도 되나?"

200 + 바디의 항목별 결과가 일반적 관례다. **부분 실패를 4xx/5xx로 주면 HTTP 계층(라이브러리 재시도, 게이트웨이, 모니터링)이 바디를 열어보지 않고 전체 실패로 해석해, 성공분까지 재시도되는 중복 처리가 난다** — 이 인과 사슬을 말하는 것이 이 질문의 핵심이다.

207 Multi-Status는 WebDAV에서 온 코드로 의미상으로는 정확하지만, WebDAV 밖에서는 인지도가 낮아 특별 취급을 기대할 수 없다. 채택하려면 문서에 의미를 명시해야 한다. 206 Partial Content는 이 상황과 무관하다 — **Range 요청 전용이고, 여기서 "부분"은 결과의 일부가 아니라 자원의 일부 바이트 구간을 뜻한다.**

단, 바디 파싱 불가·인증 실패·건수 초과처럼 **"요청 수준"의 실패는 항목별 결과 이전의 문제라 4xx가 맞다.** 요청 수준과 항목 수준의 실패를 층으로 나눠 답하는 것이 포인트다.

### "실패한 3건만 재시도하게 하려면 응답에 무엇이 있어야 하나?"

세 가지다. **① 어느 항목이 실패했는지 특정할 매칭 키** — 배열 인덱스 의존보다 클라이언트가 부여한 `itemId`가 안전하다. 서버가 중복 제거를 하거나, 유효성 실패 항목을 앞으로 모으거나, 병렬 처리 후 완료 순서로 담는 순간 인덱스 대응이 어긋나기 때문이다. **② 재시도할 가치가 있는지 판단할 정보** — 항목별 에러 code에 검증 실패(비재시도성)와 일시 오류(재시도성)의 구분이 드러나야 한다. **③ 재시도가 안전하다는 보장** — `itemId`를 항목별 멱등성 키로 삼아 이미 처리된 항목의 재전송이 저장된 결과의 재생으로 흡수되게 한다.

**셋 중 하나라도 빠지면 소비자는 "전체 재시도"라는 가장 위험한 선택지로 몰린다.** 이 한 줄로 닫으면 세 요소가 왜 함께여야 하는지가 드러난다.

### "전체 롤백(원자적)과 부분 성공은 어떤 기준으로 정하나?" (시니어 변별 포인트)

기준은 항목 간 의존성과 실패의 업무적 의미다. 항목들이 하나의 의미 단위(이체의 출금+입금)면 원자적이어야 하고, 서로 독립(초대 100건)이면 부분 성공이 소비자 가치가 크다.

여기에 두 가지를 얹으면 시니어답다. **① 이건 백엔드 혼자 정할 수 없는 제품 결정이다.** 같은 "실패 3건"도 화면에서 무엇을 보여줄지가 완전히 달라지므로 기획·프론트와 합의해 스펙에 명시해야 한다. **② 원자성은 공짜가 아니다.** 묶음이 클수록 트랜잭션이 길어져 락 유지 시간과 타임아웃 위험이 커지고, 1건의 반복 실패가 전체 배치를 영구 반려시킨다.

그래서 결론은 **"원자성이 꼭 필요한 최소 단위로 묶음을 쪼개고, 그 사이는 부분 성공으로"**가 현실적 절충이라는 것이다.

### "벌크 요청의 건수 제한은 왜 필요한가?"

무제한 벌크는 처리 시간과 페이로드 크기를 소비자가 결정하게 만든다. 건수가 커질수록 HTTP 타임아웃 안에 못 끝날 확률, 메모리 사용량, (원자적 설계라면) 트랜잭션 길이가 함께 자란다. 타임아웃으로 응답을 못 받으면 소비자는 전체 재시도를 하게 되어 부분 실패 문제를 더 키운다.

**숫자로 근거를 대면 답의 무게가 달라진다.** 건당 20ms이고 한도가 1,000건이면 최악 20초인데, 계층별 타임아웃이 잘 정렬된 스택에서도 실질 상한은 10초 안팎이다 — **그 한도는 이미 지켜질 수 없는 값이다.** 응답 예산 8초를 기준으로 역산하면 직렬 처리에서는 400건이 상한이고, 여유를 두면 200건이다.

그래서 요청당 최대 건수를 계약에 명시하고 초과 시 요청 수준 4xx로 거절하며, **그 한도를 넘는 작업은 여러 요청으로 나누거나 비동기 작업(`202` + 상태 조회) 모델로 넘기는 것이 맞다.** 10만 건짜리 작업은 한도를 조절할 문제가 아니라 모델을 바꿔야 할 문제라는 선까지 그으면 좋다.

### "일부는 입력 오류, 일부는 서버 오류로 실패했다면 응답에서 구분해야 하나?"

구분해야 한다 — **소비자의 다음 행동이 다르기 때문이다.** 입력 오류 항목은 데이터를 고치기 전엔 재시도가 무의미하므로 사용자에게 노출해야 하고, 서버 오류 항목은 그대로 재시도하면 되므로 자동 재시도 대상이다. 항목별 에러를 표준 에러 code 체계로 담으면 이 구분이 자연히 따라온다.

운영 관점도 함께 말하면 좋다. **항목 실패 중 서버 오류 비율은 서버 상태의 지표라 집계·알람 대상이지만, 입력 오류는 소비자의 데이터 품질 문제라 알람 노이즈다** — 구분이 없으면 이 둘이 한 지표에 섞여, 파트너가 잘못된 CSV를 올린 날 서버 알람이 울린다.

## 한 줄 요약

벌크 API의 부분 실패 설계는 "원자적이냐 부분 성공이냐"라는 도메인 결정에서 출발한다 — 부분 성공을 택했다면 응답은 200 + 클라이언트가 부여한 식별자로 매칭되는 항목별 결과 배열(표준 에러 code 포함)이 되어야 하고, 200인 이유는 4xx를 주는 순간 **바디를 열어보지 않는** HTTP 계층이 전체 실패로 판정해 이미 성공한 97건까지 재시도시키기 때문이며, 대신 파싱 불가·인증 실패·건수 초과 같은 요청 수준 실패는 4xx로 층을 갈라야 한다. 여기에 실패 항목만 안전하게 재시도할 수 있도록 재시도 가능 여부 구분과 itemId 기반 항목별 멱등성(선점 후 처리 + 재생)을 갖추고, 건수 한도는 감이 아니라 "건당 처리 시간 × 한도 ≤ 실질 타임아웃 상한"으로 검산해 정하는 것 — 성공/실패 이분법이 아니라 소비자의 재시도 설계까지 포함한 계약을 만드는 일이다.
