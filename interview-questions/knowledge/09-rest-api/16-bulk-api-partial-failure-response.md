# 벌크 API의 부분 실패 응답 설계 — 성공/실패 이분법을 넘는 응답 모델

> 핵심 관전 포인트: **첫 결정은 기술이 아니라 도메인 질문이다 — 이
> 묶음이 원자적(전부 성공 아니면 전부 취소)이어야 하는가, 부분 성공을
> 허용하는가. 원자적이면 전체를 한 트랜잭션으로 묶고 일반 에러 응답
> 하나로 끝난다. 부분 성공이면 응답이 "항목별 결과 배열"로 바뀐다:
> 클라이언트가 준 항목 식별자로 매칭하고, 항목마다 성공/실패와 에러
> code를 담고, 전체 HTTP status는 200으로 준다(부분 실패를 4xx/5xx로
> 주면 성공한 항목까지 재시도되어 중복 처리가 난다). 그리고 실패
> 항목만 골라 재시도할 수 있도록 항목 처리를 멱등하게 만드는 것까지가
> 계약이다 — 이 결정이 클라이언트의 재시도 코드 구조를 결정한다.**

---

## 0. 질문 + 의도

**질문**: "여러 건을 한 번에 처리하는 벌크 API에서 일부만 실패하면
응답을 어떻게 설계하나요?"

**출제 의도**: 100건 중 3건 실패 시 전체 롤백인지 부분 성공인지는
클라이언트의 재시도 설계까지 바꾸는 계약 결정이다. 성공/실패
이분법을 넘어 응답 모델을 설계하는지 확인한다.

## 1. 첫 번째 설계 결정 — 원자성은 도메인이 정한다

"일부 실패 시 어떻게 응답하나"보다 앞선 질문이 있다: **일부 실패라는
상태를 허용할 것인가.** 이건 기술 선택이 아니라 업무 요구다.

- **원자적이어야 하는 묶음**: 계좌 이체의 출금+입금, 회계 분개처럼
  묶음 전체가 하나의 의미 단위인 경우. 한 건이라도 실패하면 전체를
  되돌려야 한다. → 서버는 전체를 한 트랜잭션으로 처리하고, 실패 시
  **일반 에러 응답 하나**(+ 어느 항목이 원인인지)로 답하면 된다.
  응답 모델이 단순해지는 대신, 묶음이 클수록 트랜잭션이 길어지고
  1건 때문에 99건이 계속 반려되는 처리량 문제를 안는다.
- **부분 성공이 자연스러운 묶음**: 대량 사용자 초대, 상품 100건 태그
  일괄 지정, 메시지 벌크 발송처럼 항목이 서로 독립적인 경우. "성공한
  97건은 살리고 실패한 3건만 알려달라"가 소비자가 원하는 것이다.
  → 이때부터 응답 모델 설계가 시작된다 (이하 이 문서의 본론).

면접에서 이 갈림길을 먼저 말하는 것이 중요하다 — 부분 성공 응답
스키마는 "부분 성공을 허용하기로 결정한 다음"의 이야기다.

## 2. 부분 성공 응답 스키마 — 항목별 결과와 매칭 키

부분 성공을 허용하는 순간, "성공했나요?"라는 단일 답은 성립하지
않는다. 응답은 **항목별 결과의 목록**이 되어야 한다.

```jsonc
// ❌ before: 요약만 주는 응답 — 어느 3건인지 몰라 재시도가 불가능하다
{ "success": false, "message": "100건 중 3건 실패" }
```

```jsonc
// ✅ after: 항목별 결과 + 요약 — 실패 항목만 골라 재시도할 수 있다
// POST /users/bulk-invite  요청:
{
  "items": [
    { "itemId": "req-001", "email": "a@example.com" },  // itemId: 클라이언트가 부여
    { "itemId": "req-002", "email": "b@example" },
    { "itemId": "req-003", "email": "c@example.com" }
  ]
}

// 응답 (HTTP 200):
{
  "summary": { "total": 3, "succeeded": 2, "failed": 1 },
  "results": [
    { "itemId": "req-001", "status": "SUCCESS", "userId": 501 },
    { "itemId": "req-002", "status": "FAILED",
      "code": "USER-002", "message": "이메일 형식이 아닙니다" },
    { "itemId": "req-003", "status": "SUCCESS", "userId": 502 }
  ]
}
```

설계 포인트:

- **매칭 키**: 배열 인덱스(요청의 n번째 = 응답의 n번째)에만 의존하면
  암묵적 계약이라 깨지기 쉽다 — 서버가 중복 제거·재정렬이라도 하면
  끝이다. **클라이언트가 항목마다 식별자(itemId)를 부여**하게 하고
  응답이 그걸 되돌려주는 것이 명시적이고 안전하다. 이 식별자는 뒤에서
  항목별 멱등성 키로도 재활용된다.
- **항목별 에러는 단건 API와 같은 에러 스키마로**: 항목 실패의
  code/message 구조를 표준 에러 응답(05 문서)과 같은 모양으로 맞춘다.
  소비자가 단건 API용으로 짠 에러 처리 로직을 항목 단위로 재사용할
  수 있다.
- **요약(summary) 필드**: 소비자의 90%는 "전부 성공했는지"만 궁금하다.
  전수 순회 없이 분기할 수 있도록 집계를 함께 준다.

## 3. HTTP 상태코드 — 부분 실패는 왜 200인가

부분 실패 응답의 상태코드에서 갈리는 것이 많다.

- **부분 실패를 4xx/5xx로 주면 안 된다**: HTTP 에러 status를 받은
  클라이언트(특히 재시도 로직이 있는 HTTP 라이브러리·게이트웨이)는
  "요청 전체가 실패했다"고 해석한다. 성공한 97건까지 포함해 전체를
  재시도하면 **중복 처리**가 나고, 바디를 안 열어보는 공통 에러
  처리에 걸려 성공분이 유실된 것처럼 보인다. "요청 자체는 정상
  접수·처리되었고 결과가 항목별로 다르다"는 의미로 **200 + 바디의
  항목별 상태**가 일반적 관례다.
- **207 Multi-Status는?**: WebDAV에서 유래한 "여러 리소스의 상태를
  한 응답에 담는다"는 코드로, 의미상으로는 정확히 이 상황이다. 다만
  일반 REST 생태계에서 인지도가 낮아 클라이언트 라이브러리·모니터링이
  특별 취급하지 않는 경우가 많다. 쓴다면 "우리 API에서 207은 항목별
  결과를 확인하라는 뜻"임을 문서에 명시해야 한다 — 표준 코드조차
  계약 없이는 안전하지 않다.
- **4xx가 맞는 경우는 따로 있다**: 요청 **전체**가 잘못된 경우 —
  바디 파싱 불가, 인증 실패, 허용 건수 초과 — 는 항목별 결과 이전의
  문제이므로 일반 에러 응답(4xx)이 맞다. "요청 수준의 실패는 4xx,
  항목 수준의 실패는 200 + results"로 층을 나누는 것이 계약의 골격이다.
- 전 건이 실패해도 요청 처리 자체는 정상이므로 200 + 전부 FAILED가
  일관적이다. "몇 건 이상 실패하면 status를 바꾸는" 식의 혼합 규칙은
  소비자 분기를 복잡하게 만들 뿐이다.

## 4. 실패 항목 재시도 설계 — 응답 모델이 멱등성을 요구한다

부분 성공 계약의 진짜 어려움은 응답 그 자체가 아니라 **그다음
동작**이다. 소비자는 실패한 3건만 골라 다시 보내게 된다.

- **재시도 가능 여부를 항목 에러에 담는다**: "이메일 형식 오류"는
  재시도해도 똑같이 실패한다(비재시도성). "일시적 저장 실패"는
  재시도하면 성공할 수 있다(재시도성). 항목 에러 code 체계에 이
  구분이 드러나야(또는 `retryable: true/false` 필드) 소비자가 재시도
  대상을 기계적으로 고를 수 있다.
- **항목 처리는 멱등해야 한다**: 네트워크 타임아웃으로 응답을 못 받은
  클라이언트는 전체를 다시 보낼 수 있다. 이때 이미 성공했던 97건이
  중복 처리(초대 메일 2번 발송)되면 안 된다. 요청의 itemId를 항목별
  멱등성 키로 삼아 "이미 처리한 itemId면 이전 결과를 돌려준다"로
  만들면, 부분 성공 + 재시도 조합이 안전해진다. (멱등성 키 설계
  자체는 이 카테고리의 결제 멱등성 문서 주제와 연결된다.)
- **처리 순서·독립성 명시**: 항목 간 순서 보장이 있는지, 앞 항목
  실패가 뒤 항목 처리에 영향을 주는지도 계약에 적는다. "각 항목은
  독립적으로 처리되며 순서는 보장하지 않는다"가 부분 성공 모델의
  자연스러운 짝이다.

## 5. 실무에서 이 패턴이 보이는 곳 (가산점 포인트)

이 응답 모델은 대형 API들이 이미 검증한 패턴이다. Elasticsearch의
`_bulk` API는 전체 200과 함께 항목별 성공/실패와 에러 정보를 배열로
돌려주고, AWS SQS의 배치 전송 API도 성공 목록과 실패 목록(항목
id + 에러 코드 + 재시도 가능 여부 성격의 정보)을 분리해 응답한다.
"성공 응답 안에 실패가 들어있는" 이 모양이 처음엔 어색하지만, 항목
독립적인 벌크 처리의 표준 형태라는 것을 사례로 들면 설득력이 있다.
또 하나의 실무 팁: 벌크 API에는 **최대 건수 제한**(예: 요청당
1,000건)을 계약에 명시한다 — 무제한이면 페이로드·처리 시간·트랜잭션
길이가 소비자 손에 좌우되어 타임아웃과 부분 실패 확률만 커진다.

## 6. 꼬리질문 대비 포인트

### "부분 성공일 때 HTTP 상태코드는 뭘로 주나? 207을 써도 되나?"

200 + 바디의 항목별 결과가 일반적 관례다. 부분 실패를 4xx/5xx로 주면
HTTP 계층(라이브러리 재시도, 게이트웨이, 모니터링)이 전체 실패로
해석해 성공분까지 재시도되는 중복 처리가 난다. 207 Multi-Status는
의미상 정확하지만 WebDAV 밖에서는 인지도가 낮아, 채택하려면 문서에
의미를 명시해야 한다. 단, 바디 파싱 불가·인증 실패·건수 초과처럼
"요청 수준"의 실패는 항목별 결과 이전의 문제라 4xx가 맞다 — 요청
수준과 항목 수준의 실패를 층으로 나눠 답하는 것이 포인트.

### "실패한 3건만 재시도하게 하려면 응답에 무엇이 있어야 하나?"

세 가지다. ① 어느 항목이 실패했는지 특정할 매칭 키 — 배열 인덱스
의존보다 클라이언트 부여 itemId가 안전하다. ② 재시도할 가치가 있는지
판단할 정보 — 항목별 에러 code에 검증 실패(비재시도성)와 일시
오류(재시도성)의 구분이 드러나야 한다. ③ 재시도가 안전하다는 보장 —
itemId를 멱등성 키로 삼아 이미 처리된 항목의 재전송이 중복 처리되지
않게 한다. 셋 중 하나라도 빠지면 소비자는 "전체 재시도"라는 가장
위험한 선택지로 몰린다.

### "전체 롤백(원자적)과 부분 성공은 어떤 기준으로 정하나?" (시니어 변별 포인트)

기준은 항목 간 의존성과 실패의 업무적 의미다. 항목들이 하나의 의미
단위(이체의 출금+입금)면 원자적이어야 하고, 서로 독립(초대 100건)이면
부분 성공이 소비자 가치가 크다. 여기에 두 가지를 얹으면 시니어답다:
① 이건 백엔드 혼자 정할 수 없는 **제품 결정**이라 기획·프론트와
합의해 스펙에 명시해야 한다는 것 — 같은 "실패 3건"도 UX가 완전히
달라진다. ② 원자성은 공짜가 아니라는 것 — 묶음이 클수록 트랜잭션이
길어져 락 유지 시간·타임아웃 위험이 커지고, 1건의 반복 실패가 전체
배치를 영구 반려시킨다. 그래서 "원자성이 꼭 필요한 최소 단위로 묶음을
쪼개고, 그 사이는 부분 성공으로"가 현실적 절충이다.

### "벌크 요청의 건수 제한은 왜 필요한가?"

무제한 벌크는 처리 시간과 페이로드 크기를 소비자가 결정하게 만든다.
건수가 커질수록 HTTP 타임아웃 안에 못 끝날 확률, 메모리 사용량,
(원자적 설계라면) 트랜잭션 길이가 함께 자란다. 타임아웃으로 응답을
못 받으면 소비자는 전체 재시도를 하게 되어 부분 실패 문제를 더
키운다. 그래서 요청당 최대 건수를 계약에 명시하고 초과 시 요청
수준 4xx로 거절하며, 그 한도를 넘는 작업은 여러 요청으로 나누거나
비동기 작업(202 + 상태 조회) 모델로 넘기는 것이 맞다.

### "일부는 입력 오류, 일부는 서버 오류로 실패했다면 응답에서 구분해야 하나?"

구분해야 한다 — 소비자의 다음 행동이 다르기 때문이다. 입력 오류
항목은 데이터를 고치기 전엔 재시도가 무의미하고(사용자에게 노출),
서버 오류 항목은 그대로 재시도하면 된다(자동 재시도 대상). 항목별
에러를 표준 에러 code 체계로 담으면 이 구분이 자연히 따라온다.
운영 관점도 있다: 항목 실패 중 서버 오류 비율은 서버 상태의 지표라
집계·알람 대상이지만, 입력 오류는 소비자 데이터 품질 문제라 알람
노이즈다 — 구분이 없으면 이 둘이 한 지표에 섞인다.

## 한 줄 요약

벌크 API의 부분 실패 설계는 "원자적이냐 부분 성공이냐"라는 도메인
결정에서 출발해, 부분 성공이라면 200 + 클라이언트 부여 식별자로
매칭되는 항목별 결과 배열(표준 에러 code 포함)로 응답하고, 실패
항목만 안전하게 재시도할 수 있도록 재시도 가능 여부 구분과 항목별
멱등성까지 갖추는 것 — 성공/실패 이분법이 아니라 소비자의 재시도
설계까지 포함한 계약을 만드는 일이다.
