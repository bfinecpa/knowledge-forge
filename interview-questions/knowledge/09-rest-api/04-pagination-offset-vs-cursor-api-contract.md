# 페이지네이션 API 설계 — offset과 커서는 쿼리 기법이 아니라 클라이언트와 맺는 계약이 다르다

> 핵심 관전 포인트: **offset 기반은 "몇 번째부터 몇 건"(`page`/`size`)을,
> 커서 기반은 "이 항목 다음부터 몇 건"(`cursor`/`size`)을 계약으로 삼는다.
> 차이는 세 축이다 — ① 정확성: 실시간으로 데이터가 추가되는 목록에서
> offset은 창(window)이 밀려 중복·누락을 만들고, 커서는 "마지막으로 본 값
> 다음"이라 안정적이다 ② 성능: offset 비용은 페이지 깊이에 선형으로
> 비례하고 커서는 상수다 ③ 클라이언트 계약: offset은 전체 건수·페이지
> 번호 UI(임의 점프)를 주는 대신 위 두 문제를 안고, 커서는 무한 스크롤에
> 맞지만 total count와 페이지 점프를 포기한다. 커서 토큰은 정렬 키 +
> tie-breaker를 직렬화한 불투명(opaque) 문자열로 설계해 "그대로 돌려
> 주세요"만 계약하고 내부 구조는 서버가 소유한다 — 그래야 나중에 정렬
> 키를 바꿔도 클라이언트가 안 깨진다.**

---

## 0. 질문 + 의도

**질문**: "페이지네이션 API를 설계할 때 offset 기반과 커서 기반의 차이는?"

**출제 의도**: 성능(4장 깊은 페이지네이션)에 더해, 실시간으로 데이터가
추가되는 목록에서 offset이 중복/누락을 만드는 **정확성 문제**까지 아는지
본다 — 피드형 서비스의 필수 지식. 쿼리 최적화가 아니라 "어떤 UI에 어떤
계약을 줄 것인가"라는 API 설계 결정을 할 수 있는지가 관전 포인트다.

(offset이 DB에서 왜 느린지 — read-and-discard, 힙 페치, 실행 계획 증명 —
는 [04-rdb-sql/13-deep-pagination-offset-vs-cursor.md](../04-rdb-sql/13-deep-pagination-offset-vs-cursor.md)가
깊이 다룬다. 이 문서는 **API 계약 관점** — 요청/응답 스키마, 커서 토큰
설계, 클라이언트와의 약속 — 에 집중한다.)

## 1. 두 방식의 계약 — 요청과 응답 스키마부터 다르다

### offset 기반 — "몇 번째부터"

```text
GET /posts?page=3&size=20
```

```json
{
  "content": [ { "...": "20건" } ],
  "page": 3,
  "size": 20,
  "totalElements": 12345,
  "totalPages": 618
}
```

클라이언트에 주는 것: **전체 건수, 전체 페이지 수, 임의 페이지 점프**
(1 → 500페이지로 바로). 페이지 번호가 붙은 게시판·관리자 그리드 UI가
요구하는 것들이다. 대신 서버는 매 요청 `count` 쿼리 비용과 깊은 페이지의
선형 비용을 지불하고, 아래 §3의 정확성 문제를 안는다.

### 커서 기반 — "이 항목 다음부터"

```text
GET /posts?size=20                          ← 첫 페이지: 커서 없음
GET /posts?size=20&cursor=eyJjcmVhdGVkQXQi...   ← 다음 페이지: 받은 토큰 그대로
```

```json
{
  "items": [ { "...": "20건" } ],
  "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2LTA4LTMwVDEyOjM0OjU2WiIsImlkIjoxMDIwMzR9",
  "hasNext": true
}
```

클라이언트에 주는 것: **깊이와 무관한 일정한 응답 속도, 스크롤 중
삽입·삭제에도 흔들리지 않는 목록**. 계약은 단순하다 — "응답의
`nextCursor`를 다음 요청에 그대로 넣어라. `hasNext`가 false면 끝이다."
대신 `totalElements`도, "37페이지로 점프"도 없다.

두 스키마를 나란히 놓으면 이 질문의 본질이 보인다 — **차이는 SQL이
아니라, 클라이언트에게 무엇을 약속하고 무엇을 약속하지 않는가다.**

| 계약 항목 | offset 기반 | 커서 기반 |
|---|---|---|
| 위치 표현 | `page`/`size` (숫자 좌표) | `cursor` (불투명 토큰) |
| 임의 페이지 점프 | 가능 | 불가 — 앞으로만 |
| total count | 제공 (count 쿼리 비용) | 미제공 |
| 목록 변동 시 | 중복/누락 발생 | 안정 |
| 비용 | 페이지 깊이에 선형 | 상수 |
| 어울리는 UI | 페이지 번호 게시판, 관리자 그리드 | 무한 스크롤, 피드, "더 보기" |

## 2. 커서 토큰 설계 — 불투명해야 계약이 오래간다

### 2-1. 무엇을 담나 — 정렬 키 + tie-breaker

커서는 "마지막으로 본 행"을 유일하게 식별해야 한다. `created_at DESC`
정렬이면 같은 시각에 여러 건이 있을 수 있으므로 **정렬 키 + 유일한
tie-breaker(보통 id)** 쌍을 담는다. 이 쌍이 서버에서
`WHERE (created_at, id) < ($1, $2)` 조건이 된다 — 쿼리 측 설계는
[04-rdb-sql 문서](../04-rdb-sql/13-deep-pagination-offset-vs-cursor.md) §2-1 참고.

### 2-2. 왜 불투명(opaque)이어야 하나 — 내부 구조를 계약에서 빼기 위해

```text
❌ before: 커서 구성 값을 그대로 노출하는 설계
GET /posts?lastCreatedAt=2026-08-30T12:34:56Z&lastId=102034

문제:
- 클라이언트가 값을 직접 조립해 호출하기 시작한다 (임의 값, 잘못된 조합)
- "정렬 키를 (score, id)로 바꾸자"는 순간 파라미터 이름부터 깨진다
  → 내부 구현(정렬 컬럼)이 API 계약에 박제된 것
- id 채번 방식, 데이터 규모 같은 내부 정보가 노출된다
```

```text
✅ after: 직렬화 + Base64 인코딩한 불투명 토큰 하나
GET /posts?cursor=eyJjcmVhdGVkQXQiOi4uLiwiaWQiOjEwMjAzNH0

계약: "이 문자열을 해석하지 말고, 다음 요청에 그대로 돌려주세요"
- 토큰 내부 구조는 서버 소유 → 정렬 키 교체, 필드 추가가 클라이언트에 무영향
- 파라미터는 cursor 하나로 고정 → 정렬 축이 늘어도 요청 스키마는 불변
```

핵심 원리는 **"클라이언트가 해석할 수 있는 것은 전부 계약이 된다"**는
것이다. 값이 보이면 누군가는 반드시 파싱해서 쓰고, 그 순간 서버는 토큰
구조를 영원히 못 바꾼다. 불투명 토큰은 이 진화의 자유를 지키는 장치다.

### 2-3. 서버는 토큰을 신뢰하지 않는다 — 검증과 방어

불투명하다고 해서 클라이언트가 위조하지 못하는 것은 아니다(Base64는
암호화가 아니다). 서버 측 방어 세 가지:

- **파싱 실패·형식 위반 → 400**: 커서가 해석 불가능하면 조용히 첫
  페이지를 주지 말고 명시적으로 거절한다. 조용한 폴백은 클라이언트
  버그(토큰 유실)를 숨긴다.
- **정렬 파라미터와의 일관성 검증**: `sort=score`로 만든 커서를
  `sort=createdAt` 요청에 넣으면 조건과 정렬이 어긋나 엉뚱한 결과가
  나온다. 토큰 안에 **정렬 기준(또는 그 해시)을 함께 넣어** 요청의 정렬과
  다르면 400으로 거절한다.
- **(가산점 포인트) 서명 또는 버전 필드**: 토큰에 HMAC 서명을 붙이면
  위조된 값으로 임의 조건을 주입하는 것을 차단할 수 있고, 버전 필드
  (`"v":1`)를 넣어 두면 토큰 구조를 바꿀 때 구버전 토큰을 식별해 우아하게
  만료시킬 수 있다("커서가 만료되었습니다. 목록을 새로고침하세요").

```java
// 커서 토큰의 최소 구현 — 값 객체 + 불투명 직렬화
public record PostCursor(Instant createdAt, Long id) {

    public String encode() {
        String raw = createdAt + "|" + id;
        return Base64.getUrlEncoder().withoutPadding()
                     .encodeToString(raw.getBytes(UTF_8));
    }

    public static PostCursor decode(String token) {
        try {
            String[] parts = new String(Base64.getUrlDecoder().decode(token), UTF_8)
                                 .split("\\|");
            return new PostCursor(Instant.parse(parts[0]), Long.parseLong(parts[1]));
        } catch (Exception e) {
            throw new InvalidCursorException(token);   // → @ControllerAdvice 에서 400
        }
    }
}
```

### 2-4. 응답 스키마의 디테일

- **`nextCursor`는 서버가 만들어 내려준다** — 마지막 항목에서 클라이언트가
  조립하게 하지 않는다(조립 규칙이 계약이 되는 걸 막는다). 다음 페이지가
  없으면 `nextCursor: null` + `hasNext: false`.
- **`hasNext` 판정은 size + 1건 조회**로 한다 — 21건을 읽어 21번째가
  있으면 `hasNext: true`, 20건만 응답에 담는다. count 쿼리가 필요 없다.
- **양방향 스크롤이 필요하면 `prevCursor`도 함께** 내려준다(채팅 위로
  스크롤 등). 서버는 조건·정렬을 뒤집어 조회한 뒤 결과를 다시 뒤집는다.
- 페이지 크기는 **서버가 상한을 강제**한다(`size` 최대 100 등). 클라이언트
  가 보낸 값을 그대로 믿으면 `size=100000`이 들어온다.

## 3. 정확성 — offset은 목록이 움직이면 창이 밀린다

rationale이 "성능에 더해"라고 짚은 지점이다. 피드형 서비스에서는 이게
성능보다 먼저 사용자 눈에 띈다.

```text
사용자가 1페이지(최신 20건)를 보는 동안 새 글 1건이 올라왔다.

offset 방식 — 2페이지 요청 = "21번째부터 20건"
  글이 한 칸씩 밀렸으므로, 1페이지의 마지막 글(원래 20번째)이
  이제 21번째 → 2페이지 첫머리에 다시 나온다 (중복)
  반대로 삭제가 일어나면 한 건이 조용히 건너뛰어진다 (누락)

커서 방식 — 2페이지 요청 = "1페이지 마지막 글 다음부터 20건"
  기준이 순번이 아니라 값이므로, 위에서 무엇이 끼어들든
  "그 글 다음"은 변하지 않는다
```

중복은 사용자가 보고 "같은 글이 두 번 나와요"라고 제보하지만, **누락은
아무도 모른 채 지나간다** — 피드에서 특정 글이 특정 사용자에게만 안 보인
이유를 로그로도 못 찾는다. 쓰기가 잦은 목록(피드, 알림, 댓글)에서 커서가
필수인 이유는 성능 이전에 이 정합성이다.

**선택 기준을 UI로 정리하면**:

- **무한 스크롤·피드·타임라인·"더 보기"** → 커서. 사용자는 페이지 번호를
  볼 일이 없고, 목록은 실시간으로 움직인다.
- **페이지 번호 게시판, 관리자 그리드(임의 점프 + total count 필요)** →
  offset + 깊이 상한. 데이터 변동이 적고 점프가 요구사항이면 offset이
  정당하다 — 대신 [offset 상한](../04-rdb-sql/13-deep-pagination-offset-vs-cursor.md)을
  API 레벨에서 강제한다.
- 하나의 서비스에 둘이 공존하는 게 보통이다. "무조건 커서"가 아니라
  **UI 요구사항 → 계약 선택**의 순서로 말해야 설계 답변이 된다.

## 4. 꼬리질문 대비 포인트

### "커서 토큰에는 무엇을 담고, 왜 불투명해야 하나요?"

정렬 키 + 유일한 tie-breaker(id)를 직렬화해 담는다. 불투명해야 하는
이유는 **클라이언트가 해석 가능한 것은 전부 계약이 되기 때문** — 값이
노출되면 클라이언트가 직접 조립해 호출하기 시작하고, 그 순간 정렬 키
변경·토큰 구조 변경이 파괴적 변경(breaking change)이 된다. 추가로 정렬
기준 식별자와 버전을 함께 넣으면 정렬-커서 불일치 검증과 토큰 구조
마이그레이션이 가능해진다 (가산점 포인트).

### "기획이 '전체 12,345건' 표시와 무한 스크롤을 둘 다 원하면요?"

커서 응답에 total count가 없는 건 기술 한계가 아니라 **비용 판단**이므로,
정말 필요하면 절충한다 — ① 목록과 분리된 별도 count 엔드포인트(캐시
가능, 목록 응답 속도와 독립) ② 근사치 표기("약 12,000건") + 주기적
집계 ③ 첫 페이지에만 count를 실어 주고 이후 페이지는 생략. 핵심은
"정확한 실시간 count는 매 요청 전체 스캔 비용"임을 기획에 설명하고
**요구사항의 진짜 의도(규모감 표시인지, 정확한 수치인지)**를 확인해
계약을 정하는 것이다.

### "운영 중인 offset API를 커서로 바꾸려면 어떻게 마이그레이션하나요?"

파라미터도 응답 구조도 바뀌므로 하위 호환이 불가능한 변경이다. 절차는
① 커서 기반 v2(또는 신규 파라미터 세트)를 병행 추가 ② 구 API에는 깊이
상한을 걸어 피해를 차단 ③ 클라이언트(특히 강제 업데이트가 안 되는 모바일
구버전)의 전환 기간을 두고 사용량 메트릭으로 감시 ④ 사용량이 0에
수렴하면 폐기 공지 후 제거. "처음부터 커서로 설계했으면 안 냈을 비용"
이라는 점이 이 질문(설계 시점의 선택)의 무게다.

### "커서 방식에서 '이전 페이지'는 어떻게 지원하나요?"

조건과 정렬을 반대로 뒤집어 조회한 뒤 결과 리스트를 다시 뒤집어
돌려주고, 응답에 `prevCursor`를 함께 내려준다. 같은 복합 인덱스를 반대
방향으로 읽을 뿐이라 인덱스 추가는 필요 없다. 단, "이전"은 직전
페이지로의 이동이지 임의 점프가 아니라는 한계는 그대로다.

### "정렬 기준을 사용자가 바꿀 수 있는 목록(관리자 그리드)에도 커서를 쓸 수 있나요?" (시니어 변별 포인트)

쓸 수는 있지만 맞지 않는 경우가 많다. 정렬 축마다 ① 커서 구성 값
② tie-breaker 포함 복합 인덱스 ③ 토큰 스키마가 따로 필요하고, 정렬 키는
**불변 컬럼**이어야 한다(`updated_at` 정렬에 커서를 쓰면 스크롤 중 갱신된
행이 위치를 옮겨 중복/누락이 재발한다). 정렬 축이 고정된 피드에는
커서가 정답이지만, 임의 컬럼 정렬 + 다중 필터 + total count까지 요구하는
관리자 그리드는 offset + 깊이 상한이 정직한 선택이고, 그마저 규모가
커지면 검색 엔진(`search_after`) 위임이 다음 단계다. **"커서가 항상
우월하다"가 아니라 요구사항별 비용을 비교해 고르는 것**이 설계 답변이다.

---

## 한 줄 요약

offset은 "몇 번째부터"라는 숫자 좌표 계약이라 total count와 임의 점프를
주는 대신 목록이 움직이면 중복·누락이 생기고 깊이에 비례한 비용을 내며,
커서는 "이 항목 다음부터"라는 값 기반 계약이라 변동에 안정적이고 비용이
상수인 대신 점프와 count를 포기한다 — **커서 토큰은 정렬 키 +
tie-breaker를 담은 불투명 문자열로 설계해 내부 구조를 계약에서 빼고, UI
요구사항(피드냐 페이지 번호 그리드냐)이 두 계약 중 무엇을 고를지
결정한다.**
