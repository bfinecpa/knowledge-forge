# 페이지네이션 API 설계 — offset과 커서는 쿼리 기법이 아니라 클라이언트와 맺는 계약이 다르다

> 핵심 관전 포인트: **offset 기반은 "몇 번째부터 몇 건"(`page`/`size`)을, 커서 기반은 "이 항목 다음부터 몇 건"(`cursor`/`size`)을 계약으로 삼는다. 두 방식의 모든 차이는 하나에서 갈라져 나온다 — **offset은 위치를 순번으로 가리키고 커서는 값으로 가리킨다.** 순번으로 가리키면 순번을 세어 봐야 하고(`OFFSET 100000`을 만난 DB는 앞의 10만 건을 건너뛰는 게 아니라 실제로 읽어 세고 버린 뒤 21번째부터 준다 — 비용이 깊이에 비례하는 이유), 앞쪽이 흔들리면 순번도 같이 흔들린다(글 하나가 추가되면 모든 행이 한 칸씩 밀려 페이지 경계에서 중복이, 삭제되면 누락이 난다). 값으로 가리키면 앞에서 무슨 일이 있든 "그 값보다 뒤"라는 조건이 가리키는 행 집합은 변하지 않고, 시작점을 인덱스 탐색 한 번으로 찾으므로 깊이와 무관하게 상수 비용이다. 대신 값에는 순번이 없으니 임의 페이지 점프와 total count를 포기한다. 커서 SQL의 실제 모양은 `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 21`이고, 여기서 `id`는 **tie-breaker(동점 처리 키)** — 정렬 키 값이 같은 행들 사이의 순서를 확정해 주는 보조 키로, 이게 없으면 데이터가 하나도 안 바뀌어도 페이지 경계에서 중복·누락이 난다 — 이며 `21`은 다음 페이지 존재 여부를 알기 위해 한 건 더 읽는 것이다. 그리고 이 값들을 **불투명(opaque)** 토큰 하나로 감싸는 이유는 "클라이언트가 해석할 수 있는 것은 전부 계약이 되기 때문"이다. Base64는 암호화가 아니라 인코딩이라 누구나 열어볼 수 있으므로 불투명은 기술적 은폐가 아니라 클라이언트에게 하는 **약속**이고, 위조 방지는 별개의 문제라 서명이 필요하다.**

---

## 0. 질문 + 의도

**질문**: "페이지네이션 API를 설계할 때 offset 기반과 커서 기반의 차이는?"

**출제 의도**: 성능(4장 깊은 페이지네이션)에 더해, 실시간으로 데이터가 추가되는 목록에서 offset이 중복/누락을 만드는 **정확성 문제**까지 아는지 본다 — 피드형 서비스의 필수 지식. 쿼리 최적화가 아니라 "어떤 UI에 어떤 계약을 줄 것인가"라는 API 설계 결정을 할 수 있는지가 관전 포인트다.

(offset이 DB에서 왜 느린지 — read-and-discard, 힙 페치, 실행 계획 증명 — 는 [04-rdb-sql/13-deep-pagination-offset-vs-cursor.md](../04-rdb-sql/13-deep-pagination-offset-vs-cursor.md)가 깊이 다룬다. 이 문서는 **API 계약 관점** — 요청/응답 스키마, 커서 토큰 설계, 클라이언트와의 약속 — 에 집중한다.)

## 1. 두 방식의 계약 — 요청과 응답 스키마부터 다르다

### 1-1. 전제 — 목록의 "어디부터"를 가리키는 방법은 둘뿐이다

페이지네이션이 하는 일은 하나다. 12,345건짜리 목록에서 지금 필요한 20건만 잘라 오는 것. 그러려면 **"어디부터"를 표현해야** 하는데, 표현하는 방법이 논리적으로 두 가지뿐이다.

```text
전체 목록 (최신순)
  ①  ②  ③  ④  ⑤  ⑥  ⑦  ⑧ …
  │   │   │   │
  ▼   ▼   ▼   ▼
  G   F   E   D  …

① 순번으로 가리킨다  → "4번째부터 3건"        (offset 기반)
② 값으로 가리킨다     → "E 라는 글 다음부터 3건"  (커서 기반)
```

이 한 줄의 차이에서 나머지 전부가 따라 나온다. 순번으로 가리키면 그 순번까지 **세어 봐야** 하고(성능), 앞쪽 목록이 흔들리면 순번이 가리키는 대상도 같이 **흔들린다**(정확성). 값으로 가리키면 세지 않아도 되고 앞쪽이 흔들려도 그 값은 그 값이다. 대신 값에는 "몇 번째"라는 정보가 없으니 **500페이지로 점프**할 수가 없다.

그러니까 이 질문은 성능 비교 문제가 아니라 **"우리 UI에 순번이 필요한가"**라는 설계 질문이다. 아래 두 절에서 각 방식이 클라이언트와 무엇을 주고받는지부터 본다.

### 1-2. offset 기반 — "몇 번째부터"

```text
GET /posts?page=3&size=20
```

```json
{
  "content": [ { "...": "20건" } ],
  "page": 3,
  "size": 20,
  "totalElements": 12345,
  "totalPages": 618
}
```

클라이언트에 주는 것: **전체 건수, 전체 페이지 수, 임의 페이지 점프**(1 → 500페이지로 바로). 페이지 번호가 붙은 게시판·관리자 그리드 UI가 요구하는 것들이다.

`totalPages`는 `totalElements`를 `size`로 나눠 올림한 값이다 — 12,345 ÷ 20 = 617.25이므로 마지막 5건을 담을 페이지가 하나 더 필요해 **618**이 된다. 이 숫자가 응답에 있으려면 서버가 매 요청 전체 건수를 세야 하고, 그 비용이 뒤에서 문제가 된다(4절 두 번째 질문).

대신 서버는 매 요청 `count` 쿼리 비용과 깊은 페이지의 선형 비용을 지불하고, 아래 3절의 정확성 문제를 안는다. 이 두 비용의 정체를 먼저 확인하고 넘어가자.

### 1-3. offset의 비용은 왜 깊이에 비례하나 — 건너뛰기가 아니라 읽고 버리기다

"offset이 크면 느리다"는 결론만 외우면 커서가 왜 빠른지도 설명할 수 없다. 메커니즘 한 겹만 들어가자.

핵심은 이것이다. **B-tree 인덱스에는 "앞에서 10만 번째"로 바로 가는 길이 없다.** 인덱스는 "값이 X인 곳"으로 가는 데는 트리 높이만큼(로그 시간)이면 되지만, 각 노드가 자기 아래에 행이 몇 건 있는지를 세어 두지 않기 때문에 순번으로는 찾아갈 수 없다. **그러니 10만 번째로 가려면 처음부터 세며 걷는 수밖에 없다.**

세는 주체가 누구인지가 그다음 포인트다. PostgreSQL의 실행계획은 위 노드가 아래 노드에게 "다음 행 하나 줘"라고 당기는 구조이고, `OFFSET`과 `LIMIT`은 맨 위의 **`Limit` 노드**가 처리한다. 아래 스캔 노드는 그 행이 결국 버려질 행인지 알 방법이 없으므로 **행을 온전히 만들어서 위로 올린다.**

```text
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

 ┌ Limit 노드 (offset=100,000, count=20) ────────────────────────┐  ← 세는 곳은 여기다
 │   1번째 행       → 카운터 1        아직 100,000 미만 → 버림     │
 │   2번째 행       → 카운터 2                          → 버림     │
 │   …                                                            │
 │   100,000번째 행 → 카운터 100,000                    → 버림     │
 │   100,001번째 행 → 결과 [1]                                     │
 │   …                                                            │
 │   100,020번째 행 → 결과 [20]  → 응답으로 나가고 스캔 중단        │
 └───────────────────────────▲────────────────────────────────────┘
                             │ "다음 행 하나 줘" × 100,020 회
 ┌ Index Scan Backward using idx_posts_created_at ───────────────┐
 │   인덱스 리프 엔트리 → 힙 페이지 읽기 → 가시성 확인 → 행 조립    │
 └────────────────────────────────────────────────────────────────┘

 읽어 올린 행 100,020건  /  응답에 담긴 행 20건
```

**PostgreSQL에서는 한 겹이 더 붙는다.** 인덱스 엔트리에는 그 행이 살아 있는지에 대한 정보가 없어서, 그 엔트리가 내 트랜잭션의 스냅샷에 보이는 행인지는 **힙(테이블 본체)에 있는 튜플 헤더를 읽어야만** 안다. 즉 "카운터에 넣을지 말지"를 판정하는 것 자체가 힙 접근을 요구한다. **버릴 행조차 공짜로 버릴 수 없는 구조**다.

이것을 실행계획으로 증명할 수 있다는 점도 알아두면 좋다. `EXPLAIN ANALYZE`를 찍으면 `Limit` 노드의 `actual rows`는 20인데 그 아래 스캔 노드의 `actual rows`는 100,020으로 나온다 — 두 숫자의 차이가 곧 "읽고 버린 양"이다.

비용을 계산해 보면 감이 잡힌다. 페이지 크기 20에서 1페이지는 20건을 읽고, 5,001페이지(`OFFSET 100000`)는 100,020건을 읽는다. **같은 20건을 돌려주는데 일의 양은 5,001배**다(100,020 ÷ 20 = 5,001). 응답 크기는 그대로인데 비용만 페이지 번호에 비례해 커지는 것 — 이것이 "깊은 페이지네이션"이라는 이름의 실체다.

이제 커서가 왜 빠른지 말할 준비가 됐다. **커서는 이 세기를 아예 없앤다.**

### 1-4. 커서 기반 — "이 항목 다음부터"

```text
GET /posts?size=20                          ← 첫 페이지: 커서 없음
GET /posts?size=20&cursor=eyJjcmVhdGVkQXQi...   ← 다음 페이지: 받은 토큰 그대로
```

```json
{
  "items": [ { "...": "20건" } ],
  "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2LTA4LTMwVDEyOjM0OjU2WiIsImlkIjoxMDIwMzR9",
  "hasNext": true
}
```

클라이언트에 주는 것: **깊이와 무관한 일정한 응답 속도, 스크롤 중 삽입·삭제에도 흔들리지 않는 목록**. 계약은 단순하다 — "응답의 `nextCursor`를 다음 요청에 그대로 넣어라. `hasNext`가 false면 끝이다." 대신 `totalElements`도, "37페이지로 점프"도 없다.

#### 서버 쪽 SQL — 키셋 페이지네이션

이 계약을 받은 서버가 실제로 실행하는 쿼리가 아래다. 이 방식을 **키셋 페이지네이션(keyset pagination)**이라 부르는데, 위치를 순번이 아니라 **정렬 키의 값(key set)으로 지정한다**는 뜻이다.

```sql
-- 커서가 담고 있던 값을 그대로 조건에 꽂는다
SELECT id, title, created_at
  FROM posts
 WHERE (created_at, id) < ($1, $2)        -- $1,$2 = 직전 페이지 마지막 행의 값
 ORDER BY created_at DESC, id DESC
 LIMIT 21;                                -- 요청받은 20건 + 1건
```

세 줄이 각각 왜 그렇게 생겼는지 하나씩 보자.

**`(created_at, id) < ($1, $2)` — 행 비교(row comparison)다.** 두 컬럼을 각각 비교하는 것이 아니라 **사전순으로 한 덩어리를 비교**한다. 풀어 쓰면 `created_at < $1 OR (created_at = $1 AND id < $2)`이다. 사전에서 "apple"과 "apply"를 비교할 때 앞 글자부터 보다가 같으면 다음 글자로 넘어가는 것과 같은 규칙이다.

여기서 흔한 실수를 짚어야 한다. 이걸 `WHERE created_at < $1 AND id < $2`로 쓰면 **틀린다.** `created_at`은 더 과거인데 `id`는 커서보다 큰 행들이 통째로 사라지기 때문이다. 정렬 축이 두 개일 때 `AND`는 사전순 비교가 아니라 두 조건의 교집합이 된다.

**PostgreSQL이 이 형태를 어떻게 실행하는가**가 성능의 핵심이다. 행 비교는 `(created_at, id)` 복합 인덱스의 **B-tree 범위 탐색**으로 바로 변환된다. 즉 인덱스 트리를 뿌리에서 리프까지 한 번 내려가 시작 지점을 찍고, 거기서부터 리프를 21개만 순서대로 읽고 멈춘다. **1페이지든 5,001페이지든 하는 일이 똑같다** — 이것이 "비용이 상수"의 정체다.

```text
[offset]  ①②③…………………………………………⑩⑩⑩⑩⑩⑩⑩⑩⑩⑩⑩ 100,020건을 읽고 20건만 남긴다
                                                    ↑ 깊어질수록 왼쪽 꼬리가 길어진다

[커서]    ─(인덱스 트리 하강 한 번)→ ▉▉▉…▉ 21건만 읽는다
                                       ↑ 깊이와 무관하게 이 그림이 그대로다
```

**필요한 인덱스**는 정렬 키와 tie-breaker를 순서대로 묶은 복합 인덱스 하나다.

```sql
CREATE INDEX idx_posts_created_id ON posts (created_at DESC, id DESC);
-- (created_at, id) 로 만들어도 된다. B-tree 는 양방향으로 읽을 수 있어서,
-- 두 컬럼의 방향이 함께 뒤집히는 ORDER BY created_at DESC, id DESC 는
-- 같은 인덱스를 역방향으로 훑어 처리할 수 있다.
-- 단 방향이 엇갈리면(created_at DESC, id ASC) 그 조합에 맞는 인덱스가 따로 필요하다.
```

**`LIMIT 21` — 왜 20이 아니라 21인가.** 응답에 `hasNext`를 담으려면 "뒤에 더 있는가"를 알아야 하는데, 이걸 `COUNT(*)`로 알아내면 커서 방식의 이점이 통째로 날아간다. 그래서 **요청받은 것보다 한 건 더 읽는다.** 21건이 나오면 뒤에 더 있다는 뜻이므로 `hasNext: true`로 표시하고 **응답에는 앞의 20건만 담는다.** 20건 이하가 나오면 거기가 끝이다. 추가 비용은 인덱스 엔트리 하나를 더 읽는 것뿐이다.

```text
읽어온 행 수  판정
──────────────────────────────────────────────
   21건      → hasNext = true,  응답에는 앞 20건만 (21번째는 버린다)
   20건      → hasNext = false, 마지막 페이지 (딱 떨어진 경우)
   7건       → hasNext = false, 마지막 페이지
```

### 1-5. tie-breaker — 정렬 키가 같은 행들의 순서를 확정하는 키

위 SQL에서 `id`가 왜 붙어 있는지가 이 설계에서 가장 자주 빠뜨리는 부분이다.

**tie-breaker는 정렬 키 값이 같은 행들 사이의 순서를 확정해 주는 보조 정렬 키다.** 이름은 스포츠에서 왔다 — 동점(tie)인 두 팀의 순위를 가르는(break) 규칙이 tie-breaker다. 우리말로 옮기면 **동점 처리 키**쯤 된다. `created_at`이 같은 두 주문 사이의 순서를 `id`로 가른다는 뜻이다.

없으면 무슨 일이 생기는지가 중요하다. **데이터가 하나도 안 바뀌어도 페이지 경계에서 중복과 누락이 난다.**

```text
같은 시각에 만들어진 행이 페이지 경계에 걸린 상황 (페이지 크기 3)

  글    created_at             id
  ────────────────────────────────
  P     2026-09-01 10:00:03    501
  Q     2026-09-01 10:00:01    502   ┐ 세 건의 created_at 이 완전히 같다.
  R     2026-09-01 10:00:01    503   ├ ORDER BY created_at DESC 만으로는
  S     2026-09-01 10:00:01    504   ┘ 이 셋의 순서가 정의되지 않는다.
  T     2026-09-01 10:00:00    505

[tie-breaker 없음]  ORDER BY created_at DESC
  1페이지 실행 → P, Q, R  (DB가 이번엔 이 순서로 올려줬다)
  2페이지 실행 → 같은 정렬을 다시 걸었을 뿐인데 이번엔 S, Q 순으로 올라온다
               → 사용자가 본 것: P Q R | S Q
                                        ↑ Q 가 두 번, R 은 다시 안 보임
  ※ 그 사이 데이터는 한 건도 안 바뀌었다. 순서가 애초에 정해져 있지 않았을 뿐이다.

[tie-breaker 있음]  ORDER BY created_at DESC, id DESC
  전체 순서가 언제 실행해도 P(501) → S(504) → R(503) → Q(502) → T(505) 로 고정
  1페이지 → P S R      2페이지 → Q T        중복도 누락도 없다
```

정렬이 실행할 때마다 달라질 수 있다는 게 이상하게 들릴 수 있는데, 정렬 조건이 순서를 다 정해 주지 않으면 **나머지는 DB가 편한 대로 정한다.** 어떤 실행계획을 골랐는지, 인덱스를 탔는지 정렬 노드를 거쳤는지, 병렬 워커가 몇 개였는지에 따라 결과 순서가 바뀔 수 있다. 명세되지 않은 것은 보장되지 않는다.

커서 방식에서는 tie-breaker가 한 가지 이유로 더 필요하다. **커서 값이 마지막으로 본 행을 유일하게 지목할 수 있어야** 하기 때문이다. 위 예에서 1페이지 마지막이 R인데 커서에 `created_at`만 담아 `WHERE created_at < '10:00:01'`로 조회하면, 같은 시각의 Q가 통째로 건너뛰어진다. `(created_at, id) < ('10:00:01', 503)`이어야 Q가 정확히 포함된다.

정리하면 **tie-breaker의 조건은 "유일하고 불변인 값"**이고, 그래서 보통 PK를 쓴다. 값이 유일해야 순서가 완전히 결정되고, 나중에 바뀌지 않아야 그 값을 담아 둔 커서가 계속 유효하다.

### 1-6. 두 계약을 나란히 놓으면

두 스키마를 나란히 놓으면 이 질문의 본질이 보인다 — **차이는 SQL이 아니라, 클라이언트에게 무엇을 약속하고 무엇을 약속하지 않는가다.**

| 계약 항목 | offset 기반 | 커서 기반 |
|---|---|---|
| 위치 표현 | `page`/`size` (숫자 좌표) | `cursor` (불투명 토큰) |
| 임의 페이지 점프 | 가능 | 불가 — 앞으로만 |
| total count | 제공 (count 쿼리 비용) | 미제공 |
| 목록 변동 시 | 중복/누락 발생 | 안정 |
| 비용 | 페이지 깊이에 선형 | 상수 |
| 어울리는 UI | 페이지 번호 게시판, 관리자 그리드 | 무한 스크롤, 피드, "더 보기" |

## 2. 커서 토큰 설계 — 불투명해야 계약이 오래간다

### 2-1. 무엇을 담나 — 정렬 키 + tie-breaker

커서는 "마지막으로 본 행"을 유일하게 식별해야 한다. `created_at DESC` 정렬이면 같은 시각에 여러 건이 있을 수 있으므로 **정렬 키 + 유일한 tie-breaker(보통 id)** 쌍을 담는다(1-5에서 본 그대로다). 이 쌍이 서버에서 `WHERE (created_at, id) < ($1, $2)` 조건이 된다.

여기에 선택적으로 두 가지를 더 넣는다. **정렬 기준 식별자**(2-3의 일관성 검증용)와 **토큰 버전**(구조를 바꿀 때 구버전 토큰을 식별하기 위한 것)이다. 쿼리 측 설계는 [04-rdb-sql 문서](../04-rdb-sql/13-deep-pagination-offset-vs-cursor.md) §2-1을 참고한다.

### 2-2. 왜 불투명(opaque)이어야 하나 — 이름의 뜻부터

**"불투명(opaque)"은 빛이 통과하지 않아 안이 안 보이는 물체를 가리키는 말이다.** API에서는 **"클라이언트가 안을 들여다볼 수 없는 값"**이라는 뜻으로 쓴다. 반대는 투명한 값 — 클라이언트가 읽고 뜻을 이해할 수 있는 값이다.

왜 안이 안 보여야 하는지는 반례를 보면 즉시 이해된다.

```text
Before — 커서 구성 값을 그대로 노출하는 설계
GET /posts?lastCreatedAt=2026-08-30T12:34:56Z&lastId=102034

문제:
- 클라이언트가 값을 직접 조립해 호출하기 시작한다 (임의 값, 잘못된 조합)
- "정렬 키를 (score, id) 로 바꾸자"는 순간 파라미터 이름부터 깨진다
  → 내부 구현(정렬 컬럼)이 API 계약에 박제된 것
- id 채번 방식, 데이터 규모 같은 내부 정보가 노출된다
```

```text
After — 직렬화 + Base64 인코딩한 불투명 토큰 하나
GET /posts?cursor=eyJjcmVhdGVkQXQiOi4uLiwiaWQiOjEwMjAzNH0

계약: "이 문자열을 해석하지 말고, 다음 요청에 그대로 돌려주세요"
- 토큰 내부 구조는 서버 소유 → 정렬 키 교체, 필드 추가가 클라이언트에 무영향
- 파라미터는 cursor 하나로 고정 → 정렬 축이 늘어도 요청 스키마는 불변
```

핵심 원리는 **"클라이언트가 해석할 수 있는 것은 전부 계약이 된다"**는 것이다. 값이 보이면 누군가는 반드시 파싱해서 쓰고, 그 순간 서버는 토큰 구조를 영원히 못 바꾼다. 불투명 토큰은 이 진화의 자유를 지키는 장치다.

#### 그런데 Base64는 아무것도 감추지 못한다

여기서 반드시 짚어야 할 오해가 있다. **Base64는 암호화가 아니라 인코딩이다.** 암호화는 열쇠를 모르면 못 푸는 것이고, 인코딩은 **바이트를 다른 문자 집합으로 옮겨 적는 것**일 뿐이다. Base64를 쓰는 이유는 비밀 유지가 아니라, 임의의 바이트열을 URL에 안전하게 실을 수 있는 글자들로만 바꾸기 위해서다.

그래서 커서 토큰은 누구나 1초 만에 열어볼 수 있다.

```text
받은 커서:
  eyJjcmVhdGVkQXQiOiIyMDI2LTA4LTMwVDEyOjM0OjU2WiIsImlkIjoxMDIwMzR9

브라우저 콘솔에서 atob() 한 줄:
  {"createdAt":"2026-08-30T12:34:56Z","id":102034}

열쇠도, 도구 설치도 필요 없다.
```

**그러므로 "불투명하다"는 것은 기술적 은폐가 아니라 클라이언트에게 하는 약속이다.** 정확히는 이런 약속이다 — "이 문자열의 내부 구조는 계약에 포함되지 않습니다. 열어 보고 그 결과에 의존하면 예고 없이 깨집니다."

약속만으로 충분한 것과 아닌 것을 구분해야 한다.

| 지키려는 것 | 약속만으로 되나 | 필요한 장치 |
|---|---|---|
| 토큰 구조를 나중에 바꿀 자유 | 된다 — 계약에 없는 것에 의존한 쪽 책임이다 | 문서에 "해석 금지"를 명시 |
| 내부 정보를 감추기 | 안 된다 — 디코드하면 다 보인다 | 애초에 민감한 값을 안 담는다 |
| 위조된 커서로 임의 조건 주입 막기 | 안 된다 — 값을 고쳐 다시 인코딩하면 그만이다 | HMAC 서명 (2-3) |

즉 **진화의 자유는 약속으로 지켜지지만, 위조 방지는 실제 장치가 있어야 한다.** 이 둘을 한 단어("불투명")로 뭉뚱그리면 안 된다.

### 2-3. 서버는 토큰을 신뢰하지 않는다 — 검증과 방어

불투명하다고 해서 클라이언트가 위조하지 못하는 것은 아니다(바로 위에서 본 대로 Base64는 암호화가 아니다). 서버 측 방어 세 가지를 둔다.

- **파싱 실패·형식 위반 → 400**: 커서가 해석 불가능하면 조용히 첫 페이지를 주지 말고 명시적으로 거절한다. 조용한 폴백은 클라이언트 버그(토큰 유실)를 숨긴다 — 첫 페이지가 계속 돌아오면 클라이언트는 "목록이 짧구나"로 오해하고, 아무도 문제를 발견하지 못한다.
- **정렬 파라미터와의 일관성 검증**: `sort=score`로 만든 커서를 `sort=createdAt` 요청에 넣으면 조건과 정렬이 어긋나 엉뚱한 결과가 나온다. `WHERE (score, id) < (...)` 조건을 걸어 놓고 `ORDER BY created_at`으로 정렬하는 꼴이 되기 때문이다. 토큰 안에 **정렬 기준(또는 그 해시)을 함께 넣어** 요청의 정렬과 다르면 400으로 거절한다.
- **(가산점 포인트) 서명 또는 버전 필드**: 토큰에 HMAC 서명을 붙이면 위조된 값으로 임의 조건을 주입하는 것을 차단할 수 있고, 버전 필드(`"v":1`)를 넣어 두면 토큰 구조를 바꿀 때 구버전 토큰을 식별해 우아하게 만료시킬 수 있다("커서가 만료되었습니다. 목록을 새로고침하세요").

HMAC 서명이 왜 위조를 막는지 한 줄만 보태자. **HMAC은 서버만 아는 비밀 키로 내용에 대해 계산한 짧은 검증값**이라, 클라이언트가 내용을 고치면 서명과 안 맞고 비밀 키가 없으니 맞는 서명을 새로 만들 수도 없다. 서명은 내용을 감추지 않는다 — **내용이 바뀌지 않았음을 증명할 뿐**이고, 커서에 필요한 것도 딱 그것이다.

```java
// 커서 토큰의 최소 구현 — 값 객체 + 불투명 직렬화
public record PostCursor(Instant createdAt, Long id) {

    public String encode() {
        String raw = createdAt + "|" + id;
        // URL 인코더를 쓰는 이유: 기본 Base64 의 '+' 와 '/' 는 쿼리 문자열에서
        // 다른 뜻으로 해석될 수 있어 '-' 와 '_' 로 바꿔 주는 변형이 필요하다.
        // 패딩('=') 도 URL 에서 지저분해지므로 뺀다.
        return Base64.getUrlEncoder().withoutPadding()
                     .encodeToString(raw.getBytes(UTF_8));
    }

    public static PostCursor decode(String token) {
        try {
            String[] parts = new String(Base64.getUrlDecoder().decode(token), UTF_8)
                                 .split("\\|");
            return new PostCursor(Instant.parse(parts[0]), Long.parseLong(parts[1]));
        } catch (Exception e) {
            // 첫 페이지로 조용히 폴백하지 않는다. 잘못된 커서는 클라이언트 버그이고,
            // 400 으로 돌려줘야 그쪽이 알아챌 수 있다.
            throw new InvalidCursorException(token);   // → @ControllerAdvice 에서 400
        }
    }
}
```

### 2-4. 응답 스키마의 디테일

- **`nextCursor`는 서버가 만들어 내려준다** — 마지막 항목에서 클라이언트가 조립하게 하지 않는다(조립 규칙이 계약이 되는 걸 막는다). 다음 페이지가 없으면 `nextCursor: null` + `hasNext: false`.
- **`hasNext` 판정은 size + 1건 조회**로 한다 — 21건을 읽어 21번째가 있으면 `hasNext: true`, 20건만 응답에 담는다(1-4의 `LIMIT 21`이 이것이다). count 쿼리가 필요 없다.
- **양방향 스크롤이 필요하면 `prevCursor`도 함께** 내려준다(채팅 위로 스크롤 등). 서버는 조건·정렬을 뒤집어 조회한 뒤 결과를 다시 뒤집는다.
- 페이지 크기는 **서버가 상한을 강제**한다(`size` 최대 100 등). 클라이언트가 보낸 값을 그대로 믿으면 `size=100000`이 들어온다.

## 3. 정확성 — offset은 목록이 움직이면 창이 밀린다

rationale이 "성능에 더해"라고 짚은 지점이다. 피드형 서비스에서는 이게 성능보다 먼저 사용자 눈에 띈다.

원리는 1-1에서 이미 나왔다. **offset은 위치를 순번으로 가리키는데, 앞쪽에서 행이 추가되거나 삭제되면 뒤쪽 행들의 순번이 전부 이동한다.** 1페이지를 요청한 시점과 2페이지를 요청한 시점 사이에 그 이동이 일어나면, "4번째부터"가 가리키는 대상이 내가 예상한 그 행이 아니게 된다.

### 3-1. 삽입 — 앞에 글이 하나 끼면 경계에서 중복된다

```text
목록: 최신순(created_at DESC), 페이지 크기 3

t0  1페이지 요청 = OFFSET 0 LIMIT 3
      순번 ①  [G]  ┐
      순번 ②  [F]  ├─ 화면에 보여준 3건
      순번 ③  [E]  ┘
      순번 ④  [D]
      순번 ⑤  [C]
      순번 ⑥  [B]

t1  사용자가 1페이지를 읽는 동안 새 글 [H] 가 맨 앞에 올라온다.
    → 뒤의 모든 행이 한 칸씩 밀린다.
      순번 ①  [H]   ← 끼어든 새 글
      순번 ②  [G]
      순번 ③  [F]
      순번 ④  [E]   ← t0 에서 ③ 이던 E 가 ④ 로 밀렸다  ★
      순번 ⑤  [D]
      순번 ⑥  [C]

t2  2페이지 요청 = OFFSET 3 LIMIT 3  ("4번째부터 3건")
      순번 ④  [E]   ← 1페이지에서 이미 본 글이 또 나온다   ★중복
      순번 ⑤  [D]
      순번 ⑥  [C]

    사용자가 본 순서:  G  F  E  │  E  D  C
                                  ↑ 무한 스크롤에서 같은 글이 두 번 보이는 그 현상
```

### 3-2. 삭제 — 앞의 글이 지워지면 한 건이 조용히 사라진다

```text
t0  는 위와 같다.  1페이지 = G F E

t1' 이번에는 1페이지에 있던 [G] 가 삭제된다.
    → 뒤의 모든 행이 한 칸씩 당겨진다.
      순번 ①  [F]
      순번 ②  [E]
      순번 ③  [D]   ← t0 에서 ④ 였던 D 가 ③ 으로 당겨졌다  ★
      순번 ④  [C]
      순번 ⑤  [B]
      순번 ⑥  [A]

t2' 2페이지 요청 = OFFSET 3 LIMIT 3
      순번 ④  [C]
      순번 ⑤  [B]
      순번 ⑥  [A]

    사용자가 본 순서:  G  F  E  │  C  B  A
                                  ↑ D 가 어디에도 안 나온다   ★누락
```

### 3-3. 커서는 왜 안 밀리나

```text
커서 방식 — 2페이지 요청 = "E 다음부터 3건"
  WHERE (created_at, id) < (E의 created_at, E의 id)
  ORDER BY created_at DESC, id DESC
  LIMIT 4

  t1 에서 H 가 앞에 끼어들었든, t1' 에서 G 가 지워졌든
  "E 보다 뒤" 라는 조건이 뽑아내는 행 집합은 D C B … 로 똑같다.
  → 2페이지 = D C B   중복도 누락도 없다.
```

기준이 **순번이 아니라 값**이기 때문이다. 앞쪽에서 무슨 일이 일어나도 E의 `created_at`과 `id`는 변하지 않으므로 "그 값보다 뒤"라는 조건이 가리키는 범위도 변하지 않는다. 심지어 **커서가 가리키던 E 자신이 삭제돼도 동작한다** — 조건은 E라는 행의 존재가 아니라 E가 가지고 있던 값과 비교하는 것이기 때문이다.

여기서 두 문제의 무게가 다르다는 점을 짚어야 한다. 중복은 사용자가 보고 "같은 글이 두 번 나와요"라고 제보하지만, **누락은 아무도 모른 채 지나간다** — 피드에서 특정 글이 특정 사용자에게만 안 보인 이유를 로그로도 못 찾는다. 쓰기가 잦은 목록(피드, 알림, 댓글)에서 커서가 필수인 이유는 성능 이전에 이 정합성이다.

### 3-4. 선택 기준은 성능이 아니라 UI다

- **무한 스크롤·피드·타임라인·"더 보기"** → 커서. 사용자는 페이지 번호를 볼 일이 없고, 목록은 실시간으로 움직인다.
- **페이지 번호 게시판, 관리자 그리드(임의 점프 + total count 필요)** → offset + 깊이 상한. 데이터 변동이 적고 점프가 요구사항이면 offset이 정당하다 — 대신 [offset 상한](../04-rdb-sql/13-deep-pagination-offset-vs-cursor.md)을 API 레벨에서 강제한다.
- 하나의 서비스에 둘이 공존하는 게 보통이다. "무조건 커서"가 아니라 **UI 요구사항 → 계약 선택**의 순서로 말해야 설계 답변이 된다.

깊이 상한을 강제하라는 말의 의미를 오해하지 않도록 덧붙이면, 이것은 성능 튜닝이 아니라 **안전망**이다. 사람이 손으로 500페이지를 넘길 일은 거의 없고, 깊은 페이지 요청은 대부분 크롤러이거나 스크립트다. `page`가 상한을 넘으면 400으로 거절하는 인터셉터 한 장이면 사람이 기억하지 않아도 작동한다.

## 4. 꼬리질문 대비 포인트

### "커서 토큰에는 무엇을 담고, 왜 불투명해야 하나요?"

정렬 키 + 유일한 tie-breaker(id)를 직렬화해 담는다. tie-breaker를 빠뜨리면 안 되는 이유부터 말하면 좋다 — **정렬 키 값이 같은 행들의 순서가 정의되지 않아, 데이터가 하나도 안 바뀌어도 페이지 경계에서 중복·누락이 난다.**

불투명해야 하는 이유는 **클라이언트가 해석 가능한 것은 전부 계약이 되기 때문** — 값이 노출되면 클라이언트가 직접 조립해 호출하기 시작하고, 그 순간 정렬 키 변경·토큰 구조 변경이 파괴적 변경(breaking change)이 된다.

단, "불투명"의 성격을 정확히 말해야 한다. **Base64는 암호화가 아니라 인코딩이라 누구나 열어볼 수 있으므로, 불투명은 기술적 은폐가 아니라 "이 안을 해석하지 마세요"라는 약속이다.** 진화의 자유는 그 약속만으로 지켜지지만(계약에 없는 것에 의존한 쪽 책임), 위조 방지는 약속으로 안 되므로 HMAC 서명이 따로 필요하다. 추가로 정렬 기준 식별자와 버전 필드를 함께 넣으면 정렬-커서 불일치 검증과 토큰 구조 마이그레이션이 가능해진다 (가산점 포인트).

### "기획이 '전체 12,345건' 표시와 무한 스크롤을 둘 다 원하면요?"

커서 응답에 total count가 없는 건 기술 한계가 아니라 **비용 판단**이므로, 먼저 그 비용이 무엇인지 설명할 수 있어야 한다.

**PostgreSQL은 "이 테이블에 몇 행"이라는 숫자를 어디에도 확정해 두지 않는다.** MVCC 때문에 같은 순간에도 트랜잭션마다 보이는 행 집합이 다르기 때문에 단 하나의 정답이 존재하지 않는다. 그래서 `COUNT(*)`는 조건에 맞는 행을 **매번 전부 훑어** 세는 수밖에 없다.

인덱스를 태워도 완전히 해결되지 않는다. 인덱스 엔트리에는 그 행이 내 스냅샷에 보이는지에 대한 정보가 없어서, 원칙적으로는 힙까지 확인해야 한다. PostgreSQL은 이걸 완화하려고 **가시성 맵(visibility map)** — 페이지 단위로 "이 페이지의 모든 행이 모두에게 보인다"를 표시해 둔 것 — 을 두고, 그 표시가 신선한 페이지에 한해 `Index Only Scan`이 힙을 건너뛴다(실행계획의 `Heap Fetches: 0`). 반대로 쓰기가 잦아 VACUUM이 따라가지 못하면 가시성 맵이 낡아 힙 페치가 붙는다. 어느 쪽이든 **비용이 행 수 N에 비례한다는 성질은 그대로다.**

이걸 설명한 뒤 절충안을 낸다 — ① 목록과 분리된 별도 count 엔드포인트(캐시 가능, 목록 응답 속도와 독립) ② 근사치 표기("약 12,000건"). 조건 없는 전체 건수라면 `pg_class.reltuples`(VACUUM/ANALYZE가 갱신하는 추정치)를 읽으면 상수 시간이고, 조건이 붙는 건수라면 별도 카운터 테이블이나 주기적 집계를 둔다 ③ 첫 페이지에만 count를 실어 주고 이후 페이지는 생략.

핵심은 "정확한 실시간 count는 매 요청 전체 스캔 비용"임을 기획에 설명하고 **요구사항의 진짜 의도(규모감 표시인지, 정확한 수치인지)**를 확인해 계약을 정하는 것이다. "약 12,000개의 검색 결과"라고 쓰는 서비스가 많은 것은 게을러서가 아니라 이 계산을 이미 한 결과다.

### "운영 중인 offset API를 커서로 바꾸려면 어떻게 마이그레이션하나요?"

파라미터도 응답 구조도 바뀌므로 하위 호환이 불가능한 변경이다. 절차는 ① 커서 기반 v2(또는 신규 파라미터 세트)를 병행 추가 ② 구 API에는 깊이 상한을 걸어 피해를 차단 ③ 클라이언트(특히 강제 업데이트가 안 되는 모바일 구버전)의 전환 기간을 두고 사용량 메트릭으로 감시 ④ 사용량이 0에 수렴하면 폐기 공지 후 제거.

이 절차 전체가 [03-api-versioning-strategies.md](03-api-versioning-strategies.md)의 폐기 타임라인과 같은 모양이라는 점을 짚으면 답이 커진다 — 계측 없이는 ④로 갈 수 없다는 것도 같다. "처음부터 커서로 설계했으면 안 냈을 비용"이라는 점이 이 질문(설계 시점의 선택)의 무게다.

### "커서 방식에서 '이전 페이지'는 어떻게 지원하나요?"

조건과 정렬을 반대로 뒤집어 조회한 뒤 결과 리스트를 다시 뒤집어 돌려주고, 응답에 `prevCursor`를 함께 내려준다.

구체적으로는 `WHERE (created_at, id) > ($1, $2) ORDER BY created_at ASC, id ASC LIMIT 21`로 읽은 뒤 리스트를 역순으로 뒤집어 응답한다. 부등호와 정렬 방향을 함께 뒤집는 것이 요점이다. 같은 복합 인덱스를 반대 방향으로 읽을 뿐이라 인덱스 추가는 필요 없다 — B-tree는 양방향으로 훑을 수 있기 때문이다. 단, "이전"은 직전 페이지로의 이동이지 임의 점프가 아니라는 한계는 그대로다.

### "정렬 기준을 사용자가 바꿀 수 있는 목록(관리자 그리드)에도 커서를 쓸 수 있나요?" (시니어 변별 포인트)

쓸 수는 있지만 맞지 않는 경우가 많다. 정렬 축마다 ① 커서 구성 값 ② tie-breaker 포함 복합 인덱스 ③ 토큰 스키마가 따로 필요하다. 정렬 축이 다섯 개면 복합 인덱스도 다섯 벌이고, 인덱스는 조회를 빠르게 하는 만큼 쓰기를 느리게 하며 저장 공간도 먹는다.

그리고 정렬 키는 **불변 컬럼**이어야 한다. `updated_at` 정렬에 커서를 쓰면 스크롤 중 갱신된 행이 위치를 옮겨 중복/누락이 재발한다 — 커서가 "그 값보다 뒤"를 가리키는데 그 값 자체가 움직여 버리면, 3절에서 offset이 겪던 문제가 커서에서 그대로 되살아난다. **커서의 안정성은 "정렬 키가 안 변한다"는 전제 위에 있다**는 것을 아는지가 이 질문의 변별 지점이다.

정렬 축이 고정된 피드에는 커서가 정답이지만, 임의 컬럼 정렬 + 다중 필터 + total count까지 요구하는 관리자 그리드는 offset + 깊이 상한이 정직한 선택이고, 그마저 규모가 커지면 검색 엔진(`search_after`) 위임이 다음 단계다. **"커서가 항상 우월하다"가 아니라 요구사항별 비용을 비교해 고르는 것**이 설계 답변이다.

## 한 줄 요약

offset은 "몇 번째부터"라는 순번 좌표 계약이라 total count와 임의 점프를 주는 대신, DB가 앞의 행들을 실제로 읽고 버려야 해서 비용이 깊이에 비례하고(5,001페이지는 20건을 주려고 100,020건을 읽는다) 목록이 움직이면 순번이 밀려 중복·누락이 생긴다. 커서는 "이 항목 다음부터"라는 값 기반 계약이라 인덱스 탐색 한 번으로 시작점을 찾아 비용이 상수이고 앞쪽 변동에 흔들리지 않는 대신 점프와 count를 포기한다 — **커서 토큰은 정렬 키 + tie-breaker(동점 처리 키, 없으면 데이터가 안 바뀌어도 경계에서 중복·누락이 난다)를 담은 불투명 문자열로 설계해 내부 구조를 계약에서 빼고(불투명은 은폐가 아니라 약속이므로 위조 방지는 서명이 따로 필요하다), UI 요구사항(피드냐 페이지 번호 그리드냐)이 두 계약 중 무엇을 고를지 결정한다.**
