# RESTful API 설계 원칙 — 리소스 중심 설계와 네이밍, 일관성이 곧 협업 속도

> 핵심 관전 포인트: **REST는 "리소스(자원)를 URI로 식별하고, 행위는 HTTP
> 메서드로, 결과는 상태 코드로 표현한다"는 리소스 중심 설계 스타일이다.
> URI에는 동사가 아닌 명사(복수형)를 쓰고, 계층 관계는 경로로 표현한다.
> 그런데 원칙 암기보다 중요한 건 **일관성**이다 — API는 한번 공개되면
> 바꾸기 어려운 장기 계약이고, 일관된 규칙은 클라이언트 개발자가
> "다음 엔드포인트가 어떻게 생겼을지" 예측할 수 있게 해 협업 속도를
> 만든다. 원칙은 그 일관성을 지키기 위한 공용 언어다.**

---

## 0. 질문 + 의도

**질문**: "RESTful API의 설계 원칙을 설명해주세요. 리소스 네이밍 규칙은?"

**출제 의도**: API는 한번 공개되면 바꾸기 어려운 장기 계약이다. 원칙의
준수 여부 자체보다, **일관성이 클라이언트 개발자의 예측 가능성(= 협업
속도)을 만든다**는 이유를 아는지 본다. "왜 이렇게 짓는가"를 소비자
관점에서 설명하는 사람과 규칙만 외운 사람이 갈린다.

## 1. REST의 핵심 원칙 — "리소스"가 중심이다

REST(Representational State Transfer)는 웹의 기존 인프라(HTTP)를
최대한 활용하는 아키텍처 스타일이다. 면접에서는 제약 조건 나열보다
**핵심 3가지 + 무상태**를 정확히 짚는 것이 좋다.

### ① 리소스는 URI로 식별한다

"무엇(what)"은 URI가 담당한다. 주문, 회원, 상품 같은 **자원(명사)**이
URI의 주인공이다.

```
/orders          → 주문 컬렉션이라는 자원
/orders/42       → 42번 주문이라는 자원
```

### ② 행위는 HTTP 메서드로 표현한다

"어떻게(how)"는 메서드가 담당한다. URI에 동사를 넣지 않는 이유가
바로 이것 — **행위를 표현하는 자리가 이미 있기 때문**이다.

```http
# Before: URI에 동사 — 행위 표현 자리가 중복되고 규칙이 무너진다
POST /createOrder
POST /orders/42/delete
GET  /getOrderList

# After: 메서드가 행위, URI는 자원만
POST   /orders        # 생성
DELETE /orders/42     # 삭제
GET    /orders        # 목록 조회
```

- 비유: URI는 **명사(목적어)**, HTTP 메서드는 **동사**다.
  "주문을 / 삭제한다" = `DELETE /orders/42`. 문장 구조가 통일되면
  처음 보는 API도 읽힌다.

### ③ 결과는 HTTP 상태 코드로 표현한다

성공/실패를 바디에만 담지 않고 상태 코드로 먼저 말한다.
`200 OK`, `201 Created`(생성 성공 + `Location` 헤더),
`204 No Content`(성공했지만 돌려줄 바디 없음), `400`(요청 잘못),
`404`(자원 없음), `409`(상태 충돌) 등.

```http
# Before: 무조건 200 + 바디로만 성공 여부 전달
HTTP/1.1 200 OK
{"success": false, "message": "주문 없음"}
# 문제: 클라이언트·게이트웨이·모니터링이 모두 바디를 파싱해야 실패를 안다

# After: 상태 코드가 먼저 말한다
HTTP/1.1 404 Not Found
{"code": "ORDER_NOT_FOUND", "message": "주문 없음"}
```

### ④ 무상태(Stateless)

서버가 클라이언트의 상태(세션 문맥)를 기억하지 않고, **매 요청이
처리에 필요한 정보를 모두 담는다.** 어떤 서버 인스턴스가 받아도 같은
결과가 나오므로 **스케일 아웃(서버 증설)과 장애 복구가 쉬워진다** —
로드밸런서가 요청을 아무 서버로나 보내도 된다.

이 외에 캐시 가능(Cacheable), 계층화 시스템(Layered System),
균일한 인터페이스(Uniform Interface)까지가 REST의 제약 조건이다.
전부 나열하는 것보다 **①~④를 "왜"와 함께** 말하는 편이 낫다.

## 2. 리소스 네이밍 규칙 — 예측 가능성을 만드는 문법

핵심 기준은 하나다: **처음 보는 사람이 규칙만 알면 URI를 추측할 수
있는가.**

| 규칙 | Before | After |
|---|---|---|
| 동사 금지, 명사 사용 | `/getUsers` | `/users` |
| 복수형 명사 | `/user/42` | `/users/42` |
| 소문자 + 하이픈(kebab-case) | `/orderItems`, `/order_items` | `/order-items` |
| 계층 관계는 경로로 | `/orderItemList?orderId=42` | `/orders/42/items` |
| 파일 확장자 금지 | `/users/42.json` | `/users/42` + `Accept` 헤더 |

몇 가지는 이유까지 알아야 한다:

- **복수형을 쓰는 이유**: 컬렉션(`/users`)과 단건(`/users/42`)이
  하나의 일관된 패턴으로 이어진다. 단수/복수를 섞으면 클라이언트가
  매번 문서를 확인해야 한다.
- **계층은 소유 관계일 때만**: `/orders/42/items`는 "42번 주문에
  속한 항목들"이라는 소유가 명확할 때 쓴다. 3단계 이상 깊어지면
  (`/users/1/orders/42/items/3/reviews`) 오히려 가독성이 떨어지므로
  최상위 리소스로 끌어올린다(`/reviews?itemId=3`).
- **필터·정렬·페이징은 쿼리 파라미터로**: 자원의 식별은 경로,
  자원의 "보기 방식"은 쿼리로. `GET /orders?status=PAID&page=2`

### CRUD로 표현이 안 되는 동작 — 컨트롤 리소스

"주문 취소", "비밀번호 초기화"처럼 동사가 꼭 필요한 순간이 있다.
이때는 **행위 자체를 하위 리소스(명사화)로 표현**하는 것이 관례다.

```http
# 상태 전이를 리소스의 부분 수정으로 표현하거나
PATCH /orders/42        {"status": "CANCELLED"}

# 행위를 명사화한 컨트롤 리소스로 표현
POST /orders/42/cancellation
POST /users/42/password-reset
```

원칙을 억지로 우회하지 않고 "여기는 REST의 표현력이 부족한 지점이라
팀 컨벤션으로 컨트롤 리소스를 정해 일관되게 쓴다"고 말하면
실무 감각이 드러난다. (가산점 포인트)

## 3. 실무 관점 — 원칙보다 일관성이 계약이다

API는 배포하는 순간 **소비자(모바일 앱, 파트너사, 타 팀)와의
계약**이 된다. 실무에서 진짜 문제는 "REST 원칙 위반"이 아니라
**"엔드포인트마다 규칙이 다른 것"**이다.

- 어떤 API는 `/users/42`, 어떤 API는 `/getUser?id=42` →
  클라이언트 개발자는 매번 문서를 뒤지고, 문서가 낡으면 슬랙에 묻는다.
  **일관성이 없으면 API 하나 붙일 때마다 커뮤니케이션 비용이 든다.**
- 반대로 규칙이 일관되면 문서 없이도 "상품 목록은 아마
  `GET /products`겠지"라는 **예측**이 가능해지고, 그 예측이 맞는
  경험이 쌓이면 협업 속도가 붙는다.

그래서 시니어의 답은 "REST 원칙을 100% 지킨다"가 아니라
**"팀의 API 설계 가이드(컨벤션 문서)를 만들어 원칙 준수 여부보다
전체 API의 일관성을 우선한다"**이다. 이미 운영 중인 API가 규칙에서
벗어나 있다면, 그것을 고치는 것 자체가 계약 파기(breaking change)라
새 API부터 규칙을 적용하는 현실적 판단도 필요하다.

## 4. 꼬리질문 대비 포인트

### "GET으로 삭제하는 API(`GET /orders/42/delete`)는 뭐가 문제인가요?"

HTTP 메서드에는 **안전성(safe)과 멱등성(idempotent)이라는 약속**이
있다. GET은 "몇 번을 호출해도 서버 상태를 바꾸지 않는다(safe)"는
계약이고, 브라우저·프록시·크롤러·프리페치(미리 읽기) 도구가 이 계약을
믿고 동작한다. GET으로 삭제를 만들면 **크롤러가 링크를 따라가다
데이터를 지우거나, 캐시가 삭제 요청을 응답 재사용으로 삼켜버리는**
사고가 난다. 실제로 크롤러가 관리 페이지의 삭제 링크를 순회해 데이터가
증발한 사례는 유명한 고전 사고다.

### "무상태(stateless)면 로그인 상태는 어떻게 유지하나요?"

세션을 서버 메모리에 두지 않고, **매 요청에 인증 정보를 실어
보낸다** — 토큰(JWT 등)을 `Authorization` 헤더로 전달하는 방식.
서버는 토큰만 검증하면 되므로 어느 인스턴스가 받아도 동일하게
처리된다. 서버 세션을 꼭 써야 한다면 세션 저장소를 외부(Redis 등)로
분리해 서버 자체는 무상태를 유지한다.

### "PUT, POST, PATCH는 각각 언제 쓰나요?"

- **POST**: 컬렉션에 새 자원 생성(`POST /orders`), 서버가 ID를
  발급. 멱등하지 않다(두 번 호출하면 두 건 생긴다).
- **PUT**: 지정한 URI의 자원을 **전체 교체**. 멱등하다.
- **PATCH**: 자원의 **일부만 수정**.
자세한 차이는 별도 문서(02-put-vs-patch)에서 다루지만, "행위 의미가
메서드에 실려 있어야 클라이언트와 중간 계층(캐시, 게이트웨이)이 안전하게
동작한다"는 한 줄은 여기서도 유효하다.

### "HATEOAS까지 지켜야 진짜 REST 아닌가요?" (가산점 포인트)

원론적으로는 그렇다 — 응답에 다음 행동 가능한 링크를 담아 클라이언트가
URI를 하드코딩하지 않게 하는 것이 REST의 완성 단계(리처드슨 성숙도
모델 3단계)다. 하지만 실무 대부분의 API는 2단계(리소스 + HTTP 메서드 +
상태 코드)에서 멈추며, 그것으로 충분한 경우가 많다. "HATEOAS는
클라이언트 구현 비용이 커서, 공개 API처럼 소비자를 통제할 수 없는
환경이 아니면 비용 대비 효익이 낮다"고 트레이드오프로 답하면 좋다.

### "REST 원칙을 어겨도 되는 순간은 언제인가요?" (시니어 변별 포인트)

원칙은 목적(예측 가능성, HTTP 인프라 활용)을 위한 수단이므로,
**목적과 충돌하면 원칙이 양보한다.** 대표 사례:

- **검색 조건이 너무 길거나 민감할 때**: GET 쿼리스트링은 길이 제한과
  로그 노출 문제가 있어 `POST /orders/search`로 설계하기도 한다.
- **복잡한 상태 전이**: CRUD로 억지 매핑하지 말고 컨트롤 리소스
  (`POST /orders/42/cancellation`)를 컨벤션으로 정한다.
- 단, 예외는 **팀 가이드에 명문화해 예외조차 일관되게** 만든다.
  "원칙을 아는 사람이 의도적으로, 문서화하고 어기는 것"과
  "몰라서 제각각인 것"의 차이가 API 품질을 가른다.

## 한 줄 요약

REST는 자원을 URI(명사, 복수형)로 식별하고 행위를 HTTP 메서드로,
결과를 상태 코드로 표현하는 스타일이며 — 원칙의 진짜 가치는 규칙
자체가 아니라 **일관성이 만들어내는 예측 가능성**에 있다. API는
장기 계약이므로, 원칙 준수보다 팀 전체 API의 일관성을 우선하는 것이
소비자를 위한 설계다.
