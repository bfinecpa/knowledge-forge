# RESTful API 설계 원칙 — 리소스 중심 설계와 네이밍, 일관성이 곧 협업 속도

> 핵심 관전 포인트: **REST는 "자원(리소스)을 URI로 식별하고, 그 자원에 무엇을 할지는 HTTP 메서드로, 결과는 상태 코드로 말한다"는 리소스 중심 설계 스타일이다. 이름의 뜻부터가 설계 지침이다 — 서버가 가진 자원 자체가 아니라 그 자원의 **표현(Representation, 지금 상태를 JSON 같은 형식으로 찍어낸 스냅샷)**을 주고받고, 그 표현을 받아 클라이언트의 상태가 다음 단계로 **전이(State Transfer)**한다는 뜻이다. 주고받는 것이 "명사(표현)"이므로 URI도 동사가 아닌 명사(복수형)가 되고, 동사는 이미 자리가 있는 HTTP 메서드가 맡는다. 그리고 메서드에는 안전성(safe, 서버 상태를 바꾸지 않는다)과 멱등성(idempotent, 몇 번 반복해도 최종 상태가 같다)이라는 계약이 붙어 있어 캐시·프록시·크롤러·자동 재시도 라이브러리가 그 계약만 믿고 동작한다 — 그래서 `GET /orders/42/delete` 같은 규약 위반은 내 코드가 아니라 인프라가 사고를 낸다. 그런데 원칙 암기보다 중요한 것은 **일관성**이다. API는 한번 공개되면 바꾸기 어려운 장기 계약이고, 일관된 규칙만이 클라이언트 개발자가 "다음 엔드포인트가 어떻게 생겼을지" 예측할 수 있게 해 협업 속도를 만든다. 원칙은 그 일관성을 지키기 위한 공용 언어다.**

---

## 0. 질문 + 의도

**질문**: "RESTful API의 설계 원칙을 설명해주세요. 리소스 네이밍 규칙은?"

**출제 의도**: API는 한번 공개되면 바꾸기 어려운 장기 계약이다. 원칙의 준수 여부 자체보다, **일관성이 클라이언트 개발자의 예측 가능성(= 협업 속도)을 만든다**는 이유를 아는지 본다. "왜 이렇게 짓는가"를 소비자 관점에서 설명하는 사람과 규칙만 외운 사람이 갈린다.

## 1. REST의 핵심 원칙 — "리소스"가 중심이다

### 1-1. 이름부터 풀자 — Representational State Transfer

REST는 Roy Fielding이 2000년 박사 논문에서 정리한 아키텍처 스타일이고, 이름이 곧 설계 지침이다. 그런데 대부분의 설명이 `REST(Representational State Transfer)`라고 영문만 병기하고 넘어가서, 정작 이 세 단어가 무엇을 말하는지 모른 채 규칙만 외우게 된다. 이름부터 풀고 시작하자.

먼저 **표현(Representation)**이다. 서버가 DB에 들고 있는 42번 주문 그 자체를 네트워크로 보낼 방법은 없다. 보낼 수 있는 것은 **"42번 주문의 지금 상태를 특정 형식으로 찍어낸 스냅샷"**뿐이다. 그 스냅샷이 표현이다. 같은 자원 하나가 JSON으로도, XML로도, HTML로도 표현될 수 있고, 그래서 클라이언트는 `Accept: application/json` 헤더로 "나는 JSON 표현을 달라"고 요청한다.

```
[자원(resource)]              [표현(representation)]
 42번 주문                     {"id":42,"status":"PAID","total":9900}   <- JSON 표현
 (서버 안에만 존재하는 개념)     <order><id>42</id>...</order>            <- XML 표현
                               (네트워크로 오가는 것은 언제나 이쪽)
```

이 구분이 중요한 이유는, **URI가 가리키는 것이 "특정 형식의 파일"이 아니라 "자원"**이라는 결론이 여기서 나오기 때문이다. 뒤에 나올 "URI에 `.json` 확장자를 붙이지 않는다"는 규칙이 바로 이 문장의 따름정리다.

다음은 **상태 전이(State Transfer)**다. 여기서 말하는 "상태"는 서버의 데이터가 아니라 **클라이언트(애플리케이션)가 지금 어느 화면·어느 단계에 있는가**를 뜻한다. 웹 브라우징을 떠올리면 정확하다. 목록 페이지에서 링크를 누르면 상세 페이지의 표현이 전송돼 오고, 그 순간 사용자가 있는 자리가 "목록"에서 "상세"로 옮겨간다. 즉 **표현이 전송되는 것(Transfer)이 곧 클라이언트 상태의 전이**다. 그래서 "표현을 통한 상태 전이"라는 이름이 붙었다.

정리하면 REST는 **"자원을 URI로 지목하고, 그 자원의 표현을 주고받으며, 그 주고받음으로 클라이언트가 다음 단계로 이동하는"** 구조를 웹의 기존 인프라(HTTP) 위에서 그대로 쓰자는 제안이다. 면접에서는 제약 조건 여섯 개를 나열하는 것보다 아래 ①~④를 "왜"와 함께 짚는 편이 낫다.

### 1-2. ① 리소스는 URI로 식별한다

"무엇(what)"은 URI가 담당한다. 주문, 회원, 상품 같은 **자원(명사)**이 URI의 주인공이다.

```
/orders          → 주문 컬렉션이라는 자원
/orders/42       → 42번 주문이라는 자원
```

여기서 `/orders`도 어엿한 하나의 자원이라는 점을 짚어두면 좋다. "주문들의 모음"이라는 자원이 따로 있고, 그것을 조회하면 목록 표현이, 거기에 POST하면 새 항목이 추가되는 것이다. 컬렉션과 단건이 같은 문법 위에 놓이는 이 구조가 뒤의 네이밍 규칙(복수형)의 근거가 된다.

### 1-3. ② 행위는 HTTP 메서드로 표현한다

"어떻게(how)"는 메서드가 담당한다. URI에 동사를 넣지 않는 이유가 바로 이것 — **행위를 표현하는 자리가 이미 있기 때문**이다.

```http
# Before: URI에 동사 — 행위 표현 자리가 중복되고 규칙이 무너진다
POST /createOrder
POST /orders/42/delete
GET  /getOrderList

# After: 메서드가 행위, URI는 자원만
POST   /orders        # 생성
DELETE /orders/42     # 삭제
GET    /orders        # 목록 조회
```

비유하면 URI는 **명사(목적어)**, HTTP 메서드는 **동사**다. "주문을 / 삭제한다" = `DELETE /orders/42`. 문장 구조가 통일되면 처음 보는 API도 읽힌다.

그런데 메서드를 "행위 이름표" 정도로만 이해하면 절반만 아는 것이다. **HTTP 명세(RFC 9110)는 각 메서드에 두 가지 성질을 계약으로 못박아 두었고**, 세상의 인프라 전체가 그 계약을 참으로 믿고 움직인다. 이 두 성질을 여기서 정의해 두어야 아래 상태 코드 이야기도, 4절의 꼬리질문도 근거를 갖는다.

**안전(safe)** 은 "이 요청은 서버의 상태를 바꾸지 않는다"는 약속이다. 읽기 전용이라는 뜻이다. 이름이 "안전"인 이유는 **보내는 쪽 입장에서 부담이 없다**는 데서 왔다 — 링크를 미리 눌러봐도, 크롤러가 사이트 전체를 훑어도 아무것도 망가지지 않으니 안전하다. 실무 감각으로는 **"이 요청이 크롤러에 의해 하루 만 번 호출돼도 괜찮은가?"**를 자문하면 된다.

**멱등(idempotent)** 은 "같은 요청을 1번 보내든 N번 보내든 서버의 최종 상태가 같다"는 약속이다. 상태를 바꿔도 되지만 그 변화가 **누적되지 않는다**는 뜻이다. 낯선 한자어인 멱등(冪等)은 수학에서 왔다 — 거듭 적용해도 결과가 같은 연산, 즉 `f(f(x)) = f(x)`다. 절댓값을 떠올리면 된다. `abs(-3)`도 3이고 `abs(abs(-3))`도 3이라, 몇 번을 씌워도 더는 변하지 않는다.

일상 비유로는 **엘리베이터 호출 버튼**이 정확하다. 한 번 누르든 조급해서 열 번 누르든 엘리베이터의 상태는 "호출됨" 하나다. 반면 **자판기의 결제 버튼**은 멱등이 아니다 — 열 번 누르면 열 번 결제된다.

여기서 놓치기 쉬운 것 하나. **멱등성의 기준은 "응답이 같다"가 아니라 "서버의 최종 상태가 같다"이다.** `DELETE /orders/42`를 두 번 보내면 첫 번째는 `204`, 두 번째는 `404`로 응답이 달라지지만, 두 호출이 끝난 뒤 서버는 똑같이 "42번 주문이 없는 상태"다. 그래서 DELETE는 멱등이다.

그리고 안전한 메서드는 **자동으로 멱등**이다. 상태를 아예 안 바꾸는데 반복한다고 달라질 리가 없기 때문이다. 반대는 성립하지 않는다 — DELETE는 안전하지 않지만 멱등이다.

| 메서드 | 안전(safe) | 멱등(idempotent) | 그 칸에 들어가는 이유 |
|---|---|---|---|
| GET | O | O | "이 자원의 표현을 달라" — 조회만 요청하므로 상태를 안 바꾼다 |
| HEAD | O | O | GET과 같되 본문 없이 헤더만 받는다 — 하는 일이 GET의 부분집합 |
| OPTIONS | O | O | "이 URI에 어떤 메서드를 쓸 수 있나"를 묻는다 — CORS 프리플라이트가 이것 |
| PUT | X | O | "이 자원을 이 상태로 만들어라" — 본문에 최종 상태가 통째로 담겨 반복해도 같은 자리 |
| DELETE | X | O | "이 자원이 없는 상태로 만들어라" — 최종 상태는 언제나 "없음" 하나 |
| POST | X | X | "이 데이터를 처리해라" — 반복하면 새 자원이 하나씩 더 생겨 누적된다 |
| PATCH | X | X (보장 안 함) | 수정 내용의 성질을 규약이 정하지 않는다 — 상대 연산(`+100`)이면 누적된다 |

(엄밀히는 `TRACE`도 안전·멱등이지만 요청 헤더를 그대로 되비추는 디버깅용 메서드라 보안상 대부분 차단한다.)

표에서 PATCH 칸을 오해하지 말자. **"PATCH는 절대 멱등이 아니다"가 아니라 "구현이 멱등일 수는 있지만 클라이언트·인프라가 멱등이라고 가정해서는 안 된다"**가 정확한 표현이다. 이 미묘한 차이는 [02번 문서](02-put-vs-patch.md)에서 자세히 다룬다. 안전성·멱등성 자체를 더 깊이 보려면 [8장 04번 문서](../08-network-http/04-http-method-idempotency-and-safety.md)를 함께 본다.

### 1-4. ③ 결과는 HTTP 상태 코드로 표현한다

성공과 실패를 본문에만 담지 말고 **상태 코드로 먼저 말한다.** 이유는 상태 코드가 **본문을 파싱하지 않고도 읽히는 유일한 신호**이기 때문이다. 로드밸런서, API 게이트웨이, 모니터링 에이전트, 클라이언트 라이브러리의 재시도 로직은 내 응답 JSON의 스키마를 모른다. 이들이 아는 것은 세 자리 숫자뿐이다.

```http
# Before: 무조건 200 + 본문으로만 성공 여부 전달
HTTP/1.1 200 OK
{"success": false, "message": "주문 없음"}
# 문제: 클라이언트·게이트웨이·모니터링이 모두 본문을 파싱해야 실패를 안다.
#       에러율 대시보드에는 이 응답이 "성공"으로 집계된다 — 장애가 나도 그래프가 평온하다.

# After: 상태 코드가 먼저 말한다
HTTP/1.1 404 Not Found
{"code": "ORDER_NOT_FOUND", "message": "주문 없음"}
```

자주 쓰는 코드는 다음 여섯 개다. 각각 "언제 쓰는가"를 붙여 외워야 실전에서 고를 수 있다.

| 코드 | 뜻 | 언제 쓰는가 | 응답 본문 |
|---|---|---|---|
| `200 OK` | 성공 | 조회 성공, 또는 수정 후 바뀐 자원의 표현을 돌려줄 때 | 있음 |
| `201 Created` | 새 자원이 생겼다 | `POST /orders`로 자원을 만들었을 때. `Location` 헤더에 **생성된 자원의 URI**를 담는다 | 보통 생성된 자원의 표현 |
| `204 No Content` | 성공했고 돌려줄 표현이 없다 | 삭제 성공, 또는 수정은 됐지만 클라이언트가 이미 결과를 아는 경우 | 없음 (있으면 규약 위반) |
| `400 Bad Request` | 요청 자체가 잘못됐다 | 필수 파라미터 누락, 타입 불일치처럼 **요청을 고치기 전엔 몇 번을 보내도 같은 결과**인 오류 | 오류 표현 |
| `404 Not Found` | 그 URI에 해당하는 자원이 없다 | 존재하지 않는 ID 조회 | 오류 표현 |
| `409 Conflict` | 자원의 현재 상태와 충돌한다 | 요청 자체는 멀쩡한데 **지금 상태에서는 할 수 없는** 경우 — 이미 취소된 주문을 또 취소, 중복 이메일 가입 | 오류 표현 |

`201`의 `Location` 헤더를 조금 더 보자. 클라이언트가 `POST /orders`를 보낼 때는 **만들어질 주문의 URI를 모른다.** ID를 서버가 발급하기 때문이다. 그래서 서버가 응답에 `Location: /orders/42`를 실어 "방금 만든 것은 여기에 있다"고 알려준다. 클라이언트는 이 값을 그대로 다음 요청의 주소로 쓸 수 있고, URI 조립 규칙을 자기 코드에 하드코딩하지 않아도 된다.

```http
HTTP/1.1 201 Created
Location: /orders/42
Content-Type: application/json

{"id": 42, "status": "PENDING", "total": 9900}
```

`204`를 언제 `200` 대신 쓰는가도 자주 갈리는 지점이다. 기준은 **"클라이언트에게 돌려줄 표현이 실제로 있는가"**다. `DELETE /orders/42`가 성공했다면 돌려줄 주문 표현은 이제 존재하지 않으므로 `204`가 맞다. 반대로 `PATCH`로 수정한 뒤 **서버가 계산한 값(할인 적용 후 총액, 갱신된 `updatedAt`)이 응답에 필요하다면** `200 + 본문`이 맞다. 판단이 애매할 때는 "이 응답 본문을 클라이언트가 실제로 읽고 쓰는가"를 물어보면 된다 — 아무도 안 읽는 `{"success": true}`를 매번 만들어 보내는 것은 대역폭과 파싱 비용만 늘린다.

상태 코드 전반의 사용 기준(3xx 리다이렉트, 401과 403의 구분, 5xx 계열)은 [8장 05번 문서](../08-network-http/05-http-status-codes-usage-criteria.md)에서 별도로 다룬다.

### 1-5. ④ 무상태(Stateless) — 먼저 "상태를 들고 있으면 무엇이 곤란한가"

무상태의 이점을 "스케일 아웃과 장애 복구가 쉬워진다"로 먼저 말하면 결론만 남고 이유가 사라진다. 반대편, 즉 **서버가 상태를 들고 있을 때 무슨 일이 벌어지는지**부터 보자.

전통적인 서버 세션 방식에서는 로그인에 성공하면 서버가 자기 **메모리에** 세션 객체를 만들고 그 열쇠(세션 ID)를 쿠키로 내려준다. 문제는 그 세션이 **그 서버 인스턴스의 메모리에만** 있다는 것이다. 사용자의 다음 요청이 2번 서버로 가면 2번 서버는 그 세션 ID를 모르므로 "로그인 안 한 사람"으로 취급한다.

그래서 로드밸런서에 **스티키 세션(sticky session)** — 같은 사용자의 요청을 항상 같은 서버로 붙여 보내는 설정 — 을 걸게 된다. 이름 그대로 사용자가 특정 서버에 "붙어" 버리는 것이다. 여기서 두 가지 대가가 발생한다.

```
[스티키 세션이 걸린 상태]

  사용자 A ─┐
  사용자 B ─┼─→ [1번 서버]  세션 A,B,C 보유 · 부하 90%   ← 죽으면 A,B,C 전원 로그아웃
  사용자 C ─┘
                [2번 서버]  세션 없음      · 부하 10%   ← 증설해도 기존 사용자는 안 옴
             ↑
        새로 띄운 서버
```

첫째, **서버를 늘려도 부하가 고르게 퍼지지 않는다.** 이미 1번 서버에 붙어 있는 사용자들은 계속 1번으로 간다. 트래픽이 몰려 서버를 증설해도 새 서버는 새로 들어오는 사용자만 받으므로, 지금 급한 부하는 그대로 남는다.

둘째, **그 서버가 죽으면 거기 붙어 있던 사용자의 세션이 통째로 사라진다.** 메모리에 있던 것이니 복구할 방법이 없다. 사용자 눈에는 "아무것도 안 했는데 갑자기 로그아웃됐다"로 보인다. 배포 때마다 전원 로그아웃되는 서비스가 이 구조다.

**무상태(Stateless)** 는 이 전제를 없앤다. 서버가 요청과 요청 사이에 클라이언트의 문맥을 기억하지 않고, **매 요청이 처리에 필요한 정보를 스스로 모두 담는다.** 그러면 어떤 인스턴스가 받아도 같은 결과가 나오므로 로드밸런서가 요청을 아무 서버로나 던져도 되고(부하가 고르게 퍼진다), 한 대가 죽어도 다음 요청이 다른 서버로 가서 정상 처리된다(장애 복구).

여기서 오해 하나를 짚어두자. **무상태는 "서버가 아무 데이터도 저장하지 않는다"는 뜻이 아니다.** 주문 데이터는 당연히 DB에 남는다. 무상태가 금지하는 것은 **"이 클라이언트가 지금 어느 단계까지 진행했는지"라는 대화의 문맥을 서버 메모리에 들고 다음 요청을 기다리는 것**이다. 자원의 상태(resource state)는 저장하되, 클라이언트의 애플리케이션 상태(application state)는 클라이언트가 들고 다닌다 — 이것이 REST의 무상태다.

### 1-6. 나머지 제약 조건 — 이름만 알고 넘어가면 안 되는 것들

Fielding이 정의한 REST의 아키텍처 제약은 여섯 개다. 앞의 ①~④는 그중 두 개(균일한 인터페이스, 무상태)를 실무 지침으로 풀어 쓴 것이므로, 나머지도 한 문장씩은 실체를 갖고 있어야 한다.

**클라이언트-서버(Client-Server)**: UI를 다루는 쪽과 데이터를 저장하는 쪽의 관심사를 분리한다. 둘이 HTTP라는 계약으로만 이어져 있으면 앱을 새로 만들어도 서버를 건드릴 필요가 없고, 서버 DB를 갈아엎어도 앱이 그대로 돈다. 지금은 너무 당연해 보이지만, 화면과 데이터가 한 덩어리이던 시절에 대비해 명시된 제약이다.

**무상태(Stateless)**: 1-5에서 본 그대로다. 요청은 자기 자신만으로 해석 가능해야 한다.

**캐시 가능(Cacheable)**: 응답은 **자기 자신이 캐시 가능한지, 얼마나 유효한지를 스스로 밝혀야 한다**(`Cache-Control`, `ETag`, `Last-Modified`). 그래야 브라우저와 CDN이 같은 요청을 서버까지 보내지 않고 저장해둔 응답을 재사용한다. 이 재사용이 성립하는 근거가 1-3의 안전성 계약이다 — GET이 아무것도 바꾸지 않는다는 약속이 있어야 중간에서 응답을 가로채 재사용해도 되기 때문이다. 상태를 바꾸는 GET을 만들면 이 계약이 깨져서, 삭제 요청이 캐시에 삼켜지거나 반대로 캐시된 옛 응답이 계속 돌아오는 사고가 난다.

**계층화 시스템(Layered System)**: 클라이언트는 자기가 말을 거는 상대가 최종 서버인지 중간 계층인지 **알 수 없어야 하고, 알 필요도 없어야 한다.** 이 제약이 있어서 클라이언트와 서버 사이에 리버스 프록시(Nginx), CDN, 로드밸런서, API 게이트웨이를 얼마든지 끼워 넣어도 클라이언트 코드가 한 줄도 바뀌지 않는다. 8장에서 다루는 프록시·CDN·게이트웨이 이야기가 전부 이 제약 위에 서 있다. 반대로 말하면, 클라이언트가 "우리 서버는 8080 포트로 직접 붙어야 한다" 같은 배치 정보를 알고 있다면 그 API는 이 제약을 어긴 것이고, 나중에 앞단 인프라를 바꿀 때 클라이언트를 전부 고쳐야 한다.

**균일한 인터페이스(Uniform Interface)**: REST를 다른 스타일과 구분 짓는 핵심 제약으로, "모든 자원을 똑같은 방식으로 다룬다"는 뜻이다. 하위 규칙이 넷인데, 앞의 ①②③이 바로 그중 셋이다.

| 하위 규칙 | 뜻 | 이 문서에서 |
|---|---|---|
| 자원의 식별 | 모든 자원에 URI라는 고유 주소가 있다 | ① |
| 표현을 통한 자원 조작 | 자원 자체가 아니라 표현(JSON 등)을 주고받아 변경한다 | ①, 1-1 |
| 자기 서술적 메시지 | 메시지 하나만 보고 해석할 수 있어야 한다 — 메서드·`Content-Type`·상태 코드가 그 역할 | ②③ |
| 하이퍼미디어(HATEOAS) | 응답이 "다음에 할 수 있는 행동"의 링크를 담는다 | 4절 꼬리질문 |

**코드 온 디맨드(Code-On-Demand, 선택)**: 서버가 실행 가능한 코드(자바스크립트 등)를 내려보내 클라이언트의 기능을 확장하는 것. 여섯 제약 중 **유일하게 선택 사항**이며, 지키지 않아도 RESTful하다고 부른다.

## 2. 리소스 네이밍 규칙 — 예측 가능성을 만드는 문법

### 2-1. 판단 기준은 하나다

규칙이 여러 개로 보이지만 목적은 하나로 수렴한다. **처음 보는 사람이 규칙만 알면 URI를 추측할 수 있는가.**

| 규칙 | Before | After |
|---|---|---|
| 동사 금지, 명사 사용 | `/getUsers` | `/users` |
| 복수형 명사 | `/user/42` | `/users/42` |
| 소문자 + 하이픈(kebab-case) | `/orderItems`, `/order_items` | `/order-items` |
| 계층 관계는 경로로 | `/orderItemList?orderId=42` | `/orders/42/items` |
| 파일 확장자 금지 | `/users/42.json` | `/users/42` + `Accept` 헤더 |

### 2-2. 이유까지 알아야 하는 규칙들

**복수형을 쓰는 이유**는 컬렉션과 단건이 하나의 일관된 패턴으로 이어지기 때문이다. `/users`(사용자들의 모음)와 `/users/42`(그 모음의 42번 원소)는 "컬렉션 / 컬렉션의 원소"라는 같은 문법을 공유한다. 단수와 복수를 섞으면 클라이언트는 엔드포인트마다 "여긴 `/user`였나 `/users`였나"를 문서에서 확인해야 한다. 규칙의 값어치는 문법적 정확성이 아니라 **확인하러 가지 않아도 되는 데** 있다.

**kebab-case를 쓰는 이유**는 URI의 경로 부분이 대소문자를 구분하기 때문이다. `/orderItems`와 `/orderitems`는 서로 다른 URI이고, 어느 쪽으로 적었는지 헷갈리는 순간 404가 난다. 전부 소문자로 통일하면 이 실수 자체가 사라진다. 단어 구분자로 언더스코어(`_`) 대신 하이픈(`-`)을 고르는 것은 관례에 가깝지만, 밑줄이 링크의 밑줄 표시에 가려 안 보이는 문제와 검색엔진이 하이픈을 단어 구분자로 취급하는 관행이 근거로 꼽힌다.

**파일 확장자를 쓰지 않는 이유**는 1-1로 돌아간다. URI가 가리키는 것은 자원이지 파일이 아니고, 같은 자원이 JSON으로도 XML로도 표현될 수 있다. 어떤 표현을 원하는지는 **`Accept` 헤더로 협상(content negotiation)**하는 것이 HTTP가 이미 마련해둔 자리다. 확장자를 URI에 박으면 표현 형식이 자원의 주소에 섞여 들어가, 형식이 하나 늘 때마다 URI가 한 벌씩 늘어난다.

**계층은 소유 관계일 때만** 경로로 표현한다. `/orders/42/items`는 "42번 주문에 속한 항목들"이라는 소유가 명확할 때 쓴다. 그런데 여기서 반드시 따라오는 것이 깊이 제한이다.

```
/users/1/orders/42/items/3/reviews/9
   └────┬────┘└───┬───┘└──┬──┘
    이 리뷰 하나를 지목하는 데 정말 앞의 세 조상이 필요한가?
```

**3단계 이상 깊어지면 최상위 리소스로 끌어올린다**는 규칙에는 이유가 셋 있다.

첫째, **클라이언트가 필요 없는 ID를 들고 다녀야 한다.** 리뷰 9번을 식별하는 데 논리적으로 필요한 것은 리뷰 ID 하나뿐인데, URI가 조상 전체를 요구하면 클라이언트는 리뷰 ID를 알고 있어도 요청을 만들 수 없다. "리뷰를 수정하려면 그 리뷰가 어느 주문의 어느 항목에 달렸는지부터 다시 조회해야 하는" 구조가 된다.

둘째, **같은 자원에 URI가 두 벌 생긴다.** 나중에 "내가 쓴 리뷰 전체" 화면이 필요해지면 `/reviews?userId=1` 같은 경로를 만들게 되고, 그 순간 리뷰 9번은 `/users/1/orders/42/items/3/reviews/9`와 `/reviews/9`라는 두 주소를 갖는다. 캐시 키가 갈라지고, `ETag` 관리가 두 벌이 되고, 권한 검사 코드도 두 곳에 생긴다.

셋째, **서버가 조상 검증을 매번 해야 한다.** `/users/1/orders/42`를 받으면 "42번 주문이 정말 1번 사용자 것인가"를 확인해야 하고, 이 검증을 빠뜨리면 남의 주문을 조회할 수 있는 접근 제어 취약점이 된다. 계층이 깊어질수록 검증해야 할 조합이 늘어난다.

그래서 실무 기준은 이렇게 정리된다. **상위 자원 없이는 존재 의미가 없는 자원만 중첩하고**(주문 항목은 주문 없이 의미가 없다), **독립적으로 식별·조회되는 자원은 최상위로 올린 뒤 관계를 쿼리 파라미터로 표현한다**(`/reviews?itemId=3`).

**필터·정렬·페이징은 쿼리 파라미터로** 보낸다. 경계는 명확하다 — **자원의 식별은 경로, 자원을 "어떻게 보여줄지"는 쿼리**다. `GET /orders?status=PAID&page=2&sort=createdAt,desc`에서 자원은 어디까지나 "주문 컬렉션" 하나이고, `status`·`page`·`sort`는 그 컬렉션을 걸러내고 잘라내는 방식일 뿐이다. 이 경계를 지키면 "`/paid-orders`와 `/pending-orders`를 따로 만들었다가 상태가 하나 늘 때마다 엔드포인트를 추가하는" 상황을 피할 수 있다.

### 2-3. CRUD로 표현이 안 되는 동작 — 컨트롤 리소스

"주문 취소", "비밀번호 초기화"처럼 동사가 꼭 필요한 순간이 있다. 이런 동작은 생성·조회·수정·삭제 중 어디에도 깔끔하게 들어맞지 않는다. "주문 취소"는 주문을 지우는 것도 아니고 단순히 필드 하나를 바꾸는 것도 아니다 — 재고 복구, 결제 취소, 알림 발송이 딸린 하나의 업무 절차다.

이때 쓰는 관례가 **컨트롤 리소스(control resource)**다. 이름 그대로 **"제어(control)를 위해 만들어낸 자원"**, 즉 **행위를 명사로 바꿔 자원인 척 만든 URI**를 말한다. "취소한다(cancel)"라는 동사를 "취소(cancellation)"라는 명사로 바꿔 `/orders/42/cancellation`이라는 자원을 만들고, 거기에 POST하면 취소가 실행되는 식이다. 자원이 아닌 것을 자원의 문법 안으로 들여오는 우회이므로, REST 원칙의 예외가 아니라 **표현력이 모자란 지점을 메우는 규약**으로 이해하는 편이 정확하다.

```http
# 방법 A: 상태 전이를 자원의 부분 수정으로 표현한다
PATCH /orders/42        {"status": "CANCELLED"}

# 방법 B: 행위를 명사화한 컨트롤 리소스로 표현한다
POST /orders/42/cancellation
POST /users/42/password-reset
```

둘의 갈림 기준은 **"그 전이에 딸린 부수 효과가 얼마나 되는가"**다. 상태 필드 하나만 바뀌는 단순한 전이라면 A가 자연스럽다. 반면 취소처럼 여러 시스템이 함께 움직이고 실패할 수 있는 절차라면, B가 "이것은 단순한 필드 수정이 아니라 하나의 작업"이라는 사실을 URI에 드러내 준다. 게다가 B는 취소 사유 같은 **그 행위에만 필요한 입력을 본문에 담기 좋고**, 나중에 `GET /orders/42/cancellation`으로 취소 내역을 조회하는 확장도 자연스럽다.

원칙을 억지로 우회하지 않고 "여기는 REST의 표현력이 부족한 지점이라 팀 컨벤션으로 컨트롤 리소스를 정해 일관되게 쓴다"고 말하면 실무 감각이 드러난다. (가산점 포인트)

## 3. 실무 관점 — 원칙보다 일관성이 계약이다

API는 배포하는 순간 **소비자(모바일 앱, 파트너사, 타 팀)와의 계약**이 된다. 계약이라는 말이 무거운 이유는, 한번 나간 API는 내가 고치고 싶다고 고칠 수 없기 때문이다. 앱은 스토어 심사를 거쳐 배포되고 사용자가 업데이트해야 반영되며, 파트너사는 자기 일정으로 움직인다.

그런데 실무에서 진짜 문제를 일으키는 것은 "REST 원칙 위반"이 아니라 **"엔드포인트마다 규칙이 다른 것"**이다.

어떤 API는 `/users/42`, 어떤 API는 `/getUser?id=42`, 또 어떤 API는 `/api/v1/user/get/42`인 서비스를 상상해 보자. 클라이언트 개발자는 화면 하나 붙일 때마다 문서를 뒤지고, 문서가 낡아 있으면 슬랙에 묻고, 답이 올 때까지 기다린다. **일관성이 없으면 API 하나 붙일 때마다 커뮤니케이션 비용이 든다.** 이 비용은 엔드포인트 수에 비례해 누적된다.

반대로 규칙이 일관되면 문서 없이도 "상품 목록은 아마 `GET /products`겠지"라는 **예측**이 가능해진다. 그리고 그 예측이 맞는 경험이 서너 번 쌓이면 클라이언트 개발자는 문서를 확인하러 가지 않게 된다. 이것이 협업 속도다.

그래서 시니어의 답은 "REST 원칙을 100% 지킨다"가 아니라 **"팀의 API 설계 가이드(컨벤션 문서)를 만들어, 원칙 준수 여부보다 전체 API의 일관성을 우선한다"**이다.

여기에 하나를 더 얹으면 판단력이 드러난다. **이미 운영 중인 API가 규칙에서 벗어나 있다면, 그것을 고치는 것 자체가 계약 파기(breaking change)다.** `/getUser?id=42`가 흉하다고 `/users/42`로 바꾸면 그 API를 쓰던 구버전 앱이 전부 깨진다. 현실적인 판단은 **새로 만드는 API부터 규칙을 적용하고**, 기존 것은 버전 정책이나 폐기(deprecation) 일정 위에서 다루는 것이다. 이 부분은 [08번 문서](08-backward-compatible-api-changes.md)와 [03번 문서](03-api-versioning-strategies.md)에서 이어진다.

## 4. 꼬리질문 대비 포인트

### "GET으로 삭제하는 API(`GET /orders/42/delete`)는 뭐가 문제인가요?"

1-3에서 정의한 **안전성(safe)** 계약을 근거로 답한다. GET은 "몇 번을 호출해도 서버 상태를 바꾸지 않는다"는 약속이고, **브라우저·프록시·CDN·검색엔진 크롤러·프리페치(미리 읽기) 기능이 전부 이 약속을 참으로 믿고 동작한다.**

여기서 핵심은 **"내 코드는 멀쩡한데 인프라가 사고를 낸다"**는 구조다. 이들은 내 서버 코드를 읽어보지 않았고, 오직 메서드 이름만 보고 판단한다. GET으로 삭제를 만들면 이런 일이 벌어진다.

- **크롤러가 링크를 따라가다 데이터를 지운다.** 관리 페이지의 삭제 링크를 순회해 데이터가 통째로 증발한 사고는 유명한 고전이다.
- **브라우저나 툴바의 프리페치가 사용자가 누르지도 않은 삭제를 실행한다.** 링크에 마우스만 올려도 미리 받아두는 기능이 있기 때문이다.
- **캐시가 삭제 요청을 삼킨다.** 중간 캐시는 GET 응답을 저장해뒀다가 재사용해도 된다고 배웠으므로, 두 번째 삭제 요청은 서버까지 오지도 않고 캐시된 응답이 돌아간다. 클라이언트는 "삭제했다"는 응답을 받았는데 서버에서는 아무 일도 일어나지 않는다.

정리하면, **규약 위반의 대가는 내 서버의 로그가 아니라 내가 통제하지 못하는 인프라에서 나타난다.** 그래서 위험하다.

### "무상태(stateless)면 로그인 상태는 어떻게 유지하나요?"

핵심은 **"기억하지 않는다"이지 "인증하지 않는다"가 아니다.** 서버가 세션을 메모리에 들고 있는 대신, **매 요청에 인증 정보를 실어 보내면** 된다. 토큰(JWT 등)을 `Authorization: Bearer <token>` 헤더로 전달하는 방식이 대표적이다.

이 방식이 무상태인 이유는, 토큰 자체에 "누구인지"가 서명과 함께 담겨 있어 **서버가 그 요청 하나만 보고 검증을 끝낼 수 있기 때문**이다. 이전 요청의 기억도, 다른 서버와의 공유도 필요 없다. 그래서 어느 인스턴스가 받아도 동일하게 처리된다.

서버 세션을 꼭 써야 한다면 절충안이 있다. **세션 저장소를 외부(Redis 등)로 분리**하는 것이다. 이때 세션이라는 상태 자체는 남지만 **애플리케이션 서버는 무상태**가 되므로, 1-5에서 본 스티키 세션의 두 문제(부하 편중, 인스턴스 사망 시 로그아웃)가 사라진다. 다만 요청마다 Redis 왕복이 추가되고 Redis가 새로운 단일 장애 지점이 된다는 대가가 있다. 쿠키·세션·토큰 인증의 비교는 [8장 07번 문서](../08-network-http/07-cookie-session-token-auth.md)에서 더 다룬다.

### "PUT, POST, PATCH는 각각 언제 쓰나요?"

- **POST**: 컬렉션에 새 자원을 생성한다(`POST /orders`). **서버가 ID를 발급**하므로 클라이언트는 만들어질 URI를 미리 알 수 없다. 멱등하지 않다 — 두 번 호출하면 주문이 두 건 생긴다.
- **PUT**: 지정한 URI의 자원을 **본문 내용으로 전체 교체**한다. 본문에 최종 상태가 통째로 담기므로 몇 번을 반복해도 결과가 같아 **멱등**하다.
- **PATCH**: 자원의 **일부만 수정**한다. 본문에는 바꿀 부분만 담긴다.

선택 기준을 한 줄로 말하면 이렇다. **새로 만드는데 주소를 서버가 정하면 POST, 주소가 정해진 자원을 통째로 갈아끼우면 PUT, 그중 일부만 손대면 PATCH.**

PUT과 PATCH의 자세한 차이와 "안 보낸 필드가 null로 덮이는" 사고는 [02번 문서](02-put-vs-patch.md)에서 다룬다. 다만 **"행위의 의미가 메서드에 실려 있어야 클라이언트와 중간 계층(캐시, 게이트웨이, 재시도 라이브러리)이 안전하게 동작한다"**는 한 줄은 여기서도 그대로 유효하다.

### "HATEOAS까지 지켜야 진짜 REST 아닌가요?" (가산점 포인트)

원론적으로는 그렇다. **HATEOAS(Hypermedia As The Engine Of Application State, 애플리케이션 상태의 엔진으로서의 하이퍼미디어)**는 응답에 **"지금 이 상태에서 다음에 할 수 있는 행동"의 링크를 담아** 클라이언트가 URI를 하드코딩하지 않게 하는 것이다.

```json
{
  "id": 42, "status": "PAID", "total": 9900,
  "_links": {
    "self":   {"href": "/orders/42"},
    "cancel": {"href": "/orders/42/cancellation", "method": "POST"}
  }
}
```

핵심은 **취소 가능 여부를 클라이언트가 판단하지 않는다**는 데 있다. `cancel` 링크가 응답에 있으면 취소 버튼을 보여주고, 없으면 감춘다. 취소 정책이 바뀌어도(예: 배송 시작 후 취소 불가) 서버만 고치면 되고 앱을 재배포할 필요가 없다.

이 개념은 **리처드슨 성숙도 모델(Richardson Maturity Model)**의 마지막 단계다. 성숙도 모델은 "얼마나 HTTP를 제대로 쓰고 있는가"를 네 단계로 나눈 것인데, 3단계라는 말만 던지면 의미가 없으니 전체를 봐야 한다.

| 단계 | 이름 | 무엇이 갖춰졌는가 | 전형적인 모습 |
|---|---|---|---|
| 0단계 | POX의 늪 | 아무것도 — HTTP를 단순한 전송 터널로만 쓴다 | `POST /api` 하나에 `{"method":"getOrder","id":42}`를 담아 보낸다 |
| 1단계 | 리소스 | 자원마다 URI가 갈라진다 | `POST /orders/42/get`, `POST /orders/create` — URI는 나뉘었지만 행위가 아직 URI에 있다 |
| 2단계 | HTTP 동사 | 메서드와 상태 코드를 규약대로 쓴다 | `GET /orders/42` → `200`, `DELETE /orders/42` → `204` |
| 3단계 | 하이퍼미디어 컨트롤 | 응답이 다음 행동의 링크를 담는다 | 위 JSON처럼 `_links`에 `cancel`이 실려 온다 |

실무 대부분의 API는 **2단계에서 멈추며, 그것으로 충분한 경우가 많다.** 이유를 트레이드오프로 답하면 좋다. HATEOAS는 **클라이언트가 링크를 따라 동작하도록 만들어져 있어야만 값을 한다.** 그런데 현실의 앱은 화면 흐름이 기획서로 고정돼 있어 URI를 어차피 알고 있고, 링크를 해석하는 범용 클라이언트를 만드는 비용이 크다. 서버는 링크를 열심히 내려보내는데 클라이언트가 무시하면 응답 크기만 커진다.

그래서 **"소비자를 통제할 수 없는 공개 API처럼 클라이언트를 마음대로 고칠 수 없는 환경이 아니면 비용 대비 효익이 낮다"**가 현실적인 답이다. 반대로 결제 흐름처럼 **"지금 어떤 행동이 가능한가"가 상태에 따라 자주 바뀌는 도메인**에서는 부분적으로 도입할 값어치가 있다.

### "REST 원칙을 어겨도 되는 순간은 언제인가요?" (시니어 변별 포인트)

원칙은 목적(예측 가능성, HTTP 인프라 활용)을 위한 수단이므로, **목적과 충돌하면 원칙이 양보한다.** 대표 사례가 셋이다.

**검색 조건이 너무 길거나 민감할 때.** 조회는 GET이 원칙이지만 GET은 조건을 쿼리스트링에 실어야 한다. 그런데 쿼리스트링은 서버·프록시마다 길이 상한이 있어 조건이 수십 개가 되면 잘리고, 무엇보다 **접근 로그와 브라우저 히스토리에 그대로 남는다.** 주민등록번호나 검색어 같은 민감한 값이 로그 파일에 쌓이는 것이다. 그래서 `POST /orders/search`처럼 조건을 본문에 담는 설계를 택하기도 한다. 대신 POST는 캐시되지 않는다는 대가를 감수하는 것이므로, 그 손해를 알고 고르는 것과 모르고 고르는 것은 다르다.

**복잡한 상태 전이.** CRUD로 억지 매핑하지 말고 2-3의 컨트롤 리소스(`POST /orders/42/cancellation`)를 컨벤션으로 정한다.

**단, 예외는 팀 가이드에 명문화해 예외조차 일관되게 만든다.** 이것이 핵심이다. "원칙을 아는 사람이 의도적으로, 근거와 함께 문서화하고 어기는 것"과 "몰라서 제각각인 것"은 결과물이 비슷해 보여도 완전히 다르다. 전자는 소비자가 예외의 목록을 알 수 있지만, 후자는 소비자가 매번 부딪혀 보고 알아내야 한다.

## 한 줄 요약

REST는 자원의 **표현(JSON 등)을 주고받아 클라이언트의 상태를 전이시키는** 스타일이므로 URI에는 명사(복수형)를, 행위에는 안전성·멱등성 계약이 붙은 HTTP 메서드를, 결과에는 상태 코드를 쓰고 서버는 요청 사이의 문맥을 기억하지 않는다(무상태) — 그러나 원칙의 진짜 가치는 규칙 자체가 아니라 **일관성이 만들어내는 예측 가능성**에 있으므로, API가 장기 계약임을 전제로 "원칙 준수"보다 "팀 전체 API의 일관성"을 우선하고 예외조차 문서화해 일관되게 만드는 것이 소비자를 위한 설계다.
