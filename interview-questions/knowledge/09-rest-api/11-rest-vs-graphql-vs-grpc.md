# REST vs GraphQL vs gRPC — 기술이 아니라 "누가 쓰는가"로 고른다

> 핵심 관전 포인트: **세 기술의 선택 축은 유행이 아니라 소비자 특성이다.
> 불특정 다수·외부 파트너가 쓰는 공개 API는 REST — HTTP 생태계(캐시,
> 브라우저, curl, 디버깅 도구)를 그대로 물려받고 온보딩 비용이 가장 낮다.
> 화면이 다양하고 클라이언트가 조회 형태를 주도해야 하는 앱(모바일/웹
> 멀티 클라이언트)은 GraphQL — over/under-fetching을 클라이언트 쿼리로
> 해소하되 캐싱·인가·N+1이라는 서버 복잡도를 대가로 치른다. 내부
> 서비스 간 고빈도 호출은 gRPC — Protobuf 바이너리 직렬화와 HTTP/2
> 멀티플렉싱으로 성능을 얻고, IDL(proto)이 강타입 계약이 된다.
> 그리고 실무는 셋 중 하나를 고르는 게 아니라 경계별로 혼용한다 —
> 바깥 경계는 REST/GraphQL, 내부 서비스 간은 gRPC.**

---

## 0. 질문 + 의도

**질문**: "REST vs GraphQL vs gRPC — 어떤 기준으로 선택하나요?"

**출제 의도**: 유행이 아니라 소비자 특성(외부 공개냐, 내부 서비스 간이냐,
클라이언트 주도 조회냐)으로 선택하는지 — 기술 선택의 축이 "누가
쓰는가"에 있음을 아는지 확인한다. 각 기술의 장점 나열이 아니라, "이
상황에서는 이것이 부적합하다"는 배제 논리를 갖고 있는지가 변별점이다.

## 1. 세 기술의 본질 — 무엇이 계약의 단위인가

셋은 "더 좋은 것"의 세대 교체 관계가 아니라, **계약을 맺는 방식이 다른
세 가지 스타일**이다.

| | REST | GraphQL | gRPC |
|---|---|---|---|
| 계약의 단위 | 리소스(URL) + HTTP 메서드 | 스키마(타입 그래프) + 쿼리 | proto 파일의 메서드 시그니처 |
| 응답 형태 결정권 | 서버 | **클라이언트**(쿼리로 지정) | 서버(proto에 고정) |
| 전송/직렬화 | HTTP + 주로 JSON | HTTP(주로 POST 단일 엔드포인트) + JSON | HTTP/2 + Protobuf(바이너리) |
| 대표 소비자 | 외부 공개·파트너·범용 | 다양한 화면의 자사 클라이언트 | 내부 마이크로서비스 |

비유하면 — REST는 **정식 메뉴판이 있는 식당**(누구나 메뉴판만 보면
주문 가능, 단 구성은 주방이 정한 대로), GraphQL은 **샐러드 바**(손님이
원하는 재료만 골라 담되, 주방은 어떤 조합이 와도 감당할 준비를 해야
한다), gRPC는 **주방 내부의 인터폰**(외부인은 못 쓰지만 주방끼리는
가장 빠르고 정확한 소통 수단).

## 2. 선택 기준 — 소비자가 누구인가

### ① 외부 공개·파트너 API → REST

불특정 다수가 소비하는 API의 최우선 가치는 성능이 아니라 **접근성과
예측 가능성**이다.

- 어떤 언어·환경에서든 HTTP 클라이언트만 있으면 호출 가능하다.
  curl 한 줄로 시연·디버깅이 되고, 파트너 온보딩 문서가 짧아진다.
- HTTP의 기존 인프라를 공짜로 얻는다 — CDN/브라우저/프록시의 **HTTP
  캐싱**(GET + Cache-Control + ETag), 표준 상태 코드 기반의 모니터링,
  로드밸런서의 L7 라우팅.
- 반대로 이 자리에 gRPC를 놓으면: 파트너마다 proto 파일 배포와 코드
  생성 도구 셋업을 요구하게 되고, 바이너리 프로토콜이라 중간 장비
  디버깅이 어렵다. 접근성이 가치인 자리에 성능 도구를 놓은 미스매치다.

### ② 화면이 다양한 자사 멀티 클라이언트 → GraphQL

REST의 고질 문제는 응답 형태의 결정권이 서버에 있다는 점에서 나온다.

```text
// Before: REST — 화면마다 다른 요구를 서버 응답 하나로 감당
GET /users/42
→ { id, name, email, address, grade, joinedAt, ... 30개 필드 }

문제 1 (over-fetching): 모바일 목록 화면은 name과 grade만 필요한데
        30개 필드를 다 받는다 — 모바일 네트워크에서 낭비.
문제 2 (under-fetching): 상세 화면은 유저+주문목록+쿠폰이 필요해서
        GET /users/42 → GET /users/42/orders → GET /users/42/coupons
        3번 왕복한다 — chatty API.
문제 3: 화면별 맞춤 응답을 만들다 보면
        /users/42?view=mobile-list 같은 변종 엔드포인트가 증식한다.
```

```graphql
# After: GraphQL — 클라이언트가 필요한 형태를 쿼리로 선언, 1회 왕복
query {
  user(id: 42) {
    name
    grade
    orders(last: 5) { id status }   # 연관 데이터까지 한 번에
    coupons { name expiresAt }
  }
}
```

**대가가 분명하다는 것까지 말해야 한다**: 단일 POST 엔드포인트라 HTTP
캐싱이 무력화되고, 쿼리 조합이 무한하므로 필드 단위 인가·쿼리 깊이
제한·비용 분석이 필요하며, 그래프 순회가 N+1 조회를 만들기 쉽다
(DataLoader로 배칭). 즉 **클라이언트의 유연성을 서버의 복잡도로 사서
오는 거래**다 — 화면이 몇 개 안 되고 요구가 안정적이라면 손해 보는
거래이며, 이때는 REST + 필요 시 BFF가 낫다.

### ③ 내부 마이크로서비스 간 통신 → gRPC

내부 서비스 간 호출은 소비자가 "우리가 통제하는 소수의 서버"다.
접근성보다 **성능과 계약의 엄격함**이 가치가 된다.

```protobuf
// proto 파일이 곧 계약 — 여기서 서버/클라이언트 코드를 생성한다
service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc WatchOrderEvents (WatchRequest) returns (stream OrderEvent); // 스트리밍
}
message GetOrderRequest { int64 order_id = 1; }   // 필드 번호 = 직렬화 키
```

- **Protobuf 바이너리 직렬화**: JSON 대비 페이로드가 작고
  파싱(직렬화/역직렬화) CPU 비용이 낮다 — 호출이 초당 수천 건씩 오가는
  내부 경로에서 누적 효과가 크다.
- **HTTP/2 기반**: 하나의 커넥션에서 다중 요청 동시 처리(멀티플렉싱),
  양방향 스트리밍 — 폴링 대신 서버 푸시형 내부 통신이 가능하다.
- **코드 생성 = 강타입 계약**: proto에서 각 언어의 클라이언트/서버
  스텁을 생성하므로, 필드 이름 오타나 타입 불일치가 런타임 JSON 파싱
  에러가 아니라 **컴파일 에러**로 잡힌다. 다언어(polyglot) 조직에서
  특히 유효하다.
- 한계: 브라우저가 gRPC를 직접 말하지 못하고(grpc-web 프록시 필요),
  바이너리라 사람이 읽을 수 없어 디버깅에 전용 도구가 필요하다 —
  그래서 외부 경계용이 아니라 내부용이다.

## 3. 실무의 결론 — 하나를 고르는 게 아니라 경계별로 혼용한다

전형적인 배치는 이렇다:

```text
[외부 파트너/공개]  --REST-->   ┌──────────────┐
[모바일/웹 앱]      --GraphQL/REST(BFF)--> │ 엣지(게이트웨이/BFF) │
                                └──────┬───────┘
                                       │ gRPC (내부 고빈도 호출)
                          ┌────────────┼────────────┐
                       주문 서비스   유저 서비스   결제 서비스
```

**바깥 경계는 접근성(REST) 또는 클라이언트 유연성(GraphQL), 안쪽은
성능과 강타입 계약(gRPC)** — 경계마다 소비자가 다르므로 프로토콜도
다르게 고르는 것이 자연스럽다.

반면 흔한 실패 사례 두 가지:

- **사내 어드민 CRUD에 GraphQL 도입** — 화면이 3개뿐이고 소비자가 자사
  프론트 하나인데, 캐싱 무력화·인가 복잡도·N+1 대응 비용만 떠안았다.
  "클라이언트 다양성"이라는 GraphQL의 전제가 없는 자리였다.
- **외부 파트너 연동 API를 gRPC로 공개** — 파트너사마다 proto 배포,
  코드 생성 환경, HTTP/2 지원 프록시 문제를 겪으며 온보딩이 몇 주씩
  걸렸다. 결국 REST 래퍼를 다시 만들었다 — 처음부터 소비자를 봤다면
  피할 수 있던 이중 비용이다.

## 4. 꼬리질문 대비 포인트

### "GraphQL의 N+1 문제는 왜 생기고 어떻게 해결하나요?"

GraphQL 서버는 쿼리의 각 필드를 리졸버 함수로 해석하는데, 목록 안의
연관 필드는 항목마다 리졸버가 호출된다. `users(10명) { orders }` 쿼리면
users 1회 + orders 10회 = 11회 조회가 나간다. 해결은 **DataLoader
패턴** — 같은 실행 틱 안의 개별 조회 요청을 모아서(배칭) `WHERE
user_id IN (...)` 한 방으로 바꾸고, 같은 키는 캐싱한다. "JPA의 N+1과
원리(개별 지연 조회의 반복)가 같고, 해법(배치 로딩)도 같다"고 연결하면
가산점 포인트.

### "gRPC는 왜 브라우저에서 직접 못 쓰나요?"

gRPC는 HTTP/2 프레임을 세밀하게 제어(트레일러 헤더 등)해야 하는데,
브라우저의 fetch/XHR API는 이를 노출하지 않는다. 그래서 브라우저용으로는
**grpc-web**이라는 변형 프로토콜 + 중간 프록시(Envoy 등)로 변환하는
구조를 쓴다. "이 프록시 계층이 추가된다는 것 자체가 gRPC를 외부
경계에 두지 않는 이유 중 하나"라고 묶어서 답하면 좋다.

### "GraphQL을 쓰면 HTTP 캐싱이 왜 무력화되나요? 대안은?"

REST의 HTTP 캐싱은 "GET + 고유 URL = 캐시 키"라는 전제 위에 있다.
GraphQL은 대개 단일 엔드포인트에 POST로 쿼리를 보내므로 URL이 캐시
키 역할을 못 하고, 중간 캐시(CDN/프록시)가 개입할 수 없다. 대안은
(1) persisted query — 쿼리를 서버에 등록하고 해시 ID로 GET 호출해
CDN 캐싱을 복원, (2) 클라이언트 측 정규화 캐시(Apollo 등의 타입+ID
기반 캐시), (3) 서버 내부의 데이터 소스 캐싱. "네트워크 계층 캐시를
잃고 애플리케이션 계층 캐시로 보상하는 구조"라고 정리하면 된다.

### "REST로도 필드 선택 파라미터나 BFF로 over-fetching을 풀 수 있는데, 그래도 GraphQL을 택하는 기준은?" (시니어 변별 포인트)

정확한 지적이고, 실제로 그 순서로 검토해야 한다. `?fields=name,grade`
같은 부분 응답 파라미터나 화면 전용 BFF 엔드포인트로 충분하면 REST에
머무는 것이 총비용이 낮다. GraphQL이 이기는 지점은 **조합의 수가
서버가 감당 못 할 만큼 늘어날 때**다 — 클라이언트 종류 × 화면 수 ×
필요 필드 조합이 폭발해서, BFF 엔드포인트 추가/수정 요청이 백엔드
팀의 병목이 되는 상황. 이때 GraphQL은 "조합 생산"을 클라이언트 팀에
넘겨 조직 간 대기 비용을 없앤다. 즉 기술 선택처럼 보이지만 실은
**팀 간 의존 구조를 바꾸는 결정**이며, 그 필요가 없다면 도입하지
않는다 — 이렇게 조직 관점까지 답하면 시니어 변별이 된다.

### "gRPC(proto) 계약은 어떻게 하위 호환을 지키며 바꾸나요?"

Protobuf는 필드를 이름이 아니라 **필드 번호**로 직렬화한다. 그래서
(1) 기존 필드의 번호·타입 변경 금지, (2) 필드 삭제 시 번호를
`reserved`로 묶어 재사용 방지, (3) 추가는 새 번호로 — 모르는 필드는
구버전이 무시하므로 안전하다. "REST의 '필드 추가는 안전, 삭제·의미
변경은 위험'이라는 원칙이 proto에서는 필드 번호 규율로 강제된다"고
비교하면 계약 관리의 일관된 시각을 보여줄 수 있다.

## 한 줄 요약

REST/GraphQL/gRPC는 우열이 아니라 소비자가 다른 계약 스타일이다 —
**불특정 외부에는 접근성의 REST, 화면 조합이 폭발하는 자사 멀티
클라이언트에는 클라이언트 주도 조회의 GraphQL(서버 복잡도를 대가로),
내부 고빈도 서비스 간에는 성능·강타입 계약의 gRPC** — 그리고 실무는
경계별로 혼용하되, 각 기술의 전제(소비자 특성)가 없는 자리에 유행으로
들여오는 것이 가장 흔한 실패다.
