# REST vs GraphQL vs gRPC — 기술이 아니라 "누가 쓰는가"로 고른다

> 핵심 관전 포인트: **셋은 세대 교체 관계가 아니라 계약을 어디에 적어 두느냐가 다른 세 스타일이다 — REST는 URL과 HTTP 메서드에, GraphQL은 타입 스키마에, gRPC는 IDL(Interface Definition Language, 특정 언어에 속하지 않는 중립 문법으로 "어떤 메서드가 있고 무엇을 주고받는가"를 적어 둔 파일) 한 장에 적는다. 그래서 선택 축은 유행이 아니라 **그 계약을 읽고 코드를 짜는 사람이 누구인가**다. 불특정 다수·외부 파트너가 쓰는 공개 API는 REST — HTTP 생태계(캐시, 브라우저, curl, 상태 코드 기반 모니터링)를 그대로 물려받고 온보딩 비용이 가장 낮다. 화면이 다양하고 클라이언트가 조회 형태를 주도해야 하는 자사 멀티 클라이언트는 GraphQL — 응답 형태의 결정권이 서버에 있다는 REST의 전제에서 나오는 두 증상, 즉 **over-fetching**(화면이 안 쓰는 필드까지 통째로 받는 과다 인출)과 **under-fetching**(한 번 받아도 모자라 또 부르는 과소 인출, 곧 07번의 chatty/N+1을 클라이언트 관점에서 부른 이름)을 클라이언트 쿼리로 한꺼번에 없애되, HTTP 캐싱 무력화·필드 단위 인가·리졸버 N+1이라는 서버 복잡도를 대가로 치른다. 내부 서비스 간 고빈도 호출은 gRPC — 필드를 이름이 아니라 **번호**로 직렬화하는 Protobuf 바이너리와 HTTP/2 멀티플렉싱으로 성능을 얻고, proto 파일 하나에서 여러 언어의 스텁을 생성하기 때문에 그 파일이 컴파일러가 강제하는 계약이 된다. 대신 최종 상태 코드를 본문 뒤에 오는 **트레일러 헤더**에 싣기 때문에 브라우저 fetch/XHR로는 읽을 수 없어 외부 경계에 놓을 수 없다. 그래서 실무의 결론은 셋 중 하나를 고르는 것이 아니라 경계별 혼용이다 — 바깥은 REST/GraphQL, 안쪽은 gRPC. 각 기술의 전제(소비자 특성)가 없는 자리에 유행으로 들여오는 것이 가장 흔한 실패다.**

## 0. 질문 + 의도

**질문**: "REST vs GraphQL vs gRPC — 어떤 기준으로 선택하나요?"

**출제 의도**: 유행이 아니라 소비자 특성(외부 공개냐, 내부 서비스 간이냐, 클라이언트 주도 조회냐)으로 선택하는지 — 기술 선택의 축이 "누가 쓰는가"에 있음을 아는지 확인한다. 각 기술의 장점 나열이 아니라, "이 상황에서는 이것이 부적합하다"는 배제 논리를 갖고 있는지가 변별점이다.

> RTT·멀티플렉싱·BFF·N+1의 정의와 왕복 비용 계산은 `07-chatty-api-call-explosion.md`, REST의 자원·표현·메서드 시맨틱은 `01-restful-design-principles-resource-naming.md`, 계약의 하위 호환 규율은 `03-api-versioning-strategies.md`와 `08-backward-compatible-api-changes.md`에서 다룬다. 이 문서는 그 위에서 **세 기술의 계약 단위가 어떻게 다르고, 그 차이가 어떤 소비자에게 값을 내는가**를 본다.

## 1. 세 기술이 각각 무엇인가 — 계약을 어디에 적어 두는가

### 1-1. 전제 지식 — "API 계약"이 무엇이고 왜 이것이 비교의 축인가

비교를 시작하기 전에 축을 하나 세우자. **API 계약(contract)은 "무엇을 어떤 형태로 주고받기로 한다"는 서버와 클라이언트 사이의 약속**이다. 어떤 요청을 보낼 수 있는지, 그 요청에 무엇을 실어야 하는지, 응답에 어떤 필드가 어떤 타입으로 들어 있는지가 계약의 내용이다.

계약이 왜 중요한가. **서버와 클라이언트는 서로 다른 사람이, 서로 다른 언어로, 서로 다른 시점에 만들기 때문**이다. 안드로이드 앱 개발자는 우리 서버 코드를 읽지 않는다. 그 사람이 참조하는 것은 오직 계약뿐이고, 계약이 애매하면 그 애매함이 그대로 버그가 된다.

그래서 세 기술을 가르는 진짜 질문은 "무엇이 더 빠른가"가 아니라 이것이다. **그 계약이 어디에 적혀 있고, 누가 그것을 강제하는가?**

세 기술의 답이 각각 다르다.

- REST: 계약이 **URL과 HTTP 메서드**에 적혀 있고, 강제하는 것은 **사람이 쓴 문서와 관례**다.
- GraphQL: 계약이 **타입 스키마 파일**에 적혀 있고, 강제하는 것은 **GraphQL 서버의 쿼리 검증기**다.
- gRPC: 계약이 **IDL(proto) 파일**에 적혀 있고, 강제하는 것은 **각 언어의 컴파일러**다.

이 세 줄이 이 문서 전체의 뼈대다. 아래에서 하나씩 실물을 보자.

### 1-2. REST — 계약은 URL과 메서드에 있다

REST에서 "무엇을 할 수 있는가"는 **URL 목록**으로 표현되고, "그것에 무엇을 하는가"는 **HTTP 메서드**로 표현된다. `GET /orders/42`라는 한 줄이 곧 "42번 주문의 표현을 달라"는 요청 전체다. (자원·표현·메서드 시맨틱의 정의는 `01-restful-design-principles-resource-naming.md` 1-1~1-3에 있다.)

실물을 보자. 요청은 이렇게 생겼다.

```http
GET /orders/42 HTTP/1.1
Host: api.example.com
Accept: application/json
```

응답은 이렇게 온다.

```json
{
  "id": 42,
  "status": "SHIPPED",
  "totalAmount": 45000,
  "userId": 7,
  "shippingAddress": "서울시 ...",
  "createdAt": "2026-08-30T12:34:56Z",
  "updatedAt": "2026-08-31T09:00:00Z"
}
```

여기서 눈여겨볼 것은 **클라이언트가 응답의 모양에 아무 말도 하지 않았다는 점**이다. 요청에는 "42번 주문을 달라"만 있고, 그 주문을 몇 개의 필드로 어떻게 그려서 줄지는 전부 서버가 정했다. 이 사실이 2-3에서 GraphQL이 등장하는 이유가 된다.

**계약을 강제하는 주체가 없다는 것도 짚어야 한다.** 서버가 어느 날 `totalAmount`를 문자열로 바꿔 내려보내도 HTTP는 막지 않는다. 클라이언트는 배포된 앱 안에서 파싱 에러로 죽고 나서야 안다. 그래서 REST 진영은 OpenAPI 스펙, 스펙 diff 검사, 계약 테스트 같은 **별도의 장치를 덧대어** 계약을 강제한다. 이것이 뒤에 나올 gRPC의 "컴파일 에러로 잡힌다"와 대비되는 지점이다.

### 1-3. GraphQL — 계약은 스키마에 있고, 요청은 쿼리다

**GraphQL은 서버가 가진 데이터 전체를 하나의 타입 그래프로 정의해 두고, 클라이언트가 그 그래프에서 필요한 부분만 골라 오려내는 질의 언어**다. 이름 그대로 "그래프에 대한 질의 언어(Graph Query Language)"다.

계약은 **스키마(schema)** 라는 파일에 적힌다. 스키마는 "우리 서비스에 어떤 타입이 있고, 각 타입에 어떤 필드가 어떤 타입으로 붙어 있으며, 타입끼리 어떻게 연결되는가"를 선언한 문서다.

```graphql
# 스키마 — 이 파일이 계약이다. 클라이언트가 물어볼 수 있는 것의 전부가 여기 있다.
type Order {
  id: ID!
  status: OrderStatus!
  totalAmount: Int!
  user: User!              # 주문 -> 주문자로 이어지는 간선
  items: [OrderItem!]!     # 주문 -> 주문 항목들로 이어지는 간선
}

type User {
  id: ID!
  name: String!
  grade: String!
  email: String!
}

# Query 타입은 "그래프에 들어가는 입구" 목록이다.
type Query {
  order(id: ID!): Order
}
```

`!`는 "null이 될 수 없다"는 표시다. 이 한 글자가 계약의 일부라는 점이 중요하다 — REST에서는 "이 필드가 null일 수 있는가"가 대개 문서의 산문으로만 존재하는데, GraphQL에서는 타입 시스템이 그것을 들고 있다.

이제 클라이언트가 보내는 요청이다. **요청 본문에 응답의 모양이 그대로 적혀 있다.**

```graphql
query {
  order(id: 42) {
    status
    totalAmount
    user { name }
  }
}
```

응답은 이렇게 온다.

```json
{
  "data": {
    "order": {
      "status": "SHIPPED",
      "totalAmount": 45000,
      "user": { "name": "김철수" }
    }
  }
}
```

**요청과 응답을 나란히 놓고 보면 모양이 키 하나까지 정확히 대응한다.** 요청에 `status`, `totalAmount`, `user { name }`을 적었으니 응답에도 딱 그 셋만, 그 중첩 구조 그대로 온다. 1-2의 REST 응답이 서버가 정한 7개 필드였던 것과 정확히 반대다. **응답 형태의 결정권이 서버에서 클라이언트로 넘어간 것**이 GraphQL의 한 문장 요약이다.

#### 리졸버 — 이 응답을 서버가 어떻게 만드는가

여기서 반드시 짚고 가야 할 개념이 하나 있다. **리졸버(resolver)는 GraphQL 서버가 쿼리에 등장하는 필드 하나하나마다 호출하는 함수다.** "해결한다(resolve)", 즉 "이 필드의 값이 무엇인지 알아낸다"는 뜻에서 온 이름이다.

REST 컨트롤러는 엔드포인트 하나에 함수 하나가 붙지만, GraphQL은 **필드 단위**로 함수가 붙는다. 위 쿼리 하나를 처리하면서 서버는 이런 순서로 함수를 부른다.

```
query { order(id: 42) { status totalAmount user { name } } }

  ① Query.order 리졸버       -> 주문 42를 가져온다
       ↓ 그 결과를 부모로 삼아
  ② Order.status 리졸버      -> 부모 객체에서 필드를 꺼낸다 (기본 리졸버)
  ③ Order.totalAmount 리졸버 -> 부모 객체에서 필드를 꺼낸다 (기본 리졸버)
  ④ Order.user 리졸버        -> 주문의 userId로 유저를 "따로" 조회한다  <- 여기가 위험 지점
       ↓ 그 결과를 부모로 삼아
  ⑤ User.name 리졸버         -> 부모 객체에서 필드를 꺼낸다 (기본 리졸버)
```

②③⑤처럼 부모 객체에 이미 들어 있는 값을 꺼내기만 하는 리졸버는 공짜다. 문제는 ④다. **연관 타입을 잇는 간선에는 대개 별도 조회가 붙는다.**

그리고 이 구조 위에서 목록을 조회하면 무슨 일이 생기는지가 바로 N+1이다.

```
query { orders(last: 20) { id user { name } } }

  Query.orders 리졸버       -> 주문 20건을 한 번에 조회   ... 쿼리  1회
  Order.user 리졸버 (20번)  -> 주문마다 유저 1건씩 조회   ... 쿼리 20회
                                                              ─────────
                                                              합계 21회
```

**리졸버가 "필드마다" 호출된다는 성질이, 목록 안의 연관 필드에서는 "항목마다"로 번역되기 때문**이다. 이것이 07번에서 정의한 N+1(목록 1회 + 항목마다 N회 = N+1회)과 정확히 같은 산수이고, 위치만 클라이언트↔서버에서 GraphQL 서버↔DB로 옮겨온 것이다. 대응책은 4장에서 다룬다.

### 1-4. gRPC — 계약은 IDL 파일 하나에 있다

**gRPC는 "원격 프로시저 호출(RPC, Remote Procedure Call)" 방식의 통신 프레임워크다.** RPC란 네트워크 너머의 함수를 마치 내 코드 안의 함수처럼 부르는 방식을 말한다. REST가 "자원에 무엇을 한다"는 문법이라면, RPC는 "함수를 부른다"는 문법이다.

#### IDL이 무엇인가

계약은 **IDL 파일**에 적힌다. **IDL은 Interface Definition Language, 즉 "인터페이스 정의 언어"다. 특정 프로그래밍 언어에 속하지 않는 중립적인 문법으로 "이 서비스에 어떤 메서드가 있고, 각 메서드가 무엇을 받아 무엇을 돌려주는가"를 적어 둔 파일**을 말한다.

왜 굳이 중립 문법이 필요한가. **한 파일에서 여러 언어의 코드를 생성해야 하기 때문**이다. 계약을 Java 인터페이스로 적어 두면 Go 서비스는 그것을 읽을 수 없다. 어느 언어에도 속하지 않는 문법으로 적어 두면, 거기서 Java 스텁도 Go 스텁도 Kotlin 스텁도 생성할 수 있다.

그리고 이 "생성"이 계약을 강제하는 힘의 정체다. **양쪽 코드가 같은 파일에서 기계적으로 생성됐으므로, 계약과 구현이 어긋나면 코드가 아예 컴파일되지 않는다.** REST에서는 문서와 구현이 따로 놀 수 있지만, 여기서는 원리적으로 불가능하다.

gRPC가 쓰는 IDL은 **Protocol Buffers(줄여서 Protobuf)** 문법이고, 확장자가 `.proto`라 흔히 "proto 파일"이라고 부른다.

```protobuf
syntax = "proto3";

service OrderService {
  // 단발 요청 -> 단발 응답
  rpc GetOrder (GetOrderRequest) returns (Order);
  // 요청 1회 -> 응답이 스트림으로 계속 흘러나온다 (서버 스트리밍)
  rpc WatchOrderEvents (WatchRequest) returns (stream OrderEvent);
}

message GetOrderRequest {
  int64 order_id = 1;   // 이 "= 1"은 기본값이 아니라 필드 번호다
}

message Order {
  int64 id = 1;
  string status = 2;
  int64 total_amount = 3;
}
```

#### `= 1`은 기본값이 아니라 필드 번호다

여기서 처음 보는 사람이 거의 반드시 오해하는 지점이 있다. **`int64 order_id = 1;`의 `= 1`은 "기본값이 1"이라는 뜻이 아니라 "이 필드의 번호는 1번"이라는 선언이다.**

왜 번호를 붙이는가. **Protobuf가 필드를 이름이 아니라 번호로 직렬화하기 때문**이다. JSON은 바이트 안에 키 이름을 그대로 넣는다.

```
JSON:      {"order_id":42}     -> 15바이트, 사람이 읽을 수 있다
Protobuf:  08 2A               -> 2바이트, 사람이 읽을 수 없다
           ┬  ┬
           │  └── 값 42 (16진수 0x2A)
           └───── "1번 필드이고 정수형"을 뜻하는 태그 바이트
```

바이트 안에 `order_id`라는 문자열이 아예 존재하지 않는다는 점을 보라. 수신 측은 "1번 필드"라는 번호를 자기가 들고 있는 proto 정의와 대조해 그것이 `order_id`임을 알아낸다.

여기서 gRPC의 성질 두 개가 한꺼번에 설명된다.

- **작고 빠르다.** 키 이름을 매 요청 반복해 보내지 않고, 숫자와 타입을 압축된 이진 형식으로 싣는다. 초당 수천 건이 오가는 내부 경로에서 이 차이는 누적된다.
- **사람이 읽을 수 없다.** 패킷을 떠서 봐도 `08 2A`일 뿐이다. proto 정의를 손에 들고 디코딩해야 의미가 생긴다. 그래서 중간 장비에서의 육안 디버깅이 불가능하고, `grpcurl` 같은 전용 도구가 필요하다.

이 필드 번호는 나중에 계약을 바꿀 때 지켜야 할 규율의 근거가 되는데, 그 규칙은 4장에서 다룬다.

#### 생성된 스텁을 호출하는 쪽은 이렇게 생겼다

proto 파일을 컴파일하면 각 언어의 **스텁(stub)** 이 생성된다. 스텁은 "그루터기"라는 뜻으로, **실제 구현은 원격에 있고 내 프로세스 안에는 그 자리를 대신하는 껍데기만 있다**는 의미에서 붙은 이름이다.

```java
// 아래 클래스들은 우리가 짠 것이 아니라 proto 파일에서 생성된 것이다.
OrderServiceGrpc.OrderServiceBlockingStub stub =
        OrderServiceGrpc.newBlockingStub(channel);

GetOrderRequest request = GetOrderRequest.newBuilder()
        .setOrderId(42)          // 필드명 오타는 컴파일 단계에서 걸린다
        .build();

Order order = stub.getOrder(request);   // 네트워크 호출인데 함수 호출처럼 보인다
long total = order.getTotalAmount();    // 반환 타입도 컴파일러가 알고 있다
```

REST 클라이언트라면 `response.get("totalAmount")`가 문자열인지 숫자인지 런타임에 가 봐야 알지만, 여기서는 `getTotalAmount()`가 `long`을 돌려준다는 것이 컴파일 시점에 확정돼 있다. **필드 이름 오타나 타입 불일치가 런타임 JSON 파싱 에러가 아니라 컴파일 에러로 잡힌다**는 말의 실체가 이것이다.

### 1-5. 세 계약을 겹쳐 보기

| | REST | GraphQL | gRPC |
|---|---|---|---|
| 계약이 적힌 곳 | URL 목록 + HTTP 메서드 (문서는 별도) | 타입 스키마 파일 | IDL(proto) 파일 |
| 계약을 강제하는 주체 | 없음 (문서·관례·별도 계약 테스트) | GraphQL 서버의 쿼리 검증기 | 각 언어의 컴파일러 |
| 응답 형태 결정권 | 서버 | **클라이언트**(쿼리로 지정) | 서버(proto에 고정) |
| 전송·직렬화 | HTTP + 주로 JSON(텍스트) | HTTP(주로 단일 엔드포인트에 POST) + JSON | HTTP/2 + Protobuf(바이너리) |
| 눈으로 읽을 수 있나 | 가능 | 가능 | 불가 (전용 도구 필요) |
| 브라우저에서 직접 호출 | 가능 | 가능 | 불가 (프록시 필요, 2-6) |
| 대표 소비자 | 외부 공개·파트너·범용 | 화면이 다양한 자사 클라이언트 | 내부 마이크로서비스 |

비유로 잡아두면 오래 남는다. REST는 **정식 메뉴판이 있는 식당**이다 — 누구나 메뉴판만 보면 주문할 수 있지만 구성은 주방이 정한 대로 나온다. GraphQL은 **샐러드 바**다 — 손님이 원하는 재료만 골라 담되, 주방은 어떤 조합이 와도 감당할 준비를 해 둬야 한다. gRPC는 **주방 내부의 인터폰**이다 — 외부인은 쓸 수 없지만 주방끼리는 가장 빠르고 정확한 소통 수단이다.

## 2. 선택 기준 — 소비자가 누구인가

### 2-1. 판단의 축 세 개

세 기술 중 하나를 고르는 일은 사실상 아래 세 질문에 답하는 일이다. 답이 정해지면 기술은 따라 나온다.

| 질문 | 답이 갈리는 지점 |
|---|---|
| ① 소비자를 우리가 통제할 수 있는가 | 통제 불가(파트너·불특정 다수)면 접근성이 최우선 가치가 된다 |
| ② 응답 형태를 누가 정해야 하는가 | 화면 조합이 폭발하면 결정권을 클라이언트로 넘기는 값이 커진다 |
| ③ 왕복 1회의 단가가 얼마인가 | 데이터센터 내부(1ms 미만)냐 모바일 셀룰러망(30~300ms)이냐 |

③의 수치는 07번 1-4의 RTT 표와 같은 기준이다. **RTT(round-trip time, 왕복 시간)는 요청이 상대에게 갔다가 응답이 돌아오기까지의 시간**이고, 물리적 거리와 중간 장비 수가 정하므로 서버를 좋은 것으로 바꿔도 줄지 않는다는 것이 그 문서의 결론이었다.

세 축을 이렇게 읽으면 된다. **①이 "통제 불가"면 REST로 거의 결정되고, ①이 "통제 가능"일 때에만 ②와 ③이 GraphQL과 gRPC를 가른다.** ②가 문제면 GraphQL, ③이 문제면 gRPC다.

### 2-2. ① 외부 공개·파트너 API → REST

불특정 다수가 소비하는 API의 최우선 가치는 성능이 아니라 **접근성과 예측 가능성**이다. 이유는 단순하다 — 우리가 파트너사 개발자의 언어·프레임워크·빌드 환경을 고를 수 없기 때문이다.

REST가 이 자리에서 이기는 근거는 셋이다.

**(1) 진입 비용이 사실상 0이다.** HTTP 클라이언트가 없는 언어·환경은 없다. `curl` 한 줄로 시연과 디버깅이 되고, 파트너 온보딩 문서가 "이 URL로 GET 하세요"에서 끝난다. 문제가 생겼을 때 상대 개발자가 자기 손으로 재현해 볼 수 있다는 것이 실무에서 생각보다 큰 값이다.

**(2) HTTP 생태계를 공짜로 물려받는다.** CDN·브라우저·프록시의 **HTTP 캐싱**이 그대로 붙는다. 이것이 가능한 이유는 REST의 조회가 `GET + 고유 URL` 형태이고, HTTP 캐시의 기본 키가 정확히 그 "메서드 + URL"이기 때문이다. 여기에 표준 상태 코드 기반 모니터링과 알람, 로드밸런서의 L7 경로 라우팅이 따라온다. 우리가 아무것도 만들지 않아도 이미 존재하는 인프라가 우리 API를 이해한다.

**(3) 계약이 오래 산다.** 공개 API는 한번 내면 몇 년을 유지해야 하는데, HTTP 시맨틱은 20년 넘게 안정적이었다. 특정 프레임워크 버전에 묶이지 않는다는 뜻이다.

반대로 **이 자리에 gRPC를 놓으면 무엇이 무너지는지**까지 말할 수 있어야 배제 논리가 된다. 파트너마다 proto 파일 배포와 코드 생성 도구 셋업을 요구하게 되고, 바이너리라 상대가 자기 쪽 문제인지 우리 쪽 문제인지 눈으로 확인할 수 없으며, 중간 프록시가 HTTP/2와 트레일러를 온전히 지원하는지까지 파트너사 인프라 사정에 걸린다. **접근성이 가치인 자리에 성능 도구를 놓은 미스매치**다.

### 2-3. 전제 지식 — over-fetching과 under-fetching은 한 원인의 두 얼굴

GraphQL을 말하려면 그것이 무엇을 푸는지부터 정확히 세워야 한다. 두 용어를 정의하자.

**over-fetching(과다 인출)은 화면이 실제로 쓰지 않는 필드까지 응답에 통째로 실려 오는 것**이다. 목록 화면이 이름과 등급만 그리는데 응답에는 이메일·주소·가입일까지 30개 필드가 들어 있다면, 나머지 28개는 네트워크와 파싱 비용만 쓰고 버려진다.

**under-fetching(과소 인출)은 한 번 받아서는 화면을 못 그려서 또 호출해야 하는 것**이다. 상세 화면이 주문 + 주문자 + 상품 정보를 필요로 하는데 API가 주문만 주면, 클라이언트는 나머지를 얻으려고 왕복을 두 번 더 낸다.

**이름은 반대말처럼 보이지만 원인은 하나다.** 둘 다 **응답의 형태를 서버가 미리 정해 뒀다는 사실**에서 나온다. 서버가 고정한 한 벌의 응답이 어떤 화면에는 넘치고(over) 어떤 화면에는 모자란(under) 것뿐이다. 이 한 문장이 GraphQL 절 전체의 전제다 — GraphQL이 하는 일은 두 문제를 각각 푸는 것이 아니라, **원인 하나를 없애서 두 증상을 동시에 없애는 것**이다.

그리고 **under-fetching은 07번의 chatty API·N+1과 같은 현상을 클라이언트 관점에서 부른 이름**이다. 07번은 "화면 하나에 왕복이 몇 번 드는가"라는 서버·네트워크 쪽 시선으로 이 현상을 다뤘고, 여기서는 "한 번 받은 것으로 화면을 못 그린다"는 클라이언트 쪽 시선으로 부른다. 진단명이 둘일 뿐 병은 하나다.

```text
[원인] 응답 형태의 결정권이 서버에 있다
           │
           ├──> 서버가 정한 응답이 이 화면에는 넘친다  -> over-fetching  (낭비)
           │
           └──> 서버가 정한 응답이 이 화면에는 모자란다 -> under-fetching (추가 왕복)
                                                          = 07번의 chatty / N+1
```

### 2-4. ② 화면이 다양한 자사 멀티 클라이언트 → GraphQL

이제 문제를 코드로 보자. 사용자 정보를 쓰는 화면이 둘이라고 하자.

```text
// Before: REST — 서버가 정한 한 벌의 응답으로 서로 다른 화면을 감당한다
GET /users/42
-> { id, name, email, address, grade, joinedAt, ... 30개 필드 }

증상 1 (over-fetching): 모바일 목록 화면은 name과 grade만 그리는데
        30개 필드를 다 받는다. 셀룰러망에서 전송량과 파싱이 낭비된다.

증상 2 (under-fetching): 상세 화면은 유저 + 주문목록 + 쿠폰이 필요해서
        GET /users/42 -> GET /users/42/orders -> GET /users/42/coupons
        3번 왕복한다. RTT 100ms면 이것만 300ms다.

증상 3 (변종 엔드포인트 증식): 화면별 맞춤 응답을 만들다 보면
        /users/42?view=mobile-list 같은 것이 하나씩 늘어난다.
        화면이 늘 때마다 백엔드 팀에 요청이 쌓인다.
```

```graphql
# After: GraphQL — 클라이언트가 필요한 형태를 쿼리로 선언한다. 왕복 1회.
query {
  user(id: 42) {
    name
    grade
    orders(last: 5) { id status }     # 연관 데이터까지 같은 왕복에
    coupons { name expiresAt }
  }
}
```

목록 화면은 `{ name grade }`만 적어 보내고, 상세 화면은 위처럼 적어 보낸다. **서버 코드를 한 줄도 바꾸지 않고 두 화면이 각자 원하는 응답을 받는다.** 2-3에서 세운 원인(응답 형태의 결정권)이 사라졌으므로 두 증상이 함께 사라졌고, 증상 3의 변종 엔드포인트도 만들 이유가 없어졌다.

**대가가 분명하다는 것까지 말해야 답이 완성된다.** 넷을 나눠 보자.

**(1) HTTP 캐싱이 무력화된다.** 2-2에서 봤듯 HTTP 캐시의 키는 "메서드 + URL"인데, GraphQL은 대개 `/graphql` 하나에 POST로 쿼리를 보낸다. URL이 항상 같고 메서드가 POST이므로 중간 캐시(CDN·프록시)가 개입할 근거 자체가 없다. **네트워크 계층 캐시를 잃고 애플리케이션 계층 캐시로 보상하는 구조**가 되며, 그 방법은 4장에서 다룬다.

**(2) 인가가 필드 단위로 내려간다.** REST는 "이 엔드포인트를 이 역할이 부를 수 있는가"만 판정하면 되지만, GraphQL은 클라이언트가 필드 조합을 자유롭게 만들므로 **"이 사용자가 이 필드를 볼 수 있는가"를 필드마다** 판정해야 한다. `user { email }`을 본인은 볼 수 있고 남은 볼 수 없다면, 그 판정이 리졸버 안에 들어가야 한다.

**(3) 쿼리 비용을 클라이언트가 정한다.** 깊이 제한과 복잡도 제한이 없으면 한 줄짜리 쿼리가 DB를 눕힐 수 있다. 그래서 쿼리 깊이 상한, 필드별 비용 점수 합산, 타임아웃 같은 방어를 서버가 갖춰야 한다.

**(4) N+1이 서버 안으로 들어온다.** 1-3에서 본 리졸버 구조 때문이다. DataLoader 같은 배칭 계층이 사실상 필수이고, 이는 **문제를 없앤 것이 아니라 우리 쪽으로 옮긴 것**이다.

정리하면 GraphQL은 **클라이언트의 유연성을 서버의 복잡도로 사 오는 거래**다. 화면이 몇 개 안 되고 요구가 안정적이면 손해 보는 거래이며, 그때는 REST에 머물면서 07번의 처방(목록 DTO 확장, 벌크 조회, expand, BFF)으로 푸는 편이 총비용이 낮다.

### 2-5. 전제 지식 — HTTP/1.1의 제약과 멀티플렉싱

gRPC의 장점을 말하려면 그 앞에 HTTP/1.1이 무엇을 못 했는지가 있어야 한다. 07번 1-5와 같은 계산이므로 문구를 맞춰 짚고 넘어간다.

**HTTP/1.1에는 한 커넥션에 요청 하나만 흘릴 수 있다는 제약이 있다.** 응답에 "이건 몇 번 요청의 답이다"라는 식별자가 없어서, 요청 순서와 응답 순서가 같아야만 짝이 맞기 때문이다. 그래서 앞선 요청이 끝나야 다음 요청을 보낼 수 있고, 느린 응답 하나가 뒤에 선 요청 전부를 세운다. 줄의 맨 앞이 막으면 뒤가 전부 기다린다는 뜻에서 이것을 **HOL(head-of-line) blocking**이라고 부른다.

프로토콜이 병렬을 못 하니 브라우저는 병렬성을 **커넥션 개수**로 만들었다. 같은 호스트에 동시에 여는 커넥션을 **보통 6개로 제한**하는데, 무한정 늘리면 서버 부담이 커지고 커넥션마다 TCP slow start를 따로 치러 이득이 줄기 때문이다.

**HTTP/2는 이 제약을 푼다.** 모든 조각에 길이와 스트림 ID를 붙이는 이진 프레이밍 덕분에 한 커넥션에 여러 요청을 뒤섞어 실어 보낼 수 있다. 이것이 **멀티플렉싱(multiplexing, 다중화) — 하나의 물리적 통로에 여러 논리적 통로를 겹쳐 보내는 기법**이다. 조각마다 "여기까지가 한 조각"이라는 경계와 "몇 번 요청의 것"이라는 라벨이 붙어 있으니 받는 쪽이 다시 조립할 수 있다.

```
HTTP/1.1                            HTTP/2
커넥션1: [요청A]---[응답A]          커넥션1: [A조각][C조각][A조각][B조각][C조각]...
커넥션2: [요청B]---[응답B]                   -> 조각마다 스트림 ID가 붙어 있어
커넥션3: [요청C]---[응답C]                      뒤섞어 보내도 조립된다
  ...최대 6개까지만                             커넥션 하나로 충분하다
```

(프로토콜별 상세는 `../08-network-http/09-http1-http2-http3-hol-blocking.md`에 있다.)

**gRPC는 HTTP/2를 요구한다.** 선택 사항이 아니라 전제다. 그리고 이 사실이 곧 gRPC의 장점(2-6)이자 한계(브라우저에서 못 쓰는 이유)의 뿌리가 된다.

### 2-6. ③ 내부 마이크로서비스 간 통신 → gRPC

내부 서비스 간 호출은 소비자가 **"우리가 배포하고 통제하는 소수의 서버"** 다. 2-1의 축 ①이 "통제 가능"이므로 접근성의 값이 급격히 떨어지고, 대신 축 ③(왕복 단가는 싸지만 횟수가 압도적으로 많다)과 계약의 엄격함이 전면에 나선다.

gRPC가 이 자리에서 내는 값은 넷이다.

**(1) Protobuf 바이너리 직렬화.** 1-4에서 본 대로 키 이름을 빼고 번호와 타입만 압축해 싣는다. 페이로드가 작고, 파싱(직렬화·역직렬화)에 드는 CPU가 낮다. 요청 하나로는 미미한 차이지만 초당 수천 건이 오가는 내부 경로에서는 누적된다. **줄어드는 것이 네트워크 시간만이 아니라 CPU 시간이기도 하다**는 점이 중요하다 — 데이터센터 내부에서는 어차피 RTT가 1ms 미만이라, 실제 이득의 상당 부분이 직렬화 비용 쪽에서 나온다.

**(2) HTTP/2 멀티플렉싱 위에서 커넥션 하나를 재사용한다.** 서비스 A가 서비스 B를 초당 3천 번 부를 때, 커넥션 하나에 요청을 겹쳐 보낼 수 있다는 것은 커넥션 풀 관리 부담과 handshake 비용이 사라진다는 뜻이다.

**(3) 양방향 스트리밍이 계약에 들어 있다.** `rpc WatchOrderEvents (WatchRequest) returns (stream OrderEvent)`처럼 **스트림이 IDL의 일급 문법**이다. REST에서 서버 푸시를 하려면 SSE나 WebSocket이라는 별개의 기술을 덧붙이고 그 계약을 따로 문서화해야 하지만, gRPC에서는 같은 proto 파일 안에 함께 적히고 같은 코드 생성기가 스텁을 만들어 준다.

**(4) 코드 생성이 곧 강타입 계약이다.** 1-4에서 본 그대로다. 다언어(polyglot) 조직에서 특히 값이 큰데, Java 팀과 Go 팀이 같은 proto를 보고 각자 생성하면 두 언어 사이의 필드명·타입 불일치가 원리적으로 생기지 않는다.

**한계 두 가지도 함께 말해야 한다.**

**브라우저가 gRPC를 직접 말하지 못한다.** 이 이유의 핵심에 **트레일러 헤더(trailer header)** 가 있다. 트레일러 헤더는 **응답 본문이 다 끝난 뒤에 오는 헤더**다. 보통의 헤더는 본문보다 앞에 오지만, "본문을 다 만들어 봐야 알 수 있는 정보"는 앞에 실을 수 없으므로 뒤에 붙일 자리를 마련해 둔 것이다.

**gRPC는 호출의 최종 상태 코드(`grpc-status`)를 바로 이 트레일러에 싣는다.** 스트리밍이 있는 프로토콜이라 당연한 설계다 — 응답을 10분간 흘려보내다 중간에 실패할 수도 있는데, 그 결과를 응답 맨 앞에 미리 적을 수는 없기 때문이다.

문제는 **브라우저의 `fetch`/`XHR` API가 트레일러를 노출하지 않는다**는 것이다. 자바스크립트 코드는 본문까지만 읽을 수 있고 그 뒤에 붙은 헤더에는 손이 닿지 않는다. 그래서 브라우저는 gRPC 호출이 성공했는지 실패했는지를 원리적으로 판정할 수 없다.

```
[일반 HTTP 응답]        상태줄 -> 헤더 -> 본문                         (끝)
                        └ 여기서 성공/실패가 이미 결정돼 있다

[gRPC 응답]             상태줄 -> 헤더 -> 본문(메시지들) -> 트레일러
                                                            └ grpc-status: 0
                                                              여기에 최종 결과가 있다
                                                              브라우저 fetch는 이 줄을 못 읽는다
```

해결책이 **grpc-web**이라는 변형 프로토콜이다. 중간 프록시(Envoy 등)가 gRPC 응답을 받아 **트레일러를 본문 끝에 데이터로 밀어 넣어** 브라우저가 본문만 읽고도 상태를 알 수 있게 바꿔 준다. 즉 브라우저에서 gRPC를 쓰려면 **프록시 계층 하나가 반드시 추가된다.** 그리고 이 사실 자체가 "gRPC를 외부 경계에 두지 않는" 이유 중 하나다.

**디버깅에 전용 도구가 필요하다.** 1-4에서 본 대로 바이너리라 패킷을 떠도 읽히지 않는다. 내부에서는 `grpcurl`과 서버 리플렉션으로 감당할 수 있지만, 통제 밖의 소비자에게 이 부담을 지울 수는 없다.

### 2-7. 배제 논리 — "이 자리에 이건 아니다"

면접에서 변별이 되는 것은 장점 나열이 아니라 배제 논리다. 축 ①(소비자 통제 가능 여부)을 기준으로 정리하면 이렇게 된다.

| 자리 | 고르는 것 | 배제되는 것과 그 이유 |
|---|---|---|
| 외부 파트너·공개 API | REST | gRPC 배제 — 파트너에게 proto 배포·코드 생성·HTTP/2 프록시를 요구하게 된다. GraphQL도 대체로 배제 — 소비자마다 쿼리 비용이 제각각이라 우리가 통제할 수 없는 부하가 들어온다 |
| 자사 멀티 클라이언트, 화면 조합 폭발 | GraphQL | REST 단독 배제 — 화면이 늘 때마다 엔드포인트 추가 요청이 백엔드 팀에 쌓여 조직 병목이 된다 |
| 자사 클라이언트지만 화면이 몇 개, 요구 안정적 | REST(+ 07번 처방) | GraphQL 배제 — 캐싱·인가·N+1 비용만 떠안고 유연성은 쓰이지 않는다 |
| 내부 서비스 간 고빈도 호출 | gRPC | REST 배제라기보다 우선순위 — 접근성 값이 0에 가깝고 직렬화·계약 엄격함의 값이 크다 |
| 브라우저가 직접 부르는 경로 | REST 또는 GraphQL | gRPC 배제 — 트레일러를 읽을 수 없어 프록시 없이는 성립하지 않는다(2-6) |

## 3. 실무의 결론 — 하나를 고르는 게 아니라 경계별로 혼용한다

### 3-1. 전형적인 배치 — 경계마다 소비자가 다르다

```text
경계 ①  [외부 파트너 · 공개 API]
        소비자 : 우리가 통제할 수 없는 사람들 (파트너사 개발자, 외부 서드파티)
        고른 것 : REST (JSON) — 접근성과 HTTP 생태계를 사는 값
              │
              │
경계 ②  [모바일 앱 · 웹 프런트]
        소비자 : 우리 팀이 만든 클라이언트. 화면 조합이 제각각이다
        고른 것 : GraphQL, 또는 REST + BFF — 클라이언트 주도 조회를 사는 값
              │
              ▼
        [엣지 계층 — 게이트웨이 / BFF]
        인증 · 레이트리밋 · 화면 단위 조합
              │
경계 ③        │  소비자 : 우리가 배포하고 통제하는 서버들
              │  고른 것 : gRPC — 직렬화 비용 절감과 강타입 계약을 사는 값
              ▼
        [주문 서비스]      [유저 서비스]      [결제 서비스]
```

그림에서 읽어야 할 것은 프로토콜 이름이 아니라 **왼쪽에 붙은 소비자 라벨**이다. 같은 데이터를 다루는 같은 회사의 시스템인데도 계층마다 프로토콜이 다른 이유는, **계층마다 그 계약을 읽는 사람이 다르기 때문**이다. 통제할 수 없는 사람에게는 접근성을, 우리 팀의 앱에는 유연성을, 우리가 배포하는 서버 사이에는 성능과 엄격함을 준다.

한 문장으로 정리하면 이렇다. **바깥 경계는 접근성(REST) 또는 클라이언트 유연성(GraphQL), 안쪽은 성능과 강타입 계약(gRPC).**

### 3-2. 흔한 실패 두 가지

**(1) 사내 어드민 CRUD에 GraphQL 도입.** 화면이 3개뿐이고 소비자가 자사 프론트엔드 하나인데 GraphQL을 얹었다. 결과는 2-4에서 나열한 대가만 고스란히 떠안는 것이었다 — HTTP 캐싱 무력화, 필드 단위 인가, 쿼리 비용 제한, DataLoader 배칭. 그런데 정작 얻어야 할 이득인 "클라이언트가 조합을 스스로 만든다"는 쓰이지 않았다. 화면이 3개면 조합도 3개이고, 그 3개는 REST 엔드포인트 3개로 충분했다. **"클라이언트 다양성"이라는 GraphQL의 전제가 없는 자리**였다.

**(2) 외부 파트너 연동 API를 gRPC로 공개.** 파트너사마다 proto 배포, 코드 생성 환경 구성, HTTP/2를 온전히 지원하는 프록시 확인을 거치느라 온보딩이 몇 주씩 걸렸다. 장애가 나면 "우리 쪽 문제인지 확인해 달라"는 요청이 오갔는데, 파트너가 자기 손으로 요청을 떠서 볼 수 없으니 확인이 항상 우리를 거쳐야 했다. 결국 REST 래퍼를 다시 만들었다. **처음부터 소비자를 봤다면 피할 수 있던 이중 비용**이다.

두 실패의 공통 구조가 있다. **기술의 전제 조건을 확인하지 않고 결론만 들여왔다.** GraphQL의 전제는 "클라이언트가 여럿이고 조합이 폭발한다"이고, gRPC의 전제는 "소비자를 우리가 통제한다"이다. 전제가 없으면 대가만 남는다.

### 3-3. 도입 순서 — REST에서 얼마나 갈 수 있는지 먼저 본다

새 기술을 검토할 때의 순서도 답변의 일부다. **문제 크기와 도구 크기를 맞추는 판단**을 보여주는 자리이기 때문이다.

```
① 지금 REST의 무엇이 아픈가를 증상으로 특정한다
      over-fetching이 아픈가?  under-fetching(왕복 수)이 아픈가?
      아니면 백엔드 팀이 화면 요구의 병목이 된 것이 아픈가?
                    │
② 07번의 REST 내 처방으로 풀리는가
      목록 DTO 확장 -> 벌크 조회 -> expand(깊이 1) -> BFF
                    │  여기서 풀리면 여기서 멈춘다
                    ▼
③ 조합의 수가 조직의 처리 능력을 넘어섰는가
      클라이언트 종류 × 화면 수 × 필드 조합이 폭발해
      BFF 엔드포인트 추가 요청이 백엔드 팀에 쌓이는가
                    │  그렇다면
                    ▼
④ GraphQL 검토 (2-4의 대가 넷을 감당할 준비와 함께)
```

내부 통신을 gRPC로 옮기는 판단도 같은 방식이다. **먼저 "지금 내부 호출의 무엇이 아픈가"를 특정한다** — 호출량이 많아 직렬화 CPU가 눈에 띄는가, 서비스 간 계약 불일치로 인한 장애가 반복되는가, 서버 푸시가 필요한가. 셋 중 하나라도 실측으로 확인되면 도입 근거가 되지만, "요즘 다 쓴다"는 근거가 아니다.

## 4. 꼬리질문 대비 포인트

### "GraphQL의 N+1 문제는 왜 생기고 어떻게 해결하나요?"

**원인은 리졸버가 필드 단위로 호출된다는 성질에 있다**(1-3). 목록 안의 연관 필드는 그 "필드 단위"가 "항목 단위"로 번역되므로, `users(10명) { orders }` 쿼리 하나가 users 조회 1회 + orders 조회 10회 = 11회가 된다. 07번에서 정의한 N+1(1 + N)과 같은 산수다.

해결은 **DataLoader 패턴**이다. **DataLoader는 리졸버들이 개별적으로 요청한 조회를 즉시 실행하지 않고 잠깐 모아 뒀다가, 모인 키를 하나의 `WHERE user_id = ANY(?)` 질의로 바꿔 한 번에 실행한 뒤 각 리졸버에 결과를 나눠 주는 계층**이다. 같은 키를 두 번 요청하면 캐시된 결과를 준다.

"잠깐 모아 둔다"는 것이 얼마 동안인지가 이 패턴의 핵심인데, 흔히 **"같은 실행 틱(tick) 안에서 모은다"**고 설명된다. 여기서 **틱은 이벤트 루프가 한 바퀴 도는 단위**를 말한다.

```
[틱 = 이벤트 루프 한 바퀴]

  이벤트 루프: 처리할 일이 쌓인 큐를 한 바퀴 돌며 꺼내 실행하는 구조.
              그 "한 바퀴"가 1틱이다.

  DataLoader의 동작
    같은 틱 안 : load(1), load(2), ... load(10)  <- DB에 안 간다. 키만 모은다.
    틱이 끝날 때: 모인 키 [1..10]을 한 번에 조회 -> 각 load 호출에 결과를 나눠 준다
```

같은 틱에 모인다는 것은 실무적으로 **"같은 GraphQL 요청을 처리하는 동안 서로 다른 리졸버가 낸 조회는 하나로 합쳐진다"**는 뜻이다. 요청 사이에는 합쳐지지 않으므로 DataLoader 인스턴스는 요청마다 새로 만든다 — 요청을 넘겨 공유하면 A 사용자가 조회한 결과가 B의 요청에 캐시로 나가는 인가 사고가 된다. (Java 진영에서는 `java-dataloader`와 Spring for GraphQL의 `BatchLoaderRegistry`가 같은 일을 한다.)

**"JPA의 N+1과 원리(개별 지연 조회의 반복)가 같고, 해법(배치 로딩)도 같다"**고 연결하면 가산점 포인트다. `@BatchSize`나 `fetch join`이 하던 일을 DataLoader가 리졸버 계층에서 하는 것이다.

### "gRPC는 왜 브라우저에서 직접 못 쓰나요?"

**최종 상태 코드가 트레일러 헤더에 있기 때문**이다(2-6). 트레일러 헤더는 **응답 본문이 다 끝난 뒤에 오는 헤더**이고, gRPC는 호출 결과인 `grpc-status`를 거기에 싣는다. 스트리밍 응답에서는 결과를 미리 알 수 없으므로 뒤에 붙일 수밖에 없는 설계다.

그런데 **브라우저의 `fetch`/`XHR`은 본문까지만 노출하고 트레일러는 자바스크립트에 넘겨주지 않는다.** 그래서 브라우저는 gRPC 호출의 성공/실패를 판정할 방법이 없다. 이 밖에도 브라우저는 HTTP/2 프레임을 직접 제어할 수 없어 gRPC가 요구하는 세밀한 스트림 조작이 불가능하다.

대응은 **grpc-web + 중간 프록시(Envoy 등)** 다. 프록시가 트레일러를 본문 끝에 데이터 프레임으로 밀어 넣어, 브라우저가 본문만 읽고도 상태를 알 수 있게 변환한다.

여기서 한 걸음 더 나가면 좋다. **"이 프록시 계층이 반드시 추가된다는 사실 자체가 gRPC를 외부 경계에 두지 않는 이유 중 하나"**라고 묶으면, 기술적 사실을 아키텍처 판단으로 잇는 답이 된다.

### "GraphQL을 쓰면 HTTP 캐싱이 왜 무력화되나요? 대안은?"

**전제가 깨지기 때문**이다. REST의 HTTP 캐싱은 `GET + 고유 URL = 캐시 키`라는 전제 위에 서 있다. GraphQL은 대개 `/graphql` 단일 엔드포인트에 POST로 쿼리를 보내므로 URL이 캐시 키 역할을 못 하고, POST 응답은 HTTP 시맨틱상 중간 캐시가 재사용하지 않는다. **CDN과 프록시가 개입할 근거 자체가 사라진 것**이다.

대안이 셋이다.

**(1) persisted query(등록된 쿼리).** **쿼리 본문을 서버에 미리 등록해 두고, 클라이언트는 그 쿼리의 해시 ID만 GET으로 보내는 방식**이다. `GET /graphql?id=a3f8c2&variables={"id":42}` 같은 형태가 되므로 **URL이 다시 캐시 키가 되어 CDN 캐싱이 되살아난다.** 부수 효과도 크다 — 등록되지 않은 쿼리는 아예 실행할 수 없으므로 "클라이언트가 임의의 비싼 쿼리를 만든다"는 위험(2-4의 대가 3)이 함께 막히고, 매 요청에 긴 쿼리 문자열을 실어 보내지 않아 요청 크기도 준다. Apollo의 APQ(Automatic Persisted Queries)는 이 등록을 자동화해서, 서버가 모르는 해시를 받으면 한 번만 전체 쿼리를 요구하고 이후에는 해시만 받는다.

**(2) 클라이언트 측 정규화 캐시.** **응답을 화면 단위로 통째로 저장하지 않고, 객체를 `타입명 + id`를 키로 삼아 잘게 쪼개 저장하는 캐시**다. "정규화"라는 이름은 DB 정규화와 같은 뜻으로, 같은 객체를 여러 벌 중복 저장하지 않는다는 의미다.

```
응답: { order: { id: 42, user: { id: 7, name: "김철수" } } }

정규화 캐시에 저장되는 모양
  "Order:42" -> { id: 42, user: <ref "User:7"> }
  "User:7"   -> { id: 7, name: "김철수" }

  -> 다른 화면이 User:7의 name을 물으면 네트워크에 안 나가고 여기서 답한다.
  -> User:7의 이름이 바뀌면 그 항목 하나만 갱신되고, 그를 참조하는 모든 화면이 함께 갱신된다.
```

Apollo Client가 이 방식을 쓴다. 화면 단위 캐시라면 "주문 상세"와 "주문 목록"이 같은 유저 정보를 각자 들고 있다가 따로 낡아 버리지만, 정규화 캐시에서는 그 유저가 한 벌만 존재하므로 그런 불일치가 생기지 않는다.

**(3) 서버 내부의 데이터 소스 캐싱.** 리졸버가 부르는 저장소 계층 앞에 Redis 등을 두는 것이다. 가장 익숙한 방식이지만, 네트워크 왕복은 그대로 나므로 (1)·(2)와 성격이 다르다.

정리하면 **"네트워크 계층 캐시를 잃고 애플리케이션 계층 캐시로 보상하는 구조"** 다. 덧붙여 **GraphQL은 필드 오류가 나도 대개 HTTP 200에 `errors` 배열을 담아 응답한다**는 점도 함께 말하면 좋다 — 상태 코드 기반 알람과 대시보드가 그대로 통하지 않으므로, 운영 관측 체계를 다시 세워야 한다는 비용이 캐싱 말고도 하나 더 있다는 뜻이다.

### "REST로도 필드 선택 파라미터나 BFF로 over-fetching을 풀 수 있는데, 그래도 GraphQL을 택하는 기준은?" (시니어 변별 포인트)

정확한 지적이고, 실제로 그 순서로 검토해야 한다(3-3). `?fields=name,grade` 같은 부분 응답 파라미터나 화면 전용 BFF 엔드포인트로 충분하면 REST에 머무는 것이 총비용이 낮다.

여기서 07번이 정의한 **BFF(Backend For Frontend, 특정 프론트엔드 하나를 위한 전용 백엔드)의 성격을 정확히 옮겨 오면 논지가 선명해진다. BFF는 재사용성을 대가로 왕복을 사는 거래**다. "화면마다 다른 API"는 REST의 미덕인 재사용성을 정면으로 버리는 선택이지만, 대신 그 화면이 필요한 것을 정확히 한 번에 준다.

그렇다면 GraphQL은 언제 이기는가. **BFF의 대가가 "재사용성"에서 "조직의 처리 속도"로 바뀌는 지점**이다.

```
[BFF로 충분한 구간]
  화면이 새로 필요하면 -> 백엔드 팀이 BFF 엔드포인트를 하나 추가한다
  화면 수가 적으면 이 추가가 부담이 아니다.

[BFF가 병목이 되는 구간]
  클라이언트 종류(iOS·안드로이드·웹·태블릿) × 화면 수 × 필요 필드 조합
  -> 조합이 폭발한다
  -> 엔드포인트 추가/수정 요청이 백엔드 팀 백로그에 쌓인다
  -> 프론트 팀이 화면 하나 바꾸려고 다음 스프린트를 기다린다   <- 여기가 진짜 비용
```

**GraphQL이 이기는 지점은 성능이 아니라 대기 시간이다.** 조합을 만드는 일을 클라이언트 팀에 넘겨 팀 간 대기 비용을 없앤다. 즉 기술 선택처럼 보이지만 실은 **팀 간 의존 구조를 바꾸는 결정**이고, 그 필요가 없다면 도입하지 않는다.

판단 기준을 한 줄로 주면 이렇게 된다. **"백엔드 팀이 화면 요구의 병목이 되고 있는가"가 실측되면 GraphQL, 아니면 REST + BFF.** 이렇게 조직 관점까지 답하면 시니어 변별이 된다.

### "gRPC(proto) 계약은 어떻게 하위 호환을 지키며 바꾸나요?"

**출발점은 1-4에서 본 사실 하나다 — Protobuf는 필드를 이름이 아니라 번호로 직렬화한다.** 그래서 호환성 규칙이 전부 "번호"를 중심으로 정해진다.

| 하려는 변경 | 안전한가 | 이유 |
|---|---|---|
| 새 필드를 **새 번호로** 추가 | 안전 | 구버전은 모르는 번호를 만나면 무시한다 |
| 기존 필드의 **번호 변경** | 위험 | 같은 데이터가 다른 필드로 해석된다. 조용히 값이 뒤바뀐다 |
| 기존 필드의 **타입 변경** | 위험 | 번호는 같은데 해석 방식이 달라져 역직렬화가 깨지거나 값이 망가진다 |
| 필드 **이름만** 변경 | 와이어 호환은 안전 | 바이트에는 이름이 없다. 다만 생성된 코드의 접근자 이름이 바뀌므로 양쪽 소스 코드는 깨진다 |
| 필드 **삭제** | 조건부 안전 | 번호를 `reserved`로 묶어 재사용을 금지해야 안전하다 |

**`reserved`가 왜 필요한지가 이 질문의 핵심이다.** 3번 필드를 지운 뒤 나중에 누군가 새 필드에 3번을 붙이면, 아직 구버전 proto를 들고 있는 서비스는 새 데이터를 **옛 3번 필드로 해석한다.** 타입까지 우연히 맞으면 에러도 나지 않고 값만 엉뚱해진다. 그래서 지운 번호는 무덤에 이름표를 세우듯 못박아 둔다.

```protobuf
message Order {
  reserved 3, 7 to 9;              // 이 번호들은 영원히 재사용 금지
  reserved "legacy_status";        // 이름도 함께 막아 둔다

  int64 id = 1;
  string status = 2;
  int64 total_amount = 4;
}
```

여기에 실무 디테일 하나를 얹으면 좋다. **자주 쓰는 필드는 1~15번에 배치한다.** 1-4에서 본 태그 바이트가 1~15번은 1바이트, 16번부터는 2바이트를 쓰기 때문이다. 고빈도 필드를 앞 번호에 두는 것만으로 페이로드가 줄어든다.

마지막으로 **`03-api-versioning-strategies.md`·`08-backward-compatible-api-changes.md`의 원칙과 나란히 놓으면 시각의 일관성이 드러난다.** 두 문서의 대원칙은 "추가는 안전, 삭제·의미 변경은 파괴적 변경(기존 클라이언트가 코드를 한 줄도 고치지 않은 채 새 서버와 통신했을 때 동작이 깨지는 변경)"이었고, 추가가 안전한 근거는 **받는 쪽 파서가 모르는 것을 무시한다는 규약(Tolerant Reader)** 이었다.

**proto는 그 규약을 사람의 약속이 아니라 도구로 강제한다.** REST에서는 "모르는 필드는 무시하도록 파싱하십시오"를 문서에 적어 부탁해야 하지만, Protobuf 런타임은 모르는 번호를 항상 무시한다. 대신 REST에는 없는 제약 하나가 생긴다 — 번호는 유한한 자원이고 한번 쓴 번호는 영원히 되돌릴 수 없다. **계약 관리의 부담이 사라진 것이 아니라 문서에서 도구로 옮겨간 것**이라고 정리하면 좋다.

## 한 줄 요약

REST/GraphQL/gRPC는 우열이 아니라 계약을 어디에 적고 누가 강제하는지가 다른 세 스타일이므로(URL과 메서드에 적고 문서가 강제 / 타입 스키마에 적고 검증기가 강제 / IDL 파일에 적고 컴파일러가 강제), 선택 축은 **그 계약을 읽고 코드를 짜는 사람이 누구인가**다 — 통제할 수 없는 외부에는 HTTP 생태계를 통째로 물려받는 REST, 응답 형태의 결정권이 서버에 있어 생기는 over/under-fetching이 화면 조합의 폭발로 백엔드 팀을 병목으로 만드는 자사 멀티 클라이언트에는 GraphQL(캐싱 무력화·필드 단위 인가·리졸버 N+1을 대가로), 우리가 배포하고 통제하는 서버 사이의 고빈도 호출에는 필드 번호 기반 바이너리 직렬화와 HTTP/2 멀티플렉싱의 gRPC(트레일러 헤더 때문에 브라우저에서는 프록시 없이 못 쓴다) — 그리고 실무는 경계마다 소비자가 다르므로 셋을 혼용하되, 각 기술의 전제가 없는 자리에 결론만 들여오면 이득 없이 대가만 남는다.
