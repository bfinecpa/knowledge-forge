# Chatty API 개선 — HTTP 왕복은 공짜가 아니다, N+1은 네트워크에서도 일어난다

> 핵심 관전 포인트: **목록 1회 + 상세 N회는 JPA에서 겪는 N+1 문제가 위치만 바꿔 네트워크 계층에서 반복되는 것이다. 결정적 차이는 단가다 — 애플리케이션↔DB 왕복은 1ms 미만이지만 클라이언트↔서버 왕복(RTT)은 모바일에서 수십~수백 ms라, 같은 21번이어도 후자는 화면이 멈추는 시간이 된다. 그리고 RTT는 서버를 좋은 걸로 바꿔도 줄지 않는다(물리적 거리와 홉 수가 정한다) — 그래서 유일한 처방이 **왕복 횟수를 줄이는 것**이다. 병렬 호출은 왕복 "시간"만 줄일 뿐 요청 "수"는 그대로라, HTTP/1.1의 호스트당 커넥션 6개 제한과 HTTP/2 멀티플렉싱은 이 계산의 상수만 바꾼다 — 서버 처리·직렬화·인증 검사라는 요청당 고정 비용은 여전히 N배이고, 요청이 많을수록 그중 하나가 p99에 걸릴 확률이 커져 tail latency가 화면 완성 시간을 지배한다. 처방은 층위별로 넷이다: ① 목록 응답에 화면이 그리는 요약 필드를 포함(목록 DTO를 화면 계약으로 설계) ② 여러 건을 한 번에 받는 벌크 조회(`?ids=1,2,3`) ③ 연관 리소스를 같은 응답에 옵션으로 실어 주는 `expand`/`embed` 파라미터 ④ 화면 단위 조합을 전담하는 BFF(Backend For Frontend) 계층. 본질은 "리소스별로 단순한 API"라는 백엔드 편의와 "화면당 한 번의 호출"이라는 클라이언트 효율 사이의 긴장이고, 어느 층에서 조율할지 정하는 게 설계다.**

---

## 0. 질문 + 의도

**질문**: "목록 조회 + 상세 N건 조회로 인한 API 호출 폭증(chatty API)을 어떻게 개선하나요?"

**출제 의도**: 모바일 환경(높은 왕복 지연)에서 API 호출 수가 곧 체감 속도다. 백엔드 편의(리소스별 단순 API)와 클라이언트 효율의 긴장을 인식하고 조율해본 경험을 본다 — "서버 응답은 50ms인데 왜 화면이 느리냐"는 상황에서 원인을 네트워크 왕복 구조로 진단할 수 있는지가 관전 포인트다.

> 조합 API가 부분 실패했을 때의 응답 계약은 `13-aggregation-api-partial-failure-contract.md`, 게이트웨이와 BFF의 책임 경계는 `14-gateway-vs-service-responsibility-boundary.md`, GraphQL·gRPC와의 비교는 `11-rest-vs-graphql-vs-grpc.md`에서 다룬다.

## 1. 왜 생기고 왜 문제인가 — 리소스 지향 설계의 자연스러운 부작용

### 1-1. 용어 정리 — chatty가 무슨 뜻인가

**chatty API**는 "수다스러운 API"라는 뜻이다. 한 번에 할 말을 다 하지 않고 짧은 말을 여러 번 주고받는 대화처럼, 화면 하나를 그리는 데 서버와 여러 번 왕복하는 호출 구조를 가리킨다.

반대말은 **chunky API**다. "덩어리진"이라는 뜻으로, 한 번에 큰 응답을 통째로 주고받는 구조다. 이 두 단어는 좋고 나쁨의 이름이 아니라 스펙트럼의 양 끝 이름이며, 이 문서의 결론도 "chunky로 가자"가 아니라 "어느 지점이 이 화면에 맞는가"다.

### 1-2. 발생 경로 — 잘 만든 REST API가 chatty를 만든다

리소스 중심으로 정직하게 설계하면 이렇게 된다.

```text
GET /orders            → 주문 id 목록          (백엔드 입장: 깔끔한 단일 책임)
GET /orders/1          → 주문 1 상세
GET /orders/2          → 주문 2 상세
...
GET /users/42          → 주문자 이름 표시용
GET /products/77       → 상품 썸네일 표시용
```

각 API는 단순하고 재사용 가능하고 캐시하기 좋다 — **리소스별로는 전부 옳은 설계다.** 이 점이 중요하다. chatty는 누가 실수해서 생기는 것이 아니라, 교과서대로 리소스 지향 설계를 하면 자연히 도달하는 상태다.

문제는 화면이 리소스 단위가 아니라 **조합 단위**로 그려진다는 데 있다. "주문 목록 화면"은 주문 + 주문자 이름 + 상품 썸네일을 한 번에 원하는데, 리소스별 API만 있으면 그 조합을 만드는 일이 클라이언트로 떠넘겨지고, 클라이언트는 그 조합을 **네트워크 왕복으로 지불한다.**

### 1-3. 전제 지식 — "N+1"은 정확히 어떤 산수인가

**N+1**은 이름 자체가 산수다. 목록을 가져오는 호출 **1번**, 그리고 목록에 들어 있는 항목 하나하나마다 추가 호출 **N번**. 합해서 **N+1번**이다. 항목이 20개면 1 + 20 = **21번**이다.

3년차라면 이 구조를 이미 JPA에서 만나봤을 가능성이 높다. 주문 20건을 조회한 뒤 각 주문의 `orderItems`를 지연 로딩으로 건드리면, 목록 SELECT 1번 + 주문마다 연관 SELECT 20번 = 21번의 쿼리가 나가는 그 문제다.

**chatty API는 이 N+1이 위치만 바꿔 네트워크 계층에서 그대로 반복되는 것이다.** 구조가 비슷한 정도가 아니라 같은 문제이며, 그래서 처방도 대응된다.

| | JPA의 N+1 | HTTP의 chatty(N+1) |
|---|---|---|
| "1"에 해당하는 것 | 목록 SELECT 1번 | `GET /orders` 1회 |
| "N"에 해당하는 것 | 항목마다 연관 SELECT N번 | `GET /orders/{id}` N회 |
| 왕복이 일어나는 구간 | 애플리케이션 ↔ DB | 클라이언트 ↔ 서버 |
| **왕복 1회의 단가** | **1ms 미만** (같은 데이터센터) | **30~300ms** (모바일 셀룰러망) |
| 처방 | fetch join, `@EntityGraph`, batch size | 목록 DTO 확장, 벌크 조회, expand, BFF |

표에서 읽어야 할 것은 마지막에서 두 번째 줄이다. **같은 21번이어도 단가가 100~300배 차이 난다.** DB N+1은 21ms로 끝나 눈에 잘 안 띄지만, 네트워크 N+1은 같은 21번이 몇 초가 되어 사용자가 화면 앞에서 기다린다. 그래서 이쪽이 훨씬 아프다.

### 1-4. 전제 지식 — RTT가 무엇이고 왜 줄일 수 없는가

앞 표의 "단가"를 이해하려면 단위 하나를 먼저 잡아야 한다.

**RTT(round-trip time, 왕복 시간)는 내가 보낸 요청이 상대에게 도착하고 그 응답이 나에게 돌아오기까지 걸리는 시간**이다. "왕복"이라는 이름 그대로 편도가 아니라 갔다 오는 한 세트를 센다.

RTT를 결정하는 것은 두 가지다. 하나는 **물리적 거리**로, 신호는 광케이블 안에서 빛의 속도의 약 3분의 2로 움직이므로 거리가 멀면 그만큼 시간이 든다. 다른 하나는 **중간에 거치는 장비의 수와 각 장비에서의 대기**로, 라우터·스위치·기지국을 지날 때마다 패킷이 큐에 잠깐씩 줄을 선다.

여기서 이 문서 전체의 논지가 나온다. **RTT는 서버를 좋은 것으로 바꾸거나 코드를 최적화해도 줄어들지 않는다.** 8차선 도로를 16차선으로 넓혀도 서울에서 부산까지의 거리는 그대로인 것과 같다. 서버 응답이 50ms에서 5ms가 되어도 왕복 100ms는 그대로 남는다.

그래서 **줄일 수 있는 것은 왕복 시간이 아니라 왕복 횟수뿐이다.** 이 문장이 이 문서에 나오는 모든 처방의 공통 원리다.

감각을 위한 대략적인 수치는 이렇다 (`08-network-http/01-url-to-page-dns-tcp-tls-http.md` 1-2와 같은 기준).

| 구간 | 대략적인 RTT |
|---|---|
| 같은 데이터센터 내부 (서버 ↔ DB, 서버 ↔ 서버) | 1ms 미만 |
| 같은 도시/리전 안 (사용자 ↔ 서울 서버, 유선) | 5~30ms |
| 국내 모바일 셀룰러망 (위 값 + 기지국 구간) | 30~100ms |
| 전파가 나쁜 셀 가장자리·혼잡 시간대 | 200~300ms |
| 국내 사용자 ↔ 미국 서부 서버 | 100~180ms |

이 표에서 첫 줄과 셋째 줄의 차이가 곧 **"네트워크 N+1을 서버 안의 조합으로 옮기면 왜 이득인가"**의 답이다. 서버가 대신 20번 왕복해도 그건 1ms짜리 왕복이고, 클라이언트가 20번 왕복하면 그건 100ms짜리 왕복이다.

### 1-5. 비용 계산 — 순차와 병렬은 다르고, 프로토콜이 상수를 바꾼다

이제 실제로 계산해 보자. **항목 20개짜리 목록 화면, 목록 1회 + 상세 20회 = 21회 호출**이 전제다.

먼저 가장 단순한 경우, 클라이언트가 응답을 하나 받고 다음을 부르는 **순차 호출**이다.

```text
순차 호출: 21회 × RTT

  RTT 100ms → 21 × 100 = 2,100ms  (2.1초)
  RTT 300ms → 21 × 300 = 6,300ms  (6.3초)   ← 화면이 "느리다"의 정체
```

그런데 실제 클라이언트는 대개 상세 20건을 **병렬로** 쏜다. 여기서 "그럼 20건이 동시에 나가니 1 RTT로 끝나는 것 아닌가"라고 생각하기 쉬운데, 그렇지 않다. 동시에 몇 개까지 보낼 수 있는지를 **프로토콜이 제한**하기 때문이다.

**HTTP/1.1에는 한 커넥션에 요청 하나만 흘릴 수 있다는 제약이 있다.** 응답에 "이건 몇 번 요청의 답이다"라는 식별자가 없어서 요청 순서와 응답 순서가 같아야만 짝이 맞기 때문이다. 그래서 브라우저는 병렬성을 커넥션 개수로 만들었고, **같은 호스트에 동시에 여는 커넥션을 보통 6개로 제한**한다(무한정 늘리면 서버 부담이 커지고, 커넥션마다 TCP slow start를 따로 치러 이득이 줄기 때문이다).

커넥션이 6개면 요청 20개는 한 번에 다 못 나가고 **6개씩 묶인 파도(wave)로 나간다.** 20 ÷ 6 = 3.33이므로 올림해서 **4번의 파도**가 필요하다.

**HTTP/2는 이 제약을 푼다.** 모든 조각에 길이와 스트림 ID를 붙이는 이진 프레이밍 덕분에 한 커넥션에 여러 요청을 뒤섞어 실어 보낼 수 있고(**멀티플렉싱**, multiplexing — 하나의 물리적 통로에 여러 논리적 통로를 겹쳐 보내는 기법), 그래서 상세 20건이 한 커넥션에서 동시에 나간다. (프로토콜별 상세는 `08-network-http/09-http1-http2-http3-hol-blocking.md` 참고.)

네 가지 경우를 한 표로 비교하면 이렇다. **서버 처리 시간을 0으로 두고 왕복만 센 값**이고, 커넥션은 이미 맺혀 있다고(keep-alive) 가정한다.

| 방식 | 왕복 횟수 | RTT 100ms | RTT 300ms | 서버가 받는 요청 수 |
|---|---|---|---|---|
| 순차 21회 | 21 | 2,100ms | 6,300ms | 21건 |
| 병렬 + HTTP/1.1 (호스트당 커넥션 6개) | 1 + (20을 6으로 나눠 올림) 4 = 5 | 500ms | 1,500ms | 21건 |
| 병렬 + HTTP/2 (멀티플렉싱) | 1 + 1 = 2 | 200ms | 600ms | 21건 |
| 목록 DTO 확장 또는 벌크 조회로 1회 | 1 | 100ms | 300ms | **1건** |

표의 마지막 열이 핵심이다. **병렬화도 HTTP/2도 왕복 "시간"만 줄일 뿐, 서버가 받는 요청 "수"는 21건 그대로다.** 왕복 횟수를 진짜로 줄이는 것은 마지막 줄, 즉 응답 구조를 바꾸는 처방뿐이다.

병렬 호출에는 표에 안 나오는 비용이 하나 더 있다. **파도 하나는 그 안에서 가장 느린 응답이 돌아와야 끝난다** — 이걸 **tail latency(꼬리 지연)**라 한다. 응답 시간 분포의 꼬리(느린 쪽 끝)가 전체를 지배한다는 뜻이다.

숫자로 보면 무섭다. 호출 하나가 500ms를 넘길 확률이 1%(p99가 500ms)라고 하자. 호출이 21개면 **그중 적어도 하나가 500ms를 넘길 확률은 1 − 0.99²¹ ≈ 19%**다. 서버의 p99는 그대로인데 **화면 다섯 번에 한 번은 느려진다.** 호출 수를 줄인다는 것은 이 확률을 줄인다는 뜻이기도 하다.

### 1-6. 그래서 왜 "서버 APM은 초록불인데 앱은 느리다"가 되는가

지금까지의 계산을 한 문장으로 요약하면 이렇다. **서버 메트릭에는 "요청 하나의 처리 시간"만 있고, "화면 하나의 완성 시간"은 없다.**

서버 입장에서 21건은 각각 50ms에 잘 처리된 정상 요청 21건이다. p99 대시보드는 초록색이다. 사용자 입장에서 그 21건은 몇 번의 파도로 나뉘어 몇 초를 기다리게 만든 하나의 화면이다. 이 간극이 chatty 문제의 증상이고, 그래서 진단은 서버가 아니라 클라이언트 관점에서 시작해야 한다(3장).

## 2. 개선 전략 — 층위별 선택지와 각각의 대가

면접에서는 이 네 개를 목록으로 꺼내고, 상황에 맞는 선택 기준을 붙인다. 순서에 의미가 있다 — 아래로 갈수록 강력하지만 그만큼 비싸다.

### 2-1. 목록 응답에 화면이 원하는 필드를 포함한다 — 가장 흔한 정답

"목록 API가 id만 주니까 상세를 N번 부른다"가 원인이면, **목록 DTO를 화면 요구에 맞춰 설계**하는 게 첫 번째 처방이다.

발상의 전환이 하나 필요하다. 목록 응답은 **엔티티의 축소판이 아니라 화면 계약**이다. "Order 엔티티에서 필드를 몇 개 뺀 것"이 목록 DTO라고 생각하면 무엇을 넣을지 기준이 없지만, "이 목록 화면이 그리는 것"이 기준이면 넣을 것과 뺄 것이 결정된다.

```json
// Before: 목록이 사실상 id 목록이다 → 클라이언트가 상세를 N회 호출한다
GET /orders
[ { "id": 1 }, { "id": 2 }, ... ]
```

```json
// After: 목록 항목에 화면이 실제로 그리는 요약 필드를 포함한다
GET /orders
{
  "items": [
    {
      "id": 1,
      "orderNumber": "ORD-20260830-001",
      "status": "SHIPPED",
      "ordererName": "김철수",                // users 조인 결과 — GET /users/42 를 없앤다
      "firstProductThumbnail": "https://...", // products 조인 결과 — GET /products/77 를 없앤다
      "totalAmount": 45000,
      "orderedAt": "2026-08-30T12:34:56Z"
    }
  ],
  "nextCursor": "..."
}
```

서버는 이 조합을 DB 조인(또는 조회 전용으로 미리 만들어 둔 read model) 한 번으로 만든다. 즉 **네트워크 N+1을 서버 안의 조인 한 번으로 옮기는 것**이고, 1-4의 RTT 표대로 서버↔DB 왕복은 클라이언트↔서버 왕복보다 100배 이상 싸다.

주의할 점은 서버 안에서도 N+1이 재현되지 않게 하는 것이다. 조합을 만든다면서 주문 20건을 순회하며 `userRepository.findById()`를 20번 부르면, 네트워크 N+1을 DB N+1로 옮겼을 뿐이다. `fetch join`이나 `@EntityGraph`, 또는 사용자 id를 모아 `WHERE id = ANY(?)` 한 방으로 가져오는 형태여야 개선이 완성된다.

**대가**: 목록 API가 특정 화면에 결합되고, 화면 요구가 늘 때마다 필드가 자란다(→ 4장의 "목록 응답에 필드를 계속 추가하다 보면"). 상세 API는 없애지 말고, **목록에 넣기엔 무거운 필드**(전체 배송 이력, 결제 수단, 긴 텍스트)를 주는 역할로 분리해 남긴다.

### 2-2. 벌크 조회 — "N번 부를 것을 1번에"

목록과 무관하게 "id 여러 개의 상세"가 필요한 경우의 처방이다. 장바구니에 담긴 상품들, 알림 목록에 붙는 발신자 프로필들처럼 **클라이언트가 이미 id 집합을 손에 쥐고 있는** 상황이다. 이때는 단건 API 옆에 복수 조회를 추가한다.

```text
Before: 클라이언트가 루프를 돈다
  for id in [1, 2, 3, ..., 20]:
      GET /products/{id}            → 20 왕복

After: 벌크 조회 1회
  GET /products?ids=1,2,3,...,20    → 1 왕복
```

설계 디테일이 변별 포인트다. 벌크 API는 "만들었다"가 아니라 "계약을 어떻게 정했나"에서 실력이 갈린다.

- **개수 상한을 계약에 명시**한다(예: 최대 100개). 상한 없는 벌크는 언젠가 "id 10만 개" 요청이 되어 DB 조회 폭발과 응답 비대를 부른다. 상한을 넘으면 400으로 거절하고, 상한값을 문서와 에러 메시지에 함께 적는다.
- **일부 id가 존재하지 않을 때의 계약**을 정한다. 있는 것만 돌려주고 없는 건 조용히 생략할 것인지, `found`와 `missing`을 나눠 명시적으로 돌려줄 것인지다. 정하지 않으면 클라이언트마다 해석이 갈리고, "요청은 20개인데 응답은 18개"인 상황에서 어느 2개가 빠졌는지 알아내려고 클라이언트가 또 루프를 돈다.
- id가 아주 많으면 URL 길이 한계에 걸린다. 조회여도 `POST /products:batchGet` 같은 형태로 본문에 담는 절충이 실무 관행이다(→ 4장의 "GET URL 길이 제한").
- **(가산점 포인트)** 벌크 API의 서버 구현이 내부에서 단건 조회를 루프로 돌면 네트워크 N+1을 서버 안 N+1로 옮겼을 뿐이다. 저장소 계층까지 한 방으로 내려가야 개선이 완성된다. PostgreSQL이라면 `WHERE id IN (...)`보다 **`WHERE id = ANY(?)`로 배열 파라미터 하나를 넘기는 형태**가 낫다 — id 개수가 달라질 때마다 SQL 문자열이 달라져 실행 계획 캐시가 개수별로 따로 쌓이는 일을 피할 수 있다. MSA라면 내부 서비스 간 호출도 벌크 API로 뚫려 있어야 한다.

### 2-3. expand/embed 파라미터 — 연관 리소스를 옵션으로 실어 주기

**`expand`(또는 `embed`) 파라미터는 클라이언트가 "이 자원에 딸린 연관 자원까지 같은 응답에 실어 달라"고 요청하는 쿼리 파라미터**다. "펼치다(expand)", "끼워 넣다(embed)"라는 이름 그대로, 평소에는 id 참조로만 있던 연관 자원을 요청 시 객체로 펼쳐 준다. Stripe, GitHub 같은 공개 API들이 쓰는 패턴이다.

핵심은 **리소스 API의 일반성을 유지하면서**, 왕복을 아끼고 싶은 클라이언트에게만 선택적으로 조합을 제공한다는 점이다. 2-1(목록 DTO 확장)이 "모두에게 항상 준다"면, expand는 "원하는 사람이 요청할 때만 준다"이다.

```http
# Before: 주문만 받고, 주문자와 항목은 각각 따로 부른다 → 3 왕복
GET /orders/42
GET /users/7
GET /orders/42/items
```

```json
// Before의 응답 — 연관 자원은 id 참조로만 들어 있다
{
  "id": 42,
  "userId": 7,
  "status": "SHIPPED",
  "totalAmount": 45000
}
```

```http
# After: 필요한 연관 자원을 이름으로 지정해 한 번에 받는다 → 1 왕복
GET /orders/42?expand=user,items
```

```json
// After의 응답 — userId 자리에 user 객체가 펼쳐지고, items가 함께 실린다
{
  "id": 42,
  "user": { "id": 7, "name": "김철수", "grade": "GOLD" },
  "status": "SHIPPED",
  "totalAmount": 45000,
  "items": [
    { "productId": 77, "name": "무선 이어폰", "quantity": 1, "price": 45000 }
  ]
}
```

**대가**가 셋이다.

첫째, **서버 구현 복잡도**다. expand 조합마다 조회 경로가 갈리고, 허용 키를 화이트리스트로 제한하지 않으면 "무엇이든 조인해 달라"는 API가 된다.

둘째, **응답 형태가 파라미터에 따라 변한다.** 같은 URL이 파라미터에 따라 다른 모양을 내므로 캐시 키가 파라미터 조합만큼 늘어나고(`?expand=user`와 `?expand=user,items`는 다른 캐시 엔트리다), 문서화와 클라이언트 타입 정의도 조합마다 갈린다.

셋째, **중첩 expand의 유혹**이다. `expand=items.product.seller`처럼 깊이를 열어주기 시작하면 사실상 쿼리 언어를 재발명하게 되고, 그 지경이면 GraphQL을 검토하는 편이 낫다. **깊이 1까지만 허용**하는 것이 현실적인 선이다.

### 2-4. Aggregation / BFF — 화면 단위 API를 담당하는 계층을 둔다

**BFF는 Backend For Frontend, 즉 "특정 프론트엔드 하나를 위한 전용 백엔드"**다. 이름이 곧 정의다. 모든 클라이언트가 함께 쓰는 범용 API 위에, **모바일 앱 전용 백엔드 하나, 웹 전용 백엔드 하나**를 따로 두는 구조다.

왜 이런 것이 필요한가. 범용 API 하나로 모바일과 웹과 파트너를 전부 만족시키려 하면 **모든 화면을 만족시키려다 아무 화면도 만족시키지 못하는** 상태에 빠지기 때문이다. 모바일은 데이터가 모자라 여러 번 부르고(과소 전송), 웹은 쓰지도 않는 필드를 잔뜩 받는다(과다 전송). 요구가 서로 다른데 계약이 하나뿐인 것이 문제의 뿌리다.

BFF는 여기서 **재사용성을 포기하는 대신 왕복을 줄이는 거래**를 한다. "화면마다 다른 API"는 REST의 미덕인 재사용성을 정면으로 버리는 선택이지만, 대신 그 화면이 필요한 것을 정확히 한 번에 준다.

```text
[모바일 앱]  ── 1 왕복 (RTT 100ms) ──▶  [모바일 BFF]
                                            │
                        데이터센터 내부 병렬 호출 (RTT 1ms 미만)
                          ┌─────────────────┼─────────────────┐
                          ▼                 ▼                 ▼
                    [orders-api]      [users-api]      [products-api]
                          └─────────────────┼─────────────────┘
                                            ▼
                                  화면 DTO로 조합해 반환
```

그림이 말하는 것이 BFF의 전부다. **비싼 왕복(100ms) 하나를 싼 왕복(1ms 미만) 여러 개로 치환**하고, 그 여러 개를 병렬로 돌리고 캐시하고 부분 실패를 처리하는 일을 서버가 통제한다.

**대가**를 반드시 함께 말해야 한다.

- **운영할 컴포넌트가 늘어난다.** 클라이언트 종류만큼 BFF가 생기므로, 배포·모니터링·온콜 대상이 그 수만큼 는다.
- **화면이 늘면 엔드포인트가 는다.** BFF는 화면 단위 계약이라, 화면 추가가 곧 엔드포인트 추가다. 유지보수 대상이 화면 수에 비례해 자란다.
- **도메인 로직이 새어 들어가면 새로운 모놀리스가 된다.** 조합만 하기로 했던 BFF에 "이 조건이면 할인율을 이렇게"가 하나씩 들어오기 시작하면, 모든 팀의 변경이 그 한 곳의 배포에 줄을 서게 된다 — MSA로 풀었던 문제가 되돌아온다. 이 경로와 방어책은 `14-gateway-vs-service-responsibility-boundary.md`에서 자세히 다룬다.
- **소유권을 정해야 한다.** BFF가 프론트 팀 것인지 백엔드 팀 것인지 합의되지 않으면, 화면 요구가 바뀔 때마다 팀 간 협상이 붙는다. 통상은 그 화면을 만드는 클라이언트 팀이 소유하는 편이 낫다.

그래서 **팀 규모가 작고 클라이언트가 하나면 2-1(목록 DTO 확장)로 충분한 경우가 대부분**이다. 문제 크기에 비해 큰 도구를 먼저 꺼내지 않는 것도 답변의 일부다.

### 2-5. 선택 기준 요약 — 무엇을 대가로 무엇을 얻는가

각 처방이 무엇을 주고 무엇을 받는지를 축으로 세우면 이렇게 정리된다.

| 처방 | 클라이언트↔서버 왕복 | 응답 크기 | 캐시 효율 | 서버 복잡도 | 계약 안정성 |
|---|---|---|---|---|---|
| 2-1 목록 DTO 확장 | 1회로 감소 | 증가 (안 쓰는 필드도 모두 전송) | 좋음 (URL 하나 = 캐시 키 하나) | 낮음 (조인 하나) | 낮아짐 (화면 요구가 계약에 박힘) |
| 2-2 벌크 조회 | N회 → 1회 | 요청한 만큼만 | 나쁨 (id 조합마다 캐시 키가 달라 재사용 안 됨) | 낮음 | 높음 (단건 API와 계약이 동일) |
| 2-3 expand | 원하는 클라이언트만 감소 | 클라이언트가 선택 | 나쁨 (파라미터 조합만큼 캐시 키 분화) | 중간 (조합별 조회 경로) | 높음 (기본 응답은 그대로) |
| 2-4 BFF | 1회로 감소 | 화면에 딱 맞음 (최소) | 나쁨 (화면 전용이라 공유 캐시 이득 적음) | 높음 (컴포넌트 추가) | 높음 (범용 API는 손대지 않음) |

읽는 법은 이렇다. **왕복을 줄이는 값은 대체로 캐시 효율과 계약 안정성 중 하나로 지불한다.** 2-1은 계약 안정성을 내주고 캐시를 지키며, 2-3·2-4는 계약을 지키는 대신 캐시와 복잡도를 내준다. 공짜인 칸이 없다는 것이 이 표의 요점이다.

상황별 첫 선택은 이렇다.

| 상황 | 처방 |
|---|---|
| 목록 화면이 상세를 N번 부른다 | 2-1 목록 DTO에 요약 필드 포함 |
| 클라이언트가 id 집합을 이미 쥐고 있다 (장바구니 등) | 2-2 벌크 조회 |
| 공개 API라 소비자 요구가 제각각이다 | 2-3 expand (깊이 1, 화이트리스트) |
| 클라이언트가 여럿이고 화면 조합이 서로 다르다 | 2-4 BFF/aggregation |

## 3. 실무 흐름 — 진단부터 조율까지

### 3-1. 진단 — 서버 메트릭에 답이 없다

증상은 보통 이렇게 온다. **"앱이 느리다는 VOC가 오는데 서버 APM은 전부 초록색"**이다. 1-6에서 본 이유 때문이다 — 서버 응답 시간(p99 50ms)만 보면 문제가 없고, 화면 완성 시간은 서버 메트릭에 없다.

그래서 진단은 클라이언트 관점에서 한다.

- 앱·브라우저의 네트워크 탭이나 액세스 로그에서 **한 화면 진입이 만드는 요청 수**를 센다. 같은 사용자·짧은 시간 창에 `GET /orders/{id}`가 연달아 20건 찍히면 chatty의 서명이다.
- 게이트웨이 메트릭에서 "화면당 요청 수 × RTT"로 체감 시간을 추정한다. 1-5의 표가 그 계산식이다.
- 가능하면 **실사용자 측정(RUM)**으로 화면 완성 시간을 직접 잰다. 추정이 아니라 실측이 있으면 조율(3-2) 논의가 훨씬 빨리 끝난다.

### 3-2. 조율 — 이 문항의 진짜 주제

chatty API는 백엔드 혼자 만든 문제도, 혼자 고칠 문제도 아니다. 클라이언트 팀은 "API가 잘게 쪼개져 있어서"라고 하고 백엔드 팀은 "필요한 조합을 안 알려줘서"라고 한다. 양쪽 다 맞는 말이라 기술만으로는 끝나지 않는다.

실무 해법은 **화면 설계 단계에서 "이 화면은 API 몇 번으로 그려지는가"를 리뷰 항목으로 두는 것**이다. 그리고 화면당 호출 수 예산(예: 초기 렌더링 3회 이내)을 팀 계약으로 합의한다. 2장의 기술 선택은 그 계약을 지키는 수단이지, 그 자체가 목표가 아니다.

예산이라는 형태가 중요한 이유가 있다. **"호출 수를 줄이자"는 합의는 지켜지지 않지만 "3회 이내"는 리뷰에서 위반이 눈에 보인다.** 숫자가 없으면 매번 개별 협상이 된다.

### 3-3. 역방향 함정 — chunky로 너무 멀리 가기

chatty를 피하려고 **모든 것을 한 응답에 담은 비대한 API**(god endpoint, "전지전능 엔드포인트")로 가면 반대편 비용을 낸다.

- 응답 크기가 커져 모바일 데이터와 파싱 시간을 낭비한다.
- 어느 화면도 안 쓰는 필드까지 매번 조회하므로 DB 부하가 늘어난다.
- 응답 안에 변경 주기가 다른 데이터가 섞여 캐시를 걸 수 없다 — 1초마다 바뀌는 재고와 한 달에 한 번 바뀌는 상품 설명이 한 응답에 있으면 TTL을 짧은 쪽에 맞춰야 한다.
- 모든 화면이 그 하나의 응답에 결합돼, 한 화면 때문에 바꾼 필드가 전 화면의 회귀 테스트 대상이 된다.

1-1에서 말했듯 **chatty ↔ chunky는 스펙트럼**이고, 기준은 양 끝이 아니라 **"화면이 실제로 그리는 데이터를 한 번에"**라는 가운데 지점이다.

## 4. 꼬리질문 대비 포인트

### "벌크 조회에서 id가 수백 개면 GET URL 길이 제한에 걸리지 않나요?"

먼저 사실관계부터 정확히 짚는 것이 좋다. **HTTP 스펙에는 URL 길이 상한이 없다.** 실질적 한계를 정하는 것은 브라우저·서버·프록시의 구현이다. 그래서 "URL은 몇 자까지"라는 숫자를 스펙인 양 말하면 오히려 감점이다.

실제로 걸리는 지점은 이런 것들이다.

| 주체 | 실질 한계 | 초과 시 |
|---|---|---|
| RFC 7230 권고 | 서버는 최소 8,000 옥텟의 요청 라인을 지원할 것 (하한 권고이지 상한이 아니다) | — |
| Nginx | `large_client_header_buffers` 기본값 `4 8k` → 요청 라인이 8KB를 넘으면 거절 | `414 URI Too Long` |
| Tomcat | `maxHttpHeaderSize` 기본 8,192바이트 | `400` 또는 `414` |
| 통념상 안전선 | 2,000자 안팎 (옛 IE의 2,083자 제약에서 굳어진 관행) | — |

**직접 계산해 보면 감이 잡힌다.** 숫자 id가 8자리면 콤마 포함 9바이트이므로, 2,000자 안전선에는 약 220개, Nginx 기본 8KB에는 약 900개가 들어간다. 그런데 **id가 UUID(36자 + 콤마 = 37바이트)면 이야기가 달라진다** — 2,000자에 겨우 54개, 8KB에도 221개다. 즉 "수백 개면 걸리나"의 답은 **id의 형태에 달렸다.** 숫자 id면 대체로 안 걸리고, UUID면 수십 개에서 이미 안전선을 넘는다.

실무 선택지는 둘이다. ① 개수 상한을 안전선 안으로 낮게 잡아 GET을 유지하고, 초과분은 클라이언트가 나눠 부르게 한다. ② `POST /products:batchGet`처럼 조회 의도를 이름에 드러낸 POST + 본문으로 받는다.

②의 대가는 **캐시를 포기하는 것**이다. POST 응답은 HTTP 시맨틱상 중간 캐시가 재사용하지 않는다. "REST 순수성 대 실용"의 절충임을 인지하고, 문서에 조회 전용임을 명시하는 것이 포인트다.

### "expand 파라미터를 계속 허용하다 보면 어떤 문제가 생기나요?"

허용 키를 화이트리스트로 묶지 않으면 **조합 수가 폭발해 성능을 예측할 수 없는 API**가 된다. expand 하나하나가 조인 또는 내부 호출이므로, 클라이언트가 비싼 조합을 마음대로 만들 수 있게 되는 셈이다. 어제까지 잘 돌던 API가 오늘 어떤 클라이언트가 `expand`를 세 개 붙인 순간 DB를 눕힐 수 있다.

중첩 expand까지 열면 사실상 쿼리 언어를 재발명하는 셈이다. 그 지경이면 GraphQL 같은 검증된 도구를 검토하는 게 낫다.

실무 선은 셋이다. **깊이 1까지만, 허용 키는 화이트리스트로, expand별 비용을 문서화**한다. 여기에 expand 조합별 응답 시간을 별도 메트릭으로 태깅해 두면 "누가 비싼 조합을 쓰는지"를 사후가 아니라 상시로 볼 수 있다.

### "HTTP/2를 쓰면 멀티플렉싱 덕분에 chatty는 문제가 아니게 되지 않나요?"

절반만 맞다. **HTTP/2가 푸는 것은 커넥션 수 제약 하나뿐이다.**

1-5의 표를 다시 보면 답이 나온다. HTTP/1.1에서 5 왕복이던 것이 HTTP/2에서 2 왕복이 되지만, **서버가 받는 요청은 세 경우 모두 21건으로 동일하다.** 남는 비용은 이렇다.

- **요청당 고정 비용이 그대로 N배다.** 인증 토큰 검증, rate limit 카운팅, 로깅, 트레이싱 컨텍스트 생성, 컨트롤러 진입까지의 필터 체인 — 이 전부를 21번 낸다.
- **서버 처리와 직렬화가 N배다.** 응답 JSON 21개를 만들고 21번 직렬화한다.
- **tail latency는 오히려 더 드러난다.** 21건이 동시에 나가면 그중 하나가 p99에 걸릴 확률은 1 − 0.99²¹ ≈ 19%다(1-5). 병렬은 이 확률을 줄이지 않는다.
- **서버에도 동시 스트림 상한이 있다.** HTTP/2는 커넥션당 동시 스트림 수를 서버가 정해 알려주며(Nginx 기본값은 128), 상한을 넘는 요청은 대기한다. 무한 병렬이 아니다.
- **동시 21건이 서버 스레드 풀·커넥션 풀에 한꺼번에 꽂힌다.** 사용자 100명이 같은 화면에 들어오면 2,100건이 된다. 왕복이 짧아진 만큼 부하는 더 뾰족해진다.

정리하면 **"HTTP/2는 chatty의 지연을 완화하지만 chatty의 비용을 없애지는 않는다."** 그리고 프로토콜은 우리가 통제할 수 없는 클라이언트 환경에 달려 있는 반면, 응답 구조는 우리가 정할 수 있다 — 통제 가능한 쪽부터 고치는 것이 순서다.

### "그냥 GraphQL을 도입하면 해결되는 것 아닌가요?"

GraphQL은 클라이언트가 필요한 필드와 연관을 쿼리로 선언해 한 번에 받는 모델이라, chatty 문제의 정면 해법이 맞다. 인정하고 시작하는 것이 좋다.

하지만 비용이 따라온다.

- **N+1이 서버 내부로 이동한다.** 리졸버(필드마다 값을 채우는 함수)가 순진하게 구현되면 필드 하나당 쿼리 하나가 나간다. DataLoader 같은 배칭 계층이 사실상 필수다 — 즉 **문제를 없앤 게 아니라 우리 쪽으로 옮긴 것**이다.
- **비싼 쿼리를 클라이언트가 만들 수 있다.** 쿼리 깊이·복잡도 제한이 없으면 한 줄짜리 쿼리가 DB를 눕힌다.
- **HTTP 캐싱과 모니터링 관행이 REST와 다르다.** 단일 엔드포인트에 POST로 쿼리를 보내는 형태라 URL 기반 캐시·상태 코드 기반 알람이 그대로 통하지 않는다. 운영 체계를 다시 세워야 한다.

판단 기준은 규모다. **"화면 몇 개가 chatty한 수준"이면 2-1~2-2로 충분하고**, 클라이언트 주도 조회 요구가 광범위하고 화면이 계속 늘어나는 조직일 때 도입할 도구다. 문제 크기와 도구 크기를 맞추는 판단을 보여 주는 게 핵심이다. (자세한 비교는 `11-rest-vs-graphql-vs-grpc.md`)

### "목록 응답에 필드를 계속 추가하다 보면 목록 API가 비대해지는데, 어디까지 허용하나요?" (시니어 변별 포인트)

목록 DTO 확장(2-1)의 **누적 비용**을 아는지 묻는 질문이다. 한 번의 추가는 싸지만, 추가가 쌓이면 세 가지가 동시에 나빠진다. 화면 A를 위해 넣은 필드를 화면 B는 안 쓰는데도 전송 비용은 모두가 내고, 필드 하나하나가 조인이라 목록 쿼리가 점점 무거워지며, 응답 안의 데이터마다 변경 주기가 달라 캐시 TTL을 가장 짧은 것에 맞춰야 한다.

관리 원칙은 셋이다.

① 목록 DTO는 **"이 목록을 그리는 대표 화면"의 계약**으로 정의하고, 화면별 요구가 갈라지기 시작하면 필드를 더 넣는 대신 **expand나 BFF로 분기**한다. 갈라지는 시점이 곧 2-3·2-4로 옮겨갈 신호다.

② 무거운 필드(집계값, 대용량 텍스트, 다른 서비스 호출이 필요한 값)는 목록에 넣지 않고 상세로 민다.

③ **추가 전에 "누가 쓰는가"를 확인한다.** 이유는 비대칭이다 — **필드 추가는 하위 호환 변경이라 자유롭지만, 제거는 파괴적 변경이라 소비자 전수 확인과 마이그레이션 절차가 필요하다.** 넣기는 쉽고 빼기는 어려우므로, 판단의 무게는 넣는 쪽에 실려야 한다. (이 비대칭의 전체 그림은 `08-backward-compatible-api-changes.md`)

### "화면당 호출 수를 줄였는데도 느리면 다음은 무엇을 보나요?"

병목을 옮겨 가며 잡는 **순서 감각**을 보는 질문이다. "호출 수 → 직렬성 → 크기 → 캐시 → 프로토콜" 순으로 답한다.

① **직렬 의존 체인.** A의 응답을 받아야 B를 부를 수 있는 구조면 호출 수가 적어도 RTT가 그대로 더해진다. 호출 3번이라도 순차면 3 RTT다. API 간 의존을 끊어 병렬화하거나, 아예 서버에서 조합해 1회로 만든다.

② **응답 크기.** 왕복 횟수를 다 줄였는데도 느리면 이제 전송 시간이 병목이다. 압축(gzip·brotli), 안 쓰는 필드 제거, 이미지 URL의 해상도 분기를 본다.

③ **캐싱.** 상품 정보처럼 잘 안 변하는 리소스는 `ETag`·`Cache-Control`로 조건부 요청을 만들면 왕복은 남아도 본문 전송이 사라진다(304).

④ **프로토콜.** HTTP/2·HTTP/3 적용 여부, keep-alive와 커넥션 재사용 여부를 본다. 여기는 앞의 셋을 다 하고 나서 볼 곳이지, 먼저 손댈 곳이 아니다.

## 한 줄 요약

chatty API는 JPA에서 익숙한 N+1이 애플리케이션↔DB(1ms)에서 클라이언트↔서버(수십~수백 ms)로 자리를 옮긴 것이라 호출 수가 곧 체감 속도가 되는 문제이고, RTT는 서버 성능으로 줄일 수 없으니 처방은 오직 왕복 횟수를 줄여 서버 안의 싼 조합으로 치환하는 것 — **목록 DTO에 화면 요약 필드 포함, 상한·누락 계약을 갖춘 벌크 조회, 깊이 1로 제한한 expand, 클라이언트가 여럿이면 BFF** — 이며, 병렬화나 HTTP/2 멀티플렉싱은 왕복 시간만 줄일 뿐 요청 수와 tail latency는 그대로 남기므로, 본질은 리소스별 단순함(백엔드 편의)과 화면당 한 번(클라이언트 효율)의 긴장을 "화면당 호출 수 예산"이라는 팀 계약으로 조율하는 일이다.
