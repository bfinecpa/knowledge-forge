# Chatty API 개선 — HTTP 왕복은 공짜가 아니다, N+1은 네트워크에서도 일어난다

> 핵심 관전 포인트: **목록 1회 + 상세 N회는 DB N+1 문제의 HTTP 판이다 —
> 모바일처럼 왕복 지연(RTT)이 큰 환경에서는 호출 수가 곧 체감 속도라서,
> 항목 20개 화면이 21번의 왕복이 되면 아무리 서버가 빨라도 화면은 느리다.
> 개선은 "왕복 수를 줄이는" 방향으로 층위별 선택지가 있다: ① 목록 응답에
> 화면이 필요로 하는 요약 필드를 포함(목록 DTO를 화면 요구에 맞춰 확장)
> ② 여러 건을 한 번에 받는 벌크 조회(`?ids=1,2,3`) ③ 연관 리소스를 같은
> 응답에 실어 주는 expand/embed 파라미터 ④ 화면 단위로 여러 백엔드
> 호출을 묶어 주는 aggregation/BFF 계층. 이 문제의 본질은 "리소스별로
> 단순한 API"라는 백엔드 편의와 "화면당 한 번의 호출"이라는 클라이언트
> 효율 사이의 긴장이고, 어느 층에서 조율할지 정하는 게 설계다.**

---

## 0. 질문 + 의도

**질문**: "목록 조회 + 상세 N건 조회로 인한 API 호출 폭증(chatty API)을
어떻게 개선하나요?"

**출제 의도**: 모바일 환경(높은 왕복 지연)에서 API 호출 수가 곧 체감
속도다. 백엔드 편의(리소스별 단순 API)와 클라이언트 효율의 긴장을
인식하고 조율해본 경험을 본다 — "서버 응답은 50ms인데 왜 화면이 느리냐"
는 상황에서 원인을 네트워크 왕복 구조로 진단할 수 있는지가 관전 포인트다.

## 1. 왜 생기고 왜 문제인가 — 리소스 지향 설계의 자연스러운 부작용

### 1-1. 발생 경로 — 잘 만든 REST API가 chatty를 만든다

리소스 중심으로 정직하게 설계하면 이렇게 된다:

```text
GET /orders            → 주문 id 목록          (백엔드 입장: 깔끔한 단일 책임)
GET /orders/1          → 주문 1 상세
GET /orders/2          → 주문 2 상세
...
GET /users/42          → 주문자 이름 표시용
GET /products/77       → 상품 썸네일 표시용
```

각 API는 단순하고 재사용 가능하고 캐시하기 좋다 — **리소스별로는 전부
옳은 설계다.** 문제는 화면이 리소스 단위가 아니라 **조합 단위**로
그려진다는 것. "주문 목록 화면"은 주문 + 주문자 이름 + 상품 썸네일을 한
번에 원하는데, 리소스별 API만 있으면 클라이언트가 그 조합을 왕복으로
지불한다. DB에서 목록 쿼리 1번 + 행마다 추가 쿼리 N번을 날리는 N+1과
구조가 정확히 같다 — **위치가 애플리케이션↔DB에서 클라이언트↔서버로
옮겨 왔을 뿐이다.**

### 1-2. 비용 계산 — RTT가 지배한다

서버 처리 시간이 아니라 왕복 지연이 지배 변수다:

```text
모바일 LTE RTT ≈ 100~300ms 가정, 항목 20개 화면

순차 호출:   (1 + 20) × 300ms = 6.3초        ← 화면이 "느리다"의 정체
병렬 호출:   브라우저/OS의 동시 커넥션 제한, 서버 순간 부하 20배,
             가장 느린 응답이 화면 완성 시간 (tail latency)
```

병렬로 쏘면 시간은 줄지만 **요청 수는 그대로**다 — 서버 입장에서는 화면
하나 그리는 데 21 RPS를 쓰는 클라이언트이고, 사용자가 스크롤하면 이게
계속 반복된다. 게이트웨이·인증·로깅 등 요청당 고정 비용도 21배로 낸다.
"HTTP/2 멀티플렉싱이 있으니 괜찮다"는 반쪽 답이다 — 커넥션 수 문제는
줄여 주지만 요청당 처리 비용과 tail latency는 남는다.

## 2. 개선 전략 — 층위별 선택지와 각각의 대가

면접에서는 이 네 개를 목록으로 꺼내고, 상황에 맞는 선택 기준을 붙인다.

### 2-1. 목록 응답에 화면이 원하는 필드를 포함한다 — 가장 흔한 정답

"목록 API가 id만 주니까 상세를 N번 부른다"가 원인이면, **목록 DTO를 화면
요구에 맞춰 설계**하는 게 첫 번째 처방이다. 목록 응답은 엔티티의
축소판이 아니라 **화면 계약**이다.

```json
// ❌ before: 목록이 id 목록에 가깝다 → 클라이언트가 상세 N회 호출
GET /orders
[ { "id": 1 }, { "id": 2 }, ... ]

// ✅ after: 목록 항목에 화면이 그리는 요약 필드를 포함
GET /orders
{
  "items": [
    {
      "id": 1,
      "orderNumber": "ORD-20260830-001",
      "status": "SHIPPED",
      "ordererName": "김철수",              // users 조인 결과
      "firstProductThumbnail": "https://...", // products 조인 결과
      "totalAmount": 45000,
      "orderedAt": "2026-08-30T12:34:56Z"
    }
  ],
  "nextCursor": "..."
}
```

서버는 이 조합을 DB 조인(또는 read model) 한 번으로 만든다 — **네트워크
N+1을 서버 안의 조인으로 옮기는 것**이고, 서버↔DB는 같은 데이터센터라
왕복이 수백 배 싸다. 대가: 목록 API가 특정 화면에 결합되고, 화면 요구가
늘 때마다 필드가 자란다(→ 꼬리질문 §4-5). 상세 API는 "목록에 없는 무거운
필드(전체 배송 이력, 결제 수단 등)"를 주는 역할로 분리해 남긴다.

### 2-2. 벌크 조회 — "N번 부를 것을 1번에"

목록과 무관하게 "id 여러 개의 상세"가 필요한 경우(장바구니의 상품들,
알림에 붙는 발신자 프로필들)의 처방. 단건 API 옆에 복수 조회를 추가한다.

```text
❌ before: 클라이언트 루프
for id in [1, 2, 3, ..., 20]:
    GET /products/{id}            → 20 왕복

✅ after: 벌크 조회 1회
GET /products?ids=1,2,3,...,20    → 1 왕복
```

설계 디테일이 변별 포인트다:

- **개수 상한을 계약에 명시**한다(예: 최대 100개). 상한 없는 벌크는
  "id 10만 개" 요청이 되어 DB `IN` 절 폭발과 응답 비대를 부른다.
- **일부 id가 없을 때의 계약**을 정한다 — 있는 것만 돌려주고 없는 건
  생략인지, `found`/`missing`을 구분해 주는지. 정하지 않으면 클라이언트
  마다 해석이 갈린다.
- id가 수백 개면 URL 길이 한계에 걸린다 — 조회여도 `POST /products:batchGet`
  같은 형태로 본문에 담는 절충이 실무 관행이다(→ 꼬리질문 §4-1).
- **(가산점 포인트)** 벌크 API의 서버 구현이 내부에서 단건 조회를
  루프로 돌면 네트워크 N+1을 서버 안 N+1로 옮겼을 뿐이다 — 저장소
  계층까지 `WHERE id IN (...)` 한 방으로 내려가야 개선이 완성된다.
  MSA면 내부 서비스 간 호출도 벌크 API로 뚫려 있어야 한다.

### 2-3. expand/embed 파라미터 — 연관 리소스를 옵션으로 실어 주기

리소스 API의 일반성을 유지하면서, 원하는 클라이언트에게만 연관 데이터를
함께 준다. Stripe 등 공개 API들이 쓰는 패턴이다.

```text
GET /orders/1                     → 주문만 (user 는 id 참조로)
GET /orders/1?expand=user,items   → 주문 + 주문자 객체 + 항목들을 한 응답에
```

```json
{
  "id": 1,
  "user": { "id": 42, "name": "김철수" },   // expand=user 일 때 객체로
  "items": [ ... ]
}
```

대가: ① 서버 구현 복잡도 — expand 조합마다 조회 경로가 갈리고, 허용
expand 키를 화이트리스트로 제한하지 않으면 "무엇이든 조인해 달라"는 API가
된다 ② 응답 형태가 파라미터에 따라 변해 캐싱 키와 문서화가 복잡해진다
③ 중첩 expand(`expand=items.product.seller`)를 허용하기 시작하면 사실상
GraphQL을 재발명하게 된다 — 깊이 1까지만 허용하는 것이 현실적 선이다.

### 2-4. Aggregation / BFF — 화면 단위 API를 담당하는 계층을 둔다

클라이언트 종류가 여럿이고(모바일/웹/파트너) 화면마다 필요한 조합이
다르면, 개별 리소스 API 위에 **화면 지향 API를 만드는 계층**(BFF —
Backend For Frontend)을 둔다.

```text
[모바일 앱] → GET /bff/mobile/order-list-screen   → BFF 가 내부에서
                                                     orders + users + products 를
[내부]        orders-api   users-api   products-api  병렬 호출해 화면 DTO 로 조합
```

- 리소스 API는 순수하게 유지하고, "화면 조합"이라는 관심사를 BFF가
  가져간다. 클라이언트↔서버 왕복은 1회, 조합 왕복은 데이터센터 내부의
  싼 왕복으로 치환되고 병렬화·캐싱·부분 실패 처리를 서버가 통제한다.
- 대가: 운영할 컴포넌트가 하나 늘고, BFF가 프론트 팀과 백엔드 팀 중 누구
  소유인지 조직적 합의가 필요하며, 화면이 늘 때마다 BFF 엔드포인트도
  는다. **팀 규모가 작고 클라이언트가 하나면 §2-1(목록 DTO 확장)로
  충분한 경우가 대부분**이다 — 문제 크기에 비해 큰 도구를 먼저 꺼내지
  않는 것도 답변의 일부다.

### 2-5. 선택 기준 요약

| 상황 | 처방 |
|---|---|
| 목록 화면이 상세를 N번 부른다 | §2-1 목록 DTO에 요약 필드 포함 |
| id 집합의 상세가 필요 (장바구니 등) | §2-2 벌크 조회 |
| 공개 API, 클라이언트 요구가 다양 | §2-3 expand (깊이 제한) |
| 클라이언트 여럿 + 화면 조합 복잡 | §2-4 BFF/aggregation |

## 3. 실무 흐름 — 진단부터 조율까지

증상은 보통 이렇게 온다: "앱이 느리다는 VOC가 오는데 서버 APM은 전부
초록색"이다. 서버 응답 시간(p99 50ms)만 보면 문제가 없다 — **화면 완성
시간은 서버 메트릭에 없기 때문**이다. 진단은 클라이언트 관점에서 한다:

- 앱/브라우저의 네트워크 탭 또는 액세스 로그에서 **한 화면 진입이 만드는
  요청 수**를 센다. 같은 사용자·짧은 시간 창의 `GET /orders/{id}` 연타가
  로그에 폭포처럼 찍히면 chatty의 서명이다.
- 게이트웨이 메트릭에서 "화면당 요청 수 × RTT"로 체감 시간을 추정한다.

그다음이 이 문항의 진짜 주제인 **조율**이다. chatty API는 백엔드 혼자
만든 문제도, 혼자 고칠 문제도 아니다 — 클라이언트 팀은 "API가 잘게
쪼개져 있어서"라고 하고 백엔드 팀은 "요구를 안 줘서"라고 한다. 실무
해법은 **화면 설계 단계에서 "이 화면은 API 몇 번으로 그려지는가"를
리뷰 항목으로 두고**, 화면당 호출 수 예산(예: 초기 렌더링 3회 이내)을
팀 계약으로 합의하는 것이다. 기술 선택(§2)은 그 계약을 지키는 수단이다.

역방향 함정도 짚어 둔다 — chatty를 피하려고 **모든 것을 한 응답에 담은
비대한 API**(god endpoint)로 가면, 이번엔 응답 크기·불필요한 데이터
전송·캐시 불가·모든 화면의 결합이라는 반대편 비용을 낸다. chatty ↔
chunky는 스펙트럼이고, 기준은 "**화면이 실제로 그리는 데이터**를 한
번에"다.

## 4. 꼬리질문 대비 포인트

### "벌크 조회에서 id가 수백 개면 GET URL 길이 제한에 걸리지 않나요?"

걸린다 — 서버·프록시마다 URL 길이 상한이 있어(수 KB 수준) id 수백 개면
초과할 수 있다. 실무 선택지는 ① 개수 상한을 낮게 잡아 GET을 유지하고
초과분은 클라이언트가 나눠 부르게 하거나 ② `POST /products:batchGet`
처럼 조회 의도를 이름에 드러낸 POST + 본문으로 받는다. POST는 HTTP
시맨틱상 캐시가 안 되는 대가가 있어, "REST 순수성 vs 실용"의 절충임을
인지하고 계약(문서)에 조회 전용임을 명시하는 것이 포인트다.

### "expand 파라미터를 계속 허용하다 보면 어떤 문제가 생기나요?"

허용 키를 화이트리스트로 묶지 않으면 조합 수가 폭발해 성능을 예측할 수
없는 API가 된다 — expand 하나하나가 조인 또는 내부 호출이라, 클라이언트가
비싼 조합을 마음대로 만들 수 있게 되는 것이다. 중첩 expand까지 열면
사실상 쿼리 언어를 재발명하는 셈이라, 그 지경이면 GraphQL 같은 검증된
도구를 검토하는 게 낫다. 실무 선은 "깊이 1, 화이트리스트, expand별 비용을
문서화"다.

### "그냥 GraphQL을 도입하면 해결되는 것 아닌가요?"

GraphQL은 클라이언트가 필요한 필드·연관을 선언해 한 번에 받는 모델이라
chatty 문제의 정면 해법이 맞다. 하지만 비용이 따라온다 — ① 서버의
리졸버가 순진하면 **N+1이 서버 내부로 이동**할 뿐이라 DataLoader 같은
배칭이 필수 ② 쿼리 깊이·복잡도 제한이 없으면 클라이언트가 비싼 쿼리를
만들 수 있음 ③ HTTP 캐싱·모니터링 관행이 REST와 달라 운영 체계를 다시
세워야 한다. "화면 몇 개가 chatty한 수준"이면 §2-1~2로 충분하고,
클라이언트 주도 조회 요구가 광범위할 때 도입할 도구다 — 문제 크기와
도구 크기를 맞추는 판단을 보여 주는 게 핵심이다.

### "목록 응답에 필드를 계속 추가하다 보면 목록 API가 비대해지는데, 어디까지 허용하나요?" (시니어 변별 포인트)

목록 DTO 확장(§2-1)의 누적 비용을 아는지 묻는 질문이다. 화면 A를 위해
추가한 필드를 화면 B는 안 쓰는데도 전송·조회 비용은 모두가 내고, 필드
하나하나가 조인이라 목록 쿼리가 점점 무거워진다. 관리 원칙: ① 목록
DTO는 "이 목록을 그리는 대표 화면"의 계약으로 정의하고, 화면별 요구가
갈라지기 시작하면 필드 추가가 아니라 **화면별 응답(BFF) 또는 expand로
분기**한다 ② 무거운 필드(집계, 대용량 텍스트)는 목록에 넣지 않고 상세로
민다 ③ 한 번 내보낸 필드는 하위 호환 때문에 빼기 어려우므로 추가 전에
"누가 쓰는가"를 확인한다 — **필드 추가는 싸 보이지만 제거는 파괴적
변경**이라는 비대칭이 판단 기준이다.

### "화면당 호출 수를 줄였는데도 느리면 다음은 무엇을 보나요?"

호출 수 다음 변수는 ① 직렬 의존 체인 — A 응답을 받아야 B를 부를 수
있는 구조면 호출 수가 적어도 RTT가 더해진다(병렬화 가능하게 API 의존을
끊거나 서버에서 조합) ② 응답 크기 — 압축(gzip), 불필요 필드 제거
③ 캐싱 — 변하지 않는 리소스(상품 정보 등)의 HTTP 캐시/ETag ④ 프로토콜 —
HTTP/2 멀티플렉싱, keep-alive 여부. "호출 수 → 직렬성 → 크기 → 캐시"
순서로 병목을 옮겨 가며 잡는다는 순서 감각을 보여 준다.

## 한 줄 요약

chatty API는 DB N+1의 네트워크 판이라 RTT가 큰 모바일에서 호출 수가 곧
체감 속도가 되는 문제이고, 처방은 왕복을 서버 안의 싼 조합으로 치환하는
것 — **목록 DTO에 화면 요약 필드 포함, 벌크 조회(상한·누락 계약 포함),
깊이 제한한 expand, 규모가 되면 BFF** — 이며, 본질은 리소스별 단순함
(백엔드 편의)과 화면당 한 번(클라이언트 효율) 사이의 긴장을 "화면당
호출 수 예산"이라는 팀 계약으로 조율하는 일이다.
