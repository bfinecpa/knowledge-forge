# API 문서-구현 동기화 — 문서가 거짓말하지 않게 만드는 체계

> 핵심 관전 포인트: **문서-구현 불일치의 근본 원인은 문서가 "검증되지 않는
> 별도 산출물"이라는 데 있다. 해법은 문서를 검증 루프 안에 넣는 것 —
> ① Swagger(springdoc) 어노테이션은 코드 옆에 문서를 두지만 어노테이션
> 자체는 아무도 검증하지 않아 여전히 거짓말할 수 있고, ② Spring REST Docs는
> 테스트가 통과해야만 문서 조각이 생성되므로 "문서에 적힌 요청/응답 =
> 실제로 동작 검증된 요청/응답"이 강제된다. 정확성이 계약 수준으로 중요하면
> REST Docs(또는 스펙 우선 + CI 검증), 내부용 빠른 탐색이 목적이면
> Swagger UI — 둘을 결합(테스트에서 OpenAPI 생성)하는 절충도 있다.**

---

## 0. 질문 + 의도

**질문**: "API 문서와 실제 구현의 불일치를 어떻게 방지하나요?
(Swagger 어노테이션 vs Spring REST Docs)"

**출제 의도**: 문서가 한 번 거짓말하면 아무도 안 믿게 되고, 그때부터 협업은
슬랙 질문으로 회귀한다. 테스트에서 문서를 생성(REST Docs)하거나 계약을
우선하는 접근을 아는지 — 문서를 신뢰 가능한 산출물로 관리하는 체계를 본다.

## 1. 문제의 구조 — 문서는 왜 반드시 낡는가

불일치는 게으름이 아니라 **구조**의 문제다. 문서와 코드가 별도 산출물이면:

- 코드는 컴파일러·테스트가 검증하지만, **문서는 아무도 검증하지 않는다.**
- 급한 수정(hotfix)일수록 문서 갱신은 생략된다 — 즉 가장 중요한 변경일수록
  문서가 먼저 낡는다.
- 그리고 문서의 신뢰는 비대칭이다. 한 번이라도 문서대로 했는데 400이 떨어진
  경험을 하면, 소비자는 그 뒤로 **문서를 안 보고 담당자에게 물어본다.**
  문서의 가치는 "최신인가"가 아니라 "믿을 수 있는가"이고, 이건 0 아니면 1이다.

따라서 질문의 진짜 답은 "문서를 부지런히 고친다"가 아니라
**"문서가 틀리면 빌드가 깨지게 만든다"** — 검증 루프에 문서를 편입시키는
것이다.

## 2. 두 접근의 비교 — 어노테이션 기반 vs 테스트 기반

### ① Swagger / springdoc-openapi — 코드에서 문서를 추출

컨트롤러의 어노테이션과 타입 정보를 스캔해 OpenAPI 스펙과 Swagger UI를
자동 생성한다.

```java
@Operation(summary = "주문 조회", description = "주문 상세를 반환한다")
@ApiResponse(responseCode = "200", description = "조회 성공")
@GetMapping("/orders/{id}")
public OrderResponse getOrder(@PathVariable Long id) { ... }
```

- **강점**: 진입 장벽이 낮고, URL·메서드·파라미터 타입 같은 **구조적 사실은
  코드에서 직접 추출되므로 저절로 정확**하다. Swagger UI의 try-it-out으로
  바로 호출해볼 수 있어 탐색·QA·프론트 협업에 편하다.
- **약점**: 정작 불일치가 자주 나는 부분 — **에러 응답, 제약 조건, 필드 의미,
  예제 값** — 은 어노테이션에 손으로 적는 서술이고, 이 서술은 컴파일도
  테스트도 검증하지 않는다. 즉 "문서가 코드 옆에 있을 뿐, 검증되지 않는
  별도 산출물"이라는 구조 문제가 그대로 남는다.

```java
// 어노테이션 기반 문서의 전형적 거짓말:
@ApiResponse(responseCode = "404", description = "주문 없음")   // 문서에는 404
@GetMapping("/orders/{id}")
public OrderResponse getOrder(@PathVariable Long id) {
    return orderService.find(id);   // 실제로는 예외 핸들러가 400을 반환하도록 바뀐 지 오래
}
// 컴파일 통과, 테스트 통과, 문서는 거짓말 — 아무도 모른다
```

부수 문제로, 문서를 풍부하게 만들수록 프로덕션 코드가 문서 어노테이션으로
뒤덮여 **비즈니스 로직의 가독성을 해친다**는 점도 있다.

### ② Spring REST Docs — 테스트에서 문서를 생성

MockMvc(또는 WebTestClient, REST Assured) 테스트가 **실제로 요청을 보내고
응답을 검증한 뒤**, 그 요청/응답으로 문서 조각(snippet)을 생성한다.
조각들을 AsciiDoc/Markdown 문서에 조립해 최종 문서를 만든다.

```java
@Test
void 주문_조회_문서화() throws Exception {
    mockMvc.perform(get("/orders/{id}", 1L))
        .andExpect(status().isOk())                       // ① 실제 동작을 검증하고
        .andDo(document("order-get",                      // ② 통과한 요청/응답으로 문서 생성
            pathParameters(
                parameterWithName("id").description("주문 ID")),
            responseFields(
                fieldWithPath("id").description("주문 ID"),
                fieldWithPath("amount").description("결제 금액(원)"),
                fieldWithPath("status").description("주문 상태"))));
}
// 응답에서 amount 필드가 사라지면? → responseFields 검증 실패 → 테스트 실패 → 빌드 실패
// 문서에 없는 필드가 응답에 추가되면? → 역시 실패 (문서 누락도 잡힌다)
```

- **강점**: **문서화가 곧 검증**이다. 문서에 적힌 모든 필드는 테스트를 통과한
  실제 응답에서 나온 것이므로 구조적으로 거짓말할 수 없다. 구현이 바뀌면
  문서 테스트가 깨져서 **문서 갱신을 잊는 것이 불가능**해진다. 프로덕션
  코드도 깨끗하게 유지된다.
- **약점**: 테스트 작성 비용이 크고(문서화할 필드를 전부 선언), try-it-out
  같은 인터랙티브 UI가 기본으로는 없으며, 문서 서술의 자유도가 낮다.
  또 "테스트가 커버하는 케이스만" 문서화되므로 테스트 문화가 약한 팀에서는
  오히려 유지가 안 된다.

### 비교 요약

| 축 | Swagger 어노테이션 | Spring REST Docs |
|---|---|---|
| 정확성 보장 | 구조는 자동, **서술은 미검증** | **테스트 통과분만 문서화 — 강제** |
| 도입/유지 비용 | 낮음 | 높음 (테스트 필수) |
| 인터랙티브 UI | Swagger UI 기본 제공 | 기본 없음 |
| 프로덕션 코드 오염 | 어노테이션 누적 | 없음 (테스트 코드에 위치) |
| 어울리는 곳 | 내부 API, 빠른 탐색·협업 | 외부 공개·파트너 API 등 계약 수준 문서 |

## 3. 절충과 확장 — 실무에서의 선택지

### 결합형: 테스트에서 OpenAPI를 생성 (가산점 포인트)

REST Docs의 "테스트로 검증된 문서"와 Swagger UI의 편의를 둘 다 원하면,
REST Docs 테스트 결과에서 **OpenAPI 스펙을 생성**하는 확장
(restdocs-api-spec 등 오픈소스)을 쓴다. 검증은 테스트가, UI는 그 스펙을
읽는 Swagger UI가 담당 — "검증된 스펙 + 인터랙티브 문서"를 동시에 얻는다.

### 스펙 우선(contract-first) 접근

코드에서 문서를 뽑는 대신 **OpenAPI 스펙을 먼저 쓰고 그것을 유일한 진실
공급원(source of truth)으로** 삼는 방법도 있다.

- 스펙에서 서버 인터페이스/클라이언트 코드를 생성하면 구현이 스펙에서
  벗어나기 어렵다. 프론트·백엔드가 스펙만 합의하면 **병렬 개발**이 가능한
  것이 큰 장점.
- CI에서 실제 응답을 스펙과 대조 검증하거나, 스펙 diff로 파괴적 변경을
  감지하는 검사를 붙이면 "스펙 = 계약"이 유지된다 (→ 08번 문서의 호환성
  검사와 연결).
- 소비자 관점을 더 강하게 반영하려면 **소비자 주도 계약 테스트(CDC —
  Spring Cloud Contract, Pact)**: 소비자가 의존하는 요청/응답을 계약으로
  등록하고 제공자 빌드에서 검증한다. "문서와 다르다"를 넘어 "소비자가 실제로
  쓰는 방식과 다르다"를 잡는다.

### 선택 기준

- **소비자가 외부(파트너·공개)** 이고 문서가 계약이면: 검증되는 문서가 필수 —
  REST Docs 또는 스펙 우선 + CI 검증.
- **소비자가 내부**이고 속도·탐색이 우선이면: springdoc + Swagger UI로 시작하되,
  에러 응답처럼 거짓말이 잦은 부분만이라도 테스트로 고정.
- 어느 쪽이든 원칙은 같다 — **사람의 성실함이 아니라 빌드 파이프라인이
  문서의 정확성을 보증하게 한다.**

## 4. 꼬리질문 대비 포인트

### "Swagger를 쓰면서 불일치를 줄이는 현실적인 방법은 없나요?"

있다. ① 서술 어노테이션 최소화 — 문서의 구조적 부분(타입, 필수 여부)은
Bean Validation(`@NotNull` 등)과 타입 시스템에서 추출되게 하고 손으로 쓰는
서술을 줄인다. ② 생성된 OpenAPI 스펙을 CI에서 스냅샷으로 관리해 의도치 않은
스펙 변화(필드 삭제 등)를 리뷰에 노출시킨다. ③ 에러 응답은
`@ControllerAdvice` 기반 공통 모델로 표준화하고 그 모델만 문서화한다.
다만 이 모두는 완화책이고, "서술이 검증되지 않는다"는 구조 자체는 REST Docs나
계약 테스트로만 해결된다고 선을 그으면 정확하다.

### "REST Docs는 테스트가 통과해야 문서가 나온다는데, 테스트를 mock으로 쓰면 그것도 거짓말 아닌가요?" (시니어 변별 포인트)

날카로운 지점이다. MockMvc + 서비스 계층 mock 조합이면 문서는 "컨트롤러
계층의 계약"까지만 보증한다 — mock이 실제 서비스와 다른 응답을 주면 문서도
같이 틀린다. 그래서 ① 문서화 테스트는 가능한 한 실제 빈을 태우는 통합
테스트(또는 슬라이스 + 신중한 stub)로 작성하고, ② 직렬화 경계(DTO)는 실제
객체를 쓰며, ③ mock을 쓰더라도 응답 DTO 타입은 실제 프로덕션 타입을 그대로
쓰게 해서 필드 구조만큼은 컴파일러가 보증하게 한다. "도구가 보증하는 범위가
어디까지인지"를 아는 것이 도구 이름을 아는 것보다 중요하다.

### "문서화 대상이 100개 API인데 REST Docs 전환 비용이 너무 크면?"

전면 전환이 아니라 **위험 기반으로 나눈다.** 외부 파트너에게 나가는 API,
결제·정산처럼 불일치 사고 비용이 큰 API부터 REST Docs/계약 테스트로 옮기고,
내부 조회성 API는 springdoc으로 유지한다. 신규 API부터 REST Docs를 기본으로
적용하는 "신규부터" 전략도 전환 비용을 분산시킨다. 도구 통일 자체가 목적이
아니라 "문서를 믿을 수 있는가"가 목적임을 놓치지 않는 답변이 좋다.

### "문서 불일치를 런타임에 감지할 수는 없나요?"

가능하다 — 게이트웨이나 필터에서 실제 요청/응답을 OpenAPI 스펙과 대조해
위반을 로깅하는 스펙 검증(validation) 계층을 둘 수 있다. 운영 트래픽으로
"스펙에 없는 필드가 나가고 있다"를 발견할 수 있어 전환기·감사에 유용하다.
다만 이건 사후 감지이므로, 빌드 시점 검증(테스트·스펙 diff)의 보완이지
대체가 아니다.

### "프론트엔드와의 협업에서는 뭐가 제일 효과적이었나요?"

스펙 우선 + 코드 생성 조합이 협업 효과가 크다 — 스펙이 합의되면 프론트는
생성된 클라이언트/mock 서버로 즉시 개발을 시작하고, 백엔드 구현은 병렬로
진행된다. 이때 스펙 변경은 반드시 PR 리뷰를 거치게 해서(스펙 파일이 저장소에
있으므로 가능) "말로 합의하고 코드는 딴판"이 되는 것을 막는다.

## 한 줄 요약

문서-구현 불일치는 성실함의 문제가 아니라 "문서가 검증 루프 밖에 있다"는
구조의 문제다 — Swagger 어노테이션은 편하지만 서술이 검증되지 않고,
Spring REST Docs는 테스트를 통과한 요청/응답만 문서가 되므로 거짓말이
구조적으로 불가능하다. 핵심 원칙은 **문서가 틀리면 빌드가 깨지게 만드는 것**,
그리고 외부 계약일수록 그 강제 수준을 높이는 것이다.
