# API 문서-구현 동기화 — 문서가 거짓말하지 않게 만드는 체계

> 핵심 관전 포인트: **문서-구현 불일치의 근본 원인은 게으름이 아니라 구조다 — 코드는 컴파일러와 테스트가 매일 검증하는데 문서는 아무도 검증하지 않으므로, 문서는 반드시 낡는다. 그래서 해법은 "부지런히 고치자"가 아니라 **문서를 검증 루프 안에 집어넣는 것**이고, 그 루프의 재료가 OpenAPI라는 규격이다. OpenAPI는 API의 경로·파라미터·응답 스키마를 사람의 문장이 아니라 기계가 읽는 YAML/JSON으로 적어 둔 규격이라, 그 파일 하나에서 문서 UI도 클라이언트 코드도 검증기도 스펙 diff도 나온다. 접근은 둘로 갈린다 — ① springdoc-openapi가 컨트롤러를 스캔해 규격을 뽑고 Swagger UI가 그것을 화면으로 그려주는 방식은 경로·메서드·타입 같은 **구조적 사실은 코드에서 추출되므로 저절로 정확**하지만 손으로 쓴 서술(에러 응답, 제약 조건, 예제 값)은 아무도 검증하지 않아 그대로 거짓말이 남고, ② Spring REST Docs는 테스트가 실제 요청을 보내고 응답을 검증해야만 문서 조각(snippet)을 뱉으므로 "문서에 적힌 것 = 검증된 것"이 강제된다. 정확성이 계약 수준이면 REST Docs 또는 스펙 우선 + CI 검증, 내부용 빠른 탐색이 목적이면 Swagger UI이며, 둘을 결합해 테스트에서 OpenAPI를 생성하는 절충도 있다. 마지막 층이 소비자 주도 계약 테스트(CDC)다 — 소비자가 "나는 이 요청에 이런 응답을 기대한다"를 계약 파일로 등록하고 제공자 빌드가 그것을 재생해 검증하므로, "문서와 다르다"를 넘어 "소비자가 실제로 쓰는 방식과 다르다"를 잡는다. 관통하는 원칙은 하나다 — 사람의 성실함이 아니라 빌드 파이프라인이 문서의 정확성을 보증하게 한다.**

---

## 0. 질문 + 의도

**질문**: "API 문서와 실제 구현의 불일치를 어떻게 방지하나요? (Swagger 어노테이션 vs Spring REST Docs)"

**출제 의도**: 문서가 한 번 거짓말하면 아무도 안 믿게 되고, 그때부터 협업은 슬랙 질문으로 회귀한다. 테스트에서 문서를 생성(REST Docs)하거나 계약을 우선하는 접근을 아는지 — 문서를 신뢰 가능한 산출물로 관리하는 체계를 본다.

## 1. 전제 지식과 문제의 구조

### 1-1. OpenAPI란 무엇인가 — 기계가 읽는 API 규격

이 문서에 나오는 "스펙 우선", "스펙 diff", "스펙에서 코드 생성"이라는 말이 전부 이 개념 하나에 얹혀 있으므로 여기부터 정확히 정의하고 시작한다.

**OpenAPI는 API의 경로·HTTP 메서드·요청 파라미터·요청과 응답 바디의 필드와 타입·가능한 상태 코드를, 사람이 읽는 문장이 아니라 기계가 읽을 수 있는 형식(YAML 또는 JSON)으로 적어 두는 규격이다.** 사람이 쓰는 문서가 "이 API는 주문 하나를 조회하고, 없으면 404를 줍니다"라고 문장으로 적는 자리에, OpenAPI는 같은 내용을 구조화된 데이터로 적는다.

```yaml
# openapi.yaml — 사람이 읽어도 되지만, 애초에 기계가 읽으라고 만든 형식이다
openapi: 3.0.3
paths:
  /orders/{id}:                    # 경로
    get:                           # HTTP 메서드
      summary: 주문 조회
      parameters:
        - name: id
          in: path                 # 이 파라미터가 경로에 박혀 있다는 사실까지 데이터다
          required: true
          schema: { type: integer, format: int64 }
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object
                properties:        # 응답 바디의 필드와 타입 — 이것이 기계 판독의 핵심
                  id:     { type: integer, format: int64 }
                  amount: { type: integer, description: 결제 금액(원) }
                  status: { type: string, enum: [PENDING, PAID, CANCELLED] }
        '404':
          description: 주문 없음
```

"기계가 읽을 수 있다"는 것이 왜 중요한가. **규격 파일 하나에서 여러 산출물을 자동으로 만들어낼 수 있기 때문이다.** 문장으로 쓴 문서로는 아무것도 만들 수 없지만, 구조화된 데이터로는 만들 수 있다.

| 규격 파일에서 만들 수 있는 것 | 무엇을 해주는가 |
|---|---|
| 문서 UI (Swagger UI 등) | 브라우저에서 탐색 가능한 API 문서 화면을 그려준다 |
| 클라이언트 코드 | 프론트·모바일·파트너가 쓸 호출 코드를 언어별로 생성한다 |
| 서버 인터페이스 | 컨트롤러 인터페이스와 DTO를 생성해 구현이 규격에서 벗어나기 어렵게 만든다 |
| 요청·응답 검증기 | 실제로 오간 요청과 응답이 규격과 맞는지 기계적으로 대조한다 |
| mock 서버 | 서버 구현 전에도 규격대로 응답하는 가짜 서버를 띄운다 |
| 스펙 diff | 이전 버전 규격과 비교해 필드 삭제·타입 변경 같은 파괴적 변경을 검출한다 |

마지막 줄이 이 문서와 08번 문서(`08-backward-compatible-api-changes.md`)를 잇는 다리다. **파괴적 변경이란 소비자가 코드를 고쳐야만 동작하는 변경**인데, 그것을 사람이 눈으로 찾는 대신 CI가 스펙 파일 두 개를 비교해 찾아내려면 애초에 스펙이 기계 판독 가능한 형식이어야 한다.

### 1-2. Swagger / OpenAPI / springdoc / Swagger UI — 층을 갈라 보면 헷갈리지 않는다

현장에서 이 네 이름이 뒤섞여 쓰이는데, **"규격 / 규격을 만드는 도구 / 규격을 보여주는 도구"라는 세 층으로 갈라 보면 관계가 한 번에 정리된다.**

| 층 | 이름 | 정체 |
|---|---|---|
| 규격 | **OpenAPI Specification (OAS)** | API를 YAML/JSON으로 적는 문법 그 자체. 3.0(2017년), 3.1(2021년)이 현행이다. 도구가 아니라 문서 규격이므로 "설치"하는 것이 아니다 |
| 규격을 만드는 도구 | **springdoc-openapi** | 스프링 컨트롤러·DTO·Bean Validation 어노테이션을 런타임에 스캔해 OAS 문서를 자동 생성해 주는 라이브러리. 현재 스프링 진영의 표준 선택지 |
| 규격을 만드는 도구 (구세대) | **springfox** | 같은 일을 하던 옛 라이브러리. 마지막 릴리스가 2020년의 3.0.0이고 그 뒤로 갱신이 없어, `javax` → `jakarta` 네임스페이스 전환을 겪은 Spring Boot 3에서는 동작하지 않는다. 신규 채택 대상이 아니다 |
| 규격을 보여주는 도구 | **Swagger UI** | OAS 파일을 읽어 브라우저에서 탐색·시험 호출 화면을 그려주는 도구. 규격을 만들지는 않고 읽어서 렌더링만 한다 |
| 그 밖의 도구 모음 | Swagger Editor, Swagger Codegen, OpenAPI Generator | 규격 편집기, 규격에서 코드를 뽑는 생성기 |

이름이 둘로 갈린 데는 역사가 있다. **Swagger는 원래 이 규격과 도구 모음 전체를 부르던 하나의 이름이었다.** 2011년에 나온 이 프로젝트는 명세 형식과 UI, 코드 생성기를 함께 갖고 있었다.

2015년에 규격 부분이 Linux Foundation 산하의 OpenAPI Initiative에 기증되면서 이름이 갈렸다. **규격은 "OpenAPI Specification"이라는 중립적인 표준 이름을 얻었고(Swagger Specification 2.0이 OpenAPI Specification 2.0이 되었다), "Swagger"라는 이름은 SmartBear가 관리하는 도구 모음 쪽에 남았다.** 그래서 3.0부터의 규격에는 Swagger라는 이름이 붙지 않고, 반대로 Swagger UI는 지금도 Swagger UI다.

이 역사를 알면 실무에서 겪는 두 가지 어색함이 설명된다.

**첫째, "우리는 Swagger 씁니다"라는 말의 정확한 뜻은 대개 "springdoc이 만들어 준 OpenAPI 문서를 Swagger UI로 본다"이다.** 세 층이 전부 관여하는데 사람들은 화면에 보이는 UI의 이름으로 전체를 부른다.

**둘째, springdoc을 쓰는데도 어노테이션 패키지 이름이 `io.swagger.v3.oas.annotations`다.** `@Operation`, `@Schema`, `@ApiResponse`가 전부 여기서 온다. springdoc이 어노테이션을 새로 만들지 않고 Swagger 진영이 만들어 둔 표준 어노테이션 세트를 그대로 읽어 쓰기 때문이다. 패키지 이름에 `swagger`와 `oas`가 함께 들어 있는 것이 이 관계를 그대로 보여준다.

### 1-3. source of truth — 어긋났을 때 어느 쪽이 정답인가

한 가지 용어를 더 깔고 간다. **source of truth(유일한 진실 공급원)란, 같은 정보가 여러 곳에 존재할 때 서로 어긋나면 어느 쪽을 정답으로 볼지 미리 정해 둔 그 한 곳을 말한다.**

API 정보는 최소한 두 곳에 있다 — 코드와 문서다. 코드 우선 방식(springdoc, REST Docs)에서는 코드가 정답이고 문서는 그 그림자다. 스펙 우선 방식에서는 스펙 파일이 정답이고 코드가 그것을 따라간다.

**중요한 것은 어느 쪽을 고르느냐가 아니라, 고르지 않으면 판정이 불가능해진다는 점이다.** 정해 두지 않으면 "코드는 400을 주는데 문서에는 404라고 적혀 있다"는 상황에서 누구도 무엇이 버그인지 말할 수 없다. 서버 개발자는 문서가 낡았다고 하고 프론트 개발자는 구현이 잘못됐다고 한다. 이 논쟁은 기술 문제가 아니라 **정답의 자리를 정해 두지 않은 조직 문제**다.

### 1-4. 문서는 왜 반드시 낡는가

이제 본론이다. 불일치는 개인의 게으름이 아니라 **구조**에서 나온다. 문서와 코드가 별도 산출물일 때 무슨 일이 벌어지는지 세 단계로 보자.

**첫째, 비대칭이 있다. 코드는 컴파일러와 테스트가 매일 검증하지만, 문서는 아무도 검증하지 않는다.** 응답 DTO에서 필드 하나를 지우면 그것을 참조하던 코드가 컴파일에서 터진다. 그런데 같은 필드를 문서에서 지우지 않아도 아무 일도 일어나지 않는다. 빌드는 초록불이고 테스트는 전부 통과한다. **틀렸다는 신호가 존재하지 않는 산출물은 반드시 틀린 채로 남는다.**

**둘째, 가장 중요한 변경일수록 문서가 먼저 낡는다.** 급한 수정(hotfix)일수록 "일단 배포부터 하고 문서는 나중에"가 된다. 그런데 급한 수정은 대개 에러 처리나 예외 흐름을 건드리고, 그 부분이야말로 소비자가 문서를 가장 많이 찾아보는 대목이다.

**셋째, 문서의 신뢰는 0 아니면 1이다.** 이 비대칭이 이 문제를 특별하게 만든다. 한 번이라도 문서대로 했는데 400이 떨어진 경험을 하면, 소비자는 그 뒤로 **문서를 안 보고 담당자에게 물어본다.** 그리고 한 번 그렇게 된 팀은 문서를 고쳐도 신뢰가 돌아오지 않는다 — 고쳐졌는지 확인하려면 결국 문서를 믿어야 하는데, 그 믿음이 이미 없기 때문이다.

세 번째가 특히 뼈아픈 이유는 **문서의 가치가 "최신인가"가 아니라 "믿을 수 있는가"에 있기 때문**이다. 90%가 정확한 문서는 90%의 가치가 있는 것이 아니라, 매번 검증해야 하므로 사실상 0에 가깝다.

따라서 이 질문의 진짜 답은 "문서를 부지런히 고친다"가 아니라 **"문서가 틀리면 빌드가 깨지게 만든다"** — 문서를 검증 루프에 편입시키는 것이다. 이 문서 나머지 전부가 그 방법의 목록이다.

## 2. 두 접근의 비교 — 어노테이션 기반 vs 테스트 기반

### 2-1. Swagger / springdoc-openapi — 코드에서 문서를 추출한다

springdoc은 애플리케이션이 뜰 때 컨트롤러를 스캔한다. 매핑 어노테이션에서 경로와 메서드를, 메서드 시그니처와 반환 타입에서 파라미터와 응답 스키마를, `@NotNull` 같은 Bean Validation 어노테이션에서 필수 여부와 제약을 읽어 OpenAPI 문서를 조립한다. 여기에 사람이 `@Operation`, `@Schema` 같은 서술 어노테이션으로 설명을 덧붙인다.

```java
@Operation(summary = "주문 조회", description = "주문 상세를 반환한다")
@ApiResponse(responseCode = "200", description = "조회 성공")
@GetMapping("/orders/{id}")
public OrderResponse getOrder(@PathVariable Long id) { ... }
```

**강점은 진입 장벽이 낮다는 것과, 구조적 사실이 저절로 정확하다는 것이다.** 여기서 "구조적 사실"이 무엇인지 정확히 짚어야 한다 — 경로(`/orders/{id}`), HTTP 메서드(GET), 파라미터 이름과 타입(`id`, `Long`), 응답 DTO의 필드와 타입이다. **이것들은 사람이 문서에 옮겨 적는 것이 아니라 코드에서 추출되므로, 구현과 어긋날 방법이 없다.** 필드 이름을 바꾸면 문서의 필드 이름도 자동으로 바뀐다. 여기에 Swagger UI의 try-it-out으로 브라우저에서 바로 호출해볼 수 있으니 탐색·QA·프론트 협업에는 확실히 편하다.

**약점은 정확히 그 반대편에 있다. 불일치가 자주 나는 부분이 하필 "손으로 쓴 서술"이라는 것이다.** 에러 응답, 제약 조건, 필드의 업무적 의미, 예제 값 — 이것들은 코드에서 추출할 수 없어서 어노테이션에 사람이 적어야 하고, 그 순간 1-4에서 말한 "아무도 검증하지 않는 산출물"이 코드 옆으로 자리만 옮겨 온 것이 된다.

```java
// 어노테이션 기반 문서의 전형적 거짓말:
@ApiResponse(responseCode = "404", description = "주문 없음")   // 문서에는 404라고 적혀 있다
@GetMapping("/orders/{id}")
public OrderResponse getOrder(@PathVariable Long id) {
    return orderService.find(id);   // 그런데 예외 핸들러가 400을 반환하도록 바뀐 지 오래다
}
// 컴파일 통과, 테스트 통과, 문서는 거짓말 — 어긋났다는 신호가 어디에도 없다
```

이 예시가 어노테이션 방식의 한계를 정확히 보여준다. `@ApiResponse`에 적은 `404`는 **그저 문자열**이다. 컨트롤러가 실제로 어떤 상태 코드를 내보내는지와 아무 연결이 없어서, 예외 핸들러를 고치는 커밋이 이 줄을 건드리지 않아도 되고 아무도 이 줄이 낡았다는 것을 알 수 없다.

부수 문제로, 문서를 풍부하게 만들수록 프로덕션 코드가 문서 어노테이션으로 뒤덮여 **비즈니스 로직의 가독성을 해친다**는 점도 있다. 컨트롤러 메서드 하나에 어노테이션 열 줄이 붙고 실제 코드는 두 줄인 상황이 흔하다.

### 2-2. Spring REST Docs — 테스트에서 문서를 생성한다

발상이 반대다. **문서를 코드 옆에 적는 대신, 통과한 테스트가 남긴 실제 요청과 실제 응답으로 문서를 만든다.**

```java
@Test
void 주문_조회_문서화() throws Exception {
    mockMvc.perform(get("/orders/{id}", 1L))
        .andExpect(status().isOk())                       // ① 실제 동작을 먼저 검증하고
        .andDo(document("order-get",                      // ② 통과한 요청/응답으로 문서 조각 생성
            pathParameters(
                parameterWithName("id").description("주문 ID")),
            responseFields(
                fieldWithPath("id").description("주문 ID"),
                fieldWithPath("amount").description("결제 금액(원)"),
                fieldWithPath("status").description("주문 상태"))));
}
// 응답에서 amount 필드가 사라지면? -> responseFields 검증 실패 -> 테스트 실패 -> 빌드 실패
// 문서에 없는 필드가 응답에 추가되면? -> 역시 실패 (문서화 누락도 잡힌다)
```

주석의 마지막 두 줄이 이 도구의 전부다. `responseFields`는 문서에 쓸 설명을 다는 자리인 동시에 **"응답에 정확히 이 필드들이 있다"는 단언(assertion)**이기도 하다. 선언한 필드가 응답에 없어도 실패하고, 응답에 있는 필드를 선언하지 않아도 실패한다. 그래서 문서와 응답이 어긋나는 순간이 곧 빌드가 깨지는 순간이 된다.

#### 문서 조각(snippet)과 AsciiDoc — 2단 조립 구조

여기서 "문서 조각"이라는 말이 처음 나왔으므로 정의하고 간다. **snippet은 REST Docs가 테스트 하나마다 만들어 내는 작은 문서 파일들이다.** 하나의 완성된 문서가 아니라, 최종 문서에 끼워 넣을 부품이다.

`document("order-get", ...)`을 실행하면 `build/generated-snippets/order-get/` 디렉터리 아래에 파일 여러 개가 생긴다 — 실제로 보낸 요청 원문, 실제로 받은 응답 원문, curl 명령 예시, 경로 파라미터 설명 표, 응답 필드 설명 표 같은 것들이다. 전부 기계가 만든 것이라 사람이 손대지 않는다.

그런데 이 조각들만으로는 문서가 되지 않는다. **"이 API가 왜 있는지, 언제 쓰는지, 인증은 어떻게 하는지" 같은 서술은 테스트가 만들어낼 수 없기 때문이다.** 그래서 사람이 뼈대 문서를 쓰고 거기에 조각을 끼워 넣는 2단 구조가 된다.

```
[1단] 테스트가 조각을 만든다 (기계 담당 — 사실)

   OrderDocumentationTest
        │  mockMvc.perform(...).andDo(document("order-get", ...))
        │  ★ 테스트가 통과해야만 이 줄이 실행된다 = 검증되지 않은 조각은 존재할 수 없다
        ▼
   build/generated-snippets/order-get/
        ├─ http-request.adoc       실제로 보낸 요청 원문
        ├─ http-response.adoc      실제로 받은 응답 원문
        ├─ curl-request.adoc       같은 요청의 curl 명령
        ├─ path-parameters.adoc    {id} 설명 표
        └─ response-fields.adoc    응답 필드 설명 표

[2단] 사람이 쓴 뼈대에 조각을 끼운다 (사람 담당 — 서술)

   src/docs/asciidoc/index.adoc         ← 사람이 손으로 쓴다
        │  = 주문 API
        │  이 API는 결제가 끝난 주문의 상세를 반환한다. 인증은 ...
        │
        │  == 주문 조회
        │  include::{snippets}/order-get/http-request.adoc[]      ← 조각을 끼운다
        │  include::{snippets}/order-get/response-fields.adoc[]
        ▼
   Asciidoctor 빌드
        ▼
   build/docs/asciidoc/index.html       ← 최종 문서
```

**AsciiDoc**은 마크다운과 같은 계열의 경량 마크업 언어인데, 마크다운보다 문서 조립 기능이 강하다. 특히 **다른 파일을 그 자리에 끼워 넣는 `include::` 지시어**가 있고, REST Docs가 AsciiDoc을 기본으로 삼는 이유가 정확히 이것이다. 조각 파일 수십 개를 뼈대 문서에 끼워 넣어 한 장으로 합치는 일이 마크다운에는 표준적인 방법이 없다.

이 2단 구조를 보면 **"왜 테스트가 문서를 만드는가"**가 그려진다. 문서에는 두 종류의 내용이 섞여 있는데, **사실(요청이 어떻게 생겼고 응답에 무슨 필드가 있는지)은 테스트만 보증할 수 있고, 서술(왜 이 API가 있고 언제 쓰는지)은 사람만 쓸 수 있다.** REST Docs는 이 둘을 각자 잘하는 쪽이 만들게 하고 빌드 시점에 합친다. 어노테이션 방식이 사실과 서술을 같은 자리에 섞어 두고 둘 다 사람에게 맡긴 것과 대비된다.

#### 무엇으로 요청을 보내는가 — MockMvc / WebTestClient / REST Assured

REST Docs는 테스트에서 오간 요청과 응답을 받아 적는 도구일 뿐이고, **실제로 요청을 보내는 일은 별도의 테스트 클라이언트가 한다.** 선택지가 셋이고, 셋의 차이는 **무엇을 태우고 무엇을 태우지 않는가**다. 이 차이가 뒤의 꼬리질문("mock으로 쓰면 그것도 거짓말 아닌가")의 답과 직결되므로 표로 정리한다.

| 도구 | 서블릿 컨테이너(톰캣)를 띄우나 | 실제 네트워크를 타나 | 무엇까지 검증되는가 |
|---|---|---|---|
| **MockMvc** | 아니오. `MockHttpServletRequest`라는 가짜 서블릿 객체를 만들어 `DispatcherServlet`에 직접 넘긴다 | 아니오 — 같은 JVM 안에서의 메서드 호출이다 | 컨트롤러 매핑, 인자 바인딩, 검증, 예외 핸들러, JSON 직렬화. 필터는 명시적으로 등록한 것만 (스프링 시큐리티 연동 시에는 자동 등록된다) |
| **WebTestClient** | 설정에 따라 다르다. 애플리케이션 컨텍스트에 바인딩하면 안 띄우고, `@SpringBootTest(webEnvironment = RANDOM_PORT)`와 함께 쓰면 실제로 뜬 서버의 포트에 붙는다 | 모드에 따라 다르다 | mock 모드면 MockMvc와 비슷한 범위, 실제 서버 모드면 아래 REST Assured와 같은 범위 |
| **REST Assured** | 예. 실제로 떠 있는 서버에 붙는다 | 예 — 진짜 HTTP 요청이다 | 서블릿 컨테이너, 전체 필터 체인, 보안 체인, 실제 직렬화까지 전부 |

**핵심은 위에서 아래로 갈수록 "실제와 같은 정도"가 올라가고 속도는 떨어진다는 것이다.** MockMvc는 톰캣을 안 띄우므로 빠르지만 그만큼 톰캣 계층에서 벌어지는 일(예: 서블릿 필터가 응답 헤더를 건드리는 것)은 검증 범위 밖이다. REST Assured는 전부 태우지만 서버를 띄워야 하므로 느리다.

**슬라이스 테스트**라는 용어도 여기서 나온다. **애플리케이션의 모든 빈을 올리는 대신 특정 층(slice)에 필요한 빈만 올리는 테스트**를 말한다. `@WebMvcTest`가 대표적인데, 컨트롤러와 그 주변(메시지 컨버터, 예외 핸들러)만 올리고 `@Service`·`@Repository`는 올리지 않는다. 그래서 컨텍스트가 가볍고 빠른 대신, 서비스 계층은 `@MockBean`(Spring Boot 3.4부터는 `@MockitoBean`)으로 가짜를 채워 넣어야 한다. 이 "가짜를 채워 넣는다"가 뒤 꼬리질문의 쟁점이 되는 지점이다.

#### 강점과 약점

**강점: 문서화가 곧 검증이다.** 문서에 적힌 모든 필드는 테스트를 통과한 실제 응답에서 나온 것이므로 구조적으로 거짓말할 수 없다. 구현이 바뀌면 문서 테스트가 깨져서 **문서 갱신을 잊는 것이 불가능**해진다. 프로덕션 코드에 문서 어노테이션이 쌓이지 않는 것도 부수 이득이다.

**약점: 비용이 크고 자유도가 낮다.** 문서화할 필드를 테스트에 전부 선언해야 하므로 작성 비용이 만만치 않고, try-it-out 같은 인터랙티브 UI가 기본으로는 없으며, 문서 서술의 자유도도 낮다. 그리고 **"테스트가 커버하는 케이스만" 문서화되므로 테스트 문화가 약한 팀에서는 오히려 유지가 안 된다** — 문서를 만들려면 테스트를 먼저 써야 하는데 그 테스트를 안 쓰는 팀이라면 문서 자체가 안 생긴다.

### 2-3. 비교 요약

두 접근을 나란히 놓으면 이렇게 된다. 특히 위의 두 행 — **무엇이 저절로 맞고 무엇이 검증되지 않는가** — 을 구분해 말하는 것이 이 질문의 정확도를 가른다. "Swagger는 부정확하다"고 뭉뚱그리면 틀린 답이다.

| 축 | Swagger 어노테이션 (springdoc) | Spring REST Docs |
|---|---|---|
| 무엇이 저절로 맞나 | 경로·HTTP 메서드·파라미터 타입·응답 DTO의 필드와 타입 — **코드에서 추출되므로 구현과 어긋날 수 없다** | 위와 같은 구조적 사실 + **그 필드가 실제 응답에 정말로 들어 있다는 사실**까지 |
| 무엇이 검증되지 않나 | 손으로 쓴 서술 전부 — `description`, 예제 값, 제약 조건 설명, 그리고 **어느 에러 응답이 실제로 나가는지** | 뼈대 문서에 사람이 쓴 산문(개요, 용어 설명, 인증 안내) |
| 어긋났을 때 무슨 일이 나나 | 아무 일도 안 난다 — 빌드는 초록불 | 테스트가 깨져 빌드가 실패한다 |
| 도입·유지 비용 | 낮음 | 높음 (문서화할 필드를 테스트에 전부 선언) |
| 인터랙티브 UI | Swagger UI 기본 제공 | 기본 없음 (3-1의 결합형으로 보완) |
| 프로덕션 코드 오염 | 어노테이션 누적 | 없음 (문서화 코드가 테스트에 위치) |
| 어울리는 곳 | 내부 API, 빠른 탐색·협업 | 외부 공개·파트너 API 등 계약 수준 문서 |

## 3. 절충과 확장 — 실무에서의 선택지

### 3-1. 결합형: 테스트에서 OpenAPI를 생성한다 (가산점 포인트)

두 접근의 장점이 서로 배타적이지 않다는 점이 이 절의 출발이다. REST Docs가 주는 것은 **검증**이고 Swagger UI가 주는 것은 **화면**인데, 이 둘은 다른 층의 이야기다.

그래서 REST Docs 테스트 결과에서 **OpenAPI 스펙 파일을 생성**하는 확장(restdocs-api-spec 같은 오픈소스)을 얹으면 둘 다 얻는다. 검증은 테스트가 하고, 생성된 스펙 파일을 Swagger UI가 읽어 화면을 그린다. **"테스트로 검증된 스펙 + 인터랙티브 문서"**가 동시에 성립한다.

1-1의 표를 다시 보면 이 조합의 값이 더 커진다. 스펙 파일이 손에 들어오는 순간 클라이언트 코드 생성, 스펙 diff, 런타임 검증기까지 전부 붙일 수 있게 되기 때문이다. **REST Docs 단독은 사람이 읽는 HTML에서 끝나지만, 스펙을 뽑아내면 기계가 쓸 수 있는 자산이 된다.**

### 3-2. 스펙 우선(contract-first) — 정답의 자리를 스펙 파일로 옮긴다

지금까지의 두 방식은 모두 **코드 우선**이다. 코드가 먼저 있고 문서는 거기서 파생된다. 반대 방향도 있다.

**스펙 우선은 OpenAPI 스펙을 먼저 쓰고 그것을 source of truth로 삼는 방법이다.** 1-3에서 말한 "정답의 자리"를 코드가 아니라 스펙 파일에 두는 것이다.

이 방향으로 갈아탈 때 얻는 것이 셋이다.

- **구현이 스펙에서 벗어나기 어려워진다.** 스펙에서 서버 인터페이스와 DTO를 생성해 컨트롤러가 그 인터페이스를 구현하게 하면, 스펙에 없는 응답을 내보내는 코드가 애초에 컴파일되지 않는다.
- **병렬 개발이 가능해진다.** 이것이 실무에서 가장 크게 체감되는 이득이다. 프론트와 백엔드가 스펙만 합의하면, 프론트는 생성된 클라이언트나 mock 서버로 즉시 화면을 만들기 시작하고 백엔드는 그동안 구현한다. 코드 우선에서는 백엔드가 만들 때까지 프론트가 기다려야 한다.
- **스펙이 저장소의 파일이므로 PR 리뷰를 태울 수 있다.** "말로 합의하고 코드는 딴판"이 구조적으로 어려워진다.

여기에 CI 검사를 얹으면 계약이 유지된다. **실제 응답을 스펙과 대조 검증하거나, 스펙 diff로 파괴적 변경을 감지해 빌드를 실패시키는 것이다.** 이 스펙 diff가 08번 문서(`08-backward-compatible-api-changes.md`)에서 말하는 호환성 방어선의 첫 층이다 — 필드 삭제, 타입 변경, 선택 파라미터의 필수화 같은 규칙 위반을 사람의 리뷰가 아니라 CI가 잡는다.

### 3-3. 소비자 주도 계약 테스트(CDC) — 문서가 아니라 실제 소비를 잡는다

스펙 diff에는 원리적인 한계가 하나 있다. **스펙 diff는 "규칙 위반"을 잡을 뿐, "실제로 누가 무엇을 쓰는지"는 모른다.** 스펙상 optional로 선언해 둔 필드를 지우는 것은 규칙 위반이 아니지만, 어느 소비자가 그 필드에 의존하고 있었다면 그 소비자는 깨진다. 반대로 아무도 안 쓰는 필드를 지우는 것은 규칙상 파괴적 변경이지만 실제 피해는 0이다.

**소비자 주도 계약 테스트(CDC, consumer-driven contract testing)는 이 빈틈을 메운다.** 이름 그대로 계약을 제공자가 아니라 **소비자가 주도해서 쓴다**는 것이 이 방식의 정체다. 소비자가 "나는 이 요청을 보낼 거고 응답에서 이 필드들을 읽을 거다"를 계약 파일로 등록하고, 제공자의 빌드가 그 계약을 재생해 검증한다.

흐름을 순서대로 펴 보면 이렇다.

```
[소비자 팀 — 주문 조회 화면을 만드는 앱]

  ① 소비자가 자기 테스트에 기대를 선언한다
       "GET /orders/1 을 보내면 200과 { id, amount } 를 받는다"
       │
       ├─(a) 이 선언으로 로컬에 mock 서버가 뜬다
       │     -> 제공자 구현이 없어도 소비자는 개발·테스트를 진행할 수 있다
       │
       └─(b) 같은 선언이 계약 파일로 저장돼 공유 저장소에 올라간다
                     │
                     ▼
             [계약 저장소]  (Pact Broker 등)
                     │
                     ▼
[제공자 팀 — 주문 서비스]

  ② 제공자의 CI가 계약 파일을 내려받아 재생(replay)한다
       계약에 적힌 요청을 실제 주문 서비스에 그대로 쏘고,
       돌아온 응답이 계약에 적힌 모양을 만족하는지 검사한다
       │
       ▼
  ③ 만족하지 않으면 제공자 빌드가 실패한다
       "amount 필드를 지웠더니 주문 앱의 계약이 깨졌다"가
       배포 전에, 제공자 쪽 CI에서 드러난다
```

**도구는 두 갈래다.** Pact는 위 그림 그대로 소비자가 계약을 만들고 브로커를 통해 제공자가 검증하는 방식이다. Spring Cloud Contract는 계약 파일(Groovy DSL이나 YAML)에서 **제공자 검증 테스트와 소비자용 스텁을 함께 생성**하는 방식이라 협업 절차가 조금 다르지만, "계약을 파일로 고정하고 양쪽 빌드가 그것을 검증한다"는 골격은 같다.

세 층의 역할이 다르다는 것까지 정리하면 답이 깔끔해진다.

| 방어선 | 무엇을 잡는가 | 놓치는 것 |
|---|---|---|
| 스펙 diff | 규칙 위반 — 필드 삭제, 타입 변경, 필수화 | 규칙상 안전한데 실제 소비자가 깨지는 경우, 의미만 바뀐 변경 |
| CDC | 실제 소비 — "이 소비자가 이 필드를 읽고 있다" | 계약을 등록하지 않은 소비자 (파트너·외부 앱) |
| REST Docs / 스펙 검증 | 문서와 구현의 일치 | 문서 자체가 소비자의 실제 사용과 다른 경우 |

이 표가 "문서와 다르다"와 "소비자가 실제로 쓰는 방식과 다르다"가 왜 다른 문제인지를 보여준다. 앞의 두 방어선은 문서 쪽을 지키고, CDC만이 소비자 쪽을 지킨다.

### 3-4. 선택 기준

- **소비자가 외부(파트너·공개)이고 문서가 계약이면**: 검증되는 문서가 필수다 — REST Docs 또는 스펙 우선 + CI 검증. 09번 문서(`09-partner-api-vs-internal-api.md`)에서 말하는 **"문서가 참고자료에서 계약서로 바뀐다"**가 이 선택의 근거다. 파트너 개발자는 우리 코드를 볼 수 없고 문서만 보고 구현하므로, 문서의 오류를 사람이 메워 줄 방법이 없다. 내부에서라면 슬랙 한 줄로 끝날 일이 외부에서는 연동 일정 지연과 반복 미팅이 된다.
- **소비자가 내부이고 속도·탐색이 우선이면**: springdoc + Swagger UI로 시작하되, **에러 응답처럼 거짓말이 잦은 부분만이라도 테스트로 고정**한다. 전면 도입만이 선택지가 아니다.
- 어느 쪽이든 원칙은 같다 — **사람의 성실함이 아니라 빌드 파이프라인이 문서의 정확성을 보증하게 한다.**

## 4. 꼬리질문 대비 포인트

### "Swagger를 쓰면서 불일치를 줄이는 현실적인 방법은 없나요?"

있다. 셋을 든다. **① 서술 어노테이션을 최소화한다** — 문서의 구조적 부분(타입, 필수 여부)은 Bean Validation(`@NotNull` 등)과 타입 시스템에서 추출되게 하고, 손으로 쓰는 서술의 양 자체를 줄인다. 검증되지 않는 부분이 적을수록 거짓말할 표면적이 줄어든다. **② 생성된 OpenAPI 스펙을 CI에서 스냅샷으로 관리한다** — 스펙 파일을 저장소에 커밋해 두고 빌드마다 다시 생성해 비교하면, 의도치 않은 스펙 변화(필드 삭제 등)가 PR diff에 그대로 드러나 리뷰에 노출된다. **③ 에러 응답은 `@ControllerAdvice` 기반 공통 모델로 표준화하고 그 모델만 문서화한다** — API마다 제각각인 에러를 문서화하려니 거짓말이 나는 것이므로, 에러 스키마를 하나로 고정하면 문서화할 대상 자체가 하나가 된다(에러 스키마 설계는 `05-error-response-body-standardization.md`).

다만 이 모두는 완화책이라는 선을 그어야 정확하다. **"손으로 쓴 서술이 검증되지 않는다"는 구조 자체는 REST Docs나 계약 테스트로만 해결된다.**

### "REST Docs는 테스트가 통과해야 문서가 나온다는데, 테스트를 mock으로 쓰면 그것도 거짓말 아닌가요?" (시니어 변별 포인트)

날카로운 지점이고, 2-2의 표를 그대로 답으로 쓰면 된다. **핵심은 "도구가 보증하는 범위가 어디까지인가"다.**

MockMvc + 서비스 계층 mock 조합이면 문서는 **컨트롤러 계층의 계약**까지만 보증한다. mock이 실제 서비스와 다른 응답을 주도록 짜여 있다면 문서도 그 가짜 응답을 그대로 받아 적는다. 테스트는 통과하고 문서는 생성되는데 실제 서비스는 다른 값을 준다 — 검증의 형식만 남고 내용이 빈 상태다.

대응은 세 가지다. **① 문서화 테스트는 가능한 한 실제 빈을 태우는 통합 테스트로 작성한다.** 슬라이스 테스트로 갈 수밖에 없다면 stub이 실제 서비스의 반환값과 어긋나지 않게 신중히 관리한다. **② 직렬화 경계(DTO)는 반드시 실제 객체를 쓴다.** JSON 필드 이름과 타입은 DTO에서 나오므로, DTO만 실제 것이면 응답의 구조는 사실과 일치한다. **③ mock을 쓰더라도 반환 타입을 실제 프로덕션 타입으로 고정한다** — 그러면 필드 구조만큼은 컴파일러가 보증한다.

한 줄로 닫으면 이렇다. **"도구가 보증하는 범위가 어디까지인지"를 아는 것이 도구 이름을 아는 것보다 중요하다.** REST Docs가 보증하는 것은 "이 테스트가 실제로 주고받은 것"이고, 그 테스트가 얼마나 실제에 가까운지는 여전히 우리가 정한다.

### "문서화 대상이 100개 API인데 REST Docs 전환 비용이 너무 크면?"

전면 전환이 아니라 **위험 기반으로 나눈다.** 기준은 "불일치가 났을 때의 비용"이다.

외부 파트너에게 나가는 API, 결제·정산처럼 불일치 사고 비용이 큰 API부터 REST Docs나 계약 테스트로 옮기고, 내부 조회성 API는 springdoc으로 유지한다. 여기에 **"신규 API부터 REST Docs를 기본으로 적용한다"**는 전략을 얹으면 전환 비용이 시간축으로 분산된다 — 존재하는 100개를 한 번에 옮기는 대신, 앞으로 늘어나는 것만이라도 새 기준으로 만드는 것이다.

**도구 통일 자체가 목적이 아니라 "문서를 믿을 수 있는가"가 목적임을 놓치지 않는 답변이 좋다.** 두 도구가 공존하는 상태는 어수선해 보이지만, 그 자체로 나쁜 것이 아니다.

### "문서 불일치를 런타임에 감지할 수는 없나요?"

가능하다. **게이트웨이나 필터에서 실제 요청·응답을 OpenAPI 스펙과 대조해 위반을 로깅하는 스펙 검증(validation) 계층**을 둘 수 있다. 1-1에서 본 "규격 파일에서 검증기를 만들 수 있다"가 이 용법이다.

값이 나오는 장면이 구체적이다. 운영 트래픽으로 **"스펙에 없는 필드가 나가고 있다"**나 **"스펙에는 없는 400이 실제로는 자주 나간다"**를 발견할 수 있어, 문서 체계를 전환하는 과도기나 감사(audit) 상황에 특히 유용하다. 테스트가 커버하지 못한 실제 경로를 트래픽이 대신 훑어 주는 셈이다.

다만 선을 하나 그어야 한다. **이건 사후 감지이므로 빌드 시점 검증(테스트, 스펙 diff)의 보완이지 대체가 아니다.** 운영에 나간 뒤에 알게 되는 것과 배포 전에 막는 것은 다른 층의 방어다.

### "프론트엔드와의 협업에서는 뭐가 제일 효과적이었나요?"

**스펙 우선 + 코드 생성 조합이 협업 효과가 크다.** 이유는 3-2에서 본 병렬 개발이다 — 스펙이 합의되면 프론트는 생성된 클라이언트나 mock 서버로 즉시 개발을 시작하고, 백엔드 구현은 그동안 병렬로 진행된다. 코드 우선에서는 백엔드가 API를 만들어 배포할 때까지 프론트가 기다리거나, 기다리기 싫어서 임의로 만든 가짜 데이터로 개발했다가 실제 응답과 어긋나 다시 고치게 된다.

여기에 절차 하나를 더 붙이면 답이 완성된다. **스펙 변경은 반드시 PR 리뷰를 거치게 한다.** 스펙 파일이 저장소에 있으므로 가능한 일이고, 이렇게 해야 "회의에서 말로 합의하고 코드는 딴판"이 되는 것을 막을 수 있다. 스펙을 저장소에 두는 것의 값은 파일 형식이 아니라 **변경 이력과 리뷰 절차가 코드와 같은 수준으로 붙는다는 데** 있다.

## 한 줄 요약

문서-구현 불일치는 성실함의 문제가 아니라 "문서가 검증 루프 밖에 있다"는 구조의 문제이고, 그 루프의 재료가 API를 기계 판독 형식(YAML/JSON)으로 적어 문서 UI·클라이언트 코드·검증기·스펙 diff를 전부 파생시킬 수 있게 하는 OpenAPI 규격이다 — springdoc이 코드를 스캔해 만든 규격을 Swagger UI로 보는 방식은 경로·메서드·타입 같은 구조적 사실은 저절로 정확하지만 손으로 쓴 서술은 아무도 검증하지 않아 거짓말이 남고, Spring REST Docs는 통과한 테스트가 남긴 실제 요청·응답으로 문서 조각을 만들어 사람이 쓴 뼈대에 끼워 넣으므로 문서와 구현이 어긋나는 순간이 곧 빌드가 깨지는 순간이 된다. 핵심 원칙은 **문서가 틀리면 빌드가 깨지게 만드는 것**이고, 외부 계약일수록(스펙 우선 + CI의 스펙 diff, 소비자가 계약을 등록하고 제공자 빌드가 재생하는 CDC) 그 강제 수준을 높이는 것이다.
