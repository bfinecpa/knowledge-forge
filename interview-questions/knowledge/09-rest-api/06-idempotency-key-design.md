# 멱등성 키 설계 — 네트워크는 반드시 실패하고, 클라이언트는 반드시 재시도한다

> 핵심 관전 포인트: **결제 API의 중복 요청은 "클라이언트가 조심하면 되는
> 문제"가 아니라 프로토콜의 본질적 한계다 — 타임아웃이 나면 클라이언트는
> 서버가 결제를 처리했는지 안 했는지 알 방법이 없고, 재시도할 수밖에 없다.
> 그래서 서버가 API 계약 수준에서 중복을 흡수해야 한다. 클라이언트가
> "결제 시도 1건"마다 고유한 멱등성 키(`Idempotency-Key` 헤더)를 생성해
> 보내고, 서버는 이 키를 유니크 제약이 있는 저장소에 INSERT-first로
> 기록해 최초 요청만 실제 처리하며, 같은 키의 재요청에는 저장해둔 최초
> 응답을 그대로 재생(replay)한다. 동시에 도착한 같은 키는 유니크 제약
> 충돌로 걸러내고 처리 중이면 409로 응답한다 — 핵심은 "검사 후 처리"가
> 아니라 "키 선점(원자적 INSERT) 후 처리"라는 순서다.**

---

## 0. 질문 + 의도

**질문**: "결제 API에서 중복 요청(더블 클릭, 네트워크 재시도)을 어떻게
방지하나요? (멱등성 키 설계)"

**출제 의도**: 네트워크는 반드시 실패하고 클라이언트는 반드시 재시도한다는
전제에서, 중복 결제를 API 계약 수준에서 차단하는 설계를 할 수 있는지 본다.
이 개념 없이 결제 API를 만든 팀은 반드시 이중 결제 CS를 받는다 — 결제
포지션의 필수 검증이다.

## 1. 왜 중복 요청은 "막을 수 없는" 전제인가

중복 요청의 발생 경로를 나열해보면, 클라이언트 쪽 노력(버튼 비활성화)만으로
막을 수 없다는 것이 드러난다.

- **더블 클릭**: 버튼 비활성화로 줄일 수 있다. 하지만 이건 가장 쉬운 경우다.
- **네트워크 재시도**: 진짜 문제. 클라이언트가 결제 요청을 보냈는데 응답이
  오기 전에 타임아웃이 났다. 이때 클라이언트가 아는 것은 "응답을 못 받았다"
  뿐이다. 서버에 요청이 **도달하기 전에** 끊겼는지(결제 안 됨),
  서버가 **처리를 끝내고 응답을 보내다가** 끊겼는지(결제 됨) 구분할 수 없다.
- **중간 계층의 자동 재시도**: 클라이언트 HTTP 라이브러리, 게이트웨이,
  프록시가 설정에 따라 알아서 재시도하기도 한다.
- **사용자 행동**: "결제가 안 된 것 같은데?" 하고 새로고침 후 다시 결제.

여기서 클라이언트의 선택지는 둘뿐이다 — 재시도하지 않으면 "결제했는데
주문이 없는" 고객이 생기고, 재시도하면 "한 번 샀는데 두 번 결제된" 고객이
생긴다. **어느 쪽이든 사고다.** 유일한 해법은 "재시도해도 안전한 API",
즉 멱등한 API를 서버가 제공하는 것이다.

**멱등성(idempotency)** 이란 같은 요청을 1번 보내든 N번 보내든 결과(서버
상태와 응답)가 같은 성질이다. HTTP 스펙상 GET·PUT·DELETE는 멱등하도록
정의돼 있지만 POST는 아니다 — 그런데 결제 생성은 POST다. 그래서 POST에
멱등성을 **인위적으로 부여하는 장치**가 멱등성 키다.

비유: 멱등성 키는 **접수번호가 미리 적힌 신청서**다. 같은 접수번호의
신청서가 두 번 들어오면 창구 직원은 두 번 처리하는 게 아니라 "이미 접수된
건입니다"라며 첫 번째 처리 결과를 보여준다. 접수번호가 없으면 직원은 두
신청서가 같은 건인지("아까 그분이네") 다른 건인지("같은 상품을 하나 더
사시려나") 구분할 방법이 없다.

## 2. 멱등성 키 설계 — 생성·전달·저장·재생

### 2-1. 키는 클라이언트가, "비즈니스 시도 1건"마다 생성한다

가장 많이 틀리는 지점이다. 키의 생명주기는 **HTTP 요청 단위가 아니라
비즈니스 작업(결제 시도) 단위**다.

- 사용자가 결제 버튼을 누르는 순간 클라이언트가 UUID를 하나 생성한다.
- 타임아웃으로 **재시도할 때는 같은 키를 재사용**한다. (재시도마다 새 키를
  만들면 서버는 전부 다른 요청으로 보고 전부 처리한다 — 키가 있으나 마나다.)
- 사용자가 실패 화면을 보고 **의도적으로 "다시 결제"를 누르면 새 키**를
  생성한다. (이건 새로운 시도이므로.)

전달은 관례적으로 `Idempotency-Key` HTTP 헤더를 쓴다(주요 결제사 API들이
쓰는 방식이고, IETF에서 표준화 논의가 진행돼온 헤더 이름이다).

```http
POST /payments HTTP/1.1
Idempotency-Key: 8f3c1e2a-...-b7d4
Content-Type: application/json

{ "orderId": "ORD-1001", "amount": 50000, "method": "CARD" }
```

### 2-2. 서버 처리 흐름 — "검사 후 처리"가 아니라 "선점 후 처리"

```java
// Before: check-then-act — 동시 요청에 뚫린다
@PostMapping("/payments")
public PaymentResponse pay(@RequestHeader("Idempotency-Key") String key,
                           @RequestBody PaymentRequest req) {
    if (idempotencyRepository.existsByKey(key)) {      // ① 검사
        return idempotencyRepository.findByKey(key).response();
    }
    PaymentResponse res = paymentService.process(req); // ② 처리
    idempotencyRepository.save(key, res);              // ③ 기록
    return res;
    // 문제: 더블 클릭으로 두 요청이 "동시에" 도착하면 둘 다 ①에서
    // "키 없음"을 보고 둘 다 ②를 실행한다 → 이중 결제.
    // 검사와 기록 사이의 틈이 곧 레이스 컨디션이다.
}
```

```java
// After: 원자적 INSERT로 키를 먼저 "선점"한다
@PostMapping("/payments")
public ResponseEntity<PaymentResponse> pay(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody PaymentRequest req) {

    // ① 키 선점 — idempotency_key 컬럼에 UNIQUE 제약.
    //    INSERT 성공 = 이 요청이 최초. 실패(중복 키) = 누군가 먼저 왔다.
    IdempotencyRecord record;
    try {
        record = idempotencyRepository.insert(key, hash(req)); // 상태: IN_PROGRESS
    } catch (DuplicateKeyException e) {
        record = idempotencyRepository.findByKey(key);
        if (record.isInProgress()) {
            // 최초 요청이 아직 처리 중 — 지금은 결과를 줄 수 없다
            return ResponseEntity.status(HttpStatus.CONFLICT)
                    .header("Retry-After", "1").build();       // 409
        }
        if (!record.requestHash().equals(hash(req))) {
            // 같은 키로 "다른 내용"의 요청 — 키 재사용 실수. 재생하면 위험
            return ResponseEntity.unprocessableEntity().build(); // 422
        }
        return replay(record);  // ② 저장된 최초 응답을 그대로 재생
    }

    // ③ 최초 요청만 여기 도달 — 실제 결제 처리
    PaymentResponse res = paymentService.process(req);
    idempotencyRepository.complete(key, res);  // 상태: COMPLETED + 응답 저장
    return ResponseEntity.ok(res);
}
```

설계 포인트를 풀어 쓰면:

- **유니크 제약이 동시성 제어의 본체다.** 애플리케이션 코드의 if문이 아니라
  DB의 유니크 인덱스(또는 Redis의 `SET key value NX`)가 "최초 1건"을
  보장한다. 검사와 선점이 한 번의 원자적 연산이어야 틈이 없다.
- **응답까지 저장해서 재생한다.** 재요청에 "이미 처리됨" 에러를 주는 게
  아니라 **최초 요청과 동일한 상태 코드와 바디**를 돌려준다. 그래야
  클라이언트 입장에서 "1번 보낸 것과 N번 보낸 것이 구분 불가능"해지고,
  재시도 로직이 성공/실패 분기를 다시 짤 필요가 없어진다.
- **요청 바디의 해시를 함께 저장한다.** 같은 키에 다른 금액이 실려 오면
  버그(키 재사용 실수)이므로 재생하지 말고 422로 거부한다. 잘못된 재생은
  "5만원 결제 요청에 3만원 결제 응답"을 주는 사고가 된다.
- **처리 중(IN_PROGRESS) 상태를 명시한다.** 첫 요청이 아직 PG사 응답을
  기다리는 중에 재시도가 도착할 수 있다. 이때는 결과가 없으므로 409 +
  `Retry-After`로 "잠시 후 다시"를 알린다(최초 요청 처리 완료를 기다렸다가
  응답하는 구현도 가능하지만, 커넥션을 오래 점유한다).

### 2-3. 저장소와 키 스코프

- **저장소**: 결제라면 DB 테이블(유니크 인덱스)이 기본이다. Redis
  `SETNX`는 빠르지만 유실 가능성이 있어, "키가 사라지면 이중 결제"인
  도메인에는 단독으로 쓰기 부담스럽다. Redis를 선점 락으로, DB를 응답
  저장소로 조합하기도 한다.
- **키 스코프**: 키는 사용자(또는 가맹점) 단위로 격리한다 — 유니크 제약을
  `(user_id, idempotency_key)`로 걸면 다른 사용자가 우연히(또는 악의로)
  같은 키를 써도 서로 영향이 없다.
- **TTL**: 멱등성 레코드는 영구 보관할 필요 없다 — 재시도는 보통 수 분
  안에 끝난다. 만료 기간(예: 24시간)을 정해 정리하되, 만료 후 같은 키가
  오면 새 요청으로 처리된다는 점을 계약(문서)에 명시한다.

## 3. 실무 사례 — 멱등성 키가 있어도 뚫리는 구멍들

### 사례 1: 처리 도중 서버가 죽으면 키가 "영구 처리 중"이 된다

키를 INSERT(IN_PROGRESS)한 직후, PG사 호출 전후 어딘가에서 서버가
죽었다. 레코드는 IN_PROGRESS로 남고, 이후 재시도는 전부 409를 받는다 —
사용자는 영원히 결제를 못 한다.

대응: IN_PROGRESS에 **타임아웃**을 둔다. 일정 시간이 지난 IN_PROGRESS
레코드는 "결과 불명"으로 보고, 재시도가 오면 PG사에 **거래 조회 API**로
실제 결제 여부를 확인한 뒤 이어서 처리(복구)하거나 최초 처리로 다시
진행한다. "키 저장과 실제 처리 사이의 크래시"까지 시나리오에 넣는 것이
결제 시스템 설계의 기본기다.

### 사례 2: 멱등성 키는 "같은 시도"만 막는다 — 비즈니스 중복은 별개

사용자가 결제 실패 화면에서 "다시 시도"를 눌러 **새 키**로 요청했는데,
사실 첫 결제는 성공해 있었다(응답만 유실). 키가 다르므로 멱등성 장치는
통과하고 이중 결제가 난다.

대응: 멱등성 키(전송 계층의 중복 방지)와 별개로 **비즈니스 규칙의 중복
방지**를 이중으로 둔다 — 예: "하나의 주문(orderId)에는 승인된 결제가 1건만
존재할 수 있다"는 유니크 제약. 멱등성 키는 재시도 폭풍을 흡수하는 1차
방어선이고, 도메인 불변식이 최후의 방어선이다. (가산점 포인트: 이 구분을
"transport-level dedup vs business-level dedup"으로 명확히 나눠 말하기)

### 사례 3: 우리 서버 → PG사 호출에도 같은 문제가 재귀한다

우리 API가 멱등해도, 우리 서버가 PG사를 호출하다 타임아웃 나면 같은
딜레마가 서버 안에서 반복된다. 그래서 PG사 API의 멱등성 장치(멱등성 키
헤더 또는 가맹점 주문번호 기반 중복 방지)를 확인하고, 우리 쪽 재시도에
같은 키/주문번호를 유지해야 한다. 멱등성은 호출 체인의 **모든 구간**에서
각각 보장돼야 한다.

## 4. 꼬리질문 대비 포인트

### "멱등성 키는 누가 생성하나요? 서버가 만들어주면 안 되나요?"

키의 존재 이유가 "클라이언트가 **응답을 못 받은** 요청을 다시 보낼 때
같은 요청임을 증명하는 것"이므로, 응답을 못 받는 상황에서도 키를 알고
있어야 하는 쪽 — 즉 **클라이언트**가 생성해야 한다. 서버가 응답으로 키를
내려주는 방식이면, 정작 응답이 유실된 재시도 상황에서 클라이언트에게 키가
없다. 서버 생성 토큰을 쓰려면 "결제 화면 진입 시 토큰 발급 → 결제 요청에
포함"처럼 **결제 요청보다 앞선 별도 단계**에서 미리 받아둬야 한다(폼 중복
제출 방지의 고전적 토큰 패턴과 같은 구조다).

### "같은 키로 두 요청이 완전히 동시에 도착하면 어떻게 되나요?"

유니크 제약 덕에 INSERT는 한쪽만 성공한다 — 이것이 이 설계의 심장이다.
성공한 쪽이 실제 처리를 진행하고, 실패한 쪽은 레코드를 조회해서
COMPLETED면 저장된 응답을 재생, IN_PROGRESS면 409 + `Retry-After`(또는
완료 대기 후 응답)로 처리한다. 애플리케이션 레벨 `exists` 검사로는 이
동시 도착을 못 막는다는 것, 즉 **원자성의 출처가 DB 제약**이라는 점을
짚어야 한다.

### "재생(replay)할 때 최초 요청이 실패 응답이었다면요?"

실패도 "확정된 결과"라면 그대로 재생한다 — 예: 잔액 부족(4xx 계열 확정
실패)은 재시도해도 같은 결과여야 하므로 저장된 실패 응답을 돌려준다.
반면 **일시적 오류**(우리 서버 내부 오류로 처리 자체가 안 된 경우)는
레코드를 확정 상태로 남기지 말아야 한다 — 그래야 같은 키의 재시도가
"새로운 최초 처리"로 진행될 수 있다. "어떤 실패를 확정으로 기록하고 어떤
실패를 재시도 가능으로 남기는가"의 분류가 실무 설계의 디테일이다.

### "Redis로 하면 되지 않나요? DB까지 써야 하나요?" (시니어 변별 포인트)

트레이드오프 판단 문제다. Redis `SETNX` + TTL은 빠르고 구현이 간단하지만,
(1) 장애·페일오버로 키가 유실되면 그 순간 중복 요청이 통과하고, (2) 응답
바디 저장·상태 전이(IN_PROGRESS→COMPLETED)까지 얹으면 결국 트랜잭션적
일관성이 필요해진다. 이중 결제의 비용(CS, 환불, 정산 보정, 신뢰 하락)이
DB 쓰기 1회의 비용보다 압도적으로 크므로, **결제에서는 내구성 있는
저장소(DB 유니크 제약)를 기본**으로 하고, Redis는 트래픽 앞단의 빠른
중복 차단(예: 더블 클릭 수준의 짧은 중복)에 보조로 쓴다고 답하는 것이
균형 잡힌 답이다. 반대로 "중복돼도 피해가 미미한 API"(예: 조회수 집계)
라면 Redis 단독으로 충분하다 — 도메인의 중복 비용에 따라 저장소를
고른다는 기준을 말하면 설계 감각을 보여줄 수 있다.

### "PUT은 멱등하다는데, 그럼 결제를 PUT으로 만들면 해결되나요?"

절반만 맞다. `PUT /payments/{clientGeneratedId}`처럼 클라이언트가 리소스
식별자를 정해 올리면 "같은 식별자에 대한 반복 PUT"이라는 멱등 시맨틱을
자연스럽게 얻는다 — 멱등성 키를 URI에 녹인 것과 같다. 하지만 멱등성은
시맨틱(계약)이지 구현이 아니다 — 서버가 유니크 제약·응답 재생·동시 도착
처리를 구현하지 않으면 PUT이라고 저절로 안전해지지 않는다. 또 결제처럼
"생성 + 외부 부수효과(PG 승인)"가 있는 작업은 관례상 POST + 멱등성 키가
더 일반적이고, 처리 중/완료 상태 관리도 명시적으로 설계하게 된다.

## 한 줄 요약

타임아웃 난 클라이언트는 성공/실패를 알 수 없어 반드시 재시도하므로,
서버가 클라이언트 생성 멱등성 키를 유니크 제약으로 **원자적으로 선점**하고
최초 응답을 저장해 재생함으로써 "N번 보내도 1번 처리"를 API 계약으로
보장해야 한다 — 단, 멱등성 키는 같은 시도의 재전송만 막으므로, 주문당
결제 1건 같은 **도메인 불변식과 PG 구간의 멱등성**까지 겹겹이 세워야
이중 결제가 막힌다.
