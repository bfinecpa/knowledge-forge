# 멱등성 키 설계 — 네트워크는 반드시 실패하고, 클라이언트는 반드시 재시도한다

> 핵심 관전 포인트: **결제 API의 중복 요청은 "클라이언트가 조심하면 되는 문제"가 아니라 프로토콜의 본질적 한계다 — 타임아웃이 나면 클라이언트는 서버가 결제를 처리했는지 안 했는지 알 방법이 없고, 그래서 재시도할 수밖에 없다. 결국 서버가 API 계약 수준에서 중복을 흡수해야 한다. 클라이언트가 "결제 시도 1건"마다 고유한 멱등성 키(`Idempotency-Key` 헤더)를 만들어 보내고, 서버는 그 키를 **유니크 제약이 걸린 행으로 먼저 꽂아 선점**한 뒤(PostgreSQL의 `INSERT ... ON CONFLICT DO NOTHING`이 몇 행을 넣었는지로 승패를 가른다) 이긴 요청만 실제 처리하며, 같은 키의 재요청에는 저장해 둔 최초 응답을 상태 코드까지 통째로 **재생(replay)**한다. 이 설계의 심장은 "있나 검사하고 없으면 처리"가 아니라 "먼저 선점하고 이긴 쪽만 처리"라는 **순서**다 — 검사와 처리 사이의 간극이 곧 경쟁 조건이고, 그 간극을 없애는 방법이 원자성을 DB의 유니크 인덱스에 위임하는 것이기 때문이다. 여기에 같은 키로 다른 내용이 오는 클라이언트 버그를 잡는 요청 지문(fingerprint), 처리 중 크래시된 레코드를 회수하는 리스(lease), 그리고 "멱등성 키는 같은 시도의 재전송만 막고 새 키로 온 새 시도는 도메인 유니크 제약이 막는다"는 계층 구분까지 얹어야 이중 결제가 실제로 막힌다.**

---

## 0. 질문 + 의도

**질문**: "결제 API에서 중복 요청(더블 클릭, 네트워크 재시도)을 어떻게 방지하나요? (멱등성 키 설계)"

**출제 의도**: 네트워크는 반드시 실패하고 클라이언트는 반드시 재시도한다는 전제에서, 중복 결제를 API 계약 수준에서 차단하는 설계를 할 수 있는지 본다. 이 개념 없이 결제 API를 만든 팀은 반드시 이중 결제 CS를 받는다 — 결제 포지션의 필수 검증이다.

## 1. 왜 중복 요청은 "막을 수 없는" 전제인가

### 1-1. 발생 경로를 나열해 보면 클라이언트 책임이 아님이 드러난다

"버튼을 비활성화하면 되지 않나"가 첫 반응이다. 발생 경로를 늘어놓으면 그 대책이 어디까지 유효한지 보인다.

- **더블 클릭**: 버튼 비활성화로 줄일 수 있다. 가장 쉬운 경우다. 다만 두 번째 탭, 새로고침, 앱 강제 종료 후 재실행은 못 막는다 — 화면 하나는 다른 화면의 존재를 모르기 때문이다.
- **네트워크 재시도**: 여기가 진짜 문제다. 이 절의 나머지가 전부 이 이야기다.
- **중간 계층의 자동 재시도**: 클라이언트 HTTP 라이브러리, API 게이트웨이, 리버스 프록시가 설정에 따라 알아서 재시도하기도 한다. 애플리케이션 코드는 한 번만 보냈는데 서버에는 두 번 도착한다.
- **사용자 행동**: "결제가 안 된 것 같은데?" 하고 새로고침 후 다시 결제.

### 1-2. 타임아웃이 났을 때 클라이언트가 실제로 아는 것

결제 요청을 보냈는데 응답이 오기 전에 읽기 타임아웃이 났다. 이때 벌어졌을 수 있는 일을 그려 보자.

```
클라이언트                                서버                          PG
    │  POST /payments ─────────────────>  │
    │                                     │  승인 요청 ───────────────> │
    │                                     │  <──────────────  승인 완료 │
    │                                     │  DB 커밋 (결제 확정)        │
    │  <───────── ✗ 응답이 여기서 사라짐   │
    │
    │  read timeout
    │  클라이언트가 아는 것: "응답을 못 받았다." — 이게 전부다.
```

문제는 아래 세 상황이 클라이언트 눈에 **완전히 똑같이** 보인다는 것이다.

| 실제로 일어난 일 | 결제 상태 | 클라이언트가 관측한 것 |
|---|---|---|
| ① 요청이 서버에 닿기 전에 연결이 끊겼다 | 안 됨 | 응답 없음 |
| ② 서버가 처리 중인데 클라이언트가 먼저 포기했다 | 곧 됨 | 응답 없음 |
| ③ 서버가 처리를 끝내고 응답을 보내다 끊겼다 | 이미 됨 | 응답 없음 |

셋을 구분할 방법이 **원리적으로** 없다. 네트워크로 소식을 주고받는 두 주체가 "상대가 내 메시지를 받았는지"를 확실히 알 수 없다는 것은 분산 시스템의 고전적 결과이고, 흔히 **두 장군 문제**라고 부른다(자세한 논의는 `10-payment-consistency/04-pg-timeout-unknown-state.md`). 타임아웃을 늘려도 ③은 사라지지 않는다. 사라진 응답은 기다린다고 다시 오지 않기 때문이다.

그래서 클라이언트의 선택지는 둘뿐이다.

- **재시도하지 않는다** → ①②였다면 "결제했다고 생각했는데 주문이 없는" 고객이 생긴다.
- **재시도한다** → ③이었다면 "한 번 샀는데 두 번 결제된" 고객이 생긴다.

**어느 쪽이든 사고다.** 그러니 "클라이언트가 재시도하지 않게 하자"는 해법이 될 수 없다. 유일한 출구는 **재시도해도 안전한 API를 서버가 제공하는 것**이다.

### 1-3. 멱등성과 멱등성 키

**멱등성(idempotency)**은 같은 요청을 1번 보내든 N번 보내든 결과 — 서버의 상태와 클라이언트가 받는 응답 — 가 같은 성질이다. "멱등"은 수학 용어로, 거듭할 멱(冪)에 같을 등(等), 즉 몇 번을 거듭 적용해도 결과가 더 이상 변하지 않는다는 뜻이다. 절댓값 함수를 떠올리면 된다. `abs(-3)`도 3이고 `abs(abs(-3))`도 3이다.

HTTP 명세는 GET·PUT·DELETE를 멱등한 메서드로 정의한다. 반면 POST는 멱등하지 않다 — 부를 때마다 새 자원이 생기는 것이 POST의 의미이기 때문이다(메서드별 멱등성의 정확한 정의는 `08-network-http/04-http-method-idempotency-and-safety.md`).

그런데 **결제 생성은 본질적으로 POST다.** 그래서 멱등성을 **인위적으로 부여하는 장치**가 필요하고, 그것이 **멱등성 키**다. 키란 "이 요청과 저 요청이 같은 시도인가"를 판정하기 위해 클라이언트가 요청에 붙여 보내는 고유 식별자다.

비유하면 멱등성 키는 **접수번호가 미리 적힌 신청서**다. 같은 접수번호의 신청서가 두 번 들어오면 창구 직원은 두 번 처리하지 않고 "이미 접수된 건입니다"라며 첫 번째 처리 결과를 보여준다. 접수번호가 없으면 직원은 두 신청서가 같은 건인지("아까 그분이 다시 내셨네") 다른 건인지("같은 상품을 하나 더 사시려나") 구분할 방법이 없다. 판정의 근거를 **클라이언트가 미리 심어주는 것**이 이 장치의 본질이다.

## 2. 멱등성 키 설계 — 생성·전달·선점·재생

### 2-1. 키는 클라이언트가, "비즈니스 시도 1건"마다 생성한다

가장 많이 틀리는 지점이다. 키의 생명주기는 **HTTP 요청 단위가 아니라 비즈니스 작업(결제 시도) 단위**다.

- 사용자가 결제 버튼을 누르는 순간 클라이언트가 UUID를 하나 생성한다.
- 타임아웃이 나서 **재시도할 때는 같은 키를 재사용**한다. 재시도마다 새 키를 만들면 서버는 전부 다른 요청으로 보고 전부 처리하므로, 키가 있으나 마나다.
- 사용자가 실패 화면을 보고 **의도적으로 "다시 결제"를 누르면 새 키**를 만든다. 이건 새로운 시도이기 때문이다.

```
결제 버튼 클릭
   │
   ├─ 키 K1 생성
   │
   ├─ 요청 1 (K1) ─> 타임아웃
   ├─ 요청 2 (K1) ─> 타임아웃      같은 시도의 재전송이므로 키를 유지한다
   ├─ 요청 3 (K1) ─> 응답 받음
   │
   └─ 사용자가 "다시 결제" 클릭  ─> 키 K2 생성 (새 시도이므로 새 키)
```

전달은 관례적으로 `Idempotency-Key` HTTP 헤더를 쓴다. 주요 결제사 API들이 쓰는 이름이고, IETF에서 표준 헤더로 만들기 위한 논의가 진행돼 온 이름이기도 하다(아직 RFC로 확정된 헤더는 아니므로, 우리 API 문서에 헤더 이름과 의미를 직접 적어두는 것이 여전히 필요하다).

```http
POST /payments HTTP/1.1
Idempotency-Key: 8f3c1e2a-4b7d-4a1e-9c22-a7f6b7d4e001
Content-Type: application/json

{ "orderId": "ORD-1001", "amount": 50000, "method": "CARD" }
```

### 2-2. 전제 — 경쟁 조건과 check-then-act 간극

키를 받았으니 이제 서버가 "이미 처리한 키인가"를 판단해야 한다. 가장 자연스러운 코드는 이렇게 생겼고, 이것이 틀렸다는 것이 이 문서의 핵심이다.

```java
// Before: check-then-act — 동시 요청에 뚫린다
@PostMapping("/payments")
public PaymentResponse pay(@RequestHeader("Idempotency-Key") String key,
                           @RequestBody PaymentRequest req) {
    if (idempotencyRepository.existsByKey(key)) {      // ① 검사
        return idempotencyRepository.findByKey(key).response();
    }
    PaymentResponse res = paymentService.process(req); // ② 처리
    idempotencyRepository.save(key, res);              // ③ 기록
    return res;
}
```

**경쟁 조건(race condition)**이란 두 개 이상의 실행 흐름이 같은 데이터를 건드릴 때, 어느 쪽이 먼저 도착하느냐에 따라 결과가 달라지는 상황이다. 이름 그대로 "경주" 상황이라 붙은 이름이다.

위 코드가 왜 경쟁 조건인지는 **①에서 알아낸 사실이 ③에서 확정될 때까지 참으로 남아 있지 않다**는 점에 있다. 이 패턴을 **check-then-act**(검사하고 나서 행동하기)라고 부르고, 검사와 행동 사이의 시간을 **간극**이라고 부른다. 그 간극에 다른 요청이 끼어들면 검사 결과가 낡은 정보가 된다.

더블 클릭으로 두 요청이 0.2초 간격으로 도착하는 장면을 시간축에 펴면 이렇다.

```
시각   요청 A (첫 클릭)                        요청 B (두 번째 클릭)
────   ────────────────────────────────────    ────────────────────────────────────
t1     SELECT ... WHERE key='K'
t2       → 0건. "처음 보는 키다"
t3                                             SELECT ... WHERE key='K'
t4                                               → 0건. "처음 보는 키다"
                                                 ↑ A가 아직 아무것도 안 썼으므로
                                                   B도 똑같이 "없다"를 본다
t5     PG 승인 호출 (50,000원)
t6                                             PG 승인 호출 (50,000원)
t7     INSERT key='K' + 응답 저장
t8                                             INSERT key='K'  ← 여기서 터지지만
                                                 이미 승인이 두 번 나갔다

결과: 카드 승인 2건. 고객 계좌에서 10만 원이 빠져나갔다.
```

핵심은 **t2에서 t7까지가 간극**이라는 것이다. 이 구간 동안 "키 K는 존재하지 않는다"는 사실은 아직 어디에도 기록돼 있지 않다. B는 그 빈 공간을 그대로 통과한다.

여기서 흔한 오답을 하나 걷어내자. **"트랜잭션으로 묶으면 되지 않나"는 답이 아니다.** 일반적인 격리 수준(PostgreSQL 기본값인 Read Committed)에서 SELECT는 다른 트랜잭션이 아직 커밋하지 않은 행을 못 볼 뿐이고, "앞으로 생길 행"을 예약해 주지는 않는다. 존재하지 않는 행에는 잠글 대상 자체가 없기 때문이다. 트랜잭션은 이미 있는 행의 동시 수정은 막아주지만, **"둘 다 없다고 봤다"는 이 상황은 막지 못한다.**

### 2-3. 선점 후 처리 — 원자성을 유니크 인덱스에 위임한다

간극을 없애는 방법은 하나다. **검사와 선점을 두 걸음이 아니라 한 걸음으로 만드는 것.** 즉 "있나 물어보고 없으면 쓴다"가 아니라, **"일단 써 보고, 써졌으면 내가 처음이다"**로 바꾼다.

이걸 가능하게 하는 것이 DB의 **유니크 제약**이다. 유니크 인덱스가 걸린 컬럼에 두 세션이 같은 값을 동시에 INSERT하면, DB 엔진이 인덱스 항목 수준에서 한쪽을 대기시키고 앞선 트랜잭션이 커밋되면 뒤에 온 쪽을 충돌로 판정한다. **"둘 중 누가 이겼는가"의 판정을 애플리케이션 코드가 아니라 DB 엔진에 맡기는 것**이 이 설계의 전부다. 애플리케이션의 `if`문은 두 걸음이지만, 인덱스에 항목을 꽂는 일은 DB 안에서 나눌 수 없는 한 걸음이기 때문이다.

먼저 테이블을 보자.

```sql
CREATE TABLE idempotency_record (
    user_id          bigint       NOT NULL,
    idempotency_key  varchar(64)  NOT NULL,
    fingerprint      char(64)     NOT NULL,  -- 요청 바디의 SHA-256 (16진수 64자)
    status           varchar(16)  NOT NULL,  -- IN_PROGRESS | COMPLETED
    response_status  int,                    -- 최초 응답의 HTTP 상태 코드
    response_body    jsonb,                  -- 최초 응답 바디 원문
    locked_until     timestamptz  NOT NULL,  -- 리스 만료 시각 (3절 사례 1)
    attempt          int          NOT NULL DEFAULT 0,  -- 재선점 횟수 (2-6)
    created_at       timestamptz  NOT NULL DEFAULT now(),
    -- 복합 기본키가 곧 유니크 제약이고, 이것이 이 설계의 심장이다.
    -- 키를 사용자 단위로 격리하는 이유는 2-7에서 다룬다.
    PRIMARY KEY (user_id, idempotency_key)
);

-- TTL 정리 배치가 "오래된 레코드"를 훑는 경로 (2-7)
CREATE INDEX idx_idem_created_at ON idempotency_record (created_at);
```

선점 SQL은 이렇게 쓴다.

```sql
-- 선점 시도. 충돌하면 예외를 던지는 대신 아무것도 하지 않고 0행을 보고한다.
-- "몇 행이 삽입됐는가"가 곧 "내가 이겼는가"의 답이 된다.
INSERT INTO idempotency_record
       (user_id, idempotency_key, fingerprint, status, locked_until, created_at)
VALUES (:userId, :key, :fingerprint, 'IN_PROGRESS', now() + interval '30 seconds', now())
ON CONFLICT (user_id, idempotency_key) DO NOTHING;
```

`ON CONFLICT DO NOTHING`을 쓰는 이유가 단순한 취향이 아니라는 점을 짚어야 한다. **PostgreSQL에서는 유니크 위반이 예외로 터지는 순간 그 트랜잭션 전체가 중단 상태(aborted)가 되어, 같은 트랜잭션 안에서 뒷 조회를 이어갈 수 없다.** `try { insert } catch (DuplicateKeyException e) { /* 여기서 findByKey */ }` 형태는 `@Transactional` 안에서 돌리면 catch 블록의 조회가 "현재 트랜잭션이 중단됨" 오류로 다시 터진다. 예외 대신 **영향받은 행 수**로 승패를 가르는 형태가 훨씬 안전한 것은 이 때문이다.

굳이 예외를 잡아야 한다면 두 가지 우회로가 있다. 선점만 `REQUIRES_NEW`로 별도 트랜잭션에 태우거나, `SAVEPOINT`를 잡고 실패 시 그 지점까지만 롤백하는 것이다. 어느 쪽이든 `ON CONFLICT DO NOTHING`보다 복잡하다.

```java
// After: 원자적 INSERT로 키를 먼저 "선점"한다
@PostMapping("/payments")
public ResponseEntity<?> pay(@RequestHeader("Idempotency-Key") String key,
                             @AuthenticationPrincipal Long userId,
                             @RequestBody PaymentRequest req) {

    String fingerprint = sha256(rawBodyOf(req));  // 2-5에서 설명

    // ① 선점. 위의 ON CONFLICT DO NOTHING 을 실행하고 삽입된 행 수를 받는다.
    //    1 = 내가 최초. 0 = 이미 누가 이 키로 자리를 잡았다.
    //    검사와 선점이 SQL 한 문장 안에서 원자적으로 끝나므로 2-2의 간극이 없다.
    int claimed = idempotencyRepository.claim(userId, key, fingerprint);

    if (claimed == 0) {
        IdempotencyRecord rec = idempotencyRepository.find(userId, key);

        // ② 같은 키인데 요청 내용이 다르다 = 클라이언트의 키 재사용 버그.
        //    여기서 저장된 응답을 재생하면 "3만원 요청에 5만원 결제 응답"이 나간다.
        if (!rec.fingerprint().equals(fingerprint)) {
            return ResponseEntity.unprocessableEntity().build();   // 422
        }

        // ③ 최초 요청이 아직 처리 중 = 돌려줄 결과가 아직 없다.
        //    Retry-After 로 "몇 초 뒤에 다시 물어보라"를 기계가 읽게 알린다.
        if (rec.status() == Status.IN_PROGRESS) {
            return ResponseEntity.status(HttpStatus.CONFLICT)
                    .header("Retry-After", "1").build();           // 409
        }

        // ④ COMPLETED — 저장해 둔 최초 응답을 상태 코드까지 그대로 재생한다.
        return ResponseEntity.status(rec.responseStatus()).body(rec.responseBody());
    }

    // ⑤ 선점에 성공한 최초 요청만 여기 도달한다. 실제 결제는 여기서 딱 한 번 일어난다.
    PaymentResponse res = paymentService.process(req);
    idempotencyRepository.complete(userId, key, 200, res);
    return ResponseEntity.ok(res);
}
```

이 코드에 `@Transactional`이 붙어 있지 않다는 점이 중요하다. 실수하기 쉬운 지점이라 따로 짚는다. **선점 INSERT는 실제 결제 처리와 같은 트랜잭션에 있으면 안 된다.** 두 가지가 동시에 망가지기 때문이다.

첫째, **선점한 행이 커밋되기 전에는 다른 요청에게 보이지 않는다.** IN_PROGRESS 표식을 남기는 목적 자체가 "지금 누가 처리 중"임을 다른 요청에게 알리는 것인데, 같은 트랜잭션에 묶여 있으면 결제가 다 끝나 커밋될 때까지 아무도 그 표식을 못 본다. 둘째, PostgreSQL에서 뒤에 온 INSERT는 앞선 트랜잭션이 끝날 때까지 **인덱스 항목에서 대기**하므로, 재시도한 요청이 즉시 409를 받는 대신 PG 승인이 끝날 때까지 몇 초씩 붙잡혀 있게 된다. 그래서 선점은 **짧은 자기 트랜잭션으로 커밋하고 나서** 실제 처리로 넘어간다.

같은 장면을 시간축에 다시 펴 보면 간극이 사라진 것이 보인다.

```
시각   요청 A                                  요청 B
────   ────────────────────────────────────    ────────────────────────────────────
t1     INSERT ... ON CONFLICT DO NOTHING
t2       → 1행 삽입. 내가 이겼다.
t3                                             INSERT ... ON CONFLICT DO NOTHING
t4                                               → 0행. 누가 먼저 꽂았다.
                                                 ↑ 검사와 선점이 한 문장이라
                                                   끼어들 틈이 애초에 없다
t5     PG 승인 호출 (50,000원)                 레코드 조회 → IN_PROGRESS
t6     결과 저장 (COMPLETED)                   409 + Retry-After 응답

결과: 카드 승인 1건.
```

**애플리케이션 코드의 어떤 `if`문도 이 일을 대신할 수 없다는 점**이 이 절의 결론이다. 원자성의 출처는 우리 코드가 아니라 DB의 유니크 인덱스다.

### 2-4. 재생(replay) — 무엇을, 왜 저장하는가

**재생(replay)**이란 같은 키로 두 번째 요청이 왔을 때 **처리를 다시 하지 않고, 첫 번째 요청 때 만들어 저장해 둔 응답을 그대로 다시 내보내는 것**이다. 녹음을 다시 트는 것과 같다고 해서 재생이라 부른다.

여기서 한 번 멈춰서 물어야 한다. **왜 그냥 "이미 처리된 요청입니다" 에러를 주면 안 되는가?** 그게 더 정직해 보이는데.

이유는 클라이언트가 원하는 것이 무엇인지를 보면 나온다. 재시도하는 클라이언트의 목표는 "중복이었다는 사실을 아는 것"이 아니라 **"결제 결과를 아는 것"**이다. "이미 처리됨" 에러를 주면 클라이언트는 결제 ID를 못 받았으므로 결과를 알아내려고 조회 API를 또 불러야 한다. 우리는 그 조회 경로를 따로 만들어야 하고, 클라이언트의 재시도 코드에는 "성공 / 실패" 두 갈래 외에 **"중복이니 다른 방법으로 결과를 알아내라"는 세 번째 갈래**가 생긴다.

더 근본적으로는 그 순간 멱등성이 깨진다. 멱등성의 정의는 "1번 보낸 것과 N번 보낸 것을 구분할 수 없다"는 것인데, 두 번째에 다른 응답을 주면 구분 가능해진다.

그래서 결론이 이렇게 나온다. **재생하려면 최초 응답을 통째로 저장해야 하고, 통째란 상태 코드까지 포함한다.** 바디만 저장하고 상태 코드를 매번 200으로 내보내면, 최초에 402를 받았던 클라이언트가 재시도에서는 200을 받아 결제가 성공했다고 오해한다.

저장하는 것을 하나씩 보면 각 항목이 왜 거기 있는지가 분명해진다.

| 저장 항목 | 예시 값 | 왜 필요한가 |
|---|---|---|
| `idempotency_key` | `8f3c1e2a-...-e001` | 유니크 제약의 대상 — 선점의 단위 그 자체 |
| `user_id` (키 스코프) | `10023` | 다른 사용자의 키와 섞이지 않게 격리한다 (2-7) |
| `fingerprint` | 바디의 SHA-256 | 같은 키·다른 내용을 잡아내 잘못된 재생을 막는다 (2-5) |
| `status` | `IN_PROGRESS` / `COMPLETED` | 재요청에 409를 줄지 재생할지를 가른다 |
| `response_status` | `200` / `402` | 재생은 상태 코드까지 같아야 클라이언트가 구분하지 못한다 |
| `response_body` | `{"paymentId":"P-771",...}` | 위와 같은 이유. 다시 만들지 않고 원문을 그대로 보관한다 |
| `locked_until` | `2026-09-01T14:22:31Z` | 처리 중 죽은 레코드를 회수하기 위한 리스 만료 시각 (3절 사례 1) |
| `created_at` | `2026-09-01T14:22:01Z` | TTL 정리 배치의 기준 (2-7) |

응답 바디를 다시 만들지 않고 **원문을 그대로 보관**하는 이유도 짚어둘 만하다. 나중에 응답 DTO에 필드가 추가되면, 재생 시점에 다시 조립한 바디는 최초 응답과 달라진다. "같은 응답"을 보장하려면 그때 실제로 나간 바이트를 들고 있는 것이 안전하다.

참고로 재생임을 **응답 헤더로만** 알리는 것은 무해하다. 일부 결제사는 재생된 응답에 전용 헤더를 하나 덧붙인다 — 관측과 디버깅에 쓰라는 것이고, 상태 코드와 바디는 건드리지 않으므로 멱등성이 깨지지 않는다.

### 2-5. 요청 지문(request fingerprint) — 같은 키, 다른 내용을 거절한다

**요청 지문(request fingerprint)**은 요청 내용을 하나의 짧은 값으로 압축한 것이다. 보통 요청 바디의 SHA-256 해시를 쓴다. 사람의 지문처럼 "이게 아까 그것과 같은 것인가"를 판별하는 용도라서 지문이라 부른다.

왜 필요한지는 **클라이언트가 키를 잘못 재사용하는 경우**를 보면 안다. 이런 버그는 생각보다 흔하다.

- 키를 결제 시도마다가 아니라 **세션 단위로** 만들어 두고 결제할 때마다 같은 키를 보내는 구현
- 재시도 래퍼가 요청 객체를 재사용하면서 헤더는 그대로 두고 바디만 바뀐 경우
- 파트너사의 배치 스크립트나 테스트 코드가 키를 상수로 박아둔 경우

지문 검사가 없으면 무슨 일이 나는지 보자.

```
1차:  Idempotency-Key: K   바디 {"amount": 50000}
      → 5만 원 승인. paymentId=P-771. 응답을 K에 저장.

2차:  Idempotency-Key: K   바디 {"amount": 30000}     ← 클라이언트 버그로 키를 재사용
      → 지문 검사가 없으면: 저장된 P-771(5만 원) 응답을 그대로 재생

클라이언트가 받는 것: "3만 원 결제를 요청했더니 성공 응답이 왔다"
실제로 존재하는 것:   5만 원 결제 하나뿐. 3만 원 결제는 어디에도 없다.
```

이건 **조용한 사고**라서 더 위험하다. 어느 쪽에서도 에러가 나지 않고, 로그도 정상이고, 클라이언트는 3만 원 결제가 끝났다고 믿는다. 불일치가 드러나는 것은 한참 뒤 대사(정산 대조) 단계다.

그래서 지문이 다르면 **재생하지 말고 거절**한다. 상태 코드는 **422 Unprocessable Content**를 쓴다. 요청 문법 자체는 멀쩡하므로(그래서 400이 아니다) 의미상 처리할 수 없다는 뜻의 422가 맞고, `Idempotency-Key` 헤더에 대한 IETF 초안도 이 경우 422를 권고한다. 참고로 이 코드의 이름은 RFC 9110에서 Unprocessable Entity에서 Unprocessable Content로 바뀌었다.

**무엇을 해싱할 것인가**는 계약으로 정해야 하는 세부다. 함정이 하나 있다 — JSON은 키 순서나 공백이 달라도 같은 내용일 수 있어서, 클라이언트가 재시도할 때 객체를 다시 직렬화하면 같은 요청인데 지문이 달라질 수 있다.

선택지는 둘이다.

- **수신한 원문 바이트를 그대로 해싱한다.** 서버 구현이 가장 단순하다. 대신 "재시도는 처음 보낸 바이트를 그대로 다시 보낸다"를 계약에 명시해야 한다. 대부분의 HTTP 재시도 래퍼가 바디를 버퍼에 담아두고 그대로 재전송하므로 현실적인 요구다.
- **업무상 중요한 필드만 골라 해싱한다.** 예: `orderId + amount + method`. 직렬화 차이에 관대해지는 대신, 해싱 대상에서 빠진 필드가 달라도 재생이 일어난다는 점을 감수한다.

어느 쪽이든 **문서에 적어야 계약**이 된다는 것이 핵심이다.

### 2-6. 멱등성 키의 상태 기계

지금까지 나온 상태 — 없음, IN_PROGRESS, COMPLETED — 를 하나의 그림으로 모으면 3절의 장애 시나리오를 읽을 수 있는 지도가 된다.

```
        (레코드 없음)  ── 이 키를 본 적이 없다
             │
             │ ① 선점: INSERT ... ON CONFLICT DO NOTHING 이 1행을 넣었다
             │    이 전이에 성공한 요청만 실제 결제로 나아간다
             v
        IN_PROGRESS ─────── 같은 키의 재요청 ──> 409 + Retry-After
        locked_until =                           (돌려줄 결과가 아직 없다)
        now() + 30초 (리스)
             │
             ├─ ② 처리 종료(성공이든 확정 실패든) ──> COMPLETED
             │                                        │
             │                                        └─ 같은 키의 재요청
             │                                           ──> 저장된 status + body 재생
             │
             └─ ③ 리스 만료 (처리 도중 서버가 죽었다) ──> 회수 대상
                                                          │
                                                          └─ 다음 재시도가 다시 선점하고
                                                             PG 거래 조회로 실제 여부를
                                                             확인한 뒤 이어서 처리
```

여기서 **리스(lease)**라는 용어를 정의하고 가자. 리스는 부동산의 임대차에서 온 말로, **기한이 붙은 점유권**이다. 분산 시스템에서 리스는 "지금부터 30초 동안은 내가 이 자원의 주인"이라는 시한부 표식을 뜻한다.

기한이 붙어 있다는 점이 결정적이다. **점유자가 죽어버려도 시간이 지나면 저절로 풀리기 때문에, "잠근 채로 죽는" 사고가 영구화되지 않는다.** 대신 살아 있는 점유자는 만료 전에 기한을 갱신해야 한다. 기한 없는 락을 쓰면 프로세스가 죽는 순간 그 자원은 사람이 손으로 풀어주기 전까지 영원히 잠긴다.

리스가 만료된 레코드를 다시 선점하는 SQL은 `ON CONFLICT DO UPDATE`로 쓴다.

```sql
-- 만료된 IN_PROGRESS 레코드까지 회수하는 선점.
-- DO UPDATE 의 WHERE 조건이 거짓이면 아무 행도 갱신되지 않고 0행이 보고되므로,
-- "정상 처리 중인 남의 리스"는 절대 빼앗지 않는다.
INSERT INTO idempotency_record
       (user_id, idempotency_key, fingerprint, status, locked_until, created_at)
VALUES (:userId, :key, :fingerprint, 'IN_PROGRESS', now() + interval '30 seconds', now())
ON CONFLICT (user_id, idempotency_key) DO UPDATE
   SET locked_until = now() + interval '30 seconds',
       attempt      = idempotency_record.attempt + 1
 WHERE idempotency_record.status       = 'IN_PROGRESS'   -- 완료된 건은 건드리지 않는다
   AND idempotency_record.locked_until < now();          -- 만료된 것만 회수한다
```

리스 길이를 정하는 기준은 **"최초 요청이 정상적으로 끝나는 데 걸리는 최대 시간"**이다. PG 승인의 읽기 타임아웃이 10초라면 리스를 30초쯤으로 잡는다. 너무 짧으면 정상 처리 중인 요청의 자리를 다른 재시도가 빼앗아 이중 승인이 나고, 너무 길면 크래시 후 사용자가 그만큼 오래 결제를 못 한다.

### 2-7. 저장소, 키 스코프, TTL

**저장소.** 결제라면 DB 테이블(유니크 인덱스)이 기본이다. 판단 기준은 성능이 아니라 **내구성**이다 — 이 도메인에서 "키가 사라진다"는 것은 곧 "이중 결제"이기 때문이다.

Redis의 `SET key value NX PX 30000`도 원자적 선점을 제공하고 훨씬 빠르다. `NX`가 "키가 없을 때만 쓴다", `PX`가 "밀리초 단위 만료를 함께 건다"는 뜻이라 선점과 만료가 한 명령으로 묶인다. (별도 명령인 `SETNX`는 만료를 못 걸어서 뒤에 `EXPIRE`를 따로 보내야 하는데, 그 사이에 죽으면 영구 락이 남는다 — `SET ... NX PX`가 있는 이유가 이것이다. 자세한 것은 [5장 16번 문서](../05-redis-caching/16-distributed-lock-pitfalls-redlock.md).) 하지만 Redis는 기본적으로 **비동기 복제**라, 마스터가 방금 받은 쓰기가 레플리카에 도달하기 전에 마스터가 죽고 페일오버가 일어나면 그 키는 사라진다. 그 순간 중복 요청이 그대로 통과한다. 그래서 Redis 단독은 "키가 사라지면 이중 결제"인 도메인에 쓰기 부담스럽고, 실무에서는 **Redis를 앞단의 빠른 차단(더블 클릭 수준의 짧은 중복)에, DB를 최종 판정**에 두는 조합을 쓴다.

**키 스코프.** 유니크 제약을 `idempotency_key` 하나가 아니라 `(user_id, idempotency_key)`로 거는 이유가 둘 있다.

첫째, **키가 UUID가 아닐 수 있다.** 우리는 UUID를 기대하지만 클라이언트가 `order-1`이나 타임스탬프를 보낼 수도 있다. 키를 전역으로 관리하면 서로 다른 사용자의 키가 실제로 충돌해서, 엉뚱한 사람의 결제 응답이 재생되거나 409로 막힌다.

둘째, **악용을 막는다.** 키가 전역이면 공격자가 "다음에 쓰일 법한 키"를 미리 선점해 다른 사용자의 결제를 409로 막을 수 있다. 서비스 거부의 변종이다.

스코프의 실무 기준은 **"키를 만든 주체가 곧 스코프"**다. 사용자가 만들면 `user_id`, 파트너사 시스템이 만들면 가맹점 ID다.

**TTL(보관 기간).** 멱등성 레코드를 영구 보관할 필요는 없다. 다만 **TTL은 성능 파라미터가 아니라 안전 파라미터**라는 점을 먼저 못 박아야 한다. TTL이 만료된 뒤 같은 키가 도착하면 서버는 그것을 처음 보는 키로 처리하므로, **너무 짧은 TTL은 그대로 이중 결제 경로**가 된다.

그러니 TTL은 "가장 늦게 도착할 수 있는 재시도"보다 길어야 한다. 그 상한을 정하는 것은 클라이언트의 성격이다.

| 재시도 주체 | 최대 지연 | 필요한 TTL |
|---|---|---|
| HTTP 클라이언트 라이브러리의 자동 재시도 | 수 초 ~ 수십 초 | 분 단위면 충분 |
| 모바일 앱이 오프라인 큐에 담아뒀다 앱 재실행 시 전송 | 시간 ~ 일 단위 | 24시간 이상 |
| 파트너사가 실패 건을 다음 날 배치로 재전송 | 하루 이상 | 7일 |

주요 결제사들이 쓰는 값이 대체로 24시간 안팎인 것은 두 번째 줄을 커버하기 때문이다. 파트너 연동이 일 단위 재전송을 한다면 7일까지 늘린다. 그리고 **"만료 후 같은 키가 오면 새 요청으로 처리된다"는 것을 API 문서에 명시**해야 한다. 이건 구현 세부가 아니라 계약이다.

크기 감을 잡기 위해 계산해 보자. 일 결제 시도 100만 건, 레코드 하나가 응답 바디까지 포함해 평균 1KB라고 하면 하루 적재량은 `1,000,000 × 1KB ≈ 977MB`, 약 1GB다. 기본키 인덱스와 `created_at` 인덱스를 더해도 하루 1.1GB 남짓이다. 24시간 보관이면 테이블이 그 크기에서 평형을 이루고, 7일 보관이면 약 8GB다. **결제 규모에서 이 정도 저장 비용은 이중 결제 한 건의 처리 비용(CS 응대, 환불, 정산 보정)보다 압도적으로 싸다.**

정리 방법에도 PostgreSQL 특유의 고려가 있다. PostgreSQL에는 행 단위 자동 만료 기능이 없으므로 배치가 지워야 하는데, 하루치를 한 번에 `DELETE`하면 긴 트랜잭션과 대량의 죽은 튜플(dead tuple)이 생겨 VACUUM 부담이 커진다. 두 가지 중 하나를 택한다.

```sql
-- 방법 A: 조금씩 나눠 지운다. 배치를 짧게 여러 번 돈다.
DELETE FROM idempotency_record
 WHERE ctid IN (
   SELECT ctid FROM idempotency_record
    WHERE created_at < now() - interval '24 hours'
    LIMIT 5000
 );
```

방법 B는 `created_at` 기준 일자별 **범위 파티션**으로 테이블을 나누고, 만료된 파티션을 통째로 `DROP TABLE` 하는 것이다. 파티션 드롭은 파일을 통째로 없애므로 죽은 튜플을 남기지 않고, VACUUM도 필요 없다. 보관 기간이 명확한 로그성 테이블에는 이 방식이 정석이다.

## 3. 실무 사례 — 멱등성 키가 있어도 뚫리는 구멍들

### 사례 1: 처리 도중 서버가 죽으면 키가 "영구 처리 중"이 된다

키를 선점(IN_PROGRESS)한 직후, PG 호출 전후 어딘가에서 서버 인스턴스가 죽었다. 배포로 컨테이너가 내려갔을 수도 있고 OOM으로 프로세스가 사라졌을 수도 있다.

리스가 없었다면 레코드는 IN_PROGRESS로 영원히 남고, 이후 모든 재시도가 409를 받는다. **사용자는 영원히 결제를 못 한다.** 그리고 이 사용자는 다른 키로 다시 시도할 것이므로 "결제가 자꾸 안 된다"는 CS만 남는다.

2-6의 상태 기계 위에서 보면, **죽은 지점에 따라 상황이 다르다**는 것이 명확해진다.

| 서버가 죽은 지점 | 레코드 상태 | PG 승인 | 다음 재시도가 마주치는 것 | 회수 방법 |
|---|---|---|---|---|
| 선점 INSERT 전 | 없음 | 안 됨 | 키 없음 → 정상적으로 최초 처리 | 필요 없음 |
| 선점 직후, PG 호출 전 | IN_PROGRESS | 안 됨 | 리스 만료 전이면 409 | 만료 후 재선점 → 처음부터 처리 |
| PG 호출 도중·직후, 완료 기록 전 | IN_PROGRESS | **알 수 없음** | 리스 만료 전이면 409 | 만료 후 재선점 → **PG 거래 조회로 판정** |
| 완료 기록 직후 | COMPLETED | 됨 | 저장된 응답 재생 | 필요 없음 |

세 번째 줄이 이 사례의 본체다. **PG 호출 도중에 죽으면 승인이 났는지 안 났는지 우리도 모른다.** 1-2에서 클라이언트가 겪은 것과 똑같은 불확실성이 이번엔 우리 서버 쪽에서 반복된 것이다.

그래서 회수는 두 단계다.

**(1) 리스 만료로 자리를 되찾는다.** 2-6의 `ON CONFLICT DO UPDATE ... WHERE locked_until < now()`가 이 일을 한다. 만료된 레코드만 재선점되고, 정상 처리 중인 리스는 건드리지 않는다.

**(2) 재처리 전에 PG에 물어본다.** 재선점에 성공했다고 바로 승인을 다시 부르면 안 된다. 죽기 전에 승인이 이미 났을 수 있기 때문이다. **PG의 거래 조회 API로 "우리 주문번호에 대한 승인이 존재하는가"를 먼저 확인**하고, 있으면 그 결과로 레코드를 COMPLETED로 마무리하고, 없으면 그때 처음부터 처리한다(이 판정 절차의 상세는 `10-payment-consistency/04-pg-timeout-unknown-state.md`).

**"키 저장과 실제 처리 사이의 크래시"까지 시나리오에 넣는 것**이 결제 시스템 설계의 기본기다. 멱등성 키를 설명하면서 이 구간을 빼면, 잘 동작하는 정상 경로만 그린 설계가 된다.

### 사례 2: 멱등성 키는 "같은 시도"만 막는다 — 비즈니스 중복은 별개

사용자가 결제 실패 화면에서 "다시 시도"를 눌렀다. 클라이언트는 2-1의 규칙대로 **새 키**를 만들어 보낸다. 그런데 사실 첫 결제는 성공해 있었다 — 응답만 유실됐던 것이다.

키가 다르므로 서버는 이것을 정당한 신규 요청으로 보고 그대로 통과시킨다. **이중 결제가 난다.** 그리고 클라이언트가 새 키를 만든 것은 **버그가 아니다.** 사용자가 새 시도를 했으니 새 키가 맞다.

같은 구멍이 다른 얼굴로도 나타난다. 사용자가 주문서를 채우고 결제한 뒤 브라우저를 새로고침해서 같은 상품을 한 번 더 주문하는 경우다. 이때 화면이 새로 그려지면서 새 키가 생기므로, 멱등성 키는 이 중복을 아예 인식하지 못한다.

핵심은 **중복 제거에 층이 둘 있고, 두 층이 서로 다른 질문에 답한다**는 것이다.

| | 전송 계층 중복 제거 | 비즈니스 계층 중복 제거 |
|---|---|---|
| 장치 | 멱등성 키 (`Idempotency-Key`) | 도메인 유니크 제약 |
| 묻는 질문 | "이 요청이 아까 그 요청인가" | "이 업무가 이미 이뤄졌는가" |
| 판정 근거 | 클라이언트가 붙여 보낸 키 | 도메인 데이터 자체 (주문번호, 장바구니 내용) |
| 막는 것 | 타임아웃 재시도, 게이트웨이 재전송, 더블 클릭 | 새 키로 온 같은 업무의 재요청 |
| 못 막는 것 | 새 키로 온 새 시도 | (막기는 하지만) 최초 응답을 재생해 주지는 못한다 |

두 번째 층은 도메인 데이터 위의 유니크 제약으로 만든다. PostgreSQL에서는 **부분 인덱스**를 쓰면 상태 조건까지 제약에 넣을 수 있다.

```sql
-- "한 주문에 살아 있는 승인 결제는 1건뿐"이라는 도메인 불변식을
-- DB가 지키게 한다. WHERE 절이 붙은 부분 인덱스라, 취소된 결제는
-- 조건에서 빠진다 — 그래서 취소 후 재결제는 정상적으로 허용된다.
CREATE UNIQUE INDEX uq_payment_approved_per_order
    ON payment (order_id)
 WHERE status = 'APPROVED';
```

**주문 생성처럼 아직 비즈니스 식별자가 없는 경우**는 한 단계 더 생각해야 한다. 결제는 `order_id`가 있으니 위 제약을 걸 수 있지만, 주문 자체를 만드는 API에는 걸 대상이 없다. 새로고침으로 같은 장바구니가 두 번 들어오는 것을 무엇으로 막을 것인가.

- **휴리스틱**: "같은 사용자가 같은 장바구니 내용으로 5분 안에 만든 주문은 하나로 본다" — 장바구니 스냅샷의 해시에 유니크 제약을 건다. 간단하지만 완전하지 않다. 정말로 같은 것을 두 개 사려는 사용자를 막아버릴 수 있다.
- **정공법**: 주문서 화면에 진입할 때 서버가 **주문 초안(draft)을 만들어 ID를 내려주고**, 결제는 그 초안 ID에 대해서만 이뤄지게 한다. 그러면 새로고침해도 초안 ID가 같으므로 유니크 제약이 걸린다. 즉 **비즈니스 식별자를 결제보다 앞선 단계에서 미리 확보하는 것**이다(이 구조는 4절 첫 꼬리질문의 "서버 생성 토큰"과 같은 발상이다).

정리하면 **멱등성 키는 재시도 폭풍을 흡수하는 완충재이고, 도메인 불변식이 최후의 관문**이다. 층이 다르므로 하나가 나머지를 대체하지 못한다. 면접에서는 이 구분을 **"전송 계층 중복 제거(transport-level dedup) vs 비즈니스 계층 중복 제거(business-level dedup)"**로 명확히 나눠 말하면 좋다(가산점 포인트). 계층 방어 전체 구조는 `10-payment-consistency/07-double-payment-defense-in-depth.md`가 다룬다.

### 사례 3: 우리 서버 → PG 호출에도 같은 문제가 재귀한다

우리 API가 완벽하게 멱등해도, **우리 서버가 PG를 호출하다 타임아웃 나면 1-2의 딜레마가 서버 안에서 그대로 반복된다.** 승인이 났는지 안 났는지 우리도 모르고, 재시도하면 이중 승인 위험이 있다.

구조를 그림으로 보면 문제가 한 구간이 아니라는 것이 보인다.

```
[클라이언트] ──① 멱등성 키──> [우리 API] ──② PG 멱등 장치──> [PG]

① 구간: 우리가 설계한다. 이 문서의 내용 전부.
② 구간: PG가 제공해야 성립한다. 우리가 만들 수 없다.
```

②를 위해 확인해야 할 것이 순서대로 있다.

1. **PG가 멱등성 키를 지원하는가.** 지원한다면 우리 쪽 재시도에 같은 키를 유지하면 된다. 이때 PG 쪽 키의 유효 기간도 함께 확인한다 — 우리 TTL보다 짧으면 늦은 재시도가 PG에서 새 승인이 된다.
2. **지원하지 않는다면 가맹점 주문번호 기반 중복 방지가 있는가.** 많은 PG가 "같은 가맹점 주문번호로는 승인이 한 번만"이라는 규칙을 갖고 있다. 그러면 주문번호가 사실상 멱등성 키 역할을 한다.
3. **둘 다 없다면 재시도하지 않는다.** 타임아웃 시 자동 재시도 대신 **거래 조회로 실제 상태를 확인한 뒤 판단**하는 것이 원칙이다(`10-payment-consistency/02-pg-integration-basics.md`).

**멱등성은 호출 체인의 모든 구간에서 각각 보장돼야 한다.** 한 구간만 멱등해도 그 구간만 안전할 뿐, 옆 구간의 중복은 그대로 통과한다.

## 4. 꼬리질문 대비 포인트

### "멱등성 키는 누가 생성하나요? 서버가 만들어주면 안 되나요?"

키의 존재 이유에서 답이 나온다. 키는 **"응답을 못 받은 요청을 다시 보낼 때 그게 아까 그 요청임을 증명하는 것"**이므로, **응답을 못 받는 상황에서도 키를 이미 알고 있어야 하는 쪽**이 만들어야 한다. 그게 클라이언트다.

서버가 응답 바디에 키를 담아 내려주는 방식은 여기서 자기모순이 된다. 정작 응답이 유실된 재시도 상황에서 클라이언트에게는 키가 없다. 문제를 풀어야 할 바로 그 순간에 도구가 없는 것이다.

서버 생성 토큰을 쓰고 싶다면 방법이 있다. **결제 요청보다 앞선 별도 단계에서 미리 발급받는 것**이다 — "결제 화면 진입 시 토큰 발급 → 그 토큰을 결제 요청에 포함". 그러면 결제 요청이 실패해도 클라이언트 손에 토큰이 이미 있다. 이건 서버가 폼을 내려줄 때 일회용 토큰을 심어 중복 제출을 막던 고전적 패턴과 정확히 같은 구조이고, 3절 사례 2의 "주문 초안 ID"와도 같은 발상이다.

### "같은 키로 두 요청이 완전히 동시에 도착하면 어떻게 되나요?"

**유니크 제약 덕에 INSERT는 한쪽만 성공한다 — 이것이 이 설계의 심장이다.**

성공한 쪽이 실제 처리를 진행하고, 실패한 쪽은 레코드를 조회해서 갈린다. COMPLETED면 저장된 응답을 재생하고, IN_PROGRESS면 409에 `Retry-After`를 실어 돌려준다.

이 답에서 반드시 짚어야 하는 것은 **원자성의 출처**다. 애플리케이션 레벨의 `exists` 검사로는 이 동시 도착을 못 막는다 — 두 요청이 나란히 "없음"을 보고 나란히 통과하는 check-then-act 간극이 있기 때문이다(2-2의 타임라인). **판정을 우리 `if`문이 아니라 DB의 유니크 인덱스에 위임했다는 것**이 핵심이다.

여기에 PostgreSQL 구현 디테일을 하나 얹으면 깊이가 드러난다. 유니크 위반을 **예외로 받으면 그 트랜잭션이 중단 상태가 되어 같은 트랜잭션에서 후속 조회를 이어갈 수 없으므로**, `ON CONFLICT DO NOTHING`으로 받아 **영향받은 행 수(1 또는 0)로 승패를 가르는 형태**가 안전하다는 점이다.

IN_PROGRESS에 409를 주는 것 말고 "최초 요청이 끝날 때까지 기다렸다가 같은 응답을 주는" 구현도 가능하다. 클라이언트 경험은 더 낫지만, 대기하는 동안 서버의 스레드와 커넥션을 붙잡고 있게 되어 부하 상황에서 위험하다는 트레이드오프까지 말하면 좋다.

### "재생(replay)할 때 최초 요청이 실패 응답이었다면요?"

**"확정된 실패"인가 "일시적 실패"인가로 갈린다.** 이 분류가 실무 설계의 디테일이다.

**확정 실패는 그대로 재생한다.** 잔액 부족, 한도 초과, 카드 만료 같은 4xx 계열은 몇 번을 다시 시도해도 같은 결과다. 이 결과를 COMPLETED로 저장해 두고 재요청에 그대로 돌려주면, 클라이언트는 재시도해도 일관된 답을 받는다.

**일시적 실패는 확정 상태로 남기지 않는다.** 우리 서버 내부 오류로 처리 자체가 시작되지 못했거나 DB 커넥션이 없어 실패한 경우다. 이걸 COMPLETED로 박아두면 잠시 후 상황이 나아졌을 때 같은 키로 재시도해도 영원히 저장된 500만 재생된다 — **사용자가 그 키로는 결제할 방법이 없어진다.** 그래서 이런 경우는 레코드를 지우거나 리스를 만료시켜 **"새로운 최초 처리"로 다시 진행될 수 있게** 남긴다.

경계에 걸리는 것이 하나 있고, 이걸 언급하면 답이 완성된다. **PG 호출 타임아웃은 실패가 아니라 "결과 불명"이다.** 실패로 확정해 저장하면 실제로는 승인이 났는데 클라이언트에게 실패를 재생하게 되고, 성공으로 처리해도 마찬가지로 틀릴 수 있다. 이 경우는 3절 사례 1처럼 **거래 조회로 사실을 확인한 뒤에** 확정한다.

### "Redis로 하면 되지 않나요? DB까지 써야 하나요?" (시니어 변별 포인트)

트레이드오프 판단 문제이므로 양쪽을 다 인정하고 기준을 제시하는 답이 좋다.

Redis의 `SET key value NX PX`는 원자적 선점을 제공하고 훨씬 빠르며 TTL도 공짜다. 단점은 둘이다. **(1) 내구성** — Redis는 기본적으로 비동기 복제라, 페일오버 순간에 방금 쓴 키가 레플리카에 없을 수 있고 그러면 중복 요청이 그대로 통과한다. **(2) 확장의 한계** — 응답 바디 저장과 IN_PROGRESS → COMPLETED 상태 전이까지 얹고 나면 결국 트랜잭션적 일관성이 필요해진다. 그 시점에는 Redis를 DB처럼 쓰고 있는 것이다.

판단 기준을 한 줄로 말하면 **"이 도메인에서 중복 한 건의 비용이 얼마인가"**다.

- **결제**: 이중 결제 한 건의 비용(CS 응대, 환불, 정산 보정, 신뢰 하락)이 DB 쓰기 한 번의 비용보다 압도적으로 크다. **내구성 있는 저장소(DB 유니크 제약)를 기본**으로 하고, Redis는 앞단의 빠른 중복 차단에 보조로 쓴다.
- **조회수 집계처럼 중복돼도 피해가 미미한 API**: Redis 단독으로 충분하다. 여기에 DB 쓰기를 얹는 것이 오히려 과설계다.

**저장소는 도메인의 중복 비용에 따라 고른다**는 기준을 말하는 것이 이 질문의 변별점이다. "결제니까 DB"라고만 답하면 규칙을 외운 것이고, 비용 비교로 답하면 판단할 줄 아는 것이다.

### "PUT은 멱등하다는데, 그럼 결제를 PUT으로 만들면 해결되나요?"

절반만 맞다. 이 질문은 **시맨틱(계약)과 구현을 구분하는지**를 본다.

맞는 절반부터. `PUT /payments/{clientGeneratedId}`처럼 클라이언트가 리소스 식별자를 정해서 올리면 "같은 식별자에 대한 반복 PUT"이라는 멱등 시맨틱을 자연스럽게 얻는다. **사실상 멱등성 키를 헤더가 아니라 URI에 녹인 것**이라, 발상 자체는 같다.

틀린 절반. **멱등성은 계약이지 구현이 아니다.** 메서드를 PUT으로 바꿨다고 프레임워크가 유니크 제약을 걸어주거나, 응답을 저장해 재생해주거나, 동시 도착을 정리해주지 않는다. 2-3부터 2-6까지의 설계를 그대로 다 해야 한다. PUT이라는 이름은 "이 API는 멱등합니다"라는 선언일 뿐이고, 그 선언을 참으로 만드는 것은 여전히 우리 코드와 DB 제약이다(메서드가 강제가 아니라 선언이라는 이야기는 `08-network-http/04-http-method-idempotency-and-safety.md`).

실무적으로는 결제처럼 **생성 + 외부 부수효과(PG 승인)**가 함께 있는 작업에 POST + 멱등성 키를 쓰는 쪽이 관례다. 처리 중(IN_PROGRESS) 상태를 409로 알리는 것 같은 흐름이 "리소스를 이 상태로 만들어라"라는 PUT의 의미보다 POST 쪽에 더 자연스럽게 얹히기 때문이다.

## 한 줄 요약

타임아웃 난 클라이언트는 결제 성공/실패를 원리적으로 알 수 없어 반드시 재시도하므로, 서버가 클라이언트 생성 멱등성 키를 **유니크 제약으로 원자적으로 선점**하고(검사 후 처리가 아니라 선점 후 처리 — 원자성의 출처를 DB 인덱스에 위임해 check-then-act 간극을 없앤다) 최초 응답을 상태 코드까지 저장해 재생함으로써 "N번 보내도 1번 처리"를 API 계약으로 보장해야 한다 — 여기에 같은 키·다른 내용을 422로 거절하는 요청 지문, 처리 중 크래시를 회수하는 리스, 그리고 "멱등성 키는 같은 시도의 재전송만 막으므로 새 키로 온 중복은 주문당 결제 1건 같은 도메인 불변식이 막는다"는 계층 구분까지 겹쳐야 이중 결제가 실제로 막힌다.
