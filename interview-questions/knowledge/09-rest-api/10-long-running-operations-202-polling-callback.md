# 긴 작업의 REST 표현 — "기다리게 하지 말고, 접수증을 줘라" (202 + polling, callback)

> 핵심 관전 포인트: **HTTP 요청-응답은 수 초~수십 초 안에 끝나는 것을
> 전제로 한 프로토콜이다 — 그 사이 클라이언트·게이트웨이·로드밸런서
> 곳곳에 타임아웃이 있다. 몇 분 걸리는 작업(대량 다운로드 생성 등)을
> 동기 API로 만들면 타임아웃 → 클라이언트 재시도 → 같은 무거운 작업의
> 중복 실행이 뒤엉킨다. 해법은 작업 자체를 리소스로 승격시키는 것이다:
> 요청을 받으면 즉시 `202 Accepted` + 상태 조회 URL(`Location:
> /operations/{id}`)만 돌려주고 실제 처리는 백그라운드로 넘긴다.
> 클라이언트는 상태 리소스를 폴링(`Retry-After`로 주기 안내)하다가 완료
> 시 결과 리소스로 안내받는다. 서버-서버 연동이면 폴링 대신 완료 시점에
> 콜백(webhook)으로 통지하되, 콜백은 유실·중복 전제로 서명 검증과 수신
> 측 멱등 처리를 설계해야 한다.**

---

## 0. 질문 + 의도

**질문**: "긴 작업(예: 대량 다운로드 생성)을 REST로 어떻게 표현하나요?
(202 + polling, callback)"

**출제 의도**: HTTP 타임아웃 안에 못 끝나는 작업을 동기 API로 만들면
타임아웃과 재시도 중복 실행이 뒤엉킨다. 프로토콜의 제약을 설계로
수용하는(202 + 상태 조회) 능력을 본다.

## 1. 왜 동기 API로는 안 되는가 — 타임아웃은 한 곳이 아니다

"응답이 늦어도 기다리면 되지 않나?"가 안 되는 이유는, 요청 경로의
**여러 계층이 각자 타임아웃을 갖고 있기** 때문이다.

```text
브라우저/앱 ──> CDN/게이트웨이 ──> 로드밸런서 ──> WAS
 (클라이언트     (프록시 유휴       (idle timeout)   (요청당 스레드
  타임아웃)       타임아웃)                            점유 = 자원 고갈)
```

동기로 긴 작업을 처리하면 벌어지는 일:

1. **중간 계층이 먼저 끊는다.** WAS는 아직 열심히 일하는 중인데
   게이트웨이가 응답 없음으로 연결을 끊고 클라이언트에 504를 준다.
2. **클라이언트는 재시도한다.** 결과를 못 받았으니까. 그런데 서버에서는
   첫 작업이 **아직 돌고 있다** — 같은 대량 작업이 2개, 3개 중복 실행되며
   서버가 더 느려지고, 느려지니 또 타임아웃 나는 악순환.
3. **스레드가 고갈된다.** 요청당 스레드 모델에서 몇 분짜리 요청은 그
   시간 동안 스레드 하나를 통째로 점유한다. 이런 요청이 수십 개면 짧은
   API까지 전부 대기하게 된다.

즉 "긴 작업의 동기 처리"는 정확성(중복 실행)과 가용성(스레드 고갈)을
동시에 해친다. 프로토콜과 싸우지 말고 설계로 수용해야 한다.

비유: 대형 액자 주문을 받는 가게가 손님을 계산대 앞에 3시간 세워두는
대신, **접수증을 주고 돌려보낸 뒤** "진행 상황은 접수번호로 조회하세요,
완성되면 문자 드릴게요"라고 하는 것과 같다. 접수증 = 202 + 상태 URL,
접수번호 조회 = 폴링, 완성 문자 = 콜백이다.

## 2. 202 + 폴링 패턴 — 작업을 리소스로 승격시킨다

핵심 발상: "다운로드 파일을 달라"는 요청을 **"다운로드 생성 작업"이라는
리소스의 생성**으로 모델링한다. 시간이 걸리는 것은 작업이고, 작업에는
상태가 있으며, 상태가 있는 것은 리소스로 표현할 수 있다 — 이것이 REST
어휘로 비동기를 표현하는 방법이다.

### 2-1. 요청 접수 — 202 Accepted

```http
POST /exports HTTP/1.1
Content-Type: application/json

{ "type": "ORDER_HISTORY", "range": { "from": "2026-01-01", "to": "2026-06-30" } }
```

```http
HTTP/1.1 202 Accepted
Location: /operations/op-7f3a
Retry-After: 5

{ "operationId": "op-7f3a", "status": "PENDING" }
```

- **202 Accepted**의 의미는 정확히 "접수했고, 처리는 아직 끝나지
  않았다"이다. 201(생성 완료)도 200(처리 완료)도 아닌 이유가 여기 있다.
- `Location` 헤더에 **상태를 조회할 URL**을 준다 — 클라이언트가 URL을
  조립하게 하지 않고 서버가 알려준다.
- `Retry-After`로 "몇 초 뒤에 물어보라"까지 계약에 담으면, 폴링 주기가
  클라이언트 임의가 아니라 서버 통제가 된다.
- 서버는 접수 시점에 작업 레코드(PENDING)만 저장하고 즉시 응답한다.
  실제 처리는 별도 워커(큐 컨슈머, 배치, `@Async` 등)가 가져간다.

### 2-2. 상태 조회 — 진행 중과 완료의 응답을 구분한다

```http
GET /operations/op-7f3a HTTP/1.1

HTTP/1.1 200 OK
Retry-After: 5

{ "operationId": "op-7f3a", "status": "RUNNING", "progress": 62 }
```

완료되면 상태 리소스가 **결과 리소스의 위치를 안내**한다:

```http
GET /operations/op-7f3a HTTP/1.1

HTTP/1.1 200 OK

{
  "operationId": "op-7f3a",
  "status": "SUCCEEDED",
  "result": { "downloadUrl": "/exports/files/exp-991" }
}
```

설계 포인트:

- **상태는 유한 상태 기계로 명시한다** — 예: `PENDING → RUNNING →
  SUCCEEDED | FAILED`. 어떤 상태가 종결 상태인지(더 폴링할 필요가
  없는지)를 계약에 적는다. 실패 시에는 에러 정보(사유, 재시도 가능 여부)를
  상태 리소스 안에 담는다 — 폴링에 대한 GET 자체는 200이고, **작업의
  실패는 바디의 status로 표현**한다는 구분이 중요하다.
- **상태 리소스와 결과 리소스를 분리한다.** 완료 응답에 거대한 결과를
  직접 싣지 않고 결과 리소스 URL을 준다. 파일이라면 예를 들어 오브젝트
  스토리지의 서명된 URL(만료 시간이 있는 임시 다운로드 링크)을 주는 것이
  일반적이다 — 대용량 전송을 API 서버가 직접 감당하지 않게 된다.
  (가산점 포인트: 완료 시 `303 See Other` + `Location`으로 결과 리소스로
  리다이렉트하는 고전적 변형도 있다고 언급)
- **접수(POST)에는 멱등성 키를 함께 설계한다.** 202를 받기 전에
  타임아웃이 나면 클라이언트는 접수 요청 자체를 재시도한다 — 같은 대량
  작업이 2건 접수되지 않도록 `Idempotency-Key`로 묶는다(→ 같은 카테고리
  `06-idempotency-key-design.md`). 긴 작업일수록 중복 실행 비용이 커서
  이 조합이 사실상 필수다.
- **작업 레코드의 보존 기간**을 정한다. 완료된 operation을 언제까지
  조회 가능하게 둘지(예: 며칠), 만료 후 GET은 404가 된다는 것까지가
  계약이다.

### 2-3. Before / After 요약

```java
// Before: 동기 처리 — 타임아웃과 중복 실행의 진원지
@PostMapping("/exports")
public ExportFile export(@RequestBody ExportRequest req) {
    return exportService.generate(req);   // 몇 분간 스레드 점유
    // 게이트웨이 타임아웃 → 클라이언트 재시도 → 중복 생성
}

// After: 접수와 처리의 분리
@PostMapping("/exports")
public ResponseEntity<OperationResponse> export(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody ExportRequest req) {
    Operation op = operationService.accept(key, req);  // PENDING 저장 + 큐 발행
    return ResponseEntity.accepted()                    // 202
            .location(URI.create("/operations/" + op.id()))
            .header("Retry-After", "5")
            .body(OperationResponse.of(op));
}

@GetMapping("/operations/{id}")
public OperationResponse status(@PathVariable String id) {
    return OperationResponse.of(operationService.find(id));
}
```

## 3. 콜백(webhook) — 폴링을 뒤집는다, 단 실패를 전제로

폴링은 "클라이언트가 계속 묻는" 방식이라 단순하지만, 완료를 즉시 알 수
없고(폴링 주기만큼 지연) 대부분의 폴링이 헛질의다. 소비자가 **서버**라면
(파트너사 연동, 내부 서비스 간) 방향을 뒤집을 수 있다 — 접수 시
클라이언트가 콜백 URL을 등록하고, 완료 시 서버가 그 URL로 통지한다.

```http
POST /exports
{ ..., "callbackUrl": "https://partner.example.com/hooks/export-done" }
```

콜백은 편해 보이지만 **새로운 분산 시스템 문제를 떠안는 것**이다:

- **유실**: 콜백을 쐈는데 상대가 다운이었다면? → 재시도 정책(횟수, 백오프)
  이 필요하고, 그래도 실패하면 최종적으로는 폴링으로 복구할 수 있어야
  한다. 그래서 실무에서는 **콜백 + 상태 조회 API를 함께** 제공하는 것이
  정석이다 — 콜백은 최적화, 폴링은 안전망.
- **중복**: 재시도가 있으면 같은 통지가 두 번 갈 수 있다(at-least-once).
  수신 측은 통지를 멱등하게 처리해야 한다(이벤트 ID로 중복 제거).
- **위조**: 콜백 수신 엔드포인트는 외부에 열린 문이다. 서명(공유 비밀
  기반 HMAC 서명 헤더 등)으로 발신자를 검증하게 해야 한다.
- **순서**: 재시도가 섞이면 통지 순서가 뒤바뀔 수 있다 — 통지 바디에
  상태의 최종값이나 버전을 담아 수신 측이 오래된 통지를 버릴 수 있게 한다.

즉 콜백은 "상대가 서버이고, 통지 인프라(재시도·서명·모니터링)를 감당할
수 있을 때"의 선택지다. 브라우저/모바일 앱은 콜백을 받을 수 없으므로
폴링이 기본이고, 즉시성이 필요하면 SSE(서버가 열린 연결로 이벤트를
흘려보내는 방식)나 WebSocket을 얹는다.

짧은 비교:

| 방식 | 적합한 소비자 | 강점 | 대가 |
|---|---|---|---|
| 폴링 | 모든 클라이언트 | 단순, 방화벽 무관 | 지연, 헛질의 |
| 콜백(webhook) | 서버(파트너·내부) | 즉시 통지, 헛질의 없음 | 재시도·서명·멱등 수신 설계 |
| SSE/WebSocket | 브라우저 | 즉시성 + 진행률 UI | 연결 유지 인프라 |

## 4. 꼬리질문 대비 포인트

### "폴링 주기는 어떻게 정하나요? 클라이언트가 너무 자주 물어보면요?"

서버가 `Retry-After` 헤더로 주기를 내려보내 **주기의 결정권을 서버가
갖는다** — 부하 상황에 따라 서버가 값을 늘릴 수도 있다. 클라이언트
가이드로는 고정 주기보다 점진적으로 간격을 늘리는 백오프를 권하고,
그래도 과도한 폴링이 오면 rate limit(429)으로 방어한다. "폴링 주기까지
API 계약의 일부"라는 인식이 포인트다.

### "결과가 큰 파일이면 상태 조회 응답에 실어주면 안 되나요?"

안 싣는 게 맞다. 상태 조회는 짧은 주기로 반복 호출되는 가벼운 API여야
하는데 결과를 실으면 매 폴링이 무거워질 수 있고, JSON에 파일을 담으려면
인코딩 부담도 생긴다. 결과는 별도 리소스로 분리하고, 파일은 오브젝트
스토리지의 **만료 시간이 있는 서명된 다운로드 URL**로 전달해 대용량
전송을 API 서버 밖으로 내보낸다. "API 서버는 제어(상태), 스토리지는
데이터(파일)"로 역할을 나누는 그림까지 말하면 좋다.

### "콜백이 유실되면 어떻게 하나요?" 

콜백은 at-least-once(최소 1회, 중복 가능)로 설계한다 — 실패 시 백오프를
두고 재시도하고, 최종 실패는 기록해 모니터링한다. 그리고 수신 측이
언제든 진실을 확인할 수 있도록 **상태 조회 API를 항상 함께 제공**한다.
"콜백은 알림(최적화)일 뿐 유일한 전달 수단이 아니다 — source of truth는
상태 리소스"라는 한 문장이 핵심이다. 수신 측 관점의 대비(멱등 처리,
서명 검증)까지 세트로 답한다.

### "진행 중인 작업의 취소는 어떻게 표현하나요?"

작업이 리소스이므로 취소도 리소스 조작으로 표현한다 — 상태 전이를
일으키는 요청(예: `POST /operations/{id}/cancel` 또는 상태 필드를
바꾸는 방식)을 두고, 상태 기계에 `CANCELLED`(종결 상태)를 추가한다.
중요한 건 표현보다 시맨틱이다: 이미 종결된 작업의 취소 요청은 409로
거부하고, "취소 요청 접수"와 "실제 취소 완료"가 다를 수 있다면(워커가
멈추는 데 시간이 걸리면) 취소 자체도 비동기(CANCELLING 상태)로
모델링한다.

### "이 패턴이 오히려 과한 경우는 언제인가요? 기준이 있나요?" (시니어 변별 포인트)

202 패턴은 공짜가 아니다 — 작업 저장소, 워커 인프라, 상태 조회 API,
클라이언트의 폴링 로직, 결과 보존 정책까지 **시스템이 하나 늘어나는
것**이다. 판단 기준은 "작업 시간이 경로상 가장 짧은 타임아웃 안에
안정적으로 들어오는가"다. 수백 ms~수 초에 끝나는 작업을 202로 만들면
복잡도만 산다. 반대로 지금은 2초여도 데이터 증가에 따라 선형으로
길어지는 작업(대량 export가 전형)이라면 미리 비동기 계약으로 시작하는
게 낫다 — **동기 API를 나중에 비동기 계약으로 바꾸는 것은 클라이언트
전부를 고치는 파괴적 변경**이기 때문이다. "지금의 소요 시간"이 아니라
"소요 시간의 성장 곡선"으로 판단한다고 답하면 설계 감각을 보여줄 수 있다.

## 한 줄 요약

타임아웃 안에 못 끝나는 작업은 동기로 붙들지 말고 **작업 자체를 상태를
가진 리소스로 승격**시켜 202 + `Location`으로 접수증을 주고, 폴링
(`Retry-After`)이나 콜백(유실·중복 전제, 상태 조회를 안전망으로)으로
완료를 전달한다 — 접수 요청에는 멱등성 키를 묶어 재시도 중복 실행까지
막아야 이 패턴이 완성된다.
