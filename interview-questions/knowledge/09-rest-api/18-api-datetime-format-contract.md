# API 날짜/시간 포맷 규약 — 타임존 없는 문자열이 만드는 조용한 사고

> 핵심 관전 포인트: **규약의 뼈대는 두 가지 구분이다. ① '시점'은
> ISO 8601 + 오프셋 명시(`2026-08-31T00:30:00Z`)로, '달력상 날짜'는
> 타임존 없는 date-only(`2026-08-31`)로 — 생일에 타임존을 붙이면
> 오히려 하루가 밀린다. ② 저장·전송은 UTC로 통일하고, 사용자 타임존
> 변환(표시)은 클라이언트 책임으로 나눈다. 규약이 없으면 타임존 없는
> datetime 문자열을 클라이언트마다 다르게 해석해 — 브라우저 JS의 파싱
> 규칙조차 형태에 따라 UTC/로컬이 갈린다 — 해외 사용자와 자정
> 경계에서만 터지는 버그가 난다. epoch은 초/밀리초 모호성과 가독성
> 때문에 외부 계약의 기본값으론 부적합. 이걸 팀 규약 문서로 명문화하고
> 직렬화 설정으로 강제하는 것까지가 답이다.**

---

## 0. 질문 + 의도

**질문**: "API 응답의 날짜/시간 포맷은 어떻게 규약하나요? (ISO 8601,
타임존 표기, epoch) 규약이 없으면 어떤 사고가 나나요?"

**출제 의도**: 타임존 없는 문자열, 서버 로컬 시각, epoch 밀리초가
뒤섞인 API는 클라이언트마다 다른 해석을 낳고, 그 버그는 해외
사용자에게서만 발견된다(22장 글로벌·i18n과 연결). 포맷 하나도 팀의
계약으로 명문화하는지 — API 설계의 엄밀함이 가장 사소해 보이는
지점에서 드러난다.

## 1. 규약이 없으면 나는 사고 — 같은 문자열, 다른 해석

규약 없는 API의 전형적인 응답:

```jsonc
// ❌ before: 한 응답 안에 세 가지 유파가 공존한다
{
  "createdAt": "2026-08-31 09:00:00",   // 타임존 없음 — 어느 기준 9시?
  "updatedAt": 1756600000,              // epoch — 초인가 밀리초인가?
  "expiredAt": "2026-09-01T00:00:00"    // T는 있지만 오프셋 없음
}
```

여기서 실제로 벌어지는 사고들:

- **해석이 클라이언트마다 갈린다**: `"2026-08-31 09:00:00"`은 서버
  개발자 머릿속에선 KST지만, 문자열 어디에도 그 정보가 없다. 받은
  쪽은 각자 자기 로컬 타임존이나 UTC로 해석한다. 브라우저 JS는 한술
  더 떠 **형태에 따라 해석이 갈린다** — 스펙상 date-only
  (`"2026-08-31"`)는 UTC로, 오프셋 없는 date-time
  (`"2026-08-31T09:00"`)은 로컬 시각으로 파싱한다. 같은 데이터가 필드
  형태에 따라 9시간씩 어긋나는 것이다.
- **버그가 국내에서 재현되지 않는다**: 서버(KST)와 클라이언트(KST)가
  같은 타임존이면 잘못된 해석끼리 상쇄되어 멀쩡해 보인다. 해외
  사용자, 해외 출장 중인 사용자, UTC로 도는 서버·배치에서만 9시간
  밀림·**날짜 하루 밀림**(자정 경계를 넘는 순간)이 나타난다 — 재현
  안 되는 버그의 전형.
- **epoch 초/밀리초 1000배 사고**: 초 단위 값을 밀리초로 해석하면
  1970년 근처로, 반대면 5만 년 뒤로 간다. "가입일이 1970년으로
  보여요"가 이 사고의 시그니처다.
- **정산·통계의 하루 밀림**: "8월 31일 주문"의 경계가 KST 자정이냐
  UTC 자정이냐에 따라 집계가 9시간어치 달라진다. 일별 정산·리포트가
  시스템마다 다른 숫자를 내는 원인이 대개 여기다.

## 2. 시점의 표준형 — ISO 8601 + 오프셋 명시

'어느 순간'을 가리키는 값(생성 시각, 결제 시각, 만료 시각)의 규약:

```jsonc
// ✅ after: 오프셋이 문자열 안에 있어 해석의 여지가 없다
{
  "createdAt": "2026-08-30T15:00:00Z",        // UTC 표기 (권장 기본)
  "paidAt": "2026-08-31T00:00:00+09:00"       // 오프셋 표기 — 같은 순간의 다른 표현
}
```

- **ISO 8601**(그중에서도 인터넷 프로토콜용으로 좁힌 프로파일이
  RFC 3339)의 핵심은 포맷 자체보다 **오프셋(Z 또는 ±hh:mm)이 값 안에
  포함된다**는 것이다. 해석에 문맥이 필요 없어진다. 텍스트 정렬이
  시간 정렬과 일치하고(같은 오프셋일 때), 사람이 읽을 수 있다는
  실무 이점도 크다.
- **응답은 UTC(Z)로 통일하는 것을 기본값으로**: 서버가 사용자
  타임존을 추측해 변환해주기 시작하면 "누구 기준으로 변환했는가"라는
  새 모호성이 생긴다. 서버는 UTC로 일관되게 주고, 표시 변환은
  사용자 타임존을 아는 클라이언트가 한다 — 책임 분리가 규약의
  일부다. (예외적으로 "매장 현지 시각"처럼 오프셋 자체가 정보인
  도메인은 +09:00 표기를 유지한다.)
- **요청도 같은 규약으로**: 서버는 오프셋 있는 입력만 받고, 오프셋
  없는 datetime은 400으로 거절한다. "관대하게 받아서 서버 타임존으로
  추정"하는 순간 1절의 사고가 입력 방향에서 재발한다.

## 3. '시점'과 '달력상 날짜'는 다른 타입이다

여기가 이 주제의 진짜 변별 지점이다. 모든 시간 값에 타임존을 붙이는
것이 정답이 아니다 — **날짜(date)는 시점(instant)이 아니다.**

```jsonc
// ❌ before: 생일을 시점으로 표현 — 타임존을 붙인 것이 오히려 버그
{ "birthDate": "1990-05-15T00:00:00Z" }
// 뉴욕(-05:00) 클라이언트가 로컬로 변환하면 1990-05-14 19:00 → 화면엔 "5월 14일"

// ✅ after: 달력상 날짜는 타임존 없는 date-only가 정확한 표현
{ "birthDate": "1990-05-15" }
```

- 생일, 기념일, 정산 기준일, 휴무일 같은 값은 "지구상 어느 순간"이
  아니라 "달력의 칸"이다. 어느 타임존에서 봐도 5월 15일은 5월 15일 —
  타임존 변환의 대상이 아니므로 date-only로 주고받아야 한다.
  자바 타입으로 말하면 Instant(시점)와 LocalDate(날짜)의 구분이
  API 계약에도 그대로 필요하다는 것.
- 반대로 **"날짜처럼 보이지만 사실은 시점"인 값**을 조심해야 한다.
  "쿠폰 만료일: 8월 31일"은 실제로는 "어느 타임존의 8월 31일
  자정(또는 23:59)까지"라는 시점 결정이 숨어 있다. 이건 포맷 문제가
  아니라 **도메인 결정**이다 — "만료는 KST 기준 해당일 23:59:59"라고
  정책을 정하고, API에는 그 결과 시점을 오프셋 포함으로
  (`"2026-08-31T14:59:59Z"`) 내보내는 것이 안전하다.
- 필드 네이밍으로 타입을 드러내는 규약이 실무적으로 유용하다:
  `...At`은 오프셋 포함 시점, `...Date`는 date-only — 이름만 봐도
  파싱 방법이 정해진다. (가산점 포인트)

## 4. epoch은 언제 쓰나 — 트레이드오프

epoch(Unix time, 기준 시점부터의 경과 초/밀리초)을 무조건 나쁘다고
하면 반쪽 답이다.

- **장점**: 타임존 해석의 여지가 원천적으로 없다(숫자 하나가 곧
  시점). 정렬·차이 계산이 산술 연산이고, 페이로드가 작다.
- **단점**: **단위(초/밀리초)가 값에 없어** 계약 없이는 1000배 사고가
  난다. 사람이 못 읽어 디버깅·로그 대조 때마다 변환이 필요하다.
  date-only 같은 달력 개념을 표현할 수 없다.
- **판단**: 내부 시스템 간 이벤트, 로그, 성능 민감 구간에서는
  합리적 선택이다. 그러나 사람이 읽고 여러 클라이언트가 소비하는
  외부 API 계약의 기본값으로는 ISO 8601이 낫다. epoch을 쓰기로
  했다면 "밀리초 단위"임을 계약에 명시하고 전 필드에 일관 적용한다 —
  최악은 ISO와 epoch, 초와 밀리초가 API 안에 섞이는 것이다.

## 5. 규약을 문서로 명문화하고, 직렬화 설정으로 강제한다

규약은 문서와 기본 설정 두 겹으로 지켜진다. 문서에 들어갈 항목:

- 시점 포맷(ISO 8601 + 오프셋, UTC 기본), date-only의 사용 기준,
  필드 네이밍(`...At`/`...Date`), 요청 입력 규칙(오프셋 필수),
  소수점 초 자릿수(예: 밀리초 3자리로 고정 — 파서에 따라 자릿수에
  민감한 경우가 있다).

그리고 서버 코드가 규약을 어길 수 없게 기본값을 잠근다:

```java
// ❌ before: 서버 타임존에 의존하는 타입 — 서버 TZ가 바뀌면 값의 의미가 바뀐다
public record OrderResponse(
        LocalDateTime createdAt   // 오프셋 정보가 없는 타입 → 직렬화하면 "2026-08-31T09:00:00"
) {}

// ✅ after: 시점은 오프셋을 아는 타입으로 — 직렬화 결과에 Z가 붙는다
public record OrderResponse(
        Instant createdAt         // "2026-08-31T00:00:00Z"
) {}
```

- Spring Boot + Jackson 조합은 기본으로 java.time 타입을 epoch이
  아닌 ISO 8601 문자열로 직렬화한다(`WRITE_DATES_AS_TIMESTAMPS`
  비활성). 문제는 라이브러리가 아니라 **타입 선택**이다 —
  LocalDateTime은 오프셋 정보가 없어서 직렬화해도 오프셋 없는
  문자열이 나온다. 시점 필드는 Instant(또는 OffsetDateTime)로.
- 서버·컨테이너의 기본 타임존은 UTC로 통일한다. "로컬에선 됐는데
  서버에선 9시간 밀린다"의 상당수가 환경별 기본 타임존 차이 +
  타임존 없는 타입의 조합이다. DB도 마찬가지로 세션/서버 타임존
  설정에 따라 값이 달리 해석되는 타입이 있으므로, "DB에는 UTC
  기준으로 저장"을 같은 규약에 포함시킨다.

## 6. 꼬리질문 대비 포인트

### "왜 저장·전송은 UTC로 하고, 표시 변환은 클라이언트가 하나?"

시점의 '값'과 '표현'을 분리하기 위해서다. 같은 순간도 타임존마다
표현이 다른데, 사용자의 타임존을 아는 것은 클라이언트뿐이다(기기
설정·브라우저). 서버가 표시까지 책임지려면 사용자별 타임존을
추측·관리해야 하고, 캐시 공유도 깨진다(같은 리소스가 사용자마다 다른
바디). 서버는 단일 기준(UTC)의 값을 주고 클라이언트가 표시를
맡는 분업이, 저장(비교·정렬·집계가 단일 기준에서 성립)과 전송(해석
모호성 제거) 양쪽에서 단순하다. 단, "일별 집계" 같은 서버 사이드
날짜 경계 연산은 어느 타임존의 자정인지 정책 결정이 별도로
필요하다는 것까지 말하면 좋다.

### "epoch 밀리초는 파싱 모호성이 없는데 왜 기본값으로 안 쓰나?"

모호성이 없다는 전제가 이미 계약("밀리초다")에 의존한다 — 값 자체에
단위가 없어서 초/밀리초 1000배 사고가 계약 부재의 첫 희생자가 된다.
그리고 외부 API의 소비자는 기계만이 아니다: 디버깅 중 로그와 응답을
눈으로 대조하는 개발자, 문서를 읽는 파트너에게 epoch은 매번 변환
비용이다. date-only 표현이 불가능한 것도 API 전체를 한 포맷으로
통일하는 데 걸림돌이다. 내부 이벤트 스트림·로그처럼 기계 간 대량
교환에는 epoch(단위 명시)이 합리적이고, 외부 계약 기본값은 ISO
8601 — "어디에 쓰느냐"로 답하면 된다.

### "생일 같은 필드에 타임존을 붙이면 무슨 일이 생기나?"

달력상 날짜를 시점(`...T00:00:00Z`)으로 인코딩하는 순간, 클라이언트의
"로컬 변환 후 표시"라는 표준 처리가 그 값을 망가뜨린다 — UTC 자정은
UTC보다 서쪽 타임존에서 전날 저녁이 되어 생일이 하루 밀려 보인다.
날짜는 타임존 변환의 대상이 아니므로 date-only(`"1990-05-15"`)로
주고받는 것이 정확한 표현이다. 이 질문의 본질은 "모든 시간 값에
타임존을 붙이는 게 정답은 아니다 — 시점과 날짜는 타입이 다르다"는
구분을 하는지다.

### "미래의 예약 시각도 UTC로 변환해 저장하면 되나?" (시니어 변별 포인트)

과거·현재의 시점은 UTC 저장이 정답이지만, **미래의 '벽시계 약속'은
예외**다. "2027년 3월 10일 오전 9시 서울 회의"를 지금 UTC로 환산해
고정하면, 그 사이 해당 지역의 타임존 규칙(서머타임 도입·폐지, 기준
오프셋 변경 — 실제로 각국에서 종종 일어난다)이 바뀌었을 때 사용자가
의도한 "현지 9시"와 어긋난다. 미래의 약속은 **현지 시각 + 타임존
ID(`Asia/Seoul` — 오프셋 `+09:00`이 아니라 규칙을 가리키는 지역
ID)**로 저장하고, 실행 시점에 그때의 규칙으로 UTC를 계산하는 것이
안전하다. "UTC로 통일"이라는 원칙의 예외 조건을 아는지가 이 질문의
변별점이다.

### "서버와 DB의 타임존 설정은 어떻게 관리하나?"

코드가 "기본 타임존"에 의존하는 지점을 없애는 방향으로 관리한다.
JVM·컨테이너·DB 세션의 기본 타임존을 UTC로 통일해 환경 간 차이를
제거하고, 애초에 기본 타임존을 읽는 타입/API(LocalDateTime으로 현재
시각 만들기, 타임존 인자 없는 변환) 대신 Instant처럼 기준이 명시된
타입을 쓴다. DB는 타임존 정보를 어떻게 다루는 타입인지(저장 시
변환 여부, 세션 타임존의 영향)를 확인해 "UTC 기준 저장"이 설정이
아니라 스키마 차원에서 성립하게 한다. 요지는 "설정을 잘 맞춘다"가
아니라 "설정이 뭐든 결과가 같도록 의존을 없앤다"이다.

## 한 줄 요약

날짜/시간 규약의 요체는 포맷 암기가 아니라 두 가지 분리다 — 시점은
오프셋이 값 안에 박힌 ISO 8601(UTC 기본)로, 달력상 날짜는 date-only로
구분하고, 값의 기준(UTC 저장·전송)과 표현(클라이언트 변환)의 책임을
나눈 뒤, 이를 팀 문서와 직렬화 기본값으로 강제하는 것 — 이 계약이
없으면 같은 문자열을 클라이언트마다 다르게 해석하는 버그가 해외
사용자와 자정 경계에서만 조용히 터진다.
