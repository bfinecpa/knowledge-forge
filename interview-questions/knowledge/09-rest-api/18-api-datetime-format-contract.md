# API 날짜/시간 포맷 규약 — 타임존 없는 문자열이 만드는 조용한 사고

> 핵심 관전 포인트: **규약의 뼈대는 두 가지 구분이다. ① **'시점(instant)'과 '달력상 날짜(date)'는 다른 타입이다** — 시점은 ISO 8601 + 오프셋 명시(`2026-08-31T00:30:00Z`)로, 달력상 날짜는 타임존 없는 date-only(`2026-08-31`)로 주고받는다. 생일에 타임존을 붙이면 오히려 하루가 밀린다. ② **값의 기준과 값의 표현은 책임이 다르다** — 저장·전송은 UTC로 통일하고, 사용자 타임존으로 바꿔 보여주는 일은 사용자의 타임존을 아는 유일한 주체인 클라이언트가 맡는다. 그리고 이 논의 전체를 떠받치는 선행 구분이 하나 더 있다. **오프셋(`+09:00`)은 "그 순간 UTC와 몇 시간 차이인가"라는 숫자 하나이고, 타임존 ID(`Asia/Seoul`)는 "이 지역의 시차가 언제 어떻게 바뀌어 왔고 앞으로 어떤 규칙으로 바뀌는가"를 담은 규칙 묶음이다** — 같은 `America/New_York`이 겨울엔 `-05:00`, 여름엔 `-04:00`인 것이 그 차이다. 규약이 없으면 타임존 없는 datetime 문자열을 클라이언트마다 다르게 해석해 — 브라우저 JS의 파싱 규칙조차 date-only는 UTC로, 오프셋 없는 date-time은 로컬로 갈린다 — 해외 사용자와 자정 경계에서만 터지는 버그가 난다. epoch은 초/밀리초 모호성과 가독성 때문에 외부 계약의 기본값으론 부적합하다. 이걸 팀 규약 문서로 명문화하고, 애플리케이션 타입·직렬화 설정·DB 컬럼 타입까지 잠가 두는 것까지가 답이다.**

---

## 0. 질문 + 의도

**질문**: "API 응답의 날짜/시간 포맷은 어떻게 규약하나요? (ISO 8601, 타임존 표기, epoch) 규약이 없으면 어떤 사고가 나나요?"

**출제 의도**: 타임존 없는 문자열, 서버 로컬 시각, epoch 밀리초가 뒤섞인 API는 클라이언트마다 다른 해석을 낳고, 그 버그는 해외 사용자에게서만 발견된다(22장 글로벌·i18n과 연결). 포맷 하나도 팀의 계약으로 명문화하는지 — API 설계의 엄밀함이 가장 사소해 보이는 지점에서 드러난다.

## 1. 규약이 없으면 나는 사고 — 같은 문자열, 다른 해석

### 1-1. 전제 — 오프셋과 타임존 ID는 다른 것이다

이 문서 전체가 이 구분 위에 서 있으므로 먼저 짚고 시작한다. "타임존을 붙인다"는 말이 실제로는 서로 다른 두 가지를 가리키기 때문이다.

**오프셋(offset, `+09:00` / `Z`)은 "그 순간 UTC와 몇 시간 차이인가"를 나타내는 숫자 하나다.** `2026-08-31T09:00:00+09:00`은 "UTC보다 9시간 빠른 곳의 9시", 즉 UTC 00시를 가리킨다. 그 순간이 시간선의 어디인지 계산하는 데 필요한 정보는 이것으로 충분하다. 다만 이 값은 **어느 지역인지는 말해 주지 않는다** — `+09:00`은 서울일 수도, 도쿄일 수도, 여름의 이르쿠츠크일 수도 있다.

**타임존 ID(`Asia/Seoul`, `America/New_York`)는 "이 지역의 시차가 역사적으로 언제 어떻게 바뀌었고, 앞으로 어떤 규칙으로 바뀌는가"를 담은 규칙 묶음의 이름이다.** 숫자가 아니라 규칙이므로, 같은 ID가 시점에 따라 다른 오프셋을 내놓는다.

**서머타임이 있는 지역을 보면 차이가 한 번에 보인다.** `America/New_York`은 같은 ID인데도 계절에 따라 오프셋이 바뀐다.

```text
ZoneId ny = ZoneId.of("America/New_York");

  2026-01-15 12:00  →  오프셋 -05:00   (겨울, 표준시)
  2026-07-15 12:00  →  오프셋 -04:00   (여름, 서머타임)
                          ↑
        같은 타임존 ID 인데 오프셋이 1시간 다르다.
        "America/New_York = -05:00" 이라고 외워 두면 여름에 한 시간씩 틀린다.
```

한국이 예외인 것도 아니다. `Asia/Seoul`은 지금은 언제나 `+09:00`이지만, **1987~1988년 두 해 동안은 서머타임이 있어 여름 오프셋이 `+10:00`이었다.** 규칙은 실제로 바뀐다.

정리하면 이렇다.

| | 오프셋 (`+09:00`) | 타임존 ID (`Asia/Seoul`) |
|---|---|---|
| 정체 | 숫자 하나 (UTC와의 차이) | 규칙 묶음의 이름 |
| 답할 수 있는 것 | "이 문자열이 가리키는 순간은 언제인가" | "이 지역의 2027년 3월 10일 9시는 언제인가" |
| 답할 수 없는 것 | 어느 지역인지, 다른 날엔 몇 시간 차이인지 | (없음 — 오프셋을 계산해 낼 수 있다) |
| 규칙이 바뀌면 | 이미 박힌 숫자라 그대로 (과거 시점엔 이게 맞다) | 새 규칙을 따라간다 (미래 약속엔 이게 맞다) |

이 표의 마지막 줄이 §4 마지막 꼬리질문(미래 예약 시각)의 답을 미리 담고 있다. **지나간 순간을 기록할 때는 오프셋으로 충분하고, 앞으로 올 약속을 기록할 때는 타임존 ID가 필요하다.**

여기서 "규칙"의 실체가 무엇인지도 짚어 두자. **IANA tzdb**(IANA Time Zone Database, `tz database`라고도 한다)는 전 세계 지역별 타임존 규칙 — 표준 오프셋, 서머타임 시작·종료 규칙, 그리고 과거의 변경 이력까지 — 을 모아 관리하는 공개 데이터베이스다. 각국 정부가 규칙을 바꾸면 갱신판이 발표되고(연 몇 차례), JDK·운영체제·브라우저가 그것을 받아 반영한다. `ZoneId.of("Asia/Seoul")`이 실제로 참조하는 것이 이 데이터이고, JDK에 어떤 판이 실려 있는지는 버전 문자열(`2025b` 같은)로 확인할 수 있다. 규칙 변경이 추상적인 이야기가 아니라 **정기적으로 배포되는 데이터의 변경**이라는 것이 요점이다.

### 1-2. 규약 없는 응답 — 한 JSON 안에 세 가지 유파가 공존한다

```jsonc
// Before: 규약 없는 API 의 전형
{
  "createdAt": "2026-08-31 09:00:00",   // 타임존 없음 — 어느 기준의 9시인가?
  "updatedAt": 1788134400,              // epoch — 초인가 밀리초인가?
  "expiredAt": "2026-09-01T00:00:00"    // T 는 있지만 오프셋이 없다
}
```

세 필드 모두 "언제인지 알 수 없는 값"이다. 서버 개발자 머릿속에서는 전부 KST지만, **문자열 어디에도 그 정보가 없다.** 받는 쪽은 각자 자기 로컬 타임존이나 UTC로 해석한다.

그리고 이 사고에는 고약한 성질이 하나 있다. **국내에서 재현되지 않는다.** 서버(KST)와 클라이언트(KST)가 같은 타임존이면 잘못된 해석끼리 상쇄되어 멀쩡해 보이기 때문이다. 해외 사용자, 해외 출장 중인 사용자, UTC로 도는 배치 서버에서만 9시간 밀림과 날짜 하루 밀림이 나타난다. 개발자 자리에서는 100% 정상인 버그다.

### 1-3. 브라우저 JS는 문자열의 형태에 따라 해석이 갈린다

가장 결정적인 사례가 여기다. 자바스크립트의 `new Date(문자열)`은 **같은 데이터라도 문자열이 어떤 모양이냐에 따라 UTC로 볼지 로컬로 볼지가 갈린다.**

ECMAScript 명세는 날짜/시간 문자열을 두 부류로 나눠 다르게 정의한다. **오프셋이 없을 때, date-only 형태(`"2026-08-31"`)는 UTC로, date-time 형태(`"2026-08-31T00:00:00"`)는 로컬 시각으로 해석한다.** 하나의 함수 안에 서로 반대되는 두 규칙이 들어 있는 셈이다.

실제로 돌려 보면 이렇게 어긋난다.

```text
$ TZ=Asia/Seoul node
> new Date("2026-08-31").toISOString()
'2026-08-31T00:00:00.000Z'        ← date-only 라서 UTC 자정으로 해석

> new Date("2026-08-31T00:00:00").toISOString()
'2026-08-30T15:00:00.000Z'        ← date-time 이라서 KST 자정으로 해석 → UTC 로는 전날 15시

          같은 "8월 31일 0시"인데 결과가 9시간 어긋나고,
          UTC 기준으로는 날짜까지 하루 다르다.
```

날짜가 하루 밀리는 쪽도 실증된다. UTC 자정으로 해석된 값을 서쪽 타임존에서 표시하면 전날이 된다.

```text
$ TZ=America/New_York node
> new Date("2026-08-31").toLocaleString("en-US")
'8/30/2026, 8:00:00 PM'           ← 화면에는 8월 30일로 뜬다
```

여기서 실무적으로 중요한 따름 결론이 하나 나온다. **date-only 문자열도 `Date`에 넣는 순간 UTC 시점이 되어 버리므로, 날짜 값은 애초에 `Date`로 파싱하지 않는 것이 맞다.** 문자열 그대로 다루거나, 날짜 전용 타입(브라우저에 순차 도입되고 있는 Temporal API의 `PlainDate` 등)을 쓴다. §3의 "날짜는 시점이 아니다"가 서버만의 이야기가 아니라는 뜻이다.

참고로 `"2026-08-31 09:00:00"`처럼 `T` 대신 공백을 쓴 형태는 **ECMAScript 명세가 정의하는 형식이 아니다.** 이 경우 동작은 각 엔진의 재량이라, 어떤 엔진은 로컬 시각으로 관대하게 받아 주고 어떤 엔진은 `Invalid Date`를 낸다. "우리 브라우저에서는 되던데요"가 통하지 않는 영역이다.

### 1-4. epoch 초/밀리초 1000배 사고

epoch은 기준 시점(1970-01-01T00:00:00Z)부터의 경과 시간을 나타내는 숫자다. 문제는 **단위(초인지 밀리초인지)가 값 안에 적혀 있지 않다**는 것이다. 그래서 한쪽이 초로 보내고 다른 쪽이 밀리초로 읽으면 1000배가 어긋난다.

어긋나는 규모를 직접 계산해 보면 왜 "가입일이 1970년으로 보여요"가 이 사고의 시그니처인지 알 수 있다.

```text
기준 값: 2026-08-31T00:00:00Z
  초 단위    = 1,788,134,400
  밀리초 단위 = 1,788,134,400,000

① 초 값을 밀리초로 오해했을 때 (1000배 작게 읽는다)
   1,788,134,400 ms = 1,788,134.4 초 = 약 20.7 일
   → 1970-01-21T16:42:14Z
   ※ 어떤 값을 보내든 1970년 1월 안쪽으로 몰린다.
      epoch 초 값은 대략 17억이고, 그것을 밀리초로 읽으면 17,000,000초 ≈ 200일을
      넘지 못하기 때문이다. "1970년으로 보인다"가 이 사고의 지문(指紋)인 이유.

② 밀리초 값을 초로 오해했을 때 (1000배 크게 읽는다)
   1,788,134,400,000 초 = 20,696,000 일 ÷ 365.2425 ≈ 56,664 년
   → 서기 58,633 년
   ※ 흔히 "5만 년 뒤"라고 말하는 값이 이것이다.
```

두 방향 모두 값이 **터무니없이 멀리** 떨어진다는 것이 오히려 다행이다. 눈에 띄게 이상하기 때문이다. 정말 위험한 것은 다음 항목처럼 **그럴듯하게 조금 틀리는** 경우다.

### 1-5. 정산·통계의 하루 밀림 — 조금만 틀려서 더 위험하다

"8월 31일 주문"의 경계가 KST 자정이냐 UTC 자정이냐에 따라 집계 대상이 9시간어치 달라진다. 일별 정산·리포트가 시스템마다 다른 숫자를 내는 원인이 대개 여기다.

```text
                     8/30                    8/31                    9/1
KST 기준 하루  │──────────────────────│──────────────────────│
UTC 기준 하루      │──────────────────────│──────────────────────│
                   ↑ 9시간 어긋난다
                   
  8/31 00:00~08:59 KST 에 들어온 주문 = UTC 기준으로는 8/30 의 주문
  → 어느 쪽 자정을 하루의 경계로 볼지 정하지 않으면
     같은 데이터로 만든 두 리포트의 숫자가 다르다.
```

1000배 사고는 숫자가 워낙 이상해서 금방 잡히지만, 이 밀림은 **매출이 몇 퍼센트 다르게 나오는** 형태라 몇 달간 아무도 눈치채지 못할 수 있다. 그래서 "일별 집계의 하루 경계는 어느 타임존의 자정인가"는 포맷 규약과 별개로 반드시 문서에 못박아야 하는 정책 결정이다.

## 2. 시점의 표준형 — ISO 8601 + 오프셋 명시

### 2-1. 오프셋을 값 안에 넣는다

'어느 순간'을 가리키는 값(생성 시각, 결제 시각, 만료 시각)의 규약은 하나다.

```jsonc
// After: 오프셋이 문자열 안에 있어 해석의 여지가 없다
{
  "createdAt": "2026-08-30T15:00:00Z",        // UTC 표기 (권장 기본)
  "paidAt": "2026-08-31T00:00:00+09:00"       // 오프셋 표기 — 같은 순간의 다른 표현
}
```

핵심은 포맷의 모양이 아니라 **오프셋(`Z` 또는 `±hh:mm`)이 값 안에 포함된다**는 것이다. 해석에 문맥이 필요 없어진다는 뜻이고, 그래서 "서버가 어느 타임존이더라"를 아는 사람만 값을 읽을 수 있는 상황이 사라진다.

덤으로 따라오는 실무 이점도 있다. 같은 오프셋으로 통일하면 **텍스트를 사전순으로 정렬한 결과가 시간순 정렬과 일치하고**(자릿수가 고정이라 문자 비교가 곧 크기 비교다), 사람이 로그를 눈으로 읽을 수 있다.

#### ISO 8601과 RFC 3339의 관계 — 같은 말이 아니다

이 자리에서 자주 뭉뚱그려지는 두 이름을 정리하고 가자.

- **ISO 8601**은 날짜와 시간을 표기하는 국제 표준이다. 범위가 매우 넓어서 기간(`P1Y2M`), 시간 구간, 주 번호 날짜(`2026-W35-1`), 연중 일수 날짜(`2026-243`), 구분자를 뺀 기본 형식(`20260831T090000Z`)까지 전부 포함한다.
- **RFC 3339**는 그중 인터넷 프로토콜에서 쓸 타임스탬프 표기를 위해 **좁게 골라낸 프로파일**이다. `YYYY-MM-DDThh:mm:ss(.sss)?(Z|±hh:mm)` 한 가지 모양으로 사실상 고정하고, 오프셋을 필수로 요구한다.

주의할 점은 **완전한 포함 관계가 아니라는 것**이다. 대체로 RFC 3339가 ISO 8601의 부분집합이지만, 서로 허용 범위가 조금씩 어긋나는 지점이 있다(대표적으로 RFC 3339는 "오프셋을 모른다"는 뜻의 `-00:00` 표기를 허용하는데 ISO 8601은 그렇지 않다). 세부까지 단정하기보다 **실무적 결론**을 기억하는 편이 낫다.

**계약 문서에 "ISO 8601 형식"이라고만 적으면 부족하다.** ISO 8601은 위에서 본 대로 주 번호 날짜나 구분자 없는 형식까지 포함하는 넓은 표준이라, 그 말만으로는 상대가 무엇을 보내도 규격 위반이 아니게 된다. 실제 허용 형태를 예시로 못박는다 — "`2026-08-31T00:00:00.000Z` 형태, 오프셋 필수, 소수점 초 3자리 고정" 같은 식으로.

### 2-2. 응답은 UTC 기본, 요청도 같은 규약으로

**응답의 기본값은 UTC(`Z`) 표기로 통일한다.** 서버가 사용자 타임존을 추측해 변환해 주기 시작하면 "누구 기준으로 변환한 값인가"라는 새 모호성이 생기고, 같은 리소스가 사용자마다 다른 바디를 갖게 되어 캐시 공유도 깨진다. 서버는 단일 기준의 값을 주고, 표시 변환은 사용자 타임존을 아는 클라이언트가 한다 — **책임 분리가 규약의 일부다.**

예외는 **오프셋 자체가 도메인 정보인 경우**다. "매장 현지 영업 시작 시각"처럼 "현지에서 몇 시였는가"가 의미를 갖는 값이라면 `+09:00` 표기를 유지한다. UTC로 바꿔 버리면 정보가 사라지기 때문이다.

**요청도 같은 규약을 적용한다.** 서버는 오프셋이 있는 입력만 받고, 오프셋 없는 datetime은 400으로 거절한다. "관대하게 받아서 서버 타임존으로 추정하자"는 순간 §1의 사고가 입력 방향에서 그대로 재발한다 — 그리고 입력 쪽 사고는 잘못된 값이 DB에 저장되므로 응답 쪽보다 회복이 훨씬 어렵다.

### 2-3. Java 시간 타입 — 무엇을 담는지가 다르다

포맷 규약을 코드로 지키려면 타입을 골라야 하는데, `java.time`의 타입들은 이름이 비슷해서 자주 혼동된다. **각 타입이 무엇을 담고 무엇을 담지 않는지**를 한 번에 놓고 보는 것이 가장 빠르다.

| 타입 | 무엇을 담는가 | 타임존 정보 | 어느 필드에 쓰나 | `toString()` 결과 |
|---|---|---|---|---|
| `Instant` | 시간선 위의 한 점 (epoch부터의 경과 시간) | 없음 — 항상 UTC 기준이라 필요가 없다 | **시점 필드의 기본값.** 생성·결제·수정 시각 | `2027-03-10T00:00:00Z` |
| `OffsetDateTime` | 시점 + 그때의 UTC 오프셋 | 오프셋(숫자)만 | 현지 오프셋 자체가 정보인 값 (매장 현지 시각) | `2027-03-10T09:00+09:00` |
| `ZonedDateTime` | 시점 + 타임존 ID(규칙) | **타임존 ID(규칙 묶음)** | **미래 예약** — 규칙이 바뀌어도 따라가야 하는 값 | `2027-03-10T09:00+09:00[Asia/Seoul]` |
| `LocalDateTime` | 날짜 + 시각. **어느 타임존인지는 어디에도 없다** | 없음 | 시점 필드에 쓰면 안 된다 | `2027-03-10T09:00` |
| `LocalDate` | 달력의 칸 | 없음 (있어서도 안 된다) | 생일·정산 기준일·휴무일 (§3) | `2027-03-10` |

이 표에서 두 가지가 나온다.

**`LocalDateTime`이 왜 위험한가.** 이름에 `Local`이 붙어 있어 "로컬 타임존의 시각"처럼 읽히지만, **어느 타임존이 그 '로컬'인지는 값 어디에도 적혀 있지 않다.** 담고 있는 것은 "2027년 3월 10일 9시"라는 달력·시계의 읽음값뿐이다. 그래서 직렬화해도 오프셋 없는 문자열(`"2027-03-10T09:00"`)이 나가고, §1-3의 사고가 그대로 발생한다. 게다가 이 타입으로 현재 시각을 만들면(`LocalDateTime.now()`) JVM의 기본 타임존을 읽어 오므로, **로컬 개발 머신(KST)과 운영 컨테이너(UTC)에서 같은 코드가 다른 값을 만든다.** "로컬에선 됐는데 서버에선 9시간 밀린다"의 정체가 대개 이것이다.

**`ZonedDateTime`이 왜 미래 예약에 적합한가.** 오프셋 숫자가 아니라 **타임존 ID를 들고 있기 때문**이다. `2027-03-10T09:00[Asia/Seoul]`은 "그때 서울의 규칙으로 계산했을 때의 오전 9시"라는 뜻이라, 그 사이 규칙이 바뀌면 계산 결과인 순간도 함께 바뀐다. 사용자가 의도한 것이 바로 그 "현지 9시"다(§4 마지막 꼬리질문).

단, `ZonedDateTime`을 API 계약에 쓸 때는 함정이 하나 있다. **Jackson은 기본 설정에서 직렬화 시 `[Asia/Seoul]` 부분을 떼고 오프셋만 내보낸다**(`WRITE_DATES_WITH_ZONE_ID`가 기본 비활성). 즉 자바 안에서는 규칙을 들고 있어도 JSON으로 나가는 순간 오프셋 숫자로 납작해진다. 그래서 미래 예약을 API로 주고받을 때는 대괄호 표기에 기대지 말고 **필드를 둘로 나누는 것**이 안전하다.

```jsonc
// 미래의 벽시계 약속 — 현지 시각과 타임존 ID 를 각각 명시적인 필드로 둔다
{
  "startsAt": "2027-03-10T09:00:00",   // 오프셋 없는 현지 시각 (여기서는 이게 맞다)
  "timeZone": "Asia/Seoul"             // 규칙을 가리키는 ID
}
```

### 2-4. epoch은 언제 쓰나 — 트레이드오프

epoch을 무조건 나쁘다고 하면 반쪽 답이다. 장단이 분명한 선택지이므로 나눠 보자.

- **장점**: 타임존 해석의 여지가 원천적으로 없다(숫자 하나가 곧 시점이다). 정렬·차이 계산이 그냥 산술 연산이고, 페이로드가 작다.
- **단점**: **단위(초/밀리초)가 값에 없어** 계약이 없으면 §1-4의 1000배 사고가 난다. 사람이 못 읽어서 디버깅·로그 대조 때마다 변환이 필요하다. 그리고 달력 개념(date-only)을 표현할 수 없어 API 전체를 한 포맷으로 통일하는 데 걸림돌이 된다.
- **판단**: 내부 시스템 간 이벤트, 로그, 성능 민감 구간에서는 합리적 선택이다. 그러나 **사람이 읽고 여러 클라이언트가 소비하는 외부 API 계약의 기본값으로는 ISO 8601이 낫다.** epoch을 쓰기로 했다면 "밀리초 단위"임을 계약에 명시하고 전 필드에 일관 적용한다. 최악은 ISO와 epoch, 초와 밀리초가 한 API 안에 섞이는 것이다(§1-2가 정확히 그 모습이다).

## 3. '시점'과 '달력상 날짜'는 다른 타입이다 — 그리고 그 구분을 코드·DB·문서에 박는다

### 3-1. 날짜는 시점이 아니다

여기가 이 주제의 진짜 변별 지점이다. **모든 시간 값에 타임존을 붙이는 것이 정답이 아니다.**

```jsonc
// Before: 생일을 시점으로 표현 — 타임존을 붙인 것이 오히려 버그다
{ "birthDate": "1990-05-15T00:00:00Z" }

// After: 달력상 날짜는 타임존 없는 date-only 가 정확한 표현이다
{ "birthDate": "1990-05-15" }
```

Before가 왜 버그인지 실제로 확인해 보자. 클라이언트의 표준 처리는 "받은 시점을 사용자 로컬 타임존으로 변환해 표시"인데, 그 처리가 이 값을 망가뜨린다.

```text
$ TZ=America/New_York node
> new Date("1990-05-15T00:00:00Z").toLocaleString("en-US")
'5/14/1990, 8:00:00 PM'      ← 뉴욕 사용자 화면에는 "5월 14일"로 뜬다
```

생일, 기념일, 정산 기준일, 휴무일 같은 값은 "지구상 어느 순간"이 아니라 **"달력의 칸"**이다. 어느 타임존에서 봐도 5월 15일은 5월 15일이므로 애초에 타임존 변환의 대상이 아니다. 자바 타입으로 말하면 `Instant`(시점)와 `LocalDate`(날짜)의 구분이 API 계약에도 그대로 필요하다는 뜻이다.

### 3-2. 날짜처럼 보이지만 사실은 시점인 값을 조심한다

반대 방향의 함정도 있다. **"쿠폰 만료일: 8월 31일"은 겉보기엔 날짜지만 실제로는 시점 결정이 숨어 있다.**

"8월 31일까지 쓸 수 있다"는 말은 정확히 언제까지인가? KST 8월 31일 23:59:59까지인가, UTC 기준인가, 사용자가 있는 지역의 자정인가? 이건 포맷 문제가 아니라 **도메인 결정**이다. 그리고 결정하지 않으면 "분명 31일인데 못 쓴다"는 CS가 자정 무렵에만 들어온다.

결정한 뒤에는 그 결과를 시점으로 내보낸다. "만료는 KST 기준 해당일 23:59:59"로 정했다면 이렇게 된다.

```text
KST 2026-08-31 23:59:59  =  UTC 로 환산하면 9시간을 뺀다
                         =  2026-08-31 14:59:59Z          ✓ 검산 완료

  (같은 방식으로 "KST 9월 1일 자정 직전까지"를 경계로 잡으면
   2026-08-31T15:00:00Z 미만이라는 조건이 된다 — 경계를 '이하'로 잡을지
   '미만'으로 잡을지도 함께 정해야 한다.)
```

```jsonc
{ "expiresAt": "2026-08-31T14:59:59Z" }   // 도메인 결정의 결과를 시점으로 명시
```

### 3-3. 필드 네이밍으로 타입을 드러낸다

두 종류를 구분했으면 **이름만 봐도 어느 쪽인지 알 수 있게** 하는 것이 실무적으로 유용하다. (가산점 포인트)

- `...At` → 오프셋 포함 시점 (`createdAt`, `paidAt`, `expiresAt`)
- `...Date` → date-only (`birthDate`, `settlementDate`, `holidayDate`)

이름 규칙 하나로 클라이언트 개발자가 "이 필드는 로컬 변환해서 보여줘야 하는가, 그대로 찍어야 하는가"를 문서를 찾지 않고 판단할 수 있다.

### 3-4. DB 타입도 같은 구분을 따른다 — PostgreSQL 기준

애플리케이션의 `Instant` / `LocalDate` 구분은 **DB 컬럼 타입 선택에 그대로 이어진다.** 여기서 PostgreSQL의 이름이 오해를 많이 사므로 정확히 짚어야 한다.

**`timestamptz`(= `timestamp with time zone`)는 이름과 달리 타임존을 저장하지 않는다.** 하는 일은 이렇다.

```text
[입력]  '2026-08-31T00:00:00+09:00'  또는  '2026-08-31 00:00:00'
           │                                   │
           │ 오프셋이 있으면 그것으로 해석      │ 오프셋이 없으면 세션 타임존으로 해석
           ↓                                   ↓
        ┌──────────────────────────────────────────┐
        │ UTC 로 변환해 "그 순간"만 8바이트로 저장 │   ← 지역 정보는 여기서 버려진다
        └──────────────────────────────────────────┘
           │
           │ 조회할 때 세션의 TimeZone 설정으로 다시 변환해 보여준다
           ↓
[출력]  SET TIME ZONE 'UTC'        → 2026-08-30 15:00:00+00
        SET TIME ZONE 'Asia/Seoul' → 2026-08-31 00:00:00+09
                                     ↑ 같은 행인데 표시가 다르다. 값은 같은 순간이다.
```

반면 **`timestamp`(= `timestamp without time zone`)는 변환을 하지 않고 적힌 그대로를 보관한다.** 오프셋이 붙은 문자열을 넣어도 오프셋 부분을 **조용히 버리고** 나머지만 저장한다. 그래서 저장된 값만 봐서는 **"어느 순간"인지 알 수 없다** — 애플리케이션의 `LocalDateTime`과 정확히 같은 결함을 공유한다.

| PostgreSQL 타입 | 저장하는 것 | 세션 타임존의 영향 | 짝이 되는 Java 타입 |
|---|---|---|---|
| `timestamptz` | 시간선 위의 한 점 (UTC로 정규화) | 입력 해석과 출력 표시에만 영향. **저장된 값 자체는 무관** | `Instant` / `OffsetDateTime` |
| `timestamp` | 달력·시계의 읽음값 (기준 없음) | 없음 — 대신 어느 순간인지 알 수 없다 | `LocalDateTime` (시점 필드엔 쓰지 않는다) |
| `date` | 달력의 칸 | 없음 (있어서도 안 된다) | `LocalDate` |

**결론은 단순하다. 시점(instant) 필드는 `timestamptz`, 달력상 날짜는 `date`다.** `timestamptz`가 나은 결정적 이유는 세션 설정과 무관하게 **비교·정렬·집계가 항상 같은 결과를 내기 때문**이다. 저장된 값이 이미 단일 기준(UTC)의 한 점이므로, 세션 타임존을 어떻게 바꿔도 `a < b`의 판정이 뒤집히지 않는다. `timestamp` 컬럼에 서로 다른 타임존의 값이 섞여 들어가면 그 순간 정렬 결과 자체가 무의미해진다.

그리고 §1-5의 정산 하루 밀림이 SQL 레벨에서 어떻게 나타나는지도 이 구조에서 나온다.

```sql
-- 위험: created_at::date 는 "세션 타임존 기준의 날짜"라 세션 설정에 따라 결과가 달라진다.
--       게다가 컬럼에 함수를 씌우면 인덱스도 쓰지 못한다.
SELECT count(*) FROM orders WHERE created_at::date = DATE '2026-08-31';

-- 안전: 하루의 경계를 어느 타임존의 자정으로 볼지 쿼리에 명시하고, 범위 조건으로 쓴다.
--       범위 조건이라 created_at 인덱스를 그대로 탈 수 있다.
SELECT count(*) FROM orders
 WHERE created_at >= TIMESTAMPTZ '2026-08-31 00:00:00+09'
   AND created_at <  TIMESTAMPTZ '2026-09-01 00:00:00+09';
```

### 3-5. 서버 코드가 규약을 어길 수 없게 잠근다

문서만으로는 규약이 지켜지지 않는다. **기본값을 규약대로 잠가 두어야** 무심코 쓴 코드가 규약을 지키게 된다.

```java
// Before: 서버 타임존에 의존하는 타입 — 서버 TZ 가 바뀌면 값의 의미가 바뀐다
public record OrderResponse(
        LocalDateTime createdAt   // 오프셋 정보가 없다 → 직렬화하면 "2026-08-31T09:00:00"
) {}

// After: 시점은 오프셋을 아는 타입으로 — 직렬화 결과에 Z 가 붙는다
public record OrderResponse(
        Instant createdAt         // "2026-08-31T00:00:00Z"
) {}
```

세 겹으로 잠근다.

- **타입 선택이 첫 번째 방어선이다.** Spring Boot + Jackson 조합은 기본으로 `java.time` 타입을 epoch 숫자가 아니라 ISO 8601 문자열로 직렬화한다(`WRITE_DATES_AS_TIMESTAMPS`를 비활성으로 설정해 둔다). 즉 문제는 라이브러리가 아니라 **타입이다** — `LocalDateTime`은 애초에 오프셋 정보를 갖고 있지 않으니 어떤 설정을 해도 오프셋 없는 문자열이 나간다. 시점 필드는 `Instant`(또는 `OffsetDateTime`)로 선언하는 것 자체가 규약의 강제다.
- **JVM·컨테이너의 기본 타임존을 UTC로 통일한다.** 다만 이것은 보조 수단이다. 더 근본적인 것은 **기본 타임존을 읽는 API를 코드에서 쓰지 않는 것**이다. `LocalDateTime.now()`, 타임존 인자 없는 변환 같은 것들이 그렇다. 요지는 "설정을 잘 맞춘다"가 아니라 **"설정이 뭐든 결과가 같도록 의존 자체를 없앤다"**이다.
- **DB 컬럼 타입으로 스키마 차원에서 못박는다**(§3-4). "UTC 기준 저장"이 운영 설정이 아니라 스키마의 성질이 되게 하는 것이다.

### 3-6. 팀 규약 문서에 들어갈 항목

마지막 한 겹은 문서다. 아래 항목이 정해져 있지 않으면 사람이 바뀔 때마다 같은 논쟁이 반복된다.

| 항목 | 정해야 할 것 | 이 문서에서의 기본값 |
|---|---|---|
| 시점 포맷 | 정확한 문자열 형태 (예시로 못박기) | ISO 8601 + 오프셋 필수, UTC(`Z`) 기본 (§2-1) |
| date-only 사용 기준 | 어떤 값이 달력상 날짜인가 | 생일·정산 기준일·휴무일 등 (§3-1) |
| 필드 네이밍 | 이름으로 타입 구분 | `...At` = 시점, `...Date` = date-only (§3-3) |
| 요청 입력 규칙 | 오프셋 없는 입력을 어떻게 할 것인가 | 400 거절 (§2-2) |
| 하루의 경계 | 일별 집계의 자정 기준 타임존 | 도메인 결정 — 반드시 명시 (§1-5) |
| epoch 사용 범위 | 쓸 곳과 단위 | 내부 이벤트·로그에 한정, 밀리초로 고정 (§2-4) |
| 소수점 초 자릿수 | 몇 자리로 고정할 것인가 | 밀리초 3자리 고정 |

마지막 항목이 사소해 보이지만 실제로 사고를 낸다. **`Instant`를 그대로 직렬화하면 자릿수가 값에 따라 달라지기 때문이다.** 자바의 ISO 형식은 필요한 만큼만 출력하되 3자리 단위로 끊어 쓴다.

```text
Instant.parse("2026-08-31T00:00:00Z")           → "2026-08-31T00:00:00Z"           (0자리)
Instant.ofEpochMilli(1788134400123L)            → "2026-08-31T00:00:00.123Z"       (3자리)
Instant.now()                                    → "2026-09-01T10:11:54.919910Z"   (6자리)
                                                                     ↑
              같은 필드인데 값에 따라 소수점 자릿수가 0, 3, 6, 9 로 달라진다.
```

받는 쪽이 자릿수 고정 포맷(`yyyy-MM-dd'T'HH:mm:ss.SSS'Z'`)으로 파싱하도록 구현해 두었다면, **0자리 값이나 6자리 값이 오는 순간 파싱 예외가 난다.** 소수점 초를 아예 받지 않는 기본 설정을 가진 파서도 있다. 그래서 "밀리초 3자리 고정"을 규약에 넣고 서버가 항상 그 형태로 내보내도록 포맷터를 지정한다 — 값에 따라 형태가 달라지는 필드는 계약이 아니다.

## 4. 꼬리질문 대비 포인트

### "왜 저장·전송은 UTC로 하고, 표시 변환은 클라이언트가 하나?"

시점의 '값'과 '표현'을 분리하기 위해서다. 같은 순간도 타임존마다 표현이 다른데, **사용자의 타임존을 아는 것은 클라이언트뿐이다**(기기 설정·브라우저가 알려 준다).

서버가 표시까지 책임지려면 사용자별 타임존을 추측하거나 관리해야 하고, 같은 리소스가 사용자마다 다른 바디를 갖게 되어 캐시 공유도 깨진다. 반면 서버가 단일 기준(UTC)의 값을 주면 저장 쪽에서도(비교·정렬·집계가 단일 기준에서 성립한다) 전송 쪽에서도(해석 모호성이 없다) 단순해진다.

단, 예외를 함께 말하면 답이 커진다. **"일별 집계" 같은 서버 사이드 날짜 경계 연산은 어느 타임존의 자정인지를 서버가 결정해야 한다**(§1-5, §3-4). "전부 클라이언트 책임"이 아니라 "표시는 클라이언트, 경계 정책은 서버"가 정확한 분업이다.

### "epoch 밀리초는 파싱 모호성이 없는데 왜 기본값으로 안 쓰나?"

**모호성이 없다는 전제가 이미 계약("밀리초다")에 의존한다.** 값 자체에 단위가 없어서, 계약이 부재하면 1000배 사고가 그 첫 희생자가 된다(§1-4).

그리고 외부 API의 소비자는 기계만이 아니다. 디버깅 중 로그와 응답을 눈으로 대조하는 개발자, 문서를 읽는 파트너에게 epoch은 매번 변환 비용이다. date-only 표현이 불가능해 API 전체를 한 포맷으로 통일할 수 없다는 것도 걸림돌이다.

정리하면 **"어디에 쓰느냐"로 답한다** — 내부 이벤트 스트림·로그처럼 기계 간 대량 교환에는 epoch(단위 명시)이 합리적이고, 외부 계약의 기본값은 ISO 8601이다.

### "생일 같은 필드에 타임존을 붙이면 무슨 일이 생기나?"

달력상 날짜를 시점(`...T00:00:00Z`)으로 인코딩하는 순간, 클라이언트의 표준 처리인 "로컬 변환 후 표시"가 그 값을 망가뜨린다. **UTC 자정은 UTC보다 서쪽 타임존에서 전날 저녁이 되어 생일이 하루 밀려 보인다**(§3-1에서 실제 출력으로 확인했다).

날짜는 타임존 변환의 대상이 아니므로 date-only(`"1990-05-15"`)로 주고받는 것이 정확한 표현이다. 이 질문의 본질은 **"모든 시간 값에 타임존을 붙이는 게 정답은 아니다 — 시점과 날짜는 타입이 다르다"**는 구분을 하는지다.

### "미래의 예약 시각도 UTC로 변환해 저장하면 되나?" (시니어 변별 포인트)

과거·현재의 시점은 UTC 저장이 정답이지만, **미래의 '벽시계 약속'은 예외다.**

"2027년 3월 10일 오전 9시 서울 회의"를 지금 UTC로 환산해 `2027-03-10T00:00:00Z`로 고정한다고 하자. 그 사이 해당 지역의 타임존 규칙이 바뀌면 — 서머타임 도입·폐지, 표준 오프셋 변경 — 고정해 둔 UTC 값이 가리키는 현지 시각은 9시가 아니게 된다. 사용자가 약속한 것은 UTC의 어떤 순간이 아니라 **"서울에서 9시"** 였는데도 그렇다.

이 "규칙이 바뀐다"가 추상적인 가정이 아니라는 것을 IANA tzdb(§1-1)로 뒷받침하면 답이 단단해진다. tzdb는 각국의 규칙 변경을 반영해 매년 여러 차례 갱신판이 나오는 살아 있는 데이터다. 실제로 멕시코는 2022년에 대부분 지역의 서머타임을 폐지했고, 이집트는 2023년에 서머타임을 다시 도입했다. 한국도 1987~1988년에 서머타임을 시행한 이력이 tzdb에 그대로 남아 있다.

그래서 미래의 약속은 **현지 시각 + 타임존 ID**(`Asia/Seoul` — 오프셋 `+09:00`이 아니라 규칙을 가리키는 지역 ID, §1-1)로 저장하고, 실행 시점에 **그때의 규칙으로 UTC를 계산한다.** 자바 타입으로는 `ZonedDateTime`이 이 역할을 하고(§2-3), API 계약으로는 `startsAt` + `timeZone` 두 필드로 나눠 표현하는 것이 안전하다(직렬화 과정에서 타임존 ID가 떨어져 나가지 않게).

"UTC로 통일"이라는 원칙의 **예외 조건과 그 근거**를 아는지가 이 질문의 변별점이다.

### "서버와 DB의 타임존 설정은 어떻게 관리하나?"

**코드가 "기본 타임존"에 의존하는 지점을 없애는 방향으로 관리한다.** 설정을 잘 맞추는 것은 보조 수단이고, 의존을 없애는 것이 본질이다.

세 층으로 나눠 말하면 된다.

- **애플리케이션**: JVM·컨테이너 기본 타임존을 UTC로 통일해 환경 간 차이를 없애되, 애초에 기본 타임존을 읽는 타입·API(`LocalDateTime.now()`, 타임존 인자 없는 변환)를 쓰지 않는다. `Instant`처럼 기준이 값 안에 있는 타입을 쓰면 설정이 무엇이든 결과가 같다.
- **DB**: PostgreSQL 기준으로 시점 컬럼은 `timestamptz`, 달력상 날짜는 `date`로 못박는다(§3-4). `timestamptz`는 세션 타임존이 **입력 해석과 출력 표시에만** 영향을 주고 저장된 값 자체는 바뀌지 않으므로, 세션 설정이 어긋나도 비교·정렬·집계 결과가 달라지지 않는다. 반대로 `timestamp` 컬럼을 시점에 쓰면 이 안전장치가 통째로 없다.
- **커넥션·세션**: 그럼에도 표시 일관성을 위해 커넥션 풀 수준에서 세션 타임존을 UTC로 고정해 두면, 어느 인스턴스에서 조회해도 같은 문자열이 나와 로그 대조가 쉬워진다.

요지는 **"설정을 잘 맞춘다"가 아니라 "설정이 뭐든 결과가 같도록 의존을 없앤다"**이다.

## 한 줄 요약

날짜/시간 규약의 요체는 포맷 암기가 아니라 두 가지 분리다 — 시점은 오프셋이 값 안에 박힌 ISO 8601(UTC 기본, 애플리케이션은 `Instant`, DB는 `timestamptz`)로, 달력상 날짜는 date-only(`LocalDate`, `date`)로 구분하고, 값의 기준(UTC 저장·전송)과 표현(클라이언트 변환)의 책임을 나눈 뒤, 이를 팀 문서와 타입·직렬화 기본값으로 강제하는 것 — 여기에 **오프셋(숫자 하나)과 타임존 ID(규칙 묶음)의 차이**를 얹으면 미래의 벽시계 약속만은 타임존 ID로 저장해야 한다는 예외까지 설명되고, 이 계약이 없으면 같은 문자열을 클라이언트마다 다르게 해석하는 버그가 해외 사용자와 자정 경계에서만 조용히 터진다.
