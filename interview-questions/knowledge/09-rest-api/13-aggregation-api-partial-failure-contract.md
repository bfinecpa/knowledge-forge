# Aggregation API의 부분 실패 — 전체 실패냐 부분 응답이냐는 계약으로 명시한다

> 핵심 관전 포인트: **여러 서비스를 조합하는 API(BFF/aggregation)에서
> 하위 1개가 죽었을 때 전체 실패로 볼지 부분 응답을 줄지는 기술이 아니라
> 제품 결정이며, 프론트·기획과 합의해 API 계약에 명시해야 한다. 계약의
> 골격은 세 가지 — (1) 응답의 각 섹션을 필수(core)와 선택(degradable)으로
> 구분한다: 필수가 실패하면 전체 5xx, 선택이 실패하면 200 + 성능 저하
> 응답. (2) 실패한 선택 섹션은 그냥 null이 아니라 상태를 명시하는 부분
> 응답 스키마로 표현한다 — null은 "데이터 없음"과 "조회 실패"를 구분하지
> 못한다. (3) 전체 응답 SLA에서 하위 호출별 타임아웃 예산을 배분하고,
> 선택 섹션은 짧은 예산 + 기본값으로 잘라낸다.**

---

## 0. 질문 + 의도

**질문**: "여러 마이크로서비스를 조합해 응답하는 API(BFF/aggregation)의
부분 실패를 어떻게 설계하나요?"

**출제 의도**: 5개 서비스 중 1개가 죽었을 때 전체 실패냐 부분 응답이냐는
기술이 아니라 제품 결정이며, 이를 프론트·기획과 협의해 스펙에 명시해본
경험을 확인한다. 서킷브레이커 같은 복원 패턴 나열이 아니라, "부분
실패를 클라이언트가 다룰 수 있는 응답 계약으로 어떻게 표현하는가"가
관전 포인트다.

(서킷브레이커·연쇄 장애·우아한 성능 저하 등 복원 패턴 자체는
`07-traffic-performance/` 문서들 참고. 이 문서는 **API 응답 계약
관점** — 부분 응답 스키마, 필수/선택 구분, 타임아웃 예산 — 에 집중한다.)

## 1. 문제의 구조 — 조합 API는 가용성을 곱셈으로 깎는다

주문 상세 화면용 BFF가 5개 서비스를 조합한다고 하자:

```text
GET /bff/order-detail/1234
  ├── 주문 서비스     → 주문 상태, 금액        (이게 없으면 화면 자체가 무의미)
  ├── 상품 서비스     → 상품명, 이미지
  ├── 배송 서비스     → 배송 추적 정보
  ├── 리뷰 서비스     → 작성 가능한 리뷰 배너
  └── 추천 서비스     → "함께 구매한 상품"     (없어도 화면은 성립)
```

"하나라도 실패하면 500"으로 만들면, 각 서비스 가용성이 99.9%라 해도
조합 API의 가용성은 0.999⁵ ≈ 99.5%로 떨어진다 — **추천 서비스가
죽었다는 이유로 사용자가 자기 주문 상태를 못 보는** 상황이 생긴다.
그렇다고 무조건 부분 응답이 정답도 아니다 — 결제 확인 화면에서 금액
섹션이 빠진 채 200을 주는 것은 더 위험하다.

즉 "어느 섹션까지는 없어도 화면이 성립하는가"는 코드가 결정할 문제가
아니라 **화면을 아는 프론트·기획과 함께 정하는 제품 결정**이고, 정한
결과는 구두 합의가 아니라 API 스펙 문서에 남아야 한다. 이 합의가
없으면 백엔드는 임의로 null을 내려보내고, 프론트는 null에서 NPE를
내며, 장애 때마다 "이거 빠져도 되는 거였어요?"를 반복한다.

## 2. 응답 계약 설계 — 필수/선택 구분과 부분 응답 스키마

### ① 섹션을 필수(core)와 선택(degradable)으로 구분한다

- **필수 섹션**(주문 정보): 실패하면 이 API의 존재 이유가 사라진다
  → 전체 실패(502/503)로 응답하고, 재시도 힌트(Retry-After)를 준다.
- **선택 섹션**(추천, 리뷰 배너): 실패해도 화면이 성립한다
  → 전체는 200으로 응답하되, 해당 섹션만 성능 저하 상태를 표시한다.

이 구분을 스펙 문서에 명시한다 — "recommendations는 optional 섹션이며
UNAVAILABLE일 수 있다. 클라이언트는 이 경우 해당 영역을 숨긴다."
클라이언트의 처리 방식(숨김/기본값/재시도 버튼)까지 계약의 일부다.

### ② 실패를 null로 표현하지 않는다 — 부분 응답 스키마

```json
// Before: 실패한 섹션을 그냥 null로 — 의미가 셋으로 겹친다
{
  "order":           { "status": "DELIVERED", "amount": 35000 },
  "recommendations": null
}
// 문제: 이 null이 (a) 추천할 상품이 없음, (b) 추천 서비스 장애,
//       (c) 이 화면엔 원래 없는 필드 — 셋 중 무엇인지 구분 불가.
//       프론트는 (a)로 해석해 빈 영역을 그리고, 장애는 은폐된다.
//       모니터링도 못 한다 — 200 응답 속에 장애가 숨어 있으므로.
```

```json
// After: 섹션마다 상태를 명시하는 봉투(envelope) 구조
{
  "order": { "status": "DELIVERED", "amount": 35000 },
  "sections": {
    "recommendations": {
      "status": "UNAVAILABLE",          // OK | UNAVAILABLE | TIMEOUT
      "data": null,
      "reason": "RECOMMENDATION_CIRCUIT_OPEN"   // 로그 대조용, 선택
    },
    "shipping": {
      "status": "OK",
      "data": { "carrier": "CJ", "trackingNo": "..." }
    }
  },
  "degraded": true    // 하나라도 성능 저하면 true — 모니터링/알람 집계 키
}
// 효과: "없음"과 "실패"가 구분되고, 클라이언트는 status로 분기하며,
//       서버는 degraded=true 비율을 지표로 삼아 부분 장애를 관측한다.
```

핵심 원칙: **"데이터가 없다"와 "가져오지 못했다"는 계약 수준에서 다른
값이어야 한다.** GraphQL이 응답에 `data`와 `errors`(path 포함)를 함께
담는 것도 정확히 같은 문제의 표준화된 해법이다 — 부분 성공을
일급(first-class) 개념으로 스키마에 넣은 것이다 (가산점 포인트).

### ③ HTTP 상태 코드 규약

- 필수 섹션 실패 → **502/503** (원인이 하위 서비스임을 드러내는 표준
  에러 바디와 함께).
- 선택 섹션만 실패 → **200** + 바디의 `degraded`/섹션 status로 표현.
  206(Partial Content)은 Range 요청 전용, 207(Multi-Status)은 WebDAV
  용도라 REST 조합 API에 재활용하면 중간 장비·클라이언트 라이브러리가
  오해할 수 있다 — "상태 코드는 전송 수준, 섹션별 성패는 바디 수준"으로
  계층을 나누는 것이 무난하다.

## 3. 타임아웃 예산 — 계약을 시간 축에서 지키는 장치

부분 실패는 "에러 응답"만이 아니라 **"안 끝나는 응답"**으로도 온다.
추천 서비스가 죽지 않고 5초씩 걸리기만 해도, 전체 API가 5초짜리가
된다 — 가장 느린 하위 호출이 전체 응답 시간을 결정하기 때문이다.

그래서 응답 계약에는 시간 예산이 포함된다. 전체 SLA가 1초라면:

```text
전체 예산 1000ms
  ├── 필수: 주문 700ms          (실패 시 전체 실패이므로 예산을 후하게)
  ├── 선택: 배송 500ms ┐
  ├── 선택: 리뷰 300ms │ 병렬 실행 — 순차 합산이 아니라 max()가 되게
  └── 선택: 추천 300ms ┘ (초과 시 그 섹션만 TIMEOUT 처리하고 응답은 나간다)
```

```java
// Before: 순차 호출 + 타임아웃 없음 — 최악의 조합
var order = orderClient.getOrder(id);        // 각각이 얼마나 걸릴지
var shipping = shippingClient.get(id);       // 아무도 통제하지 않고,
var reco = recoClient.recommend(id);         // 지연은 전부 합산된다
return assemble(order, shipping, reco);

// After: 병렬 + 섹션별 예산 + 선택 섹션은 기본값으로 완성
var orderF = supplyAsync(() -> orderClient.getOrder(id))
        .orTimeout(700, MILLISECONDS);            // 필수: 초과 시 예외 → 전체 실패
var shippingF = supplyAsync(() -> shippingClient.get(id))
        .completeOnTimeout(Section.timeout(), 500, MILLISECONDS);
var recoF = supplyAsync(() -> recoClient.recommend(id))
        .completeOnTimeout(Section.timeout(), 300, MILLISECONDS)
        .exceptionally(e -> Section.unavailable()); // 선택: 실패도 상태값으로 흡수
return assemble(orderF.join(), shippingF.join(), recoF.join());
// 효과: 응답 시간 상한이 계약된다 — 최악에도 max(700, 500, 300) 언저리.
//       선택 섹션의 지연·실패는 예외가 아니라 "상태값"으로 응답에 편입된다.
```

두 가지를 함께 말하면 좋다 — (1) 선택 섹션의 예산은 짧게 잡고 캐시된
이전 값이나 기본값(빈 목록)으로 대체하는 것까지가 계약이다. (2) 하위
서비스에 남은 예산을 전파(deadline propagation)해서, 이미 시간이 다 된
요청을 하위가 헛되이 처리하지 않게 한다 — 계층별 타임아웃 상세는
`07-traffic-performance/10-timeout-layers-and-budget.md` 참고.

## 4. 꼬리질문 대비 포인트

### "부분 실패인데 200을 주는 게 맞나요? 클라이언트가 성공으로 오해하지 않나요?"

전송은 성공했고(조합 API 자체는 정상 동작), 실패는 응답의 일부
섹션이므로 200 + 바디 표현이 맞다 — 5xx를 주면 "주문 정보는 멀쩡히
있는데" 클라이언트가 화면 전체를 에러로 그리는, 피하려던 결과로
돌아간다. 단 두 가지 보완이 계약에 있어야 한다: (1) `degraded` 같은
최상위 플래그로 클라이언트와 모니터링이 한 번에 감지할 수 있게 하고,
(2) "200이지만 degraded=true" 비율을 대시보드 지표로 집계해 부분
장애가 200 뒤에 숨지 않게 한다. 필수 섹션 실패는 당연히 5xx다 —
"200이냐 5xx냐"의 답은 결국 필수/선택 구분에서 나온다.

### "실패한 섹션만 클라이언트가 다시 가져오게 하려면 어떻게 설계하나요?"

섹션 상태에 **복구 경로**를 함께 내려준다 — 예: `"retryable": true`와
그 섹션만 조회하는 세부 엔드포인트(`/bff/order-detail/1234/recommendations`).
클라이언트는 화면 골격을 먼저 그리고 실패 섹션만 지연 재요청한다.
이때 재시도 폭주를 막는 규약(최소 간격, 최대 횟수)도 계약에 명시해야
한다 — 부분 장애 중인 서비스에 모든 클라이언트가 즉시 재시도하면
복구를 방해한다. 아예 처음부터 무거운 섹션을 분리 API로 설계해
"조합의 범위 자체를 줄이는" 선택지와의 트레이드오프(왕복 수 vs 실패
격리)까지 언급하면 좋다.

### "필수/선택 구분은 누가, 어떻게 정하나요?" (시니어 변별 포인트)

백엔드가 단독으로 정할 수 없다 — "이 섹션이 빠진 화면을 사용자에게
보여도 되는가"는 화면과 비즈니스의 판단이기 때문이다. 실무 절차는:
(1) BFF가 조합하는 섹션 목록을 표로 만들어 프론트·기획과 함께 각
섹션에 core/degradable을 마킹하고, 실패 시 클라이언트 동작(숨김,
기본값, 재시도 버튼)을 정한다. (2) 결과를 API 스펙 문서에 섹션별
속성으로 명시한다 — "recommendations: optional, UNAVAILABLE 시 영역
숨김". (3) 같은 섹션이라도 화면에 따라 등급이 다를 수 있음을 인지한다
— 결제 완료 화면의 금액은 필수지만, 마이페이지 요약의 금액은 선택일
수 있다. 이 질문의 정답은 스키마 문법이 아니라 **"기술 결정처럼 보이는
것을 제품 결정으로 끌어올려 합의·문서화한 경험"**이다.

### "성능 저하 상태를 테스트는 어떻게 하나요?"

부분 실패 응답은 평시에 발생하지 않으므로 테스트 없이는 장애 당일에
처음 실행되는 코드가 된다. (1) 계약 테스트 — 섹션 UNAVAILABLE 응답
예시를 스펙에 포함하고 프론트가 그 픽스처로 화면을 검증하게 한다.
(2) 통합 테스트에서 하위 서비스 stub이 에러/지연을 반환하는 시나리오를
상시 돌린다. (3) 주기적으로 스테이징(또는 통제된 프로덕션)에서 하위
서비스 하나를 실제로 차단해 degraded 응답과 화면을 확인한다 — "부분
실패 경로도 기능이므로 기능처럼 테스트한다"는 태도가 포인트다.

## 한 줄 요약

조합 API의 부분 실패 설계는 서킷브레이커가 아니라 계약에서 시작한다 —
**섹션을 필수/선택으로 구분해 프론트·기획과 합의하고(필수 실패는 5xx,
선택 실패는 200+degraded), 실패를 null이 아닌 명시적 상태로 표현하는
부분 응답 스키마를 정의하며, 전체 SLA를 하위 호출별 타임아웃 예산으로
배분해 응답 시간 상한까지 계약**하는 것 — 그래야 하위 장애가 "숨은
null"이 아니라 관측·대응 가능한 명시적 상태로 클라이언트에 도달한다.
