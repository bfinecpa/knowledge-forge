# API 에러 응답 바디 표준화 — 에러 스키마는 성공 응답과 동급의 계약이다

> 핵심 관전 포인트: **에러 응답은 "예외 상황의 부산물"이 아니라 소비자가 매일 받는 정상 트래픽이므로, 성공 응답과 똑같이 하나의 스키마로 고정된 계약이어야 한다. 스키마를 설계할 때의 뼈대는 **축을 둘로 나누는 것**이다 — HTTP status는 게이트웨이·프록시·모니터링·재시도 로직처럼 **바디를 파싱하지 않는 소비자**가 읽는 축이고(그래서 "재시도해도 되나"를 여기서 판단한다), 에러 code는 "잔액 부족인지 한도 초과인지"처럼 status가 담을 수 없는 세부 구분을 클라이언트 분기에 전달하는 축이다. 어느 한 축만으로는 안 된다. 여기에 사람이 읽는 message, 검증 실패용 필드 상세 배열, 분산 추적의 진입점인 traceId를 더하면 뼈대가 완성된다. 에러 코드는 "클라이언트가 다르게 행동해야 할 때만" 분리하고, **한번 공개한 코드는 클라이언트의 분기문에 박히므로 필드명과 같은 급의 불변 계약**이 된다 — 특히 앱 스토어에 나간 모바일 앱은 회수가 안 된다. 자체 포맷 대신 RFC 9457(구 RFC 7807) Problem Details라는 표준을 채택하는 선택지도 있고, 외부 공개 API일수록 표준이 계약 설명 비용을 줄인다. 마지막으로 "필드 추가는 안전, 모르는 코드는 status 기반 폴백"이라는 진화 규칙까지 문서화해 소비자와 공유하는 것이 설계의 끝이다.**

---

## 0. 질문 + 의도

**질문**: "API 에러 응답 바디는 어떻게 표준화하나요?"

**출제 의도**: 에러 스펙이 제각각이면 클라이언트마다 파싱 분기가 생기고, 장애 시 에러 원인 분류가 불가능하다. API를 "혼자 만드는 것"이 아니라 "여러 팀이 소비하는 제품"으로 보는지 확인한다. 스프링 구현 테크닉이 아니라, 에러 응답이라는 스키마를 소비자와의 계약으로 설계할 수 있는지를 보는 질문.

(스프링에서의 구현 — @RestControllerAdvice, ErrorCode enum, 필터/비동기 구역의 포맷 통일 — 은 `02-spring/19-global-exception-handling-error-response.md` 참고. 이 문서는 **응답 스키마 설계 자체**에 집중한다.)

## 1. 표준화가 없으면 생기는 일 — 파싱 분기와 집계 불능

### 1-1. 전제 — 왜 에러 응답만 스키마 없이 자라는가

성공 응답에는 대개 DTO 클래스가 있다. 필드 이름을 정하고, 타입을 정하고, OpenAPI 문서에 올리고, 바꿀 때는 "이거 바꿔도 되나"를 묻는다. 그런데 같은 팀이 에러 응답은 `Map.of("error", e.getMessage())`로 그 자리에서 만들어 던진다.

이 비대칭이 생기는 이유는 심리적이다. **에러는 "일어나면 안 되는 일"처럼 느껴져서, 스펙 바깥의 예외 상황으로 취급된다.** 성공 경로만 계약이고 실패 경로는 사고 처리라는 감각이다.

소비자 입장에서 보면 정반대다. 로그인 폼의 검증 실패, 만료된 토큰, 품절된 상품, 한도 초과 — 이것들은 **매일 수만 번 오는 정상 트래픽**이고, 클라이언트 코드의 절반은 이 응답들을 처리하는 분기다. 프론트 개발자에게 "이 API가 실패하면 무슨 모양이 오나요"는 성공 응답 스펙만큼이나 자주 필요한 정보다.

즉 **에러 응답은 예외가 아니라 계약의 절반**이다. 이 인식이 없는 조직의 API는 아래처럼 자란다.

### 1-2. 표준화하지 않은 API가 실제로 어떻게 생겼는가

```jsonc
// before: API마다 에러 바디 모양이 다르다
// 주문 API — A 개발자
{ "error": "재고가 없습니다" }

// 회원 API — B 개발자
{ "success": false, "errorMessage": "이미 가입된 이메일", "errCode": 1042 }

// 결제 API — 외부 SDK 스타일 흉내
{ "result": { "status": "FAIL", "reason": "LIMIT_EXCEEDED" } }
```

세 응답이 전부 다르다. 에러 메시지가 든 키 이름이 `error`, `errorMessage`, `result.reason`으로 셋이고, 코드에 해당하는 것이 없거나(`error`), 숫자거나(`1042`), 문자열이다(`LIMIT_EXCEEDED`). 실패했다는 사실을 알리는 방법조차 `success: false`가 있는 쪽과 없는 쪽으로 갈린다.

이 상태의 비용은 두 방향으로 발생한다.

**소비자(프론트·모바일·파트너) 비용**: API마다 에러 파싱 코드를 따로 짠다. HTTP 클라이언트에 에러 인터셉터를 하나 두고 모든 응답을 거기서 처리하는 흔한 패턴이 성립하지 않는다 — 인터셉터가 바디를 열어봐도 어떤 키를 읽어야 할지 API마다 다르기 때문이다. 그 결과 "이 API는 에러 때 어떤 키에 뭐가 들어오나요"를 슬랙으로 물어보는 협업이 반복되고, 그 답은 코드에만 있으므로 물어볼 사람이 자리에 없으면 진행이 멈춘다.

**운영 비용**: 장애가 났을 때 "어떤 종류의 실패가 늘고 있는지"를 집계할 공통 키가 없다. 로그 수집기에서 `code` 필드로 group by 하면 5초면 나올 답을, 로그 문자열 grep과 눈으로 세는 작업으로 대신하게 된다. 특히 "5분 전부터 재고 소진 에러가 300배 늘었다" 같은 신호는 집계 키가 있어야만 알람으로 만들 수 있다.

### 1-3. 표준화란 무엇을 고정하는 것인가

표준화란 이 응답을 **하나의 스키마**로 통일하는 것이다.

```jsonc
// after: 어떤 API가 실패해도 이 모양 — 소비자는 파서를 한 번만 짠다
{
  "code": "ORDER-001",                   // 기계 판독용 — 분기·집계의 키
  "message": "재고가 소진된 상품입니다",     // 사람용
  "errors": [],                          // 검증 실패 시 필드별 상세
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"  // 장애 추적의 진입점
}
```

여기서 "하나의 스키마"가 무슨 뜻인지 정확히 짚고 가야 한다. **에러의 종류가 늘어나도 바디의 모양은 변하지 않는다는 뜻이다.** 검증 실패라고 해서 `errors` 배열이 갑자기 생기고 다른 에러에는 없는 것이 아니라, 검증 실패가 아닐 때는 빈 배열로 나간다. 인증 에러라고 해서 `code` 대신 `reason`을 쓰지 않는다.

이 규칙이 있어야 소비자가 **한 번 짠 파서를 모든 응답에 그대로 적용**할 수 있다. 에러 종류마다 응답 모양이 달라진다면 그것은 표준화가 아니라 "포맷이 여러 개인 상태"에 이름만 붙인 것이다.

## 2. 스키마 설계 — 각 필드의 소비자와 에러 코드 체계

표준 스키마를 설계할 때 던져야 하는 질문은 "무슨 정보를 담을까"가 아니라 **"이 필드를 누가 읽는가"**다. 읽는 주체가 다르면 필드를 나눠야 하고, 같으면 합쳐야 한다.

### 2-1. 축 하나로는 왜 안 되는가

에러를 식별하는 수단은 두 개가 있다. HTTP status와 바디 안의 code다. 둘 중 하나면 충분할 것 같은데 그렇지 않다. 각각이 왜 혼자서는 모자란지 순서대로 보자.

**HTTP status만으로는 왜 부족한가.** status는 종류가 적다. 클라이언트 잘못을 뜻하는 4xx 계열이 전부 합쳐 스무 개 남짓이고, 실무에서 실제로 쓰는 것은 400, 401, 403, 404, 409, 422, 429 정도다. 반면 하나의 결제 API가 낼 수 있는 실패는 훨씬 많다.

```
POST /payments 가 400을 돌려줬다. 클라이언트가 아는 것:
  "요청이 잘못됐다"

클라이언트가 알아야 하는 것 — 화면 분기가 전부 달라진다:
  잔액이 부족한가?        -> 충전 화면으로 보낸다
  일일 한도를 넘었나?      -> 한도 안내 화면을 띄운다
  필수값이 빠졌나?        -> 입력 폼의 해당 칸에 표시한다
  카드가 만료됐나?        -> 카드 관리 화면으로 보낸다
```

status만 있으면 이 네 가지가 전부 같은 `400`이다. 클라이언트가 구분할 방법은 `message` 문자열을 비교하는 것뿐인데, 그 순간 **서버가 문구를 다듬는 커밋이 프론트 장애가 되는** 최악의 결합이 생긴다. "잔액이 부족합니다"를 "잔액이 부족해요"로 바꾸는 카피 수정 하나에 앱이 충전 화면을 못 찾는다.

**그럼 code만 두면 되지 않나.** 안 된다. **바디를 파싱하지 않는 소비자가 우리 응답을 읽고 있기 때문이다.** 이쪽이 놓치기 쉬운 절반이다.

| 바디를 안 보는 소비자 | status로 무엇을 판단하는가 |
|---|---|
| HTTP 클라이언트 라이브러리 | 재시도할지 말지 (5xx·429는 재시도, 4xx는 재시도 무의미) |
| API 게이트웨이 / 로드밸런서 | 이 인스턴스를 장애로 보고 뺄지, 서킷 브레이커를 열지 |
| 리버스 프록시 / CDN | 응답을 캐시해도 되는지 |
| APM · 모니터링 | 에러율 지표, 알람 임계치 |
| 브라우저 · 검색엔진 | 링크가 죽었는지(404), 권한 문제인지(401/403) |

이들은 우리 바디의 키 이름을 모르고, 알 필요도 없다. JSON을 열어보지 않고 상태 코드 숫자 하나만 본다. 그래서 **에러를 200에 담고 바디에 `"success": false`를 넣으면 인프라 전체가 장애를 못 본다.** 결제가 전부 실패하는 중인데 모니터링 대시보드의 에러율은 0%로 평온하고, 서킷 브레이커도 안 열리고, 클라이언트 라이브러리의 재시도도 안 돈다.

### 2-2. 이중 축 — status(분류)와 code(세부 구분)

앞의 두 결론을 합치면 축이 둘이어야 한다는 결론이 나온다. **두 축은 서로를 보완하는 것이 아니라 서로 다른 소비자를 향한다.** 이것이 이 절의 핵심이다.

| | HTTP status | 바디의 code |
|---|---|---|
| 누가 읽는가 | 게이트웨이·프록시·모니터링·재시도 로직 (바디를 안 봄) | 우리 API를 직접 쓰는 클라이언트 코드 |
| 무엇을 답하는가 | "이 실패는 어떤 부류인가 — 재시도해도 되나, 캐시해도 되나" | "구체적으로 무엇이 잘못됐고 사용자를 어디로 보내야 하나" |
| 값의 개수 | 적다 (수십 개, 표준이 정한 것) | 많다 (도메인이 늘면 늘어난다, 우리가 정한 것) |
| 바꿀 수 있나 | 바꾸면 인프라 동작이 바뀐다 — 위험 | 바꾸면 클라이언트 분기가 깨진다 — 위험 |

status를 고를 때의 실무 기준을 하나만 덧붙이면, **"이 실패를 그대로 재시도하면 결과가 달라질 수 있는가"**를 기준으로 4xx와 5xx를 가른다. 잔액 부족은 다시 보내도 여전히 부족하므로 4xx다. DB 커넥션 고갈은 잠시 후엔 될 수도 있으므로 5xx다. 이 기준으로 status를 고르면 클라이언트 라이브러리의 자동 재시도가 우리가 의도한 대로 동작한다.

### 2-3. message — "보여줘도 되는가"를 계약에 명시한다

message 필드에서 흔히 터지는 계약 불명확성이 있다. **클라이언트가 이 문구를 그대로 화면에 띄워도 되는가?** 이 질문의 답이 문서 어디에도 없으면, 서버 개발자는 디버깅에 편한 문구를 넣고 프론트 개발자는 그걸 사용자에게 띄운다. `"Cannot invoke \"Order.getItems()\" because \"order\" is null"`이 사용자 화면에 뜨는 사고가 이렇게 난다.

노선은 두 가지고, **어느 쪽을 고르든 문서에 명시하는 것**이 표준화다.

**노선 A — message는 표시 가능**: 서버가 사용자에게 보여도 안전한 문구만 담기로 계약한다. 클라이언트 구현이 단순해진다(그냥 띄우면 된다). 대신 문구의 품질과 다국어가 전부 서버 책임이 되고, "쿠폰 안내 문구를 바꿔달라"는 요청마다 서버 배포가 필요해진다.

**노선 B — message는 개발자용, 표시는 code 기반 매핑**: message는 로그와 디버깅용으로 두고, 사용자에게 보일 문구는 클라이언트가 `code → 자기 문구 테이블`로 변환해 만든다. 다국어와 A/B 문구 실험이 클라이언트의 자유가 되는 대신, 모든 code에 대응하는 매핑을 클라이언트마다(웹/iOS/Android) 관리해야 한다.

다국어 서비스이거나 클라이언트가 여럿이면 노선 B가 일반적이다. 서버가 `Accept-Language`를 받아 문구를 번역해 내려주는 구조는 번역 리소스가 서버 배포에 묶이고, 클라이언트가 이미 갖고 있는 번역 파이프라인과 이중으로 관리된다.

어느 노선이든 공통으로 지켜야 하는 규칙이 하나 있다. **내부 정보(스택트레이스, 예외 메시지 원문, SQL, 내부 호스트명)는 message에 절대 싣지 않는다.** 계약 문제이자 보안 문제다 — 예외 원문 하나로 프레임워크 버전과 테이블 이름이 공격자에게 넘어간다.

### 2-4. errors[] — 복수 오류를 담는 그릇, 그러나 포맷은 하나

검증 실패는 다른 에러와 성질이 다르다. **오류가 여러 개 동시에 존재한다.** 회원가입 폼에서 이메일 형식이 틀리고 나이가 음수이고 비밀번호가 짧다면, 잘못된 것이 셋이다.

단일 message로 첫 오류만 알려주면 "첫 오류를 고치고 제출 → 다음 오류를 만남 → 또 고치고 제출"이라는 UX가 된다. 사용자는 자기가 세 군데를 틀렸다는 사실을 세 번 나눠 알게 된다.

그래서 필드별 상세를 배열로 담는다. 중요한 것은 **검증 실패가 아닌 에러에서는 이 배열이 빈 채로 나간다**는 점이다. 1-3에서 말한 "하나의 스키마"를 지키기 위해서다.

```jsonc
{
  "code": "COMMON-001",
  "message": "입력값이 올바르지 않습니다",
  "errors": [
    { "field": "email", "reason": "이메일 형식이 아닙니다" },
    { "field": "age", "reason": "0 이상이어야 합니다" }
  ]
}
```

`field`에 무엇을 넣을지도 계약이다. 중첩 객체와 배열이 섞이면 `items[0].quantity` 같은 경로 표기가 필요해지는데, 이 표기법을 정해두지 않으면 서버는 `items.0.quantity`로 보내고 클라이언트는 `items[0].quantity`로 찾는 어긋남이 생긴다. 폼의 어느 칸에 빨간 줄을 그을지가 이 문자열 하나에 달려 있다.

### 2-5. traceId — 에러 응답을 장애 추적의 진입점으로 (가산점 포인트)

traceId를 "장애 추적용 ID" 한 줄로 넘기면 왜 이게 스키마의 한 자리를 차지할 만한지가 안 보인다. 먼저 분산 추적이 무엇인지부터 보자.

**전제 — 요청 하나가 여러 서비스를 지나간다.** 사용자가 주문 버튼을 누르면 요청은 게이트웨이를 거쳐 주문 서비스로 가고, 주문 서비스는 재고 서비스와 결제 서비스를 부르고, 결제 서비스는 PG를 부른다. 각 서비스는 각자의 로그를 각자의 파일(또는 인덱스)에 쌓는다.

여기서 문제가 생긴다. 결제 서비스 로그에 `NullPointerException` 하나가 찍혀 있다고 하자. **이게 어느 사용자의 어느 주문에서 나온 것인지 알 방법이 없다.** 같은 초에 다른 요청 200건이 함께 지나갔기 때문이다. 서비스 다섯 개의 로그를 시각으로 맞춰보는 것은 트래픽이 조금만 있어도 불가능하다.

**분산 추적(distributed tracing)은 요청이 시작되는 지점에서 ID를 하나 만들어, 그 요청이 지나가는 모든 서비스에 같은 ID를 달고 다니게 하는 기법이다.** 그 ID가 **trace ID**다. 각 서비스가 로그를 쓸 때마다 이 ID를 함께 찍으면, 나중에 ID 하나로 검색해서 전 구간의 로그를 시간순으로 꿰어 볼 수 있다.

한 단계 더 있다. 전 구간에 공통인 trace ID와 별개로, **각 구간(한 서비스 안에서 처리된 한 토막)을 span이라 부르고 span마다 span ID를 준다.** trace ID는 "이 요청 전체", span ID는 "그 안의 이 구간"이다. 그래서 로그에는 보통 둘이 나란히 찍힌다.

**ID는 어디서 생기고 어떻게 전파되는가.** 요청이 우리 시스템에 처음 들어오는 지점(보통 게이트웨이나 첫 서비스)에서 랜덤한 trace ID를 만든다. 그리고 다음 서비스를 부를 때 HTTP 헤더에 실어 넘긴다. 이 헤더 형식이 표준으로 정해져 있는데, W3C의 **Trace Context** 명세가 정의한 `traceparent` 헤더다.

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ^^ ^------------- 32자리 16진수 -------------^ ^--16자리--^ ^^
             |            trace ID (요청 전체 공통)      span ID     플래그
          버전                                        (호출한 쪽 구간)  (샘플링 여부)
```

```
[브라우저]
    |  POST /orders
    v
[게이트웨이]  --- traceparent 생성: trace=4bf9...4736 -------------+
    |                                                             |
    v                                                             |
[주문 서비스]  로그: [trace=4bf9...4736 span=00f0...] 주문 접수     |
    |  traceparent 그대로 전파 (span ID만 새로 발급)               |
    +----------------> [재고 서비스] 로그: [trace=4bf9...4736 ...]  |
    |                                                             |
    v                                                             |
[결제 서비스]  로그: [trace=4bf9...4736 span=9a2c...] NPE 발생 <---+
    |                                                        같은 trace ID로
    v                                                        전 구간이 꿰인다
[PG]
```

**Spring에서는 무엇이 이 일을 해주는가.** Spring Boot 3 기준으로 **Micrometer Tracing**이 담당한다(Boot 2 시절의 Spring Cloud Sleuth를 대체한 것이다). 들어오는 요청의 `traceparent` 헤더를 읽어 추적 컨텍스트를 만들고, `RestClient`·`WebClient`로 나가는 호출에 자동으로 헤더를 붙인다.

동시에 이 값을 **MDC**에 넣어준다. MDC(Mapped Diagnostic Context)는 로깅 프레임워크가 스레드마다 들고 다니는 키-값 맵으로, 여기에 담긴 값은 모든 로그 줄에 자동으로 찍힌다. 그래서 애플리케이션 코드는 `log.error("결제 실패", e)`라고만 써도 로그 한 줄에 traceId가 함께 나온다.

```
2026-09-01 14:22:31.114 ERROR [order-service,4bf92f3577b34da6a3ce929d0e0e4736,00f067aa0ba902b7]
    c.e.o.PaymentClient : 결제 실패
```

여기까지가 준비고, **에러 응답 스키마에 traceId를 넣는다는 것은 이 ID를 사용자에게까지 노출한다는 뜻**이다. 그러면 이런 흐름이 성립한다.

```
사용자: "결제하려는데 오류가 나요"
  -> CS: "화면에 뜬 코드를 알려주세요"  (에러 화면에 traceId를 함께 표시해 둔다)
  -> 개발자: 로그 검색창에 traceId 붙여넣기
  -> 전 구간 로그가 시간순으로 나옴 -> 결제 서비스의 NPE 한 줄 발견
```

이 연결 고리가 없으면 "어제 오후에 결제가 안 됐다"는 문의 하나를 재현하는 데 반나절이 든다. **에러 바디에 traceId를 넣는 것은 CS와 로그를 잇는 가장 싼 방법**이다.

노출해도 되는 이유도 짚어두자. trace ID는 랜덤한 16진수 문자열일 뿐이라 그 자체로는 아무 권한도, 내부 구조 정보도 담고 있지 않다. 반대로 **순차 증가하는 요청 번호나 내부 서버 이름을 traceId 자리에 넣으면 안 된다** — 그건 하루 트래픽량과 인프라 구성을 공개하는 것이 된다.

### 2-6. 에러 코드 체계 설계 — 코드는 필드명과 같은 급의 계약

code 필드를 두기로 했다면, 코드 체계 자체가 설계 대상이 된다.

**문자열 코드 vs 숫자 코드.** 1-2의 `errCode: 1042`처럼 숫자를 쓰는 API가 있다. 권하지 않는다. 로그에 `1042`가 찍혀 있으면 그것이 무슨 에러인지 알려면 매번 표를 찾아봐야 하고, 대시보드에 숫자만 늘어서면 읽을 수가 없다. `MEMBER_EMAIL_DUPLICATED`는 그 자체가 문서다.

숫자의 유일한 장점은 짧다는 것인데, 에러 응답의 바이트 수가 문제가 되는 상황은 실무에서 거의 없다. 반대로 숫자에는 비용이 붙는다 — **"다음 번호가 몇 번이지"를 관리하는 채번 문제**가 생기고, 팀이 나뉘면 번호대가 겹친다.

**도메인 접두사.** `ORDER-001`, `AUTH-003`처럼 앞에 도메인을 붙인다. 이유는 두 가지다. 첫째, 장애 대시보드에서 코드의 접두사로 group by 하면 "어느 도메인의 실패가 늘었나"가 바로 나온다. 둘째, 코드만 보고 어느 팀에 물어봐야 할지 안다. 마이크로서비스 환경이라면 접두사가 곧 소유 팀의 이름표다.

접두사 뒤를 일련번호(`ORDER-001`)로 할지 의미 있는 이름(`ORDER_SOLD_OUT`)으로 할지는 취향이 갈리지만, **의미 있는 이름 쪽이 읽기 좋고 채번 문제도 없다.** 어느 쪽이든 형식은 조직 전체에서 하나로 통일한다 — 어떤 API는 대문자 스네이크, 어떤 API는 하이픈이면 소비자가 다시 API마다 다른 파싱을 하게 된다.

**분리 기준 — 코드를 잘게 쪼갤수록 좋은 게 아니다.** 이 부분이 설계 감각이 드러나는 지점이다. 코드가 200개인데 클라이언트가 그중 8개만 분기하고 나머지 192개를 전부 "기타 오류"로 뭉갠다면, 그 192개는 만든 사람만 아는 코드다.

기준은 하나다. **"클라이언트가 다르게 행동해야 하는 경우에만 코드를 분리한다."**

| 분리해야 하는 경우 | 클라이언트의 행동 |
|---|---|
| 재고 소진 | 재입고 알림 신청 버튼을 띄운다 |
| 인증 만료 | 토큰을 갱신하고 원래 요청을 재시도한다 |
| 일일 한도 초과 | 한도 안내 화면으로 보낸다 |
| 잔액 부족 | 충전 화면으로 보낸다 |

반대로 "상품 ID 형식 오류"와 "쿠폰 ID 형식 오류"는 클라이언트가 둘 다 "입력을 확인하세요"로 처리한다면 코드를 나눌 이유가 없다. 나누고 싶다면 `errors[]`의 `field`로 구분하면 된다.

**불변성 — 여기서부터가 이 절의 결론이다.** 한번 공개한 코드는 바꿀 수 없다. 왜 그런지는 소비자 코드를 보면 즉시 납득된다.

```swift
// iOS 앱의 결제 실패 분기 — 서버가 내려준 code 문자열에 그대로 묶여 있다
switch error.code {
case "PAYMENT_INSUFFICIENT_BALANCE":
    navigate(to: .chargeScreen)      // 충전 화면으로 보낸다
case "PAYMENT_LIMIT_EXCEEDED":
    showLimitGuide()
default:
    showGenericError(status: error.status)   // 모르는 코드는 status 기반 폴백
}
```

서버가 `PAYMENT_INSUFFICIENT_BALANCE`를 `INSUFFICIENT_BALANCE`로 "정리"하는 순간, 이 앱은 잔액 부족을 만나도 `default`로 떨어져 "알 수 없는 오류"를 띄운다. 사용자는 충전 화면으로 못 간다.

**그리고 이 앱은 되돌릴 수 없다.** 앱 스토어에 이미 배포된 버전은 서버 배포 한 번으로 회수되지 않는다. 사용자가 자발적으로 업데이트할 때까지, 혹은 강제 업데이트를 띄울 때까지 구버전은 계속 살아 있다. 웹 프론트라면 배포로 수습되지만 모바일은 그렇지 않다.

그래서 **코드의 의미 변경·삭제·재사용은 응답 필드를 삭제하는 것과 같은 급의 파괴적 변경**이다. 반면 message는 언제든 고쳐도 된다. **이 비대칭이 code와 message를 두 필드로 분리한 이유 그 자체다** — 절대 안 변하는 기계용 식별자와, 자유롭게 다듬는 사람용 문구를 한 필드에 섞으면 둘 중 하나를 포기하게 된다.

**카탈로그 문서화.** 코드 목록(코드·의미·HTTP status·클라이언트 권장 행동)을 API 문서의 1급 시민으로 관리하고 소비자와 공유한다. 성공 응답 스키마는 OpenAPI로 꼼꼼히 문서화하면서 에러 코드 표는 없는 API가 흔한데, 그 API의 에러 계약은 결국 "물어봐야 아는 것"이 된다. 그리고 물어봐서 얻은 답은 문서에 남지 않으므로, 다음 사람이 또 물어본다.

## 3. 표준을 쓸 것인가, 그리고 스키마의 진화 규칙

### 3-1. RFC 9457 Problem Details — 이미 있는 국제 표준

2절에서 설계한 것을 IETF가 이미 표준으로 만들어 두었다. **RFC 7807 "Problem Details for HTTP APIs"**(2016년 3월)가 원본이고, 이를 **폐지(obsolete)한 개정판이 RFC 9457**(2023년 7월)이다.

"폐지"라는 말이 오해를 부르는데, **7807이 틀려서 없어진 것이 아니라 9457이 그 자리를 물려받았다는 뜻**이다. 다섯 개 표준 멤버로 이루어진 데이터 모델은 두 문서가 사실상 같고, 9457이 더한 것은 확장 멤버 사용 지침, 문제 유형을 IANA 레지스트리에 등록할 수 있게 한 것, 그리고 "유형 식별의 1차 키는 `title`이 아니라 `type`"이라는 명확화다. 그러니 바디 모양은 거의 같지만, 문서에 표기할 때는 현행 표준인 **9457**을 가리키는 것이 맞다.

### 3-2. 다섯 개 표준 멤버가 각각 무엇을 담는 자리인가

이름만 나열하면 `type`과 `instance`, `title`과 `detail`의 차이가 안 잡힌다. 각각이 무엇의 식별자인지로 나누면 한 번에 정리된다. **`type`·`title`은 "문제의 종류"에 딸린 값이고, `instance`·`detail`은 "이번에 일어난 한 건"에 딸린 값이다.**

| 멤버 | 타입 | 무엇을 담는 자리인가 | 발생 건마다 바뀌나 |
|---|---|---|---|
| `type` | URI 참조 | 문제 **유형**의 식별자. 같은 종류의 실패라면 언제나 같은 값이다. 생략하면 `"about:blank"`로 간주되고, 이는 "HTTP 상태 코드 이상의 의미가 없다"는 뜻이다 | 아니오 |
| `title` | 문자열 | 그 유형의 짧은 사람용 요약. 유형에 붙는 이름표라서 발생 건마다 달라지면 안 된다 | 아니오 |
| `status` | 정수 | HTTP 상태 코드의 사본. 응답 헤더의 상태 코드와 같은 값을 바디에도 넣어, 바디만 로그에 남았을 때도 부류를 알 수 있게 한다 | 유형에 따라 |
| `detail` | 문자열 | **이 한 건**에 대한 사람용 설명. 여기에만 구체적인 값(상품 번호, 남은 한도)이 들어간다 | 예 |
| `instance` | URI 참조 | **이 한 건**의 식별자. 보통 문제가 난 리소스 경로나 사건 ID URI를 쓴다 | 예 |

```jsonc
// Content-Type: application/problem+json   <- 전용 미디어 타입
{
  "type": "https://api.example.com/problems/sold-out", // 유형 식별 URI (문서 링크 겸용)
  "title": "재고 소진",                                 // 유형의 짧은 요약 — 유형마다 고정
  "status": 409,                                       // HTTP status 사본
  "detail": "상품 12345의 재고가 소진되었습니다",         // 이 발생 건의 상세
  "instance": "/orders/98765",                         // 이 발생 건의 식별 URI

  // 확장 멤버 — 표준이 정한 다섯 개 위에 자체 필드를 얹을 수 있다
  "code": "ORDER-001",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "errors": []
}
```

**`type`이 URI인 이유.** 에러 유형의 이름은 전 세계에서 충돌하지 않아야 하는데, 웹에는 이미 도메인이라는 네임스페이스 체계가 있다. `sold-out`이라는 이름은 우리 회사와 다른 회사가 서로 다른 뜻으로 쓸 수 있지만, `https://api.example.com/problems/sold-out`은 우리 것임이 분명하다. 그래서 URI를 쓴다.

여기서 반드시 짚어야 하는 것이 하나 있다. **이 URI는 반드시 접속 가능한 주소일 필요가 없다.** RFC는 그 주소를 브라우저로 열었을 때 사람이 읽을 문서가 나오는 것을 **권장**할 뿐이고, 클라이언트가 이 URI를 자동으로 GET 하는 것은 오히려 하지 말라고 한다. 자동으로 열면 에러 하나당 HTTP 요청이 하나씩 더 늘고, 우리는 그 주소를 실제로 서비스해야 할 의무를 지게 된다.

**클라이언트가 이 URI로 하는 일은 문자열 비교 하나다.** 2-6의 `switch error.code`와 정확히 같은 용법이고, 다만 값이 `"ORDER-001"` 대신 `"https://api.example.com/problems/sold-out"`인 것뿐이다. `type`이 사실상 우리 `code` 체계의 표준 버전인 셈이고, 2-6에서 말한 코드 카탈로그 문서화를 표준이 프로토콜 차원에서 흡수한 것이다.

**`application/problem+json`이 왜 따로 있는가.** 내용물이 JSON인데 굳이 미디어 타입을 나눈 이유는, **바디를 열어보지 않고 헤더만으로 "이건 에러 설명 문서다"를 알 수 있게** 하기 위해서다.

이 구분이 실제로 값을 하는 장면이 있다. 클라이언트 SDK는 응답을 받으면 성공 DTO 파서와 에러 파서 중 하나를 골라야 한다. `Content-Type`이 그냥 `application/json`이면 그 판단을 상태 코드에만 의존해야 하는데, 실무에서는 예외가 섞인다 — 게이트웨이가 대신 뱉은 HTML 에러 페이지가 502로 오기도 하고, 레거시 API가 에러를 200으로 내려주기도 한다. `application/problem+json`이 붙어 있으면 그 응답은 형식이 보장된 에러 문서다.

덧붙여 `+json`이라는 접미사(structured syntax suffix)는 "이 타입이 무엇이든 문법은 JSON을 따른다"는 표시다. 그래서 이 타입을 모르는 중간 도구도 최소한 JSON으로는 다룰 수 있다.

**Spring에서의 지원.** Spring Framework 6부터 `ProblemDetail` 타입이 들어와 있고, Spring Boot 3에서 `spring.mvc.problemdetails.enabled=true`를 켜면 프레임워크가 처리하는 예외들의 응답이 Problem Details 형식으로 바뀐다(구현 상세는 `02-spring/19-global-exception-handling-error-response.md`).

### 3-3. 자체 포맷 vs 표준 포맷 — 판단 기준은 소비자다

두 선택지가 무엇인지 먼저 정리하자. **자체 포맷**은 2절에서 설계한 `{code, message, errors, traceId}` 같은 우리 스키마이고, **표준 포맷**은 3-2의 Problem Details다. 둘 중 무엇이 우월하다는 답은 없고, **소비자가 누구인가**로 갈린다.

**소비자가 사내 프론트 팀 하나라면 자체 포맷이 편하다.** 필드를 우리 마음대로 정하고, 스키마 변경도 슬랙 한 줄로 합의된다. 표준을 따르는 대가로 얻는 "설명 없이 통하는 계약"이라는 이득이, 어차피 옆자리에 앉아 있는 팀에게는 크지 않다.

**외부 파트너·여러 회사가 붙는 공개 API라면 표준이 유리하다.** "우리 포맷 설명서를 읽으세요"보다 "RFC 9457입니다"가 훨씬 싸다. 소비자 쪽 언어와 프레임워크에 Problem Details를 이해하는 라이브러리가 이미 있는 경우도 많고, 그러면 파싱 코드를 아예 안 짜도 된다.

**둘은 양자택일이 아니다.** 3-2 예시에서 봤듯 표준은 확장 멤버를 허용하므로, 실무적 절충은 **"RFC 9457 골격 + 확장 멤버로 자체 code 체계"**다. 표준 도구가 이해하는 뼈대를 쓰면서 우리 도메인의 세부 분류도 유지한다.

마지막으로 무거운 사실 하나. **이미 자체 포맷으로 운영 중인 API를 표준으로 바꾸는 것 자체가 파괴적 변경이다.** 모든 소비자가 파서를 고쳐야 한다. 그래서 "표준이 더 좋으니 갈아타자"는 판단은 신규 API나 다음 메이저 버전에서 하는 것이지, 운영 중인 API에 조용히 적용할 일이 아니다.

### 3-4. 에러 스키마의 하위 호환 — 진화 규칙까지가 계약

성공 응답과 똑같이, 에러 스키마에도 변경 규칙이 필요하다. 규칙이 없으면 "이거 바꿔도 되나"를 매번 감으로 판단하게 되고, 그 판단은 언젠가 틀린다.

| 변경 | 안전한가 | 왜 |
|---|---|---|
| 새 필드 추가 (`traceId` 등) | 안전 | 소비자가 모르는 필드를 무시한다는 규약이 있을 때만 |
| 새 code 추가 | 조건부 안전 | 모르는 코드 폴백 규약이 있을 때만. 없으면 소비자가 터진다 |
| message 문구 수정 | 안전 | message로 분기하지 말라는 계약이 있을 때만 |
| code 의미 변경 | 위험 | 예외도 안 나고 조용히 틀린 화면으로 간다 — 삭제보다 나쁘다 |
| code 삭제·재사용 | 위험 | 응답 필드 삭제와 같은 급 |
| 에러의 HTTP status 변경 | 위험 | 재시도·캐시·모니터링·서킷 브레이커 판단이 한꺼번에 바뀐다 |

표의 오른쪽 칸에 "~규약이 있을 때만"이 반복되는 것이 핵심이다. **안전한 변경이란 그 자체로 안전한 것이 아니라, 소비자가 특정 규약을 지킨다는 전제 위에서만 안전하다.** 그래서 그 전제를 계약 문서에 명시해야 한다.

**규약 (1) — 모르는 필드는 무시한다.** 이것을 **Tolerant Reader**(관용적 파서)라고 부른다. 이 규약이 계약에 있어야 서버가 나중에 `traceId` 같은 필드를 추가할 수 있다. 없으면 필드 하나 추가에 모든 소비자가 깨진다(자세한 내용은 `08-backward-compatible-api-changes.md`).

**규약 (2) — 모르는 code는 HTTP status 기반 기본 처리로 폴백한다.** 서버는 도메인이 자라면서 새 코드를 계속 추가하게 된다. 소비자가 "아는 코드만 분기하고 나머지는 status로 처리"하기로 약속돼 있어야, 새 코드 추가가 하위 호환 변경으로 성립한다.

이 규약이 없을 때 실제로 터지는 형태가 구체적이다. **클라이언트가 code를 enum으로 역직렬화하는 경우**, 서버가 새 코드를 추가하는 순간 그 값이 enum에 없어서 역직렬화 자체가 예외를 던진다. 응답을 읽지도 못하고 앱이 크래시한다. 그래서 관용적 파싱의 구체 지침은 **"code는 문자열로 받고, 알려진 값만 매핑하고, 나머지는 기본 처리"**다. 2-6의 iOS 예시에서 `default` 절이 그 역할이었다.

## 4. 꼬리질문 대비 포인트

### "자체 에러 포맷과 RFC 9457 중 무엇을 선택하나?" (시니어 변별 포인트)

축은 "소비자가 누구인가"다. 사내 단일 프론트 팀이 소비자면 자체 포맷도 충분하고, 마이그레이션 비용이 없다면 굳이 갈아탈 이유가 약하다. 외부 파트너·공개 API·여러 조직이 소비자면 표준이 유리하다 — 설명 비용이 줄고, `application/problem+json`과 `type` URI라는 프로토콜 차원의 자기 문서화를 얻는다.

실무적 절충은 **"RFC 9457 골격 + 확장 멤버로 자체 code 체계"**다. 표준을 채택한다고 우리 코드 체계를 버릴 필요가 없다는 점을 정확히 아는지가 이 질문의 변별점이다.

마지막으로 **이미 자체 포맷으로 운영 중인 API를 표준으로 바꾸는 것 자체가 파괴적 변경**(모든 소비자의 파서 수정)이라는 점까지 언급하면, 표준의 우월함보다 계약의 무게를 먼저 보는 답이 된다.

### "에러 message를 클라이언트가 그대로 화면에 보여줘도 되나?"

"계약에 뭐라고 명시했는가"가 답이다. 명시가 없으면 서버는 개발자용 디버그 문구를 넣고 클라이언트는 그걸 사용자에게 띄우는 사고가 난다.

표시 가능 노선이면 서버가 문구 품질과 다국어를 책임지고, 개발자용 노선이면 클라이언트가 code 기반 매핑을 책임진다. 어느 쪽이든 내부 정보(예외 원문, SQL, 내부 호스트명)는 금지다.

다국어 서비스라면 code 매핑 노선이 자연스럽다는 것까지 말하면 좋다. 서버가 `Accept-Language`를 받아 번역해 내려주면 번역 리소스가 서버 배포 주기에 묶이는데, 클라이언트는 이미 자기 번역 파이프라인을 갖고 있는 경우가 대부분이다.

### "이미 운영 중인 API의 에러 코드를 바꾸거나 없애도 되나?"

안 된다. 코드는 클라이언트 분기 로직에 박힌 불변 계약이라, 의미 변경·삭제·재사용은 응답 필드 삭제와 같은 파괴적 변경이다. 특히 **모바일 앱은 배포로 회수가 안 된다**는 점을 근거로 들면 무게가 실린다.

잘못 만든 코드가 있다면 새 코드를 추가하고, 옛 코드는 지원 종료(deprecation) 공지 후 소비자 이전이 확인될 때까지 병행 유지한다. 순서가 "새것 추가 → 이전 → 옛것 제거"라는 것이 핵심이다.

여기에 대칭을 한 줄 붙이면 답이 완성된다. **message는 반대로 언제든 고칠 수 있어야 하고, 그래서 "클라이언트가 message로 분기하는 것"을 계약으로 금지해두는 것이 중요하다.** 이 금지가 없으면 message도 사실상 불변 계약이 되어버려, 오타 하나 못 고치는 API가 된다.

### "성공 응답도 {code, message, data} 래퍼로 감싸는 게 좋나?"

성공까지 감싸는 공통 래퍼(envelope)는 트레이드오프다.

장점은 성공과 실패의 파싱 구조가 완전히 같아지고, 상태 코드를 읽기 어려운 일부 레거시 환경에서 유용하다는 것이다. 단점은 HTTP status라는 표준 신호와 정보가 중복되고, 성공 응답마다 포장 비용이 붙으며, 표준 도구(OpenAPI 스키마 생성, HTTP 캐시 의미론)와 결이 어긋난다는 것이다.

REST를 제대로 쓴다면 **"성공은 맨 바디, 실패만 표준 에러 스키마"**가 일반적 권장이다. 그리고 답할 때 중요한 것은 **에러 응답 표준화는 성공 래퍼 없이도 성립한다**는 점을 분리해 말하는 것이다 — 이 둘을 한 덩어리로 묶어 생각하는 것이 흔한 혼동이다.

### "클라이언트가 모르는 에러 코드를 받으면 어떻게 처리해야 하나?"

HTTP status 기반 기본 처리로 폴백한다 — 4xx면 "요청을 확인하세요"류의 일반 안내, 5xx나 429면 재시도 또는 잠시 후 안내다. 2-2에서 정리한 **"status는 부류, code는 세부"**라는 이중 축이 여기서 값을 한다. 세부를 모르면 부류로 떨어지면 되는 것이다.

그리고 이 폴백 규약이 **계약에 명시돼 있어야** 서버가 새 코드를 추가하는 것이 하위 호환 변경으로 성립한다는 점을 짚어야 한다. 규약 없이 코드를 추가하는 것은 사실상 소비자를 깨뜨리는 도박이다.

구현 관점의 함정도 덧붙이면 좋다. **code를 enum으로 역직렬화하는 클라이언트는 모르는 값에서 응답을 읽지도 못하고 터진다.** 그래서 "코드는 문자열로 받고 알려진 것만 매핑"이 관용적 파싱(Tolerant Reader)의 구체적 형태다. 같은 원리가 필드 추가에도 적용된다는 것까지 연결하면(`08-backward-compatible-api-changes.md`), 에러 스키마의 진화를 API 호환성이라는 더 큰 규칙의 한 사례로 보고 있다는 인상을 준다.

## 한 줄 요약

에러 응답 표준화는 포맷 통일이 아니라 계약 설계다 — 바디를 안 보는 인프라가 읽는 축(HTTP status)과 클라이언트 분기가 읽는 축(불변 code)을 나눈 단일 스키마를 정하고, 여기에 사람용 message·검증 상세 `errors[]`·분산 추적의 진입점 traceId를 얹은 뒤, 코드 분리 기준("클라이언트가 다르게 행동할 때만")과 진화 규칙(필드 추가는 안전, 코드 삭제는 금지, 모르는 코드는 status로 폴백)까지 문서화해 소비자와 공유하며, 외부 공개 API라면 RFC 9457이라는 표준 골격 위에 자체 code를 확장 멤버로 얹는 것까지 검토하는 것이 "여러 팀이 소비하는 제품"으로서의 API 설계다.
