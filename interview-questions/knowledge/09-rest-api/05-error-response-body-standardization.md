# API 에러 응답 바디 표준화 — 에러 스키마는 성공 응답과 동급의 계약이다

> 핵심 관전 포인트: **모든 에러가 하나의 스키마로 나가도록 응답 바디를
> 계약으로 설계한다. 축을 둘로 나눈다 — 기계가 읽는 축(HTTP status +
> 기계 판독용 에러 code)과 사람이 읽는 축(message). 여기에 검증 실패용
> 필드 상세 배열과 장애 추적용 trace id를 더하면 뼈대가 완성된다.
> 에러 코드는 "클라이언트가 다르게 행동해야 할 때만" 분리하고, 한번
> 공개한 코드는 필드명과 같은 급의 불변 계약으로 관리한다. 자체 포맷
> 대신 RFC 9457(구 RFC 7807) Problem Details라는 표준을 채택하는
> 선택지도 있으며, 외부 공개 API일수록 표준이 계약 비용을 줄인다.
> 코드 목록을 문서화해 소비자와 공유하는 것까지가 설계다.**

---

## 0. 질문 + 의도

**질문**: "API 에러 응답 바디는 어떻게 표준화하나요?"

**출제 의도**: 에러 스펙이 제각각이면 클라이언트마다 파싱 분기가
생기고, 장애 시 에러 원인 분류가 불가능하다. API를 "혼자 만드는 것"이
아니라 "여러 팀이 소비하는 제품"으로 보는지 확인한다. 스프링 구현
테크닉이 아니라, 에러 응답이라는 스키마를 소비자와의 계약으로 설계할
수 있는지를 보는 질문.

(스프링에서의 구현 — @RestControllerAdvice, ErrorCode enum, 필터/비동기
구역의 포맷 통일 — 은 `02-spring/19-global-exception-handling-error-response.md`
참고. 이 문서는 **응답 스키마 설계 자체**에 집중한다.)

## 1. 표준화가 없으면 생기는 일 — 파싱 분기와 집계 불능

에러 포맷을 계약하지 않은 조직의 API는 이렇게 된다:

```jsonc
// ❌ before: API마다 에러 바디 모양이 다르다
// 주문 API — A 개발자
{ "error": "재고가 없습니다" }

// 회원 API — B 개발자
{ "success": false, "errorMessage": "이미 가입된 이메일", "errCode": 1042 }

// 결제 API — 외부 SDK 스타일 흉내
{ "result": { "status": "FAIL", "reason": "LIMIT_EXCEEDED" } }
```

이 상태의 비용은 두 방향으로 발생한다:

- **소비자(프론트·모바일·파트너) 비용**: API마다 에러 파싱 코드를
  따로 짠다. 공통 에러 인터셉터가 불가능해지고, "어떤 키에 뭐가
  들었는지"를 슬랙으로 물어보는 협업이 반복된다.
- **운영 비용**: 장애가 났을 때 "어떤 종류의 실패가 늘고 있는지"를
  집계할 공통 키가 없다. 에러 원인 분류가 로그 문자열 grep으로
  퇴화한다.

표준화란 이 응답을 **하나의 스키마**로 통일하는 것이다:

```jsonc
// ✅ after: 어떤 API가 실패해도 이 모양 — 소비자는 파서를 한 번만 짠다
{
  "code": "ORDER-001",            // 기계 판독용 — 분기·집계의 키
  "message": "재고가 소진된 상품입니다",  // 사람용
  "errors": [],                   // 검증 실패 시 필드별 상세
  "traceId": "a1b2c3d4"           // 장애 추적의 진입점
}
```

## 2. 스키마의 각 필드는 소비자가 다르다

표준 스키마를 설계할 때는 "필드마다 누가 읽는가"를 따져야 한다.
같은 정보를 사람용과 기계용으로 분리하는 것이 핵심이다.

### 2-1. 이중 축: HTTP status(분류) + code(세부 구분)

- **HTTP status**: 클라이언트 라이브러리·게이트웨이·로드밸런서·APM이
  공유하는 1차 신호. 재시도 가능 여부(5xx/429 vs 4xx), 캐시 가능 여부,
  에러율 지표가 여기서 나온다. 그래서 에러를 200에 담으면 안 된다 —
  인프라 전체가 장애를 못 본다.
- **code**: HTTP status는 종류가 적어 비즈니스 구분을 못 담는다.
  "재고 소진"과 "쿠폰 만료"가 둘 다 409라면, code가 없을 때 프론트가
  할 수 있는 건 message 문자열 비교뿐이고 — 그 순간 **문구 수정이
  프론트 장애가 되는** 최악의 결합이 생긴다. `ORDER-001` 같은
  기계 판독용 코드가 이 결합을 끊는다.

### 2-2. message — "보여줘도 되는가"를 계약에 명시한다

message 필드에서 흔히 터지는 계약 불명확성: 클라이언트가 이 문구를
그대로 화면에 띄워도 되는가? 두 가지 노선이 있고, **어느 쪽이든
문서에 명시하는 것**이 표준화다.

- **노선 A — message는 표시 가능**: 서버가 사용자에게 보여도 안전한
  문구만 담는다. 클라이언트 구현이 단순해지지만, 다국어와 문구
  수정 주기가 서버 배포에 묶인다.
- **노선 B — message는 개발자용, 표시는 code 기반 매핑**: 클라이언트가
  code → 자기 문구 테이블로 변환한다. 다국어·A/B 문구 제어가
  클라이언트 자유가 되는 대신, 모든 code에 대응하는 매핑 관리 부담이
  생긴다. 다국어 서비스·여러 클라이언트(웹/iOS/Android)면 이쪽이
  일반적이다.

어느 노선이든 **내부 정보(스택트레이스, 예외 메시지 원문, SQL)는
message에 절대 싣지 않는다** — 계약이자 보안 규칙이다.

### 2-3. errors[] — 복수 오류를 담는 그릇, 그러나 포맷은 하나

검증 실패는 오류가 여러 개다. 단일 message로는 "첫 오류만 고치면 또
다음 오류"라는 UX가 된다. 필드별 상세 배열을 두되, 검증 실패가 아닌
에러에서는 빈 배열로 나가게 해서 **스키마 자체는 하나로 유지**한다.
에러 종류마다 응답 모양이 달라지면 그건 표준화가 아니다.

```jsonc
{
  "code": "COMMON-001",
  "message": "입력값이 올바르지 않습니다",
  "errors": [
    { "field": "email", "reason": "이메일 형식이 아닙니다" },
    { "field": "age", "reason": "0 이상이어야 합니다" }
  ]
}
```

### 2-4. traceId — 에러 응답을 장애 추적의 진입점으로 (가산점 포인트)

사용자가 "오류가 났어요"라고 문의하면, 응답에 찍힌 traceId로 서버
로그·분산 트레이스를 바로 찾을 수 있다. 에러 응답 스키마에 추적
식별자를 넣는 순간, 에러 바디는 CS → 로그 → 원인의 연결 고리가 된다.

## 3. 에러 코드 체계 설계 — 코드는 필드명과 같은 급의 계약

code 필드를 두기로 했다면, 코드 체계 자체가 설계 대상이 된다.

- **네임스페이스**: `도메인-일련번호`(예: `ORDER-001`, `AUTH-003`)처럼
  접두어로 소유 팀/도메인이 드러나게 한다. 장애 시 "어느 도메인의
  실패가 늘었나"가 코드만으로 보인다.
- **분리 기준**: 코드를 잘게 쪼갤수록 좋은 게 아니다. 소비자가 처리할
  수 없는 코드가 쏟아지면 결국 전부 "기타 오류"로 뭉개진다. 기준은
  하나 — **"클라이언트가 다르게 행동해야 하는 경우에만 코드를
  분리한다"** (재고 소진 → 재입고 알림 버튼, 인증 만료 → 로그인 이동,
  한도 초과 → 한도 안내 화면… 처럼 행동이 갈릴 때만).
- **불변성**: 한번 공개한 코드는 클라이언트 분기 로직에 박힌다.
  코드의 **의미 변경·삭제·재사용은 필드 삭제와 같은 파괴적 변경**이다.
  message는 언제든 고쳐도 되지만 code는 안 된다 — 이 비대칭이 두
  필드를 분리한 이유 그 자체다.
- **카탈로그 문서화**: 코드 목록(코드·의미·HTTP status·클라이언트
  권장 행동)을 API 문서의 1급 시민으로 관리하고 소비자와 공유한다.
  성공 응답 스키마는 문서화하면서 에러 코드 표가 없는 API가 흔한데,
  그 API의 에러 계약은 "물어봐야 아는 것"이 된다.

## 4. 표준 형식 — RFC 9457 Problem Details

에러 응답 표준화에는 이미 국제 표준이 있다. RFC 7807 "Problem Details
for HTTP APIs", 현재는 이를 대체(obsolete)한 **RFC 9457**이다.

```jsonc
// RFC 9457 Problem Details 예시
// Content-Type: application/problem+json  ← 전용 미디어 타입
{
  "type": "https://api.example.com/problems/sold-out",  // 문제 유형 식별 URI (문서 링크 겸용)
  "title": "재고 소진",                                  // 유형의 짧은 요약 (유형마다 고정)
  "status": 409,                                        // HTTP status 복사본
  "detail": "상품 12345의 재고가 소진되었습니다",          // 이 발생 건의 상세
  "instance": "/orders/98765",                          // 이 발생 건의 식별 URI
  // 확장 멤버 — 자체 필드를 표준 위에 얹을 수 있다
  "code": "ORDER-001",
  "traceId": "a1b2c3d4"
}
```

- `type`이 이 표준의 핵심 아이디어다: 에러 유형을 URI로 식별하고,
  그 URI가 곧 **해당 에러의 문서 링크** 역할을 한다. 코드 카탈로그
  문서화(3절)를 표준이 프로토콜 차원에서 흡수한 것.
- 표준 필드만으로 부족하면 **확장 멤버**로 자체 필드(code, errors,
  traceId)를 추가하면 된다. 표준 채택과 자체 코드 체계는 양자택일이
  아니다.
- Spring Framework 6부터 `ProblemDetail` 타입으로 기본 지원된다
  (구현 상세는 02-spring/19 문서).

**자체 포맷 vs 표준 포맷의 판단 기준**: 소비자가 사내 프론트 팀
하나라면 자체 포맷의 자유도가 편하다. 그러나 외부 파트너·여러 회사가
붙는 공개 API라면, "우리 포맷 설명서"를 읽게 하는 것보다 표준을
가리키는 쪽이 계약 비용이 싸다 — 소비자 쪽 라이브러리·도구가 표준을
이미 이해하는 경우도 많다.

## 5. 에러 스키마의 하위 호환 — 진화 규칙까지가 계약

성공 응답과 똑같이, 에러 스키마에도 변경 규칙이 필요하다.

- **필드 추가는 안전, 삭제·의미 변경은 파괴적**: 소비자는 "모르는
  필드는 무시한다"는 관용적 파싱을 전제로 한다. 이 전제를 계약에
  명시해두면 서버는 traceId 같은 필드를 나중에 추가할 수 있다.
- **모르는 code에 대한 폴백 규약**: 서버는 계속 새 코드를 추가하게
  된다. 소비자에게 "모르는 code를 받으면 HTTP status 기반 기본
  처리로 폴백하라"는 규칙을 계약에 넣어야, 새 코드 추가가
  하위 호환 변경으로 성립한다. 이 규약이 없으면 코드 추가조차
  클라이언트 크래시(예: enum 역직렬화 실패)가 될 수 있다.

## 6. 꼬리질문 대비 포인트

### "자체 에러 포맷과 RFC 9457 중 무엇을 선택하나?" (시니어 변별 포인트)

축은 "소비자가 누구인가"다. 사내 단일 프론트 팀이 소비자면 자체
포맷도 충분하고 마이그레이션 비용이 없다면 굳이 갈아탈 이유가 약하다.
외부 파트너·공개 API·여러 조직이 소비자면 표준이 유리하다 — 설명
비용이 줄고, `application/problem+json`과 `type` URI라는 프로토콜
차원의 자기 문서화를 얻는다. 실무적 절충은 "RFC 9457 골격 + 확장
멤버로 자체 code 체계"다. 이미 자체 포맷으로 운영 중인 API를 표준으로
바꾸는 것 자체가 파괴적 변경이라는 점(모든 소비자의 파서 수정)까지
언급하면 계약의 무게를 아는 답이 된다.

### "에러 message를 클라이언트가 그대로 화면에 보여줘도 되나?"

"계약에 뭐라고 명시했는가"가 답이다. 명시가 없으면 서버는 개발자용
디버그 문구를 넣고 클라이언트는 그걸 사용자에게 띄우는 사고가 난다.
표시 가능 노선이면 서버가 문구 품질·다국어를 책임지고, 개발자용
노선이면 클라이언트가 code 기반 매핑을 책임진다. 어느 쪽이든 내부
정보(예외 원문, SQL)는 금지. 다국어 서비스라면 Accept-Language 처리
부담 때문에 code 매핑 노선이 자연스럽다는 것까지 말하면 좋다.

### "이미 운영 중인 API의 에러 코드를 바꾸거나 없애도 되나?"

안 된다 — 코드는 클라이언트 분기 로직에 박힌 불변 계약이라, 의미
변경·삭제·재사용은 필드 삭제와 같은 파괴적 변경이다. 잘못 만든 코드가
있다면 새 코드를 추가하고 옛 코드는 지원 종료(deprecation) 공지 후
소비자 이전이 확인될 때까지 병행 유지한다. message는 반대로 언제든
고칠 수 있어야 하며, 그래서 클라이언트가 message로 분기하는 것을
계약으로 금지해두는 것이 중요하다.

### "성공 응답도 {code, message, data} 래퍼로 감싸는 게 좋나?"

성공까지 감싸는 공통 래퍼(envelope)는 트레이드오프다. 장점: 성공/실패
파싱 구조가 완전히 동일해지고, 일부 레거시 환경(status를 읽기 어려운
클라이언트)에서 유용하다. 단점: HTTP status라는 표준 신호와 정보가
중복되고, 성공 응답마다 포장 비용이 붙으며, 표준 도구(OpenAPI 스키마,
HTTP 캐시 의미론)와 결이 어긋난다. REST를 제대로 쓴다면 "성공은 맨
바디, 실패만 표준 에러 스키마"가 일반적 권장이고, 에러 응답 표준화는
성공 래퍼 없이도 성립한다 — 둘을 구분해서 답하면 된다.

### "클라이언트가 모르는 에러 코드를 받으면 어떻게 처리해야 하나?"

HTTP status 기반 기본 처리로 폴백한다 — 4xx면 "요청을 확인하세요"류의
일반 안내, 5xx/429면 재시도 또는 잠시 후 안내. 이 폴백 규약이 계약에
있어야 서버가 새 코드를 추가하는 것이 하위 호환 변경으로 성립한다.
구현 관점에서는 코드를 enum으로 역직렬화해 모르는 값에서 터지는
클라이언트가 흔한 함정이라는 것, 그래서 "코드는 문자열로 받고 알려진
것만 매핑"이 관용적 파싱이라는 것까지 짚으면 좋다.

## 한 줄 요약

에러 응답 표준화는 포맷 통일이 아니라 계약 설계다 — 기계용
축(status + 불변 code)과 사람용 축(message)을 분리한 단일 스키마를
정하고, 코드 분리 기준("클라이언트 행동이 달라질 때만")과 진화
규칙(추가는 안전·삭제는 금지·모르는 코드는 폴백)까지 문서화해
소비자와 공유하며, 외부 공개 API라면 RFC 9457이라는 표준 위에 얹는
것까지 검토하는 것이 "여러 팀이 소비하는 제품"으로서의 API 설계다.
