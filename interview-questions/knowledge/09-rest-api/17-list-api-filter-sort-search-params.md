# 목록 API의 필터·정렬·검색 파라미터 설계 — 정렬 키 하나가 DB 인덱스와 맺는 계약

> 핵심 관전 포인트: **필터는 의미가 드러나는 명시적 파라미터
> (`status=SHIPPED&minAmount=10000`)로, 정렬은 하나의 규약된 형식
> (`sort=createdAt,desc`)으로, 전문 검색은 `q=` 하나로 분리해 설계하고 —
> 셋 다 서버가 화이트리스트로 허용 값을 제한한다. 허용 정렬 키를 제한해야
> 하는 이유는 세 겹이다: ① 성능 — 정렬 키는 곧 DB 정렬이고, 인덱스 없는
> 컬럼 정렬은 전체 읽기 + filesort라 클라이언트가 파라미터 하나로 DB
> 부하를 유발할 수 있는 문이 된다 ② 보안·캡슐화 — 요청 값을 정렬 구문에
> 반영하는 구조는 내부 컬럼명 노출과 ORDER BY 인젝션의 통로다 ③ 계약 —
> 한 번 허용한 정렬 키는 클라이언트가 의존하는 공개 계약이 되어, 그 키를
> 받치는 인덱스를 영원히 유지해야 한다. 즉 정렬 키 목록은 "API 스펙이자
> 인덱스 목록"이며, 둘을 함께 관리하는 시야가 이 문항의 핵심이다.**

---

## 0. 질문 + 의도

**질문**: "목록 조회 API의 필터·정렬·검색 파라미터는 어떻게 설계하나요?
허용 정렬 키를 제한해야 하는 이유는?"

**출제 의도**: 검색 조건은 요구사항이 끝없이 추가되는 영역이다. 파라미터
폭발을 계약으로 관리하고 허용 정렬 키를 인덱스와 연동해 제한하는지 —
API 설계와 DB 설계를 함께 쥐는 시야를 본다. "파라미터를 어떻게 받느냐"
는 표면이고, "그 파라미터가 DB에 어떤 쿼리를 만들 수 있는가"까지 내다
보는지가 관전 포인트다.

## 1. 파라미터 설계 규약 — 필터 / 정렬 / 검색을 분리한다

목록 API의 조회 조건은 성격이 다른 세 종류가 섞여 들어온다. 먼저 이 셋을
구분해 각각의 규약을 세우는 것이 설계의 시작이다.

### 1-1. 필터 — 의미가 드러나는 명시적 파라미터

```text
GET /orders?status=SHIPPED&minAmount=10000&orderedFrom=2026-08-01&orderedTo=2026-08-31
```

- **필드별 명시적 파라미터**가 기본이다. `filter=status:SHIPPED` 같은
  범용 문법을 발명하면 파싱 규칙 자체가 계약이 되어 문서화·검증·확장이
  전부 어려워진다 — 파라미터 이름이 곧 문서인 형태가 강하다.
- **범위 조건은 쌍으로**: `minAmount`/`maxAmount` 또는
  `orderedFrom`/`orderedTo`처럼 이름에 경계의 방향을 담는다. 경계 포함
  여부(이상/초과)는 문서에 명시한다 — 정하지 않으면 클라이언트마다
  해석이 갈린다.
- **다중 값은 반복 파라미터 또는 콤마**: `status=SHIPPED&status=DELIVERED`
  또는 `status=SHIPPED,DELIVERED`. 팀에서 하나로 통일하고 전 API에 같은
  규칙을 쓴다 — 목록 API 규약의 가치는 개별 설계의 우수함보다 **전체
  일관성**(클라이언트 개발자의 예측 가능성)에서 나온다.
- **허용 값 검증**: enum 필터(`status`)는 허용 값 밖이면 400으로 명시적
  거절. 오타(`status=SHIPED`)를 빈 결과로 조용히 응답하면 클라이언트
  버그가 "데이터가 없네"로 위장된다.

### 1-2. 정렬 — 하나의 형식 + 화이트리스트

```text
GET /orders?sort=createdAt,desc              ← Spring Data 관례
GET /orders?sort=-createdAt                  ← 부호 접두 관례 (JSON:API 등)
```

형식은 어느 쪽이든 좋다 — 중요한 건 **전사적으로 하나**라는 것과, 정렬
가능한 필드를 **서버가 열거해 제한**한다는 것(§2). 다중 정렬
(`sort=status,asc&sort=createdAt,desc`)을 지원한다면 우선순위가 파라미터
순서라는 것까지 계약에 적는다.

기본 정렬도 계약이다 — `sort` 생략 시의 순서(보통 `createdAt,desc`)를
문서에 명시하고 **암묵에 맡기지 않는다.** `ORDER BY` 없는 SQL의 반환
순서는 보장이 없어서, "어제까지 최신순이었는데 오늘부터 순서가 튀어요"
같은 제보는 대부분 기본 정렬을 명시하지 않은 목록에서 나온다.

### 1-3. 검색 — `q` 하나로 받고, 어디를 어떻게 찾는지는 서버가 정한다

```text
GET /orders?q=김철수
```

전문 검색(부분 일치, 여러 필드 대상)은 필터와 성격이 다르다 — 필터는
"정확한 조건"이고 검색은 "관련된 것 찾기"다. `q` 하나로 받고 대상
필드와 매칭 방식(전방 일치인지, 형태소 분석인지)은 서버 구현으로 감춘다.
클라이언트가 `searchField=name&searchOp=contains`처럼 검색의 내부를
조립하게 열어 주면, `contains`(중간 일치)는 인덱스를 못 타는 조건이라
§2의 정렬 키 문제와 똑같은 "파라미터로 DB 부하를 만드는 문"이 된다.

### 1-4. 파라미터 폭발의 관리

rationale이 짚듯 검색 조건은 끝없이 늘어난다. 관리 원칙:

- **추가는 하위 호환, 의미 변경·제거는 파괴적 변경** — 새 필터 추가는
  자유롭지만, 한 번 공개한 파라미터의 의미를 바꾸면 기존 클라이언트가
  깨진다. 추가 전에 이름과 의미를 신중히 정하는 이유다.
- 조건 조합이 수십 개로 늘고 GET 쿼리스트링이 한계에 닿으면
  `POST /orders/search` + 본문 조건 객체로 전환한다(→ 꼬리질문 §4-1).
- 다중 필터 × 자유 정렬 × 전문 검색이 **동시에** 요구되는 화면(관리자
  통합 검색)은 RDB 인덱스 설계로 감당할 조합 수를 넘어선다 — 검색
  엔진 위임을 검토할 신호다(§3).

## 2. 허용 정렬 키를 제한해야 하는 이유 — 세 겹의 방어

### 2-1. 성능 — 정렬 파라미터는 DB 부하로 통하는 문이다

`sort` 파라미터는 그대로 `ORDER BY`가 된다. 인덱스가 받치는 정렬은
인덱스를 순서대로 읽으면 끝이지만, **인덱스 없는 컬럼 정렬은 조건에 맞는
전체를 읽어 정렬(filesort / Sort 노드)한 뒤에야 첫 페이지를 줄 수 있다** —
`LIMIT 20`이 있어도 정렬 대상 전체를 읽는 비용은 그대로다. 즉 정렬 키를
제한하지 않은 목록 API는 **클라이언트가 쿼리스트링 하나로 대형 정렬
작업을 DB에 시킬 수 있는 API**다. 크롤러나 잘못 짠 클라이언트가
`sort=memo`(인덱스 없는 컬럼)로 연타하면 그게 DB CPU 스파이크가 된다.

허용 목록은 그래서 "인덱스가 받치는 정렬 축"과 일치해야 한다 — **정렬
키 화이트리스트는 API 스펙이면서 동시에 인덱스 목록이다.**

### 2-2. 보안·캡슐화 — 요청 값이 ORDER BY 구문에 닿게 하지 않는다

`WHERE` 값과 달리 `ORDER BY`의 컬럼명 자리는 **바인딩 파라미터로 처리할
수 없다**(값이 아니라 구문 요소라서). 그래서 동적 정렬을 문자열 조립으로
구현한 코드는 인젝션 통로가 된다.

```java
// ❌ before: 요청 파라미터를 ORDER BY 에 그대로 이어 붙인다
String sql = "SELECT * FROM orders WHERE user_id = ? ORDER BY " + sortParam;
// sortParam = "amount; DROP TABLE orders" 같은 주입 시도의 표적.
// 주입까지 안 가도 — 엔티티 내부 컬럼명이 그대로 API 계약에 노출되고,
// 존재하지 않는 컬럼이면 500, 인덱스 없는 컬럼이면 §2-1 의 부하.
```

Spring Data의 `Pageable`을 그대로 받는 것도 정도만 다를 뿐 같은 문제다 —
`?sort=anyField,desc`로 들어온 문자열이 정렬에 반영되므로, 존재하지 않는
속성은 `PropertyReferenceException`(500으로 새기 쉽다), 존재하지만
인덱스 없는 속성은 성능 문, 그리고 **엔티티 필드명 전체가 사실상 공개
계약**이 된다.

```java
// ✅ after: 허용 키를 enum 으로 열거하고, API 이름 → 내부 정렬을 매핑한다
public enum OrderSortKey {
    CREATED_AT("createdAt", Sort.by(DESC, "createdAt", "id")),
    AMOUNT("amount",        Sort.by(DESC, "totalAmount", "id"));
    // 각 항목은 받쳐 주는 복합 인덱스가 존재할 때만 추가한다
    // tie-breaker(id)까지 매핑에 포함 — 커서 페이지네이션과의 연동 지점

    private final String apiName;     // 외부 계약: "createdAt"
    private final Sort sort;          // 내부 구현: 실제 정렬 (컬럼명은 비공개)

    public static OrderSortKey from(String param) {
        return Arrays.stream(values())
                .filter(k -> k.apiName.equals(param))
                .findFirst()
                .orElseThrow(() -> new InvalidSortKeyException(param));
                // → @ControllerAdvice 에서 400 + "허용 정렬 키: createdAt, amount"
    }
}
```

이 매핑 한 겹이 세 문제를 한 번에 막는다 — 요청 문자열은 enum 비교에만
쓰이므로 구문에 닿을 수 없고(인젝션 차단), 외부 이름과 내부 컬럼이
분리되며(캡슐화 — 나중에 컬럼명을 바꿔도 API는 그대로), 목록에 없는 키는
400으로 거절된다(성능 문 봉쇄). 허용 밖 키를 **조용히 기본 정렬로 폴백
하지 않고 400으로 거절**하는 것도 중요하다 — 폴백은 클라이언트의 오타를
"정렬이 안 먹네?"라는 미스터리로 만든다.

### 2-3. 계약 — 한 번 허용한 정렬 키는 인덱스 유지 의무가 된다

허용 목록에 키를 추가하는 순간 클라이언트들이 의존하기 시작하고, 하위
호환 원칙상 제거는 파괴적 변경이다. 그 키를 받치는 인덱스도 함께 영구
유지 대상이 된다 — 인덱스는 공짜가 아니어서 쓰기마다 갱신 비용을 내므로,
**정렬 키 추가는 "인덱스 하나를 평생 운영한다"는 결정**이다. "일단 다
열어 두고 필요하면 막자"가 안 되는 이유가 여기 있다: 여는 건 한 순간이고
막는 건 파괴적 변경이라, **좁게 시작해서 요구가 확인될 때 넓히는 것**이
유일하게 되돌릴 수 있는 방향이다.

(가산점 포인트) 커서 페이지네이션과의 연동 — 정렬 축 하나하나가 커서
구성 값 + tie-breaker 포함 복합 인덱스를 요구하므로
([04번 문서](04-pagination-offset-vs-cursor-api-contract.md)), 커서 기반
목록에서 정렬 키 화이트리스트는 선택이 아니라 구조적 전제다. 정렬 키
enum에 tie-breaker까지 함께 매핑해 두면(위 코드) "정렬 키 추가 = 커서
설계 + 인덱스 추가"라는 체크리스트가 코드에 고정된다.

## 3. 실무 사례 — "관리자 그리드의 모든 컬럼 정렬" 요구

전형적 전개: 관리자 화면에 데이터 그리드 라이브러리를 붙였더니 모든
컬럼 헤더가 클릭으로 정렬된다. 프론트는 `Pageable`을 그대로 받는 백엔드
덕에 "이미 다 되는데요"라며 열어 달라 하고, 몇 주 뒤 운영팀이 인덱스
없는 컬럼을 정렬한 채 깊은 페이지를 넘기면서 DB CPU가 튄다. 조회
경로를 추적하면 `ORDER BY memo`가 filesort로 전체를 읽고 있다.

대응은 세 갈래로 정리된다:

- **즉시**: 정렬 키 화이트리스트(§2-2)를 걸어 문을 닫는다. 그리드에는
  "정렬 가능 컬럼"만 정렬 아이콘이 켜지도록 허용 목록을 API 스펙으로
  내려 준다 — 계약을 UI까지 전파하는 것.
- **협상**: "모든 컬럼 정렬"이 진짜 요구인지 확인한다. 대부분 실제로
  쓰는 정렬 축은 두세 개다 — 쓰는 축만 인덱스와 함께 허용 목록에
  추가한다. 요구사항의 크기를 확인하지 않고 기술로만 받으면 인덱스가
  컬럼 수만큼 늘어난다.
- **구조 전환**: 다중 필터 × 임의 정렬 × 전문 검색이 전부 진짜 요구라면
  RDB 인덱스로는 조합 폭발을 감당할 수 없다 — 검색 엔진(Elasticsearch)에
  색인해 그 화면만 위임한다. 대가는 색인 동기화 지연과 운영 컴포넌트
  추가이므로, 화이트리스트로 버틸 수 있는 동안은 꺼내지 않는다.

이 사례가 rationale의 "API 설계와 DB 설계를 함께 쥐는 시야"다 — 정렬
파라미터 설계는 프론트 편의 문제처럼 보이지만, 실체는 **DB에 어떤 쿼리를
허용할 것인가의 결정**이다.

## 4. 꼬리질문 대비 포인트

### "필터 조건이 계속 늘어 쿼리스트링이 감당이 안 되면 어떻게 하나요?"

`POST /orders/search`(또는 `/orders:search`)로 전환해 조건 객체를 본문에
담는다. URL 길이 한계와 중첩 조건(AND/OR 조합) 표현 문제를 해결하지만,
POST라 HTTP 캐시를 잃고 "조회인데 POST"라는 시맨틱 절충임을 문서에
명시해야 한다. 이때도 조건 객체의 필드와 연산자는 서버가 정의한 스키마로
제한한다 — 본문으로 옮겼다고 해서 "임의 필드 + 임의 연산자"를 열면
쿼리스트링 시절보다 더 넓은 문이 된다.

### "sort 파라미터 형식은 어떤 것을 쓰나요? 기준이 있나요?"

`sort=createdAt,desc`(Spring Data 관례)와 `sort=-createdAt`(JSON:API 등
부호 접두) 모두 실무에서 통용되고 우열은 크지 않다. 진짜 기준은 ①
**전사 일관성** — 서비스마다 형식이 다르면 클라이언트가 API마다 문서를
다시 읽어야 한다 ② 다중 정렬의 우선순위 규칙 명시 ③ 기본 정렬의 문서화.
"형식 선택보다 형식의 통일과 계약 명시가 본질"이라고 답하면 rationale의
'일관성 = 예측 가능성' 관점과 정렬된다.

### "허용 목록 밖 정렬 키가 오면 400과 기본 정렬 폴백 중 무엇이 맞나요?"

400 거절이 맞다. 폴백은 당장의 장애는 없어 보이지만 클라이언트의 오타나
잘못된 연동을 "정렬이 이상하다"는 형태로 숨긴다 — 빨리 실패(fail-fast)
해야 개발 단계에서 잡힌다. 에러 응답에 허용 키 목록을 담아 주면 문서를
다시 찾는 왕복을 줄여 준다. 단, 이미 폴백으로 동작 중인 운영 API를 400
으로 바꾸는 것은 그 자체가 파괴적 변경이므로, 유예 기간(로그로 위반
클라이언트 파악 → 공지 → 전환)을 둔다.

### "필터 조합마다 인덱스를 다 만들 수는 없는데, 필터 파라미터도 제한해야 하나요?" (시니어 변별 포인트)

원칙은 같지만 강도는 다르게 적용한다. 정렬은 인덱스가 없으면 전체 읽기
+ filesort로 비용이 급격히 나빠지므로 화이트리스트가 필수이고, 필터는
선택도 높은 다른 조건과 결합하면 인덱스 없이도 견딜 수 있는 경우가 많다.
실무 기준: ① 자주 쓰이는 필터 조합(접근 로그로 확인)에 복합 인덱스를
설계하고 ② 선택도 낮은 필터 단독 호출(예: `status`만, 전체의 90%가
같은 값)이 문제라면 "단독 사용 불가, 기간 필터 필수" 같은 **조합 제약을
계약에 명시**하며 ③ 조합이 통제 불능으로 늘면 검색 엔진 위임(§3)으로
넘어간다. "필터 파라미터 목록 = 지원을 약속한 조회 패턴"이라는 계약
관점은 정렬과 동일하다 — 받을 수 있는 것과 빠르게 처리할 수 있는 것을
구분해 후자만 약속하는 것이 설계다.

### "검색(q)이 LIKE '%키워드%'로 구현돼 있으면 어떤 문제가 있나요?"

중간 일치(`%키워드%`)는 B-tree 인덱스를 탈 수 없어(정렬된 구조는 접두
로만 탐색 가능) 전체 스캔이 된다 — 데이터가 늘면 검색이 목록 전체를
읽는 쿼리가 된다. 단계적 대응: ① 전방 일치(`키워드%`)로 요구를 좁힐 수
있는지 확인(인덱스 사용 가능) ② DB의 전문 검색 기능(PostgreSQL
`tsvector`/GIN, MySQL FULLTEXT) ③ 검색 요구가 본격적이면(형태소 분석,
랭킹, 다중 필드) 검색 엔진 위임. `q` 파라미터의 계약을 "어떻게 찾는지는
서버 구현"으로 감춰 뒀다면(§1-3) 이 전환을 클라이언트 변경 없이 할 수
있다 — 파라미터 설계가 구현 진화의 자유를 지켜 주는 사례다.

## 한 줄 요약

필터는 명시적 파라미터, 정렬은 통일된 형식, 검색은 `q` 하나로 분리하되
셋 다 서버가 허용 값을 화이트리스트로 제한한다 — 특히 정렬 키는 인덱스
없는 컬럼 정렬(전체 읽기 + filesort)이라는 DB 부하의 문이자, ORDER BY
인젝션·내부 컬럼명 노출의 통로이자, 한 번 열면 인덱스 유지 의무가 되는
공개 계약이므로, **허용 정렬 키 목록 = 인덱스 목록**으로 관리하며 좁게
시작해 요구가 확인될 때만 넓히는 것이 API와 DB를 함께 쥐는 설계다.
