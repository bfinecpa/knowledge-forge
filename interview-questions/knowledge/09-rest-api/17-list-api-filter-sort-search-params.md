# 목록 API의 필터·정렬·검색 파라미터 설계 — 정렬 키 하나가 DB 인덱스와 맺는 계약

> 핵심 관전 포인트: **목록 조회에 들어오는 조건은 성격이 다른 세 종류다 — 정확히 일치시킬 조건(필터), 결과를 어떤 순서로 줄 것인가(정렬), 관련된 것을 찾아 달라(검색). 셋을 각각 다른 규약으로 받는다: 필터는 의미가 드러나는 명시적 파라미터(`status=SHIPPED&minAmount=10000`), 정렬은 전사적으로 통일된 하나의 형식(`sort=createdAt,desc`), 검색은 `q=` 하나. 그리고 셋 다 서버가 **화이트리스트**(서버가 미리 열거해 둔 허용 값 목록, 목록에 없으면 거절)로 값을 제한한다. 특히 허용 정렬 키를 제한해야 하는 이유는 세 겹이다. ① 성능 — `sort` 파라미터는 그대로 `ORDER BY`가 되고, 인덱스가 받치지 않는 정렬은 PostgreSQL 실행계획에 `Sort` 노드를 만들어 조건에 맞는 행을 전부 읽어 정렬하며, 정렬 대상이 `work_mem`을 넘으면 메모리가 아니라 **디스크 기반 외부 병합 정렬**로 떨어진다. 즉 정렬 키를 열어 두는 것은 클라이언트가 쿼리스트링 하나로 대형 정렬 작업을 DB에 시킬 수 있는 문을 여는 것이다. ② 보안·캡슐화 — `ORDER BY`의 컬럼명 자리는 **바인딩 파라미터가 원리적으로 불가능**해서(프리페어드 스테이트먼트는 문장의 구조를 먼저 확정하고 값만 나중에 채우는데, 컬럼명은 값이 아니라 구조다) 동적 정렬은 문자열 조립일 수밖에 없고, 그래서 화이트리스트가 인젝션과 내부 컬럼명 노출을 막는 유일한 방어가 된다. ③ 계약 — 한 번 허용한 정렬 키는 클라이언트가 의존하는 공개 계약이 되고, 그 키를 받치는 인덱스를 영원히 유지해야 한다. 즉 정렬 키 목록은 "API 스펙이자 인덱스 목록"이며, 둘을 함께 관리하는 시야가 이 문항의 핵심이다.**

---

## 0. 질문 + 의도

**질문**: "목록 조회 API의 필터·정렬·검색 파라미터는 어떻게 설계하나요? 허용 정렬 키를 제한해야 하는 이유는?"

**출제 의도**: 검색 조건은 요구사항이 끝없이 추가되는 영역이다. 파라미터 폭발을 계약으로 관리하고 허용 정렬 키를 인덱스와 연동해 제한하는지 — API 설계와 DB 설계를 함께 쥐는 시야를 본다. "파라미터를 어떻게 받느냐"는 표면이고, "그 파라미터가 DB에 어떤 쿼리를 만들 수 있는가"까지 내다보는지가 관전 포인트다.

## 1. 파라미터 설계 규약 — 필터 / 정렬 / 검색을 분리한다

### 1-1. 전제 — 목록 조회의 조건은 성격이 다른 세 종류다

`GET /orders` 하나에 붙는 쿼리 파라미터를 뭉뚱그려 "조회 조건"이라고 부르면 설계가 시작되지 않는다. 실제로는 성격이 완전히 다른 세 가지가 섞여 들어온다.

| 종류 | 클라이언트가 요구하는 것 | 서버가 만드는 SQL | 잘못 열면 생기는 일 |
|---|---|---|---|
| **필터** | "이 조건에 정확히 맞는 것만" | `WHERE` 절 | 조합이 폭발해 인덱스로 감당이 안 된다 |
| **정렬** | "이 순서로 줘" | `ORDER BY` 절 | 인덱스 없는 정렬이 DB를 태운다 (§2) |
| **검색** | "이거랑 관련된 것 찾아 줘" | `LIKE` / 전문 검색 / 검색 엔진 | 중간 일치가 전체 스캔이 된다 (§4) |

세 종류를 **각각 다른 이름 규칙으로 받는 것**이 설계의 첫 단추다. 셋을 하나의 범용 문법(`filter=status:SHIPPED,sort:createdAt desc`)으로 합치고 싶은 유혹이 늘 있지만, 합치는 순간 그 문법을 파싱하는 규칙 자체가 계약이 되어 문서화·검증·확장이 전부 어려워진다. 세 종류가 서로 다른 위험과 서로 다른 관리 방법을 갖기 때문에, 규약도 따로 세우는 것이 맞다.

### 1-2. 필터 — 의미가 드러나는 명시적 파라미터

```text
GET /orders?status=SHIPPED&minAmount=10000&orderedFrom=2026-08-01&orderedTo=2026-08-31
```

- **필드별 명시적 파라미터**가 기본이다. 파라미터 이름 자체가 문서 역할을 한다 — `minAmount=10000`은 설명 없이도 뜻이 통하지만 `filter=amount:gte:10000`은 `gte`가 무슨 뜻인지, 콜론이 몇 개까지 허용되는지를 별도 문서로 정의해야 한다.
- **범위 조건은 쌍으로**: `minAmount`/`maxAmount` 또는 `orderedFrom`/`orderedTo`처럼 이름에 경계의 방향을 담는다. 경계 포함 여부(이상/초과)는 반드시 문서에 명시한다 — 정하지 않으면 클라이언트마다 해석이 갈리고, 그 차이는 "합계가 1건씩 안 맞는다"는 형태로 뒤늦게 드러난다.
- **다중 값은 반복 파라미터 또는 콤마**: `status=SHIPPED&status=DELIVERED` 또는 `status=SHIPPED,DELIVERED`. 어느 쪽이든 좋지만 **팀에서 하나로 통일하고 전 API에 같은 규칙을 쓴다.** 목록 API 규약의 가치는 개별 설계의 우수함보다 전체 일관성 — 클라이언트 개발자가 "다음 API도 이렇게 생겼겠지"라고 예측할 수 있는 데서 나온다([01번 문서](01-restful-design-principles-resource-naming.md)의 '일관성 = 예측 가능성'이 여기에도 그대로 적용된다).
- **허용 값 검증**: enum 필터(`status`)는 허용 값 밖이면 400으로 명시적으로 거절한다. 오타(`status=SHIPED`)를 빈 결과로 조용히 응답하면 클라이언트 버그가 "데이터가 없네"로 위장되어, 진짜 원인을 찾는 데 며칠이 든다.

### 1-3. 정렬 — 하나의 형식 + 화이트리스트

```text
GET /orders?sort=createdAt,desc              ← Spring Data 관례
GET /orders?sort=-createdAt                  ← 부호 접두 관례 (JSON:API 등)
```

형식은 어느 쪽이든 좋다. 중요한 건 **전사적으로 하나**라는 것과, 정렬 가능한 필드를 **서버가 열거해 제한**한다는 것이다(제한해야 하는 이유는 §2 전체가 다룬다). 다중 정렬(`sort=status,asc&sort=createdAt,desc`)을 지원한다면 우선순위가 파라미터 등장 순서라는 것까지 계약에 적는다.

기본 정렬도 계약이다. `sort`를 생략했을 때의 순서(보통 `createdAt,desc`)를 문서에 명시하고 **암묵에 맡기지 않는다.** 여기에는 SQL의 성질이 하나 깔려 있다 — `ORDER BY` 없는 `SELECT`의 반환 순서는 **표준적으로 보장이 없다.** DB는 그때그때 편한 순서로 준다. 어떤 실행계획을 골랐는지, 인덱스를 탔는지, 병렬 워커가 몇 개였는지에 따라 결과 순서가 달라질 수 있다.

"어제까지 최신순이었는데 오늘부터 순서가 튀어요" 같은 제보는 대부분 기본 정렬을 명시하지 않은 목록에서 나온다. 우연히 원하는 순서로 나오던 것이 데이터 양이나 실행계획이 바뀌면서 깨진 것이다.

### 1-4. 검색 — `q` 하나로 받고, 어디를 어떻게 찾는지는 서버가 정한다

```text
GET /orders?q=김철수
```

전문 검색(여러 필드를 대상으로 한 부분 일치)은 필터와 성격이 다르다. **필터는 "정확한 조건"이고 검색은 "관련된 것 찾기"다.** 정확한 조건은 참·거짓이 명확하지만, 관련성은 서버가 판단하는 것이라 판단 방식이 계속 진화한다.

그래서 `q` 하나로 받고, 대상 필드와 매칭 방식(전방 일치인지, 형태소 분석인지, 랭킹을 매기는지)은 서버 구현으로 감춘다. 이렇게 감춰 두면 나중에 `LIKE` → PostgreSQL 전문 검색 → Elasticsearch로 구현을 갈아타도 **클라이언트는 아무것도 바꿀 필요가 없다.**

반대로 클라이언트가 `searchField=name&searchOp=contains`처럼 검색의 내부를 조립하게 열어 주면 두 가지를 동시에 잃는다. 구현을 바꿀 자유를 잃고(`searchOp` 목록이 계약이 되어 버린다), 성능의 통제권을 잃는다 — `contains`(중간 일치)는 뒤에서 볼 이유로 인덱스를 탈 수 없는 조건이라, §2의 정렬 키 문제와 똑같은 "파라미터 하나로 DB 부하를 만드는 문"이 된다.

### 1-5. 파라미터 폭발의 관리

검색 조건은 요구사항이 끝없이 추가되는 영역이다. "이 상태도 걸러 주세요", "이 기간도요", "담당자별로도요" — 목록 API는 서비스가 성장하는 만큼 파라미터가 늘어난다. 관리 원칙은 셋이다.

- **추가는 하위 호환, 의미 변경·제거는 파괴적 변경이다.** 새 필터를 하나 더 받는 것은 기존 클라이언트에 아무 영향이 없어 자유롭지만, 한 번 공개한 파라미터의 **의미**를 바꾸면(예: `minAmount`를 "상품 금액"에서 "결제 금액"으로) 기존 클라이언트가 조용히 잘못된 결과를 받는다. 스키마는 그대로인데 뜻만 바뀌는 이 변경은 타입 검증으로도 잡히지 않아 가장 위험한 파괴적 변경으로 분류된다([08번 문서](08-backward-compatible-api-changes.md)). 파라미터를 추가하기 전에 이름과 의미를 신중히 정해야 하는 이유가 여기 있다.
- 조건 조합이 수십 개로 늘고 GET 쿼리스트링이 길이 한계에 닿으면 `POST /orders/search` + 본문 조건 객체로 전환한다(→ §4 첫 꼬리질문).
- 다중 필터 × 자유 정렬 × 전문 검색이 **동시에** 요구되는 화면(관리자 통합 검색)은 RDB 인덱스 설계로 감당할 조합 수를 넘어선다. 검색 엔진 위임을 검토할 신호다(§3).

## 2. 허용 정렬 키를 제한해야 하는 이유 — 세 겹의 방어

### 2-1. 전제 — 인덱스는 "미리 정렬해 둔 목차"다

정렬 키와 인덱스의 관계를 이해하려면 인덱스가 어떻게 생겼는지부터 한 문단 필요하다.

RDB의 기본 인덱스인 **B-tree**는 **값을 크기 순으로 정렬해 계층적으로 담아 둔 자료구조**다. 뿌리에서 시작해 "찾는 값이 이보다 큰가 작은가"를 몇 번 판단하며 내려가면 원하는 지점에 닿고, 리프(가장 아래층)는 정렬된 순서대로 옆으로 이어져 있다.

**전화번호부를 떠올리면 된다.** 이름의 가나다순으로 정렬되어 있으니 "김"으로 시작하는 사람을 찾는 것은 쉽다 — 'ㄱ' 구간을 펼쳐 그 안에서만 보면 된다. 정렬되어 있다는 성질에서 두 가지가 동시에 따라 나온다.

**(1) 접두 탐색만 된다.** "김으로 시작하는 이름"은 범위로 좁힐 수 있지만, **"이름 중간에 '철'이 들어간 사람"은 전화번호부의 정렬이 아무 도움도 못 준다.** '철'이 들어간 이름은 ㄱ부터 ㅎ까지 아무 데나 흩어져 있으니 첫 장부터 끝까지 다 봐야 한다. 이것이 `LIKE '키워드%'`(전방 일치)는 인덱스를 타고 `LIKE '%키워드%'`(중간 일치)는 못 타는 이유다.

**(2) 정렬을 이미 해 둔 셈이다.** 인덱스는 만들어질 때 이미 정렬된 순서로 저장되므로, `ORDER BY`가 그 순서와 일치하면 **DB는 정렬 작업 자체를 하지 않고** 인덱스를 순서대로 훑기만 하면 된다. 전화번호부를 가나다순으로 출력하려면 그냥 앞에서부터 읽으면 되는 것과 같다.

이 두 성질이 아래 세 절의 근거가 된다.

### 2-2. 성능 — 정렬 파라미터는 DB 부하로 통하는 문이다

`sort` 파라미터는 그대로 `ORDER BY`가 된다. 그리고 2-1에서 본 대로, 그 정렬을 받쳐 주는 인덱스가 있느냐 없느냐에 따라 DB가 하는 일이 완전히 달라진다.

**인덱스가 받치는 정렬**은 인덱스를 순서대로 읽으면 끝이다. PostgreSQL 실행계획에는 `Index Scan`(또는 역방향인 `Index Scan Backward`)만 나오고 **`Sort` 노드가 아예 등장하지 않는다.** 정렬이라는 작업이 통째로 생략된 것이다.

**인덱스가 없는 컬럼 정렬**은 다르다. 실행계획에 `Sort` 노드가 붙고, DB는 `WHERE` 조건에 맞는 행을 **전부 읽어 올린 뒤** 정렬한다. 여기서 PostgreSQL의 중요한 갈림길이 하나 있다. 정렬 대상이 세션의 `work_mem`(정렬·해시 같은 연산 하나가 쓸 수 있는 메모리 상한, 기본값 4MB 수준) 안에 들어가면 메모리에서 퀵소트로 끝나지만, **넘어가면 임시 파일로 쏟아 내어 디스크에서 조각을 병합하는 외부 병합 정렬(external merge sort)로 떨어진다.** 메모리 정렬과 디스크 정렬은 비용의 차원이 다르다.

이건 추측이 아니라 관측할 수 있다. `EXPLAIN (ANALYZE, BUFFERS)`를 걸면 `Sort` 노드 아래에 정렬 방식이 그대로 찍힌다.

```text
[인덱스 없는 컬럼으로 정렬]  ORDER BY memo DESC
  Sort                                              ← 정렬 노드가 붙었다
    Sort Key: memo DESC
    Sort Method: external merge  Disk: 41008kB      ← work_mem 초과 → 디스크로 쏟아졌다
    └─ Seq Scan on orders                           ← 조건에 맞는 행을 전부 읽어 올린다
         Filter: (user_id = 42)

[인덱스가 받치는 정렬]  ORDER BY created_at DESC, id DESC
  Index Scan Backward using idx_orders_created_at_id
                                                    ↑ Sort 노드가 아예 없다.
                                                      이미 정렬된 순서로 앞에서부터 읽고 멈춘다
```

`Sort Method`에 찍히는 값이 판정 기준이다. `quicksort  Memory: 25kB`면 메모리 안에서 끝난 것이고, `external merge  Disk: 41008kB`면 디스크로 떨어진 것이다. 후자가 목록 API에서 반복 호출되고 있다면 그것만으로 DB CPU와 디스크 I/O가 함께 튄다.

여기서 자주 나오는 반론을 하나 정리해 두자. **"`LIMIT 20`이 붙어 있으니 20건만 처리하는 것 아닌가?"** 아니다. **상위 20건이 무엇인지 알려면 후보 전체를 봐야 한다.**

PostgreSQL은 `LIMIT`이 붙은 정렬에서는 **상위 N건만 들고 비교해 나가는 `top-N heapsort`** 방식을 고른다. 그래서 실행계획에는 디스크 대신 `Sort Method: top-N heapsort  Memory: 30kB`처럼 찍히기도 한다. 하지만 **정렬용 메모리를 아꼈을 뿐, 그 아래 `Seq Scan`이 조건에 맞는 행을 전부 읽어 하나씩 비교하는 비용은 그대로다.** 20건을 주려고 124만 행을 읽는 상황은 변하지 않는다.

그리고 페이지가 깊어질수록(`OFFSET 20000`이면 들고 있어야 할 N이 20,020이다) 유지 대상이 커져 결국 `work_mem`을 넘고 디스크 정렬로 내려간다. 정렬 대상 전체를 내보내는 CSV 익스포트 같은 경로에서는 처음부터 디스크 정렬이다.

정리하면 이렇다. **정렬 키를 제한하지 않은 목록 API는 클라이언트가 쿼리스트링 하나로 대형 정렬 작업을 DB에 시킬 수 있는 API다.** 크롤러나 잘못 짠 클라이언트가 `sort=memo`(인덱스 없는 컬럼)로 연타하면 그게 그대로 DB CPU 스파이크가 된다.

그러므로 허용 목록은 **"인덱스가 받치는 정렬 축"과 일치해야 한다.** 정렬 키 화이트리스트는 API 스펙이면서 동시에 인덱스 목록이다.

### 2-3. 보안·캡슐화 — 요청 값이 ORDER BY 구문에 닿게 하지 않는다

#### 왜 정렬만 유독 위험한가 — 바인딩 파라미터가 안 되기 때문이다

`WHERE user_id = ?`의 `?` 자리에는 요청 값을 안전하게 꽂을 수 있는데, `ORDER BY ?`는 왜 안 될까. 이게 이 절 전체의 전제이므로 정확히 짚고 가야 한다.

**프리페어드 스테이트먼트(prepared statement)** 는 SQL을 DB에 두 단계로 넘기는 방식이다. 먼저 **문장의 뼈대**를 보내면 DB가 그것을 구문 분석하고 실행 계획까지 세워 둔다. 그다음 값만 따로 보내면 DB가 준비된 계획에 값을 꽂아 실행한다.

핵심은 **구조가 값보다 먼저 확정된다**는 것이다. 어느 테이블의 어느 컬럼을 어떤 순서로 읽을지가 정해져야 실행 계획을 세울 수 있으니, 그 구조를 이루는 부분은 나중에 채울 수 없다.

```text
SELECT * FROM orders WHERE user_id = ?  ORDER BY created_at DESC
       └────────┬────────┘         ↑              └──────┬──────┘
        구조 — 먼저 확정          값 자리            구조 — 먼저 확정
        (테이블·컬럼명)         파라미터 가능       (컬럼명, ASC/DESC)
                                                       파라미터 불가

  값은 "무엇을 비교할지"가 이미 정해진 뒤 채워 넣는 재료이지만,
  컬럼명과 정렬 방향은 "무엇을 어떻게 할지"라는 문장의 뼈대 자체다.
```

그래서 **동적 정렬은 문자열 조립 말고 방법이 없다.** JPA Criteria나 QueryDSL을 쓰더라도 결국 "어느 필드로 정렬할지"를 코드가 선택하는 구조이지, 요청 문자열이 바인딩되는 것이 아니다.

그리고 문자열 조립이라는 뜻은, **요청 문자열이 SQL 문장의 일부가 될 수 있다**는 뜻이다. 그래서 화이트리스트가 유일한 방어가 된다. "값을 안전하게 이스케이프한다"는 접근은 여기서 통하지 않는다 — 애초에 값으로 취급되는 자리가 아니기 때문이다.

#### 열어 두면 생기는 세 가지

```java
// Before: 요청 파라미터를 ORDER BY 에 그대로 이어 붙인다
String sql = "SELECT * FROM orders WHERE user_id = ? ORDER BY " + sortParam;
// ① SQL 인젝션 — sortParam 이 값이 아니라 SQL 문장의 일부로 해석되므로,
//    "amount; DROP TABLE orders" 같은 문자열이 그대로 구문에 섞여 들어간다.
//    (요청 문자열이 값이 아니라 구문으로 해석되어 공격자가 원래 의도와
//     다른 쿼리를 실행시키는 것 — 이것이 SQL 인젝션이다)
// ② 캡슐화 붕괴 — 엔티티의 내부 컬럼명이 그대로 API 계약이 된다.
//    나중에 컬럼명을 바꾸면 클라이언트가 깨진다.
// ③ 성능 — 존재하지만 인덱스가 없는 컬럼이면 §2-2 의 디스크 정렬.
//    존재하지 않는 컬럼이면 SQL 오류 → 500.
```

Spring Data의 `Pageable`을 컨트롤러에서 그대로 받는 것도 정도만 다를 뿐 같은 문제다. `?sort=anyField,desc`로 들어온 문자열이 그대로 정렬에 반영되기 때문이다.

- 존재하지 않는 속성이면 `PropertyReferenceException`이 난다. Spring Data가 `Sort`에 담긴 이름을 엔티티 필드에서 찾지 못할 때 던지는 예외인데, 따로 처리해 두지 않으면 500으로 새어 나간다. 클라이언트의 오타가 서버 에러로 보고되는 셈이다.
- 존재하지만 인덱스가 없는 속성이면 2-2의 성능 문이 그대로 열린다.
- 그리고 무엇보다, **엔티티 필드명 전체가 사실상 공개 계약**이 된다. 문서에 적지 않았을 뿐 실제로 동작하니, 누군가는 반드시 그것을 발견해 쓰기 시작한다.

#### 매핑 한 겹으로 세 문제를 동시에 막는다

```java
// After: 허용 키를 enum 으로 열거하고, API 이름 → 내부 정렬을 매핑한다
public enum OrderSortKey {
    CREATED_AT("createdAt", Sort.by(DESC, "createdAt", "id")),
    AMOUNT("amount",        Sort.by(DESC, "totalAmount", "id"));
    // 각 항목은 그 정렬을 받쳐 주는 복합 인덱스가 존재할 때만 추가한다 (§2-2, §2-4)
    //
    // 끝에 붙은 "id" 는 tie-breaker(동점 처리 키) — 정렬 키 값이 같은 행들
    // 사이의 순서를 확정해 주는 보조 키다. 여기에 함께 매핑해 두는 이유는
    // 커서 페이지네이션 때문이다: 커서는 "마지막으로 본 행"을 값으로 지목하는데,
    // tie-breaker 가 없으면 같은 createdAt 을 가진 행들의 순서가 정해지지 않아
    // 데이터가 하나도 안 바뀌어도 페이지 경계에서 중복·누락이 난다.
    // 정렬 키와 tie-breaker 를 한 자리에서 함께 선언해 두면
    // "정렬 키를 추가할 때 커서 설계도 같이 한다"가 코드에 고정된다.
    // → 04-pagination-offset-vs-cursor-api-contract.md §1-5

    private final String apiName;     // 외부 계약: "createdAt"
    private final Sort sort;          // 내부 구현: 실제 정렬 (컬럼명은 비공개)

    public static OrderSortKey from(String param) {
        return Arrays.stream(values())
                .filter(k -> k.apiName.equals(param))
                .findFirst()
                .orElseThrow(() -> new InvalidSortKeyException(param));
                // → @ControllerAdvice 에서 400 + "허용 정렬 키: createdAt, amount"
    }
}
```

이 매핑 한 겹이 앞의 세 문제를 한 번에 막는다.

- **인젝션 차단** — 요청 문자열은 `equals` 비교에만 쓰이고, 실제 SQL에 들어가는 것은 우리가 코드에 적어 둔 컬럼명뿐이다. 요청 문자열이 구문에 닿을 경로가 없다.
- **캡슐화** — 외부 이름(`createdAt`)과 내부 컬럼(`created_at`, `total_amount`)이 분리된다. 나중에 컬럼명을 바꿔도 매핑만 고치면 API는 그대로다.
- **성능 문 봉쇄** — 목록에 없는 키는 400으로 거절되므로, 인덱스 없는 컬럼 정렬이 애초에 도달할 수 없다.

허용 밖 키를 **조용히 기본 정렬로 폴백하지 않고 400으로 거절**하는 것도 중요하다. 폴백은 클라이언트의 오타를 "정렬이 안 먹네?"라는 미스터리로 바꿔 놓는다.

### 2-4. 계약 — 한 번 허용한 정렬 키는 인덱스 유지 의무가 된다

허용 목록에 키를 하나 추가하는 순간 클라이언트들이 그것에 의존하기 시작한다. 그리고 하위 호환 원칙상 이미 공개한 기능의 제거는 파괴적 변경이다([08번 문서](08-backward-compatible-api-changes.md)).

그런데 정렬 키의 경우, 제거하지 못하는 것이 API 스펙 한 줄만이 아니다. **그 키를 받치는 인덱스도 함께 영구 유지 대상이 된다.** 인덱스는 공짜가 아니다 — 해당 테이블에 `INSERT`/`UPDATE`가 일어날 때마다 인덱스도 함께 갱신해야 하므로 쓰기가 느려지고, 저장 공간도 따로 먹는다.

즉 **정렬 키를 하나 여는 것은 "인덱스 하나를 평생 운영한다"는 결정이다.**

"일단 다 열어 두고 필요하면 막자"가 안 되는 이유가 여기 있다. 방향이 비대칭이기 때문이다.

```text
좁게 시작 ──────── 넓히기 ────────→  넓게 열려 있음
             (하위 호환 변경, 언제든 가능)

좁게 시작 ←──────── 좁히기 ────────  넓게 열려 있음
             (파괴적 변경, 유예 기간·공지·측정이 필요하다)
```

**여는 건 한 순간이고 막는 건 파괴적 변경이다.** 그래서 좁게 시작해서 요구가 확인될 때 넓히는 것이 유일하게 되돌릴 수 있는 방향이다.

(가산점 포인트) **커서 페이지네이션과의 연동.** 커서 기반 목록에서는 정렬 축 하나하나가 ① 커서에 담을 값 ② tie-breaker를 포함한 복합 인덱스 ③ 토큰 스키마를 각각 요구한다([04번 문서](04-pagination-offset-vs-cursor-api-contract.md)). 정렬 축이 다섯 개면 복합 인덱스도 다섯 벌이라는 뜻이다. 그래서 커서 기반 목록에서 정렬 키 화이트리스트는 선택이 아니라 **구조적 전제**다. 위 코드처럼 정렬 키 enum에 tie-breaker까지 함께 매핑해 두면 "정렬 키 추가 = 커서 설계 + 인덱스 추가"라는 체크리스트가 코드 자체에 박힌다.

## 3. 실무 사례 — "관리자 그리드의 모든 컬럼 정렬" 요구

이 요구는 거의 언제나 같은 경로로 도착한다. 시간 순으로 펼치면 이렇다.

```text
1주차  │ 관리자 화면에 데이터 그리드 라이브러리를 붙인다
       │   → 라이브러리가 모든 컬럼 헤더에 클릭 정렬 UI 를 자동으로 달아 준다
       ↓
2주차  │ 프론트: "백엔드가 Pageable 을 그대로 받고 있어서 이미 다 되는데요"
       │   → 실제로 동작한다(§2-3). 스펙 논의 없이 그대로 배포된다
       ↓
3~6주차│ 운영팀이 실사용 — 조건 필터 + memo 컬럼 정렬 + 20 페이지 넘김
       │   → 아무도 이걸 "새 기능"이라고 인지하지 못한 상태
       ↓
7주차  │ DB CPU 가 60% → 95% 로 스파이크. 특정 시간대에 반복된다
       ↓
추적   │ pg_stat_statements 상위 쿼리 = ORDER BY memo ... LIMIT 20 OFFSET 400
       │ EXPLAIN (ANALYZE, BUFFERS) 결과
       │   Sort  (Sort Method: top-N heapsort  Memory: 45kB)
       │     └─ Seq Scan on orders  (actual rows=1,240,000)
       │   = 20건을 주려고 매 호출마다 124만 행을 읽어 비교하고 있었다.
       │     깊은 페이지로 넘어가면 여기에 external merge 디스크 정렬까지 얹힌다
```

이 타임라인의 무서운 점은 **어느 단계에서도 "잘못된 코드"가 작성되지 않았다**는 것이다. 그리드 라이브러리는 정상이고, 프론트의 요청도 합리적이며, 백엔드는 `Pageable`을 받았을 뿐이다. 문제는 **정렬 키가 계약으로 관리되지 않아, 기능이 추가되었다는 사실 자체를 아무도 몰랐다**는 데 있다.

대응은 세 갈래로 정리된다.

- **즉시** — 정렬 키 화이트리스트(§2-3)를 걸어 문을 닫는다. 그리고 그리드 쪽에는 "정렬 가능 컬럼" 목록을 API 스펙으로 내려 줘서, 허용된 컬럼에만 정렬 아이콘이 켜지게 한다. 계약을 UI까지 전파하는 것이다 — 그래야 사용자가 "왜 이 컬럼만 정렬이 안 되지?"라고 400 에러로 배우지 않는다.
- **협상** — "모든 컬럼 정렬"이 진짜 요구인지 확인한다. 접근 로그를 보면 대부분 실제로 쓰는 정렬 축은 두세 개다. 쓰는 축만 인덱스와 함께 허용 목록에 추가한다. 요구사항의 크기를 확인하지 않고 기술로만 받으면 인덱스가 컬럼 수만큼 늘어나고, 그만큼 쓰기가 느려진다(§2-4).
- **구조 전환** — 다중 필터 × 임의 정렬 × 전문 검색이 전부 진짜 요구라면 RDB 인덱스로는 조합 폭발을 감당할 수 없다. 검색 엔진(Elasticsearch)에 색인해 그 화면만 위임한다. 대가는 색인 동기화 지연(RDB에 쓴 것이 검색 엔진에 반영되기까지의 시차)과 운영 컴포넌트 추가이므로, 화이트리스트로 버틸 수 있는 동안은 꺼내지 않는다.

이 사례가 출제 의도의 "API 설계와 DB 설계를 함께 쥐는 시야"다. 정렬 파라미터 설계는 프론트 편의 문제처럼 보이지만, 실체는 **DB에 어떤 쿼리를 허용할 것인가의 결정**이다.

## 4. 꼬리질문 대비 포인트

### "필터 조건이 계속 늘어 쿼리스트링이 감당이 안 되면 어떻게 하나요?"

`POST /orders/search`(또는 `/orders:search`)로 전환해 조건 객체를 본문에 담는다. URL 길이 한계와 중첩 조건(AND/OR 조합) 표현 문제를 한 번에 해결한다.

대가는 두 가지다. POST라서 **HTTP 캐시를 잃고**(GET이 아니면 중간 캐시가 응답을 재사용하지 않는다), "조회인데 POST"라는 시맨틱 절충이 생긴다. 이 절충을 문서에 명시해 두어야 나중에 "왜 조회가 POST죠?"라는 리뷰 지적이 반복되지 않는다.

이때도 **조건 객체의 필드와 연산자는 서버가 정의한 스키마로 제한한다.** 본문으로 옮겼다고 해서 "임의 필드 + 임의 연산자"를 열면 쿼리스트링 시절보다 더 넓은 문이 된다 — 위치가 바뀌었을 뿐 §2의 세 가지 위험은 그대로다.

### "sort 파라미터 형식은 어떤 것을 쓰나요? 기준이 있나요?"

`sort=createdAt,desc`(Spring Data 관례)와 `sort=-createdAt`(JSON:API 등 부호 접두) 모두 실무에서 통용되고 우열은 크지 않다.

진짜 기준은 셋이다. ① **전사 일관성** — 서비스마다 형식이 다르면 클라이언트가 API마다 문서를 다시 읽어야 한다 ② **다중 정렬의 우선순위 규칙 명시** ③ **기본 정렬의 문서화**(§1-3).

"형식 선택보다 형식의 통일과 계약 명시가 본질"이라고 답하면 [01번 문서](01-restful-design-principles-resource-naming.md)의 '일관성이 예측 가능성을 만든다'는 관점과 정확히 정렬된다.

### "허용 목록 밖 정렬 키가 오면 400과 기본 정렬 폴백 중 무엇이 맞나요?"

400 거절이 맞다. 폴백은 당장의 장애는 없어 보이지만 클라이언트의 오타나 잘못된 연동을 "정렬이 이상하다"는 형태로 숨긴다. **빨리 실패(fail-fast)해야 개발 단계에서 잡힌다.** 에러 응답 본문에 허용 키 목록을 담아 주면 문서를 다시 찾는 왕복도 줄어든다.

단, 조건이 하나 붙는다. **이미 폴백으로 동작 중인 운영 API를 400으로 바꾸는 것은 그 자체가 파괴적 변경이다.** 지금까지 조용히 무시되던 요청이 갑자기 실패하기 시작하기 때문이다. 유예 기간을 둔다 — 먼저 로그로 위반 클라이언트를 파악하고, 공지한 뒤, 전환한다.

### "필터 조합마다 인덱스를 다 만들 수는 없는데, 필터 파라미터도 제한해야 하나요?" (시니어 변별 포인트)

원칙은 같지만 **강도를 다르게 적용한다.** 그 이유를 말하려면 용어 하나가 필요하다.

**선택도(selectivity)** 는 조건 하나가 전체 행 중 몇 퍼센트로 좁혀 주는가를 뜻한다. 100만 건 중 3건이 남는 조건은 선택도가 높고(0.0003%), 90만 건이 남는 조건은 선택도가 낮다(90%). **선택도가 낮은 조건은 인덱스를 타도 이득이 없다.** 인덱스로 90만 건의 위치를 알아낸 뒤 그 90만 건을 다시 테이블에서 읽어 와야 하는데, 그럴 바에는 처음부터 테이블을 순차로 훑는 편이 빠르기 때문이다. PostgreSQL의 플래너가 선택도가 낮다고 판단하면 인덱스가 있어도 `Seq Scan`을 고르는 이유다.

정렬과 필터의 차이가 여기서 나온다. **정렬은 인덱스가 없으면 예외 없이 비용이 급격히 나빠지지만**(조건에 맞는 행 전체를 읽어 정렬해야 하고, 크면 디스크로 떨어진다 — §2-2), **필터는 선택도 높은 다른 조건과 결합하면 인덱스 없이도 견딜 수 있다.** `orderedFrom/To`로 이미 3천 건까지 좁혀 놓았다면, 그 안에서 `memo LIKE`를 걸어도 3천 건만 훑으면 된다.

실무 기준은 셋이다.

- **자주 쓰이는 필터 조합**을 접근 로그로 확인하고, 그 조합에 복합 인덱스를 설계한다.
- **선택도가 낮은 필터의 단독 호출**(예: 전체의 90%가 `SHIPPED`인데 `status`만 걸고 조회)이 문제라면 "단독 사용 불가, 기간 필터 필수" 같은 **조합 제약을 계약에 명시**한다. 즉 필터도 화이트리스트를 걸되, 대상이 "필드"가 아니라 "조합"이 된다.
- **조합이 통제 불능으로 늘면** 검색 엔진 위임(§3)으로 넘어간다.

"필터 파라미터 목록 = 지원을 약속한 조회 패턴"이라는 계약 관점은 정렬과 동일하다. **받을 수 있는 것과 빠르게 처리할 수 있는 것을 구분해, 후자만 약속하는 것이 설계다.**

### "검색(q)이 LIKE '%키워드%'로 구현돼 있으면 어떤 문제가 있나요?"

먼저 왜 느린지부터. 2-1에서 본 대로 **B-tree 인덱스는 값을 정렬해 담아 두므로 "이렇게 시작하는 것"은 범위로 좁힐 수 있지만 "중간에 이게 들어간 것"은 어디에 있을지 알 수 없다.** 그래서 `LIKE '%키워드%'`는 일반 B-tree 인덱스를 탈 수 없고, 조건에 맞는 후보 전체를 읽어 한 건씩 문자열을 대조하게 된다. 데이터가 늘면 검색 한 번이 목록 테이블 전체를 읽는 쿼리가 된다.

대응은 단계적이다.

**① 전방 일치로 요구를 좁힐 수 있는지 확인한다.** `키워드%`는 B-tree 범위 탐색이 되므로 인덱스가 그대로 듣는다. "이름 검색"이 실제로는 "이름 앞부분으로 찾기"면 충분한 경우가 의외로 많다. 가장 싼 해법이므로 먼저 물어본다.

**② 중간 일치 자체를 인덱스로 살리려면 `pg_trgm`이 있다.** PostgreSQL의 확장 모듈로, 문자열을 3글자씩 겹쳐 자른 조각(**트라이그램**)으로 쪼개 GIN 인덱스에 담아 둔다. 검색어도 같은 방식으로 쪼갠 뒤 "이 조각들을 전부 가진 행"으로 후보를 좁히므로, `LIKE '%키워드%'`도 인덱스의 도움을 받을 수 있다. 그래서 "중간 일치는 무조건 전체 스캔"이라는 단정은 정확하지 않다.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_orders_memo_trgm ON orders USING gin (memo gin_trgm_ops);
-- 이후 memo LIKE '%키워드%' 가 이 인덱스를 후보 축소에 쓸 수 있다
```

대가도 분명하다. 트라이그램 인덱스는 원문보다 커지기 쉬워 저장 공간과 쓰기 비용이 크고, **검색어가 3글자 미만이면 트라이그램을 만들 수 없어 인덱스가 도움이 안 된다.**

**③ 본격적인 전문 검색이면 `tsvector` + GIN이다.** 두 가지가 각각 무엇인지 짚고 가자.

- **`tsvector`** 는 **문서를 검색 가능한 단어 목록으로 미리 쪼개 정규화해 담아 두는 PostgreSQL 타입**이다. `to_tsvector('english', 'The cats are running')`을 돌리면 `'cat':2 'run':4` 같은 형태가 나온다 — 관사 같은 불용어는 버리고, 어미를 떼어 어간으로 통일하고, 각 단어의 위치까지 기록한다. 검색할 때마다 문자열을 훑는 대신 **미리 쪼개 둔 단어 목록끼리 비교**하는 것이 전문 검색의 원리다.
- **GIN(Generalized Inverted Index, 일반화 역색인)** 은 그 `tsvector`에 맞는 인덱스다. B-tree는 "한 행에 키 하나"를 전제하는데, `tsvector`는 **한 행이 수십 개의 단어를 갖는 다대다 구조**라 그 전제가 성립하지 않는다. GIN은 방향을 뒤집어 **"단어 → 그 단어를 가진 행 목록"** 을 저장한다. 그래서 역(inverted)색인이라 부른다. 책 뒤의 찾아보기와 정확히 같은 구조다 — 단어를 찾으면 그 단어가 나온 쪽 번호들이 적혀 있다.

```sql
-- 생성 컬럼으로 tsvector 를 유지하고 GIN 인덱스를 건다
ALTER TABLE orders ADD COLUMN search_doc tsvector
    GENERATED ALWAYS AS (to_tsvector('simple', coalesce(customer_name,'') || ' ' || coalesce(memo,''))) STORED;
CREATE INDEX idx_orders_search ON orders USING gin (search_doc);

-- 조회
SELECT * FROM orders WHERE search_doc @@ plainto_tsquery('simple', '김철수');
```

한국어에는 주의점이 하나 있다. PostgreSQL 기본 파서는 한국어 형태소 분석을 하지 못해 공백 단위 분리에 가깝게 동작한다. "김철수의"를 "김철수"로 검색하면 안 걸릴 수 있다는 뜻이다. 본격적인 한국어 검색이 요구되면 별도 확장을 붙이거나 ④로 넘어가야 한다.

**④ 검색 요구가 본격적이면(형태소 분석, 랭킹, 다중 필드, 오타 교정) 검색 엔진에 위임한다.**

그리고 이 전환 전체가 가능한 이유가 §1-4의 설계에 있다. **`q` 파라미터의 계약을 "어떻게 찾는지는 서버 구현"으로 감춰 뒀다면 ①→②→③→④를 클라이언트 변경 없이 갈아탈 수 있다.** 반대로 `searchOp=contains`를 계약으로 노출했다면 구현을 바꿀 때마다 클라이언트를 함께 옮겨야 한다. 파라미터 설계가 구현 진화의 자유를 지켜 주는 사례다.

## 한 줄 요약

필터는 명시적 파라미터, 정렬은 통일된 형식, 검색은 `q` 하나로 분리하되 셋 다 서버가 허용 값을 화이트리스트로 제한한다 — 특히 정렬 키는 ① 인덱스 없는 컬럼 정렬이 실행계획에 `Sort` 노드를 만들고 `work_mem`을 넘으면 디스크 외부 병합 정렬로 떨어지는 DB 부하의 문이자, ② `ORDER BY`의 컬럼명은 바인딩 파라미터가 원리적으로 불가능해 문자열 조립일 수밖에 없다는 점에서 인젝션·내부 컬럼명 노출의 통로이자, ③ 한 번 열면 그 인덱스를 평생 유지해야 하는 공개 계약이므로, **허용 정렬 키 목록 = 인덱스 목록**으로 관리하며 좁게 시작해 요구가 확인될 때만 넓히는 것이 API와 DB를 함께 쥐는 설계다.
