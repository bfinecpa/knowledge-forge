# API 게이트웨이 vs 서비스의 책임 경계 — "도메인을 알아야 하는가"가 자르는 선

> 핵심 관전 포인트: **경계 기준은 한 문장이다 — "도메인 지식 없이, 모든
> 요청에 균일하게 적용되는가?" 그렇다면 게이트웨이(TLS 종료, 라우팅,
> 인증 토큰 검증, 전역 rate limit, 공통 로깅·트레이싱, CORS), 도메인
> 지식이 필요하면 서비스(리소스 소유권 기반 인가, 도메인 검증, 비즈니스
> 규칙). 대표 분할이 인증/인가다 — 게이트웨이는 "누구인가"(토큰 서명
> 검증)까지, "이 리소스에 이걸 해도 되는가"는 서비스가 한다. 그리고 이
> 경계를 지키지 못해 도메인 로직이 게이트웨이에 쌓이면, 모든 팀의 변경이
> 게이트웨이 배포에 줄을 서는 새로운 모놀리스가 된다 — MSA로 풀었던
> 결합을 게이트웨이에서 재조립하는 함정이다.**

---

## 0. 질문 + 의도

**질문**: "API 게이트웨이에서 처리할 것과 각 서비스에서 처리할 것의
경계를 어떻게 나누나요?"

**출제 의도**: 공통 관심사(인증, rate limit)의 위치 결정은 "게이트웨이가
비대해지면 그것이 새로운 모놀리스"라는 함정과의 균형이다. 시스템 전체의
책임 배치를 사고하는 아키텍처 감각을 잰다 — 기능 나열이 아니라, 배치
기준과 그 기준이 무너질 때의 조직적 비용까지 말할 수 있는지 본다.

## 1. 게이트웨이의 존재 이유 — 공통 관심사의 단일 시공 지점

게이트웨이가 없으면 N개 서비스가 각자 TLS, 인증, rate limit, CORS,
접근 로그를 구현한다 — N번 중복 구현되고, N개 중 하나는 반드시 빠뜨리며
(보안 구멍), 정책 변경 시 N번 배포해야 한다. 게이트웨이는 이 **횡단
관심사를 트래픽이 반드시 지나는 단일 지점에서 한 번만 시공**하려는
장치다.

비유하면 건물의 **정문 보안 게이트**다 — 출입증 검사(인증), 출입 기록
(로깅), 혼잡 시 입장 제한(rate limit)은 정문에서 하지만, "이 방문자가
3층 회의실을 예약했는지"(도메인 인가)는 정문이 알 수 없고 알아서도
안 된다. 그건 3층 부서(서비스)의 일이다.

전형적인 게이트웨이 책임: TLS 종료, 라우팅(경로 → 서비스 매핑), 인증
토큰 검증, 전역/클라이언트별 rate limit, CORS, 공통 요청 로깅과 trace
id 발급, 요청 크기 제한, IP 차단 같은 경계 보안.

## 2. 경계 기준 — 세 가지 질문으로 자른다

어떤 처리를 어디에 둘지 애매할 때 이 순서로 묻는다:

1. **도메인 지식이 필요한가?** 필요하면 무조건 서비스. 게이트웨이가
   "주문", "쿠폰"의 의미를 알기 시작하는 순간 경계가 무너진다.
2. **모든(대부분의) 요청에 균일하게 적용되는가?** 균일하면 게이트웨이
   후보. 특정 서비스에만 필요한 처리를 게이트웨이에 두면, 그 서비스의
   변경이 게이트웨이 배포를 요구하게 된다.
3. **바뀌는 주기와 주체가 누구인가?** 서비스 팀의 기능 변경 때마다 함께
   바뀌어야 하는 로직이면 서비스에 — 변경의 주인과 코드의 위치를
   일치시켜야 배포가 서로를 기다리지 않는다.

### 대표 사례: 인증(Authentication)과 인가(Authorization)의 분할

- **인증 = "누구인가"** — JWT 서명 검증, 만료 확인, 토큰에서 사용자
  ID/권한 클레임 추출. 도메인 지식이 필요 없고 모든 요청에 균일하다
  → **게이트웨이**. 검증 결과(사용자 ID 등)는 내부 헤더로 서비스에
  전달한다.
- **인가 = "이 리소스에 이걸 해도 되는가"** — "이 주문은 이 사용자의
  것인가", "이 문서의 편집 권한이 있는가"는 주문/문서 데이터를 아는
  쪽만 판단할 수 있다 → **서비스**.

```java
// Before: 게이트웨이에 도메인 인가를 넣은 경우 (경계 붕괴의 시작)
// gateway의 라우트 필터에서 —
if (path.matches("/orders/\\{id}")) {
    var order = orderServiceClient.getOrder(orderId);   // 문제 1: 게이트웨이가
    if (!order.ownerId().equals(userId)) {              //   주문 도메인을 조회·해석한다
        return forbidden();                             // 문제 2: 인가 규칙이 바뀌면
    }                                                   //   (예: '가족 계정도 조회 가능')
}                                                       //   주문팀이 게이트웨이 배포를 기다린다
                                                        // 문제 3: 주문 조회가 2번 일어난다

// After: 게이트웨이는 신원 검증까지만, 인가는 서비스가
// [게이트웨이] JWT 검증 → 통과 시 내부 헤더로 신원 전달
//   X-User-Id: 42  (+ 위변조 방지 서명, 아래 꼬리질문 참고)
// [주문 서비스] 도메인 데이터로 인가 판단
@GetMapping("/orders/{id}")
Order getOrder(@PathVariable long id,
               @RequestHeader("X-User-Id") long userId) {
    var order = orderRepository.findById(id);
    accessPolicy.checkReadable(order, userId);   // 소유권·가족계정 규칙은
    return order;                                // 주문팀 코드에, 주문팀 배포 주기로
}
```

### 회색 지대의 판단 예시

- **rate limit**: "IP당/클라이언트당 전역 한도"는 게이트웨이. "포인트
  전환은 사용자당 하루 3회" 같은 건 한도가 아니라 **비즈니스 규칙**이라
  서비스. 같은 이름이라도 도메인 의미가 실리는 순간 서비스로 넘어간다.
- **응답 변환/조합**: 여러 서비스 응답을 화면용으로 조합하는 것은
  도메인+화면 지식이 필요하다 → 게이트웨이가 아니라 **별도의 BFF**로
  분리한다. 게이트웨이의 변환은 헤더 추가 같은 무해한 수준까지만.
- **요청 검증**: "JSON 문법이 맞는가, 크기 제한"은 게이트웨이 가능.
  "배송지가 유효한 주소인가"는 서비스.
- **캐싱**: 정적/공통 응답 캐시는 게이트웨이(또는 그 앞 CDN) 가능하나,
  무효화 규칙이 도메인 이벤트에 묶이는 캐시는 서비스가 소유해야 한다.

## 3. 함정 — 게이트웨이가 새로운 모놀리스가 되는 경로

경계가 무너지는 것은 한 번의 큰 결정이 아니라 **작은 편의의 누적**이다.
"이번 한 번만 게이트웨이에서 이 필드 바꿔서 내려주자"(레거시 클라이언트
호환), "이 경로만 특별히 분기하자"(A/B 라우팅에 도메인 조건), "서비스
고치기 전에 게이트웨이에서 임시로 막자"(핫픽스) — 각각은 합리적이지만
쌓이면:

- **배포 병목**: 여러 팀의 변경이 게이트웨이라는 단일 배포 파이프라인에
  줄을 선다. 서비스는 하루 10번 배포하는데 게이트웨이는 조심스러워
  주 1회가 되고, 모두가 그 주기에 묶인다 — MSA로 분리했던 조직 결합이
  게이트웨이에서 부활한다.
- **폭발 반경 확대**: 게이트웨이는 전 트래픽의 단일 경로다. 특정 팀의
  로직 버그가 전 서비스 장애가 된다.
- **소유권 실종**: 게이트웨이 안의 도메인 로직은 게이트웨이 팀도 도메인
  팀도 자기 것이라 여기지 않아, 아무도 테스트하지 않는 코드가 된다.

방지 장치 (가산점 포인트):

- **"게이트웨이 변경은 설정이어야지 코드가 아니어야 한다"는 원칙** —
  라우트 추가, 한도 조정은 선언적 설정으로 하고, 도메인 조건문이 담긴
  커스텀 필터가 PR에 등장하면 경계 위반 신호로 리뷰에서 잡는다.
- **화면/클라이언트 맞춤 요구는 BFF로 배출** — 조합·변환 요구를
  게이트웨이가 아니라 클라이언트 팀이 소유하는 BFF 계층으로 보낸다.
  게이트웨이는 얇게, 맞춤은 BFF에, 도메인은 서비스에 — 세 층의 역할을
  구분하면 게이트웨이 비대화 압력이 크게 준다.
- **게이트웨이의 SLO와 변경 통계를 관리** — 게이트웨이 배포 빈도가
  올라가고 배포 사유가 특정 도메인 요구로 채워지면 경계가 새고 있다는
  정량 신호다.

## 4. 꼬리질문 대비 포인트

### "게이트웨이가 인증했다는 걸 서비스는 어떻게 신뢰하나요? 내부에서 X-User-Id 헤더를 위조하면요?"

"내부망이니까 믿는다"는 답은 감점이다 — 내부의 어떤 프로세스든 헤더를
꾸며 호출할 수 있기 때문이다. 실무 답: (1) 게이트웨이가 검증 결과를
**서명된 내부 토큰**(짧은 만료의 내부용 JWT 등)으로 재발급해 전달하고
서비스는 서명을 확인한다, (2) 네트워크 수준에서 서비스가 게이트웨이
외의 직접 호출을 받지 않도록 격리하고 서비스 간 mTLS로 호출자 신원을
보장한다, (3) 원본 토큰을 그대로 전파해 필요한 서비스가 재검증한다.
"경계 안이라고 무조건 신뢰하지 않는다(zero trust 방향)"는 태도를
보여주는 것이 포인트다.

### "그럼 인가를 위한 공통 권한 체크가 서비스마다 중복 구현되지 않나요?"

역할(role) 수준의 거친 체크("ADMIN만 접근")는 토큰 클레임 기반으로
게이트웨이나 공통 라이브러리에서 균일 처리할 수 있다. 중복이 문제되는
것은 리소스 소유권 수준인데, 이것을 게이트웨이로 올리는 대신 (1) 공통
인가 라이브러리/미들웨어로 패턴을 표준화하거나, (2) 정책 결정을 별도
컴포넌트(정책 엔진)로 빼고 서비스는 질의만 하는 구조(PDP/PEP 분리)로
푼다. 핵심은 "중복 제거의 방향이 게이트웨이 집중이 아니라 라이브러리화
또는 전담 컴포넌트화"라는 것 — 실행 위치는 여전히 도메인 문맥이 있는
서비스 쪽이다.

### "BFF와 API 게이트웨이는 뭐가 다른가요?"

역할과 소유권이 다르다. **게이트웨이는 전 트래픽 공통의 인프라 경계**
(인증, rate limit, 라우팅)로 플랫폼 팀이 소유하고, **BFF는 특정
클라이언트(모바일/웹)를 위한 응답 조합·변환 계층**으로 그 클라이언트
팀이 소유한다. 게이트웨이는 도메인을 모르는 채 얇게, BFF는 화면 요구에
맞춰 자주 바뀌게 — 변경 주기가 다른 두 책임을 한 컴포넌트에 합치면
게이트웨이 모놀리스화가 시작되므로 분리한다. "게이트웨이 → BFF →
서비스"로 층을 나눠 답하면 구조가 선명해진다.

### "게이트웨이 자체가 단일 장애점(SPOF)이자 병목이 되지 않나요?"

된다 — 그래서 게이트웨이는 (1) 무상태(stateless)로 설계해 수평 확장
가능하게 하고(상태가 필요한 rate limit 카운터는 외부 저장소로), (2)
다중 인스턴스 + 헬스체크 기반 로드밸런싱으로 가용성을 확보하며, (3)
로직을 얇게 유지해 처리 지연과 장애 확률 자체를 낮춘다. "게이트웨이를
얇게 유지하는 것은 아키텍처 순수성 문제이기 전에 가용성 문제"라고
연결하면 좋다 — 2장의 경계 기준과 같은 결론에 도달하는 다른 경로다.

### "지금 모놀리스에서 MSA로 전환 중이라면, 게이트웨이 도입 시점과 초기 책임 범위를 어떻게 잡겠어요?" (시니어 변별 포인트)

처음부터 만능 게이트웨이를 만들지 않는다. 전환 초기의 게이트웨이는
**라우팅 + 인증 + 공통 로깅**의 최소 책임으로 시작한다 — 이 셋은
모놀리스에서 서비스를 떼어낼 때마다 즉시 필요해지는 것들이고, 도메인
지식이 필요 없어 안전하다. rate limit·IP 차단 같은 경계 보안은 트래픽
특성이 파악되는 대로 추가한다. 반대로 응답 변환·조합 요구는 처음부터
BFF로 격리해 게이트웨이에 들어올 길을 막는다. 그리고 "게이트웨이에
넣자"는 제안이 나올 때마다 2장의 세 질문(도메인 지식? 균일 적용? 변경
주체?)을 리뷰 기준으로 명문화해 두는 것 — 경계는 아키텍처 다이어그램이
아니라 **반복되는 개별 결정의 기준을 팀이 공유하는 것**으로 지켜진다는
답이 시니어의 답이다.

## 한 줄 요약

게이트웨이와 서비스의 경계는 **"도메인 지식 없이 모든 요청에 균일하게
적용되는가"**로 자른다 — 인증·라우팅·전역 rate limit·공통 로깅은
게이트웨이, 리소스 소유권 인가·도메인 검증·비즈니스 규칙은 서비스,
화면 맞춤 조합은 BFF로 — 이 기준이 무너져 도메인 로직이 게이트웨이에
쌓이면 모든 팀의 배포가 한 지점에 줄을 서는 새로운 모놀리스가 되므로,
경계 기준을 팀의 리뷰 기준으로 명문화해 지키는 것까지가 설계다.
