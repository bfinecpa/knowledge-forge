# API 게이트웨이 vs 서비스의 책임 경계 — "도메인을 알아야 하는가"가 자르는 선

> 핵심 관전 포인트: **경계 기준은 한 문장이다 — "도메인 지식 없이, 모든 요청에 균일하게 적용되는가?" 그렇다면 게이트웨이(TLS 종료, 라우팅, 인증 토큰 검증, 전역 rate limit, 공통 로깅·트레이싱, CORS), 도메인 지식이 필요하면 서비스(리소스 소유권 기반 인가, 도메인 검증, 비즈니스 규칙). 대표 분할이 인증/인가다 — 게이트웨이는 "누구인가"(토큰 서명 검증)까지, "이 리소스에 이걸 해도 되는가"는 서비스가 한다. 그리고 이 경계를 지키지 못해 도메인 로직이 게이트웨이에 쌓이면, 모든 팀의 변경이 게이트웨이 배포에 줄을 서는 새로운 모놀리스가 된다 — MSA로 풀었던 결합을 게이트웨이에서 재조립하는 함정이다. 경계가 무너지는 것은 한 번의 큰 결정이 아니라 **각각은 합리적이었던 작은 편의의 누적**이라, 방어책도 "다이어그램을 잘 그리기"가 아니라 "게이트웨이에 넣자는 제안이 나올 때마다 적용하는 리뷰 기준을 팀이 공유하기"가 된다. 층은 셋으로 본다 — 게이트웨이는 도메인을 모른 채 얇게, BFF는 화면 요구에 맞춰 자주 바뀌게, 도메인은 서비스에.**

---

## 0. 질문 + 의도

**질문**: "API 게이트웨이에서 처리할 것과 각 서비스에서 처리할 것의 경계를 어떻게 나누나요?"

**출제 의도**: 공통 관심사(인증, rate limit)의 위치 결정은 "게이트웨이가 비대해지면 그것이 새로운 모놀리스"라는 함정과의 균형이다. 시스템 전체의 책임 배치를 사고하는 아키텍처 감각을 잰다 — 기능 나열이 아니라, 배치 기준과 그 기준이 무너질 때의 조직적 비용까지 말할 수 있는지 본다.

## 1. 게이트웨이의 존재 이유 — 횡단 관심사의 단일 시공 지점

### 1-1. 전제 정리 — 횡단 관심사가 무엇인가

**횡단 관심사(cross-cutting concern)**는 **특정 기능 하나에 속하지 않고, 모든 기능을 가로질러 똑같이 필요한 일**을 뜻한다. "횡단"은 기능들을 가로지른다는 뜻이고, "관심사"는 소프트웨어가 신경 써야 할 일이라는 뜻이다.

3년차라면 이 개념을 이미 만난 적이 있다. **Spring AOP가 정확히 이것을 위한 장치**다. 로깅, 트랜잭션, 성능 측정은 주문 기능에도 회원 기능에도 결제 기능에도 똑같이 필요한데, 이걸 메서드마다 손으로 넣으면 같은 코드가 수백 벌 복사되고 하나를 빠뜨려도 아무도 모른다. 그래서 `@Transactional` 하나로 선언하면 프레임워크가 모든 대상 메서드에 같은 처리를 끼워 넣어 준다.

```java
// 횡단 관심사를 손으로 넣으면 — 메서드마다 같은 코드가 반복된다
public Order createOrder(...) {
    tx.begin();                       // 모든 메서드에 똑같이 필요한 일
    log.info("createOrder start");    // 모든 메서드에 똑같이 필요한 일
    try { /* 진짜 하려던 일 */ }
    finally { tx.commit(); log.info("end"); }
}

// AOP로 빼면 — 한 곳에 한 번만 시공하고 전부에 적용된다
@Transactional                        // 선언만 하면 프레임워크가 끼워 넣는다
public Order createOrder(...) { /* 진짜 하려던 일만 남는다 */ }
```

**API 게이트웨이는 이 발상을 애플리케이션 안에서 네트워크 층으로 옮긴 것**이다. AOP가 메서드 호출을 가로채 공통 처리를 하듯, 게이트웨이는 **HTTP 요청을 가로채 공통 처리를 한다.** 개념이 같고 적용 범위만 다르다.

### 1-2. 게이트웨이가 없으면 무슨 일이 생기는가

N개 서비스가 각자 TLS, 인증, rate limit, CORS, 접근 로그를 구현하는 상황을 생각해 보자. 세 가지 비용이 발생한다.

**중복 구현.** 같은 JWT 검증 코드가 N벌 존재한다. 공통 라이브러리로 뽑아도 버전이 갈리기 시작하면 사실상 N벌이다.

**보안 구멍.** N개 중 하나는 반드시 빠뜨린다. 새로 만든 서비스에서 인증 필터를 안 걸고 배포하면, 그 서비스만 인증 없이 뚫려 있는데 아무도 모른다. **"전부에 적용됐는지"를 확인할 단일 지점이 없다**는 것이 문제의 본질이다.

**변경 비용.** "rate limit 한도를 조정하자"는 결정 하나에 N번 배포가 필요하다. 그러면 실무에서는 아무도 조정하지 않게 된다.

게이트웨이는 이 **횡단 관심사를 트래픽이 반드시 지나는 단일 지점에서 한 번만 시공**하려는 장치다.

비유하면 건물의 **정문 보안 게이트**다. 출입증 검사(인증), 출입 기록(로깅), 혼잡 시 입장 제한(rate limit)은 정문에서 하지만, "이 방문자가 3층 회의실을 예약했는지"(도메인 인가)는 정문이 알 수 없고 알아서도 안 된다. 그건 3층 부서(서비스)의 일이다. 정문 경비가 전 부서의 예약 현황을 실시간으로 알아야 한다면, 그건 정문이 회사 전체가 된 것이다.

### 1-3. 게이트웨이의 전형적 책임 — 이름만 나열하지 않는다

책임 목록을 외워서 나열하는 것과, 각각이 **왜 게이트웨이에 있어도 되는지**를 아는 것은 다르다. 각 항목이 무엇이고 왜 여기 있는지를 함께 본다.

| 책임 | 무엇을 하는가 | 왜 게이트웨이인가 |
|---|---|---|
| **TLS 종료** | HTTPS 암호를 여기서 풀고 내부로는 평문(또는 별도 mTLS)으로 보낸다 | 인증서 관리와 암복호화 CPU 비용을 한 곳에 모은다 |
| 라우팅 | 경로·호스트를 보고 어느 서비스로 보낼지 정한다 | 클라이언트가 서비스 분할 구조를 몰라도 되게 만든다 |
| 인증 토큰 검증 | JWT 서명·만료 확인, 클레임 추출 | 도메인 지식이 필요 없고 모든 요청에 균일하다 |
| 전역 rate limit | IP당·클라이언트당 요청 수 상한 | 서비스에 도달하기 전에 막아야 보호 효과가 있다 |
| CORS와 프리플라이트 | 브라우저의 교차 출처 요청 허용 여부를 헤더로 응답 | 도메인 지식이 전혀 필요 없고 모든 요청에 규칙이 같다 |
| 접근 로그와 trace id 발급 | 요청마다 추적 ID를 만들어 하위로 전파, 공통 로그 기록 | 모든 요청이 지나는 지점이라야 누락 없는 전수 기록이 된다 |
| 요청 크기 제한 | 본문 최대 크기 초과 시 거절 | 바이트만 세면 되고 내용을 해석할 필요가 없다 |
| IP 차단·경계 보안 | 알려진 공격 IP 차단, WAF 연동 | 안쪽으로 들여보내기 전에 걸러야 의미가 있다 |

**TLS 종료(TLS termination)**만 따로 풀어 두자. "종료"라는 번역 때문에 **연결을 끊는다**는 뜻으로 오해하기 쉬운데, 정확한 의미는 **암호화 구간이 여기서 끝난다**는 것이다. 클라이언트와 게이트웨이 사이는 HTTPS로 암호화되고, 게이트웨이가 그 암호를 풀어 평문 HTTP 요청을 얻은 뒤, 게이트웨이와 내부 서비스 사이는 평문으로(또는 내부용으로 다시 맺은 별개의 TLS로) 보낸다. 연결은 계속 살아 있고, 끝나는 것은 그 하나의 암호화 구간이다. 어느 계층에서 TLS를 종료할지의 트레이드오프는 `08-network-http/17-tls-termination-lb-vs-app.md`가 다룬다.

### 1-4. 층은 셋이다 — 게이트웨이 → BFF → 서비스

경계 논의가 어려워지는 이유는 대부분 **층을 둘로만 보기 때문**이다. "게이트웨이냐 서비스냐"로만 물으면 "화면용 응답 조합"처럼 어느 쪽에도 안 맞는 요구가 갈 곳이 없어져 게이트웨이로 흘러든다.

층을 셋으로 보면 각 요구가 갈 자리가 생긴다. 각 층이 **무엇을 알아도 되고 무엇을 알면 안 되는지**, 그리고 **언제 바뀌는지**를 함께 보는 것이 핵심이다.

```text
                    [브라우저 / 모바일 앱]
                              │  HTTPS
                              ▼
 ────────────────────────────────────────────────────────────────────────
  ① API 게이트웨이                                       소유: 플랫폼 팀
     아는 것     HTTP 문법, 경로 패턴, 토큰의 서명과 만료, 클라이언트 식별자
     몰라야 함   "주문"·"쿠폰"이 무엇인지, 누가 그 리소스의 주인인지
     하는 일     TLS 종료 · 라우팅 · 토큰 서명 검증 · 전역 rate limit
                 CORS와 프리플라이트 · 요청 크기 제한 · 접근 로그와 trace id
     바뀌는 때   보안·인프라 정책이 바뀔 때 (도메인 기능 변경과 무관해야 정상)
 ────────────────────────────────────────────────────────────────────────
                              │  내부 호출 + 서명된 내부 토큰
                              ▼
 ────────────────────────────────────────────────────────────────────────
  ② BFF (화면 전용 백엔드)                    소유: 그 화면의 클라이언트 팀
     아는 것     이 화면이 무엇을 그리는가, 어느 조각이 필수이고 어느 조각이 선택인가
     몰라야 함   할인율 계산식, 주문 상태 전이 규칙 같은 도메인 규칙
     하는 일     여러 서비스 병렬 호출과 조합 · 화면 DTO 변환 · 부분 실패 처리
     바뀌는 때   화면이 바뀔 때 (하루에도 여러 번일 수 있다)
 ────────────────────────────────────────────────────────────────────────
                              │
                ┌─────────────┼─────────────┐
                ▼             ▼             ▼
 ────────────────────────────────────────────────────────────────────────
  ③ 주문 / 상품 / 쿠폰 서비스                          소유: 각 도메인 팀
     아는 것     자기 도메인 전부 — 데이터, 소유권, 상태 전이, 업무 규칙
     하는 일     리소스 소유권 인가 · 도메인 검증 · 비즈니스 규칙 실행
     바뀌는 때   그 도메인의 기능이 바뀔 때
 ────────────────────────────────────────────────────────────────────────
```

이 그림이 말하는 것은 **"아는 것"이 아래로 갈수록 깊어지고, "바뀌는 주기"가 아래로 갈수록 빨라진다**는 것이다. 그리고 두 축이 같은 방향으로 움직인다는 사실이 이 문서 전체의 근거가 된다 — **도메인을 아는 층일수록 자주 바뀌므로, 도메인 지식이 위층으로 올라가면 위층도 함께 자주 바뀌어야 한다.** 그런데 게이트웨이는 전 트래픽이 지나는 지점이라 자주 바꾸기 가장 위험한 곳이다. 여기서 모순이 터진다.

BFF의 정의와 그 대가(운영 컴포넌트 증가, 화면 수에 비례하는 엔드포인트, 소유권 합의)는 `07-chatty-api-call-explosion.md`가, BFF가 조합한 응답의 부분 실패 계약은 `13-aggregation-api-partial-failure-contract.md`가 다룬다.

## 2. 경계 기준 — 세 가지 질문으로 자른다

어떤 처리를 어디에 둘지 애매할 때 이 순서로 묻는다. 순서가 중요하다 — 앞의 질문에서 결론이 나면 뒤는 안 봐도 된다.

**① 도메인 지식이 필요한가?** 필요하면 무조건 서비스다. 게이트웨이가 "주문", "쿠폰"의 의미를 알기 시작하는 순간 경계가 무너진다. 이 질문이 첫 번째인 이유는, 나머지 두 질문을 아무리 잘 통과해도 이것 하나가 걸리면 답이 뒤집히기 때문이다.

**② 모든(대부분의) 요청에 균일하게 적용되는가?** 균일하면 게이트웨이 후보다. 특정 서비스에만 필요한 처리를 게이트웨이에 두면, **그 서비스의 변경이 게이트웨이 배포를 요구하게 된다** — 1-4 그림의 위층이 아래층의 주기로 끌려 내려오는 것이다.

**③ 바뀌는 주기와 주체가 누구인가?** 서비스 팀의 기능 변경 때마다 함께 바뀌어야 하는 로직이면 서비스에 둔다. **변경의 주인과 코드의 위치를 일치시켜야 배포가 서로를 기다리지 않는다.** 이 질문은 코드의 성질이 아니라 조직의 성질을 묻는 것이고, 그래서 앞의 둘로 애매한 회색 지대에서 결정적인 판정을 해 준다.

### 2-1. 대표 사례: 인증(Authentication)과 인가(Authorization)의 분할

이 둘은 이름이 비슷해 자주 뭉뚱그려지는데, 세 질문에 대한 답이 정반대라 갈라지는 자리가 명확하다.

- **인증 = "누구인가"** — JWT 서명 검증, 만료 확인, 토큰에서 사용자 ID와 권한 클레임 추출. 토큰의 서명이 유효한지는 **공개키와 서명 알고리즘만 있으면 판정**할 수 있고, 주문이 뭔지 쿠폰이 뭔지 몰라도 된다. 도메인 지식이 필요 없고 모든 요청에 균일하다 → **게이트웨이**. 검증 결과(사용자 ID 등)는 내부 헤더로 서비스에 전달한다.
- **인가 = "이 리소스에 이걸 해도 되는가"** — "이 주문은 이 사용자의 것인가", "이 문서의 편집 권한이 있는가". 이 판정에는 **주문 테이블의 `owner_id`를 읽어야** 하고, 그 데이터를 가진 쪽은 주문 서비스뿐이다 → **서비스**.

핵심은 이것이다. **인증은 "요청에 딸려 온 증명서를 검사하는 일"이라 데이터가 필요 없고, 인가는 "우리 DB의 상태와 대조하는 일"이라 데이터가 필요하다.** 데이터가 있는 곳에 판정이 있어야 한다.

```java
// Before: 게이트웨이에 도메인 인가를 넣은 경우 (경계 붕괴의 시작)
// gateway의 라우트 필터에서 —
if (path.matches("/orders/\\{id}")) {
    var order = orderServiceClient.getOrder(orderId);   // 문제 1: 게이트웨이가
    if (!order.ownerId().equals(userId)) {              //   주문 도메인을 조회·해석한다
        return forbidden();                             // 문제 2: 인가 규칙이 바뀌면
    }                                                   //   (예: '가족 계정도 조회 가능')
}                                                       //   주문팀이 게이트웨이 배포를 기다린다
                                                        // 문제 3: 주문 조회가 2번 일어난다

// After: 게이트웨이는 신원 검증까지만, 인가는 서비스가
// [게이트웨이] JWT 검증 → 통과 시 내부 헤더로 신원 전달
//   X-User-Id: 42  (+ 위변조 방지 서명, 아래 꼬리질문 참고)
// [주문 서비스] 도메인 데이터로 인가 판단
@GetMapping("/orders/{id}")
Order getOrder(@PathVariable long id,
               @RequestHeader("X-User-Id") long userId) {
    var order = orderRepository.findById(id);
    accessPolicy.checkReadable(order, userId);   // 소유권·가족계정 규칙은
    return order;                                // 주문팀 코드에, 주문팀 배포 주기로
}
```

Before의 세 가지 문제 중 **문제 2가 가장 비싸다.** 문제 1과 3은 성능·구조의 문제라 아프지만 국지적인데, 문제 2는 **조직의 배포 속도**를 건드린다. "가족 계정도 조회 가능하게 해 주세요"라는 기획 요구 하나가 주문팀의 코드 수정이 아니라 게이트웨이 PR과 플랫폼 팀 리뷰와 전 트래픽 리스크를 동반하는 배포가 된다. 세 번째 질문("바뀌는 주기와 주체")이 이 비용을 미리 잡아내라고 있는 것이다.

### 2-2. 회색 지대의 판단 예시

기준을 외우는 것보다 **기준을 애매한 사례에 적용해 보는 것**이 실력이다. 자주 나오는 넷을 본다.

| 사례 | 게이트웨이에 두는 경우 | 서비스에 두는 경우 | 가르는 근거 |
|---|---|---|---|
| rate limit | IP당·클라이언트당 전역 한도 | "포인트 전환은 사용자당 하루 3회" | 후자는 한도가 아니라 **비즈니스 규칙**이다. 같은 이름이라도 도메인 의미가 실리는 순간 넘어간다 |
| 응답 변환·조합 | 헤더 추가 같은 무해한 수준 | 여러 서비스 응답을 화면용으로 조합 | 조합에는 도메인+화면 지식이 필요하다. 게이트웨이가 아니라 **BFF**로 분리한다 |
| 요청 검증 | JSON 문법이 맞는가, 크기 제한 | "배송지가 유효한 주소인가" | 전자는 바이트만 보면 되고, 후자는 주소 도메인을 알아야 한다 |
| 캐싱 | 정적·공통 응답 캐시 (또는 그 앞 CDN) | 무효화 규칙이 도메인 이벤트에 묶인 캐시 | "주문이 취소되면 이 캐시를 비운다"는 규칙 자체가 도메인 지식이다 |

rate limit 행이 특히 좋은 훈련 재료다. 두 항목의 이름이 같고, 구현 기술도 같고(카운터 + 윈도우), 심지어 저장소도 같은 Redis일 수 있는데, 배치는 반대로 갈린다. **판단은 기술이 아니라 "이 한도를 정한 사람이 보안팀인가 기획자인가"로 난다.**

### 2-3. CORS 프리플라이트 — 이 기준에 정확히 들어맞는 예

**CORS(Cross-Origin Resource Sharing, 교차 출처 자원 공유)**는 브라우저가 지금 보고 있는 페이지의 출처(origin, 스킴 + 호스트 + 포트)와 **다른 출처로 가는 요청의 응답을 기본적으로 못 읽게 막고**, 서버가 응답 헤더로 "이 출처는 허용한다"고 명시적으로 동의해 줄 때만 풀어 주는 브라우저의 규칙이다. 집행자는 언제나 브라우저이므로 서버 간 호출이나 curl에는 아무 효력이 없다(상세는 `08-network-http/08-cors-and-preflight.md`).

여기서 이 문서와 이어지는 지점이 **프리플라이트(preflight, 사전 확인)**다. 브라우저는 `PUT`/`DELETE`, `application/json` 본문, 커스텀 헤더처럼 "예전 웹에는 없던 형태"의 교차 출처 요청을 보내기 전에, 먼저 **`OPTIONS` 메서드로 "이런 메서드·헤더의 요청을 보내도 되나요?"를 물어본다.** 서버가 허용 헤더로 답해야만 진짜 요청을 보낸다.

이 `OPTIONS` 요청이 게이트웨이에서 처리하기 좋은 이유를 2절의 세 질문으로 그대로 검사해 보자.

- **① 도메인 지식이 필요한가?** 필요 없다. 응답에 담을 것은 허용 출처 목록, 허용 메서드, 허용 헤더, 캐시 시간뿐이고 주문이 뭔지 알 필요가 없다.
- **② 모든 요청에 균일한가?** 균일하다. `/orders`든 `/coupons`든 프리플라이트 응답 규칙이 같다.
- **③ 바뀌는 주기와 주체는?** 프론트 도메인이 추가될 때 바뀌고, 그 주체는 플랫폼·보안 쪽이다. 주문팀의 기능 변경과 무관하다.

세 질문을 모두 통과한다. 게다가 실무적 이득이 하나 더 있다. **프리플라이트는 본 요청 앞에 붙는 추가 왕복**이라 서비스까지 내려보내면 트래픽이 두 배가 되는데, 게이트웨이에서 즉시 응답하면 그 왕복이 내부망까지 들어오지 않는다. `Access-Control-Max-Age`로 브라우저에 프리플라이트 결과를 캐시시키는 것도 한 곳에서 일괄 설정하면 끝난다.

한편 `OPTIONS`는 HTTP 메서드 자체로도 **safe(서버 상태를 바꾸지 않음)이면서 멱등(여러 번 보내도 결과가 같음)**이라 게이트웨이가 마음대로 응답해도 부작용이 없다(`01-restful-design-principles-resource-naming.md`의 메서드 속성 표 참고). 안전하게 가로챌 수 있다는 성질까지 갖춘 것이다.

## 3. 함정 — 게이트웨이가 새로운 모놀리스가 되는 경로

### 3-1. 작은 편의의 누적 — 각각은 다 합리적이었다

경계가 무너지는 것은 한 번의 큰 잘못된 결정이 아니다. 아무도 "게이트웨이에 도메인 로직을 넣자"고 결정하지 않는다. 무너짐은 **각각은 합리적이었던 작은 결정들의 누적**으로 온다.

실제로 어떻게 진행되는지 시간 순으로 보면 이 함정의 성격이 드러난다.

```text
 1월  [요청] 레거시 모바일 앱이 옛 필드명을 기대한다. 서비스 수정·배포는 다음 분기.
      [결정] "이번 한 번만" 게이트웨이 응답 필터에서 필드명을 바꿔 준다.
      [당시 판단] 합리적이다 — 코드 5줄이고, 서비스는 손대지 않는다.
      [실제로 넘은 선] 게이트웨이가 응답 "내용"을 해석하기 시작했다.
        │
        ▼
 3월  [요청] 신규 결제 플로우를 VIP 회원에게만 먼저 열고 싶다.
      [결정] 게이트웨이 라우팅에 "회원 등급이 VIP면 신규 서비스로" 조건을 넣는다.
      [당시 판단] 합리적이다 — 라우팅은 원래 게이트웨이의 일이다.
      [실제로 넘은 선] 게이트웨이가 "회원 등급"이라는 도메인 개념을 알게 됐다.
                       등급 정책이 바뀌면 게이트웨이를 고쳐야 한다.
        │
        ▼
 6월  [요청] 특정 파트너가 어뷰징 중이다. 서비스 수정·배포에는 이틀이 걸린다.
      [결정] 게이트웨이에서 그 파트너의 특정 엔드포인트만 임시 차단한다.
      [당시 판단] 합리적이다 — 핫픽스는 가장 빨리 배포되는 곳에서 하는 게 맞다.
      [실제로 넘은 선] "임시"가 지워지지 않는다. 왜 넣었는지 아는 사람이
                       퇴사하면 아무도 지우지 못한다.
        │
        ▼
 9월  [현재] 게이트웨이 필터에 도메인 조건문 40개. 그중 절반은 사유를 아무도 모른다.
      게이트웨이 배포는 전 트래픽 리스크라 "목요일 오후, 플랫폼 팀 입회"로 고정됐다.
      주문팀이 응답 필드 하나 바꾸려면 게이트웨이 PR을 올리고 목요일을 기다린다.

      결정 40개가 전부 그때는 합리적이었다. 합리적인 결정 40개의 합이 배포 병목이다.
```

이 타임라인이 보여주는 것이 이 함정의 진짜 성격이다. **각 결정 시점에는 "이게 경계 위반인가?"를 판단할 근거가 안 보인다.** 5줄짜리 필드 변환은 아무리 봐도 아키텍처 문제가 아니고, 라우팅 조건은 게이트웨이의 정당한 일처럼 보인다. 위반이 눈에 보이는 시점은 40개가 쌓인 뒤이고, 그때는 이미 빼기가 넣기보다 훨씬 비싸다.

그래서 방어는 "다이어그램을 잘 그리기"가 아니라 **개별 결정의 순간에 적용할 기준을 팀이 미리 공유하기**가 된다. 3-3의 방지 장치들이 전부 이 형태인 이유다.

### 3-2. 쌓이면 무엇을 잃는가 — 세 가지 비용

**배포 병목.** 여러 팀의 변경이 게이트웨이라는 단일 배포 파이프라인에 줄을 선다. 서비스는 하루 10번 배포하는데 게이트웨이는 조심스러워 주 1회가 되고, 게이트웨이에 로직을 둔 팀은 모두 그 주기에 묶인다. **MSA로 분리했던 조직 결합이 게이트웨이에서 부활한다.** 이것이 "새로운 모놀리스"라는 표현의 정확한 의미다 — 코드가 한 덩어리라는 뜻이 아니라, **배포 단위가 한 덩어리로 되돌아왔다**는 뜻이다.

**폭발 반경 확대.** 게이트웨이는 전 트래픽의 단일 경로다. 특정 팀이 넣은 필터 하나의 버그가 전 서비스 장애가 된다. 서비스에 있었으면 그 도메인만 죽었을 문제가, 게이트웨이에 있으면 회사 전체가 죽는다.

**소유권 실종.** 게이트웨이 안의 도메인 로직은 게이트웨이 팀도 도메인 팀도 자기 것이라 여기지 않는다. 게이트웨이 팀은 "그 도메인은 모른다"고 하고, 도메인 팀은 "우리 저장소가 아니다"라고 한다. 결과는 **아무도 테스트하지 않고 아무도 지우지 못하는 코드**다. 3-1 타임라인의 6월 항목이 9월까지 살아남는 이유가 이것이다.

### 3-3. 방지 장치 (가산점 포인트)

**"게이트웨이 변경은 설정이어야지 코드가 아니어야 한다"는 원칙.** 라우트 추가, 한도 조정은 선언적 설정(YAML 등)으로 하고, **도메인 조건문이 담긴 커스텀 필터가 PR에 등장하면 그것 자체를 경계 위반 신호로 리뷰에서 잡는다.** 이 원칙의 값은 "판정이 기계적"이라는 데 있다 — 3-1에서 본 것처럼 개별 결정의 합리성으로는 판단이 안 되므로, **형태로 거르는 규칙**이 필요하다.

**화면·클라이언트 맞춤 요구는 BFF로 배출한다.** 조합·변환 요구를 게이트웨이가 아니라 클라이언트 팀이 소유하는 BFF 계층으로 보낸다. 1-4의 3층 구조가 여기서 값을 한다 — **갈 곳이 있어야 배출이 된다.** BFF가 없으면 "이 요구는 게이트웨이에 두면 안 된다"고 말해도 대안이 없어 결국 들어온다.

**게이트웨이의 SLO와 변경 통계를 관리한다.** 게이트웨이 배포 빈도가 올라가고 배포 사유가 특정 도메인 요구로 채워지면 경계가 새고 있다는 **정량 신호**다. "이번 분기 게이트웨이 배포 12건 중 9건이 특정 팀의 도메인 요구"라는 숫자는 리뷰에서 개별 PR을 막는 것보다 훨씬 강한 근거가 된다.

## 4. 꼬리질문 대비 포인트

### "게이트웨이가 인증했다는 걸 서비스는 어떻게 신뢰하나요? 내부에서 X-User-Id 헤더를 위조하면요?"

"내부망이니까 믿는다"는 답은 감점이다. 왜 위험한지를 공격자 시점으로 보면 즉시 이해된다.

```bash
# 공격자가 사내망의 아무 컨테이너(또는 침해된 다른 서비스)에서 이 한 줄을 실행하면
curl -H "X-User-Id: 1" http://order-service.internal:8080/orders/8471
#      ^^^^^^^^^^^^^^^^^^^ 게이트웨이가 붙여주기로 한 헤더를 직접 붙였을 뿐이다

# 주문 서비스는 "게이트웨이가 인증을 마친 사용자 1번의 요청"이라고 믿고 응답한다.
# 공격자는 로그인할 필요도, 토큰을 훔칠 필요도 없었다 —
# 인증을 통과한 것이 아니라 인증의 '결과'를 자칭했기 때문이다.
```

문제의 구조는 이것이다. **`X-User-Id`는 신원의 증명이 아니라 신원의 주장**이다. 증명(서명된 토큰)은 게이트웨이에서 소비되고 사라졌고, 서비스에는 주장만 도착한다. 그런데 서비스는 그 주장을 검증할 수단이 없다.

실무 답은 세 층이고, 보통 겹쳐서 쓴다.

**(1) 서명된 내부 토큰으로 재발급한다.** 게이트웨이가 외부 토큰을 검증한 뒤, 그 결과를 **짧은 만료의 내부용 JWT**로 새로 서명해 전달한다. 서비스는 게이트웨이의 공개키로 서명을 확인하므로, 게이트웨이의 개인키 없이는 위조할 수 없다. 위 curl은 서명이 없어 즉시 거부된다.

**(2) 네트워크 수준에서 호출자를 확인한다.** 서비스가 게이트웨이 외의 직접 호출을 받지 않도록 격리하고, 서비스 간에는 **mTLS**를 쓴다. mTLS는 **상호 TLS(mutual TLS)**로, 평소 HTTPS가 서버만 인증서를 제시하는 것과 달리 **클라이언트도 인증서를 제시해 서로를 확인**하는 방식이다. 그래서 "이 호출이 정말 게이트웨이에서 온 것인가"를 애플리케이션 코드가 아니라 **네트워크 계층에서 보장**할 수 있다. 서비스 메시(Istio 등)를 쓰면 애플리케이션 수정 없이 이 층을 깔 수 있다.

**(3) 원본 토큰을 그대로 전파한다.** 게이트웨이가 검증한 원본 토큰을 하위로도 넘겨 필요한 서비스가 재검증한다. 가장 단순하지만 검증이 N번 반복되고, 토큰 수명·스코프 관리가 복잡해진다.

이 세 대응을 관통하는 태도가 **zero trust**다. 이름 그대로 **신뢰를 0으로 둔다**는 뜻으로, "내부망이니까 믿는다"는 전제 자체를 버리고 **모든 호출을 그때마다 검증하는** 원칙이다. 방화벽 안쪽을 안전지대로 보던 과거 모델이, 내부의 컨테이너 하나만 뚫려도 전부 무너진다는 경험으로 폐기된 결과다. "경계 안이라고 무조건 신뢰하지 않는다"는 태도를 보여주는 것이 이 질문의 포인트다.

### "그럼 인가를 위한 공통 권한 체크가 서비스마다 중복 구현되지 않나요?"

먼저 중복을 두 종류로 갈라야 답이 정확해진다.

**역할(role) 수준의 거친 체크**("ADMIN만 접근")는 토큰 클레임만 보면 판정되므로 도메인 데이터가 필요 없다. 이건 게이트웨이나 공통 라이브러리에서 균일 처리할 수 있고, 실제로 중복 문제가 크지 않다.

진짜 중복이 생기는 곳은 **리소스 소유권 수준**이다. "본인 것이거나, 같은 가족 계정이거나, ADMIN이면 조회 가능"이라는 규칙이 주문·문서·결제 서비스에 각각 하드코딩되면, 규칙 하나 바뀔 때 세 곳을 고쳐야 하고 한 곳을 빠뜨리면 보안 사고가 된다.

이걸 게이트웨이로 올리는 것은 답이 아니다(2-1에서 본 이유 그대로 — 판정에 도메인 데이터가 필요하다). 대신 두 가지 방향이 있다. **(1) 공통 인가 라이브러리로 패턴을 표준화**하거나, **(2) 정책 결정을 별도 컴포넌트로 빼고 서비스는 질의만 하는 구조**로 푼다. 후자를 **PDP/PEP 분리**라고 부른다.

풀네임부터 확정하자.

- **PDP = Policy Decision Point(정책 결정 지점)** — **"이 사람이 이걸 해도 되나?"를 판단하는 곳.** 인가 규칙이 여기 한 곳에만 존재한다.
- **PEP = Policy Enforcement Point(정책 집행 지점)** — **그 판단을 받아 실제로 막거나 통과시키는 곳.** 판단하지 않고 집행만 한다.

왜 둘로 나누면 중복이 줄면서도 실행은 서비스에 남는지를 그림으로 보면 명확하다.

```text
  ① 요청 도착: "사용자 42가 주문 8471을 조회하려 한다"
        │
        ▼
  ┌ 주문 서비스 안의 PEP — 정책 집행 지점
  │    실제로 막거나 통과시키는 코드. 도메인 문맥을 아는 쪽에 있어야 한다.
  │    order.ownerId = 42, order.status = PAID   ← 주문 서비스만 아는 정보
  └───┬────────────────────────────────────────────────────────────────
      │  ② 질의: 주체=user:42 / 리소스=order:8471(owner=42, status=PAID)
      │          / 행위=read
      ▼
  ┌ PDP — 정책 결정 지점 (전담 정책 엔진 또는 사이드카)
  │    "해도 되나?"를 판단한다. 인가 규칙이 여기 한 곳에만 있다.
  │    규칙: 소유자 본인 OR 같은 가족 계정 구성원 OR ADMIN 역할
  │    → 가족 계정 규칙이 바뀌면 이 규칙 하나만 고친다 (서비스 배포 없음)
  └───┬────────────────────────────────────────────────────────────────
      │  ③ 결정: PERMIT
      ▼
  ④ PEP가 결정을 받아 요청을 통과시킨다 (DENY였다면 403)
```

이 구조가 두 요구를 동시에 만족시키는 방식이 핵심이다. **규칙은 PDP 한 곳에 모여 중복이 사라지지만, 그 규칙을 적용할 재료(주문의 소유자, 상태)를 모으고 결과를 집행하는 일은 여전히 도메인 문맥이 있는 서비스 쪽에 남는다.** 게이트웨이 집중과 다른 점이 여기다 — 게이트웨이로 올리면 재료를 모으기 위해 게이트웨이가 도메인을 조회해야 하지만, PDP는 서비스가 재료를 들고 와서 물어보는 구조라 도메인 지식이 위로 새지 않는다.

핵심은 **"중복 제거의 방향이 게이트웨이 집중이 아니라 라이브러리화 또는 전담 컴포넌트화"**라는 것이다. 실행 위치는 여전히 도메인 문맥이 있는 서비스 쪽이다.

한 가지 대가도 함께 말하면 좋다. **PDP 질의가 요청마다 네트워크 왕복을 추가**하므로, 실무에서는 PDP를 사이드카로 같은 파드에 붙이거나 정책을 각 서비스에 배포해 로컬에서 평가하는 방식(OPA 같은 도구가 이 형태를 지원한다)을 쓴다. 그리고 **PDP 자체가 새로운 단일 장애점**이 되지 않도록 가용성 설계가 필요하다.

### "BFF와 API 게이트웨이는 뭐가 다른가요?"

같은 자리에 있는 것처럼 보이지만 **소유권과 변경 주기가 다르다.** 이 둘이 다르면 컴포넌트를 합칠 수 없다는 것이 답의 골격이다.

**게이트웨이는 전 트래픽 공통의 인프라 경계**(인증, rate limit, 라우팅)로 **플랫폼 팀이 소유**한다. 도메인을 모르는 채 얇게 유지되며, 보안·인프라 정책이 바뀔 때만 바뀐다.

**BFF는 특정 프론트엔드 하나를 위한 전용 백엔드**로, 그 클라이언트 팀이 소유한다. 07번 문서의 정의대로 **재사용성을 대가로 왕복을 사는 거래**이고, 화면 요구에 맞춰 자주 바뀌는 것이 정상이다.

가르는 축을 표로 세우면 이렇게 된다.

| | API 게이트웨이 | BFF |
|---|---|---|
| 소유 | 플랫폼 팀 (전사 공통) | 그 화면을 만드는 클라이언트 팀 |
| 대상 | 모든 트래픽 | 특정 클라이언트 하나(모바일 앱, 웹) |
| 도메인 지식 | 없어야 한다 | 화면 조합 수준까지 (도메인 규칙은 아니다) |
| 변경 주기 | 드물게 (보안·인프라 정책 변경 시) | 자주 (화면이 바뀔 때마다) |
| 배포 리스크 | 전 서비스 (폭발 반경 최대) | 그 클라이언트만 |
| 개수 | 보통 1개 | 클라이언트 종류만큼 |

표의 마지막 두 행이 결론을 만든다. **변경 주기가 정반대인 두 책임을 한 컴포넌트에 합치면, 자주 바뀌어야 하는 쪽이 폭발 반경 최대인 컴포넌트의 배포 절차에 묶인다.** 그것이 3-2의 배포 병목이고, 게이트웨이 모놀리스화의 시작이다. 그래서 분리한다.

"게이트웨이 → BFF → 서비스"로 층을 나눠 답하면 구조가 선명해진다(1-4의 그림).

### "게이트웨이 자체가 단일 장애점(SPOF)이자 병목이 되지 않나요?"

**SPOF(Single Point Of Failure, 단일 장애점)**는 **그것 하나가 죽으면 전체가 죽는 지점**을 말한다. 게이트웨이는 전 트래픽이 반드시 지나는 곳이므로 정의상 여기에 해당한다. "아니다"라고 답하면 안 된다 — 맞다고 인정하고, 그래서 어떻게 하는지를 말하는 것이 답이다.

세 가지로 대응한다.

**(1) 무상태(stateless)로 설계해 수평 확장 가능하게 한다.** 게이트웨이 인스턴스가 요청 간에 기억하는 것이 없어야 아무 인스턴스나 아무 요청을 처리할 수 있고, 그래야 앞에 로드밸런서를 두고 대수를 늘릴 수 있다. 상태가 필요한 rate limit 카운터는 인스턴스 메모리가 아니라 외부 저장소(Redis 등)에 둔다 — 메모리에 두면 인스턴스가 늘어날수록 실제 한도가 인스턴스 수만큼 느슨해진다.

**(2) 다중 인스턴스 + 헬스체크 기반 로드밸런싱**으로 한 대가 죽어도 트래픽이 살아 있는 대수로 넘어가게 한다. 배포도 무중단(롤링·블루그린)으로 한다.

**(3) 로직을 얇게 유지해 처리 지연과 장애 확률 자체를 낮춘다.** 이 세 번째가 2절·3절과 이어지는 지점이다. 게이트웨이에 도메인 조건문 40개가 쌓이면 요청당 처리 시간이 늘고(전 트래픽에 곱해진다), 버그가 들어갈 표면적이 넓어지며, 그 버그의 폭발 반경은 전 서비스다.

그래서 **"게이트웨이를 얇게 유지하는 것은 아키텍처 순수성 문제이기 전에 가용성 문제"**라고 연결하면 좋다. 2절의 경계 기준과 같은 결론에 도달하는 다른 경로다 — 설계 취향으로 지키자고 하면 개별 요구 앞에서 밀리지만, 가용성 문제로 프레이밍하면 지킬 근거가 생긴다.

### "지금 모놀리스에서 MSA로 전환 중이라면, 게이트웨이 도입 시점과 초기 책임 범위를 어떻게 잡겠어요?" (시니어 변별 포인트)

처음부터 만능 게이트웨이를 만들지 않는다. 전환 초기의 게이트웨이는 **라우팅 + 인증 + 공통 로깅**의 최소 책임으로 시작한다.

이 셋을 고른 이유가 답의 절반이다. **모놀리스에서 서비스를 하나 떼어낼 때마다 즉시 필요해지는 것들**이면서(라우팅이 없으면 클라이언트가 분할 구조를 알아야 하고, 인증이 없으면 새 서비스마다 재구현이고, 공통 로깅이 없으면 요청이 어디서 끊겼는지 못 찾는다), **동시에 도메인 지식이 필요 없어 안전한 것들**이다. 즉 "필요성은 최대, 경계 위험은 최소"인 교집합이다.

rate limit·IP 차단 같은 경계 보안은 그다음이다. 트래픽 특성과 공격 패턴이 파악되기 전에 한도를 정하면 정상 사용자를 막거나 아무것도 못 막는 값이 되므로, 데이터가 쌓이는 대로 추가한다.

반대로 **응답 변환·조합 요구는 처음부터 BFF로 격리해 게이트웨이에 들어올 길을 막는다.** 3-3에서 말한 대로 갈 곳이 있어야 배출이 되고, 첫 사례가 게이트웨이로 들어가면 그것이 선례가 되어 두 번째부터는 막을 근거가 사라진다.

그리고 마지막이 이 질문의 핵심이다. **"게이트웨이에 넣자"는 제안이 나올 때마다 2절의 세 질문(도메인 지식? 균일 적용? 변경 주체?)을 리뷰 기준으로 명문화해 둔다.** 3-1에서 본 것처럼 경계는 한 번의 큰 결정이 아니라 40개의 작은 결정으로 무너지므로, 방어도 큰 결정 한 번이 아니라 **작은 결정마다 적용되는 기준**이어야 한다.

경계는 아키텍처 다이어그램이 아니라 **반복되는 개별 결정의 기준을 팀이 공유하는 것**으로 지켜진다는 답이 시니어의 답이다.

## 한 줄 요약

게이트웨이와 서비스의 경계는 **"도메인 지식 없이 모든 요청에 균일하게 적용되는가"**로 자른다 — 인증·라우팅·전역 rate limit·CORS 프리플라이트·공통 로깅은 게이트웨이, 리소스 소유권 인가·도메인 검증·비즈니스 규칙은 서비스, 화면 맞춤 조합은 BFF로 나누고(층이 셋이어야 각 요구가 갈 자리가 생긴다), 인가 중복은 게이트웨이 집중이 아니라 PDP/PEP 분리로 풀어 규칙은 한 곳에 모으되 집행은 도메인 문맥이 있는 서비스에 남긴다 — 이 기준이 무너져 도메인 로직이 게이트웨이에 쌓이면 모든 팀의 배포가 한 지점에 줄을 서는 새로운 모놀리스가 되는데, 그 붕괴는 각각 합리적이었던 작은 편의의 누적으로 오므로 **경계 기준을 팀의 리뷰 기준으로 명문화해 개별 결정마다 적용하는 것**까지가 설계다.
