# 외부 파트너 API vs 내부 API — 신뢰 경계가 바뀌면 설계가 바뀐다

> 핵심 관전 포인트: **둘의 차이는 기능이 아니라 신뢰 경계다 — 신뢰 경계란 "이 선을 넘어오는 요청은 우리가 통제하지 못하는 쪽에서 온다"고 선언하는 자리이고, 내부 API가 느슨해도 되는 이유는 안전해서가 아니라 **호출자를 우리가 고칠 수 있어서**다. 파트너는 고칠 수 없으므로 ① 인증은 "누구인지"를 넘어 자격증명의 생명주기(발급·무중단 로테이션·HMAC 요청 서명·스코프·즉시 회수)까지, ② rate limit은 파트너별 쿼터와 `429` + `Retry-After` + 남은 한도 헤더라는 응답 계약까지 — 파트너가 자기 소진량을 볼 수 없으면 한도는 보호 장치일 뿐 상품 조건이 되지 못한다 — ③ 문서는 참고자료가 아니라 파트너가 그것만 보고 구현하는 계약서로, ④ 약속은 SLI(측정하는 지표) → SLO(내부 목표) → SLA(어기면 환불·크레딧이 따르는 계약)의 3단으로 명문화하되 SLA는 계측 오차를 흡수하고 위반 전에 개입할 시간을 벌기 위해 반드시 SLO보다 느슨하게 잡는다. 그리고 한 번 공개한 필드는 회수에 몇 달이 걸리므로 "최소한으로 공개하고, 외부 전용 계약 층을 내부 API 위에 얹는다"가 원칙이다 — 공개는 한 방향 문이다.**

---

## 0. 질문 + 의도

**질문**: "외부 파트너사에 제공하는 API(콘텐츠 연동)와 내부 API 설계의 차이점은? (인증, rate limit, 문서화, SLA)"

**출제 의도**: 신뢰 경계가 바뀌면 설계가 바뀐다(인증 강화, rate limit, 문서가 곧 계약)는 것을 아는지 본다. 콘텐츠 연동 업무의 실제 형태라, 외부와의 기술 계약을 다뤄본 경험을 검증한다.

## 1. 신뢰 경계 — 이 선 너머의 호출자는 우리가 고칠 수 없다

### 1-1. 전제 지식 — 신뢰 경계란 무엇인가

이 문서의 모든 결론이 하나의 개념에서 나오므로, 그 개념부터 정확히 정의하고 시작한다.

**신뢰 경계(trust boundary)는 "여기서부터 들어오는 데이터와 요청은 그대로 믿을 수 없다"고 선언하는 선이다.** 이름 그대로 **신뢰가 끝나는 자리**에 긋는 경계다. 보안 설계에서 쓰는 말이지만 뜻은 단순하다 — 경계 안쪽은 우리가 만들고 배포하고 고치는 코드가 있는 영역이고, 바깥쪽은 그렇지 않은 영역이다.

우리 시스템의 지도 위에 이 선을 그어 보면 이렇게 된다.

```text
        [ 경계 안 — 우리가 통제하는 영역 ]             │      [ 경계 밖 — 통제할 수 없는 영역 ]
                                                       │
   주문 서비스 ── 사내 게이트웨이 ── 콘텐츠 서비스        │    파트너 A의 연동 서버
        │              │                 │             │    파트너 B의 야간 배치
        └──────────────┴─────────────────┘             │    파트너 C가 외주 준 스크립트
         같은 조직 · 같은 배포 파이프라인 · 코드 열람 가능 │    (코드를 볼 수도, 고칠 수도, 재배포할 수도 없다)
                                                       │
                                            신뢰 경계 ──┘
```

경계를 넘어오는 요청에 대해 우리가 아는 것은 **요청 그 자체뿐**이다. 그 요청을 보낸 코드가 어떤 모습인지, 언제 배포됐는지, 재시도를 어떻게 구현했는지, 심지어 정말 그 파트너가 보낸 것인지조차 요청 자체를 검증하지 않고서는 알 수 없다. 그래서 검증·인증·한도가 **필요해진다.** 이것들은 외부 API에 붙이는 장식이 아니라, "믿을 수 없다"는 전제에서 논리적으로 따라 나오는 결과다.

### 1-2. 내부 API가 느슨해도 되는 진짜 이유

여기가 이 문서 전체의 뼈대이므로 한 번 더 강조해서 짚는다. 내부 API에 인증이 간단하고 rate limit이 없어도 굴러가는 이유는 **내부가 안전해서가 아니다.** 사내 네트워크에도 버그 있는 코드가 있고, 잘못 배포된 배치가 초당 수천 번을 때릴 수 있다.

진짜 이유는 이것이다. **호출자를 우리가 고칠 수 있다.**

- 내부 서비스가 폭주하면 그 팀에 연락해서 배포를 롤백시키거나 코드를 고치게 할 수 있다.
- 계약을 바꿔야 하면 소비자 팀과 합의해서 **같은 스프린트 안에 양쪽을 함께 바꾼다.**
- 누가 잘못 호출하고 있으면 그 코드를 직접 열어서 확인할 수 있다.

즉 내부 API의 느슨함은 **"사후에 고칠 수 있다"는 능력으로 지불되고 있는 비용**이다. 방어를 코드에 미리 심는 대신, 문제가 생기면 사람이 개입해서 해결하는 쪽을 택한 것이다.

파트너 API에서는 이 지불 수단이 사라진다. 파트너의 코드는 우리가 못 고치고, 파트너의 배포 일정은 우리가 못 정하고, 파트너의 재시도 로직은 우리가 못 끈다. **사후 개입이 불가능하니, 방어를 사전에 시스템으로 심어야 한다.** 인증·한도·계약·SLA라는 네 층은 전부 여기서 나온다.

한 문장으로 정리하면 이렇다. **내부 API는 "고칠 수 있어서" 느슨한 것이고, 외부 API는 "고칠 수 없어서" 빡빡한 것이다.** 이 인과를 뒤집어 "외부는 위험하고 내부는 안전하다"로 이해하면, 사내에서 벌어지는 사고를 설명하지 못하게 된다.

### 1-3. 통제 불가가 낳는 세 가지 결과

경계 밖의 소비자를 상대한다는 사실은 구체적으로 세 가지 결과를 낳는다.

**하나, 호출 패턴을 예측할 수 없다.** 파트너가 언제 배포하는지, 새 기능이 언제 트래픽을 몇 배로 늘릴지, 실패했을 때 몇 번 재시도하는지 우리는 모른다. 지수 백오프 없이 즉시 재시도를 무한 반복하는 클라이언트가 하나만 있어도 우리 서비스가 흔들린다.

**둘, 악의를 배제할 수 없다.** 여기서 "악의"는 파트너 회사가 나쁘다는 뜻이 아니라, **자격증명이 유출된 순간 그 자격증명을 쥔 쪽이 누구인지 우리는 알 수 없다**는 뜻이다. 파트너 사원의 노트북에서 API 키가 새어 나가면, 그 키로 들어오는 요청은 파트너의 정상 요청과 구별되지 않는다. 계약에 없는 데이터를 대량으로 긁어가는 시도도 마찬가지다.

**셋, 기술 문제가 곧 계약 문제가 된다.** 내부 API 장애는 우리 조직 안의 사고지만, 파트너 API 장애는 **파트너사의 매출 손실**이고 계약서에 적힌 배상 조항의 발동 조건이다. 장애 대응이 기술 대응에서 끝나지 않고 고지·보상·정산까지 이어진다.

정리하면 이렇게 갈린다.

| | 내부 API | 외부 파트너 API |
|---|---|---|
| 소비자 | 같은 조직의 서비스 | 통제 밖의 파트너 시스템 |
| 잘못 호출할 때 | 그 팀에 연락해 고치게 한다 | 고칠 수 없다 — 서버가 막아야 한다 |
| 계약 변경 | 소비자와 합의하면 오늘 가능 | 공지 → 고지 기간 → 이전 확인 → 제거 (몇 달) |
| 자격증명 | 서비스 간 토큰·mTLS, 식별이 목적 | 발급·서명·회수·로테이션까지의 생명주기 |
| 폭주 대응 | 사후 개입 (연락) | 사전 방어 (파트너별 rate limit) |
| 장애의 성격 | 우리 조직 내부 사고 | 파트너 매출 손실 = 계약 분쟁 |
| 약속의 수준 | SLO (내부 운영 목표) | SLA (위반 시 대가가 따르는 계약) |

비유하면 **내부 API는 사무실 안의 구두 회의 약속이고, 외부 파트너 API는 도장을 찍은 계약서다.** 회의 약속은 사정이 생기면 슬랙 한 줄로 바꿀 수 있지만, 계약서는 바꾸려면 상대의 동의와 절차와 기간이 필요하다. 같은 기능을 제공하더라도 이 성격 차이 때문에 설계가 달라진다.

## 2. 네 축의 구체적 설계 — 인증, 한도, 문서, 약속

### 2-1. 인증 — "누구인지"에서 "자격증명의 생명주기"로

**내부**: 게이트웨이나 서비스 메시 뒤의 네트워크 신뢰, 또는 서비스 간 토큰(mTLS, 내부 발급 JWT) 정도로 충분한 경우가 많다. 목적이 **식별**이기 때문이다 — "이 요청이 주문 서비스에서 왔다"만 알면 된다.

**외부**: 식별만으로는 부족하다. 유출·위조·권한 초과·회수까지 전부 설계 범위에 들어온다. 하나씩 풀어 보자.

#### API 키 — 가장 단순하고, 가장 오래 유효한 자격증명

**API 키는 서버가 파트너에게 발급한 긴 무작위 문자열로, 요청 헤더에 그대로 실어 보내는 자격증명이다.** 비밀번호를 매 요청에 붙이는 것과 구조가 같다.

단순해서 연동이 빠르다는 것이 최대 장점이고, 문제도 여기서 나온다. **키는 폐기할 때까지 영원히 유효하다.** 파트너의 로그 파일, 깃 저장소, CI 설정 어딘가에 키가 남아 유출되면, 우리가 그 사실을 알아채고 폐기 버튼을 누르기 전까지 공격자는 그 키를 계속 쓸 수 있다. **유출과 폐기 사이의 시간이 곧 피해 시간**인데, 그 시간이 며칠일지 몇 달일지 우리는 통제할 수 없다.

#### OAuth2 client credentials 그랜트 — 사용자가 없는 서버-대-서버 인증

OAuth2를 처음 접하면 "사용자가 구글 로그인 버튼을 눌러 동의하는 그 화면"이 먼저 떠오른다. **client credentials 그랜트는 그 사용자가 없는 경우를 위한 방식이다.** 파트너 서버가 우리 API를 호출하는 데는 사람이 개입하지 않으므로, 동의 화면도 리다이렉트도 없다. 파트너 시스템이 **자기 자신의 자격**으로 인증한다. 그래서 이름이 "클라이언트(= 애플리케이션) 자격증명"이다.

흐름은 두 단계다. 먼저 client id/secret으로 **수명이 짧은 액세스 토큰**을 받고, 그다음 그 토큰으로 API를 호출한다.

```text
[파트너 서버]                                    [우리 인증 서버]        [우리 API 서버]
     │                                                 │                      │
     │ ① POST /oauth2/token                            │                      │
     │    grant_type=client_credentials                │                      │
     │    client_id=partner-a                          │                      │
     │    client_secret=**** (또는 Basic 인증 헤더)     │                      │
     │    scope=content:read content:write             │                      │
     │────────────────────────────────────────────────▶│                      │
     │                                                 │ secret 검증           │
     │                                                 │ 파트너에게 허용된      │
     │                                                 │ scope인지 확인        │
     │ ② 200 OK                                        │                      │
     │    { "access_token": "eyJ...",                  │                      │
     │      "token_type": "Bearer",                    │                      │
     │      "expires_in": 3600,        ← 1시간 뒤 만료   │                      │
     │      "scope": "content:read" }  ← 실제 부여된 범위 │                      │
     │◀────────────────────────────────────────────────│                      │
     │                                                 │                      │
     │ ③ GET /partner/v1/contents                                             │
     │    Authorization: Bearer eyJ...                                        │
     │───────────────────────────────────────────────────────────────────────▶│
     │                                                 토큰 서명·만료·scope 검증 │
     │ ④ 200 OK                                                               │
     │◀───────────────────────────────────────────────────────────────────────│
     │                                                                        │
     │ ⑤ 1시간 뒤 토큰 만료 → ①부터 다시 (client secret은 그대로 재사용)         │
```

여기서 client secret과 액세스 토큰의 **역할 분리**를 정확히 봐야 한다. secret은 **인증 서버에만, 한 시간에 한 번** 제시되고 API 서버로는 절대 가지 않는다. 반면 API 서버로 매번 오가는 것은 **한 시간 뒤에 저절로 죽는 토큰**이다. 노출 빈도가 높은 쪽을 수명이 짧은 것으로 바꿔 놓은 구조다.

API 키와 무엇이 달라지는지 표로 대비하면 이렇다.

| | API 키 | OAuth2 client credentials |
|---|---|---|
| 매 요청에 실리는 것 | 장기 자격증명 그 자체 | 수명 짧은 액세스 토큰 |
| 유출됐을 때 | 우리가 폐기할 때까지 **영원히** 유효 | 만료 시각(예: 1시간)에 **저절로** 무효화 |
| 권한 범위 | 표준에 없음 — 직접 만들어 붙여야 한다 | `scope`가 토큰 안에 담겨 표준으로 전달됨 |
| 요청당 검증 비용 | 저장소에서 키 조회 | 토큰 서명 검증(자체 검증 가능, 조회 불필요) |
| 즉시 회수 | 키 폐기로 즉시 (다음 요청부터 차단) | 이미 발급된 토큰은 만료까지 유효 — 즉시 끊으려면 별도 장치 필요 |
| 파트너 쪽 구현 부담 | 헤더 하나 추가 | 토큰 발급·캐싱·만료 갱신 로직 필요 |
| 우리 쪽 운영 부담 | 키 저장소 | 토큰 발급 서버가 운영 대상으로 추가됨 |

**"유출됐을 때" 행이 이 표의 핵심이다.** API 키는 피해 시간이 "우리가 알아챌 때까지"이고, 토큰은 "최대 만료 시간까지"다. 전자는 통제 불가능한 값이고 후자는 우리가 정한 값이다. **통제 불가능한 위험을 통제 가능한 값으로 바꾸는 것**이 이 전환의 본질이다.

마지막 행의 반대 방향 트레이드오프도 함께 알아야 한다. **자체 검증 가능한 토큰(JWT 형태)은 발급된 뒤에는 서버가 조회 없이 서명만 보고 통과시키므로, 반대로 "지금 즉시 이 파트너를 끊어라"가 어렵다.** 만료 시간을 짧게(15분~1시간) 잡거나, 폐기 목록을 별도로 조회하는 절충이 필요하다. 이 대가를 알고 만료 시간을 정했는지가 설계의 깊이를 가른다.

#### 키 로테이션 — "교체가 곧 장애"가 되지 않게

**로테이션(rotation, 순환 교체)은 자격증명을 주기적으로 새것으로 바꾸는 절차다.** 유출을 사후에 알아채기 어려우므로, 알아채지 못한 유출까지 시간이 지나면 무력화되도록 미리 갈아 끼우는 것이다.

문제는 **파트너가 언제 새 키를 적용할지 우리가 정할 수 없다**는 점이다. 옛 키를 폐기하는 순간 새 키로 안 바꾼 파트너는 전부 401을 맞는다. 그래서 **둘 다 유효한 겹침 기간(overlap window)을 반드시 둔다.**

```text
  ①  새 키 발급        ②  겹침 기간(예: 30일)         ③  이전 확인      ④  옛 키 폐기
      ─────────────    ─────────────────────────      ────────────     ─────────────
  옛 키  ████████████████████████████████████████████████████████████░
  새 키              ░████████████████████████████████████████████████████████████▶
                     ↑                                ↑                ↑
                     파트너에게 새 키 전달·공지          옛 키 호출 수 0   여기서 옛 키를
                     (양쪽 다 통과하는 구간 시작)        인 것을 지표로    비활성화한다
                                                       확인             (이때가 되어야 안전)
```

③단계가 절차의 핵심이다. **"공지했으니 됐겠지"가 아니라 "옛 키로 들어오는 호출이 실제로 0"이라는 지표를 보고** 폐기한다. 그러려면 키 단위 호출량이 대시보드에 있어야 한다 — 측정이 없으면 이 절차 자체가 성립하지 않는다.

이 겹침을 지원하려면 저장소가 **파트너당 자격증명 여러 개**를 가질 수 있어야 한다. "파트너 테이블에 secret 컬럼 하나"로 설계하면 겹침이 구조적으로 불가능해지고, 그 순간 로테이션은 계획된 장애가 된다.

#### HMAC 요청 서명 — 본문이 안 바뀌었고, 비밀키를 아는 쪽이 보냈다

키나 토큰은 "누구인가"만 증명한다. 그런데 그 요청이 **중간에서 바뀌지 않았다**는 것과 **한 번 훔친 요청을 그대로 다시 보낸 것이 아니다**는 것은 별개 문제다. 정산 금액이나 콘텐츠 전송 같은 API에서는 이 둘도 증명해야 한다.

**HMAC(Hash-based Message Authentication Code)은 메시지와 비밀키를 함께 넣어 만든 해시값이다.** 해시는 입력이 1비트만 달라져도 완전히 다른 값이 나오므로 **본문이 바뀌면 값이 달라지고**, 비밀키를 모르면 그 값을 계산할 수 없으므로 **비밀키를 아는 쪽이 만들었다는 것**이 함께 증명된다. 이 두 가지를 한 값으로 증명하는 것이 요청 서명이다.

파트너는 요청을 보낼 때 정해진 규칙으로 문자열을 조립하고, 그것을 비밀키로 HMAC 해서 헤더에 싣는다.

```text
[서명 대상 문자열 — 양쪽이 똑같은 규칙으로 조립해야 한다]

  POST\n                              ← HTTP 메서드
  /partner/v1/settlements\n           ← 경로
  1774022400\n                        ← 타임스탬프 (요청 시각, epoch seconds)
  9f2c...a71b\n                       ← nonce (요청마다 새로 만드는 1회용 난수)
  e3b0c44298fc1c14...                 ← 요청 본문의 SHA-256 해시

        │ HMAC-SHA256(위 문자열, 파트너의 비밀키)
        ▼
  X-Signature: 5d41402abc4b2a76b9719d911017c592...
  X-Timestamp: 1774022400
  X-Nonce:     9f2c...a71b
```

서버는 같은 규칙으로 문자열을 다시 조립하고 자기가 보관한 비밀키로 HMAC을 계산해, 헤더의 값과 **일치하는지**만 본다. 일치하면 본문이 그대로이고 발신자가 비밀키를 안다는 뜻이다.

**타임스탬프와 nonce가 서명 대상에 들어가는 이유**는 **재전송 공격(replay attack)** 때문이다. 공격자가 정상 요청 하나를 통째로 가로채 그대로 다시 보내면, 서명은 완벽하게 유효하다 — 본문도 그대로고 서명도 그대로이니까. 이것을 막으려면 요청마다 값이 달라지는 무언가가 서명 안에 있어야 한다.

- **타임스탬프**: 서버는 "현재 시각과 5분 이상 차이 나는 요청은 거부"한다. 재전송의 유효 기간을 5분으로 좁힌다.
- **nonce**(number used once, 1회용 숫자): 요청마다 새로 만드는 난수다. 서버는 최근 5분간 본 nonce를 저장해 두고, **같은 nonce가 다시 오면 거부**한다. 타임스탬프가 좁혀 놓은 5분 안쪽마저 막는 장치다.

둘이 짝인 이유가 여기서 나온다. **타임스탬프는 nonce 저장소의 크기를 5분치로 한정해 주고, nonce는 그 5분 안의 재전송을 막는다.** 타임스탬프만 있으면 5분 안에는 재전송이 통하고, nonce만 있으면 저장소를 영원히 키워야 한다.

한 가지 성질은 정확히 알아 두는 것이 좋다. **HMAC은 양쪽이 같은 비밀키를 공유하는 대칭 방식이므로, "파트너가 보냈다"를 우리에게 증명할 뿐 제3자에게 증명하지는 못한다** — 우리도 같은 서명을 만들 수 있기 때문이다. 법적 부인 방지까지 필요하면 파트너의 개인키로 서명하는 비대칭 방식을 써야 한다. 실무에서 HMAC이 표준처럼 쓰이는 이유는 이 정도 보증이면 충분한 경우가 대부분이고 구현·검증 비용이 훨씬 싸기 때문이다.

#### 권한 범위(scope) — 파트너마다 열어 주는 문이 다르다

파트너마다 계약이 다르다. "A사는 콘텐츠 조회만, B사는 등록까지, C사는 정산 데이터까지"처럼 **키별로 접근 가능한 리소스를 처음부터 모델링**해야 한다. 나중에 붙이려 하면 이미 모든 키가 모든 API를 호출할 수 있는 상태이므로, 어느 파트너가 무엇을 쓰고 있는지부터 조사해야 하고 조사 중에 잘못 잠그면 파트너 장애가 된다.

여기에 보조 수단으로 **IP 허용 목록**(파트너 서버의 고정 IP에서만 허용)과 **TLS 필수**를 겹친다. 어느 하나가 뚫려도 다른 층이 남게 하는 구성이다.

```java
// Before: 내부 감각으로 만든 외부 API — 키 하나로 전부 통과한다
if (!apiKey.equals(request.getHeader("X-Api-Key"))) throw new Unauthorized();
// 문제 1: 전 파트너가 같은 키를 쓴다 -> 누가 호출했는지 구분할 수 없다.
// 문제 2: 한 파트너에서 유출돼도 그 파트너만 끊을 방법이 없다
//         (키를 바꾸면 전 파트너가 동시에 끊긴다).
// 문제 3: 권한 구분이 없다 -> 조회만 계약한 파트너가 등록 API도 호출할 수 있다.
// 문제 4: 본문 변조·재전송을 탐지할 수단이 전혀 없다.

// After: 파트너별 자격증명 + 서명 검증 + 권한 범위 + 파트너 단위 감사
PartnerCredential cred = credentialRepository.findActiveByKeyId(keyId);
// keyId로 조회한다 — 파트너별로 행이 따로 있어야 한 파트너만 회수할 수 있고,
// 로테이션 겹침 기간에는 같은 파트너의 활성 자격증명이 둘일 수 있다.

signatureVerifier.verify(cred.secret(), timestamp, nonce, body, signature);
// 본문 변조(해시 불일치)와 재전송(타임스탬프 만료·nonce 중복)을 한 번에 막는다.

cred.requireScope("content:read");
// 계약된 범위 밖의 호출은 401(누군지 모름)이 아니라 403(누군지는 알지만 권한 없음)이다.

partnerAuditLog.record(cred.partnerId(), request);
// 파트너 단위 감사 로그가 있어야 "언제 무엇을 호출했는가"로 분쟁에 답할 수 있고,
// 키 로테이션의 "옛 키 호출 수 0" 확인도 이 로그에서 나온다.
```

### 2-2. Rate limit — 보호 장치이자 상품 조건

**내부**: 없거나 느슨하다. 폭주하면 그 팀에 연락하면 되기 때문이다. 그래도 서비스 보호용 전역 한도 하나는 두는 것이 좋다.

**외부**: 필수이고, **두 가지 성격을 동시에 가진다.** 이 이중성이 이 절의 핵심이다.

#### 성격 하나 — 보호: 파트너 사이의 격벽

파트너 한 곳의 버그(재시도 폭풍, 잘못 배포된 배치)가 우리 서비스와 **다른 파트너까지** 죽이는 것을 막는 격벽이다. 그래서 한도는 반드시 **파트너(키)별로** 건다.

전역 한도만 두면 어떻게 되는지가 중요하다. 한 파트너가 전체 쿼터를 혼자 소진해 버리면, 아무 잘못도 하지 않은 다른 파트너들이 429를 맞는다. 이렇게 **한 사용자의 과소비가 옆 사용자의 서비스 품질을 떨어뜨리는 현상을 noisy neighbor(시끄러운 이웃)라고 부른다** — 얇은 벽 하나를 사이에 둔 옆집이 시끄러우면 내가 잠을 못 자는 것과 같아서 붙은 이름이다. 파트너별 한도는 그 벽을 두껍게 만드는 일이다.

#### 성격 둘 — 상품 조건: 한도는 계약서의 항목이다

"분당 몇 회, 일 몇 회"는 기술 파라미터가 아니라 **요금제 항목**이다. 무료 플랜은 분당 60회, 유료 플랜은 분당 600회 같은 식으로 계약서에 적힌다. 그리고 계약이 되려면 **초과했을 때 무슨 일이 일어나는지도 계약이어야 한다.**

여기서 이 문서가 진짜로 말해야 하는 지점이 나온다. **파트너가 자기 소진량을 볼 수 없으면, 한도는 상품 조건이 될 수 없다.**

이유는 단순하다. 계약서에 "분당 600회"라고 적혀 있어도, 파트너의 클라이언트 코드는 지금 자기가 몇 번째 호출을 하고 있는지 알 방법이 없다. 여러 프로세스가 병렬로 호출한다면 더욱 그렇다. 남은 여유를 알 수 없으면 파트너가 할 수 있는 일은 **벽에 부딪혀 보는 것뿐**이고, 그러면 한도는 "지킬 수 있는 조건"이 아니라 "가끔 얻어맞는 벌칙"이 된다.

그래서 응답 계약이 한도의 절반을 차지한다.

| 응답 요소 | 무엇을 알려 주는가 | 언제 내려보내는가 |
|---|---|---|
| `429 Too Many Requests` | "한도를 넘겼다" — 요청 내용이 아니라 **타이밍**의 문제라서 4xx인데도 재시도 대상이다 | 한도 초과 시 |
| `Retry-After: 12` | "12초 뒤에 다시 오라" — 이 값이 없으면 클라이언트가 할 수 있는 것은 즉시 재시도뿐이고, 거절이 새로운 부하가 된다 | 429와 함께 |
| `RateLimit-Limit: 600` | 이 창(window)에 허용된 총 요청 수 = 계약된 한도 | **성공 응답에도 매번** |
| `RateLimit-Remaining: 137` | 지금 이 창에 남은 여유 — 파트너가 벽에 닿기 전에 스스로 속도를 줄일 수 있게 하는 값 | **성공 응답에도 매번** |
| `RateLimit-Reset: 43` | 카운터가 리셋되기까지 남은 시간(초) — "언제 다시 채워지는가" | **성공 응답에도 매번** |

**표에서 "성공 응답에도 매번"이 붙은 세 줄이 한도를 상품 조건으로 만드는 부분이다.** 429가 난 뒤에야 알려 주면 파트너는 벽에 부딪히고 나서야 벽의 위치를 알게 된다. 매 응답에 남은 여유를 실어 주면 파트너 클라이언트는 여유가 줄어드는 것을 보고 스스로 감속할 수 있다.

헤더 이름에 대해서는 현황을 정확히 알아 두는 것이 좋다. **`RateLimit-*` 계열은 IETF에서 표준화가 진행 중인 초안(`draft-ietf-httpapi-ratelimit-headers`)이고 아직 RFC로 확정되지 않았다.** 초안 자체도 개정을 거치며 세 개의 개별 헤더에서 `RateLimit`이라는 구조화 필드 하나(+ 정책을 알리는 `RateLimit-Policy`)로 통합되는 방향으로 바뀌었다. 현장에서 실제로 가장 많이 보이는 것은 여전히 GitHub 등이 쓰는 `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset` 관행이다. **중요한 것은 이름이 아니라 "한도·잔량·리셋 시각 세 정보를 매 응답에 실어 준다"는 계약**이고, 어느 이름을 택하든 문서에 못 박아야 한다.

`429`와 `Retry-After`는 상황이 다르다. 429는 RFC 6585에서, `Retry-After`는 HTTP 명세(RFC 9110)에서 정의된 확정 표준이므로 이름을 고민할 필요가 없다.

**한도를 정하는 알고리즘(token bucket, sliding window, 분산 환경의 카운터 원자성)은 07장 `07-traffic-performance/08-rate-limiting-algorithms-distributed.md`가 다룬다.** 이 문서에서 다루는 것은 그 위에 얹히는 **계약 면** — 누구 단위로 걸고, 무엇을 응답으로 약속하고, 어떻게 문서에 적을 것인가 — 다.

### 2-3. 문서화 — 참고자료에서 계약서로

**내부**: 코드와 테스트가 문서 역할을 겸할 수 있다. 애매하면 소비자 팀에 물어보면 되고, 문서가 조금 낡아도 슬랙 한 번으로 해결된다. **문서의 오류를 사람이 메워 준다.**

**외부**: 파트너 개발자는 **문서만 보고 구현한다.** 우리 코드를 볼 수 없고, 애매한 부분을 물어보려면 이메일과 미팅이 필요하다. 그래서 문서가 틀리면 연동 자체가 실패하고, 그 비용은 연동 일정 지연과 반복 미팅으로 돌아온다. **문서가 참고자료가 아니라 구현의 유일한 근거**가 되는 것이 이 차이의 본질이다.

그래서 갖춰야 할 것이 달라진다.

- **개발자 포털 수준의 문서**: 요청·응답 스키마, 에러 코드 표, rate limit 정책(2-2의 헤더 계약 포함), 인증 방법, 호출 예제까지. 파트너가 "이 필드가 null일 수 있나요?"를 물어보지 않아도 되는 수준이 목표다.
- **변경 로그(changelog)와 버전 정책**: 파트너는 "언제 무엇이 바뀌는지"를 문서로만 알 수 있다. 변경 로그가 없으면 파트너는 장애가 나고 나서야 변경을 알게 된다. 버전 전략 자체는 03번 문서(`03-api-versioning-strategies.md`), 무엇이 파괴적 변경인지는 08번 문서(`08-backward-compatible-api-changes.md`)가 다룬다.
- **샌드박스(테스트 환경)와 테스트 키** (가산점 포인트): 파트너가 운영 데이터 없이 연동을 검증할 수 있어야 한다. 샌드박스가 없으면 파트너의 첫 통합 테스트가 우리 운영 환경에서 벌어진다.

그리고 문서가 계약서라면 **문서와 구현이 어긋나는 것은 계약 위반**이다. 사람의 성실함에 기대지 말고 체계로 보장해야 한다 — 코드에서 스펙을 뽑을 것인지(springdoc-openapi), 테스트가 통과해야만 문서가 나오게 할 것인지(Spring REST Docs), 스펙을 먼저 쓰고 구현을 검증할 것인지(contract-first)의 선택이 여기서 나온다. 이 주제는 15번 문서(`15-api-docs-implementation-sync.md`)가 전부 다룬다.

### 2-4. SLA / SLO / SLI — 세 글자의 차이가 곧 책임의 차이

**내부**: 장애가 나면 같이 고친다. 공식 계약 없이 운영 목표(SLO) 수준으로 관리한다.

**외부**: 가용성·성능·지원이 **계약 항목**이 된다. 그런데 이 영역의 용어 셋이 자주 뒤섞여 쓰이므로, 먼저 구분부터 정확히 하고 간다. 셋은 같은 것의 다른 이름이 아니라 **측정 → 목표 → 약속**이라는 다른 층위다.

| | 이름 | 무엇인가 | 예시 | 어겼을 때 |
|---|---|---|---|---|
| SLI | Service Level **Indicator** (지표) | 실제로 **측정하는 숫자**. 정의가 곧 계측 방법이다 | 5분 단위로 집계한 `성공 응답 수 ÷ 전체 요청 수` | 어긴다는 개념이 없다 — 측정값일 뿐 |
| SLO | Service Level **Objective** (목표) | 그 지표가 **얼마여야 하는가**에 대한 우리 내부의 목표 | 월간 가용률 99.95% 이상 | 내부 경보 — 아직 계약 위반은 아니다 |
| SLA | Service Level **Agreement** (합의·계약) | 파트너와 맺은 **약속**. 어기면 **대가**가 따른다 | 월간 가용률 99.9% 미만이면 이용료의 10% 크레딧 | 환불·크레딧·해지 사유 |

**SLI가 없으면 나머지 둘은 존재할 수 없다**는 순서를 먼저 짚어야 한다. "가용률 99.9%를 약속한다"는 말은 가용률을 **어떻게 세는지**가 정해져야 의미가 생긴다. 5xx만 실패로 볼 것인가, 타임아웃도 포함할 것인가, 파트너 쪽 네트워크 문제로 도달하지 못한 요청은 어떻게 셀 것인가, 어느 지점(로드밸런서? 애플리케이션?)에서 잴 것인가. 이것을 정하는 것이 SLI이고, **정의가 다르면 같은 시스템이 다른 숫자를 낸다.**

이제 왜 **SLA를 SLO보다 반드시 느슨하게** 잡아야 하는지를 숫자로 보자. 30일 기준으로 계산한다.

```text
한 달(30일)의 총 분 = 30 × 24 × 60 = 43,200분

  SLA 99.9%  로 약속하면 → 계약 위반선 = 43,200 × 0.001  = 43.2분/월
  SLO 99.95% 로 관리하면 → 내부 경보선 = 43,200 × 0.0005 = 21.6분/월
                            (= SLO가 허용하는 실패 총량 — 이것을 에러 예산이라 부른다)

  두 선 사이의 완충 구간 = 43.2 − 21.6 = 21.6분
```

용어를 정확히 구분해 두자. **에러 예산(error budget)은 "SLO가 허용하는 실패의 총량"**이다. 99.95%를 목표로 잡았다면 나머지 0.05%, 즉 월 21.6분이 우리가 써도 되는 예산이고, 이것을 다 쓰면 새 기능 배포를 멈추고 안정화에 집중하는 식으로 운영 판단에 쓴다. 이 예시에서 완충 구간이 21.6분으로 같은 값이 나온 것은 SLO를 SLA의 정확히 두 배 엄격도로 잡았기 때문이지, 둘이 같은 개념이라서가 아니다.

이제 그 **완충 구간이 하는 일**을 보자. **다운타임이 21.6분을 넘긴 시점에는 아직 계약 위반이 아니다.** 우리는 여기서 경보를 받고, 배포를 멈추고, 원인을 찾을 21.6분을 더 갖는다. **위반하기 전에 개입할 시간을 구조적으로 확보하는 것**이 SLO를 더 엄격하게 잡는 첫 번째 이유다.

두 번째 이유는 계측 자체가 완벽하지 않다는 데 있다. 우리 대시보드의 숫자와 파트너가 자기 쪽에서 재는 숫자는 **반드시 다르다.** 측정 지점이 다르고(우리는 로드밸런서, 파트너는 자기 애플리케이션), 파트너 쪽 네트워크 구간의 실패가 우리 지표에는 안 잡히고, 집계 창의 경계도 서로 어긋난다. 우리 지표로 99.92%인데 파트너 지표로는 99.88%일 수 있다. **SLA를 우리 SLO에 딱 붙여 놓으면 이 오차만큼 분쟁이 난다.**

그래서 규칙은 한 문장이다. **SLA는 SLO보다 느슨하게 — 그 간격이 계측 오차를 흡수하고 개입할 시간을 만든다.** 반대로 SLA와 SLO를 같은 값으로 잡은 계약서를 보면, 그것은 완충이 0이라는 뜻이고 내부 경보가 울리는 순간이 곧 계약 위반이라는 뜻이다.

SLA에 함께 들어가는 항목도 가용률만이 아니다.

- **장애 고지 채널과 시점**: 파트너가 장애를 우리 상태 페이지에서 아는 것과, 자기 CS로 문의가 들어와서 아는 것은 신뢰의 차이가 크다. 고지 시점("탐지 후 30분 내")까지 계약에 적히는 경우가 많다.
- **점검(maintenance) 사전 고지**와 **파괴적 변경·폐기의 사전 통보 기간**(예: 6개월 전): 이 조항이 들어가는 순간 **API 폐기는 기술 결정이 아니라 계약 이행 문제**가 된다.
- **지원 채널과 응답 시간 약속**: 문의 접수 창구와 1차 응답까지의 시간.

그리고 이 모든 것이 성립하려면 **파트너별 트래픽·에러율·지연시간 모니터링**이 먼저 있어야 한다 (가산점 포인트). "어느 파트너에게 몇 %의 에러를 줬는지"를 파트너 단위로 나눠 볼 수 없으면, 전체 에러율이 0.05%여도 특정 파트너에게만 3%를 주고 있었을 수 있다. **측정 단위가 계약 단위와 일치하지 않으면 SLA는 약속이 아니라 희망이다.**

## 3. 실무 사례 — 공개는 한 방향 문이다

### 사례 1: 전역 한도만 있던 날 — 파트너 A의 배치가 파트너 B를 죽였다

콘텐츠 연동 API에 전역 한도(전체 분당 5,000회)만 걸려 있었다. 어느 날 새벽, 파트너 A가 신간 30,000건을 우리 쪽에 동기화하는 배치를 돌렸다. 건당 1회 호출을 3분 안에 몰아 보내는 구현이었다.

숫자를 계산해 보면 무슨 일이 벌어졌는지 바로 보인다. 파트너 A의 계약 한도는 분당 600회였다.

```text
파트너 A의 실제 호출 속도 = 30,000건 ÷ 3분 = 10,000회/분
계약 한도                 = 600회/분
                            ─────────────────────
                            한도의 약 16.7배 (10,000 ÷ 600 = 16.67)

3분 동안 통과한 요청 = 600 × 3 = 1,800건
3분 동안 거절된 요청 = 30,000 − 1,800 = 28,200건   ← 파트너별 한도가 있었다면 이렇게 됐어야 했다
```

그런데 파트너별 한도가 없었으므로 **A의 10,000회/분이 전역 한도 5,000회/분을 통째로 먹었다.** 그 시각에 정상 트래픽을 보내던 파트너 B와 C는 자기 계약 한도의 10분의 1도 안 쓰고 있었는데도 429를 맞았다. **잘못한 쪽이 아니라 나중에 도착한 쪽이 벌을 받은 것**이다. 이것이 2-2에서 말한 noisy neighbor의 실제 모습이다.

대응은 두 방향으로 갈렸다.

**기술 쪽**: 한도를 파트너 키 단위로 재설계했다. 그리고 **성공 응답에도 `RateLimit-Remaining`을 싣기 시작했다** — 파트너 A의 배치가 남은 여유를 보고 스스로 감속할 수 있게 하기 위해서다. 이것이 없으면 파트너는 벽에 부딪히는 것 말고는 감속할 근거가 없다.

**계약 쪽**: 파트너 A에게 배치를 분산하도록 가이드했다. 계산은 간단하다.

```text
30,000건을 분당 600회 한도 안에서 보내려면
  30,000 ÷ 600 = 50분  ← 최소 50분에 걸쳐 나눠 보내야 한다
```

여기에 하나를 덧붙였다. **"매시 정각에 시작"을 금지하고 시작 시각에 지터(무작위 지연)를 넣도록** 요청했다. 여러 파트너의 배치가 전부 정각에 시작하면 우리 쪽에서 보기에는 정각마다 트래픽 절벽이 생긴다. 지수 백오프와 지터의 원리는 07장 `07-traffic-performance/11-retry-storm-backoff-jitter.md`가 다룬다.

**이 사례의 교훈은 한 줄이다. 한도의 단위는 곧 격리의 단위다.** 전역 한도는 우리 서비스를 지키지만 파트너를 서로에게서 지키지 못한다.

### 사례 2: 키를 교체하려 했더니, 교체 자체가 장애였다

파트너 한 곳의 API 키가 공개 저장소의 설정 파일에 올라간 것이 발견됐다. 즉시 폐기해야 하는 상황인데, 여기서 초기 설계의 결함이 드러났다. **파트너 테이블에 `api_key` 컬럼이 하나뿐**이었다.

컬럼이 하나라는 것은 **한 파트너에게 유효한 키가 언제나 정확히 하나**라는 뜻이다. 새 키를 넣으려면 옛 키를 덮어써야 하고, 덮어쓰는 순간 파트너의 운영 시스템이 즉시 401을 맞는다. 파트너가 새 키를 배포하는 데 걸리는 시간(그쪽 배포 주기가 주 1회였다) 동안 연동이 통째로 끊긴다.

**유출 대응이 계획된 장애가 되는 상황**이었고, 그래서 실제로는 "당장 폐기"를 못 하고 파트너 배포 일정에 맞추느라 며칠을 더 유출 상태로 두게 됐다.

구조를 이렇게 바꿨다.

```sql
-- 자격증명을 파트너의 컬럼이 아니라 별도 행으로 분리한다.
-- 핵심은 한 파트너가 활성 자격증명을 둘 이상 가질 수 있게 만드는 것이다 —
-- 겹침 기간이 없으면 로테이션은 언제나 장애다.
CREATE TABLE partner_credential (
    key_id      varchar(40)  PRIMARY KEY,      -- 요청 헤더로 오는 식별자
    partner_id  bigint       NOT NULL,
    secret_hash text         NOT NULL,         -- 원본이 아니라 해시로 보관한다
    scopes      text[]       NOT NULL,
    status      varchar(10)  NOT NULL,         -- ACTIVE | DEPRECATED | REVOKED
    expires_at  timestamptz,                   -- 겹침 기간의 종료 시각
    created_at  timestamptz  NOT NULL DEFAULT now()
);

-- 한 파트너의 활성 자격증명만 빠르게 찾기 위한 부분 인덱스.
-- 폐기된 행이 아무리 쌓여도 인덱스 크기가 커지지 않는다.
CREATE INDEX idx_cred_active ON partner_credential (partner_id)
    WHERE status = 'ACTIVE';
```

`status`가 세 값인 이유를 짚어 두자. **`DEPRECATED`는 "아직 통과시키지만 곧 죽을 키"**다. 이 상태의 키로 들어오는 호출은 정상 처리하되 별도 지표로 카운트한다. 2-1에서 본 로테이션 절차의 ③단계 — "옛 키 호출 수가 0인지 확인" — 이 이 지표로 이뤄진다. `DEPRECATED` 상태 없이 `ACTIVE`/`REVOKED` 둘만 있으면, 폐기 버튼을 누르기 전에 안전한지 확인할 방법이 없다.

**여기서 얻는 일반 규칙은 이것이다. 자격증명 설계에서 "동시에 유효한 값이 하나뿐"이라는 제약은 편의가 아니라 결함이다.** 교체 가능성은 나중에 붙이는 기능이 아니라 처음의 데이터 모델에서 결정된다.

### 사례 3: 내부 모델을 그대로 내보낸 대가

연동을 빨리 열어야 해서 내부 콘텐츠 조회 API의 응답을 그대로 파트너에게 내줬다. 응답 객체는 내부 엔티티를 그대로 직렬화한 것이었고, 거기에는 내부 관리용 필드가 여럿 섞여 있었다 — 내부 등급 코드, 담당 MD의 사번, 다음 개편에서 없어질 예정이던 레거시 카테고리 ID.

여섯 달 뒤 카테고리 체계를 개편하려는데, **파트너 세 곳이 그 레거시 카테고리 ID로 자기 쪽 매핑 테이블을 만들어 놓은 상태**였다. 그 필드는 우리에게는 삭제 예정 필드였지만, 파트너에게는 계약된 필드였다.

여기서 **외부 API의 변경 속도가 내부와 얼마나 다른지**가 드러난다. 내부 API였다면 소비자 팀과 합의해 그 주에 바꿨을 변경이, 외부에서는 이런 절차가 된다.

```text
[내부 API의 필드 삭제]
  소비자 팀과 합의  →  같은 스프린트에 양쪽 배포  →  끝        (며칠)

[외부 파트너 API의 필드 삭제]
  ① 전 파트너 공지 (변경 로그 + 메일)
  ② 계약상 사전 통보 기간 대기               ← 계약서에 적힌 기간 (예: 6개월)
  ③ 새 필드로의 이전을 파트너별로 확인        ← 옛 필드 참조가 실제로 0인지 지표로 확인
  ④ 제거
                                              (몇 달 ~ 1년)
```

이 절차의 기술적 형태 — 새것을 추가하고(expand), 소비자를 이전시키고(migrate), 옛것을 제거하는(contract) 3단계 — 는 08번 문서(`08-backward-compatible-api-changes.md`)가 다룬다. 여기서 중요한 것은 **그 절차가 기술 일정이 아니라 계약 일정에 묶인다**는 점이다.

그래서 외부 공개 전에 반드시 하는 검토가 셋이다.

**하나, 최소 공개 원칙.** 내부 모델을 그대로 노출하지 말고 **외부 전용 응답 모델(DTO)을 별도로 두고 필요한 필드만** 내보낸다. 필드 하나를 더 내보내는 비용은 지금 0이지만, 회수하는 비용은 몇 달이다. **"나중에 추가하는 것은 쉽고 회수하는 것은 어렵다"**는 비대칭이 판단의 근거다.

**둘, 쓰기 API에는 멱등성 키를 계약에 포함한다.** 파트너의 재시도를 우리가 통제할 수 없기 때문이다. 파트너 클라이언트가 타임아웃 후 재시도하는지, 몇 번 하는지 우리는 모른다. 같은 요청이 두 번 와도 결과가 한 번 실행한 것과 같도록 만드는 장치가 멱등성 키이고, 설계는 06번 문서(`06-idempotency-key-design.md`)가 다룬다. **"통제할 수 없는 재시도"라는 전제가 멱등성을 선택이 아니라 필수로 만든다.**

**셋, 내부와 외부가 같은 기능을 쓰더라도 경로를 분리한다.** 외부 전용 엔드포인트나 전용 게이트웨이를 두면 인증·한도·감사 로그 정책을 내부와 독립적으로 걸 수 있고, 파트너 트래픽만 따로 계측할 수 있다(2-4의 SLA 계측이 여기에 기댄다). 게이트웨이와 서비스의 책임 경계는 14번 문서(`14-gateway-vs-service-responsibility-boundary.md`)가 다룬다.

세 가지를 한 문장으로 묶으면 이렇다. **외부 계약 층을 내부 API 위에 어댑터로 얹어라 — 내부는 계속 빠르게 바꾸고, 외부 계약은 안정적으로 유지하는 구조다.**

## 4. 꼬리질문 대비 포인트

### "API 키와 OAuth2 client credentials 중 뭘 쓰나요?"

먼저 둘의 성격을 대비하고 판단 기준을 말한다.

**API 키**는 발급받은 문자열을 매 요청 헤더에 그대로 싣는 방식이다. 연동이 단순해 파트너가 하루면 붙일 수 있다. 대신 **장기 유효 자격증명**이라 유출 시 피해 시간이 "우리가 알아채고 폐기할 때까지"로 무한정 열려 있고, 권한 범위와 만료 개념이 표준에 없어 전부 직접 만들어야 한다.

**OAuth2 client credentials**는 client id/secret으로 수명 짧은 액세스 토큰을 받아 그 토큰으로 호출하는 방식이다. **매 요청에 오가는 것이 한 시간 뒤 저절로 죽는 토큰**이므로 유출 피해가 만료 시간으로 상한이 잡히고, scope와 만료가 표준에 내장돼 있으며, 파트너가 늘어날 때 관리 방식이 표준화된다. 대신 토큰 발급 서버가 운영 대상으로 늘어나고, 파트너 쪽에도 토큰 캐싱·갱신 구현이 필요하다.

**판단 기준은 "파트너 수와 데이터 민감도"다.** 소수 파트너의 단순 조회 연동이면 서명(HMAC)을 동반한 API 키로 충분하고, 파트너가 늘고 쓰기 API나 민감 데이터가 걸리면 OAuth2로 표준화하는 쪽이 관리 비용이 낮다.

한 단계 더 나가려면 **양쪽의 반대 방향 약점**을 짚으면 좋다. API 키는 폐기가 즉시 반영되지만(다음 요청부터 차단) 유출 피해 시간이 길고, 자체 검증형 토큰은 유출 피해 시간이 짧지만 **이미 발급된 토큰을 즉시 끊기는 어렵다**(만료까지 유효하다). 그래서 OAuth2를 쓰더라도 "즉시 차단"이 필요한 도메인이면 만료를 짧게 잡거나 폐기 목록 조회를 얹는 절충이 따라온다.

### "rate limit에 걸린 파트너가 '우리는 정상 트래픽'이라고 항의하면?"

**측정 데이터로 대화한다.** 파트너별 호출량·429 비율·시각별 분포 대시보드가 있어야 "새벽 3시에 3분간 10,000회/분을 보냈고 계약 한도는 600회/분"처럼 구체적으로 보여줄 수 있다. 이 대시보드가 없으면 대화가 "우리는 정상이다" 대 "아니다"의 말싸움이 된다.

원인 규명 다음의 해법은 **기술과 계약 양면**이다. 사례 1처럼 배치 폭주라면 배치를 분산하고 시작 시각에 지터를 넣도록 가이드하고, 실제 트래픽 성장이라면 상위 쿼터로 계약을 조정한다.

여기에 두 가지를 덧붙이면 시야가 넓어 보인다. 하나, **한도 상향은 우리 서비스의 용량 계획과 연동된 결정**이다 — 파트너 한 곳의 한도를 올리려면 그만큼의 여유가 실제로 있어야 하므로 계약과 인프라가 함께 움직인다. 둘, **우리 쪽에도 개선할 것이 있는지 먼저 본다.** 성공 응답에 잔량 헤더를 안 내려보내고 있었다면, 파트너가 감속할 수단을 우리가 안 준 것이다. 이 경우 항의의 절반은 정당하다.

### "내부 API를 그대로 파트너에게 열어주면 안 되나요?" (시니어 변별 포인트)

**가장 빠르지만 가장 비싼 선택**이라는 것부터 말한다. 이유를 셋으로 나눈다.

**하나, 내부 모델과 내부 식별자가 노출된다.** 정보 노출 자체도 문제지만 더 큰 것은 **리팩터링의 족쇄**다. 사례 3에서 본 그대로, 우리에게는 삭제 예정 필드가 파트너에게는 계약된 필드가 된다.

**둘, 변경 속도를 잃는다.** 내부 API는 소비자와 합의만 하면 오늘 바꿀 수 있는 계약인데, 외부가 붙는 순간 같은 API가 몇 달짜리 폐기 절차의 대상이 된다. **그 API를 쓰는 내부 서비스들의 변경 속도까지 함께 묶인다**는 것이 특히 아픈 부분이다.

**셋, 인증·한도·감사가 내부 전제로 설계돼 있다.** 파트너별 격리도, 서명 검증도, 파트너 단위 감사 로그도 없다. 이것들을 나중에 얹으려면 이미 붙어 있는 파트너를 깨지 않으면서 붙여야 한다.

**올바른 형태는 외부 전용 계약 층(전용 DTO·전용 엔드포인트·전용 게이트웨이)을 내부 API 위에 어댑터로 얹는 것**이다 — 내부는 계속 빠르게 바꾸고, 외부 계약은 안정적으로 유지하는 구조다.

마무리로 비가역성을 짚으면 시니어 관점이 드러난다. **공개는 한 방향 문이다.** 되돌릴 수 있는 결정은 빠르게 하고, 되돌릴 수 없는 결정은 느리게 한다는 원칙에서 외부 API 공개는 명백히 후자다.

### "파트너에게 데이터를 밀어줘야 하는 경우(웹훅)는 뭐가 달라지나요?"

**방향이 뒤집히면 역할도 뒤집힌다 — 이번엔 우리가 클라이언트이고 파트너가 서버다.** 그래서 이 문서에서 파트너에게 요구했던 것들을 이번엔 우리가 지켜야 한다.

- 상대 서버가 다운돼 있을 수 있으므로 **재시도가 전제**이고, 재시도하면 **중복 도착이 전제**이므로 파트너는 멱등하게 처리해야 한다 — 우리는 이벤트 ID를 실어 그것을 가능하게 해줘야 한다.
- 파트너가 "이 요청이 진짜 우리한테서 왔는지" 검증할 수 있도록 **서명 헤더(2-1의 HMAC)를 실어 준다.** 2-1에서는 우리가 검증하는 쪽이었고 여기서는 우리가 서명하는 쪽이다.
- 웹훅 수신에 실패한 분량을 파트너가 스스로 복구할 수 있는 **재조회(pull) API를 함께 제공**하면 운영 문의가 크게 준다 (가산점 포인트).

**콜백의 재시도·중복·서명·유실 복구 설계 전체는 10번 문서(`10-long-running-operations-202-polling-callback.md`) 3절이 다룬다.** 이 질문이 나오면 그 문서의 내용으로 답하되, 여기서는 "신뢰 경계를 우리가 넘어가는 쪽이 되면 파트너에게 요구했던 방어를 우리가 제공하는 입장이 된다"는 대칭을 짚는 것이 이 문서의 몫이다.

### "SLA와 SLO는 뭐가 다른가요?"

**SLI → SLO → SLA의 3단으로 답한다** (2-4).

- **SLI**는 실제로 측정하는 **지표**다. `성공 응답 수 ÷ 전체 요청 수` 같은 계산식이고, 어디서 어떻게 재는지가 정의에 포함된다.
- **SLO**는 그 지표가 얼마여야 하는지에 대한 **내부 목표**다. 어겨도 계약 위반은 아니고, 내부 경보가 울린다.
- **SLA**는 파트너와 맺은 **계약**이다. 어기면 크레딧·환불 같은 **대가**가 따른다.

그리고 **SLA를 SLO보다 느슨하게 잡는다는 실무 규칙**과 그 두 가지 이유를 붙이면 정리가 완성된다. 첫째, 그 간격이 **위반 전에 개입할 시간**을 만든다(SLA 99.9%는 월 43.2분까지 허용, SLO 99.95%는 월 21.6분에서 경보 — 그 사이 21.6분이 완충 구간이다). 둘째, 우리 지표와 파트너 지표는 측정 지점과 집계 창이 달라 **반드시 어긋나므로**, 그 오차를 흡수할 폭이 필요하다.

**"내부 API는 SLO까지, 외부 API는 SLA까지 올라간다"**로 한 줄 요약하면 이 문서의 주제와도 이어진다 — 신뢰 경계를 넘는 순간 약속의 층위 자체가 한 칸 올라간다.

## 한 줄 요약

내부 API와 외부 파트너 API의 차이는 기능이 아니라 **신뢰 경계**이고, 내부가 느슨해도 되는 이유는 안전해서가 아니라 **호출자를 우리가 고칠 수 있어서**다 — 고칠 수 없는 소비자를 전제로 인증은 자격증명 생명주기(파트너별 발급, 겹침 기간을 둔 무중단 로테이션, 타임스탬프·nonce를 포함한 HMAC 서명, scope, 즉시 회수)까지, rate limit은 파트너별 쿼터와 `429`+`Retry-After`+매 응답의 잔량 헤더라는 계약까지, 문서는 파트너가 그것만 보고 구현하는 계약서 수준으로, 약속은 SLI·SLO·SLA 3단으로(SLA는 계측 오차와 개입 시간을 위해 SLO보다 느슨하게) 명문화하고, 내부 모델을 직접 노출하지 않는 외부 전용 계약 층을 어댑터로 얹는 것이 핵심이다.
