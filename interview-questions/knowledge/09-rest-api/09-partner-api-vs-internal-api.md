# 외부 파트너 API vs 내부 API — 신뢰 경계가 바뀌면 설계가 바뀐다

> 핵심 관전 포인트: **둘의 차이는 기능이 아니라 신뢰 경계다. 내부 API는
> "같은 조직이 통제하는 소비자"를 전제로 단순 인증·관대한 계약·빠른 변경이
> 가능하지만, 외부 파트너 API는 통제 밖의 소비자와 맺는 기술 계약이라
> ① 인증은 키 발급·서명·회수 체계까지, ② rate limit은 파트너별 쿼터와
> 429 응답 계약까지, ③ 문서는 참고자료가 아니라 계약서 수준으로,
> ④ SLA는 가용성 약속·장애 고지·변경 사전 통보 기간까지 명문화해야 한다.
> 한 번 공개하면 회수 비용이 극도로 크므로 "최소한으로 공개하고,
> 처음부터 버전·폐기 절차를 설계에 포함"하는 것이 원칙이다.**

---

## 0. 질문 + 의도

**질문**: "외부 파트너사에 제공하는 API(콘텐츠 연동)와 내부 API 설계의
차이점은? (인증, rate limit, 문서화, SLA)"

**출제 의도**: 신뢰 경계가 바뀌면 설계가 바뀐다(인증 강화, rate limit,
문서가 곧 계약)는 것을 아는지 본다. 콘텐츠 연동 업무의 실제 형태라,
외부와의 기술 계약을 다뤄본 경험을 검증한다.

## 1. 본질 — "누가 소비하는가"가 모든 설계를 결정한다

내부 API의 소비자는 **같은 조직**이다. 문제가 생기면 슬랙으로 부르면 되고,
같이 배포 일정을 맞출 수 있고, 코드도 서로 볼 수 있다. 반면 외부 파트너
API의 소비자는:

- **내가 통제할 수 없다** — 언제 배포하는지, 어떻게 호출하는지, 재시도를
  어떻게 구현했는지 모른다.
- **악의적일 수 있다** — 키가 유출될 수 있고, 버그로 초당 수천 번 호출할 수
  있고, 계약 밖의 데이터를 긁으려 할 수 있다.
- **비즈니스 관계다** — API 장애가 곧 파트너사의 매출 문제, 즉 계약 분쟁이
  될 수 있다.

그래서 같은 기능이라도 외부용은 **방어(인증·rate limit)**,
**계약(문서·버전)**, **약속(SLA)**의 세 층이 추가된다. 비유하면 내부 API는
사무실 안의 회의 약속이고, 외부 API는 도장 찍는 계약서다.

## 2. 네 가지 축의 구체적 차이

### ① 인증 — "누구인지"에서 "누구인지 + 위조·유출 대응"으로

내부: 게이트웨이/서비스 메시 뒤의 네트워크 신뢰, 또는 서비스 간 토큰
(mTLS, 내부 발급 JWT) 정도로 충분한 경우가 많다. 핵심은 식별이다.

외부: **자격증명의 전체 생명주기**를 설계해야 한다.

- **발급·회수**: 파트너별 API 키 또는 OAuth2 client credentials.
  "키를 어떻게 전달하고, 유출 시 어떻게 즉시 무효화하고, 어떻게 무중단으로
  교체(rotation)하는가"까지가 설계 범위다. 키 두 개를 동시에 유효하게 하는
  겹침 교체를 지원하지 않으면 파트너는 키 교체 = 장애가 된다.
- **위조 방지**: 단순 키는 탈취되면 끝이므로, 중요한 API(정산, 콘텐츠 전송)는
  요청 본문·타임스탬프를 비밀키로 서명(HMAC)하게 해서 재전송 공격(replay)과
  변조를 막는다. 결제사 웹훅들이 서명 헤더를 주는 것과 같은 원리다.
- **권한 범위(scope)**: 파트너마다 접근 가능한 리소스가 다르다 — "A사는
  콘텐츠 조회만, B사는 등록도" 같은 키별 권한을 처음부터 모델링한다.
- 보조 수단: IP 허용 목록, TLS 필수.

```java
// Before: 내부 감각으로 만든 외부 API — 키 하나로 전부 통과
if (!apiKey.equals(request.getHeader("X-Api-Key"))) throw new Unauthorized();
// 문제: 전 파트너가 같은 키 / 유출돼도 회수 불가 / 누가 호출했는지 구분 불가

// After: 파트너별 키 + 서명 검증 + 권한 범위
PartnerCredential cred = credentialRepository.findActiveByKeyId(keyId); // 파트너별, 회수 가능
signatureVerifier.verify(cred.secret(), timestamp, body, signature);    // 변조·재전송 방지
cred.requireScope("content:read");                                      // 키별 권한
partnerAuditLog.record(cred.partnerId(), request);                      // 파트너 단위 감사 로그
```

### ② Rate limit — 보호 장치이자 상품 조건

내부: 없거나 느슨하다. 폭주하면 그 팀에 연락하면 된다 (그래도 서비스 보호용
전역 한도는 두는 게 좋다).

외부: **필수**이고, 두 가지 성격을 동시에 가진다.

- **보호**: 파트너 한 곳의 버그(재시도 폭풍)가 내 서비스와 다른 파트너까지
  죽이는 것을 막는 격벽. 반드시 **파트너(키)별로** 건다 — 전역 한도만 있으면
  한 파트너가 전체 쿼터를 소진해 다른 파트너가 피해를 본다(noisy neighbor).
- **계약 조건**: "분당 몇 회, 일 몇 회"는 요금제·계약서의 항목이다.
  초과 시의 동작도 계약이다 — `429 Too Many Requests` + `Retry-After` 헤더,
  남은 쿼터를 알려주는 응답 헤더(예: remaining/reset 계열)까지 문서화해야
  파트너가 클라이언트를 올바르게 구현할 수 있다.

한도를 "정하는 것"보다 "**어떻게 초과를 알려주고 어떻게 회복하게 하는가**"가
설계의 본체라고 답하면 좋다.

### ③ 문서화 — 참고자료에서 계약서로

내부: 코드·테스트가 곧 문서 역할을 겸할 수 있고, 불일치는 슬랙 한 번으로
해결된다.

외부: 파트너 개발자는 **문서만 보고 구현한다.** 내 코드를 볼 수 없으므로
문서가 틀리면 연동 자체가 실패하고, 그 비용은 미팅·이메일·연동 일정 지연으로
돌아온다. 그래서:

- 요청/응답 스키마, 에러 코드 표, rate limit 정책, 인증 방법, 예제까지
  포함한 **개발자 포털** 수준의 문서가 필요하다.
- **변경 로그(changelog)와 버전 정책**이 문서의 일부다 — 파트너는 "언제 뭐가
  바뀌는지"를 문서로만 알 수 있다.
- **샌드박스(테스트 환경)와 테스트 키** 제공 — 파트너가 운영 데이터 없이
  연동을 검증할 수 있어야 연동 기간이 짧아진다 (가산점 포인트).
- 문서-구현 일치를 체계로 보장해야 한다 (→ 이 카테고리 15번 문서,
  Swagger vs REST Docs).

### ④ SLA — 암묵적 기대에서 명문화된 약속으로

내부: 장애 나면 같이 고친다. 공식 SLA 없이 운영 목표(SLO) 수준으로 관리.

외부: **가용성·성능·지원이 계약 항목**이 된다.

- 가용성 목표(예: 월 가용률), 위반 시 보상 조건.
- **장애 고지 채널과 시점** — 장애를 파트너가 CS로 먼저 아는 것과 상태
  페이지/공지로 먼저 아는 것은 신뢰 차이가 크다.
- **점검(maintenance) 사전 고지**, **파괴적 변경·폐기의 사전 통보 기간**
  (예: 몇 개월 전 고지)이 계약서에 들어간다 — 즉 API 폐기 절차가 기술
  결정이 아니라 계약 이행 문제가 된다.
- 지원 채널: 문의 접수 창구, 응답 시간 약속.

SLA를 지키려면 역으로 **파트너별 트래픽·에러율 모니터링**이 필요하다 —
"어느 파트너에게 몇 %의 에러를 줬는지" 측정할 수 없으면 SLA는 약속이 아니라
희망이다 (가산점 포인트).

## 3. 실무 감각 — 계약 안정성이 최우선 설계 제약

콘텐츠 연동처럼 외부에 API를 내주는 순간, 가장 크게 달라지는 것은
**변경 속도**다. 내부 API는 소비자와 합의하면 오늘 바꿀 수 있지만, 외부 API의
파괴적 변경은 "전 파트너 공지 → 계약상 고지 기간 → 이전 확인 → 제거"라는
몇 달짜리 절차가 된다 (→ 08번 문서, expand-migrate-contract).

그래서 외부 공개 전 검토가 실무 요령이다:

- **최소 공개 원칙**: 내부 모델을 그대로 노출하지 말고, 외부 전용
  응답 모델(DTO)을 별도로 두고 필요한 필드만 내보낸다. 내부 필드가 한 번
  나가면 회수에 몇 달이 걸린다.
- **멱등성 요구**: 파트너의 재시도를 통제할 수 없으므로, 쓰기 API는
  멱등성 키를 계약에 포함시킨다.
- 내부와 외부가 같은 기능을 쓰더라도 **경로를 분리**(외부 전용 게이트웨이/
  엔드포인트)해서 인증·한도·감사 로그 정책을 독립적으로 걸 수 있게 한다.

## 4. 꼬리질문 대비 포인트

### "API 키와 OAuth2 client credentials 중 뭘 쓰나요?"

- **API 키**: 구현·연동이 단순. 장기 유효 자격증명이라 유출 위험이 크고,
  권한 범위·만료 개념이 빈약해 직접 만들어 붙여야 한다. 서버 간 단순
  조회 연동에 적합.
- **OAuth2 client credentials**: 키(client secret)로 **수명이 짧은 access
  token**을 발급받아 호출. 토큰 유출의 피해 시간이 짧고, scope·만료가 표준에
  내장돼 있으며 파트너 수가 늘어날 때 관리가 표준화된다. 대신 토큰 발급
  서버라는 운영 대상이 늘어난다.
- 판단 기준은 "파트너 수와 데이터 민감도" — 소수 파트너의 단순 조회면
  서명 동반 API 키로 충분하고, 파트너가 늘고 쓰기/민감 데이터가 걸리면
  OAuth2로 표준화하는 게 관리 비용이 낮다.

### "rate limit에 걸린 파트너가 '우리는 정상 트래픽'이라고 항의하면?"

측정 데이터로 대화한다 — 파트너별 호출량·429 비율 대시보드가 있어야 "언제,
어떤 패턴으로(예: 매시 정각 배치 폭주) 한도를 넘었는지" 보여줄 수 있다.
해법도 기술+계약 양면이다: 배치 폭주라면 클라이언트에 지터(무작위 지연)를
넣도록 가이드하고, 실제 트래픽 성장이라면 상위 쿼터로 계약을 조정한다.
한도 상향은 내 서비스의 용량 계획과 연동되는 결정임을 짚으면 좋다.

### "내부 API를 그대로 파트너에게 열어주면 안 되나요?" (시니어 변별 포인트)

가장 빠르지만 가장 비싼 선택이다. 내부 API는 ① 내부 모델·내부 식별자를
노출하고(정보 노출 + 리팩토링 족쇄), ② 내부 소비자와의 합의만으로 바뀌는
계약인데 외부가 붙는 순간 그 변경 속도를 잃으며, ③ 인증·한도·감사가 내부
전제로 설계돼 있다. 올바른 형태는 **외부 전용 계약(전용 DTO/엔드포인트,
전용 게이트웨이)을 내부 API 위에 어댑터로 얹는 것** — 내부는 계속 빠르게
바꾸고, 외부 계약은 안정적으로 유지하는 구조다. "공개는 한 방향 문"이라는
비가역성을 언급하는 것이 시니어 관점이다.

### "파트너에게 데이터를 밀어줘야 하는 경우(웹훅)는 뭐가 달라지나요?"

방향이 뒤집히면 역할도 뒤집힌다 — 이번엔 **내가 클라이언트**다. 파트너
서버의 장애·지연을 전제로 타임아웃, 재시도(지수 백오프 + 멱등 이벤트 ID),
실패 누적 시 격리, 재전송 조회 수단을 설계해야 하고, 파트너가 "이 요청이
진짜 우리한테서 왔는지" 검증할 수 있게 **서명 헤더**를 실어준다.
웹훅 수신 실패분을 파트너가 스스로 복구할 수 있는 재조회(pull) API를
함께 제공하면 운영 문의가 크게 준다 (가산점 포인트).

### "SLA와 SLO는 뭐가 다른가요?"

- **SLA**: 외부와 맺는 **계약** — 위반 시 보상·페널티가 따르는 약속.
- **SLO**: 내부에서 관리하는 **목표치** — SLA를 지키기 위해 더 엄격하게 잡는
  운영 기준. 보통 SLO를 SLA보다 높게 잡아 여유분(error budget)을 두고,
  SLO가 흔들리면 SLA 위반 전에 대응한다. 내부 API는 SLO까지만, 외부 API는
  SLA까지 올라간다고 정리하면 깔끔하다.

## 한 줄 요약

내부 API와 외부 파트너 API의 차이는 기능이 아니라 **신뢰 경계와 통제
가능성**이다 — 통제할 수 없는 소비자를 전제로 인증은 생명주기(발급·서명·
회수)까지, rate limit은 파트너별 쿼터와 429 계약까지, 문서는 계약서
수준으로, SLA는 고지·보상 조건까지 명문화하고, 내부 모델을 직접 노출하지
않는 외부 전용 계약 층을 두는 것이 핵심이다.
