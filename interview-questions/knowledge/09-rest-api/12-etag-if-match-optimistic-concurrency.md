# ETag / If-Match 낙관적 동시성 — lost update를 HTTP 계약으로 막는다

> 핵심 관전 포인트: **두 관리자가 같은 화면을 열어 편집하면 나중에 저장한 쪽이 먼저 저장한 쪽의 변경을 조용히 덮어쓴다(lost update). 이 구간을 DB 락으로 잡을 수 없는 이유는 GET과 PUT 사이에 몇 분짜리 "사람의 생각 시간"이 끼어 있기 때문이고, 그래서 답은 **낙관적** 방식 — 충돌이 드물 것이라 낙관하고 일단 잠그지 않은 채 진행하되, 저장하는 순간 "내가 본 그 버전이 아직 그대로인가"를 검사하는 것 — 이 된다. HTTP는 이 검사를 표현할 어휘를 표준으로 갖고 있다. **조건부 요청(conditional request)**, 즉 "이 조건이 참일 때만 이 요청을 실행하라"고 헤더로 전제를 거는 기능 묶음이다(`If-Match`·`If-None-Match`·`If-Modified-Since`·`If-Unmodified-Since`가 그 가족이다). 검사의 재료는 **ETag(Entity Tag, 자원의 표현에 붙는 꼬리표 — 값이 같으면 표현이 같다는 뜻)**이고, 서버는 GET 응답에 ETag를 실어 주고 클라이언트는 수정 요청에 `If-Match: <그 ETag>`를 붙여 되돌려준다. 버전이 어긋나면 서버는 **요청을 실행하지 않고** `412 Precondition Failed`를 돌려준다. 상태 코드 구분이 채점 포인트다 — 412는 "네가 헤더로 건 전제가 거짓"이라는 조건부 요청 전용 응답이고, 409는 전제 헤더와 무관하게 자원의 현재 상태와 충돌했다는 일반 충돌 응답이며, 428 Precondition Required는 "전제를 걸어야 하는데 안 걸었다"로 낙관적 동시성을 선택이 아닌 계약으로 강제한다. 그리고 ETag의 원천은 결국 DB의 버전 컬럼이다 — `WHERE id = ? AND version = ?`의 영향 행 수가 0이면 충돌이라는 `@Version`의 검사를, 트랜잭션 경계 밖의 사람 시간까지 넓힌 것이 이 설계의 정체다.**

---

## 0. 질문 + 의도

**질문**: "낙관적 동시성 제어를 API 레벨에서 어떻게 표현하나요? (ETag, If-Match, 409 vs 412)"

**출제 의도**: 두 관리자가 같은 데이터를 편집하는 lost update를 API 계약으로 막는 설계. DB 락 지식을 HTTP 계층으로 번역할 수 있는지 — 계층을 넘나드는 응용력을 본다.

(DB 계층의 낙관적 락 자체 — `@Version`의 UPDATE SQL, 예외 타입, 재시도 전략 — 는 `03-jpa-orm/10-optimistic-vs-pessimistic-lock.md` 참고. 이 문서는 그것을 **HTTP 계약으로 표현하는 층** — 헤더 흐름과 상태 코드 선택 — 에 집중한다.)

> lost update의 정의와 PUT/PATCH의 시맨틱은 `02-put-vs-patch.md` 2-5에서 이미 다뤘고, 그 문서가 "근본 해결은 조건부 요청이고 자세한 것은 12번"이라며 이 문서를 가리킨다. 자원의 **표현(Representation)** 이라는 용어는 `01-restful-design-principles-resource-naming.md` 1-1, 캐시 재검증용 ETag의 쓰임은 `../08-network-http/20-http-caching-headers-and-304.md` 2-2에 있다.

## 1. 문제의 형태 — API에는 트랜잭션이 없다

### 1-1. 되짚기 — lost update가 무엇이었나

**lost update(갱신 유실)는 두 사람이 같은 자원을 각자 읽어 각자 수정한 뒤 저장했을 때, 나중에 저장한 쪽이 앞사람의 수정을 덮어써 앞사람의 변경이 흔적 없이 사라지는 현상이다.** 이름 그대로 갱신이 유실된다. **에러도, 경고도, 로그도 남지 않는다는 것이 이 현상의 무서운 점**이다 — 두 요청 모두 서버 입장에서는 완벽하게 정상적인 200 응답이었다.

02번 문서 2-5에 관리자 두 명이 주문 42번의 메모와 배송지를 각각 고치다 사고가 나는 타임라인이 있다. 여기서는 그 상황을 한 문단으로 재현만 하고, 곧바로 HTTP 계약 층으로 들어간다.

관리자 A와 B가 t0·t1에 각각 `GET /orders/42`로 같은 화면을 열었다. A는 메모를 "선물포장"으로 고쳐 t4에 저장했고, B는 배송지를 "부산"으로 고쳐 t5에 저장했다. B가 보낸 본문에는 **t1에 읽은 낡은 메모(빈 값)** 가 그대로 실려 있었으므로, t5의 저장이 t4에 A가 쓴 "선물포장"을 지워 버렸다. B는 배송지만 고쳤다고 믿고 있고, 화면에도 그렇게 보인다.

이 사고를 부르는 다른 이름이 **last write wins(마지막 쓰기가 이긴다)** 다. **여러 요청이 같은 데이터를 겹쳐 쓸 때 아무 검사도 하지 않으면 시간상 가장 나중에 도착한 쓰기가 앞의 것을 전부 덮어쓰고 최종 상태가 된다**는 뜻이다. 이것은 어떤 알고리즘의 이름이 아니라 **아무 대책도 세우지 않았을 때 자동으로 얻게 되는 기본 동작**의 이름이다. 이 문서 전체가 "last write wins를 벗어나는 방법"에 관한 것이라고 봐도 된다.

### 1-2. 왜 DB 락으로 못 잡는가 — 사람의 생각 시간

DB 안에서라면 이 문제는 쉽다. read-modify-write(읽고, 고치고, 쓰기)를 한 트랜잭션으로 묶고 조회 시점에 `SELECT ... FOR UPDATE`로 행을 잠가 버리면, 뒤에 온 트랜잭션은 앞 트랜잭션이 끝날 때까지 대기하므로 낡은 값을 읽을 기회 자체가 없다.

그런데 API 소비자의 편집 흐름은 이렇게 생겼다.

```text
GET /orders/42   ──────── 몇 초 ~ 몇 분 ~ 몇 시간 ────────>  PUT /orders/42
(화면에 띄운다)          사람이 화면을 보고 생각하고 타이핑하는 구간       (저장 버튼)
                        점심을 먹으러 갈 수도 있고, 탭을 닫을 수도 있다
```

**이 구간을 DB 락으로 잡아둘 수 없는 이유가 셋이다.**

첫째, **트랜잭션을 몇 분 열어 두는 비용이 감당되지 않는다.** 트랜잭션이 열려 있는 동안 DB 커넥션 하나가 계속 점유된다. 커넥션 풀이 30개인 서버에서 편집 화면을 연 사용자 30명이 점심을 먹으러 가면 서비스 전체가 멈춘다.

둘째, **HTTP는 무상태(stateless)라 GET과 PUT이 같은 커넥션·같은 스레드라는 보장이 없다.** GET을 처리한 서버 인스턴스와 PUT을 처리할 인스턴스가 다를 수 있고, 그 사이에 배포가 일어나 GET을 처리한 프로세스가 아예 사라졌을 수도 있다. 트랜잭션은 하나의 커넥션에 묶인 개념이라 이 간극을 건널 수 없다.

셋째, **잠근 사람이 돌아오지 않으면 회수할 방법이 없다.** 사용자가 편집 화면에서 브라우저 탭을 그냥 닫으면 서버에는 아무 신호도 오지 않는다. 잠금은 남고 자원은 영원히 잠긴다.

그래서 남는 선택지는 하나다. **잠그지 않고 진행하되, 저장하는 순간에 검사한다.**

### 1-3. 낙관적과 비관적 — 이름의 뜻부터

여기서 두 단어를 정의하고 가자. 이 대비를 세워 두지 않으면 3장의 상태 코드 논의도, 4장 마지막의 "편집 잠금과 어떻게 고르나"도 근거 없이 외우는 결론이 된다.

**비관적(pessimistic)은 "충돌이 날 것이라고 비관하고 미리 잠그는" 방식이다.** 남이 건드리기 전에 내가 먼저 문을 잠그고 들어간다. `SELECT ... FOR UPDATE`가 여기 속한다. 충돌을 **예방**하지만, 잠근 동안 다른 사람은 기다려야 한다.

**낙관적(optimistic)은 "충돌은 드물 것이라고 낙관하고 일단 잠그지 않은 채 진행한 뒤, 저장할 때 검사하는" 방식이다.** 아무도 안 건드렸을 것이라 믿고 작업하다가, 저장 직전에 "내가 본 그대로인가"를 확인한다. 충돌을 **예방하지 않고 감지**하며, 감지되면 그 요청을 실패시킨다.

| | 비관적 | 낙관적 |
|---|---|---|
| 전제 | 충돌이 자주 날 것이다 | 충돌은 드물 것이다 |
| 언제 개입하나 | 읽는 시점에 미리 잠근다 | 쓰는 시점에 검사한다 |
| 충돌이 없을 때의 비용 | 잠금 획득·해제 비용을 매번 낸다 | 사실상 0 (비교 한 번) |
| 충돌이 났을 때 | 뒤에 온 쪽이 **기다린다** | 뒤에 온 쪽이 **실패한다** |
| 실패 처리 책임 | 없음(대기로 흡수) | 클라이언트가 재조회·재시도해야 한다 |
| HTTP에서의 모습 | 별도 잠금 자원(4장 마지막) | ETag + If-Match (이 문서의 주제) |

**"낙관적 락은 사실 아무것도 잠그지 않는다"**는 점을 정확히 말할 수 있어야 한다. 이름에 "락"이 붙어 있어 오해하기 쉬운데, 하는 일은 잠금이 아니라 **버전 비교**다. 그래서 낙관적 방식에서는 뒤에 온 요청이 대기하는 일이 없고, 대신 실패한다.

### 1-4. 조건부 요청 — HTTP가 이미 갖고 있는 어휘

낙관적 검사를 하려면 클라이언트가 "내가 본 버전"을 서버에 알려주고, 서버가 그 값과 현재 값을 비교해 실행 여부를 정해야 한다. 이 왕복을 표현할 어휘가 계약에 있어야 하는데, HTTP는 그것을 표준으로 갖고 있다.

**조건부 요청(conditional request)은 "이 조건이 참일 때만 이 요청을 실행하라"고 헤더로 전제를 거는 HTTP의 기능 묶음이다.** 이름 그대로 요청에 조건이 붙는다. 조건이 거짓이면 서버는 **요청 본문을 실행하지 않고** 거절 응답만 돌려준다.

이 범주를 먼저 세우는 것이 중요하다. **412라는 상태 코드가 "조건부 요청 전용 응답"이라는 3장의 논의가, 이 범주가 존재해야만 성립하기 때문**이다.

가족은 넷이다. 두 축으로 갈린다 — **무엇으로 비교하는가(ETag냐 시각이냐)**, 그리고 **같을 때 실행하는가 다를 때 실행하는가**.

| 헤더 | 비교 재료 | 실행 조건 | 주 용도 |
|---|---|---|---|
| `If-Match` | ETag | 같을 때 실행 | 낙관적 동시성 (쓰기 보호) |
| `If-None-Match` | ETag | 다를 때 실행 | 캐시 재검증 (읽기 절약) |
| `If-Unmodified-Since` | 수정 시각 | 그 시각 이후 안 바뀌었을 때 실행 | 낙관적 동시성 (정밀도가 낮은 대안) |
| `If-Modified-Since` | 수정 시각 | 그 시각 이후 바뀌었을 때 실행 | 캐시 재검증 (정밀도가 낮은 대안) |

(범위 요청 이어받기에 쓰는 `If-Range`까지 포함해 다섯으로 세기도 한다. 2-5에서 다시 나온다.)

표를 세로로 읽으면 **위 두 줄이 ETag 기반, 아래 두 줄이 시각 기반**이고, 가로로 읽으면 **`If-Match`/`If-Unmodified-Since`가 쓰기용, `If-None-Match`/`If-Modified-Since`가 읽기용**이다. 우리가 쓸 것은 왼쪽 위, 즉 `If-Match`다.

### 1-5. ETag — 이름부터 풀자

**ETag는 Entity Tag의 줄임말이다. "개체 태그", 즉 자원의 표현에 붙는 꼬리표다.**

여기서 **표현(Representation)** 은 01번 문서 1-1에서 정의한 그대로다 — 서버가 DB에 들고 있는 42번 주문 그 자체를 네트워크로 보낼 방법은 없고, 보낼 수 있는 것은 "42번 주문의 지금 상태를 JSON 같은 형식으로 찍어낸 스냅샷"뿐이며 그 스냅샷이 표현이다.

**ETag가 뜻하는 것은 딱 하나다 — 값이 같으면 표현이 같고, 값이 다르면 표현이 달라졌다.** 서버가 자원을 고칠 때마다 새 값을 붙여 주므로, 클라이언트가 들고 있는 ETag와 서버의 현재 ETag를 비교하면 "내가 본 뒤로 누가 고쳤는가"를 한 번의 문자열 비교로 알 수 있다.

값은 규격상 큰따옴표로 감싼다. 이것은 장식이 아니라 문법이고, 따옴표를 빼면 일부 클라이언트·프록시가 헤더를 해석하지 못한다.

```http
ETag: "7"           # 버전 번호 기반
ETag: "a3f8c2e1"    # 내용 해시 기반
ETag: W/"7"         # 앞에 W/ 가 붙으면 "약한" ETag (2-5)
```

비유하면 **문서 결재판에 붙은 판 버전 스티커**다. 결재판을 복사해 간 사람(GET + ETag)이 수정본을 제출할 때 "v3 기준으로 고쳤습니다"(If-Match)라고 명시하면, 접수 담당자는 원본이 이미 v4가 됐을 경우 접수를 거부한다(412). 담당자가 두 수정본을 말없이 겹쳐 붙이는 사고가 원천 차단된다.

## 2. 헤더 흐름 — ETag를 주고, If-Match로 돌려받는다

### 2-1. 전체 왕복

```http
GET /orders/42 HTTP/1.1

HTTP/1.1 200 OK
ETag: "7"                          ← 이 표현의 꼬리표. 클라이언트가 보관한다.
Content-Type: application/json

{ "id": 42, "memo": "", "shippingAddress": "서울", "status": "PAID" }
```

```http
PUT /orders/42 HTTP/1.1
If-Match: "7"                      ← "표현이 아직 7일 때만 실행하라"
Content-Type: application/json

{ "id": 42, "memo": "선물포장", "shippingAddress": "서울", "status": "PAID" }
```

결과는 둘 중 하나다.

**버전이 그대로면** 요청을 실행하고 `200 OK`와 함께 **새 ETag**(`"8"`)를 응답에 실어 준다. 새 ETag를 주는 것이 중요하다 — 클라이언트가 재조회 없이 연속 편집을 이어갈 수 있기 때문이다. 이것을 안 주면 사용자가 저장할 때마다 화면을 새로 불러와야 한다.

**그 사이 누가 고쳤으면** 요청을 실행하지 않고 `412 Precondition Failed`를 돌려준다. **서버 상태는 손대지 않은 그대로**라는 점이 핵심이다.

```http
HTTP/1.1 412 Precondition Failed
Content-Type: application/json

{ "code": "CONCURRENT_MODIFICATION",
  "message": "리소스가 다른 사용자에 의해 수정되었습니다. 다시 조회 후 수정해주세요." }
```

### 2-2. 02번의 타임라인 위에 ETag를 겹치면 — t5에서 무슨 일이 일어나는가

말로만 읽으면 와닿지 않으므로, 1-1에서 되짚은 그 사고 상황에 If-Match만 얹어 다시 돌려 보자. 등장인물과 데이터는 02번 2-5와 같다.

```text
시각   관리자 A                          관리자 B                         서버의 주문 42
──────────────────────────────────────────────────────────────────────────────────────────────────
 t0    GET /orders/42                                                     메모="" · 배송지=서울
       <- 200  ETag: "7"                                                  version = 7
 t1                                      GET /orders/42                   메모="" · 배송지=서울
                                         <- 200  ETag: "7"                version = 7
 t2    화면에서 메모를 "선물포장"으로
 t3                                      화면에서 배송지를 "부산"으로
 t4    PUT /orders/42
       If-Match: "7"        <- t0에 받은 값
       {메모:"선물포장", 배송지:"서울"}
       <- 200  ETag: "8"                                                  메모=선물포장 · 배송지=서울
                                                                          version = 8
 t5                                      PUT /orders/42
                                         If-Match: "7"   <- t1에 받은 값. 서버는 이미 8이다.
                                         {메모:"", 배송지:"부산"}
                                         <- 412 Precondition Failed       메모=선물포장 · 배송지=서울
                                            (본문은 실행되지 않았다)      version = 8   (그대로!)
 t6                                      GET /orders/42
                                         <- 200  ETag: "8"                메모=선물포장 · 배송지=서울
                                            화면에 A의 수정이 반영돼 보인다
 t7                                      PUT /orders/42
                                         If-Match: "8"
                                         {메모:"선물포장", 배송지:"부산"}
                                         <- 200  ETag: "9"                메모=선물포장 · 배송지=부산
                                                                          version = 9
```

**t5가 이 문서의 전부다.** 02번에서는 이 시점에 B의 낡은 메모가 A의 수정을 덮어써 조용히 사라졌지만, 여기서는 **서버가 요청을 아예 실행하지 않는다.** 데이터는 t4 상태 그대로 남고, B는 자기 저장이 실패했다는 사실을 즉시 안다.

이 차이를 한 줄로 요약하면 이렇다. **lost update는 "조용한 데이터 손실"이었는데, If-Match는 그것을 "시끄러운 실패"로 바꾼다.** 시끄러운 실패는 클라이언트가 대응할 수 있지만, 조용한 손실은 대응할 기회조차 없다.

그리고 t6~t7이 보여주는 것이 **낙관적 방식의 대가**다. B는 재조회하고 자기 변경을 최신본 위에 다시 얹어 재요청해야 한다. 이 절차를 누가 어떻게 밟을지가 4장 첫 꼬리질문의 주제다.

### 2-3. 서버 구현 — Before / After

```java
// Before: If-Match 없이 그대로 덮어쓰기 — last write wins
@PutMapping("/orders/{id}")
public OrderResponse update(@PathVariable Long id,
                            @RequestBody OrderRequest req) {
    return orderService.update(id, req);  // 늦게 온 쪽이 조용히 이긴다
}
```

```java
// After: GET에서 ETag를 발급하고, PUT에서 If-Match를 검증한다

@GetMapping("/orders/{id}")
public ResponseEntity<OrderResponse> get(@PathVariable Long id) {
    Order o = orderService.find(id);
    return ResponseEntity.ok()
            // @Version 컬럼 값을 그대로 ETag로 쓴다(2-4).
            // Spring의 eTag()는 따옴표가 없으면 붙여 주므로 "7" 형태로 나간다.
            .eTag(String.valueOf(o.getVersion()))
            .body(OrderResponse.of(o));
}

@PutMapping("/orders/{id}")
public ResponseEntity<OrderResponse> update(
        @PathVariable Long id,
        // required = false 로 받아야 "안 보냄"을 우리가 직접 판정할 수 있다.
        // required = true 로 두면 Spring이 400을 내버려서 428을 쓸 기회가 없다.
        @RequestHeader(value = "If-Match", required = false) String ifMatch,
        @RequestBody OrderRequest req) {

    if (ifMatch == null) {
        // 전제조건 없이 온 수정 요청. 이 자원에서 낙관적 동시성을 "강제"하기로
        // 했다면 여기서 거부해야 한다. 통과시키면 방어적인 클라이언트만
        // 손해 보는 구조가 된다(3-2).
        return ResponseEntity.status(HttpStatus.PRECONDITION_REQUIRED).build();
    }

    Order updated = orderService.update(id, req, parseVersion(ifMatch));
    // 서비스 내부에서 하는 일:
    //   ① 엔티티를 조회해 현재 version 과 If-Match 값을 비교한다.
    //      다르면 PreconditionFailedException -> @ControllerAdvice 에서 412
    //   ② 같으면 필드를 반영한다. 커밋 시점의 @Version UPDATE 가
    //      최후의 안전망으로 한 번 더 검사한다(2-4).

    return ResponseEntity.ok()
            .eTag(String.valueOf(updated.getVersion()))  // 연속 편집을 위해 새 ETag
            .body(OrderResponse.of(updated));
}
```

`required = false`로 받는 이유를 짚어 두자. `true`로 두면 헤더가 없을 때 Spring이 먼저 `400 Bad Request`를 내버리는데, **400은 "요청 문법이 틀렸다"는 뜻이라 "전제조건을 걸어야 하는데 안 걸었다"는 상황을 정확히 전달하지 못한다.** 428이라는 전용 코드가 있는 이유가 여기 있다(3-2).

### 2-4. ETag의 원천은 결국 버전 컬럼 — `@Version`이 만드는 실제 SQL

여기가 계층 번역의 그림이 완성되는 자리다. **ETag는 하늘에서 떨어진 값이 아니라, DB가 이미 들고 있던 버전 컬럼을 HTTP 헤더로 내보낸 것**이다.

JPA 엔티티에 `@Version` 필드를 붙이면 하이버네이트가 UPDATE 문의 모양을 바꾼다.

```sql
-- @Version 이 없을 때 — id 만 보고 덮어쓴다. 이것이 last write wins 그 자체다.
UPDATE orders
   SET memo = ?, shipping_address = ?
 WHERE id = ?;

-- @Version 이 있을 때 — 개념적으로는 이렇게 읽으면 된다.
UPDATE orders
   SET memo = ?, shipping_address = ?, version = version + 1
 WHERE id = ? AND version = ?;
--                └─────────┘
--                "내가 읽었을 때의 버전 그대로일 때만 써라"
```

**충돌 판정은 값을 다시 읽어 비교하는 것이 아니라 `UPDATE`가 돌려준 영향 행 수(affected rows)로 한다.**

```text
UPDATE ... WHERE id = 42 AND version = 7

  → 영향 행 수 1 : WHERE 조건에 걸리는 행이 있었다.
                   아무도 안 건드렸다는 뜻. version 은 이제 8.

  → 영향 행 수 0 : WHERE 조건에 걸리는 행이 없다.
                   id 42 는 분명히 있는데 version 이 7이 아니다
                   = 누군가 이미 8 이상으로 올려놨다
                   = 충돌!  → ObjectOptimisticLockingFailureException
```

**확인과 갱신이 하나의 SQL 문장 안에 들어 있다는 점이 핵심이다.** "SELECT로 버전을 확인하고 → 같으면 UPDATE"로 나누면 그 사이에 다른 트랜잭션이 끼어들 틈이 생기지만, 검사를 `WHERE`절 안에 넣으면 DB가 원자적으로 판정한다.

한 가지 정확한 디테일을 덧붙이면 가산점이다. **하이버네이트가 실제로 찍는 SQL은 `version = version + 1`이 아니라 `version = ?`이다.** 새 버전 값을 메모리에서 계산해(읽은 값 + 1) 파라미터로 바인딩하기 때문이다. 개념적으로는 `version + 1`이 맞지만, 로그에서 보게 될 문자열은 `update orders set memo=?, shipping_address=?, version=? where id=? and version=?` 쪽이다. (자세한 내용은 `03-jpa-orm/10-optimistic-vs-pessimistic-lock.md` 1-2·1-3.)

이제 두 계층을 나란히 놓으면 이 문서의 논지가 한 표로 정리된다.

| | JPA `@Version` | HTTP `ETag` / `If-Match` |
|---|---|---|
| 검사 재료 | version 컬럼 값 | **같은 version 값**을 헤더로 내보낸 것 |
| 검사가 일어나는 곳 | DB의 `UPDATE ... WHERE` | 애플리케이션의 요청 처리 진입부 |
| 검사가 덮는 구간 | 트랜잭션 시작 ~ 커밋 (밀리초) | GET ~ PUT, **사람의 생각 시간까지** (분·시간) |
| 충돌 신호 | 영향 행 수 0 → 예외 | ETag 불일치 → 412 |
| 못 막는 것 | GET~PUT 사이의 사람 시간 | 같은 서버 안의 밀리초 단위 동시 요청 |

마지막 줄이 **둘을 겹쳐 쓰는 이유**다. 표의 오른쪽만 있으면 두 요청이 거의 동시에 도착했을 때 둘 다 "현재 버전 7"을 읽고 둘 다 검증을 통과하는 레이스가 남는다. 표의 왼쪽만 있으면 사람의 생각 시간을 못 막는다. **실무에서는 API 레벨의 If-Match가 대부분을 거르고, 그 사이를 빠져나간 밀리초 단위 레이스를 `@Version`이 최종적으로 잡는다.** `ObjectOptimisticLockingFailureException`을 `@ControllerAdvice`에서 412(또는 팀 규약에 따라 409)로 번역하는 매핑까지 말하면 완성형이다. (가산점 포인트)

### 2-5. ETag 값은 무엇으로 만드나, 그리고 `W/`는 무엇인가

먼저 재료 선택이다.

- **버전 번호** (권장): `@Version` 컬럼 값 그대로. 단조 증가라 비교가 명확하고, 이미 조회한 엔티티의 필드 하나이므로 생성 비용이 사실상 0이다. 낙관적 동시성 용도에는 대부분 이것이 최선이다.
- **내용 해시**: 응답 본문을 해시한 값. 버전 컬럼이 없는 자원이나 여러 테이블에서 조합해 만드는 파생·집계 표현에 유용하지만, 매 응답마다 직렬화 결과를 해시하는 비용이 든다.
- **수정 시각**: 같은 초(또는 같은 밀리초)에 두 번 수정되면 두 표현이 같은 값을 갖는 **정밀도 함정**이 있다. `Last-Modified`/`If-Unmodified-Since`가 초 단위라 동시성 제어용으로 ETag보다 약한 이유와 같다.

#### 강한 ETag와 약한 ETag

ETag 값 앞에 `W/`가 붙으면 **약한(weak) ETag**이고, 없으면 **강한(strong) ETag**다. 둘은 "같다"의 기준이 다르다.

**강한 ETag는 "바이트까지 완전히 같다"**를 뜻한다. 두 표현의 강한 ETag가 같다면 두 응답 본문은 1바이트도 다르지 않다.

**약한 ETag는 "의미상 같다"**를 뜻한다. 공백이나 필드 순서, 응답에 박아 넣은 생성 시각 주석 정도는 달라도 "같은 것"으로 친다. 사람이 보기에 같은 내용이면 같다고 보겠다는 선언이다.

```http
ETag: "a3f8c2"      # 강한 검증자 — 바이트 단위로 동일함을 보증한다
ETag: W/"a3f8c2"    # 약한 검증자 — 의미는 같지만 바이트가 같다고는 보증하지 않는다
```

**이 구분이 실무에서 걸리는 곳이 범위 요청(range request) 이어받기다.** 큰 파일을 받다 끊겨서 "이 파일의 5MB 지점부터 주세요"라고 이어받으려면, 서버가 지금 가진 파일이 내가 앞부분을 받아둔 그 파일과 **바이트 단위로 완전히 같아야** 한다. 1바이트라도 다르면 이어붙인 파일이 깨진다.

그래서 **이어받기에 쓰는 `If-Range` 헤더는 강한 ETag만 받아들인다.** 약한 ETag밖에 없으면 이어받기가 성립하지 않고 처음부터 다시 받게 된다. "의미상 같다"로는 바이트 정합성을 보장할 수 없기 때문이다.

**`If-Match`도 같은 이유로 강한 비교를 요구한다.** 명세상 `If-Match`는 강한 비교를 쓰므로, **약한 ETag는 `If-Match`에서 절대 일치하지 않는다.** `If-Match: W/"7"`을 보내면 서버 ETag가 `W/"7"`이어도 불일치로 판정돼 언제나 412가 나간다. 반면 `If-None-Match`(캐시 재검증)는 약한 비교를 허용한다 — 읽기 절약이 목적이라 "의미상 같으면 본문을 생략해도 된다"가 성립하기 때문이다.

여기서 실무 함정이 하나 나온다. **응답 압축(gzip 등)을 켜면 본문 바이트가 바뀌므로 원본의 강한 ETag를 그대로 유지하는 것은 거짓말이 된다.** 그래서 압축 계층을 통과한 응답의 ETag는 약한 것으로 낮아지거나 제거된다(Nginx는 약한 ETag로 낮춘다). **압축을 켰더니 If-Match가 항상 412를 내더라**는 현상의 정체가 이것이다. 버전 번호를 ETag로 쓰면서 압축 계층이 그것을 건드리지 않도록 확인해 두는 것이 안전하다.

정리하면 **동시성 제어용 ETag는 강한 ETag여야 하고, 버전 번호 기반이면 자연히 강한 ETag가 된다.**

## 3. 상태 코드 선택 — 409 vs 412, 그리고 428

### 3-1. 결정 트리로 한 번에 보기

질문의 괄호가 굳이 "409 vs 412"를 짚는 이유는, 두 코드가 모두 "충돌"처럼 들리지만 **메커니즘이 다르기 때문**이다. 산문으로 읽기 전에 판정 순서를 그림으로 잡아 두자.

```text
수정 요청(PUT / PATCH / DELETE)이 도착했다
            │
            ▼
     If-Match 헤더가 있는가?
            │
            ├── 없다 ──────> 이 자원의 수정에 전제조건이 필수인가?
            │                    │
            │                    ├── 필수다 ─────────> 428 Precondition Required
            │                    │                     "전제를 걸고 다시 오라"
            │                    │
            │                    └── 선택이다 ───────> 그냥 처리한다
            │                                          (last write wins 위험을 감수한 것)
            │
            └── 있다 ──────> 현재 ETag와 일치하는가?
                                 │
                                 ├── 일치 ───────────> 실행 + 200 OK + 새 ETag
                                 │
                                 └── 불일치 ─────────> 412 Precondition Failed
                                                       (요청은 실행하지 않는다)

  ─────────────────────────────────────────────────────────────────────────
  전제 헤더와 무관하게, 요청이 자원의 현재 "상태"와 충돌하는 경우
  (이미 배송 시작된 주문의 취소 요청, 중복 이름 생성, CANCELLED 상태에서의 수정)
                                                   ──────> 409 Conflict
```

트리의 모양이 말해 주는 것이 있다. **412와 428은 `If-Match`라는 가지 위에 있고, 409는 그 가지 바깥에 있다.** 이것이 두 코드를 가르는 기준 전부다.

### 3-2. 세 코드를 각각 정확히

**412 Precondition Failed** 는 클라이언트가 조건부 헤더(`If-Match`, `If-Unmodified-Since` 등)로 건 **전제조건이 거짓으로 평가되어, 서버가 요청을 실행하지 않았다**는 뜻이다. 이름 그대로 "전제조건(precondition)이 실패(failed)했다"다. **412는 조건부 요청 메커니즘 전용 응답**이고, 1-4에서 조건부 요청이라는 범주를 세운 이유가 여기 있다 — 그 범주 안에서만 쓰이는 코드다. ETag/If-Match로 낙관적 동시성을 구현했다면 충돌의 정답은 412다.

**409 Conflict** 는 전제조건 헤더와 무관하게, 요청이 **자원의 현재 상태와 충돌**해서 수행할 수 없다는 뜻이다. 예를 들면 이렇다.

- 이미 배송이 시작된 주문에 대한 취소 요청 (상태 기계 위반)
- 이미 존재하는 이름으로 자원을 생성하려는 요청 (유니크 제약 충돌)
- `CANCELLED` 상태의 주문을 수정하려는 요청

여기에 하나 더 붙는다. **버전을 헤더가 아니라 요청 본문의 필드**(예: `"version": 7`)로 받는 설계라면 조건부 요청 메커니즘을 쓰는 것이 아니므로, 충돌 시 412가 아니라 409를 쓰는 것이 자연스럽다. 실무 API 중 이 방식도 많고, 틀린 설계가 아니다(4장에서 비교한다).

**428 Precondition Required** 는 이 자원의 수정에 전제조건이 **필수**인데 클라이언트가 `If-Match` 없이 요청했다는 뜻이다.

**이 코드가 왜 필요한지가 설계 감각을 보여주는 지점이다.** `If-Match` 없는 PUT을 그냥 통과시키면, 낙관적 동시성은 **"보내는 클라이언트만 보호받는 옵션"** 이 된다. 그러면 어떻게 되는가.

```text
[428 없이 통과시킬 때]
  성실한 클라이언트 A: If-Match 를 꼬박꼬박 보낸다 -> 충돌 시 412 받고 재조회한다
  게으른 클라이언트 B: If-Match 를 안 보낸다      -> 항상 성공한다. 남의 수정을 덮어쓴다

  결과: A 가 애써 지킨 계약을 B 가 무력화한다.
       규칙을 지킨 쪽만 손해 보는 구조가 된다.

[428로 거부할 때]
  B 의 요청이 428로 막히므로 모든 소비자가 같은 계약 위에 서게 된다.
```

즉 428은 **낙관적 동시성을 "옵션"에서 "모든 소비자에게 강제되는 계약"으로 승격시키는 장치**다.

한 줄 기준으로 외워 두면 이렇다. **"클라이언트가 헤더로 건 전제가 깨졌다 → 412, 전제 헤더와 무관하게 상태가 안 맞는다 → 409, 전제를 걸어야 하는데 안 걸었다 → 428."**

### 3-3. 같은 ETag, 반대 방향의 두 헤더

같은 헤더 가족의 다른 용도와 혼동하지 않는 것도 채점 포인트다.

| 헤더 조합 | 용도 | 조건이 참일 때 | 조건이 거짓일 때 |
|---|---|---|---|
| `If-Match` + PUT/PATCH/DELETE | 낙관적 동시성 (lost update 방지) | 실행하고 200 | **412** — 실행하지 않음 |
| `If-None-Match` + GET | 캐시 재검증 ("바뀐 것 없으면 본문 생략") | 본문과 함께 200 | **304 Not Modified** — 본문 생략 |
| `If-None-Match: *` + PUT/POST | "없을 때만 만들어라" (덮어쓰기 방지 생성) | 생성하고 201 | **412** — 이미 존재함 |

**같은 ETag 값 하나를 재료로 쓰지만, `If-Match`는 쓰기 안전이고 `If-None-Match`는 읽기 절약이다.** 방향이 정반대라는 점을 눈여겨보자 — 앞은 "같을 때만 실행", 뒤는 "다를 때만 실행"이다. "ETag = 캐시용"으로만 알고 있으면 이 질문에서 바로 드러난다.

세 번째 줄은 덜 알려졌지만 유용하다. **`If-None-Match: *`의 `*`는 "어떤 ETag든", 즉 "그 자원이 존재하기만 하면"을 뜻한다.** 그러므로 `If-None-Match: *`는 "그 자원이 존재하지 않을 때만 실행하라"가 되어, **PUT으로 자원을 만들 때 남이 이미 만들어 둔 것을 실수로 덮어쓰는 일을 막는다.** 반대로 `If-Match: *`는 "존재하기만 하면 실행하라"이므로 "없는 자원에는 실행하지 마라"라는 뜻이 된다.

## 4. 꼬리질문 대비 포인트

### "412를 받은 클라이언트는 그다음에 뭘 해야 하나요?"

412는 **"네 사본이 낡았다"**는 신호이므로 복구 절차는 셋이다.

① 다시 GET해서 최신 표현과 새 ETag를 받는다. ② **자신의 변경을 최신본 위에 다시 적용할 수 있는지 판단한다.** ③ 새 ETag를 `If-Match`에 실어 재요청한다. 2-2 타임라인의 t6~t7이 바로 이 절차다.

**여기서 ②는 기술이 아니라 UX·제품 결정이라는 점이 핵심이다.** 서버가 대신 정해 줄 수 없다.

- 겹치는 필드가 없으면(A는 메모, B는 배송지) 자동 병합해 재시도할 수 있다.
- 같은 필드를 고쳤다면 "다른 사용자가 수정했습니다"를 보여주고 **diff와 함께 사람에게 선택을 넘겨야** 한다.
- 편집량이 큰 화면이라면 사용자의 입력을 잃지 않도록 로컬에 보관한 뒤 최신본과 나란히 보여주는 설계가 필요하다.

그리고 반드시 붙여야 할 지적이 하나 있다. **412를 자동 재시도로 뭉개면 결국 last write wins로 되돌아간다.**

1-1에서 정의했듯 last write wins는 **아무 검사도 하지 않을 때 나중 쓰기가 앞의 것을 전부 덮어써 최종 상태가 되는 기본 동작**이다. 그런데 클라이언트가 412를 받고 "재조회 후 내 본문 그대로 재전송"을 자동으로 수행하면 어떻게 되는지 보자.

```text
t5  B 의 PUT (If-Match: "7")  -> 412
t6  B 의 클라이언트가 자동으로 GET -> ETag "8" 획득
t7  B 의 클라이언트가 자동으로 PUT (If-Match: "8", 본문은 t3의 낡은 값 그대로)
    -> 200. A 의 "선물포장"이 결국 덮여 사라진다.

    검사를 통과했을 뿐 결과는 아무 검사도 안 한 것과 같다.
    = last write wins 로 되돌아갔다
```

**If-Match가 막아 주는 것은 "덮어쓰기"가 아니라 "덮어쓰는 줄 모르고 덮어쓰기"다.** 클라이언트가 그 신호를 받고도 사람에게 알리지 않은 채 같은 본문을 다시 밀어 넣으면, 프로토콜이 만들어 준 개입 기회를 스스로 버린 것이다. **412는 자동 재시도 대상이 아니라 사용자에게 보여야 하는 에러**라고 정리하면 좋다.

### "PATCH는 부분 수정인데도 If-Match가 필요한가요?"

필요하다. **PATCH가 바꾸는 필드가 하나여도, 그 하나를 무엇으로 바꿀지 결정한 근거는 낡은 사본일 수 있기 때문**이다.

예를 보면 분명해진다. 관리자가 화면에서 재고가 10인 것을 보고 "2개 출고했으니 8로"라고 판단해 `PATCH {"stock": 8}`을 보낸다. 그런데 그 사이 다른 곳에서 7개가 팔려 재고가 3이 됐다면, 올바른 값은 8이 아니라 1이다. **PATCH가 보낸 값은 "절대값"이지만 그 절대값을 계산한 근거는 낡은 읽기였다.**

오히려 **PATCH가 더 위험한 면이 있다.** "겹치는 필드만 아니면 안전하다"는 착시 때문에 If-Match를 생략하기 쉽기 때문이다. 02번 4장에서도 "PATCH는 lost update의 발생 범위를 줄일 뿐 없애지 못한다"고 정리했다.

다만 예외가 있다. **"조회 없이도 항상 유효한 연산"으로 설계된 엔드포인트**라면 전제조건 없이도 안전하다. `{"op": "increment", "field": "stock", "by": -2}` 같은 **상대 연산**은 현재 값이 무엇이든 "2 줄인다"가 항상 의도한 바이므로 낡은 읽기에 의존하지 않는다.

그래서 판단 기준을 이렇게 세우면 정확하다. **전제조건의 필요 여부는 메서드 이름이 아니라 "이 연산이 낡은 읽기에 의존하는가"로 정한다.** 절대값을 보내면 필요하고, 상대 연산이면 대체로 불필요하다. (대신 상대 연산은 멱등하지 않아 재시도가 위험해진다 — 02번 1-3.)

### "ETag 없이 요청 바디에 version 필드를 넣는 방식과 뭐가 다른가요?"

**기능적으로는 같은 낙관적 검사다.** 이것을 먼저 인정하고 시작하는 편이 좋다. 어느 쪽이든 "내가 본 버전"을 서버에 알려 주고 서버가 대조하는 구조는 동일하다.

차이는 **계약이 어디에 놓이는가**에서 나온다.

| | 헤더 방식 (`ETag` / `If-Match`) | 본문 방식 (`{"version": 7}`) |
|---|---|---|
| 표준성 | HTTP 표준 시맨틱 — 중간 계층이 이해한다 | 우리 팀의 자체 규약 |
| 충돌 응답 코드 | 412 (표준이 정해 준다) | 팀 규약 (주로 409) |
| 관심사 분리 | 동시성 제어가 헤더에 있어 자원 표현이 깨끗하다 | 자원 표현 안에 동시성 제어 필드가 섞인다 |
| DELETE에 적용 | 자연스럽다 (헤더만 붙이면 된다) | 어색하다 (DELETE에 본문을 싣는 것은 권장되지 않는다) |
| 캐시·게이트웨이 연계 | 같은 ETag를 캐시 재검증에 재사용할 수 있다 | 불가 |
| 구현 난이도 | 헤더 파싱·따옴표 처리가 필요 | 낮음 (DTO 필드 하나) |
| 폼 전송 | 헤더를 못 붙이는 환경이 있다 | 폼 필드로 그냥 실린다 |

**헤더 방식의 결정적 이점은 "우리 앱을 모르는 바깥의 것들이 이해한다"는 점이다.** 표준 클라이언트 라이브러리, API 게이트웨이, 캐시가 `If-Match`와 412를 이미 알고 있다. 본문 방식은 우리 문서를 읽은 사람만 이해한다.

**본문 방식이 나쁜 설계는 아니다.** 구현이 직관적이고, 폼 전송이나 헤더 조작이 까다로운 클라이언트 환경에서 현실적이다. 다만 그 선택에는 "충돌 코드를 팀 규약으로 정해야 한다"와 "DELETE에는 적용하기 애매하다"가 딸려 온다.

마무리는 이렇게 짓는다. **"어느 쪽이든 팀 전체가 한 방식으로 일관되게 쓰고, 그 선택과 충돌 응답 코드를 API 문서에 명시하는 것"**이 정답이다. 같은 회사 API인데 어떤 엔드포인트는 412를 주고 어떤 엔드포인트는 409를 주면, 클라이언트는 둘 다 처리하는 코드를 짜야 한다.

### "GET마다 ETag를 만들려면 비용이 들지 않나요? 컬렉션 응답은요?"

**재료에 따라 다르다는 것이 답의 출발점이다**(2-5).

단건 자원이 버전 컬럼 기반이면 비용은 사실상 0이다. 이미 조회한 엔티티의 필드 하나를 문자열로 바꿔 헤더에 넣을 뿐이다. 해시 기반이면 응답을 직렬화한 결과에 해시 비용이 붙는데, **동시성 제어가 목적이라면 해시를 계산하는 대신 버전 컬럼을 두는 쪽으로 문제를 옮기는 게 낫다.**

컬렉션(목록) 응답은 판단이 갈린다.

**동시성 제어 목적이라면 목록에 ETag가 필요 없다.** 편집 대상은 개별 자원이지 목록 자체가 아니기 때문이다. `PUT /orders`처럼 목록 전체를 통째로 교체하는 API를 만들지 않는 한, 목록에 `If-Match`를 걸 일이 없다.

**캐시 재검증 목적이라면 별개의 판단**이고, 이때는 재료를 고르기가 까다롭다. 목록의 ETag는 "이 목록에 담긴 모든 항목이 그대로인가"를 표현해야 하므로 항목들의 최대 `updated_at`이나 전체 응답 해시 같은 것이 되는데, 항목 하나만 바뀌어도 전체가 무효화되므로 적중률이 낮다. 페이지네이션 파라미터마다 캐시 키가 갈리는 것도 감안해야 한다.

그래서 답의 골자는 이것이다. **"ETag를 어디에 왜 붙이는가"를 용도별(쓰기 보호 vs 캐시 재검증)로 나눠 판단한다.** 두 용도가 같은 값을 재사용할 수 있다는 것이 ETag의 매력이지만, 붙일지 말지의 판단 기준은 용도마다 다르다.

### "이 방식 대신 비관적으로 '편집 잠금'을 거는 설계와는 어떻게 고르나요?" (시니어 변별 포인트)

1-3의 대비를 실제 선택으로 옮기는 질문이다. **기준은 충돌의 빈도와 실패했을 때 잃는 것의 크기**다.

**낙관적(ETag/If-Match)이 이기는 조건은 "충돌이 드물다"**이다. 충돌이 없을 때의 비용이 0이므로, 평상시에는 아무 대가도 치르지 않고 드문 충돌만 412로 처리한다. 대부분의 어드민 CRUD가 여기 해당한다.

**그런데 편집 세션이 길면 이 계산이 뒤집힌다.** 30분짜리 긴 편집(대형 문서, 복잡한 설정 화면)에서 충돌이 잦다면, 사용자가 30분 작업을 마치고 저장을 눌렀을 때 412를 받는 경험은 재앙이다. 낙관적 방식의 대가인 "실패를 클라이언트가 감당한다"가 여기서는 **30분의 작업 손실**이라는 값으로 청구된다.

```text
충돌 확률 × 실패 시 잃는 것

  낮음 × 작음  ->  낙관적 (ETag/If-Match)          기본값
  낮음 × 큼    ->  낙관적 + 초안 자동저장 · 병합 UI  (실패 비용을 UX로 낮춘다)
  높음 × 큼    ->  비관적 (편집 잠금 자원)
  높음 × 작음  ->  낙관적으로 충분하되 충돌 빈도를 모니터링
```

비관적으로 가기로 했다면 **HTTP에서의 모습은 "잠금 자체를 하나의 자원으로 만드는 것"**이다. DB 락은 트랜잭션에 묶여 있어 사람 시간을 건널 수 없으므로(1-2), 잠금을 애플리케이션 자원으로 승격시킨다.

```http
POST /documents/42/lock      -> 201 Created, { "lockId": "...", "expiresAt": "..." }
                                이미 남이 잠갔으면 409 Conflict + 누가 잠갔는지

PUT  /documents/42           -> 잠금 소유자만 실행 가능
DELETE /documents/42/lock    -> 편집 종료 시 해제
```

**그리고 잠금을 도입하면 반드시 따라오는 비용 셋을 함께 말해야 한다.**

- **TTL과 유령 잠금.** 사용자가 탭을 닫으면 해제 요청이 오지 않으므로(1-2의 셋째 이유가 그대로 재현된다) 잠금에 만료 시각을 두고 자동 회수해야 한다. 그러면 "편집 중인데 잠금이 만료되는" 반대 문제가 생겨 하트비트 갱신이 필요해진다.
- **강제 해제와 권한.** 잠근 사람이 휴가를 갔을 때 관리자가 뺏을 수 있어야 하고, 뺏겼을 때 원래 사용자의 작업은 어떻게 되는지 정해야 한다.
- **소유권 UX.** "김철수님이 편집 중입니다"를 보여주고, 언제까지 기다려야 하는지 알려 줘야 한다.

세 번째 선택지도 있다. **충돌 자체를 병합으로 흡수하는 실시간 협업 편집**(OT나 CRDT 계열)이다. 구글 독스처럼 두 사람의 편집을 동시에 반영해 애초에 "충돌"이라는 사건을 없애는 방식인데, 구현 난도가 한 자릿수 이상 높아지므로 그 자체가 제품의 핵심 가치일 때만 선택한다.

정리하면 답은 이렇다. **기본은 낙관적, 편집 세션이 길고 충돌 비용이 크면 잠금 자원 도입, 협업 편집이 제품의 본질이면 병합 모델.** 그리고 어느 쪽으로 가든 **선택의 근거를 "충돌 빈도 × 실패 비용"이라는 축으로 말하고, 잠금 도입에 딸려 오는 TTL·강제 해제·소유권 UX까지 계산에 넣는 것**이 계층 번역 능력에 더해 트레이드오프 감각을 보여 준다.

## 한 줄 요약

GET과 PUT 사이의 사람 시간은 DB 락으로 잡을 수 없으므로 잠그지 않고 저장 시점에 검사하는 낙관적 방식을 택하고, 그 검사를 표현하는 HTTP의 어휘가 조건부 요청 — 서버가 GET 응답에 표현의 꼬리표인 `ETag`(Entity Tag)를 실어 주고 클라이언트가 수정 요청의 `If-Match`로 되돌려주면, 어긋날 때 서버가 **요청을 실행하지 않고** 412를 돌려주는 왕복 — 이다. 상태 코드는 "헤더로 건 전제가 깨졌다 → 412, 전제 헤더와 무관한 상태 충돌 → 409, 전제를 걸어야 하는데 안 걸었다 → 428"로 갈리며 428이 있어야 낙관적 동시성이 옵션이 아닌 계약이 되고, ETag의 원천은 결국 `WHERE id = ? AND version = ?`의 영향 행 수로 충돌을 판정하는 `@Version` 컬럼이라 API 레벨의 If-Match가 사람 시간을 덮고 DB의 `@Version`이 밀리초 레이스를 덮는 이중 방어가 된다 — 다만 412를 자동 재시도로 뭉개면 결국 last write wins로 되돌아가므로, 412는 삼키는 에러가 아니라 사람에게 보여 병합을 결정하게 하는 신호다.
