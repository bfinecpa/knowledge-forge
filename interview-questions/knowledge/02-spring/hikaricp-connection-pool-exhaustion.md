# HikariCP 커넥션 고갈 진단 — 증상은 하나, 원인은 넷: "오래 점유"와 "미반환(누수)"을 구분하라

> 핵심 관전 포인트: `Connection is not available, request timed out after 30000ms`는 **증상이 하나인데 원인은 여럿**인 전형적 상황이다. 원인 후보를 4계열 — ① 풀 크기 부족 ② 느린 쿼리·락 대기 ③ 트랜잭션 내 외부 호출·CPU 작업(오래 점유) ④ 커넥션 누수(미반환) — 로 나열하고, **메트릭으로 계열을 좁힌 뒤 계열별 배제 수단**(풀 메트릭, 슬로우 쿼리 로그/PROCESSLIST, APM 트레이스, `leakDetectionThreshold`·스레드 덤프)을 말하는 것이 이 질문의 본령이다. 특히 "쿼리는 빠르고 DB는 한가한데 active가 max에 붙어 안 내려온다"면 점유가 긴 게 아니라 **반환 자체가 안 되는 누수**다.

## 0. 질문 + 의도

**질문**: "HikariCP에서 커넥션 고갈(connection pool exhaustion)이 발생했습니다. 원인 후보와 진단 방법은?"

**출제 의도**: 증상(timeout 로그)은 하나인데 원인은 여럿(누수, 느린 쿼리, 트랜잭션 내 외부 호출, 풀 크기)인 전형적 상황이다. 원인 후보를 나열하고 각각의 배제 방법을 말할 수 있는지 — 진단 방법론 자체를 평가한다.

## 1. 감별 진단 프레임 — 원인 후보 4계열과 배제 수단

| 계열 | 원인 | 확인(배제) 수단 |
|---|---|---|
| ① 풀 크기 부족 | 트래픽 증가로 필요 동시수 > maximumPoolSize | 풀 메트릭 추이: `active`/`idle`/`pending` — 트래픽과 함께 active가 서서히 차오르면 용량 문제 (산정은 `thread-pool-connection-pool-sizing.md`) |
| ② 느린 쿼리·락 대기 | 인덱스 누락, 락 경합으로 점유 시간 W 증가 | 슬로우 쿼리 로그, `SHOW PROCESSLIST`(MySQL) / `pg_stat_activity`(PG) — 특히 **idle in transaction**(트랜잭션 열고 쿼리 없이 대기) |
| ③ 트랜잭션 내 외부 호출·CPU 작업 | 커넥션을 문 채 외부 API 3초 대기 등 — "오래 점유" | APM **트레이스 스팬**: 트랜잭션 구간 안에 HTTP 호출/긴 연산 스팬이 끼어 있는지 |
| ④ 커넥션 누수 | close 누락(수동 getConnection, 예외 경로) — "미반환" | `leakDetectionThreshold`, 스레드 덤프 — 아래 상세 |

- 어느 계열이든 결과는 같다: 커넥션 반환 속도 < 요구 속도 → 대기 → 30초 타임아웃.
- 진단 순서: **앱 쪽 메트릭으로 계열 좁히기 → 계열별 배제** (앱과 DB 양방향에서 교차 확인). 코드부터 뒤지는 게 아니라 장애 중 장비에서 관측 데이터를 먼저 본다.

## 2. 핵심 구분 — "오래 점유" vs "미반환(누수)"

같은 고갈이라도 두 상황은 원인·수단이 다르다:

- **오래 점유 (②③)**: 커넥션이 결국 돌아오긴 하는데 느리게 돈다. → DB나 트레이스에 흔적이 남는다(느린 쿼리, 긴 스팬).
- **미반환 = 누수 (④)**: 커넥션이 **영영 안 돌아온다**. 시그니처: **느린 쿼리 없음 + DB 한가(CPU 낮음, PROCESSLIST 깨끗) + active가 maximumPoolSize에 붙은 채 트래픽이 줄어도 안 내려옴 + pending만 누적**. 트레이스에도 안 잡힌다(반환 이벤트 자체가 없으니까).

```java
// 전형적 누수 — 트랜잭션 관리 밖에서 수동 획득 후 close 누락
Connection con = dataSource.getConnection();
PreparedStatement ps = con.prepareStatement(sql);
ps.executeQuery();               // 예외가 나면? → con은 영영 미반환
// try-with-resources 없이 정상 경로에서만 close해도 예외 경로에서 샌다
```

## 3. 누수를 잡는 도구 — leakDetectionThreshold

```yaml
spring:
  datasource:
    hikari:
      leak-detection-threshold: 30000   # ms — 이 시간 이상 미반환이면
```

- 임계 초과 시 그 커넥션이 **어디서 획득됐는지 스택트레이스**를 WARN 로그로 남긴다 (`Apparent connection leak detected`) — 누수 지점을 코드 라인 단위로 특정하는 가장 빠른 수단.
- 오탐 주의: 정상적으로 오래 점유하는 배치/긴 트랜잭션도 걸린다 — 로그는 "누수 확정"이 아니라 "이 획득 지점이 임계 이상 물고 있음"이라는 단서.

## 4. 스레드 덤프로 교차 확인

`jstack`(또는 Actuator threaddump)으로 두 부류를 구분해 읽는다:

- **커넥션을 기다리는 스레드**: `HikariPool.getConnection` → `SynchronousQueue`/`park`에서 대기 — 이건 피해자. 수십 개면 고갈 확정.
- **커넥션을 잡고 있는 스레드**: 소켓 read 대기(외부 API 호출 중), RUNNABLE로 긴 연산 중, 혹은 WAITING인데 트랜잭션 안 — 이게 용의자. 이 스레드의 스택이 "커넥션을 문 채 무엇을 하고 있는지"를 그대로 보여준다.

## 5. 연쇄 위험 — 커넥션 고갈은 커넥션에서 끝나지 않는다

- 커넥션을 기다리는 요청들은 **톰캣 스레드를 문 채** 30초씩 대기 → 스레드풀도 고갈 → **DB와 무관한 기능·헬스체크까지 사망** → LB가 인스턴스를 제외하며 장애 전면화.
- 그래서 `connection-timeout`(기본 30초)을 짧게(예: 3초) 잡아 **빨리 실패**시키는 것도 방어선이다 — 대기 줄이 스레드풀로 전이되는 걸 끊는다.

## 6. 꼬리질문 대비 포인트

- **"leakDetectionThreshold 로그가 찍혔는데 누수가 아니라면?"** — 배치·대량 처리의 정상적 장기 점유. 임계값을 그 작업보다 크게 잡거나, 그 작업의 점유 자체를 줄이는(청크 커밋) 게 다음 수순.
- **"idle in transaction은 왜 위험한가?"** — 쿼리는 안 도는데 트랜잭션(=커넥션+락)을 쥐고 있는 상태. 트랜잭션 안에서 외부 호출·사용자 대기가 낀 코드의 DB 쪽 시그니처다.
- **"고갈 났으니 풀을 늘리면 되지 않나?"** — ①이 원인일 때만 정답. ②③은 대기 줄이 DB 앞으로 옮겨질 뿐이고(DB 한계가 상한), ④는 큰 풀이 마르는 시간만 늦출 뿐 반드시 다시 마른다.
- **"평소에 뭘 걸어두나?"** — 풀 메트릭(active/pending/acquire wait) 대시보드 + 알람, leak-detection-threshold 상시 설정, 트랜잭션 안 외부 호출 금지 컨벤션(코드 리뷰 체크리스트).

## 한 줄 요약

커넥션 고갈은 증상 하나에 원인 4계열(풀 크기/느린 쿼리·락/트랜잭션 내 외부 호출/누수) — 풀 메트릭으로 계열을 좁히고 슬로우 쿼리·PROCESSLIST·트레이스·`leakDetectionThreshold`·스레드 덤프로 배제해 가되, "쿼리 빠르고 DB 한가한데 active가 안 내려오면" 오래 점유가 아니라 **미반환 누수**임을 구분하는 것이 진단의 핵심이다.
