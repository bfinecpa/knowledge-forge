# Graceful Shutdown과 무중단 배포 — 배포할 때마다 에러가 소량 나는 이유

> 핵심 관전 포인트: **배포 때 나는 에러는 원인이 두 갈래이고 처방도 두 갈래다. (a) 구버전 프로세스가 죽으면서 이미 처리 중이던 요청이 끊기는 것, (b) 로드밸런서가 아직 트래픽을 보내는데 앱은 이미 새 요청을 거부하기 시작한 순서 레이스. (a)는 앱이 막는다 — `server.shutdown=graceful`은 새 요청 수락을 멈추고 진행 중인 요청이 끝날 때까지 기다린다(스프링 부트 3.4부터 기본값). (b)는 앱이 절대 못 막는다. 파드가 종료 상태가 되는 것과 kube-proxy·인그레스·클라우드 LB가 그 사실을 알고 라우팅에서 빼는 것은 서로에게 보고하지 않는 별개의 비동기 경로이고, 죽이는 쪽이 항상 먼저 끝나기 때문이다. 그래서 인프라 쪽 처방이 하필 `preStop sleep`이다 — 무언가를 정리하는 시간이 아니라 전파가 끝나기를 기다리며 시간을 버는 구간이고, 그동안 앱은 멀쩡히 서빙한다. 여기에 시간 예산이 맞아야 한다: `terminationGracePeriodSeconds`(k8s가 SIGKILL까지 기다리는 총 시간, 기본 30초, 카운트다운은 preStop 실행 전에 시작된다) ≥ preStop sleep + `spring.lifecycle.timeout-per-shutdown-phase`(기본 30초) + 여유. 마지막으로 종료 시 내릴 것은 readiness뿐이고 liveness를 건드리면 k8s가 재시작을 시도한다는 것, graceful은 웹 요청만 지켜줄 뿐 `@Async`·`@Scheduled`·메시지 컨슈머는 별도 설정이 필요하다는 것까지가 "graceful 켰는데 왜 아직도 에러가 나지"의 나머지 절반이다.**

---

## 0. 질문 + 의도

**질문**: "배포 중 무중단(graceful shutdown)을 위해 Spring Boot에서 어떤 설정과 인프라 구성이 필요한가요?"

**출제 의도**: 배포할 때마다 에러가 소량 발생하는데 아무도 신경 안 쓰는 팀이 많다. 이를 문제로 인식하고 인프라(LB 제외)와 앱(진행 중 요청 완료)의 협업으로 풀어본 사람인지 — 운영 품질에 대한 기준선을 본다.

## 1. 문제 정의 — 배포 에러에는 두 가지 실패 모드가 있고, 처방이 서로 다르다

### 1-1. 전제 지식 — "프로세스를 내린다"는 것이 실제로 무슨 일인가

배포는 결국 구버전 프로세스를 죽이고 신버전을 띄우는 일이다. 그런데 "죽인다"에도 두 가지가 있고, 이 구분을 모르면 뒤의 이야기가 전부 안 붙는다.

리눅스에서 프로세스를 종료시키는 방법은 **시그널(signal)** 을 보내는 것이다. 시그널은 커널이 프로세스에게 보내는 한 글자짜리 통지다.

- **SIGTERM(15)** — "정리하고 끝내라"는 정중한 요청이다. 프로세스는 이 시그널을 **가로채서**(핸들러 등록) 자기가 원하는 정리 작업을 한 뒤 스스로 종료할 수 있다. JVM은 SIGTERM을 받으면 등록된 **셧다운 훅(shutdown hook)** 을 실행하는데, 스프링 부트는 이 훅에서 애플리케이션 컨텍스트를 닫는다. `kill <pid>`가 기본으로 보내는 것이 이것이다.
- **SIGKILL(9)** — "지금 즉시 죽어라"다. 프로세스는 이 시그널을 **가로챌 수 없다.** 커널이 프로세스를 그냥 없앤다. 셧다운 훅도, 컨텍스트 종료도, 진행 중 요청 마무리도 전부 일어나지 않는다. `kill -9 <pid>`가 이것이다.

그래서 이 문서에서 다루는 모든 기법은 **SIGTERM을 받은 뒤 SIGKILL이 오기 전까지의 시간을 어떻게 쓸 것인가**의 이야기다. 배포 스크립트가 SIGTERM 없이 곧바로 `kill -9`를 쏜다면 아래 내용은 전부 무의미하다.

### 1-2. 실패 모드 (a) — 진행 중 요청이 끊긴다

첫 번째 실패 모드는 이렇다. 사용자가 결제 요청을 보냈고, 서버가 DB에 쓰는 중이다. 이때 배포가 프로세스를 내린다.

```
클라이언트 ──POST /payments──> [구버전 앱]
                                   │ DB 트랜잭션 진행 중...
                                   ▼
                              SIGTERM 도착 → 즉시 종료
                                   │
클라이언트 <──커넥션 리셋(또는 502)──┘
```

DB 트랜잭션 자체는 커밋되지 않았으니 롤백되어 데이터는 안전하다. 하지만 **클라이언트가 받는 것은 실패 응답**이다. 사용자 화면에는 "결제에 실패했습니다"가 뜬다. 서버 입장에서는 "데이터 정합성은 지켰다"이지만 사용자 입장에서는 그냥 장애다.

이것이 **앱이 책임지는 실패 모드**다. 앱은 자기가 지금 무슨 요청을 처리 중인지 알고 있으므로, SIGTERM을 받고 곧바로 죽는 대신 "처리 중인 것만 마저 끝내고 죽겠다"고 할 수 있다. 그 스위치가 `server.shutdown=graceful`이다.

### 1-3. 실패 모드 (b) — 순서 레이스

두 번째 실패 모드는 성격이 완전히 다르다. 앱은 이미 "새 요청은 안 받는다" 모드에 들어갔는데, **로드밸런서는 그 사실을 아직 모르고 계속 요청을 보내는** 상황이다.

```
로드밸런서 ──GET /orders──> [구버전 앱]  이미 리스너를 닫음
                                │
로드밸런서 <──connection refused/502──┘
```

이 요청은 애초에 앱에 "들어오지도 못한" 요청이다. 그러니 `server.shutdown=graceful`이 지켜줄 대상이 아니다. graceful은 **이미 들어온 요청**을 보호하는 장치지, 아직 오지 않은 요청까지 받아주는 장치가 아니다. 오히려 graceful의 1단계가 "새 요청 수락 중단"이므로, 이 실패 모드는 graceful을 켜도 그대로 남는다.

| 실패 모드 | 증상 | 누가 막는가 |
|---|---|---|
| (a) 진행 중 요청 끊김 | 처리하다 만 요청이 커넥션 리셋 또는 502 | 앱 (`server.shutdown=graceful`) |
| (b) 순서 레이스 | 앱이 리스너를 닫은 뒤 도착한 요청이 connection refused 또는 502 | 인프라 + 배포 절차 |

### 1-4. 많은 팀이 여기서 멈춘다

현장에서 흔한 진행은 이렇다. 배포 때 에러가 난다는 걸 발견 → 검색 → `server.shutdown=graceful`을 켠다 → 에러가 줄긴 하는데 여전히 난다 → "원래 그런가 보다" 하고 넘어간다.

남은 것이 전부 (b)다. 그리고 (b)는 앱 설정을 아무리 만져도 안 없어진다. **왜 안 없어지는지의 근본 원인이 2절이고, 그것을 아는 것이 이 질문의 본체다.**

## 2. (b)의 근본 원인 — 라우팅에서 빼는 일은 비동기로 전파된다

### 2-1. "목록에서 뺐다"는 원본 하나를 고친 것일 뿐이다

먼저 로드밸런싱이 실제로 어떻게 이뤄지는지부터 보자. "LB가 트래픽을 나눠준다"는 말은 실제로는 **어딘가에 있는 "살아있는 백엔드 목록"을 보고 그중 하나를 고른다**는 뜻이다.

문제는 그 목록이 한 부에만 있는 게 아니라는 점이다. 쿠버네티스라면 노드가 50대일 때 각 노드의 kube-proxy 50개가 **각자 사본을 들고 각자 판단한다.** 인그레스 컨트롤러 파드도 자기 사본을 들고 있고, 클라우드 LB는 아예 클라우드 쪽에 자기 타겟 목록을 따로 갖고 있다.

그래서 "이 인스턴스 빼"는 **중앙 스위치를 한 번 내리는 일이 아니라, 복제된 데이터가 모든 사본에 도달해야 끝나는 일**이다. 원본을 고친 시점과 마지막 사본이 갱신된 시점 사이에는 시간차가 있고, 그 시간차 동안 아직 옛 목록을 들고 있는 프록시는 **죽어가는 인스턴스로 요청을 계속 보낸다.**

비유하면 이렇다. 회사 대표번호를 바꿨다고 치자. 사내 전화번호부(원본)는 즉시 고쳤지만, 이미 인쇄되어 각 부서 책상에 놓인 종이 명부 50부는 그대로다. 명부를 다시 돌리기 전까지 옛 번호로 거는 사람이 계속 나온다. **"고쳤다"와 "모두가 알게 됐다"는 다른 시각의 사건이다.**

### 2-2. 전파가 왜 느린지 — 세 가지 원인

전파 지연은 하나의 뭉뚱그린 지연이 아니라 성격이 다른 세 단계가 더해진 것이다.

| 원인 | 무엇에 걸리는 시간인가 | 대략의 크기 |
|---|---|---|
| ① 헬스체크 주기 | 상대가 "쟤 이제 안 되네"를 **알아채는** 시간. LB는 통보받는 게 아니라 주기적으로 찔러보고 판단한다 | 주기 30초 × 연속 실패 2회 = 최악 60초 이상 |
| ② 목록 전파 | 알아낸 사실이 **모든 사본에 도달**하는 시간. 감시 이벤트가 노드 수만큼 각각 날아가고 도착 시각도 제각각이다 | 수백 ms ~ 수 초 |
| ③ 프록시 규칙 갱신 | 사본을 받은 뒤 **실제 라우팅 규칙을 다시 쓰는** 시간. kube-proxy는 iptables 규칙을 재작성하고, nginx는 upstream을 리로드한다 | 서비스가 많은 클러스터에서 수 초 |

셋을 합치면 **인지(①) + 배포(②) + 적용(③) = 수 초에서 수십 초**다.

여기서 중요한 판단 기준 하나가 나온다. **헬스체크를 실패시켜서 빠지는 방식(readiness DOWN)은 ①이 통째로 붙기 때문에 가장 느리다.** 내가 아무리 빨리 "나 준비 안 됐어"라고 응답해도, 상대가 물어보러 오는 것은 최대 한 주기 뒤다. 반면 API로 직접 디레지스터하거나 쿠버네티스 컨트롤러가 삭제 표시를 감지하는 방식은 ①을 건너뛴다.

### 2-3. "트래픽 차단 신호" 세 가지는 목적이 같고 주체가 다르다

트래픽을 끊는 방법은 환경에 따라 셋 중 하나다. 나란히 놓고 보면 무엇이 무엇인지 헷갈리지 않는다.

| 방법 | 누가 실행하는가 | 방식 | 쓰는 환경 |
|---|---|---|---|
| LB 디레지스터 | 배포 스크립트가 능동적으로 | LB API를 직접 호출해 "이 인스턴스 빼" | VM + 클라우드 LB, LB API 권한이 있을 때 |
| readiness DOWN | 앱이 수동적으로 당함 | 헬스체크에 실패로 응답 → 상대가 알아서 뺌 | LB API 권한이 없을 때. 대신 ①만큼 느리다 |
| 엔드포인트 제거 | 쿠버네티스 컨트롤러가 자동으로 | 파드의 삭제 표시를 보고 컨트롤러가 목록에서 뺌 | 쿠버네티스. 내가 시키는 게 아니라 저절로 일어난다 |

**셋의 공통점이 이 절의 결론이다. 전부 "신호"일 뿐 "완료"가 아니다.**

- 디레지스터 API가 200을 반환해도 → LB 노드들에 반영은 아직이다.
- readiness가 DOWN을 응답해도 → 다음 헬스체크가 오기 전까지는 아무도 모른다.
- 엔드포인트 목록에서 빠져도 → 노드 50대의 iptables는 아직 옛날 것이다.

그래서 차단 신호를 보낸 직후 곧바로 프로세스를 죽이면 안 되고, **가운데에 전파를 기다리는 구간이 반드시 들어가야 한다.**

### 2-4. 쿠버네티스에서는 누가 무엇을 하는가

k8s를 예로 들면 등장인물이 이렇게 나뉜다. 이 표의 핵심은 **죽이는 주체와 목록에서 빼는 주체가 서로 다른 프로세스**라는 점이다.

| 주체 | 어디서 도는가 | 하는 일 |
|---|---|---|
| API 서버(etcd) | 마스터 | 모든 상태의 원본. "이 파드 죽는 중"이라는 사실이 여기 기록된다 |
| kubelet | 노드마다 1개 | 자기 노드의 컨테이너 관리. preStop 훅 실행과 SIGTERM 전송이 이쪽 담당 |
| EndpointSlice 컨트롤러 | 마스터 | "이 서비스의 살아있는 파드 IP 목록" 관리. 목록에서 빼는 것이 이쪽 담당 |
| kube-proxy | 노드마다 1개 | 위 목록을 보고 자기 노드의 iptables/IPVS 규칙을 다시 쓴다 |
| 인그레스 컨트롤러 | 파드로 여러 개 | 위 목록을 보고 자기 upstream 설정을 다시 쓴다 |
| 클라우드 LB | 클라우드 쪽 | 자체 타겟 목록 보유. 컨트롤러가 API로 디레지스터해줘야 빠진다 |

쿠버네티스 공식 문서도 이 동시성을 명시한다. "kubelet이 파드의 graceful shutdown을 시작하는 것과 **동시에**, 컨트롤 플레인이 종료 중인 파드를 EndpointSlice에서 제거할지 평가한다." 두 일은 순차가 아니라 병렬이고, **어느 쪽이 먼저 끝나는지 보장이 없다.**

### 2-5. 타임라인 — 시간차가 정확히 어디에서 벌어지는가

`kubectl delete pod`나 롤링 업데이트가 하는 일은 딱 하나, API 서버의 파드 객체에 **삭제 표시(`deletionTimestamp`)를 찍는 것**뿐이다. 그 순간 이걸 지켜보던 두 부류가 동시에, 각자 움직인다.

```
                     [API 서버] 파드에 "삭제 중" 표시  (t=0)
                           │
             ┌─────────────┴──────────────────────────────┐
      (경로 A: 죽이는 쪽)                          (경로 B: 트래픽 끊는 쪽)
             ▼                                            ▼
        그 노드의 kubelet                        EndpointSlice 컨트롤러
             │                                            │
        preStop 훅 실행                            목록에서 파드 IP 제거
             │                                            │
        SIGTERM 전송                       ┌──────────────┼───────────────┐
             │                             ▼              ▼               ▼
     앱: 새 요청 거부 시작            노드1 kube-proxy  노드2 ...   nginx 인그레스
                                     iptables 재작성            upstream 리로드
                                                                          │
                                                                          ▼
                                                              클라우드 LB 디레지스터
```

경로 A는 짧다. 마스터에서 그 노드의 kubelet으로, 다시 컨테이너로. 한두 홉이면 끝난다.

경로 B는 길다. 마스터에서 목록을 갱신하고, 클러스터의 **모든 노드**가 각자 그 변화를 감지하고, **각자** iptables를 재작성하고, 인그레스도 각자 리로드하고, 클라우드 LB는 API 호출까지 거친다.

그래서 preStop 훅이 없으면 A가 먼저 끝난다. 시각으로 놓고 보면 이렇다.

```
 t=0.00s   API 서버에 삭제 표시. 경로 A와 B가 동시에 출발.
 t=0.05s   [A] kubelet이 SIGTERM 전송.
 t=0.06s   [A] 앱이 리스너를 닫는다 — 이 시점부터 새 커넥션은 전부 거부된다.
           ★ 여기서부터 사고 구간이 열린다 ★
 t=0.30s   [B] EndpointSlice에서 파드 IP 제거 완료. 하지만 이건 "원본"일 뿐이다.
 t=0.9s    [B] 노드1의 kube-proxy가 iptables 재작성 완료.
 t=1.4s    [B] 노드2의 kube-proxy가 iptables 재작성 완료.
 t=2.7s    [B] nginx 인그레스 upstream 리로드 완료.
 t=6.0s    [B] 클라우드 LB 타겟 디레지스터 반영 완료.
           ★ 여기서 사고 구간이 닫힌다 ★

 → t=0.06s ~ t=6.0s 사이에 도착한 요청은 전부 connection refused / 502.
   초당 500 요청을 받던 서비스라면 약 3,000건이 실패한다.
```

**누가 버그를 낸 것이 아니다.** 두 경로의 순서를 맞춰줄 조정자가 애초에 설계상 없다. 그러니 순서는 우리가 만들어 넣어야 한다.

## 3. 처방 — 앱 설정, 전파 대기, 시간 예산

### 3-1. 앱: `server.shutdown=graceful`이 하는 일

먼저 실패 모드 (a)를 막는 앱 설정이다.

```yaml
server:
  shutdown: graceful
spring:
  lifecycle:
    # 진행 중 요청이 끝나기를 기다려주는 상한. 기본 30s.
    # 이 시간을 넘긴 요청은 포기하고 종료 절차를 계속 진행한다.
    timeout-per-shutdown-phase: 30s
```

**버전 주의 (2026년 9월 기준).** `server.shutdown`의 기본값은 스프링 부트 버전에 따라 다르다.

- 부트 2.3(graceful shutdown 도입) ~ 3.3: 기본값 `immediate`. 명시적으로 `graceful`로 켜야 한다.
- 부트 3.4 이상: **기본값이 `graceful`로 바뀌었다.** 3.4 릴리스 노트가 "내장 웹 서버의 graceful shutdown이 이제 기본으로 활성화된다"고 명시하며, 예전 동작이 필요하면 `server.shutdown=immediate`로 되돌리라고 안내한다.

즉 부트 3.4 이상을 쓰고 있다면 "graceful을 켰다"는 것 자체는 자랑거리가 아니고, 이미 켜져 있는데도 배포 에러가 난다면 그건 100% (b) 쪽 문제라는 뜻이다.

SIGTERM 수신 시 동작 순서는 이렇다.

```
SIGTERM 수신
   │
   ├─ ① 신규 요청 수용 중단
   │     톰캣/Jetty/Reactor Netty: 네트워크 계층에서 아예 수락을 멈춘다
   │     Undertow: 커넥션은 받되 즉시 503으로 응답한다
   │
   ├─ ② 진행 중(in-flight) 요청 완료 대기
   │     최대 timeout-per-shutdown-phase(기본 30s)까지
   │
   └─ ③ 애플리케이션 컨텍스트 종료
         SmartLifecycle 빈들을 phase 역순으로 stop → 커넥션 풀 close → JVM 종료
```

②의 타임아웃 이름에 "per-shutdown-phase"가 들어간 이유를 짚어두면 좋다. 이것은 **전체 종료 시간의 상한이 아니라 종료 단계 하나당 상한**이다. `SmartLifecycle` 빈들은 phase 값에 따라 여러 단계로 나뉘어 역순으로 멈추는데, 각 단계마다 이 타임아웃이 따로 적용된다. 그래서 최악의 경우 총 종료 시간은 30초보다 길어질 수 있다. 뒤의 시간 예산 계산에서 여유를 두는 이유 중 하나가 이것이다.

### 3-2. graceful이 **하지 않는** 일 — 여기가 나머지 절반이다

`server.shutdown=graceful`은 이름이 오해를 부른다. 이것은 **웹 서버(HTTP 요청 처리)에 한정된 장치**다. 앱 안에서 도는 다른 종류의 작업은 이 설정의 사정권 밖이다.

**(1) `@Async` 작업.** `@Async` 메서드는 `ThreadPoolTaskExecutor`가 별도 스레드에서 돌린다. 이 실행기는 컨텍스트 종료 시 멈추는데, 기본 동작이 **진행 중 작업을 인터럽트하고 큐에 남은 작업을 버리는 것**이다. 진행 중이던 비동기 작업이 그대로 날아간다.

```yaml
# before: 아무 설정 없음 — 종료 시 @Async 진행 중 작업이 인터럽트된다
# after:
spring:
  task:
    execution:
      shutdown:
        # 진행 중 작업이 끝날 때까지 기다린 뒤 실행기를 내린다. 기본값은 false다.
        await-termination: true
        # 무한정 기다리면 배포가 안 끝나므로 상한을 둔다.
        await-termination-period: 20s
    scheduling:
      shutdown:
        # @Scheduled를 돌리는 스케줄러도 별개의 실행기라 따로 설정해야 한다.
        await-termination: true
        await-termination-period: 20s
```

**(2) `@Scheduled` 작업.** 스케줄러도 마찬가지로 별도 실행기이며, 위처럼 `spring.task.scheduling.shutdown.*`을 따로 설정해야 한다. 특히 배치성 `@Scheduled` 작업이 몇 분씩 걸린다면 이 값을 늘리는 것이 답이 아니다 — 배포 때마다 그만큼 기다려야 하기 때문이다. 상세한 스레드 모델과 대안은 [34-scheduled-tasks-threading.md](34-scheduled-tasks-threading.md), `@Async`의 실행기 구성은 [15-async-annotation.md](15-async-annotation.md)를 참고한다.

**(3) 메시지 컨슈머.** Kafka나 RabbitMQ 리스너 컨테이너는 HTTP 요청이 아니므로 `server.shutdown`과 아무 관계가 없다. 이들은 `SmartLifecycle` 빈이라 컨텍스트 종료 단계에서 멈추지만, "처리 중이던 메시지를 끝까지 처리하고 ack까지 보내는가"는 컨테이너별 종료 설정과 ack 모드에 달린 별개의 축이다. 여기서 실수하면 **웹 에러는 0건인데 메시지가 중복 처리되는** 형태로 문제가 옮겨간다.

정리하면, "graceful 켰는데 왜 아직도 에러가 나지"의 답은 두 갈래다. **HTTP 에러가 남는다면 원인은 (b) 순서 레이스이고, HTTP는 깨끗한데 백그라운드 작업이 잘린다면 원인은 이 절이다.**

### 3-3. 종료 시에는 readiness만 내린다 — liveness는 절대 건드리지 않는다

쿠버네티스의 두 probe는 이름이 비슷하지만 **실패했을 때 k8s의 대응이 정반대**다.

- **liveness 실패** → "이 컨테이너 죽었네" → **컨테이너를 재시작한다.**
- **readiness 실패** → "지금은 트래픽 받을 상태가 아니네" → **서비스 목록에서만 뺀다.** 프로세스는 그대로 둔다.

종료 절차에서 원하는 것은 후자다. 트래픽만 빼고 프로세스는 살아 있어야 진행 중 요청을 마저 처리할 수 있다. 여기서 liveness까지 실패시키면 k8s가 "고장 났으니 재시작"으로 판단해 종료 중인 컨테이너를 되살리려 든다.

이 구분은 종료 때만 쓰이는 게 아니라 평상시 DB 순단 대응에서 훨씬 자주 문제가 된다. 두 probe의 역할 분담과 "DB 체크를 liveness에 넣으면 왜 재시작 폭풍이 나는가"는 별도 문서에 정리돼 있다: [liveness-readiness-probe-db-check.md](../15-container-infra/liveness-readiness-probe-db-check.md).

여기서는 종료 시퀀스에 한정해 한 가지만 더 짚는다. **스프링 부트는 종료가 시작되면 readiness 상태를 자동으로 `REFUSING_TRAFFIC`으로 바꾼다.** 부트 공식 문서의 애플리케이션 수명주기 표가 그렇게 정의한다.

| 종료 단계 | LivenessState | ReadinessState | HTTP 서버 |
|---|---|---|---|
| Running | CORRECT | ACCEPTING_TRAFFIC | 요청 수락 |
| Graceful shutdown | CORRECT | REFUSING_TRAFFIC | 새 요청 거부 |
| Shutdown complete | 해당 없음 | 해당 없음 | 종료됨 |

liveness는 종료 중에도 CORRECT로 유지된다는 점을 보라. 부트가 이렇게 설계한 이유가 방금 말한 그것이다.

그런데 **이 자동 전환이 (b) 레이스를 풀어주지는 못한다.** 표를 다시 보면 readiness가 REFUSING_TRAFFIC이 되는 시점은 "graceful shutdown 단계"다. 즉 **이미 SIGTERM을 받은 뒤**다. 우리가 필요한 것은 SIGTERM보다 **먼저** 트래픽이 끊기는 것인데, 부트의 자동 전환은 그보다 늦게 일어난다. 이것이 다음 절의 preStop sleep이 필요한 정확한 이유다.

### 3-4. `preStop sleep` — 왜 하필 "아무것도 안 하기"가 처방인가

preStop 훅은 컨테이너에 SIGTERM을 보내기 **직전에** kubelet이 실행해주는 명령이다. 이름만 보면 "종료 전 정리 작업"을 넣는 자리 같고, 실제로 그런 용도로도 쓴다. 그런데 무중단 배포 맥락에서 여기 들어가는 것은 대개 `sleep 15` 한 줄이다.

처음 보면 이상하다. 아무것도 안 하고 그냥 15초를 버리는 것이 왜 처방인가.

답은 2-5의 타임라인에 있다. **문제는 앱이 정리할 게 남아서가 아니라, 경로 B(트래픽 끊기)가 경로 A(죽이기)보다 느려서 생긴다.** 그러니 처방은 두 가지 중 하나여야 한다 — B를 빠르게 만들거나, A를 느리게 만들거나. B는 클러스터 규모와 프록시 구현에 달린 것이라 우리가 손댈 수 없다. 그래서 **A에 일부러 브레이크를 건다.** 그것이 sleep이다.

여기서 결정적인 사실 하나. **sleep이 도는 동안 앱은 아무 일도 겪지 않는다.** SIGTERM은 아직 오지 않았으므로 앱은 여전히 정상 서빙 중이고, 이 15초 사이에 도착한 요청도 전부 정상 처리된다. 즉 sleep 구간은 "죽어가는 시간"이 아니라 **"멀쩡한 채로 기다려주는 시간"** 이다.

```
[preStop sleep 없이]
  t=0     삭제 표시
  t=0.05  SIGTERM → 앱이 리스너 닫음    ← 여기서 사고 시작
  t=6.0   전파 완료                      ← 여기서 사고 종료
          사고 구간 약 6초

[preStop sleep 15초]
  t=0     삭제 표시
  t=0.05  kubelet이 preStop 실행 시작 (sleep 15)
          ── 이 구간 내내 앱은 정상 서빙. 새 요청도 정상 처리된다 ──
  t=6.0   전파 완료. 이제 아무도 이 파드로 보내지 않는다.
  t=15.05 preStop 종료 → SIGTERM → 앱이 리스너 닫음
          ← 닫을 때는 이미 오는 요청이 없다. 사고 구간 0초.
```

sleep 길이는 "전파가 끝나는 데 걸리는 최악의 시간"보다 커야 한다. 클라우드 LB까지 물려 있는 구성에서 10~15초가 흔한 출발점이고, 정확히 정하려면 배포 중 5xx가 실제로 언제까지 나는지를 관측해서 역산한다.

VM 환경에서 `deregister → sleep → kill` 순서를 쓰는 것도 정확히 같은 이유다. 이름만 preStop이 아닐 뿐 구조가 같다.

### 3-5. 시간 예산 — 세 숫자가 어긋나면 graceful이 통째로 무의미해진다

여기가 실무에서 가장 자주 틀리는 지점이다. 관련된 숫자가 셋인데, 서로 독립된 값이 아니라 **하나가 나머지 둘을 담는 총 예산**이다.

| 값 | 누가 지키는가 | 기본값 | 의미 |
|---|---|---|---|
| `terminationGracePeriodSeconds` | 쿠버네티스 | 30초 | 삭제 표시부터 SIGKILL까지의 **총** 시간 |
| preStop 훅 실행 시간 | kubelet | 없음(미설정) | 전파를 기다리는 구간 |
| `spring.lifecycle.timeout-per-shutdown-phase` | 스프링 부트 | 30초 | SIGTERM 이후 진행 중 요청을 기다리는 상한 |

쿠버네티스 문서가 명시하는 핵심 규칙이 둘이다.

1. **"파드의 종료 유예 기간 카운트다운은 preStop 훅이 실행되기 전에 시작된다."** 즉 preStop에 쓴 시간은 총 예산에서 **차감된다.** preStop 15초 뒤에 30초가 새로 주어지는 것이 아니다.
2. **"preStop 훅이 유예 기간이 끝난 뒤에도 여전히 실행 중이면, kubelet은 2초의 일회성 유예 연장을 요청한다."** 딱 2초다. 그 뒤에는 SIGKILL이다.

이제 기본값 그대로 두면 무슨 일이 나는지 계산해 보자.

```
terminationGracePeriodSeconds = 30 (기본값)
preStop sleep                 = 15
timeout-per-shutdown-phase    = 30 (기본값)

 t=0     삭제 표시. 30초 카운트다운 시작.
 t=0     preStop sleep 15 시작
 t=15    preStop 종료 → SIGTERM 전송
         앱은 "최대 30초까지 진행 중 요청을 기다리겠다"고 생각한다
         하지만 남은 예산은 30 - 15 = 15초뿐이다
 t=30    ★ SIGKILL ★
         → 15초 넘게 걸리던 요청은 그냥 끊긴다. graceful이 무의미해진다.
```

필요한 값은 이렇게 나온다.

```
terminationGracePeriodSeconds ≥ preStop sleep + timeout-per-shutdown-phase + 여유
                              ≥ 15           + 30                         + 5~15
                              ≥ 50 ~ 60      → 60으로 잡는다
```

여유를 두는 이유는 두 가지다. 첫째, 3-1에서 본 대로 `timeout-per-shutdown-phase`는 단계 하나당 상한이라 컨텍스트 종료 전체는 그보다 길어질 수 있다. 둘째, 커넥션 풀 종료·리스너 컨테이너 정지 같은 마무리 작업이 그 뒤에 더 붙는다.

**세 값이 어긋났을 때의 증상을 알아두면 진단이 빨라진다.**

- `terminationGracePeriodSeconds`가 너무 짧다 → 진행 중 요청이 끊기는데 앱 로그에는 종료 로그조차 다 안 찍힌다. SIGKILL은 로그를 남길 틈을 주지 않기 때문이다.
- preStop sleep이 너무 짧다 → 배포 초반 몇 초에 502가 몰린다. 요청 자체가 앱에 도달하지 못한 형태다.
- `timeout-per-shutdown-phase`가 너무 짧다 → 오래 걸리는 요청만 선택적으로 실패한다. 짧은 요청은 멀쩡하다.

### 3-6. 전체 설정 — 쿠버네티스

```yaml
spec:
  # 총 예산. preStop(15) + graceful(30) + 여유(15) = 60
  terminationGracePeriodSeconds: 60
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            # 정리 작업이 아니라 엔드포인트 제거가 전파될 시간을 버는 구간.
            # 이 15초 동안 앱은 정상 서빙하며 새 요청도 정상 처리한다.
            command: ["sh", "-c", "sleep 15"]
      readinessProbe:
        # 롤링 업데이트의 반대 방향 보호막 — 신버전이 준비되기 전에
        # 트래픽이 들어오는 것을 막는다.
        httpGet: { path: /actuator/health/readiness, port: 8080 }
      livenessProbe:
        # 종료 절차에서 이 probe가 실패하면 k8s가 재시작을 시도한다.
        # 그래서 여기에는 DB 같은 외부 의존성을 절대 넣지 않는다.
        httpGet: { path: /actuator/health/liveness, port: 8080 }
```

`/actuator/health/liveness`와 `/actuator/health/readiness` 두 경로는 부트가 제공하는 health group이다. 다만 actuator를 여는 순간 보안 면적이 생기므로 노출 범위는 별도 기준을 따른다: [30-actuator-endpoints-security.md](30-actuator-endpoints-security.md).

### 3-7. 전체 설정 — VM + 로드밸런서

쿠버네티스가 아니라면 순서를 보장할 주체가 없다. **배포 스크립트가 직접 세 단계를 만들어야 한다.**

```bash
#!/bin/bash
set -euo pipefail

# ① 트래픽 차단 신호 — LB에게 "이 인스턴스 빼"라고 알린다.
#    이 호출이 200을 반환해도 "빠졌다"가 아니라 "요청했다"일 뿐이다.
aws elbv2 deregister-targets \
    --target-group-arn "$TG_ARN" \
    --targets "Id=$INSTANCE_ID"

# ② 전파 대기 — ①이 실제로 모든 LB 노드에 반영될 때까지 기다린다.
#    ALB라면 대상 그룹의 deregistration_delay(기본 300초) 설정과 맞춰
#    실제 draining이 끝나는 시간을 관측해서 정한다.
sleep "$DRAIN_SECONDS"

# ③ 이제 SIGTERM. 여기서부터는 진행 중 요청만 남았다.
kill -TERM "$PID"

# ④ graceful이 끝날 시간을 준 뒤에야 강제 종료. 이 대기 없이 -9를 쏘면
#    앞의 모든 절차가 무의미해진다.
for _ in $(seq 1 40); do
    kill -0 "$PID" 2>/dev/null || exit 0
    sleep 1
done
kill -KILL "$PID"
```

LB API 권한이 없는 환경이라면 ①을 "관리 엔드포인트를 호출해 readiness를 DOWN으로 전환"으로 대체할 수 있다. 단 그렇게 하면 2-2의 ①(헬스체크 주기)이 통째로 붙으므로, **`sleep $DRAIN_SECONDS`를 "헬스체크 주기 × 실패 판정 횟수 + 전파 시간"만큼 길게** 잡아야 한다. 주기 10초에 2회 연속 실패로 판정한다면 최악 20초에 전파 시간까지 더한 값이다.

### 3-8. 프로세스를 곱게 내리는 것만으로는 부족하다

마지막으로 무중단 배포의 나머지 조건 하나를 짚는다. **롤링 배포는 정의상 신버전과 구버전이 동시에 살아 있는 시간을 만든다.** 파드 10개를 하나씩 교체한다면, 중간의 몇 분 동안 같은 DB를 구버전 7개와 신버전 3개가 함께 쓰고 있다.

그래서 프로세스 종료를 아무리 곱게 해도 다음이 깨지면 배포 중 에러가 난다.

- **DB 스키마 하위호환.** 컬럼을 삭제하거나 `NOT NULL`을 추가하는 마이그레이션이 배포와 같이 나가면, 아직 살아 있는 구버전이 그 순간 깨진다. 스키마 변경은 "추가 → 양쪽 버전 배포 완료 → 제거"의 여러 단계로 쪼갠다.
- **메시지·이벤트 포맷 하위호환.** 신버전이 발행한 새 포맷 메시지를 구버전 컨슈머가 읽는 상황이 실제로 생긴다.
- **세션·캐시 직렬화 포맷.** 공유 세션 저장소에 신버전이 쓴 객체를 구버전이 역직렬화하다 깨진다.

**무중단 배포는 종료 절차의 문제이자 호환성의 문제다.** 앞의 3-1~3-7을 완벽히 해도 이 셋 중 하나가 깨지면 배포 중 에러는 그대로 난다.

## 4. 꼬리질문 대비 포인트

### "graceful을 켰는데도 배포 때 에러가 납니다. 왜죠?"

**에러의 종류부터 나눠서 답한다.** 이 구분을 못 하고 설정만 나열하면 감점이다.

- HTTP 5xx/connection refused가 배포 **초반 몇 초에 몰린다** → (b) 순서 레이스다. 트래픽 차단 신호가 전파되기 전에 SIGTERM이 도착했다. 처방은 preStop sleep 또는 디레지스터 후 draining 대기.
- **오래 걸리는 요청만** 골라서 실패한다 → 시간 예산 문제다. `terminationGracePeriodSeconds`가 preStop + `timeout-per-shutdown-phase`를 못 담아서 SIGKILL이 먼저 왔거나, `timeout-per-shutdown-phase` 자체가 짧다.
- HTTP는 깨끗한데 **배치·비동기 작업이 잘린다** → 3-2다. graceful은 웹 요청만 보호한다. `spring.task.execution.shutdown.await-termination`과 스케줄러 쪽 설정을 따로 켜야 한다.
- **배포 후에** 데이터 오류가 난다 → 3-8이다. 종료 절차가 아니라 신구 버전 호환성 문제다.

한 문장으로 정리하면 이렇다. **앱 설정은 이미 들어온 요청만 지킬 수 있고, 아직 오지 않은 요청은 인프라와 배포 절차의 몫이다.**

### "preStop에 왜 sleep을 넣나요? 아무것도 안 하는데 의미가 있나요?" (시니어 변별 포인트)

**의도가 "정리"가 아니라 "대기"라는 것을 정확히 말하는지가 갈림길이다.**

파드를 죽이는 경로와 라우팅에서 빼는 경로는 서로에게 보고하지 않는 별개의 비동기 경로이고, 죽이는 쪽이 구조적으로 항상 빠르다. 우리가 손댈 수 있는 것은 느린 쪽이 아니라 빠른 쪽이므로, **빠른 쪽에 브레이크를 걸어 두 경로의 순서를 강제로 맞춘다.** 그 브레이크가 sleep이다.

여기에 반드시 덧붙일 것이 하나 더 있다. **sleep 구간 동안 앱은 죽어가는 중이 아니라 멀쩡하다.** SIGTERM이 아직 오지 않았으므로 그 사이 도착한 요청도 전부 정상 처리된다. 이걸 모르면 "그 15초 동안 들어온 요청은 어떻게 되냐"는 반문에 막힌다.

가산점 포인트: **sleep은 임시방편이라는 인식**까지 보이면 좋다. 근본 해법은 "SIGTERM 전송 전에 엔드포인트 제거 완료를 확인하는 것"인데 쿠버네티스가 그 보장을 제공하지 않으므로, 관측된 최악 전파 시간보다 넉넉한 sleep으로 대체하고 있는 것이다. 그래서 sleep 값은 감으로 정하는 게 아니라 **배포 중 5xx가 실제로 언제까지 나는지를 관측해 역산해야** 한다.

### "종료할 때 readiness만 내리고 liveness는 왜 안 내리나요?"

**두 probe는 실패 시 k8s의 대응이 정반대이기 때문이다.**

- readiness 실패 → 서비스 목록에서만 제외한다. 프로세스는 살아 있다. 이것이 종료 절차에서 원하는 것이다 — 트래픽만 끊고 진행 중 요청은 마저 처리해야 하니까.
- liveness 실패 → **컨테이너를 재시작한다.** 종료 중인 컨테이너를 k8s가 되살리려 들면서 상황이 꼬인다.

스프링 부트도 이 원칙대로 동작한다. 종료가 시작되면 readiness는 `REFUSING_TRAFFIC`으로 바뀌지만 **liveness는 CORRECT를 유지한다.**

한 걸음 더 나가면 이 원칙은 종료 때만의 이야기가 아니다. **재기동으로 고칠 수 없는 것을 liveness에 넣으면 안 된다**가 일반 규칙이고, 그래서 DB 헬스체크는 readiness에만 넣는다. DB 순단에 liveness가 걸리면 전 파드가 동시에 재시작하는 폭풍이 난다. 상세: [liveness-readiness-probe-db-check.md](../15-container-infra/liveness-readiness-probe-db-check.md).

### "진행 중인 요청이 5분짜리라면 어떻게 하나요?"

**설정으로 푸는 문제가 아니라는 것을 말해야 한다.**

`timeout-per-shutdown-phase`를 5분으로 늘리면 산술적으로는 되지만, 그러면 `terminationGracePeriodSeconds`도 5분 이상이어야 하고, 파드 10개를 하나씩 교체하는 롤링 배포는 최악의 경우 50분이 걸린다. 배포와 롤백이 그만큼 느려진다는 뜻이고, 장애 상황에서 롤백이 50분 걸리는 것은 그 자체로 더 큰 위험이다.

**설계 정답은 요청-응답 안에서 5분짜리 작업을 하지 않는 것이다.** 요청은 작업을 큐에 넣고 작업 ID만 즉시 반환하고, 실제 처리는 워커가 맡고, 클라이언트는 폴링이나 콜백으로 결과를 받는다. 이렇게 바꾸면 웹 요청은 수십 ms로 짧아져 graceful이 쉽게 지켜주고, 워커는 중단되더라도 큐에서 다시 집어 가면 되므로 배포에 강해진다.

즉 **"긴 요청을 어떻게 지킬까"가 아니라 "왜 긴 요청이 있어야 하는가"를 되묻는 방향**으로 답한다.

### "무한정 기다리게 하면 안 되나요?"

안 된다. 상한이 없으면 **좀비 배포**가 된다. 파드 하나가 안 죽으면 롤링 업데이트가 그 자리에서 멈추고, 신버전 배포가 영영 안 끝난다. 장애 대응 중이라면 롤백조차 못 하게 된다.

게다가 쿠버네티스는 어차피 상한을 강제한다. `terminationGracePeriodSeconds`가 지나면 SIGKILL이 오고, preStop 훅이 아직 돌고 있어도 2초의 일회성 연장 뒤에는 죽는다. 앱 쪽에서 무한정을 원해도 플랫폼이 허용하지 않는다.

그래서 방향은 "상한을 없애기"가 아니라 **"상한 안에 들어오도록 작업을 짧게 만들기"** 다. 위 질문의 답과 같은 결론으로 수렴한다.

### "배포 중 에러가 실제로 0이 됐는지 어떻게 확인하나요?" (시니어 변별 포인트)

**설정을 넣었다는 사실이 아니라 관측 결과로 답해야 한다.** 이 질문에 "설정 넣었으니 됐습니다"로 답하면 운영 경험이 없다는 신호가 된다.

확인 방법은 세 층이다.

1. **LB 쪽 지표.** 앱 로그가 아니라 LB의 5xx 카운트를 본다. (b) 레이스로 죽은 요청은 애초에 앱에 도달하지 못했으므로 **앱 로그에는 흔적이 남지 않는다.** 앱 로그만 보고 "에러 없다"고 판단하는 것이 가장 흔한 착각이다.
2. **배포 중 부하 시험.** 스테이징에서 초당 수백 요청을 흘리며 롤링 배포를 돌리고, 실패 건수와 실패가 몰린 시각 구간을 본다. 실패 구간의 길이가 곧 부족한 sleep 시간이다.
3. **종료 로그의 완결성.** `Commencing graceful shutdown`으로 시작해 컨텍스트 종료 로그까지 매번 끝까지 찍히는지 본다. 로그가 중간에 끊긴다면 SIGKILL이 먼저 온 것이고, 시간 예산이 어긋났다는 뜻이다.

## 한 줄 요약

배포 에러는 (a) 진행 중 요청 끊김과 (b) 순서 레이스 두 갈래이고, (a)는 앱의 `server.shutdown=graceful`(부트 3.4부터 기본값)이 막지만 (b)는 파드를 죽이는 경로와 라우팅에서 빼는 경로가 서로 보고하지 않는 별개의 비동기 경로라 앱이 손댈 수 없으므로 — 죽이는 쪽에 `preStop sleep`으로 브레이크를 걸어 전파를 기다려주고, `terminationGracePeriodSeconds` ≥ preStop + `timeout-per-shutdown-phase` + 여유로 시간 예산을 맞추고, 종료 시에는 readiness만 내리며(liveness를 내리면 재시작이 걸린다), `@Async`·`@Scheduled`·메시지 컨슈머는 graceful의 사정권 밖이므로 따로 챙기는 것까지가 무중단 배포의 완성형이다.
