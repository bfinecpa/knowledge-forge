# AOP 동작 원리 — JDK Dynamic Proxy vs CGLIB, "붙였는데 동작 안 함"의 뿌리

> 핵심 관전 포인트: **스프링 AOP는 대상 빈을 감싸는 프록시 객체를 만들어
> 컨테이너에 등록하고, 주입받는 쪽은 전부 이 프록시를 받는 구조다.
> 프록시가 "원본인 척"하는 방법은 자바에 딱 두 가지 — 인터페이스를
> 구현하거나(JDK Dynamic Proxy), 원본 클래스를 상속하거나(CGLIB).
> 스프링 부트 기본값은 CGLIB이며, 상속 기반이라는 사실에서
> `final` 클래스(기동 실패)·`final` 메서드(조용한 미적용)라는
> 실무 함정이 그대로 따라 나온다. @Transactional, @Cacheable, @Async가
> "붙였는데 동작 안 하는" 상황은 전부 이 프록시 구조로 설명된다.**

---

## 0. 질문 + 의도

**질문**: "AOP의 동작 원리(JDK Dynamic Proxy vs CGLIB)를 설명해주세요."

**출제 의도**: 프록시 기반이라는 사실을 모르면 `@Transactional`, `@Async`,
`@Cacheable`이 "붙였는데 동작 안 하는" 상황을 이해할 수 없다. 스프링의
마법 대부분이 이 하나의 원리로 설명되므로, 이걸 아는지가 스프링을
"쓰는" 사람과 "이해하는" 사람의 분기점이다.

## 1. 동작 원리 — 프록시가 메서드 호출을 가로챈다

AOP(관점 지향 프로그래밍)는 트랜잭션, 로깅, 캐싱처럼 여러 곳에 반복되는
부가 기능(횡단 관심사)을 비즈니스 코드에서 분리하는 기법이다.
스프링 AOP의 구현 방식은 **런타임 프록시**다: 빈을 만들 때 원본 대신
원본을 감싼 대리인 객체를 컨테이너에 등록한다.

```java
// 프록시가 하는 일 (개념적으로)
public Order order(OrderRequest request) {
    // ① 전작업 (예: 트랜잭션 시작, 캐시 조회, 로그)
    Order result = target.order(request);   // ② 진짜 객체의 메서드 실행
    // ③ 후작업 (예: 커밋, 캐시 저장)
    return result;                           // ④ 리턴값 그대로 반환
}
```

핵심은 **다른 빈이 주입받는 것이 원본이 아니라 프록시**라는 점이다.
부가 기능 코드는 프록시에만 있으므로, 프록시를 거치지 않는 호출
(자기 호출 `this.method()`)에는 부가 기능이 걸리지 않는다.

전체 구도를 그려두면 각 기술의 위치가 분명해진다. JDK Dynamic Proxy와
CGLIB은 **"프록시 방식 안에서의" 선택지**이고, AspectJ는 프록시 방식
자체의 바깥에 있는 **다른 계열**이다.

```
AOP를 구현하는 방법
├─ ① 프록시 방식 (스프링 AOP)
│   ├─ JDK Dynamic Proxy  ← 인터페이스 구현으로 "척"
│   └─ CGLIB              ← 상속으로 "척"
└─ ② 바이트코드 위빙 방식 (AspectJ)
    └─ 컴파일/로드 시점에 클래스 코드 자체를 수정
```

AspectJ가 이 문서에 등장하는 이유는 **대조군**이기 때문이다. 자기 호출
미적용, `final`/`private` 미적용 같은 함정은 "AOP의 한계"가 아니라
"프록시 방식의 한계"다. AspectJ는 프록시를 만들지 않고 원본 클래스의
바이트코드에 부가 기능 코드를 **직접 박아넣기** 때문에, 프록시를 거칠
필요가 없어서 이 제약이 전부 사라진다. 대조군이 있어야 "이 함정의
원인은 프록시 구조다"라는 진단이 완성된다. 비유하면 — 프록시는 담당자
앞에 안내원을 앉히는 방식이고, AspectJ는 담당자 본인을 교육시켜서
기록까지 하게 만드는 방식이라, 안내원 방식의 문제(직접 말 걸면 기록 안
됨)가 후자에는 아예 없다.

## 2. 프록시는 어떻게 "원본인 척"하나 — 두 가지 방법

프록시의 존재 조건은 **원본과 같은 타입으로 취급될 수 있어야 한다**는
것이다. 주입받는 쪽 코드는 `OrderService orderService = ...`처럼
원래 타입 변수에 담아 쓰기 때문이다. 자바에서 어떤 객체가 다른 타입
"인 척"할 수 있는 방법은 정확히 두 가지고, 그것이 두 프록시 기술의
정체다.

|               | JDK Dynamic Proxy                                             | CGLIB                             |
|---------------|---------------------------------------------------------------|-----------------------------------|
| 같은 타입인 척하는 방법 | 대상의 **인터페이스를 구현**                                             | 대상 클래스를 **상속**한 자식 클래스 생성         |
| 필요한 것         | 인터페이스가 반드시 있어야 함                                              | 클래스만 있으면 됨                        |
| 구현 수단         | JDK 내장 리플렉션 (`java.lang.reflect.Proxy` + `InvocationHandler`) | 바이트코드 생성 라이브러리 (런타임에 자식 클래스를 찍어냄) |
| 프록시의 타입       | 인터페이스 타입으로만 캐스팅 가능                                            | 구체 클래스 타입으로도 캐스팅 가능               |
| 못 만드는 경우      | 인터페이스가 없으면 불가                                                 | `final` 클래스면 불가                   |

```java
// JDK Dynamic Proxy: 인터페이스를 구현한 가짜 객체
public interface OrderService {

    Order order(OrderRequest request);
}

OrderService proxy = (OrderService) Proxy.newProxyInstance(
    classLoader,
    new Class[]{OrderService.class},   // "이 인터페이스인 척 해라"
    invocationHandler                  // 가로챈 호출을 처리할 로직
);

// CGLIB: 런타임에 이런 자식 클래스를 바이트코드로 생성하는 것과 같음
public class OrderServiceProxy extends OrderService {

    @Override
    public Order order(OrderRequest request) {
        // 전작업 → super 격의 원본 호출 → 후작업
    }
}
```

## 3. 스프링 부트의 선택 — 기본값은 CGLIB

스프링 부트는 `proxyTargetClass=true`, 즉 **인터페이스가 있어도 CGLIB**을
기본으로 쓴다. 이유는 두 가지다.

1. **인터페이스 없는 빈도 프록시할 수 있어야 한다.** 요즘 실무는
   구현체가 하나뿐인 서비스에 인터페이스를 강제로 만들지 않는 경우가
   많다. JDK 프록시만 쓰면 이런 빈에는 @Transactional을 못 건다.
2. **타입 캐스팅 사고 방지.** JDK 프록시는 인터페이스인 척만 할 수 있어서
   구체 클래스로 캐스팅하면 `ClassCastException`이 난다.

```java
// JDK 프록시 환경에서 나는 고전적 사고
OrderService bean = context.getBean(OrderService.class);       // OK (인터페이스)
OrderServiceImpl impl = (OrderServiceImpl) bean;                // ❌ ClassCastException!
// bean은 OrderServiceImpl의 자식이 아니라 "OrderService 인터페이스를 구현한 남남"이기 때문
```

## 4. 상속 기반이라서 생기는 함정 — final

CGLIB이 "상속받은 자식 클래스"라는 사실에서 함정이 기계적으로 따라 나온다.
자바에서 상속과 오버라이드를 금지하는 키워드는 `final`이다.

| 위치          | 무슨 일이 벌어지나                                            | 발견 시점     |
|-------------|-------------------------------------------------------|-----------|
| `final` 클래스 | 상속 자체가 불가 → **프록시 생성 실패, 기동 에러**                      | 시끄럽게, 즉시  |
| `final` 메서드 | 프록시는 생성되지만 그 메서드는 오버라이드 불가 → **그 메서드만 조용히 부가 기능 미적용** | 조용히, 한참 뒤 |

둘 중 악질은 **`final` 메서드** 쪽이다. `final` 클래스는 기동이
실패하니 바로 발견되지만, `final` 메서드는 애플리케이션이 멀쩡히 뜨고
`@Transactional`이 붙은 메서드가 **트랜잭션 없이 조용히 실행**된다.
예외도 경고도 없어서, 장애가 나고 데이터가 반쯤 커밋된 뒤에야 발견된다.

```java

@Service
public class SettlementService {

    @Transactional
    public final void settle(Long orderId) {   // ❌ final — 프록시가 오버라이드 못 함
        // 트랜잭션 없이 실행된다. 컴파일도 기동도 멀쩡하다.
    }
}
```

같은 원리로 `private` 메서드도 오버라이드 대상이 아니므로 부가 기능이
걸리지 않는다. 코틀린에서 이 함정이 더 자주 터지는 이유도 여기 있다 —
**코틀린 클래스/메서드는 기본이 final**이라, `open`을 붙이거나
`kotlin-spring`(allopen) 플러그인으로 스프링 애너테이션이 붙은 클래스를
자동으로 열어줘야 한다.

## 5. 자기 호출은 왜 안 걸리나 — "어떤 메서드를 감쌌나"가 아니라 "어느 객체로 들어왔나"

여기서 흔한 오해: "프록시가 특정 메서드만 감싸는 것도 아니고 모든
메서드를 감쌀 텐데, 왜 자기 호출은 부가 기능이 안 붙지?"
맞다 — **프록시는 모든 public 메서드를 감싼다.** 그런데 부가 기능이
실행되는 조건은 "감싸져 있느냐"가 아니라 **호출이 프록시 객체를
통과했느냐**다. 프록시 구조에서는 메모리에 객체가 **두 개** 존재한다는
사실이 핵심이다.

```
[프록시 객체]  ──원본을 참조──▶  [원본 객체(target)]
 order() ← 부가기능 있음           order() ← 순수 비즈니스 로직
 inner() ← 부가기능 있음           inner() ← 순수 비즈니스 로직
```

자기 호출이 일어나는 순간을 따라가 보면:

```java

@Service
public class OrderService {

    public void order() {
        this.inner();   // ← 문제의 자기 호출
    }

    @Transactional
    public void inner() { ...}
}
```

1. 컨트롤러가 `orderService.order()` 호출 → 이 참조는 프록시니까 **프록시의 `order()`** 실행
2. 프록시는 부가 기능 처리 후 **원본 객체의 `order()`에 위임** — 이 순간부터 실행 흐름은 원본 객체 안
3. 원본의 `order()` 안에서 `this.inner()` 실행 — 이때 `this`는 **원본 객체 자신**이지 프록시가 아님
4. 원본의 `inner()`가 직접 실행됨. 프록시의 `inner()`는 감싸고 있지만 **그쪽으로 호출이 들어오지 않았으므로** 부가 기능 미적용

비유하면 회사 대표번호(프록시)로 걸려온 전화는 안내원이 기록을 남기고
담당자(원본)에게 연결하지만, 담당자가 옆자리 동료에게 직접 말을 걸면
(`this.inner()`) 대표번호를 안 거쳤으니 기록이 남지 않는다. 안내원이
"모든 직원의 전화"를 받을 수 있다는 사실과는 무관하게, **그 경로로
들어오지 않은 호출은 잡을 수 없다.**

### "CGLIB은 상속이라며? 오버라이드됐으면 this.inner()도 프록시 걸로 불려야 하는 것 아닌가"

자바의 동적 디스패치대로라면 맞는 지적이다. 그게 안 되는 이유는
**스프링의 CGLIB 프록시가 `super` 호출 방식으로 동작하지 않기
때문**이다. 상속은 "같은 타입인 척"하기 위한 수단일 뿐이고, 실제
동작은 **별도 인스턴스에 대한 위임**이다.

```java
// 상속이니까 이렇게 동작할 것 같지만 (이 방식이면 자기 호출도 걸린다)
public void order() {
    부가기능();
    super.order();        // ❌ 스프링은 이 방식이 아님
}

// 실제로는 별도의 원본 인스턴스에게 위임
public void order() {
    부가기능();
    target.order();       // ✅ 완전히 다른 객체의 메서드 호출
}
```

`super` 호출이었다면 실행 주체가 프록시 인스턴스 하나뿐이라 `this` =
프록시가 되어 자기 호출도 걸렸을 것이다. 하지만 스프링은 프록시
인스턴스와 원본 인스턴스를 따로 두고 위임하므로, 원본 안으로 흐름이
넘어간 순간 `this`는 순수한 원본이고 프록시는 호출 경로에서 완전히
빠진다. 해결책이 "별도 빈으로 분리해서 주입받기"인 이유도 이것 —
**프록시라는 문을 다시 통과하게 만드는 것**이다.

참고로 주입과 관련된 디테일 하나: 의존성 주입은 원본 객체에 일어나고
프록시는 호출을 넘기는 껍데기라서, 디버거로 프록시 객체의 필드를 보면
전부 `null`인 경우가 있다. "주입이 안 됐나?" 싶지만 실제 일은 필드가
채워진 원본(target)이 하므로 정상이다.

## 6. 꼬리질문 대비 포인트

### "프록시는 원본과 '같은 타입인 척'해야 한다 — 자바에서 같은 타입인 척하는 두 가지 방법은?" (실제 면접 흐름)

인터페이스 구현과 상속. 이 두 가지가 각각 JDK Dynamic Proxy(대상의
인터페이스를 구현한 객체를 리플렉션으로 생성)와 CGLIB(대상 클래스를
상속한 자식 클래스를 바이트코드로 생성)의 정체다. "추상 클래스"가
아니라 **상속 그 자체**라는 점에 주의 — CGLIB은 평범한 구체 클래스를
그대로 extends 한다.

### "CGLIB이 상속 기반이라면, 프록시가 안 만들어지거나 부가 기능이 안 걸리는 경우는?" (실제 면접 흐름)

`final` 클래스는 상속이 불가능해 프록시 생성 자체가 실패한다(기동 에러).
`final` 메서드는 프록시는 만들어지지만 해당 메서드를 오버라이드할 수
없어 그 메서드만 부가 기능이 빠진다. `private` 메서드도 마찬가지.
"대상이 이미 다른 클래스를 상속한 경우"는 함정이 **아니다** — 프록시가
대상을 상속하는 것이므로 프록시→대상→부모로 체인이 이어질 뿐이다.

### "final이 클래스에 붙었을 때와 메서드에 붙었을 때, 어느 쪽이 더 악질적인 장애인가?" (실제 면접 흐름)

`final` 메서드 쪽. `final` 클래스는 기동 실패라 즉시 발견되지만(fail-fast),
`final` 메서드는 기동도 실행도 멀쩡한 채 **부가 기능만 조용히 빠진다.**
@Transactional이면 트랜잭션 없이 돌다가 정합성 사고로 발견되는,
"조용한 미적용" 유형이다. 장애의 악질성은 에러의 크기가 아니라
**발견되기까지의 침묵**으로 결정된다는 관점을 보여주면 좋다.

### "스프링 부트는 왜 CGLIB을 기본값으로 골랐나?"

인터페이스 없는 빈도 프록시해야 하고(구현체 하나짜리 서비스에
인터페이스 강제하지 않는 실무 흐름), JDK 프록시의 구체 클래스 캐스팅
불가(`ClassCastException`) 사고를 피하기 위해서다. `proxyTargetClass=true`가
그 설정이다.

### "그 프록시 구조 때문에 @Transactional이 안 먹는 다른 경우도 있지 않나?"

자기 호출(self-invocation). 부가 기능은 프록시에 있는데
`this.method()`는 프록시를 거치지 않고 원본을 직접 부르기 때문이다.
final 메서드와 마찬가지로 **조용히** 미적용된다. 해결은 별도 빈으로
분리해 프록시를 통해 호출되게 하는 것. — 상세는
[@Transactional 문서](07-transactional-default-behavior-rollback.md)의
자기 호출 절 참고.

### "프록시는 모든 메서드를 감싸는데, 왜 자기 호출만 부가 기능이 빠지나?"

부가 기능의 실행 조건이 "메서드가 감싸져 있는가"가 아니라 **"호출이
프록시 객체를 통과했는가"**이기 때문. 프록시와 원본은 별도의 두
인스턴스이고, 프록시가 원본에 위임한 뒤 원본 안에서 실행되는
`this.method()`의 `this`는 원본 자신이라 프록시가 호출 경로에서
빠진다. "CGLIB은 상속인데 오버라이드된 프록시 메서드가 불려야 하지
않나"라는 재반문에는 — 스프링 CGLIB 프록시는 `super` 호출이 아니라
**별도 target 인스턴스에 위임**하는 구조라서 동적 디스패치가 개입할
여지가 없다고 답하면 된다(§5).

### "스프링 AOP와 AspectJ의 차이는?"

스프링 AOP는 런타임 프록시 기반이라 (1) 스프링 빈에만, (2) 메서드
실행 지점에만, (3) 프록시를 거치는 호출에만 적용된다. AspectJ는
컴파일/로드 타임에 바이트코드를 직접 수정(위빙)하므로 자기 호출·final·
private·생성자·필드 접근까지 전부 가능하지만, 빌드 파이프라인이
복잡해진다. "제약을 만나면 AspectJ로 도망가는 게 아니라, 대부분은
빈 분리 같은 설계로 푸는 게 실무 관례"까지 말하면 판단력을 보여준다.

### "@Aspect, @Around 쓰고 있으면 AspectJ를 쓰고 있는 것 아닌가?"

아니다 — 자주 혼동되는 지점. 스프링 AOP는 AspectJ의 **애너테이션과
포인트컷 표현식 문법만 빌려온 것**이고(`@Aspect`,
`@Around("execution(...)")`), 실제 동작 방식은 여전히 런타임 프록시다.
"AspectJ 문법을 쓰니까 AspectJ 위빙이 된다"가 아니라, 문법은 AspectJ /
엔진은 프록시라는 조합이다. 그래서 `@Aspect`를 쓰고 있어도 자기 호출·
final 함정은 그대로 적용된다. 진짜 AspectJ 위빙을 쓰려면 컴파일 타임
위빙(ajc)이나 로드 타임 위빙(LTW) 설정이 별도로 필요하다.

---

## 한 줄 요약

스프링 AOP는 "원본인 척하는 대리인"을 끼워 넣는 구조고, 척하는 방법이
인터페이스 구현(JDK Proxy)이냐 상속(CGLIB, 부트 기본값)이냐의 차이라서 —
final 클래스는 기동 실패로, final 메서드·private·자기 호출은 **조용한
미적용**으로 이어지며, "붙였는데 동작 안 함" 계열 장애는 전부
"이 호출이 프록시를 거쳤는가, 프록시가 이 메서드를 오버라이드할 수
있는가" 두 질문으로 진단된다.
