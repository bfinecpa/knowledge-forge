# AOP 동작 원리 — JDK Dynamic Proxy vs CGLIB, "붙였는데 동작 안 함"의 뿌리

> 핵심 관전 포인트: **스프링 AOP는 대상 빈을 그대로 등록하지 않고, 그 빈을 감싼 프록시 객체를 대신 등록한다. 그래서 다른 빈이 주입받는 것은 원본이 아니라 전부 프록시다. 프록시가 "원본인 척"할 수 있는 방법은 자바에 정확히 두 가지뿐이다 — 원본의 인터페이스를 구현하거나(JDK 동적 프록시), 원본 클래스를 상속하거나(CGLIB). 이 한 문장에서 실무 함정이 기계적으로 따라 나온다. JDK 방식은 인터페이스 목록으로 클래스를 찍어내므로 인터페이스가 없으면 만들 수가 없고, 만들어진 프록시는 구현 클래스의 자식이 아니라서 구현 클래스 타입으로 주입받으면 `BeanNotOfRequiredTypeException`이 난다 — 스프링 부트가 인터페이스가 있어도 CGLIB을 기본값(`proxyTargetClass=true`)으로 쓰는 이유가 이것이다. 반대로 CGLIB은 상속이라서 `final` 클래스는 프록시 생성 자체가 실패해 기동이 죽고(시끄럽다), `final` 메서드는 프록시는 만들어지되 그 메서드만 조용히 부가 기능이 빠진다(조용하다) — 장애의 악질성은 에러의 크기가 아니라 발견되기까지의 침묵으로 결정된다. 그리고 양쪽 공통으로, 호출이 프록시를 통과하지 않으면 부가 기능은 걸리지 않는다. `@Transactional`·`@Async`·`@Cacheable`이 "붙였는데 동작 안 하는" 상황은 전부 이 프록시 구조 하나로 설명된다.**

---

## 0. 질문 + 의도

**질문**: "AOP의 동작 원리(JDK Dynamic Proxy vs CGLIB)를 설명해주세요."

**출제 의도**: 프록시 기반이라는 사실을 모르면 `@Transactional`, `@Async`, `@Cacheable`이 "붙였는데 동작 안 하는" 상황을 이해할 수 없다. 스프링의 마법 대부분이 이 하나의 원리로 설명되므로, 이걸 아는지가 스프링을 "쓰는" 사람과 "이해하는" 사람의 분기점이다.

이 문서는 **스프링 프록시 3부작의 원리 편**이다. 여기서는 프록시가 어떻게 만들어지고 무엇이 그 생성을 방해하는지를 다룬다. `@Transactional`의 기본 동작과 롤백 규칙은 [07번 문서](07-transactional-default-behavior-rollback.md), 자기 호출 함정의 진단과 해법은 [11번 문서](11-transactional-self-invocation.md)가 본론이다. 버전에 따라 달라지는 서술은 **스프링 프레임워크 6.x / 스프링 부트 3.x 기준**으로 쓴다.

## 1. AOP와 프록시 — 스프링의 "마법"이 하나의 구조로 설명되는 이유

### 1-1. 전제 지식 — AOP가 풀려는 문제는 무엇인가

AOP를 "관점 지향 프로그래밍"이라고 번역해 놓으면 아무것도 설명되지 않는다. 먼저 무엇을 풀려는 기법인지부터 보자.

서비스 코드에는 두 종류의 관심사가 섞여 있다. 하나는 그 메서드가 존재하는 이유인 **비즈니스 로직**(주문을 만든다, 재고를 깎는다)이고, 다른 하나는 그 로직이 무엇이든 상관없이 똑같이 필요한 **부가 관심사**(트랜잭션을 열고 닫는다, 실행 시간을 로그로 남긴다, 권한을 확인한다, 결과를 캐시에 넣는다)다.

문제는 부가 관심사가 **여러 클래스에 똑같은 모양으로 흩어진다**는 것이다. 서비스가 50개면 트랜잭션 시작/커밋/롤백 코드가 50벌 복제된다. 한 곳을 고치면 49곳을 놓친다.

```java
// before: 부가 관심사가 비즈니스 로직에 얽혀 모든 메서드에 복제된다
public Order order(OrderRequest request) {
    Connection conn = dataSource.getConnection();
    conn.setAutoCommit(false);          // 트랜잭션 시작 — 이 서비스와 아무 상관 없는 코드
    long start = System.nanoTime();     // 로깅 — 역시 상관 없다
    try {
        Order result = doOrder(request, conn);   // 이 한 줄만이 이 메서드의 존재 이유다
        conn.commit();
        return result;
    } catch (Exception e) {
        conn.rollback();
        throw e;
    } finally {
        log.info("order took {}ms", (System.nanoTime() - start) / 1_000_000);
        conn.close();
    }
}
```

이렇게 **여러 모듈을 가로질러(cross-cutting) 반복되는 부가 관심사**를 **횡단 관심사(cross-cutting concern)**라 부른다. AOP는 이 횡단 관심사를 한 곳에 모아 정의해 두고, **대상 코드를 한 글자도 건드리지 않은 채 실행 시점에 끼워 넣는** 기법이다.

이름이 "관점(aspect)"인 이유도 여기서 나온다. 기존의 객체 지향은 시스템을 "주문", "재고", "회원" 같은 **명사(객체)** 단위로 자른다. 그런데 "트랜잭션"이나 "감사 로깅"은 그 어느 명사에도 속하지 않고 전부를 가로지른다 — 시스템을 자르는 **또 다른 관점(측면)**인 것이다. 그 관점 하나를 독립된 모듈로 떼어낸 것이 aspect이고, 그렇게 자르는 프로그래밍이 aspect-oriented programming이다.

```java
// after: 부가 관심사는 사라지고 존재 이유만 남는다
@Transactional
public Order order(OrderRequest request) {
    return doOrder(request);
}
```

### 1-2. 스프링의 구현 방식 — 런타임 프록시

그렇다면 `@Transactional` 한 줄이 어떻게 위의 try-catch-finally를 대신하는가. 스프링이 고른 방법은 **런타임 프록시**다.

**프록시(proxy)는 원본 객체인 척하면서 호출을 먼저 받아 부가 작업을 한 뒤 원본에 넘기는 대리인 객체다.** 영문 병기가 아니라 이 정의가 중요하다 — 프록시는 "감싸는 코드"가 아니라 **메모리에 따로 존재하는 별개의 객체**다.

스프링 컨테이너가 하는 일을 순서대로 보면 이렇다.

```text
① 원본 빈(target)을 평범하게 생성한다.            OrderService 인스턴스 #1
② AOP 대상인지 검사한다.                          @Transactional이 붙어 있네
③ 원본을 감싼 프록시 객체를 만든다.                OrderService$$SpringCGLIB 인스턴스 #2
④ 컨테이너에 등록하는 것은 ③ 쪽이다.              ← 여기가 핵심
⑤ 다른 빈은 전부 ③을 주입받는다.                 컨트롤러가 손에 쥔 것은 프록시
```

프록시가 하는 일을 의사코드로 풀면 이렇다.

```java
// 프록시 객체 안에서 개념적으로 벌어지는 일
public Order order(OrderRequest request) {
    // ① 전작업 — 트랜잭션 시작 / 캐시 조회 / 시작 시각 기록 / 권한 검사
    Order result = target.order(request);   // ② target은 원본 인스턴스 #1을 가리키는 필드다
    // ③ 후작업 — 커밋 / 캐시 저장 / 소요 시간 로깅
    return result;                          // ④ 리턴값은 손대지 않고 그대로 돌려준다
}
```

여기서 반드시 붙잡아야 할 문장이 하나 있다. **부가 기능 코드는 프록시에만 있고 원본에는 없다.** 그러므로 부가 기능이 실행될 조건은 "그 메서드에 애너테이션이 붙어 있는가"가 아니라 **"이 호출이 프록시 객체를 통과했는가"**다. 3-6절과 11번 문서의 자기 호출 함정이 전부 이 한 문장에서 나온다.

### 1-3. 지도 — 프록시 방식과 바이트코드 위빙

AOP를 구현하는 방법이 프록시뿐인 것은 아니다. 전체 지형을 한 번 그려두면 이 문서가 다루는 범위가 분명해진다.

```text
AOP를 구현하는 방법
├─ ① 프록시 방식 (스프링 AOP)  — 원본은 그대로 두고 앞에 대리인을 세운다
│   ├─ JDK 동적 프록시   ← 인터페이스를 "구현"해서 원본인 척
│   └─ CGLIB            ← 원본 클래스를 "상속"해서 원본인 척
└─ ② 바이트코드 위빙 방식 (AspectJ) — 원본 클래스의 코드 자체를 고친다
    ├─ 컴파일 타임 위빙 (ajc 전용 컴파일러)
    └─ 로드 타임 위빙 (LTW, 클래스 로딩 시점에 변조)
```

이 문서의 주제인 JDK 동적 프록시와 CGLIB은 **①번 안에서의 두 선택지**다. AspectJ는 ②번이라 계열 자체가 다르다.

AspectJ를 굳이 여기서 언급하는 이유는 **대조군**이기 때문이다. 앞으로 볼 함정들 — `final` 미적용, `private` 미적용, 자기 호출 미적용 — 은 "AOP의 한계"가 아니라 **"프록시 방식의 한계"**다. AspectJ는 프록시를 만들지 않고 원본 클래스의 바이트코드에 부가 기능을 직접 박아 넣으므로, 프록시를 거칠 필요가 아예 없어서 이 제약이 전부 사라진다. 대조군이 있어야 "이 함정의 원인은 프록시 구조다"라는 진단이 완성된다.

비유하면 이렇다. **프록시는 담당자 앞에 안내원을 앉히는 방식**이고, **AspectJ는 담당자 본인을 교육시켜 스스로 기록하게 만드는 방식**이다. 안내원 방식의 약점(담당자에게 직접 말을 걸면 기록이 안 남는다)이 후자에는 애초에 존재하지 않는다.

## 2. "원본인 척"하는 방법 — 자바에는 둘뿐이다

### 2-1. 프록시의 존재 조건

프록시가 성립하려면 반드시 만족해야 하는 조건이 하나 있다. **원본과 같은 타입으로 취급될 수 있어야 한다.**

이유는 단순하다. 주입받는 쪽 코드는 이렇게 생겼기 때문이다.

```java
@RequiredArgsConstructor
public class OrderController {
    private final OrderService orderService;   // 이 변수에 프록시가 담겨야 한다
}
```

컨테이너가 프록시를 이 필드에 넣으려면 프록시가 `OrderService`로 대입 가능해야 한다. 자바에서 어떤 객체가 다른 타입으로 대입될 수 있는 경우는 정확히 둘뿐이다 — **그 타입을 구현했거나(인터페이스), 그 타입을 상속했거나(클래스).** 이 두 갈래가 그대로 두 프록시 기술의 정체다. 선택지가 왜 하필 이 둘인지는 스프링이 정한 것이 아니라 **자바 타입 시스템이 정한 것**이다.

### 2-2. JDK 동적 프록시 — 인터페이스가 없으면 만들 수가 없다

JDK 동적 프록시는 JDK에 내장된 `java.lang.reflect.Proxy`를 쓴다. 핵심 메서드는 이것 하나다.

```java
OrderService proxy = (OrderService) Proxy.newProxyInstance(
    classLoader,                       // ① 만들어낸 클래스를 어디에 적재할지
    new Class[]{OrderService.class},   // ② "이 인터페이스들을 구현한 클래스를 만들어라"
    invocationHandler                  // ③ 가로챈 호출을 어떻게 처리할지
);
```

`newProxyInstance`는 **런타임에 새 클래스를 바이트코드로 찍어내는** 메서드다. 그리고 그 클래스가 무슨 타입인지를 결정하는 정보는 **②번 인터페이스 배열이 유일하다.** 그러니 인과가 명확해진다 — 인터페이스가 없으면 배열이 비고, 배열이 비면 아무 타입도 아닌 클래스가 만들어지며, 그건 `OrderService orderService = ...` 자리에 담길 수 없다. **JDK 방식에 인터페이스가 필수인 이유는 "스프링이 그렇게 정해서"가 아니라, 타입 정보를 얻을 통로가 그것뿐이기 때문이다.**

생성된 클래스의 모양을 개념적으로 쓰면 이렇다.

```java
// Proxy.newProxyInstance가 런타임에 만들어내는 클래스 (개념적 형태)
public final class $Proxy0 extends java.lang.reflect.Proxy implements OrderService {

    @Override
    public Order order(OrderRequest request) {
        // 모든 메서드가 이 한 줄로 수렴한다 — 어떤 메서드가 불렸는지를
        // Method 객체로 넘겨주고, 실제 처리는 핸들러에 위임한다.
        return (Order) h.invoke(this, ORDER_METHOD, new Object[]{request});
    }
}
```

여기서 3-2절의 함정으로 직결되는 사실이 하나 보인다. **생성된 클래스는 이미 `java.lang.reflect.Proxy`를 상속하고 있다.** 자바는 단일 상속이므로, 이 클래스가 `OrderServiceImpl`을 추가로 상속할 자리는 **구조적으로 남아 있지 않다.** 즉 JDK 프록시는 인터페이스의 형제일 뿐 구현 클래스와는 아무 혈연이 없는 남남이다.

### 2-3. CGLIB — 원본을 상속한 자식 클래스를 찍어낸다

CGLIB은 바이트코드 조작 라이브러리다. 원래는 별도 의존성이었지만, 스프링은 이것을 자기 안에 재패키징해 넣었으므로 따로 추가할 필요가 없다.

CGLIB이 만드는 것은 **원본 클래스를 상속한 자식 클래스**다.

```java
// CGLIB이 런타임에 생성하는 클래스 (개념적 형태)
// 실제 이름은 OrderService$$SpringCGLIB$$0 처럼 붙는다 (스프링 6 기준).
public class OrderService$$SpringCGLIB$$0 extends OrderService {

    private final Object target;   // 원본 인스턴스 — super가 아니라 별도 객체다

    @Override
    public Order order(OrderRequest request) {
        // 전작업 → 원본 호출 → 후작업
        return (Order) interceptor.intercept(target, ORDER_METHOD, new Object[]{request});
    }
}
```

여기서 오해하기 쉬운 대목을 미리 못 박아 두자. **상속은 "같은 타입인 척"하기 위한 수단일 뿐, 실제 실행은 `super.order()`가 아니라 별도 원본 인스턴스에 대한 위임이다.** 이 구분이 왜 중요한지는 11번 문서에서 자기 호출을 설명할 때 결정적으로 쓰인다.

### 2-4. 한눈에 보는 대조표

|  | JDK 동적 프록시 | CGLIB |
|---|---|---|
| 같은 타입인 척하는 방법 | 대상의 **인터페이스를 구현** | 대상 클래스를 **상속**한 자식 생성 |
| 타입 정보를 어디서 얻나 | `newProxyInstance`에 넘긴 인터페이스 배열 | 대상 클래스 그 자체 |
| 필요한 것 | 인터페이스가 반드시 있어야 함 | 클래스만 있으면 됨 |
| 구현 수단 | JDK 내장 (`java.lang.reflect.Proxy`) | 바이트코드 생성 (스프링이 재패키징해 내장) |
| 캐스팅 가능한 타입 | 인터페이스 타입으로만 | 인터페이스 + 구체 클래스 타입 |
| 못 만드는 경우 | 인터페이스가 없을 때 | `final` 클래스일 때 |
| 부가 기능이 빠지는 메서드 | 인터페이스에 선언되지 않은 메서드 | `final`·`private` 메서드 |

### 2-5. 생성자는 몇 번 호출되나 (가산점 포인트)

CGLIB이 자식 클래스를 만든다는 사실에서 자연스럽게 나오는 의문이 있다. **자식 인스턴스를 만들려면 부모 생성자가 먼저 돌아야 하는데, 그러면 원본 생성자가 두 번 실행되는 것 아닌가?** 원본 인스턴스 #1을 만들 때 한 번, 프록시 인스턴스 #2를 만들 때 또 한 번.

**스프링 4.0 이전에는 실제로 그랬다.** 그래서 프록시 대상 클래스에 기본 생성자가 반드시 있어야 했고, 생성자에 로깅이나 카운터 증가 같은 부수 효과를 넣어두면 그것이 두 번 실행됐다.

스프링 4.0부터는 **Objenesis**라는 라이브러리(역시 스프링에 재패키징돼 내장)를 써서 이 문제를 없앴다. Objenesis는 생성자를 거치지 않고 객체 인스턴스만 확보하는 JVM별 우회 기법을 모아둔 도구다. 덕분에 프록시 인스턴스를 만들 때 **생성자가 아예 한 번도 호출되지 않고**, 기본 생성자도 더 이상 요구되지 않는다.

다만 공식 문서는 단서를 하나 달아둔다. **JVM이 생성자 우회를 허용하지 않는 환경에서는 여전히 두 번 호출될 수 있고**, 그 경우 스프링 AOP가 디버그 로그를 남긴다. 그래서 결론은 "생성자는 절대 두 번 안 불린다"가 아니라 **"생성자에 부수 효과를 두지 않는 것이 안전하다"**가 된다.

## 3. 어느 쪽이 쓰이나 — 부트가 CGLIB으로 갈아탄 이유와 상속의 대가

### 3-1. 선택 규칙과 스프링 부트의 기본값

**스프링 프레임워크의 원래 규칙**은 이렇다. 대상 빈이 인터페이스를 하나라도 구현하고 있으면 JDK 동적 프록시를 쓰고, 하나도 구현하지 않았으면 CGLIB으로 자식 클래스를 만든다. `proxyTargetClass = true`를 주면 인터페이스가 있어도 CGLIB을 강제한다.

```java
@EnableAspectJAutoProxy(proxyTargetClass = true)     // AOP 전반
@EnableTransactionManagement(proxyTargetClass = true) // 트랜잭션
```

**스프링 부트는 이 값을 처음부터 `true`로 켜둔다.** 설정 키로는 `spring.aop.proxy-target-class=true`이며, 이것이 부트의 기본값이다. 즉 부트 애플리케이션에서 만나는 프록시는 **인터페이스가 있든 없든 거의 전부 CGLIB**이다.

부트가 왜 프레임워크 기본값을 뒤집었는지, 그 이유가 다음 두 절이다.

### 3-2. JDK 프록시의 대가 — 구현 클래스로 주입받으면 터진다

주니어가 반드시 한 번은 밟는 함정이 이것이다. 코드는 아무 문제 없어 보이는데 기동이 실패한다.

```java
public interface OrderService {
    void order(Long orderId);
}

@Service
public class OrderServiceImpl implements OrderService {

    @Transactional
    @Override
    public void order(Long orderId) { /* ... */ }
}

@RestController
@RequiredArgsConstructor
public class OrderController {

    // 문제: 인터페이스가 아니라 구현 클래스 타입으로 받았다.
    // "구현체가 하나뿐이니 구체 타입이 더 명확하지 않나?"는 자연스러운 판단이고,
    // 프록시가 없다면 실제로 아무 문제가 없다.
    private final OrderServiceImpl orderService;
}
```

JDK 프록시가 쓰이는 환경이라면 기동 시점에 이런 예외가 난다.

```text
org.springframework.beans.factory.BeanNotOfRequiredTypeException:
  Bean named 'orderServiceImpl' is expected to be of type
  'com.example.OrderServiceImpl' but was actually of type 'jdk.proxy2.$Proxy123'
```

스프링 부트는 여기에 진단 메시지를 한 겹 더 붙여준다 — "이 빈은 `OrderService`만 구현한 JDK 동적 프록시라서 `OrderServiceImpl`로 주입할 수 없다. 인터페이스 타입으로 주입받거나 `proxyTargetClass=true`로 CGLIB을 강제하라."

**원인은 2-2절에서 이미 봤다.** JDK 프록시가 만든 `$Proxy123`은 `java.lang.reflect.Proxy`를 상속하고 `OrderService`를 구현했을 뿐, **`OrderServiceImpl`을 상속한 적이 없다.** 부모-자식 관계가 아니라 인터페이스를 공유하는 형제일 뿐이니 대입이 성립하지 않는다.

같은 원인이 캐스팅에서도 그대로 나타난다.

```java
OrderService bean = context.getBean(OrderService.class);   // 인터페이스 타입 — 성립
OrderServiceImpl impl = (OrderServiceImpl) bean;           // 문제: ClassCastException
// bean은 OrderServiceImpl의 자식이 아니라, 같은 인터페이스를 구현한 남남이다.
```

여기서 정직하게 짚어둘 것이 하나 있다. **부트 기본값이 CGLIB이므로 요즘 이 예외를 직접 만나기는 오히려 어렵다.** 지금도 나오는 경우는 셋이다.

- `spring.aop.proxy-target-class=false`로 되돌린 프로젝트
- 부트 없이 스프링 프레임워크만 쓰면서 `proxyTargetClass`를 지정하지 않은 설정
- 일부 라이브러리가 자기 기능을 위해 JDK 방식으로 프록시를 별도로 씌우는 경우

그리고 이 목록이 짧다는 사실 자체가 요점이다. **부트가 기본값을 바꾼 덕분에 이 사고가 사라진 것**이지, 프록시 구조가 바뀐 것이 아니다.

### 3-3. 그래서 부트의 결론 — 인터페이스가 있어도 CGLIB

부트가 `proxyTargetClass=true`를 기본으로 삼은 근거를 정리하면 둘이다.

**① 타입 주입 사고를 원천 차단한다.** 3-2절의 함정이 통째로 사라진다. CGLIB 프록시는 `OrderServiceImpl`의 자식이므로 인터페이스 타입으로도, 구현 클래스 타입으로도 주입된다.

**② 인터페이스 없는 빈도 프록시할 수 있어야 한다.** 요즘 실무는 구현체가 하나뿐인 서비스에 인터페이스를 억지로 만들지 않는 쪽으로 기울었다. JDK 방식만 쓴다면 그런 빈에는 `@Transactional`을 아예 걸 수 없다.

대가는 다음 두 절이다. 상속으로 갈아탔으니 **상속을 막는 키워드가 곧 함정**이 된다.

### 3-4. 상속의 대가 ① — `final` 클래스는 시끄럽게 죽는다

자바에서 상속을 금지하는 키워드가 `final`이다. CGLIB이 상속으로 동작하므로, `final` 클래스는 **자식 클래스를 만들 수 없어 프록시 생성 자체가 실패한다.**

```java
// 문제: 클래스에 final — CGLIB이 상속할 수 없다
@Service
public final class SettlementService {

    @Transactional
    public void settle(Long orderId) { /* ... */ }
}
// 기동 시점에 프록시 생성이 실패하며 애플리케이션이 뜨지 않는다.
```

이 실패는 **기동 중에 즉시 드러난다.** 로컬에서 한 번 실행하면 바로 알 수 있고, CI에서도 컨텍스트 로딩 테스트에 걸린다. 고치는 방법도 `final`을 떼는 것 하나뿐이라 고민할 여지가 없다.

### 3-5. 상속의 대가 ② — `final` 메서드는 조용히 샌다

같은 `final`인데 붙는 위치가 메서드로 바뀌면 증상이 완전히 달라진다. 클래스는 상속 가능하므로 **프록시는 정상적으로 만들어진다.** 다만 그 메서드만 오버라이드할 수 없다.

```java
// 문제: 메서드에 final — 프록시는 만들어지지만 이 메서드는 오버라이드가 안 된다
@Service
public class SettlementService {

    @Transactional
    public final void settle(Long orderId) {
        // 컴파일도 되고 기동도 되고 실행도 된다. 트랜잭션만 없다.
    }
}

// 고침: final을 뗀다. 프록시가 오버라이드할 수 있어야 부가 기능이 걸린다.
@Service
public class SettlementService {

    @Transactional
    public void settle(Long orderId) { /* ... */ }
}
```

두 함정을 나란히 놓고 보면 차이가 선명하다.

| 붙은 위치 | 프록시 생성 | 부가 기능 | 발견 시점 | 증상 |
|---|---|---|---|---|
| `final` 클래스 | 실패 | — | 기동 즉시 | 애플리케이션이 아예 안 뜬다 |
| `final` 메서드 | 성공 | 그 메서드만 미적용 | 정합성 사고가 난 뒤 | 아무 신호 없이 트랜잭션만 없다 |

**둘 중 진짜 악질은 `final` 메서드 쪽이다.** `final` 클래스는 기동이 실패하니 배포되지 못한다 — 즉 사고가 될 기회 자체가 없다. `final` 메서드는 애플리케이션이 멀쩡히 뜨고, 테스트도 통과하고(예외가 나지 않는 정상 경로에서는 트랜잭션 유무와 결과가 같다), 운영에서 실패 경로를 밟는 순간에야 **데이터가 반쯤 커밋된 상태**로 발견된다.

여기서 얻어갈 관점은 이것이다. **장애의 악질성은 에러의 크기가 아니라 발견되기까지의 침묵으로 결정된다.** 이 기준으로 보면 `final` 클래스는 좋은 실패(fail-fast)이고 `final` 메서드는 나쁜 실패다.

### 3-6. `private`·패키지 프라이빗, 그리고 코틀린

오버라이드가 안 되는 메서드는 `final`만이 아니다. 스프링 공식 문서가 CGLIB의 제약으로 명시하는 목록은 다음과 같다.

- `final` 클래스는 상속할 수 없어 프록시로 만들 수 없다.
- `final` 메서드는 오버라이드할 수 없어 부가 기능이 적용되지 않는다.
- `private` 메서드는 오버라이드 대상이 아니므로 부가 기능이 적용되지 않는다.
- 다른 패키지에 있는 부모 클래스의 패키지 프라이빗 메서드도 사실상 `private`처럼 취급되어 적용되지 않는다.

`private`은 JDK 방식에서도 당연히 불가능하다. 인터페이스에 `private` 메서드를 선언할 수 없으니 프록시가 가로챌 통로 자체가 없다. **`private`은 어느 프록시 방식으로도 구제되지 않는다**는 것이 결론이다.

코틀린에서 이 함정이 유난히 자주 터지는 이유도 여기 있다. **코틀린은 클래스와 메서드가 기본적으로 `final`이다.** 자바에서 `final`을 붙이는 것은 의식적인 행위지만, 코틀린에서는 아무것도 안 쓰면 `final`이 된다. 그래서 `open` 키워드를 붙이거나, 스프링 애너테이션이 달린 클래스를 자동으로 열어주는 `kotlin-spring`(allopen) 컴파일러 플러그인을 반드시 쓴다. 스프링 이니셜라이저가 코틀린 프로젝트에 이 플러그인을 기본 포함시키는 것도 이 때문이다.

### 3-7. 양쪽 공통의 대가 — 프록시를 통과하지 않은 호출

지금까지의 함정은 "프록시가 그 메서드를 감쌀 수 있는가"의 문제였다. 마지막 함정은 성격이 다르다. **프록시가 멀쩡히 그 메서드를 감쌌는데도 부가 기능이 안 걸리는 경우**가 있다.

원리는 1-2절의 한 문장으로 끝난다. 부가 기능은 프록시에만 있고, 메모리에는 **프록시와 원본 두 개의 객체**가 따로 존재한다. 프록시가 원본에 위임한 순간부터 실행 흐름은 원본 객체 안에 있고, 그 안에서 부르는 `this.method()`의 `this`는 **원본 자신**이다. 프록시가 호출 경로에서 완전히 빠진다.

```text
[프록시 객체]  ──target 참조──▶  [원본 객체]
 order()  부가 기능 있음            order()  순수 로직만
 inner()  부가 기능 있음            inner()  순수 로직만
                                       └── this.inner() 는 여기서 여기로 간다
                                           (프록시를 통과하지 않는다)
```

이것을 **자기 호출(self-invocation)** 문제라 부른다. 증상은 `final` 메서드와 똑같이 **조용한 미적용**이고, 그래서 실무 사고의 빈도로는 이쪽이 훨씬 높다.

이 문제의 진단 절차와 네 가지 해법, 그리고 각 해법이 치르는 대가는 [11번 문서](11-transactional-self-invocation.md)에서 본론으로 다룬다. 여기서는 **원인이 애너테이션이 아니라 프록시 구조라는 것**만 붙잡고 넘어가면 된다.

## 4. 꼬리질문 대비 포인트

### "프록시는 원본과 '같은 타입인 척'해야 한다 — 자바에서 같은 타입인 척하는 방법은 몇 가지인가요?"

**두 가지다. 인터페이스 구현과 상속.** 그리고 이것이 스프링이 정한 것이 아니라 자바 타입 시스템이 정한 것이라는 점을 짚으면 좋다. 어떤 객체가 다른 타입 변수에 대입될 수 있는 경우가 그 둘뿐이므로, 프록시 기술도 그 둘뿐일 수밖에 없다.

각각이 JDK 동적 프록시(`java.lang.reflect.Proxy`가 인터페이스 배열을 받아 런타임에 클래스를 생성)와 CGLIB(대상 클래스를 상속한 자식 클래스를 바이트코드로 생성)이다.

주의할 표현이 하나 있다. CGLIB이 상속하는 것은 **추상 클래스가 아니라 평범한 구체 클래스 그 자체**다. "인터페이스 대신 추상 클래스를 쓴다"가 아니라 "대상 클래스를 그대로 `extends` 한다"가 정확한 설명이다.

### "JDK 동적 프록시는 왜 인터페이스가 반드시 필요한가요?"

`Proxy.newProxyInstance(classLoader, interfaces, handler)`가 **인터페이스 배열만을 타입 정보로 받아 런타임에 클래스를 찍어내기 때문**이다. 이 배열이 비면 아무 타입도 구현하지 않은 클래스가 만들어지고, 그것은 `OrderService` 타입 변수에 담길 수 없다. **타입 정보를 얻을 통로가 인터페이스밖에 없다**는 것이 인과의 전부다.

여기서 한 걸음 더 나가면 가산점이다. 생성된 클래스는 `java.lang.reflect.Proxy`를 이미 상속하고 있고, 자바는 단일 상속이므로 **대상 구현 클래스를 추가로 상속할 자리가 구조적으로 없다.** 그래서 JDK 프록시는 구현 클래스 타입으로 절대 캐스팅되지 않는다.

### "JDK 프록시일 때 `@Autowired`로 구현 클래스 타입을 주입받으면 어떻게 되나요?" (실무 함정)

`BeanNotOfRequiredTypeException`이 나며 기동이 실패한다. 메시지는 "빈 `orderServiceImpl`은 `OrderServiceImpl` 타입이어야 하는데 실제로는 `$Proxy123`이었다"는 형태이고, 스프링 부트는 여기에 "이 빈은 `OrderService`만 구현한 JDK 동적 프록시라서 그렇다. 인터페이스로 주입받거나 `proxyTargetClass=true`를 켜라"는 진단을 덧붙여 준다.

원인을 한 문장으로 답하면 이렇다. **프록시는 인터페이스를 구현했을 뿐 구현 클래스를 상속한 적이 없어서, 둘은 부모-자식이 아니라 형제 관계다.**

그리고 이 답의 진짜 값은 다음 연결에 있다. **스프링 부트가 `proxyTargetClass=true`를 기본값으로 삼은 이유가 바로 이 사고를 없애기 위해서다.** 함정을 아는 것과, 그 함정이 프레임워크 기본값을 바꿔놓은 역사를 아는 것은 다르다.

### "스프링 부트는 왜 CGLIB을 기본값으로 골랐나요?"

근거는 둘이다.

**① 타입 주입 사고 차단.** JDK 프록시는 구현 클래스 타입으로 주입·캐스팅되지 않아 `BeanNotOfRequiredTypeException`과 `ClassCastException`을 만든다. CGLIB 프록시는 대상 클래스의 자식이라 인터페이스로도 구체 클래스로도 받을 수 있다.

**② 인터페이스 없는 빈도 프록시해야 한다.** 구현체가 하나뿐인 서비스에 인터페이스를 강제하지 않는 요즘 실무에서, JDK 방식만으로는 `@Transactional`을 걸 수 없는 빈이 대량으로 생긴다.

설정 키는 `spring.aop.proxy-target-class=true`(부트 기본값)이고, 자바 설정으로는 `@EnableAspectJAutoProxy(proxyTargetClass = true)`, `@EnableTransactionManagement(proxyTargetClass = true)`다.

### "`final`이 클래스에 붙었을 때와 메서드에 붙었을 때, 어느 쪽이 더 악질적인 장애인가요?" (시니어 변별 포인트)

**`final` 메서드 쪽이다.**

`final` 클래스는 상속이 불가능해 **프록시 생성 자체가 실패**하고 애플리케이션이 뜨지 않는다. 시끄럽게 즉시 죽으므로 배포될 기회조차 없다 — fail-fast의 교과서적 사례다.

`final` 메서드는 클래스가 상속 가능하니 **프록시는 정상적으로 만들어진다.** 다만 그 메서드만 오버라이드되지 않아 부가 기능이 빠진다. 컴파일도 기동도 실행도 멀쩡하고, 예외가 나지 않는 정상 경로에서는 결과도 동일하므로 테스트까지 통과한다. `@Transactional`이었다면 **트랜잭션 없이 돌다가 실패 경로에서 데이터가 반쯤 커밋된 뒤에야** 발견된다.

여기서 관점 하나를 얹으면 답이 완성된다. **장애의 악질성은 에러의 크기가 아니라 발견되기까지의 침묵으로 결정된다.** 같은 논리로 자기 호출도 `final` 메서드와 같은 등급의 위험이다.

### "그럼 대상 클래스가 이미 다른 클래스를 상속하고 있으면 CGLIB이 안 되나요?"

**함정이 아니다.** 상속하는 쪽은 프록시이고 상속당하는 쪽이 대상 클래스이므로, 대상이 이미 부모를 갖고 있어도 `프록시 → 대상 → 대상의 부모`로 체인이 한 칸 늘어날 뿐이다.

문제가 되는 것은 어디까지나 **대상 자신이 `final`이라 상속당할 수 없는 경우**다. "상속을 쓴다"는 말에서 "다중 상속이 안 되니 문제 아닌가"로 넘어가는 오해를 정확히 끊어주면 이해도가 드러난다.

### "CGLIB 프록시를 만들면 원본 생성자가 두 번 호출되나요?" (가산점 포인트)

**스프링 4.0 이전에는 그랬고, 지금은 아니다.** 스프링 4.0부터 CGLIB 프록시 인스턴스를 **Objenesis**로 생성한다. Objenesis는 생성자를 거치지 않고 인스턴스만 확보하는 기법을 모아둔 라이브러리이고, 그래서 프록시 생성 시 대상 생성자가 **한 번도 호출되지 않는다.** 기본 생성자가 반드시 있어야 한다는 옛 제약도 이때 함께 사라졌다.

다만 공식 문서는 "JVM이 생성자 우회를 허용하지 않는 환경에서는 여전히 두 번 호출되고 디버그 로그가 남을 수 있다"는 단서를 남겨두었다. 그래서 실무 결론은 "절대 안 불린다"가 아니라 **"생성자에 부수 효과(로깅, 카운터 증가, 외부 호출)를 두지 않는다"**가 된다.

### "스프링 AOP와 AspectJ의 차이는 무엇인가요?"

**적용 시점과 적용 방식이 다르다.**

스프링 AOP는 **런타임에 프록시 객체를 세우는** 방식이라 제약이 셋이다 — (1) 스프링 빈에만, (2) 메서드 실행 지점에만, (3) 프록시를 통과한 호출에만 적용된다.

AspectJ는 **컴파일 타임이나 클래스 로딩 시점에 바이트코드를 직접 수정(위빙)하는** 방식이라 프록시가 아예 존재하지 않는다. 그래서 자기 호출·`final`·`private`·생성자·필드 접근까지 전부 잡을 수 있다. 대가는 전용 컴파일러(ajc)나 로드 타임 위빙 에이전트가 필요해 **빌드·실행 파이프라인이 복잡해진다**는 것이다.

여기에 판단을 얹으면 좋다. **"제약을 만나면 AspectJ로 도망가는 것이 아니라, 대부분은 빈 분리 같은 설계로 푸는 것이 실무 관례"**다. 자기 호출 문제 하나를 풀자고 AspectJ를 도입하는 것은 명백한 과잉이다.

### "`@Aspect`, `@Around`를 쓰고 있으면 AspectJ를 쓰고 있는 것 아닌가요?"

**아니다. 가장 자주 혼동되는 지점이다.**

스프링 AOP는 AspectJ의 **애너테이션과 포인트컷 표현식 문법만 빌려왔다.** `@Aspect`, `@Around("execution(...)")`를 쓰고 있어도 실제 엔진은 여전히 런타임 프록시다. **문법은 AspectJ, 동작은 프록시**라는 조합인 것이다.

그래서 `@Aspect`를 쓰는 코드에도 자기 호출·`final`·`private` 함정이 그대로 적용된다. 진짜 AspectJ 위빙을 쓰려면 컴파일 타임 위빙(ajc)이나 로드 타임 위빙(LTW)을 별도로 설정해야 한다.

### "프록시는 모든 public 메서드를 감싸는데, 왜 자기 호출만 부가 기능이 빠지나요?"

부가 기능의 실행 조건이 **"메서드가 감싸져 있는가"가 아니라 "호출이 프록시 객체를 통과했는가"**이기 때문이다. 프록시는 실제로 모든 대상 메서드를 감싸고 있다 — 다만 그 경로로 호출이 들어오지 않았을 뿐이다.

"CGLIB은 상속이니 오버라이드된 프록시 메서드가 동적 디스패치로 불려야 하지 않나"라는 재반문이 따라올 수 있다. 답은 **스프링의 CGLIB 프록시가 `super` 호출 방식이 아니라 별도 원본 인스턴스에 위임하는 구조**라는 것이다. 상속은 타입을 맞추기 위한 수단일 뿐이고, 실행 주체가 원본 인스턴스로 넘어간 순간 프록시는 호출 경로에서 빠지므로 동적 디스패치가 개입할 여지가 없다.

상세한 진단 방법과 해법은 [11번 문서](11-transactional-self-invocation.md)에서 다룬다.

### "디버거로 프록시 객체를 열어보니 필드가 전부 null이던데, 주입이 안 된 건가요?" (가산점 포인트)

**정상이다.** 의존성 주입은 **원본 객체(target)**에 일어나고, 프록시는 호출을 넘기는 껍데기라서 자기 필드를 채울 이유가 없다. 실제 일은 필드가 채워진 원본이 하므로 동작에는 문제가 없다.

이 현상 자체가 "프록시와 원본은 메모리에 존재하는 서로 다른 두 객체"라는 사실의 직접적인 증거이기도 하다. 자기 호출 함정을 설명할 때 이 관찰을 근거로 쓰면 설명이 훨씬 구체적이 된다.

## 한 줄 요약

스프링 AOP는 원본 대신 "원본인 척하는 대리인"을 컨테이너에 등록하는 구조이고, 척하는 방법이 인터페이스 구현(JDK 동적 프록시)이냐 상속(CGLIB, 부트 기본값)이냐의 차이일 뿐이라서 — JDK 방식은 인터페이스가 없으면 만들 수 없고 구현 클래스 타입으로 주입받으면 `BeanNotOfRequiredTypeException`을 내며(부트가 CGLIB으로 갈아탄 이유), CGLIB 방식은 `final` 클래스면 기동이 죽고 `final`·`private` 메서드면 조용히 새고, 양쪽 모두 프록시를 통과하지 않은 자기 호출에는 걸리지 않는다 — "붙였는데 동작 안 함" 계열 장애는 전부 **"프록시가 이 메서드를 오버라이드할 수 있었는가"**와 **"이 호출이 프록시를 통과했는가"** 두 질문으로 진단된다.
