# Spring WebFlux vs MVC 스레딩 모델 — "대기를 스레드 개수로 흡수하나, 이벤트로 흡수하나"

> 핵심 관전 포인트: MVC는 **thread-per-request** — 요청당 스레드 1개가 응답까지 묶이고, 대기 시간을 **스레드 개수**로 흡수한다(톰캣 기본 200개 = 동시 요청 상한). WebFlux(Netty)는 **이벤트 루프** — 스레드를 코어 수만큼만 띄우고, I/O를 걸어놓은 뒤 스레드를 **즉시 반납**해 다음 이벤트를 처리한다(대기를 이벤트 통지로 흡수 → 적은 스레드로 수만 동시 연결). 그래서 WebFlux의 전제는 **전 구간 논블로킹**이다 — 이벤트 루프 위에서 블로킹(JDBC 등) 한 번이면 코어 수만큼뿐인 스레드가 잠겨 전체가 마비되므로, 블로킹 스택·CPU 바운드·팀 역량에 따라 오히려 독이 된다. 그런데 Java 21 **가상 스레드**가 "블로킹 코드 그대로" 이벤트 루프급 동시성을 주면서 "동시 연결 때문에 WebFlux"라는 근거는 상당 부분 약화됐다 — 남는 자리는 `request(n)`으로 수요를 상류에 전파해야 하는 **스트리밍**과 유휴 연결이 극단적으로 많은 경우뿐이다. 대신 가상 스레드는 스레드풀이 암묵적으로 해주던 **유입 제어**를 없애 커넥션 풀 앞에서 실패 양상을 악화시키므로, 그 문지기를 명시적으로 복원해야 한다.

## 0. 질문 + 의도

**질문**: "Spring WebFlux와 MVC의 스레딩 모델 차이를 설명해주세요. WebFlux
도입이 오히려 독이 되는 경우는?"

**출제 의도**: 기술 선택에서 "우리 팀의 학습 비용, 디버깅 난이도, 블로킹
라이브러리 의존성"까지 넣어 판단하는지 본다. 이력서에 WebFlux를 쓴 지원자의
이해가 튜토리얼 수준인지 운영 수준인지 가르는 질문이기도 하다.

## 1. MVC — thread-per-request (대기 = 스레드 점유)

- 요청 1개 = 톰캣 스레드 1개가 **응답을 쓸 때까지** 전담. DB 50ms 대기 중에도 스레드는 BLOCKED로 묶여 있다(다른 요청을 처리하지 못한다 — `25-thread-pool-connection-pool-sizing.md` 오개념 교정 2).
- 동시 요청 상한 = 스레드풀 크기(기본 200). 필요 스레드 수는 Little's law로: 500 TPS × 응답 100ms = 동시 50개.
- 대기가 길어질수록(외부 API 지연 등) 같은 TPS에 더 많은 스레드가 필요 — **대기 시간을 스레드 개수로 사는 모델**. 스레드는 스택 ~1MB·컨텍스트 스위칭 비용이 있어 수천~수만 동시 연결에는 한계.

## 2. WebFlux(Netty) — 이벤트 루프 (대기 = 스레드 반납)

- 이벤트 루프 스레드는 **코어 수만큼만**(Netty 기본 = 가용 코어 수, 최소 4). 스레드가 요청에 전속되지 않는다.
- 동작 방식:
  1. 요청 도착 → 이벤트 루프 스레드가 핸들러 체인 실행
  2. DB/외부 API 호출을 **논블로킹으로 걸어놓고(콜백 등록)** 스레드는 **즉시 다음 이벤트 처리로 이동**
  3. 50ms 뒤 응답이 소켓에 도착하면 → OS(epoll/kqueue)가 이벤트로 통지 → 이벤트 루프가 등록된 콜백(리액티브 체인의 다음 단계)을 이어서 실행
- 스레드는 "요청을 기다리는" 일이 없고 **항상 실행할 이벤트만 처리** → 대기 시간이 스레드를 소모하지 않아, 4~8개 스레드로 수만 동시 연결 감당.
- Reactor의 `Mono`/`Flux`는 이 "걸어놓고 나중에 이어 하기"를 선언적 체인으로 표현한 것. 백프레셔(소비 측이 감당할 만큼만 당겨 받기)도 스펙에 내장.

## 3. 두 모델 비교

| | MVC (Tomcat) | WebFlux (Netty) |
|---|---|---|
| 스레드 수 | 동시 요청만큼 (기본 200) | ≈ 코어 수 |
| I/O 대기 시 스레드 | BLOCKED로 점유(그 요청 전속) | 반납 — 다른 이벤트 처리 |
| 동시성 한계 결정 요인 | 스레드풀 크기 (Little's law) | 소켓/메모리 한계 (스레드 아님) |
| 블로킹 호출 1건의 피해 | 스레드 200개 중 1개 잠김 — 미미 | 스레드 4개 중 1개 잠김 — **처리량 25% 증발** |
| 백프레셔 | **암묵적** — 블로킹·풀 크기·큐 상한이 대신한다 (§6-2) | **명시적** — `request(n)` 수요 신호가 체인 전체를 거슬러 전파 |
| 적합 워크로드 | 일반 CRUD API, 블로킹 스택(JDBC), 팀 친숙도 우선 | 대량 동시 연결(스트리밍·SSE·게이트웨이), I/O 대기 비중 큰 중계 호출, 전 구간 논블로킹 가능할 때 |

## 4. WebFlux가 독이 되는 경우

1. **이벤트 루프 위 블로킹 호출** — JDBC, 블로킹 HTTP 클라이언트, 파일 I/O, 심지어 느린 로깅까지. MVC에서 블로킹은 "200개 중 1개"의 국소 피해지만, WebFlux에서는 "4개 중 1개"라 **폭발 반경이 정반대로 크다**. DB가 JDBC(R2DBC 아님)면 결국 어딘가에서 블로킹 — WebFlux의 이득이 사라지고 위험만 남는다. **한 구간이라도 블로킹이면 전 구간 논블로킹이라는 전제가 깨진다.**
2. **CPU 바운드 작업** — 대기가 없으면 반납할 것도 없다. 이벤트 루프가 연산에 잡혀 있는 동안 그 루프에 배정된 모든 연결이 지연. CPU 바운드는 모델과 무관하게 코어 수가 상한(`25-thread-pool-connection-pool-sizing.md` §4).
3. **팀·운영 비용** — 리액티브 학습 곡선, 체인 곳곳에서 끊기는 스택트레이스로 디버깅 난이도 급상승, ThreadLocal 전제(MDC, SecurityContext, `@Transactional`의 트랜잭션 동기화 — `24-transaction-synchronization-connection-binding.md`) 전부 재작업. 의존 라이브러리 중 하나라도 블로킹이면 도루묵이므로 **전체 의존성의 논블로킹 여부 점검**이 도입 전 필수. "튜토리얼 수준 이해로 도입한 WebFlux"는 같은 하드웨어의 MVC보다 느리고 장애만 어렵게 만든다.

## 5. 블로킹이 불가피할 때의 우회 — 그리고 그 대가

```java
// 이벤트 루프에서 블로킹 JDBC를 직접 호출하면 안 되므로 별도 스레드풀로 격리
Mono.fromCallable(() -> jdbcRepository.findById(id))   // 블로킹 호출
    .subscribeOn(Schedulers.boundedElastic())          // 전용 워커 풀에서 실행
```

- `boundedElastic`은 블로킹 작업용 워커 풀(기본 상한 = 코어 × 10) — 이벤트 루프는 지키지만, 그 구간은 **결국 thread-per-request로 회귀**한 것이라 워커 풀 크기 산정 문제(Little's law)가 그대로 되살아난다. 이 우회가 코드의 주류가 되면 WebFlux를 쓸 이유가 없다.
- `publishOn`은 체인의 이후 단계 실행 스레드를 바꾸고, `subscribeOn`은 구독(소스 실행) 스레드를 바꾼다 — 블로킹 소스 격리는 `subscribeOn`.
- **BlockHound**: 이벤트 루프 스레드에서 블로킹 호출이 일어나면 예외를 던져주는 감지 도구 — 테스트 단계에서 "숨은 블로킹"을 잡는 안전망.

## 6. 백프레셔 — 두 모델이 갈리는 지점

§2·§3에서 "WebFlux는 백프레셔가 내장"이라고 했는데, 그게 정확히 무슨 뜻인지가
다음 장(가상 스레드가 WebFlux를 대체하는가)의 전제가 된다.

### 6-1. 백프레셔란 무엇인가

**받는 쪽이 감당할 수 있는 속도로만 보내게 만드는 장치**다. 배관에서 온 말로,
하류가 좁으면 압력이 거꾸로 밀려 올라와 펌프를 막는다 — **흐름은 아래로,
"그만 보내"라는 신호는 위로** 간다.

없으면 어떻게 되는지가 핵심이다:

```java
// ❌ 백프레셔 없음 — 생산자가 소비자 사정을 모른다
BlockingQueue<Log> queue = new LinkedBlockingQueue<>();   // 상한 없는 큐

while (true) queue.offer(read());   // 생산 10,000/s — offer 는 절대 안 막힌다
while (true) send(queue.take());    // 소비  1,000/s
```

초당 9,000건이 쌓이는데 **생산자는 아무 문제 없다고 느낀다**(`offer`가 계속
성공하므로). 지연이 서서히 늘다가 힙이 차는 순간 OOM으로 급사한다 — 서서히
느려지다 멈추는 게 아니라, 멀쩡해 보이다 절벽에서 떨어진다.

```java
// ✅ 백프레셔 있음
BlockingQueue<Log> queue = new LinkedBlockingQueue<>(1_000);   // 상한을 둔다

while (true) queue.put(read());   // 큐가 차면 여기서 막힌다 → 생산 속도가 소비 속도에 맞춰진다
```

`offer` → `put`, 무제한 → 상한. 이 차이가 전부다. **큐의 상한은 제약이 아니라
신호 장치**다 — 상한이 없으면 시스템은 자기가 과부하라는 사실을 알 방법이 없다.

포화됐을 때의 선택지는 셋뿐이며, 백프레셔를 "건다"는 건 이 중 하나를 **고른다**는 뜻이다:

| 전략 | 동작 | 적합한 경우 |
|---|---|---|
| **막기**(block) | 생산자를 세운다 | 하나도 유실되면 안 될 때 (결제·주문) |
| **버리기**(drop) | 오래된 것 / 새 것을 버린다 | 최신값만 의미 있을 때 (시세·센서·위치) |
| **거절**(reject) | 생산자에게 에러 반환 | 호출자가 재시도·백오프 가능할 때 (HTTP 429) |

"막기"만 쓰면 정체가 상류로 전파되므로, 실무에서는 **막기 + 타임아웃 후 거절**
조합이 일반적이다.

### 6-2. 블로킹 모델에도 백프레셔는 있다 — 다른 이름으로

"MVC엔 백프레셔가 없다"는 말은 부정확하다. 이미 곳곳에서 쓰고 있다.

- **TCP 수신 윈도** — 받는 쪽 버퍼가 차면 윈도를 0으로 광고, 보내는 쪽 `write()`가 막힌다. 네트워크 계층의 백프레셔.
- **`CallerRunsPolicy`** (`15-async-annotation.md`) — 풀이 포화되면 **호출자 스레드가 직접 실행** → 호출자가 느려져 유입이 자연히 준다.
- **톰캣 `max-threads` + accept 큐** (`25-thread-pool-connection-pool-sizing.md`) — 처리 못 할 요청을 빨리 거절해 뒷단(DB)에 과부하가 전달되는 걸 막는다.
- **커넥션 풀 크기** (`18-resttemplate-webclient-restclient.md` — "상한은 제약이 아니라 백프레셔") — 정확히 같은 얘기다.

즉 백프레셔는 특정 프레임워크 기능이 아니라 **유한한 자원을 다루는 시스템의
일반 원리**다.

### 6-3. 그럼 Reactive Streams는 뭐가 다른가

위 사례들은 백프레셔가 **홉(hop) 하나에서 국소적으로** 작동한다 — 소켓에서,
큐에서, 풀에서 각각 따로 막힐 뿐 서로를 모른다.

Reactive Streams는 이를 **명시적인 수요 신호로 만들어 체인 전체를 거슬러
올려보낸다.**

```java
subscription.request(10);   // 소비자가 "지금 10건 받을 수 있다"고 상류에 알린다
```

`request(n)`이 없으면 생산자는 **한 건도 보내지 않는다.** 기본이
밀어내기(push)가 아니라 **당겨오기(pull)** 라서, 생산자가 소비자 속도를 추측할
필요가 없다. 그리고 6-1의 세 전략을 **선언적으로** 고를 수 있다:

```java
eventFlux
    .onBackpressureDrop(e -> log.warn("버림 {}", e.id()))            // 버리기
    // .onBackpressureBuffer(1000, BufferOverflowStrategy.DROP_OLDEST)  // 제한 버퍼
    // .sample(Duration.ofMillis(100))                                  // 100ms마다 최신값만
```

블로킹 모델로도 같은 걸 만들 수는 있지만 큐와 정책 코드를 직접 짜야 하고, 그건
결국 Reactive Streams를 손으로 재구현하는 일이다.

## 7. 제3의 선택지 — Java 21 가상 스레드(Loom)

동작 원리(Continuation freeze/thaw, pinning, ThreadLocal)는
`28-virtual-threads-pinning.md`에 있다. 여기서는 **"그래서 WebFlux를 대체하는가"**
만 다룬다.

- 가상 스레드는 블로킹 시 캐리어 스레드에서 **자동으로 마운트 해제** — "블로킹 코드를 그대로 두고" 스레드를 사실상 무한정 띄우는 모델. thread-per-request의 프로그래밍 단순함 + 이벤트 루프급 동시성.
- Spring Boot 3.2+에서 `spring.threads.virtual.enabled=true` 한 줄이면 톰캣 요청 처리에 적용 — 리액티브 재작성 없이 MVC 스타일 유지.

### 7-1. 그 플래그가 실제로 바꾸는 것 / 안 바꾸는 것

톰캣 요청 스레드만 바뀌는 게 아니다. `@Async`의 기본 executor가 풀링 없는
`SimpleAsyncTaskExecutor`로, `@Scheduled`의 스케줄러가
`SimpleAsyncTaskScheduler`로 바뀐다(`15-async-annotation.md`). **"고정 크기 풀"이라는
전제가 통째로 사라져** core/max/queue 튜닝 논의 자체가 무의미해진다.

반대로 **안 바뀌는 것**: 직접 만든 `ExecutorService` 빈, HikariCP 풀 크기,
`parallelStream`의 common ForkJoinPool(`17-parallelstream-pitfalls.md`).

### 7-2. "무한정"의 실제 상한 — 200이 아니라 8192

스레드 상한은 사라지지만 **동시 요청 상한이 사라지는 건 아니다.** 톰캣의
`max-connections`(기본 **8192**)가 새 실질 상한이 된다.

| | 기본 MVC | 가상 스레드 |
|---|---|---|
| 동시 요청 상한 | `max-threads` = 200 | `max-connections` = 8192 |

**40배**다. "무한정"은 스레드 얘기지 요청 얘기가 아니며, 이 40배가 7-4의 문제를
만든다.

### 7-3. 사라지는 건 백프레셔가 아니라 유입 제어

**톰캣 스레드풀 200개는 그 자체가 유입 제어(admission control) 장치였다.**
201번째 요청은 스레드를 못 잡고 accept 큐에서 대기하다 거절된다. 아무도 그걸
백프레셔라 부르지 않았지만, 시스템을 지켜주던 건 그 숫자다(§6-2).

가상 스레드는 그 문지기를 치운다. 상한이 없어진 게 아니라 **개발자 책임으로
옮겨진 것**이므로, 명시적으로 다시 넣어야 한다.

### 7-4. DB 커넥션 등 물리 자원 산정은 그대로 유효

한 줄 원리: **가상 스레드는 "기다리는 주체"를 싸게 만들 뿐, "기다리는 대상"의
개수를 늘리지 않는다.**

DB 커넥션·파일 디스크립터·외부 API rate limit은 물리적으로 고정돼 있다. 스레드를
1만 개 띄워도 Hikari 커넥션 10개는 10개다. Little's law는 **자원별로** 성립하므로
(`25-thread-pool-connection-pool-sizing.md` §1) 스레드 계산식만 무의미해지고
**커넥션 계산식은 그대로 남는다.**

그런데 "그대로 유효"보다 나쁘다 — **실패 양상이 악화된다.**

```java
@Transactional
public Order place(Long id) {
    Order o = orderRepository.save(...);   // 커넥션 점유 시작
    paymentClient.charge(o);               // 외부 API 300ms — 커넥션을 쥔 채로 대기!
    return o;                              // 커넥션 반납
}
```

Hikari 풀 10개인 서비스에 동시 요청 10,000개가 들어온 상황:

| | 톰캣 스레드 200개 | 가상 스레드 |
|---|---|---|
| 실제 진입 요청 | 200개 | 8,192개 |
| 커넥션 경쟁 | 200 : 10 | 8,192 : 10 |
| 나머지 요청 | accept 큐에서 **빨리 거절** | 전부 진입 후 `getConnection()`에서 대기 |
| 결과 | 일부 503 + 나머지 정상 응답 | 전면 `SQLTransientConnectionException`(기본 30초 타임아웃), 응답시간 붕괴 |

**빠른 실패가 느린 전멸로 바뀐다.** 감당 못 할 요청이 문 앞에서 걸러지던 것이,
이제 전부 들어와 메모리를 잡고 커넥션을 기다리다 30초를 채우고 죽는다.

대응 — 스레드풀이 암묵적으로 하던 유입 제어를 명시적으로 복원한다:

```java
// 커넥션을 쥐는 구간 자체를 세마포어로 제한 — 풀 크기에 맞춰 유입을 막는다
private final Semaphore dbGate = new Semaphore(10);

public Order place(Long id) {
    if (!dbGate.tryAcquire(200, TimeUnit.MILLISECONDS)) {
        throw new TooManyRequestsException();   // 30초 기다리다 죽지 말고 즉시 거절
    }
    try { return orderService.placeInTx(id); }
    finally { dbGate.release(); }
}
```

단 이건 **증상 처리**다. 근본 해결은 트랜잭션 밖으로 외부 API 호출을 빼는 것이고,
**올바른 설계는 가상 스레드가 있든 없든 동일하다**(`28-virtual-threads-pinning.md` §6)
— 가상 스레드는 그 설계 결함을 40배로 증폭시켜 드러낼 뿐이다. 실무에서는 세마포어를
직접 짜기보다 Resilience4j의 Bulkhead·RateLimiter를 쓰고, Hikari
`connection-timeout`을 30초 → 1~2초로 낮춰 빠른 실패로 되돌리는 조합이 일반적이다.

### 7-5. 그래서 WebFlux에 남는 자리

요청/응답 워크로드에서는 홉이 하나뿐이라 블로킹 백프레셔(§6-2)로 충분하므로,
"동시 연결 때문에 WebFlux"라는 근거는 상당 부분 약화됐다. 남는 건 둘이다.

**① 수요 신호를 상류로 전파해야 하는 스트리밍** — SSE·WebSocket·chunked·메시지
소비처럼 오래 사는 스트림. 블로킹으로도 자연 백프레셔는 걸리지만, 선택지가
**"막히거나 터지거나" 둘뿐**이라 drop·buffer·sample 같은 중간 전략(§6-3)을
표현할 방법이 없다.

```java
// 가상 스레드 + 블로킹 — 생산 10,000/s, 소비(브라우저) 100/s
Thread.ofVirtual().start(() -> {
    for (Event e : eventSource) emitter.send(e);   // 막히는 동안 eventSource 뒤에 쌓인다
});
```

**② 유휴 연결이 극단적으로 많은 경우** — 가상 스레드는 싸지만 공짜는 아니다.
스택이 힙에 상주하므로(연결당 수 KB~) 100만 유휴 연결급에서는 이벤트 루프 몇 개 +
연결당 작은 상태 객체가 여전히 메모리로 이긴다. 푸시 알림 게이트웨이, 대규모 SSE
팬아웃이 여기 해당한다.

| | 가상 스레드 | WebFlux |
|---|---|---|
| 수요 신호 전파 | 홉마다 블로킹으로 끊김 | `request(n)`이 체인·네트워크를 거슬러 전파 |
| 과부하 시 정책 | 막히거나 OOM | drop / buffer / sample 선언적 선택 |
| 유휴 연결 100만 개 | 가상 스레드 100만 개 (스택이 힙에 상주) | 이벤트 루프 몇 개 + 작은 상태 객체 |
| 코드 스타일 | 명령형 그대로, 스택트레이스 온전 | 리액티브 체인, 디버깅 비용 |

## 8. 꼬리질문 대비 포인트

- **"이벤트 루프 스레드가 하나 블로킹되면 정확히 무슨 일이?"** — 그 루프에 배정된 **모든 채널(연결)의 이벤트 처리가 멈춘다**. Netty는 채널을 루프에 고정 배정하므로 다른 루프가 대신 처리해주지 않는다 — 1/N 마비가 아니라 해당 연결들 전면 정지.
- **"WebFlux 쓰면 성능이 좋아지나?"** — 단일 요청 응답시간은 **빨라지지 않는다**(DB 50ms는 그대로 50ms). 좋아지는 건 같은 하드웨어로 감당하는 **동시 연결 수와 자원 효율**. 처리량 병목이 스레드가 아니라면(대부분의 사내 API가 그렇다) 이득이 없다.
- **"MVC에서 WebClient만 쓰는 건?"** — 가능하고 흔한 절충. 외부 API 병렬 호출 구간만 논블로킹으로 얻고 서블릿 모델은 유지 — 단 `block()` 하는 순간 그 스레드는 여전히 묶인다는 것을 인지할 것.
- **"@Transactional이 WebFlux에서 동작하나?"** — ThreadLocal 기반 트랜잭션 동기화는 스레드가 바뀌는 리액티브 체인에서 무의미 — R2DBC + Reactor Context 기반의 리액티브 트랜잭션 관리로 대체해야 한다.
- **"백프레셔가 MVC엔 정말 없나?"** — 있다. TCP 수신 윈도·유한 큐·풀 크기 형태의 **암묵적** 백프레셔가 이미 작동한다(§6-2). 없는 건 홉을 건너 전파되는 **명시적 수요 신호**(`request(n)`)와 drop/buffer/sample 같은 정책 선택지다.
- **"가상 스레드를 켰더니 오히려 장애가 늘었다, 왜?"** — 스레드풀이 암묵적으로 하던 **유입 제어가 사라졌기** 때문이다(§7-3). 동시 요청 상한이 200 → `max-connections` 8192로 40배가 되어, 예전엔 문 앞에서 거절되던 요청이 전부 진입한 뒤 커넥션 풀 앞에서 30초를 기다리다 전면 타임아웃된다 — **빠른 실패가 느린 전멸로 바뀐다.** 세마포어·Bulkhead와 짧은 `connection-timeout`으로 문지기를 명시적으로 복원해야 한다.
- **"어떤 기준으로 도입 판단?"** — ① 동시 연결이 실제로 스레드 한계에 부딪히는가(메트릭 근거) ② 전 의존성이 논블로킹 가능한가(DB 드라이버 포함) ③ 팀이 리액티브 디버깅을 감당하는가 ④ 가상 스레드로 충분하지 않은가(=스트리밍 백프레셔나 극단적 유휴 연결 요건이 있는가, §7-5) — 넷 다 통과해야 도입.

## 한 줄 요약

MVC는 요청당 스레드 1개가 응답까지 묶여 대기를 "스레드 개수"로 흡수하고(상한 = 풀 크기), WebFlux는 코어 수만큼의 이벤트 루프가 I/O를 걸어놓고 스레드를 반납해 대기를 "이벤트 통지"로 흡수한다(적은 스레드로 수만 연결) — 대신 전 구간 논블로킹이 전제라 이벤트 루프 위 블로킹 한 번(JDBC 등)의 폭발 반경이 MVC와 정반대로 크며, 블로킹 스택·CPU 바운드·팀 역량 부족이면 독이 된다. Java 21 가상 스레드는 "블로킹 코드 그대로" 동시성을 올려 요청/응답 워크로드에서 WebFlux의 근거를 상당 부분 무너뜨렸지만 두 가지가 남는다 — ① 스레드풀이 암묵적으로 하던 **유입 제어**가 사라져(200 → `max-connections` 8192, 40배) 커넥션 풀 앞에서 빠른 실패가 느린 전멸로 바뀌므로 세마포어·Bulkhead로 문지기를 명시 복원해야 하고, ② `request(n)`으로 수요를 상류에 전파하는 **스트리밍**과 유휴 연결이 극단적으로 많은 워크로드는 여전히 WebFlux 영역이다(물리 자원 산정은 어느 모델이든 면제되지 않는다).
