# Spring WebFlux vs MVC 스레딩 모델 — "대기를 스레드 개수로 흡수하나, 이벤트로 흡수하나"

> 핵심 관전 포인트: **두 모델의 차이는 "I/O를 기다리는 동안 무엇을 낭비하는가"로 갈린다. MVC는 thread-per-request — 요청 하나에 톰캣 스레드 하나가 응답을 다 쓸 때까지 전속되고, 대기 시간을 스레드 개수로 흡수한다(기본 200개가 곧 동시 요청 상한). WebFlux(Netty)는 이벤트 루프 — 커널에 "이 소켓에 데이터가 오면 알려달라"고 등록해 두고 스레드를 즉시 반납해 다음 이벤트로 넘어가므로, 코어 수만큼의 스레드로 수만 동시 연결을 감당한다. 그래서 WebFlux의 전제는 전 구간 논블로킹이고, 이 전제가 깨지는 순간의 폭발 반경이 결정적이다 — 50ms짜리 블로킹 호출을 감당하는 능력이 톰캣 200스레드는 200/0.05 = 4,000 TPS인데 이벤트 루프 4개는 4/0.05 = 80 TPS로 50배 차이라, JDBC 한 줄이 서버 전체를 세운다. 우회로인 `boundedElastic`(코어×10 = 40스레드)조차 40/0.05 = 800 TPS라 MVC보다 5배 좁으니, 그 우회가 코드의 주류가 되면 WebFlux를 쓸 이유가 없다. 그리고 Java 21 가상 스레드가 "블로킹 코드 그대로" 이벤트 루프급 동시성을 주면서 "동시 연결 때문에 WebFlux"라는 근거는 상당 부분 무너졌다 — 남는 자리는 `request(n)`으로 수요를 상류에 전파해야 하는 스트리밍과 유휴 연결이 극단적으로 많은 경우뿐이다. 대신 가상 스레드는 스레드풀이 암묵적으로 해주던 유입 제어를 없애(동시 요청 상한 200 → `max-connections` 8,192, 40배) 커넥션 풀 앞에서 빠른 실패를 느린 전멸로 바꾸므로, 그 문지기를 세마포어·Bulkhead로 명시 복원해야 한다.**

## 0. 질문 + 의도

**질문**: "Spring WebFlux와 MVC의 스레딩 모델 차이를 설명해주세요. WebFlux 도입이 오히려 독이 되는 경우는?"

**출제 의도**: 기술 선택에서 "우리 팀의 학습 비용, 디버깅 난이도, 블로킹 라이브러리 의존성"까지 넣어 판단하는지 본다. 이력서에 WebFlux를 쓴 지원자의 이해가 튜토리얼 수준인지 운영 수준인지 가르는 질문이기도 하다.

## 1. 전제 지식 — "스레드를 반납한다"가 OS 수준에서 무슨 뜻인가

WebFlux 설명에는 "논블로킹", "이벤트 루프", "스레드를 반납한다" 같은 말이 정의 없이 등장한다. 그런데 이 말들은 프레임워크의 어휘가 아니라 **운영체제의 어휘**다. 아래를 먼저 깔지 않으면 그다음이 전부 주문처럼 들린다.

### 1-1. 블로킹 I/O — 커널이 스레드를 재운다

DB에서 데이터를 읽는 코드는 결국 소켓에서 읽는 코드다. 자바 코드로는 `inputStream.read(buf)` 한 줄이지만, 그 아래에서는 `read(fd, buf, n)`이라는 시스템 콜이 일어난다.

**시스템 콜(system call)**은 애플리케이션이 직접 할 수 없는 일(하드웨어 접근, 네트워크 송수신)을 커널에 대신 해달라고 요청하는 호출이다. 소켓에서 읽는 것은 네트워크 카드가 받은 데이터를 가져오는 일이라 커널을 거쳐야 한다.

이때 **읽을 데이터가 아직 도착하지 않았으면 어떻게 되는가.** 기본 동작은 이렇다.

```
[블로킹 read]

 애플리케이션 스레드            커널
      |
      |── read(fd, buf, n) ──────>│
      |                            │ 소켓 수신 버퍼가 비어 있다
      |                            │ -> 이 스레드를 "대기 큐"로 옮기고 재운다
      |   (스레드 정지)             │    (스케줄러의 실행 대상에서 제외)
      |                            │
      |                            │ ... 50ms 뒤 네트워크 카드가 패킷 수신 ...
      |                            │
      |                            │ -> 대기 큐에서 이 스레드를 깨워 실행 큐로
      |<───── 데이터 반환 ─────────│
      |
      v  다음 줄 실행
```

**여기서 두 가지를 정확히 구분해야 한다.** 잠든 스레드는 CPU를 전혀 쓰지 않는다(스케줄링 대상에서 빠졌으므로). 하지만 **스레드 자체는 놓여나지 않았다.** 그 스레드의 콜 스택에는 `read` 호출까지의 프레임이 그대로 쌓여 있고, 그 스택을 치우지 않는 한 다른 요청의 코드를 실행할 수 없다.

**"CPU를 놓아준 것"과 "스레드를 놓아준 것"은 전혀 다른 이야기다.** 이 문서 전체가 이 한 문장 위에 서 있다.

### 1-2. 논블로킹 I/O — 즉시 돌아오지만, 그것만으로는 부족하다

소켓을 **논블로킹 모드**로 열면(`O_NONBLOCK` 플래그) 커널의 동작이 바뀐다. 읽을 데이터가 없을 때 스레드를 재우는 대신 **즉시 "지금은 없다"는 응답(`EAGAIN`)을 돌려준다.**

```
[논블로킹 read]
  read(fd, ...) -> EAGAIN   (없음. 스레드는 계속 실행 가능)
  read(fd, ...) -> EAGAIN
  read(fd, ...) -> EAGAIN
  ...
  read(fd, ...) -> 데이터!
```

스레드가 안 잠기는 것은 좋은데, **이대로는 더 나쁘다.** 데이터가 올 때까지 계속 물어봐야 하고(이것을 폴링이라 한다) 그 물어보는 동안 CPU를 100% 태운다. 소켓이 1만 개면 1만 번씩 물어봐야 한다.

**그래서 논블로킹 I/O 하나만으로는 아무것도 해결되지 않는다.** 여기에 반드시 짝이 필요하다.

### 1-3. I/O 다중화 — `epoll` / `kqueue`

짝이 되는 것이 **I/O 다중화(I/O multiplexing)**다. 소켓 하나하나에 물어보는 대신, **커널에 소켓 목록을 통째로 맡기고 "이 중 하나라도 읽을 게 생기면 깨워달라"고 부탁하는** 방식이다.

리눅스의 구현이 **`epoll`**(event poll), macOS·BSD의 구현이 **`kqueue`**(kernel event queue)다. 이름이 뜻 그대로다 — "이벤트를 기다리는 창구".

```
[epoll 을 쓰는 스레드 한 개가 소켓 1만 개를 감시한다]

 ① 등록:   epoll_ctl(ep, ADD, 소켓#1)   "이 소켓에 읽을 게 생기면 알려줘"
           epoll_ctl(ep, ADD, 소켓#2)
           ...  (소켓 1만 개 등록)

 ② 대기:   epoll_wait(ep, events, ...)
           -> 준비된 소켓이 하나도 없으면 여기서 이 스레드가 잠든다.
              (스레드 1개만 잠긴다. 이게 핵심이다)

 ③ 통지:   커널이 준비된 소켓 목록만 돌려준다
           -> [소켓#742, 소켓#1188, 소켓#9003]

 ④ 처리:   돌려받은 것만 read 한다. 이것들은 데이터가 확실히 있으므로 안 막힌다.
```

**핵심은 ③이다.** 1만 개를 훑어보는 것이 아니라 **준비된 것만** 돌려받는다. 그래서 감시 대상이 1만 개든 10만 개든 스레드는 하나면 된다. (구형 API인 `select`·`poll`은 매번 전체 목록을 훑어야 해서 소켓 수에 비례해 느려졌다. `epoll`·`kqueue`가 이 문제를 해결한 것이다.)

이제 **"스레드를 반납한다"가 무슨 뜻인지** 정확히 말할 수 있다.

| | 블로킹 | 논블로킹 + 다중화 |
|---|---|---|
| 기다리는 방식 | 스레드가 소켓 하나에 매달려 잠든다 | 소켓들을 커널에 위탁하고 준비된 것만 처리 |
| 소켓 1만 개를 기다리려면 | 스레드 1만 개 | 스레드 1개 |
| 대기 중 스레드의 스택 | 그 요청의 프레임이 쌓인 채 묶여 있다 | 비어 있다 — 다른 일을 할 수 있다 |

**"반납한다"는 것은 스택을 비우고 돌아온다는 뜻이다.** 그 대신 "나중에 이어서 할 일"을 콜백으로 어딘가에 적어 둬야 하는데, 그 적어 두는 방식을 선언적으로 만든 것이 Reactor의 `Mono`/`Flux`다.

### 1-4. 이벤트 루프 — 그 위에 올린 프로그래밍 모델

**이벤트 루프(event loop)**는 1-3의 `epoll_wait` 호출을 **무한 루프로 돌리는 스레드**다. 이름 그대로 "이벤트를 받아 처리하는 것을 반복하는 고리"다.

```java
// 이벤트 루프의 뼈대 (개념 코드)
while (running) {
    List<Event> ready = selector.select();   // epoll_wait — 준비된 것이 없으면 여기서 잠든다
    for (Event e : ready) {
        e.handler().run();                   // 준비된 이벤트의 콜백을 실행한다
        // ★ 이 handler 안에서 절대로 블로킹하면 안 된다.
        //    블로킹하는 순간 이 루프가 멈추고, 이 루프가 담당하는
        //    나머지 모든 연결의 이벤트 처리도 함께 멈춘다.
    }
}
```

주석의 별표가 이 문서 3절 전체의 씨앗이다. **루프 하나가 수천 개 연결을 담당하므로, 그 루프를 한 번 막으면 수천 개가 함께 멈춘다.**

## 2. 두 모델 — 대기를 스레드로 흡수하나, 이벤트로 흡수하나

### 2-1. MVC — thread-per-request

**thread-per-request(요청당 스레드)**는 이름 그대로다. 요청 하나가 도착하면 톰캣이 자기 워커 스레드 하나를 배정하고, 그 스레드가 **응답 바이트를 다 쓸 때까지** 그 요청에 전속된다.

```java
// 블로킹 서블릿 MVC + JDBC
public OrderResponse getOrder(Long id) {
    Order order = orderRepository.findById(id);
    // 이 한 줄 안에서 1-1의 블로킹 read 가 일어난다.
    // 스레드는 커널의 대기 큐로 들어가 CPU 를 쓰지 않지만,
    // getOrder 호출 프레임이 스택에 그대로 남아 있어 다른 요청을 못 받는다.
    return toResponse(order);
}
```

그래서 **동시 요청 상한 = 스레드풀 크기**가 된다. 톰캣 기본값은 `max-threads` 200이다. 필요한 스레드 수는 Little's law로 계산한다 — 500 TPS × 응답 100ms = 동시 50개(`25-thread-pool-connection-pool-sizing.md`).

이 모델의 성질은 한 문장으로 요약된다. **대기 시간을 스레드 개수로 산다.** 대기가 길어지면(외부 API 지연 등) 같은 처리량을 내는 데 더 많은 스레드가 필요하다. 그런데 스레드는 스택 메모리(플랫폼에 따라 수백 KB~2MB 예약)와 컨텍스트 스위칭 비용이 있어서, 수천~수만 동시 연결로 가면 이 방식이 물리적으로 감당이 안 된다.

한 가지 흔한 오해를 여기서 정리하자. 스레드 덤프에서 **DB 응답을 기다리는 스레드는 `BLOCKED`가 아니라 `RUNNABLE`로 표시된다.** `BLOCKED`는 오직 `synchronized` 락 경쟁을 뜻하는 상태 이름이고, 소켓 대기는 네이티브 메서드 안에서 일어나 JVM이 상태를 알 수 없기 때문에 `RUNNABLE`로 남는다. 자세한 것은 25번 문서 2-1에 있다.

### 2-2. WebFlux(Netty) — 이벤트 루프

WebFlux는 서블릿 컨테이너 대신 **Netty**를 기본 서버로 쓴다. Netty는 1-4의 이벤트 루프를 자바로 구현한 네트워크 프레임워크다.

**이벤트 루프 스레드는 코어 수만큼만 뜬다.** Spring WebFlux가 쓰는 Reactor Netty의 기본값은 `max(가용 코어 수, 4)`이고, `reactor.netty.ioWorkerCount` 시스템 프로퍼티로 바꿀 수 있다. 4코어 장비면 **4개**다.

동작을 순서대로 보면 이렇다.

```
① 요청 도착
   -> 이벤트 루프 스레드가 핸들러 체인을 실행한다

② DB/외부 API 호출을 논블로킹으로 걸어놓는다
   -> 쿼리를 소켓에 쓰고, "이 소켓에 응답이 오면 알려달라"고 epoll 에 등록한다
   -> 이어서 할 일(리액티브 체인의 다음 단계)을 콜백으로 등록해 둔다
   -> 그리고 스레드는 즉시 다음 이벤트 처리로 넘어간다  ★ 여기가 "반납"

③ 50ms 뒤 응답이 소켓에 도착
   -> 커널(epoll/kqueue)이 이벤트 루프에 통지
   -> 이벤트 루프가 ②에서 등록해 둔 콜백을 이어서 실행한다
```

스레드가 "무언가를 기다리는" 일이 없고 **항상 실행할 이벤트만 처리**한다. 그래서 대기 시간이 스레드를 소모하지 않고, 4~8개 스레드로 수만 동시 연결을 감당한다.

`Mono`/`Flux`는 이 "걸어놓고 나중에 이어 하기"를 사람이 읽을 수 있는 체인으로 표현한 것이다. 콜백을 손으로 중첩해 쓰면(콜백 지옥) 관리가 안 되므로, 그것을 선언적 연산자 체인으로 바꾼 것이 리액티브 라이브러리의 존재 이유다.

여기에 하나 더, **백프레셔**가 스펙에 내장돼 있다. 이게 정확히 무슨 뜻인지는 2-5에서 따로 다룬다.

### 2-3. 같은 상황 하나로 겹쳐 보기

말로 하는 대비는 잘 안 남는다. **똑같은 상황 하나**를 두 모델에 넣어 보자.

> 요청 100개가 동시에 도착한다. 각 요청은 DB 쿼리 하나를 보내고 응답을 50ms 기다린 뒤 결과를 돌려준다. 장비는 4코어다.

```
[MVC — 톰캣 스레드 100개가 잠든다]

 t=0ms    요청 100개 도착 -> 톰캣이 워커 스레드 100개 배정
          각 스레드가 쿼리를 보내고 소켓 read 에서 블로킹

 t=0~50   ┌ 스레드 #1   [잠듦] ─── 소켓 대기
          ├ 스레드 #2   [잠듦] ─── 소켓 대기
          ├ ...
          └ 스레드 #100 [잠듦] ─── 소켓 대기
          CPU 사용률 ≈ 0%   (아무도 일하지 않는다)
          점유 자원: 스레드 100개 + 스택 100개어치 메모리

 t=50     DB 응답 도착 -> 100개 스레드가 차례로 깨어나 결과를 매핑하고 응답


[WebFlux — 이벤트 루프 4개가 돌아다닌다]

 t=0ms    요청 100개 도착 -> 이벤트 루프 4개가 나눠 받아
          각각 쿼리를 소켓에 쓰고 epoll 에 "응답 오면 알려줘" 등록 후 다음으로

 t≈1ms    등록 100건 완료. 루프 4개는 다시 epoll_wait 에서 대기.
          ┌ 이벤트 루프 #1 [epoll_wait]  <- 담당 연결 25개어치 콜백을 들고 있다
          ├ 이벤트 루프 #2 [epoll_wait]
          ├ 이벤트 루프 #3 [epoll_wait]
          └ 이벤트 루프 #4 [epoll_wait]
          CPU 사용률 ≈ 0%   (여기까진 같다)
          점유 자원: 스레드 4개 + 콜백 객체 100개 (수십~수백 바이트씩)

 t=50     커널이 준비된 소켓 100개를 통지
          -> 루프 4개가 콜백 100개를 나눠 실행
```

**두 모델 모두 50ms를 기다린다는 사실은 같다.** 대기 시간이 짧아지는 것이 아니다. 다른 것은 **그 50ms 동안 묶여 있는 스레드의 개수**뿐이다 — 100 대 4.

그래서 이런 따름정리가 나온다. **WebFlux를 쓴다고 단일 요청이 빨라지지 않는다.** 좋아지는 것은 "같은 하드웨어로 몇 개를 동시에 물고 있을 수 있는가"다. 요청 100개짜리 서비스에서는 차이가 없고, 요청 10만 개짜리 서비스에서 갈린다.

### 2-4. 두 모델 비교

| | MVC (Tomcat) | WebFlux (Netty) |
|---|---|---|
| 스레드 수 | 동시 요청만큼 (기본 200) | ≈ 코어 수 (Reactor Netty: `max(코어, 4)`) |
| I/O 대기 시 스레드 | 커널 대기 큐에서 잠듦, 그 요청에 전속 | 반납 — 다른 이벤트를 처리 |
| 동시성 한계 결정 요인 | 스레드풀 크기 (Little's law) | 소켓·메모리 한계 (스레드가 아님) |
| 블로킹 호출 1건의 피해 | 스레드 200개 중 1개 잠김 | 스레드 4개 중 1개 잠김 — 그 루프의 모든 연결 정지 |
| 백프레셔 | 암묵적 — 스레드풀 크기·큐 상한·풀 크기가 대신한다 (2-6) | 명시적 — `request(n)` 수요 신호가 체인 전체를 거슬러 전파 (2-7) |
| 적합 워크로드 | 일반 CRUD API, 블로킹 스택(JDBC), 팀 친숙도 우선 | 대량 동시 연결(스트리밍·SSE·게이트웨이), I/O 대기 비중이 큰 중계 호출, 전 구간 논블로킹이 가능할 때 |

### 2-5. 백프레셔란 무엇인가

2-2에서 "WebFlux는 백프레셔가 내장"이라고 넘어갔다. 이 개념은 3-9(가상 스레드가 무엇을 없애는가)의 전제가 되므로 여기서 제대로 정의하고 간다.

**백프레셔(backpressure)는 받는 쪽이 감당할 수 있는 속도로만 보내게 만드는 장치다.** 배관에서 온 말이다 — 하류가 좁으면 압력이 거꾸로 밀려 올라와 펌프를 막는다. **흐름은 아래로 가고, "그만 보내"라는 신호는 위로 간다.**

없으면 어떻게 되는지를 보는 것이 이해가 빠르다.

```java
// before: 백프레셔 없음 — 생산자가 소비자 사정을 모른다
BlockingQueue<Log> queue = new LinkedBlockingQueue<>();   // 상한 없는 큐

while (true) queue.offer(read());   // 생산 10,000/s — offer 는 상한이 없어 절대 안 막힌다
while (true) send(queue.take());    // 소비  1,000/s
```

초당 9,000건씩 쌓이는데 **생산자는 아무 문제 없다고 느낀다** — `offer`가 계속 성공하기 때문이다. 지연이 서서히 늘다가 힙이 차는 순간 OOM으로 급사한다. **서서히 느려지다 멈추는 것이 아니라, 멀쩡해 보이다 절벽에서 떨어진다.**

```java
// after: 백프레셔 있음
BlockingQueue<Log> queue = new LinkedBlockingQueue<>(1_000);   // 상한을 둔다

while (true) queue.put(read());
// 큐가 가득 차면 put 이 여기서 막힌다.
// 그러면 read() 를 덜 부르게 되고, 생산 속도가 소비 속도에 자동으로 맞춰진다.
```

`offer` → `put`, 무제한 → 상한. 이 차이가 전부다. **큐의 상한은 제약이 아니라 신호 장치다** — 상한이 없으면 시스템은 자기가 과부하라는 사실을 알 방법이 없다.

포화됐을 때의 선택지는 셋뿐이고, 백프레셔를 "건다"는 것은 이 중 하나를 **고른다**는 뜻이다.

| 전략 | 동작 | 적합한 경우 |
|---|---|---|
| 막기(block) | 생산자를 세운다 | 하나도 유실되면 안 될 때 (결제·주문) |
| 버리기(drop) | 오래된 것 또는 새 것을 버린다 | 최신값만 의미 있을 때 (시세·센서·위치) |
| 거절(reject) | 생산자에게 에러를 반환한다 | 호출자가 재시도·백오프 가능할 때 (HTTP 429) |

"막기"만 쓰면 정체가 상류로 계속 전파되므로, 실무에서는 **막기 + 타임아웃 후 거절** 조합이 일반적이다. 백프레셔를 적용 지점별로 정리한 논의는 `07-traffic-performance/16-backpressure-and-application-points.md`에 있다.

### 2-6. 블로킹 모델에도 백프레셔는 있다 — 다른 이름으로

**"MVC엔 백프레셔가 없다"는 말은 부정확하다.** 이미 곳곳에서 쓰고 있고, 다만 아무도 그렇게 부르지 않았을 뿐이다.

- **TCP 수신 윈도** — 받는 쪽 버퍼가 차면 윈도 크기를 0으로 광고하고, 보내는 쪽의 `write()`가 막힌다. 네트워크 계층의 백프레셔다.
- **`CallerRunsPolicy`** — 스레드풀이 포화되면 **호출자 스레드가 그 작업을 직접 실행**한다. 호출자가 그동안 새 작업을 못 넣으니 유입이 자연히 준다(`15-async-annotation.md`).
- **톰캣 `max-threads` + accept 큐** — 처리 못 할 요청을 앞에서 거절해 뒷단(DB)에 과부하가 전달되는 것을 막는다(`25-thread-pool-connection-pool-sizing.md`).
- **커넥션 풀 크기** — "DB에 동시에 이만큼까지만 보낸다"는 선언이다. 정확히 같은 얘기다(`26-hikaricp-connection-pool-exhaustion.md`).

즉 **백프레셔는 특정 프레임워크의 기능이 아니라 유한한 자원을 다루는 시스템의 일반 원리**다.

2-5의 세 전략이 블로킹 세계에서는 스레드풀의 거부 정책(`RejectedExecutionHandler`)으로 나타난다. 리액티브 세계의 연산자와 나란히 놓으면 대응이 정확히 보인다.

| 포화 시 정책 | 블로킹(스레드풀·큐) | Reactive Streams |
|---|---|---|
| 막기 | 유한 `BlockingQueue.put`, `CallerRunsPolicy` | 기본 동작 — `request(n)` 없으면 생산자가 멈춘다 |
| 새 것 버리기 | `DiscardPolicy` | `onBackpressureDrop()` |
| 오래된 것 버리기 | `DiscardOldestPolicy` | `onBackpressureBuffer(n, DROP_OLDEST)`, `onBackpressureLatest()` |
| 거절 | `AbortPolicy` (`RejectedExecutionException`) | `onBackpressureError()` |

### 2-7. 그럼 Reactive Streams는 무엇이 다른가

2-6의 사례들은 백프레셔가 **홉(hop) 하나에서 국소적으로** 작동한다. 소켓에서, 큐에서, 풀에서 각각 따로 막힐 뿐 **서로를 모른다.** 커넥션 풀이 막혀 있다는 사실이 그 위의 HTTP 클라이언트나 그보다 더 위의 데이터 소스에 전달되지 않는다.

Reactive Streams는 이것을 **명시적인 수요 신호로 만들어 체인 전체를 거슬러 올려보낸다.**

```java
subscription.request(10);   // 소비자가 "지금 10건 받을 수 있다"고 상류에 알린다
```

**`request(n)`이 없으면 생산자는 한 건도 보내지 않는다.** 기본이 밀어내기(push)가 아니라 **당겨오기(pull)**라서, 생산자가 소비자의 속도를 추측할 필요가 없다. 그리고 2-5의 세 전략을 **선언적으로** 고를 수 있다.

```java
eventFlux
    .onBackpressureDrop(e -> log.warn("버림 {}", e.id()))
    // 소비자가 못 따라오면 새로 들어온 것을 버린다. 콜백에서 무엇을 버렸는지 남긴다.

    // .onBackpressureBuffer(1000, BufferOverflowStrategy.DROP_OLDEST)
    //   1,000개까지 버퍼링하고 넘치면 가장 오래된 것부터 버린다.

    // .sample(Duration.ofMillis(100))
    //   100ms 마다 최신값 하나만 통과시킨다. 시세·위치처럼 최신값만 의미 있을 때.
```

블로킹 모델로도 같은 것을 만들 수는 있지만 큐와 정책 코드를 직접 짜야 하고, 그것은 결국 **Reactive Streams를 손으로 재구현하는 일**이다.

## 3. WebFlux가 독이 되는 경우 — 폭발 반경, 우회의 대가, 그리고 제3의 선택지

여기가 이 질문의 본체다. WebFlux의 이점은 **전 구간 논블로킹**이라는 전제 위에서만 성립하고, 그 전제가 깨졌을 때의 피해가 MVC와 **질적으로 다르다.**

### 3-1. 이벤트 루프 위의 블로킹 호출 — 폭발 반경을 숫자로

"블로킹 라이브러리를 쓰면 WebFlux의 이점이 사라진다"는 흔한 설명은 **너무 순한 표현이다.** 이점이 사라지는 정도가 아니라 **서버가 멈춘다.**

1-4의 이벤트 루프 코드를 다시 보면 이유가 자명하다. 핸들러 안에서 블로킹하면 그 `while` 루프가 그 자리에 선다. 그 루프가 담당하는 **모든 연결**의 이벤트 처리가 함께 멈춘다.

숫자로 보면 차이가 분명해진다. 50ms 걸리는 블로킹 호출(JDBC 쿼리 하나라고 하자)을 각 모델이 초당 몇 건이나 감당할 수 있는지 Little's law로 계산해 보자. 스레드 하나가 1초에 50ms짜리 작업을 20건 처리할 수 있다.

```
감당 가능한 블로킹 호출 = 스레드 수 / 블로킹 시간

  이벤트 루프 4개    :   4 / 0.05s =    80 TPS
  톰캣 스레드 200개  : 200 / 0.05s = 4,000 TPS

  차이 = 4,000 / 80 = 50배
```

**초당 80건.** 이것이 4코어 WebFlux 서버가 JDBC 호출을 흘려보낼 수 있는 전부다. 그 이상이 들어오면 이벤트 루프 4개가 전부 소켓 대기에 잠기고, **그 순간부터 이 서버는 어떤 요청도 받지 못한다.** 이미 열려 있는 연결의 이벤트도, 새 연결의 accept도, 헬스체크도 처리되지 않는다.

MVC에서 같은 일이 벌어지면 4,000 TPS까지는 아무 일도 없다. **"200개 중 1개가 잠기는 것"과 "4개 중 1개가 잠기는 것"은 산술적으로 50배 차이이고, 체감으로는 "느려짐"과 "정지"의 차이다.**

Netty의 구조 때문에 피해가 한 겹 더 있다. **Netty는 채널(연결) 하나를 이벤트 루프 하나에 고정 배정한다.** 연결이 수립될 때 루프가 정해지고 그 연결이 닫힐 때까지 바뀌지 않는다. 그래서 루프 #1이 막히면 루프 #2가 그 연결들을 대신 처리해 주지 않는다. **루프 하나가 막히는 것은 "전체의 1/4이 느려지는 것"이 아니라 "그 루프가 담당하는 연결들의 전면 정지"다.**

그래서 결론은 이렇다. **DB 드라이버가 JDBC(R2DBC가 아니라)라면 어딘가에서 반드시 블로킹이 일어나고, WebFlux의 이득은 사라지고 위험만 남는다.** 한 구간이라도 블로킹이면 전 구간 논블로킹이라는 전제가 통째로 깨진다.

### 3-2. 숨은 블로킹을 찾는 법 — BlockHound (가산점 포인트)

문제는 블로킹이 **눈에 잘 안 띈다**는 것이다. JDBC처럼 명백한 것만 있는 게 아니다.

- 동기 HTTP 클라이언트(`RestTemplate`, 구식 SDK)
- 파일 I/O (`Files.readAllBytes`, 로컬 캐시 읽기)
- 동기 로깅 어펜더 — **디스크가 느려지면 로그 한 줄이 이벤트 루프를 막는다**
- 서드파티 라이브러리 내부의 `synchronized` 블록, `Thread.sleep`, `CountDownLatch.await`
- `Mono.block()` — 리액티브 코드 안에서 무심코 호출한 경우

**BlockHound**는 이것을 잡아주는 도구다. JVM 에이전트로 붙어서, **논블로킹으로 지정된 스레드(이벤트 루프)에서 블로킹 호출이 일어나면 `BlockingOperationError`를 던진다.**

```java
// 테스트 소스셋에서 한 번 설치해 두면 그 뒤 테스트 전체에 적용된다
BlockHound.install();

// 정상적으로 논블로킹인데 오탐이 나는 지점은 예외로 등록한다
BlockHound.builder()
    .allowBlockingCallsInside("com.example.legacy.LegacyCache", "warmUp")
    .install();
```

**테스트 단계에서 켜는 것이 핵심이다.** 운영에서 켜면 블로킹이 발견될 때마다 에러가 나므로 오히려 위험하다. CI에서 통합 테스트를 BlockHound와 함께 돌려 "이번 커밋에서 블로킹이 들어왔는지"를 자동으로 막는 것이 제대로 된 사용법이다.

면접에서 이 도구 이름이 나오면, **"WebFlux는 전 구간 논블로킹이 전제인데 그 전제를 사람 눈으로 지킬 수 없다는 걸 알고 있다"**는 신호가 된다.

### 3-3. CPU 바운드 작업 — 반납할 대기가 없다

이벤트 루프의 이점은 **"기다리는 시간을 다른 일에 쓴다"**는 것이다. 그렇다면 기다리는 시간이 없는 작업에는 아무 이점이 없다.

이미지 리사이징, 암호화, 대량 집계 같은 CPU 바운드 작업은 **반납할 대기가 없다.** 이벤트 루프가 연산에 잡혀 있는 동안 그 루프에 배정된 모든 연결이 지연되므로, 3-1과 정확히 같은 피해가 난다. 블로킹 I/O가 아니라 계산이 루프를 막는다는 점만 다르다.

그리고 근본적으로 **CPU 바운드는 모델과 무관하게 코어 수가 상한**이다. 4코어는 초당 4,000ms의 CPU 시간을 제공하고, 그 이상은 어떤 스레딩 모델로도 만들어낼 수 없다(`25-thread-pool-connection-pool-sizing.md` 2-3). 여기서 WebFlux를 도입하는 것은 이득이 0인데 위험만 도입하는 선택이다.

### 3-4. 팀·운영 비용 — 가장 자주 과소평가되는 항목

출제 의도가 명시적으로 짚는 항목이다. 기술적 우열이 아니라 **조직의 감당 능력**을 판단에 넣는지를 본다.

**(1) 학습 곡선.** 리액티브는 명령형과 사고 방식이 다르다. `map`과 `flatMap`의 구분, `subscribeOn`과 `publishOn`의 차이, 구독하지 않으면 아무 일도 일어나지 않는다(cold publisher)는 성질 — 이것들을 팀 전체가 알아야 한다. 한 명이라도 모르면 그 사람이 짠 코드에 `block()`이 들어간다.

**(2) 디버깅 난이도.** 스택트레이스가 체인 곳곳에서 끊긴다. 예외가 발생한 시점의 스택에는 **원래 요청이 어디서 시작됐는지가 없다** — 그 요청을 시작한 스레드는 이미 다른 일을 하고 있기 때문이다. `Hooks.onOperatorDebug()`나 `checkpoint()`로 보완할 수 있지만, 전자는 오버헤드가 커서 운영에서 상시 켜기 어렵다.

**(3) ThreadLocal 전제가 깨진다.** 이게 실무에서 가장 크게 물린다. 자바 생태계의 많은 것들이 "한 요청은 한 스레드에서 처리된다"를 전제로 ThreadLocal에 컨텍스트를 담아 왔다.

| 기능 | 무엇을 ThreadLocal에 담는가 | WebFlux에서 |
|---|---|---|
| 로깅 MDC | 요청 ID, 사용자 ID | 스레드가 바뀌면 사라진다 — Reactor Context로 옮겨야 한다 |
| Spring Security | `SecurityContext`(인증 주체) | `ReactiveSecurityContextHolder`로 대체 |
| `@Transactional` | 트랜잭션 동기화, 커넥션 바인딩 | 무의미 — R2DBC + 리액티브 트랜잭션 관리로 대체 |

`@Transactional`이 안 되는 이유를 정확히 말할 수 있어야 한다. Spring의 트랜잭션 동기화는 **커넥션을 `TransactionSynchronizationManager`의 ThreadLocal에 묶어** 같은 스레드의 후속 DB 접근이 그 커넥션을 재사용하게 하는 구조다(`24-transaction-synchronization-connection-binding.md`). 리액티브 체인은 단계마다 스레드가 바뀔 수 있으므로 이 연결고리가 성립하지 않는다.

**(4) 의존성 전수 조사.** 도입 전에 **모든 의존 라이브러리의 논블로킹 여부를 점검**해야 한다. 하나라도 블로킹이면 3-1의 피해를 본다. 이건 라이브러리 목록을 훑는 정도로 끝나지 않고, 그 라이브러리들이 내부에서 뭘 쓰는지까지 봐야 한다.

정리하면 이렇다. **튜토리얼 수준의 이해로 도입한 WebFlux는 같은 하드웨어의 MVC보다 느리고 장애만 어렵게 만든다.** 이 문장을 말할 수 있으면 출제 의도에 정면으로 답한 것이다.

### 3-5. 블로킹이 불가피할 때의 우회와 그 대가

레거시 JDBC를 당장 R2DBC로 바꿀 수 없는 상황이 실제로는 대부분이다. 이때 쓰는 우회가 **블로킹 작업을 전용 워커 풀로 격리하는 것**이다.

```java
// 이벤트 루프에서 블로킹 JDBC 를 직접 호출하면 안 되므로 별도 스레드풀로 격리한다
Mono.fromCallable(() -> jdbcRepository.findById(id))   // 블로킹 호출을 감싼다
    .subscribeOn(Schedulers.boundedElastic());
    // subscribeOn 은 "이 체인의 소스를 어느 스레드에서 실행할지"를 정한다.
    // 블로킹 소스를 격리하려면 publishOn 이 아니라 subscribeOn 이다 —
    // publishOn 은 그 지점 이후 단계의 실행 스레드만 바꾸므로,
    // 소스 자체가 이벤트 루프에서 실행되는 것을 막지 못한다.
```

`boundedElastic`은 Reactor가 블로킹 작업용으로 제공하는 워커 풀이다. 기본 상한은 **가용 코어 수 × 10**이고(4코어면 40개), 그것도 다 차면 최대 10만 건까지 큐에 쌓았다가 처리한다. 유휴 스레드는 60초 뒤 회수된다.

**그런데 이 우회의 대가를 정확히 계산하면 결론이 뒤집힌다.**

```
50ms 짜리 블로킹 호출을 감당하는 능력

  이벤트 루프 4개 (우회 없음)     :   4 / 0.05s =    80 TPS
  boundedElastic 40개 (우회)      :  40 / 0.05s =   800 TPS
  톰캣 스레드 200개 (그냥 MVC)    : 200 / 0.05s = 4,000 TPS
```

**우회로는 MVC보다 5배 좁다.** 이벤트 루프를 지키는 데는 성공했지만, 그 구간은 **결국 thread-per-request로 회귀**한 것이고 그 풀이 톰캣 기본값보다 작기 때문이다. 그리고 회귀했으므로 풀 크기 산정 문제(Little's law)가 그대로 되살아난다 — 800 TPS를 넘기려면 `boundedElastic`의 크기를 조정해야 하는데, 그 순간 "우리는 왜 WebFlux를 쓰고 있는가"라는 질문이 돌아온다.

거기에 스레드 간 전환 비용도 얹힌다. 이벤트 루프 → 워커 → 이벤트 루프로 두 번 넘어가므로 요청당 컨텍스트 스위칭이 늘고 지연이 조금 붙는다.

**그래서 판단 기준은 이것이다. 이 우회가 몇 군데에 쓰이는가.** 전체 엔드포인트의 소수(레거시 한두 개)라면 합리적인 절충이지만, **이 우회가 코드의 주류가 되면 WebFlux를 쓸 이유가 남지 않는다.** 그때는 MVC로 돌아가는 것이 더 빠르고 더 단순하다.

### 3-6. 제3의 선택지 — Java 21 가상 스레드

여기까지의 논의는 "블로킹 코드를 쓰려면 스레드가 많아야 하고, 스레드는 비싸다"는 전제 위에 있었다. **Java 21의 가상 스레드가 그 전제를 무너뜨린다.**

**가상 스레드(virtual thread)**는 OS 스레드에 1:1로 대응하지 않는, JVM이 스케줄링하는 경량 스레드다. 핵심 동작은 이렇다.

```
[플랫폼 스레드]
  블로킹 -> OS 가 그 스레드를 재운다 -> OS 스레드 하나가 통째로 묶인다

[가상 스레드]
  블로킹 -> JDK 가 시스템 콜 직전에 가로채서
            ① 소켓을 epoll 에 등록하고
            ② 이 가상 스레드의 콜 스택을 힙으로 옮겨 얼린 뒤(freeze)
            ③ 캐리어 스레드(실제 OS 스레드)를 반납한다
         -> 캐리어는 즉시 다른 가상 스레드를 실행한다
         -> 응답이 오면 스택을 다시 캐리어에 올려 이어서 실행한다(thaw)
```

**결과적으로 WebFlux가 하는 일과 같은 일을 한다.** 차이는 **누가 하는가**다. WebFlux는 개발자가 코드를 리액티브 체인으로 다시 써서 "이어서 할 일"을 콜백으로 만들어야 하지만, 가상 스레드는 **런타임이 콜 스택을 통째로 저장·복원해** 그 일을 대신해 준다. 그래서 코드는 블로킹 스타일 그대로다.

```java
// 이 코드가 가상 스레드 위에서 실행되면, 블로킹 두 줄에서 캐리어가 반납된다.
// 코드는 한 글자도 리액티브가 아니고, 스택트레이스도 온전하다.
public OrderResponse getOrder(Long id) {
    Member member = memberClient.get(id);        // 300ms 대기 — 여기서 캐리어 반납
    Order order = orderRepository.findById(id);  // 50ms 대기 — 여기서도 반납
    return toResponse(order, member);
}
```

**이것이 "가상 스레드가 WebFlux의 대안이 되는 이유"다.** 리액티브 재작성 없이, ThreadLocal을 버리지 않고, 스택트레이스를 잃지 않고 동시성을 얻는다.

Spring Boot 3.2 이상에서는 설정 한 줄이면 켜진다.

```yaml
spring:
  threads:
    virtual:
      enabled: true    # 톰캣 요청 처리를 가상 스레드로 — MVC 스타일 코드를 그대로 둔다
```

다만 공짜는 아니다. **핀닝(pinning)** — JVM이 시스템 콜 경로를 소유하지 못하는 지점(`synchronized` 블록 안에서의 블로킹, 네이티브 호출)에서는 캐리어를 반납하지 못하고 못박히는 함정이 있다. 동작 원리와 JDK 버전별 차이는 `01-java-kotlin/28-virtual-threads-pinning.md`에서 다룬다.

### 3-7. 그 플래그가 실제로 바꾸는 것 / 안 바꾸는 것

`spring.threads.virtual.enabled=true`는 톰캣 요청 스레드만 바꾸는 것이 아니다. **"고정 크기 풀"이라는 전제가 통째로 사라지는** 변화다.

**바뀌는 것**: 톰캣 요청 처리 스레드. 그리고 `@Async`의 기본 executor가 풀링 없는 `SimpleAsyncTaskExecutor`로, `@Scheduled`의 스케줄러가 `SimpleAsyncTaskScheduler`로 바뀐다(`15-async-annotation.md`). 이들은 작업마다 새 가상 스레드를 띄우므로 core/max/queue 튜닝 논의 자체가 무의미해진다.

**안 바뀌는 것**: 직접 만들어 등록한 `ExecutorService` 빈, HikariCP 풀 크기, `parallelStream`이 쓰는 공용 ForkJoinPool(`01-java-kotlin/17-parallelstream-pitfalls.md`).

이 구분이 중요한 이유는, **플래그 하나로 시스템의 절반만 바뀌면 나머지 절반이 병목이 되기 때문**이다. 그게 3-10의 내용이다.

### 3-8. "무한정"의 실제 상한 — 200이 아니라 8,192

가상 스레드를 켜면 스레드 개수 제한이 사라진다. 그런데 **동시 요청 상한이 사라지는 것은 아니다.**

톰캣에는 스레드 수와 별개로 **`max-connections`**라는 설정이 있다. 동시에 열어 둘 수 있는 연결의 최대 개수이고, NIO 커넥터의 **기본값은 8,192**다. 가상 스레드를 켜면 `max-threads`가 실질적 제한을 못 하게 되므로, **이 값이 새로운 실질 상한**이 된다.

| | 기본 MVC | 가상 스레드 |
|---|---|---|
| 동시 요청 상한 | `max-threads` = 200 | `max-connections` = 8,192 |

**40배**다. "무한정"은 스레드 얘기이지 요청 얘기가 아니고, 이 40배가 3-9와 3-10의 문제를 만든다.

### 3-9. 사라지는 것은 백프레셔가 아니라 유입 제어

2-6에서 "블로킹 모델에도 백프레셔가 있다"고 했다. 그 목록에 있던 항목 하나가 가상 스레드로 사라진다.

**톰캣 스레드풀 200개는 그 자체가 유입 제어(admission control) 장치였다.** 유입 제어란 "시스템에 들어오는 요청의 수 자체를 문 앞에서 제한하는 것"이다. 201번째 요청은 스레드를 못 잡아 accept 큐에서 대기하다 거절된다. 아무도 그것을 백프레셔라고 부르지 않았지만, **시스템을 지켜주던 것은 그 숫자였다.**

가상 스레드는 그 문지기를 치운다. 여기서 정확히 짚어야 할 것이 있다. **상한이 없어진 것이 아니라 개발자 책임으로 옮겨진 것**이다. 물리 자원(DB 커넥션, 파일 디스크립터, 외부 API rate limit)의 상한은 그대로 있고, 다만 그 앞에서 요청을 걸러 주던 장치가 없어졌을 뿐이다. 그러니 **명시적으로 다시 넣어야 한다.**

### 3-10. 물리 자원 산정은 그대로 유효하고, 실패 양상은 악화된다

한 줄 원리는 이것이다. **가상 스레드는 "기다리는 주체"를 싸게 만들 뿐, "기다리는 대상"의 개수를 늘리지 않는다.**

DB 커넥션, 파일 디스크립터, 외부 API의 초당 허용량은 물리적으로 고정돼 있다. 가상 스레드를 1만 개 띄워도 Hikari 커넥션 10개는 10개다. Little's law는 **자원별로** 성립하므로(`25-thread-pool-connection-pool-sizing.md` 1-3) 스레드 계산식만 무의미해지고 **커넥션 계산식은 그대로 남는다.**

그런데 "그대로 유효"보다 나쁘다. **실패 양상이 악화된다.** 흔한 안티패턴 하나로 따라가 보자.

```java
@Transactional
public Order place(Long id) {
    Order o = orderRepository.save(...);   // 여기서 커넥션을 잡는다 — 이 줄부터 커밋까지가 점유 구간
    paymentClient.charge(o);               // 외부 API 300ms — 커넥션을 쥔 채로 기다린다
    return o;                              // 커밋 시점에 커넥션 반환
}
```

Hikari 풀 10개인 서비스에 동시 요청 10,000개가 들어온 상황을 두 모델로 비교하면 이렇다.

| | 톰캣 스레드 200개 | 가상 스레드 |
|---|---|---|
| 실제 진입 요청 | 200개 | 8,192개 |
| 커넥션 경쟁 | 200 : 10 | 8,192 : 10 |
| 나머지 요청 | accept 큐에서 **빨리 거절** | 전부 진입 후 `getConnection()`에서 대기 |
| 결과 | 일부 503 + 나머지는 정상 응답 | 전면 `SQLTransientConnectionException`(기본 30초 타임아웃), 응답시간 붕괴 |

**빠른 실패가 느린 전멸로 바뀐다.** 감당 못 할 요청이 문 앞에서 걸러지던 것이, 이제 전부 들어와 메모리를 잡고 커넥션을 기다리다 30초를 채우고 죽는다. 그리고 그 30초 동안 정상적으로 처리될 수 있었던 요청들의 응답시간도 함께 무너진다.

대응은 **스레드풀이 암묵적으로 하던 유입 제어를 명시적으로 복원하는 것**이다.

```java
// 커넥션을 쥐는 구간 자체를 세마포어로 제한한다 — 풀 크기에 맞춰 유입을 막는 문지기
private final Semaphore dbGate = new Semaphore(10);

public Order place(Long id) {
    if (!dbGate.tryAcquire(200, TimeUnit.MILLISECONDS)) {
        // 200ms 안에 자리를 못 잡으면 즉시 거절한다.
        // 30초를 기다리다 죽는 것보다, 지금 429/503 을 주는 편이 호출자에게도 낫다.
        throw new TooManyRequestsException();
    }
    try { return orderService.placeInTx(id); }
    finally { dbGate.release(); }
}
```

단 이건 **증상 처리**다. 근본 해결은 트랜잭션 밖으로 외부 API 호출을 빼는 것이고(`22-external-api-call-inside-transaction.md`), **올바른 설계는 가상 스레드가 있든 없든 동일하다.** 가상 스레드는 그 설계 결함을 40배로 증폭시켜 드러낼 뿐이다.

실무에서는 세마포어를 직접 짜기보다 Resilience4j의 Bulkhead·RateLimiter를 쓰고, Hikari `connection-timeout`을 30초에서 1~2초로 낮춰 빠른 실패로 되돌리는 조합이 일반적이다(`26-hikaricp-connection-pool-exhaustion.md` 3-3).

### 3-11. 그래서 WebFlux에 남는 자리

가상 스레드가 나온 뒤 WebFlux의 위치를 정직하게 정리하면 이렇다.

**일반적인 요청/응답 워크로드에서는 근거가 상당 부분 약해졌다.** 홉이 하나뿐이라 2-6의 블로킹 백프레셔로 충분하고, 동시 연결 문제는 가상 스레드가 훨씬 싼 값에 해결해 준다. 남는 자리는 둘이다.

**① 수요 신호를 상류로 전파해야 하는 스트리밍.** SSE, WebSocket, chunked 응답, 메시지 소비처럼 **오래 사는 스트림**이다. 블로킹으로도 자연 백프레셔는 걸리지만, 선택지가 **"막히거나 터지거나" 둘뿐**이라 drop·buffer·sample 같은 중간 전략(2-7)을 표현할 방법이 없다.

```java
// 가상 스레드 + 블로킹 — 생산 10,000/s, 소비(브라우저) 100/s
Thread.ofVirtual().start(() -> {
    for (Event e : eventSource) emitter.send(e);
    // send 가 막히면 이 가상 스레드는 얌전히 멈춘다. 여기까진 백프레셔가 작동한 것이다.
    // 문제는 그 사이 eventSource 뒤에 이벤트가 쌓인다는 것이고,
    // "쌓지 말고 버려라" 나 "100ms 마다 최신값만" 을 표현할 자리가 없다.
});
```

**② 유휴 연결이 극단적으로 많은 경우.** 가상 스레드는 싸지만 공짜는 아니다. 스택이 힙에 상주하므로 연결당 수 KB가 든다. 100만 유휴 연결급에서는 **이벤트 루프 몇 개 + 연결당 작은 상태 객체**가 여전히 메모리로 이긴다. 푸시 알림 게이트웨이, 대규모 SSE 팬아웃이 여기 해당한다.

| | 가상 스레드 | WebFlux |
|---|---|---|
| 수요 신호 전파 | 홉마다 블로킹으로 끊긴다 | `request(n)`이 체인·네트워크를 거슬러 전파 |
| 과부하 시 정책 | 막히거나 OOM | drop / buffer / sample을 선언적으로 선택 |
| 유휴 연결 100만 개 | 가상 스레드 100만 개 (스택이 힙에 상주) | 이벤트 루프 몇 개 + 작은 상태 객체 |
| 코드 스타일 | 명령형 그대로, 스택트레이스 온전 | 리액티브 체인, 디버깅 비용 |

## 4. 꼬리질문 대비 포인트

### "이벤트 루프 스레드가 하나 블로킹되면 정확히 무슨 일이 벌어지나요?"

**그 루프에 배정된 모든 채널(연결)의 이벤트 처리가 멈춘다.**

이유를 구조로 답한다. Netty는 채널 하나를 이벤트 루프 하나에 **고정 배정**하고, 그 배정은 연결이 닫힐 때까지 바뀌지 않는다. 그래서 다른 루프가 대신 처리해 주지 않는다. **"전체의 1/N이 느려진다"가 아니라 "그 루프가 담당하는 연결들의 전면 정지"다.**

숫자를 붙이면 강해진다(3-1). 4코어면 루프가 4개이고, 50ms 블로킹 호출을 감당하는 능력은 4/0.05 = **80 TPS**다. 톰캣 200스레드의 4,000 TPS와 **50배** 차이다. 그 이상이 들어오면 루프 4개가 전부 잠기고 서버가 어떤 요청도 받지 못한다 — 헬스체크까지 포함해서.

### "WebFlux를 쓰면 성능이 좋아지나요?"

**단일 요청의 응답시간은 빨라지지 않는다.** DB 50ms는 어느 모델에서든 50ms다(2-3의 도식). 이걸 먼저 못 박는 것이 중요하다.

좋아지는 것은 **같은 하드웨어로 감당하는 동시 연결 수와 자원 효율**이다. 요청 100개가 각각 50ms를 기다릴 때, MVC는 스레드 100개를 묶어 두고 WebFlux는 4개로 처리한다.

그래서 판단 기준이 나온다. **처리량 병목이 스레드인가.** 대부분의 사내 API는 병목이 DB이거나 외부 API이지 스레드가 아니다. 그런 경우 WebFlux로 바꿔도 **처리량이 그대로이거나 오히려 떨어진다** — 병목은 그대로인데 3-4의 비용만 추가되기 때문이다.

### "MVC를 쓰면서 WebClient만 쓰는 건 어떤가요?"

가능하고 실제로 흔한 절충이다. 외부 API를 **여러 개 병렬로 호출**하는 구간만 논블로킹으로 얻고, 나머지는 서블릿 모델을 유지한다.

```java
// 외부 3곳을 병렬 호출 — 순차면 300ms, 병렬이면 가장 느린 하나(120ms)로 끝난다
Mono<A> a = webClient.get()...retrieve().bodyToMono(A.class);   // 100ms
Mono<B> b = webClient.get()...retrieve().bodyToMono(B.class);   // 120ms
Mono<C> c = webClient.get()...retrieve().bodyToMono(C.class);   //  80ms

// block() 하는 순간 이 톰캣 스레드는 다시 묶인다.
// 다만 "묶인 시간"이 300ms 에서 120ms 로 줄었으므로 Little's law 상 이득은 명확하다.
Result r = Mono.zip(a, b, c).map(this::merge).block();
```

**`block()` 하는 순간 그 스레드는 여전히 묶인다는 것을 인지하고 쓰는지**가 이 답의 변별점이다. 논블로킹의 이득은 "스레드가 안 묶인다"가 아니라 "묶이는 시간이 짧아진다"에서 온다. 클라이언트 3종 비교는 `18-resttemplate-webclient-restclient.md`에 있다.

### "`@Transactional`이 WebFlux에서 동작하나요?"

**동작하지 않는다.** 이유를 구조로 답해야 한다.

Spring의 트랜잭션 동기화는 커넥션을 `TransactionSynchronizationManager`의 **ThreadLocal에 묶어** 같은 스레드의 후속 DB 접근이 그 커넥션을 재사용하게 만드는 구조다(`24-transaction-synchronization-connection-binding.md`). 리액티브 체인은 단계마다 실행 스레드가 바뀔 수 있으므로 **"같은 스레드"라는 연결고리 자체가 성립하지 않는다.**

대안은 **R2DBC + Reactor Context 기반의 리액티브 트랜잭션 관리**다. ThreadLocal 대신 구독마다 따라다니는 Reactor Context에 트랜잭션 자원을 담는다. `@Transactional`을 리액티브 리포지토리와 함께 쓰면 Spring이 `ReactiveTransactionManager`를 통해 처리하지만, **JDBC 리포지토리에 붙인 `@Transactional`은 리액티브 체인 안에서 그냥 안 먹는다.**

같은 이유로 MDC와 `SecurityContextHolder`도 재작업 대상이다(3-4의 표).

### "백프레셔가 MVC엔 정말 없나요?" (시니어 변별 포인트)

**있다.** TCP 수신 윈도, 유한 큐, `CallerRunsPolicy`, 스레드풀 크기, 커넥션 풀 크기 형태의 **암묵적** 백프레셔가 이미 곳곳에서 작동한다(2-6). 백프레셔는 프레임워크 기능이 아니라 **유한한 자원을 다루는 시스템의 일반 원리**다.

없는 것은 둘이다.

- **홉을 건너 전파되는 명시적 수요 신호**(`request(n)`). 블로킹 세계의 백프레셔는 각 홉에서 국소적으로 막힐 뿐 서로를 모른다.
- **drop / buffer / sample 같은 정책 선택지.** 블로킹에서는 "막히거나 터지거나"가 사실상 전부이고, 중간 전략을 쓰려면 큐와 정책 코드를 직접 짜야 한다.

**"없다"가 아니라 "이름이 다르고, 전파 범위와 정책 선택지가 다르다"**로 답하면 이 질문은 통과다.

### "가상 스레드를 켰더니 오히려 장애가 늘었습니다. 왜죠?" (시니어 변별 포인트)

**스레드풀이 암묵적으로 하던 유입 제어가 사라졌기 때문이다**(3-9).

경로를 숫자로 설명한다. 동시 요청 상한이 `max-threads` 200에서 `max-connections` 8,192로 **40배**가 되면서, 예전에는 문 앞에서 거절되던 요청이 전부 진입한다. 그런데 Hikari 커넥션 10개는 그대로다. 8,192개가 10개를 두고 경쟁하다 `connection-timeout` 기본값 30초를 채우고 전면 타임아웃된다.

**빠른 실패가 느린 전멸로 바뀐 것**이고, 이 표현으로 요약하면 좋다.

대응은 두 층이다.

- **즉시 대응**: 세마포어나 Resilience4j Bulkhead로 문지기를 명시적으로 복원하고, `connection-timeout`을 1~2초로 낮춰 빠른 실패를 되살린다.
- **근본 대응**: 트랜잭션 안의 외부 호출을 밖으로 뺀다. **올바른 설계는 가상 스레드가 있든 없든 같고**, 가상 스레드는 그 결함을 40배로 증폭시켜 드러냈을 뿐이다.

마지막 문장이 이 답의 핵심이다. **가상 스레드가 장애를 만든 것이 아니라, 원래 있던 설계 결함의 안전 마진을 걷어낸 것이다.**

### "어떤 기준으로 도입을 판단하시겠어요?"

넷을 전부 통과해야 도입한다는 식으로 답한다.

```
① 동시 연결이 실제로 스레드 한계에 부딪히고 있는가?
     -> tomcat.threads.busy 가 max 에 붙는지 메트릭으로 확인. 근거 없이 시작하지 않는다.

② 전 의존성이 논블로킹으로 갈 수 있는가?
     -> DB 드라이버(R2DBC), HTTP 클라이언트, 로깅, 서드파티 SDK까지 전수 조사.
        하나라도 블로킹이면 4개 스레드 중 하나가 잠긴다 (3-1).

③ 팀이 리액티브 디버깅을 감당하는가?
     -> 끊긴 스택트레이스, ThreadLocal 재작업(MDC/Security/트랜잭션) (3-4).

④ 가상 스레드로 충분하지 않은가?
     -> 스트리밍 백프레셔나 극단적 유휴 연결 요건이 있는가 (3-11).
        없다면 가상 스레드가 같은 이득을 훨씬 싸게 준다.
```

**④를 먼저 묻는 것이 요즘 기준의 시니어다.** 2019년의 정답과 지금의 정답이 다르고, 그 변화의 이유(가상 스레드가 "블로킹 코드 그대로" 동시성을 준다)를 설명할 수 있어야 한다.

### "R2DBC로 바꾸면 다 해결되나요?" (가산점 포인트)

이벤트 루프 블로킹 문제는 해결되지만 **커넥션 풀 문제는 그대로 남는다.**

R2DBC도 커넥션 풀(`ConnectionPool`)을 쓰고, DB 쪽 커넥션은 여전히 물리 자원이다. 3-10의 한 줄 원리가 여기서도 그대로다 — **논블로킹은 기다리는 주체를 싸게 만들 뿐, 기다리는 대상의 개수를 늘리지 않는다.** 커넥션 10개짜리 풀은 R2DBC에서도 10개이고, Little's law 산정은 그대로 필요하다.

그리고 생태계 비용을 짚으면 좋다. R2DBC를 쓰면 **JPA/Hibernate를 쓸 수 없다.** JPA 명세 자체가 블로킹 API로 정의돼 있기 때문이다. 지연 로딩, 영속성 컨텍스트, 더티 체킹 같은 것들을 전부 포기하고 Spring Data R2DBC의 얇은 매핑으로 가야 한다. **"WebFlux 도입"이 실제로는 "데이터 접근 계층 전면 재작성"인 경우가 많다**는 사실이 3-4의 비용 항목에서 가장 크게 물리는 부분이다.

## 한 줄 요약

MVC는 요청당 스레드 하나가 응답까지 묶여 대기를 "스레드 개수"로 흡수하고(상한 = 풀 크기 200), WebFlux는 코어 수만큼의 이벤트 루프가 커널의 `epoll`에 "이 소켓에 데이터가 오면 알려달라"를 등록해 두고 스레드를 반납해 대기를 "이벤트 통지"로 흡수한다(요청 100개 × DB 50ms에서 묶이는 스레드가 100개 대 4개) — 대신 전 구간 논블로킹이 전제라 이벤트 루프 위 블로킹 한 번의 폭발 반경이 질적으로 다르며, 50ms 블로킹 호출 감당량이 톰캣 200스레드는 4,000 TPS인데 이벤트 루프 4개는 80 TPS로 50배 차이라 JDBC 한 줄이 서버를 세운다. 우회로인 `boundedElastic`(코어×10)조차 800 TPS라 MVC보다 5배 좁으니 우회가 주류가 되면 WebFlux를 쓸 이유가 없고, 여기에 리액티브 학습 곡선·끊긴 스택트레이스·ThreadLocal(MDC·Security·`@Transactional`) 전면 재작업 비용이 얹힌다. Java 21 가상 스레드는 코드를 블로킹 스타일로 둔 채 런타임이 대기 시 캐리어를 반납해 같은 이득을 훨씬 싸게 주므로 "동시 연결 때문에 WebFlux"라는 근거를 대부분 무너뜨렸고, 남는 자리는 `request(n)`으로 수요를 상류에 전파해야 하는 스트리밍과 유휴 연결 100만 개급 워크로드뿐이다 — 단 가상 스레드는 스레드풀이 암묵적으로 하던 유입 제어를 없애(200 → `max-connections` 8,192, 40배) 커넥션 풀 앞의 빠른 실패를 느린 전멸로 바꾸므로, 세마포어·Bulkhead와 짧은 `connection-timeout`으로 문지기를 명시 복원해야 한다(물리 자원 산정은 어느 모델에서도 면제되지 않는다).
