# 트랜잭션 전파 REQUIRED vs REQUIRES_NEW — 운명 공동체냐 독립이냐, 그리고 커넥션 2개의 비용

> 핵심 관전 포인트: **REQUIRED(기본값)는 이미 열린 트랜잭션이 있으면
> 거기에 합류한다 — 하나의 물리 트랜잭션을 공유하는 운명 공동체라서
> 어느 한쪽이 실패하면 전체가 롤백된다. REQUIRES_NEW는 기존
> 트랜잭션을 잠시 유보(suspend)하고 새 커넥션으로 완전히 독립된
> 트랜잭션을 연다 — 본 처리가 롤백돼도 감사 로그·실패 이력은 남아야
> 하는 요구사항의 도구다. 단 그 독립성의 비용이 커넥션 2개 동시
> 점유라서, 남용하면 커넥션 풀 고갈과 자기 자신에 의한 데드락을
> 만든다.**

---

## 0. 질문 + 의도

**질문**: "`@Transactional`의 전파(propagation) 옵션 중 `REQUIRED`와
`REQUIRES_NEW`의 차이와 실무 활용 사례는?"

**출제 의도**: "본 처리는 롤백돼도 감사 로그는 남아야 한다" 같은
요구사항을 구현하는 도구를 아는지, 그리고 반대로 REQUIRES_NEW 남용이
커넥션 2개 점유로 데드락과 풀 고갈을 만드는 것까지 아는지 — 도구의
비용을 아는 사람인지 본다.

## 1. 전파란 무엇인가 — "이미 트랜잭션이 있는데 또 시작하라면?"

전파(propagation)는 **트랜잭션 메서드가 트랜잭션 메서드를 호출했을 때
경계를 어떻게 그을지**에 대한 규칙이다. `order()`(@Transactional)가
`saveLog()`(@Transactional)를 부르면, saveLog의 트랜잭션은 새로
여는가, 기존 것에 합류하는가?

이 질문에 답하려면 스프링이 구분하는 두 층을 알아야 한다.

- **물리 트랜잭션**: DB 커넥션 위에서 실제로 BEGIN~COMMIT 되는
  트랜잭션. 커밋/롤백의 실제 단위.
- **논리 트랜잭션**: `@Transactional` 메서드 하나하나에 대응하는
  스프링 관리 단위. 여러 논리 트랜잭션이 하나의 물리 트랜잭션을
  공유할 수 있다.

REQUIRED와 REQUIRES_NEW의 차이는 정확히 "**물리 트랜잭션을 공유하느냐,
새로 만드느냐**"다.

|              | REQUIRED (기본값)        | REQUIRES_NEW              |
|--------------|-----------------------|---------------------------|
| 기존 트랜잭션이 있으면 | 합류 (물리 트랜잭션 공유)       | 기존 것을 유보하고 새로 시작          |
| 기존 트랜잭션이 없으면 | 새로 시작                 | 새로 시작                     |
| DB 커넥션       | 1개 공유                 | **별도 커넥션 추가 획득 (동시 2개)**  |
| 커밋/롤백 운명     | 공동체 — 한쪽 실패 시 전체 롤백   | 독립 — 각자 커밋/롤백             |
| 안쪽 커밋 시점     | 최종적으로 바깥이 커밋할 때 함께    | 안쪽 메서드가 끝나는 즉시            |

## 2. REQUIRED — 합류, 그리고 운명 공동체

기본값이 REQUIRED인 이유는 대부분의 비즈니스 로직이 원하는 것이
"전부 성공하거나 전부 실패하거나"이기 때문이다. 주문 저장과 재고
차감이 서로 다른 서비스 메서드에 있어도, 하나의 물리 트랜잭션에
합류하므로 원자성이 보장된다.

```java
@Service
public class OrderService {

    @Transactional   // 물리 트랜잭션 시작
    public void order(OrderRequest request) {
        orderRepository.save(order);
        stockService.decrease(request.itemId());  // 같은 트랜잭션에 합류
    }
}

@Service
public class StockService {

    @Transactional   // REQUIRED(기본) — 새로 안 열고 합류
    public void decrease(Long itemId) { ... }
}
```

운명 공동체라는 말에는 함정이 하나 딸려 있다 — 합류한 안쪽 논리
트랜잭션에서 예외가 나면 스프링은 공유 중인 물리 트랜잭션에
**rollback-only 마크**를 찍는다. 바깥이 그 예외를 try-catch로 잡고
정상 진행해도 마크는 지워지지 않아서, 최종 커밋 시점에
`UnexpectedRollbackException`이 터진다. "잡았는데 왜 롤백돼?"의
정체가 이것이다. — 상세 시나리오는
[@Transactional 기본 동작 문서](07-transactional-default-behavior-rollback.md) §4.

## 3. REQUIRES_NEW — 유보하고 새로 연다

REQUIRES_NEW는 진행 중이던 트랜잭션을 잠시 **유보(suspend)**하고,
**새 커넥션을 추가로 얻어** 완전히 독립된 물리 트랜잭션을 시작한다.
안쪽 트랜잭션은 메서드가 끝나는 즉시 자기 혼자 커밋/롤백되고, 그 뒤
유보됐던 바깥 트랜잭션이 재개된다.

```
바깥 트랜잭션(커넥션 A) ──── [유보] ················ [재개] ── 커밋/롤백
                              │                        ▲
안쪽 REQUIRES_NEW(커넥션 B)     └─ 시작 ── 작업 ── 커밋 ──┘  ← 이미 확정됨
```

핵심 성질 두 가지:

1. **안쪽이 롤백돼도 바깥은 무사할 수 있다** — rollback-only 마크가
   찍히는 물리 트랜잭션 자체가 다르기 때문. (단, 안쪽 예외를 바깥이
   catch로 막아줘야 한다. 예외가 그대로 전파되면 바깥도 자기 롤백
   규칙에 따라 롤백된다 — 전파를 바꿨다고 예외가 사라지는 게 아니다.)
2. **안쪽이 커밋되면 바깥이 나중에 롤백돼도 못 되돌린다** — 이미
   확정된 독립 트랜잭션이기 때문. 이 비가역성이 활용 사례와 주의점을
   동시에 만든다.

## 4. 실무 활용 사례 — "본 처리가 실패해도 이건 남아야 한다"

대표 사례는 **감사 로그/시도 이력**이다. "주문 처리가 실패하면 주문은
롤백돼야 하지만, 실패했다는 기록 자체는 남아야 한다" — REQUIRED로는
불가능한 요구사항이다. 기록도 같은 물리 트랜잭션이라 본 처리와 함께
증발하기 때문이다.

```java
// before — 실패 이력도 같이 롤백돼서 "실패 기록이 없다"
@Service
public class OrderService {

    @Transactional
    public void order(OrderRequest request) {
        try {
            process(request);
        } catch (Exception e) {
            historyService.saveFailure(request, e);  // ❌ 같은 트랜잭션
            throw e;   // order 롤백 → saveFailure도 함께 롤백. 기록 증발
        }
    }
}

// after — 이력 저장만 독립 트랜잭션으로 분리
@Service
public class HistoryService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveFailure(OrderRequest request, Exception e) {
        // ✅ 별도 커넥션·별도 트랜잭션 — 바깥이 롤백돼도 이 기록은 커밋됨
        historyRepository.save(FailureHistory.of(request, e));
    }
}
```

같은 패턴이 쓰이는 곳: 외부 연동 시도/응답 로그(결제 게이트웨이 호출
기록), 배치의 건별 처리 결과 기록(한 건 실패가 전체 롤백로 번지지
않게), 알림 발송 이력. 공통점은 **"본 처리와 운명을 같이하면 안 되는,
남아도 무해하거나 남아야만 하는 데이터"**라는 것이다.

주의 — 두 가지 함정이 세트로 따라온다.

- **자기 호출이면 무효**: REQUIRES_NEW도 프록시가 적용하는 속성이므로,
  같은 클래스 안에서 `this.saveFailure()`로 부르면 전파 옵션이 통째로
  무시된다. 위 예시에서 HistoryService를 별도 빈으로 둔 이유다. —
  [자기 호출 문서](11-transactional-self-invocation.md) 참고.
- **반대 방향도 확인**: 이력은 남기되 이력 저장 실패가 본 처리를
  죽이면 안 된다면, 바깥에서 saveFailure 호출을 try-catch로 감싸야
  한다. "안쪽 독립"과 "예외 전파 차단"은 별개의 일이다.

## 5. REQUIRES_NEW의 비용 — 커넥션 2개 점유와 풀 데드락

REQUIRES_NEW의 독립성은 공짜가 아니다. 유보된 바깥 트랜잭션의
커넥션은 **반납되지 않고 그대로 물려 있는 채로**, 안쪽 트랜잭션이 새
커넥션을 추가로 요구한다. 즉 **스레드 하나가 커넥션 2개를 동시에
점유**한다.

이게 만드는 최악의 시나리오가 **커넥션 풀 자기 데드락**이다.
HikariCP 풀 크기가 10이고 동시 요청 10개가 각각 REQUIRES_NEW 경로를
탄다고 하자.

1. 스레드 10개가 각자 바깥 트랜잭션용 커넥션을 하나씩 잡는다 → 풀 소진
2. 10개 모두 REQUIRES_NEW 지점에 도달해 두 번째 커넥션을 기다린다
3. 그런데 커넥션을 반납할 주체가 자기들뿐이다 — **전원이 서로가 쥔
   커넥션을 기다리는 교착** → connection timeout까지 전체 멈춤

락 경합 없이, 쿼리 한 줄 문제없이, 순전히 전파 옵션만으로 서비스가
멈출 수 있다는 것이다. 그래서 실무 기준은:

- REQUIRES_NEW는 **위 사례처럼 명확한 요구사항이 있을 때만**, 짧은
  작업(이력 insert 한 건 수준)에 한정해서 쓴다.
- 트래픽이 몰리는 핵심 경로에 REQUIRES_NEW가 있다면 풀 크기 산정에
  "스레드당 커넥션 2개"를 반영해야 한다.
- "실패해도 남길 기록"이 본 트랜잭션과 굳이 동기일 필요가 없다면,
  트랜잭션 밖으로 빼는 대안이 더 안전한 경우가 많다 —
  `@TransactionalEventListener(phase = AFTER_ROLLBACK)` 같은 커밋/롤백
  후처리, 또는 큐로 넘겨 별도 소비자가 기록. (가산점 포인트: 도구를
  아는 것보다 "안 쓰고 풀 수 있는 길"을 먼저 검토하는 태도가
  시니어의 신호다.)

## 6. 꼬리질문 대비 포인트

### "REQUIRES_NEW 안에서 예외가 났고 바깥이 catch하지 않았다. 바깥 트랜잭션은?"

바깥도 롤백된다. REQUIRES_NEW의 독립성은 "안쪽 롤백이 바깥 물리
트랜잭션에 rollback-only를 찍지 않는다"는 뜻이지, 예외 객체가 콜
스택을 타고 올라가는 것까지 막아주지 않는다. 바깥으로 전파된
RuntimeException은 바깥 트랜잭션의 롤백 규칙에 그대로 걸린다.
"독립시키고 싶으면 catch까지가 한 세트"라고 답하면 정확하다.

### "바깥이 롤백되면 REQUIRES_NEW로 이미 커밋된 데이터는 어떻게 되나?" (시니어 변별 포인트)

되돌릴 수 없다. 이미 독립적으로 커밋이 확정됐기 때문이다. 그래서
REQUIRES_NEW에 넣을 데이터는 "본 처리가 롤백된 세상에서도 존재해도
되는(또는 존재해야 하는) 데이터"인지로 판별해야 한다. 감사 로그·시도
이력은 적합하고, 본 처리와 정합성이 묶인 데이터(재고, 잔액)를
REQUIRES_NEW로 빼는 것은 부분 커밋을 설계로 박아 넣는 실수다.
비가역 커밋이라는 성질에서 사용 기준을 도출해 답하는 것이 포인트.

### "REQUIRES_NEW가 커넥션 풀을 고갈시키는 시나리오를 구체적으로 설명해보라" (시니어 변별 포인트)

유보된 바깥 트랜잭션이 커넥션을 쥔 채로 안쪽이 새 커넥션을 요구하므로
스레드당 2개 점유. 풀 크기만큼의 동시 요청이 전부 REQUIRES_NEW
지점에 도달하면, 모두가 첫 커넥션을 쥔 채 두 번째를 기다리는데 반납할
주체가 자기들뿐이라 교착된다(§5). 해결은 풀 크기에 스레드당 커넥션
수를 반영하거나, REQUIRES_NEW를 핵심 경로에서 제거하는 것.

### "NESTED와 REQUIRES_NEW의 차이는?"

NESTED는 새 물리 트랜잭션이 아니라 **같은 트랜잭션 안에
세이브포인트(savepoint)**를 찍는 방식이다. 안쪽 실패 시 세이브포인트까지만
부분 롤백하고 바깥은 계속 갈 수 있지만, 물리 트랜잭션이 하나이므로
바깥이 롤백되면 안쪽도 함께 사라진다(REQUIRES_NEW와의 결정적 차이).
커넥션도 1개라 풀 비용이 없다. 단 JDBC 세이브포인트 기반이라 지원
범위가 제한적이고, JPA(Hibernate)에서는 사실상 쓰지 못한다 — 그래서
JPA 실무에서 "독립 커밋"이 필요하면 선택지가 REQUIRES_NEW로 좁혀진다.

### "같은 클래스 안의 메서드에 REQUIRES_NEW를 붙여 호출하면?"

자기 호출이면 프록시를 거치지 않으므로 전파 옵션이 통째로 무시되고,
그냥 바깥 트랜잭션 안에서 실행된다. "독립 트랜잭션으로 분리했다고
믿었는데 실제로는 운명 공동체"라는, 이 주제와 자기 호출 함정이
교차하는 지점이다. 별도 빈 분리가 답이다. —
[자기 호출 문서](11-transactional-self-invocation.md) 참고.

## 한 줄 요약

REQUIRED는 하나의 물리 트랜잭션에 합류하는 운명 공동체, REQUIRES_NEW는
기존 것을 유보하고 새 커넥션으로 여는 독립 트랜잭션이라 "본 처리가
롤백돼도 남아야 할 기록"에 쓰는 도구다 — 단 스레드당 커넥션 2개
점유라는 비용이 풀 고갈·자기 데드락으로 이어질 수 있으므로, 짧고
명확한 요구사항에만 제한적으로 쓰고 가능하면 커밋 후 이벤트 같은
트랜잭션 밖 대안을 먼저 검토한다.
