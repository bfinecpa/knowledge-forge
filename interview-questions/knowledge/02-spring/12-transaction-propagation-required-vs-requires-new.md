# 트랜잭션 전파 REQUIRED vs REQUIRES_NEW — 바깥 트랜잭션을 물려받을 것인가, 새로 열 것인가

> 핵심 관전 포인트: **전파는 트랜잭션 경계를 가진 메서드가 또 다른 트랜잭션 메서드를 호출했을 때 "바깥에 이미 열려 있는 트랜잭션을 물려받을 것인가"를 정하는 규칙이다. REQUIRED(기본값)는 물려받는다 — 새 BEGIN이 아예 나가지 않고 같은 커넥션·같은 물리 트랜잭션을 그대로 쓰며, 안쪽 메서드가 정상 종료할 때의 "커밋"은 실제 COMMIT이 아니라 아무 일도 하지 않는 것이다. 그래서 둘은 한 몸이 되고, 그 운명 공동체의 실체는 안쪽 실패가 공유 트랜잭션에 찍는 rollback-only 플래그다. REQUIRES_NEW는 물려받지 않는다 — 바깥을 유보(suspend)하고 커넥션을 하나 더 얻어 독립된 물리 트랜잭션을 열기 때문에 본 처리가 롤백돼도 이력은 남지만, 대가로 스레드 하나가 커넥션 2개를 동시에 점유한다. 풀 크기 10에 이 경로를 타는 요청 10개가 동시에 들어오면 전원이 첫 커넥션을 쥔 채 두 번째를 기다려 connectionTimeout까지 API 전체가 멈춘다. 교착을 원천 차단하는 풀 크기는 `스레드 수 x (스레드당 최대 커넥션 - 1) + 1`인데 톰캣 기본 스레드 200을 대입하면 201이라는 비현실적인 수가 나온다 — 그래서 답은 풀을 키우는 것이 아니라 스레드당 커넥션 수를 1로 되돌리는 것이다.**

---

## 0. 질문 + 의도

**질문**: "`@Transactional`의 전파(propagation) 옵션 중 `REQUIRED`와 `REQUIRES_NEW`의 차이와 실무 활용 사례는?"

**출제 의도**: "본 처리는 롤백돼도 감사 로그는 남아야 한다" 같은 요구사항을 구현하는 도구를 아는지, 그리고 반대로 REQUIRES_NEW 남용이 커넥션 2개 점유로 데드락과 풀 고갈을 만드는 것까지 아는지 — 도구의 비용을 아는 사람인지 본다.

## 1. 전파란 무엇인가 — 무엇이 무엇에게 "전파"되는가

### 1-1. 이름부터 풀기

전파(propagation)는 "퍼져 나감"이라는 뜻이다. 그런데 무엇이 무엇에게 퍼져 나간다는 걸까. 답은 **트랜잭션 경계가 호출 체인을 따라 안쪽으로 퍼져 나간다**는 것이다.

상황을 구체적으로 그려 보자. `order()`에 `@Transactional`이 붙어 있어서 이 메서드가 시작될 때 트랜잭션이 하나 열린다. 그런데 `order()`가 호출하는 `decrease()`에도 `@Transactional`이 붙어 있다. 이 순간 스프링은 반드시 하나를 결정해야 한다. **"바깥에서 이미 열려 있는 그 트랜잭션을 `decrease()`도 그대로 물려받을 것인가, 아니면 `decrease()` 몫의 트랜잭션을 따로 열 것인가."**

전파 옵션은 정확히 이 질문 하나에 대한 답이다. 그래서 정의는 이렇게 한 문장으로 세울 수 있다. **전파란 트랜잭션 경계를 가진 메서드가 다른 트랜잭션 메서드를 호출했을 때, 바깥의 트랜잭션을 안쪽이 어떻게 물려받을지 정하는 규칙이다.**

주의할 것이 하나 있다. 전파는 **호출된 쪽(안쪽)의 어노테이션**이 결정한다. `decrease()`에 붙은 `propagation` 값이 "나는 바깥 것을 물려받겠다 / 안 받겠다"를 말하는 것이지, 부르는 쪽이 강요하는 게 아니다.

### 1-2. 전제 지식 — 트랜잭션은 커넥션 위에 열린다

전파를 이해하려면 트랜잭션이 어디에 존재하는지를 먼저 짚어야 한다. **트랜잭션은 자바 객체가 아니라 DB 커넥션 위에서 열리고 닫히는 상태**다. JDBC로 쓰면 이런 모양이다.

```java
Connection con = dataSource.getConnection();  // 풀에서 커넥션 한 개를 빌린다 — 여기부터 점유 구간
con.setAutoCommit(false);                     // 이 순간부터가 트랜잭션 안이다 (사실상의 BEGIN)
// ... 여러 SQL ...
con.commit();                                 // 또는 con.rollback()
con.close();                                  // 풀에 반납 — 여기서 점유 구간이 끝난다
```

여기서 놓치면 안 되는 사실이 둘이다. 첫째, **트랜잭션 하나는 커넥션 하나에 묶인다.** 커넥션 A에서 시작한 트랜잭션을 커넥션 B에서 커밋할 방법은 없다. 둘째, **커넥션은 트랜잭션이 끝날 때까지 풀에 반납되지 않는다.** 트랜잭션이 길면 커넥션 점유도 그만큼 길다.

스프링은 이 커넥션을 `TransactionSynchronizationManager`라는 창고의 ThreadLocal에 담아 둔다. 같은 스레드에서 도는 리포지토리 코드는 이 창고를 뒤져 "지금 진행 중인 트랜잭션의 커넥션"을 찾아 쓴다. 그래서 서로 다른 클래스의 메서드들이 자연스럽게 같은 트랜잭션에 참여한다. (자세한 경로는 [트랜잭션 동기화 문서](24-transaction-synchronization-connection-binding.md) 참고.)

이 사실 두 개가 뒤에서 계속 쓰인다. **"같은 트랜잭션에 합류한다 = 같은 커넥션을 쓴다"**이고, **"독립 트랜잭션을 연다 = 커넥션을 하나 더 빌린다"**이기 때문이다.

### 1-3. 물리 트랜잭션과 논리 트랜잭션

스프링 문서를 읽다 보면 물리/논리라는 말이 나오는데, 이것도 위 사실에서 그대로 따라 나온다.

- **물리 트랜잭션**: 커넥션 위에서 실제로 BEGIN부터 COMMIT/ROLLBACK까지 진행되는 진짜 트랜잭션. DB가 인식하는 단위이고, 커밋과 롤백의 실제 단위다.
- **논리 트랜잭션**: `@Transactional`이 붙은 메서드 하나하나에 대응하는 스프링의 관리 단위. 스프링이 "이 메서드가 트랜잭션 경계다"라고 세어 두는 회계 장부에 가깝다.

**논리 트랜잭션 여러 개가 물리 트랜잭션 하나를 공유할 수 있다**는 것이 핵심이다. `order()`와 `decrease()`는 논리적으로는 둘이지만 물리적으로는 하나일 수 있다.

REQUIRED와 REQUIRES_NEW의 차이는 결국 **물리 트랜잭션을 공유하느냐, 새로 만드느냐** 한 줄로 압축된다.

| | REQUIRED (기본값) | REQUIRES_NEW |
|---|---|---|
| 바깥 트랜잭션이 있으면 | 물려받아 합류 (물리 트랜잭션 공유) | 바깥을 유보하고 새로 시작 |
| 바깥 트랜잭션이 없으면 | 새로 시작 | 새로 시작 |
| DB 커넥션 | 1개를 공유 | **별도 커넥션을 추가로 획득 (동시 2개)** |
| 안쪽 메서드가 정상 종료할 때 | COMMIT을 보내지 않는다 (아무 일도 안 함) | 즉시 실제 COMMIT |
| 커밋/롤백 운명 | 공동체 — 한쪽 실패 시 전체 롤백 | 독립 — 각자 커밋/롤백 |

## 2. REQUIRED — "합류"의 물리적 의미

### 2-1. 합류란 새 BEGIN이 나가지 않는다는 뜻이다

기본값이 REQUIRED인 이유는 대부분의 비즈니스 로직이 원하는 것이 "전부 성공하거나 전부 실패하거나"이기 때문이다. 주문 저장과 재고 차감이 서로 다른 서비스 메서드에 흩어져 있어도 하나의 물리 트랜잭션으로 묶여 원자성이 지켜진다.

문제는 "합류"라는 단어가 마치 두 트랜잭션이 손을 잡는 그림처럼 들린다는 것이다. 실제로 일어나는 일은 훨씬 밋밋하다. **안쪽에서는 아무 트랜잭션도 시작되지 않는다.** 스프링은 창고를 뒤져 "이미 진행 중인 트랜잭션이 있네"를 확인하고, 그냥 그것을 계속 쓴다. 커넥션 관점으로 그리면 이렇다.

```text
[스레드 1개 · 커넥션 A 1개]

order()  @Transactional                       <- 여기서 트랜잭션의 "주인"이 정해진다
  │  풀에서 커넥션 A 획득 + setAutoCommit(false)   (실제 BEGIN)
  │
  ├─ INSERT order                              (커넥션 A)
  │
  ├─ decrease()  @Transactional(REQUIRED)      <- 새 BEGIN 없음. 커넥션도 안 빌린다.
  │    │  UPDATE stock                          (커넥션 A — 같은 커넥션)
  │    └─ 정상 종료 = "커밋"                     <- COMMIT을 보내지 않는다. 아무 일도 안 함.
  │
  └─ COMMIT (커넥션 A)                          <- 여기서 딱 한 번 실제 COMMIT이 나간다
     커넥션 A 반납
```

```java
@Service
public class OrderService {

    @Transactional   // 진행 중인 트랜잭션이 없으므로 여기가 물리 트랜잭션의 시작점
    public void order(OrderRequest request) {
        orderRepository.save(order);
        stockService.decrease(request.itemId());
    }
}

@Service
public class StockService {

    @Transactional   // REQUIRED(기본값) — order()의 트랜잭션을 물려받는다.
    public void decrease(Long itemId) {
        // 이 메서드가 리턴해도 DB에는 COMMIT이 나가지 않는다.
        // 커밋 권한은 트랜잭션을 시작한 order() 쪽에만 있다.
    }
}
```

### 2-2. 안쪽의 "커밋"은 실제 커밋이 아니다

여기가 주니어가 가장 자주 오해하는 지점이다. `decrease()`에도 `@Transactional`이 붙어 있으니 "이 메서드가 끝나면 여기까지는 커밋되겠지"라고 읽기 쉽다. 아니다.

스프링은 트랜잭션을 시작한 쪽과 합류한 쪽을 구분해 기억한다. 그리고 커밋 처리 시점에 이렇게 갈린다.

```text
안쪽(합류한) 논리 트랜잭션이 정상 종료
      │
      ├─ 내가 이 트랜잭션을 시작한 주인인가?
      │        아니오 (합류한 참여자)
      │           └─> 아무 일도 하지 않고 그냥 리턴한다.
      │               COMMIT 호출 없음. 커넥션 반납도 없음.
      │
바깥(시작한) 논리 트랜잭션이 정상 종료
      │
      └─ 내가 주인인가? 예
             └─> rollback-only 플래그를 확인하고
                 실제 COMMIT을 커넥션에 내려보낸 뒤 커넥션을 반납한다.
```

그래서 "안쪽 메서드가 끝나면 그때까지의 변경이 확정된다"는 기대는 REQUIRED에서 성립하지 않는다. **커밋은 오직 트랜잭션을 시작한 가장 바깥에서 한 번 일어난다.** 이 성질을 바꾸고 싶을 때 꺼내는 도구가 3절의 REQUIRES_NEW다.

### 2-3. 운명 공동체의 실체 — rollback-only 플래그

물리 트랜잭션이 하나이므로 한쪽이 롤백되면 다른 쪽도 롤백된다. 여기까지는 당연하다. 그런데 이 "운명 공동체"에는 눈에 잘 안 보이는 장치가 하나 딸려 있다.

합류한 안쪽에서 예외가 났다고 하자. 안쪽은 트랜잭션의 주인이 아니라서 직접 롤백할 수 없다 — 롤백해 버리면 바깥이 지금까지 한 작업까지 함께 날아가는데, 그럴 권한이 없기 때문이다. 그래서 스프링은 대신 **공유 중인 트랜잭션에 "이건 커밋하면 안 됨"이라는 표식을 찍는다.** 이것이 **rollback-only 플래그**다.

```text
t0  order()   BEGIN (커넥션 A)
t1  order()   INSERT order
t2  decrease() 진입 (합류)
t3  decrease() RuntimeException 발생
t4  decrease()의 프록시: 나는 주인이 아니다 -> 롤백 대신 rollback-only 마크만 찍는다
t5  order()   try-catch로 예외를 잡고 대체 로직 수행 후 정상 리턴
t6  order()의 프록시: 커밋하려고 보니 rollback-only 마크가 찍혀 있다
                     -> 전체 ROLLBACK + UnexpectedRollbackException 던짐
```

**예외는 잡을 수 있어도 이미 찍힌 마크는 잡을 수 없다.** "분명 try-catch로 잡았는데 왜 전부 롤백되지?"라는 고전적 함정의 정체가 이것이고, 운명 공동체라는 비유의 실물이 바로 이 플래그다. 시나리오 전문과 해법 비교는 [@Transactional 기본 동작 문서](07-transactional-default-behavior-rollback.md) 4절에 있다.

이 플래그를 이해하면 REQUIRES_NEW가 왜 필요한지도 저절로 따라온다. **rollback-only 플래그는 물리 트랜잭션에 붙는다.** 물리 트랜잭션이 다르면 마크도 따로 논다 — 그것이 다음 절의 출발점이다.

## 3. REQUIRES_NEW — 독립의 값과 그 청구서

### 3-1. 유보(suspend)하고 커넥션을 하나 더 빌린다

REQUIRES_NEW는 진행 중이던 트랜잭션을 잠시 **유보(suspend)**한다. 유보란 "지금 창고에 올려둔 트랜잭션 정보를 통째로 꺼내 옆에 치워 두고, 창고를 빈 상태로 만드는 것"이다. 창고가 비었으니 스프링은 "진행 중인 트랜잭션이 없다"고 판단하고, **풀에서 커넥션을 하나 더 빌려** 완전히 새 물리 트랜잭션을 연다.

중요한 것은 **유보가 반납이 아니라는 점**이다. 치워 둔 바깥 트랜잭션의 커넥션은 여전히 이 스레드가 쥐고 있다. 나중에 재개해서 커밋해야 하니 놓을 수가 없다.

```text
[스레드 1개 · 커넥션 2개를 동시에 점유]

order()  @Transactional
  │  커넥션 A 획득, BEGIN
  │  INSERT order                                   (커넥션 A)
  │
  │  ┌── saveFailure()  @Transactional(REQUIRES_NEW)
  │  │     바깥 트랜잭션 유보 (커넥션 A는 반납하지 않고 옆에 치워 둠)
  │  │     커넥션 B 획득, BEGIN                       <- 풀에서 하나 더 꺼낸다
  │  │     INSERT history                            (커넥션 B)
  │  │     COMMIT (커넥션 B)                          <- 여기서 진짜로 확정. 되돌릴 수 없다.
  │  │     커넥션 B 반납
  │  └── 바깥 트랜잭션 재개 (커넥션 A를 창고에 되돌려 놓음)
  │
  │   ※ 위 구간 내내 커넥션 A는 아무것도 안 하면서 붙잡혀 있었다
  │
  └─ ROLLBACK (커넥션 A) ── 주문은 사라지지만 history 한 줄은 남는다
     커넥션 A 반납
```

### 3-2. 독립이 만드는 두 가지 성질

**성질 하나. 안쪽이 롤백돼도 바깥은 무사할 수 있다.** 2-3에서 본 rollback-only 플래그가 찍히는 대상이 서로 다른 물리 트랜잭션이기 때문이다.

단, 여기에 조건이 붙는다. **바깥이 그 예외를 try-catch로 막아 줘야 한다.** 전파 옵션을 바꿨다고 예외 객체가 사라지는 게 아니다. 예외는 그대로 콜 스택을 타고 바깥으로 올라가고, 바깥은 자기 롤백 규칙(런타임 예외면 롤백)에 따라 자기 트랜잭션을 롤백한다. **"안쪽을 독립시키기"와 "예외 전파를 끊기"는 서로 다른 일이고, 둘 다 해야 의도한 그림이 된다.**

**성질 둘. 안쪽이 커밋되면 바깥이 나중에 롤백돼도 되돌릴 수 없다.** 이미 DB에 COMMIT이 나갔기 때문이다. 이 비가역성이 REQUIRES_NEW의 존재 이유이자 위험의 근원이다.

그래서 REQUIRES_NEW에 넣을 데이터인지 판별하는 기준은 하나로 정리된다. **"본 처리가 롤백된 세상에 이 데이터만 남아 있어도 괜찮은가, 혹은 남아 있어야 하는가?"** 감사 로그와 시도 이력은 남아야 하니 적합하고, 재고·잔액처럼 본 처리와 정합성이 묶인 데이터는 남으면 안 되니 부적합하다.

### 3-3. 실무 활용 사례 — "본 처리가 실패해도 이건 남아야 한다"

대표 사례는 **실패 이력·감사 로그**다. "주문 처리가 실패하면 주문은 롤백돼야 하지만, 실패했다는 기록 자체는 남아야 한다"는 요구는 REQUIRED로는 원천적으로 불가능하다. 기록도 같은 물리 트랜잭션에 실려 있어 본 처리와 함께 증발하기 때문이다.

```java
// before: 실패 이력까지 함께 롤백돼서 "왜 실패했는지가 어디에도 없다"
@Service
public class OrderService {

    @Transactional
    public void order(OrderRequest request) {
        try {
            process(request);
        } catch (Exception e) {
            // 문제: 이 save도 order()와 같은 물리 트랜잭션에 실린다.
            historyService.saveFailure(request, e);
            throw e;   // order()가 롤백되면서 방금 남긴 실패 기록도 같이 롤백된다
        }
    }
}
```

```java
// after: 이력 저장만 독립 물리 트랜잭션으로 떼어낸다
@Service
public class HistoryService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveFailure(OrderRequest request, Exception e) {
        // 커넥션 B에서 열린 별도 트랜잭션이라, 이 메서드가 끝나는 순간 COMMIT이 나간다.
        // 바깥 order()가 그 뒤에 롤백돼도 이 한 줄은 남는다.
        historyRepository.save(FailureHistory.of(request, e));
    }
}
```

같은 패턴이 쓰이는 자리는 셋 정도다. 외부 연동의 시도/응답 기록(결제 게이트웨이 호출 로그), 배치의 건별 처리 결과 기록(한 건 실패가 전체 롤백으로 번지지 않게), 알림 발송 이력. 공통점은 **본 처리와 운명을 같이하면 안 되는, 남아도 무해하거나 남아야만 하는 데이터**라는 것이다.

함정 두 개가 세트로 따라온다.

**자기 호출이면 통째로 무효다.** REQUIRES_NEW도 프록시가 적용하는 속성이라, 같은 클래스 안에서 `this.saveFailure()`로 부르면 프록시를 거치지 않아 전파 옵션이 없는 것과 똑같이 동작한다. 위 예시에서 `HistoryService`를 굳이 별도 빈으로 둔 이유가 이것이다. 자세한 내용은 [자기 호출 문서](11-transactional-self-invocation.md) 참고.

**반대 방향도 막아야 한다.** 이력은 남기되 이력 저장 실패가 본 처리를 죽이면 안 된다면, 호출부에서 `saveFailure()`를 try-catch로 감싸야 한다. 3-2에서 말한 대로 독립성과 예외 차단은 별개다.

### 3-4. 그럼에도 REQUIRES_NEW가 답이 아닌 경우

"본 처리가 실패해도 남아야 한다"는 요구가 나왔다고 해서 반사적으로 REQUIRES_NEW를 꺼내면 안 된다. 남길 대상이 무엇이냐에 따라 더 나은 도구가 있다.

**남길 것이 외부 시스템 호출이나 메시지 발행이라면 아웃박스가 낫다.** 예를 들어 "주문이 커밋되면 Kafka로 이벤트를 쏜다"를 REQUIRES_NEW로 풀려는 시도가 있는데, 이건 애초에 문제 정의가 틀렸다. DB 쓰기와 브로커 발행은 서로 다른 시스템이라 어떤 전파 옵션으로도 한 트랜잭션에 묶이지 않는다(이중 쓰기 문제). 답은 보낼 메시지를 **같은 DB의 outbox 테이블에 INSERT해 본 트랜잭션과 한 몸으로 커밋**하고, 별도 릴레이가 그것을 읽어 발행하는 것이다. [Transactional Outbox 문서](23-transactional-outbox-pattern.md)를 그대로 따르면 된다.

**본 트랜잭션과 동기일 필요가 없다면 트랜잭션 밖으로 빼는 것이 더 안전하다.** 스프링은 커밋/롤백이 끝난 뒤에 실행되는 이벤트 리스너를 제공한다.

```java
@TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
// AFTER_ROLLBACK 시점에는 원래 트랜잭션이 이미 끝나 있다.
// 그래서 여기서 DB에 쓰려면 리스너 자신이 새 트랜잭션을 열어야 한다.
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void onOrderFailed(OrderFailedEvent event) {
    historyRepository.save(FailureHistory.of(event));
}
```

이 방식의 이점은 커넥션 2개를 **동시에** 쥐는 구간이 없다는 것이다. 바깥 트랜잭션이 완전히 끝나 커넥션을 반납한 뒤에 새 커넥션을 빌리므로, 3-5의 교착이 구조적으로 생기지 않는다. 자세한 사용법은 [스프링 이벤트 문서](16-spring-event-transactional-event-listener.md) 참고.

**외부 API 호출을 REQUIRES_NEW로 감싸는 것은 최악이다.** 트랜잭션 안에서 외부 API를 부르면 안 되는 이유는 응답 대기 시간 내내 커넥션을 붙잡기 때문인데, REQUIRES_NEW로 감싸면 그 대기 시간 동안 커넥션을 **2개** 붙잡는다. 문제를 두 배로 키운 셈이다. ([트랜잭션 안 외부 호출 문서](22-external-api-call-inside-transaction.md) 참고.)

### 3-5. 비용을 숫자로 — 커넥션 2개 점유와 풀 자기 데드락

REQUIRES_NEW의 독립성은 공짜가 아니다. 3-1의 도식이 보여주듯 **스레드 하나가 커넥션 2개를 동시에 점유**한다. 이것이 만드는 최악의 시나리오가 **커넥션 풀 자기 데드락**이다. 다른 서비스도, 락 경합도, 느린 쿼리도 없이, 순전히 자기들끼리 물려서 멈추는 교착이다.

HikariCP 풀 크기가 10이고, 동시 요청 10개가 각각 REQUIRES_NEW 경로를 탄다고 하자. 단계별로 세어 보면 이렇게 된다.

```text
maximumPoolSize = 10 · 동시 요청 10개 · 각 요청이 REQUIRES_NEW 경로

t0  스레드 #1~#10 이 각자 바깥 트랜잭션용 커넥션을 1개씩 획득
    사용 중 10 / 유휴 0                    <- 이 시점에 풀은 이미 바닥났다

t1  10개 스레드가 전부 REQUIRES_NEW 지점에 도달
    각자 두 번째 커넥션을 요청 -> 대기자 10명, 반납 예정 0개

t2  누가 반납해야 이 대기가 풀리는가?
      바깥 커넥션은 바깥 트랜잭션이 끝나야 반납된다
      바깥 트랜잭션은 안쪽 REQUIRES_NEW가 끝나야 끝난다
      안쪽은 커넥션을 못 받아 시작조차 못 한다
    -> 반납할 수 있는 주체가 이 세상에 없다

t3  connectionTimeout(HikariCP 기본 30초) 경과
    10개 스레드 전부 SQLTransientConnectionException
    그동안 이 API는 완전히 멈춰 있었다
```

여기서 정확히 짚을 것이 하나 있다. 이 교착은 **영원히 지속되지는 않는다.** HikariCP는 `connectionTimeout`(기본값 30,000ms)만큼 기다린 뒤 예외를 던지고 포기한다. 즉 30초 동안 전원이 멈춰 있다가 한꺼번에 실패하고, 실패한 스레드들이 커넥션을 반납하면서 다시 풀린다. 트래픽이 계속 들어오면 이 사이클이 반복되므로 실제로는 "간헐적으로 30초씩 멈추는 API"로 관측된다 — 원인을 짐작하기 가장 어려운 형태의 장애다.

### 3-6. 그래서 풀 크기는 최소 얼마여야 하는가

교착을 **원천적으로** 불가능하게 만들려면 어떤 조건이 필요한지 계산해 보자. 조건은 하나다. **어떤 순간에도 적어도 한 스레드는 필요한 커넥션을 전부 모을 수 있어야 한다.** 그 한 명이 완주하고 반납하면 다음 사람이 완주하고, 연쇄적으로 전부 풀린다.

```text
  Tn = 동시에 이 경로를 탈 수 있는 스레드 수
  Cm = 스레드 하나가 동시에 쥐어야 하는 최대 커넥션 수

  최악의 배분: 모든 스레드에 (Cm - 1)개씩 나눠준 상태
               -> 전원이 1개씩 모자라 아무도 완주하지 못한다 = 교착
               -> 이때 쥐여 있는 커넥션 수 = Tn x (Cm - 1)

  여기에 딱 1개만 더 있으면 한 명이 완주 -> 반납 -> 연쇄 해소

  필요한 풀 크기 = Tn x (Cm - 1) + 1
```

이 문서의 사례를 대입하면 `Tn = 10`, `Cm = 2`이므로 `10 x (2 - 1) + 1 = 11`이다. 풀이 10일 때 교착이었던 것이 **11이면 교착이 아니다.** 딱 하나 차이다.

문제는 실제 서버에 대입할 때 드러난다. 톰캣의 기본 `max-threads`는 200이고, 그 스레드 전부가 이 경로를 탈 수 있다면 `Tn = 200`이다.

```text
Tn = 200, Cm = 2  ->  200 x (2 - 1) + 1 = 201개
```

**커넥션 201개짜리 풀은 현실적이지 않다.** DB 쪽 `max_connections`도 문제지만, 애초에 커넥션 풀은 작을수록 좋다는 것이 정설이다(컨텍스트 스위칭과 디스크 경합 때문에 커넥션을 늘려도 처리량은 어느 지점부터 오히려 떨어진다). 그래서 **풀 크기를 키워서 이 식을 만족시키겠다는 접근 자체가 틀렸다.** 식이 알려주는 진짜 결론은 이것이다.

**해법은 `Cm`을 1로 되돌리는 것이다.** 스레드 하나가 커넥션을 하나만 쥐게 만들면 `Tn x 0 + 1 = 1`이 되어 교착 조건이 소멸한다. 3-4의 대안들 — 아웃박스, 커밋/롤백 후 이벤트, 큐 위임 — 이 전부 이 방향의 처방이다.

여기서 흥미로운 대비가 하나 나온다. **처리량 관점에서 REQUIRES_NEW의 추가 비용은 사실 거의 없다.** 풀 크기 산정의 기본식(Little's law: 동시 점유 수 = TPS × 점유 시간, [풀 크기 산정 문서](25-thread-pool-connection-pool-sizing.md) 참고)으로 계산해 보면 그렇다.

```text
목표 500 TPS, 요청당 커넥션 점유 50ms
  기본 필요 커넥션 = 500 x 0.05s = 25개

그중 10%가 REQUIRES_NEW 경로이고 안쪽 INSERT가 5ms 걸린다면
  추가로 필요한 동시 커넥션 = (500 x 0.1) x 0.005s = 0.25개

평균적으로는 커넥션 0.25개어치만 더 있으면 된다.
```

평균 0.25개. 그런데 이 경로가 서비스를 30초씩 멈춰 세운다. **왜냐하면 교착은 평균이 아니라 동시 도착의 꼬리에서 터지기 때문이다.** 평상시 지표로는 아무 문제가 없어 보이다가, 트래픽이 몰려 그 경로를 탄 요청이 풀 크기만큼 겹치는 순간 한 번에 터진다. "평소에 멀쩡하니 괜찮다"가 근거가 될 수 없는 종류의 위험이고, 이 구분을 말할 수 있는지가 변별점이다.

한 가지 완화 요인은 짚어 둘 만하다. Spring Boot 3.x의 기본 구성에서 하이버네이트는 커넥션을 **트랜잭션 시작 시점이 아니라 첫 쿼리 시점에** 가져와 트랜잭션이 끝날 때까지 쥔다(`hibernate.connection.handling_mode`가 `DELAYED_ACQUISITION_AND_HOLD`). 그래서 바깥 메서드가 DB를 건드리기 전에 REQUIRES_NEW를 호출한다면 그 순간 바깥은 아직 커넥션을 안 쥐고 있을 수도 있다. 다만 이것은 우연한 코드 배치에 기대는 것이지 설계가 아니다. 게다가 `readOnly`나 `isolation`을 지정한 트랜잭션은 그 값을 커넥션에 설정해야 하므로 시작 시점에 커넥션을 미리 잡는다. 요행에 기대지 말고 `Cm`을 1로 만드는 것이 정답이다.

### 3-7. NESTED — 세이브포인트, 그리고 JPA에서 안 쓰이는 이유

전파 옵션 중 세 번째로 자주 언급되는 것이 NESTED다. REQUIRES_NEW와 헷갈리기 쉬우니 정확히 구분해 두자.

**NESTED는 새 물리 트랜잭션을 열지 않는다.** 대신 진행 중인 트랜잭션 안에 **세이브포인트(savepoint)**를 찍는다. 세이브포인트는 트랜잭션 중간에 꽂아 두는 되감기 지점으로, 롤백할 때 트랜잭션 전체가 아니라 그 지점까지만 되감을 수 있게 해 준다. 게임의 중간 저장과 같은 개념이다.

```text
REQUIRES_NEW                          NESTED
──────────────────────                ──────────────────────
커넥션 2개                             커넥션 1개 (세이브포인트만 추가)
안쪽이 독립적으로 COMMIT               안쪽 성공분은 바깥 커밋에 함께 실린다
바깥이 롤백돼도 안쪽은 남는다           바깥이 롤백되면 안쪽도 함께 사라진다
안쪽 실패 -> 바깥에 영향 없음           안쪽 실패 -> 세이브포인트까지만 부분 롤백
```

**결정적 차이는 "바깥이 롤백될 때"다.** REQUIRES_NEW는 남고 NESTED는 사라진다. 그래서 3-3의 실패 이력 요구사항은 NESTED로 풀 수 없다.

그리고 JPA 환경에서는 NESTED를 사실상 쓰지 않는다. 이유가 둘이다.

첫째, `JpaTransactionManager`는 중첩 트랜잭션을 **기본적으로 허용하지 않는다.** `nestedTransactionAllowed` 값이 꺼져 있어서 NESTED를 선언하면 `NestedTransactionNotSupportedException`이 난다. (JDBC/MyBatis에서 쓰는 `DataSourceTransactionManager`는 이 값이 켜져 있어 정상 동작한다.)

둘째, 설령 그 값을 켠다 해도 **세이브포인트는 JDBC 커넥션 수준의 되감기일 뿐 영속성 컨텍스트를 되돌려 주지 않는다.** DB에서는 UPDATE가 취소됐는데 1차 캐시 안의 엔티티는 여전히 변경된 상태로 남아 있고, 그 상태가 다음 플러시에 다시 UPDATE로 나갈 수 있다. DB와 메모리가 어긋나는 것이다. 그래서 스프링 문서도 NESTED를 JDBC 자원 트랜잭션 기준으로 설명한다.

정리하면, **JPA 실무에서 "부분적으로 독립된 커밋"이 필요하면 선택지는 REQUIRES_NEW로 좁혀지고, 그래서 3-5의 커넥션 비용을 피할 수 없다** — 이 인과가 REQUIRES_NEW의 대안을 3-4처럼 트랜잭션 바깥에서 찾아야 하는 이유다.

## 4. 꼬리질문 대비 포인트

### "REQUIRED로 합류한 안쪽 메서드가 정상 리턴하면 그 시점에 커밋되나요?"

안 된다. **합류한 논리 트랜잭션은 커밋 권한이 없다.** 스프링은 커밋 처리에서 "내가 이 트랜잭션을 시작한 주인인가"를 먼저 확인하고, 주인이 아니면 COMMIT을 보내지 않고 그냥 리턴한다. 실제 COMMIT은 트랜잭션을 시작한 가장 바깥에서 단 한 번 나간다.

이어서 "그럼 안쪽 메서드에 붙은 `@Transactional`은 아무 일도 안 하나요?"라고 물어오면, **경계 선언으로서는 여전히 의미가 있다**고 답한다. 그 메서드가 단독으로 호출될 때는 자기가 주인이 되어 트랜잭션을 열고, 합류할 때는 rollback-only를 찍는 주체가 된다. "커밋만 안 할 뿐 아무것도 안 하는 것은 아니다"가 정확한 표현이다.

### "REQUIRES_NEW 안에서 예외가 났고 바깥이 catch하지 않았다. 바깥 트랜잭션은 어떻게 되나?"

바깥도 롤백된다. REQUIRES_NEW의 독립성은 **"안쪽 롤백이 바깥 물리 트랜잭션에 rollback-only를 찍지 않는다"**는 뜻이지, 예외 객체가 콜 스택을 타고 올라가는 것까지 막아 주지 않는다. 바깥으로 전파된 런타임 예외는 바깥 트랜잭션의 평범한 롤백 규칙에 그대로 걸린다.

**"독립시키고 싶으면 catch까지가 한 세트"**라고 답하면 정확하다. 반대로 이력 저장 실패가 본 처리를 죽이면 안 되는 경우에도 같은 catch가 필요하므로, 어느 방향이든 호출부의 예외 처리는 설계의 일부다.

### "바깥이 롤백되면 REQUIRES_NEW로 이미 커밋된 데이터는 어떻게 되나요?" (시니어 변별 포인트)

되돌릴 수 없다. 이미 DB에 COMMIT이 나갔기 때문이고, 커밋된 트랜잭션을 취소하는 표준 SQL은 존재하지 않는다.

그래서 판별 기준을 **비가역성에서 도출해** 답하는 것이 포인트다. **"본 처리가 롤백된 세상에 이 데이터만 남아 있어도 되는가?"** 감사 로그·시도 이력은 남아야 하니 적합하다. 반면 재고·잔액처럼 본 처리와 정합성이 묶인 데이터를 REQUIRES_NEW로 빼는 것은 **부분 커밋을 설계로 못 박아 넣는 실수**다. 롤백된 주문의 재고만 차감된 채로 남는 상태를 코드가 스스로 만들어내는 셈이다.

### "REQUIRES_NEW가 커넥션 풀을 고갈시키는 시나리오를 숫자로 설명해보세요." (시니어 변별 포인트)

세 단계로 답한다.

먼저 **왜 2개인지**다. 바깥 트랜잭션은 유보돼도 커넥션을 반납하지 않고(나중에 커밋해야 하므로) 쥐고 있는데, 안쪽이 별도 커넥션을 추가로 요구하므로 스레드당 동시 2개 점유가 된다.

다음은 **교착의 계산**이다. 풀 크기 10에 이 경로를 타는 동시 요청 10개면, 전원이 첫 커넥션을 쥔 채 두 번째를 기다리는데 반납할 주체가 자기들뿐이라 아무도 진행하지 못한다. 영원히는 아니고 `connectionTimeout`(HikariCP 기본 30초)까지 멈췄다가 전원 실패한다.

마지막이 **처방**이다. 교착을 원천 차단하는 풀 크기는 `Tn x (Cm - 1) + 1`인데, 톰캣 기본 스레드 200을 넣으면 201이 나와 현실성이 없다. 그러니 풀을 키우는 방향이 아니라 **`Cm`을 1로 되돌리는 방향** — 아웃박스, 커밋/롤백 후 이벤트, 큐 위임 — 이 정답이다. 여기에 "처리량 관점의 추가 비용은 평균 0.25개 수준으로 미미한데도 위험한 이유는 교착이 평균이 아니라 동시 도착의 꼬리에서 터지기 때문"이라는 대비까지 붙이면 계산과 감각을 동시에 보여줄 수 있다.

### "NESTED와 REQUIRES_NEW의 차이는 무엇인가요?"

NESTED는 새 물리 트랜잭션이 아니라 **같은 트랜잭션 안에 세이브포인트**를 찍는 방식이다. 안쪽이 실패하면 세이브포인트까지만 부분 롤백하고 바깥은 계속 갈 수 있다. 커넥션이 1개라 3-5의 풀 비용도 없다.

결정적 차이는 **바깥이 롤백될 때**다. 물리 트랜잭션이 하나이므로 바깥이 롤백되면 안쪽 작업도 함께 사라진다. REQUIRES_NEW는 남는다. 그래서 "본 처리가 실패해도 이력은 남아야 한다"는 요구는 NESTED로 풀 수 없다.

JPA에서는 두 겹으로 막힌다. `JpaTransactionManager`가 중첩 트랜잭션을 기본적으로 허용하지 않아 `NestedTransactionNotSupportedException`이 나고, 설령 허용해도 세이브포인트는 JDBC 커넥션만 되감을 뿐 영속성 컨텍스트의 엔티티 상태는 그대로 남아 DB와 어긋난다. **그래서 JPA 실무의 선택지는 REQUIRES_NEW로 좁혀지고, 그 비용을 피하려면 전파 옵션이 아니라 트랜잭션 바깥의 도구를 봐야 한다**로 마무리하면 좋다.

### "같은 클래스 안의 메서드에 REQUIRES_NEW를 붙여 호출하면 어떻게 되나요?"

자기 호출은 프록시를 거치지 않으므로 전파 옵션이 통째로 무시되고, 그냥 바깥 트랜잭션 안에서 실행된다. **"독립 트랜잭션으로 분리했다고 믿었는데 실제로는 운명 공동체"**라는, 이 주제와 자기 호출 함정이 교차하는 지점이다.

특히 악질인 이유는 **에러가 안 나기 때문**이다. 컴파일도 되고 실행도 되고 평소에는 이력이 잘 쌓인다. 정작 본 처리가 롤백되는 장애 순간에만 이력이 함께 사라져서, 원인 분석에 가장 필요한 순간에 데이터가 없다. 답은 별도 빈으로 분리하는 것이다. ([자기 호출 문서](11-transactional-self-invocation.md) 참고.)

## 한 줄 요약

전파는 "바깥에 이미 열린 트랜잭션을 안쪽이 물려받을 것인가"의 규칙이고, REQUIRED는 물려받아 새 BEGIN 없이 같은 커넥션을 쓰며 안쪽의 커밋이 실제로는 아무 일도 하지 않는 운명 공동체(그 실체는 rollback-only 플래그)를 만드는 반면, REQUIRES_NEW는 바깥을 유보하고 커넥션을 하나 더 빌려 독립 커밋을 만들어 "본 처리가 롤백돼도 남아야 할 이력"을 가능하게 하지만 스레드당 커넥션 2개 점유라는 청구서가 따라온다 — 풀 10에 동시 요청 10이면 connectionTimeout까지 전원 교착이고 이를 원천 차단하는 풀 크기 `Tn x (Cm - 1) + 1`은 톰캣 스레드 200 기준 201이라 현실성이 없으므로, 답은 풀을 키우는 것이 아니라 아웃박스·커밋 후 이벤트·큐 위임으로 스레드당 커넥션 수를 1로 되돌리는 것이다.
