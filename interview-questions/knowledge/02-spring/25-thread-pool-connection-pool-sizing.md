# 톰캣 스레드풀 / HikariCP 크기 산정 — 코어 수가 아니라 "점유 시간"으로 계산한다

> 핵심 관전 포인트: **풀 크기는 감이 아니라 Little's law(동시 점유 수 L = 처리량 λ × 점유 시간 W)로 계산하는 공학적 결정이다. 핵심은 같은 요청이라도 자원마다 W가 다르다는 것 — 블로킹 MVC에서 톰캣 스레드는 응답을 다 쓸 때까지 전체 응답시간 동안 묶이지만, DB 커넥션은 트랜잭션·쿼리 구간에만 묶인다. 그래서 500 TPS·응답 100ms·커넥션 점유 50ms인 서버는 톰캣 50, Hikari 25라는 서로 다른 숫자가 나오고, "스레드 수 = 커넥션 수"로 맞추는 것은 근거가 없다. 코어 수는 스레드 수의 기준이 아니라 CPU 연산 총량의 상한일 뿐이라(요청당 CPU 5ms면 4코어 = 800 TPS가 천장), I/O 바운드 서버는 스레드가 코어보다 훨씬 많은 것이 정상이다. 계산값 L은 이용률 100%에 해당하는 값이라 그대로 쓰면 안 되고, 목표 이용률 ρ로 나눠 c = L/ρ로 여유를 만든다 — "×1.5"는 주술이 아니라 ρ=0.67의 역수다. 반대편에는 DB 쪽 상한이 있어서 HikariCP 위키는 `connections = (core_count × 2) + effective_spindle_count`를 권하는데 여기서 core_count는 앱 서버가 아니라 DB 서버의 코어 수이고, 앱 계산값과 DB 상한 중 작은 쪽이 실질 상한이다. 마지막으로 자원은 연쇄로 묶이므로(톰캣 200에 Hikari 10이면 실질 처리량은 10/0.05s = 200 TPS에서 막힌다) 풀 크기는 따로 정하는 것이 아니라 병목 지점을 의식하고 정한다. 그리고 계산은 출발점일 뿐, 최종 숫자는 `hikaricp.connections.pending`과 `tomcat.threads.busy`로 검증한다.**

## 1. 산정의 뼈대 — Little's law를 직관에서 식으로

### 1-1. 법칙 이름을 꺼내기 전에 — 가게에 몇 명이 있는가

식을 먼저 보면 무슨 소리인지 모른다. 그래서 식 없이 답할 수 있는 문제부터 시작하자.

어떤 가게에 **손님이 초당 10명씩** 들어온다. 한 손님은 들어와서 **평균 3초** 머물다 나간다. 그렇다면 아무 순간에나 가게 안을 들여다보면 평균 몇 명이 있겠는가.

**30명**이다. 왜 그런지는 이렇게 보면 된다. 지금 이 순간 가게 안에 있는 사람은 "지금부터 3초 전 사이에 들어온 사람"들이다. 3초 동안 들어온 사람은 10명/초 × 3초 = 30명이다. 그래서 30명이 있다.

여기서 눈여겨볼 것은 **가게의 크기나 직원 수를 전혀 묻지 않았다**는 점이다. 들어오는 속도와 머무는 시간만 알면 안에 있는 사람 수가 정해진다. 이건 특정 가게의 성질이 아니라 "들어온 것은 언젠가 나간다"는 보존 관계에서 나오는 산수다.

### 1-2. 식으로 옮기기

방금 한 계산이 **Little's law**다. MIT의 John Little이 1961년에 증명해 그의 이름이 붙었다.

```
L  =  λ  ×  W

L (동시 점유 수)  — 어느 순간 시스템 안에 있는 것의 평균 개수
λ (도착률·처리량) — 단위 시간당 들어오는 개수 (초당 몇 건)
W (체류 시간)     — 하나가 안에 머무는 평균 시간
```

성립 조건은 하나뿐이다. **안정 상태(steady state)** — 들어오는 속도와 나가는 속도가 장기적으로 같아야 한다. 유입이 처리보다 계속 빠르면 L은 수렴하지 않고 무한정 늘어난다. 그래서 이 법칙은 "감당 가능한 부하 안에서" 쓰는 도구다.

반대로 성립 조건에 **없는** 것들이 더 중요하다. 도착이 균일하든 몰리든, 처리 순서가 선착순이든 아니든, 처리 시간 분포가 어떻든 상관없이 성립한다. 그래서 어떤 자원에도 그대로 갖다 쓸 수 있다.

### 1-3. 서버에 대입한다 — 자원마다 W가 다르다

이제 가게를 서버로 바꾼다. "가게 안의 손님 수"가 "그 자원을 동시에 점유 중인 요청 수"가 되고, 그 숫자가 곧 **필요한 풀 크기**다.

예제 조건은 이렇다.

```
장비             4코어
평균 응답시간     100ms   (요청이 들어와서 응답을 다 쓸 때까지)
  그중 DB 커넥션 점유    50ms   (트랜잭션 시작 ~ 커밋/반환)
  나머지                 50ms   (역직렬화, 검증, 외부 API, 직렬화, 응답 전송)
목표 처리량       500 TPS
```

여기서 **결정적인 지점**은 톰캣 스레드와 DB 커넥션의 W가 다르다는 것이다.

- **톰캣 스레드의 W = 100ms.** 블로킹 서블릿 모델에서 스레드는 요청을 받는 순간부터 응답 바이트를 다 쓸 때까지 그 요청에 전속된다. 중간에 DB를 기다리든 외부 API를 기다리든 스레드는 놓여나지 않는다(2-2에서 자세히).
- **Hikari 커넥션의 W = 50ms.** 커넥션은 트랜잭션이 시작될 때 잡히고 커밋/롤백 시 반환된다. 요청의 나머지 50ms 동안에는 커넥션이 풀에 돌아가 있어 다른 요청이 쓸 수 있다.

단위를 한 단계씩 맞춰서 계산해 보자. λ는 "초당", W는 "밀리초"로 되어 있으니 먼저 초로 바꾼다.

```
[톰캣 스레드]
  W = 100ms = 100 / 1000 초 = 0.1초
  L = λ × W = 500건/초 × 0.1초/건 = 50건

[Hikari 커넥션]
  W = 50ms = 50 / 1000 초 = 0.05초
  L = λ × W = 500건/초 × 0.05초/건 = 25건
```

단위 환산이 왜 필요한지 감이 안 오면 환산하지 않고 계산해 보면 뜻이 더 선명하다.

```
500건/초 × 100ms/건 = 50,000 ms/초 = 50초/초

읽는 법: "실제 시간 1초가 흐를 때마다 스레드-시간 50초어치가 필요하다."
스레드 하나는 1초에 1초어치밖에 못 대므로 → 스레드 50개가 필요하다.
```

정리하면 이렇다.

| 자원 | 점유 구간 | W | 계산 | 계산값 L |
|---|---|---|---|---|
| 톰캣 스레드 | 요청 수신 ~ 응답 완료 | 100ms | 500 × 0.1 | **50** |
| Hikari 커넥션 | 트랜잭션 시작 ~ 반환 | 50ms | 500 × 0.05 | **25** |

**"스레드 수 = 커넥션 수"로 맞추는 것이 왜 근거 없는지**가 이 표에서 나온다. 두 자원의 W가 2배 차이나므로 필요한 개수도 2배 차이난다. 커넥션을 50개로 맞추면 25개는 평생 놀면서 DB 쪽 자원만 잡아먹고, 스레드를 25개로 맞추면 처리량이 절반으로 잘린다.

그리고 여기서 실무적으로 가장 값진 따름정리가 나온다. **W를 줄이면 같은 λ를 더 작은 풀로 감당한다.** 커넥션 점유 시간 50ms를 25ms로 줄이면 필요 커넥션은 25개에서 12.5개가 된다. 풀을 늘리기 전에 점유 시간부터 의심해야 하는 이유다(줄이는 방법은 3-6과 `22-external-api-call-inside-transaction.md`).

### 1-4. 식을 거꾸로 쓰면 — 풀 크기가 처리량의 천장을 정한다

L = λW는 등식이므로 λ = L / W로 돌려 쓸 수 있다. 그러면 **"풀 크기 c를 정하는 순간 그 자원을 지나는 최대 처리량이 정해진다"**는 뜻이 된다.

```
λ_max = c / W

커넥션 10개, 점유 50ms  ->  10 / 0.05 = 200 TPS
커넥션 25개, 점유 50ms  ->  25 / 0.05 = 500 TPS
커넥션 50개, 점유 50ms  ->  50 / 0.05 = 1,000 TPS
```

이 방향이 중요한 이유는, 면접에서 "풀 크기를 왜 그렇게 잡았나"를 물었을 때 **"그 값이 우리 서비스의 처리량 상한을 얼마로 선언한 것인지"**를 같이 말할 수 있어야 하기 때문이다. 풀 크기는 성능 설정이 아니라 **용량 선언**이다.

## 2. 오개념 교정 — 스레드, 코어, 그리고 대기

여기서 다루는 두 오개념은 이 문서의 핵심이다. 계산식을 외워도 이 둘을 틀리면 숫자가 통째로 어긋난다.

### 2-1. 오개념 1 — "스레드 수는 코어 수만큼"이 아니다

"4코어니까 스레드도 4개쯤"이라는 말이 자연스럽게 들리는 이유는 코어 수를 **동시에 존재할 수 있는 스레드 수의 제한**으로 오해하기 때문이다.

정확히는 이렇다. **코어 수 = 어느 한 순간에 CPU 위에서 실제로 명령어를 실행 중일 수 있는 스레드의 최대 개수**다. 존재할 수 있는 스레드 수와는 아무 상관이 없다. 스레드 50개를 만들어 두고 그중 4개만 실행 중이고 46개는 자고 있어도 아무 문제가 없다.

그럼 나머지 46개는 어떤 상태로 있는가. 자바 스레드의 상태를 알아야 이 질문에 답할 수 있다.

```
[자바 스레드 상태 — java.lang.Thread.State]

NEW           아직 start() 되지 않음

RUNNABLE      실행 중이거나 실행 가능. ★ 함정: 소켓 read 대기도 여기다.
              CPU 위에 올라가 있는 것과 코어를 기다리는 것을 구분하지 않는다.

BLOCKED       synchronized 모니터 락을 기다리는 중. (이것만이 BLOCKED다)

WAITING       Object.wait(), Thread.join(), LockSupport.park() 등으로
              누군가 깨워줄 때까지 무기한 대기

TIMED_WAITING 위와 같지만 시간 제한이 있는 대기 (sleep, park(nanos), poll(timeout))

TERMINATED    실행 종료
```

여기서 주니어가 거의 반드시 틀리는 지점이 하나 있다. **JDBC로 DB 응답을 기다리는 스레드는 `BLOCKED`가 아니라 `RUNNABLE`로 보인다.** `BLOCKED`는 오직 `synchronized` 락 경쟁을 뜻하는 상태 이름이다.

왜 그런가. 소켓 read는 JVM 입장에서는 네이티브 메서드 호출이다. JVM이 네이티브 코드에 진입하는 순간 그 안에서 OS가 스레드를 재웠는지 어쨌는지 JVM은 알 수 없다. 그래서 "네이티브 안에 있다 = 실행 중일 수도 있다"로 보고 `RUNNABLE`로 표시한다. **자바가 보는 상태와 OS가 보는 상태가 어긋나는 지점**이다.

실제 스레드 덤프에서는 이렇게 보인다.

```
"http-nio-8080-exec-42" #142 daemon prio=5 tid=0x... nid=0x... runnable
   java.lang.Thread.State: RUNNABLE            <- BLOCKED가 아니다
        at sun.nio.ch.Net.poll(Native Method)  <- 여기서 OS가 이 스레드를 재웠다
        at sun.nio.ch.NioSocketImpl.park(...)
        at sun.nio.ch.NioSocketImpl.timedRead(...)
        at java.net.Socket$SocketInputStream.read(...)
        at org.postgresql.core.VisibleBufferedInputStream.readMore(...)
        at org.postgresql.core.PGStream.receiveChar(...)
        at org.postgresql.jdbc.PgStatement.executeQuery(...)     <- DB 응답 대기 중
```

이 사실이 왜 중요한가. 장애 중 스레드 덤프를 떠서 "`RUNNABLE`이 200개니까 CPU가 포화됐구나"라고 읽으면 정반대의 진단이 나온다. 실제로는 200개 전부가 소켓 대기 중이라 **CPU 사용률은 거의 0%**일 수 있다. 상태 이름이 아니라 **스택 최상단이 무엇인지**를 봐야 한다.

이제 처음 질문으로 돌아가자. 4코어에서 스레드 50개가 도는 방식은 이렇다.

```
[4코어 장비, 톰캣 스레드 50개의 어느 한 순간 스냅샷]

 ┌─ 소켓 대기 (RUNNABLE이지만 OS가 재움) ── 약 25개
 │     DB 응답을 기다리는 중. 스케줄러의 실행 대기열에 아예 없다.
 │     CPU 0%. 비용은 스택 메모리(플랫폼에 따라 수백 KB~2MB 예약)뿐.
 │     응답 패킷이 도착하면 OS가 깨워 실행 대기열에 넣는다.
 │
 ├─ 소켓 대기 (클라이언트 쪽) ───────────── 약 20개
 │     요청 본문 수신 중이거나 응답 전송 중. 역시 CPU 0%.
 │
 ├─ 실행 대기열에서 코어를 기다림 ────────── 몇 개
 │     스케줄러가 수 ms 타임 슬라이스로 코어 4개에 번갈아 태운다.
 │
 └─ 실제로 코어 위에서 실행 중 ─────────── 최대 4개
       역직렬화, 검증, 매핑, 직렬화 같은 CPU 작업

 => 실제로 CPU가 필요한 스레드는 극소수라서 4코어로 충분하다.
```

**대기 중인 스레드는 CPU를 전혀 소모하지 않는다.** 이것이 I/O 바운드 서버에서 스레드가 코어보다 훨씬 많아도 되는 이유다.

### 2-2. 오개념 2 — 블로킹 MVC에서 대기 중인 스레드는 다른 요청을 처리하지 못한다

2-1에서 "대기 중인 스레드는 CPU를 안 쓴다"고 했다. 여기서 **"그럼 그동안 다른 요청을 처리하면 되지 않나"**로 넘어가는 것이 두 번째 오개념이다. 못 한다.

```java
// before 의 오해: "DB 기다리는 동안 이 스레드가 다른 요청을 처리한다"
public OrderResponse getOrder(Long id) {
    Order order = orderRepository.findById(id);
    // 위 한 줄에서 소켓 read가 반환될 때까지 이 메서드는 이 줄에 멈춰 있다.
    // 이 스레드의 콜 스택에는 getOrder 호출 프레임이 그대로 쌓여 있고,
    // 그 프레임을 치우지 않는 한 다른 요청의 코드를 실행할 수 없다.
    // CPU를 놓아준 것과 스레드를 놓아준 것은 전혀 다른 이야기다.
    return toResponse(order);
}
```

핵심은 **스레드가 곧 콜 스택**이라는 점이다. 스레드 하나에는 콜 스택이 하나뿐이고, 그 스택에는 지금 진행 중인 요청의 호출 프레임이 쌓여 있다. 다른 요청을 처리하려면 그 스택을 어딘가에 치워두고 새 스택을 올려야 하는데, 플랫폼 스레드에는 그런 기능이 없다.

그래서 갈림길은 셋이다.

| 대기를 흡수하는 방법 | 어떻게 | 대표 |
|---|---|---|
| 스레드 개수로 흡수 | 대기하는 스레드를 여러 개 둔다 | 블로킹 MVC (이 문서) |
| 이벤트 통지로 흡수 | 아예 대기하지 않고 콜백을 걸어둔다 | WebFlux (`27-...md`) |
| 스택을 힙에 옮겨 흡수 | 대기 시 스택을 얼려 치우고 캐리어를 반납 | 가상 스레드 (`01-java-kotlin/28-virtual-threads-pinning.md`) |

이 문서가 다루는 블로킹 MVC에서는 **대기 시간을 흡수하는 수단이 스레드 개수뿐**이다. 그러니 I/O 대기가 긴 서버일수록 스레드가 많이 필요하고, 이것이 "I/O 바운드 서버는 스레드 ≫ 코어"의 정확한 근거다.

### 2-3. 그럼 코어 수는 무엇을 정하는가 — CPU 연산 총량의 상한

코어 수가 스레드 수의 기준이 아니라면 아무 의미가 없는 것인가. 아니다. **코어 수는 초당 처리 가능한 CPU 연산의 총량을 정한다.** 계산으로 보자.

```
[CPU 예산 계산]

4코어 = 초당 4 × 1,000ms = 4,000ms 의 CPU 시간을 제공한다.
요청 하나가 실제로 쓰는 CPU 시간이 5ms 라면,

  CPU 상한 = 4,000ms / 5ms = 800 TPS

즉 스레드를 50개로 잡든 500개로 잡든 이 서버는 800 TPS를 넘을 수 없다.
목표 500 TPS일 때의 CPU 이용률 = 500 / 800 = 62.5%
```

요청당 CPU 시간이 늘어나면 천장이 어떻게 내려앉는지도 같은 식으로 나온다.

| 요청당 CPU | 4코어의 CPU 상한 | 500 TPS일 때 CPU 이용률 |
|---|---|---|
| 5ms | 4,000 / 5 = **800 TPS** | 62.5% |
| 8ms | 4,000 / 8 = **500 TPS** | 100% — 이미 위험 |
| 10ms | 4,000 / 10 = **400 TPS** | 125% — 목표 달성 불가 |

**요청당 CPU가 8ms면 CPU 상한이 정확히 목표와 같아진다.** 숫자상으로는 "딱 맞는다"처럼 보이지만 실제로는 이미 사고다. 이용률 100%에서 큐가 어떻게 되는지는 3-2에서 다룬다.

그래서 워크로드 성격에 따라 산정 방식이 완전히 갈린다.

- **I/O 바운드** (일반적인 웹 API — DB, 캐시, 외부 API를 기다리는 시간이 대부분): 스레드 ≫ 코어. 스레드 수는 Little's law로 계산한다.
- **CPU 바운드** (암호화, 이미지 인코딩, 대량 집계): 스레드 ≈ 코어(±1~2). 여기서 스레드를 늘리는 것은 아무 효과가 없다 — 코어가 4개인데 연산 스레드를 40개 만들어도 초당 4,000ms라는 CPU 예산은 그대로다. 오히려 컨텍스트 스위칭과 캐시 오염 비용이 붙어 처리량이 **떨어진다.**

### 2-4. 그래서 "많을수록 좋다"가 왜 틀린가

스레드를 늘리는 데 드는 비용은 셋이다.

**(1) 스택 메모리.** 플랫폼 스레드는 만들 때 전용 콜 스택을 네이티브 메모리에 예약한다. 크기는 플랫폼마다 달라 수백 KB~2MB 수준이다(리눅스 x86-64 기본 1MB, macOS/AArch64 OpenJDK 21은 2MB). 예약이지 즉시 소모는 아니지만, **주소 공간과 커널 자료구조는 스레드 수에 정직하게 비례**한다.

**(2) 컨텍스트 스위칭.** 실행 가능한 스레드가 코어보다 훨씬 많으면 스케줄러가 계속 갈아 끼운다. 레지스터 저장·복원 비용도 있지만 더 아픈 것은 **CPU 캐시 오염**이다 — 새로 올라온 스레드는 자기 데이터가 캐시에 없어 메모리에서 다시 읽어야 한다.

**(3) 뒷단으로 과부하를 그대로 흘려보낸다.** 이게 가장 실무적으로 중요하다. `max-threads`를 2000으로 잡으면 그 2000개가 전부 DB 커넥션을 요구하러 몰려간다. 처리 못 할 요청을 앞에서 받아들이는 것은 문제를 뒤로 미루는 것이 아니라 **더 나쁜 곳에서 터지게 만드는 것**이다. 이 주제는 `07-traffic-performance/16-backpressure-and-application-points.md`에서 백프레셔로 다룬다.

## 3. 계산값에서 운영 설정값으로 — 여유, DB 상한, 병목, 실측

1절에서 나온 50과 25는 **계산값이지 설정값이 아니다.** 그대로 설정에 넣으면 안 되는 이유와, 그 사이를 메우는 네 가지 고려를 차례로 본다.

### 3-1. 평균이 아니라 피크로 계산한다

가장 흔한 실수는 λ에 **일평균 TPS**를 넣는 것이다. 트래픽은 평평하지 않다.

```
[하루 트래픽 예시]
  일평균          150 TPS
  피크 시간대 평균  500 TPS   (평균의 3.3배)
  초 단위 순간 최대  900 TPS   (버스트)
```

일평균 150으로 계산하면 톰캣 15, Hikari 8이 나온다. 그 설정으로 피크 시간대를 맞으면 어떻게 되는가. λ_max = c/W이므로 톰캣 15개는 15/0.1 = 150 TPS까지만 흘려보낸다. 나머지 350 TPS는 accept 큐에 쌓이다가 거절된다.

**λ에는 감당해야 하는 피크를 넣는다.** 그리고 W에도 같은 원칙이 적용된다 — 평균 응답시간 100ms가 아니라 **p95나 p99**를 봐야 한다. 평균 100ms인데 p99가 800ms라면, 그 1%의 느린 요청들이 스레드를 8배 오래 잡는다. 느린 쿼리 하나가 풀을 잠식하는 메커니즘이 바로 이것이다.

### 3-2. 여유는 주술이 아니라 "목표 이용률의 역수"다

"계산값 × 1.5" 같은 숫자를 근거 없이 던지면 안 된다. 여유가 필요한 이유부터 짚자.

L = λW로 나온 50은 **"평균적으로 50개가 동시에 점유 중"**이라는 뜻이다. 여기서 풀 크기를 정확히 50으로 잡으면 이용률(utilization) ρ = L/c = 50/50 = **100%**가 된다. 이건 "딱 맞게 썼다"가 아니라 "쉴 틈이 하나도 없다"는 뜻이다.

문제는 도착이 평균값대로 균일하게 오지 않는다는 것이다. 어떤 순간에는 55개가 몰리고 어떤 순간에는 45개다. 이용률이 100%라면 55개가 몰린 순간의 5개는 **대기해야 하고**, 그 대기가 응답시간을 늘려 W가 커지고, W가 커지면 L이 커지고, L이 커지면 대기가 더 늘어난다.

이 되먹임을 정량화한 것이 대기행렬 이론이다. 가장 단순한 M/M/1 모델(창구 1개)에서 평균 대기 시간은 이렇게 나온다.

```
평균 대기 시간 = 서비스 시간 × ρ / (1 - ρ)
```

분모에 (1 - ρ)가 있는 것이 전부다. ρ가 1에 가까워지면 분모가 0으로 가면서 대기가 폭발한다.

| 이용률 ρ | 평균 대기 (서비스 시간의 몇 배) | 총 체류 시간 |
|---|---|---|
| 0.5 | 1.0배 | 2.0배 |
| 0.7 | 2.3배 | 3.3배 |
| 0.8 | 4.0배 | 5.0배 |
| 0.9 | 9.0배 | 10.0배 |
| 0.95 | 19.0배 | 20.0배 |
| 0.99 | 99.0배 | 100.0배 |

이용률을 0.5에서 0.9로 올리는 것은 "1.8배 더 쓰는 것"이 아니라 **응답시간을 5배로 만드는 것**이다. 이것이 "여유를 둬야 한다"의 정확한 근거다.

다만 정직하게 덧붙일 것이 있다. 위 표는 창구가 1개일 때다. 풀은 창구가 c개인 M/M/c에 가깝고, c가 클수록 같은 ρ에서 대기가 훨씬 완만하다. 실제로 계산해 보면 이렇다.

| 풀 크기 c | ρ=0.7 대기 확률 | ρ=0.8 | ρ=0.9 | ρ=0.95 |
|---|---|---|---|---|
| 4 | 42.9% | 59.6% | 78.8% | 89.1% |
| 10 | 22.2% | 40.9% | 66.9% | 82.6% |
| 25 | 6.4% | 20.9% | 50.8% | 72.8% |
| 50 | 1.1% | 8.7% | 36.4% | 62.9% |

여기서 읽어야 할 것은 두 가지다. 첫째, **풀이 작을수록 같은 이용률에서 더 아프다** — 커넥션 4개짜리 풀은 ρ=0.8만 돼도 요청의 60%가 대기를 겪는다. HikariCP가 작은 풀을 권하는데(3-3) 작은 풀일수록 이용률에 민감하다는 것은 함께 알아야 하는 사실이다. 둘째, **어느 크기든 ρ가 0.9를 넘으면 급격히 나빠진다.**

그래서 여유는 이렇게 정한다.

```
풀 크기 c = L / ρ_target

톰캣  L=50,  ρ=0.7 -> c = 50/0.7  = 71.4 -> 72 (또는 여유 있게 80)
Hikari L=25, ρ=0.7 -> c = 25/0.7  = 35.7 -> 36
톰캣  L=50,  ρ=0.8 -> c = 50/0.8  = 62.5 -> 64
Hikari L=25, ρ=0.8 -> c = 25/0.8  = 31.2 -> 32
```

**"계산값 × 1.5"의 정체는 ρ_target ≈ 0.67이다.** 1/0.7 = 1.43배, 1/0.8 = 1.25배. 배수를 외우는 것이 아니라 "이 자원을 몇 %까지 쓸 작정인가"를 정하는 것이고, 그 판단 기준은 위 표의 대기 확률과 서비스의 지연 목표(SLO)다.

한 가지 더. 위 모델들은 도착이 무작위(포아송)라고 가정한다. 실제 트래픽은 그보다 더 몰려서 오므로, **모델이 말하는 대기보다 실제 대기가 나쁘다.** 그래서 이 계산은 하한선을 주는 것이고 최종 확인은 3-6의 실측이다.

### 3-3. 반대편의 상한 — HikariCP는 왜 "풀은 작을수록 좋다"고 하는가

3-2까지는 앱 쪽 사정만 봤다. 커넥션은 반대편에 DB가 있다는 점이 다르다.

HikariCP 공식 위키의 "About Pool Sizing" 문서는 반직관적인 주장을 한다. **풀을 키우면 처리량이 오히려 떨어진다.** 근거가 필요한 주장이니 왜 그런지부터 보자.

커넥션 하나는 DB 쪽에서 **실행 주체 하나**를 뜻한다. PostgreSQL은 커넥션마다 백엔드 프로세스를 하나씩 띄운다(MySQL은 스레드 하나). 그러니 커넥션 1,000개는 DB 서버에 프로세스 1,000개다. 그 DB 서버의 코어가 8개라면, 8개 코어가 1,000개 프로세스를 시분할해야 한다.

여기서 세 가지가 나빠진다.

**(1) 컨텍스트 스위칭.** 2-4에서 본 것과 같은 비용이 이번엔 DB 서버에서 발생한다. 코어 8개 위에 1,000개를 번갈아 태우면 실제 쿼리 실행보다 갈아 끼우는 데 쓰는 시간이 늘어난다.

**(2) 락 경합.** 동시에 실행되는 트랜잭션이 많을수록 같은 행·같은 인덱스 페이지·같은 내부 자료구조를 건드릴 확률이 올라간다. PostgreSQL의 경우 행 잠금뿐 아니라 버퍼 맵핑 같은 내부 경량 락(LWLock) 경합도 늘어난다. 경합은 대기이고, 대기는 W를 늘리고, W가 늘면 커넥션이 더 오래 잡힌다.

**(3) 디스크 시크와 캐시 오염.** 회전 디스크에서는 동시 요청이 많을수록 헤드가 이리저리 움직여 순차성이 깨진다. SSD에서는 이 효과가 훨씬 작지만 0은 아니고, 대신 **공유 버퍼 오염**이 그 자리를 대신한다 — 동시 실행 쿼리가 많으면 서로의 캐시된 페이지를 밀어낸다.

세 가지가 겹치면 **커넥션을 늘렸는데 전체 처리량이 떨어지는** 구간이 생긴다. 위키가 인용하는 Oracle Real-World Performance 그룹의 실험이 이 현상을 보여준다 — 커넥션 풀을 2,048개에서 96개로 줄였더니 응답시간과 처리량이 **모두 개선**됐다.

그래서 위키가 제시하는 출발점 공식은 이렇다.

```
connections = (core_count × 2) + effective_spindle_count
```

**여기서 주니어가 반드시 틀리는 지점이 있다. `core_count`는 DB 서버의 코어 수다.** 앱 서버의 코어 수가 아니다. 이 공식이 말하는 것은 "DB가 동시에 의미 있게 진행시킬 수 있는 작업의 개수"이지 앱이 몇 개를 요청할 수 있는지가 아니다.

- `core_count × 2` — 코어 수의 2배까지 두는 이유는, 커넥션 하나가 항상 CPU를 쓰는 게 아니라 중간중간 디스크·네트워크를 기다리기 때문이다. 그 대기 동안 다른 커넥션이 코어를 쓰라고 여유분을 둔 것이다.
- `effective_spindle_count` — 동시에 독립적으로 탐색(seek)할 수 있는 디스크의 개수다. 회전 디스크 시절의 어휘라 SSD·클라우드 스토리지에서는 그대로 대입하기 어렵다. 실무에서는 이 항을 작게(1~2) 두거나 사실상 무시하고, 대신 실측으로 보정한다.

DB 서버가 8코어라면 (8 × 2) + 1 = **17개** 정도가 출발점이 된다. 3-2에서 앱 계산으로 나온 36과 이 17이 충돌한다.

**충돌하면 작은 쪽이 실질 상한이다.** 앱이 36개를 꽂아도 DB가 17개어치의 일밖에 못 하면, 나머지 19개는 대기 줄을 앱 쪽에서 DB 쪽으로 옮겨 놓은 것에 불과하다. 오히려 DB 안에서의 경합을 늘려 W를 더 나쁘게 만든다.

그럼 어떻게 하는가. **c를 늘리는 대신 W를 줄인다.** L = λW에서 c가 17로 묶여 있고 λ가 500이라면, W는 17/500 = 34ms 이하여야 한다. 50ms를 34ms로 줄이는 것이 진짜 과제가 된다.

### 3-4. 앱 인스턴스 수를 곱하는 것을 잊지 않는다

풀 크기는 **인스턴스 하나당** 값이다. 그런데 DB가 보는 것은 전체 합계다.

```
앱 인스턴스 6대 × Hikari maximumPoolSize 30 = DB에 최대 180개 커넥션
```

PostgreSQL의 `max_connections` 기본값은 **100**이다(그중 몇 개는 `superuser_reserved_connections`로 예약되어 일반 사용자가 쓸 수 있는 것은 더 적다). 위 구성은 기본 설정의 DB에 그대로 붙이면 `FATAL: sorry, too many clients already`로 접속 자체가 거부된다.

이것이 오토스케일링과 만나면 더 고약해진다. 트래픽이 늘어 인스턴스가 6대에서 12대로 늘면 DB 커넥션 요구가 360개로 자동으로 두 배가 된다. **앱을 수평 확장했는데 DB가 먼저 죽는** 전형적인 패턴이다.

대응은 셋이다.

- 인스턴스 수를 곱한 총합을 기준으로 인스턴스당 풀 크기를 정한다.
- DB 앞에 **PgBouncer** 같은 커넥션 풀러를 둔다 — 앱들의 커넥션을 받아 DB에는 훨씬 적은 수의 실제 커넥션으로 다중화해 준다.
- 배치·관리 도구·읽기 전용 조회처럼 성격이 다른 워크로드는 별도 데이터소스로 분리해 서로의 풀을 잠식하지 않게 한다.

### 3-5. 자원은 연쇄로 묶인다 — 병목을 의식하고 정한다

지금까지 스레드와 커넥션을 따로 계산했지만, 실제 요청은 **두 자원을 순서대로 통과**한다. 그래서 하나만 잘 잡아도 소용이 없다.

톰캣 200, Hikari 10인 흔한 조합(둘 다 각각의 기본값에 가깝다)에서 500 TPS가 들어오면 무슨 일이 생기는지 따라가 보자.

```
[요청 500 TPS 유입]
        |
        v
 톰캣 스레드풀 (max-threads 200)
        |  200개까지 받아들인다. 문은 넓다.
        v
 HikariCP (maximumPoolSize 10, 점유 50ms)
        |  λ_max = 10 / 0.05s = 200 TPS  <- 여기가 진짜 천장
        v
      PostgreSQL

 결과:
   - 실제로 처리되는 것은 200 TPS. 나머지 300 TPS는 커넥션 대기.
   - 대기하는 요청은 톰캣 스레드를 문 채로 기다린다 (2-2).
   - 톰캣 스레드 200개가 순식간에 전부 "커넥션 대기" 상태가 된다.
   - 그때부터 새 요청은 톰캣 accept 큐에 쌓이고, DB와 무관한 API도
     헬스체크도 응답하지 못한다.
   - 30초(HikariCP connection-timeout 기본값) 뒤 SQLTransientConnectionException.
```

**문을 넓게 열어두고 안쪽 통로를 좁게 두면, 좁은 통로 앞에 사람이 쌓이는 것이 아니라 건물 전체가 마비된다.** 톰캣 스레드 200개가 전부 대기에 쓰이면 그 200개는 없는 것이나 마찬가지다.

여기서 나오는 산정 원칙이 이것이다.

- **연쇄 자원의 처리량 상한은 가장 좁은 자원이 정한다.** 톰캣을 200으로 잡아둔 것이 200 TPS 서버를 만들지 않는다. Hikari 10이 그렇게 만든다.
- **그러니 풀 크기는 따로 정하는 것이 아니라, 어디를 병목으로 삼을지 정하고 나머지를 거기에 맞춘다.** 병목을 DB에 두기로 했다면(대개 그렇다) 톰캣 스레드는 커넥션 대기 요청을 잔뜩 쌓아두지 않을 만큼만 두는 것이 낫다.
- **그리고 좁은 지점 앞에서는 오래 기다리게 두지 말고 빨리 거절한다.** HikariCP `connection-timeout`을 기본 30초에서 2~3초로 낮추면, 대기 줄이 톰캣 스레드풀로 전이되는 시간이 10배 짧아진다. 이 대응은 `26-hikaricp-connection-pool-exhaustion.md`에서 처방으로 다시 다룬다.

### 3-6. 계산은 출발점이다 — 무엇을 보고 검증하는가

계산이 끝나면 부하 테스트로 목표 λ를 걸고 아래 지표를 본다. **각 지표를 "어떤 값이면 무슨 뜻인지"까지 정해두고 봐야** 검증이 된다.

| 지표 | 이 값이면 | 뜻 |
|---|---|---|
| `hikaricp.connections.pending` | **0보다 크다** | 커넥션을 못 받고 기다리는 스레드가 있다 = 풀 부족 또는 W 증가 |
| `hikaricp.connections.active` | max에 붙어 있다 | 풀이 포화. pending과 함께 봐야 원인이 갈린다 |
| `hikaricp.connections.usage` | 계산에 쓴 W보다 크다 | 점유 시간 가정이 틀렸다. 이 값이 실측 W다 |
| `hikaricp.connections.acquire` | 0에서 벗어난다 | 커넥션을 얻는 데 걸리는 시간. 여기가 늘면 이미 대기 중 |
| `tomcat.threads.busy` | `tomcat.threads.config.max`에 붙는다 | 스레드 포화. 응답시간 악화의 결과일 수도 있다 |
| CPU 사용률 | 포화인데 TPS가 안 오른다 | 2-3의 CPU 상한에 걸린 것. 스레드를 늘려도 소용없다 |

이 중 **`hikaricp.connections.usage`가 특별히 중요하다.** 이것이 Little's law의 W를 실측해 주는 값이기 때문이다. 계산할 때 W=50ms로 가정했는데 실측이 120ms로 나온다면, 필요 커넥션은 25가 아니라 500 × 0.12 = **60개**다. 계산이 틀린 게 아니라 **입력 가정이 틀렸던 것**이다.

`pending`이 0보다 크면서 `usage`가 가정치와 같다면 진짜 풀 부족이고, `pending`이 크면서 `usage`가 늘었다면 풀 부족이 아니라 점유 시간 문제다. **이 두 갈래가 26번 문서의 진단 프레임으로 그대로 이어진다.**

메트릭 자체를 켜는 법도 알아두면 좋다. Spring Boot에서 Hikari 메트릭은 Micrometer가 붙어 있으면 자동으로 나오지만, **톰캣 메트릭(`tomcat.*`)은 `server.tomcat.mbeanregistry.enabled=true`를 켜야** 노출된다. 이걸 몰라서 "톰캣 지표가 안 보인다"고 하는 경우가 흔하다.

마지막으로, p99가 평균과 크게 벌어지면 평균 기반 계산 자체가 깨진다(3-1). **분포를 보지 않고 평균만으로 산정하면 느린 요청 1%가 풀을 잠식하는 상황을 계산에서 놓친다.**

## 4. 꼬리질문 대비 포인트

### "그래서 이 서버는 결국 몇으로 잡나요?"

숫자 하나가 아니라 **계산 → 보정 → 검증**의 순서로 답한다.

```
① 계산    L_tomcat = 500 × 0.1  = 50
          L_hikari = 500 × 0.05 = 25
② 여유    ρ_target = 0.7 -> tomcat 72, hikari 36
③ DB 상한 DB 8코어 -> (8×2)+1 = 17 -> hikari는 17이 상한
④ 인스턴스 6대 × 17 = 102 -> PostgreSQL max_connections 100 초과, 재조정 필요
⑤ 결론    hikari는 계산값(36)이 아니라 DB 상한에 묶인다.
          -> 풀을 늘리는 대신 점유 시간 W를 50ms -> 34ms 이하로 줄이는 것이 과제
⑥ 검증    부하 테스트에서 pending > 0 여부와 usage 실측치로 가정을 확인
```

**"앱 계산값과 DB 상한 중 작은 쪽이 실질 상한이고, 거기서 막히면 c가 아니라 W를 손대야 한다"**까지 말하면 이 질문은 끝난다.

### "트래픽이 2배(1,000 TPS)가 되면 풀도 2배로 잡으면 되나요?"

산술적으로는 스레드 100, 커넥션 50이 맞다. 하지만 그 전에 확인할 것이 둘 있다.

**(1) CPU 예산이 버티는가.** 요청당 CPU 5ms면 4코어의 상한은 800 TPS다(2-3). 1,000 TPS는 **애초에 이 장비에서 불가능**하다. 풀을 아무리 늘려도 안 된다.

**(2) DB가 버티는가.** 커넥션 50개는 DB 쪽 공식이 말하는 17개를 크게 넘는다. 늘려도 DB 안에서 경합만 늘어난다(3-3).

그래서 답은 **한 대의 수직 확장이 아니라 인스턴스 증설(수평 확장)**이다. 단 3-4의 함정이 여기서 튀어나온다 — 인스턴스를 2배로 늘리면 DB 커넥션 요구도 2배가 되므로, 인스턴스당 풀 크기를 함께 줄이거나 PgBouncer를 넣어야 한다. **"수평 확장하면 DB 쪽 총 커넥션이 같이 늘어난다"는 것을 짚는 것이 이 질문의 변별점이다.**

### "응답시간이 갑자기 늘어나면 무슨 일이 벌어지나요?" (시니어 변별 포인트)

L = λW를 그대로 읽으면 답이 나온다. **λ는 그대로인데 W가 늘면 L이 비례해서 늘어난다.**

```
평상시  500 TPS × 0.05s = 25개 필요, 풀 36개 -> 이용률 69%, 여유 있음
느린 쿼리로 점유 시간이 300ms가 되면
        500 TPS × 0.30s = 150개 필요, 풀은 36개 -> 즉시 고갈
```

여기서 멈추면 절반이다. 진짜 무서운 것은 **되먹임**이다.

```
W 증가 -> 필요 L 증가 -> 풀 고갈 -> 커넥션 대기 발생
      -> 대기 시간이 응답시간에 더해져 W가 더 증가 -> ...
```

3-2의 표가 말하는 그대로다. 이용률이 1에 가까워지면 대기가 폭발하고, 그 대기가 다시 W를 밀어 올린다. 그래서 **풀 크기 문제로 보이는 장애의 상당수가 실제로는 W 악화(느린 쿼리, 인덱스 누락, 외부 API 지연, 락 경합)가 원인**이다. 진단 절차는 `26-hikaricp-connection-pool-exhaustion.md`가 다룬다.

그리고 W 악화는 풀 크기로 못 메운다. 위 예에서 300ms를 감당하려면 커넥션 150개가 필요한데, DB 상한이 17이라면 **어떤 풀 크기로도 불가능**하다.

### "톰캣 max-threads를 그냥 크게(예: 2,000) 잡으면 안 되나요?"

세 층위로 답한다.

**(1) 자원 비용.** 스레드당 스택이 수백 KB~2MB 예약되므로 2,000개면 수 GB의 주소 공간이다. 컨텍스트 스위칭 비용도 붙는다(2-4).

**(2) 뒷단으로 과부하가 그대로 전달된다.** 이게 핵심이다. 3-5에서 봤듯이 스레드를 넓게 열면 그 스레드들이 전부 커넥션을 요구하러 몰려간다. **처리 못 할 요청을 받아들이는 것은 문제를 뒤로 미루는 것이 아니라 더 나쁜 곳에서 터지게 하는 것**이다.

**(3) 그래서 빨리 거절하는 것이 낫다.** 감당 가능한 만큼만 받고 나머지는 accept 큐 상한에서 거절해 503을 주는 편이, 전부 받아들여 30초 뒤 전면 타임아웃되는 것보다 낫다. 이것이 백프레셔의 관점이다 — **풀 크기의 상한은 제약이 아니라 신호 장치다**(`07-traffic-performance/16-backpressure-and-application-points.md`).

여기서 한 걸음 더 나가면 가산점이다. **톰캣의 `max-threads` 200은 그 자체가 유입 제어(admission control) 장치였다.** 아무도 그걸 백프레셔라고 부르지 않았지만, 시스템을 지켜주던 것은 그 숫자다. 다음 질문이 바로 이 지점을 건드린다.

### "가상 스레드(Java 21)를 켜면 이 산정 문제가 사라지나요?" (시니어 변별 포인트)

절반만 사라지고, 나머지 절반은 **오히려 나빠진다.**

**사라지는 쪽**: 가상 스레드는 블로킹 시 캐리어 스레드를 반납하므로 스레드 개수가 사실상 제약이 아니게 된다. 톰캣 요청 스레드 산정 문제는 의미가 옅어진다. Spring Boot 3.2+에서 `spring.threads.virtual.enabled=true` 한 줄이면 켜진다.

**그대로인 쪽**: **DB 커넥션은 여전히 물리 자원이다.** 한 줄 원리로 말하면 **"가상 스레드는 기다리는 주체를 싸게 만들 뿐, 기다리는 대상의 개수를 늘리지 않는다."** 스레드를 1만 개 띄워도 Hikari 커넥션 17개는 17개다. Little's law는 **자원별로** 성립하므로 스레드 계산식만 무의미해지고 커넥션 계산식은 그대로 남는다.

**나빠지는 쪽**: 스레드풀이 암묵적으로 하던 유입 제어가 사라진다. 동시 요청 상한이 `max-threads` 200에서 `max-connections` 8,192로 뛰므로, 예전엔 문 앞에서 거절되던 요청이 전부 들어와 커넥션 풀 앞에서 30초를 기다린다. **빠른 실패가 느린 전멸로 바뀐다.** 대응은 세마포어·Resilience4j Bulkhead로 문지기를 명시적으로 복원하고 `connection-timeout`을 짧게 잡는 것이다.

자세한 논의는 `27-webflux-vs-mvc-threading-model.md`(모델 비교와 유입 제어)와 `01-java-kotlin/28-virtual-threads-pinning.md`(동작 원리와 핀닝)에 있다.

### "Hikari의 minimumIdle은 어떻게 잡나요?" (가산점 포인트)

HikariCP는 `minimumIdle`의 기본값을 `maximumPoolSize`와 **같게** 둔다. 즉 기본 동작은 **고정 크기 풀**이고, 이것이 공식 권장이기도 하다.

이유를 말할 수 있으면 좋다. 커넥션을 새로 여는 것은 TCP 핸드셰이크 + TLS + DB 인증이라 수십 ms가 드는 비싼 작업이다. 트래픽이 잠깐 줄었다고 커넥션을 닫아버리면, 다시 늘었을 때 **가장 바쁜 순간에 커넥션을 새로 여느라 응답시간이 튄다.** 풀을 고정 크기로 두면 그 지연이 애초에 발생하지 않는다.

`minimumIdle`을 낮추는 것이 의미 있는 경우는 3-4의 상황 — 인스턴스가 많아 DB의 `max_connections`가 빠듯할 때, 유휴 인스턴스가 커넥션을 붙들고 있지 않게 하려는 목적뿐이다. **"메모리 아끼려고" 낮추는 것은 얻는 것 없이 지연만 사는 선택이다.**

## 한 줄 요약

풀 크기는 Little's law(L = λ × W)로 자원별 점유 시간을 기준으로 계산한다 — 블로킹 MVC에서 톰캣 스레드는 전체 응답시간(100ms) 동안, Hikari 커넥션은 트랜잭션 구간(50ms) 동안만 묶이므로 500 TPS 서버에서 톰캣 50·커넥션 25라는 서로 다른 숫자가 나오고, 코어 수는 스레드 수의 기준이 아니라 CPU 연산 총량의 상한(요청당 5ms면 4코어 = 800 TPS)일 뿐이다. 계산값 L은 이용률 100%에 해당하므로 목표 이용률로 나눠 c = L/ρ로 여유를 만들되(ρ=0.7이면 1.43배 — 대기는 1/(1-ρ)로 폭발한다), 커넥션은 DB 쪽 상한 `(DB 코어 × 2) + spindle`과 앱 인스턴스 수를 곱한 총합에 다시 묶이며 둘 중 작은 쪽이 실질 상한이다. 그리고 자원은 연쇄로 묶여 있어 톰캣 200에 Hikari 10이면 서버 전체가 10/0.05 = 200 TPS에서 막히므로 풀 크기는 병목을 정하고 거기에 맞추는 것이고, 최종 숫자는 `hikaricp.connections.pending`(0 초과면 부족)과 `hikaricp.connections.usage`(실측 W)로 검증한다.
