# Bean 생명주기와 싱글턴 스코프 — 컨테이너의 기본 계약, 그리고 싱글턴에 상태를 두면 안 되는 이유

> 핵심 관전 포인트: **스프링 빈의 기본 스코프는 싱글턴이다 — 컨테이너당 인스턴스를 하나만 만들어 모든 요청 스레드가 그 하나를 공유한다. 생명주기는 "인스턴스화 → 의존성 주입 → 초기화 전 후처리 → 초기화 콜백(`@PostConstruct`) → 초기화 후 후처리(여기서 AOP 프록시가 씌워진다) → 사용 → 소멸 콜백(`@PreDestroy`)" 순서로 흐른다. 이 계약에서 곧바로 따라 나오는 결론이 있다. 싱글턴 빈의 인스턴스 필드는 사실상 전역 변수이므로, 거기에 요청별 상태를 담으면 여러 스레드가 같은 칸을 덮어쓰며 사용자 간 데이터가 섞인다 — 단일 사용자 테스트는 전부 통과하고 동시 접속에서만 터지는, 테스트로 못 잡는 버그의 전형이다. 그래서 싱글턴 빈이 필드로 가질 수 있는 것은 주입받은 불변 의존성과 설정값뿐이고, 요청마다 달라지는 데이터는 지역 변수와 메서드 파라미터로만 다룬다.**

---

## 0. 질문 + 의도

**질문**: "Bean의 생명주기와 기본 스코프(singleton)를 설명해주세요. 싱글턴 빈에 상태를 두면 왜 위험한가요?"

**출제 의도**: 싱글턴 빈의 인스턴스 필드에 요청별 상태를 둔 코드는 단일 사용자 테스트를 전부 통과하고 동시 접속에서만 데이터가 섞인다. 프레임워크의 기본 계약(빈 하나를 모든 스레드가 공유한다)을 아는지가 이런 "테스트로 못 잡는 버그"의 예방선이다.

*(이 문서의 서술은 Spring Boot 3.x / Spring Framework 6.x 기준이다. 애너테이션 패키지가 `javax.annotation`에서 `jakarta.annotation`으로 바뀐 것이 Boot 2.x와의 대표적 차이다.)*

## 1. Bean 생명주기 — 컨테이너가 대신 해주는 일의 순서

IoC의 요지가 "객체의 생성·소멸 주도권을 컨테이너에 넘긴다"였다면, 생명주기는 **컨테이너가 그 일을 정확히 어떤 순서로 해주는지에 대한 계약**이다. 순서를 아는 것이 왜 실무 문제인지는 1-3절에서 드러난다 — `@Transactional`이 안 먹는 대표적 상황이 이 순서에서 나오기 때문이다.

### 1-1. 일곱 단계

```text
[컨테이너 기동]
 1. 빈 정의 읽기      컴포넌트 스캔, @Configuration 파싱
                       -> "무엇을 만들지"에 대한 설계도만 등록. 아직 객체는 없다.
 2. 인스턴스화        생성자 호출로 실제 객체를 만든다
                       -> 생성자 주입은 이 단계에서 의존성이 함께 들어간다
 3. 의존성 주입        필드 주입·세터 주입은 여기서 값이 채워진다
                       -> 2단계와 3단계 사이에는 필드가 아직 null 인 순간이 있다
 4. 초기화 전 후처리   BeanPostProcessor.postProcessBeforeInitialization
 5. 초기화 콜백        @PostConstruct -> afterPropertiesSet() -> @Bean(initMethod)
 6. 초기화 후 후처리   BeanPostProcessor.postProcessAfterInitialization
                       ★ AOP 프록시가 씌워지는 지점 — @Transactional 이 작동하기 시작한다
                       -> 여기까지 끝난 객체가 컨테이너의 Map 에 보관되고,
                          다른 빈에게 주입되며 요청 처리에 쓰인다

[사용 — 애플리케이션 동작 중]

[컨테이너 종료]
 7. 소멸 콜백          @PreDestroy -> destroy() -> @Bean(destroyMethod)
```

정확히 하자면 4번과 5번은 완전히 별개의 단계가 아니다. `@PostConstruct`를 실제로 호출하는 주체가 `InitDestroyAnnotationBeanPostProcessor`라는 **후처리기**이고, 그것이 4단계(초기화 전 후처리) 안에서 애너테이션 붙은 메서드를 찾아 불러준다. 즉 스프링의 초기화 콜백 자체가 후처리기 메커니즘 위에 올라가 있다. 이 사실이 다음 절과 이어진다.

### 1-2. BeanPostProcessor가 무엇인가

도식에 갑자기 등장한 이 이름부터 정의하고 가자.

**`BeanPostProcessor`는 "빈이 만들어진 뒤 초기화 전후에 끼어들어, 그 빈을 손보거나 아예 다른 객체로 바꿔치기할 수 있는 확장 지점"이다.** 메서드가 두 개뿐인 인터페이스이고, 컨테이너는 **모든 빈 하나하나에 대해** 등록된 모든 후처리기의 두 메서드를 불러준다.

```java
public interface BeanPostProcessor {
    // 5단계(초기화 콜백) 직전에 불린다
    Object postProcessBeforeInitialization(Object bean, String beanName);

    // 5단계(초기화 콜백) 직후에 불린다
    Object postProcessAfterInitialization(Object bean, String beanName);
}
```

여기서 결정적인 것은 **반환 타입이 `void`가 아니라 `Object`** 라는 점이다. 후처리기는 받은 빈을 그대로 돌려줄 수도 있지만, **전혀 다른 객체를 돌려줄 수도 있다.** 컨테이너는 그 반환값을 최종 빈으로 채택한다. 창구에 제출한 서류를 담당자가 검토만 하고 돌려주는 게 아니라, **다른 서류로 바꿔서 돌려줄 수 있는 구조**인 셈이다.

이 "바꿔치기 가능"이 AOP의 작동 원리 전부다. 스프링 AOP의 후처리기(`AbstractAutoProxyCreator`)는 `postProcessAfterInitialization`에서 **원본 빈을 감싼 프록시를 만들어 원본 대신 반환한다.** 그래서 6단계가 "AOP 프록시가 씌워지는 지점"이 된다.

참고로 이름이 비슷한 `BeanFactoryPostProcessor`는 전혀 다른 것이다. 이쪽은 **객체가 만들어지기도 전에, 1단계의 빈 정의(설계도)를 고치는** 확장 지점이다. `${...}` 프로퍼티 치환이 대표적인 예다. **후처리 대상이 "완성된 객체"인가 "설계도"인가**로 구분하면 헷갈리지 않는다. (가산점 포인트)

### 1-3. 6단계가 왜 중요한가 — `@PostConstruct` 안에서는 `@Transactional`이 안 먹는다

이제 순서가 실무 사고로 이어지는 지점을 보자.

먼저 프록시가 무엇인지 다시 세운다. **프록시는 원본 객체인 척하면서 호출을 먼저 받아 부가 작업을 한 뒤 원본에 넘기는 대리인 객체다.** `@Transactional`이 붙은 서비스에 대해 컨테이너는 원본을 감싼 프록시를 만들고, 다른 빈에게 **원본이 아니라 프록시를 주입한다.**

```text
컨테이너가 다른 빈에게 건네주는 것은 프록시다.

  호출자 -> [OrderService 프록시]
                |  (1) 트랜잭션 시작 — 커넥션 획득, BEGIN
                |
                +--(2) 원본 인스턴스의 메서드 호출
                |          -> [OrderService 원본]   ← @PostConstruct 는 여기서 실행된다
                |
                <--(3) 정상 반환이면 COMMIT, 예외면 ROLLBACK
```

그런데 **`@PostConstruct`는 5단계에서 실행되고, 프록시는 6단계에서 만들어진다.** 순서상 `@PostConstruct`가 도는 시점에는 프록시가 이 세상에 아직 존재하지 않는다. 게다가 `@PostConstruct` 메서드 안의 `this`는 언제나 **원본 인스턴스**다. 원본이 자기 자신의 메서드를 부르면 프록시를 거치지 않으므로, 프록시가 있었더라도 어차피 가로챌 수 없다.

```java
@Service
public class ReportService {

    private final ReportRepository repository;

    public ReportService(ReportRepository repository) {
        this.repository = repository;
    }

    @PostConstruct
    void warmUp() {
        // 문제: 이 시점은 5단계다. 프록시는 6단계에서야 만들어지므로 아직 없다.
        //      게다가 this 로 부르는 순간 프록시를 거치지 않는다 — 이중으로 안 먹는다.
        //      결과적으로 loadAll() 은 트랜잭션 없이 실행되고,
        //      영속성 컨텍스트가 없으니 지연 로딩 접근에서 LazyInitializationException 이 나거나
        //      쿼리마다 커넥션을 따로 잡았다 놓는 형태가 된다.
        loadAll();
    }

    @Transactional
    public void loadAll() { /* ... */ }
}
```

고치는 방법은 두 가지다.

```java
// 고침 1: 기동이 "완료된 뒤"로 미룬다.
// ApplicationReadyEvent 는 모든 빈이 만들어지고 프록시까지 씌워진 뒤 발행되므로,
// 이 시점에는 self 필드에 담긴 것도 프록시이고 다른 빈도 전부 프록시다.
@Component
public class ReportWarmUpRunner {

    private final ReportService reportService;   // 주입받은 것 = 프록시

    public ReportWarmUpRunner(ReportService reportService) {
        this.reportService = reportService;
    }

    @EventListener(ApplicationReadyEvent.class)
    void warmUp() {
        reportService.loadAll();   // 프록시를 거치므로 트랜잭션이 정상 적용된다
    }
}
```

```java
// 고침 2: 초기화 로직을 별도 빈으로 분리해 그 빈을 주입받아 호출한다.
// 핵심은 같다 — "자기 자신을 부르지 말고, 주입받은 프록시를 통해 부른다".
```

**"`@PostConstruct` 안에서 자기 트랜잭션 메서드를 부르면 트랜잭션이 적용되지 않는다"** 는 사실을 생명주기 6단계와 연결해 설명할 수 있으면, 순서를 외운 게 아니라 이해한 것으로 읽힌다. (가산점 포인트)

### 1-4. 초기화 로직은 생성자가 아니라 `@PostConstruct`에

순서가 알려주는 두 번째 실무 지침이다. **필드 주입이나 세터 주입을 쓰는 클래스는 생성자 실행 시점(2단계)에 의존성이 아직 비어 있다.** 주입은 3단계에서 일어나기 때문이다.

```java
// 문제: 필드 주입 + 생성자에서 의존성 사용
@Service
public class CacheService {
    @Autowired
    private RedisTemplate<String, String> redis;   // 3단계에서 채워진다

    public CacheService() {
        redis.opsForValue().set("warm", "1");      // 2단계 — redis 는 아직 null. NPE.
    }
}

// 고침: 주입 완료가 보장된 뒤(5단계)에 실행되는 콜백으로 옮긴다
@Service
public class CacheService {
    @Autowired
    private RedisTemplate<String, String> redis;

    @PostConstruct
    void warmUp() {
        redis.opsForValue().set("warm", "1");      // 5단계 — 주입이 끝났음이 보장된다
    }
}
```

다만 생성자 주입을 쓰면 2단계에서 이미 의존성이 손에 들어와 있으므로 이 함정 자체가 사라진다. 그래서 **"단순한 값 검증이나 방어적 복사 정도는 생성자에서 해도 되고, 주입받은 빈을 호출하는 초기화는 `@PostConstruct`에 둔다"** 가 실용적인 기준이다. 트랜잭션이 필요한 초기화라면 1-3절의 이유로 `ApplicationReadyEvent`까지 미룬다.

### 1-5. 소멸 콜백 — 자원을 반납하는 자리

`@PreDestroy`는 **컨테이너가 그 빈의 관리를 끝내는 시점**에 불린다. 커넥션 풀 반납, 직접 만든 스레드 풀의 `shutdown()`, 열어둔 파일 핸들 정리 같은 것을 여기에 둔다.

실무에서 함께 짚어야 하는 것이 **graceful shutdown**이다. 종료 신호를 받은 즉시 프로세스를 끊으면 처리 중이던 요청이 잘려 나가므로, 새 요청 수신은 멈추되 진행 중인 요청은 마치도록 유예를 주는 방식이다. Spring Boot에서는 `server.shutdown=graceful` 설정으로 켠다. 이 유예가 끝난 뒤에야 컨테이너가 닫히고 소멸 콜백이 돈다.

한 가지 예외를 기억해 둘 것 — **프로토타입 스코프 빈에는 소멸 콜백이 불리지 않는다.** 이유는 2-4절에서 다룬다.

## 2. 스코프 — 기본은 싱글턴, 그런데 왜 싱글턴인가

**스코프는 "빈 인스턴스를 몇 개 만들고 언제까지 살려둘 것인가"의 규칙이다.**

| 스코프 | 인스턴스 수 | 특징 |
|---|---|---|
| `singleton` | 컨테이너당 1개 | **기본값.** 기동 시 미리 만들어 둔다 |
| `prototype` | 주입·조회할 때마다 새로 | 소멸 콜백을 컨테이너가 안 불러준다 |
| `request` | HTTP 요청당 1개 | 웹 환경 전용 |
| `session` | HTTP 세션당 1개 | 웹 환경 전용 |

### 2-1. 기본이 싱글턴인 이유

서비스·리포지토리 같은 빈은 **로직(코드)만 담고 데이터를 담지 않는 것이 전제**다. 그렇다면 요청마다 새로 만들 이유가 없다. 같은 코드를 담은 객체를 초당 수천 개씩 새로 만들고 버리는 것은 순수한 낭비이기 때문이다.

인스턴스를 하나만 두면 세 가지가 따라온다.

첫째, **객체 생성 비용과 GC 부담이 사라진다.** 초당 1,000 요청이 들어오고 요청 하나가 서비스·리포지토리·컨버터 등 빈 10개를 거친다면, 프로토타입이었다면 초당 10,000개의 객체가 만들어졌다 버려진다. 싱글턴에서는 0개다.

둘째, **의존성 문제가 기동 시점에 드러난다.** 싱글턴 빈은 기본적으로 기동 중에 미리 만들어지므로(eager initialization), 주입할 빈이 없거나 순환 참조가 있으면 **애플리케이션이 아예 뜨지 않는다.** 배포 후 특정 요청이 들어와야 터지는 것보다 훨씬 싼 실패다.

셋째, **프록시를 한 번만 씌우면 된다.** AOP 프록시 생성은 클래스 단위로 바이트코드를 만들어내는 비싼 작업이라, 요청마다 반복할 일이 아니다.

비유하면 싱글턴 빈은 **은행 창구의 직원**이다. 직원(빈)은 한 명인데 손님(요청)은 계속 바뀐다. 직원이 업무 절차(로직)만 기억하고 있으면 아무 문제가 없다. 그런데 "방금 손님의 계좌번호"를 자기 수첩(인스턴스 필드)에 적어두고 다음 손님 응대에 그대로 쓰면 사고가 난다. 3절 전체가 이 비유의 각주다.

### 2-2. 스프링의 싱글턴은 GoF 싱글턴 패턴이 아니다

용어가 같아서 자주 섞이는 지점이다.

**GoF 싱글턴 패턴**은 생성자를 `private`으로 막고 `static` 필드에 인스턴스를 하나 두어, **클래스 차원에서 두 번째 인스턴스를 만들 수 없게** 강제하는 코드 기법이다. 클래스 자체가 오염된다 — 상속도 어렵고, 테스트에서 갈아 끼우기도 어렵고, `static` 상태가 테스트 간에 새어 나간다.

**스프링의 싱글턴**은 그냥 **"이 빈 정의당 컨테이너가 인스턴스를 하나만 만들어 재사용한다"** 는 컨테이너의 관리 정책이다. 클래스는 평범한 자바 클래스 그대로이고, 누구든 `new OrderService(...)`로 얼마든지 더 만들 수 있다. 테스트에서 `new`로 만들어 쓰는 것이 아무 문제가 안 되는 이유가 여기 있다.

정리하면 **스프링은 코드를 싱글턴 패턴으로 오염시키지 않고도 싱글턴의 이점(재사용)만 가져가는 방식**이다. 덧붙여 "컨테이너당 1개"이므로, 한 JVM에 컨테이너가 둘 뜨면(테스트 컨텍스트 여러 개 등) 인스턴스도 둘이다. (가산점 포인트)

### 2-3. 그럼 상태가 필요하면 프로토타입을 쓰면 되나?

3절을 읽고 나면 자연스럽게 드는 의문이다. "요청마다 새 인스턴스면 상태를 필드에 둬도 안전한 것 아닌가?"

**대부분의 경우 이 답은 함정이다.** 이유가 둘이다.

첫째, **싱글턴이 프로토타입 빈을 주입받으면 프로토타입의 의미가 사라진다.** 이것이 핵심 함정이다.

```java
// 문제: 프로토타입 빈을 싱글턴 빈의 필드로 주입받았다
@Component
@Scope("prototype")
public class OrderContext {          // 요청별 상태를 담으려고 프로토타입으로 만들었다
    private Order order;
    public void setOrder(Order o) { this.order = o; }
    public Order getOrder() { return order; }
}

@Service                              // 이 빈은 싱글턴이다
public class OrderService {

    private final OrderContext context;   // 주입은 "기동 시 딱 한 번" 일어난다

    public OrderService(OrderContext context) {
        this.context = context;           // 여기서 받은 그 인스턴스를 영원히 들고 있는다
    }

    public void process(OrderRequest request) {
        context.setOrder(createOrder(request));   // 모든 스레드가 같은 인스턴스를 덮어쓴다
        pay(context.getOrder());
    }
}
```

왜 이렇게 되는지 시점으로 보면 분명하다.

```text
[기동 시점 — 딱 한 번]
  컨테이너: OrderService 를 만들자 -> 생성자에 OrderContext 가 필요하다
            -> 프로토타입이니 새 인스턴스 #1 을 만들어 넘긴다
            -> OrderService 의 context 필드 = 인스턴스 #1  (여기서 끝. 다시는 안 바뀐다)

[운영 중 — 요청 1,000건]
  요청 1 -> OrderService.process() -> context(#1) 에 쓴다
  요청 2 -> OrderService.process() -> context(#1) 에 쓴다   ← 같은 인스턴스
  요청 3 -> OrderService.process() -> context(#1) 에 쓴다   ← 같은 인스턴스
  ...
  "쓸 때마다 새 인스턴스" 라는 의도가 조용히 깨진다.
  결국 3절의 데이터 섞임 문제가 그대로 재현된다 — 필드가 한 단계 밖으로 옮겨졌을 뿐이다.
```

**프로토타입은 "주입할 때마다 새로"이지 "사용할 때마다 새로"가 아니다.** 그리고 싱글턴에 대한 주입은 기동 시 한 번뿐이다.

정말 사용 시점마다 새 인스턴스를 받아야 한다면 방법은 셋이다.

```java
// 방법 1: ObjectProvider — 사용하는 순간에 컨테이너에서 꺼낸다
@Service
public class OrderService {
    private final ObjectProvider<OrderContext> contextProvider;

    public OrderService(ObjectProvider<OrderContext> contextProvider) {
        this.contextProvider = contextProvider;   // 주입되는 것은 "꺼내는 도구"이지 인스턴스가 아니다
    }

    public void process(OrderRequest request) {
        OrderContext context = contextProvider.getObject();   // 호출할 때마다 새 인스턴스
        // 게다가 이 참조는 지역 변수이므로 스레드마다 독립이다 — 섞일 수가 없다
    }
}
```

- **방법 2: `@Lookup` 메서드 주입.** 추상 메서드에 `@Lookup`을 붙이면 스프링이 그 메서드 구현을 대신 만들어 매 호출마다 새 빈을 돌려준다.
- **방법 3: 스코프 프록시.** `@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)`로 두면 주입되는 것이 프록시이고, 그 프록시가 호출 시점에 실제 빈을 찾아 위임한다.

둘째 이유는 더 근본적이다. **애초에 상태를 필드에 둘 필요가 없는 경우가 대부분이다.** 위 예시의 `OrderContext`도 그냥 메서드 파라미터로 넘기면 그만이다. 프로토타입은 "상태를 필드에 두고 싶다"는 요구의 해법이 아니라, "생성 비용이 있고 재사용하면 안 되는 객체(예: 상태를 가진 빌더)를 컨테이너가 만들어 주기를 바란다"는 드문 요구의 해법이다.

### 2-4. 프로토타입 빈에 소멸 콜백이 안 불리는 이유

컨테이너는 **프로토타입 빈을 만들어 건네준 뒤 그 인스턴스를 추적하지 않는다.** 몇 개를 만들었는지, 지금 누가 들고 있는지, 언제 버려지는지를 기록하지 않는다는 뜻이다. 추적하지 않으니 `@PreDestroy`를 불러줄 대상 목록도 없다.

그래서 프로토타입 빈이 커넥션이나 파일 핸들 같은 자원을 쥐고 있다면 **정리는 그것을 받아 쓴 쪽의 책임**이다. `try-with-resources`로 감싸거나, 명시적으로 닫는 코드를 직접 넣어야 한다. 컨테이너가 알아서 해줄 것이라 믿고 두면 자원이 새어 나간다.

## 3. 싱글턴에 상태를 두면 왜 위험한가 — 요청은 여럿, 빈은 하나

### 3-1. 전제 — 요청마다 스레드가 붙는다

톰캣 같은 서블릿 컨테이너는 **요청 하나에 스레드 하나를 배정**해 처리한다. 스레드는 매번 새로 만드는 게 아니라 미리 만들어 둔 풀에서 꺼내 쓰고 돌려준다. Spring Boot의 내장 톰캣은 이 풀 크기가 기본 200(`server.tomcat.threads.max`)이다.

즉 **최대 200개의 스레드가 동시에 같은 서비스 빈의 메서드 안을 돌아다닌다.** 그런데 그 빈은 싱글턴이라 딱 하나다.

```text
  [톰캣 스레드 풀 — 최대 200개]
   http-nio-8080-exec-1  ─┐
   http-nio-8080-exec-2  ─┤
   http-nio-8080-exec-3  ─┼──▶  [ OrderService 인스턴스 1개 ]  ← 힙에 하나뿐이다
        ...              ─┤
   http-nio-8080-exec-200 ─┘
```

여기서 결론이 하나 나온다. **싱글턴 빈의 인스턴스 필드는 모든 동시 요청이 함께 쓰는 전역 변수와 같다.**

### 3-2. before — 요청별 상태를 필드에 담은 코드

```java
// before: 싱글턴 빈에 요청별 상태 — 동시 접속에서 데이터가 섞인다
@Service
public class OrderService {

    private Order currentOrder;   // 모든 스레드가 공유하는 단 한 칸

    public void process(OrderRequest request) {
        this.currentOrder = createOrder(request);   // ① 자기 주문을 이 칸에 넣는다
        validate();                                 // ② 이 사이에 다른 스레드가 칸을 덮어쓴다
        pay(this.currentOrder);                     // ③ 다시 읽으면 남의 주문이 나온다
    }
}
```

코드만 보면 지극히 자연스러워 보인다는 것이 이 버그의 성질이다. 한 줄씩 읽으면 논리에 아무 잘못이 없다. **문제는 "이 메서드가 동시에 여러 번 실행된다"는 사실이 코드 어디에도 적혀 있지 않다**는 것이다.

### 3-3. 두 스레드가 같은 칸을 밟는 타임라인

이 문서에서 가장 중요한 그림이다. 사용자 1의 요청(스레드 A)과 사용자 2의 요청(스레드 B)이 거의 동시에 들어왔다고 하자.

```text
힙에 있는 OrderService 인스턴스는 단 하나이고,
그 안의 currentOrder 필드도 단 한 칸이다. 두 스레드가 이 한 칸을 같이 밟는다.

 시각   스레드 A (사용자 1의 요청)         currentOrder 필드     스레드 B (사용자 2의 요청)
 ────────────────────────────────────────────────────────────────────────────────────
 t1     currentOrder = 주문#1  ──────▶   [  주문#1  ]
                                                                (아직 도착 전)
 t2     validate() 실행 중                [  주문#1  ]           요청 도착
 t3                                       [  주문#2  ]  ◀──────  currentOrder = 주문#2
                                            ↑ A가 넣어둔 주문#1이 사라졌다
 t4     pay(currentOrder) ◀──── 읽음      [  주문#2  ]           validate() 실행 중
          ↑ 사용자 1의 요청인데 사용자 2의 주문#2가 결제된다
 t5                                       [  주문#2  ]  ──────▶  pay(currentOrder) 읽음
                                                                   ↑ 주문#2가 두 번째로 결제된다
 ────────────────────────────────────────────────────────────────────────────────────
 결과: 주문#1 은 결제되지 않았고, 주문#2 는 두 번 결제됐다.
       사용자 1의 응답 화면에는 사용자 2의 주문 정보가 담겨 나간다.
```

t3에서 벌어진 일을 다시 짚자. **B의 쓰기가 A의 값을 지운 것이 아니라 덮어쓴 것**이고, A는 그 사실을 알 방법이 없다. A 입장에서는 자기가 t1에 넣은 값을 t4에 읽었을 뿐이다. 값이 바뀌었다는 신호는 어디에도 없다.

피해가 어디까지 가는지도 봐두자.

- **금전 사고**: 사용자 1은 결제되지 않았는데 성공 화면을 보고, 사용자 2는 두 번 결제된다.
- **개인정보 사고**: 응답에 남의 주문 정보(수령인 이름, 주소, 연락처)가 실려 나간다. "내 주문 내역에 모르는 사람 정보가 보인다"는 유형의 사고가 정확히 이것이다.
- **재현 불가 장애**: t1~t4 사이에 다른 스레드가 끼어들어야만 발생하므로, 같은 코드가 대부분의 요청에서는 멀쩡히 돈다.

### 3-4. 왜 테스트로 못 잡는가

이 버그가 특별히 위험한 이유는 **우리가 가진 모든 검증 수단이 단일 스레드**라는 데 있다.

| 검증 수단 | 실행 형태 | 이 버그를 잡는가 |
|---|---|---|
| 단위 테스트 | 스레드 1개가 순차 실행 | 못 잡음 |
| `@SpringBootTest` 통합 테스트 | 대개 스레드 1개가 순차 호출 | 못 잡음 |
| QA 수동 테스트 | 사람 한 명이 클릭 | 못 잡음 |
| 코드 리뷰 | 사람이 읽음 | **여기서만 잡힌다** |
| 운영 | 동시 접속 | 간헐적으로 터짐 |

t1~t4 사이의 아주 좁은 창에 다른 스레드가 정확히 끼어들어야 재현되므로, 부하 테스트를 돌려도 안 나올 수 있다. 그리고 **터졌을 때조차 원인 추적이 어렵다.** 로그에는 "사용자 1의 요청이 주문#2를 결제했다"는 결과만 남고, 그렇게 된 경위는 어디에도 기록되지 않기 때문이다.

**결국 이 유형은 "발견해서 고치는" 버그가 아니라 "구조적으로 발생 불가능하게 만드는" 버그다.** 그래서 프레임워크의 기본 계약을 아는 것이 곧 예방선이 된다.

### 3-5. after — 상태를 스택으로 옮긴다

```java
// after: 상태를 필드가 아니라 지역 변수/파라미터로 — 무상태(stateless) 설계
@Service
public class OrderService {

    private final PaymentGateway gateway;   // 불변 의존성. 모두가 읽기만 하므로 공유해도 안전하다

    public OrderService(PaymentGateway gateway) {
        this.gateway = gateway;
    }

    public void process(OrderRequest request) {
        Order order = createOrder(request);   // 지역 변수 = 스레드마다 자기 스택에 따로 생긴다
        validate(order);                      // 상태는 필드에 두지 말고 파라미터로 흘려보낸다
        gateway.pay(order);                   // 다른 스레드가 이 order 를 볼 방법이 아예 없다
    }
}
```

왜 이것으로 문제가 사라지는지는 메모리 구조를 보면 즉시 납득된다.

```text
[힙 — 모든 스레드가 공유하는 영역]
   OrderService 인스턴스 (1개)
     gateway : PaymentGateway   ← final, 아무도 바꾸지 않는다. 읽기만 하니 경합이 없다.

[스택 — 스레드마다 하나씩, 남이 접근할 수 없는 영역]
   스레드 A 의 스택              스레드 B 의 스택
     order = 주문#1                order = 주문#2
     ↑ B는 이 칸의 존재조차 모른다   ↑ A도 마찬가지다
```

**지역 변수는 각 스레드의 스택 프레임에 만들어지고, 스택은 스레드 전용 공간이다.** 다른 스레드가 물리적으로 접근할 수 없으므로 섞일 여지가 없다. 락도 동기화도 필요 없는 이유가 이것이다.

원칙 한 줄로 정리하면 이렇다. **싱글턴 빈이 가질 수 있는 필드는 불변인 것(주입받은 의존성, 설정값)뿐이고, 요청마다 달라지는 데이터는 지역 변수와 메서드 파라미터로만 다룬다.**

### 3-6. 고전 사례 — `SimpleDateFormat`을 필드로 둔 코드

직접 상태를 넣지 않았는데도 같은 사고가 나는 경우가 있다. **내부에 상태를 가진 객체를 필드로 뒀을 때**다.

```java
// before: SimpleDateFormat 은 스레드 안전하지 않다
@Service
public class SettlementService {
    // 매번 new 하기 아까워서 필드로 뺐다 — 흔하고 자연스러운 최적화처럼 보인다
    private final SimpleDateFormat format = new SimpleDateFormat("yyyy-MM-dd");

    public Date parse(String text) throws ParseException {
        return format.parse(text);   // 내부 Calendar 를 두 스레드가 함께 밟는다
    }
}
```

`final`을 붙였는데도 안전하지 않다는 점이 중요하다. `final`이 막아주는 것은 **참조를 다른 객체로 바꾸는 것**이지, **그 객체 내부의 상태가 바뀌는 것**이 아니다. `SimpleDateFormat`은 파싱 도중의 중간 결과를 자기 내부 `Calendar` 필드에 담아두고 쓰기 때문에, 두 스레드가 동시에 `parse()`를 부르면 엉뚱한 날짜가 나오거나 `NumberFormatException`이 터진다. 3-3절의 타임라인과 정확히 같은 구조가 라이브러리 안쪽에서 벌어지는 것이다.

```java
// after: DateTimeFormatter 는 불변이라 공유해도 안전하다
@Service
public class SettlementService {
    private final DateTimeFormatter format = DateTimeFormatter.ofPattern("yyyy-MM-dd");

    public LocalDate parse(String text) {
        return LocalDate.parse(text, format);   // 파싱 중간 상태를 포맷터에 담지 않는다
    }
}
```

여기서 얻을 일반 규칙은 이것이다. **어떤 객체를 싱글턴 빈의 필드로 두기 전에 "이 객체가 내부에 변경되는 상태를 갖는가"를 확인해야 한다.** `final`은 그 질문에 답해주지 않는다. (가산점 포인트)

## 4. 꼬리질문 대비 포인트

### "그럼 스프링은 `synchronized` 하나 없이 어떻게 안전한가요?"

**스프링이 안전하게 만들어주는 것이 아니다.** 빈을 무상태로 설계하는 것이 개발자와 프레임워크 사이의 **계약**이고, 스프링은 그 계약이 지켜졌다는 전제 위에서 인스턴스를 하나만 만들어 공유하는 것이다. 계약을 어기면 3절의 사고가 그대로 난다.

구조로 보면 이렇다. 공유되는 것은 불변 의존성뿐이고 변하는 데이터는 각 스레드의 스택에만 있으므로, **경합할 대상 자체가 존재하지 않는다.**

이 점이 중요한 이유는, 만약 상태를 공유해야만 했다면 `synchronized`를 걸어 해결하는 것이 **답이 아니기 때문**이다. 서비스 메서드 전체에 락을 걸면 동시 처리량이 1로 떨어져 200개 스레드가 줄을 선다. **동기화가 필요 없는 것이 아니라, 동기화가 필요 없는 구조를 강제하는 것**이 싱글턴 + 무상태 조합의 설계 의도다.

### "정말 상태가 필요하면 어떤 선택지가 있나요?" (시니어 변별 포인트)

요구사항의 단위에 따라 도구가 다르고, 각각 대가가 있다.

**1. 지역 변수·파라미터로 재구성 — 첫 번째 답은 언제나 이것이다.** 실무에서 "상태가 꼭 필요하다"고 느껴지는 경우의 대부분은 메서드를 쪼개다가 값을 넘기기 귀찮아진 상황이지, 진짜 요구가 아니다. 값을 파라미터로 넘기거나, 그 값들을 묶은 컨텍스트 객체를 만들어 메서드 인자로 흘려보내면 해결된다.

**2. `request` 스코프 빈 — 요청 단위 상태.** 요청 하나가 여러 계층을 거치며 공유해야 하는 컨텍스트에 쓴다. 주의점은 **싱글턴 빈이 요청 스코프 빈을 그냥 주입받으면 2-3절과 같은 문제가 생긴다**는 것이다. 기동 시점에는 처리 중인 HTTP 요청이 없으므로 주입할 대상 자체가 없다. 그래서 `proxyMode = ScopedProxyMode.TARGET_CLASS`로 프록시를 주입받고, 그 프록시가 호출 시점에 현재 요청에 묶인 실제 빈을 찾아 위임하게 한다.

**3. `ThreadLocal` — 스레드 단위 상태.** 스프링 시큐리티의 `SecurityContextHolder`가 이 방식으로 현재 인증 정보를 들고 있다. 대가가 둘이다. 첫째, **톰캣은 스레드를 풀에서 재사용하므로 요청이 끝날 때 `remove()`를 안 하면 다음 요청에 이전 사용자의 값이 그대로 남는다** — 인증 정보에서 이 실수가 나면 곧바로 계정 도용 수준의 사고다. 둘째, `@Async`나 별도 스레드 풀로 넘어가는 경계에서는 값이 전파되지 않아 그쪽에서는 비어 있다.

**4. 진짜 공유 상태(카운터, 로컬 캐시).** 여기서만 동시성 도구를 의도적으로 쓴다 — `AtomicLong`, `ConcurrentHashMap` 등. 다만 **서버를 여러 대로 늘리는 순간 인스턴스마다 값이 갈라진다**는 한계를 함께 말해야 한다. 서버별 카운터 합이 전체 카운트가 아니게 되므로, 정확한 값이 필요하면 Redis 같은 외부 저장소로 빼는 것까지 검토한다.

덧붙이면 좋은 최신 맥락 하나. Spring Boot 3.2부터 `spring.threads.virtual.enabled=true`로 요청을 가상 스레드에서 처리할 수 있는데, 가상 스레드는 요청마다 새로 만들어지고 풀에서 재사용되지 않으므로 `ThreadLocal`의 "지우는 것을 잊어 다음 요청에 새어 나가는" 위험은 줄어든다. 반면 **싱글턴 빈 필드 공유 문제는 조금도 달라지지 않는다** — 스레드가 무엇이든 인스턴스는 여전히 하나이기 때문이다. (가산점 포인트)

### "프로토타입 빈은 왜 소멸 콜백이 안 불리나요? 실무에서 뭘 조심해야 하죠?"

컨테이너는 프로토타입 인스턴스를 **만들어 넘겨준 시점에 관리를 끝낸다.** 몇 개를 만들었고 누가 들고 있는지 추적하지 않으므로 `@PreDestroy`를 호출할 대상 목록 자체가 없다.

실무에서 조심할 것은 **자원을 쥔 프로토타입 빈**이다. 파일 핸들이나 커넥션을 열어두는 객체를 프로토타입으로 만들어 놓고 컨테이너가 닫아줄 것이라 기대하면 자원이 그대로 샌다. 정리 책임은 그것을 받아 쓴 코드에 있으므로, `try-with-resources`나 명시적 `close()`를 직접 넣어야 한다.

여기에 2-3절을 얹으면 답이 완성된다. **프로토타입은 "주입할 때마다 새로"이지 "사용할 때마다 새로"가 아니므로**, 싱글턴에 주입하면 인스턴스가 하나로 고정된다. 사용 시점마다 새로 받으려면 `ObjectProvider`, `@Lookup`, 스코프 프록시 중 하나를 써야 한다.

### "`@PostConstruct`와 생성자의 차이는 뭐고, 초기화 로직은 어디에 두나요?"

시점이 다르다. **생성자는 2단계(인스턴스화), `@PostConstruct`는 5단계(초기화 콜백)** 에서 실행된다.

그래서 판단 기준이 이렇게 갈린다.

- **필드/세터 주입을 쓰는 클래스**라면 생성자 시점에 의존성이 아직 비어 있으므로(3단계 전), 주입받은 빈을 사용하는 초기화는 반드시 `@PostConstruct`에 둔다.
- **생성자 주입을 쓰는 클래스**라면 생성자 시점에 이미 의존성이 들어와 있으므로, 값 검증이나 방어적 복사 같은 가벼운 작업은 생성자에서 해도 된다.
- **트랜잭션이 필요한 초기화**라면 둘 다 안 된다. `@PostConstruct` 시점(5단계)에도 AOP 프록시는 아직 없고(6단계), `this`로 부르면 프록시를 거치지도 않는다. `ApplicationReadyEvent` 리스너로 미뤄 기동이 완전히 끝난 뒤 주입받은 프록시를 통해 호출한다.

마지막 항목을 생명주기 단계 번호와 함께 설명할 수 있으면, 순서를 외운 것이 아니라 이해한 것으로 읽힌다.

## 한 줄 요약

스프링 빈은 "컨테이너가 인스턴스화 → 주입 → 초기화 콜백 → 프록시 씌우기 → 소멸까지 대신 관리하고, 기본은 컨테이너당 1개(싱글턴)를 모든 스레드가 공유한다"는 계약 위에 있다 — 그래서 싱글턴 빈은 불변 의존성만 필드로 갖고 요청별 상태는 지역 변수와 파라미터(스레드 전용 스택)로만 다루는 무상태 설계가 원칙이며, 이를 어긴 코드는 단위·통합·QA 테스트를 전부 통과한 뒤 운영의 동시 접속에서만 사용자 데이터가 섞이는, 코드 리뷰 말고는 잡을 수단이 없는 사고를 낸다.
