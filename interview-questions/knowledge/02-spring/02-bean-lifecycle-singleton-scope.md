# Bean 생명주기와 싱글턴 스코프 — 컨테이너의 기본 계약, 그리고 싱글턴에 상태를 두면 안 되는 이유

> 핵심 관전 포인트: **스프링 빈의 기본 스코프는 싱글턴 — 컨테이너당
> 인스턴스를 하나만 만들어 모든 요청(스레드)이 공유한다. 생명주기는
> "인스턴스화 → 의존성 주입 → 초기화 콜백(`@PostConstruct`) → 사용 →
> 소멸 콜백(`@PreDestroy`)" 순서다. 그래서 싱글턴 빈의 인스턴스 필드에
> 요청별 상태를 두면 여러 스레드가 같은 필드를 동시에 읽고 써서
> 사용자 간 데이터가 섞인다 — 단일 사용자 테스트는 전부 통과하고
> 동시 접속에서만 터지는, 테스트로 못 잡는 버그의 전형이다.**

---

## 0. 질문 + 의도

**질문**: "Bean의 생명주기와 기본 스코프(singleton)를 설명해주세요.
싱글턴 빈에 상태를 두면 왜 위험한가요?"

**출제 의도**: 싱글턴 빈의 인스턴스 필드에 요청별 상태를 둔 코드는
단일 사용자 테스트를 전부 통과하고 동시 접속에서만 데이터가 섞인다.
프레임워크의 기본 계약(빈 하나를 모든 스레드가 공유한다)을 아는지가
이런 "테스트로 못 잡는 버그"의 예방선이다.

## 1. Bean 생명주기 — 컨테이너가 대신 해주는 일의 순서

IoC의 핵심이 "객체의 생성·소멸 주도권을 컨테이너에 넘긴다"였다면,
생명주기는 **컨테이너가 그 일을 어떤 순서로 하는지**의 계약이다.

```text
[컨테이너 기동]
 1. 빈 정의 읽기        — 컴포넌트 스캔, @Configuration 파싱
 2. 인스턴스화           — 생성자 호출 (생성자 주입은 여기서 함께)
 3. 의존성 주입          — 필드/세터 주입은 이 단계에서
 4. 초기화 전 후처리     — BeanPostProcessor.postProcessBeforeInitialization
 5. 초기화 콜백          — @PostConstruct → afterPropertiesSet() → @Bean(initMethod)
 6. 초기화 후 후처리     — postProcessAfterInitialization ← AOP 프록시가 씌워지는 지점
[사용 — 애플리케이션 동작 중]
[컨테이너 종료]
 7. 소멸 콜백            — @PreDestroy → destroy() → @Bean(destroyMethod)
```

실무에서 이 순서가 중요해지는 지점 두 가지:

- **초기화 로직은 생성자가 아니라 `@PostConstruct`에** — 필드/세터
  주입을 쓰는 클래스라면 생성자 실행 시점에는 아직 의존성이 비어 있다
  (3단계 전). `@PostConstruct`는 주입 완료를 보장받은 뒤 실행된다.
- **AOP 프록시는 초기화 이후에 씌워진다** — `@Transactional`,
  `@Cacheable` 같은 기능이 `BeanPostProcessor`가 만든 프록시 위에서
  동작한다는 사실이 생명주기의 6단계에 해당한다. 그래서
  `@PostConstruct` 안에서 자기 트랜잭션 메서드를 호출하면 트랜잭션이
  적용되지 않을 수 있다. (가산점 포인트)

소멸 콜백은 **컨테이너가 관리를 끝내는 시점**(graceful shutdown 등)에
불린다. 커넥션풀 반납, 스레드풀 종료 같은 자원 정리를 여기에 둔다.

## 2. 스코프 — 기본은 싱글턴, 그리고 왜 싱글턴인가

스코프는 "빈 인스턴스를 **몇 개 만들고 언제까지 살려두는가**"의 규칙이다.

| 스코프         | 인스턴스 수        | 비고                          |
|-------------|---------------|-----------------------------|
| `singleton` | 컨테이너당 1개      | **기본값.** 기동 시 미리 생성          |
| `prototype` | 요청(주입/조회)마다 새로 | 소멸 콜백을 컨테이너가 안 불러줌       |
| `request`   | HTTP 요청당 1개    | 웹 환경 전용                      |
| `session`   | HTTP 세션당 1개    | 웹 환경 전용                      |

기본이 싱글턴인 이유는 단순하다. 서비스·리포지토리 같은 빈은
**로직(코드)만 담고 상태를 안 담는 것이 전제**라서, 매 요청마다 새로
만들 이유가 없다. 인스턴스 하나를 재사용하면 객체 생성·GC 비용이
사라지고, 컨테이너 기동 시점에 미리 만들어두므로 의존성 문제
(주입 누락, 순환 참조)도 기동 시점에 드러난다.

- 비유: 싱글턴 빈은 **은행 창구의 직원**이다. 직원(빈)은 한 명인데
  손님(요청)은 계속 바뀐다. 직원이 업무 절차(로직)만 기억하면 문제가
  없지만, "아까 손님의 계좌번호"를 자기 수첩(인스턴스 필드)에 적어두고
  다음 손님에게 그대로 쓰면 사고가 난다.

주의할 것: 스프링의 싱글턴은 **GoF 싱글턴 패턴(클래스당 1개,
`private` 생성자 + `static` 인스턴스)이 아니다.** 컨테이너가 "이
빈 정의당 1개"를 보장해주는 것뿐이고, `new`로 얼마든지 더 만들 수
있다. 스프링이 이렇게 관리해주는 덕에 코드를 싱글턴 패턴으로 오염시키지
않고도 싱글턴의 이점을 얻는다. (가산점 포인트)

## 3. 싱글턴에 상태를 두면 왜 위험한가 — 요청은 여럿, 빈은 하나

톰캣 같은 서블릿 컨테이너는 **요청마다 스레드를 배정**한다.
그런데 그 스레드들이 호출하는 서비스 빈은 **한 개**다.
즉 싱글턴 빈의 인스턴스 필드는 **모든 동시 요청이 공유하는 전역 변수**와 같다.

```java
// Before: 싱글턴 빈에 요청별 상태 — 동시 접속에서 데이터가 섞인다
@Service
public class OrderService {

    private Order currentOrder;   // ← 모든 스레드가 공유하는 필드!

    public void process(OrderRequest request) {
        this.currentOrder = createOrder(request);  // ① A가 자기 주문을 저장
        validate();                                 // ② 그 사이 B가 필드를 덮어씀
        pay(this.currentOrder);                     // ③ A가 B의 주문을 결제!
    }
}
```

시간 순서로 보면:

```text
스레드 A: currentOrder = A의 주문
스레드 B: currentOrder = B의 주문   ← A의 값을 덮어씀
스레드 A: pay(currentOrder)          ← B의 주문이 결제됨 (데이터 섞임)
```

이 버그의 진짜 무서운 점은 **테스트로 잡히지 않는다**는 것이다.
단위 테스트도, 혼자 하는 통합 테스트도, QA의 수동 테스트도 전부
단일 스레드라서 항상 통과한다. 동시 접속이 있는 운영에서만, 그것도
간헐적으로만 재현된다. "내 정보 페이지에 다른 사람 정보가 보인다"는
개인정보 사고로 이어지는 유형이다.

```java
// After: 상태를 필드가 아니라 지역 변수/파라미터로 — stateless
@Service
public class OrderService {

    private final PaymentGateway gateway;   // 불변 의존성은 공유해도 안전

    public void process(OrderRequest request) {
        Order order = createOrder(request);  // 지역 변수 = 스레드마다 독립 (스택)
        validate(order);                     // 상태는 파라미터로 흘려보낸다
        gateway.pay(order);
    }
}
```

원칙은 하나다. **싱글턴 빈이 가질 수 있는 필드는 불변(주입받은
의존성, 설정값)뿐이고, 요청마다 달라지는 데이터는 지역 변수와
메서드 파라미터로만 다룬다.** 지역 변수는 각 스레드의 스택에 만들어지므로
스레드끼리 절대 섞이지 않는다.

고전 사례로 `SimpleDateFormat`을 싱글턴 빈의 필드로 둔 코드가 있다 —
이 클래스는 내부에 파싱 중간 상태를 갖고 있어서 여러 스레드가 동시에
쓰면 엉뚱한 날짜가 나온다. 스레드 안전한 `DateTimeFormatter`로
교체하는 것이 정석이다. (가산점 포인트)

## 4. 꼬리질문 대비 포인트

### "그럼 스프링은 동기화(synchronized)도 없이 어떻게 안전한가요?"

스프링이 안전하게 만들어주는 것이 아니라, **빈을 무상태(stateless)로
설계하는 것이 개발자와 프레임워크 사이의 계약**이기 때문이다.
공유되는 것은 불변 의존성뿐이고, 변하는 데이터는 각 스레드의
스택(지역 변수)에만 있으므로 경합 자체가 발생하지 않는다.
동기화가 필요 없는 것이 아니라, **동기화가 필요 없는 구조를 강제하는
것**이 싱글턴 + 무상태 조합의 설계 의도다.

### "정말 상태가 필요하면 어떤 선택지가 있나요?" (시니어 변별 포인트)

요구사항에 따라 도구가 다르고, 각각 비용이 있다:

1. **지역 변수/파라미터로 재구성** — 대부분은 설계를 고치면 상태가
   필요 없어진다. 첫 번째 답은 항상 이것.
2. **`request` 스코프 빈** — 요청 단위 상태(예: 요청 컨텍스트).
   싱글턴에 주입할 때는 프록시(`proxyMode`)가 필요하다.
3. **`ThreadLocal`** — 스레드 단위 상태(스프링 시큐리티의
   `SecurityContextHolder`가 이 방식). 단, 톰캣은 스레드를
   풀에서 재사용하므로 **요청 끝에 `remove()`를 안 하면 다음 요청에
   이전 사용자의 값이 남는다.** 또 `@Async` 등 스레드가 바뀌는
   경계에서는 값이 전파되지 않는다.
4. **진짜 공유 상태(카운터, 캐시)** — `AtomicLong`,
   `ConcurrentHashMap` 같은 동시성 도구를 의도적으로 쓰고,
   여러 서버로 확장하면 어차피 인스턴스별로 갈라지므로
   Redis 등 외부 저장소로 빼는 것까지 검토한다.

### "prototype 빈을 싱글턴 빈에 주입하면 어떻게 되나요?"

**주입은 컨테이너 기동 시 한 번만 일어나므로**, 싱글턴이 들고 있는
prototype 인스턴스도 결국 하나로 고정된다 — "쓸 때마다 새 인스턴스"라는
의도가 조용히 깨진다. 매번 새로 받으려면 `ObjectProvider<T>`로
사용 시점에 조회하거나, `@Lookup` 메서드 주입, 스코프 프록시를 쓴다.
덧붙여 prototype 빈은 **소멸 콜백(`@PreDestroy`)을 컨테이너가 불러주지
않는다** — 만들어 건네준 뒤에는 관리를 끝내기 때문에, 자원 정리는
사용하는 쪽 책임이다.

### "@PostConstruct와 생성자의 차이는? 초기화 로직은 어디에 두나요?"

생성자는 생명주기 2단계(인스턴스화)에서 실행되므로, 필드/세터 주입
의존성은 아직 비어 있고 AOP 프록시도 적용 전이다. `@PostConstruct`는
의존성 주입이 끝난 뒤(5단계) 실행이 보장되므로 "주입받은 빈을 사용하는
초기화"는 여기에 둔다. 단 `@PostConstruct` 시점에도 프록시 적용은
완료 전일 수 있어, 트랜잭션이 필요한 초기화라면
`ApplicationReadyEvent`(기동 완료 후) 리스너로 미루는 것이 안전하다.
생성자 주입을 쓰면 생성자 시점에 의존성이 보장되므로 단순 검증 정도는
생성자에서 해도 된다.

## 한 줄 요약

스프링 빈은 "컨테이너가 인스턴스화 → 주입 → 초기화 → 소멸을 대신
관리하고, 기본은 컨테이너당 1개(싱글턴)를 모든 스레드가 공유한다"는
계약 위에 있다 — 그래서 싱글턴 빈은 불변 의존성만 필드로 갖고
**요청별 상태는 절대 필드에 두지 않는 무상태 설계**가 원칙이며,
이를 어긴 코드는 테스트를 전부 통과한 뒤 운영의 동시 접속에서만
사용자 데이터가 섞이는 사고를 낸다.
