# @Scheduled 실행 스레드와 지연 전파 — 기본은 스레드 "1개"를 전원이 나눠 쓴다

> 핵심 관전 포인트: **Spring Boot의 `@Scheduled`는 기본적으로 풀 크기 1짜리 `ThreadPoolTaskScheduler`(스레드 이름 `scheduling-1`)에서 실행된다. 애플리케이션의 모든 `@Scheduled` 작업이 이 한 스레드를 공유하므로, 한 작업이 오래 블록되면 코드상 아무 관련도 없는 다른 스케줄까지 전부 밀린다 — "통계 배치가 안 돌았다"의 진범이 옆자리 정산 배치인 구조다. 밀린 회차의 운명은 방식마다 다르다. `fixedDelay`는 이전 실행이 끝난 시점부터 재므로 그냥 뒤로 밀리고, `fixedRate`는 예정 시각 기준이라 블록이 풀리는 순간 밀린 회차가 연달아 몰아서 실행되며(동시 실행은 아니다), `cron`은 지나간 시각을 그냥 건너뛴다. 대책은 풀 확장 / `@Async`로 트리거와 실행 분리 / 작업군별 스케줄러 분리 세 가지인데 각각 대가가 다르다 — 특히 `@Async`는 트리거를 제때 돌게 만드는 대신 병목을 그 풀로 옮기고, 스케줄러가 완료를 기다리지 않게 되므로 같은 작업의 중복 실행이라는 새 문제를 만든다. 여기에 인스턴스를 N대로 늘리면 배치도 N번 돌므로 ShedLock 같은 분산 락이 필요하고, 그 락도 `lockAtMostFor`가 만료되면 두 인스턴스가 동시에 도는 실패 모드를 갖는다.**

---

## 0. 질문 + 의도

**질문**: "`@Scheduled` 작업들은 기본적으로 어떤 스레드에서 실행되나요? 한 작업의 지연이 다른 작업에 미치는 영향과 대책은?"

**출제 의도**: 기본이 단일 스레드 풀이라 느린 작업 하나가 다른 모든 스케줄을 밀리게 하는데, 증상(특정 작업이 제때 안 돎)에서 원인(스레드 공유)으로 가는 연결이 어렵다. "프레임워크 기본값을 확인하고 쓰는" 습관의 표본으로서 묻는다.

> 이 문서의 서술은 **Spring Boot 3.x / Spring Framework 6.x**와 **Java 21** 기준이며, 스케줄러의 동작은 `ThreadPoolTaskScheduler`·`TaskUtils`의 소스와 실제 실행 결과로 확인했다. 실행 풀 자체의 설정(core/max/queue/거부 정책)은 `15-async-annotation.md`에 있고, 이 문서는 스케줄러 스레드를 여러 작업이 **공유**해서 생기는 문제에 집중한다.

## 1. 기본 동작 — 스레드 하나를 전 작업이 공유한다

### 1-1. 전제 지식 — `@Scheduled` 메서드는 누가 부르는가

`@Scheduled`가 붙은 메서드는 아무도 호출하지 않는데 저절로 실행되는 것처럼 보인다. 실제로는 애플리케이션 기동 시점에 스프링이 그 메서드들을 전부 찾아내 **스케줄러에 "언제 불러 달라"고 등록**해두고, 그 스케줄러가 시각이 되면 호출한다.

여기서 스케줄러란 **"이 작업을 N초 뒤에 실행해 달라"는 예약을 받아 두었다가 시각이 되면 자기 스레드로 실행하는 부품**이다. 스프링은 `TaskScheduler` 인터페이스로 이 역할을 추상화하고, 스프링 부트는 별도 설정이 없으면 `ThreadPoolTaskScheduler` 구현체를 자동 구성한다.

문제는 그 자동 구성의 **기본값**이다.

```yaml
# spring.task.scheduling 의 기본값 (Spring Boot 3.x에서 확인)
spring:
  task:
    scheduling:
      pool:
        size: 1                        # <- 스레드 1개
      thread-name-prefix: "scheduling-"  # <- 그래서 이름이 scheduling-1
```

**풀 크기가 1이다.** 애플리케이션에 `@Scheduled` 메서드가 열 개든 백 개든 전부 이 **한 스레드**에서 순서대로 실행된다. `@Async`용 풀의 `core-size`가 8인 것과 대비하면 유독 작은데, "기본값은 최소한으로 두고 필요한 사람이 늘려 쓴다"는 방침 때문이다. 문제는 이 값을 확인하지 않고 쓰는 사람이 대부분이라는 점이다.

한 스레드를 공유한다는 말은 곧 **작업들이 한 줄로 서서 차례를 기다린다**는 뜻이다. 앞사람이 오래 걸리면 뒷사람은 자기 차례가 와도 시작할 수 없다.

### 1-2. 장애 시나리오 — 정산 배치 하나가 전체를 40분 세운다

말로만 하면 실감이 안 나니 실제로 어떤 모양인지 시간축에 그려보자. 스케줄이 셋 있다고 하자.

- 새벽 3시 정산 배치 (`cron = "0 0 3 * * *"`) — 외부 정산 API를 호출한다
- 5분마다 만료 토큰 정리 (`fixedDelay = 300_000`)
- 10분마다 통계 집계 (`fixedDelay = 600_000`)

어느 날 외부 정산 API가 응답을 40분간 안 준다.

```text
시각     scheduling-1 스레드가 하는 일           그동안 실행되지 못한 것
──────────────────────────────────────────────────────────────────────────
03:00   정산 배치 시작 ─┐
                        │ 외부 API 응답 대기로 블록 (소켓에서 read 중)
03:05                   │                       토큰 정리  <- 못 돈다
03:10                   │                       토큰 정리, 통계 집계  <- 못 돈다
03:15                   │                       토큰 정리
  ...                   │                         ...
03:35                   │                       토큰 정리, 통계 집계
03:40   정산 배치 종료 ─┘
03:40   그제서야 밀려 있던 작업들을 하나씩 처리하기 시작한다
```

40분 동안 **토큰 정리는 8회, 통계 집계는 4회 실행되지 않았다.** 코드상 정산 배치와 아무 관계도 없는 작업들이, 스레드 하나를 공유한다는 이유만으로 서로를 막은 것이다.

이 구조를 모르면 다음 날 아침 "통계 배치가 안 돌았다"는 장애를 통계 코드 안에서만 찾게 된다. 통계 코드에는 아무 문제가 없으므로 원인을 못 찾는다. **진범은 옆 작업이다.**

여기에 한 겹이 더 있다. 정산 배치가 외부 API를 트랜잭션 안에서 부르고 있었다면, 그 40분 동안 DB 커넥션 하나도 함께 잡혀 있다(`22-external-api-call-inside-transaction.md`). 스케줄러 스레드 하나의 블록이 커넥션풀 잠식으로까지 번지는 것이다.

### 1-3. 진단 — 스레드 이름 하나로 끝난다

이 문제는 다행히 진단이 쉽다. **스레드 이름이 자백**하기 때문이다.

로그 패턴에 스레드 이름을 넣어두면(`%thread`) 스케줄 작업 로그가 전부 `scheduling-1`로 찍힌다. 여러 스케줄이 같은 이름 하나로만 찍히고 있다면 그 자체가 단일 스레드 공유 상태라는 증거다.

작업이 안 돌고 있을 때는 스레드 덤프를 뜬다.

```bash
# 애플리케이션 프로세스의 스레드 덤프를 떠서 스케줄러 스레드만 본다
jstack <pid> | grep -A 30 "scheduling-1"
```

`scheduling-1`이 **어느 스택에서 멈춰 있는지**가 그대로 나온다. 소켓 read에서 멈춰 있으면 외부 API 대기, `AbstractQueuedSynchronizer` 계열에서 멈춰 있으면 락 대기, `HikariPool.getConnection`이면 커넥션 대기다. "이 애플리케이션이 지금 무엇을 기다리며 조용한가"를 스택으로 확인하는 절차는 `32-slow-application-startup-diagnosis.md`의 침묵 구간 진단과 동일한 도구다.

지표로 상시 감시하려면 각 스케줄 작업의 **마지막 성공 시각**을 게이지로 남기고 "예상 주기의 3배가 지났는데 갱신이 없으면 알림"을 거는 것이 가장 값싸다. 작업이 실행되지 않는 것은 에러 로그를 남기지 않으므로, 에러 기반 알림으로는 절대 잡히지 않는다.

## 2. 밀린 회차와 죽은 회차 — 다음 실행은 언제, 그리고 정말 오는가

1절에서 "40분간 밀렸다"고 했는데, 밀린 8회의 토큰 정리는 나중에 몰아서 도는가 아니면 그냥 사라지는가? 답은 **어떤 방식으로 주기를 지정했느냐에 따라 완전히 다르다.** 주니어가 전혀 예상하지 못하는 지점이라 반드시 짚고 넘어가야 한다.

### 2-1. 세 방식은 "무엇을 기준으로 다음 시각을 재는가"로 갈린다

셋의 차이는 딱 하나, **다음 실행 시각의 기준점**이다.

| 방식 | 다음 실행 시각의 기준점 | 이전 실행이 주기보다 오래 걸리면 |
|---|---|---|
| `fixedDelay` | 이전 실행이 **끝난** 시각 + N | 그냥 뒤로 밀린다. 회차가 몰리지 않고 겹치지도 않는다 |
| `fixedRate` | 이전 실행의 **예정** 시각 + N | 지나가버린 예정 시각들이 밀린 회차로 남아 **연달아 몰아서** 실행된다 |
| `cron` | 이전 실행이 **끝난** 뒤 처음 오는 cron 시각 | 지나간 cron 시각은 **그냥 버려진다** |

그림으로 보면 확실해진다. 작업 1회가 500ms 걸리는데 주기를 100ms로 잡은 극단적인 경우다.

```text
fixedDelay(100)  — "끝난 시점부터 100ms를 잰다"
  run#1 ████████████████ (500ms)
                          ├100ms┤
  run#2                         ██
                                  ├100ms┤
  run#3                                  ██
  => 밀린 회차라는 개념 자체가 없다. 실행 간격이 600ms꼴로 늘어날 뿐이다.
     같은 작업이 겹칠 수 없다 — 끝나야 다음을 재기 시작하니까.

fixedRate(100)   — "예정 시각 0, 100, 200, 300, 400, 500 ... 을 지킨다"
  run#1 ████████████████ (0ms에 시작, 500ms 소요)
        ↑ 그동안 100·200·300·400·500ms 회차의 예정 시각이 전부 지나가버렸다
  run#2~#6                ▌▌▌▌▌   <- 끝나자마자 밀린 5회차를 연달아 실행(따라잡기)
  run#7 이후                      ██ ... ██ ... ██  <- 다시 100ms 간격으로 정상화
  => 회차가 사라지지 않고 몰려서 온다. 단, 한 스레드에서 순차로 돈다 — 동시 실행은 아니다.

cron("*/1 * * * * *")  — "끝난 뒤 처음 오는 cron 시각"
  run#1 ████████████████ (500ms)
        ↑ 그 사이 지나간 cron 시각들은 아무도 기억하지 않는다
  run#2                   (다음 초 경계에 1회만)
  => 따라잡기가 없다. 밀린 회차는 그냥 없어진다.
```

`fixedRate`의 따라잡기는 실제로 실행해보면 이렇게 나온다. (Java 21에서 `ScheduledExecutorService.scheduleAtFixedRate(period=100ms)`로 1회차만 500ms 걸리게 만들어 측정한 결과다. `ThreadPoolTaskScheduler`는 내부적으로 이 JDK 스케줄러에 위임한다.)

```text
rate  run#1 start t=   16ms      <- 여기서 500ms를 잡아먹는다
rate  run#2 start t=  551ms  ┐
rate  run#3 start t=  552ms  │
rate  run#4 start t=  552ms  ├─ 밀린 5회차가 1~2ms 간격으로 연달아 터진다
rate  run#5 start t=  552ms  │
rate  run#6 start t=  553ms  ┘
rate  run#7 start t=  616ms      <- 따라잡기가 끝나고 100ms 간격으로 복귀
rate  run#8 start t=  718ms
```

같은 조건에서 `scheduleWithFixedDelay`는 이렇게 나온다.

```text
delay run#1 start t=    0ms
delay run#2 start t=  614ms      <- 500ms(작업) + 100ms(지연) + 오버헤드
delay run#3 start t=  717ms
delay run#4 start t=  822ms
```

밀린 회차가 하나도 없다. **`fixedDelay`는 회차를 버리는 대신 간격을 늘리고, `fixedRate`는 간격을 지키는 대신 회차를 몰아서 갚는다.**

### 2-2. 그래서 무엇을 골라야 하는가

이 차이는 취향 문제가 아니라 **작업의 성격**으로 정해진다.

**`fixedDelay`를 고르는 경우**: 작업이 멱등하지 않거나(같은 걸 두 번 하면 문제가 되거나), 매 회차의 처리량이 유동적이라 이전 회차와 겹치면 곤란한 경우다. 정산·발송처럼 "두 번 돌면 사고"인 작업의 기본 선택지다. 대가는 실행 간격이 보장되지 않는다는 것 — 작업이 느려지면 하루 288회 돌 예정이던 5분 주기 작업이 200회밖에 못 돌 수 있다.

**`fixedRate`를 고르는 경우**: 주기 자체가 요구사항인 경우다. "1분마다 헬스 체크 지표를 남긴다"처럼 회차 수가 의미를 갖는 작업이 여기 해당한다. 대가는 따라잡기다 — 위 실측처럼 밀린 회차가 한꺼번에 터지면 그 순간 부하가 몰린다. 그래서 `fixedRate`를 쓸 때는 **작업이 주기보다 오래 걸리는 상황을 정상 경로로 간주하고 설계**해야 한다.

**`cron`을 고르는 경우**: 실행 시각이 벽시계 기준으로 정해져 있을 때다. "매일 새벽 3시", "매월 1일" 같은 요구는 `cron`으로만 표현된다. 밀린 회차를 건너뛰는 성질은 오히려 장점이다 — 새벽 3시 배치가 4시까지 걸렸다고 해서 그날 두 번 돌면 안 되니까.

`cron`을 쓸 때는 **시간대를 반드시 명시**한다. `zone` 속성을 안 주면 JVM 기본 시간대를 따르는데, 로컬은 KST이고 운영 컨테이너는 UTC인 흔한 조합에서 배치가 9시간 어긋난다.

```java
// zone을 명시하지 않으면 서버의 기본 시간대를 따른다.
// 컨테이너가 UTC면 "새벽 3시"가 한국 시간 정오가 된다.
@Scheduled(cron = "0 0 3 * * *", zone = "Asia/Seoul")
public void settleDaily() { ... }
```

### 2-3. 예외가 나면 다음 회차는 도는가 — 프레임워크가 개입하는 지점

**작업 안에서 예외를 밖으로 던지면 다음 회차는 실행되는가?** 답이 두 갈래로 갈리고, 그 갈림을 아는 것이 이 절의 핵심이다.

**순수 JDK 스케줄러라면 다시는 안 돈다.** `ScheduledExecutorService.scheduleAtFixedRate`는 작업이 예외를 던지면 **그 스케줄 등록 자체를 종료시킨다.** 다음 회차도, 그다음 회차도 영원히 오지 않는다. 실제로 확인해보면 이렇다.

```text
(period=100ms로 등록하고 2회차에서 IllegalStateException을 던진 경우)
  run#1 t=    2ms
  run#2 t=  107ms          <- 여기서 예외를 던졌다
  총 실행 횟수 = 2 / future.isDone()=true / isCancelled()=false
  future.get() -> ExecutionException: java.lang.IllegalStateException: boom
```

`isDone()`이 `true`가 됐다는 것은 **이 반복 작업이 끝나버렸다**는 뜻이다. 예외를 던지지 않았다면 영원히 `false`였을 값이다. 아무도 `cancel()`하지 않았는데(`isCancelled()=false`) 스케줄이 죽었고, 예외는 아무 데도 로그되지 않은 채 `Future` 안에만 담겨 있다. `Future`를 아무도 안 들여다보면 **완전한 침묵 속에 배치가 사라진다.**

**그런데 스프링의 `@Scheduled`는 이 동작을 그대로 두지 않는다.** `ThreadPoolTaskScheduler`는 작업을 JDK 스케줄러에 넘기기 전에 `errorHandlingTask(task, true)`로 한 겹 감싼다. 여기서 두 번째 인자 `true`는 "반복 작업"이라는 뜻이고, 반복 작업의 기본 에러 핸들러는 **`LOG_AND_SUPPRESS_ERROR_HANDLER`** — 예외를 `"Unexpected error occurred in scheduled task"`라는 에러 로그로 남기고 **삼켜버리는** 핸들러다.

```text
[내 @Scheduled 메서드]  ---- 예외 발생
        │
        v
[스프링이 씌운 DelegatingErrorHandlingRunnable]
        │  예외를 여기서 잡아 ERROR 로그로 남기고 삼킨다
        v
[JDK ScheduledExecutorService]  <- 예외가 여기까지 도달하지 않는다
        => 스케줄 등록이 살아남고, 다음 회차는 정상 실행된다
```

정리하면 **스프링의 `@Scheduled`에서는 예외가 나도 다음 회차가 계속 실행된다.** "예외 한 번에 배치가 영구 정지한다"는 것은 순수 JDK 스케줄러의 동작이지 `@Scheduled`의 동작이 아니다.

다만 이 사실이 안심할 근거는 아니다. 뒤집으면 **"로그만 남고 조용히 실패가 무한 반복되는 것"이 기본값**이라는 뜻이기 때문이다. 5분마다 도는 배치가 두 달째 매번 실패하고 있어도 시스템은 아무에게도 알리지 않는다.

그래서 실무 결론은 **작업 안에서 직접 예외를 잡아 실패를 지표와 알림으로 승격시키는 것**이다.

```java
// before: 예외가 나면 스프링이 로그 한 줄만 남기고 조용히 넘어간다
@Scheduled(fixedDelay = 300_000)
public void cleanUpTokens() {
    tokenRepository.deleteExpired();   // 여기서 터지면 아무도 모른다
}
```

```java
// after: 실패를 잡아 관측 가능하게 만들고, 스케줄은 계속 살려둔다
@Scheduled(fixedDelay = 300_000)
public void cleanUpTokens() {
    try {
        int deleted = tokenRepository.deleteExpired();
        // 성공 시각을 남겨둬야 "며칠째 안 돌고 있다"를 지표로 감시할 수 있다.
        // 실행되지 않는 것은 에러 로그를 남기지 않으므로 에러 기반 알림으로는 안 잡힌다.
        meterRegistry.gauge("batch.token_cleanup.last_success", System.currentTimeMillis());
        meterRegistry.counter("batch.token_cleanup.deleted").increment(deleted);
    } catch (Exception e) {
        log.error("[batch] 토큰 정리 실패", e);
        // 로그만으로는 아무도 안 본다. 카운터를 올려 임계치 알림에 연결한다.
        meterRegistry.counter("batch.token_cleanup.failure").increment();
    }
}
```

전역으로 처리하고 싶다면 `SchedulingConfigurer`에서 `TaskScheduler`에 커스텀 `ErrorHandler`를 심는 방법도 있다. 기본 핸들러를 대체해 모든 스케줄 작업의 실패를 한곳에서 지표화할 수 있다.

## 3. 대책과 그 대가 — 격리, 중복 실행, 다중 인스턴스

### 3-1. 대책 ① 풀 확장 — 가장 값싸지만 가장 얕다

```yaml
spring:
  task:
    scheduling:
      pool:
        size: 5     # 작업들이 서로를 막지 않게 여유를 준다
```

한 줄로 끝나는 대책이고 대부분의 경우 이것으로 충분하다. 다만 **무엇을 산 것인지 정확히 알아야 한다.**

산 것은 "동시에 5개까지 돌 수 있다"는 여유일 뿐이다. **작업 간 우선순위는 여전히 없다.** 무거운 작업이 다섯 개 동시에 걸리면 6번째 작업은 똑같이 밀린다. 즉 풀 확장은 문제를 **해결**한 것이 아니라 **발생 확률을 낮춘** 것이다.

크기를 정하는 기준은 "동시에 실행될 수 있는 스케줄 작업의 최대 개수"가 아니라 **"오래 걸리는 작업의 개수 + 여유 1~2"** 정도가 현실적이다. 1초 만에 끝나는 작업 열 개는 스레드 하나로도 충분히 소화되므로 세지 않는다.

### 3-2. 대책 ② @Async 조합 — 트리거와 실행을 분리한다

```java
// 스케줄러 스레드는 '트리거'만 하고, 실제 실행은 별도 풀로 넘긴다
@Async("batchExecutor")
@Scheduled(fixedDelay = 300_000)
public void cleanUpTokens() { ... }
```

`@Scheduled`가 붙은 메서드도 프록시를 거쳐 호출되므로 `@Async`가 정상 적용된다(스케줄러가 원본이 아니라 프록시를 들고 있기 때문이며, 자기 호출이 아니라서 프록시 함정에도 걸리지 않는다). 스케줄러 스레드는 작업을 `batchExecutor`에 제출하는 순간 곧바로 반납되므로, **트리거는 언제나 제때 온다.**

대가가 둘이다.

**첫째, 병목이 옮겨갈 뿐 사라지지 않는다.** 실행은 `batchExecutor`가 하므로 이제 그 풀의 포화가 새 병목이 된다. 그 풀의 기본 큐가 무제한이면 동시 실행이 core 개수에 고정되고 큐만 쌓인다 — `15-async-annotation.md`에서 다룬 그 함정이 그대로 재현된다. 즉 이 대책은 **"스케줄러 풀의 문제를 실행 풀의 문제로 바꾼" 것**이며, 실행 풀을 제대로 설정하지 않으면 아무것도 나아지지 않는다.

**둘째, 스케줄러가 완료를 기다리지 않게 된다.** 이것이 다음 절에서 다룰 중복 실행 문제의 원인이다.

### 3-3. 대책 ③ 작업군별 스케줄러 분리 — 중요한 것을 물리적으로 격리한다

풀을 키우는 것은 "같은 방에 의자를 더 놓는" 대책이다. 정말로 중요한 작업이라면 아예 **방을 나누는** 편이 확실하다.

```java
@Configuration
public class SchedulerConfig implements SchedulingConfigurer {

    @Override
    public void configureTasks(ScheduledTaskRegistrar registrar) {
        ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
        scheduler.setPoolSize(3);
        // 이름을 나눠야 스레드 덤프에서 "지금 막힌 게 어느 작업군인지"가 즉시 보인다.
        // 1-3의 진단이 성립하려면 이 한 줄이 필수다.
        scheduler.setThreadNamePrefix("critical-sched-");
        scheduler.initialize();
        registrar.setTaskScheduler(scheduler);
    }
}
```

한 걸음 더 밀면 **무거운 배치를 아예 별도 인스턴스로 분리**한다. API 서버의 스케줄러와 물리적으로 격리되므로 배치가 무슨 짓을 해도 API 응답에 영향이 없고, 배치 인스턴스만 따로 스케일하거나 재시작할 수 있다. 재시작 지점 관리·청크 처리·실패 건 스킵 같은 요구가 붙기 시작하면 그때가 Spring Batch를 꺼낼 시점이다.

### 3-4. 파생 문제 ① — 같은 작업이 겹쳐 도는 순간은 언제인가

병렬화를 하면 반드시 따라오는 질문이 있다. **"같은 작업이 동시에 두 개 돌 수 있는가?"**

**순수 스케줄러만 쓸 때는 겹치지 않는다.** 2-1의 실측이 그 근거다. `fixedRate`에서 밀린 5회차가 몰아서 실행됐지만 시작 시각이 551·552·552·552·553ms로 **순차**였고 전부 같은 스레드였다. JDK `scheduleAtFixedRate`의 계약이 "늦게 시작할 수는 있어도 동시에 실행되지는 않는다"이기 때문이다. **풀 크기를 5로 늘려도 마찬가지다** — 풀 크기는 서로 다른 작업들이 서로를 막지 않게 해줄 뿐, 같은 등록의 회차끼리는 여전히 순차다.

**중복 실행이 실제로 생기는 지점은 3-2의 `@Async` 조합이다.** 스케줄러가 "제출"만 하고 완료를 기다리지 않으므로, 작업 시간이 주기보다 길면 이전 회차가 끝나기 전에 다음 회차가 시작된다.

```text
@Async 없이 (fixedRate 5분, 작업이 7분 걸림)
  scheduling-1: ████████ run#1 (7분) ████████ run#2 ...
                 회차는 밀리지만 겹치지는 않는다

@Async 조합 (fixedRate 5분, 작업이 7분 걸림)
  scheduling-1: |제출|      |제출|      |제출|     <- 5분마다 정확히 트리거
  batch-1:      ████████████ run#1 (7분)
  batch-2:            ████████████ run#2 (7분)     <- 2분간 run#1과 겹친다
                      ↑ 여기서 같은 정산 배치가 동시에 두 개 돈다
```

멱등하지 않은 배치(정산, 발송, 포인트 지급)라면 이것은 그대로 사고다. 같은 건에 대해 정산이 두 번 잡히거나 알림이 두 번 나간다.

가드는 셋이다.

- **`fixedDelay`로 바꾼다** — `@Async`가 없다면 근본적으로 겹칠 수 없다. 가장 확실하다.
- **실행 중 플래그** — `AtomicBoolean`으로 진입을 한 번만 허용한다. 한 인스턴스 안에서만 유효하다.
- **락** — 3-5의 분산 락은 다중 인스턴스와 중복 실행을 한 번에 막는다.

```java
// @Async를 쓰면서 중복 실행을 막아야 할 때의 최소 가드
private final AtomicBoolean running = new AtomicBoolean(false);

@Async("batchExecutor")
@Scheduled(fixedRate = 300_000)
public void settle() {
    // compareAndSet(false, true)가 false를 리턴하면 이미 누가 돌고 있다는 뜻이다.
    // 검사와 선점이 한 번에 원자적으로 일어나야 두 스레드가 나란히 통과하지 않는다.
    if (!running.compareAndSet(false, true)) {
        log.warn("[batch] 이전 회차가 아직 실행 중이라 이번 회차를 건너뛴다");
        return;
    }
    try {
        doSettle();
    } finally {
        // 예외가 나도 반드시 풀어야 한다. 안 풀면 이후 모든 회차가 영구 스킵된다.
        running.set(false);
    }
}
```

`finally`가 특히 중요하다. 플래그를 안 되돌리면 예외 한 번에 그 배치가 영원히 스킵되는데, 2-3에서 본 대로 스프링은 예외를 삼키므로 **아무 신호 없이 배치가 죽는다.**

한 가지 예외 케이스를 알아두면 좋다. **가상 스레드를 켜면(Spring Boot 3.2 이상, `spring.threads.virtual.enabled=true`) 스케줄러 구현이 `SimpleAsyncTaskScheduler`로 바뀌는데, 이 구현의 `fixedRate` 경로는 트리거 스레드가 작업을 새 스레드로 넘기고 완료를 기다리지 않는다.** 즉 `@Async`를 붙이지 않아도 `@Async`를 붙인 것과 같은 겹침이 가능해진다. (같은 구현에서도 `fixedDelay` 경로는 스케줄러 스레드에서 그대로 실행하므로 겹치지 않는다.) 가상 스레드를 켤 때 `fixedRate` 배치의 멱등성을 다시 점검해야 하는 이유다.

### 3-5. 파생 문제 ② — 서버가 2대면 배치도 2번 돈다

여기서부터가 시니어 변별 대목이다.

`@Scheduled`는 **각 JVM 인스턴스가 자기 스케줄러를 갖고 각자 실행한다.** 스케줄 등록은 애플리케이션 기동 시점에 그 인스턴스 안에서 일어나는 일이고, 다른 인스턴스와 조율하는 장치는 어디에도 없다. **오토스케일로 파드가 3개가 되는 순간 정산 배치도 3번 돈다.**

이 사고가 특히 고약한 것은 **개발·스테이징에서 절대 재현되지 않기** 때문이다. 인스턴스 1대로 띄운 환경에서는 완벽하게 동작한다.

**해법 ①: 분산 락 — ShedLock**

여러 인스턴스가 공유하는 저장소(DB 테이블이나 Redis)에 "이 작업은 지금 누가 실행 중"이라는 표식을 만들고, 그것을 잡은 인스턴스만 실행하는 방식이다. ShedLock이 이 용도의 사실상 표준 라이브러리다.

```java
@Scheduled(cron = "0 0 3 * * *", zone = "Asia/Seoul")
@SchedulerLock(
    name = "dailySettlement",        // 락의 식별자. 이 이름으로 인스턴스들이 경쟁한다
    lockAtMostFor = "PT2H",          // 안전핀: 최대 2시간 뒤에는 락이 강제로 풀린다
    lockAtLeastFor = "PT5M"          // 최소 5분은 락을 유지한다
)
public void settleDaily() { ... }
```

세 속성이 각각 무엇을 막는지 알아야 한다.

`name`은 락의 식별자다. 인스턴스들이 이 이름으로 같은 락 레코드를 두고 경쟁하고, 먼저 잡은 하나만 실행하며 나머지는 조용히 건너뛴다.

`lockAtMostFor`는 **실행 중이던 인스턴스가 죽었을 때 락이 영원히 안 풀리는 것을 막는 안전핀**이다. 정상 종료라면 작업이 끝날 때 락을 풀지만, 프로세스가 갑자기 죽으면 풀어줄 사람이 없다. 이 값이 만료 시각을 미리 박아두는 역할을 한다.

`lockAtLeastFor`는 **작업이 너무 빨리 끝났을 때 다른 인스턴스가 뒤이어 또 도는 것을 막는다.** 인스턴스 간 시계가 조금씩 어긋나 있으면(클럭 스큐), A가 0.1초 만에 끝내고 락을 푼 직후 시계가 살짝 느린 B가 같은 트리거 시각으로 진입해 락을 잡아버릴 수 있다. 최소 유지 시간을 두면 그 창이 닫힌다.

**그리고 이 락에는 명확한 실패 모드가 있다.**

```text
lockAtMostFor = 2시간, 그런데 정산이 2시간 10분 걸린 날

03:00  인스턴스 A가 락 획득 → 정산 시작
05:00  ★ lockAtMostFor 만료 — A는 아직 돌고 있는데 락이 자동으로 풀린다
05:00  인스턴스 B가 다음 트리거에서 락을 잡고 정산을 또 시작한다
       => 같은 정산이 A와 B에서 동시에 돈다. 막으려던 바로 그 사고가 난다.
```

**`lockAtMostFor`는 "작업의 최장 소요 시간"이 아니라 그보다 넉넉히 잡아야 한다.** 그렇다고 무한정 길게 잡으면 반대 대가가 있다 — 인스턴스가 죽었을 때 그 시간만큼 아무도 그 배치를 돌리지 못한다. 하루 한 번 도는 배치에 24시간을 걸면 하루치를 통째로 날린다.

즉 `lockAtMostFor`는 **"동시 실행 위험"과 "장애 시 공백"을 저울질해 정하는 값**이다. 이 트레이드오프를 말할 수 있으면 "ShedLock 쓰면 됩니다"보다 두 단계 위의 답변이 된다.

**해법 ②: 실행 주체를 하나로 못 박는다**

락으로 경쟁시키는 대신, 애초에 **스케줄 작업을 배치 전용 인스턴스 1대에만 등록**하는 방법이다. 프로파일로 가르면 간단하다.

```java
// 배치 프로파일로 뜬 인스턴스에서만 이 빈이 등록되므로,
// API 인스턴스를 몇 대로 늘리든 스케줄은 배치 인스턴스에서만 돈다.
@Profile("batch")
@Component
public class SettlementScheduler { ... }
```

락 인프라가 필요 없고 동작이 명확하다는 것이 장점이다. 대신 **그 인스턴스가 단일 장애점이 된다** — 배치 인스턴스가 죽으면 아무도 대신 돌지 않는다. 그래서 이 방식은 "죽으면 다음 회차에 복구되면 되는" 배치나, 오케스트레이터가 파드를 자동 복구해주는 환경에 맞는다.

**해법 ③: 리더 선출**

여러 인스턴스 중 하나를 리더로 뽑고 리더만 스케줄을 실행하는 방식이다. ShedLock이 "작업 단위로 매번 경쟁"한다면 리더 선출은 "인스턴스 단위로 한 번 정하고 유지"한다. 리더가 죽으면 남은 인스턴스 중 새 리더가 뽑히므로 해법 ②의 단일 장애점 문제가 없다. 대신 리더 선출을 관리할 장치(주키퍼, Redis 기반 구현, 쿠버네티스 리스 등)가 하나 더 필요하다.

셋 중 무엇을 고를지는 **"이 배치가 한 회차 걸러도 되는가"**로 갈린다. 걸러도 되면 ②가 가장 단순하고, 걸러서는 안 되면 ①이나 ③으로 간다.

## 4. 꼬리질문 대비 포인트

### "풀 크기를 5로 늘리면 같은 작업이 겹쳐 돌 걱정은 없나요?"

없다. 풀 크기는 **서로 다른 작업들**이 서로를 막지 않게 해주는 값이지, 같은 등록의 회차를 병렬화하지 않는다. JDK 스케줄러의 계약이 "늦게 시작할 수는 있어도 같은 작업을 동시에 실행하지는 않는다"이기 때문이다.

실제로 `fixedRate` 100ms짜리 작업이 500ms를 잡아먹게 만들어 측정해보면, 밀린 5회차가 1~2ms 간격으로 몰아서 실행되긴 하지만 시작 시각이 전부 순차이고 같은 스레드다.

**겹침은 `@Async`를 조합했을 때 생긴다.** 스케줄러가 제출만 하고 완료를 기다리지 않게 되기 때문이다. 가상 스레드를 켠 경우의 `fixedRate`도 같은 이유로 겹칠 수 있다는 점까지 말하면 가산점이다.

### "fixedDelay 5분짜리 작업이 6분 걸리면 어떻게 되나요?"

`fixedDelay`는 **이전 실행이 끝난 시점**부터 간격을 재므로, 다음 실행은 6분 뒤가 아니라 "6분(실행) + 5분(지연) = 11분" 뒤에 시작된다. 회차가 밀려 쌓이지도 않고 겹치지도 않는다.

대신 **실행 간격이 보장되지 않는다.** 5분 주기로 하루 288회 돌 예정이던 작업이 131회밖에 못 돈다. 회차 수 자체가 요구사항이라면 `fixedRate`로 바꿔야 하는데, 그 순간 밀린 회차가 몰아서 실행되는 성질이 따라오므로 **멱등성이나 락이 함께 필요해진다.**

### "@Scheduled 작업에서 예외가 나면 다음 회차는 도나요?" (시니어 변별 포인트)

**스프링의 `@Scheduled`에서는 계속 돈다.** `ThreadPoolTaskScheduler`가 작업을 JDK 스케줄러에 넘기기 전에 에러 핸들러로 감싸는데, 반복 작업의 기본 핸들러가 예외를 에러 로그로 남기고 **삼키기** 때문이다. 예외가 JDK 스케줄러까지 도달하지 않으므로 스케줄 등록이 살아남는다.

여기서 대비를 하나 얹으면 이해도가 드러난다. **순수 JDK `ScheduledExecutorService`였다면 정반대다** — 작업이 예외를 던지는 순간 그 스케줄 등록이 종료되어 다시는 실행되지 않는다. `Future`의 `isDone()`이 `true`가 되고 예외는 그 `Future` 안에만 담긴 채, 아무도 조회하지 않으면 로그조차 남지 않는다. 스프링이 이 위험한 기본값을 덮어써 준 것이다.

다만 스프링의 처리가 안심할 근거는 아니다. 뒤집으면 **"로그만 남고 조용히 실패가 무한 반복되는 것"이 기본값**이라는 뜻이다. 그래서 실무에서는 작업 안에서 예외를 잡아 실패 카운터와 마지막 성공 시각을 지표로 남기거나, `SchedulingConfigurer`에서 커스텀 `ErrorHandler`를 심어 전역으로 알림에 연결한다.

### "서버가 2대인데 배치가 두 번 돌았습니다. 어떻게 막나요?" (시니어 변별 포인트)

`@Scheduled`는 인스턴스마다 각자 실행되고 인스턴스 간에 조율하는 장치가 없기 때문이다. 인스턴스 1대인 개발 환경에서는 절대 재현되지 않는다는 점도 함께 말하면 좋다.

해법은 셋이다. **분산 락(ShedLock)**으로 공유 저장소의 락을 먼저 잡은 인스턴스만 실행하게 하거나, **배치 전용 인스턴스**로 스케줄 등록 자체를 한 곳에만 두거나(`@Profile("batch")`), **리더 선출**로 리더만 실행하게 한다.

ShedLock을 고른다면 실패 모드까지 짚어야 한다. **`lockAtMostFor`가 만료되기 전에 작업이 안 끝나면 락이 자동으로 풀려 다른 인스턴스가 같은 작업을 또 시작한다** — 막으려던 바로 그 사고가 난다. 그렇다고 무한정 길게 잡으면 실행 인스턴스가 죽었을 때 그 시간만큼 배치 공백이 생긴다. **"동시 실행 위험"과 "장애 시 공백"을 저울질해 정하는 값**이라고 답하는 것이 정확하다. 클럭 스큐로 인한 연속 실행을 막는 `lockAtLeastFor`까지 언급하면 완결이다.

### "@Scheduled 메서드에 @Transactional을 붙이면 정상 동작하나요?"

정상 적용된다. 스케줄러가 붙잡고 있는 것은 원본 빈이 아니라 **프록시**이고, 스케줄러가 그 프록시의 메서드를 호출하므로 자기 호출 문제에 걸리지 않는다. `@Async`를 함께 붙이는 경우도 같은 이유로 정상 동작한다.

다만 **트랜잭션이 열려 있는 동안 커넥션을 계속 점유한다**는 사실은 그대로다. 배치가 수십만 건을 한 트랜잭션으로 처리하면 그 시간 내내 커넥션 하나가 묶여 있고, 여기에 외부 API 호출까지 트랜잭션 안에 들어 있으면 커넥션풀 고갈로 번진다(`26-hikaricp-connection-pool-exhaustion.md`, `22-external-api-call-inside-transaction.md`).

긴 배치라면 트랜잭션을 청크 단위로 쪼개는 것이 정석이고, 그 요구가 본격화되면 Spring Batch를 쓸 시점이다.

### "cron 표현식으로 새벽 3시에 걸었는데 엉뚱한 시각에 돌았습니다."

가장 흔한 원인은 **시간대**다. `zone` 속성을 지정하지 않으면 JVM의 기본 시간대를 따르는데, 개발자 로컬은 KST이고 운영 컨테이너 이미지는 UTC인 조합이 흔하다. 그러면 "새벽 3시"가 한국 시간 정오에 실행된다. `@Scheduled(cron = "0 0 3 * * *", zone = "Asia/Seoul")`처럼 명시해야 한다.

두 번째로 흔한 원인은 **앞 작업이 스레드를 잡고 있어 트리거 시각을 놓친 것**이다. 이 경우 `cron`은 밀린 회차를 따라잡지 않고 **그냥 건너뛰므로**, 로그를 보면 그날 실행 자체가 없다. 스레드 이름이 전부 `scheduling-1`이라면 1절의 단일 스레드 공유를 의심한다.

### "밀린 회차가 나중에 몰아서 도는 게 문제가 되는 경우가 있나요?" (가산점 포인트)

`fixedRate`에서 실제로 관측되는 현상이고, 두 가지 방식으로 사고가 된다.

**하나, 부하가 한 점에 몰린다.** 40분간 막혀 있던 5분 주기 작업이라면 풀리는 순간 8회차가 거의 동시에 연달아 실행된다. 각 회차가 DB를 크게 건드리는 작업이라면 그 순간 DB에 8배의 부하가 몰린다.

**둘, 시간에 의존하는 작업이 잘못된 구간을 처리한다.** "직전 5분간의 데이터를 집계한다"를 `now()` 기준으로 계산하고 있다면, 몰아서 실행되는 8회차가 전부 거의 같은 `now()`를 보게 되어 **같은 구간을 8번 집계하고 나머지 35분치는 영영 집계되지 않는다.**

그래서 시간 구간을 다루는 배치는 **실행 시각이 아니라 "마지막으로 처리한 지점"을 DB에 저장해두고 거기서부터 이어 처리**하도록 설계해야 한다. 이렇게 하면 몰아서 실행되든 한 회차를 건너뛰든 결과가 같아진다 — 스케줄러의 타이밍에 정합성을 맡기지 않는 것이 원칙이다.

## 한 줄 요약

`@Scheduled`의 기본값은 "스레드 1개를 전 작업이 공유"라서 한 작업의 블록이 아무 관련 없는 작업 전체를 밀리게 하고, 밀린 회차는 `fixedDelay`면 그냥 뒤로 밀리고 `fixedRate`면 몰아서 따라잡고 `cron`이면 버려지며, 예외는 스프링이 삼켜 다음 회차를 살리는 대신 실패를 조용하게 만든다 — 그래서 풀 확장·`@Async` 분리·스케줄러 분리로 격리하되 `@Async`가 병목을 실행 풀로 옮기고 같은 작업의 중복 실행을 만든다는 대가를 알고, 다중 인스턴스에서는 ShedLock의 `lockAtMostFor`가 "동시 실행 위험 대 장애 시 공백"의 저울이라는 것까지 쥐어야 완성이다.
