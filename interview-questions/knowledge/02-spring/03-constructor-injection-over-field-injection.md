# 생성자 주입을 권장하는 이유 — 필드 주입 대비, 컨벤션이 아니라 근거로

> 핵심 관전 포인트: **생성자 주입을 권장하는 근거는 네 가지다.
> ① `final` 선언이 가능해 불변이 보장되고 주입 누락이 기동 시점에
> 즉시 실패한다. ② 순환 참조를 기동 시점에 조기 발견한다.
> ③ 스프링 컨테이너 없이 `new Service(mock)`으로 순수 자바 테스트가
> 가능하다 — 필드 주입은 `private` 필드라 리플렉션 없이는 mock을
> 넣을 자리가 없다. ④ 생성자 파라미터가 비대해지면 "이 클래스의
> 책임이 너무 많다"는 설계 신호가 겉으로 드러난다.**

---

## 0. 질문 + 의도

**질문**: "생성자 주입을 권장하는 이유는 무엇인가요? (필드 주입 대비)"

**출제 의도**: 순환 참조의 조기 발견, 불변성, 테스트 시 목 주입
용이성까지 연결해 말하는지 본다. 컨벤션을 "팀 규칙이라서"가 아니라
근거로 이해하는 사람은 새로운 상황에서도 올바른 선택을 한다.

## 1. 주입 방식 3가지 — 무엇이 어떻게 다른가

| 방식        | 주입 시점         | 용도                      |
|-----------|---------------|-------------------------|
| 생성자 주입    | 인스턴스 생성과 동시에  | **필수 의존성 (권장 기본값)**     |
| 수정자(setter) 주입 | 생성 후 별도 호출    | 선택적·재설정 가능한 의존성         |
| 필드 주입     | 생성 후 리플렉션으로   | 지양 (테스트·불변성에 불리)        |

```java
// 필드 주입 — 짧아 보이지만 문제를 숨긴다
@Service
public class OrderService {
    @Autowired
    private PaymentGateway gateway;   // private 필드에 리플렉션으로 꽂아 넣음
}

// 생성자 주입 — 의존성이 클래스의 공개 계약(생성자 시그니처)에 드러난다
@Service
public class OrderService {
    private final PaymentGateway gateway;

    public OrderService(PaymentGateway gateway) {  // 생성자가 하나면 @Autowired 생략 가능
        this.gateway = gateway;
    }
}
```

핵심 차이는 **의존성이 어디에 드러나는가**다. 생성자 주입은 "이 객체를
만들려면 이것들이 반드시 필요하다"를 생성자 시그니처로 선언한다.
필드 주입은 그 계약을 클래스 내부에 숨기고, 스프링이 리플렉션으로
`private` 필드를 몰래 채워주는 방식이다 — 컨테이너 없이는 완성될 수
없는 객체가 된다.

## 2. 권장 근거 4가지 — 각각 어떤 사고를 막아주는가

### ① 불변성 + 필수 의존성 보장 — 실패를 기동 시점으로 앞당긴다

생성자 주입만이 필드를 `final`로 선언할 수 있다.

```java
// Before: 필드 주입 — 주입이 빠져도 객체는 만들어진다
@Service
public class OrderService {
    @Autowired
    private PaymentGateway gateway;
    // 설정 실수로 주입이 안 되거나, 누가 setter/리플렉션으로 바꿔치기해도
    // 컴파일러는 침묵한다. 문제는 실제 호출 순간 NPE로 드러난다.
}

// After: 생성자 주입 — 주입이 빠지면 애플리케이션이 아예 안 뜬다
@Service
public class OrderService {
    private final PaymentGateway gateway;   // 한 번 주입되면 교체 불가
    // 빈이 없으면 기동 시점에 UnsatisfiedDependencyException → 배포 전에 발견
}
```

"런타임의 어느 요청에서 터질지 모르는 NPE"를 "기동 실패"로 바꾸는 것 —
**실패를 가장 싼 시점(배포 전)으로 앞당기는 것**이 이 항목의 본질이다.
또한 `final` 불변 필드는 싱글턴 빈의 무상태 설계(모든 스레드가 공유해도
안전한 유일한 필드는 불변 의존성)와도 맞물린다.

### ② 순환 참조의 조기 발견

A가 B를 필요로 하고 B가 A를 필요로 하는 순환 구조에서:

- **생성자 주입**: A를 만들려면 B가 완성돼야 하고 B를 만들려면 A가
  완성돼야 하므로 **기동 시점에 `BeanCurrentlyInCreationException`으로
  즉시 실패**한다. 문제가 숨을 수가 없다.
- **필드/세터 주입**: 객체를 먼저 만들어두고 나중에 필드를 채우는
  방식이라 컨테이너가 미완성 참조로 순환을 이어붙여 **기동은 된다.**
  잘못된 설계(양방향 의존)가 겉으로 드러나지 않은 채 굴러간다.

순환 참조는 대부분 잘못된 책임 분배의 증상이므로, "기동이 되게
덮는 것"보다 "기동 실패로 드러나는 것"이 낫다. 스프링 부트도 최근
버전에서는 순환 참조를 기본적으로 금지하는 방향으로 바뀌었다 —
프레임워크 스스로 생성자 주입의 관점(순환은 오류다)을 채택한 셈이다.
(가산점 포인트)

### ③ 테스트 용이성 — mock을 넣을 "자리"가 있는가

실무에서 체감이 가장 큰 차이다.

```java
// Before: 필드 주입된 클래스의 테스트 — mock을 넣을 방법이 없다
OrderService service = new OrderService();
// service.gateway는 private + setter 없음 → null인 채로 테스트?
// 결국 리플렉션(ReflectionTestUtils.setField)이나
// 스프링 컨테이너 기동(@SpringBootTest)에 의존하게 된다 — 느리고 취약

// After: 생성자 주입 — 컨테이너 없이 순수 자바로 끝난다
PaymentGateway fake = mock(PaymentGateway.class);
OrderService service = new OrderService(fake);   // 그냥 new
service.placeOrder(order);                        // 밀리초 단위 단위 테스트
```

리플렉션으로 필드를 꽂는 테스트는 **필드명이 바뀌면 컴파일 에러 없이
깨지고**, 컨테이너를 띄우는 테스트는 느려서 피드백 루프를 망가뜨린다.
생성자 주입은 테스트 코드가 프로덕션 코드와 같은 공개 계약(생성자)만
쓰게 만든다.

### ④ 설계 신호 — 나쁜 냄새를 숨기지 못하게 한다

의존성이 8개인 클래스는 필드 주입에서는 `@Autowired` 8줄로 조용히
지나가지만, 생성자 주입에서는 파라미터 8개짜리 생성자로 **눈에 보이는
고통**이 된다. 이 고통이 "이 클래스가 책임을 너무 많이 진 것 아닌가
(SRP 위반)"를 리팩터링하게 만드는 압력으로 작동한다. 필드 주입은
이 신호를 무음 처리하는 셈이다.

## 3. 실무 작성법 — 보일러플레이트는 도구로 지운다

"생성자 코드가 길어진다"는 반론은 도구로 해소된다.

```java
// Lombok — 필드 선언만 하면 final 필드 생성자를 자동 생성
@Service
@RequiredArgsConstructor
public class OrderService {
    private final PaymentGateway gateway;
    private final OrderRepository orderRepository;
}
```

```kotlin
// Kotlin — 주 생성자 문법이라 애초에 보일러플레이트가 없다
@Service
class OrderService(
    private val gateway: PaymentGateway,
    private val orderRepository: OrderRepository,
)
```

생성자가 하나뿐이면 `@Autowired`도 생략할 수 있어, 결과적으로
필드 주입보다 특별히 길지도 않다.

## 4. 꼬리질문 대비 포인트

### "그럼 setter 주입은 언제 쓰나요?"

**없어도 객체가 성립하는 선택적 의존성**, 또는 런타임에 교체될 수
있는 의존성에 쓴다(레거시 프레임워크 연동 등 드문 경우). 원칙은
"필수는 생성자, 선택은 setter"인데, 실무에서는 선택적 의존성 자체가
드물고 그마저도 `ObjectProvider`나 기본값 있는 생성자로 풀 수 있어
setter 주입의 자리는 거의 없다.

### "필드 주입이 테스트에 불리한 이유를 구체적으로 설명해보세요"

`private` 필드 + setter 없음이라 정상적인 자바 문법으로는 주입 수단이
없다. 남는 선택지는 ① `ReflectionTestUtils.setField` 같은 리플렉션
(필드명 문자열에 의존해 리팩터링에 취약), ② `@SpringBootTest`로
컨테이너 기동(단위 테스트가 통합 테스트 비용을 치름) 뿐이다.
생성자 주입은 `new OrderService(mock)` 한 줄로 끝난다 —
**"컨테이너 없이 인스턴스화할 수 있는가"가 테스트 가능성의 분기점**이다.

### "생성자 주입인데 순환 참조가 발생하면 어떻게 해결하나요?" (시니어 변별 포인트)

`@Lazy`를 한쪽에 붙여 프록시로 지연시키면 기동은 되지만, 이는
**증상을 덮는 임시방편**이다. 순환은 대부분 책임 분배가 잘못됐다는
신호이므로 설계를 고치는 답이 먼저 나와야 한다:

1. **공통 로직을 제3의 빈으로 추출** — A ↔ B가 서로 부르는 부분을
   C로 빼서 A → C ← B 단방향으로.
2. **이벤트로 방향 끊기** — B가 A를 직접 호출하는 대신
   `ApplicationEventPublisher`로 발행하고 A가 구독.
3. **경계 재검토** — 애초에 두 클래스가 한 책임을 나눠 가진 것은
   아닌지(합치거나 다시 쪼개기).

"@Lazy로 돌리겠다"가 첫 답이면 설계 감각을 의심받는다.

### "생성자 파라미터가 10개가 됐습니다. 어떻게 하시겠어요?"

주입 방식을 바꿀 문제가 아니라 **클래스 분리 신호로 읽는다.**
파라미터들을 용도별로 묶어보면 보통 2~3개의 응집된 책임이 나오고,
각각을 별도 클래스로 추출한다(예: 주문 검증 관련 의존성 4개 →
`OrderValidator`로). 생성자 주입의 장점 ④가 바로 이 리팩터링을
촉발하는 것이므로, "롬복으로 가려서 계속 간다"는 답은 감점 요인이다.

---

## 한 줄 요약

생성자 주입은 의존성을 클래스의 공개 계약으로 드러내는 방식이라
**불변(`final`) 보장, 주입 누락·순환 참조의 기동 시점 발견,
컨테이너 없는 순수 단위 테스트, 책임 비대화의 가시화**를 한꺼번에
얻는다 — "팀 규칙이라서"가 아니라, 실패를 가장 싼 시점으로 앞당기고
나쁜 설계를 숨기지 못하게 하는 구조적 근거가 있는 선택이다.
