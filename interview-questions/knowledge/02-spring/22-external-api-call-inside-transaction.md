# 트랜잭션 안의 외부 API 호출 — 외부사 지연 하나가 전 서비스 마비로 번지는 연쇄

> 핵심 관전 포인트: **트랜잭션은 시작부터 커밋까지 DB 커넥션 1개를 독점하는 구간이다. 그 안에서 외부 API를 호출하면 커넥션 점유 시간이 "우리가 통제할 수 없는 외부사의 응답 속도"에 종속된다 — 외부가 200ms에서 3초로 느려지는 순간 필요 커넥션이 11개에서 151개로 뛰고, 풀 30개는 0.6초 만에 바닥나며, 커넥션을 기다리는 톰캣 스레드 200개까지 5초 안에 전부 묶여 외부 API와 무관한 조회·헬스체크마저 응답하지 못한다. 헬스체크가 죽으면 로드밸런서가 인스턴스를 빼고 남은 인스턴스가 같은 경로로 무너져 전면 장애가 된다. 정합성도 함께 깨진다 — 롤백은 우리 DB 안만 되돌리므로 "외부 결제는 승인됐는데 주문은 롤백"이 남고, 특히 타임아웃은 "실패"가 아니라 "결과 불명"이라 가장 위험하다. 설계의 답은 트랜잭션 경계를 DB 작업만으로 좁혀 외부 호출을 밖으로 빼고, `PENDING → CONFIRMED / FAILED` 상태 기계로 중간 실패를 관측 가능하게 만든 뒤, 남은 구멍(외부 호출 후 두 번째 트랜잭션 직전 크래시)은 조회 API와 멱등키를 쓰는 복구 배치로 수렴시키는 것이다.**

---

## 0. 질문 + 의도

**질문**: "트랜잭션 안에서 외부 API를 호출하면 어떤 문제가 생기나요? 어떻게 설계를 바꾸겠습니까?"

**출제 의도**: DB 커넥션을 문 채로 3초짜리 외부 호출을 기다리면, 외부사 지연 하나가 커넥션풀 고갈 → 전 서비스 마비로 번진다. 이 연쇄를 머리로 시뮬레이션할 수 있는 사람만 장애가 나기 전에 구조를 바꾼다. 대용량 서비스 면접의 핵심 변별 문항.

이 문서는 Spring Boot 3.x / Spring Framework 6.x, HikariCP 기본 설정, 내장 톰캣 기준으로 쓴다.

## 1. 트랜잭션이 독점하는 것 — 커넥션 1개, 시작부터 커밋까지

### 1-1. 전제 지식 — 커넥션풀이 무엇이고 왜 개수가 적은가

먼저 깔아야 할 사실이 하나 있다. **DB 커넥션은 요청마다 새로 만드는 것이 아니라, 미리 몇 개만 만들어 두고 돌려 쓰는 자원이다.** 이 "미리 만들어 둔 커넥션 보관함"이 커넥션풀이고, 스프링 부트의 기본 구현체가 HikariCP다.

왜 미리 만들어 두는가. 커넥션 하나를 새로 여는 데는 TCP 연결, 인증, 세션 초기화가 필요해서 보통 수십 ms가 든다. 실제 쿼리가 2ms인데 연결에 50ms를 쓰는 것은 낭비다. 그래서 애플리케이션이 뜰 때 몇 개를 열어 두고, 요청이 오면 빌려주고, 끝나면 돌려받는다.

그러면 왜 넉넉히 만들지 않는가. **커넥션 하나는 DB 서버 쪽에서도 프로세스나 스레드 하나를 잡아먹기 때문**이다. PostgreSQL은 커넥션마다 백엔드 프로세스를 하나씩 띄우므로, 커넥션 1,000개는 DB 서버에 프로세스 1,000개다. 그래서 풀 크기는 수십 개 수준으로 잡는 것이 정상이고, HikariCP의 기본 `maximumPoolSize`도 10이다.

여기서 이 문서 전체의 전제가 나온다. **커넥션은 수십 개짜리 한정 자원이다.** 한정 자원이므로 "누가 얼마나 오래 쥐고 있는가"가 곧 처리량을 결정한다. (풀 크기를 어떤 근거로 정하는지는 `25-thread-pool-connection-pool-sizing.md`에 따로 있다.)

### 1-2. `@Transactional`은 그 한정 자원을 통째로 붙잡는 구간이다

`@Transactional` 메서드에 진입하면 스프링의 트랜잭션 매니저는 풀에서 커넥션 하나를 꺼내 `setAutoCommit(false)`로 바꾼 뒤 **현재 스레드에 바인딩**한다. 그리고 그 커넥션은 메서드가 끝나 커밋 또는 롤백될 때까지 풀로 돌아가지 않는다. (스레드에 바인딩한다는 것이 정확히 무슨 뜻이고 그 커넥션을 이후 쿼리들이 어떻게 찾아 쓰는지는 `24-transaction-synchronization-connection-binding.md`에 정리돼 있다.)

돌아가지 않는 이유는 트랜잭션의 정의 자체에 있다. 트랜잭션은 "여러 쿼리를 하나의 원자적 단위로 묶는" 것인데, 그 묶음은 **한 커넥션 안에서만 성립한다.** 중간에 커넥션을 반납했다가 다른 커넥션으로 이어 붙일 수 있다면 애초에 롤백할 대상이 어디에 있는지도 알 수 없다.

그래서 **트랜잭션 구간 = 커넥션 독점 구간**이다. 이 등식이 문제의 전부다.

```java
// before: DB 작업 사이에 외부 호출이 끼어 있다
@Transactional
public Order placeOrder(OrderRequest request) {
    // 이 줄에 도달하기 전에 이미 커넥션을 꺼내 왔다 — 여기부터가 점유 구간이다
    Order order = orderRepository.save(Order.of(request));  // 실제 DB 작업: 약 5ms

    // 이 한 줄이 문제다. HTTP 응답을 기다리는 동안에도 커넥션은
    // 이 스레드에 묶여 있다 — 풀에는 그만큼 빈자리가 사라진 상태다.
    paymentClient.approve(order);   // 외부 PG 호출: 평소 200ms, 장애 시 3초

    order.confirm();                                        // 실제 DB 작업: 약 5ms
    return order;
}   // 커밋과 커넥션 반환이 일어나는 지점은 여기다
```

이 메서드가 DB를 실제로 쓰는 시간은 10ms 남짓인데, 커넥션을 붙잡고 있는 시간은 210ms다. **점유 시간의 95%가 우리 코드가 아니라 남의 서버 사정으로 결정된다.**

### 1-3. 비유 — 식당 테이블에 앉아 친구를 기다리는 손님

식당에 테이블(커넥션)이 30개 있다. 손님이 앉아 주문하고 먹는 데 실제로 걸리는 시간은 짧은데, "친구(외부 API)가 올 때까지 계산 안 하고 앉아 있을게요"라고 한다.

친구가 제때 오면 테이블은 금방 빈다. 친구가 늦으면 테이블은 그만큼 오래 잠긴다. 문제는 **테이블이 언제 비는지를 식당이 정하지 못하고 손님의 친구가 정한다**는 점이다.

밖의 대기줄(커넥션을 기다리는 톰캣 스레드)은 그동안 계속 길어진다. 2절에서 이 대기줄이 어떻게 식당 전체를 마비시키는지 숫자로 따라간다.

### 1-4. 여기서 문제가 두 갈래로 갈린다

트랜잭션 안에 외부 호출을 두면 두 종류의 사고가 각각 따로 발생한다. 서로 원인이 다르므로 나눠서 봐야 한다.

- **성능**: 점유 시간이 늘어나 커넥션풀 → 톰캣 스레드풀 순서로 자원이 마른다 (2절).
- **정합성**: 외부 호출은 롤백되지 않아 "외부는 됐는데 우리 DB는 없던 일"이 남는다 (3절).

면접에서 한쪽만 말하면 절반 답변이다. 그리고 3절의 설계 변경은 두 문제를 동시에 푼다.

## 2. 성능 붕괴 — 장애 연쇄를 숫자로 따라간다

### 2-1. 계산 도구 — Little's law

동시에 몇 개의 커넥션이 필요한지는 감이 아니라 계산으로 나온다. 쓰는 공식은 **Little's law**다.

```
동시에 자원을 점유 중인 개수(L) = 도착률(λ) × 하나당 점유 시간(W)
```

말로 풀면 이렇다. 초당 50건이 들어오고 한 건이 자원을 0.2초 쥔다면, 어느 순간을 잘라 봐도 평균 `50 × 0.2 = 10`건이 그 자원을 쥔 채로 있다. 식당으로 치면 "초당 손님 수 × 손님 한 명의 체류 시간 = 지금 앉아 있는 손님 수"다.

여기서 결정적인 사실은 **점유 시간 W가 두 배가 되면 필요 개수 L도 두 배가 된다**는 것이다. 트래픽이 하나도 안 늘었는데 외부사가 느려졌다는 이유만으로 필요 커넥션이 폭증하는 이유가 이 비례 관계다.

### 2-2. 조건을 고정한다

계산 전제를 명시해 두자.

| 항목 | 값 | 근거 |
|---|---|---|
| 주문 API 도착률 λ | 초당 50건 | 가정 |
| DB 작업 시간 | 합계 10ms | `save` + `confirm` |
| 외부 PG 응답 (평시) | 200ms | 평시 관측값 |
| 외부 PG 응답 (장애) | 3,000ms | 외부사 지연 |
| HikariCP `maximumPoolSize` | 30 | 기본값 10에서 늘려 둔 상태 |
| HikariCP `connection-timeout` | 30,000ms | 기본값 |
| 톰캣 `server.tomcat.threads.max` | 200 | 스프링 부트 기본값 |

### 2-3. 1단계 — 평시에는 몇 개가 필요한가

요청 하나당 커넥션 점유 시간은 DB 작업 10ms + 외부 호출 200ms = **210ms = 0.21초**다.

```
L = λ × W = 50건/초 × 0.21초 = 10.5개
```

필요 커넥션 약 11개, 풀은 30개. 사용률 35%로 여유롭다. **평시 지표만 보면 이 코드는 아무 문제가 없어 보인다.** 이것이 이 장애가 배포 시점에 잡히지 않는 이유다.

### 2-4. 2단계 — 외부가 3초로 느려지면 필요량이 얼마가 되는가

외부 응답만 200ms → 3,000ms로 바뀐다. 우리 트래픽도, 우리 쿼리도 그대로다.

```
W = 10ms + 3,000ms = 3,010ms = 3.01초
L = 50건/초 × 3.01초 = 150.5개
```

**필요 커넥션 11개 → 151개.** 외부 응답이 15배(200ms → 3,000ms) 느려지자 필요량도 약 15배로 뛰었다. 풀은 30개뿐이므로 121개가 모자란다.

반대로 읽으면 이렇다. 풀 30개로 감당 가능한 처리량은 `L / W = 30 / 3.01 = 9.97`, 즉 **초당 10건**이다. 들어오는 50건 중 10건만 처리되고 **초당 40건이 갈 곳을 잃는다.**

### 2-5. 3단계 — 풀이 바닥나기까지 0.6초

"언젠가 고갈된다"가 아니라 몇 초 만인지를 계산할 수 있다.

지연이 시작된 순간을 t=0이라 하자. 이때부터 들어온 요청은 3.01초가 지나야 커넥션을 반납한다. 즉 **첫 3.01초 동안은 반납이 한 건도 없다.** 그동안 점유된 커넥션 수는 그냥 도착한 건수와 같다.

```
점유 커넥션 수 = 50 × t
30 = 50 × t
t = 0.6초
```

**외부사가 느려지고 0.6초 만에 풀 30개가 전부 나간다.** 사람이 알림을 보고 대시보드를 여는 시간보다 훨씬 짧다.

이 순간부터 새 요청은 커넥션을 기다린다. 기다림의 한도는 HikariCP의 `connection-timeout` 기본값 30초이고, 그 시간이 지나면 이런 예외가 난다.

```
java.sql.SQLTransientConnectionException:
    HikariPool-1 - Connection is not available, request timed out after 30000ms
```

### 2-6. 4단계 — 두 번째 고갈: 톰캣 스레드가 대기로 말라붙는다

여기가 이 문제의 핵심이고, 커넥션풀 이야기만 하고 멈추면 놓치는 지점이다.

블로킹 방식의 Spring MVC에서는 **요청 하나가 톰캣 워커 스레드 하나를 처음부터 끝까지 점유한다.** 커넥션을 기다리는 동안에도 그 스레드는 다른 요청을 처리하러 가지 않는다. 그냥 `getConnection()` 호출에 멈춰 서 있다.

그러면 스레드가 얼마나 빨리 마르는지 계산해 보자.

```
t = 0.6초  : 커넥션 30개 전부 사용 중 = 톰캣 스레드 30개가 일하는 중
             남은 톰캣 스레드 슬롯 = 200 - 30 = 170개

이후 초당 순증 = 유입 50건 - 처리 완료 약 10건 = 40건/초

170개 ÷ 40개/초 = 약 4.3초
```

**t ≈ 4.9초에 톰캣 스레드 200개가 전부 커넥션 대기 상태가 된다.** 외부사 지연이 시작되고 5초가 채 지나기 전이다.

이 시점의 서버 상태를 정확히 짚자. **CPU는 거의 놀고 있고, DB도 한가하며, 애플리케이션 로그에는 아직 에러가 없다.** 스레드 200개가 전부 `getConnection()`에서 park된 채 30초 타임아웃을 기다리고 있을 뿐이다. 그래서 "서버가 죽었는데 지표는 멀쩡해 보이는" 기묘한 장애가 된다. 이 상태를 확인하는 수단은 스레드 덤프다 — 스택 최상단이 전부 HikariCP의 대기 지점을 가리킨다.

그리고 결정적인 결과가 나온다. **톰캣 스레드가 하나도 안 남았으므로, 이제 서버는 어떤 요청도 받지 못한다.** 결제와 아무 상관 없는 상품 조회, 캐시에서만 읽는 API, DB를 건드리지도 않는 헬스체크까지 전부 응답이 없다. 자원 하나(커넥션)의 고갈이 자원 둘(스레드)의 고갈로 번역되는 순간, 장애 범위는 "결제 기능"에서 "이 인스턴스 전체"로 확대된다.

### 2-7. 5단계 — 마지막 고리: 헬스체크 실패가 전면 장애를 만든다

여기까지가 인스턴스 하나의 이야기다. 마지막 한 고리가 이것을 서비스 전체의 장애로 바꾼다.

```
[t=0]  외부 PG 응답 200ms -> 3,000ms
   │
   ▼
[t=0.6초]  커넥션풀 30개 고갈
   │        · 이후 요청은 최대 30초 커넥션 대기
   ▼
[t≈4.9초]  톰캣 스레드 200개 전부 대기로 묶임
   │        · 결제와 무관한 조회 API도 응답 없음
   │        · /actuator/health 도 스레드를 못 받아 무응답
   ▼
[헬스체크 실패]
   ├─ LB(또는 k8s readinessProbe): 이 인스턴스를 라우팅 대상에서 제외
   └─ k8s livenessProbe: 컨테이너를 죽이고 재시작
   │
   ▼
[남은 인스턴스로 트래픽 재분배]
   │   · 3대 중 1대가 빠지면 남은 2대의 λ 가 50 -> 75건/초
   │   · 같은 W(3.01초)에 λ만 커졌으므로 더 빨리 고갈된다
   ▼
[같은 연쇄가 남은 인스턴스에서 반복]
   │   · 재시작된 인스턴스는 뜨자마자 밀린 트래픽을 맞고 다시 죽는다
   ▼
[전면 장애 — 서비스 전체가 응답하지 않음]
```

이 도식의 요점은 **자동 복구 장치가 오히려 붕괴를 가속한다**는 것이다. 로드밸런서의 인스턴스 제외와 쿠버네티스의 재시작은 "한 대가 이상하면 나머지가 받아준다"는 전제로 만들어진 장치인데, 지금은 모든 인스턴스가 같은 원인으로 아프기 때문에 트래픽을 몰아줄수록 나머지가 더 빨리 죽는다.

장애 보고서에는 "PG사 지연"이라고 적히지만, **200ms의 지연을 전면 장애로 증폭시킨 것은 우리 트랜잭션 설계다.** 이 문장을 말할 수 있느냐가 이 문항의 변별점이다.

### 2-8. 덧: 커넥션만 잡고 기다리는 게 아니다 — 행 락도 같이 잡는다

한 겹 더 있다. 트랜잭션 안에서 `SELECT ... FOR UPDATE`나 UPDATE로 특정 행을 이미 건드린 상태라면, 그 트랜잭션은 **행 락을 쥔 채로** 외부 응답을 기다린다.

```java
@Transactional
public void useCoupon(Long couponId) {
    Coupon c = couponRepository.findByIdForUpdate(couponId); // 이 행에 락이 걸린다
    paymentClient.approve(...);                              // 락을 쥔 채 3초 대기
    c.markUsed();
}
```

같은 쿠폰(또는 같은 재고 행, 같은 계좌 행)을 갱신하려는 다른 트랜잭션들은 커넥션을 얻는 데 성공하더라도 DB 안에서 락을 기다리며 다시 멈춘다. 인기 상품처럼 경합이 집중되는 행이 있으면 **커넥션 고갈과 락 대기가 겹쳐 붕괴가 더 빨라진다.** PostgreSQL이라면 `pg_stat_activity`에서 `state = 'idle in transaction'`인 세션이 쌓이는 모습으로 보인다 — 트랜잭션은 열려 있는데 쿼리는 안 돌고 있는 상태, 정확히 "외부 응답을 기다리는 중"의 DB 쪽 그림자다.

## 3. 정합성 붕괴와 설계 변경 — 롤백은 우리 DB 안에서만 유효하다

### 3-1. 롤백이 되돌리지 못하는 것

성능만의 문제가 아니다. 트랜잭션의 롤백은 **DB가 자기 데이터에 대해 제공하는 기능**이다. 변경 전 값을 DB가 보관하고 있다가 `ROLLBACK` 신호에 되돌려 주는 것이지, 세상의 모든 변화를 되감는 마법이 아니다.

외부 API 호출은 이미 상대 시스템에 도달했고, 상대는 자기 DB에 커밋을 끝냈다. 우리 쪽 롤백은 거기에 아무 영향도 주지 못한다.

```java
// before: 롤백이 정합성을 지켜준다는 믿음이 깨지는 코드
@Transactional
public Order placeOrder(OrderRequest request) {
    Order order = orderRepository.save(Order.of(request));
    paymentClient.approve(order);           // ① 성공 — PG사 원장에 승인이 확정된다
    couponService.use(request.couponId());  // ② 쿠폰이 이미 사용됨 -> 예외 -> 전체 롤백
    return order;
}
// 롤백이 지운 것: 우리 DB의 주문 행
// 롤백이 지우지 못한 것: PG사의 승인 기록, 고객 카드의 승인 문자
// 결과: 고객은 결제됐는데 우리에겐 주문이 없다. 돈이 붕 뜬다.
```

### 3-2. 네 가지 실패 조합 — 무엇이 정상이고 무엇이 사고인가

"외부 호출 결과"와 "DB 트랜잭션 결과"를 곱하면 조합이 넷이다. 이 표를 그릴 수 있어야 어떤 케이스를 설계로 막아야 하는지 정리된다.

| # | 외부 호출 | DB 트랜잭션 | 최종 상태 | 판정 |
|---|---|---|---|---|
| ① | 성공 | 커밋 | 결제됨 + 주문 있음 | 정상 |
| ② | 성공 | 롤백 | 결제됨 + 주문 없음 | **사고** — 고객 돈이 나갔는데 우리에겐 기록이 없다 |
| ③ | 실패(명시적 거절) | 롤백 | 결제 안 됨 + 주문 없음 | 정상 |
| ④ | 응답 불명(타임아웃) | 롤백 | **모름** + 주문 없음 | **최악** — ①인지 ③인지 알 수 없다 |

①과 ③은 아무 문제가 없다. 사고는 ②와 ④뿐이고, 성격이 완전히 다르다.

**②는 "무엇이 잘못됐는지 아는" 사고다.** PG 승인 번호가 우리 로그에는 남아 있으니, 취소 API를 부르거나 수동으로 환불하면 수습이 된다. 다만 그 수습 코드가 트랜잭션 롤백 이후에 실행돼야 하는데, 롤백은 자동이고 수습은 우리가 짜 넣어야 하므로 대개 빠져 있다.

**④는 "무엇이 잘못됐는지도 모르는" 사고다.** 다음 절이 이것만 따로 다루는 이유다.

### 3-3. 타임아웃이 가장 위험한 이유 — 실패가 아니라 "결과 불명"이다

타임아웃을 실패로 취급하는 것이 가장 흔한 오해다. **타임아웃은 "상대가 처리하지 않았다"가 아니라 "정해진 시간 안에 답을 못 들었다"는 뜻**이고, 그 안에는 서로 다른 세 가지 세계가 섞여 있다.

```
우리 서버가 타임아웃을 만났을 때, 상대(PG)의 실제 상태 가능성

(A) 요청이 PG에 도달조차 못 했다              -> 승인 안 됨
(B) PG가 처리 중이다 (아직 진행 중)            -> 곧 승인될 수 있음
(C) PG는 승인을 끝냈고 응답만 늦거나 유실됐다   -> 이미 승인됨  ★ 위험
```

세 경우가 **우리 쪽에서는 완전히 똑같이 보인다.** 소켓에서 아무것도 안 오는 것은 (A)든 (C)든 동일하다. 그래서 타임아웃을 만난 순간 우리가 아는 것은 "모른다"뿐이다.

여기서 잘못된 선택을 하면 이렇게 된다.

- **실패로 간주하고 롤백** → (C)였다면 표의 ②가 된다. 고객 돈만 나갔다.
- **성공으로 간주하고 커밋** → (A)였다면 결제도 안 됐는데 주문이 확정된다. 이번엔 우리가 손해다.
- **재시도** → (C)였다면 이중 결제다. 멱등키 없이 재시도하면 안 되는 이유가 이것이다.

**정답은 "지금 정하지 않는 것"이다.** 결과가 불명이면 불명이라고 데이터에 적어두고, 진실을 아는 쪽(PG)에게 나중에 물어본다.

- **조회 API로 확인한다(reconcile).** PG사는 대개 "우리 주문번호로 승인 내역을 조회하는" API를 제공한다. 이 API가 있어야 ④를 ①이나 ③으로 확정할 수 있으므로, **외부사 연동 스펙을 검토할 때 조회 API의 유무를 반드시 확인해야 한다.** 없다면 그 자체가 설계 리스크다.
- **멱등키(idempotency key)를 실어 보낸다.** 멱등키는 "이 요청은 아까 그 요청과 같은 요청"임을 상대가 알아볼 수 있게 하는 식별자다. 우리 주문 ID를 키로 실어 보내면, (C) 상태에서 재시도해도 PG는 새 승인을 만들지 않고 기존 승인 결과를 그대로 돌려준다. **재시도를 안전하게 만드는 유일한 수단**이라 결과 불명 상황의 필수 장비다.

### 3-4. before — 하나의 트랜잭션에 DB 쓰기·외부 호출·DB 쓰기가 섞여 있다

지금까지의 문제를 전부 안고 있는 형태를 먼저 못박아 두자.

```java
// before: 커넥션 점유 시간이 외부사에 종속되고, 롤백은 외부를 되돌리지 못한다
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional
    public Order placeOrder(OrderRequest request) {
        Order order = orderRepository.save(Order.of(request));   // DB 쓰기 (약 5ms)
        PaymentResult result = paymentClient.approve(order);     // 외부 호출 (200ms ~ 3초)
        order.confirm(result);                                   // DB 쓰기 (약 5ms)
        return order;
    }   // 커밋 + 커넥션 반환
}
```

문제를 두 줄로 정리하면 이렇다. **점유 구간이 하나뿐이라 그 안의 가장 느린 것이 전체를 지배한다**(2절), 그리고 **원자성의 범위 안에 되돌릴 수 없는 것이 들어와 있다**(3-1).

### 3-5. after — 트랜잭션을 둘로 쪼개고 외부 호출을 그 사이에 둔다

고치는 방향은 하나다. **커넥션을 쥐는 구간에서 외부 호출을 몰아낸다.** 구조적으로는 트랜잭션이 없는 조율자(퍼사드) 하나를 위에 두고, 그 아래에 짧은 트랜잭션 메서드 둘을 두는 모양이 된다.

```java
// after: [tx1 커밋] -> [커넥션 없이 외부 호출] -> [tx2 커밋]
@Service
@RequiredArgsConstructor
public class OrderFacade {          // 이 클래스에는 @Transactional을 붙이지 않는다.
                                    // 붙이는 순간 전체가 다시 하나의 점유 구간이 된다.
    private final OrderService orderService;
    private final PaymentClient paymentClient;

    public Order placeOrder(OrderRequest request) {
        // tx1: PENDING 상태로 주문을 먼저 남긴다.
        // 이 메서드가 리턴되는 순간 커밋이 끝나고 커넥션은 풀로 돌아간다.
        Order order = orderService.createPending(request);

        // 이 구간에는 커넥션이 없다. 외부가 3초를 쓰든 30초를 쓰든
        // 풀의 여유는 줄지 않는다 — 지연이 커넥션풀로 전파되지 않는다.
        PaymentResult result = paymentClient.approve(order.getId(), order.getAmount());

        // tx2: 외부 결과를 반영한다. 여기도 DB 작업만 있으므로 수 ms짜리 짧은 점유다.
        return orderService.confirm(order.getId(), result);
    }
}

@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional
    public Order createPending(OrderRequest request) {
        return orderRepository.save(Order.pending(request));
    }

    @Transactional
    public Order confirm(Long orderId, PaymentResult result) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.confirm(result);   // PENDING -> CONFIRMED
        return order;
    }
}
```

여기서 반드시 짚어야 할 함정이 하나 있다. **`OrderFacade`와 `OrderService`는 반드시 서로 다른 빈이어야 한다.** 같은 클래스 안에서 `this.createPending(...)`처럼 자기 자신을 호출하면 프록시를 거치지 않아 `@Transactional`이 아예 적용되지 않는다(상세는 `11-transactional-self-invocation.md`). 트랜잭션을 쪼개려고 메서드만 나누고 클래스는 그대로 두는 실수가 흔하다.

효과를 2절의 숫자로 되짚어 보자. 외부가 3초로 느려져도 커넥션 점유 시간 W는 여전히 10ms 수준이다.

```
개선 후 필요 커넥션 = 50건/초 × 0.01초 = 0.5개
```

**필요 커넥션 151개 → 1개 미만.** 커넥션풀은 아무 영향을 받지 않는다. 물론 톰캣 스레드는 여전히 외부 응답을 기다리므로 `50 × 3.01 = 151개`가 필요하다 — 스레드 200개 안이라 버티지만 여유는 크지 않다. 그래서 3-9의 타임아웃·서킷 브레이커가 짝으로 따라와야 한다. **경계를 좁히는 것은 "커넥션풀로의 전파를 끊는" 조치이지 외부 지연 자체를 없애는 조치가 아니다.**

### 3-6. after에도 남는 구멍 — 여기까지 가야 시니어 답변이다

트랜잭션을 쪼갠 대가로 **틈이 생긴다.** before에는 없던 새로운 실패 지점이다.

```
tx1 커밋       외부 호출        tx2 커밋
  │              │                │
  ▼              ▼                ▼
──●──────────────●────────────────●──────>
  PENDING 저장   PG 승인 성공      CONFIRMED
       ▲              ▲
       │              │
   여기서 죽으면    ★ 여기서 죽으면
   PG 호출 전이라   PG에는 승인이 있는데
   PENDING만 남음   우리는 PENDING인 채로 영영 남는다
   (안전한 쪽)      (돈이 붕 뜬 상태)
```

프로세스가 `kill -9`로 죽거나, 파드가 축출되거나, 그냥 배포로 재시작돼도 같은 일이 생긴다. **`try`/`catch`로는 못 막는다** — 프로세스가 사라지면 어떤 catch 블록도 실행되지 않기 때문이다.

그러므로 이 구멍은 코드가 아니라 **바깥의 복구 프로세스**로 메운다. 이것이 "상태 기계 + 복구 배치" 설계의 진짜 이유다.

```java
// 복구 배치: 오래 PENDING인 주문을 주워 외부에 진실을 물어본다
@Scheduled(fixedDelay = 60_000)
public void reconcilePendingOrders() {
    // 5분 기준을 두는 이유: 방금 만들어져 정상 진행 중인 PENDING까지 건드리면
    // 아직 처리 중인 결제를 취소해 버릴 수 있다. 정상 흐름의 최대 소요보다
    // 넉넉히 긴 값을 잡는다.
    List<Order> stuck = orderRepository.findPendingOlderThan(Duration.ofMinutes(5));

    for (Order order : stuck) {
        // 우리가 모르는 사실(진짜 승인됐는가)을 아는 쪽은 PG뿐이다.
        // 그래서 추측하지 않고 조회 API로 물어본다.
        PaymentStatus status = paymentClient.inquire(order.getId());

        switch (status) {
            // PG에 승인이 있다 -> 우리 쪽 tx2만 유실된 것이므로 이어서 확정한다
            case APPROVED -> orderService.confirm(order.getId(), status.toResult());
            // PG에 아무것도 없다 -> 승인 전에 끊긴 것이므로 실패로 닫는다
            case NOT_FOUND -> orderService.fail(order.getId(), "PG 승인 기록 없음");
            // PG도 아직 확정 못 한 상태 -> 다음 주기에 다시 물어본다
            case IN_PROGRESS -> { }
        }
    }
}
```

배치 자체도 여러 번 돌 수 있으므로 `confirm`은 멱등해야 한다. `PENDING`일 때만 `CONFIRMED`로 바꾸는 조건부 전이(상태 기계 가드)로 만들면, 같은 주문에 배치가 두 번 돌아도 두 번째는 조용히 아무 일도 하지 않는다.

여기까지 오면 잃은 것과 얻은 것이 분명해진다. 잃은 것은 **"큰 트랜잭션 하나의 즉시 원자성"**이다. 얻은 것은 **"어디까지 진행됐는지가 데이터로 남아 관측 가능하고, 언젠가 수렴한다"**는 성질(최종 일관성)과 **장애 격리**다. 그리고 원래 그 원자성은 외부 세계까지 덮어주지 못했으므로 애초에 반쪽짜리였다 — 이 점을 짚는 것이 답변의 마무리다.

### 3-7. 상태 전이도 — 상태를 넷으로 두는 이유

`PENDING`과 `CONFIRMED`만으로는 부족하다. 3-3에서 본 "결과 불명"을 담을 자리가 필요하기 때문이다.

```
                     ┌──────────────────────────────┐
                     │                              │
   [tx1]             ▼      [외부 호출 성공]         │
  주문 생성 ──> ( PENDING ) ─────────────────> ( CONFIRMED )   종료
                     │                              ▲
                     │ [외부 호출 명시적 거절]       │
                     ├──────────────────> ( FAILED )│         종료
                     │                              │
                     │ [타임아웃 = 결과 불명]        │
                     └──────────────────> ( UNKNOWN )┘
                                              │
                                              │ 복구 배치가 PG 조회 API로 확인
                                              ├─ 승인 있음 ──> CONFIRMED
                                              ├─ 기록 없음 ──> FAILED
                                              └─ 아직 진행중 ─> UNKNOWN 유지(다음 주기)

  · PENDING  : 우리가 시작은 했으나 외부 결과를 아직 못 받음
  · UNKNOWN  : 외부에 요청은 갔고 결과를 모름 — PENDING과 구분해야 하는 이유는
               "재시도해도 되는가"가 다르기 때문이다. PENDING은 아직 안 보냈을 수
               있으니 그냥 보내도 되지만, UNKNOWN은 이미 갔을 수 있으므로
               멱등키 없이 재전송하면 이중 결제가 된다.
  · CONFIRMED / FAILED : 종료 상태. 배치가 더 이상 건드리지 않는다.
```

`UNKNOWN`을 따로 두는 것이 실무의 디테일이다. 많은 구현이 타임아웃을 `FAILED`로 뭉개는데, 그러면 3-3의 (C) 경우 — PG는 승인했는데 우리는 실패로 닫은 상태 — 를 영영 발견하지 못한다. **상태 하나를 아끼는 대신 돈이 새는 경로를 만드는 셈**이다.

운영 지표도 여기서 나온다. "`PENDING`/`UNKNOWN`인 채 N분 넘은 건수"에 알람을 걸면, 복구 배치가 조용히 죽어 있는 장애를 발견할 수 있다.

### 3-8. 외부 호출이 "결과를 결정하지 않는" 경우 — 이벤트와 아웃박스

지금까지는 외부 호출 결과가 주문의 확정 여부를 결정하는 경우였다. 그런데 알림 발송, 캐시 갱신, 통계 집계처럼 **주문 성공 여부와 무관한 부수 작업**이라면 더 간단한 길이 있다.

이 경우 필요한 것은 "커밋이 확정된 뒤에만 실행되게 하는 것"이다. `@TransactionalEventListener(phase = AFTER_COMMIT)`에 `@Async`를 얹으면 커밋 이후 다른 스레드에서 실행되므로 트랜잭션 경계 밖으로 나간다 (상세는 `16-spring-event-transactional-event-listener.md`).

다만 그 방식은 이벤트가 JVM 메모리에만 있어서 커밋 직후 서버가 죽으면 통째로 유실된다. 유실이 허용되지 않는 이벤트라면 트랜잭셔널 아웃박스로 간다 (`23-transactional-outbox-pattern.md`).

### 3-9. 외부 호출 자체의 방어선 (가산점 포인트)

경계를 옮겨도 외부는 여전히 느려지고 실패한다. 3-5에서 봤듯 톰캣 스레드는 여전히 외부 응답을 기다리므로, 다음 세 가지가 짝으로 따라와야 한다.

**타임아웃은 선택이 아니라 필수다.** connect 타임아웃(연결 수립까지)과 read 타임아웃(응답 수신까지)을 둘 다 명시한다. 클라이언트 기본값이 무제한인 경우가 많은데, 그러면 "느린 실패"가 "영원한 대기"가 되어 스레드가 영영 안 돌아온다. 값의 기준은 **외부사 응답 시간의 99분위 × 여유 배수**로 잡고, 그보다 오래 걸리는 건은 애초에 성공해도 사용자에게 의미가 없다고 판단한다.

**재시도는 멱등키와 세트다.** 3-3에서 본 대로, 멱등키 없는 재시도는 이중 결제를 만든다. 그리고 재시도 간격은 지수 백오프(1초, 2초, 4초처럼 늘려 가는 방식)로 둔다 — 이미 힘들어하는 상대에게 재시도 폭풍을 얹지 않기 위해서다.

**서킷 브레이커는 연쇄 차단의 마지막 방어선이다.** 서킷 브레이커는 최근 실패율이 임계치를 넘으면 한동안 아예 호출을 시도하지 않고 즉시 실패시키는 장치다(전기 회로의 차단기에서 온 이름이다). 이것이 하는 일은 **스레드를 기다림에서 해방하는 것**이다. 2-6에서 스레드를 마르게 한 것은 실패가 아니라 대기였으므로, "빨리 실패시키는" 것만으로 스레드풀 고갈을 막을 수 있다.

## 4. 꼬리질문 대비 포인트

### "외부 API 호출이 실패하면 트랜잭션을 롤백하면 되는 것 아닌가요?"

두 가지 이유로 불충분하다.

첫째, **타임아웃은 실패 확정이 아니다.** 상대는 성공했고 응답만 유실됐을 수 있어서, 롤백하면 3-2 표의 ② — 외부는 성공했는데 우리 DB는 없던 일 — 이 된다. 확정하려면 조회 API로 실제 결과를 물어봐야 하고, 그 조회는 트랜잭션 롤백 이후에 일어나야 하므로 애초에 트랜잭션 안에서 해결될 문제가 아니다.

둘째, **롤백으로 정합성을 지킬 수 있는 경우라 해도 성능 문제는 그대로 남는다.** 실패를 기다리는 동안(타임아웃 30초라면 30초 내내) 커넥션을 문 채이므로 2절의 연쇄는 똑같이 일어난다. 롤백은 성능 문제를 하나도 해결하지 못한다.

한 줄로 정리하면 **"롤백은 우리 DB 안의 세계만 되돌린다"**가 답의 뼈대다.

### "커넥션풀 고갈이 전 서비스 장애로 번지는 경로를 구체적으로 설명해주세요"

숫자를 붙여 단계로 답한다.

```
외부 응답 200ms -> 3초
  -> 점유 시간 W: 0.21초 -> 3.01초
  -> 필요 커넥션 L = 50 × W: 11개 -> 151개 (풀은 30개)
  -> 반납이 없는 첫 3초 동안 50t = 30 -> t=0.6초에 풀 고갈
  -> 커넥션 대기 요청이 톰캣 스레드를 점유한 채 멈춤 (블로킹 MVC)
  -> 순증 40건/초, 남은 슬롯 170개 -> 약 4.3초 뒤 스레드 200개 소진
  -> DB가 필요 없는 조회·헬스체크까지 무응답
  -> LB 제외 / k8s 재시작 -> 남은 인스턴스의 λ 증가 -> 같은 연쇄 반복
  -> 전면 장애
```

핵심 문장은 **"커넥션풀과 톰캣 스레드풀이라는 두 겹의 공유 자원이 차례로 마르는 연쇄"**이고, 마지막 고리인 **"헬스체크 실패가 자동 복구 장치를 붕괴 가속기로 바꾼다"**까지 말하면 완성이다. 이 시점의 서버가 CPU도 놀고 DB도 한가한데 응답만 없다는 점, 그래서 스레드 덤프로 확인해야 한다는 점을 덧붙이면 실제 겪어본 사람의 답이 된다.

### "트랜잭션을 쪼개면 중간 실패 시 정합성은 어떻게 지키나요?" (시니어 변별 포인트)

원자성이 사라지는 것이 아니라 **원자성의 단위를 줄이고 단위 사이를 상태로 잇는 것**이라고 답한다.

`PENDING`을 커밋해 두면 "어디까지 진행됐는지"가 데이터로 남는다. 메모리에만 있던 진행 상황이 DB로 나왔다는 것이 핵심이다 — 프로세스가 죽어도 다른 인스턴스나 배치가 그 행을 보고 이어받을 수 있다.

그 위에 복구 배치를 얹는다. 오래 `PENDING`/`UNKNOWN`인 건을 주워 외부 조회 API로 진실을 확인하고 `CONFIRMED`나 `FAILED`로 수렴시킨다. 재시도가 안전하려면 외부 호출에 멱등키가 실려 있어야 하고, 우리 쪽 전이도 "현재 상태가 PENDING일 때만"이라는 가드로 멱등하게 만든다.

마지막으로 트레이드오프를 명시한다. **"큰 트랜잭션의 즉시 일관성"과 "쪼갠 구조의 최종 일관성 + 장애 격리"** 중 무엇을 택할지는 요구사항이 정한다 — 다만 외부 호출이 끼어 있는 순간 전자는 원래 불가능했으므로, 실제 선택지는 "관측 가능한 최종 일관성"과 "관측조차 안 되는 불일치" 사이라고 답하면 시니어 답변이다.

### "결제 승인 결과가 있어야 주문을 확정할 수 있는데, 그래도 트랜잭션 밖으로 뺄 수 있나요?"

뺄 수 있고, 빼야 한다. **"외부 결과에 의존한다"와 "같은 트랜잭션이어야 한다"는 서로 다른 명제**다.

진행 순서는 그대로 유지된다. tx1(PENDING 저장) → 외부 승인 → tx2(결과 반영)이므로 "승인 결과를 보고 확정한다"는 요구는 조금도 훼손되지 않는다. 바뀐 것은 그 사이에 커넥션을 쥐고 있느냐뿐이다.

잃는 것은 "실패 시 자동 롤백" 하나인데, 그 자동 롤백은 어차피 PG사의 승인을 되돌리지 못하므로 애초에 환상이었다. 결제처럼 **진실의 원천이 외부에 있는 도메인**은 조회 API와 멱등키로 정합성을 맞추는 것이 정석이고, DB 트랜잭션은 우리 쪽 기록을 짧고 확실하게 남기는 역할만 맡는다.

### "그럼 `@Transactional(propagation = REQUIRES_NEW)`로 쪼개면 되지 않나요?" (가산점 포인트)

안 된다. 오히려 나빠진다.

`REQUIRES_NEW`는 기존 트랜잭션을 **끝내는 것이 아니라 잠시 보류(suspend)하고 새 트랜잭션을 여는** 전파 옵션이다. 보류된 트랜잭션의 커넥션은 풀로 돌아가지 않고 그대로 붙잡혀 있다. 그래서 안쪽 트랜잭션이 도는 동안 **커넥션을 2개 쥔다.**

바깥 트랜잭션 안에 외부 호출이 있고 그 안에서 `REQUIRES_NEW`를 쓰면, 커넥션 점유량이 요청당 2개가 되어 풀이 절반의 시간에 고갈된다. 게다가 풀 크기가 동시 요청 수보다 작으면 "바깥 커넥션을 쥔 채 안쪽 커넥션을 기다리는" 요청들이 서로를 막는 자기 교착에 빠질 수 있다.

필요한 것은 트랜잭션의 **중첩**이 아니라 **종료**다. 즉 3-5처럼 트랜잭션이 없는 조율자를 두고 커밋을 실제로 끝낸 뒤 외부를 호출해야 한다. (전파 옵션의 의미는 `12-transaction-propagation-required-vs-requires-new.md`에 있다.)

### "AI가 생성한 서비스 코드에서 이 문제를 리뷰할 때 무엇을 보나요?" (가산점 포인트)

생성 도구는 "서비스 메서드에는 `@Transactional`"이라는 관성이 강해서, 트랜잭션 경계 안에 `RestTemplate`/`WebClient`/`FeignClient` 호출이 들어간 코드를 자주 만든다. 눈에 띄는 오류가 없고 테스트도 통과하므로 리뷰에서 걸러야 한다.

체크리스트는 넷이다.

1. `@Transactional` 메서드 안에 HTTP 클라이언트 호출, 메시지 발행, 파일/S3 IO 같은 **블로킹 외부 호출**이 있는가.
2. 있다면 그 호출에 connect/read **타임아웃이 명시**돼 있는가 (기본값 무제한이면 스레드가 영영 안 돌아온다).
3. 실패 처리 로직이 **"외부는 롤백되지 않는다"를 간과**하고 있지 않은가 — `catch` 후 그냥 예외를 다시 던져 롤백에 맡기는 코드가 전형적이다.
4. 경계를 쪼갠 코드라면 **중간 상태(PENDING)와 복구 경로**가 함께 설계돼 있는가 — 쪼개기만 하고 복구가 없으면 3-6의 구멍이 그대로 남는다.

(트랜잭션 관련 AI 코드 리뷰 관점 전반은 `35-ai-code-transaction-review-checklist.md`에 따로 정리돼 있다.)

## 한 줄 요약

트랜잭션은 커넥션이라는 수십 개짜리 한정 자원의 독점 구간이므로 그 안에 외부 API 호출을 넣으면 점유 시간이 외부사 손에 넘어가고, 외부가 200ms에서 3초로 느려지는 것만으로 필요 커넥션이 11개에서 151개로 뛰어 풀은 0.6초 만에, 톰캣 스레드 200개는 5초 안에 마르며 헬스체크 실패 → 인스턴스 제외 → 남은 인스턴스 붕괴의 전면 장애로 번진다 — 게다가 롤백은 우리 DB 안만 되돌리므로 "외부 성공 + DB 롤백"과 "타임아웃 = 결과 불명"이라는 정합성 사고까지 함께 생기니, 트랜잭션 경계를 DB 작업만으로 좁혀 외부 호출을 밖으로 빼고 `PENDING → CONFIRMED / FAILED / UNKNOWN` 상태 기계와 조회 API·멱등키 기반 복구 배치로 남은 구멍까지 수렴시키는 것이 정석 설계다.
