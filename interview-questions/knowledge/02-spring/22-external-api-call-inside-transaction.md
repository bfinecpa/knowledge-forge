# 트랜잭션 안의 외부 API 호출 — 외부사 지연 하나가 전 서비스 마비로 번지는 연쇄

> 핵심 관전 포인트: **트랜잭션은 시작부터 커밋까지 DB 커넥션 1개를
> 독점한다. 그 안에서 외부 API를 호출하면 커넥션 점유 시간이 "우리가
> 통제할 수 없는 외부사의 응답 속도"에 종속된다 — 외부가 3초 느려지는
> 순간 커넥션풀이 고갈되고, 커넥션을 기다리는 톰캣 스레드까지 말라붙어
> 외부 API와 무관한 요청까지 전부 죽는다. 정합성도 깨진다: 외부 호출은
> 롤백이 안 되므로 "결제는 됐는데 주문은 롤백"이 생긴다.
> 설계는 트랜잭션 경계를 좁혀 외부 호출을 밖으로 빼고,
> 상태 기계(PENDING→CONFIRMED)로 중간 실패를 복구 가능하게 만든다.**

---

## 0. 질문 + 의도

**질문**: "트랜잭션 안에서 외부 API를 호출하면 어떤 문제가 생기나요?
어떻게 설계를 바꾸겠습니까?"

**출제 의도**: DB 커넥션을 문 채로 3초짜리 외부 호출을 기다리면, 외부사
지연 하나가 커넥션풀 고갈 → 전 서비스 마비로 번진다. 이 연쇄를 머리로
시뮬레이션할 수 있는 사람만 장애가 나기 전에 구조를 바꾼다. 대용량
서비스 면접의 핵심 변별 문항.

## 1. 트랜잭션이 실제로 점유하는 것 — 커넥션 1개, 시작부터 끝까지

`@Transactional` 메서드에 진입하면 Spring은 커넥션풀(HikariCP)에서
커넥션 하나를 꺼내 현재 스레드에 바인딩하고, **메서드가 끝나
커밋/롤백될 때까지 반환하지 않는다.** 트랜잭션 = "커넥션 독점 구간"이다.

```java
@Transactional
public Order placeOrder(OrderRequest request) {
    Order order = orderRepository.save(Order.of(request)); // DB 작업: 수 ms
    paymentClient.approve(order);   // 외부 PG 호출: 평소 300ms, 장애 시 30초
    order.confirm();                                        // DB 작업: 수 ms
    return order;
}   // ← 여기서야 커밋 + 커넥션 반환
```

이 메서드에서 실제 DB 작업은 수 ms인데, 커넥션 점유 시간은
"외부 API 응답 시간"이 지배한다. 커넥션이라는 **한정된 공유 자원의
점유 시간을 외부 시스템에 위임**해버린 구조 — 이게 문제의 본질이다.

식당에 비유하면: 테이블(커넥션)에 앉은 손님이 주문(DB 작업)은 1분 만에
끝냈는데, "친구(외부 API)가 올 때까지 계산 안 하고 앉아 있을게요"라고
하는 상황이다. 친구가 안 오면 테이블은 무한정 잠기고, 밖의 대기줄
(커넥션 대기 스레드)이 길어진다.

## 2. 장애 연쇄 시뮬레이션 — 숫자로 따라가 보기

커넥션풀 30개, 평소 외부 API 응답 300ms, 주문 API 초당 50건이라고 하자.

- **평시**: 요청당 커넥션 점유 ≈ 0.3초 → 동시 점유 커넥션 ≈ 50 × 0.3
  = 15개. 풀 30개로 여유 있다.
- **외부사 장애로 응답이 10초로 늘어남**: 동시 점유 필요량 ≈ 50 × 10
  = 500개. 풀은 30개 — 순식간에 전부 소진.
- **연쇄 1단**: 이후 요청들은 커넥션을 기다리다
  `connection-timeout`(기본 30초) 후 `SQLTransientConnectionException`.
- **연쇄 2단**: 커넥션을 기다리는 동안 **톰캣 워커 스레드도 블로킹**된다.
  스레드풀(기본 200)마저 대기 스레드로 차면, 커넥션이 필요 없는
  헬스체크·정적 응답까지 전부 매달린다.
- **연쇄 3단**: 헬스체크 실패 → 로드밸런서가 인스턴스를 제외하거나
  오케스트레이터가 재시작 → 남은 인스턴스로 트래픽이 몰려 더 빨리 사망.

**"외부 결제사 장애"가 "우리 서비스 전체 장애"로 번역되는 경로**다.
장애 원인 보고서에 "PG사 지연"이라고 쓰지만, 지연을 전면 장애로
증폭시킨 건 우리 트랜잭션 설계다.

추가로 놓치기 쉬운 한 겹: 트랜잭션이 **행 락(row lock)을 잡은 채**
외부를 기다리면, 같은 행을 갱신하려는 다른 트랜잭션들도 DB 안에서
줄줄이 대기한다. 커넥션풀 고갈에 락 경합까지 겹치는 이중 연쇄다.

## 3. 정합성 문제 — 외부 호출은 롤백이 없다

성능만의 문제가 아니다. DB 트랜잭션의 롤백은 DB 안의 변경만 되돌린다.
외부 API 호출은 이미 상대 시스템에 도달한 뒤라 **롤백으로 취소되지
않는다.**

```java
@Transactional
public Order placeOrder(OrderRequest request) {
    Order order = orderRepository.save(Order.of(request));
    paymentClient.approve(order);      // ① 결제 승인 성공 (외부 세계에 확정)
    couponService.use(request.couponId()); // ② 여기서 예외 → 전체 롤백
    return order;
}
// 결과: DB의 주문은 사라졌는데(롤백) 고객 카드는 결제됐다.
// PG사에는 승인 기록이 있고 우리 DB에는 주문이 없다 — 돈이 붕 뜬다.
```

반대 방향의 함정도 있다. 외부 호출이 **타임아웃**으로 실패하면 우리는
롤백하지만, 타임아웃은 "실패 확정"이 아니라 "결과를 모름"이다 —
상대는 처리에 성공했고 응답만 늦었을 수 있다. 이 경우에도
"결제 성공 + 주문 롤백" 불일치가 생긴다. 트랜잭션 안에 외부 호출을
넣는 순간, 롤백이 정합성을 보장해준다는 믿음 자체가 깨진다.

## 4. 설계를 바꾸는 법 — 트랜잭션 경계를 좁히고, 상태로 잇는다

### 4-1. 원칙: 트랜잭션 안에는 DB 작업만

외부 호출을 트랜잭션 밖으로 꺼내고, 트랜잭션은 짧은 DB 작업 단위로
쪼갠다. 흔한 형태가 **비(非)트랜잭션 오케스트레이터(퍼사드)** 구조다:

```java
// ✅ after: 트랜잭션 밖의 조율자가 [짧은 tx] → [외부 호출] → [짧은 tx] 순서로 진행
@Service
@RequiredArgsConstructor
public class OrderFacade {          // 이 클래스에는 @Transactional이 없다

    public Order placeOrder(OrderRequest request) {
        Order order = orderService.createPending(request); // tx1: PENDING 저장 후 커밋·커넥션 반환
        PaymentResult result = paymentClient.approve(order); // 커넥션 없이 외부 대기
        return orderService.confirm(order.getId(), result);  // tx2: 결과 반영
    }
}

@Service
public class OrderService {
    @Transactional
    public Order createPending(OrderRequest request) {
        return orderRepository.save(Order.pending(request));
    }

    @Transactional
    public Order confirm(Long orderId, PaymentResult result) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.confirm(result);
        return order;
    }
}
```

외부 API가 10초 걸려도 그동안 커넥션은 풀에 반환되어 있다.
외부사 장애가 "해당 기능의 지연"에 머물고 전 서비스로 번지지 않는다.

### 4-2. 중간 실패는 상태 기계로 복구한다

트랜잭션을 쪼개면 "tx1 커밋 후, tx2 전"에 서버가 죽거나 외부 호출이
실패하는 창이 생긴다. 이걸 하나의 큰 트랜잭션으로 되돌아가서 풀면
원점이다 — 대신 **상태 전이(PENDING → CONFIRMED / FAILED)를 데이터로
남기고, 복구 프로세스가 뒤처리**하게 설계한다.

- PENDING인 채 오래 머문 주문을 배치/스케줄러가 주기적으로 스캔한다.
- PG사에 **조회 API로 실제 결제 여부를 확인**(reconcile)해서
  CONFIRMED로 올리거나, 취소 API를 호출하고 FAILED로 내린다.
- 외부 호출에는 멱등키(idempotency key)를 실어 재시도가 중복 결제가
  되지 않게 한다.

"큰 트랜잭션 하나의 원자성"을 포기하는 대신 "**중간 상태를 관측
가능하게 만들고 언젠가는 수렴시키는**(eventually consistent) 구조"를
얻는 것이다. 이 트레이드오프를 말로 설명할 수 있어야 한다.

### 4-3. 커밋 후에만 해야 하는 부수 작업이라면 — 이벤트로

외부 호출이 "주문 결과를 결정하는" 게 아니라 알림·캐시 갱신 같은
**부수 작업**이라면, `@TransactionalEventListener(phase = AFTER_COMMIT)`
(+ `@Async`)로 커밋 확정 뒤에 실행하고, 유실이 허용되지 않으면
Transactional Outbox로 간다. (상세는
`16-spring-event-transactional-event-listener.md`,
`23-transactional-outbox-pattern.md` 참고.)

### 4-4. 외부 호출 자체의 방어선 (가산점 포인트)

구조를 바꿔도 외부 호출은 여전히 실패한다. 기본 방어 세트:

- **타임아웃 필수**: connect/read 타임아웃을 반드시 명시한다.
  기본값이 무제한인 클라이언트 설정을 그대로 쓰면 "느린 실패"가
  "무한 대기"가 된다.
- **재시도는 멱등성과 세트**: 멱등키 없이 재시도하면 중복 결제.
- **서킷 브레이커**: 외부가 죽었으면 빠르게 실패시켜 스레드를
  기다림에서 해방한다 — 연쇄 차단의 마지막 방어선.

## 5. 꼬리질문 대비 포인트

### "외부 API 호출이 실패하면 트랜잭션을 롤백하면 되는 것 아닌가?"

두 가지 이유로 불충분하다. 첫째, 타임아웃은 실패 확정이 아니다 —
상대는 성공했고 응답만 유실됐을 수 있어서, 롤백하면 "외부 성공 + DB
롤백" 불일치가 생긴다. 확정하려면 조회(reconcile) API로 실제 결과를
물어봐야 한다. 둘째, 롤백으로 정합성을 지킬 수 있는 경우라 해도
실패를 기다리는 동안 커넥션을 문 채라는 성능 문제는 그대로 남는다.
롤백은 DB 안의 세계만 되돌린다는 사실이 답의 뼈대다.

### "커넥션풀 고갈이 전 서비스 장애로 번지는 경로를 구체적으로 설명해달라"

외부 지연 → 트랜잭션(=커넥션) 점유 시간 증가 → 동시 필요 커넥션 수가
풀 크기 초과 → 이후 요청은 커넥션 대기 → 대기하는 동안 톰캣 워커
스레드도 블로킹 → 스레드풀 소진 → DB가 필요 없는 요청·헬스체크까지
응답 불가 → LB 제외/재시작 → 남은 인스턴스로 트래픽 집중.
"커넥션풀과 스레드풀이라는 두 겹의 공유 자원이 차례로 마르는 연쇄"로
설명하면 된다. 숫자(풀 30, 응답 10초, 50TPS → 필요 커넥션 500)를
붙이면 가산점.

### "트랜잭션을 쪼개면 중간 실패 시 정합성은 어떻게 지키나?" (시니어 변별 포인트)

원자성이 사라지는 게 아니라 "원자성의 단위를 줄이고, 단위 사이를
상태로 잇는" 것이다. PENDING 같은 중간 상태를 커밋해 두면 어디까지
진행됐는지 관측 가능해지고, 복구 배치가 외부 시스템에 결과를 조회해
CONFIRMED/FAILED로 수렴시킨다. 재시도를 위해 외부 호출에는 멱등키가
필수다. "큰 트랜잭션의 즉시 일관성"과 "쪼갠 구조의 최종 일관성 +
장애 격리" 사이의 트레이드오프를 요구사항으로 판단한다고 답하면
시니어 답변이다.

### "결제 승인 결과가 있어야 주문 확정이 가능한데, 그래도 트랜잭션 밖으로 뺄 수 있나?"

뺄 수 있고, 빼야 한다. "외부 결과에 의존한다"와 "같은 트랜잭션이어야
한다"는 다른 명제다. 진행 순서는 tx1(PENDING 저장) → 외부 승인 →
tx2(결과 반영)로 유지되고, 잃는 것은 "실패 시 자동 롤백"뿐인데 그
자동 롤백은 어차피 외부 세계를 되돌리지 못하므로 애초에 환상이었다.
결제처럼 진실의 원천이 외부(PG)에 있는 도메인은 조회·취소 API와
멱등키로 정합성을 맞추는 게 정석이다.

### "AI가 생성한 서비스 코드에서 이 문제를 리뷰할 때 무엇을 보나?" (가산점 포인트)

AI는 "서비스 메서드에 @Transactional"을 관성적으로 붙이는 경향이
있어서, 트랜잭션 경계 안에 RestTemplate/WebClient/FeignClient 호출이
들어간 코드를 자주 만든다. 리뷰 체크리스트: ① @Transactional 메서드
안에 HTTP 클라이언트·메시지 발행·파일 IO 같은 블로킹 외부 호출이
있는가 ② 있다면 그 호출의 타임아웃 설정은 있는가 ③ 외부 호출 결과에
따라 롤백하는 로직이 "외부는 롤백되지 않는다"를 간과하고 있는가
④ 경계를 쪼갤 때 중간 상태(PENDING)와 복구 경로가 설계됐는가.

## 한 줄 요약

트랜잭션은 커넥션이라는 한정 자원의 독점 구간이므로 그 안에 외부 API
호출을 넣으면 점유 시간이 외부사 손에 넘어가 커넥션풀 → 스레드풀
고갈의 연쇄로 전 서비스가 마비되고, 외부 호출은 롤백되지 않아 정합성
보장도 환상이 된다 — 트랜잭션 경계를 DB 작업만으로 좁히고, 외부
호출은 PENDING 상태 커밋 뒤 트랜잭션 밖에서 수행하며, 중간 실패는
상태 기계 + 조회/멱등키 기반 복구로 수렴시키는 것이 정석 설계다.
