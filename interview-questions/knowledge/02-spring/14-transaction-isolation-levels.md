# 트랜잭션 격리 수준 4가지와 이상 현상 — 매트릭스 암기가 아니라 "무엇이 끼어들어 무엇이 달라 보이는가"로 답하기

> 핵심 관전 포인트: **격리 수준은 "동시에 도는 다른 트랜잭션의 변경이 나에게 얼마나 보이는가"를 4단계(READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE)로 정한 SQL 표준이고, 각 단계는 허용하는 이상 현상으로 정의된다. 1차 변별 포인트는 세 현상을 두 축으로 가르는 것이다 — dirty read는 아직 확정되지 않은 값을 읽는 것, non-repeatable read는 같은 행을 다시 읽었더니 값이 달라진 것(원인은 UPDATE), phantom read는 같은 조건으로 다시 세었더니 행 수가 달라진 것(원인은 INSERT·DELETE). 그다음이 표준과 실제 DB의 분리다 — PostgreSQL은 MVCC로 각 트랜잭션이 자기 스냅샷에 보이는 튜플 버전만 읽으므로 dirty read가 구조적으로 불가능하고, 기본값 READ COMMITTED는 문장마다 스냅샷을 새로 뜨는 반면 REPEATABLE READ는 첫 문장 시점 스냅샷을 끝까지 유지해 표준이 허용하는 phantom까지 막으며, SERIALIZABLE은 SSI로 충돌을 사후 감지해 한쪽을 실패시키므로 애플리케이션에 재시도 준비가 필요하다(MySQL InnoDB는 기본값이 REPEATABLE READ이고 넥스트 키 락으로 막는다는 점이 다르다). 스프링에서는 `Isolation.DEFAULT`가 특정 수준이 아니라 DB 위임이고, 명시 지정은 트랜잭션을 새로 시작하는 쪽에만 적용되며 합류할 때는 조용히 무시된다. 마지막으로 재고 차감 같은 쓰기 충돌은 광역 설정인 격리 수준이 아니라 국소 도구(원자적 UPDATE·비관적 락·낙관적 락+재시도)로 푸는 것이 정석이라는 판단까지가 이 질문의 전체 사거리다.**

## 0. 질문 + 의도

**질문**: "트랜잭션 격리 수준 4가지와 각각에서 발생 가능한 문제(dirty read, non-repeatable read, phantom read)를 설명해주세요."

**출제 의도**: 격리 수준은 "정합성 버그가 재현 안 되는 이유"의 단골 원인이다. non-repeatable read를 모르면 "같은 트랜잭션에서 두 번 읽었는데 값이 달라요"라는 버그 리포트 앞에서 코드만 백날 들여다본다 — 동시성 버그를 코드가 아니라 격리 수준 관점에서 진단할 수 있는지 확인하는 질문이다.

## 1. 세 가지 이상 현상 — 무엇이 끼어들어 무엇이 달라 보이는가

### 1-1. 전제 지식 — 격리성은 왜 4단계로 쪼개졌나

트랜잭션의 ACID 중 **I(Isolation, 격리성)**는 "동시에 실행되는 트랜잭션들이 서로 없는 것처럼 보이게 한다"는 성질이다. 내 트랜잭션이 도는 동안 세상에 나 혼자만 있는 것처럼 보여야 한다는 뜻이다.

이걸 완벽하게 지키는 방법은 사실 하나뿐이다. **트랜잭션을 한 줄로 세워 하나씩 순차 실행하는 것.** 그러면 서로 끼어들 틈이 없으니 완벽하다. 그리고 동시성이 죽는다. 초당 수천 건을 처리해야 하는 서비스에서 이건 선택지가 아니다.

그래서 SQL 표준은 타협을 제도화했다. **"어떤 이상 현상까지는 눈감아 줄 것인가"를 4단계로 정의**한 것이다. 여기서 중요한 것은 순서다. **이상 현상이 먼저 정의되고, 격리 수준은 그 현상들의 허용 여부로 정의된다.** 격리 수준을 외우려 하지 말고 이상 현상을 이해해야 하는 이유가 이것이다.

| 격리 수준 | Dirty Read | Non-Repeatable Read | Phantom Read |
|---|---|---|---|
| READ UNCOMMITTED | 허용 | 허용 | 허용 |
| READ COMMITTED | 방지 | 허용 | 허용 |
| REPEATABLE READ | 방지 | 방지 | 허용 |
| SERIALIZABLE | 방지 | 방지 | 방지 |

아래로 갈수록 격리가 강해지고 이상 현상이 줄지만, 대신 동시성이 떨어진다. 락을 더 오래·더 넓게 잡거나, 옛 버전을 더 오래 보관하거나, 충돌 검사 비용을 더 치러야 하기 때문이다. **격리 수준 선택은 정합성과 동시성의 트레이드오프다.**

이 표는 어디까지나 **표준의 정의**라는 점을 기억해 두자. 2절에서 보겠지만 실제 DB의 동작은 이 표보다 강하기도 하고 다르기도 하다.

### 1-2. Dirty Read — 아직 확정되지 않은 값을 읽는다

세 현상 모두 "트랜잭션 A가 읽는 중에 트랜잭션 B가 끼어드는" 시나리오다. 표를 외우는 것보다 이 시간 순서를 손으로 그릴 수 있어야 면접에서 무너지지 않는다.

```text
시간 ↓   Tx A (결제 승인 판정)                  Tx B (잔액 차감 시도)
────────────────────────────────────────────────────────────────────
 t1                                             BEGIN
 t2                                             UPDATE 잔액 = 0 WHERE id=1
                                                (아직 COMMIT 하지 않았다)
 t3      BEGIN
 t4      SELECT 잔액 WHERE id=1
           -> 0 을 읽는다                       ← 확정되지 않은 값을 봤다
 t5      "잔액 부족" 판정 -> 결제 거절
 t6                                             ROLLBACK
           ↑ 잔액 0은 세상에 한 번도 존재한 적이 없는 값이 되었다
 t7      COMMIT
           결과: 잔액이 멀쩡한 고객의 결제를 거절했고, 그 근거가 된 값은
                 DB 어디에도 남아 있지 않아 원인 추적이 거의 불가능하다
```

**dirty(더러운)라는 이름이 붙은 이유**가 여기 있다. 읽은 값이 확정된 사실이 아니라 언제든 취소될 수 있는 "작업 중인 오물"이기 때문이다. 롤백이 일어나는 순간 그 값은 소급해서 존재하지 않았던 것이 되므로, 그것을 근거로 내린 판정은 전부 근거를 잃는다.

가장 위험한 현상이라 READ UNCOMMITTED를 제외한 모든 수준에서 막는다. 그리고 실무에서 READ UNCOMMITTED를 쓰는 경우는 사실상 없다.

### 1-3. Non-Repeatable Read — 같은 행을 다시 읽었더니 값이 달라졌다

```text
시간 ↓   Tx A (정산 리포트 생성)                Tx B (고객의 출금 요청)
────────────────────────────────────────────────────────────────────
 t1      BEGIN
 t2      SELECT 잔액 WHERE id=1
           -> 10,000                            (이 값으로 앞부분 계산)
 t3                                             BEGIN
 t4                                             UPDATE 잔액 = 5,000 WHERE id=1
 t5                                             COMMIT   ← 정상적으로 확정된 값
 t6      SELECT 잔액 WHERE id=1
           -> 5,000                             ← 같은 행, 같은 트랜잭션, 다른 값
 t7      COMMIT
           결과: 10,000 을 전제로 만든 앞부분과 5,000 을 전제로 만든 뒷부분이
                 한 리포트 안에 섞인다. 합계가 안 맞는데 각 값은 다 정상이다.
```

dirty read와 결정적으로 다른 점은 **두 번 다 "정상적으로 커밋된 값"을 읽었다**는 것이다. 어느 값도 틀리지 않았다. 문제는 **한 트랜잭션 안에서 같은 것을 두 번 봤는데 답이 달라졌다**는 것 — 다시 읽을 수 없다(non-repeatable)는 이름 그대로다.

"잔액을 확인한 뒤 그 값을 전제로 계산을 이어 가는" 로직은 이 지점에서 무너진다. 확인과 사용 사이에 세상이 바뀌었기 때문이다.

READ COMMITTED에서는 발생한다. "커밋된 것만 읽는다"는 규칙은 지키지만 **매 SELECT마다 그 시점의 최신 커밋을 읽기** 때문이다. REPEATABLE READ부터 막힌다. 트랜잭션이 처음 읽은 시점의 세상을 끝까지 그대로 유지해 주기 때문이다.

### 1-4. Phantom Read — 같은 조건으로 다시 세었더니 행 수가 달라졌다

```text
시간 ↓   Tx A (고액 급여자 감사)                Tx B (신규 입사 처리)
────────────────────────────────────────────────────────────────────
 t1      BEGIN
 t2      SELECT count(*) WHERE 급여 > 500
           -> 3건                               (보고서에 "대상 3명"이라 적음)
 t3                                             BEGIN
 t4                                             INSERT 급여 600 인 직원 1명
 t5                                             COMMIT
 t6      SELECT * WHERE 급여 > 500
           -> 4건                               ← 없던 행이 나타났다
 t7      COMMIT
           결과: "대상 3명"이라고 써 놓고 4명의 급여를 합산한 보고서가 나온다
```

**유령(phantom)**이라는 이름은 없던 행이 홀연히 나타나는 모습에서 왔다. 반대로 DELETE로 있던 행이 사라지는 것도 같은 부류다.

### 1-5. 두 축으로 가른다 — 여기가 1차 변별 포인트

주니어가 가장 못 구분하는 것이 non-repeatable read와 phantom read다. 둘 다 "다시 읽었더니 다르다"로 들리기 때문이다. 축을 이렇게 갈라 두면 헷갈릴 여지가 없다.

|  | 무엇이 달라졌나 | 무엇을 다시 읽었나 | 원인이 되는 작업 |
|---|---|---|---|
| **Non-repeatable read** | 이미 읽은 **그 행의 값** | 같은 행 (`WHERE id = 1`) | **UPDATE** |
| **Phantom read** | 조건에 걸리는 **행의 개수** | 같은 조건 (`WHERE 급여 > 500`) | **INSERT / DELETE** |

한 문장으로 외운다면 이렇게 된다. **"같은 행을 다시 읽었더니 값이 달라졌다" vs "같은 조건으로 다시 세었더니 행 수가 달라졌다".**

### 1-6. 왜 굳이 따로 구분하나 — 막는 방법이 다르기 때문이다

이 질문에 답할 수 있으면 암기가 아니라 이해로 들린다. (가산점 포인트)

**기존 행의 값 변경은 그 행을 잠그면 막힌다.** `id = 1`인 행에 락을 걸어 두면 다른 트랜잭션이 그 행을 UPDATE하지 못한다. 대상이 이미 존재하므로 잠글 대상이 명확하다.

**그런데 아직 존재하지 않는 행의 INSERT는 행 락으로 막을 수 없다.** 존재하지 않는 것을 잠글 수는 없기 때문이다. `급여 > 500`이라는 조건에 나중에 들어올 행을 미리 막으려면, 행이 아니라 **조건에 해당하는 범위 자체**를 잠그거나, 아예 순차 실행에 준하는 제어가 필요하다.

**방어 수단의 난이도가 다르니 단계도 따로 나뉜 것이다.** 그래서 표준에서는 REPEATABLE READ까지는 phantom을 허용하고, SERIALIZABLE에서만 막는다. 현상의 분류가 아니라 **방어 수단의 분류**라고 답하면 정확하다.

## 2. DB는 격리 수준을 어떤 메커니즘으로 구현하는가 — PostgreSQL 기준

여기까지가 표준의 정의다. 그런데 면접에서 진짜 갈리는 지점은 **"그래서 지금 쓰는 DB는 이걸 어떻게 구현하고 있는가"**다. 이 절의 서술은 **PostgreSQL**을 기준으로 하고, 필요한 곳에서 MySQL(InnoDB)과 대비한다.

### 2-1. MVCC — 값을 덮어쓰지 않고 새 버전을 쌓는다

PostgreSQL이 격리를 구현하는 토대는 **MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)**다. 이름 그대로 **한 행에 대해 여러 버전을 동시에 보관하고, 트랜잭션마다 자기가 볼 버전을 고르게 하는** 방식이다.

핵심은 **UPDATE가 기존 값을 덮어쓰지 않는다**는 것이다. 새 버전을 하나 더 쓴다.

```text
UPDATE 잔액 = 5,000 WHERE id = 1   을 205번 트랜잭션이 실행했을 때

  [기존 튜플]  id=1  잔액 10,000   xmin=100   xmax=205
  [새 튜플]    id=1  잔액  5,000   xmin=205   xmax=(없음)

  xmin = 이 버전을 만들어 낸 트랜잭션 번호
  xmax = 이 버전을 무효화한 트랜잭션 번호 (아직 없으면 비어 있음)

  "튜플(tuple)"은 PostgreSQL이 디스크에 저장하는 행 하나의 물리적 실체를 부르는 말이다.
  한 논리적 행(id=1)이 여러 개의 물리적 튜플로 존재할 수 있다는 것이 MVCC의 출발점이다.
```

그리고 각 트랜잭션은 읽기를 시작할 때 **스냅샷(snapshot)**을 뜬다. 스냅샷은 사진이 아니라 **"이 시점에 어떤 트랜잭션들이 이미 커밋을 마쳤는가"를 적어 둔 명단**이다. 튜플을 하나 만날 때마다 이 명단과 대조해 보이는지 판정한다.

```text
어떤 튜플 버전이 나에게 보이는가?

  ① 이 버전을 만든 트랜잭션(xmin)이 내 스냅샷 기준으로 이미 커밋됐는가?
        아니오 -> 안 보인다 (아직 진행 중이거나 나보다 나중에 시작한 트랜잭션의 작업)
  ② 이 버전을 무효화한 트랜잭션(xmax)이 내 스냅샷 기준으로 이미 커밋됐는가?
        예 -> 안 보인다 (내가 보기엔 이미 지워진 버전)
  ③ 둘 다 통과 -> 이 버전이 내가 읽을 값이다
```

**여기서 dirty read가 왜 구조적으로 불가능한지가 곧바로 나온다.** 아직 커밋하지 않은 트랜잭션이 만든 튜플은 ①에서 걸러진다. **읽기 규칙 자체가 "커밋된 것만 본다"이므로, 커밋 안 된 값을 읽는 경로가 애초에 없다.** 그래서 PostgreSQL은 READ UNCOMMITTED를 요청받아도 READ COMMITTED로 처리한다 — 더 낮출 방법이 없어서다.

MVCC의 또 다른 결과 하나도 알아 두면 좋다. **읽기는 쓰기를 막지 않고, 쓰기도 읽기를 막지 않는다.** 읽는 쪽은 옛 버전을 보면 되고 쓰는 쪽은 새 버전을 쓰면 되기 때문이다. 락으로 격리를 구현하던 옛 DB와 결정적으로 다른 점이다.

### 2-2. READ COMMITTED — 문장마다 스냅샷을 새로 뜬다

PostgreSQL의 기본 격리 수준이다. 규칙은 하나다. **각 SQL 문장이 시작될 때마다 스냅샷을 새로 뜬다.**

```text
BEGIN                    (아직 스냅샷 없음)
SELECT ...   ← 스냅샷 #1 을 뜬다. 이 시점까지 커밋된 세상을 본다.
             ... 이 사이에 다른 트랜잭션들이 커밋한다 ...
SELECT ...   ← 스냅샷 #2 를 새로 뜬다. 방금 커밋된 것까지 보인다.
COMMIT
```

**그래서 dirty read는 없고, non-repeatable read와 phantom read는 그대로 발생한다.** 1-3과 1-4의 타임라인이 PostgreSQL 기본 설정에서 실제로 재현되는 시나리오라는 뜻이다. 이 사실을 아는 것과 모르는 것의 차이가 크다 — "우리는 기본값이니까 괜찮겠지"가 아니라 "우리는 기본값이니까 이 둘은 언제든 난다"가 맞는 인식이다.

쓰기 쪽에는 규칙이 하나 더 붙는다. UPDATE나 DELETE가 대상 행을 찾았는데 그 행을 다른 트랜잭션이 이미 갱신 중이라면, **그 트랜잭션이 끝날 때까지 기다린 뒤 최신 버전으로 WHERE 조건을 다시 평가한다.** 이 성질이 3-6의 "원자적 UPDATE"가 READ COMMITTED에서도 안전한 근거가 된다.

### 2-3. REPEATABLE READ — 스냅샷을 하나로 고정한다

규칙은 단순하다. **트랜잭션의 첫 문장이 뜬 스냅샷을 트랜잭션이 끝날 때까지 그대로 재사용한다.**

정확히 말하면 `BEGIN` 시점이 아니라 **첫 번째 실제 문장이 실행되는 시점**이다. `BEGIN`만 해 두고 5분 뒤에 첫 SELECT를 날리면 스냅샷은 그 5분 뒤에 떠진다. 사소해 보이지만 "트랜잭션을 언제 열었느냐"가 아니라 "언제 처음 읽었느냐"가 기준이라는 점은 디버깅할 때 실제로 차이를 만든다.

스냅샷이 하나로 고정되므로 **non-repeatable read가 사라진다.** 그리고 여기서 표준을 앞지르는 일이 벌어진다. **phantom read도 함께 사라진다.** 스냅샷 이후에 커밋된 INSERT는 어떤 조건으로 조회하든 보이지 않기 때문이다. 표준은 REPEATABLE READ에서 phantom을 허용하지만, PostgreSQL의 구현은 그보다 강하다.

대신 쓰기에서 새로운 실패 모드가 생긴다. 내 스냅샷 이후에 다른 트랜잭션이 커밋한 행을 내가 UPDATE하려고 하면, PostgreSQL은 그 갱신을 허용하지 않고 트랜잭션을 실패시킨다.

```text
ERROR:  could not serialize access due to concurrent update
SQLSTATE: 40001
```

**이 오류를 만나는 순간 그 트랜잭션은 끝이다. 애플리케이션이 처음부터 다시 실행해야 한다.** 격리 수준을 올리면 "더 안전해진다"가 아니라 **"실패의 형태가 바뀐다"**는 것이 정확한 이해다. 조용한 데이터 오염이 시끄러운 예외로 바뀌는 것이고, 그 예외를 받아 줄 재시도 코드는 애플리케이션 몫이다.

### 2-4. SERIALIZABLE — SSI로 사후에 잡아내고 실패시킨다

가장 강한 수준이다. 보장하는 것은 **"동시에 실행된 트랜잭션들의 결과가, 그것들을 어떤 순서로든 한 줄로 세워 실행한 결과와 같아야 한다"**는 것이다.

PostgreSQL은 이것을 락이 아니라 **SSI(Serializable Snapshot Isolation, 직렬화 가능 스냅샷 격리)**로 구현한다. 동작 방식이 독특하니 순서대로 보자.

```text
① 각 트랜잭션은 REPEATABLE READ처럼 자기 스냅샷으로 자유롭게 읽는다.
     읽기는 아무도 막지 않는다.
② 대신 DB가 "누가 무엇을 읽었는지"를 기록해 둔다.
     조건 조회라면 그 조건이 걸치는 범위를 통째로 기록한다 (술어 락, predicate lock).
③ 커밋 시점에 트랜잭션들 사이의 읽기-쓰기 의존 관계를 검사한다.
     어떤 순서로 줄을 세워도 설명이 안 되는 조합이 발견되면
④ 그중 한 트랜잭션을 실패시킨다.

     ERROR:  could not serialize access due to read/write dependencies
             among transactions
     SQLSTATE: 40001
```

**락으로 미리 막는 것이 아니라 일단 진행시킨 뒤 사후에 잡아내는 방식**이라, 충돌이 없으면 REPEATABLE READ와 성능이 비슷하다. 읽기가 블로킹되지 않는다는 것이 특히 중요한 장점이다. 대신 충돌이 잦으면 실패와 재시도가 늘어 처리량이 급격히 떨어진다.

그래서 SERIALIZABLE을 쓰기로 했다면 **재시도가 옵션이 아니라 필수 구성 요소**다.

```java
// SQLSTATE 40001 은 "다시 하면 될 수도 있다"는 뜻의 일시적 실패다.
// 스프링은 이 계열을 ConcurrencyFailureException 하위 타입으로 번역해 올려 준다.
// 주의: 재시도는 반드시 "새 트랜잭션"으로 처음부터 다시 실행해야 한다.
//       이미 실패한 트랜잭션 안에서는 어떤 문장도 더 실행할 수 없다.
@Retryable(retryFor = ConcurrencyFailureException.class,
           maxAttempts = 3,
           backoff = @Backoff(delay = 50, multiplier = 2))
@Transactional(isolation = Isolation.SERIALIZABLE)
public void issueCoupon(Long eventId, Long userId) { ... }
```

그럼 REPEATABLE READ로 충분하지 않고 SERIALIZABLE이 필요한 경우는 언제인가. 스냅샷 격리가 못 막는 이상 현상이 하나 남아 있기 때문이다. **쓰기 왜곡(write skew)**이라고 부른다.

```text
쿠폰 발급 한도 100장. 현재 99장 발급됨. 두 요청이 동시에 들어온다.

시간 ↓   Tx A                                Tx B
──────────────────────────────────────────────────────────────
 t1      SELECT count(*) FROM coupon -> 99
 t2                                          SELECT count(*) FROM coupon -> 99
 t3      "99 < 100 이니 발급 가능"
 t4                                          "99 < 100 이니 발급 가능"
 t5      INSERT coupon (A용)   COMMIT
 t6                                          INSERT coupon (B용)   COMMIT

  결과: 101장.  두 트랜잭션은 서로 다른 행을 INSERT 했으므로 행 충돌이 없고,
        REPEATABLE READ 의 스냅샷 격리로는 아무 문제도 감지되지 않는다.
        각자가 "읽은 조건"이 상대의 INSERT 때문에 무효가 됐다는 사실은
        읽은 범위를 추적하는 SERIALIZABLE 만이 알아챌 수 있다.
```

**서로 다른 행을 쓰기 때문에 행 단위 방어가 통하지 않는다** — 이것이 write skew의 본질이고, SERIALIZABLE이 존재하는 이유다.

### 2-5. 교과서 표준 vs PostgreSQL의 실제

이제 1-1의 표를 PostgreSQL의 실제 동작으로 다시 그릴 수 있다. 실무 답변에는 반드시 이 분리가 들어가야 한다.

| 요청한 격리 수준 | PostgreSQL의 실제 동작 | Dirty | Non-repeatable | Phantom | Write skew |
|---|---|---|---|---|---|
| READ UNCOMMITTED | READ COMMITTED로 처리 | 불가 | 발생 | 발생 | 발생 |
| **READ COMMITTED (기본값)** | 문장마다 새 스냅샷 | 불가 | 발생 | 발생 | 발생 |
| REPEATABLE READ | 첫 문장 스냅샷을 끝까지 고정 | 불가 | 방지 | **방지** (표준은 허용) | 발생 |
| SERIALIZABLE | SSI로 충돌 감지 후 한쪽 실패 | 불가 | 방지 | 방지 | 방지 |

MySQL을 함께 쓰는 조직이라면 대비도 알아 두는 것이 좋다. **두 DB는 기본값부터 다르다.**

| | PostgreSQL | MySQL (InnoDB) |
|---|---|---|
| 기본 격리 수준 | **READ COMMITTED** | **REPEATABLE READ** |
| 옛 버전 보관 위치 | 테이블 안에 옛 튜플이 그대로 남고 VACUUM이 청소 | 언두(undo) 로그에 따로 보관 |
| REPEATABLE READ의 phantom | 스냅샷 고정으로 막힌다 | 일반 SELECT는 스냅샷으로, `FOR UPDATE` 같은 잠금 읽기는 넥스트 키 락(레코드 락 + 갭 락)으로 막는다. 한 트랜잭션에서 둘을 섞으면 어긋난 결과가 보일 수 있다 |
| SERIALIZABLE 구현 | SSI — 진행시킨 뒤 충돌을 감지해 실패시킨다 | 일반 SELECT까지 잠금 읽기로 바꿔 대기시킨다 |

**"지금 쓰는 서비스 DB의 기본 격리 수준이 뭔지 아는가"는 실무 감각을 보는 단골 확인 질문**이다. 같은 애플리케이션 코드가 PostgreSQL 위에서는 READ COMMITTED로, MySQL 위에서는 REPEATABLE READ로 돈다는 것은, **DB를 이전하면 코드를 한 줄도 안 바꿨는데 동시성 동작이 바뀐다**는 뜻이기도 하다.

확인하는 SQL도 알아 두자.

```sql
-- PostgreSQL
SHOW transaction_isolation;

-- MySQL
SELECT @@transaction_isolation;
```

### 2-6. 공짜가 아니다 — 죽은 튜플과 VACUUM

MVCC의 대가를 짚어야 설명이 완성된다. UPDATE가 새 버전을 쌓기만 한다면, 아무도 보지 않게 된 옛 버전은 누가 치우는가.

PostgreSQL에서 그 청소부가 **VACUUM**이다. **어떤 트랜잭션에게도 더 이상 보이지 않는 튜플(죽은 튜플)을 찾아 공간을 재사용 가능하게 만드는 작업**이고, 보통 오토배큠이 백그라운드에서 알아서 돌린다.

여기에 실무 함정이 하나 있다. **오래 열려 있는 트랜잭션은 VACUUM을 방해한다.** 그 트랜잭션의 스냅샷에 아직 보일 수도 있는 옛 버전은 지울 수 없기 때문이다. 결과는 테이블 부풀기(bloat)와 스캔 성능 저하이고, 죽은 튜플이 계속 쌓이는 이 상태는 특정 테이블이 아니라 DB 전체의 문제로 번진다.

그래서 격리 수준과 트랜잭션 길이는 함께 봐야 한다. **REPEATABLE READ로 스냅샷을 고정한 채 몇십 분짜리 정산 배치를 돌리는 것은, 그 시간 내내 DB 전체의 청소를 붙잡아 두는 결정**이다. 격리 수준을 올렸을 때 치르는 비용이 그 트랜잭션 하나에만 국한되지 않는다는 감각이 시니어의 감각이다.

## 3. 스프링에서 격리 수준을 다룰 때 — 그리고 격리 수준으로 풀 문제 vs 락으로 풀 문제

이 질문이 02-spring 섹션에 있는 이유가 여기 있다. 격리 수준을 "아는 것"과 "스프링 코드에서 올바르게 다루는 것" 사이에 함정이 몇 개 놓여 있다.

### 3-1. `Isolation.DEFAULT`는 특정 수준이 아니다

```java
@Transactional  // isolation 을 생략하면 Isolation.DEFAULT
public BalanceSummary summarize(Long accountId) { ... }
```

`Isolation.DEFAULT`는 **"스프링이 정하지 않고 DB(커넥션)의 기본값을 그대로 따른다"**는 뜻이다. 즉 같은 코드가 PostgreSQL 위에서는 READ COMMITTED로, MySQL 위에서는 REPEATABLE READ로 돈다.

그래서 "스프링 트랜잭션의 기본 격리 수준은?"이라는 질문에 `READ_COMMITTED`라고 박아 답하면 틀린다. **"DB 위임"이 정답이고, 굳이 수준을 말하려면 "우리 DB가 PostgreSQL이니 결과적으로 READ COMMITTED"라고 조건을 붙여야 한다.**

### 3-2. 명시 지정이 DB까지 실제로 전달되는가

```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public SettlementReport settle(YearMonth month) { ... }
```

이렇게 적으면 무슨 일이 일어나는가. 트랜잭션 매니저가 트랜잭션을 **새로 시작할 때** 커넥션에 `Connection.setTransactionIsolation(...)`을 호출하고, 트랜잭션이 끝나면 원래 값으로 되돌린다. 커넥션 풀을 여러 스레드가 돌려 쓰므로, DB 전역 설정을 건드리는 대신 이렇게 **트랜잭션 단위로 걸었다 푸는 것이 정석**이다.

다만 "그 호출이 항상 일어나는가"는 트랜잭션 매니저와 다이얼렉트에 달렸다. 갈래를 정확히 나눠 두자.

**JDBC/MyBatis에서 쓰는 `DataSourceTransactionManager`**는 커넥션을 직접 다루므로 문제없이 적용된다.

**JPA에서 쓰는 `JpaTransactionManager` + 하이버네이트 조합**도 적용된다. 스프링이 하이버네이트 세션에서 물리 커넥션을 꺼내 같은 방식으로 격리 수준을 설정하기 때문이다. 단 조건이 있다 — **커넥션을 트랜잭션 내내 붙들고 있는 구성이어야 한다.** 스프링 부트의 기본 구성이 이 조건을 만족하므로 보통은 신경 쓸 일이 없지만, 커넥션 획득/반납 정책을 직접 바꿨다면 이야기가 달라진다. 조건이 어긋나면 조용히 무시되는 게 아니라 **`InvalidIsolationLevelException`이 발생한다.**

**하이버네이트가 아닌 JPA 구현체를 전용 다이얼렉트 없이 쓰는 경우**에는 표준 JPA API만으로 격리 수준을 설정할 방법이 없어서, 마찬가지로 `InvalidIsolationLevelException`이 난다.

여기서 정리해 둘 문장은 이것이다. **적용되거나, 못 하면 예외를 던진다. 조용히 무시되는 경우는 딱 하나 — 다음 절의 합류다.**

### 3-3. 함정 하나 — 합류하는 트랜잭션에는 적용되지 않는다

격리 수준은 **커넥션에, 트랜잭션을 시작하는 시점에** 설정된다. 그러면 이미 시작된 트랜잭션에 나중에 합류하는 메서드는 어떻게 될까. 설정할 시점이 이미 지나갔다.

```java
// before: 의도대로 동작하지 않는 코드
@Service
public class OrderService {
    @Transactional   // 여기서 트랜잭션이 시작된다 (DB 기본값으로)
    public void placeOrder(OrderCommand cmd) {
        stockService.checkStock(cmd);
    }
}

@Service
public class StockService {
    // 의도: "재고 확인은 항상 최신 커밋을 봐야 하니 READ_COMMITTED 로!"
    @Transactional(isolation = Isolation.READ_COMMITTED)
    public void checkStock(OrderCommand cmd) { ... }
    // 문제: 전파 기본값 REQUIRED 로 placeOrder 의 트랜잭션에 합류한다.
    //       트랜잭션을 새로 시작하지 않으므로 격리 수준 지정은 조용히 무시되고,
    //       실제로는 바깥 트랜잭션의 격리 수준으로 돈다.
}
```

```java
// 고침 (1): 정말 다른 격리 수준이 필요하다면 트랜잭션을 새로 시작해야 한다
@Transactional(isolation = Isolation.READ_COMMITTED,
               propagation = Propagation.REQUIRES_NEW)
public void checkStock(OrderCommand cmd) { ... }
// 다만 REQUIRES_NEW 는 커넥션을 하나 더 점유한다 — 풀 고갈과 자기 데드락의
// 비용을 알고 써야 한다 (12번 전파 문서 참고).
```

```java
// 고침 (2): 불일치를 조용히 넘기지 말고 예외로 드러나게 만든다
//   트랜잭션 매니저 설정: setValidateExistingTransaction(true)
//   -> 합류 시 격리 수준이나 읽기 전용 여부가 어긋나면
//      IllegalTransactionStateException 을 던진다
```

**"격리 수준은 트랜잭션을 새로 시작하는 쪽이 정한다"**는 한 문장으로 정리하면 전파 질문([12번 문서](12-transaction-propagation-required-vs-requires-new.md))과 자연스럽게 연결된다. (가산점 포인트)

### 3-4. 함정 둘 — 애초에 트랜잭션이 있기는 한가

"같은 메서드에서 두 번 읽었는데 값이 달라요"라는 증상이 격리 수준 문제가 **아닐** 수도 있다.

프록시 자기 호출 같은 이유로 `@Transactional`이 적용되지 않으면, 각 SELECT가 **각자 별도의 자동 커밋 트랜잭션**으로 실행된다. 트랜잭션이 두 개니 당연히 스냅샷도 두 개다. 이러면 REPEATABLE READ를 쓰는 DB에서도 non-repeatable read처럼 보이는 현상이 그대로 난다.

**격리 수준을 의심하기 전에 "두 읽기가 정말 같은 트랜잭션 안인가"부터 확인하는 것이 진단의 정석**이다. 확인 수단은 트랜잭션 로그를 켜 보거나, 코드에서 `TransactionSynchronizationManager.isActualTransactionActive()`로 찍어 보는 것이다. ([자기 호출 문서](11-transactional-self-invocation.md) 참고.)

### 3-5. 전제 지식 — lost update가 무엇인가

다음 절로 넘어가기 전에 용어 하나를 깔아야 한다. 낙관적 락을 이야기하려면 그것이 막으려는 현상을 먼저 알아야 하기 때문이다.

**갱신 분실(lost update)**은 두 트랜잭션이 같은 데이터를 각자 읽어 각자 계산한 뒤 각자 쓰는 바람에, **한쪽의 갱신이 흔적도 없이 사라지는** 현상이다.

```text
재고 10개. 두 주문이 동시에 1개씩 차감한다.

시간 ↓   Tx A                                Tx B
──────────────────────────────────────────────────────────────
 t1      SELECT stock -> 10
 t2                                          SELECT stock -> 10
 t3      애플리케이션에서 계산: 10 - 1 = 9
 t4                                          애플리케이션에서 계산: 10 - 1 = 9
 t5      UPDATE stock = 9   COMMIT
 t6                                          UPDATE stock = 9   COMMIT

  결과: 재고 9.  2개를 팔았는데 1개만 줄었다.
        B가 t2에서 읽은 10은 t5 이후로는 낡은 값이 됐는데,
        B는 그 사실을 모른 채 낡은 값으로 계산한 결과를 덮어썼다.
```

**읽기와 쓰기 사이에 틈이 있고, 그 틈에서 세상이 바뀌었는데도 낡은 값으로 계산한 결과를 쓰는 것** — 이것이 lost update의 구조다.

PostgreSQL 기준으로 격리 수준별 결과를 정확히 알아 두면 좋다. **READ COMMITTED에서는 위 시나리오가 그대로 발생한다.** 반면 **REPEATABLE READ에서는 t6이 `could not serialize access due to concurrent update`로 실패**한다(2-3). 스냅샷 이후에 커밋된 행을 갱신하려 했기 때문이다. 즉 PostgreSQL의 REPEATABLE READ는 lost update를 **막아 주는 것이 아니라 실패로 알려 준다.** 그래서 재시도가 짝으로 붙어야 한다.

### 3-6. 재고 차감을 푸는 네 갈래 — 비용과 함께 대비하기

이제 이 문서의 시니어 변별 대목이다. **"동시성 문제니까 격리 수준을 올리자"**는 반응이 왜 대개 틀린 처방인지를 구체 사례로 보여야 한다.

**갈래 A — 격리 수준을 올린다.**

```java
@Transactional(isolation = Isolation.SERIALIZABLE)
public void decrease(Long itemId) {
    Item item = itemRepository.findById(itemId).orElseThrow();
    item.decreaseStock(1);
}
```

기술적으로는 막힌다. 문제는 **격리 수준이 이 트랜잭션 전체에 걸리는 광역 설정**이라는 것이다. 이 메서드가 재고 외에 다른 조회를 열 개 더 한다면 그 열 개도 전부 충돌 검사 대상이 되고, 무관한 읽기까지 40001 실패에 휘말린다. 게다가 이 방식은 재시도 코드를 반드시 동반해야 한다. **국소적인 문제를 광역 설정으로 푸는 대표적 오답이다.**

**갈래 B — 원자적 UPDATE (읽기·판단·쓰기를 한 문장으로).**

```sql
UPDATE item SET stock = stock - 1 WHERE id = 1 AND stock >= 1;
-- 갱신된 행 수가 0이면 재고 부족이라는 뜻이다
```

lost update의 원인이 "읽기와 쓰기 사이의 틈"이었으므로, **틈 자체를 없애는 것**이 가장 근본적인 해법이다. `stock - 1`을 애플리케이션이 아니라 DB가 계산하고, `stock >= 1` 판정도 같은 문장 안에서 한다.

READ COMMITTED에서도 이것이 안전한 이유가 중요하다. 2-2에서 본 규칙 때문이다. **UPDATE는 대상 행에 잠금을 걸고, 다른 트랜잭션이 그 행을 갱신 중이면 끝날 때까지 기다린 뒤 최신 버전으로 조건을 다시 평가한다.** 그래서 `stock >= 1` 검사는 언제나 최신 값 기준으로 이뤄진다.

**가장 싸고 가장 확실하다.** 잠금은 그 행 하나에만, 그것도 아주 짧게 걸린다. 다만 한계가 있다 — 읽고-판단-쓰기를 한 문장으로 표현할 수 있을 때만 쓸 수 있고, 복잡한 도메인 규칙은 담기 어렵다. JPA에서 쓸 때는 이 UPDATE가 영속성 컨텍스트를 우회하므로 1차 캐시의 엔티티가 낡은 값을 들고 있게 된다는 점도 챙겨야 한다.

**갈래 C — 비관적 락 (먼저 잠그고 읽는다).**

```sql
SELECT stock FROM item WHERE id = 1 FOR UPDATE;
-- 이 행을 내 트랜잭션이 끝날 때까지 아무도 갱신하지 못하게 잠근다
```

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)   // FOR UPDATE 로 번역된다
@Query("select i from Item i where i.id = :id")
Optional<Item> findByIdForUpdate(@Param("id") Long id);
```

**비관적(pessimistic)**이라는 이름은 "충돌이 날 것이라고 비관적으로 가정하고 미리 막는다"에서 왔다. 읽는 시점에 이미 잠그므로 lost update가 원천적으로 불가능하다.

비용은 **대기**다. 락을 쥔 트랜잭션이 끝날 때까지 같은 행을 원하는 다른 트랜잭션은 전부 줄을 선다. 그리고 기다리는 동안 각자 DB 커넥션을 붙잡고 있으므로, 경합이 심하면 **커넥션 풀 고갈로 번진다.** 여러 행을 서로 다른 순서로 잠그면 데드락도 난다.

PostgreSQL에는 대기를 제어하는 선택지가 있다. `FOR UPDATE NOWAIT`은 잠겨 있으면 기다리지 않고 즉시 실패하고, **`FOR UPDATE SKIP LOCKED`**는 잠긴 행을 건너뛰고 다음 행을 집는다. 작업 큐를 여러 워커가 나눠 처리할 때 쓰는 관용구다.

**갈래 D — 낙관적 락 + 재시도.**

```java
@Entity
public class Item {
    @Id private Long id;
    private int stock;

    @Version                 // 이 필드가 있으면 하이버네이트가 UPDATE 문에
    private Long version;    // WHERE version = ? 를 자동으로 끼워 넣는다
}
```

```sql
-- 하이버네이트가 만들어 내는 SQL
UPDATE item SET stock = 9, version = 6 WHERE id = 1 AND version = 5;
-- 갱신된 행 수가 0이면 "내가 읽은 뒤 누군가 먼저 바꿨다"는 뜻이다
-- -> ObjectOptimisticLockingFailureException
```

**낙관적(optimistic)**이라는 이름은 "충돌은 드물 것이라고 낙관하고 일단 진행한 뒤, 커밋 시점에 확인한다"에서 왔다. 잠그지 않으므로 대기가 없다.

비용은 **버려지는 작업**이다. 충돌이 감지되면 그때까지 한 일을 전부 버리고 트랜잭션을 처음부터 다시 해야 한다. 충돌률이 높으면 재시도가 재시도를 부르면서 오히려 비관적 락보다 느려진다. **재시도 횟수 상한과 백오프는 애플리케이션이 직접 짜 넣어야 한다.**

네 갈래를 한 표로 놓고 보면 선택 기준이 분명해진다.

| | 무엇을 하는가 | 대기 | 실패의 형태 | 잘 맞는 상황 |
|---|---|---|---|---|
| 격리 수준 인상 | 트랜잭션 전체의 읽기 일관성을 올린다 | REPEATABLE READ는 없음, SERIALIZABLE은 검사 비용 | 40001 직렬화 오류 | 여러 읽기가 한 시점으로 일관돼야 하는 리포트·정산 |
| 원자적 UPDATE | 읽기·판단·쓰기의 틈을 없앤다 | 그 행에만 아주 짧게 | 갱신 행 수 0 | 단순 증감. 대부분의 재고 차감 |
| 비관적 락 | 읽기 전에 그 행을 잠근다 | 있음 — 뒤 트랜잭션이 줄을 선다 | 락 대기 타임아웃, 데드락 | 경합이 심한 핫 로우, 실패보다 대기가 나은 경우 |
| 낙관적 락 | 버전이 그대로일 때만 갱신한다 | 없음 | 갱신 실패 → 재시도 | 경합이 드문 일반적인 갱신, 사용자 편집 화면 |

한 문장으로 압축하면 이렇다. **격리 수준은 "이 트랜잭션이 세상을 얼마나 일관되게 보는가"라는 광역 설정이고, 재고 차감은 "이 행 하나의 갱신이 충돌한다"는 국소 문제다. 국소 문제를 광역 설정으로 풀면 무관한 트랜잭션까지 전부 비용을 치른다.**

## 4. 꼬리질문 대비 포인트

### "같은 트랜잭션에서 같은 행을 두 번 읽었는데 값이 달라요. 무슨 현상이고 어떻게 진단하나요?"

전형적인 **non-repeatable read**이고, 격리 수준이 READ COMMITTED 이하일 때 발생하는 현상이다. PostgreSQL은 기본값이 READ COMMITTED이므로 특별한 설정 없이도 일어난다.

진단은 순서가 있다. 먼저 **실제 격리 수준을 확인**한다(`SHOW transaction_isolation`). 다음으로 **애초에 두 읽기가 정말 같은 트랜잭션 안인지 확인**한다 — 프록시 자기 호출 등으로 트랜잭션이 안 걸려 각 SELECT가 별도 자동 커밋으로 돌았다면 격리 수준을 아무리 올려도 증상이 그대로다(3-4). 이 순서를 뒤집지 않는 것이 중요하다.

해결은 요구사항에 따라 갈린다. 정말 트랜잭션 내내 같은 시점을 봐야 한다면 그 로직만 REPEATABLE READ로 올린다. 값을 두 번 읽을 이유가 없다면 첫 읽기 결과를 변수로 들고 간다. 본질이 갱신 충돌이라면 격리 수준이 아니라 `FOR UPDATE`나 원자적 UPDATE로 그 지점만 다룬다(3-6).

### "스프링 `@Transactional`의 격리 수준 기본값은 무엇인가요?"

`Isolation.DEFAULT`이고, 이것은 특정 수준이 아니라 **"DB의 기본값을 그대로 따른다"**는 의미다. 그래서 같은 코드가 PostgreSQL(READ COMMITTED)과 MySQL(REPEATABLE READ) 위에서 다르게 돈다.

명시 지정하면 트랜잭션을 **새로 시작하는 시점에** 커넥션에 `setTransactionIsolation`을 호출했다가 종료 시 원복한다. 다만 이미 열린 트랜잭션에 REQUIRED로 합류하는 경우에는 적용되지 않고, 기본 설정에서는 예외도 없이 조용히 무시된다(`validateExistingTransaction`을 켜면 예외로 바뀐다). **"격리 수준은 트랜잭션을 새로 시작하는 쪽이 정한다"**까지 말하면 전파 질문과 이어진다.

### "non-repeatable read와 phantom read를 왜 따로 구분하나요? 둘 다 '다시 읽으니 다르다' 아닌가요?"

**막는 메커니즘이 다르기 때문**이다.

non-repeatable read의 원인은 이미 존재하는 행의 UPDATE라서 **그 행을 잠그면** 막을 수 있다. 대상이 명확하기 때문이다. phantom read의 원인은 아직 존재하지 않는 행의 INSERT라서 행 락으로는 막을 수 없다. **조건에 걸리는 범위 자체를 다루는 제어**가 필요하다.

방어 난이도가 다르니 표준도 단계를 나눴고, REPEATABLE READ까지는 phantom을 허용한다. **"현상의 분류가 아니라 방어 수단의 분류"**라고 답하면 정확하다.

여기에 구현 이야기를 한 겹 얹으면 좋다. PostgreSQL은 스냅샷 방식이라 REPEATABLE READ에서 phantom까지 함께 막히고, MySQL InnoDB는 일반 SELECT는 스냅샷으로 잠금 읽기는 넥스트 키 락으로 막는다. **표준의 단계 구분과 실제 구현의 방어선이 일치하지 않는다**는 것을 아는 것이 실무 감각이다.

### "동시성 버그가 났는데 격리 수준을 올려서 풀면 안 되나요?" (시니어 변별 포인트)

**문제의 스코프부터 판별하는 것**으로 답을 시작한다.

"한 트랜잭션 안의 여러 읽기가 같은 시점으로 일관돼야 한다"는 **읽기 일관성** 문제라면 격리 수준이 맞는 도구다. 정산 리포트처럼 여러 테이블을 훑는 작업이 그렇다.

"두 트랜잭션이 같은 행을 갱신하며 충돌한다"는 **쓰기 충돌**이면 국소 문제이므로 국소 도구로 푼다. 원자적 UPDATE가 가장 싸고, 경합이 심하면 `FOR UPDATE` 비관적 락, 경합이 드물면 `@Version` 낙관적 락 + 재시도다(3-6).

격리 수준 인상의 청구서도 함께 말해야 한다. SERIALIZABLE로 올리면 기술적으로는 막히지만 **무관한 조회 트래픽까지 충돌 검사와 40001 재시도 비용을 치르고**, 재시도 코드가 없으면 그냥 500 에러가 늘어날 뿐이다. 여기에 2-6의 관점 — **오래 유지되는 스냅샷은 VACUUM을 방해해 DB 전체에 비용을 전가한다** — 까지 덧붙이면 비용을 입체적으로 보는 답이 된다.

마지막으로 3-3의 사실 하나를 얹으면 결정타가 된다. **격리 수준을 올려도 그 메서드가 이미 열린 트랜잭션에 합류하는 자리라면 지정 자체가 적용되지 않는다.** "올렸는데 안 고쳐졌다"의 흔한 원인이다.

### "PostgreSQL의 REPEATABLE READ가 phantom read를 막는다면, SERIALIZABLE은 왜 필요한가요?" (가산점 포인트)

**스냅샷 격리가 못 막는 이상 현상이 하나 남기 때문**이라고 답한다. 그것이 **쓰기 왜곡(write skew)**이다.

두 트랜잭션이 같은 조건을 읽고 각자 판단한 뒤 **서로 다른 행을 INSERT/UPDATE**하는 경우, 행 단위로는 아무 충돌이 없어 스냅샷 격리는 문제를 감지하지 못한다. 쿠폰 한도 100장에 각자 99장을 읽고 각자 1장씩 발급해 101장이 되는 시나리오가 대표적이다(2-4).

SERIALIZABLE은 **읽은 조건의 범위까지 추적**해서 "이 트랜잭션이 읽은 전제가 저 트랜잭션의 쓰기 때문에 무효가 됐다"를 잡아낸다. PostgreSQL은 이것을 락이 아니라 SSI로 구현해 읽기를 막지 않는 대신 커밋 시점에 충돌을 감지하고 한쪽을 40001로 실패시킨다. **그래서 SERIALIZABLE을 선택한다는 것은 재시도 코드를 함께 짜겠다는 선언**이라는 점까지 말하면 좋다.

덧붙여 "그럼 이 문제를 SERIALIZABLE 없이 푸는 방법은?"까지 준비해 두면 완성도가 높다. 답은 **판단의 근거를 한 행으로 모으는 것**이다. 발급 수량을 별도 카운터 행 하나로 관리하고 `UPDATE ... SET issued = issued + 1 WHERE issued < 100`으로 갱신하면, 범위 조건 문제가 행 하나의 갱신 충돌 문제로 바뀌어 READ COMMITTED에서도 안전해진다. **광역 도구를 꺼내기 전에 모델을 바꿔 국소 문제로 만드는 것**이 대체로 더 나은 설계다.

## 한 줄 요약

격리 수준 4단계는 dirty read(확정 안 된 값을 읽음) / non-repeatable read(같은 행을 다시 읽으니 값이 달라짐, 원인은 UPDATE) / phantom read(같은 조건으로 다시 세니 행 수가 달라짐, 원인은 INSERT·DELETE)를 어디까지 허용하느냐의 매트릭스이고, PostgreSQL은 이것을 MVCC로 구현해 각 트랜잭션이 스냅샷에 보이는 튜플 버전만 읽게 하므로 dirty read가 구조적으로 불가능하며 기본값 READ COMMITTED는 문장마다 스냅샷을 새로 뜨고 REPEATABLE READ는 첫 문장 스냅샷을 고정해 표준이 허용하는 phantom까지 막는 반면 SERIALIZABLE은 SSI로 충돌을 사후 감지해 40001로 실패시키므로 재시도가 필수다 — 스프링에서는 `Isolation.DEFAULT`가 DB 위임이고 명시 지정은 트랜잭션을 새로 시작하는 쪽에만 적용되며, 재고 차감 같은 쓰기 충돌은 광역 설정인 격리 수준이 아니라 원자적 UPDATE·비관적 락·낙관적 락 + 재시도라는 국소 도구로 푸는 것이 정석이다.
