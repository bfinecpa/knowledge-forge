# @Transactional(readOnly = true)의 실제 최적화 — 무엇을 아껴 주고, 무엇을 막아 주지 않는가

> 핵심 관전 포인트: **readOnly=true의 실효는 대부분 하이버네이트 계층에서 나온다. 스프링은 트랜잭션을 시작할 때 하이버네이트 세션의 플러시 모드를 MANUAL로 바꿔 커밋 시 자동 플러시를 없애고, 그와 함께 세션을 읽기 전용 모드로 돌려 조회한 엔티티의 스냅샷(더티 체킹용 원본 사본)을 아예 만들지 않게 한다 — 엔티티 10만 건이면 스냅샷 배열과 박싱 객체만으로 수십 MB, 플러시 때마다 수백만 번의 필드 비교가 통째로 사라진다. 그 아래로 JDBC 커넥션에 `setReadOnly(true)`가 전달되는데 PostgreSQL 드라이버는 이것을 읽기 전용 트랜잭션으로 번역하므로 SQL이 실제로 도달하면 거부되고, 맨 아래 인프라 계층에서는 `AbstractRoutingDataSource`가 이 플래그를 보고 리플리카로 라우팅하는 근거가 된다. 단 readOnly는 쓰기를 막아 주는 안전장치가 아니다 — 하이버네이트가 SQL을 아예 만들지 않으므로 변경은 예외 없이 조용히 증발하고, "저장했는데 반영이 안 된다"는 버그 리포트로 돌아온다. 그리고 스냅샷을 안 뜰 뿐 엔티티 10만 건은 여전히 영속성 컨텍스트에 남으므로 대량 조회의 OOM은 readOnly로 해결되지 않는다.**

---

## 0. 질문 + 의도

**질문**: "`@Transactional(readOnly = true)`는 실제로 어떤 최적화를 해주나요?"

**출제 의도**: 플러시 생략, replica 라우팅 힌트 등 실효를 아는지 본다. "붙이면 좋다더라"식 카고컬트 습관인지, 효과를 알고 쓰는지를 가리는 질문이다.

## 1. 전제 지식 — readOnly가 꺼 주는 기계장치가 무엇인가

"readOnly를 붙이면 플러시를 생략하고 스냅샷을 안 만든다"는 문장은 플러시와 스냅샷이 무엇인지 모르면 아무 정보도 주지 못한다. 그래서 그 둘부터 세운다.

### 1-1. 영속성 컨텍스트 — 트랜잭션 동안 엔티티를 담아 두는 방

**영속성 컨텍스트(persistence context)**는 JPA가 트랜잭션 동안 엔티티 객체를 담아 두는 메모리 공간이다. `findById(1L)`을 호출하면 JPA는 DB에서 읽어 온 행으로 `Member` 객체를 만들고, 그 객체를 이 방에 넣어 두고 우리에게 참조를 넘긴다. 같은 트랜잭션에서 `findById(1L)`을 또 부르면 DB에 가지 않고 방 안의 그 객체를 그대로 돌려준다. 그래서 **1차 캐시**라고도 부른다.

중요한 것은 **이 방이 트랜잭션과 생명주기를 같이한다**는 점이다. 트랜잭션이 끝나면 방은 통째로 비워진다. 반대로 말하면 **트랜잭션이 도는 동안 조회한 엔티티는 전부 이 방에 쌓여 있다.** 10만 건을 조회하면 10만 개의 객체가 방 안에 남아 있는 것이고, 이 사실이 2-5에서 다시 중요해진다.

### 1-2. 스냅샷과 더티 체킹 — 왜 원본 사본을 뜨는가

JPA에는 신기해 보이는 기능이 하나 있다. 조회해 온 엔티티의 필드를 자바 코드로 바꾸기만 하면 `save()`를 부르지 않아도 UPDATE가 나간다.

```java
@Transactional
public void changeName(Long id, String newName) {
    Member member = memberRepository.findById(id).orElseThrow();
    member.setName(newName);   // save() 호출이 없는데도 UPDATE가 나간다
}
```

이것이 **더티 체킹(dirty checking, 변경 감지)**이다. 그런데 JPA는 어떻게 "바뀌었다"는 걸 알까. 자바에는 "이 필드가 언제 바뀌었는지" 알려 주는 기능이 없다. 답은 단순 무식하다. **JPA는 엔티티를 방에 넣는 순간 그 필드 값들을 그대로 복사해 따로 보관해 둔다.** 이 복사본이 **스냅샷(snapshot)**이다. 그리고 나중에 현재 값과 스냅샷을 필드별로 하나씩 비교해서, 달라진 필드만 골라 UPDATE 문을 만든다.

```text
조회 시점                                     비교 시점
┌──────────────┐   복사    ┌──────────────┐   ┌──────────────┐
│ Member 객체  │ ───────>  │   스냅샷     │   │ Member 객체  │
│ name="철수"  │           │ name="철수"  │   │ name="영희"  │  <- 코드가 바꿈
│ age =30      │           │ age =30      │   │ age =30      │
└──────────────┘           └──────────────┘   └──────────────┘
                                    │  필드별로 하나씩 비교  │
                                    └──────────┬───────────┘
                                               v
                                UPDATE member SET name='영희' WHERE id=1
                                (age는 같으므로 UPDATE 문에 넣지 않는다)
```

여기서 두 가지 비용이 발생한다는 점을 기억하자. **스냅샷을 들고 있는 메모리 비용**과 **필드별로 비교하는 CPU 비용**이다. 이 둘이 readOnly가 없애는 대상이다.

### 1-3. 플러시 — 쌓인 변경을 SQL로 내보내는 순간

위 비교는 언제 일어날까. 코드가 필드를 바꾼 그 순간이 아니다. JPA는 변경을 방 안에 모아 뒀다가 **한 번에 SQL로 만들어 DB로 내보내는데**, 이 "내보내기" 동작이 **플러시(flush)**다.

플러시가 자동으로 일어나는 시점은 기본 설정에서 둘이다. **트랜잭션 커밋 직전**이 첫째이고, **JPQL 같은 쿼리를 실행하기 직전**이 둘째다. 두 번째가 필요한 이유는 정합성 때문이다. 방금 자바 코드로 바꾼 내용이 아직 DB에 안 나갔는데 그 상태로 SELECT를 날리면 옛날 값이 돌아와 버린다. 그래서 쿼리 전에 미리 밀어내는 것이다.

플러시가 하는 일을 순서대로 쓰면 이렇다.

```text
flush()
  ① 영속성 컨텍스트 안의 모든 엔티티를 순회한다
  ② 각 엔티티의 현재 값 vs 스냅샷을 필드별로 비교한다   <- 더티 체킹
  ③ 달라진 것이 있으면 UPDATE 문을 만든다
  ④ persist()로 쌓아 둔 INSERT, remove()로 쌓아 둔 DELETE와 함께 DB로 전송한다
```

그리고 플러시 시점을 정하는 설정이 **플러시 모드**다. 기본값은 `AUTO`(위 두 시점에 자동 플러시)이고, `MANUAL`은 **"애플리케이션이 `flush()`를 직접 부르지 않는 한 절대 자동으로 플러시하지 않는다"**는 뜻이다.

### 1-4. 여기까지의 그림

이제 readOnly가 무엇을 끄는지 말할 수 있다. **스냅샷을 안 만들면 ②의 비교가 불가능해지고, 플러시 모드가 MANUAL이면 ①~④ 자체가 아예 실행되지 않는다.** 다음 절은 스프링이 실제로 이 둘을 어떻게 끄는지의 이야기다.

## 2. 계층별 분해 — readOnly 하나가 세 계층에 각각 다르게 닿는다

### 2-1. 계층 지도

"readOnly는 성능에 좋다더라"는 암기 답변과, "어느 계층에서 무슨 최적화가 일어나는지"를 분해하는 답변은 급이 다르다. 어노테이션 하나에 세 계층이 각각 다르게 반응하기 때문이다.

| 계층 | 무슨 일이 일어나나 | 실효 |
|---|---|---|
| JPA/Hibernate | 플러시 모드 MANUAL + 세션 읽기 전용(스냅샷 생략) | **가장 큼 — 확실한 최적화** |
| JDBC 드라이버 | 커넥션에 `setReadOnly(true)` 전달 | 드라이버/DB마다 다름 (PostgreSQL은 강제) |
| 인프라(DataSource) | 리플리카 라우팅의 판단 근거 | 구성했다면 매우 큼 |

첫 문장은 이렇게 시작하면 된다. **"readOnly의 실효는 대부분 하이버네이트 계층에서 나옵니다."** 그리고 계층을 내려가며 설명한다.

### 2-2. JPA/Hibernate 계층 — 실제로 무엇이 호출되나

스프링의 트랜잭션 매니저는 새 트랜잭션을 시작할 때 `readOnly` 값을 보고 하이버네이트 세션에 두 가지를 건다. 순서대로 짚자.

**하나. 플러시 모드를 `MANUAL`로 바꾼다.** 1-3에서 본 자동 플러시 두 시점이 모두 사라진다. 커밋 직전에도 플러시하지 않고, JPQL 실행 직전에도 플러시하지 않는다. 트랜잭션이 끝나도 UPDATE는 단 한 건도 나가지 않는다. (트랜잭션이 끝나면 원래 플러시 모드로 되돌려 놓는다.)

**둘. 세션의 기본 읽기 전용 모드를 켠다.** 이 트랜잭션 안에서 로드되는 엔티티는 **읽기 전용 엔티티**로 방에 등록되고, 하이버네이트는 그런 엔티티에 대해서는 **스냅샷을 아예 만들지 않는다.** 1-2의 복사 화살표가 통째로 사라지는 것이다.

두 번째가 언제부터 동작하는지는 정확히 알아 둘 가치가 있다. **스프링 프레임워크 5.1(스프링 부트 2.1)부터** 읽기 전용 플래그가 하이버네이트 세션까지 전달되기 시작했다. 그 이전 버전에서는 플러시 모드만 MANUAL로 바꿨고 스냅샷은 그대로 만들었다. 이 문서의 서술은 **스프링 부트 3.x + 하이버네이트 6 기준**이며, 트랜잭션 매니저는 기본값인 `JpaTransactionManager`를 전제한다.

주의할 조건이 하나 있다. **이 두 가지는 트랜잭션을 새로 시작할 때만 적용된다.** 이미 열려 있는 트랜잭션에 REQUIRED로 합류하는 경우에는 안쪽 메서드에 붙인 `readOnly` 값이 조용히 무시된다. 트랜잭션의 읽기 전용 여부는 트랜잭션을 시작한 쪽이 정하기 때문이다. 이 성질이 3-3에서 실제 사고의 원인이 된다.

### 2-3. 아끼는 양을 숫자로 — 10만 건 조회의 스냅샷 비용

"메모리를 절약한다"는 말만으로는 감이 안 온다. 계산해 보자.

먼저 스냅샷의 정체를 정확히 알아야 한다. **스냅샷은 엔티티 객체를 통째로 복제한 것이 아니라, 필드 값들을 순서대로 담은 `Object[]` 배열 하나다.** 그리고 배열에는 객체만 담을 수 있으므로 `long`, `int` 같은 원시 타입 필드는 `Long`, `Integer`로 **박싱**된다. 이 박싱된 객체들이 스냅샷에 붙들려 살아남는다.

```text
전제: 엔티티 Member 의 필드가 20개 (Long 5개, int 5개, String 10개)
     JVM은 64비트 + compressed oops (힙 32GB 미만이면 기본값)

  ① Object[20] 배열 자체
       배열 헤더 16B + 참조 20개 x 4B                       =  96B
  ② 원시 타입 필드의 박싱 — 배열에 담으려면 객체여야 한다
       Long    5개 x 24B                                   = 120B
       Integer 5개 x 16B                                   =  80B
  ③ String 10개
       엔티티와 같은 String 인스턴스를 가리키는 참조뿐      =   0B
       (byte[]·Date·컬렉션처럼 변경 가능한 타입은 깊은 복사가
        일어나므로 이 항목이 통째로 더 붙는다)

  엔티티 1건당 스냅샷  =  96 + 120 + 80  ≈  300B

  10만 건 조회 시      =  300B x 100,000  =  30,000,000B  ≈  30MB
```

정확한 수치가 아니라 **자릿수 감각**으로 읽어야 한다. 필드 수와 타입 구성에 따라 몇 배씩 달라지기 때문이다. 하지만 계산의 뼈대는 분명하다. **엔티티당 필드 수 × 조회 건수만큼의 배열 슬롯과 박싱 객체가 통째로 얹힌다.**

여기서 흔히 도는 설명 하나를 바로잡아 두자. "readOnly를 붙이면 메모리가 절반이 된다"는 말은 정확하지 않다. 엔티티 껍데기(필드 슬롯)만 놓고 보면 원시 타입이 박싱되는 스냅샷 쪽이 오히려 더 클 수도 있고, 반대로 String 내용처럼 두 쪽이 공유하는 부분은 한 번만 계산해야 한다. **"딱 2배"라고 말하는 대신 "건수에 비례하는 배열과 박싱 객체가 추가로 붙는다"고 말하는 편이 정확하다.**

CPU 비용도 같은 방식으로 센다.

```text
플러시 1회의 비교 횟수 = 엔티티 건수 x 필드 수
                       = 100,000 x 20 = 2,000,000회

그리고 플러시는 트랜잭션당 1회가 아니다 — JPQL 쿼리를 실행할 때마다 자동 플러시가 돈다.
트랜잭션 안에서 쿼리를 5번 날렸다면  2,000,000 x 5 = 1,000만 회 비교

전부 "바뀐 게 하나도 없다"는 결론을 내기 위한 비교다.
```

조회 전용 메서드에서 이 1,000만 번의 비교는 **한 건의 UPDATE도 만들어 내지 않는다.** 100% 헛수고다. readOnly가 지우는 것이 정확히 이 헛수고다.

### 2-4. before / after

```java
// before: 조회만 하는데 쓰기 트랜잭션으로 열려 있다
@Transactional
public List<MemberResponse> findMembers(SearchCondition condition) {
    List<Member> members = memberRepository.search(condition);  // 10만 건
    return members.stream().map(MemberResponse::from).toList();
}
// 내부에서 벌어지는 일:
// - 엔티티 10만 건마다 Object[20] 스냅샷 생성 -> 약 30MB가 트랜잭션 내내 붙들린다
// - 커밋 직전 자동 플러시: 10만 x 20 = 200만 번 필드 비교
// - 결과는 UPDATE 0건. 위 비용 전부가 아무 산출물 없이 소모된다.
```

```java
// after: 읽기 전용 트랜잭션으로 선언
@Transactional(readOnly = true)
public List<MemberResponse> findMembers(SearchCondition condition) {
    List<Member> members = memberRepository.search(condition);  // 10만 건
    return members.stream().map(MemberResponse::from).toList();
}
// - 세션이 읽기 전용이라 스냅샷 자체를 만들지 않는다 -> 약 30MB가 통째로 사라진다
// - 플러시 모드 MANUAL이라 커밋 직전 자동 플러시가 없다 -> 200만 번 비교도 사라진다
// - "이 메서드는 아무것도 바꾸지 않는다"는 의도가 시그니처에 드러나는 문서화 효과는 덤
```

### 2-5. 그래도 대량 조회의 OOM은 readOnly가 막아 주지 못한다

여기가 readOnly를 만능으로 오해하기 쉬운 지점이다. 스냅샷은 사라졌지만 **엔티티 10만 건 자체는 여전히 영속성 컨텍스트에 그대로 남아 있다.** 1-1에서 본 대로 방은 트랜잭션이 끝날 때까지 비워지지 않기 때문이다.

```text
readOnly 없음:  엔티티 10만 건  +  스냅샷 30MB   -> 방이 터진다
readOnly 있음:  엔티티 10만 건                   -> 여전히 방이 터질 수 있다
                 ↑ 이건 readOnly가 손대지 않는다
```

그래서 배치나 대량 조회에서 OOM이 난다면 처방은 readOnly가 아니다. 방에 쌓이는 엔티티 수 자체를 줄여야 한다.

- **페이징으로 끊어 읽기** — 한 번에 방에 들어오는 건수의 상한을 만든다.
- **일정 건수마다 `entityManager.clear()`** — 방을 주기적으로 비운다. 배치의 정석이다.
- **DTO 프로젝션** — 필요한 컬럼만 골라 DTO로 바로 받는다. 엔티티가 아니므로 애초에 영속성 컨텍스트에 등록되지 않고, 스냅샷도 더티 체킹도 처음부터 무관해진다. 조회 전용이라면 이것이 readOnly보다 더 큰 최적화다.

**readOnly는 "건당 부가 비용"을 없애는 도구이지 "건수"를 줄이는 도구가 아니다.** 이 구분을 말할 수 있으면 도구의 한계를 아는 답변이 된다.

### 2-6. JDBC 드라이버 계층 — 힌트이면서, PostgreSQL에서는 강제

스프링 트랜잭션 매니저는 readOnly 트랜잭션을 시작할 때 커넥션에 `Connection.setReadOnly(true)`를 호출한다. 여기서부터는 스프링의 손을 떠나 **드라이버와 DB가 이 신호로 무엇을 할지 각자 정한다.**

**PostgreSQL**에서는 이것이 힌트 이상으로 작동한다. 최근 pgjdbc 드라이버는 기본 설정(`readOnlyMode=transaction`)에서 이 플래그를 **읽기 전용 트랜잭션**으로 번역한다. 그래서 그 트랜잭션 안에서 쓰기 SQL이 실제로 DB까지 도달하면 `25006 cannot execute INSERT in a read-only transaction` 같은 오류로 거부당한다. (드라이버 설정으로 `ignore`나 `always`로 바꿀 수 있으므로 "PostgreSQL이면 무조건"이라고 단정하지는 말고 "기본 설정에서는"이라고 말하는 편이 안전하다.)

**MySQL**은 서버에 읽기 전용 트랜잭션임을 알려 주고, InnoDB는 이를 이용해 트랜잭션 ID 발급 같은 준비 작업을 건너뛰는 최적화를 한다. 쓰기 시도는 오류가 된다.

**그 외 DB/드라이버는 아무것도 안 하기도 한다.** 그래서 이 계층만 근거로 readOnly의 가치를 논하면 안 되고, "확실한 실효는 하이버네이트 계층"이라고 정리하는 것이 정확하다.

한 가지 부수 효과도 알아 둘 만하다. **`setReadOnly(true)`를 걸려면 커넥션이 있어야 하므로, readOnly 트랜잭션은 트랜잭션 시작 시점에 커넥션을 미리 가져온다.** 일반 트랜잭션이 첫 쿼리 시점에 커넥션을 잡는 것과 다르다. 이 차이가 2-8의 라우팅 함정과 맞물린다.

### 2-7. 인프라 계층 — 리더/리플리카 라우팅의 근거

트래픽이 커지면 쓰기는 리더(primary)로, 읽기는 리플리카(replica, 복제본)로 나눠 보낸다. 이때 "이 트랜잭션을 어느 DB로 보낼까"를 판단할 근거가 필요한데, **애플리케이션이 이미 갖고 있는 유일한 표식이 readOnly 플래그**다. 그래서 이 플래그가 라우팅 키가 된다.

스프링에는 `AbstractRoutingDataSource`라는 클래스가 있다. **커넥션을 요청받을 때마다 "지금은 어느 DataSource를 써야 하지?"를 묻고 그 답에 따라 실제 DataSource를 고르는 분배기**다. 우리가 구현할 것은 그 질문에 답하는 메서드 하나다.

```java
public class ReplicaRoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        // 이 메서드는 커넥션을 실제로 가져오는 그 순간에 호출된다.
        // 스프링은 트랜잭션 시작 시 readOnly 여부를 ThreadLocal에 담아 두므로
        // 같은 스레드에서 그 값을 꺼내 보면 지금 트랜잭션의 성격을 알 수 있다.
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
                ? "replica" : "primary";
    }
}
```

```java
@Configuration
public class DataSourceConfig {

    @Bean
    public DataSource routingDataSource(DataSource primary, DataSource replica) {
        ReplicaRoutingDataSource routing = new ReplicaRoutingDataSource();
        routing.setTargetDataSources(Map.of("primary", primary, "replica", replica));
        routing.setDefaultTargetDataSource(primary);  // 트랜잭션 밖 호출은 리더로
        return routing;
    }

    @Bean
    @Primary
    public DataSource dataSource(DataSource routingDataSource) {
        // 이 한 겹이 없으면 라우팅이 통째로 안 먹는다 — 이유는 2-8에서.
        return new LazyConnectionDataSourceProxy(routingDataSource);
    }
}
```

이것이 실무에서 **조회 메서드에 readOnly를 규율 있게 붙여야 하는 진짜 이유 중 하나**다. 지금 리플리카가 없어도, 붙여 둔 팀은 나중에 위 설정 파일 하나만 추가하면 읽기 분산을 도입할 수 있다. 안 붙인 팀은 서비스 코드 전체를 뒤져 조회 메서드를 하나씩 찾아내는 마이그레이션을 치러야 한다.

### 2-8. 라우팅의 함정 두 가지

**함정 하나. `LazyConnectionDataSourceProxy` 없이는 라우팅이 항상 리더로 간다.**

원인은 순서에 있다. 스프링이 트랜잭션을 시작할 때 하는 일의 순서를 보자.

```text
① 트랜잭션 매니저가 DataSource에서 커넥션을 가져온다
     -> 이 순간 determineCurrentLookupKey() 가 호출된다
     -> 그런데 isCurrentTransactionReadOnly() 는 아직 false 다!
② 그다음에야 readOnly 플래그를 ThreadLocal에 담는다
     -> 판정이 이미 끝난 뒤라 아무 소용이 없다
```

**커넥션을 잡는 시점이 플래그를 세우는 시점보다 앞선다.** 그래서 모든 트랜잭션이 `primary`로 흘러간다. `LazyConnectionDataSourceProxy`는 이 순서를 뒤집는 장치다. ①에서는 진짜 커넥션 대신 **껍데기 프록시**를 내주고, 실제 SQL이 처음 실행되는 순간에야 진짜 커넥션을 가져온다. 그때는 ②가 이미 끝나 있으므로 판정이 제대로 된다.

**함정 둘. 트랜잭션이 시작된 뒤에는 라우팅을 바꿀 수 없다.**

한 트랜잭션은 커넥션 하나에 묶인다. 그러니 쓰기 트랜잭션 안에서 readOnly 메서드를 호출해도 그 호출은 이미 잡혀 있는 리더 커넥션을 그대로 쓴다. 안쪽에 `readOnly = true`를 붙였다고 그 쿼리만 리플리카로 빠져나가지 않는다. **읽기와 쓰기를 나누고 싶으면 트랜잭션 경계를 나눠야 하고, 그것은 원자성을 나눈다는 뜻이므로 공짜가 아니다.**

**함정 셋. 복제 지연은 애플리케이션이 감당해야 한다.**

리더에 쓴 내용이 리플리카에 도착하기까지는 시간차가 있다. 이것을 **복제 지연(replication lag)**이라 한다. 그래서 "회원 가입(쓰기 → 리더) 직후 내 정보 조회(읽기 → 리플리카)"가 방금 만든 데이터를 못 찾는 일이 생긴다. 내가 쓴 것을 내가 못 읽는 이 문제를 **read-your-own-writes** 문제라고 부른다.

```text
t0  리더에 INSERT member  커밋
t1  응답 200 OK -> 클라이언트가 곧바로 조회 요청
t2  리플리카로 SELECT     -> 아직 복제 안 됨 -> 404
t3  (수십~수백 ms 뒤) 복제 완료 -> 이제는 조회됨
```

대응은 셋 정도다. 쓰기 직후의 읽기는 같은 트랜잭션 안에서 처리해 리더에 묶어 두거나, 특정 사용자에 대해 일정 시간 동안 리더 고정으로 라우팅하거나, 복제 위치를 확인해 따라잡을 때까지 기다리는 방식이다. **이 함정까지 말하면 "읽어 본 사람"이 아니라 "구성해 본 사람"의 답변이 된다.**

## 3. 오해 바로잡기 — 쓰기를 "막아 주는" 안전장치가 아니다

여기가 이 질문의 변별 포인트다. readOnly=true를 "이 트랜잭션에서는 쓰기가 금지된다"는 방어막으로 이해하면 정반대의 결과를 얻는다.

### 3-1. readOnly 안에서 엔티티를 수정하면 단계별로 무슨 일이 일어나나

```java
@Transactional(readOnly = true)   // 실수로 붙었거나, 클래스 레벨 설정을 물려받았거나
public void updateName(Long id, String name) {
    Member member = memberRepository.findById(id).orElseThrow();
    member.changeName(name);      // 이름을 바꿨다. 개발자는 저장됐다고 믿는다.
}
```

```text
① 트랜잭션 시작
     - 하이버네이트 세션 플러시 모드 = MANUAL
     - 세션 기본 읽기 전용 = on
     - JDBC 커넥션 setReadOnly(true)
②  findById(id) 로 Member 로드
     - 읽기 전용 엔티티로 영속성 컨텍스트에 등록
     - 스냅샷을 만들지 않는다                    <- 결정적인 지점
③  member.changeName(name)
     - 자바 객체의 필드 하나가 바뀐다. DB와는 아직 아무 상관이 없다.
④  메서드 리턴 -> 트랜잭션 커밋
     - 플러시 모드가 MANUAL이라 커밋 직전 자동 플러시가 없다
     - 설령 플러시가 돌아도 비교할 스냅샷이 없어 변경으로 인식되지 않는다
     - 만들어진 SQL: 0건.  던져진 예외: 0건.
⑤  호출자에게 정상 리턴 (200 OK)
     - 애플리케이션 로그에도, DB 로그에도 아무 흔적이 없다
```

**막힌 것이 아니라 보내지 않은 것**이다. 그리고 이 차이가 결과를 완전히 갈라 놓는다. 막혔다면 예외가 나고 스택 트레이스가 남아 5분이면 고친다. 보내지 않으면 아무 일도 안 일어난 것처럼 보이다가, 며칠 뒤 **"이름을 수정했는데 반영이 안 돼요"**라는 CS 티켓으로 돌아온다. 그때부터 개발자는 컨트롤러부터 리포지토리까지 코드를 정독하지만, 정작 원인은 코드가 아니라 어노테이션 속성 하나에 있다.

여기서 PostgreSQL의 읽기 전용 트랜잭션(2-6)이 왜 구원이 되지 못하는지도 분명해진다. **DB가 거부하려면 SQL이 DB까지 가야 하는데, 하이버네이트가 SQL을 아예 만들지 않았다.** 두 겹의 방어처럼 보이지만 실제로는 위쪽 한 겹이 아래쪽 한 겹의 발동 기회를 없애 버린 것이다.

### 3-2. 침묵을 깨는 경로들 — 여기서는 단정하지 말고 조건을 붙여야 한다

"readOnly면 무조건 조용히 무시된다"고 외우면 그것도 틀린다. SQL이 DB까지 도달하는 경로가 몇 개 있고, 그 경우엔 오히려 예외가 터진다. 조건을 정확히 구분해 두자.

**명시적으로 `flush()`를 부르면 플러시는 실행된다.** 플러시 모드 MANUAL은 "자동으로는 안 한다"는 뜻이지 "부르면 거부한다"는 뜻이 아니다. 다만 읽기 전용으로 로드된 엔티티는 스냅샷이 없어 여전히 UPDATE가 만들어지지 않는다. 반면 `persist()`로 쌓아 둔 INSERT는 더티 체킹과 무관하게 별도 큐에 대기하고 있으므로 이때 DB로 나가고, PostgreSQL 읽기 전용 트랜잭션이라면 그 자리에서 오류가 난다.

**ID 생성 전략이 `IDENTITY`면 `persist()` 시점에 즉시 INSERT가 나간다.** DB가 채번한 ID를 받아야 영속성 컨텍스트에 키를 등록할 수 있어서 미룰 수가 없기 때문이다. 플러시 모드와 무관하게 SQL이 실행되고, 읽기 전용 트랜잭션이면 거기서 예외가 난다.

**JPQL/네이티브 벌크 연산은 영속성 컨텍스트를 거치지 않고 곧장 SQL로 나간다.** `@Modifying` UPDATE/DELETE 쿼리가 그렇다. 이 경우도 DB가 거부한다.

**반대로, JPQL 조회 직전의 자동 플러시는 일어나지 않는다.** 1-3에서 본 두 번째 자동 플러시 시점은 플러시 모드가 AUTO일 때의 이야기이고, MANUAL에서는 발동하지 않는다. 그래서 "쿼리를 날리면 그때 UPDATE가 같이 나가지 않을까"라는 기대는 성립하지 않는다.

정리하면 이렇게 답하는 것이 정확하다. **"기본은 조용한 무시다. 다만 SQL이 어떤 경로로든 DB에 도달하면 그때는 DB가 거부해 예외가 난다."** 어느 쪽이든 **개발자가 의도한 저장은 일어나지 않는다**는 결론은 같다.

### 3-3. 가장 흔한 실사고 — 합류 때문에 readOnly가 옮겨 붙는다

실무에서 이 함정이 터지는 형태는 "실수로 readOnly를 붙였다"보다 **"클래스 레벨 설정이 물려 내려왔다"**가 압도적으로 많다.

```java
// before: 흔한 관용구 — 클래스 레벨은 읽기 전용, 쓰기 메서드만 오버라이드
@Service
@Transactional(readOnly = true)
public class MemberService {

    @Transactional                 // 오버라이드해서 쓰기 트랜잭션으로 연다 — 정상
    public void register(...) { ... }

    public void changeName(Long id, String name) {   // 문제: 어노테이션을 빼먹었다
        memberRepository.findById(id).orElseThrow().changeName(name);
    }
    // 클래스 레벨의 readOnly=true가 그대로 적용되어 변경이 조용히 증발한다
}
```

한 겹 더 고약한 형태도 있다. 조회 메서드가 쓰기 메서드를 호출하는 경우다.

```java
@Transactional(readOnly = true)
public MemberDetail getDetail(Long id) {
    Member member = memberRepository.findById(id).orElseThrow();
    viewLogService.recordView(member.getId());   // 이 안에 @Transactional(쓰기)이 붙어 있어도
    return MemberDetail.from(member);            // 이미 열린 읽기 전용 트랜잭션에 합류할 뿐이다
}
```

2-2 끝에서 말한 성질이 여기서 사고로 나타난다. **읽기 전용 여부는 트랜잭션을 시작한 바깥이 이미 정했고, 합류하는 안쪽의 선언은 조용히 무시된다.** `recordView()`의 INSERT는 나가지 않는다. 조회수가 안 오르는 버그의 원인이 조회 메서드의 어노테이션에 있는 셈이라, 원인을 찾기가 특히 어렵다.

방어책은 규칙이 아니라 장치여야 한다. 스프링은 기본적으로 이 불일치를 조용히 넘기지만, 트랜잭션 매니저의 `validateExistingTransaction` 옵션을 켜면 **합류 시 읽기 전용/격리 수준이 어긋날 때 `IllegalTransactionStateException`을 던지도록** 바꿀 수 있다. 조용한 버그를 시끄러운 예외로 바꾸는 설정이다. 다만 기존 코드에 갑자기 켜면 여기저기서 터질 수 있으므로, 새 프로젝트에서 처음부터 켜거나 테스트 프로파일에만 켜는 식으로 도입한다.

## 4. 꼬리질문 대비 포인트

### "readOnly=true인데 안에서 save()를 호출하면 무슨 일이 벌어지나요?"

**기본은 조용한 무시, 조건이 맞으면 예외**라고 두 갈래로 답한다.

하이버네이트 계층에서는 대부분 아무 일도 일어나지 않는다. `persist()`는 영속성 컨텍스트에 쌓이기만 하고, 플러시 모드가 MANUAL이라 자동 플러시가 없으니 INSERT가 나가지 않는다. 예외도 없다.

다만 SQL이 DB까지 도달하는 경로가 있다. ID 생성 전략이 `IDENTITY`면 ID를 받기 위해 `persist()` 시점에 즉시 INSERT를 보내야 하고, `@Modifying` 벌크 연산은 애초에 영속성 컨텍스트를 우회한다. 이때 커넥션이 읽기 전용 트랜잭션으로 열려 있다면(PostgreSQL 기본 구성) DB가 거부해 그 자리에서 예외가 난다.

마무리는 이렇게 한다. **어느 쪽이든 개발자가 의도한 저장은 일어나지 않는다.** 그러니 진짜 대책은 예외 여부를 외우는 것이 아니라, 조회 전용 메서드에 쓰기 로직이 섞이지 않게 하는 설계와 3-3의 검증 장치다.

### "조회 메서드에 트랜잭션을 아예 안 거는 것과 readOnly 트랜잭션을 거는 것의 차이는 뭔가요?"

세 가지로 답한다.

**영속성 컨텍스트의 범위가 다르다.** 트랜잭션이 없으면 리포지토리 호출 하나하나가 각자의 짧은 영속성 컨텍스트에서 돌고 즉시 닫힌다. 그래서 서비스 메서드에서 지연 로딩을 시도하면 이미 닫힌 컨텍스트에서 프록시를 초기화하려다 `LazyInitializationException`이 난다. readOnly 트랜잭션을 걸면 메서드 전체가 하나의 컨텍스트를 공유해 지연 로딩이 안전하다.

**커넥션과 라우팅의 일관성이 다르다.** 트랜잭션이 없으면 쿼리마다 커넥션을 따로 얻을 수 있어, 리플리카가 여러 대인 환경에서는 쿼리들이 서로 다른 복제본으로 흩어질 수 있다. 복제 지연이 서로 다르면 한 화면 안의 데이터가 어긋난다. 트랜잭션은 이것을 커넥션 하나에 묶는다.

**읽기 일관성이 다르다.** 한 트랜잭션 안이면 격리 수준에 따라 여러 쿼리가 같은 스냅샷을 볼 수 있지만, 트랜잭션이 없으면 쿼리 사이에 다른 트랜잭션의 커밋이 끼어들어 서로 안 맞는 데이터를 조합하게 된다. ([격리 수준 문서](14-transaction-isolation-levels.md) 참고.)

### "리더/리플리카 분리를 readOnly 기반으로 구현하는 방법과 함정은?" (시니어 변별 포인트)

구현은 `AbstractRoutingDataSource`를 상속해 `determineCurrentLookupKey()`에서 `TransactionSynchronizationManager.isCurrentTransactionReadOnly()`로 분기하는 것이 표준 패턴이다(2-7 코드). DB 프록시 계층에 맡기는 선택지도 있다.

함정을 셋 다 말하는 것이 변별 포인트다.

**첫째, `LazyConnectionDataSourceProxy`로 감싸지 않으면 전부 리더로 간다.** 커넥션을 잡는 시점이 readOnly 플래그를 세우는 시점보다 앞서기 때문이다. 프록시가 실제 커넥션 획득을 첫 SQL 실행 시점까지 미뤄 줘야 판정이 제대로 된다. "설정은 했는데 리플리카로 안 가요"의 1순위 원인이다.

**둘째, 트랜잭션이 시작된 뒤에는 라우팅을 못 바꾼다.** 쓰기 트랜잭션 안에서 readOnly 메서드를 불러도 이미 잡힌 리더 커넥션을 그대로 쓴다. 나누고 싶으면 트랜잭션 경계를 나눠야 하고, 그건 원자성을 나누는 결정이다.

**셋째, 복제 지연 때문에 쓰고 바로 읽으면 옛 데이터가 나온다.** 대응은 쓰기 직후 읽기를 리더로 보내거나(같은 트랜잭션 안에서 처리, 또는 일정 시간 리더 고정), 복제 위치를 확인해 기다리는 방식이다.

### "모든 조회 메서드에 readOnly를 붙이는 팀 컨벤션은 합리적인가요?"

**"기본은 붙인다, 단 안전장치가 아님을 팀이 공유한다"**가 균형 잡힌 답이다. 근거를 양쪽에서 말한다.

찬성 근거는 셋이다. 조회가 많은 서비스에서 스냅샷과 플러시 절약은 실질 이득이고(2-3의 계산), 리플리카 라우팅을 나중에 도입할 수 있는 전제 조건이 되며, "이 메서드는 아무것도 바꾸지 않는다"는 의도가 시그니처에 드러난다. "필요할 때만 붙이자"고 하면 규율이 없어 결국 아무도 안 붙이고, 라우팅 도입 시점에 전면 수정을 치른다.

주의점도 셋이다. 붙였다고 안전해진 것이 아니므로(3절) 조회 메서드에 쓰기가 섞이면 조용히 증발한다. 클래스 레벨 readOnly + 쓰기 메서드 오버라이드 패턴에서 어노테이션을 빼먹으면 같은 사고가 나므로 `validateExistingTransaction` 같은 장치나 테스트가 함께 가야 한다. 그리고 초단순 조회에까지 트랜잭션을 여는 비용 논란이 있지만, 어차피 쿼리 실행에 커넥션은 필요하고 readOnly 트랜잭션의 추가 비용은 크지 않아 일관성의 이득이 더 크다는 것이 일반적인 결론이다.

### "readOnly를 붙였는데도 조회가 느립니다. 어디를 의심하나요?"

**readOnly가 아끼는 것은 스냅샷과 플러시 비용이지 쿼리 자체가 아니다**부터 짚는다. N+1 문제, 인덱스 미사용, 필요 없는 컬럼까지 전부 엔티티로 끌어오는 것은 readOnly와 무관하게 그대로 남는다.

그리고 한 걸음 더 들어가 **조회 건수 자체**를 본다(2-5). 10만 건을 엔티티로 읽는 한 영속성 컨텍스트에 10만 개의 객체가 쌓이는 것은 readOnly로도 막지 못하므로, 페이징이나 주기적 `clear()`가 필요하다. 애초에 엔티티가 필요 없는 조회라면 **DTO 프로젝션으로 영속성 컨텍스트를 통째로 우회하는 것이 readOnly보다 큰 최적화**라는 점까지 말하면 도구의 한계를 아는 답변이 된다.

## 한 줄 요약

`@Transactional(readOnly = true)`의 실효는 하이버네이트 계층에 몰려 있다 — 플러시 모드를 MANUAL로 바꿔 자동 플러시를 없애고 세션을 읽기 전용으로 돌려 더티 체킹용 스냅샷을 아예 만들지 않으므로, 엔티티 10만 건 조회에서 수십 MB의 배열·박싱 객체와 수백만 번의 필드 비교가 통째로 사라진다. 그 아래로 커넥션 `setReadOnly(true)`가 전달되고(PostgreSQL 기본 구성에서는 읽기 전용 트랜잭션으로 강제된다) 인프라 계층에서는 리플리카 라우팅의 근거가 되지만, readOnly는 쓰기를 막아 주는 방어막이 아니라 SQL을 만들지 않는 힌트일 뿐이라 변경은 예외 없이 조용히 증발하고, 스냅샷을 안 뜰 뿐 엔티티 자체는 그대로 쌓이므로 대량 조회의 OOM은 페이징·`clear()`·DTO 프로젝션으로 따로 풀어야 한다.
