# 타임아웃 설정 — connection/read/전체 타임아웃과 타임아웃 예산

> 핵심 관전 포인트: **타임아웃은 종류별로 지키는 구간이 다르다 —
> connection timeout은 "TCP 연결 수립까지", read timeout은 "응답
> 데이터 조각 사이의 대기", 전체(요청) timeout은 "호출 시작부터 끝까지".
> read timeout만 있으면 조금씩 흘러오는 응답에 무한정 끌려갈 수 있어
> 전체 상한이 따로 필요하다. 값의 기준은 감이 아니라 대상의 p99 응답시간
> + 여유분이고, 호출 체인 전체로는 상류의 타임아웃 예산 안에 하류
> 타임아웃(재시도 포함)의 합이 들어와야 한다. 타임아웃 없는 외부 호출은
> 상대 장애 시 내 스레드를 무기한 인질로 잡아 스레드 풀 고갈 →
> 연쇄 장애(cascading failure)로 번지는 시한폭탄이다.**

---

## 0. 질문 + 의도

**질문**: "타임아웃은 어디에(connection/read/전체) 어떤 기준으로 설정하나요? 타임아웃 없는 외부 호출의 위험은?"

**출제 의도**: 타임아웃 없는 외부 호출은 시한폭탄이고, 너무 긴
타임아웃은 스레드를 인질로 잡는다. 전 구간(connection/read/전체)의
타임아웃 예산을 계산해본 사람인지 — 연쇄 장애 방어의 첫 번째 나사를
조여본 경험을 확인하는 질문이다.

## 1. 타임아웃 없는 호출의 위험 — 스레드 인질극

외부 호출의 본질은 "내 스레드가 상대의 응답을 **기다리는** 것"이다.
타임아웃이 없으면 이 기다림에 상한이 없다.

전파 경로를 단계별로 그리면:

1. 외부 API(예: 결제사)가 응답을 못 주는 상태가 된다 —
   죽은 게 아니라 **매우 느려진** 경우가 더 위험하다.
   (연결은 되는데 응답이 안 옴 → connection 단계는 통과)
2. 그 API를 호출한 내 서버의 스레드가 응답 대기 상태로 묶인다.
   타임아웃이 없으니 **영원히** 안 풀릴 수 있다.
3. 요청은 계속 들어오므로 묶이는 스레드가 하나씩 늘어난다.
   톰캣 워커 스레드 풀(유한하다)이 몇 분 안에 바닥난다.
4. 이제 결제와 **무관한 요청**(웹툰 조회, 로그인)도 처리할 스레드가
   없어 전부 대기·실패한다. 외부 API 하나의 장애가 **내 서비스 전체
   다운**이 됐다.
5. 내 서비스를 호출하던 상류 서비스도 같은 원리로 묶인다 —
   장애가 호출 체인을 거슬러 올라가는 **연쇄 장애(cascading failure)**.

비유하면 은행 창구 직원(스레드)이 전화 한 통(외부 호출)을 붙들고
무한정 대기하는 상황이다. 직원 수는 유한하므로, 전화가 안 끊기면
창구 전체가 마비된다. 타임아웃은 "전화는 최대 3초만 기다리고 끊는다"는
규칙이고, **유한한 자원(스레드)을 무한한 대기로부터 지키는 최소한의
방어선**이다.

위험한 것은 많은 HTTP 클라이언트·드라이버가 **타임아웃을 명시하지
않으면 사실상 무한 대기**로 동작한다는 점이다. "라이브러리 기본값이
있겠지"가 가장 흔한 시한폭탄이다 — 외부 호출 코드 리뷰에서 타임아웃
설정이 안 보이면 그 자체가 지적 사항이다.

```java
// Before: 타임아웃 미설정 — 상대가 응답을 안 주면 스레드 무한 대기
RestClient client = RestClient.create();  // 어떤 상한도 명시하지 않음

// After: 구간별 타임아웃 명시
ClientHttpRequestFactorySettings settings = ClientHttpRequestFactorySettings.defaults()
        .withConnectTimeout(Duration.ofSeconds(1))   // 연결 수립까지 1초
        .withReadTimeout(Duration.ofSeconds(3));     // 응답 대기 3초

RestClient client = RestClient.builder()
        .requestFactory(ClientHttpRequestFactories.get(settings))
        .build();
```

## 2. 타임아웃 3종 — 각각 무엇을 지키는가

한 번의 HTTP 호출은 여러 구간으로 이뤄지고, 타임아웃은 구간마다
따로 있다. "타임아웃 하나 걸었으니 안전하다"가 왜 착각인지가
이 구분에서 나온다.

| 종류 | 지키는 구간 | 터지는 대표 상황 |
|---|---|---|
| connection timeout | TCP 연결 수립(3-way handshake)까지 | 상대 서버 다운, 네트워크 단절, 방화벽 drop |
| read(socket) timeout | 응답 **데이터 조각 사이의** 대기 | 상대가 연결은 받았으나 처리가 느림 |
| 전체(요청) timeout | 호출 시작~응답 완료 전체 | 응답이 조금씩 끊임없이 흘러올 때 |

- **connection timeout**: 아직 요청을 보내기 전, "연결이 되냐"의
  문제다. 정상적인 연결 수립은 네트워크 왕복 몇 번이면 끝나므로
  **짧게**(같은 데이터센터 내부라면 1초 안팎이면 충분히 관대한 값)
  잡는다. 이게 길면 상대가 죽었을 때 죽음을 확인하는 데만 한참 걸린다.
- **read timeout**: 연결 후 응답을 기다리는 시간인데, 정확히는
  "**바이트와 바이트 사이**의 무응답 허용 시간"이다. 상대의 처리
  속도에 대한 인내심이므로 **대상 API의 응답시간 분포를 근거로** 잡는다.
- **전체 timeout**: read timeout의 함정을 막는 상한이다.
  아래에서 따로 설명한다.

### read timeout의 함정 — 전체 시간을 보장하지 않는다 (가산점 포인트)

read timeout 3초는 "총 3초 안에 응답 완료"가 **아니다**. 상대가
큰 응답을 2초 간격으로 조금씩 흘려보내면 read timeout은 한 번도
터지지 않으면서 전체 호출이 수십 초를 넘길 수 있다. 재시도까지
겹치면 (connect + read) × 시도 횟수만큼 최악 시간이 더 늘어난다.

그래서 "이 호출은 무슨 일이 있어도 N초 안에 끝난다"는 보장이 필요하면
**호출 전체를 감싸는 상한**을 따로 둬야 한다 — 비동기 호출의
`orTimeout()`/타임아웃 연산자, Resilience4j `TimeLimiter` 같은
요청 단위 타임아웃이 그 역할이다.

```java
// read timeout만으로는 총 소요 시간을 못 막는다 — 전체 상한을 별도로
CompletableFuture.supplyAsync(() -> paymentClient.pay(order), executor)
        .orTimeout(3, TimeUnit.SECONDS);   // 호출 전체가 3초를 넘으면 실패
```

## 3. 값을 정하는 기준 — p99와 타임아웃 예산

### 개별 값: 감이 아니라 관측된 분포로

read timeout의 근거는 **대상 API의 p99(또는 p99.9) 응답시간 + 여유분**이다.
평균으로 잡으면 정상 요청의 절반 가까이가 타임아웃으로 잘려나간다
(평균은 분포의 가운데일 뿐이다). p99 기준이면 정상 요청의 99%는
안 걸리고, 그보다 느린 요청은 "이미 비정상"이므로 잘라도 된다는 논리가
선다. 즉 **타임아웃을 정하려면 먼저 상대의 응답시간을 측정·모니터링하고
있어야 한다** — 근거 없는 "그냥 30초"는 스레드를 30초씩 인질 잡는
설정이다.

반대 방향의 실수도 있다. 너무 짧으면 멀쩡히 처리 중인 요청을 실패로
판정하는 **거짓 실패**가 늘고, 이것이 재시도를 유발해 오히려 부하를
키운다(재시도 문서에서 다루는 증폭의 입구). 타임아웃은 "짧을수록
좋다"가 아니라 "정상 분포는 통과시키고 비정상만 자르는 지점"이다.

### 체인 전체: 타임아웃 예산(timeout budget)

호출이 체인을 이룰 때는 개별 값이 아니라 **합이 문제**다.

```
사용자 → [게이트웨이 10초] → [주문 서비스] → 결제 API (read 5초 × 재시도 2회)
                                          → 포인트 API (read 4초)
```

주문 서비스의 최악 소요는 5×2 + 4 = 14초. 게이트웨이는 10초에
연결을 끊으므로, 주문 서비스가 아직 일하고 있는데 상류는 이미 실패로
응답한 상태가 된다 — 사용자는 실패를 봤는데 결제는 나중에 성공하는
**유령 성공** 같은 정합성 문제로 이어진다.

그래서 **상류의 타임아웃이 예산이고, 하류에서 일어나는 일(직렬 호출 +
재시도 포함)의 최악 합이 그 예산 안에 들어와야 한다.** 설계 순서는
바깥에서 안으로다: "사용자에게 최대 몇 초 안에 응답할 것인가"라는
SLO에서 출발해, 그 예산을 안쪽 호출들에 나눠주는 방식으로 계산한다.
이 산수를 해봤는지가 "타임아웃을 걸어봤다"와 "타임아웃을 설계해봤다"의
차이다.

## 4. 꼬리질문 대비 포인트

### "connection timeout과 read timeout이 터지는 상황은 어떻게 다르고, 대응도 달라지나요?"

connection timeout은 요청이 **상대에게 도달하기 전**의 실패라서
부작용이 없다는 것이 확실하다 — 안전하게 재시도할 수 있다.
read timeout은 요청이 이미 상대에게 도달해 **처리됐을 수도 있는**
상태의 실패다 — 결제 요청이었다면 "실패로 보였지만 실제로는 승인된"
경우가 가능하므로, 멱등성 보장 없이 재시도하면 중복 결제가 난다.
같은 타임아웃이라도 "요청이 넘어갔는가"에 따라 재시도 안전성이
갈린다는 구분이 핵심이다.

### "read timeout이 있는데도 전체 응답이 한없이 길어질 수 있는 이유는?"

read timeout은 데이터 조각 사이의 무응답 시간만 제한하기 때문이다.
상대가 타임아웃 직전 간격으로 응답을 조금씩 흘리면 read timeout은
계속 리셋되며 전체 시간은 무한정 늘어난다. 또 재시도가 있으면
(connect + read) × 시도 횟수로 최악 시간이 곱해진다. 그래서 총
소요 시간의 보장이 필요한 곳에는 요청 전체를 감싸는 타임아웃
(`TimeLimiter`, `orTimeout` 등)을 별도로 둔다.

### "타임아웃 값을 너무 짧게 잡으면 어떤 문제가 생기나요?"

정상적으로 처리 중인 요청을 실패로 판정하는 거짓 실패가 늘어난다.
그 실패가 재시도를 유발하면 상대 입장에서는 "아직 처리 중인 요청 +
새로 온 재시도"로 부하가 배가 되고, 부하 증가로 응답이 더 느려져
타임아웃이 더 많이 터지는 악순환에 들어간다. 그래서 타임아웃 단축은
반드시 대상의 p99 관측치를 근거로 해야 하고, 재시도 정책과 함께
검토해야 한다.

### "HTTP 말고 DB 호출에는 어떤 타임아웃들이 있나요?" (가산점 포인트)

같은 원리가 계층마다 반복된다. 커넥션 풀에서 커넥션을 얻기까지의
대기(HikariCP `connectionTimeout`), 소켓 수준 무응답(JDBC socket
timeout — DB 서버 다운 시 무한 대기를 막는 최후 방어선), 쿼리 실행
상한(statement/query timeout, `@Transactional(timeout=...)`)이 각각
따로 있다. 특히 socket timeout은 DB 장애 시나리오에서 없으면
쿼리 타임아웃조차 동작하지 않는 경우(취소 신호 자체가 소켓으로
전달되므로)가 있어, "타임아웃은 HTTP 클라이언트만의 문제가 아니라
모든 블로킹 I/O의 문제"라고 답하면 시야가 넓어 보인다.

### "타임아웃 값은 한 번 정하면 끝인가요?" (시니어 변별 포인트)

아니다. 타임아웃은 상대의 응답시간 분포에 대한 **가설**이므로, 상대의
성능이 변하면(데이터 증가, 트래픽 성장, 상대 쪽 배포) 무효가 된다.
운영에서는 (1) 대상별 응답시간 p99와 타임아웃 발생률을 대시보드로
추적하고, (2) 타임아웃 발생률이 평상시 baseline을 넘으면 알림을 걸고,
(3) p99가 타임아웃 값에 근접해오면 "타임아웃을 늘릴지, 상대 성능을
개선할지"를 의사결정한다. 무조건 늘리는 것은 스레드 인질 시간을
늘리는 것이므로, 전체 예산 안에서만 조정한다는 원칙까지 말하면
운영 경험이 드러난다.

## 한 줄 요약

타임아웃은 connection(연결 수립)·read(응답 조각 간 대기)·전체(호출
총 상한)가 각각 다른 구간을 지키는 별개의 나사이며, 값은 상대의 p99
관측치 + 여유로, 체인 전체로는 상류 예산 안에 하류(재시도 포함)의
최악 합이 들어오도록 계산한다 — 타임아웃 없는 외부 호출은 상대 장애
때 내 스레드 풀을 고갈시켜 연쇄 장애를 일으키는 시한폭탄이다.
