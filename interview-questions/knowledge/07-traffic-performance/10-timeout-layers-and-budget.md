# 타임아웃 설정 — connection/read/전체 타임아웃과 타임아웃 예산

> 핵심 관전 포인트: **타임아웃은 종류별로 지키는 구간이 다르다 — connection timeout은 "TCP 연결 수립까지", read timeout은 "응답 데이터 조각 사이의 대기", 전체(요청) timeout은 "호출 시작부터 끝까지". read timeout만 있으면 조금씩 흘러오는 응답에 무한정 끌려갈 수 있어 전체 상한이 따로 필요하다. 값의 기준은 감이 아니라 대상의 p99 응답시간 + 여유분이고, 호출 체인 전체로는 상류의 타임아웃 예산 안에 하류 타임아웃(재시도 포함)의 합이 들어와야 한다 — 어긋나면 상위가 먼저 포기해 하위의 작업이 버려지는 낭비가 되고, 심하면 상위는 실패를 응답한 뒤에 하위가 쓰기를 완료해 정합성이 깨진다. 타임아웃 없는 외부 호출은 상대 장애 시 내 스레드를 무기한 인질로 잡아 스레드 풀 고갈 → 연쇄 장애(cascading failure)로 번지는 시한폭탄이고, 이때 죽는 것은 그 외부 API를 쓰는 기능만이 아니라 **같은 스레드 풀을 쓰는 전혀 무관한 API 전부**다. 그리고 같은 원리가 HTTP 밖에서도 반복된다 — HikariCP `connectionTimeout`은 "DB에 연결하는 시간"이 아니라 "풀에서 커넥션을 얻기까지 기다리는 시간"이라는 것이 이름 때문에 거의 모두가 오해하는 지점이다.**

---

## 0. 질문 + 의도

**질문**: "타임아웃은 어디에(connection/read/전체) 어떤 기준으로 설정하나요? 타임아웃 없는 외부 호출의 위험은?"

**출제 의도**: 타임아웃 없는 외부 호출은 시한폭탄이고, 너무 긴 타임아웃은 스레드를 인질로 잡는다. 전 구간(connection/read/전체)의 타임아웃 예산을 계산해본 사람인지 — 연쇄 장애 방어의 첫 번째 나사를 조여본 경험을 확인하는 질문이다.

## 1. 타임아웃 없는 호출의 위험 — 스레드 인질극

### 1-1. 전제 지식 — 기다리는 스레드는 자리를 비켜주지 않는다

먼저 깔아둘 사실이 둘 있다.

**하나, 톰캣 같은 전통적인 서블릿 서버에서 HTTP 요청 하나는 워커 스레드 하나가 처음부터 끝까지 맡는다.** 요청이 처리되는 동안 그 스레드는 다른 요청을 볼 수 없다.

**둘, 외부 호출을 기다리는 동안에도 스레드는 자리를 지킨다.** 이것이 직관에 반하는 부분이다. 응답을 기다리는 스레드는 CPU를 쓰지 않는다 — 소켓에서 데이터가 오기를 대기하며 잠들어 있다. 일을 하지 않으니 자리를 비켜줄 것 같지만, 블로킹 I/O 모델에서는 그렇지 않다. **그 스레드의 호출 스택에 요청 처리의 진행 상황이 담겨 있으므로 다른 요청에 내줄 수 없다.**

그래서 외부 호출의 본질은 "내 스레드가 상대의 응답을 **기다리는** 것"이고, 타임아웃이 없으면 이 기다림에 상한이 없다. 워커 스레드 수는 유한하다(Spring Boot의 톰캣 기본값은 200개). **유한한 자원이 무한한 대기에 노출되는 구조**가 이 문서의 문제 전체다.

### 1-2. 시간축으로 본 스레드 고갈 — 2초 만에 전부 마른다

문장으로는 "스레드가 하나씩 묶여 결국 고갈된다"인데, 실제로 얼마나 빨리 벌어지는지를 숫자로 보면 감각이 완전히 달라진다. 조건을 정해 계산해 보자.

```text
톰캣 워커 스레드 수                              200개
전체 유입                                        300 TPS
  ├─ 결제 API를 호출하는 주문 요청                100 TPS
  └─ 결제와 무관한 웹툰 조회·로그인                200 TPS (건당 20ms 처리)
결제 API 평상시 응답 시간                         100ms
결제 호출에 걸린 타임아웃                          없음
```

**평상시의 동시 점유 스레드**부터 확인하자. 초당 들어오는 건수에 건당 머무는 시간을 곱하면 평균 동시 점유가 나온다.

```text
주문 요청       100건/초 × 0.1초  = 10개
조회·로그인     200건/초 × 0.02초 =  4개
                                  ─────
                        합계         14개  (풀 200개 중 14개)
```

여유가 넉넉하다. 이 상태에서 결제 API가 **죽지는 않고 응답만 멈췄다**고 하자. 연결은 받아 주므로 connection 단계는 통과하고, 응답이 오지 않는다. 타임아웃이 없으니 그 요청의 스레드는 **반환되지 않는다.**

점유 스레드는 주문 유입량만큼, 즉 초당 100개씩 순수하게 늘어난다.

```text
스레드 전부 소진까지 = (200개 − 평상시 점유분) ÷ 100개/초
                    ≈ 196 ÷ 100 = 약 2초
```

시간축에 올리면 이렇게 진행된다.

```text
        점유 스레드
  200 ┤                                    ██████████████████████████
      │                              ██████
  150 ┤                        ██████
      │                  ██████
  100 ┤            ██████
      │      ██████
   50 ┤██████
      │
    0 └──┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬──▶ 시간
         0    0.5   1.0   1.5   2.0   2.3   3.0   ...          ∞

  t=0.0s  결제 API가 응답을 멈춘다. 지표상 아무 이상 없음.
  t=0.5s  점유 50개. "결제가 좀 느리네" — 조회·로그인은 정상.
  t=1.0s  점유 100개. 여전히 조회·로그인은 정상.
  t=1.5s  점유 150개. 응답 시간 그래프가 꺾이기 시작.
  t=2.0s  ★ 200개 전부 소진.
          이 순간부터 웹툰 조회와 로그인도 스레드를 받지 못한다.
          결제를 쓰지 않는 요청인데도 처리되지 않는다.
  t=2.3s  ★ 대기 큐(예: 100)까지 소진 → 새 연결 자체가 거부된다.
          계산: 100 ÷ 300건/초 = 0.33초
  t=3.0s  이후로도 회복되지 않는다. 점유된 200개는 응답이 오지
          않는 한 영원히 풀리지 않는다 — 처리율이 0으로 고정된다.
```

**t=2.0s 지점이 이 문서에서 가장 중요한 한 줄이다.** 느려진 것은 결제 API 하나인데, 응답 불가가 된 것은 **이 서버의 모든 API**다.

### 1-3. 왜 관련 없는 API까지 죽는가 — 스레드 풀은 공유 자원이다

이유는 단순하지만 놓치기 쉽다. **톰캣 워커 스레드 풀은 API별로 나뉘어 있지 않다.** 하나의 풀에서 모든 요청이 스레드를 꺼내 쓴다.

```text
                 [ 톰캣 워커 스레드 풀 — 200개, 전 API 공유 ]
                    │        │        │        │        │
        ┌───────────┘        │        │        │        └───────────┐
        ▼                    ▼        ▼        ▼                    ▼
  POST /orders         GET /webtoons  ...  POST /login       GET /health
  (결제 API 호출)        (DB 조회만)          (DB 조회만)        (아무것도 안 함)

  결제 API가 무응답 → /orders 요청들이 스레드를 반환하지 않고 쌓임
                    → 풀이 마름
                    → 결제와 무관한 /webtoons, /login, /health까지
                      스레드를 못 받아 전부 대기·실패
```

`/health`가 함께 죽는다는 점이 특히 고약하다. **헬스체크가 응답하지 못하면 로드밸런서는 이 인스턴스를 죽은 것으로 판정해 풀에서 제거한다.** 남은 인스턴스에 부하가 집중되고, 그 인스턴스들도 같은 이유로 마른다 — 회복 장치가 장애를 가속하는 역설이다.

이 전파를 한 단계 더 밀면 상류 서비스로 번진다. 우리 서비스가 응답을 못 주니, 우리를 호출한 게이트웨이의 스레드도 **정확히 같은 원리로** 묶인다. 그리고 실패를 본 사용자가 새로고침을 연타하면 유입 자체가 늘어난다. 장애가 호출 방향의 역방향으로 번식하는 것을 **연쇄 장애(cascading failure)**라 부르고, 18번 문서(`18-cascading-failure-mechanism-and-bulkhead.md`)에서 방어 계층 전체를 다룬다.

### 1-4. 비유와 함정 — "라이브러리 기본값이 있겠지"

비유하면 은행 창구 직원(스레드)이 전화 한 통(외부 호출)을 붙들고 무한정 대기하는 상황이다. 직원 수는 유한하므로, 전화가 안 끊기면 창구 전체가 마비된다. 대기 중인 직원은 아무 일도 하지 않지만 창구를 비워 주지도 않는다 — 1-1에서 본 그대로다.

타임아웃은 **"전화는 최대 3초만 기다리고 끊는다"**는 규칙이고, **유한한 자원(스레드)을 무한한 대기로부터 지키는 최소한의 방어선**이다.

여기서 실무의 함정이 하나 있다. **많은 HTTP 클라이언트와 드라이버는 타임아웃을 명시하지 않으면 사실상 무한 대기로 동작한다.** 예를 들어 PostgreSQL JDBC 드라이버의 `socketTimeout` 기본값은 0이고, 0은 "제한 없음"을 뜻한다. `RestTemplate`/`RestClient`의 기본 요청 팩토리도 값을 주지 않으면 JDK 기본값을 쓰는데 그 역시 무제한이다.

**"라이브러리 기본값이 있겠지"가 가장 흔한 시한폭탄이다** — 외부 호출 코드 리뷰에서 타임아웃 설정이 안 보이면 그 자체가 지적 사항이다.

```java
// Before: 타임아웃 미설정 — 상대가 응답을 안 주면 스레드 무한 대기
RestClient client = RestClient.create();  // 어떤 상한도 명시하지 않음
// 이 클라이언트로 호출하면 1-2의 시간축이 그대로 재현된다.
// 코드에는 아무 에러도 없고, 테스트도 통과하고, 상대가 건강한 동안은
// 완벽하게 동작한다. 상대가 느려지는 그 순간에만 터진다.

// After: 구간별 타임아웃 명시
ClientHttpRequestFactorySettings settings = ClientHttpRequestFactorySettings.defaults()
        .withConnectTimeout(Duration.ofSeconds(1))   // 연결 수립까지 1초
        .withReadTimeout(Duration.ofSeconds(3));     // 응답 조각 간 대기 3초

RestClient client = RestClient.builder()
        .requestFactory(ClientHttpRequestFactories.get(settings))
        .build();
// 주의: 이것으로도 "총 소요 시간"은 보장되지 않는다.
// 왜 그런지는 2-4에서, 전체 상한을 어떻게 씌우는지는 2-5에서 다룬다.
```

## 2. 타임아웃 3종 — 각각 무엇을 지키는가

### 2-1. 요청 한 건의 타임라인 위에 세 타임아웃을 올려 본다

"타임아웃 하나 걸었으니 안전하다"가 왜 착각인지는 **한 번의 호출이 여러 구간으로 이뤄져 있고, 타임아웃마다 덮는 구간이 다르다**는 사실에서 나온다. 요청 한 건을 시간축에 펼쳐 보자.

```text
[요청 한 건의 타임라인 — 위에서 아래로 시간이 흐른다]

  t=0   호출 시작
   │
   │  ① 이름 풀이 (DNS 조회)             ◀── 어느 타임아웃도 안 덮는 경우가 많다!
   │                                          DNS가 응답하지 않으면 여기서 멈춘다
   │
   ├─ ② TCP 연결 (3-way handshake)   ┐
   │                                  ├── connection timeout이 재는 구간
   │  (HTTPS라면 TLS 핸드셰이크)        ┘    "연결이 맺어질 때까지"
   │                                        연결되면 이 시계는 역할을 끝낸다
   ├─ ③ 요청 전송
   │
   ├─ ④ 상대가 처리하는 동안 무응답    ┐
   │                                  │
   ├─ ⑤ 응답 첫 조각 도착  ▒▒         ├── read timeout이 재는 구간
   │     (여기서 read 시계가 0으로 리셋) │   "조각과 조각 사이의 무응답 시간"
   ├─ ⑥ ... 다시 무응답 ...            │   ★ 구간마다 따로 재고, 조각이 오면 리셋
   ├─ ⑦ 응답 둘째 조각 도착 ▒▒        ┘
   │
   └─ ⑧ 응답 완료
  t=끝

  ├────────────────────────────────────────────────────────┤
  └── 전체(요청) timeout이 재는 구간: t=0 부터 t=끝 까지 전부
      ①~⑧을 통째로 덮는 유일한 상한이다
```

이 그림에서 세 가지가 읽힌다. connection timeout은 **앞쪽 한 칸**만 덮는다. read timeout은 **뒤쪽 여러 칸을 각각** 덮는다(합이 아니다). 전체 timeout만이 **처음부터 끝까지**를 덮는다.

표로 정리하면 이렇다.

| 종류 | 지키는 구간 | 터지는 대표 상황 |
|---|---|---|
| connection timeout | TCP 연결 수립(3-way handshake)까지 | 상대 서버 다운, 네트워크 단절, 방화벽 drop |
| read(socket) timeout | 응답 **데이터 조각 사이의** 대기 | 상대가 연결은 받았으나 처리가 느림 |
| 전체(요청) timeout | 호출 시작~응답 완료 전체 | 응답이 조금씩 끊임없이 흘러올 때 |

### 2-2. connection timeout — "연결이 되냐"의 문제

아직 요청을 보내기 전 단계다. 상대에게 아무것도 전달되지 않았으므로 **부작용이 없다는 것이 확실한** 구간이다(이 성질이 재시도 안전성으로 이어진다 — 4절 첫 꼬리질문).

정상적인 연결 수립은 네트워크 왕복 몇 번이면 끝난다. 같은 데이터센터 내부라면 수 밀리초, 인터넷을 건너도 수십에서 수백 밀리초다. 그래서 **짧게** 잡는다 — 내부 호출이라면 1초 안팎도 충분히 관대한 값이다.

이 값이 길면 손해는 이렇다. 상대 서버가 완전히 죽었을 때, 그 사실을 확인하는 데만 그 시간을 쓴다. 연결 타임아웃 10초짜리 클라이언트로 죽은 서버를 호출하면 요청마다 10초씩 스레드가 묶인다 — **죽음을 확인하는 비용이 장애 자체보다 커지는** 상황이다.

### 2-3. read timeout — 상대의 처리 속도에 대한 인내심

연결 후 응답을 기다리는 시간인데, 정확히는 **"바이트와 바이트 사이의 무응답 허용 시간"**이다. 이 정의가 중요하고, 다음 절의 함정이 전부 여기서 나온다.

값의 근거는 **대상 API의 응답시간 분포**다. 상대가 보통 얼마나 걸리는지를 모르면 정할 수 없다(3-1에서 자세히 다룬다).

### 2-4. read timeout의 함정 — 전체 시간을 보장하지 않는다 (가산점 포인트)

**read timeout 3초는 "총 3초 안에 응답 완료"가 아니다.** 2-1 그림에서 read 시계가 조각이 도착할 때마다 리셋된다는 부분이 이유다. 상대가 타임아웃 직전 간격으로 응답을 조금씩 흘려보내면 read timeout은 **한 번도 터지지 않으면서** 전체 호출이 수십 초를 넘길 수 있다.

숫자로 보면 이렇다.

```text
[read timeout = 3초 인데 전체가 21초 걸리는 경우]

시간(초)   0     2.9    5.8    8.7   11.6   14.5   17.4   20.3   21.0
           │      │      │      │      │      │      │      │      │
           요청   ▒▒     ▒▒     ▒▒     ▒▒     ▒▒     ▒▒     ▒▒    완료
                └2.9s┘└2.9s┘└2.9s┘└2.9s┘└2.9s┘└2.9s┘└2.9s┘

  각 구간의 무응답 시간 = 2.9초 < read timeout 3초  → 매번 정상 판정
  read timeout이 본 최댓값 = 2.9초                   → 한 번도 안 터짐
  실제 총 소요            = 2.9 × 7 + 0.7 = 21초     → 스레드는 21초간 묶임
```

read timeout 관점에서 이 호출은 아무 문제가 없다. 그런데 1-1의 관점에서는 **21초짜리 스레드 인질**이다. 상대가 악의적일 필요도 없다 — 큰 응답을 스트리밍으로 흘려보내는 정상 동작이나, 상대의 백엔드가 페이지 단위로 느리게 조회하는 구현이면 자연히 이렇게 된다.

재시도까지 겹치면 최악 시간이 더 늘어난다. `(connect + read) × 시도 횟수`만큼 곱해지므로, 3초 read timeout에 3회 재시도면 최악은 30초를 훌쩍 넘긴다.

### 2-5. 전체 타임아웃 — "무슨 일이 있어도 N초"

그래서 "이 호출은 무슨 일이 있어도 N초 안에 끝난다"는 보장이 필요하면 **호출 전체를 감싸는 상한**을 따로 둬야 한다. 이것만이 2-1 그림의 t=0부터 t=끝까지를 덮는다.

블로킹 클라이언트에는 이런 상한이 없는 경우가 많아 바깥에서 씌운다.

```java
// read timeout만으로는 총 소요 시간을 못 막는다 — 전체 상한을 별도로
CompletableFuture.supplyAsync(() -> paymentClient.pay(order), executor)
        .orTimeout(3, TimeUnit.SECONDS);   // 호출 전체가 3초를 넘으면 실패
// 주의: orTimeout은 "기다리는 쪽"을 3초에 끊어 주지만,
// executor 안에서 돌고 있는 블로킹 호출 자체는 계속 진행된다.
// 그 스레드를 정말 회수하려면 executor 스레드를 별도 풀로 격리해
// 최악의 경우 그 풀만 마르게 만들어야 한다(bulkhead — 18번 문서).
```

Resilience4j를 쓰면 같은 일을 선언적으로 할 수 있다.

```java
TimeLimiterConfig config = TimeLimiterConfig.custom()
        // 3-2에서 계산한 결제 API 예산 1,200ms를 그대로 상한으로 쓴다.
        .timeoutDuration(Duration.ofMillis(1_200))
        // 상한을 넘겼을 때 진행 중인 작업에 인터럽트를 걸어 정리를 시도한다.
        // 이것이 없으면 "포기했는데 작업은 계속되는" 3-3의 낭비가 남는다.
        .cancelRunningFuture(true)
        .build();
```

반응형 클라이언트라면 세 종류를 한자리에서 다 지정할 수 있다.

```java
HttpClient httpClient = HttpClient.create()
        // ① connection timeout — 2-1 그림의 ② 구간
        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 1_000)
        // ② read/write timeout — 조각 사이의 무응답 상한 (그림의 ④~⑦)
        .doOnConnected(conn -> conn
                .addHandlerLast(new ReadTimeoutHandler(3, TimeUnit.SECONDS))
                .addHandlerLast(new WriteTimeoutHandler(3, TimeUnit.SECONDS)))
        // ③ 요청을 다 보낸 뒤 응답이 시작되기까지의 상한
        .responseTimeout(Duration.ofSeconds(3));

WebClient client = WebClient.builder()
        .clientConnector(new ReactorClientHttpConnector(httpClient))
        .build();

Mono<PaymentResult> result = client.post().uri("/pay")
        .bodyValue(order)
        .retrieve()
        .bodyToMono(PaymentResult.class)
        // ④ 전체 타임아웃 — 위 셋을 다 통과해도 이 벽은 넘지 못한다.
        //    2-4의 "조금씩 흘려보내는" 응답을 막는 유일한 장치다.
        .timeout(Duration.ofMillis(1_200));
```

**DNS 이야기를 한 번 더 짚어 둘 만하다.** 2-1 그림의 ① 구간, 즉 호스트명을 IP로 바꾸는 단계는 connection timeout이 덮지 않는 경우가 많다. DNS 서버가 응답하지 않으면 연결을 시도하기 전에 멈춰 버리고, connection timeout도 read timeout도 터지지 않는다. **이 구간을 덮는 것도 전체 타임아웃뿐이다** — 전체 상한이 왜 별도로 필요한지의 또 하나의 근거다.

## 3. 값을 정하는 기준 — p99와 타임아웃 예산

### 3-1. 개별 값: 감이 아니라 관측된 분포로

read timeout의 근거는 **대상 API의 p99(또는 p99.9) 응답시간 + 여유분**이다. 왜 평균이 아니고 p99인지부터 보자.

**p99는 "느린 쪽부터 세어 상위 1%를 뺀 나머지가 그 안에 들어오는 시간"**이다. p99가 400ms라면 요청 100건 중 99건은 400ms 안에 끝나고 1건은 그보다 오래 걸린다는 뜻이다.

평균으로 타임아웃을 잡으면 어떻게 되는가. 평균은 분포의 가운데일 뿐이므로, **정상 요청의 상당수가 평균보다 느리다.** 평균 80ms인 API에 타임아웃 80ms를 걸면 정상 처리 중인 요청이 대량으로 잘려 나간다. 응답시간 분포는 대개 오른쪽으로 긴 꼬리를 가지므로 이 손실이 생각보다 크다.

p99 기준이면 논리가 선다 — **정상 요청의 99%는 걸리지 않고, 그보다 느린 요청은 이미 비정상이므로 잘라도 된다.** 여기에 여유를 곱해 잡는다(p99 400ms에 3배면 1.2초).

즉 **타임아웃을 정하려면 먼저 상대의 응답시간을 측정·모니터링하고 있어야 한다** — 근거 없는 "그냥 30초"는 스레드를 30초씩 인질 잡는 설정이다.

반대 방향의 실수도 있다. 너무 짧으면 멀쩡히 처리 중인 요청을 실패로 판정하는 **거짓 실패**가 늘고, 이것이 재시도를 유발해 오히려 부하를 키운다.

```text
[거짓 실패의 악순환]

타임아웃을 너무 짧게 잡음
   → 정상 처리 중인 요청이 실패로 판정됨 (그런데 상대는 계속 처리 중)
   → 클라이언트가 재시도 → 상대는 "처리 중인 요청 + 새 재시도" 둘을 안게 됨
   → 상대의 부하 증가 → 응답이 더 느려짐
   → 타임아웃이 더 많이 터짐  (처음으로)
```

이 되먹임의 상세는 11번 문서(`11-retry-storm-backoff-jitter.md`)의 증폭 메커니즘과 같다. 타임아웃은 **"짧을수록 좋다"가 아니라 "정상 분포는 통과시키고 비정상만 자르는 지점"**이다.

### 3-2. 체인 전체: 타임아웃 예산을 한 단계씩 나눠 준다

호출이 체인을 이룰 때는 개별 값이 아니라 **합이 문제**다. 그리고 이 합은 아래에서 위로 더해 올리는 것이 아니라, **위에서 아래로 나눠 주는 것**으로 계산해야 한다.

출발점은 기술이 아니라 약속이다. **"사용자에게 최대 몇 초 안에 응답할 것인가"**라는 SLO를 정하고, 그 숫자를 예산으로 삼아 안쪽 호출들에 배분한다. 예산 3초를 가정해 한 단계씩 풀어 보자.

**① 게이트웨이 층 — 사용자 예산에서 자기 몫과 여유를 뺀다.**

```text
사용자 SLO (전체 예산)                      3,000ms
− 게이트웨이 자체 처리 (라우팅·인증·네트워크)   100ms
− 안전 여유 (전체의 10%)                      300ms
────────────────────────────────────────────────────
= 주문 서비스에 줄 수 있는 예산               2,600ms
```

안전 여유를 왜 남기는지 짚어 두자. 계산에 들어가지 않는 시간이 실제로는 존재한다 — GC 일시 정지, 스레드 풀 대기, 커널의 스케줄링 지연, 로그 기록. 이것들을 0으로 가정하면 예산이 딱 맞아떨어지는 설계가 실전에서 아슬아슬하게 넘친다.

**② 주문 서비스 층 — 받은 예산에서 다시 자기 몫을 뺀다.**

```text
주문 서비스가 받은 예산                     2,600ms
− 자기 처리 (DB 조회·검증·직렬화)             300ms
− 안전 여유                                  200ms
────────────────────────────────────────────────────
= 하위 호출에 쓸 수 있는 총량                2,100ms
```

**③ 하위 호출들에 나눈다 — 직렬이면 합, 병렬이면 최댓값.**

결제 API와 포인트 API를 순서대로 호출한다면 두 시간의 **합**이 예산 안에 들어와야 한다.

```text
하위 호출 총량                              2,100ms
├─ 결제 API 예산                            1,200ms
├─ 포인트 API 예산                            700ms
└─ 남긴 여유                                  200ms
                                          ─────────
                                   합계     2,100ms  (예산과 정확히 일치)
```

**④ 각 API 예산 안에서 다시 재시도와 구간 타임아웃을 나눈다.** 여기가 가장 자주 빠지는 단계다.

결제 API에 재시도를 1회 두기로 했다면(총 2회 시도), 재시도 사이의 대기(backoff)까지 예산 안에 들어와야 한다. 한 번의 시도에 쓸 수 있는 시간 T를 구해 보자.

```text
2 × (한 번의 시도 시간) + backoff 대기 ≤ 결제 예산 1,200ms
2 × T + 200 ≤ 1,200
2 × T ≤ 1,000
T ≤ 500ms

한 번의 시도 500ms를 구간별로 다시 나누면:
  connection timeout  100ms
  read timeout        400ms
                    ───────
                      500ms

검산: (100 + 400) × 2회 + backoff 200 = 1,000 + 200 = 1,200ms — 결제 예산과 일치한다
```

**재시도 1회를 넣는 대가로 한 번의 시도에 쓸 수 있는 시간이 1,200ms에서 500ms로 줄었다.** 이것이 "재시도는 공짜가 아니다"의 정확한 의미다 — 재시도 횟수를 늘릴수록 개별 호출의 타임아웃을 조여야 하고, 조이면 3-1의 거짓 실패가 늘어난다.

포인트 API는 재시도를 두지 않았으므로 예산을 그대로 쓴다.

```text
  connection timeout  100ms
  read timeout        600ms
                    ───────
                      700ms  (포인트 예산과 일치)
```

**⑤ 병렬로 바꾸면 예산이 남는다.** 결제와 포인트가 서로의 결과를 필요로 하지 않는다면 병렬 호출로 바꿀 수 있다. 이때 최악 소요는 합이 아니라 **최댓값**이다.

```text
직렬: 1,200 + 700 = 1,900ms  (하위 총량 2,100ms 중 1,900 사용)
병렬: max(1,200, 700) = 1,200ms  → 900ms가 남는다

남은 900ms의 용도는 셋 중 하나다.
  ① 여유로 남긴다 (가장 안전)
  ② 결제 API의 재시도를 1회 더 늘린다
  ③ 사용자 SLO를 3초에서 2초로 줄여 약속을 강화한다
```

**타임아웃 예산은 이렇게 "무엇을 포기하고 무엇을 살지"를 정하는 자원 배분표다.** 이 산수를 해봤는지가 "타임아웃을 걸어봤다"와 "타임아웃을 설계해봤다"의 차이다.

### 3-3. 예산이 지켜지지 않으면 — 낭비와 정합성 파괴

거꾸로, 예산을 계산하지 않고 계층마다 각자 값을 정하면 어떻게 되는지 보자. 실제로 흔한 조합이다.

```text
사용자 → [게이트웨이 10초] → [주문 서비스] → 결제 API (read 5초 × 재시도 2회)
                                          → 포인트 API (read 4초)
```

주문 서비스의 최악 소요를 계산하면 `5초 × 2회 + 4초 = 14초`다. 그런데 게이트웨이는 10초에 연결을 끊는다. **하위의 타임아웃 합이 상위보다 길다** — 원칙이 깨진 것이다.

이때 벌어지는 일을 시간축으로 보자.

```text
t = 0s    사용자 요청 도착. 게이트웨이가 주문 서비스 호출.
t = 5s    결제 API 1차 시도 read timeout.
t = 10s   ★ 게이트웨이가 10초 예산 초과로 포기 → 사용자에게 504 응답
          사용자 화면: "주문 실패"
          그런데 주문 서비스는 아직 일하고 있다.
t = 10s   결제 API 2차 시도 read timeout.
t = 12s   ★ 알고 보니 결제 API는 1차 시도를 실제로 처리했고,
          승인이 뒤늦게 완료됐다.
t = 14s   주문 서비스가 포인트 API까지 마치고 주문을 생성한다.
          DB 상태: 결제 승인됨 + 주문 생성됨
          사용자 화면: "주문 실패"
```

여기서 두 가지 사고가 동시에 났다.

**하나, 버려지는 작업(낭비).** t=10s부터 t=14s까지 4초 동안 주문 서비스는 **아무도 기다리지 않는 응답**을 만들고 있었다. 그 4초 동안 워커 스레드 하나, DB 커넥션, 결제 API 호출 슬롯을 썼다. 부하가 높을 때 이 낭비가 누적되면 실질 처리 능력이 그만큼 줄어든다 — **이미 포기된 요청이 아직 살아 있는 요청의 자원을 빼앗는** 구조다.

**둘, 정합성 파괴(더 심각).** 사용자는 실패를 봤는데 DB에는 결제와 주문이 남았다. 이 상태를 흔히 **유령 성공**이라 부른다. 사용자는 실패했다고 믿으니 다시 주문하고, 멱등성 장치가 없으면 이중 결제가 된다. 반대로 포기하고 떠나면 결제만 되고 아무도 모르는 주문이 남는다.

그래서 원칙은 한 문장이다. **각 계층의 타임아웃(재시도와 backoff를 포함한 최악 합)은 자기 상위의 남은 예산보다 반드시 작아야 한다.** 이 순서가 지켜지면 "상위가 먼저 포기하는" 상황 자체가 생기지 않는다.

돈이 걸린 경로라면 여기에 하나를 더 붙여야 한다. 타임아웃은 성공인지 실패인지 알 수 없는 상태를 만들므로, 쓰기 연산에는 **멱등성 키**가 함께 있어야 한다(10장 `10-payment-consistency/10-distributed-saga-compensation-idempotency.md`). 타임아웃 설계와 멱등성 설계는 짝이다.

### 3-4. 남은 예산을 하위로 전파한다 (가산점 포인트)

3-2의 배분에는 한계가 하나 있다. **하위 서비스에 걸린 타임아웃은 고정값이라, "자기가 언제 호출되었는지"를 모른다.**

게이트웨이 예산이 3초인데 게이트웨이 내부 지연으로 이미 2.5초가 지난 뒤 주문 서비스가 호출됐다고 하자. 주문 서비스는 자기 타임아웃 2.6초를 온전히 쓸 것이므로 총합은 5.1초가 되어 예산을 크게 넘긴다. 게이트웨이는 3초에 끊을 테니 그 뒤의 작업은 전부 3-3의 낭비가 된다.

해법은 **남은 예산을 값으로 넘겨 주는 것**이다. 상위가 "너에게 남은 시간은 500ms다"를 헤더에 실어 보내면, 하위는 그 안에서 자기 타임아웃을 다시 계산한다.

```java
// 상위: 남은 예산을 계산해 헤더로 전파한다
long elapsed = System.currentTimeMillis() - requestStartMillis;
long remaining = totalBudgetMillis - elapsed;   // 예: 3000 - 2500 = 500

// 이미 예산을 다 썼다면 호출 자체를 하지 않는다.
// 어차피 버려질 작업을 하위에 만들지 않는 것이 가장 값싼 방어다.
if (remaining <= MIN_USEFUL_MILLIS) {
    throw new DeadlineExceededException();
}

headers.set("X-Request-Deadline-Millis", String.valueOf(remaining));
```

```java
// 하위: 받은 남은 예산을 자기 타임아웃의 상한으로 쓴다
long budget = header("X-Request-Deadline-Millis")
        .map(Long::parseLong)
        .orElse(DEFAULT_BUDGET_MILLIS);   // 헤더가 없으면 기본 예산으로 폴백

// ★ 이 판단이 핵심이다.
// 남은 시간이 자기 최소 처리 시간보다 짧으면, 시작해도 완주할 수 없다.
// 그럴 때는 시작하지 않고 즉시 포기하는 것이 옳다 —
// 결과가 버려질 작업에 DB 커넥션과 스레드를 쓰지 않는다.
if (budget < minimumProcessingMillis) {
    throw new DeadlineExceededException();
}

long callBudget = Math.min(budget - myProcessingMillis, PAYMENT_BUDGET_MILLIS);
```

이 방식을 **데드라인 전파(deadline propagation)**라고 부른다. gRPC는 이것을 프로토콜 차원에서 기본 기능으로 제공하고(호출에 deadline을 걸면 하위 호출로 자동 전파된다), HTTP에서는 위처럼 헤더 규약을 팀에서 정해 쓴다.

효과가 두 가지다. **정확성** — 고정 타임아웃보다 예산을 정확히 지킨다. 그리고 **효율** — "이미 늦었으니 시작하지 않는다"는 판단은 과부하 상황에서 가장 값싼 부하 감소 수단이다(요청을 선별해 버리는 load shedding의 한 형태로, 21번 문서 `21-load-shedding-priority-and-location.md`와 이어진다).

### 3-5. HTTP 밖의 타임아웃 — 커넥션 풀과 PostgreSQL

같은 원리가 계층마다 반복된다. 그런데 DB 쪽에는 **이름 때문에 거의 모두가 오해하는 설정**이 하나 있어, 이것부터 바로잡아야 한다.

#### HikariCP `connectionTimeout`은 "DB에 연결하는 시간"이 아니다

이름을 읽으면 "DB 서버에 TCP 연결을 맺는 데 걸리는 시간의 상한"으로 보인다. **아니다.**

**HikariCP의 `connectionTimeout`은 "커넥션 풀에서 커넥션을 얻기까지 기다리는 시간"의 상한이다.** 즉 `dataSource.getConnection()`을 호출했을 때, 이 시간 안에 커넥션을 손에 쥐지 못하면 `SQLTransientConnectionException`을 던진다.

동작을 나눠 보면 분명해진다.

```text
dataSource.getConnection() 호출

  풀에 유휴 커넥션이 있다        → 즉시 반환. connectionTimeout은 안 쓰인다.
  풀이 전부 대여 중이다          → 누군가 반납할 때까지 기다린다.
                                  ★ 이 대기의 상한이 connectionTimeout이다.
  풀에 여유가 있어 새로 만든다    → 새 커넥션을 만드는 시간도 이 대기에 포함된다.
```

**DB 서버로의 TCP 연결 수립 시간은 이 값이 아니라 JDBC 드라이버의 연결 옵션이 담당한다.** PostgreSQL 드라이버라면 `connectTimeout`이다. 이름이 거의 같고(`connectionTimeout` vs `connectTimeout`), 단위도 다르고(밀리초 vs 초), 재는 것은 완전히 다르다. 이 셋이 겹쳐 혼동이 생긴다.

그리고 이 값의 **기본값 30초가 위험하다.** 풀이 고갈되면 요청마다 30초씩 커넥션을 기다리며 워커 스레드를 붙잡는다 — **1절의 스레드 인질극이 DB 쪽에서 그대로 재현된다.** 외부 API 타임아웃만 조여 놓고 이 값을 기본값으로 둔 시스템은 방어에 큰 구멍이 있는 셈이다. 3-2의 예산 안으로 이 값도 끌고 들어와야 한다.

```yaml
spring:
  datasource:
    hikari:
      # 풀에서 커넥션을 "얻기까지" 기다리는 시간. 기본 30초는 너무 길다.
      # 풀이 마르면 여기서 30초씩 워커 스레드가 묶인다.
      # 3-2에서 계산한 예산 안으로 끌어와 짧게 잡고, 못 얻으면 빨리 실패한다.
      connection-timeout: 2000        # 2초
      # 풀 크기. 이 값이 곧 "동시에 실행될 수 있는 쿼리 수"의 상한이다.
      maximum-pool-size: 20
      # 커넥션이 살아 있는지 확인하는 데 쓰는 시간의 상한.
      validation-timeout: 1000
      data-source-properties:
        # ↓ 여기부터는 PostgreSQL JDBC 드라이버 옵션이다 (단위: 초).
        # DB 서버로 TCP 연결이 맺어질 때까지의 상한.
        # 위 connection-timeout과 재는 것이 완전히 다르다.
        connectTimeout: 2
        # 소켓 무응답의 상한. 기본값 0 = 무한이므로 반드시 지정한다.
        # DB 서버가 응답 없이 사라진 경우(네트워크 단절, 서버 프리즈)에
        # 쿼리 타임아웃조차 동작하지 않을 수 있어 이것이 최후 방어선이다.
        socketTimeout: 10
```

#### PostgreSQL 서버가 스스로 강제하는 세 가지

클라이언트 쪽 타임아웃은 네트워크가 정상이어야 동작한다. **서버가 스스로 끊어 주는 장치**를 함께 둬야 방어가 완성된다. PostgreSQL에는 성격이 다른 세 가지가 있다.

**`statement_timeout` — SQL 문 하나의 실행 시간 상한.** 이 시간을 넘긴 문은 서버가 취소하고 에러를 반환한다. 단위가 "문"이라는 점이 중요하다 — 트랜잭션 전체가 아니라 문 하나마다 따로 적용되므로, 3초짜리 문이 다섯 개면 트랜잭션은 15초까지 갈 수 있다.

**`lock_timeout` — 락을 획득하기 위해 기다리는 시간의 상한.** 넘기면 에러가 난다. `statement_timeout`과 재는 것이 다르다 — 이쪽은 **대기만** 잰다. 락을 얻은 뒤의 실행 시간은 관여하지 않는다. 이 값이 왜 따로 필요한가 하면, 락 대기는 내 쿼리가 무거워서가 아니라 **남이 쥐고 있어서** 생기는 지연이므로 실행 시간과 별개로 통제해야 한다. 예를 들어 `ALTER TABLE`처럼 강한 락이 필요한 작업에 `lock_timeout`을 짧게 걸면, 락을 못 얻을 때 조용히 포기하게 되어 **뒤에 줄 선 모든 쿼리를 막는 사고**를 막을 수 있다.

**`idle_in_transaction_session_timeout` — 트랜잭션을 열어 둔 채 아무 쿼리도 실행하지 않는 세션을 끊는다.** 애플리케이션이 트랜잭션 안에서 외부 API를 호출하다 멈추면 이런 세션이 생긴다. 방치하면 두 가지 피해가 난다. 그 트랜잭션이 쥔 락이 계속 남아 다른 작업을 막고, **오래된 행 버전을 정리하는 VACUUM이 그 트랜잭션 때문에 진행되지 못해 테이블이 부푼다.** 애플리케이션 버그가 DB 전체의 성능 문제로 번지는 경로를 막는 안전판이다.

값은 애플리케이션 계정에 기본값으로 박아 두는 것이 안전하다. 코드에서 빠뜨려도 서버가 지켜 준다.

```sql
-- 온라인 API용 계정: 짧게 조인다
ALTER ROLE app_user SET statement_timeout = '3s';
ALTER ROLE app_user SET lock_timeout = '1s';
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '30s';

-- 배치 계정은 긴 쿼리가 정상이므로 따로 준다.
-- 같은 값을 전 계정에 걸면 배치가 죽거나, 배치에 맞추면 온라인이 위험해진다.
ALTER ROLE batch_user SET statement_timeout = '30min';
ALTER ROLE batch_user SET lock_timeout = '10s';

-- 특정 쿼리 하나만 예외를 두고 싶으면 세션·트랜잭션 단위로 덮어쓴다
BEGIN;
SET LOCAL statement_timeout = '60s';   -- 이 트랜잭션 안에서만 유효
SELECT ... ;                            -- 무거운 집계 한 방
COMMIT;
```

#### `@Transactional(timeout)`과 JDBC `queryTimeout`의 관계

Spring의 `@Transactional(timeout = 3)`은 초 단위로 **트랜잭션 전체의 데드라인**을 정한다. 동작 방식을 알아 두면 왜 이것이 예산 배분과 같은 성질인지 보인다.

```java
// 트랜잭션 시작 시각을 기준으로 3초의 데드라인이 설정된다.
@Transactional(timeout = 3)
public void createOrder(OrderRequest req) {
    orderRepository.save(req.toEntity());   // 여기서 1.2초 걸렸다면
    pointRepository.deduct(req.userId());   // 이 쿼리에는 남은 1.8초가 걸린다
    couponRepository.use(req.couponId());   // 앞의 둘이 2.9초를 썼다면 0.1초만 남는다
}
```

Spring은 트랜잭션 시작 시각과 timeout으로 데드라인을 계산해 두고, 그 트랜잭션 안에서 실행되는 **각 JDBC Statement에 "남은 시간"을 `setQueryTimeout()`으로 걸어 준다.** 그래서 "쿼리 하나당 3초"가 아니라 **"트랜잭션 전체 3초"**이며, 이미 쓴 만큼을 빼서 다음 쿼리에 주는 방식이다 — 3-2에서 예산을 위에서 아래로 나눠 준 것과 정확히 같은 발상이다.

여기에 한계가 하나 있다. **`setQueryTimeout`은 드라이버가 서버에 취소를 요청하는 방식**이다. PostgreSQL 드라이버는 별도의 연결로 취소 요청을 보내는데, 네트워크가 끊긴 상황에서는 그 요청 자체가 전달되지 않는다. 즉 **네트워크 장애에는 클라이언트 쪽 타임아웃이 무력할 수 있다.**

그래서 세 겹이 다 필요하다. 서버가 스스로 강제하는 `statement_timeout`은 네트워크와 무관하게 동작하고, 소켓 수준의 `socketTimeout`은 응답이 영원히 오지 않는 경우의 최후 방어선이 된다.

전체를 계층으로 정리하면 이렇다.

```text
[애플리케이션]  @Transactional(timeout=3)
                  트랜잭션 전체의 데드라인. 각 Statement에 남은 시간을
                  setQueryTimeout으로 전달한다. 드라이버가 취소를 "요청"한다.
        │
[커넥션 풀]     HikariCP connectionTimeout (기본 30초 — 짧게 조일 대상)
                  ★ 풀에서 커넥션을 얻기까지 기다리는 시간.
                    DB에 연결하는 시간이 아니다.
        │
[JDBC 드라이버] connectTimeout   DB 서버로 TCP 연결이 맺어질 때까지
                socketTimeout    소켓 무응답의 상한 (기본 0 = 무한)
        │
[DB 서버]       statement_timeout                    문 하나의 실행 시간 상한
                lock_timeout                         락 획득 대기의 상한
                idle_in_transaction_session_timeout   트랜잭션 열어둔 유휴 세션 정리
```

**"타임아웃은 HTTP 클라이언트만의 문제가 아니라 모든 블로킹 I/O의 문제"**이고, 계층 중 하나라도 무한이면 그 계층이 전체 방어의 구멍이 된다.

### 3-6. 서킷 브레이커·재시도와의 관계

세 장치는 대체재가 아니라 **순서가 있는 한 세트**다. **타임아웃이 있어야 실패가 유한 시간 안에 판정되고**, 실패 판정이 있어야 **재시도와 서킷이 성립하며**(무엇을 세어 실패율을 계산할지가 정해진다), **서킷이 없으면 재시도가 이미 죽은 상대를 계속 두드린다.** 그래서 도입 순서도 타임아웃 → 재시도 → 서킷이다.

**타임아웃이 첫 번째 나사인 이유**를 정확히 짚자. 타임아웃이 없으면 응답이 오지 않는 호출은 실패로도 성공으로도 판정되지 않고 영원히 "진행 중"이다. 판정되지 않은 호출은 서킷의 슬라이딩 윈도우에 들어가지 못하므로 실패율이 올라가지 않고, **서킷은 열리지 않은 채 스레드가 다 마른다.** 재시도도 마찬가지다 — 첫 시도가 끝나지 않으니 재시도할 기회 자체가 오지 않는다. **타임아웃은 재시도와 서킷의 전제 조건**이다.

배치 순서는 호출에 가까운 안쪽부터 타임아웃 → 재시도 → 서킷이 일반적이다. 여기서 타임아웃이 두 위치에 있을 수 있다는 점만 구분하면 된다.

```text
서킷 ( 재시도 ( 구간 타임아웃 ( 실제 호출 ) ) )
              ↑
              시도 한 번의 상한 (2-1의 connection/read)

전체 타임아웃 ( 서킷 ( 재시도 ( 구간 타임아웃 ( 실제 호출 ) ) ) )
↑
재시도 전체를 포함한 논리적 호출 하나의 상한
```

**구간 타임아웃은 재시도 안쪽에서 시도 하나하나를 자르고, 전체 타임아웃은 재시도 바깥에서 전부를 합쳐 자른다.** 3-2의 계산에서 결제 예산 1,200ms가 후자이고, 한 시도의 500ms(connect 100 + read 400)가 전자였다. Resilience4j의 기본 조합 순서에서는 `TimeLimiter`가 `Retry`보다 안쪽이라 시도별 상한으로 동작하므로, 재시도 전체를 묶는 상한이 필요하면 바깥에 따로 씌워야 한다.

서킷의 `slowCallDurationThreshold`도 타임아웃과 함께 정해야 하는 값이다. **타임아웃보다 이 값이 크면 느린 호출로 집계될 기회가 없다** — 타임아웃이 먼저 터져 전부 실패로 잡히기 때문이다. (서킷 설정 전체: 9번 문서 `09-circuit-breaker-state-transition-tuning.md`, 재시도와 backoff 계산: 11번 문서 `11-retry-storm-backoff-jitter.md`)

## 4. 꼬리질문 대비 포인트

### "connection timeout과 read timeout이 터지는 상황은 어떻게 다르고, 대응도 달라지나요?"

connection timeout은 요청이 **상대에게 도달하기 전**의 실패라서 부작용이 없다는 것이 확실하다 — 안전하게 재시도할 수 있다. read timeout은 요청이 이미 상대에게 도달해 **처리됐을 수도 있는** 상태의 실패다 — 결제 요청이었다면 "실패로 보였지만 실제로는 승인된" 경우가 가능하므로, 멱등성 보장 없이 재시도하면 중복 결제가 난다. 같은 타임아웃이라도 "요청이 넘어갔는가"에 따라 재시도 안전성이 갈린다는 구분이 핵심이다.

한 걸음 더 나가면 좋은 대답이 된다. **타임아웃은 실패가 아니라 "결과를 모르는 상태"다.** 명시적인 실패 응답(500)은 "확실히 안 됐다"는 정보인데, 타임아웃은 됐는지 안 됐는지 알려 주지 않는다. 그래서 read timeout 후의 재시도는 **멱등성 키가 있을 때만** 안전하고, 없으면 재시도 대신 조회로 결과를 확인하거나 사람이 개입할 대기열에 넣어야 한다.

### "read timeout이 있는데도 전체 응답이 한없이 길어질 수 있는 이유는?"

read timeout은 **데이터 조각 사이의 무응답 시간만** 제한하기 때문이다. 상대가 타임아웃 직전 간격으로 응답을 조금씩 흘리면 read timeout은 계속 리셋되며 전체 시간은 무한정 늘어난다.

숫자를 붙이면 설득력이 생긴다. read timeout 3초에 2.9초 간격으로 조각이 7번 오면 read timeout은 한 번도 터지지 않는데 총 소요는 21초다(2.9 × 7 + 0.7). 또 재시도가 있으면 `(connect + read) × 시도 횟수`로 최악 시간이 곱해진다.

그래서 총 소요 시간의 보장이 필요한 곳에는 요청 전체를 감싸는 타임아웃(`TimeLimiter`, `orTimeout`, WebClient의 `.timeout()` 등)을 별도로 둔다. **DNS 조회 구간을 덮는 것도 이 전체 타임아웃뿐**이라는 점까지 말하면 좋다 — 호스트명 해석이 멈추면 connection timeout도 read timeout도 터지지 않는다.

### "타임아웃 값을 너무 짧게 잡으면 어떤 문제가 생기나요?"

정상적으로 처리 중인 요청을 실패로 판정하는 거짓 실패가 늘어난다. 그 실패가 재시도를 유발하면 상대 입장에서는 "아직 처리 중인 요청 + 새로 온 재시도"로 부하가 배가 되고, 부하 증가로 응답이 더 느려져 타임아웃이 더 많이 터지는 악순환에 들어간다.

그래서 타임아웃 단축은 반드시 대상의 p99 관측치를 근거로 해야 하고, 재시도 정책과 함께 검토해야 한다. **평균으로 잡으면 안 되는 이유**를 덧붙이면 좋다 — 응답시간 분포는 오른쪽으로 긴 꼬리를 가지므로 평균 위에 정상 요청이 상당수 있고, 평균에 맞춘 타임아웃은 그것들을 통째로 자른다.

### "HTTP 말고 DB 호출에는 어떤 타임아웃들이 있나요?" (가산점 포인트)

같은 원리가 계층마다 반복된다. **네 계층으로 나눠 답하면 정리가 깔끔하다.**

**(1) 커넥션 풀 — HikariCP `connectionTimeout`.** 여기서 오해를 먼저 바로잡는 것이 이 질문의 득점 포인트다. 이 값은 "DB에 연결하는 시간"이 아니라 **"풀에서 커넥션을 얻기까지 기다리는 시간"**이다. 기본값 30초라 풀이 고갈되면 요청마다 30초씩 워커 스레드가 묶인다 — 1절의 스레드 인질극이 DB 쪽에서 재현되는 경로다.

**(2) 드라이버 — `connectTimeout`, `socketTimeout`.** DB 서버로 TCP 연결이 맺어질 때까지(`connectTimeout`)와 소켓 무응답의 상한(`socketTimeout`)이다. PostgreSQL 드라이버의 `socketTimeout` 기본값은 0, 즉 무한이므로 반드시 지정한다. **socket timeout이 없으면 쿼리 타임아웃조차 동작하지 않는 경우**가 있는데, 취소 신호가 네트워크로 전달돼야 하기 때문이다.

**(3) 애플리케이션 — `@Transactional(timeout)`.** 트랜잭션 전체의 데드라인을 정하고, 각 JDBC Statement에 남은 시간을 `setQueryTimeout`으로 전달한다. "쿼리당"이 아니라 "트랜잭션 전체"라는 점, 그리고 드라이버가 **취소를 요청하는** 방식이라 네트워크 장애에는 무력할 수 있다는 점을 같이 말하면 좋다.

**(4) DB 서버 — PostgreSQL의 세 가지.** `statement_timeout`은 문 하나의 실행 시간 상한, `lock_timeout`은 락 획득 대기의 상한(실행 시간은 안 잰다), `idle_in_transaction_session_timeout`은 트랜잭션을 열어 둔 채 유휴인 세션을 끊는다. 마지막 것은 그런 세션이 락을 붙잡고 VACUUM까지 막아 테이블을 부풀리기 때문에 필요하다. **서버 쪽 값은 애플리케이션 계정과 배치 계정에 각각 다르게 걸어 두는 것**이 실무 관행이다.

마무리는 이렇게 하면 좋다. **"타임아웃은 HTTP 클라이언트만의 문제가 아니라 모든 블로킹 I/O의 문제이고, 계층 중 하나라도 무한이면 그 계층이 전체 방어의 구멍이 된다."**

### "타임아웃 값은 한 번 정하면 끝인가요?" (시니어 변별 포인트)

아니다. 타임아웃은 상대의 응답시간 분포에 대한 **가설**이므로, 상대의 성능이 변하면(데이터 증가, 트래픽 성장, 상대 쪽 배포) 무효가 된다.

운영에서는 (1) 대상별 응답시간 p99와 타임아웃 발생률을 대시보드로 추적하고, (2) 타임아웃 발생률이 평상시 baseline을 넘으면 알림을 걸고, (3) p99가 타임아웃 값에 근접해오면 "타임아웃을 늘릴지, 상대 성능을 개선할지"를 의사결정한다.

**무조건 늘리는 것은 스레드 인질 시간을 늘리는 것**이므로, 전체 예산 안에서만 조정한다는 원칙까지 말하면 운영 경험이 드러난다. 한 계층의 타임아웃을 늘리려면 3-2의 배분표를 다시 계산해 어디서 그만큼을 빼올지 정해야 한다 — 재시도 횟수를 줄이거나, 직렬 호출을 병렬로 바꾸거나, 사용자 SLO 자체를 재협상하거나다. **"타임아웃을 늘렸다"는 결정이 "무엇을 포기했다"와 짝을 이루지 않으면 예산은 이미 깨진 것이다.**

## 한 줄 요약

타임아웃은 connection(연결 수립)·read(응답 조각 간 대기)·전체(호출 총 상한)가 각각 다른 구간을 지키는 별개의 나사이며 — read timeout 3초여도 2.9초 간격으로 조각이 오면 21초가 걸리므로 전체 상한이 따로 필요하다 — 값은 상대의 p99 관측치 + 여유로 잡고, 체인 전체로는 사용자 SLO를 위에서 아래로 나눠 주는 예산 배분(3,000 − 게이트웨이 몫 − 여유 = 2,600 → 자기 처리·여유를 빼고 하위에 2,100 → 재시도 1회면 시도당 500)으로 계산해 하류의 최악 합이 상류 예산 안에 들어오게 해야 한다. 어긋나면 상위가 먼저 포기해 하위 작업이 버려지고 심하면 유령 성공으로 정합성이 깨지며, 타임아웃 없는 외부 호출은 2초 만에 스레드 풀을 마르게 해 그 API와 무관한 요청까지 전부 죽이는 연쇄 장애의 시한폭탄이고, 같은 방어를 HikariCP(`connectionTimeout`은 풀 대기 시간이다)·JDBC(`socketTimeout` 기본 0)·PostgreSQL(`statement_timeout`/`lock_timeout`/`idle_in_transaction_session_timeout`) 계층마다 반복해야 완성된다.
