# 대기열 시스템 설계 — "전원 수용 불가"를 인정하는 데서 설계가 시작된다

> 핵심 관전 포인트: **티켓팅급 트래픽은 서버 증설로 풀 수 없다 — 병목이
> 무상태 서버가 아니라 "한정 수량"이라는 공유 상태(재고 row)로 수렴하기
> 때문이다. 그래서 목표를 "전원을 즉시 처리"에서 "코어 시스템이 감당
> 가능한 속도만큼만 흘려보내고, 나머지는 공정한 순서로 기다리게 한다"로
> 재정의한다. 구조는 3계층 — (1) 대기 페이지는 정적으로 만들어 CDN이
> 체류 트래픽을 받고, (2) 대기열 계층이 Redis Sorted Set으로 진입 순서를
> 관리하며, (3) 뒷단 처리 용량에서 역산한 속도로만 입장 토큰을 발급하고,
> 주문 API는 토큰 없는 요청을 거절한다. 대기열은 동시성 제어 장치가
> 아니라 유량 제어 장치다 — 재고 정합성은 뒷단에서 따로 지킨다.**

---

## 0. 질문 + 의도

**질문**: "특정 시각 선착순 이벤트(티켓팅급 트래픽)를 위한 대기열 시스템을
설계해보세요."

**출제 의도**: 수요가 공급을 초과할 때 "전원 수용 불가"를 인정하고 실패를
공정하고 우아하게 배분하는 설계를 할 수 있는지 본다. 시스템 한계를
인정하는 데서 출발하는 사고 — 무한 확장 환상이 없는지가 관전 포인트다.

## 1. 문제의 재정의 — 왜 스케일 아웃이 답이 아닌가

숫자로 상황을 그려보자. 한정 수량 1만 개, 오픈 시각에 몰리는 사용자
100만 명. 어떤 설계를 하든 **99%는 실패한다** — 이것은 버그가 아니라
이 문제의 정의다. 그렇다면 설계 목표는 "전원 성공"이 될 수 없고, 다음
세 가지로 재정의된다:

1. **코어 시스템 보호** — 주문·결제·재고 처리 계층은 평상시와 같은
   부하 수준에서 동작해야 한다.
2. **실패의 공정한 배분** — 먼저 온 사람이 먼저 처리되고, 내 순서가
   언제쯤인지 예측 가능해야 한다. "운 좋게 새로고침 잘한 사람"이
   이기는 구조는 실패한 설계다.
3. **대기 트래픽의 저렴한 수용** — 기다리는 99만 명의 체류는 가장 값싼
   계층(CDN·정적 페이지)이 받아야 한다.

"서버를 100대로 늘리면 되지 않나?"가 통하지 않는 이유가 이 질문의
핵심이다:

- **병목이 상태 있는 계층으로 수렴한다.** 무상태 API 서버는 얼마든지
  늘릴 수 있다. 하지만 모든 요청은 결국 **같은 재고 데이터**를 두고
  경쟁한다. 재고 1만 개라는 상태는 복제해서 늘릴 수 없고, DB의 해당
  row에 대한 락 경쟁은 서버가 많아질수록 오히려 심해진다.
- **"다 받아주기"는 전원을 느리게 만든다.** 100만 요청을 모두 코어까지
  들여보내면 커넥션 풀·락 대기가 폭발해 전원이 타임아웃을 겪는다.
  성공했어야 할 1만 명까지 실패하는 최악의 결과다.
- **실패시키는 데에 가장 비싼 자원을 쓴다.** 어차피 실패할 99만 요청이
  DB까지 내려가서야 실패를 알게 되는 구조는, 거절 비용을 시스템에서
  가장 비싼 곳에서 치르는 셈이다.

비유하면 은행 창구다. 명절에 고객이 몰린다고 창구를 100개로 늘리는 게
아니라 **번호표를 뽑게 한다** — 창구(코어)는 자기 속도로 일하고,
대기 고객은 로비(값싼 계층)에서 자기 순서를 예측하며 기다린다.

## 2. 아키텍처 — 3계층 설계

```text
클라이언트 100만
  → [CDN / 정적 대기 페이지]     대부분의 "체류"를 값싼 계층이 감당
  → [대기열 서비스]              Redis Sorted Set: 진입 시각 기준 순번
      · 순번 조회 (polling / SSE)
      · 입장 토큰 발급 — 뒷단 용량에서 역산한 속도로만
  → [게이트웨이: 입장 토큰 검증]  토큰 없으면 대기열로 돌려보냄
  → [코어: 주문·결제·재고]       평상시 수준의 부하로 동작
```

### ① 진입과 순번 관리 — Redis Sorted Set

사용자가 이벤트 페이지에 진입하면 대기열에 등록하고 순번을 부여한다.
Sorted Set은 "점수(score) 순으로 정렬된 집합"이라 진입 시각을 점수로
쓰면 순번 관리가 그대로 된다:

```text
# 진입 — 이미 등록된 사용자는 점수를 덮어쓰지 않는다(NX)
#        → 새로고침해도 순번이 뒤로 밀리지 않는 공정성의 핵심
ZADD waiting NX <진입시각 epochMillis> user:1234

# 내 순번 조회 (0부터, O(log N))
ZRANK waiting user:1234

# 입장 처리 — 스케줄러가 주기마다 맨 앞에서 N명을 꺼내 토큰 발급
ZPOPMIN waiting N
```

순번 조회는 클라이언트 polling(수 초 간격 + 랜덤 지터로 동시 폭주 방지)
또는 SSE로 내려준다. polling 자체도 대량 트래픽이므로 처리 경로를
"Redis ZRANK 한 번"으로 끝나게 가볍게 유지하고, 대기 페이지의 정적
자원은 전부 CDN에 태운다.

### ② 입장 속도 결정 — 감이 아니라 역산 (가산점 포인트)

"초당 몇 명 입장"은 대기열 설계의 심장이고, 이 숫자는 **뒷단 처리
용량에서 역산**한다. Little's Law(L = λ × W)를 쓰면: 코어가 초당
λ건을 처리하고 주문 완료까지 평균 W초가 걸린다면, 시스템 안에 동시에
머무는 사용자는 L = λ×W 명이다. 부하 테스트로 코어의 한계 처리량을
실측하고, 안전 마진을 둔 λ만큼만 입장시키면 코어는 이벤트 중에도
평상시처럼 동작한다. 고정값 대신 뒷단 지표(p99 지연, DB 커넥션
사용률)를 보고 입장 속도를 동적으로 조이는 것까지 말하면 가산점이다.

### ③ 코어 보호 — 입장 토큰 검증

대기열이 있어도 주문 API가 그대로 열려 있으면 우회당한다. 입장한
사용자에게 **서명된 토큰**(위조 불가 + 짧은 만료시간 + 1회성)을 주고,
코어 진입점에서 강제한다:

```java
// Before: 이벤트 시작 = 주문 API에 100만 명이 직접 충돌
@PostMapping("/orders")
public OrderResponse order(@RequestBody OrderRequest req) {
    // 문제 1: 모든 요청이 같은 재고 row를 두고 락 경쟁
    //         → DB 커넥션 고갈, 락 대기 타임아웃, 무관한 기능까지 마비
    // 문제 2: 어차피 실패할 99% 요청도 DB까지 내려가서야 실패를 안다
    return orderService.order(req);
}
```

```java
// After: 입장 토큰이 없으면 코어에 들어오지 못한다
public class AdmissionTokenFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain) throws ... {
        String token = req.getHeader("X-Admission-Token");
        if (!tokenVerifier.isValid(token)) {   // 서명·만료·사용 여부 검증
            res.setStatus(HttpServletResponse.SC_TOO_MANY_REQUESTS);
            res.setHeader("Location", waitingPageUrl);  // 대기열로 안내
            return;   // 코어 로직·DB 근처에도 못 온다 — 거절이 가장 싸다
        }
        chain.doFilter(req, res);   // 검증된 소수만 코어 진입
    }
}
```

거절 지점이 앞 계층(게이트웨이/필터)일수록 거절 비용이 싸진다 —
"실패는 가능한 한 바깥 경계에서, 싸게"가 이 계층의 원칙이다.

## 3. 실무 디테일 — 설계가 실제로 부딪히는 지점

**대기열은 유량 제어이지 동시성 제어가 아니다.** 입장을 초당 N명으로
줄여도 재고 초과 판매(oversell) 방지는 별도 문제다. 재고 차감은
뒷단에서 원자적으로 처리한다 — Redis 원자 감소로 선차감 후 주문을
만들거나, DB에서 `UPDATE stock SET qty = qty - 1 WHERE id = ? AND
qty > 0` 같은 조건부 갱신으로 지킨다. "대기열을 넣었으니 동시성 문제는
끝"이라고 답하면 두 문제를 혼동한 것이다.

**공정성의 경계 조건들.** 이벤트 시작 전에 미리 들어와 있는 사용자는
시작 시각까지 카운트다운 페이지(역시 CDN)에 머물게 하고, 시작 시각에
대기열 등록이 열리게 한다. 등록 시 `NX` 옵션으로 재접속·새로고침에도
순번을 유지하고, 예상 대기시간은 `내 순번 ÷ 초당 입장 수`로 계산해
보여준다 — "예측 가능한 기다림"이 무한 새로고침을 막는 UX 장치다.

**우회·부정 사용 방지.** 토큰은 서버 서명으로 위조를 막고, 사용 처리로
재사용을 막는다. 매크로·봇 대응은 대기열 진입 시점의 봇 판별(CAPTCHA
등)과 계정당 구매 수량 제한을 병행한다 — 대기열 자체는 봇을 막지
못한다는 한계를 인지하고 있다고 말하는 것이 오히려 신뢰를 준다.

**대기열 자체의 장애.** Redis가 죽으면 대기열이 단일 장애점(SPOF)이
된다. 복제 구성으로 가용성을 올리되, "그래도 죽었을 때"의 정책을 미리
정해둔다 — 순번 데이터가 유실되면 어설픈 복구보다 "대기열 재시작"을
공지하는 편이 낫고, 대기열이 내려간 동안 코어를 열어버리는 것(무순번
입장)은 코어 보호와 공정성을 동시에 깨므로 기본값은 차단 유지다.
완벽한 복구보다 **예측 가능한 실패 정책**이 먼저다.

## 4. 꼬리질문 대비 포인트

### "초당 몇 명씩 입장시킬지는 어떻게 정하나요?"

뒷단(주문·결제·재고)의 실측 처리량에서 역산한다. 부하 테스트로 코어의
한계 TPS와 요청당 평균 처리 시간(W)을 재고, Little's Law(L = λW)로
동시 체류 인원의 상한을 잡은 뒤 안전 마진을 둔다. 한 걸음 더 —
운영 중에는 고정값이 아니라 뒷단 지표(p99, DB 커넥션 사용률, 에러율)를
보며 입장 속도를 동적으로 조절하는 피드백 루프를 두면, 외부 PG가
느려지는 등의 변수에도 코어가 보호된다.

### "사용자가 새로고침하거나 나갔다 다시 들어오면 순번은 어떻게 되나요?"

순번의 키를 요청이 아니라 사용자(로그인 유저 id, 비로그인이면 발급한
쿠키 토큰) 단위로 잡고, 등록 시 이미 있으면 점수를 갱신하지 않는다
(`ZADD NX`). 재접속하면 기존 순번을 그대로 돌려준다. 이걸 놓치면
"새로고침하면 맨 뒤로"가 되어 사용자가 새로고침을 두려워하거나,
반대로 매 요청 등록이면 폭주를 유발한다.

### "대기열을 우회해서 주문 API를 직접 호출하면 어떻게 되나요?"

코어 진입점(게이트웨이 또는 서비스 앞 필터)에서 입장 토큰 검증을
강제한다. 토큰은 서버 서명(HMAC 등)으로 위조 불가하게, 짧은 TTL과
1회성으로 재사용 불가하게 만든다. 원칙은 "클라이언트는 신뢰하지
않는다" — 프런트에서 버튼을 숨기는 것은 방어가 아니고, 검증은 반드시
서버 경계에서 한다.

### "Redis 대기열 자체가 죽으면 어떻게 하나요?"

대기열이 SPOF임을 인정하는 데서 출발한다. 복제/자동 페일오버로
가용성을 올리되, 그래도 죽는 경우의 정책을 사전에 정한다: 기본값은
코어 차단 유지(무순번 입장은 코어 보호와 공정성을 동시에 깬다), 순번
유실 시에는 "대기열 재시작" 공지가 어설픈 복구보다 낫다. "장애가 안
나게 한다"가 아니라 "장애 시의 동작을 미리 결정해둔다"로 답하는 것이
포인트다.

### "그냥 이벤트 시간에만 서버와 DB를 크게 늘려두면 안 되나요?" (시니어 변별 포인트)

세 겹으로 답한다. ① **병목이 공유 상태로 수렴한다** — 재고라는 상태는
늘릴 수 없고, 같은 row를 향한 락 경쟁은 서버가 많을수록 심해진다.
증설은 무상태 계층의 해법이지 이 문제의 해법이 아니다. ② **전원이
느린 실패를 겪는다** — 다 받아주면 성공할 1만 명까지 타임아웃에
휩쓸린다. 수용 불가를 인정하고 명시적으로 기다리게 하는 쪽이 UX도
낫다. ③ **비용** — 연중 몇 시간의 피크를 위해 상시급 인프라를 사는
셈이다. 결국 이 질문은 "무한 확장 환상이 있는가"를 보는 것이므로,
"확장으로 풀 문제와 흐름 제어로 풀 문제를 구분한다"는 프레임을
보여주는 것이 답의 뼈대다.

## 한 줄 요약

티켓팅급 트래픽의 대기열 설계는 "전원 수용 불가"라는 한계를 인정하고
목표를 재정의하는 데서 시작한다 — 체류는 CDN이, 순서는 Redis Sorted
Set이, 입장 속도는 뒷단 용량의 역산(Little's Law)이 담당하고, 코어는
서명된 입장 토큰 뒤에서 평상시 부하로 동작한다. **대기열은 유량
제어 장치이며, 재고 정합성은 뒷단에서 원자적으로 따로 지킨다.**
