# Cascading Failure — 느린 다운스트림 하나가 전체를 마비시키는 메커니즘과 방어 계층

> 핵심 관전 포인트: **연쇄 장애의 매개체는 "공유 자원의 고갈"이다.
> 느린 다운스트림을 기다리는 스레드가 서버의 공용 스레드 풀을 하나씩
> 점유하고, 풀이 바닥나면 그 다운스트림과 무관한 요청까지 전부 막힌다 —
> 장애가 기능 경계를 넘는 순간이다. 같은 패턴이 상류로 반복되며 호출
> 체인을 거슬러 올라가고, 재시도 증폭과 헬스체크 실패(LB의 인스턴스
> 제거 → 남은 인스턴스 부하 집중)가 전파를 가속한다. 방어는 단일
> 수단이 아니라 계층이다: 타임아웃(개별 대기의 상한) → 재시도
> 제한(증폭 차단) → 서킷 브레이커(지속 장애 시 호출 중단) →
> bulkhead(의존성별 자원 분리로 폭발 반경 제한) → load shedding·
> graceful degradation(그래도 남는 피해의 흡수). bulkhead가 다른 벽과
> 다른 점은 "최악의 경우에도 이 의존성이 점유할 수 있는 자원의 상한"을
> 구조적으로 보장한다는 것이다.**

---

## 0. 질문 + 의도

**질문**: "하나의 느린 다운스트림 서비스가 전체 시스템을 마비시키는 cascading failure의 메커니즘과 방어 계층(bulkhead 등)을 설명해주세요."

**출제 의도**: 대형 장애의 대부분은 단일 원인이 아니라 전파다.
전파 경로(스레드 고갈 → 상류 적체)를 그릴 수 있어야 방어벽(bulkhead,
타임아웃, 서킷)을 어디에 세울지 정할 수 있다 — 대규모 시스템 운영자의
핵심 심성 모델을 갖췄는지 확인하는 질문이다.

## 1. 메커니즘 — 왜 "죽은" 것보다 "느린" 것이 더 위험한가

완전히 죽은 서비스는 connection refused로 **즉시** 실패한다. 호출자는
빠르게 실패를 알고 스레드를 회수한다. 반면 **느린** 서비스는 연결을
받아주고 응답만 늦게 준다 — 호출자의 스레드를 응답 대기 상태로
**붙잡는다**. 연쇄 장애의 연료는 에러가 아니라 이 "붙잡힌 대기"다.

전파를 단계별로 그리면 (추천 서비스가 느려진 상황):

```text
[추천 서비스]  응답이 3초 → 30초로 느려짐 (죽지는 않음)
      ▲ 대기
[웹 서비스]    톰캣 워커 스레드 200개가 순차적으로 추천 대기에 점유됨
               → 풀 고갈: 추천과 무관한 회차 조회·로그인까지 전부 대기
      ▲ 대기
[게이트웨이]   웹 서비스가 응답을 못 주니 게이트웨이 스레드도 적체
      ▲ 재시도
[클라이언트]   타임아웃·에러를 본 사용자가 새로고침 연타 → 유입 자체가 증가
```

단계별 핵심:

1. **점유의 누적**: 추천 응답이 30초 걸리면, 초당 10건의 추천 호출만으로도
   동시 점유 스레드가 300개에 도달한다(Little's Law: L = λ × W =
   10 × 30). 풀 크기 200은 몇십 초 만에 바닥난다.
2. **기능 경계를 넘는 순간**: 스레드 풀은 **공유 자원**이다. 풀이
   바닥나면 추천을 쓰지 않는 요청(회차 조회, 결제)도 스레드를 못 받아
   대기한다 — "추천 저하"였던 장애가 "서비스 전체 다운"이 되는 지점.
3. **상류로 반복**: 웹 서비스가 느려지니 게이트웨이의 스레드도 같은
   원리로 붙잡힌다. 장애가 호출 방향의 **역방향**으로 번식한다.
4. **증폭 가속**: 실패를 본 각 계층과 사용자의 재시도가 부하를
   곱하고(11-retry-storm-backoff-jitter.md의 메커니즘), 과부하로
   **헬스체크까지 타임아웃**되면 LB가 멀쩡한 인스턴스를 풀에서 제거해
   남은 인스턴스에 부하가 집중된다 — 회복 장치가 장애를 가속하는 역설.

요약하면 cascading failure는 "장애가 옮는" 게 아니라 **"대기가 자원을
고갈시키는 패턴이 계층마다 반복되는"** 것이다. 그래서 방어의 본질은
대기에 상한을 두고(타임아웃), 대기가 점유할 수 있는 자원에 상한을
두는(bulkhead) 것이 된다.

## 2. Bulkhead — 폭발 반경(blast radius)을 자원 분리로 제한한다

bulkhead는 배의 격벽에서 온 이름이다 — 선체를 구획으로 나눠 한 구획에
물이 차도 배 전체가 가라앉지 않게 한다. 소프트웨어에서는 **의존성별로
자원(스레드·동시 실행 수·커넥션)을 분리·할당해, 한 의존성의 장애가
소모할 수 있는 자원의 상한을 구조적으로 보장**하는 패턴이다.

```java
// Before: 모든 외부 호출이 톰캣 공용 워커 스레드에서 실행
// → 추천이 느려지면 워커 200개 전부가 추천 대기에 점유될 수 있다
public MainPageResponse getMainPage(Long userId) {
    List<Webtoon> rec = recommendClient.recommend(userId); // 공용 스레드 점유
    ...
}

// After: 추천 호출에 bulkhead — 동시 실행 상한을 20으로 제한
@Bulkhead(name = "recommend", fallbackMethod = "recommendFallback")
public List<Webtoon> getRecommendations(Long userId) {
    return recommendClient.recommend(userId);
}
```

```yaml
resilience4j.bulkhead:
  instances:
    recommend:
      maxConcurrentCalls: 20    # 추천 호출의 동시 실행 상한
      maxWaitDuration: 0        # 자리가 없으면 대기하지 않고 즉시 거절 → fallback
```

효과: 추천이 아무리 느려져도 추천 대기에 붙잡히는 스레드는 **최대
20개**다. 나머지 180개 워커는 회차 조회·결제를 계속 처리한다 —
장애가 "추천 섹션 저하"로 **국소화**되고, 넘친 추천 요청은 즉시
거절되어 fallback(인기순 대체 —
15-graceful-degradation-design.md)으로 빠진다.

### 두 가지 구현 방식 (가산점 포인트)

- **세마포어 방식**: 호출자의 스레드에서 그대로 실행하되 동시 진입
  수만 카운트로 제한한다. 오버헤드가 거의 없고 단순하지만, 진입한
  스레드 자체는 여전히 호출자(톰캣 워커)의 것이다.
- **전용 스레드 풀 방식**: 의존성별 별도 스레드 풀에서 호출을 실행하고
  호출자는 결과만 기다린다. 격리가 더 강하고(타임아웃 시 호출자 스레드는
  즉시 복귀) 풀 단위 모니터링이 되지만, 스레드 문맥 전환과 풀 관리
  비용이 든다.

같은 원리의 bulkhead는 스레드 밖에도 있다: **커넥션 풀 분리**(배치용과
온라인용 DB 풀 분리 — 배치가 커넥션을 다 먹어도 온라인은 생존),
**인스턴스 그룹 분리**(핵심 API 전용 서버군과 비핵심 API 서버군의
물리적 분리), **큐 분리**(중요 작업과 대량 작업의 큐를 나눠 대량
작업의 적체가 중요 작업을 막지 않게). "격벽은 스레드 풀 기법이
아니라 어느 계층에든 적용하는 자원 분리 원칙"이라고 말하면 시야가
넓어 보인다.

## 3. 방어 계층의 조립 — 어떤 벽이 어떤 단계를 막는가

각 방어 수단은 전파 경로의 **서로 다른 단계**를 자른다. 하나로는
안 되고 겹겹이 세우는 이유가 이것이다(심층 방어).

| 방어 계층 | 자르는 단계 | 한계(다음 벽이 필요한 이유) |
|---|---|---|
| 타임아웃 | 개별 대기 시간의 상한 | 동시 점유 "개수"는 제한 못 함 |
| 재시도 제한(backoff+jitter, budget) | 실패 후의 부하 증폭 | 원 트래픽 자체의 대기·점유는 남음 |
| 서킷 브레이커 | 지속 장애 국면의 호출 자체 | 열리기까지 통계 창 동안은 무방비 |
| bulkhead | 의존성당 자원 점유의 상한 | 거절된 요청의 사용자 경험은 별도 |
| load shedding / degradation | 그래도 남는 과부하·기능 공백 | — (최후의 흡수층) |

본문으로 풀면:

- **타임아웃**(10-timeout-layers-and-budget.md)은 스레드 인질극의
  1차 방어선이지만, "3초 타임아웃"이어도 초당 100건이 유입되면 동시
  점유는 300개에 이른다 — **시간의 상한이지 개수의 상한이 아니다**.
- **재시도 설계**(11-retry-storm-backoff-jitter.md)는 실패가 부하를
  곱하는 되먹임을 끊는다.
- **서킷 브레이커**(09-circuit-breaker-state-transition-tuning.md)는
  지속 장애를 감지해 호출을 통째로 차단하지만, 실패율 통계가 쌓여
  열리기까지의 **시간 창** 동안, 그리고 통계 조건이 안 맞는 애매한
  저하(실패율은 낮은데 느린) 국면에는 스레드가 계속 소모될 수 있다.
- **bulkhead**는 위의 벽들이 전부 뚫리거나 늦더라도 "이 의존성이
  가져갈 수 있는 자원은 최대 N"이라는 상한을 **구조로** 보장한다.
  감지·판단이 필요 없는 벽이라는 점이 다른 계층과의 결정적 차이다.
- 마지막으로, 막지 못한 피해는 **load shedding**(과부하 시 우선순위
  낮은 요청 거절, 21-load-shedding-priority-and-location.md)과
  **graceful degradation**(거절·차단된 기능의 대체 동작)이 흡수한다.

## 4. 꼬리질문 대비 포인트

### "완전히 죽은 서비스보다 느린 서비스가 더 위험한 이유는?"

죽은 서비스는 connection refused로 즉시 실패해 호출자의 스레드가 바로
회수된다 — 빠른 실패는 전파력이 약하다. 느린 서비스는 연결을 받아주고
응답만 늦게 줘서 호출자의 스레드를 대기 상태로 붙잡는다. 연쇄 장애의
연료는 에러가 아니라 이 붙잡힌 대기이고, 그래서 서킷 브레이커도
실패율과 별개로 느린 호출 비율(slow call rate)을 따로 집계해 열 수
있게 되어 있다.

### "타임아웃과 서킷이 이미 있는데 bulkhead가 왜 또 필요한가요?" (시니어 변별 포인트)

둘 다 구멍이 있기 때문이다. 타임아웃은 개별 대기의 **시간** 상한일 뿐
동시 점유 **개수**를 제한하지 못한다 — 3초 타임아웃에 초당 100건이면
동시 300 스레드가 점유된다(L = λW). 서킷은 실패율/느린 호출 통계가
임계치를 넘어야 열리므로 그때까지의 시간 창 동안 무방비이고, 통계
조건에 안 걸리는 애매한 저하에서는 안 열릴 수 있다. bulkhead는 감지나
통계 판단 없이 "이 의존성은 최대 N개"라는 상한을 구조적으로 보장하는,
**가정이 전부 틀렸을 때를 위한 벽**이다. 심층 방어에서 각 벽은 서로의
실패 모드를 보완한다고 답하면 좋다.

### "bulkhead의 동시 실행 상한 N은 어떻게 정하나요?"

두 방향의 제약 사이에서 정한다. 아래로는 그 의존성의 정상 트래픽이
통과할 수 있어야 한다 — Little's Law로 필요 동시성을 계산한다(호출
λ건/초 × 정상 p99 W초 = 평시 점유 L, 여기에 여유분). 위로는 전체 풀
대비 "이 의존성이 최악에 가져가도 되는 비율"이 상한이다(워커 200개
중 비핵심 추천에 10%인 20개까지). 즉 정상 부하의 관측치와 기능
중요도(폭발 반경 허용치)의 함수이지 감으로 정하는 값이 아니다.

### "연쇄 장애의 시작을 조기에 감지하려면 어떤 지표를 봐야 하나요?"

에러율은 후행 지표다 — 스레드가 고갈된 뒤에야 에러가 난다. 선행
지표는 **점유와 대기**다: 스레드 풀 활성 스레드 수·큐 대기 길이,
커넥션 풀 대기 시간(HikariCP pending), 다운스트림별 응답시간 p99와
타임아웃 발생률, 서킷 상태와 bulkhead 거절 카운트. "다운스트림별"
분해가 핵심인데, 전체 평균에 묻히기 전에 특정 의존성의 p99 상승을
잡아야 전파 전에 개입할 수 있기 때문이다.

### "원인 서비스가 복구됐는데도 시스템이 정상으로 안 돌아오는 이유는?" (가산점 포인트)

장애가 스스로를 유지하는 상태(metastable failure)에 빠졌기 때문이다.
원인이 제거돼도 (1) 각 계층에 쌓인 대기 큐와 밀린 재시도가 복구
직후의 서버를 다시 과부하로 밀어 넣고, (2) 재기동한 인스턴스는 캐시가
비어 있어 평시보다 처리 비용이 높으며(cold cache), (3) 클라이언트의
적체된 새로고침이 유입 자체를 키워 놓았다. 그래서 대형 장애의 복구는
"원인 제거"가 아니라 **부하를 일부 차단(shedding)한 상태에서 서서히
트래픽을 복원**하는 절차가 필요하다 — 서킷의 half-open이 소량 탐침부터
여는 것과 같은 원리다.

## 한 줄 요약

cascading failure는 느린 다운스트림을 기다리는 대기가 공유 스레드
풀을 고갈시켜 무관한 기능까지 마비시키고, 같은 패턴이 상류로 반복되며
재시도 증폭·헬스체크 오작동으로 가속되는 전파 현상이다 — 방어는
타임아웃(대기 시간 상한) → 재시도 제한(증폭 차단) → 서킷(지속 장애
차단) → bulkhead(의존성별 자원 점유 상한으로 폭발 반경 국소화) →
shedding/degradation(잔여 피해 흡수)을 겹겹이 세우는 것이고, 그중
bulkhead는 감지·통계 없이 구조로 상한을 보장하는 마지막 격벽이다.
