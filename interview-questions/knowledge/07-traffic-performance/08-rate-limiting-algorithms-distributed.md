# Rate Limiting 알고리즘과 분산 구현 — 로컬 카운트의 합은 전체 한도가 아니다

> 핵심 관전 포인트: **Rate limiting은 호출자별로 "단위 시간당 허용 요청 수"라는 계약을 강제하는 유입 제어다. 평상시에도 항상 켜져 있고, 한도는 사전에 정해진 값이며, 대상은 호출자별이다 — 이 셋이 load shedding·백프레셔와 갈리는 지점이다. 알고리즘은 "짧은 몰아치기를 허용할 것인가"라는 정책 질문으로 갈린다: token bucket은 장기 평균 속도를 충전률로 제한하면서 통의 크기만큼 순간 버스트를 허용하고, sliding window는 버스트 없이 구간 총량을 일정하게 누른다. Fixed window는 가장 단순하지만 구간이 리셋되는 경계에서 한도의 정확히 2배가 뚫리므로 실무에서 단독으로 쓰지 않는다. 분산 환경의 본체는 세 가지 문제다 — ① 서버별 로컬 카운트의 합은 전체 한도와 같아지지 않는다(나눠 주면 남기면서 거절하고, 넉넉히 주면 서버 대수만큼 뚫린다), ② 카운터를 Redis로 중앙화해도 "읽고 나서 쓰는" 두 단계 사이에 다른 요청이 끼어들어 한도를 넘긴다 — `INCR`의 반환값으로 판정하거나 Lua 스크립트로 판정과 갱신을 한 덩어리로 묶어야 한다, ③ 요청마다 원격 왕복이 붙고 Redis가 단일 장애점이 되므로 "얼마나 정확해야 하는가"를 먼저 정하고 동기 중앙 카운터와 로컬 근사 중에서 고른다. 그리고 429는 던지는 것으로 끝이 아니다 — `Retry-After`와 남은 한도를 함께 내려야 거절이 재시도 폭풍으로 되돌아오지 않는다.**

---

## 0. 질문 + 의도

**질문**: "Rate limiting 알고리즘(token bucket, sliding window)을 비교해주세요. 분산 환경에서는 어떻게 구현하나요?"

**출제 의도**: 알고리즘 비교보다, 분산 환경에서 "서버별 로컬 카운트의 합이 전체 한도를 넘는" 문제를 인지하는지가 핵심이다. 단일 서버에서 동작하던 지식을 분산으로 확장할 때 무엇이 깨지는지를 보는 사고 실험 — 정합성(정확한 한도)과 성능(요청마다 원격 호출) 사이의 트레이드오프를 설계로 다룰 수 있는지 드러난다.

## 1. Rate limiting이 지키는 것 — 계약된 유입 속도

### 1-1. 전제 지식 — "유입을 제어한다"는 장치는 셋이고, 서로 다른 질문에 답한다

이 장에는 이름이 다른데 하는 일이 비슷해 보이는 장치가 셋 있다. Rate limiting, load shedding, 백프레셔다. 셋 다 "들어오는 요청을 그대로 다 받지 않는다"는 점이 같아서 자주 뒤섞이는데, 실은 **서로 다른 질문에 답하는 별개의 계층**이다. 이 문서를 읽는 동안 계속 대조가 되므로 먼저 갈라 두자.

**Rate limiting은 계약을 지키는 것이다.** "API 키당 초당 100회"라는 값을 미리 정해 두고, 시스템이 한가하든 붐비든 그 값을 집행한다. 판단 기준은 사전에 정해진 숫자이고, 대상은 호출자별(API 키·사용자 ID·IP)이다.

**Load shedding은 과부하 상황에서만 발동해 일부를 버리는 것이다.** 판단 기준이 사전 값이 아니라 **실시간 부하 지표**(큐 길이, in-flight 요청 수, 응답시간)이고, 대상은 호출자가 아니라 **우선순위가 낮은 요청**이다. 평상시에는 아무 요청도 버리지 않는다. (21번 문서)

**백프레셔는 버리거나 거절하는 대신 상류의 속도 자체를 늦추는 것이다.** 하류가 처리할 수 있는 속도를 상류에 되전달해 유입 속도를 하류의 처리 속도에 맞춘다. 거절이 아니라 감속이 기본 동작이라는 점이 앞의 둘과 다르다. (16번 문서)

| | 언제 켜지나 | 무엇을 기준으로 판단하나 | 무엇을 대상으로 하나 | 초과분을 어떻게 하나 |
|---|---|---|---|---|
| Rate limiting | 항상 (평상시에도) | 사전에 정해진 한도 | 호출자별 | 거절 (429) |
| Load shedding | 과부하일 때만 | 실시간 부하 지표 | 우선순위가 낮은 요청 | 거절 (503) |
| 백프레셔 | 항상 (경계마다) | 하류의 실제 처리 속도 | 상류의 유입 속도 자체 | 늦춤 (유계 큐가 차면 거절) |

세 장치는 대체재가 아니라 **보완재**다. 모든 클라이언트가 각자 계약을 완벽히 지켜도 클라이언트 수가 늘면 합계는 용량을 넘을 수 있으므로 load shedding이 따로 필요하고, 경계마다 유계 큐를 두는 백프레셔가 없으면 두 장치가 판정하기 전에 큐가 먼저 터진다.

### 1-2. 무엇을 지키는가 — 서버 자원만이 아니라 클라이언트 간 공정성

Rate limiting이 보호하는 것을 "서버 자원"이라고만 답하면 절반이다. 서버 자원 보호는 load shedding이 더 직접적으로 하는 일이고, rate limiting이 고유하게 하는 일은 **한 호출자의 폭주가 다른 호출자의 몫을 잠식하지 못하게 막는 것**이다.

구체적으로 무엇을 막는지 보면 분명해진다. 클라이언트 한 곳의 버그 루프(재시도 로직을 잘못 짜서 초당 수천 건을 쏘는), 악의적 크롤링, 잘못 설정된 배치가 흔한 범인이다. 이때 서버 전체 용량에는 여유가 있어도 그 한 클라이언트가 커넥션 풀이나 특정 테이블의 락을 독점하면 다른 클라이언트는 느려진다. 한도를 호출자별로 걸면 폭주의 영향이 그 호출자 안에 갇힌다.

비유하자면 놀이공원의 "1인당 하루 입장 1회" 규칙이다. 공원이 한가하든 붐비든 규칙은 항상 적용된다. 한 사람이 하루에 스무 번 들어와 자리를 차지하는 것을 막는 규칙이지, 공원이 꽉 찼을 때 입장을 통제하는 규칙이 아니다. 후자는 load shedding이 하는 일이다.

### 1-3. 한도를 넘긴 요청에 무엇을 돌려주는가 — 429는 던지는 것으로 끝이 아니다

한도를 넘긴 요청에는 **HTTP 429 (Too Many Requests)** 를 반환한다. 그런데 상태 코드만 던지면 설계가 미완성이다. 클라이언트 입장에서 429는 "지금은 안 된다"까지만 알려 주고 **"언제 다시 오면 되는지"를 알려 주지 않기 때문**이다. 알 수 없으면 클라이언트가 할 수 있는 유일한 행동은 즉시 다시 시도하는 것이고, 그러면 거절 응답 자체가 새로운 부하가 된다.

그래서 429에는 최소한 다음 정보가 함께 실려야 한다.

**`Retry-After`** 는 "이 시각(또는 이만큼 뒤) 이후에 다시 오라"를 알려 주는 표준 응답 헤더다. 값은 초 단위 정수(`Retry-After: 5`) 또는 HTTP 날짜 형식 둘 다 쓸 수 있다. 이 헤더가 있으면 클라이언트는 무의미한 재시도를 멈추고 정확히 필요한 만큼만 기다린다.

**`X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset`** 은 각각 "당신의 한도", "지금 남은 여유", "카운터가 리셋되는 시각"을 알려 준다. 표준으로 확정된 헤더가 아니라 사실상의 관행(GitHub·Twitter 등 대형 API가 쓰는 형태)이므로 이름은 조직마다 조금씩 다르다. 중요한 것은 이름이 아니라 **성공 응답에도 함께 내린다**는 점이다. 429가 난 뒤에야 알려 주면 클라이언트는 벽에 부딪히고 나서야 벽의 위치를 알게 된다. 매 응답에 남은 여유를 실어 주면 클라이언트가 벽에 닿기 전에 스스로 속도를 줄일 수 있다.

```java
// 429를 던지는 지점 — 상태 코드만 던지지 않고 "언제, 얼마나"를 함께 내린다
@Component
public class RateLimitFilter extends OncePerRequestFilter {

    private final RateLimiter limiter;   // 3절에서 만드는 Redis 기반 리미터

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws IOException, ServletException {
        String key = resolveKey(req);        // API 키 > 사용자 ID > IP 순으로 (4절 참고)
        Decision d = limiter.tryConsume(key);

        // 한도와 남은 여유는 통과했을 때도 내린다. 그래야 클라이언트가
        // 벽에 부딪히기 전에 스스로 속도를 줄일 수 있다.
        res.setHeader("X-RateLimit-Limit", String.valueOf(d.limit()));
        res.setHeader("X-RateLimit-Remaining", String.valueOf(d.remaining()));
        res.setHeader("X-RateLimit-Reset", String.valueOf(d.resetEpochSeconds()));

        if (!d.allowed()) {
            // Retry-After가 없으면 클라이언트가 할 수 있는 일은 즉시 재시도뿐이고,
            // 그러면 거절 응답이 그대로 새 부하가 된다. 이 한 줄이 그 되먹임을 끊는다.
            res.setHeader("Retry-After", String.valueOf(d.retryAfterSeconds()));
            res.setStatus(429);
            res.setContentType("application/json");
            res.getWriter().write("{\"error\":\"rate_limit_exceeded\"}");
            return;
        }
        chain.doFilter(req, res);
    }
}
```

`Retry-After`를 계산할 수 있어야 한다는 요구가 알고리즘 선택에도 영향을 준다. Fixed window라면 "현재 구간이 끝나는 시각까지"로 간단히 나오지만, token bucket이라면 "토큰 1개가 충전될 때까지 남은 시간"을 충전률로 계산해야 한다. 뒤에서 알고리즘을 볼 때 이 값을 뽑을 수 있는지도 같이 보자.

## 2. 알고리즘 비교 — 버스트를 허용할 것인가

### 2-1. 전제 지식 — 이름에 나오는 "버킷", "윈도", "로그"가 각각 무엇인가

알고리즘 네 개의 이름에 낯선 단어가 셋 들어 있다. 이름이 곧 자료 구조를 가리키므로 먼저 정의하면 나머지가 쉽다.

**버킷(bucket, 통)** 은 허용량을 담아 두는 그릇이다. 통 안에 들어 있는 것을 **토큰**이라 부르고, 요청 하나가 토큰 하나를 꺼내 쓴다. 통이 비면 더 못 쓴다. "허용량을 미리 통에 담아 둔다"는 발상 때문에 통이라는 이름이 붙었다.

**윈도(window, 창)** 는 "카운트를 세는 시간 구간"이다. 분당 100회라면 윈도의 길이가 1분이다. 이 창을 시계에 맞춰 고정해 두면 **fixed window**, 지금 시각을 기준으로 계속 따라 움직이면 **sliding window**다. 창을 고정하느냐 미끄러뜨리느냐가 두 계열을 가르는 전부다.

**로그(log)** 는 여기서 "기록부"라는 뜻이다. 요청이 올 때마다 그 시각을 한 줄씩 적어 두는 목록이다. 애플리케이션 로그 파일과는 무관하고, "언제 요청이 왔는지를 전부 적어 놓은 대장"에 가깝다.

이 셋을 알면 네 알고리즘의 이름이 그대로 설명이 된다. Token bucket은 "토큰 통", fixed window counter는 "고정 구간의 카운터", sliding window log는 "미끄러지는 구간 + 요청 기록부", sliding window counter는 "미끄러지는 구간 + 카운터"다.

### 2-2. ① Token bucket — 평균은 제한, 순간 몰아치기는 허용

Token bucket에는 **통 하나**가 있다. 통에는 토큰이 **일정 속도로 계속 떨어지고**(예: 초당 10개), 요청 하나가 도착하면 토큰 하나를 꺼내 쓴다. 꺼낼 토큰이 없으면 그 요청은 거절된다. 통에는 **크기 상한**이 있어서(예: 100개) 그 이상은 담기지 않고 넘치는 토큰은 그냥 버려진다.

```text
                  초당 10개씩 토큰이 떨어진다 (충전률 rate = 10개/s)
                        │  │  │
                        v  v  v
                 ┌──────────────────┐
                 │  o o o o o o o   │  <- 통(bucket)
                 │  o o o o o o     │     최대 100개까지만 담긴다 (capacity = 100)
                 │  o o o           │     넘치는 토큰은 버려진다
                 └────────┬─────────┘
                          │  요청 1건 = 토큰 1개 소모
                          v
   요청 ──▶ [꺼낼 토큰이 있나?] ──있다──▶ 토큰 1개 빼고 통과
                     └──────────없다──▶ 429 거절
                                        (통에 토큰이 다시 떨어질 때까지)
```

이 구조의 핵심은 **조절 손잡이가 두 개**라는 것이다. 그리고 두 손잡이가 각각 무엇을 정하는지가 다르다.

```text
충전률 rate      = 장기 평균 속도의 상한       (초당 10건)
통의 크기 capacity = 한 번에 몰아칠 수 있는 양   (100건)

  - 100초 동안 요청이 없었다면 통에 쌓인 토큰
        = min(100, 0 + 100초 × 10개/s) = min(100, 1000) = 100개
    -> 통이 꽉 찼으므로 그 순간 100건을 한꺼번에 통과시킬 수 있다.
       즉 "통의 크기가 곧 허용 버스트 양"이다.

  - 빈 통이 다시 꽉 차기까지 걸리는 시간
        = 100개 ÷ 10개/s = 10초

  - 길이 T초의 임의 구간에서 통과할 수 있는 최대 건수
        = capacity + rate × T = 100 + 10T
      T = 60초 -> 100 + 10 × 60 = 700건
      (같은 1분에 sliding window로 600건을 걸면 정확히 600건에서 멈춘다.
       token bucket은 통에 미리 쌓아 둔 100건만큼 더 통과시킨다.)
```

마지막 줄이 token bucket의 성격을 가장 잘 드러낸다. **평균 속도는 충전률로 확실히 눌리지만, 어떤 구간을 잘라도 통 크기만큼의 초과는 항상 가능하다.** 이것이 결함이 아니라 의도다 — "평소엔 초당 10건, 화면 첫 로딩처럼 API를 여러 개 동시에 부르는 순간은 100건까지"라는 현실적인 정책이 두 손잡이로 그대로 표현된다.

구현상의 장점은 **상태가 아주 작다**는 것이다. 키당 값 두 개, 즉 (남은 토큰 수, 마지막으로 계산한 시각)만 있으면 된다. 그리고 토큰을 실제로 초당 10번 떨어뜨리는 타이머는 필요 없다. 요청이 올 때 **경과 시간만큼 게으르게(lazy) 계산**하면 결과가 같다.

```text
[게으른 충전 계산 — 요청이 올 때 한 번만 계산한다]

  Redis에 남아 있던 기록:  ts = 12:00:00.0,  tokens = 30
  지금 요청이 도착한 시각:  now = 12:00:02.5   (경과 2.5초)

  ① 경과 시간 = 12:00:02.5 − 12:00:00.0 = 2.5초
  ② 그 사이 충전됐어야 할 양 = 2.5초 × 10개/s = 25개
  ③ tokens = min(capacity, 30 + 25) = min(100, 55) = 55개
  ④ 요청 1건이 토큰 1개를 쓴다 -> 54개 남기고 통과
  ⑤ (tokens=54, ts=12:00:02.5) 로 갱신

  타이머 스레드도, 초당 10번의 쓰기도 필요 없다.
  "지난번 이후 흐른 시간"만 알면 결과가 동일하기 때문이다.
```

1-3에서 말한 `Retry-After`도 이 구조에서 바로 나온다. 토큰이 0개라면 1개가 충전되기까지 `1 ÷ rate` 초, 즉 초당 10개 충전이면 0.1초다. 소수점 이하는 헤더로 표현할 수 없으니 올림해 1초를 내려 주면 된다.

### 2-3. ② Fixed window counter — 가장 단순하지만 경계에서 정확히 2배가 뚫린다

Fixed window counter는 시계를 고정된 구간으로 자르고, 구간마다 카운터 하나만 증가시킨다. "매 분 100회"라면 10:00~10:01 구간의 카운터, 10:01~10:02 구간의 카운터를 따로 세고, 분이 바뀌면 새 카운터가 0에서 시작한다.

구현이 압도적으로 쉽다. Redis 키를 `ratelimit:{apiKey}:{yyyyMMddHHmm}`처럼 시각을 포함해 만들고 `INCR`만 하면 끝이며, 구간이 지나면 키가 TTL로 저절로 사라진다. 그런데 실무에서 이것을 단독으로 쓰지 않는 이유가 하나 있고, 그 하나가 결정적이다.

```text
한도: 분당 100회.  카운터는 분이 바뀌는 순간 0으로 리셋된다.

     구간 A [10:00:00 ~ 10:01:00)            구간 B [10:01:00 ~ 10:02:00)
  ├──────────────────────────────────┤   ├──────────────────────────────────┤
                          ↑↑↑↑↑↑↑         ↑↑↑↑↑↑↑
                   10:00:59.5에 100회    10:01:00.5에 100회
                   (구간 A 카운터 = 100)  (카운터가 0으로 리셋됐으므로 또 100)
                          │                   │
                          └───── 1초 ─────────┘

  실제로 통과한 양을 세어 보면:
    10:00:59.5 부터 10:01:00.5 까지 = 1초 사이에 100 + 100 = 200회

  의도한 한도는 "어느 60초 구간을 잘라도 100회 이하"였다.
  그런데 1초 구간에서 200회가 통과했다 = 한도의 2배.
```

왜 정확히 2배인가. 어떤 슬라이딩 구간을 잡아도 그 구간은 고정 구간 **두 개**에만 걸칠 수 있고, 각 고정 구간이 허용하는 최대는 한도만큼이다. 따라서 최악의 경우가 `한도 × 2`이고 그 이상은 되지 않는다. 반대로 말하면 **fixed window의 실질 한도는 명목 한도의 2배**이므로, 이 방식을 쓸 거라면 애초에 한도를 절반으로 잡아야 계약이 지켜진다. 그러면 평상시에는 필요 이상으로 조이는 셈이 된다.

이 경계 문제는 공격자가 노릴 수 있는 결함이기도 하다. 구간이 리셋되는 시각은 시계만 보면 알 수 있으므로, 리셋 직전과 직후에 몰아 보내는 것은 아무 기술도 필요 없다.

### 2-4. ③ Sliding window log — 정확하지만 비싸다

Sliding window log는 근사 없이 정확하게 계산하는 방식이다. 요청이 올 때마다 **그 시각을 기록부에 한 줄 적고**, 판정할 때는 "지금부터 과거 1분" 안에 있는 줄의 개수를 센다. 창이 지금 시각을 따라 계속 미끄러지므로 2-3의 경계 문제가 원천적으로 없다.

Redis라면 정렬된 집합(sorted set)이 자연스러운 자료 구조다. 점수(score)를 타임스탬프로 두고, 판정 전에 창 밖으로 나간 항목을 `ZREMRANGEBYSCORE`로 잘라내고 `ZCARD`로 개수를 센다.

```text
한도: 1분당 100회.  지금 시각 10:01:15.
유효 구간 = [10:00:15 ~ 10:01:15)

기록부(sorted set)에 남아 있는 항목:
  10:00:03  <- 창 밖. ZREMRANGEBYSCORE로 잘라낸다
  10:00:09  <- 창 밖. 잘라낸다
  10:00:41  ┐
  10:00:58  │
  10:01:02  ├─ 창 안. 이 개수를 센다 (ZCARD)
  10:01:11  ┘

창 안의 개수가 100 미만이면 지금 시각을 ZADD 하고 통과.
```

정확한 대가로 **키당 메모리가 요청 수만큼 늘어난다.** 이게 얼마나 부담인지 숫자로 보면 바로 드러난다. 한도가 "1분당 10,000회"인 API에서 한 키는 최대 10,000개의 항목을 들고 있어야 한다. 키가 API 키 100만 개라면 최악의 경우 항목 수는 `10,000 × 1,000,000 = 100억 개`다. 항목 하나가 몇 바이트인지 따질 필요도 없이 성립하지 않는 규모다.

그래서 sliding window log는 **한도가 작고 정확성이 중요한 곳**에 쓴다. 대표적인 것이 로그인 시도 제한("5분 안에 5회")이다. 키당 항목이 다섯 개뿐이므로 메모리가 문제되지 않고, 대신 한 번의 초과가 곧 보안 문제이므로 근사를 쓰면 안 된다.

### 2-5. ④ Sliding window counter — log의 근사, 실무 절충안

Sliding window counter는 log의 정확성과 fixed window의 저렴함 사이를 잇는다. 발상은 이렇다. **기록부를 통째로 들고 있지 않고, 고정 구간 카운터 두 개(이전 구간과 현재 구간)만 들고 있으면서, 슬라이딩 창이 이전 구간과 겹치는 비율만큼만 이전 카운트를 인정한다.**

먼저 창이 어떻게 겹치는지 그림으로 보자.

```text
한도: 1분당 100회.  윈도 길이 = 60초.
지금 시각 10:01:15  ->  현재 고정 구간(10:01:00~)에 15초 경과

지금부터 과거 60초를 되짚은 슬라이딩 창은 [10:00:15 ~ 10:01:15) 이다.

  이전 고정 구간                              현재 고정 구간
  10:00:00 ──────────────────── 10:01:00     10:01:00 ─── 10:01:15 (지금)
  ├────────────┬───────────────────────┤     ├─────────────────────┤
   겹치지 않음 │      겹치는 45초                  전부 겹침 (15초)
   (앞 15초)   │
            10:00:15  <- 슬라이딩 창의 왼쪽 끝

  이전 구간 중 겹치는 비율 = 45초 ÷ 60초 = 0.75

  추정 카운트 = 이전 구간 카운트 × 0.75 + 현재 구간 카운트
```

이제 실제 숫자로 한 단계씩 따라가 보자.

```text
[주어진 값]
  이전 구간(10:00:00~10:01:00) 카운트 = 80
  현재 구간(10:01:00~10:01:15) 카운트 = 20
  한도 = 100

① 현재 구간의 경과 비율 = 15초 ÷ 60초 = 0.25
② 이전 구간과 겹치는 비율 = 1 − 0.25 = 0.75
                          (= (60 − 15) ÷ 60 = 45 ÷ 60 = 0.75)
③ 이전 구간의 기여분 = 80 × 0.75 = 60
④ 추정 카운트 = 60 + 20 = 80
⑤ 80 < 100 이므로 통과. 남은 여유 = 100 − 80 = 20건
```

메모리는 카운터 두 개, 즉 fixed window와 같은 수준이다. 경계 버스트는 실용적으로 막힌다 — 2-3처럼 이전 구간에서 100회를 다 쓰고 구간이 바뀌자마자 몰아 보내려 해도, 이전 구간의 카운트가 비율만큼 그대로 따라오므로 즉시 막힌다. 그래서 실무의 기본 선택이 된다.

#### 이 근사는 언제, 어느 방향으로 틀리는가

이 계산에는 숨은 가정이 하나 있다. **"이전 구간 안에서 요청이 시간에 걸쳐 고르게 분포했다"** 는 가정이다. 80건을 0.75로 곱한다는 것은 "80건이 60초에 골고루 흩어져 있었으니 그중 75%가 겹치는 구간에 있을 것"이라고 본다는 뜻이다. 실제 분포가 한쪽에 몰려 있으면 틀린다. 양쪽 방향을 각각 숫자로 확인하자.

```text
[방향 1: 과소 추정 — 한도를 넘겨 통과시킨다]

이전 구간 카운트 = 100인데, 그 100건이 전부 10:00:50~10:01:00 (마지막 10초)에 몰려 있었다.

  추정 = 100 × 0.75 + 현재 구간 카운트 = 75 + C
        -> 추정이 한도 100에 닿을 때까지 통과하므로 C는 25까지 올라간다.

  그런데 진짜 [10:00:15 ~ 10:01:15) 안의 실제 요청 수는:
     이전 구간의 100건은 전부 10:00:50 이후 = 창 안에 있다 -> 100건
     현재 구간                                              ->  25건
     합계                                                    = 125건

  -> 1분 창에 125건이 통과했다. 한도 100의 25% 초과.
     원인: 이전 구간의 100건 중 창 안에 있는 것이 실제로는 100건인데
           0.75를 곱해 75건으로 과소 계산했다 (25건을 놓쳤다).
```

```text
[방향 2: 과대 추정 — 여유가 있는데 거절한다]

이전 구간 카운트 = 100인데, 그 100건이 전부 10:00:00~10:00:10 (첫 10초)에 몰려 있었다.

  진짜 [10:00:15 ~ 10:01:15) 안의 실제 요청 수:
     이전 구간의 100건은 전부 10:00:15 이전 = 창 밖이다 ->   0건
     현재 구간                                          ->   C건

  추정 = 75 + C  -> C가 25가 되는 순간 막힌다.
  실제로는 25건만 쓴 사용자가 한도 100 중 25에서 거절당한다.
```

정리하면 오차의 상한은 `이전 구간 카운트 × (1 − 겹치는 비율)`이고, 방향은 이전 구간의 요청이 창 안쪽에 몰려 있었는지(과소 추정) 창 밖쪽에 몰려 있었는지(과대 추정)에 따라 갈린다. 위 예에서는 `100 × 0.25 = 25건`이 그 상한이다.

이 오차를 어떻게 볼 것인가가 판단이다. 남용 방지 목적이라면 최악에도 25% 초과는 충분히 받아들일 만하다 — fixed window의 최악(한도의 2배, 즉 100% 초과)과 비교하면 훨씬 낫고, 메모리는 카운터 두 개로 끝난다(log는 한도가 100이면 항목을 100개 든다). 반면 과금이나 보안 한도라면 이 근사를 쓰지 않고 log 계열로 간다.

### 2-6. 비교 정리와 선택 기준

여기까지의 내용을 표로 압축하면 이렇다. 표는 이미 설명한 것을 되짚는 용도이고, 판단 근거는 표 아래의 한 문장이다.

| 알고리즘 | 버스트 | 메모리(키당) | 특징 |
|---|---|---|---|
| Token bucket | 통 크기만큼 **허용** | 값 2개 (토큰 수, 시각) | 평균/순간을 손잡이 두 개로 분리 제어 |
| Fixed window | 경계에서 정확히 2배 **뚫림** | 카운터 1개 | 가장 단순, 단독 사용 부적합 |
| Sliding window log | 없음 (정확) | 요청 수만큼 | 한도가 작고 정확해야 하는 곳에만 |
| Sliding window counter | 근사적으로 차단 (최악 오차 = 이전 카운트 × 미겹침 비율) | 카운터 2개 | 실무 절충안 |

선택 기준을 한 문장으로 세우면 이렇다. **"버스트가 우리 서비스에서 정당한 사용 패턴인가?"** 정당하면(첫 화면 로딩에서 API를 열 개 동시에 부르는 것처럼) token bucket을 쓰고 통 크기로 그 정당한 버스트만큼을 열어 준다. 총량을 일정하게 눌러야 하면(뒷단의 과금이 걸린 API, 외부에 제공하는 API) sliding window로 구간 총량을 강제한다.

### 2-7. leaky bucket — 거절이 아니라 지연 (가산점 포인트)

**Leaky bucket(새는 통)** 도 함께 언급할 수 있다. Token bucket과 이름이 비슷하지만 통에 담기는 것이 다르다. Token bucket의 통에는 **허용량(토큰)** 이 담기지만, leaky bucket의 통에는 **요청 자체**가 담긴다. 그리고 통 아래의 구멍에서 요청이 **일정 속도로 새어 나가며** 처리된다.

```text
[token bucket]                    [leaky bucket]
 통에 담기는 것: 토큰(허용량)        통에 담기는 것: 요청 그 자체
 토큰이 없으면 -> 즉시 거절          통이 넘치면   -> 거절
 통과한 요청은 곧바로 하류로         통과한 요청은 일정 속도로만 하류로
 -> 버스트가 하류에 그대로 전달됨     -> 하류에는 항상 일정 속도로 도달
```

목적이 "거절"보다 **"처리 속도의 평탄화"** 에 가깝다는 것이 차이다. 하류에 도달하는 속도가 항상 일정하므로, 하류가 순간 동시성에 약할 때 유용하다. 대가는 통에서 기다리는 시간, 즉 지연이다. Token bucket과는 수학적으로 쌍대 관계라 같은 정책을 양쪽 방식으로 표현할 수 있다.

## 3. 분산 환경 — 무엇이 깨지는가

여기가 이 질문의 본체다. 앞 절의 알고리즘은 모두 "카운터(또는 토큰 수)가 한 곳에 있다"는 전제 위에 서 있다. 서버가 여러 대가 되면 그 전제가 무너지고, 무너지는 방식이 세 가지다.

### 3-1. 문제 1: 로컬 카운트의 합은 전체 한도와 같아지지 않는다

각 서버가 자기 메모리에서 카운트하면 어떤 일이 생기는지 숫자로 따라가 보자. 전체 한도가 초당 1,000건이고 서버가 10대라고 하자. 가장 자연스러운 발상은 "그럼 서버당 100건으로 나눠 주자"다.

```text
전체 한도: 초당 1,000건.  서버 10대.  서버당 한도 = 1,000 ÷ 10 = 100건.
클라이언트가 정확히 초당 1,000건을 보낸다 (= 계약을 정확히 지키고 있다).

[실제로 흔한 상황: 분배가 고르지 않다]
  로드밸런서는 요청 단위가 아니라 커넥션 단위로 붙이고, 커넥션 수명도
  제각각이므로 순간 분배가 균등할 이유가 없다.

  서버 A       : 400건 도착 -> 100건 통과, 300건 거절
  서버 B       : 200건 도착 -> 100건 통과, 100건 거절
  서버 C ~ J   : 각 50건 도착 (8대 × 50 = 400건) -> 전부 통과 (50 < 100)
  (도착 합계 검산: 400 + 200 + 400 = 1,000건 = 클라이언트가 보낸 양)

  ① 통과한 양        = 100 + 100 + 400 = 600건
  ② 거절당한 양      = 300 + 100       = 400건
  ③ 안 쓰고 남은 여유 = 8대 × (100 − 50) = 400건

  -> 전체 한도 1,000건 중 400건이 고스란히 남았는데,
     사용자는 정확히 그 400건만큼을 거절당했다.
     한도를 지킨 것도 아니고(전체 여유를 못 쓰게 막았다),
     사용자에게 계약을 이행한 것도 아니다.
```

여기서 반대 방향으로도 생각해 봐야 한다. "거절이 아까우니 서버당 한도를 넉넉히 주자"는 발상은 더 나쁜 결과를 낸다.

```text
[반대 방향: 서버당 한도를 전체 한도와 같게 넉넉히 준 경우]
  서버당 한도 = 1,000건 (= 전체 한도)

  클라이언트가 초당 1,000건을 보내고 트래픽이 10대에 고르게 분산되면
    서버마다 100건씩 도착 -> 전부 통과 -> 합계 1,000건.  여기까지는 우연히 맞다.

  그런데 클라이언트가 초당 10,000건을 보내면
    서버마다 1,000건씩 도착 -> 각 서버가 모두 "내 한도 이내"라고 판정
    -> 10,000건 전부 통과 = 전체 한도 1,000건의 10배

  일반화하면 로컬 판정의 최악 통과량 = 서버 대수 × 서버당 한도.
  한도를 넉넉히 주는 만큼 리미터가 없는 것에 가까워진다.
```

두 방향을 합치면 결론이 나온다. **로컬 판정은 나눠 주면 남기면서 거절하고, 넉넉히 주면 서버 대수만큼 뚫린다.** 사이의 어떤 값을 골라도 두 오차가 동시에 존재하고, 분배 비율이 배포·스케일링·커넥션 재수립에 따라 계속 변하므로 값을 고정할 근거도 없다. 나눠 갖기는 근사조차 어렵다.

"그럼 같은 API 키를 항상 같은 서버로 보내면(sticky, 일관 해싱) 로컬 카운트가 맞지 않느냐"는 반문이 나올 수 있다. 원리적으로는 맞다. 그러나 대가가 셋 붙는다. ① 서버가 늘거나 줄 때 키의 목적지가 바뀌고, 그 순간 새 서버는 카운트를 0에서 시작하므로 한도가 리셋된다. ② 트래픽이 큰 키가 특정 서버에 고정되어 부하가 편중된다. ③ 로드밸런서의 분배 정책과 rate limiter의 정확성이 결합되어, LB 설정을 바꿀 때마다 리미터의 동작이 바뀐다.

그래서 결론은 **카운터를 공유 저장소(대표적으로 Redis)로 중앙화**해서 전 서버가 하나의 한도를 보게 하는 것이다.

### 3-2. 문제 2: 중앙화해도 남는 경쟁 조건 (check-then-act)

카운터를 Redis에 두었다고 문제가 끝나지 않는다. 코드를 그대로 옮기면 새로운 결함이 생긴다.

```java
// Before: 읽기와 쓰기가 두 명령으로 분리된 구현 — 경쟁 조건
Long count = redis.get(key);          // ① 현재 카운트 조회
if (count != null && count >= limit) {
    return reject();                  // ② 조회한 값으로 판정
}
redis.incr(key);                      // ③ 증가
// ①에서 읽은 값을 근거로 ②에서 판정하고 ③에서 반영한다.
// 세 단계가 별개의 왕복이므로 그 사이에 다른 서버가 끼어들 수 있다.
```

이 패턴을 **check-then-act**(확인한 뒤 행동)라고 부른다. 확인한 시점의 값과 행동하는 시점의 값이 다를 수 있다는 것이 결함의 본질이다. 타임라인으로 보면 어디서 어긋나는지 정확히 보인다.

```text
한도 100. 현재 카운터 = 99.  요청 두 건이 서버 A와 서버 B에 거의 동시에 도착했다.

 시각   서버 A                       서버 B                       Redis의 값
 ───────────────────────────────────────────────────────────────────────────
 t1    GET count -> 99                                                 99
 t2                                 GET count -> 99                    99
 t3    99 < 100 -> "통과" 판정                                          99
 t4                                 99 < 100 -> "통과" 판정             99
 t5    INCR -> 100                                                     100
 t6                                 INCR -> 101                        101

 결과: 한도 100인데 101건이 통과했다.
      t3과 t4에서 두 서버가 본 99는 둘 다 "판정 시점에는 이미 낡은 값"이었다.
      서버가 10대면 최악의 경우 한 번에 10건이 이렇게 새어 나갈 수 있다.
```

Redis는 명령 **하나**는 원자적으로 처리한다. 그러나 **여러 명령에 걸친 판정은 원자적이지 않다.** 그래서 해법의 방향은 하나다 — **판정과 갱신을 하나의 명령으로 합친다.**

가장 간단한 합치기는 판정의 근거를 "읽은 값"에서 **"`INCR`의 반환값"** 으로 바꾸는 것이다. `INCR`은 증가시킨 뒤의 값을 돌려주므로, 두 요청이 동시에 호출해도 각자 다른 숫자를 받는다.

```java
// After 1단계: 판정 근거를 INCR의 반환값으로 바꾼다 (fixed/sliding window counter)
Long count = redis.incr(key);   // 증가와 값 획득이 한 명령 = 원자적
if (count == 1L) {
    redis.expire(key, 60);      // 첫 증가일 때만 이 구간 카운터의 수명을 정한다
}
if (count > limit) {
    return reject();
}
// t5/t6의 두 요청은 각각 100과 101을 받는다.
// 같은 값을 두 번 받는 일이 원리적으로 없으므로 101번째는 반드시 거절된다.
```

원자적 연산이 왜 문제를 해결하는지 한 문장으로 짚자. **읽기와 쓰기가 하나의 명령으로 합쳐지면 그 사이에 다른 요청이 끼어들 수 있는 틈이 사라진다.** 3-1에서 본 문제가 "카운터가 여러 곳에 있다"는 문제였다면, 이것은 "한 곳에 있어도 보는 시점과 쓰는 시점이 다르다"는 문제이고, 해결 수단이 원자적 연산이다.

그런데 위 코드에도 아직 구멍이 하나 남아 있다. `INCR`과 `EXPIRE`가 **두 번의 왕복**이라는 점이다.

```text
 t1  INCR key -> 1        키가 새로 생성됐다. Redis의 INCR은 TTL을 설정하지 않는다.
 t2  ★ 여기서 프로세스가 죽거나 Redis 연결이 끊긴다 — EXPIRE를 못 보냈다
 t3  키는 TTL 없이 영구히 남는다
     -> 이 구간 카운터가 영원히 리셋되지 않는다
     -> 그 클라이언트는 한도를 넘긴 카운터를 짊어진 채 영구 차단된다
```

즉 두 명령으로 나뉘는 순간 다시 원자적이지 않아진다. 이것도 두 방향으로 풀 수 있다. 가벼운 쪽은 카운터를 만드는 명령 자체에 TTL을 실어 보내는 것이다(`SET key 0 EX 60 NX` — 키가 없을 때만 TTL과 함께 0으로 만들고, 이미 있으면 아무것도 하지 않는다. 이 명령 자체가 원자적이고 여러 번 실행해도 결과가 같다). 그다음 `INCR`을 부르면 TTL이 없는 키가 생길 수 없다.

근본적인 쪽은 **필요한 모든 단계를 Lua 스크립트 하나로 묶는 것**이다. Lua가 왜 원자적인지가 중요한데, 이유는 단순하다. **Redis는 명령을 단일 스레드로 하나씩 처리하고, `EVAL`로 들어온 스크립트를 그 자체로 하나의 명령처럼 취급해 끝까지 실행한 뒤에야 다음 클라이언트의 명령을 처리한다.** 그래서 스크립트 안의 여러 `redis.call` 사이에는 어떤 요청도 끼어들 수 없다.

Token bucket처럼 읽기·계산·쓰기가 여럿 필요한 알고리즘은 사실상 Lua가 유일한 답이다.

```java
// After 2단계: token bucket 전체를 Lua 스크립트 하나로 묶는다
// Redis가 이 스크립트를 하나의 명령처럼 단일 스레드에서 끝까지 실행하므로,
// 안쪽의 HMGET / 계산 / HMSET 사이에 다른 서버의 요청이 끼어들 수 없다.
String script = """
    local tokens_key = KEYS[1]
    local rate = tonumber(ARGV[1])      -- 초당 충전량 (2-2의 rate)
    local capacity = tonumber(ARGV[2])  -- 통의 크기 (2-2의 capacity = 허용 버스트)
    local now = tonumber(ARGV[3])       -- 호출자가 넘긴 현재 시각(초)

    local data = redis.call('HMGET', tokens_key, 'tokens', 'ts')
    -- 처음 보는 키라면 통이 꽉 찬 상태에서 시작한다.
    -- 그래야 "한동안 안 쓴 클라이언트는 버스트를 쓸 수 있다"는 정책과 일치한다.
    local tokens = tonumber(data[1]) or capacity
    local ts = tonumber(data[2]) or now

    -- 2-2의 게으른 충전. 타이머 없이 경과 시간만으로 같은 결과를 만든다.
    tokens = math.min(capacity, tokens + (now - ts) * rate)

    local allowed = tokens >= 1
    if allowed then tokens = tokens - 1 end

    redis.call('HMSET', tokens_key, 'tokens', tokens, 'ts', now)
    -- 유휴 키를 남겨 두면 키 수가 사용자 수만큼 무한히 누적된다.
    -- 통이 꽉 차는 데 걸리는 시간(capacity/rate)보다 넉넉히 잡으면
    -- 만료로 사라진 키를 "꽉 찬 통"으로 다시 시작해도 정책이 어긋나지 않는다.
    redis.call('EXPIRE', tokens_key, 60)
    return allowed and 1 or 0
    """;
```

스크립트에 `now`를 **호출자가 넘긴다**는 점을 눈여겨볼 만하다. 스크립트 안에서 Redis의 시각을 읽는 대신 애플리케이션의 시각을 넘기는 구현이 흔한데, 그러면 서버 간 시계 오차가 그대로 판정에 섞인다. 반대로 Redis의 시각을 쓰면 오차는 없지만 복제본에 스크립트를 재생할 때 결과가 달라질 수 있다는 별개의 제약이 붙는다. 어느 쪽이든 **시각의 출처를 하나로 통일하는 것**이 원칙이다.

### 3-3. 문제 3: 중앙화의 비용 — 정확성 vs 성능·가용성

중앙화로 정확성을 얻었지만 대가를 두 개 지불했다. 첫째, **모든 요청에 네트워크 왕복 하나가 추가된다.** 요청 경로에 붙는 지연이므로 p99 응답시간에 그대로 드러난다(1번 문서). 둘째, **Redis가 rate limiter 전체의 단일 장애점이 된다.** Redis가 흔들리면 정상 트래픽까지 판정을 받지 못한다.

그래서 실무 설계는 "얼마나 정확해야 하는가"를 먼저 정하고 그에 맞는 구조를 고른다. 선택지가 셋이다.

**동기 중앙 카운터.** 요청마다 Redis에 물어보고 답을 기다린다. 가장 정확하다. 초과 1건이 곧 비용이나 위험인 한도 — 과금 API, 로그인 시도 제한 같은 보안 한도 — 에 쓴다. 대가는 요청 경로의 원격 호출이다.

**로컬 카운터 + 주기적 동기화.** 각 서버가 자기 로컬 카운터로 즉시 판정하고, 짧은 주기(예: 수백 밀리초~수 초)로 중앙에 자기 소비량을 보고하면서 전체 소비량을 받아 와 로컬 한도를 재조정한다. 동기화 주기 동안의 오차, 즉 잠깐의 한도 초과를 허용하는 대신 **요청 경로에서 원격 호출을 완전히 뺀다.** 일반적인 남용 방지 목적이라면 이 정도 근사로 충분한 경우가 많다.

**게이트웨이 계층에서 일괄 처리.** 각 애플리케이션이 아니라 API 게이트웨이(nginx, Spring Cloud Gateway 등) 한 층에서 공통으로 적용한다. 정책이 한 곳에 모여 관리가 쉬워지고 애플리케이션 코드에서 리미팅 관심사가 빠진다. 다만 게이트웨이가 아는 정보는 경로·헤더·토큰 수준이므로, 도메인 지식이 필요한 한도(예: "이 사용자의 구독 등급에 따른 한도")는 애플리케이션 계층에 남는다. 실무에서는 두 층을 겹쳐 쓴다.

여기에 반드시 함께 정해야 하는 것이 하나 더 있다. **Redis 장애 시의 동작**이다 (가산점 포인트).

**fail open**은 판정을 못 하면 통과시키는 것이고, **fail closed**는 판정을 못 하면 거절하는 것이다. 어느 쪽이 맞는지는 이 리미터가 무엇을 지키고 있느냐로 갈린다.

```text
남용 방지 목적의 리미터  -> fail open
   비교할 손실: (한도가 잠깐 안 걸려 초과 통과) vs (전 사용자에게 서비스 거절)
   후자가 압도적으로 크다. 리미터가 서비스를 죽이는 원인이 되면 안 된다.

보안 한도 (비밀번호 시도 제한 등)  -> fail closed
   비교할 손실: (로그인이 잠깐 안 됨) vs (무제한 비밀번호 대입 허용)
   후자가 훨씬 크다. 판정을 못 하면 막는 것이 맞다.
```

이 선택을 코드에 명시적으로 남기는 것까지가 설계다. 예외를 잡지 않아 500이 나가거나, 잡아서 통과시키면서 그 결정을 아무도 모르는 상태가 실무에서 가장 흔한 형태다.

```java
// 장애 시 동작을 "정하지 않은" 상태로 두지 않는다
try {
    return limiter.tryConsume(key);
} catch (RedisConnectionFailureException e) {
    // 이 리미터가 지키는 것이 남용 방지이므로 fail open을 택한다.
    // 다만 통과시켰다는 사실은 반드시 지표로 남긴다 —
    // "리미터가 사실상 꺼져 있었다"를 나중에 알 수 있어야 하기 때문이다.
    meterRegistry.counter("ratelimit.fail_open").increment();
    return Decision.allowedByFailOpen();
}
```

## 4. 꼬리질문 대비 포인트

### "429를 받은 클라이언트는 어떻게 동작해야 하나요?"

`Retry-After` 헤더(또는 `X-RateLimit-Reset` 류의 헤더)를 존중해 그 시각 이후에 재시도해야 한다. 이 헤더 없이 429만 주면 클라이언트가 즉시 재시도를 반복해 **거절 자체가 부하가 되는** 역설이 생긴다. 서버는 남은 한도(`X-RateLimit-Remaining`)를 함께 내려 클라이언트가 스스로 속도를 조절하게 돕는 것이 좋은 API 설계다(1-3).

한 걸음 더 나가면 두 가지를 덧붙일 수 있다. 첫째, `Retry-After`가 있어도 **여러 클라이언트가 같은 시각을 받으면 그 시각에 몰려 다시 벽을 친다.** 그래서 클라이언트는 헤더의 값에 무작위 지터(jitter)를 얹어 흩어져야 한다(11번 문서). 둘째, 429는 **재시도해도 되는 실패**이지만 무한 재시도는 안 된다 — 재시도 상한을 두고, 넘으면 사용자에게 실패를 알리거나 큐에 넣어 나중에 처리하는 폴백을 준비해야 한다.

### "Token bucket의 버스트 허용이 오히려 문제가 되는 경우는?"

통 크기만큼의 요청이 **한 순간에** 하류(DB, 외부 API)로 쏟아진다. 하류가 순간 동시성에 약하면(커넥션 풀이 작으면) 평균으로는 한도 이내인데 순간 스파이크로 하류가 흔들린다. 이 경우 통 크기를 줄이거나 sliding window로 총량을 평탄하게 누르는 게 맞다.

핵심 프레임은 **"평균 속도"와 "순간 동시성"이 다른 축이라는 것**이다. 2-2의 계산으로 말하면, 충전률 10개/s는 장기 평균을 눌러 주지만 통 크기 100은 "어느 순간이든 100건이 동시에 들어올 수 있다"를 뜻한다. 하류의 커넥션 풀이 25개라면 나머지 75건은 풀 앞에서 대기하고, 그 대기가 곧 지연이다. 이 대기가 바로 백프레셔가 다루는 문제이므로 16번 문서로 이어진다. 리미터의 통 크기는 **하류가 동시에 감당할 수 있는 양을 보고 정하는 값**이라는 관점을 보이면 좋다.

### "사용자별 한도는 어떤 키로 잡나요?"

인증된 트래픽은 사용자 ID나 API 키, 비인증 트래픽은 IP가 기본이다. 그런데 IP는 NAT이나 모바일 게이트웨이 뒤에서 다수 사용자가 공유될 수 있어 **한 사람의 폭주로 같은 IP의 무고한 사용자들이 함께 막히는** 과잉 차단 위험이 있다. 반대로 IP를 쓰지 않으면 인증 없이 때리는 트래픽을 전혀 제어할 수 없다.

그래서 실무에서는 계층화한다. **"IP당 넉넉한 한도(봇·스캐너 방어) + 사용자당 정밀 한도(공정성)"** 처럼 키가 다른 리미터를 겹쳐 쓰고, 요청은 두 리미터를 모두 통과해야 한다. 여기에 "엔드포인트별 한도"를 한 축 더 얹는 것도 흔하다 — 조회 API와 결제 API의 적정 한도가 같을 이유가 없기 때문이다.

키 설계에서 하나 더 짚을 것은 **키를 클라이언트가 정하게 두면 안 된다**는 점이다. 클라이언트가 보낸 헤더 값을 그대로 키로 쓰면 값을 바꿔 가며 한도를 무한히 얻을 수 있다. 키는 서버가 검증한 정보(인증 토큰에서 꺼낸 사용자 ID, 신뢰할 수 있는 프록시가 붙인 클라이언트 IP)에서만 만든다.

### "정확한 한도 보장과 낮은 지연 중 하나를 포기해야 한다면?" (시니어 변별 포인트)

목적에 따라 갈린다는 프레임으로 답한다. 남용 방지나 트래픽 평탄화가 목적이면 **근사를 택한다** — 로컬 판정 + 주기 동기화로 오차 몇 퍼센트를 허용하고, 요청 경로에서 원격 호출을 뺀다. 반면 요금 부과 한도나 보안 한도처럼 초과 1건이 곧 비용이나 위험이면 **동기 중앙 카운터**를 쓰고 지연을 받아들인다.

"rate limiter는 원래 방어선이지 회계 장부가 아니다"라는 관점을 세우면 답이 정리된다. 정확성 요구 수준을 먼저 묻고 그다음에 설계를 고르는 순서 자체가 시니어의 답이다.

여기에 숫자를 붙이면 더 좋다. 요청당 Redis 왕복이 1ms이고 평균 응답시간이 20ms인 API라면 5%의 지연 증가다. 응답시간이 3ms인 초저지연 API라면 33% 증가이므로 같은 1ms의 의미가 완전히 다르다. **같은 트레이드오프도 기준 응답시간에 따라 결론이 바뀐다**는 것까지 말할 수 있으면 계산으로 판단하는 사람으로 보인다.

### "Load shedding과는 뭐가 다른가요?"

1-1의 세 축으로 답한다. Rate limiting은 **호출자별 사전 계약**을 평상시에도 항상 집행하는 것이다(대상: 호출자별, 기준: 사전에 정해진 한도, 발동: 항상). Load shedding은 **시스템의 현재 과부하 상태**를 실시간 지표로 감지해 우선순위가 낮은 요청부터 버리는 자기 방어다(대상: 우선순위가 낮은 요청, 기준: 실시간 부하 지표, 발동: 과부하일 때만).

왜 둘 다 필요한지가 이 질문의 핵심이다. **모든 클라이언트가 각자의 계약을 완벽히 지켜도 전체 유입 합계가 처리 용량을 넘을 수 있다.** 클라이언트 100곳에 각각 초당 100건을 허용했다면 계약상 합계는 초당 10,000건이고, 우리 용량이 5,000건이라면 아무도 계약을 위반하지 않은 상태에서 과부하가 성립한다. Rate limiting은 이 상황을 감지하지도, 막지도 못한다. 그래서 shedding이 별도 계층으로 필요하다(21번 문서).

응답 코드가 다른 것도 여기서 나온다. 429는 "당신이 너무 많이 보냈다"(계약 위반), 503은 "지금 우리가 감당할 수 없다"(서버 과부하)라는 뜻이므로, 원인이 누구에게 있는지가 다르고 클라이언트의 대응도 달라져야 한다. **두 층은 대체재가 아니라 보완재**이고, 여기에 경계마다의 백프레셔(16번 문서)까지 셋을 계층으로 쌓는 것이 완성형이다.

## 한 줄 요약

Rate limiting은 호출자별 사전 계약을 평상시에도 집행하는 유입 제어이고(과부하 때만 발동하는 load shedding, 상류를 감속시키는 백프레셔와는 별개 계층), 알고리즘은 "버스트를 허용할 것인가"로 갈려 token bucket이 충전률과 통 크기라는 두 손잡이로 평균과 순간을 분리 제어하는 반면 sliding window는 구간 총량을 눌러 주며 fixed window는 경계에서 정확히 2배가 뚫린다 — 분산 환경에서는 로컬 카운트의 합이 전체 한도와 같아지지 않으므로(나눠 주면 남기면서 거절하고 넉넉히 주면 서버 대수만큼 뚫린다) 카운터를 중앙화하되, check-then-act 경쟁 조건은 `INCR`의 반환값이나 Lua 스크립트 같은 원자적 연산으로 막고, 중앙화의 지연·가용성 비용은 "얼마나 정확해야 하는가"에 대한 답과 fail open/closed 결정으로 절충하며, 429에는 `Retry-After`와 남은 한도를 실어 거절이 재시도 폭풍으로 되돌아오지 않게 하는 것까지가 설계의 완성이다.
