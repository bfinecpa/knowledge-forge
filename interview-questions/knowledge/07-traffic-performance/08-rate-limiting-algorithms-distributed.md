# Rate Limiting 알고리즘과 분산 구현 — 로컬 카운트의 합은 전체 한도가 아니다

> 핵심 관전 포인트: **Rate limiting은 클라이언트(또는 API)별로 "단위 시간당
> 허용 요청 수"라는 계약을 강제하는 유입 제어다. Token bucket은 평균
> 속도를 제한하되 버킷 용량만큼의 순간 버스트를 허용하고, sliding window는
> 버스트 없이 구간 내 총량을 일정하게 강제한다 — 어느 쪽이 맞는지는
> "짧은 몰아치기를 허용할 것인가"라는 정책 질문이다. 분산 환경의 핵심
> 문제는 서버마다 로컬로 카운트하면 그 합이 전체 한도를 초과한다는 것 —
> 그래서 카운터를 Redis 같은 공유 저장소로 중앙화하되, "읽고 나서 쓰는"
> 두 단계 사이의 경쟁 조건을 Lua 스크립트 등 원자적 연산으로 막아야 한다.**

---

## 0. 질문 + 의도

**질문**: "Rate limiting 알고리즘(token bucket, sliding window)을 비교해주세요. 분산 환경에서는 어떻게 구현하나요?"

**출제 의도**: 알고리즘 비교보다, 분산 환경에서 "서버별 로컬 카운트의
합이 전체 한도를 넘는" 문제를 인지하는지가 핵심이다. 단일 서버에서
동작하던 지식을 분산으로 확장할 때 무엇이 깨지는지를 보는 사고 실험 —
정합성(정확한 한도)과 성능(요청마다 원격 호출) 사이의 트레이드오프를
설계로 다룰 수 있는지 드러난다.

## 1. Rate limiting이 지키는 것 — "계약된 유입 속도"

Rate limiting은 **평시에도 항상 동작하는 사전 계약**이다.
"API 키당 초당 100회"처럼 클라이언트별 한도를 정해두고, 한 클라이언트의
폭주(버그 루프, 악의적 크롤링, 잘못 짠 재시도)가 다른 클라이언트의 몫을
잠식하지 못하게 막는다. 즉 보호 대상은 서버 자원이기도 하지만,
**클라이언트 간 공정성**이기도 하다.

- 비유: 놀이공원의 "1인당 하루 입장 1회" 규칙. 공원이 한가하든 붐비든
  규칙은 항상 적용된다. (반면 "공원이 꽉 차서 입장 자체를 막는 것"은
  load shedding — 과부하 시의 자기 방어로, 별개 주제다.)

한도를 넘긴 요청에는 **HTTP 429 (Too Many Requests)** 를 반환하고,
`Retry-After` 헤더로 언제 다시 오면 되는지 알려주는 것까지가 구현의
완성이다 (가산점 포인트).

## 2. 알고리즘 비교 — 버스트를 허용할 것인가

### ① Token bucket — "평균은 제한, 순간 몰아치기는 허용"

버킷에 토큰이 **일정 속도로 충전**되고(예: 초당 10개), 요청 하나가
토큰 하나를 소비한다. 토큰이 없으면 거절. 버킷에는 **용량 상한**이
있어(예: 100개), 한동안 요청이 없었다면 토큰이 쌓여 있다가
**한 번에 100개까지 버스트**를 받아줄 수 있다.

- 평균 속도(충전률)와 순간 허용량(버킷 용량)을 **따로 조절**할 수 있는
  것이 최대 장점 — "평소엔 초당 10, 페이지 첫 로딩처럼 몰리는 순간은
  100까지" 같은 현실적인 정책이 표현된다.
- 상태가 작다: 키당 (남은 토큰 수, 마지막 충전 시각) 두 값이면 된다.
  충전은 타이머로 돌리는 게 아니라 **요청이 올 때 경과 시간만큼
  게으르게(lazy) 계산**한다.

### ② Fixed window counter — 단순하지만 경계에서 뚫린다

"매 분 100회"처럼 시계를 고정 구간으로 자르고 구간별 카운터만 증가시킨다.
구현은 가장 쉽지만 **구간 경계 버스트**가 문제다:

```text
한도: 분당 100회
10:00:59에 100회 + 10:01:00에 100회
→ 2초 동안 200회 통과 (한도의 2배)
```

구간이 리셋되는 순간을 노리면 실질 한도의 최대 2배가 뚫린다.

### ③ Sliding window log — 정확하지만 비싸다

요청마다 **타임스탬프를 전부 기록**하고, "지금부터 과거 1분" 안의
개수를 센다. 경계 문제가 없고 정확하지만, 키당 요청 수만큼 메모리를
쓰므로 한도가 큰 API에서는 부담이 크다.

### ④ Sliding window counter — log의 근사, 실무 절충안

이전 구간 카운트와 현재 구간 카운트를 **시간 비율로 가중 합산**해
슬라이딩 구간을 근사한다.

```text
현재 시각이 10:01:15 (현재 구간의 25% 경과)라면
추정 카운트 = 이전 구간(10:00~10:01) 카운트 × 0.75
            + 현재 구간(10:01~) 카운트
```

"이전 구간의 요청이 구간 내에 고르게 분포했다"는 가정 위의 근사지만,
경계 버스트를 실용적으로 막으면서 메모리는 fixed window 수준(카운터
2개)이라 실무에서 널리 쓰인다.

### 비교 정리

| 알고리즘 | 버스트 | 메모리(키당) | 특징 |
|---|---|---|---|
| Token bucket | 버킷 용량만큼 **허용** | 값 2개 | 평균/순간 분리 제어 |
| Fixed window | 경계에서 최대 2배 **뚫림** | 카운터 1개 | 가장 단순 |
| Sliding window log | 없음 (정확) | 요청 수만큼 | 비싸다 |
| Sliding window counter | 근사적으로 차단 | 카운터 2개 | 실무 절충안 |

선택 기준을 한 문장으로: **"버스트가 우리 서비스에 정당한 사용
패턴인가?"** — 정당하면(첫 화면 로딩의 동시 API 호출 등) token bucket,
총량을 일정하게 눌러야 하면(과금 API, 외부 제공 API) sliding window.

(가산점 포인트) leaky bucket도 언급할 수 있다 — 유입은 큐에 담고
**유출을 일정 속도로 고정**하는 방식. 처리 속도의 평탄화가 목적이라
"거절"보다 "지연"에 가깝고, token bucket과 수학적으로 쌍대 관계다.

## 3. 분산 환경 — 무엇이 깨지는가

### 문제 1: 로컬 카운트의 합 > 전체 한도

서버가 10대일 때 각자 메모리에서 카운트하면, 클라이언트 한 명의 요청이
로드밸런서에 의해 10대에 분산되므로 **각 서버는 한도 미만이라고
판단하는데 합계는 한도의 10배**까지 통과한다.

- "그럼 서버당 한도를 1/10로 나누면?" — 트래픽이 서버에 **균등하게
  분배된다는 보장이 없다.** 특정 서버로 쏠리면 전체 한도가 남았는데도
  그 서버에서만 거절이 나오고(과소 허용), sticky session이 없으면
  분배 비율은 계속 변한다. 나눠 갖기는 근사조차 어렵다.

결론: **카운터를 공유 저장소(대표적으로 Redis)로 중앙화**해야
전 서버가 하나의 한도를 본다.

### 문제 2: 중앙화해도 남는 경쟁 조건 (check-then-act)

```java
// Before: 읽기와 쓰기가 분리된 구현 — 경쟁 조건
Long count = redis.get(key);          // ① 현재 카운트 조회
if (count != null && count >= limit) {
    return reject();
}
redis.incr(key);                      // ② 증가
// 문제: ①과 ② 사이에 다른 서버가 끼어들면
//       두 서버 모두 "한도 미만"을 보고 동시에 통과 → 한도 초과
```

Redis는 단일 명령은 원자적이지만, **여러 명령에 걸친 "확인 후 행동"은
원자적이지 않다.** 해법은 판정과 갱신을 한 덩어리로 묶는 것:

```java
// After: Lua 스크립트로 판정+갱신을 원자적으로 실행
// (Redis는 스크립트 하나를 통째로 원자 실행한다)
String script = """
    local tokens_key = KEYS[1]
    local rate = tonumber(ARGV[1])      -- 초당 충전량
    local capacity = tonumber(ARGV[2])  -- 버킷 용량
    local now = tonumber(ARGV[3])

    local data = redis.call('HMGET', tokens_key, 'tokens', 'ts')
    local tokens = tonumber(data[1]) or capacity
    local ts = tonumber(data[2]) or now

    -- 경과 시간만큼 게으른 충전 (용량 상한)
    tokens = math.min(capacity, tokens + (now - ts) * rate)

    local allowed = tokens >= 1
    if allowed then tokens = tokens - 1 end

    redis.call('HMSET', tokens_key, 'tokens', tokens, 'ts', now)
    redis.call('EXPIRE', tokens_key, 60)  -- 유휴 키 자동 정리
    return allowed and 1 or 0
    """;
// 서버가 몇 대든 이 스크립트를 호출하는 순간만큼은 직렬화된다
```

간단한 fixed/sliding window라면 `INCR` 후 반환값으로 판정하고
첫 증가일 때 `EXPIRE`를 거는 패턴으로도 원자성을 확보할 수 있다.

### 문제 3: 중앙화의 비용 — 정확성 vs 성능/가용성

요청마다 Redis를 왕복하면 **모든 요청에 네트워크 홉이 하나 추가**되고,
Redis가 rate limiter 전체의 단일 장애점이 된다. 그래서 실무 설계는
"얼마나 정확해야 하는가"를 두고 절충한다:

- **동기 중앙 카운터**: 정확하지만 요청마다 원격 호출. 과금·보안이
  걸린 한도(로그인 시도 제한 등)에 적합.
- **로컬 카운터 + 주기적 동기화**: 각 서버가 로컬에서 판정하고,
  짧은 주기로 합계를 중앙과 동기화해 로컬 한도를 재조정한다.
  잠깐의 한도 초과(오차)를 허용하는 대신 지연과 의존성을 줄인다.
  일반적인 남용 방지 목적이면 이 정도 근사로 충분한 경우가 많다.
- **게이트웨이 계층에서 일괄 처리**: 각 애플리케이션이 아니라
  API 게이트웨이(nginx, Spring Cloud Gateway 등)에서 공통으로
  적용하면 정책이 한 곳에 모이고 애플리케이션 코드가 깨끗해진다.

(가산점 포인트) Redis 장애 시의 동작을 미리 정해두는 것 —
**fail open**(제한 없이 통과)이냐 **fail closed**(전부 거절)냐는
rate limiter가 지키는 것이 무엇이냐에 따라 갈린다. 남용 방지가
목적이면 fail open(한도 초과 위험 < 전체 서비스 거절 손실),
보안 한도(비밀번호 시도 제한)면 fail closed가 맞다.

## 4. 꼬리질문 대비 포인트

### "429를 받은 클라이언트는 어떻게 동작해야 하나요?"

`Retry-After` 헤더(또는 `X-RateLimit-Reset` 류의 헤더)를 존중해
그 시각 이후에 재시도해야 한다. 이 헤더 없이 429만 주면 클라이언트가
즉시 재시도를 반복해 **거절 자체가 부하가 되는** 역설이 생긴다.
서버는 남은 한도(`X-RateLimit-Remaining`)를 함께 내려 클라이언트가
스스로 속도를 조절하게 돕는 것이 좋은 API 설계다.

### "Token bucket의 버스트 허용이 오히려 문제가 되는 경우는?"

버킷 용량만큼의 요청이 **한 순간에** 하류(DB, 외부 API)로 쏟아진다.
하류가 순간 동시성에 약하면(커넥션 풀이 작으면) 평균으로는 한도
이내인데 순간 스파이크로 하류가 흔들린다. 이 경우 버킷 용량을 줄이거나
sliding window로 총량을 평탄하게 누르는 게 맞다 — "평균 속도"와
"순간 동시성"은 다른 축이라는 걸 짚으면 좋다.

### "사용자별 한도는 어떤 키로 잡나요?"

인증된 트래픽은 사용자 ID/API 키, 비인증 트래픽은 IP가 기본이지만
IP는 NAT·모바일 게이트웨이 뒤에서 다수 사용자가 공유될 수 있어
과잉 차단 위험이 있다. 그래서 실무에서는 계층화한다 —
"IP당 넉넉한 한도(봇 방어) + 사용자당 정밀 한도(공정성)"처럼
키가 다른 리미터를 겹쳐 쓴다.

### "정확한 한도 보장과 낮은 지연 중 하나를 포기해야 한다면?" (시니어 변별 포인트)

목적에 따라 갈린다는 프레임으로 답한다. 남용 방지·트래픽 평탄화가
목적이면 **근사를 택한다** — 로컬 판정 + 주기 동기화로 오차 몇 %를
허용하고, 요청 경로에서 원격 호출을 뺀다. 반면 요금 부과 한도나
보안 한도처럼 초과 1건이 곧 비용/위험이면 **동기 중앙 카운터**를
쓰고 지연을 받아들인다. "rate limiter는 원래 방어선이지 회계 장부가
아니다"라는 관점 — 정확성 요구 수준을 먼저 묻고 설계를 고르는 태도가
시니어의 답이다.

### "Load shedding과는 뭐가 다른가요?"

Rate limiting은 **클라이언트별 사전 계약**을 평시에도 항상 집행하는
것이고(주체: 클라이언트 단위, 기준: 정해진 한도), load shedding은
**시스템의 현재 과부하 상태**를 보고 요청 중요도 순으로 버리는 자기
방어다(주체: 시스템 전체, 기준: 실시간 부하). 전자가 정상 작동해도
전체 유입 합계가 처리 용량을 넘을 수 있으므로 후자가 별도로 필요하다
— 두 층은 대체재가 아니라 보완재다.

## 한 줄 요약

Token bucket은 "평균 제한 + 버스트 허용", sliding window는 "구간 총량
강제"라는 서로 다른 정책이고, 분산 환경에서는 로컬 카운트의 합이 전체
한도를 넘는 문제 때문에 카운터를 중앙화하되 — check-then-act 경쟁
조건은 Lua 같은 원자적 연산으로, 중앙화의 지연·가용성 비용은 "얼마나
정확해야 하는가"에 대한 답으로 절충한다.
