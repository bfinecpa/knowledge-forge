# 부하 테스트 설계 — 목표 TPS 산정, 시나리오, 도구 선택

> 핵심 관전 포인트: **부하 테스트는 "돌려봤다"가 아니라 설계가 핵심이다.
> ① 목표는 실측 데이터에서 나온다 — 운영 피크 트래픽 × 성장 계수 ×
> 안전 마진으로 목표 TPS를 산정하고, "그 TPS에서 p99 ≤ N ms,
> 에러율 ≤ N%"라는 합격 기준(SLO)까지 함께 정의한다.
> ② 시나리오는 실제 트래픽을 닮아야 한다 — 단일 API 반복이 아니라
> 사용자 여정과 읽기/쓰기 비율을 반영한 트래픽 믹스.
> ③ 목적에 따라 유형을 고른다 — load(목표 검증) / stress(한계 탐색) /
> spike(급증 대응) / soak(장기 누수). 도구는 그다음 문제다.**

---

## 0. 질문 + 의도

**질문**: "부하 테스트는 어떻게 설계하나요? 목표 TPS 산정, 시나리오,
도구 경험을 말해주세요."

**출제 의도**: 목표 TPS를 어디서 얻는지(실측 피크 × 성장 계수),
시나리오가 실제 트래픽 패턴을 닮았는지를 통해 **형식적 부하 테스트와
의미 있는 부하 테스트를 구분해본 사람인지** 가린다. 숫자의 근거 없이
"만 TPS 넣어봤어요"로 답하는 사람은 테스트를 통과 의례로만 해본 것이다.

## 1. 목표 산정 — 목표 TPS는 계산의 결과물이다

가장 흔한 탈락 답변이 "일단 높은 부하를 넣어본다"이다.
목표가 없으면 결과를 해석할 수 없다 — 5,000 TPS가 나왔을 때 그것이
합격인지 불합격인지 판단할 기준이 없기 때문이다.

**목표 TPS 산정의 재료는 운영 실측 데이터다.**

```
목표 TPS = 실측 피크 TPS × 성장 계수 × 안전 마진

예) 최근 3개월 피크: 1,000 TPS (이벤트 시각 실측)
    내년 성장 전망:  × 2 (트래픽 2배 성장 계획)
    안전 마진:       × 1.5 (예측 오차·순간 스파이크 흡수)
    → 목표: 3,000 TPS
```

- **실측 피크**: 평균이 아니라 **피크**다. 하루 평균 100 TPS인
  서비스도 밤 11시 신작 공개 순간엔 10배가 될 수 있다.
  APM·액세스 로그에서 분 단위 최대치를 뽑는다.
- **신규 서비스라 실측이 없다면**: 예상 DAU → 피크 시간대 집중률 →
  사용자당 요청 수로 추정한다. 예: DAU 100만, 피크 1시간에 트래픽의
  20% 집중, 사용자당 요청 10건이면
  `100만 × 0.2 × 10 / 3600초 ≈ 556 TPS`. 추정임을 명시하고
  보수적으로(마진 크게) 잡는다.
- **TPS만으로는 목표가 아니다** (가산점 포인트): 합격 기준은
  반드시 응답시간·에러율과 한 세트다 —
  "3,000 TPS를 **p99 500ms 이하, 에러율 0.1% 이하로** 처리".
  TPS는 나오는데 p99가 10초라면 그건 처리가 아니라 적체다.

## 2. 시나리오 설계 — 실제 트래픽을 닮게 만든다

단일 API를 최대 속도로 두드리는 것은 벤치마크일 뿐, 시스템 검증이
아니다. 운영 트래픽의 특성을 시나리오에 옮겨야 한다.

- **트래픽 믹스**: 액세스 로그를 집계해 엔드포인트별 호출 비율을
  반영한다. 예: 목록 조회 50% : 상세 조회 30% : 댓글 작성 15% :
  결제 5%. **읽기만 있는 테스트는 쓰기가 만드는 락 경합·캐시 무효화를
  못 본다.**
- **사용자 여정(journey) 시나리오**: 로그인 → 목록 → 상세 → 구매처럼
  상태가 이어지는 흐름으로 만든다. 각 단계 사이에 **think time**
  (사용자가 화면을 읽는 시간)을 넣어야 동시 사용자 수와 TPS의 관계가
  현실과 비슷해진다.
- **데이터 다양성**: 같은 상품 ID만 반복 조회하면 캐시가 전부
  받아내서 DB는 놀게 된다. 파라미터를 운영 분포와 비슷하게 랜덤화한다.
- **부하 패턴(램프업)**: 0에서 목표까지 서서히 올리며(ramp-up)
  어느 지점부터 지표가 꺾이는지 관찰하고, 목표 부하를 일정 시간
  유지(sustain)한다.

**테스트 유형은 목적에 따라 4가지를 구분해 쓴다:**

| 유형 | 목적 |
|---|---|
| Load test | 목표 부하에서 SLO 충족 검증 (합격/불합격) |
| Stress test | 목표 너머로 올려 **한계점과 죽는 방식** 확인 |
| Spike test | 순간 급증(0→피크) 시 회복력 확인 |
| Soak test | 목표 부하를 수 시간 유지 — 누수·적체 등 장기 문제 |

stress test에서 봐야 할 것은 "몇 TPS까지 버티나"만이 아니라
**어떻게 무너지는가**다 — 에러를 빠르게 반환하며 버티는가(우아한 저하),
전체가 함께 침몰하는가. soak test는 짧은 테스트로는 절대 안 보이는
메모리 누수, 커넥션 누수, 디스크 적체를 잡는 유일한 방법이다.

## 3. 도구 — 선택 기준과 사용 예

도구는 시나리오를 표현할 수 있고 팀이 유지보수할 수 있으면 된다.
대표 도구와 특징:

- **k6**: JS로 시나리오 작성, 코드 리뷰·버전 관리·CI 통합이 쉬움.
  임계값(threshold)을 스크립트에 선언해 합격/불합격을 자동 판정.
- **nGrinder**: 네이버 오픈소스, 웹 콘솔 + 에이전트 분산 부하,
  Groovy 스크립트. 국내 실무에서 채택 사례 많음.
- **JMeter**: GUI 기반, 오래된 만큼 플러그인 생태계가 넓음.
- **Gatling / Locust**: 코드 기반(Scala·Kotlin / Python) 시나리오.

k6 예시 — 목표와 합격 기준이 스크립트에 명시된다:

```javascript
// load-test.js: "3,000 TPS급 부하에서 p99 500ms, 에러율 0.1%" 검증
export const options = {
  stages: [
    { duration: '5m', target: 3000 },  // 램프업: 서서히 목표까지
    { duration: '20m', target: 3000 }, // 유지: 목표 부하 지속
    { duration: '3m', target: 0 },     // 램프다운
  ],
  thresholds: {
    http_req_duration: ['p(99)<500'],  // 합격 기준: p99 < 500ms
    http_req_failed: ['rate<0.001'],   // 합격 기준: 에러율 < 0.1%
  },
};

export default function () {
  // 트래픽 믹스: 목록 50% / 상세 30% / 쓰기 20% 비율로 분기
  // 파라미터는 운영 분포를 닮은 데이터셋에서 랜덤 추출
}
```

## 4. 실행과 해석 — 테스트 중에 서버를 봐야 한다

부하 도구의 리포트(클라이언트 관점)만 보는 것은 반쪽 테스트다.
테스트 중 **서버 쪽 지표를 함께 관찰**해야 한다 — CPU, GC, 스레드풀,
커넥션 풀, DB 지표. 목적이 "합격 확인"이 아니라 **"어디가 먼저
포화되는지(병목 자원) 알아내는 것"**이기 때문이다.

- 부하를 올릴수록 TPS가 선형으로 오르다가 꺾이는 지점이
  **포화점(saturation point)** — 그 순간 어느 자원이 한계에 닿았는지가
  다음 개선 대상이다.
- 부하 발생기 자체가 병목이면(발생기 CPU 포화, 포트 고갈) 서버가
  아니라 도구의 한계를 측정한 것이다. 발생기 쪽 자원도 모니터링하고,
  필요하면 분산 에이전트로 부하를 나눈다.
- 테스트 환경은 운영과 최대한 유사해야 하고, 그 괴리가 결과의
  신뢰도를 결정한다 — 괴리 원인은 별도 주제(23번 문서)로 깊게 다룬다.

## 5. 꼬리질문 대비 포인트

### "동시 사용자(VU) 수와 TPS는 어떤 관계인가요?"

Little's Law로 연결된다: `동시 사용자 L = 처리량 λ × 사용자당 체류
시간 W`. 예를 들어 한 사용자가 요청→응답→think time까지 10초를
쓴다면, 3,000 TPS를 만들려면 약 30,000명의 동시 사용자가 필요하다.
think time을 0으로 두면 적은 VU로도 높은 TPS가 나오지만 커넥션 수 등
동시성 특성이 운영과 달라진다 — VU와 TPS 중 무엇을 고정할지는
검증하려는 대상에 따라 정한다.

### "부하 테스트는 어떤 환경에서 돌리나요?"

원칙은 **운영과 같은 스펙·같은 구성의 격리된 환경 + 운영 규모를 닮은
데이터**다. 비용 때문에 축소 환경을 쓴다면 결과를 선형 환산할 수
있다고 가정하면 안 된다(병목은 비선형으로 나타난다). 운영 환경에서
직접 하는 경우는 실제 트래픽이 적은 시간대 + 즉시 중단 가능한 안전장치
전제로 제한적으로 한다. 외부 연동(결제사 등)은 실제로 때릴 수 없으니
**운영 수준의 지연·에러율을 흉내 내는 stub**으로 대체한다.

### "soak test에서 실제로 어떤 문제가 잡히나요?"

짧은 테스트에선 절대 안 보이는 시간 축적형 문제들이다 — 메모리 누수로
힙이 계단식 증가하다 Full GC 연발, 커넥션/파일 핸들 누수, 로그·임시
파일로 디스크 고갈, 캐시 무한 증가, 큐의 서서히 진행되는 적체.
"20분 테스트는 통과했는데 운영에서 6시간 뒤 죽는" 문제의 예방선이다.

### "합격 기준(p99 500ms 같은)은 누가 어떻게 정하나요?" (시니어 변별 포인트)

기술팀이 임의로 정하는 숫자가 아니라 **비즈니스 요구에서 역산한 SLO**다.
사용자 이탈 데이터나 프론트 성능 예산에서 "이 API는 500ms를 넘으면
체감 저하"라는 요구를 얻고, 거기서 하위 구간(게이트웨이·앱·DB)의
지연 예산을 배분한다. 또한 기준은 평균이 아니라 백분위로 정한다 —
p50이 아니라 p99를 쓰는 이유는 "가장 나쁜 경험을 하는 1%의 사용자"가
대개 가장 요청을 많이 하는 헤비 유저이기 때문이다. 기준 없는 부하
테스트는 결과 해석이 불가능하다는 점을 먼저 짚고 시작하면 좋다.

### "부하 테스트를 CI/CD에 넣을 수 있나요?" (가산점 포인트)

k6 같은 코드 기반 도구는 threshold 판정이 exit code로 나오므로
파이프라인 게이트로 쓸 수 있다. 다만 풀스케일 테스트를 매 배포마다
돌리는 건 비용상 비현실적이라, 배포 파이프라인엔 축소된 스모크 성능
테스트(회귀 감지용)를 넣고, 풀스케일은 릴리스 전·이벤트 전에 정기
수행하는 식으로 층을 나눈다.

## 한 줄 요약

부하 테스트 설계란 **실측 피크에서 계산한 목표(TPS + p99 + 에러율)**를
세우고, **운영 트래픽을 닮은 시나리오**(믹스·think time·데이터 분포)로,
**목적에 맞는 유형**(load/stress/spike/soak)의 부하를 걸어, 서버 지표와
함께 **병목 자원을 찾아내는 일**이다 — 도구는 그 설계를 담는 그릇일
뿐이다.
