# Stateless 서버 설계 — 확장의 전제 조건, 세션은 서버 밖으로

> 핵심 관전 포인트: **Stateless 서버란 "상태가 없는 서버"가 아니라 "그 인스턴스에만 있고 다른 인스턴스는 모르는 상태"를 들고 있지 않는 서버다 — 그래서 DB나 Redis를 쓰는 것은 stateless를 깨지 않는다. 판정 기준은 하나다: "이 서버를 지금 꺼도 다른 서버가 같은 요청을 받아 같은 결과를 낼 수 있는가." 이 성질이 성립하면 서버 N대가 완전히 교체 가능한 부품이 되고, scale-out·scale-in·롤링 배포·장애 격리가 전부 안전해진다 — 즉 Stateless는 오토스케일링과 무중단 배포의 전제 조건이다. 세션 같은 상태는 없애는 게 아니라 서버 밖의 공유 저장소(Redis 등)나 클라이언트(토큰)로 옮긴다. 그리고 상태는 사라지지 않고 이동할 뿐이며, 그 이동은 공짜가 아니다 — Redis로 옮기면 요청당 네트워크 왕복과 직렬화 비용이 생기고 Redis가 새 단일 장애점이 되며, JWT로 옮기면 발급된 토큰을 만료 전에 무효화할 수 없어(로그아웃·강제 탈퇴·권한 회수가 즉시 반영되지 않는다) 결국 짧은 액세스 토큰 + 서버에 상태를 두는 리프레시 토큰이라는 절충으로 상태가 서버로 되돌아온다.**

---

## 0. 질문 + 의도

**질문**: "Stateless 서버 설계가 왜 확장에 유리한가요? 세션은 어떻게 처리하나요?"

**출제 의도**: 오토스케일링의 전제 조건을 이해하는지 본다. 로컬 상태(메모리 세션, 로컬 파일)가 하나라도 있으면 스케일 아웃이 곧 버그 발생기가 된다는 것을 **배포 전에** 아는 사람인지 확인하는 질문이다 — 운영에서 "서버 2대로 늘렸더니 로그인이 랜덤하게 풀려요"를 겪고 나서야 배우면 이미 늦다.

## 1. Stateless가 왜 확장에 유리한가 — "아무 서버나 골라도 된다"

### 1-1. 전제 지식 — 여기서 말하는 "상태"는 무엇인가

이 주제에서 가장 자주 나오는 오해부터 정리해야 한다. **"DB를 쓰면 stateful 아닌가요? 우리 서버는 회원 정보를 DB에 저장하는데요."**

아니다. 여기서 말하는 상태는 **"그 서버 인스턴스에만 있고 다른 인스턴스는 모르는 상태"**다. 판정 기준을 문장 하나로 만들면 이렇다.

> **이 서버를 지금 전원 코드 뽑듯 꺼도, 다른 서버가 같은 요청을 받아 같은 결과를 낼 수 있는가?**

DB에 저장된 회원 정보는 **모든 서버가 같은 DB를 보므로** 이 질문에 "예"라고 답한다. 1번 서버가 죽어도 2번 서버가 같은 DB를 조회해 같은 답을 낸다. 그래서 **공유 저장소의 상태는 stateless를 깨지 않는다.** Redis에 넣은 세션도 마찬가지다.

반대로 톰캣 기본 설정의 `HttpSession`에 담긴 로그인 정보는 **1번 서버의 JVM 힙 안에만** 있다. 2번 서버는 그런 게 있는지조차 모른다. 이것이 로컬 상태이고, stateless를 깨는 것이다.

정리하면 이렇게 갈린다.

| 어디에 있는 상태인가 | stateless를 깨는가 | 예 |
|---|---|---|
| 그 인스턴스의 메모리·로컬 디스크 | 깬다 | `HttpSession`, 인메모리 캐시, 로컬 업로드 파일 |
| 모든 인스턴스가 공유하는 저장소 | 깨지 않는다 | PostgreSQL, Redis, S3 |
| 요청 자체에 실려 온 것 | 깨지 않는다 | JWT, 요청 파라미터 |

그러니 정확한 표현은 **"애플리케이션 서버 계층이 stateless하다"**다. 시스템 전체가 상태 없이 굴러가는 것이 아니라, **계층 하나를 상태 없게 만들어 그 계층만 자유롭게 늘리고 줄이는 것**이 목표다. 이 구분이 4절의 "완전한 stateless가 가능한가"에 대한 답의 뼈대가 된다.

용어 하나 더 정리하고 넘어가자. "HTTP는 stateless 프로토콜"이라는 말과 여기서 말하는 stateless는 층위가 다르다. 앞의 것은 **프로토콜이 이전 요청을 기억하지 않는다**는 규약이고, 뒤의 것은 **서버 구현이 로컬에 상태를 두지 않는다**는 설계 선택이다. HTTP가 stateless여도 서버는 얼마든지 stateful하게 만들 수 있다 — `HttpSession`이 정확히 그런 장치다.

### 1-2. Stateful 서버가 만드는 세 가지 사고

로컬 상태가 하나 생기는 순간, 서버들은 서로 **대체 불가능한 존재**가 된다. 그러면 무엇이 깨지는지 하나씩 본다.

**(1) 로드밸런서가 자유롭게 분배할 수 없다.** 로그인은 1번 서버에서 했는데 다음 요청이 2번 서버로 가면 세션이 없으니 비로그인 사용자 취급을 받는다. 사용자 눈에는 **화면을 옮길 때마다 랜덤하게 로그아웃되는** 증상으로 나타난다. 서버 2대면 확률상 절반이 그렇다.

```
[서버 1대일 때 — 우연히 동작한다]
  요청 1 (로그인)  -> 서버 A  : 세션 생성, A의 메모리에 저장
  요청 2 (마이페이지) -> 서버 A : 세션 있음. 정상.

[서버 2대로 늘린 순간]
  요청 1 (로그인)  -> 서버 A  : 세션 생성, A의 메모리에 저장
  요청 2 (마이페이지) -> 서버 B : B의 메모리에는 그 세션이 없다 -> 로그인 화면으로 튕김
  요청 3 (다시 로그인) -> 서버 B : 세션 생성, B의 메모리에 저장
  요청 4            -> 서버 A  : A에는 방금 만든 세션이 없다 -> 또 튕김
```

이를 피하려고 같은 사용자를 같은 서버에 고정하는 것이 sticky session인데, 그러면 부하가 편중되고 아래 (2)(3)의 문제는 그대로 남는다(03번 문서 2-6).

**(2) scale-in이 사용자 강제 로그아웃이 된다.** 오토스케일링이 트래픽 감소를 보고 서버를 내리는 순간, 그 서버 메모리의 세션이 전부 증발한다. 즉 **"트래픽이 줄었으니 서버를 줄이자"는 정상적인 판단이 사용자 수백 명을 로그아웃시키는 사고가 된다.** 오토스케일링을 켜 놓고 로컬 세션을 쓰는 조합은, 시스템이 스스로 사고를 일으키도록 설정한 것과 같다.

**(3) 배포가 곧 장애가 된다.** 롤링 배포는 서버를 하나씩 내리고 새 버전을 올리는 방식이다. 로컬 세션이 있으면 **재시작할 때마다 그 서버의 세션이 날아간다.** 서버 3대를 순차 배포하면 배포 한 번에 전 사용자가 한 번씩 로그아웃되는 셈이다. "배포는 새벽에" 같은 관행이 이 지점에서 생긴다 — 기술 문제를 운영 시간으로 덮은 것이다.

### 1-3. Stateless 서버는 무엇이 다른가 — 비유

**Stateless 서버**는 요청 처리에 필요한 모든 상태를 **요청 자체(토큰, 파라미터)와 외부 저장소(DB, Redis)**에서 가져온다. 서버는 "계산만 하는 교체 가능한 부품"이 된다.

비유하면 이렇다. 상태가 있는 서버는 **단골 손님의 취향을 머릿속에 외우고 있는 특정 직원**이다. 그 직원이 쉬면 서비스 품질이 무너지고, 그 손님은 반드시 그 직원에게만 가야 한다. Stateless 서버는 **주문서(요청)와 고객 카드(외부 저장소)만 보고 일하는 직원**이다. 누가 응대해도 결과가 같고, 바쁘면 직원을 몇 명이든 더 투입할 수 있고, 한 명이 퇴근해도 손님은 눈치채지 못한다.

핵심은 **지식이 사람 머릿속에 있는가, 고객 카드에 있는가**다. 카드에 적혀 있으면 사람은 얼마든지 바꿔 끼울 수 있다.

### 1-4. 하나로 수렴한다 — 교체 가능성

Stateless가 확장에 유리한 이유는 결국 하나의 성질로 수렴한다. **"서버 N대가 완전히 동일하고 서로 교체 가능하다."**

이 성질이 성립하면 다음 네 가지가 전부 안전해진다.

- **scale-out** — 새 서버를 아무 준비 없이 LB 뒤에 꽂으면 즉시 일을 나눠 받는다.
- **scale-in** — 아무 서버나 골라 내려도 잃는 것이 없다.
- **롤링 배포** — 하나씩 내려 갈아 끼워도 사용자는 모른다.
- **장애 격리** — 이상한 서버를 그냥 죽이면 된다. 그 서버에만 있는 것이 없으므로 조사도 나중에 해도 된다.

거꾸로 읽는 것이 더 유용하다. **"아무 서버나 죽여도 되는가"에 예라고 답할 수 있으면 오토스케일링을 켤 수 있고, 아니라면 켜면 안 된다.** 이것이 이 질문의 출제 의도가 겨냥하는 판단이다.

## 2. 세션은 어떻게 처리하나 — 세 가지 선택지와 각각의 대가

세션(로그인 상태)은 없앨 수 없다. 사용자가 매 요청마다 아이디와 비밀번호를 보내는 것이 아니라면, "이 요청이 누구인지"를 어딘가에 기록해 둬야 한다. 그래서 문제는 **"어디에 둘 것인가"**다.

논리적으로 둘 곳은 세 군데뿐이다 — **서버 안, 서버 밖의 공유 저장소, 클라이언트.** 세 선택지가 정확히 이 셋에 대응한다.

여기서 반드시 붙잡아야 할 관점이 있다. **상태를 옮기는 것은 공짜가 아니다.** 옮기면 로컬 상태 문제는 사라지지만, 그 자리에 **새 문제가 들어선다.** "상태는 사라지지 않고 이동할 뿐이다"라는 문장이 통찰이 되려면 이 대가를 함께 말해야 한다.

### 2-1. ① 외부 세션 저장소 (Redis + Spring Session) — 가장 일반적

세션을 서버 메모리가 아닌 **모든 서버가 공유하는 Redis**에 둔다. 어느 서버가 요청을 받아도 같은 세션을 조회할 수 있으므로 1-2의 세 가지 사고가 전부 사라진다.

```java
// Before: 톰캣 기본 — 세션이 "이 서버" 메모리에 저장된다
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    Member member = authService.authenticate(req);
    session.setAttribute("memberId", member.getId());
    // 이 setAttribute가 쓰는 곳은 이 JVM의 힙이다.
    // 문제: 서버가 2대가 되는 순간, 다음 요청이 다른 서버로 가면
    //       그 서버의 힙에는 이 세션이 없다 -> 랜덤 로그아웃 버그
    //       그리고 이 서버를 재시작하면 세션은 그냥 사라진다.
}
```

```yaml
# After: Spring Session Redis — 애플리케이션 코드는 그대로, 저장 위치만 이동
spring:
  session:
    store-type: redis
    timeout: 30m            # 세션 만료 — Redis의 TTL로 구현된다
  data:
    redis:
      host: session-redis.internal
      port: 6379
# Spring Session이 HttpSession 구현을 Redis 기반으로 갈아끼운다.
# 컨트롤러의 session.setAttribute(...) 코드는 한 줄도 바뀌지 않는다.
```

`HttpSession` API를 그대로 쓰면서 저장소만 Redis로 바뀌므로 **기존 코드 수정이 거의 없다**는 것이 이 방식의 최대 장점이다. 세션 만료도 Redis의 TTL로 자동 처리되므로 만료 청소 배치를 따로 만들지 않아도 된다.

**그런데 무엇이 새로 생겼는가.** 세 가지다. 이것을 말하지 못하면 "Redis로 빼면 됩니다"에서 멈춘 답변이 된다.

**(1) 요청당 네트워크 왕복이 생긴다.** 원래는 힙에서 참조 하나 따라가는 일(수십 나노초)이었던 것이, 이제 **다른 장비에 다녀오는 일**이 된다. 왕복은 최소 1회(조회)이고, 세션 속성이 바뀌거나 마지막 접근 시각을 갱신하면 2회가 된다.

같은 리전·같은 가용 영역이면 왕복이 밀리초 미만이므로 평상시에는 문제가 안 된다. **문제는 그 왕복이 느려질 때 전 요청이 함께 느려진다는 점이다.** 인증이 필요한 모든 요청이 이 경로를 지나기 때문이다. 숫자로 세워 보면 영향의 크기가 보인다.

```
[전제] 500 TPS, 인증 필요 요청이 전부 세션을 조회한다.

평상시 세션 조회 1ms
  Little의 법칙(동시 요청 수 = 유입률 x 체류시간)으로 스레드 점유를 본다.
    500건/s x 0.001s = 0.5건
  -> 세션 조회 때문에 상시 묶여 있는 스레드가 0.5개. 무시할 수 있다.

Redis가 느려져 세션 조회 20ms
    500건/s x 0.020s = 10건
  -> 스레드 10개가 "Redis 응답 대기" 상태로 상시 묶인다.
     톰캣 기본 스레드가 200개라면 5%가 대기에 잠긴 것이다.

Redis가 더 느려져 세션 조회 500ms
    500건/s x 0.5s = 250건
  -> 200개짜리 스레드풀로는 감당이 안 된다. 스레드풀 고갈.
     세션 저장소 하나가 느려진 것으로 전 API가 멈춘다.
```

검산하면 500 × 0.001 = 0.5, 500 × 0.02 = 10, 500 × 0.5 = 250이다. **"느려진 저장소가 죽은 저장소보다 나쁘다"**는 말이 여기서 나온다 — 죽었으면 즉시 연결 실패를 받고 폴백으로 갈 텐데, 느려지면 모든 스레드가 그 앞에 줄을 선다(계산의 근거는 17번 문서, 스레드 고갈의 전파는 18번 문서).

그래서 세션 저장소에는 **반드시 짧은 타임아웃을 건다.** 무한 대기는 장애를 전파시키는 통로다.

```yaml
spring:
  data:
    redis:
      timeout: 300ms            # 명령 응답 대기 상한
      connect-timeout: 200ms    # 연결 수립 대기 상한
      # 이 두 값이 "Redis 지연이 애플리케이션 스레드를 묶을 수 있는 최대 시간"이다.
      # 기본값(무한 또는 수 초)으로 두면 저장소 지연이 그대로 스레드 고갈이 된다.
```

**(2) 직렬화 비용과 직렬화 사고가 생긴다.** 세션 객체를 네트워크로 보내려면 바이트 배열로 바꿔야 한다(직렬화). 여기에는 CPU 비용도 있지만, 실무에서 더 아픈 것은 **운영 사고**다.

Spring Session Redis는 기본적으로 JDK 직렬화를 쓴다. 그러면 세션에 담은 객체의 클래스 구조가 바뀌는 배포에서 문제가 생긴다 — **구 버전이 저장한 세션을 신 버전이 역직렬화하지 못해 예외가 나고, 그 사용자는 로그인이 풀린다.** 롤링 배포 중에는 신·구 버전이 동시에 떠 있으므로 양방향으로 터진다.

```java
// Before: 도메인 객체를 세션에 그대로 담는다 — 배포마다 폭탄이 된다
session.setAttribute("loginMember", member);
// member는 Member 엔티티. 필드가 하나 추가되거나 타입이 바뀌면
// 구 버전이 저장한 바이트를 신 버전이 못 읽는다 -> 역직렬화 실패
// 게다가 엔티티를 담으면 지연 로딩 프록시나 연관 객체까지 딸려 들어가
// 세션 크기가 예상 밖으로 커진다.
```

```java
// After: 세션에는 식별자와 최소 정보만 담는다
session.setAttribute("memberId", member.getId());
session.setAttribute("roles", List.of("ROLE_USER"));   // 문자열·숫자 위주
// 이유 1: 클래스 구조 변경의 영향을 받지 않는다 (Long, String, List는 안정적이다)
// 이유 2: 세션 크기가 작아 왕복 비용과 Redis 메모리 사용량이 준다
// 이유 3: 회원 정보가 바뀌었을 때 세션의 옛 사본이 남지 않는다
//         (필요한 순간에 memberId로 다시 조회하면 항상 최신이다)
```

여기에 직렬화 방식을 JSON으로 바꿔 두면 사람이 읽을 수 있고 버전 호환성도 다루기 쉬워진다. 다만 **어느 쪽을 쓰든 "세션에 담는 것은 식별자와 최소 정보"라는 원칙이 먼저**다.

**(3) Redis가 새로운 단일 장애점이 된다.** 이것이 가장 크다 — 별도로 다룬다.

### 2-2. 옮긴 곳의 장애까지 설계의 일부다

세션을 한곳에 모으면 **그곳이 전 사용자의 로그인을 쥔 단일 장애점(SPOF)**이 된다. 원래는 "서버 한 대가 죽으면 그 서버 사용자만 로그아웃"이었던 위험이, 이제 **"Redis가 죽으면 전 사용자가 동시에 로그아웃"**으로 바뀐 것이다. 위험의 총량이 줄어든 게 아니라 **모양이 바뀌었고, 대신 그 한 곳을 집중적으로 지킬 수 있게 된 것**이다.

그래서 대비가 설계에 포함돼야 한다. 두 층으로 나눈다.

**(1) 저장소 자체를 고가용 구성으로 만든다.** 복제본을 두고(replication) 마스터 장애 시 자동으로 승격시킨다(Sentinel 또는 Cluster). 여기서 정확히 알아야 할 것은 **복제가 비동기라서 페일오버 시 마지막 몇 밀리초의 쓰기는 유실될 수 있다**는 점이다. 세션에서는 이것이 대개 감수 가능하다 — 방금 로그인한 소수가 다시 로그인하면 되는 일이다. 반면 결제 정보를 같은 Redis에 담아 두면 감수 불가가 된다. **저장소를 용도별로 나누는 이유가 이것이다.**

**(2) 장애 시나리오를 등급화한다.** 세션 조회 실패를 곧바로 500 에러로 만들면, 저장소 장애가 **전 기능 정지**가 된다. 그럴 필요가 없는 기능이 대부분이다.

```java
// Before: 세션 조회 실패가 전체 요청 실패가 된다
public MemberContext resolve(HttpServletRequest req) {
    Long memberId = (Long) req.getSession().getAttribute("memberId");
    // Redis 장애 시 여기서 예외 -> 500. 비로그인도 볼 수 있는
    // 웹툰 목록·회차 열람까지 전부 막힌다.
    return memberRepository.findById(memberId).orElseThrow();
}
```

```java
// After: 세션 조회 실패를 "비로그인"으로 강등하고, 기능별로 처리를 나눈다
public MemberContext resolve(HttpServletRequest req) {
    try {
        Long memberId = (Long) req.getSession().getAttribute("memberId");
        return memberId == null ? MemberContext.anonymous()
                                : MemberContext.of(memberId);
    } catch (RedisConnectionFailureException | QueryTimeoutException e) {
        // 세션 저장소 장애를 "인증 실패"가 아니라 "인증 미확인"으로 취급한다.
        // 열람·목록 같은 비로그인 허용 기능은 이 상태로도 서비스된다.
        // 결제·구매처럼 인증이 필수인 기능은 이 컨텍스트를 받아
        // 상위에서 401로 거절하면 된다 — 거절 범위를 최소화하는 것이 요점이다.
        degradationMetrics.increment("session.store.unavailable");
        return MemberContext.unknown();
    }
}
```

**"Redis로 뺐다"에서 끝나지 않고 "뺀 곳의 장애까지 설계했다"가 한 단계 위의 답변이다.** 어떤 기능까지 비로그인으로 살릴지는 서비스 성격에 따라 다르므로, 이 등급화는 기술 결정이 아니라 제품 결정과 함께 해야 한다(단계적 성능 저하 설계는 15번 문서).

### 2-3. ② 토큰 기반 인증 (JWT) — 상태를 클라이언트로

세션 저장소 자체를 없애고, **서명된 토큰**에 사용자 정보를 담아 클라이언트가 매 요청 들고 오게 한다.

**JWT(JSON Web Token)**는 사용자 정보(claim)를 담은 JSON에 서버의 비밀 키로 서명을 붙여 만든 문자열이다. 구조를 보면 왜 저장소가 필요 없는지 바로 보인다.

```
헤더.페이로드.서명

헤더    {"alg":"HS256","typ":"JWT"}          — 어떤 알고리즘으로 서명했는지
페이로드 {"sub":"9412","exp":1735689600,...}  — 누구인지, 언제까지 유효한지
서명    HMAC-SHA256(비밀키, 헤더 + "." + 페이로드)
```

**서버가 stateless해지는 이유는 "검증만 하고 아무것도 저장하지 않기" 때문이다.** 토큰이 오면 서버는 같은 비밀 키로 서명을 다시 계산해 첨부된 서명과 비교한다. 일치하면 **그 페이로드는 우리가 발급한 것이고 그 뒤 위조되지 않았다**는 사실이 수학적으로 확인된다. 만료 시각도 페이로드 안에 있으니 그것도 그 자리에서 검사한다. **어떤 저장소도 조회하지 않고, 어떤 것도 기록하지 않는다.** 그래서 서버 몇 대든, 어느 서버로 가든 결과가 같다.

```java
// 검증은 순수 계산이다 — 저장소 조회가 0회
public Authentication authenticate(String token) {
    Jws<Claims> jws = Jwts.parser()
            .verifyWith(secretKey)   // 같은 키로 서명을 재계산해 비교한다
            .build()
            .parseSignedClaims(token);   // 서명 불일치나 만료면 예외
    // 이 시점에 확인된 것: ① 우리가 발급했다 ② 내용이 위조되지 않았다 ③ 안 만료됐다
    // 확인되지 않은 것: 이 토큰이 "지금도 유효해야 하는가" — 이것이 아래의 대가다.
    return new JwtAuthentication(jws.getPayload().getSubject());
}
```

장점은 명확하다. 저장소 인프라가 필요 없고, 서버 간 세션 공유 문제가 원천적으로 사라지며, 여러 서비스가 같은 키(또는 공개 키)로 각자 검증할 수 있으니 **MSA에서 인증 정보를 전달하기 쉽다.**

**그러나 대가가 있다. 그리고 이 대가가 이 문서에서 가장 중요한 부분이다.**

**(1) 발급된 토큰을 만료 전에 무효화할 수 없다.** 서버가 아무것도 저장하지 않으므로, **"이 토큰은 이제 쓰지 마"라고 적어 둘 곳이 없다.** 서명이 유효하고 만료 시각이 지나지 않았으면 서버는 그 토큰을 받아들일 수밖에 없다. 이것은 구현 미비가 아니라 **stateless의 정의에서 따라 나오는 결과**다.

이것이 실무에서 무엇을 뜻하는지 구체적으로 보자. 유효 기간 1시간짜리 토큰을 쓰고 있다면,

- **로그아웃이 즉시 반영되지 않는다.** 사용자가 로그아웃 버튼을 눌러도 서버가 할 수 있는 일은 "클라이언트에게 토큰을 지우라고 안내하는 것"뿐이다. 그 토큰을 어딘가에 복사해 뒀다면 남은 시간 동안 계속 쓸 수 있다.
- **계정 탈취 대응이 늦다.** 토큰이 유출된 것을 알아채고 비밀번호를 바꿔도, **이미 발급된 토큰은 최대 1시간 더 살아 있다.**
- **강제 탈퇴·정지가 즉시 반영되지 않는다.** 어뷰징 계정을 차단해도 남은 유효 기간 동안 API를 계속 호출한다.
- **권한 회수가 즉시 반영되지 않는다.** 토큰 페이로드에 `roles`를 담아 뒀다면, 관리자 권한을 회수해도 **그 토큰에 적힌 "관리자"는 만료까지 유효하다.** 이것이 가장 위험한 경우다.

**(2) 매 요청에 실려 크기가 부담이 된다.** 세션 방식에서 쿠키에 실리는 것은 세션 ID 하나(수십 바이트)다. JWT는 사용자 정보 전체가 실린다. 권한 목록까지 담으면 1KB를 넘기기 쉽다.

```
[전제] 10,000 TPS, 토큰 크기 1KB

토큰만으로 발생하는 업링크 트래픽 = 10,000건/s x 1KB = 약 10MB/s
```

초당 10MB에 가까운 트래픽이 **순수하게 헤더로** 흐른다. 게다가 헤더 크기에는 상한이 있다 — Spring Boot의 `server.max-http-header-size` 기본값은 8KB다. 권한이 많은 사용자의 토큰이 이 한도를 넘기면 **그 사용자만 요청이 400으로 거절되는** 재현 어려운 버그가 된다. 그래서 **토큰에는 권한 목록을 다 담지 않고 식별자와 최소 정보만 담는다**는 원칙이 나온다. 2-1에서 "세션에는 식별자만 담아라"고 했던 것과 같은 결론에 다른 이유로 도달한 것이다.

**(3) 그래서 상태가 다시 서버로 돌아온다.** 여기가 이 주제의 반전이다.

(1)의 즉시 무효화 문제를 해결하려면 결국 **"무효화된 토큰 목록"을 서버가 어딘가에 들고 있어야 한다.** 블랙리스트를 Redis에 두는 것이 전형적인 해법인데, 그러면 **매 요청마다 "이 토큰이 블랙리스트에 있나"를 조회하게 되므로 저장소 왕복이 다시 생긴다.** JWT를 쓴 이유가 바로 그 왕복을 없애는 것이었으니, 목적을 되돌린 셈이다.

그래서 실무는 다른 절충으로 간다. **짧은 액세스 토큰 + 서버에 상태를 두는 리프레시 토큰**이다.

```
[액세스 토큰]  JWT, 유효 기간 짧게(수 분 ~ 수십 분)
   · 매 요청에 실려 오고, 서버는 서명만 검증한다 (저장소 조회 0회)
   · 무효화 못 하는 문제는 "유효 기간이 짧아서 곧 알아서 죽는다"로 감수한다
   · 감수의 크기가 곧 유효 기간이다 — 5분이면 최악의 노출 창이 5분이다

[리프레시 토큰]  서버 저장소(Redis/DB)에 기록해 둔다
   · 액세스 토큰이 만료되면 이것으로 새 액세스 토큰을 받아간다
   · 저장소에 있으므로 삭제할 수 있다 = 즉시 무효화가 가능하다
   · 사용 빈도가 낮으므로(수 분에 1회) 왕복 비용이 문제가 되지 않는다
```

```
[강제 로그아웃이 실제로 반영되는 경로]

  t=0    관리자가 계정 정지 -> 리프레시 토큰을 저장소에서 삭제
  t=0    이미 발급된 액세스 토큰은 여전히 유효하다 (막을 수 없다)
  t=~5분 액세스 토큰 만료
  t=~5분 클라이언트가 갱신을 시도 -> 리프레시 토큰이 저장소에 없다 -> 거절
         -> 여기서 실제로 접근이 끊긴다

  즉 "즉시"가 아니라 "액세스 토큰 유효 기간 이내"가 실제 보장 수준이다.
  이 수치를 아는 것과 모르는 것의 차이가 크다 — 보안 요구가
  "탈취 시 30초 내 차단"이라면 이 구조로는 미달이다.
```

**결국 상태가 다시 서버로 돌아왔다.** 다만 돌아온 위치가 다르다 — 매 요청이 지나는 경로가 아니라, **수 분에 한 번만 지나는 갱신 경로**로 옮겨 놓은 것이다. 이것이 "상태는 사라지지 않고 이동할 뿐이다"의 가장 정확한 사례이고, 무효화 요구와 왕복 비용 사이의 절충점을 **유효 기간이라는 하나의 숫자로 조절 가능하게** 만든 설계다.

### 2-4. ③ Sticky Session — 임시방편임을 알고 쓰기

로드밸런서가 같은 사용자를 같은 서버로 고정하는 방식이다. **상태를 옮기지 않고 그대로 둔 채, 요청이 그 상태를 찾아가게 만드는** 접근이다.

코드 수정 없이 당장 동작한다는 것이 유일한 장점이고, 1-2에서 본 세 가지 문제 중 **첫 번째(랜덤 로그아웃)만 해결하고 나머지 둘은 하나도 해결하지 못한다.** scale-in과 배포 시 세션 소실은 그대로고, 부하 편중이라는 새 문제까지 생긴다. 오토스케일링으로 서버를 늘려도 기존 사용자는 기존 서버에 묶여 있으니 **확장했는데 확장 효과가 없는** 상태가 된다.

"왜 임시방편인지"를 설명할 수 있어야 하고, 면접에서는 **마이그레이션 과도기 전략** 정도로만 언급하는 것이 안전하다(LB 쪽 관점은 03번 문서 2-6).

### 2-5. 세 선택지 정리

| | 상태의 위치 | 요청당 저장소 왕복 | 즉시 무효화 | 주된 대가 |
|---|---|---|---|---|
| Redis 세션 | 서버 밖 공유 저장소 | 1~2회 | 가능 | 왕복 지연, 직렬화, 저장소가 SPOF |
| JWT | 클라이언트 | 0회 | 불가 | 만료 전 무효화 불가, 매 요청 크기 |
| Sticky session | 서버 안 (그대로) | 0회 | 가능 | 확장·배포 문제가 남는다 |
| JWT + 리프레시 토큰 | 양쪽에 나눠 | 갱신 시에만 | 유효 기간 이내 | 구현 복잡도 |

## 3. 실무 사례 — 세션 말고도 서버를 Stateful로 만드는 것들

**"세션은 Redis로 뺐으니 우리 서버는 stateless"라고 안심하는 순간이 가장 위험하다.** 로컬 상태는 여러 얼굴로 숨어 있고, 대부분 서버가 한 대일 때는 완벽하게 동작하기 때문에 scale-out 이전에는 버그로 보이지도 않는다.

각각을 **"무엇이 깨지는가 → 어떻게 옮기는가"** 한 쌍으로 본다. 1-1의 판정 문장을 계속 적용해 보면 된다 — **이 서버를 지금 꺼도 다른 서버가 같은 결과를 낼 수 있는가.**

### 3-1. 로컬 디스크에 저장한 업로드 파일

```java
// Before: 업로드 파일을 이 서버의 로컬 디스크에 저장한다
@PostMapping("/episodes/{id}/images")
public void upload(@PathVariable long id, MultipartFile file) throws IOException {
    file.transferTo(new File("/data/uploads/" + id + "/" + file.getOriginalFilename()));
    imageRepository.save(new Image(id, file.getOriginalFilename()));
    // DB에는 파일명만 남는다. "그 파일이 어느 서버에 있는지"는 아무도 모른다.
}
```

**무엇이 깨지는가.** 업로드는 1번 서버가 받았고 파일은 1번 서버 디스크에 있다. 다운로드 요청이 LB를 통해 2번 서버로 가면 **파일이 없어서 404**다. 서버 3대면 성공 확률이 1/3이 되므로 사용자에게는 "때때로 이미지가 안 보인다"로 나타난다. 게다가 그 서버가 교체되면 파일이 **영구히 사라진다** — 컨테이너 환경이라면 재시작만으로도 사라진다.

**어떻게 옮기는가.** 파일을 모든 서버가 같은 주소로 접근할 수 있는 오브젝트 스토리지(S3 등)에 둔다.

```java
// After: 오브젝트 스토리지에 저장하고, DB에는 그 키를 남긴다
@PostMapping("/episodes/{id}/images")
public void upload(@PathVariable long id, MultipartFile file) throws IOException {
    String key = "episodes/%d/%s".formatted(id, UUID.randomUUID());
    objectStorage.put(key, file.getInputStream(), file.getSize(), file.getContentType());
    imageRepository.save(new Image(id, key));
    // 저장된 key는 서버와 무관한 전역 주소다. 어느 서버가 받아도 같은 것을 읽고,
    // 서버가 교체돼도 파일은 남는다. (여기서 05번 문서의 CDN 서빙으로 이어진다.)
}
```

### 3-2. 인메모리 캐시 — 인스턴스별로 다른 값을 보게 되는 문제

```java
// Before: 인스턴스 로컬 캐시. 서버가 3대면 캐시도 3개, 값도 3개일 수 있다.
@Component
public class EpisodeCache {
    private final Map<Long, Episode> cache = new ConcurrentHashMap<>();

    public Episode get(long id) {
        return cache.computeIfAbsent(id, episodeRepository::findByIdOrThrow);
    }

    public void evict(long id) {
        cache.remove(id);   // 이 서버의 캐시만 지운다. 다른 두 대는 옛 값을 그대로 들고 있다.
    }
}
```

**무엇이 깨지는가.** 운영자가 회차 제목의 오타를 고쳤다. 수정 API를 받은 인스턴스 A는 자기 캐시를 무효화했지만 **B와 C는 그런 일이 있었는지 모른다.** 사용자가 새로고침할 때마다 LB가 다른 인스턴스로 보내므로 **제목이 새 값과 옛 값 사이에서 오간다.** 이것을 "새로고침 룰렛"이라 부를 만한데, 재현이 불규칙해서 버그 리포트를 받아도 개발자 로컬에서는 절대 재현되지 않는다(서버가 한 대니까).

카운터라면 더 나쁘다. 조회수를 로컬 `Map`에 모으고 있었다면 **세 인스턴스의 값이 각자 다르고, 인스턴스가 내려갈 때 그 몫이 그냥 사라진다.**

**어떻게 옮기는가.** 두 갈래다.

**① 캐시 자체를 공유 저장소로 옮긴다.** 가장 단순하고, 값이 하나이므로 불일치가 원천적으로 없다. 대가는 2-1에서 본 그대로 — 요청당 왕복이 생긴다.

```java
// After ①: 공유 캐시. 인스턴스가 몇 대든 값은 하나다.
@Cacheable(cacheNames = "episode", key = "#id")   // CacheManager가 Redis 기반
public Episode get(long id) { return episodeRepository.findByIdOrThrow(id); }

@CacheEvict(cacheNames = "episode", key = "#id")  // 무효화도 한 번에 전역 반영
public void update(long id, EpisodeUpdate cmd) { ... }
```

**② 로컬 캐시는 유지하고, 무효화만 전파한다.** 로컬 캐시의 속도(왕복 0회)를 포기하지 않는 대신, 무효화 이벤트를 pub/sub으로 전 인스턴스에 방송해 각자 자기 캐시를 지우게 한다. 두 계층을 쓰므로 2계층 캐시라고 부른다.

```java
// After ②: 로컬 캐시 + 무효화 방송
@Component
public class EpisodeCache {
    private final Cache<Long, Episode> local;   // Caffeine 등, TTL을 짧게 잡는다
    private final StringRedisTemplate redis;

    public void evict(long id) {
        local.invalidate(id);
        redis.convertAndSend("cache:episode:evict", String.valueOf(id));
        // 자기 것만 지우고 끝내지 않고, 다른 인스턴스에게도 알린다.
    }

    @EventListener   // Redis 메시지 리스너가 이 이벤트로 변환해 준다
    public void onEvictMessage(EpisodeEvictedEvent e) {
        local.invalidate(e.id());
        // 각 인스턴스가 방송을 받아 자기 로컬 캐시를 지운다.
    }
    // 주의: 방송은 유실될 수 있고 순서 보장도 없다. 그래서 로컬 캐시의 TTL을
    //       짧게(수십 초) 잡아 "방송이 유실돼도 곧 만료된다"는 안전망을 함께 둔다.
}
```

### 3-3. `@Scheduled` — scale-out 직후 반드시 밟는 함정

```java
// Before: 인스턴스마다 스케줄러가 돈다
@Component
public class SettlementScheduler {
    @Scheduled(cron = "0 0 3 * * *")
    public void settleDaily() {
        settlementService.settle(LocalDate.now().minusDays(1));
    }
}
```

**무엇이 깨지는가.** `@Scheduled`는 **그 JVM 안의 타이머**다. 즉 인스턴스가 3대면 **매일 새벽 3시에 정산이 3번 돈다.** 그리고 셋이 거의 동시에 시작하므로 결과가 세 갈래로 갈린다.

```
[인스턴스 3대에서 동시에 시작된 정산]

  ① 운이 나쁘면: 세 번 다 성공 -> 정산 금액이 3배로 적립된다 (돈 사고)
  ② 조금 나으면: 유니크 제약에 둘이 걸려 실패 -> 새벽마다 알 수 없는 에러 알림
  ③ 최악:        세 트랜잭션이 같은 행을 반대 순서로 잠가 데드락 ->
                 셋 다 실패하고 정산이 아예 안 된다
```

**이 함정이 특히 위험한 이유는 시점이다.** scale-out은 트래픽이 늘어서 하는 것이고, 스케줄러 중복은 그 직후 첫 실행 시각에 조용히 터진다. 그리고 배치는 대개 새벽에 돌므로 **아침에 발견한다.**

**어떻게 옮기는가.** 세 가지 방법이 있고, 근본적인 쪽으로 갈수록 뒤에 있다.

**① 분산 락 — 락을 잡은 하나만 실행한다.** 코드 변경이 가장 작다. Spring 환경에서는 ShedLock이 널리 쓰인다.

```sql
-- ShedLock의 잠금 상태를 저장하는 테이블 (PostgreSQL)
CREATE TABLE shedlock (
    name       varchar(64)  NOT NULL PRIMARY KEY,   -- 작업 이름. PK가 곧 상호 배제의 근거다
    lock_until timestamptz  NOT NULL,               -- 이 시각까지 이 락은 유효하다
    locked_at  timestamptz  NOT NULL,
    locked_by  varchar(255) NOT NULL                -- 어느 인스턴스가 잡았는지 (추적용)
);
-- 상호 배제가 성립하는 이유: 세 인스턴스가 같은 name으로 동시에 쓰려 하면
-- PK 제약 때문에 DB가 한 건만 통과시킨다. 판정이 애플리케이션이 아니라
-- DB 안에서 원자적으로 일어나는 것이 핵심이다.
```

```java
// After ①: 락을 잡은 인스턴스 하나만 실행한다
@Component
public class SettlementScheduler {

    @Scheduled(cron = "0 0 3 * * *")
    @SchedulerLock(name = "settleDaily",
                   lockAtMostFor = "PT30M",   // 락 보유 상한
                   lockAtLeastFor = "PT1M")   // 락 보유 하한
    public void settleDaily() {
        settlementService.settle(LocalDate.now().minusDays(1));
    }
    // lockAtMostFor: 락을 잡은 인스턴스가 죽어 락을 못 풀 때를 대비한 강제 해제 시한이다.
    //                실제 작업 시간보다 넉넉히 크게 잡아야 한다 — 작업이 아직 도는 중에
    //                시한이 지나면 다른 인스턴스가 락을 잡아 중복 실행이 다시 생긴다.
    // lockAtLeastFor: 작업이 너무 빨리 끝났을 때 최소 이만큼은 락을 쥐고 있게 한다.
    //                 인스턴스 간 시계 오차 때문에 "먼저 끝난 뒤 옆 인스턴스가
    //                 같은 스케줄로 또 잡는" 경우를 막는 장치다.
}
```

여기서 반드시 함께 말해야 하는 사실이 있다. **분산 락은 "정확히 한 번"을 보장하지 않는다.** 락을 잡은 인스턴스가 긴 GC로 멈춘 사이 `lockAtMostFor`가 지나면 다른 인스턴스가 락을 잡고, 그 뒤 원래 인스턴스가 깨어나 작업을 계속할 수 있다. 그래서 **락은 중복 실행의 확률을 크게 낮추는 장치이고, 작업 자체를 멱등하게 만드는 것이 그 아래의 안전망**이다. 정산이라면 `(정산일자)`에 유니크 제약을 걸어 두 번째 시도가 DB에서 거절되게 만드는 식이다.

**② 리더 선출 — "이 역할은 한 인스턴스만"을 명시한다.** 인스턴스 중 하나를 리더로 뽑고 리더만 스케줄러를 켠다. 쿠버네티스의 Lease, ZooKeeper·etcd 같은 조정 서비스가 이 역할을 맡는다. 스케줄 작업이 여러 개일 때 각각에 락을 거는 것보다 관리가 단순해진다.

**③ 배치를 애플리케이션에서 분리한다.** 가장 근본적이다. 정산 배치를 API 서버에 얹지 않고 **별도의 단일 실행 워크로드**로 뺀다. 쿠버네티스의 CronJob이 대표적이다.

```yaml
# After ③: 스케줄 실행 주체를 클러스터가 관리한다
apiVersion: batch/v1
kind: CronJob
metadata:
  name: settlement-daily
spec:
  schedule: "0 3 * * *"
  concurrencyPolicy: Forbid   # 이전 실행이 안 끝났으면 새 실행을 시작하지 않는다
  # 이 설정이 요점이다. 중복 실행 방지를 애플리케이션 코드가 아니라
  # 플랫폼이 책임지므로, API 서버는 몇 대로 늘려도 배치와 무관해진다.
  # 부가 이득: 배치의 자원 요구(메모리, CPU)를 API 서버와 따로 잡을 수 있고,
  #           배치가 폭주해도 API 서버의 스레드를 잡아먹지 않는다.
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: settlement
              image: myapp/batch:1.4.2
              args: ["--job=settlementDaily"]
```

### 3-4. WebSocket·SSE — 연결 자체가 특정 인스턴스에 묶인다

```java
// Before: 연결을 자기 메모리의 Map에 들고 있다
@Component
public class NotificationHub {
    private final Map<Long, WebSocketSession> sessions = new ConcurrentHashMap<>();

    public void register(long memberId, WebSocketSession session) {
        sessions.put(memberId, session);
    }

    public void notify(long memberId, String message) throws IOException {
        WebSocketSession s = sessions.get(memberId);
        if (s != null) s.sendMessage(new TextMessage(message));
        // 이 인스턴스에 붙은 사용자에게만 보낼 수 있다.
    }
}
```

**무엇이 깨지는가.** WebSocket과 SSE는 **연결이 유지되는 동안 그 인스턴스에 물리적으로 붙어 있다.** 이건 설정 문제가 아니라 TCP 연결의 성질이다. 그래서 사용자 A의 연결은 인스턴스 1에, B의 연결은 인스턴스 3에 있다.

이제 "A에게 알림을 보내라"는 내부 API 호출이 LB를 통해 **인스턴스 2**에 도착하면, 인스턴스 2의 `sessions`에는 A가 없다. **알림이 조용히 유실된다.** 서버 3대면 성공 확률이 1/3이다.

**어떻게 옮기는가.** 연결 자체는 옮길 수 없으므로, **"누구에게 보내야 하는지"라는 정보를 전 인스턴스에 방송**하고 그 사용자를 들고 있는 인스턴스가 실제 전송을 맡게 한다.

```java
// After: 발행은 전 인스턴스에 방송하고, 전송은 연결을 가진 인스턴스가 한다
@Component
public class NotificationHub {
    private final Map<Long, WebSocketSession> sessions = new ConcurrentHashMap<>();
    private final StringRedisTemplate redis;

    // ① 알림 발생: 내가 그 연결을 갖고 있는지 따지지 않고 채널에 던진다
    public void publish(long memberId, String message) {
        redis.convertAndSend("notify", memberId + ":" + message);
    }

    // ② 모든 인스턴스가 이 채널을 구독한다. 자기가 가진 연결에만 전달하고,
    //    없으면 그냥 무시한다 — 어느 한 인스턴스는 반드시 갖고 있다.
    @EventListener
    public void onNotifyMessage(NotifyMessage m) throws IOException {
        WebSocketSession s = sessions.get(m.memberId());
        if (s != null) s.sendMessage(new TextMessage(m.message()));
    }
    // 여기서 로컬 Map은 남아 있지만 stateless를 깨지 않는다.
    // "이 인스턴스만 아는 상태"가 요청 처리 결과를 좌우하지 않기 때문이다 —
    // 어느 인스턴스가 발행 요청을 받아도 결과가 같아졌다.
    // 다만 인스턴스가 죽으면 그 연결들은 끊어지므로, 클라이언트의 재연결 로직은
    // 여전히 필수다. 이 계층에서는 "끊김을 없애는 것"이 아니라
    // "끊긴 뒤 아무 인스턴스에 다시 붙어도 되게 만드는 것"이 목표다.
}
```

이 사례는 **로컬 상태가 남아 있어도 stateless일 수 있다**는 것을 보여주는 좋은 예다. 1-1의 판정 문장을 다시 대 보면 답이 나온다 — 발행 요청을 어느 인스턴스가 받아도 결과가 같으므로 통과한다.

### 3-5. 로컬 디스크 기반 락 파일 — 락처럼 보이지만 락이 아니다

```java
// Before: 파일 생성으로 중복 실행을 막으려는 시도
public void runOnce() {
    File lock = new File("/tmp/settlement.lock");
    if (lock.exists()) return;          // 이미 누가 돌고 있다고 판단
    try {
        lock.createNewFile();
        settlementService.settle(LocalDate.now().minusDays(1));
    } finally {
        lock.delete();
    }
}
```

**무엇이 깨지는가.** 두 가지가 동시에 깨진다.

첫째, **인스턴스마다 파일시스템이 다르다.** 인스턴스 1의 `/tmp/settlement.lock`과 인스턴스 3의 `/tmp/settlement.lock`은 완전히 다른 파일이다. 셋이 각자 자기 락을 만들고 각자 통과한다 — **상호 배제가 전혀 성립하지 않는다.** 한 대일 때만 동작하던 코드의 전형이다.

둘째, 한 대라도 **`exists()` 확인과 `createNewFile()` 사이에 틈이 있다.** 두 스레드가 나란히 `exists()`를 통과할 수 있으므로 같은 인스턴스 안에서도 안전하지 않다. **"확인한 뒤 선점"은 원자적이지 않다**는 원칙은 로컬에서도 유효하다.

셋째, `finally`의 `delete()`가 실행되기 전에 프로세스가 죽으면 **락 파일이 영구히 남아 다음부터 아무도 실행하지 못한다.** 만료 시각이 없는 락은 항상 이 위험을 갖는다.

**어떻게 옮기는가.** 상호 배제 판정을 **모든 인스턴스가 공유하는 한 곳에서, 원자적으로** 하게 만든다. 이미 PostgreSQL을 쓰고 있다면 어드바이저리 락이 가장 간편하다.

```java
// After: PostgreSQL 어드바이저리 락 — 판정을 DB가 원자적으로 한다
@Transactional
public void runOnce() {
    // pg_try_advisory_xact_lock: 락을 잡을 수 있으면 true, 이미 누가 잡고 있으면
    // 즉시 false를 반환한다(대기하지 않는다). "_xact_" 는 트랜잭션이 끝나면
    // 락이 자동으로 풀린다는 뜻이라, 프로세스가 죽어도 락이 남지 않는다 —
    // 락 파일 방식의 세 번째 문제가 구조적으로 사라진다.
    Boolean acquired = jdbcTemplate.queryForObject(
            "SELECT pg_try_advisory_xact_lock(hashtext('settlement-daily'))",
            Boolean.class);
    if (!Boolean.TRUE.equals(acquired)) {
        return;   // 다른 인스턴스가 이미 돌고 있다. 조용히 넘어간다.
    }
    settlementService.settle(LocalDate.now().minusDays(1));
}
// 어드바이저리 락은 특정 행이나 테이블이 아니라 "우리가 정한 숫자 키"에 걸리는
// 락이다. 그래서 "DB에 없는 개념(배치 실행 권한)"에 대한 상호 배제에 쓸 수 있다.
// 주의: hashtext는 64비트가 아닌 32비트 해시를 내므로 키 충돌 가능성이 있다.
//       배치 종류가 많아지면 키를 상수 표로 관리해 충돌을 직접 통제하는 편이 안전하다.
```

### 3-6. 공통 패턴 — 상태를 없애는 것이 아니라 몰아넣는 것

다섯 사례를 나란히 놓으면 처방이 전부 같은 모양이다.

| 숨은 로컬 상태 | 무엇이 깨지는가 | 어디로 옮기는가 |
|---|---|---|
| 로컬 디스크의 업로드 파일 | 다른 서버에서 404, 교체 시 영구 소실 | 오브젝트 스토리지 |
| 인메모리 캐시·카운터 | 인스턴스별로 값이 다름, scale-in 시 유실 | 공유 캐시 또는 무효화 방송 |
| `@Scheduled` | N대면 N번 실행 (중복 정산·데드락) | 분산 락 / 리더 선출 / 배치 분리 |
| WebSocket·SSE 연결 | 연결 없는 인스턴스에 도착한 알림이 유실 | pub/sub 방송 후 각자 전송 |
| 로컬 락 파일 | 상호 배제가 아예 성립하지 않음 | DB 어드바이저리 락 / Redis 락 |

**공통 패턴은 이것이다. 상태를 없애는 게 아니라 상태 있는 전용 계층(Redis, 오브젝트 스토리지, MQ, DB)으로 몰아넣고, 애플리케이션 서버 계층만 stateless로 유지한다.**

그리고 이 정리에서 자연스럽게 다음 논점이 나온다. **몰아넣었으니 그 계층이 이제 병목이자 장애점이다.** 앱 서버는 마음껏 늘릴 수 있지만 DB와 Redis는 "같은 것 한 대 더"로 늘어나지 않는다. **"확장의 병목은 결국 상태 있는 계층으로 수렴한다"**는 문장이 이 문서와 2번 문서를 잇는 다리다.

## 4. 꼬리질문 대비 포인트

### "Sticky session으로도 동작하는데 굳이 외부 저장소가 필요한가요?"

**동작하는 것과 확장에 안전한 것은 다르다**는 프레임부터 세운다. sticky session이 해결하는 것은 1-2의 세 문제 중 첫 번째(랜덤 로그아웃)뿐이고, 나머지는 그대로 남는다.

**① scale-in·배포·서버 장애 때** 그 서버에 고정된 사용자들의 세션이 전부 소실된다. 롤링 배포를 하면 배포 한 번에 전 사용자가 순차적으로 로그아웃되는 셈이다.

**② 부하가 편중된다.** 특정 서버에 헤비 유저가 몰리면 로드밸런싱 효과가 깨진다. 03번 문서에서 본 "스펙이 같은데 한 대만 힘든" 장애의 원인 후보 중 하나가 정확히 이것이다.

**③ 오토스케일링으로 서버를 늘려도 기존 사용자는 기존 서버에 묶여 있어 새 서버가 부하를 나눠 받지 못한다.** 즉 **"확장했는데 확장 효과가 없는" 상태**가 된다. 새 서버는 신규 로그인만 받으므로, 부하가 이미 최고조인 순간에 증설해도 효과가 서서히 나타난다.

여기에 한 단계 더 얹으면 **"고정된 서버를 내릴 때의 절차"** 문제를 말할 수 있다. sticky session이 걸린 서버를 배포하려면 신규 고정은 받지 않고 기존 사용자의 세션이 만료되기를 기다려야 하는데, **이 대기 시간이 세션 만료 시간(예: 30분)만큼 길어진다.** 배포 한 번에 30분씩 기다릴 수 없으니 결국 세션을 버리고 배포하게 되고, 그러면 애초에 sticky session의 이득이 사라진다. **"임시방편이 임시로 끝나지 않는 이유"**까지 말하면 운영을 아는 답변으로 들린다.

### "JWT와 Redis 세션 중 무엇을 선택하나요?" (시니어 변별 포인트)

기준은 **"즉시 무효화 요구가 있는가"**다. 그리고 이 기준이 왜 결정적인지부터 말해야 한다 — **JWT가 stateless한 이유는 서버가 아무것도 저장하지 않기 때문이고, 그래서 "이 토큰은 이제 무효"라고 적어 둘 곳이 원리적으로 없다.** 구현으로 보완할 수 있는 단점이 아니라 정의에서 따라 나오는 결과다.

- 강제 로그아웃, 계정 탈취 대응, 동시 접속 제한처럼 **서버가 세션을 능동적으로 끊어야 하는 요구**가 있으면 → **Redis 세션**. 서버가 상태의 주인이어야 제어할 수 있다.
- 서비스 간 인증 전달(MSA), 모바일 API처럼 **매 요청 저장소 조회를 줄이고 싶고** 무효화는 "짧은 액세스 토큰 만료(수 분~수십 분)로 충분히 감수 가능"하면 → **JWT + 리프레시 토큰.**
- 실무에서는 절충형이 흔하다. **액세스 토큰은 JWT로 stateless하게 검증하고, 리프레시 토큰만 저장소에 두어 무효화 지점을 확보한다.** "JWT를 쓰는 순간 무효화라는 상태 관리가 완전히 사라지는 게 아니라 리프레시 토큰 계층으로 이동한다"고 말하면 트레이드오프를 이해한 답변이 된다.

여기서 변별을 확실히 하는 방법은 **"즉시"라는 말을 숫자로 바꿔 말하는 것**이다. 이 구조에서 실제 보장 수준은 "즉시"가 아니라 **"액세스 토큰 유효 기간 이내"**다. 액세스 토큰을 5분으로 잡았다면 강제 로그아웃이 실제로 반영되는 것은 최대 5분 뒤다. 보안 요구가 "탈취 인지 후 30초 내 차단"이라면 이 구조로는 미달이므로, 그때는 매 요청 블랙리스트 조회(= 왕복 복귀)나 Redis 세션으로 가야 한다. **트레이드오프를 유효 기간이라는 조절 가능한 숫자로 표현하는 것이 이 답변의 핵심이다.**

토큰 크기 이야기까지 붙이면 좋다. 토큰에 권한 목록을 다 담으면 매 요청에 실리는 크기가 부담이 되고(10,000 TPS × 1KB ≈ 10MB/s), Spring Boot의 헤더 크기 기본 한도 8KB를 넘기면 **권한 많은 사용자만 요청이 거절되는** 버그가 된다. 그래서 **토큰에도 식별자와 최소 정보만 담는다**는 원칙이 필요하다.

### "세션 저장소 Redis가 죽으면 전 사용자 로그인이 풀리는데, 어떻게 대비하나요?"

먼저 **위험의 총량이 줄어든 게 아니라 모양이 바뀐 것**이라는 인식을 보여준다. 원래는 "서버 한 대가 죽으면 그 서버 사용자만 로그아웃"이었던 것이, 세션을 한곳에 모으자 **"저장소가 죽으면 전 사용자가 동시에 로그아웃"**이 됐다. 대신 지킬 곳이 한 곳으로 모였으니 집중적으로 방어할 수 있게 된 것이다.

대비는 두 층이다.

**① 저장소 자체를 고가용으로 만든다.** replication + 자동 페일오버(Sentinel 또는 Cluster)로 구성한다. 이때 **복제가 비동기라 페일오버 시 마지막 몇 밀리초의 쓰기는 유실될 수 있다**는 점을 함께 말하면 좋다. 세션에서는 대개 감수 가능하지만(방금 로그인한 소수가 다시 로그인하면 된다), 그래서 결제 정보 같은 것을 같은 저장소에 담지 않는다는 원칙이 따라온다.

**② 장애 시나리오를 등급화한다.** 세션 조회 실패를 전체 500 에러로 만들지 말고 **"비로그인"으로 강등**해, 열람·목록처럼 인증이 필요 없는 핵심 기능은 살린다. 결제·구매처럼 인증이 필수인 기능만 거절한다. **거절 범위를 최소화하는 것이 목표**이고, 이것이 단계적 성능 저하(graceful degradation) 설계다(15번 문서).

세 번째로 얹을 것은 **타임아웃**이다. 저장소가 죽는 것보다 **느려지는 것이 더 위험하다.** 세션 조회에 타임아웃이 없으면 500ms짜리 지연이 500 TPS 서비스에서 스레드 250개를 상시 묶어(500 × 0.5 = 250) 스레드풀을 고갈시키고, 그러면 세션과 무관한 API까지 전부 멈춘다. **짧은 타임아웃이 폴백보다 먼저 필요한 방어선**이다.

**"Redis로 뺐다"에서 끝나지 않고 "뺀 곳의 장애까지 설계했다"가 한 단계 위의 답변이다.**

### "완전한 stateless 시스템이 가능한가요?"

불가능하다. 상태(주문, 회원, 세션)가 있어야 서비스가 성립한다.

Stateless 설계의 본질은 상태 제거가 아니라 **상태의 재배치**다 — 수평 확장이 쉬운 계산 계층(애플리케이션 서버)에서 상태를 걷어내, 상태 관리에 특화된 계층(DB, Redis, 오브젝트 스토리지)으로 몰아넣는 것이다. 그러니 정확한 표현은 "stateless 시스템"이 아니라 **"stateless한 애플리케이션 서버 계층"**이다.

이 답변에 정확성을 더하려면 **판정 기준을 제시하는 것**이 좋다. "그 인스턴스에만 있고 다른 인스턴스는 모르는 상태가 요청 처리 결과를 좌우하는가"가 기준이고, 실무적으로는 **"이 서버를 지금 꺼도 다른 서버가 같은 요청에 같은 결과를 낼 수 있는가"**로 물으면 된다. 이 기준으로 보면 DB·Redis 사용은 stateless를 깨지 않고, 3-4의 WebSocket 연결 맵처럼 **로컬 상태가 남아 있어도 stateless일 수 있다**는 것까지 설명된다.

그리고 확장 논의의 다음 단계가 항상 **"그럼 그 상태 계층은 어떻게 확장하나"**(수직 확장 → 읽기 복제 → 캐시 → 샤딩)로 이어진다는 점을 붙이면 2번 문서와의 연결이 완성된다.

### "세션 외에 스케일 아웃을 막는 로컬 상태의 예를 들어보세요."

3절 그대로 답하되, **각각을 "무엇이 깨지는가 → 어디로 옮기는가" 쌍으로** 말하는 것이 좋다.

**로컬 디스크의 업로드 파일** — 다운로드 요청이 다른 서버로 가면 404, 서버 교체 시 영구 소실 → 오브젝트 스토리지.

**인메모리 캐시·카운터** — 인스턴스마다 값이 달라 새로고침할 때마다 다른 값이 보이고, scale-in 시 그 인스턴스가 모은 몫이 유실 → 공유 캐시로 옮기거나, 로컬 캐시를 유지하되 pub/sub으로 무효화를 방송하고 로컬 TTL을 짧게 잡아 안전망을 둔다.

**`@Scheduled`** — 인스턴스가 3대면 3번 실행돼 중복 정산·데드락이 난다. **scale-out 직후 첫 실행 시각에 조용히 터지고 대개 새벽이라 아침에 발견한다**는 점을 짚으면 좋다 → 분산 락(ShedLock), 리더 선출, 또는 배치를 별도 CronJob으로 분리. 여기서 한 걸음 더 나가면 **분산 락도 "정확히 한 번"을 보장하지 않으므로**(락 보유 상한이 지나는 사이 GC로 멈췄던 인스턴스가 깨어날 수 있다) 작업 자체를 멱등하게 만드는 것이 최종 안전망이라는 점까지 말한다.

**WebSocket·SSE 연결** — 연결은 TCP 성질상 특정 인스턴스에 붙으므로, 알림 발행 요청이 다른 인스턴스에 도착하면 조용히 유실 → pub/sub으로 전 인스턴스에 방송하고 연결을 가진 인스턴스가 전송. **연결을 옮길 수는 없으니 "끊김을 없애는 것"이 아니라 "끊긴 뒤 아무 인스턴스에 다시 붙어도 되게 만드는 것"이 목표**라는 점이 이 항목의 핵심이다.

**로컬 락 파일** — 인스턴스마다 파일시스템이 달라 상호 배제가 아예 성립하지 않고, 프로세스가 죽으면 락 파일이 영구히 남는다 → PostgreSQL 어드바이저리 락처럼 **판정이 공유 저장소 안에서 원자적으로 일어나고 세션 종료 시 자동 해제되는** 장치.

**인메모리 rate limit 카운터**도 같은 부류다 — 서버별 카운트의 합이 전체 한도를 초과하므로, 인스턴스 3대에 각각 100 TPS 한도를 걸면 실제 통과량은 300 TPS가 된다(8번 문서).

## 한 줄 요약

Stateless 설계는 "상태가 없는 서버"가 아니라 **그 인스턴스만 아는 상태가 없는 서버**를 만드는 일이고(그래서 DB·Redis 사용은 stateless를 깨지 않으며, 판정 기준은 "이 서버를 꺼도 다른 서버가 같은 결과를 내는가"다), 그 성질이 서버 N대를 교체 가능한 부품으로 만들어 scale-out·scale-in·배포·장애 격리를 전부 안전하게 하는 **확장의 전제 조건**이 된다 — 세션은 없애는 게 아니라 공유 저장소(요청당 왕복·직렬화·새 SPOF를 대가로)나 클라이언트 토큰(만료 전 무효화 불가를 대가로, 그래서 리프레시 토큰이라는 형태로 상태가 서버에 되돌아온다)으로 옮기는 것이고, 세션 말고도 로컬 파일·인메모리 캐시·`@Scheduled`·WebSocket 연결·락 파일이 같은 방식으로 확장을 막으므로 **상태는 사라지지 않고 관리하기 좋은 계층으로 이동할 뿐이며 그 이동은 공짜가 아니다.**
