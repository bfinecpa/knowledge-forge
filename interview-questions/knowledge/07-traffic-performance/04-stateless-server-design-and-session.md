# Stateless 서버 설계 — 확장의 전제 조건, 세션은 서버 밖으로

> 핵심 관전 포인트: **Stateless 서버란 요청을 처리하는 데 필요한 상태를
> 서버 자신의 메모리나 디스크에 들고 있지 않는 서버다. 어떤 요청이든
> 어떤 서버가 받아도 같은 결과가 나오므로, 서버를 늘리고(scale-out)
> 줄이고(scale-in) 교체(배포·장애 격리)하는 일이 전부 안전해진다 —
> 즉 Stateless는 오토스케일링과 무중단 배포의 전제 조건이다.
> 세션 같은 상태는 없애는 게 아니라 서버 밖의 공유 저장소(Redis 등)나
> 클라이언트(토큰)로 옮긴다. 상태는 사라지지 않고 이동할 뿐이다.**

---

## 0. 질문 + 의도

**질문**: "Stateless 서버 설계가 왜 확장에 유리한가요? 세션은 어떻게 처리하나요?"

**출제 의도**: 오토스케일링의 전제 조건을 이해하는지 본다. 로컬 상태
(메모리 세션, 로컬 파일)가 하나라도 있으면 스케일 아웃이 곧 버그
발생기가 된다는 것을 **배포 전에** 아는 사람인지 확인하는 질문이다 —
운영에서 "서버 2대로 늘렸더니 로그인이 랜덤하게 풀려요"를 겪고 나서야
배우면 이미 늦다.

## 1. Stateless가 왜 확장에 유리한가 — "아무 서버나 골라도 된다"

**Stateful 서버**는 이전 요청의 흔적(상태)을 자기 메모리에 남긴다.
대표적인 예가 톰캣 기본 설정의 `HttpSession` — 로그인 정보가
**그 서버의 메모리**에 저장된다.

이 순간 서버들은 서로 대체 불가능한 존재가 된다:

- **로드밸런서가 자유롭게 분배 못 한다** — 로그인은 1번 서버에서 했는데
  다음 요청이 2번 서버로 가면 "비로그인 사용자" 취급. 이를 피하려고
  같은 사용자를 같은 서버에 고정(sticky session)하면 부하가 편중된다.
- **scale-in(서버 축소)이 사용자 강제 로그아웃이 된다** — 오토스케일링이
  트래픽 감소를 보고 서버를 내리는 순간, 그 서버 메모리의 세션이 전부 증발.
- **배포가 곧 장애가 된다** — 롤링 배포로 서버를 하나씩 재시작할 때마다
  해당 서버의 세션이 날아간다.

**Stateless 서버**는 요청 처리에 필요한 모든 상태를 요청 자체
(토큰, 파라미터)와 외부 저장소(DB, Redis)에서 가져온다. 서버는
"계산만 하는 교체 가능한 부품"이 된다.

- 비유: 상태가 있는 서버는 **단골 손님의 취향을 외우고 있는 특정 직원** —
  그 직원이 쉬면 서비스 품질이 무너진다. Stateless 서버는 **주문서(요청)와
  고객 카드(외부 저장소)만 보고 일하는 직원** — 누가 응대해도 결과가 같고,
  바쁘면 직원을 몇 명이든 더 투입할 수 있다.

정리하면, Stateless가 확장에 유리한 이유는 하나로 수렴한다:
**"서버 N대가 완전히 동일하고 서로 교체 가능하다"**는 성질이
scale-out, scale-in, 롤링 배포, 장애 서버 격리를 전부 안전하게 만든다.

## 2. 세션은 어떻게 처리하나 — 세 가지 선택지

세션(로그인 상태)은 없앨 수 없다. **어디에 둘 것인가**의 문제다.

### ① 외부 세션 저장소 (Redis + Spring Session) — 가장 일반적

세션을 서버 메모리가 아닌 모든 서버가 공유하는 Redis에 둔다.
어느 서버가 요청을 받아도 같은 세션을 조회할 수 있다.

```java
// Before: 톰캣 기본 — 세션이 "이 서버" 메모리에 저장됨
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("memberId", member.getId());
    // 문제: 서버가 2대가 되는 순간, 다음 요청이 다른 서버로 가면
    //       이 세션이 없다 → 랜덤 로그아웃 버그
}
```

```yaml
# After: Spring Session Redis — 코드는 그대로, 저장 위치만 이동
spring:
  session:
    store-type: redis
  data:
    redis:
      host: session-redis.internal
```

`HttpSession` API를 그대로 쓰면서 저장소만 Redis로 바뀌므로
기존 코드 수정이 거의 없다는 것이 장점. 대신 **모든 요청마다 Redis
왕복이 추가**되고, Redis가 새로운 단일 장애 지점이 되므로 HA 구성
(replication + 자동 failover)이 필수다.

### ② 토큰 기반 인증 (JWT) — 상태를 클라이언트로

세션 저장소 자체를 없애고, 서명된 토큰에 사용자 정보를 담아
클라이언트가 매 요청 들고 오게 한다. 서버는 서명만 검증하면 되므로
저장소 조회가 0회 — 인증 계층까지 완전한 stateless가 된다.

- 장점: 저장소 인프라 불필요, 서버 간 공유 문제 원천 소멸,
  서비스 간(MSA) 인증 전달이 쉬움.
- 단점: **즉시 무효화가 안 된다** — 로그아웃·강제 탈퇴 처리를 해도
  만료 전 토큰은 유효하다. 결국 블랙리스트(= 다시 상태 저장소)나
  짧은 만료 + refresh token으로 보완하게 된다.

### ③ Sticky Session — 임시방편임을 알고 쓰기

로드밸런서가 같은 사용자를 같은 서버로 고정하는 방식. 코드 수정 없이
당장은 동작하지만, 1절의 문제(scale-in·배포 시 세션 소실, 부하 편중)를
하나도 해결하지 못한다. "왜 임시방편인지"를 설명할 수 있어야 하고,
면접에서는 마이그레이션 과도기 전략 정도로만 언급하는 것이 안전하다.

## 3. 실무 사례 — 세션 말고도 서버를 Stateful로 만드는 것들

"세션은 Redis로 뺐으니 우리 서버는 stateless"라고 안심하면 안 된다.
로컬 상태는 여러 얼굴로 숨어 있다:

```java
// 함정 1: 업로드 파일을 로컬 디스크에 저장
file.transferTo(new File("/data/uploads/" + filename));
// → 다운로드 요청이 다른 서버로 가면 404.
//    해결: S3 같은 오브젝트 스토리지로.

// 함정 2: 인메모리 캐시/카운터
private final Map<Long, Integer> viewCountBuffer = new ConcurrentHashMap<>();
// → 서버마다 값이 제각각, scale-in 시 유실.
//    해결: Redis 카운터 or 메시지 큐로.

// 함정 3: 스케줄러
@Scheduled(cron = "0 0 * * * *")
public void settle() { ... }
// → 서버가 3대면 3번 실행(중복 정산!).
//    해결: 분산 락(ShedLock 등) or 별도 배치 인스턴스로 분리.
```

**공통 패턴**: 상태를 없애는 게 아니라 **상태 있는 전용 계층**(Redis,
오브젝트 스토리지, MQ, DB)으로 몰아넣고, 애플리케이션 서버 계층만
stateless로 유지하는 것이다. 그래서 "확장의 병목은 결국 상태 있는
계층(DB, Redis)으로 수렴한다"까지 언급하면 가산점 포인트.

## 4. 꼬리질문 대비 포인트

### "Sticky session으로도 동작하는데 굳이 외부 저장소가 필요한가요?"

동작하는 것과 확장에 안전한 것은 다르다. sticky session은
① scale-in·배포·서버 장애 때 그 서버에 고정된 사용자들의 세션이
전부 소실되고, ② 특정 서버에 헤비 유저가 몰리면 부하가 편중되어
로드밸런싱 효과가 깨지며, ③ 오토스케일링으로 서버를 늘려도 기존
사용자는 기존 서버에 묶여 있어 **새 서버가 부하를 나눠 받지 못한다.**
즉 "확장했는데 확장 효과가 없는" 상태가 된다.

### "JWT와 Redis 세션 중 무엇을 선택하나요?" (시니어 변별 포인트)

기준은 **"즉시 무효화 요구가 있는가"**다.

- 강제 로그아웃, 계정 탈취 대응, 동시 접속 제한처럼 서버가 세션을
  능동적으로 끊어야 하는 요구가 있으면 → **Redis 세션**. 서버가
  상태의 주인이어야 제어할 수 있다.
- 서비스 간 인증 전달(MSA), 모바일 API처럼 매 요청 저장소 조회를
  줄이고 싶고 무효화는 "짧은 access token 만료(수 분~수십 분)로
  충분히 감수 가능"하면 → **JWT + refresh token**.
- 실무에서는 절충형이 흔하다: access token은 JWT로 stateless하게
  검증하고, refresh token만 저장소에 두어 무효화 지점을 확보한다.
  "JWT를 쓰는 순간 무효화라는 상태 관리가 완전히 사라지는 게 아니라
  refresh token 계층으로 이동한다"고 말하면 트레이드오프를 이해한
  답변이 된다.

### "세션 저장소 Redis가 죽으면 전 사용자 로그인이 풀리는데, 어떻게 대비하나요?"

세션을 한곳에 모으면 그곳이 단일 장애 지점(SPOF)이 된다.
① replication + 자동 failover(Sentinel/Cluster)로 저장소 자체를
고가용성으로 만들고, ② 장애 시나리오를 등급화한다 — 세션 조회 실패를
전체 500 에러로 만들지 말고, 비로그인으로 강등해 열람 같은 핵심 기능은
살리는 graceful degradation을 설계할 수 있다(서비스 성격에 따라).
"Redis로 뺐다"에서 끝나지 않고 "뺀 곳의 장애까지 설계했다"가
한 단계 위의 답변이다.

### "완전한 stateless 시스템이 가능한가요?"

불가능하다. 상태(주문, 회원, 세션)가 있어야 서비스가 성립한다.
Stateless 설계의 본질은 상태 제거가 아니라 **상태의 재배치** —
수평 확장이 쉬운 계산 계층(애플리케이션 서버)에서 상태를 걷어내
상태 관리에 특화된 계층(DB, Redis, 오브젝트 스토리지)으로 몰아넣는
것이다. 그래서 확장 논의의 다음 단계는 항상 "그럼 그 상태 계층은
어떻게 확장하나"(replication, 샤딩, 캐싱)로 이어진다.

### "세션 외에 스케일 아웃을 막는 로컬 상태의 예를 들어보세요."

3절 그대로: 로컬 디스크의 업로드 파일(→ 오브젝트 스토리지),
인메모리 캐시·카운터(→ Redis/MQ), 다중 인스턴스에서 중복 실행되는
스케줄러(→ 분산 락 또는 배치 분리), 그리고 WebSocket처럼 연결 자체가
특정 서버에 붙는 경우(→ 메시지 브로커로 서버 간 브로드캐스트)까지
언급하면 실전 경험이 있는 답변으로 들린다.

---

## 한 줄 요약

Stateless 설계는 서버들을 완전히 동일한 교체 가능 부품으로 만들어
scale-out·scale-in·배포·장애 격리를 전부 안전하게 만드는
**확장의 전제 조건**이고, 세션 같은 상태는 없애는 게 아니라
공유 저장소(Redis)나 클라이언트(토큰)로 **옮기는 것**이다 —
상태는 사라지지 않고, 관리하기 좋은 계층으로 이동할 뿐이다.
