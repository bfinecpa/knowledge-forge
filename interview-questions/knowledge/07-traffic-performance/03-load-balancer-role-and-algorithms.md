# 로드밸런서 — 역할과 알고리즘, "특정 서버만 부하가 몰릴 때" 푸는 열쇠

> 핵심 관전 포인트: **로드밸런서는 여러 서버에 트래픽을 나눠주는 분배기이자,
> 헬스체크로 죽은 서버를 자동으로 빼는 장애 격리 장치이며, scale-out의
> 유일한 진입점이다. 분배 알고리즘은 round robin(순서대로 한 대씩)이
> 기본이지만, 이는 "모든 요청의 처리 시간이 비슷하다"는 가정 위에서만
> 공평하다. 요청별 처리 시간 편차가 크면(무거운 조회, long-polling 혼재)
> 순번은 공평해도 부하는 불공평해진다 — 이때 현재 연결 수가 가장 적은
> 서버로 보내는 least connection이 필요하다. LB를 블랙박스로 두면
> "서버 스펙이 같은데 왜 한 대만 힘들지?"를 영원히 못 푼다.**

---

## 0. 질문 + 의도

**질문**: "로드밸런서의 역할과 알고리즘(round robin, least connection)을 설명해주세요."

**출제 의도**: least connection이 필요한 상황(요청별 처리 시간 편차)을
아는지 본다. LB를 블랙박스로 두면 "특정 서버만 부하가 몰리는" 현상을
영원히 못 푼다 — 알고리즘의 가정이 깨지는 지점을 아는 사람만이 그
장애를 진단할 수 있다.

## 1. 로드밸런서의 역할 — 분배기 그 이상

로드밸런서(LB)는 클라이언트와 서버 무리 사이에 서서 요청을 나눠주는
장치다. 역할은 크게 세 가지다.

1. **트래픽 분산**: 요청을 여러 서버에 나눠 한 대의 한계를 넘는
   처리량을 만든다. scale-out(서버 증설)이 실제로 동작하려면
   "늘어난 서버로 트래픽을 보내주는 입구"가 반드시 필요하다 —
   LB가 그 입구다.
2. **장애 격리 (헬스체크)**: 주기적으로 각 서버에 확인 요청을 보내
   응답하지 않는 서버를 분배 대상에서 자동으로 뺀다. 서버 한 대가
   죽어도 사용자는 모르게 지나가는 것, 무중단 배포에서 구 버전을
   하나씩 빼고 새 버전을 넣는 것 모두 이 메커니즘 위에서 돌아간다.
3. **공통 관심사의 집결지**: TLS 종료(암호화 해제를 LB에서 한 번만),
   요청 라우팅(경로별로 다른 서버 그룹), 그리고 rate limiting이나
   load shedding 같은 방어 로직을 두기 가장 싼 위치다.

- 비유: 은행 창구 안내원이다. 손님(요청)을 빈 창구(서버)로 보내고,
  자리를 비운 창구(죽은 서버)로는 보내지 않으며, "대출 상담은 2층"
  (경로 라우팅)도 안내한다.

**L4와 L7의 구분** (한 줄로): L4 LB는 IP·포트만 보고 TCP 연결 단위로
분배하고(빠르고 단순), L7 LB는 HTTP를 해석해 URL·헤더·쿠키 기준으로
분배한다(정교하지만 비용 있음). Nginx, ALB가 L7의 대표다.

## 2. 알고리즘 — 각자의 "공평함"과 그 가정

### Round Robin — 순번의 공평함

서버 목록을 돌면서 한 대씩 차례로 보낸다. 구현이 단순하고 상태 추적이
필요 없으며, **모든 요청의 처리 비용이 비슷하다면** 결과도 공평하다.
서버 스펙이 다르면 가중치를 줘서(weighted round robin) 좋은 서버에
더 보낼 수 있다.

문제는 가정이 깨질 때다. 요청마다 처리 시간이 1초 vs 100ms로 갈리는
서비스에서 RR은 순번만 공평할 뿐, 운 나쁘게 무거운 요청을 연달아 받은
서버에는 **미완료 요청이 계속 쌓인다**. RR은 "지금 저 서버가 얼마나
바쁜지"를 전혀 보지 않기 때문이다.

### Least Connection — 현재 상태를 보는 공평함

요청이 올 때마다 **현재 활성 연결 수가 가장 적은 서버**로 보낸다.
활성 연결 수는 "그 서버가 아직 못 끝낸 일의 양"의 근사치이므로,
처리 시간이 들쭉날쭉해도 부하가 자동으로 평준화된다. 오래 물고 있는
연결(파일 업로드, long-polling, 무거운 리포트 조회)이 섞여 있는
서비스라면 이쪽이 맞다.

대가는 상태 추적이다. LB가 서버별 연결 수를 계속 세야 하므로 RR보다
복잡하고, LB가 여러 대로 분산돼 있으면 각자 자기가 보낸 연결만 알아서
집계가 부정확해질 수 있다.

```nginx
# Before: 기본 round robin — 처리 시간 편차가 크면 부하 쏠림
upstream api_servers {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    server 10.0.1.13:8080;
    # 문제: 무거운 요청을 연달아 받은 서버에 미완료 작업이 누적돼도
    #       순번은 계속 돌아온다 → 그 서버만 응답 지연·스레드풀 고갈
}

# After: least_conn — 미완료 연결이 적은(한가한) 서버부터 채움
upstream api_servers {
    least_conn;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    server 10.0.1.13:8080;
    # 효과: 요청별 처리 시간이 달라도 "밀린 일의 양" 기준으로 분배돼
    #       특정 서버 쏠림이 구조적으로 완화된다
}
```

(가산점 포인트) 이 둘 외에 언급하면 좋은 것: **IP hash / consistent
hashing**은 같은 클라이언트(또는 같은 키)를 항상 같은 서버로 보내는
방식으로, 로컬 캐시 적중이나 세션 유지가 필요할 때 쓴다. **least
response time** 계열은 연결 수 대신 최근 응답 시간까지 반영한다.

## 3. 실무 사례 — "스펙이 같은데 한 대만 죽는" 미스터리

이 질문의 출제 의도가 겨냥하는 실제 장애 패턴 두 가지.

**사례 1 — RR + 처리 시간 편차**: 일반 조회(수십 ms)와 대용량 정산
다운로드(수십 초)가 같은 서버 그룹에 섞여 있었다. RR이라 다운로드
요청도 균등하게 순환 분배됐지만, 하필 다운로드가 몰린 서버는 스레드가
장시간 점유돼 일반 조회까지 느려졌다. 지표를 보면 "서버 3번만 p99가
튀는" 모양 — 원인은 서버가 아니라 **분배 알고리즘의 가정 붕괴**다.
처방은 least connection 전환, 또는 무거운 API를 별도 서버 그룹으로
분리(라우팅)하는 것.

**사례 2 — 연결 단위 분배의 함정**: 클라이언트가 keep-alive나
gRPC(HTTP/2)처럼 **연결 하나를 오래 재사용**하면, 연결 시점에만
분배가 일어나고 이후 수만 건의 요청이 전부 같은 서버로 간다. 서버를
증설해도 기존 연결은 안 옮겨가서 새 서버가 논다. 처방은 L7에서
요청 단위로 분배하거나, 연결에 수명을 줘 주기적으로 재수립하게
하는 것. "LB가 무엇을 단위로 분배하는가(연결 vs 요청)"를 아는지가
이 장애의 진단 가능 여부를 가른다.

## 4. 꼬리질문 대비 포인트

### "헬스체크는 어떻게 설정하나요? 잘못 설정하면 어떤 일이 생기나요?"

두 축이다. **무엇을 확인하나** — 포트가 열렸는지만 보는 얕은 체크보다,
애플리케이션이 실제 응답 가능한지 보는 HTTP 체크(예: `/health`)가
낫다. 단, 헬스 엔드포인트가 DB까지 찌르게 만들면 DB 순단에 전 서버가
동시에 "불건강" 판정돼 전체가 분리되는 참사가 난다 — 자기 프로세스의
생존과 의존성 상태는 분리해서 판단해야 한다. **얼마나 민감하게** —
너무 민감하면(1회 실패로 제외) 일시 지연에 서버가 들락날락하고
(flapping), 너무 둔감하면 죽은 서버로 트래픽이 계속 간다. 연속 N회
실패 시 제외, 연속 M회 성공 시 복귀처럼 히스테리시스를 둔다.

### "least connection이 항상 round robin보다 좋은 것 아닌가요?" (시니어 변별 포인트)

아니다. ① **연결 수 ≠ 부하**다 — 연결 수는 같아도 어떤 요청은 CPU를
태우고 어떤 요청은 대기만 한다. 근사치일 뿐이다. ② **처리 시간이
균일한 서비스**라면 RR과 결과가 같으면서 상태 추적 비용만 낸다.
③ LB가 여러 대일 때 각 LB는 자기 로컬 연결 수만 보므로 전역적으론
부정확하다. ④ 갓 투입된 서버는 연결 수 0이라 트래픽이 순간에 몰리는
문제(워밍업 전 폭주)가 있어, 신규 서버에 점진적으로 트래픽을 올리는
slow start와 함께 써야 안전하다. "무엇이 좋냐"가 아니라 "우리 요청
분포가 어느 가정에 맞냐"로 답하는 게 시니어의 답이다.

### "sticky session(세션 고정)은 언제 쓰고, 왜 피하라고 하나요?"

같은 사용자를 항상 같은 서버로 보내는 설정이다. 서버 메모리에 세션을
두는 레거시를 당장 못 고칠 때의 응급 처치로는 유효하지만, 근본적으로
분배 균형을 깨고(특정 서버에 무거운 사용자가 고정), 그 서버가 죽으면
해당 사용자들의 세션이 통째로 날아가며, scale-in도 어렵게 만든다.
정석은 세션을 외부 저장소(Redis 등)로 빼서 서버를 stateless로 만들고
LB는 자유롭게 분배하게 하는 것 — stateless 설계 질문과 한 몸이다.

### "L4와 L7 로드밸런서는 어떻게 다르고 무엇을 쓰나요?"

L4는 TCP/UDP 수준에서 IP·포트만 보고 연결을 통째로 넘긴다 — 해석을
안 하니 빠르고 대용량에 강하다. L7은 HTTP를 해석하므로 경로·헤더 기반
라우팅, 요청 단위 분배, 재시도·서킷브레이커 같은 정교한 제어가 된다.
실전에서는 겹쳐 쓴다: 맨 앞에 L4(또는 DNS/애니캐스트)로 대량 유입을
받고, 그 뒤 L7 게이트웨이가 서비스별로 정교하게 분배하는 구성이
일반적이다.

### "로드밸런서 자체가 단일 장애점(SPOF)이 되지 않나요?"

된다 — 그래서 LB도 이중화한다. 액티브-스탠바이 쌍을 두고 가상
IP(VIP)를 넘겨받는 방식, 또는 DNS에 LB 여러 대를 등록하는 방식이
전형적이다. 클라우드 관리형 LB(ALB 등)는 이 이중화를 서비스가 대신
해준다. "분배기를 누가 분배하나"라는 재귀 질문에 DNS → L4 → L7의
계층 구조로 답하면 구조를 이해하고 있다는 신호가 된다.

## 한 줄 요약

로드밸런서는 트래픽 분산 + 헬스체크 기반 장애 격리 + 공통 방어 로직의
집결지이고, round robin은 "요청 비용이 균일하다"는 가정 위의 순번
공평, least connection은 처리 시간 편차가 클 때 미완료 작업량 기준으로
분배하는 상태 기반 공평이다 — 알고리즘의 가정이 깨지는 지점을 알아야
"특정 서버만 부하가 몰리는" 장애를 풀 수 있다.
