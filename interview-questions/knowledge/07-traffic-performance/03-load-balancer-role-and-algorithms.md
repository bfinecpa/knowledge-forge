# 로드밸런서 — 역할과 알고리즘, "특정 서버만 부하가 몰릴 때" 푸는 열쇠

> 핵심 관전 포인트: **로드밸런서는 여러 서버에 트래픽을 나눠주는 분배기이자, 헬스체크로 죽은 서버를 자동으로 빼는 장애 격리 장치이며, scale-out의 유일한 진입점이다. 분배 알고리즘은 round robin(순서대로 한 대씩)이 기본이지만, 이는 "모든 요청의 처리 시간이 비슷하다"는 가정 위에서만 공평하다 — 무거운 요청과 가벼운 요청이 번갈아 들어오면 순번은 4:4로 공평한데 서버가 실제로 일한 시간은 10:1로 벌어진다. 이때 필요한 것이 "미완료 요청 수"(LB가 보내놓고 아직 응답을 못 받은 요청 수)가 가장 적은 서버로 보내는 least connection이다. 단 이 지표도 근사치라, keep-alive로 연결이 오래 재사용되거나 long-polling·SSE처럼 오래 열려 있으면서 일은 안 하는 연결이 섞이면 "연결 수"가 작업량을 대변하지 못한다. 그리고 헬스체크는 민감도가 양쪽으로 다 위험하다 — 너무 민감하면 정상 서버가 들락날락하고, 너무 둔감하면 죽은 서버로 계속 보내며, 헬스체크가 DB까지 확인하게 만들면 DB 순단에 전 서버가 동시에 빠져 서비스가 통째로 내려간다. LB를 블랙박스로 두면 "서버 스펙이 같은데 왜 한 대만 힘들지?"를 영원히 못 푼다.**

---

## 0. 질문 + 의도

**질문**: "로드밸런서의 역할과 알고리즘(round robin, least connection)을 설명해주세요."

**출제 의도**: least connection이 필요한 상황(요청별 처리 시간 편차)을 아는지 본다. LB를 블랙박스로 두면 "특정 서버만 부하가 몰리는" 현상을 영원히 못 푼다 — 알고리즘의 가정이 깨지는 지점을 아는 사람만이 그 장애를 진단할 수 있다.

## 1. 로드밸런서의 역할 — 분배기 그 이상

### 1-1. 전제 지식 — scale-out은 "입구"가 없으면 성립하지 않는다

서버가 한 대일 때는 로드밸런서라는 말을 들을 일이 없다. 클라이언트가 `api.example.com`을 DNS로 조회하면 그 한 대의 IP가 나오고, 요청은 거기로 간다. 단순하다.

서버를 두 대로 늘리는 순간 새 문제가 생긴다. **"어느 IP를 알려줄 것인가."** 클라이언트가 서버 목록을 알고 직접 고르게 만들 수는 없다 — 서버가 늘거나 줄 때마다 전 세계 클라이언트를 고쳐야 하고, 죽은 서버를 클라이언트가 알아서 피할 방법도 없다.

그래서 **"클라이언트에게는 항상 같은 하나의 주소를 주고, 그 주소 뒤에서 실제 서버를 골라 넘겨주는 중간 계층"**을 둔다. 이것이 로드밸런서(LB)다. 즉 LB는 성능을 위한 부가 장치가 아니라, **scale-out을 성립시키는 구조적 전제**다. 서버를 100대로 늘려도 LB가 그쪽으로 트래픽을 보내주지 않으면 99대는 그냥 전기만 쓴다(2번 문서의 수평 확장은 이 계층이 있다는 가정 위에 서 있다).

비유를 하나 두자. LB는 **은행 창구 안내원**이다. 손님(요청)을 빈 창구(서버)로 보내고, 자리를 비운 창구(죽은 서버)로는 보내지 않으며, "대출 상담은 2층"(경로 라우팅)도 안내한다. 손님은 창구가 몇 개인지, 어느 창구가 쉬는지 알 필요가 없다 — 안내원만 보면 된다.

역할은 크게 세 가지이고, 하나씩 본다.

### 1-2. 역할 ① 트래픽 분산 — 한 대의 한계를 넘는다

요청을 여러 서버에 나눠 한 대의 처리 한계를 넘는 처리량을 만든다. 이것이 가장 먼저 떠오르는 역할이고, 실제로 이 하나만으로도 LB의 존재 이유는 충분하다.

여기서 짚어야 할 것은 **"무엇을 단위로 나누는가"**다. 요청 단위로 나누는지, TCP 연결 단위로 나누는지에 따라 같은 트래픽이 전혀 다르게 분배된다. 이 구분이 1-5의 L4/L7이고, 3-4의 장애를 진단하는 열쇠가 된다. "LB가 요청을 나눠준다"는 문장을 무비판적으로 받아들이면 이 함정에 걸린다.

### 1-3. 역할 ② 헬스체크 기반 장애 격리 — 그리고 그 설정이 만드는 두 방향의 사고

**헬스체크(health check)**는 LB가 각 서버에 주기적으로 "너 살아 있냐"를 확인하고, 응답하지 못하는 서버를 분배 대상에서 자동으로 빼는 장치다. 서버 한 대가 죽어도 사용자는 모르게 지나가는 것, 롤링 배포에서 구 버전을 하나씩 빼고 새 버전을 넣는 것이 전부 이 메커니즘 위에서 돌아간다.

문제는 이 장치가 **양방향으로 위험하다**는 점이다. 헬스체크를 잘못 설정하면 없을 때보다 나쁠 수 있다.

**(1) 너무 민감하면 정상 서버가 빠진다.** GC로 300ms 멈춘 서버, 순간적으로 지연이 튄 서버가 "죽었다"고 판정돼 제외된다. 그러면 남은 서버들이 그 몫까지 받아 더 느려지고, 그 서버들도 헬스체크에 실패하기 시작한다. 서버가 들락날락하는 이 현상을 **플래핑(flapping, 펄럭임)**이라 부르고, 최악의 경우 **전 서버가 순차적으로 빠져 LB 뒤에 아무도 남지 않는다.**

**(2) 너무 둔감하면 죽은 서버로 계속 보낸다.** 30초에 한 번 확인하고 5회 연속 실패해야 뺀다면, 서버가 죽은 뒤 최대 150초 동안 트래픽의 1/N이 계속 허공으로 간다. 계산으로 보면 바로 드러난다 — **최악의 방치 시간 = 확인 주기 × 실패 임계 횟수**다. 30초 × 5회 = 150초. 이 곱셈을 해보지 않고 기본값을 쓰면 "장애는 격리했는데 2분 반 동안 사용자는 에러를 봤다"가 된다.

**(3) 그리고 가장 위험한 실수 — 헬스체크가 의존성까지 확인하는 경우.** 헬스 엔드포인트가 DB에 쿼리를 던져 보고 결과에 따라 200/503을 내려주게 만들면, 논리적으로는 그럴듯하다("DB를 못 쓰면 일을 못 하니 트래픽 받지 말자"). 그런데 DB는 **모든 서버가 공유하는 자원**이다.

```
[DB가 3초 순단했을 때 벌어지는 일]

  DB 순단
    |
    v
  서버 1 헬스체크 실패 ─┐
  서버 2 헬스체크 실패 ─┼─ 전부 같은 원인이므로 "동시에" 실패한다
  서버 3 헬스체크 실패 ─┘
    |
    v
  LB: 살아 있는 서버가 0대 -> 모든 요청 503
    |
    v
  DB는 3초 뒤 복구됐는데, 서버들은 헬스체크 성공 임계(연속 M회)를
  다시 채우기까지 복귀하지 못한다 -> 장애가 DB 순단보다 길어진다
```

**공유 의존성의 짧은 장애를 전면 장애로 증폭시킨 것이다.** 원래라면 "DB 관련 API만 3초 실패하고 나머지는 정상"이었을 사고가, 헬스체크 한 줄 때문에 "전 서비스 다운"이 됐다.

그래서 원칙은 이렇다. **LB가 보는 헬스체크는 "이 프로세스가 요청을 받을 수 있는 상태인가"만 판정하고, 의존성 상태는 별도 엔드포인트로 분리해 사람과 모니터링이 본다.** 판정의 결과가 "트래픽 제외"라는 되돌리기 어려운 행동으로 이어지는 경우에는, 그 판정에 **나 혼자만의 사정**만 넣어야 한다.

Spring Boot에서는 Actuator가 이 분리를 그대로 제공한다.

```yaml
# Before: 헬스체크 하나에 전부 넣은 설정 — DB 순단이 전면 장애가 된다
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      show-details: always
# /actuator/health 는 기본적으로 DataSource, Redis 등 등록된 모든
# HealthIndicator를 합산한다. DB가 죽으면 이 엔드포인트가 503을 내려주고,
# 이걸 LB 헬스체크로 쓰면 전 서버가 동시에 분배 대상에서 빠진다.
```

```yaml
# After: liveness / readiness 를 나누고, LB에는 "자기 사정"만 보여준다
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      probes:
        enabled: true
      # probes.enabled=true 를 켜면 두 엔드포인트가 따로 열린다.
      #   /actuator/health/liveness  — "프로세스가 살아 있나" (실패 시 재시작 대상)
      #   /actuator/health/readiness — "지금 트래픽을 받아도 되나" (실패 시 분배 제외)
      group:
        liveness:
          include: livenessState
          # 여기에 DB를 넣으면 DB 장애로 컨테이너가 재시작된다. 최악의 조합이다.
        readiness:
          include: readinessState
          # 기동 완료 여부만 본다. db, redis 를 여기 넣지 않는 것이 이 설정의 요점.
          # 공유 의존성 장애는 "전 서버 동시 제외"로 증폭되기 때문이다.
      show-details: never   # 헬스 엔드포인트는 인증 없이 노출되므로 내부 정보를 감춘다
```

두 프로브의 역할이 왜 다른지는 **실패했을 때 시스템이 취하는 행동**으로 구분하면 명확하다. liveness 실패의 처방은 **재시작**이고, readiness 실패의 처방은 **트래픽 제외**다. 재시작은 되돌릴 수 없는 데다 진행 중인 요청을 죽이므로, liveness는 readiness보다 훨씬 둔감해야 한다.

쿠버네티스 환경이라면 민감도가 프로브 설정으로 드러난다.

```yaml
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  periodSeconds: 5        # 5초마다 확인
  timeoutSeconds: 2       # 2초 안에 응답 없으면 실패로 센다
  failureThreshold: 3     # 연속 3회 실패해야 제외 -> 순간 지연 한 번에 흔들리지 않는다
  successThreshold: 2     # 연속 2회 성공해야 복귀 -> 복귀 직후 다시 빠지는 진동을 막는다
  # 최악의 방치 시간 = 5초 x 3회 = 15초. 이 곱셈을 해보고 SLO와 견줘 정한다.

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  periodSeconds: 10
  failureThreshold: 6     # 10초 x 6회 = 60초. readiness보다 훨씬 둔감하게 잡는다.
  # 이유: 이쪽 실패의 결과는 "재시작"이라 되돌릴 수 없다.
  #       일시적 지연으로 재시작을 유발하면 스스로 장애를 만든다.
```

여기서 쓴 **"연속 N회 실패 시 제외, 연속 M회 성공 시 복귀"**라는 구조를 **히스테리시스(hysteresis)**라고 부른다. 넣는 기준과 빼는 기준을 일부러 다르게 잡아 경계선 근처에서 상태가 진동하지 않게 하는 기법이고, 온도조절기가 설정 온도 정확히 하나로 켜고 끄지 않고 위아래로 여유를 두는 것과 같은 원리다.

nginx만 놓고 보면 한 가지 사실을 정확히 알아야 한다. **오픈소스 nginx의 기본 헬스체크는 능동(active)이 아니라 수동(passive)이다.** 별도의 확인 요청을 보내는 게 아니라, **실제 사용자 요청이 실패하는 것을 세어** 판정한다.

```nginx
upstream api_servers {
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=10s;
    # max_fails=3, fail_timeout=10s 의 뜻은 두 가지가 한 쌍이다.
    #   ① 10초 안에 실패가 3번 누적되면 그 서버를 "장애"로 판정한다.
    #   ② 판정되면 그 뒤 10초 동안 분배 대상에서 제외한다.
    # 즉 fail_timeout 은 "실패를 세는 창"과 "제외 기간"을 겸한다.
    #
    # max_fails=0 은 "절대 제외하지 않는다"는 뜻이다. 헬스체크를
    # 끄는 설정이라, 죽은 서버로 계속 보내게 된다.
}
```

능동적 헬스체크(`health_check` 디렉티브)와 신규 서버에 트래픽을 서서히 올리는 `slow_start`는 상용 버전(NGINX Plus)의 기능이다. 오픈소스 nginx만 쓴다면 그 역할을 **앞단의 클라우드 LB(ALB 등)나 쿠버네티스 readiness probe**가 맡는 구성이 일반적이다. 이 경계를 모르고 "nginx에 health_check 넣으면 되죠"라고 답하면 실제로 설정해 본 적이 없다는 신호가 된다.

### 1-4. 역할 ③ 공통 관심사의 집결지

모든 요청이 반드시 지나가는 지점이라는 성질 때문에, LB는 **모든 서버에 공통으로 적용할 일을 한 번만 처리하기 가장 싼 위치**가 된다.

**TLS 종료(TLS termination)**가 대표적이다. HTTPS 암호를 푸는 연산을 LB에서 한 번만 하고 뒤로는 평문(또는 내부 전용 암호화)으로 넘기면, 서버 N대가 각자 복호화 비용을 내지 않는다. 인증서 갱신도 LB 한 곳에서 끝난다.

**경로 라우팅**도 여기 있다. `/api/**`는 API 서버 그룹으로, `/images/**`는 이미지 서버 그룹으로 보내는 식이다. 이것이 3-3 사례의 처방 중 하나가 된다 — 무거운 API를 아예 다른 서버 그룹으로 격리하는 것.

**rate limiting과 load shedding** 같은 방어 로직도 LB가 최적의 위치다. 애플리케이션에서 막으면 이미 스레드와 커넥션을 소비한 뒤이지만, LB에서 막으면 그 요청은 애플리케이션에 도달조차 하지 않는다(각각 8번, 21번 문서).

### 1-5. L4와 L7 — "무엇을 단위로 분배하는가"의 차이

이름의 숫자는 OSI 계층 번호다. **L4는 전송 계층(TCP/UDP)까지만 보고, L7은 응용 계층(HTTP)까지 해석한다.** 이 차이가 곧 분배 단위의 차이로 이어진다.

**L4 LB**는 IP와 포트만 보고 **TCP 연결을 통째로** 한 서버에 넘긴다. HTTP를 해석하지 않으므로 빠르고 대용량에 강하다. 대신 한 번 연결이 어느 서버로 정해지면 **그 연결 위에 흐르는 모든 요청이 같은 서버로 간다.**

**L7 LB**는 HTTP를 해석하므로 **요청 하나하나를 따로** 분배할 수 있다. URL·헤더·쿠키로 라우팅하고, 요청 단위 재시도나 서킷 브레이킹 같은 정교한 제어가 가능하다. 대가는 해석 비용과 지연이다. nginx, ALB, Envoy가 L7의 대표다.

```
[L4 — 연결 단위 분배]
  클라이언트 --TCP 연결 1개 개설--> LB --> 서버 A
                                          그 연결의 요청 1..10,000건 전부 A로
  (분배 판단이 "연결을 맺는 순간" 딱 한 번 일어난다)

[L7 — 요청 단위 분배]
  클라이언트 --TCP 연결 1개 개설--> LB
                                     ├─ 요청 1 --> 서버 A
                                     ├─ 요청 2 --> 서버 B
                                     └─ 요청 3 --> 서버 C
  (분배 판단이 "요청마다" 일어난다)
```

이 그림이 3-4의 장애를 그대로 설명한다. **연결을 오래 재사용하는 클라이언트 + L4 = 사실상 분배가 없다.**

실전에서는 둘을 겹쳐 쓴다. 맨 앞에서 L4(또는 DNS·애니캐스트)로 대량 유입을 받고, 그 뒤 L7 게이트웨이가 서비스별로 정교하게 분배하는 구성이 일반적이다.

### 1-6. LB 자신은 단일 장애점이 아닌가 — 계층으로 답한다

모든 요청이 반드시 지나간다는 것은, **LB가 죽으면 서버가 다 살아 있어도 서비스가 죽는다**는 뜻이다. LB는 정의상 단일 장애점(SPOF, single point of failure) 후보다.

그래서 LB도 이중화한다. 전형적인 방식은 **가상 IP(VIP) 인수**다. 액티브 LB와 스탠바이 LB를 쌍으로 두고, 클라이언트에게 알려준 IP는 물리 장비의 IP가 아니라 둘 사이를 옮겨 다닐 수 있는 가상 IP로 잡는다. 액티브가 죽으면 스탠바이가 그 IP를 인수하므로 클라이언트가 보는 주소는 바뀌지 않는다.

"그러면 분배기를 누가 분배하나"라는 재귀 질문이 남는데, 답은 **계층을 올라가는 것**이다.

```
DNS (여러 LB의 IP를 등록, 또는 애니캐스트로 같은 IP를 여러 지점에 광고)
  |
  v
L4 LB (이중화된 쌍, VIP 인수) — 대량 유입을 받는다
  |
  v
L7 게이트웨이 (여러 대, 위 계층이 분배해 준다)
  |
  v
애플리케이션 서버 N대
```

각 계층은 자기 아래를 분배하고, 자기 자신의 이중화는 위 계층이 담당한다. 맨 위인 DNS는 애초에 여러 IP를 돌려줄 수 있으므로 재귀가 여기서 끝난다. 클라우드 관리형 LB(ALB, NLB 등)는 이 이중화를 서비스가 내부적으로 대신 해주므로, 사용자는 "이중화됐다"는 사실만 알면 된다.

## 2. 알고리즘 — 각자의 "공평함"과 그 가정

여기서 반드시 붙잡아야 할 관점이 하나 있다. **모든 분배 알고리즘은 "무엇이 공평인가"에 대한 서로 다른 정의이고, 각 정의는 특정 가정 위에서만 실제 부하 균등으로 이어진다.** 알고리즘을 고르는 일은 "좋은 것 고르기"가 아니라 **"우리 요청 분포가 어느 가정에 맞는지 판정하기"**다.

### 2-1. Round Robin — 순번의 공평함, 그리고 그 가정

서버 목록을 돌면서 한 대씩 차례로 보낸다. 상태를 하나도 추적하지 않으므로 구현이 가장 단순하고, LB의 기본값인 경우가 많다.

RR이 정의하는 공평은 **"받은 요청 개수가 같다"**다. 그리고 개수의 공평이 부하의 공평이 되려면 조건이 하나 필요하다 — **모든 요청의 처리 비용이 비슷해야 한다.** 요청 하나가 다 같은 무게라면 개수를 똑같이 나누는 것이 곧 일을 똑같이 나누는 것이다.

서버 스펙이 서로 다르면 이 정의를 조금 비틀어 **가중 라운드 로빈(weighted round robin)**을 쓴다. 좋은 서버에 순번을 더 자주 준다.

```nginx
upstream api_servers {
    server 10.0.1.11:8080 weight=3;   # 3배 좋은 장비라 3번에 한 번씩이 아니라
    server 10.0.1.12:8080 weight=1;   # 4번 중 3번을 받는다
    # 가중치는 "장비 성능 차이"를 보정할 뿐, "요청 무게 차이"는 보정하지 못한다.
}
```

문제는 가정이 깨질 때다. 그런데 이 문장을 말로만 하면 감이 오지 않으므로 숫자로 세워 보자.

### 2-2. 가정이 깨지는 순간 — 요청 8건으로 손으로 따라가기

무거운 요청과 가벼운 요청이 번갈아 들어오는 상황을 잡는다. 조건을 최대한 단순하게 고정한다.

```
[전제]
  - 서버 2대(A, B). 스펙 동일.
  - 요청은 100ms 간격으로 8건 도착한다.
  - 요청 종류가 번갈아 나온다.
      H = 무거운 요청 (처리 1,000ms) — 예: 정산 내역 대용량 조회
      L = 가벼운 요청 (처리   100ms) — 예: 프로필 단건 조회
  - 서버는 동시에 여러 건을 처리할 수 있다(스레드풀이 넉넉하다고 본다).

도착 시각   0      100    200    300    400    500    600    700
요청       R1(H)  R2(L)  R3(H)  R4(L)  R5(H)  R6(L)  R7(H)  R8(L)
RR 배정      A      B      A      B      A      B      A      B
```

배정만 보고 이미 문제가 보인다. **요청 종류가 2건 주기로 반복되고 서버가 2대이므로, 순번과 무게의 주기가 딱 맞아떨어져 무거운 요청이 전부 A로 간다.** 시간축에 그리면 이렇다.

```
[서버 A — 무거운 요청만 4건]
  R1  ████████████████████                        (   0 -> 1,000)
  R3      ████████████████████                    ( 200 -> 1,200)
  R5          ████████████████████                ( 400 -> 1,400)
  R7              ████████████████████            ( 600 -> 1,600)
                                    t=700 시점 A의 미완료 요청 = 4건

[서버 B — 가벼운 요청만 4건]
  R2   ██                                          ( 100 ->   200)
  R4       ██                                      ( 300 ->   400)
  R6           ██                                  ( 500 ->   600)
  R8               ██                              ( 700 ->   800)
                                    t=700 시점 B의 미완료 요청 = 1건
```

두 서버가 실제로 일한 시간을 더해 본다.

```
서버 A 누적 처리 시간 = 1,000ms x 4건 = 4,000ms
서버 B 누적 처리 시간 =   100ms x 4건 =   400ms

받은 요청 개수 : 4건 : 4건        <- RR의 기준으로는 완벽하게 공평하다
실제 일한 시간 : 4,000ms : 400ms  <- 실제 부하는 10배 차이다
```

**순번은 공평했는데 부하는 10:1로 벌어졌다.** RR은 "지금 저 서버가 얼마나 바쁜지"를 전혀 보지 않기 때문이다. 이것이 알고리즘의 가정이 깨진다는 말의 실체다.

지금까지는 스레드풀이 무한하다고 가정했으므로 응답 시간에는 차이가 없었다. **스레드풀이 유한해지는 순간 이 누적 차이가 곧 응답 시간 차이로 바뀐다.** 서버당 워커 스레드가 2개뿐이라고 놓고 A를 다시 그려 보자.

```
[서버 A, 워커 스레드 2개]
  스레드1:  R1 (    0 -> 1,000)  |  R5 (1,000 -> 2,000)
  스레드2:  R3 (  200 -> 1,200)  |  R7 (1,200 -> 2,200)

  R5는 t=400에 도착했지만 빈 스레드가 없어 1,000까지 대기 -> 응답 1,600ms
  R7은 t=600에 도착했지만 빈 스레드가 없어 1,200까지 대기 -> 응답 1,600ms
  (대기 600ms + 처리 1,000ms = 1,600ms)

[서버 B, 워커 스레드 2개]
  가벼운 요청이 200ms 간격으로 들어오고 처리가 100ms이므로 대기가 없다.
  -> 응답 100ms
```

**같은 스펙의 서버인데 A의 응답시간이 1,600ms, B가 100ms다.** 그리고 무거운 요청이 계속 들어오면 A의 대기 큐는 무한히 자라 결국 스레드풀 고갈에 이른다. 지표만 보는 사람 눈에는 "서버 A만 p99가 튀고 스레드풀이 마른다"로 보이고, 서버를 재부팅해도 재현된다. **원인은 서버가 아니라 분배 알고리즘의 가정 붕괴다.**

### 2-3. Least Connection — "연결 수"가 정확히 무엇을 세는가

요청이 올 때마다 **현재 연결 수가 가장 적은 서버**로 보낸다. 이름만 들으면 무엇을 세는지 애매하니 여기서 정의를 못 박자.

**least connection이 세는 "연결 수"는 "LB가 그 서버로 보내놓고 아직 응답을 다 받지 못한 요청 수"다.** 보냈지만 아직 끝나지 않은 것들의 개수 — 그래서 **미완료 요청 수(in-flight)**라고 부르는 편이 오해가 적다. 서버의 CPU 사용률이나 스레드 상태를 물어보는 것이 아니다. LB가 자기가 보낸 것과 받은 것을 세어 뺀 값일 뿐이다.

이 값이 좋은 지표인 이유는 **처리 시간을 몰라도 처리 시간의 결과가 자동으로 반영된다**는 데 있다. 무거운 요청을 받은 서버는 그것이 끝나지 않는 동안 미완료 수가 계속 1을 유지하므로, LB가 "저 서버는 아직 바쁘다"는 것을 요청 종류를 몰라도 알게 된다. **관측값이 가정을 대신하는 구조**다.

같은 8건을 least connection으로 다시 배정해 보면 차이가 눈에 보인다. 동수일 때는 앞선 서버를 고른다고 하자.

```
도착 t   요청     그 순간의 미완료 수        선택   이유
─────────────────────────────────────────────────────────────
    0    R1(H)    A=0, B=0                   A     동수 -> 앞선 서버
  100    R2(L)    A=1(R1), B=0               B     B가 적다
  200    R3(H)    A=1(R1), B=0 (R2 종료)     B     B가 적다
  300    R4(L)    A=1(R1), B=1(R3)           A     동수
  400    R5(H)    A=1(R1), B=1(R3)           A     동수 (R4가 400에 종료)
  500    R6(L)    A=2(R1,R5), B=1(R3)        B     B가 적다
  600    R7(H)    A=2(R1,R5), B=1 (R6 종료)  B     B가 적다
  700    R8(L)    A=2(R1,R5), B=2(R3,R7)     A     동수

누적 처리 시간
  서버 A = R1(1,000) + R4(100) + R5(1,000) + R8(100) = 2,200ms
  서버 B = R2(  100) + R3(1,000) + R6(100) + R7(1,000) = 2,200ms
```

**2,200ms 대 2,200ms — 완전히 균등해졌다.** RR에서 4,000 대 400이던 것이 알고리즘 한 줄로 바로잡혔다. 그리고 이 결과를 얻는 데 LB는 어느 요청이 무거운지 **전혀 알 필요가 없었다.** 미완료 수라는 관측값만 봤다.

```nginx
# Before: 기본 round robin — 처리 시간 편차가 크면 부하 쏠림
upstream api_servers {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    server 10.0.1.13:8080;
    # 문제: 무거운 요청을 연달아 받은 서버에 미완료 작업이 누적돼도
    #       순번은 계속 돌아온다 -> 그 서버만 응답 지연·스레드풀 고갈
}

# After: least_conn — 미완료 요청이 적은(한가한) 서버부터 채운다
upstream api_servers {
    least_conn;
    zone api_servers 64k;
    # zone 이 없으면 미완료 수 집계가 워커 프로세스별로 따로 유지된다.
    # nginx 워커가 8개면 각 워커가 자기가 보낸 것만 세어 8개의 부분 시야로
    # 판단하는 셈이 되므로, 공유 메모리 존을 잡아 집계를 하나로 모은다.

    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=10s;
    # 효과: 요청별 처리 시간이 달라도 "밀린 일의 양" 기준으로 분배돼
    #       특정 서버 쏠림이 구조적으로 완화된다
}
```

대가는 **상태 추적**이다. LB가 서버별 미완료 수를 계속 세고 갱신해야 하므로 RR보다 무겁고, 방금 본 `zone` 문제처럼 **집계 범위가 곧 판단의 정확도**가 된다. LB가 여러 대로 분산돼 있으면 각 LB는 자기가 보낸 요청만 알기 때문에 전역적으로는 부정확할 수밖에 없다.

### 2-4. 함정 — "연결 수"가 작업량을 대변하지 못할 때

여기가 이 문서에서 가장 중요한 지점이다. least connection의 미완료 요청 수는 어디까지나 **작업량의 근사치**이고, 그 근사가 무너지는 상황이 실무에 흔하다.

**(1) 오래 열려 있지만 일은 하지 않는 연결.** long-polling(응답을 보내지 않고 붙잡고 있다가 이벤트가 생기면 응답하는 방식), SSE(Server-Sent Events, 서버가 한 응답 스트림으로 계속 밀어 보내는 방식), WebSocket이 그렇다. 이 연결들은 **몇 분에서 몇 시간 동안 미완료 상태로 남아 있으면서 CPU는 거의 쓰지 않는다.**

```
서버 A: SSE 연결 5,000개 (전부 대기 중, CPU 사용률 5%)
서버 B: 정산 집계 요청 3개 (CPU 사용률 95%)

LB의 눈에 보이는 미완료 수:  A = 5,000,  B = 3
LB의 판단: "B가 한가하다" -> 새 요청을 전부 B로 보낸다
실제:      B는 이미 죽어가고, A는 놀고 있다
```

**미완료 수가 많은 쪽이 오히려 한가하고, 적은 쪽이 죽어가는 완전한 역전**이다. 이 경우 least connection은 RR보다 나쁘다. 처방은 알고리즘 튜닝이 아니라 **분리**다 — 실시간 연결을 받는 서버 그룹과 일반 API 서버 그룹을 아예 다른 upstream으로 나눈다. 성격이 다른 트래픽을 한 풀에 섞은 것이 근본 원인이다.

**(2) HTTP keep-alive로 재사용되는 연결.** keep-alive는 요청 하나가 끝나도 TCP 연결을 끊지 않고 다음 요청에 재사용하는 것이다. 왕복 비용을 아끼는 좋은 기능이지만, **"연결 개수"와 "처리 중인 요청 개수"의 관계를 끊어 놓는다.** 연결은 열려 있는데 그 위에 아무 요청도 안 흐르는 순간이 대부분이고, 반대로 HTTP/2라면 연결 하나에 요청 수십 개가 동시에 흐른다.

그래서 LB가 세는 대상이 **TCP 연결**인지 **미완료 요청**인지가 결정적이다. L7 LB는 요청을 해석하므로 미완료 요청을 셀 수 있지만, **L4 LB는 연결만 볼 수 있다.** L4에서 least connection을 켜면 "연결 수가 적은 서버"로 보내는데, 그 연결 하나가 초당 수천 요청을 실어 보내는 중일 수 있다.

**(3) 갓 투입된 서버는 미완료 수가 0이다.** 배포나 오토스케일링으로 새 서버가 들어오면 미완료 수가 0이므로, least connection은 **다른 서버들이 균형에 도달할 때까지 새 요청을 전부 그 서버에만 보낸다.** 그런데 새 서버는 JIT 컴파일 전이고, 캐시가 비어 있고, 커넥션 풀도 아직 안 늘어난 상태다. **가장 약한 서버에 가장 많은 트래픽이 순간적으로 몰린다.** 이것이 신규 서버가 투입 직후 죽는 전형적인 경로이고, 대응은 신규 서버에 트래픽을 서서히 올리는 **slow start**(NGINX Plus의 `slow_start`, ALB 대상 그룹의 slow start 설정)다.

**이 세 함정이 전부 문서 제목의 "특정 서버만 부하가 몰릴 때"와 직결된다.** least connection으로 바꿨는데도 쏠림이 남거나 오히려 심해졌다면, 세는 대상이 작업량을 대변하지 못하는 경우가 아닌지 먼저 의심한다.

### 2-5. 그 외 알고리즘 — 해시 계열과 응답시간 계열 (가산점 포인트)

**IP hash / consistent hashing**은 **같은 클라이언트(또는 같은 키)를 항상 같은 서버로 보내는** 방식이다. 부하 균등이 목표가 아니라 **목적지의 일관성**이 목표라는 점에서 앞의 둘과 성격이 다르다. 서버 로컬 캐시의 적중률을 높이거나(같은 사용자의 요청이 같은 서버로 가면 그 서버 캐시에 이미 데이터가 있다), 세션을 서버 메모리에 둔 레거시를 지탱할 때 쓴다.

```nginx
# ① IP 기준 — 클라이언트 IP를 해시해 서버를 고정한다
upstream api_servers {
    ip_hash;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    # 주의 1: nginx는 IPv4의 앞 3옥텟만 해시 키로 쓴다. 같은 /24 대역의
    #         사용자들이 한 서버로 뭉치므로, 회사·통신사 NAT 뒤의 대규모
    #         사용자가 한 서버에 쏠릴 수 있다.
    # 주의 2: 서버 대수가 바뀌면 나머지 연산의 분모가 바뀌어 대부분의
    #         키가 다른 서버로 재배치된다 -> 캐시 전부 미스, 세션 전부 소실.
}

# ② 임의 키 기준 + consistent — 서버 대수 변화의 충격을 줄인다
upstream api_servers {
    hash $arg_userId consistent;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    # consistent 를 붙이면 일관된 해싱(consistent hashing)을 쓴다.
    # 서버 한 대가 빠질 때 그 서버가 맡던 키만 재배치되고 나머지는
    # 그대로 유지된다 — 나머지 연산 방식의 "전면 재배치"를 피하는 것이
    # 이 알고리즘의 존재 이유다.
}
```

**least response time 계열**은 미완료 수 대신 **최근 응답 시간까지 반영**한다. 미완료 수가 같아도 실제로 더 빨리 응답해 온 서버를 선호하므로, 서버 간 성능 편차나 일시적 저하를 더 잘 반영한다. 대가는 더 많은 상태 추적과, 응답 시간 측정 창을 어떻게 잡느냐에 따른 민감도 문제다.

### 2-6. Sticky Session — 분배를 일부러 포기하는 선택

**sticky session(세션 고정)**은 같은 사용자를 항상 같은 서버로 보내는 설정이다. LB의 본업이 분배인데 그 분배를 일부러 제한하는 것이니, 왜 그런 선택을 하는지부터 알아야 한다.

이유는 하나다. **서버가 상태를 자기 메모리에 들고 있어서, 다른 서버로 가면 그 상태가 없기 때문이다.** 톰캣 기본 설정의 `HttpSession`이 대표적이다. 로그인 정보가 1번 서버 메모리에 있는데 다음 요청이 2번 서버로 가면 비로그인 취급을 받는다. sticky session은 **원인(로컬 상태)을 그대로 두고 증상만 막는** 처방이다.

응급 처치로는 유효하다. 코드를 한 줄도 안 고치고 당장 동작하게 만들 수 있다. 하지만 대가가 크다.

그 서버가 죽으면 **그 서버에 고정돼 있던 사용자들의 세션이 통째로 날아간다.** 무거운 사용자가 한 서버에 고정되면 **분배 균형이 깨진다.** 오토스케일링으로 서버를 늘려도 **기존 사용자는 기존 서버에 묶여 있어 새 서버가 부하를 나눠 받지 못한다.** scale-in도 어려워진다 — 서버를 내리는 것이 곧 사용자 강제 로그아웃이기 때문이다.

정석은 세션을 서버 밖 공유 저장소로 빼서 서버를 stateless로 만들고, LB는 자유롭게 분배하게 하는 것이다. **이 문서의 04번 문서(stateless 서버 설계)와 한 몸인 주제**이고, sticky session은 그 마이그레이션 과도기의 임시 수단으로 위치를 정해 두는 것이 정확하다.

## 3. 실무 사례 — "스펙이 같은데 한 대만 죽는" 미스터리

이 질문의 출제 의도가 겨냥하는 실제 장애 패턴이다. 증상은 언제나 같은 모양으로 나타난다 — **"서버 3대가 완전히 동일한 스펙·동일한 이미지인데, 유독 한 대만 p99가 튀거나 스레드풀이 마르거나 재시작된다."**

이 증상 하나에 원인 후보가 여럿이므로, **관측 순서를 정해 두고 분기로 좁히는 것**이 진단의 본체다. 원인을 하나로 단정하고 시작하면 대개 틀린다.

### 3-1. 진단 순서 — 어떤 지표를 어떤 순서로 보는가

순서에 원칙이 있다. **분배가 이상한지(LB의 문제) → 분배는 정상인데 내용이 이상한지(요청 종류의 문제) → 둘 다 정상인데 서버가 이상한지(서버 자체 문제)** 순으로 좁힌다. 뒤로 갈수록 조사 비용이 크므로 싼 것부터 본다.

**① 서버별 요청 수** — 가장 먼저 본다. 같은 시간 창에서 각 서버가 받은 요청 건수다. 이것이 균등한지 아닌지가 **"LB가 나눠주기는 제대로 했는가"**에 대한 답이고, 첫 갈림길이 된다. LB 액세스 로그의 upstream 주소별 집계나, 서버별 요청 카운터 지표로 본다.

**② 서버별 미완료 요청 수 / 활성 연결 수** — 요청 수는 균등한데 미완료 수만 한쪽에 쌓여 있으면, 들어온 개수는 같은데 **끝나지 않는 것들이 한쪽에 몰려 있다**는 뜻이다.

**③ 서버별 응답시간 분포(p50과 p99를 함께)** — p50까지 같이 높으면 그 서버의 모든 요청이 느린 것이고(서버 자체 문제 의심), p50은 같은데 p99만 높으면 **일부 요청만 무겁다**는 뜻이다(요청 종류 편중 의심). 평균만 보면 이 구분이 지워진다(1번 문서).

**④ 서버별 요청 종류 분포** — ③에서 p99만 튀었다면 여기가 결정적이다. 엔드포인트별로 쪼개서, 무거운 API가 특정 서버에 몰렸는지 본다.

**⑤ 서버별 스레드풀 활성 수·대기 큐 길이, 커넥션 풀 대기** — 자원 고갈이 실제로 일어났는지 확인한다. 2-2의 계산이 현실에서 어떻게 보이는지가 이 지표다.

**⑥ 서버별 CPU·GC·디스크·이웃 부하** — 여기까지 와서야 "서버 자체가 이상한가"를 본다. 같은 스펙이라도 물리 호스트를 공유하는 다른 워크로드가 자원을 뺏는 경우(노이지 네이버), GC 설정이 다르게 적용된 경우, 특정 서버만 디스크가 느린 경우가 있다.

### 3-2. 분기 — 무엇이 관측되면 무엇을 의심하는가

위 지표들의 조합이 원인 후보를 가른다.

```
"한 대만 힘들다"
│
├─[①] 서버별 요청 수가 균등한가?
│   │
│   ├─ 아니오 (한 서버에 요청이 몰린다)
│   │   └─ 분배 자체가 안 되고 있다. 후보:
│   │      · 연결 단위 분배 + keep-alive/HTTP2 (3-4) — L4인지, 클라이언트가
│   │        연결을 재사용하는지 확인
│   │      · sticky session이 켜져 있다 — 설정 확인
│   │      · ip_hash 계열의 키 편중 — NAT 뒤 대규모 사용자가 한 대역인지
│   │      · 다른 서버가 헬스체크로 빠져 있었다 — 이때는 "한 대만 힘들다"가
│   │        아니라 "한 대만 남아 있었다"다. LB의 서버 제외 이력을 먼저 본다
│   │
│   └─ 예 (요청 수는 균등하다)
│       │
│       └─[②③④] 무엇이 한쪽에 쏠려 있는가?
│           │
│           ├─ 미완료 요청 수만 쏠림 -> 오래 끝나지 않는 연결이 그 서버에 고정
│           │   후보: SSE·WebSocket·long-polling·대용량 업로드/다운로드
│           │   (2-4의 함정. least_conn이면 오히려 이 서버를 피해 버린다)
│           │
│           ├─ p99만 쏠림 + 무거운 API 비중이 높다 -> RR + 처리 시간 편차 (3-3)
│           │
│           ├─ p50까지 함께 높다 -> 서버 자체 문제 의심 -> [⑥]으로
│           │   후보: 노이지 네이버, GC 이상, 디스크, 커널/설정 드리프트
│           │
│           └─ 방금 투입된 서버다 -> least_conn + 미완료 수 0 -> 워밍업 전 폭주
│               (2-4의 세 번째 함정. slow start로 대응)
│
└─[전 서버 동시 상승] LB 문제가 아니다.
    후보: 공유 자원 포화 — DB, 캐시, 외부 API, 공용 커넥션 풀
    이 경우 서버별 편차를 아무리 봐도 답이 없다 (6번 문서로)
```

이 트리에서 실무적으로 가장 값진 줄은 마지막이다. **"전 서버가 같이 나빠졌다"면 LB나 서버가 아니라 뒷단 공유 자원을 봐야 한다.** 편차가 없는 문제를 편차 지표로 쫓는 시간이 장애 대응에서 가장 많이 낭비되는 시간이다.

### 3-3. 사례 1 — RR + 처리 시간 편차

일반 조회(수십 ms)와 대용량 정산 다운로드(수십 초)가 같은 서버 그룹에 섞여 있었다. RR이라 다운로드 요청도 균등하게 순환 분배됐지만, 하필 다운로드가 몰린 서버는 스레드가 장시간 점유돼 **그 서버에 온 일반 조회까지 느려졌다.**

지표는 3-2의 분기 그대로 나온다. 서버별 요청 수는 균등하다. p50은 세 서버가 비슷한데 **서버 3번만 p99가 튄다.** 엔드포인트별로 쪼개 보면 그 시간대에 정산 다운로드가 3번 서버에 집중돼 있다. 2-2에서 계산한 상황이 실제 지표로 나타난 것이다.

처방은 세 가지이고, 근본적인 쪽으로 갈수록 뒤에 있다.

**① least connection으로 전환.** 가장 싼 처방이다. 2-3의 계산대로 미완료 작업량 기준으로 분배되므로 쏠림이 구조적으로 완화된다. 다만 2-4의 함정에 해당하지 않는지 먼저 확인해야 한다.

**② 무거운 API를 별도 서버 그룹으로 분리.** 경로 라우팅으로 정산 다운로드를 전용 그룹에 보낸다. 이쪽이 근본적이다 — **성격이 다른 트래픽을 한 풀에 섞은 것 자체가 원인**이므로, 알고리즘을 바꾸는 것은 섞인 상태를 더 잘 견디게 만드는 것이고 분리는 섞지 않는 것이다. 무거운 요청이 폭주해도 일반 조회는 다른 그룹에서 멀쩡하다는 격리 효과까지 얻는다(벌크헤드, 18번 문서).

```nginx
# 무거운 API를 전용 upstream으로 격리한다
upstream api_light {
    least_conn;
    zone api_light 64k;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
}

upstream api_heavy {
    least_conn;
    zone api_heavy 64k;
    server 10.0.2.21:8080 max_fails=3 fail_timeout=10s;
    server 10.0.2.22:8080 max_fails=3 fail_timeout=10s;
}

server {
    listen 80;

    location /api/settlements/export {
        proxy_pass http://api_heavy;
        proxy_read_timeout 120s;   # 무거운 쪽만 긴 타임아웃을 허용한다
        # 격리의 효과: 이 API가 폭주해 api_heavy가 마비돼도
        #             일반 조회는 api_light에서 정상 응답한다
    }

    location /api/ {
        proxy_pass http://api_light;
        proxy_read_timeout 5s;     # 일반 API는 짧게 잡아 빨리 실패시킨다
    }
}
```

**③ 무거운 작업을 요청-응답에서 떼어낸다.** 다운로드 요청을 받으면 즉시 접수 응답을 주고, 실제 생성은 비동기 작업으로 넘긴 뒤 완료되면 알린다. 애초에 스레드를 수십 초 점유하는 요청을 없애는 것이므로 가장 근본적이다.

### 3-4. 사례 2 — 연결 단위 분배의 함정

클라이언트가 keep-alive나 gRPC(HTTP/2)처럼 **연결 하나를 오래 재사용**하면, 분배 판단이 **연결을 맺는 순간에만 한 번** 일어나고 이후 그 연결 위의 수만 건 요청이 전부 같은 서버로 간다. 1-5의 도식이 그대로 현실이 되는 경우다.

이 사례의 지표는 3-2의 첫 갈림길에서 바로 갈린다. **서버별 요청 수 자체가 불균등하다.** RR로 설정해 뒀는데도 그렇다 — RR이 나눈 것은 요청이 아니라 연결이기 때문이다.

특히 고약한 변형이 **서버 증설 후에도 새 서버가 노는 것**이다. 기존 연결은 계속 유지되므로 옮겨가지 않고, 새 연결이 생길 때만 새 서버가 몫을 받는다. 클라이언트가 내부 서비스이고 연결을 영구적으로 유지한다면 새 서버는 영원히 논다.

처방은 셋이다.

**① L7에서 요청 단위로 분배한다.** HTTP/2·gRPC를 이해하는 L7 프록시(nginx, Envoy 등)를 두어 하나의 클라이언트 연결에서 온 요청들을 여러 서버로 나눈다. 근본 처방이다.

**② 연결에 수명을 준다.** 서버나 LB에서 연결의 최대 요청 수와 최대 지속 시간을 제한해, 주기적으로 재수립되게 만든다. 재수립될 때마다 분배가 다시 일어나므로 시간이 지나면 균형이 잡힌다.

```nginx
# nginx가 클라이언트 연결을 붙잡는 정도를 제한한다
http {
    keepalive_timeout  30s;     # 유휴 연결을 30초 뒤 닫는다
    keepalive_requests 1000;    # 연결 하나로 1,000건을 처리하면 닫는다
    # 이 두 값이 곧 "분배 판단이 다시 일어나는 주기"다. 무한히 재사용되면
    # 분배는 최초 1회로 끝나므로, 상한을 두는 것 자체가 분배 정책이 된다.
}
```

**③ 클라이언트 쪽 커넥션 풀에도 같은 상한을 준다.** gRPC나 HTTP 클라이언트 라이브러리에 연결 최대 수명 설정이 있으면 함께 잡는다. 서버만 닫으면 클라이언트가 즉시 새로 열어 같은 서버로 다시 붙을 수도 있으므로, 양쪽을 함께 봐야 한다.

**"LB가 무엇을 단위로 분배하는가(연결 vs 요청)"를 아는지가 이 장애의 진단 가능 여부를 가른다.** 알고리즘 설정만 들여다보면 영원히 못 찾는다 — 설정은 RR로 정상이기 때문이다.

## 4. 꼬리질문 대비 포인트

### "헬스체크는 어떻게 설정하나요? 잘못 설정하면 어떤 일이 생기나요?"

두 축으로 답한다(1-3).

**무엇을 확인하나** — 포트가 열렸는지만 보는 얕은 체크(TCP 연결 성공 여부)는 프로세스가 살아만 있으면 통과하므로, 애플리케이션이 실제로 응답 가능한지 보는 HTTP 체크가 낫다. 단, **헬스 엔드포인트가 DB까지 찌르게 만들면 DB 순단에 전 서버가 동시에 불건강 판정돼 전체가 분리되는 참사가 난다.** 공유 의존성의 짧은 장애가 전면 장애로 증폭되는 구조다. 자기 프로세스의 생존과 의존성 상태는 분리해서 판단해야 하고, Spring Boot라면 `/actuator/health/liveness`와 `/actuator/health/readiness`를 나누고 readiness 그룹에 `db`를 넣지 않는 것이 그 분리의 구현이다.

**얼마나 민감하게** — 너무 민감하면(1회 실패로 제외) 일시 지연에 서버가 들락날락하고(flapping), 심하면 전 서버가 순차적으로 빠진다. 너무 둔감하면 죽은 서버로 트래픽이 계속 간다. **최악의 방치 시간 = 확인 주기 × 실패 임계 횟수**로 계산해 SLO와 견줘 정하고, 연속 N회 실패 시 제외·연속 M회 성공 시 복귀라는 히스테리시스를 둬 경계에서 진동하지 않게 한다.

여기에 한 단계 더 얹으면 좋은 것이 **두 프로브의 실패 처방 차이**다. liveness 실패의 결과는 재시작, readiness 실패의 결과는 트래픽 제외다. 재시작은 되돌릴 수 없으니 liveness를 더 둔감하게 잡아야 하고, **liveness에 의존성을 넣으면 DB 장애로 전 컨테이너가 재시작되는** 최악의 조합이 된다.

### "least connection이 항상 round robin보다 좋은 것 아닌가요?" (시니어 변별 포인트)

아니다. 네 가지 이유가 있고, 앞의 둘은 "지표의 한계", 뒤의 둘은 "구현의 한계"다.

**① 연결 수 ≠ 부하다.** least connection이 세는 것은 미완료 요청 수일 뿐, 그 요청이 CPU를 태우는지 그냥 대기 중인지는 모른다. SSE 연결 5,000개를 들고 있는 서버(CPU 5%)와 집계 요청 3건을 처리하는 서버(CPU 95%)를 비교하면 LB는 후자가 한가하다고 판단한다 — **근사가 역전되는 구간**이다(2-4).

**② 처리 시간이 균일한 서비스라면 RR과 결과가 같다.** 그러면서 상태 추적 비용만 낸다. 요청 무게가 고른 서비스에서 least connection은 이득 없는 복잡도다.

**③ LB가 여러 대면 집계가 부정확하다.** 각 LB는 자기가 보낸 요청만 세므로 전역 미완료 수를 모른다. nginx 안에서도 공유 메모리 존을 안 잡으면 워커 프로세스별로 따로 세어 부분 시야로 판단한다.

**④ 갓 투입된 서버는 미완료 수가 0이라 트래픽이 순간에 몰린다.** 가장 준비가 안 된 서버(JIT 미최적화, 캐시 콜드, 커넥션 풀 미확장)에 가장 많은 요청이 가는 역설이므로, 신규 서버에 점진적으로 트래픽을 올리는 slow start와 함께 써야 안전하다.

**"무엇이 좋냐"가 아니라 "우리 요청 분포가 어느 가정에 맞냐"로 답하는 게 시니어의 답이다.** 여기에 한 가지 더 붙이면 좋다 — **알고리즘 선택보다 트래픽 분리가 근본 처방인 경우가 많다.** 성격이 다른 요청을 한 upstream에 섞어 두고 알고리즘으로 해결하려는 것 자체가 설계 문제일 수 있다.

### "sticky session(세션 고정)은 언제 쓰고, 왜 피하라고 하나요?"

같은 사용자를 항상 같은 서버로 보내는 설정이다. **서버가 상태를 자기 메모리에 들고 있다는 원인은 그대로 두고 증상만 막는 처방**이라는 점이 핵심이다.

서버 메모리에 세션을 두는 레거시를 당장 못 고칠 때의 응급 처치로는 유효하다. 코드 변경이 0이다. 하지만 대가가 넷이다. 분배 균형이 깨지고(특정 서버에 무거운 사용자가 고정), 그 서버가 죽으면 **고정된 사용자들의 세션이 통째로** 날아가며, 오토스케일링으로 늘린 새 서버는 기존 사용자를 받지 못해 **확장 효과가 나지 않고**, scale-in은 곧 사용자 강제 로그아웃이 된다.

정석은 세션을 외부 저장소(Redis 등)로 빼서 서버를 stateless로 만들고 LB는 자유롭게 분배하게 하는 것 — **04번 문서(stateless 설계)와 한 몸이다.**

한 단계 더 파고들면 **고정 방식의 차이**를 말할 수 있다. LB가 발급한 쿠키로 고정하는 방식은 사용자 단위로 정확하지만 쿠키를 못 쓰는 클라이언트에서 깨지고, IP 해시로 고정하는 방식은 쿠키가 필요 없지만 NAT 뒤 사용자들이 한 서버로 뭉치고 모바일 IP 변경 시 고정이 풀린다. 그리고 **고정된 서버를 내릴 때의 드레이닝** — 신규 고정은 받지 않고 기존 고정 사용자의 세션이 만료되기를 기다리는 절차 — 가 반드시 필요한데, 이 대기 시간이 세션 만료 시간만큼 길어진다는 점까지 말하면 실제로 운영해 본 답변으로 들린다.

### "L4와 L7 로드밸런서는 어떻게 다르고 무엇을 쓰나요?"

L4는 TCP/UDP 수준에서 IP·포트만 보고 **연결을 통째로** 넘긴다 — 해석을 안 하니 빠르고 대용량에 강하다. L7은 HTTP를 해석하므로 경로·헤더 기반 라우팅, **요청 단위 분배**, 재시도·서킷브레이커 같은 정교한 제어가 된다.

실전에서는 겹쳐 쓴다. 맨 앞에 L4(또는 DNS/애니캐스트)로 대량 유입을 받고, 그 뒤 L7 게이트웨이가 서비스별로 정교하게 분배하는 구성이 일반적이다.

이 질문에서 변별이 갈리는 지점은 **"차이가 실제로 어떤 장애로 나타나는가"**다. 분배 단위가 연결이라는 것은 곧 **분배 판단이 연결당 한 번뿐**이라는 뜻이고, 클라이언트가 keep-alive나 HTTP/2로 연결을 오래 재사용하면 사실상 분배가 사라진다(3-4). 서버를 증설해도 기존 연결이 옮겨가지 않아 새 서버가 노는 것도 같은 원인이다. 또 L7만이 요청 단위 재시도를 안전하게 할 수 있다 — L4는 연결이 끊긴 뒤에 그 위의 요청이 처리됐는지 안 됐는지 알 방법이 없다.

### "로드밸런서 자체가 단일 장애점(SPOF)이 되지 않나요?"

된다 — 모든 요청이 반드시 지나가는 지점이니 정의상 SPOF 후보다. 그래서 LB도 이중화한다.

전형적인 방식은 **액티브-스탠바이 쌍 + 가상 IP(VIP) 인수**다. 클라이언트에게 알려준 IP를 물리 장비가 아니라 둘 사이를 옮겨 다닐 수 있는 가상 IP로 잡아 두면, 액티브가 죽어도 스탠바이가 그 IP를 인수하므로 클라이언트가 보는 주소는 바뀌지 않는다. DNS에 LB 여러 대를 등록하는 방식도 쓴다. 클라우드 관리형 LB(ALB 등)는 이 이중화를 서비스가 대신 해준다.

**"분배기를 누가 분배하나"라는 재귀 질문에 DNS → L4 → L7의 계층 구조로 답하면 구조를 이해하고 있다는 신호가 된다** — 각 계층은 자기 아래를 분배하고 자기 이중화는 위 계층이 맡으며, 맨 위의 DNS는 애초에 여러 IP를 돌려줄 수 있으므로 재귀가 여기서 끝난다.

한 걸음 더 나가면 **"이중화했어도 남는 문제"**를 말할 수 있다. 페일오버에는 시간이 걸리므로 그 사이 요청은 실패하고, 클라이언트나 중간 DNS 캐시가 옛 IP를 붙들고 있으면 복구가 더 늦어진다. 그리고 액티브 한 대의 용량으로 전체 트래픽을 받고 있었다면, **스탠바이도 같은 용량을 상시 확보해 두지 않으면 페일오버 직후에 그쪽이 무너진다.** 이중화는 "죽어도 되게" 만드는 것이지 "죽어도 아무 일 없게" 만드는 것이 아니다.

## 한 줄 요약

로드밸런서는 트래픽 분산 + 헬스체크 기반 장애 격리 + 공통 방어 로직의 집결지이고, round robin은 "요청 비용이 균일하다"는 가정 위의 순번 공평(무거운·가벼운 요청이 번갈아 오면 순번 4:4에 부하 4,000ms:400ms), least connection은 미완료 요청 수를 관측해 처리 시간 편차를 자동으로 흡수하는 상태 기반 공평(같은 8건이 2,200ms:2,200ms로 균등해진다)이다 — 다만 그 미완료 수도 근사치라 keep-alive·SSE·신규 서버 앞에서 역전되고, 헬스체크는 민감도가 양쪽으로 위험하며 의존성까지 확인하게 만들면 공유 장애를 전면 장애로 증폭시키므로, 알고리즘의 가정이 깨지는 지점을 알아야 "특정 서버만 부하가 몰리는" 장애를 풀 수 있다.
