# CDN — 오리진 앞의 방패, 웹툰 이미지 트래픽을 엣지에서 끝내기

> 핵심 관전 포인트: **CDN은 전 세계(또는 전국)에 분산된 엣지 서버가
> 콘텐츠를 캐싱해 사용자와 가까운 곳에서 대신 응답하는 계층이다.
> 효과는 두 방향 — 사용자에게는 지연시간 감소, 서버(오리진)에게는
> 유입 트래픽 자체의 구조적 감소. "여러 사용자가 같은 것을 반복해서
> 요청하고, 그 내용이 잘 변하지 않을 때" 가장 효과적인데, 웹툰 이미지가
> 정확히 그 경우다 — 한 번 발행되면 불변이고, 인기작 한 회차를 수십만
> 명이 본다. 이 도메인에서 트래픽의 대부분은 이미지이므로, 캐시 히트율
> 1%가 서버 코드 최적화보다 오리진 부하에 더 크게 작용한다.**

---

## 0. 질문 + 의도

**질문**: "CDN은 무엇이고 언제 효과적인가요? (웹툰 이미지 서빙 관점에서)"

**출제 의도**: 웹툰 도메인에서 트래픽의 대부분은 이미지다. 오리진까지
오는 트래픽을 구조적으로 줄이는 계층을 이해해야 "서버 최적화보다
캐시 히트율 1% 올리는 게 크다" 같은 우선순위 판단이 가능하다 —
애플리케이션 코드 안만 보는 사람인지, 요청이 서버에 도달하기 전의
계층까지 보는 사람인지를 가리는 질문이다.

## 1. CDN이란 — "요청이 서버에 도착하기 전에 끝내는 계층"

CDN(Content Delivery Network)은 지리적으로 분산 배치된
**엣지 서버들의 캐시 네트워크**다. 동작은 단순하다:

1. 사용자의 요청이 가장 가까운 엣지 서버로 라우팅된다.
2. 엣지에 캐시가 있으면(**cache hit**) 오리진(내 서버)까지 가지 않고
   엣지가 바로 응답한다.
3. 없으면(**cache miss**) 엣지가 오리진에서 받아와 응답하고,
   그 사본을 캐시해 둔다 — 이후 같은 요청은 전부 hit.

- 비유: 오리진은 파주의 **중앙 물류창고**, 엣지는 동네
  **편의점**이다. 라면(인기 콘텐츠) 사러 모두가 파주까지 갈 필요 없이
  동네에서 사간다. 편의점에 없는 물건만 창고에서 가져온다.

효과는 두 방향으로 정리해서 말해야 한다:

- **사용자 관점 — 지연시간 감소**: 물리적 거리가 줄어든다. 특히 이미지
  같은 대용량 전송은 왕복 시간(RTT)의 영향이 커서 체감 차이가 크다.
- **서버 관점 — 오리진 보호**: 히트한 요청은 오리진에 **도달 자체를
  안 한다.** 히트율 99%라면 오리진은 전체 트래픽의 1%만 감당하면 된다.
  대역폭 비용 절감도 여기서 나온다.

면접에서 사용자 관점만 말하는 답변이 흔한데, 이 질문의 맥락
(대용량 트래픽 섹션)에서는 **오리진 보호가 본론**이다.

## 2. 언제 효과적인가 — 판단 기준은 "재사용률 × 불변성"

CDN 캐시가 힘을 쓰는 조건은 두 가지다:

1. **여러 사용자가 같은 콘텐츠를 요청한다** (재사용률이 높다)
2. **콘텐츠가 잘 변하지 않는다** (캐시를 오래 믿을 수 있다)

웹툰 이미지는 이 두 조건의 교과서적 사례다:

- 한 번 발행된 회차 이미지는 **사실상 불변**이다 (수정되면 새 파일로
  올리면 된다).
- 인기작 신작 회차는 공개 직후 **수십만 명이 완전히 동일한 이미지들**을
  내려받는다 — 캐시 한 번 채우면 나머지는 전부 엣지에서 끝난다.

반대로 효과가 없거나 역효과인 경우도 말할 수 있어야 한다:

- **개인화된 응답** — "내 서재", "내 코인 잔액" 같은 사용자별로 다른
  API 응답은 재사용률이 0에 가깝다. 캐시해봤자 아무도 재사용 안 한다.
- **실시간성이 강한 데이터** — 댓글 수, 실시간 랭킹처럼 초 단위로 변하는
  것은 캐시 신선도 관리 비용이 이득을 상쇄한다 (아주 짧은 TTL로
  절충하는 기법은 4절 꼬리질문 참고).

## 3. 웹툰 이미지 서빙 설계 — 실무 디테일

### ① 불변 URL + 긴 캐시: "무효화하지 말고 URL을 바꿔라"

캐시 정책의 핵심은 헤더다. 잘못된 설정과 올바른 설정의 대비:

```http
# Before: 캐시를 사실상 무력화하는 응답 헤더
GET /episodes/1234/image_01.jpg
Cache-Control: no-cache        # 매번 오리진에 재검증 → CDN이 있으나 마나

# After: 콘텐츠 해시(버전)를 URL에 포함 + 불변 선언
GET /episodes/1234/01_a3f8c2.jpg
Cache-Control: public, max-age=31536000, immutable
# → 1년간 재검증 없이 엣지에서 응답.
#   이미지를 수정해야 하면? 파일 내용이 바뀌면 해시가 바뀌므로
#   새 URL이 됨 → 구 캐시는 자연히 안 쓰이게 됨 (무효화 불필요)
```

**버전드 URL(versioned URL)** 전략이 핵심 가산점 포인트다:
"콘텐츠가 바뀌면 URL도 바뀐다"는 규칙을 세우면 캐시 무효화(purge)라는
어려운 문제가 통째로 사라지고, max-age를 마음껏 길게 줄 수 있다.

### ② 유료 콘텐츠 보호 — Signed URL

이미지를 CDN에 태우면 URL만 알면 누구나 볼 수 있게 되는 문제가 생긴다.
유료 회차는 **서명된 URL(signed URL)**로 보호한다 — 애플리케이션 서버가
"이 사용자는 구매자"임을 확인한 뒤, 만료 시각과 서명이 붙은 URL을
발급하고, CDN 엣지가 서명을 검증한다. **권한 판단은 오리진(서버)이,
전송은 엣지가** 하는 역할 분담이다.

### ③ 신작 공개 순간의 cache miss 폭주 대비

공개 직전에는 엣지에 캐시가 하나도 없다. 공개 순간 수십만 요청이
전부 miss가 되어 오리진으로 쏟아지는 것을 막는 장치:

- **사전 워밍(cache warming)**: 공개 전에 엣지에 미리 요청을 넣어
  캐시를 채워 둔다.
- **origin shield / 계층형 캐시**: 수백 개 엣지가 각자 오리진에
  miss를 보내지 않고, 중간 상위 캐시 한 곳으로 모아 오리진 요청을
  1회로 수렴시킨다.
- **request coalescing(요청 병합)**: 같은 리소스에 대한 동시 miss들을
  묶어 오리진에는 한 번만 가져온다.

### ④ 이미지 최적화는 엣지/전처리 계층에서

디바이스별 리사이징, WebP/AVIF 변환은 요청마다 오리진에서 하는 게
아니라 업로드 시 전처리하거나 이미지 처리 계층 + CDN 캐시로 해결한다.
"변환 결과도 결국 캐시 가능한 불변 콘텐츠"라는 관점이 일관되게 적용된다.

## 4. 꼬리질문 대비 포인트

### "캐시 무효화(purge)와 버전드 URL, 어느 쪽을 쓰나요?"

기본 전략은 버전드 URL이다. purge는 ① 전 세계 엣지에 전파되는 데
시간이 걸려 그 사이 신구 콘텐츠가 섞여 보이고, ② 대상 지정을 실수하면
멀쩡한 캐시까지 날려 miss 폭주를 자초한다. 버전드 URL은 무효화라는
동작 자체가 필요 없고, 배포 시점에 신구 버전이 공존해도 안전하다.
purge는 잘못 올라간 콘텐츠 긴급 제거(법적 삭제 요청 등)처럼
"URL을 유지한 채 내용을 지워야 하는" 예외 상황용으로 남겨 둔다.

### "CDN 히트율이 기대보다 낮습니다. 원인을 어디서 찾나요?" (시니어 변별 포인트)

히트율은 **캐시 키가 얼마나 잘 모이는가**의 문제다. 점검 순서:

1. **캐시 키 분산** — 불필요한 쿼리스트링(추적 파라미터 등)이나 `Vary`
   헤더가 캐시 키에 들어가면 같은 이미지가 수십 개 키로 쪼개진다.
   캐시 키에서 무의미한 파라미터를 제거하는 것이 첫 번째 처방.
2. **TTL이 너무 짧다** — 오리진이 `no-cache`나 짧은 max-age를 내려주고
   있지 않은지 응답 헤더부터 확인.
3. **롱테일 콘텐츠** — 비인기 구작은 요청 간격이 캐시 보존 기간보다
   길어 엣지에서 밀려난다(eviction). 이건 히트율의 자연스러운 하한이며,
   계층형 캐시(origin shield)로 상위 캐시 히트를 늘려 보완한다.
4. **엣지 분산** — 같은 콘텐츠도 엣지(지역)마다 따로 캐시되므로,
   지역별 첫 요청은 반드시 miss다. 전체 히트율만 보지 말고
   엣지별/콘텐츠별로 쪼개 봐야 원인이 보인다.

### "동적인 API 응답도 CDN에 캐싱할 수 있나요?"

가능하고, 조건은 같다 — "여러 사용자에게 동일한 응답인가".
메인 페이지의 인기 웹툰 목록, 회차 목록 같은 **공용 응답**은
수 초~수십 초의 짧은 TTL로도 오리진 요청을 크게 줄일 수 있다
(1초 TTL이라도 그 1초간 몰린 수천 요청이 1회로 수렴).
`stale-while-revalidate`(만료된 캐시를 일단 응답하고 뒤에서 갱신)까지
언급하면 가산점 포인트. 단, 개인화 응답에 `public` 캐시를 잘못 걸면
**남의 데이터가 보이는 사고**가 나므로, 인증이 필요한 응답은
기본적으로 캐시 제외라는 안전선을 함께 말해야 한다.

### "유료 회차 이미지가 URL 공유로 유출되는 것은 어떻게 막나요?"

signed URL의 만료 시간을 짧게(열람 세션 수준) 잡아 URL이 공유되어도
금방 죽게 만들고, 서명에 추가 조건을 결합해 재사용을 어렵게 한다.
다만 "화면에 보이는 이상 완벽한 유출 방지는 불가능하다(화면 캡처)"는
한계를 인정하고, 목표를 '완전 차단'이 아니라 '대량·자동화된 수집을
비싸게 만드는 것'으로 정의하는 답변이 현실적이다.

### "CDN 도입의 비용이나 단점은 없나요?" (시니어 변별 포인트)

① **캐시 정합성 문제의 도입** — 잘못 캐시된 응답(개인화 응답의 public
캐시, 잘못된 이미지)은 서버 재배포로 해결되지 않는 새로운 유형의
장애가 된다. ② **관측의 분리** — 트래픽 대부분이 오리진에 안 오므로,
서버 로그만 봐서는 실제 사용자 트래픽을 모른다. CDN 로그/지표를
모니터링 체계에 통합해야 한다. ③ **장애 도메인 추가** — CDN 자체 장애
시의 대응(오리진 직접 서빙은 그 트래픽을 감당 못 하므로, 사실상 CDN이
필수 인프라가 됨)을 인지해야 한다. "도입하면 끝"이 아니라 운영 대상이
하나 늘어나는 것이라는 시각이 시니어의 답변이다.

## 한 줄 요약

CDN은 "여러 사용자가 반복 요청하는 잘 안 변하는 콘텐츠"를 사용자
가까운 엣지에서 대신 응답해 지연시간과 오리진 부하를 동시에 줄이는
계층이고, 불변·고재사용의 웹툰 이미지는 그 이상적인 대상이다 —
버전드 URL + 긴 캐시로 히트율을 극대화하면, 오리진 서버 최적화보다
캐시 히트율 1%가 시스템 전체 부하에 더 크게 작용한다.
