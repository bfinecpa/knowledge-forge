# 백프레셔 — "유입 > 처리"가 지속되면 큐는 반드시 어딘가에서 터진다

> 핵심 관전 포인트: **백프레셔는 "하류(소비자)의 처리 능력을 상류(생산자)에게
> 신호로 전달해 유입 속도를 처리 속도에 맞추는 흐름 제어(flow control)
> 메커니즘**이다. 유입 속도가 처리 속도를 지속적으로 초과하면 그 차이만큼
> 어딘가의 큐에 쌓인다는 것은 보존 법칙이고, 큐를 키우는 것은 해결이 아니라
> **폭발 지점을 뒤로 미루는 지연**일 뿐이다. 그래서 시스템의 모든 "속도가
> 다른 두 구간이 만나는 경계"(클라이언트↔서버, 스레드풀 큐, 서비스 간 호출,
> 메시지 큐 소비, DB 커넥션 앞)에 유입을 제한하거나 빠르게 거절하는 장치가
> 필요하다.

---

## 0. 질문 + 의도

**질문**: "백프레셔(backpressure)란 무엇이고, 시스템의 어떤 지점들에 필요한가요?"

**출제 의도**: 유입 속도 > 처리 속도가 지속되면 큐가 어딘가에서 터진다는
보존 법칙을 아는지 본다. 이를 아는 사람은 "큐를 키우자"가 해결이 아니라
지연임을 알고, 유입 제한이나 처리 확장 중에서 답을 찾는다.

## 1. 개념 — 수도관의 압력이 거꾸로 전달되는 것

생산자(요청을 보내는 쪽)가 소비자(처리하는 쪽)보다 빠른 상황을 생각하면:

```
생산 1,000/s  →  [ 큐 ]  →  처리 600/s
                    ↑
        매초 400개씩 무한히 쌓인다 (보존 법칙)
```

쌓인 것들이 갈 곳은 셋 중 하나뿐이다 — **메모리(OOM), 디스크,
사용자의 인내심(타임아웃)**. 어디서 터질지만 다를 뿐 반드시 터진다.

백프레셔는 이 압력을 **하류에서 상류로 거꾸로 전파**해서, 생산자가
소비자의 속도에 맞추게 만드는 것이다. 수도관 끝을 막으면 수압이
수원지까지 거꾸로 전달되는 것과 같다. 전달 방식은 세 가지다:

- **막기(block)**: 소비자가 받을 때까지 생산자를 대기시킴 — 동기
  호출의 대기, bounded queue의 `put()` 블로킹
- **거절(reject/error)**: 즉시 실패를 돌려줌 — HTTP 429, 스레드풀
  `RejectedExecutionException`
- **수요 신호(demand signal)**: 소비자가 "n개 더 줘"라고 명시적으로
  요청 — Reactive Streams의 `request(n)`, Kafka의 pull 모델

## 2. "큐를 키우자"가 왜 답이 아닌가

큐는 **일시적 버스트를 흡수**하는 장치다. 유입이 처리를 **지속적으로**
초과하는 상황에서 큐를 키우면:

- 큐 길이만큼 **대기 시간이 비례 증가**한다 (Little's Law: 대기 시간 =
  큐 길이 ÷ 처리율). 큐에 6,000개가 쌓였고 처리율이 600/s면 새 요청은
  10초를 기다린다.
- 클라이언트 타임아웃(예: 3초)보다 대기가 길어지는 순간부터 서버는
  **아무도 기다리지 않는 죽은 요청을 처리하는 데 자원을 태운다** —
  처리량은 그대로인데 유효 처리량(goodput)은 0으로 수렴.
- 결국 메모리가 먼저 터지거나(unbounded queue → OOM), 전 구간이 느려진
  채로 좀비 상태가 된다.

그래서 근본 선택지는 둘뿐이다 — **처리 속도를 올리거나(스케일 아웃,
튜닝), 유입을 제한하거나(백프레셔·거절)**. 큐 크기는 "버스트를 얼마나,
얼마 동안의 추가 대기를 감수하고 흡수할 것인가"의 선언이지 용량 확장
수단이 아니다.

## 3. 시스템의 어떤 지점들에 필요한가 — "속도가 다른 두 구간의 경계"마다

### ① 클라이언트 ↔ 서버 경계

- **TCP 자체가 백프레셔를 내장**한다(수신 윈도우, receive window) —
  수신 버퍼가 차면 송신 측이 전송을 늦춘다. "백프레셔는 특별한 기술이
  아니라 네트워크 스택에 이미 있는 원리"라고 짚으면 가산점.
- 애플리케이션 레벨에서는 **rate limiting + 429 응답**이 유입 제한
  장치다. 수용 못 할 요청은 큐에 넣지 말고 빨리 거절하는 게 전체에 낫다.

### ② 서버 내부 — 스레드풀과 그 앞의 큐

```java
// Before: unbounded 큐 — 백프레셔 없음, 압력이 메모리에서 터진다
ExecutorService pool = new ThreadPoolExecutor(
    10, 10, 0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<>());          // 크기 무제한
// 유입 > 처리가 지속되면 큐가 무한히 자라 OOM.
// 그동안 응답 시간은 계속 늘어나는데 거절은 한 번도 안 한다.

// After: bounded 큐 + 거절 정책 — 압력을 호출자에게 전파
ExecutorService pool = new ThreadPoolExecutor(
    10, 10, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(100),          // 허용 대기량을 명시
    new ThreadPoolExecutor.CallerRunsPolicy());
// 큐가 차면 제출한 스레드가 직접 실행 → 제출 속도가 저절로 느려짐
// (또는 AbortPolicy로 즉시 예외 → 상류에서 폴백/거절 처리)
```

`CallerRunsPolicy`는 "생산자를 일 시켜서 생산 속도를 늦추는" 소박하지만
효과적인 백프레셔다. 톰캣의 max connections / accept-count 제한도 같은
계층의 장치다.

### ③ 서비스 간 호출 경계

- **타임아웃 + bounded 커넥션 풀 + 세마포어(bulkhead)**: 느린 다운스트림에
  보낼 수 있는 동시 요청 수를 제한하면, 하류의 느림이 상류의 스레드
  고갈로 번지는 것을 막고 초과분은 빨리 실패시킨다.
- **서킷 브레이커**도 넓게 보면 백프레셔다 — "하류가 처리 불능"이라는
  신호를 받아 유입 자체를 차단한다.

### ④ 메시지 큐 / 스트림 소비 경계

- **Kafka가 백프레셔에 유리한 이유는 pull 모델**이기 때문이다. 소비자가
  자기 속도로 `poll()`하므로 밀어넣기(push)에 압도될 일이 없고, 밀린
  분량은 브로커의 디스크(대용량 버퍼)에 안전하게 쌓인다. 소비 지연은
  consumer lag 지표로 드러난다.
- 함정: poll은 자기 속도로 해놓고 **가져온 레코드를 무한 메모리 버퍼에
  쌓으면** 백프레셔가 끊긴다. 내부 처리 큐가 차면 `pause()`로 poll을
  멈추고, 비워지면 `resume()`하는 식으로 압력을 브로커까지 되돌려야 한다.
- 프로듀서 쪽도 마찬가지 — 전송 버퍼가 차면 블로킹되거나 예외를 내는데,
  이것이 브로커의 압력이 애플리케이션까지 전파되는 지점이다.

### ⑤ 리액티브 스트림 — 백프레셔를 프로토콜로 만든 것

Reactive Streams(Reactor, RxJava, WebFlux)의 핵심 계약이 바로
`Subscription.request(n)` — **소비자가 수요를 명시적으로 선언**하고,
생산자는 그만큼만 발행한다. 감당 못 할 때의 전략도 명시적으로 고른다:
`onBackpressureBuffer`(쌓기) / `Drop`(버리기) / `Latest`(최신만 유지).
"리액티브의 본질은 논블로킹이 아니라 백프레셔 계약"이라고 말하면 가산점.

### ⑥ DB 앞 — 커넥션 풀

커넥션 풀 자체가 백프레셔 장치다. 풀 크기가 DB에 동시에 걸리는 부하의
상한이 되고, 풀 고갈 시 acquire timeout이 빨리 실패시켜 압력을 상류로
돌려준다. 풀을 무작정 키우는 건 DB 앞으로 대기 줄을 옮기는 것일 뿐이다.

## 4. 꼬리질문 대비 포인트

### "백프레셔, rate limiting, load shedding은 뭐가 다른가요?" (시니어 변별 포인트)

셋 다 "유입 제한"이지만 작동 시점과 신호의 방향이 다르다:

- **백프레셔**: 하류의 **실시간 처리 능력**을 상류로 전파해 속도를
  맞추는 협조적 메커니즘 (수요-공급 신호)
- **Rate limiting**: 처리 능력과 무관하게 **사전에 정한 정책적
  한도**(계약, 공정성)로 자르는 것 — 시스템이 한가해도 한도는 유효
- **Load shedding**: 이미 과부하에 빠졌을 때 **우선순위 낮은 요청부터
  버리는** 최후의 방어

건강한 시스템은 셋을 계층적으로 함께 쓴다 — 평시엔 rate limit, 경계마다
백프레셔, 그래도 넘치면 shedding.

### "동기(블로킹) 시스템에는 백프레셔가 없는 건가요?"

아니다 — **동기 호출의 '대기' 자체가 자연스러운 백프레셔**다. 하류가
느리면 상류 스레드가 블로킹되어 유입이 저절로 준다. 문제는 이 방식이
스레드를 인질로 잡는다는 것 — 대기가 길어지면 상류 스레드풀이 고갈되어
장애가 **전파**된다. 그래서 동기 시스템에서는 타임아웃·bounded 풀·거절
정책으로 "대기 대신 빠른 실패"를 택하는 지점을 설계해야 한다.

### "Kafka 같은 브로커를 중간에 두면 백프레셔가 필요 없지 않나요?"

브로커는 **거대한 bounded 버퍼**이지 처리 능력이 아니다. 유입 > 소비가
지속되면 consumer lag가 무한히 늘고, retention을 넘긴 데이터는 유실된다.
브로커는 폭발을 며칠 뒤로 미뤄줄 뿐, "소비 확장 또는 유입 제한"이라는
근본 선택은 그대로 남는다. 대신 그 유예 시간과 lag라는 명확한 지표를
주는 것이 브로커의 가치다.

### "큐가 차면 막기(block)와 거절(error) 중 뭘 선택하나요?"

- **막기**: 배치·내부 파이프라인처럼 생산자를 늦춰도 되는 곳. 유실이
  없다는 장점, 상류 스레드 점유라는 비용.
- **거절**: 사용자 대면 요청 경로. 어차피 기다려도 타임아웃될 요청이면
  즉시 429/503 + Retry-After로 돌려주는 게 사용자에게도 시스템에도 낫다.
- 판단 기준은 "**생산자가 기다릴 수 있는 주체인가**"다. 사람은 못
  기다리고, 배치는 기다릴 수 있다.

### "백프레셔가 잘 되고 있는지 어떤 지표로 확인하나요?"

경계마다 큐의 깊이와 대기 시간을 본다 — 스레드풀 큐 길이와 거절 수,
커넥션 풀 pending/acquire time, Kafka consumer lag, 429 응답률.
**"큐 깊이가 지속 증가 추세"가 유입 > 처리의 확정 신호**이고, 이때
대응은 큐 확대가 아니라 소비 확장 또는 유입 제한이다.

## 한 줄 요약

백프레셔는 하류의 처리 능력을 상류로 전파해 유입을 처리 속도에 맞추는
흐름 제어이고, "유입 > 처리가 지속되면 큐는 반드시 어딘가에서 터진다"는
보존 법칙 때문에 속도가 다른 두 구간이 만나는 모든 경계 — 클라이언트
유입(rate limit·429), 스레드풀(bounded 큐+거절 정책), 서비스 간
호출(타임아웃·bulkhead), 메시지 소비(pull·pause/resume), DB 앞(커넥션
풀) — 에 필요하며, 큐 확대는 해결이 아니라 폭발의 지연일 뿐이다.
