# Load Shedding — 모두에게 느린 서비스보다 일부를 빨리 거절하는 서비스가 낫다

> 핵심 관전 포인트: **Load shedding은 처리 용량을 넘는 부하가 들어올 때
> 일부 요청을 의도적으로, 즉시 거절해 나머지 요청의 정상 처리를 지키는
> 자기 방어다. 과부하 상태에서 전 요청을 받아주면 큐잉 지연으로 전원이
> 타임아웃을 겪고, 서버는 "이미 클라이언트가 포기한 요청"을 처리하느라
> 자원을 태우는 처리량 붕괴에 빠진다 — 그래서 전부 느린 것보다 일부를
> 빨리 거절하는 것이 낫다. 무엇부터 버릴지는 비즈니스 우선순위(비핵심
> API, 비로그인·봇 트래픽부터)이고, 어디서 버릴지는 "가능한 한 바깥,
> 가능한 한 싸게"(게이트웨이 > 애플리케이션 > 큐)가 원칙이다.**

---

## 0. 질문 + 의도

**질문**: "Load shedding이란? 과부하 시 어떤 요청부터, 어디서 버리나요?"

**출제 의도**: "모두에게 느린 서비스보다 일부를 빨리 거절하는 서비스가
낫다"는 반직관을 수용하는지 본다. 무엇부터 버릴지(비핵심 API, 비로그인
트래픽)의 우선순위 결정은 기술이 아니라 비즈니스 이해도에서 나온다 —
장애 상황에서 서비스의 어느 부분이 진짜 핵심인지 말할 수 있는 사람인지
확인하는 질문이다.

## 1. 왜 버리는 게 지키는 것인가 — 과부하의 물리학

서버가 초당 1,000건을 처리할 수 있는데 1,500건이 들어온다고 하자.
"최대한 다 받아서 처리하자"는 선의는 다음 악순환을 만든다:

```text
유입 > 처리 용량
→ 초과분이 큐(스레드풀 대기열, TCP backlog)에 쌓임
→ 큐 대기 시간이 계속 증가 (유입이 줄지 않는 한 무한히)
→ 모든 요청의 응답시간이 대기 시간만큼 늘어남
→ 클라이언트가 타임아웃으로 먼저 포기
→ 서버는 "이미 주인이 떠난 요청"을 꺼내 처리 (자원 낭비)
→ 포기한 클라이언트는 재시도 → 유입이 오히려 증가
→ 실질 처리량(goodput)이 0을 향해 붕괴
```

핵심 개념이 **goodput과 throughput의 분리**다. 서버가 초당 1,000건을
"처리"해도(throughput), 그중 800건이 클라이언트 타임아웃 이후에
완료됐다면 의미 있는 처리(goodput)는 200건뿐이다. 과부하 상태에서
전원 수용은 goodput을 파괴한다.

- 비유: 만석 식당에 계속 손님을 들이면, 앉은 손님도 음식을 못 받고
  전원이 화내며 나간다. 입구에서 "지금은 자리가 없습니다"라고 빨리
  돌려보내는 것이 앉은 손님의 식사를 지키는 길이다.

Load shedding은 이 붕괴를 끊는 장치다: 처리할 수 없는 만큼을
**빨리, 싸게 거절**해서(503 + `Retry-After`), 수용한 요청만큼은
정상 지연시간으로 완료한다.

**Rate limiting과의 구분** (한 줄로): rate limiting은 클라이언트별
사전 계약을 평시에도 집행하는 것, load shedding은 시스템의 **현재
상태**를 보고 발동하는 비상 방어다. 모든 클라이언트가 각자 한도를
지켜도 합계가 용량을 넘으면 shedding이 필요하다 — 별개의 계층이다.

## 2. 어떤 요청부터 버리나 — 우선순위는 비즈니스에서 나온다

버릴 순서를 정하는 것은 기술 판단이 아니라 **"장애 시 이 서비스의
존재 이유가 무엇인가"** 라는 비즈니스 판단이다. 일반적인 우선순위
(먼저 버리는 것부터):

1. **봇·크롤러·비인증 트래픽** — 사람이 아닌 트래픽, 로그인하지 않은
   익명 탐색. 거절해도 비즈니스 손실이 가장 작다.
2. **비핵심 기능 API** — 추천, 연관 콘텐츠, 조회수 갱신, 배너.
   없어도 핵심 여정(콘텐츠 보기, 결제)이 완결된다.
3. **재시도 요청보다 신규 요청 우대 여부 결정** — 재시도는 이미 부하
   증폭의 신호다. 클라이언트가 보낸 재시도 표식(예: 시도 횟수 헤더)이
   있으면 재시도부터 버려 retry storm을 끊을 수 있다.
4. **끝까지 지키는 것** — 결제·주문 같은 돈이 걸린 쓰기, 로그인,
   핵심 콘텐츠 조회.

이를 구현하려면 **요청에 중요도 등급(criticality)이 붙어 있어야 한다.**
게이트웨이에서 경로·인증 여부·클라이언트 종류로 분류해 헤더로 태깅하고,
과부하 수위가 올라갈수록 낮은 등급부터 차단선을 올린다.
"수위별로 단계적으로 버린다"는 개념을 말하면 좋다 — 과부하 70%에선
봇만, 90%에선 비핵심 API까지, 임계 상황에선 핵심만 남긴다.

(가산점 포인트) 이 우선순위 문서화는 평시에 해두는 것이다. 장애
한복판에서 "추천이 중요해요, 배너가 중요해요?"를 논쟁할 수는 없다 —
graceful degradation 설계(기능별 중요도 매트릭스)와 같은 뿌리다.

## 3. 어디서 버리나 — 바깥일수록, 쌀수록 좋다

버리는 위치의 원칙: **요청에 자원을 쓰기 전에, 가장 바깥에서, 가장
싼 방법으로.** 깊이 들어온 요청을 버리면 이미 파싱·인증·DB 커넥션에
자원을 쓴 뒤라 "버렸는데도 비용은 냈다"가 된다.

### 계층별 shedding 지점

- **CDN / L7 로드밸런서·게이트웨이**: 가장 싸다. 애플리케이션에
  닿기 전에 정적인 규칙(경로, 인증 여부, 등급 헤더)으로 거절.
  다만 여기는 백엔드의 내부 상태를 잘 모르므로 정밀도가 낮다.
- **애플리케이션 입구 (서블릿 필터 등)**: 시스템 상태(동시 처리 수,
  큐 길이)를 직접 보면서 요청별 중요도까지 반영하는 정밀 shedding.
  비즈니스 로직·DB 접근 전에 잘라야 의미가 있다.
- **스레드풀·큐의 경계**: 마지막 방어선. 무한 큐는 shedding을
  "지연"으로 바꿔버리는 함정이므로, **큐를 유한하게 잡고 넘치면
  즉시 거절**이 기본이다.

```java
// Before: 무한 큐 — 거절 대신 무한 대기 (shedding 불가능한 구조)
ExecutorService pool = new ThreadPoolExecutor(
    100, 100, 0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<>());   // 무한 큐: 과부하가 지연으로 축적됨
// 문제: 큐가 계속 자라며 전 요청의 대기시간 증가 + 메모리 압박
//       클라이언트는 타임아웃, 서버는 죽은 요청 처리 중

// After: 유한 큐 + 넘치면 즉시 거절 → 호출측에 503 반환
ExecutorService pool = new ThreadPoolExecutor(
    100, 100, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(200),          // 감당할 만큼만 대기
    new ThreadPoolExecutor.AbortPolicy());  // 초과분은 예외 → 503 매핑
// 효과: 수용한 요청은 정상 지연으로 완료, 초과분은 1ms 만에 거절
```

```java
// 애플리케이션 입구 shedding 필터의 뼈대: 동시 처리 수 기반
public class SheddingFilter implements Filter {
    private final AtomicInteger inflight = new AtomicInteger();
    private final int limit = 300;   // 정상 지연을 유지할 수 있는 동시 처리 한계

    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        // 과부하 시 낮은 등급부터: 여기선 단순화해 비핵심 경로를 먼저 차단
        if (inflight.get() >= limit && !isCritical(req)) {
            ((HttpServletResponse) res).setHeader("Retry-After", "5");
            ((HttpServletResponse) res).sendError(503);  // 즉시, 싸게 거절
            return;
        }
        inflight.incrementAndGet();
        try {
            chain.doFilter(req, res);
        } finally {
            inflight.decrementAndGet();
        }
    }
}
```

### 과부하를 무엇으로 감지하나

CPU 사용률만으로는 부족하다(I/O 대기 중이면 CPU가 낮아도 과부하다).
실전에서 쓰는 신호는 **동시 처리 중 요청 수(inflight)**, **큐 대기
길이/대기 시간**, **최근 응답시간의 악화 추이**다. 고정 임계값 대신
"지연이 나빠지기 시작하는 동시성 수준"을 런타임에 추정해 한계를
움직이는 적응형 동시성 제한(adaptive concurrency limit) 기법도 있다
(가산점 포인트 — Netflix의 concurrency-limits, TCP 혼잡 제어에서
빌려온 아이디어라고 덧붙이면 좋다).

## 4. 꼬리질문 대비 포인트

### "거절당한 클라이언트는 어떻게 해야 하나요? 재시도하면 다시 과부하 아닌가요?"

거절 응답이 재시도 폭탄으로 돌아오면 shedding이 무력화된다. 그래서
거절에는 **`Retry-After`를 실어 재시도 시점을 분산**시키고,
클라이언트는 exponential backoff + jitter로 물러나야 한다.
서버가 "지금 과부하"라는 신호를 명시적으로 주는 것(503)과
클라이언트의 예의 바른 재시도는 한 세트다 — 어느 한쪽만으로는
retry storm을 못 막는다.

### "429와 503 중 무엇을 반환하나요?"

의미가 다르다. **429는 "너(클라이언트)가 너의 한도를 넘었다"**(rate
limit 위반 — 원인이 클라이언트), **503은 "나(서버)가 지금 여력이
없다"**(과부하 shedding — 원인이 서버)다. Load shedding의 거절은
클라이언트 잘못이 아니므로 503이 맞다. 이 구분은 클라이언트의 대응도
가르는데, 429는 자기 속도를 줄여야 하고 503은 잠시 후 재시도가 맞다.

### "우선순위를 붙일 수 없는 트래픽이 섞여 있으면요?"

분류 정보가 없을 때의 폴백은 **무작위 확률 shedding**이다 — 초과분
비율만큼(예: 유입의 20%) 무작위로 거절하면 특정 사용자만 계속
불운해지는 걸 피하면서 총량을 용량 아래로 누른다. 다만 이것은
차선책이고, 정석은 게이트웨이에서 미리 등급을 태깅해두는 것이다.

### "Load shedding이 오히려 해가 되는 경우는 없나요?" (시니어 변별 포인트)

세 가지를 짚으면 좋다. ① **임계값 오설정** — 한계를 실제 용량보다
낮게 잡으면 여력이 있는데도 정상 트래픽을 버린다(과민), 높게 잡으면
붕괴를 못 막는다(둔감). 그래서 임계값은 부하 테스트로 "지연이 꺾이는
지점"을 실측해 정하고, 가능하면 적응형으로 둔다. ② **감지 신호의
왜곡** — 거절 응답은 매우 빠르므로, 평균 응답시간을 신호로 쓰면
"많이 버릴수록 지표가 좋아져 더 안 버리는" 되먹임 오류가 생길 수 있다.
수용된 요청만의 지연을 봐야 한다. ③ **버리는 위치가 너무 안쪽** —
DB 앞에서 버리면 이미 웹 계층 자원을 다 쓴 뒤다. shedding은 결국
"어디서 버려야 낭비가 최소인가"의 배치 문제라는 관점을 보이면
시니어답다.

### "Graceful degradation과는 어떤 관계인가요?"

같은 철학("전부 아니면 전무를 거부")의 두 실행 형태다.
Load shedding은 **요청 단위로 수용/거절**을 가르는 것이고, graceful
degradation은 **기능 단위로 품질을 낮춰서라도 응답하는 것**(추천이
죽으면 인기순으로 대체)이다. 실전에서는 결합된다 — 비핵심 기능은
degrade로 값싸게 응답하고, 그래도 넘치는 유입은 shed한다.

## 한 줄 요약

Load shedding은 과부하 시 "전원이 타임아웃으로 전멸"하는 처리량 붕괴를
막기 위해 일부 요청을 즉시 거절해 goodput을 지키는 자기 방어이며 —
무엇부터 버릴지는 비즈니스 우선순위(봇·비핵심부터, 결제·핵심은
끝까지), 어디서 버릴지는 "자원을 쓰기 전, 가장 바깥에서 가장 싸게"가
답이다.
