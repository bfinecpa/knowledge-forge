# API 병목 추적 — 감이 아닌 측정으로, 모니터링에서 프로파일링까지

> 핵심 관전 포인트: **병목 추적은 넓은 곳에서 좁은 곳으로 내려가는 탑다운 수사다. ① 먼저 "무엇이 변했는가"를 확정하고(배포·설정·데이터·트래픽·의존 서비스·인프라 작업·배치), ② 모니터링 지표(p99, 에러율, 자원 사용률)로 어느 계층이 느린지 좁히고, ③ 분산 트레이싱으로 요청 한 건의 시간을 구간별로 분해해 범인 구간을 찾고, ④ 마지막에 그 구간만 프로파일링(스레드 덤프, 플레임 그래프)으로 파고든다. 순서의 핵심은 "코드부터 열어보지 않는 것" — 추측이 아니라 측정이 다음 단계를 결정한다. 그리고 이 수사에서 가장 자주 놓치는 것은 **큐 대기 시간**이다. 요청이 톰캣 워커 스레드를 기다린 시간과 DB 커넥션을 기다린 시간은 애플리케이션 로그에 잡히지 않으므로, "우리 코드는 10ms인데요"라는 말과 "사용자는 5초 기다렸다"는 사실이 동시에 참일 수 있다. 앞단이 잰 시간과 앱이 잰 시간의 차이가 곧 그 보이지 않는 대기다.**

---

## 0. 질문 + 의도

**질문**: "API 응답이 갑자기 느려졌습니다. 병목 지점을 찾는 과정을 처음부터 끝까지 설명해주세요. (모니터링 → 프로파일링)"

**출제 의도**: 이 질문의 진짜 목적은 방법론이다 — 어디부터 보는지(지표 → 구간 분해 → 프로파일링), 판단의 근거가 추측인지 측정인지. 체계 없이 "코드를 봤어요"로 시작하는 사람은 실전에서 몇 시간을 낭비한다. 장애 상황에서 침착하게 범위를 좁혀가는 수사 능력을 확인하는 질문이다.

## 1. 요청 한 건의 시간은 어디로 가는가 — 수사의 지도부터 그린다

수사를 시작하기 전에 지도가 필요하다. **응답시간 200ms라는 숫자 하나는 실제로는 일곱 개쯤의 구간이 더해진 합계**인데, 이 사실을 모르면 "느리다"는 말에서 다음 행동으로 넘어갈 수 없다.

### 1-1. 전제 지식 — 200ms 응답 한 건을 쪼개 보면

정상적으로 200ms에 응답하는 API 하나를 시간축에 늘어놓으면 이렇게 된다. 각 칸은 그 구간에서 실제로 흘러간 시간이다.

```text
요청 도착                                                              응답 반환
t=0ms                                                                  t=200ms
  │                                                                        │
  ├─[ LB/게이트웨이 통과 ]──────────────────────────────────── 0 ~   3ms (  3ms)
  │    TLS 종료, 라우팅 판정, 업스트림 연결
  │
  ├─[ ★ 톰캣 accept 큐 대기 ]────────────────────────────────  3 ~  45ms ( 42ms)
  │    워커 스레드 200개가 전부 사용 중이라 순서를 기다린 시간.
  │    이 구간에서는 우리 코드가 한 줄도 실행되지 않는다.
  │
  ├─[ 핸들러 진입: 역직렬화·검증 ]─────────────────────────── 45 ~  47ms (  2ms)
  │
  ├─[ ★ DB 커넥션 풀 대기 ]───────────────────────────────── 47 ~  92ms ( 45ms)
  │    HikariCP 풀에 빈 커넥션이 없어 기다린 시간.
  │    DataSource.getConnection() 안에서 멈춰 있다.
  │
  ├─[ 쿼리 실행 ]──────────────────────────────────────────  92 ~ 122ms ( 30ms)
  │    SELECT 2회. PostgreSQL이 실제로 일한 시간.
  │
  ├─[ 외부 API 호출 ]───────────────────────────────────────122 ~ 190ms ( 68ms)
  │    결제사 조회. 네트워크 왕복 + 상대 서버 처리 시간.
  │
  └─[ 직렬화·응답 전송 ]────────────────────────────────────190 ~ 200ms ( 10ms)
       JSON 직렬화 + 소켓 쓰기

  합계: 3 + 42 + 2 + 45 + 30 + 68 + 10 = 200ms
```

이 그림에서 별표를 붙인 두 칸이 이 문서의 핵심이다. **42ms와 45ms, 합쳐서 87ms — 전체의 43.5%가 "아무 코드도 실행되지 않고 그냥 줄만 서 있던 시간"이다.** 계산은 `(42 + 45) ÷ 200 = 0.435`다.

여기서 **큐 대기**라는 말을 정확히 정의하고 넘어가자. 서버의 자원은 무한하지 않아서, 톰캣의 워커 스레드도 200개, DB 커넥션 풀도 10개처럼 개수가 정해져 있다. 그 자원이 전부 사용 중일 때 새로 도착한 요청은 **거절되지 않고 줄을 선다.** 그 줄에서 보낸 시간이 큐 대기 시간이다. CPU를 쓰지도 않고, 네트워크를 타지도 않고, 그냥 자기 차례를 기다린다.

비유하면 병원 진료다. 진료 자체는 5분인데 대기실에서 40분 기다렸다면 환자의 체감 시간은 45분이다. 그런데 의사의 진료 기록에는 "5분 진료"만 남는다. **대기실은 진료 기록에 없다.**

### 1-2. 큐 대기 시간은 애플리케이션 로그에 없다

위 그림의 87ms가 애플리케이션 로그에 안 잡히는 이유는 구조적이다.

톰캣 accept 큐 대기(42ms)를 보자. 이 구간에서 요청은 아직 **워커 스레드에 배정되지 않았다.** 스프링의 서블릿 필터, 인터셉터, `@RestController` 메서드는 모두 워커 스레드가 요청을 집어든 다음에 실행된다. 그러니 필터에서 스톱워치를 켜도 그 스톱워치는 45ms 지점에서 시작한다 — 앞의 45ms는 측정 자체가 불가능하다. 마이크로미터의 `http.server.requests` 타이머도 서블릿 필터 체인 안에서 재므로 마찬가지다.

DB 커넥션 풀 대기(45ms)는 다르게 숨는다. 이 시간은 워커 스레드 안에서 흐르므로 필터의 스톱워치에는 포함되지만, **"DB 구간"으로 뭉쳐진다.** 개발자가 로그를 남길 때 보통 이렇게 쓴다.

```java
// Before: 전체 시간만 로깅한다 — 800ms가 나와도 어디서 썼는지 모른다
public OrderDetail getDetail(long orderId) {
    long start = System.currentTimeMillis();
    OrderDetail result = doGetDetail(orderId);
    log.info("getDetail took {}ms", System.currentTimeMillis() - start);
    return result;
}
```

이 로그는 "800ms 걸렸다"까지만 말한다. 그다음 질문 — DB인가, 외부 API인가, 직렬화인가 — 에 아무 답을 주지 못한다. 그래서 개발자는 급한 마음에 코드를 열고 눈으로 읽기 시작하고, 여기서 몇 시간이 사라진다.

구간을 나눠 재면 그 몇 시간이 5분이 된다.

```java
// After: 단계별로 시간을 쪼개 기록한다
public OrderDetail getDetail(long orderId) {
    long t0 = System.nanoTime();
    Order order = orderRepository.findById(orderId).orElseThrow();  // DB 구간
    long t1 = System.nanoTime();
    Coupon coupon = couponClient.fetch(order.userId());             // 외부 API 구간
    long t2 = System.nanoTime();
    OrderDetail dto = mapper.toDetail(order, coupon);               // CPU 구간
    long t3 = System.nanoTime();

    // nanoTime을 쓰는 이유: currentTimeMillis()는 NTP 시각 보정에 영향을 받아
    // 두 시점의 차이가 음수로 나오거나 튀는 경우가 있다. 구간 측정에는
    // 단조 증가가 보장되는 nanoTime이 맞다.
    log.info("getDetail orderId={} db={}ms api={}ms map={}ms total={}ms",
            orderId, ms(t0, t1), ms(t1, t2), ms(t2, t3), ms(t0, t3));
    return dto;
}

private static long ms(long from, long to) {
    return (to - from) / 1_000_000;
}
```

그런데 이 after 코드에도 한계가 하나 남는다. **`db=` 안에는 "커넥션을 얻기까지 기다린 시간"과 "쿼리가 실제로 실행된 시간"이 섞여 있다.** `findById`는 내부적으로 `DataSource.getConnection()`을 먼저 호출하기 때문이다.

이 둘을 가르는 방법이 있다. 앱이 잰 `db=250ms`와 PostgreSQL이 잰 그 쿼리의 평균 실행 시간을 비교하는 것이다.

```text
앱이 잰 db 구간                    250ms
PostgreSQL이 잰 그 쿼리 평균         3ms   (pg_stat_statements.mean_exec_time)
                                 ───────
차이                               247ms   <- 쿼리가 아니다. 커넥션을 기다린 시간이다.
```

**DB가 "나는 3ms에 끝냈다"고 말하는데 앱이 "250ms 걸렸다"고 말하면, 그 차이는 DB 밖에서 생긴 것이다.** 커넥션 획득 대기, 네트워크, 드라이버 오버헤드 순으로 의심한다. 이 비교 하나가 "DB가 느리다"와 "DB에 도달하지 못하고 있다"를 갈라 준다. 3절의 시나리오가 정확히 이 갈림에서 풀린다.

### 1-3. 그래서 큐 대기 시간은 어떻게 보는가

앱 로그에 안 나온다면 어디서 보는가. 방법은 세 가지다.

**첫째, 앞단이 잰 시간과 앱이 잰 시간의 차이를 본다.** 이것이 가장 범용적이고 언제나 통하는 방법이다. LB나 nginx는 요청이 도착한 순간부터 재고, 앱은 워커 스레드가 요청을 집어든 순간부터 잰다. **그 차이가 곧 앱 앞의 큐 대기다.**

nginx라면 로그 포맷에 두 값을 나란히 남긴다.

```nginx
# $request_time         : 클라이언트에서 첫 바이트를 읽기 시작해 응답 마지막
#                         바이트를 다 쓸 때까지. 클라이언트 네트워크까지 포함한다.
# $upstream_connect_time: 업스트림(톰캣)에 TCP 연결을 수립하기까지 걸린 시간.
#                         톰캣의 accept 큐가 꽉 차면 이 값이 커진다.
# $upstream_header_time : 업스트림이 응답 헤더의 첫 바이트를 줄 때까지.
# $upstream_response_time: 업스트림 응답을 다 받을 때까지.
log_format timing '$remote_addr "$request" $status '
                  'rt=$request_time uct=$upstream_connect_time '
                  'uht=$upstream_header_time urt=$upstream_response_time';

access_log /var/log/nginx/access.log timing;
```

읽는 법은 이렇다.

- `uct`(connect time)가 평소 0.001초인데 0.04초로 뛰었다 → **톰캣이 새 연결을 받아들이지 못하고 있다.** 워커 스레드 포화 신호다.
- `urt`(upstream response time)는 큰데 `uct`는 정상이다 → 연결은 바로 됐으니 큐 문제가 아니고, 톰캣 안에서 시간을 쓰고 있다.
- `rt` − `urt`가 크다 → 업스트림은 빨리 응답했는데 클라이언트로 내보내는 데 시간이 걸렸다. 느린 클라이언트나 네트워크 문제다. 서버를 뒤질 일이 아니다.

**둘째, 스레드풀과 커넥션풀의 지표를 직접 본다.** 큐 대기 시간을 직접 재는 지표가 이미 존재한다.

```text
[톰캣 워커 스레드 — 마이크로미터]
  tomcat.threads.busy        지금 요청을 처리 중인 스레드 수
  tomcat.threads.config.max  최대치 (server.tomcat.threads.max, 기본 200)
  -> busy / max 가 1.0에 붙어 있으면 그 뒤로는 전부 accept 큐에서 대기한다.

[HikariCP 커넥션 풀 — 마이크로미터]
  hikaricp.connections.active   대여 중인 커넥션 수
  hikaricp.connections.idle     반납돼 있는 커넥션 수
  hikaricp.connections.pending  ★ 커넥션을 기다리며 멈춰 있는 스레드 수
  hikaricp.connections.acquire  ★ 커넥션 획득까지 걸린 시간 (타이머)
  hikaricp.connections.usage    커넥션을 쥐고 있던 시간 (타이머)
  hikaricp.connections.timeout  획득 실패(타임아웃) 누적 횟수
```

별표 둘이 큐 대기의 직접 증거다. `pending`이 0보다 크다는 것은 **지금 이 순간 커넥션을 못 얻어 멈춰 있는 스레드가 있다**는 뜻이고, `acquire`의 p99가 곧 그 대기 시간의 실측치다.

지표 수집 체계가 없는 서버에서도 HikariCP 자신의 로그를 켜면 30초마다 상태를 찍어 준다.

```text
# logging.level.com.zaxxer.hikari.pool.HikariPool=DEBUG
HikariPool-1 - Pool stats (total=10, active=10, idle=0, waiting=180)
```

`waiting=180`은 180개 스레드가 커넥션 하나를 얻으려고 줄 서 있다는 뜻이다. 이 한 줄이 보이면 수사는 거의 끝난 것이다.

풀이 완전히 말라 대기가 타임아웃까지 가면 이 예외가 뜬다.

```text
java.sql.SQLTransientConnectionException:
  HikariPool-1 - Connection is not available, request timed out after 30000ms.
```

**이 예외를 "DB 장애"로 읽는 것이 흔한 오독이다.** DB는 멀쩡한데 우리 풀이 비어 있는 상황이고, 원인은 커넥션을 오래 쥐고 있는 누군가다.

**셋째, 분산 트레이싱으로 구간마다 시작·종료 시각을 남긴다.** 다음 절의 주제이므로 여기서는 이름만 두고 넘어간다.

### 1-4. 왜 탑다운이어야 하는가

지도를 그렸으니 수사 순서를 정할 수 있다. 원칙은 하나다. **비싼 도구를 나중에 쓴다.**

```text
넓다 ┌─────────────────────────────────────────────────────────┐ 싸다
     │ 0단계  무엇이 변했나 (배포 이력, 설정 이력, 트래픽 그래프)  │ 몇 분
     ├─────────────────────────────────────────────────────────┤
     │ 1단계  지표로 계층 좁히기 (RED / USE)                     │ 몇 분
     ├─────────────────────────────────────────────────────────┤
     │ 2단계  구간 분해 (트레이스 폭포수, 구간 로그)              │ 십여 분
     ├─────────────────────────────────────────────────────────┤
     │ 3단계  프로파일링 (스레드 덤프, 플레임 그래프, 힙 덤프)     │ 수십 분
좁다 └─────────────────────────────────────────────────────────┘ 비싸다
```

3단계를 먼저 하면 왜 손해인가. 스레드 덤프는 그 순간 200개 스레드가 각자 어디에 있는지를 수백 줄로 뱉는다. **어느 구간이 범인인지 모르는 상태에서 이걸 읽으면 정보량에 압사한다.** 반대로 2단계에서 "DB 구간이 범인"까지 좁혀 놓고 덤프를 뜨면, `HikariPool.getConnection`에 몰려 있는 스레드가 눈에 바로 들어온다.

그리고 코드를 눈으로 읽는 것은 이 표에 아예 없다. **코드는 "이 구간이 느리다"가 확정된 뒤에 여는 것**이고, 그 전에 여는 코드 읽기는 수사가 아니라 점(占)이다.

## 2. 수사 절차 — 넓은 곳에서 좁은 곳으로

### 2-1. 0단계 — "갑자기"라는 단어부터 수사한다

질문에 담긴 **"갑자기"**라는 단어가 이미 결정적인 단서다. 서버 코드는 스스로 변하지 않는다. 어제까지 200ms였던 API가 오늘 5초가 됐다면, **그 사이에 무언가가 바뀐 것**이고 그 무언가를 찾는 것이 코드를 읽는 것보다 훨씬 빠르다.

무엇이 바뀔 수 있는지는 유한한 목록이다. 각각을 어디서 확인하는지까지 외워 두면 이 단계가 5분으로 끝난다.

| 무엇이 바뀌었나 | 어디서 확인하나 |
|---|---|
| 배포 | CD 파이프라인 배포 이력, `kubectl rollout history deployment/<name>`, 파드 생성 시각 |
| 설정 변경 | ConfigMap·Secret 리비전, 기능 플래그(feature flag) 변경 이력, 환경변수 diff |
| 라이브러리 업데이트 | 의존성 lock 파일의 커밋 이력, 빌드 산출물의 의존성 트리 비교 |
| 데이터 증가 | 테이블·인덱스 크기 추이, 통계 갱신 시각(`pg_stat_user_tables`) |
| 트래픽 패턴 | LB 요청 수·상태 코드 분포, User-Agent별 집계, 상위 IP 집계 |
| 의존 서비스 | 그 서비스의 상태 페이지·지표, 우리 쪽 외부 호출 응답시간 그래프 |
| 인프라 작업 | 클라우드 이벤트 로그, `kubectl get events`, 노드 교체·재기동 이력 |
| 배치 작업 | 배치 스케줄표와 느려진 시각의 대조, 같은 DB를 쓰는 다른 서비스의 배치 |

**배포**가 시점상 겹치면 가장 유력한 용의자다. 그리고 이때 중요한 판단이 하나 있다 — **원인을 확정하기 전에 롤백하는 것이 대개 옳다.** 롤백은 5분이고 원인 규명은 두 시간일 수 있으므로, 사용자 피해를 먼저 멈추고 원인은 롤백된 이미지로 재현하며 찾는다. (이 판단은 4절의 꼬리질문에서 다시 다룬다.)

**데이터 증가**는 가장 교활한 후보다. 배포도 없었고 트래픽도 그대로인데 어느 날 갑자기 느려지는 사고의 대부분이 여기서 나온다. 확인 쿼리는 이것이다.

```sql
-- 테이블별 규모와 통계 갱신 시각을 한 번에 본다.
-- last_autoanalyze가 며칠 전이면 옵티마이저가 낡은 통계로 계획을 세우고 있다는 뜻이다.
SELECT relname,
       n_live_tup                                AS live_rows,
       pg_size_pretty(pg_relation_size(relid))   AS heap_size,
       pg_size_pretty(pg_indexes_size(relid))    AS index_size,
       last_autoanalyze,
       last_autovacuum
  FROM pg_stat_user_tables
 ORDER BY pg_total_relation_size(relid) DESC
 LIMIT 15;
```

**트래픽 패턴**은 요청량 그래프와 응답시간 그래프를 **같은 시간축에 겹쳐** 보는 것이 요령이다. 두 선이 같이 올라갔으면 용량 문제이고, 요청량은 그대로인데 응답시간만 올라갔으면 건당 처리 비용이 늘어난 것이다. 이 구분만으로 대응 방향이 정반대로 갈린다.

**의존 서비스**를 확인할 때는 상대가 알려주기를 기다리지 않는다. 우리 쪽에서 잰 외부 호출 응답시간 그래프가 우리의 증거다. 상대는 "우리는 정상입니다"라고 말할 수 있지만, 우리 쪽에서 잰 왕복 시간이 3배가 됐다면 그것이 사실이다.

동시에 **영향 범위를 확정**한다. 이것이 0단계의 나머지 절반이고, 수사 범위를 절반으로 접는다.

```text
전체 API가 느리다  ->  공유 자원을 의심한다
                       톰캣 스레드풀, DB 커넥션 풀, GC, DB 자체,
                       CPU, 네트워크, 인프라

특정 API만 느리다  ->  그 API의 고유 경로를 의심한다
                       그 쿼리, 그 외부 호출, 그 로직
```

**공유 자원 후보는 목록이 짧다.** 그래서 "전체가 느리다"는 정보는 나쁜 소식이지만 수사에는 좋은 소식이다.

### 2-2. 1단계 — 모니터링: 지표로 계층을 좁힌다

요청이 지나가는 경로를 계층으로 그리고, 각 계층의 지표를 확인한다. 이때 **큐가 어디에 있는지를 함께 그려 두는 것**이 1절에서 얻은 교훈이다.

```text
클라이언트
   │
   ▼
CDN ── WAF ── LB / API 게이트웨이
   │           (커넥션 한도, 큐, 타임아웃)
   ▼
[★ 톰캣 accept 큐]  <- server.tomcat.accept-count
   │
   ▼
톰캣 워커 스레드 (server.tomcat.threads.max, 기본 200)
   │
   ├──[★ HikariCP 대기 큐]── DB 커넥션 ── PostgreSQL
   │
   ├── Redis 커넥션 풀 ── Redis
   │
   └── HTTP 커넥션 풀 ── 외부 API
```

지표는 두 계열로 나눠 본다. 이름을 붙여 두면 빠뜨리지 않는다.

**RED — 요청 관점의 세 지표.** Rate(초당 요청 수), Errors(에러율), Duration(응답시간)의 머리글자다. "사용자가 겪는 것"을 재는 쪽이다.

Duration을 볼 때 **평균이 아니라 백분위(percentile)를 본다.** 백분위란 값을 오름차순으로 늘어놓았을 때 특정 위치의 값이다 — p99는 "100건 중 99번째로 느린 값", 즉 가장 느린 1%의 경계다.

왜 평균이 위험한지 숫자로 보자.

```text
100건의 응답시간: 99건이 50ms, 1건이 5,000ms

평균 = (99 × 50 + 1 × 5,000) ÷ 100 = (4,950 + 5,000) ÷ 100 = 99.5ms
p99  = 5,000ms
```

**평균은 99.5ms라고 말하고, 실제로 5초를 기다린 사용자가 존재한다.** 평균은 소수의 느린 요청을 나머지에 녹여 버린다. 그리고 그 1%는 하루 100만 요청이면 1만 명이다.

그다음, 백분위들이 어떻게 움직였는지가 진단 정보다.

- **p99만 튀고 p50은 그대로** → 일부 요청만 느리다. GC pause, 특정 파라미터, 캐시 미스 경로, 간헐적 풀 대기가 후보다.
- **p50부터 p99까지 전부 함께 밀렸다** → 공유 자원이 포화됐다. 모든 요청이 같은 줄에서 기다리고 있다는 신호다.

**USE — 자원 관점의 세 지표.** Utilization(사용률), Saturation(포화 정도, 즉 대기 큐의 길이), Errors다. "자원이 겪는 것"을 재는 쪽이다.

계층별로 무엇을 보는지 정리하면 이렇다.

| 계층 | Utilization | Saturation (대기) |
|---|---|---|
| 앱 서버 | CPU 사용률, 힙 사용량 | GC pause 시간·빈도 |
| 톰캣 | `tomcat.threads.busy / max` | accept 큐 길이, nginx `$upstream_connect_time` |
| 커넥션 풀 | `hikaricp.connections.active` | `hikaricp.connections.pending`, `acquire` p99 |
| DB | CPU, 활성 세션 수 | 락 대기, 슬로우 쿼리 수 |
| 캐시 | 히트율 | 응답시간, 커넥션 풀 대기 |

**Saturation 열이 이 표의 핵심이다.** Utilization만 보는 팀은 "CPU 30%인데 왜 느리죠?"에서 멈추고, Saturation을 보는 팀은 그 자리에서 답을 찾는다.

여기서 자주 갈리는 결정적 분기가 하나 있다.

```text
응답이 느리다
   │
   ├─ CPU가 높다  ->  계산하느라 느리다
   │                  비효율 연산, 과도한 직렬화, 정규식, GC,
   │                  N+1로 인한 객체 대량 생성
   │
   └─ CPU가 낮다  ->  ★ 기다리느라 느리다
                      DB 응답, 커넥션 풀 대기, 스레드풀 대기,
                      외부 API, 락, 디스크 I/O
```

**"CPU는 낮은데 느리다"는 것은 곧 "어딘가에서 대기하고 있다"는 뜻이다.** 스레드가 대기 상태일 때는 CPU를 쓰지 않으므로, 200개 스레드가 전부 뭔가를 기다리고 있으면 CPU는 한가하고 서비스는 마비된다. 이 분기 하나로 수사 범위가 절반으로 줄어든다. 3절의 시나리오가 이 분기의 오른쪽 사례다.

캐시 히트율도 빠뜨리면 안 되는 지표다. **히트율이 떨어지면 그 차이만큼이 그대로 DB 부하로 전가된다.** 히트율 95%에서 80%로 떨어졌다면 DB로 가는 조회는 5%에서 20%로, 즉 4배가 된 것이다. 계산은 `20 ÷ 5 = 4`다. 캐시 서버 하나가 빠지거나 인기 키가 만료되는 순간 DB가 죽는 사고가 이 산수에서 나온다.

### 2-3. 2단계 — 구간 분해: 요청 한 건의 시간을 쪼갠다

계층을 좁혔으면 이제 **요청 하나가 어디서 시간을 쓰는지** 분해한다. 1-1의 그림을 실제 데이터로 만드는 작업이다.

#### 분산 트레이싱이란 무엇인가

**분산 트레이싱(distributed tracing)은 요청 하나에 고유한 추적 ID를 붙여 서비스와 구간마다 시작 시각·종료 시각을 남기고, 그것들을 ID로 다시 이어 붙여 하나의 타임라인으로 보는 기법이다.** 이름의 "분산"은 요청이 여러 서비스를 거쳐도 ID가 따라다니므로 서비스 경계를 넘어 하나로 꿰맬 수 있다는 뜻이다.

용어가 두 개 나오는데 각각 한 줄로 정의하면 이렇다.

- **span(스팬)** — 구간 하나. 이름, 시작 시각, 종료 시각, 부모 span의 ID를 가진다. "DB 쿼리 실행", "결제사 호출" 같은 것이 각각 하나의 span이다. 이름이 span인 것은 시간축에서 차지하는 **폭(span)** 하나를 뜻하기 때문이다.
- **trace(트레이스)** — 같은 요청에 속한 span 전체의 묶음. 하나의 trace ID로 묶이고, span들의 부모-자식 관계가 트리를 이룬다.

span을 시간축에 늘어놓으면 계단처럼 겹쳐 보이는데, 이 모양 때문에 **폭포수(waterfall)** 라고 부른다.

```text
trace_id = 4bf92f3577b34da6a3ce929d0e0e4736        (전체 820ms)

GET /orders/8471                              ├────────────────────────────┤ 820ms
  └ order-api: findOrder                        ├──┤                         12ms
  └ order-api: getConnection (HikariCP)            ├──────────────────┤     640ms  ★
  └ order-api: SELECT order_items                                    ├─┤      18ms
  └ payment-api: GET /v1/payments/8471                                 ├────┤ 140ms
      └ payment-api: SELECT payments                                    ├─┤   22ms
  └ order-api: serialize response                                          ├┤  10ms
```

이 그림을 보면 **범인 구간이 눈으로 확정된다.** 820ms 중 640ms가 커넥션 획득이고, 쿼리 실행은 18ms다. "DB가 느리다"가 아니라 "DB에 도달하지 못하고 있다"는 결론이 이 한 장에서 나온다.

추적 ID가 서비스 경계를 넘는 방법은 HTTP 헤더다. W3C가 표준화한 `traceparent` 헤더를 쓴다.

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  │                                │                └ 플래그(샘플링 여부)
             │  │                                └ 이 요청을 보낸 쪽의 span ID (16자리 hex)
             │  └ trace ID (32자리 hex) — 요청 전체를 관통하는 하나의 ID
             └ 버전
```

도구로는 Pinpoint, Scouter, Zipkin, Jaeger, Grafana Tempo 등이 있다. Spring Boot 3 계열이면 Micrometer Tracing이 표준 통로다. **최소한의 도입이라도 반드시 해야 하는 이유는, 트레이스가 있으면 위 폭포수 한 장으로 끝나는 수사가 없으면 몇 시간이 되기 때문이다.**

로그와 트레이스를 연결해 두는 것도 필수다. 로그 패턴에 trace ID를 박아 두면 "이 느린 요청의 로그만" 골라 볼 수 있다.

```yaml
# application.yml — 로그 한 줄마다 traceId/spanId를 남긴다.
# 이게 없으면 트레이스에서 범인 요청을 찾아도 그 요청의 로그를 특정할 수 없다.
logging:
  pattern:
    level: "%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]"
```

#### APM이 없다면 (가산점 포인트)

도구가 없는 환경도 흔하다. 그때도 **구간은 만들 수 있다.** "도구가 없어서 못 찾았다"가 아니라 "도구가 없으면 로그로 구간을 만든다"고 답하는 것이 좋다.

앞단 구간은 액세스 로그로 만든다. 1-3의 nginx `log_format`이 그것이다. 그리고 느린 URL 패턴을 집계한다.

```bash
# 응답시간($request_time) 상위 요청을 뽑는다.
# 필드 위치는 log_format에 맞춰 조정한다.
awk '{print $NF, $0}' /var/log/nginx/access.log | sort -rn | head -20

# URL 패턴별 평균·최대 응답시간 — "어느 엔드포인트가 느린가"의 답
awk '{split($0,a,"rt="); split(a[2],b," "); print $3, b[1]}' access.log \
  | awk '{s[$1]+=$2; c[$1]++; if($2>m[$1]) m[$1]=$2}
         END{for(u in s) printf "%8.3f %8.3f %6d %s\n", s[u]/c[u], m[u], c[u], u}' \
  | sort -rn | head -20
```

앱 내부 구간은 1-2의 after 코드처럼 단계별 로그로 만든다.

DB 구간은 PostgreSQL이 직접 알려준다. 두 가지 수단이 있고 역할이 다르다.

```sql
-- ① log_min_duration_statement: 지정 시간을 넘긴 개별 쿼리를 로그에 남긴다.
--    "어떤 파라미터의 어떤 쿼리가 느렸나"를 개별 건으로 잡을 때 쓴다.
ALTER SYSTEM SET log_min_duration_statement = '200ms';

-- 락 대기도 함께 남긴다. deadlock_timeout(기본 1초)보다 오래 락을 기다린
-- 세션을 로그에 남기므로, 경합이 있었다는 사실 자체가 기록된다.
ALTER SYSTEM SET log_lock_waits = on;

SELECT pg_reload_conf();   -- 두 설정 모두 재기동 없이 반영된다
```

```sql
-- ② pg_stat_statements: 쿼리를 정규화해 누적 통계로 쌓는다.
--    "전체 부하에서 어느 쿼리가 시간을 가장 많이 먹었나"를 볼 때 쓴다.
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT calls,
       round(total_exec_time::numeric)      AS total_ms,
       round(mean_exec_time::numeric, 2)    AS mean_ms,
       round(max_exec_time::numeric, 2)     AS max_ms,
       rows,
       shared_blks_hit,
       shared_blks_read,                    -- 0이 아니면 디스크를 읽었다는 뜻
       left(query, 70)                      AS query
  FROM pg_stat_statements
 ORDER BY total_exec_time DESC
 LIMIT 10;
```

**두 수단의 차이가 중요하다.** `log_min_duration_statement`는 개별 사건을 잡고, `pg_stat_statements`는 총량을 잡는다. 10초짜리 쿼리 한 건보다 50ms짜리 쿼리 10만 건이 DB를 더 괴롭히는데, 전자는 로그에만 남고 후자는 `total_exec_time` 상위에만 나타난다. 그래서 둘 다 본다.

지금 이 순간 DB에서 무슨 일이 벌어지는지는 `pg_stat_activity`가 보여준다.

```sql
-- 지금 실행 중인 세션과 그들이 무엇을 기다리는지.
-- wait_event_type이 'Lock'이면 락 대기, 'IO'면 디스크 읽기 대기다.
SELECT pid,
       now() - query_start        AS duration,
       state,
       wait_event_type,
       wait_event,
       pg_blocking_pids(pid)      AS blocked_by,   -- 나를 막고 있는 세션들
       left(query, 60)            AS query
  FROM pg_stat_activity
 WHERE state <> 'idle'
   AND pid <> pg_backend_pid()
 ORDER BY duration DESC;
```

외부 API 구간은 호출 전후 타이머로 만든다. 여기서 한 가지 실무 요령을 덧붙이면 좋다 — **외부 호출은 응답시간과 함께 "타임아웃이 설정되어 있는지"를 확인한다.** 타임아웃이 없는 외부 호출은 상대가 응답하지 않는 동안 우리 스레드를 무한히 붙잡아 두므로, 남의 장애가 우리 장애가 되는 통로가 된다. (계층별 타임아웃 설계: 10번 문서)

#### 구간별 대표 용의자와 확인 방법

| 범인 구간 | 확인 방법 |
|---|---|
| DB 쿼리 | `pg_stat_statements`의 `mean_exec_time`, `log_min_duration_statement`, `EXPLAIN (ANALYZE, BUFFERS)`로 실행계획 변화, `pg_stat_activity`의 락 대기 |
| 커넥션 풀 대기 | `hikaricp.connections.pending`, `acquire` p99, HikariCP `Pool stats` 로그의 `waiting` |
| 스레드풀 포화 | `tomcat.threads.busy / max`가 1.0, nginx `$upstream_connect_time` 상승 |
| 외부 API | 호출별 응답시간 로그, 타임아웃 설정 여부, 상대 서비스 지표 |
| GC | GC 로그의 pause 시간·빈도 (전체 API가 주기적으로 함께 느려지는 톱니 패턴) |
| 직렬화·CPU 연산 | CPU 사용률 상승과 동반, 플레임 그래프에서 해당 메서드 폭 |

### 2-4. 3단계 — 프로파일링: 프로세스 내부를 연다

구간 분해로도 안 잡히거나(앱 내부 코드가 느린 경우), CPU가 높은 경우, 프로세스 안을 직접 들여다본다.

#### 스레드 덤프 — 지금 각 스레드가 어디에 있는가

**스레드 덤프는 그 순간 JVM 안의 모든 스레드가 각각 어느 코드 줄에 있는지를 찍은 스냅샷이다.**

```bash
# ① 대상 JVM의 PID 확인
jcmd -l
# 또는  jps -l

# ② 스레드 덤프. 3~5초 간격으로 3회 이상 뜬다. 이유는 아래에.
for i in 1 2 3; do
  jcmd <pid> Thread.print > dump-$i.txt
  sleep 4
done
# jstack <pid> 도 같은 결과를 준다. jcmd가 최신 권장 도구다.
```

출력에서 읽어야 하는 것은 딱 두 가지다 — **스레드 상태**와 **스택 최상단**이다.

```text
"http-nio-8080-exec-42" #142 daemon prio=5 tid=0x00007f8a1c0d2000 nid=0x2b1a
   java.lang.Thread.State: TIMED_WAITING (parking)
	at jdk.internal.misc.Unsafe.park(java.base@17/Native Method)
	- parking to wait for  <0x00000006c1234567> (a java.util.concurrent.SynchronousQueue$TransferStack)
	at java.util.concurrent.locks.LockSupport.parkNanos(...)
	at com.zaxxer.hikari.util.ConcurrentBag.borrow(ConcurrentBag.java:151)
	at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:158)   <- ★ 여기
	at com.zaxxer.hikari.HikariDataSource.getConnection(HikariDataSource.java:100)
	at org.springframework.jdbc.datasource.DataSourceUtils.fetchConnection(...)
	...
	at com.example.order.OrderRepository.findById(OrderRepository.java:34)
```

스레드 상태의 뜻은 이렇다.

- **`RUNNABLE`** — 실행 중이거나 실행 가능한 상태. CPU를 쓰고 있을 수 있다. 단, 소켓 읽기 대기도 JVM 입장에서는 `RUNNABLE`로 보이므로(OS 레벨의 블로킹을 JVM이 구분하지 못한다) 스택 최상단이 `SocketRead`류라면 실제로는 기다리는 중이다.
- **`BLOCKED`** — `synchronized` 모니터 락을 얻으려고 대기 중. 다른 스레드가 그 락을 쥐고 있다. 스택에 `- waiting to lock <0x...>`가 나온다.
- **`WAITING` / `TIMED_WAITING`** — `wait()`, `park()`, `sleep()` 등으로 명시적으로 기다리는 중. 커넥션 풀 대기, 외부 응답 대기, 큐에서 작업 대기가 여기 온다.

**그리고 결정적인 것은 스택 최상단이다.** 상태만 보면 "기다린다"까지만 알지만, 최상단을 보면 **무엇을 기다리는지**가 나온다. 위 예시는 `HikariPool.getConnection`이므로 커넥션 풀 대기가 확정된다.

`BLOCKED`의 예시도 보자.

```text
"http-nio-8080-exec-17" #117 daemon prio=5 tid=0x00007f8a1c0a1800 nid=0x2a03
   java.lang.Thread.State: BLOCKED (on object monitor)
	at com.example.coupon.CouponService.issue(CouponService.java:42)
	- waiting to lock <0x00000006c0aabbcc> (a java.lang.Object)   <- ★ 이 락을
	at com.example.coupon.CouponController.issue(CouponController.java:28)
```

`<0x00000006c0aabbcc>`라는 락 주소를 덤프 전체에서 검색하면 **그 락을 쥐고 있는 스레드**를 찾을 수 있다. 그쪽 스택에는 `- locked <0x00000006c0aabbcc>`가 있고, 그 스레드의 최상단이 진짜 범인이다. 100개가 `BLOCKED`고 1개가 락을 쥔 채 느린 쿼리를 돌리고 있다면, 고쳐야 하는 것은 그 1개다.

수백 줄을 눈으로 읽지 않고 집계하는 요령이 있다.

```bash
# 상태별 스레드 수 — 전체 그림
grep 'java.lang.Thread.State' dump-1.txt | sort | uniq -c | sort -rn

# 톰캣 워커 스레드만 골라 상태 집계 — "워커 200개가 지금 무슨 상태인가"
grep -A1 '^"http-nio' dump-1.txt | grep 'Thread.State' | sort | uniq -c | sort -rn

# 스택 최상단 몇 줄을 집계 — "무엇을 기다리는가"의 순위
grep -A4 'java.lang.Thread.State' dump-1.txt | grep $'^\tat ' \
  | sort | uniq -c | sort -rn | head -15
```

```text
[집계 결과 예시]
   183 java.lang.Thread.State: TIMED_WAITING (parking)
    12 java.lang.Thread.State: RUNNABLE
     5 java.lang.Thread.State: WAITING (parking)

   183 	at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:158)
```

**워커 200개 중 183개가 커넥션 풀에서 대기 중이라는 사실이 두 줄로 확정된다.**

**왜 3~5초 간격으로 3회 이상 뜨는가.** 덤프 한 장은 순간의 스냅샷이라, 그 순간 우연히 그 코드를 지나던 스레드와 병목에 갇힌 스레드를 구분할 수 없다. 100ms 만에 지나가는 코드도 200개 스레드가 계속 통과한다면 한 장에는 몇 개가 찍힌다. 간격을 두고 여러 장을 떠서 **여러 장에 걸쳐 같은 지점에 머무는 스레드**를 찾아야 그것이 대기·블로킹의 실체다.

CCTV를 연속 캡처해 계속 같은 자리에 서 있는 사람을 찾는 것과 같다. 한 장으로는 지나가던 사람과 서 있는 사람을 구분할 수 없다. 원리로 보면 이것은 **샘플링 프로파일러가 하는 일을 손으로 하는 것**이다.

#### 힙과 GC — 메모리가 원인일 때

```bash
# 힙 구성과 사용량 스냅샷
jcmd <pid> GC.heap_info
```

```text
 garbage-first heap   total 4194304K, used 3982336K [0x00000006c0000000, ...)
  region size 2048K, 118 young (241664K), 9 survivors (18432K)
 Metaspace       used 78901K, committed 79680K, reserved 1122304K
```

읽는 법은 `used / total` 비율이다. 위 예시는 `3,982,336 ÷ 4,194,304 = 0.95`, 즉 힙의 95%가 차 있다. **힙이 거의 꽉 찬 상태에서는 GC가 공간을 조금 확보하고 곧 다시 꽉 차므로 Full GC가 연발한다.** 이때 애플리케이션 스레드는 GC pause 동안 전부 멈추므로, 전체 API가 주기적으로 함께 느려지는 톱니 패턴이 나타난다.

시간에 따른 추이는 `jstat`으로 본다.

```bash
# 1초 간격 20회. 힙 각 영역의 사용률(%)과 GC 횟수·누적 시간을 보여준다.
jstat -gcutil <pid> 1000 20
```

```text
  S0     S1     E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
  0.00  12.50  87.31  94.12  96.85  93.21   1842   62.104    18   41.882  103.986
                      ^^^^^                         ^^^^^^   ^^   ^^^^^^
                      Old 영역 94% — 회수가 안 되고 있다      Full GC 18회, 누적 41.8초
```

**`O`(Old 영역)가 Full GC 후에도 내려오지 않으면 메모리 누수다.** 정상이라면 Full GC가 Old를 크게 비워 주는데, 참조가 살아 있어 회수할 수 없으면 사용률이 그대로 유지되거나 계단식으로 올라간다. 이 패턴이 확인되면 힙 덤프를 떠서 무엇이 쌓이는지 본다.

```bash
# 힙 덤프. live 옵션은 GC를 먼저 돌려 도달 불가능한 객체를 제외하고 뜬다.
# 주의: 힙 크기만큼 파일이 생기고 그 동안 애플리케이션이 멈춘다.
# 운영에서는 이미 죽어가는 인스턴스에, 트래픽을 뺀 뒤 뜬다.
jcmd <pid> GC.heap_dump -all=false /tmp/heap.hprof

# 덤프를 뜰 여유가 없다면 클래스별 인스턴스 수만 빠르게 본다
jcmd <pid> GC.class_histogram | head -25
```

#### CPU 프로파일러와 플레임 그래프

CPU가 높은 경우에 쓰는 도구다. **샘플링 프로파일러**는 짧은 주기로 스레드 스택을 반복 채취해, 어떤 메서드가 스택에 자주 나타나는지로 CPU 점유를 추정한다. 모든 메서드 호출을 계측하는 방식과 달리 오버헤드가 낮아 **운영 환경에서도 잠깐 붙일 수 있다** (가산점 포인트).

```bash
# async-profiler로 30초간 CPU 프로파일을 떠서 플레임 그래프 HTML로 만든다
./profiler.sh -d 30 -e cpu -f /tmp/flame.html <pid>

# 대기가 원인일 때는 wall-clock 모드를 쓴다. CPU 모드는 "CPU를 쓰는 시간"만
# 재므로, 기다리기만 하는 스레드는 그래프에 거의 나타나지 않는다.
./profiler.sh -d 30 -e wall -f /tmp/flame-wall.html <pid>
```

**플레임 그래프의 읽는 법은 가로 폭이다.** 세로는 호출 스택의 깊이이고, 가로 폭은 그 메서드가 샘플에 등장한 비율 — 곧 시간 점유율이다. 넓고 평평한 봉우리가 범인이다. 위에서 아래로 읽는 것이 아니라 **넓은 곳을 찾아 그 아래로 파고드는 것**이 사용법이다.

그리고 `-e cpu`와 `-e wall`의 구분이 실무에서 중요하다. **CPU 모드는 "계산하느라 느린" 경우를, wall-clock 모드는 "기다리느라 느린" 경우를 보여준다.** 2-2의 분기에서 CPU가 낮았다면 wall 모드를 써야 한다.

## 3. 실제 시나리오 — "CPU는 낮은데 전 API가 느리다"

면접에서는 과정을 서사로 묶어 보여주면 설득력이 크게 올라간다. 그리고 서사의 힘은 **결론을 먼저 말하지 않는 것**에서 나온다. 관측된 사실을 나열하고, 각 사실이 무엇을 배제하는지 짚고, 그래서 어떤 가설이 남는지의 순서로 간다.

### 3-1. 관측된 사실들

알람이 울렸다. 순서대로 확인한 사실은 이렇다.

```text
사실 ①  p99가 300ms에서 5초로. p50도 함께 250ms에서 3.2초로 올랐다.
        에러율도 0.1% -> 4%로 상승 (대부분 게이트웨이 504 타임아웃).

사실 ②  느려진 것이 특정 엔드포인트가 아니다. /orders, /products, /users,
        심지어 DB를 쓰지 않는 /health 까지 전부 느리다.

사실 ③  앱 서버 CPU 20%. 평시(18%)와 거의 같다.
        힙 사용률 62%, GC pause 누적도 평시 수준. Full GC 없음.

사실 ④  DB 서버 CPU 35%. 평시 30%와 큰 차이 없다.

사실 ⑤  tomcat.threads.busy = 200 / tomcat.threads.config.max = 200.
        꽉 찼다.

사실 ⑥  HikariCP: active=10, idle=0, pending=180.
        hikaricp.connections.acquire p99 = 4.2초.

사실 ⑦  pg_stat_statements: 특정 쿼리 하나의 mean_exec_time이 3,100ms.
        평시 이 쿼리의 mean은 4ms였다. calls는 평시의 1.1배로 거의 같다.

사실 ⑧  배포 이력 없음. 설정 변경 없음. 트래픽 총량 평시 대비 1.05배.
```

### 3-2. 각 사실이 무엇을 배제하는가

**사실 ①과 ②의 조합**부터 본다. p50까지 함께 밀렸고 모든 엔드포인트가 느리다. 특히 **DB를 전혀 쓰지 않는 `/health`가 느리다**는 것이 강력한 정보다.

이것이 배제하는 것 — 특정 엔드포인트의 로직이나 쿼리 문제는 아니다. `/health`는 그 코드를 지나가지도 않는데 느리기 때문이다. 남는 것은 **모든 요청이 공유하는 무언가**다. 후보 목록은 짧다: CPU, 힙/GC, 톰캣 스레드풀, DB 커넥션 풀, DB 자체, 네트워크, 인프라.

**사실 ③**은 CPU와 GC를 후보에서 지운다. CPU가 평시 수준이라는 것은 계산 때문이 아니라는 뜻이고, GC pause가 평시 수준이라는 것은 stop-the-world 정지 때문도 아니라는 뜻이다. 2-2의 분기표에서 오른쪽으로 확정됐다 — **기다리느라 느린 것이다.**

**사실 ④**는 "DB 자체가 포화됐다"를 지운다. DB가 CPU를 다 쓰고 있다면 모든 쿼리가 느려질 텐데, DB CPU는 평시 수준이다. **DB는 한가하다.** 이것이 이 시나리오의 반전 포인트다.

**사실 ⑤**는 톰캣 스레드풀이 꽉 찼다는 것을 알려준다. 그런데 여기서 사실 ③과 나란히 놓으면 이상한 그림이 된다 — **스레드 200개가 전부 사용 중인데 CPU는 20%다.** 스레드가 CPU를 쓰지 않으면서 점유되어 있다는 것은 200개가 전부 **뭔가를 기다리고 있다**는 뜻이다. 1-1의 그림에서 별표 붙인 칸에 200개가 몰려 있는 상태다.

**사실 ⑥**이 "무엇을 기다리는지"를 확정한다. 커넥션 풀이다. `active=10`으로 풀 전체가 대여 중이고 `idle=0`이며, `pending=180`은 180개 스레드가 커넥션을 얻으려고 멈춰 있다는 뜻이다. 획득에 p99 4.2초가 걸린다.

여기서 수사는 다음 질문으로 넘어간다. **왜 커넥션 10개가 돌아오지 않는가?** 가능성은 둘이다.

- (a) 커넥션을 쓰는 작업 하나가 오래 걸린다 — 느린 쿼리
- (b) 작업은 빠른데 커넥션을 오래 쥐고 있다 — 트랜잭션 안에서 외부 API를 호출하거나, 반납을 빠뜨린 누수

**사실 ⑦**이 (a)로 확정한다. 특정 쿼리의 평균 실행 시간이 4ms에서 3,100ms로, 775배가 됐다. 계산은 `3,100 ÷ 4 = 775`다. 그리고 `calls`가 평시의 1.1배라는 것이 결정적이다 — **호출량이 늘어서가 아니라 건당 비용이 늘었다.**

**사실 ⑧**은 배포와 설정 변경, 트래픽 급증을 지운다. 2-1의 목록에서 남는 것은 **데이터 증가**와 **의존 서비스**, **인프라 작업**, **배치**다. 그리고 사실 ⑦이 DB 쿼리를 가리키고 있으므로 데이터 증가가 유력하다.

### 3-3. 남은 가설을 산수로 확인한다

가설은 이제 하나다. **"쿼리 하나가 3.1초로 느려져 커넥션 풀을 잠식했고, 그 결과 톰캣 워커 전체가 커넥션 대기로 소진되어 무관한 API까지 느려졌다."**

이 가설이 성립하는지 Little's Law로 검산해 보자. Little's Law는 `동시에 시스템 안에 있는 개수 L = 도착률 λ × 체류 시간 W`라는 관계다(17번 문서). 여기서는 "동시에 대여 중인 커넥션 수 = 초당 커넥션 요청 수 × 커넥션을 쥐고 있는 시간"으로 쓴다.

**평시 검산.**

```text
전체 유입             250 TPS
커넥션 평균 점유 시간   8ms = 0.008초

필요 커넥션 = 250 × 0.008 = 2개
풀 크기 10개  ->  여유롭다. pending은 0이다.
```

**장애 시 검산.** 문제의 쿼리를 쓰는 엔드포인트가 전체 트래픽의 5%라고 하자.

```text
그 엔드포인트 유입     250 × 0.05 = 12.5 TPS
커넥션 점유 시간        3.1초 (쿼리 실행 시간이 곧 점유 시간이다)

필요 커넥션 = 12.5 × 3.1 = 38.75개
풀 크기 10개  ->  필요량이 풀 크기의 3.875배. 계산: 38.75 ÷ 10 = 3.875
```

**이 한 줄이 사고의 전부를 설명한다.** 트래픽의 5%밖에 안 되는 엔드포인트 하나가 필요로 하는 커넥션이 풀 전체의 3.9배다. 그러니 풀 10개는 100% 이 쿼리에 점유되고, **나머지 95%의 트래픽(237.5 TPS)은 커넥션을 아예 얻을 수 없다.**

붕괴까지 걸리는 시간도 계산된다.

```text
풀이 이 쿼리를 소화할 수 있는 최대 속도 = 10개 ÷ 3.1초 = 3.2 TPS
그 엔드포인트로 들어오는 속도            = 12.5 TPS
                                       ─────────────
초당 대기로 쌓이는 요청                  = 12.5 − 3.2 = 9.3건/초

톰캣 워커 200개가 전부 커넥션 대기로 소진되기까지
        = 200 ÷ 9.3 ≈ 21.5초
```

**21초.** 쿼리 하나가 느려진 시점부터 21초 만에 서버 전체가 마비된다. 그리고 워커 200개가 전부 커넥션 대기에 묶인 순간부터는 **DB를 쓰지 않는 `/health`조차 워커를 배정받지 못해 accept 큐에서 기다린다.** 사실 ②가 이렇게 설명된다.

이것이 **연대책임의 메커니즘**이다. 겉으로 느려진 곳(전체 API)과 진짜 원인(쿼리 하나)이 다른 이유는, 그 사이에 **커넥션 풀과 스레드풀이라는 공유 자원**이 끼어 있기 때문이다. 느린 쿼리 하나가 공유 자원을 잠식하면 멀쩡한 API까지 연대책임을 진다.

### 3-4. 진짜 원인까지 — 실행계획을 본다

가설이 검산으로 확인됐으니 마지막 질문 하나가 남는다. **왜 그 쿼리가 4ms에서 3.1초가 됐는가?** `EXPLAIN`을 붙인다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
 WHERE user_id = 40219
 ORDER BY created_at DESC
 LIMIT 20;
```

```text
Limit  (cost=0.00..184203.11 rows=20 width=248)
       (actual time=3101.882..3102.004 rows=20 loops=1)
  ->  Index Scan Backward using idx_orders_created_at on orders
        (actual time=3101.879..3101.998 rows=20 loops=1)
        Filter: (user_id = 40219)
        Rows Removed by Filter: 42881903          <- ★ 20건 찾으려고 4,288만 건을 버렸다
        Buffers: shared hit=1204 read=419733      <- ★ 41만 페이지를 디스크에서 읽었다
Planning Time: 0.19 ms
Execution Time: 3102.1 ms
```

두 줄이 범인을 자백한다.

**`Rows Removed by Filter: 42881903`** — 이 쿼리는 `created_at` 인덱스를 최신순으로 거꾸로 훑으면서 `user_id = 40219`인 행을 찾고 있다. 20건을 모으기까지 4,288만 건을 읽고 버렸다.

**`read=419733`** — `Buffers: shared hit=N read=M`에서 `hit`은 메모리(shared_buffers)에서 찾은 페이지 수, `read`는 디스크에서 읽어 온 페이지 수다. 41만 페이지를 디스크에서 읽었다. 페이지 하나가 8KB이므로 `419,733 × 8KB ≈ 3.2GB`를 읽은 것이다.

**그런데 왜 어제는 4ms였는가.** 데이터가 커졌기 때문이다. 이 쿼리에는 `(user_id)` 인덱스가 없고 `(created_at)` 인덱스만 있었다.

```text
테이블이 작았을 때 (100만 행, 사용자 1만 명)
  한 사용자당 평균 100건. created_at 인덱스를 최신순으로 훑으면
  수백 건 안에서 그 사용자의 20건이 모인다.  ->  4ms. 통과.

테이블이 커진 뒤 (1억 행, 사용자 300만 명)
  한 사용자당 평균 33건이고, 최근 데이터에 그 사용자의 주문이 없다면
  4,288만 건을 훑어야 20건이 모인다.        ->  3.1초. 사고.
```

**같은 쿼리, 같은 인덱스, 같은 코드인데 데이터가 커지면서 절벽에서 떨어진 것이다.** `ORDER BY ... LIMIT`은 "필요한 만큼만 읽고 멈춘다"는 최적화 때문에 작은 테이블에서 유난히 빠르게 보이고, 그래서 이 절벽은 테스트에서 절대 발견되지 않는다. (테스트가 이런 결함을 못 잡는 구조적 이유: 23번 문서)

옵티마이저가 계획을 바꾸는 경우도 함께 알아두면 좋다. **선택성이 나빠지면 플래너가 인덱스를 포기하고 순차 스캔으로 전환한다.** 위 사례처럼 인덱스 스캔을 유지한 채 느려지는 것과, 계획 자체가 `Seq Scan`으로 바뀌는 것은 다른 사건이지만 원인은 같다 — 데이터가 커져서 원래 계획의 가정이 깨졌다. 그리고 통계가 낡았을 때도(대량 적재 후 `ANALYZE`가 안 돌았을 때) 플래너가 잘못된 계획을 고르는데, 이것은 `pg_stat_user_tables.last_autoanalyze`로 확인한다.

### 3-5. 조치와 재발 방지

조치는 조건에 맞는 인덱스를 추가하는 것이다.

```sql
-- WHERE user_id = ? ORDER BY created_at DESC LIMIT 20 에 맞춘 복합 인덱스.
-- 컬럼 순서가 중요하다: 등호 조건(user_id)이 앞, 정렬 기준(created_at)이 뒤.
-- 그러면 user_id로 좁힌 구간 안이 이미 created_at 순으로 정렬돼 있어
-- 앞에서 20건만 읽고 멈출 수 있다.
CREATE INDEX CONCURRENTLY idx_orders_user_created
    ON orders (user_id, created_at DESC);

-- CONCURRENTLY: 인덱스를 만드는 동안 그 테이블에 대한 쓰기를 막지 않는다.
-- 1억 행 테이블에 이걸 빼고 만들면 인덱스 생성 시간 내내 INSERT/UPDATE가
-- 막혀, 병목을 고치려다 더 큰 장애를 만든다.
```

```text
[인덱스 추가 후]
Limit  (cost=0.57..8.94 rows=20 width=248)
       (actual time=0.028..0.041 rows=20 loops=1)
  ->  Index Scan using idx_orders_user_created on orders
        (actual time=0.026..0.037 rows=20 loops=1)
        Index Cond: (user_id = 40219)
        Buffers: shared hit=5              <- 41만 -> 5. 디스크 읽기 0.
Execution Time: 0.06 ms
```

`Rows Removed by Filter`가 사라졌고 `Buffers`가 5로 줄었다. 3,102ms에서 0.06ms가 됐다.

**재발 방지가 조치의 절반이다.** 이번 사고에서 배운 것을 지표와 알람으로 바꿔 놓는다.

- `hikaricp.connections.pending > 0`이 N초 이상 지속되면 알람. 이 지표가 있었다면 21초의 붕괴 과정 중 첫 몇 초에 알 수 있었다.
- `hikaricp.connections.acquire` p99에 알람. 사용자 영향과 가장 직결된 지표다.
- `pg_stat_statements`의 `mean_exec_time` 급증에 알람. 쿼리별 회귀 감지다.
- `log_min_duration_statement`를 켜 두어 느린 쿼리가 로그로 남게 한다.
- 테이블 규모 추이를 대시보드에 둔다. **데이터 증가는 예측 가능한 사고**이므로, 절벽에 닿기 전에 알 수 있다.

그리고 포스트모템에 반드시 남길 질문이 하나 있다. **"왜 유저보다 먼저 몰랐는가."** 이번 사고의 답은 "커넥션 풀 지표에 알람이 없었다"이고, 그것이 곧 위 목록이 된다.

## 4. 꼬리질문 대비 포인트

### "평균 응답시간은 정상인데 p99만 튄다면 어디를 보나요?"

전체가 아니라 **일부 요청만** 느린 패턴이다. 2-2에서 본 백분위 해석의 왼쪽 갈래다. 후보는 넷이다.

**① 주기성이 있으면 GC pause나 배치 작업이다.** p99 그래프가 일정 간격으로 톱니처럼 튄다면 무언가 주기적으로 도는 것이다 — Full GC, 캐시 갱신 배치, 백업, 통계 집계. `jstat -gcutil`로 GC 시각과 튀는 시각을 맞춰 보면 바로 갈린다.

**② 특정 파라미터에서만 느리면 데이터 편중이다.** 대형 고객사의 데이터가 비대해서 그 고객의 요청만 느린 경우(hot data), 인기 상품 하나에 조회가 몰려 그 행의 락 경합이 생기는 경우. 느린 요청의 파라미터를 모아 공통점을 찾는다.

**③ 캐시 미스 경로다.** 히트는 2ms, 미스는 400ms라면 히트율 99%인 API의 p99는 미스 경로의 시간이다. 이 경우 p99를 낮추는 방법은 코드 최적화가 아니라 히트율을 올리는 것이거나, 미스 경로 자체를 빠르게 만드는 것이다.

**④ 풀의 간헐적 대기다.** 평소에는 커넥션이 남지만 순간적인 유입 스파이크에 몇 건이 대기하는 경우. `hikaricp.connections.acquire`의 p99가 p50보다 훨씬 크면 이 패턴이다.

접근법은 **느린 요청만 골라 트레이스를 보는 것**이다. 대부분의 APM은 지연 상위 요청을 따로 모아 준다. 그 트레이스들의 공통 패턴 — 시간대, 파라미터, 특정 서버 인스턴스, 특정 구간 — 을 찾으면 위 넷 중 하나로 떨어진다.

한 가지 덧붙이면 좋은 것이 있다. **특정 인스턴스만 느린 경우**를 놓치지 않는 것이다. 인스턴스 10대 중 1대만 느리면 그 1대의 요청이 전체의 10%이므로 p90~p99에 나타난다. 서버별로 지표를 나눠 볼 수 있어야 이걸 잡는다.

### "스레드 덤프는 왜 한 번이 아니라 여러 번 뜨나요?"

덤프 한 장은 순간의 스냅샷이라, **그 순간 우연히 그 코드를 지나던 스레드와 병목에 갇힌 스레드를 구분할 수 없다.**

100ms 만에 지나가는 정상 코드도, 스레드 200개가 계속 통과하고 있으면 스냅샷 한 장에는 몇 개가 찍힌다. 그것만 보고 "여기가 병목"이라고 판단하면 오진이다.

간격을 두고 여러 장을 떠서 **여러 장에 걸쳐 같은 지점에 머무는 스레드**를 찾아야 그것이 대기·블로킹의 실체다. 3초 뒤에도 같은 스레드가 같은 줄에 서 있다면 그 스레드는 최소 3초를 그 자리에서 보낸 것이고, 그건 우연이 아니다.

CCTV를 연속 캡처해서 계속 같은 자리에 서 있는 사람을 찾는 것과 같다. 원리로 말하면 **샘플링 프로파일러가 하는 일을 수동으로 하는 것**이다 — 샘플링 프로파일러도 짧은 주기로 스택을 반복 채취해 자주 등장하는 지점을 병목으로 판정한다.

간격은 3~5초, 횟수는 3회 이상이 실무 기준이다. 간격이 너무 짧으면 세 장이 거의 같은 그림이라 비교 의미가 없고, 너무 길면 그 사이에 상황이 바뀐다.

### "APM 같은 도구가 전혀 없는 환경이라면 어떻게 하시겠어요?"

**구간을 로그로 직접 만든다.** 순서대로 답한다.

앞단은 액세스 로그다. nginx라면 `$request_time`, `$upstream_connect_time`, `$upstream_header_time`, `$upstream_response_time`을 로그 포맷에 넣는다. 이 네 값만 있어도 "클라이언트 구간 / 큐 대기 / 서버 처리"가 갈린다.

앱 내부는 단계별 타이머 로그다. 1-2의 after 코드처럼 DB·외부 호출·직렬화를 나눠 남긴다. 요청 ID를 MDC에 넣어 같은 요청의 로그를 묶을 수 있게 하는 것이 필수다 — 이게 없으면 동시 요청의 로그가 섞여 읽을 수 없다.

DB는 `log_min_duration_statement`와 `pg_stat_statements`다. 둘 다 확장이나 재기동 없이(전자는 `pg_reload_conf()`, 후자는 확장 설치만) 켤 수 있다.

OS 레벨은 기본 도구로 본다 — `top`/`vmstat`으로 CPU·메모리·컨텍스트 스위칭, `iostat`으로 디스크, `ss -s`로 소켓 상태 요약, `jstat -gcutil`로 GC.

JVM 내부는 `jcmd`다. `Thread.print`, `GC.heap_info`, `GC.class_histogram`은 JDK에 기본 포함이라 추가 설치가 없다.

그리고 답의 마무리로 반드시 붙여야 하는 것이 있다. **"이번에 없어서 고생한 관측 수단을 도입하는 것까지가 대응의 마무리"**라는 태도다. 같은 장애가 다시 오면 또 몇 시간을 쓸 것이고, 그것은 도구가 없어서가 아니라 도입하지 않아서다.

### "느려진 원인을 못 찾고 있는데 장애는 진행 중입니다. 어떻게 하시겠어요?" (시니어 변별 포인트)

**원인 규명과 서비스 복구를 분리한다. 복구가 우선이다.**

이것이 핵심이고, 주니어와 갈리는 지점이다. 원인을 알아야 고칠 수 있다는 생각은 자연스럽지만, 운영에서는 **원인을 모른 채로도 실행할 수 있는 완화 조치들이 있다.**

- **최근 배포가 있었다면 원인 확정 전이라도 롤백.** 롤백은 5분이고 원인 규명은 두 시간일 수 있다.
- **스케일 아웃.** 원인이 용량이든 아니든, 인스턴스를 늘리면 인스턴스당 부하가 줄어 시간을 벌 수 있다. 단, 병목이 DB나 외부 API 같은 공유 자원이면 스케일 아웃이 오히려 그쪽 부하를 늘려 악화시킨다는 것을 알고 있어야 한다.
- **캐시 TTL 연장.** DB 부하를 줄이는 가장 빠른 카드다.
- **비핵심 기능 차단(graceful degradation).** 추천, 통계, 부가 알림을 끄고 핵심 경로만 살린다. (15번 문서)
- **부하 제한(load shedding).** 받을 수 있는 만큼만 받고 나머지는 빨리 거절한다. 전부 느려지는 것보다 일부를 확실히 처리하는 것이 낫다. (21번 문서)

**단, 복구 조치 전에 증거를 확보해 둔다.** 이것이 답을 완성시키는 부분이다.

```bash
# 재기동·롤백 전 30초. 이걸 안 하면 현장이 사라진다.
jcmd <pid> Thread.print > /tmp/dump-$(date +%H%M%S).txt
jcmd <pid> GC.heap_info  > /tmp/heap-$(date +%H%M%S).txt
jstat -gcutil <pid> 1000 10 > /tmp/gc-$(date +%H%M%S).txt
curl -s localhost:8080/actuator/metrics/hikaricp.connections.pending > /tmp/pool.json
```

```sql
-- DB 쪽 현장도 함께 뜬다. 지금 무엇이 돌고 있고 무엇이 막혀 있는지.
SELECT * FROM pg_stat_activity WHERE state <> 'idle';
SELECT * FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 20;
```

**재기동하면 스레드 상태, 힙 내용, 풀 상태가 전부 초기화되어 사후 분석(포스트모템)이 불가능해진다.** 그리고 원인을 모른 채 복구하면 같은 장애가 반복된다.

인스턴스가 여러 대라면 더 좋은 방법이 있다. **한 대만 트래픽에서 떼어 내고 살려 둔다.** LB에서 빼면 사용자 영향은 없어지고, 그 인스턴스는 문제 상태를 그대로 유지한 채 마음껏 프로파일링할 수 있다. 나머지는 재기동해 서비스를 복구한다.

**"복구 먼저, 그러나 증거 보존과 함께"**가 운영 경험자의 답이다.

### "병목을 찾아 고쳤습니다. 그다음은요?"

재발 방지의 체계화다. 셋으로 나눠 답한다.

**① 이번에 범인이었던 지표에 알람을 건다.** 목적은 하나다 — **다음엔 유저보다 먼저 알기 위해.** 3-5의 목록이 그것이다. 알람 없는 개선은 "이번엔 운이 좋았다"에 가깝다.

**② 포스트모템으로 "왜 몰랐는지"를 기록한다.** 사고 보고서에서 "무엇이 원인이었나"보다 중요한 질문이 **"왜 유저 문의를 통해 알았나"**다. 앞의 질문은 이번 사고를 설명하고, 뒤의 질문은 다음 사고를 막는다.

**③ 같은 패턴의 잠재 병목이 다른 곳에 없는지 점검한다.** 이번에 `(user_id)` 인덱스가 없어서 터졌다면, 같은 패턴의 `ORDER BY ... LIMIT` 쿼리가 다른 테이블에 몇 개 더 있을 가능성이 높다. 하나를 고쳤을 때 같은 유형을 한 번에 훑는 것이 비용 효율이 가장 좋은 시점이다.

그리고 마지막에 개념 하나를 얹으면 가산점이 된다. **병목 하나를 고치면 병목은 사라지지 않고 다음 지점으로 이동한다.** 제약 이론(theory of constraints)이 말하는 것이고, 실제로 이번 사례에서도 그렇다.

```text
쿼리가 3.1초  ->  커넥션 풀(10개)이 병목  ->  톰캣 워커(200개)가 다 묶임

인덱스 추가로 쿼리가 0.06ms가 되면
  -> 커넥션 풀은 여유로워진다
  -> 그러면 다음 한계는 무엇인가?
     톰캣 워커 200개? DB의 max_connections? 외부 API의 처리량? CPU?
```

**"병목이 다음으로 이동했으니 다음 한계는 어디인지 부하 테스트로 확인한다"**까지 말하면, 문제를 하나 고친 사람이 아니라 시스템의 용량 곡선을 이해하는 사람으로 보인다. (부하 테스트로 포화점을 찾는 방법: 7번 문서)

## 한 줄 요약

병목 추적은 "무엇이 변했나" 확정 → 지표(RED/USE)로 계층 좁히기 → 트레이스로 구간 분해 → 프로파일링으로 내부 확인의 **탑다운 수사**이며, 매 단계에서 다음 행선지를 정하는 것은 추측이 아니라 **측정된 데이터**다 — 그리고 이 수사에서 가장 자주 놓치는 구간은 애플리케이션 로그에 잡히지 않는 **큐 대기**(톰캣 워커 대기, 커넥션 풀 대기)이므로, 앞단이 잰 시간과 앱이 잰 시간의 차이, 그리고 앱이 잰 DB 구간과 DB가 잰 실행 시간의 차이를 반드시 확인해야 "느린 쿼리 하나가 공유 자원을 잠식해 전 API가 연대책임을 지는" 구조를 21초 안에 읽어낼 수 있다.
