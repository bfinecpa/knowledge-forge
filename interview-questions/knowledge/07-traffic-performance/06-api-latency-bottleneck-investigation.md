# API 병목 추적 — 감이 아닌 측정으로, 모니터링에서 프로파일링까지

> 핵심 관전 포인트: **병목 추적은 넓은 곳에서 좁은 곳으로 내려가는
> 탑다운 과정이다. ① 먼저 "무엇이 변했는가"를 확정하고(배포·트래픽·데이터),
> ② 모니터링 지표(p99, 에러율, 자원 사용률)로 어느 계층이 느린지 좁히고,
> ③ APM 트레이스로 요청 한 건의 시간을 구간별로 분해해 범인 구간을 찾고,
> ④ 마지막에 그 구간만 프로파일링(스레드 덤프, 플레임 그래프)으로
> 파고든다. 순서의 핵심은 "코드부터 열어보지 않는 것" — 추측이 아니라
> 측정이 다음 단계를 결정한다.**

---

## 0. 질문 + 의도

**질문**: "API 응답이 갑자기 느려졌습니다. 병목 지점을 찾는 과정을
처음부터 끝까지 설명해주세요. (모니터링 → 프로파일링)"

**출제 의도**: 이 질문의 진짜 목적은 방법론이다 — 어디부터 보는지
(지표 → 구간 분해 → 프로파일링), 판단의 근거가 추측인지 측정인지.
체계 없이 "코드를 봤어요"로 시작하는 사람은 실전에서 몇 시간을 낭비한다.
장애 상황에서 침착하게 범위를 좁혀가는 수사 능력을 확인하는 질문이다.

## 1. 0단계 — "갑자기"라는 단어부터 수사한다

느려짐이 **갑자기** 시작됐다면, 그 시점에 **무언가 변한 것**이다.
코드를 열기 전에 변화 후보부터 나열한다.

- **배포가 있었나?** — 최근 배포·설정 변경·라이브러리 업데이트.
  시점이 겹치면 가장 유력한 용의자다 (롤백이 가장 빠른 복구일 수 있음).
- **트래픽이 변했나?** — 이벤트, 마케팅, 크롤러, 특정 클라이언트의
  재시도 폭주. 요청량(rate) 그래프를 응답시간 그래프와 겹쳐 본다.
- **데이터가 변했나?** — 테이블이 임계 크기를 넘어 실행계획이 바뀌었거나,
  특정 유저의 데이터가 비대해졌거나(hot data).
- **주변 환경이 변했나?** — 같은 DB를 쓰는 다른 서비스의 배치,
  인프라 작업, 외부 API의 응답 지연.

동시에 **영향 범위를 확정**한다: 전체 API가 느린가, 특정 API만 느린가?
전체가 느리면 공유 자원(DB, 커넥션 풀, GC, 인프라)이,
특정 API만 느리면 그 API의 경로(특정 쿼리, 특정 외부 호출)가 유력하다.

## 2. 1단계 — 모니터링: 지표로 계층을 좁힌다

요청이 지나가는 경로를 계층으로 그리고, 각 계층의 지표를 확인한다.

```
클라이언트 → LB/게이트웨이 → 앱 서버 → (커넥션 풀) → DB
                                └→ 캐시(Redis)
                                └→ 외부 API
```

- **요청 단위 지표 (RED)**: Rate(처리량)·Errors(에러율)·Duration(지연).
  이때 평균이 아니라 **p95/p99**를 본다 — 평균은 소수의 느린 요청을
  숨긴다. 평균 50ms에 p99가 5초라면 "일부 요청이 심하게 느린" 것이고,
  전체 백분위가 함께 밀렸다면 "공유 자원이 포화된" 것이다.
- **자원 단위 지표 (USE)**: 각 계층의 Utilization(사용률)·
  Saturation(포화/대기 큐)·Errors. 구체적으로:
    - 앱 서버: CPU, 힙 사용량, **GC pause 시간**, 스레드풀 활성/큐 대기 수
    - 커넥션 풀: 활성 커넥션 수, **커넥션 대기 시간** (HikariCP 지표)
    - DB: CPU, 슬로우 쿼리 수, 락 대기
    - 캐시: 히트율 (히트율 급락 → DB로 부하 전가)

여기서 자주 갈리는 분기가 하나 있다 — **"응답은 느린데 CPU는 낮다"**.
이건 계산이 느린 게 아니라 **어딘가를 기다리고 있다**는 뜻이다
(DB 응답, 커넥션 풀 대기, 외부 API, 락). 반대로 CPU가 높으면
비효율 연산·직렬화·GC가 용의자다. 이 분기 하나로 수사 범위가 절반으로
줄어든다.

## 3. 2단계 — 구간 분해: 요청 한 건의 시간을 쪼갠다

계층을 좁혔으면, 이제 **요청 하나가 어디서 시간을 쓰는지** 분해한다.

- **APM / 분산 트레이싱** (Pinpoint, Scouter, Zipkin, Grafana Tempo 등):
  느린 요청의 트레이스를 열면 폭포수(waterfall)로 구간별 소요 시간이
  보인다 — "전체 3초 중 DB 쿼리 하나가 2.8초" 같은 식으로 범인 구간이
  바로 드러난다. 병목 추적에서 가장 강력한 도구다.
- **APM이 없다면** (가산점 포인트): 수동으로도 분해할 수 있다.
    - 액세스 로그에 처리 시간 필드를 남겨(nginx `$request_time` 등)
      느린 요청의 URL 패턴을 집계
    - DB 슬로우 쿼리 로그로 DB 구간을 확인
    - 외부 호출 전후 로그 타이머로 외부 구간을 확인
  즉 "도구가 없어서 못 찾았다"가 아니라 "도구가 없으면 로그로
  구간을 만든다"고 답하는 것이 좋다.

구간별 대표 용의자와 확인 방법:

| 범인 구간 | 확인 방법 |
|---|---|
| DB 쿼리 | 슬로우 쿼리 로그, 실행계획(`EXPLAIN`) 변화, 락 대기 |
| 커넥션 풀 대기 | 풀 지표(대기 시간·대기 스레드 수) |
| 외부 API | 호출별 응답시간 로그, 타임아웃 설정 여부 |
| GC | GC 로그의 pause 시간·빈도 (전체 API가 주기적으로 같이 느려짐) |
| 스레드풀 포화 | 활성 스레드 수 = 최대치, 큐 적체 |

## 4. 3단계 — 프로파일링: 프로세스 내부를 연다

구간 분해로도 안 잡히거나(앱 내부 코드가 느림), CPU가 높은 경우
프로세스 안을 직접 들여다본다.

- **스레드 덤프** — 지금 각 스레드가 뭘 하고 있는지의 스냅샷.
  실무 요령은 **3~5초 간격으로 3회 이상 떠서 비교**하는 것이다.
  한 장은 우연일 수 있지만, 여러 장에서 같은 지점에 스레드가 몰려
  있으면(같은 락에 `BLOCKED`, 같은 외부 호출에 `WAITING`) 그곳이
  병목이다. 마치 CCTV를 연속 캡처해서 계속 같은 자리에 서 있는
  사람을 찾는 것과 같다.
- **CPU 프로파일러 / 플레임 그래프** — async-profiler 같은 샘플링
  프로파일러로 "CPU 시간을 어떤 메서드가 먹는지"를 불꽃 모양 그래프로
  본다. 샘플링 방식이라 오버헤드가 낮아 **운영 환경에서도 잠깐 붙일 수
  있다** (가산점 포인트).
- **힙 덤프 / GC 분석** — 메모리가 원인일 때. 힙 사용량이 계단식으로
  올라가며 Full GC가 잦아지면 누수를 의심하고 힙 덤프로 무엇이 쌓이는지
  확인한다.

## 5. 실제 시나리오 예시 — "CPU는 낮은데 전 API가 느리다"

면접에서 과정을 서사로 묶어 보여주면 설득력이 크게 올라간다.

1. 알람: p99가 300ms → 5초. 에러율도 상승 (타임아웃).
2. 범위 확정: 특정 API가 아니라 **전체 API**가 느림 → 공유 자원 의심.
3. 지표: 앱 CPU 20%로 낮음 → "기다리는 중". 커넥션 풀 지표를 보니
   **활성 커넥션이 최대치에 붙어 있고 대기 스레드가 쌓임** → 풀 고갈.
4. 원인 추적: 풀을 고갈시킨 건 누구인가 → DB 슬로우 쿼리 로그에서
   특정 쿼리가 수 초씩 커넥션을 점유. `EXPLAIN` 확인 결과 데이터
   증가로 실행계획이 인덱스 → 풀스캔으로 바뀜.
5. 조치: 인덱스 추가로 복구. 재발 방지로 커넥션 풀 대기 시간 알람과
   슬로우 쿼리 알람 추가.

핵심 교훈: **겉으로 느려진 곳(전체 API)과 진짜 원인(쿼리 하나)은
다르다.** 느린 쿼리 하나가 커넥션 풀이라는 공유 자원을 잠식하면
멀쩡한 API까지 연대책임을 진다.

## 6. 꼬리질문 대비 포인트

### "평균 응답시간은 정상인데 p99만 튄다면 어디를 보나요?"

전체가 아니라 **일부 요청만** 느린 패턴이다. 후보는:
① 주기성이 있으면 GC pause나 배치 작업(캐시 갱신, 백업),
② 특정 파라미터에서만 느리면 데이터 편중(hot key, 비대한 유저),
③ 캐시 미스 경로(히트는 빠르고 미스만 느림),
④ 커넥션/스레드 풀의 간헐적 대기.
느린 요청만 샘플링해 트레이스를 보고 공통 패턴(시간대·파라미터·서버)을
찾는 것이 접근법이다.

### "스레드 덤프는 왜 한 번이 아니라 여러 번 뜨나요?"

덤프 한 장은 순간의 스냅샷이라, 그 순간 우연히 그 코드를 지나던
스레드와 병목에 갇힌 스레드를 구분할 수 없다. 간격을 두고 여러 장을
떠서 **여러 장에 걸쳐 같은 지점에 머무는 스레드**를 찾아야 그것이
대기·블로킹의 실체다. 샘플링 프로파일러의 원리를 수동으로 하는 셈이다.

### "APM 같은 도구가 전혀 없는 환경이라면 어떻게 하시겠어요?"

구간을 로그로 직접 만든다 — 액세스 로그에 처리 시간을 남겨 느린
엔드포인트를 집계하고, DB 슬로우 쿼리 로그를 켜고, 외부 호출 전후에
소요 시간 로그를 심는다. OS 레벨은 `top`/`vmstat`으로 CPU·메모리,
`jstat`으로 GC를 본다. 그리고 사후에는 "이번에 없어서 고생한 관측
수단을 도입하는 것"까지가 대응의 마무리라고 답하면 좋다.

### "느려진 원인을 못 찾고 있는데 장애는 진행 중입니다. 어떻게 하시겠어요?" (시니어 변별 포인트)

**원인 규명과 서비스 복구를 분리한다.** 복구가 우선이다 —
최근 배포가 있었다면 원인 확정 전이라도 롤백, 스케일 아웃, 캐시 TTL
연장, 비핵심 기능 차단(degradation) 같은 완화 조치를 먼저 실행한다.
단, 복구 조치 전에 **스레드 덤프·힙 덤프·지표 스냅샷 등 증거를
확보**해 둔다 — 재기동하면 현장이 사라져 사후 분석(포스트모템)이
불가능해지기 때문이다. "복구 먼저, 그러나 증거 보존과 함께"가
운영 경험자의 답이다.

### "병목을 찾아 고쳤습니다. 그다음은요?"

재발 방지의 체계화다. ① 이번에 범인이었던 지표(커넥션 풀 대기,
슬로우 쿼리 등)에 알람을 건다 — 다음엔 유저보다 먼저 알기 위해.
② 포스트모템으로 "왜 몰랐는지"를 기록한다. ③ 같은 패턴의 잠재 병목이
다른 곳에 없는지 점검한다. 병목 하나를 고치면 병목은 다음 지점으로
이동한다는 것(theory of constraints)도 언급하면 가산점.

## 한 줄 요약

병목 추적은 "무엇이 변했나" 확정 → 지표로 계층 좁히기 → 트레이스로
구간 분해 → 프로파일링으로 내부 확인의 **탑다운 수사**이며,
매 단계에서 다음 행선지를 정하는 것은 추측이 아니라 **측정된 데이터**다.
