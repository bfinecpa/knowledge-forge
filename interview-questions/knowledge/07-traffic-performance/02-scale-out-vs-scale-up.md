# 수평 확장(scale-out) vs 수직 확장(scale-up) — 병목은 결국 "상태 있는 계층"으로 수렴한다

> 핵심 관전 포인트: **수직 확장(scale-up)은 한 장비의 사양(CPU/메모리)을 올리는 것 — 코드 변경 없이 즉시 효과가 있지만, 하드웨어 상한과 비용의 비선형 증가에 부딪히고 단일 장애점이 그대로 남는다. 수평 확장(scale-out)은 장비 수를 늘리는 것 — 이론상 한계가 없고 장애 격리·탄력적 스케일링이 되지만, 서버가 stateless여야 한다는 전제가 있고 상태를 가진 계층(DB, 세션)은 대수를 늘리는 것만으로 확장되지 않는다. 그래서 실전의 확장 문제는 "앱 서버를 몇 대 늘리느냐"가 아니라, 수평 확장이 안 통하는 지점 — 상태 있는 계층 — 을 어떻게 다루느냐(세션 외부화, 읽기 복제, 캐시, 샤딩)로 귀결된다.**

---

## 0. 질문 + 의도

**질문**: "수평 확장(scale-out)과 수직 확장(scale-up)의 차이와 각각의 한계는?"

**출제 의도**: "서버 늘리면 되죠"가 통하지 않는 지점(DB, 상태 공유)을 아는지. 확장의 병목이 결국 상태 있는 계층으로 수렴한다는 인식이 아키텍처 논의의 출발점이다.

## 1. 정의와 비교 — 슈퍼맨 한 명 vs 일꾼 여러 명

- **수직 확장(scale-up)**: 지금 쓰는 장비를 더 좋은 장비로 — CPU 코어, 메모리, 디스크를 올린다. 일꾼 한 명을 슈퍼맨으로 만드는 방식.
- **수평 확장(scale-out)**: 같은 역할의 장비를 여러 대로 — 로드밸런서 뒤에 서버를 추가한다. 일꾼 수를 늘리는 방식.

| | 수직 확장 (scale-up) | 수평 확장 (scale-out) |
|---|---|---|
| 방법 | 장비 사양 업그레이드 | 장비 대수 증설 |
| 아키텍처 변경 | 거의 불필요 | LB + stateless 설계 전제 |
| 확장 상한 | 하드웨어 물리 상한 존재 | 이론상 상한 없음 |
| 비용 곡선 | 상위 사양일수록 비선형 급증 | 대체로 대수에 선형 |
| 장애 내성 | 단일 장애점 그대로 | 1대 죽어도 N-1대가 감당 |
| 탄력성 | 업그레이드에 다운타임/재시작 수반 | 오토스케일링으로 증감 자동화 |

## 2. 수직 확장의 한계 — 올릴 수 있는 천장이 있다

1. **물리적 상한**: 한 장비에 넣을 수 있는 코어·메모리에는 끝이 있다. 상한에 도달하면 그다음 수단이 없다.
2. **비용의 비선형성**: 사양이 2배인 장비는 가격이 2배가 아니라 그 이상으로 뛰는 구간이 온다.
3. **가용성은 그대로**: 아무리 좋은 장비도 한 대다 — 그 장비가 죽으면 서비스 전체가 죽는 단일 장애점(SPOF)이며, 업그레이드 자체에도 중단이 필요하다.
4. **한계 효용**: 코어를 늘려도 애플리케이션의 락 경합·직렬 구간 때문에 성능이 코어 수에 비례해 오르지 않는 경우가 많다. (가산점 포인트) Amdahl의 법칙 — 병렬화 안 되는 부분이 전체 개선의 상한을 정한다.

## 3. 수평 확장의 전제와 한계 — "서버 늘리면 되죠"가 깨지는 지점

수평 확장은 무한해 보이지만 **전제 조건**이 있고, 그 전제가 깨지는 곳이 실전의 병목이다.

### 3-1. 전제: 서버가 stateless여야 한다

서버 로컬에 상태(메모리 세션, 로컬 파일, 인메모리 캐시)가 있으면, 요청이 어느 서버로 가느냐에 따라 결과가 달라진다 — 2대로 늘리는 순간부터 버그 발생기가 된다.

```java
// before: 서버 로컬 메모리에 세션 보관 — 1대일 때만 우연히 동작하던 코드
@Component
public class LoginSessionStore {
    private final Map<String, UserSession> sessions = new ConcurrentHashMap<>();
    // 서버 2대로 늘리면: 로그인은 A서버에서, 다음 요청은 B서버로
    // → B에는 세션이 없어 "랜덤하게 로그아웃되는" 장애
}
```

```java
// after: 상태를 외부 저장소(Redis)로 빼서 서버를 stateless로
@Component
public class LoginSessionStore {
    private final StringRedisTemplate redis;
    public void save(String sessionId, UserSession s) {
        redis.opsForValue().set("session:" + sessionId, serialize(s), Duration.ofMinutes(30));
        // 어느 서버가 받아도 같은 Redis를 보므로 대수를 마음껏 늘릴 수 있다
    }
}
```

세션 외에도 로컬 파일 업로드 저장(→ 오브젝트 스토리지로), 갱신되는 인메모리 캐시(→ 외부 캐시 또는 무효화 전파), 단일 실행을 가정한 스케줄러(→ 분산 락/리더 선출) 등이 같은 이유로 깨진다.

### 3-2. 한계: 상태 있는 계층은 대수를 늘려서 확장되지 않는다

앱 서버는 stateless로 만들면 얼마든지 늘릴 수 있다. 그러나 **모든 서버가 공유하는 데이터의 원본 — DB — 은 "같은 것 한 대 더"가 불가능하다**. 똑같은 DB를 2대 두면 어느 쪽이 진실인지(쓰기 충돌, 정합성) 문제가 생기기 때문이다. 그래서:

- 앱 서버를 10배로 늘려도 모든 요청이 결국 한 대의 DB로 몰리면 **처리량은 DB 상한에서 멈춘다**. 오히려 앱 서버 증설이 DB 커넥션 수만 10배로 늘려 DB를 먼저 쓰러뜨리기도 한다.
- **확장 논의의 병목은 항상 상태 있는 계층으로 수렴한다** — 이 인식이 이 질문의 핵심이다.

### 3-3. 비용: 분산 시스템의 복잡도

대수가 늘면 배포·설정 전파·로그 추적·모니터링이 분산 문제가 되고, 캐시 정합성·중복 실행 같은 새 버그 클래스가 생긴다. 수평 확장은 공짜가 아니라 "운영 복잡도를 지불하고 확장성을 사는" 거래다.

## 4. 그러면 상태 계층(DB)은 어떻게 확장하나 — 단계별 전략

병목이 DB로 수렴한다는 걸 아는 사람은 다음 사다리를 순서대로 오른다 (각 단계가 다음 단계보다 싸고 덜 위험하므로):

1. **수직 확장 먼저** — DB야말로 scale-up이 잘 먹히는 계층이다. 사양을 올리는 것이 아키텍처 변경 없이 가장 싸게 상한을 올린다.
2. **읽기 분산 (read replica)** — 대부분의 서비스는 읽기가 압도적이므로, 복제본을 늘려 읽기를 분산한다. 대신 복제 지연(replication lag)으로 "방금 쓴 데이터가 안 보이는" 문제를 감수/설계해야 한다.
3. **캐시** — DB 앞단(Redis 등)에서 반복 읽기를 흡수해 DB 도달 트래픽 자체를 줄인다.
4. **샤딩 (쓰기 분산)** — 데이터를 키 기준으로 여러 DB에 쪼갠다. 쓰기까지 수평 확장되는 유일한 수단이지만, 크로스 샤드 조인·트랜잭션을 포기해야 하고 리밸런싱이 어려운 **비가역에 가까운 결정**이므로 마지막 카드다.

## 5. 꼬리질문 대비 포인트

### "앱 서버를 크게 늘렸는데 처리량이 안 올라갑니다. 왜죠?"

병목이 앱 서버가 아니라는 뜻이다. 후보는 뒷단 공유 자원 — DB(CPU, 커넥션 수, 락 경합), 외부 API, 공용 캐시. 특히 앱 인스턴스가 N대면 DB에 꽂히는 커넥션은 N × 풀 크기로 늘어나 DB를 더 빨리 포화시킨다. 증설 전후로 각 계층의 사용률·대기 지표를 비교해 병목 자원을 먼저 찾아야 하고, "확장은 병목인 자원에 해야 효과가 있다"가 원칙이다.

### "오토스케일링을 도입하려면 무엇이 준비돼야 하나요?"

(1) stateless — 어느 인스턴스가 사라져도/새로 떠도 무방해야 한다. (2) 빠른 기동과 워밍업 — 뜨는 데 5분 걸리면 스파이크를 못 따라간다. (3) graceful shutdown — 축소 시 처리 중 요청을 안전하게 마무리(LB에서 제외 → 드레이닝 → 종료). (4) 병목과 일치하는 스케일링 지표 — I/O 바운드 서비스는 CPU가 낮은 채로 죽으므로 CPU 기준 HPA는 영원히 발동하지 않을 수 있다.

### "수평 확장이 항상 정답인가요? 수직 확장을 택할 상황은?" (시니어 변별 포인트)

아니다. 트래픽 규모가 작거나 예측 가능하면 수직 확장이 더 싸고 단순하다 — 분산 복잡도(배포, 정합성, 관측)를 지불할 이유가 없다. DB·캐시처럼 상태 있는 계층은 애초에 scale-up이 1순위 수단이고, 라이선스가 장비 단위인 소프트웨어나 강한 단일 노드 성능이 필요한 워크로드(대형 트랜잭션, 인메모리 연산)도 수직이 낫다. "무조건 scale-out"은 트레이드오프를 계산 안 해봤다는 신호다 — 확장 방식은 종교가 아니라 비용·복잡도·가용성 요구의 함수다.

### "세션 말고 scale-out을 방해하는 로컬 상태의 예를 더 들어보세요."

로컬 디스크에 저장한 업로드 파일(다른 서버에서 404), 서버별 인메모리 캐시의 갱신 불일치(A서버는 새 값, B서버는 옛 값 응답), `@Scheduled` 같은 단일 실행 가정 배치의 N중 중복 실행(분산 락 필요), 인메모리 rate limit 카운터(서버별 카운트 합이 전체 한도를 초과), WebSocket처럼 연결 자체가 상태인 경우(특정 서버에 붙은 연결로만 푸시 가능 → pub/sub로 브로드캐스트 필요).

## 한 줄 요약

scale-up은 장비 사양을 올려 단순하지만 물리적·비용적 천장과 단일 장애점이 남고, scale-out은 대수를 늘려 상한 없이 확장하지만 stateless 전제와 분산 복잡도를 요구한다 — 그리고 앱 서버를 아무리 늘려도 확장의 병목은 결국 상태 있는 계층(DB·세션)으로 수렴하므로, 실전의 확장 설계란 상태를 외부화하고 DB를 수직 확장 → 읽기 복제 → 캐시 → 샤딩의 사다리로 다루는 일이다.
