# 수평 확장(scale-out) vs 수직 확장(scale-up) — 병목은 결국 "상태 있는 계층"으로 수렴한다

> 핵심 관전 포인트: **수직 확장(scale-up)은 한 장비의 사양(CPU/메모리)을 올리는 것 — 코드 변경 없이 즉시 효과가 있지만, 하드웨어 상한과 비용의 비선형 증가에 부딪히고 단일 장애점이 그대로 남는다. 수평 확장(scale-out)은 장비 수를 늘리는 것 — 이론상 한계가 없고 장애 격리·탄력적 스케일링이 되지만, 서버가 stateless여야 한다는 전제가 있고 상태를 가진 계층(DB, 세션)은 대수를 늘리는 것만으로 확장되지 않는다. 그래서 "서버를 늘렸는데 처리량이 안 올라간다"는 상황은 확장이 실패한 것이 아니라 병목이 앱 서버에서 뒷단으로 이동한 것이고, 더 나쁜 것은 인스턴스마다 자기 커넥션 풀을 갖기 때문에 앱 증설이 DB를 오히려 더 빨리 죽인다는 점이다. 그래서 실전의 확장 문제는 "앱 서버를 몇 대 늘리느냐"가 아니라, 수평 확장이 안 통하는 지점 — 상태 있는 계층 — 을 어떻게 다루느냐(세션 외부화, 읽기 복제, 캐시, 샤딩)로 귀결된다.**

---

## 0. 질문 + 의도

**질문**: "수평 확장(scale-out)과 수직 확장(scale-up)의 차이와 각각의 한계는?"

**출제 의도**: "서버 늘리면 되죠"가 통하지 않는 지점(DB, 상태 공유)을 아는지. 확장의 병목이 결국 상태 있는 계층으로 수렴한다는 인식이 아키텍처 논의의 출발점이다.

## 1. 두 방식은 물리적으로 무엇을 하는 일인가

### 1-1. 수직 확장 — 같은 자리의 장비를 더 좋은 것으로 바꾼다

**수직 확장(scale-up)은 지금 서비스가 올라가 있는 장비 자체의 사양을 올리는 것**이다. 물리 서버라면 CPU를 코어가 더 많은 모델로 바꾸거나, 메모리 모듈을 더 큰 것으로 교체하거나, 디스크를 더 빠른 것으로 바꾼다. 클라우드라면 인스턴스 타입을 한 단계 위로 변경한다.

여기서 중요한 것은 **애플리케이션 관점에서 아무것도 달라지지 않는다**는 점이다. 서버는 여전히 한 대이고, 프로세스도 하나이며, 메모리에 들고 있던 상태도 그대로 유효하다. 코드를 한 줄도 고치지 않고 처리 능력을 올릴 수 있는 이유가 이것이다. 대신 CPU 코어나 메모리 모듈을 바꾸려면 장비를 멈춰야 하므로, 클라우드에서 인스턴스 타입을 변경하는 것도 대개 정지 후 재시작을 수반한다.

### 1-2. 수평 확장 — 같은 역할의 장비를 여러 대 세우고 앞에 분배기를 둔다

**수평 확장(scale-out)은 똑같은 애플리케이션을 여러 장비에 띄우고, 그 앞에 요청을 나눠 주는 장치를 두는 것**이다. 그 장치가 **로드밸런서(load balancer)**다 — 들어온 요청을 뒤의 여러 서버 중 하나로 보내 부하를 고르게 나눈다(3번 문서).

이쪽은 애플리케이션 관점에서 세계가 바뀐다. **어떤 요청이 어느 서버로 갈지 애플리케이션이 통제할 수 없게 되기 때문**이다. 같은 사용자의 연속된 두 요청이 서로 다른 서버에 도착할 수 있고, 각 서버는 서로의 메모리를 볼 수 없다. 이 사실 하나가 2-5에서 다룰 stateless 전제의 뿌리다.

**일꾼 비유**로 정리하면 이렇다. 수직 확장은 **일꾼 한 명을 슈퍼맨으로 만드는 방식**이고, 수평 확장은 **일꾼 수를 늘리는 방식**이다. 슈퍼맨은 지시를 하나만 내려도 되고 서로 손발을 맞출 필요도 없어서 관리가 단순하다. 대신 아무리 강해도 한 명이라 쓰러지면 일이 멈추고, 더 강하게 만드는 데는 한계가 있다. 일꾼 여러 명은 한 명이 쓰러져도 나머지가 일하지만, 누가 무엇을 하는지 나눠 주는 사람이 필요하고 서로 같은 정보를 봐야 한다.

| | 수직 확장 (scale-up) | 수평 확장 (scale-out) |
|---|---|---|
| 방법 | 장비 사양 업그레이드 | 장비 대수 증설 |
| 아키텍처 변경 | 거의 불필요 | LB + stateless 설계 전제 |
| 확장 상한 | 하드웨어 물리 상한 존재 | 이론상 상한 없음 |
| 비용 곡선 | 상위 사양일수록 비선형 급증 | 대체로 대수에 선형 |
| 장애 내성 | 단일 장애점 그대로 | 1대 죽어도 N-1대가 감당 |
| 탄력성 | 업그레이드에 다운타임/재시작 수반 | 오토스케일링으로 증감 자동화 |

## 2. 각 방식의 한계 — 어디서 막히는가

### 2-1. 수직 확장의 물리적 상한 — 그다음 수단이 없다

한 장비에 넣을 수 있는 코어 수와 메모리 용량에는 끝이 있다. CPU 소켓 수, 메모리 슬롯 수, 메인보드가 지원하는 최대 용량이 전부 유한하기 때문이다. 그리고 **상한에 도달하면 수직 확장에는 그다음 카드가 없다** — 사양을 올리는 것 말고는 할 수 있는 일이 없는 전략이라서, 천장에 닿는 순간 전략 자체가 끝난다.

이것이 수평 확장과의 근본적 차이다. 수평 확장은 "이론상 상한 없음"이라고 표에 적혀 있는데, 그 말의 실제 의미는 **한 대를 더 붙이는 동작을 계속 반복할 수 있다**는 것이다. 다만 실제로 어디까지 반복할 수 있는지는 3절의 병목 문제에 달려 있다.

### 2-2. 비용은 왜 사양보다 빨리 오르는가

"사양이 2배인 장비는 가격이 2배가 아니라 그 이상"이라는 말을 근거 없이 하면 안 된다. 구조가 있다. (구체적인 가격이나 모델명은 시점과 지역에 따라 달라지므로, 여기서는 왜 그런 모양이 되는지만 본다.)

**고사양 CPU는 성능 대비 단가가 더 비싸다.** 같은 세대의 CPU라도 코어 수가 많은 모델은 칩 면적이 크고, 면적이 크면 제조 결함에 걸릴 확률이 높아져 양품 비율이 떨어진다. 그래서 최상위 모델의 단가는 코어 수에 비례하지 않고 더 빨리 오른다. 게다가 최상위 모델은 "그 성능이 아니면 안 되는" 수요를 상대하므로, 가격이 성능비가 아니라 대체 불가능성으로 결정되는 구간에 들어간다.

**메모리는 슬롯이라는 계단을 만난다.** 총 메모리를 2배로 늘리려면 두 가지 방법이 있다. 빈 슬롯에 모듈을 더 꽂거나, 한 장당 용량이 2배인 모듈로 갈아 끼우는 것이다. 빈 슬롯이 있는 동안은 대체로 선형이다. 그런데 슬롯을 다 채우면 **한 장당 용량이 큰 모듈로 바꿔야 하고, 대용량 모듈은 GB당 단가가 더 높다.** 그것마저 최대 용량에 닿으면 슬롯이 더 많은 상위 플랫폼(소켓 수가 더 많은 CPU와 메인보드)으로 가야 하는데, 이 지점에서 가격이 계단식으로 뛴다.

**클라우드에서는 원하지 않는 항목까지 함께 산다.** 인스턴스 타입을 한 단계 올리면 vCPU와 메모리만 오르는 것이 아니다. 네트워크 대역폭, 블록 스토리지 대역폭, 인스턴스에 붙는 로컬 디스크 용량 같은 항목이 **타입에 묶여 함께 올라가고 요금에 반영된다.** CPU만 부족한 상황이어도 나머지를 같이 사야 한다. 게다가 한 단계 위 타입이 대체로 정확히 2배 사양이므로, "1.3배만 필요한" 상황에서도 2배를 사게 된다.

정리하면 이렇다. **수평 확장은 "같은 것을 하나 더" 사는 것이므로 단가가 대체로 일정하다. 수직 확장은 "더 귀한 것 하나"를 사는 것이므로 상위 구간에서 단가가 급격히 오른다.** 다만 하위 구간에서는 수직 확장이 훨씬 싸다는 점도 같이 알아야 한다 — 작은 인스턴스 두 대보다 그 두 배 사양 한 대가 저렴한 구간이 실제로 존재하고, 여기에 로드밸런서 비용과 운영 인력 시간까지 더하면 격차가 더 벌어진다.

### 2-3. 가용성은 그대로다 — 좋은 장비도 한 대다

아무리 좋은 장비도 한 대다. 그 장비가 죽으면 서비스 전체가 죽는 **단일 장애점(SPOF, single point of failure)**이며, 업그레이드 자체에도 중단이 필요하다.

여기서 짚어야 할 것은 **수직 확장이 가용성을 개선하지 않는다는 것이 아니라, 오히려 나빠질 수 있다는 점**이다. 사양을 올린 한 대에 전체 트래픽을 태우면 그 한 대가 죽었을 때의 영향 범위가 100%다. 반면 같은 총 용량을 4대로 나눠 놓으면 한 대가 죽어도 25%의 용량만 잃는다. 남은 3대가 트래픽을 다 받으면 사용률이 급등하는데, 이때 1번 문서에서 본 ρ/(1−ρ) 곡선을 타고 지연시간이 폭발할 수 있다는 것도 함께 알아야 한다 — **"1대 죽어도 N-1대가 감당한다"는 말은 N-1대로 감당할 여유를 미리 남겨 뒀을 때만 참이다.**

### 2-4. 한계 효용 — 코어를 늘려도 그만큼 안 빨라진다

코어를 늘려도 애플리케이션의 락 경합·직렬 구간 때문에 성능이 코어 수에 비례해 오르지 않는 경우가 많다. (가산점 포인트) **Amdahl의 법칙**이 이 상한을 계산해 준다 — 병렬화되지 않는 부분이 전체 개선의 상한을 정한다는 법칙이다.

식은 이렇다. 전체 작업 중 **어떤 수를 써도 순차로만 실행되는 비율**을 s라고 하면,

```
코어 N개일 때 최대 배속 = 1 / ( s + (1 − s) / N )
```

직렬 구간이 전체의 5%(s = 0.05)뿐인, 꽤 잘 병렬화된 애플리케이션으로 계산해 보자.

| 코어 수 N | 이론 최대 배속 | 코어당 효율 |
|---|---|---|
| 1 | 1.00배 | 100% |
| 2 | 1.90배 | 95% |
| 4 | 3.48배 | 87% |
| 8 | 5.93배 | 74% |
| 16 | 9.14배 | 57% |
| 32 | 12.55배 | 39% |
| 무한 | 20.0배 | 0% |

검산해 보면 N = 8에서 0.95 ÷ 8 = 0.11875, 여기에 0.05를 더하면 0.16875이고 1 ÷ 0.16875 = 5.93이다. N = 32는 0.95 ÷ 32 = 0.0296875, + 0.05 = 0.0796875, 1 ÷ 0.0796875 = 12.55다. 코어당 효율은 배속을 코어 수로 나눈 값이다(5.93 ÷ 8 = 0.74).

표에서 읽어야 하는 것은 마지막 행이다. **직렬 구간이 5%뿐이어도 코어를 무한히 늘려서 얻을 수 있는 최대 배속은 20배다.** 그리고 32코어에서 이미 12.55배를 얻었으므로, 남은 7.5배를 위해 코어를 32개에서 무한히 늘려야 한다. 수직 확장의 비용 곡선이 급하게 오르는 구간과 이 효율 하락 구간이 겹치는 것이 문제다 — **가장 비싼 코어가 가장 적게 기여한다.**

그리고 실제 애플리케이션에서 s는 계산으로 아는 값이 아니라 측정해야 하는 값이다. 동기화 블록, 단일 커넥션으로 나가는 쿼리, 하나뿐인 외부 API, 로그 파일 하나에 몰리는 쓰기 같은 것이 전부 s에 들어간다. 코어를 2배로 늘렸는데 처리량이 1.2배만 올랐다면 s가 생각보다 크다는 뜻이고, 그 지점을 찾는 것이 사양 올리기보다 훨씬 값싼 개선이다.

### 2-5. 수평 확장의 전제 — 서버가 stateless여야 한다

서버 로컬에 상태(메모리 세션, 로컬 파일, 인메모리 캐시)가 있으면, 요청이 어느 서버로 가느냐에 따라 결과가 달라진다 — **2대로 늘리는 순간부터 버그 발생기가 된다.** 1-2에서 본 대로 어느 서버로 갈지를 애플리케이션이 통제할 수 없기 때문이다.

```java
// before: 서버 로컬 메모리에 세션 보관 — 1대일 때만 우연히 동작하던 코드
@Component
public class LoginSessionStore {
    private final Map<String, UserSession> sessions = new ConcurrentHashMap<>();
    // 서버 2대로 늘리면: 로그인은 A서버에서, 다음 요청은 B서버로
    // → B에는 세션이 없어 "랜덤하게 로그아웃되는" 장애
    // 재현이 어려운 것이 특히 나쁘다 — 요청이 같은 서버로 갈 확률이 1/N이라
    // 2대에서는 절반만 실패하고, 개발 환경(1대)에서는 절대 재현되지 않는다.
}
```

```java
// after: 상태를 외부 저장소(Redis)로 빼서 서버를 stateless로
@Component
public class LoginSessionStore {
    private final StringRedisTemplate redis;
    public void save(String sessionId, UserSession s) {
        redis.opsForValue().set("session:" + sessionId, serialize(s), Duration.ofMinutes(30));
        // 어느 서버가 받아도 같은 Redis를 보므로 대수를 마음껏 늘릴 수 있다
    }
}
```

세션 외에도 로컬 파일 업로드 저장(→ 오브젝트 스토리지로), 갱신되는 인메모리 캐시(→ 외부 캐시 또는 무효화 전파), 단일 실행을 가정한 스케줄러(→ 분산 락/리더 선출) 등이 같은 이유로 깨진다. 어떤 상태가 왜 깨지고 각각을 어떻게 외부화하는지는 **4번 문서(stateless 서버 설계와 세션)**의 주제이므로 여기서는 전제만 확인하고 넘어간다.

이 문서의 무게는 다음 절에 있다. **stateless를 만들어 앱 서버를 마음껏 늘릴 수 있게 되어도 확장은 거기서 끝나지 않기 때문**이다.

### 2-6. 수평 확장의 비용 — 분산 시스템의 복잡도

대수가 늘면 배포·설정 전파·로그 추적·모니터링이 분산 문제가 되고, 캐시 정합성·중복 실행 같은 새 버그 클래스가 생긴다. **수평 확장은 공짜가 아니라 "운영 복잡도를 지불하고 확장성을 사는" 거래다.**

구체적으로 무엇이 어려워지는지 알아 두면 좋다. 장애 조사를 할 때 로그가 N개 서버에 흩어져 있으므로 요청 하나의 전체 경로를 따라가려면 분산 추적(trace id 전파)이 필요해진다. 지표도 인스턴스별로 나오므로 1번 문서에서 본 대로 **백분위를 인스턴스별로 평균 내면 틀린 값이 나온다.** 설정을 바꿀 때도 N대에 동시에 반영되지 않는 중간 상태가 존재하고, 배포 중에는 구버전과 신버전이 같이 떠 있는 시간이 생긴다.

## 3. 병목은 사라지지 않고 이동한다 — 이 문서의 핵심

앱 서버는 stateless로 만들면 얼마든지 늘릴 수 있다. 그런데 그렇게 늘려도 처리량이 안 오르는 일이 매우 흔하다. **확장이 실패한 것이 아니라 병목이 다른 계층으로 이동한 것**이다. 이 절은 그 이동을 숫자로 따라간다.

### 3-1. 앱 서버를 늘리면 DB 커넥션 요구량은 어떻게 되는가

먼저 전제를 하나 깔자. **애플리케이션 인스턴스는 각자 자기 커넥션 풀을 갖는다.** 커넥션 풀은 애플리케이션 프로세스 안의 객체이므로 프로세스가 늘어나면 풀도 그만큼 늘어난다. 이것이 주니어가 가장 자주 밟는 함정의 뿌리다 — 설정 파일에 적힌 `maximum-pool-size`는 **한 인스턴스의 값**이고, DB가 실제로 받는 커넥션은 그 값 곱하기 인스턴스 수다.

`maximum-pool-size: 20`으로 배포한 서비스의 대수를 늘려 보자.

```
인스턴스당 풀 크기 20, PostgreSQL max_connections = 100 (기본값)

  앱 서버  2대  ->  2 × 20 =  40개   여유 있음
  앱 서버  4대  ->  4 × 20 =  80개   슬슬 위험
  앱 서버  5대  ->  5 × 20 = 100개   상한에 정확히 도달
  앱 서버  6대  ->  6 × 20 = 120개   ★ 초과분은 연결 자체가 거부된다
                                      FATAL: sorry, too many clients already
```

여기서 두 가지를 알아야 한다.

**첫째, `max_connections`를 전부 쓸 수 있는 것도 아니다.** PostgreSQL은 `superuser_reserved_connections`(기본 3개)만큼을 슈퍼유저용으로 남겨 두므로, 일반 애플리케이션이 실제로 쓸 수 있는 것은 97개다. 운영 도구나 모니터링 에이전트가 쓰는 커넥션도 이 안에서 나간다.

**둘째, `max_connections`를 그냥 올리면 되는 문제가 아니다.** PostgreSQL은 커넥션 하나당 **별도의 OS 프로세스**를 띄우는 구조다. 커넥션 500개는 백엔드 프로세스 500개를 뜻하고, 각 프로세스는 자기 몫의 메모리(정렬·해시에 쓰는 `work_mem` 등)를 따로 잡는다. 그래서 상한을 무작정 올리면 커넥션이 늘어난 만큼 메모리 사용과 프로세스 스케줄링 부담이 늘어, DB가 쿼리를 처리하는 대신 프로세스를 관리하는 데 시간을 쓰게 된다.

지금 상태를 확인하는 쿼리는 이렇다.

```sql
-- 상한이 얼마인지, 지금 몇 개가 붙어 있는지 먼저 본다.
SHOW max_connections;

-- 상태별로 세면 "필요해서 붙어 있는 것"과 "그냥 잡고 있는 것"이 구분된다.
SELECT state, count(*)
  FROM pg_stat_activity
 GROUP BY state;
-- state = 'active'          : 지금 쿼리를 실행 중
-- state = 'idle'            : 풀이 잡고만 있고 아무것도 안 함
-- state = 'idle in transaction' : ★ 트랜잭션을 열어 놓고 놀고 있다.
--   이 값이 크면 트랜잭션 안에서 외부 API를 호출하는 등의 코드를 의심한다.
--   커넥션을 점유하는 시간(W)이 길어져 필요 풀 크기를 부풀리는 원인이다.

-- 인스턴스별로 몇 개씩 붙어 있는지도 볼 수 있다 — 특정 인스턴스만 많이 잡고
-- 있다면 그쪽에 커넥션 누수나 느린 쿼리가 있다는 신호다.
SELECT client_addr, count(*)
  FROM pg_stat_activity
 GROUP BY client_addr
 ORDER BY count(*) DESC;
```

**그래서 앱 서버 증설이 오히려 DB를 더 빨리 죽이는 경로가 성립한다.** 앱 서버가 병목이라고 판단해 대수를 2배로 늘리면, 처리량은 DB 상한에 걸려 그대로인데 DB에 꽂히는 커넥션은 정확히 2배가 된다. DB는 같은 일을 하면서 두 배의 프로세스와 두 배의 락 경합을 감당해야 하므로, 쿼리 하나의 응답시간이 늘어난다. 1번 문서의 표현으로 말하면 **사용률을 더 밀어 올려 ρ/(1−ρ) 곡선의 오른쪽으로 이동한 것**이다. 처리량은 안 오르고 지연시간만 나빠진다.

### 3-2. 필요한 커넥션 수는 앱 대수가 아니라 λW가 정한다

그러면 인스턴스당 풀을 몇으로 잡아야 하는가. 여기서 반드시 짚어야 할 사실이 있다. **앱 서버를 늘려도 사용자 수는 그대로다.** 즉 DB에 도달하는 요청의 유입률 λ는 앱 대수와 무관하다. 그런데 필요한 커넥션 수는 λ로 정해진다.

17번 문서의 Little's Law로 계산해 보자.

```
목표 처리량 λ            = 500 TPS
요청 1건이 DB 커넥션을    = 50ms  (= 0.05초, TPS와 단위를 맞춰야 한다)
붙잡고 있는 시간 W

동시에 필요한 커넥션 수 L = λ × W = 500 × 0.05 = 25개
```

**전체 시스템에 필요한 커넥션은 25개다.** 앱 서버가 1대든 5대든 25개다. 그러므로 인스턴스당 풀 크기는 이렇게 나온다.

```
앱 서버  1대 -> 인스턴스당 25개
앱 서버  5대 -> 인스턴스당 25 ÷ 5 = 5개
앱 서버 10대 -> 인스턴스당 25 ÷ 10 = 3개 (반올림)
```

**앱 서버를 늘리면 인스턴스당 풀 크기는 오히려 줄어야 한다.** 각 인스턴스가 처리하는 트래픽이 그만큼 줄었으니 당연한 결론인데, 실무에서는 배포 설정을 그대로 복사하기 때문에 총량만 늘어난다. 인스턴스당 20개로 5대를 띄우면 총 100개 — **필요량 25개의 4배를 DB에 들이대고 있는 것**이고, 그 75개는 아무 처리량도 만들지 못하면서 DB의 프로세스와 메모리만 잡아먹는다.

설정으로 옮기면 이렇게 달라진다.

```yaml
# Before: 인스턴스마다 "넉넉하게" 20개. 대수가 늘면 총량도 같이 늘어난다.
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
```

```yaml
# After: 총 필요량을 먼저 계산하고 "최대" 인스턴스 수로 나눈다.
spring:
  datasource:
    hikari:
      # 총 필요량 25 ÷ 최대 인스턴스 5대 = 5. 오토스케일링이라면
      # 현재 대수가 아니라 maxReplicas 기준으로 나눠야 한다 —
      # 스케일 아웃이 발동한 순간 총량이 상한을 넘으면 그때 터진다.
      maximum-pool-size: 5

      # 풀이 말랐을 때 무한정 기다리지 않게 상한을 둔다.
      # 이 값이 없으면 커넥션을 기다리는 톰캣 스레드가 계속 쌓여
      # DB 문제 하나가 앱 전체의 스레드 고갈로 번진다.
      # 2초 뒤 실패시키면 그 지점에서 요청이 끊기고 상류가 폴백할 수 있다.
      connection-timeout: 2000

      # 커넥션을 20초 넘게 반납하지 않는 코드가 있으면 로그로 알려준다.
      # 풀 고갈의 원인은 대개 크기가 아니라 반납이 늦은 코드다.
      leak-detection-threshold: 20000
```

```conf
# postgresql.conf — 총량이 상한 안에 들어오는지 반드시 역산해 확인한다.
#   최대 인스턴스 수 5 × maximum-pool-size 5 = 25
#   + 배치 애플리케이션 10 + 운영/모니터링 도구 10 + 슈퍼유저 예약 3 = 48
#   여유를 두어 100으로 둔다. 무작정 500으로 올리는 것은 답이 아니다 —
#   커넥션 1개 = 백엔드 프로세스 1개이므로 상한이 곧 메모리 예산이다.
max_connections = 100
```

(가산점 포인트) 인스턴스 수가 많거나 오토스케일링으로 계속 변하는 환경에서는 인스턴스별 풀만으로 총량을 통제하기 어렵다. 이때 DB 앞에 **커넥션 풀러(connection pooler)**를 둔다 — PostgreSQL에서는 **PgBouncer**가 대표적이다. 앱은 PgBouncer에 붙고, PgBouncer가 훨씬 적은 수의 실제 DB 커넥션을 돌려쓰게 만든다. 특히 **트랜잭션 풀링 모드**에서는 트랜잭션이 끝나는 순간 커넥션을 회수해 다른 클라이언트에 넘기므로, 앱 쪽 커넥션 1,000개를 실제 DB 커넥션 수십 개로 다중화할 수 있다. 대가는 세션 단위 상태를 쓸 수 없다는 것이다 — 세션에 걸어 두는 advisory lock, 세션 수준 `SET`, 일부 prepared statement 사용 방식이 트랜잭션 풀링과 충돌한다. **"앱 대수와 실제 DB 커넥션 수를 분리한다"**는 것이 이 도구의 핵심 가치다.

### 3-3. 왜 읽기는 대수를 늘려 확장되고 쓰기는 안 되는가

앱 서버는 stateless로 만들면 늘어난다. 그러나 **모든 서버가 공유하는 데이터의 원본 — DB — 은 "같은 것 한 대 더"가 불가능하다.** 똑같은 DB를 2대 두면 어느 쪽이 진실인지 정할 방법이 없기 때문이다. 그런데 왜 읽기 복제본은 늘려도 괜찮은가. 이 비대칭의 이유를 설명할 수 있어야 한다.

#### 전제 지식 — PostgreSQL 스트리밍 복제가 하는 일

PostgreSQL은 데이터 파일을 고치기 전에 **"무엇을 어떻게 고칠지"를 먼저 순서대로 적어 두는 로그**를 남긴다. 이것이 **WAL(write-ahead log, 선행 기록 로그)**이다. 장애가 나도 이 로그를 다시 재생하면 상태를 복구할 수 있다.

**스트리밍 복제(streaming replication)**는 이 WAL을 다른 서버에 계속 흘려보내는 방식이다. 쓰기를 받는 서버를 **프라이머리(primary)**, WAL을 받아 재생하는 서버를 **스탠바이(standby)**라고 한다. 스탠바이를 **hot standby**로 띄우면 WAL을 재생하는 중에도 조회 쿼리를 받을 수 있다 — 여기서 읽기 확장이 나온다.

```
                    [프라이머리]  쓰기 전부 여기로
                     │  │  │
              WAL 전송│  │  │  (walsender 프로세스가 스탠바이마다 하나씩)
                     v  v  v
        [스탠바이 1] [스탠바이 2] [스탠바이 3]   읽기만 받는다 (hot standby)
```

#### 읽기가 확장되는 이유 — 읽기는 서로를 방해하지 않는다

같은 행을 100명이 동시에 읽어도 결과가 달라지지 않는다. 읽기는 상태를 바꾸지 않으므로 **순서를 정할 필요가 없다.** 그래서 데이터의 복사본을 여러 개 만들어 두고 아무 데서나 읽게 하면 되고, 복사본 수만큼 읽기 처리량이 늘어난다. 대부분의 서비스는 읽기가 압도적으로 많으므로 이 카드가 잘 먹힌다.

#### 쓰기가 확장되지 않는 이유 — 쓰기는 순서를 정해야 한다

쓰기는 다르다. 잔액 10,000원에서 3,000원 차감 요청이 두 건 들어오면 결과는 4,000원이어야 한다. 이것이 성립하려면 **두 쓰기 중 누가 먼저인지를 누군가 결정해야 한다.**

복사본 두 곳에서 각각 차감을 받아들이면 어떻게 되는지 보자.

```
        [복사본 A] 잔액 10,000        [복사본 B] 잔액 10,000
              │                              │
        3,000 차감                     3,000 차감
              v                              v
        [복사본 A] 잔액 7,000         [복사본 B] 잔액 7,000

  나중에 두 결과를 합치려 하면? 어느 쪽도 4,000이 아니고,
  "둘 다 7,000"이라는 사실만으로는 3,000이 두 번 빠졌는지
  한 번 빠졌는지 구분할 수 없다. 정보가 이미 사라졌다.
```

**순서를 정하려면 한 지점으로 수렴해야 하고, 한 지점은 대수로 늘릴 수 없다.** 이것이 확장의 근본 비대칭이다. 그래서 PostgreSQL 스트리밍 복제에서 스탠바이는 **read-only**이고, 쓰기를 시도하면 `cannot execute INSERT in a read-only transaction` 에러를 낸다. 이 제약은 구현의 한계가 아니라 **정합성이 성립하기 위한 조건**이다.

#### 그리고 복제본을 늘리면 프라이머리의 부담이 늘어난다

읽기 복제가 무료가 아니라는 점도 짚어야 한다. 프라이머리는 스탠바이마다 WAL을 보내는 전송 프로세스(walsender)를 하나씩 띄운다. **스탠바이가 10대면 같은 WAL을 10번 전송한다.** 프라이머리의 네트워크 대역과 CPU를 그만큼 더 쓰는 것이다. 즉 읽기 복제본을 계속 늘리면 어느 지점부터는 쓰기 성능이 떨어지기 시작한다.

완화책은 **캐스케이딩 복제(cascading replication)**다 — 스탠바이가 받은 WAL을 다시 다른 스탠바이에 중계하게 해서 프라이머리의 전송 팬아웃을 줄인다. 대가는 중계 단계가 늘어난 만큼 복제 지연이 더 커진다는 것이다.

#### 감수해야 하는 것 — 복제 지연

스탠바이는 WAL을 받아 재생하므로 **프라이머리보다 항상 조금 뒤처져 있다.** 이것을 **복제 지연(replication lag)**이라고 한다. 그 결과 "방금 저장했는데 목록에 안 보이는" 현상이 생긴다 — 쓰기는 프라이머리로 갔고 곧바로 이어진 조회는 아직 재생이 안 된 스탠바이로 갔기 때문이다.

대응은 세 가지다. **쓰기 직후의 조회는 프라이머리로 보내기**(가장 흔하고 단순하다), **복제 지연을 모니터링해 지연이 큰 스탠바이는 라우팅에서 제외하기**, 그리고 **동기 복제**(`synchronous_standby_names` 설정으로 스탠바이가 WAL을 받았음을 확인한 뒤에 커밋을 완료시키는 것)다. 동기 복제는 지연 문제를 없애지만 커밋마다 네트워크 왕복을 기다리므로 쓰기 지연시간이 늘어난다 — 1번 문서의 언어로 말하면 W가 늘어난다.

(MySQL을 쓰는 조직이라면 어휘만 다르다 — WAL 대신 바이너리 로그(binlog)를 보내고, 스탠바이 대신 레플리카라고 부른다. "쓰기는 한 지점으로 수렴해야 한다"는 구조는 동일하다.)

### 3-4. 상태 계층의 확장 사다리 — 왜 이 순서인가

병목이 상태 계층으로 수렴한다는 걸 아는 사람은 다음 사다리를 순서대로 오른다. 순서를 정하는 기준이 두 개 있고, 이 기준을 말할 수 있는 것이 단계를 나열하는 것보다 중요하다.

```
기준 ① 되돌리기 쉬운 것부터   — 잘못 골랐을 때 원복 비용이 작은 것이 먼저
기준 ② 코드 변경이 적은 것부터 — 새로 들어오는 버그의 양이 적은 것이 먼저
```

**1단계: 수직 확장 먼저.** DB야말로 scale-up이 잘 먹히는 계층이다. 사양을 올리는 것이 아키텍처 변경 없이 가장 싸게 상한을 올린다. 두 기준 모두에서 최상위다 — **코드 변경이 0이고, 잘못 골랐으면 사양을 다시 내리면 끝난다.** 지불하는 것은 재시작 다운타임뿐이다. 그리고 3-3에서 본 대로 쓰기는 애초에 대수로 확장되지 않으므로, 쓰기 용량을 올리는 수단으로는 사실상 이것뿐이다.

**2단계: 읽기 분산(read replica).** 대부분의 서비스는 읽기가 압도적이므로, 복제본을 늘려 읽기를 분산한다. 대신 복제 지연으로 "방금 쓴 데이터가 안 보이는" 문제를 감수하거나 설계로 회피해야 한다(3-3). 여기서 코드 변경이 시작된다 — 읽기를 어느 DataSource로 보낼지 라우팅하는 코드가 필요하다. 그래도 되돌리기는 쉽다. **라우팅을 끄면 모든 쿼리가 프라이머리로 돌아가고, 그 상태는 도입 전과 동일하다.** 그리고 새로 생기는 정합성 문제가 "복제 지연" 하나의 축으로 국한된다는 점도 중요하다.

**3단계: 캐시.** DB 앞단(Redis 등)에서 반복 읽기를 흡수해 DB 도달 트래픽 자체를 줄인다. 읽기 복제와 방향이 비슷하지만 대가의 성격이 다르다 — **캐시는 "무효화를 어디서 하는가"라는 새로운 버그 클래스를 들여온다.** 데이터를 바꾸는 모든 경로에서 캐시를 지워야 하는데, 한 곳을 빠뜨리면 옛 값이 무기한 남는다. 게다가 캐시가 흡수하던 트래픽 비중이 커지면 되돌리기가 사실상 불가능해진다 — 캐시를 끄는 순간 그 트래픽이 전부 DB로 쏟아지기 때문이다.

2단계와 3단계의 순서는 상황에 따라 뒤집힌다. 판단 기준은 **적중률**이다. 읽기가 소수의 인기 데이터에 집중돼 있으면 캐시가 훨씬 효율적이고 복제본보다 싸다. 반대로 읽기가 넓게 퍼져 있으면 적중률이 낮아 캐시가 별 효과가 없고 복제가 낫다.

**4단계: 샤딩(쓰기 분산).** 데이터를 키 기준으로 여러 DB에 쪼갠다. **쓰기까지 수평 확장되는 유일한 수단**이지만 마지막 카드다. 이유가 셋이다.

- **조인이 성립하지 않는다.** 두 테이블이 다른 샤드에 있으면 SQL 조인을 쓸 수 없고, 애플리케이션이 각 샤드를 따로 조회해 메모리에서 합쳐야 한다. 지금 잘 돌던 쿼리들을 다시 써야 한다는 뜻이다.
- **트랜잭션이 샤드를 넘지 못한다.** 두 샤드에 걸친 원자적 쓰기가 불가능하므로, 그런 흐름은 Saga 같은 분산 트랜잭션 설계로 다시 만들어야 한다(10장). 확장 문제를 풀려다 정합성 문제를 새로 얻는 셈이다.
- **재분배가 지독하게 어렵다.** 샤드 키를 잘못 골라 데이터가 한 샤드에 몰리면(핫 샤드) 고치려면 운영 중에 데이터를 옮겨야 한다. 옮기는 동안 어느 샤드를 봐야 하는지가 모호하므로 이중 기록·이중 조회 기간이 필요하고, 그 기간의 정합성을 따로 설계해야 한다.

그래서 샤딩은 **비가역에 가까운 결정**이다. 위의 세 기준 모두에서 최하위이므로 마지막에 온다. 그리고 이 사다리를 아는 것의 실질적 가치는 **"샤딩을 언제 하는가"가 아니라 "샤딩 전에 아직 안 해 본 것이 있는가"를 점검할 수 있다는 데** 있다.

## 4. 꼬리질문 대비 포인트

### "앱 서버를 크게 늘렸는데 처리량이 안 올라갑니다. 왜죠?"

병목이 앱 서버가 아니라는 뜻이다. 후보는 뒷단 공유 자원 — DB(CPU, 커넥션 수, 락 경합), 외부 API, 공용 캐시. 특히 앱 인스턴스가 N대면 DB에 꽂히는 커넥션은 N × 풀 크기로 늘어나 DB를 더 빨리 포화시킨다. 증설 전후로 각 계층의 사용률·대기 지표를 비교해 병목 자원을 먼저 찾아야 하고, **"확장은 병목인 자원에 해야 효과가 있다"**가 원칙이다.

여기에 3-1의 숫자를 붙이면 답이 완성된다. 인스턴스당 풀 20개로 5대를 띄우면 DB에 100개가 꽂히는데, PostgreSQL의 `max_connections` 기본값이 100이므로 6대째부터는 커넥션 획득 자체가 실패한다(`FATAL: sorry, too many clients already`). 그리고 상한에 걸리지 않아도 문제다 — **처리량은 DB 상한에 묶여 그대로인데 DB가 감당하는 프로세스 수와 락 경합만 2배가 되므로, 쿼리 하나의 응답시간이 오히려 나빠진다.** 앱 증설이 DB를 더 빨리 죽이는 경로가 이것이다.

옳은 접근은 필요 커넥션 수를 대수가 아니라 Little's Law로 정하는 것이다(3-2). 목표 500 TPS에 커넥션 점유 시간 50ms면 전체 필요량은 500 × 0.05 = 25개이고, 이 값은 앱 서버가 몇 대든 변하지 않는다. **앱 서버를 늘리면 인스턴스당 풀은 오히려 줄어야 한다.**

병목을 찾는 방법도 한 줄 얹으면 좋다. 각 계층의 **사용률과 대기 지표를 짝으로** 본다 — 앱은 톰캣 스레드 사용률과 큐 대기, DB 앞단은 커넥션 풀의 대기 시간(HikariCP의 acquire time)과 `pg_stat_activity`의 상태 분포, DB 안은 CPU와 락 대기다. 어느 계층의 **대기 시간이 늘고 있는지**가 병목의 위치를 가리킨다.

### "오토스케일링을 도입하려면 무엇이 준비돼야 하나요?"

(1) **stateless** — 어느 인스턴스가 사라져도, 새로 떠도 무방해야 한다. 2-5의 전제가 여기서 훨씬 엄격해진다. 대수가 사람이 아니라 자동으로 바뀌므로, 로컬 상태에 의존하는 버그는 새벽에 축소가 일어날 때 처음 드러난다.

(2) **빠른 기동과 워밍업** — 뜨는 데 5분 걸리면 스파이크를 못 따라간다. 컨테이너 이미지 크기, 스프링 컨텍스트 초기화 시간, JIT 워밍업, 캐시 예열이 전부 여기에 들어간다. 그리고 워밍업이 안 된 인스턴스에 트래픽을 바로 보내면 그 인스턴스만 응답이 느려 p99를 끌어올린다.

(3) **graceful shutdown** — 축소 시 처리 중 요청을 안전하게 마무리해야 한다. 순서는 LB에서 제외 → 새 요청 유입 차단 → 진행 중 요청 완료 대기(드레이닝) → 종료다. 이 순서가 어긋나면 축소마다 5xx가 튄다.

(4) **병목과 일치하는 스케일링 지표** — I/O 바운드 서비스는 CPU가 낮은 채로 죽으므로 CPU 기준 HPA는 영원히 발동하지 않을 수 있다. 이 주제는 22번 문서에서 다룬다.

(5) **커넥션 총량이 최대 대수 기준으로 계산돼 있을 것.** 3-2에서 본 지점이다. 현재 3대 기준으로 풀을 잡아 두면 스케일 아웃이 20대까지 갔을 때 DB 커넥션 상한을 넘겨 터진다. **오토스케일링을 켜는 순간 "최대 대수 × 인스턴스당 풀"이 DB 상한 안에 들어오는지 반드시 역산해야 한다.**

### "수평 확장이 항상 정답인가요? 수직 확장을 택할 상황은?" (시니어 변별 포인트)

아니다. 트래픽 규모가 작거나 예측 가능하면 수직 확장이 더 싸고 단순하다 — 분산 복잡도(배포, 정합성, 관측)를 지불할 이유가 없다. DB·캐시처럼 상태 있는 계층은 애초에 scale-up이 1순위 수단이고, 라이선스가 장비 단위인 소프트웨어나 강한 단일 노드 성능이 필요한 워크로드(대형 트랜잭션, 인메모리 연산)도 수직이 낫다. **"무조건 scale-out"은 트레이드오프를 계산 안 해봤다는 신호다** — 확장 방식은 종교가 아니라 비용·복잡도·가용성 요구의 함수다.

근거를 조금 더 대면 좋다. **수직 확장의 비용 곡선은 하위 구간에서는 오히려 유리하다**(2-2). 작은 인스턴스 두 대보다 그 두 배 사양 한 대가 저렴한 구간이 실제로 있고, 여기에 로드밸런서 비용과 분산 추적·배포 파이프라인을 유지하는 사람의 시간까지 더하면 격차가 더 벌어진다. 비용 곡선이 급해지는 것은 최상위 사양 구간이므로, **아직 그 구간에 도달하지 않았다면 수직 확장이 합리적 선택**이다.

그리고 3-3의 근거를 얹으면 결정적이다. **쓰기는 대수로 확장되지 않으므로, 쓰기 용량을 올리는 수단은 샤딩 전까지 수직 확장뿐이다.** "DB도 scale-out하면 되죠"라고 답하면 읽기와 쓰기의 비대칭을 모른다는 뜻이 된다.

역으로 수평 확장이 반드시 필요한 조건도 말할 수 있어야 한다. **가용성 요구가 단일 장애점을 허용하지 않을 때**(2-3)와 **트래픽 변동 폭이 커서 상시 최대 사양을 유지하는 것이 낭비일 때**다. 후자는 비용 절감이 아니라 "필요할 때만 산다"는 탄력성의 가치이고, 수직 확장에는 이 카드가 없다.

### "세션 말고 scale-out을 방해하는 로컬 상태의 예를 더 들어보세요."

로컬 디스크에 저장한 업로드 파일(다른 서버에서 404), 서버별 인메모리 캐시의 갱신 불일치(A서버는 새 값, B서버는 옛 값 응답), `@Scheduled` 같은 단일 실행 가정 배치의 N중 중복 실행(분산 락 필요), 인메모리 rate limit 카운터(서버별 카운트 합이 전체 한도를 초과), WebSocket처럼 연결 자체가 상태인 경우(특정 서버에 붙은 연결로만 푸시 가능 → pub/sub로 브로드캐스트 필요).

각각이 왜 깨지는지 한 줄로 붙이면 이해도가 드러난다. 공통 구조는 **"어느 서버로 갈지 모른다"와 "각 서버는 서로의 메모리를 못 본다"** 두 사실의 조합이다. 업로드 파일은 쓴 서버와 읽는 서버가 달라서, 인메모리 캐시는 무효화가 한 서버에만 적용돼서, `@Scheduled`는 모든 서버가 같은 시각에 같은 일을 시작해서, rate limit 카운터는 서버마다 따로 세서 깨진다.

특히 rate limit는 숫자로 말하면 명확하다. **인스턴스별 인메모리 카운터로 "분당 100회" 한도를 걸고 서버를 3대로 늘리면 실제 허용량은 분당 300회가 된다.** 한도가 조용히 3배로 풀린 것이고, 대수를 바꿀 때마다 값이 또 달라진다. 그래서 rate limit는 중앙 저장소(Redis)에 카운터를 두거나 한도를 대수로 나눠 배분해야 한다(8번 문서).

각 상태를 어떻게 외부화하는지는 4번 문서에서 다룬다.

## 한 줄 요약

scale-up은 장비 사양을 올려 단순하지만 물리적·비용적 천장과 단일 장애점이 남고(직렬 구간이 5%뿐인 애플리케이션도 코어를 무한히 늘려 얻을 수 있는 상한은 20배다), scale-out은 대수를 늘려 상한 없이 확장하지만 stateless 전제와 분산 복잡도를 요구한다 — 그리고 앱 서버를 아무리 늘려도 확장의 병목은 결국 상태 있는 계층(DB·세션)으로 수렴하는데, 인스턴스마다 자기 커넥션 풀을 갖기 때문에 앱 증설은 처리량을 못 올린 채 DB 커넥션만 배수로 늘려 오히려 DB를 먼저 쓰러뜨린다 — 필요 커넥션은 앱 대수가 아니라 λW가 정하므로 총량을 계산해 대수로 나누고, 쓰기는 순서를 정해야 해서 한 지점으로 수렴하는 반면 읽기는 복사본을 늘려 확장되는 비대칭을 이해한 뒤, 상태를 외부화하고 DB를 수직 확장 → 읽기 복제 → 캐시 → 샤딩의 사다리로(되돌리기 쉬운 것부터, 코드 변경이 적은 것부터) 다루는 것이 실전의 확장 설계다.
