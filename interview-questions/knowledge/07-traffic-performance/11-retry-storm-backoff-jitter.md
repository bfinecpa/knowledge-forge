# 재시도(retry) 설계 — 선의의 재시도가 장애를 증폭시키는 이유와 backoff + jitter

> 핵심 관전 포인트: **재시도는 일시적 실패를 흡수하는 장치지만, 상대가
> 지속적 장애 상태일 때는 실패한 요청 수만큼 트래픽을 곱해서 다시
> 던지는 부하 증폭기가 된다. 실패율이 높을수록 재시도가 많아지고,
> 그 재시도가 부하를 키워 실패율을 더 높이는 양의 되먹임이
> retry storm이다 — 죽어가는 상대의 복구를 재시도가 막는다.
> 특히 호출 체인의 여러 계층이 각자 재시도하면 증폭은 곱셈으로
> 폭발한다(계층당 3회면 3계층에 27배). 방어는 exponential backoff로
> 재시도 간격을 지수적으로 벌리고, jitter로 재시도 시각의 동기화를
> 깨고, 재시도 횟수·예산(retry budget)에 상한을 두고, 재시도는
> 호출 체인에서 한 계층만 담당하게 하는 것이다.**

---

## 0. 질문 + 의도

**질문**: "재시도(retry)를 잘못 설계하면 장애를 증폭시키는 이유는? (retry storm, exponential backoff + jitter)"

**출제 의도**: 장애 중인 서버에 재시도 폭탄이 떨어져 복구를 막는
retry storm은 "선의의 코드가 장애를 키우는" 대표 사례다.
backoff+jitter라는 기법을 아는지보다, 실패 대응 코드가 오히려 장애를
증폭시킨다는 이 역설을 인식하고 있는지가 중요하다.

## 1. 증폭의 산수 — 재시도는 실패율에 비례해 부하를 곱한다

재시도의 전제는 "실패가 **일시적**이다"라는 가설이다. 네트워크 패킷
유실, 순간적 GC pause, 배포 중 순단 같은 실패는 한 번 더 시도하면
대부분 성공한다. 이 가설이 맞을 때 재시도는 훌륭한 장치다.

문제는 가설이 틀렸을 때, 즉 상대가 **과부하나 지속 장애**로 실패하고
있을 때다. 산수로 보면:

- 서버가 용량 초과로 요청의 100%를 실패시키는 상황에서, 클라이언트가
  최대 3회 재시도하면 원래 트래픽의 **최대 4배**(원 요청 1 + 재시도 3)가
  들어온다. 과부하 때문에 실패하는 서버에 부하를 4배로 늘려준 것이다.
- 더 나쁜 것은 **되먹임 구조**다: 부하 증가 → 실패율 상승 → 재시도
  증가 → 부하 추가 증가. 실패율이 높을수록 재시도가 많아지는 구조라서,
  장애가 깊어질수록 증폭 배율도 커진다. 상대가 재기동해도 밀려 있는
  재시도 파도에 맞아 다시 쓰러진다 — **복구를 재시도가 막는** 상태,
  이것이 retry storm이다.

### 다층 재시도 — 증폭은 곱셈이 된다 (가산점 포인트)

호출 체인의 각 계층이 각자 재시도하면 배율이 곱해진다.

```text
앱 클라이언트(3회) → 게이트웨이(3회) → 주문 서비스(3회) → 결제 API
```

결제 API가 죽으면 주문 서비스는 3회 시도하고 실패를 반환한다.
게이트웨이는 그 실패를 보고 주문 서비스를 다시 3회 호출하고 —
호출마다 주문 서비스는 또 결제를 3회 시도한다. 앱까지 합치면
결제 API가 받는 요청은 원 요청 1건당 **3 × 3 × 3 = 27건**이다.
계층마다 "고작 3회"라는 합리적으로 보이는 설정이 모여 시스템 전체로는
장애 지점에 수십 배 부하를 퍼붓는다. 그래서 재시도 설계는 개별 호출의
문제가 아니라 **호출 체인 전체를 놓고 봐야 하는 문제**다.

```java
// Before: 간격 없는 즉시 재시도 — 실패 즉시 다시 두드린다
public PaymentResult payWithRetry(Order order) {
    for (int i = 0; i < 3; i++) {
        try {
            return paymentClient.pay(order);
        } catch (Exception e) {
            // 대기 없이 즉시 재시도 — 장애 중인 상대에게 초 단위로 부하 3배
        }
    }
    throw new PaymentFailedException();
}
```

## 2. exponential backoff + jitter — 간격을 벌리고, 동기화를 깬다

### backoff: 재시도 간격을 지수적으로 늘린다

즉시 재시도의 문제는 실패 원인(과부하)이 해소될 시간을 주지 않는다는
것이다. exponential backoff는 재시도 간격을 시도마다 지수적으로
늘린다 — 1초, 2초, 4초, 8초… "상대가 아픈 것 같으니 점점 더 오래
기다렸다가 물어본다"는 전략으로, 지속 장애일수록 재시도 빈도가
자동으로 떨어져 증폭이 완화된다.

### jitter: backoff만으로는 파도가 남는다

그런데 backoff에는 함정이 있다. 장애가 나는 순간 **수천 개의
클라이언트가 동시에 실패**하고, 모두 같은 backoff 규칙을 따르면
**같은 시각에 일제히 재시도**한다. 1초 뒤 수천 건, 2초 뒤 수천 건 —
평균 부하는 낮아졌지만 순간 부하는 여전히 스파이크의 파도로 몰려온다.
회복 중인 서버는 평균이 아니라 순간 피크에 쓰러진다.

jitter(지터)는 이 **동기화를 무작위성으로 깨는 것**이다. 각
클라이언트가 backoff 간격에 무작위 편차를 더해 재시도 시각을 흩뿌리면,
파도가 완만한 흐름으로 펴진다. 널리 쓰이는 full jitter 방식은
"0 ~ (기본 간격 × 2^시도횟수)" 범위에서 균등 난수로 대기 시간을 뽑는다.

```java
// After: exponential backoff + jitter (Resilience4j)
RetryConfig config = RetryConfig.custom()
        .maxAttempts(3)                              // 원 호출 포함 총 3회 상한
        .intervalFunction(IntervalFunction
                .ofExponentialRandomBackoff(
                        Duration.ofMillis(500),      // 초기 간격 500ms
                        2.0,                         // 시도마다 2배 (500 → 1000 → 2000)
                        0.5))                        // 무작위 편차 ±50% = jitter
        .retryExceptions(IOException.class, TimeoutException.class)  // 재시도할 실패만
        .build();
```

한 문장으로: **backoff는 재시도의 총량(빈도)을 줄이고, jitter는
재시도의 분포(동시성)를 펴준다.** 둘은 세트다 — backoff만 있으면
동기화된 파도가 남고, jitter만 있으면 총량이 줄지 않는다.

## 3. backoff + jitter로도 부족한 것 — 재시도 설계 체크리스트

backoff + jitter는 증폭을 완화할 뿐 없애지 못한다. 실무 재시도
설계에서 함께 점검할 것들:

- **재시도해도 되는 실패인지부터 구분한다.** 4xx(잘못된 요청, 인증
  실패)는 몇 번을 다시 보내도 결과가 같다 — 재시도는 순수한 낭비다.
  재시도 대상은 일시성이 있는 실패(연결 실패, 타임아웃, 5xx 일부,
  429는 Retry-After 존중)로 한정한다. 또 **멱등성**: read timeout처럼
  "요청이 상대에 도달해 처리됐을 수도 있는" 실패를 비멱등 요청(결제
  승인)에 재시도하면 중복 처리가 난다 — 멱등 키 없이는 재시도하면
  안 된다(타임아웃 문서 10-timeout-layers-and-budget.md의 구분 참고).
- **retry budget — 횟수 제한을 시스템 단위로 보강한다. (가산점 포인트)**
  `maxAttempts=3`은 요청 1건의 상한일 뿐, 유입이 초당 1,000건이면
  재시도도 초당 수천 건이 될 수 있다. retry budget은 "전체 트래픽 중
  재시도가 차지하는 비율은 최대 N%(예: 10%)"처럼 **총량에 상한**을
  두는 방식이다. 예산을 넘으면 재시도를 포기하고 즉시 실패시킨다 —
  대규모 장애일수록 재시도를 접는, retry storm의 구조적 차단기다.
- **재시도는 호출 체인에서 한 계층만.** 다층 곱셈 증폭을 막으려면
  "재시도는 실패 지점에 가장 가까운 한 곳(또는 최상위 한 곳)만
  담당한다"를 팀 규칙으로 정해야 한다. 특히 HTTP 클라이언트·DB
  드라이버·메시지 프로듀서가 **기본값으로 자동 재시도**를 하는 경우가
  있어, 내가 명시한 재시도 외에 숨은 재시도가 없는지 감사해야 한다.
- **타임아웃 예산 안에서.** 재시도의 최악 소요는 (호출 타임아웃 +
  backoff) × 시도 횟수로 곱해진다. 이 합이 상류 타임아웃 예산을 넘으면
  하류는 아직 재시도 중인데 상류는 이미 실패로 응답하는 모순이 생긴다.
- **서킷 브레이커와의 결합.** 재시도는 "일시적 실패"용이고, 지속
  장애 국면에서는 서킷이 열려 재시도 자체를 차단해야 한다. 배치 순서는
  안쪽부터 타임아웃 → 재시도 → 서킷 — 서킷이 재시도 바깥에 있어야
  서킷 open 시 재시도까지 함께 멈춘다(서킷 문서
  09-circuit-breaker-state-transition-tuning.md 참고).

## 4. 꼬리질문 대비 포인트

### "backoff가 있는데 jitter는 왜 또 필요한가요?"

backoff는 개별 클라이언트의 재시도 빈도만 줄인다. 장애 순간에 동시에
실패한 수많은 클라이언트가 같은 backoff 스케줄을 따르면 1초 뒤, 2초 뒤
같은 시각에 일제히 재시도하는 **동기화된 파도**가 생긴다. 회복 중인
서버는 평균 부하가 아니라 순간 피크에 다시 쓰러지므로, 재시도 시각에
무작위 편차를 줘 파도를 시간 축으로 펴는 jitter가 반드시 필요하다.
"backoff는 총량, jitter는 분포"가 핵심 문장.

### "어떤 실패는 재시도하면 안 되나요?"

두 축으로 거른다. (1) **일시성**: 4xx처럼 다시 보내도 결과가 같은
결정적 실패는 재시도가 낭비다. 연결 실패·타임아웃·5xx 일부만 대상으로
한다. (2) **멱등성**: connection timeout은 요청이 상대에 도달하기 전의
실패라 재시도가 안전하지만, read timeout은 이미 처리됐을 수 있는
상태라 비멱등 요청(결제·주문 생성)에 재시도하면 중복 처리가 난다 —
멱등 키(idempotency key)를 함께 설계했을 때만 재시도할 수 있다.

### "재시도 횟수와 간격은 어떤 근거로 정하나요?"

위로는 **상류의 타임아웃 예산**이 상한이다 — (호출 타임아웃 + backoff)
× 시도 횟수의 최악 합이 예산 안에 들어와야 한다. 아래로는 실패의
성격이다 — 일시적 실패는 대부분 첫 번째 재시도에서 해소되므로,
실무에서는 1~2회면 충분한 경우가 많고 횟수를 늘릴수록 성공 확률은
미미하게 오르는데 장애 시 증폭 배율만 커진다. "많이 재시도할수록
견고하다"가 아니라 "재시도 1회의 한계 효용이 급감한다"는 관점으로
답하면 좋다.

### "재시도 로직을 넣었는데도 장애가 증폭됐다면 어디를 의심하나요?" (시니어 변별 포인트)

내가 작성한 재시도 바깥의 **숨은 재시도 계층**들을 감사한다.
(1) HTTP 클라이언트·DB 드라이버·Kafka 프로듀서 등 라이브러리의
기본 자동 재시도, (2) 로드밸런서·서비스 메시의 요청 재전송,
(3) 프론트엔드/앱의 재시도와 **사용자의 새로고침 연타** — 시스템
바깥의 인간도 재시도 계층이다, (4) 실패한 메시지를 다시 큐에 넣는
컨슈머 재처리 루프. 이들이 겹치면 코드상 3회가 실제로는 수십 배가
된다. 그리고 복구 국면도 본다 — 장애 중 쌓인 재시도 대기분이 복구
직후 한꺼번에 몰리는 2차 파도까지 관측(재시도 비율 지표, 대상별
재시도 카운트)으로 확인해야 "재시도를 설계했다"고 말할 수 있다.

### "429(Too Many Requests)를 받았을 때의 재시도는 어떻게 다르게 처리하나요?" (가산점 포인트)

429는 상대가 "지금 과부하이니 물러나라"고 **명시적으로 신호**한
것이므로, 내 backoff 스케줄보다 상대가 준 Retry-After 헤더를
우선한다. 이를 무시하고 자체 backoff로 재시도하면 rate limit에 계속
걸리며 상대의 차단 정책을 악화시킬 수 있다. 상대의 backpressure
신호를 존중하는 것까지가 재시도 설계다(backpressure 문서
16-backpressure-and-application-points.md 참고).

## 한 줄 요약

재시도는 "실패가 일시적"이라는 가설 위의 장치라서, 지속 장애 국면에는
실패율에 비례해 부하를 곱하는 증폭기가 되고(다층이면 곱셈 폭발)
복구까지 막는 retry storm을 만든다 — exponential backoff로 빈도를
줄이고 jitter로 동시성을 흩뿌리되, 재시도 가능한 실패의 구분(일시성·
멱등성), retry budget, 단일 계층 원칙, 타임아웃 예산, 서킷과의 결합까지
갖춰야 "장애를 키우지 않는 재시도"가 된다.
