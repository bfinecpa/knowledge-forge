# 재시도(retry) 설계 — 선의의 재시도가 장애를 증폭시키는 이유와 backoff + jitter

> 핵심 관전 포인트: **재시도는 일시적 실패를 흡수하는 장치지만, 상대가 지속적 장애 상태일 때는 실패한 요청 수만큼 트래픽을 곱해서 다시 던지는 부하 증폭기가 된다. 실패율이 높을수록 재시도가 많아지고, 그 재시도가 부하를 키워 실패율을 더 높이는 양의 되먹임이 retry storm이다 — 죽어가는 상대의 복구를 재시도가 막는다. 단일 계층에서도 재시도 3회는 유입을 최대 4배로 만들고(원 호출 1 + 재시도 3), 호출 체인의 여러 계층이 각자 재시도하면 상위의 재시도가 하위 전체를 통째로 다시 실행하므로 증폭이 덧셈이 아니라 **곱셈**으로 폭발한다(계층당 총 시도 3회면 3계층에 3×3×3 = 27배, 계층당 재시도 3회면 4×4×4 = 64배). 방어는 exponential backoff로 재시도 간격을 지수적으로 벌리고, jitter로 재시도 시각의 동기화를 깨고(backoff는 총량, jitter는 분포), 재시도 횟수·예산(retry budget)에 상한을 두고, 재시도는 호출 체인에서 한 계층만 담당하게 하는 것이다. 그리고 재시도 대상의 구분에서 가장 중요한 회색지대는 **타임아웃** — 성공인지 실패인지 알 수 없는 상태이므로, 재시도하려면 그 연산이 멱등이어야 한다.**

---

## 0. 질문 + 의도

**질문**: "재시도(retry)를 잘못 설계하면 장애를 증폭시키는 이유는? (retry storm, exponential backoff + jitter)"

**출제 의도**: 장애 중인 서버에 재시도 폭탄이 떨어져 복구를 막는 retry storm은 "선의의 코드가 장애를 키우는" 대표 사례다. backoff+jitter라는 기법을 아는지보다, 실패 대응 코드가 오히려 장애를 증폭시킨다는 이 역설을 인식하고 있는지가 중요하다.

## 1. 증폭의 산수 — 재시도는 실패율에 비례해 부하를 곱한다

### 1-1. 전제 지식 — 재시도는 "실패가 일시적"이라는 가설 위에 서 있다

재시도의 전제는 **"실패가 일시적(transient)이다"**라는 가설이다. 여기서 일시적이란 **"같은 요청을 조금 뒤에 다시 보내면 결과가 달라질 수 있다"**는 뜻이다.

이 조건을 만족하는 실패가 실제로 있다. 네트워크 패킷 유실, 순간적인 GC 일시 정지, 배포 중 인스턴스가 교체되는 몇 초의 순단, 로드밸런서가 죽은 인스턴스를 아직 제거하지 못한 짧은 창. 이런 실패는 한 번 더 시도하면 대부분 성공한다. 원인이 이미 사라졌기 때문이다.

**이 가설이 맞을 때 재시도는 훌륭한 장치다.** 사용자에게 에러를 보이지 않고 실패를 흡수해 주고, 코드도 몇 줄이면 된다. 그래서 널리 쓰이고, 그래서 위험하다.

문제는 가설이 틀렸을 때다. 상대가 **과부하나 지속 장애**로 실패하고 있다면, 원인은 사라지지 않았고 오히려 우리 재시도가 원인을 키운다. 다음 절의 산수가 그것을 보여준다.

### 1-2. 단일 계층의 증폭 — 재시도 3회는 최대 4배다

용어를 먼저 정확히 하자. **"재시도 3회"와 "총 시도 3회"는 다른 말이다.** 이 구분을 흐리면 아래의 모든 계산이 어긋난다.

```text
총 시도 횟수(attempts) = 원 호출 1회 + 재시도 횟수(retries)

재시도 3회  →  총 시도 4회  →  유입 배율 최대 4배
총 시도 3회  →  재시도 2회  →  유입 배율 최대 3배
```

Spring Retry의 `maxAttempts`와 Resilience4j의 `maxAttempts`는 모두 **원 호출을 포함한 총 시도 횟수**다. `maxAttempts = 3`은 "3번 재시도"가 아니라 "원 호출 1 + 재시도 2"다. 여기서 착각하면 의도한 것보다 재시도가 하나 적거나 많아진다.

이제 계산해 보자. 유입 1,000 TPS인 API가 있고, 클라이언트가 **재시도 3회(총 시도 4회)**를 하도록 설정돼 있다. 상대의 실패율에 따라 상대가 실제로 받는 요청 수가 어떻게 달라지는지 한 단계씩 따라가 보자.

```text
[상대의 실패율 100% — 용량 초과로 모든 요청이 실패]

  원 호출            1,000건  →  전부 실패
  재시도 1회차       1,000건  →  전부 실패
  재시도 2회차       1,000건  →  전부 실패
  재시도 3회차       1,000건  →  전부 실패
                   ─────────
  상대가 받는 총량    4,000건 TPS   =  유입의 4.0배

  ★ 과부하 때문에 실패하는 서버에 부하를 4배로 늘려 준 것이다.
```

실패율이 100%가 아니면 배율은 줄어든다. 실패한 요청만 재시도되기 때문이다.

```text
[상대의 실패율 50%]

  원 호출        1,000건  →  500건 실패
  재시도 1회차     500건  →  250건 실패
  재시도 2회차     250건  →  125건 실패
  재시도 3회차     125건
               ─────────
  총량           1,875건 TPS   =  유입의 1.875배
  검산: 1,000 + 500 + 250 + 125 = 1,875

[상대의 실패율 10%]

  원 호출        1,000건  →  100건 실패
  재시도 1회차     100건  →   10건 실패
  재시도 2회차      10건  →    1건 실패
  재시도 3회차       1건
               ─────────
  총량           1,111건 TPS   =  유입의 1.111배
  검산: 1,000 + 100 + 10 + 1 = 1,111
```

표로 나란히 놓으면 이 산수의 진짜 의미가 보인다.

| 상대의 실패율 | 상대가 받는 총량 | 배율 |
|---|---|---|
| 10% | 1,111 TPS | 1.11배 |
| 50% | 1,875 TPS | 1.88배 |
| 100% | 4,000 TPS | 4.00배 |

**증폭 배율이 실패율에 비례한다.** 즉 **상대가 건강할 때는 재시도가 부하를 거의 안 늘리고, 상대가 아플 때 정확히 그만큼 더 때린다.** 이것이 재시도의 가장 고약한 성질이다. 평상시 부하 테스트로는 절대 발견되지 않고, 장애 순간에만 최대치로 발동한다.

### 1-3. 되먹임 구조 — 이것이 retry storm이다

앞 절의 표는 정적인 계산이었다. 실제로는 여기에 되먹임이 붙어 상황이 스스로 악화된다.

```text
  ┌──────────────────────────────────────────┐
  │                                          │
  ▼                                          │
상대의 부하 증가                                │
  → 상대의 처리 능력을 넘어섬                    │
  → 실패율 상승 ────────────────────────┐      │
                                       │      │
  1-2의 표에서 봤듯이 실패율이 높을수록    │      │
  증폭 배율도 커진다                      │      │
                                       ▼      │
  → 재시도 건수 증가 ──────────────────────────┘
```

실패율 10%에서 1.11배였던 증폭이, 실패율이 50%로 오르면 1.88배가 되고, 100%가 되면 4배가 된다. **증폭이 커지면 부하가 커지고, 부하가 커지면 실패율이 오르고, 실패율이 오르면 증폭이 다시 커진다.** 한 방향으로만 굴러가는 구조다.

그리고 결정적인 결과가 하나 더 있다. **상대가 재기동해도 살아나지 못한다.** 재기동 직후의 서버는 캐시가 비어 있고 커넥션 풀이 덜 차 있어 정상보다 취약한데, 그 순간 밀려 있던 재시도 파도가 정상 트래픽의 몇 배로 덮친다. 그래서 다시 쓰러지고, 다시 재기동하고, 다시 쓰러진다.

**복구를 재시도가 막는** 이 상태가 **retry storm(재시도 폭풍)**이다. 이름이 폭풍인 이유는 위 그림처럼 스스로를 강화하며 커지기 때문이다.

이것이 "선의의 코드가 장애를 키운다"의 정확한 의미다. 재시도 코드를 쓴 사람의 의도는 사용자에게 에러를 덜 보이는 것이었고, 평상시에는 정확히 그 일을 한다. 그런데 장애 순간에는 같은 코드가 장애를 깊게 만든다.

### 1-4. 다층 재시도 — 왜 덧셈이 아니라 곱셈인가 (가산점 포인트)

지금까지는 재시도하는 계층이 하나였다. 실무에서는 호출 체인의 여러 계층이 각자 재시도를 갖고 있는 경우가 훨씬 흔하다.

```text
앱 클라이언트(총 3회) → 게이트웨이(총 3회) → 주문 서비스(총 3회) → 결제 API
```

각 계층이 "고작 3회"라는 합리적으로 보이는 설정을 갖고 있다. 그러면 결제 API가 받는 호출은 3 + 3 + 3 = 9회인가? **아니다. 3 × 3 × 3 = 27회다.**

왜 곱셈이 되는지가 이 절의 핵심이다. **상위 계층의 재시도는 자기 몫만 다시 하는 것이 아니라, 그 아래 전체를 통째로 다시 실행하는 것**이기 때문이다. 게이트웨이가 주문 서비스를 다시 부르면, 주문 서비스는 처음부터 다시 시작하므로 **자기 재시도 3회도 처음부터 다시 한다.**

트리로 그리면 한눈에 보인다.

```text
사용자 요청 1건
│
└─ [앱 클라이언트] 게이트웨이를 최대 3회 시도
   │
   ├─ 시도 1 ─ [게이트웨이] 주문 서비스를 최대 3회 시도
   │            ├─ 시도 1 ─ [주문 서비스] 결제 API 최대 3회 → 결제 API 3건
   │            ├─ 시도 2 ─ [주문 서비스] 결제 API 최대 3회 → 결제 API 3건
   │            └─ 시도 3 ─ [주문 서비스] 결제 API 최대 3회 → 결제 API 3건
   │                                        게이트웨이 시도 1의 소계 = 9건
   │
   ├─ 시도 2 ─ (같은 구조 반복)                             소계 = 9건
   │
   └─ 시도 3 ─ (같은 구조 반복)                             소계 = 9건
                                        ────────────────────────────
                                        결제 API가 받는 총 호출 = 27건
```

계층 수와 계층당 시도 횟수에 따라 어떻게 불어나는지 보면 이 구조의 위험이 분명해진다.

| 재시도하는 계층 수 | 계층당 총 시도 | 최말단이 받는 호출 | 계산 |
|---|---|---|---|
| 1 | 3 | 3건 | 3¹ |
| 2 | 3 | 9건 | 3² |
| 3 | 3 | 27건 | 3³ |
| 4 | 3 | 81건 | 3⁴ |
| 3 | 4 (재시도 3회) | 64건 | 4³ |
| 3 | 5 (재시도 4회) | 125건 | 5³ |

검산하면 3³ = 27, 4³ = 64, 5³ = 125, 3⁴ = 81이다. **계층당 시도를 하나 늘리는 것보다 재시도하는 계층을 하나 늘리는 것이 훨씬 위험하다** — 전자는 배율을 더하지만 후자는 배율을 곱한다.

그리고 여기에 시스템 바깥의 계층이 하나 더 있다. **사용자다.** 실패 화면을 본 사용자가 새로고침을 세 번 누르면 27건이 81건이 된다. 사람도 재시도 계층이라는 점은 설계에서 잊기 쉽다.

**그래서 재시도 설계는 개별 호출의 문제가 아니라 호출 체인 전체를 놓고 봐야 하는 문제**이고, 원칙은 **"재시도는 한 계층에서만"**이 된다. 이 원칙의 근거가 바로 위 트리다.

### 1-5. 가장 나쁜 형태 — 간격 없는 즉시 재시도

증폭 위에 하나가 더 얹히면 최악이 된다. 대기 없이 곧바로 다시 던지는 코드다.

```java
// Before: 간격 없는 즉시 재시도 — 실패 즉시 다시 두드린다
public PaymentResult payWithRetry(Order order) {
    for (int i = 0; i < 3; i++) {
        try {
            return paymentClient.pay(order);
        } catch (Exception e) {
            // 문제 ①: 대기가 없다.
            //   실패 원인(상대의 과부하)이 해소될 시간을 0초 주고 다시 던진다.
            //   1-2의 4배 증폭이 몇 밀리초 안에 몰려서 발생한다.
            // 문제 ②: 예외를 구분하지 않는다.
            //   400 Bad Request처럼 영원히 실패할 요청도 3번 보낸다.
            //   순수한 낭비이고, 상대의 에러 로그를 3배로 오염시킨다.
            // 문제 ③: 멱등성을 고려하지 않는다.
            //   read timeout이었다면 첫 시도가 실제로 승인됐을 수 있다.
            //   그 위에 재시도를 얹으면 이중 결제다 (3-2).
            // 문제 ④: 재시도 사실이 아무 데도 기록되지 않는다.
            //   지표가 없으므로 장애 때 "재시도가 몇 배로 뛰었는지"를 볼 수 없다.
        }
    }
    throw new PaymentFailedException();
}
```

이 네 가지가 2절과 3절의 목차가 된다.

## 2. exponential backoff + jitter — 간격을 벌리고, 동기화를 깬다

### 2-1. backoff — 재시도 간격을 지수적으로 늘린다

**backoff**는 "물러남"이라는 뜻이고, 여기서는 **재시도하기 전에 기다리는 것**을 말한다. 즉시 재시도의 문제가 "실패 원인이 해소될 시간을 주지 않는다"였으므로, 시간을 주는 것이 첫 번째 처방이다.

그런데 얼마나 기다려야 하는가. 고정 간격(매번 1초)도 가능하지만, **exponential backoff(지수 백오프)**는 간격을 시도마다 배수로 늘린다 — 500ms, 1초, 2초, 4초… "상대가 아픈 것 같으니 점점 더 오래 기다렸다가 물어본다"는 전략이다.

지수적으로 늘리는 이유는 **실패가 반복될수록 "일시적 실패"라는 가설의 신뢰도가 떨어지기** 때문이다. 첫 실패는 패킷 유실일 수 있으니 금방 다시 물어볼 만하다. 세 번 연속 실패했다면 지속 장애일 확률이 훨씬 높으므로 오래 기다려야 한다. **지속 장애일수록 재시도 빈도가 자동으로 떨어져 증폭이 완화되는** 구조다.

계산은 단순하다. 초기 간격을 `base`, 배수를 `multiplier`, 재시도 회차를 `n`이라 하면 `n`번째 재시도 전에 기다리는 시간은 `base × multiplier^(n-1)`이다. 그리고 무한히 늘어나지 않게 상한(`cap`)을 둔다.

`base = 500ms`, `multiplier = 2`, `cap = 8초`로 계산해 보자.

| 재시도 회차 | 지수 계산 | 계산 결과 | cap 적용 후 |
|---|---|---|---|
| 1 | 500 × 2⁰ | 500ms | 500ms |
| 2 | 500 × 2¹ | 1,000ms | 1,000ms |
| 3 | 500 × 2² | 2,000ms | 2,000ms |
| 4 | 500 × 2³ | 4,000ms | 4,000ms |
| 5 | 500 × 2⁴ | 8,000ms | 8,000ms |
| 6 | 500 × 2⁵ | 16,000ms | **8,000ms** (cap) |

cap이 왜 필요한지도 짚어 두자. cap이 없으면 10회차의 대기가 500 × 2⁹ = 256초가 된다. 그렇게 오래 기다린 재시도는 이미 아무도 기다리지 않는 응답을 만드는 일이고(10번 문서의 예산 초과와 같은 낭비), 사용자 요청 경로에서는 애초에 불가능한 값이다.

### 2-2. backoff만으로는 파도가 남는다

여기서 끝이면 좋겠지만, backoff에는 함정이 있다. **모두가 같은 규칙을 따르면 모두가 같은 시각에 재시도한다.**

장애가 나는 순간을 생각해 보자. 상대 서버가 t=0에 응답을 멈추면 그 순간 진행 중이던 **수천 개의 클라이언트가 거의 동시에 실패**한다. 그리고 전원이 같은 backoff 규칙을 갖고 있으므로, 전원이 "500ms 뒤에 재시도"라는 같은 계산을 한다.

시간축에 요청 도착을 표시해 보면 이렇다.

```text
[jitter 없는 backoff — 1,000개 클라이언트가 t=0에 동시에 실패한 경우]

요청 수
1000 ┤ █                 █                 █                             █
     │ █                 █                 █                             █
 500 ┤ █                 █                 █                             █
     │ █                 █                 █                             █
   0 └─┴─────────────────┴─────────────────┴─────────────────────────────┴──▶
      t=0             t=0.5s            t=1.5s                       t=3.5s
      원 호출         재시도 1회차        재시도 2회차                  재시도 3회차
      (동시 실패)     (전원 같은 시각)     (전원 같은 시각)              (전원 같은 시각)

  평균 부하를 계산하면 낮아 보인다:
    3.5초 동안 총 4,000건 → 초당 약 1,143건 (검산: 4,000 ÷ 3.5 = 1,142.9)

  그런데 회복 중인 서버가 실제로 만나는 것은 평균이 아니라
  순간 1,000건의 벽이다. 그 벽에 다시 쓰러진다.
```

**핵심은 마지막 문장이다.** 서버는 평균 부하로 죽지 않는다. 순간 피크로 죽는다. 큐 길이, 스레드 풀 크기, 커넥션 풀 크기 같은 것들은 모두 **동시성의 상한**이고, 평균이 아니라 순간값에 걸린다.

backoff는 재시도의 **총량**을 시간에 걸쳐 줄였지만 **분포**는 손대지 않았다. 파도가 완만해진 것이 아니라 파도 사이의 간격만 벌어진 것이다.

### 2-3. jitter — 동기화를 무작위성으로 깬다

**jitter(지터)는 원래 신호가 미세하게 떨리는 현상을 가리키는 말이고, 여기서는 재시도 시각에 무작위 편차를 일부러 넣는 것**을 뜻한다. 각 클라이언트가 계산한 대기 시간에 난수를 섞으면 재시도 시점이 흩어진다.

같은 상황에 full jitter를 적용하면 도착 분포가 이렇게 바뀐다.

```text
[full jitter — 각자 0 ~ 상한 사이에서 무작위로 뽑는다]

요청 수
1000 ┤ █
     │ █
 500 ┤ █
     │ █
 200 ┤ █  ▒▒▒▒▒
 100 ┤ █  ▒▒▒▒▒
  50 ┤ █  ▒▒▒▒▒ ▒▒▒▒▒▒▒▒▒▒ ▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒▒
   0 └─┴────┴──────────┴──────────┴──────────┴──────────┴──────────▶
      t=0  0.5s       1.5s       2.5s       3.5s       4.5s
      원 호출  ├재시도 1회차┤ ├── 재시도 2회차 ──┤ ├─ 재시도 3회차 ─┤
              0~0.5s에 흩어짐  0~1.0s에 흩어짐    0~2.0s에 흩어짐
```

순간 피크가 얼마나 줄어드는지 계산해 보자. 100ms 단위로 구간을 잘라 세어 본다.

```text
[jitter 없음]  재시도 1회차의 1,000건이 t=0.5s 한 순간에 전부 도착
               → 그 100ms 구간에 1,000건

[full jitter]  재시도 1회차의 1,000건이 0~500ms에 균등하게 흩어짐
               → 100ms 구간 5개에 나뉘어 구간당 평균 200건
               → 순간 피크가 1/5로 (검산: 500 ÷ 100 = 5구간, 1,000 ÷ 5 = 200)

               재시도 3회차의 1,000건은 0~2,000ms에 흩어짐
               → 100ms 구간 20개에 나뉘어 구간당 평균 50건
               → 순간 피크가 1/20로 (검산: 2,000 ÷ 100 = 20구간, 1,000 ÷ 20 = 50)
```

**총량은 그대로 4,000건인데 순간 피크만 떨어졌다.** 그리고 회차가 올라갈수록 흩뿌려지는 폭이 넓어지므로 피크 감소 효과도 커진다.

한 문장으로 정리하면 이렇다. **backoff는 재시도의 총량(빈도)을 줄이고, jitter는 재시도의 분포(동시성)를 펴준다.** 둘은 세트다 — backoff만 있으면 동기화된 파도가 남고, jitter만 있으면 총량이 줄지 않는다.

### 2-4. jitter의 종류 — full, equal, decorrelated

jitter를 넣는 방식이 몇 가지 있고, 무작위성을 어디에 얼마나 섞는지가 다르다. `상한 = min(cap, base × multiplier^(n-1))`이라 두고 계산식을 정리하면 이렇다.

**full jitter** — `대기 = 0 ~ 상한 사이의 균등 난수`. 무작위성이 가장 크다. 아주 짧게 기다릴 수도 있고 상한까지 기다릴 수도 있다.

**equal jitter** — `대기 = 상한/2 + (0 ~ 상한/2 사이의 균등 난수)`. 절반은 고정, 절반은 무작위다. 즉 대기 시간이 `상한/2 ~ 상한` 범위에 들어온다. "최소한 이만큼은 기다린다"는 하한이 보장된다.

**decorrelated jitter** — `대기 = min(cap, base ~ (직전 대기 × 3) 사이의 균등 난수)`. 지수 계산 대신 **직전에 실제로 뽑은 값**을 기준으로 다음 범위를 만든다. 클라이언트마다 뽑는 값이 다르므로 회차가 지날수록 서로의 대기 시간이 점점 더 벌어진다("탈상관"이라는 이름이 여기서 왔다).

앞의 조건(`base = 500ms`, `multiplier = 2`, `cap = 8초`)으로 회차별 실제 대기 시간의 범위를 계산해 보자.

| 재시도 회차 | 상한 (cap 적용) | full jitter 범위 | full 기대값 | equal jitter 범위 | equal 기대값 |
|---|---|---|---|---|---|
| 1 | 500ms | 0 ~ 500ms | 250ms | 250 ~ 500ms | 375ms |
| 2 | 1,000ms | 0 ~ 1,000ms | 500ms | 500 ~ 1,000ms | 750ms |
| 3 | 2,000ms | 0 ~ 2,000ms | 1,000ms | 1,000 ~ 2,000ms | 1,500ms |
| 4 | 4,000ms | 0 ~ 4,000ms | 2,000ms | 2,000 ~ 4,000ms | 3,000ms |
| 5 | 8,000ms | 0 ~ 8,000ms | 4,000ms | 4,000 ~ 8,000ms | 6,000ms |

기대값 계산을 확인해 두자. full jitter는 0~상한 균등이므로 기대값이 `상한 ÷ 2`다. equal jitter는 `상한/2 + (0~상한/2의 기대값 = 상한/4)`이므로 `상한 × 3/4`다. 회차 3을 검산하면 full은 2,000 ÷ 2 = 1,000ms, equal은 2,000 × 0.75 = 1,500ms로 표와 일치한다.

decorrelated jitter는 직전 값에 의존하므로 표가 아니라 한 클라이언트의 실제 진행으로 보여야 한다.

```text
[decorrelated jitter의 한 클라이언트 예 — base 500, cap 8,000]

회차 1: 범위 = 500 ~ min(8000, 500 × 3)   = 500 ~ 1,500   → 뽑은 값 900
회차 2: 범위 = 500 ~ min(8000, 900 × 3)   = 500 ~ 2,700   → 뽑은 값 2,100
회차 3: 범위 = 500 ~ min(8000, 2100 × 3)  = 500 ~ 6,300   → 뽑은 값 1,400
회차 4: 범위 = 500 ~ min(8000, 1400 × 3)  = 500 ~ 4,200   → 뽑은 값 3,800

  ★ 지수 계산과 달리 범위가 단조 증가하지 않는다.
    작은 값을 뽑으면 다음 범위도 좁아진다 — 상대가 곧 회복했을 때
    빠르게 되돌아올 여지를 남기는 성질이다.
```

**무엇을 기본으로 고를 것인가. full jitter를 권한다.** 이유가 셋이다.

첫째, **순간 피크를 가장 크게 줄인다.** 2-3의 계산에서 봤듯이 흩뿌리는 폭이 넓을수록 구간당 요청 수가 줄어드는데, full jitter가 폭이 가장 넓다. equal jitter는 대기가 `상한/2 ~ 상한`에만 들어오므로 흩뿌리는 폭이 full의 절반이다.

둘째, **구현이 가장 단순하다.** 난수 한 번이면 끝이고, 상태(직전 값)를 들고 있지 않아도 된다.

셋째, **평균 대기가 짧다.** 회차 3에서 full은 평균 1초, equal은 평균 1.5초를 기다린다. 같은 회차 안에서 full이 더 빨리 돌아오므로 상대가 이미 회복한 경우의 손실이 작다.

equal jitter를 고르는 경우도 있다. **최소 대기 시간이 보장돼야 할 때**다. full jitter는 0에 가까운 값을 뽑을 수 있어서 "실패 직후 곧바로 재시도"가 일어날 수 있는데, 상대가 확실히 몇 백 밀리초는 필요한 상황(예: 리더 선출이 진행 중)이라면 그 즉시 재시도는 확정적으로 낭비다.

### 2-5. 코드 — 설정으로 표현하면

Resilience4j에서 지수 백오프에 무작위성을 넣는 기본 수단은 `ofExponentialRandomBackoff`다.

```java
// After: exponential backoff + jitter (Resilience4j)
RetryConfig config = RetryConfig.custom()
        .maxAttempts(3)                              // 원 호출 포함 총 3회 상한
        .intervalFunction(IntervalFunction
                .ofExponentialRandomBackoff(
                        Duration.ofMillis(500),      // 초기 간격 500ms
                        2.0,                         // 시도마다 2배 (500 → 1000 → 2000)
                        0.5))                        // 무작위 편차 ±50% = jitter
        .retryExceptions(IOException.class, TimeoutException.class)  // 재시도할 실패만
        .build();
```

여기서 정확히 알아 둘 점이 있다. **`ofExponentialRandomBackoff`의 무작위화는 계산된 간격을 중심으로 ±비율만큼 흔드는 방식**이다. 편차 0.5면 대기 범위가 `간격 × 0.5 ~ 간격 × 1.5`가 된다. 즉 2-4에서 정의한 full jitter(0 ~ 상한)와는 다르고, equal jitter에 가깝지만 그것과도 정확히 같지는 않다.

**full jitter를 그대로 쓰고 싶으면 `IntervalFunction`을 직접 주면 된다.**

```java
// full jitter를 명시적으로 구현한다 — 0 ~ 상한 사이 균등 난수
IntervalFunction fullJitter = attempt -> {   // attempt는 1부터 시작
    long base = 500L;
    long cap = 8_000L;
    // 지수 계산 후 cap을 씌운다. cap이 없으면 회차가 늘수록
    // 대기가 무한히 커져 타임아웃 예산을 통째로 넘긴다(3-5).
    long upperBound = Math.min(cap, base * (1L << (attempt - 1)));
    // 0 ~ upperBound 균등. 이 폭이 넓을수록 순간 피크가 낮아진다(2-3).
    return ThreadLocalRandom.current().nextLong(upperBound + 1);
};

RetryConfig config = RetryConfig.custom()
        .maxAttempts(3)
        .intervalFunction(fullJitter)
        .retryExceptions(IOException.class, TimeoutException.class)
        .build();
```

Spring Retry를 쓴다면 애노테이션으로 같은 정책을 표현한다.

```java
@Retryable(
        // 재시도할 예외를 화이트리스트로 정한다.
        // 지정하지 않으면 모든 예외를 재시도하므로, 400 Bad Request처럼
        // 영원히 실패할 요청까지 3번 보내게 된다(3-1).
        retryFor = { IOException.class, TimeoutException.class },
        // 절대 재시도해선 안 되는 예외는 명시적으로 제외한다.
        noRetryFor = { BadRequestException.class, UnauthorizedException.class },
        // ★ 원 호출을 포함한 총 시도 횟수다. 이 값이 3이면 재시도는 2회다.
        maxAttempts = 3,
        backoff = @Backoff(
                delay = 500,        // 초기 간격
                multiplier = 2,     // 배수 → 500, 1000, 2000
                maxDelay = 8000,    // cap
                random = true))     // 간격에 무작위 편차를 넣는다 = jitter
public PaymentResult pay(Order order) {
    return paymentClient.pay(order);
}

@Recover
public PaymentResult recover(IOException e, Order order) {
    // 재시도를 모두 소진한 뒤의 처리. 여기서 무엇을 할지가
    // 서킷 브레이커의 fallback 설계와 이어진다(9번 문서 3-7).
    return PaymentResult.pending(order.getId());
}
```

## 3. backoff + jitter로도 부족한 것 — 재시도 설계 체크리스트

backoff + jitter는 증폭을 **완화**할 뿐 없애지 못한다. 1-2의 4배가 시간에 걸쳐 퍼졌을 뿐, 상대가 받는 총량은 여전히 4배다. 그래서 실무 재시도 설계에는 다섯 가지가 더 붙는다.

### 3-1. 재시도해도 되는 실패인지부터 구분한다

가장 먼저 걸러야 할 것은 **애초에 재시도가 의미 없는 실패**다. 기준은 1-1에서 세운 가설이다 — **"조금 뒤에 다시 보내면 결과가 달라질 수 있는가?"**

4xx 계열의 대부분은 답이 "아니다"다. 400 Bad Request는 요청의 형식이 틀렸다는 뜻이고, 401은 인증 정보가 없다는 뜻이고, 404는 그 자원이 없다는 뜻이다. **요청 자체에 결함이 있으므로 같은 요청은 100번 보내도 100번 실패한다.** 재시도는 순수한 낭비이고, 상대의 에러 로그를 3배로 오염시켜 진짜 문제를 가린다.

정리하면 이렇다.

| 실패 | 재시도 | 이유 |
|---|---|---|
| connection refused, connect timeout | 예 | 요청이 상대에 도달하지 않았다 — 부작용 없음이 확실 |
| 503 Service Unavailable | 예 | "지금은 못 받는다"는 일시적 신호 |
| 429 Too Many Requests | 예 (단 `Retry-After` 존중) | 상대가 명시적으로 물러나라고 요청 |
| 5xx 일반 (500 등) | 조건부 | 일시적 장애일 수도, 결정적 버그일 수도 — 원인 불명이므로 보수적으로 |
| 400, 401, 403, 404, 422 | 아니오 | 요청 자체의 결함 — 영원히 실패한다 |
| **read timeout** | **멱등할 때만** | **결과 불명 — 다음 절의 회색지대** |

그래서 재시도 설정은 **화이트리스트 방식**이 안전하다. "이 예외들만 재시도한다"고 명시하는 것이, "이 예외들은 재시도하지 않는다"고 빼는 것보다 낫다 — 새 예외가 생겼을 때 기본 동작이 "재시도 안 함"이 되어야 사고가 덜 난다. 2-5의 `retryExceptions` / `retryFor`가 그 화이트리스트다.

### 3-2. 회색지대 — 타임아웃은 성공인지 실패인지 알 수 없다

표의 마지막 줄이 이 문서에서 가장 조심해야 할 지점이다.

**타임아웃은 실패가 아니다. "결과를 모르는 상태"다.** 명시적인 실패 응답(500)은 "확실히 안 됐다"는 정보를 준다. 타임아웃은 아무 정보도 주지 않는다 — 요청이 도달하지 못했을 수도 있고, 도달해서 처리까지 끝났는데 응답만 못 받았을 수도 있다.

10번 문서(`10-timeout-layers-and-budget.md`)의 구분이 여기서 값을 한다. **connection timeout은 요청이 상대에 도달하기 전의 실패**이므로 부작용이 없다는 것이 확실하고, 안전하게 재시도할 수 있다. **read timeout은 요청이 이미 도달해 처리됐을 수도 있는 상태**다.

시간축으로 보면 무엇이 위험한지 정확히 보인다.

```text
[클라이언트]                                [결제 API]

  t=0      요청 전송 ────────────────────▶  요청 수신
  t=0.3s                                    카드사 승인 요청
  t=0.5s   ★ read timeout 발생!
           "실패했다"고 판단하고 소켓을 닫음
  t=0.7s                                    ★ 승인 성공 (돈이 빠졌다)
  t=0.7s                                    응답 전송 → 받을 사람이 없다
  t=1.0s   재시도 전송 ──────────────────▶  요청 수신
  t=1.7s                                    ★ 또 승인 성공 (돈이 또 빠졌다)

  클라이언트가 아는 것   : "응답을 못 받았다"
  클라이언트가 모르는 것 : "승인이 됐는지"
  결과                 : 이중 결제
```

**그래서 read timeout을 재시도하려면 그 연산이 멱등이어야 한다.** 멱등(idempotent)이란 **"같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"**이다. 조회는 본래 멱등이다. 결제·주문 생성 같은 쓰기는 본래 멱등이 아니므로, **멱등성 키**를 붙여 멱등하게 만들어야 한다.

멱등성 키는 **"이것은 새 요청이 아니라 아까 그 요청의 재전송이다"를 상대에게 알려 주는 식별자**다. 코드로 보면 차이가 명확하다.

```java
// Before: 멱등성 키 없이 재시도 — 타임아웃 한 번에 이중 결제가 난다
@Retryable(retryFor = TimeoutException.class, maxAttempts = 3)
public PaymentResult pay(Order order) {
    return paymentClient.pay(new PayRequest(order.getId(), order.getAmount()));
    // 결제사 입장에서 이 두 요청은 구분이 불가능하다.
    // "같은 금액의 서로 다른 결제 두 건"인지
    // "같은 결제 한 건의 재전송"인지 알려 주는 것이 아무것도 없다.
    // 알 수 없으면 상대는 둘 다 처리하는 수밖에 없다.
}

// After: 멱등성 키를 붙여 재전송을 상대가 식별하게 만든다
@Retryable(retryFor = TimeoutException.class, maxAttempts = 3,
        backoff = @Backoff(delay = 200, multiplier = 2, random = true))
public PaymentResult pay(Order order) {
    // ★ 키를 재시도마다 새로 만들면 안 된다.
    //   UUID.randomUUID()를 여기에 쓰면 재전송된 요청 둘이
    //   서로 다른 키를 갖게 되어 멱등성이 없는 것과 완전히 같아진다.
    //   키는 "이 논리적 연산 하나"에 고정된 값에서 뽑아야 한다.
    String idempotencyKey = "pay-" + order.getId();
    return paymentClient.pay(
            new PayRequest(order.getId(), order.getAmount()), idempotencyKey);
}
```

받는 쪽도 짝을 맞춰야 멱등이 성립한다. 유니크 제약으로 DB가 중복을 판정하게 하는 것이 핵심이다.

```sql
-- 결제사(또는 우리가 서버 역할일 때) 쪽: 키에 유니크 제약을 건다.
-- 애플리케이션의 "이미 있나?" 조회는 동시 요청 둘이 나란히 통과할 수 있지만,
-- 유니크 제약은 DB가 쓰기 시점에 원자적으로 판정한다.
CREATE UNIQUE INDEX uq_payment_idem ON payment (idempotency_key);
```

```java
// 서버 쪽 처리: INSERT를 먼저 시도해 확인과 선점을 한 번에 한다
@Transactional
public PayResponse handle(PayRequest req, String idempotencyKey) {
    int inserted = paymentRepository.insertIfAbsent(idempotencyKey, req);
    // insertIfAbsent는 ON CONFLICT (idempotency_key) DO NOTHING.
    if (inserted == 0) {
        // 이미 처리된 요청이다. ★ 반드시 성공으로 응답해야 한다.
        // 여기서 에러를 주면 클라이언트가 "실패"로 오판해 보상이나
        // 재시도를 또 태운다 — 멱등성 장치가 새 사고를 만드는 셈이다.
        return paymentRepository.findByKey(idempotencyKey).toResponse();
    }
    return approve(req);
}
```

이 "이미 처리됨 = 성공 응답" 규칙과 멱등성 키 전파의 상세는 10장 결제 문서(`10-payment-consistency/10-distributed-saga-compensation-idempotency.md`)에서 다룬다. 여기서 붙잡을 것은 하나다 — **멱등성 키 없이 쓰기 연산의 타임아웃을 재시도하는 코드는 이중 처리 버그를 예약해 둔 것이다.**

### 3-3. 재시도 예산(retry budget) — 총량에 상한을 둔다 (가산점 포인트)

`maxAttempts = 3`은 **요청 1건의 상한**일 뿐이다. 시스템 전체에서 재시도가 얼마나 일어나고 있는지에 대해서는 아무것도 통제하지 않는다.

1-2의 계산이 그 한계를 보여준다. 유입이 1,000 TPS이고 실패율이 100%로 치솟으면, 요청당 상한이 4회라는 규칙을 완벽히 지키면서도 재시도만 초당 3,000건이 발생한다. **국소 규칙으로는 전역 총량을 막을 수 없다.**

**retry budget(재시도 예산)**은 여기에 다른 축의 상한을 건다. **"전체 요청 중 재시도가 차지하는 비율이 N%를 넘으면 재시도를 하지 않는다"**는 방식이다.

```text
[retry budget 10% — 유입 1,000 TPS, 실패율 100%]

  예산 없음:  원 호출 1,000 + 재시도 3,000 = 4,000 TPS   (4.0배)

  예산 10%:   재시도 상한 = 1,000 × 10% = 100 TPS
              원 호출 1,000 + 재시도 100 = 1,100 TPS      (1.1배)
              → 초과분 2,900건의 재시도는 실행되지 않고 즉시 실패한다

  검산: 1,000 × 0.1 = 100, 1,000 + 100 = 1,100
```

구현은 보통 토큰 버킷이다. **성공한 호출마다 토큰을 적립하고, 재시도할 때마다 토큰을 소비한다.** 토큰이 없으면 재시도를 포기한다. 이 구조가 왜 우아한지 보면, **상대가 건강할 때는 성공이 많아 토큰이 넉넉하고, 상대가 아플 때는 성공이 없어 토큰이 곧 마른다.** 즉 **재시도가 필요 없을 때는 여유롭고, 위험할 때는 자동으로 꺼진다.**

이것이 횟수 상한보다 나은 점이 정확히 그 지점이다. 횟수 상한은 장애가 깊어질수록 더 열심히 재시도하지만(1-2의 표), 예산은 장애가 깊어질수록 재시도를 접는다. **대규모 장애일수록 재시도를 끄는, retry storm의 구조적 차단기**다.

이 개념은 개별 애플리케이션 코드보다 인프라 계층에서 구현된 것이 많다 — Envoy의 retry budget, gRPC의 retry throttling이 대표적이다. 애플리케이션 코드로 직접 만들면 인스턴스별 로컬 카운터가 되어 9번 문서 3-8의 "인스턴스마다 갈리는 판단" 문제를 그대로 물려받으므로, 게이트웨이나 서비스 메시 계층에 두는 편이 자연스럽다.

### 3-4. 재시도는 호출 체인에서 한 계층만

1-4의 곱셈 트리가 이 원칙의 근거다. 3 × 3 × 3 = 27이 되는 것을 막으려면 곱해질 항의 개수를 줄여야 하고, 가장 확실한 방법은 **1개로 만드는 것**이다.

그러면 어느 계층이 담당해야 하는가. 두 가지 선택지가 있다.

**실패 지점에 가장 가까운 계층**이 담당하면, 재시도가 필요한 실패를 가장 정확히 판별할 수 있다. 주문 서비스는 결제 API의 어떤 응답이 일시적 실패인지 알지만, 게이트웨이는 그것을 모른다.

**최상위 한 곳**이 담당하면, 전체 예산을 알고 있으므로 시간 관리가 정확하다. 대신 재시도할 때 하위 전체를 다시 실행하므로 낭비가 크다.

**대개 전자를 고른다.** 그리고 상위 계층들에는 명시적으로 "재시도하지 않음"을 설정한다. 여기서 실무의 함정이 하나 있다.

**라이브러리와 인프라가 기본값으로 자동 재시도를 하는 경우가 많다.** 내가 명시한 재시도 외에 숨은 재시도가 있으면 곱셈은 그대로 일어난다. 감사해야 할 곳이 이렇다.

```text
[숨은 재시도 계층 감사 목록]

  ① HTTP 클라이언트 라이브러리의 기본 재시도
  ② DB 드라이버의 연결 재시도
  ③ 메시지 프로듀서의 재전송 (브로커 응답 실패 시)
  ④ 로드밸런서·서비스 메시의 요청 재전송
  ⑤ 프론트엔드/앱의 자체 재시도
  ⑥ 사용자의 새로고침 연타  ← 사람도 재시도 계층이다
  ⑦ 실패 메시지를 다시 큐에 넣는 컨슈머 재처리 루프
```

각 계층에서 실제 시도 횟수를 지표로 노출해 두면 감사가 훨씬 쉬워진다. **"이 대상에 대한 총 시도 수 ÷ 논리적 호출 수"**를 지표로 두면 곱셈이 일어나고 있는지가 숫자로 보인다.

### 3-5. 타임아웃 예산 안에서

재시도의 최악 소요는 `(시도 하나의 타임아웃 + backoff 대기) × 시도 횟수`로 곱해진다. 이 합이 상류 타임아웃 예산을 넘으면 10번 문서 3-3의 사고 — 하류는 아직 재시도 중인데 상류는 이미 실패로 응답하는 모순 — 가 그대로 발생한다.

2-4의 설정으로 계산해 보자. 시도당 타임아웃 500ms, 재시도 3회(총 4회), full jitter backoff의 상한이 500/1,000/2,000ms다.

```text
최악 소요 = 시도 4회 × 500ms + backoff 상한의 합
          = 2,000ms + (500 + 1,000 + 2,000)
          = 2,000 + 3,500
          = 5,500ms

검산: 4 × 500 = 2,000 / 500 + 1,000 + 2,000 = 3,500 / 합 5,500
```

그런데 10번 문서 3-2에서 결제 API에 배분한 예산은 **1,200ms**였다. **5,500ms는 예산의 4.6배다** — 이 설정을 그대로 쓰면 상위가 먼저 포기하고 하위의 작업은 버려진다.

예산 1,200ms 안에서 가능한 조합을 거꾸로 계산하면 이렇게 나온다.

```text
2 × (시도 하나의 시간) + backoff ≤ 1,200ms
2 × T + 200 ≤ 1,200  →  T ≤ 500ms

가능한 설정: 재시도 1회(총 2회), 시도당 500ms, backoff 상한 200ms
검산: 500 × 2 + 200 = 1,200ms — 예산과 정확히 맞는다
```

**예산 안에서 재시도는 1회밖에 넣을 수 없다.** 3회를 넣으려면 예산을 늘리거나 시도당 타임아웃을 조여야 하고, 조이면 10번 문서 3-1의 거짓 실패가 늘어난다.

**이 계산이 "재시도 횟수는 몇 회가 적절한가"라는 질문의 진짜 답이다.** 적절한 횟수는 취향이 아니라 예산이 정한다. 그리고 예산이 좁으면 재시도를 늘리는 대신 다른 카드를 써야 한다 — fallback, 비동기 처리로의 전환, 사용자에게 명시적 재시도를 요청하는 UI.

### 3-6. 서킷 브레이커와의 관계

세 장치는 대체재가 아니라 **순서가 있는 한 세트**다. **타임아웃이 있어야 실패가 유한 시간 안에 판정되고**, 실패 판정이 있어야 **재시도와 서킷이 성립하며**(무엇을 세어 실패율을 계산할지가 정해진다), **서킷이 없으면 재시도가 이미 죽은 상대를 계속 두드린다.** 그래서 도입 순서도 타임아웃 → 재시도 → 서킷이다.

재시도 쪽에서 이 관계를 보면 이렇다. **재시도는 "일시적 실패"라는 가설 위의 장치이므로, 가설이 틀린 국면 — 지속 장애 — 에서는 스스로를 멈출 방법이 없다.** 1-3의 되먹임이 그것이고, backoff와 jitter는 그 되먹임을 늦출 뿐 끊지 못한다.

**끊는 것은 서킷의 일이다.** 서킷이 열리면 재시도할 대상 호출 자체가 차단되므로 증폭이 0으로 떨어진다.

```text
[서킷 없음]  상대가 30분간 장애
             → 30분 × 1,000 TPS × 4배 = 그동안 계속 4배 증폭

[서킷 있음]  실패율 임계 초과 후 몇 초 안에 서킷 open
             → 그 이후의 호출은 즉시 실패, 재시도 루프에 진입조차 안 함
             → 증폭이 0. 상대는 half-open 탐침 몇 건만 받는다
```

**즉 서킷 브레이커가 재시도의 상한을 실질적으로 대신한다.** 3-3의 retry budget과 목적이 같고 방식이 다르다 — budget은 전체 트래픽 대비 비율로 총량을 통제하고, 서킷은 대상별 실패율로 호출 자체를 끊는다. 둘은 서로를 대체하지 않고 층이 다르다.

배치 순서는 안쪽부터 **타임아웃 → 재시도 → 서킷**이다. 서킷이 재시도 바깥에 있어야 서킷 open 시 재시도까지 함께 멈춘다. 반대로 서킷을 재시도 안쪽에 두면 서킷이 열렸는데도 재시도 루프가 계속 돈다.

여기서 라이브러리의 현실을 알아 둘 필요가 있다. **Resilience4j의 기본 조합 순서는 이 권고와 반대로 Retry가 가장 바깥이다** — `Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( 호출 ) ) ) ) )`. 이 순서에서도 서킷이 열리면 각 시도가 즉시 `CallNotPermittedException`으로 떨어지므로 상대를 두드리지는 않지만, 두 가지를 챙겨야 한다. **`CallNotPermittedException`을 재시도 대상에서 제외**해야 재시도 루프가 헛돌지 않고, **서킷의 실패 집계 단위가 "논리적 호출"이 아니라 "시도"가 되므로** 재시도 횟수만큼 실패가 부풀려 집계되는 것을 감안해 임계치를 잡아야 한다. 순서를 바꾸려면 `*AspectOrder` 설정으로 조정한다. (서킷 설정 전체: 9번 문서 `09-circuit-breaker-state-transition-tuning.md`)

### 3-7. 상대가 준 신호를 존중한다 — `Retry-After`

마지막 하나는 태도의 문제다. **상대가 "언제 다시 오라"고 말해 줬다면 내 backoff 계산보다 그것을 우선한다.** 내 계산은 추측이고, 상대가 준 값은 사실이다.

429(Too Many Requests)와 503(Service Unavailable) 응답에는 `Retry-After` 헤더가 함께 올 수 있다. 값의 형식이 두 가지라 둘 다 처리해야 한다 — 초 단위 숫자이거나, HTTP 날짜다.

```java
private Duration retryAfterOf(HttpHeaders headers, Duration myBackoff) {
    String value = headers.getFirst(HttpHeaders.RETRY_AFTER);
    if (value == null) {
        return myBackoff;   // 헤더가 없으면 내 backoff 계산을 쓴다
    }
    try {
        // 형식 ①: 초 단위 정수 — "Retry-After: 120"
        return Duration.ofSeconds(Long.parseLong(value.trim()));
    } catch (NumberFormatException notASecondsValue) {
        // 형식 ②: HTTP 날짜 — "Retry-After: Wed, 21 Oct 2026 07:28:00 GMT"
        //   이 경우 "그 시각까지 남은 시간"으로 환산해야 한다.
        ZonedDateTime until = ZonedDateTime.parse(
                value, DateTimeFormatter.RFC_1123_DATE_TIME);
        Duration wait = Duration.between(ZonedDateTime.now(), until);
        return wait.isNegative() ? Duration.ZERO : wait;
    }
}

public PaymentResult payRespectingRetryAfter(Order order) {
    for (int attempt = 1; attempt <= 3; attempt++) {
        try {
            return paymentClient.pay(order, "pay-" + order.getId());
        } catch (TooManyRequestsException e) {
            Duration myBackoff = fullJitterBackoff(attempt);
            // ★ 상대가 준 값과 내 계산 중 "더 긴 쪽"을 쓴다.
            //   상대의 값을 무시하고 짧게 재시도하면 rate limit에 계속 걸리며
            //   상대의 차단 정책을 악화시킨다(차단 기간이 늘어나거나 IP 차단).
            //   반대로 상대의 값이 내 backoff보다 짧더라도, 상대가 그렇게
            //   말했다면 그것이 상대의 용량에 대한 최신 정보다.
            Duration wait = retryAfterOf(e.getHeaders(), myBackoff);
            if (wait.compareTo(remainingBudget()) > 0) {
                // 남은 예산보다 대기가 길면 기다릴 의미가 없다(3-5).
                // 기다렸다 재시도해도 상위가 이미 포기한 뒤가 된다.
                throw new PaymentUnavailableException(e);
            }
            sleep(wait);
        }
    }
    throw new PaymentFailedException();
}
```

이것을 일반화하면 **상대의 백프레셔 신호를 존중하는 것까지가 재시도 설계**라는 원칙이 된다. 백프레셔는 하류가 처리 못 하는 만큼을 상류에 되돌려 알려 유입 속도 자체를 늦추는 것이고, `Retry-After`는 그 신호의 HTTP 표현이다. (백프레셔 전반: 16번 문서 `16-backpressure-and-application-points.md`)

## 4. 꼬리질문 대비 포인트

### "backoff가 있는데 jitter는 왜 또 필요한가요?"

backoff는 개별 클라이언트의 재시도 빈도만 줄인다. 장애 순간에 동시에 실패한 수많은 클라이언트가 같은 backoff 스케줄을 따르면 1초 뒤, 2초 뒤 같은 시각에 일제히 재시도하는 **동기화된 파도**가 생긴다. 회복 중인 서버는 평균 부하가 아니라 순간 피크에 다시 쓰러지므로, 재시도 시각에 무작위 편차를 줘 파도를 시간 축으로 펴는 jitter가 반드시 필요하다. **"backoff는 총량, jitter는 분포"**가 핵심 문장.

숫자를 붙이면 설득력이 생긴다. 1,000개 클라이언트가 동시에 실패하고 재시도 1회차 backoff가 500ms라면, jitter가 없으면 그 1,000건이 t=0.5s 한 순간에 도착한다. full jitter로 0~500ms에 흩뿌리면 100ms 구간 5개에 나뉘어 구간당 200건이 되므로 **순간 피크가 1/5로 떨어진다.** 재시도 3회차(상한 2,000ms)라면 100ms 구간 20개에 나뉘어 1/20이 된다. 총량 4,000건은 그대로인데 피크만 줄어든다는 점이 요점이다.

jitter의 종류를 구분해 말하면 한 단계 더 나간다. **full jitter는 0~상한 균등**(무작위성이 최대, 기대 대기 = 상한/2), **equal jitter는 상한/2 + 0~상한/2**(최소 대기가 보장됨, 기대 대기 = 상한 × 3/4), **decorrelated jitter는 base ~ 직전 대기 × 3**(클라이언트 간 대기가 회차마다 더 벌어짐)이다. 기본값으로는 **full jitter를 권한다** — 흩뿌리는 폭이 가장 넓어 피크 감소가 크고, 구현이 단순하며, 평균 대기가 짧다.

### "어떤 실패는 재시도하면 안 되나요?"

두 축으로 거른다.

**(1) 일시성**: 4xx처럼 다시 보내도 결과가 같은 결정적 실패는 재시도가 낭비다. 400은 요청 형식이 틀렸다는 뜻이고 401은 인증이 없다는 뜻이므로, 같은 요청은 100번 보내도 100번 실패한다. 연결 실패·타임아웃·5xx 일부만 대상으로 한다. 그리고 설정은 **화이트리스트 방식**이 안전하다 — 새 예외가 생겼을 때 기본 동작이 "재시도 안 함"이 되어야 한다.

**(2) 멱등성**: 여기가 회색지대이고 가장 중요하다. **타임아웃은 실패가 아니라 "결과를 모르는 상태"다.** connection timeout은 요청이 상대에 도달하기 전의 실패라 재시도가 안전하지만, read timeout은 이미 처리됐을 수 있는 상태라 비멱등 요청(결제·주문 생성)에 재시도하면 중복 처리가 난다 — 멱등 키(idempotency key)를 함께 설계했을 때만 재시도할 수 있다.

멱등성 키에서 흔한 실수까지 말하면 좋다. **키를 재시도마다 새로 만들면 멱등성이 없는 것과 완전히 같다.** `UUID.randomUUID()`를 호출 지점에서 뽑으면 재전송된 요청 둘이 서로 다른 키를 갖게 된다. 키는 `orderId`처럼 **논리적 연산 하나에 고정된 값**에서 뽑아야 하고, 받는 쪽은 유니크 제약과 `ON CONFLICT DO NOTHING`으로 판정하되 **"이미 처리됨"에는 반드시 성공으로 응답**해야 한다.

### "재시도 횟수와 간격은 어떤 근거로 정하나요?"

위로는 **상류의 타임아웃 예산**이 상한이다 — `(시도 하나의 타임아웃 + backoff) × 시도 횟수`의 최악 합이 예산 안에 들어와야 한다.

**계산을 실제로 보여주면 답이 달라 보인다.** 시도당 500ms, 재시도 3회(총 4회), full jitter backoff 상한 500/1,000/2,000ms라면 최악은 `4 × 500 + (500 + 1,000 + 2,000) = 5,500ms`다. 결제 API에 배분된 예산이 1,200ms라면 이 설정은 예산의 4.6배이므로 성립하지 않는다. 예산 1,200ms 안에서는 `2 × 500 + 200 = 1,200`, 즉 **재시도 1회밖에 넣을 수 없다.**

아래로는 실패의 성격이다 — 일시적 실패는 대부분 첫 번째 재시도에서 해소되므로, 실무에서는 1~2회면 충분한 경우가 많고 횟수를 늘릴수록 성공 확률은 미미하게 오르는데 장애 시 증폭 배율만 커진다. **"많이 재시도할수록 견고하다"가 아니라 "재시도 1회의 한계 효용이 급감한다"**는 관점으로 답하면 좋다.

그리고 **적절한 횟수는 취향이 아니라 예산이 정한다**는 것으로 마무리하면 설계자의 답이 된다. 예산이 좁으면 재시도를 늘리는 대신 fallback이나 비동기 전환 같은 다른 카드를 써야 한다.

### "재시도 로직을 넣었는데도 장애가 증폭됐다면 어디를 의심하나요?" (시니어 변별 포인트)

내가 작성한 재시도 바깥의 **숨은 재시도 계층**들을 감사한다.

(1) HTTP 클라이언트·DB 드라이버·Kafka 프로듀서 등 라이브러리의 기본 자동 재시도, (2) 로드밸런서·서비스 메시의 요청 재전송, (3) 프론트엔드/앱의 재시도와 **사용자의 새로고침 연타** — 시스템 바깥의 인간도 재시도 계층이다, (4) 실패한 메시지를 다시 큐에 넣는 컨슈머 재처리 루프.

**이들이 겹치면 코드상 3회가 실제로는 수십 배가 되는 이유를 계산으로 설명할 수 있어야 한다.** 상위 계층의 재시도는 자기 몫만 다시 하는 것이 아니라 **하위 전체를 통째로 다시 실행**하므로, 계층 셋이 각자 총 3회 시도하면 최말단은 3 + 3 + 3 = 9가 아니라 **3 × 3 × 3 = 27건**을 받는다. 계층당 재시도 3회(총 4회)라면 4³ = 64건이다. **계층당 시도를 하나 늘리는 것보다 재시도하는 계층을 하나 늘리는 것이 훨씬 위험하다** — 전자는 배율을 더하고 후자는 곱한다.

그리고 복구 국면도 본다 — 장애 중 쌓인 재시도 대기분이 복구 직후 한꺼번에 몰리는 2차 파도까지 관측(재시도 비율 지표, 대상별 재시도 카운트)으로 확인해야 "재시도를 설계했다"고 말할 수 있다. 지표로는 **"대상별 총 시도 수 ÷ 논리적 호출 수"**를 두면 곱셈이 일어나고 있는지가 숫자로 드러난다.

여기에 구조적 처방까지 붙이면 좋다. 횟수 상한은 요청 1건의 국소 규칙이라 전역 총량을 통제하지 못하므로, **retry budget**("전체 요청 중 재시도 비율 최대 10%")과 **서킷 브레이커**를 함께 둔다. 서킷이 열리면 재시도할 호출 자체가 차단되어 증폭이 0이 되므로, **서킷이 재시도의 상한을 실질적으로 대신한다.**

### "429(Too Many Requests)를 받았을 때의 재시도는 어떻게 다르게 처리하나요?" (가산점 포인트)

429는 상대가 "지금 과부하이니 물러나라"고 **명시적으로 신호**한 것이므로, 내 backoff 스케줄보다 상대가 준 `Retry-After` 헤더를 우선한다. **내 backoff는 추측이고, 상대가 준 값은 사실이다.**

이를 무시하고 자체 backoff로 재시도하면 rate limit에 계속 걸리며 상대의 차단 정책을 악화시킬 수 있다 — 차단 기간이 늘어나거나 IP 단위 차단으로 번지는 경우가 있다.

구현에서 챙길 것을 덧붙이면 좋다. **`Retry-After`는 초 단위 숫자와 HTTP 날짜 두 형식이 모두 가능하므로 둘 다 파싱해야 한다.** 그리고 상대가 준 대기 시간이 **남은 타임아웃 예산보다 길면 기다릴 의미가 없다** — 기다렸다 재시도해도 상류가 이미 포기한 뒤이므로, 그때는 즉시 실패로 전환하는 것이 옳다. 503에도 같은 헤더가 올 수 있다는 점까지 알면 더 좋다.

상대의 backpressure 신호를 존중하는 것까지가 재시도 설계다(backpressure 문서 16-backpressure-and-application-points.md 참고).

## 한 줄 요약

재시도는 "실패가 일시적"이라는 가설 위의 장치라서, 지속 장애 국면에는 실패율에 비례해 부하를 곱하는 증폭기가 되고(실패율 50%면 1.88배, 100%면 4배, 계층 셋이 각자 총 3회면 3×3×3 = 27배의 곱셈 폭발) 복구까지 막는 retry storm을 만든다 — exponential backoff로 빈도를 줄이고 full jitter로 동시성을 흩뿌려 순간 피크를 1/5~1/20로 낮추되(backoff는 총량, jitter는 분포), 재시도 가능한 실패의 구분(4xx는 영원히 실패하므로 제외, **타임아웃은 성공·실패를 알 수 없는 상태라 멱등성 키가 있어야만 재시도 가능**), retry budget으로 전역 총량 상한, 재시도는 한 계층만이라는 원칙, `(타임아웃 + backoff) × 시도 횟수`가 상류 예산에 들어오는지의 검산, 그리고 지속 장애에서 재시도 자체를 끊어 주는 서킷과의 결합까지 갖춰야 "장애를 키우지 않는 재시도"가 된다.
