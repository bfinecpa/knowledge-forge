# Graceful Degradation — 추천이 죽어도 메인 페이지는 뜬다: 부분 기능 저하 설계

> 핵심 관전 포인트: **장애를 정상/다운의 이분법이 아니라 스펙트럼으로
> 다루는 설계다. 전제는 기능의 중요도 분류 — "이 기능이 죽으면 서비스가
> 죽은 것인가"를 기준으로 핵심(조회·결제)과 비핵심(추천·배지·리뷰 수)을
> 평상시에 합의해 둔다. 그다음 비핵심 의존성의 실패가 핵심 경로를
> 침범하지 못하게 격리하고(짧은 타임아웃 + 서킷), 실패했을 때 무엇을
> 대신 보여줄지 fallback 체인을 미리 설계한다 — 추천이 죽으면 캐시된
> 이전 추천 → 비개인화 인기순 → 섹션 숨김 순서로, 마지막 단계는
> 절대 실패할 수 없는 것이어야 한다. 그리고 저하 상태는 조용하면
> 안 된다 — fallback 동작 비율을 지표·알림으로 노출해야 "겉으로
> 멀쩡한 채 며칠간 저하 운행"을 막는다.**

---

## 0. 질문 + 의도

**질문**: "갑작스러운 장애 상황에서 \"부분 기능 저하(graceful degradation)\"를 어떻게 설계하나요? 예를 들어 추천 시스템이 죽었을 때 서비스는 어떻게 동작해야 하나요?"

**출제 의도**: "추천이 죽으면 인기순이라도 보여준다"처럼 기능별
중요도를 나누고 비핵심의 실패를 격리하는 설계는, 장애 시 "전체 다운"과
"일부 기능 저하"의 차이를 만든다. 장애를 이분법(정상/다운)이 아닌
스펙트럼으로 사고하는지 확인하는 질문이다.

## 1. 전제 — 기능 중요도 분류는 기술이 아니라 비즈니스 결정

graceful degradation의 첫 단추는 코드가 아니라 **분류**다.
서비스의 기능을 "이것이 죽으면 서비스가 죽은 것인가"라는 질문으로
나눈다. 웹툰 서비스라면:

| 등급 | 기능 | 죽었을 때 |
|---|---|---|
| 핵심 | 회차 조회(이미지 서빙), 로그인, 결제 | 서비스 장애 — 모든 수단으로 지킨다 |
| 중요 | 이어보기, 구매 내역 | 저하 시 사용자 불편 크지만 대체 가능 |
| 비핵심 | 개인화 추천, 조회수·좋아요 표시, 배지, 이벤트 배너 | 없어도 핵심 여정은 완주 가능 |

이 분류가 중요한 이유는 두 가지다.

- **격리 설계의 근거가 된다**: 비핵심 의존성에는 공격적으로 짧은
  타임아웃과 민감한 서킷을 걸 수 있다 — "추천은 200ms 안에 안 오면
  버린다"는 결정은 추천이 비핵심이라는 합의가 있어야 가능하다.
- **장애 중에는 이 결정을 내릴 수 없다**: 장애 상황은 분류를 토론할
  시간이 아니라 분류에 따라 행동할 시간이다. 어떤 기능을 포기할지는
  개발자가 임의로 정할 수 없는 **비즈니스 우선순위**이므로, 평상시에
  기획·운영과 합의해 문서화해 둬야 한다.

과부하 시 "누구의 요청부터 버릴 것인가"를 다루는 load shedding
(21-load-shedding-priority-and-location.md)이 **수량**의 우선순위라면,
graceful degradation은 의존성 장애 시 "어떤 기능을 낮출 것인가"라는
**품질**의 우선순위다 — 같은 분류 작업을 공유하는 상보적 설계다.

## 2. 사례로 보는 설계 — 추천 시스템이 죽었을 때

### Before: 비핵심이 핵심을 인질로 잡는 구조

```java
// Before: 메인 페이지가 추천 API를 동기 호출, 실패 처리 없음
public MainPageResponse getMainPage(Long userId) {
    List<Webtoon> recommended = recommendClient.recommend(userId); // 추천 장애 = 여기서 예외/무한 대기
    List<Webtoon> ranking = rankingService.getTop(20);
    return new MainPageResponse(recommended, ranking);
}
```

추천 API가 죽거나 느려지면 **메인 페이지 전체**가 에러가 되거나
추천의 응답 시간만큼 느려진다. 비핵심 기능(추천)이 핵심 여정(메인
진입)을 인질로 잡은 구조 — 장애의 크기가 기능의 중요도와 무관하게
전파된다.

### After: 격리 + fallback 체인

```java
// After: 짧은 타임아웃 + 서킷으로 격리, 실패 시 fallback 체인으로 대체
@CircuitBreaker(name = "recommend", fallbackMethod = "recommendFallback")
@TimeLimiter(name = "recommend")   // 비핵심이므로 공격적으로 짧게 (예: 300ms)
public CompletableFuture<List<Webtoon>> getRecommendations(Long userId) {
    return recommendClient.recommendAsync(userId);
}

private CompletableFuture<List<Webtoon>> recommendFallback(Long userId, Throwable t) {
    // 1순위: 캐시에 남아 있는 이 사용자의 직전 추천 (약간 오래됐지만 개인화 유지)
    return cachedRecommendation(userId)
            // 2순위: 사전 계산된 비개인화 인기순 (전원에게 동일, 정적 캐시라 실패 확률 극히 낮음)
            .orElseGet(() -> CompletableFuture.completedFuture(precomputedPopularList()));
}
```

설계 포인트를 풀어 쓰면:

- **타임아웃은 중요도에 반비례**: 핵심 호출은 성공을 위해 기다려줄
  가치가 있지만, 비핵심 호출은 빨리 포기하는 것이 낫다. "추천을 2초
  기다려서 받는 것"보다 "300ms에 포기하고 인기순을 내주는 것"이 메인
  진입 경험에는 낫다.
- **fallback 체인은 계단식으로, 마지막은 실패 불가능한 것**: 캐시된
  이전 추천(신선도만 희생) → 비개인화 인기순(개인화 희생) → 섹션 자체
  숨김(기능 희생). 단계가 내려갈수록 품질은 낮아지고 실패 확률도
  낮아져야 한다. 최종 단계는 정적 데이터나 "숨김"처럼 **의존성이 없어
  실패할 수 없는 것**이어야 한다 — fallback도 외부 호출이면 fallback의
  fallback이 또 필요해진다.
- **fallback은 원 경로보다 싼 경로여야 한다 (가산점 포인트)**:
  fallback이 "DB에서 인기순 실시간 쿼리"라면, 추천 장애 순간 메인
  트래픽 전체가 DB로 직행해 **추천 장애가 DB 장애로 전이**된다.
  fallback 대상은 사전 계산돼 캐시에 올라간 정적 결과여야 한다.
  fallback 설계 리뷰에서 "이 대체 경로는 전체 트래픽이 몰려도
  버티는가"를 반드시 물어야 한다.
- **UI까지가 계약이다**: 서버가 빈 추천/대체 추천을 내려줄 때 클라이언트가
  그 섹션을 자연스럽게 처리(대체 렌더링 또는 숨김)하도록 응답 스키마와
  프론트 동작을 함께 설계한다. 서버만 우아하게 저하해도 앱이
  NullPointerException으로 죽으면 의미가 없다.

## 3. 저하를 "운영"한다 — 자동 저하, 수동 스위치, 그리고 관측

### 자동 저하와 수동 저하

서킷+fallback은 **자동 저하**다 — 장애를 감지해 사람 개입 없이 저하
모드로 전환한다. 실무에서는 **수동 스위치(kill switch / feature flag)**
가 이를 보완한다: 운영자가 "추천 기능 끄기", "이벤트 배너 끄기"를
설정 변경만으로(배포 없이) 실행할 수 있는 장치다. 자동 감지가 애매한
상황(추천이 죽진 않았지만 이상한 결과를 반환, 전사 부하 급증으로
비핵심 기능을 선제적으로 내려야 하는 상황)에서 사람의 판단으로 저하를
발동하는 수단이 된다.

### 저하 상태는 조용하면 안 된다

fallback이 잘 설계될수록 위험한 역설이 있다 — **겉으로 멀쩡해
보인다**는 것이다. 추천이 죽어도 인기순이 나가니 에러율 지표는
깨끗하고, 알림이 없으면 저하 운행을 며칠씩 모를 수 있다(그동안 개인화
추천이 만들던 매출은 조용히 빠진다). 그래서:

- **fallback 동작 비율을 지표로** 노출한다(전체 응답 중 대체 응답
  비율). baseline을 넘으면 알림.
- 서킷 open 이벤트는 그 자체로 장애 알림과 연동한다
  (09-circuit-breaker-state-transition-tuning.md에서 다룬 원칙).

### 안 써본 fallback은 동작하지 않는다

fallback 경로는 평상시에 실행되지 않는 코드다 — 정작 장애 때 처음
실행되면서 그 자체의 버그(직렬화 오류, 비어 있는 캐시, 권한 문제)로
실패하는 일이 흔하다. 장애 주입 테스트(추천 API를 의도적으로
차단해보는 훈련)로 fallback 경로를 **주기적으로 실제 실행**해봐야
장애 때 믿을 수 있다.

## 4. 꼬리질문 대비 포인트

### "fallback으로 내려줄 인기순 데이터는 어디서 가져오나요? fallback 자체가 부하가 되지는 않나요?"

핵심을 정확히 짚은 질문이다. fallback이 실시간 DB 집계 쿼리라면 추천
장애 순간 전체 트래픽이 DB를 때려 장애가 전이된다. 그래서 fallback
대상은 배치/스트림으로 **사전 계산해 캐시(로컬 캐시 포함)에 올려둔
정적 결과**여야 하고, "전체 트래픽이 fallback으로 몰려도 버티는가"가
fallback 설계의 검수 기준이다. 원 경로보다 fallback이 항상 싸야 한다.

### "결제처럼 대체 불가능한 핵심 기능이 죽으면 graceful degradation이 가능한가요?"

대체는 불가능해도 **저하의 여지**는 있다. (1) 결제 승인은 못 해도
주문을 "결제 대기" 상태로 접수해 큐에 쌓아두고 복구 후 처리한다 —
기능을 "지금 완료"에서 "나중에 완료"로 낮추는 것. (2) 쓰기 계열이
죽었을 때 조회는 살리는 **읽기 전용 모드**도 부분 저하다. (3) 그마저
안 되면 정확한 안내(점검 페이지, 예상 복구 시간)로 실패를 우아하게
전달하는 것까지가 degradation의 범위다. "핵심이라 저하가 불가능하다"가
아니라 "핵심은 저하의 폭이 좁을 뿐"이라고 답하면 좋다.

### "load shedding과는 어떻게 다른가요?"

축이 다르다. load shedding은 **내가 과부하**일 때 요청 일부를 버려
나머지를 지키는 것 — 수량의 문제이고 주어는 요청이다. graceful
degradation은 **의존성이 장애**일 때 기능의 품질을 낮춰 여정을 지키는
것 — 품질의 문제이고 주어는 기능이다. 다만 둘 다 "무엇이 덜
중요한가"라는 동일한 우선순위 분류에서 출발하므로, 평상시의 기능
중요도 합의가 두 설계의 공통 기반이 된다.

### "저하 모드로 전환됐는지 사용자에게 알려야 하나요?" (가산점 포인트)

기능에 따라 다르다. 추천 → 인기순 대체처럼 사용자가 차이를 거의
못 느끼는 저하는 굳이 노출하지 않는 것이 일반적이다. 반면 "결제 대기로
접수됨", "일시적으로 최신 조회수가 반영되지 않습니다"처럼 **사용자의
기대와 실제가 어긋날 수 있는 저하**는 명시해야 문의 폭주와 신뢰 손상을
막는다. 기준은 "사용자가 나중에 속았다고 느낄 수 있는가"다.

### "graceful degradation을 조직 차원에서 준비한다면 무엇부터 하시겠어요?" (시니어 변별 포인트)

코드보다 앞서는 세 가지를 말한다. (1) **기능 중요도 분류의 사전
합의** — 장애 중에는 못 정하므로 기획·운영과 평시에 등급표를 만들고
유지한다. (2) **fallback 경로의 정기 검증** — 장애 주입 훈련으로
안 쓰던 코드가 실제로 동작하는지, fallback이 부하를 견디는지 확인한다.
훈련 없는 fallback은 문서에만 있는 기능이다. (3) **저하 상태의
관측성** — fallback 비율 지표, 서킷 open 알림, kill switch 현황판.
"저하 설계의 완성은 코드가 아니라, 지금 서비스가 몇 %짜리로 돌고
있는지 아는 것"이라고 답하면 운영 경험이 드러난다.

## 한 줄 요약

graceful degradation은 기능을 핵심/비핵심으로 분류(비즈니스 결정)해
비핵심 의존성의 실패를 짧은 타임아웃과 서킷으로 격리하고, 실패 시
캐시된 결과 → 사전 계산된 인기순 → 섹션 숨김처럼 품질을 계단식으로
낮추는 fallback 체인(마지막은 실패 불가능한 것, 항상 원 경로보다 싸게)
을 미리 설계·훈련해 두는 것이다 — 장애를 정상/다운이 아닌 스펙트럼으로
다루되, 저하 상태는 반드시 지표와 알림으로 시끄럽게 만들어야 한다.
