# Graceful Degradation — 추천이 죽어도 메인 페이지는 뜬다: 부분 기능 저하 설계

> 핵심 관전 포인트: **장애를 정상/다운의 이분법이 아니라 스펙트럼으로 다루는 설계다. 전제는 기능의 중요도 분류 — "이 기능이 죽으면 서비스가 죽은 것인가"를 기준으로 핵심(조회·결제)과 비핵심(추천·배지·리뷰 수)을 **평상시에** 합의해 둔다. 장애 중에는 이 토론을 할 시간이 없기 때문이다. 그다음 비핵심 의존성의 실패가 핵심 경로를 침범하지 못하게 격리하고(짧은 타임아웃 + 서킷), 실패했을 때 무엇을 대신 보여줄지 fallback 체인을 미리 설계한다 — 추천이 죽으면 캐시된 이전 추천 → 비개인화 인기순 → 섹션 숨김 순서로, 뒤로 갈수록 신선도는 떨어지고 실패 확률도 낮아져야 하며 **마지막 단계는 외부 의존이 0이어서 실패할 수 없는 것**이어야 한다. 여기서 가장 자주 밟는 함정이 fallback 경로의 부하다 — fallback은 평상시 트래픽의 0%를 받다가 장애 순간 100%를 받으므로, 실시간 DB 쿼리를 fallback으로 두면 추천 장애가 DB 장애로 전이된다. 그리고 저하 상태는 조용하면 안 된다 — fallback이 잘 동작할수록 에러율 지표는 깨끗해지므로, fallback 동작 비율을 지표·알림으로 노출하지 않으면 "겉으로 멀쩡한 채 며칠간 저하 운행"이 된다.**

---

## 0. 질문 + 의도

**질문**: "갑작스러운 장애 상황에서 \"부분 기능 저하(graceful degradation)\"를 어떻게 설계하나요? 예를 들어 추천 시스템이 죽었을 때 서비스는 어떻게 동작해야 하나요?"

**출제 의도**: "추천이 죽으면 인기순이라도 보여준다"처럼 기능별 중요도를 나누고 비핵심의 실패를 격리하는 설계는, 장애 시 "전체 다운"과 "일부 기능 저하"의 차이를 만든다. 장애를 이분법(정상/다운)이 아닌 스펙트럼으로 사고하는지 확인하는 질문이다.

## 1. 무엇을 하는 설계인가 — 그리고 왜 코드보다 분류가 먼저인가

### 1-1. 전제 지식 — 장애에는 중간 상태가 있다

주니어가 장애를 처음 겪을 때 갖는 심상 모델은 **켜짐/꺼짐 두 가지**다. 서비스가 되거나 안 되거나. 그런데 실제 장애의 대부분은 그 사이에 있다.

추천 API가 죽었다고 해서 웹툰을 볼 수 없어야 할 이유는 없다. 조회수 집계가 멈췄다고 해서 결제가 막혀야 할 이유도 없다. 그런데 **아무 설계를 하지 않으면 실제로 그렇게 된다** — 메인 페이지가 추천 API를 동기로 호출하고 있으면, 추천이 죽는 순간 메인 페이지도 죽는다.

즉 "일부만 고장 났는데 전체가 멈추는 것"은 자연 현상이 아니라 **설계의 부재**다. 장애의 크기가 고장 난 기능의 중요도와 무관하게 전파되는 구조를 우리가 만들어 둔 결과다.

```
[설계가 없을 때]                    [설계가 있을 때]

추천 API 장애                        추천 API 장애
    │                                    │
    ▼                                    ▼
메인 페이지 응답 불가                 추천 섹션만 인기순으로 대체
    │                                    │
    ▼                                    ▼
사용자: 서비스가 죽었다               사용자: 추천이 좀 이상한데?
```

오른쪽으로 가기 위한 설계가 graceful degradation이다.

### 1-2. 용어 — 왜 'graceful'인가

**graceful degradation**은 "장애를 전면 중단이 아니라 기능과 품질을 단계적으로 낮추는 방식으로 흡수하는 설계"다. 한국어로는 보통 **부분 기능 저하**로 옮긴다.

`degradation`(저하)은 이해하기 쉽지만 `graceful`(우아한)이 왜 붙는지는 번역만으로는 알 수 없다. 이 단어가 가리키는 것은 **떨어지는 방식**이다. 성능과 기능이 절벽처럼 0으로 떨어지는 것이 아니라 계단처럼 한 칸씩 내려간다는 뜻이다.

```
[급작스러운 실패 — cliff]        [우아한 저하 — graceful]

품질                              품질
100% ─────┐                      100% ────┐
          │                                └──┐ 캐시된 추천
          │                                   └──┐ 비개인화 인기순
          │                                      └──┐ 섹션 숨김
  0%      └──────                    0%             └──────
       장애 발생                          장애 발생
```

**엘리베이터와 에스컬레이터**의 차이로 생각하면 감이 온다. 엘리베이터가 고장 나면 탈 수 없다 — 기능이 0이 된다. 에스컬레이터가 고장 나면 **계단이 된다** — 느리고 불편하지만 목적지에는 도달한다. graceful degradation은 모든 기능을 에스컬레이터로 만들려는 시도다.

### 1-3. load shedding과 무엇이 다른가 — 축이 다르다

이 셋은 실무에서 늘 함께 나오고 늘 헷갈린다. 21번 문서(load shedding)와 16번 문서(백프레셔)가 이미 앞의 세 장치를 같은 기준으로 갈라 놓았으므로, 거기에 degradation을 한 줄 더해 보면 자리가 분명해진다.

| | 언제 켜지나 | 무엇을 기준으로 판단하나 | 무엇을 대상으로 하나 | 초과분을 어떻게 하나 |
|---|---|---|---|---|
| Rate limiting | 항상 (평상시에도) | 사전에 정해진 한도 | 호출자별 | 거절 (429) |
| Load shedding | 과부하일 때만 | 실시간 부하 지표 | 우선순위가 낮은 요청 | 거절 (503) |
| 백프레셔 | 항상 (경계마다) | 하류의 실제 처리 속도 | 상류의 유입 속도 자체 | 늦춤 (유계 큐가 차면 거절) |
| **Graceful degradation** | **의존성이 장애일 때** | **그 의존성의 실패·지연** | **기능(응답의 일부)** | **품질을 낮춰 응답은 완성 (200)** |

가장 중요한 차이는 마지막 열이다. **앞의 셋은 요청을 처리하지 않기로 결정한다. degradation은 요청을 처리하되 내용의 품질을 낮춘다.**

바꿔 말하면 이렇다. shedding에서 버려진 사용자는 **에러를 받는다**. degradation에서 저하된 사용자는 **200 OK를 받는데 그 안의 추천이 개인화가 아닐 뿐**이다. 주어도 다르다 — shedding의 주어는 요청이고(누구의 요청을 버릴 것인가), degradation의 주어는 기능이다(어떤 기능을 낮출 것인가).

다만 **출발점은 같다.** 둘 다 "무엇이 덜 중요한가"라는 분류에서 시작한다. shedding은 그 분류를 요청에 적용하고 degradation은 기능에 적용할 뿐이다. 그래서 평상시에 한 번 해 두는 중요도 합의가 두 설계의 공통 기반이 된다.

18번 문서에서 본 방어 계층 순서에서 degradation이 가장 마지막(⑥)에 있는 이유도 여기서 나온다. 앞의 다섯 벽(타임아웃 → 재시도 제한 → 서킷 → bulkhead → shedding)은 **자원을 지키는** 장치이고, degradation은 그것들이 만든 실패와 거절을 **사용자에게 보여줄 응답으로 마무리하는** 장치다. degradation 없이 shedding만 넣으면 사용자에게 에러만 늘려 주는 일이 된다.

### 1-4. 기능 중요도 분류 — 기술이 아니라 비즈니스 결정

graceful degradation의 첫 단추는 코드가 아니라 **분류**다. 서비스의 기능을 "이것이 죽으면 서비스가 죽은 것인가"라는 질문으로 나눈다. 웹툰 서비스라면 이런 표가 된다.

| 등급 | 기능 | 죽었을 때 |
|---|---|---|
| 핵심 | 회차 조회(이미지 서빙), 로그인, 결제 | 서비스 장애 — 모든 수단으로 지킨다 |
| 중요 | 이어보기, 구매 내역 | 저하 시 사용자 불편 크지만 대체 가능 |
| 비핵심 | 개인화 추천, 조회수·좋아요 표시, 배지, 이벤트 배너 | 없어도 핵심 여정은 완주 가능 |

문제는 이 표를 **어떻게 합의하느냐**다. "중요도를 정한다"는 말은 쉽지만 실제 회의에서는 모든 팀이 자기 기능을 핵심이라고 주장한다. 추천 팀에게 추천은 매출 지표가 걸린 핵심이고, 이벤트 팀에게 배너는 캠페인 성과가 걸린 핵심이다. 그래서 판정에 쓸 질문을 먼저 정해 두어야 한다.

- **이 기능이 없으면 사용자가 서비스에 온 목적을 달성할 수 없는가.** 웹툰을 보러 온 사용자는 추천이 없어도 검색과 인기순으로 목적을 달성한다. 회차 이미지가 없으면 달성하지 못한다.
- **돈이 직접 움직이는가.** 결제·정산은 저하시킬 대상이 아니다.
- **법·계약상 필수인가.** 연령 확인, 이용권 만료 처리 같은 것은 편의 기능이 아니다.
- **틀린 값을 보여주는 것이 안 보여주는 것보다 나쁜가.** 조회수는 조금 늦어도 되지만 잔액은 그렇지 않다.

그리고 절차적인 장치가 하나 더 필요하다. **등급의 개수를 제한하고 상위 등급에 정원을 두는 것**이다. 등급이 다섯 개로 늘어나면 분류가 아니라 서열 다툼이 되고, "핵심"에 정원이 없으면 결국 모든 기능이 핵심이 된다. 셋 정도로 제한하고 핵심 등급의 개수를 명시적으로 세는 것만으로 논의가 현실적이 된다.

이 분류가 중요한 이유는 두 가지다.

**첫째, 격리 설계의 근거가 된다.** 비핵심 의존성에는 공격적으로 짧은 타임아웃과 민감한 서킷을 걸 수 있다 — "추천은 300ms 안에 안 오면 버린다"는 결정은 추천이 비핵심이라는 합의가 있어야 가능하다. 합의가 없으면 개발자는 그 값을 정할 권한이 없고, 결국 아무도 타임아웃을 안 걸거나 "일단 넉넉하게" 3초를 걸어 둔다.

**둘째, 장애 중에는 이 결정을 내릴 수 없다.** 장애 상황은 분류를 토론할 시간이 아니라 분류에 따라 행동할 시간이다. 새벽 3시에 "추천을 꺼도 되나요?"를 물을 사람을 찾는 것이 장애 대응이 되어서는 안 된다. 그래서 결과물은 코드가 아니라 **문서와 대시보드**에 있어야 하고, 당직자가 볼 수 있는 위치에 있어야 한다.

## 2. 사례로 보는 설계 — 추천 시스템이 죽었을 때

### 2-1. Before — 비핵심이 핵심을 인질로 잡는 구조

```java
// Before: 메인 페이지가 추천 API를 동기 호출, 실패 처리 없음
public MainPageResponse getMainPage(Long userId) {
    // 이 한 줄이 메인 페이지의 가용성을 추천 서비스의 가용성에 묶는다.
    // 추천이 죽으면 예외가 그대로 올라가고, 추천이 느려지면
    // 메인 페이지 응답 시간이 추천 응답 시간만큼 길어진다.
    List<Webtoon> recommended = recommendClient.recommend(userId);
    List<Webtoon> ranking = rankingService.getTop(20);
    return new MainPageResponse(recommended, ranking);
}
```

이 코드의 진짜 결함은 예외 처리가 없다는 것이 아니다. **가용성이 곱셈으로 계산되는 구조**를 만들었다는 것이다.

메인 페이지의 가용성은 자기 가용성 × 추천의 가용성이 된다. 추천이 99.9%라면 메인 페이지는 그보다 낮을 수밖에 없다. 의존성을 하나 더 동기로 붙이면 또 곱해진다. 비핵심 기능을 열 개 붙이면 각각 99.9%여도 전체는 99%로 떨어진다.

```
메인 페이지 가용성 = 자기 × 추천 × 배지 × 조회수 × 이벤트배너 × ...
                    각 99.9%를 10개 곱하면 -> 0.999^10 = 99.0%
```

그리고 더 나쁜 것은 **느려질 때**다. 죽는 것은 예외로 즉시 끝나지만 느려지는 것은 스레드를 붙잡는다 — 18번 문서에서 본 cascading failure의 입구가 정확히 이 지점이다.

### 2-2. 격리 — 타임아웃은 중요도에 반비례한다

```java
// After: 짧은 타임아웃 + 서킷으로 격리, 실패 시 fallback 체인으로 대체
@CircuitBreaker(name = "recommend", fallbackMethod = "recommendFallback")
@TimeLimiter(name = "recommend")   // 비핵심이므로 공격적으로 짧게 (예: 300ms)
public CompletableFuture<List<Webtoon>> getRecommendations(Long userId) {
    return recommendClient.recommendAsync(userId);
}

private CompletableFuture<List<Webtoon>> recommendFallback(Long userId, Throwable t) {
    // fallback이 호출됐다는 사실 자체를 지표로 남긴다.
    // 이것이 없으면 저하 운행을 아무도 모른다 (3-2 참고).
    degradationMetrics.count("recommend", t);
    // 1순위: 캐시에 남아 있는 이 사용자의 직전 추천 (신선도만 희생, 개인화 유지)
    return cachedRecommendation(userId)
            // 2순위: 사전 계산된 비개인화 인기순 (개인화 희생, 외부 호출 없음)
            .orElseGet(() -> CompletableFuture.completedFuture(precomputedPopularList()));
}
```

여기서 타임아웃 값을 정하는 원칙이 하나 나온다. **타임아웃은 기능의 중요도에 반비례한다.**

핵심 호출은 성공을 위해 기다려 줄 가치가 있다. 결제 승인을 300ms에 포기하면 팔 수 있는 물건을 못 파는 것이다. 반대로 비핵심 호출은 **빨리 포기하는 것이 이득**이다. "추천을 2초 기다려서 받는 것"보다 "300ms에 포기하고 인기순을 내주는 것"이 메인 진입 경험에는 낫다 — 사용자는 개인화보다 페이지가 뜨는 속도를 먼저 느낀다.

이 값의 상한을 정하는 근거는 10번 문서의 타임아웃 예산이다. 메인 페이지 전체 예산이 1초이고 그중 핵심 조회에 600ms가 필요하다면, 비핵심 호출 전체가 나눠 쓸 수 있는 시간은 나머지뿐이다. 비핵심 호출 셋을 병렬로 부른다면 각각 300ms를 줘도 되지만, 순차로 부른다면 100ms씩밖에 못 준다. **비핵심 의존성은 가능하면 병렬로 부르고 각각에 개별 타임아웃을 준다**는 결론이 여기서 나온다.

```java
// 비핵심 셋을 병렬로 호출하고, 각자 실패해도 나머지는 그대로 조립된다
public MainPageResponse getMainPage(Long userId) {
    // 핵심: 실패하면 메인 페이지도 실패해야 한다 (저하 대상이 아니다)
    List<Webtoon> ranking = rankingService.getTop(20);

    // 비핵심: 각자 독립적으로 시도하고, 실패는 각자 흡수한다
    var recommended = supplyAsync(() -> recommendClient.recommend(userId), nonCriticalPool)
            .completeOnTimeout(null, 300, MILLISECONDS)   // 시간 초과도 "없음"으로 취급
            .exceptionally(t -> { degradationMetrics.count("recommend", t); return null; });
    var badges = supplyAsync(() -> badgeClient.of(userId), nonCriticalPool)
            .completeOnTimeout(null, 200, MILLISECONDS)
            .exceptionally(t -> { degradationMetrics.count("badge", t); return null; });

    // join 시점에 이미 null 또는 값이 확정돼 있으므로 여기서 더 기다리지 않는다
    return new MainPageResponse(
            fallbackIfNull(recommended.join()),   // null이면 fallback 체인으로
            ranking,
            badges.join());                       // null이면 클라이언트가 배지를 안 그린다
}
```

`nonCriticalPool`을 따로 두는 이유는 18번 문서의 bulkhead다. 비핵심 호출이 톰캣 워커 스레드를 쓰면, 아무리 타임아웃이 짧아도 그 300ms 동안은 톰캣 스레드를 점유한다. 전용 풀로 옮기면 최악의 경우에도 비핵심 기능이 잡을 수 있는 자원의 상한이 구조적으로 정해진다.

### 2-3. fallback 체인 — 설계 규칙은 하나다

fallback을 여러 단계로 두는 것은 예시가 아니라 규칙이 있다. **뒤로 갈수록 품질은 낮아지고 실패 확률도 낮아져야 한다.**

| 단계 | 무엇을 주나 | 무엇을 희생하나 | 무엇에 의존하나 |
|---|---|---|---|
| 1 | 캐시에 남은 이 사용자의 직전 추천 | 신선도 | 캐시 (실패 가능) |
| 2 | 사전 계산된 비개인화 인기순 | 개인화 | 로컬 메모리 / 정적 파일 |
| 3 | 섹션 자체를 숨김 | 기능 | 없음 |

여기서 가장 중요한 규칙은 마지막 줄이다. **마지막 단계는 외부 의존이 0이어야 한다.**

이유는 단순하다. fallback도 실패할 수 있기 때문이다. fallback이 외부 호출이면 그 fallback의 fallback이 또 필요해지고, 그 연쇄는 어딘가에서 끝나야 한다. 끝낼 수 있는 유일한 방법은 **의존성이 없는 답**을 마지막에 두는 것이다 — 코드에 박힌 정적 목록, 섹션을 그리지 않는 것, 또는 클라이언트가 이미 들고 있는 값.

그래서 **"캐시된 이전 추천"은 마지막 단계가 될 수 없다.** 캐시도 죽을 수 있고, 무엇보다 캐시에 그 사용자의 값이 없을 수 있다(신규 사용자, 캐시 만료, 캐시 재시작). 실무에서 fallback이 실패하는 가장 흔한 이유가 이것이다 — "캐시된 값을 쓰면 되지"라고 설계했는데 장애 순간 캐시 적중률이 30%였던 경우.

### 2-4. fallback 자체가 부하가 되는 문제 — 이 절이 가장 자주 밟는 함정이다

fallback 설계에서 제일 놓치기 쉬운 사실은 이것이다. **fallback 경로는 평상시 트래픽의 0%를 받다가 장애 순간 100%를 받는다.**

평상시에 fallback은 실행되지 않는다. 그래서 부하 테스트에도 안 잡히고, 리뷰에서도 "예외 상황 코드"로 가볍게 넘어간다. 그런데 추천이 죽는 순간 전체 메인 페이지 트래픽이 그 경로로 쏟아진다.

fallback을 "DB에서 인기순을 실시간 집계"로 만들었다면 어떻게 되는지 숫자로 따라가 보자. 17번 문서의 `L = λW`를 그대로 쓴다.

```
메인 페이지 유입 λ = 3,000 TPS
fallback 인기순 쿼리 소요 W = 30ms = 0.03초

fallback 경로가 필요로 하는 동시 DB 커넥션
  L = λ × W = 3,000 × 0.03 = 90개

앱 인스턴스 5대 × 인스턴스당 풀 20개 = 총 100개
그런데 이 100개는 이미 평상시 조회·결제 트래픽이 쓰고 있다.
fallback이 추가로 90개를 요구하는 순간 풀은 즉시 고갈된다.

  -> 추천 장애가 DB 커넥션 고갈로, 다시 전 API 응답 불가로 번진다.
```

평상시에는 이 쿼리가 초당 0건 실행되므로 아무 문제가 없었다는 점이 함정의 핵심이다. **장애 대응 코드가 장애를 확대한다.**

같은 계산을 사전 계산된 정적 목록으로 바꿔 보면 왜 그것이 답인지 바로 보인다.

```
fallback을 로컬 메모리의 사전 계산 목록 조회로 바꾸면
  W ≈ 0.01ms = 0.00001초
  L = 3,000 × 0.00001 = 0.03개

즉 사실상 0. 외부 자원을 전혀 요구하지 않는다.
```

그래서 규칙은 이렇게 정리된다. **fallback 대상은 원 경로보다 반드시 싸야 하고, 원 경로와 다른 의존성 위에 있어야 한다.**

두 번째 조건도 놓치기 쉽다. 추천 서비스가 쓰는 Redis에 fallback용 인기순을 캐싱해 뒀다면, 그 Redis가 원인이었을 때 fallback도 함께 죽는다. **fallback은 원 경로와 공통 원인을 공유하지 않아야 한다.** 그래서 실무에서 최종 fallback을 로컬 메모리나 애플리케이션에 함께 배포되는 정적 파일에 두는 경우가 많다.

```java
// fallback 데이터는 미리 만들어 두고, 만드는 경로도 원 경로와 분리한다
@Component
public class PopularListCache {
    // 로컬 메모리에 보관 -> 조회 시 외부 의존 0
    private volatile List<Webtoon> snapshot = STATIC_SEED;   // 부팅 직후에도 비어 있지 않게

    // 배치가 주기적으로 갱신한다. 갱신이 실패해도 직전 값이 그대로 남는다 —
    // 오래된 인기순은 없는 인기순보다 낫다.
    @Scheduled(fixedDelay = 600_000)
    public void refresh() {
        try {
            snapshot = rankingRepository.findPopularTop20();
        } catch (Exception e) {
            log.warn("인기순 스냅샷 갱신 실패 — 직전 값 유지", e);
        }
    }

    public List<Webtoon> get() {
        return snapshot;   // 절대 예외를 던지지 않는다. 이것이 최종 fallback의 조건이다.
    }
}
```

이 코드에서 눈여겨볼 것은 `refresh()`가 실패해도 `get()`은 성공한다는 점이다. **갱신 경로의 실패와 조회 경로의 실패를 분리한 것**이 최종 fallback을 "실패할 수 없는 것"으로 만드는 방법이다.

### 2-5. 응답 스키마와 클라이언트까지가 설계 범위다

서버가 우아하게 저하해도 클라이언트가 그것을 처리하지 못하면 의미가 없다. 추천 섹션이 비어서 내려갔을 때 앱이 널 참조로 죽으면 사용자에게는 그냥 앱 크래시다.

그래서 저하를 설계할 때 **응답 스키마가 "그 필드가 없을 수 있음"을 표현할 수 있어야** 하고, 클라이언트가 그 경우의 렌더링을 정해 두어야 한다. 서버와 클라이언트 사이의 계약에 저하 상태가 포함되는 것이다.

```json
{
  "ranking": [ ... ],
  "recommended": null,              // 저하됨 — 클라이언트는 이 섹션을 숨긴다
  "degraded": ["recommend"]         // 무엇이 저하됐는지 명시 (관측과 UI 판단에 함께 쓰인다)
}
```

`degraded` 필드를 두는 것은 작지만 효과가 크다. 클라이언트가 "추천이 없는 것"과 "추천 결과가 0건인 것"을 구분할 수 있고, 저하 상태를 클라이언트 로그로도 관측할 수 있게 된다.

### 2-6. 대체 불가능한 핵심이 죽으면 — 저하의 폭이 좁을 뿐이다

"결제는 대체가 없으니 degradation이 불가능하다"는 말은 절반만 맞다. 대체는 불가능해도 **저하의 여지**는 있다. 다만 방향이 달라진다 — 품질을 낮추는 것이 아니라 **정직하게 실패하는 것**이 된다.

- **시점을 낮춘다.** 결제 승인을 지금 못 해도 주문을 "결제 대기" 상태로 접수해 큐에 쌓고 복구 후 처리한다. 기능을 "지금 완료"에서 "나중에 완료"로 낮추는 것이다. 단 이때 사용자에게 완료라고 말해서는 안 된다 — 10장 결제 문서의 "중간 상태를 감춘다"와 같은 원칙이다.
- **쓰기를 포기하고 읽기를 살린다.** 쓰기 계열이 죽었을 때 조회는 그대로 서비스하는 읽기 전용 모드도 부분 저하다.
- **그마저 안 되면 실패를 잘 전달한다.** 명확한 안내, 예상 복구 시간, 재시도 유도, 대기열. 이것까지가 degradation의 범위다.

돈 도메인에서 가장 나쁜 저하는 **애매한 성공**이다. 결제가 됐는지 안 됐는지 모르는 화면을 보여주는 것은 실패를 정직하게 보여주는 것보다 훨씬 나쁘다 — 사용자가 재시도해 이중 결제가 되거나, 문의가 폭주하거나, 신뢰를 잃는다.

## 3. 저하를 "운영"한다 — 자동, 수동, 관측, 훈련

### 3-1. 자동 저하와 수동 저하 — 역할이 다르다

서킷 + fallback은 **자동 저하**다. 장애를 감지해 사람 개입 없이 저하 모드로 전환한다. 여기에 **수동 스위치(feature flag, kill switch)**가 짝을 이룬다 — 운영자가 "추천 기능 끄기", "이벤트 배너 끄기"를 배포 없이 설정 변경만으로 실행하는 장치다.

둘의 역할 분담을 명확히 해 두는 것이 중요하다.

| | 자동 (서킷 + fallback) | 수동 (feature flag) |
|---|---|---|
| 판단 주체 | 실패율·응답시간 통계 | 사람 |
| 반응 속도 | 초 단위 | 사람이 인지하고 누를 때까지 |
| 단위 | 개별 의존성 호출 | 기능 전체 |
| 강점 | 새벽에도 즉시 동작 | 통계에 안 걸리는 상황도 판단 |
| 약점 | 통계 조건에 안 걸리면 발동하지 않음 | 사람이 필요하다 |

**자동은 개별 의존성 단위로, 수동은 기능 단위로** 두는 것이 실무의 기본형이다. 자동이 못 잡는 상황이 분명히 있기 때문이다 — 추천이 죽지는 않았지만 이상한 결과를 반환하는 경우(실패율 0%이므로 서킷이 안 열린다), 전사 부하 급증으로 비핵심 기능을 **선제적으로** 내려야 하는 경우(아직 아무것도 실패하지 않았다). 09번 문서에서 본 "실패율은 낮은데 애매하게 느린 저하 국면"이 정확히 자동 감지의 사각지대다.

수동 스위치에는 설계 항목이 하나 더 붙는다. **전파 시간**이다. 스위치를 눌렀을 때 전 인스턴스에 반영되기까지 몇 초가 걸리는지 알고 있어야 하고, 그 시간이 분 단위라면 장애 대응 수단으로는 부족하다. 설정 서버를 폴링하는 방식이라면 폴링 주기가 곧 전파 시간이다.

```java
// 수동 스위치는 "기능 전체"를 끈다 — 호출을 시도조차 하지 않는다
public List<Webtoon> recommendations(Long userId) {
    // 끈 상태에서는 서킷 통계도 쌓이지 않고 스레드도 쓰지 않는다.
    // 이것이 서킷 open과 다른 점이다 — 서킷은 스스로 다시 열어 보려 시도한다.
    if (!featureFlags.isEnabled("recommend")) {
        degradationMetrics.count("recommend", "manual-off");
        return popularListCache.get();
    }
    return getRecommendations(userId).join();
}
```

### 3-2. 저하 상태는 조용하면 안 된다

fallback이 잘 설계될수록 위험한 역설이 하나 생긴다. **겉으로 멀쩡해 보인다는 것이다.**

추천이 죽어도 인기순이 나가니 HTTP 200이 나가고, 에러율 지표는 깨끗하고, 알림은 울리지 않는다. 그동안 개인화 추천이 만들던 클릭과 매출은 조용히 빠진다. 며칠 뒤 지표 회의에서 "왜 이번 주 추천 클릭이 0인가요"로 발견되는 것이 최악의 시나리오다.

그래서 저하는 반드시 관측 가능해야 한다. 최소한 다음 셋이다.

- **기능별 fallback 동작 비율** — 전체 응답 중 대체 응답의 비율. 이것이 가장 직접적인 지표다. 평상시 baseline(0%에 가까울 것)을 알고 있어야 이상을 판정할 수 있다.
- **저하 모드 진입·이탈 이벤트** — 언제 저하가 시작되고 언제 회복됐는지가 타임라인에 남아야 사후 분석이 된다. 서킷 open 이벤트는 그 자체로 장애 알림과 연동한다(09번 문서).
- **수동 스위치 현황판** — 지금 어떤 기능이 꺼져 있는지 한 화면에서 보여야 한다. 장애 대응 중에 켰다가 **다시 끄는 것을 잊는 일**이 실제로 흔하다.

```java
// fallback 발동을 기능별로 세어 비율을 계산할 수 있게 만든다
@Component
public class DegradationMetrics {
    private final MeterRegistry registry;

    // reason을 함께 태깅하는 이유: 타임아웃 때문인지, 서킷이 열려서인지,
    // 수동으로 끈 것인지에 따라 대응이 완전히 다르다.
    public void count(String feature, String reason) {
        registry.counter("feature.fallback", "feature", feature, "reason", reason).increment();
    }

    public void count(String feature, Throwable t) {
        count(feature, t instanceof TimeoutException ? "timeout"
                     : t instanceof CallNotPermittedException ? "circuit-open"
                     : "error");
    }
}
```

```
# fallback 비율 = 대체 응답 / 전체 요청. 이것이 "지금 몇 %짜리로 돌고 있는가"다.
sum(rate(feature_fallback_total{feature="recommend"}[5m]))
  / sum(rate(http_server_requests_seconds_count{uri="/main"}[5m]))
```

### 3-3. 성공률 SLO가 거짓말을 하는 지점

앞 절의 역설이 지표 체계로 번지면 더 고약해진다. **저하된 응답을 성공으로 세는 가용성 지표는 실제 사용자 경험보다 좋게 나온다.**

메인 페이지 성공률 SLO가 99.9%라고 하자. 추천이 완전히 죽어 전원이 인기순을 받고 있어도 이 지표는 100%다. 지표상으로는 완벽한 서비스인데 사용자가 받는 것은 개인화가 사라진 화면이다.

그래서 저하가 있는 시스템에서는 가용성 지표를 두 층으로 봐야 한다.

```
전체 성공률          : 200을 돌려준 비율        -> 100%  (저하를 성공으로 센다)
완전 응답률          : 저하 없이 돌려준 비율    ->   0%  (실제 품질을 센다)
```

SLO를 어느 쪽으로 잡을지는 기능의 등급에 따라 다르다. 비핵심 기능의 저하까지 SLO 위반으로 세면 알림이 너무 자주 울리고, 전부 성공으로 세면 위와 같은 사각지대가 생긴다. 실무의 절충은 **핵심 기능은 완전 응답률로, 비핵심 기능은 fallback 비율을 별도 지표로** 두는 것이다.

### 3-4. 안 써본 fallback은 동작하지 않는다

fallback 경로는 평상시에 실행되지 않는 코드다. 정작 장애 때 처음 실행되면서 그 자체의 버그로 실패하는 일이 흔하다 — 직렬화 오류, 비어 있는 캐시, 없는 권한, 배포 때 빠진 정적 파일. 코드는 있는데 동작하지 않는 상태다.

이것을 막는 방법은 하나뿐이다. **평상시에 실행하는 것이다.**

- **소량의 트래픽을 상시 fallback으로 흘린다.** 전체 요청의 아주 작은 비율을 강제로 대체 경로로 태우면, fallback이 살아 있는지가 지표로 계속 확인된다. 이것이 가장 값싸고 확실한 방법이다.
- **의존성을 의도적으로 끊는 훈련을 한다.** 추천 API를 차단하고 메인 페이지가 뜨는지, fallback이 부하를 견디는지 확인한다. 2-4에서 본 "fallback이 DB를 때리는" 문제는 이 훈련에서만 발견된다.
- **수동 스위치를 실제로 눌러 본다.** 스위치가 있는데 아무도 눌러 본 적이 없으면 장애 중에 처음 누르게 된다. 그때 전파가 안 되거나 예상과 다른 것이 꺼지는 것을 발견한다.

세 번째가 특히 중요한데 자주 빠진다. 문서에 "kill switch로 추천을 끌 수 있음"이라고 적혀 있는 것과 그것이 실제로 동작하는 것은 다른 사실이다.

### 3-5. 방어 계층 안에서 degradation의 자리

지금까지 나온 장치들을 18번 문서의 계층 그림 위에 올려 보면 이 문서의 위치가 정리된다.

```
① 타임아웃        비핵심 호출의 대기 시간에 상한을 준다 (W)
② 재시도 제한     비핵심 호출의 재시도가 증폭되지 않게 한다
③ 서킷            지속 장애에서 호출 자체를 없앤다 -> fallback으로 즉시 전환
④ bulkhead        비핵심 호출이 쓸 수 있는 자원의 상한을 구조로 정한다 (L)
⑤ shedding        그래도 넘치는 유입을 우선순위대로 거절한다 (λ)
─────────────────────────────────────────────────────────────────
⑥ degradation     ①~⑤가 만든 실패·거절을 "낮춘 품질의 응답"으로 마무리한다
```

앞의 다섯은 **자원을 지키는** 장치이고 degradation은 **사용자에게 무엇을 보여줄지 정하는** 장치다. 그래서 순서가 이렇게 되고, 도입 순서도 같다 — degradation만 먼저 만들면 격리가 없어 저하 자체가 발동할 기회를 못 얻고(스레드가 먼저 마른다), 격리만 만들고 degradation이 없으면 사용자에게 에러만 늘어난다.

## 4. 꼬리질문 대비 포인트

### "fallback으로 내려줄 인기순 데이터는 어디서 가져오나요? fallback 자체가 부하가 되지는 않나요?"

핵심을 정확히 짚은 질문이다. 2-4에서 계산한 대로 fallback은 평상시 0%에서 장애 순간 100%를 받으므로, 실시간 DB 집계라면 `L = λW = 3,000 × 0.03 = 90개` 커넥션을 갑자기 요구해 풀을 고갈시킨다. 추천 장애가 DB 장애로 전이된다.

그래서 조건이 둘이다. **원 경로보다 싸야 하고**(사전 계산해 로컬 메모리나 정적 파일에 둔다), **원 경로와 공통 원인을 공유하지 않아야 한다**(추천이 쓰는 Redis에 fallback 데이터를 두면 그 Redis가 원인일 때 함께 죽는다). 그리고 fallback 데이터를 만드는 경로의 실패와 읽는 경로의 실패를 분리해, 갱신이 실패해도 직전 스냅샷으로 계속 응답할 수 있게 만든다 — 오래된 인기순은 없는 인기순보다 낫다.

리뷰 기준으로 정리하면 한 문장이다. "이 대체 경로에 전체 트래픽이 몰려도 버티는가, 그리고 원 경로가 죽은 원인으로 이것도 죽지는 않는가."

### "결제처럼 대체 불가능한 핵심 기능이 죽으면 graceful degradation이 가능한가요?"

대체는 불가능해도 저하의 여지는 있고, 방향이 달라진다 — 품질을 낮추는 것이 아니라 **정직하게 실패하는 것**이 된다. (1) 시점을 낮춘다: 승인을 못 해도 "결제 대기"로 접수해 큐에 쌓고 복구 후 처리한다. 단 사용자에게 완료라고 말하지 않는다. (2) 쓰기를 포기하고 읽기를 살리는 읽기 전용 모드. (3) 그마저 안 되면 명확한 안내와 예상 복구 시간, 재시도 유도.

핵심은 **돈 도메인에서 가장 나쁜 저하가 "애매한 성공"**이라는 것이다. 됐는지 안 됐는지 모르는 화면은 정직한 실패보다 훨씬 나쁘다 — 사용자가 재시도해 중복 결제가 되고, 문의가 폭주하고, 신뢰를 잃는다. "핵심이라 저하가 불가능하다"가 아니라 **"핵심은 저하의 폭이 좁을 뿐"**이라고 답하면 좋다.

### "load shedding과는 어떻게 다른가요?"

1-3의 표대로 축이 다르다. shedding은 **내가 과부하**일 때 요청 일부를 버려 나머지를 지키는 것 — 수량의 문제이고 주어는 요청이며 사용자는 503을 받는다. degradation은 **의존성이 장애**일 때 기능의 품질을 낮춰 여정을 지키는 것 — 품질의 문제이고 주어는 기능이며 사용자는 200을 받는다.

한 단계 더 들어가면 **둘은 함께 쓰인다**는 점을 말할 수 있다. 과부하 국면에서는 shedding으로 일부를 거절하기 전에 **먼저 비핵심 기능을 선제적으로 저하시키는** 것이 순서다. 추천·배지·배너를 끄면 요청당 소모 자원이 줄어 처리 용량이 올라가므로, 버려야 하는 양 자체가 줄어든다. 즉 degradation이 shedding의 필요량을 줄이는 상류 수단이 된다. 반대로 degradation으로도 부족할 때 마지막에 shedding이 발동한다.

출발점이 같다는 것도 짚어야 한다 — 둘 다 "무엇이 덜 중요한가"라는 하나의 분류에서 나오므로, 평상시의 기능 중요도 합의가 두 설계의 공통 기반이다.

### "저하 모드로 전환됐는지 사용자에게 알려야 하나요?" (가산점 포인트)

기준은 하나다. **사용자가 나중에 속았다고 느낄 수 있는가.**

추천이 인기순으로 대체되는 것처럼 사용자가 차이를 거의 못 느끼고 잘못된 판단을 유발하지도 않는 저하는 노출하지 않는 것이 일반적이다. 알릴수록 불안만 키운다. 반면 "결제 대기로 접수됨", "일시적으로 최신 조회수가 반영되지 않습니다"처럼 **사용자의 기대와 실제가 어긋나 나중에 문제가 되는 저하**는 반드시 명시해야 문의 폭주와 신뢰 손상을 막는다.

특히 사용자가 그 값을 보고 **행동을 결정하는** 경우는 무조건 알려야 한다. 잔액이 오래된 값이라는 것을 모르고 결제를 시도하게 만들면 그것은 저하가 아니라 버그다.

그리고 사용자에게 안 알리는 저하라도 **내부에는 반드시 알려야 한다**는 점을 구분해서 말하면 좋다 — 3-2의 fallback 비율 지표는 사용자 노출과 무관하게 항상 필요하다.

### "graceful degradation을 조직 차원에서 준비한다면 무엇부터 하시겠어요?" (시니어 변별 포인트)

코드보다 앞서는 세 가지를 말한다.

**(1) 기능 중요도 분류의 사전 합의.** 장애 중에는 못 정하므로 기획·운영과 평시에 등급표를 만들고 유지한다. 이때 절차적 장치가 필요하다 — 판정 질문을 미리 정하고(목적 달성 가능 여부, 돈, 법적 필수, 틀린 값의 위험), 등급 수를 셋 정도로 제한하고, 핵심 등급에 정원을 둔다. 그러지 않으면 모든 팀이 자기 기능을 핵심이라 주장해 분류가 무의미해진다. 결과물은 코드가 아니라 당직자가 볼 수 있는 문서와 현황판에 있어야 한다.

**(2) fallback 경로의 정기 검증.** 훈련 없는 fallback은 문서에만 있는 기능이다. 소량 트래픽을 상시 fallback으로 태워 살아 있음을 계속 확인하고, 의존성을 의도적으로 끊는 훈련으로 fallback이 **부하까지** 견디는지 본다. 수동 스위치는 실제로 눌러 본 적이 있어야 한다.

**(3) 저하 상태의 관측성.** fallback 비율 지표, 서킷 open 알림, 수동 스위치 현황판. 그리고 성공률 SLO가 저하를 성공으로 세어 거짓말하지 않도록 **완전 응답률을 따로 보는** 체계까지.

"저하 설계의 완성은 코드가 아니라, 지금 서비스가 몇 %짜리로 돌고 있는지 아는 것"이라고 답하면 운영 경험이 드러난다.

## 한 줄 요약

graceful degradation은 기능을 핵심/비핵심으로 분류(비즈니스 결정, 장애 전에 합의)해 비핵심 의존성의 실패를 짧은 타임아웃·서킷·전용 풀로 격리하고, 실패 시 캐시된 결과 → 사전 계산된 인기순 → 섹션 숨김처럼 품질을 계단식으로 낮추는 fallback 체인을 미리 설계·훈련해 두는 것이다 — 마지막 단계는 외부 의존이 0이어야 하고, fallback은 평상시 0%에서 장애 순간 100%를 받으므로 원 경로보다 싸고 원 경로와 공통 원인을 공유하지 않아야 하며(실시간 DB 집계를 fallback으로 두면 `L = λW = 3,000 × 0.03 = 90` 커넥션을 갑자기 요구해 추천 장애가 DB 장애로 전이된다), 저하 상태는 fallback 비율 지표와 완전 응답률로 시끄럽게 만들어야 "겉으로 멀쩡한 채 며칠간 저하 운행"을 막을 수 있다.
