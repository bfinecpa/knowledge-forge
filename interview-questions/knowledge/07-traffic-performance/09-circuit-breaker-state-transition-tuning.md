# 서킷 브레이커 — open/half-open/closed 상태 전이와 튜닝 기준

> 핵심 관전 포인트: **서킷 브레이커는 실패율이 임계치를 넘은 외부 호출을
> 아예 차단(fail fast)해서, 죽어가는 상대를 계속 두드리는 낭비와
> 우리 쪽 스레드 소모를 동시에 끊는 패턴이다. 평상시 closed(통과) →
> 실패율 초과 시 open(전면 차단) → 대기 시간 후 half-open(소량만
> 흘려보내 회복 탐침) → 성공하면 closed 복귀, 실패하면 다시 open.
> 도입 자체보다 튜닝이 어렵다 — 임계값을 너무 민감하게 잡으면 일시적
> 흔들림에 정상 트래픽까지 차단하고, 너무 둔감하게 잡으면 장애 전파를
> 못 막는다. 그래서 설정값은 감이 아니라 대상 API의 평상시
> 트래픽량·실패율·p99를 근거로 정해야 한다.**

---

## 0. 질문 + 의도

**질문**: "서킷 브레이커 패턴이란? open/half-open/closed 상태 전이와 설정값 튜닝 기준은?"

**출제 의도**: 도입은 쉽지만 임계값을 잘못 잡으면 정상 트래픽을
차단하거나(과민) 장애 전파를 못 막는다(둔감). "패턴 적용"과
"패턴 튜닝"의 차이 — 라이브러리 붙여본 수준인지, 운영까지 해봤는지를
가리는 질문이다.

## 1. 왜 필요한가 — "죽은 상대를 계속 두드리는" 비용

타임아웃과 재시도가 있어도 남는 문제가 있다. 외부 서비스가 **지속적으로
장애 상태**라면, 우리 서버는 매 요청마다 타임아웃까지 기다렸다가
실패하는 일을 반복한다.

- 요청마다 타임아웃(예: 3초)만큼 스레드가 묶인다 —
  실패가 확정적인 호출에 자원을 계속 태우는 것.
- 상대 입장에서는 죽어가는 와중에도 요청이 계속 들어와
  **복구가 방해**된다.
- 사용자 입장에서는 어차피 실패할 요청을 3초씩 기다린다.

서킷 브레이커는 이름 그대로 **두꺼비집(누전 차단기)** 이다. 과부하가
감지되면 회로를 끊어 집 전체가 타는 걸 막는다. 소프트웨어에서는
"실패율이 임계치를 넘으면 호출 자체를 차단하고 **즉시 실패**시키는"
프록시 계층으로 구현된다.

```java
// Before: 서킷 없음 — 결제사 장애 30분 동안
// 모든 주문 요청이 3초 타임아웃을 꽉 채우고 실패
public OrderResult placeOrder(Order order) {
    PaymentResult result = paymentClient.pay(order);  // 매번 3초 대기 후 실패
    ...
}

// After: 서킷 적용 — 실패율 초과 시 즉시 실패 + 대체 동작
@CircuitBreaker(name = "payment", fallbackMethod = "payLater")
public OrderResult placeOrder(Order order) {
    PaymentResult result = paymentClient.pay(order);
    ...
}

// open 상태에서는 호출 없이 이 메서드로 즉시 우회 (밀리초 단위 응답)
private OrderResult payLater(Order order, CallNotPermittedException e) {
    return OrderResult.pendingPayment(order);  // "결제 대기" 상태로 접수
}
```

핵심 효과 두 가지: **우리 쪽 자원 보호**(스레드가 타임아웃 대기에
묶이지 않음)와 **상대 쪽 회복 시간 확보**(부하를 걷어내 줌).

## 2. 상태 전이 — closed / open / half-open

이름이 직관과 반대라 헷갈리기 쉽다. **전기 회로 기준**이다 —
closed는 회로가 "닫혀서" 전기(요청)가 흐르는 정상 상태,
open은 회로가 "끊겨서" 아무것도 못 흐르는 차단 상태.

```
            실패율 ≥ 임계치
 [CLOSED] ──────────────────▶ [OPEN]
  정상 통과                      전면 차단, 즉시 실패
    ▲                            │
    │ 탐침 성공                    │ 대기 시간 경과
    │                            ▼
    └──────────────────── [HALF-OPEN]
            탐침 실패 시           소량만 통과시켜 회복 확인
            다시 OPEN으로
```

- **closed (정상)**: 모든 호출을 통과시키면서 결과(성공/실패/소요 시간)를
  집계한다. 최근 N건 또는 최근 N초의 **슬라이딩 윈도우**로 실패율을
  계산하고, 임계치를 넘으면 open으로 전이한다.
- **open (차단)**: 호출을 실행하지 않고 즉시 예외를 던진다
  (Resilience4j라면 `CallNotPermittedException`). fallback이 있으면
  fallback으로 우회한다. 설정된 대기 시간이 지나면 half-open으로 넘어간다.
- **half-open (회복 탐침)**: 제한된 수의 요청만 통과시켜 상대가
  살아났는지 확인한다. 이 탐침들이 성공하면 closed로 복귀,
  실패율이 여전히 높으면 다시 open으로 돌아가 대기한다.

half-open이 존재하는 이유가 중요하다 — open에서 곧바로 closed로
복귀시키면, 아직 회복 중인(절반쯤 살아난) 상대에게 **전체 트래픽이
한꺼번에 쏟아져** 다시 쓰러뜨린다. 소량의 탐침으로 안전을 확인한 뒤
서서히 여는 완충 단계다. 병원 퇴원 전에 가벼운 활동부터 시켜보는
재활 단계에 비유할 수 있다.

## 3. 설정값과 튜닝 기준 — "과민"과 "둔감" 사이

Resilience4j 기준으로 핵심 설정값과 각각의 튜닝 근거를 정리하면
(설정 이름은 라이브러리마다 다르지만 개념은 동일하다):

```yaml
resilience4j.circuitbreaker:
  instances:
    payment:
      slidingWindowType: COUNT_BASED     # 최근 N건 기준 (TIME_BASED: 최근 N초)
      slidingWindowSize: 100             # 실패율 계산 모수
      minimumNumberOfCalls: 20           # 이만큼 쌓이기 전엔 판단 유보
      failureRateThreshold: 50           # 실패율 50% 이상이면 open
      slowCallDurationThreshold: 2s      # 2초 넘으면 '느린 호출'로 집계
      slowCallRateThreshold: 80          # 느린 호출 비율 80% 이상이어도 open
      waitDurationInOpenState: 30s       # open 유지 시간 (회복 대기)
      permittedNumberOfCallsInHalfOpenState: 10   # half-open 탐침 수
```

각 값을 정하는 기준:

- **`minimumNumberOfCalls` — 과민 차단의 1차 방어선.**
  새벽처럼 트래픽이 적을 때 3건 중 2건 실패(실패율 66%)로 서킷이
  열리면 그건 통계가 아니라 노이즈다. "실패율이 통계적으로 의미를
  가지려면 최소 몇 건이 필요한가"를 **해당 API의 최저 트래픽
  시간대 호출량**을 보고 정한다.
- **`failureRateThreshold` — 얼마나 아파야 끊을 것인가.**
  평상시 실패율이 1% 미만인 API라면 50%는 명백한 장애 신호다.
  반대로 평소에도 실패가 잦은(예: 타사 API가 원래 불안정) 대상이라면
  임계치를 평상시 baseline보다 확실히 높게 잡아야 오탐이 없다.
  즉 **평상시 실패율을 모니터링으로 먼저 알아야 정할 수 있는 값**이다.
- **`slowCallDurationThreshold` — 느린 성공도 장애다. (가산점 포인트)**
  실패율만 보면 "타임아웃 직전까지 걸리지만 성공은 하는" 반쯤 죽은
  상태를 놓친다. 스레드를 오래 묶는다는 점에서 느린 성공은 실패만큼
  해롭다. 대상 API의 **p99 응답시간보다 여유 있게 높은 값**으로 잡아,
  정상 범위의 느린 요청은 걸리지 않되 비정상 지연은 잡히게 한다.
- **`waitDurationInOpenState` — 상대의 회복 시간에 대한 가설.**
  너무 짧으면 회복 전에 탐침을 보내 open↔half-open을 무의미하게
  반복하고(flapping), 너무 길면 이미 회복된 상대를 계속 차단해
  기회 손실이 난다. 상대 서비스의 **일반적인 재기동/failover 소요
  시간**(수십 초 단위인 경우가 많다)을 근거로 잡는다.
- **`permittedNumberOfCallsInHalfOpenState`** — 탐침이 너무 적으면
  운 나쁜 한두 건으로 판단이 튀고, 너무 많으면 탐침 자체가 회복 중인
  상대에게 부하가 된다.

튜닝의 양 극단을 한 문장씩으로 말할 수 있으면 좋다:

- **과민(임계치 낮음/모수 작음)**: 일시적 네트워크 흔들림에 서킷이
  열려 **멀쩡한 서비스를 우리가 차단**한다 — 자해가 된다.
- **둔감(임계치 높음/모수 큼)**: 서킷이 열리기 전에 이미 스레드 풀이
  고갈된다 — **있으나 마나 한 서킷**이 된다.

## 4. 꼬리질문 대비 포인트

### "open 상태에서 들어온 요청은 어떻게 처리하나요?"

호출을 실행하지 않고 즉시 예외를 던진다. 그대로 두면 사용자에게
에러가 가므로, 실무에서는 **fallback을 함께 설계**하는 것이 사실상
필수다 — 캐시된 이전 값 반환, 기본값(추천 실패 시 인기순), 나중에
처리하도록 큐에 적재("결제 대기 접수") 등. "서킷은 차단 장치이고,
차단됐을 때 사용자 경험을 뭘로 대체할지는 별도의 설계"라고 답하면
graceful degradation과 연결되어 좋은 인상을 준다.

### "느린 호출(slow call)은 왜 실패와 별도로 집계하나요?"

가장 위험한 장애 유형이 "죽진 않았는데 매우 느린" 상태이기 때문이다.
HTTP 200을 반환하므로 실패율 지표에는 안 잡히지만, 호출당 스레드
점유 시간은 수십 배가 되어 스레드 풀 고갈로 이어진다. 그래서
실패율과 별개로 느린 호출 비율만으로도 서킷을 열 수 있게 되어 있다.
"성공/실패가 아니라 자원 점유 관점에서 보면 느린 성공은 실패다"가
핵심 문장.

### "half-open에서 왜 일부 요청만 통과시키나요?"

회복 중인 서비스는 캐시가 비어 있고 커넥션 풀이 덜 차 있는 등
평상시보다 취약한 상태다. open → closed로 한 번에 전환하면 밀려 있던
전체 트래픽이 쏟아져 다시 쓰러진다(재장애). 탐침 몇 건으로 회복을
확인하고 나서 열어야 안전하다. 로드밸런서에 서버를 다시 붙일 때
warm-up 트래픽부터 흘리는 것과 같은 원리다.

### "타임아웃·재시도와는 어떤 관계로 함께 쓰나요?"

셋은 대체재가 아니라 **역할이 다른 3종 세트**다. 타임아웃은 "한 번의
호출을 얼마나 기다릴지"(개별 호출의 하한 방어), 재시도는 "일시적
실패를 어떻게 흡수할지"(짧은 흔들림 대응), 서킷은 "지속적 장애일 때
호출 자체를 멈출지"(장애 국면 전환 감지)를 담당한다. 배치 순서로는
호출에 가까운 안쪽부터 타임아웃 → 재시도 → 서킷이 일반적이다 —
서킷이 가장 바깥에 있어야 "재시도까지 다 해봤는데도 실패"가 서킷의
실패 1건으로 집계되고, 서킷이 열리면 재시도 자체가 차단된다.
반대로 서킷을 재시도 안쪽에 두면 서킷이 열렸는데도 재시도가
계속 두드리는 모순이 생긴다.

### "서킷 브레이커가 오히려 문제를 일으킨 경험이나 함정은?" (시니어 변별 포인트)

세 가지를 들 수 있다.

1. **인스턴스별 상태 불일치**: 서킷 상태는 기본적으로 서버 인스턴스별
   로컬 메모리에 있다. 10대 중 3대만 서킷이 열리면 트래픽이 나머지
   7대로 쏠리며 혼란이 생기고, "일부 사용자만 간헐 실패"라는 추적하기
   어려운 증상이 된다. 상태를 공유하는 설계도 있지만 그만큼 복잡도가
   올라가므로 트레이드오프다.
2. **과민 설정의 자해**: 배포 직후 워밍업 지연이나 순간적 GC pause로
   느린 호출 비율이 튀어 서킷이 열리고, 멀쩡한 다운스트림을 우리가
   차단해 매출 손실이 나는 사고. `minimumNumberOfCalls`와 관측된
   baseline 없이 예제 설정값을 복사해 쓰면 이렇게 된다.
3. **서킷 open은 반드시 알림과 연동**: 서킷이 열리면 시스템은 조용히
   fallback으로 동작하므로 겉보기에 멀쩡하다. 알림이 없으면 장애를
   며칠씩 모르고 지나갈 수 있다 — "서킷 open = 장애 이벤트"로
   모니터링에 노출하는 것까지가 도입이다.

## 한 줄 요약

서킷 브레이커는 실패율·느린 호출 비율이 임계치를 넘으면 호출을 차단해
(closed→open) 내 스레드와 상대의 회복 시간을 지키고, 대기 후 소량
탐침으로(half-open) 회복을 확인해 복귀하는 패턴이다 — 설정값은 감이
아니라 대상 API의 평상시 트래픽량·실패율·p99를 근거로 잡아야 하며,
과민하면 정상 트래픽을 차단하는 자해, 둔감하면 있으나 마나가 된다.
