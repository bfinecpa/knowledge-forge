# 서킷 브레이커 — open/half-open/closed 상태 전이와 튜닝 기준

> 핵심 관전 포인트: **서킷 브레이커는 실패율이 임계치를 넘은 외부 호출을 아예 차단(fail fast)해서, 죽어가는 상대를 계속 두드리는 낭비와 우리 쪽 스레드 소모를 동시에 끊는 패턴이다. 이름은 집의 누전 차단기에서 왔고 하는 일도 같다 — 과전류가 감지되면 회로를 끊어 집 전체가 타는 것을 막고, 고쳐진 뒤에 다시 올린다. 평상시 closed(통과) → 실패율 초과 시 open(전면 차단, **호출조차 하지 않으므로 스레드가 묶이지 않는다**) → 대기 시간 후 half-open(소량만 흘려보내 회복 탐침) → 성공하면 closed 복귀, 실패하면 다시 open. 도입 자체보다 튜닝이 어렵다 — 임계값을 너무 민감하게 잡으면 일시적 흔들림에 정상 트래픽까지 차단하고, 너무 둔감하게 잡으면 장애 전파를 못 막는다. 그래서 설정값은 감이 아니라 대상 API의 평상시 트래픽량·실패율·p99를 근거로 정해야 한다. 그리고 open일 때 무엇을 대신 돌려줄지(fallback)까지가 설계이고, 서킷 자체가 사고를 만드는 경우 — 복구했는데 안 닫히는 서킷, 운 나쁜 탐침 한 건이 복구를 늦추는 구조, 인스턴스마다 갈리는 판단 — 를 아는 것이 운영 경험의 증거다.**

---

## 0. 질문 + 의도

**질문**: "서킷 브레이커 패턴이란? open/half-open/closed 상태 전이와 설정값 튜닝 기준은?"

**출제 의도**: 도입은 쉽지만 임계값을 잘못 잡으면 정상 트래픽을 차단하거나(과민) 장애 전파를 못 막는다(둔감). "패턴 적용"과 "패턴 튜닝"의 차이 — 라이브러리 붙여본 수준인지, 운영까지 해봤는지를 가리는 질문이다.

## 1. 왜 필요한가 — "죽은 상대를 계속 두드리는" 비용

### 1-1. 전제 지식 — 스레드 하나가 호출 하나를 붙잡는다는 뜻

먼저 깔아둘 사실이 하나 있다. 톰캣 같은 전통적인 서블릿 서버에서 **HTTP 요청 하나는 워커 스레드 하나가 처음부터 끝까지 맡는다.** 그 요청이 처리되는 동안 그 스레드는 다른 요청을 처리할 수 없다.

그래서 요청 처리 중에 외부 API를 동기 호출하면, 그 응답을 기다리는 시간 동안 **스레드는 아무 일도 하지 않으면서 자리를 차지한다.** CPU를 쓰는 것도 아니고 그냥 소켓을 붙잡고 앉아 있다. 그런데도 다른 요청은 그 스레드를 쓸 수 없다.

워커 스레드 수는 유한하다. Spring Boot의 톰캣 기본값은 200개다. 즉 **이 서버가 동시에 처리할 수 있는 요청은 최대 200건**이고, 201번째 요청은 스레드가 하나 풀릴 때까지 대기 큐에서 기다린다.

이 두 사실 — 요청 하나당 스레드 하나, 스레드 수는 유한 — 을 곱하면 다음 절의 산수가 나온다.

### 1-2. 산수로 보는 붕괴 — 응답 3초, 스레드 200개면 초당 66건이 상한이다

주문 API가 결제 API를 동기 호출하는 구조를 놓고 계산해 보자. 조건은 이렇다.

```text
톰캣 워커 스레드 수        200개
결제 API 평상시 응답 시간   100ms (0.1초)
주문 요청 유입량           300 TPS (초당 300건)
```

**평상시.** 요청 하나가 스레드를 붙잡는 시간이 0.1초이므로, 스레드 하나는 1초에 최대 10건을 처리한다. 200개면 이론상 초당 2,000건이다.

```text
처리 상한 = 스레드 수 ÷ 건당 점유 시간
          = 200개 ÷ 0.1초
          = 2,000 TPS
```

유입은 300 TPS이니 여유가 6.7배다. 실제로 동시에 붙잡혀 있는 스레드 수도 계산할 수 있다 — 초당 300건이 들어와 각각 0.1초씩 머무르므로 평균 동시 점유는 `300 × 0.1 = 30개`다. 200개 중 30개만 쓰고 있다는 뜻이다. (이 곱셈이 리틀의 법칙 `L = λ × W`이고, 17번 문서에서 따로 다룬다.)

**장애 시.** 결제 API가 죽은 것은 아니고 **느려졌다.** 응답이 100ms에서 3초로 늘었다. 유입량은 그대로 300 TPS다. 여기서 두 가지가 동시에 벌어진다.

첫째, **처리 상한이 30분의 1로 떨어진다.**

```text
처리 상한 = 200개 ÷ 3초 = 66.7 TPS
```

둘째, **스레드가 0.67초 만에 전부 소진된다.** 장애 시작 직후 첫 3초 동안은 어떤 요청도 반환되지 않으므로, 점유 스레드가 초당 300개씩 순수하게 늘어난다.

```text
스레드 전부 소진까지 = 200개 ÷ 300건/초 = 0.67초
```

이제 유입 300 TPS 중 66.7건만 통과하고 **나머지 233건은 매 초 대기 큐로 밀린다.** 톰캣의 연결 대기 큐 크기가 100이라면 그 큐도 곧 찬다.

```text
큐가 차기까지 = 100 ÷ (300 − 66.7) = 100 ÷ 233.3 = 0.43초
→ 장애 시작 후 약 1.1초 지점부터 연결 자체가 거부된다
```

시간축에 올려 보면 이렇게 진행된다.

```text
t = 0.0s   결제 API 응답이 100ms → 3초로 느려짐 (아직 아무 증상 없음)
t = 0.3s   점유 스레드 약 90개. 지표상으로는 "응답이 좀 느리네" 수준
t = 0.67s  ★ 워커 스레드 200개 전부 결제 응답 대기로 소진
           이 순간부터 결제와 무관한 요청(웹툰 조회, 로그인)도
           스레드를 받지 못한다 — 같은 풀을 쓰기 때문이다
t = 1.1s   ★ 대기 큐 100까지 소진. 새 연결이 거부되기 시작
t = 3.0s   첫 요청들이 3초 만에 반환되며 스레드가 풀리지만,
           풀리는 즉시 대기 중인 요청이 차지한다 → 처리율 66.7 TPS로 고정
그 이후     초당 233건이 계속 밀림. 이 서버는 사실상 응답 불가
```

**여기서 핵심은 마지막 줄이 아니라 t=0.67s 줄이다.** 느려진 것은 결제 API 하나인데, 응답 불가가 된 것은 **이 서버의 모든 API**다. 스레드 풀이 기능별로 나뉘어 있지 않은 공유 자원이기 때문에, 한 의존성의 지연이 자원 고갈을 통해 기능 경계를 넘는다. 이것이 18번 문서(`18-cascading-failure-mechanism-and-bulkhead.md`)에서 다루는 cascading failure와 **정확히 같은 메커니즘**이다 — 장애가 "옮는" 것이 아니라, 대기가 공유 자원을 고갈시키는 패턴이 계층마다 반복되는 것이다.

여기에 세 가지 낭비가 더 얹힌다.

**우리 쪽 낭비.** 결제 API가 확실히 실패할 상황인데도 매 요청이 3초를 기다린 뒤 실패한다. 결과가 정해진 호출에 스레드 3초씩을 태우는 것이다.

**상대 쪽 방해.** 결제 API는 과부하로 느려졌는데, 우리는 계속 300 TPS를 밀어 넣는다. 상대가 재기동해도 밀려 있던 요청이 즉시 다시 덮치므로 **복구할 틈이 없다.**

**사용자 쪽 손해.** 어차피 실패할 요청을 3초 기다린 끝에 에러를 본다. 즉시 "결제 시스템 점검 중"이라고 알려주는 것보다 나쁜 경험이다.

### 1-3. 이름의 유래 — 집의 누전 차단기

**서킷 브레이커(circuit breaker)는 전기 회로의 차단기, 흔히 두꺼비집이라 부르는 그 장치에서 온 이름이다.** 어느 방의 배선에 과전류가 흐르면 차단기가 회로를 끊는다. 전기를 못 쓰게 되는 것은 손해지만, 그 손해를 감수하는 이유는 **끊지 않으면 배선이 과열돼 집 전체가 타기** 때문이다. 그리고 원인을 고친 뒤에는 사람이 스위치를 다시 올린다.

소프트웨어의 서킷 브레이커가 하는 일이 정확히 같다.

| 전기 차단기 | 서킷 브레이커 |
|---|---|
| 과전류를 감지 | 실패율·느린 호출 비율이 임계치를 넘는 것을 감지 |
| 회로를 끊어 전류를 막음 | 호출을 막고 즉시 실패시킴 |
| 그 방의 전기를 포기해 집을 지킴 | 그 의존성 기능을 포기해 나머지 서비스를 지킴 |
| 고친 뒤 사람이 다시 올림 | 대기 후 소량 탐침으로 스스로 확인해 다시 올림 |

마지막 행에 차이가 하나 있다. 전기 차단기는 사람이 올리지만, 서킷 브레이커는 **스스로 회복을 시험해 본다.** 그 시험 단계가 half-open이고, 2절의 주제다.

비유에서 반드시 가져가야 할 점은 **차단이 손해를 없애는 게 아니라 손해의 범위를 바꾼다**는 것이다. 서킷을 열어도 결제는 여전히 실패한다. 서킷이 구하는 것은 결제가 아니라 **결제와 무관한 나머지 전부**다.

### 1-4. 서킷이 하는 일 — 기다리지 않고 즉시 실패시킨다

코드로 보면 차이가 한 줄이지만, 스레드 관점에서는 3초와 0의 차이다.

```java
// Before: 서킷 없음 — 결제사 장애 30분 동안
// 모든 주문 요청이 3초 타임아웃을 꽉 채우고 실패
public OrderResult placeOrder(Order order) {
    // 이 한 줄이 워커 스레드를 3초간 붙잡는다.
    // 300 TPS × 3초 = 동시 점유 900개가 필요한데 풀은 200개다.
    // 1-2의 계산대로 0.67초 만에 풀이 마르고, 결제와 무관한
    // 웹툰 조회·로그인까지 스레드를 못 받아 함께 죽는다.
    PaymentResult result = paymentClient.pay(order);
    ...
}

// After: 서킷 적용 — 실패율 초과 시 즉시 실패 + 대체 동작
@CircuitBreaker(name = "payment", fallbackMethod = "payLater")
public OrderResult placeOrder(Order order) {
    // open 상태에서는 이 호출이 아예 실행되지 않는다.
    // 소켓을 열지도, 응답을 기다리지도 않으므로 스레드 점유 시간이
    // 3초에서 사실상 0이 된다 — 이것이 서킷의 본체다.
    PaymentResult result = paymentClient.pay(order);
    ...
}

// open 상태에서는 호출 없이 이 메서드로 즉시 우회 (밀리초 단위 응답)
private OrderResult payLater(Order order, CallNotPermittedException e) {
    // CallNotPermittedException은 "서킷이 열려 호출을 허용하지 않았다"는
    // 뜻의 전용 예외다. 상대가 실패한 것이 아니라 우리가 안 보낸 것이므로
    // 로그·지표에서 실제 결제 실패와 구분해 집계해야 한다.
    return OrderResult.pendingPayment(order);  // "결제 대기" 상태로 접수
}
```

핵심 효과 두 가지: **우리 쪽 자원 보호**(스레드가 타임아웃 대기에 묶이지 않음)와 **상대 쪽 회복 시간 확보**(부하를 걷어내 줌).

같은 계산을 서킷이 열린 상태에 다시 적용해 보면 효과가 숫자로 보인다. 결제 호출의 스레드 점유 시간이 3초에서 1ms 미만으로 떨어지므로, 결제 경로가 잡아먹는 동시 스레드는 `300 × 0.001 = 0.3개` 수준이다. 200개 풀이 그대로 남아 웹툰 조회와 로그인을 계속 처리한다. **결제 기능만 실패하고, 나머지는 산다.**

## 2. 상태 전이 — closed / open / half-open

### 2-1. 이름이 직관과 반대인 이유

이름이 헷갈리기 쉽다. 보통 "open(열림)"은 통하는 것, "closed(닫힘)"는 막힌 것으로 읽히는데 서킷 브레이커는 반대다.

**전기 회로 기준이기 때문이다.** 회로에서 스위치가 **닫혀야(closed)** 전선이 이어져 전류가 흐른다. 스위치가 **열리면(open)** 회로에 틈이 생겨 전류가 끊긴다. 그래서 closed가 정상 통과, open이 차단이다.

한 번 이렇게 외워 두면 헷갈리지 않는다 — **회로가 닫혀 있으면 요청이 흐른다.**

### 2-2. 전이 도식

```text
        ┌───── 실패율 ≥ failureRateThreshold
        │      또는 느린 호출 비율 ≥ slowCallRateThreshold
        │      (단, 창에 minimumNumberOfCalls 이상 모였을 때만 판정)
        │
   [ CLOSED ] ────────────────────────────────────▶ [ OPEN ]
   전부 통과 + 결과 집계                              호출하지 않고 즉시 실패
        ▲                                                │
        │                                                │ waitDurationInOpenState 경과
        │ 탐침의 실패율 < 임계치                            │ (호출 없이 시간만으로 자동 전이)
        │                                                ▼
        └───────────────────────────────────────  [ HALF-OPEN ]
                                                  permittedNumberOfCallsInHalfOpenState
                                                  건만 통과시켜 결과를 본다
                                                        │
                        탐침의 실패율 ≥ 임계치 ────────────┘
                        → 다시 OPEN (대기 시간 리셋)
```

전이 조건을 문장으로 다시 확인하자. **closed → open**은 창에 모인 결과의 실패율(또는 느린 호출 비율)이 임계치를 넘을 때 일어난다. **open → half-open**은 조건이 실패율이 아니라 **시간**이다 — 정해진 대기 시간이 지나면 아무 호출 없이 자동으로 넘어간다(그동안 호출을 안 하니 실패율을 알 방법이 없다). **half-open → closed**는 탐침 결과가 좋을 때, **half-open → open**은 탐침 결과가 나쁠 때이고, 후자의 경우 대기 시간이 처음부터 다시 흐른다.

### 2-3. 상태별로 요청은 실제로 어떻게 처리되는가

패턴을 아는 것과 "이 상태에서 내 요청이 어떻게 되는가"를 아는 것은 다르다. 상태별로 명시하면 이렇다.

**closed — 전부 통과시키면서 채점한다.** 모든 호출이 정상적으로 나간다. 서킷은 각 호출의 결과(성공/실패/소요 시간)를 슬라이딩 윈도우에 기록만 하고 흐름에 개입하지 않는다. 오버헤드는 카운터 갱신 정도다.

**open — 호출을 하지 않고 즉시 실패시킨다.** 이 문장의 "호출을 하지 않고"가 이 패턴 전체의 핵심이다. 소켓을 열지 않고, 요청을 보내지 않고, 응답을 기다리지 않는다. Resilience4j라면 `CallNotPermittedException`을 즉시 던지고, fallback이 설정돼 있으면 fallback으로 넘어간다.

**기다리지 않으므로 스레드가 묶이지 않는다.** 1-2에서 붕괴의 원인이 "3초짜리 대기 × 유입량"이었으므로, 대기를 0으로 만드는 것이 곧 해결이다. 타임아웃을 3초에서 1초로 줄이는 것과는 성질이 다르다 — 타임아웃 단축은 점유 시간을 3분의 1로 줄이지만, 서킷 open은 점유 시간을 아예 없앤다.

**half-open — 정해진 개수만 통과시키고 나머지는 거절한다.** 허용 건수(`permittedNumberOfCallsInHalfOpenState`) 안에 들어온 요청만 실제로 나가고, 그 사이 초과로 들어온 요청은 open과 마찬가지로 즉시 실패한다. 허용된 탐침이 모두 끝나면 그 결과의 실패율로 closed 복귀냐 open 회귀냐를 판정한다.

세 상태를 스레드 점유 시간 관점에서 나란히 보면 이렇다.

| 상태 | 실제 호출 | 요청당 스레드 점유 | 상대가 받는 부하 |
|---|---|---|---|
| closed | 전부 | 상대의 응답 시간만큼 (장애 시 3초) | 유입 전량 |
| open | 없음 | 사실상 0 (예외 생성 비용뿐) | 0 |
| half-open | 허용 건수만 | 탐침은 응답 시간만큼, 나머지는 0 | 탐침 건수만 |

### 2-4. half-open이 왜 필요한가

open에서 곧바로 closed로 복귀시키면 어떻게 되는지 생각해 보면 답이 나온다.

서킷이 열려 있던 30초 동안 유입은 멈추지 않았다. 30초 × 300 TPS면 9,000건이 fallback으로 처리되며 흘러갔고, 사용자와 상류 시스템은 재시도를 얹었을 수도 있다. 이 상태에서 서킷을 한 번에 열어젖히면 **아직 절반쯤 살아난 상대에게 전체 트래픽이 한꺼번에 쏟아진다.**

회복 중인 서비스는 평상시보다 취약하다. 캐시가 비어 있어 모든 요청이 DB로 가고, 커넥션 풀이 아직 덜 차 있고, JIT 컴파일이 안 돼 있고, 밀려 있던 자기 큐를 처리하는 중이다. 이 순간의 처리 능력은 정상 시의 일부에 불과하므로, 정상 트래픽만으로도 다시 쓰러진다.

그래서 사이에 완충 단계를 둔다. **소량의 탐침으로 안전을 확인한 뒤 여는 것**이 half-open이다.

병원 퇴원 절차에 비유할 수 있다. 중환자실에서 바로 마라톤을 시키지 않는다. 가벼운 보행부터 시켜 보고 괜찮으면 활동 범위를 넓힌다. 로드밸런서에 서버를 다시 붙일 때 warm-up 트래픽부터 흘리는 것도 같은 원리다.

### 2-5. 실패율을 재는 창 — count-based와 time-based

"실패율이 50%를 넘으면 open"이라고 할 때, **무엇에 대한 50%인지**를 정해야 한다. 서비스 시작 이후 전체 호출의 실패율이라면 어제의 실패가 오늘의 판단에 섞여 아무 의미가 없다. 그래서 **최근의 일정 범위만 보는 창**을 두고, 그 창 안의 결과로만 실패율을 계산한다. 이것이 슬라이딩 윈도우다.

문제는 "최근"을 무엇으로 세는가다. 논리적으로 두 가지밖에 없다 — **건수로 세거나, 시간으로 세거나.**

**count-based(최근 N건)**는 최근 호출 N건의 결과를 링 버퍼에 담아 두고, 새 호출이 들어오면 가장 오래된 것을 밀어낸다. 실패율은 `버퍼 안의 실패 건수 ÷ N`이다.

**time-based(최근 N초)**는 최근 N초 안에 완료된 호출만 집계한다. 보통 1초 단위 버킷에 결과를 모아 두고, N초가 지난 버킷은 버린다.

둘의 결정적 차이는 **창이 덮는 "시간"이 고정인가 아닌가**다. 같은 설정을 트래픽이 다른 두 시각에 적용해 보면 확실히 보인다.

```text
[설정] 창 = 최근 100건 (count-based)

  점심 피크 (300 TPS)  →  100건이 쌓이는 데 100 ÷ 300 = 0.33초
                          창이 최근 0.33초를 덮는다. 아주 민감하고 최신이다.

  새벽 3시 (5건/분)    →  100건이 쌓이는 데 100 ÷ 5 = 20분
                          창이 최근 20분을 덮는다. 20분 전의 실패가
                          아직 판단에 참여한다.

[설정] 창 = 최근 10초 (time-based)

  점심 피크 (300 TPS)  →  창 안에 약 3,000건. 표본이 충분해 실패율이 안정적이다.
  새벽 3시 (5건/분)    →  창 안에 약 1건. 표본이 거의 없어 실패율이 0% 또는 100%로 튄다.
```

즉 **count-based는 표본 수를 고정하는 대신 시간이 고무줄이 되고, time-based는 시간을 고정하는 대신 표본 수가 고무줄이 된다.** 어느 쪽도 공짜가 아니다.

그래서 고르는 기준은 이렇다.

**트래픽이 꾸준히 많은 대상은 count-based가 무난하다.** 창이 짧은 시간을 덮으므로 최신 상태를 보게 되고, 링 버퍼 하나로 끝나 계산이 가볍다. 사내 핵심 API처럼 초당 수백 건이 꾸준히 흐르는 대상이 여기 해당한다.

**트래픽 변동이 크거나 원래 적은 대상은 time-based가 낫다.** 낮에는 많고 새벽에는 거의 없는 API, 특정 사용자군만 쓰는 기능, 배치 시간에만 호출되는 경로가 그렇다. "최근 10초 실패율"은 트래픽과 무관하게 항상 지금을 뜻하므로 오래된 실패가 판단에 남지 않는다. 사람에게 설명하기 쉬운 지표라는 점도 이점이다 — "20분 전 실패 때문에 아직 열려 있습니다"보다 "최근 10초 실패율이 60%입니다"가 대응 가능한 정보다.

한 가지 덧붙이면, time-based를 고르면 **표본이 적을 때의 튐**을 따로 막아야 한다. 그 장치가 다음 절의 `minimumNumberOfCalls`다.

## 3. 설정값과 튜닝 기준 — "과민"과 "둔감" 사이

Resilience4j 기준으로 핵심 설정값을 먼저 한자리에 놓고 보자 (설정 이름은 라이브러리마다 다르지만 개념은 동일하다).

```yaml
resilience4j.circuitbreaker:
  instances:
    payment:
      slidingWindowType: COUNT_BASED     # 최근 N건 기준 (TIME_BASED: 최근 N초)
      slidingWindowSize: 100             # 실패율 계산 모수
      minimumNumberOfCalls: 20           # 이만큼 쌓이기 전엔 판단 유보
      failureRateThreshold: 50           # 실패율 50% 이상이면 open
      slowCallDurationThreshold: 2s      # 2초 넘으면 '느린 호출'로 집계
      slowCallRateThreshold: 80          # 느린 호출 비율 80% 이상이어도 open
      waitDurationInOpenState: 30s       # open 유지 시간 (회복 대기)
      permittedNumberOfCallsInHalfOpenState: 10   # half-open 탐침 수
```

각 값이 정확히 무엇을 재는 값인지 한 줄로 정리하면 이렇다. 이 정의를 먼저 붙잡아야 뒤의 튜닝 논의가 따라온다.

| 설정 | 무엇을 재는가 |
|---|---|
| `slidingWindowType` | 최근을 건수로 셀지(COUNT_BASED) 시간으로 셀지(TIME_BASED) |
| `slidingWindowSize` | 그 창의 크기 — 건수라면 몇 건, 시간이라면 몇 초 |
| `minimumNumberOfCalls` | 판정을 시작하기 위해 창에 최소 몇 건이 모여야 하는가 |
| `failureRateThreshold` | 실패로 끝난 호출의 비율이 몇 %를 넘으면 open인가 |
| `slowCallDurationThreshold` | 몇 초를 넘긴 호출을 "느린 호출"로 셀 것인가 |
| `slowCallRateThreshold` | 그 느린 호출의 비율이 몇 %를 넘으면 open인가 |
| `waitDurationInOpenState` | open을 몇 초 유지한 뒤 half-open으로 넘어가는가 |
| `permittedNumberOfCallsInHalfOpenState` | half-open에서 실제로 통과시킬 탐침 몇 건인가 |

### 3-1. `minimumNumberOfCalls` — 주니어가 반드시 밟는 함정

이 값을 먼저 다루는 이유는, 나머지를 아무리 잘 잡아도 이 하나가 없으면 서킷이 엉뚱하게 열리기 때문이다.

**이 값이 없다면(또는 1로 잡혀 있다면) 창에 호출이 단 1건만 들어와도 실패율 계산이 성립한다.** 그러면 다음 일이 벌어진다.

```text
새벽 3시. 이 API 호출량은 5분에 1건.

03:00:00  호출 1건 발생 → 네트워크 순단으로 실패
          창에 든 호출: 1건, 그중 실패: 1건
          실패율 = 1 ÷ 1 = 100%  ≥ failureRateThreshold(50%)
          → 서킷 OPEN

03:00:00 ~ 03:00:30  결제 기능 전면 차단
          상대 서버는 멀쩡했다. 실패한 것은 우연히 그 한 건이었다.
```

**통계가 아니라 노이즈로 서킷이 열린 것이다.** 실패율 100%라는 숫자는 사실이지만, 모수가 1인 100%는 아무것도 말해 주지 않는다. 동전을 한 번 던져 앞면이 나왔다고 "이 동전은 앞면 확률 100%"라고 결론 내리는 것과 같다.

`minimumNumberOfCalls: 20`은 정확히 이것을 막는다. **창에 20건이 모이기 전에는 실패율을 계산하지 않고 판단을 유보한다** — 20건 중 19건이 실패해도 서킷은 열리지 않는다. 20번째 호출이 완료된 순간부터 판정이 시작된다.

정하는 근거는 **해당 API의 최저 트래픽 시간대 호출량**이다. 새벽에 5분에 1건인 API에 `minimumNumberOfCalls: 20`을 걸면 20건이 모이는 데 100분이 걸리므로, 새벽에는 사실상 서킷이 작동하지 않는다. 이것이 나쁜가? 대개 나쁘지 않다 — 새벽에는 유입이 적어 1-2의 스레드 고갈 자체가 일어나지 않으므로 서킷이 지킬 것이 별로 없다. **"판단할 근거가 없을 때는 판단하지 않는다"가 옳은 기본값이다.**

여기에 저트래픽이 만드는 짝 함정이 하나 더 있다. **`permittedNumberOfCallsInHalfOpenState`도 저트래픽에서는 시간이 걸린다.** 탐침 10건을 요구하는데 새벽에 5분에 1건이면 판정까지 50분이 걸리고, 그동안 서킷은 half-open에 머문다. 이 체류 시간에 상한을 두는 설정이 따로 있으니(Resilience4j의 `maxWaitDurationInHalfOpenState`) 저트래픽 대상에는 함께 잡아 둔다.

### 3-2. `failureRateThreshold` — 얼마나 아파야 끊을 것인가

임계치를 정하려면 **평상시 실패율을 먼저 알아야 한다.** 이것이 이 값에 대한 유일하게 중요한 사실이다.

평상시 실패율이 1% 미만인 사내 API라면 50%는 명백한 장애 신호다. 반대로 평소에도 실패가 잦은 대상 — 예를 들어 원래 불안정한 타사 API로 평상시 실패율이 15%라면 — 임계치를 그 baseline보다 확실히 높게 잡아야 오탐이 없다. baseline이 15%인 대상에 임계치 20%를 걸면 평상시 변동만으로도 서킷이 열린다.

즉 **모니터링 없이는 정할 수 없는 값**이다. 예제 설정값을 복사해 쓰는 것이 위험한 이유가 여기 있다. 예제의 50%는 예제가 상정한 평상시 실패율에 대한 값이고, 우리 대상의 baseline은 다르다.

한 가지 주의할 것은 **무엇을 실패로 셀지**도 결정 사항이라는 점이다. HTTP 4xx는 대개 요청 쪽 결함이므로 상대의 건강 상태와 무관하다 — 이것을 실패로 세면 클라이언트 버그가 서킷을 열어 버린다. 상대의 장애를 뜻하는 실패(연결 실패, 타임아웃, 5xx)만 세도록 예외를 분류해야 한다.

```java
CircuitBreakerConfig config = CircuitBreakerConfig.custom()
        .failureRateThreshold(50)
        // recordExceptions: 이 예외들만 "실패"로 집계한다.
        // 상대 서버의 건강 상태를 반영하는 실패만 골라야 한다.
        .recordExceptions(IOException.class, TimeoutException.class)
        // ignoreExceptions: 집계에서 완전히 제외한다.
        // 400 Bad Request는 우리 요청이 잘못된 것이므로 몇 번을 보내도
        // 실패한다. 이걸 실패로 세면 클라이언트 버그 하나가 서킷을 열어
        // 멀쩡한 상대를 우리가 차단하게 된다.
        .ignoreExceptions(BadRequestException.class)
        .build();
```

### 3-3. `slowCallDurationThreshold` / `slowCallRateThreshold` — 느린 성공도 장애다 (가산점 포인트)

실패율만 보면 놓치는 상태가 있다. **타임아웃 직전까지 걸리지만 결국 성공하는** 반쯤 죽은 상태다. HTTP 200을 반환하므로 실패율 지표는 깨끗한데, 1-2의 계산에서 우리를 죽인 것은 실패가 아니라 **점유 시간**이었다. 3초 걸려 성공한 호출은 3초 걸려 실패한 호출과 자원 관점에서 완전히 같다.

그래서 서킷은 실패율과 별개로 **느린 호출 비율**만으로도 열릴 수 있게 되어 있다. `slowCallDurationThreshold`가 "몇 초를 넘으면 느린 호출로 셀지", `slowCallRateThreshold`가 "그 비율이 몇 %를 넘으면 열지"를 정한다.

`slowCallDurationThreshold`는 **대상 API의 p99 응답시간보다 여유 있게 높은 값**으로 잡는다. p99가 400ms인 API에 2초를 걸면, 정상 범위의 느린 요청(상위 1%)은 걸리지 않고 비정상 지연만 잡힌다. p99에 딱 맞춰 잡으면 평상시에도 1%가 느린 호출로 집계돼 baseline이 지저분해진다.

이 값과 read 타임아웃의 관계도 짚어 둘 만하다. 타임아웃보다 이 값이 크면 **느린 호출로 집계될 기회가 없다** — 타임아웃이 먼저 터져 전부 실패로 잡히기 때문이다. 그래서 `slowCallDurationThreshold`는 타임아웃보다 작아야 의미가 있고, 이 관계는 10번 문서(`10-timeout-layers-and-budget.md`)의 타임아웃 값과 함께 정해야 한다.

### 3-4. `waitDurationInOpenState` — 상대의 회복 시간에 대한 가설

이 값은 **"상대가 스스로 낫는 데 얼마나 걸릴까"라는 우리의 추측**이다. 근거 없는 숫자가 되기 쉬우므로 무엇을 근거로 삼는지가 중요하다.

너무 짧으면 회복 전에 탐침을 보내 실패하고 다시 open이 된다. 이 왕복이 반복되는 것을 **플래핑(flapping, 깃발이 펄럭이는 모양)**이라 부른다. 탐침이 계속 실패하니 회복은 안 되고, 상대에게는 주기적인 부하만 얹힌다.

너무 길면 반대 손해가 난다. 상대가 5초 만에 복구됐는데 대기 시간이 5분이면, 4분 55초 동안 멀쩡한 서비스를 우리가 차단한다. 그 시간의 결제 실패는 우리가 만든 것이다.

근거로 삼을 것은 **상대 서비스의 일반적인 재기동·failover 소요 시간**이다. 컨테이너 재기동과 헬스체크 통과가 수십 초 단위인 경우가 많으므로 30초 안팎에서 출발해, 실제 장애 이력의 복구 시간 분포를 보고 조정한다.

여기서 알아 두면 좋은 개선이 하나 있다 — **대기 시간을 고정값이 아니라 재시도처럼 늘려 가는 것.** 첫 번째 open은 10초, 연속으로 다시 열리면 20초, 40초로 늘린다. 짧은 흔들림에는 빨리 복귀하면서 긴 장애에는 탐침 빈도를 자동으로 줄이는 효과가 있고, 플래핑도 자연히 잦아든다. 이 아이디어는 11번 문서(`11-retry-storm-backoff-jitter.md`)의 지수 백오프와 같은 발상이다.

### 3-5. `permittedNumberOfCallsInHalfOpenState` — 운의 비중을 정하는 값

탐침 수는 **판정에 운이 얼마나 섞이게 할지**를 정하는 값이다.

너무 적으면 판정이 운에 좌우된다. 1건이면 그 한 건이 하필 무거운 파라미터의 요청이었거나 하필 GC 순간에 걸렸다는 이유로 서킷이 다시 닫히지 않는다. 너무 많으면 탐침 자체가 회복 중인 상대에게 부하가 된다 — 아직 취약한 상대에게 100건을 한꺼번에 보내는 것은 탐침이 아니라 공격이다.

10건 정도면 "10건 중 5건 미만 실패면 닫는다"는 실패율 판정이 성립하고, 회복 중인 상대에게 부담도 적다. 그리고 3-1에서 본 대로, 저트래픽 대상에서는 이 건수를 모으는 데 걸리는 시간까지 계산해야 한다.

### 3-6. 과민과 둔감 — 양쪽으로 틀렸을 때 무슨 일이 벌어지는가

지금까지의 값을 두 방향으로 잘못 잡았을 때를 대조해 보면 튜닝의 감각이 잡힌다.

| 설정 | 과민하게 잡으면 (너무 민감) | 둔감하게 잡으면 (너무 관대) |
|---|---|---|
| `slidingWindowSize` | 작다 → 창이 몇 건만 덮어 순간 변동에 서킷이 반응 | 크다 → 창에 옛 성공이 많아 지금의 실패가 희석, 늦게 열림 |
| `minimumNumberOfCalls` | 작다 → 새벽 1~2건 실패로 열림 (3-1의 함정) | 크다 → 저트래픽 시간대에는 사실상 서킷이 없음 |
| `failureRateThreshold` | 낮다 → 평상시 변동만으로 열림 | 높다 → 실패율 80%까지 참는 동안 스레드가 먼저 마름 |
| `slowCallDurationThreshold` | 짧다 → 정상적인 느린 요청이 느린 호출로 집계 | 길다(또는 타임아웃보다 큼) → 느린 호출을 아예 못 잡음 |
| `waitDurationInOpenState` | 짧다 → 플래핑, 회복 중인 상대에 반복 부하 | 길다 → 복구된 상대를 계속 차단, 기회 손실 |
| `permittedNumberOfCalls...` | 많다 → 탐침이 회복 중인 상대에 부하 | 적다 → 운 나쁜 한 건에 복구가 좌우됨 |

두 극단을 한 문장씩으로 요약하면 이렇다.

**과민(임계치 낮음/모수 작음)**: 일시적 네트워크 흔들림에 서킷이 열려 **멀쩡한 서비스를 우리가 차단**한다 — 자해가 된다.

**둔감(임계치 높음/모수 큼)**: 서킷이 열리기 전에 이미 스레드 풀이 고갈된다 — **있으나 마나 한 서킷**이 된다.

둘 중 어느 쪽이 더 위험한지는 대상의 중요도가 정한다. 비핵심 의존성(추천, 배지)에는 과민하게 잡아도 손해가 작으므로 공격적으로 짧은 타임아웃과 민감한 서킷을 건다. 핵심 의존성(결제)에는 오탐의 비용이 크므로 baseline을 충분히 관측한 뒤 보수적으로 잡는다. 이 판단의 근거가 되는 기능 중요도 분류는 15번 문서(`15-graceful-degradation-design.md`)의 주제다.

### 3-7. fallback — open일 때 무엇을 돌려줄 것인가

여기까지가 "언제 끊을지"의 튜닝이었다. 그런데 **끊은 다음에 무엇을 할지**를 정하지 않으면 서킷은 절반만 도입된 것이다.

open 상태의 기본 동작은 예외를 던지는 것이다. 그대로 두면 사용자에게 에러가 간다. 물론 3초 기다린 뒤 에러를 보는 것보다는 즉시 에러를 보는 편이 낫고 서버는 살아 있지만, **사용자 경험 관점에서는 여전히 실패**다. 그래서 실무에서는 fallback을 함께 설계하는 것이 사실상 필수다.

돌려줄 수 있는 것은 크게 세 종류다.

**캐시된 이전 값.** 조금 낡았지만 있는 값을 준다. 상품 가격, 추천 목록, 사용자 프로필처럼 몇 분 낡아도 치명적이지 않은 데이터에 쓴다. 얼마나 낡았는지를 함께 노출할지는 도메인 판단이다 — 재고 수량처럼 낡음이 오해를 만드는 데이터는 낡은 값을 주는 것 자체가 위험할 수 있다.

**기본값이나 축소된 응답.** 개인화 추천이 안 되면 비개인화 인기순을 준다. 리뷰 수를 못 가져오면 그 숫자만 화면에서 뺀다. **응답의 완성도를 낮춰 응답 자체는 성공시키는** 방식이다.

**나중에 처리하겠다는 접수.** 결제 승인을 지금 못 하면 주문을 "결제 대기"로 접수해 큐에 쌓고 복구 후 처리한다. 1-4 코드의 `payLater`가 이 유형이다. 기능을 "지금 완료"에서 "나중에 완료"로 낮추는 것이다.

**그런데 fallback 자체가 새 사고가 될 수 있다.** 이 부분을 말할 수 있어야 설계를 해 본 사람으로 보인다.

첫째, **fallback이 부하가 되는 경우.** 추천 fallback을 "실시간 DB 집계 쿼리로 인기순 계산"으로 만들어 두면, 서킷이 열리는 순간 **전체 트래픽이 그 쿼리로 몰린다.** 추천 서비스 장애가 DB 장애로 옮겨간 것이다. 그래서 **fallback은 원 경로보다 항상 싸야 한다** — 사전 계산해 캐시(가능하면 로컬 캐시)에 올려둔 정적 결과여야 한다. "전체 트래픽이 fallback으로 몰려도 버티는가"가 검수 기준이다.

둘째, **fallback이 실패하는 경우.** fallback 경로는 평상시에 실행되지 않는 코드다. 정작 장애 때 처음 실행되면서 자기 버그(직렬화 오류, 비어 있는 캐시, 권한 문제)로 실패하는 일이 흔하다. 그래서 fallback 체인의 마지막 단계는 **절대 실패할 수 없는 것**이어야 한다 — 빈 목록, 섹션 숨김처럼 외부 의존이 전혀 없는 것. 그리고 장애 주입 훈련으로 fallback 경로를 주기적으로 실제 실행해 봐야 믿을 수 있다.

셋째, **fallback이 성공해서 장애가 안 보이는 경우.** fallback이 잘 동작할수록 에러율 지표는 깨끗하다. 알림이 없으면 며칠씩 저하 운행을 모르고 지나간다(그동안 개인화 추천이 만들던 매출은 조용히 빠진다). 그래서 **서킷 open 이벤트와 fallback 동작 비율을 반드시 지표로 노출**하고 알림을 건다. "서킷 open = 장애 이벤트"로 다루는 것까지가 도입이다.

fallback의 종류·체인 설계·중요도 분류는 15번 문서(`15-graceful-degradation-design.md`)에서 본격적으로 다룬다. 여기서 붙잡을 것은 **"서킷은 차단 장치이고, 차단됐을 때 사용자에게 무엇을 줄지는 별도의 설계"**라는 분리다.

### 3-8. 서킷이 오히려 문제를 일으킬 때

서킷 브레이커는 장애를 막는 장치인데, 잘못 쓰면 스스로 장애를 만든다. 세 가지 유형이 실무에서 반복된다.

**① 상대가 복구됐는데 서킷이 닫히지 않는다.**

원인이 셋 있다. 첫째는 3-1에서 본 저트래픽 문제 — 탐침 10건을 모으는 데 시간이 오래 걸려 판정이 늦다. 둘째는 대기 시간이 너무 길게 잡혀 있어 애초에 탐침 기회가 드문 경우다.

셋째가 가장 찾기 어렵다. **커넥션 풀에 죽은 커넥션이 남아 있는 경우다.** 상대 서버가 재기동되면 우리 쪽 HTTP 커넥션 풀에 들어 있던 keep-alive 커넥션은 전부 상대편이 사라진 소켓이 된다. half-open 탐침이 그 죽은 커넥션을 집으면 상대가 멀쩡한데도 실패한다. 그러면 서킷은 다시 open이 되고, 다음 탐침도 같은 풀에서 커넥션을 집어 또 실패한다 — **상대는 살아 있는데 서킷은 영원히 안 닫히는** 상태다.

대응은 커넥션 쪽에 있다. 유휴 커넥션을 일정 시간 뒤 폐기하고(idle timeout), 대여 전에 유효성을 검증하고(일정 시간 이상 유휴였던 커넥션은 검사 후 사용), 서킷이 open으로 전이할 때 해당 대상의 커넥션 풀을 비우는 것이다. **서킷을 아무리 잘 튜닝해도 그 아래 계층이 거짓 실패를 만들면 판정이 무의미해진다.**

**② half-open의 시험 호출이 하필 실패해 복구가 지연된다.**

탐침 수를 1로 잡아 두면 복구가 단 한 건의 운에 걸린다. 그 한 건이 하필 무거운 파라미터였거나, 하필 상대의 GC pause 순간에 걸렸거나, 하필 위의 ①처럼 죽은 커넥션을 집었다면 서킷은 다시 open이 되고 대기 시간이 처음부터 다시 흐른다.

```text
대기 30초 → 탐침 1건 → 하필 실패 → 다시 OPEN
대기 30초 → 탐침 1건 → 하필 실패 → 다시 OPEN
...
상대는 첫 30초 뒤 이미 회복했지만 서킷은 5분째 열려 있다
```

대응은 두 가지다. **탐침 수를 늘려 운의 비중을 줄인다** — 10건 중 5건 미만 실패면 닫히는 구조는 한두 건의 불운을 흡수한다. 그리고 **무엇을 탐침으로 쓸지도 설계**다. 실사용 요청을 탐침으로 쓰면 그 사용자가 복구 실험의 피험자가 되므로, 가벼운 헬스체크성 호출을 별도로 보내 판단하는 구조를 두면 사용자 요청을 태우지 않고 회복을 확인할 수 있다.

**③ 서킷을 인스턴스별로 두어 판단이 인스턴스마다 갈린다.**

서킷 상태는 기본적으로 **각 서버 인스턴스의 로컬 메모리**에 있다. 각 인스턴스는 자기가 보낸 호출의 결과만 창에 담으므로, 10대가 있으면 서킷도 10개이고 판단도 10개다.

10대 중 3대만 열리면 어떤 증상이 나는가. **같은 기능이 새로고침할 때마다 성공하거나 실패한다.** 사용자에게는 재현되지 않는 간헐 장애로 보이고, CS에는 "될 때도 있고 안 될 때도 있어요"라는 재현 불가 티켓이 쌓인다. 지표는 평균으로 뭉개져 "실패율 30%"라는 숫자만 남고, 그 30%가 어디서 오는지는 보이지 않는다.

왜 이렇게 갈리는가. 로드밸런서가 라운드로빈이면 트래픽은 고를 것 같지만, 인스턴스마다 배포 시각이 다르고(워밍업 상태가 다르다), 붙어 있는 상대 인스턴스가 다르고, keep-alive 커넥션의 나이가 다르다. 실패 분포는 생각보다 쉽게 갈린다.

그렇다면 상태를 공유하면 되는가. **그것도 공짜가 아니다.** 상태를 Redis 같은 외부 저장소에 두면 매 호출마다 원격 왕복이 붙어 서킷 자체가 지연 요인이 되고, 그 저장소가 죽으면 **장애를 막는 장치가 새 장애 지점**이 된다. 그래서 실무의 답은 대개 공유가 아니라 다음 셋이다.

첫째, **인스턴스 수를 감안해 창 크기와 최소 호출 수를 정한다.** 전체 유입 300 TPS가 10대에 나뉘면 인스턴스당 30 TPS다. `minimumNumberOfCalls`는 전체 유입이 아니라 **인스턴스당 유입**을 기준으로 계산해야 한다.

둘째, **서킷 상태를 인스턴스별로 지표에 노출한다.** "몇 대가 열렸는지"가 보이면 위 증상이 즉시 진단된다. 3대만 열렸다면 그 3대에 공통된 무언가(같은 노드, 같은 AZ, 같은 배포 버전)를 찾는 것이 다음 단계다.

셋째, 판단 주체를 줄이는 방향으로 계층을 올린다. 서비스 메시나 사이드카 계층에서 서킷을 관리하면 애플리케이션 인스턴스 수와 무관하게 판단 지점이 통합된다. 복잡도가 올라가므로 이것도 트레이드오프다.

### 3-9. 타임아웃·재시도와의 관계

세 장치는 대체재가 아니라 **순서가 있는 한 세트**다. **타임아웃이 있어야 실패가 유한 시간 안에 판정되고**, 실패 판정이 있어야 **재시도와 서킷이 성립하며**(무엇을 세어 실패율을 계산할지가 정해진다), **서킷이 없으면 재시도가 이미 죽은 상대를 계속 두드린다.** 그래서 도입 순서도 타임아웃 → 재시도 → 서킷이다.

역할로 나누면 이렇다. 타임아웃은 "한 번의 호출을 얼마나 기다릴지"(개별 대기의 상한), 재시도는 "일시적 실패를 어떻게 흡수할지"(짧은 흔들림 대응), 서킷은 "지속적 장애일 때 호출 자체를 멈출지"(장애 국면 전환 감지)를 담당한다.

특히 **타임아웃 없는 호출에는 서킷이 성립하지 않는다.** 서킷은 "실패한 호출의 비율"로 판정하는데, 타임아웃이 없으면 응답이 안 오는 호출은 실패로도 성공으로도 판정되지 않고 영원히 진행 중이다. 판정되지 않은 호출은 창에 들어가지 못하므로 실패율이 올라가지 않고, 서킷은 열리지 않은 채 스레드는 다 마른다. **타임아웃은 서킷의 전제 조건**이다. (구간별 타임아웃 설계: 10번 문서 `10-timeout-layers-and-budget.md`)

배치 순서는 호출에 가까운 안쪽부터 **타임아웃 → 재시도 → 서킷**이 일반적이다. 서킷이 가장 바깥에 있어야 "재시도까지 다 해봤는데도 실패"가 서킷의 실패 1건으로 집계되고, 서킷이 열리면 재시도 자체가 차단된다. 반대로 서킷을 재시도 안쪽에 두면 서킷이 열렸는데도 재시도가 계속 두드리는 모순이 생긴다.

```text
[권고 배치]  서킷 ( 재시도 ( 타임아웃 ( 실제 호출 ) ) )

  서킷이 열려 있으면 재시도 루프에 진입조차 하지 않는다.
  서킷의 실패 1건 = "재시도까지 소진한 논리적 호출 1건의 실패".
```

여기서 라이브러리의 현실을 알아 두면 좋다. **Resilience4j의 기본 조합 순서는 이 권고와 반대로 Retry가 가장 바깥이다** — `Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( 호출 ) ) ) ) )`. 이 순서에서도 서킷이 열리면 각 재시도 시도가 즉시 `CallNotPermittedException`으로 떨어지므로 상대를 두드리지는 않는다. 다만 두 가지가 달라진다. 첫째, **재시도 루프 자체는 계속 돌므로** `CallNotPermittedException`을 재시도 대상에서 제외해야 한다. 둘째, **서킷의 집계 단위가 "논리적 호출"이 아니라 "시도"가 된다** — 재시도 3회면 실패 1건이 실패 3건으로 집계되어 서킷이 그만큼 민감해진다. 어느 쪽이 낫다고 단정하기보다, **집계 단위가 달라진다는 것을 알고 임계치를 그에 맞춰 잡는 것**이 요점이다. 순서를 바꾸고 싶으면 `*AspectOrder` 설정으로 조정한다.

## 4. 꼬리질문 대비 포인트

### "open 상태에서 들어온 요청은 어떻게 처리하나요?"

호출을 실행하지 않고 즉시 예외를 던진다. **"실행하지 않고"가 핵심이다** — 소켓을 열지 않으므로 스레드가 묶이지 않고, 그래서 1-2의 스레드 고갈이 멈춘다.

그대로 두면 사용자에게 에러가 가므로, 실무에서는 **fallback을 함께 설계**하는 것이 사실상 필수다 — 캐시된 이전 값 반환, 기본값(추천 실패 시 인기순), 나중에 처리하도록 큐에 적재("결제 대기 접수") 등. "서킷은 차단 장치이고, 차단됐을 때 사용자 경험을 뭘로 대체할지는 별도의 설계"라고 답하면 graceful degradation과 연결되어 좋은 인상을 준다.

여기에 한 겹 더 얹으면 좋다. **fallback은 원 경로보다 항상 싸야 한다.** fallback이 실시간 DB 집계라면 서킷이 열리는 순간 전체 트래픽이 DB로 몰려 장애가 옮겨간다. 사전 계산된 캐시가 답이고, 체인의 마지막 단계는 외부 의존이 없는 것(빈 목록, 섹션 숨김)이어야 한다.

### "느린 호출(slow call)은 왜 실패와 별도로 집계하나요?"

가장 위험한 장애 유형이 "죽진 않았는데 매우 느린" 상태이기 때문이다. HTTP 200을 반환하므로 실패율 지표에는 안 잡히지만, 호출당 스레드 점유 시간은 수십 배가 되어 스레드 풀 고갈로 이어진다. 그래서 실패율과 별개로 느린 호출 비율만으로도 서킷을 열 수 있게 되어 있다. **"성공/실패가 아니라 자원 점유 관점에서 보면 느린 성공은 실패다"**가 핵심 문장.

숫자로 뒷받침하면 더 좋다. 응답 100ms일 때 스레드 200개의 처리 상한은 초당 2,000건이지만, 3초로 느려지면 `200 ÷ 3 = 66.7`건으로 떨어진다. 전부 성공(200 OK)해도 처리량이 30분의 1이 된 것이므로, 성공률 100%인 채로 서비스가 마비된다.

그리고 `slowCallDurationThreshold`는 **타임아웃보다 작아야 의미가 있다.** 타임아웃이 2초인데 이 값이 3초면 느린 호출로 집계될 기회 자체가 없다 — 타임아웃이 먼저 터져 전부 실패로 잡힌다.

### "half-open에서 왜 일부 요청만 통과시키나요?"

회복 중인 서비스는 캐시가 비어 있고 커넥션 풀이 덜 차 있는 등 평상시보다 취약한 상태다. open → closed로 한 번에 전환하면 밀려 있던 전체 트래픽이 쏟아져 다시 쓰러진다(재장애). 탐침 몇 건으로 회복을 확인하고 나서 열어야 안전하다. 로드밸런서에 서버를 다시 붙일 때 warm-up 트래픽부터 흘리는 것과 같은 원리다.

반대 방향의 함정까지 말하면 깊이가 보인다. **탐침 수가 너무 적으면 복구가 운에 좌우된다.** 1건이면 그 한 건이 하필 실패해 다시 open이 되고 대기 시간이 리셋된다 — 상대는 이미 회복했는데 서킷만 몇 분씩 열려 있는 상태가 만들어진다. 10건 정도를 두어 실패율로 판정하게 하는 것이 안전하고, 저트래픽 대상에서는 그 10건을 모으는 데 걸리는 시간까지 계산해야 한다.

### "타임아웃·재시도와는 어떤 관계로 함께 쓰나요?"

셋은 대체재가 아니라 **역할이 다른 3종 세트**이고 **순서가 있다.** **타임아웃이 있어야 실패가 유한 시간 안에 판정되고**, 실패 판정이 있어야 **재시도와 서킷이 성립하며**, **서킷이 없으면 재시도가 이미 죽은 상대를 계속 두드린다.**

역할로 나누면 타임아웃은 "한 번의 호출을 얼마나 기다릴지"(개별 호출의 상한 방어), 재시도는 "일시적 실패를 어떻게 흡수할지"(짧은 흔들림 대응), 서킷은 "지속적 장애일 때 호출 자체를 멈출지"(장애 국면 전환 감지)를 담당한다.

배치 순서로는 호출에 가까운 안쪽부터 타임아웃 → 재시도 → 서킷이 일반적이다 — 서킷이 가장 바깥에 있어야 "재시도까지 다 해봤는데도 실패"가 서킷의 실패 1건으로 집계되고, 서킷이 열리면 재시도 자체가 차단된다. 반대로 서킷을 재시도 안쪽에 두면 서킷이 열렸는데도 재시도가 계속 두드리는 모순이 생긴다.

**타임아웃이 서킷의 전제 조건**이라는 점을 덧붙이면 좋다. 타임아웃이 없으면 응답 없는 호출이 실패로 판정되지 않아 창에 들어가지 못하고, 실패율이 올라가지 않아 서킷이 열리지 않는 채로 스레드가 마른다. 그리고 Resilience4j의 기본 조합 순서는 Retry가 가장 바깥이라 권고와 반대이므로, **서킷의 실패 집계 단위가 "논리적 호출"에서 "시도"로 바뀐다는 점**을 알고 임계치를 조정해야 한다는 것까지 말하면 라이브러리를 실제로 써 본 사람으로 보인다.

### "서킷 브레이커가 오히려 문제를 일으킨 경험이나 함정은?" (시니어 변별 포인트)

다섯 가지를 들 수 있다.

1. **인스턴스별 상태 불일치**: 서킷 상태는 기본적으로 서버 인스턴스별 로컬 메모리에 있다. 10대 중 3대만 서킷이 열리면 트래픽이 나머지 7대로 쏠리며 혼란이 생기고, "일부 사용자만 간헐 실패"라는 추적하기 어려운 증상이 된다. 상태를 공유하는 설계도 있지만 그만큼 복잡도가 올라가므로 트레이드오프다 — 외부 저장소를 두면 매 호출에 원격 왕복이 붙고, 그 저장소가 새 장애 지점이 된다. 실무에서는 `minimumNumberOfCalls`를 **인스턴스당 유입** 기준으로 계산하고, 서킷 상태를 인스턴스별로 지표에 노출하는 쪽이 현실적이다.
2. **과민 설정의 자해**: 배포 직후 워밍업 지연이나 순간적 GC pause로 느린 호출 비율이 튀어 서킷이 열리고, 멀쩡한 다운스트림을 우리가 차단해 매출 손실이 나는 사고. `minimumNumberOfCalls`와 관측된 baseline 없이 예제 설정값을 복사해 쓰면 이렇게 된다. 특히 저트래픽 시간대에 실패 1~2건으로 열리는 경우가 전형적이다.
3. **복구했는데 안 닫히는 서킷**: 상대가 재기동되면 우리 쪽 커넥션 풀의 keep-alive 커넥션은 전부 죽은 소켓이 된다. half-open 탐침이 그 커넥션을 집으면 상대가 멀쩡한데도 실패하고, 다음 탐침도 같은 풀에서 집어 또 실패한다. 서킷 튜닝이 아니라 **커넥션 검증·유휴 폐기·서킷 open 시 풀 비우기**로 풀어야 하는 문제다.
4. **운 나쁜 탐침이 복구를 늦춤**: 탐침 수 1건이면 복구 판정이 한 건의 운에 걸린다. 대기 30초 → 탐침 1건 실패 → 다시 open의 왕복이 반복되며, 상대가 이미 회복했는데도 몇 분씩 차단이 이어진다. 탐침 수를 늘려 실패율로 판정하게 하고, 사용자 요청 대신 별도의 가벼운 탐침 호출을 쓰는 것이 대응이다.
5. **서킷 open은 반드시 알림과 연동**: 서킷이 열리면 시스템은 조용히 fallback으로 동작하므로 겉보기에 멀쩡하다. 알림이 없으면 장애를 며칠씩 모르고 지나갈 수 있다 — "서킷 open = 장애 이벤트"로 모니터링에 노출하는 것까지가 도입이다. fallback 동작 비율도 함께 지표로 둔다.

## 한 줄 요약

서킷 브레이커는 실패율·느린 호출 비율이 임계치를 넘으면 호출을 차단해(closed→open) 내 스레드와 상대의 회복 시간을 지키고 — open에서는 호출조차 하지 않으므로 요청당 스레드 점유가 3초에서 0이 되어 스레드 200개가 초당 66건에 묶이는 붕괴(200 ÷ 3초)를 끊는다 — 대기 후 소량 탐침으로(half-open) 회복을 확인해 복귀하는 패턴이다. 설정값은 감이 아니라 대상 API의 평상시 트래픽량·실패율·p99를 근거로 잡아야 하며(특히 `minimumNumberOfCalls` 없이는 새벽 1건 실패로 열린다), 과민하면 정상 트래픽을 차단하는 자해, 둔감하면 있으나 마나가 되고, open일 때 무엇을 줄지(fallback)와 서킷 자신이 만드는 사고(안 닫히는 서킷, 운에 걸린 탐침, 인스턴스별로 갈리는 판단)까지 다루는 것이 운영 수준이다.
