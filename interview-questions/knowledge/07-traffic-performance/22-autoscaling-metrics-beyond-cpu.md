# 오토스케일링 지표 선택 — 병목 자원과 지표가 일치해야 스케일 아웃이 일어난다

> 핵심 관전 포인트: **오토스케일링 지표는 "서버가 힘든 정도"를 대변해야
> 하는데, CPU 사용률은 CPU가 병목일 때만 그 역할을 한다. 백엔드 API의
> 흔한 모습인 I/O bound 서비스(DB·외부 API 응답 대기가 대부분)는
> 스레드풀이 고갈돼 요청이 큐에 쌓여도 스레드들이 '대기 중'이라 CPU는
> 한가하다 — CPU 기준 오토스케일링은 서비스가 죽어가는데도 영원히
> 스케일 아웃을 안 한다. 대안은 병목 자원에 맞춘 지표다: 파드당 초당
> 요청 수(RPS), 동시 처리 중 요청 수(inflight)·스레드풀/커넥션 풀
> 사용률, 워커라면 큐 길이(lag). 좋은 지표의 조건은 부하에 비례해
> 오르고, 파드를 늘리면 내려가는 것이다.**

---

## 0. 질문 + 의도

**질문**: "오토스케일링 지표로 CPU 사용률이 부적합한 경우는? 대안 지표는 무엇인가요?"

**출제 의도**: I/O bound 서비스는 CPU가 낮은 채로 죽는다. HPA가 CPU
기준이면 스케일 아웃이 영원히 안 일어나는 상황 — 병목 자원과 스케일링
지표가 일치해야 함을 아는지 본다.

## 1. CPU가 부적합한 경우 — "CPU 20%인데 서비스는 죽어 있다"

오토스케일링의 논리는 단순하다: 지표가 임계값을 넘으면 서버를 늘린다.
이 논리가 성립하려면 **지표가 실제 포화도를 대변**해야 한다. CPU
사용률이 그 역할을 못 하는 대표적인 경우들:

### ① I/O bound 서비스 — 가장 흔하고 가장 치명적

전형적인 백엔드 API의 요청 처리 시간 대부분은 DB 쿼리, 외부 API 호출,
캐시 조회의 **응답 대기**다. 블로킹 서버라면 대기 중인 스레드는 CPU를
거의 안 쓴다. 트래픽이 몰리면 벌어지는 일:

```text
트래픽 증가 → 요청당 대기 시간이 긴 탓에 스레드가 빠르게 점유됨
→ 스레드풀 고갈 → 신규 요청이 큐에 쌓임 → p99 급증, 타임아웃
→ 그런데 스레드들은 '대기 중'이라 CPU는 20~30%
→ CPU 기준 오토스케일러: "한가하네" — 스케일 아웃 없음
→ 서비스는 죽어가는데 서버 대수는 그대로 (최악: 스케일 인까지 발동)
```

- 비유: 콜센터 상담원들이 전부 "고객 응답 대기 중"으로 통화 점유
  상태다. 전화는 계속 밀려오는데, "상담원들 목이 안 쉬었으니(CPU가
  낮으니) 증원 불필요"라고 판단하는 꼴이다. 봐야 할 것은 목 상태가
  아니라 **점유된 회선 수와 대기열 길이**다.

### ② CPU가 높지만 부하 때문이 아닌 경우 (반대 방향 오판)

JVM 서비스의 기동 직후 JIT 컴파일·클래스 로딩, GC 급증 구간은 실제
트래픽 부하와 무관하게 CPU를 태운다. 이때 CPU 기준 스케일러는 필요
없는 증설을 하고, 새로 뜬 파드가 또 워밍업 CPU를 태워 또 증설하는
연쇄 오판(플래핑)도 가능하다. 부하 신호와 노이즈가 섞이는 지표라는 뜻.

### ③ 큐 컨슈머/배치 워커 — 애초에 요청-응답 모델이 아님

Kafka 컨슈머 같은 워커는 자기 처리 속도만큼만 당겨 가므로 아무리
밀려도 CPU가 일정하다. 진짜 지표는 **처리가 유입을 못 따라가는
정도** — 즉 큐에 쌓인 미처리 양(lag)이다.

### ④ 정시 스파이크 — 지표 종류와 무관하게 반응형이 늦는 경우

수 초 만에 치솟는 트래픽은 어떤 지표든 "감지 → 증설 → 기동"의
리드타임(분 단위)보다 빠르다. 이건 지표 교체가 아니라 시각 기반
사전 증설(scheduled scaling)로 푸는 문제다 — 구분해서 말해야 한다.

## 2. 대안 지표 — 병목 자원에 맞춰 고른다

좋은 스케일링 지표의 조건 두 가지를 먼저 세우면 답이 정리된다:
**(a) 부하에 비례해 움직이고, (b) 파드를 늘리면 내려가야 한다.**
(b)가 무너지는 지표는 무한 증설을 유발한다(뒤 꼬리질문 참고).

### 파드당 초당 요청 수 (RPS) — 요청-응답 서비스의 기본기

부하 테스트로 "파드 1개가 목표 p99를 지키며 감당하는 RPS"를 실측해
두고, 파드당 RPS가 그 수준을 넘지 않게 대수를 조절한다. 부하에 정확히
비례하고, 파드를 늘리면 파드당 값이 즉시 내려가는 이상적인 성질을
가진다. 단, 요청별 비용 편차가 크면 "건수"가 부하를 왜곡할 수 있다.

### 동시 처리 중 요청 수(inflight) / 풀 사용률 — 포화를 직접 재는 지표

I/O bound 서비스의 실제 한계 자원은 스레드풀·커넥션 풀이다. 활성
스레드 비율, 동시 처리 중 요청 수, 커넥션 풀 대기자 수는 "밀린 일의
양"을 직접 나타내므로 CPU가 놓치는 포화를 정확히 잡는다.

### 큐 길이 / 컨슈머 lag — 워커의 정답

워커는 외부 지표(큐에 쌓인 메시지 수, lag)로 스케일한다. "lag이
늘어나는 추세면 컨슈머 증설"이 자연스러운 규칙이 된다. Kubernetes라면
HPA의 external metric이나 KEDA 같은 이벤트 기반 스케일러가 이 자리다.

```yaml
# Before: I/O bound API에 CPU 기준 HPA — 스케일 아웃이 영원히 안 일어남
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70   # 문제: 스레드풀 고갈 시에도 CPU는 20~30%
                                   #       → 임계 미달 → 증설 없음 → 타임아웃 지속

# After: 병목을 대변하는 지표 — 파드당 RPS(custom metric) 기준
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  metrics:
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second   # 앱이 노출, 어댑터로 수집
        target:
          type: AverageValue
          averageValue: "80"   # 부하 테스트 실측: 파드당 한계 RPS의 약 70~80% 선
  # 효과: 트래픽 증가 → 파드당 RPS 상승 → 증설 → 파드당 RPS 하락 (수렴)
```

(가산점 포인트) 지연시간(p99)은 스케일링 지표로는 함정이 있다.
포화의 **후행 지표**라 이미 나빠진 뒤에 반응하고, DB 병목처럼 증설로
안 내려가는 원인일 때 오작동한다. p99는 알람·SLO 감시용으로 두고,
스케일링은 선행성 있는 지표(RPS, inflight, lag)로 거는 게 정석이다.

## 3. 실무 사례 — "트래픽 2배인데 HPA는 잠잠했다"

외부 결제사 API를 호출하는 서비스에서 결제사 응답이 평소 100ms →
2초로 느려진 상황. 유입 트래픽은 그대로인데 요청당 점유 시간이 20배가
되니 스레드풀이 순식간에 고갈되고 p99가 치솟았다. CPU는 오히려
떨어졌다(스레드 전원이 대기 중이라). CPU 기준 HPA는 아무것도 하지
않았고, 장애는 "오토스케일링이 있는데 왜 안 늘었지?"라는 혼란 속에
길어졌다.

이 사례의 교훈은 둘이다. ① 스케일링 지표를 inflight/풀 사용률로
바꿨다면 증설이 발동했을 것이다. ② 그러나 **이 장애의 근본 원인은
용량이 아니라 느린 다운스트림**이다 — 증설은 결제사로 향하는 동시
호출만 늘려 상대를 더 누를 수 있다. 올바른 1차 방어는 타임아웃·서킷
브레이커이고, 스케일링은 그 다음이다. "지표를 고치면 끝"이 아니라
"이 부하가 증설로 풀리는 종류인가"까지 묻는 게 이 주제의 끝이다.

## 4. 꼬리질문 대비 포인트

### "좋은 스케일링 지표의 조건을 일반화하면요?"

세 가지로 답한다. ① **부하 비례** — 트래픽이 늘면 지표도 늘어야
증설 신호가 된다. ② **증설 반응성** — 파드를 늘리면 지표가 내려가야
피드백 루프가 수렴한다(파드당 평균으로 계산되는 지표가 이 성질을
갖는다). ③ **선행성과 안정성** — 포화 전에 움직이되 노이즈(GC,
워밍업)에 출렁이지 않아야 한다. CPU는 CPU bound 워크로드에서만 세
조건을 만족하는 지표다 — "CPU가 나쁜 지표"가 아니라 "병목과 지표의
불일치가 문제"라고 정리하면 정확하다.

### "스케일 아웃을 했는데도 지표가 안 내려가면 어떻게 되나요?" (시니어 변별 포인트)

조건 (b)의 붕괴 — **병목이 파드 바깥(DB, 외부 API)에 있는 경우**다.
파드를 늘려도 지연·inflight가 안 내려가니 스케일러는 계속 증설하고,
늘어난 파드들은 DB 커넥션과 동시 쿼리만 키워 병목을 **더 악화**시키는
악순환이 된다. 방어는 ① max replicas를 반드시 설정해 폭주를 막고,
② "증설했는데 지표 불변"을 병목이 바깥에 있다는 신호로 읽고 알람을
걸며, ③ 근본 대응은 증설이 아니라 병목 계층 보호(캐시, 커넥션 풀
한계, 서킷 브레이커)임을 아는 것. "스케일 아웃이 만능이 아니라
병목을 이동시킬 뿐"이라는 관점이 시니어 변별점이다.

### "메모리 사용률은 스케일링 지표로 어떤가요?"

대체로 부적합하다. JVM 같은 런타임은 확보한 힙을 OS에 잘 돌려주지
않아 메모리 사용률이 부하와 무관하게 높게 유지되고, 파드를 늘려도
기존 파드의 메모리는 안 내려가서 조건 (b)를 어긴다. 메모리는 스케일링
신호가 아니라 리소스 한계(requests/limits) 설정과 누수 감시의
영역으로 두는 게 맞다.

### "스케일 인은 어떻게 다루나요? 늘릴 때와 같은 기준인가요?"

비대칭으로 간다. 스케일 아웃은 공격적으로(장애 예방), 스케일 인은
보수적으로(진동 방지). 지표가 임계 근처에서 오르내리면 증설-축소를
반복하는 플래핑이 생기므로 안정화 시간(축소 전 일정 시간 관찰)을
두고, 축소 시엔 진행 중 요청을 마저 처리하는 graceful shutdown이
전제돼야 한다. 정시 스파이크 뒤의 2차 파도까지 고려해 천천히 줄인다.

### "반응형 스케일링으로 못 막는 스파이크는 어떻게 하나요?"

지표 선택과 별개의 축임을 짚는다. 수 초 만에 치솟는 정시
스파이크(신작 공개, 이벤트 오픈)는 어떤 지표를 써도 리드타임 때문에
늦는다 — 시각 기반 사전 증설(scheduled scaling)로 미리 용량을 만들고,
반응형은 예측을 벗어난 초과분 추적용으로, 그마저 넘치면 load
shedding이 마지막 방어선이다. "지표 교체 / 사전 증설 / 방어선"이
서로 다른 문제를 푸는 세 계층이라고 구분하면 완결된다.

## 한 줄 요약

오토스케일링 지표는 병목 자원과 일치해야 한다 — I/O bound 서비스는
CPU가 한가한 채로 죽으므로 CPU 기준 스케일링은 발동하지 않고, 대안은
파드당 RPS·동시 처리 수(inflight)·풀 사용률·큐 lag처럼 "부하에
비례하고 증설로 내려가는" 지표이며, 증설해도 안 내려가는 지표는
병목이 파드 바깥(DB·외부 API)에 있다는 신호라는 것까지 읽어야 한다.
