# 오토스케일링 지표 선택 — 병목 자원과 지표가 일치해야 스케일 아웃이 일어난다

> 핵심 관전 포인트: **오토스케일링 지표는 "서버가 힘든 정도"를 대변해야 하는데, CPU 사용률은 CPU가 병목일 때만 그 역할을 한다. 좋은 지표의 조건은 두 개다 — ① 부하가 오르면 지표가 오른다(포화를 대변한다), ② 파드를 늘리면 지표가 내려간다(증설이 실제로 그 지표를 해소한다). 블로킹 I/O에서 응답을 기다리는 스레드는 커널의 대기 상태에 들어가 CPU를 전혀 쓰지 않으므로, I/O bound 서비스는 스레드 200개가 전부 점유되고 큐가 밀려도 CPU가 20%로 한가하게 보인다 — 조건 ①이 깨진다. 그리고 HPA의 목표 대수는 `ceil(현재 파드 수 × 현재 지표 ÷ 목표 지표)`이므로, CPU 41.7%에 목표 70%를 두면 4파드 → 3파드로 **줄이는** 계산이 나온다. 대안은 병목 자원에 맞춘 지표다: 파드당 초당 요청 수(RPS), 동시 처리 중 요청 수(in-flight)·스레드풀/커넥션 풀 사용률, 워커라면 큐 길이(lag). 조건 ②가 깨지는 경우가 시니어 변별 지점이다 — 컨슈머 lag은 파티션 수가 상한이면 컨슈머를 늘려도 안 내려가고, 병목이 DB나 외부 API에 있으면 파드를 늘려도 지표가 그대로여서 스케일러가 무한히 늘리며 늘어난 파드가 각자 커넥션 풀을 들고 뒷단을 더 때린다. 그래서 최대 파드 수 상한은 편의 기능이 아니라 필수 안전장치다. 메모리는 두 조건 모두를 어기므로 스케일링 지표가 아니라 limit과 알람의 대상이고, 스케일 인은 재증설에 분 단위가 걸린다는 비대칭 때문에 안정화 창을 길게 둬야 한다.**

---

## 0. 질문 + 의도

**질문**: "오토스케일링 지표로 CPU 사용률이 부적합한 경우는? 대안 지표는 무엇인가요?"

**출제 의도**: I/O bound 서비스는 CPU가 낮은 채로 죽는다. HPA가 CPU 기준이면 스케일 아웃이 영원히 안 일어나는 상황 — 병목 자원과 스케일링 지표가 일치해야 함을 아는지 본다.

## 1. 판정 기준을 먼저 세운다 — 좋은 지표의 두 조건

이 질문은 "CPU가 나쁘다"로 끝나지 않는다. **어떤 지표가 좋은 지표인지 판정할 기준을 먼저 세워야** CPU가 왜 어떤 워크로드에서는 잘 동작하고 어떤 워크로드에서는 서비스를 죽이는지 설명할 수 있다. 그래서 이 절은 기준을 먼저 만들고, 그 기준으로 CPU를 평가한다.

### 1-1. 전제 지식 — I/O bound와 CPU bound

**I/O bound**는 **CPU를 실제로 쓰는 시간보다 외부(DB·API·디스크)의 응답을 기다리는 시간이 훨씬 긴 작업**을 말한다. "I/O에 묶여 있다(bound)"는 뜻이고, 이때 성능을 결정하는 것은 CPU 속도가 아니라 기다림의 길이와 동시에 기다릴 수 있는 개수다.

반대로 **CPU bound**는 **일하는 시간의 대부분을 실제 계산에 쓰는 작업**이다. 이미지 리사이징, 암호화, 대량 정렬, 직렬화가 그렇다. 여기서는 코어를 더 주면 더 빨라지고, CPU 사용률이 곧 포화도다.

Spring으로 만드는 전형적인 조회·주문 API는 거의 예외 없이 I/O bound다. 요청 하나가 하는 일은 "DB에 물어보고, 캐시에 물어보고, 다른 팀 API에 물어보고, 그 결과를 JSON으로 조립"이며 계산 자체는 별로 없다. **이 문서의 모든 이야기는 그 사실 위에 서 있다.**

### 1-2. 핵심 인과 — 왜 스레드가 200개 다 차 있는데 CPU는 20%인가

이것이 이 문서 전체의 토대다. 여기가 흐릿하면 뒤의 모든 주장이 "그렇다더라"가 된다.

**블로킹 I/O에서 응답을 기다리는 스레드는 CPU를 전혀 쓰지 않는다.** 자바의 `socket.read()`처럼 블로킹 호출을 하면, 그 스레드는 커널에게 "데이터가 오면 깨워 달라"고 등록하고 **대기 상태(blocked/waiting)**로 들어간다. 대기 상태의 스레드는 CPU 스케줄러의 실행 대기열에서 빠져 있으므로, 코어를 한 조각도 배정받지 않는다. 바쁘게 확인하며 도는 것(폴링)이 아니라 아예 잠들어 있는 것이다.

그래서 **"스레드를 점유하고 있다"와 "CPU를 쓰고 있다"는 전혀 다른 사실**이 된다. 스레드는 요청이 시작될 때 붙잡히고 응답을 다 쓸 때까지 반납되지 않지만, 그 사이에 CPU를 쓰는 구간은 일부뿐이다.

17번 문서에 나온 요청 한 건의 타임라인을 같은 숫자로 다시 가져와, **이 중 CPU 사용률에 반영되는 구간이 어디인지**를 표시해 보자.

```
[요청 1건 — 전체 응답시간 300ms]

     a  요청 파싱·인증·검증           0 ~  20ms   ( 20ms)   CPU를 쓴다
     b  비즈니스 로직 (CPU 연산)      20 ~  40ms   ( 20ms)   CPU를 쓴다
     c  DB 트랜잭션 (SELECT + UPDATE) 40 ~  90ms   ( 50ms)   기다린다
     d  외부 결제 API 호출 대기       90 ~ 290ms   (200ms)   기다린다
     e  응답 직렬화 + 로깅           290 ~ 300ms   ( 10ms)   CPU를 쓴다

  같은 시간축 위에서 (한 칸 = 5ms, 왼쪽 끝 = 0ms, 오른쪽 끝 = 300ms)

  ============================================================   톰캣 스레드 점유 (a~e 전부)
  ########..................................................##   CPU를 쓰는 구간 (a+b, e)
  ........##################################################..   기다리는 구간 (c, d)
  │       │                                                 │ │
  0ms   40ms                                            290ms 300ms
          └──── 이 250ms 동안 스레드는 커널의 대기 상태에 있고,
                CPU 사용률 계산에 1ms도 기여하지 않는다.
```

**톰캣 스레드는 300ms 전 구간을 점유한다.** 반면 **CPU에 반영되는 구간은 a + b + e = 20 + 20 + 10 = 50ms뿐이다.** 나머지 250ms는 c와 d의 대기이고, 그 시간 동안 이 스레드는 CPU 사용률 계산에 1ms도 기여하지 않는다.

이 비율에 이름을 붙여 두면 계산이 쉬워진다. **점유 시간 중 실제로 CPU를 쓰는 시간의 비율**이다.

```
CPU 사용 비율 = 요청당 CPU 시간 ÷ 요청당 스레드 점유 시간
              = 50ms ÷ 300ms
              = 0.1667  (6분의 1)
```

**즉 스레드 하나가 100% 점유돼 있어도, 그 스레드가 만드는 CPU 수요는 코어 하나의 6분의 1뿐이다.**

이제 파드 하나를 놓고 두 값을 비교해 보자. 파드 스펙을 **코어 8개, 톰캣 최대 스레드 200개**로 두겠다.

```
스레드 200개가 전부 점유된 순간, 그중 실제로 CPU에서 돌고 있는 스레드 수
  = 200개 × 0.1667 = 33.3개

이 파드의 코어는 8개다.
  -> 33.3 > 8 이므로, 스레드 200개가 다 차기 전에 CPU가 먼저 100%에 닿는다.
```

**여기서 일반 규칙이 나온다.** 두 값 중 작은 쪽이 먼저 마르는 자원이다.

```
① CPU가 먼저 마르는 지점의 처리량   = 코어 수 ÷ 요청당 CPU 시간
② 스레드가 먼저 마르는 지점의 처리량 = 스레드 수 ÷ 요청당 점유 시간(W)

위 요청(코어 8, 스레드 200, CPU 50ms, W 300ms)이라면
  ① 8 ÷ 0.05초 = 160건/초     <- 여기서 CPU 100%
  ② 200 ÷ 0.3초 = 666.7건/초  <- 여기서 스레드 만석

  160 < 666.7 이므로 CPU가 먼저 마른다.
  (검산: 160건/초에서의 스레드 점유 = 160 × 0.3 = 48개. 200개 중 24%뿐이다.)
```

**이 워크로드에서는 CPU 기준 HPA가 잘 동작한다.** "CPU가 나쁜 지표"라고 외우면 이 경우를 설명할 수 없다. 정확한 명제는 **"병목과 지표가 어긋나면 문제"**다.

그러면 처음의 질문 — "스레드가 200개 다 차 있는데 CPU는 20%"는 언제 벌어지는가. 같은 식을 뒤집으면 조건이 나온다.

```
스레드가 먼저 마르려면  스레드 수 × CPU 사용 비율 < 코어 수

  200 × (요청당 CPU 시간 ÷ 0.3초) < 8
  요청당 CPU 시간 < 8 × 0.3 ÷ 200 = 0.012초 = 12ms
```

**요청당 CPU 시간이 12ms보다 작으면 스레드가 먼저 마르고, 그 순간 CPU는 100%에 못 미친다.** 실제 값을 넣어 확인해 보자. 조회 결과를 거의 그대로 조립해 내려주는 얇은 API가 있고, 전체 300ms 중 CPU가 2ms라고 하자.

```
CPU 사용 비율 = 2ms ÷ 300ms = 0.00667
스레드 200개 만석 시 CPU 수요 = 200 × 0.00667 = 1.33 코어
CPU 사용률 = 1.33 ÷ 8 = 0.167 = 16.7%

검산: 이때 처리량은 200 ÷ 0.3 = 666.7건/초이고,
      CPU 수요는 666.7 × 0.002초 = 1.33 코어초/초 -> 같은 값이다.
```

**스레드 사용률 100%, CPU 사용률 16.7%.** 이것이 "CPU 20%인데 서비스는 죽어 있다"의 정확한 산수다. 이 상태에서 신규 요청은 스레드를 못 얻어 큐에 쌓이고, p99가 치솟고, 타임아웃이 나는데, CPU 그래프는 평온하다.

비유를 하나 붙이면 감각이 잡힌다. **콜센터 상담원들이 전부 "고객 응답 대기 중"으로 통화를 점유하고 있는 상태다.** 전화는 계속 밀려오는데 "상담원들 목이 안 쉬었으니(CPU가 낮으니) 증원 불필요"라고 판단하는 꼴이다. 봐야 할 것은 목 상태가 아니라 **점유된 회선 수와 대기열 길이**다.

### 1-3. 좋은 지표의 두 조건

1-2에서 본 것을 일반화하면 스케일링 지표의 합격 기준이 된다. 조건은 두 개다.

**조건 ① 부하가 오르면 지표가 오른다 — 포화를 대변한다.** 트래픽이 늘어 서버가 힘들어질 때 지표가 함께 움직여야 증설 신호가 된다. 반대로 부하와 무관하게 오르는 값(GC 중의 CPU, 아직 회수되지 않은 힙)은 노이즈를 증설 신호로 오인하게 만든다.

**조건 ② 파드를 늘리면 지표가 내려간다 — 스케일링이 실제로 그 지표를 해소한다.** 이 조건이 더 중요하고, 실무에서 더 자주 깨지고, 깨졌을 때 피해가 크다. 오토스케일링은 **피드백 루프**다 — 지표를 보고 대수를 바꾸고, 바뀐 대수가 지표를 되돌린다. 늘려도 지표가 안 내려가면 이 루프에 종점이 없어 **스케일러가 상한까지 무한히 늘린다.**

두 조건을 함께 놓으면 왜 대부분의 좋은 지표가 **"파드당 평균"** 형태인지가 설명된다. 총량 지표(전체 RPS, 전체 큐 길이)는 파드를 늘려도 값이 변하지 않으므로 조건 ②를 구조적으로 만족하지 못한다. 반면 파드당 평균은 분모가 파드 수이므로 **늘리면 반드시 내려간다.**

| 지표 | 조건 ① 부하에 따라 오르는가 | 조건 ② 증설하면 내려가는가 |
|---|---|---|
| CPU 사용률 (CPU bound 워크로드) | 예 | 예 |
| CPU 사용률 (I/O bound 워크로드) | **아니오** — 스레드가 먼저 마른다 | 예 |
| 파드당 RPS | 예 | 예 |
| 파드당 in-flight / 풀 사용률 | 예 | 예 |
| 컨슈머 lag (파티션 여유 있음) | 예 | 예 |
| 컨슈머 lag (파티션 수가 상한) | 예 | **아니오** — 2-5 |
| p99 지연 (병목이 파드 안) | 예 (후행) | 예 |
| p99 지연 (병목이 DB·외부 API) | 예 | **아니오** — 2-5 |
| 메모리 사용률 (JVM) | **아니오** | **아니오** — 2-6 |

이 표가 이 문서의 채점표다. 뒤에 나오는 모든 지표를 이 두 칸으로 평가한다.

### 1-4. HPA는 목표 대수를 어떻게 계산하는가 — 식과 검산

지표가 왜 "파드당" 값이어야 하는지, 목표값이 왜 곧 운영 사용률인지는 **스케일러가 실제로 돌리는 계산식**을 보면 한 번에 이해된다. 쿠버네티스 HPA의 식은 이것이다.

```
원하는 파드 수 = ceil( 현재 파드 수 × 현재 지표값 ÷ 목표 지표값 )

ceil은 소수점을 올리는 함수다. 파드를 0.4개 띄울 수는 없으므로 항상 올린다.
```

식이 이렇게 생긴 이유는 단순하다. **"지표가 파드 수에 반비례한다"는 가정** 위에 세운 비례식이기 때문이다. 파드당 RPS가 지금 150이고 목표가 100이라면 파드를 1.5배로 늘리면 파드당 값이 100이 된다 — 그 1.5배를 그대로 곱한 것이다.

숫자로 세 번 돌려 보자.

```
[예 1: 증설] 현재 4파드, 파드당 RPS 150, 목표 100
  4 × (150 ÷ 100) = 4 × 1.5 = 6.0  ->  ceil(6.0) = 6파드

  검산: 전체 유입 = 4파드 × 150 = 600 RPS
        6파드에 고르게 분배되면 600 ÷ 6 = 100 RPS/파드  -> 목표에 정확히 도달

[예 2: 큰 증설] 현재 6파드, 파드당 RPS 260, 목표 100
  6 × (260 ÷ 100) = 6 × 2.6 = 15.6  ->  ceil(15.6) = 16파드

  검산: 전체 유입 = 6 × 260 = 1,560 RPS
        1,560 ÷ 16 = 97.5 RPS/파드  -> 목표 100 이하. ceil 덕분에 살짝 여유가 남는다.

[예 3: 축소] 현재 16파드, 파드당 RPS 40, 목표 100
  16 × (40 ÷ 100) = 16 × 0.4 = 6.4  ->  ceil(6.4) = 7파드

  검산: 전체 유입 = 16 × 40 = 640 RPS
        640 ÷ 7 = 91.4 RPS/파드  -> 목표 이하
```

이 식에서 세 가지가 읽힌다.

**첫째, 지표는 반드시 "파드당" 값이어야 한다.** 식의 분자에 `현재 파드 수 × 현재 지표값`이 들어 있는데, 지표가 이미 전체 총량이면 파드 수를 한 번 더 곱하는 셈이 되어 계산이 완전히 틀어진다. HPA에서 `type: Pods`와 `AverageValue`를 쓰는 이유가 이것이다.

**둘째, 목표 지표값은 곧 "우리가 운영하려는 사용률"이다.** 루프가 수렴하면 실제 지표값이 목표값 근처에 머물게 되므로, 목표값을 물리 한계에 붙여 잡으면 사용률 100% 운영이 된다. 그러면 안 되는 이유는 01·17번 문서의 사용률 표과 정확히 같은 근거다 — 응답시간은 사용률 ρ에 대해 `1/(1−ρ)` 배로 자라므로 ρ = 0.9에서 10배, 0.95에서 20배, 0.99에서 100배가 된다. **그래서 목표값은 물리 한계의 70~80% 선에 둔다.** 스레드 200개인 파드의 in-flight 목표를 140(= 200 × 0.7)으로 잡는 것이 그 뜻이다.

**셋째, 지표를 잘못 고르면 이 식이 반대 방향으로 답을 낸다.** 1-2의 얇은 API가 스레드 만석에 CPU 16.7%인 상태를 CPU 기준 HPA에 넣어 보자.

```
현재 4파드, CPU 사용률 16.7%, 목표 70%
  4 × (16.7 ÷ 70) = 4 × 0.239 = 0.95  ->  ceil(0.95) = 1파드
```

**스레드가 만석이고 큐가 밀려 타임아웃이 나는 중에, 스케일러는 4파드를 1파드로 줄이라고 계산한다.** `minReplicas`가 없으면 실제로 줄인다. "증설이 안 일어난다"보다 한 걸음 더 나쁜 결과이고, 이것이 원래 질문의 "최악의 경우"다.

(가산점 포인트) HPA에는 **허용 오차**가 있어 현재 지표와 목표의 차이가 기본 10% 이내면 대수를 바꾸지 않는다. 임계 근처에서 1대씩 오르내리는 진동을 막기 위한 장치다. 그래서 목표값을 물리 한계에 너무 붙여 잡으면 "오차 범위 안이라 아무것도 안 하는" 구간이 위험 구간과 겹치게 된다.

### 1-5. 그래서 CPU가 부적합한 네 경우

이제 기준이 있으니 사례를 평가할 수 있다.

**① I/O bound 서비스 — 가장 흔하고 가장 치명적 (조건 ① 위반).** 1-2에서 산수로 본 그대로다. 트래픽이 몰릴 때 벌어지는 일을 시간 순으로 놓으면 이렇다.

```text
트래픽 증가 → 요청당 대기 시간이 긴 탓에 스레드가 빠르게 점유됨
→ 스레드풀 고갈 → 신규 요청이 큐에 쌓임 → p99 급증, 타임아웃
→ 그런데 스레드들은 대기 상태라 CPU는 20~30%
→ CPU 기준 오토스케일러: "한가하네" — 스케일 아웃 없음
→ 서비스는 죽어가는데 서버 대수는 그대로
   (최악: 1-4의 계산대로 스케일 인까지 발동)
```

**② CPU가 높지만 부하 때문이 아닌 경우 — 반대 방향 오판 (조건 ① 위반).** JVM 서비스의 기동 직후 JIT 컴파일·클래스 로딩 구간, 그리고 GC가 몰아서 도는 구간은 **실제 트래픽 부하와 무관하게** CPU를 태운다. 조건 ①은 "부하가 오르면 지표가 오른다"인데, 이 경우는 그 역 — "지표가 올랐는데 부하는 그대로"다.

이때 CPU 기준 스케일러는 필요 없는 증설을 하고, **새로 뜬 파드가 또 워밍업 CPU를 태워 또 증설을 부르는 연쇄 오판**이 가능하다. 부하 신호와 노이즈가 같은 지표에 섞여 있다는 뜻이고, 이 진동을 **플래핑(flapping)**이라고 부른다 — 여닫이문이 계속 펄럭이는 모양에서 온 이름이다.

**③ 큐 컨슈머·배치 워커 — 애초에 요청-응답 모델이 아니다.** Kafka 컨슈머 같은 워커는 밀려 있는 양과 무관하게 **자기 처리 속도만큼만 당겨 간다.** 유입이 10배가 되어도 컨슈머는 똑같은 속도로 폴링하므로 CPU가 거의 변하지 않는다. 요청-응답 서비스에서는 "밀린 일"이 스레드 점유와 큐로 나타나지만, 워커에서는 **브로커 쪽에 쌓인 미처리 양(lag)**으로만 나타난다. 지표를 서버 안에서 찾을 수 없는 구조다.

**④ 정시 스파이크 — 지표 종류와 무관하게 반응형이 늦는 경우.** 수 초 만에 치솟는 트래픽은 어떤 지표를 쓰든 "감지 → 판단 → 증설 → 기동 → 워밍업"의 리드타임보다 빠르다. 이건 **지표 교체로 풀리는 문제가 아니라** 시각 기반 사전 증설(scheduled scaling)로 푸는 문제다. 왜 리드타임이 필연적으로 분 단위인지는 2-8에서 단계로 분해하고, 사전 증설의 설계와 런북은 13번 문서에서 다룬다. **면접에서는 이 축을 반드시 구분해서 말해야 한다** — 지표 문제와 리드타임 문제를 섞으면 "그럼 지표를 바꾸면 되는 거 아닌가"라는 잘못된 결론에 도달한다.

## 2. 대안 지표 — 병목 자원에 맞춰 고르고, 두 조건으로 검증한다

### 2-1. 21번 문서와 무엇이 다른가 — 버릴지 판단하는 지표 vs 늘릴지 판단하는 지표

21번 문서에서 이미 과부하 감지 지표(큐 길이, 큐 대기 시간, 풀 사용률, p99, in-flight 수)를 다뤘고, CPU가 부적합한 두 이유도 거기서 짚었다. **지표 목록이 겹치므로 "같은 이야기 아닌가"라고 생각하기 쉽지만, 목적이 다르고 그래서 임계값이 달라야 한다.** 이 차이를 말할 수 있는지가 두 주제를 따로 이해했는지를 가른다.

**목적이 다르다.** 21번의 지표는 **"지금 도착한 이 요청을 받을지 버릴지"**를 밀리초 안에 결정한다. 22번의 지표는 **"몇 분 뒤에 필요한 파드 수가 몇인지"**를 결정한다. 하나는 개별 요청에 대한 즉시 판정이고, 다른 하나는 시스템 규모에 대한 예약이다.

**그래서 관측 창이 다르다.** shedding은 순간값을 봐야 한다 — 지금 in-flight가 한계에 붙어 있는데 "최근 1분 평균은 괜찮다"고 받아 주면 그 요청은 죽는다. 반대로 스케일링은 순간값으로 판단하면 안 된다 — 순간 스파이크마다 대수를 바꾸면 1-5 ②의 플래핑이 된다. 수십 초 창의 평균을 봐야 한다.

**결정적으로, 임계값이 달라야 한다.** 이유는 두 임계가 시스템에서 하는 역할이 다르기 때문이다.

**스케일링 목표값은 "정상 운영점"이다.** 1-4에서 본 대로 피드백 루프가 그 값으로 수렴하므로, 이 값은 **평상시에 지표가 머물러 있어야 하는 자리**다. 그래서 여유율을 포함한 값 — 물리 한계의 70% 선 — 이어야 한다.

**shedding 임계는 "최후 방어선"이다.** 그 값을 넘었다는 것은 이미 비정상이라는 뜻이고, 넘으면 요청을 버리기 시작한다. 그래서 포화 직전 — 물리 한계의 90% 선 — 에 둔다.

두 임계를 같은 값으로 두면 어느 쪽으로든 고장난다.

```
[두 임계를 모두 140(70%)에 두면]
  평상시에 지표가 140 근처에 머무는 것이 정상인데, 그 값에서 shedding이 켜진다.
  -> 평상시에 요청을 버린다. shedding이 rate limiting처럼 상시 발동한다.

[두 임계를 모두 180(90%)에 두면]
  스케일링 목표가 180이므로 사용률 0.9로 운영된다.
  -> 01·17번 문서의 표: ρ = 0.9에서 응답시간이 10배.
     평상시 p99가 이미 무너진 상태로 운영하는 셈이다.

[올바른 배치]
  스레드 200개 파드에서

    스케일링 목표 140  <  degradation 발동 160  <  shedding 임계 180  <  물리 한계 200
        (ρ 0.70)              (ρ 0.80)              (ρ 0.90)            (ρ 1.00)

  ① 140을 넘으면 스케일러가 파드를 늘리기 시작한다 (수 분 걸린다)
  ② 늘어나는 동안 160을 넘으면 비핵심 기능을 먼저 저하시켜 유입 부담을 줄인다 (15번 문서)
  ③ 그래도 180을 넘으면 우선순위 낮은 요청부터 버린다 (21번 문서)
  ④ 200은 물리 한계 — 여기 닿으면 선택권 없이 전부 대기한다
```

이 계단의 기준점 200은 **스레드 수**다. 즉 이 예는 1-2의 얇은 API처럼 **스레드가 먼저 마르는 워크로드**를 전제한 것이다. CPU가 먼저 마르는 워크로드라면 같은 계단을 CPU 포화 지점에서 역산해야 한다 — 그 계산은 2-3에서 다룬다.

**이 계단이 왜 이 순서인가가 핵심이다.** 스케일링은 가장 싸지만 가장 느리고(분 단위), degradation은 즉시 효과가 있지만 기능 품질을 깎고, shedding은 즉시 효과가 있지만 일부 사용자를 실패시킨다. **싸고 느린 것부터 켜고, 비싸고 빠른 것을 뒤에 둔다.** 그리고 degradation이 shedding보다 앞인 이유는 15번 문서의 논지 그대로다 — 비핵심 기능을 선제적으로 저하시켜 두면 그만큼 자원이 풀려서 **버려야 하는 요청의 양 자체가 줄어든다.**

### 2-2. 파드당 초당 요청 수(RPS) — 요청-응답 서비스의 기본기

부하 테스트로 **"파드 1개가 목표 p99를 지키며 감당하는 RPS"**를 실측해 두고, 파드당 RPS가 그 수준을 넘지 않게 대수를 조절한다. 그 실측을 어떻게 하는지는 07번 문서(부하 테스트 설계)에서 다룬다.

두 조건으로 평가해 보자. **조건 ①**: 트래픽이 늘면 파드당 RPS도 정확히 비례해 오른다. 통과. **조건 ②**: 파드를 늘리면 같은 유입이 더 많은 파드로 나뉘므로 파드당 값이 즉시 내려간다. 통과. 1-4의 예 1~3이 모두 이 지표로 계산한 것이다.

**단점은 요청별 비용 편차다.** RPS는 "건수"만 세므로, 무거운 요청과 가벼운 요청이 섞인 엔드포인트에서는 같은 건수가 전혀 다른 부하를 뜻할 수 있다. 회차 목록 조회 1건과 정산 리포트 생성 1건을 같은 1로 세는 것이다. 이 편차가 크면 in-flight 쪽이 더 정확하다 — in-flight는 "무거운 요청이 오래 붙잡고 있다"는 사실을 자동으로 반영하기 때문이다.

```yaml
# Before: I/O bound API에 CPU 기준 HPA — 증설이 영원히 안 일어난다
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-api
  minReplicas: 4
  maxReplicas: 24
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
          # 문제: 1-2의 산수대로 스레드가 만석이어도 CPU는 16.7%다.
          #      HPA 식에 넣으면 ceil(4 × 16.7/70) = 1파드 — 증설은커녕 축소다.
```

```yaml
# After: 병목을 대변하는 지표 — 파드당 RPS(custom metric) 기준
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-api
  minReplicas: 4
  # maxReplicas는 편의 값이 아니라 안전장치다. 근거를 주석으로 남긴다(2-5).
  #   ① DB 커넥션: PostgreSQL max_connections 100, 운영 도구 몫 10을 빼면 90.
  #      인스턴스당 풀 3개면 90 ÷ 3 = 30대까지가 DB가 견디는 상한이다(02번 문서).
  #   ② 외부 결제사 계약 동시 호출 상한 120건. 파드당 세마포어 5개면 24대.
  #   -> 둘 중 작은 값이 24. 이 숫자를 넘겨 늘리면 우리가 뒷단을 죽인다.
  maxReplicas: 24
  metrics:
    - type: Pods
      pods:
        metric:
          name: app_http_requests_per_second   # 앱이 노출, 어댑터가 중계 (2-8)
        target:
          type: AverageValue
          # 부하 테스트 실측: 파드당 한계 200 RPS에서 p99가 무너졌다.
          # 목표는 그 70% 선 — ρ = 0.7에서 응답시간 배수가 1/(1−0.7) ≈ 3.3배로
          # 아직 완만한 구간이다(01·17번 문서의 사용률 표).
          averageValue: "140"
  # 효과: 트래픽 증가 → 파드당 RPS 상승 → 증설 → 파드당 RPS 하락 → 수렴 (조건 ②)
```

### 2-3. 동시 처리 중 요청 수(in-flight)와 풀 사용률 — 포화를 직접 재는 지표

I/O bound 서비스의 실제 한계 자원은 CPU가 아니라 **스레드풀과 커넥션 풀**이다. 1-2에서 본 대로 이 자원들은 "기다리는 동안에도 점유된다"는 성질을 가지므로, 점유 개수를 세면 CPU가 놓치는 포화를 정확히 잡는다.

**in-flight**는 지금 이 파드가 동시에 처리 중인 요청 수다. 17번 문서의 표기로 쓰면 **L = λW의 L 그 자체**다 — 유입률 λ와 요청당 체류 시간 W의 곱이므로, 트래픽이 늘어도(λ↑) 뒷단이 느려져도(W↑) 함께 오른다. **한 지표로 두 원인을 모두 잡는다는 것이 in-flight의 결정적인 장점**이고, CPU가 절대 할 수 없는 일이다.

두 조건으로 평가하면 둘 다 통과다. **조건 ①**: λ가 오르거나 W가 늘면 L이 오른다. **조건 ②**: 파드를 늘리면 λ가 나뉘므로 파드당 L이 내려간다.

**풀 사용률**은 스레드풀·커넥션 풀에서 몇 개가 쓰이고 있는지의 비율이다. in-flight와 거의 같은 값이지만, **자원별로 따로 보면 어느 자원이 병목인지를 지목할 수 있다** — 17번 문서에서 본 대로 자원마다 W가 다르므로, 스레드는 60%인데 커넥션 풀이 100%인 상태가 실제로 생긴다. 그때 파드를 늘리는 것은 잘못된 대응이다(늘어난 파드가 커넥션을 더 요구한다).

**목표값은 "스레드 수의 70%"로 반사적으로 잡으면 안 된다.** 그 공식은 스레드가 먼저 마르는 워크로드에서만 맞는다. 1-2의 판정식대로 CPU가 먼저 마르는 워크로드에서는 스레드가 만석이 되기 전에 이미 붕괴하므로, 목표값을 **파드의 실제 포화 처리량에서 역산**해야 한다.

```
[CPU가 먼저 마르는 파드의 in-flight 목표 산정]
  1-2의 요청 A: 코어 8, CPU 50ms/건, W = 0.3초, 스레드 200개

  ① 이 파드의 포화 처리량 = 8코어 ÷ 0.05초 = 160건/초   (CPU가 먼저 마른다)
  ② 목표 사용률 0.7을 적용한 안전 처리량 = 160 × 0.7 = 112건/초
  ③ 그 처리량에서의 in-flight = L = λW = 112 × 0.3 = 33.6  ->  약 34건

  즉 in-flight 목표는 34다. "스레드 200개의 70% = 140"으로 잡았다면
  실제 한계의 4배가 넘는 값을 목표로 삼는 셈이고, HPA는 파드가
  이미 죽은 뒤에야 움직인다.
```

(가산점 포인트) 어느 자원이 병목이 될지 미리 확신할 수 없을 때는 **HPA에 지표를 여러 개 걸어 둘 수 있다.** HPA는 각 지표로 목표 대수를 따로 계산한 뒤 **가장 큰 값**을 택하므로, CPU와 in-flight를 함께 걸면 CPU bound 구간과 I/O bound 구간 중 어느 쪽이 먼저 와도 잡힌다. 지표를 "바꾸는" 것이 아니라 "겹치는" 선택지가 있다는 것을 아는지가 실제로 운영해 본 사람의 답이다.

두 값을 앱이 직접 지표로 내보내는 코드는 이렇게 쓴다.

```java
// 애플리케이션이 자기 포화도를 스스로 노출한다.
// 이 값이 수집기 -> 어댑터 -> HPA로 흘러간다 (경로는 2-8).
@Component
public class SaturationMetrics implements Filter {

    // 지금 이 파드가 동시에 물고 있는 요청 수. 프레임워크 내부 지표에 의존하지 않고
    // 직접 세는 편이 낫다 — 서블릿 컨테이너를 바꿔도 지표 이름과 의미가 유지된다.
    private final AtomicInteger inflight = new AtomicInteger();

    public SaturationMetrics(MeterRegistry registry,
                             @Value("${server.tomcat.threads.max}") int maxThreads,
                             HikariDataSource dataSource) {

        // ① HPA가 "파드당 평균"으로 읽을 절대값.
        //    목표값을 maxThreads의 70%로 두면 그것이 곧 운영 사용률 선언이 된다(1-4).
        Gauge.builder("app.http.inflight", inflight, AtomicInteger::get)
             .description("동시 처리 중인 HTTP 요청 수 (= Little's Law의 L)")
             .register(registry);

        // ② 같은 값을 비율로도 낸다. 파드 스펙이 서로 다른 환경(스레드 100개 파드와
        //    200개 파드가 섞인 클러스터)에서도 임계값 하나로 통일할 수 있기 때문이다.
        Gauge.builder("app.http.inflight.ratio", inflight,
                      i -> (double) i.get() / maxThreads)
             .description("스레드 상한 대비 동시 처리 비율 (0.0 ~ 1.0)")
             .register(registry);

        // ③ 커넥션 풀 사용률을 따로 낸다. 스레드는 여유인데 커넥션이 마르는 경우가
        //    별도로 존재하고(자원마다 W가 다르다 — 17번 문서), 그 경우에는 증설이
        //    오히려 해롭기 때문에 두 지표를 분리해 두어야 판단이 가능하다.
        HikariPoolMXBean pool = dataSource.getHikariPoolMXBean();
        int poolMax = dataSource.getMaximumPoolSize();
        Gauge.builder("app.db.pool.usage.ratio", pool,
                      p -> (double) p.getActiveConnections() / poolMax)
             .description("DB 커넥션 풀 사용률 (0.0 ~ 1.0)")
             .register(registry);
    }

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        inflight.incrementAndGet();
        try {
            chain.doFilter(req, res);
        } finally {
            // finally가 아니면 예외 경로에서 카운터가 줄지 않고 새어 나간다.
            // 새는 카운터는 시간이 갈수록 실제보다 큰 값을 보고하므로,
            // 트래픽이 없는 새벽에도 HPA가 파드를 늘리는 유령 증설을 만든다.
            inflight.decrementAndGet();
        }
    }
}
```

### 2-4. 큐 길이와 컨슈머 lag — 워커의 정답

워커는 자기 안에 포화 신호가 없으므로(1-5 ③) **외부 지표**를 본다. Kafka라면 컨슈머 그룹의 **lag** — 브로커에 쌓인 마지막 오프셋과 이 그룹이 커밋한 오프셋의 차이, 즉 "아직 안 읽은 메시지 수"다.

조건 ①은 명확히 통과한다. 유입이 처리 속도를 넘으면 lag이 쌓이고, 그 추세가 곧 `유입 > 처리`의 확정 증거다. **조건 ②는 조건부로만 통과하는데, 그 조건이 2-5의 주제다.**

쿠버네티스에서 브로커의 lag 같은 클러스터 외부 값을 쓸 때는 `type: External`을 쓴다.

```yaml
# HPA의 external metric으로 lag을 직접 쓰는 방식
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: view-count-consumer
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: view-count-consumer
  minReplicas: 2
  # 파티션이 12개다. 컨슈머 그룹의 병렬성 상한이 파티션 수이므로(6장 03번 문서)
  # 13번째 파드는 파티션을 배정받지 못하고 유휴 상태로 논다 — 비용만 늘고 lag은
  # 그대로다. 즉 조건 ②가 이 지점에서 깨지므로 상한을 파티션 수에 맞춘다.
  maxReplicas: 12
  metrics:
    - type: External
      external:
        metric:
          name: kafka_consumergroup_lag
          selector:
            matchLabels:
              consumergroup: view-count
              topic: episode-view
        target:
          # AverageValue는 "파드 수로 나눈 값"을 목표와 비교한다.
          # 파드당 lag 1,000건 = 전체 lag이 12,000건이면 12파드.
          type: AverageValue
          averageValue: "1000"
```

이 목표값 1,000이 어디서 나온 숫자인지도 근거를 댈 수 있어야 한다. 17번 문서의 큐 계산과 같은 식이다.

```
lag이 해소되기까지 걸리는 시간 = lag ÷ 처리율

컨슈머 파드 1개의 처리율이 200건/초라면
  파드당 lag 1,000건 -> 1,000 ÷ 200 = 5초 지연

"조회수 반영이 5초까지는 늦어도 된다"는 비즈니스 합의가 있으면 1,000이 맞고,
"1초 안에 반영돼야 한다"면 목표는 200이 된다.
```

**즉 lag 임계값은 감이 아니라 허용 지연 시간의 선언이다.** 큐 크기 설정이 "허용할 추가 대기 시간"의 선언이었던 것(17번 문서 2-4)과 같은 구조다.

이벤트 기반 스케일러(KEDA)를 쓰면 어댑터 설정 없이 같은 것을 더 짧게 쓸 수 있다.

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: view-count-consumer
spec:
  scaleTargetRef:
    name: view-count-consumer
  minReplicaCount: 2
  maxReplicaCount: 12        # 파티션 수. 위와 같은 이유.
  cooldownPeriod: 300        # 마지막 활동 후 이만큼 지나야 축소를 시작한다
  triggers:
    - type: kafka
      metadata:
        bootstrapServers: kafka:9092
        consumerGroup: view-count
        topic: episode-view
        lagThreshold: "1000" # 파드당 목표 lag. HPA의 averageValue와 같은 역할.
```

### 2-5. 조건 ②가 깨지는 경우 — 늘려도 안 내려가는 지표 (시니어 변별 지점)

**여기가 이 주제의 가장 깊은 곳이다.** 조건 ①은 지표를 잘못 고르면 "증설이 안 일어난다"로 끝나지만, 조건 ②가 깨지면 **스케일러가 상한까지 폭주하면서 장애를 스스로 키운다.** 방향이 반대인 실패다.

**깨지는 경우 (1) — 병렬성에 구조적 상한이 있다.** Kafka 컨슈머 그룹에서 파티션 하나는 컨슈머 하나에만 배정되므로, **파티션 수가 곧 병렬 처리의 천장**이다(6장 03번 문서). 파티션 12개인 토픽에 컨슈머 파드를 20개 띄우면 8개는 아무 파티션도 못 받고 논다.

```
[파티션 12, lag 24,000건, 파드당 목표 lag 1,000]

  파드 12개 -> 파드당 lag 2,000 -> HPA: ceil(12 × 2000/1000) = 24파드로 늘려라
  파드 24개 -> 12개만 일한다. 처리율은 그대로. lag도 그대로 24,000.
            -> 파드당 lag = 24,000 ÷ 24 = 1,000  <- 목표에 도달한 것처럼 보인다!
```

**여기서 특히 고약한 것은 지표가 "해결된 것처럼" 보인다는 점이다.** `AverageValue`는 전체 lag을 파드 수로 나누므로, 파드를 늘리면 실제로 아무것도 처리하지 않았는데도 분모가 커져 값이 내려간다. 처리율은 1도 안 올랐는데 지표는 목표에 수렴한다. 그래서 **에러도 알람도 없이 유휴 파드 비용만 늘어난다.** 이 조용함이 위험한 이유다.

**깨지는 경우 (2) — 병목이 파드 바깥에 있다.** 이쪽이 더 흔하고 더 위험하다. DB나 외부 API가 병목이면 파드를 늘려도 처리량이 오르지 않는다. 뒷단의 처리 능력이 고정이므로, 파드가 늘어난 만큼 각 파드가 더 오래 기다리게 될 뿐이다.

17번 문서의 표기로 쓰면 이렇다. 뒷단이 포화된 상태에서 파드를 늘리면 λ는 그대로인데 W가 늘어난다. 그런데 in-flight는 L = λW이므로 **W가 늘어난 만큼 L도 늘어나 파드당 in-flight가 안 내려간다.** 스케일러는 "아직 부족하다"고 읽고 또 늘린다.

```
[병목이 DB에 있을 때 벌어지는 악순환]

  파드당 in-flight 200 (목표 140) -> HPA: 파드를 늘려라
        |
        v
  파드 수 증가 -> 파드마다 자기 커넥션 풀을 가지므로
                 DB에 꽂히는 총 커넥션 = 파드 수 × 인스턴스당 풀 크기 가 늘어난다
        |
        v
  DB의 동시 실행 쿼리 증가 -> 같은 물리 자원을 더 많이 나눠 쓴다 -> 쿼리 하나가 느려진다
        |
        v
  W 증가 -> L = λW 이므로 in-flight가 오히려 오른다
        |
        v
  HPA: "여전히 200이 넘는다. 더 늘려라"  ->  (처음으로 돌아간다)
```

이 고리에서 **커넥션 총량 함정**이 특히 자주 밟힌다. 앱을 늘려도 사용자 수는 그대로이므로 DB에 필요한 커넥션 총량은 변하지 않는데, 인스턴스당 풀 크기를 그대로 두고 대수만 늘리면 총량이 대수에 비례해 커진다. 그 계산은 02번 문서에 있으니 여기서 반복하지 않는다. **오토스케일링을 켤 때 반드시 검산해야 하는 것은 "최대 파드 수 × 인스턴스당 풀 크기"가 DB의 `max_connections` 안에 들어오는가**다.

**그래서 최대 파드 수 상한은 편의 기능이 아니라 필수 안전장치다.** 이것이 이 절의 결론이다. `maxReplicas`가 없거나 무의미하게 크면, 조건 ②가 깨진 순간 스케일러는 **뒷단을 확실히 죽이는 방향으로 최대한 빠르게 움직이는 장치**가 된다. 그리고 그 상한값은 "적당히"가 아니라 뒷단의 수용 한계에서 역산한 숫자여야 한다(2-2의 YAML 주석이 그 예다).

운영에서 할 일이 하나 더 있다. **"증설했는데 지표가 안 내려간다"는 상태 자체에 알람을 걸어야 한다.** 이것은 "용량이 부족하다"가 아니라 **"병목이 파드 바깥에 있다"는 신호**이고, 이 둘은 대응이 완전히 반대다. 전자의 답은 증설이고 후자의 답은 뒷단 보호(캐시, 커넥션 풀 상한, 서킷 브레이커)다. 지표만 보면 구별이 안 되므로, 알람 규칙으로 만들어 두지 않으면 장애 중에 사람이 알아채기 어렵다.

### 2-6. 메모리는 왜 스케일링 지표가 아닌가

메모리 사용률은 직관적으로 그럴싸해 보이지만 **좋은 지표의 두 조건 모두를 만족하지 못한다.** 이유는 JVM의 힙 관리 방식에 있다.

**조건 ① 위반 — 부하와 무관하게 오른다.** JVM에서 객체를 만들면 힙에 쌓이고, **GC가 돌기 전까지는 쓰레기가 된 객체도 힙을 계속 차지한다.** 그래서 힙 사용량 그래프는 톱니 모양이 된다 — 부하가 일정해도 GC 주기에 따라 계속 오르다가 GC 순간에 뚝 떨어진다. 이 오름세는 "서버가 힘들어졌다"는 뜻이 아니라 **"아직 청소를 안 했다"는 뜻**이다. 부하 신호가 아닌 것을 증설 신호로 읽게 된다.

**조건 ② 위반 — 파드를 늘려도 내려가지 않는다.** 파드를 늘리면 새 요청은 새 파드로 가지만, **기존 파드가 이미 확보한 힙은 줄어들지 않는다.** JVM은 한번 OS에서 받아 온 메모리를 잘 돌려주지 않기 때문이다. 그래서 증설해도 기존 파드의 메모리 사용률은 그대로이고, 파드당 평균은 새 파드가 섞이며 천천히만 내려간다. 피드백 루프가 수렴하지 않는다.

**그래서 메모리는 스케일링 지표가 아니라 한계 설정과 알람의 대상이다.** `resources.limits.memory`로 상한을 걸어 한 파드가 노드를 잡아먹지 못하게 하고, 사용률이 계속 오르며 GC 후에도 안 내려오는 패턴에 알람을 걸어 **메모리 누수를 잡는 데** 쓴다. 증설로 풀 문제가 아니라 코드로 풀 문제라는 뜻이다.

### 2-7. p99는 왜 스케일링 지표로 함정인가 (가산점 포인트)

지연시간 p99는 사용자 경험을 가장 잘 대변하는 지표인데, 바로 그 이유로 스케일링에는 부적합하다. 함정이 둘이다.

**후행 지표다.** p99가 나빠졌다는 것은 **이미 사용자가 느린 응답을 받았다**는 뜻이다. 스케일 아웃에는 분 단위가 걸리므로(2-8), 후행 지표로 발동하면 "이미 나빠진 뒤에 분 단위로 더 나쁜 상태를 유지"하게 된다. in-flight나 풀 사용률은 큐가 밀리기 전에 오르는 선행 지표이므로 개입 여지가 남아 있다.

**증설로 안 내려가는 원인이 섞여 있다.** p99를 나쁘게 만드는 원인은 우리 파드의 포화만이 아니다. DB의 느린 쿼리 하나, 외부 API 지연, GC 정지도 p99를 올린다. 그중 증설로 해소되는 것은 첫 번째뿐이므로, **p99를 스케일링 트리거로 쓰면 2-5의 폭주 시나리오에 정면으로 들어간다.**

**결론은 역할 분리다.** p99는 알람과 SLO 감시에 쓰고, 스케일링은 선행성 있는 지표(파드당 RPS, in-flight, 풀 사용률, lag)로 건다.

### 2-8. custom metric이 스케일러까지 도달하는 경로 — 그리고 각 단계가 더하는 지연

"앱이 지표를 노출하면 HPA가 본다"는 설명은 한 단계를 뭉뚱그린 것이다. 실제로는 네 개의 주체를 거친다.

```
[① 애플리케이션]              [② 수집기]              [③ 메트릭 어댑터]        [④ 스케일러]
 app.http.inflight             주기적으로               수집된 시계열을          custom.metrics
 를 /actuator/prometheus  --->  /metrics 를      --->   쿠버네티스 메트릭   ---> API 를 조회해
 로 노출                        긁어 저장               API 형태로 변환         목표 대수 계산
                                (scrape)                (adapter)               (HPA 루프)
                                                                                     |
                                                                                     v
                                                                          Deployment 의
                                                                          replicas 를 변경
```

**중요한 것은 이 경로의 각 단계가 각자의 주기를 갖는다는 점이다.** ②는 scrape 간격마다 긁고, ③은 그 값을 집계해 노출하고, ④는 자기 루프 주기마다 조회한다. **직렬로 이어진 주기들이므로 지연이 더해진다.**

```
[예시 설정 — 각 값은 우리가 정하는 설정값이고, 여기 쓴 숫자는 그 예다]

  ① 지표 노출          앱이 값을 갱신                       사실상 즉시
  ② 수집 (scrape)      수집기가 /metrics 를 긁는 주기        15초
  ③ 집계·어댑터 노출    수집된 값이 메트릭 API로 나오기까지    15초
  ④ 스케일러 평가 주기  HPA 루프가 지표를 읽는 간격            15초
  ─────────────────────────────────────────────────────────────────
  지표가 바뀌고 스케일러가 그것을 보기까지                    약 45초
```

**"부하가 올랐다"는 사실이 스케일러에 도달하는 데만 이미 40~50초가 걸린다.** 그리고 스케일러가 대수를 바꾼 뒤에도 새 파드가 요청을 정상 속도로 처리하기까지 다섯 단계가 더 남아 있다 — 파드 배치, 컨테이너 기동, 애플리케이션 부팅, readiness 통과, 워밍업. 그 다섯 단계를 같은 방식으로 분해하면 합계가 **약 170초(2분 50초)**가 되고, 그 전체 분해는 13번 문서 1-1에 있다.

**이것이 1-5 ④에서 말한 "반응형은 어떤 지표를 써도 늦는다"의 정확한 정체다.** 지표를 CPU에서 in-flight로 바꾸는 것은 조건 ①을 고치는 일이고, 리드타임 170초는 **지표를 바꿔도 그대로 남는다.** 그래서 정시 스파이크에는 사전 증설이 필요하다.

거꾸로 이 분해는 **줄일 수 있는 곳도 알려 준다.** scrape 간격을 15초에서 5초로 줄이면 ②③④에서 약 20~30초를 벌 수 있지만, 수집 부하와 지표의 출렁임이 함께 늘어나 플래핑 위험이 커진다. 애플리케이션 부팅과 워밍업이 전체의 절반 이상이므로 **가장 효과가 큰 개선은 기동 시간 단축**이고(불필요한 빈 초기화 제거, 이미지 슬림화, 이미지 사전 캐싱), 그 다음이 워밍업의 자동화다.

### 2-9. 스케일 인의 비대칭 — 왜 줄일 때는 신중해야 하는가

**늘릴 때와 줄일 때의 기준이 대칭이면 안 된다.** 이유는 두 방향의 실패 비용이 완전히 다르기 때문이다.

**증설이 늦으면 그동안 사용자가 느린 응답이나 에러를 받는다.** 그러나 증설이 조금 과했으면 비용이 조금 더 나갈 뿐이다. 그래서 증설은 공격적으로 한다.

**축소가 과하면 되돌리는 데 2-8의 170초가 걸린다.** 줄인 직후에 부하가 돌아오면 그 170초 동안 **남은 파드가 원래 감당하던 것보다 많은 트래픽을 받는다.** 22파드에서 12파드로 줄인 직후 부하가 복귀하면, 12대가 22대 몫을 받으므로 파드당 부하가 1.83배가 된다. 사용률로 옮기면 0.7 × 1.83 = 1.28 — **용량을 넘어선다.** 그 상태로 3분을 버텨야 한다.

그리고 이것이 반복되면 **진동(플래핑)**이 된다.

```
[안정화 창이 없을 때]

 t0   부하 하락  -> 파드당 지표 하락 -> 축소  (22 -> 12)
 t1   부하 복귀  -> 12대가 과부하    -> 지표 급등
 t2   증설 판단  -> 그러나 새 파드는 170초 뒤에 제 성능
 t3   그 사이 p99 붕괴 / 타임아웃 / 재시도 증폭
 t4   증설 완료  -> 지표 하락 -> 다시 축소 판단  ->  (t0으로 돌아간다)

 결과: 대수는 계속 오르내리는데 사용자 경험은 계속 나쁘다.
       비용도 절약되지 않는다 — 오르내리는 동안 평균 대수는 그대로다.
```

대응은 **안정화 창(stabilization window)** — 축소 판단에 더 긴 관측 창을 두어, 그 창 안에서 계산된 목표 대수 중 **가장 큰 값**을 쓰는 것이다. 창이 900초면 "지난 15분 동안 한 번이라도 22대가 필요했다면 22대를 유지한다"는 뜻이 된다.

**창의 길이를 정하는 근거는 재증설 리드타임이다.** 재증설에 약 170초가 걸리므로, 그보다 짧은 창을 두면 "줄였다가 못 되돌리는" 구간이 생긴다. 리드타임의 몇 배 — 5분에서 15분 — 이 실무의 출발점이고, 정시 스파이크 뒤처럼 2차 파도가 예상되는 상황에서는 더 길게 잡는다(13번 문서 3-3과 같은 숫자를 쓴다).

```yaml
# 스케일 아웃은 공격적으로, 스케일 인은 보수적으로 — 비대칭 설정
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-api
  minReplicas: 4
  maxReplicas: 24
  metrics:
    - type: Pods
      pods:
        metric:
          name: app_http_requests_per_second
        target:
          type: AverageValue
          averageValue: "140"   # 2-2와 같은 지표·목표값 (파드당 한계 200 RPS의 70%)
  behavior:
    scaleUp:
      # 0이면 안정화 창 없이 즉시 판단한다. 늘리는 방향의 오판 비용이 낮으므로
      # 여기서 시간을 아끼는 것이 맞다.
      stabilizationWindowSeconds: 0
      policies:
        # 두 정책을 함께 두고 큰 쪽을 택한다 — 파드가 적을 때는 절대 개수가,
        # 많을 때는 비율이 더 크게 움직이므로 어느 규모에서도 충분히 빠르다.
        - type: Percent
          value: 100          # 30초마다 최대 2배까지
          periodSeconds: 30
        - type: Pods
          value: 4            # 30초마다 최대 4대까지
          periodSeconds: 30
      selectPolicy: Max
    scaleDown:
      # 기본값은 300초(5분)다. 이 서비스는 정시 스파이크 뒤 2차 파도가 있어
      # 15분으로 늘렸다. 근거: 재증설 리드타임 약 170초의 5배 이상을 확보한다.
      stabilizationWindowSeconds: 900
      policies:
        # 분당 10%씩만 줄인다. 22대에서 시작하면 6대까지 약 12분이 걸린다
        # (0.9^12 = 0.28, 22 × 0.28 ≈ 6). 급락하지 않는 것이 목적이다.
        - type: Percent
          value: 10
          periodSeconds: 60
```

축소에는 설정 하나가 더 전제돼야 한다. **진행 중인 요청을 끊지 않는 graceful shutdown**이다. 파드를 줄이는 것은 프로세스를 죽이는 일이므로, 종료 신호를 받으면 새 요청 수신을 멈추고 처리 중인 요청을 마친 뒤 내려가야 한다. 이것이 안 돼 있으면 스케일 인 자체가 에러를 만들고, 그러면 "축소하면 에러가 난다"는 이유로 아무도 축소를 켜지 않게 된다.

## 3. 실무 사례 — "트래픽 2배인데 HPA는 잠잠했다"

이 사례는 결론부터 말하면 재미가 없다. **관측된 사실을 순서대로 놓고, 각 사실이 무엇을 배제하는지**로 따라가 보자. 장애 대응은 실제로 이렇게 진행된다.

### 3-1. 관측된 사실

외부 결제사 API를 호출하는 주문 API에서 밤에 알람이 울렸다. 대시보드에서 확인한 사실은 다음과 같다.

```
[사실 1] p99 응답시간: 평상시 350ms -> 지금 8초 이상, 타임아웃 다수
[사실 2] 유입 요청 수:  변화 없음 (초당 440건 그대로)
[사실 3] 톰캣 스레드 사용률: 파드당 200/200 = 100%, 요청 대기 큐에 적재
[사실 4] CPU 사용률: 평상시 69% -> 지금 42%  (내려갔다)
[사실 5] 파드 수: 4개 그대로. HPA 이벤트 로그에 아무 기록도 없다.
[사실 6] 외부 결제사 API 응답시간: 200ms -> 2.9초
[사실 7] DB 쿼리 응답시간: 변화 없음
```

이 파드의 스펙과 평상시 프로필은 이렇다. 1-2와 같은 숫자다.

```
파드 스펙       코어 8개, 톰캣 최대 스레드 200개, 4파드
요청 프로필     전체 300ms = 파싱 20 + 로직 20 + DB 50 + 외부 API 200 + 직렬화 10
                그중 CPU 구간 = 20 + 20 + 10 = 50ms
평상시          파드당 110건/초
                스레드 점유 = 110 × 0.3초 = 33개  (200개 중 16.5%)
                CPU 수요   = 110 × 0.05초 = 5.5 코어초/초 -> 5.5 ÷ 8 = 69%
```

### 3-2. 각 사실이 무엇을 배제하는가

**사실 2가 "트래픽 증가"를 배제한다.** 유입이 그대로인데 p99가 20배가 됐다. 즉 이것은 용량 부족이 아니라 **요청 하나가 자원을 붙잡는 시간(W)이 늘어난 문제**다. 17번 문서의 L = λW에서 λ는 그대로이고 W가 변한 경우다.

**사실 3과 사실 4가 함께 "CPU 병목"을 배제한다.** 스레드는 만석인데 CPU는 오히려 내려갔다. CPU가 병목이라면 스레드가 만석이 되기 전에 CPU가 100%에 붙었어야 한다(1-2의 판정식). 두 사실이 동시에 성립하는 유일한 설명은 **스레드들이 대기 상태에 있다**는 것이다.

**사실 6과 사실 7이 병목의 위치를 지목한다.** DB는 정상이고 외부 결제사만 느려졌다. 그러면 W의 변화가 어디서 왔는지 계산으로 확인할 수 있다.

```
새 W = 20 + 20 + 50 + 2,900 + 10 = 3,000ms  (기존 300ms의 10배)
CPU 구간은 그대로 50ms다 — 느려진 것은 "기다리는 구간"이기 때문이다.

필요 스레드 = 110건/초 × 3.0초 = 330개  >  200개  -> 고갈. 사실 3과 일치.

파드당 실제 처리량 = 200개 ÷ 3.0초 = 66.7건/초
   (스레드가 상한이므로 유입 110건/초를 다 받지 못한다)

CPU 수요 = 66.7 × 0.05초 = 3.33 코어초/초  ->  3.33 ÷ 8 = 41.7%
   사실 4의 42%와 일치한다.
```

**CPU가 왜 내려갔는지가 여기서 설명된다.** CPU 수요는 `처리량 × 요청당 CPU 시간`이다. 요청당 CPU 시간은 그대로인데 **처리량이 110에서 66.7로 떨어졌으므로 CPU도 함께 떨어진 것**이다. 서비스가 죽어가는 것과 CPU가 내려가는 것이 같은 원인의 두 얼굴이다.

**사실 5는 이제 필연이다.** HPA 식에 넣어 보면 아무 일도 안 한 것이 아니라, 오히려 줄이려 했다.

```
현재 4파드, CPU 41.7%, 목표 70%
  4 × (41.7 ÷ 70) = 4 × 0.596 = 2.38  ->  ceil(2.38) = 3파드

허용 오차 검사: |41.7 − 70| ÷ 70 = 0.40 -> 10%를 넘으므로 HPA는 실제로 움직인다.
  -> minReplicas가 4였기 때문에 4에서 멈춘 것이다.
     minReplicas가 1이었다면 장애 중에 3파드로 줄었다.
```

### 3-3. 결론과 두 가지 교훈

**결론: 지표가 병목을 대변하지 못했다.** 이 서비스의 병목은 처음부터 스레드였는데, 평상시에는 CPU가 우연히 그것을 잘 대변했다(1-2의 판정식대로 CPU가 먼저 마르는 워크로드였다). **W가 10배로 변한 순간 그 우연이 깨졌고, 지표는 병목과 정반대 방향으로 움직였다.**

**교훈 ① 지표를 in-flight로 바꿨다면 증설이 발동했을 것이다.** 계산해 보면 규모까지 나온다. 먼저 이 파드의 in-flight 목표를 2-3의 방식으로 역산한다.

```
[in-flight 목표 산정 — 이 서비스는 CPU가 먼저 마르는 워크로드다]
  포화 처리량 = 8코어 ÷ 0.05초 = 160건/초
  안전 처리량 = 160 × 0.7 = 112건/초
  목표 in-flight = L = λW = 112 × 0.3초 = 33.6  ->  약 34건

[장애 시점의 HPA 계산]
  현재 4파드, in-flight 200(스레드 만석)
  4 × (200 ÷ 34) = 23.5  ->  ceil(23.5) = 24파드   <- maxReplicas 24에 딱 걸린다

[수렴점을 Little's Law로 확인]
  전체 유입 λ = 440건/초,  체류 시간 W = 3.0초
  시스템 전체의 동시 처리 요청 수 L = 440 × 3.0 = 1,320건
  파드당 34건이면  1,320 ÷ 34 = 38.8  ->  39파드가 "필요하다"는 계산이 나온다.
  그러나 상한이 24이므로 24에서 멈춘다.
```

**교훈 ② 그러나 이 장애의 근본 원인은 용량이 아니라 느린 다운스트림이다.** 위 계산의 결과를 다시 읽어 보면 무엇이 잘못됐는지 보인다.

24파드가 되면 스레드 고갈 자체는 풀린다(24 × 200 = 4,800개 ≥ 필요량 1,320개). 그런데 **결제사로 향하는 동시 호출도 함께 폭증한다.**

```
결제사로 가는 동시 호출 수 = λ × 결제사 호출 구간의 W

  평상시  440건/초 × 0.2초 = 88건
  장애 중  440건/초 × 2.9초 = 1,276건   ->  약 15배
```

**우리는 이미 느려진 상대를 15배 더 세게 누르는 것이다.** 상대가 완전히 무너지면 우리 서비스도 함께 무너진다. 그리고 여기서 `maxReplicas` 24가 한 일이 드러난다 — 상한이 없었다면 39파드까지 갔고 그만큼 더 눌렀을 것이다. **상한은 우리 비용을 아낀 것이 아니라 뒷단을 지킨 것이다**(2-5).

**올바른 1차 방어는 타임아웃과 서킷 브레이커다.** 외부 호출의 타임아웃을 응답시간 예산 안으로 조여 W가 3초까지 늘어나지 못하게 막고(10번 문서), 실패율이 임계를 넘으면 서킷을 열어 호출 자체를 없애고 폴백으로 전환한다(09번 문서). 그리고 외부 호출에 세마포어로 동시 호출 상한을 두어 파드가 늘어도 뒷단으로 가는 압력이 비례해 커지지 않게 한다(18번 문서의 bulkhead).

**"지표를 고치면 끝"이 아니라 "이 부하가 증설로 풀리는 종류인가"까지 묻는 것이 이 주제의 끝이다.** 그리고 그 질문의 일반형이 2-5의 조건 ②다.

## 4. 꼬리질문 대비 포인트

### "좋은 스케일링 지표의 조건을 일반화하면요?"

세 가지로 답한다. ① **부하 비례** — 트래픽이 늘면 지표도 늘어야 증설 신호가 된다. ② **증설 반응성** — 파드를 늘리면 지표가 내려가야 피드백 루프가 수렴한다. 파드당 평균으로 계산되는 지표가 이 성질을 구조적으로 갖는다 — 분모가 파드 수이기 때문이다. ③ **선행성과 안정성** — 포화 전에 움직이되 노이즈(GC, 워밍업)에 출렁이지 않아야 한다.

여기에 HPA 식을 붙이면 답이 단단해진다. `원하는 파드 수 = ceil(현재 파드 수 × 현재 지표 ÷ 목표 지표)`이므로, 지표가 파드당 값이 아니면 계산 자체가 성립하지 않고, 목표값은 곧 우리가 운영하려는 사용률 선언이 된다.

마무리는 **"CPU가 나쁜 지표"가 아니라 "병목과 지표의 불일치가 문제"**로 정리한다. CPU는 CPU bound 워크로드에서는 세 조건을 모두 만족하는 훌륭한 지표다. 판정식으로 말하면 `코어 수 ÷ 요청당 CPU 시간`이 `스레드 수 ÷ 요청당 점유 시간`보다 작은 워크로드가 그렇다.

### "스케일 아웃을 했는데도 지표가 안 내려가면 어떻게 되나요?" (시니어 변별 포인트)

조건 ②의 붕괴 — **병목이 파드 바깥(DB, 외부 API)에 있거나 병렬성에 구조적 상한이 있는 경우**다. 파드를 늘려도 지연·in-flight가 안 내려가니 스케일러는 계속 증설하고, 늘어난 파드들은 DB 커넥션과 동시 쿼리만 키워 병목을 **더 악화**시키는 악순환이 된다. in-flight = λW이므로 W가 늘어나면 지표가 오히려 오른다는 것이 이 악순환의 수학적 정체다.

방어는 셋이다. ① **최대 파드 수 상한을 반드시 설정하고, 그 값을 뒷단 수용 한계에서 역산한다** — "최대 파드 수 × 인스턴스당 커넥션 풀 크기"가 PostgreSQL `max_connections` 안에 들어오는지, 외부 API 계약 동시 호출 상한을 넘지 않는지 검산한다(02번 문서). ② **"증설했는데 지표 불변"을 병목이 바깥에 있다는 신호로 읽고 별도 알람을 건다** — 이 상태와 "용량 부족"은 지표만 보면 구별이 안 되는데 대응은 정반대다. ③ 근본 대응은 증설이 아니라 병목 계층 보호(캐시, 커넥션 풀 상한, 타임아웃, 서킷 브레이커)다.

Kafka 컨슈머의 경우는 특히 조용하게 실패한다. 파티션 12개에 파드 24개를 띄우면 12개는 유휴인데, `AverageValue`가 전체 lag을 파드 수로 나누므로 **처리율은 그대로인데 지표는 목표에 수렴한 것처럼 보인다.** 그래서 컨슈머 스케일링의 `maxReplicas`는 파티션 수에 맞춘다(6장 03번 문서).

**"스케일 아웃이 만능이 아니라 병목을 이동시킬 뿐"**이라는 관점이 시니어 변별점이다.

### "메모리 사용률은 스케일링 지표로 어떤가요?"

부적합하고, **두 조건 모두를 어긴다**고 답한다.

조건 ① 위반: JVM에서 힙 사용량은 **GC가 돌기 전까지 계속 올라간다.** 쓰레기가 된 객체도 회수 전에는 힙을 차지하므로, 부하가 일정해도 그래프는 톱니 모양으로 오른다. 부하 신호가 아닌 것이 증설 신호로 읽힌다.

조건 ② 위반: 파드를 늘려도 **기존 파드가 이미 확보한 힙은 내려오지 않는다.** JVM은 OS에서 받아 온 메모리를 잘 반환하지 않기 때문이다. 부하가 줄어도 즉시 내려오지 않는 것도 같은 이유다. 피드백 루프가 수렴하지 않는다.

그래서 메모리는 스케일링 신호가 아니라 **한계 설정(`resources.limits`)과 누수 감시 알람의 영역**이다. "GC 후에도 사용량이 계속 우상향"이라는 패턴은 증설로 풀 문제가 아니라 코드로 풀 문제다.

### "스케일 인은 어떻게 다루나요? 늘릴 때와 같은 기준인가요?"

비대칭으로 간다. 이유는 두 방향의 실패 비용이 다르기 때문이다. **증설이 과하면 비용이 조금 더 나가지만, 축소가 과하면 되돌리는 데 분 단위가 걸린다.** 지표 수집 45초 + 파드 기동·부팅·readiness·워밍업 약 125초, 합쳐서 약 170초다(2-8). 22파드를 12파드로 줄인 직후 부하가 복귀하면 12대가 22대 몫을 받으므로 파드당 부하가 1.83배 — 사용률 0.7이 1.28이 되어 용량을 넘어선 상태로 3분을 버텨야 한다.

이것이 반복되면 진동(플래핑)이 되고, 대수는 계속 오르내리는데 사용자 경험은 계속 나쁘고 비용도 절약되지 않는다.

대응은 **안정화 창** — 축소 판단에 더 긴 관측 창을 두고 그 창 안에서 계산된 목표 대수 중 가장 큰 값을 쓴다. `behavior.scaleDown.stabilizationWindowSeconds`가 그 설정이고 기본값은 300초다. **창 길이의 근거는 재증설 리드타임**이므로, 170초의 여러 배인 5~15분이 출발점이고, 정시 스파이크 뒤처럼 2차 파도가 예상되면 더 길게 잡는다(13번 문서 3-3). 여기에 분당 10% 같은 축소 속도 제한을 함께 걸어 급락을 막는다.

전제로 **graceful shutdown**이 돼 있어야 한다. 축소가 진행 중 요청을 끊으면 스케일 인 자체가 에러를 만들고, 그러면 아무도 축소를 켜지 않게 되어 비용 절감이라는 목적 자체가 사라진다.

### "반응형 스케일링으로 못 막는 스파이크는 어떻게 하나요?"

지표 선택과 별개의 축임을 먼저 짚는다. 지표를 CPU에서 in-flight로 바꾸는 것은 **조건 ①을 고치는 일**이고, 리드타임 170초는 지표를 바꿔도 그대로 남는다. 2-8의 분해를 그대로 말하면 설득력이 붙는다 — 수집 15초 + 어댑터 15초 + 평가 15초 + 파드 배치·기동·부팅·readiness 65초 + 워밍업 60초.

수 초 만에 치솟는 정시 스파이크(신작 공개, 이벤트 오픈)는 어떤 지표를 써도 이 리드타임 때문에 늦는다. 그래서 **시각 기반 사전 증설(scheduled scaling)로 미리 용량을 만들고**, 반응형은 예측을 벗어난 초과분을 따라가는 보조 수단으로 남기고, 그마저 넘치면 우선순위 기반 load shedding이 마지막 방어선이다.

**"지표 교체 / 사전 증설 / 방어선"이 서로 다른 문제를 푸는 세 계층**이라고 구분하면 완결된다. 사전 증설의 규모 산정과 시간 축 런북은 13번 문서에서 다룬다.

## 한 줄 요약

오토스케일링 지표는 병목 자원과 일치해야 하며 합격 기준은 두 개다 — 부하가 오르면 오르고(포화 대변), 파드를 늘리면 내려가야(피드백 수렴) 한다 — 블로킹 I/O에서 대기 중인 스레드는 CPU를 전혀 쓰지 않으므로 I/O bound 서비스는 스레드 200개가 만석인데 CPU가 16.7%로 보이고, `ceil(현재 파드 수 × 현재 지표 ÷ 목표 지표)`라는 HPA 식에 그 값을 넣으면 증설은커녕 축소가 계산되므로 대안은 파드당 RPS·in-flight·풀 사용률·큐 lag이며, 증설해도 안 내려가는 지표(파티션 상한에 걸린 lag, DB·외부 API가 병목일 때의 지연)는 스케일러를 폭주시켜 뒷단을 죽이므로 최대 파드 수 상한은 뒷단 수용 한계에서 역산한 필수 안전장치이고, 메모리는 두 조건 모두를 어겨 스케일링 지표가 아니라 limit·알람의 대상이며, 재증설에 약 170초가 걸린다는 비대칭 때문에 축소에는 긴 안정화 창을 둔다.
