# 조회수/좋아요 집계 파이프라인 — 정확성·실시간성·부하, 셋 다 가질 수는 없다

> 핵심 관전 포인트: **조회마다 DB `UPDATE count = count + 1`을 치는 순간
> 인기 콘텐츠의 행(row) 하나에 락 경합이 집중되어 DB가 무너진다.
> 해법의 골격은 "쓰기 버퍼링 + 주기적 배치 반영"이다 — 조회 이벤트를
> Redis `INCR`(또는 Kafka)에 흡수하고, 수 초~수십 초 주기로 합산해
> DB에 배치 UPDATE 한다. 읽기는 Redis에서 서빙해 실시간성을 확보한다.
> 단, 이 설계의 전제는 비즈니스와의 협상이다: "조회수가 몇 초 늦거나
> 1~2 틀려도 되는가?" — 조회수는 근사치 허용, 좋아요는 사용자별
> 정확한 기록이 필요하므로 둘은 다른 파이프라인이다.**

---

## 0. 질문 + 의도

**질문**: "조회수/좋아요 집계를 실시간에 가깝게 보여주되 DB 부하를
최소화하는 파이프라인을 설계해보세요."

**출제 의도**: 정확성·실시간성·부하의 3자 트레이드오프를 비즈니스
요구("조회수가 1 정도 틀려도 되는가")와 협상하며 설계하는지 본다.
기술 선택 이전에 **요구사항의 완화 가능 지점을 찾는 습관** — 요구를
전부 만족하려는 사람은 과잉 설계를 하고, 완화 지점을 찾는 사람은
값싸고 견고한 설계를 한다.

## 1. 왜 매 조회마다 UPDATE 하면 안 되는가 — 핫 로우 락 경합

```java
// Before: 조회할 때마다 카운터 UPDATE — 인기 콘텐츠에서 붕괴
@Transactional
public WebtoonDetail view(Long webtoonId) {
    webtoonRepository.incrementViewCount(webtoonId);
    // UPDATE webtoon SET view_count = view_count + 1 WHERE id = ?
    // 문제 1: 같은 행을 갱신하는 UPDATE는 행 락을 잡는다
    //         → 인기작 1편에 초당 수천 조회가 몰리면 수천 트랜잭션이
    //           "하나의 행 락"을 두고 줄을 선다 (핫 로우 경합)
    // 문제 2: 조회(읽기) 트래픽이 전부 쓰기 트래픽으로 둔갑
    //         → 읽기 복제본으로도 분산 불가 (쓰기는 primary로만 감)
    // 문제 3: 락 대기 시간이 조회 API의 응답 시간에 그대로 얹힘
    return findDetail(webtoonId);
}
```

핵심 인과를 짚어야 한다: **트래픽이 여러 행에 퍼지면 DB는 잘 버티지만,
"인기"라는 속성이 트래픽을 한 행에 모은다.** 조회수 기능은 본질적으로
핫스팟을 만드는 기능이다. 그래서 "DB를 키우자"가 아니라 "DB 앞에서
흡수하자"가 답이 된다.

## 2. 설계 골격 — 쓰기 버퍼링 + 주기 배치 반영 (write-behind)

```
[조회 이벤트]
    ↓ (API는 카운트를 DB에 쓰지 않는다)
[Redis INCR view:webtoon:123]   ← 메모리 연산, 락 경합 없음, 초당 수십만 처리
    ↓ 주기적 배치 (예: 10초마다 스케줄러/컨슈머)
[변경분 합산 → DB 배치 UPDATE]  ← 10초간 5만 조회가 UPDATE "1번"으로 압축
    ↓
[DB view_count]                  ← 영속 원본 (조회수의 최종 기록)

읽기: Redis 값 서빙 (실시간) / Redis에 없으면 DB에서 읽어 캐시 적재
```

```java
// After: Redis에 흡수하고, 주기적으로 배치 반영
public void countView(Long webtoonId) {
    redis.opsForValue().increment("view:webtoon:" + webtoonId); // O(1), 락 없음
    redis.opsForSet().add("view:dirty", webtoonId.toString());  // 변경분 추적
}

@Scheduled(fixedDelay = 10_000)
public void flushToDb() {
    Set<String> dirtyIds = redis.opsForSet().pop("view:dirty", 1000);
    for (String id : dirtyIds) {
        Long delta = redis.opsForValue().getAndSet("view:delta:" + id, 0L);
        if (delta != null && delta > 0) {
            jdbcTemplate.update(
                "UPDATE webtoon SET view_count = view_count + ? WHERE id = ?",
                delta, Long.parseLong(id)); // 수만 건의 조회가 UPDATE 1번으로
        }
    }
}
```

효과를 숫자 감각으로 말하면 좋다: 초당 5,000 조회 × 10초 = 5만 건의
쓰기가 **UPDATE 1번**으로 압축된다. DB 쓰기 부하가 조회 트래픽과
비례하지 않고 "콘텐츠 수 × 플러시 주기"에만 비례하게 된다 —
**부하의 축을 트래픽에서 분리**하는 것이 이 설계의 본질이다.

트래픽이 더 크면 Redis 대신(또는 앞단에) **Kafka로 이벤트를 흘리고
스트림 집계(윈도우 단위 합산) 후 DB upsert** 하는 구성으로 확장한다.
이벤트 로그가 남으므로 장애 시 재집계가 가능해져 유실 걱정도 줄어든다
(가산점 포인트).

## 3. 좋아요는 조회수와 다르다 — 요구사항이 파이프라인을 가른다

여기서 요구사항 협상 능력이 드러난다. 둘은 겉보기에 같은 "카운트"지만
정확성 요구가 다르다.

| 항목 | 조회수 | 좋아요 |
|---|---|---|
| 오차 허용 | 몇 개 틀려도 됨 (근사치) | 안 됨 — 내가 누른 게 사라지면 버그 |
| 사용자별 기록 | 불필요 | 필수 (중복 방지, 취소/토글) |
| 유실 시 | 재집계 or 수용 | 데이터 손실 사고 |

- **좋아요의 원본은 "누가 눌렀나"라는 관계 데이터**다. `user_like(user_id,
  content_id)` 테이블에 unique 제약으로 즉시 기록해야 중복 방지와
  토글(취소)이 성립한다. 이건 DB에 동기로 쓴다 — 다만 좋아요는
  조회보다 수십~수백 배 드물어서 동기 쓰기가 감당 가능하다.
- **좋아요 "개수"는 파생 데이터**이므로 조회수와 같은 방식(Redis 카운터
  + 배치 반영)으로 보여준다. 원본(관계)과 표시용 집계를 분리하는 것.
- 조회수의 "유니크 사용자 수"가 필요하면 정확한 집합 대신
  **HyperLogLog** 같은 확률 자료구조로 메모리를 상수 수준으로 묶을 수
  있다 — "정확도를 조금 팔아 자원을 크게 아끼는" 같은 계열의 트레이드오프다
  (가산점 포인트).

## 4. 꼬리질문 대비 포인트

### "Redis가 죽으면 아직 반영 안 된 조회수는 유실되잖아요?"

맞다, 그리고 그걸 **비즈니스와 먼저 협상**해야 한다. "장애 시 최근
10초치 조회수 유실이 허용되는가?" — 대부분의 서비스에서 조회수는
허용된다(그래서 이 설계가 성립한다). 허용 폭을 더 줄이려면 ① 플러시
주기 단축, ② Redis AOF 영속화, ③ Kafka에 원본 이벤트를 남겨 장애 후
재집계 — 순서대로 비용이 커진다. "유실 0"이 진짜 요구라면 그건
조회수가 아니라 정산용 데이터이므로 다른 파이프라인(6번 꼬리질문)이
필요하다고 답하면 좋다.

### "인기 웹툰 딱 하나에 트래픽이 몰리면 Redis 키 하나가 병목이 되지 않나요?"

Redis 단일 키 INCR도 결국 한 노드의 한 키로 직렬화된다. 초당 수십만을
넘는 극단적 핫 키라면 **카운터 샤딩**을 쓴다 — `view:123:shard:{0..9}`
처럼 키를 N개로 쪼개 무작위로 INCR하고, 읽을 때 합산한다. DB의 핫 로우
문제를 Redis에서 다시 만난 것이고, 해법(분산 후 합산)도 같은 원리라는
점을 짚으면 이해의 깊이가 드러난다.

### "flush 스케줄러가 여러 서버에서 동시에 돌면 중복 반영되지 않나요?"

서버가 N대면 `@Scheduled`도 N번 돈다. `GETSET`(읽고 0으로 초기화)처럼
원자적으로 "가져가면서 비우는" 연산을 쓰거나, 분산 락(ShedLock 등)으로
한 인스턴스만 플러시하게 하거나, 아예 플러시를 Kafka 컨슈머로 옮겨
파티션 소유권으로 자연스럽게 단일 처리자를 보장한다. delta 방식
(`view_count = view_count + delta`)이라 순서는 안 중요하지만 **중복
반영은 오차가 되므로** 원자적 회수가 핵심이라고 답한다.

### "좋아요 버튼 연타(따닥)로 카운트가 어긋나는 건 어떻게 막나요?"

원본이 관계 테이블이기 때문에 막힌다 — `(user_id, content_id)` unique
제약이 두 번째 INSERT를 거부한다. 카운터만 있고 원본이 없으면 이
문제를 애플리케이션 로직으로 막아야 해서 반드시 구멍이 난다.
"집계는 파생 데이터, 원본은 관계"라는 분리가 정합성의 근거임을
다시 강조할 기회다.

### "이 집계가 작가 정산(돈)에 쓰인다면 설계가 어떻게 달라지나요?" (시니어 변별 포인트)

허용 오차가 0에 수렴하므로 "빠른 근사치" 파이프라인을 그대로 쓰면
안 된다. **화면 표시용(실시간·근사)과 정산용(배치·정확)을 분리**한다 —
정산은 Kafka 등에 남긴 원본 이벤트 로그를 일 단위 배치로 멱등하게
재집계하고, 어뷰징 필터(동일 IP 반복 조회 등)까지 거친 값을 쓴다.
같은 숫자라도 용도에 따라 다른 파이프라인이 필요하다는 것 —
"요구사항이 아키텍처를 결정한다"는 이 질문의 출제 의도에 대한
정면 답변이다. 두 값이 달라 보이는 것에 대한 CS 문의가 올 수 있으니
표시 화면에 "집계 반영에 시간이 걸릴 수 있음"을 명시하는 운영적
디테일까지 언급하면 가산점 포인트.

## 한 줄 요약

조회수 집계의 정답은 특정 기술이 아니라 **"조회수가 몇 초 늦고 1~2
틀려도 되는가"라는 협상에서 출발해, 허용된 오차만큼 쓰기를 버퍼링
(Redis INCR → 주기 배치 UPDATE)해 DB 부하를 트래픽과 분리하고,
정확성이 필요한 좋아요(사용자별 관계)와 돈이 걸린 정산(이벤트 로그
재집계)은 별도 경로로 나누는 것**이다.
