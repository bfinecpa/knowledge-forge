# 처리량 vs 지연시간, p99를 보는 이유 — 평균은 "가장 느린 1%"를 숨긴다

> 핵심 관전 포인트: **처리량(throughput)은 시스템 관점의 지표 — 단위 시간당 처리 건수(TPS)이고, 지연시간(latency)은 사용자 관점의 지표 — 요청 하나가 응답받기까지 걸리는 시간이다. 둘은 같은 것이 아니다: 서버를 늘리면 처리량은 올라가지만 요청 하나의 지연시간은 그대로일 수 있고, 반대로 부하가 용량 한계에 다가가면 큐 대기 때문에 지연시간이 비선형으로 치솟는다. 지연시간은 평균이 아니라 백분위(p50/p95/p99)로 본다 — 응답시간 분포는 한쪽으로 길게 치우쳐 있어 평균이 "가장 느린 소수"를 숨기기 때문이다. p99는 실제 사용자 경험의 하한선이자, 시스템이 한계에 가까워질 때 평균보다 먼저 나빠지는 장애의 전조다.**

---

## 0. 질문 + 의도

**질문**: "처리량(throughput)과 지연시간(latency)의 차이는? p99 latency를 왜 보나요?"

**출제 의도**: 평균만 보는 사람은 "평균 50ms인데 왜 유저가 느리대요?"에서 막힌다. 상위 백분위가 실제 사용자 경험이고 장애의 전조라는 것 — 성능을 "측정하는 언어"를 공유할 수 있는지가 성능 업무 참여의 전제다.

## 1. 두 지표의 정의 — 관점이 다르다

| | 처리량 (throughput) | 지연시간 (latency) |
|---|---|---|
| 정의 | 단위 시간당 처리한 요청 수 (TPS, RPS) | 요청 1건이 응답받기까지 걸린 시간 (ms) |
| 관점 | 시스템/운영자 — "얼마나 많이 감당하나" | 사용자 — "얼마나 빨리 받나" |
| 개선 수단 | 병렬성 확대 (서버·스레드 증설) | 요청 경로 단축 (쿼리 튜닝, 캐시, 네트워크) |

- 고속도로 비유: 처리량은 **시간당 통과 차량 수**, 지연시간은 **차 한 대가 입구에서 출구까지 걸리는 시간**. 차선을 8차선으로 늘리면(스케일 아웃) 시간당 통과량은 늘지만, 한 대가 달리는 시간은 그대로다. 반대로 도로에 차가 가득 차기 시작하면(포화) 통과량이 늘지 않는데 통행 시간만 급증한다.
- 그래서 "성능이 좋다"는 말은 모호하다 — **처리량 목표(감당할 TPS)와 지연시간 목표(SLO, 예: p99 < 300ms)를 따로 잡아야** 대화가 성립한다.

## 2. 둘의 관계 — 포화 근처에서 지연시간이 폭발한다

독립된 축이지만 무관하지는 않다. 부하(유입 TPS)가 시스템 용량에 가까워지면 요청이 큐(톰캣 대기 큐, 커넥션 풀 대기, CPU run queue)에 쌓이기 시작하고, **큐 대기 시간이 지연시간에 더해진다**.

```
지연시간
  │                                    ╱  ← 포화 근처: 큐잉으로 급증 (hockey stick)
  │                             ╱
  │  ──────────────────╱
  └──────────────────────────────── 유입 부하(TPS)
        여유 구간: 부하가 늘어도 지연 거의 일정
```

- 이 곡선 때문에 "CPU 70~80%까지는 괜찮다가 90%부터 갑자기 느려지는" 현상이 생긴다 — 자원 사용률과 대기 시간은 비례가 아니라 비선형 관계다.
- (가산점 포인트) Little's Law(`동시 요청 수 L = 유입률 λ × 체류시간 W`)로 두 지표가 연결된다: 처리량과 지연시간을 알면 시스템 안에 머무는 동시 요청 수가 계산되고, 이것이 스레드풀·커넥션풀 크기 산정의 근거가 된다.

## 3. 평균의 함정 — 분포는 한쪽으로 길게 치우쳐 있다

응답시간은 정규분포가 아니다. 대부분은 빠르고, 소수가 GC 일시정지·캐시 미스·느린 쿼리·커넥션 대기 때문에 극단적으로 느린 **오른쪽 꼬리(long tail) 분포**다.

```
요청 100건: 99건이 10ms, 1건이 4,000ms
→ 평균 = (99×10 + 4000) / 100 ≈ 50ms   ← "평균 50ms, 문제없음"
→ p99 = 4,000ms                          ← 실제로 누군가는 4초를 기다렸다
```

- **p50(중앙값)**: 절반의 요청이 이보다 빠름 — "보통의 경험"
- **p95 / p99**: 95% / 99%의 요청이 이 값 이하 — "가장 느린 5% / 1%의 경험 하한선"
- 평균은 이 분포에서 "아무도 겪지 않은 시간"일 수 있다. 성능 이슈는 항상 꼬리에서 시작하는데, 평균은 꼬리를 다수의 빠른 요청으로 희석해 버린다.

측정 코드도 같은 함정을 밟기 쉽다:

```java
// before: 합계/건수로 평균만 남긴다 — 분포 정보가 소멸
long elapsed = System.currentTimeMillis() - start;
totalTime.addAndGet(elapsed);
count.incrementAndGet();
// 대시보드에 totalTime/count 표시 → 4초짜리 요청이 평균 속에 묻힌다
```

```java
// after: 히스토그램 기반 타이머로 백분위를 산출 (Micrometer)
Timer timer = Timer.builder("api.latency")
        .publishPercentileHistogram()   // 버킷 분포를 남겨 p95/p99 계산 가능
        .register(meterRegistry);
timer.record(() -> handleRequest());
// Grafana/Prometheus에서 p50·p95·p99를 각각 그려 꼬리를 직접 본다
```

## 4. p99를 보는 이유 세 가지

1. **1%는 적은 수가 아니다** — 하루 1,000만 요청이면 p99 바깥이 10만 건이다. 게다가 화면 하나가 API를 여러 개 호출하면(fan-out), 사용자 한 명이 "그중 하나라도 p99를 겪을" 확률은 1%보다 훨씬 커진다 — API 10개를 호출하는 페이지라면 약 1 − 0.99¹⁰ ≈ 10%의 페이지 로드가 꼬리 지연을 포함한다. **p99는 소수 이야기가 아니라 상당수 사용자의 체감 품질이다.**
2. **장애의 전조가 꼬리에 먼저 나타난다** — 커넥션 풀이 간헐적으로 고갈되기 시작하거나, 특정 파라미터만 느린 쿼리를 타거나, GC 압박이 커질 때 평균은 거의 안 움직이고 p99가 먼저 뛴다. p99 알람은 평균 알람보다 앞서 울리는 조기 경보다.
3. **목표를 합의하는 언어(SLO)** — "빠르게 해주세요"는 요구사항이 아니다. "p99 300ms 이하"는 개발·운영·기획이 같은 숫자를 보고 합의·검증할 수 있는 계약이 된다.

## 5. 실무 주의 — 백분위는 평균 낼 수 없다

- 인스턴스 A의 p99와 인스턴스 B의 p99를 **산술평균하면 전체 p99가 아니다** (백분위는 선형 연산이 안 된다). 각 인스턴스가 히스토그램 버킷(응답시간 구간별 카운트)을 내보내고, 중앙에서 버킷을 합산한 뒤 전체 분포에서 백분위를 재계산해야 한다 — Prometheus의 histogram + `histogram_quantile()`이 이 방식이다.
- (가산점 포인트) 부하 테스트에서의 **coordinated omission**: 응답이 늦어지면 도구가 다음 요청 전송도 늦춰서, 정작 느렸던 구간의 샘플이 적게 찍혀 꼬리가 실제보다 좋게 측정되는 왜곡. 고정 도착률(open model)로 쏘는 도구·설정으로 방지한다.

## 6. 꼬리질문 대비 포인트

### "왜 하필 p99인가요? p99.9나 max를 보면 안 되나요?"

max(p100)는 단발 노이즈(GC full pause, 배포 직후 워밍업, 재시도 1건)에 지배돼 알람 기준으로 쓰면 오탐이 많다. 반대로 p95만 보면 놓치는 꼬리가 크다. p99는 "노이즈에 덜 흔들리면서 꼬리를 대표하는" 실용적 절충점이고, 트래픽이 크고 비즈니스 크리티컬한 경로(결제 등)는 p99.9까지 본다 — 어느 백분위를 SLO로 삼을지는 트래픽 규모와 요청 1건의 비즈니스 가치로 정하는 판단의 문제다.

### "처리량을 올리면 지연시간도 좋아지나요?"

별개다. 용량에 여유가 있는 구간에서는 서버를 늘려도(처리량 상한↑) 요청 1건의 경로는 그대로라 지연시간이 안 변한다. 다만 **이미 포화 상태였다면** 증설이 큐 대기를 없애 지연시간이 극적으로 좋아진다 — 즉 "증설로 latency가 좋아졌다"는 것은 그동안 큐잉이 있었다는 뜻이다. 반대로 지연시간 개선(쿼리 튜닝으로 체류시간 단축)은 같은 자원으로 더 많은 동시 요청을 감당하게 해 처리량 상한도 올린다.

### "평균은 50ms로 정상인데 사용자 불만이 들어옵니다. 무엇부터 확인하나요?"

평균 대신 분포부터 본다 — p95/p99가 치솟았는지, 특정 엔드포인트·특정 시간대·특정 사용자군(데이터가 많은 헤비 유저)에 꼬리가 편중됐는지 분해한다. 꼬리의 전형적 원인은 GC pause, 커넥션 풀 대기, 캐시 미스 경로, 파라미터에 따라 실행계획이 달라지는 쿼리다. 핵심은 "전체 평균"이라는 뭉뚱그린 숫자를 세그먼트별 백분위로 쪼개는 것.

### "여러 인스턴스의 p99를 집계하려면 어떻게 하나요?" (시니어 변별 포인트)

각 인스턴스 p99의 평균을 내면 틀린 값이 나온다 — 백분위는 평균이 불가능하다. 인스턴스별로 히스토그램(구간별 카운트)을 노출하고 중앙(Prometheus 등)에서 버킷을 합산해 전체 분포로부터 백분위를 재계산해야 한다. 이걸 아는지가 "대시보드를 만들어 본 사람"과 "남이 만든 대시보드를 본 사람"을 가른다.

### "마이크로서비스처럼 한 요청이 여러 서비스를 거치면 꼬리 지연은 어떻게 되나요?"

증폭된다. 병렬로 N개 서비스를 호출하면 전체 응답은 **그중 가장 느린 하나**가 결정하므로, 개별 서비스는 p99가 준수해도 조합된 요청은 훨씬 자주 꼬리를 겪는다(tail at scale 문제). 그래서 fan-out이 큰 시스템일수록 각 구성요소의 꼬리 관리가 중요하고, 완화책으로 타임아웃 예산 배분, 헤지 요청(hedged request — 응답이 늦으면 다른 복제본에 중복 요청) 같은 기법이 쓰인다. (가산점 포인트)

---

## 한 줄 요약

처리량은 시스템이 단위 시간당 감당하는 양(TPS), 지연시간은 요청 1건의 사용자 체감 시간으로 서로 다른 축이며 포화 근처에서만 큐잉으로 얽힌다 — 지연시간은 오른쪽으로 긴 꼬리 분포라 평균이 느린 소수를 숨기므로, 실제 사용자 경험의 하한선이자 장애의 조기 경보인 p99(백분위)로 측정하고, 집계할 때는 백분위를 평균 내지 말고 히스토그램을 합산해 재계산한다.
