# 정시 트래픽 스파이크 대비 — 예측 가능한 스파이크는 계층별로, 시간 축을 갖고 준비한다

> 핵심 관전 포인트: **밤 11시 신작 공개처럼 시각이 정해진 스파이크는
> "감지 후 대응"이 아니라 "사전 준비"의 문제다. 반응형 오토스케일링은
> 감지와 인스턴스 기동에 수 분이 걸려 수 초 만에 치솟는 스파이크에
> 항상 늦는다 — 그래서 시각 기반 사전 스케일 아웃(scheduled scaling)이
> 기본이다. 대비는 요청이 흐르는 계층 순서대로 세운다: 클라이언트(유입
> 분산) → CDN(이미지 사전 워밍) → 애플리케이션(사전 증설 + 워밍업) →
> 캐시(신작 데이터 사전 적재 + stampede 방지) → DB(비동기화로 쓰기
> 부하 격리), 그리고 예측이 빗나갈 때를 위한 마지막 방어선(rate limit,
> load shedding)까지. 이 전부를 T-30분, T-10분 같은 시간 축 런북으로
> 말할 수 있어야 한다.**

---

## 0. 질문 + 의도

**질문**: "인기 웹툰 신작 공개 시각(예: 밤 11시)에 트래픽이 스파이크됩니다. 어떤 계층에서 어떻게 대비하나요?"

**출제 의도**: 예측 가능한 스파이크는 준비 안 하면 그냥 태만이다.
계층별(CDN, 캐시 사전 워밍, 사전 스케일 아웃) 대비를 시간 축까지 넣어
말하는지 본다 — 이 회사의 매일 밤 실제 상황이므로 도메인 적합성
검증이기도 하다.

## 1. 전제 — 반응형 오토스케일링은 정시 스파이크에 항상 늦는다

이 질문에서 가장 먼저 그어야 할 선: **예측 가능한 스파이크와 예측
불가능한 스파이크는 다른 문제다.** 밤 11시 공개는 날짜·시각·대상
콘텐츠까지 전부 알고 있다. 그런데도 반응형 오토스케일링에 맡기면
이런 시간표가 된다.

```text
23:00:00  공개 → 트래픽 수 초 만에 수 배로 치솟음
23:00:00~ 기존 서버 과부하 시작 (큐잉, 지연 급증, 타임아웃)
23:01~02  메트릭 수집 주기 + 판단 지연 후에야 스케일 아웃 트리거
23:02~05  인스턴스 기동, 애플리케이션 부팅, 헬스체크 통과
23:05~    새 서버 투입 — 그러나 이미 최악의 5분이 지나감
          (그 사이 타임아웃 → 클라이언트 재시도 → 부하 증폭까지)
```

스파이크의 상승 속도(초 단위)가 스케일 아웃의 리드타임(분 단위)보다
항상 빠르다. 결론은 하나다 — **시각을 아는 스파이크는 그 시각 전에
용량을 만들어 둔다(scheduled scaling).** 반응형 오토스케일링은 예측을
벗어난 초과분을 따라가는 보조 수단으로 남긴다.

- 비유: 개봉일 아침 영화관이다. 관객이 몰린 걸 보고 매표소 직원을
  집에서 불러오면 늦는다. 개봉 시각 전에 전원 출근시켜 두는 것이다.

## 2. 계층별 대비 — 요청이 흐르는 순서대로

원칙은 load shedding과 같은 뿌리다: **부하를 가능한 한 바깥 계층에서
흡수해, 안쪽(비싸고 늘리기 어려운 DB)까지 도달하는 양을 구조적으로
줄인다.**

### ① 클라이언트/유입 — 스파이크의 뾰족함부터 무디게

- **푸시 알림을 정각에 일제 발송하지 않는다.** 수백만 명에게 23:00:00에
  동시에 알림이 가면 스파이크를 우리 손으로 만드는 셈이다. 수 분에
  걸쳐 나눠 발송하면 피크가 몇 분의 일로 깎인다.
- 클라이언트가 공개 시각을 기다리며 반복 조회(폴링)하는 패턴이 있다면
  요청 시점에 무작위 지연(jitter)을 심어 정각 집중을 분산시킨다.

### ② CDN — 트래픽의 대부분(이미지)을 오리진 앞에서 끝낸다

웹툰 도메인에서 스파이크 트래픽의 대부분은 회차 이미지다. 이미지는
공개 순간부터 불변 콘텐츠이므로 CDN이 가장 잘 흡수한다.

- **사전 워밍(pre-warm)**: 공개 직후 첫 사용자들이 전부 캐시 미스로
  오리진을 때리지 않도록, 공개 전에 신작 이미지를 엣지에 미리
  적재해 둔다(내부에서 미리 요청을 흘려 캐시를 채우는 방식 포함).
- 공개 시각 전에는 접근을 막아야 하므로, "공개 전 차단"은 CDN 캐시
  가능성을 해치지 않는 방식(서명 URL 발급 시점 제어 등)으로 앱
  계층에서 푼다.

### ③ 애플리케이션 — 사전 스케일 아웃 + 워밍업

- **T-30분경 목표 대수까지 미리 증설**한다. 목표 대수는 감이 아니라
  근거에서 나온다: 지난 공개일들의 피크 지표(RPS, 동시 사용자) ×
  성장률 + 여유분, 그리고 부하 테스트로 실측한 서버 1대당 처리
  용량으로 나눠 산정한다.
- 증설만으론 부족하고 **워밍업**이 필요하다. JVM이라면 JIT 컴파일
  전의 초기 요청은 느리고, 커넥션 풀·로컬 캐시도 비어 있다. 투입 전
  내부 트래픽으로 예열하거나 LB의 slow start로 점진 투입한다.
- 이 모든 것의 전제는 **stateless 서버**다. 로컬 상태가 있으면
  증설 자체가 버그를 만든다.

### ④ 캐시 — 사전 적재와 stampede 방지

공개 정각에 벌어지는 일: 신작 회차의 메타데이터·회차 목록은 그
순간까지 캐시에 없다(또는 정각에 무효화된다). 수만 요청이 동시에
캐시 미스를 내고 전부 DB로 직행하는 **cache stampede**가 스파이크
장애의 단골 원인이다.

- **사전 적재**: 공개 시각 직전에 신작 관련 키(작품 메타, 회차 목록,
  메인 페이지 조각)를 미리 계산해 캐시에 넣어 둔다.
- **stampede 방지**: 그래도 만료·미스는 생기므로, 미스 시 재계산을
  한 요청만 하게 만든다.

```java
// Before: 순진한 get-or-load — 정각에 수만 요청이 동시에 DB 재계산
public Episode getEpisode(long id) {
    Episode cached = cache.get(key(id));
    if (cached == null) {                 // 공개 정각: 전원이 여기 도달
        cached = db.findEpisode(id);      // 같은 쿼리 수만 번 동시 실행
        cache.put(key(id), cached);
    }
    return cached;
}

// After: 재계산을 한 요청으로 제한 (single flight) — 나머지는 결과를 공유
public Episode getEpisode(long id) {
    Episode cached = cache.get(key(id));
    if (cached != null) return cached;
    // 키별 락: 최초 1명만 DB를 조회하고, 동시 도착자는 완료를 기다렸다 공유
    return loadGroup.computeIfAbsent(key(id), k -> {
        Episode fresh = db.findEpisode(id);
        cache.put(k, fresh);
        return fresh;
    });
    // 추가 방어: TTL에 jitter를 줘 대량 키의 동시 만료를 분산,
    //            인기 키는 만료 전에 백그라운드로 갱신
}
```

### ⑤ DB — 늘리기 가장 어려운 계층이니 도달량 자체를 줄인다

앞 계층이 전부 잘 돼도 병목은 결국 상태 있는 계층으로 수렴한다.

- 읽기는 캐시 히트율로 흡수하고, 남는 읽기는 레플리카로 분산한다.
- **쓰기(조회수, 좋아요, 읽음 기록)는 동기로 DB에 꽂지 않는다.**
  큐/버퍼에 쌓아 비동기 배치로 집계한다 — 스파이크 시 가장 흔한
  자충수가 "회차 조회마다 조회수 UPDATE"다.
- 커넥션 풀은 스파이크라고 늘리지 않는다. DB가 감당하는 동시 실행
  수는 정해져 있어, 풀만 늘리면 DB 쪽 경합만 키운다.

### ⑥ 마지막 방어선 — 예측이 빗나갈 때

준비량을 넘는 유입이 오면 반응형 오토스케일링이 따라잡는 동안
게이트웨이의 rate limiting / load shedding이 초과분을 빨리 거절해
수용한 요청의 정상 처리를 지킨다. 티켓팅급이 예상되면 대기열 시스템
투입까지 검토한다. "준비 + 예측 실패 대비"를 세트로 말해야 완결된다.

## 3. 시간 축 런북 — "언제 무엇을"까지 말해야 실전이다

(가산점 포인트) 계층 나열에 그치지 않고 시간표로 묶어 말하면
"매일 밤 이걸 실제로 굴려본 사람"의 답이 된다.

```text
T-1일~   : 예상 피크 산정(과거 공개일 실측 × 성장률 + 여유분),
           필요 시 부하 테스트로 서버당 용량 재확인, 런북 공유
T-30분   : scheduled scaling으로 목표 대수 증설 완료 → 워밍업
T-10분   : 신작 캐시 사전 적재, CDN 사전 워밍, 대시보드/알람 확인
T-5분    : 푸시 발송 분할 스케줄 가동, 온콜 대기
T(23:00) : 공개 — p99·에러율·캐시 히트율·DB 커넥션을 실시간 관찰
T+수십 분: 피크 소강 확인 후에도 스케일 인은 천천히
           (2차 피크·재시도 잔여 트래픽 대비, 축소는 보수적으로)
T+1일    : 실측 피크를 기록해 다음 공개일 산정치를 갱신 (피드백 루프)
```

## 4. 꼬리질문 대비 포인트

### "공개 정각에 캐시가 전부 미스 나는 문제는 어떻게 막나요?"

cache stampede 대응 3종 세트로 답한다. ① **사전 적재** — 공개 전에
신작 키를 미리 계산해 넣는다(예측 가능하니 가능한 특권). ② **single
flight** — 미스 시 재계산을 키당 한 요청으로 제한하고 나머지는 결과를
공유한다. ③ **만료 분산** — TTL에 jitter를 줘 동시 만료를 피하고,
인기 키는 만료 전 백그라운드 갱신으로 미스 자체를 없앤다.

### "사전 스케일 아웃 규모는 어떻게 산정하나요?"

근거 있는 산수로 답한다. 분자는 예상 피크 부하 — 지난 공개일들의
실측 피크(RPS, 동시 접속)에 성장 추세와 작품 화제성 보정을 얹고
여유율을 더한다. 분모는 서버 1대의 실측 처리 용량 — 부하 테스트에서
"목표 p99를 지키는 한계 RPS"로 잰다. 나눗셈 결과가 목표 대수다.
여기에 "산정이 틀릴 수 있으니 마지막 방어선(shedding)과 반응형
오토스케일링을 뒤에 둔다"까지 붙이면 완결된다.

### "스케일 아웃을 충분히 했는데도 DB가 죽으면요?"

stateless 계층 증설은 병목을 없애는 게 아니라 **상태 있는 계층으로
밀어 넣는 것**임을 짚는다. 서버가 늘면 DB로 향하는 동시 요청과
커넥션 요구만 커진다. 답은 DB 도달량 축소다 — 캐시 히트율을 올리고
(신작 조회는 캐시 적중률이 높은 대표적 워크로드), 읽기는 레플리카로,
쓰기는 비동기 집계로 뺀다. 그래도 넘치면 DB 앞이 아니라 게이트웨이에서
shedding한다(안쪽에서 버리면 이미 자원을 쓴 뒤다).

### "준비한 용량을 넘는 트래픽이 오면 어떻게 하나요?" (시니어 변별 포인트)

"예측 기반 준비"와 "예측 실패 대비"는 별개의 계층이라는 인식을
보여야 한다. ① 반응형 오토스케일링이 초과분을 따라가게 두되, 따라잡는
수 분간은 ② 게이트웨이에서 우선순위 기반 load shedding으로 비핵심
트래픽(봇, 비핵심 API)부터 거절하고, ③ 핵심 여정(회차 열람, 결제)은
graceful degradation으로 끝까지 지킨다(추천·랭킹은 정적 폴백으로).
그리고 ④ 이번 실측치를 다음 산정에 반영하는 피드백 루프를 언급하면
"한 번 겪고 끝"이 아니라 운영 체계로 말하는 것이 된다.

### "스케일 인은 언제 하나요? 바로 줄이면 안 되나요?"

바로 줄이면 위험하다. 공개 직후 피크가 지나도 2차 파도(늦게 알림을
본 사용자, 재시도 잔여 트래픽)가 올 수 있다. 스케일 아웃은 공격적으로,
스케일 인은 보수적으로가 원칙 — 안정화 시간을 두고 단계적으로 줄이고,
줄일 때도 진행 중 요청을 끊지 않는 graceful shutdown을 지킨다.

## 한 줄 요약

시각을 아는 스파이크는 감지-대응이 아니라 사전 준비의 문제다 —
유입 분산(푸시 분할)부터 CDN 사전 워밍, scheduled scaling + 워밍업,
캐시 사전 적재와 stampede 방지, DB 도달량 축소(비동기 집계)까지
계층별로 준비하고, 예측 실패에 대비한 마지막 방어선(shedding)과
시간 축 런북·피드백 루프까지 갖추는 것이 완결된 답이다.
