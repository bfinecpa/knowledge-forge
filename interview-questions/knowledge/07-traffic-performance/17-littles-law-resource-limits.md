# Little's Law와 자원 한계 설정 — 풀·큐 크기는 감이 아니라 L = λW 산수다

> 핵심 관전 포인트: **Little's Law는 "안정 상태 시스템에서 시스템 안에
> 머무는 요청의 평균 개수 L = 도착률 λ × 평균 체류 시간 W"라는
> 보존 법칙이다. 커넥션 풀, 스레드풀, 큐 같은 모든 bounded 자원의
> 크기는 "그 자원을 동시에 점유하는 요청 수의 상한 선언"이고, 그 동시
> 점유 수가 바로 L = λW로 계산된다.** 그래서 한계 설정은 감이 아니라
> 산수다 — 목표 처리량(λ)과 자원별 점유 시간(W)만 알면 필요한 크기가
> 나오고, 거꾸로 한계를 정하면 그 지점의 최대 부하와 최대 대기 시간이
> 정해진다. 한계는 용량 확장 수단이 아니라 **"여기까지 받고 나머지는
> 빨리 거절한다"는 정책 선언**이다.

---

## 0. 질문 + 의도

**질문**: "커넥션 풀, 스레드풀, 큐 크기 등 자원 한계 설정과
Little's Law의 관계를 설명해주세요."

**출제 의도**: 풀 크기·큐 크기를 감이 아니라 산수(L = λW)로 정하는지
본다. 용량 계획 회의에서 "그냥 넉넉하게요"가 아니라 계산된 숫자를
내는 능력의 유무를 확인하는 질문이다.

## 1. Little's Law 자체 — 왜 성립하는가

편의점 비유가 직관적이다. 손님이 **분당 2명(λ)** 들어오고, 한 손님이
매장에 **평균 5분(W)** 머문다면, 어느 순간이든 매장 안에는 평균
**2 × 5 = 10명(L)** 이 있다. 나가는 만큼 들어오는 안정 상태라면
이 관계는 항상 성립한다.

```
L  =  λ  ×  W
동시에 시스템 안에    도착률      평균 체류 시간
있는 평균 개수      (처리량)
```

이 법칙이 강력한 이유는 **전제가 거의 없기 때문**이다 — 도착 간격의
분포, 처리 순서(FIFO든 우선순위든), 내부 구조와 무관하게, "들어온
만큼 나가는" 안정 상태이기만 하면 성립한다. 그래서 어떤 서버, 어떤
풀, 어떤 큐에도 같은 공식을 적용할 수 있다.

단 하나의 전제가 **안정 상태(λ ≤ 처리 능력)** 다. 유입이 처리 능력을
지속적으로 초과하면 L이 무한히 자라며 공식이 말하는 "평균"이 존재하지
않는다 — 이때는 백프레셔(16번 문서)의 영역이다.

## 2. 자원 한계 설정과의 관계 — 모든 bounded 자원은 같은 공식을 쓴다

서버의 자원 한계(풀 크기, 큐 크기, 세마포어 허용량)는 전부
**"이 자원을 동시에 점유할 수 있는 요청 수의 상한"** 이다. 그리고
실제로 동시에 점유되는 개수가 바로 Little's Law의 L이다:

```
그 자원의 필요 크기 ≈ 통과 TPS(λ) × 그 자원의 점유 시간(W) + 여유분
```

핵심은 **자원마다 W가 다르다**는 것이다. 같은 요청이라도:

| 자원 | 점유 시간 W | 500 TPS 예시 |
|---|---|---|
| 톰캣 스레드 | 요청 전체 응답시간 (예: 100ms) | 500 × 0.1 = 50 |
| DB 커넥션 | 트랜잭션/쿼리 구간만 (예: 50ms) | 500 × 0.05 = 25 |
| 외부 API 세마포어 | 그 호출 구간만 (예: 200ms) | 500 × 0.2 = 100 |

- 자원마다 점유 시간이 다르므로 **"스레드 수 = 커넥션 수"처럼 크기를
  맞추는 건 근거가 없다.** 각각 따로 계산한다.
- 톰캣 스레드풀·HikariCP의 구체적 산정 과정과 검증 메트릭은
  `02-spring/25-thread-pool-connection-pool-sizing.md`에서 다룬다.
  이 문서는 그 계산이 서 있는 **일반 원리**를 다룬다.

공식은 양방향으로 쓴다:

- **정방향(크기 산정)**: 목표 λ와 측정한 W로 필요한 L을 계산한다.
- **역방향(한계 검증)**: 이미 정해진 한계 L과 현재 W로 그 지점이
  감당 가능한 최대 처리량 λ = L / W를 계산한다. 커넥션 25개에 점유
  50ms면 그 DB 앞 최대 통과량은 500 TPS — 그 이상은 물리적으로
  통과하지 못하고 대기 줄이 생긴다.

## 3. 큐 크기 — "허용할 추가 대기 시간"의 선언

큐에도 같은 법칙이 적용된다. 큐 안에 N개가 쌓여 있고 처리율이 λ면,
새로 큐에 들어온 요청의 대기 시간은:

```
큐 대기 시간 W = 큐 길이 N ÷ 처리율 λ
```

이걸 뒤집으면 큐 크기 설정의 진짜 의미가 나온다 —
**큐 크기 = 처리율 × 허용할 최대 추가 대기 시간**.

```java
// Before: "넉넉하게" 큐 10,000 — 의미를 계산해보지 않은 숫자
new ThreadPoolExecutor(10, 10, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(10_000));
// 처리율이 200/s라면 큐가 가득 찼을 때 마지막 요청의 대기 = 50초.
// 클라이언트 타임아웃이 3초라면, 큐의 대부분은 "아무도 기다리지 않는
// 죽은 요청"으로 채워진다 — 처리량은 그대로인데 유효 처리량은 0.

// After: 타임아웃 예산에서 역산한 큐 크기
// 허용 추가 대기 = 1초, 처리율 = 200/s → 큐 크기 = 200
new ThreadPoolExecutor(10, 10, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(200),
    new ThreadPoolExecutor.AbortPolicy());  // 초과분은 즉시 거절
// 큐가 차면 어차피 못 지킬 요청이므로 빨리 실패시켜 상류가 폴백하게 한다.
```

즉 **큐를 키우는 것은 용량을 늘리는 게 아니라 대기 시간을 늘리는
것**이다. 큐 크기는 "버스트를 얼마 동안의 추가 대기를 감수하고 흡수할
것인가"라는 선언이고, 그 대기의 상한은 클라이언트 타임아웃보다 짧아야
의미가 있다.

## 4. 한계 설정의 세 가지 역할 — 왜 무한이 아니라 유한이어야 하는가

Little's Law를 이해하면 "한계를 왜 두는가"에 대한 답이 정리된다.

- **① 뒷단 보호 — 부하의 상한 선언**: 커넥션 풀 크기는 DB에 동시에
  걸릴 수 있는 부하의 상한이다. 한계가 없으면 프론트의 폭주가 그대로
  DB까지 전달돼 가장 비싼 자원부터 무너진다.
- **② 빠른 실패 지점 — 백프레셔의 발화점**: bounded 자원이 가득
  찼다는 것은 "λ가 이 지점의 처리 능력을 초과했다"는 조기 신호다.
  풀 고갈의 acquire timeout, 큐의 거절이 압력을 상류로 되돌린다.
  무한 풀·무한 큐는 이 신호를 없애버려, 문제를 OOM이나 전면 지연으로
  키운 뒤에야 드러낸다.
- **③ 용량 계획의 계산 근거**: 한계가 계산된 숫자면 "트래픽이 2배가
  되면 어디가 먼저 마르는가"를 회의실에서 산수로 답할 수 있다.
  λ가 2배면 모든 지점의 필요 L이 2배 — 현재 한계와 비교해 병목
  지점을 예측하고 증설 순서를 정한다.

그리고 실무에서 가장 중요한 통찰 하나 — **L = λW에서 운영 중 갑자기
변하는 건 대개 W다.** 느린 쿼리 하나, 외부 API 지연 하나로 W가 2배가
되면 같은 트래픽(λ)에서도 필요한 L이 2배가 되어 풀이 마른다. 즉
**풀 고갈은 원인이 아니라 증상**인 경우가 많고, 이때 풀을 늘리는 건
악화된 W를 가리는 진통제일 뿐이다.

## 5. 꼬리질문 대비 포인트

### "풀이 자꾸 고갈되는데, 크기를 늘리면 해결되나요?" (시니어 변별 포인트)

먼저 L = λW의 어느 항이 변했는지 본다. **λ(트래픽)가 늘어난
고갈이면** 증설이 답일 수 있지만, **W(점유 시간)가 늘어난 고갈이면**
풀 확대는 문제를 숨긴다 — 느린 쿼리·락 대기·외부 지연이라는 근본
원인을 두고 커넥션만 늘리면, 늘어난 커넥션이 DB에 더 많은 동시
부하를 걸어 W를 더 악화시키는 악순환이 된다. 판단 재료는 점유 시간
메트릭(커넥션 acquire/usage time, 응답시간 분포)이다. 순서는
"W 정상화(쿼리 튜닝, 트랜잭션 밖으로 외부 호출 빼기) → 그래도
부족하면 계산으로 증설".

### "Little's Law가 안 맞거나 주의해야 하는 상황은?"

- **비안정 상태**: λ > 처리 능력이 지속되는 과부하 중에는 L이 계속
  자라므로 "평균 L" 자체가 없다. 이때 공식은 크기 산정이 아니라
  "터질 때까지의 시간" 계산에나 쓸 수 있다.
- **평균의 함정**: 공식의 W는 평균이다. 응답시간 분포가 꼬리가 길면
  (p99 ≫ 평균) 느린 요청 소수가 자원을 오래 잠식해 평균 기반
  계산보다 실제 필요 L이 커진다. 그래서 계산값에 여유분을 두고,
  최종 숫자는 부하 테스트로 검증한다.
- **버스트**: 평균 λ가 같아도 도착이 몰리면 순간 L이 계산값을
  넘는다. 이 순간 초과분을 흡수하는 것이 큐의 역할이다(3절).

### "사용률(utilization)을 100%에 맞춰 크기를 잡으면 안 되나요?"

안 된다 — 큐잉 이론의 기본 결론은 **사용률이 100%에 다가갈수록 대기
시간이 비선형으로 폭증**한다는 것이다. 도착 간격과 처리 시간에는
변동이 있어서, 여유가 없는 시스템은 작은 버스트도 흡수하지 못하고
대기 줄이 쌓인다. 사용률 70~80%대에서 여유를 두고 운영하는 이유가
이것이고, "평균으로는 감당 가능한데 왜 느리죠?"의 답이기도 하다 —
평균이 아니라 변동이 대기를 만든다.

### "Little's Law를 부하 테스트 설계에도 쓸 수 있나요?" (가산점 포인트)

동시 사용자(VU) 수와 TPS의 환산이 바로 이 공식이다:
`VU = TPS × 사용자당 체류 시간(요청+think time)`. 예를 들어 한
사용자가 요청→응답→think time까지 10초를 쓴다면 3,000 TPS를 내려면
약 30,000 VU가 필요하다. 거꾸로 think time 없이 VU를 잡으면 적은
VU로 높은 TPS가 나오지만 동시 연결 특성이 운영과 달라진다.

### "무한 큐(unbounded queue)는 어떤 경로로 장애가 되나요?"

유입 > 처리가 지속되면 큐 길이 N이 계속 자라고, 대기 시간 N/λ가
클라이언트 타임아웃을 넘는 순간부터 서버는 죽은 요청만 처리하는 좀비
상태가 된다 — 처리량 지표는 정상인데 유효 처리량(goodput)은 0.
최종적으로는 큐가 점유한 메모리로 OOM. 거절을 한 번도 안 하는
시스템은 친절한 게 아니라 실패를 가장 비싼 형태(전면 장애)로 미루는
것이다.

## 한 줄 요약

Little's Law(L = λW)는 "동시에 자원을 점유하는 요청 수 = 처리량 ×
그 자원의 점유 시간"이라는 보존 법칙이고, 커넥션 풀·스레드풀·큐의
크기란 바로 이 L의 상한을 선언하는 일이다 — 자원마다 다른 W로 각각
계산하고, 큐 크기는 "허용할 추가 대기 시간 × 처리율"로 타임아웃
예산에서 역산하며, 풀 고갈은 대개 W 악화의 증상이므로 크기 확대보다
점유 시간부터 의심한다 — 한계는 용량이 아니라 "여기서부터는 빨리
거절한다"는 정책의 숫자다.
