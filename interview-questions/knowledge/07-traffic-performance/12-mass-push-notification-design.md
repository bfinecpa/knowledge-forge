# 대량 푸시/알림 발송 설계 — 발송보다 무서운 것은 발송이 부르는 트래픽이다

> 핵심 관전 포인트: **대량 발송의 골격은 "요청과 발송의 분리"다 — 발송 요청을 큐(Kafka/SQS)에 넣고, 워커 무리가 배치로 꺼내 FCM/APNs 같은 외부 게이트웨이에 병렬 전송한다. 동기 발송이 불가능한 이유는 산수로 나온다: 300만 건을 건당 50ms로 순차 전송하면 `3,000,000 × 0.05 = 150,000초 ≈ 41.7시간`이다. 여기에 ① 중복 발송 방지(멱등 키 — 단 청크 단위가 아니라 수신자 단위여야 부분 실패 시 유실이 없다), ② 실패 처리(일시 오류는 backoff 재시도, 무효 토큰은 재시도 금지 + 토큰 삭제), ③ 외부 게이트웨이 보호(전송 속도 제한)를 얹는다. 그리고 진짜 승부처는 발송 이후다 — 알림을 받은 수백만 명이 동시에 앱을 여는 2차 트래픽이 우리 서버로 돌아온다. 열람률 10%에 그중 70%가 5분 안에 열고 앱 실행당 API 5건이면 `3,000,000 × 0.1 × 0.7 ÷ 300 × 5 = 3,500 TPS`로, 평상시 300 TPS의 11.7배다. 발송 시각을 30분에 펴면 이것이 6분의 1로 내려간다. 발송 시스템은 성공했는데 본진이 죽는 장애가 이 문서의 핵심이다.**

## 0. 질문 + 의도

**질문**: "대량의 푸시/알림 발송을 어떻게 설계하나요?"

**출제 의도**: 발송 자체보다 발송이 유발하는 2차 트래픽(알림 받은 수백만 명이 동시 접속)까지 그리는지 — 시스템 바깥의 피드백 루프를 보는 시야를 확인한다. 큐·워커·재시도는 교과서로 배울 수 있지만, "내가 보낸 알림이 곧 내 서버의 트래픽 폭탄이 된다"는 인과를 스스로 그리는 사람은 시스템을 경계 바깥까지 사고하는 사람이다.

## 1. 왜 동기 발송은 불가능한가 — 요청과 발송의 분리

### 1-1. 먼저 산수로 배제한다

가장 먼저 배제해야 할 설계는 "API 요청 안에서 루프 돌며 발송"이다. 그런데 "느리다"는 말로는 배제가 안 된다. 얼마나 느린지 계산해 보면 이 설계가 검토 대상조차 아니라는 것이 분명해진다.

```
대상 300만 명, FCM 호출 1건 왕복 50ms(= 0.05초)

순차 발송 소요 시간 = 3,000,000 × 0.05 = 150,000초
                    = 150,000 ÷ 3,600 ≈ 41.7시간
```

HTTP 요청 타임아웃은 보통 초 단위이고 길게 잡아도 분 단위다. **41.7시간짜리 HTTP 응답은 존재할 수 없다.**

"그럼 요청 안에서 병렬로 보내면?"이라는 반문이 자연스럽게 나온다. 스레드를 100개 쓰면 계산상 25분이 된다. 그런데 이 방향은 시간 문제를 줄여도 **더 근본적인 문제를 해결하지 못한다.**

```java
// Before: 요청 스레드에서 직접 발송 — 대량이면 즉시 붕괴
@PostMapping("/notifications/broadcast")
public void broadcast(BroadcastRequest req) {
    // 문제 0: 수백만 건을 한 번에 메모리로 올린다 — OOM
    List<User> targets = userRepository.findByMarketingAgreed(true);
    for (User user : targets) {
        fcmClient.send(user.getDeviceToken(), req.getMessage());
        // 문제 1: 41.7시간짜리 HTTP 요청 — 타임아웃으로 애초에 끝까지 못 간다
        // 문제 2: 중간에 서버가 죽으면 "어디까지 보냈는지"가 이 스레드의
        //         스택에만 있었으므로 이 세상에서 사라진다 → 재실행 시 전량 중복 발송
        // 문제 3: 이 요청이 톰캣 스레드를 점유하는 동안 다른 API도 함께 마비된다
        //         (18번 문서의 스레드 고갈)
    }
}
```

**진짜 결함은 문제 2다.** 진행 상태가 요청 스레드의 메모리에만 있다는 것 — 10장 결제 문서의 "진행 상태가 스레드의 스택에만 있다"와 정확히 같은 결함이다. 스레드가 죽으면 "150만 번째까지 보냈다"는 사실이 사라지고, 누구도 이어받을 수 없다. 다시 실행하면 이미 받은 150만 명이 알림을 두 번 받는다.

병렬화는 이 문제를 오히려 악화시킨다 — 어느 스레드가 어디까지 보냈는지가 더 복잡해질 뿐이다.

### 1-2. 그래서 진행 상태를 밖으로 꺼낸다

올바른 골격은 **발송 요청 접수와 실제 발송을 큐로 분리**하는 것이다. 큐가 하는 일의 본질은 "속도 완충"이 아니라 **진행 상태를 우리 프로세스 밖의 내구성 있는 저장소에 두는 것**이다.

```
[발송 요청 API] → 접수만 하고 즉시 202 응답
      ↓
[타겟 조회 배치] → 대상 목록을 청크(예: 1,000명)로 쪼개 메시지 큐에 적재
      ↓
[메시지 큐: Kafka / SQS]  ← 진행 상태가 여기에 있다. 워커가 죽어도 남는다.
      ↓
[발송 워커 N대] → 청크를 꺼내 FCM/APNs 배치 API로 병렬 전송
      ↓
[FCM / APNs] → 각 단말로 푸시
```

**비유는 우체국이다.** 편지 100만 통을 접수 창구에서 직접 배달하지 않는다. 접수(큐 적재)와 배달(워커 발송)을 분리하고, 배달원(워커) 수를 물량에 맞게 늘린다. 그리고 중요한 것은 **어느 편지가 배달됐는지가 배달원의 머릿속이 아니라 대장에 적혀 있다는 점**이다 — 배달원이 바뀌어도 일이 이어진다.

청크 단위로 쪼개는 이유는 둘이다. FCM 등은 한 번의 호출로 여러 토큰에 보내는 **배치 API**를 제공하므로 건당 호출보다 처리량이 수십 배 차이 난다. 그리고 청크가 곧 **재시도의 단위**가 되어 실패 범위를 좁혀 준다.

### 1-3. 워커 수는 목표 시간에서 역산한다

"워커를 몇 대 띄우나"는 감으로 정하지 않는다. 17번 문서의 `L = λW`를 그대로 쓴다. 단위는 초로 통일한다.

```
[1단계] 목표에서 필요 처리량 λ를 구한다
  300만 건을 30분(= 1,800초) 안에
  λ = 3,000,000 ÷ 1,800 ≈ 1,666.7 건/초

[2단계] 워커 1대의 처리량을 실측값에서 구한다
  배치 API 한 번에 500건, 그 호출의 왕복 시간 W = 1초
  워커 1대 = 500 ÷ 1 = 500 건/초

[3단계] 필요한 동시 발송 주체 수 L을 구한다
  L = 1,666.7 ÷ 500 = 3.33
  올려서 4대. 여기에 여유와 장애 대비를 얹는다.
```

3단계가 `L = λW`인 이유를 한 번 더 풀면 이렇다. 배치 단위로 보면 초당 필요한 배치 호출은 `1,666.7 ÷ 500 = 3.33`건이고, 호출 하나가 1초 동안 진행 중이므로 동시에 진행 중이어야 하는 호출 수는 `3.33 × 1 = 3.33`개다. 워커 하나가 동시에 호출 하나를 담당하니 워커 수가 그 값이 된다.

**그런데 이 계산의 결론은 "4대를 띄우면 된다"가 아니다.** 상한이 우리 쪽에 없기 때문이다.

- **게이트웨이의 속도 제한.** FCM·APNs는 자기 쪽 한도를 갖고 있다. 워커를 40대로 늘려도 그 한도를 넘으면 429가 돌아오고, 재시도가 겹치면 전체 발송이 오히려 느려진다. **병목이 우리 쪽에서 상대 쪽으로 넘어가는 지점**이 있다.
- **2차 트래픽을 받아낼 본진 용량.** 이것이 3절의 주제다. 빨리 보낼수록 돌아오는 트래픽이 뾰족해진다. **발송 속도의 진짜 상한은 우리 API 서버가 감당할 수 있는 유입량이다.**

즉 워커 수 계산은 하한을 주고, 상한은 다른 데서 온다.

## 2. 신뢰성 3종 세트 — 중복 방지, 재시도, DLQ

### 2-1. 중복 발송 방지 — 멱등 키의 단위가 중요하다

큐 기반 시스템은 대부분 **at-least-once**(최소 1회 전달)다. 워커가 발송 후 ack 직전에 죽으면 같은 청크가 다시 소비된다 — 즉 **중복 발송은 설계하지 않으면 반드시 일어난다.** 11번 문서에서 본 "타임아웃은 성공인지 실패인지 알 수 없다"는 회색지대가 여기서도 그대로 적용된다.

여기서 실무가 자주 틀리는 것이 **멱등 키의 단위**다. 청크 단위로 잡으면 이런 코드가 된다.

```java
// 흔하지만 위험한 방식: 청크 단위 멱등 키
String dedupKey = "push:" + campaignId + ":" + chunkId;
if (Boolean.FALSE.equals(redis.opsForValue().setIfAbsent(dedupKey, "sent", Duration.ofDays(1)))) {
    return;   // 이미 처리된 청크 -> 스킵
}
fcmClient.sendBatch(chunk);   // 1,000명 발송
```

문제는 **부분 실패**다. 위 코드는 키를 먼저 세우고 발송한다. 1,000명 중 400명까지 보내고 워커가 죽으면 어떻게 되는가.

```
t=0   dedupKey 설정 성공 ("이 청크는 처리했다")
t=1   400명 발송 완료
t=2   워커 사망
t=3   다른 워커가 같은 청크를 재소비
      -> dedupKey가 이미 있으므로 스킵
      -> 나머지 600명은 알림을 영원히 받지 못한다
```

순서를 바꿔 발송 후에 키를 세우면 반대 문제가 된다 — 400명이 두 번 받는다. **청크 단위로는 이 딜레마를 벗어날 수 없다.** 청크가 원자적으로 처리되지 않기 때문이다.

그래서 멱등 키는 **수신자 단위**여야 한다. 키의 구성은 `캠페인 식별자 + 수신자 식별자`다. 두 요소가 모두 필요한 이유가 각각 있다.

- **캠페인 식별자가 없으면** 같은 사용자에게 다른 캠페인을 보낼 수 없다. 두 번째 캠페인이 중복으로 판정된다.
- **수신자 식별자가 없으면** 위의 부분 실패 문제가 그대로 남는다.

그리고 방어선은 Redis가 아니라 **DB의 유니크 제약**에 두는 것이 안전하다. Redis는 만료되거나 유실될 수 있고, 무엇보다 "확인 후 발송" 사이의 경쟁 조건을 완전히 막지 못한다.

```sql
-- 발송 이력 테이블. (campaign_id, user_id)에 유니크 제약이 실제 방어선이다.
CREATE TABLE push_delivery (
    campaign_id BIGINT      NOT NULL,
    user_id     BIGINT      NOT NULL,
    sent_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (campaign_id, user_id)   -- 두 번째 INSERT는 DB가 거부한다
);
```

```java
// 수신자 단위로 "먼저 선점하고 보낸다"
public void sendChunk(long campaignId, List<Target> chunk) {
    // ① 아직 안 보낸 사람만 골라낸다. ON CONFLICT DO NOTHING이므로
    //    이미 있는 행은 조용히 건너뛰고, 새로 들어간 행만 반환된다.
    //    이 한 문장이 "확인"과 "선점"을 원자적으로 합친다.
    List<Long> claimed = deliveryRepository.claim(campaignId, userIdsOf(chunk));
    if (claimed.isEmpty()) return;

    // ② 선점한 사람에게만 보낸다. 재소비되면 ①에서 전부 걸러지므로
    //    부분 실패 지점부터 정확히 이어진다.
    var result = fcmClient.sendBatch(tokensOf(claimed));

    // ③ 영구 실패한 수신자는 이력을 되돌린다 — 안 그러면 재시도 대상에서
    //    빠져 "보내지도 않았는데 보낸 것으로 기록된" 상태가 남는다.
    deliveryRepository.releasePermanentFailures(campaignId, result.permanentFailures());
}
```

```sql
-- claim()의 구현: 선점과 확인이 한 문장이다
INSERT INTO push_delivery (campaign_id, user_id)
SELECT ?, u FROM unnest(?::bigint[]) AS u
ON CONFLICT (campaign_id, user_id) DO NOTHING
RETURNING user_id;   -- 실제로 새로 선점된 사람만 돌아온다
```

같은 알림이 두 번 오는 것은 단순 버그가 아니라 **사용자 이탈(알림 끄기, 앱 삭제) 요인**이라는 점까지 말하면 좋다 — 멱등성이 UX 문제이기도 하다는 시각이다. 그리고 알림을 끈 사용자는 다시 돌아오지 않으므로, 이 실수의 대가는 영구적이다.

### 2-2. 재시도 — 발송 도메인의 실패 분류

11번 문서가 재시도의 일반론(backoff, jitter, 증폭, 재시도 예산)을 다루므로 여기서는 반복하지 않는다. 발송 도메인에서 특별한 것은 **실패의 종류가 셋이고 대응이 전부 다르다**는 점이다.

| 응답 | 무엇을 뜻하나 | 재시도 | 추가로 해야 할 일 |
|---|---|---|---|
| 5xx, 타임아웃 | 게이트웨이의 일시적 문제 | 한다 (backoff + jitter) | — |
| 429 | 우리가 너무 빨리 보냈다 | 한다 (지시된 시간만큼 대기) | 발송 속도 자체를 낮춘다 |
| 토큰 무효 | 앱 삭제, 토큰 만료, 재발급 | **안 한다** | **그 토큰을 비활성화한다** |

세 번째가 이 도메인의 핵심이고 가장 자주 빠진다. 토큰이 무효라는 응답은 몇 번 재시도해도 영원히 같은 응답이 온다. 그런데 **재시도를 안 하는 것만으로는 부족하다.**

```
무효 토큰을 지우지 않으면:

  1차 캠페인: 대상 300만, 무효 3만 -> 실패 3만
  2차 캠페인: 대상 300만(무효 3만 그대로) -> 또 실패 3만
  3차 캠페인: 무효가 3.5만으로 늘어남 -> 또 실패
  ...

  발송량과 실패율이 캠페인마다 계속 부풀어 오른다.
  더 나쁜 것: 실패율이 높으면 게이트웨이가 우리를
  스팸 발신자로 취급해 전송 품질을 낮출 수 있다.
```

그래서 **무효 토큰 정리를 발송 파이프라인의 정규 피드백 루프로 설계**해야 한다(가산점 포인트). 발송 결과를 읽어 무효 토큰을 비활성화하는 경로가 파이프라인의 일부여야 하고, 예외 처리의 곁가지가 아니다.

```java
// 실패를 종류별로 갈라 대응한다
for (var failure : result.failures()) {
    switch (failure.reason()) {
        // 재시도해도 영원히 실패한다. 토큰을 지우는 것이 본질적인 대응이다.
        case UNREGISTERED, INVALID_ARGUMENT ->
                deviceTokenRepository.deactivate(failure.token());
        // 우리가 너무 빨랐다. 개별 재시도보다 발송 속도를 낮추는 것이 먼저다.
        case QUOTA_EXCEEDED -> {
            sendRateLimiter.backOff(failure.retryAfter());
            retryQueue.publish(failure.target(), failure.retryAfter());
        }
        // 일시 오류. backoff + jitter로 재시도 (11번 문서).
        case UNAVAILABLE, INTERNAL ->
                retryQueue.publish(failure.target(), nextBackoffWithJitter(failure));
    }
}
```

### 2-3. DLQ — 버리는 곳이 아니라 처리해야 할 목록이다

재시도 한도를 소진한 청크는 버리지 말고 **DLQ(Dead Letter Queue)**로 보낸다. DLQ는 "실패한 메시지가 모이는 별도 큐"다.

여기서 중요한 것은 DLQ가 **쓰레기통이 아니라 작업 목록**이라는 점이다. 그러려면 셋이 정해져 있어야 한다.

- **누가 언제 본다.** DLQ 적재량이 임계를 넘으면 알림이 가야 한다. 아무도 안 보는 DLQ는 조용히 유실하는 것과 같다. DLQ 적재량 자체가 훌륭한 **장애 감지 지표**다.
- **재발송할 것과 폐기할 것을 구분한다.** 게이트웨이 장애로 실패한 것은 재발송 대상이고, 무효 토큰으로 실패한 것은 폐기 대상이다. 2-2의 분류가 여기서 다시 쓰인다.
- **재투입이 안전하다.** 2-1의 수신자 단위 멱등 키가 있으면 DLQ를 통째로 다시 넣어도 이미 받은 사람은 다시 받지 않는다. **멱등성이 없으면 DLQ 재처리 자체가 위험한 작업이 된다.**

마지막 항목이 핵심이다. DLQ는 멱등성이 있을 때만 쓸모가 있는 장치다.

## 3. 발송 속도 제어 — 그리고 이 질문의 진짜 핵심, 2차 트래픽

### 3-1. 외부 게이트웨이 보호

워커를 무한정 늘려 FCM/APNs를 두들기면 게이트웨이 측 속도 제한에 걸려 오히려 전체 발송이 느려지거나 차단된다. 워커 수 × 배치 크기로 초당 발송량 상한을 정해 두고 조절한다 — 08번 문서의 token bucket이 그대로 쓰인다.

여기서 주의할 것은 **429에 대한 개별 재시도가 상황을 악화시킨다**는 점이다. 429는 "너무 빠르다"는 신호이므로, 그 메시지만 재시도하는 것이 아니라 **발송 속도 자체를 낮춰야** 한다. 개별 재시도만 하면 같은 속도로 계속 밀면서 재시도까지 얹는 셈이 되어 11번 문서의 retry storm이 된다.

### 3-2. 2차 트래픽 — 발송 성공이 곧 우리 서버의 부하

여기가 시니어와 주니어가 갈리는 지점이다. 푸시 발송은 시스템 바깥으로 나간 뒤 **피드백 루프가 되어 돌아온다.**

```
푸시 300만 건 발송 완료 (발송 시스템은 성공!)
      ↓ 수 초 ~ 수 분 내
알림 탭 → 앱 실행 → 로그인 갱신, 홈 API, 배너, 목록, 이미지 메타...
      ↓
API 서버 / DB에 평시 십수 배 트래픽 스파이크
      ↓
발송 시스템 장애가 아니라 "본진" 장애
```

이것을 숫자로 만들어야 설계가 된다. 아래 비율들은 서비스마다 다르므로 **가정값이고, 실제로는 자기 서비스의 과거 캠페인 로그에서 얻어야 한다.**

```
[가정] 열람률 10%, 열람자 중 70%가 발송 후 5분 안에 열람,
       앱 실행 1회당 API 요청 5건

① 앱을 여는 사람      3,000,000 × 0.10 = 300,000명
② 5분 안에 여는 사람  300,000 × 0.70   = 210,000명
③ 앱 실행 유입        210,000 ÷ 300초  = 700 건/초
④ API 유입            700 × 5          = 3,500 TPS

평상시가 300 TPS라면  3,500 ÷ 300 ≈ 11.7배
```

**발송 시스템의 모든 지표는 초록색인데 API 서버가 죽는다.** 발송 성공률 100%, 큐 lag 0, DLQ 0건. 그런데 본진은 평시의 11.7배를 맞고 있다.

### 3-3. 대비책 세 층위 — 그리고 jitter의 효과를 계산한다

**① 발송 시각 분산(jitter).** 이것이 가장 싸고 효과가 크다. 300만 건을 5분에 몰아 보내지 말고 30분 창에 걸쳐 흘려보낸다. 위 계산의 분모가 바뀐다.

```
5분(300초)에 집중  : 210,000 ÷ 300  = 700 건/초  -> API 3,500 TPS
30분(1,800초)에 분산: 210,000 ÷ 1,800 ≈ 116.7 건/초 -> API 583 TPS

  3,500 ÷ 583 = 6배 감소
```

30분에 펴기만 해도 필요 서버 용량이 6분의 1이 된다. **요구사항을 완화해 스파이크 자체를 평탄화하는 것**이 인프라를 6배 늘리는 것보다 언제나 싸다. 마케팅 알림은 대부분 "지금 즉시"일 필요가 없으므로 이 완화가 가능하다.

11번 문서의 jitter와 목적이 같다는 점을 짚어 두면 좋다 — 그쪽은 재시도 시점을 흩어 동시성을 깨고, 여기는 발송 시점을 흩어 동시성을 깬다. **같은 도구를 다른 축에 쓰는 것이다.**

대가도 명시해야 한다. 분산하면 **누군가는 30분 늦게 받는다.** 한정 수량 이벤트 알림을 30분에 걸쳐 보내면 먼저 받은 사람이 유리해져 공정성 문제가 생긴다. 그런 캠페인은 분산 대상이 아니고, 대신 대기열(14번 문서)로 유입을 제어해야 한다.

```java
// 발송 시각 분산: 청크마다 발송 예정 시각을 흩어 큐에 넣는다
public void schedule(long campaignId, List<List<Target>> chunks, Duration window) {
    // 창 전체에 균등하게 펴되, 청크 경계에서 뭉치지 않게 청크 간 간격을 계산한다
    long stepMillis = window.toMillis() / Math.max(1, chunks.size());
    for (int i = 0; i < chunks.size(); i++) {
        // 균등 간격 + 소량의 무작위 흔들기. 균등만 쓰면 각 step 경계에
        // 정확히 몰려 미세한 톱니 파형이 남는다.
        long delay = i * stepMillis + random.nextLong(stepMillis);
        sendQueue.publishAfter(new SendChunk(campaignId, chunks.get(i)),
                               Duration.ofMillis(delay));
    }
}
```

**② 랜딩 경로 준비.** 알림 클릭이 도달하는 화면(이벤트 페이지, 신작 목록)을 미리 캐시에 채워 오리진·DB까지 오는 요청을 차단한다. 05번 문서의 CDN 사전 워밍과 5장의 캐시 스탬피드 방지가 그대로 적용되므로 여기서 다시 설명하지 않는다. 다만 이 도메인의 특이점 하나는 짚을 만하다 — **알림 클릭은 전원이 정확히 같은 화면으로 간다.** 즉 캐시 적중률을 올릴 여지가 매우 크고, 반대로 그 한 화면이 미스 나면 전량이 오리진으로 간다.

**③ 사전 스케일 아웃.** 대량 발송은 **우리가 시각을 아는** 이벤트이므로 13번 문서의 정시 스파이크 대비가 그대로 적용된다. 반응형 오토스케일링은 원리적으로 늦으므로 발송 시각 전에 미리 늘려 둔다. 여기서 중요한 점은 발송 시각이 **우리 손에 있다**는 것이다 — 13번 문서의 신작 공개는 시각이 정해져 있어 우리가 못 바꾸지만, 발송은 우리가 정한다. 그래서 ①의 분산이라는 수단이 추가로 존재한다.

### 3-4. 알림 종류별 큐 분리

마지막으로 파이프라인 자체를 나눠야 한다. 주문 완료·결제 알림 같은 **트랜잭션 알림은 분산 대상이 아니다** — 즉시성이 요구사항이다.

그런데 이것이 마케팅 발송과 같은 큐에 있으면 문제가 생긴다.

```
큐: [마케팅 300만 건] ... [결제 완료 알림 1건]
                              ↑
              앞의 300만 건이 처리될 때까지 기다린다.
              30분 분산 발송이면 이 알림도 최대 30분 늦는다.
```

이것이 **head-of-line blocking**(선두 차단 — 맨 앞의 것이 뒤의 전부를 막는 현상)이다. 결제했는데 알림이 30분 뒤에 오면 사용자는 결제가 실패한 줄 안다.

그래서 우선순위별로 큐(토픽)를 분리하고 **워커 풀도 나눈다.** 큐만 나누고 워커를 공유하면 워커가 전부 마케팅 청크를 처리하는 동안 트랜잭션 큐는 여전히 대기한다. 이것이 18번 문서의 **bulkhead**와 정확히 같은 발상이다 — 자원을 분리해 한쪽의 폭주가 다른 쪽의 자원을 잠식하지 못하게 하는 것.

```yaml
# 큐와 워커를 함께 나눈다. 큐만 나누면 격리가 성립하지 않는다.
notification:
  transactional:
    topic: push.transactional
    workers: 4          # 적은 양, 즉시 처리. 항상 여유가 있어야 한다.
    jitter: none        # 분산하지 않는다 — 즉시성이 요구사항이다
  marketing:
    topic: push.marketing
    workers: 8          # 많은 양, 느려도 된다
    jitter: 30m         # 30분 창에 분산 (3-3의 계산 근거)
```

## 4. 꼬리질문 대비 포인트

### "같은 알림이 두 번 가는 걸 어떻게 막나요?"

큐 기반 시스템은 at-least-once가 기본이라 중복 소비는 전제 조건이다. 발송 단위로 멱등 키를 만들어 "처음 한 번만" 통과시킨다. 완벽한 exactly-once는 분산 시스템에서 비용이 매우 크므로, **"전달은 at-least-once로 하되 발송 시점의 멱등 처리로 사용자 관점 1회를 보장한다"**고 답하는 것이 정석이다.

한 단계 더 들어가면 **키의 단위**를 말할 수 있다. 청크 단위 키는 부분 실패에서 무너진다 — 1,000명 중 400명 보내고 죽으면, 키를 먼저 세웠으면 600명이 영구 유실되고 나중에 세웠으면 400명이 중복이다. 그래서 키는 `캠페인 식별자 + 수신자 식별자`여야 하고, 방어선은 만료·유실이 있는 Redis가 아니라 **DB의 유니크 제약**에 둔다. `INSERT ... ON CONFLICT DO NOTHING ... RETURNING`으로 확인과 선점을 한 문장에 합치면 경쟁 조건도 함께 사라진다.

### "수백만 건을 30분 안에 보내야 한다면 워커 수는 어떻게 정하나요?"

감이 아니라 산수로 답한다. 목표 처리량 `λ = 3,000,000 ÷ 1,800 ≈ 1,666.7건/초`. 워커 1대가 배치 API로 초당 500건을 처리한다고 실측되면 `1,666.7 ÷ 500 = 3.33` → 최소 4대 + 여유분. 이것이 `L = λW`의 형태라는 점(초당 필요 배치 호출 3.33건 × 호출당 1초 = 동시 진행 3.33건)까지 말하면 좋다.

그리고 **이 계산은 하한만 준다**는 점이 답의 핵심이다. 상한은 우리 쪽 능력이 아니라 두 곳에서 온다 — FCM/APNs의 속도 제한(넘으면 429가 오고 재시도가 겹쳐 오히려 느려진다)과, **2차 트래픽을 받아낼 본진 용량**이다. 후자를 말하는 것이 이 질문의 진짜 관전 포인트다: 빨리 보낼수록 돌아오는 트래픽이 뾰족해지므로, 발송 속도는 우리 API 서버의 유입 한계에서 거꾸로 정해진다.

### "발송 도중 워커가 죽으면 어떻게 되나요?"

큐의 ack 메커니즘 덕분에 미완료 청크는 다른 워커에 재전달된다(Kafka는 컨슈머 리밸런싱, SQS는 visibility timeout 만료). 이때 이미 절반 보낸 청크가 재처리될 수 있으므로 **2-1의 멱등 처리와 결합되어야** 유실도 중복도 없는 그림이 완성된다 — 재시도와 멱등성은 한 쌍이라는 점이 포인트다.

여기서 수신자 단위 멱등 키의 가치가 드러난다. 청크 단위였다면 400명까지 보낸 청크가 재전달될 때 전부 스킵되거나 전부 재발송되지만, 수신자 단위면 **정확히 401번째부터 이어진다.** 워커 사망이 특별한 사고가 아니라 정상 경로의 일부가 되는 것이 좋은 설계다.

### "알림을 보냈더니 서버가 죽었습니다. 발송 시스템 문제인가요?" (시니어 변별 포인트)

발송 시스템은 정상이었을 가능성이 높다 — 죽은 것은 알림을 받은 사용자들이 몰려온 **본진(API/DB)**이다. 3-2의 계산대로 열람률 10%, 5분 집중, 앱 실행당 API 5건이면 `3,000,000 × 0.1 × 0.7 ÷ 300 × 5 = 3,500 TPS`로 평상시의 11.7배가 된다. 이때 발송 시스템 지표는 전부 초록색이다 — 발송 성공률 100%, 큐 lag 0, DLQ 0건.

**발송 성공률만 보는 팀은 이 장애를 예측하지 못한다.** 그래서 대량 발송을 "발송 작업"이 아니라 **"트래픽 이벤트"**로 취급해야 하고, 발송 프로세스의 체크리스트에 발송 시각 분산·랜딩 캐시 워밍·사전 스케일 아웃이 들어가야 한다.

가장 실무적인 답은 관측 쪽이다. **"발송량 그래프와 API 트래픽 그래프를 같은 대시보드, 같은 시간축에 두겠다"** — 두 그래프가 몇 분 간격으로 이어지는 것을 눈으로 본 팀은 다음부터 반드시 분산한다.

### "즉시 가야 하는 알림과 마케팅 알림이 같은 큐에 있으면 무슨 문제가 생기나요?"

마케팅 캠페인 수백만 건이 큐를 채우면 그 뒤에 줄 선 결제 완료 알림이 수십 분 지연된다 — **head-of-line blocking**이다. 30분 분산 발송을 하고 있으면 결제 알림도 최대 30분 늦고, 사용자는 결제가 실패한 줄 안다.

대응은 우선순위별로 큐(토픽)를 분리하는 것인데, **큐만 나누는 것으로는 부족하다는 점**을 짚어야 한다. 워커 풀을 공유하면 모든 워커가 마케팅 청크를 처리하는 동안 트랜잭션 큐는 여전히 대기한다. 큐와 워커를 함께 나눠야 격리가 성립한다 — 18번 문서의 **bulkhead**와 같은 발상이고, "자원을 분리해 폭발 반경을 제한한다"는 원리가 메시징 계층에 적용된 형태다.

## 한 줄 요약

대량 푸시 발송은 "큐로 분리 → 청크 배치 발송 → 멱등·재시도·DLQ로 신뢰성 확보"가 골격이고, 동기 발송은 `3,000,000 × 0.05 = 41.7시간`이라는 산수로 배제되지만 진짜 결함은 시간이 아니라 진행 상태가 요청 스레드에만 있다는 것이다 — 멱등 키는 청크가 아니라 **수신자 단위**여야 부분 실패에서 유실도 중복도 없고(DB 유니크 제약이 실제 방어선), 무효 토큰은 재시도 금지에 그치지 않고 삭제까지 해야 실패율이 캠페인마다 부풀지 않는다. 그리고 설계의 완성은 시스템 바깥에 있다 — 발송이 성공하는 순간 그 알림들이 트래픽이 되어 돌아오므로(열람률 10%·5분 집중·앱 실행당 API 5건이면 `3,500 TPS`, 평시의 11.7배), 발송 시각을 30분에 분산해 그것을 6분의 1로 낮추고 랜딩 캐시 워밍과 사전 스케일 아웃을 발송 체크리스트에 넣어야 하며, 즉시성이 필요한 트랜잭션 알림은 큐와 워커를 함께 분리해 head-of-line blocking에서 지킨다.
