# 대량 푸시/알림 발송 설계 — 발송보다 무서운 것은 발송이 부르는 트래픽이다

> 핵심 관전 포인트: **대량 발송의 골격은 "요청과 발송의 분리"다 —
> 발송 요청을 큐(Kafka/SQS)에 넣고, 워커 무리가 배치로 꺼내
> FCM/APNs 같은 외부 게이트웨이에 병렬 전송한다. 여기에
> ① 중복 발송 방지(멱등 키), ② 실패 처리(재시도 + DLQ),
> ③ 외부 게이트웨이 보호(전송 속도 제한)를 얹는다.
> 그리고 진짜 승부처는 발송 이후다: 알림을 받은 수백만 명이
> 동시에 앱을 여는 2차 트래픽 스파이크까지 설계에 포함해
> 발송 시각 분산(jitter)과 사전 스케일 아웃으로 대비한다.**

---

## 0. 질문 + 의도

**질문**: "대량의 푸시/알림 발송을 어떻게 설계하나요?"

**출제 의도**: 발송 자체보다 발송이 유발하는 2차 트래픽(알림 받은 수백만
명이 동시 접속)까지 그리는지 — 시스템 바깥의 피드백 루프를 보는 시야를
확인한다. 큐·워커·재시도는 교과서로 배울 수 있지만, "내가 보낸 알림이
곧 내 서버의 트래픽 폭탄이 된다"는 인과를 스스로 그리는 사람은
시스템을 경계 바깥까지 사고하는 사람이다.

## 1. 왜 동기 발송은 불가능한가 — 요청과 발송의 분리

가장 먼저 배제해야 할 설계는 "API 요청 안에서 루프 돌며 발송"이다.

```java
// Before: 요청 스레드에서 직접 발송 — 대량이면 즉시 붕괴
@PostMapping("/notifications/broadcast")
public void broadcast(BroadcastRequest req) {
    List<User> targets = userRepository.findByMarketingAgreed(true); // 수백만 건 로드
    for (User user : targets) {
        fcmClient.send(user.getDeviceToken(), req.getMessage());
        // 문제 1: 건당 수십 ms × 수백만 건 = 몇 시간짜리 HTTP 요청
        // 문제 2: 중간에 서버가 죽으면 어디까지 보냈는지 모름 → 재실행 시 중복 발송
        // 문제 3: 요청 스레드가 인질로 잡혀 다른 API까지 마비
    }
}
```

올바른 골격은 **발송 요청 접수와 실제 발송을 큐로 분리**하는 것이다.

```
[발송 요청 API] → 접수만 하고 즉시 202 응답
      ↓
[타겟 조회 배치] → 대상 목록을 청크(예: 1,000명)로 쪼개 메시지 큐에 적재
      ↓
[메시지 큐: Kafka / SQS]  ← 여기가 완충 지대 (버퍼)
      ↓
[발송 워커 N대] → 청크를 꺼내 FCM/APNs 배치 API로 병렬 전송
      ↓
[FCM / APNs] → 각 단말로 푸시
```

- 비유: 우체국이다. 편지 100만 통을 접수 창구에서 직접 배달하지 않는다.
  접수(큐 적재)와 배달(워커 발송)을 분리하고, 배달원(워커) 수를
  물량에 맞게 늘린다.
- 청크 단위로 쪼개는 이유: FCM 등은 한 번의 호출로 여러 토큰에 보내는
  배치 API를 제공한다. 건당 호출보다 처리량이 수십 배 차이 난다.
  그리고 청크가 곧 **재시도의 단위**가 되어 실패 범위를 좁혀준다.

## 2. 신뢰성 3종 세트 — 중복 방지, 재시도, DLQ

### ① 중복 발송 방지 (멱등성)

큐 기반 시스템은 대부분 **at-least-once**(최소 1회 전달)다.
워커가 발송 후 ack 직전에 죽으면 같은 청크가 다시 소비된다 —
즉 **중복 발송은 설계하지 않으면 반드시 일어난다.**

```java
// After: 발송 이력 키로 멱등 처리
String dedupKey = "push:" + campaignId + ":" + chunkId;
Boolean first = redis.opsForValue()
        .setIfAbsent(dedupKey, "sent", Duration.ofDays(1)); // SETNX
if (Boolean.FALSE.equals(first)) {
    return; // 이미 처리된 청크 → 스킵 (재소비돼도 사용자에겐 1번만 감)
}
fcmClient.sendBatch(chunk);
```

같은 알림이 두 번 오는 것은 단순 버그가 아니라 **사용자 이탈(알림 끄기,
앱 삭제) 요인**이라는 점까지 말하면 좋다 — 멱등성이 UX 문제이기도 하다는 시각.

### ② 재시도 — 실패의 종류를 나눠서

- **일시 오류**(FCM 5xx, 타임아웃): exponential backoff + jitter로 재시도.
  게이트웨이가 이미 과부하일 수 있으므로 즉시 재시도는 retry storm으로
  장애를 증폭시킨다.
- **영구 오류**(토큰 만료·무효, 앱 삭제): 재시도해도 소용없다.
  **즉시 포기하고 해당 토큰을 DB에서 비활성화**한다. 이걸 안 하면
  죽은 토큰에 매번 발송을 시도해 발송량과 실패율이 계속 부풀어 오른다.
  (가산점 포인트: 무효 토큰 정리를 발송 파이프라인의 정규 피드백
  루프로 설계한다고 언급)

### ③ DLQ (Dead Letter Queue)

재시도 한도를 소진한 청크는 버리지 말고 DLQ로 보낸다.
장애 복구 후 DLQ만 재처리하면 유실 없이 마무리할 수 있고,
DLQ 적재량 자체가 훌륭한 **장애 감지 지표**가 된다.

## 3. 발송 속도 제어 — 그리고 이 질문의 진짜 핵심, 2차 트래픽

### 외부 게이트웨이 보호

워커를 무한정 늘려 FCM/APNs를 두들기면 게이트웨이 측 rate limit에
걸려 오히려 전체 발송이 느려지거나 차단된다. 워커 수 × 배치 크기로
**초당 발송량 상한을 정해두고 token bucket 등으로 조절**한다.

### 2차 트래픽 — 발송 성공이 곧 우리 서버의 부하

여기가 시니어와 주니어가 갈리는 지점이다. 푸시 발송은 시스템 바깥으로
나간 뒤 **피드백 루프가 되어 돌아온다**:

```
푸시 100만 건 발송 완료 (발송 시스템은 성공!)
      ↓ 수 초 ~ 수 분 내
알림 탭 → 앱 실행 → 로그인 갱신, 홈 API, 랜딩 페이지 조회...
      ↓
API 서버 / DB에 평시 수십 배 트래픽 스파이크  ← 발송 시스템 장애가 아니라 "본진" 장애
```

대비책은 세 층위로 말한다:

1. **발송 시각 분산 (jitter/스로틀링)** — 100만 건을 1분에 다 쏘지
   않고 10~30분 창(window)에 걸쳐 흘려보낸다. 마케팅 알림은 대부분
   "지금 즉시"일 필요가 없다 — **요구사항을 완화해 스파이크 자체를
   평탄화**하는 것이 가장 싼 해법이다.
2. **랜딩 경로 캐시 준비** — 알림 클릭이 도달하는 화면(이벤트 페이지,
   신작 목록)을 CDN/캐시에 미리 워밍해 오리진·DB까지 오는 요청을 차단.
3. **사전 스케일 아웃** — 대량 발송은 예측 가능한 이벤트이므로,
   발송 시각 전에 API 서버를 미리 늘려둔다 (오토스케일링은 반응이
   늦어 스파이크 초반을 못 받는다).

단, 주문 완료·결제 알림 같은 **트랜잭션 알림은 분산 대상이 아니다** —
즉시성이 요구사항이므로 마케팅성 대량 발송과 파이프라인(우선순위 큐 분리)을
나눠야 한다는 점을 덧붙이면 설계가 입체적으로 보인다.

## 4. 꼬리질문 대비 포인트

### "같은 알림이 두 번 가는 걸 어떻게 막나요?"

큐 기반 시스템은 at-least-once가 기본이라 중복 소비는 전제 조건이다.
발송 단위(캠페인 ID + 청크 ID)로 멱등 키를 만들어 Redis SETNX나
DB unique 제약으로 "처음 한 번만" 통과시킨다. 완벽한 exactly-once는
분산 시스템에서 비용이 매우 크므로, "전달은 at-least-once로 하되
발송 시점에 멱등 처리로 사용자 관점 1회를 보장한다"고 답하는 것이
정석이다.

### "수백만 건을 30분 안에 보내야 한다면 워커 수는 어떻게 정하나요?"

감이 아니라 산수로 답한다. 목표 처리량 = 3,000,000건 ÷ 1,800초
≈ 1,700건/초. 워커 1대가 배치 API로 초당 500건을 처리한다고 실측되면
최소 4대 + 여유분. 단, 상한은 우리 쪽 능력이 아니라 **FCM/APNs의
rate limit과 2차 트래픽을 받아낼 본진 용량**이 결정한다는 점을
같이 말해야 한다 (Little's Law식 용량 산정 습관 — 가산점 포인트).

### "발송 도중 워커가 죽으면 어떻게 되나요?"

큐의 ack 메커니즘 덕분에 미완료 청크는 다른 워커에 재전달된다
(Kafka는 컨슈머 리밸런싱, SQS는 visibility timeout 만료).
이때 이미 절반 보낸 청크가 재처리될 수 있으므로 2번의 멱등 처리와
결합되어야 유실도 중복도 없는 그림이 완성된다 — 재시도와 멱등성은
한 쌍이라는 점이 포인트.

### "알림을 보냈더니 서버가 죽었습니다. 발송 시스템 문제인가요?" (시니어 변별 포인트)

발송 시스템은 정상이었을 가능성이 높다 — 죽은 것은 알림을 받은
사용자들이 몰려온 **본진(API/DB)**이다. 발송 성공률만 보는 팀은 이
장애를 예측하지 못한다. 대량 발송을 "트래픽 이벤트"로 취급해
발송 시각 분산, 랜딩 캐시 워밍, 사전 스케일 아웃을 발송 프로세스의
체크리스트에 포함해야 한다. "발송량 그래프와 API 트래픽 그래프를
같은 대시보드에 두겠다"고 답하면 운영 감각까지 보여줄 수 있다.

### "즉시 가야 하는 알림과 마케팅 알림이 같은 큐에 있으면 무슨 문제가 생기나요?"

마케팅 캠페인 수백만 건이 큐를 채우면 그 뒤에 줄 선 결제 완료 알림이
수십 분 지연된다 — head-of-line blocking. 우선순위별로 큐(토픽)를
분리하고 워커 풀도 나눠서, 대량 발송이 트랜잭션 알림의 지연에 영향을
주지 못하게 격리(bulkhead)한다.

## 한 줄 요약

대량 푸시 발송은 "큐로 분리 → 청크 배치 발송 → 멱등·재시도·DLQ로
신뢰성 확보"가 골격이지만, 설계의 완성은 시스템 바깥에 있다 —
**발송이 성공하는 순간 그 알림들이 트래픽이 되어 돌아온다는 피드백
루프까지 그려서, 발송 속도 분산과 본진 사전 대비를 함께 설계하는 것**이다.
