# Redis 영속화 RDB vs AOF — 재시작하면 데이터가 어떻게 되는가

> 핵심 관전 포인트: **RDB는 특정 시점의 메모리 전체를 통째로 찍는
> 스냅샷(사진), AOF는 모든 쓰기 명령을 순서대로 적어두는 일지(로그)다.
> RDB는 파일이 작고 복구가 빠르지만 마지막 스냅샷 이후 데이터를 잃고,
> AOF는 유실 폭을 최대 1초 수준까지 줄일 수 있지만 파일이 크고 복구가
> 느리다. 정답은 하나가 아니라 용도별로 다르다 — 순수 캐시라면 유실을
> 허용하고 영속화를 끄거나 RDB만, 세션·대기열·발급 카운터처럼 잃으면
> 안 되는 데이터라면 AOF(everysec)를 켜거나 둘을 병행한다.**

---

## 0. 질문 + 의도

**질문**: "Redis 영속화(RDB vs AOF)의 차이와 트레이드오프는?"

**출제 의도**: "Redis 재시작하면 데이터 어떻게 되나요"라는 운영 질문에
답할 수 있는지 본다. 캐시 용도면 유실 허용, 대기열이면 불가 —
용도별로 다른 답을 내는지가 관건이다. 기능 나열이 아니라 "우리 데이터의
성격에 따라 무엇을 감수할 것인가"라는 판단을 드러내야 한다.

## 1. 전제 — Redis는 메모리 DB, 껐다 켜면 빈 통이다

Redis는 모든 데이터를 메모리에 들고 있다. 프로세스가 죽거나 재시작하면
메모리는 증발한다. 영속화(persistence)는 이 증발에 대비해 **디스크에
복사본을 남기는 두 가지 방식**이고, 각각 "무엇을, 얼마나 자주, 어떤
형태로 남기느냐"가 다르다.

- 비유: 게임 세이브에 빗대면 — RDB는 **일정 주기마다 세이브 파일 하나를
  통째로 저장**하는 것, AOF는 **내가 누른 모든 키 입력을 순서대로
  녹화**해두는 것이다. 전자는 세이브 이후 플레이가 날아가고, 후자는
  녹화를 처음부터 재생해야 해서 복구가 오래 걸린다.

## 2. RDB — 특정 시점 스냅샷

일정 조건(예: "60초 동안 쓰기 1만 건 이상")이 차면 그 시점의 메모리
전체를 바이너리 파일(`dump.rdb`) 하나로 찍는다.

```
# redis.conf
save 900 1      # 900초 동안 1건 이상 변경되면 스냅샷
save 300 10
save 60 10000
```

**동작 방식이 중요하다**: `BGSAVE`는 자식 프로세스를 **fork**해서
자식이 디스크에 쓰게 한다. 부모(본체)는 계속 요청을 처리하고,
스냅샷 중 변경되는 메모리 페이지만 복사되는 **copy-on-write(CoW)**
방식으로 일관된 시점의 데이터를 찍는다.

- **장점**: 파일이 압축된 바이너리라 작고, 복구(로드)가 빠르다.
  백업 파일로 옮기기 좋다(S3 업로드 등).
- **단점 1 — 유실 폭**: 마지막 스냅샷 이후의 쓰기는 장애 시 전부
  사라진다. `save 60 10000`이면 최악의 경우 수 분치가 날아간다.
- **단점 2 — fork 비용**: 데이터가 클수록 fork 자체가 순간적으로
  느려질 수 있고, 스냅샷 도중 쓰기가 많으면 CoW 때문에 **메모리
  사용량이 순간 급증**한다. 메모리를 빠듯하게 잡은 인스턴스에서
  스냅샷이 도는 순간 OOM이 나는 사고 패턴이 여기서 나온다.
- 참고: `SAVE`(포그라운드) 명령은 본체가 직접 쓰느라 **전체 요청이
  멈춘다.** 운영에서는 `BGSAVE`만 쓴다.

## 3. AOF — 쓰기 명령 로그

모든 쓰기 명령(`SET`, `INCR`, ...)을 받은 순서대로 파일에 append 한다.
복구할 때는 이 파일의 명령을 **처음부터 재실행**해서 상태를 되살린다.

핵심 트레이드오프는 **fsync 주기**다. OS 버퍼에 쓰는 것과 디스크에
실제로 내려앉는 것은 다르기 때문에, 언제 디스크 동기화(fsync)를
하느냐가 유실 폭과 성능을 가른다.

| appendfsync | 유실 폭 | 성능 |
|---|---|---|
| `always` | 사실상 0 | 매 쓰기마다 디스크 동기화 — 가장 느림 |
| `everysec` | 최대 약 1초 | **권장 기본값.** 균형점 |
| `no` | OS에 위임 — 수십 초도 가능 | 가장 빠름 |

- **장점**: 유실 폭을 크게 줄인다(everysec 기준 최대 1초 수준).
  로그가 사람이 읽을 수 있는 명령 형태라 사고 분석에도 유리하다.
- **단점 1 — 파일 크기**: 같은 키를 100번 고쳐도 100줄이 쌓인다.
  이를 압축하는 것이 **AOF rewrite**(`BGREWRITEAOF`) — 현재 메모리
  상태를 만들 최소 명령으로 파일을 다시 쓴다. 이것도 fork를 쓰므로
  RDB와 같은 CoW 메모리 급증 이슈가 있다.
- **단점 2 — 복구 속도**: 명령을 전부 재실행해야 하므로 RDB 로드보다
  느리다. 데이터가 크면 재시작 시간이 체감된다.
- (가산점 포인트) 최신 Redis는 **혼합 방식**을 기본으로 쓴다 —
  AOF rewrite 시 파일 앞부분은 RDB 스냅샷 형식으로, 그 이후 증분만
  AOF 명령으로 쌓는다(`aof-use-rdb-preamble`). "빠른 로드 + 짧은
  유실 폭"을 합친 절충안이다.

## 4. 그래서 뭘 선택하나 — 용도별 답 (면접의 핵심)

기능 비교에서 멈추지 말고 **데이터 성격별로 다른 답**을 내야 한다.

```
# ① 순수 캐시 (DB가 원본, Redis는 사본)
#    → 유실돼도 DB에서 다시 채우면 된다. 영속화가 오히려 비용.
save ""                # RDB 끔
appendonly no          # AOF 끔
# 재시작 직후 cold cache 부하가 걱정이면 RDB만 켜서
# "웜업용 대략적 스냅샷"으로 쓰는 것도 선택지

# ② 세션, 대기열, 선착순 발급 카운터 (Redis가 원본)
#    → 1초 유실도 "중복 발급/유령 주문"이 될 수 있는 데이터
appendonly yes
appendfsync everysec   # 유실 최대 ~1초를 감수
# 그 이상의 내구성이 필요하면 애초에 Redis 단독이 아니라
# RDB(관계형 DB) 병행 기록을 설계해야 한다
```

- **캐시인데 AOF `always`를 켜는 것**은 흔한 과잉 설계다 — 메모리
  DB를 쓰는 이유(속도)를 디스크 동기화로 갉아먹으면서, 잃어도 되는
  데이터를 지키는 셈이다.
- 반대로 **대기열인데 영속화를 끄는 것**은 조용한 시한폭탄이다.
  재시작 한 번에 대기열이 통째로 사라진다.

## 5. 꼬리질문 대비 포인트

### "스냅샷을 찍는 도중 쓰기가 들어오면 어떻게 되나요?"

fork된 자식은 fork 시점의 메모리 뷰를 본다. 부모가 페이지를 수정하려
하면 그 페이지만 복사본을 만들어 수정하는 copy-on-write 덕분에,
자식이 보는 스냅샷은 일관성이 유지된다. 대가는 **쓰기가 많을수록
복사되는 페이지가 늘어 메모리 사용량이 순간 급증**한다는 것 —
그래서 maxmemory를 물리 메모리에 꽉 채워 잡으면 스냅샷 중에
장애가 날 수 있다.

### "AOF 파일이 무한정 커지지 않나요?"

커진다. 그래서 AOF rewrite가 있다 — 현재 데이터 상태를 재현할 최소
명령 집합으로 파일을 새로 쓴다(`INCR` 100번 → `SET counter 100` 한 줄).
`auto-aof-rewrite-percentage` 등으로 자동 트리거되며, fork 기반이라
rewrite 도는 동안 메모리·I/O 부하가 생기는 점을 함께 말하면 좋다.

### "RDB와 AOF를 둘 다 켜면 복구는 뭘로 하나요?"

둘 다 켜져 있으면 **AOF로 복구한다** — 더 최신 상태를 담고 있기
때문이다. RDB는 백업·복제 초기 동기화·빠른 대략 복구용으로 병행하는
그림이 일반적이다.

### "복제(replica)가 있으면 영속화는 필요 없지 않나요?" (시니어 변별 포인트)

복제는 **가용성** 수단이지 **내구성** 수단이 아니다.

1. `FLUSHALL` 같은 잘못된 명령, 버그로 인한 삭제는 **복제본에도
   그대로 전파**된다 — 복제는 실수를 못 지켜준다.
2. 마스터 장애 → failover 순간, 아직 복제본에 전달 안 된 쓰기는
   유실된다 (Redis 복제는 비동기).
3. 전원 장애처럼 마스터·복제본이 **동시에** 죽는 시나리오에서
   디스크에 남은 게 없으면 전부 끝이다.

"복제는 서버 한 대의 죽음을, 영속화는 데이터의 죽음을 막는다 —
서로 대체재가 아니라 보완재"라고 정리하면 강하다.

### "영속화를 켜면 어떤 성능 비용이 생기나요?"

- AOF: 쓰기 경로에 디스크 I/O가 끼어든다. `always`면 매 명령,
  `everysec`이면 백그라운드 flush. 디스크가 느리면(특히 fsync가
  밀리면) 쓰기 지연이 튄다.
- RDB/AOF rewrite: fork 순간의 지연 + CoW 메모리 급증 + 디스크 쓰기
  I/O. 트래픽 피크 시간대에 스냅샷 조건이 차도록 두면 피크에
  부하가 겹친다.

## 한 줄 요약

RDB는 "가끔 통째로 찍는 사진"이라 작고 복구가 빠르지만 사진 이후를
잃고, AOF는 "모든 쓰기의 일지"라 유실 폭이 1초 수준까지 줄지만 크고
복구가 느리다 — 진짜 답은 방식 비교가 아니라 **"이 Redis에 든 데이터는
잃어도 되는가"를 용도별로 판단해 캐시는 끄고, 원본 데이터는
AOF(everysec) 이상으로 지키는 것**이다.
