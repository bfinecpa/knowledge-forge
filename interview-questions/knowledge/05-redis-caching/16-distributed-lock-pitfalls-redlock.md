# Redis 분산 락의 함정 — 락은 이미 넘어갔는데 나만 주인인 줄 아는 순간들

> 핵심 관전 포인트: **분산 락의 함정 세 가지는 전부 한 문장으로 수렴한다 — "내가 락을 쥐고 있다"는 프로세스의 믿음과 락의 실제 상태가 어긋나는 순간, 임계 구간에 두 프로세스가 동시에 들어간다.** ① **TTL 만료**: GC 일시 정지나 네트워크 지연으로 작업이 TTL보다 길어지면, 락은 만료되어 이미 남에게 넘어갔는데 원래 주인은 그걸 모른 채 계속 쓴다. ② **소유자 검증 없는 해제**: `DEL`은 주인을 가리지 않는다. 늦게 깨어난 프로세스가 남의 락을 지우는 사고를 막으려면 락 값에 고유 토큰을 넣고 "내 토큰일 때만 삭제"를 **Lua로 원자화**해야 한다. ③ **시계 문제**: Redlock은 락 유효 시간 판정을 각 노드의 물리 시계에 의존하는데, 시계가 점프하면(NTP 보정, 관리자 조작) 안전성 가정이 무너진다. Redlock 논쟁에 대한 내 기준은 이렇다 — **분산 락은 "같은 일을 두 번 하지 않기 위한 효율성 장치"로만 신뢰하고, 정확성(돈·정합성)이 걸린 작업의 최종 방어선은 락이 아니라 데이터 쪽(DB 유니크 제약·조건부 갱신·fencing token)에 둔다.** 이 기준이면 단일 Redis + `SET NX PX`로 충분하며, Redlock의 복잡도는 사지 않는다.

---

## 0. 질문 + 의도

**질문**: "Redis 기반 분산 락을 구현할 때의 함정(TTL 만료, 락 소유자 검증, 시계 문제)을 설명해주세요. Redlock 논쟁에 대한 본인의 견해는?"

**출제 의도**: rationale은 이렇게 적고 있다 — "TTL 만료 후에도 자기가 락 주인인 줄 아는 프로세스, 남의 락 해제 — 이 함정들은 '락을 얻었다'는 착각 속에 정합성을 조용히 깬다. Redlock 논쟁에 견해를 묻는 건 정답이 아니라 **안전성과 실용성의 트레이드오프에 자기 기준이 있는지**를 보기 위해서다." 즉 채점 지점은 락 명령어의 암기가 아니라 ① 각 함정이 **어떤 타이밍에, 왜 발생하는지**를 그림으로 그릴 수 있는가 ② 함정마다 **어디까지가 방어 가능하고 어디부터는 구조적으로 불가능한지**를 구분하는가 ③ 그 불가능성 위에서 **자기 기준(무엇을 락에 맡기고 무엇을 맡기지 않을지)** 을 세웠는가다.

## 1. 최소 구현부터 — 락이 무엇이고 왜 `SET NX PX` 한 문장인가

### 1-1. 전제 지식 — 분산 락은 무엇을 하는 물건인가

먼저 용어부터 정리하자. **락(lock, 자물쇠)**은 "한 번에 한 명만 이 구간에 들어오게 한다"는 장치다. 그 구간을 **임계 구간(critical section)**이라고 부른다 — 여러 실행 주체가 동시에 들어오면 결과가 깨지는 코드 구간이라는 뜻이다.

한 JVM 안이라면 `synchronized`나 `ReentrantLock`으로 끝난다. 자물쇠의 상태가 그 JVM의 메모리에 있고, 그 메모리를 모든 스레드가 함께 보기 때문이다.

그런데 같은 애플리케이션을 서버 3대로 늘리는 순간 이 전제가 무너진다. 3대의 JVM은 서로의 메모리를 볼 수 없으므로, 각자 자기 `synchronized`를 잡고 셋이 나란히 임계 구간에 들어간다. 자물쇠가 세 개가 되면 자물쇠가 없는 것과 같다.

그래서 **자물쇠의 상태를 모두가 볼 수 있는 바깥의 한곳에 둬야** 하고, 그 바깥을 Redis로 삼은 것이 **분산 락(distributed lock)**이다. 개념적으로는 "여러 프로세스가 공유하는 한 칸짜리 좌석"이고, 그 좌석을 Redis의 키 하나로 표현한다. 키가 있으면 누군가 앉아 있는 것, 키가 없으면 빈 좌석이다.

### 1-2. 두 문장으로 나누면 그 사이가 뚫린다

락 구현의 첫 함정은 알고리즘이 아니라 **명령을 몇 개로 쪼갰는가**에서 나온다. 흔히 시도하는 두 가지 형태가 각각 다른 방식으로 실패한다.

**실패 1 — "있는지 확인하고 없으면 잡는다"를 두 문장으로.**

```
BEFORE 1

프로세스 A                     Redis 키 lock:order:42        프로세스 B
  EXISTS lock:order:42 → 0     (키 없음)
                               (키 없음)                     EXISTS lock:order:42 → 0
  SET lock:order:42 "A"        (A가 씀)
                               (B가 덮어씀)                  SET lock:order:42 "B"
  "내가 주인이다"                                             "내가 주인이다"
  → 임계 구간에 A와 B가 동시 진입
```

이것이 **check-then-act(확인하고 행동하기)** 결함의 전형이다. 확인 시점의 사실("키가 없다")이 쓰기 시점까지 유지된다는 보장이 아무 데도 없다. 그 사이에 다른 프로세스가 끼어들면 두 프로세스가 똑같이 "내가 처음이다"라고 판단한다.

**실패 2 — "잡고 나서 TTL을 건다"를 두 문장으로.**

```
BEFORE 2

SETNX lock:order:42 "1"     → 1 (획득 성공)
   ← 바로 여기서 프로세스가 죽는다 (배포 중 SIGKILL, OOM Kill, 크래시)
EXPIRE lock:order:42 30     → 실행되지 못한다

결과: 만료 시간이 없는 키가 Redis에 영원히 남는다.
      그 자원은 사람이 손으로 지워줄 때까지 아무도 잠글 수 없다.
```

`SETNX`는 "없을 때만 SET"을 해주는 명령이라 실패 1은 막아준다. 그런데 만료 시간을 붙이는 `EXPIRE`가 별도 명령이라, 그 사이에 죽으면 **영구 락**이 남는다. 락이 정합성을 지키는 장치가 아니라 **서비스를 멈추는 장치**가 되는 것이다.

이 실패가 특히 고약한 이유는 조용하다는 점이다. 예외도 알람도 없이 그 자원만 영원히 잠긴 채로, 나중에 "왜 이 배치가 며칠째 안 돌지?"로 발견된다.

### 1-3. `SET key value NX PX 30000` — 인자를 하나씩 뜯어보면

두 실패를 동시에 없애는 방법은 하나다. **획득 판정과 만료 설정을 명령 하나에 담는 것.**

```
AFTER — 획득 조건, 소유자 표시, TTL 부여가 전부 한 문장

SET lock:order:42 "550e8400-...-c8f1" NX PX 30000
    ^^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^^^^ ^^ ^^^^^^^^
    키            값                   조건 만료
    (좌석 이름)    (소유자 토큰)         (없을 때만) (30초)
```

인자를 하나씩 보자.

- **키 `lock:order:42`**: 잠글 대상을 가리키는 이름이다. "주문 42번"이라는 자원 하나에 좌석 하나가 대응되도록 자원 식별자를 키에 넣는다. 여기를 `lock:order`처럼 뭉뚱그리면 서로 상관없는 주문끼리 줄을 서게 되어 처리량이 죽는다.
- **값 `"550e8400-...-c8f1"`**: 요청마다 새로 만든 고유 문자열(UUID 등)이다. "이 좌석에 앉은 사람이 누구인가"를 적어두는 이름표라고 보면 된다. `"1"` 같은 상수가 아니라 고유 값이어야 하는 이유는 2-2에서 회수한다.
- **`NX`**: **N**ot e**X**ists의 줄임이다. **키가 없을 때만 설정하고, 이미 있으면 아무것도 하지 않고 `nil`을 돌려준다.** 반대 옵션인 `XX`는 키가 있을 때만 설정한다. 이 두 글자가 "빈 좌석일 때만 앉는다"는 경쟁 판정을 애플리케이션에서 Redis 안으로 밀어 넣는다.
- **`PX 30000`**: 만료 시간을 **밀리초** 단위로 지정한다. 30000ms는 30초다. 초 단위로 주고 싶으면 `EX 30`을 쓴다.

핵심은 이 네 가지가 **한 명령**이라는 점이다. Redis는 명령 하나를 처리하는 동안 다른 클라이언트의 명령을 끼워 넣지 않으므로([Redis 싱글 스레드](01-redis-single-thread-performance.md) 참고), "없는지 확인 + 값 쓰기 + 만료 설정"이 쪼개지지 않는다. 1-2의 두 실패가 함께 사라진다.

여기서 한 번 붙잡고 갈 원리가 있다. **명령을 나누지 말고 조건을 명령 안에 실어 보낸다.** 이 발상은 뒤에 나오는 Lua 해제(2-2), fencing token의 조건부 `UPDATE`(2-1), 그리고 선착순 쿠폰의 Lua 판정까지 이 문서 전체를 관통한다.

### 1-4. TTL은 정합성 장치가 아니라 가용성 장치다

왜 애초에 만료 시간을 거는지 정확히 말할 수 있어야 한다.

락을 쥔 프로세스가 죽으면 해제 명령을 실행할 주체가 사라진다. TTL이 없으면 1-2의 두 번째 시나리오처럼 영구 락이 남는다. 그래서 TTL은 **"주인이 돌아오지 않으면 좌석을 강제로 비운다"**는 규칙이다. 즉 TTL이 지키는 것은 정합성이 아니라 **가용성** — 시스템이 영원히 멈추지 않게 하는 보험이다.

그런데 강제로 비운다는 것은 **주인이 아직 일하고 있는데도 비울 수 있다**는 뜻이기도 하다. 보험이 그대로 다음 함정의 원인이 된다.

```
TTL 짧게  →  주인이 죽었을 때 빨리 복구된다        (가용성 좋음)
          →  작업이 TTL을 넘길 확률이 올라간다      (안전성 나쁨)

TTL 길게  →  작업이 TTL을 넘길 확률이 내려간다      (안전성 좋음)
          →  주인이 죽으면 그만큼 오래 멈춘다       (가용성 나쁨)
```

**락의 안전성과 가용성이 TTL 하나를 사이에 두고 서로를 밀어내는 구조** — 이 긴장을 인식하는 것이 이 문항의 절반이다. 어느 값을 넣어도 한쪽은 포기하게 되어 있고, 그래서 "적절한 TTL"만으로는 이 문제가 끝나지 않는다.

## 2. 세 가지 함정 — 믿음과 실제가 어긋나는 세 가지 방식

### 2-1. 함정 ① TTL 만료 — 작업이 락보다 오래 사는 순간

#### 전제 지식: GC 일시 정지(stop-the-world)란 무엇인가

TTL을 30초로 잡았다고 하자. "30초면 충분하지"라는 가정은 **애플리케이션이 그동안 멈추지 않는다**는 가정 위에 서 있다. 그런데 JVM은 멈춘다. 왜 멈추는지부터 깔고 가자.

JVM은 개발자 대신 메모리를 정리한다. 더 이상 참조되지 않는 객체를 찾아 회수하는 일이 **가비지 컬렉션(GC, garbage collection)**이다. 그런데 회수 대상을 판정하는 도중에 애플리케이션 스레드가 계속 참조 관계를 바꾸면 판정이 어긋나므로, GC는 특정 구간 동안 **애플리케이션 스레드를 전부 멈춘다.** 세상이 통째로 정지한 것처럼 보인다고 해서 **stop-the-world(STW) 일시 정지**라고 부른다.

이게 애플리케이션 코드 입장에서 어떻게 보이는지가 결정적이다.

```java
long t1 = System.currentTimeMillis();
// ← 여기서 STW 정지가 일어난다. 이 스레드는 아무것도 하지 않은 채 시간만 흐른다.
long t2 = System.currentTimeMillis();
// t2 - t1 이 800ms 일 수 있다. 두 줄 사이에 아무 코드도 없는데도.
```

즉 **한 줄과 다음 줄 사이에서 수백 ms에서 수 초가 사라진다.** 그리고 결정적으로, **스레드는 자기가 멈췄었다는 사실을 모른다.** 깨어나서 그냥 다음 줄을 실행한다. "내가 5초 동안 정지해 있었으니 락을 다시 확인해야지"라는 판단 자체가 불가능하다.

최신 수집기(G1, ZGC 등)는 정지 시간을 짧게 유지하도록 설계돼 있지만 0이 되지는 않고, 힙이 크거나 메모리 압박이 심하면 여전히 긴 정지가 나온다. 그리고 같은 효과를 내는 원인이 GC만도 아니다.

- **컨테이너 CPU 스로틀링**: Kubernetes에서 CPU limit을 넘긴 파드는 다음 주기까지 CPU를 배정받지 못한다. 스레드는 실행 가능 상태로 대기만 한다.
- **스왑, 디스크 I/O 블로킹**: 페이지 폴트 한 번이 수십에서 수백 ms를 먹는다.
- **네트워크 지연**: Redis 호출이 나갔다가 돌아오는 시간 자체도 임계 구간을 늘린다.
- **가상 머신의 라이브 마이그레이션이나 스냅샷 복원**: 게스트 전체가 잠깐 멈춘다.

정리하면 이렇다. **TTL 30초는 "작업이 30초 안에 끝난다"가 아니라 "작업 시간 + 그 사이에 끼어들 수 있는 모든 정지의 합이 30초 안"이라야 성립한다.** 두 번째 조건은 애플리케이션이 통제할 수 없는 것들로 채워져 있다.

#### 사고의 타임라인

```
프로세스 A                          Redis                     프로세스 B
   │ SET ... NX PX 30000 ─────────▶ 락 획득 (주인 A)
   │ 작업 시작
   │
   │ ==== STW GC 일시 정지 ====
   │ (또는 CPU 스로틀링,
   │  스왑, 네트워크 단절)
   │                                (30초 경과) 락 만료·소멸
   │
   │                                                          SET ... NX PX 30000
   │                                락 획득 (주인 B) ◀────────
   │                                                          작업 시작
   │
   │ ◀── 정지 끝. 아무 일 없었다는 듯 다음 줄 실행
   │ 계속 씀 (자기가 아직 주인인 줄 안다)
   │
   └──▶ 임계 구간에 A와 B가 동시에 들어와 있다
```

핵심은 **A가 자신이 멈췄었다는 사실조차 모른다**는 것이다. GC 일시 정지는 코드 어느 줄 사이에서든 일어날 수 있고, 깨어난 스레드는 그냥 다음 줄을 실행한다.

"그럼 쓰기 직전에 락이 아직 내 것인지 확인하면 되지 않나?"도 답이 아니다. **확인과 쓰기 사이에서 또 멈출 수 있기 때문**이다. 확인은 그 순간의 사실일 뿐 다음 순간을 보장하지 않는다. 이 구조는 분산 락 논의 내내 반복해서 나온다 — **어떤 검사도 검사와 행동 사이의 시간을 없애지는 못한다.**

#### 완화책 ①: 락 연장 (Redisson watchdog) — 완화지 해결이 아니다

**watchdog(감시견)**은 락을 잡은 클라이언트가 별도의 백그라운드 스레드를 띄워, **락을 쥐고 있는 동안 주기적으로 TTL을 원래 값으로 다시 밀어주는** 기능이다. Redisson의 락이 이 방식을 쓴다. "내가 아직 살아 있다"는 심장박동을 Redis에 계속 보내는 셈이다.

효과는 분명하다. 작업 시간이 예상보다 길어져도 프로세스가 살아 있는 한 락이 만료되지 않는다. 그리고 프로세스가 죽으면 연장하는 주체가 사라지므로 TTL이 자연 소멸한다 — 1-2의 영구 락 문제도 재발하지 않는다. **"작업 시간을 잘못 예측했다"는 가장 흔한 원인 하나를 지워준다.**

하지만 구조적 한계가 그대로 남는다. **연장 스레드도 같은 JVM 안에 있다.** STW GC는 애플리케이션 스레드를 전부 멈추므로, 워커 스레드가 멈출 때 연장 스레드도 함께 멈춘다. 정지가 TTL보다 길면 위 타임라인이 그대로 재현된다. 네트워크가 끊겼다면 연장 요청 자체가 Redis에 도달하지 못한다.

한 줄로 정리하면 이렇다. **watchdog은 "살아서 정상 동작 중인 프로세스의 시간 예측 실패"를 막을 뿐, "프로세스 자신이 인지하지 못하는 정지"는 못 막는다.**

실무 함정도 하나 있다. Redisson에서 임대 시간을 명시적으로 지정하면(`lock(10, TimeUnit.SECONDS)` 같은 형태) watchdog은 동작하지 않고 그 시간이 지나면 그냥 만료된다. "Redisson을 쓰니 알아서 연장되겠지"라고 믿으면서 임대 시간을 지정하는 조합이 실제 사고로 이어진다.

#### 완화책 ②: fencing token — 방어선을 락에서 자원 쪽으로 옮긴다

지금까지의 대응은 전부 **락을 더 정확하게 만들려는 시도**였다. 그런데 "정지를 인지하지 못하는 프로세스"라는 근본 문제는 락 쪽에서 풀 수 없다는 것이 방금 드러났다. 그래서 발상을 뒤집는다.

**락을 쥔 쪽이 아무리 착각해도, 자원을 받는 쪽이 낡은 요청을 거부하면 결과는 안전하다.**

**fencing token**은 **락을 발급할 때마다 1씩 증가시켜 함께 내주는 번호**다. 이름은 울타리(fence)에서 왔다 — 자원 앞에 "이 번호 미만은 들어올 수 없음"이라는 울타리를 세워두고, 새 주인이 다녀갈 때마다 그 울타리를 한 칸씩 올린다. 뒤늦게 깨어난 옛 주인은 자기 번호가 울타리보다 낮아서 튕겨 나간다.

성립하려면 세 가지가 필요하다.

1. 락 서비스가 락을 줄 때마다 **단조 증가하는(monotonically increasing, 절대 줄어들지 않는) 번호**를 함께 발급한다. A가 33번을 받았다면 그다음 주인 B는 반드시 그보다 큰 번호를 받는다.
2. 자원을 만지는 모든 요청이 그 번호를 실어 보낸다.
3. 자원(DB, 스토리지)은 **지금까지 본 번호보다 큰 요청만** 받아들이고 나머지는 거부한다.

번호가 뒤바뀐 두 요청이 자원 쪽에서 어떻게 걸러지는지 타임라인으로 보면 이렇다.

```
프로세스 A (토큰 33)             자원 행의 fence 컬럼        프로세스 B (토큰 34)
  락 획득, 토큰 33 발급           fence = 32
  ==== STW 정지 시작 ====
                                (락 TTL 만료)
                                                            락 획득, 토큰 34 발급
                                UPDATE ... fence < 34  ◀──── B가 쓴다
                                → 조건 성립 (32 < 34)
                                fence = 34 로 갱신
  ◀── 정지 끝, 재개
  UPDATE ... fence < 33 ────────▶
                                → 조건 불성립 (34 < 33 은 거짓)
                                → 영향 행 수 0
  ◀── 0을 보고 "내가 낡았다"를 알고 자기 작업 결과를 버린다
```

```sql
-- 자원(DB) 쪽에서 낡은 토큰을 거부하는 조건부 갱신
UPDATE resource
   SET data = ?, fence = ?      -- fence = 내 토큰 (예: 33)
 WHERE id = ?
   AND fence < ?                -- 지금까지 기록된 토큰보다 내 토큰이 클 때만
-- 영향 행 수 0 = 나보다 새 주인이 이미 다녀갔다 → 내 작업 결과를 버린다
```

여기서 무슨 일이 일어났는지 정확히 짚자. **정확성의 근거가 "락이 옳았다"에서 "자원이 검사했다"로 옮겨 갔다.** 락은 여전히 틀릴 수 있다. 하지만 락이 틀려도 자원이 막아주므로 최종 결과는 깨지지 않는다. 즉 fencing token이 있으면 **정확성이 더 이상 락의 정확성에 의존하지 않는다.** 락은 "대부분의 경우 헛수고를 줄여주는 최적화"로 강등되고, 정확성은 자원 쪽 조건부 쓰기가 책임진다.

이 논리가 뒤의 Redlock 논쟁(2-3)과 실무 기준(3절) 전체의 뼈대다. 미리 요약해두면 — 락을 강화하는 방향과 자원을 방어하는 방향 중, 뚫렸을 때 잃는 것이 큰 문제일수록 후자가 답이다.

구조 자체는 낯설지 않아야 한다. **JPA `@Version` 낙관적 락과 같은 뼈대**다 — 조건을 갱신문 안에 넣고, 영향 행 수 0으로 "내가 낡았다"를 감지한다는 점이 동일하다([낙관적 락 vs 비관적 락](../03-jpa-orm/10-optimistic-vs-pessimistic-lock.md) 참고). 다른 점은 비교 대상이 그 행의 버전이 아니라 **락 발급 순번**이라는 것뿐이다.

단, 전제가 있다. **보호 대상 자원이 조건부 쓰기를 지원해야 한다.** DB라면 위처럼 `WHERE`에 조건을 얹으면 되지만, "메일 발송 API 호출", "외부 결제 승인 요청"처럼 조건부 쓰기를 받아주지 않는 자원은 fencing으로 보호할 수 없다. 이때 다음 수단은 그 자원 쪽에 멱등성 키를 받아주는 API가 있는지 확인하는 것이다.

그리고 미리 못 박아둘 것 하나. **Redlock은 이 fencing token을 제공하지 않는다.** 여러 노드에 각각 독립적으로 `SET NX`를 할 뿐이라, "전역에서 단조 증가하는 번호"를 만들어 낼 수단이 알고리즘 안에 없기 때문이다. Kleppmann 비판의 핵심 중 하나가 여기다. **(가산점 포인트)**

### 2-2. 함정 ② 락 해제 — `DEL`은 주인을 확인하지 않는다

#### 남의 락을 지우는 시나리오

```
프로세스 A: 락 획득 (TTL 30초) → 작업이 35초 걸린다
                                 (30초 시점) 락 만료·소멸
프로세스 B: 빈자리에 락 획득 → 작업 시작
프로세스 A: 작업 끝. DEL lock:order:42   ← 지운 것은 B의 락이다
프로세스 C: 빈자리에 락 획득 → 이제 B와 C가 동시 진입
```

`DEL`은 "이 키를 지워라"라는 명령일 뿐이다. **누가 요청했는지, 그 사람이 지금 주인인지 묻지 않는다.** 그래서 A는 자기 락을 정리한다고 믿으면서 B의 락을 지운다.

무서운 점은 **연쇄**다. A의 지연 하나가 B의 락을 지우고, 그 빈자리가 C를 불러들이고, C가 작업을 마치며 또 남의 락을 지울 수 있다. 한 번의 지연이 락 시스템 전체를 "있으나 마나"로 만든다.

그리고 이 붕괴는 **로그를 남기지 않는다.** `DEL`도 `SET NX`도 전부 정상 성공으로 응답하기 때문이다. 예외 하나 없이 정합성만 조용히 깨진다.

#### 해제의 올바른 형태 — 소유자 확인과 삭제를 한 덩어리로

1-3에서 락 값에 상수가 아니라 요청마다 고유한 토큰을 넣은 이유가 여기서 회수된다. 해제할 때 "지금 이 키에 적힌 값이 내 토큰인가"를 확인하고, 내 것일 때만 지우면 된다.

단, 확인과 삭제를 두 문장으로 쓰면 1-2와 똑같은 구멍이 다시 열린다.

```
BEFORE — check-then-act 를 두 문장으로

GET lock:order:42   → "내 토큰이 맞네"
   ← 이 찰나에 TTL이 만료되고 B가 락을 획득한다
DEL lock:order:42   → B의 락을 지운다
```

그러면 원자적으로 묶어야 하는데, Redis의 트랜잭션 명령인 `MULTI/EXEC`로는 안 된다. `MULTI`는 명령들을 큐에 모아 한꺼번에 실행할 뿐 **중간 조회 결과를 보고 분기할 수 없기 때문**이다. "GET 결과가 내 토큰이면 DEL, 아니면 아무것도 안 함"이라는 조건 분기를 표현할 방법이 없다.

그래서 Lua다. Redis는 Lua 스크립트를 **한 덩어리로 실행**하며 그 사이에 다른 클라이언트의 명령을 끼워 넣지 않는다. 그리고 스크립트 안에서는 조회 결과로 자유롭게 분기할 수 있다.

```lua
-- AFTER — 확인과 삭제를 Lua 스크립트 하나로 (Redis 가 원자적으로 실행한다)
-- KEYS[1] = 스크립트에 넘긴 "키 목록"의 첫 번째 = "lock:order:42"
-- ARGV[1] = 스크립트에 넘긴 "값 목록"의 첫 번째 = 내 소유자 토큰(UUID)
if redis.call("GET", KEYS[1]) == ARGV[1] then
    -- 지금 좌석에 적힌 이름표가 내 것일 때만 지운다.
    -- GET 과 DEL 사이에 다른 명령이 끼어들 수 없으므로 위 BEFORE 의 틈이 없다.
    return redis.call("DEL", KEYS[1])
else
    -- 남의 락이거나 이미 만료돼 사라진 상태다. 손대지 않고 0을 돌려준다.
    -- 예외를 던지지 않는 이유: 해제 실패는 오류가 아니라
    -- "TTL 이 나보다 먼저 일했다"는, 정상적으로 예상되는 결과이기 때문이다.
    return 0
end
```

이 스크립트가 0을 돌려줬다는 것은 **"작업하는 동안 내가 락을 쥐고 있었다는 보장이 이미 깨졌다"**는 신호다. 예외는 아니지만 무의미한 값도 아니므로, 로그나 메트릭으로 남겨서 그 빈도를 봐야 한다. 이 값이 늘어난다면 TTL이 작업 시간에 비해 짧다는 증거다.

"조회 결과를 보고 분기해서 갱신"을 원자화하는 도구가 왜 `MULTI/EXEC`가 아니라 Lua여야 하는지, WATCH를 쓰는 낙관적 재시도와는 어떻게 다른지는 [MULTI/EXEC와 WATCH vs Lua](27-multi-exec-watch-vs-lua.md)에서 따로 다룬다.

#### 여기까지가 단일 Redis 기준의 완성형

**`SET NX PX` + 요청마다 고유한 소유자 토큰 + Lua 해제 (+ 필요 시 watchdog).** Redisson의 락이 대략 이 구성이다.

**직접 구현하지 않고 검증된 라이브러리를 쓰는 것 자체가 실무 답안의 일부다.** 재진입(같은 스레드가 같은 락을 중첩해서 잡는 경우) 처리, 대기 중인 클라이언트를 pub/sub으로 깨우는 로직, 연장 스레드의 수명 관리 같은 것을 직접 만들면 그 구현 자체가 새로운 버그의 원천이 된다.

### 2-3. 함정 ③ 시계 문제와 Redlock 논쟁

#### 단일 Redis에 남은 구멍 — failover 유실

2-2까지 만들어도 구멍이 하나 남는다. **Redis 복제는 비동기다.** 마스터는 쓰기를 받아 자기 메모리에 반영하고 **클라이언트에 OK를 먼저 응답한 뒤에** 그 내용을 레플리카로 흘려보낸다. 응답과 복제가 묶여 있지 않다.

```
① A가 마스터에서 락 획득 (SET NX PX 성공, OK 응답을 받음)
② 그 락이 레플리카에 도달하기 전에 마스터가 다운된다
③ Sentinel/Cluster 가 레플리카를 새 마스터로 승격 — 이 레플리카에는 락이 없다
④ B가 새 마스터에 같은 키로 SET NX 를 보내 성공 → A와 B가 동시에 락을 보유
```

이건 락의 **존재 자체가 유실**되는 문제라 소유자 토큰 검증으로도 못 막는다. A와 B가 각자 정당한 토큰을 들고 있고, 서로의 존재를 알 방법이 없기 때문이다. Redlock은 정확히 이 구멍을 메우기 위해 제안됐다.

#### Redlock 알고리즘 — 절차를 그대로 따라가 보면

Redlock은 **서로 복제 관계가 아닌, 완전히 독립적인 Redis 마스터 N대**(관례적으로 5대)를 두고 다수결로 락을 판정하는 알고리즘이다. 노드끼리 복제하지 않으므로 한 대가 죽어도 다른 노드의 기억이 함께 사라지지 않는다.

클라이언트가 락을 잡는 절차는 이렇다.

1. **현재 시각을 밀리초 단위로 기록한다.** 뒤에서 "획득에 얼마나 걸렸는지"를 계산해야 하기 때문이다.
2. **N대 전부에 순서대로 락 획득을 시도한다.** 모든 노드에 **같은 키, 같은 소유자 토큰, 같은 TTL**로 `SET NX PX`를 보낸다. 이때 노드별 요청 타임아웃을 **락 TTL보다 훨씬 짧게** 잡는다(TTL이 10초라면 노드당 수십 ms 수준). 응답 없는 노드 하나에 오래 붙잡혀 있으면 절차 전체가 늦어지므로, 빠르게 실패로 치고 다음 노드로 넘어가야 한다.
3. **성공한 노드 수를 세고, 걸린 시간을 계산한다.** 걸린 시간은 "지금 시각 − 1에서 기록한 시각"이다.
4. **성공 조건은 두 개이고 둘 다 만족해야 한다.** (가) **과반**, 즉 `N/2 + 1`대 이상에서 성공했다(5대라면 3대). (나) **획득에 쓴 시간이 TTL보다 충분히 짧다.**
5. **실제로 쓸 수 있는 유효 시간 = TTL − 획득 소요 시간 − 시계 오차 여유.** TTL이 10초인데 획득에 3초가 걸렸다면 남은 유효 시간은 약 7초다. 이 시간이 남아 있는 동안만 임계 구간을 실행하고, 계산 결과가 0 이하이면 획득 실패로 처리한다.
6. **실패하면 획득에 성공했던 노드들까지 포함해 모든 노드에 해제를 보낸다.** 일부 노드에만 락이 남아 있으면 다음 시도들이 계속 과반을 못 채워 아무도 락을 못 잡는 상태가 되기 때문이다. 해제는 2-2의 Lua(내 토큰일 때만 삭제)를 그대로 쓴다.

4의 (나) 조건이 이 알고리즘에서 가장 헷갈리는 부분인데, 이유는 이렇다. **락의 TTL은 첫 번째 노드에 `SET`이 성공한 순간부터 이미 흐르기 시작한다.** 그런데 5대를 도는 데는 시간이 걸리므로, 마지막 노드에서 성공을 확인한 시점에는 첫 노드의 TTL이 이미 상당히 소진돼 있다. 만약 획득에 TTL만큼 오래 걸렸다면, 획득에 성공한 바로 그 순간 첫 노드의 락은 이미 만료 직전이다. 그래서 "걸린 시간을 빼고 남은 만큼만 내 것"이라고 계산하는 것이다.

한두 대가 죽거나 데이터를 유실해도 나머지가 과반을 기억하므로, failover 유실이라는 단일 장애점이 사라진다 — 여기까지가 Redlock이 실제로 해결하는 범위다.

#### 논쟁 — Kleppmann의 비판과 antirez의 반박

먼저 **시계 점프**가 무엇인지부터 짚자. 서버의 물리 시계는 조금씩 어긋나고, NTP(Network Time Protocol)가 이를 표준 시각에 맞춘다. 보통은 시계가 가는 속도를 미세하게 조정해 서서히 맞추지만, 오차가 크면 시각을 **한 번에 건너뛰게** 만든다. 관리자가 수동으로 시각을 바꾸거나, 가상 머신이 스냅샷에서 복원되거나, 윤초 처리가 어긋나도 같은 일이 생긴다. 시각이 앞으로 확 뛰면 **Redis가 보기에 아직 안 끝난 TTL이 이미 지난 것으로 판정된다.**

**Kleppmann(『Designing Data-Intensive Applications』 저자)의 비판**은 **"보장이란 무엇인가"의 층위**에 근거를 둔다. 논지를 한 문장으로 압축하면 이렇다 — Redlock의 안전성은 **타이밍 가정**(프로세스가 오래 멈추지 않는다, 시계가 튀지 않는다, 네트워크 지연에 상한이 있다) 위에 서 있는데, **비동기 네트워크에서는 그 가정 중 어느 것도 성립을 보장할 수 없으므로** Redlock은 안전성을 증명할 수 없다. 구체적 지적은 셋이다.

- **시계 점프에 취약하다.** 5의 유효 시간 계산과 각 노드의 만료 판정이 물리 시계에 기대고 있으므로, 어느 노드의 시각이 앞으로 뛰면 그 노드의 락이 조기 만료되고 과반 계산이 무너진다. 노드를 5대로 늘리는 것은 **노드 장애**에 대한 대비이지 **시계 오작동**에 대한 대비가 아니다.
- **프로세스 정지에는 어차피 똑같이 뚫린다.** 5에서 유효 시간을 확인한 **직후에** STW 정지가 오면 2-1의 타임라인이 그대로 반복된다. 노드 수를 늘려도 이 구멍은 그대로다.
- **fencing token이 없다.** 그래서 락이 뚫렸을 때 자원을 지켜줄 마지막 수단이 알고리즘 안에 없다.

이 셋이 하나의 결론으로 모인다. **정확성이 필요하면 fencing token이 있어야 하고, fencing token이 있다면 락 자체는 정확할 필요가 없으므로 Redlock의 복잡도를 살 이유가 없다.** 그리고 정말 정확한 락이 필요하다면 합의 알고리즘 기반 시스템(ZooKeeper, etcd 등 — 단조 증가하는 순번을 발급할 수 있다)을 쓰라는 것이 대안이다.

**antirez(Redis 창시자)의 반박**은 **"실무에서 무엇을 위해 락을 쓰는가"의 층위**에 근거를 둔다. 요지도 셋이다.

- **다수 사용례는 효율성 목적이다.** 배치 중복 실행 방지처럼 뚫려도 "일을 두 번 한다"로 끝나는 용도가 압도적으로 많고, 그 목적에는 Redlock이 주는 보장 수준이 충분하다.
- **시계 점프는 운영으로 통제 가능하다.** 시각을 건너뛰지 않고 미세 조정하도록 NTP를 설정하고, 관리자의 수동 시각 변경을 금지하면 실무에서 문제 되는 빈도가 크게 낮아진다. 이론적 가능성과 운영상의 발생 확률은 다르다.
- **유효 시간 확인 이후의 정지는 Redlock만의 결함이 아니다.** fencing 없이는 어떤 락 시스템도 그 구멍을 막지 못하므로 Redlock을 특별히 탓할 근거가 못 된다. 그리고 획득 과정 중에 생긴 지연은 5의 유효 시간 계산이 이미 걸러낸다.

두 사람이 끝내 합의하지 못한 이유는 **서로 다른 층위에서 말하고 있기 때문**이다. 한쪽은 "최악의 경우에도 깨지지 않음을 증명할 수 있는가"를 묻고, 다른 한쪽은 "현실에서 얼마나 자주 문제가 되는가"를 답한다. 그래서 이 논쟁은 승패를 고르는 것이 아니라 **질문을 다시 세우는 것**으로 정리해야 한다.

#### 내 견해 — "효율성의 락"과 "정확성의 락"을 나누면 논쟁이 정리된다

이 논쟁에서 가장 값진 산출물은 승패가 아니라 **Kleppmann이 제시한 구분**이다. 락을 쓰는 이유가 무엇인지를 먼저 물으면 두 층위가 갈라지고, 답도 함께 갈라진다.

**효율성(efficiency)의 락.** 같은 계산, 같은 배치, 같은 캐시 갱신을 여러 인스턴스가 중복 수행하지 않게 하려는 것이다. **뚫려도 잃는 것은 "일을 두 번 함"에 그친다** — 결과 자체는 여전히 옳다. → **단일 Redis + `SET NX PX` + 고유 토큰 + Lua 해제로 충분하다.** 드물게 중복 실행되는 비용보다 독립 Redis 5대를 운영하는 비용이 크다. 여기에 Redlock은 과잉이다.

**정확성(correctness)의 락.** 뚫리면 돈이 새거나 데이터가 깨진다. 중복 결제, 이중 차감, 재고 초과 판매. → **어떤 Redis 락도, Redlock을 포함해서, 단독으로는 부족하다.** 2-1의 정지 문제와 fencing 부재가 그대로 남기 때문이다. 이 경우 방어선을 **데이터 쪽에 이중으로** 깐다. DB 유니크 제약, 조건부 갱신(영향 행 수 확인), 멱등성 키. 락은 있어도 "경합을 줄여 재시도 횟수를 낮추는 성능 최적화"일 뿐, 정합성의 근거가 아니다.

그래서 내 답은 이렇다. **"Redlock을 쓸까 말까"가 잘못된 질문이다. "이 락이 뚫리면 무엇을 잃는가"가 맞는 질문이고, 잃는 것이 크면 락을 강화할 게 아니라 락 없이도 안전한 데이터 설계를 먼저 깐다.** 실제로 선착순 쿠폰 같은 문제는 분산 락 없이 원자적 연산만으로 푸는 것이 정석이다 — [선착순 쿠폰 설계](17-flash-sale-coupon-issuance-design.md) 참고.

## 3. 실무 선택 기준 한 장

| 상황 | 선택 | 이유 |
|---|---|---|
| 스케줄러·배치 중복 실행 방지 | 단일 Redis 락 (Redisson) | 뚫려도 중복 실행일 뿐. 단순함이 이긴다 |
| 같은 DB 안의 행 경합 | DB 락 / 원자적 UPDATE | 락과 데이터가 같은 시스템 = 실패 모드 최소 |
| 재고·쿠폰 카운트 | 원자적 연산 (INCR/Lua) | 애초에 락이 필요 없는 문제다 |
| 돈이 걸린 임계 구간 | 락 + **데이터 측 최종 방어선** | 락은 최적화, 정합성은 제약·조건부 갱신이 |
| 시스템 여러 개를 가로지르는 조정 | 그때가 분산 락의 자리 | 단, fencing 가능 여부부터 확인 |

표의 각 줄이 어떤 판단에서 나왔는지를 말로 풀면 이렇다.

**배치 중복 실행 방지**는 2-3의 구분에서 말한 전형적인 효율성의 락이다. 새벽 정산 배치가 두 인스턴스에서 동시에 돌면 같은 계산이 두 번 될 뿐이고, 결과가 멱등하게 설계돼 있으면 최종 상태도 같다. 이런 문제에 5대짜리 Redlock을 세우는 것은 리스크 대비 운영 비용이 맞지 않는다.

**같은 DB 안의 행 경합**에 Redis 락을 끌어오면 실패 모드가 늘어난다. "Redis는 살아 있는데 DB만 죽었다", "DB 트랜잭션은 롤백됐는데 Redis 락은 남아 있다" 같은 반쪽 실패가 생기기 때문이다. DB 락은 트랜잭션 롤백과 락 해제가 같은 시스템 안에서 원자적으로 묶이므로 그런 어긋남이 애초에 없다.

**재고나 쿠폰 카운트**는 락을 고를 문제가 아니다. 조건부 `UPDATE` 한 문장이나 Redis의 원자 연산 하나로 판정이 끝나면 잠글 틈 자체가 존재하지 않는다. 1-3에서 말한 "명령을 나누지 말고 조건을 명령 안에 실어 보낸다"가 그대로 적용되는 자리다.

**락을 꺼내기 전에 지켜야 할 순서**가 있다.

```
① 한 문장짜리 원자 연산으로 못 푸나?      (조건부 UPDATE, SET NX, INCR, Lua)
        └ 안 되면
② 경합 지점이 같은 DB 안이면 DB 락으로 안 되나?  (FOR UPDATE, 조건부 UPDATE)
        └ 안 되면
③ 그때 비로소 분산 락. 단, fencing 가능한 자원인지부터 확인한다.
```

분산 락은 성능 해법이 아니라 **경계를 넘는 조정이 필요할 때의 마지막 도구**다. 순서를 건너뛰고 ③부터 꺼내면, 원자 연산 하나면 끝날 문제에 락 왕복 지연과 TTL 만료·오해제라는 실패 모드를 얹게 된다.

## 4. 꼬리질문 대비 포인트

### "TTL을 아주 길게(10분) 잡으면 만료 문제가 없어지지 않나요?"

만료 함정(2-1)이 발생할 확률은 줄지만 **반대쪽 비용이 그만큼 커진다.** 1-4의 다이얼을 그대로 꺼내 답하면 된다.

락 주인이 크래시로 죽으면 그 자원은 **TTL이 다할 때까지 아무도 못 잠근다** — 10분짜리 부분 장애다. 게다가 TTL을 길게 잡아도 2-1의 근본 문제는 남는다. 정지가 10분보다 짧아지는 것이 아니라 "10분보다 긴 정지"의 확률이 낮아질 뿐이고, 확률을 0으로 만들 수는 없다.

그래서 실무 답은 조합이다. **작업 예상 시간보다 여유 있게 잡고 + watchdog으로 연장하고 + 그래도 뚫리는 경우는 fencing이나 데이터 제약으로 받는다.** TTL은 안전성과 가용성 사이의 다이얼이지, 한쪽으로 끝까지 돌려서 해결되는 값이 아니다.

### "Redisson watchdog이 있으면 TTL 만료 문제는 해결된 것 아닌가요?"

아니다. watchdog은 **살아 있는 프로세스의 시간 예측 실패**만 지운다.

연장 스레드도 같은 JVM 안에 있으므로 STW GC나 컨테이너 스로틀링 앞에서는 워커 스레드와 함께 멈춘다. 네트워크가 끊기면 연장 요청 자체가 Redis에 도달하지 못한다(2-1).

**"자신이 정지했다는 사실을 인지하지 못한 채 재개하는 프로세스"**라는 근본 문제는 락 쪽에서 풀 수 없고, 자원 쪽 방어(fencing token, 조건부 갱신)로만 막을 수 있다. 여기에 더해 Redisson에서 임대 시간을 명시하면 watchdog이 아예 동작하지 않는다는 점도 함께 말하면, 라이브러리를 읽어본 사람이라는 신호가 된다.

### "락 획득에 실패한 요청은 어떻게 처리하나요?"

**용도에 따라 갈라서 답한다.** 이 구분을 못 하면 모든 실패를 재시도로 처리하게 되고, 그게 장애로 번진다.

**중복 실행 방지 목적이면 즉시 포기**가 정답이다. 락을 못 잡았다는 것은 "누군가 이미 그 일을 하고 있다"는 뜻이므로 기다릴 이유가 없다. 기다렸다가 잡아서 또 하면 애초에 막으려던 중복 실행을 스스로 하는 셈이다.

**순서 대기 목적이면 재시도(스핀) 또는 대기**다. 다만 스핀 재시도는 Redis에 폴링 부하를 만들므로 재시도 간격과 상한을 둬야 하고, Redisson처럼 pub/sub으로 "락이 해제됐다"는 신호를 받아 깨어나는 구현이 폴링보다 낫다.

어느 쪽이든 **대기 시간 상한과 실패 응답 경로**가 반드시 있어야 한다. 없으면 락 경합이 스레드 고갈로 번진다 — 대기하는 스레드가 톰캣 워커를 붙잡고, 워커가 마르면 락과 무관한 API까지 함께 죽는다. 비관적 락이 커넥션을 고갈시키는 것과 정확히 같은 구조의 문제다([낙관적 vs 비관적 락](../03-jpa-orm/10-optimistic-vs-pessimistic-lock.md) 3-2절).

### "그냥 DB 비관적 락(SELECT FOR UPDATE)을 쓰면 안 되나요? 언제 Redis 분산 락이 필요한가요?" (시니어 변별 포인트)

**보호 대상이 그 DB 안에 있다면 DB 락이 우선이다.**

이유는 실패 모드의 개수다. 락과 데이터가 같은 시스템이면 "락은 살았는데 데이터 시스템만 죽는" 반쪽 실패가 없고, 트랜잭션 롤백과 락 해제가 원자적으로 묶인다. 반면 Redis 락 + PostgreSQL 데이터 조합은 두 시스템이 각각 죽을 수 있고, 그 조합마다 다른 사고가 난다.

Redis 분산 락이 정당해지는 경우는 둘이다.

1. **보호 대상이 DB 바깥일 때.** 외부 API 호출, 파일 작업, 여러 저장소에 걸친 절차처럼 DB의 행 락으로는 감쌀 수 없는 자원이다.
2. **DB 커넥션을 락 대기에 붙잡아두는 비용이 감당 불가일 때.** 대기 줄을 DB 밖으로 빼야 커넥션 풀이 마르지 않는다.

단, 2의 경우에도 순서가 있다. 대기 줄을 옮기기 전에 **임계 구간 자체를 줄이는 설계**(조건부 `UPDATE` 한 문장으로 접기)가 먼저다.

**"분산 환경이니까 분산 락"은 근거가 아니다** — 분산 환경에서도 경합 지점이 단일 DB면 그 DB가 이미 훌륭한 조정자다.

### "Redlock 5대 중 2대가 죽으면 어떻게 되나요?"

과반인 3대가 살아 있으므로 **락 발급은 계속된다.** 그게 Redlock의 설계 목적이므로 여기까지는 정상 동작이다.

진짜 문제는 다른 시나리오다. **락을 발급한 노드 중 하나가 디스크 영속화 없이 재시작하면** 그 노드는 자기가 발급했던 락을 잊은 채 돌아온다. 그러면 다른 클라이언트가 "그 노드 + 원래 실패했던 노드들"로 새 과반을 만들어 같은 락을 획득할 수 있다. 노드가 죽지도 않았는데 과반이 두 개가 되는 것이다.

그래서 antirez는 **delayed restart** — 재시작한 노드가 락 TTL만큼 기다린 뒤에야 요청을 받게 하는 방식 — 를 제안했다. 그 시간이 지나면 자기가 잊은 락들도 어차피 만료됐을 것이기 때문이다.

이 답을 할 수 있으면 "알고리즘을 외운 사람"과 "실패 모드를 따져본 사람"이 갈린다. **(가산점 포인트)**

## 한 줄 요약

Redis 분산 락의 세 함정 — **TTL 만료(자신의 정지를 인지하지 못한 채 재개하는 프로세스), 소유자 미검증 해제(`DEL`은 주인을 안 가림), 시계 의존(Redlock의 유효 시간 판정)** — 은 모두 "락을 쥐고 있다는 믿음"과 실제의 어긋남이며, `SET NX PX`(없을 때만 설정 + 밀리초 TTL을 한 명령으로) + 고유 토큰 + Lua 해제 + watchdog까지가 방어 가능한 영역이고 그 너머는 구조적으로 남는다. 그래서 Redlock 논쟁의 내 결론은 **락의 용도 구분**이다 — 효율성(중복 작업 방지)은 단일 Redis 락으로 충분하고, 정확성이 걸린 작업은 Redlock으로 락을 강화할 게 아니라 **최종 방어선을 데이터 쪽(유니크 제약·조건부 갱신·fencing token)에 두고 락은 경합 완화 최적화로 강등**시킨다.
