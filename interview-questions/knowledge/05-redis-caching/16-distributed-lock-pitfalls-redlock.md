# Redis 분산 락의 함정 — 락은 이미 넘어갔는데 나만 주인인 줄 아는 순간들

> 핵심 관전 포인트: **분산 락의 함정 세 가지는 전부 한 문장으로 수렴한다 — "내가 락을 쥐고 있다"는 프로세스의 믿음과 락의 실제 상태가 어긋나는 순간, 임계 구간에 두 프로세스가 동시에 들어간다.** ① **TTL 만료**: GC 일시 정지나 네트워크 지연으로 작업이 TTL보다 길어지면, 락은 만료되어 이미 남에게 넘어갔는데 원래 주인은 그걸 모른 채 계속 쓴다. ② **소유자 검증 없는 해제**: `DEL`은 주인을 가리지 않는다. 늦게 깨어난 프로세스가 남의 락을 지우는 사고를 막으려면 락 값에 고유 토큰을 넣고 "내 토큰일 때만 삭제"를 **Lua로 원자화**해야 한다. ③ **시계 문제**: Redlock은 락 유효 시간 판정을 각 노드의 물리 시계에 의존하는데, 시계가 점프하면(NTP 보정, 관리자 조작) 안전성 가정이 무너진다. Redlock 논쟁에 대한 내 기준은 이렇다 — **분산 락은 "같은 일을 두 번 하지 않기 위한 효율성 장치"로만 신뢰하고, 정확성(돈·정합성)이 걸린 작업의 최종 방어선은 락이 아니라 데이터 쪽(DB 유니크 제약·조건부 갱신·fencing token)에 둔다.** 이 기준이면 단일 Redis + `SET NX PX`로 충분하며, Redlock의 복잡도는 사지 않는다.

---

## 0. 질문 + 의도

**질문**: "Redis 기반 분산 락을 구현할 때의 함정(TTL 만료, 락 소유자 검증, 시계 문제)을 설명해주세요. Redlock 논쟁에 대한 본인의 견해는?"

**출제 의도**: rationale은 이렇게 적고 있다 — "TTL 만료 후에도 자기가 락 주인인 줄
아는 프로세스, 남의 락 해제 — 이 함정들은 '락을 얻었다'는 착각 속에 정합성을
조용히 깬다. Redlock 논쟁에 견해를 묻는 건 정답이 아니라 **안전성과 실용성의
트레이드오프에 자기 기준이 있는지**를 보기 위해서다." 즉 채점 지점은 락 명령어의
암기가 아니라 ① 각 함정이 **어떤 타이밍에, 왜 발생하는지**를 그림으로 그릴 수
있는가 ② 함정마다 **어디까지가 방어 가능하고 어디부터는 구조적으로 불가능한지**를
구분하는가 ③ 그 불가능성 위에서 **자기 기준(무엇을 락에 맡기고 무엇을 맡기지
않을지)** 을 세웠는가다.

## 1. 최소 구현부터 — 왜 `SET NX PX` 한 문장이어야 하는가

분산 락의 최소 형태는 "키가 없으면 만들고, 있으면 실패"다. 여기서부터 이미
함정이 시작된다.

```
❌ BEFORE — 두 문장으로 나누면 그 사이가 뚫린다
SETNX lock:order:42 "1"     ← 락 획득
EXPIRE lock:order:42 30     ← TTL 부여
```

`SETNX`와 `EXPIRE` **사이에서 프로세스가 죽으면**(배포, OOM Kill, 크래시)
TTL 없는 락이 영원히 남는다. 그 자원은 수동으로 지워줄 때까지 아무도 잠글 수
없다 — 락이 정합성을 지키는 게 아니라 **서비스를 멈추는 장치**가 된다.

```
✅ AFTER — 획득과 TTL 부여를 한 문장으로
SET lock:order:42 "550e8400-...-c8f1" NX PX 30000
--                 ^^^^^^^^^^^^^^^^^  ^^ ^^^^^^^^
--                 소유자 토큰(§3)     없을 때만  TTL 30초
```

- `NX`: 키가 **없을 때만** 성공 → 획득 경쟁의 원자성
- `PX 30000`: 획득과 **동시에** TTL 설정 → 주인이 죽어도 락은 스스로 풀린다
- 값에는 `"1"` 같은 상수가 아니라 **요청마다 고유한 토큰**(UUID 등)을 넣는다.
  이게 §3의 소유자 검증의 재료다.

여기서 TTL의 역할을 정확히 말할 수 있어야 한다. **TTL은 정합성 장치가 아니라
가용성 장치다.** 주인이 죽었을 때 시스템이 영원히 멈추지 않게 하는 보험이고,
그 보험이 바로 다음 함정(§2)의 원인이 된다. **락의 안전성과 가용성이 TTL 하나를
사이에 두고 서로를 밀어내는 구조** — 이 긴장을 인식하는 것이 이 문항의 절반이다.

## 2. 함정 ① TTL 만료 — 작업이 락보다 오래 사는 순간

### 2-1. 사고의 타임라인

TTL을 30초로 잡았다고 하자. "30초면 충분하지"라는 가정은 **애플리케이션이 멈추지
않는다**는 가정 위에 서 있다. 그런데 JVM은 멈춘다.

```
프로세스 A                          Redis                프로세스 B
   │ SET ... NX PX 30000 ─────────▶ 락 획득(주인 A)
   │ 작업 시작
   │ ▮▮▮▮▮ GC 일시 정지(STW) ▮▮▮▮▮
   │        (또는 네트워크 지연,      ⏰ 30초 경과 → 락 만료·소멸
   │         디스크 I/O 블로킹,
   │         컨테이너 CPU 스로틀링)                        SET ... NX ─▶ 락 획득(주인 B)
   │                                                      작업 시작
   │ ◀── 정지 끝, 아무 일 없었다는 듯 재개
   │ 계속 씀 (자기가 아직 주인인 줄 안다) ✗✗✗ 임계 구간에 A, B 동시 진입 ✗✗✗
```

핵심은 **A가 자신이 멈췄었다는 사실조차 모른다**는 것이다. GC 일시 정지는 코드
어느 줄 사이에서든 일어날 수 있고, 깨어난 스레드는 그냥 다음 줄을 실행한다.
"락을 확인한 다음 쓰면 되지 않나?"도 답이 아니다 — **확인과 쓰기 사이에서 또
멈출 수 있기 때문**이다. 확인은 그 순간의 사실일 뿐 다음 순간을 보장하지 않는다.

### 2-2. 완화책 ①: 락 연장 (watchdog) — 완화지 해결이 아니다

Redisson이 쓰는 방식이다. 락을 잡은 클라이언트가 **백그라운드 스레드로 주기적으로
TTL을 연장**한다("내가 아직 살아 있다"는 심장박동). 작업이 예상보다 길어져도
프로세스가 살아 있는 한 락이 만료되지 않고, 프로세스가 죽으면 연장이 멈춰
TTL이 자연 소멸한다. **"작업 시간 예측 실패"라는 흔한 원인 하나를 지워준다.**

하지만 구조적 한계가 그대로 남는다. **연장 스레드도 같은 JVM 안에 있다.**
STW GC가 오면 워커 스레드와 함께 연장 스레드도 멈춘다. 정지가 TTL보다 길면
§2-1의 타임라인이 그대로 재현된다. 네트워크 단절이면 연장 요청 자체가 Redis에
못 간다. **watchdog은 "정상 동작 중인 프로세스의 시간 예측 실패"를 막을 뿐,
"프로세스가 인지하지 못하는 정지"는 못 막는다.**

### 2-3. 완화책 ②: fencing token — 방어선을 락에서 자원 쪽으로 옮긴다

근본 해법은 발상을 뒤집는 것이다. **락을 쥔 쪽이 아무리 착각해도, 자원을 받는
쪽이 낡은 요청을 거부하면 된다.**

- 락을 발급할 때 **단조 증가하는 번호(fencing token)** 를 함께 발급한다
  (A가 33번, 만료 후 B가 34번).
- 보호 대상 자원(DB, 스토리지)은 요청에 실려 온 토큰이 **지금까지 본 것보다
  클 때만** 쓰기를 받아들인다.
- 늦게 깨어난 A가 33번을 들고 오면 → 이미 34번을 본 자원이 **거부**한다.

```sql
-- 자원(DB) 쪽에서 낡은 토큰을 거부하는 조건부 갱신
UPDATE resource
SET    data = ?, fence = ?          -- fence = 내 토큰(33)
WHERE  id = ? AND fence < ?         -- 지금까지 기록된 토큰보다 클 때만
-- 영향 행 수 0 = 나보다 새 주인이 이미 다녀갔다 → 내 작업을 버린다
```

이 구조가 낯설지 않아야 한다 — **JPA `@Version` 낙관적 락과 같은 뼈대**다
(조건을 갱신문 안에 넣고, 영향 행 수 0으로 낡음을 감지한다.
[낙관적 락 vs 비관적 락](../03-jpa-orm/10-optimistic-vs-pessimistic-lock.md) 참고).
단, 전제가 있다: **보호 대상 자원이 토큰 비교라는 조건부 쓰기를 지원해야 한다.**
DB라면 위처럼 가능하지만, 조건부 쓰기가 없는 외부 API 호출 같은 자원은 fencing으로
보호할 수 없다. 그리고 뒤에서 보겠지만 **Redlock은 이 fencing token을 제공하지
않는다** — Kleppmann 비판의 핵심 중 하나다. **(가산점 포인트)**

## 3. 함정 ② 락 해제 — `DEL`은 주인을 확인하지 않는다

### 3-1. 남의 락을 지우는 시나리오

```
프로세스 A: 락 획득(TTL 30초) → 작업이 35초 걸림 → ⏰ 락은 30초에 만료
프로세스 B: 만료된 자리에 락 획득 → 작업 중
프로세스 A: 작업 끝! DEL lock:order:42   ← B의 락을 지웠다
프로세스 C: 빈자리에 락 획득             ← 이제 B와 C가 동시 진입 ✗
```

무서운 점은 **연쇄**다. A의 지연 하나가 B의 락을 지우고, 그 빈자리가 C를 불러
동시 진입이 계속 번식한다. 락 시스템 전체가 "있으나 마나"가 된다.

### 3-2. 해제의 올바른 형태 — 소유자 확인과 삭제를 원자로

§1에서 락 값에 고유 토큰을 넣은 이유가 여기다. 해제할 때 "값이 내 토큰인지"
확인하고 지우면 된다. 단, **확인과 삭제가 두 문장이면 그 사이가 또 뚫린다.**

```
❌ BEFORE — check-then-act 를 두 문장으로: 확인 직후 만료+재획득되면 남의 락 삭제
GET lock:order:42          → "내 토큰이네"
                           ← 이 찰나에 만료 + B가 획득
DEL lock:order:42          → B의 락을 지움
```

```lua
-- ✅ AFTER — 확인과 삭제를 Lua 스크립트 하나로 (Redis 가 원자적으로 실행)
if redis.call("GET", KEYS[1]) == ARGV[1] then   -- 값이 내 토큰일 때만
    return redis.call("DEL", KEYS[1])
else
    return 0                                     -- 남의 락(또는 이미 만료) → 손대지 않음
end
```

"조회 결과를 보고 분기해서 갱신"을 원자화하는 도구가 왜 `MULTI/EXEC`가 아니라
Lua여야 하는지 — MULTI는 중간 조회 결과로 분기할 수 없기 때문이다. 이 구분은
[MULTI/EXEC와 WATCH vs Lua](27-multi-exec-watch-vs-lua.md)에서 따로 다룬다.

여기까지가 **단일 Redis 기준으로 "제대로 만든" 분산 락**이다: `SET NX PX` +
고유 토큰 + Lua 해제 (+ 필요 시 watchdog). Redisson의 락이 대략 이 구성이다.
직접 구현하지 않고 검증된 라이브러리를 쓰는 것 자체가 실무 답안의 일부다.

## 4. 함정 ③ 시계 문제와 Redlock 논쟁

### 4-1. 단일 Redis의 남은 구멍 — failover 유실

§3까지 만들어도 구멍이 하나 남는다. **Redis 복제는 비동기다.**

```
① A가 마스터에서 락 획득
② 락이 레플리카로 복제되기 전에 마스터 다운
③ 레플리카가 새 마스터로 승격 — 락이 없는 상태로
④ B가 새 마스터에서 같은 락 획득 → A, B 동시 보유 ✗
```

락의 존재 자체가 유실되는 문제라 토큰 검증으로도 못 막는다. Redlock은 이 구멍을
메우기 위해 제안됐다.

### 4-2. Redlock 개요 — 다수결로 유실을 버틴다

- 복제 관계가 아닌 **독립 Redis 마스터 N대**(관례적으로 5대)를 둔다.
- 클라이언트는 N대 각각에 `SET NX PX`를 시도해 **과반(3/5) 이상** 성공하면
  락 획득으로 간주한다.
- 획득에 걸린 시간을 재서, **유효 시간 = TTL − 획득 소요 시간 − 시계 오차 여유**
  로 계산한다. 유효 시간이 남아 있을 때만 락을 쓴다.
- 한두 대가 죽거나 유실돼도 과반이 기억하므로 §4-1의 단일 장애점이 사라진다.

### 4-3. 논쟁 — Kleppmann의 비판과 antirez의 반박

**Kleppmann(『Designing Data-Intensive Applications』 저자)의 비판** 요지:

- **시계 점프에 취약하다.** Redlock의 만료 판정은 각 노드의 물리 시계에 기댄다.
  NTP가 시계를 확 당기거나 관리자가 시각을 바꾸면 락이 조기 만료되어 과반 계산이
  무너진다. 안전성이 "시계가 얌전히 간다"는 **타이밍 가정** 위에 서 있는데,
  분산 시스템에서 그 가정은 보장이 아니다.
- **프로세스 정지(§2-1)에는 어차피 똑같이 뚫린다.** 유효 시간을 확인한 직후
  GC 정지가 오면? 5대로 늘려도 이 구멍은 그대로다.
- **fencing token이 없다.** 결국 "락이 뚫렸을 때 자원을 지키는 마지막 수단"이
  Redlock에는 없다. 그러니 정확성이 필요하면 Redlock이 아니라 합의 기반
  시스템(ZooKeeper 등)이나 자원 측 fencing을 쓰라는 결론.

**antirez(Redis 창시자)의 반박** 요지: 시계 "점프"는 운영으로 통제 가능하다
(점프 대신 미세 조정하는 NTP 설정). 획득 과정의 지연은 유효 시간 계산이
걸러낸다. 그리고 유효 시간 확인 **이후**의 정지는 fencing 없이는 어떤 락
시스템도 못 막는 문제이니 Redlock만의 결함이 아니다.

### 4-4. 내 견해 — "효율성의 락"과 "정확성의 락"을 나누면 논쟁이 정리된다

이 논쟁에서 가장 값진 산출물은 승패가 아니라 **Kleppmann이 제시한 구분**이다.
락을 쓰는 이유가 무엇인가?

- **효율성(efficiency)**: 같은 계산·같은 배치·같은 캐시 갱신을 여러 인스턴스가
  중복 수행하지 않게. **뚫려도 비용이 "일 두 번"에 그친다.**
  → **단일 Redis + `SET NX PX` + 토큰 + Lua 해제로 충분하다.** 드물게 중복
  실행되는 비용 < Redis 5대를 운영하는 비용. Redlock은 과잉이다.
- **정확성(correctness)**: 뚫리면 돈이 새거나 데이터가 깨진다(중복 결제,
  이중 차감). → **어떤 Redis 락도(Redlock 포함) 단독으로는 부족하다.**
  §2-1의 정지 문제와 fencing 부재가 남기 때문이다. 이 경우 방어선을
  **데이터 쪽에 이중으로** 깐다: DB 유니크 제약, 조건부 갱신(영향 행 수 확인),
  멱등키. 락은 있어도 "경합을 줄여주는 성능 최적화"일 뿐, 정합성의 근거가
  아니다.

그래서 내 답은: **"Redlock을 쓸까 말까"가 잘못된 질문이다. "이 락이 뚫리면
무엇을 잃는가"가 맞는 질문이고, 잃는 것이 크면 락을 강화할 게 아니라 락 없이도
안전한 데이터 설계를 먼저 깐다.** 실제로 선착순 쿠폰 같은 문제는 분산 락 없이
원자적 연산만으로 푸는 것이 정석이다 —
[선착순 쿠폰 설계](17-flash-sale-coupon-issuance-design.md) 참고.

## 5. 실무 선택 기준 한 장

| 상황 | 선택 | 이유 |
|---|---|---|
| 스케줄러·배치 중복 실행 방지 | 단일 Redis 락 (Redisson) | 뚫려도 중복 실행일 뿐. 단순함이 이긴다 |
| 같은 DB 안의 행 경합 | DB 락 / 원자적 UPDATE | 락과 데이터가 같은 시스템 = 실패 모드 최소 |
| 재고·쿠폰 카운트 | 원자적 연산 (INCR/Lua) | 애초에 락이 필요 없는 문제다 |
| 돈이 걸린 임계 구간 | 락 + **데이터 측 최종 방어선** | 락은 최적화, 정합성은 제약·조건부 갱신이 |
| 시스템 여러 개를 가로지르는 조정 | 그때가 분산 락의 자리 | 단, fencing 가능 여부부터 확인 |

**락을 꺼내기 전에 순서가 있다**: ① 한 문장 원자 연산으로 못 푸나(조건부
UPDATE, `SET NX`, Lua) → ② 같은 DB면 DB 락으로 안 되나 → ③ 그래도 여러 시스템에
걸친 조정이 필요할 때만 분산 락. 분산 락은 성능 해법이 아니라 **경계를 넘는
조정이 필요할 때의 마지막 도구**다.

## 6. 꼬리질문 대비 포인트

### "TTL을 아주 길게(10분) 잡으면 만료 문제가 없어지지 않나요?"

만료 함정(§2)의 확률은 줄지만 **반대쪽 비용이 커진다.** 락 주인이 크래시로
죽으면 그 자원은 **TTL이 다할 때까지 아무도 못 잠근다** — 10분짜리 부분 장애다.
TTL은 안전성(짧을수록 위험)과 가용성(길수록 복구 지연)의 다이얼이지, 한쪽으로
끝까지 돌려서 해결되는 값이 아니다. 실무 답은 "작업 예상 시간보다 여유 있게 +
watchdog으로 연장 + 그래도 뚫리는 경우는 fencing/데이터 제약으로"의 조합이다.

### "Redisson watchdog이 있으면 TTL 만료 문제는 해결된 것 아닌가요?"

아니다. watchdog은 **살아 있는 프로세스의 시간 예측 실패**만 지운다. 연장
스레드도 같은 JVM에 있으므로 STW GC·컨테이너 스로틀링·네트워크 단절 앞에서는
워커와 함께 멈춘다(§2-2). "정지를 인지하지 못한 채 재개하는 프로세스"라는 근본
문제는 자원 쪽 방어(fencing, 조건부 갱신)로만 막을 수 있다.

### "락 획득에 실패한 요청은 어떻게 처리하나요?"

용도에 따라 갈라 답한다. **중복 실행 방지 목적이면 즉시 포기**가 정답이다 —
누군가 하고 있다는 뜻이므로 기다릴 이유가 없다. **순서 대기 목적이면
재시도(스핀) 또는 대기**인데, 스핀 재시도는 Redis에 폴링 부하를 만들므로
간격·상한을 두고, Redisson처럼 pub/sub으로 "락 해제됨" 신호를 받아 깨어나는
구현이 폴링보다 낫다. 어느 쪽이든 **대기 시간 상한과 실패 응답 경로**가 없으면
락 경합이 스레드 고갈로 번진다 — 비관적 락의 커넥션 고갈과 같은 구조의 문제다
([낙관적 vs 비관적 락](../03-jpa-orm/10-optimistic-vs-pessimistic-lock.md) §3-2).

### "그냥 DB 비관적 락(SELECT FOR UPDATE)을 쓰면 안 되나요? 언제 Redis 분산 락이 필요한가요?" (시니어 변별 포인트)

**보호 대상이 그 DB 안에 있다면 DB 락이 우선이다.** 락과 데이터가 같은
시스템이라 "락은 살았는데 데이터 시스템만 죽는" 반쪽 실패가 없고, 트랜잭션
롤백과 락 해제가 원자적으로 묶인다. Redis 분산 락이 정당해지는 건 ① 보호
대상이 **DB 바깥**이거나(외부 API 호출, 파일 작업, 여러 저장소에 걸친 절차)
② DB 커넥션을 락 대기에 붙잡아두는 비용이 감당 불가라 **대기 줄을 DB 밖으로
빼야 할 때**다. 단 ②의 경우도 임계 구간 자체를 줄이는 설계(원자적 UPDATE)가
먼저다. "분산 환경이니까 분산 락"은 근거가 아니다 — **분산 환경에서도 경합
지점이 단일 DB면 DB가 이미 훌륭한 조정자다.**

### "Redlock 5대 중 2대가 죽으면 어떻게 되나요?"

과반(3대)이 살아 있으므로 **락 발급은 계속된다** — 그게 Redlock의 설계 목적이다.
문제는 다른 시나리오다: 락을 발급한 노드 중 하나가 **디스크 영속화 없이
재시작**하면 락을 잊은 채 돌아오고, 다른 클라이언트가 그 노드를 포함한 새
과반을 만들 수 있다(그래서 antirez는 재시작 시 TTL만큼 기동을 지연시키는
delayed restart를 제안했다). 이 답을 하면 "알고리즘을 외운 사람"과 "실패
모드를 따져본 사람"이 갈린다. **(가산점 포인트)**

## 한 줄 요약

Redis 분산 락의 세 함정 — **TTL 만료(정지를 인지 못 한 채 재개하는 프로세스),
소유자 미검증 해제(`DEL`은 주인을 안 가림), 시계 의존(Redlock의 만료 판정)** —
은 모두 "락을 쥐고 있다는 믿음"과 실제의 어긋남이며, `SET NX PX` + 고유 토큰 +
Lua 해제 + watchdog까지가 방어 가능한 영역이고 그 너머는 구조적으로 남는다.
그래서 Redlock 논쟁의 내 결론은 **락의 용도 구분**이다 — 효율성(중복 작업
방지)은 단일 Redis 락으로 충분하고, 정확성이 걸린 작업은 Redlock으로 락을
강화할 게 아니라 **최종 방어선을 데이터 쪽(유니크 제약·조건부 갱신·fencing
token)에 두고 락은 경합 완화 최적화로 강등**시킨다.
