# HyperLogLog와 Bitmap — "정확한 답이 꼭 필요한가"를 되물어 비용을 수백 배 줄이는 발상

> 핵심 관전 포인트: **UV(순 방문자) 집계를 Set으로 하면 방문자 수에
> 비례해 메모리가 커진다(수천만 UV = 수 GB). HyperLogLog는 약 12KB
> 고정 메모리로 표준오차 약 0.81%의 근사 유니크 카운트를 주는 확률
> 자료구조다(PFADD/PFCOUNT/PFMERGE) — 대신 "누가 왔는지"는 못 묻고
> 개수만 안다. Bitmap은 사용자 ID를 비트 오프셋으로 쓰는 방식으로,
> 1000만 유저의 출석 체크가 하루 약 1.25MB — 정확하고 비트 연산(AND/OR)으로
> "연속 출석·둘 다 방문" 같은 집합 질의까지 되지만, ID가 조밀한 정수일
> 때만 효율적이다. 핵심은 정확도를 비즈니스와 협상 가능한 파라미터로
> 다루는 감각이다.**

---

## 0. 질문 + 의도

**질문**: "HyperLogLog와 Bitmap은 각각 어떤 문제(UV 집계, 출석 체크)를
어떻게 싸게 해결하나요? 정확도의 트레이드오프는?"

**출제 의도**: 수천만 UV를 12KB로 세는 확률 자료구조의 존재를 아는지 —
"정확한 답이 꼭 필요한가"를 되물어 비용을 수백 배 줄이는 발상이다.
정확도(±0.8%)를 비즈니스와 협상 가능한 파라미터로 다루는 감각을 본다.

## 1. 문제 설정 — 순 방문자를 "정직하게" 세면 얼마가 드나

"오늘 우리 서비스에 몇 명이 왔나(UV)"는 **중복 제거 카운트(카디널리티)**
문제다. 같은 사람이 100번 와도 1로 세야 하므로, 누가 왔는지를 어딘가에
기억해야 한다. 정직한 구현은 Set이다:

```java
// 정확하지만 비싼 방법 — 방문자 수만큼 메모리가 커진다
redis.opsForSet().add("uv:2026-08-31", userId);       // SADD
Long uv = redis.opsForSet().size("uv:2026-08-31");    // SCARD
```

멤버 하나가 수십 바이트라고 치면 일 UV 5천만에 일 단위 키 하나가
GB 단위 — 게다가 일/주/월 집계를 다 들면 몇 배가 되고, 이 거대한
Set은 그 자체로 big key다. "정확한 UV"의 가격이 이만큼이라는 걸
먼저 계산해 보이는 것이 이 답변의 출발점이다.

여기서 되물어야 한다: **대시보드에 띄울 UV가 5,000만인지 5,040만인지가
비즈니스에 중요한가?** 대부분 아니다. 그 순간 확률 자료구조가 협상
카드가 된다.

## 2. HyperLogLog — 12KB로 수천만을 세는 근사 카운터

### 원리를 비유로 — 동전 던지기의 역추론

동전을 던져 "앞면이 연속 20번" 나온 걸 봤다면, 그런 희귀한 사건이
나올 만큼 **많이 던졌다**고 역추론할 수 있다. HLL이 하는 일이 이것이다:

1. 각 멤버를 해시해 비트열로 만든다 (같은 사용자는 항상 같은 비트열
   — 중복이 자동으로 같은 관측이 된다).
2. 비트열 앞부분으로 16384개 레지스터 중 하나를 고르고, 나머지
   비트열에서 "앞쪽에 0이 연속 몇 개인가"의 최댓값만 레지스터에
   기록한다 — 저장하는 건 멤버가 아니라 **이 최댓값들뿐**이다.
3. 카운트를 물으면, 레지스터들의 값을 조화평균으로 종합해 "이 정도로
   희귀한 패턴이 관측됐다면 유니크 멤버는 대략 N개"를 계산한다.

레지스터 16384개 × 몇 비트 = **약 12KB 고정**. 100만을 세든 1억을
세든 크기가 같다. 표준오차는 1.04/√16384 ≈ **0.81%** — "5,000만
±40만" 수준의 근사치를 12KB에 사는 것이다.

### 사용법 — Set과 거의 같은 모양

```java
// PFADD — 관측 추가 (멤버 자체는 저장되지 않는다)
redis.opsForHyperLogLog().add("uv:2026-08-31", userId);

// PFCOUNT — 근사 유니크 카운트
Long uv = redis.opsForHyperLogLog().size("uv:2026-08-31");

// PFMERGE — 일 단위 HLL들을 합쳐 주간 UV (합집합의 카디널리티)
redis.opsForHyperLogLog().union("uv:week-35",
        "uv:2026-08-25", "uv:2026-08-26", /* ... */ "uv:2026-08-31");
```

**PFMERGE가 실무 가치의 절반**이다. 일 단위로만 적재해 두면 주간·월간
UV를 원본 재집계 없이 합쳐서 얻는다 — 레지스터별 최댓값끼리 max를
취하면 되는 구조라 합산이 자연스럽다. 단, 이렇게 얻는 건 **합집합**
뿐이다. "월요일에도 오고 화요일에도 온 사람"(교집합)은 HLL이 직접
답하지 못한다.

### HLL이 포기한 것 — 트레이드오프의 정체

- **개별 조회 불가**: 멤버를 저장하지 않으므로 "userId 42가 오늘
  왔었나?"를 물을 수 없다. 개수만 안다.
- **삭제 불가**: 관측을 되돌릴 수 없다 (레지스터 최댓값은 낮출 수 없다).
- **±0.81% 오차**: 대시보드·트렌드 파악에는 충분하지만, **과금·정산·
  이벤트 당첨 판정처럼 숫자가 돈이나 권리가 되는 곳에는 부적합**하다.
  이 한 줄의 구분이 답변의 핵심이다.

## 3. Bitmap — 사용자 ID를 비트 위치로 쓰는 정확한 집합

### 출석 체크 — 하루 1000만 명을 1.25MB로

Bitmap은 별도 자료구조가 아니라 **String을 비트 배열로 다루는 명령들**
(SETBIT/GETBIT/BITCOUNT/BITOP)이다. 사용자 ID(정수)를 비트 오프셋으로
쓰면, "왔다/안 왔다"가 비트 1개다: 1000만 유저 = 10,000,000비트 ≈
**1.25MB/일**. Set이라면 수백 MB일 것이 수백분의 1이 된다.

```java
// 출석: 오늘 키의 userId번째 비트를 1로
redis.opsForValue().setBit("attend:2026-08-31", userId, true);   // SETBIT

// 특정 유저의 오늘 출석 여부 — HLL은 못 하는 개별 조회가 된다
Boolean attended = redis.opsForValue().getBit("attend:2026-08-31", userId);

// 오늘 총 출석자 수 — 1인 비트 개수
// BITCOUNT attend:2026-08-31
```

### 비트 연산 — Bitmap의 진짜 무기

날짜별 Bitmap끼리 AND/OR을 하면 집합 질의가 된다:

```
# 3일 연속 출석자 비트맵 (교집합)
BITOP AND attend:streak3 attend:2026-08-29 attend:2026-08-30 attend:2026-08-31
BITCOUNT attend:streak3          # → 3일 연속 출석자 수

# 이번 주 하루라도 출석 (합집합)
BITOP OR attend:week attend:2026-08-25 ... attend:2026-08-31
```

"연속 출석 보상", "이벤트 A와 B 모두 참여한 사용자"처럼 **교집합이
필요한 순간이 Bitmap을 고르는 결정적 이유**다 (HLL은 합집합만 된다).
결과가 정확하므로 보상 지급 같은 권리 판정에도 쓸 수 있다.

### Bitmap의 전제와 함정

- **ID가 조밀한(dense) 정수여야 한다**: 비트 오프셋 = 사용자 ID이므로
  UUID·이메일 키에는 그대로 못 쓴다(별도의 정수 매핑이 필요). 또
  ID가 듬성듬성하면(예: 최대 ID 1억인데 활성 유저 10만) 0으로 채워진
  공간까지 메모리를 차지해 오히려 낭비다 — **메모리는 멤버 수가
  아니라 "최대 오프셋"에 비례**한다.
- **큰 오프셋 한 방의 함정**: `SETBIT key 4000000000 1` 하나로 Redis가
  그 오프셋까지의 공간(약 500MB)을 즉시 할당한다. 검증 안 된 외부
  입력을 오프셋으로 쓰면 메모리 폭탄이 된다 (String 최대 512MB →
  오프셋 상한 2^32-1).
- 인원이 수십억 규모로 가면 비트맵도 커지므로 키를 ID 구간별로 쪼개는
  샤딩을 함께 설계한다.

## 4. 선택 기준 — 정확도는 요구사항이지 기본값이 아니다

| | Set | HyperLogLog | Bitmap |
|---|---|---|---|
| 메모리 | 멤버 수 비례 (수백 MB~GB) | 약 12KB 고정 | 최대 ID 비례 (1000만 ≈ 1.25MB) |
| 정확도 | 정확 | 오차 약 ±0.81% | 정확 |
| 개별 멤버 조회 | 가능 | 불가 | 가능 (GETBIT) |
| 집합 연산 | 교/합 모두 | 합집합만 (PFMERGE) | 교/합 모두 (BITOP) |
| 멤버 제약 | 없음 | 없음 | 조밀한 정수 ID |

고르는 사고 순서가 답변의 뼈대다:

1. **개수만 필요하고 오차가 허용되는가** (대시보드 UV, 트렌드) → HLL.
   비용이 수백~수천 배 싸다.
2. **개별 여부·교집합·정확성이 필요하고 ID가 정수인가** (출석 체크,
   보상 판정, 세그먼트 교집합) → Bitmap.
3. **멤버 자체를 열람해야 하거나 ID가 정수가 아니고 규모가 작은가**
   → 그냥 Set. 작은 규모에 확률 자료구조를 들이미는 것도 과설계다.

핵심 멘트: **"정확도를 낮출 수 있는지부터 비즈니스에 되묻는다.
±0.8%가 허용되는 순간 GB가 12KB가 된다"** — 기술 선택이 아니라
요구사항 협상이 비용을 결정한다는 관점이 이 질문의 정답 골격이다.

## 5. 꼬리질문 대비 포인트

### "어제도 오고 오늘도 온 사용자 수(교집합)가 필요하면요?"

HLL은 PFMERGE로 합집합만 직접 구한다. 교집합이 정말 필요하면 (1)
포함-배제 원리로 근사(|A∩B| = |A|+|B|−|A∪B|)할 수 있으나 오차가
증폭되어 교집합이 작을수록 신뢰도가 급락한다, (2) 정확한 교집합이
요구사항이면 애초에 Bitmap(BITOP AND)으로 설계한다 — 즉 "어떤 질의가
필요한가"가 자료구조 선택보다 먼저라는 답이 정답이다.

### "사용자 식별자가 UUID인데 Bitmap을 쓸 수 있나요?"

그대로는 못 쓴다. Bitmap의 오프셋은 정수이므로 UUID → 순번 정수의
매핑 테이블을 따로 두어야 하는데, 그 매핑 유지 비용과 정합성 부담이
생긴다. 식별자가 비정수이거나 희소하면 Bitmap의 전제가 무너지므로,
개수만 필요하면 HLL(해시 기반이라 멤버 형식 무관), 개별 여부까지
필요하면 Set이나 매핑 도입을 비교 검토한다고 답한다.

### "0.81%라는 오차는 어디서 나오는 숫자인가요?"

HLL의 표준오차는 1.04/√m (m = 레지스터 수)이고, Redis 구현은 m=16384라
1.04/128 ≈ 0.81%다. "표준"오차이므로 항상 0.81% 이내라는 보장이
아니라 통계적 분포의 폭이라는 점, 레지스터를 늘리면 오차는 √ 비율로
줄지만 메모리가 비례해 느는 구조라는 점까지 말하면 원리를 이해한
답이 된다. (가산점 포인트: Redis HLL은 카디널리티가 작을 때 희소
표현을 쓰다가 커지면 12KB 밀집 표현으로 전환해 작은 카운터는 더
싸다.)

### "이 근사 카운트를 이벤트 '선착순 N명' 판정에 써도 되나요?" (시니어 변별 포인트)

안 된다. HLL의 오차는 개수 판정이 권리·돈이 되는 순간 사고가 된다
(N명 근처에서 초과/미달 발급). 판정용 카운트는 정확해야 하므로
Set/Bitmap 또는 원자적 카운터(INCR)로 가고, HLL은 **사후 집계·대시보드
·트렌드**처럼 "숫자가 참고 정보인 자리"에만 쓴다. 같은 "카운트"라는
말 안에 "판정용 정확 카운트"와 "관측용 근사 카운트"라는 서로 다른
요구사항이 섞여 있음을 구분하는 것 — 이것이 정확도를 비즈니스
파라미터로 다루는 감각이다.

### "Redis 없이 DB로 UV를 세면 어떻게 되나요?"

방문 로그 테이블에 `COUNT(DISTINCT user_id)`가 되는데, 수천만 행의
중복 제거 집계는 실행할 때마다 큰 스캔/해시 비용을 내는 무거운
쿼리라 실시간 대시보드에는 부적합하다. 실무 구도는 역할 분리 —
원본 이벤트는 DB/로그 저장소에 남겨 정밀 분석·재집계 가능성을
보존하고, 실시간 화면용 근사치는 Redis HLL이 담당한다. (대형 분석
DB들도 근사 카운트 함수를 따로 제공할 만큼, "유니크 카운트는 비싸서
근사로 협상한다"는 발상 자체가 업계 공통이라고 덧붙이면 가산점
포인트.)

## 한 줄 요약

HyperLogLog는 멤버 대신 해시 관측의 통계만 저장해 약 12KB로 수천만
유니크를 ±0.81% 오차로 세는 "개수 전용" 자료구조이고, Bitmap은 조밀한
정수 ID를 비트 오프셋으로 써서 출석 체크를 하루 수 MB에 정확히 담고
BITOP으로 교집합 질의까지 해내는 도구라 — "개별 조회·교집합·정확성이
필요한가"로 둘을 가르고, 무엇보다 "±0.8%를 허용하면 GB가 12KB가 된다"는
정확도-비용 협상을 비즈니스에 먼저 되묻는 것이 이 질문이 요구하는
감각이다.
