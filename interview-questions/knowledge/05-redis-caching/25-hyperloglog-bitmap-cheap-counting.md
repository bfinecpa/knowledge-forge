# HyperLogLog와 Bitmap — "정확한 답이 꼭 필요한가"를 되물어 비용을 수백 배 줄이는 발상

> 핵심 관전 포인트: **UV(순 방문자) 집계를 Set으로 하면 멤버를 전부 저장해야 하므로 메모리가 방문자 수에 비례해 커진다. HyperLogLog는 멤버를 저장하지 않고 해시 관측의 통계만 남겨 12KB 고정 메모리로 표준오차 약 0.81%의 근사 유니크 카운트를 준다(PFADD/PFCOUNT/PFMERGE) — 0.81%는 `1.04/√m`에 레지스터 수 m=16384를 넣은 값이고, 12KB는 레지스터 16384개 × 6비트를 바이트로 환산한 값이다. 대신 "누가 왔는지"는 못 묻고 개수만 알며, 합집합(PFMERGE)은 되지만 교집합은 직접 구할 수 없다. Bitmap은 사용자 ID를 비트 오프셋으로 쓰는 방식이라 1000만 명 출석 체크가 하루 1,250,000바이트(약 1.25MB) — 정확하고, BITOP AND/OR로 "연속 출석·둘 다 방문" 같은 집합 질의를 서버 안에서 끝낼 수 있다. 단 ID가 조밀한 정수여야 한다는 전제가 붙는다. 핵심은 정확도를 비즈니스와 협상 가능한 파라미터로 다루는 감각이다.**

---

## 0. 질문 + 의도

**질문**: "HyperLogLog와 Bitmap은 각각 어떤 문제(UV 집계, 출석 체크)를 어떻게 싸게 해결하나요? 정확도의 트레이드오프는?"

**출제 의도**: 수천만 UV를 12KB로 세는 확률 자료구조의 존재를 아는지 — "정확한 답이 꼭 필요한가"를 되물어 비용을 수백 배 줄이는 발상이다. 정확도(±0.8%)를 비즈니스와 협상 가능한 파라미터로 다루는 감각을 본다.

## 1. 문제 설정 — 순 방문자를 "정직하게" 세면 얼마가 드나

### 1-1. 전제 지식 — 카디널리티 문제가 왜 비싼가

"오늘 우리 서비스에 몇 명이 왔나(UV)"는 **중복 제거 카운트** 문제다. 집합에 들어 있는 서로 다른 원소의 개수를 **카디널리티(cardinality, 집합의 크기)**라고 부르므로, UV는 카디널리티를 구하는 문제라고 말한다.

여기서 비용의 근원을 짚어야 한다. 단순한 방문 횟수라면 카운터 하나를 `INCR`로 올리면 끝이고 메모리는 8바이트다. 그런데 **중복을 제거하려면 "이 사람 아까 왔었나?"를 판정할 수 있어야 하고, 그러려면 지금까지 본 사람들을 어딘가에 기억해 둬야 한다.** 기억해야 하는 대상이 방문자 수만큼 늘어나므로 메모리도 같이 늘어난다.

정직한 구현은 Set이다.

```java
// 정확하지만 비싼 방법 — 멤버를 전부 저장하므로 방문자 수에 비례해 메모리가 커진다
redis.opsForSet().add("uv:2026-08-31", userId);       // SADD
Long uv = redis.opsForSet().size("uv:2026-08-31");    // SCARD
```

`SADD`가 중복을 알아서 걸러 주는 이유가 바로 "멤버를 전부 들고 있기 때문"이다. 편리함의 대가가 곧 메모리다.

### 1-2. 가격표를 먼저 계산해 보인다

Set의 메모리는 **멤버 수에 정비례한다.** 멤버 하나가 차지하는 실제 바이트는 값의 길이와 Redis 내부 자료구조(해시 테이블의 엔트리, 문자열 객체 헤더)에 따라 달라져 딱 떨어지는 상수는 아니다. 다만 자릿수 감각을 잡기 위해 **멤버 하나에 수십 바이트가 든다고 가정하고** 곱해 보면 이렇다.

```
가정: 멤버 1개당 약 50바이트 (값 + 내부 구조 오버헤드)

일 UV 5,000만  ->  50,000,000 × 50바이트 = 2,500,000,000바이트 = 약 2.5GB
```

이 2.5GB는 **가정 위에 세운 어림값**이지 측정값이 아니다. 중요한 것은 정확한 숫자가 아니라 **"멤버 수에 비례하므로 규모가 커지면 GB 단위로 간다"**는 성질이다.

게다가 이게 끝이 아니다.

- 일·주·월 집계를 각각 들면 키가 여러 벌이 된다.
- 이 거대한 Set은 그 자체로 **big key**다 — 키 하나가 수 GB면 삭제 한 번, 조회 한 번이 싱글 스레드를 오래 붙잡는다([big key 위험과 UNLINK](23-big-key-risk-and-unlink.md)).

여기서 되물어야 한다. **대시보드에 띄울 UV가 5,000만인지 5,040만인지가 비즈니스에 중요한가?** 대부분 아니다. "정확한 UV"의 가격이 이만큼이라는 것을 먼저 계산해 보이고, 그 다음에 정확도를 협상 카드로 꺼내는 것이 이 답변의 골격이다.

## 2. 두 도구 — HyperLogLog와 Bitmap

두 도구는 같은 "싸게 세기"라는 목표를 **정반대 방식**으로 푼다. HyperLogLog는 정확도를 조금 포기해서 메모리를 상수로 만들고, Bitmap은 정확도를 지키는 대신 "ID가 조밀한 정수여야 한다"는 전제를 요구한다. 하나씩 본다.

### 2-1. HyperLogLog — 12KB 고정으로 수천만을 세는 근사 카운터

먼저 분류부터. **확률 자료구조(probabilistic data structure)**는 정확한 답 대신 "정답 근처의 값"을 훨씬 적은 메모리로 돌려주는 자료구조를 말한다. 오차를 받아들이는 대가로 메모리를 극단적으로 줄인다. HyperLogLog(이하 HLL)는 그중 카디널리티 전용이다.

#### 원리 비유 — 동전 던지기의 역추론

친구가 "방금 동전을 던졌는데 앞면이 연속 20번 나왔어"라고 말했다고 하자. 우리가 곧바로 하는 추론은 **"그럼 엄청 많이 던졌겠네"**다.

왜 그런가. 앞면이 연속 k번 나올 확률은 `1/2^k`다. k=20이면 약 100만분의 1이다. 100만분의 1짜리 사건을 실제로 목격하려면 대략 100만 번쯤 시도했어야 한다. 즉 **"가장 희귀한 관측"이 "얼마나 많이 시도했는가"의 증거가 된다.** 시도 횟수를 세지 않고도, 목격한 최고 기록만 보고 시도 횟수를 역추론할 수 있다는 뜻이다.

HLL이 하는 일이 정확히 이것이다.

**① 멤버를 해시해 비트열로 바꾼다.** 좋은 해시 함수의 출력은 각 비트가 0과 1이 반반이고 서로 독립적이다. 즉 **해시 비트열은 통계적으로 동전 던지기 결과와 같다.** 그리고 같은 사용자는 항상 같은 비트열이 나오므로, 같은 사람이 100번 와도 100번 모두 똑같은 관측이 된다 — **중복 제거가 별도 로직 없이 공짜로 따라온다.** 이 점이 HLL의 출발점이다.

**② 비트열 앞쪽에 0이 연속 몇 개인지를 센다.** 앞쪽 0이 연속 k개 나올 확률도 마찬가지로 `1/2^k`다. 그러니 지금까지 본 비트열들 중 "앞쪽 0이 최대 k개"였다면, 서로 다른 값을 대략 `2^k`개쯤 봤다고 역추론할 수 있다.

```
해시 결과            앞쪽 연속 0의 개수      이 정도 희귀함
0001 0110 ...              3                 2^3  = 8개쯤 봤겠다
0000 0000 1010 ...         8                 2^8  = 256개쯤 봤겠다
0000 0000 0000 0011 ...   14                 2^14 = 16,384개쯤 봤겠다
```

저장하는 것은 멤버가 아니라 **이 최댓값 하나**뿐이다. 여기서 메모리가 상수로 떨어진다.

#### 왜 레지스터를 16384개나 두는가

방금 방식의 문제는 **편차가 너무 크다**는 것이다. 사용자를 딱 10명 봤는데 그중 한 명의 해시가 운 나쁘게 앞쪽 0을 20개 달고 나오면, HLL은 "100만 명쯤 봤군"이라고 답한다. 한 번의 관측에 전부를 거는 구조라 운 하나에 답이 뒤집힌다.

해법은 통계에서 늘 쓰는 그것이다 — **여러 번 관측해서 평균 낸다.**

HLL은 비트열의 앞부분 일부를 잘라 **레지스터(register, 관측값을 담는 작은 칸)** 번호로 쓴다. 예컨대 앞 14비트를 잘라 쓰면 `2^14 = 16384`개의 레지스터가 생기고, 멤버들은 이 16384개의 칸에 골고루 흩어진다. 각 칸은 자기에게 배정된 멤버들 중 "앞쪽 0 최댓값"만 기록한다. 카운트를 물으면 16384개 레지스터의 값을 **조화평균**으로 종합해 최종 추정치를 낸다.

여기서 조화평균을 쓰는 이유도 편차 때문이다. 레지스터 값은 지수(2의 몇 승)이므로 하나가 크게 튀면 산술평균은 그쪽으로 심하게 끌려간다. 조화평균은 큰 값의 영향을 억제하므로 튀는 레지스터 하나에 답이 흔들리지 않는다.

**그래서 레지스터가 많을수록 오차가 준다.** 표본이 많을수록 평균이 참값에 가까워지고, 그 수렴 속도는 표본 수의 제곱근에 반비례한다. HLL의 표준오차 공식이 정확히 그 모양이다.

```
표준오차 = 1.04 / √m        (m = 레지스터 개수)

Redis 구현은 m = 16384 이므로
  √16384 = 128
  1.04 / 128 = 0.008125 = 0.8125%  ->  흔히 말하는 "약 0.81%"
```

m을 바꿔 가며 계산해 보면 트레이드오프의 모양이 한눈에 보인다.

| 레지스터 수 m | 표준오차 | 레지스터 메모리 (m × 6비트) |
|---|---|---|
| 1,024 | 3.25% | 768바이트 |
| 4,096 | 1.625% | 3,072바이트 (3KiB) |
| 16,384 | 0.8125% | 12,288바이트 (12KiB) |
| 65,536 | 0.40625% | 49,152바이트 (48KiB) |

**오차를 절반으로 줄이려면 메모리가 4배 든다.** √m이 분모에 있으니 오차를 1/2로 하려면 m을 4배로 해야 하고, 메모리는 m에 비례하기 때문이다. Redis가 16384를 고른 것은 "12KB에 0.81%"가 대부분의 집계 용도에서 균형점이라는 판단이다.

#### 12KB는 어디서 나오는 숫자인가

레지스터 하나에 담기는 값은 "앞쪽 연속 0의 최대 개수"다. 해시가 64비트라면 이 값이 아무리 커야 60 언저리이므로, **0~63을 표현할 수 있는 6비트면 충분하다.** 그래서 계산은 이렇게 된다.

```
레지스터 16,384개 × 6비트 = 98,304비트
98,304비트 ÷ 8 = 12,288바이트 = 12KiB
```

여기에 짧은 헤더가 붙으므로 실제 키는 12,288바이트보다 아주 조금 크다. 어쨌든 **100만을 세든 1억을 세든 이 크기는 변하지 않는다.** 1절에서 계산한 "멤버 수 비례"와 정면으로 대비되는 지점이다. 표준오차 0.81%를 5,000만에 적용하면 `50,000,000 × 0.008125 = 406,250`이므로, "5,000만 ±40만" 수준의 근사치를 12KB에 사는 셈이다.

#### 사용법 — Set과 거의 같은 모양

```java
// PFADD — 관측 추가 (멤버 자체는 저장되지 않는다. 해시해서 레지스터만 갱신)
redis.opsForHyperLogLog().add("uv:2026-08-31", userId);

// PFCOUNT — 근사 유니크 카운트
Long uv = redis.opsForHyperLogLog().size("uv:2026-08-31");

// PFMERGE — 일 단위 HLL들을 합쳐 주간 UV (합집합의 카디널리티)
redis.opsForHyperLogLog().union("uv:week-35",
        "uv:2026-08-25", "uv:2026-08-26", /* ... */ "uv:2026-08-31");
```

**PFMERGE가 실무 가치의 절반**이다. 일 단위로만 적재해 두면 주간·월간 UV를 원본 재집계 없이 합쳐서 얻는다.

왜 합집합이 되는지도 원리에서 나온다. 각 레지스터는 "그 칸에서 본 최댓값"인데, A와 B를 합친 집합에서 그 칸의 최댓값은 **A의 최댓값과 B의 최댓값 중 큰 쪽**이다. 즉 레지스터별로 `max`만 취하면 합집합의 HLL이 정확히 만들어진다. 원본 데이터를 다시 훑을 필요가 없다.

단, 이렇게 얻는 것은 **합집합뿐**이다. "월요일에도 오고 화요일에도 온 사람"(교집합)은 HLL이 직접 답하지 못한다. 이유는 바로 아래에서 이어진다.

#### HLL이 포기한 것 — 트레이드오프의 정체

HLL의 제약은 전부 **"멤버를 저장하지 않는다"**는 한 가지 사실에서 파생된다. 이 뿌리를 잡고 있으면 네 가지가 자동으로 따라 나온다.

**개별 조회 불가.** 저장된 것이 레지스터 값뿐이라 "userId 42가 오늘 왔었나?"를 물을 수 없다. HLL이 답할 수 있는 질문은 **"몇 명"** 하나뿐이고, **"누가"**는 원천적으로 답할 수 없다.

**삭제 불가.** 레지스터는 최댓값만 들고 있어서 "이 관측을 빼라"를 처리할 수 없다. 최댓값을 만든 멤버가 누구였는지 모르니 값을 낮출 근거가 없다. 되돌리기가 없는 자료구조다.

**교집합을 직접 구할 수 없다.** 합집합이 `max`로 되는 것과 대칭인 연산이 교집합에는 없다. `max`는 "둘 중 한쪽에서라도 관측됐다"에 대응하지만, "양쪽 모두에서 관측됐다"를 레지스터 값만으로 표현할 방법이 없기 때문이다. 어느 멤버가 어느 레지스터를 어떤 값으로 만들었는지를 모르니, 두 HLL을 놓고 "겹치는 멤버"를 판정할 재료 자체가 없다.

**±0.81% 오차.** 대시보드·트렌드 파악에는 충분하지만, **과금·정산·이벤트 당첨 판정처럼 숫자가 돈이나 권리가 되는 곳에는 부적합하다.** 이 한 줄의 구분이 답변의 핵심이다.

### 2-2. Bitmap — 사용자 ID를 비트 위치로 쓰는 정확한 집합

#### 무엇인가 — 별도 자료구조가 아니다

Redis의 Bitmap은 새로운 타입이 아니다. **평범한 String 값을 "비트의 배열"로 취급해 읽고 쓰는 명령들**(`SETBIT` / `GETBIT` / `BITCOUNT` / `BITOP`)의 묶음이다. 타입 목록에 Bitmap이 따로 없는 이유가 이것이다.

핵심 아이디어는 **"사용자 ID를 비트의 위치(오프셋)로 쓴다"**이다. userId 42의 출석 여부는 42번째 비트 하나로 표현된다. 사람 한 명당 1비트다.

#### 출석 체크 — 하루 1000만 명을 1.25MB로

계산은 단순하다.

```
사용자 1000만 명 (ID가 0 ~ 9,999,999 로 조밀하게 채워져 있다고 하자)

필요한 비트 수 = 10,000,000비트
10,000,000 ÷ 8 = 1,250,000바이트

= 약 1.25MB (1MB를 100만 바이트로 볼 때)
= 약 1.19MiB (1MiB를 1,048,576바이트로 볼 때)
```

문서와 대시보드에서 흔히 "약 1.25MB"라고 말하는 값이 이것이다. 1절에서 본 Set의 수백 MB~GB와 비교하면 수백분의 1이다. 그러면서도 **결과는 근사가 아니라 정확하다.**

```java
// 출석: 오늘 키의 userId번째 비트를 1로
redis.opsForValue().setBit("attend:2026-08-31", userId, true);   // SETBIT

// 특정 유저의 오늘 출석 여부 — HLL은 못 하는 개별 조회가 된다
Boolean attended = redis.opsForValue().getBit("attend:2026-08-31", userId);

// 오늘 총 출석자 수 — 1인 비트 개수
// BITCOUNT attend:2026-08-31
```

`BITCOUNT`가 하는 일은 "1인 비트를 세는 것"이다. CPU에 비트 개수를 세는 전용 명령이 있어 바이트를 하나하나 뜯어보지 않고 워드 단위로 처리된다.

#### 비트 연산 — Bitmap의 진짜 무기

Bitmap을 고르는 결정적 이유는 메모리가 아니라 **`BITOP`이다.** 날짜별 Bitmap끼리 AND/OR을 하면 그대로 집합 질의가 된다.

```
# 3일 연속 출석자 비트맵 (교집합)
BITOP AND attend:streak3 attend:2026-08-29 attend:2026-08-30 attend:2026-08-31
BITCOUNT attend:streak3          # → 3일 연속 출석자 수

# 이번 주 하루라도 출석 (합집합)
BITOP OR attend:week attend:2026-08-25 ... attend:2026-08-31
```

이 두 줄이 왜 강력한지 정확히 짚어야 한다. **질의가 서버 안에서 끝난다.**

같은 일을 애플리케이션에서 하려면 어떻게 되는지 대비해 보면 차이가 분명하다.

```
[Bitmap 없이] 3일 연속 출석자 구하기
  3일치 출석자 명단(각 수백만 건)을 앱으로 전부 내려받는다
  -> 네트워크로 수십 MB가 오간다
  -> 자바 힙에 Set 세 개를 만든다 (GC 압박)
  -> retainAll() 로 교집합을 구한다

[BITOP AND]
  Redis 안에서 1.25MB짜리 바이트 배열 세 개를 워드 단위로 AND
  -> 앱으로 넘어오는 것은 BITCOUNT 결과 숫자 하나
```

"연속 출석 보상", "이벤트 A와 B 모두 참여한 사용자"처럼 **교집합이 필요한 순간이 Bitmap을 고르는 결정적 이유**다(HLL은 합집합만 된다). 그리고 결과가 정확하므로 보상 지급 같은 **권리 판정**에도 쓸 수 있다.

다만 `BITOP`이 공짜는 아니라는 점도 알고 있어야 한다. 대상 바이트 길이에 비례하는 O(N) 작업이라 싱글 스레드를 그만큼 붙잡는다. 1.25MB 몇 개 정도는 순식간이지만, 수백 MB짜리 비트맵을 실시간 요청 경로에서 `BITOP` 하는 설계는 피하고 배치로 미리 계산해 둔다.

#### Bitmap의 전제와 함정

**전제: ID가 조밀한 정수여야 한다.** 이것이 Bitmap의 성립 조건이자 가장 자주 깨지는 가정이다.

비트 오프셋은 정수이므로 UUID나 이메일을 키로 쓰는 시스템에는 그대로 적용할 수 없다. 더 미묘한 함정은 **정수인데 띄엄띄엄한 경우**다. **메모리는 멤버 수가 아니라 "가장 큰 오프셋"에 비례한다.**

```
활성 유저 10만 명, 그런데 최대 userId 가 1억이라면?

  필요 공간 = 100,000,000비트 ÷ 8 = 12,500,000바이트 = 약 12.5MB
  실제로 1인 비트 = 100,000개

  -> 12.5MB 중 대부분이 0으로 채워진 빈 공간이다.
     같은 10만 명을 Set으로 담는 것보다 오히려 비쌀 수 있다.
```

이런 상태를 **희소(sparse)하다**고 말한다. 희소한 비트맵은 Bitmap의 장점을 통째로 잃는다.

**전제가 깨질 때의 대안**은 ID를 조밀한 정수로 다시 매기는 것이다. `userId → 순번(0,1,2,...)` 매핑 테이블을 별도로 두고, 비트맵에는 순번을 오프셋으로 쓴다. 새 사용자가 오면 순번을 하나 발급한다(PostgreSQL이면 `bigserial` 컬럼 하나면 된다).

```sql
CREATE TABLE user_bit_slot (
    user_id  uuid   PRIMARY KEY,
    slot     bigserial NOT NULL UNIQUE   -- 비트맵 오프셋으로 쓸 조밀한 순번
);
```

대신 이 매핑에는 비용이 붙는다. 조회할 때마다 매핑을 한 번 더 타야 하고(그래서 매핑 자체를 캐시하게 된다), 매핑 테이블이 유실되면 기존 비트맵이 전부 해석 불능이 된다. **"매핑을 유지하는 비용 < Bitmap으로 얻는 이득"인지를 따져 보고 도입하는 것이지, 자동으로 정답은 아니다.**

**함정: 큰 오프셋 한 방.** `SETBIT key 4000000000 1` 명령 하나면 Redis는 그 오프셋까지의 공간을 즉시 할당한다.

```
오프셋 4,000,000,000 -> (4,000,000,000 + 1) ÷ 8 = 약 500,000,000바이트
                     = 약 500MB (약 477MiB)
```

검증하지 않은 외부 입력을 오프셋으로 쓰면 요청 한 번에 500MB가 잡히는 **메모리 폭탄**이 된다. Redis String의 최댓값은 512MiB이므로 오프셋 상한은 `2^32 - 1 = 4,294,967,295`다(512MiB = 536,870,912바이트 × 8비트 = 2^32비트). 즉 실수로 상한 근처를 찍으면 키 하나가 512MiB를 차지한다. **오프셋으로 쓸 값은 반드시 서버에서 범위를 검증한다.**

**규모가 커지면 샤딩.** 인원이 수십억 규모로 가면 비트맵 자체가 커져 big key가 되므로, ID 구간별로 키를 쪼갠다(`attend:2026-08-31:shard0`, `:shard1`, ...). `BITOP`도 샤드 단위로 수행하고 `BITCOUNT` 결과를 합산한다.

## 3. 선택 기준 — 정확도는 요구사항이지 기본값이 아니다

| | Set | HyperLogLog | Bitmap |
|---|---|---|---|
| 메모리 | 멤버 수에 비례 | 약 12KB 고정 | 최대 오프셋에 비례 (1000만 = 1,250,000바이트) |
| 정확도 | 정확 | 표준오차 약 0.81% | 정확 |
| 개별 멤버 조회 | 가능 | 불가 | 가능 (GETBIT) |
| 집합 연산 | 교집합·합집합 모두 | 합집합만 (PFMERGE) | 교집합·합집합 모두 (BITOP) |
| 멤버 제약 | 없음 | 없음 (해시하므로 형식 무관) | 조밀한 정수 ID |
| 삭제 | 가능 | 불가 | 가능 (비트를 0으로) |

고르는 **사고 순서**가 답변의 뼈대다. 자료구조를 먼저 고르고 요구사항을 맞추는 것이 아니라, **필요한 질의가 무엇인지를 먼저 확정하고 그에 맞는 도구를 고른다.**

**① 개수만 필요하고 오차가 허용되는가** (대시보드 UV, 트렌드 그래프) → HLL. 비용이 수백~수천 배 싸다.

**② 개별 여부·교집합·정확성이 필요하고 ID가 조밀한 정수인가** (출석 체크, 연속 출석 보상 판정, 세그먼트 교집합) → Bitmap.

**③ 멤버 자체를 열람해야 하거나, ID가 정수가 아니거나, 애초에 규모가 작은가** → 그냥 Set. **작은 규모에 확률 자료구조를 들이미는 것도 과설계다.** 하루 UV가 만 명인 서비스에서 Set은 몇 MB에 불과하고, 그 정도면 정확한 답을 공짜로 받는 셈이다.

핵심 멘트는 이것이다. **"정확도를 낮출 수 있는지부터 비즈니스에 되묻는다. ±0.8%가 허용되는 순간 GB가 12KB가 된다."** 기술 선택이 아니라 요구사항 협상이 비용을 결정한다는 관점이 이 질문의 정답 골격이다.

## 4. 꼬리질문 대비 포인트

### "어제도 오고 오늘도 온 사용자 수(교집합)가 필요하면요?"

HLL은 `PFMERGE`로 합집합만 직접 구한다. 2-1에서 본 이유 그대로다 — 합집합은 레지스터별 `max`로 만들어지지만, 교집합에 대응하는 레지스터 연산이 존재하지 않는다.

우회로가 하나 있긴 하다. **포함배제 원리**를 쓰는 것이다. 두 집합의 크기와 합집합 크기를 알면 교집합 크기가 산수로 나온다.

```
|A ∩ B| = |A| + |B| - |A ∪ B|
```

세 항 모두 HLL로 구할 수 있으니 계산 자체는 된다. **문제는 오차다.**

큰 수에서 큰 수를 빼면 결과는 작아지는데 **오차는 작아지지 않는다.** 각 항이 자기 크기에 비례한 오차를 갖고 있고, 그 오차들이 뺄셈 후에도 그대로 남기 때문이다. 구체적으로 넣어 보면 심각성이 보인다.

```
실제:  |A| = 5,000만,  |B| = 5,000만,  교집합 = 100만
따라서 |A ∪ B| = 5,000만 + 5,000만 - 100만 = 9,900만

각 항의 오차 (표준오차 0.8125%)
  |A|     = 5,000만 ± 406,250
  |B|     = 5,000만 ± 406,250
  |A ∪ B| = 9,900만 ± 804,375

세 오차가 최악으로 겹치면  406,250 + 406,250 + 804,375 = 1,616,875

구하려는 교집합은 100만인데, 오차 폭이 약 162만이다  ->  상대 오차 162%
```

**답의 크기(100만)보다 오차 폭(162만)이 더 크다.** 이러면 결과가 음수로 나오는 일도 흔하다. 반대로 교집합이 4,000만처럼 클 때 같은 계산을 하면 상대 오차가 약 3.2%로 떨어진다 — 즉 **교집합이 작을수록 신뢰도가 급락하는 구조**다. 그런데 실무에서 교집합을 묻는 질문은 대개 "겹치는 소수"를 찾는 것이라 하필 신뢰도가 가장 낮은 구간에 걸린다.

그래서 결론은 이렇게 정리한다. 정확한 교집합이 요구사항이면 **애초에 Bitmap(`BITOP AND`)으로 설계한다.** 즉 **"어떤 질의가 필요한가"가 자료구조 선택보다 먼저**라는 답이 정답이다. 나중에 "교집합도 필요해졌다"가 되면 HLL로 쌓아 둔 데이터로는 되돌릴 수 없고, 원본부터 다시 적재해야 한다.

### "사용자 식별자가 UUID인데 Bitmap을 쓸 수 있나요?"

그대로는 못 쓴다. Bitmap의 오프셋은 정수이므로 UUID → 순번 정수의 매핑 테이블을 따로 두어야 하는데, 그 매핑 유지 비용과 정합성 부담이 생긴다(2-2의 `user_bit_slot` 예시).

구체적으로 어떤 부담인지 말할 수 있으면 좋다. 매핑 조회가 요청 경로에 한 단계 추가되고, 매핑 자체를 캐시해야 하며, 매핑 테이블을 잃으면 기존 비트맵 전체가 해석 불능이 된다. 그리고 오프셋이 사용자 수만큼 늘어나므로 탈퇴자 순번을 재사용할지 말지 같은 운영 정책까지 따라온다.

식별자가 비정수이거나 희소하면 Bitmap의 전제가 무너지므로, **개수만 필요하면 HLL**(해시 기반이라 멤버 형식과 무관하다), **개별 여부까지 필요하면 Set이나 매핑 도입을 비교 검토한다**고 답한다.

### "0.81%라는 오차는 어디서 나오는 숫자인가요?"

공식과 대입 과정을 그대로 말한다.

```
HLL의 표준오차 = 1.04 / √m        (m = 레지스터 개수)

Redis 구현은 m = 16,384
  √16,384 = 128
  1.04 ÷ 128 = 0.008125
             = 0.8125%  ≈ 0.81%
```

여기에 두 가지를 덧붙이면 원리를 이해한 답이 된다.

**첫째, "표준"오차라는 말의 뜻.** 항상 0.81% 이내라는 보장이 아니다. 오차의 분포가 그 정도 폭을 갖는다는 통계적 서술이고, 실제 오차는 그보다 클 수도 작을 수도 있다. 대략 "대부분의 경우 ±0.81% 근처, 가끔 그 두세 배"라고 이해하는 것이 맞다.

**둘째, 오차와 메모리의 교환 비율.** 분모가 √m이므로 오차를 절반으로 줄이려면 m을 4배로 해야 하고, 메모리도 4배가 된다. 2-1의 표가 그 관계다 — 12KB에 0.81%, 48KB에 0.41%. **"오차를 줄이는 데 드는 비용이 제곱으로 붙는다"**는 것을 알고 있으면 "정확도를 조금만 더 올려 주세요"라는 요구가 얼마나 비싼지 즉답할 수 있다.

(가산점 포인트: Redis HLL은 카디널리티가 작을 때 **희소 표현**을 쓴다. 값이 들어 있는 레지스터만 압축해 기록하다가, 크기가 설정된 한계(`hll-sparse-max-bytes`)를 넘으면 12KB짜리 **밀집 표현**으로 전환한다. 그래서 "12KB 고정"은 정확히는 "최대 12KB"이고, 카운트가 작은 키는 훨씬 싸다. 일자별 HLL을 세밀한 차원으로 쪼개 두는 설계가 생각보다 저렴한 이유다.)

### "이 근사 카운트를 이벤트 '선착순 N명' 판정에 써도 되나요?" (시니어 변별 포인트)

안 된다. 이유를 오차의 성격에서 끌어내야 한다.

HLL의 오차는 **N명 경계 근처에서 그대로 사고가 된다.** 선착순 100만 명 이벤트에서 실제 카운트가 999,000명일 때 HLL이 1,004,000이라고 답하면 아직 자리가 남았는데 마감되고, 반대로 1,001,000명일 때 998,000이라고 답하면 초과 발급이 나간다. 표준오차 0.81%면 100만 근처에서 오차 폭이 ±8,000명이다 — **8,000명분의 권리가 오락가락한다.**

판정용 카운트는 정확해야 하므로 Set/Bitmap 또는 원자적 카운터(`INCR`)로 가고, HLL은 **사후 집계·대시보드·트렌드**처럼 "숫자가 참고 정보인 자리"에만 쓴다.

정리하면 이렇다. 같은 "카운트"라는 말 안에 **"판정용 정확 카운트"**와 **"관측용 근사 카운트"**라는 서로 다른 요구사항이 섞여 있다. 이 둘을 구분해 부르는 것 — 그것이 정확도를 비즈니스 파라미터로 다루는 감각이다.

### "Redis 없이 DB로 UV를 세면 어떻게 되나요?"

PostgreSQL이라면 방문 로그 테이블에 `SELECT count(DISTINCT user_id) FROM visit_log WHERE visited_at >= ...`가 된다. 문법은 한 줄인데 비용이 크다.

`DISTINCT` 집계는 **중복을 제거하기 위해 후보 값을 전부 메모리(또는 임시 파일)에 모아야** 한다 — 1절에서 본 Set의 문제가 DB 안에서 재현되는 것이다. 수천만 행이면 해시 테이블이 `work_mem`을 넘겨 디스크로 쏟아지고(spill), 실행할 때마다 같은 비용을 다시 낸다. 실시간 대시보드가 이 쿼리를 30초마다 때리면 그 자체가 DB 부하의 주범이 된다.

실무 구도는 **역할 분리**다.

```
원본 이벤트  ->  DB / 로그 저장소
                 (정밀 분석·재집계 가능성을 보존한다.
                  나중에 "그날 UV를 다시 계산해 줘"가 가능한 유일한 곳)

실시간 화면  ->  Redis HLL
                 (12KB, 즉답, ±0.81%)
```

원본을 지우고 HLL만 남기면 안 된다는 점이 중요하다. HLL은 되돌릴 수 없으므로, 나중에 "봇 트래픽을 빼고 다시 세 줘" 같은 요구가 오면 원본 없이는 답이 없다.

(가산점 포인트: 대형 분석 DB들도 대부분 근사 유니크 카운트 함수를 따로 제공한다. 그 내부 구현이 HLL인 경우도 많다. "유니크 카운트는 비싸서 근사로 협상한다"는 발상 자체가 Redis만의 트릭이 아니라 업계 공통이라고 덧붙이면 시야가 넓다는 신호가 된다.)

## 한 줄 요약

HyperLogLog는 멤버 대신 해시 관측의 통계만 저장해 레지스터 16384개 × 6비트 = 12KB로 수천만 유니크를 `1.04/√16384 = 0.81%` 표준오차로 세는 "개수 전용" 자료구조이고, Bitmap은 조밀한 정수 ID를 비트 오프셋으로 써서 1000만 명 출석 체크를 하루 1,250,000바이트에 정확히 담고 `BITOP`으로 교집합 질의까지 서버 안에서 끝내는 도구라 — "개별 조회·교집합·정확성이 필요한가"로 둘을 가르고, 무엇보다 "±0.8%를 허용하면 GB가 12KB가 된다"는 정확도-비용 협상을 비즈니스에 먼저 되묻는 것이 이 질문이 요구하는 감각이다.
