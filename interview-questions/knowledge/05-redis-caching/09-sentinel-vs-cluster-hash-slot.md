# Sentinel vs Cluster — 고가용성과 샤딩, 그리고 해시 슬롯의 제약

> 핵심 관전 포인트: **Sentinel은 "한 대의 마스터"를 감시하다가 죽으면
> 복제본을 승격시키는 자동 failover 장치(고가용성)이고, Cluster는
> 데이터를 16384개 해시 슬롯으로 쪼개 여러 마스터에 나눠 담는
> 샤딩 + 고가용성 체계다. 즉 Sentinel은 죽어도 서비스가 이어지게,
> Cluster는 한 대에 다 안 들어가는 데이터·쓰기량을 수평 확장하게
> 해준다. 대가로 Cluster에서는 여러 키를 한 번에 다루는 연산(MGET,
> 트랜잭션, Lua)이 같은 슬롯의 키끼리만 가능해진다 — 인프라 확장이
> 애플리케이션 코드를 바꾸는 대표 사례다.**

---

## 0. 질문 + 의도

**질문**: "Redis Sentinel과 Cluster의 차이는? Cluster에서 멀티 키
연산의 제약(해시 슬롯)은?"

**출제 의도**: Cluster 전환 시 멀티 키 연산(MGET, 트랜잭션)이 깨지는
것은 "인프라 확장이 애플리케이션 코드를 바꾸는" 사례다. 확장 계획을
세울 때 이 제약을 미리 아는 사람과 전환 후에 아는 사람의 차이는 크다 —
두 구성의 목적 차이(가용성 vs 확장)를 구분하고, 전환의 비용을
코드 수준까지 내려가 말할 수 있는지 본다.

## 1. 두 구성은 푸는 문제가 다르다

- **Sentinel = 가용성 문제**: "마스터가 죽으면 누가 자동으로 복제본을
  승격시키고, 클라이언트에게 새 주소를 알려주나?" 데이터는 여전히
  **마스터 한 대에 전부** 들어 있다.
- **Cluster = 용량·처리량 문제**: "데이터가 한 대 메모리에 안 들어가고,
  쓰기가 한 대 처리량을 넘으면?" 데이터를 여러 마스터에 **나눠 담는다
  (샤딩)**. 각 마스터에 복제본을 붙여 failover도 자체 처리한다.

비유: Sentinel은 **주방장 한 명 + 대기 주방장**을 두고 감독관이
쓰러짐을 감시하는 구조(일은 여전히 한 명이 다 함), Cluster는
**주방을 여러 개로 나누고 메뉴(키)마다 담당 주방을 정해두는**
구조다. 후자에서는 "여러 주방의 재료를 한 접시에 담는 요리(멀티 키
연산)"가 어려워진다.

## 2. Sentinel — 감시자 기반 자동 failover

Sentinel은 Redis 본체가 아니라 **별도의 감시 프로세스들**이다.
보통 3대 이상 홀수로 띄운다.

1. **감시**: 마스터·복제본의 생사를 지속 확인한다.
2. **합의**: 마스터가 안 보이면 Sentinel끼리 투표해서, 정족수(quorum)
   이상이 동의할 때만 "객관적 다운"으로 판정한다 — 감시자 한 명의
   착각(네트워크 순단)으로 failover가 나는 것을 막는 장치다.
3. **승격**: 복제본 중 하나를 새 마스터로 승격시키고, 나머지 복제본을
   새 마스터에 붙인다.
4. **안내**: 클라이언트는 Redis 주소를 직접 들고 있지 않고 **Sentinel에게
   "지금 마스터 누구야?"라고 물어서** 접속한다. failover 후에도
   애플리케이션 재배포 없이 새 마스터를 찾아간다.

한계는 명확하다 — **쓰기와 메모리는 여전히 마스터 한 대의 한계**를
넘지 못한다. 읽기는 복제본으로 분산할 수 있지만(복제 지연 감수),
쓰기 확장은 안 된다.

## 3. Cluster — 16384개 해시 슬롯으로 샤딩

Cluster는 키 공간을 **16384개의 해시 슬롯**으로 나누고, 각 마스터가
슬롯 범위를 나눠 갖는다.

```
슬롯 번호 = CRC16(key) mod 16384

마스터 A: 슬롯     0 ~  5460
마스터 B: 슬롯  5461 ~ 10922
마스터 C: 슬롯 10923 ~ 16383
```

- 키가 어느 노드에 있는지는 **계산으로 결정**된다. 클러스터 지원
  클라이언트는 슬롯→노드 맵을 캐싱해두고 바로 해당 노드로 보낸다.
- 엉뚱한 노드로 보내면 서버가 `MOVED <슬롯> <주소>` 응답으로 알려주고
  클라이언트가 맵을 갱신해 재시도한다 (슬롯 이동 중엔 `ASK`).
- 노드 추가/제거 시에는 슬롯 단위로 데이터를 옮긴다(리샤딩) —
  전체 재분배가 아니라 이동하는 슬롯만 영향을 받는다.
- 각 마스터에 복제본을 붙이면 failover도 클러스터가 자체 수행한다.
  즉 Cluster는 **샤딩 + Sentinel 역할까지 내장**한 구성이다.

## 4. 멀티 키 연산의 제약 — 인프라가 코드를 바꾼다 (면접의 핵심)

여러 키를 원자적으로 다루는 연산은 **모든 키가 같은 슬롯에 있을 때만**
가능하다. 서로 다른 노드에 흩어진 키를 하나의 원자 연산으로 묶을
방법이 없기 때문이다.

```java
// 단일 Redis(Sentinel 구성)에서는 잘 돌던 코드
mget("user:1:name", "user:2:name", "user:3:name");
// → Cluster에서: 키마다 슬롯이 달라 CROSSSLOT 에러
//   (error) CROSSSLOT Keys in request don't hash to the same slot

// MULTI/EXEC 트랜잭션, SINTERSTORE, Lua 스크립트(KEYS 여러 개),
// RENAME 등도 전부 같은 제약을 받는다
```

**해법 1 — 해시 태그로 같은 슬롯에 모으기**: 키 이름에 `{...}`가 있으면
**중괄호 안쪽만** 해시 계산에 쓴다. 함께 연산할 키들을 의도적으로
같은 슬롯에 배치할 수 있다.

```java
// Before: user:1의 데이터끼리도 슬롯이 제각각
"user:1:profile", "user:1:settings"     // 키 전체를 해시 → 다른 슬롯

// After: {user:1} 부분만 해시 → 두 키가 반드시 같은 슬롯
"{user:1}:profile", "{user:1}:settings" // MULTI, Lua로 함께 다룰 수 있음
```

단, 태그를 너무 굵게 잡으면(예: `{service}:*` 전부) 한 슬롯에 데이터가
몰려 **샤딩한 의미가 사라지고 hot spot**이 된다 — 원자성이 꼭 필요한
최소 단위(사용자 1명, 주문 1건)로만 묶는 것이 원칙이다.

**해법 2 — 애플리케이션에서 쪼개기**: 원자성이 필요 없다면
클라이언트가 키를 노드별로 나눠 병렬 요청하고 결과를 합친다
(좋은 클라이언트 라이브러리는 MGET을 노드별로 분할 실행해준다).
원자성이 정말 필요하다면 설계를 다시 봐야 한다.

(가산점 포인트) 그 외 전환 시 깨지는 것들: **데이터베이스 번호
(`SELECT`)는 0번만** 지원, 키스페이스 전체를 도는 작업(`SCAN`)은
노드별로 각각 돌아야 함, 파이프라인도 노드 단위로 분리됨.

## 5. 선택 기준 — 언제 무엇을 쓰나

- **데이터가 한 대 메모리에 들어가고, 쓰기량도 한 대로 충분**하다 →
  Sentinel(마스터 1 + 복제본 + Sentinel 3대). 멀티 키 연산·트랜잭션·Lua를
  제약 없이 쓸 수 있고 운영이 단순하다.
- **메모리 또는 쓰기 처리량이 한 대의 한계를 넘는다** → Cluster.
  단, 전환 전에 코드베이스에서 멀티 키 연산을 전수 조사해야 한다.
- 흔한 실수: "확장 대비"로 처음부터 Cluster를 깔아 복잡도만 사는 것.
  반대의 실수: Sentinel에서 멀티 키 연산을 마음껏 쓰다가 나중에
  Cluster 전환이 사실상 재개발이 되는 것 — **키 설계 때부터 해시
  태그 규칙을 잡아두면 전환 비용이 크게 줄어든다** (가산점 포인트).

## 6. 꼬리질문 대비 포인트

### "failover가 일어나는 몇 초 동안 쓰기는 어떻게 되나요?"

새 마스터 승격까지의 짧은 시간 동안 쓰기는 실패한다(에러 또는
타임아웃). 더 위험한 건 **유실**이다 — Redis 복제는 비동기라, 죽은
마스터가 받았지만 복제본에 아직 전달 안 된 쓰기는 승격과 함께
사라진다. 네트워크 분리로 구 마스터가 잠시 살아서 쓰기를 계속 받는
split-brain도 가능해서, `min-replicas-to-write`(복제본 N대가 살아있을
때만 쓰기 허용)로 유실 폭을 줄이는 완화책을 언급하면 좋다.
애플리케이션 쪽에서는 "이 몇 초의 실패·유실을 견디는 재시도/멱등
설계"가 필요하다는 데까지 가면 강하다.

### "해시 태그를 쓰면 다 해결되나요?"

아니다. 태그로 묶인 키들은 **영원히 같은 노드에 산다** — 묶음이
커지면 그 노드만 메모리·트래픽이 몰리는 hot spot이 되고, 리샤딩으로도
쪼갤 수 없다(슬롯 단위로만 이동하므로). 원자성이 필요한 최소
단위로만 묶고, "큰 집계는 태그로 묶지 말고 애플리케이션에서 합친다"는
원칙을 함께 말해야 한다.

### "Cluster에서 MULTI/EXEC 트랜잭션과 Lua는 못 쓰나요?"

쓸 수 있다 — 단, **관련된 키가 전부 같은 슬롯일 때만**. Lua 스크립트도
`KEYS`로 넘기는 키들이 같은 슬롯이어야 한다. 그래서 분산 락, 선착순
발급 같은 원자 연산 설계는 Cluster 전제라면 처음부터 "연산 단위 =
슬롯 단위"가 되도록 키를 설계해야 한다.

### "읽기 확장만 필요하면 어떤 구성이 낫나요?"

쓰기는 한 대로 충분하고 읽기만 많다면 Cluster까지 갈 필요 없이
**Sentinel 구성 + 복제본 읽기 분산**이 단순하다. 단 복제는 비동기라
**방금 쓴 값이 복제본에서 안 보일 수 있다**(복제 지연) — "내가 쓴 글이
목록에 없어요" 류의 문의로 이어지는 지점이라, 읽기 분산 대상은
지연을 허용하는 조회로 한정한다고 답하면 좋다.

### "Sentinel 구성에서 Cluster로 전환한다면 무엇부터 점검하나요?" (시니어 변별 포인트)

1. **코드 전수 조사**: MGET/MSET, MULTI/EXEC, Lua, `RENAME`,
   `SINTERSTORE` 등 멀티 키 연산 사용처 — 같은 슬롯 보장이 없으면
   전부 깨진다.
2. **키 설계 변경**: 원자성이 필요한 묶음에 해시 태그 도입 —
   기존 키와 슬롯이 달라지므로 사실상 키 마이그레이션이다.
3. **클라이언트 교체/설정**: 클러스터 프로토콜(MOVED/ASK)을 아는
   클라이언트인지, 파이프라인·MGET 분할을 지원하는지.
4. **운영 체계**: `SELECT` 다중 DB 사용처 제거, 키스페이스 순회
   작업(배치 SCAN)의 노드별 실행, 모니터링을 노드 단위로 재구성.

"전환은 인프라 작업이 아니라 애플리케이션 프로젝트"라는 결론까지
말하면 출제 의도에 정확히 부합한다.

---

## 한 줄 요약

Sentinel은 마스터 한 대의 죽음을 자동 failover로 견디게 하는
**가용성** 장치, Cluster는 16384개 해시 슬롯으로 데이터를 나눠
메모리·쓰기를 **수평 확장**하는 장치다 — 그리고 Cluster의 대가는
"같은 슬롯의 키끼리만 멀티 키 연산이 된다"는 제약이라서, 확장 계획은
서버 증설이 아니라 **키 설계와 코드 점검에서 시작**해야 한다.
