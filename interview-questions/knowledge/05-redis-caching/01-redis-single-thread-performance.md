# Redis가 빠른 이유 — 싱글 스레드와 높은 처리량의 역설

> 핵심 관전 포인트: **Redis가 빠른 건 ① 모든 데이터가 메모리에 있고
> ② 명령 실행이 싱글 스레드라 락·컨텍스트 스위칭 비용이 0이며
> ③ I/O 멀티플렉싱(epoll 등) 이벤트 루프로 스레드 하나가 수만 개의
> 연결을 처리하기 때문이다. 명령 하나가 마이크로초 수준이라 병목은
> CPU가 아니라 네트워크/메모리 — 그래서 스레드 하나로 충분하다.
> 단, 같은 이유로 O(N) 명령 하나(KEYS, 큰 컬렉션의 HGETALL)가
> 서버 전체를 세운다 — 빠른 이유와 느려지는 이유는 동전의 양면이다.**

---

## 0. 질문 + 의도

**질문**: "Redis는 왜 빠른가요? 싱글 스레드인데 어떻게 높은 처리량을
내나요?"

**출제 의도**: 메모리 접근·이벤트 루프라는 구조적 이유를 알아야
"Redis에 O(N) 명령 하나가 전체를 블로킹한다"는 운영상 함정까지
연결된다. 빠른 이유와 느려지는 이유가 동전의 양면임을 아는지 본다.

## 1. 빠른 이유 ① — 디스크가 아니라 메모리

RDB는 데이터가 디스크에 있고, 쿼리마다 버퍼 풀 확인 → 디스크 I/O →
파싱/플래닝을 거친다. Redis는 **모든 데이터가 처음부터 RAM에** 있다.
읽기 경로에 디스크가 아예 없다.

메모리 접근과 디스크 접근은 속도의 자릿수가 다르다. 비유하면 책상 위에
펼쳐둔 노트(메모리)와 지하 서고에서 찾아와야 하는 책(디스크)의 차이 —
Redis는 애초에 모든 것을 책상 위에 올려두는 선택을 했고, 그 대가로
"데이터 전부가 RAM에 들어가야 한다"는 용량 제약을 진다.

여기에 자료구조도 목적별로 최적화되어 있다(해시테이블, 스킵 리스트 등)
— GET/SET 같은 대부분의 명령이 O(1), 즉 데이터가 얼마나 많든 일정
시간이다.

## 2. 빠른 이유 ② — 싱글 스레드라서 '오히려' 빠르다

직관과 반대로 들리는 지점이라 면접에서 꼭 파고든다. 멀티 스레드가 항상
빠른 게 아니다 — 스레드가 여러 개면:

- **락(lock)이 필요하다**: 같은 데이터를 두 스레드가 동시에 만지면
  깨지므로, 자료구조마다 잠금을 걸고 대기하는 비용이 생긴다.
- **컨텍스트 스위칭 비용**: CPU가 스레드를 갈아끼울 때마다 레지스터
  저장/복원, CPU 캐시 오염이 발생한다.

Redis 명령 하나의 처리 시간은 **마이크로초 수준**으로 극히 짧다. 이렇게
개별 작업이 짧으면 병목은 CPU 연산이 아니라 **네트워크와 메모리 대역폭**
이다. 즉 스레드를 늘려 CPU를 더 써봤자 얻을 게 없고, 락·스위칭 비용만
얹는 꼴이다. 그래서 "명령 실행은 스레드 하나가 순서대로"가 최적이 된다.

비유: 주문 하나 처리에 1초 걸리는 바리스타라면 여러 명을 고용해야 하지만,
주문 하나가 0.001초라면 한 명이 줄 선 손님을 다 받는 게 낫다 — 여러
명이 같은 기계를 두고 서로 기다리는 낭비가 없다.

### 2-1. 공짜 보너스 — 모든 명령이 원자적

싱글 스레드의 부산물로, **명령 하나하나가 저절로 원자적(atomic)**이다.
`INCR` 실행 중간에 다른 클라이언트의 명령이 끼어들 수 없다. 애플리케이션
쪽에서 락 없이도 카운터, 재고 차감, 중복 방지 같은 동시성 로직을 Redis
명령 하나로 안전하게 처리할 수 있는 근거가 바로 이 실행 모델이다.

```java
// before: 애플리케이션에서 조회 후 갱신 — 두 요청이 겹치면 카운트 유실
Long count = redis.get("view:1234");        // 둘 다 100을 읽고
redis.set("view:1234", count + 1);          // 둘 다 101을 씀 → 1 증발

// after: Redis 원자 명령 하나로 — 싱글 스레드 실행이라 겹칠 수 없음
redis.incr("view:1234");                    // 100 → 101 → 102 보장
```

## 3. 빠른 이유 ③ — I/O 멀티플렉싱 이벤트 루프

"스레드 하나가 어떻게 수만 개 클라이언트 연결을 감당하나?"에 대한 답이다.

연결마다 스레드를 하나씩 붙이는 고전 방식(thread-per-connection)은
연결 수만큼 스레드가 필요하다. Redis는 대신 OS의 **I/O 멀티플렉싱**
(Linux의 epoll, macOS의 kqueue 등)을 쓴다 — "이 수만 개 소켓 중 지금
읽을 데이터가 도착한 것만 알려줘"라고 OS에 위임하고, 이벤트 루프가
**준비된 소켓만** 돌면서 명령을 읽고 → 실행하고 → 응답을 쓴다.

```text
[이벤트 루프 한 바퀴]
epoll_wait()  →  "소켓 3, 17, 4021에 데이터 도착"
  ├─ 소켓 3    명령 파싱 → 실행 → 응답 버퍼에 쓰기
  ├─ 소켓 17   명령 파싱 → 실행 → 응답 버퍼에 쓰기
  └─ 소켓 4021 명령 파싱 → 실행 → 응답 버퍼에 쓰기
다시 epoll_wait() ...
```

비유: 웨이터 한 명이 테이블마다 붙어 서 있는 게 아니라(연결당 스레드),
호출 벨이 울린 테이블만 찾아가는 것(이벤트 루프). 각 주문 처리가 순식간
이라면 웨이터 한 명으로 홀 전체를 감당할 수 있다.

정리하면 — **"메모리 + 싱글 스레드 + 이벤트 루프" 세 가지가 한 세트**다.
메모리라서 명령이 짧고, 짧아서 싱글 스레드로 충분하고, 싱글 스레드가
수만 연결을 받으려면 이벤트 루프가 필요하다.

### 3-1. (가산점 포인트) "완전한 싱글 스레드"는 아니다

정확히는 **명령 실행이 싱글 스레드**인 것이고, 주변 작업은 별도 스레드가
돕는다:

- **I/O 스레드**: Redis 6.0부터 소켓 읽기/쓰기(네트워크 I/O)를 여러
  스레드로 분산할 수 있다. 단 **명령 실행 자체는 여전히 한 스레드** —
  원자성 모델은 그대로다.
- **백그라운드 스레드**: `UNLINK`(비동기 삭제), AOF fsync 등 느린 작업을
  뒤로 넘긴다.
- **fork 자식 프로세스**: RDB 스냅샷, AOF rewrite는 자식 프로세스가
  수행한다.

"싱글 스레드인데 6.0부터 멀티 스레드 아닌가요?"라는 꼬리질문에 "I/O만
멀티, 실행은 싱글"로 선을 그으면 정확히 이해했다는 신호다.

## 4. 동전의 뒷면 — 같은 이유로 Redis는 통째로 멈춘다

여기까지가 "빠른 이유"라면, 시니어를 가르는 건 그 다음 문장이다:
**실행 스레드가 하나라는 말은, 느린 명령 하나가 서버 전체를 세운다는
뜻이다.** 대기열에 줄 선 다른 모든 클라이언트의 명령이 그 뒤에서 기다린다.

대표적인 블로킹 폭탄:

| 명령 | 왜 위험한가 |
|---|---|
| `KEYS *` | 전체 키스페이스 순회 O(N) — 운영에서 금지 |
| `HGETALL` / `SMEMBERS` (big key) | 수백만 필드/멤버면 그 자체가 O(N) |
| `DEL` (big key) | 큰 컬렉션 삭제도 동기적 O(N) |
| `FLUSHALL` | 전체 삭제 동기 실행 |

```text
// before: 세션 키 정리 배치에서 — 키가 수백만이면 수 초간 전 서비스 정지
KEYS session:*

// after: 커서 기반으로 조금씩 순회 — 한 호출이 짧아 루프 사이에 다른 명령 처리
SCAN 0 MATCH session:* COUNT 500
// 큰 키 삭제는 DEL 대신 UNLINK — 메모리 해제를 백그라운드 스레드로
UNLINK big:set:key
```

운영 습관으로 연결하면: **명령을 고를 때 시간 복잡도를 먼저 확인**하고
(Redis 문서에 명령마다 복잡도가 명시되어 있다), `SLOWLOG`로 느린 명령을
상시 감시하고, big key가 생기지 않게 키를 설계 단계에서 쪼갠다.

이 구조를 이해하면 "Redis가 빠르다"와 "Redis에서 O(N) 명령은 장애다"가
같은 문장의 앞뒷면임이 보인다 — RDB에서 느린 쿼리는 그 커넥션 하나가
느려질 뿐이지만, Redis에서 느린 명령은 **모두의 명령**을 세운다.

## 5. 꼬리질문 대비 포인트

### "그럼 멀티코어 서버에서 Redis는 코어 하나만 놀리고 나머지는 낭비인가요?"

명령 실행은 코어 하나를 쓰는 게 맞지만, 낭비를 줄이는 층위가 있다.
① I/O 스레드(6.0+)와 백그라운드 스레드, fork 자식이 다른 코어를 쓴다.
② 그래도 실행 코어가 병목이면 **한 장비에 인스턴스를 여러 개** 띄우거나
Cluster로 샤딩해 인스턴스 수 = 실행 코어 수로 확장하는 것이 정석이다.
즉 Redis의 수평 확장 단위는 스레드가 아니라 인스턴스다.

### "모든 명령이 원자적이라면 트랜잭션이나 Lua는 왜 필요한가요?"

원자성은 **명령 하나** 단위다. "조회해서 값을 보고 → 조건에 따라 다른
명령"처럼 **여러 명령에 걸친 로직**(check-then-act)은 명령 사이에 다른
클라이언트가 끼어들 수 있다. 그 구간을 묶는 도구가 MULTI/EXEC(일괄
실행), WATCH(낙관적 검사), Lua 스크립트(로직째 원자 실행)다. 단 Lua도
실행 중엔 서버 전체를 점유하므로, 긴 스크립트는 그 자체가 블로킹 폭탄이
된다 — 원자성의 근거(싱글 스레드)와 블로킹 위험의 근거가 같기 때문이다.

### "운영 중인 Redis가 갑자기 느려졌습니다. 어떤 원인부터 의심하나요?" (시니어 변별 포인트)

싱글 스레드 모델에서 지연의 원인은 "실행 스레드를 누가 오래 잡았나"로
좁혀진다. 순서대로: ① `SLOWLOG GET`으로 느린 명령 확인 — KEYS,
HGETALL 등 O(N) 명령이나 big key 접근이 단골. ② 대량 키 동시 만료 —
만료 삭제 작업이 몰리는 경우. ③ RDB 저장/AOF rewrite 중 fork 비용과
copy-on-write 메모리 복사 — 데이터가 클수록 fork 순간 지연이 튄다.
④ maxmemory 도달로 eviction이 쓰기마다 발생. ⑤ 스왑 발생 — 메모리 DB가
디스크로 스왑되면 성능이 자릿수로 무너진다. "Redis는 빨라서 병목일 리
없다"가 아니라, 빠른 구조의 전제(짧은 명령, 충분한 메모리)가 깨진 지점을
찾는 접근이 운영 경험의 신호다.

### "그렇게 빠르면 DB 대신 Redis에 다 저장하면 안 되나요?"

속도의 대가를 지불하고 있기 때문이다. ① 데이터 전부가 RAM에 있어야
하므로 저장 비용이 디스크 대비 훨씬 비싸고 용량 한계가 낮다. ② 기본
설정에서는 장애 시 데이터 유실 가능성이 있다(영속화는 RDB/AOF로 보완
하지만 RDB만큼의 내구성 보장과는 성격이 다르다). ③ 복잡한 조건 검색,
조인, 강한 트랜잭션 격리가 없다. 그래서 Redis는 "원본 저장소"가 아니라
**잃어도 복구 가능한 데이터의 고속 계층**(캐시, 세션, 카운터, 랭킹)으로
쓰는 것이 기본 위치다.

## 한 줄 요약

Redis는 "메모리 + 싱글 스레드 + 이벤트 루프"라는 한 세트의 설계로
마이크로초짜리 명령을 락 비용 없이 쏟아내기에 빠르고 — 바로 그 설계
때문에 O(N) 명령 하나가 모두를 세우므로, 빠르게 쓰는 법과 세우지 않는
법은 같은 원리에서 나온다.
