# Redis 5대 자료구조 — "빠른 Map"을 넘어서는 설계 도구함

> 핵심 관전 포인트: **Redis는 key-value 저장소지만 value가 단순 문자열이
> 아니라 자료구조다. String은 캐시·카운터·분산 락, Hash는 객체의 필드
> 단위 저장/부분 갱신, List는 큐와 최근 목록, Set은 중복 방지와 집합
> 연산, Sorted Set은 score 정렬이 필요한 랭킹·지연 큐에 쓴다. 애플리케이션
> 에서 짜면 조회-수정-저장 3단계 + 동시성 문제가 되는 로직을, 자료구조를
> 맞게 고르면 원자적 명령 한 방으로 끝낼 수 있다 — 이게 자료구조를 아는
> 실익이다.**

---

## 0. 질문 + 의도

**질문**: "Redis의 주요 자료구조(String, Hash, List, Set, Sorted Set)와
각각의 사용 사례는?"

**출제 의도**: Redis를 "빠른 Map"으로만 쓰는 사람과 Sorted Set으로
랭킹을, Set으로 중복 방지를 설계하는 사람의 활용 폭 차이. 도구의
표현력을 아는 만큼 설계 선택지가 넓어진다.

## 1. 왜 자료구조가 5개나 있나 — "연산을 서버로 옮기기 위해"

Redis가 단순 key→문자열 저장소였다면, 목록에 항목 하나를 추가하려면
클라이언트가 **전체를 읽고 → 수정하고 → 전체를 다시 쓰는** 3단계를
거쳐야 한다. 이 사이에 다른 요청이 끼면 갱신이 유실된다(lost update).

Redis 자료구조의 본질은 **그 연산을 서버 안으로 옮긴 것**이다. "리스트
왼쪽에 추가", "집합에 없으면 넣기", "score 1 올리기"가 각각 명령 하나고,
싱글 스레드 실행 덕에 전부 원자적이다. 자료구조를 맞게 고른다 =
동시성 처리와 네트워크 왕복을 Redis에 떠넘긴다.

```java
// before: String에 JSON 목록을 통째로 — 조회-수정-저장, 경합 시 유실
String json = redis.get("recent:user:1");        // ["A","B"]
List<String> items = parse(json);
items.add(0, "C");                                // 이 사이 다른 요청이 끼면
redis.set("recent:user:1", toJson(items));        // 한쪽 갱신이 증발

// after: List 자료구조 — 명령 하나가 원자적, 경합 자체가 없음
redis.lpush("recent:user:1", "C");
```

## 2. 다섯 가지 자료구조와 사용 사례

### 2-1. String — 만능 기본형: 캐시, 카운터, 분산 락

가장 단순한 "key 하나 = 값 하나". 값은 텍스트뿐 아니라 직렬화된 객체,
숫자, 바이너리까지 담는다.

- **캐시**: 조회 결과(JSON 직렬화)를 `SET key value EX 300`으로 TTL과
  함께 저장 — look-aside 캐시의 기본형.
- **카운터**: `INCR`/`INCRBY`가 원자적이라 조회수, 재고 차감, API 호출
  횟수 제한(rate limit)에 바로 쓴다.
- **분산 락**: `SET lock:order:42 <소유자토큰> NX PX 3000` — "없을 때만
  넣기(NX)"가 원자적이라 락 획득 경쟁을 명령 하나로 판정한다.

```text
SET  product:1234 '{"name":"콜라","price":1500}' EX 300   # TTL 캐시
INCR view:product:1234                                     # 원자 카운터
SET  lock:coupon NX PX 3000                                # 분산 락 획득
```

### 2-2. Hash — 객체를 필드 단위로: 부분 조회/부분 갱신

key 하나 아래 **field → value 쌍들**을 담는다. 객체를 통째 직렬화하지
않고 필드별로 저장하므로, **한 필드만 읽거나 고칠 수 있다.**

- **자주 부분 갱신되는 객체**: 사용자 프로필, 장바구니(field=상품ID,
  value=수량 — `HINCRBY`로 수량만 원자 증감).
- **여러 카운터를 한 키에**: 상품별 일간 통계(field=날짜)처럼 관련
  카운터를 묶어 키 수를 줄인다.

```text
HSET user:1 name "kim" grade "VIP" point 1200
HGET user:1 grade              # grade만 — 전체 역직렬화 불필요
HINCRBY cart:1 product:99 2    # 장바구니 수량만 원자 증가
```

String-JSON과의 선택 기준은 4절 꼬리질문에서 다룬다 — 이 비교가 실무
판단력을 보여주는 지점이다.

### 2-3. List — 순서 있는 양방향 목록: 큐, 최근 본 상품

양쪽 끝에서 넣고 뺄 수 있는 연결 리스트. **끝 연산(LPUSH/RPUSH/LPOP/
RPOP)은 O(1)**, 중간 접근은 O(N)이다 — 끝에서만 다루는 용도에 쓴다.

- **간단한 작업 큐**: 생산자 `LPUSH`, 소비자 `BRPOP`(비어 있으면 대기하는
  블로킹 팝) — 폴링 없이 큐를 구현한다.
- **최근 본 상품 / 최신 피드**: `LPUSH` + `LTRIM`으로 "최근 N개만 유지"를
  두 명령으로 끝낸다.

```text
LPUSH recent:user:1 "product:99"
LTRIM recent:user:1 0 9          # 항상 최근 10개만 유지 — 무한 성장 방지
```

주의: `LRANGE key 0 -1`처럼 전체 조회는 O(N) — 리스트가 크면 블로킹
폭탄이 된다. 그리고 List 큐는 소비자가 꺼낸 뒤 죽으면 메시지가 사라진다
(ack 없음) — 유실이 허용되지 않으면 List가 아니라 Streams/Kafka 영역이다.

### 2-4. Set — 중복 없는 집합: 중복 방지, 집합 연산

순서 없고 **중복이 없는** 멤버 집합. `SADD`는 "이미 있으면 0, 새로
넣었으면 1"을 반환하므로 **존재 확인과 추가가 원자적으로 한 번에** 된다.

- **중복 방지**: 이벤트 중복 응모 차단, 오늘 출석 체크, "이 공지를 이미
  본 사용자" — `SADD`의 반환값이 곧 "처음인가?"의 답이다.
- **좋아요/팔로워 집합**: `SISMEMBER`로 "내가 눌렀나" O(1) 확인,
  `SCARD`로 개수.
- **집합 연산**: `SINTER`(교집합 — 공통 팔로워, 함께 아는 친구),
  `SDIFF`(차집합 — 아직 안 본 항목).

```java
// before: 응모 여부를 DB에서 SELECT 후 INSERT — 동시 요청이 둘 다 통과
if (!db.existsEntry(userId)) { db.insertEntry(userId); }  // 중복 응모 발생

// after: SADD 반환값 하나로 판정 — 원자적이라 경합 불가
Long added = redis.sadd("event:2026-08:entries", userId);
if (added == 0) throw new AlreadyEnteredException();
```

주의: `SMEMBERS`(전체 조회)와 `SINTER`는 O(N) — 수백만 멤버 Set에서는
서버를 세운다. 큰 집합 순회는 `SSCAN`으로.

### 2-5. Sorted Set — score로 정렬된 집합: 랭킹, 지연 큐

Set에 **score(실수)**가 붙어, 멤버들이 항상 score 순으로 정렬되어 있다.
추가/score 변경/순위 조회가 O(log N) — "정렬 상태의 실시간 유지"가 이
자료구조의 존재 이유다.

- **실시간 랭킹**: 조회/좋아요마다 `ZINCRBY ranking 1 webtoon:55`,
  상위 10개는 `ZREVRANGE ranking 0 9 WITHSCORES`, 내 순위는 `ZREVRANK`.
  RDB로 하면 매번 `ORDER BY` 정렬(또는 집계 배치)이 필요한 것을 항상
  정렬된 상태로 유지한다.
- **지연 큐 / 스케줄링**: score = 실행 예정 시각(epoch)으로 넣고, 워커가
  `ZRANGEBYSCORE queue 0 <now>`로 "지금 실행할 것"만 꺼낸다.
- **슬라이딩 윈도우 rate limiter**: score = 요청 시각, 오래된 것은
  `ZREMRANGEBYSCORE`로 제거하고 `ZCARD`로 최근 N초 요청 수를 센다.

```text
ZINCRBY ranking:daily 1 "webtoon:55"       # 조회 1건 → score +1
ZREVRANGE ranking:daily 0 9 WITHSCORES     # 실시간 TOP 10
ZREVRANK ranking:daily "webtoon:55"        # 내 순위 (0부터)
```

(가산점 포인트) 내부는 **스킵 리스트 + 해시테이블** 이중 구조다.
해시테이블이 "멤버 → score" O(1) 조회를, 스킵 리스트가 정렬 순회와
범위 검색 O(log N)을 맡는다. score가 같은 멤버끼리는 멤버 문자열의
사전순으로 정렬된다 — 동점 처리 순서가 필요하면 score 설계에 시각 등을
섞어야 한다.

## 3. 한눈 비교와 선택 기준

| 자료구조 | 핵심 성질 | 대표 사용 사례 |
|---|---|---|
| String | 단일 값, 원자 증감 | 캐시, 카운터, 분산 락 |
| Hash | field 단위 접근 | 프로필, 장바구니, 부분 갱신 객체 |
| List | 양끝 O(1), 순서 유지 | 큐, 최근 본 목록 |
| Set | 중복 없음, 집합 연산 | 중복 방지, 좋아요, 교집합 |
| Sorted Set | score 정렬 유지 | 랭킹, 지연 큐, rate limiter |

고르는 사고 순서: **"이 데이터에 필요한 연산이 무엇인가"**부터.
정렬된 조회가 필요하면 Sorted Set, 중복 없는 존재 확인이면 Set, 순서
있는 push/pop이면 List, 필드 단위 갱신이면 Hash, 그 외 통값이면 String.
자료구조가 연산을 대신해 주지 못하면 결국 애플리케이션에서
조회-수정-저장을 하게 되고, 그 순간 원자성과 성능을 둘 다 잃는다.

(가산점 포인트) 모든 컬렉션형은 멤버가 적을 때 listpack(과거 ziplist)
이라는 압축 인코딩으로 메모리를 아끼다가, 커지면 해시테이블/스킵
리스트로 전환된다 — 작은 Hash 여러 개가 큰 Hash 하나보다 메모리 효율이
좋을 수 있는 이유다.

## 4. 꼬리질문 대비 포인트

### "객체 캐시는 String에 JSON으로 넣나요, Hash로 쪼개 넣나요?"

기준은 **접근 패턴**이다. 항상 통째로 읽고 통째로 갱신하는 조회 캐시라면
String-JSON이 단순하고, 직렬화 한 번이면 끝이라 오히려 빠르다. 특정
필드만 자주 읽거나 갱신한다면(장바구니 수량, 포인트) Hash가 맞다 —
부분 갱신이 원자적이고, 전체 역직렬화 비용이 없다. 결정적 차이 하나:
**TTL은 key 단위로만 걸린다**(field별 만료는 전통적으로 불가). "필드마다
수명이 달라야 한다"면 Hash 하나가 아니라 key를 쪼개는 설계가 필요하다.

### "Sorted Set은 어떻게 O(log N)으로 정렬을 유지하나요?"

스킵 리스트(skip list) 덕분이다. 정렬된 연결 리스트에 "고속도로 층"을
확률적으로 여러 겹 얹어, 탐색 시 위층에서 크게 건너뛰다가 아래층으로
내려오는 구조 — 균형 트리와 같은 O(log N)을 더 단순한 구현으로 얻는다.
여기에 해시테이블을 병행해 "멤버로 score 찾기"는 O(1)로 처리한다.
두 자료구조가 같은 멤버를 가리키는 이중 인덱스 구조라고 답하면 된다.

### "List를 메시지 큐로 쓰면 어떤 한계가 있나요?"

① **ack가 없다** — `BRPOP`으로 꺼낸 순간 큐에서 사라지므로, 소비자가
처리 중 죽으면 메시지가 유실된다. ② **소비자 그룹이 없다** — 여러
소비자에게 분배·재전송·소비 위치 관리가 안 된다. ③ 재소비(replay)가
불가능하다. 그래서 "유실돼도 되는 가벼운 작업"까지가 List 큐의 영역이고,
유실 불가·다중 소비자·재처리가 요구되면 Redis Streams나 Kafka로 넘어가야
한다. 요구사항의 축이 "유실 허용 여부"임을 짚으면 좋다.

### "랭킹 Sorted Set의 멤버가 수억 개가 되면 어떤 문제가 있나요?" (시니어 변별 포인트)

big key 문제다. ① 그 키 하나가 수 GB 메모리를 점유하고, 키 단위로
분산되는 Cluster에서도 **한 노드에 통째로** 얹힌다(샤딩 불가). ②
`ZRANGE` 범위가 크거나 집계형 연산이면 O(N)에 가까워져 싱글 스레드를
세운다. ③ 삭제·마이그레이션·복제 전부가 블로킹 폭탄이 된다(`DEL` 대신
`UNLINK`가 필요해지는 지점). 대응은 만들어진 뒤가 아니라 **키 설계
단계**에서: 기간별 분할(`ranking:2026-08-31`처럼 일/주 단위 키 + 만료),
상위 N만 유지(주기적 `ZREMRANGEBYRANK`), 전체 정밀 순위가 정말 필요한지
요구사항을 되묻는 것까지가 답이다.

### "String의 INCR로 만든 조회수 카운터, 어떤 점을 주의해야 하나요?"

① Redis 유실 가능성 — 카운터가 비즈니스 정산에 쓰인다면 Redis를 원본으로
삼으면 안 되고, 주기적으로 DB에 반영(write-behind)하는 구조가 필요하다.
② TTL 없는 카운터 키가 무한히 쌓이는 문제 — 대상(상품 등)이 많으면 키
수명 정책을 함께 설계해야 한다. ③ 값은 문자열로 저장되지만 INCR은 정수
해석이 가능할 때만 동작한다 — 같은 키를 SET으로 JSON 덮어쓰는 코드가
섞이면 런타임 에러가 난다(키 네이밍/소유권 규율 문제).

## 한 줄 요약

Redis 자료구조를 안다는 건 명령어 목록 암기가 아니라 "조회-수정-저장
3단계 + 락"으로 풀던 문제를 "원자적 명령 한 방"으로 옮길 줄 아는 것 —
String·Hash·List·Set·Sorted Set 각각이 어떤 연산을 서버에서 대신해
주는지가 곧 설계 선택지의 폭이다.
