# 세션 저장소로서의 Redis — stateless 확장의 대가로 "Redis 장애 = 전 사용자 로그아웃"을 산다

> 핵심 관전 포인트: **세션을 서버 메모리에서 Redis로 빼는 순간 서버는 자기만 아는 데이터를 갖지 않게 되고(stateless), 그래야 아무 서버나 요청을 받아도 되므로 수평 확장·무중단 배포·서버 교체가 전부 열린다. Redis는 인메모리 속도, 키마다 걸리는 TTL, 필드 단위로 읽고 쓰는 Hash 자료구조 덕에 세션에 특히 잘 맞는다. 대신 두 가지를 지불한다. 첫째, 인증이 필요한 모든 요청에 세션 조회와 저장이라는 네트워크 왕복이 붙는다. 둘째, Redis가 새로운 단일 장애점(SPOF, 그것 하나가 죽으면 전체가 멈추는 지점)이 된다. 그리고 이 두 번째가 진짜 관전 포인트다 — 서버 메모리 세션에서는 서버 한 대가 죽으면 그 서버 사용자만 로그아웃됐지만, Redis 세션에서는 Redis 한 대가 죽으면 전 사용자가 동시에 로그아웃된다. 장애의 영향이 미치는 범위(폭발 반경)가 "일부"에서 "전체"로 커진 것이다. 그러므로 장점만 나열하지 말고 replica + 자동 페일오버, 영속화 여부의 의식적 선택, 캐시 Redis와의 인스턴스 분리까지 세트로 말해야 완결된 답이 된다.**

---

## 0. 질문 + 의도

**질문**: "세션 저장소로 Redis를 쓸 때의 장단점은?"

**출제 의도**: stateless 확장의 전제 조건을 이해하는지 보는 질문이다. 세션 외부화의 이득(스케일 아웃, 무중단 배포)만 나열하는 답변과, "Redis 장애 = 전 사용자 로그아웃"이라는 폭발 반경을 인식하고 가용성 대책과 함께 말하는 답변의 차이를 가른다.

## 1. 왜 세션을 서버 밖으로 빼는가 — sticky session의 한계부터

### 1-1. 전제 — HttpSession은 어디에 사는가

로그인을 구현하면 보통 `session.setAttribute("memberId", ...)` 를 쓴다. 이때 그 값이 실제로 어디에 저장되는지 짚고 가자.

서블릿 컨테이너(톰캣)는 세션을 **그 JVM 프로세스의 힙 메모리**에 들고 있다. 브라우저에는 `JSESSIONID`라는 세션 식별자만 쿠키로 내려가고, 실제 데이터는 서버 안 `Map<세션ID, 세션객체>` 에 남는다. 즉 **세션은 그 서버 프로세스의 소유물**이다.

서버가 1대일 때는 아무 문제가 없다. 2대가 되는 순간 문제가 시작된다.

```text
[서버 2대, 로드밸런서가 요청을 번갈아 보내는 상황]

요청 1  로그인      -> A 서버   A의 힙에 {세션ID: memberId=42} 저장
요청 2  마이페이지  -> B 서버   B의 힙에는 그 세션ID가 없다
                              -> "로그인이 필요합니다"
```

로그인은 A에서 했는데 다음 요청이 B로 가면 B는 그 사용자의 세션을 모른다. 사용자 입장에서는 로그인이 제멋대로 풀리는 것으로 보인다.

### 1-2. sticky session은 왜 미봉책인가

가장 먼저 떠오르는 해법이 **sticky session**이다. 로드밸런서가 "이 사용자는 A 서버"라고 기억해 두고 같은 사용자의 요청을 항상 같은 서버로 보내는 방식이다. 세션이 A에만 있으니 항상 A로 보내면 되지 않느냐는 발상이다.

동작은 한다. 하지만 문제를 해결한 것이 아니라 **미뤄둔 것**이다. 어떻게 깨지는지 구체적으로 보자.

**서버 한 대가 죽으면 그 서버에 붙어 있던 사용자 전원이 로그아웃된다.** A 서버가 OOM으로 죽었다고 하자. A의 힙에 있던 세션이 통째로 증발한다. 로드밸런서는 그 사용자들을 B로 보내지만 B에는 세션이 없다. 서버 4대에 사용자가 고르게 붙어 있었다면 **한 대의 장애로 전체 사용자의 4분의 1이 동시에 로그아웃**된다. 결제 도중이었다면 그 흐름도 함께 날아간다.

**배포할 때마다 같은 일이 일어난다.** 이게 더 아프다. 장애는 어쩌다 한 번이지만 배포는 매주, 매일 한다. 롤링 배포로 A를 내리는 순간 A에 붙어 있던 사용자들의 세션이 사라진다. 즉 **sticky session을 쓰는 한 무중단 배포가 성립하지 않는다.** "배포는 새벽에" 라는 관행이 여기서 나온다.

**부하가 기울어도 로드밸런서가 재분배할 수 없다.** 로드밸런서의 본래 일은 지금 한가한 서버로 요청을 보내는 것이다. 그런데 sticky session은 "이 사용자는 무조건 A"라는 제약을 걸어 그 판단을 무력화한다. 무거운 작업을 하는 사용자들이 우연히 A에 몰리면 A만 CPU 90%로 허덕이고 B는 30%로 놀아도, 로드밸런서는 A로 계속 보낼 수밖에 없다.

**오토스케일링과 상극이다.** 트래픽이 늘어 서버를 2대 더 띄웠다고 하자. 새로 뜬 서버에는 붙어 있는 사용자가 없다. 기존 사용자들은 계속 원래 서버로 가므로 **새 서버는 새로 로그인하는 사용자만 조금씩 받으며 한동안 논다.** 반대로 트래픽이 줄어 서버를 줄이려 하면, 줄이는 순간 그 서버 사용자들이 로그아웃되므로 마음대로 줄일 수도 없다. 탄력적으로 늘렸다 줄이는 것 자체가 불가능해진다.

이 네 가지의 뿌리는 하나다. **세션이 특정 서버의 소유물인 한, 그 서버는 마음대로 죽일 수 없는 존재가 된다.**

### 1-3. 세션을 밖으로 빼면 서버가 "언제든 죽여도 되는 것"이 된다

그래서 세션을 **서버 밖의 공용 저장소**로 뺀다. 그 저장소로 가장 널리 쓰이는 것이 Redis다.

세션이 밖에 있으면 어떤 서버가 요청을 받아도 같은 세션을 본다. 그러면 서버는 **자기만 아는 데이터를 갖지 않는 존재**가 되고, 이것을 **stateless(무상태)** 라고 부른다. 상태가 없다는 것은 서버 하나하나가 대체 가능한 부품이 된다는 뜻이고, 그 위에 수평 확장·무중단 배포·오토스케일링이 전부 올라간다.

앞의 네 가지 문제가 어떻게 사라지는지 대응시켜 보면 명확하다.

| sticky session의 문제 | 세션 외부화 후 |
|---|---|
| 서버 장애 = 그 서버 사용자 로그아웃 | 세션이 밖에 있으므로 다른 서버가 이어받는다 |
| 배포마다 세션 소실 | 서버를 내렸다 올려도 세션은 그대로 |
| 부하 재분배 불가 | 로드밸런서가 자유롭게 분배 |
| 오토스케일링 불가 | 서버를 늘리고 줄이는 데 제약 없음 |

```java
// Before: 서버 메모리 세션 — 서버 2대부터 로그인이 풀린다
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    // 이 서버의 JVM 힙에만 저장된다. 다음 요청이 다른 서버로 가면 없다.
    session.setAttribute("memberId", authenticate(req));
}

// After: Spring Session + Redis
// build.gradle: implementation 'org.springframework.session:spring-session-data-redis'
// application.yml: spring.session.store-type: redis
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    // 코드는 한 글자도 바뀌지 않았다. 저장처만 Redis로 바뀐다.
    session.setAttribute("memberId", authenticate(req));
}
```

### 1-4. Spring Session은 어떻게 HttpSession을 가로채는가

"코드를 안 바꿔도 된다"는 말이 마법처럼 들리므로 구조를 알고 넘어가는 편이 좋다. 이걸 알면 나중에 세션 관련 문제를 디버깅할 때 어디를 봐야 하는지도 알게 된다.

Spring Session은 **서블릿 필터**를 하나 끼워 넣는다. 필터는 컨트롤러보다 앞에서 요청을 받아 가공한 뒤 뒤로 넘길 수 있는 자리다. 이 필터(`SessionRepositoryFilter`)가 하는 일은 딱 하나다 — **들어온 `HttpServletRequest`를 자기 래퍼 객체로 감싸서 뒤로 넘긴다.**

이 래퍼는 `HttpServletRequest`의 모든 메서드를 그대로 위임하되 **`getSession()`만 다르게 구현**한다. 톰캣의 세션 맵을 뒤지는 대신, 쿠키에서 세션 ID를 읽어 **Redis에서 세션을 꺼내 오는** 것이다.

```text
[요청 처리 흐름]

브라우저 --쿠키(SESSION=abc123)--> 톰캣
                                    |
                          SessionRepositoryFilter
                                    |
                          request 를 래퍼로 감싼다
                          (getSession() 만 재정의)
                                    |
                                    v
                              컨트롤러
                          session.setAttribute(...)
                                    |
                          호출이 래퍼로 간다 -> Redis
                                    |
                          필터로 되돌아오는 길에
                          변경된 세션을 Redis에 저장
```

컨트롤러 입장에서는 자기가 받은 것이 `HttpServletRequest`이고 `HttpSession`이다. 인터페이스가 같으니 코드를 바꿀 이유가 없다. **구현체만 바뀌었을 뿐이라 호출하는 쪽은 알 필요가 없다** — 이것이 인터페이스에 의존한 설계의 이득이고, Spring Session이 기존 코드를 건드리지 않고 세션 외부화를 해내는 원리다.

한 가지 부수 효과도 알아둘 만하다. 필터가 요청 처리가 끝나는 길목에서 세션을 Redis에 저장하므로, **세션 쓰기는 요청 처리가 끝날 때 한 번에 일어난다.** 3-1에서 왕복 횟수를 셀 때 이 사실이 쓰인다.

## 2. Redis가 세션 저장소로 적합한 이유 (장점)

세션을 밖으로 빼는 것까지는 정해졌다. 그러면 왜 하필 Redis인가. RDB에 세션 테이블을 만들어도 되지 않는가. 네 가지 이유가 있다.

**① 인메모리 속도.** 세션은 **모든 인증된 요청마다** 읽힌다 — 시스템에서 가장 자주 조회되는 데이터 중 하나다. 디스크 기반 DB에 세션을 두면 모든 요청이 디스크 I/O를 지불하지만, Redis는 메모리 접근이라 이 비용이 밀리초 미만으로 떨어진다. "가장 자주 읽히는 작은 데이터"라는 세션의 성격이 인메모리 저장소의 강점과 정확히 겹친다.

**② TTL이 저장소 기능으로 내장돼 있다.** 세션은 본질적으로 "일정 시간 뒤 만료되는 데이터"다. RDB에 세션을 두면 만료 시각 컬럼을 두고 지난 행을 지우는 배치를 따로 돌려야 한다 — 배치를 만들고, 돌리고, 안 도는지 감시해야 한다. Redis는 키마다 TTL을 걸면 알아서 사라진다. **세션의 생명주기와 저장소의 만료 기능이 정확히 맞아떨어지므로 만료 처리 코드가 아예 없어진다.**

**③ Hash 자료구조와의 궁합.** 세션은 "세션ID → {memberId, role, lastAccess, ...}" 형태의 필드 묶음이다. 이걸 문자열 하나로 통째 저장하면 필드 하나를 고치려 해도 전체를 읽고 전체를 쓰는 수밖에 없다. Redis Hash를 쓰면 **필드 단위로 부분 조회·부분 갱신**이 된다. Spring Session의 Redis 구현도 세션을 Hash로 저장한다.

**④ 세션 무효화가 전 서버에 즉시 반영된다.** 관리자가 특정 사용자를 강제 로그아웃시키는 기능(계정 탈취 대응), 비밀번호를 바꿨을 때 다른 기기의 세션을 끊는 기능을 생각해 보자. 세션이 한곳에 모여 있으면 **그 키를 지우는 것으로 끝난다.** 서버별 메모리에 흩어져 있으면 모든 서버에 "이 세션 지워"라고 방송해야 하고, 그 방송을 못 받은 서버가 하나라도 있으면 그쪽에서는 여전히 로그인 상태다. 이 능력은 4절에서 JWT와 비교할 때 결정적인 차이로 다시 등장한다.

## 3. 대가로 지불하는 것들 (단점) — 폭발 반경까지 말해야 한다

### 3-1. 인증이 필요한 모든 요청에 네트워크 왕복이 붙는다

서버 메모리 세션은 조회 비용이 사실상 0이다. 같은 프로세스 힙에서 참조 하나 따라가면 끝이다. Redis 세션은 그 자리에 **네트워크 왕복**이 들어간다.

요청 하나에 왕복이 몇 번 생기는지 세어 보자.

```text
[인증이 필요한 API 요청 1건]

① 필터가 쿠키의 세션 ID로 Redis에서 세션을 읽는다        -> 왕복 1회
② 컨트롤러가 처리한다 (여기서는 Redis 접근 없음)
③ 요청이 끝나는 길에 세션을 Redis에 저장한다             -> 왕복 1회
   (속성이 바뀌지 않아도 마지막 접근 시각 갱신과
    TTL 연장을 위해 쓰기가 일어난다)

  요청당 최소 2회
```

여기서 놓치기 쉬운 것이 ③이다. "세션을 수정하지 않았으니 쓰기는 없겠지"라고 생각하기 쉽지만, **세션은 마지막 접근 시각을 갱신하고 만료 시각을 뒤로 미뤄야** 한다. 사용자가 활동 중인데 30분 뒤 로그아웃되면 안 되기 때문이다. 그래서 읽기만 하는 API에서도 쓰기가 따라붙는다.

이 비용이 왜 무거운지는 **어디에 붙는지**를 보면 안다. 특정 API 하나가 아니라 **인증이 필요한 모든 API**에 붙는다. 로그인 없이 볼 수 있는 페이지를 빼면 서비스의 거의 전부다.

같은 AZ 안이라도 네트워크 왕복은 수백 마이크로초에서 밀리초 수준이다. 왕복 2회면 요청당 대략 1밀리초 안팎이 얹힌다. 초당 1,000건의 인증 요청을 받는 서비스라면 Redis에는 초당 2,000개의 명령이 세션 처리만으로 들어간다. 단일 요청의 1밀리초는 무시할 만해 보여도, 그것이 전 API에 곱해지면 Redis 인스턴스의 처리량 계산에 반드시 들어가야 하는 숫자가 된다.

여기에 **직렬화·역직렬화 비용**도 붙는다. 세션 객체를 Redis에 넣으려면 바이트 배열이나 JSON 문자열로 바꿔야 하고, 꺼낼 때는 되돌려야 한다. 세션에 큰 객체를 담아두는 습관이 있다면 이 비용이 **요청마다** 반복된다. 3-3의 문제로 이어지는 지점이다.

### 3-2. Redis가 새로운 단일 장애점(SPOF)이 된다 — 이 질문의 핵심

먼저 용어를 정확히 하고 가자.

**SPOF(single point of failure, 단일 장애점)** 는 **그것 하나가 죽으면 시스템 전체가 멈추는 지점**을 말한다. 아무리 서버를 여러 대로 늘려도 그 앞에 이중화되지 않은 로드밸런서가 하나 있으면 그 로드밸런서가 SPOF다.

그리고 **폭발 반경(blast radius)** 은 **하나가 죽었을 때 그 영향이 미치는 범위**를 말한다. 폭탄이 터졌을 때 피해가 미치는 반경에서 온 말이다. 장애를 논할 때 "죽느냐 안 죽느냐"보다 중요한 것이 "죽으면 누가, 얼마나 피해를 보느냐"인데, 그 크기를 재는 개념이다.

이 두 개념으로 세션 외부화의 아이러니를 표현할 수 있다. **서버의 장애 내성을 높이려고 세션을 밖으로 뺐는데, 그 결과 세션 저장소가 SPOF가 되면서 폭발 반경이 최대로 커졌다.**

```text
[서버 메모리 세션 + 서버 4대 중 1대 장애]
   영향: 그 서버에 붙어 있던 사용자 = 전체의 약 25%
   폭발 반경: 일부

[Redis 세션 + Redis 장애]
   영향: 모든 서버가 세션을 못 읽는다 = 전체 사용자 100%
   폭발 반경: 전체
   2차 피해: 전원이 동시에 재로그인을 시도
             -> 로그인 API와 인증 DB에 평소의 수십 배 부하
```

"Redis 한 대가 죽으면 전 사용자가 동시에 로그아웃된다"는 문장이 바로 **폭발 반경이 최대**라는 뜻이다. 게다가 그 뒤에 재로그인 폭주라는 2차 부하가 따라온다 — 장애가 복구된 직후에 평소의 수십 배 로그인 트래픽이 인증 서버와 DB를 때린다.

그래서 **세션 저장소로 쓰는 Redis는 캐시로 쓰는 Redis보다 훨씬 높은 가용성 기준으로 운영해야 한다.** 캐시 Redis가 죽으면 DB로 요청이 몰려 느려지지만 서비스는 돈다. 세션 Redis가 죽으면 서비스가 선다. 같은 Redis라도 폭발 반경이 다르므로 운영 기준도 달라야 한다는 것이 이 절의 결론이다.

구체적인 대책은 넷이다.

**Replica + 자동 페일오버(Sentinel 또는 Cluster).** 마스터가 죽었을 때 복제본이 자동으로 승격되어 수 초에서 수십 초 내에 복구되는 구조다. Sentinel은 마스터를 감시하다가 장애를 판정하면 replica를 승격시키는 별도 프로세스이고, Cluster는 샤딩과 페일오버를 함께 제공한다. "장애 시 어떻게 되나"에 대한 1차 답이 여기다.

**영속화 판단.** 캐시용 Redis는 데이터가 날아가도 DB에서 다시 채우면 되지만, 세션은 **유실 = 전원 로그아웃**이다. 재시작 시 세션을 살리고 싶다면 AOF(모든 쓰기 명령을 파일에 남겨 재시작 시 되짚어 복원하는 방식)를 켜는 것을 검토한다. 다만 "세션은 어차피 만료되는 데이터니 유실을 감수하고 성능을 택한다"도 유효한 판단이다. **어느 쪽이든 의식적으로 선택했는지**가 중요하다 — 켜지도 끄지도 않고 기본값으로 흘러온 상태가 가장 나쁘다.

**용도 분리.** 세션 Redis와 캐시 Redis를 같은 인스턴스에 두면, 캐시 쪽의 big key나 메모리 폭주가 세션까지 죽인다. 캐시는 유실돼도 되는 데이터이고 세션은 유실되면 전원 로그아웃인데, 같은 인스턴스에 두는 순간 둘의 폭발 반경이 같아진다. **폭발 반경이 다른 데이터는 인스턴스를 분리하는 것이 정석이다.** (가산점 포인트)

**eviction 정책 주의.** Redis는 `maxmemory`에 도달하면 설정된 eviction 정책에 따라 기존 키를 밀어내고 새 키를 받는다. 캐시용으로 흔히 쓰는 `allkeys-lru`는 **TTL이 남아 있든 말든** 오래 안 쓰인 키부터 지운다. 세션 저장소에 이 정책을 쓰면 **아직 만료되지 않은 세션이 밀려나면서 사용자가 영문 모를 로그아웃**을 겪는다. 게다가 이 사고는 조용히 일어난다 — 에러 로그도 안 남고, "가끔 로그아웃된다"는 산발적 민원으로만 나타나서 원인을 찾기 어렵다. 세션 저장소라면 메모리를 여유 있게 잡고 eviction으로 세션이 지워지는 일이 없는지 모니터링해야 한다. (가산점 포인트)

### 3-3. 세션 데이터 비대화의 유혹

세 번째 대가는 기술이 아니라 규율의 문제다.

세션이 "어디서든 접근되는 편한 저장소"가 되는 순간 사람들이 여기에 이것저것 담기 시작한다. 사용자 프로필 전체, 장바구니 목록, 최근 본 상품, 화면 상태. 컨트롤러 어디서나 `session.getAttribute()` 한 줄로 꺼낼 수 있으니 유혹이 크다.

세션이 커지면 두 가지가 함께 나빠진다. 첫째, 3-1에서 본 직렬화·네트워크 비용이 **요청마다** 커진다. 세션이 200바이트일 때와 50KB일 때는 전 API의 응답 시간이 다르다. 둘째, Redis 메모리가 **동시 접속자 수 × 세션 크기**로 부푼다. 동시 접속 10만 명에 세션 50KB면 5GB다.

그래서 규율이 필요하다. **세션에는 식별자와 최소한의 인증 컨텍스트(memberId, 권한 정도)만 담고, 나머지는 필요할 때 캐시나 DB에서 읽는다.** 세션은 "이 요청이 누구인지"를 알려 주는 자리이지 사용자 데이터의 보관함이 아니다.

## 4. 꼬리질문 대비 포인트

### "Redis가 죽으면 서비스는 어떻게 되나요? 대책은?"

먼저 무슨 일이 벌어지는지부터 정확히 말한다. 모든 인증 요청이 세션 조회에서 실패한다 — 사실상 전 사용자 로그아웃이다. 그리고 복구된 뒤에는 재로그인 폭주가 2차 부하로 온다.

대책은 계층별로 셋이다.

**① 인프라 계층** — replica + Sentinel/Cluster로 자동 페일오버를 걸어 수 초에서 수십 초 내에 복구되게 한다.

**② 애플리케이션 계층** — 세션 조회가 실패했을 때의 동작을 미리 정의해 둔다. 무조건 401로 떨어뜨릴 것인지, 아니면 짧은 타임아웃과 서킷 브레이커를 둘 것인지다. 여기서 서킷 브레이커가 왜 필요한지가 중요하다. **Redis가 응답하지 않을 때 타임아웃을 길게 잡아 두면, 인증 요청을 처리하던 톰캣 스레드들이 전부 Redis 응답을 기다리며 묶인다.** 스레드 풀이 고갈되면 Redis와 무관한 API까지 요청을 못 받게 된다 — 세션 저장소 장애가 애플리케이션 전체 마비로 번지는 연쇄 장애다. 빠르게 실패시키는 것이 오히려 피해를 줄인다.

**③ 용량 계층** — 재로그인 폭주에 로그인 경로가 버티는지 점검한다. 평소 트래픽 기준으로 잡은 로그인 API 용량은 전원 동시 재로그인을 감당하지 못한다.

**"Redis는 안 죽는다"가 아니라 "죽었을 때의 시나리오가 준비돼 있다"가 정답의 골격이다.**

### "그럴 바에 세션 대신 JWT를 쓰면 되지 않나요?" (시니어 변별 포인트)

먼저 JWT가 왜 다른지부터 짚는다. **JWT는 상태를 토큰 자체에 담는다.** 사용자 ID와 권한, 만료 시각을 토큰 안에 넣고 서버 서명을 붙여서 클라이언트에게 준다. 서버는 요청이 올 때마다 서명만 검증하면 되므로 **저장소를 조회하지 않는다.** 3-1의 네트워크 왕복도, 3-2의 SPOF도 구조적으로 사라진다.

여기까지만 말하면 JWT가 압도적으로 보이지만, **대가가 정확히 반대편에 있다.**

서버가 세션을 갖고 있지 않다는 말은 **발급한 토큰을 즉시 무효화할 수단이 없다**는 말이기도 하다. 서버는 그 토큰이 존재하는지조차 모른다. 만료 시각이 될 때까지 그 토큰은 유효하다.

그러면 이런 요구를 못 들어준다.

- 계정이 탈취됐을 때 즉시 강제 로그아웃
- 비밀번호 변경 시 다른 기기 세션 끊기
- 권한을 회수했을 때 즉시 반영 (토큰 안의 권한이 그대로 살아 있다)

**그래서 실무의 JWT는 대개 블랙리스트를 둔다.** 무효화된 토큰 목록을 어딘가에 저장해 두고 요청마다 "이 토큰이 블랙리스트에 있나"를 확인하는 것이다. 그 저장소로 흔히 쓰이는 것이 Redis다. 그런데 **그 순간 "저장소 조회가 없다"는 JWT의 장점이 사라진다.** 요청마다 Redis를 보게 되고, Redis가 SPOF가 된다. 세션 방식으로 돌아온 셈이다.

즉 **"세션 vs JWT"는 우열이 아니라 "즉시 무효화 능력 vs 저장소 무의존"의 트레이드오프**다. 양쪽 다 대가가 있고, 요구사항이 어느 쪽을 더 중요하게 보느냐로 결정된다.

- **즉시 차단이 중요한 서비스** — 관리자 콘솔, 금융, 결제. 세션이 맞다. 무효화가 기능 요구사항이므로 저장소 의존은 어차피 피할 수 없다.
- **서버 간 신뢰 전달** — MSA 내부 서비스끼리 "이 요청은 인증된 사용자 42번의 것"임을 전달하는 용도. JWT가 맞다. 수명이 짧고(수 분) 중간에 무효화할 일이 없으므로 JWT의 단점이 드러나지 않는다.

**요구사항 기준으로 갈라 답하는 것이 시니어 답변이다.** "JWT가 최신이니까", "세션은 확장이 안 되니까" 같은 일반론으로 답하면 이 질문의 의도를 놓친 것이다.

### "세션용 Redis에 영속화(RDB/AOF)를 켜야 하나요?"

**용도로 판단한다**고 답하고 양쪽 선택지와 근거를 다 제시한다.

세션을 "유실되면 재로그인으로 복구 가능한 데이터"로 본다면 영속화를 끄거나 RDB 스냅샷 정도만 두는 선택이 합리적이다. 반대로 "전원 로그아웃은 사고"로 본다면 AOF를 `everysec`(1초에 한 번 디스크에 밀어 쓰는 설정)으로 켜서 유실 폭을 초 단위로 줄인다.

핵심은 어느 쪽이 정답이냐가 아니라 트레이드오프를 아느냐다. **AOF는 유실 폭을 줄여 주는 대신 쓰기 비용과 재시작 시 로드 시간을 지불한다.** AOF 파일을 되짚어 메모리를 복원해야 하므로 데이터가 많으면 재시작이 느려지고, 그동안은 세션을 못 읽는다 — 유실을 막으려다 복구 시간이 길어지는 역설도 가능하다.

**"캐시면 끄고, 세션이면 서비스가 전원 로그아웃을 감당할 수 있는지로 결정한다"가 답의 뼈대다.**

### "sticky session으로 버티면 안 되나요?"

**작은 규모에서는 유효한 선택**이라는 것부터 인정하고 시작한다. Redis라는 인프라를 추가하지 않고 로드밸런서 설정만으로 동작하고, 운영해야 할 컴포넌트가 하나 줄어든다. 서버 2대에 배포가 월 1회인 서비스라면 이걸로 충분할 수 있다.

문제는 **언제까지 버틸 수 있느냐**다. 1-2에서 본 네 가지가 성장과 함께 하나씩 터진다. 서버 수가 늘면 장애 시 로그아웃되는 사용자 비율은 줄지만 장애 빈도는 늘고, 배포가 잦아질수록 배포 때마다 세션 소실 민원이 반복된다. 오토스케일링을 도입하려는 순간에는 아예 막힌다.

그래서 답의 결론은 이렇다. **성장 궤도에 있는 서비스라면 이르게 외부화하는 편이 이행 비용이 싸다.** 사용자가 적고 세션 구조가 단순할 때 옮기는 것과, 트래픽이 많고 세션에 온갖 것이 들어간 뒤에 옮기는 것은 난이도가 다르다. "언제까지 버틸 수 있는 선택인지"를 알고 쓰는 것과 모르고 쓰는 것의 차이가 이 질문의 포인트다.

### "세션 객체 구조가 배포로 바뀌면(필드 추가/삭제) 어떻게 되나요?"

**배포가 세션 데이터와의 계약을 바꾸는 사건임을 인식하는지**가 이 질문의 포인트다.

무슨 일이 벌어지는지부터 보자. 배포 시점에 Redis에는 **구버전 코드가 직렬화해 넣은 세션들**이 이미 살아 있다. 신버전 코드가 그것을 역직렬화하려다 실패하면, 배포 직후 기존 로그인 사용자들이 일제히 에러를 만난다.

실패 양상은 직렬화 방식에 따라 다르다.

**JDK 기본 직렬화**는 클래스마다 `serialVersionUID`라는 버전 번호를 가진다. 이 값을 코드에 명시하지 않으면 컴파일러가 클래스의 필드 구성과 메서드 시그니처 등으로부터 자동 계산하는데, **필드를 하나만 추가해도 이 값이 달라진다.** 그러면 역직렬화 시 "저장된 데이터의 UID"와 "현재 클래스의 UID"가 안 맞아 `InvalidClassException`이 난다. 필드가 추가됐을 뿐 데이터에는 아무 문제가 없는데도 통째로 실패하는 것이다.

**JSON 직렬화**는 훨씬 관대하다. 필드가 추가된 경우 구버전 JSON에는 그 필드가 없으니 기본값(null이나 0)으로 채워지고, 필드가 삭제된 경우에는 JSON에 남아 있는 그 필드를 어떻게 처리할지가 문제가 된다. Jackson은 기본 설정에서 **모르는 필드를 만나면 예외를 던지지만**, 이 동작을 무시하도록 설정할 수 있다. 즉 JSON이 자동으로 안전한 것이 아니라 **"모르는 필드를 무시한다"는 설정을 해 둬야 관대해진다.**

대응은 두 단계다.

1. **JDK 직렬화 대신 JSON 직렬화를 쓰고, 모르는 필드를 무시하도록 설정한다.** 필드 추가·삭제 정도의 변경은 이것으로 흡수된다.
2. **호환 불가능한 변경(필드 타입 변경, 구조 재편)이라면 세션 키 네임스페이스에 버전을 넣어 신구를 공존시킨다.** 신버전은 `v2:session:*`를 쓰고 구버전 키는 건드리지 않은 채 TTL로 자연 소멸시킨다. 롤링 배포 중에도 신구 코드가 각자 자기 버전의 키만 보므로 충돌이 없다.

두 번째 방법이 **캐시 키 버저닝과 완전히 같은 문제이자 같은 해법**이라는 점을 짚으면 좋다. 캐시든 세션이든 "저장소에 남아 있는 데이터의 형식"과 "지금 배포된 코드가 기대하는 형식"이 어긋나는 문제이고, 해법도 똑같이 "키를 바꿔 신구를 분리하고 옛것은 TTL로 버린다"이다. 같은 디렉토리의 `14-cache-key-design-and-versioning.md`가 이 문제를 캐시 쪽에서 자세히 다룬다.

## 한 줄 요약

세션을 Redis로 빼면 서버가 자기만 아는 데이터를 갖지 않게 되어(stateless) 수평 확장과 무중단 배포가 열리고 TTL·Hash·중앙 무효화까지 세션과 궁합이 완벽하지만, 그 대가로 인증이 필요한 모든 요청에 조회 1회 + 저장 1회의 네트워크 왕복이 붙고 "Redis 한 대의 장애 = 전 사용자 동시 로그아웃"이라는 최대 폭발 반경을 지불하므로 — replica + 자동 페일오버, 영속화 여부의 의식적 선택, 캐시와의 인스턴스 분리, eviction으로 세션이 밀려나지 않는지의 감시까지 세트로 설계해야 비로소 "장점을 산 것"이 된다.
