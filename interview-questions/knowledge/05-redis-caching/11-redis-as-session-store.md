# 세션 저장소로서의 Redis — stateless 확장의 대가로 "Redis 장애 = 전 사용자 로그아웃"을 산다

> 핵심 관전 포인트: **세션을 서버 메모리에서 Redis로 빼는 순간 서버는
> stateless가 되어 수평 확장·무중단 배포·서버 교체가 자유로워진다.
> Redis는 인메모리 속도 + TTL 자연 지원 + Hash 자료구조로 세션에 딱 맞는
> 저장소다. 대신 두 가지를 지불한다 — 모든 요청에 네트워크 왕복 한 번이
> 추가되고, Redis가 새로운 단일 장애점(SPOF)이 된다. Redis가 죽으면
> 전 사용자가 동시에 로그아웃되는 폭발 반경이므로, 장점만 말하지 않고
> replica + Sentinel/Cluster 같은 가용성 대책과 영속화 판단(AOF)까지
> 세트로 말해야 완결된 답이다.**

---

## 0. 질문 + 의도

**질문**: "세션 저장소로 Redis를 쓸 때의 장단점은?"

**출제 의도**: stateless 확장의 전제 조건을 이해하는지 보는 질문이다.
세션 외부화의 이득(스케일 아웃, 무중단 배포)만 나열하는 답변과, "Redis
장애 = 전 사용자 로그아웃"이라는 폭발 반경을 인식하고 가용성 대책과
함께 말하는 답변의 차이를 가른다.

## 1. 왜 세션을 서버 밖으로 빼는가 — sticky session의 한계부터

전통적인 `HttpSession`은 **그 서버의 JVM 힙 메모리**에 산다. 서버가
1대일 때는 아무 문제가 없지만, 2대가 되는 순간 문제가 시작된다:
로그인은 A 서버에서 했는데 다음 요청이 B 서버로 가면 B는 그 사용자의
세션을 모른다 — 로그인이 풀린다.

임시방편이 **sticky session**(로드밸런서가 같은 사용자를 항상 같은
서버로 보내는 방식)인데, 이건 문제를 해결한 게 아니라 미뤄둔 것이다:

- **서버 한 대가 죽으면** 그 서버에 붙어 있던 사용자들의 세션이 통째로
  증발한다 — 그 사용자들만 단체 로그아웃.
- **배포/재시작할 때마다** 같은 일이 일어난다 — 무중단 배포가 불가능.
- **부하 분산이 왜곡된다** — 특정 서버에 무거운 사용자가 몰려도
  로드밸런서가 재분배할 수 없다.
- **오토스케일링과 상극** — 서버를 줄이는 순간 세션이 날아가므로
  마음대로 늘렸다 줄일 수 없다.

그래서 세션을 **서버 밖의 공용 저장소**로 빼는 것이 정석이고, 그
저장소로 가장 널리 쓰이는 것이 Redis다. 세션이 밖에 있으면 어떤
서버가 요청을 받아도 같은 세션을 보므로 서버는 **언제든 죽이고 새로
띄워도 되는 존재(stateless)**가 된다 — 수평 확장, 무중단 배포,
오토스케일링이 전부 이 전제 위에 선다.

```java
// Before: 서버 메모리 세션 — 서버 2대부터 로그인이 풀린다
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("memberId", authenticate(req));  // ❌ 이 서버 힙에만 저장
}

// After: Spring Session + Redis — 의존성과 설정만으로 세션이 Redis로
// build.gradle: implementation 'org.springframework.session:spring-session-data-redis'
// application.yml: spring.session.store-type: redis
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("memberId", authenticate(req));  // ✅ 코드는 그대로,
}                                                          //    저장처만 Redis로 바뀜
```

Spring Session을 쓰면 `HttpSession` 인터페이스는 그대로 두고 구현체만
Redis 기반으로 바꿔주므로, 비즈니스 코드 수정 없이 세션 외부화가 된다.

## 2. Redis가 세션 저장소로 적합한 이유 (장점)

**① 인메모리 속도.** 세션은 **모든 인증된 요청마다** 읽힌다 — 시스템에서
가장 자주 조회되는 데이터 중 하나다. 디스크 기반 DB에 세션을 두면 모든
요청이 디스크 I/O를 지불하지만, Redis는 메모리 접근이라 이 비용이
밀리초 미만으로 떨어진다.

**② TTL이 저장소 기능으로 내장.** 세션은 본질적으로 "만료되는
데이터"다. RDB에 세션을 두면 만료 세션을 지우는 배치를 따로 돌려야
하지만, Redis는 키마다 TTL을 걸면 알아서 사라진다 — 세션의 생명주기와
저장소의 만료 기능이 정확히 맞아떨어진다.

**③ Hash 자료구조와의 궁합.** 세션은 "세션ID → {memberId, role,
lastAccess...}" 형태의 필드 묶음이다. Redis Hash를 쓰면 세션 전체를
통째로 읽고 쓰는 대신 **필드 단위로 부분 조회/갱신**이 가능하다
(Spring Session의 Redis 구현도 세션을 Hash로 저장한다).

**④ 세션 무효화가 서버 전체에 즉시 반영.** 관리자가 특정 사용자를
강제 로그아웃시키거나(계정 탈취 대응), 비밀번호 변경 시 다른 기기
세션을 끊는 기능 — 세션이 한곳에 모여 있어야 "그 키를 지우면 끝"이
된다. 서버별 메모리에 흩어져 있으면 이게 안 된다.

## 3. 대가로 지불하는 것들 (단점) — 폭발 반경까지 말해야 한다

### ① 모든 요청에 네트워크 왕복이 추가된다

서버 메모리 세션은 조회 비용이 0에 가깝지만, Redis 세션은 **요청마다
최소 1회의 네트워크 왕복**을 지불한다. Redis 자체는 빨라도 네트워크
지연(같은 AZ 내에서도 수백 마이크로초~밀리초)은 사라지지 않는다. 또한
세션 객체를 넣고 뺄 때마다 **직렬화/역직렬화 비용**이 든다 — 세션에
큰 객체를 담아두는 습관이 있다면 이 비용이 요청마다 반복된다.

### ② Redis가 새로운 단일 장애점(SPOF)이 된다 — 이 질문의 핵심

세션 외부화의 아이러니: 서버의 장애 내성을 높이려고 세션을 뺐는데,
그 결과 **Redis가 죽으면 전 서버가 동시에 인증 불능**이 된다.

- 서버 메모리 세션 + 서버 1대 장애 = **그 서버 사용자만** 로그아웃.
- Redis 세션 + Redis 장애 = **전 사용자** 로그아웃 + 로그인 시도 폭주
  (재로그인 트래픽이 인증 서버와 DB를 2차로 때린다).

폭발 반경이 "일부"에서 "전체"로 커진 것이다. 그래서 세션 저장소
Redis는 캐시용 Redis보다 훨씬 높은 가용성 기준으로 운영해야 한다:

- **Replica + 자동 페일오버(Sentinel 또는 Cluster)** — 마스터가 죽어도
  수 초~수십 초 내에 replica가 승격되어 복구. "장애 시 어떻게
  되나"의 1차 답.
- **영속화 판단** — 캐시용 Redis는 데이터 유실을 허용하지만, 세션은
  유실 = 전원 로그아웃이다. 재시작 시 세션을 살리고 싶다면 AOF를
  켜는 것을 검토한다. 단 "세션은 어차피 만료되는 데이터니 유실을
  감수하고 성능을 택한다"도 유효한 판단 — **어느 쪽이든 의식적으로
  선택했는지**가 중요하다.
- **용도 분리** — 세션 Redis와 캐시 Redis를 같은 인스턴스에 두면,
  캐시 쪽 big key나 메모리 폭주가 세션까지 죽인다. 폭발 반경이 다른
  데이터는 인스턴스를 분리하는 것이 정석. (가산점 포인트)
- **eviction 정책 주의** — maxmemory 도달 시 `allkeys-lru` 같은
  정책이면 **만료 안 된 세션이 밀려나며 사용자가 영문 모를 로그아웃**을
  겪는다. 세션 저장소라면 메모리를 여유 있게 잡고 eviction으로 세션이
  지워지는 일이 없도록 모니터링해야 한다. (가산점 포인트)

### ③ 세션 데이터 비대화의 유혹

"어디서든 접근되는 편한 저장소"가 되는 순간 세션에 이것저것 담기
시작한다. 세션이 커지면 요청마다의 직렬화/네트워크 비용이 커지고,
Redis 메모리도 사용자 수에 비례해 부푼다. 세션에는 **식별자와 최소한의
인증 컨텍스트만** 담고, 나머지는 필요할 때 캐시/DB에서 읽는 규율이
필요하다.

## 4. 꼬리질문 대비 포인트

### "Redis가 죽으면 서비스는 어떻게 되나요? 대책은?"

모든 인증 요청이 세션 조회에서 실패한다 — 사실상 전 사용자 로그아웃이고,
복구 후에는 재로그인 폭주가 2차 부하로 온다. 대책은 계층별로:
① replica + Sentinel/Cluster로 자동 페일오버(수 초~수십 초 내 복구),
② 세션 조회 실패 시의 애플리케이션 동작을 미리 정의 — 무조건 401로
떨어뜨릴지, 짧은 타임아웃 + 서킷 브레이커로 인증 서버 스레드가 Redis
대기에 잠기는 것(연쇄 장애)만은 막을지, ③ 재로그인 폭주에 대비한
로그인 경로의 처리 용량 점검. "Redis는 안 죽는다"가 아니라 "죽었을 때의
시나리오가 준비돼 있다"가 정답의 골격이다.

### "그럴 바에 세션 대신 JWT를 쓰면 되지 않나요?" (시니어 변별 포인트)

JWT는 상태를 토큰 자체에 담아 저장소 조회를 없앤다 — Redis SPOF 문제가
구조적으로 사라진다. 하지만 공짜가 아니다: **서버가 세션을 갖고 있지
않으므로 즉시 무효화가 안 된다.** 강제 로그아웃, 계정 탈취 대응,
권한 변경 즉시 반영이 전부 어려워지고, 이를 해결하려고 블랙리스트를
Redis에 두는 순간 "저장소 조회 없음"이라는 장점이 도로 사라진다.
즉 "세션 vs JWT"는 우열이 아니라 **"즉시 무효화 능력 vs 저장소
무의존"의 트레이드오프**이고, 즉시 차단이 중요한 서비스(관리자 콘솔,
금융)는 세션이, 서버 간 신뢰 전달(MSA 내부 토큰)은 JWT가 어울린다고
요구사항 기준으로 답하는 것이 시니어 답변이다.

### "세션용 Redis에 영속화(RDB/AOF)를 켜야 하나요?"

용도로 판단한다. 세션은 "유실되면 재로그인으로 복구 가능한" 데이터라
유실 허용으로 보고 영속화를 끄는(또는 RDB 스냅샷 정도만 두는) 선택도,
"전원 로그아웃은 사고"로 보고 AOF(everysec)를 켜는 선택도 가능하다.
핵심은 트레이드오프 — AOF는 유실 폭을 초 단위로 줄여주지만 쓰기
비용과 재시작 시 로드 시간을 지불한다. "캐시면 끄고, 세션이면 서비스가
전원 로그아웃을 감당할 수 있는지로 결정한다"가 답의 뼈대다.

### "sticky session으로 버티면 안 되나요?"

작은 규모에서는 유효한 선택이다 — 인프라 추가 없이 동작한다. 하지만
배포/장애 시 해당 서버 사용자의 세션 소실을 감수해야 하고, 오토스케일링·
무중단 배포와 충돌한다. "언제까지 버틸 수 있는 선택인지"를 아는 게
중요하다: 서버 수가 늘고 배포가 잦아지는 순간부터 세션 소실 민원이
반복되므로, 성장 궤도의 서비스라면 이르게 외부화하는 편이 이행 비용이
싸다.

### "세션 객체 구조가 배포로 바뀌면(필드 추가/삭제) 어떻게 되나요?"

Redis에 남아 있는 구버전 직렬화 데이터를 신버전 코드가 역직렬화하다
실패할 수 있다 — 배포 직후 기존 로그인 사용자들이 일제히 에러를 만나는
전형적 사고다. Java 기본 직렬화 대신 JSON 직렬화로 필드 추가에
관대하게 만들고, 호환 불가능한 변경이라면 세션 키 네임스페이스에
버전을 넣어 신구를 공존시키는 방법이 있다(캐시 키 버저닝과 같은
원리 — 14번 문서 참고). "배포가 캐시/세션 데이터와의 계약 변경"임을
인식하는지가 포인트다.

## 한 줄 요약

세션을 Redis로 빼면 서버가 stateless가 되어 수평 확장과 무중단 배포가
열리고 TTL·Hash·중앙 무효화까지 세션과 궁합이 완벽하지만, 그 대가로
요청마다의 네트워크 왕복과 "Redis 장애 = 전 사용자 로그아웃"이라는
전체 폭발 반경을 지불하므로 — replica + 자동 페일오버, 영속화 여부의
의식적 선택, 캐시와의 인스턴스 분리라는 가용성 대책까지 세트로 설계해야
"장점을 산 것"이 된다.
