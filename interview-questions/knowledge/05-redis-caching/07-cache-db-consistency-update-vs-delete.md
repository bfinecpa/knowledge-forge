# 캐시-DB 정합성: 갱신 vs 삭제 — "늦게 도착한 옛 값"이 캐시를 오염시키는 타이밍 문제

> 핵심 관전 포인트: **캐시와 DB는 서로 다른 두 저장소라 하나의 트랜잭션으로
> 함께 바꿀 수 없다 — 정합성은 보장하는 게 아니라 확률적으로 좁히는
> 것이다. 나는 갱신(update)보다 삭제(delete/evict)를 선호한다: 갱신은
> 동시 쓰기 시 캐시 도착 순서가 DB 커밋 순서와 역전되면 옛 값이 캐시의
> 최종값으로 남아 TTL 내내 서빙되지만, 삭제는 최악의 경우가 "미스 한 번
> 더"로 수렴하고 경합 시나리오도 훨씬 좁기 때문이다. 정석 조합은 DB
> 커밋 후 캐시 삭제 + 삭제 실패 대비(재시도/CDC) + TTL을 최후 안전망으로
> 겹치는 것이다.**

---

## 0. 질문 + 의도

**질문**: "캐시와 DB의 정합성을 어떻게 맞추나요? \"캐시 갱신 vs 캐시 삭제\"
중 무엇을 선호하고 왜인가요?"

**출제 의도**: 순서 역전(늦게 도착한 옛 값이 캐시를 덮는)까지 언급하는지로
분산 환경의 타이밍 문제를 사고할 수 있는지 잰다. "삭제가 안전한 이유"를
논증하는 과정이 곧 동시성 사고력 시연이다.

## 1. 왜 정합성이 "문제"인가 — 두 저장소, 하나의 트랜잭션 불가

DB 갱신과 캐시 조작은 서로 다른 시스템에 대한 **별개의 두 호출**이다.
둘을 묶는 트랜잭션은 없으므로 반드시 이런 틈이 생긴다:

- 두 호출 **사이의 시간 창** — 그 사이에 읽기가 끼어들 수 있다.
- **부분 실패** — DB는 커밋됐는데 캐시 호출이 실패할 수 있다(반대도).
- **순서 역전** — 여러 쓰기가 동시에 일어나면 DB에 반영된 순서와
  캐시에 도착한 순서가 다를 수 있다.

그래서 이 질문의 정답 프레임은 "이렇게 하면 완벽히 맞습니다"가 아니라
**"불일치 창을 어디까지 좁히고, 남는 틈은 무엇으로 막느냐"** 다. 이
프레임을 첫 문장으로 깔고 시작하는 것 자체가 관전 포인트에 대한 답이다.

## 2. 갱신(update)의 함정 — 순서 역전이 옛 값을 "최종값"으로 만든다

캐시 갱신은 DB에 쓴 새 값을 캐시에도 SET하는 방식이다. 직관적으로는
"삭제하면 미스가 나니까 갱신이 낫지 않나?" 싶지만, 동시 쓰기에서
치명적인 창이 열린다.

```
같은 상품 가격을 두 요청이 거의 동시에 수정하는 상황:

t=0  요청 A: DB 갱신 price=1000  (커밋)
t=1  요청 B: DB 갱신 price=2000  (커밋)      → DB 최종값: 2000 ✅
t=2  요청 B: 캐시 SET price=2000              (B가 먼저 도착)
t=3  요청 A: 캐시 SET price=1000  ← GC 멈춤, 네트워크 지연 등으로 늦게 도착
                                              → 캐시 최종값: 1000 ❌

DB는 2000인데 캐시는 1000 — 게다가 이 값은 "미스"가 아니라
"히트"로 서빙되므로, TTL이 다할 때까지 아무도 눈치채지 못한다.
```

핵심은 **DB의 커밋 순서(A→B)와 캐시 도착 순서(B→A)를 일치시킬 방법이
없다**는 것이다. 애플리케이션 서버가 여러 대이고, GC·네트워크 지연이
개입하는 분산 환경에서 "내가 나중에 커밋했으니 캐시에도 나중에 도착
하겠지"는 성립하지 않는다.

갱신의 부수적 단점도 있다:

- **안 읽힐 값을 미리 계산해 적재** — 쓰기가 잦고 읽기가 드문 키라면
  매번 갱신하는 비용이 순수 낭비다 (삭제는 다음 읽기가 있을 때만
  적재 비용을 낸다 — lazy).
- 캐시 값이 단순 컬럼 복사가 아니라 **조합/가공 결과**라면, 쓰기
  경로마다 그 가공 로직을 태워야 해서 쓰기 경로가 무거워지고 로직
  중복이 생긴다.

## 3. 삭제(delete)가 더 안전한 이유 — 최악이 "미스 한 번"으로 수렴

삭제는 캐시에 값을 쓰지 않고 지우기만 한다. 같은 동시 쓰기 시나리오를
삭제로 다시 돌려보면:

```
t=0  요청 A: DB 갱신 price=1000 (커밋)
t=1  요청 B: DB 갱신 price=2000 (커밋)      → DB 최종값: 2000
t=2  요청 B: 캐시 DEL
t=3  요청 A: 캐시 DEL  ← 늦게 도착해도 "또 지울" 뿐

→ 캐시는 빈 상태. 다음 읽기가 미스를 내고 DB의 최종값 2000을 적재. ✅
```

삭제는 **멱등**(몇 번 해도, 어떤 순서로 해도 결과가 같음)이라 순서
역전이 무해하다. 잘못된 값이 캐시에 "남는" 시나리오가 갱신보다 훨씬
좁고, 대가는 다음 읽기의 **미스 한 번**뿐이다. "오답을 히트로 서빙하는
위험"과 "미스 한 번의 비용"의 교환 — 이것이 삭제를 선호하는 논증의
뼈대다.

### 삭제도 완벽하지는 않다 — 읽기와의 경합

시니어 변별은 여기서 갈린다. 삭제 전략에도 남는 창이 있다:

```
t=0  읽기 A: 캐시 미스 → DB에서 price=1000 읽음 (아직 캐시 적재 전)
t=1  쓰기 B: DB 갱신 price=2000 (커밋) → 캐시 DEL (지울 것 없음)
t=2  읽기 A: 아까 읽은 1000을 캐시에 SET  ← 옛 값 적재
     → TTL까지 캐시는 1000 서빙 ❌
```

다만 이 시나리오는 ① 마침 캐시가 비어 있고(미스) ② 읽기의 "DB 조회
→ 캐시 적재" 사이라는 짧은 틈에 ③ 쓰기의 "DB 커밋 → 캐시 삭제"가
통째로 끼어들어야 성립한다. 보통 읽기는 쓰기(트랜잭션 커밋)보다
빠르므로 실제 발생 확률이 낮다 — "낮지만 0이 아니므로 TTL을 안전망
으로 둔다"까지 말해야 논증이 완성된다.

## 4. 실무 정석 조합 — 순서, 실패 대비, 안전망

### ① 순서: DB 커밋 "후"에 캐시 삭제

캐시를 먼저 지우면, 커밋 전에 끼어든 읽기가 DB의 **옛 값**(아직 커밋
전이므로)을 읽어 캐시를 도로 채운다 — 지운 보람이 없다. 그래서
"DB 쓰기(커밋) → 캐시 삭제" 순서가 기본이다.

스프링에서 흔한 함정: `@Transactional` 메서드 안에서 캐시를 지우면
**커밋 전에** 삭제가 실행된다. 삭제 직후~커밋 사이에 들어온 읽기가
옛 값을 재적재하고, 롤백되면 캐시만 지운 꼴이 된다.

```java
// ❌ 커밋 전에 삭제 — 삭제~커밋 사이의 읽기가 옛 값을 재적재
@Transactional
public void updatePrice(Long id, long newPrice) {
    productRepository.updatePrice(id, newPrice);
    redisTemplate.delete("product:" + id);   // 아직 커밋 안 됨!
}

// ✅ 커밋 이후로 삭제를 미룬다 — 이벤트 + AFTER_COMMIT
@Transactional
public void updatePrice(Long id, long newPrice) {
    productRepository.updatePrice(id, newPrice);
    eventPublisher.publishEvent(new PriceChangedEvent(id));
}

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onPriceChanged(PriceChangedEvent event) {
    redisTemplate.delete("product:" + event.productId());  // 커밋 확정 후 삭제
}
```

### ② 삭제 실패 대비 — 캐시 호출은 실패할 수 있다

DB 커밋은 됐는데 캐시 삭제가 실패하면(Redis 순단, 네트워크) 옛 값이
TTL까지 남는다. 요구 수준에 따라:

- 짧은 **재시도** (즉시 1~2회).
- 실패 시 **메시지 큐에 적재해 비동기 재시도** — 삭제를 "언젠가 반드시
  실행되는 작업"으로 만든다.
- (가산점 포인트) **CDC(Change Data Capture, 예: Debezium)** — DB의
  변경 로그(binlog) 자체를 구독해 캐시를 무효화하면, 애플리케이션
  코드가 어떤 경로로 바꿨든(배치, 수동 쿼리 포함) 무효화가 따라간다.
  "무효화를 사람이 기억해서 넣는 규칙"에서 "구조가 보장하는 규칙"으로
  바꾸는 접근.

### ③ TTL — 모든 전략의 최후 안전망

위의 어떤 조합도 불일치 확률을 0으로 만들지 못한다(경합 창, 유실).
그래서 **모든 캐시 키에 TTL을 준다** — 어떤 경로로 옛 값이 남았든
TTL이 불일치의 **최대 지속 시간 상한**이 된다. "우리 시스템의 캐시
불일치는 최악의 경우에도 N분을 넘지 않는다"고 말할 수 있게 하는
장치이며, 그 N을 정하는 것이 비즈니스와의 합의(허용 staleness)다.

## 5. 꼬리질문 대비 포인트

### "삭제도 옛 값이 적재되는 시나리오가 있는데, 왜 갱신보다 안전하다고 하나요?"

발생 **조건의 폭**이 다르다. 갱신의 순서 역전은 같은 키에 동시 쓰기
둘만 있으면 성립하고, 쓰기가 몰리는 인기 데이터일수록 오히려 잘
터진다. 삭제 쪽 경합은 "캐시가 비어 있는 순간 + 읽기의 조회~적재
틈에 쓰기의 커밋~삭제가 통째로 끼어드는" 좁은 인터리빙이 필요하고,
읽기가 쓰기보다 보통 빠르므로 확률이 낮다. 또 삭제는 멱등이라 실행
순서가 뒤집혀도 결과가 같다. "위험이 0 vs 0이 아니라, 창의 넓이와
발생 조건이 다르다"는 비교가 정답 골격이다.

### "DB 커밋은 됐는데 캐시 삭제가 실패하면 어떻게 하나요?"

옛 값이 남으므로 방어를 겹친다: ① 즉시 재시도, ② 실패분을 큐에 넣어
비동기로 반드시 재실행, ③ 근본적으로는 CDC로 DB 변경 로그에서 무효화를
구동해 애플리케이션의 삭제 호출 자체에 의존하지 않기, ④ 그래도 남는
틈은 TTL이 상한을 보장. "삭제 호출의 성공을 전제하지 않는다"는 태도가
포인트다.

### "그럼 갱신(update)이 더 나은 경우는 없나요?" (시니어 변별 포인트)

있다 — 삭제의 비용(미스)이 너무 비싼 경우다. ① 초고빈도로 읽히는
hot key는 삭제 순간 미스 폭주(스탬피드)가 DB를 때리므로, 갱신으로
"캐시가 비는 순간" 자체를 없애는 편이 나을 수 있다. ② 쓰기 경로가
단일하거나(한 서버의 순차 배치) 키별로 직렬화되어 있어 순서 역전이
구조적으로 불가능하면 갱신의 함정이 사라진다. 이때도 순서 역전
방어로 값에 버전/타임스탬프를 실어 "캐시의 버전보다 새 값만 SET"
(Lua로 비교-후-설정)하는 보강이 가능하다. 즉 "무조건 삭제"가 아니라
"기본은 삭제, 미스 비용이 지배적인 키만 갱신을 검토하되 순서 역전
방어를 함께" — 트레이드오프로 답하는 것이 시니어 답변이다.

### "인기 키를 삭제하는 순간 스탬피드가 걱정되면?"

삭제 전략의 실질적 부작용이 이것이다. 완화: ① 재계산을 분산 락이나
`sync = true`로 한 요청만 수행, ② 삭제 대신 "논리적 만료"(soft TTL) —
값에 만료 시각을 함께 저장해 두고, 지난 값도 일단 서빙하면서 백그라
운드로 한 명만 갱신, ③ 변경 이벤트를 받아 삭제가 아니라 **미리 재계산
해서 갱신**(이 경우 위 꼬리질문의 "갱신이 나은 경우"에 해당). 정합성
전략과 스탬피드 방어가 서로 영향을 주는 한 몸의 설계임을 드러내면
좋다.

### "캐시와 DB의 강한 정합성(불일치 0)이 정말 필요하다면?"

캐시로는 안 된다고 답하는 것이 정답이다. 불일치 0이 요구라면 ① 그
읽기 경로는 캐시를 빼고 DB(원본)를 직접 읽거나, ② 판단이 목적이라면
DB의 조건부 연산이 최종 심판이 되게 하고 캐시는 표시용으로만 쓴다.
분산 락으로 읽기·쓰기를 전부 직렬화하면 이론상 가능하지만 캐시를
쓰는 이유(성능)를 스스로 없애는 구조라 실무 답이 아니다. "캐시는
결국 eventual consistency(시간이 지나면 결국 일치)를 받아들이는
결정이고, 못 받아들이는 데이터는 캐시 후보가 아니다" — 03 문서(캐시
도입 기준)와 연결되는 결론이다.

## 한 줄 요약

캐시와 DB는 한 트랜잭션으로 못 묶는 두 저장소라 정합성은 "좁히는 것"
이며 — 갱신은 동시 쓰기의 순서 역전으로 옛 값이 히트로 서빙되는 넓은
창을 열지만 삭제는 멱등이라 최악이 미스 한 번으로 수렴하므로 기본은
"DB 커밋 후 삭제(AFTER_COMMIT)"이고, 삭제 실패 대비(재시도·CDC)와
TTL 상한을 겹친 뒤, hot key처럼 미스가 지배적인 예외에서만 버전 방어를
갖춘 갱신을 검토한다 — 이 논증 과정 자체가 동시성 사고력의 시연이다.
