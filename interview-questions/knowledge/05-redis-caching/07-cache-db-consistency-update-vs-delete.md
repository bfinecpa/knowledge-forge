# 캐시-DB 정합성: 갱신 vs 삭제 — "늦게 도착한 옛 값"이 캐시를 오염시키는 타이밍 문제

> 핵심 관전 포인트: **캐시와 DB는 서로 다른 두 저장소라 하나의 트랜잭션으로 함께 바꿀 수 없다  — 정합성은 보장하는 게 아니라 확률적으로 좁히는 것이다. 
> 나는 갱신(update)보다 삭제(delete/evict)를 선호한다: 갱신은 동시 쓰기 시 캐시 도착 순서가 DB 커밋 순서와 역전되면 옛 값이 캐시의 최종값으로 남아 TTL 내내 서빙되지만, 삭제는 최악의 경우가 "미스 한 번 더"로 수렴하고 경합 시나리오도 훨씬 좁기 때문이다. 
> 정석 조합은 DB 커밋 후 캐시 삭제 + 삭제 실패 대비(재시도/CDC) + TTL을 최후 안전망으로 겹치는 것이다.**

---

## 0. 질문 + 의도

**질문**: "캐시와 DB의 정합성을 어떻게 맞추나요? \"캐시 갱신 vs 캐시 삭제\" 중 무엇을 선호하고 왜인가요?"

**출제 의도**: 순서 역전(늦게 도착한 옛 값이 캐시를 덮는)까지 언급하는지로 분산 환경의 타이밍 문제를 사고할 수 있는지 잰다. "삭제가 안전한 이유"를 논증하는 과정이 곧 동시성 사고력 시연이다.

## 1. 왜 정합성이 "문제"인가 — 두 저장소, 하나의 트랜잭션 불가

### 1-1. 전제 지식 — 캐시는 실제로 어떤 순서로 도는가

이 질문을 이해하려면 먼저 캐시가 붙은 코드가 실제로 어떤 호출 순서로 도는지를 그려둬야 한다. 가장 흔한 방식이 **캐시 어사이드(cache-aside)** — 캐시를 애플리케이션이 직접 챙기는 방식이라 "옆에 둔다(aside)"고 부른다.

읽기는 이렇게 돈다.

```
① 캐시 GET
   히트 -> 그 값을 그대로 응답한다 (DB를 건드리지 않는다)
   미스 -> ② DB SELECT -> ③ 그 결과를 캐시에 SET -> 응답
```

쓰기는 이렇게 돈다.

```
① DB UPDATE (커밋)
② 캐시를 조작한다  <- 이 "조작"이 SET(갱신)이냐 DEL(삭제)이냐가 이 문서의 주제다
```

여기서 눈여겨볼 것은 읽기 경로에도 **캐시 쓰기(③)가 있다**는 점이다. 읽기가 캐시를 채우기 때문에, 뒤에서 볼 사고 시나리오는 "쓰기 둘"뿐 아니라 "읽기 하나 + 쓰기 하나" 조합에서도 터진다.

### 1-2. 두 시스템에 대한 두 번의 호출 — 여기서 틈이 생긴다

DB 갱신과 캐시 조작은 서로 다른 시스템에 대한 **별개의 두 호출**이다. PostgreSQL의 `COMMIT`은 PostgreSQL 안의 변경만 확정하고, Redis의 `DEL`은 Redis 안에서만 일어난다. 이 둘을 한꺼번에 성공시키거나 한꺼번에 되돌리는 트랜잭션은 존재하지 않는다.

그래서 반드시 이런 틈이 생긴다.

- 두 호출 **사이의 시간 창** — DB는 이미 바뀌었는데 캐시는 아직 옛 값인 구간이 있고, 그 사이에 읽기가 끼어들 수 있다.
- **부분 실패** — DB는 커밋됐는데 캐시 호출이 실패할 수 있다(반대도). 어느 한쪽만 반영된 세계가 남는다.
- **순서 역전** — 여러 쓰기가 동시에 일어나면 DB에 반영된 순서와 캐시에 도착한 순서가 다를 수 있다.

### 1-3. 순서 역전이 무엇인지부터 정의하자

세 번째 항목이 이 질문의 핵심 논거인데, 용어가 낯설 테니 여기서 못 박고 간다.

**순서 역전이란, 두 개의 동시 쓰기 W1과 W2가 있을 때 DB에 반영된 순서와 캐시에 도착한 순서가 서로 어긋나는 현상이다.** DB에서는 W1 → W2 순으로 커밋됐는데, 캐시에는 W2 → W1 순으로 도착하는 식이다.

왜 이런 일이 생기는가. **DB 커밋과 캐시 호출은 서로 다른 네트워크 경로를 타는 별개의 왕복**이기 때문이다. W1을 처리하는 서버가 커밋 직후 JVM의 GC로 잠깐 멈추거나, 그 서버에서 Redis로 가는 패킷이 재전송되거나, 스레드가 CPU를 못 받고 대기열에 밀리면, W1의 캐시 호출은 W2의 캐시 호출보다 늦게 도착한다. 애플리케이션 서버가 여러 대인 환경에서 **"내가 나중에 커밋했으니 캐시에도 나중에 도착하겠지"는 성립하지 않는 가정**이다.

그래서 이 질문의 정답 프레임은 "이렇게 하면 완벽히 맞습니다"가 아니라 **"불일치 창을 어디까지 좁히고, 남는 틈은 무엇으로 막느냐"**다. 이 프레임을 첫 문장으로 깔고 시작하는 것 자체가 관전 포인트에 대한 답이다.

## 2. 갱신 vs 삭제 — 순서 역전이 두 방식을 가른다

캐시를 조작하는 방법은 논리적으로 두 가지뿐이다. **새 값을 캐시에도 써넣거나(갱신), 캐시에서 지워서 다음 읽기가 다시 채우게 하거나(삭제).** 갱신은 캐시가 항상 값을 들고 있게 하고, 삭제는 캐시를 잠깐 비운다. 직관적으로는 "삭제하면 미스가 나니까 갱신이 낫지 않나?" 싶다. 그런데 동시 쓰기에서 방향이 뒤집힌다.

### 2-1. 갱신의 함정 — 순서 역전이 옛 값을 "최종값"으로 만든다

같은 상품의 가격을 두 요청이 거의 동시에 수정하는 상황을 시간축에 늘어놓아 보자. W1은 1000원으로, W2는 2000원으로 바꾼다. W1이 DB에 먼저 커밋됐으므로 **정답은 W2의 2000원**이다.

```
시각  W1 (먼저 커밋)              W2 (나중 커밋)             DB      캐시
--------------------------------------------------------------------------
t0   DB UPDATE price=1000 커밋                             1000    (비어 있음)
t1                               DB UPDATE price=2000 커밋  2000    (비어 있음)
t2                               캐시 SET price=2000        2000    2000
t3   (여기서 GC 정지 / 네트워크 재전송으로 캐시 호출이 밀린다)
t4   캐시 SET price=1000                                    2000    1000  <- 오염
```

t4 이후의 상태가 문제의 전부다. **DB는 2000인데 캐시는 1000이다.** 게다가 이 1000은 "값이 없음(미스)"이 아니라 **정상적인 히트로 응답된다.** 캐시 입장에서 이 값은 아무 이상이 없는 멀쩡한 값이고, 다음 쓰기가 들어오거나 TTL이 만료될 때까지 계속 그대로 서빙된다. 아무도 눈치채지 못한 채 옛 가격이 노출되는 것이다.

핵심은 **DB의 커밋 순서(W1→W2)와 캐시 도착 순서(W2→W1)를 일치시킬 방법이 애플리케이션 레벨에 없다**는 것이다. 두 저장소를 묶는 잠금이 없으니, 순서를 강제할 지점 자체가 없다.

갱신에는 부수적 단점도 둘 있다.

**안 읽힐 값을 미리 계산해 적재하는 낭비.** 쓰기가 잦고 읽기가 드문 키라면, 갱신할 때마다 만드는 그 값이 한 번도 안 읽히고 다음 갱신에 덮일 수 있다. 삭제는 다음 읽기가 실제로 있을 때만 적재 비용을 낸다 — 필요할 때 계산한다는 뜻에서 **지연 적재(lazy)**다.

**쓰기 경로가 무거워지는 문제.** 캐시 값이 컬럼 하나를 그대로 복사한 것이 아니라 여러 테이블을 조인하거나 가공해서 만든 결과라면, 갱신 방식에서는 **쓰기 경로마다 그 가공 로직을 다시 태워야 한다.** 가격을 바꾸는 코드, 재고를 바꾸는 코드, 배치가 일괄 수정하는 코드가 전부 "상품 상세 캐시 만드는 법"을 알아야 하는 구조가 되고, 그 로직이 여러 군데로 복제된다.

### 2-2. 삭제가 더 안전한 이유 — 최악이 "미스 한 번"으로 수렴

삭제는 캐시에 값을 쓰지 않고 지우기만 한다. 같은 동시 쓰기 시나리오를 삭제로 다시 돌려보자.

```
시각  W1 (먼저 커밋)              W2 (나중 커밋)             DB      캐시
--------------------------------------------------------------------------
t0   DB UPDATE price=1000 커밋                             1000    (비어 있음)
t1                               DB UPDATE price=2000 커밋  2000    (비어 있음)
t2                               캐시 DEL                   2000    (비어 있음)
t3   (여기서도 마찬가지로 W1의 캐시 호출이 밀린다)
t4   캐시 DEL  <- 늦게 도착해도 "또 지울" 뿐               2000    (비어 있음)

이후 첫 읽기: 미스 -> DB SELECT -> 2000을 적재            2000    2000
```

같은 순서 역전이 일어났는데도 결과가 멀쩡하다. 이유는 **삭제가 멱등(idempotent)이기 때문이다.** 멱등이란 **같은 작업을 몇 번 실행해도 결과가 한 번 실행한 것과 같은 성질**을 말한다. `DEL`을 한 번 하든 세 번 하든, 어떤 순서로 섞이든 끝난 뒤의 캐시 상태는 똑같이 "비어 있음"이다. 순서가 뒤집혀도 뒤집힐 결과 자체가 없다.

반대로 `SET`은 멱등이 아니다. `SET 1000`과 `SET 2000`은 **마지막에 실행된 쪽이 이긴다.** 그래서 순서가 결과를 결정하고, 순서를 보장할 수 없는 환경에서는 그것이 그대로 사고가 된다.

삭제의 대가는 다음 읽기가 내는 **미스 한 번**이다. 정리하면 이 교환이다.

| | 최악의 결과 | 대가 |
|---|---|---|
| 갱신 | 옛 값이 히트로 서빙됨 (TTL까지 지속) | 없음 |
| 삭제 | 다음 읽기가 미스 (DB를 한 번 더 감) | 미스 1회의 지연 |

**"오답을 정답인 척 서빙하는 위험"과 "미스 한 번의 비용"을 맞바꾸는 것** — 이것이 삭제를 선호하는 논증의 뼈대다.

### 2-3. 삭제도 완벽하지 않다 — 읽기와의 경합

시니어 변별은 여기서 갈린다. "삭제는 안전합니다"에서 멈추면 절반이다. **삭제 전략에도 옛 값이 캐시에 남는 창이 있다.** 다만 그 창은 쓰기 둘 사이가 아니라 **읽기 하나와 쓰기 하나 사이**에 열린다.

1-1에서 짚었듯 읽기도 캐시에 값을 쓴다. 그 쓰기가 늦게 도착하면 같은 종류의 오염이 생긴다.

```
시각  R (읽기)                        W (쓰기)                  DB      캐시
---------------------------------------------------------------------------
t0   캐시 GET -> 미스                                         1000    (비어 있음)
t1   DB SELECT -> 1000을 손에 쥠                               1000    (비어 있음)
t2                                   DB UPDATE 2000 커밋      2000    (비어 있음)
t3                                   캐시 DEL (지울 게 없음)   2000    (비어 있음)
t4   t1에서 쥔 1000을 캐시에 SET                               2000    1000  <- 오염
```

R은 잘못한 게 없다. t1 시점에 DB가 준 값은 진짜로 1000이었다. 문제는 그 값을 **캐시에 넣기까지의 사이에 세상이 바뀌었고, 세상이 바뀌었다는 신호(캐시 DEL)가 R보다 먼저 지나가 버렸다**는 것이다. R은 이미 지나간 무효화를 뒤늦게 되돌려 놓는다.

그럼 왜 이 창이 갱신 쪽 경합보다 훨씬 좁은가. 여기가 논증의 핵심이니 조건을 하나씩 세어 보자. 이 사고가 성립하려면 세 가지가 동시에 맞아떨어져야 한다.

1. 하필 그 순간 **캐시가 비어 있어야** 한다(미스). 캐시가 채워져 있으면 R은 t1로 내려가지 않고 히트로 끝난다.
2. 쓰기 W의 **"DB 커밋 → 캐시 삭제" 전체가**, 읽기 R의 **"DB에서 값을 받은 직후 ~ 캐시에 넣기 직전"이라는 짧은 구간 안에 통째로 들어와야** 한다.
3. 그 짧은 구간에 R이 계속 머물러 있어야 한다.

2번이 결정적이다. R의 취약 구간은 **DB 응답을 받고 캐시에 SET 하기까지**로, 보통 값 하나를 객체로 매핑하고 직렬화한 뒤 Redis에 한 번 왕복하는 정도다. 반면 그 안에 끼어들어야 하는 W는 **트랜잭션 커밋을 포함한 DB 쓰기 전체 + 캐시 삭제 왕복**이다. **짧은 구간 안에 그보다 훨씬 긴 작업이 통째로 들어가야 하므로 확률이 낮다.**

갱신 쪽 경합과 비교하면 차이가 선명하다. 갱신의 순서 역전은 **같은 키에 동시 쓰기 둘만 있으면 성립한다.** 캐시가 비어 있을 필요도 없고, 특정 구간에 딱 맞춰 끼어들 필요도 없다. 그냥 두 개의 캐시 호출이 도착하는 순서가 뒤집히기만 하면 된다. 게다가 **쓰기가 몰리는 인기 데이터일수록 잘 터진다** — 방어하고 싶은 대상에서 오히려 확률이 올라가는 구조다.

낮지만 0은 아니다. 그래서 뒤에 TTL을 안전망으로 둔다(3-3). "삭제가 완벽하다"가 아니라 **"창의 넓이와 발생 조건이 다르다"**까지 말해야 논증이 완성된다.

## 3. 실무 정석 조합 — 순서, 실패 대비, 안전망

전략을 골랐으면 그것을 실제로 안전하게 굴리는 조합이 필요하다. 세 겹이다.

### 3-1. 순서 — DB 커밋 "후"에 캐시 삭제

캐시를 먼저 지우고 DB를 쓰면 어떻게 되는지부터 보자. 삭제한 직후~커밋 전 사이에 읽기가 들어오면, 그 읽기는 미스를 내고 DB를 조회하는데 **아직 커밋 전이므로 DB가 주는 값은 옛 값이다.** 그 옛 값이 캐시에 다시 채워지고, 뒤이어 커밋이 끝난다. 지운 보람이 없다.

여기서 PostgreSQL의 동작을 짚고 가면 이해가 분명해진다. PostgreSQL은 다중 버전 동시성 제어(MVCC)를 쓴다 — **한 행의 여러 버전을 함께 두고, 각 트랜잭션에게 자기가 볼 수 있는 버전만 보여주는** 방식이다. 그래서 트랜잭션 T가 값을 2000으로 바꿔놓고 아직 커밋하지 않았다면, **다른 세션이 그 행을 읽을 때 보이는 것은 여전히 옛 버전인 1000이다.** 커밋 전에 캐시를 지운다는 것은 "아직 아무에게도 안 보이는 변경"을 근거로 캐시를 비우는 셈이라, 그 순간의 읽기는 정확히 지우려던 옛 값을 다시 퍼 담는다.

거기에 **롤백까지 고려하면** 커밋 전 삭제는 더 나빠진다. 트랜잭션이 롤백되면 DB는 아무것도 안 바뀌었는데 캐시만 지워진 꼴이다. 데이터가 틀리지는 않지만, 아무 이유 없이 미스를 한 번 만든 것이다.

그래서 **"DB 쓰기(커밋) → 캐시 삭제" 순서가 기본이다.**

스프링에서 흔한 함정이 정확히 이 지점이다. `@Transactional` 메서드 **안에서** 캐시를 지우면, 그 삭제는 메서드가 끝나면서 일어나는 커밋보다 **먼저** 실행된다. 코드를 위에서 아래로 읽으면 "갱신하고 지웠다"로 보이지만, 실제 커밋 시점은 메서드를 빠져나간 뒤라서 순서가 어긋난다.

```java
// Before: 커밋 전에 삭제 — 삭제~커밋 사이의 읽기가 옛 값을 재적재한다
@Transactional
public void updatePrice(Long id, long newPrice) {
    productRepository.updatePrice(id, newPrice);
    // 이 줄이 실행되는 시점에 트랜잭션은 아직 커밋 전이다.
    // 지금 다른 세션이 이 행을 읽으면 MVCC 때문에 옛 값(1000)이 보이고,
    // 그 옛 값이 캐시에 도로 채워진다. 롤백되면 캐시만 헛되이 지운 셈.
    redisTemplate.delete("product:" + id);
}

// After: 커밋 이후로 삭제를 미룬다 — 이벤트 + AFTER_COMMIT
@Transactional
public void updatePrice(Long id, long newPrice) {
    productRepository.updatePrice(id, newPrice);
    // 여기서는 "가격이 바뀌었다"는 사실만 알린다. 실제 캐시 삭제는
    // 스프링이 트랜잭션 커밋이 끝난 뒤로 미뤄서 실행해 준다.
    eventPublisher.publishEvent(new PriceChangedEvent(id));
}

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onPriceChanged(PriceChangedEvent event) {
    // AFTER_COMMIT이므로 이 메서드가 도는 시점에는 커밋이 확정돼 있다.
    // 즉 지금 이후로 DB를 읽는 누구든 새 값(2000)을 보게 된다.
    // 롤백된 트랜잭션의 이벤트는 아예 이 리스너로 전달되지 않는다 —
    // "지울 필요 없는데 지우는" 경우까지 함께 막힌다.
    redisTemplate.delete("product:" + event.productId());
}
```

`@TransactionalEventListener`가 낯설다면 `TransactionSynchronizationManager.registerSynchronization(...)`으로 `afterCommit()` 콜백을 직접 등록해도 같은 일을 한다. 스프링 이벤트가 하는 일이 결국 그 등록이다.

한 가지 짚어둘 것은, 커밋 후로 미뤘다고 해서 2-3의 읽기 경합이 사라지지는 않는다는 점이다. 커밋 후 삭제는 **"내가 만든 옛 값이 재적재되는" 자기 유발 사고를 없애는 것**이지, 다른 읽기와의 인터리빙까지 막지는 못한다.

그 남은 창까지 줄이려는 기법이 **지연 이중 삭제(delayed double delete)**다. 이름 그대로 삭제를 두 번 한다 — 커밋 후 한 번 지우고, **짧은 지연(예: 수백 밀리초) 뒤에 한 번 더 지운다.** 첫 삭제 직전에 이미 옛 값을 손에 쥐고 있던 읽기가 뒤늦게 캐시를 채우더라도, 두 번째 삭제가 그것을 걷어내는 구조다.

대신 대가가 분명하다. 지연 시간을 얼마로 잡을지에 정답이 없고(짧으면 못 막고, 길면 캐시가 두 번 비어 미스가 늘고), 두 번째 삭제를 실행할 지연 작업 인프라가 필요하며, **그 사이에 들어온 읽기가 만든 값도 함께 날아간다.** 무엇보다 이것도 확률을 더 좁힐 뿐 0으로 만들지는 못한다. 그래서 기본 조합으로 깔기보다는 **"허용 가능한 staleness가 유난히 짧은 소수의 키"에만 선택적으로 적용**하는 것이 현실적이다.

### 3-2. 삭제 실패 대비 — 캐시 호출은 실패할 수 있다

DB 커밋은 성공했는데 캐시 삭제 호출이 실패하는 경우가 있다. Redis 순단, 네트워크 오류, 커넥션 풀 고갈, 또는 삭제를 실행할 애플리케이션 인스턴스가 그 순간 죽는 경우다. 이러면 옛 값이 TTL이 다할 때까지 그대로 남는다.

여기서 중요한 태도가 하나 있다. **삭제 호출의 성공을 전제하지 않는다.** 실패를 전제로 방어를 겹친다.

**① 짧은 재시도(즉시 1~2회).** 순간적인 네트워크 흔들림은 이것으로 대부분 흡수된다. 다만 재시도하는 동안 응답을 붙잡고 있으면 사용자 지연이 늘어나므로 횟수와 타임아웃을 짧게 잡는다.

**② 실패 시 메시지 큐에 적재해 비동기 재시도.** 재시도로도 안 되면 "이 키를 지워야 한다"는 사실 자체를 큐에 남긴다. 이 순간 삭제는 **"지금 해보고 안 되면 마는 작업"에서 "언젠가 반드시 실행되는 작업"으로 성격이 바뀐다.** 요청 응답과 분리되므로 사용자 지연에도 영향이 없다.

**③ (가산점 포인트) CDC로 무효화를 구조에 맡기기.** **CDC(Change Data Capture, 변경 데이터 캡처)는 DB가 복제를 위해 남기는 변경 로그를 구독해서, 어떤 행이 어떻게 바뀌었는지를 실시간으로 잡아내는 방식**이다. PostgreSQL에서는 **WAL(Write-Ahead Log, 선행 기록 로그 — 데이터 파일에 반영하기 전에 변경 사실을 먼저 적어두는 로그)**을 논리적 디코딩으로 읽어내며, Debezium이 대표적인 구현이다.

이 방식이 왜 근본적인지가 포인트다. 애플리케이션이 캐시 삭제에 실패하거나, 아예 삭제 코드를 부르는 것을 잊었더라도, **DB를 바꿨다는 사실만큼은 WAL에 반드시 남아 있다.** 커밋된 변경이 WAL에 없을 수는 없기 때문이다. 그러니 WAL을 구독하는 별도 프로세스가 그 기록을 보고 대신 캐시를 지워 줄 수 있다.

덤으로 따라오는 이점이 하나 더 있다. **어떤 경로로 데이터가 바뀌었든 무효화가 따라온다** — 우리 서비스 코드뿐 아니라 야간 배치, 운영자가 직접 실행한 UPDATE, 다른 팀의 어드민 툴까지 전부 WAL을 지나가기 때문이다. **"캐시 지우는 코드를 사람이 기억해서 넣는 규칙"을 "구조가 보장하는 규칙"으로 바꾸는 접근**이라고 정리하면 좋다.

대가도 함께 말해야 한다. CDC 파이프라인(커넥터, 메시지 브로커, 컨슈머)이 운영 대상으로 새로 늘어나고, 무효화가 비동기라 커밋과 삭제 사이에 지연이 하나 더 낀다.

### 3-3. TTL — 모든 전략의 최후 안전망

위의 어떤 조합도 불일치 확률을 0으로 만들지 못한다. 2-3의 읽기 경합 창이 남고, 3-2의 재시도·큐·CDC도 유실될 수 있다. 그래서 **모든 캐시 키에 TTL을 준다.**

TTL을 "메모리 회수 수단"으로만 알고 있으면 이 대목이 안 잡히니 정확히 짚자. **안전망으로서 TTL의 의미는, 앞의 모든 방어가 뚫려 옛 값이 캐시에 남더라도 그 불일치가 영원히 지속되지 않고 최대 TTL만큼으로 시간 상한이 걸린다는 것이다.**

이 차이가 운영에서는 결정적이다. TTL이 없으면 한 번 오염된 키는 **다음 쓰기가 그 키를 건드릴 때까지 무한히** 옛 값을 서빙한다. 거의 안 바뀌는 데이터일수록 오염이 더 오래 간다는 뜻이다. TTL이 5분이면 최악이라도 5분이다.

그래서 이렇게 말할 수 있게 된다. **"우리 시스템의 캐시 불일치는 최악의 경우에도 N분을 넘지 않는다."** 그리고 그 N을 정하는 것은 기술 판단이 아니라 **비즈니스와의 합의**다 — 상품 설명은 10분 지나도 되지만 가격은 30초도 곤란할 수 있다. 이렇게 "허용 가능한 staleness(값이 옛것인 정도)"를 데이터별로 정하는 것이 TTL 설계의 실체다.

## 4. 꼬리질문 대비 포인트

### "삭제도 옛 값이 적재되는 시나리오가 있는데, 왜 갱신보다 안전하다고 하나요?"

**발생 조건의 폭이 다르다**는 것이 답의 골격이다. 위험이 0이냐 아니냐의 비교가 아니라, 창의 넓이 비교라는 점을 먼저 밝히고 들어간다.

갱신의 순서 역전은 **같은 키에 동시 쓰기 둘만 있으면 성립한다.** 전제 조건이 없다시피 하고, 쓰기가 몰리는 인기 데이터일수록 오히려 잘 터진다.

삭제 쪽 경합은 세 조건이 겹쳐야 한다 — 캐시가 마침 비어 있고, 읽기의 "DB 조회 ~ 캐시 적재" 사이라는 짧은 틈에, 쓰기의 "커밋 ~ 캐시 삭제" 전체가 통째로 끼어들어야 한다. **짧은 구간 안에 더 긴 작업이 들어가야 하는 구조라 확률이 낮다.**

여기에 **삭제는 멱등이라 실행 순서가 뒤집혀도 결과가 같다**는 점을 얹으면 논증이 닫힌다. `SET`은 마지막에 도착한 쪽이 이기지만, `DEL`은 몇 번을 어떤 순서로 하든 결과가 "비어 있음"으로 같다.

### "DB 커밋은 됐는데 캐시 삭제가 실패하면 어떻게 하나요?"

옛 값이 남으므로 방어를 겹친다.

1. 즉시 **재시도**(짧게 1~2회) — 순간적 네트워크 흔들림 흡수.
2. 그래도 실패하면 **큐에 적재해 비동기로 반드시 재실행** — 삭제를 "언젠가 반드시 되는 작업"으로 승격시킨다.
3. 근본적으로는 **CDC로 DB 변경 로그(PostgreSQL의 WAL)에서 무효화를 구동**해, 애플리케이션의 삭제 호출 성공 자체에 의존하지 않게 만든다.
4. 그래도 남는 틈은 **TTL이 상한을 보장**한다.

한 줄로 정리하면 **"삭제 호출의 성공을 전제하지 않는다"**는 태도가 포인트다.

### "그럼 갱신(update)이 더 나은 경우는 없나요?" (시니어 변별 포인트)

있다. **삭제의 비용인 "미스"가 감당 못 할 만큼 비싼 경우다.** 두 가지가 대표적이다.

**① 초고빈도로 읽히는 hot key.** 초당 수천 번 읽히는 키를 지우면, 그 직후 들어온 요청이 전부 미스를 내고 동시에 DB로 몰린다. 이것이 **캐시 스탬피드(stampede, 가축 떼의 폭주)**다. 갱신은 캐시가 비는 순간 자체를 만들지 않으므로 이 폭주가 원천적으로 없다.

**② 순서 역전이 구조적으로 불가능한 경우.** 그 키에 대한 쓰기 경로가 하나뿐이고 순차적이라면(예: 한 서버가 도는 단일 스레드 배치, 또는 키별로 파티션이 나뉘어 같은 키의 쓰기가 항상 같은 컨슈머 스레드로 가는 구조) 캐시 호출 순서도 자연히 커밋 순서를 따른다. 갱신의 함정 자체가 성립하지 않는다.

이때도 방어를 하나 얹을 수 있다. **캐시 값에 버전이나 타임스탬프를 함께 저장해 두고, "캐시에 있는 버전보다 새 값일 때만 SET"** 하는 것이다. 비교와 설정이 사이에 끼어들 틈 없이 한 번에 일어나야 하므로 Lua 스크립트로 처리한다. 늦게 도착한 옛 값은 버전 비교에서 걸러져 무시된다 — 순서를 보장할 수 없으니, **대신 값 자체에 순서 정보를 실어 늦게 온 것을 알아보게 만드는** 접근이다.

결론은 "무조건 삭제"가 아니라 **"기본은 삭제, 미스 비용이 지배적인 키만 갱신을 검토하되 순서 역전 방어를 함께 건다"**다. 트레이드오프로 답하는 것이 시니어 답변이다.

### "인기 키를 삭제하는 순간 스탬피드가 걱정되면?"

삭제 전략의 실질적 부작용이 이것이라는 것부터 인정하고 시작한다. 완화책은 셋이다.

**① 재계산을 한 요청만 수행하게 만든다.** 미스가 동시에 100건 나도 DB에는 한 번만 가고 나머지는 그 결과를 기다리게 하는 방식이다. 스프링 캐시의 `@Cacheable(sync = true)`가 이 역할을 하는데, 구현체에 따라 **한 인스턴스(JVM) 안에서만 유효한 경우가 있으므로** 서버가 여러 대라면 Redis 분산 락으로 인스턴스 사이까지 묶어야 한다.

**② 논리적 만료(soft TTL).** 캐시 값 안에 "이 값의 만료 시각"을 함께 저장해 두고, 실제 Redis TTL은 그보다 넉넉하게 잡는다. 읽기가 만료 시각이 지난 값을 만나면 **일단 그 옛 값을 응답하고**, 백그라운드에서 한 명만 재계산해 채운다. 캐시가 물리적으로 비는 순간이 없으므로 폭주가 없고, 대가는 재계산 동안 잠깐 옛 값이 나간다는 것이다.

**③ 변경 이벤트를 받아 미리 재계산해서 갱신한다.** 삭제 대신 새 값을 채워 넣는 것이므로, 앞 꼬리질문의 "갱신이 나은 경우"에 해당한다. 이 경우 순서 역전 방어를 함께 걸어야 한다.

**정합성 전략과 스탬피드 방어가 서로 영향을 주는 한 몸의 설계**임을 드러내면 좋다. 삭제를 택하면 스탬피드를 걱정해야 하고, 스탬피드를 피하려 갱신으로 가면 순서 역전을 걱정해야 한다.

### "캐시와 DB의 강한 정합성(불일치 0)이 정말 필요하다면?"

**캐시로는 안 된다고 답하는 것이 정답이다.** 캐시를 두는 순간 두 저장소가 되고, 두 저장소는 한 트랜잭션으로 못 묶이므로 불일치 창은 원리적으로 남는다.

불일치 0이 진짜 요구라면 방향은 둘이다.

- **그 읽기 경로에서 캐시를 뺀다.** 원본인 DB를 직접 읽는다.
- **판단이 목적이라면 DB의 조건부 연산이 최종 심판이 되게 한다.** 예를 들어 재고 차감은 `UPDATE ... WHERE stock >= 1`처럼 DB가 조건과 갱신을 한 번에 판정하게 하고, 캐시의 재고 숫자는 **화면 표시용**으로만 쓴다. 캐시가 틀려도 실제 차감은 DB에서 걸러지므로 사고가 나지 않는다.

분산 락으로 읽기·쓰기를 전부 직렬화하면 이론상 가능하지만, 그 순간 모든 읽기가 락을 기다리게 되어 **캐시를 쓰는 이유인 성능을 스스로 없애는 구조**라 실무 답이 아니다.

정리 문장은 이것이다. **"캐시는 결국 eventual consistency(결과적 일관성 — 지금은 다를 수 있지만 시간이 지나면 결국 일치한다)를 받아들이는 결정이고, 그것을 못 받아들이는 데이터는 애초에 캐시 후보가 아니다."** 03 문서(캐시 도입 기준)와 이어지는 결론이다.

## 한 줄 요약

캐시와 DB는 한 트랜잭션으로 못 묶는 두 저장소라 정합성은 "좁히는 것"이며 — 갱신은 동시 쓰기의 순서 역전(DB 커밋 순서와 캐시 도착 순서가 어긋나는 현상)으로 옛 값이 히트로 서빙되는 넓은 창을 열지만 삭제는 멱등이라 최악이 미스 한 번으로 수렴하므로 기본은 "DB 커밋 후 삭제(AFTER_COMMIT)"이고, 삭제 실패 대비(재시도·큐·CDC)와 TTL 상한을 겹친 뒤, hot key처럼 미스가 지배적인 예외에서만 버전 방어를 갖춘 갱신을 검토한다 — 이 논증 과정 자체가 동시성 사고력의 시연이다.
