# TTL·만료 정책·eviction — 메모리가 가득 차는 날, 캐시인가 장애 발생기인가

> 핵심 관전 포인트: **TTL은 키에 수명을 거는 것이고, 만료된 키는 즉시
> 지워지는 게 아니라 "접근 시 삭제(lazy) + 주기적 샘플링 삭제(active)"
> 두 방식으로 지연 정리된다. maxmemory에 도달했을 때의 행동은
> maxmemory-policy가 정하는데, 기본값 noeviction은 오래된 키를 지우는 게
> 아니라 쓰기 명령을 에러로 거부한다 — 캐시 용도라면 allkeys-lru 같은
> eviction 정책을 반드시 명시해야 하고, 이걸 모른 채 운영하면 메모리가
> 차는 날 캐시가 장애 발생기가 된다.**

---

## 0. 질문 + 의도

**질문**: "TTL과 만료 정책, maxmemory eviction 정책(LRU 등)을
설명해주세요."

**출제 의도**: maxmemory 도달 시 무슨 일이 벌어지는지(eviction? 쓰기
거부?) 모르고 운영하면, 메모리가 차는 날 캐시가 아니라 장애 발생기가
된다.

## 1. TTL — 키에 수명을 건다

TTL(Time To Live)은 키의 남은 수명이다. 수명이 다한 키는 "없는 키"로
취급된다(조회하면 nil). 캐시에서 TTL은 두 역할을 겸한다 — **정합성의
상한선**(원본과 어긋나도 최대 TTL만큼만)이자 **메모리 회수 장치**(안 쓰는
데이터가 알아서 사라짐).

```text
SET product:1234 '{"price":1500}' EX 300   # 저장과 동시에 300초 수명
EXPIRE session:abc 1800                     # 기존 키에 수명 부여/갱신
TTL product:1234                            # 남은 수명 조회 (-1: 수명 없음, -2: 키 없음)
PERSIST session:abc                         # 수명 제거 → 영구 키로
```

주의 두 가지. ① `SET`으로 값을 덮어쓰면 **기존 TTL이 사라진다**(수명
없는 영구 키가 됨) — 갱신 코드에서 EX를 빼먹으면 "언젠가부터 안 지워지는
키"가 조용히 쌓인다. ② TTL 없는 키는 아래 3절의 eviction 정책에 따라
**영원히 회수되지 않을 수도** 있다.

```java
// before: 캐시 갱신 시 TTL 누락 — 이 키는 이제 영구 키
redis.set("product:1234", newJson);

// after: 갱신에도 항상 TTL을 함께 — "모든 캐시 키는 TTL을 가진다" 규율
redis.set("product:1234", newJson, SetArgs.Builder.ex(300));
```

## 2. 만료 정책 — "만료된 키가 즉시 사라진다"는 착각

키가 수백만 개인데 만료 시각마다 알람을 걸어 정확히 그 순간 지우려면
그 관리 비용 자체가 서버를 짓누른다. 그래서 Redis는 **정확한 즉시 삭제를
포기하고** 두 가지를 조합한다:

- **Lazy(수동적) 삭제**: 키에 **접근하는 순간** 만료 여부를 확인하고,
  만료됐으면 그때 지우고 nil을 반환한다. 접근 없는 키는 이 경로로는
  영영 안 지워진다.
- **Active(능동적) 삭제**: 백그라운드에서 **주기적으로 TTL 있는 키를
  무작위 샘플링**해 만료된 것을 지운다. 샘플 중 만료 비율이 높으면 한
  사이클에서 반복 수행해 따라잡는다.

비유: 냉장고의 유통기한 지난 음식은 ① 꺼낼 때 발견하면 버리고(lazy)
② 주기적으로 몇 칸씩 뒤져서 버린다(active). 매초 전 칸을 검사하지는
않는다.

여기서 나오는 실무적 함의:

1. **만료된 키도 삭제 전까지 메모리를 차지한다.** "TTL 합계상 메모리가
   남아야 하는데 왜 차 있지?"의 답이 이것이다.
2. **대량의 키가 같은 시각에 만료되면** active 삭제 작업이 몰려 지연
   스파이크가 생기고, 캐시 미스도 동시에 터진다(캐시 스탬피드의 한 형태).
   → TTL에 무작위 지터(jitter)를 더해 만료 시각을 흩는다.

```java
// before: 배치가 상품 10만 건을 전부 TTL 3600으로 적재 — 1시간 뒤 동시 만료
redis.set(key, json, ex(3600));

// after: 기본 TTL ± 무작위 지터 — 만료 시각을 흩어 삭제 부하·미스 폭주 분산
long ttl = 3600 + ThreadLocalRandom.current().nextLong(0, 300);
redis.set(key, json, ex(ttl));
```

(가산점 포인트) 복제 구조에서는 **만료 삭제를 master만 결정**하고,
replica에는 DEL이 전파된다 — replica가 제멋대로 지우면 master와 데이터가
어긋나기 때문이다. replica는 논리적으로 만료된 키의 읽기에 nil을
반환하도록 처리한다.

## 3. maxmemory와 eviction — 가득 찼을 때의 행동 규칙

`maxmemory`는 Redis가 사용할 메모리 상한이다. 문제는 **도달했을 때 무엇을
할 것인가** — 이것이 `maxmemory-policy`고, 이 질문의 심장이다.

### 3-1. 기본값 noeviction — "지우기"가 아니라 "거부"

많은 사람이 "가득 차면 알아서 오래된 걸 지우겠지"라고 가정하지만,
**기본 정책 noeviction은 아무것도 지우지 않고 메모리를 쓰는 명령(쓰기)을
에러로 거부한다**(읽기는 계속된다). 캐시 쓰기가 전부 예외를 던지기
시작하고, 예외 처리가 허술하면 조회 API 전체가 5xx로 번진다 — "메모리가
차는 날 캐시가 장애 발생기가 된다"는 말의 정확한 의미다.

### 3-2. 정책 8가지 — 두 축으로 기억한다

정책 이름은 **[대상 범위] - [고르는 기준]** 조합이라 두 축으로 기억하면
외울 게 없다.

| | 모든 키 대상 (allkeys-) | TTL 있는 키만 (volatile-) |
|---|---|---|
| LRU (가장 오래 안 쓴) | allkeys-lru | volatile-lru |
| LFU (가장 덜 쓰인) | allkeys-lfu | volatile-lfu |
| 무작위 | allkeys-random | volatile-random |
| TTL 임박 순 | — | volatile-ttl |
| 안 지움 (쓰기 거부) | noeviction | — |

- **LRU**(Least Recently Used): 가장 오래 접근 없던 키부터 — "최근에 쓴
  건 또 쓸 것"이라는 가정. 일반 캐시의 무난한 기본.
- **LFU**(Least Frequently Used): 접근 빈도가 가장 낮은 키부터 — 어쩌다
  한 번의 대량 순회(배치 스캔)가 "최근 접근"을 만들어 LRU를 오염시키는
  패턴에서 인기 키를 더 잘 지킨다.
- **volatile-***: **TTL이 걸린 키만** 후보다. TTL 없는 키(세션, 설정 등)를
  보호하는 대신 — TTL 걸린 키가 하나도 없으면 지울 게 없어 **noeviction
  처럼 쓰기 에러**가 난다는 함정이 있다.

### 3-3. 용도별 선택

- **순수 캐시 전용 인스턴스**: `allkeys-lru`(또는 접근 패턴에 따라
  allkeys-lfu). 어떤 키든 다시 만들 수 있으므로 지워도 안전.
- **캐시 + 지워지면 안 되는 데이터 혼재**: 원칙은 **인스턴스 분리**다.
  분리 전이라면 volatile-lru + "캐시에만 TTL을 건다"는 규율 — 단 이
  규율이 한 번이라도 깨지면(TTL 누락 캐시 키) 보호가 무너진다.
- **큐·원본성 데이터 전용**: noeviction이 오히려 맞다 — 데이터를 임의로
  지우면 안 되므로, 대신 메모리 알람으로 차기 전에 사람이 개입한다.

```text
# redis.conf — 캐시 전용 인스턴스의 최소 규율
maxmemory 4gb
maxmemory-policy allkeys-lru
```

(가산점 포인트) eviction은 공짜가 아니다 — maxmemory 언저리에서
운영하면 **쓰기마다 지울 키를 고르는 작업**이 얹혀 지연이 늘고, 지운
키를 곧 다시 캐시 미스로 채우는 낭비가 반복된다. eviction은 안전망이지
용량 계획의 대체재가 아니다: 메모리 사용률 알람(예: 80%)을 걸고 그 전에
증설·TTL 재점검이 정석이다.

## 4. 실무 사례 — "kubectl도 안 건드렸는데 캐시 쓰기가 전부 실패"

전형적 시나리오: 캐시 도입 초기에 maxmemory-policy를 기본값(noeviction)
으로 둔 채 운영 → 몇 달간 TTL 누락 키와 신규 기능 키가 누적 →
maxmemory 도달 → 어느 날 새벽부터 캐시 SET이 전부 OOM 에러.

- 코드 배포가 없었으므로 애플리케이션 원인 추적은 헛돈다 — Redis
  `INFO memory`의 used_memory와 maxmemory, evicted_keys 지표를 봤다면
  즉시 좁혀졌을 문제.
- 근본 원인은 셋의 합: ① 정책 미설정(noeviction) ② TTL 규율 부재(영구
  키 누적) ③ 메모리 사용률 알람 부재.
- 복구는 정책 변경(allkeys-lru)으로 급한 불을 끄고, `SCAN`으로 TTL 없는
  키를 찾아(`TTL`이 -1인 키) 정리·수명 부여, 이후 알람 설정.

이 사례 하나로 이 질문의 세 요소(TTL 규율, 만료 방식, eviction 정책)가
전부 연결된다 — 면접에서 이 흐름으로 답하면 "운영해 본 사람"의 답이 된다.

## 5. 꼬리질문 대비 포인트

### "TTL이 지난 키는 그 순간 메모리에서 사라지나요?"

아니다. 만료는 "접근 시 확인·삭제(lazy) + 주기적 샘플링 삭제(active)"로
지연 처리되므로, 만료됐지만 아직 안 지워진 키가 메모리를 차지하고 있을
수 있다. 논리적으로는 만료 즉시 없는 키로 취급되므로(조회 시 nil) 정합성
문제는 없고, 문제는 메모리 회수 시점과 대량 동시 만료 시의 삭제 부하다.

### "maxmemory에 도달하면 정확히 무슨 일이 벌어지나요?"

maxmemory-policy에 따라 갈린다. 기본값 noeviction이면 **지우는 게 아니라
쓰기 명령을 에러로 거부**한다(읽기는 유지) — 애플리케이션의 캐시 저장이
전부 예외를 던지는 상태다. eviction 정책이 설정돼 있으면 정책 기준으로
키를 지워 공간을 만든 뒤 쓰기를 받는다. 그래서 "캐시 용도인데 정책을
기본값으로 뒀다"는 것 자체가 설정 사고이며, 배포 전 점검 항목이다.

### "Redis의 LRU는 정확한 LRU인가요?" (시니어 변별 포인트)

**근사(approximate) LRU**다. 정확한 LRU는 전 키를 접근 순서 연결
리스트로 꿰어야 하는데, 수천만 키의 포인터 유지 비용(메모리+연산)이
과하다. Redis는 키마다 마지막 접근 시각 정보만 저장해 두고, evict할 때
**무작위로 몇 개를 샘플링해 그중 가장 오래된 것**을 지운다(샘플 수는
maxmemory-samples로 조정 — 키울수록 정확하지만 CPU를 더 쓴다). "캐시
eviction은 대략만 맞아도 충분하다"는 판단으로 정확도를 성능과 맞바꾼
설계다 — 트레이드오프에 이유를 붙여 설명하면 변별이 된다.

### "세션과 캐시가 한 인스턴스에 있는데 allkeys-lru라면 어떤 사고가 나나요?"

메모리가 차면 **오래 접근 없던 세션 키가 eviction 후보**가 된다 — 어느 날
사용자들이 이유 없이 로그아웃되는데, 에러 로그는 한 줄도 없다(eviction은
장애가 아니라 정상 동작이므로). 지표로는 evicted_keys 증가만 남는다.
교훈은 "지워도 되는 데이터와 지우면 안 되는 데이터는 eviction 정책을
공유하면 안 된다" — 인스턴스 분리가 원칙이고, 못 하면 volatile 계열 +
TTL 규율로 임시 방어한다.

### "볼륨이 크고 TTL이 다양한 캐시에서 LRU와 LFU 중 뭘 고르겠어요?"

접근 패턴을 먼저 본다. 꾸준히 읽히는 인기 키가 뚜렷하고, 배치·크롤러
같은 일회성 대량 순회가 섞이는 환경이면 LFU가 유리하다 — LRU는 일회성
순회가 훑고 간 콜드 키들을 "방금 접근됨"으로 만들어 진짜 인기 키를
밀어낼 수 있기 때문(캐시 오염). 반면 접근 패턴이 시간대별로 빠르게
바뀌는 서비스면 빈도 누적이 과거에 발목 잡히는 LFU보다 LRU가 낫다.
"정답은 지표로 검증한다 — 정책 변경 후 히트율 변화를 본다"까지 붙이면
좋다.

## 한 줄 요약

TTL은 키의 수명이고 만료는 lazy+active로 지연 정리되며, 메모리가 가득
찬 날의 운명은 maxmemory-policy가 정한다 — 기본값은 "지우기"가 아니라
"쓰기 거부"이므로, 캐시 인스턴스에 eviction 정책과 TTL 규율, 메모리
알람을 미리 깔아두는 것이 캐시와 장애 발생기를 가르는 선이다.
