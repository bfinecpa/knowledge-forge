# Redis 메모리 포화(OOM) — 가득 차면 무슨 일이 벌어지고, 어떻게 막는가

> 핵심 관전 포인트: **Redis 메모리가 maxmemory에 닿으면 무슨 일이
> 벌어지는지는 eviction 정책이 결정한다 — `noeviction`(기본값)이면
> 모든 쓰기가 에러로 실패하기 시작하고(읽기는 됨), eviction 정책이면
> 기존 키가 지워지면서 자리를 만드는데, 세션·락·발급 카운터처럼
> "지워지면 안 되는 데이터"가 섞여 있으면 조용한 데이터 유실이 된다.
> maxmemory를 아예 안 잡으면 더 나쁘다 — OS 스왑으로 지연이 폭발하거나
> OOM killer가 프로세스를 통째로 죽인다. 방어는 사후가 아니라 사전이다:
> 용도별 인스턴스 분리, 용도에 맞는 eviction 정책, 전 키 TTL 규율,
> 메모리 사용률·evicted_keys 알람, 그리고 캐시 쓰기 실패가 서비스
> 실패로 번지지 않게 하는 애플리케이션 방어.**

---

## 0. 질문 + 의도

**질문**: "Redis 메모리가 가득 찼을 때(OOM) 서비스에 어떤 일이
벌어지나요? 사전 방어책은?"

**출제 의도**: "캐시가 죽으면 서비스가 어떻게 되는가"를 미리 그려보고
방어(메모리 알람, eviction 정책, 키 TTL 규율)를 깔아두는 운영 성숙도를
확인한다. 증상 나열이 아니라 "우리 설정에서는 이렇게 되고, 그래서
이런 방어를 깔아뒀다"는 구체적인 시나리오를 그릴 수 있는지 본다.

## 1. 가득 차면 벌어지는 일 — 설정에 따라 세 갈래

같은 "메모리 포화"라도 결과는 설정에 따라 완전히 다르다.
면접에서는 이 분기를 그릴 수 있느냐가 핵심이다.

### ① `maxmemory` + `noeviction` (기본값) — 쓰기 전면 실패

메모리를 더 쓰는 명령(`SET`, `LPUSH`, `INCR`, ...)이 전부 에러를 받는다.

```
(error) OOM command not allowed when used memory > 'maxmemory'.
```

읽기(`GET`)와 삭제(`DEL`)는 계속 된다. 서비스 관점에서는:

- 캐시 put 실패 → 코드가 예외를 안 감쌌다면 **조회 API 자체가 500**
- 세션 저장 실패 → **신규 로그인 전면 불가** (기존 세션 읽기는 됨)
- 분산 락 획득(`SET NX`) 실패 → 락이 필요한 기능 전체 정지

"캐시가 꽉 찼을 뿐인데 로그인이 안 되는" 장애가 이 경로다.

### ② `maxmemory` + eviction 정책 — 키가 지워지며 버틴다

`allkeys-lru` 등이면 정책에 따라 기존 키를 지워 자리를 만든다.
캐시 전용 인스턴스라면 이게 **정상 동작**이다 — 다만:

- **혼합 사용의 함정**: 캐시와 세션·락·쿠폰 카운터가 한 인스턴스에
  있으면, LRU가 "한동안 안 쓴 세션"을 지워버린다. 에러 한 줄 없이
  **사용자가 무작위로 로그아웃**되는, 원인 추적이 지독한 장애가 된다.
- `volatile-*` 계열(TTL 있는 키만 축출)인데 TTL 있는 키가 바닥나면
  지울 게 없어 **결국 noeviction처럼 쓰기 에러**로 넘어간다.
- eviction이 격하게 돌면 그 자체로 지연이 튀고, 지워진 캐시만큼
  DB 조회가 늘어 **DB 부하가 함께 오르는** 2차 효과가 있다.

### ③ `maxmemory` 미설정 — 최악의 경로

Redis가 한계 없이 자라다가 OS 수준에서 터진다.

- 물리 메모리를 넘으면 **스왑** — 메모리 DB가 디스크를 오가며
  응답 시간이 수십~수백 배로 튄다. "죽지도 않고 살지도 않은" 상태.
- 더 가면 커널 **OOM killer가 Redis 프로세스를 강제 종료** —
  부분 실패가 아니라 인스턴스 전체 다운, 영속화가 없다면 데이터
  전체 증발이다.

(가산점 포인트) maxmemory 안에서도 터질 수 있다 — RDB 스냅샷·AOF
rewrite의 fork는 copy-on-write로 **순간 메모리 사용량을 크게 늘린다.**
그래서 maxmemory는 물리 메모리보다 충분히 낮게(fork 여유분을 남기고)
잡아야 한다.

## 2. 사전 방어책 — 네 겹의 방어선

### 방어선 1: 용도별 인스턴스 분리 (구조)

eviction 정책은 인스턴스당 하나다. "지워도 되는 데이터(캐시)"와
"지우면 안 되는 데이터(세션, 락, 카운터)"가 한 인스턴스에 있으면
어떤 정책을 골라도 한쪽이 틀린다.

- 캐시 인스턴스: `allkeys-lru`(또는 `allkeys-lfu`) — 가득 차면
  안 쓰는 것부터 지우는 게 정답
- 세션/원본 인스턴스: `noeviction` + 넉넉한 용량 + 알람 —
  지우느니 쓰기 에러를 내고 사람이 대응하는 게 정답

### 방어선 2: TTL 규율 (누수 차단)

TTL 없는 캐시 키는 **메모리 누수**다. 한 번 쓰이고 잊힌 키가
영원히 쌓인다.

```java
// Before: TTL 없는 캐시 put — 지워질 계기가 eviction뿐
redis.set("product:detail:" + id, json);

// After: 모든 캐시 키에 TTL을 강제하는 래퍼를 팀 표준으로
cacheClient.set("product:detail:" + id, json, Duration.ofMinutes(30));
// 래퍼 내부에서 TTL 미지정이면 예외/기본값 — "깜빡함"을 구조로 차단
```

키 버저닝으로 버려진 구버전 키, 배치가 만든 임시 키 등
"주인 잃은 키"를 SCAN 기반으로 주기 점검하는 것까지 말하면 좋다.

### 방어선 3: 관측과 알람 (조기 경보)

가득 찬 뒤에 아는 것과 70%에서 아는 것의 차이가 장애 유무를 가른다.

- `INFO memory`의 `used_memory` / maxmemory 비율 — 임계치(예: 70~80%)
  알람
- `evicted_keys` 증가율 — 캐시 인스턴스라도 급증하면 "용량 부족 또는
  누수" 신호, noeviction 인스턴스에서 0이 아니면 즉시 조사
- `mem_fragmentation_ratio` — 실제 데이터보다 프로세스가 메모리를
  훨씬 더 쥐고 있는 단편화 감지
- Big key 감시 — 수백만 멤버 컬렉션 하나가 용량 계획을 무의미하게
  만든다

### 방어선 4: 애플리케이션 방어 (폭발 반경 축소)

캐시는 언젠가 실패한다는 전제로, **캐시 에러가 서비스 에러로
전파되지 않게** 한다.

```java
// Before: 캐시 put 실패 = 조회 API 500
public Product getProduct(Long id) {
    Product p = repository.findById(id);
    redis.set(key(id), serialize(p), TTL);   // OOM 에러가 그대로 전파
    return p;
}

// After: 캐시는 최선노력(best-effort) — 실패해도 본 기능은 산다
public Product getProduct(Long id) {
    Product p = repository.findById(id);
    try {
        redis.set(key(id), serialize(p), TTL);
    } catch (RedisException e) {
        log.warn("cache put failed, serving without cache", e);
        // 메트릭 증가 → 알람으로 연결. 응답은 정상 반환
    }
    return p;
}
```

단, 이 방어의 이면도 말해야 한다 — 캐시 put이 계속 실패하면 모든
조회가 DB로 직행하므로, **DB가 캐시 없는 트래픽을 견딜 수 있는지**
(캐시 무력화 방어)가 다음 질문이 된다.

## 3. 실무 시나리오 — "배포 후 로그인이 안 돼요"

혼합 사용 + noeviction 인스턴스에서 전형적으로 벌어지는 사고 흐름:

1. 새 기능이 TTL 없는 캐시 키를 대량 생성 (코드 리뷰에서 못 잡음)
2. 몇 주에 걸쳐 메모리가 서서히 참 — 알람이 없어 아무도 모름
3. 어느 날 maxmemory 도달 → 세션 `SET` 실패 → 신규 로그인 전면 불가
4. "Redis는 살아 있음(PING OK), DB도 정상"이라 원인 추적이 헤맴 —
   헬스체크가 읽기만 확인하면 이 상태를 못 잡는다

이 시나리오에서 위 네 방어선이 각각 어느 단계를 끊는지
(1→TTL 규율, 2→알람, 3→인스턴스 분리·정책, 4→쓰기 헬스체크)를
연결해 말하면 "미리 그려본 사람"이라는 인상을 준다.

## 4. 꼬리질문 대비 포인트

### "noeviction으로 가득 찬 상태에서 읽기도 실패하나요?"

아니다. 메모리를 추가로 쓰는 명령만 거부되고 `GET`, `DEL`,
`EXPIRE`(줄이는 방향) 등은 동작한다. 그래서 겉보기 헬스체크(PING,
GET)는 멀쩡한데 쓰기 경로만 죽는 **반쪽 장애**가 된다 — 헬스체크에
쓰기 확인을 포함해야 하는 이유다.

### "Redis의 LRU는 정확한 LRU인가요?"

아니다 — **근사(approximated) LRU**다. 전체 키를 정렬해 관리하면
그 자체가 메모리·CPU 비용이라, 소수의 키를 샘플링해 그중 가장 오래
안 쓴 것을 지운다(`maxmemory-samples`로 정밀도 조절). (가산점 포인트)
접근 "빈도"까지 보는 LFU(`allkeys-lfu`)를 언급하고, "한 번 크게
스캔당하면 자주 쓰는 키가 밀려나는 LRU의 약점을 LFU가 보완한다"까지
말하면 좋다.

### "maxmemory를 물리 메모리와 같게 잡으면 왜 위험한가요?"

Redis 프로세스는 데이터 외에도 메모리를 쓴다 — 클라이언트 버퍼,
복제 버퍼, 그리고 결정적으로 **RDB/AOF rewrite fork 시 copy-on-write로
불어나는 몫**. maxmemory에 딱 맞춰 잡으면 스냅샷이 도는 순간 OS 레벨
OOM으로 프로세스가 죽을 수 있다. 여유분을 남기고 잡는 것이 원칙이다.

### "이미 70~80% 알람이 울렸다. 당장 뭘 하나요?"

단기: `INFO memory`·big key 점검으로 **뭐가 먹고 있는지**부터 확인 →
TTL 없는 키·버려진 키 정리(대형 컬렉션은 `DEL` 대신 `UNLINK`로
비동기 삭제), 급하면 maxmemory 상향(물리 여유 내에서).
구조: 증가 추세 분석 → 용량 증설 또는 용도 분리 계획. "일단 재시작"은
답이 아니다 — 원인(누수)이 그대로면 다시 찬다.

### "캐시와 세션이 이미 한 인스턴스에 섞여 운영 중입니다. 어떻게 풀어가나요?" (시니어 변별 포인트)

한 번에 못 바꾼다 — 이행 계획을 말해야 한다.

1. **현황 파악**: 키 패턴별 메모리 점유(SCAN + 샘플링)로 캐시/세션
   비중을 수치화
2. **신규 인스턴스 준비**: 세션용(noeviction) 분리 인스턴스 구축
3. **이중 쓰기 → 읽기 전환 → 구 데이터 소멸 대기**: 세션은 TTL이
   있으므로 이중 쓰기 기간을 TTL만큼 유지하면 자연 이관된다
4. **기존 인스턴스를 캐시 전용으로 확정**: `allkeys-lru`로 정책 변경

"정책 하나로 두 용도를 만족시킬 수 없다는 것"이 분리의 근거이고,
세션의 TTL 특성을 이관 전략에 활용하는 것이 판단 포인트다.

## 한 줄 요약

Redis가 가득 찼을 때의 증상은 설정이 결정한다 — noeviction이면 쓰기
전면 실패, eviction이면 (섞어 쓴 경우) 조용한 데이터 유실, maxmemory
미설정이면 스왑·프로세스 강제 종료라는 최악 — 그래서 방어는 **용도별
인스턴스 분리와 그에 맞는 eviction 정책, 전 키 TTL 규율, 사용률·축출
알람, 캐시 실패를 삼키는 애플리케이션 코드**로 가득 차기 전에
겹겹이 깔아둬야 한다.
