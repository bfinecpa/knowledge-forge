# Redis 메모리 포화(OOM) — 가득 차면 무슨 일이 벌어지고, 어떻게 막는가

> 핵심 관전 포인트: **Redis 메모리가 `maxmemory`에 닿았을 때 무슨 일이 벌어지는지는 eviction(축출) 정책이 결정한다 — `noeviction`이면 메모리를 더 쓰는 명령만 골라 에러로 실패하고 읽기는 멀쩡히 되는 반쪽 장애가 되고, eviction 정책이면 기존 키를 지워 자리를 만드는데 세션·락·발급 카운터처럼 "지워지면 안 되는 데이터"가 섞여 있으면 에러 한 줄 없는 조용한 데이터 유실이 된다. `maxmemory`를 아예 안 잡으면 더 나쁘다 — 스왑으로 지연이 폭발하거나(싱글 스레드라 한 명령의 디스크 대기가 뒤에 줄 선 전부의 지연이 된다) 리눅스 커널의 OOM killer가 프로세스를 통째로 죽인다. 그리고 `maxmemory` 안에서도 터진다 — fork의 copy-on-write, 클라이언트 버퍼, 복제 버퍼, 단편화가 데이터 바깥에서 메모리를 더 먹기 때문이다. 방어는 사후가 아니라 사전이다: 용도별 인스턴스 분리, 용도에 맞는 eviction 정책, 전 키 TTL 규율, 사용률·`evicted_keys` 알람, 그리고 캐시 쓰기 실패가 서비스 실패로 번지지 않게 하는 애플리케이션 방어.**

---

## 0. 질문 + 의도

**질문**: "Redis 메모리가 가득 찼을 때(OOM) 서비스에 어떤 일이 벌어지나요? 사전 방어책은?"

**출제 의도**: "캐시가 죽으면 서비스가 어떻게 되는가"를 미리 그려보고 방어(메모리 알람, eviction 정책, 키 TTL 규율)를 깔아두는 운영 성숙도를 확인한다. 증상 나열이 아니라 "우리 설정에서는 이렇게 되고, 그래서 이런 방어를 깔아뒀다"는 구체적인 시나리오를 그릴 수 있는지 본다.

## 1. 가득 차면 벌어지는 일 — 설정에 따라 세 갈래

### 1-1. 전제 지식 — `maxmemory`와 eviction 정책이 무엇인가

같은 "메모리 포화"라도 결과는 설정에 따라 완전히 달라진다. 그 설정이 두 개다. 먼저 이 둘이 무엇인지부터 깔고 가자.

**`maxmemory`는 Redis가 스스로에게 거는 상한선이다.** "데이터가 이만큼을 넘으면 나는 더 이상 자라지 않겠다"고 Redis가 자기 자신에게 선언하는 값이다. 물리 메모리가 얼마든 상관없이, 이 값에 닿으면 Redis는 자기 판단으로 행동을 바꾼다.

**eviction(축출) 정책은 그 상한선에 닿았을 때 무엇을 할지 정하는 규칙이다.** eviction은 "쫓아냄"이라는 뜻으로, 자리를 만들기 위해 기존 키를 골라 지우는 동작을 말한다. 설정 이름은 `maxmemory-policy`다.

정책은 이름 규칙을 알면 외울 필요가 없다. 앞부분이 **후보 범위**, 뒷부분이 **고르는 기준**이다.

| 정책 | 축출 후보 | 고르는 기준 |
|---|---|---|
| `noeviction` | 없음 (아무것도 안 지움) | — |
| `allkeys-lru` | 전체 키 | 가장 오래 안 쓴 것 |
| `allkeys-lfu` | 전체 키 | 가장 적게 쓴 것 |
| `allkeys-random` | 전체 키 | 무작위 |
| `volatile-lru` | TTL이 걸린 키만 | 가장 오래 안 쓴 것 |
| `volatile-ttl` | TTL이 걸린 키만 | 만료가 가장 임박한 것 |

`allkeys-`는 모든 키가 축출 대상이라는 뜻이고, `volatile-`은 "휘발성"이라는 이름 그대로 **TTL(만료 시각)이 걸린 키만** 대상으로 삼겠다는 뜻이다. LRU는 Least Recently Used(가장 오래 안 쓴 것), LFU는 Least Frequently Used(가장 적게 쓴 것)의 약자다.

여기서 한 가지 헷갈리기 쉬운 점을 짚어두자. **`maxmemory-policy`의 기본값은 `noeviction`이지만, `maxmemory`의 기본값은 0 — 즉 "상한 없음"이다.** 그래서 아무것도 설정하지 않고 띄운 Redis는 정책이 무엇이든 애초에 발동할 상한이 없다. 뒤에 나올 갈래 ③이 실은 "손대지 않은 기본 상태"라는 뜻이다.

이제 세 갈래를 본다.

### 1-2. 갈래 ① `maxmemory` + `noeviction` — 쓰기만 골라 실패한다

이 조합에서는 상한에 닿아도 Redis가 아무것도 지우지 않는다. 대신 **메모리를 더 쓰는 명령을 거부한다.**

```
127.0.0.1:6379> SET user:1001 "{...}"
(error) OOM command not allowed when used memory > 'maxmemory'.

127.0.0.1:6379> GET user:1001
"{...}"          <- 읽기는 정상 동작한다
```

여기서 주니어가 가장 자주 막히는 지점이 이것이다. **왜 쓰기는 실패하고 읽기는 되는가?** 오류가 났으면 다 나야 자연스러워 보이는데 그렇지 않다.

이유는 Redis가 **명령마다 "이 명령은 메모리를 더 쓸 수 있는 명령인가"라는 표시를 미리 붙여두기** 때문이다. Redis 내부에는 모든 명령의 목록이 있고, 각 명령에 성격을 나타내는 표식이 달려 있다. 그중 하나가 "메모리를 늘릴 수 있음"이라는 표식이다. 메모리가 상한에 닿아 자리를 확보하지 못하면, Redis는 **그 표식이 붙은 명령만 골라 거부**한다.

```
[명령이 들어옴]
      |
      v
  메모리가 maxmemory를 넘었고, 축출로도 자리를 못 만들었는가?
      |
   아니오 --> 정상 실행
      |
     예
      v
  이 명령에 "메모리를 늘릴 수 있음" 표식이 붙어 있는가?
      |
   아니오 --> 정상 실행       (GET, DEL, TTL, EXISTS ...)
      |
     예 --> OOM 에러 반환      (SET, LPUSH, INCR, HSET, SADD ...)
```

`SET`, `LPUSH`, `INCR`, `HSET`은 값을 새로 넣거나 자료구조를 키우므로 표식이 붙어 있다. 그래서 `OOM command not allowed when used memory > 'maxmemory'.`로 실패한다. 반면 `GET`은 있는 값을 읽어 돌려줄 뿐이고 `DEL`은 오히려 메모리를 **줄이므로** 표식이 없다. 그래서 그대로 동작한다.

서비스 관점에서 이 반쪽 장애가 어떻게 보이는지가 중요하다.

- **캐시 put 실패** — 코드가 이 예외를 감싸두지 않았다면 캐시에 저장하는 그 줄에서 예외가 터져 **조회 API 자체가 500**을 낸다. DB에서 데이터를 이미 잘 읽어왔는데도 응답을 못 준다.
- **세션 저장 실패** — 로그인은 세션을 Redis에 **쓰는** 동작이다. 그래서 **신규 로그인이 전면 불가**가 된다. 반면 이미 로그인한 사용자는 세션을 **읽기만** 하므로 멀쩡히 서비스를 쓴다. 사내에서 테스트하는 사람들은 이미 로그인 상태라 "잘 되는데요?"라고 말하게 되는 구간이다.
- **분산 락 획득 실패** — 분산 락은 보통 `SET key value NX`(없을 때만 쓰기)로 잡는다. 이것도 쓰기이므로 실패하고, 락이 필요한 기능 전체가 정지한다.

"캐시가 꽉 찼을 뿐인데 로그인이 안 되는" 장애가 정확히 이 경로다.

### 1-3. 갈래 ② `maxmemory` + eviction 정책 — 키를 지우며 버틴다

`allkeys-lru` 같은 정책이 걸려 있으면 Redis는 에러를 내는 대신 **기존 키를 지워 자리를 만들고 쓰기를 성공시킨다.** 캐시 전용 인스턴스라면 이것이 장애가 아니라 **정상 동작**이다. 캐시는 원래 지워져도 DB에서 다시 읽어오면 그만인 데이터니까.

문제는 세 가지 상황에서 생긴다.

**(1) 혼합 사용의 함정.** 캐시와 세션·분산 락·쿠폰 발급 카운터가 한 인스턴스에 같이 있으면, `allkeys-lru`는 이 둘을 구분하지 못한다. LRU는 "가장 오래 안 쓴 키"를 지울 뿐이고, 한동안 활동이 없던 사용자의 세션이 딱 그 조건에 들어맞는다.

결과는 **에러 한 줄 없이 사용자가 무작위로 로그아웃되는** 장애다. 애플리케이션 로그에는 아무것도 안 남는다. Redis 입장에서는 설정대로 정상 동작한 것이고, 애플리케이션 입장에서는 "세션 키를 조회했더니 없더라 = 로그인 안 한 사용자"로 해석될 뿐이기 때문이다. 원인 추적이 지독하게 어려운 이유가 여기 있다 — 아무도 실패하지 않았는데 사용자만 튕긴다.

쿠폰 발급 카운터가 축출되면 더 나쁘다. 카운터가 사라지면 발급 수가 0부터 다시 세지므로 **한정 수량을 초과 발급**하게 된다.

**(2) `volatile-*` 정책의 축출 후보 고갈.** `volatile-lru`처럼 TTL이 걸린 키만 지우는 정책을 골랐는데, 정작 인스턴스 안에 TTL 있는 키가 다 소진되면 어떻게 될까. 지울 후보가 없으므로 Redis는 자리를 못 만들고, **결국 `noeviction`과 똑같이 쓰기 에러로 넘어간다.**

이것이 함정인 이유는 설정 파일만 봐서는 안전해 보이기 때문이다. `volatile-lru`라고 적혀 있으니 "가득 차면 알아서 지우겠지"라고 믿는데, 실제로는 TTL 없는 키가 메모리를 다 먹은 상태였고 그 키들은 축출 대상이 아니라서 갈래 ①의 증상이 그대로 나온다.

**(3) 축출 자체의 2차 효과.** eviction이 격하게 돌면 지우는 작업 자체가 CPU를 먹어 응답 지연이 튄다. 그리고 지워진 캐시만큼 요청이 DB로 내려가므로 **DB 부하가 함께 오른다.** 즉 Redis 메모리 부족이 DB 장애의 방아쇠가 될 수 있다. 이 연결은 19번(캐시 무력화 방어) 문서의 주제로 이어진다.

### 1-4. 갈래 ③ `maxmemory` 미설정 — 스왑과 OOM killer

상한이 없으면 Redis는 데이터가 들어오는 대로 계속 자란다. 그러다 **OS 수준에서** 터진다. 여기서 벌어지는 두 가지는 앞의 두 갈래와 성격이 완전히 다르다 — 앞의 둘은 Redis가 스스로 판단해서 취하는 행동이지만, 이번 둘은 **Redis가 아니라 운영체제가 개입하는** 사건이다.

**첫 번째는 스왑(swap)이다.**

스왑은 물리 메모리가 부족해질 때 **당장 안 쓰는 메모리 페이지를 디스크로 밀어내 공간을 확보하는** OS의 기능이다. 그 자체로는 고마운 기능이다. 일반적인 애플리케이션이라면 잠깐 느려지고 말 일이다.

그런데 Redis에게는 치명적이다. 이유가 두 겹이다.

먼저 **Redis는 메모리에 데이터를 두는 것이 존재 이유**인 데이터베이스다. 디스크로 밀려난 페이지에 접근하는 순간, 나노초 단위였던 메모리 접근이 밀리초 단위의 디스크 접근으로 바뀐다. 메모리 DB의 장점이 통째로 사라진다.

더 결정적인 것은 **Redis가 명령을 하나의 스레드로 순서대로 처리한다**는 점이다. 다시 말해 명령들은 한 줄로 줄을 서 있고 앞사람이 끝나야 뒷사람 차례가 온다. 그래서 스왑에 걸린 명령 하나가 디스크를 기다리는 동안, **그 뒤에 줄 선 모든 요청이 함께 기다린다.** 한 요청의 불운이 전체의 지연이 되는 구조다.

```
[정상 상태 — 모든 데이터가 메모리에]
  요청1 --0.1ms--> 요청2 --0.1ms--> 요청3 --0.1ms-->   총 0.3ms

[스왑 발생 — 요청2의 키가 디스크로 밀려남]
  요청1 --0.1ms--> 요청2 -----10ms(디스크)-----> 요청3 --0.1ms-->  총 10.2ms
                            ^
                            요청3은 아무 잘못이 없는데
                            싱글 스레드라 같이 기다린다
```

이 상태를 "죽지도 않고 살지도 않은" 상태라고 부른다. 헬스체크(`PING`)는 성공하므로 모니터링은 초록불인데 사용자는 응답을 못 받는다. **느려진 Redis가 죽은 Redis보다 나쁘다**는 말이 여기서 나온다. 죽었으면 클라이언트가 즉시 연결 실패를 받고 폴백 경로로 갈 텐데, 느려지면 모두가 그 앞에 줄을 서서 기다리기 때문이다. 이 논점은 19번 문서에서 애플리케이션 스레드 고갈 이야기로 이어진다.

**두 번째는 OOM killer다.**

**OOM killer는 리눅스 커널이 시스템 전체 메모리가 바닥났을 때 프로세스 하나를 골라 강제 종료하는 기능이다.** 이름 그대로 "메모리 부족(Out Of Memory) 상황의 처형자"다. 커널 입장에서는 메모리를 확보할 방법이 더 없을 때, 시스템 전체가 멈추는 것보다 프로세스 하나를 죽이는 쪽이 낫다고 판단하는 것이다.

**그런데 왜 하필 Redis가 뽑히는가.** 커널은 프로세스마다 점수를 매기는데, **메모리를 많이 쓰는 프로세스일수록 높은 점수를 받는다.** 죽였을 때 확보되는 메모리가 가장 크기 때문이다. Redis는 그 서버에서 대체로 가장 큰 메모리 소비자이므로 자연스럽게 1순위 후보가 된다.

이때 벌어지는 일이 앞의 두 갈래와 어떻게 다른지가 핵심이다.

| | 갈래 ① noeviction | 갈래 ② eviction | 갈래 ③ OOM killer |
|---|---|---|---|
| 누가 판단하나 | Redis | Redis | 리눅스 커널 |
| 프로세스 | 살아 있음 | 살아 있음 | **사라짐** |
| 데이터 | 그대로 | 일부 유실 | **전부 증발** (영속화 없으면) |
| 애플리케이션이 받는 것 | OOM 에러 | 정상 응답 (값이 없을 뿐) | 연결 거부 |

**갈래 ①·②는 "느려지거나 일부가 실패하는" 것이고, 갈래 ③은 "프로세스가 통째로 사라지는" 것이다.** 부분 실패가 아니라 인스턴스 전체 다운이고, RDB나 AOF 같은 영속화 설정이 없다면 메모리에 있던 데이터가 전부 증발한다. 대응의 성격이 완전히 달라진다 — ①·②는 설정과 코드로 흡수할 수 있지만 ③은 인스턴스를 다시 띄우고 데이터를 다시 채워 넣는 복구 작업이 된다.

### 1-5. `maxmemory` 안에서도 터진다 — 여유분을 남겨야 하는 네 가지 이유 (가산점 포인트)

"그럼 `maxmemory`를 물리 메모리와 똑같이 잡으면 되는 것 아닌가?" 자연스러운 생각이지만 위험하다.

이유는 하나로 요약된다. **`maxmemory`가 통제하는 것은 Redis가 "데이터"에 쓰는 메모리뿐인데, Redis 프로세스는 데이터 말고도 메모리를 쓴다.** 그 바깥의 몫이 물리 메모리를 밀어내면 결국 갈래 ③(스왑·OOM killer)으로 떨어진다.

데이터 바깥에서 메모리를 먹는 것이 네 가지다.

**(1) fork 자식 프로세스의 copy-on-write 몫.** Redis가 RDB 스냅샷을 저장하거나 AOF 파일을 다시 쓸 때(rewrite), 자기 자신을 복제한 자식 프로세스를 만든다. 이 복제를 fork라고 한다. fork 직후에는 부모와 자식이 같은 메모리 페이지를 공유하므로 추가 메모리가 거의 안 든다. 그런데 **부모(원래 Redis)가 데이터를 변경하면 그 페이지를 복사해서 바꾼다.** 자식이 보고 있는 원본을 훼손하면 안 되기 때문이다. 이것이 copy-on-write, "쓸 때 복사한다"는 이름의 유래다.

그래서 **스냅샷이 도는 동안 쓰기 트래픽이 많을수록 메모리 사용량이 순간적으로 크게 불어난다.** 최악의 경우 스냅샷 도중에 전체 데이터가 한 번씩 바뀌면 메모리가 두 배까지 갈 수 있다. 이 순간이 OOM killer가 방문하는 대표적인 시점이다.

**(2) 클라이언트별 입출력 버퍼.** Redis는 연결된 클라이언트마다 받은 명령과 보낼 응답을 담아둘 버퍼를 갖는다. 클라이언트가 1,000개면 버퍼도 1,000개다. 특히 큰 값을 조회하거나 `KEYS`처럼 방대한 결과를 반환하는 명령이 오면 출력 버퍼가 크게 부풀 수 있다.

**(3) 복제본에 보낼 버퍼.** 복제(replication) 구성이라면 복제본에 전달할 변경 내역을 담아두는 버퍼가 따로 있다. 복제본이 느리거나 잠시 끊기면 이 버퍼가 계속 쌓인다.

**(4) 메모리 단편화.** Redis가 "나는 데이터에 4GB를 쓰고 있다"고 계산해도, OS가 이 프로세스에 실제로 내준 메모리는 5GB일 수 있다. 크고 작은 할당과 해제가 반복되면서 메모리 사이사이에 못 쓰는 빈틈이 생기기 때문이다. 이 차이를 단편화라고 부르며, 다음 절의 지표로 관측한다.

결론은 하나다. **`maxmemory`는 물리 메모리보다 충분히 낮게 잡는다.** 얼마나 낮춰야 하는지는 쓰기 비율과 클라이언트 수에 따라 달라지므로 고정된 숫자로 외우기보다, 위 네 항목이 실제로 얼마나 먹고 있는지를 관측해 정하는 것이 맞다.

## 2. 사전 방어책 — 네 겹의 방어선

### 방어선 1: 용도별 인스턴스 분리 (구조)

**eviction 정책은 인스턴스당 하나다.** 이 한 문장이 이 방어선의 전부다.

한 Redis 인스턴스 안에 "지워도 되는 데이터"와 "지우면 안 되는 데이터"가 섞여 있으면, 어떤 정책을 골라도 한쪽이 틀린다.

```
[한 인스턴스에 섞인 상태]
  캐시 키 (지워도 됨)      +      세션·락·카운터 (지우면 안 됨)
        |                                 |
        +------- allkeys-lru 선택 --------+
        |                                 |
     정답: 안 쓰는 것부터           오답: 세션이 조용히 사라짐
     지우고 계속 서비스
        |                                 |
        +------- noeviction 선택 ---------+
        |                                 |
     오답: 캐시가 못 들어가         정답: 쓰기 에러 + 알람으로
     조회 API가 500                 사람이 대응
```

그래서 인스턴스를 나누고, 각각에 맞는 정책을 준다.

- **캐시 인스턴스**: `allkeys-lru` 또는 `allkeys-lfu`. 가득 차면 안 쓰는 것부터 지우는 것이 정답인 데이터다.
- **세션·원본 인스턴스**: `noeviction` + 넉넉한 용량 + 알람. 여기서는 데이터가 조용히 사라지는 것보다 쓰기 에러를 내고 사람이 개입하는 편이 낫다. **에러는 시끄럽고, 유실은 조용하다.** 시끄러운 실패를 고르는 것이 이 판단의 본질이다.

### 방어선 2: TTL 규율 (누수 차단)

**TTL(Time To Live, 키의 수명) 없는 캐시 키는 메모리 누수다.** 한 번 쓰이고 다시는 조회되지 않는 키가 영원히 남아 자리를 차지한다. 자바의 메모리 누수와 구조가 똑같다 — 아무도 안 쓰는데 회수되지 않는 것.

문제는 이것이 "깜빡함"으로 발생한다는 점이다. TTL을 빼먹은 코드는 정상 동작하므로 리뷰에서도 테스트에서도 안 걸린다. 몇 주 뒤 메모리가 찼을 때야 드러난다. 그러니 개인의 주의력이 아니라 **구조로 막아야** 한다.

```java
// Before: TTL 없는 캐시 put — 이 키가 지워질 계기는 eviction뿐이다.
// noeviction 인스턴스라면 지워질 계기가 아예 없어 영구히 남는다.
redis.set("product:detail:" + id, json);

// After: TTL을 인자로 강제하는 래퍼를 팀 표준으로 둔다.
// TTL 인자가 필수이므로 "깜빡함"이 컴파일 단계에서 불가능해진다.
cacheClient.set("product:detail:" + id, json, Duration.ofMinutes(30));
// 래퍼 내부에서 TTL 미지정·과도한 TTL을 예외로 막거나 기본값을 넣는다.
// 규율을 코드 리뷰가 아니라 타입 시그니처가 강제하게 만드는 것이 요점이다.
```

여기에 더해, TTL이 있어도 남는 "주인 잃은 키"가 있다. 키 이름 규칙을 바꾸면서 버려진 구버전 키(`product:v1:*`), 배치가 만들고 정리하지 않은 임시 키 같은 것들이다. 이런 키는 `SCAN`으로 키 공간을 조금씩 훑어 주기적으로 점검한다.

`SCAN`을 쓰는 이유도 알아두면 좋다. `KEYS *`는 전체 키를 한 번에 훑는 동안 싱글 스레드를 통째로 점유해 **그 사이 모든 요청을 멈춰 세운다.** `SCAN`은 조금씩 끊어 순회하므로 다른 명령이 사이사이 처리된다. 운영 중인 Redis에 `KEYS`를 날리면 안 되는 이유가 이것이다.

### 방어선 3: 관측과 알람 (조기 경보)

**가득 찬 뒤에 아는 것과 70%에서 아는 것의 차이가 장애의 유무를 가른다.** 70%에서 알면 키를 정리하거나 증설할 시간이 있고, 100%에서 알면 이미 사용자가 로그인을 못 하고 있다.

`INFO memory` 명령이 내주는 지표 중 봐야 할 것들을 하나씩 뜯어보자.

**`used_memory` 대비 `maxmemory` 비율.** 가장 기본이고 가장 중요하다. 임계치(예: 70~80%)에서 알람을 건다. 숫자 자체보다 **"조치할 시간이 남아 있는 지점"에서 울리게 하는 것**이 기준이다. 키 정리든 증설이든 사람이 움직이는 데 걸리는 시간을 역산해서 정한다.

**`used_memory`와 `used_memory_rss`의 차이.** 이 둘의 뜻이 다르다는 것을 아는 것이 해석의 출발점이다.

- **`used_memory`**: Redis가 **자기가 데이터에 쓰고 있다고 스스로 계산한** 양이다. Redis가 자기 장부에 적어둔 숫자다.
- **`used_memory_rss`**: **OS가 이 프로세스에 실제로 할당해 준** 물리 메모리 양이다. RSS는 Resident Set Size, "메모리에 상주하고 있는 크기"라는 뜻이다. OS 쪽 장부의 숫자다.

두 장부가 다른 이유는 앞서 본 그대로다 — Redis는 데이터 바깥에서도 메모리를 쓰고, 반납한 메모리가 OS에 즉시 돌아가지 않아 빈틈으로 남기 때문이다.

**`mem_fragmentation_ratio`는 이 둘의 비율(`used_memory_rss` / `used_memory`)이다.** 그래서 이 값 하나로 두 가지 다른 문제를 진단할 수 있다.

```
mem_fragmentation_ratio = used_memory_rss / used_memory

  약 1.0 ~ 1.5   정상 범위. 약간의 단편화는 항상 있다.

  1.5보다 크게 높음
    -> OS가 준 메모리가 데이터보다 훨씬 많다 = 단편화
    -> 빈틈이 많다는 뜻. 큰 값의 잦은 삽입·삭제가 원인인 경우가 많다.

  1.0보다 작음  (여기가 중요하다)
    -> "실제 물리 메모리에 있는 양"이 "데이터라고 계산한 양"보다 적다
    -> 나머지는 어디 갔나? 디스크로 밀려났다는 뜻이다 = 스왑 발생
    -> 1-4의 최악 경로에 이미 진입했다는 신호. 즉시 대응 대상.
```

비율이 1보다 작다는 것이 왜 스왑을 뜻하는지 한 번 더 짚자. Redis는 "나는 4GB어치 데이터를 갖고 있다"고 계산하는데 OS는 "이 프로세스는 물리 메모리에 3GB만 올라와 있다"고 답하는 상황이다. 1GB는 사라진 게 아니라 **디스크로 밀려나 있는** 것이다. 이 지표가 1 아래로 내려가면 응답 시간이 이미 튀고 있을 가능성이 높다.

**`evicted_keys`.** **축출로 지워진 키의 누적 개수**다. Redis가 시작된 이후 eviction 정책에 의해 삭제한 키가 몇 개인지 세는 카운터다. TTL 만료로 자연히 사라진 키는 여기 안 들어간다 — **오직 "자리가 모자라서 강제로 지운" 키만** 센다.

그래서 해석이 명확하다.

- **`noeviction` 인스턴스에서 0이 아니면**: 정책상 축출이 일어날 수 없으므로, 누군가 정책을 바꿨거나 설정이 의도와 다르다는 뜻이다. 즉시 조사 대상이다.
- **캐시 인스턴스에서 값이 증가 중이면**: 이미 메모리가 한계에 닿아 아슬아슬하게 돌고 있다는 뜻이다. 지금 당장 에러는 안 나지만 **캐시 히트율이 떨어지고 있고 그만큼 DB 부하가 오르고 있다.** 증가율이 갑자기 뛰면 "용량 부족 또는 어딘가의 키 누수"를 의심한다.

**big key 감시.** 멤버가 수백만 개인 리스트나 셋 하나가 있으면 용량 계획 자체가 무의미해진다. 게다가 그런 키를 `DEL`로 지우는 순간 싱글 스레드가 오래 붙잡혀 전체 지연이 튄다. `--bigkeys` 스캔 등으로 주기 점검한다.

### 방어선 4: 애플리케이션 방어 (폭발 반경 축소)

앞의 세 방어선을 다 깔아도 캐시는 언젠가 실패한다. 그 전제에서 마지막 방어선은 **캐시 에러가 서비스 에러로 전파되지 않게 막는 것**이다.

```java
// Before: 캐시 put 실패가 그대로 조회 API의 500이 된다
public Product getProduct(Long id) {
    Product p = repository.findById(id);
    redis.set(key(id), serialize(p), TTL);   // OOM 에러가 그대로 위로 전파된다
    return p;
    // DB에서 데이터를 이미 성공적으로 읽어왔는데도,
    // "캐시에 넣어두려던" 부수적 동작 하나 때문에 응답을 못 준다.
}

// After: 캐시는 최선노력(best-effort) — 실패해도 본 기능은 산다
public Product getProduct(Long id) {
    Product p = repository.findById(id);
    try {
        redis.set(key(id), serialize(p), TTL);
    } catch (RedisException e) {
        // 삼키되 반드시 남긴다. 조용히 무시하면 캐시가 몇 주째
        // 동작하지 않고 있어도 아무도 모르는 상태가 된다.
        log.warn("cache put failed, serving without cache", e);
        cacheFailureCounter.increment();   // 메트릭 -> 알람으로 연결
    }
    return p;   // 응답은 정상. 사용자는 조금 느릴 뿐 실패하지 않는다.
}
```

여기서 반드시 함께 말해야 하는 것이 이 방어의 **이면**이다. 캐시 put이 계속 실패하면 캐시에 아무것도 안 쌓이고, 결국 **모든 조회가 DB로 직행**한다. 서비스는 죽지 않았지만 DB가 평소의 몇 배를 맞게 된다.

즉 이 방어선은 "캐시 장애를 DB 부하 문제로 바꿔치기한 것"이다. 그래서 **"DB가 캐시 없는 트래픽을 견딜 수 있는가"**가 곧바로 다음 질문이 된다. 그것이 19번 문서(캐시 무력화 방어)의 주제다. 두 문항이 한 몸이라는 것을 아는 것이 이 방어선의 마무리다.

## 3. 실무 시나리오 — "배포 후 로그인이 안 돼요"

혼합 사용 + `noeviction` 인스턴스에서 전형적으로 벌어지는 사고다. 결론을 먼저 말하지 않고, **증상에서 출발해 어떻게 원인에 도달하는지** 순서대로 따라가 보자.

### 3-1. 들어온 신고

CS로 들어온 문구는 이것뿐이다. **"어제 배포 이후로 로그인이 안 된다는 문의가 늘고 있어요."**

그런데 확인해 보면 이상하다.

- 이미 로그인해 있는 사용자는 아무 문제 없이 서비스를 쓰고 있다.
- 애플리케이션 서버의 5xx 에러율은 평소와 비슷하다.
- Redis에 `PING`을 날리면 `PONG`이 온다. 헬스체크 대시보드는 전부 초록불이다.
- DB도 정상이고 슬로우 쿼리도 없다.

**"다 정상인데 로그인만 안 된다."** 여기서 헤매기 시작한다.

### 3-2. 추적 순서

**① "로그인만 안 된다"에서 공통점을 찾는다.**

작동하는 것과 안 되는 것을 갈라 놓고 본다. 기존 사용자의 조회는 되고, 신규 로그인은 안 된다. 로그인은 세션을 **쓰는** 동작이고 기존 사용자의 요청은 세션을 **읽는** 동작이다. 여기서 가설이 하나 선다 — **"읽기는 되는데 쓰기만 안 되는 상태 아닌가?"**

`PING`이 성공한다는 사실이 왜 도움이 안 됐는지도 이 순간 이해된다. **`PING`은 메모리를 쓰지 않는 명령이라 OOM 상태에서도 성공한다.** 헬스체크가 읽기 계열만 확인하고 있었다면 이 상태를 원천적으로 감지할 수 없다.

**② 가설을 직접 검증한다.**

Redis에 직접 붙어 아무 키나 하나 써 본다.

```
127.0.0.1:6379> SET healthcheck:probe 1 EX 10
(error) OOM command not allowed when used memory > 'maxmemory'.
```

여기서 원인의 성격이 확정된다. 애플리케이션 버그도 네트워크 문제도 아니고 **Redis 메모리 포화**다. 한 줄로 판정이 끝났다.

**③ 얼마나 찼고 정책이 무엇인지 본다.**

```
127.0.0.1:6379> INFO memory
used_memory_human:7.94G
maxmemory_human:8.00G          <- 상한에 거의 닿아 있다
mem_fragmentation_ratio:1.12   <- 단편화는 정상 범위, 스왑도 아니다

127.0.0.1:6379> CONFIG GET maxmemory-policy
1) "maxmemory-policy"
2) "noeviction"                <- 그래서 지우지 않고 쓰기를 거부한 것
```

여기까지로 **"왜 이런 증상이 나오는가"**가 완전히 설명된다. 갈래 ①의 교과서적 전개다.

**④ 그럼 무엇이 메모리를 먹었는가 — 원인을 찾는다.**

증상의 원인은 알았지만 **메모리가 찬 원인**은 아직 모른다. 여기서 멈추고 재시작하면 며칠 뒤 똑같은 일이 반복된다.

키 패턴별로 얼마를 쓰고 있는지 본다. `--bigkeys`로 거대한 키가 있는지, `SCAN`으로 접두사별 키 개수를 세어 어떤 패턴이 비정상적으로 많은지 확인한다.

```
키 패턴별 개수 (SCAN 샘플링)
  session:*                  약 42만 개    (평소 수준)
  cache:product:*            약 31만 개    (평소 수준)
  cache:searchresult:*     약 1,180만 개   <- 어제 배포된 신규 기능
```

그리고 그 키의 TTL을 확인한다.

```
127.0.0.1:6379> TTL cache:searchresult:a3f9...
(integer) -1        <- -1은 "만료 시각이 설정되지 않았다"는 뜻. 영구 키다.
```

**⑤ 결론이 조립된다.**

어제 배포된 검색 결과 캐시가 **TTL 없이** 키를 만들고 있었다. 검색어 조합마다 키가 하나씩 생기므로 증가 속도가 대단히 빨랐고, 하루 만에 남은 메모리를 다 먹었다.

그리고 **세션과 캐시가 같은 인스턴스에 있었기 때문에**, 캐시가 먹어치운 메모리가 곧바로 세션 쓰기의 실패로 나타났다. 캐시 기능의 결함이 인증 기능의 장애가 된 것이다.

### 3-3. 네 방어선이 각각 어느 단계를 끊는가

이 사고가 흥미로운 이유는, 2절의 네 방어선 중 **어느 하나만 있었어도 여기까지 오지 않았다**는 점이다.

```
[신규 기능이 TTL 없는 키를 대량 생성]
        |
        |  <-- 방어선 2 (TTL 규율): 래퍼가 TTL을 강제했다면
        |                          이 키들은 30분 뒤 사라졌다.
        v
[메모리가 서서히 차오름 — 알람이 없어 아무도 모름]
        |
        |  <-- 방어선 3 (알람): 70%에서 울렸다면 배포 당일에
        |                      정리하거나 증설할 시간이 있었다.
        v
[maxmemory 도달 -> 세션 SET 실패 -> 신규 로그인 전면 불가]
        |
        |  <-- 방어선 1 (인스턴스 분리): 세션이 별도 인스턴스에
        |                              있었다면 로그인은 멀쩡했다.
        |                              캐시 인스턴스만 축출이 돌았을 뿐.
        v
[PING OK, DB 정상 -> 원인 추적이 헤맴]
        |
        |  <-- 방어선 4 + 쓰기 헬스체크: 헬스체크가 실제 SET을
        |                              시도했다면 알람이 "Redis 쓰기 실패"를
        |                              바로 가리켰다. 추적 시간이 사라진다.
        v
[장애 인지 -> 원인 파악 -> 복구]
```

면접에서는 이 매핑을 말하는 것이 좋다. 방어책을 목록으로 나열하는 것과, **"이 사고의 이 단계를 이 방어선이 끊는다"**고 연결해 말하는 것은 다르게 들린다. 후자는 실제로 사고를 겪어보고 미리 그려본 사람의 말투다.

## 4. 꼬리질문 대비 포인트

### "noeviction으로 가득 찬 상태에서 읽기도 실패하나요?"

아니다. **메모리를 추가로 쓸 수 있는 명령만 거부된다.** `GET`, `DEL`, `EXPIRE`(수명을 줄이는 방향), `EXISTS` 같은 명령은 그대로 동작한다.

이 비대칭이 나오는 이유는 Redis가 명령마다 "메모리를 늘릴 수 있음" 표식을 미리 붙여두고, 상한을 넘었을 때 그 표식이 붙은 명령만 골라 막기 때문이다.

그래서 이 상태는 **반쪽 장애**가 된다. `PING`이나 `GET`으로 하는 겉보기 헬스체크는 멀쩡히 통과하는데 쓰기 경로만 죽어 있다. 결론은 하나다 — **헬스체크에 실제 쓰기 확인을 포함해야 한다.** 짧은 TTL을 건 프로브 키에 `SET`을 한 번 날려보는 것으로 충분하다.

### "Redis의 LRU는 정확한 LRU인가요?"

아니다. **근사(approximated) LRU**다.

정확한 LRU를 구현하려면 모든 키를 최근 사용 순서로 정렬한 연결 리스트로 관리해야 한다. 키가 하나 접근될 때마다 그 키를 리스트 맨 앞으로 옮겨야 하고, 그 리스트를 유지하는 포인터들이 키마다 추가 메모리를 먹는다. **메모리를 아끼려고 도입한 기능이 메모리를 더 먹는** 역설이 생긴다.

그래서 Redis는 타협한다. 축출이 필요할 때 **키 몇 개를 무작위로 뽑아(샘플링), 그중에서 가장 오래 안 쓴 것을 지운다.** 전체에서 가장 오래된 키가 아니라 "뽑힌 것 중 가장 오래된 키"다. 샘플 개수는 `maxmemory-samples`로 조절하는데, 늘리면 정확도가 오르고 CPU를 더 쓴다. 정확도와 비용 사이의 다이얼인 셈이다.

(가산점 포인트) 여기에 LFU를 얹으면 좋다. **LRU는 "언제 마지막으로 썼는가"만 보므로 한 번의 대량 스캔에 취약하다.** 배치가 상품 100만 건을 한 번씩 훑고 지나가면, 그 100만 개가 전부 "방금 쓴 키"가 되어 원래 자주 쓰이던 인기 키를 밀어낸다. 캐시 히트율이 배치 한 번에 무너지는 것이다. **LFU(`allkeys-lfu`)는 "얼마나 자주 썼는가"를 보므로** 한 번 스쳐간 키는 빈도가 낮아 우선 축출된다. 이 약점 보완 관계까지 말하면 정책 선택을 이유 있게 하는 사람으로 들린다.

### "maxmemory를 물리 메모리와 같게 잡으면 왜 위험한가요?"

**`maxmemory`가 통제하는 것은 데이터에 쓰는 메모리뿐인데, Redis 프로세스는 데이터 바깥에서도 메모리를 쓰기 때문이다.** 그 바깥의 몫이 물리 메모리를 넘기면 OS 레벨에서 스왑이나 OOM killer가 발동한다.

바깥의 몫이 넷이다.

1. **fork 자식의 copy-on-write 몫** — RDB 스냅샷이나 AOF rewrite 중 부모가 변경한 페이지만큼 복사본이 생긴다. 쓰기가 많으면 순간 사용량이 크게 뛴다. 가장 결정적인 항목이다.
2. **클라이언트별 입출력 버퍼** — 연결 수에 비례해 늘고, 큰 응답을 내보낼 때 부푼다.
3. **복제본에 보낼 버퍼** — 복제본이 느리거나 끊기면 계속 쌓인다.
4. **메모리 단편화** — 잦은 할당·해제로 생긴 빈틈. `mem_fragmentation_ratio`로 관측한다.

**`maxmemory`에 딱 맞춰 잡으면 스냅샷이 도는 순간 OOM killer가 방문할 수 있다.** 그리고 이때는 쓰기 몇 개가 실패하는 게 아니라 프로세스가 통째로 사라진다. 여유분을 남기는 것이 원칙이고, 여유의 크기는 쓰기 비율·클라이언트 수를 관측해 정한다.

### "이미 70~80% 알람이 울렸다. 당장 뭘 하나요?"

**단기 대응과 구조 대응을 나눠서 답한다.** 이 구분 자체가 답의 절반이다.

**단기 — 무엇이 먹고 있는지부터 확인한다.** `INFO memory`로 현재 사용량과 단편화 비율을 보고, `--bigkeys`와 `SCAN` 샘플링으로 어떤 키 패턴이 메모리를 점유하는지 찾는다. **원인을 모르는 채 용량부터 올리면 같은 일이 곧 반복된다.**

그다음 TTL 없는 키·버려진 구버전 키를 정리한다. 이때 **대형 컬렉션은 `DEL` 대신 `UNLINK`를 쓴다.** `DEL`은 키를 지우는 작업 전부를 그 자리에서 처리하므로, 멤버가 수백만 개인 키를 지우면 싱글 스레드가 오래 붙잡혀 **전체 요청이 그동안 멈춘다.** `UNLINK`는 키 공간에서 참조만 즉시 끊고 실제 메모리 회수는 백그라운드로 넘긴다. 이름 그대로 "링크만 끊는다"는 뜻이다.

정말 급하면 `maxmemory`를 올린다. 단 **물리 여유 안에서** 올려야 한다. 여기서 물리 메모리에 붙여 올리면 1-5의 이유로 OOM killer를 부르게 되어 상황이 더 나빠진다.

**구조 — 증가 추세를 분석해 용량 증설이나 용도 분리를 계획한다.** 최근 며칠의 사용량 곡선을 보면 "정상적으로 늘어난 것"인지 "새 기능이 누수를 만든 것"인지 갈린다. 전자면 증설, 후자면 해당 키의 TTL 규율을 잡는 것이 답이다.

**"일단 재시작"은 답이 아니다.** 재시작하면 메모리는 즉시 내려간다. 하지만 원인이 누수라면 며칠 뒤 다시 찬다. 게다가 영속화가 없으면 그 순간 캐시가 전부 비어 **모든 요청이 DB로 쏟아지는** 2차 장애를 스스로 만드는 셈이 된다.

### "캐시와 세션이 이미 한 인스턴스에 섞여 운영 중입니다. 어떻게 풀어가나요?" (시니어 변별 포인트)

한 번에 못 바꾼다. 그러니 **이행 계획**을 말해야 한다. "분리해야 합니다"까지만 말하면 문제 인식만 있고 실행 경험은 없는 사람으로 들린다.

**1단계 — 현황 파악.** `SCAN`으로 키 패턴별 개수와 메모리 점유를 샘플링해 캐시와 세션의 비중을 **수치화**한다. 새 인스턴스의 용량을 정하려면 이 숫자가 필요하고, 분리 후에도 캐시 쪽이 여전히 부족할지를 여기서 판단한다.

**2단계 — 신규 인스턴스 준비.** 세션용으로 `noeviction` 인스턴스를 따로 띄운다. 세션이 옮겨 가는 쪽이 되는 이유는, 세션이 "지우면 안 되는" 데이터라 정책 요구가 더 엄격하기 때문이다.

**3단계 — 이중 쓰기 → 읽기 전환 → 구 데이터 소멸 대기.** 여기가 핵심이고, **세션의 TTL 특성을 이관 전략에 활용하는 것**이 판단 포인트다.

```
[3-a] 이중 쓰기 시작
      세션 쓰기를 기존 인스턴스와 신규 인스턴스 양쪽에 한다.
      읽기는 아직 기존에서. 이 시점에는 아무 위험이 없다.
          |
          |  세션 TTL이 30분이라면, 30분 뒤에는 신규 인스턴스에
          |  "살아 있는 모든 세션"이 들어와 있다.
          |  만료된 세션은 옮길 필요가 없기 때문이다.
          v
[3-b] 읽기 전환
      읽기를 신규 인스턴스로 돌린다. 쓰기는 아직 양쪽 유지.
      문제가 생기면 읽기만 되돌리면 되므로 롤백이 안전하다.
          |
          v
[3-c] 이중 쓰기 종료
      기존 인스턴스의 세션 키는 TTL이 지나며 자연 소멸한다.
      명시적으로 지울 필요조차 없다.
```

**세션은 TTL이 있으므로 "이관"이 필요 없다.** 이중 쓰기를 TTL 기간만큼만 유지하면 살아 있는 세션이 자연스럽게 신규 인스턴스에 채워지고, 구 세션은 알아서 사라진다. 데이터를 복사하는 마이그레이션 스크립트도, 다운타임도 필요 없다. 이 점을 짚는 것이 이 답의 핵심이다.

**4단계 — 기존 인스턴스를 캐시 전용으로 확정.** 세션이 빠졌으니 정책을 `allkeys-lru`로 바꾼다. 이제 축출이 돌아도 지워지는 것은 캐시뿐이다.

전체를 한 문장으로 묶으면 이렇다. **분리의 근거는 "eviction 정책 하나로 두 용도를 동시에 만족시킬 수 없다"는 것이고, 무중단 이행의 열쇠는 "세션에는 TTL이 있으므로 기다리면 저절로 넘어간다"는 성질이다.**

## 한 줄 요약

Redis가 가득 찼을 때의 증상은 설정이 결정한다 — `noeviction`이면 "메모리를 늘리는 명령" 표식이 붙은 쓰기만 골라 실패해 로그인이 막히는 반쪽 장애가 되고, eviction 정책이면 (캐시와 세션을 섞어 쓴 경우) 에러 없이 세션이 사라지는 조용한 유실이 되며, `maxmemory` 미설정이면 싱글 스레드가 스왑에 걸려 전체 요청이 줄줄이 밀리거나 커널 OOM killer가 프로세스를 통째로 죽인다 — 그래서 방어는 **용도별 인스턴스 분리와 그에 맞는 eviction 정책, 전 키 TTL 규율, 사용률·`evicted_keys`·단편화 비율 알람, 캐시 실패를 삼키는 애플리케이션 코드**로 가득 차기 전에 겹겹이 깔아둬야 하고, `maxmemory`는 fork의 copy-on-write·클라이언트 버퍼·복제 버퍼·단편화가 데이터 바깥에서 먹는 몫만큼 물리 메모리보다 낮게 잡아야 한다.
