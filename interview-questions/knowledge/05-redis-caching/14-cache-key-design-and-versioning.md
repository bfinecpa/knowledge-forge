# 캐시 키 설계와 키 버저닝 — 캐시는 저장소가 아니라 "배포와 함께 움직이는 계약"이다

> 핵심 관전 포인트: **캐시 키는 `서비스:엔티티:버전:식별자`처럼 계층적
> 네임스페이스로 설계하고, 결과를 가르는 조회 조건(테넌트·사용자·로케일·
> 페이지 등)을 빠짐없이 키에 넣는다 — 하나라도 빠지면 남의 데이터가
> 보이는 사고다. 그리고 배포로 캐시 객체의 구조가 바뀌면 Redis에 남은
> 구버전 데이터를 신버전 코드가 역직렬화하다 실패해 "배포 직후에만
> 터지는 장애"가 된다. 해법은 키에 버전을 넣는 키 버저닝 —
> `member:v2:{id}`처럼 신버전 코드는 새 키 공간을 쓰고 구버전 데이터는
> TTL로 자연 소멸시킨다. 롤링 배포 중 신구 코드가 공존해도 각자 자기
> 버전 키만 읽으므로 서로를 깨뜨리지 않는다.**

---

## 0. 질문 + 의도

**질문**: "캐시 키는 어떻게 설계하나요? 배포로 캐시 데이터 구조가 바뀔
때(역직렬화 실패) 어떻게 대응하나요? (키 버저닝)"

**출제 의도**: 배포로 캐시 객체 구조가 바뀌면 구버전 데이터의 역직렬화
실패가 배포 직후 장애로 나타난다. 키에 버전을 넣어 신구가 공존하게
하는지 — 캐시를 "저장소"가 아니라 "배포와 함께 움직이는 계약"으로
다루는지 본다. 롤링 배포 중 신구 코드가 같은 캐시를 읽는 순간까지
상상하면 상급.

## 1. 캐시 키 설계 원칙 — 키는 곧 데이터의 주소이자 명세다

Redis는 스키마가 없다. 테이블도 컬럼도 없이 키 하나가 "이게 무슨
데이터이고, 누구의 것이고, 어떤 조건으로 만들어졌는지"를 전부 표현해야
한다. 그래서 키 설계는 곧 데이터 모델링이다.

### ① 계층적 네임스페이스 — 구분자로 소속을 표현

```
{서비스/도메인}:{엔티티}:{버전}:{식별자}

member:v1:1234            # 회원 1234의 캐시
ranking:webtoon:v2:daily:2026-08-31   # 일간 웹툰 랭킹
session:a1b2c3...         # 세션
```

관례상 콜론(`:`)으로 계층을 나눈다. 이렇게 하면 ① 키만 보고 무슨
데이터인지 알 수 있고(운영 중 디버깅), ② `SCAN MATCH member:v1:*`처럼
prefix로 특정 그룹만 골라 순회/삭제할 수 있고, ③ 모니터링에서 prefix별
메모리/히트율 집계가 가능해진다. 아무 규칙 없이 만든 키는 "지울 수도,
셀 수도, 추적할 수도 없는" 데이터가 된다.

### ② 결과를 가르는 조건은 전부 키에 — 하나라도 빠지면 데이터 유출

캐시 키의 철칙: **메서드의 반환값을 바꾸는 입력은 전부 키에 들어가야
한다.** 빠진 조건이 있으면 먼저 조회한 사람의 결과를 다른 조건의
사람이 받아간다.

```java
// ❌ 회사(테넌트) 구분 누락 — A사가 채운 캐시를 B사가 받는다
@Cacheable(cacheNames = "menu", key = "#menuId")
public MenuAuth findMenuAuth(Long companyId, Long menuId) { ... }

// ❌ 로케일 누락 — 한국어 사용자가 채운 캐시를 일본어 사용자가 받는다
@Cacheable(cacheNames = "notice", key = "#noticeId")
public NoticeView findNotice(Long noticeId, Locale locale) { ... }

// ✅ 결과에 영향을 주는 입력을 모두 키에 포함
@Cacheable(cacheNames = "menu", key = "#companyId + ':' + #menuId")
public MenuAuth findMenuAuth(Long companyId, Long menuId) { ... }
```

성능 버그가 아니라 **보안 사고**(타사/타인 데이터 노출)로 직결되는
지점이고, 단일 테넌트로 테스트하면 멀쩡해서 기능 테스트로는 못 잡는다.
반대 방향의 실수도 있다 — 결과와 무관한 값(요청 시각, 랜덤 값 등)이
키에 섞이면 매번 다른 키가 되어 히트율이 0%로 떨어진다. "키 = 결과를
결정하는 입력의 집합, 그 이상도 이하도 아니게"가 원칙이다.

### ③ 키 자체의 위생 — 길이, 가변 문자열, big key 회피

- 키는 짧고 예측 가능하게. 사용자 입력 문자열(검색어 등)을 키에 그대로
  넣어야 한다면 해시(예: SHA-256 앞부분)로 정규화해 길이 폭주와 특수문자
  문제를 막는다.
- 컬렉션형 키 하나에 수백만 멤버를 쌓는 설계(big key)는 조회·삭제·
  마이그레이션 전부를 블로킹 폭탄으로 만든다 — 키 설계 단계에서
  샤딩(날짜별·범위별 분할)으로 막는다. (가산점 포인트)

## 2. 배포가 캐시를 깨뜨리는 순간 — 역직렬화 실패 장애의 해부

캐시에는 객체가 **직렬화된 바이트**로 저장된다. 즉 Redis에 들어 있는
데이터는 "그 시점 코드의 클래스 구조"로 찍힌 스냅샷이다. 배포로 클래스
구조가 바뀌면 어떻게 되나:

```java
// 배포 전 코드가 캐시에 저장한 구조
public class ProductView {
    private Long id;
    private String name;
    private int price;          // int였던 필드
}

// 배포 후 코드 — 필드 타입 변경 + 필드 삭제
public class ProductView {
    private Long id;
    private String name;
    private Money price;        // ❌ int → Money 타입 변경
    // name 옆에 있던 필드 하나는 삭제됨
}
```

배포 직후, 신버전 코드가 캐시를 조회하면 **캐시 히트가 성공하는 순간
역직렬화 예외가 터진다.** 여기가 이 문제의 고약한 점이다:

- **캐시 미스면 오히려 정상 동작**한다(DB에서 읽어 새 구조로 저장).
  **히트일 때만 터지므로** 트래픽 많은 인기 데이터일수록 먼저 터진다.
- 테스트/스테이징에서는 캐시가 비어 있거나 신버전 데이터뿐이라
  재현이 안 된다 — **운영 배포 직후에만 나타나는 장애**다.
- Java 기본 직렬화(JdkSerializationRedisSerializer)는 클래스 구조
  변화에 극도로 취약하고(serialVersionUID 불일치 즉시 실패), JSON
  직렬화(GenericJackson2JsonRedisSerializer 등)는 필드 추가에는
  관대하지만 **타입 변경·의미 변경 앞에서는 마찬가지로 깨지거나 —
  더 나쁘게는 — 조용히 잘못된 값으로 읽힌다.**

원인을 한 문장으로: **캐시에 저장된 데이터의 구조는 코드와 함께
배포되지 않는다.** 코드는 새것, 데이터는 옛것 — 이 어긋남이 장애다.

## 3. 대응 — 키 버저닝으로 신구를 공존시킨다

### 정석: 키에 버전을 넣는다

캐시 객체 구조가 바뀌는 배포에서는 키의 버전 세그먼트를 올린다.

```java
// Before: 버전 없는 키 — 구조 변경 배포마다 역직렬화 지뢰밭
String key = "product:" + productId;

// After: 키에 버전 포함 — 구조가 바뀌면 버전을 올린다
static final String CACHE_VERSION = "v2";   // 구조 변경 배포 시 v3으로
String key = "product:" + CACHE_VERSION + ":" + productId;
```

효과의 핵심은 **신버전 코드가 구버전 데이터를 아예 만나지 않는다**는
것이다:

- 신버전 코드는 `product:v2:*`만 읽고 쓴다 — 처음엔 전부 미스라서
  DB에서 읽어 새 구조로 채운다. 역직렬화 실패가 원천 차단된다.
- 구버전 데이터(`product:v1:*`)는 아무도 안 읽게 되고 **TTL이 다하면
  자연 소멸**한다. 지우는 작업조차 필요 없다.
- **롤링 배포 중 신구 코드가 공존해도 안전하다** — 구버전 인스턴스는
  v1을, 신버전 인스턴스는 v2를 각자 읽고 쓰므로 서로의 캐시를 깨뜨리지
  않는다. 롤백해도 마찬가지로 안전하다(구 코드는 여전히 v1을 읽는다).
  이 지점까지 말하면 상급 답변이다.

Spring Cache라면 캐시 이름이나 key prefix에 버전을 넣는다:

```java
// RedisCacheManager 설정에서 캐시 prefix에 버전을 박아두면
// 애플리케이션 전역에 일괄 적용된다
RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
        .computePrefixWith(cacheName -> "myapp:" + cacheName + ":v2:")
        .entryTtl(Duration.ofMinutes(30));
```

버전 값은 손으로 올리는 상수 대신 "캐시 구조에 영향을 주는 변경"과
함께 리뷰되도록 한 곳에 모아 관리한다. 클래스 구조 해시나 배포 버전을
자동으로 쓰는 방법도 있지만, 배포마다 무조건 캐시가 리셋되는(불필요한
cold start) 부작용이 있어 "구조가 실제로 바뀔 때만 수동으로 올리는"
쪽이 실무 절충이다.

### 보조 수단들 — 버저닝과 함께 쓰는 방어선

**① 역직렬화 실패를 캐시 미스로 강등하는 방어 코드.** 버전 올리는 걸
깜빡한 배포에서도 장애 대신 성능 저하로 끝나게 하는 안전망이다.

```java
public Optional<ProductView> getFromCache(String key) {
    try {
        return Optional.ofNullable(redisTemplate.opsForValue().get(key));
    } catch (SerializationException e) {
        redisTemplate.delete(key);            // 깨진 데이터는 지우고
        log.warn("cache deserialization failed, treat as miss: {}", key, e);
        return Optional.empty();              // 미스로 처리 → DB에서 읽어 재적재
    }
}
```

Spring Cache에서는 `CacheErrorHandler`를 커스터마이징해 조회 예외를
미스로 처리하는 같은 효과를 전역으로 걸 수 있다. (가산점 포인트)

**② 구조 변화에 강한 직렬화 포맷 선택.** Java 기본 직렬화는 피하고
JSON을 기본으로 — 필드 추가 정도는 버전 업 없이 흡수된다. 단 JSON도
타입 변경·필드 의미 변경은 못 지켜주므로 "JSON이면 버저닝이 필요
없다"는 오답이다.

**③ 배포 시 전체 flush는 최후의 수단.** `FLUSHDB`나 prefix 일괄 삭제로
깨진 데이터를 치울 수는 있지만, 캐시 전체가 비는 순간 DB가 원래
트래픽을 그대로 맞는다(cold cache → 미스 폭주). 트래픽이 낮은 시간대가
아니면 그 자체가 2차 장애가 된다. 키 버저닝은 이 flush를 "필요 없는
작업"으로 만드는 설계다.

## 4. 꼬리질문 대비 포인트

### "배포할 때마다 캐시를 전부 지우면 간단하지 않나요?"

동작은 하지만 두 가지 비용이 크다. ① cold cache: 캐시 히트율을 전제로
용량이 설계된 시스템에서 캐시가 비는 순간 DB가 전체 트래픽을 직격으로
맞는다 — 트래픽이 높은 시간대 배포라면 그 자체가 장애다. ② 롤링 배포와
충돌: flush 후에도 아직 구버전 인스턴스가 남아 있으면 구버전이 다시
구 구조로 캐시를 채우고, 신버전이 그걸 읽다 또 깨진다. 키 버저닝은
flush 없이(cold cache 없이) 신버전만 새 공간에서 점진적으로 캐시를
채우게 하므로 두 문제를 다 피한다.

### "롤링 배포 중 신구 코드가 같은 캐시를 읽으면 정확히 무슨 일이 벌어지나요?" (시니어 변별 포인트)

버전 없는 키라면 양방향으로 깨진다. ① 구버전 인스턴스가 구 구조로
저장 → 신버전 인스턴스가 히트해서 역직렬화 실패. ② 반대로 신버전이
신 구조로 저장 → 구버전 인스턴스가 히트해서 실패. 즉 배포가 진행되는
내내 양쪽 모두에서 산발적으로 에러가 나고, **롤백해도 신 구조 데이터가
캐시에 남아 있어 롤백 후에도 장애가 계속된다** — "롤백했는데 왜 안
낫지?"가 이 사고의 전형적 전개다. 키 버저닝이면 신구가 각자의 키
공간을 쓰므로 배포 중에도, 롤백 후에도 서로 간섭이 없다. 이 "롤백
안전성"까지 짚는 것이 상급이다.

### "키에 버전을 넣으면 전환 기간 동안 메모리가 이중으로 들지 않나요?"

맞다 — v1과 v2가 공존하는 동안(최대 구버전 TTL만큼) 그 캐시의 메모리가
일시적으로 최대 2배가 된다. 그래서 ① 메모리 여유가 빠듯하면 배포 후
구버전 prefix를 `SCAN` + `UNLINK`로 점진 삭제해 회수 기간을 줄이고
(`KEYS`는 금지 — 운영 블로킹), ② maxmemory와 eviction 정책(예:
allkeys-lru)이 설정돼 있는지 확인해 최악의 경우에도 OOM이 아니라
오래된 키부터 밀려나게 해둔다. "일시적 2배 메모리"는 역직렬화 장애를
피하는 값싼 보험료라는 게 결론이다.

### "JSON 직렬화를 쓰면 버저닝 없이도 되지 않나요?"

부분적으로만 맞다. JSON은 필드 추가(구 데이터에 없는 필드 → 기본값)와
필드 삭제(모르는 필드 무시)에는 관대하다. 하지만 ① 필드 타입 변경
(int → 객체), ② 같은 필드의 의미/단위 변경(원 → 달러), ③ enum 상수
제거 같은 변경은 예외가 나거나 — 더 위험하게는 — **조용히 잘못된
값으로 읽힌다.** 예외는 눈에 띄기라도 하지, 의미가 바뀐 값이 정상처럼
서빙되는 쪽이 더 나쁜 사고다. 그래서 실무 규칙은 "JSON을 기본 포맷으로
쓰되, 하위 호환이 깨지는 변경에는 반드시 키 버전을 올린다"이다.

### "버전을 올려야 하는 변경인지 아닌지, 어떻게 리뷰에서 잡나요?"

캐시에 들어가는 DTO를 별도 패키지/네이밍으로 격리해 "이 클래스 변경 =
캐시 계약 변경"이 리뷰에서 보이게 하는 게 첫걸음이다. 판단 기준은 API
하위 호환성과 동일하다 — 필드 추가는 호환(버전 유지 가능), 타입 변경·
삭제·의미 변경은 비호환(버전 업). 여기에 역직렬화 실패를 미스로
강등하는 CacheErrorHandler를 전역 안전망으로 깔아두면, 사람이 놓친
경우에도 장애가 아니라 "일시적 히트율 저하 + 경고 로그"로 끝난다.
사람의 규율과 구조적 안전망을 겹치는 것이 정답이다.

## 한 줄 요약

캐시 키는 계층적 네임스페이스에 "결과를 가르는 조건 전부 + 버전"을
담는 계약서다 — 조건이 빠지면 남의 데이터가 보이고, 버전이 없으면
구조 변경 배포 순간 구버전 데이터의 역직렬화 실패가 "배포 직후에만,
히트일 때만, 롤백해도 안 낫는" 장애로 터지므로, 키 버저닝으로 신구
코드가 각자의 키 공간을 쓰게 해 구데이터는 TTL로 자연 소멸시키는 것이
캐시를 배포와 함께 움직이는 계약으로 다루는 방법이다.
