# 캐시 키 설계와 키 버저닝 — 캐시는 저장소가 아니라 "배포와 함께 움직이는 계약"이다

> 핵심 관전 포인트: **캐시 키는 `서비스:엔티티:버전:식별자`처럼 계층적 네임스페이스로 설계하고, 결과를 가르는 조회 조건(테넌트·사용자·로케일·페이지 등)을 빠짐없이 키에 넣는다 — 하나라도 빠지면 먼저 조회한 사람이 채운 캐시를 다른 조건의 사람이 받아가는, 성능 버그가 아니라 데이터 유출 사고가 된다. 그리고 배포로 캐시 객체의 구조가 바뀌면 Redis에 남아 있던 구버전 데이터를 신버전 코드가 자기 클래스로 역직렬화하다 실패하고, 그 예외가 캐시 미스로 강등되지 않고 요청 전체를 500으로 떨어뜨려 "배포 직후에만, 캐시 히트일 때만 터지는 장애"가 된다. 해법은 키에 버전을 넣는 키 버저닝 — `member:v2:{id}`처럼 신버전 코드는 새 키 공간을 쓰고 구버전 데이터는 TTL로 자연 소멸시킨다. 롤링 배포로 신구 코드가 몇 분간 공존해도 각자 자기 버전 키만 읽으므로 서로를 깨뜨리지 않고, 롤백해도 안전하다. 대가는 전환 기간(구버전 TTL) 동안 같은 데이터가 두 벌 존재해 메모리가 최대 2배가 된다는 것이다.**

---

## 0. 질문 + 의도

**질문**: "캐시 키는 어떻게 설계하나요? 배포로 캐시 데이터 구조가 바뀔 때(역직렬화 실패) 어떻게 대응하나요? (키 버저닝)"

**출제 의도**: 배포로 캐시 객체 구조가 바뀌면 구버전 데이터의 역직렬화 실패가 배포 직후 장애로 나타난다. 키에 버전을 넣어 신구가 공존하게 하는지 — 캐시를 "저장소"가 아니라 "배포와 함께 움직이는 계약"으로 다루는지 본다. 롤링 배포 중 신구 코드가 같은 캐시를 읽는 순간까지 상상하면 상급.

## 1. 캐시 키 설계 원칙 — 키는 곧 데이터의 주소이자 명세다

### 1-1. 왜 키 설계가 데이터 모델링인가

RDB에는 스키마가 있다. `product` 테이블의 `price` 컬럼이 `numeric`이라는 사실이 DB 안에 선언돼 있고, 어긋나는 값은 DB가 거부한다.

Redis에는 그런 것이 없다. 테이블도 컬럼도 타입 선언도 없이 **키 하나가 "이게 무슨 데이터이고, 누구의 것이고, 어떤 조건으로 만들어졌는지"를 전부 표현해야 한다.** 키 이름이 곧 스키마이자 계약서인 셈이다.

그래서 키 설계는 이름 짓기가 아니라 데이터 모델링이다. 그리고 이 계약서에 조항이 하나 빠지면, 뒤에서 볼 것처럼 곧바로 사고가 된다.

### 1-2. 원칙 ① 계층적 네임스페이스 — 구분자로 소속을 표현한다

```
{서비스/도메인}:{엔티티}:{버전}:{식별자}

member:v1:1234                        # 회원 1234의 캐시
ranking:webtoon:v2:daily:2026-08-31   # 일간 웹툰 랭킹
session:a1b2c3...                     # 세션
```

관례상 콜론(`:`)으로 계층을 나눈다. 이렇게 하면 얻는 것이 셋이다.

첫째, **키만 보고 무슨 데이터인지 알 수 있다.** 새벽 두 시에 메모리를 잡아먹는 키를 발견했을 때 그 키가 무엇인지 코드를 뒤지지 않고 알 수 있느냐가 대응 속도를 가른다.

둘째, **prefix로 특정 그룹만 골라 순회하거나 지울 수 있다.** `SCAN MATCH member:v1:*`처럼 접두사로 묶이지 않으면 "회원 캐시만 비우기" 같은 운영 작업이 불가능해진다.

셋째, **모니터링에서 prefix별 메모리·히트율 집계가 가능해진다.** 어느 캐시가 메모리를 얼마나 쓰고 히트율은 얼마인지를 그룹 단위로 볼 수 있어야 튜닝 대상을 고를 수 있다.

아무 규칙 없이 만든 키는 **"지울 수도, 셀 수도, 추적할 수도 없는" 데이터**가 된다. 잘 동작하는 동안에는 아무 문제가 없다가, 문제가 생긴 그 순간에 손댈 방법이 없다는 것이 이 실수의 성격이다.

### 1-3. 원칙 ② 결과를 가르는 조건은 전부 키에 — 하나라도 빠지면 남의 데이터가 보인다

여기가 이 문서에서 **가장 직접적으로 사고로 이어지는 지점**이다.

철칙은 한 문장이다. **메서드의 반환값을 바꾸는 입력은 전부 키에 들어가야 한다.** 왜 그런지는 원칙으로 외울 것이 아니라 사고가 나는 과정을 한 번 따라가 보면 몸에 남는다.

메뉴 권한 조회 메서드가 있다. 회사(테넌트) ID와 메뉴 ID를 받아 그 회사가 그 메뉴에 어떤 권한을 갖는지 돌려준다. 그런데 캐시 키에 메뉴 ID만 넣었다.

```java
// Before: 회사(테넌트) 구분이 키에서 빠졌다.
// 반환값은 companyId에 따라 달라지는데, 키는 menuId만 보고 있다.
@Cacheable(cacheNames = "menu", key = "#menuId")
public MenuAuth findMenuAuth(Long companyId, Long menuId) { ... }
```

이 코드에서 무슨 일이 벌어지는지 요청 순서로 그려 보면 이렇다.

```
[요청 1]  A사 사용자가 메뉴 7번 권한을 조회
          findMenuAuth(companyId=100, menuId=7)
          캐시 키 = "menu::7"          <- companyId가 어디에도 없다
          미스 -> DB 조회 -> A사 기준 권한(쓰기 허용)을 이 키에 저장

[요청 2]  B사 사용자가 같은 메뉴 7번 권한을 조회
          findMenuAuth(companyId=200, menuId=7)
          캐시 키 = "menu::7"          <- 요청 1이 만든 것과 완전히 같은 키
          히트! -> DB를 보지도 않고 A사의 권한을 그대로 반환

          결과: B사 사용자의 화면에 A사 기준으로 계산된 권한이 뜬다
                B사에서는 막혀 있어야 할 메뉴가 열린다
```

이 사고의 성질을 세 가지로 정리하면 심각성이 분명해진다.

**(1) 성능 버그가 아니라 보안 사고다.** 캐시 값이 단순 조회 데이터였다면 "남의 데이터가 화면에 뜨는" 정보 유출이고, 지금처럼 권한 데이터였다면 **인가 우회**다. 로그인은 B사 계정으로 했는데 A사 기준으로 판정된 권한을 들고 다니게 된다.

**(2) 간헐적이지 않다.** 캐시가 살아 있는 TTL 동안 **먼저 채운 쪽이 계속 이긴다.** "가끔 이상하다"가 아니라 "TTL 동안 확정적으로 틀리다"이므로 피해 범위가 크다.

**(3) 기능 테스트로는 절대 못 잡는다.** 테스트는 대개 단일 테넌트로 돈다. `companyId=100`으로만 테스트하면 키가 충돌할 상대가 없어서 영원히 통과한다. **테스트에 두 개 이상의 테넌트가 등장하지 않는 한 이 버그는 코드 리뷰로만 잡힌다.**

로케일도 정확히 같은 구조의 사고를 만든다.

```java
// Before: 로케일 누락 — 한국어 사용자가 채운 캐시를 일본어 사용자가 받는다.
// 첫 조회자가 한국인이면 그 TTL 동안 전 세계가 한국어 공지를 본다.
@Cacheable(cacheNames = "notice", key = "#noticeId")
public NoticeView findNotice(Long noticeId, Locale locale) { ... }
```

고치는 방법은 단순하다. **반환값을 바꾸는 입력을 전부 키에 넣는다.**

```java
// After: 결과에 영향을 주는 입력을 모두 키에 포함한다.
// companyId가 다르면 키가 달라지므로 서로의 캐시를 만날 수 없다.
@Cacheable(cacheNames = "menu", key = "#companyId + ':' + #menuId")
public MenuAuth findMenuAuth(Long companyId, Long menuId) { ... }

// After: 로케일도 같은 원리. locale이 결과를 바꾸므로 키에 들어간다.
@Cacheable(cacheNames = "notice", key = "#noticeId + ':' + #locale")
public NoticeView findNotice(Long noticeId, Locale locale) { ... }
```

리뷰에서 쓸 수 있는 점검 문장으로 바꾸면 이렇다. **"이 메서드의 파라미터 중 반환값을 바꾸는 것이 무엇인가? 그것이 전부 키에 있는가?"** 파라미터가 아니어도 결과를 바꾸는 것(현재 로그인 사용자, 요청 헤더의 로케일, 스레드 로컬의 테넌트 컨텍스트)이 있다면 그것도 포함이다. 오히려 파라미터가 아닌 암묵적 입력이 더 위험하다 — 메서드 시그니처만 보고는 안 보이기 때문이다.

### 1-4. 반대 방향의 실수 — 결과와 무관한 값이 키에 섞이면

빠뜨리는 것만 문제가 아니다. 반대로 **결과에 영향을 주지 않는 값**(요청 시각, 랜덤 값, 트레이스 ID 등)이 키에 섞이면 매 요청마다 다른 키가 만들어진다.

그러면 캐시는 항상 미스가 되고, 그 위에 **아무도 다시 읽지 않을 데이터가 계속 쌓여** 메모리까지 먹는다. 히트율 0%짜리 캐시는 없는 것보다 나쁘다 — DB 부하는 그대로인데 Redis 왕복 시간과 메모리만 추가로 낸다.

그래서 원칙은 양방향이다. **키 = 결과를 결정하는 입력의 집합, 그 이상도 이하도 아니게.**

### 1-5. 원칙 ③ 키 자체의 위생 — 길이, 가변 문자열, big key 회피

- 키는 짧고 예측 가능하게 만든다. 사용자 입력 문자열(검색어 등)을 키에 그대로 넣어야 한다면 해시(예: SHA-256 앞부분)로 정규화해 **길이 폭주와 특수문자 문제**를 막는다. 검색어가 그대로 키가 되면 수 KB짜리 키가 생길 수도 있고, 콜론이 섞인 입력이 계층 구분자를 망가뜨릴 수도 있다.
- 컬렉션형 키 하나에 수백만 멤버를 쌓는 설계(big key)는 조회·삭제·마이그레이션 전부를 블로킹 폭탄으로 만든다. Redis는 명령을 단일 스레드로 처리하므로 큰 값 하나를 다루는 동안 다른 모든 명령이 대기한다. 키 설계 단계에서 샤딩(날짜별·범위별 분할)으로 막는다. (가산점 포인트)

## 2. 배포가 캐시를 깨뜨리는 순간 — 역직렬화 실패 장애의 해부

### 2-1. 전제 — 캐시에는 객체가 아니라 바이트가 들어 있다

Redis에 자바 객체를 그대로 넣을 수는 없다. 객체를 바이트 배열로 펼쳐서(직렬화) 저장하고, 꺼낼 때 그 바이트를 다시 객체로 되살린다(역직렬화).

여기서 결정적인 사실 하나. **저장된 바이트는 "그 시점 코드의 클래스 구조"로 찍힌 스냅샷이다.** 어떤 필드가 어떤 순서로 어떤 타입으로 있었는지가 그 바이트에 반영돼 있다.

그리고 또 하나. **캐시는 배포 대상이 아니다.** 애플리케이션을 새 버전으로 교체해도 Redis 안의 바이트는 그대로 남아 있다. 코드는 새것, 데이터는 옛것 — 이 어긋남이 장애의 씨앗이다.

```java
// 배포 전(v1) 코드가 캐시에 저장한 구조
public class ProductView {
    private Long id;
    private String name;
    private int price;          // 이때는 int였다
    private String category;    // v2에서 삭제될 필드
}

// 배포 후(v2) 코드 — 필드 타입 변경 + 필드 삭제
public class ProductView {
    private Long id;
    private String name;
    private Money price;        // int -> Money 객체로 타입이 바뀌었다
    // category 필드는 삭제됐다
}
```

### 2-2. 왜 배포 직후에만 터지는가 — 단계로 풀면

```
① 배포 전 (v1 인스턴스만 떠 있음)
   v1이 ProductView{id, name, price:int, category}를 직렬화해 Redis에 저장.
   TTL 30분. 인기 상품일수록 이 데이터가 계속 갱신되며 살아 있다.

② 배포 (애플리케이션만 v2로 교체)
   Redis는 아무것도 바뀌지 않는다. ①이 넣은 바이트가 그대로 남아 있다.

③ 배포 직후 첫 요청
   v2 코드가 "product:1234" 조회 -> 캐시 히트
   (①이 넣어 둔 바이트가 아직 TTL 안이므로 당연히 히트한다)
   그 바이트를 v2의 ProductView 클래스로 되살리려 시도
   price 자리에 정수가 들어 있는데 v2는 Money 객체를 기대한다 -> 예외

④ 예외가 캐시 미스로 처리되지 않는다  <- 여기가 핵심
   요청은 500으로 끝난다. (2-3에서 자세히)

⑤ TTL 30분이 지나 ①의 데이터가 전부 만료되면 저절로 멎는다
   "아무것도 안 했는데 30분 뒤에 나았다"는 사후 분석을 어렵게 만든다
```

이 장애의 성질을 세 가지로 정리한다.

**(1) 캐시 미스면 오히려 정상이다.** 미스면 DB에서 읽어 v2 구조로 새로 저장하므로 아무 문제가 없다. **히트일 때만 터진다.** 그래서 조회가 많은 인기 데이터일수록 먼저, 그리고 많이 터진다. 히트율이 99%인 인기 키라면 그 엔드포인트로 오는 요청의 99%가 500이 된다는 뜻이다.

**(2) 테스트와 스테이징에서는 재현되지 않는다.** 그 환경의 캐시는 비어 있거나 이미 v2 데이터뿐이다. 구버전 코드가 채워 놓은 데이터가 실제로 쌓여 있는 곳은 운영 환경밖에 없다. **운영 배포 직후에만 나타나는 장애**라는 성격이 여기서 나온다.

**(3) 배포 자체는 성공으로 보인다.** 헬스 체크는 통과하고 파드는 정상 기동한다. 깨지는 것은 캐시를 읽는 특정 경로뿐이라, 배포 파이프라인상으로는 초록불인데 에러율만 치솟는 그림이 된다.

### 2-3. 왜 미스가 아니라 500이 되는가

"역직렬화가 실패했으면 캐시에 없는 셈 치고 DB에서 읽으면 되지 않나"가 자연스러운 기대다. 그런데 기본 동작은 그렇지 않다.

Spring Cache에서 캐시 조회 중 발생한 예외를 처리하는 것은 `CacheErrorHandler`인데, **기본 구현은 예외를 그대로 위로 다시 던진다.** 캐시 계층에서 삼키지 않는다는 뜻이다.

그래서 흐름이 이렇게 된다.

```
Redis에서 바이트를 읽음
  -> 직렬화기가 v2 클래스로 변환 시도 -> 예외 발생
  -> 기본 CacheErrorHandler가 예외를 그대로 던짐
  -> @Cacheable이 감싼 메서드는 아예 실행되지 않는다
  -> 서비스 -> 컨트롤러 -> 500 응답
```

**메서드 본문이 실행조차 되지 않는다**는 점이 중요하다. `@Cacheable`은 "캐시를 먼저 보고 없으면 메서드를 부른다"는 구조인데, 캐시를 보는 단계에서 예외가 터졌으므로 "없으면"까지 도달하지 못한다. DB는 멀쩡하고 쿼리는 문제없는데 **캐시 하나 때문에 기능 전체가 죽는 것**이다.

이 기본값을 뒤집는 것이 3-5의 보조 수단이다. 다만 순서를 분명히 해 두자 — 그것은 **안전망이지 해법이 아니다.** 해법은 애초에 신버전 코드가 구버전 데이터를 만나지 않게 하는 키 버저닝이다.

### 2-4. JDK 직렬화와 JSON 직렬화는 다르게 실패한다

직렬화 방식에 따라 이 장애의 얼굴이 달라진다. 이 차이를 구분해 말할 수 있어야 "그럼 JSON 쓰면 되는 거 아닌가"라는 흔한 오해를 정리할 수 있다.

**JDK 기본 직렬화(`JdkSerializationRedisSerializer`)는 즉시, 시끄럽게 실패한다.** 자바 직렬화 바이트에는 `serialVersionUID`라는 클래스 구조의 지문이 함께 박힌다. 클래스에 이 값을 명시하지 않으면 컴파일러가 필드·메서드 구성을 바탕으로 자동 계산하는데, **필드를 하나만 추가해도 값이 달라진다.** 역직렬화 시점에 바이트에 박힌 값과 현재 클래스의 값이 다르면 그 자리에서 예외다. 설령 `serialVersionUID`를 손으로 고정해 두었더라도, 위 예시처럼 `int price`가 `Money price`로 바뀌면 타입이 맞지 않아 결국 실패한다.

**JSON 직렬화는 설정에 따라 조용히 살아남을 수 있고, 그게 더 나쁠 수 있다.** JSON에는 필드 이름과 값만 있고 클래스 구조의 지문이 없다. 그래서 모르는 필드를 만났을 때 어떻게 할지가 설정에 달려 있다.

- **알 수 없는 필드를 무시하도록 설정한 경우**: v1이 남긴 `category` 필드를 v2가 무시하고 넘어간다. 예외 없이 통과한다.
- **v2에서 새로 추가된 필드**: v1이 저장한 JSON에는 그 필드가 아예 없으므로 객체 필드에 `null`(원시 타입이면 0)이 들어간다. **예외도 로그도 없이.**

두 번째가 진짜 함정이다. 예외는 스택 트레이스가 남고 알람이 울리지만, 조용히 `null`이 들어간 값은 **한참 뒤 엉뚱한 곳에서 `NullPointerException`으로 나타나거나, 더 나쁘게는 0으로 계산된 금액이 정상처럼 서빙된다.** "터지는 버그"보다 "틀린 값을 성공적으로 응답하는 버그"가 훨씬 찾기 어렵고 피해도 크다.

여기서 결론이 나온다. **"JSON을 쓰면 버저닝이 필요 없다"는 오해다.** JSON이 관대한 것은 필드 추가와 삭제라는 좁은 범위뿐이다. 다음은 JSON도 못 막는다.

- **필드 타입 변경**(`int` → 객체): 값을 객체로 읽을 수 없어 예외가 난다.
- **같은 필드의 의미·단위 변경**(금액 단위를 원에서 달러로): 타입도 이름도 그대로라 **아무도 못 알아채고**, 1,200원이 1,200달러가 된다.
- **enum 상수 제거**: 사라진 상수 이름이 담긴 데이터를 만나면 예외가 난다.

정확한 규칙은 이것이다. **JSON을 기본 포맷으로 쓰되, 하위 호환이 깨지는 변경에는 반드시 키 버전을 올린다.** JSON은 "버저닝이 필요한 횟수를 줄여 주는 도구"이지 버저닝의 대체재가 아니다.

### 2-5. 롤링 배포 — 신구 코드가 공존하는 몇 분

지금까지는 "v1이 남긴 데이터를 v2가 읽는" 한 방향만 봤다. 실제 배포는 순간에 끝나지 않는다. **롤링 배포는 인스턴스를 한 대씩 교체하므로, 그 몇 분 동안 v1과 v2가 동시에 떠서 같은 Redis를 본다.** 그러면 오염이 양방향으로 일어난다.

```
t0   v1 인스턴스 4대. 캐시에는 v1 구조 데이터만 있다. 정상.

t1   1대를 v2로 교체 -> v1 3대 + v2 1대 공존
     v2가 캐시 히트  -> v1 구조 데이터를 읽다 실패 -> 500
     v2가 캐시 미스  -> DB에서 읽어 v2 구조로 저장
                       ★ 이 순간부터 캐시에 v2 구조 데이터가 섞이기 시작한다

t2   v1 인스턴스가 그 키를 조회 -> 히트 -> v2 구조 데이터를 읽다 실패 -> 500
     ★ 이제 양방향으로 깨진다.
       v1도 v2도 상대가 남긴 데이터에 걸려 넘어진다.
       어느 인스턴스로 요청이 갔느냐에 따라 성공과 실패가 뒤섞이므로
       "산발적으로 500이 난다"는 재현 불가능해 보이는 증상이 된다.

t3   전량 v2 교체 완료. 그래도 t1 이전에 v1이 남긴 데이터가
     TTL 동안 살아 있어 산발적 500이 계속된다.

t4   "장애다, 롤백하자" -> 전량 v1으로 복귀
     그런데 캐시에는 t1~t3 동안 v2가 채워 놓은 신 구조 데이터가 가득하다
     -> v1이 그것을 읽다 실패
     ★ 롤백했는데 장애가 안 낫는다
```

`t4`가 이 사고의 가장 악명 높은 지점이다. 장애 대응의 첫 번째 카드인 롤백이 통하지 않는다. **캐시라는 공유 상태가 코드 버전과 독립적으로 존재하기 때문에, 코드만 되돌려서는 세상이 원래대로 돌아가지 않는다.**

정리하면 원인은 한 문장이다. **캐시에 저장된 데이터의 구조는 코드와 함께 배포되지도, 함께 롤백되지도 않는다.**

## 3. 대응 — 키 버저닝으로 신구를 공존시킨다

### 3-1. 정석: 키에 버전을 넣는다

캐시 객체 구조가 바뀌는 배포에서는 키의 버전 세그먼트를 올린다.

```java
// Before: 버전 없는 키 — 구조 변경 배포마다 2-5의 지뢰밭을 밟는다
String key = "product:" + productId;

// After: 키에 버전을 포함한다.
// 캐시에 들어가는 클래스의 구조가 바뀌는 배포에서 v3으로 올린다.
static final String CACHE_VERSION = "v2";
String key = "product:" + CACHE_VERSION + ":" + productId;
```

효과의 핵심은 한 문장으로 요약된다. **신버전 코드가 구버전 데이터를 아예 만나지 않는다.** 2절에서 본 모든 문제가 "만나기 때문에" 생겼으므로, 만나지 않게 하면 전부 사라진다.

```
v1 인스턴스:  product:v1:1234 만 읽고 쓴다
v2 인스턴스:  product:v2:1234 만 읽고 쓴다
              ↑ 키 이름이 다르므로 서로 다른 데이터다. 만날 수가 없다.
```

이것이 2-5의 타임라인에 어떻게 작용하는지 대비해 보면 값이 분명해진다.

- `t1` (공존 시작): v2는 `product:v2:*`를 보는데 아무것도 없다 → **전부 미스** → DB에서 읽어 v2 구조로 채운다. 역직렬화 실패가 일어날 여지가 없다. v1은 여전히 `product:v1:*`를 보고 자기 구조 데이터만 만난다.
- `t2` (양방향 오염): 애초에 두 키 공간이 겹치지 않으므로 **오염이라는 사건 자체가 없다.**
- `t3` (전량 교체 후): `product:v1:*`는 아무도 읽지 않게 되고 **TTL이 다하면 자연 소멸한다.** 지우는 작업조차 필요 없다.
- `t4` (롤백): v1으로 되돌리면 v1은 다시 `product:v1:*`를 본다. 자기가 이해할 수 있는 구조의 데이터만 있다. **롤백이 제대로 작동한다.**

이 "롤백 안전성"까지 말할 수 있으면 상급 답변이다. 키 버저닝의 값어치는 배포 중 몇 분을 넘기는 데 있는 것이 아니라, **문제가 생겼을 때 되돌릴 수 있게 만드는 데** 있다.

### 3-2. Spring Cache에 적용하기

키를 문자열로 직접 조립하지 않고 `@Cacheable`을 쓴다면, 캐시 이름이나 key prefix에 버전을 넣는다.

```java
// RedisCacheManager 설정에서 prefix에 버전을 박아 두면
// 개별 @Cacheable을 하나하나 고치지 않고 전역에 일괄 적용된다.
RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
        // 실제 키가 "myapp:product:v2:1234" 형태로 만들어진다
        .computePrefixWith(cacheName -> "myapp:" + cacheName + ":v2:")
        .entryTtl(Duration.ofMinutes(30));
```

전역 적용은 편하지만 대가가 있다. **버전을 올리면 모든 캐시가 한꺼번에 새 공간으로 옮겨 간다** — 구조가 바뀌지 않은 캐시까지 전부 미스가 되어 다시 채워야 한다. 캐시 종류가 많고 그중 하나만 바뀌었다면 캐시 이름 단위로 버전을 관리하는 편이 낫다.

### 3-3. 버전 값을 어떻게 관리하나

버전을 손으로 올리는 상수로 두면 깜빡할 수 있다. 그래서 "캐시 구조에 영향을 주는 변경"과 함께 리뷰에 걸리도록 **한 곳에 모아** 관리한다.

자동화하고 싶은 유혹도 생긴다. 클래스 구조 해시나 배포 버전을 자동으로 키에 넣으면 사람이 깜빡할 일이 없다. 그런데 이 방법에는 명확한 부작용이 있다 — **구조가 안 바뀐 배포에서도 캐시가 통째로 리셋된다.** 하루에 몇 번씩 배포하는 팀이라면 그때마다 캐시가 비고, 그 순간마다 DB가 전체 트래픽을 맞는다(cold cache). 배포가 곧 장애 위험이 되는 셈이다.

그래서 실무 절충은 **"구조가 실제로 바뀔 때만 수동으로 올리고, 깜빡한 경우를 3-5의 안전망으로 받는다"**가 된다.

### 3-4. 대가 — 전환 기간의 이중 메모리

키 버저닝이 공짜는 아니다. **전환 기간 동안 같은 데이터가 두 벌 존재한다.**

```
배포 전     product:v1:*  만 존재            메모리 4GB 사용
배포 직후   product:v1:*  (아무도 안 읽지만 TTL까지 남아 있다)
          + product:v2:*  (새로 채워지는 중)
            -> 최대 8GB까지 부푼다
TTL 경과    product:v1:*  전부 만료 소멸      다시 4GB로 복귀
```

**부푼 상태가 유지되는 기간은 구버전 데이터의 TTL만큼이다.** TTL 30분짜리 캐시라면 배포 완료 후 최대 30분이다. TTL을 하루로 잡아 둔 캐시라면 하루 동안 메모리가 두 배라는 뜻이므로, TTL이 길수록 이 대가가 커진다는 점을 함께 계산해야 한다.

메모리 여유가 빠듯하면 두 가지로 대응한다.

- **회수 기간을 줄인다.** 배포 후 구버전 prefix를 `SCAN` + `UNLINK`로 점진 삭제한다. `KEYS`는 전체 키스페이스를 한 번에 훑으며 서버를 블로킹하므로 운영에서 금지다. `UNLINK`는 삭제를 백그라운드 스레드에 넘기므로 큰 값을 지울 때도 서버가 멈추지 않는다.
- **최악의 경우를 OOM이 아니라 축출로 만든다.** `maxmemory`와 eviction 정책(예: `allkeys-lru`)이 설정돼 있는지 확인한다. 설정돼 있으면 메모리가 차더라도 오래된 키부터 밀려날 뿐이지만, 설정이 없으면 쓰기가 거부되거나 프로세스가 죽는다.

결론은 이렇다. **"일시적 2배 메모리"는 역직렬화 장애와 롤백 불능을 피하는 값싼 보험료다.**

### 3-5. 보조 수단 ① — 역직렬화 실패를 캐시 미스로 강등한다

2-3에서 본 대로 기본 동작은 예외를 위로 던지는 것이다. 이 기본값을 뒤집어 두면, **버전 올리는 걸 깜빡한 배포에서도 장애 대신 성능 저하로 끝난다.**

```java
public Optional<ProductView> getFromCache(String key) {
    try {
        return Optional.ofNullable(redisTemplate.opsForValue().get(key));
    } catch (SerializationException e) {
        // 읽을 수 없는 데이터는 남겨 둘 이유가 없다.
        // 지워야 다음 요청이 DB에서 읽어 새 구조로 다시 채운다.
        redisTemplate.delete(key);
        // 조용히 넘기면 안 된다. 이 로그가 "버전을 안 올렸다"는 유일한 신호다.
        log.warn("cache deserialization failed, treat as miss: {}", key, e);
        // 빈 결과 = 캐시 미스. 호출부는 평소처럼 DB에서 읽는다.
        return Optional.empty();
    }
}
```

Spring Cache를 쓴다면 같은 효과를 `CacheErrorHandler`를 커스터마이징해 전역으로 걸 수 있다. 조회 예외를 미스로 처리하도록 바꾸는 것이다. (가산점 포인트)

다만 이것을 해법으로 착각하면 안 된다. 이 안전망만 있고 버저닝이 없으면 **배포 직후 캐시 전체가 한 번씩 실패하고 지워지므로 사실상 전면 flush와 같아진다** — 장애는 면하지만 DB가 그 순간 전체 트래픽을 맞는 위험은 남는다.

### 3-6. 보조 수단 ② — 구조 변화에 강한 직렬화 포맷을 고른다

2-4의 결론대로, **JDK 기본 직렬화는 피하고 JSON을 기본으로 쓴다.** 필드 추가·삭제 정도는 버전 업 없이 흡수되므로 버전을 올려야 하는 횟수 자체가 줄어든다.

단, JSON도 타입 변경과 의미 변경 앞에서는 무력하고 오히려 조용히 틀린 값을 서빙할 수 있으므로 **"JSON이면 버저닝이 필요 없다"는 오답이다.**

### 3-7. 보조 수단 ③ — 배포 시 전체 flush는 최후의 수단

`FLUSHDB`나 prefix 일괄 삭제로 깨진 데이터를 치울 수는 있다. 하지만 두 가지 문제가 있다.

**(1) cold cache.** 캐시 전체가 비는 순간 DB가 원래 트래픽을 그대로 맞는다. 캐시 히트율 99%를 전제로 용량이 잡힌 시스템이라면 DB에 평소의 100배가 몰린다는 뜻이다. 트래픽이 낮은 시간대가 아니면 그 자체가 2차 장애가 된다.

**(2) 롤링 배포와 충돌한다.** flush를 해도 아직 v1 인스턴스가 남아 있으면 v1이 다시 구 구조로 캐시를 채우고, v2가 그걸 읽다 또 깨진다. **flush는 한 시점의 청소일 뿐이고 오염원은 아직 살아 있다.**

키 버저닝은 이 flush를 **"필요 없는 작업"으로 만드는 설계**다. 신버전은 애초에 빈 키 공간에서 시작하므로 청소할 대상이 없고, 구 데이터는 아무도 안 읽는 채로 TTL을 기다리다 사라진다.

## 4. 꼬리질문 대비 포인트

### "배포할 때마다 캐시를 전부 지우면 간단하지 않나요?"

동작은 하지만 비용이 두 가지 크다.

**① cold cache.** 캐시 히트율을 전제로 용량이 설계된 시스템에서 캐시가 비는 순간 DB가 전체 트래픽을 직격으로 맞는다. 트래픽이 높은 시간대 배포라면 그 자체가 장애다.

**② 롤링 배포와 충돌.** flush 후에도 아직 구버전 인스턴스가 남아 있으면 구버전이 다시 구 구조로 캐시를 채우고, 신버전이 그걸 읽다 또 깨진다. 오염원이 살아 있는 한 청소는 한 번으로 끝나지 않는다.

키 버저닝은 flush 없이(따라서 cold cache 없이) 신버전만 새 공간에서 **점진적으로** 캐시를 채우게 하므로 두 문제를 모두 피한다.

### "롤링 배포 중 신구 코드가 같은 캐시를 읽으면 정확히 무슨 일이 벌어지나요?" (시니어 변별 포인트)

버전 없는 키라면 **양방향으로 깨진다**(2-5의 타임라인).

① 구버전 인스턴스가 구 구조로 저장 → 신버전 인스턴스가 히트해서 역직렬화 실패. ② 반대로 신버전이 신 구조로 저장 → 구버전 인스턴스가 히트해서 실패.

즉 배포가 진행되는 내내 양쪽 모두에서 산발적으로 에러가 난다. 어느 인스턴스로 요청이 갔느냐에 따라 성패가 갈리므로 재현이 안 되는 것처럼 보인다.

가장 아픈 지점은 그다음이다. **롤백해도 신 구조 데이터가 캐시에 남아 있어 롤백 후에도 장애가 계속된다.** "롤백했는데 왜 안 낫지?"가 이 사고의 전형적 전개이고, 이때는 캐시를 직접 지우기 전까지 낫지 않는다.

키 버저닝이면 신구가 각자의 키 공간을 쓰므로 배포 중에도, 롤백 후에도 서로 간섭이 없다. 이 **롤백 안전성**까지 짚는 것이 상급이다.

### "키에 버전을 넣으면 전환 기간 동안 메모리가 이중으로 들지 않나요?"

**맞다.** v1과 v2가 공존하는 동안 그 캐시의 메모리가 일시적으로 최대 2배가 되고, 그 기간은 **구버전 데이터의 TTL만큼**이다. TTL 30분이면 30분, 하루면 하루다.

그래서 두 가지로 관리한다. ① 메모리 여유가 빠듯하면 배포 후 구버전 prefix를 `SCAN` + `UNLINK`로 점진 삭제해 회수 기간을 줄인다(`KEYS`는 서버를 블로킹하므로 운영 금지, `UNLINK`는 삭제를 백그라운드로 넘긴다). ② `maxmemory`와 eviction 정책(예: `allkeys-lru`)이 설정돼 있는지 확인해, 최악의 경우에도 OOM이 아니라 오래된 키부터 밀려나게 해 둔다.

**"일시적 2배 메모리"는 역직렬화 장애와 롤백 불능을 피하는 값싼 보험료**라는 게 결론이다.

### "JSON 직렬화를 쓰면 버저닝 없이도 되지 않나요?"

**부분적으로만 맞다.** JSON은 필드 추가(구 데이터에 없는 필드 → 기본값)와 필드 삭제(모르는 필드 무시 설정 시)에는 관대하다.

하지만 다음은 못 막는다. ① 필드 타입 변경(`int` → 객체)은 예외가 난다. ② 같은 필드의 의미·단위 변경(원 → 달러)은 타입도 이름도 그대로라 **아무도 못 알아채고 조용히 잘못된 값으로 읽힌다.** ③ enum 상수 제거는 사라진 이름을 만나면 예외가 난다.

그리고 JSON이 "관대하게" 넘어가는 경우도 마냥 좋은 게 아니다. **v2에서 새로 추가한 필드는 구 데이터에 없으므로 `null`로 들어오고, 예외도 로그도 없다.** 예외는 알람이라도 울리지만, 의미가 바뀐 값이 정상처럼 서빙되는 쪽이 훨씬 찾기 어렵고 피해가 크다.

그래서 실무 규칙은 **"JSON을 기본 포맷으로 쓰되, 하위 호환이 깨지는 변경에는 반드시 키 버전을 올린다"**이다. JSON은 버저닝의 대체재가 아니라 버저닝 횟수를 줄여 주는 도구다.

### "버전을 올려야 하는 변경인지 아닌지, 어떻게 리뷰에서 잡나요?"

첫걸음은 **캐시에 들어가는 DTO를 별도 패키지나 네이밍으로 격리**하는 것이다. 그러면 "이 클래스를 고쳤다 = 캐시 계약을 고쳤다"가 diff에서 눈에 보인다. 엔티티를 그대로 캐시에 넣으면 이 신호가 사라진다 — 도메인 로직 때문에 필드를 고쳤을 뿐인데 캐시 계약이 함께 깨지고, 리뷰어는 그 사실을 알아챌 단서가 없다.

판단 기준은 **API 하위 호환성과 동일하다.** 필드 추가는 호환(버전 유지 가능), 타입 변경·삭제·의미 변경은 비호환(버전 업).

여기에 역직렬화 실패를 미스로 강등하는 `CacheErrorHandler`를 전역 안전망으로 깔아 두면, 사람이 놓친 경우에도 장애가 아니라 **"일시적 히트율 저하 + 경고 로그"**로 끝난다.

**사람의 규율과 구조적 안전망을 겹치는 것이 정답이다.** 규율만 있으면 언젠가 놓치고, 안전망만 있으면 놓친 줄도 모른 채 성능이 새어 나간다.

---

## 한 줄 요약

캐시 키는 계층적 네임스페이스에 "결과를 가르는 조건 전부 + 버전"을 담는 계약서다 — 조건이 빠지면 먼저 채운 사람의 결과를 다른 조건의 사람이 받아가 남의 데이터가 화면에 뜨고, 버전이 없으면 구조 변경 배포 순간 구버전 데이터의 역직렬화 실패가 캐시 미스로 강등되지 않고 500으로 터져 "배포 직후에만, 히트일 때만, 롤백해도 안 낫는" 장애가 되므로, 키 버저닝으로 신구 코드가 각자의 키 공간을 쓰게 하고 구데이터는 TTL로 자연 소멸시키되 그 기간 동안의 이중 메모리를 대가로 인정하는 것이 캐시를 배포와 함께 움직이는 계약으로 다루는 방법이다.
