# KEYS vs SCAN — 편한 명령의 시간 복잡도를 확인하는 습관

> 핵심 관전 포인트: **Redis는 싱글 스레드 이벤트 루프라서 명령 하나가
> 실행되는 동안 다른 모든 요청이 줄을 선다. `KEYS`는 전체 키 공간을
> 한 번에 훑는 O(N) 명령이라, 키가 수백만 개인 운영 서버에서 치면
> 그 수 초 동안 Redis 전체가 멈추고 — 캐시를 보던 모든 서비스가
> 동시에 타임아웃난다. 대안인 `SCAN`은 커서 기반으로 키 공간을
> 조금씩 나눠 순회한다. 호출 한 번은 짧게 끝나고 그 사이사이에 다른
> 명령이 끼어들 수 있어서, 전체를 다 도는 총량은 같아도 서비스를
> 세우지 않는다. 운영에서는 `rename-command`로 KEYS를 아예 봉인하고,
> 애초에 패턴 검색이 필요 없도록 키 목록을 Set 등으로 따로 관리하는
> 설계까지 가면 상급이다.**

---

## 0. 질문 + 의도

**질문**: "`KEYS` 명령을 운영에서 쓰면 안 되는 이유와 대안(`SCAN`)은?"

**출제 의도**: 운영 Redis에 KEYS 한 방으로 전 서비스가 수 초 멈춘
사고는 업계 단골이다. "편한 명령의 시간 복잡도"를 확인하는 습관이
있는지 — 사고를 안 쳐본 티가 나는지 본다. 빠른 이유(싱글 스레드
이벤트 루프)와 느려지는 이유(O(N) 명령의 블로킹)가 동전의 양면임을
연결해서 말할 수 있는지가 관전 포인트다.

## 1. 왜 위험한가 — 싱글 스레드 + O(N)의 조합

Redis가 빠른 이유는 모든 명령을 **싱글 스레드 이벤트 루프**가 메모리
위에서 처리하기 때문이다. 락도 컨텍스트 스위칭도 없다. 그런데 이
구조의 대가가 있다: **명령 하나가 오래 걸리면 그 시간만큼 서버 전체가
멈춘다.** 계산대가 하나뿐인 마트에서 한 손님이 카트 3개 분량을
계산하는 동안 뒷줄 전체가 기다리는 것과 같다.

`KEYS pattern`은 이 구조에서 최악의 손님이다:

- **전체 키 공간을 처음부터 끝까지 훑는 O(N)** 명령이다. 패턴에
  매칭되는 키가 하나뿐이어도, 매칭 여부를 확인하려면 모든 키를
  검사해야 한다.
- 키 수백만~수천만 개면 이 순회에 **수 초**가 걸리고, 그동안 GET
  하나도 처리되지 않는다.
- 결과가 크면 응답을 만들어 클라이언트로 보내는 비용(메모리 할당,
  네트워크 버퍼)까지 얹힌다.

전형적인 사고 시나리오:

```text
1. 운영 이슈 조사 중 "특정 유저 캐시가 몇 개나 있지?" 궁금해짐
2. redis-cli에서 KEYS user:12345:*  ← 개발 환경에선 즉시 나왔음
3. 운영은 키가 2,000만 개 → Redis가 3초간 정지
4. 캐시를 보던 모든 API가 동시에 타임아웃 → 커넥션 풀 고갈
5. 캐시 미스 폭주로 DB까지 부하 전이 → 장애 전파
```

핵심은 "KEYS가 나쁜 명령"이 아니라 **"개발 환경에서 빠르던 명령이
데이터 크기에 비례해 느려진다"는 사실을 치기 전에 확인하는 습관**이다.
같은 계열로 big key에 대한 `SMEMBERS`/`HGETALL`, `FLUSHALL`,
긴 Lua 스크립트도 모두 싱글 스레드를 세우는 블로킹 폭탄이다
(big key는 `23-big-key-risk-and-unlink.md` 참고).

## 2. 대안 — SCAN의 동작 원리와 보장

`SCAN`은 **커서 기반 점진 순회**다. 전체를 한 번에 훑는 대신, 호출
한 번에 키 공간의 일부만 보고 "다음에 어디부터 볼지"를 커서로
돌려준다.

```text
SCAN 0 MATCH user:12345:* COUNT 1000
→ 1) "17408"          ← 다음 커서
  2) 매칭된 키 목록 (이번 구간에서 찾은 것만, 0개일 수도 있음)

SCAN 17408 MATCH user:12345:* COUNT 1000
→ ... 반복 ...

SCAN <커서> ... 가 커서 0을 돌려주면 순회 완료
```

- **호출 한 번은 짧다.** COUNT(기본 10)는 "이번에 검사할 해시 버킷
  수의 힌트"이고, 한 호출이 검사하는 양이 제한되므로 이벤트 루프를
  오래 점유하지 않는다.
- **호출과 호출 사이에 다른 클라이언트의 명령이 끼어든다.** 전체 순회
  총비용은 KEYS와 비슷하거나 오히려 크지만, 잘게 쪼개져 있어서
  서비스가 멈추지 않는다 — 이것이 KEYS와의 본질적 차이다.
- 컬렉션 내부용 형제 명령이 있다: `SSCAN`(Set), `HSCAN`(Hash),
  `ZSCAN`(Sorted Set). big key 내부를 훑을 때도 같은 원리를 쓴다.

SCAN의 보장은 "느슨한" 편이라 정확히 알아야 한다:

- **순회 시작부터 끝까지 계속 존재한 키는 반드시 반환된다** (누락
  없음).
- **같은 키가 중복 반환될 수 있다** — 순회 중 rehashing(키 증감으로
  해시 테이블이 리사이즈)이 일어나면 발생. 호출 측에서 중복 제거
  (Set에 모으기)가 필요하다.
- 순회 중에 추가/삭제된 키는 나올 수도, 안 나올 수도 있다 —
  스냅샷이 아니다.

애플리케이션 코드 예시 (Spring Data Redis):

```java
// Before: 운영 금지 패턴 — 전체 키 공간 블로킹
Set<String> keys = redisTemplate.keys("user:12345:*"); // 내부적으로 KEYS

// After: SCAN 커서 순회 — 이벤트 루프를 점유하지 않음
Set<String> keys = new HashSet<>();   // 중복 반환 대비 Set에 수집
ScanOptions options = ScanOptions.scanOptions()
        .match("user:12345:*")
        .count(1000)                  // 힌트일 뿐, 반환 개수 보장 아님
        .build();
try (Cursor<String> cursor = redisTemplate.scan(options)) {
    cursor.forEachRemaining(keys::add);
}
```

주의: SCAN도 **공짜가 아니다.** 루프를 지연 없이 최대 속도로 돌리면
CPU를 상당히 먹고, COUNT를 너무 크게 주면 한 호출이 길어져 KEYS에
가까워진다. 운영 중 대량 순회 작업(키 마이그레이션, 일괄 삭제)은
호출 사이에 짧은 대기를 넣거나 트래픽이 적은 시간대에 돌린다.

## 3. 운영 방어선 — 명령 봉인과 "검색이 필요 없는 설계"

### 사고를 시스템으로 막기

사람의 습관에만 기대지 않고 구조로 막는다:

```text
# redis.conf — KEYS를 아예 못 치게 봉인 (FLUSHALL 등도 함께)
rename-command KEYS ""
rename-command FLUSHALL "OPS-FLUSHALL-20xx"   # 운영자만 아는 이름으로

# ACL 사용 시 (Redis 6+): 애플리케이션 계정에서 위험 명령 차단
acl setuser app-user on >password ~* +@all -keys -flushall -flushdb
```

이미 느린 명령이 실행됐는지 추적할 때는 `SLOWLOG GET`으로 확인한다 —
"Redis가 순간 멈췄다"는 장애의 원인 조사에서 첫 번째로 보는 곳이다.

### 애초에 패턴 검색이 필요 없게 설계하기 (가산점 포인트)

운영 코드가 주기적으로 SCAN을 돌리고 있다면 그 자체가 설계 신호다.
Redis는 검색 엔진이 아니라 key-value 저장소라, **"어떤 키들이
있는지"를 알아야 한다면 그 목록을 별도 자료구조로 직접 관리**하는
것이 정석이다.

```java
// Before: "유저의 세션 키들"을 매번 패턴 검색으로 찾음
scan("session:user123:*")  // 주기적 SCAN — 부하 + 코드 복잡

// After: 키 목록을 Set으로 인덱싱 — O(1)~O(멤버 수) 직접 조회
redis.opsForSet().add("user:123:sessions", sessionKey); // 세션 생성 시 등록
Set<String> keys = redis.opsForSet().members("user:123:sessions"); // 즉시 조회
// 세션 삭제 시 Set에서도 제거 (또는 Set 자체에 TTL)
```

일괄 무효화가 목적이라면 패턴 삭제 대신 **키 버저닝**(키에 버전을
넣고 버전만 올리면 구버전은 TTL로 자연 소멸)이 SCAN+DEL보다
훨씬 싸고 안전하다.

## 4. 꼬리질문 대비 포인트

### "SCAN도 결국 전체 키를 다 도는데, 왜 KEYS보다 안전한가요?"

총 작업량이 아니라 **점유 시간의 분포**가 다르기 때문이다. KEYS는
전체 순회를 이벤트 루프 한 턴에 통째로 잡고 있어 그동안 아무도
처리되지 않지만, SCAN은 한 호출이 짧게 끝나고 호출 사이사이에 다른
클라이언트 명령이 처리된다. 지연의 총합은 비슷해도 "수 초짜리 정지
1번"과 "수 마이크로초짜리 지연 수만 번"은 서비스 입장에서 전혀 다른
사건이다 — 전자는 타임아웃·장애, 후자는 눈에 안 띄는 백그라운드
작업이다.

### "SCAN의 COUNT는 반환 개수를 보장하나요? 순회 중 키가 바뀌면 어떻게 되나요?"

COUNT는 "이번 호출에서 검사할 내부 버킷 수의 힌트"일 뿐, 반환되는 키
개수가 아니다. MATCH 필터는 검사 후에 적용되므로 COUNT 1000이어도
매칭 결과가 0개일 수 있다 — "빈 결과 = 순회 끝"이 아니라 **커서가
0일 때만 끝**이라는 점이 실무 버그 포인트다. 순회 중 변경에 대한
보장은: 처음부터 끝까지 존재한 키는 반드시 반환, 중복 반환 가능
(rehashing 시), 도중에 생기거나 지워진 키는 미보장. 그래서 결과는
Set으로 모아 중복을 제거하고, 정확한 스냅샷이 필요한 용도로는 쓰지
않는다.

### "운영에서 특정 패턴의 키를 수백만 개 지워야 한다면 어떻게 하나요?"

SCAN으로 배치를 잘라 가며 지운다: SCAN으로 키를 1000개 단위로 얻고,
`UNLINK`(DEL 대신 — 비동기 해제)로 지우고, 배치 사이에 짧은 대기를
넣어 부하를 흘려보낸다. 애초에 이런 작업이 예상되는 키라면 만들 때
TTL을 걸어 자연 소멸시키거나, 키 버저닝으로 "삭제 없이 버리는"
구조를 택하는 것이 더 좋은 답이다. 대량 삭제 자체의 위험은
`23-big-key-risk-and-unlink.md`에서 다룬다.

### "KEYS 말고도 운영에서 조심해야 할 블로킹 명령은 뭐가 있나요?" (시니어 변별 포인트)

원리로 답한다 — **"데이터 크기에 비례하는 O(N) 명령 + 싱글 스레드"
조합은 전부 같은 폭탄**이다:

- big key에 대한 `SMEMBERS`, `HGETALL`, `LRANGE 0 -1`, `ZRANGE 0 -1`
  — 컬렉션 전체 반환.
- `DEL`도 컬렉션 멤버 수에 비례한다 — 수백만 멤버 Set의 DEL은 블로킹.
- `FLUSHALL`/`FLUSHDB` (ASYNC 옵션 없이), 무거운 `SORT`,
  `SUNION`/`SINTER` 같은 집합 연산.
- 긴 **Lua 스크립트** — 실행 중엔 어떤 명령도 끼어들 수 없다.
- 명령은 아니지만 같은 축: RDB 스냅샷 fork 순간의 지연, 대량
  만료(expire) 처리.

"각 명령의 문서에서 시간 복잡도를 확인하고, O(N)이면 N의 운영 상한을
따져보는 습관"이 이 질문 계열 전체의 한 줄 답이다. 모니터링으로는
`SLOWLOG`와 latency 지표로 이런 명령의 흔적을 잡는다고 덧붙이면
가산점.

## 한 줄 요약

KEYS는 싱글 스레드 Redis에서 전체 키 공간을 한 턴에 훑는 O(N)
블로킹 명령이라 운영에서 치면 서비스 전체가 수 초 멈추고, SCAN은
같은 순회를 커서로 잘게 쪼개 사이사이 다른 명령이 처리되게 한다 —
그리고 진짜 상급 답변은 rename-command로 KEYS를 봉인하고, 키 목록을
Set으로 인덱싱해 **애초에 패턴 검색이 필요 없는 설계**로 가는 것이다.
