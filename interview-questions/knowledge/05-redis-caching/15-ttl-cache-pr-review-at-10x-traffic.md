# TTL 1시간 캐시 PR 리뷰 — "테스트 통과"가 보증하지 않는 것: 트래픽 10배에서의 붕괴 지점

> 핵심 관전 포인트: **테스트 통과는 "요청 하나가 기능적으로 맞다"는 증명일 뿐이고, 캐시가 무너지는 방식은 전부 동시성과 규모에서 나오므로 테스트에는 애초에 등장하지 않는 조건이다. 인기 목록처럼 모두가 같은 키 하나를 보는 캐시는 트래픽 10배에서 세 곳이 무너진다 — ① 키가 하나면 만료 시각도 하나뿐이라 매 정시마다 전 서버의 미스가 동시에 터지는 캐시 스탬피드(1시간마다 반복되는 정기 미니 장애), ② 배포·재시작 직후 캐시가 빈 채로 전체 트래픽을 맞는 cold cache, ③ 키 하나에 조회가 집중돼 클러스터로도 못 나누는 hot key. 여기에 TTL 1시간이라는 신선도 결정이 비즈니스와 합의된 것인지도 물어야 한다. `sync = true`는 JVM 안에서만 유효한 잠금이라 서버가 10대면 재계산이 10번 남으므로 완화이지 해결이 아니다. 그리고 이 지식의 결과물은 개념 설명이 아니라 동료의 PR에 실제로 남길 문장이며, 그 문장은 "지금 코드가 틀렸다"가 아니라 "트래픽 조건이 바뀌면 여기가 깨진다 + 이렇게 보완하자"의 형태여야 한다.**

---

## 0. 질문 + 의도

**질문**: "동료의 PR: 인기 목록 조회를 TTL 1시간 캐시로 감쌌고 테스트도 통과했습니다. 트래픽이 10배가 되면 생길 수 있는 문제를 리뷰 코멘트로 남겨보세요."

**출제 의도**: 캐시 스탬피드 개념 문항과 짝을 이루는 상황 인지 검사. "지금 잘 동작하는 코드"에서 트래픽 조건이 바뀌었을 때의 붕괴 지점 (동시 만료, 미스 폭주)을 배포 전에 말할 수 있는지 — 지식이 리뷰 코멘트라는 실행 가능한 형태로 나오는지 본다.

## 1. 왜 "테스트 통과"가 안전을 보증하지 못하는가

이 문항은 지식을 묻는 것이 아니라 **지식의 출력 형태**를 묻는다. 최종 산출물은 개념 설명이 아니라 **동료의 PR에 그대로 붙일 수 있는 문장**이고, 3절이 그 문장이다. 1~2절은 그 문장을 쓰기 위해 필요한 근거다.

### 1-1. 리뷰 대상 코드

PR의 코드는 대략 이런 모양일 것이다.

```java
@Cacheable(cacheNames = "popularList")   // TTL 1시간은 CacheManager 설정에
public List<Product> getPopularList() {
    return productRepository.findPopular();   // 비싼 집계 쿼리
}
```

한 줄 어노테이션이고, 잘못된 곳이 없다. 테스트도 통과한다. **이 코드는 지금 트래픽에서는 정말로 맞는 코드다.** 리뷰가 어려운 이유가 여기 있다 — 틀린 것을 찾는 게 아니라, **조건이 바뀌면 틀려지는 것**을 찾아야 한다.

### 1-2. 테스트가 검증하는 것과, 여기서 터지는 것

기능 테스트가 검증하는 것은 이것이다. "첫 호출은 DB를 읽고, 두 번째 호출은 캐시를 읽는다."

이 검증이 성립하는 세계를 정확히 보자. **테스트는 요청을 하나씩 순서대로 넣고 출력을 확인한다.** 입력 하나에 출력 하나를 대응시키는 구조이므로, 검증하는 대상은 **"요청 하나의 정확성"**이다.

그런데 캐시가 무너지는 방식은 전부 다른 두 축에서 나온다.

- **동시성**: 같은 순간에 몇 개의 요청이 겹치는가. 만료되는 그 찰나에 동시에 미스를 보는 요청이 1개인지 500개인지.
- **규모**: 캐시가 비었을 때 DB가 감당해야 하는 배수가 얼마인지.

**이 두 축은 단위 테스트에 아예 등장하지 않는다.** 등장하지 않는 조건에서 문제가 나오므로, 테스트가 통과하는 것은 당연하고 통과했다는 사실이 아무것도 보증하지 않는다. "테스트 통과 = 배포 가능"이 성립하지 않는 이유는 테스트가 부실해서가 아니라 **검증 대상의 축 자체가 다르기 때문**이다.

```
단위 테스트가 서는 축:   요청 1개  ->  출력이 맞는가          (정확성)
캐시가 무너지는 축:      요청 500개가 같은 순간에 겹치면?      (동시성)
                         캐시가 0%일 때 DB가 버티는가?         (규모)
```

### 1-3. 그럼 무엇으로 잡는가

축이 다르다는 진단이 나왔으면 처방도 그 축에서 나와야 한다.

**부하 테스트.** 동시성과 규모를 인위적으로 만들어 보는 것이 유일한 사전 검증이다. 다만 "그냥 부하를 준다"로는 부족하고, **시나리오에 "캐시 만료 직후"와 "cold cache 상태"를 명시적으로 포함**시켜야 한다. 캐시가 데워진 상태로만 부하를 주면 히트율 99%짜리 예쁜 그래프만 얻고 끝난다.

**카나리 배포.** 새 코드를 전체가 아니라 인스턴스 한 대에만 먼저 흘리고 지표를 본다. 문제가 있어도 피해 범위가 전체의 몇 분의 일로 제한된다.

**지표 알람.** 캐시 히트율, 원본 쿼리 실행 횟수, 그리고 **TTL 주기와 일치하는 DB 부하 패턴**을 본다. 마지막 것이 특히 중요하다 — 매시 정각에 DB 부하가 튀는 그래프는 스탬피드의 서명이나 마찬가지다.

여기서 한 가지를 더 짚어야 한다. **이 셋은 전부 배포 이후의 장치다.** 배포 전에 이 문제를 잡을 수 있는 유일한 장치가 **코드 리뷰**다. 리뷰어의 역할이 정확히 여기다 — 트래픽이라는 숨은 입력이 10배가 됐을 때 이 코드의 어디가 깨지는지를, 아직 안 깨졌을 때 말로 만들어내는 것.

## 2. 붕괴 지점 세 곳 + 신선도 결정

### 2-1. 붕괴 지점 ① 캐시 스탬피드 — 1시간마다 반복되는 정기 미니 장애

#### 스탬피드가 무엇인가

**캐시 스탬피드(cache stampede, 또는 thundering herd — 우르르 몰려드는 무리)**는 캐시가 없는 상태에서 같은 데이터를 요구하는 요청들이 동시에 도착해, **전부가 각자 원본 계산을 실행해 버리는 현상**이다.

이름의 유래가 구조를 잘 설명한다. 문 하나가 열리는 순간 밖에서 기다리던 무리가 한꺼번에 밀려 들어가는 그림이다. 한 마리만 들어가서 먹이를 가져와 나눠 주면 될 일을, 전부가 각자 들어간다.

핵심은 **"필요한 계산은 1번인데 실제로는 N번 실행된다"**는 낭비다. 그 N번이 전부 비싼 집계 쿼리라면 DB가 그 순간을 못 버틴다. (스탬피드 자체는 같은 디렉토리의 `06-cache-stampede.md`에서 깊게 다룬다.)

#### 왜 정확히 1시간마다 반복되는가

여기가 이 PR의 특수성이다. 인과를 한 단계씩 밟아 보자.

**인기 목록은 모든 사용자가 같은 키 하나를 본다.** 사용자별 캐시가 아니므로 키가 딱 하나다. 그러면 그 키가 캐시에 적재된 시각도 하나이고, 따라서 **만료 시각도 하나뿐**이다. 만료가 흩어질 축이 아예 없다.

타임라인으로 보면 이렇다.

```
09:00:00.0  최초 조회 -> 미스 -> 집계 쿼리 -> 캐시 적재 (TTL 1시간)
            ★ 이 순간 만료 시각이 10:00:00 하나로 확정된다

09:00 ~ 10:00
            전 서버, 전 사용자가 이 키 하나를 보고 전부 히트
            DB 부하 0. 그래프는 완벽하게 평온하다.

10:00:00.0  키 소멸. 이후 도착하는 모든 요청이 미스가 된다.
            ★ 어느 서버로 갔든 상관없다. 키가 하나이므로 전부 미스다.

10:00:00.0 ~ 10:00:00.5
            집계 쿼리가 끝나 캐시가 다시 채워질 때까지 0.5초.
            이 0.5초 동안 도착한 요청이 전부 미스를 보고
            전부 각자 집계 쿼리를 실행한다.

10:00:00.5  누군가 캐시를 채운다 -> 이후 요청은 다시 전부 히트

11:00:00.0  같은 일이 그대로 반복
```

이 구조에서 **"만료 순간에 동시에 미스를 보는 요청 수"는 계산할 수 있다.**

```
동시 미스 수 ≈ 초당 요청 수 × 원본 계산 소요 시간

지금(1x):   초당 100 요청  × 0.5초 =  50개  -> 티가 안 난다
10배(10x):  초당 1,000 요청 × 0.5초 = 500개  -> DB가 못 버틴다
```

**"지금 문제없음"이 "10배에서 문제없음"의 근거가 못 되는 이유가 이 식에 그대로 있다.** 동시 미스 수는 트래픽에 정비례하므로, 트래픽이 10배면 동시 미스도 정확히 10배가 된다.

#### 500개가 동시에 오면 무슨 일이 벌어지나

```
[만료 직전]  요청 1,000/s -> 전부 캐시 히트, DB 부하 0

[만료 순간]  0.5초 동안 500개 요청이 전부 미스
             -> 500개가 동시에 같은 비싼 집계 쿼리를 DB에 실행
             -> DB 커넥션 풀 고갈
                (서버 10대 x 풀 20개 = 총 200개. 500개가 200개를 두고 경합)
             -> ★ 캐시와 무관한 다른 API까지 커넥션을 못 잡고 대기한다
                이 캐시를 안 쓰는 기능도 함께 느려진다
             -> 응답 지연 -> 타임아웃
             -> 악순환: DB가 느려져 쿼리가 0.5초에서 2초로 늘면
                미스 창도 4배로 늘어 동시 미스가 2,000개가 된다

[재적재 후]  아무 일 없었다는 듯 정상
             -> 증상은 "매시 정각마다 몇 초씩 느려져요"로만 보고된다
```

마지막 줄이 이 장애의 성격을 말해 준다. **스스로 회복되기 때문에 장애로 분류되지 않고, 그래서 오래 방치된다.** "가끔 느려요"라는 CS가 쌓이는데 원인을 못 찾는 전형적인 형태다.

#### 이 PR에 고유한 성질 두 가지

**(1) TTL이 길수록 한 방이 크다.** 1시간짜리 캐시는 미스 빈도는 낮다(하루 24번). 그런데 그동안 시스템 전체가 "이 캐시는 항상 있다"는 전제로 용량이 잡히기 때문에, 만료 순간의 낙차가 그만큼 크다. 미스가 드물다는 것이 안전을 뜻하지 않는다.

**(2) TTL 지터로는 못 푼다.** 만료 시각에 랜덤 오차를 주어 흩뜨리는 기법이 있지만, 그건 **키가 여러 개**일 때 서로 다른 시각에 만료되게 하는 해법이다. 여기는 **키가 하나**라서 흩뜨릴 대상이 없다. 이 PR에 필요한 것은 **단일 키 스탬피드**에 맞는 해법, 즉 "재계산을 하나로 직렬화"하는 방향이다.

#### 해법 — "재계산은 한 놈만"

**완화 1: `sync = true`** — 가장 싸고, 가장 먼저 붙일 수 있다.

```java
// sync = true: 같은 JVM 안에서는 한 스레드만 재계산하고
// 나머지는 그 결과를 기다렸다가 받아 간다.
@Cacheable(cacheNames = "popularList", sync = true)
public List<Product> getPopularList() { ... }
```

효과와 한계를 정확히 세워야 한다. **이것은 JVM 안에서만 유효한 잠금이다.** 애플리케이션 프로세스 내부의 동기화 장치를 쓰는 것이라, 다른 서버에서 같은 순간 벌어지는 재계산에 대해서는 아무것도 모른다.

```
[sync = false]  서버 10대에 걸쳐 동시 미스 500개
                -> 500개가 전부 재계산 -> DB에 집계 쿼리 500회

[sync = true]   서버마다 자기 JVM 안에서 1개로 합쳐진다
                -> 서버 10대 x 1개 = 재계산 10개 -> DB에 집계 쿼리 10회
                   나머지 490개는 자기 서버의 재계산이 끝나기를 기다린다
```

**500번이 10번으로 줄었으니 의미는 크지만, 해결은 아니다.** 남은 10번도 서버 대수에 비례해 늘어나므로, 오토스케일링으로 서버가 50대가 되면 재계산도 50번이 된다.

부수 효과도 하나 있다. 기다리는 490개 요청의 **응답 시간은 여전히 집계 쿼리 소요 시간만큼 늘어난다.** DB 부하는 줄었지만 사용자가 겪는 지연은 남아 있다는 뜻이다.

**완화 2: 분산 락으로 전 시스템에서 1개만 재계산** — 서버가 몇 대든 재계산을 하나로 줄인다. 락을 못 잡은 요청은 잠깐 대기 후 캐시를 다시 조회하거나, 아래의 낡은 값을 받는다. 다만 분산 락 자체의 운영 복잡도(락 TTL을 얼마로 잡을지, 락 해제 실패 시 어떻게 되는지)가 새로 생긴다.

**완화 3: soft TTL / 백그라운드 갱신** — 물리 TTL은 길게 잡고(예: 2시간), **논리 만료 시각(예: 55분)을 값과 함께 저장**해 둔다. 논리 만료가 지나면 **일단 낡은 값을 그대로 반환하면서** 백그라운드로 한 번만 재계산한다.

이 방식의 값어치는 **사용자가 미스를 아예 경험하지 않는다**는 것이다. 캐시는 물리적으로 살아 있으므로 "빈 순간"이 존재하지 않고, 갱신은 요청 경로 밖에서 일어난다. 인기 목록처럼 "몇 분 낡아도 되는" 데이터에 가장 잘 맞는 해법이다. (가산점 포인트)

**완화 4: 스케줄러 선갱신** — 구조를 뒤집는다. 인기 목록을 "누가 조회해서 채우는" 캐시가 아니라 **"주기적으로 만들어 밀어 넣는" 데이터**로 바꾼다. 5분마다 배치가 갱신하고 TTL은 갱신 주기보다 넉넉히 잡으면, **요청 경로에서 미스라는 개념 자체가 사라진다.** 조회 빈도가 압도적으로 높은 소수 키에는 이 구조 전환이 근본 해법이다. 이 방식은 2-2의 cold cache까지 함께 없앤다.

### 2-2. 붕괴 지점 ② cold cache — 배포·장애 복구 직후에는 캐시가 없다

#### cold cache가 무엇인가

**cold cache(차가운 캐시)**는 캐시가 비어 있어 히트율이 0%에 가까운 상태를 말한다. 반대말인 warm(데워진) 상태는 자주 쓰이는 데이터가 이미 캐시에 올라와 있어 대부분의 요청이 히트하는 상태다.

이 상태가 왜 위험한지는 **용량 산정과 연결해야** 보인다. 캐시 히트율 99%를 전제로 운영되는 시스템은, 사실상 **"DB는 전체 트래픽의 1%만 감당하면 되는" 용량**으로 굳어 있다. 그 전제가 사라지는 순간 DB는 자기가 한 번도 겪어 본 적 없는 부하를 맞는다. (cold cache와 워밍 전략은 같은 디렉토리의 `26-cold-cache-and-cache-warming.md`에서 깊게 다룬다.)

#### 이 PR에서 언제 발생하는가

캐시가 비는 순간은 생각보다 자주 온다.

- Redis 재시작이나 장애 복구 직후
- 배포하면서 캐시 키 버전을 올렸거나 flush 했을 때
- 신규 인스턴스가 투입돼 로컬 캐시가 비어 있을 때

**트래픽 1x일 때는 어찌어찌 버티던 cold start가 10x에서는 즉시 장애다.** 1%만 받던 DB가 100%를 받는데, 그 100%가 원래의 10배이므로 결과적으로 평소의 1,000배를 맞는 셈이다.

대응은 두 가지다. **배포 절차에 캐시 워밍**(트래픽을 받기 전에 인기 키를 미리 적재하는 단계)을 넣거나, **2-1의 완화 4(스케줄러 선갱신) 구조로 바꾸면 자연히 해소된다** — 요청과 무관하게 배치가 채워 두므로 캐시가 빈 채로 트래픽을 맞는 상황이 생기지 않는다.

### 2-3. 붕괴 지점 ③ hot key — 키 하나에 몰리는 조회는 분산도 못 구한다

#### hot key가 무엇인가

**hot key(뜨거운 키)**는 접근이 특정 소수의 키에 집중돼, 그 키를 가진 노드 하나만 과부하되는 현상이다.

핵심은 **Redis Cluster로 확장해도 해결되지 않는다**는 점이다. 클러스터는 키 이름을 해시해 슬롯을 정하고 그 슬롯을 가진 노드로 보내므로, **분산의 단위가 키**다. 키 이름이 같으면 해시 결과도 같으므로, 노드를 10대로 늘려도 그 키는 여전히 딱 한 노드에 산다. 여러 키는 잘 나뉘지만 키 하나는 안 나뉜다. (감지와 해소는 같은 디렉토리의 `13-hot-key-detection-and-mitigation.md`에서 깊게 다룬다.)

#### 이 PR의 인기 목록 키가 전형적인 hot key다

모든 사용자가 같은 `popularList` 키 하나를 본다는 조건이 스탬피드의 원인이었는데, **같은 조건이 hot key의 원인이기도 하다.**

여기서는 CPU보다 **네트워크 대역폭이 먼저 문제가 될 가능성이 높다.** 목록 전체를 직렬화한 값은 수십~수백 KB에 이르는데, 그것이 초당 수천 번 나가면 호출량 × 값 크기가 그 노드의 NIC 대역폭을 채운다.

10배 트래픽에서 감지되는 증상은 이렇다. **"Redis 클러스터 전체는 여유인데 특정 노드만 CPU와 대역폭이 튄다."** 전체 평균만 보는 대시보드에서는 끝까지 안 보인다.

대응으로 가장 효과적인 것은 **앞단에 로컬 캐시(Caffeine)를 수 초~수십 초 TTL로 겹치는 것**이다. 그러면 Redis 조회 횟수가 "요청 수"가 아니라 **"서버 대수 ÷ 로컬 TTL"**에 비례하게 바뀐다. 서버 10대에 로컬 TTL 5초면 Redis 조회는 초당 2회다. 인기 목록은 몇 초의 불일치를 허용하므로 로컬 캐시와 궁합이 좋다.

덤으로 로컬 캐시는 **2-1의 스탬피드도 함께 완화한다.** Redis 키가 만료돼도 각 서버의 로컬 캐시가 살아 있는 동안은 미스가 그쪽까지 도달하지 않기 때문이다.

### 2-4. TTL 1시간이라는 신선도 결정

세 붕괴 지점은 전부 기술 문제다. 그런데 리뷰에서 놓치기 쉬운 항목이 하나 더 있다. **TTL 1시간은 기술 설정이 아니라 비즈니스 결정이기도 하다.**

"인기 목록이 최장 1시간 낡아도 되는가"라는 질문이다. 방금 급상승한 상품이 1시간 동안 목록에 안 보여도 괜찮은지, 품절된 상품이 1시간 동안 인기 목록에 남아 있어도 되는지 — **이 합의 없이 정한 TTL이라면 그 자체가 리뷰 코멘트감이다.** 개발자가 혼자 정할 수 있는 값이 아니다.

그리고 이 항목은 앞의 기술 문제와 얽혀 있다.

```
신선도를 높이려고 TTL을 줄인다  -> 만료가 잦아진다
                                -> 스탬피드에 노출되는 횟수가 늘어난다
신선도를 포기하고 TTL을 늘린다  -> 만료는 드물어진다
                                -> 한 번 터질 때의 낙차가 커지고 데이터는 더 낡는다
```

**어느 방향으로 가도 다른 쪽이 나빠진다.** 그래서 TTL 튜닝만으로는 이 딜레마를 못 푼다. 2-1의 완화 3(soft TTL/백그라운드 갱신)과 완화 4(스케줄러 선갱신)가 좋은 해법인 이유가 여기 있다 — **신선도를 짧은 주기로 확보하면서 미스를 요청 경로 밖으로 빼기 때문에** 두 축을 동시에 개선한다.

## 3. 실제 리뷰 코멘트로 옮기면 — 지식을 실행 가능한 형태로

### 3-1. 톤 — "틀렸다"가 아니라 "조건이 바뀌면 깨진다"

면접에서 요구하는 것은 지식 나열이 아니라 **동료가 바로 행동할 수 있는 코멘트**다. 그리고 내용만큼 톤도 본다. 실패하는 코멘트를 먼저 보면 기준이 분명해진다.

**나쁜 예 1 — 판정만 있고 근거가 없다.**

> 이렇게 캐시 쓰면 안 됩니다. 스탬피드 터져요.

지금 코드는 틀리지 않았다(1-1). 틀렸다고 단정하면 사실과도 어긋나고, 받는 사람은 방어부터 하게 된다.

**나쁜 예 2 — 지시만 있고 왜가 없다.**

> `sync = true` 붙여 주세요.

동료는 시키는 대로 고칠 수는 있지만 **다음번에 같은 실수를 반복한다.** 왜 필요한지가 전달되지 않았기 때문이다. 그리고 `sync = true`가 부분 완화일 뿐이라는 사실(2-1)도 함께 사라진다.

**좋은 예 — 조건을 근거로 제안한다.**

> 지금 트래픽에서는 문제없는데, 목표 트래픽(10배)에서는 이 지점이 이렇게 깨집니다. 이렇게 보완하면 좋겠습니다.

이 톤이 성립하는 이유는 **실제로 그것이 사실이기 때문**이다. 배려하는 화법을 고른 게 아니라 정확하게 말한 결과가 이 형태가 된다.

여기에 하나 더. **판단을 대신하지 않고 확인을 요청해야 하는 항목을 구분한다.** TTL 1시간이 적절한지는 리뷰어가 결정할 수 없는 비즈니스 사안이므로(2-4), "고쳐 주세요"가 아니라 "확인 부탁해요"로 남긴다.

### 3-2. 코멘트 예시

> 캐시 적용 좋습니다. 배포 전에 한 가지만 같이 봐요 — 이 키는 모든 사용자가 공유하는 단일 키라서, TTL 1시간마다 만료되는 순간 그때 들어온 요청 전부가 동시에 `findPopular()` 집계 쿼리를 실행합니다 (cache stampede). 지금 트래픽에선 만료 순간에 겹치는 요청이 수십 건이라 티가 안 나는데, 목표 트래픽(10배)에서는 매시간 수백 건의 동시 집계가 DB 커넥션 풀을 잡아 이 캐시와 무관한 요청까지 밀릴 수 있어요.
>
> 제안: ① 최소한 `sync = true`로 JVM당 재계산 1개로 줄이고(서버 대수만큼은 남으니 완화까지입니다), ② 가능하면 논리 만료 + 백그라운드 갱신(낡은 값을 서빙하며 1개만 재계산)이나 스케줄러 선갱신으로 가면 미스 자체가 없어집니다. 추가로 ③ 배포·장애 복구 직후엔 캐시가 비어서 DB가 전체 트래픽을 직격으로 맞으니 워밍 절차도 함께 챙기면 좋겠고, ④ 이 키는 단일 키라 Redis Cluster에서도 한 노드에 몰리는데 앞단 로컬 캐시(수 초 TTL)를 겹치면 ①③과 함께 해소됩니다. 마지막으로 ⑤ TTL 1시간이면 인기 목록이 최장 1시간 낡는데, 이게 기획과 합의된 값인지 확인 부탁해요.

### 3-3. 이 코멘트의 뼈대

좋은 리뷰 코멘트는 네 부분으로 이루어진다.

| 부분 | 내용 | 위 코멘트에서 |
|---|---|---|
| 증상 | 무엇이 벌어지는가 | 만료 순간 전부가 동시에 집계 쿼리를 실행한다 |
| 조건 | 언제부터 문제인가 | 지금은 수십 건, 10배에서는 수백 건 |
| 파급 | 어디까지 번지는가 | 커넥션 풀 고갈로 무관한 요청까지 밀린다 |
| 제안 | 어떻게, 난이도 순으로 | `sync = true` → soft TTL/선갱신 → 워밍 → 로컬 캐시 |

**제안을 난이도 순으로 배열하는 것**이 특히 중요하다. "전부 다 하자"는 실행되지 않는다. 지금 당장 할 수 있는 것과 다음 단계에서 할 것을 구분해 주어야 동료가 이 PR에서 무엇을 하고 무엇을 티켓으로 남길지 결정할 수 있다.

## 4. 꼬리질문 대비 포인트

### "제안한 해법 중 뭐부터 적용하겠습니까? 우선순위 기준은?" (시니어 변별 포인트)

**비용 대비 효과 순**으로 간다.

**① `sync = true`는 코드 한 줄이라 즉시 적용한다.** 서버가 N대면 동시 재계산이 N개로 줄어드는 것뿐이지만, 500 → 10이면 이미 대부분의 위험이 제거된다. 완전한 해결이 아니라는 이유로 미루는 것보다, 지금 당장 위험의 대부분을 없애는 쪽이 낫다.

**② 그걸로 부족하다는 신호가 보이면 soft TTL / 백그라운드 갱신을 도입한다.** 신호란 구체적으로 **만료 시각과 일치하는 DB 스파이크가 모니터링에 계속 보이는 것**이다. 짐작이 아니라 지표를 근거로 다음 단계를 결정한다.

**③ 스케줄러 선갱신은 구조 변경이라 가장 크지만**, 이 키가 서비스의 간판 조회라면 투자 가치가 있다. 미스라는 개념 자체를 없애면서 cold cache까지 함께 해소된다.

분산 락은 순위에서 뒤로 둔다. **락 자체의 운영 복잡도(락 TTL 설정, 해제 실패 시 교착)가 새로 생기므로, 같은 효과를 내는 soft TTL이 가능하면 그쪽을 먼저 고려한다.**

**"전부 다 하자"가 아니라 모니터링 신호를 근거로 단계적으로 간다**는 것이 시니어의 답이다.

### "TTL을 10분으로 줄이거나 10시간으로 늘리면 해결되나요?"

**어느 쪽도 스탬피드를 해결하지 못한다.** 만료라는 이벤트가 존재하는 한, 그 순간의 동시 미스는 그대로 발생하기 때문이다.

줄이면: 신선도는 좋아지지만 만료가 6배 잦아져 **스탬피드에 노출되는 횟수가 늘어난다.** 늘리면: 만료 빈도는 줄지만 **한 번 터질 때의 낙차**(그동안 커진 트래픽을 전제로 용량이 잡혀 있다)와 데이터 신선도 문제가 커진다.

정리하면 **TTL 튜닝은 "빈도 대 신선도"의 트레이드오프 조절일 뿐이고, 스탬피드는 "재계산을 하나로 직렬화"라는 별도의 축으로 풀어야 한다.** 두 축을 구분하는 것이 이 질문의 포인트다.

### "TTL에 지터(랜덤 오차)를 주는 건 여기서 효과가 있나요?"

**거의 없다.** 지터는 **수많은 키가 같은 시각에 일제히 만료되는 것**(대량 적재 후 동시 만료)을 시간축으로 흩뜨리는 해법이다. 흩뜨릴 대상이 여러 개일 때 성립한다.

이 PR은 **키가 하나**라서 분산할 대상이 없다. 만료 시각을 랜덤하게 흔들어도 여전히 시각은 하나이고, 그 하나의 순간에 동시 요청이 몰리는 구조는 그대로다.

여기에 맞는 정답은 **single-flight(재계산을 1개로 직렬화)** 계열이다. 해법을 문제 유형에 매칭할 수 있는지(**다중 키 동시 만료** 대 **단일 키 미스 폭주**)를 보는 꼬리질문이다.

### "이런 문제를 테스트로 미리 잡을 수는 없나요?"

**단위·통합 테스트로는 어렵다**(1-2). 잡으려면 조건 자체를 재현해야 한다.

**① 부하 테스트 시나리오에 조건을 명시적으로 넣는다.** "캐시 만료 직후"와 "cold cache 상태"를 시나리오로 만들고, k6나 Gatling 등으로 만료 시점에 동시 요청을 주입한다. 데워진 캐시에 부하를 주는 테스트는 아무것도 검증하지 못한다.

**② 재계산 동시 실행 수를 검증하는 동시성 테스트는 단위 레벨로도 가능하다.** 스레드 N개가 동시에 미스를 보게 만들고 **원본 메서드가 몇 번 호출됐는지를 세는** 테스트다. `sync = true`가 실제로 작동하는지를 이걸로 확인할 수 있다.

**③ 더 현실적으로는 운영 모니터링으로 잡는다.** 캐시 히트율, 원본 쿼리 실행 횟수의 시간대별 스파이크, 그리고 **만료 주기와 일치하는 DB 부하 패턴**. 매시 정각의 톱니 모양 그래프가 보이면 스탬피드다.

**"테스트 통과"의 공백을 부하 시나리오와 모니터링으로 메운다**는 답의 구조가 중요하다. 테스트를 더 잘 짜면 잡힌다는 답이 아니라, 축이 다르니 다른 도구가 필요하다는 답이어야 한다.

### "인기 목록 hot key가 실제로 문제인지 어떻게 감지하나요?"

세 레벨로 접근한다.

**Redis 레벨**: `redis-cli --hotkeys`(축출 정책이 LFU일 때만 키별 접근 빈도 카운터가 존재하므로 LFU 필요), 그리고 Cluster라면 **노드별 CPU·네트워크 지표의 불균형** — 전체는 여유인데 한 노드만 튀는 패턴이 hot key의 서명이다.

**프록시/클라이언트 레벨**: 키별 조회 카운트를 앞단에서 집계한다. Redis 서버는 기본적으로 키별 호출 횟수를 기록하지 않으므로, 상시 감지는 호출하는 쪽에서 하는 것이 정확하다.

**애플리케이션 레벨**: 키 prefix별 조회 메트릭을 직접 심는다. 키 전체가 아니라 prefix 단위로 묶어야 메트릭 태그 수가 폭발하지 않는다.

감지 후 해소는 **앞단 로컬 캐시로 Redis 조회 자체를 줄이는 것이 우선**이고, 읽기 replica 분산이나 키 복제(`popular:1` ~ `popular:N`에 같은 값을 두고 랜덤 조회)는 그다음 단계다. 로컬 캐시가 먼저인 이유는 효과가 가장 크고(Redis 조회가 서버 대수에 비례하도록 바뀐다) 인프라 변경이 없기 때문이다.

## 한 줄 요약

"테스트 통과"는 요청이 하나씩 올 때의 정확성 증명일 뿐이고 캐시는 동시성과 규모에서 무너지므로, 단일 키·TTL 1시간·인기 목록이라는 조합에서 트래픽 10배가 되면 만료 시각이 하나뿐이라 매시간 전 서버의 미스가 동시에 DB를 때리는 스탬피드, 배포 직후의 cold cache, 키 하나에 몰리는 hot key가 붕괴 지점이 된다 — 리뷰 코멘트는 이를 "증상 + 조건 + 파급 + 난이도순 제안(JVM 안에서만 유효해 완화에 그치는 sync=true → soft TTL/백그라운드 갱신 → 선갱신 구조 → 로컬 캐시)"의 실행 가능한 형태로, 판정이 아니라 조건 변화를 근거로 남기는 것까지가 답이다.
