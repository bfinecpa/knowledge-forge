# TTL 1시간 캐시 PR 리뷰 — "테스트 통과"가 보증하지 않는 것: 트래픽 10배에서의 붕괴 지점

> 핵심 관전 포인트: **테스트 통과는 "기능이 맞다"는 증명일 뿐, 트래픽
> 조건이 바뀌었을 때의 동작은 아무것도 보증하지 않는다. 인기 목록처럼
> 모두가 같은 키 하나를 보는 캐시는 트래픽 10배에서 세 곳이 무너진다 —
> ① 캐시 만료 순간 동시 미스가 전부 DB를 때리는 캐시 스탬피드(1시간마다
> 반복되는 정기 미니 장애), ② 배포·재시작 직후 캐시가 빈 상태로 전체
> 트래픽을 맞는 cold cache, ③ 키 하나에 조회가 집중되는 hot key.
> 여기에 TTL 1시간이라는 신선도 결정이 비즈니스와 합의된 것인지도
> 물어야 한다. 리뷰 코멘트는 "지금 코드가 틀렸다"가 아니라 "트래픽
> 조건이 바뀌면 여기가 깨진다 + 이렇게 보완하자"의 형태여야 한다.**

---

## 0. 질문 + 의도

**질문**: "동료의 PR: 인기 목록 조회를 TTL 1시간 캐시로 감쌌고 테스트도
통과했습니다. 트래픽이 10배가 되면 생길 수 있는 문제를 리뷰 코멘트로
남겨보세요."

**출제 의도**: 캐시 스탬피드 개념 문항과 짝을 이루는 상황 인지 검사.
"지금 잘 동작하는 코드"에서 트래픽 조건이 바뀌었을 때의 붕괴 지점
(동시 만료, 미스 폭주)을 배포 전에 말할 수 있는지 — 지식이 리뷰
코멘트라는 실행 가능한 형태로 나오는지 본다.

## 1. 왜 "테스트 통과"가 안전을 보증하지 못하는가

PR의 코드는 대략 이런 모양일 것이다:

```java
@Cacheable(cacheNames = "popularList")   // TTL 1시간은 CacheManager 설정에
public List<Product> getPopularList() {
    return productRepository.findPopular();   // 비싼 집계 쿼리
}
```

기능 테스트가 검증하는 것: "첫 호출은 DB를 읽고, 두 번째 호출은 캐시를
읽는다." — 이건 **요청이 한 번에 하나씩 올 때**의 이야기다. 캐시의
진짜 시험대는 전부 **동시성과 규모**에서 온다: 만료되는 순간 몇 개의
요청이 동시에 미스를 보는가, 캐시가 비어 있는 순간 DB가 몇 배의
트래픽을 맞는가. 이것들은 단위 테스트에 등장하지 않는 조건이라
"테스트 통과 = 배포 가능"이 성립하지 않는다.

리뷰어의 역할이 여기다 — **트래픽이라는 숨은 입력이 10배가 됐을 때
이 코드의 어디가 깨지는지**를 배포 전에 말로 만들어내는 것.

## 2. 붕괴 지점 ① — 캐시 스탬피드: 1시간마다 반복되는 정기 미니 장애

인기 목록은 **모든 사용자가 같은 키 하나**를 본다. TTL이 1시간이면
정확히 1시간마다 그 키가 만료되는 순간이 오고, 그 순간 들어온 요청들은
**전부 미스를 보고 전부 원본 쿼리를 실행**한다.

```
[만료 직전]  요청 1000/s → 전부 캐시 히트, DB 부하 0
[만료 순간]  동시에 들어온 수백 개 요청이 전부 미스
             → 수백 개가 동시에 같은 비싼 집계 쿼리를 DB에 실행
             → DB 커넥션 풀 고갈 → 캐시와 무관한 다른 요청까지 대기
             → 응답 지연 → 타임아웃 → (최악) 커넥션을 못 잡은 재계산이
               실패해 캐시가 계속 안 채워지는 악순환
[재적재 후]  아무 일 없었다는 듯 정상 — "1시간마다 몇 초씩 느려져요"
```

이것이 캐시 스탬피드(cache stampede, thundering herd)다. 핵심 성질:

- **트래픽에 비례해 심해진다.** 지금(1x)은 만료 순간에 겹치는 요청이
  몇 개라 티가 안 나지만, 10배가 되면 같은 순간에 수백 개가 겹친다.
  "지금 문제없음"이 "10배에서 문제없음"의 근거가 못 되는 이유.
- **TTL이 길수록 한 방이 크다.** 1시간짜리 캐시는 미스 빈도는 낮지만,
  그동안 시스템 전체가 "캐시가 항상 있다"는 전제로 용량이 잡히기
  때문에 만료 순간의 낙차가 크다.
- 인기 목록은 키가 하나라서 "TTL 지터로 만료 시각 분산" 같은 다중 키
  해법이 안 통한다 — **단일 키 스탬피드**에 맞는 해법이 필요하다.

### 해법 — "재계산은 한 놈만"

```java
// 완화 1: sync = true — 같은 JVM 안에서는 한 스레드만 재계산, 나머지는 대기
@Cacheable(cacheNames = "popularList", sync = true)
public List<Product> getPopularList() { ... }
// 단, 서버가 N대면 여전히 N개의 동시 재계산이 남는다
```

- **분산 락으로 전체에서 1개만 재계산** — 서버가 여러 대여도 재계산을
  전 시스템에서 하나로 줄인다. 락을 못 잡은 요청은 잠깐 대기 후 캐시
  재조회, 또는 아래의 낡은 값 서빙.
- **soft TTL / 백그라운드 갱신** — 물리 TTL은 길게(예: 2시간), 논리
  만료(예: 55분)를 값에 함께 저장해두고, 논리 만료가 지나면 **일단
  낡은 값을 반환하면서** 백그라운드로 한 번만 재계산한다. 사용자는
  미스를 아예 경험하지 않는다 — 인기 목록처럼 "몇 분 낡아도 되는"
  데이터에 가장 잘 맞는 해법. (가산점 포인트)
- **스케줄러 선갱신** — 인기 목록은 "누가 조회해서 채우는" 캐시가 아니라
  "주기적으로 만들어 밀어 넣는" 데이터로 뒤집을 수도 있다. 5분마다
  배치가 갱신하고 TTL은 갱신 주기보다 넉넉히 — 요청 경로에서 미스라는
  개념 자체가 사라진다. 조회 빈도가 압도적으로 높은 소수 키에는 이
  구조 전환이 근본 해법이다.

## 3. 붕괴 지점 ② ③ — cold cache와 hot key

### ② cold cache: 배포·장애 복구 직후에는 캐시가 없다

캐시 히트율 99%를 전제로 운영되는 시스템은 사실상 "DB는 트래픽의 1%만
감당하면 되는" 용량으로 굳어 있다. 배포로 Redis가 비거나(키 버전 변경,
flush) 재시작되면 그 순간 **DB가 10배 트래픽을 캐시 없이 정면으로**
맞는다. 트래픽 1x일 때는 어찌어찌 버티던 cold start가 10x에서는 즉시
장애다. 대응: 배포 절차에 캐시 워밍(트래픽을 받기 전에 인기 키를 미리
적재)을 넣거나, 위의 스케줄러 선갱신 구조로 바꾸면 자연히 해소된다.

### ③ hot key: 키 하나에 몰리는 조회는 분산도 못 구한다

인기 목록 키는 전형적인 hot key다. Redis를 Cluster로 확장해도 **키
하나는 해시 슬롯 하나, 즉 한 노드**에 산다 — 노드를 10대로 늘려도 이
키의 조회는 전부 한 노드에 몰린다. 값이 크면(목록 전체 직렬화) 그
노드의 네트워크 대역폭부터 포화된다. 10배 트래픽에서 감지되는 증상은
"Redis 전체는 여유인데 특정 노드만 CPU/대역폭이 튀는" 것. 대응: 앞단에
로컬 캐시(Caffeine)를 수 초~수십 초 TTL로 겹쳐 Redis 조회 자체를
서버 대수만큼으로 줄이는 것이 가장 효과적이다 — 인기 목록은 몇 초의
불일치를 허용하므로 로컬 캐시와 궁합이 좋다.

### 덤: TTL 1시간은 신선도 결정이기도 하다

기술 문제와 별개로, "인기 목록이 최장 1시간 낡아도 되는가"는 비즈니스
결정이다. 방금 급상승한 상품이 1시간 동안 목록에 안 보여도 되는지 —
이 합의 없이 TTL을 정했다면 그것도 리뷰 코멘트감이다. (신선도를
올리려고 TTL을 줄이면 미스 빈도가 늘어 스탬피드 노출이 잦아진다 —
soft TTL/선갱신 구조는 이 딜레마도 함께 푼다.)

## 4. 실제 리뷰 코멘트로 옮기면 — 지식을 실행 가능한 형태로

면접에서 요구하는 건 지식 나열이 아니라 **동료가 바로 행동할 수 있는
코멘트**다. 톤도 본다 — 코드를 깎아내리지 않고, 조건 변화를 근거로
제안한다.

> 캐시 적용 좋습니다. 배포 전에 한 가지만 같이 봐요 — 이 키는 모든
> 사용자가 공유하는 단일 키라서, TTL 1시간마다 만료되는 순간 그때
> 들어온 요청 전부가 동시에 `findPopular()` 집계 쿼리를 실행합니다
> (cache stampede). 지금 트래픽에선 몇 건이라 티가 안 나는데, 목표
> 트래픽(10배)에서는 매시간 수백 건의 동시 집계가 DB 커넥션 풀을 잡아
> 캐시와 무관한 요청까지 밀릴 수 있어요.
>
> 제안: ① 최소한 `sync = true`로 JVM당 재계산 1개로 줄이고, ② 가능하면
> 논리 만료 + 백그라운드 갱신(낡은 값을 서빙하며 1개만 재계산)이나
> 스케줄러 선갱신으로 가면 미스 자체가 없어집니다. 추가로 ③ 배포/장애
> 복구 직후엔 캐시가 비어서 DB가 전체 트래픽을 직격으로 맞으니 워밍
> 절차도 함께 챙기면 좋겠고, ④ TTL 1시간이면 인기 목록이 최장 1시간
> 낡는데 이게 기획과 합의된 값인지 확인 부탁해요.

이 코멘트가 담고 있는 구조 — **증상(무엇이) + 조건(언제부터) + 파급
(어디까지) + 제안(어떻게, 난이도 순)** — 이 곧 모범답안의 뼈대다.

## 5. 꼬리질문 대비 포인트

### "제안한 해법 중 뭐부터 적용하겠습니까? 우선순위 기준은?" (시니어 변별 포인트)

비용 대비 효과 순으로. ① `sync = true`는 코드 한 줄이라 즉시 —
서버 N대면 동시 재계산이 N개로 줄어드는 것뿐이지만, 수백 → N이면 이미
대부분의 위험이 제거된다. ② 그걸로 부족하다는 신호(만료 시각의 DB
스파이크가 모니터링에 계속 보임)가 있으면 soft TTL/백그라운드 갱신을
도입. ③ 스케줄러 선갱신은 구조 변경이라 가장 크지만, 이 키가 서비스의
간판 조회라면 투자 가치가 있다. "전부 다 하자"가 아니라 **모니터링
신호를 근거로 단계적으로**가 시니어의 답이다. 분산 락은 락 자체의 운영
복잡도(TTL, 해제 실패)를 추가하므로, 같은 효과를 내는 soft TTL이
가능하면 그쪽을 먼저 고려한다.

### "TTL을 10분으로 줄이거나 10시간으로 늘리면 해결되나요?"

어느 쪽도 스탬피드를 해결하지 못한다 — 만료라는 이벤트가 존재하는 한
그 순간의 동시 미스는 그대로다. 줄이면: 신선도는 좋아지지만 만료가
6배 잦아져 스탬피드 노출 횟수가 늘고, 늘리면: 만료 빈도는 줄지만 한 번
터질 때의 낙차(그동안 커진 트래픽 전제)와 데이터 신선도 문제가 커진다.
TTL 튜닝은 "빈도 vs 신선도"의 트레이드오프 조절일 뿐이고, 스탬피드는
"재계산을 하나로 직렬화"라는 별도의 축으로 풀어야 한다는 걸 구분하는
게 포인트다.

### "TTL에 지터(랜덤 오차)를 주는 건 여기서 효과가 있나요?"

거의 없다. 지터는 **수많은 키가 같은 시각에 일제히 만료**되는 것(대량
적재 후 동시 만료)을 분산시키는 해법이다. 이 PR은 키가 하나라서 분산할
대상이 없다 — 그 키 하나의 만료 순간에 동시 요청이 몰리는 게 문제이므로
single-flight(재계산 1개로 직렬화) 계열이 정답이다. 해법을 문제 유형에
매칭할 수 있는지(다중 키 동시 만료 vs 단일 키 미스 폭주)를 보는
꼬리질문이다.

### "이런 문제를 테스트로 미리 잡을 수는 없나요?"

단위/통합 테스트로는 어렵고, 잡으려면 조건을 재현해야 한다 — ① 부하
테스트 시나리오에 "캐시 만료 직후"와 "cold cache 상태"를 명시적으로
포함시키고(k6, Gatling 등으로 만료 시점에 동시 요청 주입), ② 재계산
동시 실행 수를 검증하는 동시성 테스트(스레드 N개가 동시에 미스를 볼 때
원본 메서드 호출 횟수를 세는 테스트)는 단위 레벨로도 가능하다. 더
현실적으로는 운영 모니터링으로 잡는다 — 캐시 히트율, 원본 쿼리 실행
횟수의 시간대별 스파이크, 만료 주기와 일치하는 DB 부하 패턴. "테스트
통과"의 공백을 부하 시나리오와 모니터링으로 메운다는 답의 구조가
중요하다.

### "인기 목록 hot key가 실제로 문제인지 어떻게 감지하나요?"

Redis 레벨: `redis-cli --hotkeys`(LFU 정책 기반), 프록시/클라이언트
레벨의 키별 조회 카운트, Cluster라면 노드별 CPU/네트워크 지표의 불균형
(전체는 여유인데 한 노드만 튀는 패턴). 애플리케이션 레벨: 키 prefix별
조회 메트릭을 직접 심는 방법. 감지 후 해소는 앞단 로컬 캐시로 Redis
조회 자체를 줄이는 것이 우선이고, 읽기 replica 분산이나 키 복제
(popular:1 ~ popular:N에 같은 값을 두고 랜덤 조회)는 그다음 단계다.

## 한 줄 요약

"테스트 통과"는 요청이 하나씩 올 때의 기능 증명일 뿐이므로, 단일 키·
TTL 1시간·인기 목록이라는 조합에서 트래픽 10배가 되면 만료 순간의 동시
미스가 DB를 때리는 스탬피드(매시간 반복), 배포 직후의 cold cache, 키
하나에 몰리는 hot key가 붕괴 지점이 된다 — 리뷰 코멘트는 이를 "증상 +
조건 + 파급 + 난이도순 제안(sync=true → soft TTL/백그라운드 갱신 →
선갱신 구조)"의 실행 가능한 형태로 남기는 것까지가 답이다.
