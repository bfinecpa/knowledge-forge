# 캐시 스탬피드 — 인기 키 하나의 만료가 DB를 뚫는 순간

> 핵심 관전 포인트: **캐시 스탬피드는 "동시 요청이 몰리는 인기 키"가
> "만료되는 순간", 재계산이 끝나기 전까지 도착하는 모든 요청이 전부
> 미스를 보고 전부 DB로 직행하는 현상이다. 발생 조건은 ① 인기 키
> ② 비싼 재계산 ③ 만료 순간의 동시 미스 — 셋이 겹칠 때만 터지므로
> 트래픽이 적은 환경에서는 존재하지 않는 문제다. 해결은 락(single
> flight)으로 재계산을 한 놈만 하게 하거나, 논리적 만료(soft TTL)로
> 물리적 미스 자체를 없애거나, TTL 지터·사전 갱신(refresh-ahead)으로
> 만료 순간의 동시성을 흩뜨리는 것 — 각각 "미스 후 수습 / 미스 제거 /
> 만료 분산"이라는 다른 지점을 공략한다.**

---

## 0. 질문 + 의도

**질문**: "캐시 스탬피드(cache stampede/thundering herd)란? 해결 방법
3가지 이상을 설명해주세요."

**출제 의도**: 인기 키 하나의 만료가 DB를 뚫는 이 현상은 "트래픽이
많아야만 존재하는 문제"의 대표라, 대용량 경험의 진위를 가리는 데
효과적이다. 해결책을 여러 개 아는지보다 문제의 발생 조건을 정확히
그리는지를 본다.

## 1. 발생 조건 — 언제, 왜 터지는지 정확히 그리기

Look-aside(cache-aside) 패턴의 기본 흐름은 "캐시 조회 → 미스면 DB
조회 → 캐시 적재"다. 이 흐름 자체에 구조적 빈틈이 있다: **미스를
확인한 시점과 캐시가 다시 채워지는 시점 사이의 창(window)** 동안
도착하는 요청은 전부 미스를 본다.

평소에는 이 창이 문제가 안 된다. 창이 좁고(재계산이 빠르고) 그 사이
도착하는 요청이 몇 개 안 되기 때문이다. 스탬피드는 다음 세 조건이
**동시에** 겹칠 때 터진다:

1. **인기 키** — 그 키 하나에 초당 수백~수천 요청이 몰린다
   (메인 페이지 인기 목록, 실시간 랭킹 등).
2. **비싼 재계산** — 캐시를 채우는 원본 쿼리가 느리다
   (집계, 조인, 수백 ms~수 초). 창이 그만큼 넓어진다.
3. **만료 순간** — TTL이 다해 그 키가 캐시에서 사라진다.

타임라인으로 그리면:

```
t=0        인기 키 만료 (TTL 도달)
t=0~500ms  재계산(느린 집계 쿼리)이 끝나기 전까지의 "미스 창"
           → 이 500ms 동안 도착한 요청 수백 개가 전부 미스
           → 전부 각자 같은 쿼리를 DB에 날림
t=500ms+   누군가의 결과가 캐시에 적재 → 이후 요청은 히트
```

그런데 실제로는 t=500ms에 안 끝난다. **같은 무거운 쿼리 수백 개가
동시에 DB를 때리면 DB가 느려지고, DB가 느려지면 재계산 창이 더
넓어지고, 창이 넓어지면 미스 요청이 더 쌓이는** 양의 되먹임(악순환)이
걸린다. 커넥션 풀이 고갈되면 그 키와 무관한 다른 쿼리까지 대기하며
장애가 서비스 전체로 번진다. "쿼리가 N번 중복 실행된다"가 아니라
"자기 강화 붕괴가 시작된다"까지 그려야 문제를 정확히 이해한 것이다.

thundering herd(우르르 몰려드는 소떼)라는 별칭이 그림 그대로다 —
문(캐시)이 열려 있을 땐 아무 일 없다가, 문이 닫히는 순간 소떼 전체가
울타리(DB)로 돌진한다.

### 스탬피드가 아닌 것과 구분

- **캐시 관통(penetration)**: 애초에 존재하지 않는 키를 반복 조회해
  매번 미스가 나는 것 — 만료와 무관하다. (해법은 null 캐싱, 짧은 TTL)
- **캐시 무력화/장애**: 캐시 계층 자체가 죽어 모든 키가 미스가 되는
  것 — 별도 방어 설계가 필요하다 (→ 19번 문서).
- **cold cache**: 배포·복구 직후 캐시가 통째로 비어 있는 상태
  (→ 26번 문서). 스탬피드가 "키 하나 단위"라면 이쪽은 "전체 단위"다.

스탬피드는 이 중 **"멀쩡히 운영 중인 캐시에서, 인기 키 하나의 만료"**
라는 가장 국소적인 조건으로 터지는 문제다.

## 2. 해결 방법 — 어느 지점을 공략하는지로 분류해서 답하기

해법을 나열만 하지 말고 "미스가 난 뒤 수습하는가 / 미스 자체를
없애는가 / 만료의 동시성을 흩뜨리는가"로 묶어서 답하면 이해도가
드러난다.

### ① 락 / single flight — 재계산을 "한 놈만" 하게 (미스 후 수습)

미스를 본 요청 중 **하나만** 락을 잡고 재계산하고, 나머지는 결과를
기다리거나(대기) 이전 값을 받는다(stale 반환).

```java
// ❌ before: 순진한 look-aside — 동시 미스 = 동시 재계산
public Ranking getRanking() {
    Ranking cached = redis.get("ranking");
    if (cached != null) return cached;
    Ranking fresh = rankingRepository.calculate(); // 비싼 쿼리 — 미스 본 놈 전부 실행
    redis.set("ranking", fresh, TTL);
    return fresh;
}

// ✅ after: 분산 락으로 재계산을 전체에서 1회로 제한
public Ranking getRanking() {
    Ranking cached = redis.get("ranking");
    if (cached != null) return cached;

    RLock lock = redisson.getLock("lock:ranking");
    if (lock.tryLock()) {                          // 락 획득 성공 = 재계산 담당
        try {
            Ranking again = redis.get("ranking");  // double-check: 이미 채워졌으면 끝
            if (again != null) return again;
            Ranking fresh = rankingRepository.calculate();
            redis.set("ranking", fresh, TTL);
            return fresh;
        } finally {
            lock.unlock();
        }
    }
    // 락 획득 실패 = 다른 놈이 재계산 중
    // → 잠깐 대기 후 재조회하거나, 직전 stale 값을 반환
    return waitAndRetryOrServeStale();
}
```

- 스프링이라면 `@Cacheable(sync = true)`가 같은 발상의 내장 장치다 —
  단 **같은 JVM 안에서만** 직렬화되므로, 서버가 N대면 재계산이
  N번까지는 일어난다. "N번이면 감당 가능한가"로 분산 락까지 갈지
  판단한다 (인스턴스 10대에 쿼리 10번은 대부분 괜찮다 — 1000번이
  문제였던 것).
- 락 방식의 함정: 락 잡은 요청이 죽으면? 락 대기가 길어지면? —
  꼬리질문 대비 포인트에서 다룬다.

### ② 논리적 만료 (soft TTL) — 물리적 미스 자체를 없애기

키를 물리적으로 만료시키지 않고(TTL을 아주 길게 또는 없이),
**값 안에 논리적 만료 시각을 넣어둔다.** 조회 시 논리 만료가 지났으면
— 미스가 아니라 — **일단 낡은 값을 즉시 반환하면서**, 백그라운드에서
한 놈만 갱신을 수행한다 (stale-while-revalidate 발상).

```java
// 캐시에 저장하는 값에 논리 만료 시각을 함께 넣는다
record CachedRanking(Ranking data, Instant logicalExpiry) {}

public Ranking getRanking() {
    CachedRanking cached = redis.get("ranking");   // 물리 TTL이 길어 거의 항상 히트

    if (cached.logicalExpiry().isBefore(Instant.now())) {
        // 논리적으로 만료 — 그래도 요청은 낡은 값으로 즉시 응답
        if (tryLock("lock:ranking:refresh")) {     // 갱신은 백그라운드 한 놈만
            asyncExecutor.submit(this::refreshRanking);
        }
    }
    return cached.data();  // 미스 창이 존재하지 않는다 — DB로 가는 요청 0
}
```

미스 창이 아예 사라지므로 스탬피드가 원천 봉쇄된다. 대가는
**갱신되는 동안 낡은 값이 서빙된다**는 것 — "랭킹이 몇 초 낡아도
되는가"라는 정합성 요구로 채택 여부를 정한다. 인기 목록·랭킹처럼
원래부터 근사값인 데이터에 최적이다.

### ③ TTL 지터(jitter) — 동시 만료를 흩뜨리기

같은 시각에 대량 적재된 키들이 같은 시각에 일제히 만료되는 것
(배치로 밤 12시에 적재 → 다음 날 밤 12시에 전부 만료)을 막기 위해
TTL에 랜덤 오차를 섞는다.

```java
// ❌ 전 키 TTL 1시간 — 적재가 몰리면 만료도 몰린다
redis.set(key, value, Duration.ofHours(1));

// ✅ 1시간 ± 최대 5분 랜덤 — 만료 시각이 흩어진다
Duration ttl = Duration.ofHours(1)
        .plusSeconds(ThreadLocalRandom.current().nextLong(300));
redis.set(key, value, ttl);
```

주의: 지터는 **"여러 키의 동시 만료"**를 분산하는 도구다.
**단일 인기 키** 하나가 만료되는 순간의 폭주는 못 막는다 — 그건
①·②의 몫이다. 이 구분을 정확히 말하면 도구의 적용 범위를 아는
것이다.

### ④ 사전 갱신 (refresh-ahead) — 만료가 오기 전에 미리 채우기

인기 키 목록을 알고 있다면, 만료를 기다리지 말고 **스케줄러/배치가
만료 전에 미리 갱신**한다. 사용자 요청은 항상 히트만 본다.

- Caffeine(로컬 캐시)은 `refreshAfterWrite`로 내장 지원 — 쓴 지 N분
  지난 키에 접근이 오면, 낡은 값을 반환하면서 백그라운드로 갱신.
- Redis라면 "인기 키 상위 N개를 주기적으로 재적재하는 배치"로 구현.
  대상 키가 명확하고 수가 적은 핵심 데이터(메인 페이지 구성요소)에
  적합하다. 모든 키에 적용하면 안 쓰는 키까지 갱신하는 낭비가 되므로
  대상 선정이 곧 설계다.

### (가산점 포인트) ⑤ 확률적 조기 재계산 — PER

만료 시각이 다가올수록 **각 요청이 확률적으로 "미리 재계산"을
자원**하게 하는 기법(Probabilistic Early Recomputation, XFetch로
알려진 알고리즘). 만료 직전에 누군가가 자연스럽게 갱신해두므로 락
없이도 스탬피드가 완화된다. 락 인프라 없이 코드만으로 되는 대신
동작이 확률적이라 보장은 약하다 — 존재를 알고 트레이드오프를 말하면
가산점.

## 3. 실무 감각 — "TTL 1시간 캐시" PR에 남길 리뷰 코멘트

동료가 인기 목록 조회를 `TTL 1시간 캐시`로 감싸고 테스트를 통과시킨
PR — 지금은 잘 동작한다. 트래픽 10배에서 붕괴하는 지점이 이 문서의
내용 그대로다:

- "이 키는 만료 순간 동시 미스가 몇 개나 되나요? 재계산 쿼리가
  느리다면 그 수만큼 DB에 중복 실행됩니다 (스탬피드)."
- "적재 시각이 몰리면 만료도 몰립니다 — TTL에 지터를 섞으면
  좋겠습니다."
- "이 데이터는 몇 분 낡아도 되는 성격이니, 물리 만료 대신 논리
  만료 + 백그라운드 갱신이 더 안전해 보입니다."

"지금 잘 동작하는 코드"에서 트래픽 조건이 바뀌었을 때의 붕괴 지점을
배포 전에 말할 수 있는지 — 이 질문 지식의 실행 가능한 형태다.

## 4. 꼬리질문 대비 포인트

### "락 방식에서, 락을 잡은 요청이 죽어버리면 어떻게 되나요?"

락에 TTL이 없으면 아무도 재계산을 못 하는 교착이 된다. 그래서 분산
락에는 반드시 **락 TTL**을 건다 — 잡은 놈이 죽어도 TTL 후 자동
해제된다. 대신 새 함정이 생긴다: 재계산이 락 TTL보다 오래 걸리면
락이 먼저 풀려 두 번째 놈이 또 재계산에 들어간다 (락 소유자 검증,
워치독 연장 — 분산 락 문서의 주제). 그리고 락을 못 잡은 요청들의
**대기에도 반드시 타임아웃**을 걸어야 한다 — 무한 대기는 스레드 풀
고갈로 이어져, DB를 지키려다 애플리케이션이 먼저 죽는다.

### "락을 못 잡은 요청은 대기시키나요, 이전 값을 주나요?" (시니어 변별 포인트)

정합성과 지연의 트레이드오프 문제다. **대기**는 모두가 최신 값을
받지만 재계산 시간만큼 응답이 늦고, 대기자가 쌓이면 스레드 풀을
위협한다. **stale 반환**은 응답이 즉시 나가지만 재계산이 끝날 때까지
낡은 값이 서빙된다. 판단 기준은 데이터 성격이다 — 인기 목록·랭킹은
몇 초 낡아도 아무도 모르므로 stale 반환이 정답에 가깝고, 재고
수량처럼 낡은 값이 잘못된 행동(품절 상품 구매 시도)을 유발하는
데이터는 대기 또는 애초에 캐시하지 않는 선택이 맞다. "무엇을
캐시했는가에 따라 다르다"를 근거와 함께 말하는 것이 시니어 답변이다.

### "TTL 지터만 넣으면 스탬피드가 해결되나요?"

아니다. 지터는 **여러 키가 같은 시각에 만료되는 것**을 흩뜨릴 뿐,
**단일 인기 키**가 만료되는 그 순간의 동시 미스는 그대로다. 메인
페이지 인기 목록 키 하나가 초당 수천 요청을 받는다면 지터와 무관하게
그 키의 만료 순간 스탬피드가 난다. 지터는 값싸고 부작용이 없어 항상
깔아두는 기본기이고, 인기 키에는 락이나 논리적 만료를 얹는다 —
"어느 지점을 공략하는 도구인지"의 구분이 이 꼬리질문의 핵심이다.

### "@Cacheable(sync = true)를 썼는데 서버가 10대라면?"

sync = true는 스프링이 **같은 JVM 안에서** 한 스레드만 실행하도록
직렬화하는 것이라, 10대면 최악의 경우 재계산이 10번 동시 실행된다.
여기서 바로 "그러니 분산 락"으로 점프하지 말고 **10번이 감당
가능한지부터** 따진다 — 원래 문제가 "수천 번의 중복 실행"이었다면
10번은 대부분 무해하고, 분산 락은 락 TTL·소유자 검증·해제 실패라는
새 복잡도를 데려온다. 재계산이 정말 비싸거나(수 초짜리 집계) DB
여력이 없을 때만 분산 락으로 승격한다. 복잡도를 추가하는 결정에
근거를 대는 모습이 곧 변별 포인트다.

### "캐시 관통(penetration)과는 뭐가 다른가요?"

스탬피드는 **존재하는 인기 키의 만료 순간** 폭주 — 시간 축의 문제고,
관통은 **애초에 존재하지 않는 키**의 반복 조회 — 키 공간의 문제다.
관통은 만료와 무관하게 매 요청이 미스이므로 락·지터가 아니라
**null 캐싱(없음을 짧은 TTL로 기억) 또는 블룸 필터(존재할 리 없는
키를 DB 전에 걸러냄)**가 해법이다. 둘 다 "미스가 DB를 때린다"는
증상이 같아 혼동하기 쉬운데, 원인이 다르면 처방이 다르다.

## 한 줄 요약

캐시 스탬피드는 인기 키·비싼 재계산·만료 순간이라는 세 조건이 겹칠 때
미스 창에 도착한 요청 전부가 DB로 직행해 자기 강화 붕괴를 만드는
현상이고 — 락(재계산 1회 제한), 논리적 만료(미스 창 제거), TTL
지터(동시 만료 분산), refresh-ahead(만료 전 선제 갱신)가 각각 다른
지점을 공략하므로, 데이터의 낡음 허용치와 인프라 복잡도를 저울질해
조합하는 것이 답이다.
