# Cold cache와 캐시 워밍 — "복구 완료"와 "히트율 회복" 사이의 시간

> 핵심 관전 포인트: **캐시 히트율을 전제로 용량이 설계된 시스템은,
> 캐시가 비어 있는 순간 DB가 원래 트래픽을 그대로 맞는다 — 캐시는
> 살아 있고 프로세스도 정상인데 시스템은 장애 상태인 것이 cold
> cache다. 로컬 캐시는 앱을 배포할 때마다, Redis는 영속화 없이
> 재시작·복구될 때마다, 그리고 캐시 플러시·키 버전 변경 때마다
> 발생한다. 대응은 트래픽을 받기 전에 인기 키를 미리 적재하는
> 워밍(pre-warming), 캐시가 채워질 시간을 벌어주는 점진적 트래픽
> 유입(ramp-up), 캐시 수명을 배포 수명과 분리(외부 캐시 + 영속화·
> replica)하는 것 — 즉 배포·복구 절차에 "프로세스가 떴는가"만이
> 아니라 "캐시가 채워졌는가"라는 축을 넣는 운영 감각이 핵심이다.**

---

## 0. 질문 + 의도

**질문**: "배포나 장애 복구 직후 캐시가 비어 있는 상태(cold cache)로
트래픽을 받으면 무슨 일이 벌어지나요? 캐시 워밍은 어떻게 하나요?"

**출제 의도**: 캐시 히트율을 전제로 용량이 설계된 시스템은 캐시가 빈
순간 DB가 원래 트래픽을 그대로 맞는다. 배포·장애 복구 절차에 "캐시
상태"라는 축이 들어 있는지 — 캐시 무력화 방어(고난이도 문항)와 같은
뿌리의 운영 감각이다.

## 1. Cold cache에서 벌어지는 일 — 모든 게 정상인데 장애인 상태

warm cache(운영 중 데이터가 채워진 캐시)에서 히트율 90%로 돌던
시스템이 있다고 하자. 캐시가 빈 채로 트래픽을 받으면:

- **히트율 0%에서 시작** — 전 요청이 미스. DB는 평소의 10배에
  해당하는 유효 부하를 맞는다. 캐시 무력화(캐시가 죽은 상황, → 19번
  문서)와 부하 크기는 같은데, **이번엔 아무것도 고장 나지 않았다**는
  점이 음험하다. 프로세스도 Redis도 헬스체크도 전부 초록불인데 DB만
  비명을 지른다.
- **미스 폭주는 스탬피드의 전체판** — 스탬피드(→ 06번 문서)가 "인기
  키 하나의 만료"라면, cold cache는 **모든 인기 키가 동시에 미스인
  상태**다. 같은 인기 키에 대한 동시 요청들이 각자 DB를 때리는 중복
  재계산이 키마다 벌어진다.
- **적재 쓰기 폭주** — 미스마다 캐시 SET이 따라오므로 복구 직후
  Redis에 쓰기가 몰리고, 직렬화 비용으로 애플리케이션 CPU도 평소보다
  높다.
- **지연 스파이크와 오탐 연쇄** — p99 지연이 튀면서 타임아웃·재시도가
  늘고, 헬스체크가 지연에 민감하게 설정돼 있으면 멀쩡한 인스턴스가
  비정상 판정을 받아 재기동되는 2차 사고(재기동 = 로컬 캐시 또
  cold)로 번질 수 있다.

한 문장으로: **"복구 완료 = 프로세스가 떴다"가 아니라 "히트율이
회복됐다"까지가 복구다.** 이 인식이 이 질문의 채점 기준이다.

### 언제 cold가 되는가 — 생각보다 자주

- **로컬 캐시(Caffeine)는 배포할 때마다** — 프로세스 메모리에 사는
  캐시는 재배포·재시작 = 전멸이다. 오토스케일로 새로 뜬 인스턴스도
  cold로 시작한다.
- **Redis 재시작·장애 복구** — 영속화(RDB/AOF) 없이 운영하는 캐시
  용도 Redis는 재시작하면 빈 채로 뜬다. 페일오버로 승격된 replica는
  데이터를 갖고 있지만, 복제가 깨져 있었다면 부분 cold다.
- **의도적 무효화** — 캐시 전체 플러시, 캐시 키 버전 변경(직렬화
  구조 변경 배포), 캐시 클러스터 이전. "우리가 버튼을 눌러서" cold를
  만드는 경우라 오히려 예방 가능성이 가장 높다.

## 2. 캐시 워밍 — 트래픽이 오기 전에, 또는 트래픽을 천천히

### ① 사전 적재 (pre-warming) — 인기 키를 미리 채워 넣기

트래픽을 받기 전에 워밍 작업이 인기 키들을 조회·적재한다. 관건은
**"인기 키를 어떻게 아는가"** — 전체 데이터를 다 넣는 건 워밍이
아니라 DB 풀스캔이다.

- **접근 패턴 기반**: 접근 로그·캐시 미스/히트 로그에서 상위 N개 키
  집계, 또는 장애 전 Redis의 키 목록 덤프(SCAN으로 주기 백업).
- **비즈니스 지식 기반**: 메인 페이지 구성요소, 인기 상품 상위
  1000개, 활성 테넌트의 설정 — 도메인이 이미 알려주는 것들.
- 파레토 법칙이 우군이다 — 트래픽의 대부분은 소수 키에 몰리므로,
  **상위 일부만 채워도 히트율은 대부분 회복**된다. 전량 워밍은
  필요도 없고 해서도 안 된다.

```java
// 배포 파이프라인 또는 ApplicationReadyEvent에서 실행하는 워밍 작업
@EventListener(ApplicationReadyEvent.class)  // 앱 기동 직후, LB 투입 전
public void warmUp() {
    List<Long> hotProductIds = warmupKeyProvider.topN(1000); // 인기 키 출처: 로그 집계

    for (List<Long> chunk : Lists.partition(hotProductIds, 100)) {
        List<Product> products = productRepository.findAllById(chunk); // 청크 단위 벌크 조회
        products.forEach(p -> redis.set(key(p.getId()), p, ttlWithJitter()));
        // ttl에 지터: 워밍으로 "같은 시각 대량 적재"가 일어나므로
        // 지터 없이는 N시간 뒤 "같은 시각 대량 만료" = 스탬피드 예약이 된다
        throttle();  // DB·Redis를 워밍 작업이 때리지 않게 속도 제한
    }
}
```

워밍 코드에서 짚을 세 가지 (그대로 말하면 가산점 포인트):

- **워밍 완료 전에 LB에 투입하지 않기** — readiness probe를 워밍
  완료와 연동하거나, 배포 파이프라인에서 워밍 단계를 트래픽 투입
  앞에 둔다.
- **워밍 자체의 부하 제어** — 스로틀, 청크 단위 벌크 조회, 가능하면
  DB replica에서 읽기. 워밍이 새벽 배포라면 여유가 있지만 장애 복구
  중이라면 DB도 여력이 없는 상태다.
- **적재 TTL에 지터** — 워밍은 정의상 동시 대량 적재이므로, 지터가
  없으면 몇 시간 뒤 동시 대량 만료라는 스탬피드를 스스로 심는 셈이다.

### ② 점진적 트래픽 유입 (ramp-up) — 캐시가 채워질 시간 벌기

사전 적재가 어렵다면(인기 키 예측 불가, 키 공간이 넓음) 트래픽
쪽을 조절한다. LB 가중치를 낮게 시작해 서서히 올리거나(카나리와
같은 메커니즘), 신규 인스턴스에 슬로우 스타트를 준다. 초기의 적은
트래픽이 자연스럽게 인기 키부터 캐시를 채우고 — 실제 접근 패턴이
곧 워밍이므로 "무엇을 채울지" 고민이 필요 없다는 게 장점이다.
롤링 배포는 로컬 캐시에 대해 이 효과를 공짜로 준다 — 한 번에 한
인스턴스만 cold이므로 전체 히트율 하락이 1/N로 희석된다.

### ③ 캐시 수명을 배포 수명과 분리 — cold 자체를 줄이는 구조

가장 근본적인 축은 "워밍을 잘하기"가 아니라 **"cold가 되는 횟수를
줄이기"**다.

- **외부 캐시(Redis) 중심 구조**: 앱을 아무리 배포해도 Redis의
  데이터는 살아 있다 — 로컬 캐시 위주 구조가 배포마다 cold인 것과의
  결정적 차이. 로컬 캐시를 쓰더라도 뒤에 Redis를 겹친 2단 구조면
  로컬이 cold여도 Redis 히트로 DB를 보호한다.
- **Redis 영속화·replica**: 캐시 용도라도 RDB 스냅샷을 켜두면 재시작
  시 "다소 낡았지만 채워진" 상태로 뜬다 — 캐시는 어차피 낡음을
  허용하는 데이터라 스냅샷 시점의 낡음은 대부분 무해하고, cold보다
  압도적으로 낫다. 장애 시 replica 승격은 데이터를 유지한 채
  페일오버하므로 cold 자체가 발생하지 않는다.
- **전체 플러시 대신 키 버전 전환**: 배포로 캐시 구조가 바뀔 때
  FLUSHALL이 아니라 키에 버전을 넣어 새 버전 키가 점진적으로 채워지게
  한다 — 의도적 cold를 점진적 워밍으로 바꾸는 설계다.

### (가산점 포인트) ④ 트래픽 리플레이 / 섀도잉

운영 접근 로그의 최근 요청을 신규 환경에 재생(replay)하거나, 운영
트래픽을 복제해 응답은 버리고 캐시만 채우는(shadow traffic) 방식.
대규모 캐시 클러스터 이전처럼 "실 트래픽과 동일한 분포로 채워야
하는" 상황에서 쓴다. 구축 비용이 있어 상시 장치라기보다 이전·재해
복구 시나리오용이다.

## 3. 운영 절차 관점 — 체크리스트에 "캐시 상태" 축 넣기

이 질문의 뿌리는 기법이 아니라 절차다. 배포·복구 런북에 다음이
들어 있는지가 곧 답변의 완성도다:

- 배포 절차: 워밍 단계가 트래픽 투입 **앞에** 있는가, readiness가
  워밍과 연동되는가.
- 복구 절차: "Redis 재기동 완료"가 아니라 "히트율 X% 회복"이 복구
  완료 조건인가.
- 모니터링: **캐시 히트율이 대시보드의 1급 지표**인가 — cold 상태는
  에러율로는 안 보이고 히트율과 DB 부하로만 보인다. 히트율 급락
  알람이 있으면 cold를 사람보다 먼저 안다.
- 방어와의 연결: 스탬피드 대책(락, sync=true — 06번)과 DB 유입
  제어(load shedding — 19번)가 깔려 있으면 cold 순간의 미스 폭주도
  같은 장치가 완충한다. 워밍은 이 방어들 위에 얹는 것이지 대체재가
  아니다.

## 4. 꼬리질문 대비 포인트

### "인기 키를 어떻게 알아내서 워밍하나요?"

세 출처를 조합한다 — ① 접근 로그·미스 로그 집계로 상위 N개 키를
주기적으로 산출해 두거나, ② 운영 Redis의 키 스냅샷을 SCAN으로 주기
백업해 두거나(장애 대비용 — 죽기 전 캐시의 키 목록이 최고의 워밍
목록이다), ③ 도메인 지식(메인 페이지 데이터, 인기 상품 상위권,
활성 테넌트 설정)으로 정적 목록을 관리한다. 파레토 분포 덕에 상위
일부만 채워도 히트율 대부분이 회복되므로 "전체가 아니라 상위 N"이
핵심이고, N은 히트율 기여 누적치로 정한다.

### "워밍 배치가 오히려 DB를 때리는 것 아닌가요?"

맞다, 그래서 워밍 작업도 부하 설계가 필요하다 — 청크 단위 벌크
조회(단건 N번 금지), 호출 간 스로틀, 가능하면 DB replica에서 읽기,
그리고 배포라면 트래픽이 낮은 시간대 실행. 중요한 차이는 워밍 부하가
**통제된 부하**라는 것이다 — 속도·시점·양을 우리가 정하지만, cold로
트래픽을 받으면 같은 양의 부하가 통제 불가능한 형태(동시 미스 폭주)로
온다. "어차피 낼 부하를 통제된 형태로 미리 내는 것"이 워밍의 본질이다.

### "Redis에 영속화를 켜두면 워밍이 필요 없지 않나요?"

상당 부분 대체하지만 전부는 아니다. RDB 스냅샷 복구는 "스냅샷 시점의
데이터"라 낡음이 있고(캐시라 대부분 허용 가능), AOF도 장애 유형에
따라 유실 구간이 있다. 무엇보다 영속화가 못 덮는 cold가 있다 —
로컬 캐시의 배포 cold, 키 버전 변경, 클러스터 이전, 그리고 영속화
파일까지 잃는 장애. 또 캐시 용도 Redis에 AOF까지 켜는 건 쓰기 성능·
디스크라는 비용이 있어 "캐시는 유실 허용이니 영속화 없이, 대신 워밍
절차로"라는 반대 방향의 선택도 유효하다. 어느 쪽이든 "재시작하면
데이터가 어떻게 되는지"를 알고 내린 결정인지가 관전 포인트다.

### "로컬 캐시(Caffeine)를 쓰는 서비스의 롤링 배포에서는 무슨 일이 벌어지나요?" (시니어 변별 포인트)

인스턴스가 하나씩 교체되므로 매 순간 "방금 뜬 cold 인스턴스"가
존재하고, LB가 그쪽으로 보낸 요청만 미스를 겪는다 — 전체 히트율
하락은 1/N로 희석되므로 롤링 자체가 자연스러운 점진 워밍이다. 다만
함정이 있다: **배포 속도를 올려 동시 교체 폭을 키우면 cold 비율이
그만큼 커진다** — "배포를 빨리 끝내고 싶다"와 "캐시 완충을 유지하고
싶다"가 충돌하는 지점이고, 최대 동시 교체 수(maxUnavailable/maxSurge
류 설정)가 사실상 캐시 워밍 파라미터가 된다. 오토스케일 급증 시에도
새 인스턴스는 전부 cold라 "스케일아웃 했는데 지연이 더 튀는" 역설이
난다 — 기동 시 웜업(자주 쓰는 데이터 선적재, JIT 웜업 포함) 후 투입이
해법이다. 배포 파라미터를 캐시 관점으로 읽는 것이 변별 지점이다.

### "히트율이 회복됐는지는 어떻게 확인하나요?"

캐시 히트율(히트/전체 조회)을 애플리케이션 메트릭으로 노출(Micrometer
등)하고 대시보드 1급 지표로 둔다 — Redis 서버 쪽 keyspace hit/miss
통계로도 교차 확인. 함께 볼 것은 DB 쿼리 수·커넥션 사용률(히트율의
거울 지표)과 p99 지연이다. 운영 기준선(예: 평시 히트율)을 알고 있어야
"회복됐다"를 판정할 수 있으므로, 평시 지표를 모르면 복구 판정 자체가
불가능하다 — cold cache 대응의 절반은 평상시 모니터링이다.

## 한 줄 요약

Cold cache는 아무것도 고장 나지 않았는데 DB가 원래 트래픽을 그대로
맞는 상태 — 모든 인기 키가 동시에 미스인 스탬피드의 전체판이므로,
인기 키 사전 적재(pre-warming, 지터·스로틀 포함)와 점진 트래픽
유입으로 채워질 시간을 벌고, 근본적으로는 외부 캐시·영속화·키
버저닝으로 cold가 되는 횟수 자체를 줄이며, "프로세스가 떴다"가 아니라
"히트율이 회복됐다"를 배포·복구 완료 조건으로 삼는 운영 절차가 답이다.
