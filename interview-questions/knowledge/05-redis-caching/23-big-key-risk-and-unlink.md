# Big Key와 UNLINK — 지우는 법보다 만들지 않는 설계가 먼저다

> 핵심 관전 포인트: **big key(수백만 멤버의 Set/Hash/List 하나)는
> 싱글 스레드 Redis에서 그 키를 만지는 모든 연산 — 전체 조회, 삭제,
> 만료, 클러스터 마이그레이션 — 을 블로킹 폭탄으로 만든다. 특히
> `DEL`은 멤버 수에 비례하는 O(N)이라 수백만 멤버 키 하나를 지우는
> 순간 서버가 수 초 멈춘다. 안전한 삭제는 `UNLINK` — 키 공간에서
> 이름만 O(1)로 떼어내고 실제 메모리 해제는 백그라운드 스레드에
> 맡긴다. 하지만 UNLINK는 "이미 만들어진 폭탄의 안전한 처리법"일
> 뿐이고, 본질은 키 설계 단계에서 컬렉션을 버킷으로 쪼개고 TTL
> 규율을 세워 big key가 만들어지지 않게 막는 것이다.**

---

## 0. 질문 + 의도

**질문**: "Big key(수백만 멤버 컬렉션)는 왜 위험한가요? 안전하게
삭제하려면? (UNLINK)"

**출제 의도**: 수백만 멤버 컬렉션은 조회·삭제·마이그레이션 전부를
블로킹 폭탄으로 만든다. big key는 지우는 법(UNLINK, 점진 삭제)보다
만들어지기 전에 키 설계로 막는 것임을 아는지 — 사후 대응 지식과
예방 설계 감각을 함께 본다.

## 1. 왜 위험한가 — 키 하나가 서버 전체의 급소가 된다

big key는 보통 "컬렉션 하나에 멤버가 수십만~수백만 개" 또는 "값
하나가 수 MB 이상"인 키를 말한다. 문제의 뿌리는 Redis의 많은 연산이
**키 단위로는 쪼개지지 않는다**는 것 — 싱글 스레드에서 그 키를 통째로
만지는 순간마다 서버가 선다. 배는 멀쩡한데 화물 하나가 너무 커서
크레인이 들 때마다 항구 전체가 멈추는 상황이다.

위험이 터지는 지점을 연산별로 보면:

- **전체 조회**: `SMEMBERS`, `HGETALL`, `LRANGE 0 -1` 등은 멤버 수에
  비례하는 O(N)이다. 수백만 멤버를 응답으로 만들면 이벤트 루프
  점유에 더해, 응답을 담는 출력 버퍼가 부풀고 네트워크로 수십 MB가
  쏟아진다.
- **삭제**: `DEL`은 O(1)이 아니다 — 컬렉션 멤버를 하나하나 해제하는
  **O(N)**이라, "이제 안 쓰니 지우자"는 정리 작업이 곧 장애가 된다.
- **만료(expire)**: TTL이 걸린 big key가 만료되는 순간에도 같은 해제
  비용이 발생한다. 지운 적이 없는데 "특정 시각마다 Redis가 멈춘다"는
  미스터리 지연의 단골 원인이다.
- **클러스터 마이그레이션/리샤딩**: 슬롯 이동은 키 단위로 일어나는데
  big key는 통째로 직렬화해 옮겨야 해서 이동이 오래 걸리거나
  실패한다 — "샤드를 늘리면 되지"라는 확장 계획이 big key 하나에
  막힌다.
- **복제·영속화 부담**: 전체 동기화 시 직렬화 비용이 크고, 메모리가
  한 노드에 편중돼 클러스터의 분산 효과를 깎는다. 접근까지 몰리면
  hot key 문제와 겹친다.

즉 big key는 "느린 명령" 문제가 아니라 **조회·삭제·만료·이동 전
생애주기가 블로킹인 데이터 모양** 문제다. KEYS가 "전체 키 공간을
훑는 명령"의 위험이라면(→ `12-keys-vs-scan.md`), big key는 "키
하나가 너무 큰" 위험 — 같은 싱글 스레드 블로킹의 다른 얼굴이다.

## 2. 안전한 삭제 — UNLINK와 점진 삭제

### UNLINK: 이름은 지금 떼고, 해제는 뒤에서

```text
DEL bigset     → 키 제거 + 멤버 N개 메모리 해제를 지금, 메인 스레드에서 (O(N) 블로킹)
UNLINK bigset  → 키 공간에서 이름만 즉시 분리 (O(1))
                 실제 메모리 해제는 백그라운드(lazy-free) 스레드가 수행
```

UNLINK 직후 그 키는 더 이상 보이지 않고(같은 이름으로 새 키 생성도
가능), 비용이 큰 해제 작업만 뒤로 넘어간다. 명령 처리 자체는 여전히
싱글 스레드지만, **메모리 해제는 별도 스레드가 해도 안전**하기에
가능한 분리다. 작은 키는 UNLINK도 그냥 그 자리에서 해제한다 —
비동기화가 이득인 크기일 때만 백그라운드로 넘기므로, "DEL 대신
UNLINK"를 기본 습관으로 삼아도 손해가 없다.

삭제 명령만 바꿔서는 절반이다 — **만료와 eviction도 같은 폭탄**이므로
설정으로 함께 비동기화한다:

```text
# redis.conf — 삭제 이외의 해제 경로도 lazy-free로
lazyfree-lazy-expire yes       # TTL 만료 시
lazyfree-lazy-eviction yes     # maxmemory 도달로 쫓아낼 때
lazyfree-lazy-user-del yes     # DEL을 UNLINK처럼 동작시킴
lazyfree-lazy-server-del yes   # 내부적 암묵 삭제(덮어쓰기 등)
```

### 점진 삭제: 컬렉션을 안에서부터 갉아내기

UNLINK가 없던 시절의 방법이자, 지금도 "해제 부하 자체를 시간축으로
펴고 싶을 때" 쓰는 패턴 — SCAN 계열로 멤버를 배치로 꺼내 지운다:

```java
// Before: 한 방 삭제 — 수백만 멤버면 서버 정지
redis.delete("bigset");

// After(1): UNLINK — 대부분의 경우 이걸로 충분
redis.unlink("bigset");

// After(2): 점진 삭제 — SSCAN으로 배치 단위 SREM (Hash면 HSCAN+HDEL)
ScanOptions opt = ScanOptions.scanOptions().count(500).build();
try (Cursor<String> cursor = redis.opsForSet().scan("bigset", opt)) {
    List<String> batch = new ArrayList<>(500);
    while (cursor.hasNext()) {
        batch.add(cursor.next());
        if (batch.size() == 500) {
            redis.opsForSet().remove("bigset", batch.toArray());
            batch.clear();
            // 필요 시 배치 사이 짧은 대기로 부하를 흘려보냄
        }
    }
    if (!batch.isEmpty()) redis.opsForSet().remove("bigset", batch.toArray());
}
redis.unlink("bigset");  // 마지막 잔여분 정리
```

### 감지: 폭탄이 이미 있는지 찾기

- `redis-cli --bigkeys`: SCAN 기반으로 전체를 점진 순회하며 타입별
  최대 키를 리포트한다 — 운영 중에도 비교적 안전하게 돌릴 수 있다.
- `MEMORY USAGE <key>`: 특정 키의 메모리 사용량 확인.
- `SCAN` + 타입별 `SCARD`/`HLEN`/`LLEN`(멤버 수 확인은 O(1))으로
  자체 감사 스크립트를 돌려 주기적으로 리포트하는 팀도 많다.
- 징후로는: 특정 시간대의 latency 스파이크, SLOWLOG에 찍힌
  DEL/HGETALL, 클러스터 노드 간 메모리 편중.

## 3. 본질은 예방 — big key가 만들어지지 않는 키 설계 (가산점 포인트)

UNLINK는 "안전한 폭탄 처리"지 해법이 아니다. big key는 대부분
**"전부를 한 키에 모으는" 모델링**에서 생기므로, 설계로 막는다:

```text
# Before: 전 사용자의 방문 기록을 키 하나에
visited:all                     → Set 멤버 수천만 개

# After: 버킷 분할(sharding) — 사용자 id 해시로 1024개 버킷에 분산
visited:{userId % 1024}         → 버킷당 수만 개 수준
# 조회·삭제·마이그레이션이 전부 버킷 단위 = 블로킹 없음
# 전체 집계가 필요하면 버킷을 순회 합산 (또는 카운트는 HyperLogLog로)
```

- **버킷 분할**: 컬렉션을 해시로 N등분. 단일 키 연산은 그대로 빠르고,
  전체 연산은 버킷 순회로 바뀌어 자연스럽게 점진적이 된다. 대신
  "컬렉션 전체에 대한 원자적 연산"은 포기하는 트레이드오프다.
- **TTL 규율**: 무한히 자라는 키는 대부분 "지우는 규칙이 없는" 키다.
  쌓이는 데이터라면 기간별 키(`daily:2026-08-31:…`)로 잘라 TTL로
  자연 소멸시킨다.
- **용도에 맞는 자료구조**: "존재 여부만" 필요한데 Set에 원본 값을
  다 넣고 있다면 Bitmap/HyperLogLog로 수백 배 작게 해결될 수 있다.
- **경계 모니터링**: 컬렉션에 쓰기 전에 크기 상한을 두거나(넘으면
  알람/버킷 증설), 주기 감사로 성장 추세를 본다 — "big key는 어느 날
  갑자기가 아니라 조용히 자라서 발견된다".

면접에서 "UNLINK 쓰면 됩니다"에서 멈추면 반쪽이고, "왜 이 키가
수백만 멤버가 되도록 설계됐는가를 먼저 묻겠다"까지 가야 출제 의도에
정면으로 답하는 것이다.

## 4. 꼬리질문 대비 포인트

### "UNLINK가 백그라운드에서 해제한다면, 그 사이 메모리는요?"

해제가 끝날 때까지 메모리는 점유된 상태다. 즉 UNLINK는 지연을
없애는 것이지 메모리를 즉시 돌려주는 게 아니다 — maxmemory에 이미
근접한 상태에서 "지웠는데 왜 메모리가 안 줄지?"의 답이 이것이다.
백그라운드 해제가 쓰기 유입 속도를 못 따라가면 일시적으로 메모리가
더 오를 수도 있으므로, OOM 직전의 비상 정리는 해제 속도까지 감안해야
한다.

### "DEL이 O(N)인 걸 몰랐다면 어떤 장애로 나타나나요?"

배치성 정리 작업(예: 자정에 전일 캐시 삭제)이 도는 시각마다 수 초의
latency 스파이크가 찍히고, 그 시간대의 API 타임아웃이 몰린다.
SLOWLOG를 보면 DEL이 최상단에 있다. TTL 만료도 같은 해제 비용이라,
같은 시각에 대량 생성된 키들이 같은 시각에 만료되며 스파이크를
만들기도 한다 — TTL에 지터(무작위 가감)를 주는 이유가 캐시 스탬피드
방지만이 아니라 만료 해제 부하 분산이기도 하다.

### "big key를 읽어야만 한다면 어떻게 안전하게 읽나요?"

전체 반환 명령(SMEMBERS/HGETALL/LRANGE 0 -1)을 금지하고 커서 계열
(SSCAN/HSCAN/ZSCAN, List는 LRANGE를 구간으로 잘라)로 배치 순회한다.
페이징이 목적이라면 애초에 Sorted Set의 범위 조회처럼 "부분만 읽는
연산이 O(log N + 반환분)"인 구조를 고른다. 그리고 이 질문 자체를
"왜 전체를 읽어야 하는 요구가 생겼지?"로 되돌려 모델링을 의심하는
것이 상급이다.

### "클러스터 확장 계획 중인데 big key가 있다면 순서는요?" (시니어 변별 포인트)

리샤딩이 big key에서 막히므로 **분해가 먼저다**: (1) --bigkeys 등으로
전수 조사, (2) 신규 쓰기를 버킷 구조로 전환(dual-write 또는 신규
버전 키), (3) 기존 big key는 SCAN 배치로 새 구조에 옮기고, (4)
UNLINK로 원본 제거, (5) 그 다음 리샤딩. "인프라 확장이 데이터 모양에
발목 잡히는" 사례로, 확장 전에 데이터 감사부터 하는 순서 감각 —
그리고 버킷 수는 나중에 바꾸기 어려우니(재해싱 필요) 여유 있게
잡는다는 비가역 결정 인식까지 말하면 좋다.

### "Redis는 싱글 스레드라더니 백그라운드 해제 스레드는 뭔가요?"

"싱글 스레드"는 **명령 실행 경로**가 하나라는 뜻이다. 그 외 작업 —
lazy-free 해제, RDB/AOF 디스크 I/O(fork 자식 프로세스), 최근
버전의 I/O 스레드(네트워크 읽기/쓰기 보조) — 는 별도
스레드/프로세스가 담당한다. 명령 실행이 단일 경로라 락 없이
원자성이 보장되는 것이고, 그 경로 밖으로 뺄 수 있는 비용(메모리
해제, 디스크, 네트워크 I/O)을 빼내는 방향으로 진화해 왔다고
정리하면 구조 이해를 보여줄 수 있다.

## 한 줄 요약

big key는 조회·삭제·만료·마이그레이션 전부가 멤버 수에 비례하는
블로킹이 되는 "데이터 모양의 폭탄"이라, 지울 때는 O(N) DEL 대신
이름만 O(1)로 떼고 해제를 백그라운드로 넘기는 UNLINK(+
lazyfree 설정, 필요시 SSCAN 점진 삭제)를 쓴다 — 그러나 진짜 답은
버킷 분할과 TTL 규율로 **big key가 만들어지기 전에 키 설계로 막는
것**이다.
