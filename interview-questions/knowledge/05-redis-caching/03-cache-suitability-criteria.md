# 캐시 도입 판단 기준 — 캐시는 "정합성 완화"라는 비용을 지불하는 결정이다

> 핵심 관전 포인트: **캐시하기 좋은 데이터는 ① 읽기가 쓰기보다 압도적으로
> 많고 ② 자주 바뀌지 않으며 ③ 잠깐 낡은 값이어도 비즈니스가 허용하고
> ④ 원본 조회/계산 비용이 비싼 데이터다. 반대로 계좌 잔액·재고 차감
> 판단·권한처럼 낡은 값이 곧 돈·보안 사고가 되는 데이터는 캐시하면
> 안 된다. 그리고 진짜 기준은 데이터 종류가 아니라 "읽기의 용도" —
> 같은 잔액도 화면 표시용은 캐시할 수 있지만 출금 가능 판단은 반드시
> 원본을 봐야 한다. 즉 "이 값이 몇 초 낡아도 되는가"를 비즈니스에
> 물어보는 것이 캐시 도입 결정의 본질이다.**

---

## 0. 질문 + 의도

**질문**: "캐시를 도입하면 좋은 데이터와 도입하면 안 되는 데이터의 기준은?"

**출제 의도**: 캐시 도입은 "정합성 완화"라는 비용을 지불하는 결정이다.
잔액을 캐시하면 안 되는 이유를 즉답 못 하는 사람에게 결제 시스템을
맡길 수 없다 — 성능 개선 수단을 아는지가 아니라, 그 수단의 대가를
알고 트레이드오프를 판단할 수 있는지를 보는 질문이다.

## 1. 캐시가 하는 거래 — 성능을 사고, 정합성을 판다

캐시는 원본(DB)의 **사본**이다. 사본은 원본이 바뀌는 순간부터 낡기
시작하고, TTL(만료 시간)이나 무효화(evict)로 낡은 시간을 **줄일 수는
있어도 0으로 만들 수는 없다** — 캐시와 DB는 서로 다른 두 시스템이라
하나의 트랜잭션으로 함께 바꿀 수 없기 때문이다.

그래서 캐시 도입은 항상 이 거래다:

```
얻는 것: 응답 속도 (메모리 조회는 디스크/쿼리보다 수십~수백 배 빠름)
         DB 부하 감소 (읽기 트래픽을 캐시가 흡수)
잃는 것: 정합성 (사용자가 "낡은 값"을 볼 수 있는 시간 창이 생김)
         복잡도 (무효화 로직, 장애 시나리오, 모니터링 대상 +1)
```

"캐시 붙이면 빨라지니까 좋다"가 아니라 "이 데이터는 낡아도 되는가?"를
먼저 묻는 것이 올바른 순서다. 면접에서 이 프레임(비용을 지불하는 결정)
을 첫 문장으로 깔면 이후 답변 전체에 설득력이 생긴다.

## 2. 도입하면 좋은 데이터 — 4가지 기준

네 가지를 **동시에** 만족할수록 캐시 효과가 크다.

### ① 읽기 ≫ 쓰기 (읽기 비율이 압도적)

캐시의 이득은 히트(hit)에서 나오고, 쓰기는 매번 무효화/갱신 비용을
낸다. 읽기 100 : 쓰기 1이면 캐시 한 번 채워서 100번 우려먹지만,
읽기 1 : 쓰기 1이면 채우자마자 지우는 헛수고만 반복한다.

### ② 변경이 드물다

카테고리 트리, 공통 코드, 정책/설정값처럼 하루에 몇 번 바뀌지 않는
데이터는 TTL을 길게 줘도 안전하다. 반대로 초 단위로 바뀌는 값은
캐시가 낡아 있는 시간 비율이 높아진다.

### ③ 잠깐 낡아도 비즈니스가 허용한다 (staleness 허용)

이것이 **가장 중요한 기준**이다. "인기 웹툰 목록이 30초 전 기준이어도
되는가?" → 된다. "출금 가능 잔액이 30초 전 기준이어도 되는가?" →
안 된다(이중 출금). 허용 여부는 기술이 아니라 **비즈니스 요구사항**
이므로, 캐시 TTL을 정하는 일은 사실 기획/도메인과의 협상이다.

### ④ 원본 조회/계산이 비싸다

5개 테이블 조인 + 집계로 만드는 대시보드 통계, 외부 API 호출 결과처럼
한 번 만들기 비싼 값일수록 캐시 한 번의 이득이 크다. 반대로 PK 단건
조회처럼 이미 인덱스로 밀리초에 끝나는 쿼리는 캐시를 붙여도 체감
이득이 작고, 미스 시에는 오히려 왕복(캐시 조회 + DB 조회)이 늘어난다.

**전형적인 좋은 후보**: 인기 콘텐츠 목록, 카테고리/메뉴 트리, 상품
상세(설명·이미지 URL), 공통 코드, 화면 표시용 환율, 집계성 통계.

## 3. 도입하면 안 되는(신중해야 하는) 데이터

### ① 낡은 값이 곧 돈 사고 — 잔액, 포인트, 재고 "차감 판단"

캐시된 잔액으로 출금 가능 여부를 판단하면 어떻게 되는지 시나리오로:

```
캐시: 잔액 10,000원 (TTL 60초)
t=0  사용자가 A 기기에서 10,000원 출금 → DB 잔액 0원
     (캐시는 아직 10,000원 — 무효화 지연 or TTL 대기 중)
t=3  사용자가 B 기기에서 10,000원 출금 요청
     → 서버가 캐시를 보고 "잔액 충분" 판단 → 출금 승인
     → DB 잔액 -10,000원. 이중 출금 사고.
```

낡은 값을 근거로 **비가역적 결정**(출금 승인, 재고 차감, 쿠폰 발급)을
내리는 순간 정합성 완화가 금전 사고로 직결된다. 이런 판단은 반드시
원본(DB)에서, 그것도 조건부 연산으로 해야 한다:

```java
// ❌ 캐시(또는 미리 읽어둔 값)를 근거로 판단
Long balance = cache.get("balance:" + userId);   // 낡은 값일 수 있음
if (balance >= amount) {
    accountRepository.withdraw(userId, amount);   // 판단과 차감 사이도 벌어져 있음
}

// ✅ DB가 최종 심판 — 조건을 쿼리에 넣어 원자적으로 판단+차감
// UPDATE account SET balance = balance - :amount
//  WHERE user_id = :userId AND balance >= :amount
int updated = accountRepository.withdrawIfEnough(userId, amount);
if (updated == 0) {
    throw new InsufficientBalanceException();
}
```

### ② 즉시 회수가 요구되는 보안 데이터 — 권한, 세션 차단 상태

퇴사자 계정을 차단했는데 권한 캐시 TTL이 10분이면, 차단 후 10분간
그 계정이 살아 있다. "권한 변경은 즉시 반영"이 보안 요구사항이라면
캐시하지 않거나, 캐시하더라도 변경 이벤트로 **즉시 무효화하는 경로**
를 반드시 함께 깔아야 한다 (TTL만 믿으면 안 된다).

### ③ 히트율이 안 나오는 데이터 — 개인화·롱테일

캐시의 이득은 "같은 키가 반복 조회"될 때 나온다. 사용자별로 다 다른
개인화 결과나, 수백만 개 키가 골고루 한 번씩만 조회되는 롱테일
데이터는 히트율이 바닥이라 — 매 요청이 "캐시 조회(미스) + DB 조회 +
캐시 적재"가 되어 **캐시 없을 때보다 오히려 느려지고**, 메모리만
차지해 정작 인기 키를 밀어낸다(eviction).

### ④ 쓰기가 잦은 데이터

변경 때마다 무효화가 따라붙어 히트율은 낮고 무효화 비용·정합성이
깨질 기회만 늘어난다. 읽기:쓰기 비율이 낮으면 캐시 후보에서 뺀다.

## 4. 진짜 기준은 "데이터 종류"가 아니라 "읽기의 용도"

시니어 변별이 여기서 갈린다. "잔액은 캐시하면 안 된다"에서 멈추지
말고 한 걸음 더:

- **표시용 읽기** (마이페이지에 잔액 보여주기): 몇 초 낡아도 사용자
  경험 문제일 뿐 사고가 아니다 → 짧은 TTL(수 초) 캐시 + 변경 시
  무효화로 캐시 **가능**.
- **판단용 읽기** (출금 승인 여부 결정): 낡은 값이 곧 이중 출금 →
  캐시 **불가**, DB가 조건부 연산으로 최종 판단.

같은 데이터라도 읽기의 용도에 따라 답이 갈린다. 재고도 마찬가지 —
상품 목록에 "품절 임박" 배지를 띄우는 건 캐시로, 주문 시 재고 차감
판단은 DB(또는 Redis 원자 연산)로. 이렇게 **경로를 분리**하면 "잔액
조회 트래픽 때문에 DB가 힘든데 캐시는 못 쓰는" 딜레마가 풀린다.
(가산점 포인트: "캐시 가능 여부는 데이터가 아니라 read path별로
판단한다"고 명시적으로 말하기)

## 5. 꼬리질문 대비 포인트

### "잔액 조회 트래픽이 너무 많아서 DB가 힘들면 그래도 캐시 못 쓰나요?" (시니어 변별 포인트)

쓸 수 있다 — 단, **용도를 분리**해서. ① 표시용 조회는 짧은 TTL 캐시
+ 잔액 변경 트랜잭션 커밋 후 즉시 무효화로 흡수하고, ② 출금/결제
판단은 반드시 DB 조건부 UPDATE(원자적 판단+차감)로 남긴다. 판단
트래픽 자체가 병목이면 캐시가 아니라 Redis 원자 연산(DECRBY + Lua)
으로 판단 자체를 옮기는 설계(선착순 쿠폰과 동일 계열)를 검토한다 —
이건 "캐시"가 아니라 "판단 저장소의 이전"이라 정합성 책임도 함께
옮겨간다는 점을 구분해 말하면 상급.

### "쓰기가 많은 데이터를 캐시하면 구체적으로 무슨 일이 벌어지나요?"

변경 때마다 무효화/갱신이 따라붙어 히트율이 낮아지고(채우자마자
지움), 캐시-DB를 함께 바꾸는 지점이 많아질수록 순서 역전 같은
정합성 깨질 기회가 늘어난다. 결과적으로 이득(히트) 없이 비용
(무효화 로직, 정합성 리스크, 캐시 왕복)만 지불하는 구조가 된다.

### "히트율이 낮으면 캐시가 왜 '없느니만 못한' 게 되나요?"

미스 경로는 "캐시 조회 → 미스 → DB 조회 → 캐시 적재"로, 캐시가
없을 때(DB 조회 한 번)보다 네트워크 왕복이 2~3배다. 히트율이
낮으면 대부분의 요청이 이 비싼 경로를 타고, 적재된 데이터는 다시
안 읽혀 메모리만 차지하며 인기 키를 밀어낸다. 그래서 캐시 도입
후에는 **히트율 모니터링이 필수**다 — 히트율이 안 나오면 캐시를
빼는 것도 결정이다.

### "권한 정보를 캐시했는데 '차단 즉시 반영' 요건이 생기면 어떻게 하나요?"

TTL만으로는 못 지킨다(TTL 동안 살아 있음). ① 권한 변경 시 해당
키를 즉시 무효화하는 이벤트 경로를 깔고(같은 서비스면 커밋 후
evict, 다른 서비스면 pub/sub·메시지로 전파), ② 무효화 유실에
대비해 짧은 TTL을 안전망으로 겹친다. 그래도 전파 지연 수 초는
남으므로, "즉시"의 허용 오차(수 초 vs 0초)를 보안팀과 합의하는
것까지가 설계다 — 0초 요구면 캐시를 포기하는 게 답이다.

### "캐시 도입 전에 확인할 것을 체크리스트로 말해보세요"

① 읽기:쓰기 비율(읽기가 압도적인가), ② 허용 staleness(몇 초 낡아도
되는지 비즈니스와 합의), ③ 원본 비용(캐시 한 번의 이득 크기),
④ 예상 히트율(키가 반복 조회되는 분포인가), ⑤ 무효화 경로(변경
지점이 한 곳인가, 외부 변경은 없는가), ⑥ 캐시 장애 시나리오(캐시가
죽으면 DB가 그 트래픽을 버티는가). ⑥까지 말하면 운영 감각 가산점 —
캐시 히트를 전제로 용량을 설계하면 캐시 장애가 곧 DB 장애가 된다.

## 한 줄 요약

캐시 도입은 "속도를 사고 정합성을 파는 거래"라서 — 읽기가 압도적이고
변경이 드물며 낡아도 되는 비싼 데이터에는 이득이고, 잔액·재고 차감·
권한처럼 낡은 값이 곧 사고인 데이터에는 금지이며, 진짜 판단 기준은
데이터 종류가 아니라 읽기의 용도(표시용은 캐시, 비가역 판단용은 DB가
최종 심판)라는 것까지 말해야 트레이드오프를 아는 답변이 된다.
