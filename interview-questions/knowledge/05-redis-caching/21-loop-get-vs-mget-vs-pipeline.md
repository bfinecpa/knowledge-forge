# 루프 GET vs MGET vs Pipeline — Redis 성능의 지배 요인은 네트워크 왕복이다

> 핵심 관전 포인트: **Redis에서 키 100개를 조회할 때 진짜 비용은 명령 처리(마이크로초 단위)가 아니라 네트워크 왕복(RTT, 밀리초 단위)이다. 루프 GET은 왕복 100번 = RTT × 100이고, MGET과 pipeline은 왕복 1번으로 줄인다 — 같은 데이터를 가져오는데 지연이 수십 배 차이난다. 둘의 구분은: MGET은 "같은 종류(String 조회)의 멀티 키 명령 하나"라서 가장 단순하지만 String GET에만 쓸 수 있고 Cluster에서는 해시 슬롯 제약을 받는다. pipeline은 "서로 다른 명령 여러 개를 응답을 기다리지 않고 몰아 보내는 전송 방식"이라 조합이 자유롭지만, 트랜잭션이 아니므로 원자성은 없다. 리뷰에서 루프 안의 GET N번을 잡아내는 눈이 이 지식의 실전 형태다.**

---

## 0. 질문 + 의도

**질문**: "여러 키를 조회할 때 루프 GET, MGET, pipeline의 차이는?"

**출제 의도**: Redis 성능의 실제 지배 요인이 명령 처리 속도가 아니라 네트워크 왕복임을 아는지 본다. 루프 안에서 GET을 N번 치는 코드를 리뷰에서 잡는 눈 — "Redis는 빠르니까"라는 막연한 믿음이 아니라 지연이 어디서 생기는지를 분해해 본 경험이 있는지가 드러난다.

## 1. 비용의 분해 — 명령 처리는 마이크로초, 왕복은 밀리초

### 1-1. 전제 지식 — RTT가 무엇인가

이 주제의 모든 논의가 **RTT**라는 약어 위에 서 있으니 먼저 풀고 가자.

**RTT는 Round Trip Time, 즉 "왕복 시간"이다.** 요청이 클라이언트를 떠나 서버에 도착하고, 서버의 응답이 다시 클라이언트로 돌아오기까지 걸리는 전체 시간을 말한다. 편지를 부치고 답장을 받기까지의 시간이라고 보면 된다.

여기서 중요한 것은 **이 시간의 대부분이 Redis가 일한 시간이 아니라 그냥 오가는 데 쓰인 시간**이라는 점이다. Redis 명령 하나의 체감 지연을 쪼개면 이렇게 생겼다.

```text
[클라이언트]  --요청 전송-->  [Redis: 명령 처리]  --응답 전송-->  [클라이언트]
     |<------------------------ RTT (왕복 시간) ------------------------>|
     |<--- 이동 --->|         |<-- 실제 일 -->|        |<--- 이동 --->|
        수백 마이크로초           수 마이크로초           수백 마이크로초
```

자릿수로 대비하면 이렇다.

| 구간 | 하는 일 | 대략적 시간 |
|---|---|---|
| 명령 처리 | 메모리의 해시 테이블에서 값 하나 찾아 반환 | **마이크로초(µs)** 단위 |
| 네트워크 왕복 | 소켓 → 커널 → NIC → 스위치 → 반대 방향 | 같은 데이터센터 안이라도 **0.5ms 안팎** |

**0.5밀리초는 500마이크로초다.** 명령 처리가 1마이크로초라면 **비용의 500배가 이동 시간**인 셈이다. 물리적으로 멀어지면(다른 가용 영역, 다른 리전) 이 격차는 더 벌어진다.

택배에 비유하면 물건 포장(명령 처리)은 10초인데 배송 왕복이 이틀인 상황이다. 이런 상황에서 전체 시간을 결정하는 것은 포장 속도가 아니라 **물건 100개를 한 상자에 담아 한 번 보내느냐, 100번 따로 보내느냐**다.

그래서 이 질문의 본체는 "어떤 명령이 빠른가"가 아니라 **"왕복 횟수를 몇 번으로 줄일 수 있는가"**다.

### 1-2. 키 100개를 세 방식으로 조회했을 때 — 계산해 보자

세 방식의 시간을 실제로 계산해 보면 차이의 정체가 분명해진다. 계산에 쓸 가정은 둘이다.

- RTT = **0.5ms** (같은 데이터센터 안이라고 가정)
- 키 하나당 서버 처리 시간 = **1µs = 0.001ms**
- 조회할 키 = **100개**

**루프 GET**은 `GET key1`을 보내고 **응답이 올 때까지 기다렸다가** `GET key2`를 보낸다. 앞 응답을 받아야 다음 요청을 보내는 직렬 구조라 왕복이 키 수만큼 발생한다.

```
왕복 시간 = 0.5ms × 100 = 50ms
처리 시간 = 0.001ms × 100 = 0.1ms
합계     = 50.1ms
```

**MGET**은 `MGET key1 key2 ... key100`이라는 **명령 하나**를 보낸다. 왕복은 1번이고, 서버는 그 안에서 100개를 찾는다.

```
왕복 시간 = 0.5ms × 1 = 0.5ms
처리 시간 = 0.001ms × 100 = 0.1ms   <- 루프 GET과 똑같다
합계     = 0.6ms
```

**pipeline**은 `GET`을 100개 연달아 밀어 넣고 응답 100개를 몰아서 받는다. 왕복은 역시 1번이다.

```
왕복 시간 = 0.5ms × 1 = 0.5ms
처리 시간 = 0.001ms × 100 = 0.1ms   <- 역시 똑같다
합계     = 0.6ms
```

표로 나란히 보면 어디서 차이가 나는지가 한눈에 들어온다.

| 방식 | 왕복 횟수 | 왕복 시간 | 서버 처리 시간 | 합계 |
|---|---|---|---|---|
| 루프 GET | 100 | 0.5ms × 100 = **50ms** | 0.001ms × 100 = 0.1ms | **50.1ms** |
| MGET | 1 | 0.5ms × 1 = **0.5ms** | 0.001ms × 100 = 0.1ms | **0.6ms** |
| pipeline | 1 | 0.5ms × 1 = **0.5ms** | 0.001ms × 100 = 0.1ms | **0.6ms** |

50.1 ÷ 0.6 ≈ **83배**. 자릿수가 두 개 가까이 차이난다.

**요지는 처리 시간 열이 세 줄 모두 0.1ms로 같다는 것이다.** Redis가 하는 일의 양은 어느 방식이든 똑같다 — 키 100개를 찾는 것뿐이다. **달라지는 것은 왕복 횟수 하나뿐**이고, 그 하나가 전체 시간의 99%를 결정한다.

시간축으로 그리면 이렇다.

```
[루프 GET]  요청 --0.5ms--> 응답 | 요청 --0.5ms--> 응답 | ... (100세트)
            |<------------------- 50ms ------------------->|

[MGET / pipeline]
            요청(100개분) ----0.5ms----> 응답(100개분)
            |<--------- 0.6ms --------->|
```

### 1-3. 루프 GET의 숨은 비용 — 커넥션 풀 고갈

지연 말고 하나가 더 있다. 왕복 한 번마다 커넥션 하나를 그 시간 동안 점유하므로, 루프 GET은 **커넥션 풀 고갈**을 부른다.

커넥션 풀은 미리 만들어 둔 Redis 연결을 여러 스레드가 빌려 쓰고 반납하는 구조다. 요청 하나가 Redis 호출을 100번 한다면 그 요청은 커넥션을 50ms 동안 붙들고 있는 셈이다. 동시 요청이 조금만 늘어도 풀의 커넥션이 전부 대여 중이 되고, **뒤늦게 온 요청은 커넥션을 기다리는 시간이 지연에 추가로 가산된다.**

즉 루프 GET은 자기 응답 시간만 나빠지는 것이 아니라 **같은 풀을 쓰는 다른 요청까지 느리게 만든다.** 트래픽이 늘 때 갑자기 비선형으로 무너지는 장애의 흔한 원인이다.

```java
// Before: 루프 GET — 리뷰에서 잡아야 할 코드
List<Product> products = new ArrayList<>();
for (Long id : productIds) {                                 // id가 100개면
    // 이 한 줄이 "요청 보내고 응답 올 때까지 대기"다.
    // 루프를 도는 동안 왕복 100번, 커넥션 점유 50ms.
    String json = redis.opsForValue().get("product:" + id);
    products.add(parse(json));
}

// After: MGET — 왕복 1번
List<String> keys = productIds.stream()
        .map(id -> "product:" + id)
        .toList();
// multiGet은 MGET 명령 하나로 나간다. 왕복 1회.
List<String> jsons = redis.opsForValue().multiGet(keys);
// 반환 리스트는 요청한 키 순서와 같고, 존재하지 않는 키의 자리는 null이다.
// 그래서 인덱스로 원래 키와 짝지을 수 있고, null 체크는 호출부의 책임이다.
```

## 2. MGET vs pipeline — "명령 하나" vs "전송 방식"

둘 다 왕복을 1번으로 줄이지만 **층위가 다르다.** MGET은 Redis가 제공하는 **명령**이고, pipeline은 클라이언트가 명령들을 **보내는 방식**이다. 명령과 전송 방식은 애초에 같은 종류의 것이 아니다.

### 2-1. MGET은 명령이다

`MGET`은 "String 타입 키 여러 개를 한 번에 읽는" **하나의 명령**이다. 서버는 이것을 명령 하나로 받아 통째로 실행한다.

Redis는 명령을 **한 번에 하나씩** 실행한다(명령 실행이 단일 스레드로 이뤄진다). 그래서 한 명령이 실행되는 동안에는 다른 클라이언트의 명령이 **중간에 끼어들 수 없다.** MGET이 키 100개를 읽는 동안 다른 클라이언트가 그중 50번째 키를 바꾸는 일은 일어나지 않는다. 즉 **MGET의 결과는 어느 한 시점의 일관된 스냅샷**이다.

대신 제약이 분명하다. **GET의 묶음만 가능하다.** Hash를 읽거나(`HGETALL`) TTL을 갱신하는(`EXPIRE`) 명령을 섞을 수 없다. 쓰기 쪽 짝으로는 `MSET`이 있다.

### 2-2. pipeline은 전송 방식이다 — "몰아 보낸다"의 실체

pipeline을 "명령을 몰아 보내는 것"이라고만 설명하면 감이 안 오니, 실제로 무슨 일이 일어나는지 풀어 보자.

**보통의 요청-응답은 핑퐁이다.** 클라이언트는 명령 하나를 소켓에 쓰고, **응답이 돌아올 때까지 블로킹된 채 기다리고**, 응답을 읽은 뒤에 다음 명령을 쓴다. 이 "기다림"이 왕복 시간이고, 명령 수만큼 반복된다.

**pipeline은 이 기다림을 없앤다.** 클라이언트는 응답을 기다리지 않고 명령 1, 2, 3, ..., 100을 **연달아 소켓에 밀어 넣는다.** 그리고 나서 응답 100개를 순서대로 읽는다. 서버는 서버대로 소켓에 도착하는 명령들을 받는 대로 처리해 응답을 차례로 돌려보낸다.

```
[일반 요청-응답: 핑퐁]
  클라이언트  GET a ---------->
                              (대기)
             <---------- "1"
             GET b ---------->
                              (대기)
             <---------- "2"          왕복 2번

[pipeline: 기다리지 않고 밀어 넣는다]
  클라이언트  GET a  GET b ---->      (한 번에 씀)
                              [서버: a 처리 -> b 처리]
             <---- "1"  "2"          왕복 1번
```

여기서 결정적인 사실이 나온다. **pipeline 안의 명령들 사이에는 다른 클라이언트의 명령이 끼어들 수 있다.**

서버 입장에서 pipeline으로 온 100개는 "한 덩어리"가 아니라 **그냥 순서대로 도착한 개별 명령 100개**다. 다른 클라이언트가 보낸 명령이 그 사이에 도착하면 서버는 그것도 순서대로 처리한다.

```
  내 pipeline:   GET a   GET b                GET c
  다른 클라이언트:              SET b "changed"
  서버의 실제 실행 순서:
       GET a  ->  GET b  ->  SET b "changed"  ->  GET c
                                  ^
                     내 명령들 사이에 남의 명령이 들어왔다
```

**이것이 "pipeline에는 원자성이 없다"는 말의 실체다.** "몰아 보냈다"는 것은 **전송**의 이야기이지 **실행**의 이야기가 아니다. 왕복을 아꼈을 뿐, 서버는 여전히 도착 순서대로 하나씩 처리할 뿐이다.

대신 얻는 것이 있다. 서버 입장에서 개별 명령이 순서대로 온 것과 같으므로 **어떤 명령이든 자유롭게 조합할 수 있다.** GET과 HGETALL과 EXPIRE를 한 번의 왕복에 섞어 보낼 수 있다.

```java
// pipeline: 서로 다른 명령을 한 왕복에 — Spring Data Redis
List<Object> results = redisTemplate.executePipelined(
    (RedisCallback<Object>) conn -> {
        for (Long id : productIds) {
            // 여기서 각 호출은 "명령을 버퍼에 담는" 동작이다.
            // 응답을 기다리지 않으므로 반환값도 이 자리에서는 의미가 없다.
            conn.stringCommands().get(("product:" + id).getBytes());
        }
        // MGET으로는 불가능한 부분 — 타입이 다른 명령을 같은 왕복에 섞는다.
        conn.hashCommands().hGetAll("category:map".getBytes());
        // 콜백의 반환값은 무시된다. 결과는 executePipelined가 응답을
        // 보낸 순서대로 모아 List로 돌려준다.
        return null;
    });
```

### 2-3. pipeline과 MULTI/EXEC를 헷갈리지 않기

원자적 일괄 실행이 필요하다면 pipeline이 아니라 **MULTI/EXEC**다.

`MULTI`를 보내면 서버는 그 뒤에 오는 명령들을 실행하지 않고 **큐에 쌓아둔다.** `EXEC`를 받는 순간 쌓아둔 명령들을 **통째로 실행하고**, 그 사이에 다른 클라이언트의 명령이 끼어들지 않는다.

축을 이렇게 나누면 정확하다.

| | 무엇을 해결하나 | 중간 개입 |
|---|---|---|
| pipeline | **전송 최적화** — 왕복 절약 | 끼어들 수 있다 |
| MULTI/EXEC | **실행 보장** — 원자적 일괄 실행 | 끼어들 수 없다 |

**"pipeline = 성능, MULTI/Lua = 원자성"**으로 축을 나눠 답하면 이 구분이 흔들리지 않는다.

중간 조회 결과를 보고 분기까지 해야 한다면 MULTI/EXEC로도 부족하다. MULTI에 쌓인 명령들은 서로의 결과를 볼 수 없기 때문이다. 이때는 **Lua 스크립트**를 쓴다 — 스크립트 전체가 하나의 명령처럼 원자적으로 실행되면서 그 안에서는 조건 분기를 쓸 수 있다.

정리하면 선택 기준은 이렇다.

| 상황 | 선택 |
|---|---|
| String 키 여러 개 단순 조회/저장 | MGET / MSET |
| 서로 다른 명령·자료구조를 한 왕복에 | pipeline |
| 원자적 일괄 실행 (중간 개입 차단) | MULTI/EXEC 또는 Lua |

## 3. 실무의 함정 — Cluster 제약과 배치 크기

### 3-1. Cluster에서는 MGET이 그냥 안 된다

단일 인스턴스에서 잘 돌던 MGET이 Redis Cluster로 옮기는 순간 깨진다. 원리를 알아야 미리 대비할 수 있으니 순서대로 보자.

**전제: Cluster는 키를 슬롯으로 나눠 노드에 분산한다.** Redis Cluster는 전체 키 공간을 **16384개의 해시 슬롯**으로 나눠 두고, 키 이름을 해싱해서 그 키가 어느 슬롯에 속하는지 정한다. 그리고 각 노드가 슬롯 범위를 나눠 가진다. 노드가 3대라면 대략 5461개씩 맡는 식이다.

**그리고 한 명령은 한 노드에서만 실행된다.** 클라이언트가 명령을 보낼 때 그 명령이 다루는 키의 슬롯을 계산해 담당 노드로 보내는데, 명령 하나가 여러 노드에 걸쳐 실행되는 메커니즘은 없다.

이 둘을 합치면 결론이 나온다. **MGET의 키들이 서로 다른 슬롯에 속하면 서로 다른 노드에 있고, 한 명령으로는 실행할 수 없다.** 그래서 Redis는 `CROSSSLOT` 에러를 돌려준다.

```
MGET product:1  product:2  product:3
      |           |           |
   슬롯 8421    슬롯 12190   슬롯 3055
      |           |           |
    노드 B      노드 C       노드 A     <- 명령 하나가 세 노드에 갈 수 없다
                                       -> CROSSSLOT 에러
```

대응은 둘이다.

**해시 태그로 같은 슬롯에 모으기.** 키 이름에 중괄호를 쓰면 **중괄호 안의 부분만 해싱**된다. `user:{123}:profile`과 `user:{123}:cart`는 해싱 대상이 둘 다 `123`이라 반드시 같은 슬롯에 들어가고, 따라서 같은 노드에 있으므로 함께 MGET할 수 있다. 다만 이건 공짜가 아니다. 같은 태그를 쓰는 키가 많아지면 **특정 슬롯에 데이터가 몰리는 편중**이 생기므로, 분산을 일부 포기하고 멀티 키 조회를 얻는 교환이다.

**클라이언트 라이브러리에 맡기기.** 임의의 키를 대량 조회해야 한다면, 클라이언트가 키들을 **슬롯(노드)별로 쪼개서 각 노드에 병렬로 요청을 보내고, 돌아온 결과를 원래 요청 순서에 맞춰 합치는** 방식으로 처리한다. 노드가 3대면 왕복 100번이 아니라 병렬 3번으로 끝나는 셈이다. 다만 **이 동작을 라이브러리가 자동으로 해 주는지, 어떤 API에서 해 주는지는 라이브러리마다 다르므로 쓰기 전에 확인이 필요하다.** 자동으로 쪼개 주는 줄 알았는데 그냥 에러를 던지거나, 쪼개기는 하되 순차로 보내 왕복이 노드 수만큼 직렬로 쌓이는 경우도 있다.

이 제약이 중요한 이유는 **"단일 인스턴스에서 Cluster로 확장하는 순간 애플리케이션 코드가 깨지는" 대표 사례**이기 때문이다. 확장은 보통 트래픽이 감당이 안 될 때 급하게 하는 일이라, 그 시점에 코드가 깨지는 것을 발견하면 최악이다. 확장 계획 단계에서 미리 아는 것이 이 지식의 값이다.

### 3-2. 몰아 보내기도 과하면 블로킹 폭탄 (가산점 포인트)

왕복을 아끼는 것이 좋다고 해서 한 번에 수만 개를 묶으면 반대편 문제가 생긴다. 이유는 **Redis가 명령을 한 번에 하나씩 처리한다**는 데 있다.

**거대한 MGET은 절대적인 블로킹이다.** 키 10만 개짜리 MGET은 **명령 하나**다. 그 명령이 10만 개를 다 찾을 때까지 Redis는 다른 어떤 클라이언트의 명령도 처리하지 못한다. 키 하나에 1µs만 잡아도 100ms 동안 서버 전체가 멈춰 있는 셈이고, 그동안 다른 모든 요청의 응답 시간에 그 100ms가 통째로 얹힌다. `KEYS` 명령이 위험한 것과 정확히 같은 계열의 문제다 (`12-keys-vs-scan.md`의 원리).

**거대한 pipeline도 정도만 덜할 뿐 같은 문제를 만든다.** pipeline은 명령들 사이에 다른 클라이언트가 끼어들 수는 있지만, 서버는 소켓에서 읽어 들인 명령들을 연달아 처리한다. 10만 개를 밀어 넣으면 서버가 그것들을 소화하는 동안 다른 클라이언트의 대기 시간이 계속 늘어난다.

**응답 쪽도 부담이다.** 10만 개의 응답은 클라이언트가 다 읽어 갈 때까지 서버의 **출력 버퍼**에 쌓여 서버 메모리를 부풀리고, 클라이언트 쪽에서도 결과 리스트 10만 개가 힙에 통째로 올라온다. 요청은 작은데 응답이 거대한 비대칭이 여기서 생긴다.

그래서 실무 패턴은 **적당한 크기(수백~수천)로 잘라서 배치 왕복**이다. 키 1만 개를 조회해야 한다면 500개씩 20번 나눠 보낸다. 왕복이 20번으로 늘지만 20 × 0.5ms = 10ms이므로 여전히 루프 GET(5초)과는 비교가 안 되고, 서버를 한 번에 오래 붙들지 않는다.

목표를 정확히 표현하면 이렇다. **"왕복 1번"이 목표가 아니라 "키 수 N에 비례하던 왕복을 N과 무관한 상수 몇 번으로 만드는 것"이 목표다.** 왕복 최소화와 단일 명령 비대화 사이에 균형점이 있다는 감각까지 말하면 시니어답다.

## 4. 꼬리질문 대비 포인트

### "MGET과 pipeline으로 GET을 묶는 것, 결과가 같다면 무엇을 쓰나요?"

String 조회만이라면 **MGET이 낫다.** 이유가 셋이다.

1. **서버 부담이 적다.** 명령 파싱과 디스패치가 100번이 아니라 1번이다.
2. **코드가 단순하다.** `multiGet(keys)` 한 줄과 콜백 안의 루프는 읽는 부담이 다르다.
3. **한 명령이라 그 시점의 일관된 조회가 된다.** pipeline은 명령 사이에 남의 쓰기가 끼어들 수 있어 100개가 서로 다른 시점의 값일 수 있다.

pipeline은 **명령 종류가 섞일 때**, 또는 **Cluster에서 노드별 분배가 필요할 때** 꺼내는 도구다.

한 줄로는 **"기본은 MGET, 조합이 필요하면 pipeline"**이 간명한 답이다.

### "pipeline과 MULTI/EXEC의 차이는요?"

pipeline은 **전송 최적화**(왕복 절약)이고 MULTI/EXEC는 **실행 보장**(원자적 일괄 실행)이다. 해결하는 문제 자체가 다르다.

pipeline 안의 명령들 사이에는 다른 클라이언트의 명령이 끼어들 수 있다. MULTI/EXEC는 명령을 큐에 쌓아뒀다가 EXEC 시점에 통째로 실행하므로 중간 개입이 없다.

**둘은 배타적이지 않다.** MULTI/EXEC 자체를 pipeline에 실어 보내면 원자성을 얻으면서 왕복도 아낄 수 있다.

다만 MULTI/EXEC에도 한계가 있다. **중간 조회 결과로 분기하지 못한다** — 큐에 쌓인 명령들은 서로의 결과를 볼 수 없기 때문이다. "값을 읽어 보고 조건에 맞으면 쓴다"는 check-then-act가 필요하면 `WATCH`(감시하던 키가 바뀌면 EXEC를 실패시키는 낙관적 방식)나 Lua 스크립트로 가야 한다.

### "루프 GET인데 왕복을 못 줄이는 상황도 있나요?"

있다. **앞 조회의 결과가 다음 조회의 키를 결정하는 의존 체인**이면 묶을 수 없다. 예를 들어 `GET session:abc`로 얻은 userId로 `GET user:{userId}`를 조회해야 한다면, 두 번째 키를 미리 알 수 없으므로 한 왕복에 담을 수가 없다.

이때의 답은 둘이다.

1. **Lua 스크립트로 체인 전체를 서버에서 실행한다.** 왕복 1번으로 보내고 서버 안에서 "읽고 → 그 값으로 다음 키를 만들고 → 또 읽는" 과정을 끝낸다.
2. **자료구조 설계를 바꿔 한 번에 읽히게 만든다.** 함께 읽히는 필드를 Hash 한 키에 모아두면 `HGETALL` 한 번으로 끝난다.

여기서 한 걸음 더 나가면 좋다. **"왕복 수는 코드가 아니라 데이터 모델이 결정할 때가 많다."** 루프를 아무리 고쳐도 안 줄어드는 왕복은 대개 키를 잘못 쪼개 놓은 결과이고, 진짜 해법은 키 설계로 돌아가는 것이다.

### "이 지식이 코드 리뷰에서 어떻게 쓰이나요?" (시니어 변별 포인트)

**루프 안의 원격 호출을 보면 반사적으로 두 가지를 묻는다.** "N이 얼마까지 커질 수 있는가", "왕복당 비용이 얼마인가".

그리고 이 패턴은 Redis만의 것이 아니다. **JPA의 N+1 문제와 구조가 완전히 같다.**

N+1은 주문 목록 10건을 조회하고(쿼리 1번), 각 주문의 회원을 지연 로딩으로 꺼내면서(쿼리 10번) 총 11번의 쿼리가 나가는 현상이다. 여기서 왕복 10번을 만드는 것은 **루프 안에 원격 호출이 들어 있다는 사실 그 자체**다. Redis 루프 GET에서 왕복 100번이 나오는 것과 완전히 동일한 구조이고, 해법의 형태도 같다 — JPA에서는 `fetch join`이나 `@BatchSize`로 한 번에 가져오고, Redis에서는 MGET이나 pipeline으로 묶는다.

| 저장소 | 문제 코드 | 해법 |
|---|---|---|
| JPA/RDB | 루프 안 지연 로딩 → 쿼리 N번 | fetch join, `@BatchSize`, `IN` 절 |
| Redis | 루프 안 GET → 왕복 N번 | MGET, pipeline |
| HTTP API | 루프 안 REST 호출 → 왕복 N번 | 벌크 엔드포인트, 병렬 호출 |

**"루프 × 네트워크 왕복"은 저장소가 무엇이든 지연을 N배로 만든다.** 이 한 문장을 쥐고 있으면 처음 보는 기술 스택에서도 같은 냄새를 맡을 수 있다.

리뷰 코멘트의 형태로 말하면 이렇다.

> "productIds가 화면 요구사항상 최대 몇 개인가요? 100개면 이 루프가 왕복 100번이라 p99가 수십 ms 늘어납니다. multiGet으로 묶고, 상한이 없다면 1,000개 단위로 잘라주세요."

**문제 지적 + 근거 + 대안 + 상한 확인까지가 한 세트다.** "N+1이네요"라고만 쓰면 상대는 무엇을 얼마나 고쳐야 하는지 모른다. 특히 마지막의 **상한 확인**이 중요한데, N이 무한히 커질 수 있는 코드는 묶는 것만으로는 해결되지 않고 배치 분할까지 필요하기 때문이다.

## 한 줄 요약

여러 키 조회의 비용은 명령 처리(µs)가 아니라 네트워크 왕복(ms)이 지배하므로 루프 GET(왕복 N번)은 MGET이나 pipeline(왕복 1번)으로 묶어야 한다 — MGET은 String 전용 단일 명령이라 중간 개입 없이 통째로 실행되는 반면 **pipeline은 전송 방식일 뿐이라 명령 사이에 남의 명령이 끼어들 수 있고(원자성 없음, 원자성이 필요하면 MULTI/EXEC나 Lua)**, 여기에 Cluster의 해시 슬롯 제약과 "너무 큰 배치는 그 자체가 블로킹"이라는 균형까지 말하면 왕복을 분해해 본 경험이 증명된다.
