# 루프 GET vs MGET vs Pipeline — Redis 성능의 지배 요인은 네트워크 왕복이다

> 핵심 관전 포인트: **Redis에서 키 100개를 조회할 때 진짜 비용은 명령
> 처리(마이크로초 단위)가 아니라 네트워크 왕복(RTT, 밀리초 단위)이다.
> 루프 GET은 왕복 100번 = RTT × 100이고, MGET과 pipeline은 왕복
> 1번으로 줄인다 — 같은 데이터를 가져오는데 지연이 수십 배 차이난다.
> 둘의 구분은: MGET은 "같은 종류(String 조회)의 멀티 키 명령
> 하나"라서 가장 단순하지만 String GET에만 쓸 수 있고 Cluster에서는
> 해시 슬롯 제약을 받는다. pipeline은 "서로 다른 명령 여러 개를
> 응답을 기다리지 않고 몰아 보내는 전송 방식"이라 조합이 자유롭지만,
> 트랜잭션이 아니므로 원자성은 없다. 리뷰에서 루프 안의 GET N번을
> 잡아내는 눈이 이 지식의 실전 형태다.**

---

## 0. 질문 + 의도

**질문**: "여러 키를 조회할 때 루프 GET, MGET, pipeline의 차이는?"

**출제 의도**: Redis 성능의 실제 지배 요인이 명령 처리 속도가 아니라
네트워크 왕복임을 아는지 본다. 루프 안에서 GET을 N번 치는 코드를
리뷰에서 잡는 눈 — "Redis는 빠르니까"라는 막연한 믿음이 아니라 지연이
어디서 생기는지를 분해해 본 경험이 있는지가 드러난다.

## 1. 비용의 분해 — 명령 처리는 μs, 왕복은 ms

Redis 명령 하나의 체감 지연은 대략 이렇게 쪼개진다:

```text
[클라이언트] --요청 전송--> [Redis: 명령 처리 (수 μs)] --응답 전송--> [클라이언트]
              └────────────── 네트워크 왕복 RTT (같은 AZ ~0.5ms 안팎) ──────────────┘
```

메모리에서 값 하나 찾는 것은 마이크로초 단위지만, 요청이 네트워크를
건너갔다 오는 왕복은 밀리초에 가깝다 — **비용의 수백 배가 이동
시간**이다. 택배에 비유하면 물건 포장(명령 처리)은 10초인데 배송
왕복이 이틀인 상황이라, 물건 100개를 한 상자에 담느냐 100번
따로 보내느냐가 전체 시간을 결정한다.

그래서 키 100개 조회의 총 지연은:

- **루프 GET**: RTT × 100. 앞 응답을 받아야 다음 요청을 보내는 직렬
  왕복이라 키 수에 정비례로 느려진다. RTT 0.5ms면 50ms — 이 API 하나가
  전체 응답 시간 예산을 다 먹는다.
- **MGET**: RTT × 1 + 키 100개 처리(여전히 μs 수준).
- **pipeline**: RTT × 1(혹은 배치 수만큼) + 명령 100개 처리.

루프 GET의 숨은 비용이 하나 더 있다: 왕복마다 커넥션을 점유하므로
**커넥션 풀 고갈**을 부른다. 요청당 Redis 호출이 100번이면 트래픽이
조금만 늘어도 풀 대기 시간이 지연에 가산된다.

```java
// Before: 루프 GET — 리뷰에서 잡아야 할 코드
List<Product> products = new ArrayList<>();
for (Long id : productIds) {                       // id 100개면
    String json = redis.opsForValue().get("product:" + id);  // 왕복 100번
    products.add(parse(json));
}

// After: MGET — 왕복 1번
List<String> keys = productIds.stream()
        .map(id -> "product:" + id)
        .toList();
List<String> jsons = redis.opsForValue().multiGet(keys);  // MGET
// 반환 리스트는 요청 키 순서와 동일, 없는 키 자리는 null
```

## 2. MGET vs pipeline — "명령 하나" vs "전송 방식"

둘 다 왕복을 1번으로 줄이지만 **층위가 다르다.**

- **MGET은 명령이다.** String 전용 멀티 키 조회 명령 하나가 서버에서
  통째로 실행된다. 한 명령이므로 실행 도중 다른 클라이언트의 명령이
  끼어들지 않는다(그 시점의 일관된 조회). 대신 GET의 묶음만 가능 —
  Hash를 읽거나 TTL을 갱신하는 건 못 섞는다. 쓰기 짝으로는 MSET이 있다.
- **pipeline은 프로토콜 사용 방식이다.** 클라이언트가 "요청 → 응답
  대기 → 다음 요청"의 핑퐁을 깨고, 명령 여러 개를 **응답을 기다리지
  않고 연달아 써 보낸 뒤** 응답을 몰아서 받는다. 서버 입장에서는
  개별 명령이 순서대로 도착한 것과 같아서 **어떤 명령이든 조합
  가능**하다 — GET과 HGETALL과 EXPIRE를 한 번의 왕복에 섞을 수 있다.

```java
// pipeline: 서로 다른 명령을 한 왕복에 — Spring Data Redis
List<Object> results = redisTemplate.executePipelined(
    (RedisCallback<Object>) conn -> {
        for (Long id : productIds) {
            conn.stringCommands().get(("product:" + id).getBytes());
        }
        conn.hashCommands().hGetAll("category:map".getBytes()); // 다른 명령도 OK
        return null;  // 반환값은 무시됨 — 결과는 executePipelined가 모아서 반환
    });
```

중요한 구분 — **pipeline은 트랜잭션이 아니다**:

- pipeline 안의 명령들 **사이에** 다른 클라이언트의 명령이 끼어들 수
  있다. "몰아 보냈다"는 전송의 이야기지, 원자적 실행의 이야기가
  아니다.
- 원자적 일괄 실행이 필요하면 MULTI/EXEC(큐잉 후 일괄 실행), 중간
  조회 결과로 분기까지 필요하면 Lua 스크립트다. "pipeline =
  성능(왕복 절약), MULTI/Lua = 원자성"으로 축을 나눠 답하면
  정확하다.

선택 기준을 정리하면:

| 상황 | 선택 |
|---|---|
| String 키 여러 개 단순 조회/저장 | MGET / MSET |
| 서로 다른 명령·자료구조를 한 왕복에 | pipeline |
| 원자적 일괄 실행 (중간 개입 차단) | MULTI/EXEC 또는 Lua |

## 3. 실무의 함정 — Cluster 제약과 배치 크기

### Cluster에서는 MGET이 그냥 안 된다

Redis Cluster는 키를 해시 슬롯로 쪼개 노드에 분산한다. 멀티 키
명령은 **모든 키가 같은 슬롯에 있어야** 실행되므로, 임의의 키
100개를 MGET하면 `CROSSSLOT` 에러가 난다.

- 같은 묶음으로 조회할 키들은 **해시 태그**로 같은 슬롯에 모을 수
  있다: `user:{123}:profile`, `user:{123}:cart` — `{}` 안의 값만
  해싱된다. 단, 특정 슬롯에 데이터가 몰리는 편중과 교환하는
  결정이다.
- 임의 키 대량 조회는 클라이언트 라이브러리가 키를 노드별로 나눠
  **노드당 pipeline**을 보내고 결과를 합치는 방식으로 처리한다
  (라이브러리 지원 여부와 동작 방식을 확인하고 써야 한다).
- 이 제약은 "단일 인스턴스에서 Cluster로 확장하는 순간 애플리케이션
  코드가 깨지는" 대표 사례라, 확장 계획 단계에서 미리 아는 것이
  중요하다.

### 몰아 보내기도 과하면 블로킹 폭탄 (가산점 포인트)

왕복을 아끼려고 한 번에 수만 개를 묶으면 반대편 문제가 생긴다:

- 키 10만 개짜리 MGET은 **명령 하나**라서 실행되는 동안 싱글 스레드가
  다른 요청을 전혀 처리하지 못한다 — KEYS와 같은 계열의 블로킹이
  된다 (`12-keys-vs-scan.md`의 원리).
- 거대한 응답은 서버의 출력 버퍼와 클라이언트 메모리를 부풀린다.
  pipeline도 응답이 몰아서 돌아오므로 같은 문제가 있다.

그래서 실무 패턴은 **적당한 크기(수백~수천)로 잘라서 배치 왕복**이다.
"1번의 왕복"이 목표가 아니라 "키 수에 비례하는 왕복을 상수 몇 번으로"
가 목표라는 감각 — 왕복 최소화와 단일 명령 비대화 사이의 균형점을
말하면 시니어답다.

## 4. 꼬리질문 대비 포인트

### "MGET과 pipeline으로 GET을 묶는 것, 결과가 같다면 무엇을 쓰나요?"

String 조회만이라면 MGET이 낫다 — 명령 파싱·디스패치가 1회라 서버
부담이 더 적고, 코드도 단순하며, 한 명령이라 그 시점의 일관된 조회가
된다. pipeline은 명령 종류가 섞일 때, 또는 Cluster에서 노드별 분배가
필요할 때 꺼내는 도구다. "기본은 MGET, 조합이 필요하면 pipeline"이
간명한 답이다.

### "pipeline과 MULTI/EXEC의 차이는요?"

pipeline은 **전송 최적화**(왕복 절약)고 MULTI/EXEC는 **실행
보장**(원자적 일괄 실행)이다. pipeline 안의 명령 사이에는 다른
클라이언트 명령이 끼어들 수 있지만, MULTI/EXEC는 큐에 쌓았다가
EXEC 시점에 통째로 실행해 중간 개입이 없다. 둘은 배타적이지 않아서
MULTI/EXEC를 pipeline에 실어 보내 왕복도 아낄 수 있다. 다만
MULTI/EXEC도 중간 조회 결과로 분기하지는 못하므로 check-then-act는
WATCH나 Lua가 필요하다.

### "루프 GET인데 왕복을 못 줄이는 상황도 있나요?"

앞 조회의 **결과가 다음 조회의 키를 결정**하는 의존 체인이면 묶을 수
없다 (예: GET으로 얻은 id로 다음 키를 구성). 이때는 (1) Lua
스크립트로 체인 전체를 서버에서 실행하거나, (2) 자료구조 설계를
바꿔 한 번에 읽히게(Hash 한 키에 묶기 등) 만드는 것이 답이다.
"왕복 수는 코드가 아니라 데이터 모델이 결정할 때가 많다"까지 가면
좋다.

### "이 지식이 코드 리뷰에서 어떻게 쓰이나요?" (시니어 변별 포인트)

루프 안의 원격 호출을 보면 반사적으로 "N이 얼마까지 커질 수 있는가,
왕복당 비용이 얼마인가"를 묻는다. Redis 루프 GET뿐 아니라 JPA의
N+1, 루프 안 HTTP 호출과 **완전히 같은 패턴** — "루프 × 네트워크
왕복"은 저장소가 무엇이든 지연을 N배로 만든다. 리뷰 코멘트의 형태로
말하면: "productIds가 화면 요구사항상 최대 몇 개인가요? 100개면 이
루프가 왕복 100번이라 p99가 수십 ms 늘어납니다. multiGet으로 묶고,
상한이 없다면 1,000개 단위로 잘라주세요." — 문제 지적 + 근거 +
대안 + 상한 확인까지가 한 세트다.

## 한 줄 요약

여러 키 조회의 비용은 명령 처리(μs)가 아니라 네트워크 왕복(ms)이
지배하므로 루프 GET(왕복 N번)은 MGET이나 pipeline(왕복 1번)으로
묶어야 한다 — MGET은 String 전용 단일 명령, pipeline은 임의 명령을
몰아 보내는 전송 방식이며 **원자성은 둘 다 없고**, Cluster의 해시
슬롯 제약과 "너무 큰 배치는 그 자체가 블로킹"이라는 균형까지 말하면
왕복을 분해해 본 경험이 증명된다.
