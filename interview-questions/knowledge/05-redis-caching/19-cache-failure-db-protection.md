# 캐시 무력화 방어 — 캐시가 죽는 날, DB가 살아남는 설계

> 핵심 관전 포인트: **캐시는 언젠가 죽는다는 전제에서 출발해야 한다.
> 히트율 90% 시스템에서 캐시가 죽으면 DB는 평소의 10배 트래픽을
> 맞는데, DB가 그걸 못 견디는 구조라면 캐시는 가용성을 높인 게 아니라
> 장애 지점을 하나 추가한 것이다. 방어는 계층별로 깐다 — 캐시 호출에
> 짧은 타임아웃과 서킷 브레이커(느려진 캐시가 더 위험하다), DB 앞에
> 커넥션 풀 상한·부하 차단(load shedding), 그 위에 성능 저하
> 모드(낡은 스냅샷·기능 축소로 버티기), 로컬 캐시 폴백, 그리고 캐시
> 자체의 HA. 핵심 설계 질문은 하나다 — "캐시 없이 DB가 트래픽의 몇
> %를 견디는지 알고 있는가, 그 초과분을 어디서 어떻게 떨어뜨릴
> 것인가."**

---

## 0. 질문 + 의도

**질문**: "캐시 장애 시 DB로 트래픽이 폭주하는 상황(캐시 무력화)에
대한 방어 설계를 설명해주세요."

**출제 의도**: 캐시는 언젠가 죽는다는 전제에서 출발하는지. 캐시
장애가 곧 DB 장애가 되는 구조라면 캐시는 가용성을 높인 게 아니라
장애 지점을 추가한 것 — 이 역설을 이해하는지 본다.

## 1. 문제의 구조 — 캐시가 "가용성의 역설"이 되는 이유

캐시를 도입하면 시스템은 그 히트율에 **적응**한다. 히트율 90%라면 DB
용량·커넥션 풀·인덱스 튜닝이 전부 "트래픽의 10%만 온다"는 전제 위에
설계되고, 트래픽은 그 전제 위에서 계속 자란다. 이 상태에서 캐시가
죽으면:

```
Redis 다운
  → 전 요청 캐시 미스 (히트율 90% → 0%)
  → DB 유효 부하 10배 (전제가 무너짐)
  → 쿼리 지연 급증 → DB 커넥션 풀 고갈
  → 커넥션을 기다리는 요청이 애플리케이션 스레드 점유
  → 스레드 풀 고갈 → 캐시와 무관한 API까지 전부 응답 불가
  → 서비스 전체 다운 (연쇄 장애, cascading failure)
```

여기서 역설이 나온다. 캐시를 "성능 개선 + DB 보호 장치"로 도입했는데,
방어 설계가 없으면 **캐시 장애가 곧 전체 장애가 되는 단일 장애점을
하나 추가한 셈**이다. 캐시 도입 전에는 컴포넌트 하나(DB)가 죽어야
장애였는데, 이제는 둘 중 하나만 죽어도 장애다 — 산술적으로 가용성이
내려갔다. 이 역설을 스스로 말하고 시작하면 질문의 절반은 답한 것이다.

### 더 흔하고 더 음험한 시나리오 — 죽은 캐시가 아니라 "느려진" 캐시

완전히 죽은 캐시는 차라리 낫다 — 연결 거부는 즉시 실패하므로 폴백이
빨리 동작한다. 실제로 더 자주 겪는 것은 **캐시가 느려지는** 경우다
(네트워크 순단, Redis에서 O(N) 명령·big key 삭제가 이벤트 루프를
잡은 순간, 페일오버 진행 중). 캐시 조회 타임아웃이 기본값(수 초)
이라면:

- 모든 요청이 "캐시 응답 대기"에 수 초씩 묶인다.
- DB는 멀쩡한데 애플리케이션 스레드 풀이 먼저 고갈된다.
- **성능 올리려고 넣은 캐시가 병목 그 자체**가 된다.

그래서 방어의 1번은 락도 폴백도 아니고 **캐시 호출의 타임아웃
설정**이다.

## 2. 방어 계층 — 요청이 지나는 순서대로 깔기

### ① 캐시 호출: 짧은 타임아웃 + 예외 격리 — "캐시는 best-effort"

캐시는 없어도 되는 계층이다(원본은 DB에 있다). 그러므로 캐시 조회
실패가 **요청 실패로 전파되면 안 되고**, 캐시 응답을 **오래 기다려도
안 된다**.

```java
// ❌ before: 캐시 예외가 요청을 죽이고, 타임아웃은 기본값(수 초)
public Product getProduct(Long id) {
    Product cached = redis.get(key(id));   // Redis 다운 → 예외 → 500 응답
    if (cached != null) return cached;     // Redis 느림 → 여기서 수 초 대기
    ...
}

// ✅ after: 짧은 타임아웃 + 캐시 실패는 삼키고 DB로 폴백
//   (Lettuce 등 클라이언트에 command timeout을 수십~수백 ms로 설정)
public Product getProduct(Long id) {
    try {
        Product cached = redis.get(key(id));  // 타임아웃 짧음 — 빨리 실패
        if (cached != null) return cached;
    } catch (CacheAccessException e) {
        log.warn("cache unavailable, falling back to DB", e);  // 실패는 기록만
    }
    return productRepository.findById(id);    // 캐시 없이도 동작하는 경로
}
```

타임아웃 기준은 "캐시가 이 시간 안에 답을 못 주면 캐시의 의미가
없다"로 잡는다 — DB 쿼리보다 오래 기다리는 캐시 조회는 존재 이유가
없다. 단, 이 폴백은 **개별 요청을 살리는 장치**일 뿐이다. 전 요청이
폴백을 타는 순간 DB 폭주라는 원래 문제로 돌아오므로, 다음 계층들이
반드시 뒤따라야 한다.

### ② 서킷 브레이커 — 죽은 캐시에 계속 노크하지 않기

캐시 호출에 서킷 브레이커(Resilience4j 등)를 건다. 연속 실패·지연이
임계치를 넘으면 회로가 열리고, 이후 요청은 **캐시를 시도조차 하지
않고 즉시 폴백 경로로** 간다.

- 얻는 것: 요청마다 타임아웃만큼 기다렸다 실패하는 낭비 제거(빠른
  실패), 죽어가는 Redis에 연결 시도를 퍼붓지 않음(복구 여유),
  half-open 상태로 **복구를 자동 감지**해 재개.
- 서킷이 열렸다는 것 = "지금 캐시 없이 운영 중"이라는 명확한 신호 —
  알람과 대시보드에 직결시켜 ④의 성능 저하 모드 발동 트리거로 쓴다.

### ③ DB 앞: 유입량 자체를 깎기 — 커넥션 풀 상한, 부하 차단

캐시가 없어진 순간 DB로 가는 트래픽을 **DB가 견디는 수준으로
떨어뜨리는** 장치. 여기가 이 질문의 본론이다 — "폴백으로 DB 간다"
까지만 말하면 폭주를 방어한 게 아니라 폭주를 전달한 것이다.

- **커넥션 풀 상한 = 내장 스로틀**: 풀 크기가 DB가 동시에 처리
  가능한 수준으로 제한돼 있으면, 초과 요청은 DB에 닿지 못하고 풀
  대기에서 걸러진다. 단 **대기 타임아웃을 짧게** 잡아야 한다 —
  무한정 대기시키면 스레드 풀 고갈로 전이되므로, 짧게 기다리고
  실패시켜야 한다.
- **부하 차단(load shedding)**: 처리 용량을 넘는 요청은 큐에 쌓지
  말고 **입구에서 빠르게 429/503으로 거절**한다. 100% 요청이 다
  느려져 전원이 타임아웃을 겪는 것보다, 70%는 정상 서빙하고 30%를
  즉시 실패시키는 쪽이 총 피해가 작다 — "전원이 조금씩 죽는 것보다
  일부를 빨리 포기하는" 결정이다.
- **재시도 규율**: 클라이언트·내부 호출의 무분별한 재시도는 폭주를
  증폭시킨다(재시도 폭풍). 지수 백오프 + 재시도 상한이 전제돼야
  위 장치들이 산다.

### ④ 성능 저하 모드 (graceful degradation) — 낡은 값으로 버티기

"정확한 응답 불가 = 에러"가 아니라, **품질을 낮춘 응답**으로 버티는
계층. 캐시하던 데이터는 대부분 낡아도 되는 데이터였다는 점을
역이용한다.

- 인기 목록·랭킹·추천 → 주기적으로 떠 둔 **정적 스냅샷**(서버 메모리,
  CDN, 파일)으로 응답. "1시간 전 인기 목록"은 에러 페이지보다 백배
  낫다.
- 비핵심 기능(추천 위젯, 조회수 표시)은 **피처 플래그로 끈다** —
  핵심 경로(조회·주문)에 DB 여력을 몰아준다.
- 이 모드로 "무엇을 보여줄지"는 장애 당일에 정할 수 없다 — **평시에
  설계하고 스위치만 준비**해 두는 것이 방어 설계의 실체다.

### ⑤ 로컬 캐시 폴백 — Redis가 죽어도 남는 계층

Caffeine 같은 로컬 캐시를 Redis 앞에 겹쳐 두면(2단 캐시), Redis가
죽어도 각 인스턴스에 남은 로컬 캐시가 인기 키의 상당량을 흡수한다.
평시엔 Redis 왕복도 아끼는 성능 장치이고, 장애 시엔 완충재다.
대가는 인스턴스 간 불일치라는 새 문제(무효화 전파) — 그래서 "초고빈도
읽기 + 낡음 허용" 데이터에 한정해 도입한다. (2단 캐시 자체는 별도
문항의 주제이므로 여기서는 "장애 완충" 역할만.)

### ⑥ 캐시 자체의 HA — 확률 줄이기, 단 전제는 유지

replica + Sentinel(자동 페일오버), Cluster 구성으로 "캐시가 통째로
사라지는" 확률 자체를 줄인다. 단 두 가지를 같이 말해야 한다:

- **페일오버에도 공백은 있다** — 감지·승격까지 수 초~수십 초는 위
  ①~④가 버텨줘야 하는 시간이다.
- HA는 장애 확률을 줄일 뿐 0으로 만들지 않는다 — **"그래도 죽으면"의
  방어(①~⑤)를 대체하지 못한다.** HA를 했으니 방어 설계가 불필요하다는
  답이 이 질문의 함정이다.

## 3. 설계 질문 하나로 요약 — "캐시 없이 몇 %를 견디는가"

방어 장치들을 관통하는 사전 숙제: **캐시를 끄고 부하 테스트를 해서,
DB가 단독으로 트래픽의 몇 %를 견디는지 숫자로 알고 있어야 한다.**
그 숫자가 곧 ③에서 어디까지 흘려보내고 어디부터 떨어뜨릴지의
기준선이고, ④에서 어떤 기능을 꺼야 할지의 근거다. (가산점 포인트)
카오스 엔지니어링식으로 스테이징에서 주기적으로 "캐시 강제 다운"
훈련을 돌려 폴백·서킷·저하 모드가 실제로 동작하는지 검증한다고
말하면 — 방어 설계를 문서가 아니라 동작하는 코드로 유지하는
운영 성숙도가 드러난다.

## 4. 꼬리질문 대비 포인트

### "Redis가 완전히 죽은 것보다 느려진 게 왜 더 위험한가요?"

죽은 캐시는 연결 거부로 **즉시 실패**하므로 폴백이 바로 동작하지만,
느린 캐시는 요청마다 타임아웃 직전까지 스레드를 **붙잡고** 있는다.
타임아웃이 수 초라면 전 요청이 수 초씩 캐시 대기에 묶여, DB가
멀쩡한데도 애플리케이션 스레드 풀이 먼저 고갈된다. 장애 신호도
모호해서(에러율은 낮고 지연만 상승) 감지가 늦다. 그래서 방어의
시작은 짧은 command timeout이고, "느림"을 실패로 승격시켜 주는
서킷 브레이커가 그 다음이다.

### "캐시 장애면 그냥 전부 DB로 보내면 되는 것 아닌가요?"

DB 용량이 "히트율만큼 깎인 트래픽" 전제로 설계·성장해 왔다는 게
함정이다. 히트율 90%였다면 폴백은 DB에 10배 부하를 의미하고, DB가
무너지면 캐시 장애가 데이터 원본 장애로 승격된다 — 복구 난이도가
차원이 달라진다. 그래서 폴백(①)은 반드시 유입 제어(③)와 한 몸으로
설계해야 하고, "DB가 캐시 없이 몇 %를 견디는지"를 측정해 둔 숫자가
그 제어의 기준선이 된다.

### "일부 요청을 일부러 실패시키는 결정을 어떻게 정당화하나요?" (시니어 변별 포인트)

전부 받으면 전부 느려진다 — 큐와 커넥션 대기가 쌓이면 100%의
요청이 타임아웃 근처의 지연을 겪고, 결국 전원이 실패를 경험하면서
시스템 복구도 늦어진다. 용량의 70%만 받고 30%를 즉시 거절하면
70%는 정상 품질로 서빙되고 시스템은 안정 상태를 유지한다. 즉 load
shedding은 "실패를 만드는" 게 아니라 **이미 발생할 실패를 빠르고
싸게, 통제된 위치에서 발생시키는** 것이다. 여기에 우선순위를 얹으면
더 좋은 답이 된다 — 결제·주문 같은 핵심 경로는 보호하고 조회성·
비핵심 트래픽부터 떨어뜨리는 차등 차단. "무엇을 먼저 포기할지"가
비즈니스 판단과 연결돼 있음을 말하는 것이 시니어 변별 지점이다.

### "서킷 브레이커는 캐시 호출에 거나요, DB 호출에 거나요?"

목적이 다른 두 개다. **캐시 호출의 서킷**은 죽은/느린 캐시를
건너뛰어 빠른 실패와 복구 여유를 주는 것 — 열리면 폴백(DB) 경로로
간다. **DB 쪽은 서킷보다 벌크헤드/스로틀 성격**이 맞다 — DB는
건너뛸 폴백이 없으므로(원본이니까), 회로를 열어봤자 전 요청 실패다.
커넥션 풀 상한과 대기 타임아웃, 입구의 load shedding으로 유입량을
깎는 것이 DB 보호의 실체다. "서킷 브레이커를 어디에 왜 거는지"를
구분하면 도구를 패턴 이름이 아니라 목적으로 이해하는 것이다.

### "Sentinel로 HA를 구성했는데도 이 방어들이 필요한가요?"

필요하다. 페일오버는 장애 **감지 → 승격 → 클라이언트 재연결**까지
수 초~수십 초의 공백이 있고, 그 공백 동안의 트래픽은 ①~④가 받아야
한다. 또 HA가 못 막는 무력화 유형이 있다 — 전 노드에 영향 주는
네트워크 장애, 잘못된 배포로 인한 캐시 전체 플러시, 키 버전 변경,
그리고 복구는 됐지만 데이터가 빈 cold cache 상태(→ 26번 문서).
HA는 "무력화 확률을 줄이는" 축이고, 방어 설계는 "무력화가 그래도
일어났을 때"의 축 — 서로 대체재가 아니라 보완재다.

## 한 줄 요약

캐시 장애가 곧 DB 장애가 되는 구조라면 캐시는 가용성을 높인 게
아니라 장애 지점을 추가한 것이므로 — 캐시 호출엔 짧은 타임아웃과
서킷 브레이커, DB 앞엔 커넥션 풀 상한과 load shedding, 그 위에 낡은
스냅샷으로 버티는 성능 저하 모드와 로컬 캐시 완충, HA까지 계층으로
깔되, 출발점은 "캐시 없이 DB가 몇 %를 견디는지"를 숫자로 알고 초과분을
어디서 떨어뜨릴지 미리 정해두는 것이다.
