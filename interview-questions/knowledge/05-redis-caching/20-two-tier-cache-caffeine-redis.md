# Local cache(Caffeine) + Redis 2단 캐시 — 속도를 얻고 일관성을 지불하는 거래

> 핵심 관전 포인트: **2단 캐시는 L1(Caffeine, JVM 힙 안 — 네트워크 없이
> 나노초~마이크로초)과 L2(Redis, 공유 저장소 — 네트워크 왕복 포함
> 밀리초 미만)를 겹쳐서, Redis 왕복조차 아까운 초고빈도 읽기를 로컬에서
> 끝내는 구조다. 대가는 "노드마다 다른 값을 들고 있을 수 있다"는
> 인스턴스 간 불일치이고, 무효화는 Redis pub/sub 브로드캐스트로
> 전파하는 것이 정석이다. 단 pub/sub은 메시지 유실 시 재전달이 없으므로
> 무효화 전파는 불완전하며, 짧은 로컬 TTL을 최후의 안전망으로 반드시
> 함께 둬야 한다. 이 복잡도를 감수할 만한 데이터(초고빈도 읽기 + 변경
> 드묾 + 짧은 불일치 허용)인지 판별하는 것이 설계의 핵심이다.**

---

## 0. 질문 + 의도

**질문**: "Local cache(Caffeine) + Redis 2단 캐시 구조의 장단점과 무효화 전파
방법은?"

**출제 의도**: 로컬 캐시의 노드 간 불일치라는 새 문제를 감수할 만큼
이득이 큰 상황(초고빈도 읽기)을 판별할 수 있는지, 그리고 pub/sub
무효화 같은 해법의 불완전함(메시지 유실 시 불일치가 TTL까지 지속)까지
짚을 수 있는지 — 시스템에 복잡도를 추가하는 결정을 얼마나 신중하게
내리는지를 잰다.

## 1. 왜 Redis 앞에 또 캐시를 두나 — 네트워크 왕복이라는 남은 비용

Redis 캐시를 도입하면 DB 쿼리(수 ms~수백 ms)를 Redis 조회로 바꿔
큰 이득을 본다. 하지만 Redis 조회에도 **네트워크 왕복**이라는 비용이
남아 있다. 같은 데이터센터라도 왕복 수백 µs~1ms 수준이고, 요청 하나를
처리하며 캐시를 수십 번 읽는 코드라면 이 왕복이 누적돼 응답 시간의
주범이 된다.

반면 JVM 힙 안의 로컬 캐시(Caffeine)는 그냥 메모리의 Map 조회다 —
네트워크가 없으니 나노초~마이크로초. 이 차이를 이용해 캐시를
2단으로 겹친다:

```
요청 → L1: Caffeine (JVM 힙, 인스턴스마다 따로)
         ├─ 히트 → 즉시 반환 (네트워크 0회)
         └─ 미스 → L2: Redis (전 인스턴스 공유)
                     ├─ 히트 → L1에 채우고 반환 (네트워크 1회)
                     └─ 미스 → DB 조회 → L2, L1 채우고 반환
```

전형적인 대상은 **읽기가 폭발적으로 많고, 잘 안 바뀌고, 크기가 작은**
데이터다: 시스템 설정, 기능 플래그, 권한/역할 정의, 카테고리 트리,
코드성 데이터(공통 코드 테이블) 등. 요청마다 반드시 읽히는 데이터가
가장 좋은 후보다.

```java
// ❌ before: 모든 요청이 매번 Redis 왕복 — 설정값 하나 읽는데 네트워크 1회
public boolean isFeatureEnabled(String featureKey) {
    return redisTemplate.opsForValue().get("feature:" + featureKey) != null;
}
// 요청당 이런 조회가 20번이면 요청당 Redis 왕복 20회 — Redis도 지치고 나도 느리다.

// ✅ after: Caffeine을 앞단에 — 대부분의 조회가 JVM 안에서 끝난다
private final Cache<String, Boolean> localCache = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofSeconds(30))  // 불일치 허용 상한 = 로컬 TTL
        .build();

public boolean isFeatureEnabled(String featureKey) {
    return localCache.get(featureKey, key ->              // L1 미스일 때만
            redisTemplate.opsForValue().get("feature:" + key) != null); // L2로
}
```

## 2. 장단점 — 얻는 것과 지불하는 것

### 얻는 것

- **지연 시간 제거**: L1 히트는 네트워크 왕복이 없다. 히트율이 높은
  초고빈도 키라면 응답 시간에서 Redis 왕복 누적분이 통째로 사라진다.
- **Redis 부하·hot key 완화**: 전 인스턴스가 같은 인기 키를 초당
  수만 번 때리던 트래픽이 각자의 로컬 캐시에 흡수된다. hot key가
  Redis 특정 노드 하나에 몰리는 문제의 실전 해법이기도 하다.
- **Redis 장애 시 완충**: Redis가 잠깐 죽어도 L1에 살아 있는 데이터로
  당분간 버틸 수 있다 — 캐시 전면 무력화(전 트래픽 DB 직행)까지의
  완충재가 된다.

### 지불하는 것

- **인스턴스 간 불일치 (가장 큰 비용)**: L1은 인스턴스마다 따로다.
  서버 A에서 값을 바꿔도 서버 B의 L1에는 옛 값이 남는다. 사용자가
  새로고침할 때마다 로드밸런서가 다른 서버로 보내면 "값이 바뀌었다
  안 바뀌었다 왔다갔다 하는" 전형적 증상이 나온다.
- **JVM 메모리 점유와 GC 압박**: 캐시 데이터가 힙에 산다.
  `maximumSize` 없이 쓰면 로컬 캐시가 OOM의 원인이 된다.
- **메모리 중복**: 같은 데이터가 인스턴스 수만큼 복제된다.
- **무효화 복잡도**: Redis 한 곳만 지우면 되던 것이, 전 인스턴스의
  L1까지 지워야 하는 분산 문제로 바뀐다 (아래 3절).
- **디버깅 난이도**: "이 값이 L1 것인가 L2 것인가 DB 것인가"라는
  계층이 하나 늘어, 낡은 값 추적이 어려워진다.

요약하면 **속도와 부하를 얻고 일관성과 단순함을 판다.** 그래서
"몇 초의 불일치를 견딜 수 있는 데이터인가"가 도입 판단의 첫 질문이다.
잔액·재고·권한 회수처럼 즉시 일관성이 필요한 데이터는 후보가 아니다.

## 3. 무효화 전파 — pub/sub 브로드캐스트와 그 불완전함

### 정석: Redis pub/sub으로 무효화 이벤트 브로드캐스트

데이터를 변경한 인스턴스가 L2(Redis)를 지우고, 동시에 무효화
채널에 키를 발행한다. 전 인스턴스가 이 채널을 구독하고 있다가
메시지를 받으면 각자의 L1에서 그 키를 지운다.

```
서버 A: 데이터 변경
  → ① DB 커밋
  → ② Redis(L2) 키 삭제
  → ③ PUBLISH cache-invalidation "feature:new-editor"

서버 A, B, C (전원 구독 중):
  ← 메시지 수신 → 각자 localCache.invalidate("feature:new-editor")
```

```java
// 발행 측 — 변경 지점에서
public void updateFeature(String featureKey, boolean enabled) {
    featureRepository.update(featureKey, enabled);            // ① DB
    redisTemplate.delete("feature:" + featureKey);            // ② L2 삭제
    redisTemplate.convertAndSend("cache-invalidation",        // ③ 전파
            "feature:" + featureKey);
}

// 구독 측 — 전 인스턴스 공통 (자기 자신도 받는다 — 멱등이라 무해)
public void onInvalidationMessage(String key) {
    localCache.invalidate(key);   // L1에서 제거 → 다음 조회는 L2/DB로
}
```

순서에 주의할 점: **L2 삭제가 전파보다 먼저**여야 한다. 전파를 먼저
하면, 메시지를 받은 다른 서버가 L1을 지우고 곧장 L2를 읽었는데
아직 옛 값이 남아 있어 낡은 값을 L1에 도로 채우는 경합이 생긴다.

### 이 해법의 불완전함 — pub/sub은 유실되면 끝이다 (이 질문의 급소)

Redis pub/sub은 **저장 없이 지금 연결된 구독자에게만 던지는
방송**이다 (at-most-once). 그래서:

- 구독 연결이 잠깐 끊긴 사이(네트워크 흔들림, Redis 페일오버,
  재배포 중 재접속)의 무효화 메시지는 **그냥 사라진다.** 재전달이
  없다.
- 메시지를 놓친 노드는 자기 L1이 낡았다는 사실을 알 방법이 없고,
  **불일치가 로컬 TTL이 다할 때까지 지속된다.**

그래서 pub/sub 무효화는 "빠른 전파 경로"일 뿐 보장 장치가 아니며,
**짧은 로컬 TTL이 반드시 최후의 안전망으로 함께 있어야 한다.**
불일치의 상한선은 결국 로컬 TTL이다 — "무효화가 다 유실돼도 최대
30초 뒤엔 맞는 값"처럼 상한을 설계값으로 정해두는 것이 실무 정석이다.
구독 재연결 시 L1을 통째로 비우는(clear) 방어를 더하면 "끊긴 동안
놓친 것"의 대부분을 커버할 수 있다 (가산점 포인트).

### 그 밖의 전파/완화 방법

- **버전 키 (논리 버저닝)**: Redis에 `config:version` 같은 버전
  카운터를 두고 변경 시 INCR. 각 노드는 주기적으로(또는 조회마다
  싸게) 버전을 확인해 바뀌었으면 L1을 비운다. pub/sub과 달리
  polling이라 유실이 없지만 전파 지연은 폴링 주기만큼 생긴다.
- **Redis 서버 주도 무효화 (client-side caching)**: Redis 6부터
  RESP3 프로토콜 기반으로, 서버가 "어떤 클라이언트가 어떤 키를
  캐시했는지" 추적하다가 그 키가 변경되면 해당 클라이언트에
  무효화 메시지를 **서버가 직접 푸시**해준다. 직접 구현하는 pub/sub
  방식의 표준화판이라 볼 수 있고, 클라이언트 라이브러리 지원이
  전제다 (가산점 포인트).
- **그냥 짧은 TTL만으로**: 전파 장치 없이 로컬 TTL 수 초~수십 초만
  두는 방식. 가장 단순하고, "몇 초 불일치 허용 + 변경 드묾"인
  데이터라면 이걸로 충분한 경우가 실무에 의외로 많다 — 복잡도를
  추가하지 않는 것도 유효한 설계 선택이다.

## 4. 실무 판단 기준 — 언제 2단이 정당한가

2단 캐시는 문제를 하나 풀고(지연·부하) 문제를 하나 만든다(불일치·
복잡도). 도입이 정당해지는 조건을 체크리스트로:

- **초고빈도 읽기인가** — 요청마다, 혹은 요청당 여러 번 읽히는가.
  하루 몇 번 읽는 데이터에 2단은 순수한 복잡도 낭비다.
- **변경이 드문가** — 자주 바뀌는 데이터는 무효화 전파가 상시
  가동돼 이득이 상쇄된다.
- **짧은 불일치를 비즈니스가 견디는가** — "최대 N초 옛 값"이 허용
  가능한가. 권한 회수, 잔액, 재고 차감은 불가.
- **크기가 작은가** — 힙에 인스턴스 수만큼 복제돼도 부담 없는
  크기인가.

이 조건을 만족하는 대표가 설정/플래그/코드성 데이터이고, 만족하지
못하면 Redis 단독(1단)이 정답이다. 면접에서 "무조건 2단이 빠르니
좋다"가 아니라 **"이 조건일 때만 복잡도가 정당화된다"는 판별 기준을
먼저 말하는 것**이 이 질문이 원하는 답의 골격이다.

## 5. 꼬리질문 대비 포인트

### "pub/sub 무효화 메시지가 유실되면 어떻게 되나요?"

놓친 노드의 L1에 낡은 값이 남고, **그 노드 스스로는 낡았다는 걸 알 수
없어 불일치가 로컬 TTL 만료까지 지속된다.** pub/sub은 저장·재전달이
없는 at-most-once 방송이기 때문이다. 그래서 방어를 겹으로 둔다 —
① 짧은 로컬 TTL(불일치 상한), ② 구독 재연결 시 L1 전체 clear,
③ 유실이 정말 치명적이면 pub/sub 대신 유실 없는 채널(버전 키 폴링,
Redis Streams)로 전파를 바꾼다. "pub/sub 전파는 최적화이고, 정합성의
보장은 TTL이 진다"는 역할 분리로 답하면 정확하다.

### "로컬(L1) TTL은 Redis(L2) TTL보다 길게 잡나요, 짧게 잡나요?"

**짧게.** L1은 인스턴스마다 따로라 무효화가 불완전하고, 불일치의
상한이 곧 L1 TTL이기 때문이다. L2는 전 인스턴스가 공유하고 삭제
한 번으로 확실히 지워지므로 상대적으로 길게 가져가도 된다. 전형적
구성은 L1 수 초~수십 초 / L2 수 분~수 시간. L1을 L2보다 길게 잡으면
"L2는 갱신됐는데 L1이 옛 값을 더 오래 서빙"하는 역전이 생긴다.

### "캐시 무효화(evict)와 캐시 갱신(put) 중 무엇을 전파해야 하나요?"

**삭제(evict)를 전파한다.** 새 값을 pub/sub에 실어 각 노드가 L1에
put하게 만들면, 메시지 도착 순서가 꼬였을 때(연속 두 번 변경) 늦게
도착한 옛 값이 새 값을 덮는 순서 역전 문제가 생긴다. 삭제는 몇 번
어떤 순서로 적용돼도 결과가 같아(멱등) 안전하고, 다음 조회가 L2/DB
에서 최신 값을 다시 채운다. "캐시 갱신 vs 삭제" 일반론과 같은 논리가
전파 채널에서는 더 극적으로 적용되는 셈이다.

### "이 구조를 도입하면 안 되는 데이터는 무엇인가요?" (시니어 변별 포인트)

즉시 일관성이 요구되는 데이터 — 결제·잔액·재고 차감, 그리고 특히
**권한/세션 회수**다. 관리자가 계정을 차단해도 어떤 노드의 L1에
옛 권한이 TTL 동안 남아 있으면 차단된 사용자가 계속 접근하는 보안
문제가 된다. 또 변경이 잦은 데이터(무효화 전파가 상시 가동돼 이득
상쇄), 큰 객체(힙 압박·GC), 히트율이 낮은 롱테일 키(L1이 사실상
낭비)도 부적합하다. 핵심은 "2단 캐시의 불일치 상한(L1 TTL)을 그
데이터의 비즈니스가 견딜 수 있는가"라는 질문으로 판별한다는 것 —
기술이 아니라 요구사항으로 답하는 게 시니어의 답이다.

### "Redis 6의 client-side caching은 직접 구현한 pub/sub 무효화와 뭐가 다른가요?" (가산점 포인트)

직접 구현은 **애플리케이션이** 변경 지점마다 PUBLISH를 심어야 해서
누락 가능성(변경 경로가 여럿일 때)이 있다. client-side caching은
**Redis 서버가** 키 접근을 추적해, 그 키가 어떤 경로로든 변경되면
캐시한 클라이언트에 무효화를 푸시한다 — 변경 경로 누락이 구조적으로
없다. 대신 RESP3와 클라이언트 라이브러리의 지원이 전제이고, 서버가
추적 정보를 유지하는 부담이 있다. 둘 다 "연결이 끊긴 사이의 무효화는
보장 못 한다"는 한계는 같아서, 끊김 감지 시 로컬 캐시 flush + TTL
안전망이라는 방어는 동일하게 필요하다.

## 한 줄 요약

2단 캐시는 Redis 왕복조차 병목인 초고빈도 읽기를 JVM 안(Caffeine)에서
끝내 지연과 Redis 부하를 없애는 대신 "노드마다 값이 다를 수 있다"는
불일치를 지불하는 구조로, 무효화는 Redis pub/sub 브로드캐스트로
전파하되 pub/sub은 유실 시 재전달이 없어 불완전하므로 짧은 L1 TTL을
불일치의 상한이자 최후의 안전망으로 반드시 함께 두고 — 애초에 이
복잡도는 "초고빈도 읽기 + 변경 드묾 + 짧은 불일치 허용" 조건을
만족하는 데이터에서만 정당화된다.
