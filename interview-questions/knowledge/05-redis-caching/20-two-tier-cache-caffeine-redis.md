# Local cache(Caffeine) + Redis 2단 캐시 — 속도를 얻고 일관성을 지불하는 거래

> 핵심 관전 포인트: **2단 캐시는 L1(Caffeine, JVM 힙 안 — 네트워크 없이 나노초~마이크로초)과 L2(Redis, 공유 저장소 — 네트워크 왕복 포함 밀리초 미만)를 겹쳐서, Redis 왕복조차 아까운 초고빈도 읽기를 로컬에서 끝내는 구조다. 대가는 "노드마다 다른 값을 들고 있을 수 있다"는 인스턴스 간 불일치이고, 무효화는 Redis pub/sub 브로드캐스트로 전파하는 것이 정석이다. 단 pub/sub은 메시지 유실 시 재전달이 없으므로 무효화 전파는 불완전하며, 짧은 로컬 TTL을 최후의 안전망으로 반드시 함께 둬야 한다. 이 복잡도를 감수할 만한 데이터(초고빈도 읽기 + 변경 드묾 + 짧은 불일치 허용)인지 판별하는 것이 설계의 핵심이다.**

---

## 0. 질문 + 의도

**질문**: "Local cache(Caffeine) + Redis 2단 캐시 구조의 장단점과 무효화 전파 방법은?"

**출제 의도**: 로컬 캐시의 노드 간 불일치라는 새 문제를 감수할 만큼 이득이 큰 상황(초고빈도 읽기)을 판별할 수 있는지, 그리고 pub/sub 무효화 같은 해법의 불완전함(메시지 유실 시 불일치가 TTL까지 지속)까지 짚을 수 있는지 — 시스템에 복잡도를 추가하는 결정을 얼마나 신중하게 내리는지를 잰다.

## 1. 왜 Redis 앞에 또 캐시를 두나 — 네트워크 왕복이라는 남은 비용

### 1-1. 전제 지식 — "L1", "L2"라는 이름은 어디서 왔나

이 주제에서 L1, L2라는 표기가 설명 없이 튀어나오는 경우가 많은데, 이 이름은 **CPU 캐시 계층**에서 빌려온 관례다.

CPU는 연산 장치 바로 옆에 아주 작고 아주 빠른 메모리를 두고, 그 바깥에 조금 더 크고 조금 더 느린 메모리를 두고, 다시 그 바깥에 메인 메모리를 둔다. 이때 **연산 장치에 가장 가까운 것이 레벨 1(Level 1, L1)이고, 멀어질수록 번호가 커진다.** 즉 번호는 "빠르기 등급"이 아니라 **"요청 지점으로부터의 거리"**를 뜻한다.

애플리케이션 캐시도 이 관례를 그대로 가져다 쓴다. 여기서 "요청 지점"은 요청을 처리하는 우리 애플리케이션 코드다.

| 레벨 | 무엇 | 어디에 있나 | 왜 이 번호인가 |
|---|---|---|---|
| L1 | Caffeine | 애플리케이션과 **같은 JVM 프로세스의 힙** | 요청을 처리하는 코드에 가장 가깝다 |
| L2 | Redis | **네트워크 건너** 다른 서버의 메모리 | 한 단계 멀다 |
| (원본) | PostgreSQL | 네트워크 건너 + 디스크 | 가장 멀다 |

그래서 "L1 캐시"라고 하면 이 문서에서는 항상 **JVM 안의 Caffeine**을 가리키고, "L2 캐시"는 **Redis**를 가리킨다.

### 1-2. Caffeine이 무엇인가

**Caffeine은 자바용 로컬(local) 캐시 라이브러리다.** "로컬"이라는 말이 핵심인데, 캐시된 데이터가 **애플리케이션 프로세스 자신의 힙 메모리 안에** 들어 있다는 뜻이다. 그래서 조회에 네트워크가 전혀 개입하지 않는다 — 코드 입장에서는 `HashMap.get()`을 부르는 것과 같은 층위의 연산이다.

그냥 `HashMap`을 쓰지 않는 이유는, 캐시에는 맵에 없는 두 가지가 필요하기 때문이다. **크기 상한**(무한히 쌓이면 힙이 터진다)과 **만료**(오래된 값은 스스로 사라져야 한다)다. Caffeine은 이 둘에 더해 어떤 항목을 먼저 버릴지 정하는 축출 정책과 히트율 통계를 제공한다. Spring Boot에서 캐시 추상화(`@Cacheable`)의 구현체로 흔히 쓰이는 것도 Caffeine이다.

정리하면 **L1은 "네트워크가 없는 캐시", L2는 "네트워크가 있는 캐시"**다. 이 한 줄이 2단 캐시의 모든 장단점의 출발점이다.

### 1-3. Redis를 붙여도 남아 있는 비용 — 왕복

Redis 캐시를 도입하면 DB 쿼리를 Redis 조회로 바꿔 큰 이득을 본다. 하지만 Redis 조회에도 **네트워크 왕복**이라는 비용이 여전히 남아 있다. 같은 데이터센터 안이라도 왕복은 수백 마이크로초에서 1밀리초 수준이고, 요청 하나를 처리하면서 캐시를 수십 번 읽는 코드라면 이 왕복이 누적돼 응답 시간의 주범이 된다.

세 계층의 지연을 자릿수로 나란히 놓으면 왜 한 겹을 더 얹는지가 보인다.

| 계층 | 실제로 하는 일 | 대략적 지연 |
|---|---|---|
| L1 (Caffeine) | 같은 프로세스 힙에서 참조 하나 따라가기 | 수십~수백 **나노초** (0.0001ms 안팎) |
| L2 (Redis) | 소켓으로 요청 보내고 응답 받기 + 메모리 조회 | 수백 마이크로초~1**밀리초** (0.5ms 안팎) |
| DB (PostgreSQL) | 네트워크 + 파서·플래너 + 버퍼/디스크 접근 | 수 밀리초~수백 밀리초 |

L1과 L2 사이는 **세 자릿수 이상**의 차이다(0.0001ms 대 0.5ms). L2와 DB 사이는 한 자릿수에서 세 자릿수 사이다. 즉 **DB → Redis로 옮겨서 얻은 것만큼의 이득이, Redis → 로컬로 옮길 때 한 번 더 남아 있다.**

그리고 Redis 조회 시간의 대부분은 Redis의 처리가 아니라 **오가는 데** 쓰인다는 점이 중요하다. 값 하나를 찾는 것은 마이크로초인데 왕복이 수백 마이크로초라면, 아끼는 대상은 Redis의 일이 아니라 **왕복 그 자체**다.

### 1-4. 조회 흐름 — 미스는 아래로 내려가고, 채우기는 역순으로 올라온다

2단 캐시의 동작은 두 방향으로 읽어야 한다. **찾을 때는 가까운 곳부터 아래로 내려가고, 찾은 값을 채울 때는 먼 곳부터 역순으로 올라온다.**

```
[조회 — 가까운 쪽부터 아래로]

  요청
   |
   v
  L1: Caffeine (JVM 힙, 인스턴스마다 따로)
   |-- 히트 --> 즉시 반환                      네트워크 0회
   |
   `-- 미스 --> L2: Redis (전 인스턴스 공유)
                 |-- 히트 --> [L1 채우기] --> 반환    네트워크 1회
                 |
                 `-- 미스 --> DB 조회
                               |
                               v
                          [L2 채우기] --> [L1 채우기] --> 반환
                                                        네트워크 1회 + DB 1회

[채우기 — 먼 쪽부터 역순으로 올라온다]

  DB에서 읽은 값 --> L2에 쓴다 --> L1에 쓴다 --> 응답
  (이 순서여야 다른 인스턴스도 다음 조회에서 L2에서 받아갈 수 있다)
```

채우기가 역순인 이유는 이렇다. DB에서 읽은 값을 L1에만 넣고 L2를 건너뛰면, **다른 인스턴스들은 여전히 L2 미스를 겪고 각자 DB를 때린다.** L2를 먼저 채워 놓아야 그 뒤에 오는 다른 인스턴스의 요청이 DB까지 내려가지 않는다.

기대 효과는 히트율의 곱으로 나타난다. L1 히트율이 95%라면 **전체 요청의 95%가 네트워크를 한 번도 타지 않고 끝난다.** 나머지 5%만 Redis로 내려가므로 Redis가 받는 트래픽 자체가 20분의 1로 줄어든다.

### 1-5. 어떤 데이터가 대상인가

전형적인 대상은 **읽기가 폭발적으로 많고, 잘 안 바뀌고, 크기가 작은** 데이터다. 시스템 설정, 기능 플래그(feature flag), 권한/역할 정의, 카테고리 트리, 코드성 데이터(공통 코드 테이블) 같은 것들이다.

가장 좋은 후보는 **요청마다 반드시 읽히는 데이터**다. 요청 하나를 처리하며 20번 읽히는 설정값이라면, 2단 캐시가 없애는 것은 왕복 1회가 아니라 왕복 20회다.

```java
// Before: 모든 요청이 매번 Redis 왕복 — 설정값 하나 읽는데 네트워크 1회
public boolean isFeatureEnabled(String featureKey) {
    return redisTemplate.opsForValue().get("feature:" + featureKey) != null;
}
// 요청당 이런 조회가 20번이면 요청당 Redis 왕복 20회.
// 왕복 0.5ms 기준으로 요청당 10ms를 네트워크에서만 쓰는 셈이고,
// Redis 입장에서도 인스턴스 수 x 초당 요청 수 x 20 만큼의 명령을 받는다.

// After: Caffeine을 앞단에 — 대부분의 조회가 JVM 안에서 끝난다
private final Cache<String, Boolean> localCache = Caffeine.newBuilder()
        // maximumSize가 없으면 캐시가 힙을 무한히 먹는다. 로컬 캐시로 인한
        // OOM은 대부분 이 한 줄이 빠져서 생긴다.
        .maximumSize(10_000)
        // 이 30초가 곧 "인스턴스 간 값이 어긋난 채로 있을 수 있는 최대 시간"이다.
        // 무효화 전파가 전부 실패해도 30초 뒤에는 맞는 값으로 돌아온다는 뜻 (3-2 참고).
        .expireAfterWrite(Duration.ofSeconds(30))
        .build();

public boolean isFeatureEnabled(String featureKey) {
    // get(key, loader)는 L1에 없을 때만 loader를 부른다.
    // 즉 L2(Redis) 왕복은 L1 미스일 때만 발생한다.
    return localCache.get(featureKey, key ->
            redisTemplate.opsForValue().get("feature:" + key) != null);
}
```

## 2. 얻는 것과 지불하는 것

### 2-1. 얻는 것

**지연 시간 제거.** L1 히트는 네트워크 왕복이 없다. 히트율이 높은 초고빈도 키라면 응답 시간에서 Redis 왕복 누적분이 통째로 사라진다. 위 예시에서 요청당 왕복 20회가 0회가 되면 요청당 10ms 안팎이 그냥 없어진다.

**Redis 부하와 hot key 완화.** 전 인스턴스가 같은 인기 키를 초당 수만 번 때리던 트래픽이 각자의 로컬 캐시에 흡수된다. 이건 **hot key 문제의 실전 해법**이기도 한데, 특정 키 하나에 트래픽이 몰리면 Redis Cluster에서 그 키를 담당하는 노드 하나만 과부하가 되고 노드를 늘려도 해결되지 않는다. 샤딩으로 못 푸는 문제를 "애초에 그 노드까지 안 가게 만들어서" 푸는 것이다.

**Redis 장애 시 완충.** Redis가 잠깐 죽어도 L1에 살아 있는 데이터로 당분간은 버틸 수 있다. 1단 캐시라면 Redis가 죽는 순간 전 트래픽이 DB로 직행해 DB까지 무너지는데, L1이 그 사이의 완충재가 된다.

### 2-2. 지불하는 것 — 인스턴스 간 불일치 (가장 큰 비용)

이 구조의 본질적 대가는 하나다. **L1은 인스턴스마다 따로 있고, 서로 모른다.**

서버 A와 서버 B가 각자의 힙에 같은 키의 값을 들고 있다고 하자. A에서 데이터가 바뀌면 A는 자기 L1을 갱신할 수 있지만, **B는 아무 일도 일어나지 않았다.** 무효화가 B까지 전파되기 전까지 B의 힙에는 옛 값이 그대로 살아 있다.

두 서버의 타임라인을 나란히 놓으면 이렇다.

```
        서버 A                                    서버 B
       ------------------------------------     ------------------------------------
 t0    L1["feature:new-editor"] = false          L1["feature:new-editor"] = false
       (두 서버가 같은 값을 들고 있다)

 t1    관리자 요청이 A로 들어옴
       값을 true로 변경
         (1) DB 커밋 -> true
         (2) L2(Redis) 키 삭제
         (3) A의 L1 무효화
       L1: (비어 있음)                            L1: false   <- A에서 무슨 일이
                                                              일어났는지 모른다

 t2    사용자 요청이 A로                          사용자 요청이 B로
       L1 미스 -> L2/DB 조회 -> true              L1 히트 -> false
       응답: 새 기능 보임                          응답: 새 기능 안 보임
       (L1에 true를 채움)

 t3    이후로도 무효화가 B에 도달하거나 B의 L1 TTL이 만료될 때까지
       "같은 요청인데 어느 서버로 가느냐에 따라 다른 답"이 계속된다
```

**핵심은 t2다.** 완전히 동일한 요청이 로드밸런서의 분배에 따라 다른 답을 받는다. 이건 버그가 아니라 이 구조가 원래 그런 것이다.

사용자 눈에는 이것이 이렇게 보인다. **새로고침할 때마다 값이 바뀌었다 안 바뀌었다 왔다갔다 한다.** 관리자가 "설정을 저장했는데 적용이 안 됐다"며 새로고침을 연타하면, 인스턴스가 4대일 때 대략 4번 중 1번만 새 값이 보인다. 로그를 봐도 애플리케이션 코드는 정상이라 원인을 찾기가 어렵다.

그래서 2단 캐시를 얹는 결정은 곧 **"이 데이터는 잠깐 어긋나도 되는가"**라는 질문에 예라고 답하는 결정이다.

### 2-3. 지불하는 것 — 나머지 비용

**JVM 메모리 점유와 GC 압박.** 캐시 데이터가 힙에 산다. `maximumSize` 없이 쓰면 로컬 캐시가 OOM의 직접적인 원인이 되고, 그 정도가 아니어도 힙에 오래 살아남는 객체가 늘면 GC가 훑어야 할 양이 늘어 정지 시간이 길어진다.

**메모리 중복.** 같은 데이터가 인스턴스 수만큼 복제된다. 인스턴스 20대면 같은 카테고리 트리가 힙에 20벌 존재한다. 크기가 작아야 한다는 조건이 여기서 나온다.

**무효화 복잡도.** Redis 한 곳만 지우면 끝나던 일이, **전 인스턴스의 L1까지 지워야 하는 분산 문제**로 바뀐다. 3절 전체가 이 문제를 다룬다.

**디버깅 난이도.** "이 값이 L1 것인가, L2 것인가, DB 것인가"라는 계층이 하나 늘어난다. 낡은 값을 추적하려면 어느 인스턴스의 L1인지까지 좁혀야 하는데, 로컬 캐시는 밖에서 들여다볼 수단이 기본으로는 없다.

### 2-4. 그래서 판단의 첫 질문

요약하면 **속도와 부하를 얻고 일관성과 단순함을 판다.**

그래서 도입 판단의 첫 질문은 성능이 아니라 **"몇 초의 불일치를 견딜 수 있는 데이터인가"**다. 잔액, 재고, 권한 회수처럼 즉시 일관성이 필요한 데이터는 애초에 후보가 아니다. 이 순서 — 성능 이득을 재기 전에 불일치 허용치를 먼저 묻는 것 — 가 면접에서 보려는 태도다.

## 3. 무효화 전파와 도입 판단 기준

### 3-1. 정석: Redis pub/sub으로 무효화 이벤트를 브로드캐스트

무효화 전파의 정석은 **Redis의 pub/sub(발행/구독)**을 방송 채널로 쓰는 것이다. pub/sub은 어떤 클라이언트가 채널에 메시지를 발행(PUBLISH)하면, 그 채널을 구독(SUBSCRIBE)하고 있는 모든 클라이언트에게 Redis가 그 메시지를 뿌려주는 기능이다.

데이터를 변경한 인스턴스가 L2(Redis)를 지우고, 동시에 무효화 채널에 키 이름을 발행한다. 전 인스턴스가 이 채널을 구독하고 있다가 메시지를 받으면 각자의 L1에서 그 키를 지운다.

```
서버 A: 데이터 변경
  -> (1) DB 커밋
  -> (2) Redis(L2) 키 삭제
  -> (3) PUBLISH cache-invalidation "feature:new-editor"

서버 A, B, C (전원 구독 중):
  <- 메시지 수신 -> 각자 localCache.invalidate("feature:new-editor")
```

```java
// 발행 측 — 데이터를 변경하는 모든 지점에서
public void updateFeature(String featureKey, boolean enabled) {
    featureRepository.update(featureKey, enabled);            // (1) DB
    redisTemplate.delete("feature:" + featureKey);            // (2) L2 삭제
    redisTemplate.convertAndSend("cache-invalidation",        // (3) 전 인스턴스에 전파
            "feature:" + featureKey);
}

// 구독 측 — 전 인스턴스가 동일하게 갖는 핸들러
public void onInvalidationMessage(String key) {
    // 새 값을 채우지 않고 지우기만 한다. 다음 조회가 L2/DB에서 최신 값을 가져온다.
    // 지우는 동작은 몇 번을 해도 결과가 같아서(멱등) 중복 수신에 안전하다.
    localCache.invalidate(key);
}
```

**순서에 주의할 점이 하나 있다. L2 삭제가 전파보다 먼저여야 한다.**

전파를 먼저 하면 이런 경합이 생긴다. 메시지를 받은 서버 B가 즉시 자기 L1을 지우고, 곧장 다음 요청을 처리하려고 L2를 읽는다. 그런데 A가 아직 L2를 안 지웠다면 **B는 L2에 남아 있는 옛 값을 읽어 자기 L1에 도로 채운다.** 방금 지운 자리에 옛 값이 다시 들어앉은 것이고, 이 값은 다음 무효화가 올 때까지 또는 TTL까지 살아남는다. 순서를 뒤집는 것만으로 무효화가 무력화되는 셈이다.

**자기가 발행한 메시지를 자기도 받는다.** pub/sub에서 발행자와 구독자는 별개의 역할이 아니라서, 서버 A가 발행한 무효화 메시지는 구독 중인 A 자신에게도 배달된다. 처리 방법은 둘이다.

- **그냥 받고 처리한다.** 삭제는 몇 번을 해도 결과가 같으므로, A가 이미 지운 키를 한 번 더 지워도 아무 해가 없다. 대부분 이걸로 충분하다.
- **발행자 식별자를 메시지에 실어 자기 것은 무시한다.** 인스턴스마다 고유 ID를 만들어 `{"key":"feature:x","from":"instance-7"}` 형태로 보내고, 수신 측에서 `from`이 자기 ID면 건너뛴다. 메시지가 아주 잦아 불필요한 무효화 작업 자체가 부담일 때만 필요한 최적화다.

### 3-2. 이 해법의 불완전함 — pub/sub은 유실되면 끝이다 (이 질문의 급소)

여기가 이 질문의 급소다. **Redis pub/sub은 메시지를 저장하지 않는다.**

발행 시점에 그 채널을 구독하고 있는 연결에만 즉시 뿌리고, 뿌린 뒤에는 잊는다. 큐처럼 쌓아뒀다가 나중에 접속한 구독자에게 주는 일이 없고, 못 받은 구독자에게 재전달하는 일도 없다. 이런 전달 보장을 **at-most-once(최대 1회)**라고 부른다 — "많아야 한 번 도착한다", 즉 **0번 도착할 수도 있다**는 뜻이다.

그래서 **그 순간 구독 중이지 않은 서버는 그 메시지를 영영 받지 못한다.** 언제 그런 일이 생기는가.

- **배포 중 재시작하는 서버.** 롤링 배포로 인스턴스가 하나씩 내려갔다 올라오는 동안, 내려가 있던 그 서버는 구독자가 아니다. 그 사이에 발행된 무효화는 이 서버에게는 없었던 일이 된다.
- **네트워크가 잠깐 끊긴 서버.** 커넥션이 흔들려 재접속하는 몇 초 사이의 메시지가 사라진다.
- **Redis 페일오버.** 마스터가 교체되는 동안 구독 연결이 끊겼다가 새 마스터로 재접속하는데, 그 틈의 메시지는 어디에도 없다.

메시지를 놓친 노드는 **자기 L1이 낡았다는 사실 자체를 알 방법이 없다.** 아무 신호도 못 받았으니 정상이라고 믿고 옛 값을 계속 서빙한다. 그리고 이 상태는 **그 키의 로컬 TTL이 다할 때까지 지속된다.**

바로 이것이 **짧은 L1 TTL이 선택이 아니라 필수인 이유**다.

```
[전파 성공 경로]   변경 --> PUBLISH --> 수신 --> L1 무효화       (수 ms 안에 정합)
[전파 실패 경로]   변경 --> PUBLISH --> (유실) --> ...
                                                  |
                                                  v
                                        L1 TTL 만료 --> 다음 조회가 L2/DB로
                                                        (최대 TTL만큼 늦게 정합)

  불일치 지속 시간의 상한 = L1 TTL.  TTL이 없으면 상한도 없다.
```

역할을 이렇게 나눠서 기억하면 정확하다. **pub/sub 전파는 "빠른 경로"이고, 정합성의 보장은 TTL이 진다.** 전파가 하는 일은 불일치를 30초에서 5밀리초로 줄이는 것이지, 불일치를 없애는 것이 아니다. 없앨 수 없는 나머지를 TTL이 유한한 시간 안에 정리한다.

그래서 실무에서는 **"무효화가 전부 유실돼도 최대 30초 뒤에는 맞는 값"**처럼 상한을 설계값으로 명시해 둔다. TTL 숫자가 성능 튜닝 파라미터가 아니라 **비즈니스와 합의한 불일치 허용치**라는 것이 이 구조의 관점이다.

여기에 방어를 한 겹 더 얹을 수 있다. **구독 연결이 끊겼다가 재연결될 때 L1을 통째로 비우는 것**이다(가산점 포인트). 끊겨 있던 동안 무엇을 놓쳤는지는 알 수 없지만, "끊겨 있었다"는 사실 자체는 클라이언트가 안다. 그러면 놓친 후보를 특정하는 대신 전부 버리면 된다. 재연결 직후 잠깐 L1 미스가 몰리는 대가로 "끊긴 동안 놓친 것"의 대부분을 커버한다.

### 3-3. 그 밖의 전파 방법과 완화책

**버전 키 (논리 버저닝).** Redis에 `config:version` 같은 카운터를 하나 두고, 데이터가 바뀔 때마다 `INCR`한다. 각 노드는 주기적으로(또는 조회할 때 싸게) 이 버전만 확인해서, 자기가 알던 버전과 다르면 L1을 통째로 비운다. pub/sub과 달리 **가져오는(polling) 방식이라 유실이 없다** — 메시지를 놓칠 일이 없고, 몇 번을 놓쳐도 다음 확인 때 값이 다르다는 사실은 그대로 남아 있다. 대신 전파 지연이 폴링 주기만큼 생기고, 키 단위가 아니라 뭉텅이로 비우게 되는 것이 보통이다.

**Redis 서버 주도 무효화 (client-side caching).** Redis 6부터 RESP3 프로토콜을 기반으로 제공되는 기능이다(가산점 포인트). 직접 만든 pub/sub 무효화와의 차이가 이 기능의 요점이므로 정확히 갈라 두자.

- **직접 만든 pub/sub은 브로드캐스트다.** 채널 하나에 모든 무효화가 흐르고, 모든 인스턴스가 그것을 다 받는다. 내가 캐시하지도 않은 키의 무효화 메시지도 받아서 "어? 그건 내 L1에 없는데" 하고 버린다. 그리고 발행 코드를 **애플리케이션이 변경 지점마다 직접 심어야** 해서, 변경 경로가 여럿이면 하나를 빠뜨릴 수 있다.
- **client-side caching은 서버가 추적해서 골라 보낸다.** Redis가 **각 클라이언트가 어떤 키를 읽어 갔는지(= 캐시하고 있을 법한지)를 기억해 두었다가**, 그 키가 변경되면 그 키를 캐시한 클라이언트에게만 무효화를 밀어준다. 즉 **"내가 관심 있는 키만" 받는다**는 점이 브로드캐스트와의 결정적 차이다. 그리고 변경이 어느 경로로 일어나든 서버가 감지하므로 **애플리케이션이 PUBLISH를 심는 것을 빠뜨릴 여지가 없다.**

전제 조건이 둘 있다. 서버가 클라이언트에게 먼저 말을 걸 수 있어야 하므로 **RESP3를 지원하는 클라이언트 라이브러리**가 필요하고, 서버가 "누가 무엇을 캐시했는지"를 들고 있어야 하므로 **서버 쪽에 추적 정보 유지 비용**이 든다. 참고로 키를 하나씩 추적하지 않고 키 접두사 단위로 알림을 받는 브로드캐스트 모드도 있는데, 이 경우 서버의 추적 부담이 줄어드는 대신 관심 없는 키의 알림도 받게 된다.

**그냥 짧은 TTL만으로.** 전파 장치를 아예 두지 않고 로컬 TTL 수 초~수십 초만 걸어두는 방식이다. 가장 단순하고, **"몇 초 불일치 허용 + 변경 드묾"인 데이터라면 이걸로 충분한 경우가 실무에 의외로 많다.** 하루에 한 번 바뀌는 설정에 pub/sub 구독자와 발행 코드와 재연결 처리를 붙이는 것은, 얻는 것에 비해 유지보수할 코드가 너무 많다. **복잡도를 추가하지 않는 것도 유효한 설계 선택**이라는 점을 말할 수 있어야 한다.

### 3-4. 언제 2단이 정당한가

2단 캐시는 문제를 하나 풀고(지연·부하) 문제를 하나 만든다(불일치·복잡도). 그래서 도입이 정당해지는 조건을 체크리스트로 두고 판단한다.

- **초고빈도 읽기인가.** 요청마다, 혹은 요청당 여러 번 읽히는가. 하루에 몇 번 읽는 데이터에 2단은 순수한 복잡도 낭비다.
- **변경이 드문가.** 자주 바뀌면 무효화 전파가 상시 가동돼 L1 히트율이 떨어지고, 지불하는 복잡도만 남는다.
- **짧은 불일치를 비즈니스가 견디는가.** "최대 N초 동안 옛 값"이 허용되는가. 권한 회수, 잔액, 재고 차감은 불가다.
- **크기가 작은가.** 힙에 인스턴스 수만큼 복제돼도 부담 없는 크기인가.

이 조건을 모두 만족하는 대표가 설정·플래그·코드성 데이터이고, 하나라도 어긋나면 **Redis 단독(1단)이 정답**이다.

면접에서 원하는 답의 골격은 "무조건 2단이 빠르니 좋다"가 아니라 **"이 조건일 때만 복잡도가 정당화된다"는 판별 기준을 먼저 말하는 것**이다.

## 4. 꼬리질문 대비 포인트

### "pub/sub 무효화 메시지가 유실되면 어떻게 되나요?"

놓친 노드의 L1에 낡은 값이 남고, **그 노드 스스로는 낡았다는 걸 알 수 없어 불일치가 로컬 TTL 만료까지 지속된다.** pub/sub이 저장도 재전달도 하지 않는 at-most-once 방송이기 때문이다.

그래서 방어를 겹으로 둔다.

1. **짧은 로컬 TTL** — 불일치 지속 시간의 상한을 만든다. 이것이 없으면 상한 자체가 없다.
2. **구독 재연결 시 L1 전체 clear** — 끊겨 있던 동안 놓친 것을 특정할 수 없으니 전부 버린다.
3. **유실이 정말 치명적이면 전파 채널을 바꾼다** — 버전 키 폴링처럼 가져오는 방식이나, 메시지가 저장되는 Redis Streams로 옮긴다.

한 문장으로 정리하면 **"pub/sub 전파는 최적화이고, 정합성의 보장은 TTL이 진다"**는 역할 분리다.

### "로컬(L1) TTL은 Redis(L2) TTL보다 길게 잡나요, 짧게 잡나요?"

**짧게 잡는다.** 근거는 두 캐시의 무효화 신뢰도가 다르다는 데 있다.

L2는 전 인스턴스가 공유하는 한 곳이라 `DEL` 한 번이면 확실히 지워진다. 반면 L1은 인스턴스마다 따로라 무효화가 방송에 의존하고, 그 방송은 유실될 수 있다. 즉 **L1의 불일치 상한이 곧 L1 TTL**이고, L2에는 그런 상한이 필요 없다.

전형적인 구성은 **L1 수 초~수십 초 / L2 수 분~수 시간**이다.

거꾸로 L1을 L2보다 길게 잡으면 역전이 생긴다. L2는 이미 갱신됐는데 L1이 옛 값을 더 오래 붙들고 서빙하므로, L2를 갱신한 의미가 그 인스턴스에서는 사라진다.

### "캐시 무효화(evict)와 캐시 갱신(put) 중 무엇을 전파해야 하나요?"

**삭제(evict)를 전파한다.**

새 값을 메시지에 실어 각 노드가 자기 L1에 `put`하게 만들면 **순서 역전** 문제가 생긴다. 값을 연속으로 두 번 바꿔서 무효화 메시지가 두 개 나갔는데, 네트워크 사정으로 첫 번째 메시지가 두 번째보다 늦게 도착하면, **늦게 도착한 옛 값이 이미 들어와 있던 새 값을 덮어쓴다.** 그리고 이 잘못된 값은 다음 변경이나 TTL까지 살아남는다.

삭제는 이 문제가 없다. 몇 번을 어떤 순서로 적용해도 결과가 "그 키가 없음"으로 같기 때문이다(멱등). 비어 있는 자리는 다음 조회가 L2/DB에서 최신 값으로 채운다.

"캐시 갱신 vs 삭제"라는 일반론과 같은 논리인데, 전파 채널에서는 **순서 보장이 없다**는 조건이 더해져 더 극적으로 적용되는 셈이다.

### "이 구조를 도입하면 안 되는 데이터는 무엇인가요?" (시니어 변별 포인트)

즉시 일관성이 요구되는 데이터다. 결제, 잔액, 재고 차감이 대표이고, 특히 위험한 것이 **권한/세션 회수**다.

관리자가 계정을 차단했는데 어떤 노드의 L1에 옛 권한이 TTL 동안 남아 있으면, **차단된 사용자가 그 노드로 라우팅되는 동안 계속 접근할 수 있다.** 성능 최적화가 보안 사고로 이어지는 경로다. 세션·권한은 "짧은 불일치"가 곧 "짧은 무단 접근 시간"이라서 허용치를 0으로 잡을 수밖에 없다.

그 밖에 부적합한 것들도 이유가 각각 있다.

- **변경이 잦은 데이터** — 무효화 전파가 상시 가동돼 히트율이 낮아지고, 이득은 사라지고 복잡도만 남는다.
- **큰 객체** — 인스턴스 수만큼 힙에 복제되므로 GC 압박을 그 배수로 만든다.
- **히트율이 낮은 롱테일 키** — 캐시에 넣어도 다시 조회되기 전에 축출되므로 L1이 사실상 낭비다.

핵심은 판별을 기술이 아니라 **요구사항으로** 한다는 점이다. **"이 데이터의 불일치 상한(L1 TTL)을 비즈니스가 견딜 수 있는가"** 한 문장으로 판단한다는 것이 시니어의 답이다.

### "Redis 6의 client-side caching은 직접 구현한 pub/sub 무효화와 뭐가 다른가요?" (가산점 포인트)

차이가 두 가지다.

**첫째, 무효화를 누가 감지하는가.** 직접 구현은 **애플리케이션이** 변경 지점마다 `PUBLISH`를 심어야 한다. 변경 경로가 여럿이면(관리자 API, 배치, 마이그레이션 스크립트) 하나를 빠뜨리기 쉽고, 빠뜨린 경로로 값이 바뀌면 그 변경은 영원히 전파되지 않는다. client-side caching은 **Redis 서버가** 키 변경을 감지하므로 변경 경로 누락이 구조적으로 없다.

**둘째, 누구에게 보내는가.** 직접 구현은 채널 하나에 뿌리는 **브로드캐스트**라 모든 인스턴스가 모든 무효화를 다 받는다. client-side caching은 서버가 **각 클라이언트가 어떤 키를 읽어 갔는지 추적해 두었다가, 그 키를 캐시한 클라이언트에게만** 무효화를 밀어준다. **"내가 관심 있는 키만" 받는다는 점**이 결정적 차이다.

대신 전제와 비용이 있다. RESP3와 클라이언트 라이브러리 지원이 필요하고, 서버가 추적 정보를 들고 있는 부담이 생긴다.

그리고 **둘 다 "연결이 끊긴 사이의 무효화는 보장하지 못한다"는 한계는 같다.** 그래서 방어는 동일하게 필요하다 — 끊김을 감지하면 로컬 캐시를 비우고, 짧은 TTL을 최후의 안전망으로 둔다.

## 한 줄 요약

2단 캐시는 Redis 왕복조차 병목인 초고빈도 읽기를 JVM 안(Caffeine)에서 끝내 지연과 Redis 부하를 없애는 대신 "노드마다 값이 다를 수 있다"는 불일치를 지불하는 구조로, 무효화는 Redis pub/sub 브로드캐스트로 전파하되 pub/sub은 유실 시 재전달이 없어 불완전하므로 짧은 L1 TTL을 불일치의 상한이자 최후의 안전망으로 반드시 함께 두고 — 애초에 이 복잡도는 "초고빈도 읽기 + 변경 드묾 + 짧은 불일치 허용" 조건을 만족하는 데이터에서만 정당화된다.
