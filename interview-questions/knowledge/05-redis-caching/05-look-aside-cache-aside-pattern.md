# Look-aside(Cache-aside) 패턴 — 애플리케이션이 캐시를 "옆에 두고" 직접 채우는 기본기와 그 빈틈

> 핵심 관전 포인트: **Look-aside는 애플리케이션이 ① 캐시를 먼저 조회하고 ② 히트면 그대로 반환, ③ 미스면 DB에서 읽어 ④ 캐시에 적재한 뒤 반환하는 패턴이다. 
> 캐시는 get/set만 받는 수동적인 저장소일 뿐이고 **적재 책임이 애플리케이션에 있다**는 것이 핵심이며, 이 점이 캐시가 스스로 원본을 읽어 채우는 read-through, 쓰기까지 캐시가 대신하는 write-through/write-behind와 갈리는 지점이다. 
> 쓰기는 DB에 쓰고 캐시를 삭제하는 조합이 정석이다. look-aside가 실무 기본값인 이유는 캐시가 통째로 죽어도 모든 읽기가 DB로 흘러 서비스가 살아남고, 무엇을 어떤 키로 얼마나 캐시할지를 애플리케이션이 조회 경로별로 통제할 수 있기 때문이다 
> — 대신 이 패턴에는 미스 시 왕복 비용, 동시 미스 폭주(스탬피드), 그리고 읽기가 DB에서 읽은 값을 적재하기 직전에 쓰기가 끼어들어 옛 값이 최종 승자가 되는 경합 창이 구조적으로 내장되어 있다. 
> 이 창은 읽기와 쓰기가 서로를 모르는 별개 경로라 완전히 막을 수 없고, 그래서 TTL은 성능 장치가 아니라 정합성의 최후 안전망이다 — 이 빈틈들이 곧 캐싱 고난이도 질문 전체의 출발점이다.**

---

## 0. 질문 + 의도

**질문**: "Look-aside(Cache-aside) 패턴을 설명해주세요."

**출제 의도**: 기본 패턴의 흐름을 알아야 그 패턴의 빈틈(미스 폭주, 갱신 경합)을 논할 수 있다. 이후 고난이도 질문들(스탬피드, 정합성, 캐시 무력화 방어)의 공통 기반 — 흐름을 그릴 수 있는지와 함께, 그 흐름의 어느 지점에서 문제가 자라는지까지 짚는지를 본다.

## 1. 선택지부터 — 캐시 패턴 네 가지와 look-aside가 기본값이 된 이유

"look-aside가 표준이다"부터 말하면 왜 그것인지가 빠진다. **선택지가 무엇이고 어떤 축으로 갈리는지를 먼저 세운 다음** 결론으로 가자.

### 1-1. 패턴이 갈리는 단 하나의 축

캐시를 쓰는 코드에는 반드시 있어야 하는 일이 있다. **캐시에 없을 때 원본(DB)을 다녀와 채우는 일**, 그리고 **원본이 바뀌었을 때 캐시를 맞추는 일**이다.

패턴을 나누는 축은 하나다. **그 일을 하는 코드가 어디에 사는가.**

애플리케이션 코드 안에 있으면 look-aside이고, 캐시 계층(라이브러리·미들웨어) 안에 숨어 있으면 read-through / write-through / write-behind다. 이름들이 복잡해 보이지만 이 한 축으로 전부 정리된다.

### 1-2. read-through — 캐시가 스스로 원본을 읽어 채운다

**read-through(읽기 관통)**는 애플리케이션이 **캐시만 바라보는** 방식이다. 앱은 `cache.get(key)` 하나만 호출하고, 그 키가 없으면 **캐시가 미리 등록해 둔 로더(loader)를 호출해 원본에서 읽어 스스로 채운 뒤** 값을 돌려준다. 
앱 입장에서는 미스가 존재하지 않는 것처럼 보이고, 요청이 캐시를 "관통해서" 원본까지 갔다 온다는 의미로 through라는 이름이 붙었다.

Java 진영에서는 Caffeine의 `CacheLoader`가 대표적이다. 캐시를 만들 때 "이 키가 없으면 이 함수로 값을 만들어라"를 등록해 두는 형태다.

```java
// read-through: 로더를 캐시에 등록해 두면 미스 처리는 캐시가 알아서 한다
LoadingCache<Long, Product> cache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofMinutes(5))
        .build(id -> productRepository.findById(id)   // 이것이 로더
                .orElseThrow(ProductNotFoundException::new));

// 호출부에는 캐시 조회 한 줄뿐이다. 미스/DB조회/적재가 전부 캐시 안에 있다.
Product product = cache.get(id);
```

### 1-3. write-through — 캐시에 쓰면 캐시가 DB까지 동기로 반영한다

**write-through(쓰기 관통)**는 쓰기의 대칭형이다. 앱이 **캐시에 쓰면** 캐시가 그 쓰기를 **DB까지 동기적으로 전달**하고, DB 쓰기까지 성공해야 앱에 성공을 돌려준다.

장점은 캐시와 DB가 항상 같은 값을 갖는다는 것이다. 쓰기가 한 경로로만 흐르므로 "캐시만 낡은 상태"가 원리적으로 생기지 않는다.

대가는 **쓰기 지연이 캐시 쓰기 + DB 쓰기의 합이 된다**는 것, 그리고 **읽히지도 않을 값까지 캐시에 올라간다**는 것이다. 쓰기가 많고 그중 다시 읽히는 비율이 낮은 데이터라면 캐시가 쓰레기로 채워진다.

### 1-4. write-behind — 캐시에 먼저 쓰고 DB 반영은 나중에

**write-behind(뒤에서 쓰기, write-back이라고도 한다)**는 앱이 캐시에 쓰면 **캐시가 즉시 성공을 반환하고, DB 반영은 비동기로 나중에** 처리하는 방식이다. 여러 건을 모아 한 번에 쓰거나(배치), 같은 키에 대한 연속 쓰기를 마지막 값 하나로 합쳐서 쓸 수 있어 **쓰기 처리량이 압도적으로 높다.**

대가는 명확하다. **DB에 반영되기 전 구간이 존재하므로, 그 사이 캐시 노드가 죽으면 그 쓰기는 사라진다.** 캐시는 기본적으로 휘발성 저장소이므로 이 유실은 실재하는 위험이다. 조회수·좋아요 카운터처럼 몇 건 사라져도 되는 데이터에는 훌륭한 선택이지만, **잔액·주문처럼 유실이 곧 사고인 데이터에는 쓸 수 없다.**

### 1-5. look-aside — 애플리케이션이 캐시를 옆에 두고 직접 오간다

**look-aside(옆을 본다, cache-aside라고도 한다)**는 앞의 셋과 반대로 **원본을 다녀오는 코드가 전부 애플리케이션에 있는** 방식이다. 캐시와 DB는 서로의 존재를 모르고, 둘 사이를 오가며 조율하는 유일한 주체가 애플리케이션이다.

이름의 뜻이 구조를 그대로 말해 준다. 캐시가 요청 경로 **위에(through)** 놓여 요청이 그것을 관통하는 것이 아니라, 요청 경로 **옆에(aside)** 비켜 놓여 있고 애플리케이션이 필요할 때 고개를 돌려 들여다보는 것이다.

### 1-6. 그래서 왜 look-aside가 실무 기본값인가

이제 결론을 낼 수 있다. 근거는 셋이다.

**첫째, Redis에는 애초에 다른 선택지가 없다.** read-through와 write-through는 캐시 계층이 DB를 읽고 쓸 줄 알아야 성립하는데, **Redis는 여러분의 DB를 모른다.** 어떤 테이블에서 어떤 조건으로 읽어야 하는지 알려줄 방법 자체가 없다. 그러니 누군가가 채워야 하고, 그 누군가는 애플리케이션이다. Caffeine 같은 인프로세스(같은 JVM 안에서 도는) 캐시는 로더를 자바 함수로 등록할 수 있어 read-through가 되지만, 네트워크 건너편의 Redis에는 그 방법이 없다.

**둘째, 캐시가 죽어도 서비스가 산다.** look-aside에서 캐시는 **선택적 최적화 계층**으로 남는다. 캐시 조회가 실패하면 그것은 미스와 같은 상황이고, 코드는 DB로 간다. Redis 클러스터가 통째로 내려가도 **모든 읽기가 DB로 흘러 기능은 유지된다.** 성능 저하이지 기능 장애가 아니다. read-through에서는 캐시가 요청 경로 위에 있으므로 캐시 계층이 죽으면 그 경로 자체가 끊긴다. (단, 이 장점에는 조건이 붙는다 — DB가 그 트래픽을 버틸 때만이다. 3-4에서 다룬다.)

**셋째, 무엇을 캐시할지를 애플리케이션이 통제한다.** 같은 상품 데이터라도 목록 조회에는 요약 형태를, 상세 조회에는 전체 형태를 캐시하고 싶을 수 있다. 로그인 사용자에게만 캐시하고 싶을 수도 있고, 결과가 비어 있으면 캐시하지 않거나 아주 짧은 TTL만 주고 싶을 수도 있다. **키 설계·TTL·캐시 여부를 조회 경로별로 다르게 정하는 자유**는 적재 코드가 애플리케이션에 있기 때문에 생긴다. 캐시 계층에 로직을 밀어 넣으면 이 세밀한 통제가 어려워진다.

정리하면 이렇다.

| 패턴 | 원본을 다녀오는 코드의 위치 | 특징 |
|---|---|---|
| Look-aside | 애플리케이션 | 미스 시 앱이 DB를 읽고 직접 적재 |
| Read-through | 캐시 계층 | 미스 시 캐시가 등록된 로더로 원본을 읽어 채움 |
| Write-through | 캐시 계층 | 쓰기를 캐시에 하면 캐시가 DB까지 동기 반영 |
| Write-behind | 캐시 계층 | 캐시에 먼저 쓰고 DB 반영은 비동기 (유실 위험) |

## 2. 흐름 — 읽기와 쓰기를 어떻게 짜는가

### 2-1. 읽기 흐름

```
[읽기 요청]
    │
    ▼
① 캐시 조회 (GET product:42)
    │
    ├─ 히트 ──▶ ② 캐시 값 반환 (DB 안 감. 끝)
    │
    └─ 미스 ──▶ ③ DB 조회
                    │
                    ▼
                ④ 캐시에 적재 (SET product:42 <값> EX 300)
                    │
                    ▼
                ⑤ 값 반환
```

코드로 쓰면 이 다섯 단계가 그대로 다섯 줄이 된다.

```java
public Product findProduct(Long id) {
    String key = "product:" + id;

    // ① 캐시 먼저. DB보다 먼저 보는 것이 look-aside의 출발점이다.
    Product cached = redisTemplate.opsForValue().get(key);
    if (cached != null) {
        return cached;                                       // ② 히트 → 즉시 반환
    }

    // ③ 미스 → 원본으로. 이 코드가 애플리케이션에 있다는 것이
    //    look-aside를 read-through와 가르는 지점이다.
    Product product = productRepository.findById(id)
            .orElseThrow(ProductNotFoundException::new);

    // ④ 적재. TTL을 반드시 함께 준다 — 3-3의 경합으로 옛 값이 들어갔을 때
    //    그 낡음을 끝내주는 유일한 장치가 TTL이기 때문이다.
    redisTemplate.opsForValue()
            .set(key, product, Duration.ofMinutes(5));
    return product;                                          // ⑤ 반환
}
```

### 2-2. 게으른 적재(lazy loading)란 무엇인가 — 그리고 그 반대편

이 흐름의 첫 번째 성질이 **게으른 적재(lazy loading)**다. 여기서 "게으르다"는 **미리 준비해 두지 않고, 실제로 그 데이터를 달라는 요청이 왔을 때 비로소 채운다**는 뜻이다. 캐시에 무엇이 들어갈지를 미리 계획하지 않고 트래픽이 알아서 결정하게 두는 것이다.

**이득은 메모리 효율**이다. 실제로 읽힌 데이터만 캐시에 들어가므로, 아무도 안 보는 데이터로 메모리를 낭비하지 않는다. 상품이 100만 개라도 실제 조회되는 것이 1만 개라면 캐시에는 1만 개만 산다.

**대가는 첫 요청이 반드시 비용을 낸다는 것**이다. 어떤 키든 처음 읽히는 순간과 만료 직후 다시 읽히는 순간에는 반드시 미스가 나고, 그 요청은 DB까지 갔다 온다. **캐시의 이득은 "두 번째 이후 요청"에만 생긴다.**

반대편 개념이 **캐시 워밍(cache warming, 예열)**이다. 요청을 기다리지 않고 **미리 캐시를 채워 두는 것**이다. 배포 직후 배치가 인기 상품 상위 1,000개를 미리 적재해 두면, 사용자 첫 요청부터 히트가 된다. 게으른 적재가 "수요가 공급을 부른다"면 워밍은 "공급을 미리 깔아 둔다"이다.

둘은 배타적이지 않다. **기본은 게으른 적재로 두고, 미스 비용을 감당할 수 없는 소수의 핵심 키에만 워밍을 얹는 것**이 실무의 조합이다. 워밍을 전체에 적용하면 게으른 적재의 이득(메모리 효율)을 통째로 버리는 셈이 되기 때문이다.

### 2-3. 적재 책임이 애플리케이션에 있다는 뜻

두 번째 성질은 **적재 책임의 소재**다. 캐시는 get/set만 받는 수동적 저장소이고, **무엇을 어떤 키로 언제 얼마 동안 넣을지는 전부 애플리케이션 코드가 정한다.**

이것이 1-6의 세 번째 근거(통제권)의 실체이자, 동시에 뒤에 나올 모든 빈틈의 원인이기도 하다. **캐시가 아무것도 조율해 주지 않으므로, 조율이 필요한 상황은 전부 애플리케이션이 직접 처리해야 한다.** 3절의 빈틈들은 하나같이 "캐시가 대신 해 주지 않는 조율"의 목록이다.

(가산점 포인트) 스프링의 `@Cacheable`은 이 look-aside 흐름을 **프록시가 대신 해 주는 선언적 구현**이다. 메서드 호출을 가로채 캐시를 먼저 보고, 없으면 원래 메서드를 실행해 그 반환값을 캐시에 넣는다. "직접 짜면 위 코드고, 애너테이션을 붙이면 프록시가 똑같은 일을 한다"고 연결하면 좋다. 다만 프록시가 대신 해 주는 것은 흐름일 뿐 **조율이 아니라는 점**은 구분해야 한다 — 3절의 빈틈들은 `@Cacheable`을 써도 그대로 남는다.

### 2-4. 쓰기 흐름 — DB에 쓰고, 캐시는 갱신이 아니라 삭제한다

look-aside는 이름 그대로 **읽기 패턴**이다. 쓰기를 어떻게 할지는 별도로 정해야 하고, 정석 조합은 **DB에 먼저 쓰고(커밋), 캐시를 삭제(evict)**하는 것이다.

```java
@Transactional
public void updatePrice(Long id, long newPrice) {
    productRepository.updatePrice(id, newPrice);   // ① DB 갱신 (트랜잭션 안)
}
// ② 커밋 "후" 캐시 삭제 — 다음 읽기가 미스를 내고 DB의 새 값을 적재한다.
//    커밋 전에 지우면, 그 사이 들어온 읽기가 아직 롤백될지 모르는
//    상태의 DB를 읽어 캐시에 올릴 수 있다.
//    (커밋 후여야 하는 이유의 전개는 07 문서에서 상세히 다룬다)
```

삭제해 두면 다음 읽기가 자연스럽게 미스 → DB의 새 값 적재로 이어진다. 그런데 여기서 자연스러운 의문이 하나 생긴다. **새 값을 이미 알고 있는데, 왜 지우기만 하고 그 값을 캐시에 넣어 주지 않는가?** 넣어 주면 다음 읽기가 미스를 안 낼 텐데 말이다.

이유가 셋이다.

**첫째, 동시 쓰기의 순서가 역전될 수 있다.** 쓰기 A(가격 2000)와 쓰기 B(가격 3000)가 거의 동시에 들어왔다고 하자. DB에서는 락이 순서를 정리해 주므로 최종 값이 무엇인지 확정된다. 그런데 캐시 갱신은 그 락 바깥에서 일어나는 별도의 네트워크 호출이라, **DB에는 B가 마지막으로 반영됐는데 캐시 SET은 A가 나중에 도착**하는 순서 역전이 가능하다. 그러면 캐시에는 2000이 남고 DB에는 3000이 있는 불일치가 TTL이 다할 때까지 지속된다. **삭제는 이 문제가 없다** — 둘 다 "삭제"이므로 어느 쪽이 나중에 도착하든 결과는 "키 없음"으로 같고, 다음 읽기가 DB의 진실을 가져온다.

**둘째, 쓰기 경로가 캐시의 값 형태를 만들 수 있다는 보장이 없다.** 캐시에 들어 있는 것이 단순한 엔티티가 아니라 여러 테이블을 조인해 만든 화면용 DTO이거나 집계 결과라면, 가격만 바꾸는 쓰기 경로가 그 전체 형태를 다시 만들어야 한다. 이는 **쓰기 코드가 읽기 코드의 조회 로직을 복제해 갖게 되는 결합**이다. 삭제는 그 결합을 만들지 않는다 — "이 값은 이제 못 믿는다"는 신호만 보내고, 새 값을 만드는 일은 읽기 경로에 그대로 남겨 둔다.

**셋째, 읽히지도 않을 값을 미리 계산하는 낭비가 생긴다.** 쓰기가 잦고 읽기가 드문 키라면, 매 쓰기마다 캐시를 갱신해 봐야 대부분 읽히기 전에 다시 덮어써진다. 삭제는 다음 읽기가 있을 때만 값을 만든다 — 2-2의 게으른 적재 원칙과 일관된다.

이 논쟁(갱신 vs 삭제)에는 더 들어갈 층이 있고, 그것은 별도 문서 `07-cache-db-consistency-update-vs-delete.md`에서 다룬다. 여기서는 **"기본값은 삭제이고, 그 근거는 순서 역전·결합·낭비 셋"**까지 말할 수 있으면 된다.

## 3. 이 패턴에 내장된 빈틈 — 고난이도 질문들의 출발점

Look-aside를 **"설명할 줄 안다"와 "빈틈을 안다"의 차이**가 이 질문의 변별점이다. 아래 넷은 구현을 잘못해서 생기는 버그가 아니라 **패턴의 구조에서 필연적으로 나오는 성질**이다.

### 3-1. 미스 비용과 cold cache

미스가 났을 때 정확히 무엇이 늘어나는지 단계로 세어 보자.

| | 히트일 때 | 미스일 때 |
|---|---|---|
| 캐시 왕복 | 1회 (GET) | 2회 (GET + SET) |
| DB 왕복 | 0회 | 1회 |
| 합계 | 1회 | 3회 |

**미스 한 번은 캐시 조회 1회 + DB 조회 1회 + 캐시 적재 1회, 총 3회의 네트워크 왕복**이다. 캐시를 안 썼을 때(DB 1회)보다 **오히려 두 번 더 왕복한다.** 미스 상황에서 캐시는 도움이 아니라 순수한 오버헤드라는 뜻이다.

평소에는 이것이 문제가 안 된다. 히트율이 90%라면 대부분의 요청은 1회 왕복으로 끝나고, 10%가 내는 3회 왕복은 전체 평균에 묻힌다.

문제는 **히트율이 0이 되는 순간**이다. 배포 직후나 캐시 장애 복구 직후에는 캐시가 통째로 비어 있고, 이 상태를 **cold cache(차가운 캐시)**라고 부른다. 데워지지 않았다는 뜻이다. 이때 들어오는 모든 요청이 미스이므로 **DB는 캐시가 없던 시절의 트래픽을 그대로 맞는다.** 게다가 요청마다 쓸모없는 캐시 왕복 2회가 얹힌다.

여기서 진짜 위험은 **용량 계획의 전제가 깨진다**는 데 있다. 캐시 히트율 90%를 전제로 DB 스펙을 잡았다면, DB는 평소 트래픽의 10분의 1만 감당하도록 준비된 상태다. cold cache 순간 DB가 받는 부하는 **평소의 10배**가 되고, 이건 장애다. 그래서 **캐시 워밍(2-2)이 배포 절차에 들어간다.**

### 3-2. 동시 미스 폭주 — 캐시 스탬피드

인기 키 하나가 만료되는 순간을 생각해 보자. 그 키를 초당 1,000번 읽던 요청들이 **전부 동시에 미스를 본다.** 그리고 전부 DB로 가서 **같은 쿼리를 1,000번 실행하고, 전부 같은 값을 캐시에 적재한다.**

원인은 look-aside의 구조 그 자체다. **미스 처리에 "한 명만 다녀와라"라는 조정 장치가 없다.** 2-3에서 본 대로 캐시는 아무것도 조율해 주지 않고, 각 요청 스레드는 다른 스레드가 지금 같은 키를 재계산 중이라는 사실을 알 방법이 없다.

완화책은 넷이다 — **분산 락으로 한 요청만 재계산하게 하기**, **TTL에 지터를 섞어 만료 시각 자체를 분산하기**, **만료 전에 백그라운드로 미리 갱신하기(refresh-ahead)**, 스프링이라면 **`@Cacheable(sync = true)`**. 각각이 무엇을 공략하고 어떤 대가를 치르는지는 06번 문서(캐시 스탬피드)에서 본격적으로 다룬다.

### 3-3. 읽기·쓰기 경합 — 옛 값이 늦게 적재되는 창

**이 문서에서 가장 중요한 대목이다.** look-aside를 쓰는 한 반드시 존재하고, 이 창을 그릴 수 있는지가 시니어 변별의 실체다.

문제의 씨앗은 2-1의 읽기 흐름에 있다. **③ DB 조회와 ④ 캐시 적재는 같은 순간이 아니다.** 그 사이에는 애플리케이션이 값을 가공하고, 직렬화하고, Redis로 네트워크 요청을 보내는 시간이 있다. 짧지만 0은 아니다. 그리고 **그 사이에 쓰기 요청이 통째로 지나갈 수 있다.**

```
                읽기 요청 A                     쓰기 요청 B
              (price 조회)                   (price를 2000으로 변경)
 ─────────────────────────────────────────────────────────────────────
 t0   ① 캐시 GET product:42 → 미스
      (캐시에 아무것도 없다)
 
 t1   ③ DB 조회 → price=1000 을 읽음
      ★ 이 값을 손에 들고 있다.
        아직 캐시에는 안 넣었다.
 
 t2                                    ① DB UPDATE price=2000, 커밋
                                          (DB의 진실은 이제 2000)
 
 t3                                    ② 캐시 DEL product:42
                                          지울 것이 없다. 캐시는 t0부터 비어 있었으니까.
                                          B는 자기 할 일을 완벽하게 수행했다.
 
 t4   ④ 캐시 SET product:42 = 1000
      ★ t1에 읽어둔 옛 값이 지금 적재된다.
        옛 값이 최종 승자가 됐다.
 ─────────────────────────────────────────────────────────────────────
 결과: DB = 2000,  캐시 = 1000
       TTL이 다할 때까지 모든 읽기가 1000을 받는다.
```

이 시나리오의 고약한 점을 정확히 짚자. **누구도 잘못하지 않았다.** 읽기 A는 look-aside를 교과서대로 수행했고, 쓰기 B도 "DB 쓰고 캐시 삭제"라는 정석을 정확히 지켰다. 삭제 호출이 실패한 것도 아니다 — **성공했는데 지울 것이 그 시점에 없었을 뿐**이다. 그리고 그 뒤에 A가 자기 손에 들고 있던 과거의 값을 되살렸다.

**왜 이 창을 완전히 막을 수 없는가.** 막으려면 "A가 t1에 읽은 값이 t4 시점에도 여전히 최신인가"를 A가 알아야 한다. 그런데 look-aside에서 읽기 경로와 쓰기 경로는 **서로의 존재를 모르는 완전히 별개의 코드 경로**다. 같은 트랜잭션도 아니고, 같은 락도 공유하지 않는다.

공유하게 만들면 되지 않느냐고 물을 수 있다. 실제로 방법은 있다 — 키마다 버전 번호를 두고 적재 시점에 버전이 그대로인지 확인하거나(비교 후 교환), 읽기와 쓰기가 같은 분산 락을 잡게 하는 것이다. 그런데 **읽기 경로에 락을 거는 순간 캐시를 도입한 이유가 사라진다.** 캐시는 읽기를 빠르게 하려고 넣은 것인데, 모든 읽기가 락 획득을 기다려야 한다면 원래 목적과 정면으로 충돌한다. 버전 검사도 왕복과 복잡도를 늘린다. **이 창의 발생 확률은 매우 낮은데(미스 처리 중 정확히 그 키를 쓰는 요청이 끼어들어야 한다) 막는 비용은 상시로 발생하므로, 비용 대비 효과가 성립하지 않는다.**

그래서 실무의 답은 **"막지 않고, 낡음의 지속 시간을 유한하게 만든다"**가 된다. 그 장치가 **TTL**이다.

여기서 TTL의 성격이 새로 정의된다. **TTL은 메모리를 아끼는 성능 장치가 아니라, 정합성의 최후 안전망이다.** 어떤 경합으로 옛 값이 들어갔든, 어떤 삭제 호출이 유실됐든, **TTL이 지나면 그 값은 반드시 사라지고 다음 읽기가 DB의 진실을 다시 가져온다.** 그래서 TTL을 정할 때의 질문은 "메모리가 얼마나 여유 있나"가 아니라 **"이 데이터가 최악의 경우 얼마나 오래 낡아 있어도 되는가"**다.

같은 이유로 **무한 TTL(만료 없는 캐시)은 금물이다.** 무한 TTL은 이 창을 영구화한다 — 한 번 잘못 들어간 값이 영원히 서빙되고, 그 사실을 아무도 모른다.

### 3-4. 캐시 장애 = DB 직격

1-6에서 look-aside의 장점으로 꼽은 **"캐시가 죽어도 DB로 동작한다"**에는 반드시 조건이 붙는다. **DB가 그 트래픽을 버틸 때만 성립한다.**

숫자로 확인해 보자. 캐시 히트율이 90%라면 DB는 평소 읽기의 10%만 받고 있다. 캐시가 죽으면 그 10%가 100%가 되므로 **DB 부하는 10배**가 된다. 히트율이 99%였다면 100배다. **히트율이 높을수록 캐시 장애의 충격이 크다**는 역설이 여기 있다.

방어책은 넷이고, 각각 다른 지점을 막는다.

**캐시 클라이언트에 짧은 타임아웃을 건다.** Redis가 응답하지 않을 때 기본 타임아웃(수 초)을 기다리면, 그 대기가 애플리케이션 스레드를 붙잡아 **캐시 장애가 애플리케이션 응답 지연으로 전파된다.** 타임아웃을 수십~수백 ms로 짧게 잡아 즉시 포기하고 DB로 넘어가게 만드는 것이 **fail-fast(빨리 실패하기)**다.

**DB 앞에 서킷 브레이커를 둔다.** DB가 이미 밀리기 시작했다면 요청을 더 보내 봐야 전부 타임아웃이 되고 커넥션 풀만 고갈된다. 실패율이 임계치를 넘으면 **회로를 끊어 즉시 실패를 반환**해 DB에 회복할 틈을 준다.

**캐시를 단일 장애점으로 만들지 않는다.** 레플리카·Sentinel·클러스터 구성으로 노드 하나의 장애가 캐시 전체의 장애가 되지 않게 한다.

**용량 계획에서 히트율 전제를 검증한다.** 가장 근본적인 방어다. "캐시 히트율 90%를 전제로 DB를 잡았다"면 그 순간 **캐시는 성능 최적화 장치가 아니라 필수 구성 요소**가 된 것이고, 그렇다면 캐시의 가용성 요구 수준도 DB와 같아야 한다. 이 점검을 안 하면 **가용성을 높이려고 넣은 캐시가 실제로는 장애 지점을 하나 추가한 구조**가 된다.

## 4. 꼬리질문 대비 포인트

### "Read-through와 Look-aside의 차이는 무엇인가요?"

**원본을 다녀오는 코드의 위치**다.

Look-aside는 애플리케이션이 미스를 직접 확인하고 DB를 읽어 적재한다. Read-through는 캐시에 로더를 등록해 두면 미스 시 **캐시가 알아서** 원본을 읽어 채우고, 애플리케이션은 캐시만 바라본다.

기술 스택으로 연결하면 구체적이 된다. **Redis는 로더 개념이 없어 look-aside로 쓸 수밖에 없고**, Caffeine의 `CacheLoader`나 스프링 `@Cacheable`은 read-through 형태를 제공한다.

마지막에 차이의 의미까지 붙이면 좋다. 동작 결과는 비슷해도 **"적재 로직을 누가 소유하느냐"**가 다르고, look-aside는 그만큼 **제어권(키 설계·TTL·조건부 캐싱)이 애플리케이션에 있다.**

### "캐시(Redis)가 통째로 죽으면 서비스는 어떻게 되나요?"

**기능은 유지된다** — 모든 읽기가 미스 경로처럼 DB로 간다. 여기까지가 look-aside의 장점이다.

문제는 성능과 용량이다. 캐시가 흡수하던 읽기 트래픽을 DB가 그대로 맞으므로, 히트율 90%였다면 DB 부하가 10배가 된다. DB가 밀리기 시작하면 **캐시 장애가 전체 장애로 번진다.**

그래서 답은 셋이다. **첫째, 캐시 호출에 짧은 타임아웃**을 줘서 캐시 장애가 응답 지연으로 전파되지 않게 한다(fail-fast). **둘째, DB가 버틸 수 없는 구조라면 서킷 브레이커·요청 제한으로 DB를 보호**한다. **셋째, 애초에 "캐시 히트율 전제 없이 DB가 버티는가"를 용량 계획에서 따진다.**

**"캐시가 가용성을 높인 게 아니라 장애 지점을 추가한 구조인지"를 점검한다**고 말하면 상급이다. 캐시 없이는 못 버티는 시스템에서 캐시는 최적화가 아니라 의존성이기 때문이다.

### "인기 키가 만료되는 순간 동시 요청 1000개가 들어오면?"

**캐시 스탬피드**다. 1,000개가 전부 미스 → 전부 같은 DB 쿼리 → 전부 같은 값을 적재한다.

답변 순서가 중요하다. **원인 진단을 먼저 말한다** — "look-aside의 미스 처리에 '한 명만 다녀와라'라는 조정 장치가 없어서 생기는 구조적 문제"라고. 그다음 해법을 붙인다.

해법은 셋이다. **분산 락(또는 스프링 `sync = true`)으로 한 요청만 재계산하고 나머지는 대기**시키거나, **TTL에 지터를 섞어 대량 동시 만료 자체를 분산**하거나, **만료 전에 백그라운드에서 미리 갱신(refresh-ahead, soft TTL)**한다.

단, 지터는 **여러 키의 동시 만료**를 흩뜨리는 도구라서 **단일 인기 키 하나의 만료 폭주는 못 막는다**는 구분까지 말하면 도구의 적용 범위를 아는 것이 된다.

### "Look-aside에서 캐시와 DB가 달라지는 시나리오를 구체적으로 그려보세요" (시니어 변별 포인트)

**두 개를 그릴 수 있어야 한다.**

**① 읽기-쓰기 경합** (3-3의 타임라인). 읽기가 미스로 DB의 옛 값을 읽은 뒤, 아직 적재하기 전에 쓰기가 DB 갱신 + 캐시 삭제를 끝낸다. 삭제 시점에는 지울 것이 없으므로 삭제는 아무 일도 하지 않고, 그 뒤 읽기가 손에 들고 있던 옛 값을 적재한다. **누구도 실수하지 않았는데 옛 값이 최종 승자가 된다.**

**② 삭제 실패/유실.** DB 커밋은 성공했는데 캐시 삭제 호출이 실패하면(네트워크 순단, Redis 재시작, 타임아웃) 캐시에 옛 값이 그대로 남는다. 이쪽은 ①과 달리 **실패가 실제로 일어난** 경우다.

두 시나리오의 성격이 다르다는 점도 짚으면 좋다. **①은 정상 동작들의 인터리빙**이고 **②는 호출 실패**다. ②는 재시도나 삭제 이벤트 발행으로 확률을 더 낮출 수 있지만, ①은 앞서 본 대로 비용 없이는 막을 수 없다.

결론으로 묶는다. **"캐시-DB 정합성은 완전히 보장하는 것이 아니라 확률적으로 좁히는 것이고, TTL이 최후 안전망이다."** 그리고 이 두 타임라인을 그리는 능력 자체가 **분산 환경 타이밍 사고력의 증명**이다 — 동시성 문제는 "언제 무엇이 끼어들 수 있는가"를 시간축에 그려야만 보인다.

### "적재(SET)할 때 꼭 챙겨야 할 것은?"

**TTL이 첫 번째 답이다.** 무한 캐시는 무효화 유실이나 경합으로 들어간 옛 값이 **영원히 남는 구조**이므로, 아무리 짧더라도 만료를 준다. 정합성 안전망이면서 동시에 메모리 보호 장치다.

(가산점 포인트) 여기에 둘을 더 붙이면 실무 경험이 드러난다.

**null/부재 결과 처리.** 존재하지 않는 키를 캐시하지 않으면, 그 키를 반복 조회하는 요청이 매번 캐시를 그냥 지나쳐 DB를 때린다. 이것을 **캐시 관통(cache penetration)**이라고 부른다 — 캐시가 아무것도 막아 주지 못하고 요청이 관통해 버린다는 뜻이다. 대응은 **"없음"이라는 사실도 아주 짧은 TTL로 캐시하는 절충**이다. TTL을 짧게 두는 이유는, 그 사이 실제로 데이터가 생겼을 때 "없음"이 오래 남지 않게 하기 위해서다.

**직렬화 형식과 키 네이밍·버저닝.** 캐시에 넣는 객체 구조가 배포로 바뀌면, 이전 형식으로 직렬화된 값을 새 코드가 역직렬화하다 예외가 난다. 캐시 미스도 아니고 예외라서 요청이 그대로 실패한다. 그래서 키에 버전을 넣어(`product:v2:42`) **배포와 함께 키 공간을 갈아타는** 방식을 쓴다.

## 한 줄 요약

Look-aside는 애플리케이션이 캐시를 먼저 보고 미스면 DB에서 읽어 직접 적재하는(쓰기는 DB에 쓰고 캐시는 갱신이 아니라 삭제) 패턴으로, Redis에는 애초에 다른 선택지가 없고 캐시가 죽어도 서비스가 살며 무엇을 캐시할지 통제할 수 있어 실무 기본값이 되었지만 — 적재 책임이 앱에 있고 읽기와 쓰기가 서로를 모르는 구조라서 cold cache, 미스 폭주(스탬피드), 읽기가 든 옛 값이 쓰기의 삭제 뒤에 적재되는 경합, 캐시 장애 시 DB 직격이라는 빈틈이 내장되어 있고, 이 창들을 TTL이라는 최후 안전망과 워밍·락·타임아웃으로 어떻게 좁히는지까지 말해야 패턴을 "운영해 본" 답변이 된다.
