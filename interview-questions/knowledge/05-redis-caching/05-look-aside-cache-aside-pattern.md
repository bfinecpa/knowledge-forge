# Look-aside(Cache-aside) 패턴 — 애플리케이션이 캐시를 "옆에 두고" 직접 채우는 기본기와 그 빈틈

> 핵심 관전 포인트: **Look-aside는 애플리케이션이 ① 캐시를 먼저 조회하고
> ② 히트면 그대로 반환, ③ 미스면 DB에서 읽어 ④ 캐시에 적재한 뒤 반환하는
> 패턴이다. 캐시는 수동적인 저장소일 뿐, 적재 책임이 애플리케이션에
> 있다는 것이 핵심이다. 쓰기는 DB에 쓰고 캐시를 삭제하는 조합이 정석.
> 장점은 필요한 데이터만 게으르게(lazy) 적재되고 캐시가 죽어도 DB로
> 기능이 유지된다는 것 — 대신 이 패턴에는 미스 시 왕복 비용, 동시 미스
> 폭주(스탬피드), 읽기·쓰기 경합으로 옛 값이 적재되는 빈틈이 구조적으로
> 내장되어 있고, 이 빈틈들이 곧 캐싱 고난이도 질문 전체의 출발점이다.**

---

## 0. 질문 + 의도

**질문**: "Look-aside(Cache-aside) 패턴을 설명해주세요."

**출제 의도**: 기본 패턴의 흐름을 알아야 그 패턴의 빈틈(미스 폭주,
갱신 경합)을 논할 수 있다. 이후 고난이도 질문들(스탬피드, 정합성,
캐시 무력화 방어)의 공통 기반 — 흐름을 그릴 수 있는지와 함께, 그
흐름의 어느 지점에서 문제가 자라는지까지 짚는지를 본다.

## 1. 읽기 흐름 — "캐시를 먼저 보고, 없으면 내가 채운다"

이름 그대로 애플리케이션이 캐시를 **옆에(aside) 두고** 직접 들여다보는
구조다. 캐시와 DB는 서로를 모르고, 둘을 오가는 주체는 애플리케이션이다.

```
[읽기 요청]
    │
    ▼
① 캐시 조회 (GET product:42)
    │
    ├─ 히트 ──▶ ② 캐시 값 반환 (DB 안 감. 끝)
    │
    └─ 미스 ──▶ ③ DB 조회
                    │
                    ▼
                ④ 캐시에 적재 (SET product:42 <값> EX 300)
                    │
                    ▼
                ⑤ 값 반환
```

코드로 쓰면 이 정도가 뼈대다:

```java
public Product findProduct(Long id) {
    String key = "product:" + id;

    Product cached = redisTemplate.opsForValue().get(key);   // ① 캐시 먼저
    if (cached != null) {
        return cached;                                       // ② 히트 → 즉시 반환
    }

    Product product = productRepository.findById(id)         // ③ 미스 → DB
            .orElseThrow(ProductNotFoundException::new);

    redisTemplate.opsForValue()
            .set(key, product, Duration.ofMinutes(5));       // ④ 적재 (TTL 필수)
    return product;                                          // ⑤ 반환
}
```

핵심 특성 두 가지:

- **Lazy loading** — 실제로 조회된 데이터만 캐시에 들어간다. 안 읽히는
  데이터로 메모리를 낭비하지 않는다. (뒤집으면: 처음 읽는 요청과 만료
  직후 요청은 반드시 미스 비용을 낸다.)
- **적재 책임이 애플리케이션에** — 캐시는 get/set만 받는 수동적 저장소다.
  무엇을, 언제, 얼마 동안(TTL) 넣을지는 전부 애플리케이션 코드가 정한다.

스프링의 `@Cacheable`이 바로 이 look-aside 흐름을 프록시가 대신 해주는
선언적 구현이다 — "직접 짜면 이 코드, 애너테이션이면 프록시가 같은 일을
한다"고 연결하면 가산점 포인트.

## 2. 쓰기 흐름 — DB에 쓰고, 캐시는 삭제한다

Look-aside 자체는 읽기 패턴이라, 쓰기는 별도 결정이 필요하다. 정석 조합은
**DB에 먼저 쓰고(커밋), 캐시를 삭제(evict)** 하는 것이다.

```java
@Transactional
public void updatePrice(Long id, long newPrice) {
    productRepository.updatePrice(id, newPrice);   // ① DB 갱신 (트랜잭션)
}
// ② 커밋 후 캐시 삭제 — 다음 읽기가 미스를 내고 DB의 새 값을 적재
//    (커밋 "후"여야 하는 이유와 갱신 vs 삭제 논쟁은 07 문서에서 상세히)
```

삭제해 두면 다음 읽기가 자연스럽게 미스 → DB의 새 값 적재로 이어진다.
캐시를 새 값으로 직접 갱신(update)하는 선택지도 있지만 동시 쓰기 시
순서 역전 문제가 있어 삭제가 기본값이다 — 이 논쟁은 별도 문서
(`07-cache-db-consistency-update-vs-delete.md`)에서 다룬다.

## 3. 다른 패턴과의 비교 — 적재 책임이 어디 있는가

| 패턴 | 캐시 적재/동기화 주체 | 특징 |
|---|---|---|
| Look-aside | 애플리케이션 | 미스 시 앱이 DB 읽고 직접 적재 |
| Read-through | 캐시 계층 | 미스 시 캐시(라이브러리)가 원본을 읽어 채움 |
| Write-through | 캐시 계층 | 쓰기를 캐시에 하면 캐시가 DB까지 동기 반영 |
| Write-behind | 캐시 계층 | 캐시에 먼저 쓰고 DB 반영은 비동기(유실 위험) |

구분 축은 **"미스/쓰기 때 원본을 다녀오는 코드가 어디 있는가"** 다.
Look-aside는 그 코드가 애플리케이션에 있고, read/write-through는 캐시
계층(예: Caffeine의 CacheLoader, 스프링 캐시 추상화)에 숨어 있다.

Redis를 쓰는 실무에서 look-aside가 사실상 표준인 이유:

- Redis 자체는 DB를 모른다 — DB에서 읽어오는 기능이 없으니 누군가
  (애플리케이션)가 채워야 하고, 그게 곧 look-aside다.
- 캐시가 **선택적 최적화 계층**으로 남는다. 캐시가 통째로 죽어도
  모든 읽기가 DB로 가서 기능은 유지된다(성능 저하일 뿐 장애 아님 —
  단, DB가 그 트래픽을 버틸 때 이야기).
- 키 설계, TTL, 캐시할지 말지를 조회 경로별로 자유롭게 제어할 수 있다.

## 4. 이 패턴에 내장된 빈틈 — 고난이도 질문들의 출발점

Look-aside를 "설명할 줄 안다"와 "빈틈을 안다"의 차이가 변별점이다.

### ① 미스 비용과 cold cache

처음 읽히는 키와 만료 직후 키는 반드시 "캐시 조회(미스) + DB 조회 +
캐시 적재"라는 3-왕복을 낸다. 평소엔 문제가 아니지만, **배포/장애
복구 직후 캐시가 통째로 빈 상태(cold cache)** 로 트래픽을 받으면 전
요청이 미스가 되어 DB가 캐시 없던 시절의 트래픽을 그대로 맞는다.
캐시 히트를 전제로 DB 용량을 잡았다면 이 순간이 장애다 → 캐시 워밍
(예열)이 배포 절차에 들어가는 이유.

### ② 동시 미스 폭주 — 캐시 스탬피드

인기 키 하나가 만료되는 순간, 그 키를 읽던 동시 요청 수백 개가
**전부 미스를 보고 전부 DB로 몰려간다**(그리고 전부 같은 값을 적재).
look-aside의 미스 처리에 "한 명만 다녀와라"라는 조정 장치가 없기
때문에 생기는 문제다. 완화: 분산 락으로 한 요청만 재계산, TTL 지터
(만료 시각 분산), 만료 전 백그라운드 갱신(refresh-ahead), 스프링
`@Cacheable(sync = true)`.

### ③ 읽기·쓰기 경합 — 옛 값이 늦게 적재되는 창

미스 처리(③ DB 읽기 → ④ 캐시 적재) 사이에 쓰기가 끼어들면:

```
t=0  읽기 A: 캐시 미스 → DB에서 price=1000 읽음  (아직 적재 전)
t=1  쓰기 B: DB를 price=2000으로 갱신, 캐시 삭제  (지울 것도 없었음)
t=2  읽기 A: 아까 읽어둔 1000을 캐시에 적재       ← 옛 값이 최종 승자
     → TTL이 다할 때까지 캐시는 1000을 서빙
```

look-aside의 읽기와 쓰기는 서로를 모르는 별개 경로라 이런 인터리빙을
막을 수 없다. 그래서 **TTL은 성능 장치가 아니라 정합성의 최후 안전망**
이고, 무한 TTL(만료 없는 캐시)은 이 창이 영구화되므로 금물이다.

### ④ 캐시 장애 = DB 직격

"캐시가 죽어도 DB로 동작한다"는 장점은 DB가 전체 트래픽을 버틸 때만
성립한다. 캐시가 흡수하던 트래픽이 90%였다면 캐시 장애 순간 DB는
10배 트래픽을 맞는다. 캐시 클라이언트에 짧은 타임아웃 + 실패 시 즉시
DB로(fail-fast), DB 앞 서킷 브레이커, 캐시를 단일 장애점으로 만들지
않는 구성(replica/Sentinel)이 방어책이다.

## 5. 꼬리질문 대비 포인트

### "Read-through와 Look-aside의 차이는 무엇인가요?"

원본을 다녀오는 코드의 **위치**다. Look-aside는 애플리케이션이 미스를
보고 직접 DB를 읽어 적재하고, read-through는 캐시 계층에 로더를 등록해
두면 미스 시 캐시가 알아서 원본을 읽어 채운다(앱은 캐시만 바라봄).
Redis는 로더 개념이 없어 look-aside로 쓰고, Caffeine(CacheLoader)이나
스프링 `@Cacheable`은 read-through 형태를 제공한다 — 동작 결과는
비슷해도 "적재 로직을 누가 소유하느냐"가 다르고, look-aside는 그만큼
제어권(키·TTL·조건부 캐싱)이 앱에 있다.

### "캐시(Redis)가 통째로 죽으면 서비스는 어떻게 되나요?"

기능은 유지된다 — 모든 읽기가 미스 경로처럼 DB로 간다. 문제는 성능과
용량: 캐시가 흡수하던 읽기 트래픽을 DB가 그대로 맞아 DB가 밀리면
캐시 장애가 전체 장애로 번진다. 그래서 ① 캐시 호출에 짧은 타임아웃을
줘서 캐시 장애가 응답 지연으로 전파되지 않게 하고(fail-fast), ②
DB가 버틸 수 없는 구조라면 서킷 브레이커·요청 제한으로 DB를 보호하며,
③ 애초에 "캐시 히트율 전제 없이 DB가 버티는가"를 용량 계획에서
따져야 한다. "캐시가 가용성을 높인 게 아니라 장애 지점을 추가한
구조인지"를 점검한다고 말하면 상급.

### "인기 키가 만료되는 순간 동시 요청 1000개가 들어오면?"

캐시 스탬피드. 1000개가 전부 미스 → 전부 같은 DB 쿼리 → 전부 적재.
완화책: ① 분산 락(또는 스프링 `sync = true`)으로 한 요청만 재계산하고
나머지는 대기, ② TTL에 지터를 섞어 대량 동시 만료 자체를 분산, ③
만료 전에 백그라운드에서 미리 갱신(refresh-ahead, soft TTL). look-aside
의 미스 처리에 조정 장치가 없어서 생기는 문제라는 **원인 진단**을
먼저 말하고 해법을 붙이는 순서가 좋다.

### "Look-aside에서 캐시와 DB가 달라지는 시나리오를 구체적으로 그려보세요" (시니어 변별 포인트)

두 개를 그릴 수 있어야 한다. ① **읽기-쓰기 경합**: 읽기가 미스로 DB
옛 값을 읽은 뒤 적재하기 전에, 쓰기가 DB 갱신+캐시 삭제를 끝내면 —
읽기가 마지막에 옛 값을 적재해 TTL 동안 낡은 값이 서빙된다. ② **삭제
실패/유실**: DB 커밋은 됐는데 캐시 삭제 호출이 실패하면(네트워크,
Redis 순단) 옛 값이 남는다. 둘 다 확률은 낮지만 0이 아니므로, "캐시-DB
정합성은 확률적으로 좁히는 것이고 TTL이 최후 안전망"이라는 결론으로
묶는다. 이 두 시나리오를 타임라인으로 그리는 능력 자체가 분산 환경
타이밍 사고력의 증명이다.

### "적재(SET)할 때 꼭 챙겨야 할 것은?"

**TTL**. 무한 캐시는 무효화 유실·경합으로 들어간 옛 값이 영원히
남는 구조라, 아무리 짧아도 만료를 준다(정합성 안전망 + 메모리 보호).
추가로 ① null/부재 결과 처리 — 없는 키를 캐시 안 하면 반복 조회가
매번 DB 관통(cache penetration)하므로 짧은 TTL로 "없음"도 캐시하는
절충, ② 직렬화 형식과 키 네이밍/버저닝(배포로 구조 바뀔 때 역직렬화
실패 방지)까지 언급하면 실무 경험이 드러난다. (가산점 포인트)

## 한 줄 요약

Look-aside는 애플리케이션이 캐시를 먼저 보고 미스면 DB에서 읽어 직접
적재하는(쓰기는 DB 쓰고 캐시 삭제) 가장 기본적이고 유연한 캐싱 패턴
이지만 — 적재 책임이 앱에 있고 읽기·쓰기가 서로를 모르는 구조라서
cold cache, 미스 폭주(스탬피드), 옛 값 적재 경합, 캐시 장애 시 DB
직격이라는 빈틈이 내장되어 있고, 이 빈틈들을 TTL 안전망·락·워밍으로
어떻게 메우는지까지 말해야 패턴을 "운영해 본" 답변이 된다.
