# Sorted Set 실시간 랭킹 설계 — 기본 설계는 10분, 시간 윈도우와 규모 검증이 진짜 문제

> 핵심 관전 포인트: **Sorted Set은 (멤버, 점수) 쌍을 점수순 정렬 상태로
> 유지하는 자료구조라서, 조회 이벤트마다 ZINCRBY로 점수를 올리고
> ZREVRANGE로 TOP N을 꺼내면 랭킹이 된다 — 삽입/갱신 O(log N), 상위 M개
> 조회 O(log N + M). 그런데 "실시간 인기"는 누적이 아니라 **최근 N시간**
> 랭킹이므로 시간 버킷 키 분할 + ZUNIONSTORE 합산이 필요하고, 대규모에서는
> (1) 랭킹 키 하나가 결국 한 노드에 몰리는 hot key, (2) 수억 멤버 big key,
> (3) 조회 트래픽 = 쓰기 트래픽이 되는 ZINCRBY 폭주, (4) 클러스터의 멀티 키
> 제약이라는 한계에 부딪힌다. 도구 적용과 함께 규모 검증까지 말해야 한다.**

---

## 0. 질문 + 의도

**질문**: "랭킹(실시간 인기 웹툰) 기능을 Sorted Set으로 설계해보세요.
대규모에서의 한계는?"

**출제 의도**: 실시간 인기 웹툰은 이 회사의 실제 기능이다. Sorted Set으로
기본 설계를 하는 것은 출발점이고, "시간 윈도우는 어떻게 처리할지, 멤버가
수억이면 어떻게 되는지"의 한계 인식까지 가는지 — 도구를 적용하는 능력과
규모를 검증하는 습관을 함께 갖췄는지 본다.

## 1. Sorted Set이 랭킹에 맞는 이유 — 정렬을 "유지"하는 자료구조

Sorted Set은 **멤버(문자열)마다 점수(double)를 붙여 저장하고, 점수순
정렬 상태를 항상 유지**하는 자료구조다. 내부적으로 두 구조를 같이 쓴다:

- **해시테이블**: 멤버 → 점수를 O(1)로 찾는다 (ZSCORE).
- **스킵 리스트(skip list)**: 점수순 정렬을 유지한다. 정렬 리스트에
  "고속도로 층"을 여러 개 얹은 구조라고 생각하면 된다 — 삽입/삭제/순위
  조회가 전부 O(log N).

랭킹에 필요한 연산이 전부 명령어 하나씩으로 존재한다:

| 연산 | 명령 | 복잡도 |
|---|---|---|
| 점수 증가 | `ZINCRBY key 1 member` | O(log N) |
| 상위 M개 | `ZREVRANGE key 0 M-1 WITHSCORES` | O(log N + M) |
| 특정 멤버 순위 | `ZREVRANK key member` | O(log N) |
| 특정 멤버 점수 | `ZSCORE key member` | O(1) |

RDB로 같은 걸 하면 `ORDER BY view_count DESC LIMIT 10`인데, 조회수처럼
**초당 수천 번 갱신되는 컬럼에 인덱스를 걸면 갱신마다 인덱스 재정렬
비용**을 내고, 같은 인기 행에 UPDATE가 몰리면 락 경합까지 생긴다.
Sorted Set은 "자주 바뀌는 값의 정렬 조회"라는 이 문제를 구조 자체로
해결한다 — 이것이 "빠른 Map"을 넘어선 Redis의 표현력이다.

## 2. 기본 설계 — 이벤트 적재와 조회

웹툰 조회(또는 좋아요 등 가중치 이벤트)가 발생할 때 점수를 올리고,
랭킹 화면에서 상위 N개를 꺼낸다.

```java
// 조회 이벤트 발생 시 — 점수 +1
redisTemplate.opsForZSet().incrementScore("ranking:webtoon", webtoonId, 1);

// 랭킹 화면 — TOP 10 (점수 높은 순)
Set<TypedTuple<String>> top10 = redisTemplate.opsForZSet()
        .reverseRangeWithScores("ranking:webtoon", 0, 9);

// "이 웹툰은 현재 몇 위?" — 0-based라 +1
Long rank = redisTemplate.opsForZSet().reverseRank("ranking:webtoon", webtoonId);
```

여기서 멈추면 절반이다. 두 가지를 스스로 짚어야 한다:

**① 멤버에는 ID만 넣는다.** 제목·썸네일 같은 메타데이터를 멤버에
직렬화해 넣으면 제목 변경 시 다른 멤버가 되어 점수가 갈라진다. 랭킹은
ID 목록만 주고, 메타데이터는 별도 캐시/DB에서 ID로 조회해 조합한다.

**② 동점 처리.** 점수가 같으면 Redis는 **멤버 문자열의 사전순**으로
정렬한다. "먼저 도달한 쪽이 위" 같은 비즈니스 규칙이 필요하면 점수의
소수부에 타임스탬프를 역산해 심는 식의 합성 점수를 설계해야 한다
(double 정밀도 한계 — 53비트 정수까지만 정확 — 를 인지하고 있다고
언급하면 가산점 포인트).

## 3. "실시간 인기"의 진짜 문제 — 시간 윈도우

키 하나에 계속 ZINCRBY하면 그건 **역대 누적 랭킹**이다. 몇 달 전
메가히트작이 영원히 1위에 박제된다. "실시간 인기"는 보통 "최근
1시간/24시간" 같은 **움직이는 시간 창(sliding window)** 인데, Sorted Set에는
"점수에 유효기간"이라는 개념이 없다 — 그래서 키를 시간으로 쪼갠다.

### 시간 버킷 + ZUNIONSTORE 합산 (정석 패턴)

```java
// ① 쓰기: 현재 시간 버킷 키에 적재 (예: 시간 단위 버킷)
String bucket = "ranking:webtoon:" + now.format(yyyyMMddHH);  // ranking:webtoon:2026083114
zSet.incrementScore(bucket, webtoonId, 1);
redisTemplate.expire(bucket, Duration.ofHours(25));  // 윈도우 + 여유만큼만 보관

// ② 읽기: 최근 24개 버킷을 합산한 결과 키를 만들어 조회
List<String> last24 = recentBucketKeys(24);          // 최근 24시간 버킷 키 목록
zSet.unionAndStore("ranking:webtoon:2026083114", last24, "ranking:webtoon:merged");
redisTemplate.expire("ranking:webtoon:merged", Duration.ofMinutes(1));
```

핵심 판단 두 가지:

- **합산은 요청마다 하지 않는다.** ZUNIONSTORE는 O(N·K)급의 비싼
  연산이라, 스케줄러(예: 1분마다)가 merged 키를 미리 만들어 두고 조회는
  그 결과만 읽는다. 랭킹은 "1분 정도 낡아도 되는" 데이터라는 요구사항
  협상이 설계에 들어가는 지점이다.
- **버킷 크기 = 윈도우 정밀도와 키 개수의 트레이드오프.** 시간 버킷
  24개면 "최근 24시간"이 최대 1시간 단위로 어긋난다. 더 정밀하려면
  10분 버킷 144개 — 합산 비용이 커진다.

## 4. 대규모에서의 한계 — 이 질문의 승부처

### ① 랭킹 키는 클러스터로도 분산되지 않는다 (hot key)

Redis Cluster는 **키 단위**로 샤딩한다. `ranking:webtoon` 키 하나에
전 서비스의 조회 쓰기와 랭킹 읽기가 몰리면, 노드가 100대여도 그 키를
가진 **한 노드**가 전부 받는다. "클러스터를 쓰니까 확장된다"는 착각이
깨지는 대표 사례다. 읽기는 merged 결과를 로컬 캐시(TOP N은 몇 KB밖에
안 된다)로 내리는 게 효과적이고, 쓰기는 ③으로 푼다.

### ② 멤버 수억 개 = big key

웹툰 수만 개 랭킹이면 문제없지만, 이 설계를 그대로 "전체 유저 게임
점수 랭킹"(수억 멤버)에 옮기면 big key가 된다: 메모리 수십 GB가 한
노드에 몰리고, ZUNIONSTORE·ZRANGEBYSCORE 같은 O(N) 연산 한 방이 싱글
스레드 전체를 세우며, 삭제·마이그레이션도 블로킹 폭탄이 된다.
대응은 랭킹의 요구사항을 되묻는 것: **TOP 1000만 정확하면 되는가?**
그렇다면 주기적으로 `ZREMRANGEBYRANK`로 하위를 잘라 크기를 상수로
유지한다. "내 순위"까지 수억 명에게 정확히 줘야 한다면 점수 구간별
카운트(히스토그램)로 근사 순위를 주는 절충이 현실적이다.

### ③ 조회 트래픽 = 쓰기 트래픽이 된다

조회 이벤트마다 ZINCRBY를 치면 **페이지뷰 QPS가 그대로 Redis 쓰기
QPS**다. O(log N)이라도 초당 수십만 건이면 한 노드가 못 버틴다.
해법은 집계의 지연을 허용하는 것:

```java
// ❌ 이벤트마다 Redis 왕복
public void onView(long webtoonId) {
    zSet.incrementScore(bucket(), String.valueOf(webtoonId), 1);
}

// ✅ 애플리케이션 로컬에서 모았다가 주기 플러시 (횟수를 묶어서 반영)
private final ConcurrentHashMap<Long, LongAdder> buffer = new ConcurrentHashMap<>();

public void onView(long webtoonId) {
    buffer.computeIfAbsent(webtoonId, k -> new LongAdder()).increment();
}

@Scheduled(fixedDelay = 5_000)  // 5초마다 — 쓰기 QPS가 1/수백로 줄어든다
public void flush() {
    // 스냅샷 떠서 pipeline으로 ZINCRBY 일괄 반영
}
```

랭킹이 5초 늦는 대신 쓰기 부하가 수백분의 1이 된다 — "정확·즉시"를
"근사·지연 허용"으로 협상해 비용을 낮추는 전형적 설계 판단이다.
(Kafka로 이벤트를 버퍼링해 컨슈머가 집계 반영하는 구조도 같은 원리.)

### ④ 클러스터의 멀티 키 제약

ZUNIONSTORE는 여러 키를 다루므로 Cluster에서는 **모든 키가 같은 해시
슬롯**에 있어야 한다. 시간 버킷 키들에 해시태그(`ranking:{webtoon}:2026083114`
— `{}` 안만 해싱)를 써서 같은 슬롯에 모으는데, 이는 곧 "그 슬롯의 한
노드에 랭킹 부하 전부가 몰린다"는 ①의 문제를 다시 부른다. 인프라 확장
방식이 키 설계를 역으로 규정하는 사례다.

## 5. 꼬리질문 대비 포인트

### "점수가 같은 웹툰끼리의 순서는 어떻게 되나요?"

멤버 문자열의 **사전순(바이너리 비교)** 이다. `"10"`이 `"9"`보다 앞에
오는 식이라 ID 크기순도 아니다. 비즈니스 규칙(선점순 등)이 필요하면
점수를 합성한다 — 예: 정수부는 조회수, 소수부는 `1 - (timestamp/최댓값)`
처럼 먼저 도달할수록 큰 값. 이때 double은 53비트를 넘는 정수를 정확히
표현하지 못하므로 합성 점수의 자릿수 설계에 한계가 있다는 것까지
말하면 정확하다.

### "최근 1시간 랭킹인데 10분 전 조회까지만 반영하고 싶다면?"

버킷 정밀도의 문제다. 1시간 윈도우를 10분 단위로 움직이려면 10분
버킷 6개를 합산한다. 정밀도를 올릴수록 버킷 수·합산 비용·키 관리
비용이 늘므로, "윈도우가 얼마나 부드럽게 움직여야 하는가"를 제품
요구사항과 협상해서 버킷 크기를 정한다고 답하면 된다.

### "'내 웹툰은 지금 몇 위' 조회는 비싸지 않나요?"

ZREVRANK 자체는 O(log N)이라 조회 연산은 싸다. 문제는 그걸 위해
**전체 멤버를 다 들고 있어야 한다**는 것 — 멤버가 수억이면 ②의 big
key 문제로 돌아간다. TOP N만 유지하는 잘린 랭킹에서는 순위권 밖
멤버의 순위를 줄 수 없으므로, "순위권 밖" 표시로 타협하거나 점수
히스토그램 근사를 쓴다.

### "DB에도 어차피 조회수를 저장할 텐데, 랭킹도 DB로 하면 안 되나요?"

`ORDER BY view_count DESC LIMIT 10`은 실행할 수는 있지만, (1) 조회수
컬럼 인덱스는 초당 수천 갱신마다 재정렬 비용을 내고, (2) 인기 행에
UPDATE가 몰려 락 경합이 생기며, (3) 시간 윈도우 랭킹은 이벤트 로그
테이블의 GROUP BY 집계가 되어 훨씬 비싸진다. 반대로 Redis 랭킹은
재시작 시 유실될 수 있으므로, **정산·통계용 정확한 수치는 DB(이벤트
적재)가 원본이고 Redis는 화면용 실시간 근사**라는 역할 분리로 답하는
것이 정석이다.

### "이 설계를 그대로 두고 트래픽이 100배가 되면 어디가 먼저 무너지나요?" (시니어 변별 포인트)

순서대로: **쓰기 경로가 먼저** 무너진다 — 조회 QPS와 같은 ZINCRBY가
랭킹 키를 가진 단일 노드에 몰린다(hot key + 쓰기 폭주). 그다음이
스케줄러의 ZUNIONSTORE 합산 비용, 마지막이 메모리다. 그래서 방어도
같은 순서로: 로컬 버퍼링/파이프라인으로 쓰기를 묶고, 읽기는 merged
TOP N을 애플리케이션 로컬 캐시로 내리고, 하위 랭크를 잘라 크기를
상수로 유지한다. "어디가 병목인지의 순서"를 짚는 것 자체가 규모
검증 습관의 증거다.

## 한 줄 요약

Sorted Set은 ZINCRBY/ZREVRANGE 만으로 O(log N) 랭킹을 주는 최적의
도구지만, "실시간 인기"에는 시간 버킷 + ZUNIONSTORE 합산이라는 윈도우
설계가 추가로 필요하고, 대규모에서는 랭킹 키 하나가 클러스터로도
분산되지 않는 hot key·수억 멤버 big key·조회 트래픽과 같아지는 쓰기
QPS·멀티 키 제약이라는 한계가 있어 — 쓰기 버퍼링, TOP N 잘라내기,
결과 로컬 캐시, "정확·즉시를 근사·지연으로 협상"까지 붙여야 규모를
견디는 설계가 된다.
