# Sorted Set 실시간 랭킹 설계 — 기본 설계는 10분, 시간 윈도우와 규모 검증이 진짜 문제

> 핵심 관전 포인트: **Sorted Set은 (멤버, 점수) 쌍을 항상 점수순 정렬 상태로 유지해 주는 자료구조다. 그래서 조회가 일어날 때마다 `ZINCRBY`로 점수를 1 올리고 화면에서는 `ZREVRANGE`로 위에서부터 M개를 꺼내면, 정렬 코드를 한 줄도 쓰지 않고 랭킹이 완성된다 — 갱신 O(log N), 상위 M개 조회 O(log N + M). 여기까지가 출발점이다. 진짜 문제는 그다음부터인데, 첫째로 "실시간 인기"는 누적 점수가 아니라 최근 N시간의 점수이므로 키를 시간 단위로 쪼개 쌓고 조회 시 최근 버킷들을 `ZUNIONSTORE`로 합산하는 윈도우 설계가 따로 필요하다. 둘째로 규모가 커지면 구조 자체에서 한계가 나온다 — 랭킹 키는 하나뿐이라 Redis Cluster를 써도 그 키를 가진 한 노드에만 부하가 몰리고(hot key), 여기에 "조회 이벤트마다 쓰기"라는 구조가 겹쳐 읽기 트래픽이 그대로 쓰기 트래픽으로 바뀌어 그 한 노드를 때린다. 멤버가 수억이면 big key가 되어 O(N) 명령 한 방이 싱글 스레드를 세우고, `ZUNIONSTORE`는 멀티 키 명령이라 Cluster에서 같은 슬롯 제약까지 붙는다. 도구를 적용하는 답이 아니라 이 규모 한계를 스스로 짚는 답을 해야 한다.**

---

## 0. 질문 + 의도

**질문**: "랭킹(실시간 인기 웹툰) 기능을 Sorted Set으로 설계해보세요. 대규모에서의 한계는?"

**출제 의도**: 실시간 인기 웹툰은 이 회사의 실제 기능이다. Sorted Set으로 기본 설계를 하는 것은 출발점이고, "시간 윈도우는 어떻게 처리할지, 멤버가 수억이면 어떻게 되는지"의 한계 인식까지 가는지 — 도구를 적용하는 능력과 규모를 검증하는 습관을 함께 갖췄는지 본다.

## 1. Sorted Set이 랭킹에 맞는 이유와 기본 설계

### 1-1. 전제 — 랭킹은 "자주 바뀌는 값을 정렬해서 읽는" 문제다

랭킹이라는 요구를 데이터 관점으로 번역하면 두 가지 동작의 조합이다.

- **쓰기**: 조회수·좋아요 같은 값이 초당 수천 번 바뀐다.
- **읽기**: 그 값 기준으로 정렬해서 위에서부터 10개를 뽑는다.

RDB로 하면 `ORDER BY view_count DESC LIMIT 10`이다. 실행 자체는 된다. 문제는 이 두 동작이 RDB에서 서로를 방해한다는 점이다.

정렬 조회를 빠르게 하려면 `view_count`에 인덱스를 걸어야 하는데, 인덱스는 **정렬된 자료구조(B-tree)** 라서 값이 바뀔 때마다 그 자리에서 빠져나와 새 자리에 다시 들어가야 한다. 조회수는 초당 수천 번 바뀌는 컬럼이므로 갱신마다 이 재배치 비용을 낸다. PostgreSQL이라면 UPDATE가 새 튜플 버전을 만들고 인덱스 엔트리도 새로 다는 방식이라 부담이 더 직접적이다.

게다가 인기 있는 행일수록 UPDATE가 그 한 행에 몰린다. 같은 행을 동시에 갱신하려는 트랜잭션들은 행 잠금을 두고 줄을 서므로, **인기가 많을수록 갱신이 느려지는** 역설이 생긴다.

즉 랭킹은 "쓰기가 잦은 값을 정렬해서 읽어야 한다"는, RDB의 인덱스 구조와 상성이 나쁜 요구다. Sorted Set은 정확히 이 조합을 위한 자료구조다.

### 1-2. Sorted Set의 내부 — 해시테이블 + 스킵 리스트

Sorted Set은 **멤버(문자열)마다 점수(double)를 붙여 저장하고, 점수순 정렬 상태를 항상 유지**하는 자료구조다. "정렬해서 읽는" 것이 아니라 "정렬된 상태를 유지한 채로 쓰는" 쪽이라는 점이 핵심이다.

이걸 가능하게 하려고 Redis는 내부에서 두 자료구조를 같이 들고 있다.

- **해시테이블**: 멤버 → 점수를 O(1)로 찾는다. "이 웹툰의 현재 점수가 몇인가"를 즉시 답할 수 있는 이유다.
- **스킵 리스트(skip list)**: 점수순 정렬을 유지한다. 정렬된 연결 리스트에 "고속도로 층"을 여러 개 얹은 구조라고 생각하면 된다 — 아래층은 모든 노드를 하나씩 잇고, 위층으로 갈수록 노드를 건너뛰며 이어서, 위층으로 크게 이동한 뒤 아래층으로 내려와 정밀하게 찾는다. 그래서 삽입·삭제·순위 조회가 전부 O(log N)이다.

같은 데이터를 두 벌로 들고 있으니 메모리는 더 쓴다. 그 대가로 "점수로 찾기"와 "순위로 찾기"가 둘 다 빠르다. 이 메모리 오버헤드는 나중에 3-2의 big key 문제로 되돌아온다.

### 1-3. 랭킹에 필요한 명령이 전부 하나씩 있다

랭킹을 만드는 데 필요한 연산이 명령어 하나씩으로 이미 존재한다. 각 명령이 무슨 일을 하는지부터 보자.

- **`ZINCRBY key increment member`** — 멤버의 점수를 주어진 만큼 올린다. 중요한 성질이 하나 있는데, **그 멤버가 아직 없으면 점수 0에서 시작해 만들어 준다.** 그래서 "이 웹툰이 오늘 처음 조회된 건가?"를 확인하는 분기가 애플리케이션 코드에 필요 없다. 첫 조회든 백만 번째 조회든 같은 한 줄이다.
- **`ZREVRANGE key start stop [WITHSCORES]`** — 점수가 **높은 순**으로 start번째부터 stop번째까지 꺼낸다. 0-based이므로 `0 9`가 TOP 10이다. `REV`가 붙은 이유는 기본형인 `ZRANGE`가 점수 낮은 순이기 때문이다. 랭킹은 높은 순이니 `ZREVRANGE`를 쓴다. `WITHSCORES`를 붙이면 점수까지 함께 돌려준다.
- **`ZREVRANK key member`** — 그 멤버가 점수 높은 순으로 몇 번째인지 돌려준다. 역시 0-based라 화면에 "3위"로 보이려면 +1 해야 한다.
- **`ZSCORE key member`** — 그 멤버의 현재 점수를 돌려준다.

복잡도까지 정리하면 이렇다.

| 연산 | 명령 | 복잡도 |
|---|---|---|
| 점수 증가 | `ZINCRBY key 1 member` | O(log N) |
| 상위 M개 | `ZREVRANGE key 0 M-1 WITHSCORES` | O(log N + M) |
| 특정 멤버 순위 | `ZREVRANK key member` | O(log N) |
| 특정 멤버 점수 | `ZSCORE key member` | O(1) |

여기서 N은 그 Sorted Set에 들어 있는 전체 멤버 수, M은 꺼내오는 개수다. TOP 10을 꺼내는 비용이 전체 멤버 수에 거의 영향받지 않는다는 것 — 멤버가 100만 개든 1000만 개든 log 차이뿐이라는 것 — 이 랭킹 용도에서 결정적이다.

RDB의 인덱스와 비교하면 결국 이런 그림이다. RDB는 "값 갱신"과 "정렬 유지"를 따로 관리하는 두 개의 일(테이블 UPDATE + 인덱스 재배치)로 처리하고 그 사이에 락 경합이 끼어들지만, Sorted Set은 **갱신이 곧 정렬 유지**인 단일 연산이고 Redis는 싱글 스레드라 애초에 경합이라는 개념이 없다. "빠른 Map"을 넘어선 Redis의 표현력이란 이런 것이다.

### 1-4. 기본 설계 — 이벤트 적재와 조회

웹툰 조회(또는 좋아요 등 가중치 이벤트)가 발생할 때 점수를 올리고, 랭킹 화면에서 상위 N개를 꺼낸다.

```java
// 조회 이벤트 발생 시 — 점수 +1
// incrementScore는 ZINCRBY다. 해당 웹툰이 키에 없으면 0에서 시작해
// 자동으로 만들어 주므로 "처음 조회된 웹툰인가" 분기가 필요 없다.
redisTemplate.opsForZSet().incrementScore("ranking:webtoon", webtoonId, 1);

// 랭킹 화면 — TOP 10 (점수 높은 순)
// reverseRangeWithScores는 ZREVRANGE ... WITHSCORES다.
// 0..9는 0-based 구간이라 1위부터 10위까지를 뜻한다.
Set<TypedTuple<String>> top10 = redisTemplate.opsForZSet()
        .reverseRangeWithScores("ranking:webtoon", 0, 9);

// "이 웹툰은 현재 몇 위?" — ZREVRANK. 0-based라 화면 표기는 +1
Long rank = redisTemplate.opsForZSet().reverseRank("ranking:webtoon", webtoonId);
```

여기서 멈추면 절반이다. 면접에서 시키지 않아도 두 가지를 스스로 짚어야 한다.

### 1-5. 멤버에는 ID만 넣는다

**멤버 문자열은 곧 그 항목의 정체성**이다. Sorted Set은 멤버 문자열이 같으면 같은 항목으로, 한 글자라도 다르면 다른 항목으로 취급한다.

그래서 제목·썸네일 같은 메타데이터를 멤버에 직렬화해 넣으면 사고가 난다. 제목을 수정하는 순간 멤버 문자열이 달라지므로 Redis는 그것을 **새로운 웹툰**으로 인식한다. 그때까지 쌓인 점수는 옛 멤버에 남아 있고 새 멤버는 0점부터 다시 시작한다. 랭킹에 같은 웹툰이 두 줄로 나오거나, 1위였던 작품이 제목 오타 수정 한 번에 순위권 밖으로 사라진다.

그래서 랭킹은 **ID 목록만** 주는 역할로 한정하고, 제목·썸네일 같은 메타데이터는 별도 캐시나 DB에서 그 ID로 조회해 조합한다. 랭킹 키에는 변하지 않는 식별자만 넣는다는 원칙이다.

### 1-6. 동점 처리와 "점수는 double"이라는 사실

점수가 같은 멤버가 여럿이면 순서는 어떻게 되는가. Redis는 **멤버 문자열의 사전순(바이너리 비교)** 으로 정렬한다. 숫자 크기순이 아니라 문자열 비교라서 `"10"`이 `"9"`보다 앞에 온다.

"먼저 도달한 쪽이 위" 같은 비즈니스 규칙이 필요하면 점수 하나에 두 정보를 실어야 한다. 흔한 기법이 **합성 점수**다 — 정수부에는 조회수를, 소수부에는 타임스탬프를 역산해(먼저일수록 큰 값이 되도록) 심어서, 조회수가 같으면 소수부가 승부를 가르게 만든다.

그런데 여기서 반드시 짚어야 할 사실이 있다. **Sorted Set의 점수는 정수가 아니라 배정도 부동소수점(double)이다.**

double은 값을 부호·지수·가수(significand)로 나눠 저장하는데, 정수를 정확히 표현할 수 있는 범위가 가수 비트 수에 묶인다. 배정도의 가수는 53비트(저장되는 52비트 + 항상 1인 앞자리 1비트)라서, **절댓값이 2^53 = 9007199254740992 이하인 정수까지만 정확히 표현된다.**

그 위로 넘어가면 어떤 일이 생기는지가 중요하다. 표현 가능한 값들의 간격이 1보다 커지므로, **1을 더해도 값이 그대로인 구간**이 생긴다.

```text
9007199254740992     (= 2^53)  까지는 정수가 정확히 표현된다
9007199254740992 + 1 을 double로 계산하면?
  -> 9007199254740992   (변하지 않는다. 이 구간의 표현 간격이 2이기 때문)
```

즉 점수가 2^53을 넘어선 뒤로는 `ZINCRBY key 1 member`를 아무리 호출해도 점수가 오르지 않는다. 조회수 카운터로 쓸 때 900경이라는 값에 현실적으로 도달할 일은 없지만, **"점수는 정수가 아니라 double이다"라는 사실 자체는 두 군데에서 실제로 문제가 된다.**

첫째, 위에서 말한 합성 점수다. 정수부에 조회수, 소수부에 타임스탬프를 심으려면 두 정보를 합쳐 53비트 안에 들어가야 한다. 소수부에 자릿수를 많이 할당할수록 정수부(조회수)가 정확히 표현되는 상한이 내려간다. 자릿수 예산을 나눠 쓰는 설계라는 것을 알고 있어야 한다.

둘째, 금액이나 정밀한 소수를 점수로 쓰는 경우다. 0.1 같은 값은 이진 부동소수점으로 정확히 표현되지 않으므로 더하다 보면 오차가 누적된다. 돈을 다루는 랭킹이라면 점수는 원 단위 정수로 환산해 넣는 편이 안전하다.

면접에서는 "double이라 53비트 정수까지만 정확하다"까지 말하면 가산점 포인트다.

## 2. "실시간 인기"의 진짜 문제 — 시간 윈도우

### 2-1. 누적 점수로 랭킹을 만들면 새 작품이 영원히 못 올라온다

1절의 설계에는 아직 시간이라는 축이 없다. 키 하나에 계속 `ZINCRBY`하면 그건 **서비스 개시 이래의 역대 누적 랭킹**이다.

이게 왜 문제인지 숫자로 보면 분명하다. 3년 전 메가히트작 A가 그동안 누적 조회수 5,000만을 쌓아뒀다고 하자. 오늘 공개된 신작 B가 하루 만에 10만 조회를 기록해 화제가 됐다. 그런데 랭킹은 이렇다.

```text
1위  A (누적 5,000만)   ← 3년 전 작품. 요즘은 하루 100회 조회.
...
어딘가  B (누적 10만)    ← 오늘 폭발한 신작. 하루 10만 조회.
```

B가 A를 따라잡으려면 하루 10만 조회를 500일 유지해야 한다. 즉 **누적 랭킹에서 1위는 사실상 영구 지정석**이고, "지금 뜨는 작품"은 절대 보이지 않는다. 사용자가 실시간 인기 랭킹에서 보고 싶은 것과 정반대의 결과다.

문제의 본질은 이렇다. `ZINCRBY`로 올린 점수는 **한 번 올라가면 절대 내려오지 않는다.** 그런데 "실시간 인기"라는 요구는 오래된 점수가 시간이 지나면 랭킹에서 빠지기를 기대한다. 보통 "최근 1시간", "최근 24시간" 같은 **움직이는 시간 창(sliding window)** 이다.

Sorted Set에는 "이 점수는 1시간 뒤 만료" 같은 개념이 없다. TTL은 **키 전체**에만 걸 수 있지 멤버별·점수 증분별로는 걸 수 없다. 그래서 우회한다 — **점수에 유효기간을 걸 수 없다면, 키를 시간으로 쪼개서 키 자체에 TTL을 건다.**

### 2-2. 시간 버킷 — 키가 생기고 사라지는 타임라인

**시간 버킷**은 "이 시간대의 점수만 담는 통"이다. 키 이름에 시각을 박아서 시간대마다 다른 키를 쓰고, 각 키에 윈도우 길이만큼의 TTL을 건다. 그러면 오래된 시간대의 점수는 애플리케이션이 지울 필요 없이 **키째로 자연 소멸**한다.

시간이 흐르면서 키가 어떻게 생기고 사라지는지가 이 패턴의 전부다.

```text
[윈도우 = 최근 24시간, 버킷 = 1시간 단위, TTL = 25시간]

시각 14:37 — 이 순간의 키 공간
   ranking:webtoon:2026090114   <- 지금 ZINCRBY가 들어가는 버킷 (쓰기 대상)
   ranking:webtoon:2026090113   TTL 남음
   ranking:webtoon:2026090112   TTL 남음
   ...
   ranking:webtoon:2026083115   TTL 남음 (23시간 전)
   ranking:webtoon:2026083114   TTL 곧 만료
                                <- 그 이전 버킷들은 이미 사라짐

시각 15:00 — 시간이 넘어가는 순간
   ranking:webtoon:2026090115   <- 새 버킷이 첫 ZINCRBY 때 자동 생성
   ranking:webtoon:2026090114   쓰기가 멈추고 읽기 전용이 됨
   ranking:webtoon:2026083114   TTL 만료 -> 윈도우 밖으로 빠짐

조회 시 —
   최근 24개 버킷 키를 계산해서 그것들의 점수를 합산한다
   14:37이면 2026083115 ~ 2026090114 의 24개
```

여기서 눈여겨볼 것이 셋이다.

**애플리케이션은 아무것도 지우지 않는다.** 윈도우에서 빠지는 일은 Redis의 TTL이 알아서 한다. "오래된 점수 감산" 같은 배치가 없다.

**쓰기는 항상 현재 버킷 하나에만 들어간다.** 지금 시각으로 키 이름을 만들어 `ZINCRBY`하면 끝이다. 새 버킷이 처음 생길 때도 `ZINCRBY`가 알아서 만들어 주므로(1-3) 초기화 코드가 필요 없다.

**TTL은 윈도우보다 넉넉히 잡는다.** 24시간 윈도우에 TTL을 정확히 24시간으로 걸면, 합산하려는 순간 가장 오래된 버킷이 방금 만료돼 사라져 있을 수 있다. 여유를 둬서 25시간으로 건다.

### 2-3. ZUNIONSTORE로 버킷들을 합산한다

조회할 때는 최근 24개 버킷의 점수를 웹툰별로 더해야 한다. 이걸 하는 명령이 **`ZUNIONSTORE`** 다.

`ZUNIONSTORE 결과키 키개수 키1 키2 ...` 형태로 쓴다. 여러 Sorted Set의 **합집합**을 구하되, **같은 멤버가 여러 키에 들어 있으면 점수를 더해서** 결과 키에 저장한다. 랭킹 합산에 필요한 동작이 바로 이 "같은 멤버면 점수 합산"이다.

```text
ranking:webtoon:2026090112  { 웹툰A: 300, 웹툰B: 120 }
ranking:webtoon:2026090113  { 웹툰A: 500, 웹툰C:  80 }
ranking:webtoon:2026090114  { 웹툰B: 200 }

  ZUNIONSTORE ranking:webtoon:merged 3 (위 세 키)

ranking:webtoon:merged      { 웹툰A: 800, 웹툰B: 320, 웹툰C: 80 }
                              300+500      120+200      80
```

이름 끝의 `STORE`가 말해 주듯 결과를 돌려주는 게 아니라 **새 키에 저장**한다. 이 성질이 뒤에서 중요해진다 — 저장해 두면 여러 요청이 그 결과를 재사용할 수 있다.

코드로 옮기면 이렇다.

```java
// ① 쓰기: 현재 시간 버킷 키에 적재 (시간 단위 버킷)
String bucket = "ranking:webtoon:" + now.format(yyyyMMddHH);  // ranking:webtoon:2026090114
zSet.incrementScore(bucket, webtoonId, 1);
// TTL은 윈도우(24h)보다 넉넉히. 합산 직전에 가장 오래된 버킷이
// 만료돼 사라지는 것을 막기 위한 여유분이다.
redisTemplate.expire(bucket, Duration.ofHours(25));

// ② 읽기: 최근 24개 버킷을 합산한 결과 키를 만들어 조회
List<String> last24 = recentBucketKeys(24);          // 최근 24시간 버킷 키 목록
// unionAndStore는 ZUNIONSTORE. 같은 웹툰이 여러 버킷에 있으면
// 점수를 더해서 merged 키에 저장한다.
zSet.unionAndStore("ranking:webtoon:2026090114", last24, "ranking:webtoon:merged");
// merged는 파생 데이터라 오래 두면 낡은 랭킹이 된다. 짧은 TTL로 안전장치를 건다.
redisTemplate.expire("ranking:webtoon:merged", Duration.ofMinutes(1));
```

### 2-4. 합산은 요청마다 하지 않는다

`ZUNIONSTORE`의 시간 복잡도는 **O(N) + O(M log M)** 이다. N은 입력 키들에 든 멤버 수의 총합, M은 결과에 남는 멤버 수다. 앞의 O(N)은 모든 입력을 한 번씩 훑는 비용이고, 뒤의 O(M log M)은 합산 결과를 정렬된 자료구조로 만드는 비용이다.

웹툰 2만 개에 24개 버킷이면 최악의 경우 입력 멤버가 48만 개다. 이걸 랭킹 화면 요청마다 실행하면, **Redis는 싱글 스레드라서** 그 계산이 도는 동안 다른 모든 명령이 줄을 선다. 랭킹 페이지 조회 1,000 QPS에 이 명령이 그대로 붙는 구조는 성립하지 않는다.

그래서 **스케줄러가 주기적으로(예: 1분마다) merged 키를 미리 만들어 두고, 조회는 그 결과 키에 `ZREVRANGE`만 친다.** `ZUNIONSTORE`가 결과를 키에 저장하는 명령인 덕에 가능한 구조다.

이 결정은 사실 기술 결정이 아니라 **요구사항 협상**이다. 1분마다 갱신한다는 것은 "랭킹이 최대 1분 낡을 수 있다"는 뜻이다. 실시간 인기 랭킹이 60초 낡아도 되는지를 기획과 합의하고 나서야 이 설계가 성립한다. 랭킹처럼 "근사해도 되는" 데이터에서 정확도를 조금 내주고 비용을 크게 줄이는 협상이 설계의 일부라는 것을 보여주는 지점이다.

### 2-5. 버킷 크기는 정밀도와 비용의 트레이드오프

버킷을 1시간 단위로 잡으면 윈도우가 1시간씩 뚝뚝 움직인다. 14:59에 보던 "최근 24시간"과 15:00에 보는 "최근 24시간"이 한 시간치만큼 달라진다는 뜻이다.

더 부드럽게 움직이게 하려면 버킷을 잘게 쪼갠다. 10분 버킷이면 24시간 윈도우가 버킷 144개다. 정밀도는 6배 좋아지지만 대가가 따라온다.

- 합산 대상 키가 24개에서 144개로 늘어 `ZUNIONSTORE` 비용이 커진다.
- 관리해야 할 키 개수와 메모리도 늘어난다(같은 웹툰이 144개 버킷에 나뉘어 들어간다).

그래서 "윈도우가 얼마나 부드럽게 움직여야 하는가"를 제품 요구사항과 맞춰서 버킷 크기를 정한다. 정답이 있는 문제가 아니라 협상 결과다.

## 3. 대규모에서의 한계 — 이 질문의 승부처

지금까지의 설계는 웹툰 수만 개, 조회 수천 QPS 규모에서는 잘 돈다. 여기서부터는 그 설계를 100배 규모에 놓았을 때 어디가 먼저 무너지는지의 이야기다.

### 3-1. 랭킹 키 하나는 클러스터로도 분산되지 않는다 (hot key)

**Redis Cluster는 키 단위로 샤딩한다.** 키 이름을 해싱해 16384개의 해시 슬롯 중 하나에 배정하고, 각 노드가 슬롯 범위를 나눠 맡는다. 즉 **하나의 키는 통째로 한 노드에 산다. 키를 쪼개서 여러 노드에 나눠 담는 기능은 없다.**

그런데 랭킹 키는 `ranking:webtoon` 하나뿐이다. 전 서비스의 조회 쓰기와 랭킹 읽기가 이 키 하나로 수렴한다. 노드를 100대로 늘려도 **그 키를 가진 한 노드가 전부 받는다.** 나머지 99대는 이 트래픽에 아무 도움이 안 된다.

이렇게 특정 키 하나에 트래픽이 몰려 그 키가 사는 노드가 병목이 되는 현상을 **hot key**라고 부른다. "클러스터를 쓰니까 확장된다"는 착각이 깨지는 대표 사례이고, 샤딩의 단위가 키라는 사실을 이해하고 있는지가 그대로 드러나는 지점이다.

**읽기 쪽 완화책**은 merged 결과를 애플리케이션 로컬 캐시로 내리는 것이다. TOP N은 ID와 점수 몇십 개뿐이라 몇 KB밖에 안 된다. 애플리케이션 서버 각자가 이걸 몇 초간 들고 있으면 랭킹 읽기 QPS가 Redis에 거의 도달하지 않는다. 대가는 지연이다 — Redis의 merged가 1분마다 갱신되고 로컬 캐시가 5초를 더 얹으면 사용자가 보는 랭킹은 최대 1분 5초 낡는다.

**쓰기 쪽**은 3-3에서 다룬다. 그쪽이 hot key의 진짜 원인이다.

### 3-2. 멤버 수억 개는 big key가 된다

웹툰은 많아야 수만 개라 이 설계로 충분하다. 문제는 같은 설계를 그대로 "전체 유저 게임 점수 랭킹"에 옮겼을 때다. 멤버가 수억 개가 된다.

**big key**는 하나의 키가 담고 있는 데이터가 지나치게 큰 상태를 말한다. 세 방향에서 터진다.

**메모리가 한 노드에 몰린다.** 1-2에서 봤듯 Sorted Set은 멤버 하나마다 멤버 문자열 자체 말고도 스킵 리스트 노드와 해시테이블 엔트리를 함께 들고 있다. 멤버당 수십~수백 바이트가 붙으므로 수억 멤버면 수십 GB가 되고, 그 전부가 **한 노드**에 올라간다(3-1의 이유로 쪼갤 수 없다).

**O(N) 명령 한 방이 서버를 세운다.** Redis는 싱글 스레드다. `ZUNIONSTORE`나 `ZRANGEBYSCORE`처럼 멤버 수에 비례하는 명령을 수억 멤버 키에 치면, 그 명령이 끝날 때까지 다른 모든 클라이언트의 GET 하나까지 전부 대기한다.

**삭제와 마이그레이션도 폭탄이다.** 큰 컬렉션을 `DEL`로 지우면 그 해제 작업이 이벤트 루프에서 돌아 그 시간만큼 서버가 멈춘다(`UNLINK`를 쓰는 이유는 `12-keys-vs-scan.md`에서 다룬다). 클러스터에서 슬롯을 다른 노드로 옮길 때도 큰 키 하나가 통째로 이동해야 해서 그동안 지연이 튄다.

대응은 기술이 아니라 **요구사항을 되묻는 것**에서 시작한다. **정말 수억 명 전원의 정확한 순위가 필요한가, 아니면 TOP 1000만 정확하면 되는가?**

TOP N만 필요하다면 **`ZREMRANGEBYRANK`** 로 주기적으로 하위를 잘라내 크기를 상수로 유지한다. 이 명령은 순위 구간을 지정해 그 구간의 멤버를 지운다 — 예를 들어 점수 낮은 쪽 0번부터 세어 상위 1000명만 남기고 나머지를 날린다. 멤버 수가 1000으로 고정되면 위의 세 문제가 전부 사라진다.

"내 순위"까지 수억 명 전원에게 정확히 줘야 한다면 절충이 필요하다. **점수 구간별 카운트(히스토그램)** 로 근사 순위를 주는 방식이다 — 점수 구간마다 인원 수만 세어 두고, "내 점수보다 높은 구간들의 인원 합 + 1" 로 대략적인 순위를 계산해 "상위 12% (약 3만 등)" 처럼 보여준다. 정확한 등수를 포기하는 대신 수억 멤버를 다 들고 있지 않아도 된다.

### 3-3. 조회 트래픽이 그대로 쓰기 트래픽이 된다

이 항목이 이 문서에서 가장 중요한 인식이다.

**캐시는 보통 읽기를 흡수하는 장치다.** DB로 갈 조회를 Redis가 대신 받아 주니 DB의 부하가 줄어든다. 캐시를 도입하면 시스템 전체의 부하가 내려간다는 직관은 여기서 온다.

**그런데 랭킹은 정반대로 동작한다.** 조회 이벤트가 발생할 때마다 `ZINCRBY`를 쳐야 하는데, `ZINCRBY`는 값을 바꾸는 **쓰기** 명령이다. 즉 랭킹 집계는 **페이지뷰라는 읽기 트래픽을 Redis 쓰기 트래픽으로 변환하는 구조**다.

```text
[일반 캐시]   사용자 조회 100,000 QPS
              -> Redis 읽기 100,000 QPS (여러 replica로 분산 가능)
              -> DB 부하는 캐시 미스만큼만

[랭킹 집계]   사용자 조회 100,000 QPS
              -> Redis 쓰기 100,000 QPS  ★ 읽기가 쓰기로 바뀐다
              -> 쓰기는 마스터로만 간다 (replica로 분산 불가)
              -> 랭킹 키는 하나뿐이다 (3-1)
              -> 결국 단일 노드가 100,000 QPS 쓰기를 전부 받는다
```

이 세 줄이 이어지는 것이 hot key의 정체다. 읽기라면 replica를 늘려 나눠 받을 수 있지만, **쓰기는 마스터 한 대로만 간다.** 거기에 3-1의 "랭킹 키는 하나뿐"이 겹치면서 확장의 여지가 완전히 막힌다. `ZINCRBY` 하나가 O(log N)으로 빠르다는 사실은 이 지점에서 도움이 안 된다 — 명령 하나의 비용이 아니라 한 노드가 받는 명령의 개수가 병목이기 때문이다.

해법은 **집계의 지연을 허용해 쓰기 횟수 자체를 줄이는 것**이다.

```java
// Before: 이벤트마다 Redis 왕복 — 조회 QPS가 그대로 쓰기 QPS가 된다
public void onView(long webtoonId) {
    zSet.incrementScore(bucket(), String.valueOf(webtoonId), 1);
}

// After: 애플리케이션 로컬에서 모았다가 주기적으로 한 번에 반영
// LongAdder는 여러 스레드가 동시에 증가시킬 때 경합을 분산시키는 카운터다.
// 이 서버가 5초 동안 본 조회 횟수를 웹툰별로 메모리에 쌓아 둔다.
private final ConcurrentHashMap<Long, LongAdder> buffer = new ConcurrentHashMap<>();

public void onView(long webtoonId) {
    buffer.computeIfAbsent(webtoonId, k -> new LongAdder()).increment();
}

@Scheduled(fixedDelay = 5_000)
public void flush() {
    // 버퍼를 통째로 스냅샷 떠서 비우고, 웹툰별 누적 횟수를
    // ZINCRBY 한 번씩으로 반영한다. 파이프라인으로 묶어 보내면
    // 네트워크 왕복 횟수까지 한 번으로 줄어든다.
}
```

효과를 숫자로 확인해 보자. 조회 100,000 QPS, 애플리케이션 서버 50대, 플러시 주기 5초라고 하자.

```text
Before: 5초 동안 조회 500,000건 -> ZINCRBY 500,000회

After:  서버 한 대가 5초 동안 받는 조회 = 500,000 / 50 = 10,000건
        그 안에 등장한 서로 다른 웹툰이 500종이라면
        서버당 ZINCRBY 500회 -> 전체 50 x 500 = 25,000회

        500,000 -> 25,000  = 20분의 1
```

압축률은 고정된 값이 아니라 **한 서버가 한 주기 안에 같은 웹툰을 몇 번 보느냐**로 결정된다. 위 예에서는 서버당 10,000건이 500종에 나뉘었으니 평균 20회, 그래서 정확히 20분의 1이다. 트래픽이 더 몰릴수록, 주기가 길수록, 인기가 소수 작품에 집중될수록 압축률이 좋아진다. 반대로 조회가 아주 많은 종류에 얇게 흩어져 있으면 효과가 떨어진다 — 이 구조의 한계도 함께 알고 있어야 한다.

**대가는 두 가지다.** 첫째, 랭킹이 최대 5초 늦게 반영된다. 둘째, 서버가 플러시 전에 죽으면 버퍼에 든 조회수가 유실된다. 랭킹은 화면용 근사치이므로 둘 다 감수할 만하지만, "정확·즉시"를 "근사·지연 허용"으로 협상해서 비용을 낮췄다는 사실 자체는 명시적으로 말해야 한다.

Kafka로 조회 이벤트를 흘려보내고 컨슈머가 일정 시간 단위로 집계해 반영하는 구조도 같은 원리다. 버퍼가 애플리케이션 메모리 대신 Kafka에 있다는 차이인데, 대신 서버가 죽어도 이벤트가 유실되지 않는다는 이점이 붙고 인프라 한 겹이 늘어나는 비용을 낸다.

**샘플링**은 또 다른 완화책이다. 조회 10건 중 1건만 골라 점수를 10씩 올리면 쓰기가 10분의 1이 된다. 대가는 정확도다 — 조회수가 큰 상위권은 표본이 충분해 오차가 작지만, 실제 조회 30회짜리 하위권 작품은 표본이 3건이라 하나만 어긋나도 점수가 20에서 40으로 흔들린다. **상위권 순위는 믿을 만하고 하위권은 노이즈가 크다**는 성질을 이해하고 쓰면 되는 기법이다. TOP N만 보여 주는 랭킹이라면 합리적인 선택이고, "내 작품 지금 몇 위" 같은 개별 순위 조회에는 부적합하다.

### 3-4. 클러스터의 멀티 키 제약이 hot key를 되부른다

마지막 한계는 앞의 것들이 서로 엮여서 나온다.

`ZUNIONSTORE`는 **여러 키를 한 명령에서 다루는 멀티 키 명령**이다. 그런데 Redis Cluster에서 키들은 각자 다른 노드에 흩어져 있을 수 있고, **한 명령은 한 노드 안에서만 실행된다.** 그래서 클러스터는 멀티 키 명령에 조건을 건다 — **명령에 등장하는 모든 키가 같은 해시 슬롯에 있어야 한다.** 아니면 `CROSSSLOT` 오류가 난다.

시간 버킷 키들은 이름이 다 다르니 자연 상태로는 서로 다른 슬롯에 흩어진다. 이걸 같은 슬롯으로 모으는 장치가 **해시태그**다. 키 이름에 중괄호를 넣으면 Redis는 **중괄호 안의 부분만 해싱해서** 슬롯을 정한다.

```text
ranking:{webtoon}:2026090113
ranking:{webtoon}:2026090114
ranking:{webtoon}:merged
  -> 셋 다 "webtoon" 만 해싱된다 -> 같은 슬롯 -> ZUNIONSTORE 가능
```

문제는 여기서 끝나지 않는다는 것이다. 같은 슬롯에 있다는 말은 **같은 노드에 있다**는 말이고, 그러면 랭킹 관련 키 전부와 그 부하 전부가 다시 한 노드로 모인다. 3-1의 hot key 문제를 해시태그로 한 번 더 못 박는 셈이다.

이것이 이 질문의 마지막 관전 포인트다. **인프라의 확장 방식(클러스터의 슬롯 단위 샤딩)이 애플리케이션의 키 설계를 역으로 규정한다.** 애플리케이션이 원하는 대로 키를 설계한 뒤 인프라를 붙이는 것이 아니라, 인프라의 제약을 알고 키를 설계해야 한다는 사례다.

## 4. 꼬리질문 대비 포인트

### "점수가 같은 웹툰끼리의 순서는 어떻게 되나요?"

멤버 문자열의 **사전순(바이너리 비교)** 이다. 숫자 크기순이 아니라 문자열 비교라 `"10"`이 `"9"`보다 앞에 온다.

비즈니스 규칙(선점순 등)이 필요하면 점수를 합성한다 — 예를 들어 정수부는 조회수, 소수부는 `1 - (timestamp / 최댓값)` 처럼 먼저 도달할수록 큰 값이 되게 만든다. 그러면 조회수가 같을 때 소수부가 승부를 가른다.

여기에 1-6의 사실을 얹으면 답이 정확해진다. 점수는 double이고 정수를 정확히 표현할 수 있는 상한이 2^53 = 9007199254740992이므로, 정수부와 소수부가 그 53비트 예산을 나눠 쓴다. 소수부에 자릿수를 많이 줄수록 정수부(조회수)의 정확 표현 상한이 내려간다는 것까지 말하면 좋다.

### "최근 1시간 랭킹인데 10분 전 조회까지만 반영하고 싶다면?"

버킷 정밀도의 문제다(2-5). 1시간 윈도우를 10분 단위로 움직이려면 10분 버킷 6개를 합산한다.

정밀도를 올릴수록 버킷 개수, `ZUNIONSTORE` 합산 비용, 키 관리 비용이 함께 늘어난다. 그래서 "윈도우가 얼마나 부드럽게 움직여야 하는가"를 제품 요구사항과 협상해서 버킷 크기를 정한다고 답하면 된다. 기술로 정하는 값이 아니라 요구사항에서 역산하는 값이라는 점이 답의 골자다.

### "'내 웹툰은 지금 몇 위' 조회는 비싸지 않나요?"

명령 자체는 싸다. `ZREVRANK`는 O(log N)이라 멤버가 많아도 조회 한 번의 비용은 문제가 안 된다.

진짜 문제는 그 명령을 쓰려면 **전체 멤버를 다 들고 있어야 한다**는 것이다. 순위를 매기려면 나보다 위에 몇 명이 있는지 알아야 하고, 그러려면 전원이 Sorted Set 안에 있어야 한다. 멤버가 수억이면 3-2의 big key 문제로 그대로 돌아간다.

그래서 TOP N만 유지하는 잘린 랭킹에서는 순위권 밖 멤버의 순위를 줄 수 없다. 선택지는 둘이다 — "순위권 밖"이라고만 표시하고 타협하거나, 점수 히스토그램으로 "상위 12%" 같은 근사 순위를 주거나. 어느 쪽이든 정확한 등수를 포기하는 대가로 크기를 상수로 유지하는 거래다.

### "DB에도 어차피 조회수를 저장할 텐데, 랭킹도 DB로 하면 안 되나요?"

`ORDER BY view_count DESC LIMIT 10`은 실행할 수는 있다. 안 되는 이유는 셋이다(1-1).

1. 조회수 컬럼 인덱스는 초당 수천 번의 갱신마다 재정렬 비용을 낸다.
2. 인기 행에 UPDATE가 몰려 락 경합이 생긴다 — 인기가 많을수록 느려지는 역설.
3. 시간 윈도우 랭킹은 컬럼 하나 정렬로 안 되고 이벤트 로그 테이블을 `GROUP BY`로 집계해야 해서 훨씬 비싸진다.

다만 Redis 편만 들면 답이 반쪽이다. **Redis 랭킹은 재시작이나 장애로 유실될 수 있다.** 그래서 실무의 정석은 역할 분리다 — **정산·통계처럼 정확해야 하는 수치는 DB(이벤트 적재)가 원본이고, Redis는 화면에 보여 줄 실시간 근사치다.** 둘은 경쟁 관계가 아니라 용도가 다른 두 저장소이고, 어긋나도 되는 데이터와 어긋나면 안 되는 데이터를 구분했다는 점이 답의 핵심이다.

### "이 설계를 그대로 두고 트래픽이 100배가 되면 어디가 먼저 무너지나요?" (시니어 변별 포인트)

순서를 짚어서 답한다.

**첫째, 쓰기 경로가 먼저 무너진다.** 조회 QPS와 같은 수의 `ZINCRBY`가 랭킹 키를 가진 단일 노드로 몰린다(3-3의 읽기→쓰기 역전 + 3-1의 hot key). 쓰기는 replica로 분산되지 않으므로 여기서 가장 먼저 한계에 닿는다.

**둘째, 스케줄러의 `ZUNIONSTORE` 합산이다.** 멤버가 늘수록 O(N) + O(M log M)의 N과 M이 커지고, 싱글 스레드를 그만큼 오래 점유한다.

**셋째, 메모리다.** 멤버 수 × (문자열 + 스킵 리스트 노드 + 해시테이블 엔트리)가 한 노드에 쌓인다.

방어도 같은 순서로 간다.

1. 로컬 버퍼링 + 파이프라인으로 쓰기 횟수를 묶는다(3-3).
2. merged TOP N을 애플리케이션 로컬 캐시로 내려 읽기가 Redis에 도달하지 않게 한다(3-1).
3. `ZREMRANGEBYRANK`로 하위 랭크를 잘라 크기를 상수로 유지한다(3-2).

**"어디가 병목인지의 순서"를 짚는 것 자체가 규모 검증 습관의 증거다.** 모든 한계를 한꺼번에 나열하는 답과, 무엇이 먼저 무너지는지 순서를 매기고 방어도 그 순서로 배치하는 답의 차이가 이 질문의 변별점이다.

## 한 줄 요약

Sorted Set은 `ZINCRBY`(없으면 0에서 만들어 주는 점수 증가)와 `ZREVRANGE`(점수 높은 순 M개)만으로 O(log N) 랭킹을 주는 최적의 도구지만, "실시간 인기"는 누적이 아니라 최근 N시간이므로 시간 버킷 키 + TTL + `ZUNIONSTORE` 합산이라는 윈도우 설계가 따로 필요하고, 대규모에서는 랭킹 키가 하나뿐이라 클러스터로도 분산되지 않는 hot key에 "조회 이벤트마다 쓰기"라는 읽기·쓰기 역전이 겹쳐 단일 노드가 먼저 무너지며, 그 뒤로 수억 멤버 big key와 멀티 키 슬롯 제약이 따라오므로 — 로컬 버퍼링으로 쓰기를 묶고, 결과를 로컬 캐시로 내리고, 하위 랭크를 잘라내고, "정확·즉시"를 "근사·지연 허용"으로 협상하는 것까지 붙여야 규모를 견디는 설계가 된다.
