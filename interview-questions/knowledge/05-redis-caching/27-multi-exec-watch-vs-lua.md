# MULTI/EXEC, WATCH, Lua — 같은 "트랜잭션"이라는 말, 전혀 다른 보장

> 핵심 관전 포인트: **MULTI/EXEC가 보장하는 것은 "모아둔 명령의 원자적 일괄 실행" 하나뿐이다 — 실행 중 다른 클라이언트의 명령이 끼어들지 않는다는 격리이지, RDB 트랜잭션이 아니다.** 두 가지가 없다: ① **롤백이 없다** — 실행 중 한 명령이 실패해도 나머지는 그대로 실행되고 되돌리지 않는다. ② **중간 조회 결과로 분기할 수 없다** — MULTI 안의 명령은 큐에 쌓일 뿐(`QUEUED`) EXEC 전에는 실행되지 않으므로, "GET 해보고 값에 따라 다음 명령을 결정"이 원천 불가능하다. 그래서 check-then-act(조회 후 조건부 갱신)에는 **WATCH**(감시 키가 바뀌었으면 EXEC 전체를 무효화하는 낙관적 방식 — 실패 시 재시도 필요)나 **Lua 스크립트**(조회→분기→갱신을 서버 안에서 원자적으로 실행)가 필요하다. 실무 기본값은 Lua다 — 왕복 1회에 분기까지 되고 재시도 루프가 없다. 대신 **긴 스크립트는 싱글 스레드 전체를 세운다**는 양날을 함께 말해야 한다.

---

## 0. 질문 + 의도

**질문**: "Redis의 MULTI/EXEC 트랜잭션과 WATCH는 무엇을 보장하나요? Lua 스크립트와의 차이는?"

**출제 의도**: rationale은 이렇게 적고 있다 — "MULTI는 원자적 일괄 실행일 뿐
중간 조회 결과로 분기할 수 없다는 제약(그래서 check-then-act는 WATCH나 Lua가
필요)을 아는지 — **'트랜잭션'이라는 같은 단어가 RDB와 Redis에서 전혀 다른
보장임을 구분하는 정밀함**을 본다." 즉 채점 지점은 명령어 사용법이 아니라
① MULTI의 보장 범위를 정확히 좁혀 말하는가(무엇이 **없는지**까지)
② check-then-act라는 문제 유형과 도구(WATCH/Lua)를 짝지을 수 있는가
③ Lua를 기본값으로 고르면서 그 비용(블로킹)까지 아는가다.

## 1. MULTI/EXEC의 실제 동작 — "큐에 모았다가 한 번에"

```
클라이언트                          Redis
MULTI                    ─────▶    OK        (지금부터 큐잉 모드)
INCR  stock:reserved     ─────▶    QUEUED    ← 실행 안 됨. 쌓이기만 한다
DECR  stock:available    ─────▶    QUEUED
EXEC                     ─────▶    [1, 99]   ← 이 순간 두 명령을 연달아 실행
```

EXEC 시점에 큐의 명령들이 **하나의 덩어리로 연속 실행**되고, Redis는 싱글
스레드이므로 그 사이에 다른 클라이언트의 명령이 끼어들 수 없다. 보장은 이것이
전부다: **격리된 일괄 실행.** "여러 키를 반드시 함께 바꿔야 하고, 중간 상태를
남에게 보이면 안 될 때" 쓰는 도구다.

### 1-1. 없는 것 ① — 롤백

에러가 두 종류로 갈리고, 어느 쪽도 RDB식 롤백이 아니다.

- **큐잉 시점 에러**(없는 명령, 문법 오류): Redis가 큐잉 단계에서 이미 알 수
  있는 오류다. 이 경우 EXEC가 거부되어 **전체가 실행되지 않는다.**
- **실행 시점 에러**(타입 불일치 등 — 예: 문자열 키에 `LPUSH`): EXEC는 각
  명령의 결과 배열에 그 명령만 에러로 표시하고, **앞뒤의 다른 명령들은
  그대로 실행·확정된다. 되돌리지 않는다.**

```
MULTI
SET  k1 "a"
LPUSH k1 "b"      ← 실행 시점에 타입 에러가 날 명령
SET  k2 "c"
EXEC
→ [OK, (error) WRONGTYPE..., OK]   ← k1="a", k2="c" 는 이미 반영됐고 남는다
```

RDB의 "전부 성공 아니면 전부 취소"에 익숙한 채로 옮겨 오면 여기서 정합성이
깨진다. Redis 트랜잭션에서 "부분 실패 후 정리"는 **애플리케이션의 몫**이다 —
그래서 MULTI 안에는 실행 시점에 실패할 수 있는 명령을 애초에 넣지 않도록
설계하는 것이 실무 규율이다.

### 1-2. 없는 것 ② — 중간 결과로 분기하기

이 문항의 핵심 함정이다. MULTI 안의 명령은 EXEC 전에 실행되지 않으므로
**조회 결과가 손에 없다.**

```
❌ BEFORE — 이런 코드를 상상하지만, 성립 자체가 안 된다
MULTI
GET stock            ← 반환값은 "QUEUED". 재고 값이 아니다!
(값이 0보다 크면)     ← 분기할 값이 존재하지 않는다
DECR stock
EXEC
```

"조회해서 확인한 뒤 조건에 맞으면 갱신한다"(check-then-act)는 요구는 MULTI로는
**구조적으로 표현 불가능**하다. 그렇다고 MULTI 밖에서 GET 하고 조건 확인 후
MULTI를 열면? GET과 EXEC 사이에 다른 클라이언트가 값을 바꿀 수 있다 — 확인과
행동이 두 문장이면 그 사이는 언제나 뚫린다는, 낙관적 락 문서에서 본 것과 같은
원리다([낙관적 vs 비관적 락](../03-jpa-orm/10-optimistic-vs-pessimistic-lock.md)
§1-1). 이 틈을 메우는 도구가 WATCH와 Lua다.

## 2. WATCH — Redis판 낙관적 동시성 제어

### 2-1. 동작: 감시하던 키가 바뀌면 EXEC 전체가 무효

```
WATCH stock              ← 이 키를 감시 시작
GET   stock              → 5   (MULTI 밖이므로 진짜 값을 받는다)
(애플리케이션에서 판단: 0보다 크네, 차감하자)
MULTI
DECR  stock
EXEC
→ 감시 시작 후 stock 이 그대로였으면: [4] — 반영
→ 그 사이 누군가 stock 을 바꿨으면:   (nil) — 큐 전체가 실행되지 않음
```

EXEC가 `nil`을 돌려주면 "내가 본 값이 낡았다"는 뜻이므로 **처음(WATCH+GET)부터
재시도**한다. 잠그지 않고, 충돌을 사후에 감지해 무효화한다 — JPA `@Version`과
정확히 같은 철학의 낙관적 방식이고, 실패 모드도 같다: **경합이 심하면 재시도
폭풍**이 된다. 성공 1건당 나머지 전원이 처음부터 다시 도는 구조라, 선착순처럼
전 요청이 같은 키를 치는 상황에서는 틀린 도구다.

### 2-2. 실무 주의점 — WATCH는 커넥션에 붙는 상태다

WATCH는 "그 커넥션이 무엇을 감시 중인가"라는 **커넥션 단위 상태**를 만든다.
EXEC나 DISCARD가 실행되면 감시가 풀리지만, 애플리케이션에서 **커넥션 풀**을
쓴다면 WATCH~EXEC 시퀀스가 반드시 **같은 커넥션**에서 실행되도록 묶어야 한다
(라이브러리의 세션/트랜잭션 콜백 API가 그 역할을 한다). 명령 단위로 커넥션을
빌려 쓰는 일반적인 사용 방식과 충돌하는 지점이라, WATCH가 실무에서 잘 안 쓰이는
현실적 이유이기도 하다. **(가산점 포인트)**

## 3. Lua — 조회·분기·갱신을 서버 안으로 밀어 넣는다

### 3-1. 무엇이 달라지는가

Lua 스크립트(EVAL)는 Redis 서버 **안에서** 실행된다. 스크립트 전체가 원자적으로
실행되고(실행 중 다른 명령이 끼어들 수 없음), 결정적으로 — **`redis.call`의
반환값을 변수로 받아 분기할 수 있다.** MULTI가 못 하던 그것이다.

```lua
-- ✅ AFTER — check-then-act 가 서버 안에서 한 덩어리로
-- KEYS[1] = stock
local stock = tonumber(redis.call("GET", KEYS[1]) or "0")
if stock <= 0 then
    return 0                          -- 조회 결과를 보고 분기한다
end
redis.call("DECR", KEYS[1])
return stock - 1
```

세 도구를 한 줄씩 대면 이렇다.

| | MULTI/EXEC | WATCH + MULTI | Lua (EVAL) |
|---|---|---|---|
| 원자성 | 일괄 실행 원자 | 일괄 실행 원자 | 스크립트 전체 원자 |
| 중간 결과 분기 | **불가** | 클라이언트에서 (낡을 수 있음) | **서버 안에서 가능** |
| 충돌 시 | 해당 없음 | EXEC 무효 → **재시도 필요** | 충돌 자체가 없음 |
| 왕복 | 명령 수만큼 큐잉 왕복* | +WATCH/GET 왕복 | **1회** |
| 실패 모드 | 부분 실패(롤백 없음) | 재시도 폭풍 | 긴 스크립트 = 전역 블로킹 |

*파이프라인과 함께 쓰면 큐잉 왕복은 묶을 수 있다 — MULTI와 파이프라인은 별개
개념이다(§4 꼬리질문).

그래서 실무 기본값이 Lua다. 분산 락의 소유자 검증 해제
([분산 락의 함정](16-distributed-lock-pitfalls-redlock.md) §3), 선착순 쿠폰의
중복+초과 판정([선착순 쿠폰 설계](17-flash-sale-coupon-issuance-design.md) §2),
레이트 리미터의 카운트+만료 갱신 — 전부 "조회하고 조건 보고 갱신"이라 Lua의
자리다.

### 3-2. Lua의 비용 — 원자성의 재료는 "전원 정지"다

Lua가 원자적인 이유는 마법이 아니라 **실행 중 싱글 스레드가 그 스크립트만 붙잡고
있기 때문**이다. 즉 스크립트가 도는 동안 **Redis 전체가 다른 요청을 처리하지
못한다.** O(N) 명령(`SMEMBERS`, `KEYS`)이나 루프가 든 스크립트 하나가 전 서비스의
캐시 응답을 세운다 — `KEYS` 금지와 같은 뿌리의 문제다. 규율은 두 가지:
**스크립트는 O(1)~O(logN) 명령 몇 개로 짧게**, 그리고 **무거운 계산은 스크립트
밖(애플리케이션)에서 끝내고 판정·갱신만 서버 안으로** 가져간다.

운영 관점 주의점 두 가지를 더 얹으면 답이 단단해진다. **(가산점 포인트)**

- **Cluster에서는 스크립트가 접근할 키를 반드시 `KEYS[]` 인자로 선언**해야
  하고, 그 키들이 **같은 해시 슬롯**에 있어야 한다(해시 태그 `{...}`로 묶는다).
  MULTI도 마찬가지로 Cluster에서는 같은 슬롯 키끼리만 가능하다 — "인프라 확장이
  애플리케이션 코드를 바꾸는" 대표 사례.
- 매번 스크립트 원문을 보내는 대신 **`EVALSHA`(스크립트 해시로 호출)** 를 쓰되,
  서버 재시작 등으로 캐시가 비어 `NOSCRIPT` 에러가 오면 EVAL로 재적재하는
  폴백이 클라이언트 라이브러리에 필요하다(대부분 내장).

## 4. 꼬리질문 대비 포인트

### "MULTI 실행 중 한 명령이 실패하면 앞의 명령은 롤백되나요?"

안 된다. 에러 시점으로 나눠 답한다 — **큐잉 시점 에러**(문법·존재하지 않는
명령)는 EXEC 자체가 거부되어 전체가 실행되지 않지만, **실행 시점 에러**(타입
불일치 등)는 그 명령만 에러이고 **앞뒤 명령은 실행된 채 남는다.** Redis는
롤백을 구현하지 않는 대신 단순함과 속도를 택했고, 공식 입장도 "실행 시점
에러는 코드 버그이니 개발 중에 잡아라"다. 그래서 MULTI 블록은 실패할 수 있는
명령이 없도록 설계하는 것이 규율이다.

### "WATCH한 키를 나 말고 아무도 안 바꿨는데 EXEC가 nil이 나올 수 있나요?"

있다. WATCH는 "누가" 바꿨는지가 아니라 **바뀌었는지**만 본다. 예컨대 감시 중인
키가 **TTL 만료로 삭제**되는 것도 변경으로 취급되어 EXEC가 무효화될 수 있다.
반대 방향의 함정도 있다 — 같은 값으로 덮어써도(값이 동일해도 SET이 일어났으면)
변경으로 본다. 판정 기준이 "값의 동일성"이 아니라 "키에 대한 쓰기 발생"임을
아는지 확인하는 질문이다.

### "Lua 스크립트가 실행 중에 너무 오래 걸리면 어떻게 하나요?" (시니어 변별 포인트)

일정 시간이 지나면 Redis는 다른 클라이언트에게 BUSY 에러를 응답하기 시작하지만
**스크립트 자체는 계속 돈다** — 원자성 때문에 중간에 함부로 끊을 수 없어서다.
이때 개입 수단이 갈린다: 스크립트가 **아직 쓰기를 하지 않았다면** `SCRIPT KILL`
로 중단 가능하지만, **이미 쓰기를 시작했다면** 부분 실행 상태를 남길 수 없으므로
KILL이 거부되고, 남는 선택지는 사실상 서버 강제 종료뿐이다 — 사고다. 그래서
방어는 사후 개입이 아니라 사전 규율(짧은 스크립트, O(1) 명령, 스테이징에서
슬로우로그 확인)이고, "원자성은 공짜가 아니라 블로킹으로 지불한다"는 문장으로
정리하면 좋다.

### "파이프라인과 MULTI는 뭐가 다른가요?"

축이 다르다. **파이프라인은 네트워크 최적화**다 — 여러 명령을 응답을 기다리지
않고 한 번에 보내 왕복 횟수를 줄일 뿐, 명령들 사이에 다른 클라이언트의 명령이
끼어들 수 있다(원자성 없음). **MULTI는 원자성 장치**다 — 끼어들기를 막지만
왕복을 줄여주지는 않는다. 그래서 "원자적일 필요는 없고 빠르게 여러 개"면
파이프라인(또는 MGET), "반드시 한 덩어리"면 MULTI나 Lua — 둘을 섞어 쓸 수도
있다(파이프라인으로 MULTI 블록 전송).

### "RDB 트랜잭션의 ACID 기준으로 MULTI/EXEC를 평가하면?" (시니어 변별 포인트)

- **A(원자성)**: 절반만 — "전부 실행"은 보장하지만 "아니면 전부 취소"(롤백)가
  없다.
- **C(일관성)**: 제약 개념 자체가 없으므로 애플리케이션 책임.
- **I(격리성)**: 싱글 스레드 일괄 실행이라 **가장 강하게** 보장된다 — 끼어들기
  자체가 불가능하니 격리 수준 논의가 필요 없다.
- **D(내구성)**: 트랜잭션과 무관하게 영속화 설정(RDB/AOF, fsync 정책)이 결정하며
  EXEC 성공이 디스크 기록을 의미하지 않는다.

"같은 단어, 다른 보장"을 이렇게 축별로 해부해 보이면 — 그리고 "그래서 Redis에서
트랜잭션이라는 말을 들으면 나는 격리된 일괄 실행으로 번역해 듣는다"로 맺으면 —
이 문항의 출제 의도에 정면으로 답한 것이 된다.

---

## 한 줄 요약

MULTI/EXEC는 **롤백도, 중간 결과 분기도 없는 "격리된 일괄 실행"** 일 뿐이라
check-then-act를 표현할 수 없고, 그 틈은 **WATCH(낙관적 무효화 + 재시도)** 나
**Lua(서버 안에서 조회→분기→갱신을 원자로, 왕복 1회)** 가 메우며 — 실무
기본값은 Lua이되 **그 원자성의 대가는 스크립트가 도는 동안 싱글 스레드 전체가
멈춘다는 것**이므로, 스크립트를 짧게 유지하는 규율까지 말해야 답이 완성된다.
