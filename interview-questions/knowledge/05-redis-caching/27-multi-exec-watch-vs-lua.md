# MULTI/EXEC, WATCH, Lua — 같은 "트랜잭션"이라는 말, 전혀 다른 보장

> 핵심 관전 포인트: **MULTI/EXEC가 보장하는 것은 "모아둔 명령의 원자적 일괄 실행" 하나뿐이다 — 실행 중 다른 클라이언트의 명령이 끼어들지 않는다는 격리이지, RDB 트랜잭션이 아니다.** 두 가지가 없다: ① **롤백이 없다** — 실행 중 한 명령이 실패해도 나머지는 그대로 실행되고 되돌리지 않는다. ② **중간 조회 결과로 분기할 수 없다** — MULTI 안의 명령은 큐에 쌓일 뿐(`QUEUED`) EXEC 전에는 실행되지 않으므로, "GET 해보고 값에 따라 다음 명령을 결정"이 원천 불가능하다. 그래서 check-then-act(조회 후 조건부 갱신)에는 **WATCH**(감시 키가 바뀌었으면 EXEC 전체를 무효화하는 낙관적 방식 — 실패 시 재시도 필요)나 **Lua 스크립트**(조회→분기→갱신을 서버 안에서 원자적으로 실행)가 필요하다. 실무 기본값은 Lua다 — 왕복 1회에 분기까지 되고 재시도 루프가 없다. 대신 **긴 스크립트는 싱글 스레드 전체를 세운다**는 양날을 함께 말해야 한다.

---

## 0. 질문 + 의도

**질문**: "Redis의 MULTI/EXEC 트랜잭션과 WATCH는 무엇을 보장하나요? Lua 스크립트와의 차이는?"

**출제 의도**: rationale은 이렇게 적고 있다 — "MULTI는 원자적 일괄 실행일 뿐 중간 조회 결과로 분기할 수 없다는 제약(그래서 check-then-act는 WATCH나 Lua가 필요)을 아는지 — **'트랜잭션'이라는 같은 단어가 RDB와 Redis에서 전혀 다른 보장임을 구분하는 정밀함**을 본다." 즉 채점 지점은 명령어 사용법이 아니라 ① MULTI의 보장 범위를 정확히 좁혀 말하는가(무엇이 **없는지**까지) ② check-then-act라는 문제 유형과 도구(WATCH/Lua)를 짝지을 수 있는가 ③ Lua를 기본값으로 고르면서 그 비용(블로킹)까지 아는가다.

## 1. MULTI/EXEC의 실제 동작 — "큐에 모았다가 한 번에"

### 1-1. 전제 지식 — RDB의 트랜잭션과 무엇이 같고 무엇이 다른가

Spring에서 `@Transactional`을 붙였을 때 우리가 기대하는 것은 네 가지다. 전부 성공 아니면 전부 취소(원자성), 제약 위반이 없는 상태 유지(일관성), 다른 트랜잭션의 중간 상태가 안 보임(격리성), 커밋되면 살아남음(내구성). ACID다.

Redis의 "트랜잭션"은 **이 중 격리성 하나만** 강하게 보장하는 물건이다. 같은 단어를 쓰지만 담고 있는 약속이 다르다. 그래서 이 문항의 핵심은 명령어 사용법이 아니라 **"무엇을 보장하지 않는지를 정확히 아는가"**다.

동작부터 보자.

```
클라이언트                          Redis
MULTI                    ─────▶    OK        (지금부터 큐잉 모드)
INCR  stock:reserved     ─────▶    QUEUED    ← 실행 안 됨. 쌓이기만 한다
DECR  stock:available    ─────▶    QUEUED
EXEC                     ─────▶    [1, 99]   ← 이 순간 두 명령을 연달아 실행
```

`MULTI`를 보낸 뒤의 명령들은 **실행되지 않고 서버 쪽 큐에 쌓인다.** 응답으로 오는 `QUEUED`는 "접수했다"는 뜻이지 결과가 아니다.

`EXEC`를 보내는 순간 큐의 명령들이 **하나의 덩어리로 연속 실행**되고, Redis는 싱글 스레드이므로 그 사이에 다른 클라이언트의 명령이 끼어들 수 없다.

보장은 이것이 전부다. **격리된 일괄 실행.** "여러 키를 반드시 함께 바꿔야 하고, 중간 상태를 남에게 보이면 안 될 때" 쓰는 도구다. 예컨대 예약 수를 늘리면서 가용 재고를 줄이는 두 명령 사이에 누가 끼어들어 조회하면 합계가 안 맞는 순간이 보이는데, MULTI는 그 순간을 없앤다.

### 1-2. 없는 것 ① — 롤백

"롤백이 없다"는 문장은 자주 인용되지만 부정확하게 이해되는 경우가 많다. **에러가 두 종류로 갈리고, 두 경우의 결과가 정반대**이기 때문이다. 이 둘을 구분해 말하는 것이 정확한 답이다.

#### 경우 (1) 큐잉 시점 에러 — 전체가 취소된다

`MULTI` 이후 명령을 보내는 시점에, Redis가 **명령을 큐에 넣기도 전에** 알 수 있는 오류가 있다. 존재하지 않는 명령 이름이거나 인자 개수가 안 맞는 경우다. 이때는 그 자리에서 에러가 돌아오고, Redis는 이 트랜잭션에 "오류 있음" 표식을 붙인다. 나중에 `EXEC`를 보내면 **실행 자체를 거부**한다.

```
MULTI                    ─────▶  OK
SET  k1 "a"              ─────▶  QUEUED
SETX k1 "b"              ─────▶  (error) ERR unknown command 'SETX'
                                  ← 큐에 안 들어갔고, 트랜잭션이 오염 표시됨
SET  k2 "c"              ─────▶  QUEUED
EXEC                     ─────▶  (error) EXECABORT Transaction discarded
                                          because of previous errors.

결과: k1도 k2도 바뀌지 않았다. 아무것도 실행되지 않았다.
```

이 경우만 보면 "RDB처럼 전부 취소되네"라고 오해하기 쉽다. 그런데 이건 롤백이 아니다. **애초에 아무것도 실행하지 않은 것**일 뿐이다. 실행 전에 걸러낸 것과, 실행한 뒤 되돌리는 것은 완전히 다른 일이다.

#### 경우 (2) 실행 시점 에러 — 그 명령만 실패하고 나머지는 그대로 남는다

문법적으로는 멀쩡해서 큐잉은 정상적으로 됐는데, **실제로 실행해 보니** 실패하는 경우다. 대표적인 것이 타입 불일치다 — 문자열이 들어 있는 키에 리스트 명령(`LPUSH`)을 거는 것은 문법상 아무 문제가 없다. 그 키에 뭐가 들어 있는지는 실행해 봐야 알기 때문이다.

```
MULTI                    ─────▶  OK
SET   k1 "a"             ─────▶  QUEUED
LPUSH k1 "b"             ─────▶  QUEUED   ← 문법은 정상. 큐에 들어간다
SET   k2 "c"             ─────▶  QUEUED
EXEC                     ─────▶  1) OK
                                 2) (error) WRONGTYPE Operation against a key
                                            holding the wrong kind of value
                                 3) OK

결과: k1 = "a" 로 이미 바뀌었고 그대로 남는다.
      k2 = "c" 도 실행됐고 그대로 남는다.
      실패한 명령 하나만 결과 배열에 에러로 표시될 뿐,
      앞뒤 명령은 되돌아가지 않는다.
```

**이것이 "롤백이 없다"의 정확한 형태다.** EXEC의 응답은 단일 성공/실패가 아니라 **명령별 결과 배열**이고, 그 배열 안에 에러가 섞여 있어도 나머지는 이미 확정됐다.

두 경우를 나란히 놓으면 이렇게 된다.

| | 큐잉 시점 에러 | 실행 시점 에러 |
|---|---|---|
| 예 | 없는 명령, 인자 개수 오류 | 타입 불일치(`WRONGTYPE`) |
| 언제 발견 | 명령을 보낼 때 즉시 | `EXEC` 실행 중 |
| EXEC 결과 | `EXECABORT` — 전체 미실행 | 결과 배열 안에 에러 하나 |
| 다른 명령 | 하나도 실행 안 됨 | **전부 실행되고 남음** |

RDB의 "전부 성공 아니면 전부 취소"에 익숙한 채로 옮겨 오면 경우 (2)에서 정합성이 깨진다. Redis 트랜잭션에서 **"부분 실패 후 정리"는 애플리케이션의 몫**이다.

그래서 실무 규율이 하나 나온다. **MULTI 블록 안에는 실행 시점에 실패할 수 있는 명령을 애초에 넣지 않는다.** 되돌릴 수단이 없으니 실패 가능성 자체를 설계에서 제거하는 방향으로 간다. 같은 키에 대해 타입이 뒤섞이지 않도록 키 이름 규칙을 잡는 것도 이 규율의 일부다.

### 1-3. 없는 것 ② — 중간 결과로 분기하기

이 문항의 핵심 함정이다. MULTI 안의 명령은 EXEC 전에 실행되지 않으므로 **조회 결과가 손에 없다.**

```
BEFORE — 이런 코드를 상상하지만, 성립 자체가 안 된다
MULTI
GET stock            ← 반환값은 "QUEUED". 재고 값이 아니다!
(값이 0보다 크면)     ← 분기할 값이 존재하지 않는다
DECR stock
EXEC
```

"조회해서 확인한 뒤 조건에 맞으면 갱신한다"를 **check-then-act**(확인하고 행동하기)라고 부른다. 재고 차감, 쿠폰 발급, 레이트 리미터 — 실무의 동시성 문제 대부분이 이 모양이다. 그런데 이 요구는 MULTI로는 **구조적으로 표현 불가능**하다. 분기에 쓸 값이 EXEC 전에는 손에 들어오지 않기 때문이다.

그렇다고 MULTI 밖에서 GET 하고 조건 확인 후 MULTI를 열면 어떻게 되는가.

```
클라이언트 A                 클라이언트 B
GET stock -> 1
(1 > 0 이니 차감하자)
                            GET stock -> 1
                            (1 > 0 이니 차감하자)
MULTI
DECR stock
EXEC      -> 0
                            MULTI
                            DECR stock
                            EXEC      -> -1   ← 재고가 음수가 됐다
```

GET과 EXEC 사이에 다른 클라이언트가 값을 바꿀 수 있다. **확인과 행동이 두 문장으로 나뉘면 그 사이는 언제나 뚫린다** — 낙관적 락 문서에서 본 lost update와 정확히 같은 원리다([낙관적 vs 비관적 락](../03-jpa-orm/10-optimistic-vs-pessimistic-lock.md) §1-1).

이 틈을 메우는 도구가 WATCH와 Lua다. 각각 접근 방식이 다르다 — **WATCH는 틈이 뚫렸는지를 사후에 감지해 무효화하고, Lua는 틈 자체가 생기지 않게 확인과 행동을 한 덩어리로 만든다.**

## 2. WATCH — Redis판 낙관적 동시성 제어

### 2-1. 전제 지식 — 낙관적 동시성 제어란 무엇인가

WATCH를 이해하려면 그 앞에 깔린 발상을 먼저 알아야 한다.

동시에 같은 데이터를 고치려는 상황을 다루는 방법은 크게 둘이다.

**비관적 잠금(pessimistic lock).** "충돌이 자주 날 것"이라고 비관하고, **작업을 시작하기 전에 미리 잠근다.** PostgreSQL의 `SELECT ... FOR UPDATE`가 이것이다. 잠근 동안 남들은 기다린다. 충돌이 잦은 곳에서는 확실하지만, 잠금을 쥐고 있는 동안 처리량이 떨어지고 데드락 위험이 생긴다.

**낙관적 동시성 제어(optimistic concurrency control).** "충돌은 드물 것"이라고 낙관하고, **잠그지 않고 일단 진행한다.** 대신 **커밋하는 시점에 "내가 읽은 뒤로 누가 건드렸나"를 검사해서, 건드렸으면 실패시키고 재시도**한다. 잠금 비용이 없는 대신, 충돌이 나면 그 작업은 버려지고 처음부터 다시 해야 한다.

JPA를 써 봤다면 이미 만나본 발상이다. `@Version` 필드를 붙이면 JPA는 `UPDATE ... WHERE id = ? AND version = ?`로 갱신하고, 영향받은 행이 0이면 "그 사이 누가 바꿨다"고 판단해 `OptimisticLockException`을 던진다. **읽을 때는 안 잠그고, 쓸 때 검사한다.**

**WATCH는 Redis에서 이 낙관적 방식을 구현하는 장치다.**

### 2-2. 동작: 감시하던 키가 바뀌면 EXEC 전체가 무효

```
WATCH stock              ← 이 키를 감시 시작
GET   stock              → 5   (MULTI 밖이므로 진짜 값을 받는다)
(애플리케이션에서 판단: 0보다 크네, 차감하자)
MULTI
DECR  stock
EXEC
→ 감시 시작 후 stock 이 그대로였으면: [4] — 반영
→ 그 사이 누군가 stock 을 바꿨으면:   (nil) — 큐 전체가 실행되지 않음
```

`GET`이 MULTI 밖에 있다는 점이 핵심이다. 그래서 진짜 값 5를 받아 애플리케이션에서 분기할 수 있다. 1-3에서 불가능했던 일이 가능해진 것이다.

그리고 그 분기가 낡은 값에 근거한 것이었다면 `EXEC`가 `nil`을 돌려주며 **아무것도 실행하지 않는다.** 즉 "낡은 판단으로 쓰기가 나가는 일"이 차단된다.

`EXEC`가 `nil`을 돌려주면 "내가 본 값이 낡았다"는 뜻이므로 **처음(WATCH + GET)부터 재시도**한다. 부분적으로 다시 하는 게 아니라 전부 다시 한다 — 판단의 근거였던 값 자체가 무효가 됐기 때문이다.

```java
// WATCH 재시도 루프의 골격
int attempts = 0;
while (attempts++ < MAX_RETRY) {
    // 매 시도마다 WATCH부터 다시 시작한다.
    // 이전 시도에서 읽은 값은 이미 낡았을 수 있으므로 재사용하면 안 된다
    List<Object> result = tryDecrementWithWatch();
    if (result != null) return result;   // EXEC 성공
    // null = EXEC 무효화. 다른 누군가가 먼저 성공했다는 뜻이다
}
throw new IllegalStateException("재시도 한도 초과");
```

### 2-3. 재시도 루프의 대가 — 왜 실무 기본값이 Lua인가

낙관적 방식의 실패 모드는 JPA `@Version`과 동일하다. **경합이 심하면 재시도 폭풍이 된다.**

구조를 그려 보면 왜 그런지 보인다.

```
같은 키(stock)에 동시 요청 100건

시도 1회차:  100건이 WATCH + GET + MULTI + EXEC
             -> 1건 성공,  99건 nil (무효화)
시도 2회차:  99건이 처음부터 다시
             -> 1건 성공,  98건 nil
시도 3회차:  98건이 처음부터 다시
             ...

성공 1건당 나머지 전원이 왕복을 한 벌씩 더 쓴다.
```

대가가 두 가지다.

**네트워크 왕복이 곱절로 는다.** 한 번의 시도가 WATCH, GET, MULTI, EXEC로 최소 몇 번의 왕복이고, 그것이 재시도 횟수만큼 곱해진다. Redis 자체는 빨라도 **왕복 지연이 쌓여 p99가 튄다.**

**공정성이 없다.** 먼저 온 요청이 먼저 성공한다는 보장이 없다. 운 나쁜 요청은 계속 밀려 재시도 한도를 소진하고 실패한다.

그래서 **선착순 이벤트처럼 전 요청이 같은 키 하나를 치는 상황에서 WATCH는 틀린 도구다.** 경합률이 사실상 100%이므로 낙관의 전제("충돌은 드물다") 자체가 성립하지 않는다.

이 결론이 3절에서 "실무 기본값은 Lua"로 이어지는 근거다. Lua에는 재시도 루프가 아예 없다 — 충돌이 발생할 틈을 만들지 않기 때문이다.

### 2-4. WATCH의 판정 기준 — 값이 아니라 "쓰기가 있었는가"

WATCH가 무엇을 감시하는지 정확히 짚어야 한다. **WATCH는 "값이 달라졌는가"가 아니라 "그 키에 쓰기가 한 번이라도 일어났는가"를 본다.**

이 차이가 드러나는 상황이 이것이다.

```
시각  클라이언트 A              다른 클라이언트
t0    WATCH stock
t1    GET stock -> 100
t2                              SET stock 200
t3                              SET stock 100    ← 원래 값으로 되돌아왔다
t4    MULTI
t5    DECR stock
t6    EXEC -> (nil)             ← 값은 100 그대로인데 무효화된다
```

값만 보면 t1의 100과 t6 시점의 100이 같으므로 A의 판단은 여전히 유효하다. 그런데 EXEC는 무효화된다. 같은 값으로 덮어써도 마찬가지다 — `SET stock 100`이 일어났다는 사실만으로 감시가 깨진다.

이런 성질을 **ABA 문제**라고 부른다. 값이 A → B → A로 돌아왔을 때, 값만 봐서는 "아무 일도 없었다"와 구분할 수 없다는 문제다. 낙관적 동시성 제어를 값 비교로 구현하면 이 함정에 빠진다.

**WATCH는 이 함정을 안전한 쪽으로 피해 간다.** 값 비교가 아니라 "쓰기 발생 여부"로 판정하므로, A → B → A인 경우에도 "뭔가 일어났다"를 놓치지 않는다. 그 대신 실제로는 문제없는 경우까지 무효화하는 **과잉 실패(false abort)**를 감수한다.

**이것은 결함이 아니라 의도적으로 안전한 쪽으로 기운 설계다.** 놓쳐서 잘못된 쓰기가 나가는 것보다, 불필요하게 한 번 더 재시도하는 쪽이 낫다는 판단이다. 값이 같아 보여도 그 사이에 다른 필드가 함께 바뀌었거나 자료구조 내부가 달라졌을 수 있으므로, "쓰기 발생"이 더 보수적이고 안전한 기준이다.

같은 이유로 **TTL 만료에 의한 삭제도 변경으로 취급되어 EXEC가 무효화될 수 있다.** 우리 코드에서는 아무도 그 키를 건드리지 않았는데 EXEC가 nil이 되는 상황이 실제로 생긴다는 뜻이다.

### 2-5. 실무 주의점 — WATCH는 커넥션에 붙는 상태다

이것이 WATCH를 실제로 쓸 때 가장 자주 사고가 나는 지점이다.

WATCH는 서버가 **"이 커넥션이 무엇을 감시 중인가"**를 기억하는 방식으로 동작한다. 즉 감시 상태는 키에 붙는 것도, 클라이언트 애플리케이션에 붙는 것도 아니고 **커넥션(연결)에 붙는다.** `EXEC`나 `DISCARD`가 실행되면 그 커넥션의 감시가 풀린다.

문제는 우리가 커넥션을 **풀(pool)**로 쓴다는 것이다. 커넥션 풀은 명령을 보낼 때마다 놀고 있는 커넥션을 빌려 주고 반납받는 구조다. 그러면 이런 일이 생긴다.

```
[커넥션 풀 사용 시 — WATCH가 무력화되는 경로]

redisTemplate.watch("stock")   -> 커넥션 #3 을 빌려 WATCH 실행 -> 반납
redisTemplate.opsForValue().get("stock")
                               -> 커넥션 #7 을 빌려 GET 실행   -> 반납
redisTemplate.multi()          -> 커넥션 #1 을 빌려 MULTI      -> 반납
redisTemplate.exec()           -> 커넥션 #5 를 빌려 EXEC 실행

결과: 감시는 커넥션 #3 에 걸려 있는데
      EXEC 는 커넥션 #5 에서 실행됐다.
      #5 는 아무것도 감시하고 있지 않으므로
      EXEC 는 "충돌 없음"으로 판정하고 그냥 실행된다.

-> WATCH 를 썼는데 아무 보호도 받지 못한다. 그리고 에러도 안 난다.
```

**에러가 나지 않는다는 점이 가장 위험하다.** 코드는 정상 동작하는 것처럼 보이고, 경합이 실제로 일어나는 순간에만 조용히 값이 깨진다. 부하 테스트를 하기 전까지 발견되지 않는 부류의 버그다.

그래서 Spring Data Redis에서는 `SessionCallback`을 쓴다. **콜백 안의 모든 명령을 같은 커넥션에서 실행하도록 묶어 주는 API**이고, WATCH가 커넥션 단위 상태이기 때문에 존재하는 장치다.

```java
// BEFORE — 각 호출이 서로 다른 커넥션을 빌릴 수 있다. WATCH가 무의미해진다
redisTemplate.watch("stock");
Integer stock = (Integer) redisTemplate.opsForValue().get("stock");
if (stock != null && stock > 0) {
    redisTemplate.multi();
    redisTemplate.opsForValue().decrement("stock");
    redisTemplate.exec();
}
```

```java
// AFTER — SessionCallback 안의 명령은 전부 같은 커넥션에서 실행된다
List<Object> result = redisTemplate.execute(new SessionCallback<>() {
    @Override
    public List<Object> execute(RedisOperations operations) {
        // 여기부터 아래까지가 하나의 커넥션에 묶인다.
        // 이 보장이 없으면 아래 WATCH는 EXEC와 무관한 커넥션에 걸린다
        operations.watch("stock");

        Integer stock = (Integer) operations.opsForValue().get("stock");
        if (stock == null || stock <= 0) {
            // 진행하지 않을 것이므로 감시를 명시적으로 푼다.
            // 안 풀면 그 커넥션이 반납된 뒤에도 감시 상태가 남아
            // 다음에 그 커넥션을 빌린 코드의 EXEC가 엉뚱하게 무효화될 수 있다
            operations.unwatch();
            return null;
        }

        operations.multi();
        operations.opsForValue().decrement("stock");

        // 감시 키가 바뀌었으면 빈 리스트가 돌아온다(무효화).
        // 그 경우 호출부에서 WATCH부터 다시 시작해야 한다
        return operations.exec();
    }
});
```

**명령 단위로 커넥션을 빌려 쓰는 일반적인 사용 방식과 정면으로 충돌하는 지점이라, 이것이 WATCH가 실무에서 잘 안 쓰이는 현실적 이유이기도 하다.** 재시도 루프의 비용(2-3)에 더해, 코드 형태까지 특수해진다. **(가산점 포인트)**

## 3. Lua — 조회·분기·갱신을 서버 안으로 밀어 넣는다

### 3-1. 무엇이 달라지는가

Lua 스크립트(`EVAL`)는 Redis 서버 **안에서** 실행된다. 스크립트 전체가 원자적으로 실행되고(실행 중 다른 명령이 끼어들 수 없음), 결정적으로 — **`redis.call`의 반환값을 변수로 받아 분기할 수 있다.** MULTI가 못 하던 그것이다.

```lua
-- AFTER — check-then-act 가 서버 안에서 한 덩어리로
-- KEYS[1] = stock
local stock = tonumber(redis.call("GET", KEYS[1]) or "0")
if stock <= 0 then
    return 0                          -- 조회 결과를 보고 분기한다
end
redis.call("DECR", KEYS[1])
return stock - 1
```

WATCH와의 차이를 정확히 말하면 이렇다. **WATCH는 "확인과 행동 사이에 틈이 있다"는 것을 전제하고 그 틈에서 사고가 났는지를 사후에 감지한다. Lua는 확인과 행동을 서버 안에서 한 덩어리로 만들어 틈 자체를 없앤다.** 그래서 Lua에는 무효화도, 재시도도 없다.

세 도구를 한 줄씩 대면 이렇다.

| | MULTI/EXEC | WATCH + MULTI | Lua (EVAL) |
|---|---|---|---|
| 원자성 | 일괄 실행 원자 | 일괄 실행 원자 | 스크립트 전체 원자 |
| 중간 결과 분기 | **불가** | 클라이언트에서 (낡을 수 있음) | **서버 안에서 가능** |
| 충돌 시 | 해당 없음 | EXEC 무효 → **재시도 필요** | 충돌 자체가 없음 |
| 왕복 | 명령 수만큼 큐잉 왕복* | +WATCH/GET 왕복 × 재시도 횟수 | **1회** |
| 실패 모드 | 부분 실패(롤백 없음) | 재시도 폭풍 | 긴 스크립트 = 전역 블로킹 |

*파이프라인과 함께 쓰면 큐잉 왕복은 묶을 수 있다 — MULTI와 파이프라인은 별개 개념이다(§4 꼬리질문).

그래서 실무 기본값이 Lua다. 분산 락의 소유자 검증 해제([분산 락의 함정](16-distributed-lock-pitfalls-redlock.md) §2-2), 선착순 쿠폰의 중복+초과 판정([선착순 쿠폰 설계](17-flash-sale-coupon-issuance-design.md) §2), 레이트 리미터의 카운트+만료 갱신 — 전부 "조회하고 조건 보고 갱신"이라 Lua의 자리다.

### 3-2. Lua의 비용 — 원자성의 재료는 "전원 정지"다

Lua가 원자적인 이유는 마법이 아니다. **실행 중 싱글 스레드가 그 스크립트만 붙잡고 있기 때문이다.** 원자성을 만들어 내는 방법이 "다른 일을 아무것도 하지 않는 것"이라는 뜻이다.

그러니 대가도 거기서 나온다. **스크립트가 도는 동안 Redis 전체가 다른 요청을 처리하지 못한다.** 그 스크립트와 무관한 키를 조회하는 다른 서비스의 요청도, 세션 조회도, 전부 줄을 서서 기다린다. `SMEMBERS`나 `KEYS` 같은 O(N) 명령이나 큰 루프가 든 스크립트 하나가 전 서비스의 캐시 응답을 세운다 — `KEYS` 금지와 정확히 같은 뿌리의 문제다.

규율은 두 가지다. **스크립트는 O(1)~O(logN) 명령 몇 개로 짧게** 유지하고, **무거운 계산은 스크립트 밖(애플리케이션)에서 끝내고 판정·갱신만 서버 안으로** 가져간다.

이 블로킹 비용과 그 운영 대응은 [Lua 스크립트와 원자성](22-lua-script-atomicity.md)에서 더 깊게 다룬다. 여기서는 **"Lua를 기본값으로 고르되 그 원자성이 전역 블로킹으로 지불된다는 것을 안다"**까지가 이 문항의 몫이다.

운영 관점 주의점 두 가지를 더 얹으면 답이 단단해진다. **(가산점 포인트)**

- **Cluster에서는 스크립트가 접근할 키를 반드시 `KEYS[]` 인자로 선언**해야 하고, 그 키들이 **같은 해시 슬롯**에 있어야 한다(해시 태그 `{...}`로 묶는다). 클러스터는 키를 슬롯 단위로 여러 노드에 나눠 두는데, 한 노드가 자기가 갖고 있지 않은 키를 건드릴 수는 없기 때문이다. MULTI도 마찬가지로 Cluster에서는 같은 슬롯 키끼리만 가능하다 — **"인프라 확장이 애플리케이션 코드를 바꾸는" 대표 사례**다.
- 매번 스크립트 원문을 보내는 대신 **`EVALSHA`(스크립트 해시로 호출)**를 쓰되, 서버 재시작 등으로 스크립트 캐시가 비어 `NOSCRIPT` 에러가 오면 EVAL로 재적재하는 폴백이 클라이언트 라이브러리에 필요하다(대부분 내장돼 있다).

## 4. 꼬리질문 대비 포인트

### "MULTI 실행 중 한 명령이 실패하면 앞의 명령은 롤백되나요?"

안 된다. 다만 **에러 시점으로 나눠 답해야** 정확하다(1-2 상세).

**큐잉 시점 에러**(문법 오류, 존재하지 않는 명령)는 Redis가 명령을 큐에 넣기 전에 걸러 내고 트랜잭션을 오염 표시하므로, `EXEC` 자체가 `EXECABORT`로 거부되어 **전체가 실행되지 않는다.** 이건 롤백이 아니라 애초에 실행하지 않은 것이다.

**실행 시점 에러**(타입 불일치 등)는 그 명령만 결과 배열에 에러로 표시되고 **앞뒤 명령은 실행된 채 남는다.** 이쪽이 "롤백이 없다"의 실체다.

Redis가 롤백을 구현하지 않은 것은 못 해서가 아니라 선택이다. 공식 입장은 "실행 시점 에러는 대개 잘못된 타입에 잘못된 명령을 건 프로그래밍 오류이니 개발 중에 잡아라"이고, 롤백 기능을 넣지 않는 대가로 단순함과 속도를 얻었다. 그래서 **MULTI 블록은 실패할 수 있는 명령이 없도록 설계하는 것이 규율**이다.

### "WATCH한 키를 나 말고 아무도 안 바꿨는데 EXEC가 nil이 나올 수 있나요?"

있다. **WATCH는 "값이 달라졌는가"가 아니라 "그 키에 쓰기가 일어났는가"를 보기 때문이다**(2-4 상세).

두 방향의 사례를 들면 좋다.

**값이 제자리로 돌아와도 무효화된다.** 100 → 200 → 100으로 되돌아오면 최종 값은 내가 읽은 값과 같지만, 그 사이 쓰기가 두 번 일어났으므로 EXEC는 무효화된다. 같은 값으로 덮어쓴 경우(`SET stock 100`)도 마찬가지다. 이것이 **ABA 문제**를 안전한 쪽으로 처리하는 방식이다 — 값 비교로 판정하면 A → B → A를 "아무 일 없었음"으로 오판하게 되므로, 쓰기 발생 여부라는 더 보수적인 기준을 쓴다.

**아무도 명령을 보내지 않아도 무효화될 수 있다.** 감시 중인 키가 **TTL 만료로 삭제**되는 것도 변경으로 취급될 수 있다. 우리 애플리케이션은 아무것도 안 했는데 EXEC가 nil이 되는 경우다.

즉 판정 기준이 **"값의 동일성"이 아니라 "키에 대한 쓰기 발생"**임을 아는지 확인하는 질문이다. 그리고 이것이 결함이 아니라 **놓치는 것보다 과잉 실패가 낫다는 안전 쪽으로 기운 설계**라는 해석까지 붙이면 답이 완성된다. 실무적 함의는 하나 — **EXEC가 nil이면 "진짜 충돌"과 "과잉 실패"를 구분하려 하지 말고 그냥 재시도한다.**

### "Lua 스크립트가 실행 중에 너무 오래 걸리면 어떻게 하나요?" (시니어 변별 포인트)

일정 시간이 지나면 Redis는 다른 클라이언트에게 BUSY 에러를 응답하기 시작하지만 **스크립트 자체는 계속 돈다** — 원자성 때문에 중간에 함부로 끊을 수 없어서다. 여기서 이미 "원자성이 발목을 잡는다"는 구조가 드러난다.

이때 개입 수단이 갈린다.

- 스크립트가 **아직 쓰기를 하지 않았다면** `SCRIPT KILL`로 중단할 수 있다. 아무것도 안 바꿨으니 없던 일로 해도 원자성이 안 깨진다.
- **이미 쓰기를 시작했다면** 중단하는 순간 부분 실행 상태가 남는다. 그건 원자성 위반이므로 Redis는 `SCRIPT KILL`을 거부한다. 남는 선택지는 사실상 서버 강제 종료뿐이고, 그러면 그 시점까지의 쓰기가 어중간하게 남는다 — **사고다.**

그래서 방어는 사후 개입이 아니라 **사전 규율**이다. 짧은 스크립트, O(1)~O(logN) 명령만 사용, 스테이징에서 슬로우로그 확인. **"원자성은 공짜가 아니라 블로킹으로 지불한다"**는 문장으로 정리하면 좋다.

### "파이프라인과 MULTI는 뭐가 다른가요?"

**축이 다르다.** 둘 다 "여러 명령을 묶는다"처럼 보여서 헷갈리지만, 해결하는 문제가 서로 무관하다.

**파이프라인은 네트워크 최적화**다. 여러 명령을 응답을 기다리지 않고 한 번에 보내 **왕복 횟수를 줄인다.** 명령들 사이에 다른 클라이언트의 명령이 끼어들 수 있다 — **원자성은 없다.**

**MULTI는 원자성 장치**다. 끼어들기를 막지만 **왕복을 줄여 주지는 않는다.** 명령 하나하나가 `QUEUED` 응답을 받으며 왕복하기 때문이다.

정리하면 이렇다.

| | 해결하는 문제 | 왕복 | 끼어들기 |
|---|---|---|---|
| 파이프라인 | 네트워크 지연 | 줄어듦 | 가능 |
| MULTI/EXEC | 끼어들기 | 안 줄어듦 | 불가 |

그래서 "원자적일 필요는 없고 빠르게 여러 개"면 파이프라인(또는 `MGET`), "반드시 한 덩어리"면 MULTI나 Lua다. 그리고 **둘은 배타적이지 않아 섞어 쓸 수 있다** — 파이프라인으로 MULTI 블록 전체를 한 번에 전송하면 원자성과 왕복 절감을 동시에 얻는다.

### "RDB 트랜잭션의 ACID 기준으로 MULTI/EXEC를 평가하면?" (시니어 변별 포인트)

- **A(원자성)**: 절반만 — "전부 실행"은 보장하지만 "아니면 전부 취소"(롤백)가 없다.
- **C(일관성)**: 제약 개념 자체가 없으므로 애플리케이션 책임. Redis에는 외래 키도 체크 제약도 없다.
- **I(격리성)**: 싱글 스레드 일괄 실행이라 **가장 강하게** 보장된다 — 끼어들기 자체가 불가능하니 격리 수준 논의가 필요 없다. RDB에서 READ COMMITTED니 REPEATABLE READ니 고민하는 문제가 Redis에는 없다.
- **D(내구성)**: 트랜잭션과 무관하게 영속화 설정(RDB/AOF, fsync 정책)이 결정하며 EXEC 성공이 디스크 기록을 의미하지 않는다.

"같은 단어, 다른 보장"을 이렇게 축별로 해부해 보이면 — 그리고 **"그래서 Redis에서 트랜잭션이라는 말을 들으면 나는 격리된 일괄 실행으로 번역해 듣는다"**로 맺으면 — 이 문항의 출제 의도에 정면으로 답한 것이 된다.

---

## 한 줄 요약

MULTI/EXEC는 **롤백도, 중간 결과 분기도 없는 "격리된 일괄 실행"** 일 뿐이라(큐잉 시점 에러는 전체 취소지만 실행 시점 에러는 그 명령만 실패하고 나머지는 확정된다) check-then-act를 표현할 수 없고, 그 틈은 **WATCH**(값이 아니라 "쓰기 발생"으로 판정하는 낙관적 무효화 + 재시도, 그리고 커넥션 단위 상태라 `SessionCallback` 같은 장치가 필요)나 **Lua**(서버 안에서 조회→분기→갱신을 원자로, 왕복 1회, 재시도 없음)가 메우며 — 경합이 심하면 WATCH는 재시도 폭풍이 되므로 실무 기본값은 Lua이되 **그 원자성의 대가는 스크립트가 도는 동안 싱글 스레드 전체가 멈춘다는 것**이므로, 스크립트를 짧게 유지하는 규율까지 말해야 답이 완성된다.
