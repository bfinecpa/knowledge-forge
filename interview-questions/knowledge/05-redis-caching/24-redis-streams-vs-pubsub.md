# Redis Streams vs Pub/Sub — "유실 허용 여부"라는 축으로 메시징 도구 고르기

> 핵심 관전 포인트: **Pub/Sub은 저장하지 않는 실시간 방송이다 —
> 메시지는 그 순간 연결돼 있는 구독자에게만 전달되고, 구독자가 없거나
> 연결이 끊겨 있으면 그냥 사라진다(at-most-once). Streams는
> append-only 로그다 — 메시지가 ID와 함께 저장되고, 소비자가 나중에
> 붙어도 따라 읽을 수 있으며, 소비자 그룹 + ACK로 "처리 완료까지
> 추적"하는 at-least-once 전달이 가능하다. 그래서 선택 기준은 기능이
> 아니라 요구사항이다: 유실돼도 되는 실시간 신호(캐시 무효화 전파,
> 라이브 알림)는 Pub/Sub, 유실되면 안 되는 작업(주문 이벤트, 작업 큐)은
> Streams — 그리고 규모·보존이 커지면 Kafka로 넘어가는 경계까지
> 그릴 수 있어야 한다.**

---

## 0. 질문 + 의도

**질문**: "Redis Streams와 Pub/Sub의 차이는? 각각 어떤 상황에 적합한가요?"

**출제 의도**: pub/sub은 구독자가 없던 순간의 메시지가 그냥 사라진다는
유실 특성을 아는지 — "유실 허용 여부"라는 요구사항 축으로 기능을
고르는 판단력을 보며, 메시징 요구가 커졌을 때 Kafka(6장)와 선을 긋는
경계 감각도 함께 확인한다.

## 1. 근본 차이 — 방송이냐, 로그냐

### Pub/Sub = 라디오 방송

PUBLISH된 메시지는 **어디에도 저장되지 않고**, 그 순간 채널을
구독(SUBSCRIBE) 중인 클라이언트들에게 밀어넣어진 뒤 사라진다.
라디오와 같다 — 방송 시점에 주파수를 맞추고 있던 사람만 듣고,
지나간 방송을 다시 들을 방법은 없다.

- 구독자가 0명이면 메시지는 **그 자리에서 소멸**한다.
- 구독자의 연결이 잠깐 끊겨 있던 사이(재배포, 네트워크 흔들림,
  Redis 페일오버)의 메시지도 **소멸**한다. 재전달이 없다.
- 전달 보장: **at-most-once** (최대 한 번 — 즉, 0번일 수 있다).
- ACK도, 소비 위치(offset) 개념도 없다. "누가 어디까지 읽었나"를
  아무도 모른다.

### Streams = 추가 전용 로그(append-only log)

XADD로 넣은 메시지는 **자료구조로 저장**되고, 시간 기반의 고유
ID(`1726123456789-0` 형태)가 붙는다. 소비자는 원하는 위치부터
읽는다 — 나중에 접속해도 쌓여 있는 메시지를 따라 읽을 수 있고,
같은 메시지를 여러 번 다시 읽을 수도 있다. Kafka의 로그 모델을
Redis 자료구조 하나로 축소해 담은 것에 가깝다.

- 메시지가 남아 있으므로 **소비자 부재·단절 = 유실**이 아니다.
- **소비자 그룹(consumer group)**: 그룹 안의 여러 소비자가 메시지를
  나눠 받아 병렬 처리(경쟁 소비)하고, 그룹별로 "어디까지 전달했나"를
  Redis가 기록한다.
- **ACK와 PEL(Pending Entries List)**: 소비자에게 전달됐지만 아직
  XACK되지 않은 메시지는 "미처리 목록"에 남는다. 소비자가 처리 중
  죽어도 그 메시지는 pending으로 남아 있어, 다른 소비자가
  XAUTOCLAIM으로 가져가 재처리할 수 있다 → **at-least-once** 전달.
- 무한히 쌓이면 메모리를 먹으므로 **트리밍(MAXLEN/MINID)**으로
  길이를 제한한다.

### 비교 한눈에

| 축 | Pub/Sub | Streams |
|---|---|---|
| 저장 | 없음 (즉시 소멸) | append-only 로그로 저장 |
| 구독자 부재/단절 시 | 유실 | 보존 — 나중에 따라 읽음 |
| 전달 보장 | at-most-once | at-least-once 가능 (ACK/PEL) |
| 소비 모델 | 전 구독자에 전부 방송 | 그룹 내 분배(경쟁 소비) + 그룹 간 방송 |
| 재처리/재조회 | 불가 | 가능 (ID로 범위 조회, XAUTOCLAIM) |
| 메모리 | 거의 안 씀 | 쌓인 만큼 사용 → 트리밍 필수 |

## 2. 코드로 보는 유실 시나리오 — 이 질문의 급소

```bash
# ❌ Pub/Sub: 구독자가 잠깐 없던 사이의 메시지
# [서버 B가 재배포로 15초간 구독 끊김]
PUBLISH order-events '{"orderId": 42, "status": "PAID"}'   # ← 이 메시지는
# B가 재접속해도 이 메시지를 받을 방법이 없다. 흔적조차 없다.
# "결제됐는데 후속 처리가 안 된" 주문 42는 아무도 모르게 누락된다.
```

```bash
# ✅ Streams: 같은 상황
XADD order-events * orderId 42 status PAID    # 로그에 저장됨 (ID 발급)

# B가 재접속 후 소비자 그룹으로 읽기 — 끊긴 동안 쌓인 것부터 이어서 온다
XREADGROUP GROUP order-workers consumer-b COUNT 10 STREAMS order-events >

# 처리 완료 확인 응답 — 이걸 보내야 "완료"로 기록된다
XACK order-events order-workers 1726123456789-0
# 처리 중 B가 죽으면? 메시지는 PEL(미처리 목록)에 남고,
# 다른 소비자가 XAUTOCLAIM으로 회수해 재처리한다. 누락이 구조적으로 안 생긴다.
```

면접에서 이 차이를 한 문장으로: **"Pub/Sub의 유실은 장애가 아니라
설계된 동작이다."** 이걸 모르고 주문·결제 이벤트를 Pub/Sub에 실으면,
평소엔 멀쩡하다가 재배포·페일오버 때마다 조용히 이벤트가 증발하는
찾기 어려운 버그가 된다.

## 3. 각각 적합한 상황 — 요구사항 축으로 고르기

### Pub/Sub이 맞는 곳: "지금 듣고 있는 사람에게만 의미 있는 신호"

- **캐시 무효화 전파** (2단 캐시의 L1 evict 브로드캐스트): 놓쳐도
  로컬 TTL이 안전망으로 받쳐주는, 유실 허용 설계의 대표.
- **실시간 알림/채팅의 팬아웃**: 접속 중인 사용자에게 지금 보여주는
  것이 목적 — 부재중 메시지는 어차피 DB 등 별도 저장소가 책임진다.
- **설정 리로드 신호** 같은 "다시 읽어라" 트리거.

공통점: **메시지 자체가 진실의 원본이 아니고**, 놓쳐도 다른
경로(TTL, DB 재조회)로 복구되는 구조가 뒤에 있다.

### Streams가 맞는 곳: "한 건도 잃으면 안 되는 작업"

- **작업 큐**: 이미지 처리, 메일 발송 — 소비자 그룹으로 워커에 분배,
  ACK로 완료 추적, 죽은 워커의 작업 재처리.
- **서비스 간 이벤트 전달**: 주문 생성 → 알림/정산 서비스가 각자의
  그룹으로 소비 (그룹이 다르면 같은 메시지를 각자 다 받는다).
- **최근 이벤트 버퍼**: 최근 N건을 ID 범위로 재조회하는 활동 피드,
  센서/로그 수집 버퍼.

공통점: 메시지가 곧 처리해야 할 **작업 그 자체**라서, "받았고 처리를
끝냈다"는 확인(ACK)까지 필요하다.

```java
// 판단 기준을 코드 리뷰 감각으로 옮기면:
// ❌ 유실되면 안 되는 도메인 이벤트를 Pub/Sub에
redisTemplate.convertAndSend("order-events", orderPaidEvent);
// 리뷰 코멘트: "구독 서비스 재배포 중의 결제 이벤트는 소멸합니다.
//              누락 감지 수단도 없습니다. Streams(또는 MQ)로 가야 합니다."

// ✅ 유실 허용 신호는 Pub/Sub이 오히려 정답 (가볍고 즉시)
redisTemplate.convertAndSend("cache-invalidation", "feature:" + key);
```

## 4. Kafka와의 선긋기 — Streams로 버티는 구간과 넘어가는 지점

Streams는 "Redis 안의 미니 Kafka"지만 같은 물건이 아니다.
**Streams로 충분한 구간**: 이미 Redis를 운영 중이고, 처리량이
Redis 한 벌로 감당되며, 메시지를 오래 보관할 필요가 없는(트리밍
전제) 가벼운 큐/이벤트 전달 — 브로커를 새로 도입하는 운영 비용
없이 얻는 실용적 선택이다.

**Kafka로 넘어가야 하는 신호**:

- **보존**: Streams는 메모리에 산다 — 길게·많이 보관할수록 비싸고,
  트리밍하면 리플레이 범위가 사라진다. 디스크 기반으로 장기 보존과
  전체 리플레이가 필요하면 Kafka.
- **처리량·확장**: 스트림 하나는 클러스터에서도 한 노드(한 슬롯)에
  산다. 파티션 병렬화로 수평 확장하는 규모라면 Kafka.
- **생태계**: 커넥터(CDC, 싱크), 스트림 처리, 스키마 관리 같은
  파이프라인 요구가 생기면 Kafka 생태계가 답이다.

"일단 Streams로 시작해 규모·보존 요구가 커지면 Kafka"가 아니라,
**처음부터 요구사항(보존 기간, 처리량, 리플레이)을 보고 고른다**고
말하는 편이 좋다 — 메시징 채널은 나중에 갈아타기 비싼 결정이다.

## 5. Streams 운영 주의점 (가산점 포인트)

- **트리밍 없으면 OOM 폭탄**: 스트림은 소비돼도 지워지지 않는다
  (Pub/Sub과 반대 방향의 함정). `XADD ... MAXLEN ~ 100000`처럼
  대략적(`~`) 길이 제한을 습관화 — 정확한 MAXLEN보다 `~`가 노드
  단위로 잘라 훨씬 싸다.
- **PEL 방치 = 좀비 메시지 누적**: ACK를 잊은 소비자, 죽은 소비자의
  pending이 쌓이면 메모리와 재처리 지연의 원인 — XPENDING 모니터링과
  XAUTOCLAIM 기반 회수 루틴이 운영의 일부다.
- **at-least-once는 중복을 뜻한다**: 재처리 과정에서 같은 메시지가
  두 번 올 수 있으므로 소비자는 멱등하게 짜야 한다 (처리 완료 기록을
  키로 중복 스킵 등).

## 6. 꼬리질문 대비 포인트

### "구독자가 재접속하면 끊겨 있던 동안의 메시지를 받을 수 있나요?"

Pub/Sub은 **불가능하다.** 메시지가 어디에도 저장되지 않았으므로
"끊긴 동안의 메시지"라는 것 자체가 존재하지 않는다 — 이 유실은
버그가 아니라 Pub/Sub의 설계다. Streams는 가능하다 — 메시지가 ID와
함께 로그로 남아 있고, 소비자 그룹이 "어디까지 전달했는지"를
기억하므로 재접속한 소비자는 이어서 읽는다. 이 한 가지 차이가 두
기능의 용도를 가른다.

### "Streams에서 소비자가 메시지를 받고 처리 중에 죽으면 그 메시지는 어떻게 되나요?"

전달됐지만 XACK되지 않은 메시지는 **PEL(Pending Entries List)**에
그 소비자 앞으로 남는다. 다른 소비자(또는 복구 프로세스)가
XPENDING으로 오래 방치된 메시지를 찾고 XAUTOCLAIM으로 소유권을
가져와 재처리한다 — 이것이 at-least-once의 구현 장치다. 따라서
같은 메시지가 두 번 처리될 수 있으므로 **소비자 멱등성**이 세트로
필요하다는 것까지 붙이면 완성된 답이다.

### "그럼 Kafka 안 쓰고 전부 Redis Streams로 하면 되지 않나요?" (시니어 변별 포인트)

규모와 보존이 선이다. Streams는 **메모리**에 살아서 장기 보존이
비싸고, 트리밍하는 순간 리플레이 범위를 포기한다. 스트림 하나의
처리량은 결국 한 노드의 한계에 묶이고, 파티션 재분배·컨슈머 리밸런싱·
커넥터 생태계 같은 대규모 파이프라인 장치도 없다. 반대로 "이미 있는
Redis로, 가벼운 작업 큐 하나"에 Kafka 클러스터를 새로 들이는 것도
과잉이다. 즉 정답은 도구 우열이 아니라 **요구사항(보존 기간, 처리량,
리플레이 필요, 운영 여력)이 정하는 경계**를 말하는 것 — 어느 쪽이든
"왜 이 규모에선 이쪽인가"를 논증하는 게 시니어 답변이다.

### "2단 캐시의 무효화 전파에는 둘 중 뭘 쓰는 게 맞나요?"

**Pub/Sub.** 무효화 신호는 유실돼도 로컬 TTL이라는 안전망이 뒤에
있는 대표적 유실 허용 설계라, 저장·ACK의 무게가 필요 없고 지연이
가장 짧은 Pub/Sub이 적격이다. 오히려 Streams로 하면 모든 인스턴스가
같은 메시지를 받아야 하는 방송 요구와 소비자 그룹의 분배 모델이
안 맞고(인스턴스마다 그룹을 따로 파야 함), 트리밍·PEL 관리 부담만
는다. "보장이 센 도구가 항상 좋은 게 아니라 요구에 맞는 도구가
좋다"는 판단력을 보여줄 기회다.

### "Pub/Sub에서 느린 구독자는 어떻게 되나요?" (가산점 포인트)

Pub/Sub은 서버가 구독자별 출력 버퍼에 메시지를 밀어넣는 push
모델이라, 소비가 느린 구독자는 버퍼가 계속 부푼다. Redis는
`client-output-buffer-limit`(pubsub 클래스) 한도를 넘긴 구독자의
**연결을 끊어버린다** — 서버 메모리를 지키는 대신 그 구독자는 끊긴
동안의 메시지까지 유실한다. 반면 Streams는 소비자가 자기 속도로
당겨 읽는 pull 모델이라 느린 소비자가 있어도 메시지는 로그에 남는다
(대신 스트림 길이·PEL이 자라는 것으로 비용이 이동한다).

## 한 줄 요약

Pub/Sub은 저장 없이 지금 연결된 구독자에게만 던지고 사라지는
at-most-once 방송이고 Streams는 ID로 저장되고 소비자 그룹 + ACK/PEL로
처리 완료까지 추적하는 at-least-once 로그라서 — 유실돼도 안전망이
있는 신호(캐시 무효화, 실시간 알림)는 Pub/Sub, 한 건도 잃으면 안 되는
작업·이벤트는 Streams를 고르되, 장기 보존·대규모 처리량·리플레이가
필요해지는 지점부터는 Kafka와의 경계를 긋는 것까지가 이 질문의 답이다.
