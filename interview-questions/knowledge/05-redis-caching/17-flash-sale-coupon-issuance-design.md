# 선착순 쿠폰 10만 장 설계 — 판정은 Redis 원자 연산으로, 원장은 DB로

> 핵심 관전 포인트: **역할을 둘로 쪼개는 것이 설계의 골격이다 — Redis는 "발급 가능/불가"를 초고속으로 판정하는 판정기, DB는 발급 사실을 보관하는 원장(최종 진실).** ① **정확성**: 중복 발급은 사용자 Set(`SADD`의 0/1 반환)으로, 초과 발급은 발급 수 카운트로 막되, "확인하고 발급"이라는 두 동작을 **Lua 스크립트 하나로 원자화**한다 — Set 하나가 중복 방지와 카운트(`SCARD`)를 겸하면 카운터 불일치 여지도 사라진다. **분산 락은 쓰지 않는다** — Redis 명령 자체가 원자적이라 잠글 대상이 없고, 락은 병목과 실패 모드만 추가한다. ② **내구성**: Redis는 어떤 설정으로도 유실 가능성이 남으므로(AOF everysec의 마지막 ~1초, 비동기 복제 failover) **발급 사실을 이벤트로 흘려 DB에 비동기 반영**하고, DB의 유니크 제약을 최종 방어선으로 삼는다. Redis 데이터가 유실되면 **발급을 멈추고(fail-closed) DB 원장에서 Set을 재구축한 뒤 재개**한다.

---

## 0. 질문 + 의도

**질문**: "선착순 쿠폰 발급 10만 건을 Redis로 설계해보세요. 정확성(중복/초과 발급 방지)과 내구성을 어떻게 보장하나요?"

**출제 의도**: rationale은 이렇게 적고 있다 — "정확성(원자적 카운트), 내구성
(Redis 유실 시), 공정성, DB 반영의 비동기화까지 — 한 문제에 이 섹션 전체 지식을
조합해야 한다. **지식의 보유가 아니라 조합 능력을 보는 설계 질문.**" 즉 채점
지점은 개별 명령어가 아니라 ① 경합 지점을 원자 연산으로 접는 판단 ② "Redis는
유실될 수 있다"는 전제에서 출발하는 내구성 설계 ③ 판정 경로와 영속화 경로를
분리하고 그 사이의 실패를 처리하는 구성력이다.

## 1. 왜 DB 직행이 안 되는가 — 문제의 좌표부터

쿠폰 10만 장 이벤트에 요청은 10만 건이 아니라 **수십·수백만 건**이 수 초~수 분에
몰린다. 이것을 DB로 직접 받으면:

```sql
-- 모든 요청이 이 한 행을 두드린다
UPDATE coupon_event SET issued = issued + 1
WHERE  id = 1 AND issued < 100000;
```

원자성은 지켜지지만 **단일 행 락에 전 요청이 직렬화**된다. 행 락을 기다리는
트랜잭션이 커넥션을 붙잡은 채 줄을 서므로, 커넥션 풀이 마르고 **쿠폰과 무관한
API까지 함께 죽는다**(락 대기 = 커넥션 점유 문제.
[낙관적 vs 비관적 락](../03-jpa-orm/10-optimistic-vs-pessimistic-lock.md) §3-2와
같은 구조다). 그래서 **경합 판정을 메모리(Redis)로 옮기고, DB에는 정리된 결과만
흘려보내는** 구조가 필요하다. 이 문제의 본질은 "빠른 저장소 선택"이 아니라
**경합 지점과 영속 지점의 분리**다.

## 2. 정확성 — 중복과 초과를 하나의 원자 단위로 막는다

### 2-1. 나눠서 하면 반드시 새는 이유

```
❌ BEFORE — 확인과 발급이 여러 문장: 문장 사이마다 다른 요청이 끼어든다
GET  coupon:count            → 99,999 (아직 남았네)
SISMEMBER coupon:users u1    → 0 (처음이네)
   ← 이 틈에 다른 요청 수백 개가 같은 판정을 통과
INCR coupon:count            → 100,001... 초과 발급 ✗
SADD coupon:users u1
```

check-then-act를 여러 문장으로 쓰면 그 사이가 뚫린다 — DB든 Redis든 동일한
원리다. Redis가 싱글 스레드라 **명령 하나**는 원자적이지만, **명령 사이**는
아무것도 보장하지 않는다.

### 2-2. 원자화 — Set 하나로 중복과 카운트를 겸하게

발급받은 사용자 Set 하나면 두 조건을 다 판정할 수 있다. **`SCARD`(집합 크기)가
곧 발급 수**이므로 별도 카운터와 어긋날 가능성 자체가 없다. 이 판정을 Lua
스크립트로 묶으면 Redis가 통째로 원자 실행한다.

```lua
-- ✅ AFTER — 판정 전체가 한 덩어리: 실행 중 다른 명령이 끼어들 수 없다
-- KEYS[1] = coupon:{1}:users   ARGV[1] = userId   ARGV[2] = 100000
if redis.call("SISMEMBER", KEYS[1], ARGV[1]) == 1 then
    return -1                                  -- 이미 발급받음 (중복)
end
if redis.call("SCARD", KEYS[1]) >= tonumber(ARGV[2]) then
    return 0                                   -- 소진 (초과 방지)
end
redis.call("SADD", KEYS[1], ARGV[1])
return 1                                       -- 발급 성공
```

- 왜 `MULTI/EXEC`가 아니라 Lua인가 — MULTI는 **중간 조회 결과로 분기할 수
  없다.** check-then-act에는 WATCH 재시도나 Lua가 필요하고, 경합이 극심한 이
  시나리오에서 WATCH는 재시도 폭풍이 되므로 Lua가 정답이다. 상세 비교는
  [MULTI/EXEC와 WATCH vs Lua](27-multi-exec-watch-vs-lua.md).
- 키를 `coupon:{1}:users`처럼 해시 태그로 묶어 두면 Cluster 전환 시에도
  스크립트의 키들이 같은 슬롯에 있어 깨지지 않는다. **(가산점 포인트)**
- 10만 멤버 Set은 big key 걱정 범위가 아니고, `SISMEMBER`/`SADD`/`SCARD` 모두
  O(1)이라 스크립트가 싱글 스레드를 붙잡는 시간도 상수다.

**분산 락으로 감싸지 않는 이유를 명시적으로 말해야 한다**: 위 스크립트 자체가
원자라 **잠글 틈이 존재하지 않는다.** 락을 추가하면 처리량은 락 왕복만큼
떨어지고, TTL 만료·해제 누락이라는 실패 모드만 얹는다
([분산 락의 함정](16-distributed-lock-pitfalls-redlock.md) §5 — "락을 꺼내기 전에
원자 연산으로 못 푸는지부터"). "동시성 제어 = 락"이라는 반사작용을 끊는 것이
이 문항의 변별 지점 중 하나다.

## 3. 내구성 — "Redis는 유실될 수 있다"에서 출발한다

### 3-1. Redis 단독으로는 왜 부족한가

발급 판정이 Redis 메모리에만 있다면, 유실 시나리오마다 사고가 다르게 난다.

- **RDB 스냅샷만**: 마지막 스냅샷 이후의 발급 기록이 통째로 사라진다.
- **AOF `everysec`**: 크래시 시 **마지막 약 1초**의 발급이 사라질 수 있다.
  1초면 이 트래픽에서는 수천 건이다.
- **AOF `always`**: 유실은 최소화되지만 매 쓰기 fsync로 처리량이 크게 떨어져
  "Redis로 받는 이유"가 약해진다.
- **복제 + failover**: Redis 복제는 비동기다. 마스터가 죽고 레플리카가 승격되면
  **복제가 못 따라간 최신 발급 기록이 사라진다.** AOF 설정과 무관하게 남는
  구멍이다.

유실의 결과를 구체화하면: Set이 과거로 돌아가 `SCARD`가 줄어든 상태에서 발급이
계속되면 **초과 발급**, 이미 받은 사용자가 Set에서 사라지면 **중복 발급**이다.
"AOF 켰으니 안전"이 아니라 **유실이 곧 정확성 붕괴로 직결되는 구조임을 인정하는
것**이 내구성 설계의 출발점이다.

### 3-2. 구조로 푼다 — 판정과 원장의 분리

```
사용자 ──▶ API ──▶ ① Lua 판정 (성공/중복/소진)          ... 동기, ms 단위
                    └ 성공 시: ② 발급 이벤트 적재
                                  │
                    컨슈머 ◀──────┘                      ... 비동기
                    ③ DB INSERT coupon_issue
                       UNIQUE (coupon_event_id, user_id) ← 최종 방어선
```

- **① 판정**: §2의 Lua. 사용자는 여기서 바로 "발급 완료" 응답을 받는다.
- **② 이벤트 적재**: 발급 사실을 큐(Kafka 또는 Redis Streams)에 남긴다.
  Redis Streams를 쓰면 **판정 Lua 안에서 `XADD`까지 한 덩어리로** 묶을 수 있어
  "판정은 됐는데 이벤트가 안 남는" 틈이 사라진다는 장점이 있고, 대신 내구성이
  다시 Redis에 묶인다는 한계가 있다. Kafka를 쓰면 내구성은 강해지지만 "Lua 성공
  후 발행 실패" 틈이 생기므로 발행 재시도와 ③의 멱등성이 그 틈을 메운다.
- **③ 원장 기록**: 컨슈머가 DB에 INSERT. **`(coupon_event_id, user_id)` 유니크
  제약**이 있으므로 이벤트가 중복 소비돼도(재시도, 유실 후 재구축) 중복 발급으로
  이어지지 않는다 — 멱등한 소비. 락이 아니라 **제약이 최종 진실을 지킨다.**

이 구조에서 각 계층의 실패가 어떻게 흡수되는지가 답의 핵심이다:

- **컨슈머/DB가 일시 장애** → 이벤트는 큐에 남아 있으므로 복구 후 이어서 처리.
  발급 응답은 이미 나갔지만 원장 반영이 늦을 뿐, 잃지 않는다.
- **Redis 유실(failover 포함)** → **발급을 즉시 멈춘다(fail-closed).** 소진
  플래그를 확인할 수 없는 상태에서 발급을 계속하는 것이 최악이다. DB 원장에서
  `SELECT user_id`로 **Set을 재구축**하고(10만 건 `SADD`는 수 초 작업), 재개한다.
  재구축 동안 큐에 남은 미반영 이벤트가 있으면 그것까지 반영 후 재개해야
  중복·초과가 안 생긴다.
- **그래도 새어 나간 소량의 초과 발급**(유실 직전 판정분) → DB 원장 기준으로
  발급 수를 재검증하고, 소진 초과분은 비즈니스 결정(그대로 인정 or 안내 후
  회수)으로 처리한다. **기술로 0으로 만들 수 없는 잔여 위험을 식별하고 처리
  정책을 미리 정해두는 것**까지가 설계다. (가산점 포인트)

### 3-3. 트래픽 앞단 방어 — 소진 이후의 수백만 요청

10만 번째 발급 이후에도 요청은 계속 온다. 전부 Lua까지 보낼 필요가 없다.

- 소진 순간 별도 플래그 키(`coupon:{1}:soldout`)를 세우고, API 서버는 이 값을
  **로컬 캐시(수 초 TTL)** 로 들고 즉시 "소진" 응답 — Redis 왕복조차 생략.
- 유입 자체가 감당 밖이면 앞단에 **대기열**(진입 토큰 발급)을 두어 초당 유입을
  평탄화한다. 선착순의 "순서"가 대기열 진입 시점으로 옮겨질 뿐, 사용자 경험은
  오히려 예측 가능해진다.

## 4. 꼬리질문 대비 포인트

### "왜 분산 락으로 안 감싸나요?"

잠글 틈이 없기 때문이다. 경합 지점(중복 확인 + 카운트 + 기록)이 이미 Lua 한
덩어리로 원자화되어 있고, Redis는 싱글 스레드라 스크립트 실행 중 다른 명령이
끼어들 수 없다. 락을 얹으면 얻는 것 없이 락 왕복 지연과 TTL 만료·오해제라는
실패 모드([분산 락의 함정](16-distributed-lock-pitfalls-redlock.md))만 추가된다.
분산 락이 정당한 건 여러 시스템에 걸친 절차를 조정할 때이지, 단일 Redis 안의
원자 연산으로 끝나는 문제가 아니다.

### "failover로 카운터가 과거로 돌아갔다면 어떻게 감지하고 무엇부터 하나요?" (시니어 변별 포인트)

감지: ① failover 이벤트 자체를 알람으로 받고(Sentinel/managed 서비스 알림),
② DB 원장 건수와 `SCARD`의 주기적 대사(reconciliation)로 어긋남을 잡는다.
대응 순서는 **멈춤 → 재구축 → 재개**다. 먼저 발급을 fail-closed로 멈추고
(플래그 키 또는 애플리케이션 스위치), 큐에 남은 미반영 이벤트를 DB까지 소진시킨
뒤, DB 원장으로 Set을 재구축하고 재개한다. 순서를 지키지 않으면(재구축을 먼저
하면) 큐에만 있고 DB에 없는 발급이 Set에서 빠져 중복 발급 여지가 생긴다.
"장애 시 절차"를 시간 순서로 말할 수 있는지가 운영 성숙도의 지표다.

### "컨슈머가 DB INSERT에 실패하면 사용자는 이미 '발급 완료'를 봤는데요?"

이벤트가 큐에 남아 있으므로 **재시도로 결국 반영된다**(at-least-once). 재시도로
같은 이벤트가 두 번 처리되는 경우는 유니크 제약이 흡수한다 — 그래서 소비가
멱등해야 한다. 계속 실패하는 독약 이벤트는 DLQ로 빼고 알람을 울린다. 사용자
관점의 계약은 "판정 즉시 확정, 원장 반영은 지연 가능"이며, 쿠폰 **사용** 시점에
원장을 확인하므로 반영 지연이 길어지면 사용 실패로 드러난다 — 반영 지연(큐 lag)
자체를 모니터링 지표로 둔다.

### "10만 명이 같은 키를 치면 hot key 아닌가요? Cluster로 분산하면요?" (시니어 변별 포인트)

맞다, 구조적으로 hot key다 — 그리고 **Cluster는 해법이 아니다.** 같은 키는 해시
슬롯 하나, 즉 한 노드로만 간다. 그래서 순서가 이렇다: ① 먼저 **산수로 검증** —
O(1) 명령 몇 개짜리 Lua면 단일 노드로도 초당 수만 건 수준을 처리하므로, 앞단
방어(§3-3)로 유입을 깎으면 대부분 단일 키로 충분하다. ② 정말 초과하면 **카운터
샤딩** — 재고를 N조각(`coupon:{1}:shard:0~N`)으로 나눠 요청을 무작위 조각에
붙인다. 대신 "한 조각만 소진됐을 때의 처리"(다른 조각 재시도)와 중복 방지
Set의 분리 등 복잡도가 크게 오르므로, **필요가 증명되기 전에는 꺼내지 않는다.**

### "'선착순'인데 정말 먼저 요청한 사람이 먼저 받나요?"

엄밀한 전역 순서는 보장하지 않으며, **보장할 수 있는 시스템은 사실상 없다**는
것까지 말해야 한다. 사용자 단말~LB~서버~Redis 사이의 지연 편차 때문에 "버튼을
먼저 누른 순서"와 "Redis 도착 순서"는 다를 수 있다. 시스템이 보장하는 것은
**Redis에 도착한 순서대로의 공정한 직렬 처리**(싱글 스레드가 도착순 실행)다.
이 정의를 비즈니스와 합의해 두는 것이 분쟁을 막는 실무 답이고, 더 엄격한
공정성이 요구되면 대기열 진입 시각 기준으로 순서를 박제하는 설계로 옮긴다.

## 한 줄 요약

선착순 쿠폰의 정확성은 **"확인 후 발급"을 Lua 한 덩어리로 원자화한 판정기
(Set 하나가 중복 방지와 카운트를 겸함)** 가, 내구성은 **판정 즉시 이벤트로
흘려 DB 원장에 멱등하게 쌓는 비동기 경로와 유니크 제약이라는 최종 방어선**이
지키며 — 분산 락은 잠글 틈이 없어 불필요하고, Redis 유실 시에는 **멈추고(fail-
closed) 원장에서 재구축 후 재개**한다는 절차까지 말해야 설계가 완성된다.
