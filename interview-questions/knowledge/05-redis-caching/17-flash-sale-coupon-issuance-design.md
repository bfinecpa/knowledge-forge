# 선착순 쿠폰 10만 장 설계 — 판정은 Redis 원자 연산으로, 원장은 DB로

> 핵심 관전 포인트: **역할을 둘로 쪼개는 것이 설계의 골격이다 — Redis는 "발급 가능/불가"를 초고속으로 판정하는 판정기, DB는 발급 사실을 보관하는 원장(최종 진실).** ① **정확성**: 중복 발급은 사용자 Set(`SADD`의 0/1 반환)으로, 초과 발급은 발급 수 카운트로 막되, "확인하고 발급"이라는 두 동작을 **Lua 스크립트 하나로 원자화**한다 — Set 하나가 중복 방지와 카운트(`SCARD`)를 겸하면 카운터 불일치 여지도 사라진다. **분산 락은 쓰지 않는다** — Redis 명령 자체가 원자적이라 잠글 대상이 없고, 락은 병목과 실패 모드만 추가한다. ② **내구성**: Redis는 어떤 설정으로도 유실 가능성이 남으므로(AOF everysec의 마지막 ~1초, 비동기 복제 failover) **발급 사실을 이벤트로 흘려 DB에 비동기 반영**하고, DB의 유니크 제약을 최종 방어선으로 삼는다. Redis 데이터가 유실되면 **발급을 멈추고(fail-closed) DB 원장에서 Set을 재구축한 뒤 재개**한다.

---

## 0. 질문 + 의도

**질문**: "선착순 쿠폰 발급 10만 건을 Redis로 설계해보세요. 정확성(중복/초과 발급 방지)과 내구성을 어떻게 보장하나요?"

**출제 의도**: rationale은 이렇게 적고 있다 — "정확성(원자적 카운트), 내구성 (Redis 유실 시), 공정성, DB 반영의 비동기화까지 — 한 문제에 이 섹션 전체 지식을 조합해야 한다. **지식의 보유가 아니라 조합 능력을 보는 설계 질문.**" 즉 채점 지점은 개별 명령어가 아니라 ① 경합 지점을 원자 연산으로 접는 판단 ② "Redis는 유실될 수 있다"는 전제에서 출발하는 내구성 설계 ③ 판정 경로와 영속화 경로를 분리하고 그 사이의 실패를 처리하는 구성력이다.

## 1. 왜 DB 직행이 안 되는가 — 문제의 좌표부터

### 1-1. 트래픽의 모양부터 본다

쿠폰 10만 장 이벤트에 들어오는 요청은 10만 건이 아니다. **수십만에서 수백만 건**이 수 초에서 수 분 안에 몰린다. 발급받지 못할 사람들도 전부 요청을 보내기 때문이고, 실패하면 다시 누르기 때문이다.

이 모양이 중요한 이유는, 이 문제의 부하가 **"10만 번의 쓰기"가 아니라 "수백만 번의 판정"**이라는 데 있다. 성공하는 요청보다 거절되는 요청이 훨씬 많고, 그 거절을 얼마나 싸게 처리하느냐가 설계의 절반을 차지한다.

### 1-2. DB로 직접 받으면 무너지는 메커니즘

가장 단순한 구현은 이렇게 생겼다.

```sql
-- 모든 요청이 이 한 행을 두드린다
UPDATE coupon_event SET issued = issued + 1
WHERE  id = 1 AND issued < 100000;
```

이 문장 자체는 옳다. `issued = issued + 1`과 `issued < 100000` 검사가 한 문장 안에 있으므로 초과 발급은 나지 않는다. PostgreSQL은 이 행에 배타 락을 걸고 갱신하며, 영향 행 수가 0이면 소진이라는 뜻이다. **정확성은 지켜진다.**

무너지는 것은 처리량이다. 같은 행을 갱신하려는 트랜잭션은 앞선 트랜잭션이 커밋할 때까지 그 행의 락을 기다린다. 즉 **모든 요청이 단일 행 락 위에서 한 줄로 직렬화된다.** 수백만 건이 한 줄로 서면 뒤쪽은 사실상 영원히 못 들어온다.

여기서 끝이 아니다. 진짜 사고는 다음 단계에서 난다.

```
요청 하나가 락을 기다린다
   └─ 그 트랜잭션이 DB 커넥션 하나를 붙잡은 채로 기다린다
        └─ 커넥션 풀(예: 50개)이 전부 쿠폰 요청에 점유된다
             └─ 주문 조회, 로그인, 상품 목록 API 가 커넥션을 못 얻는다
                  └─ 쿠폰과 아무 상관 없는 서비스 전체가 함께 죽는다
```

**락 대기가 커넥션 점유로 번지고, 커넥션 고갈이 전체 장애로 번진다.** 이것이 비관적 락을 트래픽 앞단에 두면 안 되는 이유이고([낙관적 vs 비관적 락](../03-jpa-orm/10-optimistic-vs-pessimistic-lock.md) 3-2절과 같은 구조다), 이 문제에서 DB 직행이 배제되는 진짜 근거다.

### 1-3. 그래서 구조는 "경합 지점과 영속 지점의 분리"다

해법의 방향은 "더 빠른 DB를 고른다"가 아니다. **경합이 일어나는 지점을 커넥션·디스크와 무관한 곳으로 옮기고, DB에는 이미 판정이 끝난 결과만 흘려보내는 것**이다.

```
경합 지점(판정)          →  Redis 메모리. 원자 연산 하나로 끝난다. 커넥션을 붙잡지 않는다.
영속 지점(원장 기록)     →  DB. 판정 결과만 비동기로 받아 쌓는다. 경합이 없다.
```

이 분리가 이 문제의 본질이다. "빠른 저장소를 골랐다"가 아니라 **"경합과 영속을 서로 다른 시스템에 배치했다"**로 말할 수 있어야 한다.

## 2. 정확성 — 중복과 초과를 하나의 원자 단위로 막는다

막아야 할 것은 둘이다. **중복 발급**(한 사람이 두 장 받는 것)과 **초과 발급**(총량이 10만 장을 넘는 것). 둘 다 "확인하고 발급"이라는 두 걸음 사이에서 새어 나간다.

### 2-1. 나눠서 하면 반드시 새는 이유

```
BEFORE — 확인과 발급이 여러 문장: 문장 사이마다 다른 요청이 끼어든다
GET  coupon:count            → 99,999 (아직 남았네)
SISMEMBER coupon:users u1    → 0 (처음이네)
   ← 이 틈에 다른 요청 수백 개가 같은 판정을 통과한다
INCR coupon:count            → 100,001... 초과 발급
SADD coupon:users u1
```

check-then-act를 여러 문장으로 쓰면 그 사이가 뚫린다 — DB든 Redis든 같은 원리다. **Redis가 싱글 스레드라 명령 하나는 원자적이지만, 명령과 명령 사이는 아무것도 보장하지 않는다.** 오히려 처리 속도가 빠른 만큼 그 틈에 더 많은 요청이 들어온다.

중복 발급 쪽만 떼어서 두 요청의 타임라인으로 보면 구멍이 선명해진다. 같은 사용자가 버튼을 두 번 눌렀거나, 클라이언트가 타임아웃으로 재시도한 상황이다.

```
시각   요청 X (u1)                  Set 의 실제 내용        요청 Y (u1, 같은 사용자)
t0     SISMEMBER users u1 → 0       { }
t1                                  { }                     SISMEMBER users u1 → 0
                                                            ← 아직 아무도 넣지 않았으므로 통과
t2     SADD users u1                { u1 }
t3                                  { u1 }                  SADD users u1  (이미 있으므로 변화 없음)
t4     "발급 완료" 응답                                       "발급 완료" 응답
       → 같은 사용자에게 쿠폰 두 장이 나갔다
```

문제의 위치를 정확히 말하면, **t0의 확인 결과를 t2까지 믿었다는 것**이다. 확인은 그 순간의 사실일 뿐 다음 순간을 보장하지 않는다.

### 2-2. `SADD`의 반환값 — 확인과 선점이 한 명령 안에서 끝난다

여기서 이 설계의 급소가 나온다. **`SADD`는 실제로 새로 추가된 멤버 수를 돌려준다.**

```
SADD coupon:{1}:users u1   → 1   (없었다. 이번에 내가 넣었다 = 내가 선점했다)
SADD coupon:{1}:users u1   → 0   (이미 있었다 = 중복이다)
```

즉 `SADD` 한 번으로 **"이미 받았는지 확인"과 "안 받았다면 지금 자리를 잡기"가 동시에, 원자적으로** 끝난다. 반환값이 1이면 내가 처음이고, 0이면 누군가(또는 내가) 이미 넣었다는 뜻이다.

이것이 왜 결정적인지는 2-1의 타임라인에 바로 대입해 보면 안다.

```
시각   요청 X (u1)                  Set 의 실제 내용        요청 Y (u1, 같은 사용자)
t0     SADD users u1 → 1            { u1 }
t1                                  { u1 }                  SADD users u1 → 0
t2     반환값 1 → "발급 완료"                                반환값 0 → "이미 발급받으셨습니다"
```

**"확인하고 발급"이라는 두 걸음이 한 걸음으로 접혔으므로, 그 사이에 끼어들 틈이 사라졌다.** 앞 문서에서 본 `SET NX`(없을 때만 설정)와 정확히 같은 발상이다 — 명령을 나누지 말고 조건을 명령 안에 실어 보낸다.

거꾸로 말하면, `SISMEMBER`로 확인한 뒤 `SADD`하는 코드는 **`SADD`가 이미 원자적으로 해주는 일을 굳이 두 걸음으로 되돌린 것**이다. 조회 한 번이 늘어나서 느려지는 정도가 아니라 정확성이 깨진다.

### 2-3. 남은 조건은 수량 — 그래서 Lua로 묶는다

중복은 `SADD` 하나로 해결됐다. 그런데 조건이 하나 더 있다. **"10만 장을 넘지 않았는가"**다. 이 판정에는 지금까지 몇 장 나갔는지를 읽는 명령이 따로 필요하므로, 다시 명령이 둘이 된다.

```
SCARD coupon:{1}:users   → 99,999 (아직 남았다)
   ← 이 틈에 다른 요청 수백 개가 같은 판정을 통과한다
SADD  coupon:{1}:users u1
```

두 명령 사이가 또 뚫린다. 그래서 **두 명령을 Redis 서버 안에서 한 덩어리로 실행**시켜야 하고, 그 도구가 Lua 스크립트다. Redis는 Lua 스크립트를 실행하는 동안 다른 클라이언트의 명령을 끼워 넣지 않는다.

```lua
-- AFTER — 판정 전체가 한 덩어리: 실행 중 다른 명령이 끼어들 수 없다
-- KEYS[1] = coupon:{1}:users   ARGV[1] = userId   ARGV[2] = 100000
if redis.call("SISMEMBER", KEYS[1], ARGV[1]) == 1 then
    -- 이미 발급받은 사용자다. 소진 여부와 무관하게 중복으로 판정해
    -- "이미 받으셨습니다" 와 "다 떨어졌습니다" 를 구분해 응답할 수 있게 한다.
    return -1
end
if redis.call("SCARD", KEYS[1]) >= tonumber(ARGV[2]) then
    -- 집합 크기가 곧 발급 수다. 한도에 도달했으면 여기서 끊는다.
    -- ARGV 로 넘어온 값은 항상 문자열이므로 tonumber 로 숫자 변환이 필요하다.
    return 0
end
-- 위 두 검사를 통과했을 때만 실제로 자리를 잡는다.
-- 이 세 명령이 한 스크립트 안에 있으므로 검사와 추가 사이에 틈이 없다.
redis.call("SADD", KEYS[1], ARGV[1])
return 1
```

`KEYS`와 `ARGV`가 무엇인지 짚고 가자. 스크립트를 실행하는 명령의 형태는 이렇다.

```
EVAL <스크립트> 1 coupon:{1}:users u1 100000
                ^ 뒤따르는 인자 중 앞의 몇 개가 "키"인지를 알려주는 숫자
                  → 키 1개:  KEYS[1] = "coupon:{1}:users"
                  → 나머지:  ARGV[1] = "u1",  ARGV[2] = "100000"
```

**`KEYS`는 이 스크립트가 건드릴 키 목록, `ARGV`는 그 밖의 값 목록**이다(Lua의 배열은 1부터 센다). 키를 굳이 `ARGV`가 아니라 `KEYS`로 넘겨야 하는 이유가 있다 — Redis Cluster는 이 스크립트를 **어느 노드로 보낼지** 정해야 하는데, 그 판단을 `KEYS`에 적힌 키로 한다. 키를 `ARGV`에 섞어 넣으면 Cluster 환경에서 엉뚱한 노드로 가서 깨진다.

몇 가지를 더 짚는다.

- **왜 `MULTI/EXEC`가 아니라 Lua인가** — `MULTI`는 명령을 큐에 모아 한꺼번에 실행할 뿐 **중간 조회 결과로 분기할 수 없다.** "SCARD 결과가 한도 미만이면 SADD"라는 조건문을 표현할 방법이 없다. check-then-act를 원자화하려면 `WATCH` 기반 낙관적 재시도나 Lua가 필요한데, 경합이 극심한 이 시나리오에서 `WATCH`는 재시도 폭풍이 된다. 상세 비교는 [MULTI/EXEC와 WATCH vs Lua](27-multi-exec-watch-vs-lua.md).
- **`coupon:{1}:users`의 중괄호**는 Redis Cluster의 **해시 태그**다. Cluster는 키를 해시해 슬롯을 정하는데, 중괄호가 있으면 **중괄호 안의 부분만** 해시한다. 그래서 `coupon:{1}:users`와 `coupon:{1}:soldout`은 반드시 같은 슬롯, 같은 노드에 놓인다. 스크립트가 여러 키를 만질 때 Cluster로 전환해도 깨지지 않게 미리 깔아두는 장치다. **(가산점 포인트)**
- **`SISMEMBER` 대신 `SADD`의 반환값으로도 같은 스크립트를 쓸 수 있다.** `SCARD` 검사를 먼저 하고 `SADD` 반환값이 0이면 중복으로 처리하는 형태다. 위 코드가 `SISMEMBER`를 먼저 두는 이유는 **중복과 소진을 구분해 응답하기 위해서**다(소진된 뒤에 같은 사용자가 다시 눌러도 "이미 받으셨습니다"가 나가야 한다). 어느 쪽이든 Lua 안에 있으므로 원자성은 동일하다.
- **명령 세 개 모두 O(1)이다.** `SISMEMBER`, `SCARD`, `SADD` 전부 상수 시간이라, 스크립트가 Redis의 싱글 스레드를 붙잡는 시간이 집합 크기와 무관하게 일정하다. 이 성질이 없으면 Lua로 묶는 순간 그 스크립트가 서버 전체를 멈추는 흉기가 된다.

### 2-4. Set 하나가 카운터를 겸하게 하는 이유와 그 대가

발급 수를 세는 방법은 둘이다. `INCR`로 올리는 별도 카운터 키를 두거나, **집합의 크기(`SCARD`)를 그대로 발급 수로 쓰거나.** 여기서는 후자를 택했다.

이유는 **진실의 원천을 하나로 두기 위해서**다. 카운터를 따로 두면 "Set에는 들어갔는데 카운터가 안 올라간" 상태가 존재할 수 있고, 그 순간 시스템에는 서로 다른 두 개의 답이 생긴다. 지금은 Lua로 묶여 있으니 스크립트 안에서는 어긋나지 않겠지만, 어긋남은 스크립트 밖에서 온다.

- 장애 복구로 Set을 DB 원장에서 **재구축**하면(3-3) 카운터도 별도로 다시 계산해 맞춰야 한다. 하나를 빠뜨리면 그때부터 두 값이 어긋난 채로 운영된다.
- 운영자가 수동으로 특정 사용자를 Set에서 빼는 보정 작업을 하면 카운터가 따라 내려가지 않는다.
- 마이그레이션이나 부분 만료로 한쪽만 사라질 수 있다.

**Set 하나가 유일한 진실이면 어긋날 대상 자체가 없다.** 두 값을 맞추는 로직도, 둘이 어긋났을 때의 대사 절차도 필요 없어진다.

대가도 정확히 알고 있어야 한다.

- **시간은 문제없다.** `SCARD`는 O(1)이다. Redis가 집합의 원소 개수를 따로 들고 있어서 세지 않고 바로 답한다. 10만이든 1000만이든 같은 시간이다.
- **메모리는 멤버 수에 비례한다.** 카운터는 어디까지나 정수 하나지만, Set은 발급받은 사용자 ID를 전부 들고 있어야 한다. 10만 멤버라면 메가바이트 단위에 그치므로 이 설계에서는 문제가 아니다.

### 2-5. 이 설계가 감당하는 규모의 상한 — big key 경계

10만 멤버 Set은 걱정할 크기가 아니다. 그러나 **이 설계를 그대로 수백만·수천만 규모로 늘리면 그 Set은 big key가 된다.**

**big key**란 값 하나가 지나치게 큰 키를 말한다. 문제는 Redis가 싱글 스레드라는 점에서 나온다. 그 키를 통째로 훑는 명령이 들어오면 **그 명령이 끝날 때까지 다른 모든 요청이 대기한다.**

발급 판정 경로 자체는 O(1) 명령만 쓰므로 안전하다. 위험한 것은 그 바깥이다.

- 운영자가 상태를 확인하려고 `SMEMBERS`를 치는 순간, 수백만 멤버를 전부 직렬화하는 동안 서버가 멈춘다. 이럴 때는 커서로 조금씩 훑는 `SSCAN`을 쓴다.
- 이벤트가 끝나고 `DEL`로 정리하는 순간에도 같은 일이 생긴다. 큰 키의 메모리를 회수하는 작업이 그 명령 안에서 일어나기 때문이다. Redis 4.0에서 추가된 `UNLINK`는 키를 즉시 네임스페이스에서 떼어내고 메모리 회수는 백그라운드 스레드에 맡기므로, 큰 키를 지울 때는 `UNLINK`를 쓴다.

즉 **이 설계의 상한은 "발급 대상 수"가 아니라 "Set 하나가 커졌을 때 그 키를 만지는 모든 경로"**에 있다. 상세는 [big key의 위험과 UNLINK](23-big-key-risk-and-unlink.md)에서 다룬다. 규모가 커지면 사용자 ID를 여러 Set으로 나누거나(그러면 `SCARD` 겸용을 포기해야 한다), 중복 방지 자체를 DB 유니크 제약 쪽으로 옮기는 재설계가 필요해진다.

### 2-6. 분산 락으로 감싸지 않는 이유

**분산 락을 쓰지 않는 이유를 먼저 말하는 것**이 이 문항의 변별 지점 중 하나다. "동시성 제어니까 락"이라는 반사작용을 끊을 수 있는지를 본다.

**잠글 틈이 존재하지 않는다.** 경합 지점(중복 확인 + 수량 확인 + 기록)이 이미 Lua 한 덩어리로 원자화되어 있고, Redis는 그 스크립트를 실행하는 동안 다른 명령을 끼워 넣지 않는다. 락이란 "여러 명령 사이의 틈을 막는 장치"인데, 막을 틈이 없으면 락은 할 일이 없다.

그런데도 락을 얹으면 얻는 것 없이 잃기만 한다.

- **처리량이 떨어진다.** 락 획득 왕복 한 번, 해제 왕복 한 번이 매 요청마다 추가된다. 판정 자체보다 락 처리가 더 비싸진다.
- **실패 모드가 늘어난다.** TTL 만료로 락이 남에게 넘어가거나, 해제가 누락되어 이벤트가 멈추는 상황이 새로 생긴다([분산 락의 함정](16-distributed-lock-pitfalls-redlock.md)).

분산 락 문서의 판단 순서를 그대로 적용하면 이 문제는 1단계에서 끝난다 — "한 문장짜리 원자 연산으로 못 푸나?"에 답이 "된다"이기 때문이다([분산 락의 함정](16-distributed-lock-pitfalls-redlock.md) 3절). 분산 락이 정당한 자리는 여러 시스템에 걸친 절차를 조정할 때이지, 단일 Redis 안의 원자 연산으로 끝나는 문제가 아니다.

## 3. 내구성 — "Redis는 유실될 수 있다"에서 출발한다

### 3-1. Redis 단독으로는 왜 부족한가

Redis는 데이터를 메모리에 두고 디스크에는 부차적으로 남긴다. 그래서 어떤 설정을 골라도 유실 가능성이 남는다. 선택지마다 무엇을 잃는지 보자.

- **RDB 스냅샷만 쓰는 경우**: 주기적으로 메모리 전체를 파일로 떠둔다. 크래시가 나면 **마지막 스냅샷 이후의 발급 기록이 통째로 사라진다.**
- **AOF `everysec`**: 모든 쓰기 명령을 파일에 기록하되 디스크 반영(fsync)은 1초에 한 번 한다. 크래시 시 **마지막 약 1초** 분량이 사라질 수 있다. 평소에는 무시할 만한 양이지만, 이 트래픽에서 1초는 수천 건이다.
- **AOF `always`**: 매 쓰기마다 fsync한다. 유실은 최소화되지만 모든 쓰기가 디스크를 기다리게 되어 처리량이 크게 떨어진다. "Redis로 받는 이유" 자체가 약해진다.
- **복제 + failover**: 아래에서 따로 본다. **AOF 설정과 무관하게 남는 구멍**이다.

상세는 [RDB vs AOF](08-redis-persistence-rdb-vs-aof.md)에서 다룬다.

#### failover가 카운터를 과거로 되돌리는 메커니즘

이 부분은 반드시 메커니즘까지 말할 수 있어야 한다. **Redis 복제는 비동기다.**

```
정상 동작

  클라이언트 ── SADD u1 ──▶ [마스터]  메모리에 반영
             ◀──── OK ─────           ← 이 OK 는 "복제됐다"는 뜻이 아니다

                            [마스터] ── 복제 스트림 ──▶ [레플리카]
                                     (응답을 보낸 뒤에, 비동기로)
```

**마스터는 클라이언트에게 OK를 먼저 응답하고, 그 뒤에 레플리카로 내용을 흘려보낸다.** 응답과 복제가 묶여 있지 않다. 그래서 어느 순간에도 "마스터에는 있지만 아직 레플리카에는 없는 쓰기"가 존재한다.

마스터가 죽는 순간 그 쓰기들이 어떻게 되는지가 문제다.

```
유실 시나리오

t0  99,900 번째 발급까지는 마스터와 레플리카가 같은 상태
t1  u99901 ~ u100000 (마지막 100 명) 이 마스터의 Set 에 들어가고 OK 응답이 나간다
    → 이 100 명은 화면에서 "발급 완료" 를 이미 봤다
t2  그 100 건이 복제 스트림을 타고 레플리카에 도달하기 전에 마스터가 다운된다
t3  Sentinel/Cluster 가 레플리카를 새 마스터로 승격시킨다
t4  새 마스터의 Set 에는 99,900 명까지만 들어 있다
    SCARD 가 100,000 → 99,900 으로 되돌아갔다
t5  결과 ① 초과 발급: 남은 100 장이 다시 발급되어 실제 발급 총량이 100,100 장이 된다
    결과 ② 중복 발급: u99901~u100000 이 다시 신청하면 Set 에 없으므로 통과해 두 장을 받는다
```

**"없던 일이 된 쓰기"**가 핵심이다. 마스터가 응답한 OK는 취소되지 않는다 — 사용자는 이미 발급 완료 화면을 봤다. 그런데 시스템의 기억에서는 그 발급이 사라졌다. **응답은 나갔는데 기록은 없는 상태**가 초과 발급과 중복 발급을 동시에 만든다.

이 구멍을 좁히는 수단이 아예 없지는 않다. Redis의 `WAIT` 명령은 지정한 수의 레플리카가 쓰기를 확인할 때까지 응답을 미룬다. 하지만 응답 지연을 사게 되고, 그마저도 모든 failover 시나리오를 막아주는 완전한 보장은 아니다. **"복제 지연 창을 좁힐 수는 있어도 없앨 수는 없다"**가 정확한 표현이다.

유실의 결과를 다시 요약하면 이렇다. Set이 과거로 돌아가 `SCARD`가 줄어든 상태에서 발급이 계속되면 **초과 발급**, 이미 받은 사용자가 Set에서 사라지면 **중복 발급**이다. **"AOF 켰으니 안전"이 아니라 유실이 곧 정확성 붕괴로 직결되는 구조임을 인정하는 것**이 내구성 설계의 출발점이다.

### 3-2. 구조로 푼다 — 판정 경로와 원장 경로의 분리

Redis가 유실될 수 있다면, **잃어도 되는 것만 Redis에 두면 된다.** 발급 사실의 최종 진실은 DB에 둔다.

```
사용자 ──▶ API ──▶ ① Lua 판정 (성공/중복/소진)          ... 동기, ms 단위
                    └ 성공 시: ② 발급 이벤트 적재
                                  │
                    컨슈머 ◀──────┘                      ... 비동기
                    ③ DB INSERT coupon_issue
                       UNIQUE (coupon_event_id, user_id) ← 최종 방어선
```

- **① 판정**: 2절의 Lua다. 사용자는 여기서 바로 "발급 완료" 응답을 받는다. DB를 기다리지 않으므로 응답이 밀리초 단위로 끝난다.
- **② 이벤트 적재**: 발급 사실을 큐(Kafka 또는 Redis Streams)에 남긴다. 두 선택지의 트레이드오프가 갈린다.
  - **Redis Streams**를 쓰면 **판정 Lua 안에서 `XADD`까지 한 덩어리로** 묶을 수 있어 "판정은 됐는데 이벤트가 안 남는" 틈이 사라진다. 대신 내구성이 다시 Redis에 묶이므로 3-1의 유실이 이벤트에도 그대로 적용된다.
  - **Kafka**를 쓰면 내구성은 강해지지만 "Lua 성공 후 발행 실패"라는 틈이 새로 생긴다. 이 틈은 발행 재시도와 ③의 멱등성으로 메운다.
- **③ 원장 기록**: 컨슈머가 DB에 INSERT한다. **`(coupon_event_id, user_id)` 유니크 제약**이 있으므로 같은 이벤트가 두 번 소비돼도(재시도, 유실 후 재구축) 중복 발급으로 이어지지 않는다 — 소비가 멱등해진다.

```sql
CREATE TABLE coupon_issue (
    id              bigserial   PRIMARY KEY,
    coupon_event_id bigint      NOT NULL,
    user_id         bigint      NOT NULL,
    issued_at       timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_coupon_issue UNIQUE (coupon_event_id, user_id)
);
-- 이 제약이 최종 방어선이다. 앞단의 Redis 판정이 어떤 이유로 뚫려도
-- 같은 사용자에게 같은 이벤트의 쿠폰이 두 줄 들어가는 일은 DB 가 거부한다.
```

컨슈머는 조회로 확인하지 않고 곧장 넣는다. `INSERT ... ON CONFLICT (coupon_event_id, user_id) DO NOTHING`을 쓰면 이미 있는 경우에도 예외 없이 흡수된다. **"이미 있나?"를 조회로 확인하고 INSERT하면 그 사이가 뚫리지만, 유니크 제약과 결합한 INSERT는 확인과 선점이 DB 안에서 한 번에 원자적으로 일어난다.** 2-2에서 본 `SADD` 반환값과 정확히 같은 발상이다.

여기서 말할 수 있어야 하는 한 줄은 이것이다. **락이 아니라 제약이 최종 진실을 지킨다.**

### 3-3. 각 계층의 실패가 어떻게 흡수되는가

구조를 그렸다면 다음은 "그래서 각 지점이 죽으면 무슨 일이 나는가"다. 이 답이 설계의 핵심이다.

**컨슈머나 DB가 일시 장애를 겪으면** 이벤트가 큐에 남아 있으므로 복구 후 이어서 처리된다. 발급 응답은 이미 나갔지만 원장 반영이 늦을 뿐, 발급 사실을 잃지는 않는다.

**Redis가 유실되면(failover 포함) 발급을 즉시 멈춘다.** 이 판단의 이름이 fail-closed다.

#### fail-closed란 무엇인가

**fail-closed**는 시스템이 정상 판단을 할 수 없는 상태가 됐을 때 **허용이 아니라 차단 쪽으로 기우는** 설계 원칙이다. 이름은 문에서 왔다 — 잠금장치가 고장 났을 때 문이 **닫힌 채로** 멈추면 fail-closed, **열린 채로** 멈추면 fail-open이다.

발급에서 fail-closed를 택하는 근거는 **되돌릴 수 있는 쪽으로 실패하기** 위해서다.

| | fail-open (계속 발급) | fail-closed (발급 중단) |
|---|---|---|
| 잘못됐을 때 생기는 일 | 초과 발급 | 받을 수 있었던 사람이 못 받음 |
| 되돌릴 수 있나 | 이미 나간 쿠폰은 회수 불가 | 재개하면 그 사람들이 다시 받을 수 있음 |

**초과 발급은 회수가 불가능하다.** 사용자에게 이미 "발급 완료"라고 응답한 쿠폰을 나중에 뺏는 것은 기술 문제가 아니라 신뢰 문제이고, 이미 사용된 쿠폰이라면 회수 자체가 성립하지 않는다. 반면 발급 중단은 불편하지만 **나중에 재개하면 복구된다.** 확신이 없을 때는 되돌릴 수 있는 실패를 고른다.

fail-closed가 언제나 정답인 것은 아니라는 점도 함께 알아야 한다. 캐시가 죽었을 때 요청을 DB로 흘려보내는 것(fail-open)이 맞는 경우도 있다([캐시 장애와 DB 보호](19-cache-failure-db-protection.md)). **판단 기준은 "차단이 안전한가"가 아니라 "어느 쪽으로 실패해야 되돌릴 수 있는가"다.** 발급은 그 기준에서 fail-closed다.

#### 복구 절차 — 멈춤, 재구축, 재개

발급을 멈춘 뒤에는 순서가 중요하다.

```
① 멈춤     발급을 fail-closed 로 차단한다 (소진 플래그 또는 애플리케이션 스위치)
              └ 먼저 멈추지 않으면 재구축 도중에도 새 발급이 계속 들어와 Set 이 또 어긋난다
② 소진     큐에 남아 있는 미반영 이벤트를 컨슈머가 DB 까지 전부 밀어 넣는다
              └ 이걸 건너뛰면 "큐에는 있고 DB 에는 없는" 발급이 재구축에서 빠진다
③ 재구축   DB 원장에서 user_id 를 읽어 Set 을 다시 만든다
              └ SELECT user_id FROM coupon_issue WHERE coupon_event_id = 1
              └ 1,000 개씩 묶어 SADD 를 보내면 왕복 100 번, 초 단위로 끝난다
④ 재개     스위치를 되돌린다
```

②를 ③보다 먼저 해야 하는 이유가 이 절차의 급소다. 순서를 바꿔 재구축을 먼저 하면, **큐에만 있고 DB에는 아직 없는 발급이 새 Set에서 빠진다.** 그 사용자들이 다시 신청하면 Set에 없으므로 통과해 중복 발급이 된다.

**그래도 새어 나간 소량의 초과 발급**(유실 직전에 판정만 통과한 건들)은 기술로 0으로 만들 수 없다. DB 원장 기준으로 실제 발급 수를 재검증하고, 소진 초과분은 비즈니스 결정(그대로 인정할지, 안내 후 회수할지)으로 처리한다. **기술로 없앨 수 없는 잔여 위험을 식별하고 그 처리 정책을 미리 정해두는 것**까지가 설계다. (가산점 포인트)

### 3-4. 트래픽 앞단 방어 — 소진 이후의 수백만 요청

10만 번째 발급이 끝난 뒤에도 요청은 계속 온다. 1-1에서 본 대로 거절되는 요청이 성공하는 요청보다 훨씬 많으므로, **거절을 어디서 하느냐가 전체 비용을 결정한다.**

원리는 단순하다. **요청은 안쪽으로 들어올수록 더 비싼 자원을 잡는다.** 그러니 거절할 요청은 최대한 바깥에서 거절한다.

```
계층                              요청 하나를 거절하는 비용
────────────────────────────────────────────────────────────────────
CDN / 엣지                        거의 0. 우리 서버에 도달조차 하지 않는다
LB / API Gateway                  TCP 연결 처리 + 라우팅
API 서버 (로컬 캐시로 즉시 판정)   스레드 하나가 마이크로초 단위로 끝낸다
API 서버 → Redis 왕복              네트워크 왕복 + Redis 싱글 스레드 점유
API 서버 → DB                      커넥션 점유 + 디스크 I/O   ← 여기까지 오면 1-2 의 붕괴
```

이 계층을 알고 나면 대응이 자연스럽게 나온다.

**소진 플래그를 앞으로 당긴다.** 소진되는 순간 별도 플래그 키(`coupon:{1}:soldout`)를 세우고, API 서버는 이 값을 **로컬 캐시(수 초 TTL)**로 들고 있다가 즉시 "소진" 응답을 돌려준다. Redis 왕복조차 생략되므로 위 표에서 두 계단을 올라간다.

로컬 캐시의 TTL이 만드는 오차도 짚을 수 있어야 한다. 소진 직후 수 초간은 캐시가 갱신되지 않은 서버에서 Redis까지 가는 요청이 남는다(무해하다 — Lua가 정확히 판정한다). 반대로 취소·반환으로 재고가 다시 생겼을 때는 수 초간 잘못 거절할 수 있는데, 이것은 fail-closed 방향의 오차이므로 허용 가능하다.

**유입 자체가 감당 밖이면 앞단에 대기열을 둔다.** 진입 토큰을 발급해 초당 유입을 평탄화하는 방식이다(가상 대기실). 선착순의 "순서"가 발급 요청 시점에서 **대기열 진입 시점**으로 옮겨질 뿐이고, 사용자 입장에서는 "지금 몇 번째" 같은 정보를 받으므로 오히려 예측 가능해진다. 무엇보다 뒤쪽 계층이 감당 가능한 속도로만 요청을 흘려보낼 수 있다는 것이 핵심이다.

## 4. 꼬리질문 대비 포인트

### "왜 분산 락으로 안 감싸나요?"

**잠글 틈이 없기 때문이다.**

경합 지점(중복 확인 + 수량 확인 + 기록)이 이미 Lua 한 덩어리로 원자화되어 있고, Redis는 싱글 스레드라 스크립트 실행 중 다른 명령이 끼어들 수 없다. 락은 "명령 사이의 틈을 막는 장치"인데 막을 틈이 없으면 할 일이 없다.

락을 얹으면 얻는 것 없이 락 왕복 지연이 붙고, TTL 만료나 오해제라는 실패 모드만 추가된다([분산 락의 함정](16-distributed-lock-pitfalls-redlock.md)).

분산 락이 정당한 건 여러 시스템에 걸친 절차를 조정할 때이지, 단일 Redis 안의 원자 연산으로 끝나는 문제가 아니다.

### "failover로 카운터가 과거로 돌아갔다면 어떻게 감지하고 무엇부터 하나요?" (시니어 변별 포인트)

**감지 수단은 둘이다.** ① failover 이벤트 자체를 알람으로 받는다(Sentinel이나 관리형 서비스의 알림). ② DB 원장 건수와 `SCARD`를 주기적으로 맞춰보는 **대사(reconciliation)**로 어긋남을 잡는다. 두 값이 벌어지면 어딘가에서 기록이 사라졌다는 뜻이다.

**대응은 3-3의 순서 그대로 멈춤 → 소진 → 재구축 → 재개다.** 먼저 발급을 fail-closed로 멈추고, 큐에 남은 미반영 이벤트를 DB까지 밀어 넣고, DB 원장으로 Set을 재구축한 뒤 재개한다.

순서를 지키지 않으면, 특히 재구축을 큐 소진보다 먼저 하면 **큐에만 있고 DB에 없는 발급이 Set에서 빠져 중복 발급 여지가 생긴다.** "장애 시 절차"를 시간 순서로 말할 수 있는지가 운영 성숙도의 지표다.

### "컨슈머가 DB INSERT에 실패하면 사용자는 이미 '발급 완료'를 봤는데요?"

이벤트가 큐에 남아 있으므로 **재시도로 결국 반영된다**(at-least-once 전달 — "적어도 한 번은 도착한다"는 보장이지 "정확히 한 번"이 아니다).

재시도로 같은 이벤트가 두 번 처리되는 경우는 유니크 제약이 흡수한다. 그래서 소비가 멱등해야 한다는 요구가 여기서 나온다.

계속 실패하는 독약 이벤트는 DLQ(dead letter queue, 처리에 반복 실패한 메시지를 따로 모아두는 큐)로 빼고 알람을 울린다. 그냥 두면 그 한 건이 뒤의 모든 이벤트를 막는다.

사용자 관점의 계약은 **"판정 즉시 확정, 원장 반영은 지연 가능"**이다. 그리고 쿠폰을 **사용**하는 시점에는 원장을 확인하므로, 반영 지연이 길어지면 사용 실패로 드러난다. 그래서 반영 지연(큐 lag) 자체를 모니터링 지표로 둔다.

### "10만 명이 같은 키를 치면 hot key 아닌가요? Cluster로 분산하면요?" (시니어 변별 포인트)

맞다, 구조적으로 hot key다 — 특정 키 하나에 요청이 집중되는 상태다. 그리고 **Cluster는 이 문제의 해법이 아니다.**

Cluster는 키를 해시해 슬롯으로 나누고 슬롯을 노드에 배분한다. 그런데 **같은 키는 언제나 같은 슬롯, 즉 한 노드로만 간다.** 노드를 100대로 늘려도 이 키를 처리하는 것은 여전히 한 대다. 분산의 단위가 키이기 때문에, 키가 하나면 분산되지 않는다([hot key 탐지와 완화](13-hot-key-detection-and-mitigation.md)).

그래서 순서는 이렇다.

**① 먼저 산수로 검증한다.** O(1) 명령 몇 개짜리 Lua면 단일 노드로도 초당 수만 건 수준을 처리한다. 여기에 3-4의 앞단 방어로 유입을 깎으면 대부분의 이벤트는 단일 키로 충분하다. 필요 없는 복잡도를 사지 않는 것이 먼저다.

**② 정말 초과하면 카운터 샤딩을 검토한다.** 재고를 N조각(`coupon:{1}:shard:0` ~ `shard:N`)으로 나눠 요청을 무작위 조각에 붙이는 방식이다. 대신 대가가 크다 — 한 조각만 소진됐을 때 다른 조각으로 재시도하는 로직이 필요하고, 중복 방지 Set을 어떻게 나눌지도 다시 설계해야 하며, 전체 발급 수를 알려면 N개를 다 더해야 한다.

**필요가 증명되기 전에는 꺼내지 않는다**가 결론이다.

### "'선착순'인데 정말 먼저 요청한 사람이 먼저 받나요?"

엄밀한 전역 순서는 보장하지 않으며, **보장할 수 있는 시스템은 사실상 없다**는 것까지 말해야 한다.

사용자 단말에서 LB, 서버, Redis까지 이어지는 경로마다 지연 편차가 있다. 통신사 회선, 지리적 거리, 서버별 부하가 다르므로 "버튼을 먼저 누른 순서"와 "Redis에 도착한 순서"는 얼마든지 달라진다. 이 편차를 없애려면 모든 사용자의 네트워크 지연을 통제해야 하는데, 그건 불가능하다.

**시스템이 보장하는 것은 "Redis에 도착한 순서대로의 공정한 직렬 처리"**다. 싱글 스레드가 도착순으로 하나씩 실행하므로, 도착한 뒤로는 뒤집히지 않는다.

이 정의를 비즈니스와 미리 합의해 두는 것이 분쟁을 막는 실무 답이다. 더 엄격한 공정성이 요구되면 **대기열 진입 시각을 기준으로 순서를 박제**하는 설계로 옮긴다(3-4의 가상 대기실). 그러면 순서 결정 시점이 발급 요청보다 앞으로 당겨지고, 그 시각은 기록으로 남길 수 있다.

## 한 줄 요약

선착순 쿠폰의 정확성은 **"확인 후 발급"을 Lua 한 덩어리로 원자화한 판정기**(`SADD`의 0/1 반환이 중복 확인과 선점을 한 명령에 담고, Set 하나가 `SCARD`로 카운트까지 겸해 카운터 불일치 여지를 없앤다)가, 내구성은 **판정 즉시 이벤트로 흘려 DB 원장에 멱등하게 쌓는 비동기 경로와 유니크 제약이라는 최종 방어선**이 지키며 — 분산 락은 잠글 틈이 없어 불필요하고, 비동기 복제 때문에 failover가 마지막 쓰기들을 없던 일로 만들 수 있으므로 Redis 유실 시에는 **되돌릴 수 있는 쪽으로 실패하도록 멈추고(fail-closed) 큐를 소진시킨 뒤 원장에서 재구축하고 재개**한다는 절차까지 말해야 설계가 완성된다.
