# Hot key — "클러스터로 분산했으니 괜찮다"는 착각을 깨는 문제

> 핵심 관전 포인트: **Hot key는 접근이 특정 소수 키에 집중되어, 그 키를
> 가진 노드 하나만 과부하되는 현상이다. Redis Cluster는 키 단위로
> 샤딩하므로 노드를 아무리 늘려도 키 하나의 부하는 쪼개지지 않는다 —
> "분산 = 해결"이 아닌 이유다. 감지는 노드별 지표 불균형(CPU/네트워크
> 편중) → `redis-cli --hotkeys`(LFU 정책 필요)·클라이언트 사이드
> 접근 집계 순으로 좁혀 들어가고, 해소는 읽기 hot key면 로컬 캐시·복제본
> 읽기·키 복제 분산, 쓰기 hot key면 키를 suffix로 쪼개 여러 노드에
> 나눠 쓰고 읽을 때 합산하는 방식이다.**

---

## 0. 질문 + 의도

**질문**: "Hot key 문제란? 어떻게 감지하고 해소하나요?"

**출제 의도**: 클러스터로 분산해도 인기 키 하나는 한 노드에 몰린다는,
"분산 = 해결"이라는 착각을 깨는 질문. 개념에 그치지 않고 감지
방법(모니터링)까지 답하는지로 운영 감각을 잰다.

## 1. 문제의 구조 — 분산은 "키들"을 나눌 뿐, "키 하나"는 못 나눈다

Redis Cluster는 키를 CRC16 해시 → 16384개 슬롯 중 하나 → 그 슬롯을
담당하는 노드로 배치한다. 즉 **분산의 단위가 키**다. 키가 100만 개면
노드들에 고르게 퍼지지만, 그중 `event:blackfriday:landing` 키 하나에
전체 트래픽의 절반이 몰리면 — 그 키는 여전히 **딱 한 노드**에 있고,
그 노드만 CPU와 네트워크 대역폭이 바닥난다.

비유하면, 창구 10개를 열었는데(클러스터) 고객들이 업무 종류별로
지정 창구에 가야 하는 규칙이라(해시 슬롯), 인기 업무 하나의 줄은
창구를 늘려도 절대 짧아지지 않는 상황이다.

실무에서 hot key가 태어나는 순간들:

- **이벤트/프로모션**: 이벤트 페이지 설정, 선착순 쿠폰 재고 카운터 키.
- **랭킹·메인 화면**: 전 사용자가 같은 `ranking:webtoon` 키를 읽는다.
- **연예인 계정 / 메가히트 콘텐츠**: 데이터 분포 자체가 지수적으로
  치우친 도메인(팔로워, 인기 웹툰)에서는 hot key가 상수로 존재한다.
- **설정/플래그 키**: 모든 요청이 기능 플래그 키 하나를 읽는 구조.

증상은 "Redis가 느리다"가 아니라 **"특정 노드만 느리다"** 로 나타난다.
그 노드를 지나는 요청만 지연이 튀므로, 전체 평균 지표만 보면 멀쩡해
보이는 게 이 문제의 고약한 점이다. 극단적으로는 단일 키 트래픽이
노드의 NIC 대역폭을 채워서 CPU는 남는데 응답이 밀리는 형태도 있다
(값이 큰 hot key일수록 — big key와 겹치면 최악).

## 2. 감지 — "평균이 아니라 편차를 본다"

### ① 인프라 지표에서 의심 시작 (상시 모니터링)

가장 먼저 걸리는 신호는 **노드 간 불균형**이다:

- 노드별 CPU 사용률·네트워크 out 대역폭·초당 명령 수(instantaneous_ops_per_sec)를
  나란히 놓고 본다. 특정 노드만 2~3배 높으면 hot key(또는 슬롯 쏠림) 의심.
- 클러스터 전체 평균만 보는 대시보드는 hot key를 못 잡는다 —
  **노드별로 쪼갠 그래프**가 있어야 한다는 것 자체가 운영 감각 포인트.

### ② Redis 쪽에서 범인 키 좁히기

```bash
# maxmemory-policy가 allkeys-lfu / volatile-lfu 일 때만 사용 가능
# — LFU가 키별 접근 빈도 카운터를 유지하기 때문
redis-cli --hotkeys
```

`--hotkeys`는 내부적으로 SCAN + OBJECT FREQ로 접근 빈도가 높은 키를
찾아준다. **eviction 정책이 LFU가 아니면 빈도 데이터 자체가 없어서
동작하지 않는다**는 전제 조건을 아는 게 중요하다.

`MONITOR`로 흘러가는 명령을 직접 보고 집계할 수도 있지만, MONITOR는
**모든 명령을 복제해 흘려보내느라 처리량을 크게 떨어뜨리는** 명령이라
과부하로 의심되는 그 순간의 운영 장비에 붙이는 건 불난 집에 부채질이다.
쓴다면 수 초만, 그것도 최후 수단으로. (KEYS 금지와 같은 결의 "편한
명령의 비용을 확인하는 습관" 이다.)

### ③ 클라이언트/프록시 사이드 집계 (가장 정확, 사전 대비 필요)

Redis 서버는 "어느 키가 몇 번 불렸는지"를 기본으로 기록하지 않으므로,
정밀한 상시 감지는 **호출하는 쪽**에서 한다:

- 애플리케이션의 Redis 클라이언트 레이어에서 키 패턴별 호출 수를
  메트릭으로 뽑는다 (키 전체가 아니라 `ranking:*` 같은 패턴 단위로
  집계해 카디널리티 폭발을 피한다).
- 프록시(Envoy 등)나 APM이 있다면 그 지점에서 키별 통계를 수집.

"장애 나고 나서 --hotkeys로 찾는 것"과 "평소에 클라이언트 메트릭으로
보이게 만들어 둔 것"의 차이가 운영 성숙도의 차이다.

## 3. 해소 — 읽기 hot key와 쓰기 hot key는 처방이 다르다

### 읽기 hot key ① — 로컬 캐시 (가장 효과가 크고 가장 흔한 처방)

전 서버가 같은 키를 읽는다면, 그 값을 각 서버의 로컬 메모리(Caffeine
등)에 수 초짜리 TTL로 얹는 것만으로 Redis 호출이 "서버 수 × 초당
몇 회" 수준으로 줄어든다.

```java
// ❌ 요청마다 Redis의 같은 키를 직격 — 서버가 늘수록 hot key 노드만 더 맞는다
public EventConfig getEventConfig() {
    return redis.get("event:blackfriday:config");
}

// ✅ 로컬 캐시로 흡수 — Redis 조회는 서버당 몇 초에 1번으로 감소
LoadingCache<String, EventConfig> local = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofSeconds(3))   // 3초 불일치 허용이 협상 포인트
        .build(key -> redis.get(key));

public EventConfig getEventConfig() {
    return local.get("event:blackfriday:config");
}
```

대가는 **노드 간 최대 TTL만큼의 불일치**다. "이 데이터가 3초 낡아도
되는가"를 되묻고 허용되는 데이터에만 쓴다 — 이벤트 설정·랭킹 TOP N은
대부분 허용, 재고 수량처럼 정확성이 돈인 데이터는 불가.

### 읽기 hot key ② — 복제본 읽기, 키 복제

- **replica read**: 해당 샤드의 복제본들로 읽기를 분산한다. 복제
  지연만큼의 낡은 읽기를 허용해야 하고, 분산 폭이 "복제본 수"로
  제한된다.
- **키 복제(read diffusion)**: `config:hot`을 `config:hot:0` ~
  `config:hot:9` 열 개로 복사해 두고 읽을 때 랜덤 suffix를 붙여
  읽는다. 키가 10개가 되므로 여러 노드로 퍼진다. 대가는 **갱신 시
  10개를 모두 갱신해야 하는 정합성 부담** — 갱신이 드문 설정성
  데이터에만 적합하다.

### 쓰기 hot key — 키 샤딩(분할) 후 읽기 시 합산

쓰기는 복제본으로 못 나눈다(쓰기는 마스터로만 간다). 카운터처럼
**연산이 합산 가능(commutative)한 경우**, 키를 쪼개 쓰고 읽을 때 합친다:

```java
// ❌ 전 트래픽이 카운터 키 하나에 INCR — 한 노드에 쓰기 집중
redis.incr("event:pageview");

// ✅ N개 조각에 분산해 쓰고, 읽을 때 합산
int shard = ThreadLocalRandom.current().nextInt(10);
redis.incr("event:pageview:" + shard);           // 10개 키 → 여러 노드로 분산

long total = IntStream.range(0, 10)
        .mapToLong(i -> parse(redis.get("event:pageview:" + i)))
        .sum();                                   // 읽기는 드물게, 합산 결과는 캐시
```

합산이 불가능한 쓰기(단일 값 갱신)라면 애플리케이션에서 버퍼링해
쓰기 빈도 자체를 줄이거나, 그 키를 Redis 밖(예: 전용 저장소)으로
빼는 설계 재검토가 답이다.

### 구조적 예방

- **키 설계 단계에서 접근 분포를 상상한다**: "이 키를 누가, 얼마나
  자주 읽/쓰나"를 설계 리뷰 항목에 넣는다. 전 요청이 건드리는 키는
  태어날 때부터 hot key 후보다.
- hot key가 **big key이기도 하면 최악**(호출량 × 값 크기 = 대역폭
  폭발)이므로, 인기 키일수록 값을 작게 유지한다 — 랭킹이면 TOP N
  ID만, 메타데이터는 분리.

## 4. 꼬리질문 대비 포인트

### "Hot key와 big key는 뭐가 다른가요?"

축이 다르다. **hot key는 접근 빈도**의 문제(작은 키라도 초당 수십만
번 불리면 hot), **big key는 값의 크기**의 문제(수백만 멤버 컬렉션은
하루 한 번 조회해도 위험)다. 처방도 다르다 — hot key는 부하 분산(로컬
캐시, 키 복제/샤딩), big key는 크기 관리(분할 설계, 점진 삭제·UNLINK).
둘이 겹친 "크고 인기 있는 키"는 네트워크 대역폭을 채우는 최악의
조합이라 가장 먼저 손봐야 한다.

### "MONITOR로 보면 되지 않나요?"

MONITOR는 서버가 처리하는 모든 명령을 실시간 복제 전송하는 명령이라
처리량을 크게 떨어뜨린다 — 이미 과부하 의심인 노드에 붙이면 장애를
앞당길 수 있다. 대신 (1) LFU 정책이라면 `redis-cli --hotkeys`,
(2) 평상시라면 클라이언트 사이드 키 패턴별 메트릭, (3) 노드별 지표
편차로 접근한다. "편리한 진단 명령의 비용부터 확인한다"는 태도가
KEYS 금지와 같은 맥락임을 짚으면 좋다.

### "로컬 캐시를 얹으면 서버마다 값이 다를 텐데 괜찮나요?"

괜찮은 데이터에만 쓴다는 게 답이다. 노드 간 불일치는 최대 로컬 TTL
만큼이므로, "이 값이 몇 초 낡아도 비즈니스가 깨지지 않는가"로 판단한다.
이벤트 설정·랭킹·기능 플래그는 대부분 허용. 재고·잔액처럼 정확성이
필수인 값은 로컬 캐시 대상이 아니고, 그런 키가 hot 하다면 쓰기 샤딩이나
설계 재검토로 간다. 더 줄이고 싶으면 pub/sub 무효화 전파를 얹되,
pub/sub은 유실 가능하므로 짧은 TTL을 안전망으로 함께 둔다.

### "키를 10개로 복제하면 갱신은 어떻게 하나요?"

복제본 10개를 모두 갱신해야 하는데, 중간에 실패하면 일부만 새 값인
불일치 상태가 된다. 그래서 키 복제는 **갱신이 드물고 잠깐의 불일치가
허용되는 읽기 전용성 데이터**(설정, 공지)에만 쓰고, 전 조각에 동일
TTL을 걸어 최악의 경우에도 만료로 수렴하게 한다. 갱신이 잦다면 키
복제 대신 로컬 캐시가 맞는 도구다.

### "어떤 해법을 언제 고르나요?" (시니어 변별 포인트)

판단 축은 두 가지 — **읽기냐 쓰기냐**, 그리고 **불일치를 얼마나
허용하느냐**다. 읽기 hot + 초 단위 불일치 허용이면 로컬 캐시(효과
최대, 비용 최소)가 1순위. 읽기 hot + 불일치 최소화 필요면 replica
read. 쓰기 hot + 합산 가능한 연산이면 키 샤딩 후 합산. 쓰기 hot +
합산 불가면 버퍼링으로 빈도를 줄이거나 구조 재검토. 그리고 어떤
해법이든 "감지 체계(노드별 편차, 키 패턴 메트릭)가 먼저"다 — 감지
없이는 해소가 아니라 추측이 된다. 해법 나열이 아니라 이 선택 기준을
말하는 것이 시니어 답변이다.

## 한 줄 요약

Hot key는 접근이 키 하나에 몰려 클러스터로도 분산되지 않는(분산 단위가
키이므로) 특정 노드 과부하 문제로 — 노드별 지표 편차와 클라이언트 사이드
키 패턴 메트릭, LFU 기반 `--hotkeys`로 감지하고, 읽기 hot이면 로컬
캐시·replica read·키 복제, 쓰기 hot이면 키 샤딩 후 합산으로 해소하되,
모든 해법이 "불일치 허용량"을 지불하므로 데이터별 허용치를 협상하는
것까지가 설계다.
