# Redis Lua 스크립트 — "확인하고 행동하는" 두 걸음을 한 걸음으로

> 핵심 관전 포인트: **Lua 스크립트는 "조회 결과를 보고 조건 분기해서
> 다음 명령을 실행"하는 check-then-act 로직을 Redis 서버 안에서
> 하나의 원자적 단위로 실행해, 명령과 명령 사이에 다른 클라이언트가
> 끼어드는 race condition을 없앤다. 락 소유자 검증 후 해제, 선착순
> 쿠폰의 잔여 수량 확인 후 발급, rate limiter가 대표 사례다. 대신
> Redis는 싱글 스레드라 스크립트가 도는 동안 다른 모든 명령이
> 멈추므로, 긴 스크립트는 서버 전체를 세우는 블로킹 폭탄이 된다.
> 짧고 단순하게 유지하고, 접근하는 키는 반드시 KEYS 인자로 선언하는
> 것(클러스터 라우팅)이 주의점의 골자다.**

---

## 0. 질문 + 의도

**질문**: "Lua 스크립트는 어떤 문제를 해결하나요? 사용 시 주의점은?"

**출제 의도**: check-then-act(조회 후 조건부 갱신)를 원자화하는 실무
도구(쿠폰 발급, 락 소유자 검증 해제)를 다뤄봤는지, 동시에 긴
스크립트가 싱글 스레드 전체를 세우는 양날의 검임을 아는지 본다 —
도구의 효용과 위험을 함께 말할 수 있는지가 관전 포인트다.

## 1. 해결하는 문제 — 명령 "사이의 틈"

Redis의 개별 명령(GET, SET, INCR...)은 각각 원자적이다. 문제는
**명령 여러 개 + 그 사이의 애플리케이션 로직**으로 이루어진 작업이다.
"GET으로 값을 확인하고 → 조건에 맞으면 → SET/DEL 한다"는 흐름에서,
확인과 행동 사이에 다른 클라이언트의 명령이 끼어들 수 있다.
이 패턴을 check-then-act라 부르고, 끼어듦이 만드는 버그가 race
condition이다.

대표 사고 — 분산 락 해제:

```java
// ❌ before: GET과 DEL 사이에 틈이 있다
String owner = redis.get("lock:order:42");   // ① 내 락인지 확인
if (myToken.equals(owner)) {
    // ← 바로 이 순간 락 TTL이 만료되고, 다른 프로세스 B가 락을 새로 획득하면?
    redis.del("lock:order:42");              // ② B의 락을 내가 지워버린다!
}
// 결과: B는 락을 쥐고 있다고 믿는데 실제 락은 사라짐 → 제3의 프로세스 C도
// 락 획득 성공 → 임계 구역에 B와 C가 동시 진입 → 정합성 파괴 (조용히)
```

```lua
-- ✅ after: 확인과 삭제를 서버 안에서 한 덩어리로 (락 해제 Lua 관용구)
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])   -- 내 토큰일 때만 삭제
else
    return 0                            -- 남의 락이면 건드리지 않음
end
```

Lua 스크립트가 이 틈을 없앨 수 있는 이유는 **Redis가 명령을 싱글
스레드로 처리**하기 때문이다. 스크립트 실행이 시작되면 끝날 때까지
다른 클라이언트의 어떤 명령도 사이에 실행되지 않는다 — 스크립트
전체가 하나의 명령처럼 보인다. 원자성을 "락을 걸어서" 얻는 게 아니라
"애초에 끼어들 틈이 없는 실행 모델"에서 공짜로 얻는 것이다.

## 2. 대표 실무 사례

### 선착순 쿠폰 — 잔여 확인과 차감을 원자로

```java
// ❌ before: 확인(GET)과 차감(DECR) 사이에 다른 요청들이 끼어든다
long remaining = Long.parseLong(redis.get("coupon:event1:stock"));
if (remaining > 0) {
    redis.decr("coupon:event1:stock");     // 동시에 1000명이 여기 도달하면
    issueCoupon(userId);                   // 재고 100개에 1000장 발급 (초과 발급)
}
```

```lua
-- ✅ after: 재고 확인 + 차감 + 중복 발급 방지를 한 번에
-- KEYS[1] = 재고 키, KEYS[2] = 발급자 Set 키, ARGV[1] = userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1                                    -- 이미 받은 사용자 (중복 방지)
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return 0                                     -- 소진
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1                                         -- 발급 성공
```

동시에 몇만 요청이 몰려도 스크립트가 한 번에 하나씩 실행되므로
초과 발급·중복 발급이 구조적으로 불가능해진다.

### 그 밖의 단골

- **Rate limiter**: "현재 카운트 확인 → 한도 미만이면 증가 + TTL
  설정"을 원자화 (고정 윈도우, 슬라이딩 윈도우 로그 등).
- **락 연장(lease 갱신)**: "내 락인지 확인 → 맞으면 PEXPIRE"를
  원자화 — 락 해제와 같은 소유자 검증 패턴이다.
- **조건부 갱신**: "저장된 버전보다 새 값일 때만 SET" 같은
  compare-and-set.

공통 형태는 전부 **"읽고 → 판단하고 → 쓴다"**이다. 이 형태가 보이면
Lua(또는 그에 준하는 원자적 수단)를 떠올리는 것이 반사신경이다.

## 3. MULTI/EXEC로는 왜 안 되나 — 트랜잭션과의 차이

Redis에도 MULTI/EXEC "트랜잭션"이 있지만 동작이 다르다. MULTI는
명령들을 **큐에 쌓아뒀다가 EXEC 때 일괄 실행**하는 것이라,
**중간 조회 결과를 보고 분기할 수 없다** — GET 결과는 EXEC가 끝나야
받기 때문이다. check-then-act가 원천적으로 불가능하다.

WATCH를 곁들이면 낙관적 잠금(값이 안 바뀌었을 때만 EXEC 성공)으로
흉내는 낼 수 있지만, 경합이 심하면 실패·재시도가 반복돼 코드가
복잡해지고 성능이 떨어진다. Lua는 서버 안에서 조회 결과로 분기하는
로직을 그대로 쓸 수 있으므로 check-then-act의 정공법이다.

| 수단 | 중간 결과로 분기 | 원자성 | 특징 |
|---|---|---|---|
| MULTI/EXEC | 불가 | 일괄 실행 보장 | 큐잉 후 몰아 실행일 뿐 |
| WATCH + MULTI | 간접(재시도) | 낙관적 | 경합 시 재시도 폭증 |
| Lua 스크립트 | **가능** | 전체 원자 | check-then-act 정공법 |

또 하나 중요한 구분 — Lua의 원자성은 **격리(끼어들기 방지)**이지
RDB의 롤백이 아니다. 스크립트 중간에 에러가 나면 **이미 실행된 쓰기는
남는다.** "실패 시 전부 없던 일로"가 필요하면 스크립트 안에서 사전
검증을 먼저 다 끝내고 쓰기를 마지막에 몰아넣는 식으로 작성해야 한다.

## 4. 사용 시 주의점 — 원자성의 청구서

### ① 긴 스크립트 = 서버 전체 정지 (가장 중요)

원자성의 원천이 "싱글 스레드가 스크립트만 실행"이므로, 그 시간 동안
**Redis의 다른 모든 명령이 대기한다.** 스크립트 안에서 수십만 멤버를
루프 돌거나 big key를 순회하면, 캐시 조회·세션 확인 등 그 Redis를
쓰는 **전 서비스가 함께 멈춘다.** KEYS 명령 금지와 정확히 같은 원리의
함정이다.

일정 시간(기본 5초)을 넘기면 Redis는 다른 클라이언트에게 BUSY 에러를
반환하기 시작하는데, 이때도 스크립트가 중단되는 게 아니다.
`SCRIPT KILL`로 죽일 수 있는 것은 **아직 쓰기를 하지 않은 스크립트뿐**
— 이미 쓰기를 시작한 스크립트는 데이터 일관성 때문에 죽일 수 없고,
서버를 내리는 극단적 선택지밖에 남지 않는다. 결론: **스크립트는 짧은
check-then-act 한 덩어리로만. 배치·순회 작업을 Lua에 넣지 않는다.**

### ② 접근하는 키는 반드시 KEYS 배열로 선언

```java
// ❌ before: 키를 ARGV나 스크립트 본문에 하드코딩
redis.eval("return redis.call('GET', 'lock:' .. ARGV[1])", 0, token);
// 단일 노드에선 돌지만, Cluster는 어떤 키에 접근하는지 몰라 라우팅 불가

// ✅ after: 키는 KEYS로, 값은 ARGV로
redis.eval(script, List.of("lock:order:42"), List.of(token));
```

Cluster는 키의 해시 슬롯으로 명령을 라우팅하는데, KEYS 선언이 없으면
어느 노드로 보낼지 판단할 수 없다. 그리고 **한 스크립트가 접근하는
모든 키는 같은 해시 슬롯에 있어야 한다** — 여러 키를 다루는
스크립트(쿠폰 재고 + 발급자 Set)라면 `coupon:{event1}:stock`,
`coupon:{event1}:issued`처럼 **해시 태그(`{...}`)**로 같은 슬롯을
강제해야 한다 (가산점 포인트).

### ③ EVALSHA와 스크립트 캐시 — NOSCRIPT 대비

매번 스크립트 전문을 보내는 EVAL은 네트워크 낭비라, 실무에선
스크립트의 SHA1 해시로 호출하는 EVALSHA를 쓴다. 단 스크립트 캐시는
서버 메모리에만 있어 **재시작·페일오버 후엔 비어 있다** — EVALSHA가
NOSCRIPT 에러를 반환하면 EVAL로 폴백해 재등록하는 로직이 필요하다.
Spring Data Redis, Redisson 같은 클라이언트는 이 폴백을 내장하고
있지만, "왜 그런 처리가 필요한가"를 아는지가 변별 지점이다.

### ④ 결정적(deterministic)으로 작성

스크립트는 복제본·AOF에도 반영돼야 하므로, 실행할 때마다 결과가
달라지는 요소(랜덤, 현재 시각)를 데이터에 그대로 쓰면 위험하다.
시각이 필요하면 스크립트 안에서 구하지 말고 **애플리케이션이 ARGV로
넘겨주는** 것이 안전한 관용구다 (rate limiter에서 흔한 실수).

## 5. 실무 감각 — "Lua를 쓸까"의 판단 기준

- 명령 2~3개 + 분기 하나 수준의 **짧은 check-then-act** → Lua가 정답.
- 왕복만 줄이고 싶고 분기가 없다 → Lua가 아니라 **pipeline/MGET**이
  맞는 도구다 (원자성이 필요 없는데 Lua를 쓰는 것은 과잉).
- 정확성이 돈과 직결(쿠폰·재고·락)되는데 로직이 길고 복잡하다 →
  Lua에 다 넣지 말고, Redis에는 원자적 판정만 남기고 나머지는
  애플리케이션/DB로 옮기는 분해를 먼저 고민한다.

## 6. 꼬리질문 대비 포인트

### "MULTI/EXEC 트랜잭션으로는 같은 걸 못 하나요?"

못 한다. MULTI는 명령을 큐에 모았다가 EXEC에서 일괄 실행하는
구조라 **중간 조회 결과를 받아 분기할 수 없다** — GET의 결과 자체가
EXEC 이후에야 온다. check-then-act를 하려면 WATCH로 낙관적 잠금을
걸고 충돌 시 재시도하는 우회가 필요한데, 경합이 심한 상황(선착순)
에서는 재시도 폭풍이 된다. Lua는 서버 안에서 분기하므로 재시도
없이 한 번에 끝난다. "같은 '트랜잭션'이라는 단어지만 RDB 트랜잭션과
전혀 다른 보장"이라고 선을 그으면 좋다.

### "스크립트가 5초씩 걸리면 무슨 일이 벌어지나요?" (시니어 변별 포인트)

싱글 스레드가 스크립트에 붙잡혀 있으므로 **그 Redis를 쓰는 모든
서비스의 모든 명령이 대기**한다 — 캐시 조회, 세션 확인, 락 획득
전부. 임계 시간을 넘기면 다른 클라이언트에 BUSY 에러가 나가기
시작하고, 애플리케이션에서는 타임아웃·에러 폭증으로 나타난다.
이미 쓰기를 수행한 스크립트는 SCRIPT KILL로도 못 죽인다 — 일관성을
지키려면 완주시키는 수밖에 없기 때문. 그래서 방어는 사후가 아니라
사전이다: 스크립트를 짧게 유지하는 코드 리뷰 규율, slowlog
모니터링. "원자성의 원천(싱글 스레드 독점)이 곧 위험의 원천"이라는
양날 구조를 짚는 것이 핵심이다.

### "Cluster 환경에서 Lua 쓸 때 뭐가 다른가요?"

두 가지. ① 접근 키를 전부 KEYS 배열로 선언해야 라우팅이 된다.
② 한 스크립트의 모든 키가 **같은 해시 슬롯**에 있어야 하므로, 여러
키를 다루면 해시 태그(`{event1}`)로 슬롯을 맞춰야 한다. 이는 MGET·
MULTI와 같은 멀티 키 제약의 연장선이고, "단일 노드에서 잘 돌던
스크립트가 Cluster 전환 때 깨지는" 대표 사례라 확장 계획 단계에서
미리 알아야 하는 제약이다.

### "Lua 실행 도중 Redis가 죽으면 절반만 실행된 상태가 남나요?"

살아 있는 서버 기준으로는 "절반 실행된 상태를 다른 클라이언트가
보는 일"은 없다 — 원자적이라 끼어들 수 없기 때문. 장애 시에는
스크립트의 효과가 **통째로 반영됐거나 통째로 유실**되는 쪽에
가깝지만, 주의할 것은 Redis의 내구성 자체가 설정(AOF 정책, 복제
지연)에 달려 있다는 점이다. 즉 Lua는 **동시성(원자성)** 문제를 푸는
도구이지 **내구성**을 주는 도구가 아니다 — 쿠폰 발급처럼 유실이
치명적인 데이터는 Redis 판정 후 DB에 비동기 기록하는 등 내구성
설계를 따로 얹어야 한다.

### "매번 스크립트 본문을 전송하나요?" (가산점 포인트)

아니다. SCRIPT LOAD로 등록해두고 SHA1 해시로 EVALSHA 호출하는 것이
정석 — 본문 전송 비용이 사라진다. 단 스크립트 캐시는 휘발성이라
재시작·페일오버 후 NOSCRIPT 에러가 나며, 이때 EVAL로 폴백해
재등록해야 한다. 클라이언트 라이브러리가 대부분 자동 처리하지만
페일오버 직후 잠깐의 NOSCRIPT 에러 로그가 왜 찍히는지 설명할 수
있으면 운영 경험이 드러난다.

## 한 줄 요약
