# Redis Lua 스크립트 — "확인하고 행동하는" 두 걸음을 한 걸음으로

> 핵심 관전 포인트: **Lua 스크립트는 "값을 조회해서 그 결과를 보고 조건 분기한 뒤 다음 명령을 실행"하는 check-then-act 로직을 Redis 서버 안에서 하나의 원자적 단위로 실행해, 명령과 명령 사이에 다른 클라이언트가 끼어드는 race condition을 없앤다. 락 소유자 검증 후 해제, 선착순 쿠폰의 잔여 수량 확인 후 발급, rate limiter가 대표 사례다. MULTI/EXEC로는 이걸 못 하는데, MULTI는 명령을 큐에 쌓아뒀다가 몰아 실행하는 구조라 중간 조회 결과를 받아 분기할 수 없기 때문이다. 대신 Redis는 명령 실행이 싱글 스레드라 스크립트가 도는 동안 다른 모든 명령이 멈추므로, 긴 스크립트는 서버 전체를 세우는 블로킹 폭탄이 된다 — 게다가 이미 쓰기를 한 스크립트는 `SCRIPT KILL`로 죽일 수도 없어서(절반만 반영된 상태를 남기면 원자성이 깨지므로 Redis가 거부한다) 남는 선택지가 `SHUTDOWN NOSAVE`뿐이다. 짧고 단순하게 유지하고, 접근하는 키는 반드시 `KEYS` 인자로 선언하며(클러스터가 라우팅할 노드를 판단하는 근거다), `EVALSHA`의 `NOSCRIPT` 폴백까지 아는 것이 주의점의 골자다.**

---

## 0. 질문 + 의도

**질문**: "Lua 스크립트는 어떤 문제를 해결하나요? 사용 시 주의점은?"

**출제 의도**: check-then-act(조회 후 조건부 갱신)를 원자화하는 실무 도구(쿠폰 발급, 락 소유자 검증 해제)를 다뤄봤는지, 동시에 긴 스크립트가 싱글 스레드 전체를 세우는 양날의 검임을 아는지 본다 — 도구의 효용과 위험을 함께 말할 수 있는지가 관전 포인트다.

## 1. 해결하는 문제 — 명령 사이의 틈

### 1-1. 전제 지식 — check-then-act가 무엇인가

이 문서 전체가 이 용어 위에 서 있으므로 먼저 정의부터 하자.

**check-then-act는 이름 그대로 "값을 확인한(check) 뒤 그 결과에 따라 행동하는(act)" 코드 형태**다. "재고를 조회해서 0보다 크면 하나 깎는다", "락의 주인이 나인지 확인해서 맞으면 지운다", "요청 카운트를 읽어서 한도 미만이면 1 올린다" — 전부 같은 모양이다.

문제는 확인과 행동이 **서로 다른 명령**이라는 데 있다. 확인 명령을 보내고 응답을 받아 애플리케이션에서 조건을 따지고 다시 행동 명령을 보내는 동안, 짧지만 분명한 시간이 흐른다. 그 사이에 다른 요청이 같은 데이터를 바꾸면, **내가 손에 쥔 확인 결과는 이미 낡은 정보**가 된다. 낡은 정보를 근거로 행동하니 틀린 결과가 나온다.

재고가 1개 남은 쿠폰에 두 요청이 동시에 도착한 상황을 시간축으로 그리면 이렇다.

```
시각   요청 A                      요청 B                      재고 키의 값
t0     GET stock  -> 1                                              1
t1                                 GET stock  -> 1                  1
t2     "1 > 0 이니 발급하자"                                        1
t3                                 "1 > 0 이니 발급하자"            1
t4     DECR stock -> 0                                              0
t5                                 DECR stock -> -1                -1

결과: 재고 1개짜리 이벤트에서 쿠폰 2장이 나갔고, 재고는 -1이 됐다.
      A도 B도 각자 코드는 정확히 시킨 대로 실행했다.
```

여기서 벌어진 버그를 **race condition(경쟁 상태)**이라 부른다. 두 요청이 자원을 먼저 차지하려고 경쟁하는 모양새이고, **누가 먼저 도착하느냐는 실행 순서에 따라 결과가 달라지며, 그중 일부 순서가 틀린 결과를 낸다**는 뜻이다. 재현이 어려운 이유도 여기 있다 — t1과 t4가 겹치는 아주 좁은 구간에서만 터진다.

### 1-2. 대표 사고 — 분산 락 해제

check-then-act가 만드는 사고 중 가장 조용하고 가장 치명적인 것이 분산 락 해제다.

```java
// Before: GET과 DEL 사이에 틈이 있다
String owner = redis.get("lock:order:42");   // ① 지금 이 락의 주인이 나인지 확인
if (myToken.equals(owner)) {
    // ← 바로 이 순간 락 TTL이 만료되고, 다른 프로세스 B가 락을 새로 획득하면?
    redis.del("lock:order:42");              // ② B의 락을 내가 지워버린다
}
// 결과: B는 락을 쥐고 있다고 믿는데 실제 락 키는 사라졌다.
//       그래서 제3의 프로세스 C도 락 획득에 성공한다.
//       임계 구역(한 번에 하나만 들어가야 하는 구간)에 B와 C가 동시 진입.
//       그런데 어디에도 에러가 찍히지 않는다 — 조용히 정합성만 깨진다.
```

이 코드의 결함은 예외 처리가 없는 게 아니다. **①에서 확인한 사실이 ②를 실행하는 시점에도 여전히 참이라는 보장이 없다**는 것이다. 그 사이에 TTL 만료라는, 내 코드와 무관하게 시간이 알아서 일으키는 사건이 끼어들 수 있다.

```lua
-- After: 확인과 삭제를 서버 안에서 한 덩어리로 (락 해제 Lua 관용구)
-- KEYS[1] = 락 키, ARGV[1] = 내 소유 토큰
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])   -- 내 토큰일 때만 삭제한다
else
    return 0                            -- 남의 락이면 손대지 않는다
end
```

`GET`과 `DEL` 사이의 틈이 없어졌다. 정확히는, 그 틈에 다른 클라이언트가 들어올 수 없게 됐다.

### 1-3. 왜 Lua가 그 틈을 없애는가 — 싱글 스레드라는 실행 모델

Lua 스크립트가 원자성을 얻는 이유는 락을 걸어서가 아니다. **Redis가 명령 실행을 스레드 하나로 처리하기 때문**이다(→ `01-redis-single-thread-performance.md`).

`EVAL`이 시작되면 그 메인 스레드는 스크립트가 끝날 때까지 다른 클라이언트의 명령을 하나도 처리하지 않는다. 다른 클라이언트들의 명령은 소켓 버퍼에서 순서를 기다린다. 즉 **스크립트 전체가 바깥에서 보면 하나의 명령처럼 보인다.**

```
[클라이언트 B의 GET]  ─┐
[클라이언트 C의 SET]  ─┼─→ 커널 소켓 버퍼에서 대기
[클라이언트 D의 DEL]  ─┘         ↑
                                 이 시간 동안 아무것도 실행되지 않는다
[메인 스레드] ── EVAL 스크립트 실행 ──────────────→ 다음 명령 처리
                 (GET, 비교, DEL 이 통째로 한 덩어리)
```

원자성을 "락을 걸어서" 얻는 게 아니라 **"애초에 끼어들 틈이 존재하지 않는 실행 모델"에서 공짜로 얻는 것**이다. 이 문장은 3-1에서 그대로 뒤집혀 위험의 근거가 된다 — 공짜가 아니었다는 사실이 거기서 드러난다.

### 1-4. MULTI/EXEC로는 왜 안 되나

"Redis에도 트랜잭션이 있지 않나?"가 자연스러운 반문이다. 있다. 그런데 이름만 같고 동작이 다르다.

**MULTI/EXEC는 명령들을 서버 쪽 큐에 쌓아뒀다가 `EXEC`를 만나면 한꺼번에 순서대로 실행하는 장치**다. 큐에 쌓는 단계에서는 각 명령이 실행되지 않으므로 응답도 오지 않는다 — `QUEUED`라는 접수증만 돌아온다. 실제 결과들은 `EXEC`가 끝난 뒤 배열로 한 번에 온다.

바로 여기가 한계다. **중간 조회 결과를 보고 분기할 수 없다.** `GET`의 결과를 받아야 "0보다 큰가"를 판단할 텐데, 그 결과는 `EXEC`가 다 끝난 뒤에야 손에 들어온다. 판단할 시점에는 이미 모든 명령이 실행되고 난 뒤다. check-then-act가 원천적으로 불가능하다.

```
[MULTI/EXEC]
  MULTI
  GET stock      -> QUEUED   (결과가 아직 없다)
  DECR stock     -> QUEUED   (그래서 "GET 결과가 0보다 크면" 이라는 조건을 쓸 수 없다)
  EXEC           -> [1, 0]   (여기서 처음으로 두 결과를 함께 받는다)

[Lua]
  EVAL           -> 서버 안에서 GET 결과를 즉시 변수에 받아 if 문에 쓴다
```

`WATCH`를 곁들이면 우회는 된다. `WATCH key`는 "이 키가 `EXEC` 전에 다른 클라이언트에 의해 바뀌면 `EXEC`를 통째로 실패시켜라"라고 예약하는 명령이다. 이런 방식을 **낙관적 잠금(optimistic locking)**이라 부른다 — 충돌이 드물 것이라 낙관하고 일단 진행한 뒤, 충돌이 감지되면 그때 실패시키고 처음부터 다시 하는 전략이다.

문제는 "처음부터 다시"의 비용이다. 선착순 쿠폰처럼 수만 요청이 같은 키에 몰리는 상황에서는 대부분의 `EXEC`가 실패하고, 실패한 요청들이 일제히 재시도하며 다시 충돌한다. **경합이 심할수록 재시도가 폭증하는 구조**라 정확히 필요한 순간에 무너진다.

| 수단 | 중간 결과로 분기 | 원자성 | 특징 |
|---|---|---|---|
| MULTI/EXEC | 불가 | 일괄 실행 보장 | 큐잉 후 몰아 실행일 뿐 |
| WATCH + MULTI | 간접(재시도) | 낙관적 | 경합 시 재시도 폭증 |
| Lua 스크립트 | 가능 | 전체 원자 | check-then-act 정공법 |

더 깊은 비교는 `27-multi-exec-watch-vs-lua.md`에 있다.

### 1-5. 원자성은 격리이지 롤백이 아니다

여기가 RDB 트랜잭션에 익숙한 사람이 가장 잘 헛디디는 지점이다.

Lua가 주는 원자성은 **격리(다른 클라이언트가 중간 상태를 보거나 끼어들 수 없음)**이지, **RDB의 롤백(실패하면 앞의 변경을 되돌림)이 아니다.** 스크립트 중간에 에러가 나면 **이미 실행된 쓰기는 그대로 남는다.**

```lua
redis.call('SET', KEYS[1], 'hello')   -- 성공한다. 그리고 남는다.
redis.call('INCR', KEYS[1])           -- 'hello'는 숫자가 아니라 에러 -> 스크립트 중단
-- 위의 SET은 롤백되지 않는다. 키에는 'hello'가 남아 있다.
```

왜 롤백이 없는가. Redis에는 변경 전 값을 따로 보관해 두는 장치가 없기 때문이다. PostgreSQL은 MVCC로 이전 튜플 버전을 남겨두고 WAL에 변경 이력을 적어두므로 되돌릴 근거가 있지만, Redis는 메모리 위 자료구조를 그 자리에서 고친다. 되돌릴 재료가 애초에 없다.

여기서 `redis.call`과 `redis.pcall`의 차이가 실무적으로 의미를 갖는다.

- **`redis.call`**: 명령이 에러를 내면 **스크립트 전체가 그 자리에서 중단**되고 에러가 클라이언트로 반환된다. 그 전까지의 쓰기는 남는다.
- **`redis.pcall`**: 에러를 예외처럼 터뜨리지 않고 **에러 정보를 담은 값(테이블)으로 돌려준다.** 스크립트가 계속 실행되며, 직접 확인해서 처리할 수 있다. `p`는 protected call의 약자다.

```lua
local res = redis.pcall('INCR', KEYS[1])
-- 반환값이 err 필드를 가진 테이블이면 에러가 났다는 뜻이다.
if type(res) == 'table' and res.err then
    -- 여기서 정리 작업을 하거나, 의미 있는 에러 메시지로 바꿔 반환할 수 있다.
    return redis.error_reply('counter is not an integer')
end
return res
```

그러면 실무 규율은 무엇인가. **검증을 스크립트 앞부분에서 전부 끝내고, 쓰기는 뒷부분에 몰아넣는다.** 검증 단계에서 걸러졌다면 아직 아무것도 쓰지 않았으므로 "실패 = 아무 일도 없었음"이 성립하고, 검증을 통과한 뒤의 쓰기들은 에러 없이 완주할 가능성이 높다. 롤백이 없는 세계에서 정합성을 지키는 방법은 **애초에 실패할 수 있는 것을 쓰기 앞으로 옮기는 순서 설계**다.

## 2. 대표 실무 사례

### 2-1. 선착순 쿠폰 — 잔여 확인과 차감을 원자로

1-1의 타임라인이 그대로 재현되는 현장이다.

```java
// Before: 확인(GET)과 차감(DECR) 사이에 다른 요청들이 끼어든다
long remaining = Long.parseLong(redis.get("coupon:event1:stock"));
if (remaining > 0) {
    redis.decr("coupon:event1:stock");     // 동시에 1000명이 여기 도달하면
    issueCoupon(userId);                   // 재고 100개에 1000장 발급 (초과 발급)
}
```

```lua
-- After: 재고 확인 + 차감 + 중복 발급 방지를 한 번에
-- KEYS[1] = 재고 키, KEYS[2] = 발급자 Set 키, ARGV[1] = userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1                                    -- 이미 받은 사용자 (중복 방지)
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then
    return 0                                     -- 소진
end
-- 여기까지가 검증이다. 여기서 걸러지면 아무것도 쓰지 않았다 (1-5의 순서 규율).
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1                                         -- 발급 성공
```

`stock == nil` 검사가 필요한 이유를 짚자. 키가 없으면 `GET`은 Lua에서 `false`를 돌려주고 `tonumber(false)`는 `nil`이 된다. 이 검사를 빼면 `nil <= 0` 비교에서 Lua 에러가 나 스크립트가 중단된다. **이벤트 키가 아직 세팅되지 않았거나 TTL로 사라진 순간에만 터지는 버그**라 테스트에서 잘 안 잡힌다.

호출하는 쪽은 이렇게 생겼다.

```java
// 키는 KEYS로, 값은 ARGV로 넘긴다. 이 구분이 왜 중요한지는 3-2에서 다룬다.
Long result = redis.execute(
        couponScript,
        List.of("coupon:{event1}:stock", "coupon:{event1}:issued"),  // KEYS
        userId);                                                      // ARGV

// 반환값을 의미로 되돌린다. 스크립트는 숫자만 돌려줄 수 있으므로
// 성공/소진/중복을 코드로 약속해 두고 호출부에서 해석한다.
if (result == 1)       issueCouponInDb(userId);
else if (result == 0)  throw new SoldOutException();
else                   throw new AlreadyIssuedException();
```

동시에 몇만 요청이 몰려도 스크립트는 한 번에 하나씩 실행되므로 초과 발급과 중복 발급이 **구조적으로 불가능**해진다. "검사를 잘 짜서 막는" 것이 아니라 "끼어들 틈이 없어서 못 생기는" 것이다. 이 사례의 전체 설계는 `17-flash-sale-coupon-issuance-design.md`에 있다.

### 2-2. Rate limiter — TTL이 유실되는 틈

두 번째 단골이다. "현재 카운트를 확인해서 한도 미만이면 증가시키고 TTL을 건다"는 로직인데, 여기서 Lua가 필요한 이유가 조금 다르다.

```java
// Before: INCR과 EXPIRE 사이에 프로세스가 죽으면?
long count = redis.incr("rate:" + userId);   // ① 카운터를 올린다
if (count == 1) {
    redis.expire("rate:" + userId, 60);      // ② 첫 요청일 때만 TTL을 건다
}
// ①과 ② 사이에 이 애플리케이션 인스턴스가 죽거나 네트워크가 끊기면
// TTL 없는 영구 카운터가 남는다 -> 그 사용자는 영원히 차단된다.
```

```lua
-- After: 증가와 TTL 설정이 한 덩어리
-- KEYS[1] = 카운터 키, ARGV[1] = 한도, ARGV[2] = 윈도우 길이(초)
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    -- 첫 요청일 때만 TTL을 건다. 매번 걸면 창이 계속 밀려 윈도우가 무한정 늘어난다.
    redis.call('EXPIRE', KEYS[1], ARGV[2])
end
if current > tonumber(ARGV[1]) then
    return 0    -- 한도 초과, 차단
end
return 1        -- 통과
```

여기서 Lua가 막는 것은 "두 요청이 서로를 방해하는" race condition이 아니라 **"두 명령 중 하나만 실행된 채 남는" 부분 실행**이다. check-then-act의 사촌이고, 원자성이 푸는 문제라는 점은 같다.

### 2-3. 그 밖의 단골

- **락 연장(lease 갱신)**: "내 락인지 확인 → 맞으면 `PEXPIRE`로 시간 연장"을 원자화한다. 1-2의 락 해제와 똑같은 소유자 검증 패턴이고, 검증 없이 연장하면 **남의 락 수명을 내가 늘려주는** 반대 방향의 사고가 난다.
- **조건부 갱신(compare-and-set)**: "저장된 버전 번호보다 큰 값일 때만 `SET`" 같은 형태. 늦게 도착한 오래된 갱신이 새 값을 덮어쓰는 것을 막는다.

공통 형태는 전부 **"읽고 → 판단하고 → 쓴다"**이다. 코드 리뷰에서 이 형태가 보이면 Lua(또는 그에 준하는 원자적 수단)를 떠올리는 것이 반사신경이 돼야 한다.

## 3. 원자성의 청구서 — 주의점과 판단 기준

1-3에서 원자성을 "공짜로 얻는다"고 썼다. 정확히는 **다른 계정으로 청구된다.** 그 청구서가 이 절이다.

### 3-1. 긴 스크립트 = 서버 전체 정지 (가장 중요)

원자성의 원천이 "싱글 스레드가 스크립트를 독점한다"이므로, 그 시간 동안 **Redis의 다른 모든 명령이 대기한다.** 스크립트 안에서 수십만 멤버를 루프 돌거나 big key를 순회하면, 캐시 조회·세션 확인·락 획득 등 그 Redis를 쓰는 **전 서비스가 함께 멈춘다.** `KEYS` 명령 금지(→ `12-keys-vs-scan.md`)와 정확히 같은 원리의 함정이다.

여기서 대부분의 설명이 끝나는데, 시니어를 가르는 것은 그 다음 질문이다. **그래서 폭주하면 어떻게 멈추는가?**

먼저 Redis가 하는 일. 스크립트 실행이 설정된 시간(`busy-reply-threshold`, 예전 이름 `lua-time-limit`, 기본 5초)을 넘기면 Redis는 다른 클라이언트의 요청에 **`BUSY` 에러를 반환하기 시작한다.** 착각하기 쉬운데, **이때도 스크립트는 중단되지 않는다.** 그저 "지금 스크립트 때문에 바쁘다"고 알려줄 뿐이다. 무한정 기다리게 두지 않고 클라이언트가 빨리 실패할 기회를 주는 것이 목적이다.

여기서부터가 대응 절차다.

```
스크립트 폭주 (다른 클라이언트들이 BUSY 에러를 받기 시작)
        |
        +-- 이 스크립트가 아직 쓰기를 하지 않았는가?
             |
             +-- 예 --> SCRIPT KILL 로 중단.
             |          해당 클라이언트는 에러를 받고, 서버는 정상 복귀.
             |          데이터는 아무것도 변하지 않았으므로 안전하다.
             |
             +-- 아니오 (이미 쓰기를 실행했다)
                      |
                      +-- SCRIPT KILL 은 거부된다 (UNKILLABLE 에러)
                      |
                      v
                 남은 선택지: SHUTDOWN NOSAVE
                 (지금 상태를 RDB로 저장하지 않고 프로세스를 내린다)
```

**왜 이미 쓴 스크립트를 못 죽이는가.** 중간에 죽이면 "절반만 반영된 상태"가 남는다. 그러면 이 스크립트가 약속한 원자성 — 전부 실행되거나 전혀 실행되지 않는다 — 이 깨진다. 게다가 그 절반의 결과는 복제본과 AOF에도 이미 전파되고 있어서, 나중에 되돌릴 방법이 없다. Redis는 **"서버를 계속 세워두는 것"보다 "데이터가 반쯤 망가진 채 살아 있는 것"이 더 나쁘다고 판단**하고 kill을 거부한다.

**그래서 `SHUTDOWN NOSAVE`가 무엇을 뜻하는가.** `NOSAVE`는 종료 시 RDB 스냅샷을 남기지 말라는 뜻이다. 반쯤 반영된 상태를 디스크에 굳혀버리지 않기 위해서다. 대신 마지막 저장 이후의 데이터를 잃고, 복제 구성이라면 페일오버가 일어난다. **사고 대응이 아니라 사고 확대다.**

결론은 하나로 모인다. **긴 스크립트는 사고가 나면 되돌릴 방법이 사실상 없다.** 그러므로 방어는 사후가 아니라 사전이어야 한다.

- 스크립트는 **짧은 check-then-act 한 덩어리로만** 쓴다. 명령 몇 개와 분기 하나 수준.
- 배치·순회 작업을 Lua에 넣지 않는다. 멤버 수에 비례하는 루프가 보이면 그 자리에서 반려한다.
- 스크립트 본문을 코드 리뷰 대상으로 다룬다. 문자열 안에 있어서 리뷰에서 자주 그냥 넘어간다.
- SLOWLOG에 `EVAL`/`EVALSHA`가 찍히는지 모니터링한다.

### 3-2. 접근하는 키는 반드시 KEYS 배열로 선언

먼저 `KEYS`와 `ARGV`가 각각 무엇인지부터.

- **`KEYS`**: 이 스크립트가 **접근할 키의 이름 목록**이다. `KEYS[1]`, `KEYS[2]`처럼 1부터 시작하는 배열로 참조한다.
- **`ARGV`**: 키가 아닌 **그 밖의 값 목록**이다. 사용자 ID, 한도, 타임스탬프, 소유 토큰 같은 것들.

호출 형태를 뜯어보면 둘의 경계가 어떻게 정해지는지 보인다.

```
EVAL <script> 2 coupon:{event1}:stock coupon:{event1}:issued 12345
              ^  ^--------KEYS[1]-------^ ^--------KEYS[2]-------^ ^ARGV[1]
              |
              키의 개수. "여기서부터 2개는 키, 그 뒤는 값"이라는 경계 선언이다.
```

**왜 키를 굳이 `KEYS`로 넘겨야 하는가.** 단일 인스턴스만 보면 아무 차이가 없다. 키를 `ARGV`로 넘기든 스크립트 본문에 하드코딩하든 잘 돈다. 차이는 **Redis Cluster**에서 드러난다.

Redis Cluster는 데이터를 16384개의 **해시 슬롯**에 나눠 담고, 슬롯들을 여러 노드에 분배한다. 키가 어느 슬롯에 속하는지는 `CRC16(키 이름) mod 16384`로 정해진다. 클라이언트는 명령을 보내기 전에 **그 명령이 다루는 키 이름을 보고 슬롯을 계산해, 그 슬롯을 담당하는 노드로 보낸다.**

여기서 문제가 명확해진다. **키 이름이 `ARGV`에 숨어 있거나 스크립트 안에서 문자열로 조립되면, 클라이언트도 서버도 "이 스크립트가 어느 키를 만질지" 알 수 없다.** 알 수 없으면 어느 노드로 보낼지 판단할 근거가 없다.

```java
// Before: 키를 ARGV로 넘기고 스크립트 안에서 조립한다
redis.eval("return redis.call('GET', 'lock:' .. ARGV[1])", 0, orderId);
//          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 키 이름이 실행 시점에야 만들어진다
// numkeys가 0이므로 "이 스크립트는 어떤 키도 만지지 않는다"고 선언한 셈이다.
// 단일 노드에선 멀쩡히 돈다. Cluster로 옮기는 순간 라우팅이 불가능해진다.

// After: 키는 KEYS로, 값은 ARGV로
redis.eval(script, List.of("lock:order:42"), List.of(token));
//                          ^^^^^^^^^^^^^^ 호출 시점에 키 이름이 드러나 있다
```

**단일 인스턴스에서 잘 돌다가 클러스터로 옮기는 순간 깨지는 대표적 코드**다. 그것도 조용히 깨지는 게 아니라 라우팅 단계에서 깨지므로, 이관 당일 대량 에러로 나타난다.

그리고 제약이 하나 더 붙는다. **한 스크립트가 접근하는 모든 키는 같은 해시 슬롯에 있어야 한다.** 슬롯이 다르면 서로 다른 노드에 있을 수 있고, 노드 하나가 남의 노드 데이터를 만질 수는 없기 때문이다.

쿠폰 스크립트처럼 키를 둘 다루는 경우가 여기 걸린다. `coupon:event1:stock`과 `coupon:event1:issued`는 이름이 달라 CRC16 결과도 다르고, 따라서 다른 슬롯에 떨어진다. 해결책이 **해시 태그(`{...}`)**다 — 키 이름에 중괄호가 있으면 Redis는 **중괄호 안의 문자열만으로 슬롯을 계산한다.**

```
coupon:{event1}:stock    ─┐
                          ├─ 둘 다 CRC16("event1")로 슬롯을 계산 -> 같은 슬롯, 같은 노드
coupon:{event1}:issued   ─┘
```

이 제약은 `MGET`, `MULTI` 등 여러 키를 한 번에 다루는 모든 명령에 공통이다 (가산점 포인트).

### 3-3. EVALSHA와 스크립트 캐시 — NOSCRIPT 대비

`EVAL`은 호출할 때마다 스크립트 본문 전체를 네트워크로 보낸다. 수십 줄짜리 스크립트를 초당 수만 번 호출하면 그 자체가 대역폭 낭비다.

그래서 실무에서는 **스크립트를 한 번 등록해 두고, 이후에는 그 본문의 SHA1 해시값(40자 16진수 문자열)만 보내는** `EVALSHA`를 쓴다. Redis는 등록된 스크립트를 **스크립트 캐시**라는 서버 메모리 영역에 보관하고, 해시값으로 찾아 실행한다.

```
[최초 1회]
  앱 ── SCRIPT LOAD "<스크립트 본문 전체>" ──> Redis
     <── "a1b2c3...4f" (SHA1 해시 40자) ────
                                              Redis가 본문을 스크립트 캐시에 보관

[이후 매 호출]
  앱 ── EVALSHA a1b2c3...4f 2 key1 key2 arg1 ──> Redis
     (본문 대신 40자 해시만 오간다. 왕복 데이터가 크게 줄어든다.)

[서버 재시작 / 페일오버로 캐시가 비어 있는 경우]
  앱 ── EVALSHA a1b2c3...4f ──> Redis
     <── NOSCRIPT 에러 ────────
  앱 ── EVAL "<본문 전체>" ... ──> Redis   본문을 다시 보내며 재등록 + 실행
```

핵심은 **스크립트 캐시가 서버 메모리에만 있고 영속화되지 않는다**는 점이다. 프로세스가 재시작하면 비어 있다. 페일오버로 승격된 노드에 그 스크립트가 캐시돼 있다는 보장도 없다. 그래서 `EVALSHA`는 **언젠가 반드시 `NOSCRIPT` 에러를 만난다**는 전제로 짜야 한다.

```java
try {
    return redis.evalsha(sha, keys, args);
} catch (RedisNoScriptException e) {
    // NOSCRIPT는 "그 해시로 등록된 스크립트가 없다"는 뜻이다.
    // 장애가 아니라 캐시가 비었다는 신호이므로, 본문을 보내 재등록하며 실행한다.
    return redis.eval(scriptBody, keys, args);
}
```

Spring Data Redis의 `DefaultRedisScript`나 Redisson 같은 클라이언트는 이 폴백을 내장하고 있다. 그래서 직접 짤 일은 드물지만, **"페일오버 직후 잠깐 NOSCRIPT 에러 로그가 왜 찍혔는지"를 설명할 수 있는지**가 운영 경험의 변별 지점이다.

### 3-4. 결정적(deterministic)으로 작성

**결정적이라는 것은 "같은 입력에 대해 언제 어디서 실행해도 같은 결과가 나온다"는 성질**이다. 왜 이게 문제가 되는가.

Redis의 쓰기는 그 노드에만 머물지 않는다. 복제본으로 전파되고, AOF(명령 로그)에 기록됐다가 재시작 시 다시 실행되어 상태를 복원한다. 그러니 **같은 스크립트가 원본과 복제본에서, 또는 지금과 AOF 재생 시점에 서로 다른 결과를 만들면, 그 순간부터 데이터가 갈라진다.**

랜덤 값과 현재 시각이 대표적인 비결정 요소다. 이것을 스크립트 안에서 구해 **데이터에 그대로 쓰면** 위험하다.

```lua
-- Before: 스크립트 안에서 현재 시각을 구해 데이터에 쓴다
local now = redis.call('TIME')[1]              -- 실행하는 순간마다 값이 다르다
redis.call('ZADD', KEYS[1], now, ARGV[1])      -- 그 값이 데이터로 남는다
```

```lua
-- After: 시각은 애플리케이션이 정해 ARGV로 넘긴다
-- ARGV[1] = 호출 시각(ms), ARGV[2] = 멤버
-- 같은 인자로 다시 실행하면 언제나 같은 결과가 나온다 = 결정적이다
redis.call('ZADD', KEYS[1], ARGV[1], ARGV[2])
```

이것이 rate limiter나 슬라이딩 윈도우 구현에서 특히 흔한 실수다. 다만 정직하게 짚어둘 대가가 하나 있다 — **시각을 애플리케이션이 넘기면 이번엔 앱 서버들의 시계가 서로 어긋나는 문제가 생긴다.** 여러 인스턴스의 시계가 수백 ms씩 다르면 윈도우 경계가 인스턴스마다 미세하게 달라진다. NTP 동기화를 전제로 하되, 그것도 완벽하지 않다는 것을 알고 쓰는 것이 정확한 이해다.

실무 규율로 정리하면 이렇다. **스크립트 안에서 랜덤·시각을 만들어 데이터에 쓰지 않는다. 필요하면 호출하는 쪽이 정해서 `ARGV`로 넘긴다.**

### 3-5. "Lua를 쓸까"의 판단 기준

원자성이 필요 없는데 Lua를 쓰는 것도 잘못된 선택이다. 세 갈래로 갈린다.

**명령 2~3개 + 분기 하나 수준의 짧은 check-then-act라면 Lua가 정답이다.** 이 문서의 사례들이 전부 여기 속한다.

**왕복만 줄이고 싶고 분기가 없다면 Lua가 아니라 파이프라인이나 `MGET`이 맞는 도구다.** 파이프라인은 여러 명령을 한 번에 보내 네트워크 왕복 횟수를 줄이는 기법인데, 원자성은 주지 않는다(→ `21-loop-get-vs-mget-vs-pipeline.md`). 원자성이 필요 없는 상황에서 Lua를 쓰면 3-1의 위험만 떠안는 셈이다.

**정확성이 돈과 직결되는데(쿠폰·재고·락) 로직이 길고 복잡하다면, Lua에 다 넣지 말고 분해를 먼저 고민한다.** Redis에는 원자적 판정만 남기고 — "발급 가능한가, 가능하면 재고 하나 차감" — 나머지 비즈니스 로직은 애플리케이션이나 DB로 옮긴다. Lua가 길어진다는 것은 대개 **Redis가 하지 않아도 될 일까지 떠안았다는 신호**다.

## 4. 꼬리질문 대비 포인트

### "MULTI/EXEC 트랜잭션으로는 같은 걸 못 하나요?"

못 한다. MULTI는 명령을 큐에 모았다가 `EXEC`에서 일괄 실행하는 구조라 **중간 조회 결과를 받아 분기할 수 없다** — `GET`의 결과 자체가 `EXEC` 이후에야 온다. check-then-act를 하려면 `WATCH`로 낙관적 잠금을 걸고 충돌 시 재시도하는 우회가 필요한데, 경합이 심한 상황(선착순)에서는 재시도 폭풍이 된다. Lua는 서버 안에서 분기하므로 재시도 없이 한 번에 끝난다.

**"같은 '트랜잭션'이라는 단어지만 RDB 트랜잭션과 전혀 다른 보장"**이라고 선을 그으면 좋다. MULTI/EXEC가 주는 것은 "묶어서 순서대로 실행"이지 "실패 시 되돌림"이 아니다.

### "스크립트가 5초씩 걸리면 무슨 일이 벌어지나요?" (시니어 변별 포인트)

싱글 스레드가 스크립트에 붙잡혀 있으므로 **그 Redis를 쓰는 모든 서비스의 모든 명령이 대기한다** — 캐시 조회, 세션 확인, 락 획득 전부. 애플리케이션에서는 타임아웃과 에러 폭증으로 나타나고, 커넥션 풀이 마르면서 그 뒤의 요청까지 밀린다.

임계 시간을 넘기면 다른 클라이언트에 `BUSY` 에러가 나가기 시작하는데, **이때도 스크립트는 계속 돈다.** `BUSY`는 중단 신호가 아니라 "지금 바쁘니 기다리지 말고 실패하라"는 안내다.

그리고 여기서 한 발 더 들어가야 한다. **이미 쓰기를 수행한 스크립트는 `SCRIPT KILL`로도 못 죽인다.** 중간에 죽이면 절반만 반영된 상태가 남고, 그건 이미 복제본과 AOF로 흘러가고 있어 되돌릴 수 없기 때문이다. 남는 선택지는 `SHUTDOWN NOSAVE`로 서버를 내리는 것뿐인데, 이건 마지막 저장 이후 데이터를 버리고 페일오버를 유발하는 **사고 확대**다.

그래서 방어는 사후가 아니라 사전이다 — 스크립트를 짧게 유지하는 코드 리뷰 규율, SLOWLOG 모니터링. **"원자성의 원천(싱글 스레드 독점)이 곧 위험의 원천"**이라는 양날 구조를 짚는 것이 핵심이다.

### "Cluster 환경에서 Lua 쓸 때 뭐가 다른가요?"

두 가지다.

**첫째, 접근하는 키를 전부 `KEYS` 배열로 선언해야 한다.** 클러스터는 명령에 등장하는 키 이름으로 슬롯을 계산해 노드를 고르는데, 키가 `ARGV`에 숨어 있거나 스크립트 안에서 조립되면 그 판단을 할 수 없다.

**둘째, 한 스크립트의 모든 키가 같은 해시 슬롯에 있어야 한다.** 슬롯이 다르면 서로 다른 노드에 있을 수 있고, 한 노드가 남의 데이터를 만질 수 없기 때문이다. 여러 키를 다루면 해시 태그(`coupon:{event1}:stock`)로 슬롯을 맞춘다.

이는 `MGET`·`MULTI`와 같은 멀티 키 제약의 연장선이고, **"단일 노드에서 잘 돌던 스크립트가 Cluster 전환 때 깨지는" 대표 사례**라 확장 계획 단계에서 미리 알아야 하는 제약이다.

### "Lua 실행 도중 Redis가 죽으면 절반만 실행된 상태가 남나요?"

살아 있는 서버 기준으로 **"절반 실행된 상태를 다른 클라이언트가 보는 일"은 없다** — 원자적이라 그 사이에 조회가 끼어들 수 없기 때문이다.

장애 시에는 스크립트의 효과가 **통째로 반영됐거나 통째로 유실**되는 쪽에 가깝다. 그러나 여기서 주의할 것은, **Redis의 내구성 자체가 설정에 달려 있다**는 점이다 — AOF의 fsync 정책, 복제 지연에 따라 "커밋됐다고 응답받은 쓰기가 재시작 후 사라지는" 창이 존재한다(→ `08-redis-persistence-rdb-vs-aof.md`).

즉 **Lua는 동시성(원자성) 문제를 푸는 도구이지 내구성을 주는 도구가 아니다.** 쿠폰 발급처럼 유실이 치명적인 데이터는 Redis에서 원자적으로 판정한 뒤 DB에 기록하는 등 내구성 설계를 따로 얹어야 한다.

### "스크립트 중간에 에러가 나면 앞의 쓰기는 롤백되나요?"

**롤백되지 않는다.** Lua의 원자성은 격리(끼어들기 방지)이지 RDB의 롤백이 아니다. Redis에는 변경 전 값을 보관하는 장치가 없어서 되돌릴 재료 자체가 없다.

`redis.call`은 에러 발생 시 스크립트를 그 자리에서 중단시키고, 그 전까지의 쓰기는 그대로 남는다. `redis.pcall`은 에러를 예외로 터뜨리지 않고 값(테이블)으로 돌려주므로, 스크립트 안에서 확인해 직접 처리할 수 있다.

그래서 설계 규율은 **"검증을 앞에, 쓰기를 뒤에"**다. 실패할 수 있는 판단을 전부 앞쪽에서 끝내면, 걸러졌을 때 아직 아무것도 쓰지 않은 상태이므로 "실패 = 아무 일도 없었음"이 성립한다. 롤백이 없는 세계에서 정합성을 지키는 방법은 되돌리기가 아니라 **순서 설계**다.

### "매번 스크립트 본문을 전송하나요?" (가산점 포인트)

아니다. `SCRIPT LOAD`로 등록해두고 SHA1 해시로 `EVALSHA`를 호출하는 것이 정석이다 — 본문 전송 비용이 사라지고 40자 해시만 오간다.

단 **스크립트 캐시는 서버 메모리에만 있고 영속화되지 않는다.** 재시작하면 비어 있고, 페일오버로 승격된 노드에 그 스크립트가 있다는 보장도 없다. 그래서 `EVALSHA`가 `NOSCRIPT` 에러를 반환하면 `EVAL`로 폴백해 본문을 다시 보내며 재등록하는 처리가 필요하다.

클라이언트 라이브러리가 대부분 자동 처리하지만, **페일오버 직후 잠깐의 NOSCRIPT 에러 로그가 왜 찍히는지** 설명할 수 있으면 운영 경험이 드러난다.

## 한 줄 요약

Lua 스크립트는 "읽고 → 판단하고 → 쓴다"는 check-then-act를 싱글 스레드 Redis 안에서 끼어들 틈 없는 한 덩어리로 실행해 락 소유자 검증 해제·선착순 쿠폰 같은 정확성 문제를 푸는 도구이고 MULTI/EXEC로는 중간 결과 분기가 불가능해 대체되지 않지만, 바로 그 실행 모델 때문에 긴 스크립트는 서버 전체를 세우는 블로킹 폭탄이 되며 이미 쓰기를 한 스크립트는 `SCRIPT KILL`조차 거부돼 `SHUTDOWN NOSAVE` 말고는 수습 수단이 없으므로 — 짧은 원자 단위로만 쓰고, 키는 `KEYS`로 선언해 클러스터 라우팅이 가능하게 하며, `EVALSHA`의 `NOSCRIPT` 폴백과 "원자성은 롤백도 내구성도 아니다"라는 경계까지 아는 것이 완성된 답이다.
