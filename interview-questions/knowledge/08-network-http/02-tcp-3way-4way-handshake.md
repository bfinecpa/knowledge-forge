# TCP 3-way / 4-way handshake — 연결의 시작과 끝, 그리고 그 비용

> 핵심 관전 포인트: **3-way handshake(SYN → SYN+ACK → ACK)는 양쪽
> 모두 "보낼 수 있고 받을 수 있음"을 상호 확인하고 시퀀스 번호
> 초기값을 합의하는 절차다 — 최소 왕복(1 RTT)으로 양방향을 확인하려면
> 3번이 필요하다. 종료는 4-way(FIN → ACK → FIN → ACK)인데, 내가 보낼
> 게 없어져도 상대는 아직 보낼 게 남았을 수 있어 양방향을 따로 닫기
> 때문이다. 먼저 끊은 쪽은 TIME_WAIT 상태로 일정 시간 대기한다 —
> 마지막 ACK 유실 대비와 지연 패킷의 새 연결 오염 방지를 위해서다.
> 이 수립 비용(RTT)이 keep-alive·커넥션 풀의 존재 이유이고, TIME_WAIT
> 대량 발생은 종료 절차가 만드는 자연스러운 산물이다.**

---

## 0. 질문 + 의도

**질문**: "TCP 3-way handshake와 4-way handshake(종료)를 설명해주세요."

**출제 의도**: 커넥션 수립 비용을 알아야 keep-alive와 커넥션 풀의
존재 이유가 이해되고, TIME_WAIT 같은 운영 현상이 종료 절차의 산물임을
안다. 외운 지식이 아니라 뒤 개념들의 지반인지 확인하는 질문이다.

## 1. 3-way handshake — 왜 하필 3번인가

TCP는 "보낸 데이터가 순서대로, 빠짐없이 도착한다"를 보장하는
프로토콜이고, 그 보장을 시작하려면 대화 전에 두 가지를 확정해야 한다:
**양쪽 모두 송신·수신이 가능한가**, 그리고 **데이터 순서를 셀 기준점
(시퀀스 번호 초기값)은 무엇인가**.

```
클라이언트                                서버
    │  ── SYN (seq=x) ──────────────▶     │   "연결하자. 내 번호는 x부터"
    │                                     │   (서버: SYN_RECEIVED 상태)
    │  ◀── SYN+ACK (seq=y, ack=x+1) ──    │   "잘 받았다(x+1). 내 번호는 y부터"
    │  ── ACK (ack=y+1) ────────────▶     │   "네 것도 잘 받았다(y+1)"
    │                                     │
  ESTABLISHED                        ESTABLISHED  → 이제 데이터 교환
```

전화 통화의 시작과 같다. "여보세요, 들리세요?"(SYN) — "네 들려요,
제 목소리는요?"(SYN+ACK) — "네 잘 들려요"(ACK). 이 세 마디가 끝나야
"서로의 말이 상대에게 닿는다"가 **양쪽 모두에게** 확인된다.

**왜 2번으로는 안 되는가**: SYN → SYN+ACK에서 멈추면, 클라이언트는
"내 송신 + 서버 수신 + 서버 송신"까지 확인했지만 **서버는 자기가 보낸
SYN+ACK이 도착했는지 모른다** — 즉 "서버 송신 → 클라이언트 수신"
방향이 미확인이다. 마지막 ACK이 그 마지막 조각을 채운다. 또한 2-way면
네트워크에 떠돌던 **옛날 SYN**(지연 도착한 과거 연결 시도)만으로
서버가 연결을 확립해버려, 아무도 쓰지 않는 유령 연결에 자원을 낭비하게
된다 — 3번째 ACK은 "이 연결 요청이 지금 유효하다"는 재확인이기도 하다.

**비용 감각이 핵심이다**: 이 절차는 네트워크 왕복 1회(1 RTT)를
소모하고, 데이터는 그 뒤에야 흐른다. 서울-미국 간이면 RTT가 100ms를
넘을 수 있으니, 요청마다 연결을 새로 맺으면 본론도 꺼내기 전에
100ms를 선불로 내는 셈이다. HTTPS면 TLS handshake 왕복이 더해져
선불이 더 커진다. **이 비용이 keep-alive와 커넥션 풀이 존재하는
이유다** — 한 번 맺은 연결을 재사용해 handshake를 상환하는 것.

## 2. 4-way handshake — 종료는 왜 한 번 더 많은가

종료가 4단계인 이유는 **TCP가 양방향(full-duplex) 통로이고, 두 방향을
따로 닫아야 하기 때문**이다. 내가 보낼 게 없어졌다고 해서 상대도
끝났다는 보장이 없다.

```
클라이언트(먼저 끊는 쪽)                    서버
    │  ── FIN ──────────────────────▶     │   "나는 보낼 게 끝났어"
 FIN_WAIT_1                          CLOSE_WAIT
    │  ◀── ACK ──────────────────────     │   "알았어" (아직 보낼 게 남았을 수 있음)
 FIN_WAIT_2                               │   ... 남은 데이터 마저 전송 ...
    │  ◀── FIN ──────────────────────     │   "나도 이제 끝났어"
    │  ── ACK ──────────────────────▶     │
 TIME_WAIT                            CLOSED
    │  (2MSL 대기 후)
  CLOSED
```

서버의 ACK과 FIN이 분리되어 있는 것이 4-way의 본질이다. FIN을 받은
서버는 "네 말은 끝났구나"라고 즉시 응답(ACK)하되, **자기가 보내던
데이터를 마저 보낸 뒤에야** 자기 쪽 FIN을 보낸다. 통화로 치면 "저는
할 말 다 했어요" — "알겠어요, 근데 저는 마저 할 말이 있어요 …(계속)…
이제 저도 끝났어요" — "네, 끊습니다"이다. 이렇게 한쪽만 닫힌 상태
(half-close)가 존재할 수 있다는 것이 3-way와의 구조적 차이다.

### TIME_WAIT — 먼저 끊은 쪽이 치르는 마무리 비용

마지막 ACK을 보낸 쪽(**먼저 끊은 쪽, active closer**)은 곧바로
소켓을 정리하지 않고 **TIME_WAIT** 상태로 일정 시간(2MSL — 패킷이
네트워크에서 살아있을 수 있는 최대 시간의 2배) 대기한다. 이유는
두 가지다.

1. **마지막 ACK 유실 대비**: ACK이 유실되면 서버는 FIN을 재전송한다.
   내가 이미 소켓을 없앴다면 그 FIN에 답할 수 없어 상대가 정상 종료를
   못 한다. TIME_WAIT 동안 자리를 지키며 재전송된 FIN에 다시 ACK할
   수 있어야 한다.
2. **지연 패킷의 새 연결 오염 방지**: 같은 주소·포트 조합으로 곧장
   새 연결을 맺었는데 옛 연결의 패킷이 뒤늦게 도착하면, 새 연결이
   그것을 자기 데이터로 착각할 수 있다. 옛 패킷이 자연 소멸할 때까지
   그 조합의 재사용을 막는 격리 기간이 TIME_WAIT이다.

즉 TIME_WAIT은 버그나 누수가 아니라 **프로토콜이 의도한 안전장치**다.
문제가 되는 것은 그 자체가 아니라 **대량으로 쌓이는 패턴**이다.

## 3. 실무 사례 — TIME_WAIT 폭증과 커넥션 재사용

이 지식이 운영에서 만나는 대표 현상: 외부 API를 대량 호출하는 서버에서
`netstat`을 치면 TIME_WAIT 소켓이 수만 개 보이고, 심하면 로컬 포트가
고갈되어 새 연결 자체가 실패한다(`Cannot assign requested address`).

원인은 대부분 **요청마다 연결을 새로 맺고 끊는 클라이언트 코드**다.
끊을 때마다 (먼저 끊는 쪽인) 클라이언트에 TIME_WAIT이 하나씩 남고,
로컬 포트는 유한하므로(수만 개 수준) 초당 수백 요청이면 금방 바닥난다.

```java
// Before: 매 호출마다 클라이언트 생성 — 요청마다 handshake + 종료,
// TIME_WAIT이 호출 수만큼 쌓인다
public String callApi() {
    RestClient client = RestClient.create();   // 새 커넥션 수립
    return client.get().uri(url).retrieve().body(String.class);
}   // 응답 후 연결 종료 → TIME_WAIT 적립

// After: 클라이언트를 빈으로 한 번만 만들어 커넥션 풀 공유 —
// keep-alive로 연결을 재사용하므로 handshake도 TIME_WAIT도 재사용분만큼 사라진다
@Configuration
class HttpClientConfig {
    @Bean
    RestClient restClient(RestClient.Builder builder) {
        return builder.baseUrl(apiUrl).build();  // 풀링되는 커넥션 재사용
    }
}
```

진단은 상태 분포를 세어보는 것부터다.

```bash
# 커넥션 상태별 개수 — TIME_WAIT이 비정상적으로 많은지 확인
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn
```

대응의 우선순위는 커널 파라미터 만지기가 아니라 **연결 재사용**이다.
keep-alive/커넥션 풀로 "맺고 끊는 횟수" 자체를 줄이는 것이 원인 치료
이고, 커널 옵션 조정은 증상 완화일 뿐이다. 또 하나의 설계 감각:
TIME_WAIT은 먼저 끊는 쪽에 남으므로, **어느 쪽이 먼저 끊는 구조인가**
가 어느 서버에 TIME_WAIT이 쌓이는가를 결정한다.

## 4. 꼬리질문 대비 포인트

### "왜 2-way로는 연결을 수립할 수 없나요?"

연결의 전제는 "양쪽 모두 송수신 가능"인데, 이는 네 가지 방향 확인
(내 송신, 내 수신, 상대 송신, 상대 수신)을 요구한다. SYN과 SYN+ACK
두 번만으로는 서버가 자신의 송신이 클라이언트에 닿는지 확인할 수 없다
— 마지막 ACK이 그 확인을 완성한다. 덧붙여 2-way면 네트워크를 떠돌다
뒤늦게 도착한 옛 SYN만으로 서버가 연결을 열어버려 유령 연결이 생긴다.
3번째 메시지는 "이 요청이 현재 유효하다"는 방어이기도 하다.

### "TIME_WAIT은 왜 존재하고, 클라이언트와 서버 중 어느 쪽에 생기나요?"

방향과 무관하게 **먼저 FIN을 보낸 쪽(active closer)**에 생긴다.
존재 이유는 (1) 마지막 ACK이 유실됐을 때 상대의 FIN 재전송에 다시
응답해 상대의 정상 종료를 보장하고, (2) 옛 연결의 지연 패킷이 같은
주소·포트 조합의 새 연결에 섞여 들어가는 것을 막기 위해서다. 즉
프로토콜이 의도한 안전장치이며, 없애야 할 대상이 아니라 대량으로
쌓이지 않게 연결을 재사용해야 할 대상이다.

### "서버에서 TIME_WAIT이 수만 개 발견됐습니다. 원인과 대응은?"

먼저 "누가 먼저 끊는가"를 본다. 우리 서버가 클라이언트로서 외부를
대량 호출하며 매번 연결을 새로 맺고 끊는 패턴이 가장 흔한 원인이다 —
대응은 HTTP 클라이언트의 커넥션 풀/keep-alive 활성화로 맺고 끊는
횟수 자체를 줄이는 것이다. 반대로 우리가 서버 입장인데 쌓인다면
keep-alive 없이 요청마다 끊는 클라이언트들 또는 서버가 먼저 끊는
설정(짧은 keep-alive 타임아웃 등)이 원인이다. 커널 파라미터 조정은
증상 완화일 뿐 원인 치료가 아니라는 순서를 지켜 답하는 것이 좋다.
포트 고갈로 신규 연결이 실패하는 지경이면 장애로 번지기 전 단계라는
심각도 감각도 함께 언급한다.

### "CLOSE_WAIT이 계속 쌓이는 건 무슨 의미인가요?" (가산점 포인트)

CLOSE_WAIT은 **상대의 FIN을 받고 ACK까지 보냈지만, 우리 쪽이 아직
close()를 호출하지 않은** 상태다. TIME_WAIT이 프로토콜의 정상 대기라면
CLOSE_WAIT 누적은 대부분 **애플리케이션 버그**다 — 응답 스트림이나
커넥션을 닫지 않는 코드, 반납되지 않는 리소스 누수가 원인이고, 시간이
지나도 저절로 사라지지 않아 결국 파일 디스크립터 고갈로 이어진다.
"TIME_WAIT은 정상의 산물, CLOSE_WAIT 누적은 코드의 문제"라는 구분을
말하면 운영 경험이 드러난다.

### "3-way handshake의 수립 비용은 시스템 설계에 어떤 영향을 주나요?" (시니어 변별 포인트)

handshake는 요청마다 반복하면 RTT × 요청 수만큼의 순수 대기이고,
HTTPS면 TLS 왕복까지 곱해진다. 그래서 설계 전반에 "연결을 재사용하는
장치"가 깔린다 — HTTP keep-alive, 서버 간 커넥션 풀, DB 커넥션 풀
모두 같은 비용을 상환하는 구조다. 또 SYN을 받고 ACK을 기다리는
half-open 상태는 서버 자원을 선점하므로, 이를 악용해 SYN만 대량으로
보내는 SYN flood 공격이 성립한다(backlog 큐 고갈 → 정상 연결 거부,
방어는 SYN cookie 등). "handshake를 안다"의 완성형은 절차 암기가
아니라, 이 비용과 상태가 커넥션 풀·keep-alive·DDoS 방어 같은 상위
설계의 존재 이유임을 연결해 말하는 것이다.

## 한 줄 요약

3-way는 양방향 송수신 확인과 시퀀스 번호 합의를 최소 횟수로 끝내는
절차이고, 4-way는 양방향 통로를 따로 닫느라 ACK과 FIN이 분리된
절차이며, 먼저 끊은 쪽에 남는 TIME_WAIT은 종료의 안전장치다 — 이
수립·종료 비용이 keep-alive와 커넥션 풀의 존재 이유이고, TIME_WAIT
폭증 같은 운영 현상을 읽는 지반이다.
