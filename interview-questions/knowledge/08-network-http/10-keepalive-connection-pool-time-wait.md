# keep-alive · 커넥션 풀 · TIME_WAIT — 연결 재사용이 왜 생존 문제인가

> 핵심 관전 포인트: **TCP 연결 하나를 새로 맺는 데는 3-way handshake +
> (HTTPS면) TLS handshake의 왕복 비용이 들고, 갓 맺은 연결은 slow
> start 때문에 전송 속도도 낮다. keep-alive는 이 비용을 낸 연결을
> 재사용하는 약속이고, 커넥션 풀은 그 재사용을 체계화한 관리자다.
> 재사용 없이 요청마다 연결을 만들고 닫으면, 먼저 닫은 쪽에 TIME_WAIT
> 소켓이 60초씩 쌓인다 — 같은 목적지로 나가는 클라이언트 쪽에서는
> 임시 포트(약 2.8만 개)가 고갈돼 "포트가 없어 연결 자체가 안 되는"
> 장애가 된다. 근본 대응은 커널 튜닝이 아니라 연결 재사용(클라이언트
> 풀, Nginx upstream keepalive)이다.**

---

## 0. 질문 + 의도

**질문**: "keep-alive와 커넥션 풀은 왜 중요한가요? `TIME_WAIT`이 대량 발생하는 원인과 대응은?"

**출제 의도**: 커넥션을 재사용하지 않는 클라이언트 코드가 포트
고갈로 이어지는 실제 장애 패턴을 아는지 — netstat/ss 출력에서 이상을
읽어내고 원인 코드를 짚어내는 운영 능력과 직결되는 질문이다.

## 1. 연결 수립의 비용 — keep-alive와 커넥션 풀의 존재 이유

HTTP 요청 하나를 보내려면 그 아래에서 벌어지는 일:

1. **TCP 3-way handshake** — 왕복 1회. 데이터를 보내기도 전에
   네트워크를 한 번 다녀온다.
2. **TLS handshake** (HTTPS) — 추가 왕복 + 인증서 검증 + 키 교환
   연산. 연결 수립 비용의 대부분이 여기다.
3. **slow start** — TCP는 갓 맺은 연결을 신뢰하지 않아 전송량을
   조금씩만 늘린다. 새 연결은 한동안 제 속도를 못 낸다.

요청마다 이 비용을 다시 내는 것은, 전화를 걸어 한 마디 하고 끊고
같은 상대에게 다시 걸기를 반복하는 것과 같다. **keep-alive**는
"통화를 끊지 말고 다음 용건도 이 전화로 하자"는 약속으로,
HTTP/1.1부터는 기본 동작이다(응답 후 연결 유지, `Connection: close`를
보내야 끊는다).

**커넥션 풀**은 이 재사용을 클라이언트 쪽에서 체계화한 것이다 —
맺어둔 연결 여러 개를 보관하고, 요청이 오면 빌려주고, 끝나면 회수해
다음 요청에 재사용한다. 최대 개수로 동시 사용량을 제한하고, 오래 논
연결을 청소하는 관리까지 담당한다. DB 커넥션 풀(HikariCP)과 HTTP
클라이언트 풀은 같은 원리의 형제다.

```java
// Before: 호출마다 새 클라이언트 — 매 요청이 새 TCP+TLS 연결을 만들고 닫는다
public PaymentResult pay(Order order) {
    RestTemplate rest = new RestTemplate();   // 풀 없음, 매번 생성
    return rest.postForObject(PAY_URL, order, PaymentResult.class);
}   // 요청 종료와 함께 연결도 버려짐 → 닫은 쪽에 TIME_WAIT 적립

// After: 커넥션 풀을 가진 클라이언트를 싱글턴 빈으로 — 연결을 재사용
@Bean
RestClient paymentClient(RestClient.Builder builder) {
    CloseableHttpClient http = HttpClients.custom()
            .setConnectionManager(PoolingHttpClientConnectionManagerBuilder.create()
                    .setMaxConnPerRoute(50)      // 목적지(호스트)당 최대 연결
                    .setMaxConnTotal(100)
                    .build())
            .evictIdleConnections(TimeValue.ofSeconds(30))  // 서버의 idle timeout보다 짧게
            .build();
    return builder
            .requestFactory(new HttpComponentsClientHttpRequestFactory(http))
            .build();
}
```

중요한 것은 keep-alive가 **성능 최적화이면서 동시에 장애 예방**이라는
점이다. 재사용하지 않으면 아래의 TIME_WAIT 문제로 직행한다.

## 2. TIME_WAIT — 4-way handshake가 남기는 그림자

### 정체와 존재 이유

TCP 연결 종료(4-way handshake)에서 **먼저 FIN을 보낸 쪽(능동
종료자)** 은 마지막 ACK를 보낸 뒤 바로 사라지지 않고 **TIME_WAIT**
상태로 2×MSL(패킷의 최대 생존 시간의 2배, 리눅스에서는 60초 고정)
동안 머문다. 이유는 두 가지다:

1. 내가 보낸 마지막 ACK가 유실되면 상대가 FIN을 재전송하는데, 그때
   받아줄 소켓이 남아 있어야 상대가 깔끔하게 종료된다.
2. 같은 주소 쌍(내 IP:포트 ↔ 상대 IP:포트)으로 **곧바로 새 연결**이
   생기면, 네트워크를 떠돌던 이전 연결의 늦은 패킷이 새 연결의
   데이터로 오인될 수 있다 — 그 패킷들이 자연사할 시간을 벌어주는
   격리 기간이다.

즉 TIME_WAIT 자체는 버그가 아니라 **정상 종료 절차의 산물**이다.
문제는 "대량"일 때다.

### 대량 발생의 원인 — 짧은 연결의 대량 생성 + 우리가 먼저 닫음

TIME_WAIT은 **먼저 닫은 쪽**에 남으므로, 대량으로 쌓였다는 것은
"우리 쪽이 짧은 연결을 대량으로 만들고 먼저 닫고 있다"는 뜻이다.
전형적 범인:

- 위 Before 코드처럼 **요청마다 클라이언트/연결을 새로 만드는 코드**로
  외부 API를 고빈도 호출.
- **Nginx → 백엔드(Tomcat) 구간을 upstream keepalive 없이** 운영 —
  기본 동작으로는 요청마다 백엔드 연결을 새로 맺고 끊는다.
- 애플리케이션이나 프록시가 `Connection: close`를 강제하는 설정.

### 왜 장애가 되나 — 임시 포트 고갈의 산수

바깥으로 나가는 연결은 (내 IP, **내 임시 포트**, 상대 IP, 상대 포트)
네 값의 조합으로 식별된다. 상대가 고정(예: 결제 API의 IP:443)이면
가변부는 내 임시 포트뿐인데, 리눅스 기본 범위는 약 2.8만 개
(`net.ipv4.ip_local_port_range` 기본 32768~60999)다.

TIME_WAIT이 60초 유지되므로: **같은 목적지로 초당 500개씩 연결을
만들고 닫으면 60초 후 TIME_WAIT이 3만 개** — 임시 포트가 바닥나고,
새 연결 시도는 `EADDRNOTAVAIL`(Cannot assign requested address)로
실패한다. 증상은 "외부 API 호출이 간헐적으로 연결 단계부터 실패",
원인은 코드의 연결 비재사용이다. 트래픽이 늘던 어느 날 갑자기
터지는, 전형적인 "잘 돌던 코드가 규모에서 무너지는" 패턴이다.

## 3. 진단과 대응 — 순서가 중요하다

### 진단: 어디로 향한 TIME_WAIT인가

```bash
ss -s                          # 상태별 소켓 개수 요약 — timewait 규모 확인
ss -tan state time-wait | awk '{print $4}' | sort | uniq -c | sort -rn | head
# → TIME_WAIT이 "어느 목적지(IP:포트)로" 몰려 있는지 집계 — 범인 식별
```

몰린 목적지가 외부 API면 해당 호출 코드의 클라이언트 재사용 여부를,
자기 백엔드 포트(예: 8080)면 프록시-백엔드 구간의 keepalive 설정을
의심한다.

### 1순위 대응: 연결 재사용 (근본 원인 제거)

- 애플리케이션: 1절의 After 코드처럼 **풀을 가진 클라이언트를 싱글턴으로**.
- Nginx → 백엔드 구간:

```nginx
# Before: 기본 동작 — 요청마다 백엔드 연결 생성/종료, TIME_WAIT은 Nginx 서버에 적립
upstream app { server 127.0.0.1:8080; }

# After: 백엔드로의 유휴 연결을 풀처럼 유지
upstream app {
    server 127.0.0.1:8080;
    keepalive 64;                     # 유지할 유휴 연결 수
}
server {
    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;       # keep-alive는 HTTP/1.1 전제
        proxy_set_header Connection ""; # 클라이언트의 close 헤더 전파 차단
    }
}
```

### 2순위 대응: 커널 완화 (증상 완화일 뿐)

- `net.ipv4.tcp_tw_reuse=1` — **바깥으로 나가는 연결에 한해**
  TIME_WAIT 소켓의 포트를 재사용 허용(TCP timestamp로 이전 연결의
  늦은 패킷을 구분할 수 있을 때만). 비교적 안전한 완화책.
- `net.ipv4.ip_local_port_range` 확대 — 포트 여유분을 늘린다.
- **하지 말 것**: `tcp_tw_recycle` — NAT 뒤의 여러 클라이언트를
  오판해 정상 연결을 끊는 부작용으로 악명이 높았고, 최신 리눅스
  커널에서는 아예 제거됐다. 검색으로 나오는 오래된 튜닝 글의 대표적
  함정이다.

순서를 강조할 것: 커널 튜닝부터 꺼내는 답은 "증상 덮기"다. 원인은
연결을 재사용하지 않는 구조이고, 튜닝은 재사용을 적용하기까지의
시간 벌기 또는 마지막 여유분 확보로 답해야 운영 감각이 드러난다.

## 4. 꼬리질문 대비 포인트

### "TIME_WAIT은 왜 존재하나요? 그냥 짧게 줄이면 안 되나요?"

마지막 ACK 유실 시 상대의 FIN 재전송을 받아줄 소켓을 남겨두고, 같은
주소 쌍의 새 연결이 이전 연결의 늦은 패킷을 자기 데이터로 오인하지
않도록 격리 기간을 두는 것이다. 그래서 2×MSL(리눅스 60초)이며,
리눅스에서는 이 값이 커널에 고정돼 있어 sysctl로 못 줄인다. 흔히
`tcp_fin_timeout`으로 줄인다고 알려져 있지만 그것은 FIN_WAIT_2
상태의 타이머라 TIME_WAIT과 무관하다 — 이 구분을 하면 실제로 만져본
사람이다. (가산점 포인트)

### "서버 입장(우리가 연결을 받는 쪽)에서 TIME_WAIT이 쌓이면 무엇이 다른가요?"

받는 쪽의 포트는 고정된 리슨 포트 하나라 임시 포트 고갈 문제는 없고,
소켓 테이블 항목이 늘어나는 부담 정도라 같은 개수라도 위험도가
낮다. 대신 "서버 쪽에 TIME_WAIT이 쌓인다 = 서버가 먼저 닫고 있다"는
신호이므로, keep-alive가 꺼져 있거나 idle timeout이 지나치게 짧아
재사용이 안 되고 있는지 점검할 단서가 된다. TIME_WAIT을 볼 때는
개수보다 "어느 방향의 연결에서, 누가 먼저 닫아서 생겼나"를 읽는 것이
핵심이다.

### "keep-alive idle timeout을 클라이언트가 서버보다 길게 잡으면 무슨 일이 생기나요?"

서버가 유휴 연결을 먼저 닫았는데 클라이언트 풀은 그 연결을 살아있다
믿고 재사용하는 순간이 생긴다 — 요청을 쓰자마자 connection reset을
맞는 간헐 오류(재현도 안 되는 유령 에러)가 된다. 그래서 규칙은
**클라이언트(호출하는 쪽)의 idle 상한 < 서버(받는 쪽)의 idle
상한**이고, 풀의 유휴 연결 정리 주기를 서버 timeout보다 짧게 잡거나
재사용 전 검증을 켠다. Nginx ↔ Tomcat 사이, 앱 ↔ 외부 API 사이 모두
같은 원리다.

### "TIME_WAIT 3만 개가 보입니다. 이것만으로 장애 상황인가요?"

아니다. TIME_WAIT 개수 자체는 "짧은 연결이 많이 만들어지고 있다"는
사실의 표시일 뿐이고, 장애 여부는 **임시 포트 사용률과 연결 실패
발생 여부**로 판단한다 — 목적지별 집계로 특정 목적지에 몰렸는지,
`EADDRNOTAVAIL`류 연결 실패나 그 시점의 에러 로그가 있는지를 본다.
실패가 없다면 지금은 "낭비"이지 "장애"는 아니므로, 연결 재사용
개선을 과제로 잡되 긴급 대응은 아니다. 숫자 하나에 놀라지 않고
영향으로 판단하는 순서를 보여주는 것이 포인트다.

### "커넥션 풀 크기는 어떻게 정하나요?" (시니어 변별 포인트)

수요와 공급의 산수다. 필요한 동시 연결 수 ≈ 대상으로의 초당 요청 수
× 평균 응답시간(리틀의 법칙)이고, 여기에 스파이크 여유를 더해
시작점을 잡은 뒤 실측으로 조정한다. 무작정 키우면 상대 서버에
연결을 그만큼 꽂아넣는 것이라 상대의 스레드·연결 자원을 잠식하고,
장애 시 재시도 폭주의 통로가 된다. 또 풀 크기와 함께 "풀에서
연결을 얻기까지의 대기 타임아웃"을 반드시 설정해, 풀 고갈이 무한
대기(스레드 인질)가 아니라 빠른 실패로 드러나게 해야 한다 — 풀은
성능 장치이자 동시성 제한(bulkhead) 장치라는 관점까지 말하면 설계
경험이 드러난다.

## 한 줄 요약

keep-alive와 커넥션 풀은 handshake·TLS·slow start라는 연결 수립
비용을 재사용으로 상쇄하는 장치이자, 요청마다 연결을 만들고 닫을 때
먼저 닫은 쪽에 60초씩 쌓이는 TIME_WAIT이 임시 포트 고갈(약 2.8만
개)로 번지는 장애를 막는 방어선이다 — 대량 TIME_WAIT의 대응은 커널
튜닝(tcp_tw_reuse는 완화, tw_recycle은 금지)이 아니라 클라이언트
풀·Nginx upstream keepalive로 연결을 재사용하게 만드는 것이 근본이다.
