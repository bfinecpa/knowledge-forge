# HTTP 상태 코드 사용 기준 — 클라이언트·모니터링·재시도가 의존하는 계약

> 핵심 관전 포인트: **상태 코드는 첫 자리가 책임 소재를 가른다 —
> 2xx 성공, 3xx 리다이렉트, 4xx는 클라이언트 잘못(고쳐서 보내야 하며
> 재시도 무의미), 5xx는 서버 잘못(재시도 후보). 세부적으로는
> 201(생성됨)·204(성공, 본문 없음)로 성공의 종류를, 401(누군지
> 모름)·403(누군지 알지만 권한 없음)으로 인증과 인가를,
> 409로 리소스 상태 충돌을, 502(뒷단이 죽었거나 이상 응답)·
> 504(뒷단이 느림)로 게이트웨이 뒤의 장애 양상을 구분해 전달한다.
> 이 코드를 정확히 쓰는 API는 에러율 대시보드와 자동 재시도가 제대로
> 동작하고, 전부 200에 에러 바디를 담는 API는 모니터링이 장님이 된다.**

---

## 0. 질문 + 의도

**질문**: "HTTP 상태 코드: 200/201/204, 301/302, 400/401/403/404/409,
500/502/503/504의 의미와 사용 기준은?"

**출제 의도**: 상태 코드는 클라이언트·모니터링·재시도 로직이 모두
의존하는 계약이다. 401/403 구분, 409의 활용을 정확히 하는 사람의
API는 장애 시 에러율 분류가 가능하고, 대충 200에 에러 바디를 넣는
사람의 API는 모니터링이 눈뜬장님이 된다.

## 1. 큰 그림 — 첫 자리가 말하는 것

상태 코드는 개별 암기 이전에 **첫 자리 숫자의 의미 체계**로 잡아야
한다. 첫 자리가 "누구 잘못이고, 받은 쪽이 무엇을 해야 하는가"를
말해주기 때문이다.

| 대역 | 의미 | 받은 쪽의 행동 |
|---|---|---|
| 2xx | 성공 | 결과를 사용 |
| 3xx | 다른 곳으로 가라 | 안내된 위치로 재요청 |
| 4xx | **요청(클라이언트)이 잘못됨** | 요청을 고치기 전엔 재시도 무의미 |
| 5xx | **서버가 처리에 실패함** | 잠시 후 재시도해볼 수 있음 |

이 구분이 곧 자동화의 근거다. 재시도 라이브러리는 5xx만 재시도하고
4xx는 즉시 포기한다(같은 요청을 다시 보내봐야 같은 이유로 거절되므로).
모니터링은 5xx 비율로 "우리 잘못인 장애"를, 4xx 비율로 "클라이언트
이상(잘못된 연동, 공격 시도)"을 따로 집계한다. 상태 코드를 틀리게
쓰면 이 자동화가 전부 오작동한다.

## 2. 2xx — 성공에도 종류가 있다

- **200 OK**: 일반 성공. 응답 본문에 결과가 담긴다. 조회·수정의 기본값.
- **201 Created**: 요청이 **새 리소스를 생성**했다. POST로 주문·회원을
  만들었을 때의 정답이며, 생성된 리소스의 위치를 `Location` 헤더로
  알려주는 것이 규약의 완성형이다.
- **204 No Content**: 성공했고 **돌려줄 본문이 없다**. DELETE 성공,
  본문 없는 PUT 성공의 전형. 클라이언트에게 "본문 파싱하지 마라"를
  코드로 알려주는 것이다.

```java
// Before: 뭘 하든 200 — 성공의 의미가 뭉개진다
@PostMapping("/orders")
public ResponseEntity<Order> create(@RequestBody OrderRequest req) {
    return ResponseEntity.ok(orderService.create(req));  // 생성인데 200
}

// After: 생성은 201 + Location
@PostMapping("/orders")
public ResponseEntity<Order> create(@RequestBody OrderRequest req) {
    Order order = orderService.create(req);
    return ResponseEntity
            .created(URI.create("/orders/" + order.getId()))  // 201 + Location
            .body(order);
}
```

## 3. 3xx — 301과 302, "얼마나 오래 가는 이사인가"

- **301 Moved Permanently**: **영구 이전**. 브라우저·크롤러가 이
  응답을 캐시하고, 검색엔진은 링크 평가를 새 주소로 옮긴다.
  도메인 변경, `http → https` 강제 전환에 쓴다.
- **302 Found**: **임시 이전**. 캐시되지 않고, 다음에도 원래 주소로
  다시 온다. 로그인 후 리다이렉트, 일시적 이벤트 페이지 이동에 쓴다.

사용 기준은 "**이 이전이 되돌려질 수 있는가**"다. 301의 무서운 점은
캐시다 — 실수로 301을 내려보내면 클라이언트 브라우저에 이전 정보가
박제되어, 서버 설정을 되돌려도 사용자는 계속 옛 응답대로 이동한다.
서버 로그에는 아무것도 안 남는(캐시가 서버에 안 물어보므로) 되돌리기
어려운 실수이므로, 확신이 없으면 302로 시작하는 것이 실무 감각이다.

(가산점 포인트) 301/302는 오랜 브라우저 관행상 재요청 시 POST가
GET으로 바뀔 수 있다. 메서드를 보존해야 하는 리다이렉트에는
307(임시)/308(영구)이 따로 있다 — 이 구분을 알면 API 게이트웨이
리다이렉트 설계에서 실수를 피할 수 있다.

## 4. 4xx — 클라이언트 잘못을 정확하게 분류하기

- **400 Bad Request**: 요청 자체가 문법·형식·값 검증에서 틀렸다.
  파싱 불가 JSON, 필수 필드 누락, 형식 위반. "고쳐서 다시 보내라."
- **401 Unauthorized**: **누구인지 모른다** — 인증(authentication)
  실패. 토큰이 없거나, 만료됐거나, 위조됐다. 올바른 자격증명으로
  다시 오면 해결된다. 이름과 달리 인가가 아니라 인증의 코드다.
- **403 Forbidden**: **누구인지는 알지만 권한이 없다** — 인가
  (authorization) 실패. 일반 사용자가 관리자 API를 호출한 경우.
  재로그인해도 소용없다는 점이 401과의 실질적 차이다.
- **404 Not Found**: 리소스가 없다. 보안 목적으로 "존재하지만 너에게
  숨기고 싶은" 리소스에도 쓴다(아래 꼬리질문).
- **409 Conflict**: 요청 자체는 멀쩡하지만 **리소스의 현재 상태와
  충돌**한다. 이미 존재하는 아이디로 가입, 이미 취소된 주문의 결제
  시도, 낙관적 락 버전 불일치. "지금 상태를 다시 확인하고 와라."

401/403 구분은 클라이언트 동작을 가른다 — 401을 받으면 앱은 토큰
갱신이나 로그인 화면 이동을 자동으로 수행하고, 403을 받으면 "권한
없음" 안내를 띄운다. 서버가 이 둘을 섞어 내리면 클라이언트는 권한
부족인데 무한 재로그인을 돌리는 식으로 오동작한다.

409는 아는 사람이 적어서 변별력이 있다. 400(요청 형식이 틀림)과
409(형식은 맞지만 상태와 안 맞음)를 구분해 쓰면, 클라이언트가
"입력을 고쳐라"와 "최신 상태를 다시 조회하라"를 코드만 보고 분기할
수 있다.

```java
// After: 같은 "실패"라도 원인별로 다른 코드 — 클라이언트가 분기할 수 있다
@PostMapping("/members")
public ResponseEntity<?> signUp(@Valid @RequestBody SignUpRequest req) {
    // @Valid 실패(형식 오류)는 전역 핸들러에서 400으로
    if (memberService.existsByLoginId(req.loginId())) {
        // 형식은 정상, 현재 상태(이미 존재)와 충돌 → 409
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(ErrorResponse.of("DUPLICATE_LOGIN_ID"));
    }
    Member member = memberService.signUp(req);
    return ResponseEntity.created(URI.create("/members/" + member.getId())).build();
}
```

## 5. 5xx — 서버 잘못, 그리고 "게이트웨이 뒤에서 무슨 일이"

- **500 Internal Server Error**: 서버 내부에서 처리 중 예외가 터졌다.
  처리하지 못한 예외의 기본 귀결이며, 원인은 서버 로그에 있다.
- **502 Bad Gateway**: 프록시/게이트웨이(Nginx, LB)가 **뒷단(업스트림)
  으로부터 정상 응답을 받지 못했다** — 뒷단이 죽어서 연결이 거부되거나,
  응답이 도중에 끊기거나, 해석 불가능한 응답이 온 경우.
- **503 Service Unavailable**: 서버가 **일시적으로 처리할 수 없는
  상태**다 — 과부하, 점검 중, 헬스체크 실패로 LB에서 제외된 상태.
  "지금은 안 되지만 나중엔 될 수 있다"는 뉘앙스가 500과 다르고,
  `Retry-After` 헤더로 재시도 시점을 안내할 수 있다.
- **504 Gateway Timeout**: 게이트웨이가 뒷단의 응답을 **제한 시간
  안에 받지 못했다** — 뒷단이 죽은 게 아니라 **느린** 것이다.

502와 504의 구분이 장애 초동 대응의 방향을 정한다. 502는 "뒷단
프로세스가 죽었나? 배포 중 커넥션이 끊겼나?"부터 보고(프로세스 상태,
재시작·배포 이력), 504는 "뒷단이 왜 느린가?"를 본다(스레드 풀 고갈,
느린 쿼리, 외부 API 지연). 같은 5xx라도 코드 하나가 "죽었다"와
"느리다"를 갈라주므로, 이 구분을 아는 사람은 장애 첫 1분에 볼 곳이
다르다.

## 6. "전부 200 + 에러 바디"가 만드는 재앙

실무에서 가장 흔한 안티패턴 — 모든 응답을 200으로 내리고 본문의
`success: false`로 실패를 표현하는 API. 기능은 돌아가지만 상태 코드
계약에 의존하는 모든 것이 망가진다:

1. **모니터링 실명(失明)**: 에러율 대시보드·알림은 5xx 비율을 본다.
   전부 200이면 서비스가 반쯤 죽어도 대시보드는 초록색이다 —
   장애를 사용자 문의로 처음 알게 된다.
2. **재시도 오동작**: 게이트웨이·클라이언트의 자동 재시도는 5xx를
   보고 동작한다. 200으로 포장된 서버 오류는 재시도 대상에서 빠진다.
3. **캐시 오염**: 200은 캐시 가능한 성공이다. 에러 바디가 CDN에
   캐시되면 서버가 복구된 뒤에도 사용자는 캐시된 에러를 계속 받는다.
4. **연동 비용 증가**: 표준 대신 우리만의 에러 규격을 모든 연동자가
   따로 학습·구현해야 한다.

```java
// Before: 모든 실패가 200 — 모니터링·재시도·캐시가 전부 속는다
return ResponseEntity.ok(Map.of("success", false, "message", "서버 오류"));

// After: 상태 코드로 계약을 지키고, 본문은 상세 설명에 쓴다
@ExceptionHandler(Exception.class)
public ResponseEntity<ErrorResponse> handleUnexpected(Exception e) {
    log.error("unhandled exception", e);
    return ResponseEntity.internalServerError()       // 500 — 서버 잘못임을 코드로 선언
            .body(ErrorResponse.of("INTERNAL_ERROR"));  // 상세 원인·추적 ID는 본문으로
}
```

원칙은 "**분류는 상태 코드로, 상세는 본문으로**"다. 상태 코드는
기계(모니터링·재시도·캐시)가 읽는 계약이고, 본문의 에러 코드·메시지는
사람과 클라이언트 개발자가 읽는 설명이다. 이 역할 분담을 말할 수
있으면 API를 "혼자 쓰는 기능"이 아니라 "생태계의 계약"으로 보는
시야가 드러난다.

## 7. 꼬리질문 대비 포인트

### "401과 403의 차이를 실제 API에서 어떻게 적용하나요?"

401은 인증 실패("누군지 모름") — 토큰 없음·만료·위조. 클라이언트는
토큰 갱신이나 로그인 유도로 대응한다. 403은 인가 실패("누군지 알지만
권한 없음") — 재로그인으로 해결되지 않으므로 권한 안내를 띄운다.
Spring Security 기준으로 인증 실패는 `AuthenticationEntryPoint`(401),
인가 실패는 `AccessDeniedHandler`(403)에서 처리하도록 진입점 자체가
분리되어 있다고 덧붙이면 실무 연결이 된다.

### "권한 없는 리소스에 403 대신 404를 주는 경우는 왜인가요?" (가산점 포인트)

403은 "리소스가 **존재한다**"는 정보를 흘린다. 예컨대 남의 주문
`GET /orders/1234`에 403을 주면 공격자는 1234번 주문이 존재함을 알고
ID를 순회하며 정찰할 수 있다. 존재 자체를 숨겨야 하는 리소스라면
"없음"과 "권한 없음"을 똑같이 404로 응답해 정보 노출을 막는다.
정확성(403)과 은닉(404) 사이의 보안 트레이드오프이며, GitHub이 비공개
저장소에 404를 주는 것이 유명한 예다.

### "502와 504가 떴을 때 각각 어디를 먼저 보나요?"

둘 다 게이트웨이(Nginx/LB)가 낸 코드이므로 문제는 그 **뒤**에 있다.
502는 뒷단에서 정상 응답 자체를 못 받은 것 — 앱 프로세스 생존 여부,
직전 배포/재시작 이력, 게이트웨이 에러 로그의 connection refused/reset
여부를 먼저 본다. 504는 뒷단이 시간 안에 응답을 못 준 것 — 앱은 살아
있으므로 스레드 풀 상태, 느린 쿼리, 외부 API 지연 등 "왜 느린가"를
본다. 그리고 앱 로그에 아무 흔적이 없는 502(요청이 앱에 도달 전
반려됨)가 가능하다는 점을 알면 "앱 로그가 깨끗한데 사용자는 에러를
본다"는 상황에서 헤매지 않는다.

### "409는 실무에서 구체적으로 언제 쓰나요?"

"요청은 유효하나 리소스의 현재 상태가 전제와 다를 때"다. 대표 사례
세 가지 — (1) 유니크 충돌: 이미 존재하는 아이디로 가입. (2) 상태 전이
위반: 이미 취소된 주문에 결제 확정 시도. (3) 낙관적 락 충돌: 내가
읽은 버전과 저장 시점 버전이 다름(동시 수정 감지). 공통점은
클라이언트가 **최신 상태를 다시 조회한 뒤 판단해야** 풀린다는 것이고,
그 행동 지침을 코드로 전달하는 것이 409의 역할이다.

### "재시도 로직을 만든다면 어떤 상태 코드를 재시도 대상으로 삼겠어요?" (시니어 변별 포인트)

기본 원칙은 "일시적 실패만 재시도"다. 5xx 중 503(일시적 불가,
`Retry-After` 존중)·502·504(게이트웨이 뒤 일시 장애 가능성)는 재시도
후보이고, 500은 코드 버그일 가능성이 높아 재시도 이득이 작다.
4xx는 원칙적으로 재시도 금지 — 단 429(요청 과다)는 예외적으로 대기 후
재시도 대상이다. 여기에 두 겹을 더하면 시니어 답변이 된다:
(1) 코드가 재시도 후보라도 **요청이 멱등해야** 재시도할 수 있다 —
504는 뒷단이 처리했을 수 있으므로 비멱등 POST의 재시도는 중복 실행
위험이 있다. (2) 재시도는 지수 백오프 + 지터로, 장애 중인 서버에
재시도 폭풍을 보태지 않아야 한다. 상태 코드 지식이 재시도 정책·멱등성
설계와 연결되는 지점이다.

---

## 한 줄 요약

상태 코드는 첫 자리로 책임 소재(4xx 클라이언트 / 5xx 서버)와 재시도
가능성을 선언하는 기계용 계약이며, 201/204로 성공의 종류를, 401/403으로
인증과 인가를, 409로 상태 충돌을, 502/504로 "뒷단이 죽었다/느리다"를
구분해 전달한다 — 이 계약을 지킨 API만이 모니터링·자동 재시도·캐시가
제대로 동작하고, 전부 200에 에러를 담는 API는 모니터링을 장님으로
만든다.
