# HTTP 상태 코드 사용 기준 — 클라이언트·모니터링·재시도가 의존하는 계약

> 핵심 관전 포인트: **상태 코드는 사람에게 보내는 메시지가 아니라 **기계가 읽는 계약**이다. 첫 자리가 "누구 잘못이고 받은 쪽이 무엇을 해야 하는가"를 선언한다 — 2xx 성공, 3xx 다른 곳으로 가라, 4xx는 요청 자체가 문제라 고치기 전엔 재시도해도 같은 결과, 5xx는 서버가 처리에 실패한 것이라 시간이 지나면 달라질 수 있으므로 재시도 후보. 이 4xx/5xx의 갈림은 "실패 원인이 요청 안에 있는가, 서버의 일시적 상태에 있는가"라는 한 가지 질문에서 나오며, 그래서 429(요청 과다)는 4xx인데도 재시도 대상이고(원인이 요청 내용이 아니라 타이밍이므로) 504를 받은 비멱등 POST는 5xx인데도 함부로 재시도하면 안 된다(뒷단이 이미 처리했을 수 있으므로 — 재시도 가능 여부의 최종 판단은 상태 코드가 아니라 멱등성이 쥔다). 세부적으로는 201+Location과 202 Accepted로 "만들었다"와 "접수만 했다"를, 204와 200+빈 배열로 "본문 없음"과 "빈 결과"를, 301/302/307/308의 네 조합으로 영구·임시와 메서드 보존 여부를, 401(누군지 모름)·403(알지만 권한 없음)으로 인증과 인가를, 409로 상태 충돌을, 422로 "문법은 맞는데 의미가 틀림"을, 502(뒷단이 죽었거나 깨진 응답)·504(뒷단이 느림)로 게이트웨이 뒤의 장애 양상을 구분해 전달한다. 이 계약을 지킨 API만 에러율 대시보드와 자동 재시도가 제대로 동작하고, 전부 200에 에러 바디를 담는 API는 모니터링을 장님으로 만든다.**

---

## 0. 질문 + 의도

**질문**: "HTTP 상태 코드: 200/201/204, 301/302, 400/401/403/404/409, 500/502/503/504의 의미와 사용 기준은?"

**출제 의도**: 상태 코드는 클라이언트·모니터링·재시도 로직이 모두 의존하는 계약이다. 401/403 구분, 409의 활용을 정확히 하는 사람의 API는 장애 시 에러율 분류가 가능하고, 대충 200에 에러 바디를 넣는 사람의 API는 모니터링이 눈뜬장님이 된다.

## 1. 큰 그림 — 첫 자리가 정하는 것

### 1-1. 상태 코드는 사람이 아니라 기계가 읽는다

먼저 관점 하나를 바로잡자. 상태 코드를 "에러 메시지의 짧은 버전"으로 생각하면 이 문서의 나머지가 전부 사소해 보인다. 어차피 본문에 `"message": "로그인이 필요합니다"`라고 적어 보낼 텐데 숫자를 정확히 고르는 게 뭐가 그리 중요한가 싶어진다.

**상태 코드의 진짜 독자는 사람이 아니라 소프트웨어다.** 브라우저, CDN, 프록시, 로드밸런서, HTTP 클라이언트 라이브러리, 재시도 모듈, APM과 에러율 대시보드. 이들은 응답 본문의 한국어 메시지를 읽지 못하고 읽으려 하지도 않는다. 오직 세 자리 숫자만 보고 자기 행동을 결정한다.

그래서 상태 코드는 **기계에게 보내는 구조화된 지시**에 가깝다. 본문은 사람과 클라이언트 개발자가 읽는 설명이고, 상태 코드는 기계가 읽는 분류다. 이 역할 분담을 놓치면 3절의 재앙이 그대로 일어난다.

### 1-2. 첫 자리가 말하는 것 — 누구 잘못이고, 무엇을 해야 하는가

상태 코드는 개별 암기 이전에 **첫 자리 숫자의 의미 체계**로 잡아야 한다. 코드가 수십 개지만 첫 자리는 다섯 개뿐이고, 실무에서 마주치는 판단의 대부분은 첫 자리 수준에서 끝난다.

| 대역 | 뜻 | 받은 쪽이 해야 할 일 |
|---|---|---|
| 1xx | 정보 — 계속 진행 중 | 대개 인프라 층에서 처리, 앱이 신경 쓸 일 드묾 |
| 2xx | 성공 | 결과를 사용 |
| 3xx | 다른 곳으로 가라 | 안내된 위치로 재요청 |
| 4xx | **요청(클라이언트)이 잘못됨** | 요청을 고치기 전에는 다시 보내도 소용없음 |
| 5xx | **서버가 처리에 실패함** | 잠시 후 다시 보내볼 수 있음 |

여기서 4xx와 5xx의 구분을 "누구 잘못인가"로만 외우면 절반만 아는 것이다. 이 구분이 실무에서 값을 하는 이유는 **책임 소재보다 "그래서 어떻게 할 것인가"를 결정해 주기 때문**이다. 다음 절이 그 논리다.

### 1-3. 왜 4xx는 재시도해도 소용없고 5xx는 재시도할 수 있는가

이 문서의 뼈대가 여기다. 결론부터 외우지 말고 논리를 따라가 보자.

**재시도가 의미를 가지려면 딱 한 가지 조건이 성립해야 한다. "같은 요청을 조금 뒤에 다시 보냈을 때 결과가 달라질 수 있어야 한다."** 결과가 반드시 같을 것이 확실하다면 재시도는 시간 낭비이고, 부하를 늘리는 해악일 뿐이다.

그러면 언제 결과가 달라질 수 있는가. **실패의 원인이 어디에 있는지**에 달렸다. 원인이 될 수 있는 자리는 둘뿐이다 — 요청 안이거나, 서버의 상태 안이거나.

```
[4xx — 실패 원인이 "요청" 안에 있다]

  요청 (그대로)  --->  서버 (판정)  --->  거절
     |
     '-- 재시도해도 요청은 한 글자도 안 바뀐다
         서버의 판정 기준도 안 바뀐다
         ==> 같은 입력, 같은 규칙, 같은 결과. 몇 번을 보내도 거절.

  예) 토큰이 만료됐다(401), 권한이 없다(403), 필수 필드가 빠졌다(400),
      그런 리소스가 없다(404)
      -- 이 사실들은 1초 뒤에도, 1시간 뒤에도 그대로다.


[5xx — 실패 원인이 "서버의 상태" 안에 있다]

  요청 (문제 없음)  --->  서버 (지금 힘듦)  --->  실패
                            |
                            '-- 이 상태는 시간이 지나면 변한다
                                과부하는 가라앉고, 재기동은 끝나고,
                                끊긴 DB 커넥션은 다시 붙는다
                                ==> 같은 요청, 달라진 서버 상태, 다른 결과 가능
```

**즉 4xx는 결정론적 실패이고 5xx는 상태 의존적 실패다.** 4xx는 요청이라는 입력이 고정돼 있으므로 재시도해도 같은 함수에 같은 값을 넣는 것과 같고, 5xx는 서버 컨디션이라는 숨은 변수가 시간에 따라 변하므로 재시도가 다른 결과를 낳을 여지가 있다.

이 논리를 이해하면 자동화가 왜 그렇게 만들어졌는지도 자연히 설명된다. 재시도 라이브러리가 "5xx만 재시도, 4xx는 즉시 포기"를 기본값으로 삼는 이유는 규칙을 외워서가 아니라, **재시도가 의미를 가질 수 있는 유일한 대역이 5xx이기 때문**이다.

### 1-4. 실무의 함정 둘 — 429는 4xx인데 재시도 대상이고, 5xx라고 다 재시도해선 안 된다

앞의 논리를 "4xx는 재시도 금지, 5xx는 재시도 허용"이라는 규칙으로만 압축해 외우면 실무에서 두 번 넘어진다. 규칙이 아니라 논리를 잡아야 하는 이유가 여기 있다.

**함정 ① — 429 Too Many Requests는 4xx인데 재시도해야 한다.**

429는 "요청 한도를 초과했다"는 뜻이다. 4xx에 속하니 앞의 논리대로면 재시도해도 소용없어야 하는데, 실제로는 정반대다. 잠시 기다렸다가 다시 보내면 성공한다.

논리로 돌아가면 이유가 보인다. **429의 실패 원인은 요청의 "내용"이 아니라 요청의 "타이밍과 빈도"에 있다.** 요청 자체는 완벽히 유효하고, 다만 지금 이 순간 너무 자주 보냈을 뿐이다. 그리고 타이밍은 시간이 지나면 바뀐다 — 원인이 시간에 따라 변하는 값이므로, 결과도 달라질 수 있다. 4xx라는 대역에 있지만 성질은 5xx에 가까운 것이다.

그래서 429는 **`Retry-After` 헤더**를 함께 내려주는 것이 규약의 완성형이다. 이 헤더는 "몇 초 뒤에(또는 어느 시각 이후에) 다시 오라"는 값을 담아, 클라이언트가 아무 때나 다시 두드려 상황을 악화시키지 않게 안내한다. 클라이언트는 이 값을 존중해 대기해야 한다.

비슷한 성격이 하나 더 있다. **408 Request Timeout**은 "클라이언트가 요청을 제한 시간 안에 다 보내지 않았다"는 뜻이라 역시 요청 내용의 문제가 아니고, 다시 보내면 성공할 수 있다.

**함정 ② — 5xx여도 멱등하지 않은 POST는 함부로 재시도하면 안 된다.**

이쪽이 더 위험하다. 5xx를 받았으니 재시도해도 된다고 판단하는 순간 중복 결제가 난다.

이유는 **5xx가 "서버가 아무것도 안 했다"를 보장하지 않기 때문**이다. 특히 504 Gateway Timeout이 그렇다. 504는 게이트웨이(프록시·로드밸런서)가 뒷단의 응답을 제한 시간 안에 받지 못했다는 뜻인데, **뒷단은 살아 있고 지금도 그 요청을 처리하고 있거나 이미 처리를 끝냈을 수 있다.** 게이트웨이가 기다리다 지쳐 먼저 포기한 것뿐이다.

```
[504를 받았을 때 실제로 서버에서 벌어졌을 수 있는 일]

  클라이언트        게이트웨이                     앱 서버
      |                 |                            |
      |-- POST /pay --->|--- 전달 ------------------>|  결제 처리 시작
      |                 |                            |  ... 오래 걸림 ...
      |                 |  X 응답 대기 시간 초과      |  결제 INSERT + COMMIT ★
      |<-- 504 ---------|                            |  (돈은 이미 빠져나갔다)
      |                                              |
      ★ 클라이언트는 실패로 알지만 서버 상태는 이미 바뀌었다.
        여기서 재시도하면 두 번 결제된다.
```

502도 마찬가지다. 뒷단이 응답을 보내던 도중 연결이 끊겨 게이트웨이가 502를 냈다면, 그 요청은 이미 처리가 끝난 뒤일 수 있다.

그래서 정확한 판단 순서는 **"상태 코드가 재시도 후보인가"를 먼저 보고, 그다음 "이 요청이 멱등한가"를 봐야** 한다. 두 조건이 모두 참일 때만 재시도한다.

```
재시도해도 되는가?

  ① 상태 코드가 재시도 후보인가?    (5xx 일부, 429, 408)
        아니오 -> 재시도 금지
        예     -> ②로

  ② 이 요청이 멱등한가?             (GET/HEAD/OPTIONS/PUT/DELETE, 또는 멱등성 키가 있는 POST)
        아니오 -> 재시도 금지. 조회로 처리 여부 확인 후 판단.
        예     -> 재시도 (지수 백오프 + 지터)
```

**재시도 가능 여부의 최종 결정권은 상태 코드가 아니라 멱등성이 쥐고 있다.** 상태 코드는 "다시 보내면 성공할 가능성이 있는가"만 말해주고, "다시 보내도 안전한가"는 메서드의 멱등성이 말해준다. 이 두 질문이 다르다는 것을 구분하는 것이 실무 판단의 핵심이다. (멱등성은 04번 문서에서 자세히 다룬다.)

### 1-5. 이 계약을 믿고 움직이는 것들

상태 코드를 정확히 쓰는 것이 왜 취향이 아니라 필수인지는, 이 숫자를 읽고 자기 행동을 바꾸는 것들을 열거해 보면 분명해진다.

**재시도 라이브러리와 게이트웨이**는 앞에서 본 대로 5xx를 보고 재시도한다. Spring Retry, Resilience4j, 각종 HTTP 클라이언트의 재시도 설정, Nginx의 `proxy_next_upstream` 지시자가 전부 상태 코드를 조건으로 삼는다. 이들은 내 비즈니스 로직을 모르고 숫자만 본다.

**모니터링과 알림**은 **5xx 비율을 "우리 잘못인 장애"로, 4xx 비율을 "클라이언트 이상"으로** 따로 집계한다. 이 분리가 성립해야 "에러율 1% 초과 시 호출" 같은 알림 규칙이 의미를 갖는다. 4xx와 5xx가 섞이면 잘못된 연동을 하는 클라이언트 하나 때문에 새벽에 호출당하거나, 반대로 진짜 장애가 클라이언트 오류에 묻힌다.

여기에 **로드밸런서의 헬스체크**도 얹힌다. 헬스체크 엔드포인트가 2xx를 주면 살아 있는 인스턴스로 판정해 트래픽을 보내고, 5xx를 주면 풀에서 제외한다. 앱이 DB 연결을 잃었는데도 헬스체크가 200을 반환하면, 로드밸런서는 그 인스턴스가 멀쩡하다고 믿고 계속 요청을 밀어 넣는다.

**브라우저와 프록시, 캐시**는 코드에 따라 응답을 저장할지 말지를 정한다. 200은 기본적으로 캐시 가능한 성공이고, 301은 영구 이전이라 브라우저가 오래 기억하며, 304는 "네가 가진 캐시가 아직 유효하다"는 뜻으로 본문 없이 캐시 재사용을 지시한다. 코드가 틀리면 캐시가 틀린 것을 오래 붙잡는다.

**클라이언트 앱의 분기 로직**도 상태 코드 위에 세워진다. 401을 받으면 토큰을 갱신하거나 로그인 화면으로 보내고, 403을 받으면 권한 안내를 띄우고, 409를 받으면 최신 상태를 다시 조회한다. 서버가 이 코드들을 섞어 내리면 클라이언트는 권한 부족인데 무한 재로그인을 도는 식으로 오동작한다.

## 2. 대역별 사용 기준

### 2-1. 2xx — 성공에도 종류가 있다

성공을 전부 200으로 내려도 화면은 잘 그려진다. 그래서 2xx 구분은 "굳이 왜?"라는 반문이 가장 많이 나오는 지점이다. 각 코드가 **무엇을 추가로 알려주는지**를 기준으로 보면 이유가 보인다.

**200 OK — 일반 성공, 본문에 결과가 담겨 있다.** 조회와 수정의 기본값이다. 클라이언트는 본문을 파싱해 결과를 쓰면 된다.

**201 Created — 요청이 새 리소스를 만들었다.** 200과의 차이는 "성공했다"에 **"그래서 새로운 것이 생겼다"**가 추가된 것이다. 그리고 새로운 것이 생겼다면 클라이언트가 던질 다음 질문은 정해져 있다 — **"그게 어디에 있는데?"** 그 답을 담는 것이 `Location` 헤더다.

```java
// Before: 뭘 하든 200 — 성공의 의미가 뭉개진다
@PostMapping("/orders")
public ResponseEntity<Order> create(@RequestBody OrderRequest req) {
    return ResponseEntity.ok(orderService.create(req));  // 생성인데 200
}

// After: 생성은 201 + Location
@PostMapping("/orders")
public ResponseEntity<Order> create(@RequestBody OrderRequest req) {
    Order order = orderService.create(req);
    // ResponseEntity.created(URI)는 201 상태와 Location 헤더를 함께 세팅한다.
    // Location은 "방금 만든 것의 주소"이므로, 클라이언트는 응답 본문을 파싱하지 않고도
    // 이 헤더만으로 후속 조회·수정 요청을 조립할 수 있다.
    return ResponseEntity
            .created(URI.create("/orders/" + order.getId()))
            .body(order);
}
```

**202 Accepted — 접수는 했는데 아직 처리하지 않았다.** 이 코드가 비동기 처리에서 왜 필요한지가 2xx에서 가장 중요한 지점이다.

전제부터 깔자. 대량 정산 배치, 동영상 인코딩, 수만 건 푸시 발송 같은 작업은 수 초 안에 끝나지 않는다. 그런데 HTTP 요청은 응답을 기다리는 동안 클라이언트의 연결과 서버의 스레드를 붙잡고 있다. 처리에 5분이 걸리는 작업을 동기로 처리하려 들면 게이트웨이의 응답 대기 시간을 넘겨 504가 나거나, 스레드가 쌓여 서버가 무너진다. **그래서 이런 작업은 "요청을 큐에 넣고 즉시 응답"하는 구조로 만든다.**

여기서 문제가 생긴다. 즉시 응답할 때 200을 주면 클라이언트는 **작업이 완료됐다고 믿는다.** 실제로는 큐에 들어갔을 뿐인데 화면에는 "정산 완료"가 뜬다. 나중에 그 작업이 실패해도 사용자는 이미 성공을 본 뒤다.

202는 정확히 이 간극을 메운다. **"요청을 받아들였다. 하지만 아직 처리하지 않았고, 처리될 것이라고 약속하지도 않는다."** 클라이언트는 이 코드를 보고 "완료됨"이 아니라 "접수됨"으로 화면을 그리고, 결과는 따로 확인해야 한다는 것을 안다.

그래서 202 응답에는 **결과를 확인할 수 있는 방법**을 함께 주는 것이 관행이다. 작업의 상태를 조회할 수 있는 URI를 `Location` 헤더나 본문에 담아주면 클라이언트가 그곳을 폴링해 진행 상황을 볼 수 있다.

```java
// After: 오래 걸리는 작업은 202 + 상태 조회 URI
@PostMapping("/settlements")
public ResponseEntity<JobAccepted> requestSettlement(@RequestBody SettlementRequest req) {
    // 실제 정산은 여기서 하지 않는다. 작업만 등록하고 즉시 반환한다.
    String jobId = settlementJobService.enqueue(req);

    // 202: "받았지만 아직 안 했다".  200이면 클라이언트가 완료로 오해한다.
    // Location에 상태 조회 URI를 담아 "결과는 여기서 확인하라"고 알려준다.
    return ResponseEntity
            .accepted()
            .location(URI.create("/settlements/jobs/" + jobId))
            .body(new JobAccepted(jobId, "PENDING"));
}
```

**204 No Content — 성공했고, 돌려줄 본문이 아예 없다.** DELETE 성공이나 본문을 반환하지 않는 PUT 성공의 전형이다. 이 코드의 의미는 "본문이 비어 있다"가 아니라 **"본문이라는 것이 존재하지 않으니 파싱을 시도하지 마라"**이다. 실제로 204 응답에 본문을 담는 것은 규약 위반이고, 일부 클라이언트는 빈 본문을 JSON으로 파싱하려다 예외를 던진다.

여기서 자주 헷갈리는 것이 **204와 "200 + 빈 배열"의 차이**다. 둘 다 "결과가 없다"처럼 보이지만 뜻이 전혀 다르다.

```
GET /users/1/orders   — 주문이 하나도 없는 사용자

  [올바름]  200 OK
            []
            뜻: "주문 목록이라는 리소스는 존재하고, 그 내용이 빈 목록이다."
                빈 목록은 엄연한 조회 결과다.

  [틀림]    204 No Content
            (본문 없음)
            뜻: "돌려줄 본문 자체가 없다."
            문제: 클라이언트는 목록을 렌더링할 수 없고 특수 분기를 짜야 한다.
                  `orders.length === 0`으로 끝날 것이 `if (res.status === 204)`로 갈라진다.
```

판별 기준은 **"클라이언트가 이 응답으로 무엇을 그릴 수 있어야 하는가"**다. 조회는 결과가 비어도 "비어 있다"는 사실 자체가 결과이므로 200 + `[]`가 맞다. 반면 DELETE는 지운 뒤에 돌려줄 표현이라는 것이 애초에 없으므로 204가 맞다. **"결과가 비었다"와 "결과라는 개념이 없다"의 차이**로 기억하면 헷갈리지 않는다.

### 2-2. 3xx — 리다이렉트의 네 조합

3xx는 "네가 찾는 것이 여기 없으니 다른 곳으로 가라"는 대역이다. (엄밀히는 3xx 전부가 리다이렉트는 아니다 — 304 Not Modified는 "네가 가진 캐시가 아직 유효하다"는 캐시 응답이며, 이는 20번 문서에서 다룬다.)

리다이렉트 코드를 고를 때 결정해야 하는 것은 **두 가지 독립적인 질문**이다. 이 둘을 따로 떼어놓고 보면 네 개의 코드가 왜 존재하는지 한 번에 정리된다.

**첫째 질문 — 이 이전이 영구적인가 임시적인가.** 다시 말해 클라이언트가 이 안내를 기억해 두고 다음부터 곧바로 새 주소로 가도 되는가, 아니면 다음에도 원래 주소로 다시 물어봐야 하는가.

**둘째 질문 — 재요청할 때 메서드를 그대로 유지해야 하는가.** POST로 왔던 요청을 새 주소에도 POST로 보낼 것인가, GET으로 바꿔 보낼 것인가.

두 질문의 조합이 정확히 네 가지이고, 코드도 네 개다.

| | 임시 이전 (기억하지 마라) | 영구 이전 (기억해라) |
|---|---|---|
| **메서드가 바뀔 수 있음** | **302 Found** | **301 Moved Permanently** |
| **메서드를 반드시 보존** | **307 Temporary Redirect** | **308 Permanent Redirect** |

"메서드가 바뀔 수 있음"이라는 애매한 표현을 쓴 이유가 있다. 301과 302의 원래 명세는 메서드를 유지하라는 쪽이었지만, 초기 브라우저들이 POST 요청을 리다이렉트할 때 GET으로 바꿔 보내는 구현을 했고 그것이 웹 전체의 관행으로 굳었다. 명세가 현실을 따라가 "그렇게 동작할 수 있다"고 인정한 상태다. **즉 301/302로 리다이렉트하면 POST가 GET으로 바뀌어 도착할 수 있고, 그때 요청 본문은 사라진다.**

이 관행이 문제가 되는 상황은 명확하다. **API 게이트웨이에서 경로를 옮기거나 도메인을 바꿀 때**다. `POST /api/v1/payments`를 301로 `/api/v2/payments`에 보냈더니 클라이언트가 GET으로 바꿔 보내면서 결제 본문이 통째로 사라진다. 브라우저 화면 이동이라면 무해하지만 API에서는 치명적이다. 그래서 **메서드와 본문을 반드시 보존해야 하는 리다이렉트에는 307(임시) / 308(영구)을 쓴다.** 이 두 코드는 메서드 변경을 명시적으로 금지한다.

반대로 **메서드를 일부러 GET으로 바꾸고 싶은 경우**도 있다. 폼을 POST로 제출한 뒤 결과 페이지로 보낼 때, 그 페이지를 GET으로 만들어야 사용자가 새로고침해도 재제출 경고가 뜨지 않는다. 이 의도를 명확히 표현하는 코드가 **303 See Other**로, "메서드를 GET으로 바꿔 저기로 가라"는 뜻이다. 302에 의존해 우연히 그렇게 동작하기를 기대하는 것보다 정확하다.

**301의 무서운 점은 캐시다.** 영구 이전이라고 선언했으므로 브라우저는 이 정보를 저장해 두고, 다음부터는 **서버에 물어보지도 않고** 새 주소로 간다. 실수로 301을 내려보내면 그 정보가 사용자 브라우저에 박제되어, 서버 설정을 되돌려도 사용자는 계속 옛 안내대로 이동한다.

이 실수의 악질적인 점은 **서버 로그에 아무 흔적이 없다는 것**이다. 캐시가 서버에 물어보지 않으므로 요청 자체가 도달하지 않는다. "설정을 되돌렸는데 일부 사용자만 계속 이상한 곳으로 갑니다"라는 문의가 오고, 서버에서는 재현되지 않는다. 되돌리려면 사용자에게 캐시를 지우게 하거나, 새 주소에서 다시 원래 주소로 리다이렉트하는 우회로를 놓아야 한다.

**그래서 확신이 없으면 302(또는 307)로 시작하는 것이 실무 감각이다.** 임시로 시작해서 영구로 바꾸는 것은 쉽지만, 영구로 시작해서 되돌리는 것은 어렵다. 되돌릴 수 없는 결정은 미루는 것이 원칙이다.

301을 확신을 갖고 쓰는 대표적인 경우는 `http → https` 강제 전환이나 도메인 통합처럼 **다시는 돌아갈 계획이 없는 이전**이다. 이때는 캐시되는 것이 오히려 이득이다 — 매번 리다이렉트 왕복을 하지 않게 되고, 검색엔진이 링크 평가를 새 주소로 옮겨준다.

```nginx
# http로 들어온 요청을 https로 영구 전환 — 되돌릴 계획이 없으므로 301이 적절하다.
# 브라우저가 이 응답을 캐시하므로 두 번째 방문부터는 리다이렉트 왕복 자체가 사라진다.
server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}
```

```java
// API 경로를 옮기면서 메서드와 본문을 보존해야 하는 경우 — 301/302가 아니라 308
@PostMapping("/api/v1/payments")
public ResponseEntity<Void> movedPayments() {
    // 308은 "영구 이전이되 메서드를 바꾸지 마라"는 뜻이다.
    // 301을 쓰면 클라이언트가 POST를 GET으로 바꿔 보내면서 결제 본문이 사라질 수 있다.
    return ResponseEntity
            .status(HttpStatus.PERMANENT_REDIRECT)
            .location(URI.create("/api/v2/payments"))
            .build();
}
```

### 2-3. 4xx — 클라이언트 잘못을 정확하게 분류하기

4xx는 코드가 가장 많고 실무 판단이 가장 자주 필요한 대역이다. 하나씩 "무엇을 알려주는 코드인가"로 따져 보자.

**400 Bad Request — 요청 자체가 문법·형식에서 틀렸다.** 파싱할 수 없는 JSON, 필수 필드 누락, 숫자여야 할 자리에 문자열. 서버가 요청을 **이해조차 할 수 없는** 상태다. 클라이언트에게 주는 지시는 "요청을 고쳐서 다시 보내라"이다.

**401 Unauthorized — 누구인지 모른다.** **인증(authentication)** 실패다. 토큰이 아예 없거나, 만료됐거나, 서명이 맞지 않는다. 이름이 "Unauthorized(권한 없음)"라서 인가 코드처럼 보이지만, **실제 의미는 인증 실패**다. HTTP 초기의 작명 실수가 그대로 굳은 것이므로 이름이 아니라 의미로 외워야 한다.

401의 핵심 성질은 **"올바른 자격증명을 가지고 다시 오면 해결된다"**는 것이다. 그래서 규약은 401 응답에 `WWW-Authenticate` 헤더를 포함해 **어떤 방식으로 인증하면 되는지**를 알려주도록 정하고 있다.

**403 Forbidden — 누구인지는 알지만 권한이 없다.** **인가(authorization)** 실패다. 일반 사용자가 관리자 API를 호출한 경우가 전형이다.

401과의 실질적 차이는 **재로그인이 소용없다는 점**이다. 이 차이가 클라이언트 동작을 완전히 갈라놓는다. 401을 받은 앱은 토큰을 갱신하거나 로그인 화면으로 보내야 하고, 403을 받은 앱은 "권한이 없습니다" 안내를 띄우고 멈춰야 한다. 서버가 이 둘을 섞어 내리면 **권한이 부족한 사용자가 무한 재로그인 루프를 도는** 오동작이 발생한다. 로그인은 계속 성공하는데 다시 403이 나고, 앱은 그것을 401로 알고 또 로그인시킨다.

**404 Not Found — 그런 리소스가 없다.** 단순해 보이지만 두 가지 다른 상황에 쓰인다. 진짜로 없는 경우와, **존재하지만 존재 사실 자체를 숨기고 싶은 경우**다. 후자는 보안 판단이므로 꼬리질문에서 자세히 다룬다.

**409 Conflict — 요청은 유효한데 리소스의 현재 상태와 충돌한다.** 400과의 차이를 정확히 잡는 것이 중요하다.

```
400: 요청을 "이해할 수 없다"        — 형식이 틀렸다
409: 요청은 이해했는데 "지금은 안 된다" — 형식은 맞지만 현재 상태와 안 맞는다
```

409가 실무에서 값을 하는 이유는 **클라이언트에게 주는 지시가 다르기 때문**이다. 400은 "입력을 고쳐라"이고, 409는 "최신 상태를 다시 조회하고 판단하라"이다. 이 둘을 구분해 내려주면 클라이언트가 **본문을 읽지 않고 코드만 보고** 분기할 수 있다.

**422 Unprocessable Content — 문법은 맞는데 의미가 틀렸다.** (RFC 9110 이전에는 Unprocessable Entity라는 이름이었고 두 이름이 혼용된다.) 400과 409 사이에 있는 코드다.

세 코드의 자리를 나란히 놓으면 이렇게 된다.

```
  400  JSON 파싱 실패, 필수 필드 누락       -> 서버가 요청을 "읽지" 못한다
  422  형식은 완벽한데 값이 규칙에 안 맞는다 -> 읽었지만 "처리"할 수 없다
       (예: 종료일이 시작일보다 앞선다, 결제 금액이 0 이하다)
  409  값도 유효한데 지금 상태와 충돌한다    -> 처리할 수 있는데 "지금은" 안 된다
       (예: 이미 취소된 주문, 이미 존재하는 아이디)
```

다만 실무에서는 **400과 422를 굳이 나누지 않고 검증 실패를 전부 400으로 통일하는 팀도 많다.** 클라이언트가 어차피 본문의 에러 코드를 보고 필드별 메시지를 띄우기 때문에 구분의 실익이 작다는 판단이다. 어느 쪽이든 **팀 안에서 기준을 정해 일관되게 쓰는 것**이 코드 하나를 정확히 고르는 것보다 중요하다. 일관성이 없으면 클라이언트는 결국 상태 코드를 믿지 못하고 본문만 보게 되고, 그러면 상태 코드는 장식이 된다.

**429 Too Many Requests — 요청 한도를 초과했다.** 1-4에서 본 대로 4xx 중 유일하게 "기다렸다 다시 오라"는 성격을 가진 코드이며, `Retry-After`로 대기 시간을 안내한다.

이제 이 구분을 코드로 옮겨 보자. 같은 "회원 가입 실패"라도 원인에 따라 다른 코드를 내려야 클라이언트가 분기할 수 있다.

```java
// 예외에 상태 코드를 붙여 둔다.
// @ResponseStatus는 "이 예외가 컨트롤러 밖으로 나가면 이 코드로 응답하라"는 선언이다.
// 예외 타입 하나에 코드 하나가 고정되므로, 상황에 따라 코드가 달라져야 하면
// ResponseEntity나 ResponseStatusException을 쓴다.
@ResponseStatus(HttpStatus.CONFLICT)
public class DuplicateLoginIdException extends RuntimeException {
    public DuplicateLoginIdException(String loginId) {
        super("이미 사용 중인 아이디입니다: " + loginId);
    }
}

@PostMapping("/members")
public ResponseEntity<Void> signUp(@Valid @RequestBody SignUpRequest req) {
    // @Valid 실패(형식 오류)는 MethodArgumentNotValidException으로 던져지고,
    // 아래 전역 핸들러가 400으로 변환한다.
    if (memberService.existsByLoginId(req.loginId())) {
        // 형식은 정상이고 값도 유효한데 현재 상태(이미 존재)와 충돌 -> 409
        throw new DuplicateLoginIdException(req.loginId());
    }
    Member member = memberService.signUp(req);
    return ResponseEntity.created(URI.create("/members/" + member.getId())).build();
}
```

```java
// 전역 예외 핸들러 — "분류는 상태 코드로, 상세는 본문으로"를 한곳에서 강제한다.
@RestControllerAdvice
public class ApiExceptionHandler {

    // 형식 검증 실패 -> 400. 서버가 요청을 이해하지 못한 것이므로 클라이언트가 고쳐야 한다.
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidation(MethodArgumentNotValidException e) {
        // ProblemDetail은 RFC 7807(문제 상세) 형식의 에러 본문을 만드는 Spring의 표준 타입이다.
        // 팀마다 다른 에러 본문 규격을 만들지 않아도 되고, 클라이언트가 학습할 것이 줄어든다.
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.BAD_REQUEST, "요청 값이 올바르지 않습니다.");
        problem.setTitle("Validation Failed");
        // 어떤 필드가 왜 틀렸는지는 본문에 담는다 — 상태 코드로는 표현할 수 없는 상세다.
        problem.setProperty("errors", e.getBindingResult().getFieldErrors().stream()
                .map(fe -> Map.of("field", fe.getField(), "reason", fe.getDefaultMessage()))
                .toList());
        return problem;
    }

    // 낙관적 락 충돌 -> 409. 요청은 유효했지만 그 사이 남이 먼저 고쳤다는 뜻이다.
    // 클라이언트가 해야 할 일은 "입력 수정"이 아니라 "최신 상태 재조회"이므로 400이 아니다.
    @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
    public ProblemDetail handleConflict(ObjectOptimisticLockingFailureException e) {
        return ProblemDetail.forStatusAndDetail(
                HttpStatus.CONFLICT, "다른 사용자가 먼저 수정했습니다. 최신 내용을 다시 확인해 주세요.");
    }
}
```

### 2-4. 5xx — 서버 잘못, 그리고 "게이트웨이 뒤에서 무슨 일이"

5xx는 "요청에는 문제가 없었는데 내가 처리에 실패했다"는 서버의 자백이다. 네 코드의 구분 기준은 **"실패를 누가, 어느 위치에서 감지했는가"**다.

먼저 전제를 하나 깔자. 요즘 서비스의 요청 경로에는 애플리케이션 앞에 **프록시나 로드밸런서**가 서 있다. Nginx, ALB, CDN 같은 것들이다. 이때 5xx를 만드는 주체가 둘이 된다 — **앱이 직접 만든 5xx**와 **프록시가 앱을 대신해 만든 5xx**다. 이 구분이 502와 504의 존재 이유다.

```
  클라이언트  ---->  프록시/게이트웨이  ---->  앱 서버  ---->  DB·외부 API
                        (Nginx, ALB)
                          |                     |
                    이쪽이 만든 코드        이쪽이 만든 코드
                    502, 503, 504            500, 503
```

**500 Internal Server Error — 앱 내부에서 처리 중 예외가 터졌다.** 처리하지 못한 예외의 기본 귀결이고, 원인은 앱 로그에 스택 트레이스로 남아 있다. 대체로 코드 버그이거나 예상 못 한 데이터를 만난 경우다.

**502 Bad Gateway — 프록시가 뒷단으로부터 정상 응답을 받지 못했다.** 뒷단 프로세스가 죽어 연결이 거부되거나, 응답을 받던 중 연결이 끊기거나, 해석할 수 없는 응답이 온 경우다. 요점은 **"응답을 못 받았다"**이다.

**504 Gateway Timeout — 프록시가 뒷단의 응답을 제한 시간 안에 받지 못했다.** 뒷단이 죽은 것이 아니라 **느린** 것이다. 502가 "연결이 안 되거나 깨졌다"라면 504는 "연결은 됐는데 답이 안 온다"이다.

**502와 504의 구분이 장애 초동 대응의 방향을 정한다.** 502는 "뒷단 프로세스가 살아 있나? 배포 중이었나?"부터 보고, 504는 "뒷단이 왜 느린가?"(스레드 풀 고갈, 느린 쿼리, 외부 API 지연)를 본다. 같은 5xx인데 코드 하나가 **"죽었다"와 "느리다"**를 갈라주므로 첫 1분에 볼 곳이 달라진다. (이 둘의 원인 분석과 튜닝은 11번 문서에서 깊게 다룬다.)

**503 Service Unavailable — 지금은 처리할 수 없지만 나중엔 될 수 있다.** 과부하로 요청을 거절하는 경우, 점검 모드, 헬스체크 실패로 로드밸런서 풀에서 제외된 상태가 여기 해당한다.

503이 500과 다른 점은 **"일시적"이라는 뉘앙스가 코드에 담겨 있다는 것**이다. 500은 "무언가 터졌다"이지만 503은 "지금은 안 되지만 기다리면 된다"이다. 그래서 503에는 `Retry-After` 헤더로 재시도 시점을 안내할 수 있고, 클라이언트와 재시도 라이브러리는 그 값을 존중해 대기한다. **의도적으로 요청을 거절할 때(과부하 차단, 점검) 500 대신 503을 쓰는 것**이 규약을 제대로 쓰는 것이다.

(가산점 포인트) 로그에서 자주 보이지만 표준이 아닌 코드도 있다. Nginx의 **499**는 "클라이언트가 응답을 기다리다 먼저 연결을 끊었다"는 뜻으로 Nginx가 자체적으로 기록하는 값이다. 표준 HTTP 코드가 아니므로 클라이언트에게 실제로 전달되지는 않지만, 액세스 로그에 499가 늘어나면 **사용자가 기다리다 포기할 만큼 응답이 느려졌다**는 신호로 읽을 수 있다.

## 3. "전부 200 + 에러 바디"가 만드는 재앙

### 3-1. 안티패턴의 모습

실무에서 가장 흔한 상태 코드 안티패턴은 **모든 응답을 200으로 내리고 본문의 `success: false`로 실패를 표현하는 것**이다.

```java
// Before: 모든 실패가 200 — 기능은 도는데 계약이 통째로 깨진다
@PostMapping("/orders")
public ResponseEntity<Map<String, Object>> create(@RequestBody OrderRequest req) {
    try {
        Order order = orderService.create(req);
        return ResponseEntity.ok(Map.of("success", true, "data", order));
    } catch (Exception e) {
        // 서버가 터졌는데 HTTP 층에서는 "성공"이라고 말하고 있다
        return ResponseEntity.ok(Map.of("success", false, "message", "서버 오류"));
    }
}
```

이 코드가 만들어지는 동기는 대체로 선의다. 클라이언트가 에러 처리를 한곳에서 하기 편하도록, 혹은 예전 프로젝트가 그랬으니까. 그리고 **화면은 잘 동작한다.** 클라이언트가 `success` 필드를 보고 분기하면 되기 때문이다.

**문제는 화면 밖에서 터진다.** 1-5에서 열거한, 상태 코드를 읽고 움직이는 것들이 전부 속는다.

### 3-2. 무엇이 망가지는가

**첫째, 모니터링이 눈을 잃는다.** 에러율 대시보드와 알림 규칙은 5xx 비율을 본다. 모든 응답이 200이면 서비스가 반쯤 죽어도 대시보드는 초록색이다. **장애를 사용자 문의로 처음 알게 되는 상태**가 되고, 이것이 이 안티패턴의 가장 비싼 대가다.

문제는 이 실명이 조용하다는 것이다. 대시보드가 "측정에 실패했다"고 알려주지 않는다. 지표는 정상적으로 수집되고 있고, 값이 0일 뿐이다. 아무도 이상하다고 생각하지 않는다.

**둘째, 자동 재시도가 동작하지 않는다.** 게이트웨이와 클라이언트 라이브러리의 재시도는 5xx를 보고 동작한다. 200으로 포장된 서버 오류는 재시도 대상에서 빠지므로, 일시적 장애로 실패한 요청이 한 번 더 시도되면 성공했을 텐데 그냥 실패로 끝난다.

**셋째, 캐시가 오염된다.** 200은 캐시 가능한 성공 응답이다. 에러 바디가 CDN이나 프록시에 캐시되면, **서버가 복구된 뒤에도 사용자는 캐시된 에러를 계속 받는다.** 서버 지표는 정상으로 돌아왔는데 사용자 문의는 계속 들어오는, 원인을 찾기 어려운 상황이 만들어진다.

**넷째, 로드밸런서가 죽은 인스턴스를 살아 있다고 판정한다.** 헬스체크가 2xx를 성공으로 읽으므로, 앱이 DB 연결을 잃어 모든 요청에 에러 바디를 반환하는 상태에서도 200을 주면 트래픽이 계속 그 인스턴스로 들어간다.

**다섯째, 연동 비용이 늘어난다.** 표준 대신 우리만의 에러 규격을 만든 것이므로, 모든 연동 상대가 그 규격을 따로 학습하고 구현해야 한다. `success` 필드를 안 보고 넘어간 클라이언트는 에러 본문을 정상 데이터로 파싱하려다 엉뚱한 곳에서 터진다.

### 3-3. 원칙 — 분류는 상태 코드로, 상세는 본문으로

```java
// After: 상태 코드로 계약을 지키고, 본문은 상세 설명에 쓴다
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ProblemDetail> handleUnexpected(Exception e) {
        // 추적 ID를 먼저 만든다. 로그와 응답에 같은 값을 심어야
        // 사용자 문의("이 화면에서 에러가 났어요")를 로그 한 줄에 곧바로 연결할 수 있다.
        String traceId = UUID.randomUUID().toString();
        log.error("unhandled exception. traceId={}", traceId, e);

        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.INTERNAL_SERVER_ERROR, "일시적인 오류가 발생했습니다.");
        problem.setProperty("traceId", traceId);
        // 예외 메시지나 스택 트레이스를 그대로 담지 않는다.
        // 내부 클래스명·SQL·경로는 공격자에게 유용한 정보이고 사용자에게는 쓸모가 없다.

        // 500: "서버 잘못이며 재시도 후보"임을 기계가 읽을 수 있게 선언한다.
        // 이 한 줄이 모니터링 집계, 자동 재시도, 캐시 회피, 헬스체크 판정을 동시에 살린다.
        return ResponseEntity.internalServerError().body(problem);
    }
}
```

원칙을 한 문장으로 압축하면 이렇다. **"분류는 상태 코드로, 상세는 본문으로."**

상태 코드는 **기계가 읽는 계약**이다. 모니터링이 집계하고, 재시도 라이브러리가 판단하고, 캐시가 저장 여부를 정하고, 로드밸런서가 인스턴스 생존을 판정하는 데 쓰인다. 표현할 수 있는 정보량은 세 자리 숫자만큼 적지만, 그 대신 **누구나 해석 방법을 이미 알고 있다.**

본문은 **사람과 클라이언트 개발자가 읽는 설명**이다. 어떤 필드가 왜 틀렸는지, 어떤 에러 코드인지, 추적 ID가 무엇인지 같은 상세를 담는다. 표현력은 무한하지만 우리 API를 아는 사람만 해석할 수 있다.

**둘은 대체 관계가 아니라 역할 분담이다.** 본문이 아무리 친절해도 상태 코드가 틀리면 기계가 오작동하고, 상태 코드가 아무리 정확해도 본문이 없으면 개발자가 원인을 못 찾는다. 이 역할 분담을 설명할 수 있으면 API를 "우리 화면이 쓰는 기능"이 아니라 **"생태계와 맺은 계약"**으로 보고 있다는 신호가 된다.

## 4. 꼬리질문 대비 포인트

### "401과 403의 차이를 실제 API에서 어떻게 적용하나요?"

401은 **인증 실패**("누군지 모름") — 토큰이 없거나, 만료됐거나, 서명이 맞지 않는다. 403은 **인가 실패**("누군지는 알지만 권한이 없음") — 신원은 확인됐는데 그 신원으로는 이 리소스에 접근할 수 없다.

실무에서 이 구분이 값을 하는 지점은 **클라이언트의 후속 행동이 정반대**라는 것이다. 401은 자격증명을 고치면 해결되므로 앱은 토큰 갱신이나 로그인 화면 이동을 시도해야 하고, 403은 재로그인해도 결과가 같으므로 "권한이 없습니다" 안내를 띄우고 멈춰야 한다. 서버가 이 둘을 섞어 내리면 앱이 무한 재로그인 루프에 빠진다.

Spring Security 기준으로 말하면 실무 연결이 확실해진다. **인증 실패는 `AuthenticationEntryPoint`가, 인가 실패는 `AccessDeniedHandler`가 처리**하도록 진입점 자체가 분리되어 있다. 프레임워크가 이미 두 개념을 다른 지점에서 다루고 있다는 뜻이므로, 그 두 핸들러에서 각각 401과 403을 내려주면 구분이 자연스럽게 지켜진다.

(가산점 포인트) 규약상 401 응답에는 `WWW-Authenticate` 헤더를 담아 **어떤 방식으로 인증해야 하는지**를 알려주게 되어 있다. 실무의 토큰 기반 API에서는 생략되는 경우가 많지만, 이 헤더의 존재를 아는 것 자체가 "401은 인증 코드"라는 사실을 정확히 이해했다는 근거가 된다.

### "권한 없는 리소스에 403 대신 404를 주는 경우는 왜인가요?" (가산점 포인트)

**403은 "그 리소스가 존재한다"는 정보를 흘리기 때문**이다.

공격자 입장에서 생각하면 분명해진다. 남의 주문 `GET /orders/1234`에 403이 오고 `GET /orders/9999`에 404가 온다면, 공격자는 **주문 ID를 순회하며 어느 번호가 실제로 존재하는지 지도를 그릴 수 있다.** 내용을 못 봐도 "1000번부터 5000번까지 주문이 있다"는 사실만으로 서비스 규모나 거래량을 추정할 수 있고, 특정 사용자의 리소스 ID를 알아내는 발판이 된다.

그래서 **존재 자체를 숨겨야 하는 리소스라면 "없음"과 "권한 없음"을 똑같이 404로 응답한다.** 비공개 저장소에 접근했을 때 403이 아니라 404를 주는 서비스들이 이 방식을 쓴다.

이것은 **정확성(403)과 은닉(404) 사이의 트레이드오프**이며, 언제나 404가 옳은 것은 아니다. 사내 관리 도구처럼 사용자가 모두 신뢰된 직원이고 "권한이 없어서 못 보는 것"과 "정말 없는 것"을 구분해야 문의 대응이 되는 경우에는 403이 낫다. **"열거될 위험이 있는 리소스인가"를 기준으로 판단한다**까지 말하면 규칙 암기가 아니라 판단으로 들린다.

### "502와 504가 떴을 때 각각 어디를 먼저 보나요?"

둘 다 **게이트웨이(Nginx, 로드밸런서)가 만든 코드이므로 문제는 그 뒤에 있다.** 이 전제를 먼저 말하는 것이 중요하다 — 게이트웨이 설정을 뒤지기 전에 뒷단부터 봐야 한다는 방향이 여기서 나온다.

**502는 "정상 응답 자체를 못 받았다"**이므로 앱 프로세스의 생존 여부, 직전 배포·재시작 이력, 게이트웨이 에러 로그의 connection refused / connection reset 여부를 먼저 본다. 배포 시간대에만 502가 몇 초씩 뜨는 패턴이 전형적이다.

**504는 "시간 안에 답을 못 받았다"**이므로 앱은 살아 있다. 그러면 "왜 느린가"를 본다 — 스레드 풀 고갈, 느린 쿼리, 외부 API 지연, 커넥션 풀 대기.

여기에 실무에서 사람을 헤매게 만드는 함정을 하나 얹으면 답변이 깊어진다. **앱 로그에 아무 흔적이 없는 502가 가능하다.** 요청이 앱에 도달하기 전에 게이트웨이 단계에서 반려됐기 때문이다. "앱 로그는 깨끗한데 사용자는 에러를 본다"는 상황에서 앱 로그만 뒤지면 영원히 못 찾는다. 반대로 **504인데 앱 로그에는 그 요청이 성공으로 남아 있는 경우**도 있다 — 게이트웨이가 먼저 포기했을 뿐 앱은 끝까지 처리했기 때문이며, 이것이 1-4에서 본 "504 + 비멱등 POST 재시도 금지"의 근거다.

**503과의 구분**도 함께 말하면 좋다. 503은 **서버가 스스로 "지금은 못 한다"고 의도적으로 거절한 것**(과부하 차단, 점검, 헬스체크 실패로 인한 풀 제외)이고, 502/504는 **게이트웨이가 뒷단과의 통신 결과로 판정한 것**이다. 즉 503에는 의도가 있고 502/504에는 의도가 없다. (자세한 원인 분석은 11번 문서에서 다룬다.)

### "409는 실무에서 구체적으로 언제 쓰나요?"

**"요청은 유효한데 리소스의 현재 상태가 전제와 다를 때"**다. 대표 사례가 셋이다.

**첫째, 유니크 충돌.** 이미 존재하는 아이디로 가입하거나, 이미 등록된 사업자번호로 가맹점을 만드는 경우다. 요청 형식은 완벽하고 값도 유효한데, 서버의 현재 데이터와 부딪힌다.

**둘째, 상태 전이 위반.** 이미 취소된 주문에 결제 확정을 시도하거나, 이미 배송이 시작된 주문을 취소하려는 경우다. 도메인의 상태 머신이 허용하지 않는 전이다.

**셋째, 낙관적 락 충돌.** 내가 읽은 버전과 저장 시점의 버전이 달라 동시 수정이 감지된 경우다. JPA의 `@Version`이 붙은 엔티티에서 `ObjectOptimisticLockingFailureException`이 던져지는 상황이 여기 해당한다.

세 사례의 **공통점이 409의 존재 이유**다. 전부 클라이언트가 **최신 상태를 다시 조회한 뒤 판단해야** 풀린다. 입력을 고치는 것으로는 해결되지 않으므로 400이 아니고, 서버가 잘못한 것도 아니므로 5xx가 아니다. **"다시 읽고 오라"는 행동 지침을 코드 하나로 전달하는 것**이 409의 역할이다.

(가산점 포인트) 낙관적 락 충돌에는 **412 Precondition Failed**라는 더 정확한 코드가 있다. 클라이언트가 `If-Match` 헤더에 자기가 읽은 버전(ETag)을 실어 보내고 서버가 그것을 검사하는, HTTP 층에서 동시성 제어를 하는 방식이다. 다만 REST API 실무에서는 버전 필드를 요청 본문에 담고 409로 응답하는 방식이 더 흔하다. **412는 HTTP 헤더로 조건을 검사할 때, 409는 애플리케이션이 도메인 규칙으로 충돌을 판정할 때** 쓴다고 구분하면 정확하다.

### "재시도 로직을 만든다면 어떤 상태 코드를 재시도 대상으로 삼겠어요?" (시니어 변별 포인트)

원칙부터 말한다. **"재시도는 다시 보내면 결과가 달라질 수 있는 실패에만 의미가 있다."** 코드 목록을 외워서 답하는 것이 아니라 이 기준에서 도출하는 것이 중요하다.

**재시도 후보는** 503(일시적 불가 — `Retry-After`가 있으면 반드시 존중), 502와 504(게이트웨이 뒤의 일시 장애 가능성), 429(요청 과다 — 4xx지만 원인이 요청 내용이 아니라 타이밍이므로), 408(요청 전송이 제때 완료되지 않음)이다. **500은 재시도 이득이 작다** — 코드 버그로 인한 예외일 가능성이 높고, 그렇다면 몇 번을 다시 보내도 같은 곳에서 터진다.

**4xx는 원칙적으로 재시도 금지**다. 실패 원인이 요청 안에 있고, 재시도해도 요청은 바뀌지 않기 때문이다.

여기까지가 "상태 코드를 아는" 답변이고, 여기에 세 겹을 더하면 시니어 답변이 된다.

**첫째, 코드가 재시도 후보라도 요청이 멱등해야 재시도할 수 있다.** 504는 뒷단이 이미 처리했을 수 있으므로 비멱등 POST를 재시도하면 중복 실행이 난다. 재시도 가능 여부는 **"상태 코드 조건 AND 멱등성 조건"의 논리곱**이며, 최종 결정권은 멱등성이 쥔다. 멱등성 키를 붙여 POST를 멱등하게 만들어 두면 이 제약을 풀 수 있다(04번 문서).

**둘째, 재시도는 지수 백오프 + 지터로 한다.** 즉시 재시도를 반복하면 이미 힘들어하는 서버에 부하를 곱해서 얹는 재시도 폭풍이 된다. 간격을 지수적으로 벌리고(백오프), 여러 클라이언트의 재시도 시각이 한 점에 몰리지 않도록 무작위 흔들림(지터)을 준다.

**셋째, 재시도는 호출 체인에서 한 계층만 담당해야 한다.** 게이트웨이도 재시도하고 클라이언트 라이브러리도 재시도하고 애플리케이션 코드도 재시도하면 증폭이 덧셈이 아니라 곱셈이 된다. 계층마다 3번씩 재시도하는 3계층 체인은 원 요청 하나가 수십 배로 불어난다.

상태 코드 지식이 **재시도 정책과 멱등성 설계로 이어지는 지점**을 보여주는 것이 이 질문의 목적이다.

## 한 줄 요약

상태 코드는 사람이 아니라 기계가 읽는 계약이라 첫 자리로 책임 소재(4xx 클라이언트 / 5xx 서버)와 재시도 가능성을 선언하며 — 그 갈림의 근거는 "실패 원인이 바뀌지 않는 요청 안에 있는가, 시간에 따라 변하는 서버 상태에 있는가"이고, 그래서 429는 4xx인데 재시도 대상이고 504를 받은 비멱등 POST는 5xx인데 재시도 금지다(최종 결정권은 상태 코드가 아니라 멱등성이 쥔다) — 세부적으로 201+Location과 202 Accepted로 "만들었다"와 "접수만 했다"를, 204와 200+빈 배열로 "본문 없음"과 "빈 결과"를, 301/302/307/308로 영구·임시와 메서드 보존을, 401/403으로 인증과 인가를, 409·422로 상태 충돌과 의미 오류를, 502/504로 "뒷단이 죽었다/느리다"를 구분해 전달한다 — 이 계약을 지킨 API만 모니터링·자동 재시도·캐시·헬스체크가 제대로 동작하고, 전부 200에 에러 바디를 담는 API는 서비스가 반쯤 죽어도 대시보드를 초록색으로 유지해 장애를 사용자 문의로 처음 알게 만든다.
