# TLS handshake — 비대칭키로 열쇠를 나누고, 대칭키로 본문을 잠근다

> 핵심 관전 포인트: **TLS는 두 종류의 암호화에 역할을 나눠 맡긴다 — 느리지만 "처음 만난 상대와 비밀을 만드는 문제"를 풀 수 있는 비대칭키로 handshake에서 (1) 서버 신원 확인(인증서의 CA 서명을 신뢰 사슬을 따라 검증)과 (2) 대칭키 합의(ECDHE)를 끝내고, 그 뒤의 실제 데이터는 빠른 대칭키로 암호화한다. 전 구간을 비대칭으로 하면 서버 CPU가 못 견디고, 처음부터 대칭으로 하면 키를 건네줄 방법이 없기 때문이다. 이 구조를 알면 "HTTPS는 왜 첫 요청만 느린가"(왕복과 비대칭 연산이 연결 수립 시점에 몰려 있다 → 답은 연결 재사용), "인증서 만료가 왜 전면 장애인가"(신원 확인이 handshake 초입의 관문이라 신규 연결이 통째로 거절된다), "왜 내 브라우저는 되는데 안드로이드에서만 SSL 에러인가"(중간 인증서 누락) 같은 운영 질문이 전부 같은 원리로 풀린다.**

---

## 0. 질문 + 의도

**질문**: "HTTPS(TLS) handshake 과정을 설명해주세요. 대칭키와 비대칭키는 각각 어디에 쓰이나요?"

**출제 의도**: HTTPS 인증서 만료, 핸드셰이크 지연 같은 운영 이슈를 다룰 때의 기초. 비대칭으로 키 교환, 대칭으로 본문 암호화라는 구조를 알면 "TLS가 왜 첫 요청만 느린가"류의 성능 질문도 풀린다.

## 1. 왜 키가 두 종류인가 — 각자 못 푸는 문제가 있다

### 1-1. 전제 — TLS가 풀어야 하는 문제는 사실 두 개다

HTTPS를 "통신을 암호화하는 것"이라고만 알면 절반만 아는 것이다. TLS(Transport Layer Security, 전송 계층 보안 — TCP 위에 얹혀 그 위의 HTTP를 감싸므로 "전송 계층"이라는 이름이 붙었다)가 풀어야 하는 문제는 성격이 전혀 다른 두 개다.

첫째는 **기밀성**이다. 중간에 있는 누군가(공용 와이파이의 라우터, 통신사 장비, 침해당한 스위치)가 오가는 바이트를 그대로 읽지 못하게 하는 것. 이건 암호화로 푼다.

둘째는 **인증**이다. 내가 지금 암호화 통신을 하고 있는 그 상대가 정말 `api.example.com`이 맞는지 확인하는 것. 이건 암호화로 풀리지 않는다. 공격자와 완벽하게 암호화된 통신을 하는 것도 "암호화된 통신"이기 때문이다.

이 둘을 구분하지 못하면 뒤에 나오는 인증서 이야기가 왜 필요한지 이해되지 않는다. **암호화는 "내용을 못 보게" 하고, 인증서는 "누구와 통신하는지"를 보장한다.** 둘 중 하나만 있으면 안전하지 않다.

### 1-2. 대칭키: 빠르지만 "키 배달 문제"가 있다

**대칭키 암호화**는 **잠글 때와 열 때 같은 키**를 쓰는 방식이다. 양쪽이 같은(대칭인) 키를 갖고 있어야 하므로 대칭키라고 부른다. AES가 대표적이다.

장점은 속도다. 연산이 단순한 데다 요즘 CPU에는 **AES-NI**(Advanced Encryption Standard New Instructions — AES 연산을 전용 명령어로 처리하는 CPU 기능)처럼 하드웨어 가속까지 들어 있어서, 초당 수 GB 규모의 데이터를 실시간으로 암복호화할 수 있다. HTTP 본문·헤더처럼 양이 많은 데이터를 감싸는 데는 이쪽이 적임자다.

문제는 **시작점**이다. 서버와 브라우저가 같은 키를 나눠 가져야 하는데, 그 키를 어떻게 전달하나? 아직 암호화 통신이 없는 상태에서 키를 평문으로 보내면, 중간에서 훔쳐보는 공격자도 그 키를 그대로 갖게 된다.

비유하면 **잠긴 금고를 택배로 보내면서 열쇠를 금고 겉면에 테이프로 붙여 보내는** 격이다. 금고는 완벽하지만 아무 의미가 없다. 이것을 **키 배달 문제(key distribution problem)**라고 부른다.

"미리 만나서 키를 정해두면 되지 않나"는 답이 안 된다. HTTPS는 서로 처음 보는 전 세계 브라우저와 서버 사이에서 성립해야 하기 때문이다.

### 1-3. 비대칭키: 키 배달 문제를 풀지만 느리다

**비대칭키 암호화**(공개키 암호화)는 키가 **한 쌍**이다. 두 키의 역할이 서로 달라서(비대칭이라서) 붙은 이름이다.

- **공개키(public key)**: 누구에게나 공개해도 되는 키.
- **개인키(private key)**: 소유자만 갖고 절대 밖으로 내보내지 않는 키.

이 쌍은 두 방향으로 쓸 수 있고, 두 방향이 각각 다른 일을 한다.

```
[방향 1 — 암호화]   공개키로 잠근 것은  →  개인키로만 열린다
                    (누구나 나에게 비밀을 보낼 수 있다)

[방향 2 — 서명]     개인키로 서명한 것은 →  공개키로 검증된다
                    (나만 만들 수 있고, 누구나 진짜인지 확인할 수 있다)
```

이 성질 덕분에 "사전에 아무 비밀도 공유하지 않은 상대와 비밀을 만드는" 문제를 풀 수 있다. 대칭키가 못 푸는 바로 그 문제다.

대신 대가가 있다. 비대칭 연산은 큰 수의 거듭제곱이나 타원곡선 위의 점 연산처럼 수학적으로 무거운 계산이라, 대칭키 연산과는 **비용의 자릿수가 다르다.** 모든 HTTP 요청·응답 본문을 비대칭키로 암호화하면 서버 CPU가 암호 연산만 하다가 끝난다.

### 1-4. 그래서 역할 분담이다

두 방식은 서로가 못 푸는 문제를 상대가 풀어준다. 그래서 TLS는 둘 중 하나를 고르는 대신 **일을 나눈다.**

| | 비대칭키 | 대칭키 |
|---|---|---|
| 쓰이는 곳 | handshake — 신원 확인 + 키 합의 | handshake 이후 모든 데이터 |
| 푸는 문제 | 처음 만난 상대와 안전하게 비밀 만들기 | 대량 데이터의 빠른 암복호화 |
| 실행 횟수 | 연결당 몇 번 | 모든 바이트에 |
| 비용 | 무겁다 | 가볍다 (하드웨어 가속) |

비유하면 **비대칭키는 계약 자리에서 신분증을 확인하고 금고 비밀번호를 함께 정하는 절차**이고, **대칭키는 그 뒤로 금고를 실제로 여닫는 비밀번호**다. 비싼 절차는 처음 한 번, 싼 연산은 매번.

여기서 곧바로 따라 나오는 결론이 있다. **TLS 비용은 연결 수립 시점에 몰려 있다.** 이 한 문장이 3절의 성능 이야기 전체를 지배한다.

## 2. handshake 과정 — 무엇이 오가는가

**handshake**는 말 그대로 악수다. 본론(HTTP 요청)에 들어가기 전에 서로 인사하고, 상대가 누구인지 확인하고, 앞으로 쓸 규칙(어떤 암호 알고리즘을 쓸지)과 비밀번호(대칭키)를 정하는 절차라서 붙은 이름이다.

### 2-1. 전체 흐름 먼저 — TLS 1.2 기준

TLS는 TCP 위에서 동작하므로, TCP 3-way handshake로 연결이 만들어진 **다음에** TLS handshake가 시작된다. 이 순서가 3-1의 타임라인에서 중요해진다.

```
클라이언트                                         서버
   │                                               │
   │── ClientHello ───────────────────────────────→│  "내가 지원하는 TLS 버전과
   │     · 지원 TLS 버전 목록                        │   암호 스위트는 이것들이고,
   │     · 지원 암호 스위트 목록                      │   내 랜덤값은 이것,
   │     · 클라이언트 랜덤값                          │   접속하려는 도메인은 이것"
   │     · SNI 확장 = "api.example.com"             │
   │                                               │
   │←────────────────────────── ServerHello ───────│  "그중 이 암호 스위트로 하자,
   │                             · 선택된 암호 스위트  │   내 랜덤값은 이것"
   │                             · 서버 랜덤값       │
   │←───────────────────────── Certificate ────────│  서버 인증서 + 중간 인증서
   │                                               │  (leaf → 중간 순서로)
   │←──────────────────── ServerKeyExchange ───────│  ECDHE 임시 공개 파라미터
   │                                               │  + 그것에 대한 개인키 서명
   │←────────────────────── ServerHelloDone ───────│  "내 할 말 끝"
   │                                               │
   │  ┌───────────────────────────────────────┐    │
   │  │ 인증서 검증:                            │    │
   │  │  ① 서명 사슬이 내 신뢰 저장소까지 닿는가   │    │
   │  │  ② 유효기간 안인가                       │    │
   │  │  ③ 도메인이 일치하는가                   │    │
   │  └───────────────────────────────────────┘    │
   │                                               │
   │── ClientKeyExchange ─────────────────────────→│  클라이언트의 ECDHE 공개 파라미터
   │                                               │
   │  [양쪽이 같은 비밀값을 각자 계산 → 대칭키 파생]    │
   │                                               │
   │── ChangeCipherSpec, Finished ────────────────→│  "여기부터 대칭키로 간다"
   │←──────────── ChangeCipherSpec, Finished ──────│  "확인, 나도 간다"
   │                                               │
   │══ 이후 HTTP 요청/응답 전부: 대칭키 암호화 ═══════│
```

여기서 **암호 스위트(cipher suite)**는 "키 교환 방식 + 서명 방식 + 대칭키 암호 + 해시 함수"를 한 묶음으로 정해둔 조합의 이름이다. `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256`처럼 생겼고, 읽는 법은 "ECDHE로 키를 합의하고, RSA로 서명하고, AES-128-GCM으로 본문을 암호화하고, SHA-256을 해시로 쓴다"다. 클라이언트가 지원 목록을 보내면 서버가 그중 하나를 고르는 협상 구조다.

그리고 위 흐름에서 비대칭키는 **서로 다른 두 가지 일**을 하고 있다. 이 둘을 분리해서 말할 수 있는지가 이 질문의 채점 포인트다.

- **신원 확인(2-2 ~ 2-5)**: 서버가 인증서를 내밀고, 클라이언트가 그 인증서의 서명을 검증한다.
- **키 합의(2-7)**: 양쪽이 임시 키 쌍을 만들어 파라미터를 주고받고, 같은 대칭키를 각자 계산해 낸다.

### 2-2. 인증서란 정확히 무엇인가 — 세 가지가 한 묶음

"인증서"라는 말이 막연하게 들린다면, 실제로 그 안에 뭐가 들었는지부터 보면 된다. TLS 인증서(X.509 형식)는 **세 덩어리가 한 묶음**이다.

```
┌─────────────────────────────────────────────────┐
│ ① 주체 정보  Subject / SAN                       │
│    api.example.com, www.example.com             │  ← "누구의 것인가"
│                                                 │
│ ② 공개키                                         │
│    04:a3:f1:...(서버의 공개키)                    │  ← "그 사람의 공개키는 이것"
│                                                 │
│    유효기간  2026-01-01 ~ 2026-04-01             │
│    발급자    CN=Example CA R3                    │
├─────────────────────────────────────────────────┤
│ ③ CA의 서명                                      │
│    9f:2c:be:...                                 │  ← "위 내용이 맞다고 CA가 보증"
└─────────────────────────────────────────────────┘
```

핵심은 ①과 ②를 **③이 묶어 놓았다**는 것이다. 인증서가 하는 말은 딱 한 문장이다. **"이 공개키는 이 도메인 소유자의 것이며, 그 사실을 내가(CA가) 보증한다."**

**CA(Certificate Authority, 인증기관)**는 도메인 소유권을 확인한 뒤 그 보증을 서주는 기관이다. 무료로는 Let's Encrypt, 유료로는 여러 상용 CA가 있다. "도메인 소유권 확인"은 보통 해당 도메인의 특정 경로에 지정된 파일을 올리게 하거나 DNS에 지정된 TXT 레코드를 넣게 해서, "이 도메인을 실제로 통제하는 사람이 맞다"를 기계적으로 검증하는 방식이다.

여기서 `SAN`(Subject Alternative Name, 주체 대체 이름)은 이 인증서가 커버하는 도메인 목록이다. 예전에는 `CN`(Common Name) 필드를 도메인 확인에 썼지만 지금 브라우저들은 SAN을 본다. `*.example.com` 같은 와일드카드도 여기에 들어간다. 도메인을 하나 추가했는데 "인증서 도메인 불일치" 에러가 나는 사고의 원인은 대부분 **SAN에 그 도메인이 안 들어간 채 발급된 인증서**다.

### 2-3. 서명이란 무엇인가 — 왜 개인키로 서명해 공개키로 검증하는가

"CA가 서명했다"는 말을 정확히 풀어야 인증서 검증이 이해된다.

**서명(signature)**은 원문에 개인키 연산을 적용해 만든 짧은 값이다. 정확히는 원문 전체가 아니라 **원문의 해시값**(내용이 1비트만 달라져도 완전히 달라지는 고정 길이 요약값)에 개인키 연산을 적용한다. 원문이 길어도 서명은 짧게 유지하기 위해서다.

검증은 그 반대 방향이다. 검증하는 쪽은 **공개키**를 써서, 그 서명이 정말 짝이 되는 개인키로 만들어진 것인지, 그리고 그 대상이 지금 눈앞의 원문의 해시와 일치하는지를 확인한다.

이 방향이 왜 이렇게 정해져 있는지가 중요하다.

- **개인키는 한 사람만 갖고 있다** → 그 서명을 만들 수 있는 것은 그 사람뿐이다 (위조 불가).
- **공개키는 모두가 갖고 있다** → 누구나 그 서명이 진짜인지 확인할 수 있다 (검증 가능).

즉 서명은 **"만들기는 어렵고 확인하기는 쉬운"** 비대칭성을 그대로 이용한다. 만약 반대로 공개키로 서명한다면 아무나 서명을 만들 수 있으니 보증이 되지 않는다.

암호화와 서명은 같은 키 쌍을 쓰지만 목적이 정반대라는 점을 한 번 정리하고 가자.

| | 무엇을 쓰나 | 얻는 것 |
|---|---|---|
| 암호화 | 받는 사람의 **공개키**로 잠근다 | 그 사람만 읽을 수 있다 (기밀성) |
| 서명 | 보내는 사람의 **개인키**로 서명한다 | 그 사람이 만든 게 맞다 (인증·무결성) |

인증서에서 쓰이는 것은 **서명 쪽**이다. 인증서 내용은 비밀이 아니다 — 누구나 봐도 되는 공개 정보이고, 필요한 것은 "이 내용이 변조되지 않았고 CA가 보증했다"는 사실뿐이다.

### 2-4. 신뢰 사슬 — 루트 CA는 왜 브라우저에 미리 박혀 있는가

여기서 한 단계 더 파고들면 자연스러운 의문이 생긴다. **CA의 서명을 검증하려면 CA의 공개키가 필요한데, 그 공개키는 어떻게 믿나?** CA 공개키도 인증서에 담아 보내면, 그 인증서를 또 누가 보증하나? 무한히 거슬러 올라간다.

이 무한 후퇴를 끊는 방법은 하나뿐이다. **어딘가에서 "묻지 않고 믿는 출발점"을 정해두는 것.** 그 출발점이 **루트 CA(Root CA)**다.

루트 CA 인증서는 브라우저와 운영체제에 **미리 설치되어** 배포된다. 이 목록을 **신뢰 저장소(trust store)**라고 부른다. 크롬·파이어폭스·윈도우·macOS·안드로이드가 각각 자기 신뢰 저장소를 갖고 있고, 여기 들어가려면 CA가 엄격한 감사를 통과해야 한다. 루트 CA 인증서는 **자기 자신의 개인키로 서명**되어 있다(self-signed) — 위에 보증해줄 상위가 없으니 당연하다. 루트를 믿는 근거는 수학이 아니라 **"소프트웨어에 담겨 배포되는 경로 자체를 믿는다"**는 사회적 합의다.

실제 사슬은 보통 3단이다.

```
     [루트 CA 인증서]  ← 브라우저/OS 신뢰 저장소에 미리 들어 있음 (self-signed)
          │  루트의 개인키로 서명
          ▼
     [중간 CA 인증서]  ← 서버가 클라이언트에게 함께 보내줘야 하는 것
          │  중간 CA의 개인키로 서명
          ▼
     [서버 인증서]     ← 내 도메인의 인증서. 사슬의 끝이라 "리프(leaf, 잎)"라고 부른다
```

검증은 아래에서 위로 올라간다. 서버 인증서의 서명을 중간 CA 공개키로 검증하고, 중간 CA 인증서의 서명을 루트 CA 공개키로 검증하고, 루트가 신뢰 저장소에 있으면 거기서 멈춘다. 한 칸이라도 끊기면 전체가 실패한다. 이것이 **신뢰 사슬(chain of trust)**이다.

**중간 CA는 왜 있는가.** 루트가 직접 서버 인증서를 발급하면 될 것 같은데 한 단계를 더 둔 데는 실용적인 이유가 있다.

첫째, **루트 개인키를 오프라인에 격리하기 위해서다.** 루트 개인키는 인터넷에 연결되지 않은 금고 안 장비에 보관하고, 중간 CA 인증서에 서명할 때만 아주 드물게 꺼낸다. 매일 수백만 장의 인증서를 발급하는 일은 온라인에 있는 중간 CA가 맡는다.

둘째, **사고가 났을 때 갈아끼울 수 있게 하기 위해서다.** 중간 CA 키가 유출되면 그 중간 CA만 폐기하고 새 중간 CA로 교체하면 된다. 반면 루트가 오염되면 전 세계 브라우저와 OS의 신뢰 저장소를 업데이트해야 한다 — 몇 년이 걸리는 일이다. **중간 CA는 루트를 지키기 위한 완충 계층**이다.

### 2-5. 실무 사고 — "내 브라우저는 되는데 안드로이드에서만 SSL 에러"

운영에서 가장 자주 겪는 인증서 사고가 여기서 나온다. 원인은 **중간 인증서 누락**이다.

앞의 사슬 그림에서 각 인증서가 어디에 있어야 하는지를 다시 보자. 루트는 클라이언트가 이미 갖고 있다. 서버 인증서는 당연히 서버가 보낸다. 그러면 **중간 인증서는 누가 주나?** 답은 **서버**다. 서버는 Certificate 메시지에 자기 인증서뿐 아니라 **루트 바로 아래까지의 중간 인증서를 함께 실어 보내야** 한다.

그런데 인증서를 설치할 때 이걸 빠뜨리기 쉽다. Let's Encrypt의 certbot은 발급 결과로 여러 파일을 만드는데, `cert.pem`은 **서버 인증서만** 들어 있고 `fullchain.pem`이 **서버 인증서 + 중간 인증서**다. 여기서 `cert.pem`을 지정하면 사슬이 끊긴 채로 서비스가 뜬다.

```nginx
# Before: 서버 인증서만 지정 — 중간 인증서가 안 나간다
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/cert.pem;      # leaf 한 장뿐
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
}
```

```nginx
# After: leaf + 중간 인증서가 합쳐진 파일을 지정 — 사슬이 완성된다
server {
    listen 443 ssl;
    server_name api.example.com;

    # fullchain.pem = 서버 인증서 + 중간 인증서 (루트는 클라이언트가 이미 갖고 있으므로 불필요)
    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;
}
```

**여기서 진짜 함정은, 이 설정 실수가 어떤 클라이언트에서는 안 드러난다는 것이다.**

중간 인증서가 없을 때 클라이언트가 취할 수 있는 행동이 두 갈래이기 때문이다.

- **스스로 메워 보는 클라이언트**: 서버 인증서에는 발급자 정보를 받아올 수 있는 URL이 들어 있다(AIA, Authority Information Access — 발급 기관 정보 접근). 데스크톱 브라우저 중에는 이 URL로 중간 인증서를 직접 내려받아 사슬을 메우거나, 예전에 다른 사이트에서 본 중간 인증서를 캐시해뒀다가 재사용하는 것들이 있다. 그러면 **검증이 성공한다.**
- **못 메우는 클라이언트**: 안드로이드의 기본 TLS 스택, 각종 언어의 HTTP 클라이언트, `curl`, 모니터링 에이전트 같은 것들은 서버가 준 사슬만으로 판단한다. 중간이 없으면 **바로 실패**한다.

그래서 증상이 이렇게 나타난다.

```
개발자 크롬     →  자물쇠 정상. "잘 되는데요?"
사파리/iOS      →  대체로 정상
안드로이드 앱    →  SSLHandshakeException: Trust anchor for certification path not found
서버 간 API 호출 →  PKIX path building failed
모니터링 봇      →  간헐적으로만 실패 (캐시 유무에 따라)
```

**"일부 클라이언트에서만 SSL 에러"**라는 신고가 오면 가장 먼저 의심할 것이 이것이다. 브라우저에서 되는지 여부는 판단 근거가 못 된다.

확인은 브라우저가 아니라 사슬을 그대로 보여주는 도구로 한다.

```bash
# 서버가 실제로 내려보내는 인증서 사슬을 그대로 확인한다
#  -servername: SNI 값. 이걸 빼면 서버가 엉뚱한(기본) 인증서를 줄 수 있다 (2-6 참고)
#  </dev/null:  연결만 맺고 바로 끊기 위해 표준입력을 비운다
openssl s_client -connect api.example.com:443 -servername api.example.com -showcerts </dev/null
```

출력의 `Certificate chain` 항목을 센다. `0 s:CN=api.example.com` 하나만 있고 `1 s:...CA...`가 없으면 중간 인증서가 안 나가고 있는 것이다. 정상이라면 리프 다음에 중간 CA 인증서가 이어지고, 맨 끝에 `Verify return code: 0 (ok)`가 나온다.

정리하면 이 사고의 교훈은 두 가지다. **인증서 설치는 "파일 하나"가 아니라 "사슬"을 설치하는 일이고, 검증 결과는 클라이언트마다 다를 수 있으므로 관대한 클라이언트로 테스트하면 사고를 놓친다.**

### 2-6. SNI — 한 IP에 여러 도메인이 있을 때 어느 인증서를 내미나

앞의 다이어그램에서 ClientHello에 `SNI 확장 = "api.example.com"`이 들어 있었다. 이게 왜 필요한지를 보면 TLS 설계의 순서 문제가 드러난다.

전제부터 깔자. 한 대의 서버(하나의 IP:443)에 여러 도메인을 얹는 것은 아주 흔하다. Nginx의 가상 호스트가 그것이다. 그런데 **HTTP는 어느 도메인으로 온 요청인지를 `Host` 헤더로 알린다.** 문제는 `Host` 헤더가 **암호화된 뒤에** 오는 HTTP의 일부라는 것이다.

```
서버 입장의 순서 문제:
  ① TLS handshake에서 인증서를 먼저 내밀어야 한다
  ② 그런데 어느 도메인의 인증서를 내밀지는 Host 헤더를 봐야 안다
  ③ Host 헤더는 handshake가 끝나야 복호화해서 볼 수 있다
  → 순환. 인증서를 고를 수 없다.
```

이 순환을 끊으려고 만든 것이 **SNI(Server Name Indication, 서버 이름 알림)**다. **클라이언트가 ClientHello에 "나는 이 도메인에 접속하려 한다"를 평문으로 적어 보내는 TLS 확장**이다. 서버는 그 값을 보고 해당 도메인의 인증서를 골라 내민다.

```nginx
# 같은 IP:443에 두 도메인. 서버는 ClientHello의 SNI 값으로 server 블록을 고른다.
server {
    listen 443 ssl;
    server_name api.example.com;
    ssl_certificate     /etc/nginx/certs/api-fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/api-privkey.pem;
}

server {
    listen 443 ssl;
    server_name admin.example.com;
    ssl_certificate     /etc/nginx/certs/admin-fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/admin-privkey.pem;
}
```

여기서 실무적으로 알아둘 점이 셋이다.

**SNI가 없으면 서버는 기본 인증서를 준다.** SNI를 안 보내는(혹은 잘못 보내는) 클라이언트에게는 첫 번째 server 블록의 인증서가 나가고, 클라이언트는 "도메인 불일치"로 거절한다. 위의 `openssl s_client`에서 `-servername`을 빼면 딱 이 현상이 재현된다 — 도구 사용 실수로 멀쩡한 서버를 장애로 오진하기 쉬운 지점이다.

**SNI는 평문이다.** handshake 초입에 인증서를 고르기 위한 정보이므로 암호화할 수가 없다(암호화 키를 아직 못 정했으니까). 그래서 HTTPS를 써도 **어느 도메인에 접속하는지는 중간에서 관찰 가능**하다. 이걸 감추려는 것이 ECH(Encrypted Client Hello) 같은 확장이 나온 배경이다.

**SNI는 암호문을 풀지 않고도 읽을 수 있다.** 이 성질이 17번(TLS termination) 문서에서 다시 등장한다. L4 로드밸런서는 TLS를 종료하지 않아 HTTP를 못 보지만, ClientHello의 SNI만은 평문이라 **그것을 보고 백엔드를 고르는 라우팅**은 할 수 있다.

### 2-7. 키 합의 — RSA 키 교환(과거)과 ECDHE(현재)

신원 확인이 끝났으면 이제 대칭키를 만들어야 한다. 여기에 역사적으로 두 가지 방식이 있었고, **왜 하나가 퇴출됐는지**가 이 주제의 핵심이다.

#### 방식 ① RSA 키 교환 — 서버 공개키로 비밀을 배달한다 (과거)

가장 직관적인 방법이다. 클라이언트가 대칭키의 재료가 될 랜덤한 비밀값을 만들고, **인증서에 들어 있던 서버의 공개키로 암호화해서** 보낸다. 서버는 자기 개인키로 그것을 풀어 같은 비밀값을 얻는다.

```
클라이언트: 비밀값 S를 만든다
            서버 공개키로 암호화한 E(S)를 전송  ──────→  서버: 개인키로 풀어 S를 얻는다
                        (도청자는 E(S)를 봐도 개인키가 없어 S를 못 얻는다)
양쪽이 S를 공유 → 여기서 대칭키를 파생
```

동작한다. 그런데 치명적인 성질이 하나 숨어 있다. **비밀값 S가 서버의 개인키로 잠겨서 네트워크를 지나갔다**는 점이다.

공격자가 지금 당장 S를 못 푼다고 해서 끝이 아니다. **암호문을 통째로 녹화해 저장해 두면 된다.** 몇 년 뒤 어떤 경로로든 서버 개인키가 유출되는 순간, 그 공격자는 저장해둔 과거 트래픽의 E(S)를 전부 풀어 S를 얻고, S에서 대칭키를 파생해 **과거의 모든 통신을 복호화**할 수 있다. 개인키 유출 하나가 과거 전체로 소급되는 구조다.

#### 방식 ② ECDHE — 매번 버리는 임시 키로 비밀을 "각자 계산"한다 (현재)

**ECDHE**는 Elliptic Curve Diffie-Hellman Ephemeral의 약자다. 이름을 뜯으면 성격이 그대로 드러난다.

- **DH(Diffie-Hellman)**: 두 사람이 각자 비밀값을 갖고 공개 파라미터만 주고받았는데, 수학적 성질에 의해 **양쪽이 같은 값에 도달하는** 키 합의 방식. 도청자는 오간 공개 파라미터를 전부 봐도 그 값을 계산할 수 없다.
- **EC(Elliptic Curve, 타원곡선)**: 같은 안전성을 훨씬 짧은 키로 얻는 수학적 토대.
- **E(Ephemeral, 임시)**: **연결마다 키 쌍을 새로 만들고, 다 쓰면 버린다.** 이 글자 하나가 순방향 비밀성의 전부다.

```
클라이언트                                   서버
  임시 키 쌍 (a, A) 생성                       임시 키 쌍 (b, B) 생성
      │                                          │
      │──────────  A (공개 파라미터)  ──────────→ │
      │←─────────  B (공개 파라미터) + 서명 ──────│  ← 서명은 인증서의 개인키로
      │                                          │
  a와 B로 비밀값 계산                          b와 A로 비밀값 계산
      └────────── 양쪽이 같은 값에 도달 ──────────┘
                        │
                   대칭키 파생
        (a, b는 연결이 끝나면 버려진다 — 어디에도 저장되지 않는다)
```

**핵심 차이는 "비밀값이 네트워크를 지나가지 않는다"는 것이다.** RSA 방식에서는 비밀값이 암호화된 채로라도 전송됐지만, ECDHE에서는 **양쪽이 각자 계산해서 도달**한다. 오간 것은 공개 파라미터뿐이다.

그러면 인증서의 개인키는 여기서 무슨 일을 하나? **서명만 한다.** 서버는 자기가 보낸 임시 파라미터 B에 인증서의 개인키로 서명을 붙인다. 클라이언트는 인증서의 공개키로 그 서명을 검증해서 **"이 키 합의를 하고 있는 상대가 인증서의 주인이 맞다"**를 확인한다. 만약 이 서명이 없으면 중간자가 자기 임시 파라미터로 갈아치워 양쪽과 각각 키 합의를 해버릴 수 있다.

#### 순방향 비밀성 — 두 방식이 갈리는 지점

**순방향 비밀성(forward secrecy)**은 **서버의 장기 개인키가 나중에 유출되더라도, 그 이전에 오간 통신은 복호화되지 않는다**는 성질이다.

이름의 "앞으로(forward)"는 시간의 앞쪽, 즉 **미래에 일어날 키 유출 사건**을 가리킨다. 그런 일이 앞으로 벌어져도 과거의 비밀은 지켜진다는 뜻이다.

| | RSA 키 교환 | ECDHE |
|---|---|---|
| 대칭키 재료가 네트워크를 지나가나 | 지나간다 (서버 공개키로 암호화된 채) | 지나가지 않는다 (양쪽이 각자 계산) |
| 인증서 개인키의 역할 | 비밀값 복호화 + 신원 증명 | **신원 증명(서명)만** |
| 개인키 유출 시 과거 트래픽 | 전부 복호화됨 | 안전 |
| 순방향 비밀성 | 없음 | 있음 |

**"왜 지금은 RSA 키 교환을 안 쓰는가"의 답이 이 표다.** TLS 1.3은 아예 RSA 키 교환을 프로토콜에서 제거하고 (EC)DHE 계열만 남겼다. 선택지로 남겨두면 협상 과정에서 약한 쪽으로 끌어내려지는 공격이 가능하기 때문에, **위험한 선택지 자체를 없앤 것**이다.

여기서 한 가지 오해를 짚고 가자. RSA가 TLS에서 사라진 게 아니다. **키 교환에서 빠졌을 뿐 서명에는 그대로 쓰인다.** `TLS_ECDHE_RSA_WITH_...` 스위트가 그 뜻이다 — 키 합의는 ECDHE, 서명은 RSA.

### 2-8. TLS 1.3 — 1-RTT, 세션 재개, 그리고 0-RTT의 재전송 위험

**RTT(Round Trip Time)**는 패킷이 상대에게 갔다가 돌아오는 데 걸리는 왕복 시간이다. handshake 성능을 말할 때 "몇 왕복이 필요한가"가 곧 지연이 된다.

2-1에서 본 TLS 1.2 흐름은 왕복이 **2회**다. ①ClientHello를 보내고 ServerHello~ServerHelloDone을 받는 데 1회, ②ClientKeyExchange~Finished를 보내고 서버의 Finished를 받는 데 1회. 이게 끝나야 HTTP 요청을 보낼 수 있다.

TLS 1.3은 이걸 **1회**로 줄였다. 방법은 **추측 선반영**이다. 클라이언트가 ClientHello를 보낼 때 "어차피 서버가 고를 만한 방식은 뻔하니" **키 교환 파라미터를 미리 같이 실어 보낸다**(key_share). 서버는 그것을 받아 곧바로 자기 파라미터·인증서·Finished까지 한 번에 답한다. 클라이언트는 답을 받자마자 대칭키를 만들 수 있으므로, 자기 Finished와 함께 **HTTP 요청을 바로 붙여 보낸다.**

```
[TLS 1.2 — 2 RTT]
  C ──ClientHello──────────────────→ S
  C ←──ServerHello, Cert, SKE, Done─ S     (1 RTT)
  C ──CKE, CCS, Finished───────────→ S
  C ←──CCS, Finished──────────────── S     (2 RTT)
  C ──HTTP 요청────────────────────→ S

[TLS 1.3 — 1 RTT]
  C ──ClientHello + key_share──────→ S
  C ←──ServerHello + key_share,
        Cert, CertVerify, Finished── S     (1 RTT)
  C ──Finished + HTTP 요청─────────→ S     ← 요청을 바로 붙여 보낸다
```

TLS 1.3에서 인증서가 **암호화되어 전달**된다는 점도 부수적인 개선이다(위 그림의 Cert는 ServerHello 이후이므로 이미 키가 정해진 뒤다). TLS 1.2에서는 인증서가 평문으로 오갔다.

#### 세션 재개 — 한 번 만난 서버와는 처음부터 다시 하지 않는다

**세션 재개(session resumption)**는 이전 연결에서 합의했던 비밀을 근거로 **인증서 검증과 키 합의를 생략**하고 짧게 연결을 여는 방식이다. 브라우저가 같은 사이트를 다시 열 때, 또는 커넥션 풀의 연결이 끊겼다 다시 붙을 때 값을 한다.

구현 방식이 두 갈래인데, 이 구분이 운영에서 의미가 있다.

- **세션 ID 방식**: 서버가 세션 상태를 **자기 메모리에 캐시**해두고 클라이언트에게는 ID만 준다. 서버가 상태를 들고 있으므로, 서버 인스턴스가 여러 대면 **다른 인스턴스로 붙었을 때 재개가 안 된다.**
- **세션 티켓 방식**: 서버가 세션 상태를 **자기만 아는 키로 암호화해 클라이언트에게 통째로 맡긴다.** 서버는 상태를 안 들고 있어도 되지만, 그 **티켓 암호화 키를 모든 인스턴스가 공유**해야 재개가 성립한다.

TLS 1.3은 이 둘을 PSK(Pre-Shared Key, 미리 공유된 키) 기반의 한 가지 방식으로 통합했다.

여기에 시니어가 짚을 만한 포인트가 하나 있다. **티켓 암호화 키를 오래 쓰면 순방향 비밀성이 약해진다.** 그 키 하나가 유출되면 그 키로 발급된 모든 티켓이 열리고, 티켓 안에는 세션 비밀이 들어 있기 때문이다. 그래서 티켓 키는 주기적으로 교체해야 한다 — ECDHE로 애써 확보한 성질을 운영 설정 하나로 잃을 수 있다는 예다.

#### 0-RTT — 왕복 0회, 대신 재전송 위험

TLS 1.3에는 한 걸음 더 나간 **0-RTT**가 있다. 이전에 재개용 키를 받아둔 서버에는 **ClientHello와 함께 HTTP 요청을 바로 실어 보낸다**(early data, 조기 데이터). 왕복을 기다리지 않으므로 handshake 지연이 사실상 0이 된다.

대가는 **재전송(replay) 공격에 취약하다**는 것이다. 이유는 간단하다. 0-RTT 데이터는 이번 연결에서 새로 합의한 비밀이 아니라 **이전에 받아둔 키**로 암호화된다. 그래서 handshake의 "이번 연결에만 유효함"을 보장하는 절차를 거치지 않는다.

```
공격자가 0-RTT 요청 패킷을 그대로 복사해 여러 번 서버에 보낸다
   → 서버는 그것이 재전송인지 구분할 근거가 없다
   → 만약 그 요청이 POST /orders 였다면? 주문이 여러 건 생긴다
```

그래서 0-RTT는 **여러 번 실행돼도 결과가 같은 요청(멱등한 요청)에만 허용**하는 것이 원칙이다. 실무에서는 CDN·프록시 설정에서 0-RTT를 GET에만 허용하거나 아예 끄는 선택을 한다. "성능을 위해 켰더니 결제가 두 번 됐다"가 나올 수 있는 자리다.

## 3. 운영 관점 — 이 구조가 설명하는 현상들

### 3-1. "첫 요청만 느리다"의 정체 — 어느 구간에서 시간이 가는가

1-4의 결론 — **TLS 비용은 연결 수립 시점에 몰려 있다** — 을 시간축에 펼쳐 보면 왜 첫 요청만 느린지가 눈에 보인다.

비용은 두 종류다. **왕복 지연**(handshake 메시지가 오가는 시간)과 **연산 비용**(서명 검증, 키 합의 같은 비대칭 연산). 둘 다 연결을 만들 때만 발생하고, 그 뒤의 대칭키 암복호화는 하드웨어 가속을 받아 거의 공짜에 가깝다.

RTT가 40ms인 환경에서 TLS 1.3으로 HTTPS 첫 요청을 보내면 이렇게 된다.

```
[첫 요청 — 새 연결]
  0ms     40ms     80ms    120ms    160ms
  │        │        │        │        │
  ├─ DNS ──┤                                  도메인 → IP 조회 (캐시에 있으면 0)
           ├─ TCP ──┤                         SYN → SYN+ACK → ACK
                    ├─ TLS ──┤                ClientHello → ServerHello+인증서+Finished
                             ├─ HTTP ─┤       GET → 응답 첫 바이트
                                      ↑
                              여기까지 왕복 4회 = 160ms + 서버 처리 시간

[같은 연결을 재사용하는 두 번째 요청]
  0ms     40ms
  ├─ HTTP ─┤                                  왕복 1회 = 40ms + 서버 처리 시간
```

한 단계씩 세어 보면 이렇다. DNS 조회 1회, TCP 3-way handshake 1회(세 번째 ACK와 함께 데이터를 보낼 수 있으므로 실질 1왕복), TLS 1.3 handshake 1회, HTTP 요청·응답 1회 — 합쳐서 **4왕복 = 160ms**. 반면 연결을 재사용하는 두 번째 요청은 HTTP 1왕복 = **40ms**뿐이다. **같은 API인데 첫 요청이 네 배 느린 것**이고, DNS가 캐시돼 있어도 3왕복 대 1왕복이라 세 배다. TLS 1.2였다면 TLS 구간이 2왕복이라 첫 요청은 5왕복 = 200ms가 된다.

여기서 두 가지가 따라 나온다.

**첫째, 대응의 1순위는 프로토콜 튜닝이 아니라 연결 재사용이다.** TLS 1.3으로 올려서 아끼는 것이 1왕복인데, 연결을 재사용하면 TCP+TLS 2~3왕복을 통째로 없앤다. 서버 간 API 호출에서 매번 새 클라이언트를 만드는 코드가 있다면 그것이 가장 큰 손해다.

```java
// Before: 반복문 안에서 매번 새 클라이언트 — 요청마다 TCP handshake + TLS handshake를 새로 한다.
// 주문 1000건이면 handshake도 1000번. 서버 처리 시간은 그대로인데 대기 시간만 몇 배가 된다.
for (Order order : orders) {
    RestClient client = RestClient.create();          // 커넥션 풀이 없으므로 연결이 재사용되지 않는다
    client.post().uri(PAYMENT_URL).body(order).retrieve().toBodilessEntity();
}

// After: 커넥션 풀을 가진 클라이언트를 빈으로 만들어 재사용 — handshake는 풀이 연결을 새로 열 때만.
// 두 번째 요청부터는 위 타임라인의 "HTTP 1왕복"만 남는다.
RestClient client = RestClient.builder()
        .requestFactory(pooledRequestFactory)          // keep-alive + 커넥션 풀
        .build();
for (Order order : orders) {
    client.post().uri(PAYMENT_URL).body(order).retrieve().toBodilessEntity();
}
```

**둘째, 남은 왕복 비용은 "거리"의 문제다.** handshake 왕복 횟수는 프로토콜이 정하지만 한 왕복에 걸리는 시간은 물리적 거리가 정한다. 그래서 사용자 가까운 엣지(CDN)에서 TLS를 종료하면 왕복이 짧아진다 — 서버를 옮기지 않고도 handshake 지연을 줄이는 방법이다.

서버 쪽에서 할 수 있는 것은 **세션 재개를 켜서**(2-8) 재접속 클라이언트의 handshake를 줄이는 것, 그리고 **TLS 종료를 LB 계층으로 모아** 앱의 암복호화·연결 관리 부담을 분리하는 것이다. 후자는 17번(TLS termination) 문서에서 따로 다룬다.

### 3-2. 인증서 만료 = 전면 장애

인증서 검증은 handshake **초입의 관문**이다(2-1의 검증 박스). 여기서 실패하면 HTTP 요청은 시작도 못 한다. 그래서 인증서 만료의 증상은 특이하다.

- 앱 코드는 멀쩡하고, 배포한 것도 없고, 로그에 에러도 없다.
- 서버에 SSH로 붙으면 프로세스는 정상이고 `curl -k`(검증 생략)로는 응답이 온다.
- 그런데 **모든 신규 연결이 거절**되어 서비스 전체가 접속 불가다.

이미 맺어진 연결은 잠시 살아 있을 수 있어서 "일부만 되는 것처럼" 보이다가 순식간에 전면 장애로 번진다. 원인 파악이 늦어지기 딱 좋은 형태다.

이 장애의 유일한 대응은 **예방**이다. 터진 뒤에 할 수 있는 일은 갱신뿐이고, 갱신에는 발급 대기·배포·리로드 시간이 걸린다.

**갱신 자동화가 1순위다.** Let's Encrypt 인증서는 유효기간이 90일이라 애초에 손으로 관리할 수 없고, 이런 짧은 유효기간이 표준이 되어 가는 흐름이라 자동 갱신은 이제 선택이 아니다. ACME 프로토콜을 쓰는 도구(certbot 등)나 클라우드의 관리형 인증서로 발급·갱신·배포를 자동화한다.

**그리고 자동화를 믿지 말고 만료일을 감시한다.** 자동 갱신은 생각보다 자주 조용히 실패한다 — 도메인 검증 방식이 바뀌거나, 갱신 후 서버 리로드가 빠졌거나(파일은 새 것인데 프로세스는 옛 인증서를 메모리에 들고 있는 경우), 갱신 훅이 다른 서버에만 적용됐거나. 그래서 **실제로 서비스가 내려보내고 있는 인증서**의 만료일을 밖에서 확인하는 감시를 따로 둔다.

```bash
# 실제 서비스 포트가 내려보내는 인증서의 만료일을 확인한다.
# 파일이 아니라 "밖에서 본 값"을 보는 것이 핵심 — 갱신은 됐는데 리로드가 안 된 경우까지 잡힌다.
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -enddate

# 만료까지 30일 미만이면 실패로 떨어뜨린다 (알림 연동용)
#  -checkend 는 "지정한 초 뒤에도 유효한가"를 판정한다. 2592000초 = 30일
openssl s_client -connect api.example.com:443 -servername api.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -checkend 2592000
```

임계값은 **D-30 알림 + D-7 에스컬레이션**처럼 두 단계로 두는 것이 실용적이다. D-30은 "갱신 파이프라인이 돌 시간이 아직 충분하다"는 여유 구간이고, D-7은 "사람이 개입해야 한다"는 신호다.

감시 대상을 빠뜨리지 않는 것도 중요하다. **종료 지점이 여러 곳이면 감시 대상도 그만큼 늘어난다.** 외부 LB, 내부 통신용 인증서, 배치 서버가 쓰는 클라이언트 인증서, 개발·스테이징 환경까지 각각이 별도의 만료 시한을 갖는다. 이 "종료 지점 수 = 만료 사고 가능 지점 수"라는 산수가 17번 문서에서 종료 위치를 고르는 핵심 근거가 된다.

## 4. 꼬리질문 대비 포인트

### "왜 전부 비대칭키로 암호화하지 않나요?"

성능 때문이다. 비대칭 연산은 큰 수의 거듭제곱이나 타원곡선 연산이라 대칭키 연산과 비용의 자릿수가 다르다. 게다가 대칭키 쪽은 CPU의 AES 하드웨어 가속까지 받는다. 모든 요청·응답 본문을 비대칭으로 처리하면 서버 CPU가 암호 연산에 묶여 병목이 된다.

그렇다고 전부 대칭키로만 할 수도 없다. 처음 만난 상대와 **키를 안전하게 나눠 가질 방법이 없기** 때문이다(1-2의 키 배달 문제).

그래서 답은 "둘 중 뭐가 낫냐"가 아니라 **역할 분담**이다. 비싼 비대칭은 연결당 한 번, 그것도 **신원 확인과 키 합의라는 딱 두 가지 일에만** 쓰고, 싼 대칭은 그 뒤 모든 바이트에 쓴다. 각 방식이 못 푸는 문제를 상대가 정확히 하나씩 풀어주는 구조라고 말하면 설명이 닫힌다.

### "인증서는 정확히 무엇을 보장하나요? 없으면 어떤 공격이 가능한가요?"

인증서가 보장하는 것은 한 문장이다. **"이 공개키는 이 도메인 소유자의 것"이라는 사실을 CA가 서명으로 보증한다.** 인증서 자체는 비밀이 아니고 암호화에 쓰이지도 않는다 — 보장하는 것은 기밀성이 아니라 **인증**이다.

없으면 **중간자 공격(MITM)**이 성립한다. 공격자가 클라이언트와 서버 사이에 끼어 클라이언트에게는 자기 공개키를 "내가 그 서버다"라며 내밀고, 서버에게는 자기가 클라이언트인 척 붙는다. 그러면 공격자는 양쪽과 각각 정상적으로 암호화된 연결을 맺고, 가운데서 평문을 다 본다. **클라이언트는 자물쇠 아이콘을 보면서 공격자와 안전하게 통신한다.**

여기서 핵심은 **암호화(도청 방지)와 인증(상대 확인)이 별개의 보장**이라는 것이다. 암호화만으로는 "누구와" 통신하는지가 비어 있고, 그 빈칸을 인증서가 채운다.

메커니즘까지 덧붙이면 좋다. 클라이언트는 서버 인증서의 서명을 중간 CA 공개키로, 중간 CA 인증서의 서명을 루트 CA 공개키로 검증해 올라가고, 그 루트가 브라우저·OS의 신뢰 저장소에 들어 있으면 사슬이 완성된다. 여기에 유효기간과 도메인(SAN) 일치까지 확인해야 통과다. 폐기 확인(OCSP·CRL)이라는 항목도 있지만 클라이언트마다 정책이 달라 실시간 확인에 의존하지 않는 경우가 많다는 점까지 알면 충분하다.

### "순방향 비밀성(forward secrecy)이 뭔가요?" (시니어 변별 포인트)

**서버의 개인키가 나중에 유출되더라도, 그 이전에 도청해 저장해둔 트래픽은 복호화되지 않는다**는 성질이다. 이름의 "앞으로(forward)"는 미래에 일어날 키 유출 사건을 가리킨다 — 그 일이 앞으로 벌어져도 과거는 지켜진다는 뜻이다.

왜 방식에 따라 갈리는지가 답의 본체다. RSA 키 교환에서는 대칭키의 재료가 **서버 공개키로 암호화된 채 네트워크를 지나갔다.** 공격자가 암호문을 통째로 녹화해두면, 훗날 개인키가 유출되는 순간 저장해둔 과거 트래픽이 전부 열린다.

ECDHE는 **연결마다 임시 키 쌍을 만들어 쓰고 버린다.** 대칭키의 재료는 양쪽이 각자 계산해 도달할 뿐 네트워크를 지나가지 않고, 임시 키는 어디에도 저장되지 않는다. 인증서의 개인키는 **서명(신원 증명)에만** 쓰여서 대칭키 재료와 아무 관계가 없다. 그래서 개인키 유출이 과거로 소급되지 않는다.

TLS 1.3이 RSA 키 교환을 아예 제거한 이유가 이것이다. **선택지로 남겨두면 협상에서 약한 쪽으로 끌어내려질 수 있으니 위험한 선택지 자체를 없앤 것**이다.

한 걸음 더 나가면 가산점이다. **세션 티켓 키를 오래 재사용하면 순방향 비밀성이 약해진다.** 티켓 안에는 세션 비밀이 들어 있고 그것을 티켓 키가 잠그고 있으므로, 티켓 키 하나의 유출이 그 키로 발급된 모든 세션을 연다. ECDHE로 확보한 성질을 운영 설정으로 잃을 수 있다는 것 — "키 유출이라는 최악의 시나리오에서 피해 범위를 얼마나 좁혀 두었나"를 설계와 운영 양쪽에서 보는 사고방식이다.

### "TLS handshake 지연을 줄이려면 어떤 방법들이 있나요?"

**어느 비용을 줄이는 방법인지**를 구분해서 말하면 정리가 좋아 보인다. 비용은 왕복 지연과 연산, 둘뿐이다.

**(1) 왕복 횟수 자체를 없앤다 — 연결 재사용.** 가장 효과가 크다. keep-alive와 커넥션 풀로 연결을 유지하면 TCP+TLS 왕복(2~3회)이 통째로 사라지고 HTTP 1왕복만 남는다. HTTP/2도 한 연결에 여러 요청을 실어 연결 수 자체를 줄이므로 같은 계열의 효과다.

**(2) 왕복 횟수를 줄인다 — 프로토콜.** TLS 1.3으로 2왕복을 1왕복으로, 세션 재개로 재접속 시 handshake를 더 짧게. 0-RTT까지 가면 왕복 0회지만 재전송 위험 때문에 멱등한 요청에만 제한적으로 쓴다.

**(3) 한 왕복의 시간을 줄인다 — 거리.** 왕복 시간은 물리적 거리가 정한다. CDN·엣지에서 TLS를 종료하면 사용자 가까운 곳에서 handshake가 끝난다.

**(4) 연산 부담을 옮긴다 — 오프로드.** TLS 종료를 LB 계층으로 모아 비대칭 연산과 연결 관리를 앱에서 분리한다. 다만 이건 지연을 줄인다기보다 **앱 CPU를 비즈니스 로직에 돌려주는** 쪽에 가깝다.

우선순위를 말하라면 (1)이 압도적이다. 나머지는 (1)을 이미 하고 있다는 전제 위의 최적화다.

### "HTTPS면 요청 내용이 전부 안 보이나요?" (가산점 포인트)

**다 숨는 것은 아니다.** 무엇이 감춰지고 무엇이 남는지를 구분할 수 있어야 한다.

**감춰지는 것**: HTTP 요청 라인(메서드·경로·쿼리스트링), 모든 헤더(쿠키·Authorization 포함), 본문. 즉 `POST /orders?couponId=3`이라는 사실 자체가 안 보인다.

**남는 것**: 먼저 **접속 대상 IP와 포트**는 TCP 계층이라 그대로 보인다. 그리고 **도메인 이름**은 handshake의 SNI가 평문이라(2-6) 관찰 가능하다 — 인증서를 고르기 위해 암호화 이전에 보내야 하는 값이라서 구조적으로 그렇다. 이것을 감추려는 것이 ECH(Encrypted Client Hello)가 나온 배경이다.

마지막으로 **트래픽의 크기와 타이밍 패턴**은 암호화와 무관하게 관찰된다. 언제 얼마나 주고받았는지만으로도 어떤 페이지를 봤는지 추론하는 연구가 있을 만큼 의미 있는 신호다.

정리하면 **HTTPS는 "무엇을 말했는지"를 감추지 "누구와 언제 얼마나 말했는지"까지 감추지는 않는다.** 암호화의 보장 범위를 정확히 아는 것도 보안 감각의 일부다.

## 한 줄 요약

TLS handshake는 비대칭키로 "상대가 진짜인가"(인증서의 CA 서명을 신뢰 사슬을 따라 검증)와 "대칭키를 안전하게 합의"(ECDHE — 임시 키 쌍이라 개인키가 유출돼도 과거가 안전한 순방향 비밀성)를 끝내는 비싼 개회식이고 그 뒤 모든 데이터는 싸고 빠른 대칭키가 맡는다 — 비용이 연결 수립에 몰려 있으므로 연결 재사용(keep-alive)이 곧 TLS 성능 최적화이고, 인증서는 그 개회식의 관문이라 만료되면 전면 장애이며 중간 인증서를 빠뜨리면 "일부 클라이언트에서만 실패"라는 추적하기 까다로운 사고가 난다.
