# TLS handshake — 비대칭키로 열쇠를 나누고, 대칭키로 본문을 잠근다

> 핵심 관전 포인트: **TLS는 두 종류의 암호화를 역할 분담시킨다 —
> 느리지만 "키를 안전하게 나눠 갖는 문제"를 풀 수 있는 비대칭키로
> handshake에서 (1) 서버 신원 확인(인증서 서명 검증)과 (2) 대칭키
> 합의를 끝내고, 그 뒤의 실제 데이터는 빠른 대칭키로 암호화한다.
> 전 구간을 비대칭으로 하면 너무 느리고, 처음부터 대칭으로 하면
> 키를 건네줄 방법이 없기 때문이다. 이 구조를 알면 "HTTPS는 왜
> 첫 요청만 느린가"(handshake의 왕복 + 비대칭 연산이 연결 수립
> 시점에 몰려 있다), "인증서 만료가 왜 전면 장애인가"(신원 확인
> 단계에서 연결 자체가 거절된다) 같은 운영 질문이 전부 풀린다.**

---

## 0. 질문 + 의도

**질문**: "HTTPS(TLS) handshake 과정을 설명해주세요. 대칭키와 비대칭키는 각각 어디에 쓰이나요?"

**출제 의도**: HTTPS 인증서 만료, 핸드셰이크 지연 같은 운영 이슈를
다룰 때의 기초. 비대칭으로 키 교환, 대칭으로 본문 암호화라는 구조를
알면 "TLS가 왜 첫 요청만 느린가"류의 성능 질문도 풀린다.

## 1. 왜 키가 두 종류인가 — 각자 못 푸는 문제가 있다

### 대칭키: 빠르지만 "키 배달 문제"가 있다

대칭키 암호화(AES 등)는 **잠글 때와 열 때 같은 키**를 쓴다.
연산이 가볍고 CPU의 하드웨어 가속(AES-NI)까지 받아 대용량 데이터를
실시간으로 암복호화할 수 있다 — 본문 암호화의 적임자다.

문제는 시작점이다. 서버와 브라우저가 같은 키를 나눠 가져야 하는데,
그 키를 **어떻게 전달하나?** 아직 암호화 통신이 없는 상태에서 키를
평문으로 보내면 중간에서 훔쳐보는 공격자(중간자)도 키를 갖게 된다.
잠긴 금고를 보내면서 열쇠를 금고 옆에 테이프로 붙여 보내는 격이다.

### 비대칭키: 키 배달 문제를 풀지만 느리다

비대칭키(공개키 암호화)는 **키가 쌍**이다 — 공개키로 잠근 것은
개인키로만 열리고, 개인키로 서명한 것은 공개키로 검증된다.
공개키는 누구에게나 공개해도 되므로 "사전에 비밀을 공유하지 않은
상대와 비밀을 만드는" 문제를 풀 수 있다.

대신 수학적 연산(큰 수의 거듭제곱 등)이 대칭키 대비 훨씬 무겁다.
모든 HTTP 본문을 비대칭으로 암호화하면 서버 CPU가 견디지 못한다.

그래서 TLS의 설계는 역할 분담이다:

| | 비대칭키 | 대칭키 |
|---|---|---|
| 쓰이는 곳 | handshake (신원 확인 + 키 합의) | handshake 이후 모든 데이터 |
| 푸는 문제 | 처음 만난 상대와 안전하게 비밀 만들기 | 대량 데이터의 빠른 암복호화 |
| 비용 | 무겁다 (연결당 몇 번만) | 가볍다 (모든 바이트에) |

비유하면 **비대칭키는 계약 자리에서 신분증을 확인하고 금고 비밀번호를
정하는 절차**이고, **대칭키는 그 뒤 금고를 실제로 여닫는 비밀번호**다.
비싼 절차는 처음 한 번, 싼 연산은 매번.

## 2. handshake 과정 — 신원 확인과 키 합의

TCP 연결(3-way handshake)이 끝난 위에서 TLS handshake가 시작된다.
TLS 1.2 기준 흐름:

```
클라이언트                                서버
   │── ClientHello ─────────────────────→│  지원하는 TLS 버전·암호 스위트 목록,
   │                                     │  클라이언트 랜덤값
   │←───────────────── ServerHello ──────│  선택한 암호 스위트, 서버 랜덤값
   │←──────────────────── Certificate ───│  서버 인증서 (공개키 포함)
   │←──────────── ServerKeyExchange ─────│  키 교환용 임시(ECDHE) 파라미터 + 서명
   │                                     │
   │  [인증서 검증: CA 서명 사슬 확인]     │
   │                                     │
   │── ClientKeyExchange ───────────────→│  키 교환 파라미터 전달
   │  [양쪽이 동일한 대칭키를 각자 계산]    │
   │── Finished (이후 대칭키 암호화) ────→│
   │←──────────────────── Finished ──────│
   │                                     │
   │══ 이후 HTTP 요청/응답: 대칭키 암호화 ══│
```

단계별로 비대칭키가 하는 일이 두 가지로 나뉜다는 점이 핵심이다.

### (1) 신원 확인 — "이 공개키가 진짜 이 도메인의 것인가"

서버가 보낸 인증서에는 서버의 공개키와 도메인 정보가 들어 있고,
**CA(인증기관)의 개인키로 서명**되어 있다. 브라우저는 내장된 CA
공개키로 이 서명을 검증한다(중간 CA가 있으면 사슬을 따라 올라간다).
이 검증이 없으면 중간자가 자기 공개키를 "내가 그 서버다"라며 내밀어도
구분할 수 없다 — **암호화만으로는 부족하고, "누구와" 암호화 통신을
하는지가 인증서로 보장**된다. 인증서 만료·도메인 불일치 시 연결이
이 단계에서 거절되는 이유다.

### (2) 키 합의 — 대칭키를 안전하게 만들기

현대 TLS의 표준은 **ECDHE(임시 디피-헬만) 키 교환**이다. 양쪽이
임시 키 쌍을 만들어 공개 파라미터만 주고받으면, 수학적 성질에 의해
**양쪽이 같은 비밀값을 각자 계산**해낸다 — 도청자는 오간 파라미터를
다 봐도 비밀값을 계산할 수 없다. 이 비밀값에서 대칭키(세션 키)가
파생된다. 서버는 이 임시 파라미터에 인증서의 개인키로 서명해
"이 키 교환을 하는 게 진짜 나"임을 증명한다.

과거에는 클라이언트가 비밀값을 서버 공개키로 암호화해 보내는
RSA 키 교환도 썼지만, 서버 개인키가 유출되면 과거 트래픽까지 전부
복호화되는 약점 때문에 TLS 1.3에서는 제거됐다(꼬리질문의
순방향 비밀성 참고).

### TLS 1.3의 간소화 (가산점 포인트)

TLS 1.2는 handshake에 왕복 2회(2-RTT)가 필요하지만, TLS 1.3은
ClientHello에 키 교환 파라미터를 실어 보내 **1-RTT**로 줄였고,
한 번 접속한 서버에는 세션 재개로 handshake를 더 줄일 수 있다
(0-RTT는 재전송 공격 고려 필요). 지연에 민감한 서비스에서 TLS 1.3
활성화가 체감 성능 개선이 되는 이유다.

## 3. 운영 관점 — 이 구조가 설명하는 현상들

### "첫 요청만 느리다"의 정체

TLS 비용은 **연결 수립 시점에 몰려 있다**: handshake 왕복(RTT × 1~2회)
+ 비대칭 연산(서명 검증, 키 합의). 연결이 만들어진 뒤의 대칭키
암복호화는 매우 싸다. 따라서 대응도 "연결을 아껴 쓰기"가 된다 —
keep-alive와 커넥션 풀로 연결을 재사용하면 handshake를 반복하지 않는다.

```java
// Before: 요청마다 새 클라이언트/연결 — 매번 TCP + TLS handshake 비용
for (Order order : orders) {
    RestClient client = RestClient.create();          // 연결 재사용 없음
    client.post().uri(PAYMENT_URL).body(order).retrieve().toBodilessEntity();
}

// After: 커넥션 풀을 가진 클라이언트를 재사용 — handshake는 연결당 1회
RestClient client = RestClient.builder()
        .requestFactory(pooledRequestFactory)          // keep-alive + 커넥션 풀
        .build();
for (Order order : orders) {
    client.post().uri(PAYMENT_URL).body(order).retrieve().toBodilessEntity();
}
```

같은 원리로 서버 쪽에서는 세션 재개(session resumption)를 켜서
재접속 클라이언트의 handshake를 단축하고, TLS 종료를 LB로 모아
앱의 암복호화 부담을 덜기도 한다(TLS termination 문서에서 별도로 다룸).

### 인증서 만료 = 전면 장애

인증서 검증은 handshake 초입의 관문이라, 만료된 순간부터 **모든 신규
연결이 수립 단계에서 거절**된다. 앱 코드는 멀쩡한데 서비스 전체가
접속 불가가 되는, 예방(만료 모니터링, 갱신 자동화)이 유일한 대응인
장애 유형이다.

## 4. 꼬리질문 대비 포인트

### "왜 전부 비대칭키로 암호화하지 않나요?"

성능 때문이다. 비대칭 연산은 대칭 대비 수백 배 이상 무거워서 모든
요청/응답 본문에 쓰면 서버 CPU가 병목이 된다. 반대로 전부 대칭키로만
하려면 최초에 키를 안전하게 나눠 가질 방법이 없다. 그래서 "비싼
비대칭은 연결당 한 번(신원 확인 + 키 합의), 싼 대칭은 모든 바이트에"
라는 분담이 나온다 — 각 방식이 못 푸는 문제를 상대가 풀어주는 구조다.

### "인증서는 정확히 무엇을 보장하나요? 없으면 어떤 공격이 가능한가요?"

인증서는 "이 공개키가 이 도메인 소유자의 것"임을 CA의 서명으로
보장한다. 이게 없으면 중간자(MITM)가 통신 사이에 끼어 클라이언트에게
자기 공개키를 내밀 수 있다 — 클라이언트는 공격자와 암호화 통신을
하면서 안전하다고 믿게 된다. 즉 **암호화(도청 방지)와 인증(상대 확인)은
별개의 보장**이고, 인증서가 후자를 담당한다. 브라우저가 신뢰하는
루트 CA 목록에서 시작해 중간 CA → 서버 인증서로 이어지는 서명 사슬을
검증하는 것이 그 메커니즘이다.

### "순방향 비밀성(forward secrecy)이 뭔가요?" (시니어 변별 포인트)

**서버의 개인키가 나중에 유출되더라도 과거에 도청해 저장해둔 트래픽을
복호화할 수 없다**는 성질이다. RSA 키 교환에서는 대칭키 재료를 서버
공개키로 암호화해 보냈으므로, 개인키가 유출되면 녹화해둔 과거 트래픽이
전부 열린다. ECDHE는 연결마다 임시 키 쌍을 만들고 쓰고 버리므로,
인증서 개인키는 서명(신원 증명)에만 쓰이고 대칭키 재료와 무관하다 —
개인키 유출이 과거로 소급되지 않는다. TLS 1.3이 RSA 키 교환을 아예
제거하고 ECDHE 계열만 남긴 이유이며, "키 유출"이라는 최악 시나리오의
피해 범위를 설계로 줄이는 사고방식의 예다.

### "TLS handshake 지연을 줄이려면 어떤 방법들이 있나요?"

층위별로: (1) **연결 재사용** — keep-alive·커넥션 풀로 handshake
자체를 반복하지 않는 것이 가장 크다. (2) **프로토콜** — TLS 1.3으로
1-RTT, 세션 재개로 재접속 비용 단축. HTTP/2는 한 연결에 요청을
다중화하므로 연결 수 자체를 줄인다. (3) **거리** — handshake는 왕복
지연에 비례하므로 CDN/엣지에서 TLS를 종료하면 사용자 가까운 곳에서
왕복이 끝난다. (4) **오프로드** — TLS 종료를 LB로 모아 앱 CPU 부담을
분리한다. "어느 비용(왕복 vs 연산)을 줄이는 방법인지" 구분해서 말하면
정리가 좋아 보인다.

### "HTTPS면 요청 내용이 전부 안 보이나요?" (가산점 포인트)

본문·헤더·경로는 암호화되지만 **다 숨는 것은 아니다**. 접속 대상
IP와 포트는 TCP 계층이라 보이고, 도메인명도 handshake의 SNI(어느
도메인의 인증서를 원하는지 알리는 확장) 평문 전송 때문에 노출될 수
있다 — 이를 암호화하는 ECH 같은 확장이 나온 배경이다. 또 트래픽의
크기·타이밍 패턴은 암호화와 무관하게 관찰 가능하다. "암호화의 보장
범위"를 정확히 아는 것도 보안 감각의 일부다.

## 한 줄 요약

TLS handshake는 비대칭키로 "상대가 진짜인지"(인증서 서명 검증)와
"대칭키를 안전하게 합의"(ECDHE)를 해결하는 비싼 개회식이고, 그 뒤의
모든 데이터는 싸고 빠른 대칭키로 암호화된다 — 비용이 연결 수립에
몰려 있으므로 연결 재사용(keep-alive)이 곧 TLS 성능 최적화이고,
인증서는 그 개회식의 관문이라 만료되면 전면 장애가 된다.
