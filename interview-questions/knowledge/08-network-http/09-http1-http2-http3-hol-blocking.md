# HTTP/1.1 → 2 → 3 — HOL blocking을 한 계단씩 아래로 밀어낸 진화

> 핵심 관전 포인트: **세 버전의 차이는 "HOL(head-of-line, 줄 맨 앞) blocking이 어느 계층에 남아 있는가"라는 한 축으로 관통된다. HTTP/1.1은 응답에 "이건 몇 번 요청의 답이다"라는 식별자가 없어서 요청 순서와 응답 순서가 같아야만 짝이 맞는다 — 그래서 한 연결에서 요청 하나를 끝내야 다음을 보낼 수 있고, 느린 응답 하나가 뒤를 전부 세우는 HTTP 계층 HOL이 생긴다. HTTP/2는 메시지를 **이진 프레임**으로 쪼개고 프레임마다 **스트림 ID**를 붙여 이 문제를 풀었다 — 길이와 라벨이 생겼으니 여러 요청의 조각을 뒤섞어 보내도 받는 쪽이 다시 조립할 수 있다(멀티플렉싱). 텍스트 기반이던 HTTP/1.1이 그렇게 못 했던 이유가 정확히 "경계와 라벨이 없어서"이므로, 이진 프레이밍은 멀티플렉싱의 부가 기능이 아니라 전제 조건이다. 그런데 줄이 사라진 게 아니라 한 계층 아래로 내려갔을 뿐이다 — 여전히 전송로는 하나의 TCP이고, TCP는 순서 보장 때문에 패킷 하나가 유실되면 무관한 스트림의 데이터까지 커널 버퍼에 붙들어 둔다(TCP 계층 HOL). HTTP/3은 그래서 전송 계층 자체를 UDP 기반 QUIC으로 갈아, 순서 보장의 단위를 커넥션이 아니라 **스트림**으로 다시 정의했다 — 한 스트림의 유실이 다른 스트림을 멈추지 않는다. 실무 판단으로 이어지면 "2가 항상 빠르다"는 틀렸다는 것까지 말할 수 있어야 한다 — 손실이 잦은 망에서는 연결 6개로 분산돼 있던 1.1이 오히려 나을 수 있고, 도메인 샤딩 같은 1.1 시대의 편법은 HTTP/2에서 역효과가 되므로 프로토콜을 올릴 때는 옛 편법을 걷어내는 것까지가 마이그레이션이다.**

---

## 0. 질문 + 의도

**질문**: "HTTP/1.1, HTTP/2, HTTP/3의 차이(HOL blocking 관점)를 설명해주세요."

**출제 의도**: 프로토콜 버전이 이미지 수십 장을 싣는 웹툰 페이지의 로딩 특성을 바꾼다. 기능 나열이 아니라 각 버전이 "무슨 문제를 풀었는지"의 흐름으로 이해하는 사람은, 자기 서비스에 새 프로토콜을 도입할지 판단할 수 있는 사람이다.

## 1. HOL blocking이란 — 그리고 줄이 두 계층에 있다는 것

### 1-1. 개념과 비유

**HOL(head-of-line) blocking은 줄의 맨 앞이 막히면 뒤에 선 전부가 자기 잘못 없이 기다리게 되는 현상**이다. 이름 그대로 "줄(line)의 맨 앞(head)이 막는다(blocking)"는 뜻이다.

마트 계산대를 떠올리면 된다. 맨 앞 손님이 지갑을 못 찾아 헤매면, 뒤에 선 사람은 물건이 하나뿐이어도 그 사람이 끝날 때까지 움직일 수 없다. **뒤에 선 사람의 처리 속도와는 아무 상관이 없다는 것**이 이 현상의 핵심이다. 병목은 자기 자신이 아니라 자기 앞에 있다.

이 현상이 생기는 조건은 둘이다. **처리 통로가 하나뿐이고, 처리 순서가 고정돼 있을 것.** 계산대가 여러 개면 다른 줄로 옮기면 되고, 순서를 바꿔도 된다면 뒷사람을 먼저 처리하면 된다. 앞으로 볼 세 버전의 진화는 전부 이 두 조건 중 하나를 무너뜨리는 시도다.

### 1-2. 전제 지식 — HTTP는 TCP 위에 얹힌 규약이다

버전 이야기를 하기 전에 계층 구조를 한 번 정리하자. HTTP는 **전송 계층 위에 얹힌 규약**이지 그 자체로 데이터를 나르는 것이 아니다.

```
[HTTP/1.1]              [HTTP/2]                [HTTP/3]
  요청·응답 텍스트         이진 프레임 + 스트림       이진 프레임 + 스트림
      │                      │                        │
      ▼                      ▼                        ▼
    TLS                    TLS                    ┌──────────┐
      │                      │                    │  QUIC    │ ← 신뢰성·순서·암호화를
      ▼                      ▼                    │ (TLS 1.3 │   여기서 직접 수행
    TCP                    TCP                    │  통합)   │
      │                      │                    └────┬─────┘
      ▼                      ▼                         ▼
     IP                     IP                        UDP
                                                       │
                                                       ▼
                                                      IP
```

이 그림이 중요한 이유는, **HTTP 계층에서 아무리 잘 설계해도 그 아래 층이 만드는 제약은 HTTP 계층에서 고칠 수 없다**는 사실을 보여주기 때문이다. HTTP/2가 못 푼 문제와 HTTP/3이 전송 계층을 통째로 바꾼 이유가 전부 여기서 나온다.

### 1-3. 줄은 두 계층에 있다

HTTP 통신에서 "줄"은 서로 다른 두 계층에 존재할 수 있고, **이 둘을 구분하는 것이 이 질문의 전부**다.

**HTTP 계층의 줄**은 한 연결 안에서 요청-응답이 순서대로만 오갈 수 있을 때 생긴다. 앞 요청의 응답이 다 와야 다음 요청을 보낼 수 있으니, 느린 응답 하나가 뒤 요청 전부를 세운다. 이것은 **HTTP 규약이 만든 제약**이므로 HTTP 규약을 바꿔서 고칠 수 있다.

**TCP 계층의 줄**은 그보다 아래에 있다. TCP는 "보낸 바이트가 보낸 순서 그대로 도착한다"를 계약한 프로토콜이라, 패킷 하나가 유실되면 **재전송이 도착할 때까지 그 뒤에 이미 도착해 있는 패킷들도 커널이 애플리케이션에 올려주지 않는다.** 위 계층에서 아무리 여러 요청을 섞어 보내도, 아래층 배관이 하나라면 배관 막힘은 전체 막힘이다. (이 메커니즘의 상세는 `03-tcp-vs-udp.md`의 2-3에서 같은 용어로 다룬다.)

```
[HTTP 계층 HOL]                       [TCP 계층 HOL]

요청1 ──▶ (느린 응답 처리 중...)        패킷 5 유실
요청2 ──▶ 대기 (보내지도 못함)           패킷 6,7,8은 도착했지만
요청3 ──▶ 대기                          커널 버퍼에 갇혀 애플리케이션에
                                        올라가지 못함
원인: HTTP 규약이 순서를 강제           원인: TCP가 순서를 계약
고치는 법: HTTP 규약을 바꾼다           고치는 법: 전송 프로토콜을 바꾼다
       → HTTP/2                              → HTTP/3
```

**세 버전의 차이는 이 두 줄을 각각 어떻게 없앴는가로 정확히 설명된다.**

## 2. 버전별 — 무엇을 풀었고 무엇이 남았나

### 2-1. HTTP/1.1 — 연결 재사용까지는 왔지만, 한 줄로만 통행

#### 무엇이 개선됐나

HTTP/1.0에서는 요청 하나를 처리하고 연결을 닫는 것이 기본이었다. 이미지 열 장이 있는 페이지는 TCP handshake를 열 번(HTTPS면 TLS까지 열 번) 치렀다는 뜻이다.

HTTP/1.1은 **keep-alive를 기본 동작으로** 만들어 이 낭비를 없앴다. 한 번 맺은 연결을 여러 요청이 이어서 쓴다. 이것만으로도 큰 개선이었다.

#### 그런데 왜 한 연결에 요청 하나씩인가

여기가 이 문서에서 가장 중요한 대목이다. **"HTTP/1.1은 한 연결에 한 요청씩만 처리한다"는 것을 규칙으로 외우면 안 되고, 왜 그럴 수밖에 없는지를 알아야 HTTP/2의 설계가 이해된다.**

HTTP/1.1의 메시지가 실제로 회선 위에 어떻게 흐르는지 보자. 텍스트다.

```
[클라이언트가 보내는 바이트]
GET /page.html HTTP/1.1\r\n
Host: example.com\r\n
\r\n                        ← 빈 줄 = 헤더 끝

[서버가 보내는 바이트]
HTTP/1.1 200 OK\r\n
Content-Type: text/html\r\n
Content-Length: 1024\r\n
\r\n
<html>....(1024바이트)....</html>
```

이 바이트들을 아무리 뜯어봐도 **"이 응답은 몇 번 요청에 대한 답이다"라는 정보가 어디에도 없다.** 요청 쪽에도 "나는 3번 요청이다"라는 자리가 없다.

그러면 클라이언트는 응답과 요청을 어떻게 짝지을까. **순서로만 짝짓는다.** 첫 번째 응답은 첫 번째 요청의 답이고, 두 번째 응답은 두 번째 요청의 답이다. 이것 말고 다른 방법이 없다.

여기서 두 가지 제약이 동시에 따라 나온다.

**첫째, 응답 순서를 바꿀 수 없다.** 3번 요청이 먼저 처리됐다고 3번 응답을 먼저 보내면 클라이언트가 그것을 1번 응답으로 읽는다. 서버는 빨리 끝난 응답을 손에 쥐고도 앞 순서가 끝날 때까지 기다려야 한다.

**둘째, 메시지를 중간에 끊고 다른 메시지를 끼워 넣을 수 없다.** 본문을 1024바이트 보내야 하는데 500바이트만 보내고 다른 응답 조각을 끼워 넣으면, 파서는 그 조각을 **첫 응답의 본문 나머지로 읽는다.** `Content-Length: 1024`를 채울 때까지 오는 바이트는 전부 본문이기 때문이다. 파서 입장에서 그것을 구분할 방법 자체가 없다.

**정리하면, HTTP/1.1의 텍스트 메시지에는 "라벨"도 "조각의 경계"도 없다.** 그래서 한 연결에는 한 번에 하나의 메시지만 흐를 수 있다.

#### 파이프라이닝이 왜 실패했나

스펙에는 **파이프라이닝(pipelining)**이 있었다. 응답을 기다리지 않고 요청을 연달아 보내는 기능이다.

```
요청1 ──▶
요청2 ──▶   (응답을 기다리지 않고 연달아 보냄)
요청3 ──▶
        ◀── 응답1
        ◀── 응답2      ← 순서는 여전히 고정
        ◀── 응답3
```

요청 전송의 왕복은 줄었지만 **응답은 여전히 요청 순서대로 와야 한다** — 위에서 본 이유 때문이다. 그래서 응답1이 느리면 응답2, 3은 준비돼 있어도 나갈 수 없다. **HOL이 그대로 남았다.** 여기에 중간 프록시나 서버가 파이프라인 요청을 제대로 처리하지 못하는 호환성 문제까지 겹쳐, 브라우저들은 이 기능을 사실상 꺼버렸다.

#### 그래서 편법의 시대가 열렸다

프로토콜이 병렬 처리를 못 하니, 병렬성을 **연결 개수로** 만들었다. 브라우저는 **같은 호스트에 대해 연결을 여러 개(보통 6개) 동시에 열어** 요청을 나눠 싣는다.

왜 하필 6개쯤에서 멈출까. 무한정 늘리면 서버 부담이 커지고, **각 연결이 slow start를 따로 치르기 때문**이다(`03-tcp-vs-udp.md` 1-5). 연결마다 혼잡 윈도우가 독립적이므로 연결을 쪼갤수록 각 연결은 느린 상태에서 시작한다. 그래서 늘릴수록 이득이 줄어드는 지점이 생긴다.

6개로도 부족하니 서비스들은 프로토콜을 **속이는** 방향으로 갔다.

**도메인 샤딩(domain sharding)**은 같은 서버의 이미지를 `img1.example.com`, `img2.example.com`처럼 여러 도메인으로 나눠 서빙하는 기법이다. 연결 수 제한이 **호스트 단위**로 걸리므로, 도메인을 셋으로 쪼개면 6개가 18개가 된다. "shard(조각)"라는 이름은 하나의 자원을 여러 조각으로 나눈다는 뜻에서 왔다.

**이미지 스프라이트**는 작은 아이콘 수십 개를 큰 이미지 한 장으로 합치고 CSS로 잘라 쓰는 기법이고, **파일 병합**은 JS·CSS 파일 여러 개를 하나로 합치는 것이며, **인라이닝**은 작은 이미지를 `data:` URL로 HTML에 직접 박아 넣는 것이다. 셋 다 목적이 같다 — **요청 개수 자체를 줄이는 것.** 요청 하나가 비싸니까 요청을 줄이는 것이 최적화였던 시대다.

**이 편법들이 왜 존재했는지를 기억해야 한다.** 2-2 끝에서 이것들이 HTTP/2에서 왜 역효과가 되는지가 여기서 설명되기 때문이다.

### 2-2. HTTP/2 — 이진 프레이밍이 먼저, 멀티플렉싱은 그 결과

#### 세 용어를 먼저 정의한다

HTTP/2를 설명할 때 프레임·스트림·멀티플렉싱을 정의 없이 쓰면 아무것도 전달되지 않는다. 하나씩 짚자.

**프레임(frame)**은 HTTP/2가 회선 위에서 주고받는 **최소 단위**다. 고정된 형식의 이진 덩어리이고, 맨 앞 9바이트가 헤더 역할을 한다.

```
HTTP/2 프레임
┌──────────────┬──────┬───────┬─────────────────┬──────────────────┐
│  길이 (3B)    │타입(1B)│플래그(1B)│  스트림 ID (4B)  │   페이로드 (가변)  │
└──────────────┴──────┴───────┴─────────────────┴──────────────────┘
       │           │                    │
       │           │                    └─ 이 조각이 어느 요청의 것인지 (라벨)
       │           └─ HEADERS(헤더) / DATA(본문) / SETTINGS(설정) 등
       └─ 페이로드가 몇 바이트인지 (경계)
```

이름이 "프레임(틀, 액자)"인 이유는, 가변 길이 데이터에 앞뒤 경계를 씌워 **"여기부터 여기까지가 한 조각"임을 정하기** 때문이다. `03-tcp-vs-udp.md` 1-6에서 본 프레이밍과 정확히 같은 개념이다.

**스트림(stream)**은 하나의 연결 안에서 요청-응답 한 쌍이 오가는 **논리적 통로**다. 물리적으로 회선이 여러 개인 것이 아니라, 번호(스트림 ID)로 구분되는 가상의 통로다. 요청 하나가 스트림 하나를 쓰고, 그 요청의 헤더 프레임과 본문 프레임들이 전부 같은 스트림 ID를 달고 다닌다.

**멀티플렉싱(multiplexing, 다중화)**은 하나의 물리적 통로에 여러 논리적 통로를 번갈아 실어 보내는 기법이다. "multi(여럿) + plex(겹치다)", 즉 여럿을 겹쳐 보낸다는 뜻이다.

비유하면 이렇다. 한 차선짜리 도로에 화물을 보내야 하는데, **모든 상자에 목적지 라벨(스트림 ID)과 크기 표시(길이)를 붙여두면** 여러 목적지의 상자를 뒤섞어 실어 보내도 받는 쪽에서 라벨별로 다시 모을 수 있다. 라벨이 없으면 순서대로 한 목적지씩 보내는 수밖에 없다 — 그것이 HTTP/1.1이었다.

#### 왜 텍스트로는 멀티플렉싱이 불가능한가

이제 2-1에서 본 HTTP/1.1의 두 제약을 다시 보자. **"라벨이 없다"와 "조각의 경계가 없다."**

이진 프레이밍이 하는 일이 정확히 그 둘을 채우는 것이다. **모든 조각에 길이를 붙여 경계를 만들고, 스트림 ID를 붙여 라벨을 만든다.** 이 둘이 생기는 순간 멀티플렉싱이 가능해진다 — 받는 쪽이 "이 조각은 여기까지고, 3번 요청의 것"이라고 판정할 수 있으니 뒤섞어 보내도 조립이 된다.

**그래서 이진 프레이밍은 HTTP/2의 여러 기능 중 하나가 아니라 멀티플렉싱의 전제 조건이다.** 이 인과를 뒤집어 말하는 사람이 많은데("HTTP/2는 이진이고 멀티플렉싱도 된다"), 정확히는 **"멀티플렉싱을 하려면 이진 프레이밍이 필요했다"**가 맞다.

회선 위의 모습을 비교하면 차이가 한눈에 보인다.

```
[HTTP/1.1 — 한 연결의 바이트 흐름]
GET /a.css HTTP/1.1\r\nHost:...\r\n\r\n
HTTP/1.1 200 OK\r\nContent-Length: 5000\r\n\r\n<5000바이트 전부>
GET /b.js HTTP/1.1\r\n...                     ← a.css가 완전히 끝나야 b를 시작
HTTP/1.1 200 OK\r\n...

[HTTP/2 — 한 연결의 프레임 흐름]
[HEADERS  stream=1]   ← /a.css 요청
[HEADERS  stream=3]   ← /b.js 요청   (a의 응답을 기다리지 않고 바로 보냄)
[HEADERS  stream=5]   ← /c.png 요청
[DATA     stream=3]   ← b.js 응답 조각      (3번이 먼저 준비됐으면 먼저 나간다)
[DATA     stream=1]   ← a.css 응답 조각
[DATA     stream=3]   ← b.js 응답 조각
[DATA     stream=5]   ← c.png 응답 조각
[DATA     stream=1]   ← a.css 응답 조각 (끝)
                        ↑
              조각들이 뒤섞여 있어도 스트림 ID로 다시 모을 수 있다
```

이 그림에서 두 가지를 더 읽을 수 있다. **응답 순서가 요청 순서와 달라도 된다**는 것(3번이 1번보다 먼저 나갔다), 그리고 **느린 응답이 다른 응답을 막지 않는다**는 것이다. 1번이 오래 걸려도 3번과 5번의 프레임은 그 사이사이로 계속 흐른다. **HTTP 계층의 HOL이 사라졌다.**

참고로 스트림 ID는 클라이언트가 시작한 스트림에 홀수, 서버가 시작한 스트림에 짝수를 쓴다. 양쪽이 동시에 새 스트림을 만들어도 번호가 충돌하지 않게 하기 위한 규칙이다. 그리고 한 연결에서 동시에 열 수 있는 스트림 수는 무제한이 아니라 서버가 SETTINGS 프레임으로 알려주는 상한(흔히 100 전후)이 있다.

#### 헤더 압축(HPACK) — 요청이 싸지니 새 문제가 보였다

멀티플렉싱으로 요청을 많이 보낼 수 있게 되자 다른 낭비가 눈에 띄었다. **헤더가 매번 통째로 반복된다는 것**이다.

같은 페이지의 리소스 50개를 요청하면 `Cookie`, `User-Agent`, `Accept`, `Referer` 같은 헤더가 50번 반복된다. 쿠키가 큰 서비스면 요청 하나당 헤더만 1KB가 넘는 경우도 흔하고, 그러면 50번 반복에 50KB가 헤더로만 나간다. **본문보다 헤더가 큰 요청들이 줄줄이 나가는 것**이다.

**HPACK**은 이 반복을 압축한다. 원리는 두 갈래다. 자주 쓰이는 헤더 이름과 값 조합을 미리 번호로 정해둔 **정적 테이블**이 있어서 `:method: GET` 같은 것은 번호 하나로 보낼 수 있고, 이 연결에서 실제로 오간 헤더를 양쪽이 같은 순서로 쌓아두는 **동적 테이블**이 있어서 두 번째 요청부터는 "아까 그 쿠키"를 인덱스 번호로만 가리킬 수 있다.

동적 테이블이 **연결 단위**라는 사실을 기억해 두자. 2-2 끝의 도메인 샤딩 역효과에서 다시 나온다.

#### 서버 푸시 — 스펙에 있었지만 사실상 폐기됐다

**서버 푸시(server push)**는 클라이언트가 요청하지 않은 리소스를 서버가 미리 밀어 보내는 기능이었다. HTML을 요청받은 서버가 "어차피 이 페이지는 style.css도 필요할 텐데"라며 응답과 함께 CSS를 보내는 식이다. 왕복을 한 번 아끼자는 발상이었다.

**그런데 실무에서 거의 쓰이지 않았고, 주요 브라우저가 지원을 제거했다.** 이유를 아는 것이 이 항목의 가치다.

가장 큰 문제는 **서버가 클라이언트의 캐시 상태를 모른다**는 것이다. 사용자가 이미 `style.css`를 캐시에 갖고 있어도 서버는 그 사실을 알 수 없으므로 매번 밀어 보낸다. 절약하려던 왕복 하나 대신 **불필요한 대역폭을 반복해서 낭비**하게 되고, 느린 모바일망에서는 그 낭비가 정작 필요한 리소스의 전송을 밀어내 오히려 느려진다.

두 번째 문제는 **우선순위 판단이 서버 쪽에 있다는 것**이다. 지금 화면에 무엇이 먼저 필요한지는 브라우저가 훨씬 잘 안다. 서버가 밀어 보낸 리소스가 브라우저가 급히 필요로 하는 리소스의 대역폭을 잡아먹는 상황이 생긴다.

세 번째는 **구현과 운영 복잡도 대비 실측 이득이 작았다는 것**이다.

대체 수단이 자리를 잡았다는 것까지 말하면 좋다. HTML 안의 `<link rel="preload">`는 **브라우저가 자기 캐시를 확인한 뒤 필요할 때만 받아온다**는 점에서 푸시의 낭비를 피한다. 그리고 `103 Early Hints`는 서버가 최종 응답을 만들기 전에 "이 리소스들을 미리 받아두라"는 힌트만 먼저 보내는 방식이라, **데이터를 밀어 보내지 않고 힌트만 준다**는 점에서 캐시 상태 문제를 클라이언트에게 되돌려 준다. **"밀어 보내기" 대신 "미리 알려주기"로 방향이 바뀐 것**이 이 이야기의 결론이다.

#### 그런데 줄이 한 계층 아래로 내려갔을 뿐이다

HTTP 계층의 HOL은 사라졌지만, 여전히 전송로는 **하나의 TCP 연결**이다.

TCP 입장에서 이 연결에 흐르는 것은 스트림 여러 개가 아니라 **그냥 하나의 바이트 물줄기**다. TCP는 HTTP/2의 프레임도 스트림 ID도 모른다. 그저 "보낸 순서대로 올려준다"는 자기 계약을 지킬 뿐이다.

그래서 패킷 하나가 유실되면, **그 패킷과 아무 상관없는 스트림의 데이터가 이미 도착해 있어도** TCP가 순서 보장을 위해 전부 붙들고 있는다. 애플리케이션(브라우저)은 그 데이터를 받지 못한다.

**이것이 TCP 계층 HOL blocking이고, HTTP/2가 구조적으로 풀 수 없는 문제다.** 스트림을 아무리 잘 나눠도 아래층 배관이 하나이기 때문이다.

#### 도메인 샤딩이 HTTP/2에서 역효과인 이유

2-1에서 본 편법들이 여기서 어떻게 되는지 보자. **도메인 샤딩은 HTTP/2에서 이득이 없는 정도가 아니라 손해다.** 이유가 셋이다.

**첫째, 도메인마다 연결 세트가 통째로 추가된다.** 도메인이 다르면 DNS 조회 + TCP handshake + TLS handshake를 처음부터 다시 해야 한다(`01-url-to-page-dns-tcp-tls-http.md`의 관문 [2][3][4] 전체). 멀티플렉싱 덕분에 연결 하나로 충분한데 굳이 연결을 늘려 이 비용을 자초하는 셈이다.

**둘째, 각 연결이 slow start를 따로 치른다.** 혼잡 윈도우는 연결마다 독립이므로, 연결을 셋으로 쪼개면 세 연결이 각각 작은 속도에서 시작한다. 한 연결에 모으면 그 연결의 속도가 빠르게 올라가 전체가 이득이다.

**셋째, 연결 단위로 유지되는 최적화 컨텍스트가 흩어진다.** HPACK 동적 테이블이 연결마다 따로이므로 연결을 쪼개면 같은 쿠키를 연결 수만큼 반복해서 압축 사전에 쌓아야 한다. 스트림 우선순위도 한 연결 안에서만 비교되므로, 연결이 쪼개지면 브라우저가 "이 이미지보다 저 CSS가 급하다"는 판단을 프로토콜에 전달할 방법이 없어진다.

같은 논리로 **파일 병합과 이미지 스프라이트도 재검토 대상**이 된다. 요청이 싸졌으니 굳이 합칠 이유가 줄었고, 오히려 합쳐두면 그중 한 조각만 바뀌어도 캐시 전체가 무효화되는 손해가 생긴다. **다만 "무조건 쪼개라"는 것은 아니다** — 파일이 지나치게 잘게 쪼개지면 요청당 오버헤드와 압축 효율 저하가 다시 문제가 되므로, 실측으로 균형점을 찾는 일이다.

### 2-3. HTTP/3 — 전송 계층을 갈아 TCP의 줄까지 없앰

#### 왜 TCP를 고치지 않았나

TCP 계층 HOL을 없애려면 TCP를 고쳐야 하는데, 이것이 사실상 불가능하다.

TCP는 **OS 커널에 구현돼 있다.** 고치려면 전 세계의 윈도우·리눅스·안드로이드·iOS를 다 업데이트해야 하고, 그것만으로도 부족하다. 경로 중간의 **NAT 공유기, 방화벽, 통신사 장비**들이 TCP 헤더를 들여다보고 자기 방식대로 해석하거나 변형하는데, 이 장비들은 자기가 모르는 형태의 TCP를 흔히 차단하거나 망가뜨린다.

**프로토콜이 중간 장비들 때문에 굳어져 바꿀 수 없게 되는 이 현상을 프로토콜 경직화(ossification, 골화)라고 부른다.** 뼈처럼 굳었다는 뜻이다.

#### QUIC — UDP 위에 사용자 공간으로 구현한 전송 계층

그래서 HTTP/3은 다른 길을 택했다. **UDP 위에 QUIC이라는 새 전송 프로토콜을 애플리케이션(사용자 공간)에 구현**하는 것이다.

UDP를 고른 이유는 성능이 아니라 **통과 가능성**이다. UDP는 DNS 등에 쓰이므로 어디서나 통과되는 최소한의 배관이고, 중간 장비들은 UDP 페이로드 안을 들여다보지 않는다. 그 안에 무엇을 넣든 자유롭다는 뜻이다.

그리고 사용자 공간에 구현했으므로 **커널 교체 없이 애플리케이션 배포만으로 전송 계층을 진화시킬 수 있다.** 브라우저와 서버 소프트웨어를 업데이트하면 끝이다. QUIC이 헤더 대부분까지 암호화해 중간 장비가 들여다보고 간섭할 여지를 없앤 것도, 다시 경직화되는 것을 막으려는 같은 맥락의 설계다.

#### QUIC이 준 것 세 가지

**스트림별 독립 전달**이 핵심이다. QUIC은 **순서 보장의 단위를 커넥션이 아니라 스트림으로 다시 정의했다.** 각 스트림이 자기 오프셋(어디까지 받았는가)을 따로 관리하므로, 한 스트림의 패킷이 유실되면 **그 스트림만 기다리고 다른 스트림은 계속 애플리케이션에 전달된다.** TCP 계층 HOL이 사라진다. 물론 유실된 그 스트림 자신은 재전송을 기다려야 한다 — 이건 어떤 프로토콜로도 피할 수 없다.

**핸드셰이크 통합**이 두 번째다. 기존에는 TCP 3-way handshake(1 RTT)를 끝내고 그 위에서 TLS handshake(1~2 RTT)를 따로 했는데, QUIC은 **연결 수립과 암호 협상을 하나로 합쳐** 첫 연결을 1 RTT로 끝낸다. 그리고 전에 붙어본 서버라면 **0-RTT** — 핸드셰이크가 끝나기 전에 데이터를 함께 실어 보내는 것 — 까지 가능하다. 다만 0-RTT 데이터는 재전송 공격에 노출될 수 있어 멱등한 요청에만 쓰는 것이 원칙이다.

**커넥션 마이그레이션**이 세 번째다. TCP 연결은 4-튜플(출발지/목적지 IP와 포트)로 식별되므로 **IP가 바뀌면 연결이 끊긴다.** 지하철에서 Wi-Fi가 끊겨 LTE로 넘어가면 진행 중이던 다운로드가 죽는 것이 이 때문이다. QUIC은 연결을 IP가 아니라 **커넥션 ID**라는 별도 식별자로 구분하므로, IP가 바뀌어도 같은 연결로 이어서 통신할 수 있다. **이동 중인 모바일 사용자에게 특히 값이 크다.**

헤더 압축은 HPACK 대신 **QPACK**을 쓴다. HPACK의 동적 테이블은 양쪽이 같은 순서로 갱신돼야 해석이 맞는데, 이 순서 의존성이 스트림 독립성과 충돌한다 — 헤더 테이블 갱신 정보가 담긴 스트림이 늦게 도착하면 다른 스트림의 헤더를 해석할 수 없어 결국 막히기 때문이다. QPACK은 테이블 갱신을 별도 스트림으로 분리하고 순서에 덜 의존하도록 설계해 이 문제를 피한다. **QUIC의 스트림 독립성을 살리려면 헤더 압축까지 그에 맞게 다시 설계해야 했다는 점**이 재미있는 지점이다.

### 2-4. 세 버전을 나란히 — 패킷 하나가 유실되면 무슨 일이 일어나는가

지금까지의 이야기를 하나의 상황으로 압축해 보자. **CSS, JS, 이미지 세 리소스를 동시에 받는 중에 패킷 하나가 유실됐다.** 각 버전에서 무슨 일이 일어나는가.

```
─────────────────────────────────────────────────────────────────
HTTP/1.1  (연결 6개에 요청을 나눠 실음)

  연결 A: [CSS 요청 → 응답 전송 중] ── 패킷 유실 ✗
          → CSS만 재전송을 기다린다. 이 연결의 뒤 요청도 함께 멈춤.
  연결 B: [JS  요청 → 응답 전송 중] ── 정상 진행 ✓
  연결 C: [IMG 요청 → 응답 전송 중] ── 정상 진행 ✓

  결과: 유실의 피해가 연결 A로 격리된다.
        대신 평상시에 연결 6개를 유지하는 비용(handshake, slow start)을
        계속 내고 있고, 리소스가 6개를 넘으면 HTTP 계층 HOL로 줄을 선다.
─────────────────────────────────────────────────────────────────
HTTP/2  (연결 1개에 스트림 3개)

  TCP 연결 1개
    ├─ stream 1 (CSS)  [DATA] ── 패킷 유실 ✗
    ├─ stream 3 (JS )  [DATA] ── 도착했지만 커널 버퍼에 갇힘 (대기)
    └─ stream 5 (IMG)  [DATA] ── 도착했지만 커널 버퍼에 갇힘 (대기)

  결과: TCP가 순서 보장을 위해 전부 붙들어, 무관한 JS와 이미지까지 멈춘다.
        ★ 손실이 잦은 망에서는 HTTP/1.1보다 나빠질 수 있는 지점이 정확히 여기다.
─────────────────────────────────────────────────────────────────
HTTP/3  (QUIC 연결 1개에 스트림 3개, 스트림별 독립 순서 보장)

  QUIC 연결 1개
    ├─ stream 1 (CSS)  ── 패킷 유실 ✗ → 이 스트림만 재전송 대기
    ├─ stream 3 (JS )  ── 애플리케이션에 그대로 전달 ✓
    └─ stream 5 (IMG)  ── 애플리케이션에 그대로 전달 ✓

  결과: 피해가 유실이 난 스트림 하나로 격리되면서,
        연결은 하나만 유지해 handshake·slow start 비용도 아낀다.
        → HTTP/1.1의 "격리"와 HTTP/2의 "연결 절약"을 둘 다 가진 셈.
─────────────────────────────────────────────────────────────────
```

이 세 그림이 **"각 버전은 앞 버전이 못 푼 줄막힘을 한 계층 아래로 내려가 푼 역사"**라는 문장의 실체다.

### 2-5. 한눈 비교

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 계층 | TCP | TCP | QUIC (UDP 기반) |
| 메시지 형식 | 텍스트 | 이진 프레임 | 이진 프레임 |
| 한 연결의 동시 요청 | 1개 (순차) | 다수 (멀티플렉싱) | 다수 (멀티플렉싱) |
| HTTP 계층 HOL | 있음 | 없음 | 없음 |
| TCP(전송) 계층 HOL | 있음 | **있음** | 없음 (스트림별 독립 순서 보장) |
| 헤더 압축 | 없음 | HPACK | QPACK |
| TLS 핸드셰이크 | TCP 위에 별도 | TCP 위에 별도 | 전송 계층에 통합 (1-RTT, 재접속 0-RTT) |
| 연결 식별 | 4-튜플 (IP 바뀌면 끊김) | 4-튜플 | 커넥션 ID (IP 바뀌어도 유지) |
| 병렬성 확보 수단 | 연결 여러 개 + 도메인 샤딩 | 스트림 (샤딩은 역효과) | 스트림 |

## 3. 실무 맥락 — 웹툰 페이지, 프로토콜 협상, 도입 판단

### 3-1. 이미지 수십 장짜리 페이지에서의 체감 차이

웹툰 뷰어처럼 이미지 수십 장을 한 화면에 싣는 페이지가 세 버전의 차이를 가장 극명하게 보여준다.

**HTTP/1.1**에서는 연결 6개에 이미지 수십 장이 줄을 선다. 개발자도구 워터폴 차트를 보면 **계단식 대기**가 보인다 — 앞 이미지가 끝나야 뒤 이미지가 시작하는 모양이다. 이미지 하나가 유난히 느리면 같은 연결에 배정된 뒤 이미지들이 통째로 늦는다.

**HTTP/2**에서는 연결 하나에 전부 태워 동시에 흘러온다. 워터폴에서 계단이 사라지고 막대들이 나란히 시작한다. **다만 여기에 반전이 있다.** 패킷 손실이 잦은 열악한 모바일망에서는 유실 한 번이 모든 이미지 스트림을 동시에 세우므로, 연결 6개로 위험이 분산돼 있던 1.1보다 **오히려 나빠질 수 있다.** 2-4의 그림이 그대로 현실이 되는 것이다. "2가 항상 빠르다"가 틀린 이유가 여기 있다.

**HTTP/3**에서는 유실이 해당 스트림만 세우므로 손실 많은 무선망에서 강하고, 지하철에서 Wi-Fi와 LTE가 전환돼도 커넥션 마이그레이션 덕분에 연결이 유지된다. **모바일 비중이 높은 서비스일수록 이득이 크다**는 결론이 여기서 나온다.

### 3-2. 프로토콜 협상 — 브라우저와 서버는 버전을 어떻게 합의하나

같은 URL에 대해 브라우저가 h1로 붙을지 h2로 붙을지 h3로 붙을지는 어떻게 정해질까. **버전마다 협상 방식이 다르고, 이걸 알아야 "왜 우리 서비스는 h2로 안 붙지"를 진단할 수 있다.**

#### h1 vs h2 — TLS handshake 안에서 ALPN으로

**ALPN(Application-Layer Protocol Negotiation, 애플리케이션 계층 프로토콜 협상)**은 TLS handshake 안에서 "이 암호 채널 위에 어떤 프로토콜을 얹을지"를 함께 정하는 확장이다.

**왜 TLS 안에서 하는가**가 중요한 포인트다. 별도의 협상 절차를 두면 왕복이 하나 더 늘어난다. 어차피 TLS handshake를 하고 있으니 그 메시지에 목록을 얹어 보내면 **추가 왕복 없이** 협상이 끝난다.

```
클라이언트                                        서버
    │ ── ClientHello ─────────────────────────▶   │
    │    ALPN: ["h2", "http/1.1"]                 │  "나는 이 둘을 할 줄 안다,
    │                                             │   h2를 더 선호한다"
    │                                             │
    │ ◀── ServerHello ────────────────────────    │
    │    ALPN: "h2"                               │  "그럼 h2로 하자"
    │                                             │
    └─ TLS handshake 완료 시점에 버전이 이미 정해져 있다 ─┘
```

여기서 실무 함의가 하나 나온다. **브라우저는 TLS 없는 평문 HTTP/2(h2c)를 지원하지 않는다.** 그래서 "HTTP/2를 켰는데 브라우저가 h1로 붙는다"는 문제의 흔한 원인이 **TLS 종단 지점의 ALPN 설정 누락**이다. 로드밸런서에서 TLS를 종단한다면 HTTP/2를 켜야 할 곳은 애플리케이션 서버가 아니라 **그 로드밸런서**다.

#### h3 — ALPN으로는 안 되고, Alt-Svc로 광고한다

HTTP/3은 ALPN으로 협상할 수 없다. **전송 계층 자체가 다르기 때문**이다. 브라우저가 TCP로 연결해 TLS handshake를 하는 시점에는 이미 TCP를 쓰기로 결정한 뒤라서, 거기서 "사실 UDP로 하자"고 할 수 없다.

그래서 **`Alt-Svc`(Alternative Services, 대체 서비스) 응답 헤더**로 광고한다. "이 서비스는 다른 방법으로도 접속할 수 있다"고 알려주는 헤더다.

```
[1회차 접속]
  브라우저 ── TCP + TLS(ALPN: h2) ──▶ 서버
  브라우저 ◀── 200 OK ───────────────  서버
             Alt-Svc: h3=":443"; ma=86400
                       │        │
                       │        └─ 이 정보를 86400초(24시간) 기억하라
                       └─ "443 포트에서 h3로도 받는다"

[2회차 접속부터]
  브라우저가 UDP 443으로 QUIC 연결을 시도한다.
  성공하면 h3로, UDP가 막혀 실패하면 조용히 TCP(h2)로 폴백한다.
```

**즉 h3 도입은 "전환"이 아니라 "가능한 클라이언트에게만 추가로 제공"이다.** h1/h2 경로는 항상 살아 있어야 한다.

#### 실제로 무엇으로 붙었는지 확인하는 법

```bash
# ALPN 협상 결과를 직접 확인한다 — 서버가 h2를 제안받고 무엇을 골랐는지
openssl s_client -alpn h2,http/1.1 -connect example.com:443 -servername example.com </dev/null 2>/dev/null \
  | grep -i 'ALPN protocol'
# 출력 예: ALPN protocol: h2      ← 서버가 h2를 선택함
#          (아무것도 안 나오면 서버가 ALPN을 지원하지 않는다는 뜻 → h1로 붙게 된다)

# curl로 실제 사용된 버전 확인 — 응답 첫 줄에 프로토콜이 찍힌다
curl -sI --http2 https://example.com | head -1
# HTTP/2 200          ← h2로 붙음
# HTTP/1.1 200 OK     ← h2 협상 실패, h1로 폴백됨

# Alt-Svc 헤더가 실제로 나가는지 확인 — h3 광고가 되고 있는가
curl -sI https://example.com | grep -i alt-svc

# HTTP/3으로 직접 붙어본다 (HTTP/3 지원이 포함된 curl 빌드가 필요하다)
curl -sI --http3 https://example.com | head -1
```

브라우저 개발자도구에서도 확인할 수 있다. Network 탭에서 컬럼 헤더를 우클릭해 **Protocol** 컬럼을 켜면 요청마다 `http/1.1`, `h2`, `h3`가 표시된다. **도입 후 실제로 몇 퍼센트가 h3로 붙는지를 이 값으로 집계하는 것이 3-5의 검증 방법이다.**

### 3-3. 어디서 켜는가 — 최전방에서 종단하고 뒤는 그대로

HTTP/2·3은 보통 **CDN이나 로드밸런서 같은 최전방에서 종단(terminate)하고, 그 뒤 내부 구간(LB → 앱 서버)은 HTTP/1.1을 유지**한다.

이 구성이 표준인 이유를 아는 것이 중요하다. **HTTP/2·3이 푸는 것은 사용자 구간의 문제**다 — 높은 RTT, 패킷 손실, 한 페이지에 수십 개씩 딸리는 동시 리소스. 반면 로드밸런서와 애플리케이션 서버 사이는 같은 데이터센터 안이라 RTT가 1ms 미만이고 손실이 거의 없으며, 커넥션 풀로 이미 연결을 재사용하고 있다. **이 구간에는 HTTP/2가 풀 문제가 애초에 없다.**

```
[사용자] ══ HTTP/3 또는 HTTP/2 (높은 RTT, 손실 있음) ══▶ [CDN / LB]
                                                            │
                                          HTTP/1.1 keep-alive (RTT < 1ms)
                                                            ▼
                                                        [앱 서버]
```

Nginx 설정으로 보면 이렇다.

```nginx
server {
    listen 443 ssl;
    listen 443 quic reuseport;   # HTTP/3(QUIC)용 UDP 리스너.
                                 # HTTP/3 모듈이 포함된 빌드에서만 동작한다.
                                 # reuseport는 워커 프로세스들이 같은 포트를 나눠 듣게 해
                                 # UDP 패킷 분배를 커널에 맡기는 옵션이다.

    http2 on;                    # HTTP/2 활성화.
                                 # nginx 1.25 계열부터 이 지시자 방식으로 바뀌었고,
                                 # 그 이전 버전에서는 `listen 443 ssl http2;`처럼
                                 # listen 파라미터로 켠다. 버전에 맞춰 쓸 것.

    ssl_certificate     /etc/ssl/example.com.crt;
    ssl_certificate_key /etc/ssl/example.com.key;
    ssl_protocols       TLSv1.2 TLSv1.3;   # h3(QUIC)는 TLS 1.3을 전제로 한다

    # "이 사이트는 h3로도 접속할 수 있다"는 광고.
    # 이 헤더가 없으면 브라우저는 UDP를 시도조차 하지 않으므로,
    # quic 리스너만 열어두고 이 줄을 빠뜨리면 h3 트래픽이 0으로 남는다.
    add_header Alt-Svc 'h3=":443"; ma=86400' always;

    location / {
        proxy_pass http://app_upstream;

        # 내부 구간은 HTTP/1.1 keep-alive면 충분하다.
        # 이 두 줄이 없으면 매 요청마다 업스트림 연결을 새로 맺어
        # 내부 구간에서 handshake와 TIME_WAIT 비용이 발생한다.
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}

upstream app_upstream {
    server 10.0.1.10:8080;
    keepalive 64;   # 업스트림 연결을 유지하는 풀 크기.
                    # proxy_http_version 1.1과 짝을 이뤄야 의미가 있다.
}
```

애플리케이션 서버에서 직접 HTTP/2를 종단해야 하는 경우(로드밸런서 없이 노출하거나, LB가 TCP 패스스루인 경우)에는 Spring Boot에서 이렇게 켠다.

```yaml
server:
  # HTTP/2 활성화. 다만 이것만으로 브라우저가 h2로 붙지는 않는다 —
  # 브라우저는 TLS 없는 h2(h2c)를 지원하지 않으므로 SSL이 함께 켜져 있어야
  # ALPN 협상이 일어나 h2로 붙는다.
  http2:
    enabled: true

  ssl:
    enabled: true
    key-store: classpath:keystore.p12
    key-store-type: PKCS12
    key-store-password: ${KEYSTORE_PASSWORD}
```

**설정을 켠 뒤에는 반드시 3-2의 확인 명령으로 실제 협상 결과를 검증해야 한다.** "설정은 넣었는데 여전히 h1로 붙고 있었다"는 상황이 흔한데, 대개 원인은 TLS 종단이 앞단에 있어서 그쪽이 h1으로 협상하고 있었던 것이다.

### 3-4. 마이그레이션은 옛 편법을 걷어내는 것까지다

2-2에서 본 대로 **HTTP/1.1 시대의 최적화 편법은 HTTP/2에서 역효과**다. 프로토콜만 올리고 이것들을 그대로 두면 이득의 상당 부분이 상쇄된다.

**도메인 샤딩을 되돌린다.** 쪼개둔 이미지 도메인을 하나로 합친다. 연결 하나에 모여야 slow start와 헤더 압축 컨텍스트, 우선순위가 제 값을 한다.

**파일 병합과 스프라이트를 재검토한다.** 요청이 싸졌으므로 합칠 이유가 줄었고, 오히려 합쳐두면 한 조각의 변경이 전체 캐시를 무효화한다. 다만 무한정 쪼개는 것도 답이 아니므로 실측으로 균형점을 찾는다.

**인라이닝을 되돌린다.** `data:` URL로 HTML에 박아 넣은 리소스는 **개별 캐싱이 안 되고 압축 효율도 떨어진다.** 요청 하나를 아끼려고 HTML 크기를 키우는 거래였는데, 요청이 싸진 지금은 손해 쪽이 크다.

**프로토콜을 올릴 때는 옛 편법을 걷어내는 것까지가 마이그레이션이다.** 이 문장을 말할 수 있으면 "기능을 아는 사람"이 아니라 "도입을 해본 사람"으로 들린다.

### 3-5. 도입 효과를 검증하는 법

프로토콜 도입은 켜고 끝이 아니라 **효과를 측정할 수 있어야** 의미가 있다.

핵심은 **프로토콜별로 지표를 분리해서 보는 것**이다. 전체 평균만 보면 h3로 붙은 일부 사용자의 개선이 전체에 희석돼 보이지 않는다. 접속 프로토콜을 차원(dimension)으로 붙여 h1/h2/h3 각각의 지표를 따로 집계해야 한다.

봐야 할 지표는 세 가지다. **프로토콜별 접속 비율**(h3를 켰는데 실제로 몇 퍼센트가 h3로 붙는가 — UDP 차단 환경의 비율을 알 수 있다), **프로토콜별 페이지 로딩 지표**(실사용자 측정, 특히 손실이 많은 모바일 구간), **프로토콜별 에러율**(h3 경로에서만 실패가 늘고 있지 않은가).

Nginx라면 액세스 로그 포맷에 프로토콜을 넣어 집계의 기반을 만든다.

```nginx
# $server_protocol 에 HTTP/1.1, HTTP/2.0, HTTP/3.0 이 찍힌다.
# 이 값이 있어야 로그 집계에서 프로토콜별로 나눠 볼 수 있다.
log_format proto_aware '$remote_addr $server_protocol $status '
                       '$request_time $upstream_response_time "$request"';
access_log /var/log/nginx/access.log proto_aware;
```

## 4. 꼬리질문 대비 포인트

### "HTTP/2가 멀티플렉싱을 해결했는데 왜 HTTP/3이 또 필요했나요?"

**HTTP/2가 없앤 것은 HTTP 계층의 줄뿐이고, 전송로는 여전히 하나의 TCP였기 때문**이다. 줄이 사라진 게 아니라 한 계층 아래로 내려갔다.

메커니즘으로 설명하면 이렇다. TCP는 HTTP/2의 스트림이라는 개념을 전혀 모른다. TCP 입장에서 그 연결에 흐르는 것은 그냥 하나의 바이트 물줄기이고, TCP는 "보낸 순서대로 올려준다"는 자기 계약만 지킨다. 그래서 **패킷 하나가 유실되면 그 패킷과 아무 상관없는 스트림의 데이터가 이미 커널 버퍼에 도착해 있어도 애플리케이션에 전달되지 않는다.**

이것은 TCP의 계약에서 나오는 필연이라 HTTP 계층에서 고칠 방법이 없다. 그래서 **전송 프로토콜 자체를 스트림 단위로 순서를 보장하는 QUIC으로 바꿔야 했다.** QUIC은 순서 보장의 단위를 커넥션이 아니라 스트림으로 다시 정의해, 한 스트림의 유실이 다른 스트림을 멈추지 않게 만들었다.

### "QUIC은 왜 새 프로토콜을 만들지 않고 UDP 위에 얹었나요?" (가산점 포인트)

**배포 가능성 때문**이다. 성능 이유가 아니라는 것이 포인트다.

TCP를 고치거나 제5의 전송 프로토콜을 새로 만들면, 전 세계의 OS 커널과 중간 장비(NAT 공유기, 방화벽, 통신사 장비)가 그것을 이해해야 한다. 그런데 이 장비들은 자기가 모르는 프로토콜을 흔히 **차단해 버린다.** 프로토콜이 중간 장비들 때문에 굳어져 바꿀 수 없게 되는 이 현상을 **프로토콜 경직화(ossification)**라고 부른다.

**UDP는 어디서나 통과되는 최소한의 배관**이고, 중간 장비들은 UDP 페이로드 안을 들여다보지 않는다. 그 안에 신뢰성·순서·암호화를 **사용자 공간 라이브러리로** 구현하면, 커널 교체 없이 브라우저와 서버 소프트웨어 배포만으로 전송 계층을 진화시킬 수 있다. **진화 속도가 OS 업데이트 주기가 아니라 애플리케이션 배포 주기가 되는 것**이 이 선택의 본질적 이득이다.

QUIC이 헤더 대부분까지 암호화한 것도 같은 맥락이다. 중간 장비가 내부를 들여다보고 자기 방식대로 해석하거나 간섭할 여지를 처음부터 없애 **다시 경직화되는 것을 막으려는** 설계다.

### "HTTP/2로 올리면 무조건 빨라지나요?"

**아니다.** 반례 세 가지를 구조로 답한다.

**첫째, 패킷 손실이 잦은 환경에서는 오히려 나빠질 수 있다.** HTTP/1.1은 연결 6개에 요청을 나눠 실었으므로 유실의 피해가 한 연결로 격리됐는데, HTTP/2는 한 연결에 전부 몰아넣었으므로 유실 한 번이 **모든 스트림을 동시에 세운다.** 열악한 모바일망에서 이 차이가 드러난다.

**둘째, HTTP/1.1 시대의 편법을 걷어내지 않으면 이득이 상쇄된다.** 도메인 샤딩은 연결 세트를 늘려 handshake와 slow start 비용을 자초하고, 헤더 압축의 동적 테이블과 스트림 우선순위가 연결마다 흩어져 제 값을 못 한다. 파일 병합과 인라이닝도 재검토 대상이다.

**셋째, 서버 간 내부 호출에서는 체감 이득이 거의 없다.** 같은 데이터센터 안이라 RTT가 1ms 미만이고 손실도 거의 없으며, 커넥션 풀로 이미 연결을 재사용하고 동시 요청도 연결 수로 풀고 있다. **HTTP/2가 푸는 문제가 그 구간에는 애초에 없다.**

결론은 **"어느 구간의 어떤 문제를 푸는가"를 확인하고 도입해야 한다**는 것이다.

### "HTTP/3을 도입했는데 일부 사용자는 계속 HTTP/2로 접속합니다. 왜죠?"

**UDP 443 포트를 기업 방화벽이나 일부 네트워크가 차단하는 경우가 흔하기 때문**이다. 그리고 그것은 버그가 아니라 설계된 동작이다.

3-2에서 본 대로 HTTP/3은 ALPN으로 협상할 수 없다 — 전송 계층 자체가 다르기 때문이다. 그래서 브라우저는 **먼저 TCP로 붙어(h1/h2) 응답의 `Alt-Svc` 헤더를 보고 "이 서비스는 h3도 된다"를 학습한 뒤, 다음 연결부터 UDP로 시도한다.** UDP가 막혀 있으면 조용히 TCP로 폴백한다.

그래서 **h3 도입은 "전환"이 아니라 "가능한 클라이언트에게만 추가 제공"**이고, h1/h2 경로는 항상 살려둬야 한다. 이것을 모르면 "h3를 켰는데 절반만 h3로 붙는다"를 장애로 오해하게 된다.

여기서 두 가지를 더 확인하라고 말하면 좋다. **`Alt-Svc` 헤더가 실제로 응답에 실려 나가고 있는지**(QUIC 리스너만 열고 이 헤더를 빠뜨리면 브라우저가 UDP를 시도조차 하지 않아 h3 비율이 0으로 남는다), 그리고 **프로토콜별로 지표를 분리 수집하고 있는지**다. 전체 평균만 보면 h3 도입 효과를 검증할 수 없다.

### "우리 서비스에 HTTP/3 도입을 검토한다면 어떤 기준으로 판단하겠어요?" (시니어 변별 포인트)

**순서가 있는 판단**으로 답하는 것이 핵심이다.

**첫째, 어느 구간의 문제인지부터 가른다.** h3가 푸는 것은 사용자 구간의 지연·손실·이동성이다. 그러니 근거가 되는 데이터는 **모바일 사용자 비중, 사용자 구간의 RTT와 패킷 손실률**이고, 이건 서버 로그가 아니라 실사용자 측정(RUM) 데이터로만 알 수 있다. 사용자가 대부분 국내 유선망이고 손실률이 낮다면 h3의 이득은 작다 — **"신기술이라 켠다"가 아니라 "우리 트래픽의 병목이 h3가 푸는 병목인가"**로 답해야 한다.

**둘째, 종단 지점을 정한다.** 원 서버에 직접 붙이기보다 **CDN이나 로드밸런서에서 켜는 것**이 인증서·프로토콜 관리 비용이 낮고, 원 서버 구간은 손대지 않아 리스크가 작다. 롤백도 설정 한 줄이다.

**셋째, 폴백과 관측을 먼저 갖춘다.** UDP 차단 환경에서 폴백이 자연스러운지 확인하고(`Alt-Svc` 광고와 TCP 경로가 함께 살아 있는지), **프로토콜별 성능·에러 지표를 분리 수집**할 수 있는 상태를 만든 뒤에 켠다. 측정할 수 없으면 켜도 효과를 증명할 수 없고, 문제가 생겨도 h3 탓인지 알 수 없다.

**넷째, 그 전에 더 싼 수단이 남아 있는지 본다.** 응답 크기 줄이기, 캐싱 헤더 정비, 이미지 포맷 최적화, CDN 엣지 확대는 프로토콜 교체보다 비용이 낮고 효과가 확실한 경우가 많다. **프로토콜 버전은 우선순위가 높은 카드가 아니다.**

## 한 줄 요약

HTTP/1.1은 응답에 요청 식별자가 없어 순서로만 짝을 맞추는 텍스트 규약이라 한 연결에 요청 하나씩만 흘릴 수 있었고(HTTP 계층 HOL), HTTP/2는 모든 조각에 길이와 스트림 ID를 붙이는 이진 프레이밍으로 경계와 라벨을 만들어 멀티플렉싱을 가능하게 했지만 전송로가 여전히 하나의 TCP라 패킷 유실 하나가 무관한 스트림까지 세우는 TCP 계층 HOL이 남았으며, HTTP/3은 순서 보장의 단위를 커넥션에서 스트림으로 옮긴 UDP 기반 QUIC으로 전송 계층을 갈아 그것까지 풀고 핸드셰이크 통합과 커넥션 마이그레이션을 덤으로 얻었다 — 다만 손실 많은 망에서 HTTP/2가 1.1보다 나빠질 수 있고 옛 편법을 걷어내지 않으면 이득이 상쇄되므로, "어느 구간의 어떤 문제를 푸는가"를 측정으로 확인한 뒤 최전방에서 켜는 것이 도입의 정석이다.
