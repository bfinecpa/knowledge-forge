# HTTP/1.1 → 2 → 3 — HOL blocking을 한 계단씩 아래로 밀어낸 진화

> 핵심 관전 포인트: **세 버전의 차이는 "HOL(Head-of-Line) blocking이
> 어느 계층에 남아 있는가"로 관통된다. HTTP/1.1은 한 연결에서 한 번에
> 하나의 요청-응답만 처리해 HTTP 계층에서 줄이 막힌다. HTTP/2는
> 멀티플렉싱으로 그 줄을 없앴지만, 여전히 하나의 TCP 위라서 패킷
> 하나만 유실돼도 모든 스트림이 함께 멈추는 TCP 계층 HOL이 남았다.
> HTTP/3은 전송 계층 자체를 UDP 기반 QUIC으로 갈아, 스트림별로 독립
> 복구하게 만들어 그것까지 풀었다. 즉 각 버전은 "앞 버전이 못 푼
> 줄막힘을 한 계층 아래로 내려가 푼 역사"다.**

---

## 0. 질문 + 의도

**질문**: "HTTP/1.1, HTTP/2, HTTP/3의 차이(HOL blocking 관점)를 설명해주세요."

**출제 의도**: 프로토콜 버전이 이미지 수십 장을 싣는 웹툰 페이지의
로딩 특성을 바꾼다. 기능 나열이 아니라 각 버전이 "무슨 문제를
풀었는지"의 흐름으로 이해하는 사람은, 자기 서비스에 새 프로토콜을
도입할지 판단할 수 있는 사람이다.

## 1. HOL blocking이란 — 계산대 줄의 맨 앞 손님

HOL(Head-of-Line) blocking은 **줄의 맨 앞이 막히면, 뒤에 선 전부가
자기 잘못 없이 기다리는 현상**이다. 마트 계산대에서 맨 앞 손님이
지갑을 못 찾으면 뒤의 손님들은 물건이 하나뿐이어도 멈춘다.

HTTP에서 "줄"은 두 계층에 존재할 수 있다:

- **HTTP 계층의 줄**: 한 연결 안에서 요청-응답이 순서대로만 오갈 때,
  느린 응답 하나가 뒤 요청 전부를 세운다.
- **TCP 계층의 줄**: TCP는 "바이트가 보낸 순서 그대로 도착함"을
  보장하는 프로토콜이라, 패킷 하나가 유실되면 **재전송이 도착할
  때까지 그 뒤에 이미 도착한 패킷들도 커널이 애플리케이션에 안
  올려준다**. 위에서 아무리 여러 요청을 섞어 보내도, 아래층 배관이
  하나면 배관 막힘은 전체 막힘이다.

세 버전의 차이는 이 두 줄을 각각 어떻게 없앴는가다.

## 2. 버전별 — 무엇을 풀었고 무엇이 남았나

### HTTP/1.1 — 연결 재사용까지는 왔지만, 한 줄로만 통행

keep-alive가 기본이 되어 요청마다 TCP 연결을 새로 맺는 낭비는
없앴다. 그러나 **한 연결에서는 요청 하나를 보내고 그 응답을 다
받아야 다음 요청을 보낼 수 있다**. 파이프라이닝(응답을 기다리지 않고
요청을 연달아 보내는 기능)이 스펙에는 있지만, 응답은 여전히 요청
순서대로 와야 해서 HOL이 그대로인 데다 중간 장비 호환성 문제로
브라우저들이 사실상 꺼버렸다.

그래서 브라우저는 **도메인당 연결을 여러 개(통상 6개 안팎) 열어**
병렬성을 흉내 냈고, 서비스들은 이미지를 `img1.example.com`,
`img2.example.com`처럼 도메인을 쪼개 연결 수를 늘리는
**도메인 샤딩**까지 했다 — 프로토콜의 한계를 우회하는 편법의 시대.

### HTTP/2 — 멀티플렉싱으로 HTTP 계층의 줄을 없앰

HTTP/2는 메시지를 텍스트가 아닌 **바이너리 프레임**으로 쪼개고, 각
프레임에 스트림 ID를 붙여 **하나의 TCP 연결 위에서 여러 요청-응답
스트림을 뒤섞어(멀티플렉싱) 주고받는다**. 느린 응답이 있어도 다른
스트림의 프레임은 그 사이사이로 계속 흐르므로 HTTP 계층의 HOL은
사라진다. 반복되는 헤더를 압축하는 HPACK, 스트림 우선순위도 함께
들어왔다 (서버 푸시도 스펙에 있었지만 실무에서 거의 쓰이지 않았고
브라우저 지원도 제거되는 추세다).

그런데 **줄이 한 계층 아래로 내려갔을 뿐이다.** 여전히 전송로는
하나의 TCP다. 패킷 하나가 유실되면, 그 패킷과 무관한 스트림의
데이터가 이미 도착해 있어도 TCP가 순서 보장을 위해 전부 붙들고
있는다 — **TCP 계층 HOL**. 스트림을 아무리 나눠도 TCP 입장에서는
그냥 하나의 바이트 물줄기이기 때문이다.

### HTTP/3 — 전송 계층을 갈아 TCP의 줄까지 없앰

TCP 자체를 고치는 것은 전 세계 커널·중간 장비(공유기, 방화벽,
통신사 장비)를 다 바꿔야 하는 일이라 사실상 불가능하다. 그래서
HTTP/3은 **UDP 위에 새 전송 프로토콜 QUIC을 사용자 공간에
구현**하는 길을 택했다. QUIC이 재전송·혼잡 제어·암호화(TLS 1.3
내장)를 직접 수행하며, 핵심은:

- **스트림별 독립 전달**: 유실 복구를 스트림 단위로 하므로, 한
  스트림의 패킷이 유실돼도 **다른 스트림은 멈추지 않는다**. TCP 계층
  HOL 해소 (유실된 그 스트림 자신은 당연히 기다린다).
- **핸드셰이크 통합**: TCP 3-way handshake 후 TLS handshake를 따로
  하던 것을 하나로 합쳐 첫 연결 왕복을 줄이고, 재연결 시에는
  0-RTT(핸드셰이크 완료 전에 데이터 동봉)까지 가능하다.
- **커넥션 마이그레이션**: 연결을 IP+포트가 아니라 **커넥션 ID**로
  식별하므로, Wi-Fi에서 LTE로 넘어가 IP가 바뀌어도 연결이 안 끊긴다
  — 이동 중 모바일 사용자에게 특히 유효하다.

헤더 압축은 HPACK의 순서 의존 문제를 손본 QPACK을 쓴다.

### 한눈 비교

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 전송 계층 | TCP | TCP | QUIC (UDP 기반) |
| 한 연결의 동시 요청 | 1개 (순차) | 다수 (멀티플렉싱) | 다수 (멀티플렉싱) |
| HTTP 계층 HOL | 있음 | 없음 | 없음 |
| TCP(전송) 계층 HOL | 있음 | **있음** | 없음 (스트림 독립) |
| TLS 핸드셰이크 | 별도 | 별도 | 전송 계층에 통합 |

## 3. 실무 맥락 — 웹툰 페이지와 도입 판단

이미지 수십 장을 싣는 웹툰 뷰어 페이지로 체감 차이를 그려보면:

- **HTTP/1.1**: 연결 6개에 이미지 수십 장이 줄을 서므로, 한 이미지가
  느리면 같은 연결 뒤의 이미지들이 통째로 늦는다. 워터폴 차트에
  계단식 대기가 보인다.
- **HTTP/2**: 연결 하나에 전부 태워 동시에 흘러온다. 단, **패킷
  손실이 잦은 열악한 모바일망에서는 유실 한 번이 모든 이미지
  스트림을 동시에 세우므로, 연결이 6개로 분산돼 있던 1.1보다 오히려
  나빠질 수도 있다** — "2가 항상 빠르다"가 아닌 이유.
- **HTTP/3**: 유실이 해당 스트림만 세우므로 손실 많은 무선망에서
  강하고, 지하철에서 네트워크가 전환돼도 연결이 유지된다.

도입 판단의 현실도 알아야 한다. HTTP/2·3은 보통 **CDN이나 로드밸런서
같은 최전방에서 종단(terminate)** 하고, 그 뒤 내부 구간(LB → 앱
서버)은 HTTP/1.1을 유지하는 구성이 일반적이다 — 사용자 구간의
문제(높은 지연, 패킷 손실, 많은 동시 리소스)를 푸는 프로토콜이지,
저지연 내부망의 서버 간 호출에서는 이득이 작기 때문이다.

```nginx
# 최전방(Nginx)에서만 프로토콜을 올리고, 뒤는 그대로 두는 전형적 구성
server {
    listen 443 ssl http2;          # HTTP/2 활성화
    listen 443 quic reuseport;     # HTTP/3(QUIC) 활성화 (지원 빌드 기준)
    add_header Alt-Svc 'h3=":443"';  # "HTTP/3도 됩니다" 광고 → 브라우저가 다음부터 h3 시도

    location / {
        proxy_pass http://app;     # 내부 구간은 HTTP/1.1 keep-alive면 충분
    }
}
```

또 하나: HTTP/1.1 시대의 최적화 편법(도메인 샤딩, 이미지 스프라이트,
파일 병합)은 **HTTP/2에서는 역효과**다. 멀티플렉싱으로 연결 하나면
충분한데 도메인을 쪼개면 연결·TLS 핸드셰이크 비용과 각 연결의 slow
start만 늘어난다. 프로토콜을 올릴 때는 옛 편법을 걷어내는 것까지가
마이그레이션이다.

## 4. 꼬리질문 대비 포인트

### "HTTP/2가 멀티플렉싱을 해결했는데 왜 HTTP/3이 또 필요했나요?"

HTTP/2는 HTTP 계층의 줄만 없앴고, 전송로는 여전히 하나의 TCP라서
줄이 한 층 아래로 내려갔을 뿐이기 때문이다. TCP는 바이트 순서
보장을 위해 유실 패킷의 재전송이 올 때까지 뒤에 도착한 데이터를
전부 붙들고 있으므로, 패킷 하나의 유실이 무관한 스트림까지 전부
세운다. 이건 TCP의 본성이라 HTTP 계층에서는 못 고치고, 전송
프로토콜 자체를 스트림 단위 복구가 가능한 QUIC으로 바꿔야 했다.

### "QUIC은 왜 새 프로토콜을 만들지 않고 UDP 위에 얹었나요?"

TCP를 고치거나 제4의 전송 프로토콜을 만들면 전 세계의 OS 커널과
중간 장비(NAT 공유기, 방화벽, 통신사 장비)가 그것을 이해해야 하는데,
이 장비들은 TCP/UDP 외의 프로토콜을 흔히 차단해버린다(프로토콜
경직화, ossification). UDP는 어디서나 통과되는 최소한의 배관이므로,
그 위에 신뢰성·순서·암호화를 **사용자 공간 라이브러리로** 구현하면
커널 교체 없이 애플리케이션 배포만으로 전송 계층을 진화시킬 수 있다.
QUIC이 암호화를 강제해 중간 장비가 내부를 들여다보고 간섭할 여지를
없앤 것도 같은 맥락이다. (가산점 포인트)

### "HTTP/2로 올리면 무조건 빨라지나요?"

아니다. 세 가지 반례를 들 수 있다. (1) 패킷 손실이 잦은 환경에서는
단일 TCP 연결의 HOL 때문에 여러 연결로 분산되던 1.1보다 나빠질 수
있다. (2) 도메인 샤딩·파일 병합 같은 1.1 시대 편법을 걷어내지 않으면
멀티플렉싱의 이득을 못 살리거나 역효과가 난다. (3) 서버 간 내부
호출처럼 커넥션 풀로 이미 연결을 재사용하고 동시 요청도 연결 수로
풀고 있는 구간에서는 체감 이득이 작다. "어느 구간의 어떤 문제를
푸는가"를 확인하고 도입해야 한다.

### "HTTP/3을 도입했는데 일부 사용자는 계속 HTTP/2로 접속합니다. 왜죠?"

UDP 443을 기업 방화벽이나 일부 네트워크가 차단하는 경우가 흔하기
때문이다. 브라우저는 보통 먼저 TCP(h1/h2)로 접속한 뒤 응답의
`Alt-Svc` 헤더를 보고 다음 연결부터 h3를 시도하며, QUIC이 막혀
있으면 조용히 TCP로 폴백한다. 그래서 h3 도입은 "전환"이 아니라
"가능한 클라이언트에게만 추가 제공"이고, h1/h2 경로는 항상 살려둬야
한다. 모니터링도 프로토콜별로 나눠 봐야 도입 효과를 검증할 수 있다.

### "우리 서비스에 HTTP/3 도입을 검토한다면 어떤 기준으로 판단하겠어요?" (시니어 변별 포인트)

먼저 **어느 구간의 문제인지**부터 가른다 — h3가 푸는 것은 사용자
구간의 지연·손실·이동성이므로, 모바일 사용자 비중과 사용자 구간
RTT/패킷 손실 지표(RUM 데이터)가 근거다. 다음으로 **종단 지점**:
직접 서버에 붙이기보다 CDN/LB에서 켜는 것이 인증서·프로토콜 관리
비용이 낮고, 원 서버 구간은 손대지 않아 리스크가 작다. 그리고
**폴백과 관측**: UDP 차단 환경 폴백이 자연스러운지, 프로토콜별
성능·에러 지표를 분리 수집해 실제 개선을 검증할 수 있는지를 갖춘
뒤에 켠다. "신기술이라 켠다"가 아니라 "우리 트래픽의 병목이 h3가
푸는 병목인가"로 답하는 것이 핵심이다.

## 한 줄 요약

HTTP/1.1은 한 연결에 한 요청씩이라 HTTP 계층에서 줄이 막혔고,
HTTP/2는 멀티플렉싱으로 그 줄을 없앴지만 단일 TCP의 순서 보장 탓에
패킷 유실 하나가 전 스트림을 세우는 TCP 계층 HOL이 남았으며,
HTTP/3은 UDP 기반 QUIC으로 전송 계층을 갈아 스트림별 독립 복구 +
핸드셰이크 통합 + 커넥션 마이그레이션까지 얻었다 — 각 버전은 앞
버전이 못 푼 줄막힘을 한 계층 아래로 내려가 푼 진화다.
