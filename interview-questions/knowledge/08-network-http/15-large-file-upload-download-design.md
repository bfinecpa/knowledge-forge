# 대용량 파일 업로드/다운로드 — 데이터가 흐르는 경로 자체를 설계하기

> 핵심 관전 포인트: **대용량 파일 처리의 원칙은 두 단계다. 1단계는 "메모리 사용량이 파일 크기에 비례하지 않게 하라" — `MultipartFile.getBytes()`처럼 통째로 읽는 코드는 파일 크기 × 동시 요청 수만큼 힙을 먹다가 OOM으로 죽으므로, 요청 스트림에서 저장소로 조각 단위로 흘려보내야 한다. 2단계는 "파일이 애플리케이션 서버를 아예 거치지 않게 하라" — presigned URL(스토리지가 특정 객체에 대해 특정 동작을 특정 시각까지만 허용한다고 자기 키로 서명해 발급한 URL. 서명 자체가 권한의 증거이므로 별도 인증 없이 스토리지가 검증할 수 있다)로 클라이언트가 오브젝트 스토리지에 직접 올리고, 다운로드는 CDN + signed URL로 엣지가 대신 내려준다. 앱 서버는 파일 바이트를 한 번도 만지지 않고 권한 검증·URL 발급·메타데이터 확정이라는 제어만 맡으므로, 파일 트래픽이 10배가 되어도 서버 용량 계획이 흔들리지 않는다. 대신 새 책임이 생긴다 — 앱이 업로드 완료를 모르므로 스토리지 이벤트나 완료 콜백으로 확인해야 하고, 크기·타입을 앱이 직접 막을 수 없어 서명에 조건을 넣어야 하며, 바이러스 검사와 후처리를 업로드 이벤트 기반 비동기 파이프라인으로 옮겨야 하고, "URL만 발급되고 안 올라간 경우"와 "올라갔는데 DB 레코드가 없는 경우"라는 양방향 고아를 `PENDING → CONFIRMED` 상태 전이와 정리 배치로 수습해야 한다. 여기에 경로상 계층별 크기·타임아웃 정합(Nginx `client_max_body_size`가 가장 흔한 범인), 다운로드의 Range 요청(`Range: bytes=0-1023` → `206 Partial Content`)이 만드는 이어받기·구간 탐색, 파일이 커질수록 필수가 되는 분할 업로드와 재개까지가 실무 고려사항의 전체 그림이다.**

---

## 0. 질문 + 의도

**질문**: "대용량 파일(이미지) 업로드/다운로드 시 서버 설계 고려사항은? (스트리밍, presigned URL)"

**출제 의도**: 파일을 서버 메모리에 통째로 올리는 코드는 파일이 크면 OOM이다. 스트리밍과 presigned URL(서버를 우회시키는 설계)을 아는지 — 요청 처리 코드 한 줄이 아니라 **데이터가 흐르는 경로 자체를 설계하는 능력**을 확인하는 질문이다.

## 1. 문제의 본질 — 파일이 어디를 거쳐 흐르는가

### 1-1. 경로 위의 모든 지점이 병목·장애 후보가 된다

평범한 API 응답은 수 KB다. 어디를 거치든 아무도 신경 쓰지 않는다. **파일이 수십 MB~수 GB가 되는 순간, 그동안 보이지 않던 모든 제한이 한꺼번에 드러난다.**

먼저 파일이 실제로 지나는 길과, 각 지점이 걸어둔 제한을 펼쳐 보자.

```
 ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
 │클라이언트 │──>│  CDN/LB  │──>│  Nginx   │──>│  Tomcat  │──>│  앱 힙   │──>│ 스토리지 │
 └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
      │              │              │              │              │              │
      │              │              │              │              │              │
  업로드 속도    본문 크기 한도  client_max_    maxThreads     힙 크기      단일 PUT 한도
  (느린 회선)    유휴 타임아웃   body_size      (전송 내내      (버퍼링하면   (S3 계열은
  중단 가능성    (전송 중 끊김)  (기본 1MB!)    스레드 점유)    OOM)         5GB)
                                client_body_    connection                   객체 키 정책
                                timeout         Timeout                     수명주기 규칙
                                요청 버퍼링                    임시 파일
                                (디스크 스풀)                   디스크 용량
```

**이 그림의 요점은 "가장 작은 값이 실질 한도"라는 것**이다. 앱에서 100MB를 받도록 설정했어도 Nginx가 1MB에서 자르면 실질 한도는 1MB다. 그리고 **Nginx가 자른 요청은 Tomcat에 도달한 적이 없으므로 앱 로그에 아무것도 남지 않는다**([12번 문서](12-nginx-roles-and-event-driven-architecture.md) 1절). "특정 크기부터만 실패하는데 로그에는 아무것도 없다"는 유령 현상의 정체가 대부분 이것이다.

그래서 이 질문의 답은 **"코드를 어떻게 짤까"가 아니라 "파일을 어느 경로로 흘릴까"**에서 시작한다. 아래에서 두 단계로 올라간다 — 먼저 서버를 지나야 한다면 어떻게 지날 것인가(1단계), 다음으로 아예 안 지나게 할 수 있는가(2단계).

### 1-2. 1단계 원칙 — 메모리 사용량이 파일 크기에 비례하면 잘못된 설계다

#### 왜 통째로 읽으면 죽는가

가장 흔한 코드부터 보자.

```java
// Before: 파일 전체를 byte[]로 힙에 적재한다
@PostMapping("/api/files")
public FileResponse upload(@RequestParam MultipartFile file) throws IOException {
    byte[] bytes = file.getBytes();   // ★ 여기서 파일 전체가 힙에 올라온다
    return storage.save(bytes);       // 저장이 끝날 때까지 그대로 붙들고 있다
}
```

`getBytes()`는 이름 그대로 파일 전체를 `byte[]` 하나로 만들어 준다. 편하지만, **`byte[]`는 힙에 통째로 잡히는 연속된 메모리**다.

문제는 단건이 아니라 동시성에서 터진다. 계산을 한 단계씩 따라가 보자.

```
[1단계] 요청 하나가 잡는 힙
        200MB 파일 → byte[] 200MB

[2단계] 동시 요청 수를 곱한다
        동시 업로드 50건 → 200MB × 50 = 10,000MB ≈ 9.8GB

[3단계] 힙 크기와 비교한다
        JVM 힙이 4GB라면 → 4GB를 넘는 20건째쯤에서 OutOfMemoryError

[4단계] 실제로는 더 빨리 죽는다
        · byte[] 말고도 애플리케이션이 쓸 힙이 필요하다
        · GC가 큰 배열을 옮기지 못해(대개 Old 영역 직행) Full GC가 잦아진다
        · 200MB 배열 하나를 할당할 연속된 공간이 없으면 힙에 여유가 있어도 실패한다
```

**여기서 진짜 위험한 것은 OOM 자체가 아니라 "누가 죽는가"다.** `OutOfMemoryError`는 힙을 요청한 스레드에서 터지므로, **파일 업로드와 아무 상관없는 결제 요청 스레드가 죽을 수 있다.** 업로드 기능 하나가 프로세스 전체를 불안정하게 만든다.

#### 스트리밍으로 바꾼다

```java
// After: 입력 스트림에서 저장소로 조각 단위로 흘려보낸다
@PostMapping("/api/files")
public FileResponse upload(@RequestParam MultipartFile file) throws IOException {
    try (InputStream in = file.getInputStream()) {
        // 저장소 클라이언트가 내부적으로 수 KB~수 MB 버퍼로 read → write를 반복한다.
        // 어느 순간에도 힙에 올라와 있는 것은 그 버퍼 하나뿐이다.
        // 파일이 200MB든 2GB든 이 메서드가 쓰는 힙은 동일하다.
        return storage.save(in, file.getSize(), file.getContentType());
    }   // try-with-resources: 예외가 나도 스트림이 닫힌다 (핸들 누수 방지)
}
```

```
[Before]  힙 사용량 = 파일 크기 × 동시 요청 수      ← 파일이 커지면 선형으로 증가
[After]   힙 사용량 = 버퍼 크기 × 동시 요청 수      ← 파일 크기와 무관, 상수
```

**외울 문장은 하나다.** "메모리 사용량이 파일 크기에 비례하면 잘못된 설계, 버퍼 크기로 고정되면 올바른 설계."

다운로드도 대칭이다. 파일을 `byte[]`로 읽어 응답 바디에 담지 말고, 저장소의 스트림을 응답 스트림에 이어 붙인다.

```java
// Before: 파일 전체를 읽어 응답 바디에 담는다 — 업로드와 같은 이유로 위험하다
@GetMapping("/api/files/{id}")
public ResponseEntity<byte[]> downloadBad(@PathVariable Long id) throws IOException {
    byte[] bytes = storage.readAll(id);   // 힙에 통째로
    return ResponseEntity.ok(bytes);
}
```

```java
// After: 저장소 스트림을 응답 스트림으로 흘린다
@GetMapping("/api/files/{id}")
public ResponseEntity<StreamingResponseBody> download(@PathVariable Long id) {
    FileMeta meta = fileService.getForDownload(id);   // ★ 권한·존재 검증은 여기서 끝낸다

    StreamingResponseBody body = out -> {
        try (InputStream in = storage.open(meta.storageKey())) {
            in.transferTo(out);    // 내부 버퍼로 read → write 반복
        }
    };

    return ResponseEntity.ok()
            // 크기를 알면 반드시 명시한다. 이것이 없으면 청크 전송으로 나가고,
            // 클라이언트는 전체 크기를 몰라 진행률을 계산할 수 없다.
            .contentLength(meta.size())
            .contentType(MediaType.parseMediaType(meta.contentType()))
            .body(body);
}
```

`StreamingResponseBody`를 반환하면 Spring이 이 응답을 **비동기로 처리**한다 — 컨트롤러 메서드는 즉시 반환되고, 실제 전송은 별도의 태스크 실행자 스레드에서 일어난다. 요청 스레드를 전송 시간 내내 붙들지 않는다는 점이 `ResponseEntity<byte[]>`와의 차이다. 다만 **완전히 공짜는 아니다** — 전송 자체는 여전히 블로킹이므로 태스크 실행자의 스레드 하나가 전송 내내 점유된다. **문제를 다른 풀로 옮겼을 뿐 없앤 것은 아니라는 점**을 인식하는 것이 중요하고, 이것이 2단계로 가는 이유 중 하나가 된다.

### 1-3. 그런데 Spring은 업로드 파일을 어디에 두는가

여기서 반드시 짚어야 할 사실이 있다. **`file.getInputStream()`으로 스트리밍한다고 해서 "요청이 도착하는 대로 저장소로 흘러가는" 것이 아니다.**

`MultipartFile`이 컨트롤러 메서드의 파라미터로 들어와 있다는 것은, **그 시점에 이미 요청 본문 전체가 수신되어 어딘가에 저장을 마쳤다**는 뜻이다. Spring Boot의 기본 구성에서 그 "어딘가"는 서블릿 컨테이너(Tomcat)가 관리하는 임시 저장소다.

어디에 저장되는지는 설정 하나가 결정한다.

```yaml
spring:
  servlet:
    multipart:
      # 이 크기 이하의 파트는 메모리에 두고, 초과분은 디스크 임시 파일로 내린다.
      # ★ 기본값은 0B다 — 즉 기본 동작은 "전부 디스크"다.
      file-size-threshold: 0B
      # 임시 파일을 둘 디렉토리. 비워두면 서블릿 컨테이너의 기본 임시 디렉토리를 쓴다.
      location: ""
      # 파일 하나의 상한. 기본 1MB.
      max-file-size: 1MB
      # 요청 전체(여러 파일 + 폼 필드)의 상한. 기본 10MB.
      max-request-size: 10MB
```

```
[요청이 도착하고 컨트롤러가 실행되기까지]

  클라이언트 ──(200MB 업로드)──> Nginx ──> Tomcat
                                            │
                                            │ ① multipart 본문을 파싱한다
                                            │ ② 각 파트를 file-size-threshold와 비교
                                            │     · 이하  → 메모리에 보관
                                            │     · 초과  → location의 임시 파일로 기록
                                            │ ③ 전체 수신이 끝나야 비로소
                                            v
                                    컨트롤러 메서드 실행
                                    file.getInputStream()
                                            │
                                            v
                                    ② 에서 만든 임시 파일을 읽는다
```

이 사실이 실무에서 만드는 결과가 셋이다.

**첫째, `getBytes()`가 위험한 진짜 이유가 더 선명해진다.** 파일은 이미 디스크에 안전하게 있는데, `getBytes()`는 **그것을 굳이 힙으로 한 번 더 복사한다.** 아무 이득 없이 OOM 위험만 사는 셈이다. `getInputStream()`은 그 임시 파일을 스트림으로 읽을 뿐이다.

**둘째, 임시 디렉토리가 가득 차는 사고가 실재한다.** 디스크 사용량은 **동시 업로드 수 × 파일 크기**로 늘어난다.

```
동시 업로드 100건 × 500MB = 50GB의 임시 파일

  · 컨테이너의 기본 임시 디렉토리가 작은 이미지 레이어 위에 있으면 순식간에 찬다.
  · 디스크가 차면 업로드만 실패하는 게 아니다 —
    같은 볼륨을 쓰는 로그 기록, JVM의 힙 덤프, 다른 임시 파일 작업이 전부 실패한다.
  · Tomcat은 요청이 끝나면 임시 파일을 지우지만, "요청이 겹쳐 있는 동안"의
    최대 동시 사용량이 문제이므로 정리 여부와 무관하게 순간 피크가 터진다.
```

대응은 **임시 디렉토리를 충분한 용량의 별도 볼륨으로 지정하고(`spring.servlet.multipart.location`), 그 볼륨의 사용률을 모니터링에 올리는 것**이다. 그리고 동시 업로드 수 자체에 상한을 두는 것(세마포어, 게이트웨이의 동시성 제한)도 유효한 방어다.

**셋째, 정말로 "받는 즉시 흘리려면" multipart 리졸버를 우회해야 한다.** `spring.servlet.multipart.enabled=false`로 두고 `HttpServletRequest.getInputStream()`을 직접 읽어 파싱하거나(스트리밍 방식의 multipart 파서 사용), WebFlux에서 `FilePart` / `Flux<DataBuffer>`로 받는 방식이다. **다만 이것은 복잡도가 확 올라가는 선택**이라, 대개는 여기까지 가지 않고 2절의 presigned URL로 넘어간다.

한 가지 더. **Nginx도 기본적으로 요청 본문을 먼저 버퍼링한다**(`proxy_request_buffering on`). 느린 클라이언트로부터 Tomcat을 보호하는 좋은 기본값이지만, 그 말은 **Nginx 쪽에도 같은 크기의 임시 파일이 쌓인다**는 뜻이다(`client_body_temp_path`). 대용량 업로드가 많다면 **Nginx의 디스크도 함께 봐야 한다.**

### 1-4. 스트리밍해도 남는 비용 — 2단계로 가는 이유

1단계를 다 적용해도 근본적으로 남는 것이 있다. **전송이 서버를 통과하는 동안 서버의 자원을 계속 쓴다는 것**이다.

```
느린 회선의 사용자가 1GB 파일을 받는다. 실효 속도 5Mbps.

  전송 시간 = 1GB × 8 bit/byte ÷ 5Mbps
            = 8,000 Mbit ÷ 5 Mbit/s
            = 1,600초 ≈ 26분 40초

이 26분 동안 계속 점유되는 것:
  · 커넥션 하나 (Nginx의 워커가 관리)
  · 전송 스레드 하나 (블로킹 I/O라면)
  · 우리 서버의 아웃바운드 대역폭
  · 스토리지에서 우리 서버로 들어오는 인바운드 대역폭 (같은 바이트를 두 번 나른다)
```

**마지막 줄이 특히 중요하다.** 서버 경유 다운로드는 같은 1GB를 **스토리지 → 서버**로 한 번, **서버 → 클라이언트**로 한 번, 총 두 번 나른다. 서버의 네트워크 대역폭이 실질적으로 절반이 되는 셈이고, 클라우드라면 데이터 전송 요금도 두 번 낸다.

동시 사용자 수를 곱해 보면 문제가 분명해진다. 26분짜리 전송이 100건 동시에 있으면 커넥션 100개와 스레드 100개가 26분 동안 묶여 있다. **애플리케이션 서버의 용량 계획이 "비즈니스 로직 처리량"이 아니라 "파일 전송량"에 지배당하기 시작한다.**

그래서 다음 질문이 나온다. **"파일을 서버가 꼭 통과해야 하는가?"**

## 2. 2단계 원칙 — 서버를 경유시키지 말라 (presigned URL)

### 2-1. presigned URL이란 무엇이고, 왜 인증을 대신할 수 있는가

#### 정의

**presigned URL(사전 서명 URL)은 오브젝트 스토리지가 "특정 객체에 대해, 특정 동작을, 특정 시각까지만 허용한다"고 자기 비밀 키로 서명해서 발급한 URL이다.** "미리(pre) 서명된(signed)"이라는 이름 그대로, 실제 요청이 오기 전에 미리 허가증을 만들어 둔 것이다.

URL 안에 무엇이 들어 있는지 펼쳐 보면 구조가 보인다.

```
https://my-bucket.s3.ap-northeast-2.amazonaws.com/uploads/2026/09/a3f1c9.jpg
    ?X-Amz-Algorithm=AWS4-HMAC-SHA256          ← 서명 알고리즘
    &X-Amz-Credential=AKIA.../20260901/...     ← 누구의 키로 서명했는가
    &X-Amz-Date=20260901T090000Z               ← 언제 서명했는가
    &X-Amz-Expires=300                         ← 발급 후 300초(5분)까지 유효
    &X-Amz-SignedHeaders=content-type;host     ← 서명이 보호하는 헤더 목록
    &X-Amz-Signature=4f3c2a...                 ← ★ 위 모든 것에 대한 서명값
```

서명값은 **HTTP 메서드(PUT인지 GET인지), 버킷과 객체 키, 만료 시각, 서명에 포함시킨 헤더들**을 전부 입력으로 넣어 계산된다. 그래서 이 중 **하나라도 다르게 요청하면 서명이 안 맞는다.**

#### 왜 이것이 인증을 대신할 수 있는가

여기가 이 개념의 핵심이다.

보통의 인증은 **"당신이 누구인지 증명하시오"**를 요구한다. 토큰을 보내고, 서버가 그것을 확인하고, 그 사용자의 권한을 조회하고, 이 동작이 허용되는지 판정한다. 이 과정에는 **사용자 정보와 권한 정보가 필요하고, 그것은 우리 서비스에만 있다.** 스토리지는 우리 서비스의 사용자 테이블을 모른다.

presigned URL은 질문을 바꾼다. **"누구인가"를 묻지 않고 "이 요청이 허가된 것인가"만 묻는다.**

```
[보통의 인증]
  요청 → "이 토큰의 주인은 누구인가?" → 사용자 조회 → "이 사용자가 이걸 해도 되나?" → 판정
         (사용자·권한 정보가 필요하다 = 우리 서비스만 할 수 있다)

[presigned URL]
  요청 → "이 URL의 서명이 우리 키로 계산한 값과 같은가?" → 판정
         (비밀 키 하나만 있으면 된다 = 스토리지가 혼자 할 수 있다)
```

**서명은 "이 비밀 키를 가진 누군가가 이 동작을 명시적으로 허가했다"는 사실 자체의 증거다.** 그리고 그 비밀 키는 우리 앱 서버만 갖고 있다. 그러므로 **유효한 서명이 붙어 있다는 것은 "우리 앱 서버가 권한 검사를 통과시킨 요청"이라는 뜻**이 된다. 권한 판단은 이미 발급 시점에 우리 서버에서 끝났고, URL은 그 판단의 결과를 실어 나르는 것뿐이다.

**비유하자면 놀이공원의 자유이용권이다.** 매표소(앱 서버)에서 신분증을 확인하고 결제를 받고 표를 발급한다. 놀이기구 앞의 직원(스토리지)은 신분증을 다시 보지 않는다 — **표에 찍힌 위조 방지 홀로그램(서명)이 진짜인지와 유효 시간이 지나지 않았는지만 본다.** 그것만으로 충분하다. 매표소가 이미 확인했기 때문이다.

이 구조 덕분에 **권한 판단은 우리 서비스가 하고, 실제 전송은 스토리지가 하는** 역할 분리가 성립한다.

### 2-2. 업로드 흐름 — 앱 서버가 파일 바이트를 한 번도 만지지 않는다

```
 클라이언트                     앱 서버                      오브젝트 스토리지
     │                            │                                │
     │  ① POST /api/files/upload-url                              │
     │     {name, size, contentType}                              │
     ├───────────────────────────>│                                │
     │                            │                                │
     │                            │ ② 권한 검사                     │
     │                            │    (이 사용자가 올려도 되는가)   │
     │                            │ ③ 저장 키 결정                  │
     │                            │    uploads/2026/09/a3f1c9.jpg  │
     │                            │    ★ 클라이언트가 준 파일명을    │
     │                            │      그대로 키로 쓰지 않는다     │
     │                            │ ④ DB에 PENDING 레코드 INSERT   │
     │                            │ ⑤ presigned PUT URL 서명 발급   │
     │                            │    (만료 5분, content-type 고정)│
     │                            │                                │
     │  {fileId, uploadUrl}       │                                │
     │<───────────────────────────┤                                │
     │                            │                                │
     │  ⑥ PUT <uploadUrl>   파일 바이트 그대로                       │
     ├────────────────────────────────────────────────────────────>│
     │                            │                                │ 서명 검증
     │                            │                                │ 객체 저장
     │  200 OK  (ETag)            │                                │
     │<────────────────────────────────────────────────────────────┤
     │                            │                                │
     │  ⑦ POST /api/files/{fileId}/complete                        │
     ├───────────────────────────>│                                │
     │                            │ ⑧ HEAD로 객체 존재·크기 확인     │
     │                            ├───────────────────────────────>│
     │                            │<───────────────────────────────┤
     │                            │ ⑨ PENDING → CONFIRMED 전이      │
     │                            │ ⑩ 후처리 작업을 큐에 적재        │
     │  {status: CONFIRMED}       │                                │
     │<───────────────────────────┤                                │

  ★★ 굵은 화살표(⑥)가 유일하게 파일 바이트가 흐르는 구간이고,
     그 구간에 앱 서버가 없다. 앱 서버는 ①②③④⑤⑦⑧⑨⑩ 전부를
     수 KB짜리 JSON 요청 두 번으로 처리한다.
```

**⑦⑧이 없으면 설계가 완성되지 않는다.** 클라이언트의 "다 올렸어요"라는 신고를 그대로 믿으면 안 되는 이유는 3-2절에서 자세히 다룬다.

### 2-3. 코드

```java
@RestController
@RequiredArgsConstructor
class FileUploadController {

    private final FileService fileService;

    // ① 업로드 URL 발급 — 요청도 응답도 수 KB짜리 JSON이다
    @PostMapping("/api/files/upload-url")
    public UploadUrlResponse issueUploadUrl(
            @AuthenticationPrincipal Long userId,
            @Valid @RequestBody UploadUrlRequest req) {
        return fileService.issueUploadUrl(userId, req);
    }

    // ⑦ 업로드 완료 통보
    @PostMapping("/api/files/{fileId}/complete")
    public FileResponse complete(
            @AuthenticationPrincipal Long userId,
            @PathVariable Long fileId) {
        return fileService.confirmUpload(userId, fileId);
    }
}
```

```java
@Service
@RequiredArgsConstructor
class FileService {

    private final S3Presigner presigner;   // 서명 발급 전용 클라이언트
    private final S3Client s3;             // HEAD 등 제어 API용
    private final FileRepository files;
    private final String bucket;

    private static final Duration UPLOAD_URL_TTL = Duration.ofMinutes(5);
    private static final long MAX_UPLOAD_BYTES = 100L * 1024 * 1024;   // 100MB

    @Transactional
    public UploadUrlResponse issueUploadUrl(Long userId, UploadUrlRequest req) {
        // ② 권한 검사 — 이 판단이 곧 서명의 근거가 된다.
        //    서명을 발급하는 순간 "허가했다"는 뜻이므로 여기가 유일한 검문소다.
        permissionChecker.checkCanUpload(userId, req.purpose());

        // 앱이 강제할 수 있는 것은 여기서 미리 막는다.
        // 다만 클라이언트가 신고한 size는 신뢰할 수 없다 — 확정 검증은 ⑧에서 한다.
        if (req.size() > MAX_UPLOAD_BYTES) {
            throw new BadRequestException("파일이 너무 큽니다");
        }
        if (!ALLOWED_TYPES.contains(req.contentType())) {
            throw new BadRequestException("허용되지 않는 형식입니다");
        }

        // ③ 저장 키는 서버가 만든다. 클라이언트가 준 파일명을 그대로 키로 쓰면
        //    경로 조작(../), 다른 사용자 파일 덮어쓰기, 키 충돌이 전부 가능해진다.
        //    원본 파일명은 표시용으로 DB에만 저장한다.
        String key = "uploads/%s/%s".formatted(
                LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy/MM")),
                UUID.randomUUID());

        // ④ 먼저 PENDING으로 레코드를 만든다.
        //    "업로드는 됐는데 DB에 아무 흔적이 없는" 고아를 원천적으로 줄이기 위해,
        //    서명을 발급하기 전에 의도를 기록해 둔다 (3-2절).
        FileRecord record = files.save(FileRecord.pending(userId, key, req));

        // ⑤ 서명 발급.
        PutObjectRequest objectRequest = PutObjectRequest.builder()
                .bucket(bucket)
                .key(key)
                // Content-Type을 지정하면 이 값이 서명에 포함되므로,
                // 클라이언트는 정확히 이 타입으로만 PUT할 수 있다.
                // 다른 값을 보내면 서명 불일치로 스토리지가 거부한다.
                .contentType(req.contentType())
                .build();

        PutObjectPresignRequest presignRequest = PutObjectPresignRequest.builder()
                // 만료를 짧게 잡는 것이 URL 유출에 대한 1차 방어다 (3-2절).
                .signatureDuration(UPLOAD_URL_TTL)
                .putObjectRequest(objectRequest)
                .build();

        String uploadUrl = presigner.presignPutObject(presignRequest).url().toString();
        return new UploadUrlResponse(record.getId(), uploadUrl, UPLOAD_URL_TTL.toSeconds());
    }
}
```

> SDK 버전에 따라 클래스·메서드 이름이 다르다. 위 코드는 AWS SDK for Java v2의 `S3Presigner` 형태를 기준으로 한 것이므로, 실제 적용 시에는 사용하는 SDK 문서로 시그니처를 확인한다. **개념(무엇을 서명에 넣고 만료를 어떻게 주는가)은 SDK가 달라도 같다.**

완료 확인은 이렇게 한다.

```java
    @Transactional
    public FileResponse confirmUpload(Long userId, Long fileId) {
        FileRecord record = files.findByIdAndOwner(fileId, userId)
                .orElseThrow(() -> new NotFoundException("파일을 찾을 수 없습니다"));

        // 이미 확정된 건이면 그대로 돌려준다.
        // 클라이언트의 완료 통보는 네트워크 재시도로 두 번 올 수 있으므로
        // 이 메서드는 멱등해야 한다 — 두 번째 호출이 에러가 되면 안 된다.
        if (record.getStatus() == Status.CONFIRMED) {
            return FileResponse.from(record);
        }

        // ⑧ ★ 클라이언트의 신고를 믿지 않고 스토리지에 직접 확인한다.
        //    "완료됐다"는 말만 믿으면, 실제로는 안 올라간 파일에 대해
        //    CONFIRMED 레코드가 생겨 나중에 404를 뿜는 유령 파일이 된다.
        HeadObjectResponse head;
        try {
            head = s3.headObject(b -> b.bucket(bucket).key(record.getStorageKey()));
        } catch (NoSuchKeyException e) {
            throw new BadRequestException("업로드가 완료되지 않았습니다");
        }

        // 크기도 여기서 확정한다. 발급 시 클라이언트가 신고한 size는 참고값일 뿐이고,
        // 실제로 얼마가 올라왔는지는 스토리지만 안다.
        if (head.contentLength() > MAX_UPLOAD_BYTES) {
            s3.deleteObject(b -> b.bucket(bucket).key(record.getStorageKey()));
            record.markRejected("크기 초과");
            throw new BadRequestException("파일이 너무 큽니다");
        }

        // ⑨ 상태 전이
        record.confirm(head.contentLength(), head.eTag());

        // ⑩ 후처리는 여기서 하지 않고 큐에 넣는다 (3-4절)
        postProcessQueue.enqueue(record.getId());

        return FileResponse.from(record);
    }
```

### 2-4. 다운로드는 방향만 반대다

```java
    @Transactional(readOnly = true)
    public String issueDownloadUrl(Long userId, Long fileId) {
        FileRecord record = files.findById(fileId)
                .orElseThrow(() -> new NotFoundException("파일을 찾을 수 없습니다"));

        // 권한 판단은 여전히 우리가 한다. 스토리지는 이 사용자가 누구인지 모른다.
        permissionChecker.checkCanDownload(userId, record);

        GetObjectRequest objectRequest = GetObjectRequest.builder()
                .bucket(bucket)
                .key(record.getStorageKey())
                // 스토리지가 응답할 때 붙일 헤더를 서명에 넣어 지정할 수 있다.
                // 이렇게 하면 저장 키는 UUID여도 사용자에게는 원본 파일명으로 저장된다.
                .responseContentDisposition(contentDisposition(record.getOriginalName()))
                .build();

        return presigner.presignGetObject(b -> b
                .signatureDuration(Duration.ofMinutes(10))
                .getObjectRequest(objectRequest)).url().toString();
    }
```

이미지처럼 **여러 사용자가 반복 조회하는 콘텐츠**는 여기에 CDN을 한 겹 더 얹는 것이 정석이다. 스토리지의 presigned URL 대신 **CDN의 signed URL**을 발급하면, 전송을 사용자와 가까운 엣지 서버가 담당하고 같은 파일에 대한 두 번째 이후 요청은 스토리지까지 가지도 않는다. **권한 판단은 서버가, 전송은 엣지가** 하는 구조는 [07-traffic-performance/05](../07-traffic-performance/05-cdn-webtoon-image-serving.md)에서 다루는 CDN 설계와 정확히 같은 원리다.

### 2-5. 이 설계가 답의 중심인 이유

**파일 전송이라는 가장 무거운 일이 애플리케이션 서버의 용량 계획에서 통째로 빠진다.**

```
[서버 경유]
  파일 트래픽 10배 → 대역폭 10배, 커넥션 10배, 전송 스레드 10배 → 서버 증설 필요
  용량 계획의 지배 변수 = 파일 전송량

[presigned URL 경유]
  파일 트래픽 10배 → 앱 서버가 처리하는 것은 URL 발급 요청 10배 (수 KB짜리 JSON)
                     파일 바이트는 스토리지가 전부 받아낸다
  용량 계획의 지배 변수 = 비즈니스 요청 수
```

1-4절에서 본 26분짜리 전송이 앱 서버 입장에서는 **URL 발급 요청 한 건(수 밀리초)**으로 줄어든다. 그리고 스토리지는 애초에 이 일을 하려고 만들어진 시스템이라 사실상 무제한으로 확장된다.

**단, 공짜는 아니다.** 전송 부담을 덜어내는 대신 "제어와 정합성 관리"라는 새 책임을 산다. 그것이 3-2절이다.

## 3. 실무 고려사항 — 경로 위 계층 전부를 점검한다

### 3-1. 계층별 크기 제한·타임아웃 정합

1-1절의 그림에서 본 대로, 파일은 여러 계층을 지나고 **각 계층은 독립적인 제한을 갖고 있으며 서로의 값을 모른다.** 가장 작은 값이 실질 한도다.

가장 흔한 범인부터 순서대로 본다.

**Nginx `client_max_body_size` (기본 1MB).** 이것을 넘는 요청 본문은 **Tomcat에 도달하기 전에 `413`으로 반려**된다. Spring의 multipart 한도만 20MB로 늘려놓고 Nginx를 잊으면 "작은 파일은 되는데 큰 파일만 실패하고 앱 로그엔 아무것도 없는" 상태가 된다. (`413`은 오랫동안 "Request Entity Too Large"로 불렸고 최근 명세에서는 "Content Too Large"라는 이름을 쓴다. 어느 쪽이든 뜻은 같다.)

**Nginx `client_body_timeout` (기본 60초).** 클라이언트로부터 본문의 다음 조각을 읽기까지 기다리는 상한이다. 느린 회선에서 전송이 잠깐 멈추면 여기에 걸려 `408`이 난다. **파일이 클수록, 회선이 느릴수록 재현된다** — 그래서 "특정 사용자만 큰 파일 업로드에 실패"하는 형태로 나타난다.

**LB의 유휴 타임아웃.** 클라우드 LB에도 별도의 유휴 상한이 있고, Nginx만 늘리고 그 앞을 그대로 두면 아무 효과가 없다. [13번 문서](13-nginx-tomcat-timeout-buffer-mismatch.md)의 계층 정렬 원칙 그대로다.

**Spring `max-file-size` / `max-request-size` (기본 1MB / 10MB).** 파일 하나의 상한과 요청 전체의 상한이 따로 있다는 점을 놓치기 쉽다. 파일 여러 개를 한 요청에 담는 화면이라면 `max-request-size`가 먼저 걸린다.

```nginx
# 업로드 경로만 크게 연다. 전역으로 열면 다른 엔드포인트가 거대 본문 공격에 노출된다.
location /api/files {
    proxy_pass http://app;

    client_max_body_size 100m;    # 서비스 요구 크기 + 여유
    client_body_timeout  120s;    # 느린 회선의 전송 중단을 견딜 만큼

    # 요청 본문 버퍼링을 끄면 Nginx가 다 받기를 기다리지 않고 곧바로 흘려보낸다.
    # Nginx 디스크에 임시 파일이 쌓이지 않는 대신, 느린 클라이언트가
    # Tomcat 스레드를 직접 붙들게 되므로 트레이드오프를 알고 켜야 한다.
    # proxy_request_buffering off;

    proxy_read_timeout 300s;
    proxy_send_timeout 300s;
}
```

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 100MB
      max-request-size: 110MB    # 파일 100MB + 폼 필드 여유
      location: /var/upload-tmp  # 1-3절 — 충분한 용량의 볼륨으로 지정
```

**그리고 presigned URL 설계의 숨은 장점이 여기서 한 번 더 드러난다.** 파일이 이 계층 스택을 아예 통과하지 않으므로 **정합 문제 자체가 사라진다.** 앱 서버로 가는 것은 수 KB짜리 JSON 두 번뿐이라 어떤 계층의 크기 한도에도 걸리지 않는다.

### 3-2. presigned URL의 대가 — 무엇을 새로 책임지게 되는가 (시니어 변별 포인트)

**"presigned URL을 쓰면 됩니다"에서 멈추면 절반의 답이다.** 서버가 경로에서 빠지는 순간 서버가 하던 일들이 사라지는데, 그 일들이 필요 없어진 것이 아니라 **다른 방식으로 다시 만들어야 하는 것**이기 때문이다. 다섯 가지다.

#### ① 앱이 업로드 완료를 모른다

서버 경유 업로드에서는 요청이 끝나는 순간이 곧 업로드 완료 시점이었다. presigned 방식에서는 **파일이 스토리지로 직접 가므로 앱은 그 일이 일어났는지조차 모른다.**

확인 수단이 둘 있다.

**완료 콜백(클라이언트가 알려주는 방식)** — 2-2절의 ⑦번이다. 단순하지만 **클라이언트가 알려주지 않으면 영영 모른다.** 사용자가 업로드 직후 브라우저를 닫거나, 네트워크가 끊기거나, 앱이 죽으면 통보가 안 온다. 그리고 클라이언트의 말을 그대로 믿을 수도 없어서 반드시 스토리지에 `HEAD`로 실물을 확인해야 한다(2-3절의 ⑧).

**스토리지 이벤트 통지(스토리지가 알려주는 방식)** — 오브젝트 스토리지는 객체가 생성될 때 이벤트를 발행하는 기능을 제공한다(S3라면 이벤트 통지를 큐나 함수로 보낼 수 있다). **클라이언트를 신뢰하지 않아도 되고 클라이언트가 죽어도 동작한다**는 것이 결정적 장점이다.

```
[클라이언트 콜백]        빠르다 (사용자가 즉시 결과를 본다)
                        누락된다 (브라우저 닫힘, 네트워크 끊김)
                        신뢰할 수 없다 (반드시 HEAD로 실물 확인)

[스토리지 이벤트]        누락되지 않는다
                        약간 늦게 온다 (초 단위 지연)
                        클라이언트와 무관하게 동작한다

→ 실무에서는 둘 다 건다.
  콜백으로 사용자 응답을 빠르게 주고, 이벤트를 최종 진실로 삼는다.
  둘 다 같은 처리를 호출하므로 그 처리는 반드시 멱등해야 한다.
```

#### ② 클라이언트가 URL을 남에게 넘길 수 있다

발급된 URL은 **그것을 가진 누구나 쓸 수 있다.** 서명 안에 "누가 쓸 수 있는지"는 들어 있지 않기 때문이다. 사용자가 URL을 복사해 다른 사람에게 주거나, 브라우저 히스토리·로그·에러 리포트를 통해 새어 나가면 그 사람도 같은 동작을 할 수 있다.

방어는 셋이다.

**만료를 짧게.** 업로드 URL은 몇 분이면 충분하다. 다운로드 URL도 "이 링크로 지금 받는다"는 용도라면 10분 안쪽이면 된다. 유출되더라도 창이 좁으면 피해가 제한된다. (S3 계열의 서명 방식에서는 최대 만료가 7일로 제한되기도 하므로, "영구 링크"를 이 방식으로 만들 수는 없다.)

**동작과 대상을 최대한 좁혀서 서명.** PUT용 서명은 GET에 쓸 수 없고, 특정 키에 대한 서명은 다른 키에 쓸 수 없다. **"업로드용 URL로 다른 파일을 덮어쓸 수 있나?"라는 질문의 답이 "없다"가 되도록** 키를 서버가 정하고 서명에 고정하는 것이다.

**조건을 서명에 포함.** `Content-Type`을 서명에 넣으면 클라이언트는 정확히 그 타입으로만 올릴 수 있다(2-3절). 다른 값을 보내면 서명이 안 맞아 스토리지가 거부한다.

#### ③ 파일 크기·타입을 앱이 강제하기 어렵다

②의 마지막이 부분적인 답이지만, **크기는 더 까다롭다.** 단순한 presigned PUT에서는 클라이언트가 신고한 크기와 실제 올리는 크기가 다를 수 있다. 앱이 "100MB까지"라고 판단해 URL을 줬는데 클라이언트가 5GB를 올려도, 스토리지 입장에서는 서명이 유효한 정상 요청이다.

대응은 두 방향이다.

**스토리지 정책과 조건부 서명.** S3 계열에는 브라우저 폼 업로드용의 POST 방식이 따로 있고, 여기에는 **크기 범위 조건(content-length-range)을 정책에 넣어 서명**할 수 있다. 스토리지가 업로드 시점에 크기를 직접 강제하므로 이것이 가장 확실하다. PUT 방식이라면 `Content-Length`를 서명 대상 헤더에 포함시켜 정확한 크기를 강제하는 방법이 있지만, **업로드 전에 정확한 바이트 수를 알아야** 쓸 수 있다.

**업로드 완료 시점의 사후 검증.** 2-3절의 `confirmUpload`처럼 `HEAD`로 실제 크기를 확인하고, 초과했으면 **객체를 지우고 레코드를 거부 상태로 만든다.** 스토리지에 잠깐 올라갔다가 지워지는 낭비는 있지만, 앱이 최종 판단을 쥔다는 점에서 반드시 있어야 하는 방어선이다.

**타입도 같은 구조다.** `Content-Type` 헤더는 클라이언트가 보내는 값이라 서명으로 고정해도 **"내용이 실제로 그 타입인지"는 보장하지 못한다.** `image/jpeg`라고 선언하고 실행 파일을 올릴 수 있다. 그래서 내용 기반 검증은 결국 업로드 후 후처리에서 해야 한다(다음 항목).

#### ④ 바이러스 검사와 후처리를 어디서 하는가

서버 경유였다면 저장 직전에 파일 시그니처를 확인하고 스캔할 수 있었다. **presigned 방식에서는 앱이 바이트를 한 번도 못 보므로 그 지점이 사라진다.**

해법은 **검증의 시점을 옮기는 것**이다 — 업로드 전에서 업로드 후로. 그리고 검증이 끝나기 전에는 그 파일이 노출되지 않게 상태로 막는다.

```
 클라이언트 ──PUT──> [격리 영역]  quarantine/... 프리픽스 또는 별도 버킷
                          │        · 공개 읽기 권한 없음
                          │        · CDN이 이 영역을 바라보지 않음
                          │        · DB 상태는 CONFIRMED (아직 READY 아님)
                          │
                    업로드 이벤트 발행
                          │
                          v
                    ┌───────────┐
                    │  큐        │  (RabbitMQ / SQS 등)
                    └─────┬─────┘
                          │
                          v
                  ┌───────────────┐
                  │  검증 워커     │  · 매직 바이트로 실제 형식 판별
                  │               │  · 바이러스 스캔
                  │               │  · 이미지면 재인코딩 (변조 페이로드 제거)
                  │               │  · 썸네일 생성, WebP 변환
                  └───────┬───────┘
                          │
              ┌───────────┴────────────┐
              │                        │
           통과                      실패
              │                        │
              v                        v
   [서비스 영역]으로 이동        객체 삭제 + REJECTED 전이
   DB 상태 → READY              사용자에게 사유 통보
   이제부터 노출된다
```

**격리 영역과 서비스 영역을 물리적으로 나누는 것이 요점**이다. 상태 필드만으로 막으면 어딘가의 코드 한 줄이 상태 검사를 빠뜨렸을 때 미검증 파일이 노출된다. **저장 위치 자체를 나누면 그런 실수가 원천적으로 불가능해진다.**

이미지 재인코딩이 검증에 포함되는 이유도 짚어두면 좋다. 이미지 파일의 메타데이터 영역에 악성 페이로드를 숨겨두는 공격이 있는데, **디코딩해서 픽셀만 꺼낸 뒤 다시 인코딩하면 원본의 부가 데이터가 전부 사라진다.** 검증이자 정화(sanitize)인 셈이다.

#### ⑤ 고아 파일 — 양방향 정합성 문제

**이것이 presigned 설계에서 가장 놓치기 쉬운 부분**이고, 시니어 변별의 핵심이다.

DB(메타데이터)와 스토리지(실물)는 **서로 다른 시스템**이라 하나의 트랜잭션으로 묶을 수 없다. 그래서 어긋남이 **양방향으로** 생긴다.

```
[방향 A] DB에는 있는데 스토리지에는 없다
  · URL만 발급받고 업로드를 안 했다 (사용자가 취소, 브라우저 닫음)
  · 업로드하다 실패했다
  → PENDING 레코드만 영원히 남는다
  → 목록 조회에 뜨는데 클릭하면 404가 나는 유령 파일

[방향 B] 스토리지에는 있는데 DB에는 없다(또는 미확정)
  · 업로드는 성공했는데 완료 통보가 안 왔다
  · 완료 처리 중 앱이 죽었다
  · 나중에 파일을 교체하면서 옛 객체를 지우는 것을 잊었다
  → 아무도 참조하지 않는 객체가 스토리지에 쌓인다
  → 보이지 않게 스토리지 비용이 계속 늘어난다
```

**이것은 10장(결제/정합성)에서 다루는 문제와 같은 구조다.** 서로 다른 시스템에 두 번 쓰는 이상 원자성이 없으므로, **"어긋남을 없애는 것"이 아니라 "어긋남을 발견해서 수습하는 루프"를 설계하는 것**이 답이 된다. 결제 도메인의 Saga가 실패한 단계를 보상으로 메우듯, 여기서는 상태 전이와 정리 배치가 그 역할을 한다.

**대응 ① — 상태 전이로 중간 단계를 명시한다.**

```
                 ┌──────────────────────────────────────────────┐
                 │                                              │
  URL 발급     PENDING ──완료 확인(HEAD로 실물 검증)──> CONFIRMED │
                 │                                        │     │
                 │                                    검증·후처리 │
                 │                                        │     │
                 │                                        v     │
                 │                                      READY   │
                 │                                              │
                 │ N시간 경과 + 객체 없음                          │
                 v                                              │
             EXPIRED ─── 정리 배치가 레코드 삭제 ─────────────────┘

  · PENDING은 "의도만 기록된 상태"다. 사용자에게 노출되지 않는다.
  · CONFIRMED는 "실물이 있음을 확인한 상태"다. 아직 검증 전이라 노출되지 않는다.
  · READY만 노출된다.
  · ★ URL 발급 시점에 PENDING을 먼저 만드는 것이 요점이다.
    그래야 "업로드는 됐는데 DB에 흔적이 전혀 없는" 최악의 경우가 줄어든다.
```

**대응 ② — 양방향 정리 루프를 둔다.**

```sql
-- 방향 A: 오래된 PENDING을 찾아 정리한다.
-- URL 만료(5분)보다 충분히 긴 시간(예: 24시간)을 기다린 뒤 처리한다 —
-- 느린 회선의 사용자가 아직 올리고 있는 중일 수 있기 때문이다.
SELECT id, storage_key
  FROM file_record
 WHERE status = 'PENDING'
   AND created_at < now() - interval '24 hours'
 ORDER BY created_at
 LIMIT 500;
-- 각 건에 대해 스토리지에 실물이 있는지 확인한다.
--   있으면  → CONFIRMED로 되살린다 (완료 통보만 유실된 경우다)
--   없으면  → 레코드 삭제 (진짜 미완료다)
```

방향 B는 스토리지 쪽 기능을 함께 쓴다. **수명주기 규칙(lifecycle rule)**은 오브젝트 스토리지가 제공하는 "이 조건의 객체를 N일 뒤 자동으로 삭제한다"는 정책이다. 격리 영역(`quarantine/` 프리픽스)에 만료 규칙을 걸어두면, 검증을 통과해 서비스 영역으로 옮겨진 객체는 살아남고 **어떤 이유로든 옮겨지지 못한 객체는 자동으로 사라진다.** 서비스 영역의 진짜 고아는 주기적인 대사 배치로 잡는다 — 스토리지의 객체 목록과 DB의 키 목록을 대조해 참조 없는 객체를 찾는다.

**정리하면 presigned URL은 "전송 부담을 덜어내는 대신 제어와 정합성 관리라는 새 책임을 사는 거래"다.** 그 책임의 목록(완료 확인, URL 유출 방어, 조건 강제, 검증 파이프라인, 고아 정리)을 알고 도입하는지가 변별 포인트다.

### 3-3. 업로드 검증 — 신뢰 경계 밖에서 온 파일

3-2절 ④에서 다룬 내용을 검증 항목 관점에서 정리한다. **핵심 인식은 "클라이언트가 보낸 모든 값은 위조 가능하다"**는 것이다.

**확장자와 `Content-Type` 헤더는 클라이언트가 정한 문자열일 뿐이다.** `.jpg`로 끝나고 `image/jpeg`라고 선언한 실행 파일을 만드는 데는 1초도 걸리지 않는다.

**실제 형식은 파일 시그니처(매직 바이트)로 판별한다.** 대부분의 파일 형식은 맨 앞 몇 바이트에 고유한 값을 갖는다 — 그것을 읽어 선언된 타입과 일치하는지 확인한다.

**크기 상한은 두 곳에서 건다** — 발급 시점의 조건 서명(가능하면)과 완료 시점의 실물 확인(반드시).

**이미지는 재인코딩한다.** 검증이면서 동시에 정화다.

**저장 키는 서버가 만든다.** 클라이언트가 준 파일명을 그대로 키로 쓰면 경로 조작(`../../etc/...`), 다른 사용자 파일 덮어쓰기, 키 충돌이 전부 가능하다. 원본 파일명은 표시용으로 DB에만 두고, 다운로드 시 `Content-Disposition`으로 되살린다(3-6절).

### 3-4. 후처리는 비동기로 — 업로드 응답과 분리한다

썸네일 생성, 포맷 변환(WebP), 바이러스 스캔, 동영상 인코딩 같은 후처리를 **업로드 요청 안에서 동기로 처리하면 안 된다.**

```
[Before: 동기 후처리]
  완료 통보 요청 → 스캔(5초) → 썸네일 3종 생성(8초) → WebP 변환(4초) → 응답
                  총 17초

  · 사용자는 17초 동안 로딩 화면을 본다
  · 그 사이 브라우저·프록시·LB의 타임아웃에 걸릴 수 있다
  · 타임아웃 후 사용자가 재시도하면 후처리가 처음부터 다시 돈다
  · 후처리 중 하나만 실패해도 업로드 전체가 실패로 보인다
  · CPU를 많이 쓰는 작업이 API 서버에서 돌아 다른 요청의 응답 시간을 밀어낸다

[After: 비동기 후처리]
  완료 통보 요청 → 상태를 CONFIRMED로 전이 → 큐에 적재 → 즉시 응답 (수십 ms)
                                                 │
                                                 v
                                        워커가 꺼내서 처리
                                        끝나면 상태를 READY로 전이

  · 사용자는 즉시 "업로드 완료, 처리 중" 응답을 받는다
  · 처리 상태를 폴링하거나 SSE로 진행률을 받는다 (14번 문서)
  · 후처리 실패는 재시도 대상이지 업로드 실패가 아니다
  · CPU 무거운 작업이 API 서버와 분리되어 독립적으로 스케일된다
```

**상태 필드가 이 설계의 뼈대다.** `CONFIRMED`(실물은 있으나 처리 전)와 `READY`(처리 완료, 노출 가능)를 구분해 두면, 클라이언트는 그 상태를 보고 "처리 중" 표시를 하거나 원본을 임시로 보여줄 수 있다.

워커는 **멱등해야 한다.** 큐는 대개 최소 1회 전달을 보장하므로 같은 메시지를 두 번 받을 수 있고, 그때 썸네일을 두 번 만드는 것은 괜찮지만 카운터를 두 번 올리거나 알림을 두 번 보내는 것은 곤란하다.

### 3-5. 분할 업로드와 재개 (가산점 포인트)

#### 왜 큰 파일을 조각으로 나누는가

이유가 셋이다.

**첫째, 네트워크가 끊겼을 때 처음부터 다시 하지 않기 위해서다.** 이것이 가장 큰 이유다.

```
[단일 PUT으로 5GB를 올리는 경우]
  전송률 20Mbps → 5GB × 8 ÷ 20Mbps = 40,000Mbit ÷ 20 = 2,000초 ≈ 33분

  32분째에 와이파이가 끊기면?
  → 32분 동안 보낸 4.8GB가 전부 무의미해진다. 처음부터 다시.
  → 모바일 환경에서 33분 동안 한 번도 안 끊길 확률이 얼마나 될까.

[8MB 조각 640개로 나눈 경우]
  32분째에 끊기면?
  → 이미 성공한 조각들은 스토리지에 남아 있다.
  → 재개할 때 "어느 조각이 이미 올라갔는지" 조회해서 안 올라간 것만 다시 보낸다.
  → 잃는 것은 전송 중이던 조각 하나(최대 8MB)뿐이다.
```

**둘째, 병렬 전송으로 대역폭을 제대로 쓰기 위해서다.** TCP 연결 하나의 처리량은 혼잡 윈도우와 왕복 시간에 묶여 있어([10번 문서](10-keepalive-connection-pool-time-wait.md) 1-2절), 회선 대역폭이 남아도 한 연결로는 다 못 채우는 경우가 많다. **조각 여러 개를 여러 연결로 동시에 보내면** 그 상한을 넘어설 수 있다.

**셋째, 단일 요청의 크기 상한을 넘기기 위해서다.** S3 계열은 단일 PUT으로 올릴 수 있는 크기에 상한이 있다(5GB). 그보다 큰 객체는 분할 업로드가 유일한 방법이다.

#### 흐름

```
 클라이언트                  앱 서버                      스토리지
     │                        │                             │
     │ ① 분할 업로드 시작 요청  │                             │
     ├───────────────────────>│  CreateMultipartUpload      │
     │                        ├────────────────────────────>│
     │                        │<──── uploadId ──────────────┤
     │ {uploadId, 조각별 URL}  │  각 조각 번호마다 presigned   │
     │<───────────────────────┤  URL을 발급해 함께 내려준다   │
     │                        │                             │
     │ ② 조각 1 PUT (병렬)                                   │
     ├──────────────────────────────────────────────────────>│
     │<──────────── ETag_1 ──────────────────────────────────┤
     │ ② 조각 2 PUT (병렬)                                   │
     ├──────────────────────────────────────────────────────>│
     │<──────────── ETag_2 ──────────────────────────────────┤
     │   ... (실패한 조각은 그 조각만 재시도) ...              │
     │                        │                             │
     │ ③ 완료 요청            │                             │
     │   [(1,ETag_1),(2,ETag_2),...]                        │
     ├───────────────────────>│  CompleteMultipartUpload    │
     │                        ├────────────────────────────>│
     │                        │  스토리지가 조각들을 하나의   │
     │                        │  객체로 조립한다              │
     │<───────────────────────┤<────────────────────────────┤
```

**`ETag`는 각 조각의 내용에 대한 식별자**로, 스토리지가 조각을 받을 때 응답으로 돌려준다. 완료 요청에 조각 번호와 `ETag`의 목록을 함께 보내면, 스토리지가 "이 순서로 이 내용의 조각들을 이어 붙이라"는 지시로 해석한다. **번호가 순서를, `ETag`가 무결성을 담당한다.**

#### 조각 크기를 어떻게 정하는가

제약과 트레이드오프를 함께 봐야 한다. S3 계열의 제약은 이렇다 — **조각 최소 크기 5MB(마지막 조각은 예외), 최대 조각 수 10,000개.**

이 둘에서 하한이 계산으로 나온다.

```
[제약 1] 조각 수가 10,000개를 넘으면 안 된다
         → 최소 조각 크기 = 전체 크기 ÷ 10,000

  파일 100GB의 경우:
    100GB = 102,400MB
    102,400MB ÷ 10,000 = 10.24MB
    → 조각을 10.24MB 이상으로 잡아야 한다. 5MB로 잡으면 20,480개가 되어 한도 초과.

  검산: 조각 8MB로 잡으면 → 102,400 ÷ 8 = 12,800개 > 10,000 ✗
        조각 16MB로 잡으면 → 102,400 ÷ 16 = 6,400개 ≤ 10,000 ✓
```

여기에 트레이드오프가 얹힌다.

```
조각을 작게 잡으면
  ✓ 실패 시 다시 보낼 양이 적다
  ✓ 병렬도를 높이기 쉽다
  ✗ 요청 수가 많아진다 (요청마다 왕복 비용과 API 호출 요금)
  ✗ 조각 수 한도에 걸릴 수 있다

조각을 크게 잡으면
  ✓ 요청 수가 적다
  ✗ 실패 시 다시 보낼 양이 크다
  ✗ 조각 하나를 메모리에 들고 있어야 하는 클라이언트라면 메모리 부담

→ 실무 감각: 수 MB~수십 MB 범위에서 고르고,
  "전체 크기 ÷ 10,000"보다 큰지 반드시 확인한다.
  네트워크가 불안정한 환경일수록 작게, 안정적일수록 크게.
```

#### 미완성 업로드 정리 정책

**분할 업로드는 새로운 종류의 고아를 만든다.** 시작해놓고 완료 요청을 보내지 않으면, 이미 올린 조각들이 스토리지에 남는다. **그리고 이 조각들은 객체 목록 조회에 나타나지 않는다** — 아직 객체가 아니라 "조립 대기 중인 부품"이기 때문이다. 그래서 **보이지 않는 채로 스토리지 요금만 계속 나가는** 상태가 된다.

대응은 수명주기 규칙이다. 오브젝트 스토리지는 **"N일 이상 완료되지 않은 분할 업로드를 자동으로 폐기하라"**는 규칙을 지원한다(S3의 `AbortIncompleteMultipartUpload`). 대용량 업로드를 쓰는 버킷이라면 **이 규칙을 걸어두는 것이 사실상 필수**다.

```
[반드시 걸어야 하는 수명주기 규칙 세 가지]

  ① 미완성 분할 업로드 폐기        7일 후    → 보이지 않는 조각 비용 방지
  ② 격리 프리픽스 객체 만료         1일 후    → 검증 실패/누락 파일 정리 (3-2절 ④)
  ③ 임시 프리픽스 객체 만료         N일 후    → 고아 객체 정리 (3-2절 ⑤)
```

### 3-6. 다운로드의 Range 요청과 응답 헤더

#### Range 요청 — 이어받기와 구간 탐색의 근거

**Range 요청은 "파일 전체가 아니라 이 바이트 구간만 주세요"라고 요청하는 HTTP 기능**이다.

```http
GET /files/movie.mp4 HTTP/1.1
Host: cdn.example.com
Range: bytes=0-1023
```

서버가 지원하면 **`206 Partial Content`**로 답한다. 200이 아니라는 점이 중요하다 — "요청한 것을 다 줬다"가 아니라 "일부만 줬다"는 뜻이기 때문이다.

```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 0-1023/5242880
Content-Length: 1024
Accept-Ranges: bytes
Content-Type: video/mp4
```

`Content-Range: bytes 0-1023/5242880`을 읽는 법은 이렇다 — **"전체 5,242,880바이트 중 0번부터 1023번까지"**를 줬다는 뜻이다. 슬래시 뒤가 전체 크기이므로, 클라이언트는 첫 응답만으로 전체 크기를 알 수 있다.

`Accept-Ranges: bytes`는 **"나는 바이트 단위 Range 요청을 지원한다"**는 서버의 선언이다. 이 헤더는 일반적인 200 응답에도 붙일 수 있고, 그래야 클라이언트가 "이 서버라면 이어받기가 되겠다"를 미리 안다. 지원하지 않으면 `Accept-Ranges: none`을 보내거나 헤더를 생략한다.

이것이 만드는 두 기능이 실무에서 중요하다.

**① 이어받기(resume).** 300MB 중 180MB를 받고 끊겼다면, 다시 시작할 때 `Range: bytes=188743680-`을 보내 나머지만 받는다. 다운로드 관리자와 모바일 앱의 파일 다운로더가 하는 일이 정확히 이것이다.

**② 미디어 구간 탐색(seek).** 사용자가 1시간짜리 영상의 40분 지점으로 점프하면, 플레이어는 "40분 지점의 데이터가 파일의 몇 바이트쯤인지" 계산해 그 구간만 Range로 요청한다. **Range를 지원하지 않으면 앞에서부터 40분 분량을 전부 받아야 하므로 사실상 탐색이 불가능하다.** 브라우저의 `<video>` 태그가 서버에 Range 지원을 기대하는 이유다.

여기에 **`If-Range`**를 얹으면 안전해진다. 이어받는 사이에 서버의 파일이 바뀌었다면, 앞부분(옛 파일)과 뒷부분(새 파일)이 섞인 깨진 파일이 만들어진다. `If-Range`에 첫 응답에서 받은 `ETag`를 실어 보내면, **서버가 파일이 그대로일 때만 206으로 부분 응답을 주고 바뀌었으면 200으로 전체를 새로 준다.** 클라이언트는 그것을 보고 처음부터 다시 받는다.

요청한 범위가 파일 크기를 벗어나면 **`416`**(Range Not Satisfiable)이 나온다.

**그리고 이것이 서버 직접 서빙을 버릴 또 하나의 이유다.** Range 요청을 직접 구현하려면 헤더 파싱, 여러 구간 요청 처리, `If-Range` 조건 판정, 경계 검사, 206/416 분기를 전부 만들어야 한다. **오브젝트 스토리지와 CDN은 이것을 기본으로 지원한다** — presigned GET URL로 넘기면 우리가 만들 것이 없다.

#### `Content-Disposition` — 파일명과 표시 방식

응답 헤더 `Content-Disposition`은 **브라우저에게 "이 응답을 화면에 표시할지, 파일로 저장할지"와 "저장한다면 어떤 이름으로 할지"**를 알려준다.

```http
Content-Disposition: inline                          ← 브라우저에서 바로 표시 (이미지, PDF)
Content-Disposition: attachment                      ← 다운로드 (파일명은 브라우저가 추측)
Content-Disposition: attachment; filename="report.pdf"   ← 다운로드 + 파일명 지정
```

**한글 파일명에서 함정이 나온다.** HTTP 헤더는 전통적으로 ASCII 범위를 전제하므로, `filename="분기보고서.pdf"`처럼 비ASCII 문자를 그냥 넣으면 브라우저마다 다르게 해석해 **깨진 이름으로 저장되거나 무시된다.**

표준 해법은 **`filename*`(별표가 붙은 파라미터)**이다. 문자 인코딩을 명시하고 퍼센트 인코딩으로 표현한다.

```http
Content-Disposition: attachment; filename="download.pdf"; filename*=UTF-8''%ED%95%9C%EA%B8%80.pdf
```

읽는 법은 이렇다. `UTF-8''` 부분이 **"인코딩은 UTF-8이고, 언어 지정은 생략"**이라는 뜻이고(작은따옴표 두 개 사이가 언어 자리다), 그 뒤가 UTF-8 바이트를 퍼센트 인코딩한 값이다. 위 예시의 `%ED%95%9C%EA%B8%80.pdf`는 `한글.pdf`다.

**둘을 함께 주는 것이 정석이다.** `filename*`을 이해하는 브라우저는 그쪽을 쓰고, 이해하지 못하는 오래된 클라이언트는 ASCII로 된 `filename` 값으로 폴백한다.

직접 만들 필요는 없다. Spring이 규칙에 맞게 조립해 준다.

```java
// Before: 한글 파일명이 깨지거나 무시된다
response.setHeader("Content-Disposition",
        "attachment; filename=\"" + originalName + "\"");
```

```java
// After: filename과 filename*을 규칙에 맞게 함께 생성한다
ContentDisposition disposition = ContentDisposition.attachment()
        // 두 번째 인자로 문자셋을 주면 filename*= 형태를 함께 만들어 준다.
        .filename(originalName, StandardCharsets.UTF_8)
        .build();

return ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, disposition.toString())
        .contentLength(meta.size())
        .body(body);
```

presigned URL 방식이라면 이 헤더를 **서명 시점에 지정**해서 스토리지가 응답에 붙이게 한다(2-4절의 `responseContentDisposition`). 저장 키는 UUID여도 사용자에게는 원본 파일명으로 저장되게 만드는 방법이다.

#### 압축은 다시 걸지 않는다

JPEG, PNG, MP4, ZIP처럼 **이미 압축된 포맷에 gzip을 다시 거는 것은 낭비**다. 압축률이 거의 0인데 CPU만 쓰고, 경우에 따라 크기가 오히려 늘어난다. 압축이 이득인 것은 텍스트 계열(JSON, HTML, CSS, JS)이다. 판단 기준은 [21번 문서](21-response-compression-tradeoffs.md)와 같다.

## 4. 꼬리질문 대비 포인트

### "presigned URL 방식의 단점이나 주의점은 없나요?" (시니어 변별 포인트)

**"전송 부담을 덜어내는 대신 제어와 정합성 관리라는 새 책임을 사는 거래"**라는 프레임으로 답한다. 구체적으로 다섯 가지다.

**① 앱이 업로드 완료를 모른다.** 파일이 스토리지로 직접 가므로 앱은 그 일이 일어났는지조차 모른다. 클라이언트의 완료 콜백은 브라우저가 닫히거나 네트워크가 끊기면 오지 않고, 온다 해도 그 말을 그대로 믿을 수 없다. 그래서 **스토리지에 `HEAD`로 실물을 직접 확인하거나, 스토리지 이벤트 통지를 받는다.** 실무에서는 둘 다 걸고 — 콜백으로 사용자 응답을 빠르게 주고 이벤트를 최종 진실로 삼는다 — 그 처리를 멱등하게 만든다.

**② 클라이언트가 URL을 남에게 넘길 수 있다.** 서명 안에 "누가 쓸 수 있는지"는 들어 있지 않으므로 URL을 가진 누구나 쓸 수 있다. 방어는 **짧은 만료(업로드는 몇 분)**, **동작과 키를 서명에 고정**(업로드용 URL로 다른 파일을 덮어쓸 수 없게), **`Content-Type` 같은 조건을 서명에 포함**이다.

**③ 크기·타입을 앱이 강제하기 어렵다.** 단순 PUT 서명에서는 클라이언트가 신고한 크기와 실제 올리는 크기가 다를 수 있다. 대응은 두 방향 — **스토리지가 강제하게 하는 것**(크기 범위 조건을 정책에 넣어 서명하는 POST 방식, 또는 `Content-Length`를 서명 대상 헤더에 포함)과 **완료 시점의 사후 검증**(`HEAD`로 실제 크기 확인, 초과면 객체 삭제 + 거부 상태). 타입은 헤더를 고정해도 내용까지 보장하지 못하므로 결국 후처리에서 매직 바이트로 판별해야 한다.

**④ 바이러스 검사와 후처리 지점이 사라진다.** 앱이 바이트를 못 보므로 저장 직전 검사가 불가능하다. 해법은 **검증 시점을 업로드 후로 옮기고, 그 사이 노출되지 않게 막는 것**이다 — 격리 영역(별도 프리픽스나 버킷)에 올리고, 업로드 이벤트로 검증 워커를 깨우고, 통과한 것만 서비스 영역으로 옮긴다. **상태 필드만으로 막지 않고 저장 위치를 물리적으로 나누는 것**이 요점이다.

**⑤ 고아 파일 — 양방향 정합성.** DB와 스토리지는 다른 시스템이라 한 트랜잭션으로 묶을 수 없어 어긋남이 양방향으로 생긴다. **"URL만 발급되고 안 올라간 경우"**는 PENDING 레코드만 남고, **"올라갔는데 완료 통보가 안 온 경우"**는 참조 없는 객체가 남는다. 대응은 `PENDING → CONFIRMED → READY` 상태 전이(URL 발급 시점에 PENDING을 먼저 만든다)와 양방향 정리 루프다 — 오래된 PENDING을 찾아 스토리지에 실물이 있으면 되살리고 없으면 지우는 배치, 그리고 격리·임시 프리픽스에 건 수명주기 규칙. 분할 업로드를 쓴다면 **미완성 업로드 자동 폐기 규칙**도 필수다(조각들은 객체 목록에 안 보이는데 요금은 나간다).

**이 다섯을 인지하고 도입하는지가 변별 포인트**다. "presigned URL을 쓰면 됩니다"에서 멈추면 절반의 답이다.

### "그래도 서버 경유 업로드를 유지해야 하는 경우가 있을까요?"

**"기본값은 우회, 예외 조건이 있을 때만 경유"**로 정리하되, 그 예외를 구체적으로 말할 수 있어야 한다.

**① 저장 전 동기 검증·변환이 필수인 경우.** 업로드 즉시 파싱해서 결과를 응답에 담아야 하는 경우(정산 파일을 올리면 그 자리에서 항목 수와 합계를 보여줘야 하는 화면), 또는 검증 실패 시 즉시 반려해야 하는 문서 심사가 여기 해당한다. presigned 방식에서는 검증이 업로드 후 비동기가 되므로 "올렸는데 나중에 반려됐습니다"라는 UX가 되는데, 그것이 허용되지 않는 요구가 있다.

**② 스토리지를 외부에 직접 노출할 수 없는 보안 요건.** 폐쇄망, 또는 "모든 데이터 접근은 애플리케이션의 감사 로그를 거쳐야 한다"는 규정이 있는 환경이다. presigned URL은 스토리지 엔드포인트를 클라이언트에게 노출하는 것이므로 이 요건과 충돌한다.

**③ 파일이 작고 빈도가 낮아 우회 설계의 복잡도가 이득을 넘는 경우.** 프로필 이미지 수백 KB 수준이면 스트리밍 경유로 충분하다. presigned 방식은 API가 둘로 늘고(발급 + 완료), 상태 전이가 생기고, 정리 배치가 필요하다 — **작은 파일에 이 복잡도를 지불할 이유가 없다.**

다만 반드시 덧붙일 것이 있다. **규모가 커지면 경유 방식이 서버 용량 계획을 지배하게 된다.** 프로필 이미지도 사용자가 100만 명이 되고 이미지 조회가 초당 수천 건이 되면 이야기가 달라진다. **"지금 규모에서는 경유가 맞지만, 어느 지점에서 우회로 전환할지"를 미리 정해두는 것**이 설계 감각이다.

### "업로드가 10MB까지는 되는데 그 이상은 실패합니다. 어디를 보나요?"

**크기 의존적 실패는 코드 버그보다 계층별 제한의 신호다.** 코드는 파일 크기를 보고 분기하지 않지만, 인프라 설정은 정확히 크기로 자른다.

**먼저 사용자가 받은 상태 코드를 확인한다.** 여기서 방향이 갈린다.

**`413`이면 크기 제한이다.** 바깥에서 안쪽으로 순서대로 본다 — CDN/LB의 본문 크기 한도, Nginx `client_max_body_size`(기본 1MB라 가장 흔한 범인), Spring `max-file-size`와 `max-request-size`(기본 1MB / 10MB). **10MB에서 걸린다면 `max-request-size` 기본값 10MB가 유력한 용의자다.**

**`504`나 커넥션 끊김이면 타임아웃이다.** 전송 시간이 어느 계층의 상한을 넘은 것이다. Nginx `client_body_timeout`, LB의 유휴 타임아웃이 후보다. **이 경우 "느린 회선의 사용자만" 재현된다**는 특징이 있다 — 같은 파일도 빠른 회선에서는 상한 안에 들어오기 때문이다. 제보자의 네트워크 환경을 물어보면 빠르게 좁혀진다.

**`500`이면 앱 예외일 가능성이 있다.** OOM(1-2절), 디스크 부족(1-3절)이 후보다.

**그리고 결정적 단서 하나.** **앱 로그에 아무것도 없으면 요청이 앱에 도달하기 전에 반려된 것**이다. 그러면 앱 설정은 볼 필요가 없고 Nginx의 error log부터 봐야 한다 — `client intended to send too large body` 같은 문구가 바로 답을 준다([13번 문서](13-nginx-tomcat-timeout-buffer-mismatch.md) 4절).

근본적으로는 **파일 크기 요구사항이 바뀔 때 전 계층 한도를 함께 바꾸는 체크리스트**가 있어야 재발을 막는다. 그리고 presigned URL 방식이라면 이 계층 스택을 아예 안 지나므로 **이 문제 자체가 없어진다**는 점까지 말하면 좋다.

### "다운로드 트래픽이 몰리면 어떻게 확장하나요?"

**서버 증설이 아니라 경로 재설계가 답이다.**

먼저 왜 서버 증설이 답이 아닌지 짚는다. 서버 직접 서빙은 같은 바이트를 두 번 나른다 — **스토리지 → 서버**, **서버 → 클라이언트**. 그래서 서버의 대역폭이 실질적으로 절반이 되고, 클라우드라면 전송 요금도 두 번 낸다. 여기에 전송 시간 내내 커넥션과 스레드가 묶인다(1-4절). **이 구조에서는 서버를 늘려도 대역폭이라는 물리적 한계에 같은 비율로 부딪힌다.**

구조적인 답은 **전송을 서버 밖으로 내보내는 것**이다.

**① 오브젝트 스토리지 + CDN으로 옮기고 서버는 signed URL 발급만 한다.** 앱 서버가 처리하는 것은 수 KB짜리 JSON 요청이 되고, 파일 바이트는 CDN 엣지가 나른다.

**② 이미지처럼 재사용률이 높은 불변 콘텐츠는 CDN 히트율이 대부분의 트래픽을 흡수한다.** 여기서 중요한 것이 **버전드 URL + 긴 캐시**다 — 파일 내용이 바뀌면 URL도 바뀌게 만들면(경로에 해시나 버전을 넣는다), 같은 URL은 영원히 같은 내용이므로 캐시 만료를 아주 길게 잡아도 안전하다. 캐시 무효화라는 어려운 문제를 "무효화할 일이 없게" 설계로 없앤 것이다.

**③ 비공개·유료 파일은 signed URL의 만료로 접근을 통제한다.** CDN 위에서도 권한 판단은 여전히 우리 서버가 한다 — 서버가 권한을 확인하고 짧은 만료의 signed URL을 발급하며, 전송은 엣지가 한다.

**④ Range 요청도 스토리지/CDN이 기본 지원**하므로 이어받기와 구간 탐색이 자동으로 따라온다(3-6절).

**정리하면 "다운로드 확장"의 답은 서버 증설이 아니라 경로 재설계이고, 그 원리는 "권한 판단은 서버가, 전송은 엣지가"다.**

### "스트리밍 다운로드 구현에서 흔한 실수는?"

**① 응답이 시작된 뒤에는 에러 처리가 불가능하다.** 스트림을 열어 흘리기 시작한 뒤 중간에 예외가 나면, 이미 `200 OK`와 바디 일부가 클라이언트에 나간 상태다. **이제 와서 `404`나 `500`으로 바꿀 방법이 없다.** 클라이언트는 "성공했는데 파일이 잘린" 상태를 받는다. 대응은 **전송을 시작하기 전에 존재·권한 검증을 전부 끝내는 것**이다(1-2절 After 코드의 `getForDownload` 호출이 바디 람다 바깥에 있는 이유다).

**② try-with-resources 누락으로 인한 핸들 누수.** 전송 중 클라이언트가 끊으면 쓰기에서 예외가 나는데, 그때 저장소 스트림을 닫지 않으면 파일 핸들이나 HTTP 커넥션이 새어 나간다. **정상 종료 경로가 아니라 예외 경로에서 새기 때문에** 평소에는 안 보이다가 부하 상황에서 드러난다.

**③ 느린 클라이언트가 전송 내내 스레드를 점유한다.** 블로킹 I/O에서는 전송 속도가 클라이언트의 속도에 묶이므로, 26분짜리 전송이 스레드를 26분 동안 잡는다(1-4절). `StreamingResponseBody`를 쓰면 요청 스레드는 놓아주지만 **태스크 실행자의 스레드로 옮겨갈 뿐 사라지지 않는다.** Nginx의 응답 버퍼링이 어느 정도 완충해 주지만(빠른 로컬 전송으로 WAS를 해방시키고 Nginx가 느린 클라이언트를 상대한다), **대용량 응답은 Nginx의 버퍼를 넘겨 디스크 임시 파일로 스풀되므로 이번엔 Nginx의 디스크 I/O가 병목이 된다.** 전송량이 많다면 결국 CDN/스토리지 직접 서빙으로 옮기는 것이 답이다.

**④ `Content-Length`를 안 주면 진행률과 재개가 어려워진다.** 크기를 모른 채 흘리면 청크 전송으로 나가고, 클라이언트는 전체 크기를 모르므로 진행률 퍼센트를 계산할 수 없다. **크기를 아는 경우에는 반드시 명시한다.**

**⑤ Range 요청을 무시한다.** `Range` 헤더가 왔는데 그냥 `200`으로 전체를 내려주면, 클라이언트의 이어받기와 미디어 탐색이 동작하지 않는다. 직접 구현할 계획이 없다면 **`Accept-Ranges: none`을 명시해 클라이언트가 헛되이 시도하지 않게** 하고, 필요하다면 스토리지/CDN 직접 서빙으로 옮기는 것이 정직한 선택이다.

## 한 줄 요약

대용량 파일 설계의 요체는 "경로"다 — 서버를 지나야 한다면 메모리 사용이 파일 크기에 비례하지 않게 스트리밍하고(그리고 Spring은 임계값 초과분을 디스크 임시 파일로 이미 내려두었다는 사실까지 알고 그 볼륨을 관리하고), 가능하다면 presigned URL로 파일 바이트가 애플리케이션 서버를 아예 우회하게 만들어 서버는 권한 검증·URL 발급·메타데이터 확정이라는 제어만 맡는다 — 그 대가로 완료 확인(스토리지 이벤트 또는 `HEAD` 검증), URL 유출 방어(짧은 만료 + 조건 서명), 검증·후처리의 비동기 파이프라인화, `PENDING → CONFIRMED → READY` 상태 전이와 양방향 고아 정리라는 새 책임을 지며, 여기에 계층별 크기·타임아웃 정합, Range 요청 기반 이어받기·구간 탐색, 분할 업로드와 미완성 업로드 정리까지 갖추면 전송량이 늘어도 서버 용량 계획이 흔들리지 않는 구조가 된다.
