# 대용량 파일 업로드/다운로드 — 데이터가 흐르는 경로 자체를 설계하기

> 핵심 관전 포인트: **대용량 파일 처리의 원칙은 두 단계다. 첫째,
> 파일을 서버 메모리에 통째로 올리지 않는다 — 요청 스트림에서 저장소로
> 조각 단위로 흘려보내는 스트리밍이 기본이고, 통째로 읽는 코드는 파일
> 크기 × 동시 요청 수만큼 힙을 먹다가 OOM으로 죽는다. 둘째, 한 발 더
> 나아가 파일이 애플리케이션 서버를 아예 거치지 않게 한다 — 업로드는
> presigned URL로 클라이언트가 오브젝트 스토리지에 직접 올리고,
> 다운로드는 CDN + signed URL로 엣지가 대신 내려준다. 서버는 권한 검증과
> URL 발급, 완료 후 메타데이터 처리만 맡는다. 여기에 계층별 크기/타임아웃
> 설정 정합(Nginx `client_max_body_size` 등), 업로드 후 비동기 후처리,
> 다운로드의 Range 지원까지가 실무 고려사항의 전체 그림이다.**

---

## 0. 질문 + 의도

**질문**: "대용량 파일(이미지) 업로드/다운로드 시 서버 설계 고려사항은?
(스트리밍, presigned URL)"

**출제 의도**: 파일을 서버 메모리에 통째로 올리는 코드는 파일이 크면
OOM이다. 스트리밍과 presigned URL(서버를 우회시키는 설계)을 아는지 —
요청 처리 코드 한 줄이 아니라 **데이터가 흐르는 경로 자체를 설계하는
능력**을 확인하는 질문이다.

## 1. 문제의 본질 — "파일이 어디를 거쳐 흐르는가"

일반 API 응답은 수 KB라 어디를 거치든 문제가 없다. 파일이 수십 MB~수 GB가
되는 순간, **경로 위의 모든 지점이 병목·장애 후보**가 된다: 서버 힙
(버퍼링하면 OOM), 요청 스레드(전송 시간 내내 점유), 프록시 버퍼(디스크
스풀링), 각 계층의 크기 제한과 타임아웃. 그래서 이 질문의 답은
"코드를 어떻게 짤까"가 아니라 "파일을 어느 경로로 흘릴까"에서 시작한다.

### 1단계 원칙: 통째로 읽지 말고 스트리밍하라

```java
// Before: 파일 전체를 byte[]로 힙에 적재 — 200MB 파일 × 동시 50건 = 10GB 힙
@PostMapping("/upload")
public void upload(@RequestParam MultipartFile file) throws IOException {
    byte[] bytes = file.getBytes();          // 여기서 파일 전체가 메모리에 올라옴
    storage.save(bytes);                     // 저장 끝날 때까지 전부 유지 → OOM 위험
}

// After: 입력 스트림을 저장소로 조각 단위로 흘려보냄 — 메모리 사용은 버퍼 크기로 고정
@PostMapping("/upload")
public void upload(@RequestParam MultipartFile file) throws IOException {
    try (InputStream in = file.getInputStream()) {
        storage.save(in, file.getSize());    // 수 KB 버퍼로 read→write 반복
    }                                        // 파일이 1GB여도 메모리 점유는 일정
}
```

다운로드도 대칭이다 — 파일을 `byte[]`로 읽어 응답 바디에 넣지 말고,
저장소의 스트림을 응답 스트림으로 이어 붙인다(Spring이라면
`InputStreamResource`/`StreamingResponseBody`). 핵심 문장은 하나다:
**"메모리 사용량이 파일 크기에 비례하면 잘못된 설계, 버퍼 크기로
고정되면 올바른 설계."**

다만 스트리밍을 해도 남는 비용이 있다 — 전송이 서버를 **통과**하는 동안
대역폭과 커넥션, (블로킹 I/O라면) 스레드를 계속 쓴다. 느린 회선의
사용자가 1GB를 받는 30분 동안 그 자원이 잡혀 있다. 이것이 2단계로
가는 이유다.

## 2. 2단계 원칙: 서버를 경유시키지 말라 — presigned URL

**presigned URL(서명된 URL)**은 오브젝트 스토리지(S3 등)가 "이 URL로
제한 시간 안에, 지정된 조건으로 PUT/GET 해도 좋다"고 미리 서명해 준
일회성 출입증이다. 파일 바이트는 클라이언트 ↔ 스토리지가 직접 주고받고,
애플리케이션 서버는 **제어(권한 검증, URL 발급, 메타데이터)만** 담당한다.

업로드 흐름:

```text
1. 클라이언트 → 서버:   "profile.jpg 올릴게요" (파일명, 크기, 타입)
2. 서버:               권한 확인 → 저장 키 결정 → presigned PUT URL 발급 (만료 수분)
3. 클라이언트 → 스토리지: 발급받은 URL로 파일 직접 PUT  ← 파일 바이트는 서버를 안 거침
4. 클라이언트 → 서버:   "업로드 완료" 알림 (또는 스토리지 이벤트 통지)
5. 서버:               스토리지에 실제 객체 존재/크기 확인 후 DB에 메타데이터 확정
```

다운로드는 방향만 반대다 — 서버가 권한을 확인하고 presigned GET URL
(또는 CDN의 signed URL)을 발급하면, 전송은 스토리지/CDN 엣지가 한다.
이미지처럼 여러 사용자가 반복 조회하는 콘텐츠는 CDN 캐시까지 얹는 것이
정석이다(권한 판단은 서버가, 전송은 엣지가 — CDN 문서와 같은 원리).

이 설계가 답의 중심인 이유: 파일 전송이라는 **가장 무거운 일**이
애플리케이션 서버의 용량 계획에서 통째로 빠진다. 서버는 가벼운 제어
요청만 처리하므로 파일 트래픽이 10배가 되어도 서버 증설이 필요 없다.

## 3. 실무 고려사항 — 경로 위 계층 전부를 점검한다

### ① 계층별 크기 제한·타임아웃 정합

파일은 클라이언트 → LB → Nginx → WAS → 스토리지를 지난다. 각 계층에
독립적인 크기 제한과 타임아웃이 있고, **가장 작은 값이 실질 한도**다.
Nginx `client_max_body_size`(초과 시 413 — 앱 로그에는 아무것도 안 남는다),
Spring `max-file-size`/`max-request-size`, LB의 유휴 타임아웃(느린 회선
업로드가 전송 중 끊김) 등. "업로드가 특정 크기부터만 실패한다"는 유령
현상의 정체가 대부분 이것이다. presigned URL 설계의 숨은 장점이 여기에도
있다 — 파일이 이 계층 스택을 아예 안 지나므로 정합 문제 자체가 사라진다.

### ② 업로드 검증 — 신뢰 경계 밖에서 온 파일

확장자·`Content-Type` 헤더는 클라이언트가 보낸 값이라 위조 가능하다.
파일 시그니처(매직 바이트) 검증, 크기 상한, 이미지라면 재인코딩(변조
페이로드 제거 효과)까지가 방어선이다. presigned URL 방식에서는 발급 시
조건(Content-Type, 크기 범위)을 서명에 포함해 스토리지가 강제하게 하고,
정밀 검증은 업로드 완료 후 후처리에서 수행한다.

### ③ 후처리는 비동기로 — 업로드 응답과 분리

썸네일/리사이징, 포맷 변환(WebP), 바이러스 스캔 같은 후처리를 업로드
요청 안에서 동기로 하면 응답이 수십 초로 늘어지고 타임아웃·재시도
문제를 부른다. 업로드 완료 이벤트(스토리지 이벤트 통지 또는 완료 API)를
받아 **큐에 넣고 워커가 비동기 처리**하는 것이 정석이다. 처리 전에는
원본 또는 "처리 중" 상태로 응답하도록 상태 필드를 둔다.

### ④ 대형 파일 업로드의 분할과 재개 (가산점 포인트)

수백 MB~GB급은 한 번의 PUT이 실패하면 전체를 다시 올려야 한다.
**멀티파트 업로드**(파일을 조각으로 나눠 병렬 업로드, 실패한 조각만
재시도, 마지막에 조립)로 재개 가능성과 속도를 확보한다. 조각별
presigned URL을 발급하는 형태로 서버 우회 설계와도 결합된다.

### ⑤ 다운로드의 Range 지원과 응답 헤더

대용량 다운로드는 중단 후 이어받기(resume)와 미디어 구간 탐색을 위해
**Range 요청(`Range: bytes=...` → 206 Partial Content)**을 지원해야
한다. 오브젝트 스토리지/CDN은 기본 지원하므로 — 서버 직접 서빙을
버릴 또 하나의 이유다. 파일명·표시 방식은 `Content-Disposition`으로
제어하고, 이미 압축된 포맷(JPEG/PNG/MP4)에 gzip을 다시 거는 낭비는
피한다.

### ⑥ 정합성 뒷정리 — 고아 파일과 상태 관리

presigned 방식은 "URL만 발급받고 안 올리는" 경우와 "올렸지만 완료
알림이 안 오는" 경우가 생긴다. DB 메타데이터를 `PENDING` → 완료 확인 후
`ACTIVE`로 전이시키고, 오래된 `PENDING`과 참조 없는 객체를 주기적으로
청소(수명주기 정책)하는 운영 루프까지 언급하면 설계가 완결된다.

## 4. 꼬리질문 대비 포인트

### "presigned URL 방식의 단점이나 주의점은 없나요?" (시니어 변별 포인트)

① **서버가 바이트를 못 본다** — 업로드 시점의 내용 검증(시그니처, 스캔)이
불가능해지므로 발급 시 조건 서명 + 완료 후 비동기 검증으로 검증 시점을
옮겨야 하고, 검증 전 파일이 노출되지 않게 상태 관리가 필요하다.
② **완료를 클라이언트 신고에 의존하면 안 된다** — 신고 누락/허위에
대비해 스토리지에 객체 존재·크기를 확인하거나 스토리지 이벤트 통지를
받는다. ③ **URL 유출 창구** — 만료를 짧게(수분) 잡고, 업로드 URL은
키·조건을 고정해 다른 용도로 못 쓰게 한다. ④ **고아 파일 청소** 같은
운영 루프가 추가된다. 즉 전송 부담을 덜어내는 대신 "제어와 정합성
관리"라는 새 책임을 사는 트레이드오프이며, 이를 인지하고 도입하는지가
변별 포인트다.

### "그래도 서버 경유 업로드를 유지해야 하는 경우가 있을까요?"

① 저장 전 **동기 검증·변환이 필수**인 경우(예: 즉시 반려해야 하는 문서
심사, 업로드 즉시 파싱해 응답에 결과를 담아야 하는 경우).
② 스토리지를 외부에 직접 노출할 수 없는 보안 요건·폐쇄망.
③ 파일이 작고 빈도가 낮아 우회 설계의 복잡도가 이득을 넘는 경우 —
프로필 이미지 수백 KB 수준이면 스트리밍 경유로 충분할 수 있다.
"기본값은 우회, 예외 조건이 있을 때만 경유"로 정리하되 규모가 커지면
경유 방식이 서버 용량 계획을 지배하게 된다는 점을 함께 말한다.

### "업로드가 10MB까지는 되는데 그 이상은 실패합니다. 어디를 보나요?"

크기 의존 실패는 코드 버그보다 **계층별 제한** 신호다. 응답 코드부터
본다 — 413이면 크기 제한(Nginx `client_max_body_size`, WAS/프레임워크
max-file-size를 경로 순서대로), 504/커넥션 끊김이면 타임아웃(전송 시간이
LB·프록시 타임아웃 초과 — 느린 회선일수록 큰 파일에서만 재현).
"앱 로그에 아무것도 없으면 요청이 앱에 도달하기 전 계층에서 반려된 것"
이라는 원칙으로, 클라이언트 → LB → Nginx → WAS 순서로 각 계층의
제한/로그를 확인한다.

### "다운로드 트래픽이 몰리면 어떻게 확장하나요?"

서버 직접 서빙이라면 대역폭·커넥션이 곧 병목이므로, 구조 답은
**전송을 서버 밖으로**: 오브젝트 스토리지 + CDN으로 옮기고 서버는
signed URL 발급만 한다. 이미지처럼 재사용률 높은 불변 콘텐츠는 CDN
히트율이 대부분의 트래픽을 흡수한다(버전드 URL + 긴 캐시). 유료·비공개
파일은 signed URL 만료로 접근을 통제한다. 즉 "다운로드 확장"의 답은
서버 증설이 아니라 경로 재설계다.

### "스트리밍 다운로드 구현에서 흔한 실수는?"

① 스트림을 열어놓고 응답 도중 예외가 나면 이미 200과 바디 일부가
나간 상태라 에러 처리가 불가능하다 — 시작 전에 존재·권한 검증을 끝낸다.
② try-with-resources 누락으로 커넥션/파일 핸들 누수.
③ 블로킹 I/O에서 느린 클라이언트가 전송 내내 요청 스레드를 점유
(slow client) — 전송량이 많다면 이 자체가 스레드 풀 고갈 요인이므로,
프록시 버퍼링을 활용하거나 결국 CDN/스토리지 직접 서빙으로 옮긴다.
④ `Content-Length`를 못 주면 진행률 표시·재개가 어려워지므로 크기를
아는 경우 명시한다.

## 한 줄 요약

대용량 파일 설계의 요체는 "경로"다 — 서버를 지나야 한다면 메모리 사용이
파일 크기에 비례하지 않게 스트리밍하고, 가능하다면 presigned URL과
CDN으로 파일 바이트가 애플리케이션 서버를 아예 우회하게 만들어 서버는
권한·발급·메타데이터라는 제어만 맡는다 — 여기에 계층별 크기/타임아웃
정합, 비동기 후처리, 완료 확인과 고아 파일 청소까지 갖추면 전송량이
늘어도 서버 용량 계획이 흔들리지 않는 구조가 된다.
