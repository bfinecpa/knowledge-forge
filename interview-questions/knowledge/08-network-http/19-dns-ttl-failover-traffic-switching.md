# DNS TTL과 배포·failover — "DNS 바꿨는데 왜 아직 옛 서버로 오지?"의 원리

> 핵심 관전 포인트: **DNS 전환은 스위치가 아니라 물결이다. TTL은 "이
> 응답을 최대 얼마나 캐시해도 되는가"의 상한일 뿐이고, 전 세계에 흩어진
> 캐시(브라우저, OS, 공유기, ISP 리졸버, JVM, 그리고 DNS를 아예 다시
> 안 보는 keep-alive 커넥션)는 각자 자기가 조회한 시점부터 만료를
> 센다. 심지어 TTL을 무시하고 더 오래 캐시하는 리졸버도 있어, 전환
> 후에도 옛 주소로 가는 긴 꼬리 트래픽이 남는다. 그래서 DNS 전환
> 작업은 "사전 TTL 인하 → 전환 → 옛 서버 유예 운영"의 절차로 설계해야
> 하고, 초 단위 전환이 필요한 failover는 DNS가 아니라 IP가 바뀌지 않는
> 지점(LB, VIP, anycast) 뒤에서 해야 한다.**

---

## 0. 질문 + 의도

**질문**: "DNS TTL과 배포/failover의 관계 — DNS 기반 트래픽 전환의 함정은?"

**출제 의도**: "DNS 바꿨는데 왜 아직 옛 서버로 오지?"라는, 전환 작업
때마다 등장하는 현상. 캐싱 계층이 곳곳에 있는 인터넷의 실제 동작을
아는지 — 그리고 그 이해가 재해 복구 계획의 현실성(DNS failover로 RTO를
맞출 수 있다는 계획이 진짜 성립하는지)을 검증할 수 있는 수준인지 본다.

## 1. TTL의 실제 동작 — 상한이지 동기화 신호가 아니다

DNS 조회는 한 곳에서 일어나지 않는다. 사용자와 권위 서버(레코드의
원본을 가진 DNS 서버) 사이에 캐시가 사슬로 늘어서 있다:

```
브라우저 캐시 → OS 캐시 → 공유기 → ISP/공용 리졸버 → 권위 DNS 서버
```

TTL은 권위 서버가 응답에 붙여 보내는 "이 답을 최대 이만큼은 다시
묻지 말고 써도 된다"는 **유효기간**이다. 여기서 흔한 착각이 생긴다 —
"TTL이 300초니까 레코드를 바꾸면 300초 뒤엔 전부 새 주소를 쓰겠지".

실제로는 각 캐시가 **자기가 조회한 시점부터** 카운트다운한다. 전환
직전에 조회해간 리졸버는 전환 후에도 남은 TTL 동안 옛 답을 주고, 그
리졸버를 쓰는 수많은 사용자가 옛 서버로 간다. 즉 TTL 300초의 의미는
"전환 후 **최대** 300초에 걸쳐 사용자들이 **제각각의 시점에** 새 주소로
넘어온다"이고, 그마저도 모든 캐시가 규칙을 지킨다는 가정 위의
이야기다. 전환은 일제히 일어나는 스위치가 아니라 서서히 번지는
물결이다.

## 2. 함정 목록 — 이상적 TTL 모델이 깨지는 지점들

### (1) TTL을 지키지 않는 캐시가 있다

일부 ISP 리졸버는 부하를 줄이려고 짧은 TTL을 무시하고 자체 최소값을
강제하거나 캐시를 연장한다. 이 사용자들에게는 내가 설정한 TTL이
의미가 없다. 전환 후 트래픽이 "0에 수렴하지만 완전히 0이 되지 않는"
꼬리의 주요 원인이다.

### (2) 애플리케이션 자체 캐시 — JVM의 DNS 캐시

OS 밖에도 캐시가 있다. 대표적으로 JVM은 한 번 조회한 호스트명→IP
결과를 자체 캐시하는데, 설정에 따라 **매우 오래, 심하면 프로세스가
살아있는 동안 계속** 캐시할 수 있다. 서버 간 호출을 하는 백엔드에서
상대가 DNS를 전환했는데 우리 서버만 계속 옛 IP를 찌르는 사고의
전형적 원인이다.

```
# Before: JVM DNS 캐시의 존재를 모름 — 상대가 전환해도 옛 IP를 계속 사용

# After: JVM 캐시 유효시간을 명시적으로 관리
-Dnetworkaddress.cache.ttl=10    # 조회 결과를 10초만 신뢰
```

### (3) 커넥션은 DNS를 다시 보지 않는다

가장 자주 잊는 함정. DNS는 **연결을 새로 맺을 때만** 조회된다. 이미
맺어진 keep-alive 커넥션, 커넥션 풀 안의 커넥션은 IP로 연결이 유지되고
있으므로 DNS가 어떻게 바뀌든 **재연결 전까지 옛 서버로 계속 간다**.
TTL을 아무리 줄여도 이 트래픽은 안 넘어온다. 대응은 풀 커넥션에
최대 수명(max lifetime)을 두어 주기적으로 재연결하게 하거나, 전환 시
옛 서버 쪽에서 커넥션을 우아하게 종료(drain)하는 것이다.

### (4) TTL 인하 자체에 리드타임이 필요하다

전환일에 TTL을 낮추는 것은 이미 늦다. 기존 TTL이 하루였다면, "TTL을
60초로 낮춘 새 레코드"가 모든 캐시에 퍼지는 데 **기존 TTL만큼**
걸린다 — 캐시들이 옛 TTL로 잡아둔 옛 응답이 만료돼야 새 TTL을 보기
때문이다. 그래서 전환 계획에는 "D-데이 충분히 전(기존 TTL 이상의
여유)에 TTL 인하"가 첫 줄에 온다.

### (5) 옛 서버를 바로 끄면 안 된다

위의 모든 이유로 전환 후에도 옛 서버로 트래픽이 한동안 온다. 즉시
끄면 그 사용자들은 전부 연결 실패를 겪는다. 옛 서버는 유예 기간 동안
정상 서비스(또는 새 서버로의 프록시)를 유지하고, 유입 트래픽이 0에
수렴하는 것을 **관측으로 확인한 뒤** 내린다.

## 3. failover 관점 — DNS로 초 단위 전환은 안 된다

DNS 기반 failover(헬스체크가 실패하면 레코드를 대기 서버로 교체)는
가장 손쉬운 재해 대비처럼 보이지만, 실제 전환 시간은:

```
장애 감지 시간 + 레코드 교체 + (TTL + 캐시 꼬리)만큼의 전파 시간
```

이다. TTL을 아무리 줄여도 캐시 꼬리와 커넥션 유지 때문에 **분 단위
이상**을 각오해야 하고, 일부 사용자는 그보다 오래 옛 주소를 본다.
"우리 RTO는 30초인데 failover는 DNS로 한다"는 계획은 성립하지 않는다 —
이 산수를 해봤는지가 재해 복구 계획의 현실성을 가른다.

즉시 전환이 필요하면 원칙은 **"클라이언트가 보는 IP는 바뀌지 않게
하고, 그 뒤에서 바꾸는 것"**이다:

- **LB 뒤 백엔드 교체**: DNS는 LB를 가리키고, 전환은 LB의 분배 대상
  변경으로 — 즉시 반영되고 롤백도 즉시.
- **VIP 이관**: 가상 IP를 장애 시 대기 장비가 넘겨받는 방식
  (keepalived 류) — IP가 그대로라 DNS 전파가 필요 없다.
- **anycast/GSLB**: 같은 IP를 여러 위치에서 광고하거나, 지리·상태 기반
  분배를 DNS 앞단 인프라가 맡는 방식. (가산점 포인트)

DNS failover가 유효한 곳은 리전 전체 장애 같은 **분 단위 RTO가 허용되는
큰 단위의 전환**이고, 그 경우에도 위 함정들을 계획에 반영해야 한다.

## 4. 실무 시나리오 — 무중단 이전(전환) 체크리스트

서버 이전이나 DNS 기반 블루-그린 전환을 한다면 절차는 이렇게 짜인다:

1. **D-여유일**: TTL 인하 (기존 TTL 이상의 리드타임 확보 — 함정 4)
2. **D-day**: 레코드 전환. 이 시점에 **양쪽 서버 모두 정상 서비스
   가능 상태**여야 한다 (물결이 번지는 동안 둘 다 트래픽을 받는다)
3. **전환 후**: 옛 서버 유입량을 모니터링 — 0에 수렴하는지 확인.
   완전한 0이 안 되는 경우의 원인 파악(TTL 무시 캐시, 어딘가에
   하드코딩된 IP, 갱신 안 한 내부 시스템)
4. **유예 후**: 옛 서버 종료, TTL 원복 (낮은 TTL을 방치하면 조회
   부하·지연 비용을 계속 낸다)

이 절차 없이 "레코드 바꾸고 옛 서버 종료"를 하루에 하면, 며칠간
일부 사용자만 접속이 안 되는 — 그리고 재현도 안 되는 — 장애 신고가
쌓인다.

## 5. 꼬리질문 대비 포인트

### "그럼 TTL을 평소에 아주 짧게(몇 초) 유지하면 되지 않나요?"

비용이 따른다. (1) 캐시 적중률이 떨어져 리졸버와 권위 DNS의 조회
부하가 늘고, 사용자마다 새 연결 때 DNS 조회 지연을 더 자주 낸다.
(2) 캐시는 권위 DNS 장애 때의 방패이기도 하다 — TTL이 길면 권위
서버가 잠깐 죽어도 세상은 캐시로 돌아가지만, TTL이 짧으면 DNS 장애가
곧 서비스 장애가 된다. (3) 그렇게 줄여도 TTL 무시 캐시와 유지 중인
커넥션 문제는 해결되지 않는다. 그래서 평상시엔 적당한 TTL을 쓰고,
계획된 전환 전에만 낮추는 운영이 일반적이다.

### "커넥션 풀을 쓰는 서버 간 호출에서 DNS 전환이 반영 안 되는 이유와 대응은?"

DNS는 연결 수립 시에만 조회되는데, 풀은 연결을 재사용하는 것이 존재
이유라서 재조회 계기가 없기 때문이다. 여기에 JVM 자체 DNS 캐시까지
겹치면 재연결을 해도 옛 IP로 다시 붙는다. 대응은 풀 커넥션의 최대
수명을 설정해 주기적 재연결을 강제하고, JVM DNS 캐시 TTL을 명시하며,
전환 시 옛 서버가 커넥션을 우아하게 닫아(drain) 클라이언트의 재연결을
유도하는 것이다.

### "DNS 기반 failover는 그럼 어디에 적합한가요?" (시니어 변별 포인트)

전환 단위가 크고 RTO가 분 단위 이상 허용되는 곳 — 리전 전체 장애의
재해 복구, 지리 기반 분배(GSLB)의 상위 라우팅 같은 자리다. 반대로
서버 몇 대의 장애 대응처럼 초 단위가 필요한 곳은 LB 헬스체크나 VIP
이관이 맡아야 한다. 즉 계층을 나눠서 "빠른 전환은 IP가 안 바뀌는
지점(LB/VIP)에서, 큰 단위의 전환만 DNS에서"라고 역할을 배치하는 것이
설계 답안이다. 여기에 "DNS failover를 쓴다면 그 전파 지연을 RTO
계산에 명시적으로 넣고, 실제로 전환 훈련으로 측정해봐야 한다"까지
말하면 재해 복구를 문서가 아니라 운영으로 다뤄본 사람으로 보인다.

### "블루-그린 배포를 DNS 전환으로 구현하면 어떤 문제가 있나요?"

블루-그린의 핵심 가치는 **즉시 전환과 즉시 롤백**인데, DNS 전환은
둘 다 물결처럼 번지므로 그 가치를 잃는다. 전환 중에는 사용자마다
구버전/신버전이 섞여서 도달하는 기간이 길어지고(양버전 호환성 요구가
길어짐), 문제 발견 시 롤백해도 같은 전파 지연을 다시 겪는다. 그래서
블루-그린 전환점은 DNS가 아니라 LB(대상 그룹 교체)에 두는 것이
정석이고, DNS는 그 LB를 가리키는 고정된 이름으로만 쓴다.

## 한 줄 요약

TTL은 캐시 유효기간의 상한일 뿐 동기화 신호가 아니어서 DNS 전환은
항상 긴 꼬리를 남긴다 — TTL 무시 리졸버, JVM 캐시, DNS를 다시 보지
않는 keep-alive 커넥션까지 감안해 "사전 TTL 인하 → 양쪽 공존 전환 →
옛 서버 유예 운영"으로 절차를 설계하고, 초 단위 failover가 필요한
곳은 DNS가 아니라 IP가 바뀌지 않는 LB·VIP 뒤에서 전환해야 한다.
