# DNS TTL과 배포·failover — "DNS 바꿨는데 왜 아직 옛 서버로 오지?"의 원리

> 핵심 관전 포인트: **DNS 전환은 스위치가 아니라 물결이다. TTL은 "이 응답을 최대 얼마나 캐시해도 되는가"의 상한일 뿐이고, 전 세계에 흩어진 캐시(브라우저, OS, 공유기, ISP 리졸버, JVM, 그리고 DNS를 아예 다시 안 보는 keep-alive 커넥션)는 각자 자기가 조회한 시점부터 만료를 센다. 심지어 TTL을 무시하고 더 오래 캐시하는 리졸버도 있어, 전환 후에도 옛 주소로 가는 긴 꼬리 트래픽이 남는다. 그래서 DNS 전환 작업은 "사전 TTL 인하 → 전환 → 옛 서버 유예 운영"의 절차로 설계해야 하고, 초 단위 전환이 필요한 failover는 DNS가 아니라 IP가 바뀌지 않는 지점(LB, VIP, anycast) 뒤에서 해야 한다.**

---

## 0. 질문 + 의도

**질문**: "DNS TTL과 배포/failover의 관계 — DNS 기반 트래픽 전환의 함정은?"

**출제 의도**: "DNS 바꿨는데 왜 아직 옛 서버로 오지?"라는, 전환 작업 때마다 등장하는 현상. 캐싱 계층이 곳곳에 있는 인터넷의 실제 동작을 아는지 — 그리고 그 이해가 재해 복구 계획의 현실성(DNS failover로 RTO를 맞출 수 있다는 계획이 진짜 성립하는지)을 검증할 수 있는 수준인지 본다.

## 1. TTL의 실제 동작 — 상한이지 동기화 신호가 아니다

### 1-1. 전제 — DNS 레코드에는 종류가 있고, 종류가 전환 방식을 바꾼다

TTL 이야기를 하기 전에 **무엇에 TTL이 붙는지**부터 정해야 한다. DNS는 "이름 하나에 값 하나"가 아니라 **이름 아래에 종류별 레코드가 붙는 구조**이고, TTL은 그 레코드마다 따로 붙는다.

전환 작업에서 실제로 만지는 것은 대체로 다음 넷이다.

**A 레코드**는 이름을 IPv4 주소로 매핑한다. `api.example.com → 203.0.113.10`. 이름의 "A"는 Address의 A다. 가장 기본이고, 최종적으로 클라이언트가 원하는 답이 이것이다.

**AAAA 레코드**는 같은 일을 IPv6 주소로 한다. 이름이 A 네 개인 이유는 **IPv6 주소가 IPv4의 네 배 길이**(32비트 대 128비트)이기 때문이다. 요즘 클라이언트는 A와 AAAA를 둘 다 조회하므로, 전환할 때 **한쪽만 바꾸고 다른 쪽을 잊는 사고**가 실제로 자주 난다.

**CNAME 레코드**는 이름을 **다른 이름으로** 매핑한다. Canonical Name, 즉 "정식 이름"의 약자로, "이 이름의 진짜 이름은 저것이다"라는 뜻이다. `www.example.com → lb-123.elb.amazonaws.com`처럼 관리형 로드밸런서를 가리킬 때 쓴다. 리졸버는 CNAME을 받으면 그 대상 이름을 **다시 조회**해서 최종 A/AAAA까지 따라간다.

**NS 레코드**는 이 도메인을 어느 권한 네임서버가 관리하는지를 가리킨다. 계층 위임의 실체다(`01-url-to-page-dns-tcp-tls-http.md` 2-2절).

여기서 실무적으로 아주 중요한 제약이 하나 나온다. **CNAME은 apex 도메인에 붙일 수 없다.**

apex 도메인이란 `www`나 `api` 같은 접두어 없는 도메인 그 자체, 즉 `example.com`을 말한다. 영역(zone)의 꼭대기라서 apex(정점)라고 부른다. 왜 여기에 CNAME을 못 붙이는가.

```
DNS 표준의 규칙: 어떤 이름에 CNAME이 있으면, 그 이름에는 다른 레코드가 있으면 안 된다.
                 ("이 이름의 진짜 이름은 저것"이라고 했으면서 자기 데이터를 따로 갖는 것은 모순)

그런데 apex 에는 반드시 있어야 하는 레코드가 있다:
    example.com.  SOA  ...   <- 이 영역의 관리 정보
    example.com.  NS   ...   <- 이 영역을 관리하는 네임서버

  -> SOA/NS 와 CNAME 은 같은 이름에 공존할 수 없다
  -> 그래서 example.com 에는 CNAME 을 못 쓴다.
```

이게 왜 문제인가. 관리형 로드밸런서(AWS의 ELB, GCP의 LB 등)는 **IP가 고정이 아니라 이름으로 제공된다.** 뒤에서 IP가 늘거나 바뀔 수 있기 때문이다. 그러면 `example.com`을 그 LB에 붙이려면 CNAME이 필요한데 apex라서 못 쓴다.

그래서 클라우드 DNS 서비스들이 만든 우회가 **ALIAS(또는 ANAME, CNAME flattening)** 레코드다. **동작은 CNAME인데 응답은 A로 나가는** 특수 레코드다. 권한 네임서버가 질의를 받는 시점에 대상 이름을 자기가 대신 조회해서 최종 IP를 A 레코드로 돌려주므로, 클라이언트 입장에서는 평범한 A 레코드를 받은 것이고 apex 제약에 걸리지 않는다. **DNS 표준 레코드가 아니라 제공자별 기능**이므로 이름과 동작 세부는 제공자 문서를 확인해야 한다.

여기서 하나만 기억하면 된다. **apex 도메인을 관리형 LB에 붙이는 방법은 제공자가 제공하는 ALIAS류이거나, LB의 IP를 A 레코드에 직접 박는 것뿐이다.** 후자는 제공자가 IP를 바꾸는 순간 조용히 죽으므로 하면 안 된다.

### 1-2. 캐시는 사슬로 늘어서 있다

DNS 조회는 한 곳에서 일어나지 않는다. 사용자와 **권한 네임서버**(그 도메인의 원본 레코드를 가진, 최종 답을 낼 권한이 있는 서버) 사이에 캐시가 사슬로 늘어서 있다.

```
[브라우저 캐시] -> [OS 캐시 / hosts] -> [공유기] -> [ISP·공용 재귀 리졸버] -> [권한 네임서버]
   각자 TTL만큼      각자 TTL만큼         각자         각자 TTL만큼               원본
   기억한다          기억한다             기억한다      기억한다
```

**그리고 이 사슬 밖에 하나가 더 있다.** 자바 애플리케이션이라면 JVM 자체의 DNS 캐시가 OS 캐시보다도 앞에 있고(2-2절), 그보다 더 앞에는 **DNS를 아예 다시 조회하지 않는 커넥션 풀**이 있다(2-3절). 이 두 개가 실무에서 가장 자주 사고를 낸다.

### 1-3. TTL이 약속하는 것과 약속하지 않는 것

**TTL(Time To Live, 생존 시간)**은 권한 네임서버가 응답에 붙여 보내는 초 단위 숫자로, **"이 답을 최대 이만큼은 다시 묻지 말고 써도 된다"**는 유효기간이다.

여기서 아주 흔한 착각이 생긴다. **"TTL이 300초니까 레코드를 바꾸면 300초 뒤엔 전부 새 주소를 쓰겠지."**

틀렸다. 실제로는 각 캐시가 **자기가 조회한 시점부터** 따로 카운트다운한다. 전 세계의 리졸버들이 같은 순간에 조회한 것이 아니므로, 만료 시점도 제각각 흩어져 있다.

```
권한 서버의 레코드를 t=100 에 바꿨다고 하자. TTL = 300.

리졸버 X: t=  0 에 조회 -> 자기 캐시 만료는 t=300.  t=100~300 동안 옛 답을 계속 준다.
리졸버 Y: t= 99 에 조회 -> 자기 캐시 만료는 t=399.  거의 TTL 전체를 옛 답으로 버틴다.
리졸버 Z: t=101 에 조회 -> 이미 새 답을 받는다.     즉시 넘어간다.
리졸버 W: t=250 에 처음 조회 -> 새 답.

  t:   0          100        200        300        400
       |          |          |          |          |
       |          | <- 여기서 권한 서버의 레코드를 바꿨다
       |          |
  X:   [============= old ==============]   t=300 만료, 이후 새 답
  Y:              [============= old ==============]   t=399 만료, 이후 새 답
  Z:               [ 새 답 ]
  W:                              [ 새 답 ]

  -> 전환은 t=100 의 한 점에서 일어나지 않는다.
     t=100 부터 t=400 사이에 걸쳐 사용자들이 제각각의 시점에 넘어온다.
```

그러니 TTL 300초의 정확한 의미는 이렇다. **"전환 후 최대 300초에 걸쳐 사용자들이 제각각의 시점에 새 주소로 넘어온다."** 300초 뒤에 일제히 바뀌는 것이 아니다.

비유하면 **TTL은 유통기한이지 알람이 아니다.** 우유에 유통기한이 적혀 있다고 해서 전국의 냉장고에 있는 우유가 같은 날 동시에 버려지지는 않는다. 각 집이 산 날이 다르니까.

그리고 이 그림은 **모든 캐시가 규칙을 지킨다는 가정 위**에서만 성립한다. 2절에서 볼 함정들은 이 가정이 여러 방향으로 깨진다는 이야기다.

**전환은 일제히 일어나는 스위치가 아니라 서서히 번지는 물결이다.** 이 문서 전체가 이 한 문장에서 나온다.

TTL이 실제로 어떻게 흘러가는지는 눈으로 확인할 수 있다.

```bash
# 지금 이 리졸버가 들고 있는 답과 남은 TTL. 두 번째 열의 숫자가 TTL이다.
dig +noall +answer api.example.com

# 같은 명령을 몇 초 간격으로 다시 치면 TTL이 줄어드는 것이 보인다.
# 그게 0이 되면 리졸버가 다시 물어보고 TTL이 원래 값으로 되돌아간다.
# "캐시가 카운트다운한다"를 눈으로 확인하는 가장 빠른 방법이다.

# 특정 공용 리졸버가 지금 무엇을 주는지 — 캐시별로 답이 다를 수 있음을 확인한다.
dig @8.8.8.8 api.example.com
dig @1.1.1.1 api.example.com

# 캐시를 완전히 배제하고 원본을 본다. 권한 서버에 직접 묻는다.
# "레코드는 제대로 바뀌었는데 캐시 때문에 안 보이는 것"인지를 이걸로 가른다.
dig @ns1.example.com api.example.com

# 루트부터 계층을 따라 내려가며 어디서 어떤 답이 나오는지 전부 본다.
dig +trace api.example.com
```

**`dig @권한서버`와 `dig @8.8.8.8`의 답이 다르면 그것이 곧 "지금 전파 중"이라는 증거다.** 전환 작업 중에 가장 먼저 확인해야 할 것이 이 두 값의 대조다.

### 1-4. 어느 층의 레코드를 바꾸느냐가 체감 속도를 바꾼다

CNAME을 쓰면 캐시가 하나가 아니라 **사슬의 각 마디마다** 따로 잡힌다. 이 사실이 전환 속도에 직접 영향을 준다.

```
www.example.com.       CNAME  blue.example.com.     TTL 3600
blue.example.com.      A      203.0.113.10          TTL 60

리졸버는 두 레코드를 각자의 TTL로 따로 캐시한다.
  - CNAME(www -> blue)   : 3600초
  - A(blue -> .10)       : 60초
```

이제 blue에서 green으로 전환하는 방법이 두 가지가 되고, **걸리는 시간이 완전히 다르다.**

**(A) CNAME의 대상을 바꾼다** — `www → green.example.com`으로. 리졸버는 CNAME을 3600초 동안 캐시하고 있으므로, 그 3600초가 지나야 새 대상을 본다. **전환 지연은 CNAME의 TTL 3600초가 지배한다.** A 레코드의 TTL 60초는 아무 도움이 안 된다.

**(B) blue의 A 레코드를 green의 IP로 바꾼다** — CNAME은 그대로 두고. 리졸버가 캐시한 CNAME은 여전히 유효하고, A 레코드만 60초 뒤 만료된다. **전환 지연은 60초다.**

여기서 실무 규칙이 나온다. **전환 지연을 지배하는 것은 "내가 실제로 바꾼 그 레코드의 TTL"이다.** 사슬 아래쪽 레코드의 TTL이 아무리 짧아도 위쪽을 바꾸면 위쪽 TTL만큼 기다린다.

이 구조가 관리형 LB를 쓸 때 값을 한다. `www.example.com`을 LB의 이름에 CNAME으로 걸어두면, 실제 IP 변경은 **LB 제공자가 자기 A 레코드(대개 짧은 TTL)에서 처리**한다. 우리 CNAME은 손댈 일이 없고, IP가 바뀌어도 우리는 아무것도 안 해도 된다. **"자주 바뀌는 것은 사슬의 아래쪽에, 안 바뀌는 이름은 위쪽에" 두는 것이 설계 원칙**이다.

## 2. 이상적 TTL 모델이 깨지는 지점들

1절의 모델은 "모든 캐시가 TTL을 정확히 지키고, 클라이언트는 필요할 때마다 DNS를 다시 본다"를 전제한다. 실제로는 다섯 군데에서 깨진다.

### 2-1. (1) TTL을 지키지 않는 캐시가 있다

일부 ISP 리졸버는 자기 부하와 상류 질의량을 줄이려고 **짧은 TTL을 그대로 따르지 않는다.** 대표적인 리졸버 구현에는 캐시 TTL의 하한을 강제하는 설정이 있다 — Unbound의 `cache-min-ttl`, BIND의 `min-cache-ttl` 같은 것이다. 운영자가 이 값을 예컨대 300초로 켜두면, **내가 TTL 30초로 내려도 그 리졸버를 쓰는 사용자에게는 300초로 동작한다.**

내 쪽에서는 이걸 감지할 방법도, 통제할 방법도 없다. 그래서 이런 결론이 나온다. **TTL은 "내가 통제하는 상한"이 아니라 "권한 서버가 권고하는 값"에 가깝다.** 전환 후 트래픽이 0에 수렴하다가 **완전한 0이 되지 않고 남는 긴 꼬리**의 주요 원인이 이것이다.

여기 짝으로 알아둘 것이 하나 더 있다. **부정 응답도 캐시된다.** "그런 이름은 없다"(NXDOMAIN)는 답 역시 캐시되고, 그 시간은 해당 영역의 SOA 레코드에 적힌 값이 정한다. 그래서 **아직 만들지 않은 이름을 실수로 한 번 조회해버리면, 레코드를 만든 뒤에도 한동안 "없음"으로 나온다.** 새 도메인을 붙이는 날 "레코드 만들었는데 왜 안 보이죠"의 흔한 정체다.

```bash
# 부정 캐시 시간을 확인한다. SOA의 마지막 숫자가 그 값이다.
dig example.com SOA +noall +answer
```

### 2-2. (2) 애플리케이션 자체 캐시 — JVM의 DNS 캐시

OS 밖에도 캐시가 있다. 자바의 `InetAddress`는 조회 결과를 **JVM 자체 캐시**에 담아두고, **DNS 응답의 TTL이 아니라 JVM 자신의 정책**을 따른다. 즉 권한 서버가 TTL 30초를 줘도 JVM은 그것과 무관하게 자기 정책대로 붙들 수 있다.

**이 캐시의 동작과 설정 방법은 `01-url-to-page-dns-tcp-tls-http.md` 2-2절에서 코드와 함께 다뤘으므로 여기서는 반복하지 않는다.** 이 문서에서 알아야 할 것은 **결과**다. 이 계층 하나 때문에 "TTL을 30초로 줄여뒀으니 30초면 넘어온다"는 계산이 자바 서버에서는 성립하지 않을 수 있고, 심하면 **재기동 전까지 옛 IP를 계속 찌른다.** 상대 팀이 DNS를 전환했는데 우리 서버만 계속 옛 인스턴스로 붙는 사고의 절반이 여기서 나온다.

그리고 **JVM 캐시는 다음 절의 문제와 겹칠 때 훨씬 나빠진다.** 커넥션 풀이 연결을 새로 맺으려는 그 순간에도 JVM 캐시가 옛 IP를 돌려주면, **재연결을 해도 다시 옛 서버에 붙는다.** 두 개의 자물쇠를 둘 다 풀어야 전환이 완료된다.

### 2-3. (3) 커넥션 풀은 DNS를 다시 보지 않는다

**이 문서에서 가장 실무적인 함정이고, 가장 자주 잊힌다.**

#### 전제 — DNS는 언제 조회되는가

DNS 조회가 일어나는 시점은 딱 하나다. **새 TCP 연결을 맺으려 할 때.** 이름으로는 패킷을 보낼 수 없으니 연결 직전에 IP로 바꿔야 하고, 그때 한 번 조회한다.

그리고 한 번 맺어진 TCP 연결은 **4-튜플(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)로 고정된다**(`01-url-to-page-dns-tcp-tls-http.md` 2-3절, `10-keepalive-connection-pool-time-wait.md` 2-2절). 목적지 IP가 그 연결의 정체성의 일부라서, **연결이 살아 있는 동안 목적지가 바뀔 수 있는 방법은 없다.**

여기서 결론이 자동으로 나온다. **이미 맺어진 keep-alive 커넥션과 풀 안의 커넥션은 DNS를 다시 볼 계기가 없다.** 커넥션 풀의 존재 이유가 "연결을 다시 맺지 않는 것"이니까, 재조회 계기가 없는 것이 버그가 아니라 설계 그대로다.

```
t =   0s   DNS: api.example.com -> 10.0.0.10 (구서버)
           우리 서비스의 풀이 구서버로 연결 50개를 맺는다.

t = 100s   상대 팀이 레코드를 10.0.0.20 (신서버)으로 바꾼다. TTL 60.

t = 160s   TTL 만료. 지금 새로 조회하는 클라이언트는 10.0.0.20을 받는다.
           |
           +-- 그런데 우리 풀의 연결 50개는 여전히 10.0.0.10에 물려 있다.
               이 연결들은 조회할 계기가 없다. 이미 연결돼 있으니까.
               트래픽 100%가 계속 구서버로 간다.

t = ???    구서버를 종료하는 순간, 우리 서비스만 전면 장애.
           상대 팀은 "우리는 어제 전환 끝냈는데요"라고 답한다.
```

**TTL을 아무리 줄여도 이 트래픽은 안 넘어온다.** DNS 계층의 문제가 아니기 때문이다.

#### 대응 — 자물쇠 세 개를 전부 푼다

**(1) 연결에 최대 수명을 준다.** 멀쩡한 연결이라도 일정 시간이 지나면 폐기하고 새로 맺게 한다. 그래야 재조회 계기가 주기적으로 생긴다. 이 값이 곧 **"전환이 반영되기까지의 상한"**이 된다.

```java
// Before: 풀에 수명 제한이 없다.
// - 연결이 정상인 한 영원히 재사용되므로, 상대가 DNS를 바꾸든
//   스케일 아웃으로 인스턴스를 늘리든 우리는 계속 옛 IP만 본다.
// - 새로 뜬 인스턴스로는 트래픽이 한 건도 안 가는 부하 편중도 같은 원인이다.
PoolingHttpClientConnectionManager pool =
        PoolingHttpClientConnectionManagerBuilder.create()
                .setMaxConnPerRoute(50)
                .build();

// After: 최대 수명과 유휴 상한으로 재조회 계기를 강제로 만든다.
PoolingHttpClientConnectionManager pool =
        PoolingHttpClientConnectionManagerBuilder.create()
                .setMaxConnPerRoute(50)
                .setDefaultConnectionConfig(ConnectionConfig.custom()
                        // 연결 하나의 최대 수명. 5분이 지나면 멀쩡해도 버리고 새로 맺는다.
                        // 이 값이 "상대가 DNS를 바꾼 뒤 우리가 따라가는 데 걸리는 최대 시간"의
                        // 상한을 만든다. 전환이 잦은 의존성일수록 짧게 잡는다.
                        .setTimeToLive(TimeValue.ofMinutes(5))
                        .build())
                .build();

CloseableHttpClient http = HttpClients.custom()
        .setConnectionManager(pool)
        // 놀고 있는 연결은 더 빨리 정리한다. 유휴 연결을 오래 들고 있을수록
        // 옛 IP에 물린 채로 남아 있는 시간이 길어진다.
        .evictIdleConnections(TimeValue.ofSeconds(60))
        .build();
```

Reactor Netty(WebClient)라면 `maxLifeTime`, HikariCP라면 `maxLifetime`이 같은 나사다(`10-keepalive-connection-pool-time-wait.md` 1-4절의 네 나사 표). **DB 엔드포인트가 failover로 IP가 바뀌는 구성에서 `maxLifetime`이 없으면 재기동 전까지 옛 인스턴스에 계속 붙어 있는다.**

**(2) JVM DNS 캐시 수명을 명시한다.** (1)만 해두면 재연결은 일어나지만, 그 순간 JVM 캐시가 옛 IP를 돌려주면 다시 옛 서버로 간다. 두 값 중 **긴 쪽이 실제 전환 지연을 지배**하므로 둘을 함께 잡아야 한다(설정 방법은 01번 문서).

**(3) 전환 시점에 옛 서버가 연결을 놓아준다(drain).** 위 둘은 클라이언트 쪽 조치라서, 우리가 통제하지 못하는 외부 클라이언트에는 적용할 수 없다. 그래서 **서버 쪽에서 연결을 우아하게 끊어 클라이언트가 재연결하도록 유도**하는 방법이 함께 필요하다.

```nginx
# 구서버(전환 대상에서 빠지는 쪽)에서 전환 시작과 함께 keep-alive를 끈다.
#
# keepalive_timeout 0 은 응답마다 "Connection: close" 헤더를 붙인다.
# 클라이언트는 그 응답을 받은 뒤 이 연결을 재사용하지 않고 닫으므로,
# 다음 요청은 반드시 새 연결 = 새 DNS 조회가 된다.
#
# 강제 종료(연결을 끊어버리는 것)와 달리 진행 중인 요청은 정상으로 끝나므로
# 사용자에게 오류가 보이지 않는다. 이것이 "우아하게"의 뜻이다.
keepalive_timeout 0;
```

**(4) 우리 서비스 쪽은 전환 시점에 롤링 재시작을 건다.** 가장 확실하고 가장 단순한 방법이다. 프로세스가 새로 뜨면 풀도 JVM 캐시도 전부 비어 있으므로 무조건 새 IP로 붙는다. 인스턴스를 한 대씩 순차 교체하면 서비스 중단 없이 할 수 있다. **"설정을 정교하게 맞추는 것"보다 "전환 절차에 롤링 재시작을 한 줄 넣는 것"이 실패 확률이 낮다.**

### 2-4. (4) TTL 인하 자체에 리드타임이 필요하다

"전환 당일에 TTL을 낮추고 바로 전환하자"는 계획은 **이미 늦었다.**

이유를 한 단계씩 따라가 보자. TTL은 **응답에 함께 실려 나가는 값**이다. 그러니 "TTL을 60초로 낮췄다"는 사실을 어떤 리졸버가 알려면, 그 리졸버가 **새로 조회해서 새 응답을 받아야** 한다. 그런데 그 리졸버는 지금 옛 응답을 옛 TTL(예: 86400초)로 캐시하고 있으므로, **그 옛 TTL이 만료돼야 새로 조회한다.**

```
기존 TTL = 86400 (24시간)

t=0        권한 서버에서 TTL을 86400 -> 60 으로 낮춘다.
           |
           +-- 이 순간 이미 옛 응답(TTL 86400)을 캐시한 리졸버들이 세상에 있다.
               그들은 자기가 조회한 시점부터 최대 86400초 동안 다시 안 묻는다.
               즉 "TTL이 60으로 바뀌었다"는 사실 자체를 최대 24시간 동안 모른다.

t=0 ~ 86400  새로 조회하는 리졸버부터 순차적으로 TTL 60을 받아간다.
             이 구간에서는 어떤 리졸버는 60초짜리, 어떤 리졸버는 86400초짜리를
             들고 있는 혼재 상태다.

t=86400 이후 경로상의 캐시가 대체로 TTL 60으로 통일됐다고 볼 수 있다.
             ★ 여기서부터 비로소 "전환하면 60초 안에 대부분 넘어온다"가 성립한다.
```

**TTL 인하는 그 자체가 "기존 TTL만큼의 전파 시간"을 요구하는 작업**이다. 그래서 전환 계획의 첫 줄은 언제나 **"D-데이보다 기존 TTL 이상 앞서서 TTL 인하"**가 된다. 기존 TTL이 24시간이면 최소 하루, 안전하게는 며칠 앞이다.

이게 계획서 한 줄이 아니라 실제 사고의 원인이 되는 이유가 있다. **당일에 TTL을 낮추고 전환하면, 옛 TTL로 캐시된 리졸버들은 24시간 동안 옛 서버를 바라본다.** 그런데 담당자는 "TTL 60초로 낮췄으니 1분이면 끝"이라고 생각하고 옛 서버를 몇 분 뒤에 내려버린다. 그 결과가 다음 절이다.

### 2-5. (5) 옛 서버를 바로 끄면 안 된다

앞의 네 함정을 전부 합치면 결론이 하나 나온다. **전환 후에도 옛 서버로 트래픽이 한동안, 그리고 예상보다 오래 온다.**

남는 트래픽의 출처를 정리하면 이렇다.

**잔여 TTL.** 전환 직전에 조회해간 리졸버들이 각자의 남은 TTL만큼 옛 답을 계속 나눠준다(1-3절).

**TTL을 무시하는 캐시.** 리졸버의 최소 TTL 강제 설정 때문에 내가 정한 시간보다 오래 붙들고 있는 곳이 있다(2-1절).

**커넥션 풀과 keep-alive.** DNS가 어떻게 바뀌든 이미 맺어진 연결은 옛 IP로 계속 간다(2-3절). **이쪽은 TTL과 아무 상관이 없어서, TTL 기준으로 세운 일정에 잡히지 않는다.**

**어딘가에 하드코딩된 IP.** 오래된 배치 스크립트, 모니터링 설정, 파트너사의 방화벽 허용 목록, 누군가의 `/etc/hosts`. **이건 만료되지 않는다.** 관측으로 찾아내는 수밖에 없다.

옛 서버를 즉시 끄면 이 트래픽이 **전부 연결 실패**가 된다. 그리고 이 장애의 성질이 고약하다 — 전체 사용자의 몇 퍼센트만 겪고, 담당자 본인은 재현이 안 되며(본인 캐시는 이미 갱신됐으니까), 신고가 며칠에 걸쳐 산발적으로 들어온다. **"재현 안 되는 접속 장애 신고가 며칠간 쌓이는" 상황의 정체가 대개 이것이다.**

그래서 규칙은 이렇다. **옛 서버는 유예 기간 동안 정상 서비스를 유지하거나, 최소한 새 서버로 프록시하는 상태로 남긴다. 그리고 유입 트래픽이 0에 수렴하는 것을 관측으로 확인한 뒤에 내린다.** 날짜로 정하는 것이 아니라 **관측 결과로 정하는 것**이 핵심이다.

## 3. 실무 — DNS failover의 한계와 무중단 전환 절차

### 3-1. DNS failover의 전환 시간을 단계로 분해하면

**DNS failover**는 헬스체크가 실패하면 레코드를 대기 서버 IP로 자동 교체하는 방식이다. 설정이 간단하고 인프라를 추가로 살 필요가 없어서 가장 손쉬운 재해 대비처럼 보인다.

그런데 **"장애 발생부터 트래픽이 실제로 넘어가기까지"를 단계로 분해하면** 그림이 달라진다. 지연이 한 곳이 아니라 네 곳에서 각각 발생하고, 그 값이 전부 더해진다.

```
t=0       실제 장애 발생 (서버 A 다운)
          |
          | (1) 헬스체크 감지 지연
          |     체크 간격 x 실패 임계 횟수.
          |     한 번 실패했다고 바로 전환하면 순간적인 흔들림에도 전환이 일어나므로
          |     임계 횟수를 두는 것이 정상이고, 그만큼 감지가 늦어진다.
          |     예: 30초 간격 x 3회 = 최대 90초
          v
t=90s     unhealthy 판정. 레코드를 B로 교체.
          |
          | (2) 레코드 갱신이 권한 서버들에 반영되는 시간
          |     관리형 DNS는 권한 서버를 여러 대(여러 지역에) 두므로
          |     전부에 새 값이 퍼지는 데 시간이 든다. 수초~수십초.
          v
t=110s    모든 권한 서버가 새 답을 낸다.
          |
          | (3) 캐시 TTL 만료
          |     리졸버가 t=0 직전에 조회했다면 TTL을 꽉 채워 기다린다.
          |     리졸버마다 조회 시점이 달라 만료도 흩어지고,
          |     TTL을 늘려 잡는 리졸버는 더 오래 걸린다.
          |     예: TTL 60초 -> 사실상 60초 + 꼬리
          v
t=170s    대부분의 리졸버가 새 답을 캐시했다.
          |
          | (4) 클라이언트가 실제로 다시 조회하는 시점
          |     DNS는 "새 연결을 맺을 때"만 조회된다.
          |     ★ 커넥션 풀이 옛 IP에 물려 있으면 이 단계가 영영 안 온다 (2-3절).
          v
t=???     비로소 트래픽이 넘어간다. 그리고 꼬리는 훨씬 오래 남는다.
```

숫자를 더해 보면 **공격적으로 TTL 60초를 걸어도 감지부터 전파 완료까지 3분 가까이** 나온다. 그리고 (4)는 값을 정할 수조차 없다 — 클라이언트가 어떻게 만들어졌는지에 달려 있기 때문이다.

여기서 나오는 결론이 이 절의 핵심이다. **"우리 RTO는 30초인데 failover는 DNS로 한다"는 계획은 산수상 성립하지 않는다.** (RTO는 Recovery Time Objective, 장애 발생부터 서비스 복구까지 허용하는 목표 시간이다.) 이 산수를 해봤는지가 재해 복구 계획이 문서인지 운영인지를 가른다.

각 단계의 값은 제품마다 다르므로 **자기 환경의 숫자를 넣어 직접 계산해 봐야 한다.** 관리형 DNS의 헬스체크 간격과 임계 횟수는 제품 문서에 나와 있고, (2)는 제공자의 SLA나 실측으로 잡고, (3)은 내가 정한 TTL이고, (4)는 우리 클라이언트 설정이다.

### 3-2. 그럼 TTL을 아주 짧게 유지하면 되지 않나

"평소에 TTL을 5초로 두면 3-1의 (3)이 사라지지 않나?"는 자연스러운 반문이고, 실제로 첫 답으로 나와야 하는 내용이다. **답은 "비용이 따르고, 그래도 문제가 다 안 풀린다"**이다. 네 가지를 나눠서 보자.

**(1) 권한 서버 질의량이 그대로 늘고, 그게 곧 비용이다.** 캐시 적중률이 TTL에 비례하므로 TTL을 1/10로 줄이면 권한 서버로 올라오는 질의가 그만큼 늘어난다. 관리형 DNS는 대체로 **질의 건수로 과금**하므로 요금이 그대로 따라 오르고, 자체 운영이라면 권한 서버 자체를 증설해야 한다.

**(2) 사용자 지연이 늘어난다.** 캐시가 비면 클라이언트는 조회를 기다려야 한다. 미적중 조회는 계층을 타느라 여러 왕복이 들 수 있다(`01-url-to-page-dns-tcp-tls-http.md` 2-2절). 개별 요청에는 수십 ms지만, **모든 사용자의 모든 새 연결에 곱해지므로** 무시할 크기가 아니다.

**(3) 캐시는 DNS 장애 때의 방패다. 이게 가장 중요하다.** TTL이 길면 권한 서버가 잠깐 죽어도 세상은 캐시로 굴러간다. TTL이 5초면 **권한 서버 장애가 곧바로 전면 서비스 장애**가 된다. 이름을 못 풀면 아무 데도 접속할 수 없기 때문이다. **TTL을 줄인다는 것은 전환 속도를 얻는 대신 DNS 인프라의 가용성 요구를 그만큼 올리는 거래다.**

**(4) 그렇게 해도 문제가 다 안 풀린다.** 2-1의 최소 TTL 강제 리졸버는 내 값을 안 따르고, 2-3의 커넥션 풀은 TTL과 무관하게 옛 IP를 붙들고 있으며, 3-1의 (1)(2)(4)는 TTL을 0으로 만들어도 그대로 남는다.

그래서 실무의 표준 운영은 **"평상시에는 적당한 TTL(수 분 단위)을 쓰고, 계획된 전환 전에만 미리 낮췄다가 끝나면 되돌린다"**가 된다. 낮춘 채로 방치하면 (1)(2)(3)의 값을 계속 지불하게 되므로, **원복이 절차의 마지막 줄에 반드시 들어가야 한다.**

### 3-3. 초 단위가 필요하면 DNS가 아닌 곳에서 바꾼다

3-1과 3-2를 합치면 원칙이 하나 나온다. **빠른 전환이 필요하면 클라이언트가 보는 IP를 바꾸지 말고, 그 IP 뒤에서 바꾼다.**

DNS가 느린 근본 이유는 **"바뀐 사실을 전 세계의 캐시에 알려야 한다"**는 데 있다. 그러니 알릴 필요가 없게 만들면 된다. 클라이언트가 보는 주소가 그대로면 전파할 것이 없다.

**LB 뒤 백엔드 교체.** DNS는 로드밸런서 하나를 가리키게 두고, 전환은 LB의 분배 대상(대상 그룹)을 바꾸는 것으로 한다. LB는 자기 설정을 바꾸는 것이므로 **즉시 반영되고 롤백도 즉시**다. 클라이언트가 보는 IP는 변하지 않으므로 캐시고 TTL이고 관계가 없다. **평상시 배포와 장애 대응의 기본 수단이 이것이다.**

**VIP 이관.** VIP(Virtual IP, 가상 IP)는 특정 장비에 고정되지 않고 **현재 활성 장비가 넘겨받는 IP 주소**다. keepalived 같은 도구가 장애를 감지하면 대기 장비가 그 IP를 자기 것으로 선언한다. IP 자체는 안 바뀌므로 DNS 전파가 필요 없고, 전환이 초 단위 이하로 끝난다.

**anycast.** 같은 IP를 여러 위치에서 동시에 광고하고, 네트워크의 라우팅이 알아서 가까운 곳으로 보내게 하는 방식이다. 한 위치가 죽으면 광고가 사라지고 라우팅이 다른 위치로 흐른다. **클라이언트는 아무것도 모르고, DNS도 아무것도 안 한다.** CDN과 공용 DNS 서비스가 쓰는 방식이다. (가산점 포인트)

**클라이언트 재시도.** 인프라를 바꾸지 않고도 초 단위 전환에 가까워지는 길이 하나 더 있다. **레코드에 IP를 여러 개 넣어두고, 클라이언트가 한 IP에 연결 실패하면 다음 IP로 즉시 넘어가게 하는 것**이다. DNS를 다시 조회할 필요도, 레코드를 바꿀 필요도 없다 — 이미 받아둔 목록 안에서 해결되므로 **전환 시간이 연결 타임아웃 한 번**으로 끝난다. 다만 클라이언트가 그렇게 만들어져 있어야 한다(꼬리질문 5번).

정리하면 역할 배치는 이렇다.

| 전환 수단 | 반영 속도 | 적합한 단위 |
|---|---|---|
| LB 대상 그룹 교체 | 즉시 | 배포, 인스턴스 교체, 블루-그린 |
| VIP 이관 | 초 단위 | 장비 이중화, 액티브-스탠바이 |
| anycast | 라우팅 수렴 시간 | 지역·거점 단위 장애 |
| 클라이언트 재시도 (다중 IP) | 연결 타임아웃 1회 | 엔드포인트 몇 개짜리 이중화 |
| **DNS 레코드 교체** | **분 단위 + 긴 꼬리** | **리전 전체 전환, 서버 이전, 도메인 이관** |

**DNS는 "빠른 전환 수단"이 아니라 "느리지만 확실한, 큰 단위의 전환 수단"이다.** 리전 전체 장애의 재해 복구나 데이터센터 이전처럼 어차피 분 단위 이상이 걸리는 전환에서는 DNS가 맞는 도구다. 그 경우에도 2절의 함정들은 그대로 계획에 반영해야 한다.

### 3-4. 무중단 이전 체크리스트 — 시간축 절차

서버 이전이나 DNS 기반 전환을 실제로 한다면 절차는 이렇게 짜인다. **각 단계가 왜 그 순서인지가 앞 절들의 결론과 1:1로 대응한다.**

```
D-7 (또는 기존 TTL 이상 앞서서)
 |  [1] TTL 인하:  86400 -> 60
 |      근거: 2-4절. TTL 인하 자체가 기존 TTL만큼 전파를 기다려야 한다.
 |      이 시점 이후 며칠간은 "TTL 86400짜리 옛 응답"과 "TTL 60짜리 새 응답"이
 |      세상에 섞여 있는 구간이다.
 v
D-1
 |  [2] 인하가 퍼졌는지 확인
 |      여러 공용 리졸버에 직접 물어 TTL 값이 60으로 내려왔는지 대조한다.
 |        dig @8.8.8.8 api.example.com
 |        dig @1.1.1.1 api.example.com
 |      아직 큰 값이 보이면 전환을 미룬다. 여기서 미루는 것이 사후 수습보다 싸다.
 |
 |  [3] 신서버를 완전히 준비하고 실트래픽 없이 검증
 |      전환 순간부터 두 서버가 동시에 트래픽을 받으므로, 신서버는
 |      전환 전에 이미 100%를 감당할 수 있는 상태여야 한다.
 v
D-day
 |  [4] 레코드 전환
 |      ★ 양쪽 서버 모두 정상 서비스 가능 상태를 유지한다.
 |        물결이 번지는 동안 둘 다 트래픽을 받는다 (1-3절).
 |        상태를 가진 서비스라면 이 구간에 두 서버가 같은 데이터를 봐야 한다 —
 |        DB를 공유하든 복제하든, 여기 설계가 없으면 전환 중에 데이터가 갈린다.
 |
 |  [5] 우리가 클라이언트인 쪽은 롤링 재시작
 |      풀과 JVM 캐시를 비워 새 IP로 붙게 한다 (2-3절).
 |
 |  [6] 구서버의 keep-alive를 끈다 (drain)
 |      외부 클라이언트의 유지 중인 연결을 놓아준다 (2-3절).
 v
D-day ~ D+N (유예 관찰 기간)
 |  [7] 구서버 유입량을 모니터링. 0에 수렴하는가?
 |      완전한 0이 안 되면 남은 것의 정체를 밝힌다:
 |        - TTL을 늘려 잡는 리졸버 (2-1)  -> 기다린다
 |        - 유지 중인 커넥션 (2-3)        -> drain 확인
 |        - 하드코딩된 IP                 -> 만료되지 않는다. 찾아서 고쳐야 한다.
 |      ★ 종료 시점은 날짜가 아니라 이 관측 결과가 정한다 (2-5절).
 v
D+N
 |  [8] 구서버 종료
 |
 |  [9] TTL 원복: 60 -> 86400
 |      낮은 TTL을 방치하면 질의 부하·비용·DNS 장애 취약성을 계속 지불한다 (3-2절).
 v
완료
```

이 절차 없이 "레코드 바꾸고 구서버 종료"를 하루에 끝내면 어떻게 되는지는 2-5절에 적은 그대로다. **며칠에 걸쳐, 일부 사용자만, 재현도 안 되는 접속 장애 신고가 쌓인다.** 그리고 그때는 이미 구서버가 없어서 되돌릴 수도 없다.

## 4. 꼬리질문 대비 포인트

### "그럼 TTL을 평소에 아주 짧게(몇 초) 유지하면 되지 않나요?"

**비용이 따르고, 그렇게 해도 문제가 다 풀리지 않는다.** 네 가지로 나눠 답한다(3-2절).

**질의량과 비용.** 캐시 적중률이 떨어져 권한 서버 질의가 그만큼 늘고, 관리형 DNS는 대개 질의 건수로 과금하므로 요금이 바로 오른다.

**사용자 지연.** 캐시 미적중이 잦아져 새 연결마다 DNS 조회 시간을 더 자주 낸다. 개별로는 작지만 모든 사용자의 모든 연결에 곱해진다.

**가용성. 이게 가장 중요한 포인트다.** 캐시는 권한 DNS 장애 때의 방패 역할을 한다. TTL이 길면 권한 서버가 잠깐 죽어도 세상은 캐시로 돌아가지만, **TTL이 몇 초면 DNS 장애가 곧바로 전면 서비스 장애가 된다.** 이름을 못 풀면 접속 자체가 안 되기 때문이다. **TTL 단축은 전환 속도를 사는 대신 DNS 인프라 가용성 요구를 올리는 거래**라는 프레임으로 말하면 트레이드오프를 이해하고 있음이 드러난다.

**그리고 문제가 다 안 풀린다.** 최소 TTL을 강제하는 리졸버는 내 값을 무시하고, 커넥션 풀은 TTL과 무관하게 옛 IP를 붙들고 있으며, 헬스체크 감지 지연과 레코드 전파 시간은 TTL을 0으로 해도 남는다.

결론은 **"평상시엔 적당한 TTL, 계획된 전환 전에만 낮췄다가 끝나면 원복"**이라는 운영이다. 그리고 원복이 절차에 명시돼 있어야 한다는 점까지 말하면 좋다 — 낮춘 채 방치하는 사고가 실제로 흔하다.

### "커넥션 풀을 쓰는 서버 간 호출에서 DNS 전환이 반영 안 되는 이유와 대응은?"

**이유는 두 겹이다.**

**첫째, DNS는 새 연결을 맺을 때만 조회된다.** 그런데 커넥션 풀의 존재 이유가 "연결을 다시 맺지 않는 것"이라 재조회 계기가 구조적으로 없다. 게다가 한 번 맺어진 TCP 연결은 4-튜플로 고정돼 목적지 IP가 그 연결의 정체성의 일부이므로, **살아 있는 연결의 목적지를 바꿀 방법 자체가 없다.**

**둘째, 재연결을 하더라도 JVM DNS 캐시가 옛 IP를 돌려주면 다시 옛 서버에 붙는다.** 자물쇠가 두 개라서 하나만 풀면 증상이 그대로 남는다.

**대응도 그래서 두 겹 + 서버 쪽 조치다.**

풀 커넥션에 **최대 수명(`setTimeToLive` / `maxLifeTime` / `maxLifetime`)**을 걸어 주기적 재연결을 강제하고, 유휴 상한도 함께 줄여 놀고 있는 연결이 옛 IP에 오래 물려 있지 않게 한다. **이 값이 곧 "전환이 반영되기까지의 상한"**이라는 점을 말하면 좋다.

**JVM DNS 캐시 TTL을 명시**해 재연결 시점에 새 IP가 나오게 한다.

**전환 시 옛 서버가 연결을 우아하게 놓아준다.** nginx라면 `keepalive_timeout 0`으로 응답에 `Connection: close`를 붙여 클라이언트가 재연결하게 만든다. 우리가 통제하지 못하는 외부 클라이언트에 대해서는 이것이 유일한 수단이다.

**그리고 가장 확실한 것은 전환 절차에 롤링 재시작을 넣는 것**이다. 프로세스가 새로 뜨면 풀도 캐시도 비어 있으므로 무조건 새 IP로 붙는다. **"설정을 정교하게 맞추는 것"보다 실패 확률이 낮다**는 판단까지 말하면 운영 감각이 드러난다.

### "DNS 기반 failover는 그럼 어디에 적합한가요?" (시니어 변별 포인트)

**전환 단위가 크고 RTO가 분 단위 이상 허용되는 자리**다. 리전 전체 장애의 재해 복구, 데이터센터 이전, 지리 기반 분배(GSLB)의 상위 라우팅 같은 것들이다. 이런 전환은 어차피 데이터 복제 상태 확인이나 대기 환경 기동에 분 단위가 걸리므로, DNS 전파 시간이 병목이 아니다.

반대로 **서버 몇 대의 장애 대응처럼 초 단위가 필요한 곳은 LB 헬스체크나 VIP 이관이 맡아야 한다.** 이 둘은 클라이언트가 보는 IP를 바꾸지 않으므로 전파할 것이 없고, 그래서 즉시 반영된다.

즉 답의 형태는 "DNS는 좋다/나쁘다"가 아니라 **계층별 역할 배치**다. **빠른 전환은 IP가 안 바뀌는 지점(LB, VIP, anycast)에서, 큰 단위의 전환만 DNS에서.** 이렇게 나누면 각 계층이 자기가 잘하는 일만 한다.

여기에 두 가지를 더 얹으면 시니어로 보인다.

**첫째, DNS failover를 쓴다면 그 전파 지연을 RTO 계산에 명시적으로 넣어야 한다.** 3-1절처럼 감지 + 갱신 + TTL + 클라이언트 재조회로 분해해서 더한 값이 실제 RTO다. 이 계산 없이 "failover 설정했으니 RTO 30초"라고 적힌 문서는 실제 장애 때 그대로 깨진다.

**둘째, 계산만으로 끝내지 말고 실제로 전환 훈련을 해서 측정해야 한다.** 계산에는 안 잡히는 것들 — 커넥션 풀, 하드코딩된 IP, TTL을 늘려 잡는 리졸버 — 이 훈련에서 드러난다. **재해 복구를 문서가 아니라 운영으로 다뤄본 사람인지가 여기서 갈린다.**

### "블루-그린 배포를 DNS 전환으로 구현하면 어떤 문제가 있나요?"

**블루-그린의 핵심 가치가 즉시 전환과 즉시 롤백인데, DNS 전환은 그 둘을 정확히 못 해준다.** 가치의 전제를 깨는 구현이라 문제가 된다.

**전환이 물결이라 두 버전이 오래 공존한다.** TTL과 캐시 꼬리 때문에 사용자마다 구버전과 신버전에 제각각 도달하는 기간이 길어진다. 그동안 두 버전이 같은 DB를 쓴다면 **스키마와 데이터가 양쪽 버전 모두에서 안전해야** 하고, 세션이나 캐시를 공유한다면 그것도 양쪽 호환이어야 한다. 즉 **양버전 호환성을 유지해야 하는 기간이 계획보다 훨씬 길어진다.**

**롤백도 같은 지연을 다시 겪는다.** 문제를 발견하고 레코드를 되돌려도 다시 TTL만큼 물결이 번진다. **문제를 발견한 순간부터 피해가 멈추기까지 몇 분이 걸린다**는 뜻이고, 이건 블루-그린을 도입한 이유 자체를 무효로 만든다.

**커넥션 풀 문제까지 겹치면 롤백이 아예 안 먹을 수도 있다.** 신버전에 물린 연결은 레코드를 되돌려도 그대로 신버전으로 간다(2-3절).

그래서 **정석은 전환점을 LB에 두는 것**이다. 대상 그룹을 바꾸는 것은 즉시 반영되고 즉시 되돌릴 수 있으며, 클라이언트가 보는 IP는 그대로다. **DNS는 그 LB를 가리키는 "안 바뀌는 이름"으로만 쓴다.** 1-4절의 "자주 바뀌는 것은 사슬 아래쪽에, 안 바뀌는 이름은 위쪽에"가 여기서 그대로 적용된다.

### "레코드에 IP를 여러 개 넣어두면 클라이언트가 알아서 failover하지 않나요?" (가산점 포인트)

**될 수도 있고 안 될 수도 있다. 그리고 그게 이 방법의 핵심 리스크다.**

먼저 원리는 맞다. 한 이름에 A 레코드를 여러 개 두면 리졸버가 그 목록을 전부 돌려주고, **잘 만들어진 클라이언트는 첫 IP에 연결이 실패하면 다음 IP로 즉시 넘어간다.** 이 경우 전환 시간은 DNS와 아무 상관이 없다 — **이미 손에 들고 있는 목록 안에서 해결되므로 연결 타임아웃 한 번이면 끝난다.** 3-1절의 네 단계가 통째로 사라지는 셈이다.

**문제는 "잘 만들어진"이라는 전제다.** 클라이언트마다 동작이 다르다. 목록을 다 받아놓고도 첫 번째만 시도하고 포기하는 라이브러리가 흔하고, 재시도를 하더라도 그 시점이 언제인지, 실패한 IP를 얼마나 기억하는지가 제각각이다. **그래서 이 방식은 "클라이언트를 우리가 통제할 수 있는 구간"에서만 설계 수단으로 쓸 수 있다.** 브라우저나 파트너사의 클라이언트처럼 통제 밖이면 기대할 수 없다.

두 가지를 덧붙이면 좋다.

**첫째, 연결 실패는 넘어가지만 "느린 서버"는 못 넘어간다.** 다음 IP로 넘어가는 조건은 대개 연결 실패다. 서버가 살아 있는데 응답만 극도로 느린 상태라면 클라이언트는 그 IP에 계속 붙어 있다. **헬스체크로 판정해 목록에서 빼주는 주체가 따로 있어야** 하고, 그게 LB가 하는 일이다.

**둘째, 여러 IP를 돌려주는 것 자체는 부하 분산 수단으로는 약하다.** 리졸버가 순서를 바꿔 돌려주는 정도라 분배가 균등하지 않고, 캐시 때문에 특정 리졸버를 쓰는 사용자 전체가 같은 IP에 몰릴 수 있다. **분배는 LB에게 맡기고, 다중 IP는 "LB 자체가 죽었을 때의 마지막 안전망"으로 쓰는 것**이 역할 배치로 맞다.

## 한 줄 요약

TTL은 캐시 유효기간의 상한일 뿐 동기화 신호가 아니어서, 각 캐시가 자기 조회 시점부터 따로 만료를 세는 DNS 전환은 언제나 물결처럼 번지고 긴 꼬리를 남긴다 — TTL을 늘려 잡는 리졸버, JVM 캐시, 그리고 TTL과 무관하게 옛 IP에 물려 있는 커넥션 풀까지 감안해 "기존 TTL 이상 앞선 TTL 인하 → 양쪽 공존 전환 + 롤링 재시작 + 구서버 drain → 유입 0을 관측으로 확인한 뒤 종료 → TTL 원복"의 시간축 절차로 설계해야 하고, 감지·전파·TTL·클라이언트 재조회를 더하면 분 단위가 나오므로 초 단위 failover가 필요한 곳은 DNS가 아니라 IP가 바뀌지 않는 지점(LB 대상 그룹, VIP, anycast)에서 전환해야 한다.
