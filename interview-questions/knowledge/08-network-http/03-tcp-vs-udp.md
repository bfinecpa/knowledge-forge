# TCP vs UDP — 신뢰성의 비용과 프로토콜 선택의 기준

> 핵심 관전 포인트: **TCP는 연결 수립·순서 보장·재전송·흐름/혼잡
> 제어로 "빠짐없이 순서대로"를 보장하는 대신, 그 보장 장치들이
> 지연이라는 비용을 만든다 — 패킷 하나가 유실되면 재전송될 때까지
> 뒤 패킷들이 전부 대기한다. UDP는 그 장치를 다 뺀 최소한의
> 전송(포트 + 체크섬)이라 빠르고 오버헤드가 없지만 유실·순서 뒤바뀜을
> 감수해야 한다. 선택 기준은 "유실된 데이터를 재전송으로 복구할
> 가치가 있는가"다 — 늦게 도착한 데이터가 무가치한 실시간
> 스트리밍·게임·통화는 UDP 계열, 하나라도 빠지면 안 되는 파일 전송·
> API 호출은 TCP. 요구사항이 프로토콜을 고른다.**

---

## 0. 질문 + 의도

**질문**: "TCP와 UDP의 차이는?"

**출제 의도**: 신뢰성의 비용(재전송, 순서 보장으로 인한 지연)을
이해하는지. "왜 실시간 스트리밍은 UDP 계열인가"에 답할 수 있으면
프로토콜을 요구사항에 맞춰 고르는 사고가 있는 것이다.

## 1. 차이의 본질 — 무엇을 보장하고, 무엇을 포기했나

두 프로토콜 모두 IP 위에서 동작하는 전송 계층이고, IP 자체는 "패킷을
목적지 방향으로 던질 뿐" 도착·순서를 전혀 보장하지 않는다. 그 위에서
**TCP는 보장을 쌓아 올린 프로토콜, UDP는 거의 아무것도 얹지 않은
프로토콜**이다.

| 항목 | TCP | UDP |
|---|---|---|
| 연결 | 연결 지향 (3-way handshake) | 비연결 — 그냥 보냄 |
| 도착 보장 | 재전송으로 보장 | 없음 (유실되면 그만) |
| 순서 보장 | 시퀀스 번호로 보장 | 없음 |
| 흐름/혼잡 제어 | 있음 | 없음 |
| 전송 단위 | 바이트 스트림 (경계 없음) | 데이터그램 (메시지 경계 유지) |
| 헤더 | 20바이트+ | 8바이트 |

각 항목을 풀면:

- **연결**: TCP는 대화 전에 handshake로 회선을 뚫고 상태를 유지한다.
  UDP는 상태가 없다 — 편지를 우체통에 넣듯 각 패킷을 독립적으로
  던진다. 전화(TCP)와 엽서(UDP)의 차이다.
- **도착·순서 보장**: TCP는 받은 쪽이 "여기까지 받았다"고 확인(ACK)
  하고, 확인이 안 온 조각은 다시 보내며, 시퀀스 번호로 원래 순서대로
  재조립한다. UDP는 유실돼도, 순서가 바뀌어도 아무도 모른다 —
  알아야 한다면 애플리케이션이 직접 챙겨야 한다.
- **흐름/혼잡 제어**: TCP는 수신자의 처리 용량(흐름 제어)과 네트워크
  혼잡(혼잡 제어)에 맞춰 전송 속도를 스스로 조절한다. UDP는 조절
  없이 애플리케이션이 주는 대로 쏜다.
- **스트림 vs 데이터그램**: TCP는 경계 없는 바이트 흐름이라 "어디까지가
  한 메시지인가"를 애플리케이션이 정해야 하고(HTTP의 Content-Length
  같은 프레이밍), UDP는 보낸 패킷 하나가 그대로 메시지 하나다.

## 2. 신뢰성의 비용 — 보장 장치가 지연을 만드는 메커니즘

면접의 승부처는 표 암기가 아니라 **"TCP의 보장은 공짜가 아니다"를
메커니즘으로 설명하는 것**이다.

1. **연결 수립 비용**: 데이터를 보내기 전에 handshake 1 RTT를 선불로
   낸다. 짧은 요청 하나를 보내는 데도 왕복이 하나 더 붙는다.
2. **재전송 대기**: 유실을 복구하려면 "유실됐음을 알아채는 시간 +
   다시 보내는 시간"이 든다. 그 사이 데이터는 멈춰 있다.
3. **순서 보장의 연쇄 대기**: 가장 중요한 비용이다. 100번 패킷이
   유실되면 101, 102, …가 이미 도착해 있어도 수신 애플리케이션에
   전달되지 않는다 — TCP는 "순서대로"를 약속했으므로 100번이
   재전송되어 도착할 때까지 **뒤 패킷 전부를 버퍼에 잡아둔다**.
   패킷 하나의 유실이 스트림 전체를 멈추는 이 현상이 TCP의
   HOL(head-of-line) blocking이다.

이 비용이 치명적인 도메인이 실시간 통신이다. 화상 통화에서 0.1초
전 프레임이 유실됐다고 하자 — TCP라면 그 옛 프레임을 재전송받을
때까지 이후 프레임을 전부 멈춰 세운다. 하지만 통화에서 **지나간
프레임은 도착해봤자 이미 가치가 없다**. 차라리 그 프레임은 버리고
(화면 잠깐 깨짐) 최신 프레임을 계속 보여주는 것이 낫다. "늦은 데이터
= 무가치한 데이터"인 도메인에서 재전송·순서 보장은 보장이 아니라
방해다 — 실시간 스트리밍·게임·통화가 UDP 계열을 쓰는 이유의 전부가
이 한 문장이다.

반대로 파일 전송·결제 API·DB 통신은 1바이트라도 빠지거나 순서가
바뀌면 데이터가 깨진다. 지연을 감수하더라도 완전성이 우선이므로
TCP다.

## 3. 선택 기준과 실제 사례 — 요구사항이 프로토콜을 고른다

선택의 질문은 하나로 압축된다: **"유실된 패킷을 기다려서 복구할
가치가 있는 데이터인가?"**

- **HTTP API, 파일 전송, DB 프로토콜 → TCP**: 완전성이 생명.
  유실 복구를 프로토콜에 맡기고 애플리케이션은 비즈니스에 집중한다.
- **DNS 조회 → UDP**: 요청·응답이 각각 패킷 하나에 들어가는 작은
  교환이다. 유실되면 클라이언트가 통째로 다시 물어보면 그만이라
  재전송 로직이 하찮을 만큼 단순하고, 조회마다 handshake를 치르는
  것이 오히려 낭비다. (응답이 크거나 신뢰성이 필요한 존 전송 등은
  TCP로 전환한다.)
- **실시간 스트리밍·게임·통화 → UDP + 애플리케이션 계층 프로토콜**:
  UDP를 날것으로 쓰는 게 아니라 그 위에 RTP처럼 타임스탬프·순서
  번호를 얹되, **복구 정책은 도메인에 맞게 선택**한다 — 오래된
  프레임은 버리고, 게임이면 최신 좌표만 반영하고, 필요한 만큼만
  선별적으로 보정한다. "TCP의 일괄 보장" 대신 "우리 도메인에 맞는
  맞춤 보장"을 직접 구현하는 것이다.

```java
// TCP: 연결을 먼저 맺고, 경계 없는 스트림에 쓴다 — 도착·순서는 프로토콜이 보장
try (Socket socket = new Socket("host", 8080)) {          // 3-way handshake
    socket.getOutputStream().write(data);                  // 유실 시 자동 재전송
}

// UDP: 연결 없이 데이터그램을 그냥 던진다 — 도착 여부를 아무도 확인하지 않음
try (DatagramSocket socket = new DatagramSocket()) {
    socket.send(new DatagramPacket(data, data.length, addr, 8080));
    // 유실·순서 뒤바뀜의 감지와 대응은 전부 애플리케이션 몫
}
```

### HTTP/3(QUIC) — 이 구분이 최신 프로토콜로 이어지는 지점 (가산점 포인트)

HTTP/3는 TCP를 버리고 **UDP 위에 QUIC**을 얹었다. "신뢰성이 필요한
웹이 왜 UDP를?"이 좋은 질문인데, 답은 "신뢰성을 포기한 게 아니라
**신뢰성을 애플리케이션 계층에서 다시, 더 똑똑하게 구현**했다"이다.
TCP의 순서 보장은 커넥션 전체에 하나라서 스트림 하나의 유실이 그
커넥션에 실린 모든 요청을 멈춘다(HOL blocking). QUIC은 UDP 위에서
스트림별로 독립적인 순서·재전송을 구현해, 한 스트림의 유실이 다른
스트림을 막지 않게 했다. TCP/UDP의 차이를 정확히 아는 사람만 이
설계 의도를 설명할 수 있다 — "UDP는 신뢰성이 없다"에서 멈추지 않고
"신뢰성을 어느 계층에서 구현할지의 선택지"로 말하면 좋다.

## 4. 꼬리질문 대비 포인트

### "UDP는 신뢰성이 없는데 DNS는 왜 UDP를 쓰나요?"

DNS 조회는 작은 요청 하나·응답 하나의 교환이라 유실 시 복구 전략이
"그냥 다시 물어본다"로 충분히 단순하다. 신뢰성이 필요 없는 게 아니라
**애플리케이션 수준의 재시도만으로 신뢰성이 값싸게 확보되는 경우**라서,
조회마다 TCP handshake(1 RTT)를 내는 비용이 이득보다 크다. 즉 "얼마나
중요한 데이터냐"가 아니라 "복구 비용이 어느 계층에서 싸냐"의 문제다.
같은 DNS도 응답이 크거나(패킷 하나에 안 담김) 존 전송처럼 완전성이
필요한 작업은 TCP로 전환한다는 것까지 말하면 좋다.

### "실시간 스트리밍이나 게임은 왜 UDP 계열을 쓰나요?"

그 도메인에서는 **늦게 도착한 데이터가 무가치**하기 때문이다. TCP는
유실 패킷을 재전송받을 때까지 뒤 패킷을 전부 잡아두는데(순서 보장),
통화·게임에서 0.5초 전 프레임을 복구하느라 지금 프레임을 멈추는 것은
최악의 선택이다. UDP로 보내고 유실은 버리며 최신 데이터를 계속
흘리는 편이 체감 품질이 높다. 다만 날 UDP가 아니라 RTP 같은 상위
프로토콜로 타임스탬프·순서 번호를 얹어 "버릴 것과 보정할 것"을
도메인 규칙으로 직접 정한다.

### "TCP의 순서 보장이 오히려 지연을 만드는 이유를 설명해주세요."

시퀀스 번호 N이 유실되면 N+1 이후가 이미 도착해 있어도 애플리케이션에
전달할 수 없다 — "순서대로"라는 계약 때문에 N의 재전송 도착까지
전부 수신 버퍼에 대기한다. 패킷 하나의 유실이 그 커넥션의 스트림
전체를 멈추는 HOL blocking이다. 이 문제의식이 HTTP/2(한 TCP 커넥션에
여러 요청을 실으면 TCP 계층 HOL은 여전)를 거쳐, 스트림별 독립 전송을
UDP 위에 구현한 HTTP/3(QUIC)로 이어진다.

### "UDP 위에 신뢰성이 필요하면 어떻게 하나요?" (가산점 포인트)

애플리케이션 계층에서 필요한 만큼만 구현한다 — 순서 번호와 ACK,
선별적 재전송, 타임스탬프 기반 폐기 정책 등을 도메인 요구에 맞춰
조립한다. 대표 사례가 QUIC으로, UDP 위에 스트림별 재전송·순서 보장·
흐름 제어에 TLS까지 통합해 "TCP + TLS보다 왕복이 적고 HOL blocking이
없는" 전송을 만들었다. 요점은 신뢰성이 TCP의 전유물이 아니라 **어느
계층에서 어떤 범위로 구현할지 선택 가능한 속성**이라는 것이다.

### "새 기능에서 전송 프로토콜을 골라야 한다면 어떤 기준으로 판단하나요?" (시니어 변별 포인트)

첫 질문은 "유실된 데이터를 기다려 복구할 가치가 있는가"다. 완전성이
필수(결제, 파일, 일반 API)면 TCP — 검증된 보장을 공짜로 얻는다.
최신성이 완전성보다 중요(실시간 위치, 미디어)하면 UDP 계열 + 도메인
맞춤 복구 정책. 다만 실무에서는 순수 성능 외의 제약이 결정을 뒤집을
수 있다는 것까지 본다 — 방화벽·기업망의 UDP 차단, 로드밸런서/인프라의
지원 범위, 직접 구현할 신뢰성 계층의 개발·운영 비용. 그래서 대부분의
경우 "웹은 TCP(HTTP) 기본, 실시간 요구가 수치로 검증될 때만 UDP
계열 도입"이 현실적 기준이고, 요구사항의 '실시간'이 진짜 몇 초/몇 ms
수준인지 되묻는 것이 판단의 시작이라고 답하면 설계 경험이 드러난다.

## 한 줄 요약

TCP는 재전송·순서 보장·혼잡 제어로 완전성을 보장하는 대신 유실 하나가
스트림을 멈추는 지연 비용을 내고, UDP는 보장 없이 던지는 대신 빠르고
가벼우므로, "늦게 도착한 데이터에 가치가 있는가"라는 요구사항 질문이
프로토콜을 고른다 — DNS·스트리밍·QUIC 모두 이 기준으로 설명되는
사례들이다.
