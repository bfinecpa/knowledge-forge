# 간헐적 timeout의 네트워크 계층 추적 — tcpdump·MTU·재전송으로 앱 로그 밖의 범인을 잡는다

> 핵심 관전 포인트: **"특정 사용자만 + 간헐적"이라는 패턴 자체가 첫
> 단서다 — 코드 버그면 모두에게, 서버 과부하면 그 시간대 모두에게
> 나타난다. 특정 사용자에게만 나는 timeout은 그 사용자의 네트워크
> 경로에 의존하는 문제(MTU/PMTUD 블랙홀, 특정 구간 패킷 유실·재전송,
> 중간 장비의 유휴 커넥션 드랍)일 가능성이 높다. 추적 절차는 (1) 상관관계로
> 용의 범위 좁히기 — 어떤 사용자·요청 크기·타이밍·서버 인스턴스에서만
> 나는가, (2) tcpdump로 패킷이 실제로 어디까지 도달했는지 확인 — 필요하면
> 양단 동시 캡처로 유실 구간을 특정, (3) 재전송·MTU·idle drop 각각의
> 시그니처와 대조하는 순서다. timeout은 앱 로그에 "일어난 일"이 아니라
> "일어나지 않은 일"로만 남기 때문에, 스택 아래로 내려가야 잡힌다.**

---

## 0. 질문 + 의도

**질문**: "특정 사용자만 간헐적으로 timeout이 발생합니다. 네트워크 계층에서 어떻게 추적하나요? (tcpdump, MTU, retransmission)"

**출제 의도**: 애플리케이션 로그에 안 남는 문제를 tcpdump까지 내려가
잡는 능력은 흔치 않고, 이게 되는 사람은 팀에서 "미제 사건 해결사"가
된다. 스택 아래로 내려가길 두려워하지 않는지 — 프레임워크가 가려주는
계층 밑에서 무슨 일이 벌어지는지 직접 확인할 수 있는지를 본다.

## 1. 왜 애플리케이션 로그로는 못 잡는가

timeout은 "무언가 일어났다"가 아니라 **"기다렸는데 아무것도 오지
않았다"**는 기록이다. 그래서 로그가 알려주는 것이 근본적으로 빈약하다.

- 요청 패킷이 서버에 **도달하지 못했다면** 앱 로그에는 아무것도 없다.
  "로그에 없으니 요청이 안 온 것"까지는 알아도, 어디서 사라졌는지는
  모른다.
- 도달했더라도 access log에는 "이 요청이 오래 걸렸다"만 남는다.
  그 시간이 앱 처리에 쓰였는지, 네트워크 재전송 대기에 쓰였는지
  구분이 안 된다.
- OS의 TCP 스택은 패킷이 유실되면 **앱 몰래 재전송**한다. 앱 입장에서는
  그냥 "응답이 느리다"로만 보이고, 유실이 있었다는 사실 자체가
  애플리케이션 계층에는 전달되지 않는다.

즉 이 문제의 증거는 애플리케이션 계층이 아니라 **패킷 계층에만** 있고,
그래서 tcpdump 같은 패킷 캡처 도구가 필요하다.

## 2. 1단계 — 패턴으로 용의 범위 좁히기

바로 tcpdump를 켜는 것이 아니라, 먼저 "특정 사용자만·간헐적"이라는
패턴을 **여러 축으로 쪼개서** 가설을 세운다. 축마다 의심 대상이 다르다.

| 관찰된 패턴 | 유력한 가설 |
|---|---|
| 큰 요청/응답에서만 실패 (작은 API는 정상) | MTU/PMTUD 블랙홀 |
| 커넥션이 한동안 쉰 뒤 첫 요청만 실패 | 중간 장비(NAT/방화벽/LB)의 유휴 커넥션 드랍 |
| 특정 서버 인스턴스로 갈 때만 실패 | 그 서버의 NIC 큐 드랍, conntrack 포화 |
| 특정 ISP/지역/VPN 사용자만 실패 | 그 경로 구간의 유실·MTU |

확인 방법: 문제 사용자의 요청 시각·클라이언트 IP를 받아서, LB access
log와 대조한다 — "그 시각에 그 IP의 요청이 LB에는 도달했는가? 어느
백엔드로 갔는가? LB가 기록한 소요 시간 내역은?" 여기까지로 이미 "LB
앞이 문제인지 뒤가 문제인지"가 절반은 갈린다.

## 3. 2단계 — tcpdump로 사실 확인

가설이 섰으면 패킷 수준에서 사실을 확인한다. 핵심 원칙은 **범위를
좁혀서 캡처**하는 것이다(운영 부하와 분석량 모두를 위해).

```bash
# 문제 사용자 IP로 좁혀 캡처 — 파일 로테이션으로 디스크 보호
tcpdump -i any host 203.0.113.7 -w /var/tmp/user.pcap -C 100 -W 5

# 커넥션의 생사만 빠르게 보려면 제어 플래그(SYN/FIN/RST)만
tcpdump -i any host 203.0.113.7 -nn \
  'tcp[tcpflags] & (tcp-syn|tcp-fin|tcp-rst) != 0'
```

캡처를 Wireshark로 열어 보는 대표 시그니처:

- **TCP Retransmission / Dup ACK** — 패킷 유실이 있었다는 직접 증거
- **SYN만 반복되고 SYN-ACK가 없음** — 연결 자체가 안 됨(방화벽 drop,
  서버 backlog 포화)
- **연결은 됐는데 특정 크기의 데이터부터 침묵** — MTU 냄새
- **Zero Window** — 상대(또는 우리) 앱이 버퍼를 안 비움: 네트워크가
  아니라 수신 측 처리 지연

가장 강력한 기법은 **양단(또는 구간별) 동시 캡처 비교**다. 클라이언트
쪽 캡처에는 패킷을 보낸 기록이 있는데 서버 쪽 캡처에 없다면, 유실은
그 **사이 구간**에서 일어난 것이다. LB 앞뒤로 나눠 캡처하면 "LB까지는
왔는가"를 판정해 책임 구간을 절반씩 잘라나갈 수 있다 — 이 이분법이
네트워크 디버깅의 기본기다.

## 4. 3단계 — 대표 범인 3가지와 각각의 시그니처

### (1) 재전송(retransmission) — 어딘가에서 패킷이 새고 있다

패킷이 유실되면 TCP는 재전송 타임아웃(RTO)만큼 기다렸다 다시 보낸다.
유실이 반복되면 대기 시간이 지수적으로 늘며(백오프) 응답이 수 초씩
튀고, 앱 타임아웃을 넘겨버린다. "간헐적으로 느리다"의 가장 흔한 정체다.

확인은 캡처 외에 서버 카운터로도 가능하다:

```bash
ss -ti dst 203.0.113.7   # 소켓별 retrans 카운트, rtt 확인
netstat -s | grep -i retrans   # 시스템 전체 재전송 통계 추이
```

다음 단계는 **유실이 어느 쪽 책임인지 구분**하는 것: 서버 자체 원인
(NIC 큐 드랍 통계, `nf_conntrack: table full` 커널 로그 — 연결 추적
테이블이 차면 새 패킷을 조용히 버린다)이 아니라면 경로 상 구간 문제이고,
양단 캡처 비교로 구간을 특정해 해당 구간 운영 주체(사내 네트워크팀,
클라우드, ISP)에 증거와 함께 넘긴다.

### (2) MTU/PMTUD 블랙홀 — 큰 패킷만 조용히 사라진다

MTU는 한 번에 보낼 수 있는 패킷의 최대 크기다. 경로 중간에 MTU가
작은 구간(VPN, 터널, PPPoE)이 있으면, 원래는 중간 장비가 ICMP로
"패킷이 커서 못 보내니 줄여라"라고 알려주고 발신자가 줄이는 절차
(Path MTU Discovery)가 동작한다. 문제는 **그 ICMP를 방화벽이 막는
경우** — 발신자는 통보를 못 받고 큰 패킷을 계속 보내고, 큰 패킷만
영원히 사라진다. 이것이 "PMTUD 블랙홀"이다.

시그니처가 특징적이다: **작은 패킷(연결 수립, 작은 API)은 멀쩡한데,
큰 응답·업로드·TLS 핸드셰이크(인증서 데이터가 큼)에서만 멈춘다.**
그리고 그 작은 MTU 구간을 지나는 경로의 사용자에게만 나타나므로
"특정 사용자만"이라는 조건과 정확히 맞아떨어진다.

```bash
# 확인: DF(분할 금지)를 걸고 패킷 크기를 바꿔가며 경로의 한계를 찾는다
ping -M do -s 1472 <상대 호스트>   # 헤더 28바이트 포함 1500 — 통과하는가?
ping -M do -s 1400 <상대 호스트>   # 어느 크기부터 응답이 사라지는가?
```

대응은 서버/터널의 MTU 조정, 또는 TCP 연결 수립 때 협상되는 세그먼트
크기를 중간에서 강제로 줄이는 **MSS clamping**이다.

### (3) 중간 장비의 유휴 커넥션 드랍 — 풀의 커넥션이 몰래 죽어 있다

NAT·방화벽·LB 같은 중간 장비는 자기 테이블에서 유휴 커넥션을 정리하는데,
이때 양단에 **아무 통보 없이(RST 없이)** 지우는 경우가 있다. 클라이언트의
커넥션 풀은 그 커넥션이 살아있다고 믿고 재사용하고, 보낸 요청은
허공으로 사라져 **유휴 후 첫 요청만 timeout**이 난다. "간헐적 timeout"의
단골 범인이다.

```java
// Before: 중간 장비의 idle 정리 시간을 모른 채 커넥션을 오래 보유
//         → 오랜만의 요청이 죽은 커넥션을 타고 나가 timeout

// After: 풀의 유휴 수명을 중간 장비의 정리 주기보다 짧게
PoolingHttpClientConnectionManager cm = new PoolingHttpClientConnectionManager();
// 유휴 커넥션을 중간 장비보다 먼저 정리하고,
// 재사용 전 유효성 검증 주기를 함께 설정한다
```

핵심 대응은 (1) 풀의 idle/max-lifetime을 **경로 상 가장 짧은 장비의
정리 주기보다 짧게**, (2) TCP keepalive나 재사용 전 검증으로 죽은
커넥션을 걸러내는 것이다.

## 5. 꼬리질문 대비 포인트

### "tcpdump 캡처에서 재전송이 보이면 그 다음엔 뭘 하나요?"

재전송은 "유실이 있었다"까지만 말해준다. 다음은 **어디서 유실됐는지**의
구간 특정 — 양단(클라이언트/서버, 또는 LB 앞/뒤) 동시 캡처를 비교해서
"보낸 기록은 있는데 받은 기록이 없는" 구간을 찾는다. 병행해서 서버
자체 원인(NIC 드랍 카운터, conntrack 포화, 소켓 버퍼)을 배제한다.
구간이 외부(ISP, 클라우드 네트워크)로 특정되면 캡처 증거를 첨부해
해당 운영 주체에 이관한다 — 증거 없는 "네트워크가 이상해요"는 아무도
움직이지 못한다.

### "MTU 문제는 왜 '특정 사용자만'으로 나타나나요?"

MTU 병목은 **경로의 속성**이기 때문이다. 같은 서버라도 사용자마다
지나는 경로가 다르고, VPN·특정 ISP·해외 회선처럼 MTU가 작은 구간을
지나는 사용자만 걸린다. 게다가 작은 패킷은 통과하므로 그 사용자조차
"어떤 요청은 되고 어떤 요청은 안 되는" 간헐 증상으로 보인다 —
전형적인 "재현 안 되는 버그"의 정체다.

### "운영 서버에서 tcpdump를 켤 때 주의할 점은?" (시니어 변별 포인트)

(1) **부하**: 필터 없이 전체 트래픽을 캡처하면 CPU·디스크를 잡아먹는다.
반드시 host/port 필터로 좁히고, `-C`/`-W`로 파일 크기·개수를 제한하며,
필요한 헤더만 뜨도록 snap 길이(`-s`)를 줄인다. (2) **민감정보**: 평문
프로토콜이면 페이로드에 개인정보·인증정보가 그대로 담긴다. 캡처 파일의
보관·공유·폐기를 통제해야 하고, 가능하면 헤더 길이만 캡처한다.
(3) **종료 관리**: 켜두고 잊으면 디스크가 찬다 — 시간 제한이나 로테이션을
반드시 건다. 이 세 가지를 먼저 말하는 것이 운영 경험의 증거다.

### "트래픽이 TLS라서 내용이 안 보이는데, 뭘 분석할 수 있나요?" (가산점 포인트)

timeout 추적에는 페이로드가 필요 없다. TCP 계층의 정보 — 핸드셰이크
성사 여부, 재전송, RTT, 윈도 크기, RST — 는 암호화와 무관하게 전부
보이고, "패킷이 어디까지 갔는가"는 이것으로 판정된다. TLS 핸드셰이크
자체도 어느 단계에서 멈췄는지 관찰 가능하다. 즉 암호화는 "무엇을
주고받았나"를 가리지만 "통신이 건강한가"는 가리지 못한다.

### "매번 tcpdump로 잡지 않으려면 평소에 뭘 준비해두나요?"

(1) 재전송·소켓 통계를 서버 메트릭으로 상시 수집해서 baseline과의
편차로 알림을 건다. (2) LB access log에 구간별 소요 시간(백엔드 연결
시간, 응답 시간)을 남겨 "LB 앞/뒤" 판정을 로그만으로 할 수 있게 한다.
(3) timeout 에러율을 사용자·지역·인스턴스 차원으로 쪼개 볼 수 있는
대시보드를 준비한다 — 이 문서의 1단계(패턴 좁히기)를 사건이 터진 뒤가
아니라 상시 관측으로 만드는 것이다.

## 한 줄 요약

"특정 사용자만 간헐적 timeout"은 경로 의존적 네트워크 문제의 시그니처이며,
추적은 패턴으로 가설을 좁히고(크기 의존=MTU, 유휴 후 첫 요청=idle drop,
인스턴스 의존=서버 큐/conntrack) → tcpdump 양단 캡처로 패킷이 사라진
구간을 특정하고 → 재전송·MTU·드랍 각각의 시그니처와 대조하는 순서다 —
timeout은 앱 로그에 "없었던 일"로만 남으므로, 증거는 패킷 계층에서
직접 채집해야 한다.
