# 응답 압축(gzip/brotli) — "켜면 좋은 옵션"에도 비용 계산이 필요하다

> 핵심 관전 포인트: **응답 압축은 CPU 시간을 지불하고 전송량(대역폭·
> 전송 시간)을 사는 교환이다. 텍스트 계열(HTML, JSON, JS, CSS)은
> 압축률이 커서 남는 장사지만, 압축하지 말아야 할 응답이 분명히 있다 —
> ① 이미 압축된 포맷(JPEG/PNG/WebP, 동영상, zip)은 더 안 줄고 CPU만
> 태우며 오히려 커질 수도 있고, ② 아주 작은 응답은 압축 오버헤드가
> 절감분을 넘어서며, ③ 비밀값과 공격자가 조작한 입력이 한 응답에 섞이는
> 경우 압축 후 크기가 비밀을 누설하는 부채널(BREACH 계열)이 된다.
> gzip은 호환성의 기본값, brotli는 같은 비용에서 더 나은 압축률 —
> 특히 정적 자원을 빌드 타임에 최고 레벨로 미리 압축해 두는 전략에서
> 강하다. 어디서 압축할지(앱/Nginx/CDN)와 `Vary: Accept-Encoding`까지
> 챙기면 완성이다.**

---

## 0. 질문 + 의도

**질문**: "응답 압축(gzip/brotli)의 트레이드오프는? 압축하지 말아야 할
응답은?"

**출제 의도**: 압축은 CPU와 대역폭의 교환이며, 이미 압축된 포맷
(이미지)엔 낭비임을 아는지 — "켜면 좋은 옵션"에도 비용 계산을 하는
습관의 표본이다. 설정 하나에도 무엇을 내주고 무엇을 얻는지 따지는
사고방식이 있는지를 보는 질문이다.

## 1. 본질 — CPU를 내고 전송량을 산다

압축의 손익 구조는 한 줄이다: **서버(와 클라이언트)의 CPU 시간을
지불하고, 네트워크로 나가는 바이트를 줄인다.**

- **얻는 것**: 전송량 감소 → 대역폭 비용 절감 + 전송 시간 단축.
  특히 회선이 느린 사용자(모바일)일수록 체감 효과가 크다. 텍스트
  계열(HTML, JSON, JS, CSS)은 반복 패턴이 많아 수 배 수준으로 줄어드는
  게 보통이다.
- **내는 것**: 응답마다 압축 연산(CPU) + 약간의 지연(압축을 끝내거나
  버퍼를 채워야 내보낼 수 있음) + 클라이언트의 해제 비용(이건 대체로
  미미하다).

- 비유: 이삿짐을 **압축팩에 넣는 것**이다. 옷·이불(텍스트)은 부피가
  확 줄어 트럭 비용을 아끼지만, 이미 진공포장된 물건(JPEG)을 다시
  압축팩에 넣는 건 수고만 들고 부피는 그대로다 — 포장 시간(CPU)만
  낭비한다.

동작 방식은 콘텐츠 협상이다: 클라이언트가 `Accept-Encoding: gzip, br`로
지원 가능한 방식을 알리고, 서버가 그중 하나로 압축해
`Content-Encoding: br`로 응답한다.

## 2. gzip vs brotli — 무엇이 다르고 언제 무엇을 쓰나

- **gzip**: 사실상 모든 클라이언트·프록시가 지원하는 보편 포맷.
  압축 속도와 압축률의 균형이 무난해 동적 응답의 기본값.
- **brotli(br)**: 같은 조건에서 gzip보다 더 작게 만든다. 다만 최고
  압축 레벨은 상당히 느려서 **요청마다 실시간으로 돌리기엔 부담**이고,
  낮은 레벨로 쓰면 동적 응답에도 쓸 만하다. 진가는 **정적 자원
  사전 압축**에서 나온다.

여기서 나오는 실무 전략의 핵심 구분 (가산점 포인트):

- **정적 자원(JS/CSS 번들 등)**: 내용이 안 변하므로 **빌드 타임에
  최고 레벨로 딱 1번 압축**해 `.br`/`.gz` 파일로 저장해 두고, 서빙
  시엔 골라 주기만 한다. 압축 CPU 비용이 요청 횟수와 무관해지므로
  가장 느리고 강한 레벨을 마음껏 쓸 수 있다.
- **동적 응답(API JSON 등)**: 요청마다 새로 압축해야 하므로 중간
  레벨로 타협한다. 압축 레벨을 올릴수록 절감분은 점점 줄고 CPU는
  가파르게 늘어나는 수확 체감이 있어, 최고 레벨은 손해인 경우가 많다.

## 3. 압축하지 말아야 할 응답 — 세 가지 유형

### ① 이미 압축된 포맷 — 낭비이자 역효과

JPEG, PNG, WebP, AVIF, 동영상, zip, 대부분의 폰트(woff2) 등은 포맷
자체가 이미 압축이다. 다시 압축해도 거의 안 줄고, 압축 메타데이터가
붙어 **오히려 커질 수도 있다.** CPU만 태우는 순수 낭비.

```nginx
# Before: 타입 구분 없이 전부 압축
gzip on;
gzip_types *;    # 이미지·zip까지 압축 시도 → CPU 낭비, 크기는 그대로거나 증가

# After: 텍스트 계열만 지정 + 최소 크기 + 중간 레벨
gzip on;
gzip_comp_level 5;                  # 수확 체감 고려한 중간 레벨
gzip_min_length 1024;               # 1KB 미만은 압축 안 함 (② 참고)
gzip_types text/plain text/css application/json
           application/javascript application/xml image/svg+xml;
# (svg는 텍스트라 예외적으로 압축 대상. text/html은 기본 포함)
gzip_vary on;                       # Vary: Accept-Encoding 자동 추가 (4절)
```

### ② 아주 작은 응답 — 오버헤드가 절감분을 넘는다

압축 포맷은 헤더·사전 등 고정 오버헤드가 있어, 수백 바이트짜리 응답은
줄어드는 양이 미미하거나 오히려 커진다. 어차피 작은 응답은 패킷
몇 개 안에 들어가므로 전송 시간 이득도 없다. `gzip_min_length` 같은
최소 크기 문턱을 두는 이유다.

### ③ 비밀값 + 공격자 입력이 섞인 응답 — 압축이 부채널이 된다 (가산점 포인트)

압축은 "반복이 많을수록 작아진다"는 성질이 있다. 한 응답 안에
**비밀값(CSRF 토큰 등)** 과 **공격자가 조작할 수 있는 반사 입력**이
같이 들어 있으면, 공격자가 입력을 바꿔가며 **압축 후 크기 변화**를
관찰해 비밀값을 한 글자씩 맞출 수 있다 — 입력이 비밀값과 일치할수록
반복이 생겨 응답이 작아지기 때문이다. TLS로 암호화해도 **크기는
숨겨지지 않으므로** 성립한다(BREACH로 알려진 계열). 대응: 그런 성격의
응답은 압축을 끄거나, 비밀값을 요청마다 마스킹해 반복 패턴을 없앤다.
"압축이 보안 문제일 수 있다"를 아는 것 자체가 변별력이다.

### (운영 주의) 스트리밍 응답 — 금지라기보다 설정 주의

SSE처럼 조금씩 흘려보내는 응답은 압축 계층의 버퍼링 때문에 이벤트가
클라이언트에 늦게 도달할 수 있다. 압축을 끄거나, 이벤트 경계마다
버퍼를 비우는(flush) 설정이 되는지 확인해야 한다 — "압축 켰더니
실시간 알림이 뭉쳐서 온다"는 유령 현상의 흔한 범인이다.

## 4. 어디서 압축하나 + 캐시와의 상호작용

**압축 위치의 선택지**: 애플리케이션(Tomcat/Spring) → Nginx(리버스
프록시) → CDN. 일반 원칙은 **애플리케이션 CPU는 비즈니스 로직에 쓰고,
압축은 프록시/CDN 계층으로 오프로드**하는 것이다. Nginx는 이벤트 기반
구조라 압축 같은 I/O 성 작업 처리 효율이 좋고, CDN에서 압축하면
오리진은 아예 손을 뗀다. 단, 내부 구간(Nginx↔Tomcat)까지 압축할 필요는
보통 없다 — 병목은 사용자 구간 회선이지 내부망이 아니기 때문이다.

**`Vary: Accept-Encoding`을 빼먹으면 생기는 사고**: 같은 URL에 압축본과
비압축본이 존재하게 되므로, 중간 캐시(CDN 등)에게 "클라이언트의
`Accept-Encoding`에 따라 다른 사본을 구분해 저장하라"고 알려줘야 한다.
이 헤더가 없으면 캐시가 gzip 본문을 압축 미지원 클라이언트에 그대로
서빙해 **깨진 응답**이 나가거나, 반대로 사본이 뒤섞인다. 압축과 캐시를
같이 쓰는 순간 필수 헤더다.

## 5. 꼬리질문 대비 포인트

### "이미지도 어쨌든 조금은 줄지 않나요? 왜 손해라고 하죠?"

JPEG/PNG/WebP는 포맷 내부에서 이미 엔트로피가 압축 한계 근처까지 짜여
있어, gzip을 덧씌워도 절감이 사실상 0이고 컨테이너 오버헤드로 커지기도
한다. 반면 CPU 비용은 응답 크기에 비례해 그대로 들며, 트래픽에서
이미지 비중이 큰 서비스일수록 이 낭비가 서버 전체 CPU에서 유의미해진다.
이미지 용량을 줄이고 싶으면 gzip이 아니라 **포맷 차원의 최적화**
(WebP/AVIF 변환, 품질 조정, 리사이징)가 맞는 도구다.

### "압축 레벨은 어떻게 정하나요?" (시니어 변별 포인트)

수확 체감 곡선을 근거로 답한다 — 레벨을 올릴수록 크기 절감은 조금씩
늘고 CPU 비용은 가파르게 는다. 그래서 판단 기준은 "몇 번 압축해서 몇
번 쓰이는가": **정적 자원은 1번 압축 → N번 서빙**이므로 빌드 타임
최고 레벨(brotli 최고 레벨 포함)이 정답이고, **동적 응답은 1번 압축 →
1번 서빙**이므로 중간 레벨에서 멈추는 게 이득이다. 최종 결정은 자기
서비스의 응답 크기 분포로 실측해서 한다 — "기본값이 그래서요"가
아니라 측정 근거를 대는 것이 시니어의 답변이다.

### "압축했는데 TTFB(첫 바이트까지의 시간)가 늘었다는 리포트가 왔습니다. 왜죠?"

압축 계층은 어느 정도 데이터를 모아야(버퍼) 압축 블록을 내보낼 수
있어, 첫 바이트가 늦게 출발할 수 있다. 응답 전체가 빨리 끝나는 대신
시작이 늦어지는 것 — 큰 응답에선 총 시간이 이득이지만, 작은 응답이나
스트리밍(SSE, 청크 전송)에서는 버퍼링 지연이 그대로 체감된다.
대응은 min_length 문턱으로 작은 응답 제외, 스트리밍 경로 압축 제외
또는 flush 설정 확인.

### "HTTPS면 어차피 암호화되는데 압축이 왜 보안 문제가 되나요?"

TLS는 내용을 숨기지만 **길이는 숨기지 못한다.** 압축은 내용의 반복
정도를 길이에 반영하므로, 공격자가 자기 입력을 응답에 반사시킬 수
있다면 압축 후 크기를 관찰해 같은 응답에 든 비밀값을 추론할 수 있다
(BREACH 계열 부채널). 그래서 "비밀값 + 공격자 제어 입력이 한 응답에
공존"하는 경우가 압축 금지 대상이 된다. 정적 자원처럼 비밀이 없는
응답은 해당 없음 — 조건을 정확히 말하는 게 포인트다.

### "요청(업로드) 본문도 압축하면 안 되나요?"

응답과 달리 요청 압축은 협상이 안 된다 — 서버가 어떤 인코딩을 받아줄지
클라이언트가 미리 알 방법이 표준에 없어서, 사전 합의된 내부
클라이언트(자사 앱, 서버 간 호출)에서만 쓰는 게 현실적이다. 이때도
서버 쪽에 압축 해제 폭탄(작은 요청이 풀면 거대해지는 zip bomb) 대비로
해제 후 크기 상한을 걸어야 한다는 것까지 말하면 가산점 포인트.

## 한 줄 요약

응답 압축은 CPU로 전송량을 사는 교환이라 텍스트 응답에선 남는
장사지만, 이미 압축된 포맷·아주 작은 응답·비밀값과 공격자 입력이 섞인
응답은 예외로 걸러야 하고, 정적 자원은 빌드 타임 사전 압축(brotli
최고 레벨)·동적 응답은 중간 레벨 실시간 압축으로 나눠 설계하며
`Vary: Accept-Encoding`으로 캐시와의 충돌까지 막아야 완성이다 —
"켜면 좋은 옵션"조차 무엇을 내주는지 계산하는 습관이 이 질문의 본론이다.
