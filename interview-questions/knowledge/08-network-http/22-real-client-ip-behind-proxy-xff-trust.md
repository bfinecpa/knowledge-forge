# 프록시 뒤 실제 클라이언트 IP — X-Forwarded-For를 그대로 믿으면 안 되는 이유

> 핵심 관전 포인트: **프록시/LB 뒤에서는 소켓의 상대 주소
> (`getRemoteAddr()`)가 프록시 IP이므로, 실제 클라이언트 IP는 프록시가
> 붙여주는 `X-Forwarded-For` 헤더로 전달받는다. 문제는 이 헤더를
> 클라이언트도 처음부터 위조해 보낼 수 있다는 것 — XFF는 신뢰 경계
> 밖에서 온 사용자 입력이다. 그대로 믿으면 rate limit·IP 차단·관리자
> allowlist·감사 로그가 헤더 한 줄로 전부 우회된다. 올바른 방법은
> "내가 신뢰하는 프록시 목록"을 정의하고, XFF 체인의 오른쪽(내
> 프록시가 붙인 값)에서부터 신뢰하는 프록시를 걷어내 처음 만나는 값을
> 취하는 것이다 — 왼쪽 첫 값은 절대 아니다. 그리고 이 신뢰가 성립하려면
> 백엔드가 프록시를 우회해 직접 접근되지 않는다는 인프라 전제가
> 필요하다.**

---

## 0. 질문 + 의도

**질문**: "프록시/LB 뒤에서 실제 클라이언트 IP는 어떻게 얻나요? `X-Forwarded-For`를 그대로 믿으면 안 되는 이유는?"

**출제 의도**: 스푸핑 가능한 헤더를 그대로 믿으면 rate limit·차단·감사
로그가 전부 우회된다. "신뢰 경계 밖에서 온 값"이라는 보안 감각을
폼 입력뿐 아니라 네트워크 헤더에도 적용하는지 본다 — IP 기반 기능을
하나라도 만들어본 백엔드라면 반드시 부딪히는 문제다.

## 1. 왜 헤더가 필요한가 — 프록시 뒤에서는 소켓 주소가 프록시다

서버가 클라이언트 IP를 아는 원초적 방법은 TCP 소켓의 상대 주소다
(서블릿의 `request.getRemoteAddr()`). 이 값은 위조가 사실상 불가능하다 —
TCP 연결은 3-way handshake로 양방향 통신이 성립해야 하므로, 가짜
출발지 IP로는 연결 자체가 안 맺어진다.

문제는 중간에 프록시가 끼는 순간이다:

```
클라이언트(1.2.3.4) → LB(10.0.0.5) → Nginx(10.0.0.7) → Tomcat
                                                          ↑
                                    getRemoteAddr() = 10.0.0.7 (Nginx!)
```

Tomcat과 TCP 연결을 맺은 상대는 Nginx이므로, 소켓 주소는 언제나
**마지막 홉의 IP**다. 모든 요청의 "클라이언트 IP"가 내부 프록시
주소로 찍히는 것이다.

그래서 프록시들이 릴레이 방식으로 헤더에 원래 주소를 적어 전달한다.
`X-Forwarded-For`(XFF)는 각 프록시가 "**나에게 이 요청을 보낸 상대의
소켓 주소**"를 기존 값 뒤에 덧붙이는(append) 관례다:

```
클라이언트(1.2.3.4)가 보낸 요청이 LB → Nginx를 지나면:

LB 통과 후:    X-Forwarded-For: 1.2.3.4
Nginx 통과 후: X-Forwarded-For: 1.2.3.4, 10.0.0.5
                                ^^^^^^^  ^^^^^^^^
                                LB가 본  Nginx가 본
                                소켓주소  소켓주소(=LB)
```

즉 체인의 **오른쪽일수록 내 인프라에 가까운 프록시가 직접 관측한
값**(소켓 주소라서 위조 불가)이고, 왼쪽일수록 "전달받아 적었을 뿐인"
값이다. 이 방향성이 이 주제 전체의 열쇠다.

```nginx
# Nginx에서 뒤 계층으로 클라이언트 IP를 전달하는 표준 설정
location /api/ {
    proxy_pass http://tomcat_upstream;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;  # 기존 값 + 내가 본 소켓주소
    proxy_set_header X-Real-IP $remote_addr;                      # 내가 본 소켓주소 하나만
}
```

## 2. 왜 그대로 믿으면 안 되는가 — XFF는 사용자 입력이다

XFF는 프록시만 붙일 수 있는 특별한 헤더가 아니다. **클라이언트가
요청을 만들 때 처음부터 넣어 보낼 수 있는 평범한 HTTP 헤더**다:

```bash
# 공격자가 헤더를 위조해 보내면
curl -H "X-Forwarded-For: 10.0.0.1" https://api.example.com/admin

# LB와 Nginx가 append 방식으로 동작하면 백엔드가 받는 값:
# X-Forwarded-For: 10.0.0.1, 5.6.7.8, 10.0.0.5
#                  ^^^^^^^^  ^^^^^^^
#                  위조된 값   공격자의 진짜 IP(LB가 관측)
```

"XFF의 첫 번째(가장 왼쪽) 값 = 클라이언트 IP"라는 흔한 코드가
왜 취약한지가 여기서 드러난다 — 왼쪽 값은 공격자 마음대로다.

그대로 믿었을 때 뚫리는 것들:

- **rate limiting 우회**: IP당 분당 N회 제한을 걸었는데 키가 위조
  가능하면, 요청마다 XFF를 바꿔 보내는 것만으로 무한 우회된다.
  크리덴셜 스터핑(계정 대입 공격) 방어가 무력화되는 전형적 경로다.
- **IP 차단/허용 우회**: 차단된 공격자가 아무 IP나 적어 통과하고,
  최악은 관리자 페이지의 "사내 IP allowlist"를 내부 대역 값을 적어
  통과하는 경우다.
- **감사 로그 오염**: 사고 조사 시점에 로그의 IP가 전부 위조값이면
  추적이 원천 불가능하고, 엉뚱한 IP를 범인으로 지목하게 된다.
- **지역 차단, 부정행위 탐지, IP 기반 A/B 분기** 등 IP를 입력으로
  쓰는 모든 로직이 같은 방식으로 무너진다.

한 문장으로: **XFF는 폼 입력과 똑같은 "신뢰 경계 밖에서 온 값"이다.**
폼 입력을 검증 없이 SQL에 넣지 않듯, XFF를 검증 없이 보안 로직에
넣으면 안 된다.

## 3. 올바르게 얻는 법 — 신뢰할 프록시를 정의하고 오른쪽부터 걷어낸다

### 알고리즘: rightmost + 신뢰 프록시 제거

원리는 단순하다. 소켓 주소는 위조 불가이고, XFF의 각 항목은 "그것을
붙인 프록시가 관측한 소켓 주소"다. 따라서:

1. **내가 신뢰하는 프록시 IP 목록**(내 LB, 내 Nginx, 계약된 CDN 대역)을
   정의한다.
2. 소켓 주소(맨 뒤에 실질적으로 이어지는 값)부터 시작해 **오른쪽에서
   왼쪽으로** 훑으며, 신뢰 목록에 있는 프록시 IP를 걷어낸다.
3. **처음 만나는 신뢰 목록 밖의 값**이 실제 클라이언트 IP다. 그보다
   왼쪽은 누가 적었는지 보증할 수 없으므로 버린다.

```
X-Forwarded-For: 10.0.0.1, 5.6.7.8, 10.0.0.5     (신뢰 목록: 10.0.0.0/8)
                           ^^^^^^^  ~~~~~~~~ 신뢰 프록시 → 제거
                           └─ 신뢰 목록 밖 첫 값 = 진짜 클라이언트 (위조값 10.0.0.1은 도달 전에 무시됨)
```

### 계층별 구현

이 알고리즘을 직접 짤 필요는 없다 — 각 계층에 표준 구현이 있다.

**Nginx — realip 모듈**: 신뢰 프록시(`set_real_ip_from`)가 붙인 XFF를
해석해 `$remote_addr` 자체를 실제 클라이언트 IP로 교체해 준다.

```nginx
set_real_ip_from 10.0.0.0/8;        # 신뢰하는 앞 계층(LB) 대역
real_ip_header   X-Forwarded-For;
real_ip_recursive on;               # 신뢰 대역을 재귀적으로 걷어냄 (rightmost 알고리즘)
```

**Spring Boot(내장 Tomcat)**: 같은 일을 WAS 레벨에서 하는 것이
Tomcat의 `RemoteIpValve`다. 활성화하면 `getRemoteAddr()`가 해석된
클라이언트 IP를 반환하므로 앱 코드는 헤더를 직접 파싱할 필요가 없다.

```yaml
# Before: 앱 코드 곳곳에서 request.getHeader("X-Forwarded-For")를 split해서 [0]을 사용 — 위조에 뚫림
# After: 신뢰 프록시를 선언하고 getRemoteAddr()로 일원화
server:
  forward-headers-strategy: native   # Tomcat RemoteIpValve 사용
  tomcat:
    remoteip:
      remote-ip-header: X-Forwarded-For
      internal-proxies: "10\\.\\d{1,3}\\.\\d{1,3}\\.\\d{1,3}"  # 신뢰(내부) 프록시 패턴
```

핵심은 **해석 지점을 한 곳(최전선 또는 신뢰 체인의 입구)으로
일원화**하고, 앱 코드에서는 헤더 파싱을 금지하는 것이다. 헤더를
`split(",")[0]`으로 뜯는 유틸이 코드베이스에 굴러다니는 순간 어딘가는
위조값을 쓰게 된다.

### 인프라 전제 — 우회로가 없어야 신뢰가 성립한다 (가산점 포인트)

이 모든 논리는 "요청이 반드시 내 신뢰 프록시를 거친다"는 전제 위에
서 있다. 백엔드 인스턴스가 공인 IP로 직접 접근 가능하다면, 공격자는
프록시를 건너뛰고 위조 XFF를 직접 꽂을 수 있다 — 신뢰 체계 전체가
무너진다. 그래서 보안그룹/방화벽으로 **백엔드는 앞 계층에서 오는
트래픽만 받도록** 잠그는 것까지가 이 설계의 일부다. 또 최전선
프록시에서 클라이언트가 보낸 XFF를 제거하고 새로 시작하는 정책을
쓰면 체인 해석이 훨씬 단순해진다 — 다만 이 경우에도 "최전선을 우회할
수 없다"는 전제는 여전히 필요하다.

## 4. 꼬리질문 대비 포인트

### "XFF에 IP가 여러 개 들어 있으면 어떤 값을 써야 하나요?"

왼쪽 첫 값이 아니라, **오른쪽에서부터 내가 신뢰하는 프록시들을 걷어내고
처음 만나는 신뢰 목록 밖의 값**이다. 오른쪽 값일수록 내 인프라의
프록시가 소켓에서 직접 관측한(위조 불가) 값이고, 왼쪽은 전달받아
적었을 뿐인 값이라 클라이언트가 위조해 끼워 넣을 수 있기 때문이다.
Nginx `real_ip_recursive on`, Tomcat `RemoteIpValve`의
internal-proxies가 이 알고리즘의 구현체다.

### "그럼 헤더 말고 getRemoteAddr()만 쓰면 안전한 것 아닌가요?"

위조는 안 되지만, 프록시 뒤에서는 그 값이 프록시 IP라서 쓸모가 없다 —
모든 사용자가 같은 IP로 보인다. rate limit을 걸면 프록시 IP 하나에
전체 트래픽이 걸려 전면 차단 사고가 난다. 그래서 "소켓 주소의 위조
불가성"과 "헤더의 정보 전달"을 결합한 것이 신뢰 프록시 기반 해석이다.
프록시가 없는 직접 노출 서버라면 getRemoteAddr()만으로 충분하다는
대비까지 말하면 좋다.

### "CDN(Cloudflare, CloudFront) 뒤에 있으면 어떻게 달라지나요?"

신뢰 목록에 CDN의 엣지 IP 대역을 넣어야 하는데, 이 대역은 사업자가
공개하고 **수시로 바뀐다** — 갱신을 자동화하지 않으면 어느 날 새 엣지
대역이 "신뢰 밖"으로 분류되며 클라이언트 IP가 엣지 IP로 잘못 잡힌다.
Cloudflare의 `CF-Connecting-IP`처럼 CDN이 직접 관측한 IP를 담아주는
전용 헤더를 쓰는 것이 더 단순하지만, 이 역시 "CDN을 우회해 원본 서버로
직접 못 들어온다"(origin 보호)는 전제가 있어야 안전하다 — 우회가
가능하면 그 헤더도 위조해 꽂을 수 있다.

### "L4 LB 뒤에서는 XFF를 못 쓰지 않나요?" (가산점 포인트)

맞다. XFF는 HTTP 헤더이므로 HTTP를 해석하는 L7 장비만 붙일 수 있다.
L4(TCP) LB는 페이로드를 안 보므로, 대신 **PROXY protocol**을 쓴다 —
TCP 연결 수립 직후 원 클라이언트의 주소 정보를 담은 짧은 전문을
먼저 보내는 약속으로, 뒤 서버(Nginx 등)가 이를 해석하도록 설정한다.
양쪽 모두 활성화해야 하며 한쪽만 켜면 프로토콜이 어긋나 통신 자체가
깨진다. 표준화 관점에서는 XFF의 난립을 정리한 RFC 7239 `Forwarded`
헤더도 있다는 것까지 알면 충분하다.

### "실제 클라이언트 IP를 rate limiting이나 차단 키로 쓸 때의 한계는?" (시니어 변별 포인트)

IP를 올바르게 얻었더라도 IP 자체의 식별력에 한계가 있다. 통신사 NAT나
기업 프록시 뒤에서는 수백~수천 명이 하나의 IP를 공유하므로, IP 기준
차단은 무고한 다수를 함께 막는다(false positive). 반대로 공격자는
봇넷·프록시 풀로 IP를 대량 확보하므로 IP 차단만으로는 못 막는다
(false negative). 그래서 IP는 단독 키가 아니라 **여러 신호 중 하나**로
쓰고, 계정 단위 제한·디바이스 지문·행동 패턴과 조합한다. "IP를 정확히
얻는 것"과 "IP를 얼마나 신뢰해 결정에 쓸 것인가"는 별개의 설계
문제라고 구분해 말하면 시니어답다.

## 한 줄 요약

프록시 뒤에서 소켓 주소는 프록시 IP이므로 실제 클라이언트 IP는 XFF로
전달받지만, XFF는 클라이언트가 위조할 수 있는 신뢰 경계 밖의 입력이다 —
신뢰 프록시 목록을 정의하고 체인의 오른쪽부터 걷어내 처음 만나는
바깥 값을 취하는 해석(Nginx realip, Tomcat RemoteIpValve)을 한 곳에
일원화하고, 백엔드가 프록시를 우회해 접근될 수 없다는 인프라 전제까지
갖춰야 rate limit·차단·감사 로그가 헤더 한 줄에 뚫리지 않는다.
