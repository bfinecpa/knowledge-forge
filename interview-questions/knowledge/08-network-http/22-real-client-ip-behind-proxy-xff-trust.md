# 프록시 뒤 실제 클라이언트 IP — X-Forwarded-For를 그대로 믿으면 안 되는 이유

> 핵심 관전 포인트: **프록시/LB 뒤에서는 소켓의 상대 주소(`getRemoteAddr()`)가 프록시 IP이므로, 실제 클라이언트 IP는 프록시가 붙여주는 `X-Forwarded-For` 헤더로 전달받는다. 문제는 이 헤더가 프록시만 붙일 수 있는 특별한 헤더가 아니라 **클라이언트가 처음부터 아무 값이나 넣어 보낼 수 있는 평범한 HTTP 헤더**라는 것이다. 프록시는 들어온 값을 검증하지 않고 자기가 관측한 주소를 뒤에 덧붙일 뿐이므로, 체인의 왼쪽 값들은 전부 공격자가 심어둔 것일 수 있다. 그래서 흔히 보이는 `split(",")[0]` 코드는 rate limit·IP 차단·관리자 allowlist·감사 로그를 헤더 한 줄로 통째로 우회시킨다 — XFF는 폼 입력과 똑같은 "신뢰 경계 밖에서 온 값"이다. 올바른 해석은 방향이 반대다. 오른쪽일수록 우리 인프라에 가까운 프록시가 소켓에서 직접 관측해 적은 값이라 위조가 불가능하므로, **오른쪽 끝에서 시작해 "내가 신뢰하는 프록시 목록"에 있는 IP인 동안 계속 걷어내고, 처음 만나는 신뢰 목록 밖의 값**을 클라이언트 IP로 삼는다(Nginx `real_ip_recursive`, Tomcat `RemoteIpValve`가 이 알고리즘의 구현체다). 그리고 이 신뢰 모델 전체는 **앱에 프록시를 우회해 직접 도달할 경로가 없다**는 인프라 전제 위에서만 성립하므로, 보안 그룹으로 앱 포트를 LB에서만 열어두는 것까지가 이 설계의 일부다. 마지막으로 IP를 정확히 얻는 것과 IP를 얼마나 믿고 결정에 쓸 것인가는 별개의 문제다 — 통신사 NAT 뒤에서는 수천 명이 한 IP를 공유하고 IPv6에서는 한 사용자가 방대한 주소를 쓰므로, IP는 단독 키가 아니라 계정·기기 지문과 조합하는 보조 신호다.**

---

## 0. 질문 + 의도

**질문**: "프록시/LB 뒤에서 실제 클라이언트 IP는 어떻게 얻나요? `X-Forwarded-For`를 그대로 믿으면 안 되는 이유는?"

**출제 의도**: 스푸핑 가능한 헤더를 그대로 믿으면 rate limit·차단·감사 로그가 전부 우회된다. "신뢰 경계 밖에서 온 값"이라는 보안 감각을 폼 입력뿐 아니라 네트워크 헤더에도 적용하는지 본다 — IP 기반 기능을 하나라도 만들어본 백엔드라면 반드시 부딪히는 문제다.

## 1. 왜 헤더가 필요한가 — 프록시 뒤에서는 소켓 주소가 프록시다

### 1-1. 전제 — 소켓 주소는 왜 위조되지 않는가

서버가 클라이언트 IP를 아는 가장 원초적인 방법은 **TCP 소켓의 상대 주소**다. 서블릿에서는 `request.getRemoteAddr()`로 읽는 값이고, 커널이 연결을 관리하며 들고 있는 정보다.

이 값의 특별한 점은 **사실상 위조가 불가능하다**는 것이다. 왜 그런지 이유를 알아야 뒤의 논의가 성립한다.

TCP 연결은 **3-way handshake**로 시작한다. 클라이언트가 SYN을 보내면 서버가 SYN+ACK를 보내고, 클라이언트가 다시 ACK를 보내야 연결이 성립한다. 여기서 두 번째 단계가 핵심이다. 서버의 SYN+ACK는 **패킷에 적힌 출발지 IP로 되돌아간다.** 공격자가 출발지 IP를 8.8.8.8로 위조해 SYN을 보내면, 서버의 응답은 8.8.8.8로 날아가고 공격자는 그것을 받지 못한다. 응답 안에 든 시퀀스 번호를 모르니 세 번째 ACK를 만들 수 없고, **연결 자체가 성립하지 않는다.**

HTTP 요청은 연결이 성립한 뒤에야 보낼 수 있으므로, **HTTP 요청이 도착했다는 것 자체가 그 출발지 IP가 진짜라는 증거**다. 이 성질이 이 문서 전체의 기준점이다. 앞으로 나올 모든 판단은 "소켓 주소는 믿을 수 있고, 헤더는 못 믿는다"에서 출발한다.

### 1-2. 프록시가 끼면 그 값이 프록시를 가리킨다

문제는 중간에 프록시가 끼는 순간 시작된다.

```
클라이언트(1.2.3.4) → LB(10.0.0.5) → Nginx(10.0.0.7) → Tomcat(10.0.0.9)
                                                            ↑
                              Tomcat이 소켓에서 보는 상대 주소 = 10.0.0.7 (Nginx)
```

Tomcat과 TCP 연결을 맺은 상대는 클라이언트가 아니라 Nginx다. 그러니 `getRemoteAddr()`는 **언제나 마지막 홉의 IP**를 돌려준다. 모든 사용자의 "클라이언트 IP"가 내부 프록시 주소 하나로 찍히는 것이다.

이 상태에서 무엇이 망가지는지는 [17번 문서 3-1](17-tls-termination-lb-vs-app.md)에서 TLS 종료 관점으로 다룬 것과 같다. 접근 로그의 IP가 전부 같은 값이라 사고 조사가 불가능해지고, IP 기반 rate limit을 걸면 모든 트래픽이 키 하나에 몰려 임계값을 넘고, 그 키를 차단하는 순간 전면 장애가 된다. 지역 차단이나 부정행위 탐지처럼 IP를 입력으로 쓰는 로직도 전부 무의미해진다.

그래서 프록시들이 **원래 주소를 헤더에 적어 뒤 계층에 전달하는 관례**를 만들었다. 그 관례가 `X-Forwarded-For`다.

### 1-3. `X-Forwarded-For`의 문법 — 각 프록시가 자기가 본 것을 덧붙인다

`X-Forwarded-For`(줄여서 XFF)는 표준 규격이 아니라 **관례에서 출발한 헤더**다. 이름 앞의 `X-`가 그 흔적이다(비표준 확장 헤더에 붙이던 접두어다). 그래서 동작 규칙도 "각 프록시가 이렇게 하기로 한다"는 합의에 가깝다.

규칙은 하나다. **각 프록시는 "나에게 이 요청을 보낸 상대의 소켓 주소"를 기존 값 뒤에 쉼표로 덧붙인다(append).**

```
클라이언트(1.2.3.4)가 보낸 요청이 LB → Nginx를 지날 때

클라이언트가 보낸 원 요청: (XFF 헤더 없음)

LB 통과 후:    X-Forwarded-For: 1.2.3.4
                                ^^^^^^^ LB가 자기 소켓에서 관측한 상대 = 클라이언트

Nginx 통과 후: X-Forwarded-For: 1.2.3.4, 10.0.0.5
                                ^^^^^^^  ^^^^^^^^
                                LB가 적음  Nginx가 자기 소켓에서 관측한 상대 = LB

Tomcat이 받는 것: X-Forwarded-For: 1.2.3.4, 10.0.0.5
                  그리고 소켓 주소 = 10.0.0.7 (Nginx)
```

여기서 **방향성**을 정확히 잡아야 한다. 이것이 이 주제 전체의 열쇠다.

**오른쪽으로 갈수록 내 인프라에 가까운 프록시가 직접 관측한 값이다.** 마지막 항목은 바로 앞 홉이 소켓에서 본 주소이므로 1-1의 논리로 위조가 불가능하다. 그리고 소켓 주소(10.0.0.7)를 XFF의 맨 오른쪽에 이어 붙이면 **완전한 경로**가 된다.

**왼쪽으로 갈수록 "누군가에게 전달받아 적었을 뿐인" 값이다.** 가장 왼쪽 값은 우리 인프라의 어떤 장비도 소켓에서 관측한 적이 없다. 그저 요청에 그렇게 적혀 있었을 뿐이다.

```
   왼쪽                                                      오른쪽
   ├─────────────────────────────────────────────────────────┤
   1.2.3.4  ,  10.0.0.5   +  (소켓 주소 10.0.0.7)
   ↑                                        ↑
   전달받아 적힌 값                          내 프록시가 직접 관측한 값
   (누가 적었는지 보증 못 함)                 (위조 불가)

   신뢰도가 오른쪽으로 갈수록 높아진다.
```

Nginx에서 이 헤더를 뒤 계층으로 넘기는 설정은 이렇게 쓴다.

```nginx
location /api/ {
    proxy_pass http://tomcat_upstream;

    # $proxy_add_x_forwarded_for = (들어온 XFF 값) + ", " + (내가 관측한 소켓 주소)
    # 즉 append 방식이다. 들어온 값의 진위는 검사하지 않는다 — 이것이 2절의 출발점이다.
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    # $remote_addr = 내가 소켓에서 관측한 상대 주소 하나만
    proxy_set_header X-Real-IP $remote_addr;
}
```

### 1-4. 비슷한 헤더들 — `X-Real-IP`와 표준 `Forwarded`

XFF 말고도 같은 목적의 헤더가 몇 개 더 있어 헷갈리기 쉽다. 차이를 짧게 정리하자.

**`X-Real-IP`** 는 Nginx 진영에서 널리 쓰이는 관례로, **체인이 아니라 단일 값**이다. 위 설정처럼 `$remote_addr`로 **덮어쓰기(set)** 하는 것이 보통이라 프록시를 지날 때마다 값이 교체된다. 파싱이 단순하다는 장점이 있지만, **경로 전체를 알 수 없어** 몇 단을 거쳐 왔는지 검증할 수 없다. 그리고 덮어쓰기라는 성질 자체가 안전을 보장하지는 않는다 — 최전선에서 덮어써야 안전하고, 중간 프록시가 클라이언트가 보낸 `X-Real-IP`를 그대로 통과시키면 위조값이 그대로 흘러 들어온다.

**`Forwarded`** 는 XFF의 난립을 정리하려고 나중에 표준화한 헤더다(RFC 7239). 여러 정보를 하나의 헤더에 담을 수 있는 구조다.

```http
Forwarded: for=1.2.3.4;proto=https;by=10.0.0.5, for=10.0.0.5;proto=http;by=10.0.0.7
```

`for`(요청을 보낸 상대), `by`(이 항목을 적은 프록시), `proto`(원래 스킴), `host`(원래 호스트)를 한 항목에 묶으므로, `X-Forwarded-For`·`X-Forwarded-Proto`·`X-Forwarded-Host`를 따로 관리할 필요가 없다. IPv6 주소도 `for="[2001:db8::1]:4711"`처럼 따옴표와 대괄호로 정확히 표현할 수 있다.

**표준이지만 현실에서는 보급률이 낮다.** 이미 XFF가 사실상의 표준으로 자리 잡은 뒤에 나왔기 때문이다. 그래서 실무의 기본 대응은 여전히 XFF이고, `Forwarded`는 "표준화된 대체재가 있다"는 지식으로 알아두는 정도가 적절하다. 다만 프레임워크(스프링의 `ForwardedHeaderFilter`)는 두 헤더를 모두 해석하며, 둘 다 있으면 `Forwarded`를 우선한다.

**중요한 것은, 이름이 무엇이든 성질은 같다는 점이다.** 셋 다 HTTP 헤더이고, HTTP 헤더는 누구나 만들어 보낼 수 있다.

## 2. 왜 그대로 믿으면 안 되는가 — XFF는 사용자 입력이다

### 2-1. 헤더는 프록시의 전유물이 아니다

주니어가 XFF를 처음 배울 때 만드는 잘못된 그림은 이것이다. "프록시가 붙여주는 헤더니까 프록시만 붙일 수 있겠지."

**아니다.** HTTP 헤더는 요청을 만드는 쪽이 아무 이름과 값으로나 붙일 수 있다. `X-Forwarded-For`도 예외가 아니다.

```bash
# 공격자가 처음부터 XFF를 넣어 보낸다. 아무 도구도 필요 없다.
curl -H "X-Forwarded-For: 10.0.0.1" https://api.example.com/admin/users
```

그러면 우리 인프라를 지나면서 무슨 일이 벌어지는가. **프록시는 들어온 값의 진위를 검사하지 않는다.** 1-3에서 본 대로 `$proxy_add_x_forwarded_for`는 들어온 값 뒤에 자기가 본 주소를 덧붙일 뿐이다.

```
공격자(5.6.7.8)가 보낸 요청
   X-Forwarded-For: 10.0.0.1          ← 공격자가 직접 적어 넣은 값

LB(10.0.0.5) 통과 후
   X-Forwarded-For: 10.0.0.1, 5.6.7.8
                    ^^^^^^^^  ^^^^^^^
                    위조값     LB가 소켓에서 관측한 공격자의 진짜 IP
                    (그대로    (여기부터가 진짜)
                     살아남음)

Nginx(10.0.0.7) 통과 후 — Tomcat이 받는 값
   X-Forwarded-For: 10.0.0.1, 5.6.7.8, 10.0.0.5
                    └ 공격자 ┘ └────── 우리 인프라가 관측한 값 ──────┘
```

이 그림이 이 문서에서 가장 중요한 그림이다. **체인의 왼쪽 부분은 공격자가 통째로 지어낸 것일 수 있다.** 항목을 열 개 넣어 보내면 열 개가 전부 살아남는다. 우리 인프라는 그 뒤에 진실을 덧붙일 뿐, 앞에 적힌 거짓말을 지우지 않는다.

그래서 코드베이스에서 흔히 보이는 이 한 줄이 위험하다.

```java
// 위험: 가장 왼쪽 값 = 공격자가 마음대로 정할 수 있는 값
String clientIp = request.getHeader("X-Forwarded-For").split(",")[0].trim();
```

한 문장으로 정리하면 이렇다. **XFF는 폼 입력과 똑같은 "신뢰 경계 밖에서 온 값"이다.** 폼 입력을 검증 없이 SQL에 넣지 않듯, XFF를 검증 없이 보안 로직에 넣으면 안 된다.

### 2-2. 왼쪽 값을 쓰면 구체적으로 무엇이 뚫리는가

"위조 가능하다"는 말만으로는 위험이 잘 와닿지 않는다. IP를 쓰는 대표적인 기능 네 가지에서 각각 어떻게 무너지는지 보자.

**① rate limiting 우회 — 무제한 시도가 가능해진다**

로그인 API에 "IP당 분당 5회"를 걸었다고 하자. 목적은 **크리덴셜 스터핑**(어디선가 유출된 아이디·비밀번호 목록을 대입해 보는 공격) 방어다.

```
[의도한 동작]
  공격자 IP 5.6.7.8 → 5회 시도 후 429 Too Many Requests → 차단

[XFF 왼쪽 값을 키로 썼을 때]
  요청 1: X-Forwarded-For: 1.1.1.1     → 키 "1.1.1.1"     카운트 1
  요청 2: X-Forwarded-For: 1.1.1.2     → 키 "1.1.1.2"     카운트 1
  요청 3: X-Forwarded-For: 1.1.1.3     → 키 "1.1.1.3"     카운트 1
  ...
  → 요청마다 헤더 한 줄만 바꾸면 매번 새 사용자로 계산된다.
     제한이 존재하지 않는 것과 같다. 초당 수백 번 대입해도 걸리지 않는다.
```

더 나쁜 것은 **이 상태가 정상으로 보인다**는 점이다. 대시보드에는 "IP별 요청 수가 고르게 분포"로 찍히고, rate limiter는 매일 정상 동작 중이라고 보고한다. 뚫렸다는 사실을 알아챌 신호가 없다.

**② IP 차단 우회 — 차단 목록이 무의미해진다**

부정행위가 확인된 IP를 차단 목록에 넣어 뒀다고 하자. 공격자는 XFF에 아무 IP나 적어 넣으면 그만이다. **차단 목록에 없는 값을 적으면 통과한다.** 차단은 "공격자가 스스로 자기 신분증을 제출한다"는 전제 위에서만 동작하는데, 그 신분증을 공격자가 직접 쓰고 있는 것이다.

**③ 관리자 allowlist 우회 — 이것이 최악이다**

가장 위험한 시나리오다. 관리자 페이지에 "사내 IP 대역(10.0.0.0/8)에서만 접근 허용"을 걸어 둔 경우를 보자.

```
[의도]
  사내망(10.x.x.x)에서 온 요청만 /admin 접근 허용

[XFF 왼쪽 값으로 판정할 때]
  공격자: curl -H "X-Forwarded-For: 10.0.0.42" https://api.example.com/admin

  앱: XFF[0] == "10.0.0.42" → 사내 IP다 → 통과
  → 인터넷 어디서나 관리자 페이지에 들어올 수 있다.
```

**네트워크 경계를 인증 수단으로 쓰던 것이 헤더 한 줄로 무너진 것**이다. IP allowlist를 "그래도 한 겹의 방어"로 믿고 다른 인증을 느슨하게 뒀다면 피해는 더 커진다.

**④ 감사 로그 오염 — 사고 조사가 원천 불가능해진다**

앞의 셋과 성격이 다른 피해다. 즉시 드러나지 않고 **사고가 난 뒤에야 발견된다.**

침해 사고가 나서 로그를 뒤지는 상황을 상상해 보자. 공격자가 모든 요청에 `X-Forwarded-For: 8.8.8.8`을 넣어 보냈다면, 접근 로그에는 공격 요청이 전부 8.8.8.8에서 온 것으로 남아 있다. 진짜 출발지는 **어디에도 기록되지 않았다.** 추적이 불가능한 정도가 아니라, **엉뚱한 IP를 범인으로 지목**하게 된다. 그 IP가 실재하는 다른 조직의 것이라면 잘못된 신고와 차단으로 2차 피해가 생긴다.

로그는 사후에 고칠 수 없다. **로그에 남길 IP를 잘못 고르는 것은 그 시점의 진실을 영구히 잃는 결정**이다.

### 2-3. 그래서 판단 기준은 "누가 이 값을 적었는가"

네 시나리오의 공통 원인은 하나다. **적힌 값을 그대로 믿었다.** 값 자체는 형식이 멀쩡한 IP 주소이므로 검증 함수로도 걸러지지 않는다. 정규식으로 "IP 형식인가"를 검사해 봐야 소용없다 — 공격자도 정상 형식의 IP를 적는다.

그러므로 판단 기준은 값의 형식이 아니라 **출처**여야 한다. "이 값을 우리 인프라의 어떤 장비가 소켓에서 직접 관측해 적었는가?" 이 질문에 답할 수 있는 항목만 신뢰한다. 그리고 1-3에서 본 방향성 덕분에 이 질문에는 답할 수 있다. **오른쪽에서부터 세면 된다.**

## 3. 올바르게 얻는 법 — 신뢰할 프록시를 정의하고 오른쪽부터 걷어낸다

### 3-1. rightmost 알고리즘 — 한 단계씩

원리는 두 문장이다. 소켓 주소는 위조 불가다. 그리고 XFF의 각 항목은 "그것을 붙인 프록시가 자기 소켓에서 관측한 주소"다. 따라서 **내가 아는 프록시들이 붙인 항목까지는 신뢰할 수 있고, 그 앞부터는 신뢰할 수 없다.**

구현 단계는 이렇다.

**1단계. 신뢰하는 프록시 목록을 정의한다.** 내 LB의 IP 대역, 내 Nginx의 IP 대역, 계약된 CDN의 엣지 대역이 여기 들어간다. **이 목록은 설정으로 관리하고 코드에 흩어놓지 않는다.**

**2단계. 검사 대상 체인을 만든다.** XFF 값에 **소켓 주소를 맨 오른쪽에 이어 붙인다.** XFF에는 "마지막 홉이 관측한 주소"가 없기 때문이다(마지막 홉은 자기가 본 것을 적어 보냈지, 자기 자신을 적지는 않았다). 소켓 주소를 붙여야 체인이 완성된다.

**3단계. 오른쪽 끝에서 왼쪽으로 걸으며, 신뢰 목록에 있는 IP인 동안 계속 걷어낸다.**

**4단계. 처음 만나는 "신뢰 목록에 없는 값"이 실제 클라이언트 IP다.** 그보다 왼쪽은 전부 버린다 — 누가 적었는지 보증할 수 없기 때문이다.

**왜 오른쪽부터인가**를 다시 확인하자. 오른쪽 항목일수록 우리 인프라에 가까운 장비가 적었고, 그 장비들은 자기 소켓에서 실제로 관측한 값만 적는다. 반대로 왼쪽으로 갈수록 "전달받아 적힌" 값이라 진위를 보증할 수 없다. **신뢰는 우리 쪽에서 시작해 바깥으로 걸어 나가는 방향으로만 확장된다.**

```
받은 값:  X-Forwarded-For: 10.0.0.1, 5.6.7.8, 10.0.0.5
소켓 주소: 10.0.0.7
신뢰 목록: 10.0.0.0/8

2단계 — 소켓 주소를 이어 붙여 완전한 체인을 만든다
   [ 10.0.0.1 , 5.6.7.8 , 10.0.0.5 , 10.0.0.7 ]
                                       ↑ 여기서 출발

3단계 — 오른쪽부터 신뢰 목록에 있는 값을 걷어낸다
   10.0.0.7 → 신뢰 목록(10/8) 안 → 내 Nginx다 → 걷어낸다
   10.0.0.5 → 신뢰 목록 안       → 내 LB다   → 걷어낸다
   5.6.7.8  → 신뢰 목록 밖       → 여기서 멈춘다

4단계 — 결과
   클라이언트 IP = 5.6.7.8   (LB가 소켓에서 실제로 관측한 값)
   10.0.0.1 은 그 왼쪽에 있으므로 통째로 버려진다 — 공격자가 심은 값이었다.

   ✓ 공격자가 사내 대역(10.0.0.1)을 위조해도 소용없다.
     그 값은 우리 장비가 관측한 것이 아니므로 애초에 검사 범위 밖이다.
```

한 가지 함정을 짚어두자. **위 예에서 위조값이 마침 신뢰 대역(10/8)이었다는 점**이다. 만약 알고리즘을 반대로 짜서 "왼쪽부터 걸으며 신뢰 대역을 건너뛴다"고 하면, 공격자는 신뢰 대역 IP를 여러 개 앞에 채워 넣어 원하는 값이 선택되게 만들 수 있다. **오른쪽에서 시작하는 것이 알고리즘의 안전성 그 자체**이지 스타일 선택이 아니다.

코드로 옮기면 이렇다.

```java
// Before: 가장 왼쪽 값을 쓴다 — 2절에서 본 모든 우회에 뚫린다
public String clientIpBefore(HttpServletRequest request) {
    String xff = request.getHeader("X-Forwarded-For");
    if (xff != null && !xff.isBlank()) {
        return xff.split(",")[0].trim();   // 공격자가 정한 값
    }
    return request.getRemoteAddr();
}

// After: 소켓 주소부터 시작해 신뢰 프록시를 걷어낸다
public String clientIpAfter(HttpServletRequest request) {
    // 신뢰 프록시 대역. 설정에서 주입받아 한 곳에서만 관리한다.
    // (예: 10.0.0.0/8, CDN 엣지 대역)
    List<IpAddressMatcher> trustedProxies = this.trustedProxyMatchers;

    // ① 체인 조립: XFF 값들 뒤에 소켓 주소를 이어 붙여 완전한 경로를 만든다.
    List<String> chain = new ArrayList<>();
    // getHeaders 로 읽는다. getHeader 는 같은 이름의 헤더가 여러 개일 때
    // '첫 번째' 것만 돌려주는데, 공격자가 자기 XFF 헤더를 하나 더 보내면
    // 프록시가 붙인 헤더가 아니라 공격자의 헤더를 읽게 된다.
    Enumeration<String> headers = request.getHeaders("X-Forwarded-For");
    while (headers.hasMoreElements()) {
        for (String v : headers.nextElement().split(",")) {
            if (!v.isBlank()) chain.add(v.trim());
        }
    }
    chain.add(request.getRemoteAddr());   // 위조 불가능한 값을 맨 오른쪽에

    // ② 오른쪽 끝에서 왼쪽으로 걸으며 신뢰 프록시를 걷어낸다.
    for (int i = chain.size() - 1; i >= 0; i--) {
        String candidate = chain.get(i);
        boolean isTrustedProxy = trustedProxies.stream()
                .anyMatch(matcher -> matcher.matches(candidate));
        if (!isTrustedProxy) {
            // ③ 처음 만나는 신뢰 목록 밖의 값이 실제 클라이언트다.
            return candidate;
        }
    }

    // ④ 전부 신뢰 프록시였다 = 내부에서 발생한 요청(헬스체크 등).
    //    여기서 "가장 왼쪽 값"으로 되돌아가면 안 된다 — 그 순간 위조에 뚫린다.
    return request.getRemoteAddr();
}
```

주석의 `getHeaders` 부분은 실제로 놓치기 쉬운 함정이라 한 번 더 짚는다. HTTP는 같은 이름의 헤더가 여러 번 등장하는 것을 허용하고, 서블릿 API의 `getHeader(String)`은 그중 **첫 번째 것만** 돌려준다. 공격자가 자기 `X-Forwarded-For` 헤더를 하나 보내고 프록시가 별도 헤더로 값을 추가하는 구성이라면, `getHeader`는 공격자의 헤더를 읽는다. **직접 파싱한다면 `getHeaders`로 전부 모아야 한다.**

그리고 마지막 `④`도 중요하다. 예외 상황에서 "그럼 그냥 왼쪽 값이라도 쓰자"로 되돌아가는 fallback을 넣는 순간, 공격자는 그 예외 상황을 만들어 내는 방법을 찾아 우회한다. **불확실하면 소켓 주소로 떨어지는 것이 안전한 실패다.**

### 3-2. 실제로는 직접 짜지 않는다 — 계층별 표준 구현

위 코드는 원리를 이해하기 위한 것이고, **실무에서는 직접 짜지 않는 것이 정답이다.** 각 계층에 검증된 구현이 있고, 앞 계층에서 해석할수록 뒤 계층 전체가 혜택을 본다.

**Nginx — realip 모듈**

신뢰 프록시가 붙인 XFF를 해석해 **`$remote_addr` 자체를 실제 클라이언트 IP로 교체**한다. 즉 뒤 계층은 헤더를 볼 필요 없이 평소대로 소켓 주소를 읽으면 된다.

```nginx
# 신뢰하는 앞 계층 대역. 여러 줄로 여러 대역을 지정할 수 있다.
set_real_ip_from 10.0.0.0/8;

# 어느 헤더를 해석할 것인가. X-Real-IP 나 proxy_protocol 도 지정 가능하다.
real_ip_header   X-Forwarded-For;

# 핵심 스위치. on 이면 3-1의 rightmost 알고리즘대로 동작한다 —
# 오른쪽부터 신뢰 대역을 재귀적으로 걷어내고 처음 만나는 바깥 값을 취한다.
# off(기본)면 헤더의 마지막 항목 하나만 보고 끝내므로,
# 프록시가 2단 이상이면 앞단 프록시 IP가 클라이언트로 잡힌다.
real_ip_recursive on;
```

`real_ip_recursive`의 기본값이 `off`라는 점을 기억해 두자. **LB → Nginx처럼 프록시가 두 단 이상인 구성에서 이것을 켜지 않으면 클라이언트 IP가 LB의 IP로 잡힌다.** 설정을 다 했는데 로그에 여전히 내부 IP가 찍히는 흔한 원인이다.

교체 후에도 원래 소켓 주소가 필요하면 `$realip_remote_addr` 변수로 읽을 수 있다. 로그에 둘 다 남겨두면 사고 조사 때 유용하다.

**Spring Boot(내장 Tomcat) — `RemoteIpValve`**

같은 일을 WAS 레벨에서 하는 것이 Tomcat의 `RemoteIpValve`다. 활성화하면 `getRemoteAddr()`가 **해석된 클라이언트 IP**를 돌려주므로, 앱 코드는 헤더를 직접 파싱할 필요가 없다.

```yaml
# Before: 앱 코드 곳곳에서 request.getHeader("X-Forwarded-For").split(",")[0] 를 쓴다.
#         유틸 클래스가 하나 있고, 복붙된 변형이 서너 개 더 있다.
#         → 그중 하나라도 위조값을 쓰면 2절의 우회가 성립한다.

# After: 신뢰 프록시를 선언하고 getRemoteAddr() 로 일원화한다.
server:
  forward-headers-strategy: native      # 컨테이너(Tomcat)의 구현을 쓴다
  tomcat:
    remoteip:
      remote-ip-header: X-Forwarded-For
      protocol-header: X-Forwarded-Proto    # 스킴 복원도 함께 (17번 문서 3-2)
      # 신뢰(내부) 프록시 패턴. 여기 매칭되는 항목은 체인에서 걷어낸다.
      # 기본값도 사설 대역(10/8, 172.16-31/12, 192.168/16)과 루프백을
      # 이미 포함하고 있으므로, 프록시가 사설 IP를 쓴다면 기본값으로 충분한 경우가 많다.
      internal-proxies: "10\\.\\d{1,3}\\.\\d{1,3}\\.\\d{1,3}"
```

`RemoteIpValve`에는 신뢰 대상을 나누는 두 설정이 있고 **역할이 다르다.**

`internalProxies`는 "내 인프라의 프록시"다. 체인에서 조용히 걷어내고 기록도 남기지 않는다.

`trustedProxies`는 "신뢰하지만 기록은 남기고 싶은 프록시"다. CDN처럼 외부 사업자의 프록시가 여기 해당한다. 걷어내되 별도 헤더(`X-Forwarded-By`)에 옮겨 적어, "이 요청이 어느 CDN 엣지를 거쳐 왔는가"를 로그로 남길 수 있게 한다.

**동작 순서는 3-1의 알고리즘 그대로다.** 오른쪽 끝에서 시작해 `internalProxies`에 매칭되는 동안 걷어내고, `trustedProxies`에 매칭되면 기록하며 계속 걷어내고, 둘 다 아닌 값을 만나면 그것을 클라이언트 IP로 확정하고 멈춘다.

**Spring — `ForwardedHeaderFilter`**

`server.forward-headers-strategy: framework`를 주면 스프링이 `ForwardedHeaderFilter`를 등록한다. 이 필터는 `Forwarded`와 `X-Forwarded-*` 헤더를 읽어 요청 객체를 감싸고, `getScheme()`·`getServerName()`·`isSecure()`가 **원래 클라이언트 기준 값**을 돌려주게 만든다.

**여기서 `native`와의 차이를 정확히 알아야 한다.** [17번 문서 3-2](17-tls-termination-lb-vs-app.md)에서 다룬 것과 같은 구분이다.

| | `framework` (`ForwardedHeaderFilter`) | `native` (Tomcat `RemoteIpValve`) |
|---|---|---|
| 구현 위치 | 서블릿 필터 (컨테이너 무관) | 서블릿 컨테이너 내부 |
| 신뢰 프록시 지정 | **없다 — 헤더를 무조건 신뢰한다** | `internalProxies`/`trustedProxies`로 지정 |
| 실행 시점 | 필터 체인 안 (등록 순서에 의존) | 모든 필터보다 앞 |
| 안전 전제 | 최전선에서 XFF를 반드시 정리해야 함 | 신뢰 목록 밖 요청의 헤더는 스스로 무시 |

**`framework`는 신뢰 프록시를 지정하는 옵션이 없다.** 즉 도착한 헤더를 검증 없이 그대로 반영한다. 그래서 이 전략은 **"요청이 반드시 우리 프록시를 거쳐서만 들어온다"는 인프라 보장과, 최전선에서 클라이언트가 보낸 XFF를 덮어쓰는 정책**이 함께 있어야만 안전하다. 클라이언트 IP를 보안 판단(차단, allowlist, rate limit)에 쓸 거라면 신뢰 목록을 가진 `native` 쪽이 안전한 기본값이다.

`ForwardedHeaderFilter`에는 `removeOnly` 옵션도 있다. 헤더를 해석하지 않고 **제거만** 하는 모드로, 앞 계층에서 이미 해석이 끝났고 앱은 헤더를 아예 못 보게 하고 싶을 때 쓴다.

### 3-3. 해석 지점을 한 곳으로 모으고, 앱에서는 헤더를 읽지 않는다

계층별 구현을 다 알아도 **어디서 해석할지 정하지 않으면 소용없다.** 여러 곳에서 제각기 해석하면 계층마다 다른 답을 내놓고, 어느 것이 맞는지 아무도 모르게 된다.

원칙은 이렇다. **해석은 신뢰 체인의 입구(최전선 프록시 또는 WAS) 한 곳에서만 하고, 그 이후로는 `getRemoteAddr()`만 쓴다.** 그리고 애플리케이션 코드에서 `getHeader("X-Forwarded-For")`를 호출하는 것을 금지한다.

이 금지가 중요한 이유는 현실적이다. 헤더를 `split(",")[0]`으로 뜯는 유틸이 코드베이스에 하나 굴러다니기 시작하면, 복붙된 변형이 몇 개 더 생기고 그중 하나는 반드시 잘못 쓰인다. **정책이 아니라 구조로 막아야 한다** — 정적 분석 규칙이나 코드 리뷰 체크리스트에 넣어 아예 등장하지 못하게 하는 것이 현실적인 방어다.

**Spring Security로 IP 기반 접근 제어를 걸 때는 순서를 확인해야 한다.** Spring Security의 IP 매칭은 결국 `request.getRemoteAddr()`를 본다. 그러므로 그 값을 교체해 주는 장치가 **Security 필터 체인보다 먼저** 동작해야 한다.

```java
@Bean
SecurityFilterChain adminChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/admin/**")
        .authorizeHttpRequests(auth -> auth
            // 이 판정의 근거는 getRemoteAddr() 이다.
            // 그 값이 아직 프록시 IP라면 모든 요청이 통과하거나 모두 막힌다.
            // 그 값이 위조된 헤더로 채워졌다면 2-2 ③의 우회가 성립한다.
            .anyRequest().access(new WebExpressionAuthorizationManager(
                    "hasIpAddress('10.0.0.0/8')")));
    return http.build();
}
```

`native`(Tomcat `RemoteIpValve`)는 컨테이너 레벨이라 모든 서블릿 필터보다 먼저 동작하므로 이 문제가 없다. 반면 `framework`(`ForwardedHeaderFilter`)는 필터이므로 **Security 필터 체인보다 앞선 순서로 등록**돼야 한다.

그리고 한 가지 더. **IP allowlist는 그것만으로 관리자 인증을 대신하지 못한다.** 3-4의 전제가 깨지거나 사내망 안에서 사고가 나면 그대로 뚫린다. IP 제한은 인증·인가 위에 얹는 추가 계층으로 쓰는 것이지, 그 자리를 대신하는 것이 아니다.

### 3-4. 인프라 전제 — 우회로가 없어야 신뢰가 성립한다 (가산점 포인트)

지금까지의 논리는 전부 하나의 문장 위에 서 있다. **"요청은 반드시 내 신뢰 프록시를 거쳐서 온다."**

이 전제가 깨지면 어떻게 되는지 보자.

```
[전제가 지켜지는 구성]
  인터넷 → LB(공인 IP, 443만 열림) → 앱(사설 IP, LB에서 오는 8080만 허용)
  → 앱에 도달하는 모든 요청은 LB를 거쳤다. 체인의 오른쪽은 항상 LB다.

[전제가 깨진 구성]
  인터넷 → LB → 앱(사설 IP, 8080)
       ↘________________↗
        앱이 공인 IP를 갖고 있거나 보안 그룹이 0.0.0.0/0 으로 열려 있다

  공격자: curl -H "X-Forwarded-For: 1.2.3.4" http://<앱 공인 IP>:8080/admin

  이때 앱이 보는 것:
    소켓 주소 = 공격자 IP (신뢰 목록 밖)
    XFF       = 1.2.3.4  (공격자가 심은 값)

  → rightmost 알고리즘은 "소켓 주소가 신뢰 밖이니 그것이 클라이언트"라고
    올바르게 판정한다. 알고리즘 자체는 뚫리지 않는다.
  → 하지만 3-2의 framework 전략처럼 헤더를 무조건 신뢰하는 구성이거나,
    앞단에서 XFF를 정리하는 정책에 의존하고 있었다면 그 순간 전부 무너진다.
```

즉 **rightmost 알고리즘은 우회로가 있어도 비교적 견디지만, 그 위에 얹은 다른 전제들은 견디지 못한다.** 그리고 애초에 앱이 직접 노출돼 있다는 것 자체가 다른 종류의 위험(WAF 우회, 인증 계층 우회)을 함께 안고 있다.

그래서 **헤더 신뢰의 전제 조건은 네트워크 수준의 차단이다.**

- 앱 인스턴스에는 공인 IP를 주지 않는다. 프라이빗 서브넷에 둔다.
- 보안 그룹(또는 네트워크 정책)으로 **앱 포트를 LB의 보안 그룹에서 오는 트래픽에만 연다.** IP 대역이 아니라 보안 그룹 자체를 출발지로 지정할 수 있다면 그 편이 더 견고하다.
- 쿠버네티스라면 NetworkPolicy로 인그레스 파드에서 오는 트래픽만 허용한다.
- 최전선 프록시에서 **클라이언트가 보낸 `X-Forwarded-*`를 덮어쓰거나 제거**한다. `proxy_set_header X-Forwarded-For $remote_addr;`처럼 append가 아니라 **재시작**하면 체인이 항상 우리 관측값에서 시작하므로 해석이 극적으로 단순해진다. 다만 이 정책도 "최전선을 우회할 수 없다"는 전제 위에서만 유효하다.

**"헤더를 어떻게 파싱하느냐"는 이 설계의 절반이고, 나머지 절반은 네트워크 구성이다.** 이 둘을 함께 말하는 것이 이 질문에서 가산점을 받는 지점이다.

## 4. 꼬리질문 대비 포인트

### "XFF에 IP가 여러 개 들어 있으면 어떤 값을 써야 하나요?"

**가장 왼쪽 값이 아니다.** 오른쪽 끝(소켓 주소)에서 시작해 내가 신뢰하는 프록시 목록에 있는 IP인 동안 계속 걷어내고, **처음 만나는 신뢰 목록 밖의 값**이 실제 클라이언트 IP다.

왜 오른쪽부터인지를 설명하는 것이 답변의 핵심이다. XFF의 각 항목은 그것을 붙인 프록시가 **자기 소켓에서 직접 관측한 주소**다. 오른쪽으로 갈수록 우리 인프라에 가까운 장비가 적은 값이라 위조가 불가능하고, 왼쪽으로 갈수록 "전달받아 적혔을 뿐"이라 진위를 보증할 수 없다. 특히 가장 왼쪽 값은 클라이언트가 요청을 만들 때 직접 넣어 보낸 것일 수 있다 — 프록시는 들어온 값을 검사하지 않고 뒤에 덧붙이기만 하기 때문이다.

방향이 반대인 구현("왼쪽부터 걸으며 신뢰 대역을 건너뛴다")은 위험하다. 공격자가 신뢰 대역 IP를 앞에 여러 개 채워 넣어 자기가 원하는 값이 선택되게 만들 수 있다. **오른쪽에서 출발하는 것 자체가 안전성의 근거**다.

직접 구현할 필요는 없다. Nginx의 `real_ip_recursive on`, Tomcat `RemoteIpValve`의 `internalProxies`/`trustedProxies`가 이 알고리즘의 구현체다. 다만 `real_ip_recursive`의 기본값이 `off`라서 프록시가 2단 이상이면 앞단 프록시 IP가 클라이언트로 잡힌다는 것은 알아둬야 한다.

### "그럼 헤더 말고 getRemoteAddr()만 쓰면 안전한 것 아닌가요?"

**안전하지만 쓸모가 없다.** 이 둘을 구분해 말하는 것이 답의 핵심이다.

`getRemoteAddr()`는 TCP 소켓의 상대 주소이므로 위조되지 않는다. 3-way handshake가 성립해야 HTTP 요청을 보낼 수 있고, 출발지 IP를 위조하면 서버의 응답을 받지 못해 handshake 자체가 완료되지 않기 때문이다.

문제는 **프록시 뒤에서는 그 값이 언제나 프록시 IP**라는 것이다. 모든 사용자가 같은 IP로 보인다. 이 상태에서 IP 기반 rate limit을 걸면 전체 트래픽이 키 하나에 몰려 임계값을 즉시 넘고, 그 키를 차단하는 순간 전면 장애가 된다. 접근 로그도 전부 같은 값이라 사고 조사가 불가능하다.

그래서 답은 둘 중 하나를 고르는 것이 아니라 **결합**이다. **소켓 주소의 "위조 불가능성"** 과 **헤더의 "정보 전달"** 을 합친 것이 신뢰 프록시 기반 해석이다 — 소켓 주소에서 출발해 내가 아는 프록시들을 걷어내며 헤더를 따라 바깥으로 걸어 나간다.

덧붙여, **프록시가 없어 앱이 직접 노출된 서버라면 `getRemoteAddr()`만으로 충분하고 XFF는 오히려 무시해야 한다**는 대비까지 말하면 좋다. 그 환경에서 XFF를 읽는 코드는 순수한 취약점이다.

### "CDN(Cloudflare, CloudFront) 뒤에 있으면 어떻게 달라지나요?"

두 가지가 달라지고, 둘 다 함정이 있다.

**첫째, 신뢰 목록에 CDN의 엣지 IP 대역을 넣어야 한다.** 그런데 이 대역은 사업자가 공개하지만 **수시로 바뀐다.** 갱신을 자동화하지 않으면 어느 날 새로 추가된 엣지 대역이 "신뢰 밖"으로 분류되고, 그 엣지를 거친 요청의 클라이언트 IP가 엣지 IP로 잡힌다. 증상이 일부 사용자에게만 나타나 원인 파악이 어렵다. 사업자가 제공하는 IP 목록 엔드포인트를 주기적으로 받아 설정을 갱신하는 자동화가 필요하다.

**둘째, CDN이 주는 전용 헤더를 쓰는 방법이 있다.** Cloudflare의 `CF-Connecting-IP`, 일부 CDN이 제공하는 `True-Client-IP`처럼 **CDN이 자기 소켓에서 직접 관측한 클라이언트 IP만 담은 단일 값** 헤더다. 체인을 파싱할 필요가 없어 훨씬 단순하다.

**하지만 이 헤더 역시 그냥 믿으면 안 된다.** 이것도 결국 HTTP 헤더이므로 누구나 만들어 보낼 수 있다. **CDN을 우회해 오리진에 직접 요청하면 `CF-Connecting-IP: 1.2.3.4`를 위조해 꽂을 수 있다.** 즉 이 헤더의 안전성은 헤더 자체가 아니라 **"오리진에는 CDN을 통해서만 도달할 수 있다"는 보장**에서 나온다.

그래서 **오리진 보호가 반드시 짝으로 간다.** 오리진 방화벽에서 CDN의 IP 대역만 허용하거나, CDN과 오리진 사이에 공유 비밀값(전용 헤더나 mTLS)을 두어 CDN을 거치지 않은 요청을 거부한다. 오리진의 실제 IP를 숨기는 것만으로는 부족하다 — DNS 이력이나 인증서 투명성 로그로 노출되는 경우가 많다.

정리하면 **"CDN 전용 헤더는 편리하지만, 그 편리함의 근거는 오리진 보호"** 라는 인과를 말할 수 있어야 한다.

### "L4 LB 뒤에서는 XFF를 못 쓰지 않나요?" (가산점 포인트)

맞다. **XFF는 HTTP 헤더이므로 HTTP를 해석하는 L7 장비만 붙일 수 있다.** L4 로드밸런서는 TCP/UDP 수준에서 패킷을 전달할 뿐 페이로드를 들여다보지 않으므로, 헤더를 추가할 방법 자체가 없다([16번 문서](16-l4-vs-l7-load-balancer.md) 참고). TLS를 종료하지 않고 그대로 통과시키는 구성이라면 애초에 암호화돼 있어 손댈 수도 없다.

대안이 **PROXY protocol**이다. TCP 연결이 수립된 직후, **애플리케이션 데이터보다 먼저** 원 클라이언트의 주소 정보를 담은 짧은 전문을 한 번 보내기로 하는 약속이다. HTTP보다 아래 층에서 동작하므로 HTTP가 아닌 프로토콜(데이터베이스 연결, WebSocket, 원시 TCP)에도 쓸 수 있다는 것이 장점이다.

**주의할 점이 둘 있다.** 첫째, **양쪽 모두 활성화해야 한다.** 보내는 쪽만 켜면 뒤 서버가 그 전문을 HTTP 요청의 첫 줄로 해석해 400을 뱉고, 받는 쪽만 켜면 정상 요청의 첫 줄을 전문으로 오해해 연결이 깨진다. 통신 자체가 안 되므로 배포 순서를 맞춰야 한다.

둘째, **이것도 신뢰 문제를 그대로 안고 있다.** PROXY protocol 전문 역시 연결을 맺는 쪽이 쓰는 값이므로, 아무나 그 포트에 접속해 전문을 보낼 수 있다면 위조가 된다. 그래서 받는 쪽에 "이 대역에서 온 연결의 전문만 신뢰한다"는 설정(Nginx의 `set_real_ip_from`이 여기에도 쓰인다)이 필요하고, 3-4의 네트워크 차단 전제도 똑같이 필요하다.

### "실제 클라이언트 IP를 rate limiting이나 차단 키로 쓸 때의 한계는?" (시니어 변별 포인트)

**IP를 정확히 얻는 것과, 그 IP를 얼마나 믿고 결정에 쓸 것인가는 별개의 설계 문제다.** 이 구분에서 시작하는 것이 이 질문의 답이다. 3절까지의 내용을 완벽히 구현해도, IP라는 식별자 자체에 한계가 있다.

**한계 ① 여러 사람이 한 IP를 공유한다.** 통신사의 대규모 NAT(하나의 공인 IP를 수많은 가입자가 나눠 쓰는 구조)나 기업 프록시 뒤에서는 수백에서 수천 명이 같은 공인 IP로 나온다. 학교나 공공 와이파이도 마찬가지다. 여기서 IP 단위 차단을 걸면 **한 명의 공격자를 막으면서 같은 IP를 쓰는 무고한 사용자 전부를 함께 막는다.** 임계값을 낮게 잡을수록 이 오차단이 늘어난다.

**한계 ② IPv6에서는 정반대 문제가 생긴다.** IPv6는 주소가 방대해서 가입자 한 명에게 `/64`(주소 2의 64제곱 개) 이상의 블록을 통째로 할당하는 것이 보통이다. 그러면 같은 사용자가 요청마다 다른 주소를 쓸 수 있어 **IP 단위 제한이 무의미해진다.** 그래서 IPv6에서는 개별 주소가 아니라 **`/64` 같은 프리픽스 단위로 묶어** 카운트해야 한다. IPv4와 IPv6에 같은 로직을 쓰면 한쪽은 반드시 틀린다.

**한계 ③ 공격자 쪽에서는 IP를 대량으로 확보할 수 있다.** 봇넷, 상용 프록시 풀, 모바일 프록시 서비스를 쓰면 수만 개의 IP를 돌려가며 쓸 수 있다. IP 단위 제한은 **비용을 조금 올릴 뿐 막지는 못한다.**

**그래서 결론은 "IP는 단독 키가 아니라 보조 신호"** 라는 것이다. 실무의 조합은 이렇게 간다.

- **계정 단위 제한**을 1차로 둔다. 로그인 시도라면 대상 계정 기준으로 세는 것이 IP 기준보다 훨씬 정확하다 — 공격자가 IP를 바꿔도 표적 계정은 그대로이기 때문이다.
- **기기 지문·세션 식별자**를 함께 본다.
- **IP는 가중치 신호로** 쓴다. 차단의 단독 근거가 아니라 위험 점수를 올리는 요소로 쓰고, 점수가 높으면 차단 대신 **추가 인증(CAPTCHA, 2차 인증)** 으로 마찰을 올린다. 무고한 사용자는 통과할 수 있고 자동화 공격은 비용이 커지는 방향이다.
- 차단이 불가피하면 **기간을 짧게, 범위를 좁게** 건다. NAT 뒤 사용자를 오래 막지 않기 위해서다.

마지막으로 **관측 가능성**까지 말하면 좋다. 어떤 키로 무엇을 막았는지 로그로 남기고, 오차단이 의심되면 되돌릴 수 있어야 한다. 사고 조사를 위해 해석된 클라이언트 IP와 원래 소켓 주소, XFF 원본을 **함께** 남겨두면 나중에 판단을 재검토할 수 있다.

## 한 줄 요약

프록시 뒤에서 소켓 주소는 프록시 IP이므로 실제 클라이언트 IP는 `X-Forwarded-For`로 전달받지만, 이 헤더는 클라이언트가 처음부터 아무 값이나 넣어 보낼 수 있고 프록시는 그 뒤에 덧붙이기만 하므로 **체인의 왼쪽은 전부 위조값일 수 있다** — 그래서 `split(",")[0]`은 rate limit·차단·관리자 allowlist·감사 로그를 한 줄로 우회시키고, 올바른 해석은 위조 불가능한 소켓 주소에서 출발해 신뢰 프록시를 오른쪽부터 걷어내며 처음 만나는 바깥 값을 취하는 것(Nginx `real_ip_recursive`, Tomcat `RemoteIpValve`)을 한 곳에 일원화하는 것이다. 이 신뢰 모델은 앱에 프록시를 우회해 도달할 경로가 없다는 네트워크 차단이 있어야 성립하고(CDN 전용 헤더의 안전성도 오리진 보호에서 나온다), 그렇게 정확히 얻은 IP조차 NAT 공유와 IPv6 프리픽스 문제 때문에 단독 차단 키가 아니라 계정·기기 지문과 조합하는 보조 신호로 써야 한다.
