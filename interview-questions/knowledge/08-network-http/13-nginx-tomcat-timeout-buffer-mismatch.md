# Nginx-Tomcat 타임아웃/버퍼 불일치 — 계층 간 설정이 어긋나면 생기는 유령 현상

> 핵심 관전 포인트: **요청 하나는 Nginx와 Tomcat 양쪽의 설정 나사를 모두 통과하는데, 두 계층은 서로의 설정값을 모른다. 이 불일치가 앱 로그에 흔적을 안 남기는 유령 현상을 만든다 — Nginx의 응답 대기(`proxy_read_timeout`)가 Tomcat의 처리 시간보다 짧으면 사용자는 504를 봤는데 Tomcat은 끝까지 처리해 커밋해버리는 "유령 성공", 유휴 연결을 닫는 타이머가 어긋나면 Tomcat이 방금 닫은 연결에 Nginx가 요청을 실어 보내는 간헐적 502, 본문 크기 한도가 앱 설정과 어긋나면 "특정 크기 근처에서만 실패하는 업로드", 응답 헤더가 `proxy_buffer_size`를 넘으면 "특정 사용자만 502"가 된다. 정렬 규칙은 방향이 둘로 갈린다 — 응답을 기다리는 상한은 바깥 계층이 안쪽보다 길어야 하고(클라이언트 ≥ CDN ≥ LB ≥ Nginx ≥ 앱의 최악 처리), 유휴 연결의 수명은 반대로 재사용하는 쪽이 닫는 쪽보다 짧아야 한다. 그리고 무엇이 어긋났는지는 Nginx error log의 문구가 지문처럼 알려준다.**

---

## 0. 질문 + 의도

**질문**: "Nginx와 Tomcat 사이의 타임아웃/버퍼 설정 불일치로 생길 수 있는 문제는?"

**출제 의도**: 계층 간 설정 불일치가 만드는 유령 현상(업로드가 특정 크기에서만 실패, 간헐적 502)의 정체를 아는지 — 시스템을 자기 앱이 아니라 계층 스택 전체로 보는 시야를 확인한다. 이런 장애는 앱 로그에 단서가 없어서, 겪어본(또는 원리로 예측할 수 있는) 사람과 아닌 사람의 초동 대응이 극명하게 갈린다.

## 1. 왜 불일치가 문제인가 — 요청 하나, 나사는 양쪽에

### 1-1. 요청 하나가 통과하는 상한들

요청 하나가 사용자에게서 DB까지 갔다 오는 길에는, **계층마다 독립적으로 걸려 있는 상한**이 여럿 있다. 그림으로 보면 이렇다.

```
  [클라이언트] ──> [Nginx] ─────────────────> [Tomcat / Spring] ──> [DB · 외부 API]

                   client_max_body_size        multipart max-file-size
                   client_body_timeout         max-request-size

                   proxy_connect_timeout       (연결 수락 대기열)
                   proxy_send_timeout          connectionTimeout
                   proxy_read_timeout          실제 처리 시간

                   proxy_buffer_size           응답 헤더 크기(쿠키·토큰)
                   proxy_buffering             응답 생성 방식(스트리밍 여부)

                   upstream keepalive          keepAliveTimeout
                   keepalive_timeout           max-keep-alive-requests
```

**각 계층은 자기 나사만 알고 상대의 나사를 모른다.** Nginx는 Tomcat이 이 요청을 처리하는 데 얼마나 걸릴지 모르고, Tomcat은 Nginx가 언제쯤 기다리기를 포기할지 모른다. 두 값을 맞춰주는 자동 장치는 없다 — 사람이 손으로 맞춰야 한다.

그런데 사람은 대개 한쪽만 만진다. 업로드 크기를 늘려달라는 요구가 오면 Spring 설정만 고치고, 응답이 느리다는 말을 들으면 Nginx 타임아웃만 늘린다. 그렇게 두 값이 어긋난 채로 배포되면 **어긋난 구간에 들어오는 요청만 실패한다.**

이것이 유령 현상의 공통 구조다. 특징이 셋이다.

**첫째, 조건부로만 터진다.** 10MB짜리 파일만, 처리가 12초를 넘는 요청만, 권한이 많은 특정 사용자만 실패한다. 대부분의 요청은 멀쩡하므로 지표 대시보드에서는 잘 안 보인다.

**둘째, 재현이 어렵다.** "어제는 됐는데요"가 나오는 이유는 어제 올린 파일이 8MB였기 때문이다.

**셋째, 앱 로그에 아무것도 없다.** 반려한 주체가 Nginx라서 요청이 앱에 도달조차 하지 않았거나(413, 헤더 관련 502), 앱은 성공으로 처리를 마쳤기 때문이다(504 유령 성공). **"사용자는 에러를 봤는데 우리 로그는 깨끗하다"는 상황이면 계층 간 불일치를 의심하는 것**이 첫 반사 행동이어야 한다.

### 1-2. 나사 하나하나가 "무엇을 재는 시간"인가

설정 이름만 나열하면 외울 수 없다. 각각이 **어느 구간의 시간을 재는지**를 정의하고 넘어가야 나중에 로그를 보고 어느 나사가 터졌는지 짚을 수 있다.

**Nginx가 뒤쪽(Tomcat)을 상대로 재는 시간**

`proxy_connect_timeout`은 **백엔드와 TCP 연결을 맺기까지의 상한**이다. 3-way handshake가 끝날 때까지 기다리는 시간이지, 요청을 보내거나 응답을 받는 시간은 여기 포함되지 않는다. 같은 데이터센터 안이면 이 과정은 밀리초 단위이므로 몇 초면 충분하고, **이 값이 터졌다는 것은 "백엔드가 느리다"가 아니라 "백엔드에 닿지 못한다"는 뜻**이다(보안 그룹 차단, 라우팅 단절, 백엔드의 연결 수락 대기열 포화).

`proxy_send_timeout`은 **요청 본문을 백엔드에 쓰는 도중의 상한**이다. 그런데 여기에 중요한 단서가 붙는다 — **"연속된 두 번의 쓰기 작업 사이"의 간격이지 요청 전체를 보내는 데 걸리는 시간이 아니다.**

`proxy_read_timeout`은 **백엔드의 응답을 읽는 도중의 상한**이고, 504의 최다 발원지다. 그리고 이 역시 **"연속된 두 번의 읽기 작업 사이"의 간격**이다.

**Nginx가 앞쪽(클라이언트)을 상대로 재는 시간**

`client_header_timeout`과 `client_body_timeout`은 클라이언트가 요청 헤더/본문을 보내는 것을 기다리는 상한이고, `send_timeout`은 클라이언트에게 응답을 쓰는 도중의 상한이다. 이 셋도 전부 "두 번의 읽기/쓰기 사이" 간격이다.

`keepalive_timeout`은 성격이 다르다. **요청과 요청 사이에 아무것도 안 하고 있는 유휴 연결을 얼마나 살려둘지**를 정하는 값이다. 여기서 실무의 함정 하나 — **Nginx에는 이름이 같은 `keepalive_timeout`이 두 군데에 있다.** `http`/`server` 블록에 쓰면 **클라이언트 방향** 유휴 연결의 수명이고, `upstream` 블록 안에 쓰면 **백엔드 방향** 유휴 연결의 수명이다. 이름이 같아서 한쪽을 고치고 다른 쪽이 바뀌었다고 착각하는 일이 잦다.

**Tomcat이 재는 시간**

`connectionTimeout`은 **연결을 수락한 뒤 요청의 첫 줄(요청 URI 라인)이 도착하기를 기다리는 상한**이다. 연결만 맺어놓고 아무것도 안 보내는 클라이언트로부터 스레드를 지키는 장치다. Tomcat 자체의 기본값과 배포판이 함께 주는 `server.xml`의 값이 다르므로 짐작하지 말고 실제 설정을 확인해야 한다.

`keepAliveTimeout`은 **유휴 연결을 얼마나 살려둘지**다. **별도로 지정하지 않으면 `connectionTimeout` 값을 따라간다.** 그래서 "keep-alive 값을 안 건드렸다"는 말이 "기본값이 무엇인지 모른다"와 같은 뜻이 되는 일이 많다. Spring Boot라면 `server.tomcat.keep-alive-timeout`으로 명시적으로 박아두는 편이 안전하다.

**Tomcat에는 없는 나사 — 이것이 가장 중요하다**

여기서 반드시 짚어야 할 사실이 있다. **Tomcat에는 "요청 처리가 N초를 넘으면 중단한다"는 나사가 없다.** 위 값들은 전부 "네트워크에서 무언가를 기다리는 시간"이지, "내 스레드가 비즈니스 로직을 돌리는 시간"의 상한이 아니다.

이 사실이 뒤에 나올 유령 성공의 근본 원인이다. Nginx가 포기해도 Tomcat 스레드를 멈출 방법이 Tomcat 설정에는 없다. **안쪽의 시간 상한은 인프라 설정이 아니라 애플리케이션이 스스로 만들어야 한다** — 외부 API 호출의 connect/read 타임아웃, `@Transactional(timeout = ...)`, JDBC 문장의 `queryTimeout`, 비동기 요청이라면 `spring.mvc.async.request-timeout` 같은 것들이다.

### 1-3. `proxy_read_timeout`은 전체 응답 시간의 상한이 아니다

앞에서 두 번 언급한 "연속된 두 번의 읽기 사이"라는 단서를 따로 떼어 설명한다. **이 오해가 이 주제에서 가장 흔하고, 오해한 채로는 설명이 안 되는 현상이 여럿 생기기 때문이다.**

많은 사람이 `proxy_read_timeout 10s`를 **"응답이 10초 안에 다 끝나야 한다"**로 읽는다. 틀렸다. 정확한 의미는 **"Nginx가 백엔드로부터 아무 바이트도 못 받은 채로 10초가 지나면 포기한다"**이다. 즉 이 타이머는 **바이트가 하나라도 도착할 때마다 0으로 초기화된다.**

```
  [오해] proxy_read_timeout 10s = "응답 전체가 10초 안에 끝나야 한다"

  [사실] proxy_read_timeout 10s = "아무 바이트도 안 오는 구간이 10초를 넘으면 포기"

  ── 케이스 A: 처리에 30초 걸리고 그동안 아무것도 안 보내는 응답 ──
  t=0 ─────────────────────── (침묵) ───────────────────────> t=30 응답
      └──────── 10초 ───────┘
                            ★ 여기서 타임아웃. 504.

  ── 케이스 B: 30초 동안 3초마다 조금씩 흘려보내는 응답 ──
  t=0 ──3초──> 바이트 ──3초──> 바이트 ──3초──> 바이트 ... ──> t=30 완료
              (타이머 리셋)   (타이머 리셋)   (타이머 리셋)
                            ★ 타임아웃이 안 난다. 총 30초여도 통과.
```

**케이스 B가 스트리밍 응답이 이 타임아웃에 안 걸리는 이유**다. SSE(Server-Sent Events)나 대용량 파일 다운로드처럼 데이터를 조금씩 계속 흘려보내는 응답은, 전체 시간이 몇 시간이어도 조각과 조각 사이의 간격만 짧으면 `proxy_read_timeout`에 걸리지 않는다.

반대로 **이 성질을 이용한 실무 기법**도 나온다. SSE 연결에서 서버가 보낼 이벤트가 한동안 없으면 그 침묵 구간이 `proxy_read_timeout`을 넘겨 연결이 끊긴다. 그래서 SSE 서버는 보낼 것이 없어도 주기적으로 **하트비트(주석 줄 `: ping\n\n` 같은 무의미한 한 줄)를 흘려보낸다.** 타이머를 초기화하는 것이 목적이다. **타임아웃 값을 몇 시간으로 늘리는 대신 하트비트 주기를 타임아웃보다 짧게 잡는 것**이 더 나은 해법인데, 값을 늘리면 진짜로 멈춘 백엔드도 몇 시간 동안 붙들고 있게 되기 때문이다.

같은 논리가 `proxy_send_timeout`에도 적용된다. 대용량 업로드가 느린 모바일 회선에서 5분이 걸려도, 클라이언트가 계속 조금씩 보내고 있다면 이 값에 걸리지 않는다. **업로드가 오래 걸린다고 이 값을 무작정 키우는 것은 대개 헛다리**다.

## 2. 타임아웃 불일치 — 504와 유령 성공, 간헐적 502

### (1) proxy_read_timeout 부족 → 504와 유령 성공

**Nginx의 응답 대기 상한이 Tomcat의 실제 처리 시간보다 짧을 때** 벌어지는 일이다. 무거운 통계 쿼리나 느린 외부 API 호출이 끼어 있는 API에서 전형적으로 나온다.

1-2절의 마지막에서 짚었듯이, **Tomcat에는 처리를 중단시키는 나사가 없다.** 그래서 Nginx가 포기해도 Tomcat은 아무 일 없다는 듯 일을 계속한다. 이 두 사실이 합쳐지면 다음 타임라인이 나온다.

```
  [유령 성공 — proxy_read_timeout 10s, 실제 처리 14초인 결제 API]

  t =  0.0s  사용자 "결제하기" 클릭
             클라이언트 ──> Nginx ──> Tomcat : POST /orders
  t =  0.1s  Tomcat 스레드가 요청을 받아 처리 시작
             ┃ PG사 결제 승인 API 호출 ──> 응답 대기 중 (침묵 구간 시작)

  t = 10.0s  ★ Nginx의 proxy_read_timeout 만료 ★
             ┃ 10초 동안 백엔드로부터 단 1바이트도 안 왔다
             ┃
             ┣━ Nginx ──> 클라이언트 : 504 Gateway Timeout
             ┃            사용자 화면: "오류가 발생했습니다"
             ┃
             ┗━ Nginx ──> Tomcat : 업스트림 연결을 끊는다
                          error log: upstream timed out (110: Connection timed out)
                                     while reading response header from upstream

  t = 10.0s  Tomcat 쪽에서 일어나는 일: ★ 아무것도 없다 ★
             끊긴 것은 소켓이지 스레드가 아니다.
             서블릿 스레드는 여전히 PG 응답을 기다리는 중이고,
             자기 요청이 취소됐다는 통보를 받는 경로가 없다.

  t = 14.0s  PG 승인 성공 ──> 주문 INSERT ──> ★ COMMIT ★
             ┃ 트랜잭션은 여기서 이미 확정됐다.
             ┗━ 이제 200 응답을 쓰려 하지만 소켓은 이미 닫혀 있다
                ──> ClientAbortException (커밋은 이미 끝난 뒤다)

             앱 로그: "주문 생성 완료 orderId=8471"   <- 성공으로 남는다

  t = 20.0s  사용자가 "다시 시도" 클릭
             ──> 두 번째 주문, 두 번째 결제 승인 ──> ★ 이중 결제 ★
```

**t = 14.0s에서 COMMIT이 응답 쓰기보다 먼저 일어난다는 순서**가 이 현상의 전부다. 응답 전송이 실패해도 트랜잭션은 이미 확정됐으므로 DB에는 주문이 남는다. **"사용자는 실패를 봤는데 데이터는 만들어져 있다"는 미스터리의 정체**가 이것이고, **타임아웃은 처리를 중단시키는 게 아니라 기다림을 중단시킬 뿐**이라는 한 문장으로 요약된다.

대응은 세 방향이고, **순서가 있다.**

**첫째(근본), 그 요청이 왜 그렇게 오래 걸리는지를 고친다.** 쿼리를 튜닝하거나, 애초에 동기 요청으로 처리할 일이 아니면 비동기로 바꾼다 — 즉시 "접수했습니다"를 202로 응답하고 실제 처리는 뒤에서 하며, 클라이언트는 폴링이나 알림으로 결과를 받는다. **10초 넘게 걸리는 동기 HTTP 요청은 대개 설계가 잘못된 것**이라는 인식이 먼저다.

**둘째, 계층 간 타임아웃을 정렬한다.** Nginx의 대기 상한이 Tomcat의 최악 처리 시간(관측된 p99에 여유를 더한 값)보다 길게 만든다. 다만 **무작정 늘리는 것은 답이 아니다.** 상한을 60초로 키우면 느린 요청 하나가 Nginx 커넥션과 Tomcat 스레드를 60초씩 붙들게 허용하는 것이고, 그런 요청이 몰리면 스레드 풀이 고갈돼 전체 장애가 된다. **늘리기 전에 "이 시간이 정말 허용 가능한가"를 먼저 물어야 한다.**

**셋째, 쓰기 API를 멱등하게 만든다.** 타임아웃은 아무리 정렬해도 완전히 없앨 수 없다. 같은 요청이 두 번 와도 결과가 한 번 실행한 것과 같도록 멱등성 키를 도입하는 것이 최종 방어선이다(04번 문서 3절).

```java
// Before: 외부 호출에 타임아웃이 없다 — 안쪽 상한이 아예 존재하지 않는 상태.
// PG사가 응답을 안 주면 Tomcat 스레드는 무한정 붙들리고,
// Nginx만 혼자 포기해 504 + 유령 성공이 된다.
@Bean
RestClient pgClient() {
    return RestClient.create("https://pg.example.com");
}
```

```java
// After: 안쪽 상한을 앱이 스스로 만든다.
// Tomcat에는 "처리 시간 상한"이라는 나사가 없으므로, 이 값들의 합이
// 사실상 우리 서비스의 최악 처리 시간이 된다. Nginx 값은 이 합보다 길어야 한다.
@Bean
RestClient pgClient() {
    var factory = new SimpleClientHttpRequestFactory();
    // TCP 연결 수립까지. 같은 리전이면 1초면 충분하고,
    // 이 값이 터진다는 것은 상대가 느린 게 아니라 닿지 않는다는 뜻이다.
    factory.setConnectTimeout(Duration.ofSeconds(1));
    // 응답을 기다리는 상한. 이 값이 없으면 스레드가 영원히 묶인다.
    factory.setReadTimeout(Duration.ofSeconds(2));
    return RestClient.builder()
            .baseUrl("https://pg.example.com")
            .requestFactory(factory)
            .build();
}

// 트랜잭션에도 상한을 건다. 락 대기나 느린 쿼리로 커넥션이 무한정
// 묶이는 것을 막고, 최악 처리 시간을 계산 가능한 값으로 만든다.
@Transactional(timeout = 5)
public OrderResult placeOrder(OrderCommand command) { ... }
```

### (2) keep-alive 유휴 경쟁 → 간헐적 502

이번에는 시간의 길이가 아니라 **누가 먼저 연결을 닫느냐의 순서**가 문제가 되는 경우다.

전제부터 깔자. Nginx와 Tomcat 사이의 연결을 요청마다 새로 맺으면 3-way handshake 비용을 매번 치르고 TIME_WAIT도 쌓인다. 그래서 **`upstream` 블록에 `keepalive`를 설정해 유휴 연결을 풀에 넣어두고 재사용한다**(10번 문서 3-2절). 그런데 이 유휴 연결을 **"언제 닫을지" 결정하는 타이머가 양쪽에 따로 있다.**

```
  Nginx 쪽 : upstream 블록의 keepalive_timeout — 유휴 연결을 이만큼 보관한다
  Tomcat 쪽: keepAliveTimeout — 유휴 연결을 이만큼 뒤에 닫는다
```

**Tomcat의 유휴 상한이 Nginx보다 짧으면 경쟁 조건이 성립한다.** Tomcat이 유휴 연결을 닫는 바로 그 순간, Nginx가 아직 살아 있다고 믿는 그 연결에 새 요청을 실어 보내는 것이다.

핵심은 **Nginx가 이것을 미리 알 방법이 없다는 점**이다. Tomcat이 보낸 FIN은 "내 송신 방향이 끝났다"는 통보일 뿐이라 Nginx의 송신 방향은 여전히 열려 있고, 그래서 **요청을 쓰는 `write()`는 성공해 버린다.** 실패는 응답을 읽으려는 순간에야 드러난다. 이 half-close 경쟁의 타임라인은 **10번 문서 3-3절에 한 단계씩 그려져 있으므로 여기서 반복하지 않는다.**

Nginx 쪽에서 보이는 결과는 이렇다.

```
  error log : upstream prematurely closed connection
              while reading response header from upstream
  사용자    : 502 Bad Gateway
  특징      : 부하와 무관하게 하루 몇 번, 재현 불가, Tomcat 지표는 전부 정상
```

**규칙은 방향이 정해져 있다. 연결을 재사용하는 쪽(Nginx)의 유휴 상한이, 연결을 들고 있다가 닫는 쪽(Tomcat)의 유휴 상한보다 짧아야 한다.** 이렇게 하면 닫는 결정을 Nginx가 먼저 내리게 되는데, 풀에서 놀고 있는 연결을 자기 의지로 닫는 것이므로 경쟁 자체가 성립하지 않는다.

```nginx
# Nginx — upstream keep-alive의 정석 세트. 이 다섯 줄이 한 묶음이다.
upstream tomcat_upstream {
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;

    # 워커 프로세스 하나가 유지할 유휴 업스트림 연결 수.
    # 전체가 아니라 워커당이므로, worker_processes를 곱한 값이
    # Tomcat의 최대 커넥션 수용량을 넘지 않아야 한다.
    keepalive 64;

    # ★ 이 절의 핵심. Tomcat의 keepAliveTimeout보다 확실히 짧게 잡는다.
    #   (upstream 블록 안의 keepalive_timeout은 백엔드 방향 전용이다.
    #    server 블록의 같은 이름 지시자는 클라이언트 방향이라 별개다.)
    keepalive_timeout 30s;

    # 연결 하나로 몇 건까지 나른 뒤 폐기할지. 너무 작으면 재사용 이득이 사라지고,
    # 무한정 두면 백엔드를 교체해도 옛 인스턴스에 계속 붙어 있게 된다.
    keepalive_requests 1000;
}

server {
    location /api/ {
        proxy_pass http://tomcat_upstream;

        # keep-alive는 HTTP/1.1의 기능이다. Nginx는 업스트림에 기본적으로
        # HTTP/1.0으로 말하므로, 이 줄이 없으면 위의 keepalive가 전부 무용지물이다.
        proxy_http_version 1.1;

        # Nginx는 업스트림 요청에 기본으로 Connection: close를 붙인다.
        # 빈 문자열로 덮어 헤더 자체를 없애면 HTTP/1.1 기본값(연결 유지)이 적용된다.
        proxy_set_header Connection "";
    }
}
```

```yaml
# Spring Boot(내장 Tomcat) — 닫는 쪽. 위 Nginx 값보다 넉넉해야 한다.
server:
  tomcat:
    # 명시하지 않으면 connectionTimeout 값을 따라가므로,
    # "안 건드렸다"는 것은 "값을 모른다"와 같은 뜻이 된다. 반드시 박아둔다.
    keep-alive-timeout: 60s
    # 연결 하나로 받을 최대 요청 수. 이 값이 작으면 Tomcat이 먼저 끊는 일이
    # 잦아져 Nginx의 재사용 이득이 사라지고 경쟁 창도 자주 열린다.
    max-keep-alive-requests: 1000
```

여유를 얼마나 둘지에도 근거가 있다. Tomcat이 FIN을 보내는 순간과 그것이 Nginx에 도착하는 순간 사이에도 시간이 흐르고, 타이머가 정확히 그 값에 발동한다는 보장도 없다. **최소 몇 초, 가능하면 닫는 쪽 값의 절반 이하로 잡는 것이 안전하다** — 위 예시의 30s / 60s가 그 비율이다.

여기서 `proxy_next_upstream`이라는 나사가 함께 얽힌다. **이 지시자는 "업스트림에서 어떤 실패가 났을 때 다음 서버로 요청을 넘길지"를 정하고, 기본값은 `error timeout`이다.** keep-alive 경쟁으로 인한 끊김은 `error`로 분류되므로, **업스트림 그룹에 서버가 여러 대면 Nginx가 조용히 다른 서버로 넘겨 사용자 눈에는 502가 안 보일 수 있다.** 반대로 **서버가 한 대뿐인 그룹이면 넘길 곳이 없어 그대로 502가 된다.** 같은 버그가 스테이징에서는 안 보이고 운영에서만 보이거나 그 반대인 이유가 대개 이것이다.

그리고 이 재시도에는 대가가 따른다. **넘긴다는 것은 같은 요청을 한 번 더 실행한다는 뜻**이므로, 비멱등 요청(POST)이라면 중복 처리 위험이 생긴다. 다행히 **최근 Nginx는 요청을 이미 업스트림에 보낸 뒤라면 POST 같은 비멱등 메서드를 기본적으로 다음 서버로 넘기지 않는다** — 이 동작을 굳이 허용하는 `non_idempotent` 파라미터가 따로 있고, **그것을 켜는 순간 중복 처리가 가능해진다.** 켜기 전에 그 엔드포인트가 멱등한지 반드시 확인해야 한다.

또 하나 자주 놓치는 것은 **`timeout`이 기본 재시도 조건에 이미 들어 있다**는 점이다. 그래서 GET처럼 멱등으로 "선언된" 메서드가 실제로는 부작용을 만드는 코드라면(04번 문서의 규약 위반 사례), 프록시 계층이 조용히 그것을 두 번 실행시킨다. **프록시의 재시도도 애플리케이션 재시도와 똑같이 멱등성 검토 대상**이라는 것이 요점이다.

```nginx
location /api/ {
    proxy_pass http://tomcat_upstream;

    # 무엇을 다음 서버로 넘길지 명시한다. 기본값(error timeout)을 그냥 두는 것과
    # 알고 두는 것은 다르다. 아래는 "연결 단계 실패만 넘긴다"는 보수적 선택 —
    # 요청이 백엔드에 닿기 전이므로 중복 실행 위험이 없다.
    proxy_next_upstream error;

    # 넘기는 횟수와 총 시간에도 상한을 둔다. 없으면 장애 시
    # 한 요청이 모든 백엔드를 순회하며 전체 응답 시간을 몇 배로 키운다.
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 5s;
}
```

### (3) 체인 전체의 타임아웃 정렬 (가산점 포인트)

실제 요청 경로는 Nginx와 Tomcat 두 층이 아니다. `클라이언트 → CDN → LB → Nginx → Tomcat → 앱의 외부 호출`처럼 더 길고, **각 층이 전부 자기 대기 상한을 들고 있다.**

원칙은 한 문장이다. **바깥 계층의 대기 상한이 안쪽에서 벌어지는 일의 최악 소요보다 길어야 한다.** 이유는 (1)절에서 본 그대로다 — 안쪽이 아직 일하고 있는데 바깥이 먼저 끊으면 유령 성공이 생기고, 층이 여러 개면 그 사고가 층마다 반복된다.

숫자로 보면 규칙이 확실해진다. 아래는 **예시 값**이고, 실제 값은 자기 서비스의 관측치에서 나와야 한다.

```
  안쪽에서 바깥으로 쌓아 올린다 (합산 → 여유 추가 → 상위 층 값 확정)

  ┌ 앱 → PG사 호출 1회      : connect 1s + read 2s          =  3.0s
  │  재시도 1회 + 백오프 0.5s : 3.0 + 0.5 + 3.0               =  6.5s
  ├ DB 쿼리 + 비즈니스 로직 최악                              +  1.5s
  │                                                          ────────
  └ 앱 내부 최악 처리 시간 합                                 =  8.0s
        │  (+ 2s 여유: 스레드 배정 대기, GC 정지)
        v
    앱 자체 가드 (@Transactional timeout, async request-timeout) : 10s
        │  (+ 5s 여유)
        v
    Nginx  proxy_read_timeout                                    : 15s
        │  (+ 5s 여유)
        v
    LB(ALB) idle timeout                                         : 20s
        │  (+ 5s 여유)
        v
    CDN  origin response timeout                                 : 25s
        │  (+ 5s 여유)
        v
    클라이언트 SDK read timeout                                  : 30s

  검산: 8 < 10 < 15 < 20 < 25 < 30  — 모든 층에서 바깥이 안쪽보다 크다.
```

**여유를 두는 이유**를 짚고 넘어가자. 안쪽 값에 딱 붙여 놓으면 안 되는 것은, 층과 층 사이에 **"아직 시작도 못 한 시간"**이 끼어 있기 때문이다. 요청이 Nginx에 도착한 뒤 Tomcat의 스레드를 배정받기까지 큐에서 기다리는 시간, 네트워크 왕복, GC 정지 같은 것들이다. 이 시간은 안쪽 처리 시간에 포함되지 않는데 바깥 타이머는 이미 돌고 있다.

**이 정렬은 07장의 "타임아웃 예산"과 같은 산수를 계층 스택에 적용한 것**이다. 다만 방향이 반대다. 07장은 사용자 응답 SLO에서 출발해 바깥에서 안으로 예산을 나눠주는 하향식이고, 여기서는 안쪽 관측치에서 출발해 바깥으로 쌓아 올리는 상향식이다. **실무에서는 둘 다 해서 중간에서 만나는지 확인한다** — 상향식으로 쌓은 8초가 하향식으로 나눈 예산을 넘어서면, 타임아웃을 조정할 게 아니라 그 처리 자체를 바꿔야 한다는 신호다.

**그리고 여기에 방향이 정반대인 규칙이 하나 더 있다.** (2)절에서 본 유휴 연결 수명이다.

```
  [대기 상한] 바깥이 길게        [유휴 수명] 안쪽이 길게
   클라이언트 30s                 ALB idle timeout      60s   (재사용하는 쪽)
        ≥                              <
   CDN        25s                 Nginx keepalive_timeout 75s (닫는 쪽)
        ≥
   LB         20s                 Nginx upstream
        ≥                           keepalive_timeout   30s   (재사용하는 쪽)
   Nginx      15s                       <
        ≥                        Tomcat keepAliveTimeout 60s  (닫는 쪽)
   앱         10s
```

**두 규칙이 반대 방향인 이유**를 말할 수 있어야 한다. **대기 상한은 "일이 끝나기를 기다리는 시간"**이라 바깥이 더 오래 기다려야 안쪽 일이 완주할 수 있다. **유휴 수명은 "쓰지 않는 연결을 들고 있는 시간"**이라 재사용하는 쪽이 먼저 정리해야 "이미 닫힌 연결에 요청을 싣는" 경쟁이 안 생긴다. **"대기 상한은 바깥이 길게, 유휴 수명은 안쪽이 길게"** — 이 두 문장을 구분해 말하면 이 주제를 한 번 정리해 본 사람으로 들린다.

## 3. 크기·버퍼 불일치와 진단

### (1) client_max_body_size vs multipart 한도 → 413

이번에는 시간이 아니라 **크기**의 불일치다. 증상은 "작은 파일은 되는데 큰 파일만 안 된다"로 나타난다.

Nginx의 `client_max_body_size`는 **클라이언트가 보낸 요청 본문의 최대 크기**이고 **기본값은 1MB**다. 이 값을 넘는 요청은 **Tomcat에 도달하기 전에 Nginx가 413으로 반려한다.** 상태 코드의 이름은 Nginx 기본 에러 페이지에 `413 Request Entity Too Large`로 나오는데, 최신 HTTP 명세에서는 같은 코드가 `Content Too Large`로 개명됐다. 같은 것이다.

여기서 중요한 동작 하나. **Nginx는 요청 본문을 다 받아본 뒤에 판단하는 게 아니라, `Content-Length` 헤더 값을 보고 즉시 거절한다.** 그래서 100MB 파일을 올리면 100MB를 다 전송한 뒤 실패하는 게 아니라 시작하자마자 413이 온다. 이것은 대역폭을 아끼는 좋은 동작이지만, 뒤에 나올 "연결이 끊겨 보이는" 현상의 원인이기도 하다.

**Spring 쪽에도 같은 성격의 한도가 둘 있는데, 둘의 차이가 실무에서 자주 사고를 만든다.**

`spring.servlet.multipart.max-file-size`는 **개별 파일 하나**의 최대 크기다. `spring.servlet.multipart.max-request-size`는 **요청 전체**의 최대 크기로, 여러 파일과 다른 폼 필드, 그리고 multipart 형식이 만드는 경계 문자열과 파트 헤더까지 전부 합친 값이다.

그래서 **둘을 같은 값(예: 둘 다 10MB)으로 잡으면, 정확히 10MB짜리 파일 하나를 올렸을 때 `max-file-size`는 통과하지만 `max-request-size`에는 걸린다.** 오버헤드만큼 요청 전체가 더 크기 때문이다. "파일 크기 한도를 10MB로 맞춰놨는데 왜 10MB 파일이 안 올라가죠"의 흔한 정답이 이것이다.

단위 해석도 확인해 둘 만하다. **Nginx의 `m`과 Spring의 `MB`는 둘 다 1024×1024 기준**이라 서로 어긋나지 않는다. 다만 **운영체제 파일 탐색기가 보여주는 "MB"는 1,000,000 기준일 수 있어서**, 경계 근처에서는 사람이 보는 숫자와 서버가 재는 숫자가 다르다. 경계 테스트는 바이트 단위로 만든 파일로 해야 한다.

```nginx
# Before: 기본값 1m — 프로필 이미지 2MB 업로드가 413으로 반려된다.
# 앱에는 요청이 도달조차 하지 않으므로 앱 로그에는 아무 흔적이 없다.
server {
    location /api/ {
        proxy_pass http://tomcat_upstream;
    }
}
```

```nginx
# After: 정책 값(20MB)에 오버헤드 여유를 더해 앱보다 살짝 크게 잡는다.
# 이렇게 하면 실제 판정을 앱이 하게 되어, 사용자는 Nginx의 밋밋한 HTML 대신
# 우리 서비스의 일관된 에러 JSON을 받는다.
server {
    client_max_body_size 21m;

    location /api/ {
        proxy_pass http://tomcat_upstream;
    }
}
```

```yaml
# Spring — 실제 정책 값은 여기서 정한다.
spring:
  servlet:
    multipart:
      # 파일 하나의 상한
      max-file-size: 20MB
      # 요청 전체의 상한. 파일 + 폼 필드 + multipart 오버헤드를 모두 합친 값이므로
      # max-file-size와 같게 두면 경계에서 어긋난다. 반드시 더 크게 잡는다.
      max-request-size: 25MB
```

**Nginx를 앱보다 크게 둘지 작게 둘지는 트레이드오프**라는 것도 알고 있어야 한다. Nginx를 작게 두면 **대역폭과 디스크를 아낀다**(거대한 본문이 앱까지 오지 않는다). 앱을 판정자로 두면 **에러 응답의 일관성을 얻는다**(우리 포맷의 JSON, 사용자에게 보여줄 메시지). 정답은 서비스 성격에 달렸지만, **둘 중 어느 쪽이 판정자인지를 의식적으로 정해두는 것**이 중요하다. 모르고 두면 사용자가 받는 에러가 그때그때 다르다.

**여기에 마지막 함정이 하나 더 붙는다 — Tomcat의 `maxSwallowSize`다.**

Tomcat이 업로드를 거절하기로 결정했다고 하자(예: `max-file-size` 초과). 그런데 클라이언트는 그 사실을 모르고 **남은 본문을 계속 보내고 있다.** Tomcat이 이 연결을 다음 요청에 재사용하려면 **남은 본문을 끝까지 읽어서 버려야 한다.** 이 "읽고 버리는" 동작을 swallow(삼키기)라고 하고, **`maxSwallowSize`는 그렇게 삼켜줄 최대 바이트 수**다.

남은 본문이 이 값을 넘으면 Tomcat은 삼키기를 포기하고 **연결을 그냥 닫아버린다.** 그러면 클라이언트는 어떻게 될까? **서버가 보낸 에러 응답을 미처 읽기도 전에 연결이 끊긴 것을 먼저 감지한다.** 그래서 브라우저에는 친절한 413 에러 페이지 대신 `ERR_CONNECTION_RESET`이 뜨고, `curl`에는 `Recv failure: Connection reset by peer`가 뜬다.

**"파일 업로드에 실패하면 에러 메시지가 아니라 연결이 끊겨요"**의 정체가 이것이다. 이 값의 기본값은 Tomcat 버전에 따라 다르므로 확인해야 하고, `-1`로 두면 크기 제한 없이 전부 삼킨다(연결은 살지만 그만큼 대역폭을 낭비한다). 실무의 현실적인 대응은 **애초에 Nginx에서 먼저 잘라 큰 본문이 Tomcat까지 오지 않게 하는 것**이다.

**"10MB 근처에서만 실패한다"를 이분 탐색으로 좁히는 절차**

크기 의존적 실패는 **경로상 어딘가의 크기 한도**이므로, 어느 층인지만 찾으면 끝난다. 층은 최대 다섯 개(CDN → LB → Nginx → Tomcat → Spring)이므로 이분 탐색으로 두세 번이면 좁혀진다.

**0단계 — 경계를 바이트 단위로 확정한다.** 사람이 말하는 "10MB쯤"으로는 판단이 흔들린다.

```bash
# 정확한 크기의 파일을 만든다. 8MiB는 되고 12MiB는 안 된다면
# 그 사이를 반씩 좁혀 경계 바이트 수를 찾는다.
head -c $(( 8 * 1024 * 1024)) /dev/urandom > /tmp/8m.bin
head -c $((10 * 1024 * 1024)) /dev/urandom > /tmp/10m.bin
head -c $((12 * 1024 * 1024)) /dev/urandom > /tmp/12m.bin
```

**1단계 — 실패 응답의 지문으로 층을 추정한다.** 응답 본문과 헤더가 어느 제품의 것인지 말해준다.

```bash
curl -i -F "file=@/tmp/12m.bin" https://api.example.com/upload
```

| 응답 | 범인 |
|---|---|
| `413` + 본문에 `<center>nginx/1.x.x</center>` | Nginx `client_max_body_size` |
| `413`(또는 `500`) + 우리 서비스의 에러 JSON | Spring multipart 한도 |
| `413` + `Server: awselb/2.0` 또는 CloudFront 지문 | LB/CDN의 본문 한도 |
| `curl: (56) Recv failure: Connection reset by peer` | 반려 후 연결 종료 — `maxSwallowSize` 의심 |

**2단계 — 층을 건너뛰고 직접 때려본다.** 이것이 이분 탐색의 본체이자 가장 확실한 방법이다. 바깥 층을 빼고 같은 파일을 보내서 성공하면 **경계는 그 바깥 층에 있는 것**이고, 여전히 실패하면 **더 안쪽에 있는 것**이다.

```bash
# CDN을 건너뛰고 LB 도메인으로 직접
curl -i -F "file=@/tmp/12m.bin" https://lb-internal.example.com/upload

# Nginx를 건너뛰고 Tomcat에 직접 (사설 IP:8080)
curl -i -F "file=@/tmp/12m.bin" http://10.0.0.11:8080/upload
```

**3단계 — 로그로 확정한다.** 추정을 물증으로 바꾸는 단계다.

Nginx error log에는 `client intended to send too large body: 12582912 bytes`가 남고, **이 숫자가 서버가 실제로 본 본문 크기**다. 사람이 말한 "12MB"와 이 숫자가 다르면 오버헤드나 단위 착오가 끼어 있다는 뜻이다. Spring 쪽이면 `MaxUploadSizeExceededException`이 남는데, 원인 예외가 파일 하나 초과인지 요청 전체 초과인지를 보면 `max-file-size`와 `max-request-size` 중 어느 쪽인지가 갈린다.

**4단계 — 고칠 때는 전 계층을 한 번에 바꾼다.** 한 층만 늘리면 다음 층에서 같은 장애가 반복된다. **파일 크기 요구사항이 바뀔 때 CDN·LB·Nginx·Spring·`maxSwallowSize`를 함께 점검하는 체크리스트**를 만들어 두는 것이 재발 방지의 실질적인 답이다.

### (2) proxy_buffer_size vs 큰 응답 헤더 → 502

이번 불일치는 본문이 아니라 **응답 헤더**의 크기에서 난다. 그리고 증상이 특이해서 원인을 모르면 아주 오래 헤맨다.

전제. **Nginx는 백엔드 응답의 상태 줄과 헤더 전체를 `proxy_buffer_size` 하나에 담아야 한다.** 헤더가 여러 버퍼에 나뉘어 담기는 구조가 아니다. 기본값은 4KB 또는 8KB(플랫폼의 메모리 페이지 크기)인데, 정확한 값은 빌드에 따라 다르므로 `nginx -T`로 확인하는 편이 낫다.

응답 헤더가 이 크기를 넘으면 Nginx는 `upstream sent too big header while reading response header from upstream`을 남기고 **502**를 반환한다. 요청은 Tomcat에 정상 도달했고 Tomcat도 정상 응답을 만들었는데, **그것을 받아 담지 못한 Nginx가 502를 만드는 것**이다. 그래서 앱 로그는 성공으로 남는다.

**응답 헤더가 커지는 원인**은 대개 셋이다. 첫째, `Set-Cookie`가 여럿인 경우 — 세션 쿠키에 SSO 쿠키에 추적 쿠키가 겹치면 금방 몇 KB가 된다. 둘째, **JWT를 헤더로 내려주는 경우** — 권한 클레임이 많은 사용자의 토큰은 다른 사용자보다 훨씬 크다. 셋째, OIDC 리다이렉트처럼 `Location` 헤더에 `state`, `nonce` 같은 긴 값이 붙는 경우다.

**"로그인한 특정 사용자만 502가 난다"**는 제보의 전형적인 정답이 이것이다. 권한이 많은 관리자 계정이나 소속 조직이 많은 계정만 헤더가 커져 임계값을 넘기 때문에, **데이터에 의존해 사람마다 다르게 나타난다.** 부하와도 무관하고 재현도 그 계정으로만 된다.

```nginx
# Before: 기본 버퍼. 권한 클레임이 많은 사용자의 JWT가 헤더에 실리면
# upstream sent too big header 로그와 함께 502.
location /api/ {
    proxy_pass http://tomcat_upstream;
}
```

```nginx
# After: 헤더 버퍼를 키운다.
location /api/ {
    proxy_pass http://tomcat_upstream;

    # 응답 상태 줄 + 헤더 전체가 이 한 조각에 들어가야 한다.
    # 실제 헤더 크기를 측정한 뒤 여유를 두고 정한다 (감으로 키우지 않는다).
    proxy_buffer_size 16k;

    # 응답 본문을 담을 버퍼들. 헤더 판정과는 별개지만, 헤더를 키울 때
    # 본문 버퍼도 함께 검토하는 것이 관례다.
    proxy_buffers 8 16k;
}
```

**다만 설정을 키우는 것은 대증요법**이라는 점을 함께 말해야 한다. 근본은 **헤더에 큰 데이터를 싣지 않는 것**이다. 권한 정보 전체를 JWT에 넣는 대신 필요한 최소 클레임만 넣고 나머지는 서버에서 조회하거나, 응답 본문으로 내리는 설계가 맞다. 헤더는 모든 프록시가 버퍼에 담아야 하는 공용 자원이므로 **커질수록 모든 계층에서 문제가 된다.**

혼동하기 쉬운 것 하나. **요청 헤더가 큰 경우는 완전히 다른 지시자(`large_client_header_buffers`)의 관할이고 결과 코드도 4xx 계열**이다. `proxy_buffer_size`는 오직 **응답** 헤더용이다. Tomcat/Spring 쪽에도 요청 헤더의 상한이 따로 있으므로, "쿠키가 커서 안 된다"는 증상은 요청 방향인지 응답 방향인지부터 갈라야 한다.

### (3) 응답 버퍼링 vs 스트리밍 — SSE가 안 흐르는 이유

여기서는 **좋은 기본값이 특정 요구와 정면으로 충돌하는** 사례를 다룬다. 트레이드오프를 정직하게 다루는 것이 이 절의 목적이다.

`proxy_buffering`은 기본이 `on`이고, 이 상태에서 Nginx는 **Tomcat의 응답을 자기 버퍼에 최대한 빨리 받아 챙긴 뒤 Tomcat 스레드를 즉시 놓아주고**, 클라이언트에게는 그쪽 속도에 맞춰 천천히 흘려보낸다. **느린 클라이언트로부터 비싼 WAS 스레드를 격리하는 장치**이고, 12번 문서에서 Nginx의 핵심 역할로 다룬 바로 그 버퍼링이다. 버퍼로 감당이 안 되는 큰 응답은 디스크 임시 파일로 내려간다.

**그런데 이 좋은 기본값이 스트리밍 응답과는 정면으로 충돌한다.**

SSE(Server-Sent Events)는 서버가 이벤트를 만들 때마다 즉시 클라이언트에게 흘려보내는 방식이다. 그런데 버퍼링이 켜져 있으면 **Nginx가 이벤트를 버퍼에 모아두고 있어서** 실시간성이 깨지거나, 버퍼가 찰 때까지 아무것도 전달되지 않는다. "로컬에서는 알림이 즉시 오는데 배포하면 안 온다"는 제보의 단골 원인이다.

```nginx
# 스트리밍이 필요한 경로만 버퍼링을 끈다.
# 전역으로 끄면 버퍼링의 보호 효과를 통째로 버리는 것이다.
location /api/notifications/stream {
    proxy_pass http://tomcat_upstream;
    proxy_http_version 1.1;

    # 이벤트를 모아두지 말고 생기는 대로 클라이언트에게 흘려보낸다.
    proxy_buffering off;

    # 이벤트 사이의 침묵 구간이 이 값을 넘으면 끊긴다(1-3절).
    # 값을 키우는 것보다 앱이 하트비트를 주기적으로 보내는 편이 낫지만,
    # 안전판으로 함께 늘려둔다.
    proxy_read_timeout 3600s;
}
```

**그리고 여기서 대가를 정직하게 말해야 한다.** `proxy_buffering off`는 **응답 전송이 클라이언트의 속도에 묶인다**는 뜻이고, 그것은 곧 **Tomcat 스레드가 클라이언트가 다 읽을 때까지 붙들린다**는 뜻이다. 12번 문서에서 "버퍼링으로 WAS를 격리한다"고 한 그 보호막을 스스로 걷어내는 것이다. 지하철에서 3G로 접속한 사용자 수천 명이 붙으면 Tomcat 스레드 풀이 그대로 고갈된다.

**그래서 SSE를 쓸 때는 인프라 설정만으로 끝나지 않는다.** SSE 연결은 애초에 몇 분에서 몇 시간씩 유지되는 장수 연결이라, **서블릿 스레드 하나를 그 시간 내내 붙들면 동시 접속자 수가 스레드 풀 크기로 제한된다.** 그래서 SSE는 스레드를 붙들지 않는 비동기 방식(`SseEmitter`나 리액티브 스택)으로 구현해야 하고, `proxy_buffering off`는 그 위에 얹는 인프라 설정이다. **"버퍼링만 끄면 된다"고 답하면 절반만 아는 것**이다.

**응답 단위로 예외를 두는 방법**도 있다. 앱이 응답 헤더에 `X-Accel-Buffering: no`를 실어 보내면 Nginx가 그 응답에 한해 버퍼링을 끈다. `location` 블록을 손대지 않고 **앱이 스스로 "이 응답은 스트리밍입니다"라고 선언하는 방식**이라, 인프라 담당자와 앱 담당자가 다른 조직일 때 협업 비용이 크게 낮아진다.

```java
// 앱이 응답 단위로 버퍼링 해제를 선언한다.
// Nginx의 location 설정을 바꾸지 않아도 이 응답만 즉시 흘러간다.
@GetMapping(value = "/api/notifications/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter stream(HttpServletResponse response) {
    // Nginx가 이 헤더를 보고 이 응답에 한해 proxy_buffering을 끈다.
    response.setHeader("X-Accel-Buffering", "no");
    // 서블릿 스레드를 붙들지 않는다 — 컨트롤러는 즉시 반환하고,
    // 이후 이벤트는 별도 스레드가 emitter로 밀어 넣는다.
    SseEmitter emitter = new SseEmitter(Duration.ofHours(1).toMillis());
    notificationService.register(emitter);
    return emitter;
}
```

### (4) error log 메시지가 불일치의 지문이다

지금까지 본 불일치들은 전부 **Nginx error log에 서로 다른 문구**를 남긴다. 그래서 로그 한 줄만 읽으면 어느 나사가 어긋났는지 바로 좁혀진다. **이 매핑이 이 주제에서 실무적으로 가장 값나가는 지식**이다.

| error log 문구 | 어긋난 나사 | 사용자가 본 코드 |
|---|---|---|
| `upstream timed out (110) ... while connecting to upstream` | `proxy_connect_timeout` — 연결조차 못 맺었다(네트워크·보안 그룹·accept 큐) | 504 |
| `upstream timed out (110) ... while reading response header from upstream` | `proxy_read_timeout` < 백엔드 처리 시간 — 유령 성공 위험 | 504 |
| `upstream prematurely closed connection while reading response header` | keep-alive 유휴 경쟁, 또는 처리 중 프로세스 죽음 | 502 |
| `connect() failed (111: Connection refused) while connecting to upstream` | Tomcat 다운, 포트 오타, 배포 중 | 502 |
| `upstream sent too big header while reading response header` | `proxy_buffer_size` < 응답 헤더 | 502 |
| `client intended to send too large body: N bytes` | `client_max_body_size` < 요청 본문 (N이 실제 크기) | 413 |

**이 표를 쓰려면 전제 조건이 있다.** error log만으로는 "어느 요청이었는지"를 액세스 로그와 이어 붙이기 어렵다. 그래서 액세스 로그에 **업스트림 관련 변수**를 미리 남겨둬야 한다.

```nginx
log_format upstreamlog
    '$remote_addr "$request" '
    # 내가 클라이언트에게 내보낸 코드
    'status=$status '
    # 업스트림이 나에게 준 코드. 비어 있으면(-) 응답을 아예 못 받았다는 뜻이고,
    # 그 경우 그 코드는 "Nginx가 만든 것"이 확정된다.
    'upstream_status=$upstream_status '
    # 연결 수립까지 걸린 시간. proxy_connect_timeout에 붙어 있으면 연결 단계 문제.
    'ucon=$upstream_connect_time '
    # 응답 헤더의 첫 바이트까지 걸린 시간 = 백엔드의 실질 처리 시간.
    'uhdr=$upstream_header_time '
    # 업스트림 응답 전체 시간. 이 값이 proxy_read_timeout에 딱 붙어 있으면
    # "백엔드가 느렸다"가 아니라 "Nginx가 못 기다렸다"는 확정 증거다.
    'ures=$upstream_response_time';

access_log /var/log/nginx/access.log upstreamlog;
```

**핵심은 `$upstream_response_time`과 `proxy_read_timeout` 값의 대조**다. 응답 시간이 타임아웃 값에 소수점까지 붙어 있는 요청들이 보이면, 그것은 백엔드의 성능 문제가 아니라 **계층 간 설정 부정합의 물증**이다. 성능 튜닝을 시작하기 전에 이것부터 확인해야 엉뚱한 곳을 파지 않는다.

그리고 **Nginx 지시자의 기본값은 버전과 빌드에 따라 다를 수 있으므로 문서의 숫자를 믿지 말고 `nginx -T`로 실제 적용된 전체 설정을 덤프해 확인하는 것**이 확실하다. 특히 `include`가 여러 겹인 구성에서는 어느 파일의 값이 최종적으로 이겼는지가 눈으로 안 보인다.

## 4. 꼬리질문 대비 포인트

### "간헐적으로 502가 나는데 Tomcat 메트릭은 멀쩡합니다. 뭘 의심하겠어요?"

**먼저 Nginx error log의 문구를 본다.** 이 질문에서 가장 중요한 것은 "무엇을 의심하겠다"보다 **"어디를 보고 판단하겠다"**를 먼저 말하는 것이다. 502는 Nginx가 만든 코드이므로 1차 증거가 Nginx에 있다.

문구가 `upstream prematurely closed connection`이면 **keep-alive 유휴 타임아웃 경쟁**이 1순위 가설이다. Tomcat이 유휴 연결을 닫는 순간과 Nginx가 그 연결을 재사용하는 순간이 겹친 것이고, Nginx는 이것을 미리 알 수 없다(FIN을 받아도 `write()`는 성공하므로). 대응은 **Nginx upstream 블록의 `keepalive_timeout`을 Tomcat의 `keepAliveTimeout`보다 확실히 짧게** 정렬하는 것이다.

문구가 `connect() failed (111: Connection refused)`인데 배포 시점과 겹친다면 **롤링 재시작의 틈**을 의심한다. graceful shutdown이 없거나, LB 대상 제외보다 프로세스 종료가 먼저 일어나는 순서 문제다.

문구가 `upstream sent too big header`라면 **응답 헤더 크기**다. 이 경우 "간헐적"으로 보이는 이유는 시간이 아니라 **사용자에 따라** 헤더 크기가 다르기 때문이므로, 실패한 요청들의 계정 특성을 확인한다.

**핵심은 "Tomcat이 멀쩡해 보여도 두 계층 사이의 연결 수명 관리나 버퍼 크기 문제일 수 있다"는 방향 전환**이다. Tomcat 지표만 계속 들여다보면 영원히 못 찾는다.

### "Nginx가 504를 반환한 뒤 Tomcat에서 처리 중이던 요청은 어떻게 되나요?"

**그대로 끝까지 실행된다.** 타임아웃은 Nginx의 기다림을 끊을 뿐 Tomcat의 처리를 중단시키지 않는다. 더 정확히 말하면 **Tomcat에는 "처리 시간이 N초를 넘으면 중단"이라는 나사 자체가 없다** — `connectionTimeout`이나 `keepAliveTimeout`은 전부 네트워크에서 무언가를 기다리는 시간이지 로직 실행 시간의 상한이 아니다.

그래서 트랜잭션은 커밋되고, 그 뒤에 응답을 쓰려다 이미 닫힌 소켓을 만나 `ClientAbortException`이 난다. **커밋이 응답 쓰기보다 먼저**라는 순서가 유령 성공의 전부다. 사용자는 실패로 인지하고 재시도하므로 쓰기 요청이면 중복 처리가 된다.

방어는 세 겹으로 말하면 좋다. **(1) 안쪽 상한을 앱이 스스로 만든다** — 외부 호출 타임아웃, `@Transactional(timeout)`, 쿼리 타임아웃. 인프라가 안 해주므로 앱이 해야 한다. **(2) 계층 간 타임아웃을 정렬한다** — 바깥 상한 안에 안쪽 최악 소요가 들어오게. **(3) 멱등성 키를 도입한다** — 타임아웃은 완전히 없앨 수 없으므로 최종 방어선은 애플리케이션 레벨이다. **"타임아웃 뒤 재시도는 멱등성과 세트"라는 원칙이 프록시 계층에도 그대로 적용된다**는 것이 이 질문의 결론이다.

### "업로드가 10MB 근처에서만 실패한다는 제보를 받으면 어떤 순서로 봅니까?"

**크기 의존적 실패는 경로상 어딘가의 크기 한도**이고, 층이 최대 다섯 개(CDN → LB → Nginx → Tomcat → Spring)뿐이므로 이분 탐색으로 두세 번이면 좁혀진다는 것을 먼저 말한다.

**0단계, 경계를 바이트 단위로 확정한다.** "10MB쯤"으로는 판단이 흔들린다. 파일 탐색기의 MB는 1,000,000 기준일 수 있고 서버는 1,048,576 기준으로 재기 때문이다.

**1단계, 실패 응답의 지문을 본다.** 413에 Nginx 기본 에러 페이지면 `client_max_body_size`, 413이나 500에 우리 서비스의 에러 JSON이면 Spring multipart 한도, **연결이 그냥 끊기면 `maxSwallowSize`**를 의심한다. 마지막 것을 알고 있으면 확실히 변별된다.

**2단계, 층을 건너뛰고 직접 때려본다.** Nginx를 건너뛰고 Tomcat 사설 IP:8080으로 같은 파일을 보내서 성공하면 경계는 Nginx 이상에 있고, 실패하면 앱 쪽이다. 이것이 이분 탐색의 본체다.

**3단계, 로그로 확정한다.** Nginx의 `client intended to send too large body: N bytes`에서 **N이 서버가 실제로 본 크기**이므로, 사람이 말한 숫자와 다르면 multipart 오버헤드나 단위 착오가 끼어 있다는 뜻이다.

여기에 **`max-file-size`와 `max-request-size`의 차이**를 덧붙이면 답이 완성된다. 전자는 파일 하나, 후자는 요청 전체(여러 파일 + 폼 필드 + multipart 경계·파트 헤더)이므로, **둘을 같은 값으로 잡으면 정확히 그 크기의 파일 하나가 오버헤드 때문에 후자에 걸린다.** "한도를 10MB로 맞춰놨는데 10MB 파일이 안 올라간다"의 흔한 정답이 이것이다.

근본 대응은 **파일 크기 요구사항이 바뀔 때 전 계층 한도를 함께 바꾸는 체크리스트**다. 한 층만 늘리면 다음 층에서 같은 장애가 반복된다.

### "계층별 타임아웃 값은 어떤 원칙으로 정하나요?" (시니어 변별 포인트)

**규칙이 두 개이고 방향이 서로 반대라는 것을 구분해 말하는 것**이 이 질문의 채점 포인트다.

**첫째, 대기 상한은 바깥이 길어야 한다.** 클라이언트 ≥ CDN ≥ LB ≥ Nginx ≥ 앱의 최악 처리 시간 순이다. 이유는 명확하다 — 안쪽이 아직 일하고 있는데 바깥이 먼저 끊으면 유령 성공이 생기고, 층이 여러 개면 그 사고가 층마다 반복된다.

**둘째, 유휴 연결 수명은 안쪽이 길어야 한다.** 재사용하는 쪽(Nginx)의 유휴 상한이 연결을 들고 있는 쪽(Tomcat)보다 짧아야, 닫는 결정을 재사용하는 쪽이 먼저 내리게 되어 경쟁 조건이 성립하지 않는다.

**두 규칙이 반대인 이유까지 말해야 외운 게 아닌 것으로 들린다.** 대기 상한은 "일이 끝나기를 기다리는 시간"이라 바깥이 더 오래 기다려야 안쪽 일이 완주하고, 유휴 수명은 "쓰지 않는 연결을 들고 있는 시간"이라 재사용하는 쪽이 먼저 정리해야 사고가 안 난다.

**값을 정하는 방법**도 함께 말한다. 감으로 정하는 게 아니라 **안쪽에서 바깥으로 쌓아 올린다** — 외부 호출 타임아웃과 재시도·백오프를 합쳐 최악 소요를 구하고, 스레드 배정 대기와 GC 정지를 감안한 여유를 더해 상위 층 값을 정한다. 동시에 사용자 응답 SLO에서 출발해 바깥에서 안으로 나눠주는 하향식 계산도 해서 **둘이 중간에서 만나는지 검산**한다. 만나지 않으면 타임아웃을 조정할 게 아니라 **그 처리 자체를 바꿔야 한다는 신호**다.

마지막으로 **"Tomcat에는 처리 시간 상한이라는 나사가 없으므로 안쪽 상한은 앱이 스스로 만들어야 한다"**까지 말하면, 설정 표를 외운 게 아니라 구조를 이해한 것으로 들린다.

### "proxy_buffering은 끄는 게 좋은가요, 켜는 게 좋은가요?" (가산점 포인트)

**기본은 켠다.** 버퍼링은 Tomcat의 응답을 Nginx가 빠르게 받아 챙기고 Tomcat 스레드를 즉시 놓아주는 장치이므로, **느린 클라이언트로부터 비싼 WAS 스레드를 격리하는 보호막**이다(12번 문서). 이것을 전역으로 끄면 응답 전송이 클라이언트 속도에 묶여 Tomcat 스레드 점유 시간이 늘고, 모바일 사용자가 많으면 스레드 풀이 고갈된다.

**끄는 것은 즉시성이 필수인 특정 경로에 한해 `location` 단위로 한다.** SSE나 스트리밍 다운로드가 그것이다. 버퍼링이 켜져 있으면 이벤트가 버퍼에 갇혀 "로컬에서는 되는데 배포하면 알림이 안 온다"가 된다.

여기서 한 걸음 더 들어가면 변별이 된다. **버퍼링을 끄는 순간 12번 문서의 보호 효과를 스스로 걷어내는 것**이므로, SSE 경로는 인프라 설정만으로 끝나지 않는다. **SSE는 애초에 서블릿 스레드를 붙들지 않는 비동기 방식(`SseEmitter`, 리액티브 스택)으로 구현해야** 동시 접속자 수가 스레드 풀 크기에 묶이지 않는다. "버퍼링만 끄면 된다"는 답은 절반이다.

그리고 **`X-Accel-Buffering: no` 응답 헤더로 앱이 응답 단위로 선언하는 방법**까지 말하면 인프라와 앱의 협업 방식을 아는 것으로 보인다. `location` 블록을 고치려면 인프라 담당자를 거쳐야 하지만, 이 헤더는 앱 코드만으로 끝난다.

## 한 줄 요약

Nginx와 Tomcat은 서로의 설정값을 모르는 채 각자의 타임아웃·버퍼·크기 한도를 적용하므로, 어긋난 값 사이의 좁은 구간에서만 터지는 유령 현상(504 뒤의 유령 성공과 중복 처리, keep-alive 유휴 경쟁이 만드는 간헐적 502, 특정 크기 근처에서만 실패하는 업로드, 특정 사용자만 502가 나는 큰 응답 헤더)이 생긴다 — 정렬 규칙은 방향이 둘로 갈려서 응답을 기다리는 대기 상한은 바깥 계층이 안쪽보다 길게, 유휴 연결의 수명은 재사용하는 쪽이 닫는 쪽보다 짧게 잡아야 하고, `proxy_read_timeout`이 전체 응답 시간이 아니라 "아무 바이트도 안 오는 구간"의 상한이라는 것과 Tomcat에는 처리 시간 상한이라는 나사가 아예 없다는 것을 알아야 값을 제대로 정할 수 있으며, 무엇이 어긋났는지는 Nginx error log의 문구와 `$upstream_response_time`이 지문처럼 알려준다.
