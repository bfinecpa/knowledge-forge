# 쿠키·세션·토큰 인증 — "상태를 어디에 두고, 무엇으로 실어 나르는가"

> 핵심 관전 포인트: **셋은 같은 층위의 선택지가 아니다. HTTP는 무상태(stateless)라 "이 요청이 누구인지"를 매 요청 다시 증명해야 하는데, 쿠키는 그 증명을 브라우저가 자동으로 실어 나르는 **운반 수단**이고, 세션과 토큰은 인증 상태를 **어디에 두느냐**의 두 방식이다 — 세션은 상태를 서버에 두고 쿠키로는 열쇠(세션 ID)만 나르며, 토큰(JWT)은 상태 자체를 서명해 클라이언트에 들려 보내고 서버는 서명만 검증한다. 그래서 세션은 서버를 늘릴 때 상태 공유가 문제가 되고, 토큰은 서버가 기억하지 않으므로 확장은 쉽지만 즉시 무효화가 어렵다. 쿠키를 쓴다면 `HttpOnly`(XSS 탈취 차단)·`Secure`(평문 전송 차단)·`SameSite`(CSRF 차단) 세 속성이 사실상 필수이고, JWT를 쓴다면 서명은 위조를 막을 뿐 내용을 숨기지 않는다(payload는 누구나 디코딩 가능)는 것이 전제다. 선택은 확장성·탈취 대응·클라이언트 종류(웹/앱)가 얽힌 트레이드오프다.**

---

## 0. 질문 + 의도

**질문**: "쿠키와 세션, 토큰 기반 인증의 차이는?"

**출제 의도**: 인증 방식 선택은 확장성(서버 상태), 보안(탈취 대응), 클라이언트 종류(웹/앱)가 얽힌 실무 결정이다. IAM·인증 기능을 다루는 백엔드의 상시 업무.

## 1. 출발점 — HTTP는 무상태고, 쿠키는 운반 수단이다

### 1-1. 전제 지식 — "무상태"가 정확히 무슨 뜻인가

**무상태(stateless)**는 "서버가 요청과 요청 사이에 아무것도 기억하지 않는다"가 아니라, **HTTP 프로토콜 자체에는 요청을 이어 붙일 장치가 없다**는 뜻이다. 서버는 방금 로그인한 사용자의 다음 요청을, 처음 보는 요청과 프로토콜 차원에서 구분할 방법이 없다.

"TCP 연결이 유지되면 같은 사람 아닌가?"라고 생각하기 쉬운데 그렇지 않다. HTTP/1.1의 keep-alive로 연결이 재사용되더라도, 서버 앞에는 대개 로드밸런서와 리버스 프록시가 있어 연결과 요청이 1:1로 대응하지 않고, 서버가 여러 대면 다음 요청은 다른 서버로 갈 수도 있다. **연결은 신원의 근거가 될 수 없다.**

비유하면 매번 다른 창구 직원을 만나는 은행이다. 직원은 방금 옆 창구에서 무슨 일이 있었는지 모른다. 그래서 **매 요청에 "나는 아까 그 사람"이라는 증표를 직접 들고 가야** 하고, 이 증표를 나르는 대표 수단이 쿠키다.

### 1-2. 쿠키의 동작 — 헤더 두 개와, 브라우저가 대신 해주는 일

쿠키의 프로토콜 자체는 헤더 두 개가 전부다. 서버가 응답에 `Set-Cookie`로 증표를 심어 주면, 브라우저가 이후 요청에 `Cookie` 헤더로 되돌려 보낸다.

```http
# 서버 -> 브라우저: 응답에 증표를 심는다
HTTP/1.1 200 OK
Set-Cookie: SESSION=a1b2c3; Path=/; HttpOnly; Secure; SameSite=Lax

# 브라우저 -> 서버: 이후 같은 도메인의 요청에 자동 첨부
GET /orders HTTP/1.1
Host: app.example.com
Cookie: SESSION=a1b2c3
```

여기서 3년차가 가장 감을 못 잡는 지점은 "그래서 코드로 뭘 해야 하나"다. 답은 **아무것도 안 해도 된다**이다. 브라우저가 개발자 대신 다음을 전부 처리한다.

```
[브라우저가 자동으로 하는 일]

Set-Cookie 응답을 받으면
  ① 쿠키 저장소에 (도메인, 경로, 이름) 단위로 저장한다
  ② Expires/Max-Age가 지나면 스스로 지운다

요청을 보낼 때마다
  ③ 이 요청의 목적지 도메인·경로와 매칭되는 쿠키를 고른다
  ④ Secure면 HTTPS일 때만, SameSite 규칙에 맞을 때만 골라낸다
  ⑤ 고른 것들을 Cookie 헤더 한 줄로 합쳐 붙인다

자바스크립트 코드는 이 과정에 전혀 관여하지 않는다.
```

핵심 성질은 **자동 첨부**다. 이 자동성이 편리함(웹에서 로그인 유지가 공짜)이자 약점이다 — **사용자가 의도하지 않은 요청에도 쿠키가 붙기 때문이다.** 이것이 CSRF의 뿌리이고, 1-4의 `SameSite`가 존재하는 이유다.

### 1-3. 먼저 알아야 할 공격 두 가지 — XSS와 CSRF

쿠키 속성 이야기를 하려면 각 속성이 무엇을 막는지 알아야 하는데, 그러려면 공격 두 개를 먼저 알아야 한다. 이름이 비슷해 헷갈리지만 **완전히 다른 문제**다.

**XSS(Cross-Site Scripting, 교차 사이트 스크립팅)**는 공격자가 심은 자바스크립트가 **우리 사이트의 페이지 안에서** 실행되는 것이다. 게시글 본문에 `<script>`를 넣었는데 그대로 렌더링되는 경우가 전형이다. 이 스크립트는 우리 출처의 코드로 취급되므로 `document.cookie`를 읽고 `localStorage`를 뒤질 수 있다. **훔쳐 가는 공격**이다.

**CSRF(Cross-Site Request Forgery, 교차 사이트 요청 위조)**는 반대다. 공격자 사이트(`evil.com`)가 방문자의 브라우저를 시켜 **우리 사이트로 요청을 보내게** 만든다. 브라우저는 목적지가 우리 도메인이니 쿠키를 자동으로 붙인다. 공격자는 응답을 읽지 못하지만 **부수효과(송금, 비밀번호 변경, 탈퇴)는 이미 일어난다.** 훔치는 게 아니라 **시키는 공격**이다.

```
[XSS]   evil 스크립트가 우리 페이지 안에서 실행됨
        -> document.cookie 읽기, 토큰 유출        (기밀성 침해)

[CSRF]  evil.com의 <form>이 우리 서버로 POST
        -> 브라우저가 쿠키를 자동 첨부 -> 서버는 정상 요청으로 처리
        -> 응답은 못 읽지만 이체는 완료됨           (무결성 침해)
```

이 구분을 잡아두면 다음 절의 속성들이 "각각 어느 쪽을 막는 장치인가"로 정리된다.

### 1-4. 쿠키 속성 — 각각이 어떤 공격을 막는가

`Set-Cookie` 예시에 줄줄이 붙는 속성들은 장식이 아니다. 하나씩 **무엇을 막으려고 존재하는지** 보자.

**`HttpOnly` — XSS로 쿠키가 통째로 털리는 것을 막는다.** 이 속성이 붙은 쿠키는 자바스크립트의 `document.cookie`에서 아예 보이지 않는다. 브라우저가 HTTP 전송 경로에만 쓰고 스크립트에는 넘겨주지 않는다는 뜻이고, 이름의 "HTTP only"가 그 의미다. XSS가 터져도 공격 스크립트가 세션 ID를 읽어 자기 서버로 전송할 수 없다.

주의할 것은 이것이 XSS의 **완전한 방어가 아니라 피해 축소**라는 점이다. 쿠키를 못 읽더라도 공격 스크립트는 그 페이지 안에서 `fetch('/api/transfer', ...)`를 호출할 수 있고, 그때도 쿠키는 브라우저가 자동으로 붙여 준다. **훔쳐 가서 다른 곳에서 쓰는 것**은 막지만 **그 자리에서 사용하는 것**은 못 막는다.

**`Secure` — 평문(HTTP) 전송을 막는다.** 이 속성이 붙으면 브라우저는 HTTPS 요청에만 쿠키를 첨부한다. 없으면 어떤 일이 생기는가. 사용자가 주소창에 `http://`로 한 번만 접속해도 세션 ID가 평문으로 네트워크에 흘러 나가고, 공용 와이파이의 같은 망에 있는 누구든 패킷을 떠서 그대로 재사용할 수 있다. 로그인 페이지만 HTTPS로 만들고 나머지를 HTTP로 두는 구성이 위험한 이유가 이것이다 — 비밀번호는 안전해도 **그 결과로 받은 세션 ID가 평문으로 돌아다닌다.**

**`SameSite` — CSRF를 막는다.** 이 속성은 "다른 사이트에서 시작된 요청에도 이 쿠키를 붙일 것인가"를 결정한다. 값은 셋이다.

| 값 | 언제 쿠키를 붙이는가 | 대가 |
|---|---|---|
| `Strict` | 같은 사이트에서 시작된 요청에만 | 외부 링크로 우리 사이트에 들어오면 첫 요청에 쿠키가 안 붙어 비로그인 화면이 보인다 |
| `Lax` | 같은 사이트 요청 + **최상위 화면 이동(링크 클릭 등)의 GET** | 교차 사이트 POST·`fetch`·`iframe`·`img`에는 안 붙는다 |
| `None` | 교차 사이트라도 항상 붙인다 | CSRF 방어가 사라지므로 `Secure` 필수 + 별도 CSRF 대책 필요 |

`Lax`가 기본값으로 자리 잡은 이유는 **공격 유형과 정상 사용을 실용적으로 가른 선**이기 때문이다. CSRF의 주력은 상태를 바꾸는 POST·PUT·DELETE인데 `Lax`는 그것들을 전부 차단한다. 반면 "카카오톡으로 받은 링크를 눌러 우리 사이트에 들어오는" 최상위 GET 이동은 정상 사용이므로 허용한다. 검색 결과에서 들어와도 로그인이 유지되는 것은 이 예외 덕분이다.

**`SameSite=None`을 쓰려면 왜 `Secure`가 반드시 필요한가.** `None`은 "어떤 사이트에서 시작된 요청에도 이 쿠키를 실어 보내라"는 선언이다. 즉 이 쿠키는 우리가 통제하지 못하는 온갖 페이지에서, 우리가 모르는 타이밍에 네트워크로 나간다. **노출 기회가 구조적으로 가장 많은 쿠키**라는 뜻이다. 그런 쿠키가 평문 HTTP로도 나갈 수 있다면 스니핑 위험이 폭증하므로, 브라우저는 아예 규칙으로 못을 박았다 — **`SameSite=None`인데 `Secure`가 없으면 그 쿠키는 저장 자체가 거부된다.**

이 조합이 실무에서 부딪히는 자리가 있다. 프론트가 `https://app.example.com`, API가 `https://api.example.com`처럼 **다른 출처**여서 브라우저가 교차 사이트로 판정하는 구조라면, 쿠키 세션을 유지하려면 `SameSite=None; Secure`가 필요하다. 그리고 이때 서버 쪽에는 CORS의 자격증명 허용 설정이 짝으로 따라온다(같은 장 `08-cors-and-preflight.md`의 자격증명 절과 이어지는 주제다).

```http
# 교차 출처 구조에서 쿠키 세션을 유지하려면 이 조합이 강제된다
Set-Cookie: SESSION=a1b2c3; Path=/; HttpOnly; Secure; SameSite=None
```

`SameSite=None`을 켜는 순간 CSRF 방어를 스스로 껐다는 사실도 함께 인식해야 한다. 이 경우 CSRF 토큰이나 커스텀 헤더 검증 같은 별도 장치를 반드시 얹는다.

**`Domain` — 쿠키가 어느 호스트까지 따라갈지 정한다.** 지정하지 않으면 쿠키를 내려준 그 호스트에만 붙는다(호스트 한정). `Domain=example.com`처럼 상위 도메인을 지정하면 `api.example.com`, `blog.example.com`, `admin.example.com` 등 **모든 서브도메인 요청에 붙는다.**

편해 보이지만 이것이 곧 공격면이다. 마케팅팀이 운영하는 `event.example.com` 하나에 XSS가 터지면, 그 페이지에서 실행된 스크립트가 우리 서비스의 세션 쿠키를 함께 다룰 수 있는 위치에 서게 된다. **쿠키의 범위는 신뢰 경계와 같아야 한다** — 서브도메인 전체를 같은 수준으로 신뢰할 수 없다면 `Domain`을 넓히지 않는 것이 원칙이다. (참고로 아무 도메인이나 지정할 수는 없다. 브라우저는 `Domain=com`처럼 공용 접미사에 쿠키를 심는 시도를 거부한다.)

**`Path` — 경로 범위를 좁힌다.** `Path=/admin`이면 `/admin` 이하 요청에만 붙는다. 다만 이것은 **보안 경계가 아니다.** 같은 출처 안의 스크립트라면 숨겨진 `iframe`을 만드는 등의 방법으로 다른 경로의 쿠키에 접근할 여지가 있다. 전송량을 줄이는 정리 수단으로 보고, 격리를 기대하지는 않는 것이 맞다.

**`Max-Age` / `Expires` — 수명을 정한다.** 둘 다 없으면 **세션 쿠키**가 되어 브라우저를 닫으면 사라진다(브라우저의 세션 복원 기능 때문에 실제로는 살아남기도 한다). 값을 주면 **영속 쿠키**가 되어 디스크에 저장되고 재부팅 후에도 남는다. "로그인 상태 유지" 체크박스가 이 둘을 가르는 스위치다.

Spring에서 이 속성들을 붙이는 코드는 이렇게 대비된다.

```java
// Before: 속성 없이 쿠키를 심는다 — 세 가지 방어가 전부 빠져 있다
@PostMapping("/login")
public void login(HttpServletResponse response, LoginRequest req) {
    String sessionId = sessionService.create(authenticate(req));
    Cookie cookie = new Cookie("SESSION", sessionId);
    cookie.setPath("/");
    response.addCookie(cookie);
    // XSS 한 방이면 document.cookie로 통째로 유출된다 (HttpOnly 없음)
    // http로 접속하면 평문으로 흘러 나간다 (Secure 없음)
    // evil.com의 폼 POST에도 자동 첨부된다 (SameSite 없음)
}

// After: 무엇을 막는 속성인지 알고 붙인다
@PostMapping("/login")
public void login(HttpServletResponse response, LoginRequest req) {
    String sessionId = sessionService.create(authenticate(req));
    ResponseCookie cookie = ResponseCookie.from("SESSION", sessionId)
            .httpOnly(true)      // 스크립트가 못 읽음 -> XSS로 통째 탈취 차단
            .secure(true)        // HTTPS에서만 전송 -> 평문 스니핑 차단
            .sameSite("Lax")     // 교차 사이트 POST에 안 붙음 -> CSRF 차단
            .path("/")
            .maxAge(Duration.ofHours(2))  // 없으면 브라우저 종료 시 소멸
            .build();
    // ResponseCookie를 쓰는 이유: 서블릿 Cookie 클래스에는 SameSite를
    // 직접 설정하는 API가 없어 헤더를 문자열로 조립해야 한다.
    response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());
}
```

여기까지가 쿠키의 역할이다. 쿠키는 **증표를 나르는 봉투**일 뿐이고, **"봉투 안에 무엇이 들었는가"부터가 세션과 토큰의 갈림길**이다.

## 2. 세션 vs 토큰 — 상태를 서버에 두느냐, 들려 보내느냐

### 2-1. 왜 "쿠키 vs 세션 vs 토큰"이 잘못된 비교인가

이 질문에 셋을 나란히 비교해 답하면 층위가 꼬인다. 쿠키는 **운반 수단**이고, 세션과 토큰은 **상태를 어디에 두느냐**의 답이다. 축이 둘이라는 것을 먼저 말하고 시작하는 것이 정리된 답변이다.

```
                        [운반 수단]
                  쿠키               Authorization 헤더
                  (브라우저 자동)      (클라이언트 코드가 수동)
              +--------------------+----------------------+
  [상태 위치] |                    |                      |
              |                    |                      |
   서버에 둠  |  세션 ID 쿠키       |  세션 ID를 헤더로     |
   (세션)     |  (웹의 기본형)      |  (드물지만 가능)      |
              +--------------------+----------------------+
              |                    |                      |
 클라이언트에 |  JWT를 HttpOnly     |  JWT를 Bearer 헤더로  |
 들려 보냄    |  쿠키에 담기         |  (앱·SPA의 기본형)    |
   (토큰)     |  (XSS 방어 유리)     |                      |
              +--------------------+----------------------+
```

네 칸이 전부 실재한다는 점이 중요하다. "세션=쿠키, 토큰=헤더"는 흔한 관행이지 규칙이 아니다. **저장 위치와 운반 수단이 독립적인 축임을 아는 것**이 이 질문의 변별점이다.

### 2-2. 세션 — 상태는 서버에, 클라이언트에는 열쇠만

로그인이 성공하면 서버가 사용자 정보를 자기 저장소(톰캣 메모리, Redis 등)에 넣고, 그 항목을 가리키는 **무작위 식별자(세션 ID)**만 쿠키로 내려준다.

```
[로그인]
  브라우저 --POST /login (id, pw)--> 서버
                                      |
                                      | 저장소에 기록
                                      v
                              session:a1b2c3 -> { userId: 42, role: USER }
                                      |
  브라우저 <--Set-Cookie: SESSION=a1b2c3--+

[이후 요청]
  브라우저 --GET /orders  Cookie: SESSION=a1b2c3--> 서버
                                                     |
                                        저장소 조회 -> userId 42로 처리
```

비유하면 **물품보관함 번호표**다. 번호표(세션 ID)에는 아무 정보도 없다. 누가 번호표를 주워도 물건은 보관함(서버)에 있고, 관리인이 번호표를 무효 처리하면 그 순간부터 아무 소용이 없다.

이 구조의 강점은 **서버가 상태의 주인**이라는 데서 전부 파생된다. 로그아웃, 관리자에 의한 강제 로그아웃, 비밀번호 변경 후 전 기기 로그아웃, 권한 변경 즉시 반영이 **저장소에서 지우거나 고치는 것으로 끝난다.** 사용자별 활성 세션 목록을 들고 있으면 "다른 기기 모두 로그아웃"도 자연스럽게 구현된다.

대가는 둘이다. 첫째, **모든 요청이 저장소 조회를 거친다.** 초당 1만 요청이면 초당 1만 번의 조회다. 둘째, 서버가 여러 대로 늘어나면 "2번 서버에 저장된 세션을 3번 서버가 어떻게 아나"라는 **상태 공유 문제**가 생긴다(3절의 실무 사례).

한 가지 더 알아둘 것이 **세션 고정 공격(session fixation)**이다. 공격자가 자기가 아는 세션 ID를 피해자 브라우저에 미리 심어 놓고, 피해자가 그 ID로 로그인하기를 기다리는 공격이다. 로그인 전후로 같은 세션 ID를 계속 쓰면 성립한다. 방어는 간단하다 — **인증에 성공한 시점에 세션 ID를 새로 발급**하면 공격자가 아는 ID는 무효가 된다. Spring Security는 이 처리를 기본으로 수행하므로, 직접 세션을 다루는 코드를 짤 때만 신경 쓰면 된다.

### 2-3. 토큰(JWT) — 상태를 서명해서 들려 보낸다

로그인이 성공하면 서버가 사용자 정보(사용자 ID, 권한, 만료시각)를 담은 데이터에 **서버만 아는 키로 서명**해 통째로 내려준다. 이후 요청마다 클라이언트가 이 토큰을 붙이면, 서버는 저장소 조회 없이 **서명 검증만으로** "내가 발급했고 위조되지 않은 증표"임을 확인한다.

비유하면 **신분증**이다. 번호표와 달리 신분증에는 내용(이름, 생년월일)이 적혀 있고, 위조 방지 장치(홀로그램 = 서명)가 함께 붙어 있다. 발급 기관에 전화해 확인할 필요 없이 그 자리에서 검증된다.

#### JWT의 구조 — 점 두 개로 나뉜 세 조각

JWT(JSON Web Token)는 점(`.`) 두 개로 나뉜 문자열이다. 각 조각은 **Base64URL**로 인코딩돼 있다. Base64URL은 임의의 바이트를 URL·헤더에 안전한 문자만으로 표현하는 인코딩으로, `+`와 `/` 대신 `-`와 `_`를 쓰는 Base64 변형이다.

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiI0MiIsInJvbGUi... . dBjftJeZ4CVP...
+----------------------------------+   +----------------------+   +--------------+
             header                            payload              signature
       (어떤 알고리즘으로              (누구인지, 무엇을 할 수         (앞의 두 조각을
        서명했는지)                     있는지, 언제까지)              서명한 값)

[header 디코딩]   {"alg":"HS256","typ":"JWT"}
[payload 디코딩]  {"sub":"42","role":"USER","iat":1735689600,"exp":1735693200}
                   sub = subject, 이 토큰의 주체(사용자 ID)
                   iat = issued at, 발급 시각 (유닉스 초)
                   exp = expiration, 만료 시각 (유닉스 초)
                   위 값은 2025-01-01 00:00 발급 / 01:00 만료를 뜻한다

[signature]  HMAC-SHA256( base64url(header) + "." + base64url(payload), 서버의 비밀키 )
```

#### 반드시 짚어야 할 오해 — 서명은 위조를 막을 뿐, 내용을 숨기지 않는다

3년차가 가장 자주 오해하는 지점이다. **JWT는 암호화가 아니다.** payload는 Base64URL로 "인코딩"돼 있을 뿐이고, 인코딩은 비밀이 필요 없는 표현 변환이다. 토큰 문자열을 손에 넣은 사람은 누구나 한 줄로 내용을 읽는다.

```bash
# 서버의 비밀키 없이, 브라우저 개발자도구나 셸 한 줄이면 내용이 그대로 보인다.
# JWT는 Base64URL 패딩('=')을 떼고 쓰므로, 길이가 4의 배수가 아니면 '='을 붙여 준다.
# (아래 payload는 마침 80자라 그대로 디코딩된다.)
$ echo 'eyJzdWIiOiI0MiIsInJvbGUiOiJVU0VSIiwiaWF0IjoxNzM1Njg5NjAwLCJleHAiOjE3MzU2OTMyMDB9' | base64 -d
{"sub":"42","role":"USER","iat":1735689600,"exp":1735693200}
```

그래서 payload에 넣으면 안 되는 것이 분명하다 — 주민등록번호, 전화번호, 이메일, 내부 시스템의 상세 권한 구조 같은 것은 넣지 않는다. **넣어도 되는 것은 "노출돼도 그 자체로는 해가 없는 식별자"**다.

그렇다면 서명은 무엇을 하는가. **위조와 변조를 막는다.** 공격자가 payload의 `"role":"USER"`를 `"role":"ADMIN"`으로 바꿔 다시 Base64URL로 인코딩하는 것까지는 자유다. 하지만 서명은 서버의 비밀키가 있어야 다시 계산할 수 있으므로, 바뀐 payload에 맞는 서명을 만들어낼 수 없다. 서버는 검증 단계에서 이 불일치를 잡아낸다.

정리하면 이렇다.

| | 보장하는가 | 왜 |
|---|---|---|
| 내용 기밀성(남이 못 읽음) | 보장하지 않음 | Base64URL은 암호가 아니라 인코딩이다 |
| 무결성(내용 변조 탐지) | 보장함 | 비밀키 없이는 서명을 다시 만들 수 없다 |
| 진위(내가 발급한 것인가) | 보장함 | 서명을 검증할 수 있는 것은 발급자뿐이다 |
| 유출 후 무효화 | 보장하지 않음 | 서버가 발급 사실을 기억하지 않기 때문이다 |

#### 검증에서 자주 무너지는 지점

서명 검증 코드에서 실수하면 서명이 있어도 의미가 없어진다. 대표적인 것이 **알고리즘을 토큰이 시키는 대로 따르는 것**이다. header의 `alg`는 **공격자가 조작할 수 있는 값**인데, 라이브러리에 그대로 넘기면 `alg`를 `none`(서명 없음)으로 바꾼 토큰이나, 공개키 방식(RS256)을 대칭키 방식(HS256)으로 뒤바꿔 공개키를 비밀키처럼 쓰게 만드는 토큰에 속을 수 있다.

```java
// Before: 토큰이 주장하는 알고리즘을 그대로 믿는다
Claims claims = Jwts.parser()
        .setSigningKey(secretKey)   // alg는 토큰 header에 적힌 대로 따라간다
        .parseClaimsJws(token)
        .getBody();

// After: 서버가 알고리즘을 못 박고, 만료·발급자까지 검증한다
Claims claims = Jwts.parser()
        .verifyWith(secretKey)
        .sig().add(Jwts.SIG.HS256).and()  // HS256만 허용 — alg 조작을 원천 차단
        .requireIssuer("https://auth.example.com") // 다른 시스템의 토큰 유입 차단
        .build()
        .parseSignedClaims(token)   // 서명 불일치·만료면 여기서 예외
        .getPayload();
```

`exp` 검증을 빼먹지 않는 것도 중요하다. 만료시각은 payload에 적혀 있을 뿐이므로, **서버가 확인하지 않으면 만료된 토큰이 영원히 통과한다.** 다행히 표준 라이브러리는 파싱 단계에서 `exp`를 함께 검사하지만, 직접 구현하거나 검증을 우회하는 코드를 짜면 그 순간 구멍이 된다.

#### 토큰 방식의 진짜 대가

서버가 아무것도 기억하지 않으므로 **무상태 확장이 쉽다.** 서버를 몇 대로 늘려도, 심지어 다른 서비스·다른 도메인·모바일 앱이 호출해도 서명 검증 키만 있으면 된다.

그 대가가 **발급한 뒤에는 회수할 수 없다**는 것이다. 서버는 그 토큰이 존재한다는 사실조차 모르므로 지울 대상이 없다. 로그아웃을 눌러도 그것은 클라이언트가 자기 저장소에서 토큰을 버리는 행동일 뿐, **탈취당한 복사본은 만료시각까지 그대로 유효하다.** 이 한계가 토큰 방식의 아킬레스건이고, 3-5절과 꼬리질문에서 다시 다룬다.

### 2-4. 운반 수단의 차이가 공격면을 가른다

같은 증표라도 쿠키로 나르느냐 `Authorization` 헤더로 나르느냐에 따라 노출되는 공격이 달라진다. 앞에서 설명한 내용을 짧게 대조하면 이렇다.

| | 쿠키로 운반 | `Authorization` 헤더로 운반 |
|---|---|---|
| 첨부 방식 | 브라우저가 자동 | 클라이언트 코드가 수동 |
| CSRF | 취약(자동 첨부가 원인) — `SameSite`·CSRF 토큰 필요 | 강함(공격자 사이트는 남의 요청에 헤더를 못 붙인다) |
| XSS로 탈취 | `HttpOnly`면 스크립트가 못 읽음 | JS가 접근 가능한 곳에 두면 그대로 유출 |
| 교차 도메인·모바일 앱 | 도메인 규칙에 묶여 설정이 늘어남 | 자유로움 |

```http
# 토큰 방식의 전형적 요청 — 코드가 직접 헤더를 붙인다
GET /orders HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI0MiJ9.dBjftJeZ...
```

`Bearer`는 "소지자"라는 뜻이다. **가진 사람이 곧 권한자**라는 이 방식의 성격을 이름이 그대로 드러낸다 — 그래서 유출 자체가 곧 침해이고, 전송 구간 보호(HTTPS)와 짧은 수명이 필수 조건이 된다.

CSRF에 대해 헤더 방식이 강한 이유도 한 문장으로 정리해 두자. **공격자 사이트가 만드는 요청에는 공격자가 헤더를 넣을 수 없기 때문**이 아니라, 정확히는 **브라우저가 자동으로 붙여주지 않기 때문**이다. `<form>` 제출이나 `<img>` 로드에 커스텀 헤더를 넣을 방법이 없고, 스크립트로 `fetch`를 호출해 헤더를 붙이더라도 응답을 읽으려면 CORS 허가가 필요하다.

## 3. 실무 사례 — 서버를 늘렸더니 로그인이 풀린다

### 3-1. 증상과 원인

세션을 톰캣 로컬 메모리에 두는 기본 구성은 서버가 1대일 때만 성립한다. 트래픽이 늘어 scale-out으로 2대가 되고 로드밸런서가 요청을 번갈아 보내는 순간, 문제가 시작된다.

```
t0  사용자 로그인 -> LB가 서버 A로 라우팅
                    서버 A 메모리: session:a1b2c3 -> userId 42
                    Set-Cookie: SESSION=a1b2c3

t1  사용자가 /orders 클릭 -> LB가 서버 B로 라우팅
                    Cookie: SESSION=a1b2c3
                    서버 B 메모리: (비어 있음)
                    -> "세션 없음" -> 302 로그인 페이지

t2  사용자가 다시 로그인 -> 이번엔 서버 A -> 정상 동작
```

증상은 **간헐적으로 로그인이 풀린다**이다. 재현이 안 돼 한참 헤매는 전형적인 장애다. 로그를 봐도 각 서버는 자기 기준으로 정상 동작했으므로 에러가 없다. 배포 때마다(=인스턴스가 교체될 때마다) 전 사용자가 로그아웃되는 현상도 같은 뿌리다.

원인은 한 문장이다. **상태를 각 서버가 각자 기억하고 있었다.**

```java
// Before: 로컬 메모리 세션 — 인스턴스마다 각자 기억하므로 확장 시 깨진다
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("userId", authenticate(req)); // 이 서버의 힙에만 존재
}
```

선택지는 셋이다. **어느 것도 공짜가 아니고, 각각 무엇을 포기하는지가 이 질문의 트레이드오프다.**

### 3-2. 선택지 ① 스티키 세션 — 같은 사용자를 같은 서버로 고정

**스티키 세션(sticky session)**은 로드밸런서가 "이 사용자는 서버 A"라고 기록해 두고 이후 요청을 계속 A로 보내는 방식이다. 세션 어피니티(session affinity, 친화성)라고도 부른다. 붙여 놓는다는 뜻에서 "스티키"다. 구현은 LB가 자기 쿠키를 하나 더 심거나, 클라이언트 IP를 해시해 서버를 고르는 식이다.

```nginx
# nginx에서 IP 해시로 고정하는 예 — 애플리케이션 코드 변경이 전혀 없다
upstream backend {
    ip_hash;                 # 같은 클라이언트 IP는 항상 같은 업스트림으로
    server app-a:8080;
    server app-b:8080;
}
```

**얻는 것**: 애플리케이션을 한 줄도 고치지 않고 당장 증상이 사라진다. 급한 불을 끌 때의 가치가 크다.

**포기하는 것**은 셋이다. 첫째, **부하가 고르게 안 퍼진다.** 무거운 사용자가 몰린 서버는 계속 무겁다. 둘째, **그 서버가 죽으면 거기 붙어 있던 사용자들의 세션이 통째로 사라진다.** 배포 때마다 일부 사용자가 로그아웃되는 것도 그대로 남는다. 셋째, **스케일 아웃의 효과가 반감된다.** 서버를 새로 붙여도 기존 사용자는 옮겨오지 않아 새 서버는 한동안 놀고, 기존 서버는 계속 붐빈다.

정리하면 스티키 세션은 **"서버는 여전히 상태를 갖고 있다"는 사실을 감춘 것**이지 해결한 것이 아니다.

### 3-3. 선택지 ② 세션 저장소 외부화 — 상태를 서버 밖으로 옮긴다

**세션을 애플리케이션 프로세스 밖의 공용 저장소(주로 Redis)에 두는** 방식이다. 서버는 요청마다 그 저장소에서 세션을 읽어 오므로, 어느 서버가 받아도 같은 세션을 본다.

```
        [LB]
       /    \
  [서버 A]  [서버 B]      -> 둘 다 상태를 갖지 않는다
       \    /
      [Redis]  session:a1b2c3 -> { userId: 42 }   <- 상태는 여기 한 곳
```

Spring에서는 Spring Session이 이 교체를 대신해 준다. 핵심은 **애플리케이션 코드가 그대로라는 것**이다. `HttpSession` 인터페이스는 유지한 채 구현체만 Redis 기반으로 바뀐다.

```groovy
// build.gradle — 의존성 추가만으로 HttpSession 구현이 교체된다
implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.springframework.session:spring-session-data-redis'
```

```yaml
# application.yml
spring:
  session:
    store-type: redis
    timeout: 30m          # 세션 만료 — Redis 키의 TTL로 관리된다
  data:
    redis:
      host: session-redis.internal
      port: 6379
```

```java
// After: 코드는 Before와 한 글자도 다르지 않다. 저장 위치만 바뀌었다.
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("userId", authenticate(req)); // Redis에 저장, 전 서버 공유
}
```

**얻는 것**: 서버가 무상태에 가까워져 자유롭게 늘리고 줄일 수 있고, 배포해도 로그인이 유지된다. 그러면서도 **즉시 무효화라는 세션의 강점은 그대로 남는다** — Redis에서 키를 지우면 그 순간 로그아웃이다.

**포기하는 것**: Redis가 **전 요청의 의존점**이 된다. Redis가 죽으면 모든 사용자가 동시에 로그아웃되고, Redis 지연이 곧 전체 API 지연이 된다. 그래서 이 선택은 "Redis를 붙인다"로 끝나지 않고 **가용성 설계(Sentinel이나 Cluster 구성, 장애 시 동작 정의)까지 포함한 결정**이다.

실무에서 자주 밟는 함정도 몇 개 있다. 세션에 넣는 객체는 직렬화돼 Redis로 나가므로 `Serializable`이어야 하고(JSON 직렬화로 바꾸면 이 제약은 풀리지만 타입 정보 설정이 필요하다), 세션에 큰 객체를 담으면 매 요청마다 그만큼을 직렬화·역직렬화하며 왕복시키게 된다. **세션에는 식별자 수준의 작은 값만 담는다**는 원칙이 여기서 나온다.

### 3-4. 선택지 ③ 토큰 — 상태 자체를 없앤다

세 번째는 서버가 세션을 갖지 않도록 방식을 바꾸는 것이다.

```java
// After(방법 3): 토큰 발급 — 서버는 어떤 상태도 보관하지 않는다
@PostMapping("/login")
public TokenResponse login(LoginRequest req) {
    Long userId = authenticate(req);
    // 서명된 토큰을 클라이언트가 보관하고, 서버는 검증만 한다.
    // 서버 어디에도 "이 토큰을 발급했다"는 기록이 남지 않는다.
    return new TokenResponse(jwtProvider.issue(userId));
}
```

**얻는 것**: 세션 저장소라는 의존점이 사라진다. 서버 간 호출이 잦은 MSA에서 매 홉마다 세션 조회를 하지 않아도 되고, 모바일 앱이나 외부 파트너 API처럼 쿠키를 쓰기 어려운 클라이언트도 같은 방식으로 인증된다.

**포기하는 것**: 즉시 무효화다. 그리고 이것은 "포기하고 끝"이 아니라 **다음 절의 숙제로 이어진다.**

세 선택지를 한 표로 대조하면 이렇다.

| | 스티키 세션 | 세션 저장소 외부화 | 토큰 |
|---|---|---|---|
| 코드 변경 | 없음(LB 설정만) | 거의 없음(의존성·설정) | 인증 계층 전면 수정 |
| 서버 무상태 | 아니다(감춘 것) | 그렇다 | 그렇다 |
| 즉시 무효화 | 가능 | 가능 | 어렵다(별도 장치 필요) |
| 새 의존점 | 없음 | Redis(전 요청 경로) | 없음 |
| 인스턴스 장애 시 | 그 서버 사용자만 로그아웃 | 영향 없음 | 영향 없음 |

### 3-5. 토큰을 택하면 따라오는 숙제 — 짧은 수명과 refresh 회전

토큰의 즉시 무효화 문제를 정면으로 푸는 방법은 없다. 대신 실무는 **피해가 지속되는 시간을 줄이는** 쪽으로 설계한다. 그 장치가 access token과 refresh token의 분리다.

한 장짜리 토큰은 **"탈취 시 악용되는 시간"과 "사용자의 재로그인 빈도"가 한 값에 묶인다.** 수명을 길게 하면 탈취당했을 때 오래 악용되고, 짧게 하면 사용자가 하루에도 몇 번씩 다시 로그인해야 한다. 둘로 나누면 이 결합이 풀린다.

- **access token**: 매 요청에 실려 다녀 노출 빈도가 높다. 그래서 수명을 짧게(분 단위) 둔다. 탈취되더라도 곧 만료된다.
- **refresh token**: 재발급할 때만 전송되므로 노출이 적다. 수명을 길게(일 단위) 두는 대신 **서버 저장소에 기록해 통제 지점으로 삼는다.**

여기서 **refresh token 회전(rotation)**이 등장한다. 재발급 요청이 올 때마다 **새 refresh token을 함께 내려주고 쓰던 것은 즉시 폐기**하는 방식이다. 회전이 없으면 refresh token 하나가 만료일까지 계속 유효해 탈취 시 피해가 길어지지만, 회전을 걸면 한 토큰은 **딱 한 번만 쓸 수 있는 일회용**이 된다.

회전의 진짜 값은 **재사용 탐지(reuse detection)**에서 나온다. 이미 사용돼 폐기된 refresh token이 다시 들어왔다면, 그것은 **누군가 복사본을 갖고 있다는 증거**다. 정상 클라이언트는 새 토큰으로 이미 갈아탔으므로 옛 토큰을 다시 쓸 이유가 없기 때문이다.

```
[정상 흐름]
  RT1 사용 -> RT1 폐기, RT2 발급
  RT2 사용 -> RT2 폐기, RT3 발급

[탈취 발생]
  공격자가 RT2를 복사해 감
  사용자: RT2 사용 -> RT2 폐기, RT3 발급
  공격자: RT2 사용 -> ★ 이미 폐기된 토큰이 다시 들어왔다
                     -> 탈취로 판단 -> 해당 사용자의 토큰 계열 전체 무효화
                     -> 사용자·공격자 모두 재로그인 필요(사용자는 불편, 공격은 차단)
```

"사용자까지 로그아웃되는 게 맞나" 싶겠지만 맞다. 어느 쪽이 진짜 사용자인지 서버는 알 수 없으므로, **둘 다 끊고 자격 증명부터 다시 받는 것**이 유일하게 안전한 선택이다.

```java
// Before: refresh token이 만료 전까지 계속 재사용된다
@PostMapping("/reissue")
public TokenResponse reissue(@RequestBody String refreshToken) {
    Long userId = jwtProvider.parseRefresh(refreshToken).userId();
    return new TokenResponse(jwtProvider.issueAccess(userId));
    // 서버는 이 refresh token이 몇 번 쓰였는지 모른다.
    // 탈취되면 만료일까지 무한히 access token을 찍어낼 수 있다.
}

// After: 회전 + 재사용 탐지
@Transactional
@PostMapping("/reissue")
public TokenResponse reissue(@RequestBody String refreshToken) {
    RefreshRecord record = refreshRepository.findByToken(refreshToken)
            .orElseThrow(() -> new UnauthorizedException("unknown refresh token"));

    // 이미 사용돼 폐기된 토큰이 다시 왔다 = 복사본이 돌아다닌다는 신호.
    // 개별 요청만 거절하면 공격자가 계속 시도하므로, 계열 전체를 끊는다.
    if (record.isUsed()) {
        refreshRepository.revokeAllByUserId(record.userId());
        alertService.notifyTokenReuse(record.userId());
        throw new UnauthorizedException("refresh token reuse detected");
    }

    record.markUsed();  // 한 번 쓴 refresh token은 즉시 일회용으로 소진시킨다
    String newRefresh = jwtProvider.issueRefresh(record.userId());
    refreshRepository.save(RefreshRecord.of(record.userId(), newRefresh));

    return new TokenResponse(jwtProvider.issueAccess(record.userId()), newRefresh);
}
```

여기서 놓치면 안 되는 사실이 있다. **이 코드는 `refreshRepository`라는 서버 저장소를 쓰고 있다.** 즉 토큰을 택해 없앤 줄 알았던 서버 상태가, 무효화 요구를 만나 다시 돌아왔다. 이 되돌아옴이 다음 꼬리질문의 핵심이다.

## 4. 꼬리질문 대비 포인트

### "JWT를 쓰면 세션 저장소가 정말 필요 없어지나요?" (시니어 변별 포인트)

이론상은 그렇다. 하지만 **실무 요구가 상태를 다시 불러온다.**

돌아보면 요구는 전부 같은 모양이다. 로그아웃한 토큰 즉시 차단, 비밀번호 변경·계정 탈취 시 강제 만료, 관리자의 강제 로그아웃, 권한 변경 즉시 반영 — 전부 **"이미 발급된 토큰을 회수"**해야 하는데, 무상태 토큰에는 회수 대상이 없다.

대응은 셋이고, 각각 무엇을 치르는지가 답변의 핵심이다.

**① access token을 짧게 하고 refresh로 재발급한다.** 무효화가 아니라 **피해 시간창을 줄이는 완화**다. "로그아웃 후 최대 5분간은 탈취된 access token이 유효하다"를 받아들이는 것이다. 무상태는 완전히 유지된다.

**② refresh token을 서버 저장소에 두고 그것을 무효화 지점으로 삼는다(3-5절).** 강제 로그아웃은 refresh 레코드를 지우는 것으로 구현되고, 그 뒤로는 재발급이 막히므로 access token 수명이 다하면 끝난다. 대신 **재발급 경로에는 상태가 생긴다.** 실무에서 가장 흔한 절충이다.

**③ 차단 목록(blacklist)을 두고 매 요청 조회한다.** 즉시 차단이 가능해지지만, **매 요청 저장소 조회가 되살아나므로 토큰을 택한 이유(무상태)가 상당 부분 사라진다.** 다만 차단 목록은 활성 세션 전체가 아니라 "차단된 것만" 담고 만료된 항목은 TTL로 사라지므로, 세션 저장소보다 훨씬 작고 가볍다는 반론도 함께 말하면 좋다.

결론은 이렇게 정리한다. **완전한 무상태는 "즉시 무효화 포기"와 교환한 것**이고, 실제 시스템은 대부분 절충형 — **짧은 무상태 access + 상태 있는 refresh** — 을 쓴다. "JWT를 쓰면 서버가 가벼워집니다"에서 멈추지 않고 **어디에 상태가 되돌아오는지, 그것이 왜 받아들일 만한지**까지 말하면 설계 경험이 드러난다.

### "access token과 refresh token은 왜 나누나요?"

한 장짜리 토큰은 **탈취 피해 시간과 재로그인 빈도가 한 값에 묶여** 있어, 어느 쪽을 개선해도 다른 쪽이 나빠진다. 둘로 나누면 이 결합이 끊어진다.

매 요청에 실려 노출이 잦은 access token은 수명을 짧게 해 **탈취 피해를 시간으로 제한**하고, 재발급 때만 오가는 refresh token은 노출이 적으니 길게 두되 **서버 저장소에 기록해 통제 지점으로** 쓴다. 한 문장으로 하면 **"자주 노출되는 것은 짧게, 통제 지점은 서버에"**라는 분리다.

여기에 회전과 재사용 탐지를 얹으면 답이 완성된다(3-5절). refresh token을 일회용으로 만들고, 폐기된 토큰이 다시 들어오면 탈취 신호로 보아 **해당 사용자의 토큰 계열 전체를 무효화**한다. **탈취를 막을 수는 없어도 탈취를 탐지할 수는 있다**는 관점을 보여주는 대목이다.

### "토큰은 클라이언트 어디에 저장해야 하나요?"

웹이라면 `localStorage` vs 쿠키의 트레이드오프이고, 본질은 **XSS와 CSRF 중 어느 쪽 위험을 떠안을 것인가**다.

`localStorage`는 자바스크립트가 명시적으로 읽어 헤더에 붙이므로 자동 첨부가 없다. **CSRF와는 무관하다.** 대신 스크립트가 접근할 수 있는 곳에 있으므로 **XSS 한 방에 토큰이 통째로 유출된다.** 유출된 토큰은 공격자 서버로 넘어가 만료까지 어디서든 쓰인다.

`HttpOnly` 쿠키는 반대다. 스크립트가 읽을 수 없어 **XSS로 훔쳐 가는 것은 막지만**, 브라우저가 자동 첨부하므로 **CSRF 대비(`SameSite`, CSRF 토큰)가 필요하다.** 그리고 1-4절에서 짚었듯 `HttpOnly`도 만능은 아니다 — XSS가 터지면 공격 스크립트가 **그 페이지 안에서** 요청을 보내는 것까지는 막지 못한다.

그래서 정답은 하나가 아니고 조건부다. 웹은 **`HttpOnly` + `Secure` + `SameSite` 쿠키 조합이 무난한 기본값**이다. XSS는 완전 방어가 어려운 반면 CSRF는 `SameSite`와 CSRF 토큰으로 비교적 확실하게 막을 수 있어서, **"확실히 막을 수 있는 쪽을 떠안는" 선택**이기 때문이다. 모바일 앱은 애초에 쿠키·CSRF 구도가 아니므로 OS의 보안 저장소(안드로이드 Keystore, iOS Keychain)를 쓴다. 어느 쪽이든 **저장 위치보다 XSS를 애초에 막는 것(출력 이스케이프, CSP)이 상위 방어선**이라는 점을 덧붙이면 좋다.

### "세션 ID나 토큰이 통째로 탈취되면 각각 어떻게 대응하나요?"

**구조가 다르므로 대응 가능성 자체가 다르다**는 것부터 말한다.

세션은 서버가 상태의 주인이라 **저장소에서 해당 세션을 지우면 그 순간 차단**된다. 사용자별 활성 세션 목록을 관리해 두면 "다른 기기 모두 로그아웃"이나 "의심 세션만 선택 종료"도 구현된다. 탈취 대응력은 세션이 본질적으로 유리하다.

토큰은 개별 회수가 안 되므로 **만료까지 유효한 것이 기본**이고, 차단하려면 결국 차단 목록이나 refresh 폐기 같은 서버 상태가 필요하다. 그래서 토큰 쪽 대응은 "차단"이 아니라 **"짧은 수명으로 피해 창을 줄이는 완화"**가 기본이고, 여기에 refresh 회전의 재사용 탐지를 얹어 **탈취를 사후에라도 알아채는** 장치를 만든다.

전송·저장 단계의 방어를 함께 언급하면 가산점이다. `Secure`로 평문 전송을 막고, `HttpOnly`로 스크립트 접근을 막고, 로그인 시 세션 ID를 재발급해 세션 고정을 막고, 서버 로그·APM에 토큰이나 세션 ID가 그대로 찍히지 않게 마스킹한다. **탈취 경로 자체를 줄이는 것이 사후 대응보다 앞선다.**

### "그래서 무엇을 언제 선택하나요?" (가산점 포인트)

기준 세 가지로 답한다.

**① 클라이언트 종류.** 브라우저 단일 도메인 서비스면 쿠키+세션(또는 쿠키에 담은 토큰)이 자연스럽다. 브라우저가 자동으로 해주는 일이 많아 구현이 단순하고 `HttpOnly`의 이점을 그대로 받는다. 모바일 앱·외부 API·여러 도메인이 얽히면 토큰이 자연스럽다.

**② 확장과 아키텍처.** 서버 간 호출이 많은 MSA는 홉마다 세션 저장소를 조회하는 비용이 커서 **자가 검증되는 토큰이 유리**하다. 반대로 단일 애플리케이션에 Redis가 이미 있다면 세션 외부화가 훨씬 적은 변경으로 끝난다.

**③ 무효화 요구의 강도.** 강제 차단과 권한 즉시 반영이 중요한 도메인(관리자 콘솔, 금융, 결제)일수록 세션이나 상태 있는 절충형으로 기운다. "5분 지연된 차단"이 허용되지 않는 요구가 있다면 그것만으로 방식이 결정된다.

마무리는 **"정답이 아니라 요구사항의 함수"**라는 태도다. 실제 답변에서는 여기에 현재 시스템의 제약(이미 있는 인프라, 팀의 운영 역량, 클라이언트 구성)을 얹어 하나를 고르고, **고르면서 무엇을 포기했는지**까지 말하는 것이 이 질문의 모범 답안 골격이다.

## 한 줄 요약

쿠키는 무상태 HTTP 위에서 증표를 브라우저가 자동으로 실어 나르는 운반 수단이고(`HttpOnly`는 XSS 탈취를, `Secure`는 평문 전송을, `SameSite`는 CSRF를 막는 짝이며 `None`은 `Secure`가 강제된다), 세션은 상태를 서버에 두고 열쇠만 보내는 방식(즉시 무효화가 쉽고 확장 시 상태 공유가 숙제), 토큰은 서명된 상태를 클라이언트에 들려 보내는 방식(확장이 쉽고 서명은 위조만 막을 뿐 payload는 누구나 읽으며 즉시 무효화가 어렵다)이다 — 운반 수단과 저장 위치라는 두 축으로 나눠 놓고, 클라이언트 종류·확장 구조·무효화 요구에 따라 스티키 세션·Redis 세션·짧은 access + 상태 있는 refresh 중 하나로 절충하는 것이 실무의 선택이다.
