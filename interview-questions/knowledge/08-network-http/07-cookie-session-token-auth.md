# 쿠키·세션·토큰 인증 — "상태를 어디에 두고, 무엇으로 실어 나르는가"

> 핵심 관전 포인트: **셋은 같은 층위의 선택지가 아니다. HTTP는
> 무상태(stateless)라 "이 요청이 누구인지"를 매 요청 다시 증명해야
> 하는데, 쿠키는 그 증명을 자동으로 실어 나르는 전송 수단이고,
> 세션과 토큰은 인증 상태를 어디에 두느냐의 두 방식이다 —
> 세션은 상태를 서버에 두고 쿠키로는 열쇠(세션 ID)만 나르며,
> 토큰(JWT)은 상태 자체를 서명해 클라이언트에 들려 보내고 서버는
> 서명만 검증한다. 그래서 세션은 서버 확장 시 상태 공유가 문제가
> 되고, 토큰은 서버가 기억하지 않으므로 확장은 쉽지만 즉시 무효화가
> 어렵다. 선택은 확장성·탈취 대응·클라이언트 종류(웹/앱)가 얽힌
> 트레이드오프다.**

---

## 0. 질문 + 의도

**질문**: "쿠키와 세션, 토큰 기반 인증의 차이는?"

**출제 의도**: 인증 방식 선택은 확장성(서버 상태), 보안(탈취 대응),
클라이언트 종류(웹/앱)가 얽힌 실무 결정이다. IAM·인증 기능을 다루는
백엔드의 상시 업무.

## 1. 출발점 — HTTP는 무상태고, 쿠키는 전송 수단이다

HTTP는 요청 하나하나가 독립이다. 서버는 방금 로그인한 사용자의 다음
요청을 처음 보는 요청과 구분할 방법이 프로토콜 차원에는 없다. 그래서
**매 요청에 "나는 아까 그 사람"이라는 증표를 실어 보내야** 하고,
이 증표를 나르는 대표 수단이 쿠키다.

쿠키의 동작은 헤더 두 개가 전부다:

```http
# 서버 → 브라우저: 응답에 증표를 심는다
HTTP/1.1 200 OK
Set-Cookie: SESSION=a1b2c3; Path=/; HttpOnly; Secure; SameSite=Lax

# 브라우저 → 서버: 이후 같은 도메인의 모든 요청에 자동 첨부
GET /orders HTTP/1.1
Cookie: SESSION=a1b2c3
```

핵심 성질은 **자동 첨부**다. 개발자가 코드를 쓰지 않아도 브라우저가
해당 도메인 요청마다 쿠키를 붙인다. 이 자동성이 편리함(웹에서
로그인 유지가 공짜)이자 약점(사용자 모르게도 첨부된다 → CSRF)이다.

여기까지가 쿠키의 역할이고, **"증표의 내용이 무엇이냐"부터가 세션과
토큰의 갈림길**이다. 쿠키 vs 세션 vs 토큰을 나란히 비교하면 층위가
꼬인다 — "운반 수단(쿠키/헤더)"과 "상태 저장 위치(서버/클라이언트)"
두 축으로 나눠 설명하는 것이 정리된 답변이다.

## 2. 세션 vs 토큰 — 상태를 서버에 두느냐, 들려 보내느냐

### 세션: 상태는 서버에, 클라이언트에는 열쇠만

로그인하면 서버가 사용자 정보를 자기 저장소(메모리, Redis)에 넣고,
그 항목을 가리키는 무작위 식별자(세션 ID)만 쿠키로 내려준다.

- 증표(세션 ID) 자체에는 아무 정보가 없다 — 물품보관함 번호표와 같다.
  번호표를 주워도 보관함은 서버에 있다.
- 서버가 상태의 주인이므로 **즉시 무효화가 쉽다**: 로그아웃, 강제
  로그아웃, 권한 변경이 서버 저장소에서 지우는 것으로 끝난다.
- 대신 **모든 요청이 저장소 조회를 거치고**, 서버가 여러 대로 늘어나면
  "2번 서버에 저장된 세션을 3번 서버가 어떻게 아나"라는 상태 공유
  문제가 생긴다(아래 실무 사례).

### 토큰(JWT): 상태를 서명해서 클라이언트에 들려 보낸다

로그인하면 서버가 사용자 정보(사용자 ID, 권한, 만료시각)를 담은
데이터에 **서버만 아는 키로 서명**해서 통째로 내려준다. 이후 요청마다
클라이언트가 토큰을 첨부하면, 서버는 저장소 조회 없이 **서명 검증만으로**
"내가 발급한 위조되지 않은 증표"임을 확인한다.

- 증표가 자기완결적(self-contained)이다 — 신분증처럼 내용과 위조
  방지 장치(서명)를 함께 갖고 다닌다.
- 서버가 아무것도 기억하지 않으므로 **무상태 → 수평 확장이 쉽고**,
  도메인이 다른 서비스·모바일 앱·서버 간 호출에도 그대로 쓰인다.
- 대가는 **발급한 뒤 서버가 개별 토큰을 회수할 수 없다**는 것이다.
  만료시각까지는 유효하다 — 로그아웃·강제 차단 같은 "즉시 무효화"
  요구가 토큰 방식의 아킬레스건이다(꼬리질문 참고).
- 주의: JWT의 서명은 위조 방지이지 **암호화가 아니다**. 내용(payload)은
  누구나 디코딩해 읽을 수 있으므로 민감정보를 넣으면 안 된다.

### 전송 관점의 차이 — 자동 첨부 vs 수동 첨부

증표를 나르는 방식이 공격면을 가른다.

| | 쿠키로 운반 (주로 세션) | Authorization 헤더로 운반 (주로 토큰) |
|---|---|---|
| 첨부 방식 | 브라우저가 자동 | 클라이언트 코드가 수동 |
| CSRF | 취약 (자동 첨부가 원인) → SameSite·CSRF 토큰 필요 | 강함 (공격자 사이트는 헤더를 못 붙임) |
| XSS로 탈취 | HttpOnly면 스크립트가 못 읽음 | JS가 접근 가능한 곳에 두면 탈취됨 |
| 크로스 도메인/앱 | 도메인에 묶임, 앱에서 불편 | 자유로움 |

```http
# 토큰 방식의 전형적 요청 — 코드가 직접 헤더를 붙인다
GET /orders HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI0MiJ9.signature
```

주의할 점: "세션=쿠키, 토큰=헤더"는 관행이지 규칙이 아니다. 토큰을
HttpOnly 쿠키에 담아 나를 수도 있다(웹에서 XSS 탈취 방어에 유리).
**저장 위치(서버/클라이언트)와 운반 수단(쿠키/헤더)이 독립적인 축**임을
아는 것이 이 질문의 변별점이다.

## 3. 실무 사례 — 서버를 늘렸더니 로그인이 풀린다

세션을 톰캣 로컬 메모리에 두는 기본 구성은 서버가 1대일 때만 성립한다.
scale-out으로 2대가 되고 LB가 요청을 번갈아 보내는 순간, 1번 서버에서
로그인한 사용자의 다음 요청이 2번 서버로 가면 "세션 없음 → 로그인
페이지"가 된다. **간헐적으로 로그인이 풀리는** 전형적 증상이다.

```java
// Before: 로컬 메모리 세션 — 서버 인스턴스마다 각자 기억, 확장 시 깨짐
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("userId", authenticate(req)); // 이 서버의 메모리에만 존재
}

// After(방법 1): 세션 저장소를 중앙(Redis)으로 — 어느 서버가 받아도 동일 세션
// spring-session-data-redis 적용: 코드는 그대로, 저장 위치만 Redis로 바뀐다
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("userId", authenticate(req)); // Redis에 저장, 전 서버 공유
}

// After(방법 2): 토큰 발급 — 서버는 상태를 갖지 않는다
@PostMapping("/login")
public TokenResponse login(LoginRequest req) {
    Long userId = authenticate(req);
    return new TokenResponse(jwtProvider.issue(userId)); // 서명된 토큰을 클라이언트가 보관
}
```

이때의 선택지가 곧 이 질문의 트레이드오프다:
(1) **sticky session** — LB가 같은 사용자를 같은 서버로 고정. 설정만으로
되지만 특정 서버로 부하가 쏠리고, 그 서버가 죽으면 그 사용자들의
세션이 통째로 사라진다. (2) **중앙 세션 저장소(Redis)** — 서버는
무상태에 가까워지고 무효화도 쉽지만, 저장소가 전 요청의 의존점이
된다(Redis 장애 = 전원 로그아웃, 가용성 설계 필요). (3) **토큰** —
저장소 의존이 없어지지만 즉시 무효화 문제를 떠안는다.

## 4. 꼬리질문 대비 포인트

### "JWT를 쓰면 세션 저장소가 정말 필요 없어지나요?" (시니어 변별 포인트)

이론상 그렇지만 실무 요구가 다시 상태를 불러온다. 로그아웃한 토큰
즉시 차단, 비밀번호 변경·계정 탈취 시 강제 만료, 권한 변경 즉시 반영 —
전부 "발급된 토큰을 회수"해야 하는 요구인데, 무상태 토큰은 회수가
안 된다. 대응은 (1) access token을 짧게(피해 시간창 축소) + refresh
token으로 재발급, (2) refresh token을 서버 저장소에 두고 무효화 지점으로
사용, (3) 차단 목록(blacklist)을 두고 매 요청 조회 — 그런데 (2), (3)은
결국 서버 상태 조회다. 즉 **완전한 무상태는 "즉시 무효화 포기"와
교환한 것**이며, 실제 시스템은 대부분 절충형(짧은 무상태 access +
상태 있는 refresh)이라고 답하면 설계 경험이 드러난다.

### "access token과 refresh token은 왜 나누나요?"

한 장짜리 토큰은 "탈취 피해 시간"과 "재로그인 빈도"가 한 값에 묶인다 —
길게 하면 탈취 시 오래 악용되고, 짧게 하면 사용자가 계속 로그인해야
한다. 둘로 나누면 매 요청에 실려 다녀 노출 빈도가 높은 access token은
수명을 짧게 해 탈취 피해를 줄이고, refresh token은 재발급 시에만
전송되므로 노출이 적고 서버 저장소로 관리해 무효화 지점으로 쓴다.
"자주 노출되는 것은 짧게, 통제 지점은 서버에"라는 분리다.

### "토큰은 클라이언트 어디에 저장해야 하나요?"

웹이라면 localStorage vs 쿠키의 트레이드오프다. localStorage는 CSRF와
무관하지만 XSS 한 방에 스크립트로 토큰이 통째로 유출된다. HttpOnly
쿠키는 스크립트가 못 읽으므로 XSS의 직접 탈취를 막지만, 자동 첨부
때문에 CSRF 대비(SameSite 속성, CSRF 토큰)가 필요하다. 정답이 하나는
아니고 "XSS 방어에 자신 있는가, CSRF 방어를 갖췄는가"에 따른 선택이며,
웹은 HttpOnly+Secure+SameSite 쿠키 조합이 무난한 기본값이고 모바일
앱은 OS의 보안 저장소를 쓴다고 답하면 된다.

### "세션 ID나 토큰이 통째로 탈취되면 각각 어떻게 대응하나요?"

세션은 서버가 상태의 주인이라 **해당 세션을 저장소에서 지우면 즉시
차단**된다 — 사용자별 활성 세션 목록을 관리하면 "다른 기기 모두
로그아웃"도 구현된다. 토큰은 개별 회수가 안 되므로 만료까지 유효한
게 기본이고, 차단하려면 결국 차단 목록 등 서버 상태가 필요하다.
그래서 "탈취 대응력은 세션이 본질적으로 유리하고, 토큰은 짧은 수명으로
피해 창을 줄이는 완화가 기본"이라고 구조적으로 답하는 것이 좋다.
전송 단계 방어(Secure로 HTTPS 강제, HttpOnly로 스크립트 접근 차단)를
함께 언급하면 가산점.

### "그래서 무엇을 언제 선택하나요?" (가산점 포인트)

기준 세 가지로 답한다. (1) **클라이언트 종류**: 브라우저 단일 도메인
서비스면 쿠키+세션(또는 쿠키에 담은 토큰)이 자연스럽고, 모바일 앱·
외부 API·여러 도메인이면 토큰이 자연스럽다. (2) **확장·아키텍처**:
서버 간 호출이 많은 MSA는 매 홉마다 세션 조회가 부담이라 자가검증
토큰이 유리하다. (3) **무효화 요구**: 강제 차단·권한 즉시 반영이
중요한 도메인(관리자, 금융)일수록 세션 또는 상태 있는 절충형으로
기운다. "정답이 아니라 요구사항의 함수"라는 태도가 이 질문의
모범 답안 골격이다.

## 한 줄 요약

쿠키는 무상태 HTTP 위에서 증표를 자동으로 실어 나르는 운반 수단이고,
세션은 상태를 서버에 두고 열쇠만 보내는 방식(무효화 쉬움, 확장 시
상태 공유 문제), 토큰은 서명된 상태를 클라이언트에 들려 보내는
방식(확장 쉬움, 즉시 무효화 어려움)이다 — 운반 수단과 저장 위치라는
두 축으로 나눠, 클라이언트 종류·확장성·탈취 대응 요구에 따라
절충하는 것이 실무의 선택이다.
