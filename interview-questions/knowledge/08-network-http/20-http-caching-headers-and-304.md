# HTTP 캐싱 헤더와 304 — 백엔드가 내려주는 헤더가 모든 캐시를 조종한다

> 핵심 관전 포인트: **HTTP 캐싱은 2단계로 동작한다. ① 신선도(freshness):
> `Cache-Control: max-age` 기간 안에서는 캐시가 서버에 묻지도 않고 바로
> 응답한다 — 요청이 서버에 도달 자체를 안 하는 가장 강력한 단계.
> ② 재검증(revalidation): 신선도가 만료되면 캐시가 `ETag`/`Last-Modified`
> 값을 조건부 요청(`If-None-Match`/`If-Modified-Since`)에 실어 보내고,
> 내용이 그대로면 서버는 본문 없는 `304 Not Modified`만 돌려준다 —
> 대역폭은 아끼지만 왕복(RTT)은 발생하는 두 번째 단계. 브라우저 캐시든
> CDN이든 이 헤더 계약을 따르는 실행자일 뿐이므로, 캐시 정책의 주도권은
> 헤더를 내려주는 백엔드에 있다. 그리고 이 강력함의 이면 —
> 개인화 응답에 `public` 캐시를 잘못 걸면 남의 데이터가 보이는
> 보안 사고가 된다.**

---

## 0. 질문 + 의도

**질문**: "HTTP 캐싱 헤더(Cache-Control, ETag, Last-Modified)와 304 응답
흐름을 설명해주세요. CDN 캐시 제어와는 어떻게 연결되나요?"

**출제 의도**: CDN·브라우저 캐시는 백엔드가 내려주는 헤더로 조종된다.
콘텐츠 서비스에서 Cache-Control 설계는 성능 도구이자, 잘못 쓰면
개인화 응답이 공유 캐시에 남는 보안 사고의 원인 — 이 양면을 다
아는지 본다. 캐시를 "인프라 팀 일"로 미루는 사람인지, 응답 헤더가
캐시 계층 전체의 리모컨임을 아는 사람인지 가리는 질문이다.

## 1. 큰 그림 — 캐시의 2단계: "묻지 않기"와 "싸게 묻기"

캐시(브라우저든 CDN이든)가 저장해 둔 사본을 다룰 때의 질문은 둘이다:

1. **아직 신선한가?** → 신선하면 서버에 안 묻고 캐시가 바로 응답
   (**신선도 단계** — `Cache-Control: max-age`가 결정)
2. **신선도가 끝났으면, 내용이 그대로인지 싸게 확인할 수 있나?**
   → 조건부 요청으로 확인, 그대로면 304 (**재검증 단계** —
   `ETag`/`Last-Modified`가 결정)

- 비유: 우유(응답)에 붙은 **유통기한**이 max-age다. 기한 안이면 그냥
  마신다(서버에 안 감). 기한이 지나면 버리는 게 아니라 **냄새를 맡아
  본다**(재검증) — 멀쩡하면 유통기한만 새로 붙이고 계속 마신다(304).
  냄새 맡기(RTT)는 새 우유 사 오기(본문 전체 재전송)보다 훨씬 싸다.

이 구분이 잡혀 있으면 "304가 왜 완전한 공짜가 아닌지"(왕복은 함),
"max-age가 왜 304보다 강한지"(왕복조차 없음)가 자연히 설명된다.

## 2. Cache-Control — 신선도와 저장 범위의 선언

자주 쓰는 지시어를 역할별로 묶으면:

- **얼마나 신선한가**: `max-age=3600` (1시간 동안 재검증 없이 사용),
  `s-maxage=600` (공유 캐시(CDN)에만 적용되는 별도 수명 — 브라우저와
  CDN의 수명을 다르게 줄 때), `immutable` (수명 내 재검증 시도 자체를
  생략하라는 힌트)
- **누가 저장해도 되는가**: `public` (CDN 같은 공유 캐시도 저장 가능),
  `private` (특정 사용자의 브라우저만 — **개인화 응답의 최소 안전선**)
- **저장/사용의 금지 수준**: `no-cache` (저장은 하되 **매번 재검증 후**
  사용 — "캐시 금지"가 아니다!), `no-store` (저장 자체 금지 — 진짜 금지)

`no-cache` vs `no-store`는 면접 단골 함정이다. `no-cache`는 "쓰기 전에
꼭 물어봐"(항상 조건부 요청 → 304 가능)이고, `no-store`는 "적어두지도
마"(민감 정보용)다.

```http
# Before: 습관적으로 아무 헤더도 안 내려줌
HTTP/1.1 200 OK
Content-Type: application/json
# → 캐시 정책이 '없는' 게 아니라 '통제 불능'이 된다.
#   브라우저가 휴리스틱(자체 추정)으로 캐시할 수 있어
#   "배포했는데 일부 사용자만 옛 응답을 본다" 같은 재현 안 되는 문제가 생긴다.

# After: 응답 성격별로 명시적 선언
# ① 버전드 URL의 정적 자원 (내용이 바뀌면 URL이 바뀜)
Cache-Control: public, max-age=31536000, immutable

# ② 모두에게 같은 목록성 API (짧게 공유 캐시 허용)
Cache-Control: public, max-age=0, s-maxage=30

# ③ 개인화 응답 (내 정보, 내 주문)
Cache-Control: private, no-store
```

## 3. ETag / Last-Modified와 304 흐름 — 재검증의 실제 왕복

### 첫 응답에서 서버가 검증자(validator)를 발급한다

```http
HTTP/1.1 200 OK
Cache-Control: max-age=60
ETag: "a3f8c2"                          # 내용의 지문 (보통 해시)
Last-Modified: Mon, 25 Aug 2025 09:00:00 GMT  # 마지막 수정 시각
...본문 전체...
```

### 신선도(60초)가 지난 뒤의 재검증 왕복

```http
# 캐시가 보관해 둔 검증자를 조건에 실어 보낸다
GET /articles/42 HTTP/1.1
If-None-Match: "a3f8c2"                       # ETag의 짝
If-Modified-Since: Mon, 25 Aug 2025 09:00:00 GMT  # Last-Modified의 짝

# 내용이 안 바뀌었으면 — 본문 없이 신선도만 갱신
HTTP/1.1 304 Not Modified
Cache-Control: max-age=60      # 다시 60초간 "묻지 않기" 부활
ETag: "a3f8c2"
# (본문 없음 → 대역폭 절약. 캐시는 갖고 있던 사본을 계속 쓴다)

# 바뀌었으면 — 평범한 200 + 새 본문 + 새 ETag
HTTP/1.1 200 OK
ETag: "b9d1e7"
...새 본문...
```

### ETag vs Last-Modified — 무엇으로 판별하나

- **Last-Modified**는 초 단위 시각이다. 1초 안에 두 번 수정되면 구분
  못 하고, "내용은 그대로인데 파일만 다시 저장"된 경우 불필요한 200을
  만든다.
- **ETag**는 내용 기반 지문이라 더 정확하다. 둘 다 있으면
  `If-None-Match`(ETag)가 우선한다.
- 실무 함정 (가산점 포인트): 웹서버의 기본 ETag 생성 방식이 파일의
  서버별 메타데이터에 의존하면, **여러 대의 서버가 같은 파일에 서로
  다른 ETag**를 내려줘 재검증이 계속 실패(항상 200)한다. 다중 서버
  환경에서는 내용 해시 기반이거나 일관된 생성 방식인지 확인해야 한다.

## 4. CDN과의 연결 — 같은 헤더, 하나 더 낀 계층

CDN은 별도의 제어 체계가 아니라 **이 헤더 계약을 따르는 공유 캐시
(shared cache)** 다. 연결 지점만 정확히 잡으면 된다:

- **`public`/`private`**: CDN이 저장해도 되는지의 경계선.
  `private`·`no-store` 응답은 CDN에 남으면 안 된다 — 이 선이 뚫리면
  A 사용자의 "내 정보" 응답이 B 사용자에게 서빙되는 사고가 된다.
- **`s-maxage`**: 브라우저(max-age)와 CDN(s-maxage)의 수명을 분리한다.
  예: `max-age=0, s-maxage=60` — 브라우저는 매번 확인하되, CDN은 60초간
  엣지에서 응답. 갱신 주도권을 CDN 쪽에 두는 흔한 패턴이다.
  (많은 CDN은 자사 전용 제어 헤더도 제공하지만, 표준 우선순위는
  s-maxage → max-age 순으로 해석된다.)
- **재검증의 이중 구조**: 브라우저 ↔ CDN 사이에서도, CDN ↔ 오리진
  사이에서도 각각 조건부 요청/304가 일어난다. CDN이 오리진에 재검증해
  304를 받으면 엣지 캐시의 신선도만 갱신하고 본문 전송은 생략된다 —
  오리진 대역폭 절약이 여기서도 반복된다.
- **`Vary`**: 캐시 키의 확장이다. 예컨대 `Vary: Accept-Encoding`이
  없으면 압축본과 비압축본이 한 키에 섞이고, 반대로 `Vary`에 값이
  다양한 헤더를 넣으면 캐시가 잘게 쪼개져 히트율이 무너진다.

무효화 전략(버전드 URL vs purge)과 CDN 아키텍처 자체는
`07-traffic-performance/05-cdn-webtoon-image-serving.md`에서 다루므로,
이 문서의 초점은 "그 CDN을 조종하는 헤더가 어떻게 동작하는가"다.

## 5. 꼬리질문 대비 포인트

### "no-cache와 no-store의 차이는 뭔가요?"

`no-cache`는 저장은 허용하되 사용 전 **매번 재검증**을 강제한다 —
그래서 304로 응답하는 효율은 유지된다. `no-store`는 저장 자체를
금지한다 — 재검증도 304도 없이 매번 전체 응답이다. "캐시하지 마"라는
의도로 `no-cache`를 쓰면 여전히 디스크에 사본이 남으므로, 민감 정보
(개인정보, 결제 화면)는 `no-store`여야 한다.

### "304를 받는데도 페이지가 느립니다. 왜죠?"

304는 본문 전송(대역폭)을 아낄 뿐 **왕복(RTT) 자체는 발생**하기
때문이다. 리소스가 수십 개면 재검증 왕복도 수십 번이다. 처방은
재검증 단계가 아니라 신선도 단계로 올리는 것 — 버전드 URL +
`max-age=31536000, immutable`로 "묻지 않는 캐시"를 만들면 왕복이
0이 된다. 304는 "URL을 바꿀 수 없는데 갱신 가능성은 있는" 리소스에서
차선책으로 쓰는 것이지, 정적 자원의 1차 전략이 아니다.

### "개인화 응답에 캐시 헤더를 잘못 주면 어떤 사고가 나나요?" (시니어 변별 포인트)

`/api/me` 같은 응답에 `Cache-Control: public, max-age=...`가 나가면
CDN(공유 캐시)이 그 응답을 저장했다가 **다른 사용자에게 그대로
서빙한다** — A의 개인정보가 B에게 보이는 정보 유출 사고이고,
서버 재배포로도 해결되지 않는다(캐시에 남아 있으므로 purge까지
필요하다). 방어는 다층으로: ① 인증 필요한 응답은 기본값을
`private`(민감하면 `no-store`)으로 강제하는 공통 처리, ② CDN 쪽에서도
`Authorization`/세션 쿠키가 붙은 요청은 캐시하지 않는 설정,
③ 캐시 대상 경로를 명시적 allowlist로 관리. "성능 도구인 캐시 헤더가
곧 보안 경계"라는 인식이 이 질문의 핵심이다.

### "ETag는 어떻게 생성하는 게 좋나요? API 응답에도 쓸 수 있나요?"

정적 파일은 내용 해시가 정석이다(다중 서버에서도 일관됨). API 응답은
본문 직렬화 결과의 해시로 만들 수 있지만, "어차피 본문을 다 만든 뒤
해시"라면 서버 연산은 그대로이고 절약은 전송량뿐이라는 한계를 알아야
한다. 리소스에 수정 시각/버전 컬럼이 있으면 그것을 ETag 재료로 써서
**본문 생성 자체를 건너뛰는** 구현이 진짜 이득이다. 이 구조는
`If-Match`를 쓰는 낙관적 동시성 제어(수정 충돌 감지)로도 확장된다
(가산점 포인트).

### "배포 직후 사용자들이 옛 화면을 봅니다. 캐시 관점에서 원인은?"

계층별로 짚는다: ① HTML 문서 자체에 긴 max-age가 걸려 있으면 새
배포를 가리키는 진입점부터 갱신이 안 된다 — HTML은 `no-cache`(또는
아주 짧은 max-age)로 매번 재검증시키고, 그 HTML이 참조하는 JS/CSS는
버전드 URL + 장기 캐시로 가져가는 조합이 정석이다. ② CDN의 s-maxage가
남아 엣지가 옛 응답을 주는 경우 — 배포 파이프라인에 해당 경로 purge를
포함한다. ③ 브라우저에 이미 저장된 캐시는 서버가 원격으로 지울 수
없다는 것 — 그래서 애초에 "오래 캐시할 것은 URL로 버전을 박는다"는
설계가 사후 대응보다 중요하다.

## 한 줄 요약

HTTP 캐싱은 `Cache-Control`이 정하는 "묻지 않는 기간"과
`ETag`/`Last-Modified` 재검증이 만드는 "본문 없는 304"의 2단계 구조이고,
브라우저와 CDN은 모두 이 헤더 계약의 실행자다 — 백엔드가 내려주는
헤더 한 줄이 캐시 계층 전체의 성능을 좌우하는 동시에,
`public`/`private` 한 단어가 개인화 응답 유출 사고의 경계선이 된다.
