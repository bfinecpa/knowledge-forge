# TLS termination 위치 — 보안·성능·운영이 3자 대치하는 구성 결정

> 핵심 관전 포인트: **TLS termination은 "암호화를 어느 지점에서 풀어
> 평문으로 전환하는가"의 결정이고, LB 종료와 앱 종료는 세 축의
> 트레이드오프다. LB에서 끝내면 인증서 관리가 한 곳으로 모이고
> 암복호화가 앱에서 오프로드되며 LB가 HTTP를 볼 수 있어 L7 라우팅·
> WAF·관찰이 가능해지지만, LB 뒤 내부 구간이 평문이 된다 — 내부망을
> 신뢰할 수 있다는 전제가 필요하다. 앱까지 암호화를 끌고 가면 전
> 구간이 보호되지만 인증서를 모든 인스턴스에 배포·갱신해야 하고
> LB는 내용을 못 보는 L4 통과(passthrough)가 되어 L7 기능을 잃는다.
> 정답이 없는 결정이므로, 내부망 신뢰 수준(규제 요건)·필요한 L7
> 기능·인증서 운영 자동화 수준을 근거로 논하는 것이 답이다.**

---

## 0. 질문 + 의도

**질문**: "TLS termination을 어디서 할지(LB vs 애플리케이션)의 트레이드오프는?"

**출제 의도**: 보안(내부 구간 평문)과 성능(암복호화 오프로드),
운영(인증서 관리 지점)의 3자 트레이드오프. 정답이 없는 구성 결정을
근거로 논할 수 있는지 본다.

## 1. TLS termination이란 — 암호화가 끝나는 지점

클라이언트와 TLS handshake를 맺고 트래픽을 복호화하는 지점을 "TLS를
종료(terminate)한다"고 한다. 그 지점부터 뒤쪽은 복호화된 트래픽이
흐른다. 요청 경로에 LB가 있으면 종료 지점의 선택지가 생긴다:

```
[A] LB 종료:      클라이언트 ══TLS══→ LB ──평문 HTTP──→ 앱
[B] 앱 종료:      클라이언트 ══════TLS══════(LB는 통과)══→ 앱
[C] 재암호화:     클라이언트 ══TLS══→ LB ══내부용 TLS══→ 앱
```

이 선택이 중요한 이유는 **종료 지점이 세 가지를 동시에 결정**하기
때문이다: (1) 어느 구간이 평문인가(보안), (2) 암복호화 CPU를 누가
쓰는가(성능), (3) 인증서가 어디에 몇 벌 존재하는가(운영). 그리고
부수 효과로 (4) LB가 HTTP 내용을 볼 수 있는가(기능)까지 갈린다.

## 2. 세 축의 트레이드오프

### 보안 — 내부 구간을 평문으로 둘 수 있는가

LB 종료의 최대 약점은 **LB 뒤가 평문**이라는 것이다. "내부망이니까
괜찮다"는 VPC·방화벽으로 격리된 네트워크와 그 운영 주체를 신뢰한다는
전제 위에서만 성립한다. 이 전제가 깨지는 경우들:

- 결제·의료 등 **규제 요건이 전 구간 암호화를 요구**하는 도메인.
- 내부망이라도 여러 팀·여러 워크로드가 공존해 "내부 = 신뢰"가
  성립하지 않는 환경 — 제로 트러스트 관점은 "네트워크 위치가 아니라
  개별 연결을 검증하라"이므로 내부 평문 자체를 문제 삼는다.
- 클라우드에서 LB→앱 구간이 물리적으로 어떤 경로를 지나는지
  통제할 수 없는 경우.

앱 종료(또는 재암호화)는 이 문제를 없애지만, 아래 두 축의 비용을 낸다.

### 성능 — 암복호화를 누가 부담하는가

TLS 비용의 구조(handshake의 비대칭 연산 + 본문 대칭 암복호화)를
어디에 두느냐다. LB 종료는 이 비용을 앱 프로세스에서 **오프로드**해
앱 CPU를 비즈니스 로직에 쓰게 한다. 또 LB가 클라이언트와의 연결을
받아내고 뒤쪽으로는 적은 수의 keep-alive 연결을 재사용하므로, 앱이
직접 수만 클라이언트와 handshake하는 것보다 연결 관리 부담이 준다.

균형 잡힌 시각(가산점 포인트): 대칭 암복호화는 CPU의 AES 하드웨어
가속 덕에 예전만큼 비싸지 않다. 오늘날 오프로드의 실익은 본문
암복호화보다 **handshake 집중 처리와 연결 관리**, 그리고 다음 절의
운영·기능 쪽에 있는 경우가 많다 — "성능 때문에 무조건 LB 종료"는
낡은 근거일 수 있다고 짚으면 좋다.

### 운영 — 인증서가 몇 곳에 있는가

인증서는 만료가 곧 전면 장애인 자산이다. **종료 지점 수 = 인증서
배포·갱신·모니터링 지점 수**다.

- LB 종료: 인증서가 LB 한 곳(또는 LB 계층 한 벌)에만 있다. 클라우드
  LB라면 관리형 인증서로 갱신 자동화까지 위임된다. 개인키가 앱
  인스턴스에 흩어지지 않는 것 자체가 보안 이점이기도 하다.
- 앱 종료: 모든 인스턴스에 인증서·개인키를 배포하고 갱신을 동기화해야
  한다. 오토스케일링으로 인스턴스가 수시로 뜨는 환경이면 배포
  파이프라인·시크릿 관리와 얽혀 난이도가 올라간다. 갱신 누락 한
  인스턴스가 간헐적 TLS 에러를 만드는, 추적 어려운 장애 패턴도 생긴다.

### 기능 — LB가 HTTP를 볼 수 있는가

종료 지점의 부수 효과이지만 실무에서는 결정타가 되곤 한다. LB가
TLS를 종료해야 HTTP 내용을 볼 수 있고, 그래야 **L7 기능**이 가능하다:
경로/호스트 기반 라우팅, 쿠키 기반 sticky session, 요청/응답 헤더
조작, WAF(공격 패턴 검사), HTTP 접근 로그와 상태코드 기반 헬스체크.
앱 종료를 택하면 LB는 암호문을 그대로 흘리는 **L4 passthrough**가
되어 이 기능들을 전부 잃는다 — IP/포트 수준의 분배와 감시만 남는다.

| | LB 종료 | 앱 종료 (passthrough) |
|---|---|---|
| 내부 구간 | 평문 (신뢰 전제 필요) | 전 구간 암호화 |
| 앱 CPU | 오프로드됨 | 암복호화 부담 |
| 인증서 관리 | 1곳, 자동화 쉬움 | 전 인스턴스, 배포·동기화 필요 |
| L7 기능(라우팅·WAF·로그) | 가능 | 불가 (L4만) |
| 클라이언트 정보 | 헤더로 전달 필요 (§3) | 앱이 직접 봄 |

## 3. LB 종료가 만드는 함정 — 앱이 잃어버리는 정보

LB에서 종료하면 앱 입장에서 연결 상대는 LB다. 두 가지 정보가 사라지고,
관행적으로 헤더로 복원한다: 실제 클라이언트 IP는 `X-Forwarded-For`,
원래 프로토콜(https였는지)은 `X-Forwarded-Proto`.

이 복원을 빠뜨린 전형적 장애가 **리다이렉트 루프**다:

```
# Before: 앱이 X-Forwarded-Proto를 모른다
클라이언트 ──https──→ LB ──http──→ 앱
앱: "http로 왔네? https로 리다이렉트" → 301 https://...
클라이언트: https로 재요청 → LB → 앱은 또 http로 인식 → 또 301 → 무한 루프
```

```yaml
# After: 앱이 프록시의 헤더를 신뢰하도록 설정 (Spring Boot)
server:
  forward-headers-strategy: framework   # X-Forwarded-* 를 해석해
                                        # 요청의 scheme/호스트/IP를 복원
```

같은 이유로 접근 로그의 IP가 전부 LB IP로 찍히거나, IP 기반 rate
limit이 LB 하나를 차단해버리는 사고도 난다. 단 `X-Forwarded-For`는
클라이언트가 위조할 수 있는 헤더이므로 **신뢰할 프록시가 붙인 값만**
쓰도록 경계를 정해야 한다(별도 질문에서 다루는 주제). "LB 종료를
택하면 이 헤더 계약을 세팅하는 것까지가 한 세트"라고 말하면 운영
경험이 드러난다.

## 4. 절충안 — 재암호화와 서비스 메시 mTLS

양자택일이 아니라 스펙트럼이다.

- **재암호화(re-encryption)**: LB에서 종료해 L7 기능(라우팅, WAF)을
  쓰고, LB→앱 구간을 내부용 TLS로 다시 암호화한다. 전 구간 암호화와
  L7 기능을 모두 얻는 대신, handshake·암복호화가 두 번 일어나고
  내부용 인증서 관리가 추가된다.
- **서비스 메시의 mTLS**: 각 서비스 옆의 사이드카 프록시가 서비스 간
  통신을 상호 TLS(양쪽 모두 인증서로 신원 증명)로 자동 암호화하고,
  인증서 발급·순환도 메시의 컨트롤 플레인이 자동화한다. "전 구간
  암호화 + 인증서 운영 자동화"를 앱 코드 수정 없이 얻지만, 메시라는
  큰 인프라 복잡도를 도입하는 결정이다 — TLS 하나 때문이 아니라
  트래픽 제어·관찰 등 메시의 다른 효용과 묶어서 판단한다.

**판단 순서**를 정리하면: (1) 규제·보안 정책이 내부 평문을 허용하는가 —
불허면 재암호화/mTLS/앱 종료로 좁혀진다. (2) L7 라우팅·WAF가 필요한가 —
필요하면 어딘가에서 종료는 해야 하므로 passthrough는 탈락. (3) 인증서
운영을 자동화할 역량·도구가 있는가 — 없다면 종료 지점을 최소화(LB
한 곳)하는 쪽이 안전하다. 흔한 실무 구성이 "외부는 LB 종료 + 내부는
VPC 격리, 민감 구간만 재암호화"인 이유가 이 순서에서 나온다.

## 5. 꼬리질문 대비 포인트

### "LB에서 종료하면 앱은 클라이언트가 HTTPS로 접속했는지 어떻게 아나요?"

모른다 — 앱에 도착한 연결은 LB가 보낸 평문 HTTP다. 그래서 LB가
`X-Forwarded-Proto: https`를 붙여주고 앱이 이를 해석하도록 설정하는
것이 한 세트다. 이걸 빠뜨리면 "https로 리다이렉트" 로직이 무한
루프를 만들고, Secure 쿠키 발급이나 절대 URL 생성이 http로 잘못
만들어진다. 실제 클라이언트 IP도 같은 원리로 `X-Forwarded-For`로
전달받아야 한다.

### "내부 구간도 암호화하라는 보안 요구가 오면 어떻게 하나요?"

선택지를 비용 순으로: (1) LB→앱 재암호화 — L7 기능을 유지하면서 전
구간 암호화, 내부 인증서 관리와 이중 암복호화 비용. (2) 서비스 메시
mTLS — 서비스 간 통신까지 포함해 자동화하지만 인프라 복잡도가 크다.
(3) L4 passthrough로 앱 종료 — L7 기능 포기를 감수할 때. 어떤 걸
고르든 "인증서 발급·순환 자동화 없이는 운영이 안 된다"는 점을 함께
말하는 것이 핵심이다 — 수동 관리로는 지점 수만큼 만료 사고 확률이
곱해진다.

### "passthrough(L4)로 하면 구체적으로 뭘 잃나요?"

LB가 암호문만 보므로 HTTP 레벨의 모든 것을 잃는다: 경로·호스트 기반
라우팅(한 도메인 뒤에 여러 서비스 배치 불가), 쿠키 기반 sticky
session(소스 IP 기반만 가능), WAF, 요청 단위 접근 로그, 상태코드
기반 헬스체크(TCP 연결 확인 수준으로 후퇴). 관찰 지점이 사라지므로
"LB에서 5xx 비율 감시" 같은 모니터링도 앱 쪽으로 옮겨야 한다.

### "TLS 오프로드의 성능 이점은 지금도 유효한가요?" (가산점 포인트)

본문의 대칭 암복호화는 AES 하드웨어 가속 덕에 부담이 크게 줄어서,
"CPU 절약"만으로는 근거가 약해졌다. 여전히 유효한 것은 handshake
집중 처리(비대칭 연산과 연결 수립이 LB 계층에 모임), 클라이언트
연결 관리의 오프로드, 그리고 세션 재개 캐시를 LB에 모아 handshake
빈도 자체를 줄이는 효과다. 즉 오늘날 종료 위치 결정의 무게중심은
성능보다 보안 경계와 운영(인증서)·기능(L7) 쪽이라고 답하면
최신 감각을 보여준다.

### "우리 서비스라면 어디서 종료하겠어요?" (시니어 변별 포인트)

구성을 하나 고르고 근거를 세 축에 대응시켜 답한다. 예: "일반적인
웹 서비스이고 VPC로 격리된 내부망이라면 LB 종료를 기본으로 한다 —
관리형 인증서로 만료 사고를 구조적으로 없애고, 경로 라우팅·WAF·접근
로그를 LB 계층에서 얻는 실익이 내부 평문 리스크보다 크다. 단
`X-Forwarded-*` 계약을 세팅하고, 결제 정보가 지나는 구간처럼 규제가
걸리는 경로만 재암호화한다. 반대로 전사 제로 트러스트 정책이 있거나
멀티테넌트 내부망이라면 mTLS 기반으로 간다." — 이렇게 전제(신뢰
경계)를 명시하고 조건이 바뀌면 결론이 바뀐다는 구조로 말하는 것이
"정답 없는 질문"의 정답이다.

## 한 줄 요약

TLS termination 위치는 보안(내부 구간 평문 허용 여부)·성능(암복호화
오프로드)·운영(인증서 관리 지점 수)에 L7 기능 가용성까지 걸린
트레이드오프이며, LB 종료는 관리 집중과 L7 기능을 얻는 대신 내부
평문과 `X-Forwarded-*` 계약을 떠안고, 앱 종료는 전 구간 암호화를
얻는 대신 인증서 배포와 L7 기능 상실을 감수한다 — 내부망 신뢰
수준·규제·자동화 역량이라는 전제를 밝히고 그 함수로 결론을 내는
것이 모범 답안이다.
