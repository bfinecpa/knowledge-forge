# 웹소켓 / SSE / 폴링 — 실시간의 세 가지 구현과 "몇 초의 실시간인가"라는 질문

> 핵심 관전 포인트: **셋의 차이는 "누가, 어느 방향으로, 어떤 커넥션 위에서
> 데이터를 흘리는가"다. 폴링은 클라이언트가 주기적으로 물어보는 방식(연결
> 유지 없음), SSE는 HTTP 응답을 끊지 않고 서버→클라이언트 한 방향으로만
> 계속 흘리는 방식, 웹소켓은 HTTP로 시작해 프로토콜을 전환한 뒤 양방향으로
> 자유롭게 주고받는 전용 커넥션이다. 선택 기준은 기술 우열이 아니라
> ① 데이터 흐름의 방향(단방향이면 SSE로 충분), ② 요구되는 실시간의 실제
> 수준(수십 초 지연이 허용되면 폴링이 정답), ③ 인프라 제약(LB·프록시의
> 장수 커넥션 처리, scale-out 시 메시지 전파)이다. "실시간이 필요하다"는
> 요구를 받았을 때 "진짜 몇 초 수준의 실시간인가"부터 되묻는 것이
> 이 답변의 시작점이다.**

---

## 0. 질문 + 의도

**질문**: "웹소켓과 SSE, 폴링의 차이와 선택 기준은?"

**출제 의도**: 실시간성 요구(댓글, 알림)를 구현 비용·인프라 제약(LB의
장수 커넥션 처리)과 함께 판단하는지를 본다. 기술 스펙 비교 암기가 아니라,
"요구사항의 실시간이 진짜 몇 초 수준인지"를 되묻고 가장 싼 수단부터
검토하는 사람인지 — 요구사항을 구현 비용으로 번역하는 능력을 확인하는
질문이다.

## 1. 세 방식의 동작 원리 — "누가 먼저 말을 거는가"

### ① 폴링(Polling) — 클라이언트가 반복해서 물어본다

가장 단순하다. 클라이언트가 일정 주기로 일반 HTTP 요청을 보낸다.
"새 알림 있어요?" → "없어요" → (3초 뒤) "새 알림 있어요?" → …

- 장점: **그냥 HTTP다.** 서버·인프라에 아무 특별한 요구가 없다.
  LB, 프록시, 방화벽, 캐시 어디서도 문제가 없고 구현·디버깅이 제일 쉽다.
- 단점: 변경이 없어도 요청이 계속 발생한다(빈 응답 낭비). 실시간성은
  폴링 주기만큼 지연된다 — 주기를 줄이면 실시간성은 좋아지지만 요청 수가
  비례해서 늘어나는 트레이드오프.

변형으로 **롱 폴링(long polling)**이 있다: 서버가 "없어요"를 바로
응답하지 않고, 새 데이터가 생기거나 타임아웃될 때까지 응답을 **보류**한다.
클라이언트는 응답을 받자마자 다시 요청을 건다. 빈 응답 낭비를 줄이고
실시간성을 높인 절충안이지만, 서버가 응답 대기 중인 요청을 계속 물고
있어야 한다는 부담이 생긴다.

### ② SSE(Server-Sent Events) — 서버가 응답을 끝내지 않고 계속 흘린다

HTTP 요청 한 번에 대해 서버가 `Content-Type: text/event-stream`으로
응답을 열고, **응답 본문을 끝내지 않은 채** 이벤트가 생길 때마다
텍스트 조각을 이어서 내려보낸다. 방향은 **서버 → 클라이언트 단방향**이다.

- 장점: **여전히 HTTP다.** 별도 프로토콜이 아니라 "안 끝나는 HTTP 응답"
  이므로 기존 인프라와의 궁합이 웹소켓보다 좋다. 브라우저 표준 API인
  `EventSource`가 **끊기면 자동 재연결**하고, `Last-Event-ID` 헤더로
  "어디까지 받았는지"를 서버에 알려 유실분 재전송 설계도 표준적으로
  지원한다.
- 단점: 단방향이다. 클라이언트가 서버로 뭔가 보내려면 별도의 일반 HTTP
  요청을 써야 한다. 바이너리 전송에는 부적합(텍스트 기반).

### ③ 웹소켓(WebSocket) — 프로토콜을 갈아타는 양방향 전용선

HTTP 요청으로 시작하되, `Upgrade: websocket` 헤더로 **프로토콜 전환
(핸드셰이크)**을 한 뒤에는 HTTP가 아닌 웹소켓 프레임으로 통신한다.
하나의 TCP 커넥션 위에서 **양방향(full-duplex)**으로, 클라이언트와
서버가 각자 원할 때 메시지를 보낸다.

- 장점: 진짜 양방향. 메시지 단위 오버헤드가 작아 **고빈도 양방향
  교환**(채팅, 협업 편집, 게임, 실시간 호가)에 적합하다.
- 단점: HTTP가 아니게 되는 순간부터 비용이 시작된다 — LB/프록시가
  Upgrade를 통과시키도록 설정해야 하고, 자동 재연결·유실 복구가 표준에
  없어 **직접 설계**해야 하며(재연결, 하트비트, 놓친 메시지 동기화),
  서버는 수많은 장수 커넥션의 상태를 계속 들고 있어야 한다.

## 2. 선택 기준 — 방향 → 실시간 수준 → 인프라 비용 순으로 판단

비교표는 짧게:

| | 폴링 | SSE | 웹소켓 |
|---|---|---|---|
| 방향 | 클라 → 서버 요청 반복 | 서버 → 클라 단방향 | 양방향 |
| 커넥션 | 요청마다 (짧음) | 장수 커넥션 1개 | 장수 커넥션 1개 |
| 프로토콜 | HTTP | HTTP | 전환(ws) |
| 재연결/복구 | 해당 없음 | 표준 내장 | 직접 구현 |
| 인프라 요구 | 없음 | 낮음 (버퍼링 주의) | 높음 (Upgrade, 타임아웃) |

판단 순서를 갖고 답하는 것이 핵심이다:

1. **먼저 실시간 수준을 되묻는다.** "실시간 알림"이라는 요구가 실제로는
   30초 지연도 무방한 경우가 많다. 그 정도면 **폴링이 정답**이다 —
   가장 싸고, 가장 단순하고, 장애 지점이 가장 적다. 실시간 수단은
   "폴링으로 안 될 때" 올라가는 사다리다.
2. **데이터가 한 방향으로만 흐르는가?** 서버가 밀어주기만 하면 되는
   알림, 진행률 표시, 대시보드 갱신, 새 댓글 스트림은 **SSE로 충분**하다.
   단방향 요구에 웹소켓을 쓰는 것은 재연결·인프라 비용을 공짜로
   떠안는 과잉 설계다.
3. **양방향 + 고빈도인가?** 채팅, 협업 편집, 게임처럼 클라이언트도
   수시로 보내야 하는 경우에만 **웹소켓**을 선택한다.

```text
# 선택 사다리 (아래로 갈수록 비용 증가)
지연 수십 초 허용        → 폴링           (알림 뱃지, 상태 갱신)
서버→클라 단방향 푸시    → SSE            (알림 스트림, 진행률, 대시보드)
양방향 · 고빈도 교환     → 웹소켓          (채팅, 협업 편집, 실시간 게임)
```

"기능상 되는가"가 아니라 "이 요구에 가장 싼 수단이 무엇인가"로 고르는
것이 시니어의 답변이다. 웹소켓으로 셋 다 구현할 수 있지만, 그렇게 하면
필요 없는 곳에서까지 웹소켓의 운영 비용을 지불하게 된다.

## 3. 실무의 함정 — 장수 커넥션은 인프라 전 계층의 문제가 된다

폴링에서 SSE/웹소켓으로 넘어가는 순간, 커넥션의 수명이 "밀리초"에서
"분~시간"으로 바뀐다. 이것이 계층 곳곳에서 문제를 일으킨다.

### ① 중간 계층의 유휴 타임아웃이 커넥션을 끊는다

LB와 리버스 프록시에는 유휴(idle) 타임아웃이 있다(예: 60초). 이벤트가
한동안 없으면 중간 장비가 "죽은 커넥션"으로 판단해 끊어버린다 —
클라이언트 입장에서는 **간헐적으로 연결이 끊기는 유령 현상**이 된다.
대응은 **하트비트**: SSE는 주기적으로 주석 라인(`: ping`)을,
웹소켓은 ping/pong 프레임을 흘려 커넥션이 살아있음을 알린다.
프록시의 타임아웃 설정도 실시간 경로에 맞게 별도로 늘려준다.

### ② 프록시 버퍼링이 SSE를 무력화한다

Nginx 같은 프록시는 기본적으로 업스트림 응답을 **버퍼에 모았다가**
내려보낸다. SSE는 "조각을 즉시 흘리는" 방식이므로 버퍼링되면 이벤트가
한참 뒤에 몰아서 도착한다 — 실시간이 사라진다. SSE 경로는 프록시
버퍼링을 꺼야 한다(`X-Accel-Buffering: no` 응답 헤더 또는
`proxy_buffering off`). 애플리케이션단 gzip 압축 버퍼링도 같은 이유로
주의 대상이다.

### ③ scale-out하는 순간 "누구에게 보낼지"가 분산 문제가 된다 (가산점 포인트)

서버가 1대일 때는 커넥션 목록이 그 서버 메모리에 다 있다. 서버가
3대가 되면 사용자 A의 커넥션은 1번 서버에, 이벤트 발생은 3번 서버에서
일어날 수 있다 — **이벤트를 커넥션이 있는 서버로 전달할 방법**이
필요해진다. 표준 해법은 Redis pub/sub이나 메시지 브로커를 서버들
사이의 전파 채널로 두는 것이다. "웹소켓/SSE 서버는 커넥션이라는 상태를
들고 있는 stateful 서버가 된다"는 점을 짚으면 무상태 확장(7장)과
연결되는 좋은 답변이 된다.

### ④ 스레드 모델 — 커넥션마다 스레드를 물고 있으면 안 된다

전통적인 서블릿의 스레드-퍼-리퀘스트 모델로 장수 커넥션을 다루면
커넥션 수만큼 스레드가 잠긴다. 수천 커넥션이면 스레드 풀이 고갈된다.
SSE/웹소켓 서버는 비동기 I/O 기반(서블릿 비동기, Netty/WebFlux 등)으로
"커넥션은 많이, 스레드는 적게" 유지하는 구조여야 한다.

## 4. 꼬리질문 대비 포인트

### "SSE가 웹소켓보다 나은 경우는 언제인가요?"

데이터가 서버→클라이언트 단방향일 때다. 알림 스트림, 작업 진행률,
대시보드 갱신이 대표적이다. 이때 SSE는 ① HTTP 그대로라 인프라 수정이
거의 없고, ② 자동 재연결과 `Last-Event-ID` 기반 유실 복구가 표준에
내장돼 있어 웹소켓이라면 직접 만들어야 할 것들이 공짜다. 즉 "웹소켓의
기능이 필요 없는데 웹소켓의 비용을 낼 이유가 없다"가 답의 뼈대다.
클라이언트→서버 방향의 간헐적 요청(예: 읽음 처리)은 일반 HTTP API로
보내면 된다 — 양방향이 조금 필요하다고 바로 웹소켓으로 갈 필요는 없다.

### "웹소켓 서버를 scale-out하면 어떤 문제가 생기나요?" (시니어 변별 포인트)

두 가지가 생긴다. ① **메시지 라우팅**: 커넥션이 어느 서버에 붙어있는지와
이벤트가 어느 서버에서 발생하는지가 어긋나므로, Redis pub/sub 같은
전파 채널로 모든(또는 대상) 서버에 이벤트를 브로드캐스트하고 커넥션을
가진 서버가 내려보내는 구조가 필요하다. ② **재배포·장애 시 재연결 폭풍**:
서버 한 대를 내리면 그 서버의 수만 커넥션이 동시에 끊기고 일제히
재연결을 시도한다 — 순간 핸드셰이크 폭주가 나머지 서버를 때린다.
재연결에 지수 백오프+지터를 넣고, 배포는 커넥션을 서서히 빼는(drain)
방식으로 한다. "커넥션 = 서버가 들고 있는 상태"라서 무상태 서버처럼
막 껐다 켤 수 없다는 것이 핵심 인식이다.

### "롱 폴링은 무엇이고, 지금도 쓸 이유가 있나요?"

서버가 새 데이터가 생길 때까지 응답을 보류하는 폴링 변형이다. 일반
폴링보다 실시간성이 좋고 빈 응답 낭비가 적으면서도, 개별 요청-응답이라는
HTTP의 형태를 유지해 호환성이 최고 수준이다. SSE/웹소켓을 막는 아주
보수적인 네트워크 환경(구형 프록시, 엄격한 기업망)의 폴백 수단으로,
또는 실시간 라이브러리들의 최후 폴백 계층으로 여전히 의미가 있다.
단점은 서버가 보류 중인 요청을 계속 물고 있어 비동기 I/O가 아니면
스레드를 잠식한다는 점 — 사실상 장수 커넥션의 부담은 지면서 푸시의
효율은 못 얻는 중간 형태라, 신규 설계에서 1순위로 고를 이유는 적다.

### "LB/프록시 뒤에서 웹소켓·SSE를 쓸 때 확인할 설정은?"

① 웹소켓은 프록시가 `Upgrade`/`Connection` 헤더를 업스트림으로
전달하도록 명시 설정이 필요하다(Nginx 기준 `proxy_http_version 1.1` +
해당 헤더 전달). ② 유휴 타임아웃(`proxy_read_timeout`, LB idle timeout)을
실시간 경로에 맞게 상향하고 하트비트 주기를 그보다 짧게 잡는다.
③ SSE는 프록시 버퍼링을 끈다. ④ L4/L7 LB가 장수 커넥션을 어떻게
분배·정리하는지(커넥션 수 기반 분배인지, drain 지원 여부)를 확인한다.
"앱 코드는 맞는데 중간 계층 설정으로 끊기는" 것이 이 영역 장애의
대부분이라는 점을 언급하면 좋다.

### "폴링이 오히려 정답인 경우를 말해보세요."

① 허용 지연이 폴링 주기보다 크다(예: 1분 내 갱신이면 충분한 뱃지 카운트).
② 클라이언트 수가 적거나 조회 비용이 싸서 낭비가 무시할 수준이다.
③ 이벤트 발생 빈도가 매우 낮아 장수 커넥션 유지 비용이 오히려 더 크다.
④ 인프라 제약(프록시·방화벽)이 장수 커넥션에 적대적이다.
실시간 수단은 요청 수를 줄이는 대신 "커넥션 상태 관리"라는 새 비용을
사는 것이므로, 그 비용이 절약보다 크면 폴링이 합리적 선택이다 —
"단순한 수단으로 충분한 요구에 단순한 수단을 쓰는 것"은 기술 후퇴가
아니라 설계 판단이다.

## 한 줄 요약

폴링은 주기적으로 물어보는 보편-저비용 수단, SSE는 HTTP 위에서 서버가
단방향으로 흘리는 푸시, 웹소켓은 프로토콜을 전환한 양방향 전용선이다 —
선택은 "요구되는 실시간이 실제 몇 초인가"를 되묻는 데서 시작해,
단방향이면 SSE, 양방향 고빈도일 때만 웹소켓으로 올라가되, 장수 커넥션이
LB 타임아웃·프록시 버퍼링·scale-out 시 메시지 전파라는 인프라 비용을
동반한다는 것까지 계산에 넣는 판단이다.
