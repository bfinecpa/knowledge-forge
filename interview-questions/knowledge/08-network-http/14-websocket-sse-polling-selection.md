# 웹소켓 / SSE / 폴링 — 실시간의 세 가지 구현과 "몇 초의 실시간인가"라는 질문

> 핵심 관전 포인트: **셋의 차이는 "누가, 어느 방향으로, 어떤 커넥션 위에서 데이터를 흘리는가"다. 폴링은 클라이언트가 주기적으로 물어보는 방식이라 연결을 유지하지 않고, SSE는 HTTP 응답 본문을 끝내지 않은 채 서버→클라이언트 한 방향으로만 계속 흘리는 방식이며, 웹소켓은 HTTP 요청으로 시작해 `101 Switching Protocols`로 프로토콜을 갈아탄 뒤 그 TCP 연결이 더 이상 HTTP가 아니게 되는 양방향 전용선이다. 이 마지막 사실이 웹소켓 비용의 근원이다 — 중간 프록시가 업그레이드를 이해하지 못하면 연결을 끊고, 자동 재연결·유실 복구가 표준에 없어 직접 만들어야 하며, 그 대가로 SSE에는 `EventSource`의 자동 재연결과 `Last-Event-ID` 기반 재전송이 공짜로 딸려 온다. 선택은 기술 우열이 아니라 판단 순서다 — ① 요구되는 실시간이 실제 몇 초인지 되묻고(수십 초가 허용되면 폴링이 정답), ② 데이터가 한 방향으로만 흐르면 SSE로 충분하며, ③ 양방향 고빈도일 때만 웹소켓의 인프라 비용을 지불한다. 그 인프라 비용의 실체는 넷이다: LB·프록시의 유휴 타임아웃이 장수 커넥션을 끊으므로 하트비트 주기를 경로상 가장 짧은 유휴 상한보다 짧게 잡아야 하고, 프록시 응답 버퍼링이 SSE의 실시간성을 무력화하며, scale-out하는 순간 "이벤트가 난 인스턴스"와 "커넥션이 붙은 인스턴스"가 어긋나 Redis Pub/Sub 같은 백플레인이 필요해지고, 커넥션마다 스레드를 묶는 구현은 수천 커넥션에서 스레드 풀을 고갈시킨다. 여기에 L4 LB가 커넥션 단위로만 분배한다는 성질이 겹치면 장수 커넥션은 스케일 아웃해도 새 인스턴스가 비어 있는 부하 편중까지 만든다.**

## 0. 질문 + 의도

**질문**: "웹소켓과 SSE, 폴링의 차이와 선택 기준은?"

**출제 의도**: 실시간성 요구(댓글, 알림)를 구현 비용·인프라 제약(LB의 장수 커넥션 처리)과 함께 판단하는지를 본다. 기술 스펙 비교 암기가 아니라, "요구사항의 실시간이 진짜 몇 초 수준인지"를 되묻고 가장 싼 수단부터 검토하는 사람인지 — 요구사항을 구현 비용으로 번역하는 능력을 확인하는 질문이다.

## 1. 세 방식의 동작 원리 — 누가 먼저 말을 거는가

### 1-1. 전제 — HTTP는 "물어봐야 답한다"는 규약이다

세 방식이 왜 셋으로 갈리는지 이해하려면 HTTP의 근본 성질부터 짚어야 한다.

HTTP는 **요청-응답(request-response)** 규약이다. 클라이언트가 요청을 하나 보내면 서버가 응답을 하나 돌려주고, 그것으로 한 쌍이 끝난다. **서버가 자기 마음대로 먼저 말을 걸 수단이 규약 안에 없다.** 서버는 "누가 지금 접속해 있는지"조차 요청이 오는 순간에만 안다.

여기서 문제가 생긴다. 알림, 채팅, 실시간 대시보드는 전부 **"서버 쪽에 새 소식이 생겼을 때 클라이언트에게 알려주는"** 일이다. 그런데 서버가 먼저 말을 걸 수 없다면 어떻게 해야 하는가.

논리적으로 답은 셋뿐이다.

1. **클라이언트가 계속 물어본다** — 서버가 말을 못 거니, 듣는 쪽이 반복해서 확인한다. (폴링)
2. **한 번 물어본 응답을 서버가 안 끝낸다** — 요청-응답 규약은 지키되, "응답 하나"를 아주 길게 늘여 그 안에 여러 소식을 이어 붙인다. (SSE)
3. **HTTP를 버린다** — 요청-응답이라는 형태 자체가 문제이므로, HTTP로 연결만 맺고 그 위에서 다른 규약으로 갈아탄다. (웹소켓)

**세 방식은 취향의 문제가 아니라 이 세 갈래에서 하나씩 나온 것**이다. 아래에서 각각을 동작 원리 → 회선 위에서 실제로 오가는 것 → 얻는 것 → 치르는 대가 순서로 본다.

### 1-2. 폴링 — 클라이언트가 반복해서 물어본다

**폴링(polling)**은 클라이언트가 일정 주기로 평범한 HTTP 요청을 보내 "새 소식 있나요?"를 확인하는 방식이다. 이름은 "여론조사(poll)"에서 왔다 — 주기적으로 물어보고 다닌다는 뜻이다.

회선 위에서 벌어지는 일은 이렇다.

```
t=0s    클라이언트 → GET /api/notifications?since=41   HTTP 요청 (완결된 한 쌍)
        서버       → 200 OK  {"items": []}             응답, 연결 정리 가능

t=3s    클라이언트 → GET /api/notifications?since=41   또 한 쌍
        서버       → 200 OK  {"items": []}

t=6s    클라이언트 → GET /api/notifications?since=41
        서버       → 200 OK  {"items": [{"seq":42, ...}]}   ← 이번에야 소식이 있다
```

**얻는 것**은 단순함 그 자체다. 이것은 그냥 HTTP다 — 우리가 매일 만드는 `GET /api/...`와 조금도 다르지 않다. LB, 리버스 프록시, 방화벽, CDN, 회사 보안 게이트웨이 어디를 지나도 특별 취급이 필요 없다. 서버는 상태를 들고 있지 않으므로 인스턴스를 마음대로 늘리고 줄일 수 있고, 배포할 때 커넥션을 신경 쓸 일도 없다. 디버깅도 개발자 도구의 네트워크 탭에서 요청 하나를 클릭하면 끝난다.

**치르는 대가**는 둘이다.

첫째, **변경이 없어도 요청이 발생한다.** 위 예시에서 t=0과 t=3의 요청은 빈 배열을 받아 왔다 — 왕복 두 번과 서버의 조회 두 번이 아무 소득 없이 소모됐다. 사용자 10만 명이 3초 폴링을 하면 서버는 소식이 하나도 없어도 **초당 약 33,000건**의 요청을 받는다. (100,000 ÷ 3 = 33,333)

둘째, **실시간성이 폴링 주기에 묶인다.** 소식이 t=3.1초에 생겨도 클라이언트는 t=6초에야 안다. 평균 지연은 주기의 절반, 최악은 주기 전체다. 3초 폴링이면 평균 1.5초, 최악 3초다.

이 둘이 트레이드오프를 만든다. **주기를 줄이면 실시간성이 좋아지지만 요청 수가 반비례로 늘어난다.** 3초를 1초로 줄이면 지연은 3분의 1이 되지만 초당 요청 수는 33,000에서 100,000으로 세 배가 된다.

### 1-3. 롱 폴링 — 응답을 보류하는 절충안

빈 응답 낭비를 줄이는 변형이 **롱 폴링(long polling)**이다. 서버가 "없어요"를 즉시 응답하지 않고, **새 데이터가 생기거나 정해둔 시간이 지날 때까지 응답을 보류**한다. 클라이언트는 응답을 받는 즉시 다시 요청을 건다.

```
t=0s     클라이언트 → GET /api/notifications?since=41
         서버       ... 응답을 붙들고 대기 (소식이 없으므로 아직 안 보냄)
t=17.4s  ★ 소식 발생
         서버       → 200 OK {"items":[{"seq":42,...}]}    ← 발생 즉시 응답
t=17.4s  클라이언트 → GET /api/notifications?since=42      ← 받자마자 다시 건다
         서버       ... 또 대기
t=47.4s  서버       → 200 OK {"items": []}                 ← 30초 상한에 걸려 빈 응답
t=47.4s  클라이언트 → GET /api/notifications?since=42      ← 다시 건다
```

**얻는 것**: 빈 응답이 "30초에 한 번" 수준으로 줄고, 소식이 생기면 거의 즉시 전달된다. 그러면서도 **개별 요청-응답이라는 HTTP의 형태를 그대로 유지**하므로 호환성은 폴링과 같은 수준이다.

**치르는 대가**: 서버가 **응답 대기 중인 요청을 계속 물고 있어야 한다.** 이 순간부터 "장수 커넥션"의 세계로 들어가는 것이고, 3절의 함정들이 그대로 적용되기 시작한다 — 특히 스레드 모델(3-4)과 중간 계층 타임아웃(3-1)이 그렇다. 사실상 장수 커넥션의 부담은 다 지면서 진짜 푸시의 효율은 못 얻는 중간 형태라서, 신규 설계에서 1순위로 고를 이유는 적다. 대신 SSE·웹소켓이 막히는 보수적인 네트워크 환경의 **폴백 수단**으로서의 값이 크다.

### 1-4. SSE — 서버가 응답을 끝내지 않고 계속 흘린다

#### 동작 원리

**SSE(Server-Sent Events, 서버 전송 이벤트)**는 이름 그대로 "서버가 보내는 이벤트"다. 클라이언트가 요청을 한 번 보내면, 서버는 `Content-Type: text/event-stream`으로 응답을 열고 **응답 본문을 끝내지 않은 채** 이벤트가 생길 때마다 텍스트 조각을 이어서 내려보낸다.

핵심은 "응답을 안 끝낸다"의 의미다. 보통의 HTTP 응답은 `Content-Length`로 길이를 밝히거나 청크 전송으로 마지막 조각을 표시해 **끝을 알린다.** SSE는 그 끝을 영원히 미룬다. 클라이언트 입장에서는 "다운로드가 끝나지 않는 파일 하나"를 계속 읽고 있는 셈이고, 서버는 그 파일에 계속 줄을 덧붙이고 있는 셈이다.

**비유하자면 신문 구독이다.** 폴링은 매일 신문사에 전화를 걸어 "오늘 뉴스 있나요?"를 묻는 것이고, SSE는 한 번 구독 신청을 해두면 뉴스가 생길 때마다 배달원이 알아서 문 앞에 놓고 가는 것이다. 다만 배달은 한 방향이다 — 내가 신문사에 하고 싶은 말이 있으면 별도로 전화를 걸어야 한다.

#### 회선 위에서 실제로 오가는 것

요청은 평범하다.

```http
GET /api/notifications/stream HTTP/1.1
Host: api.example.com
Accept: text/event-stream
Last-Event-ID: 41
```

`Last-Event-ID`는 재연결일 때만 붙는다 — 아래에서 다룬다.

응답 헤더도 평범한 200이다. 특별한 것은 `Content-Type` 하나뿐이다.

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
X-Accel-Buffering: no
```

`Cache-Control: no-cache`는 중간 캐시가 이 스트림을 저장했다가 다음 구독자에게 재생하는 사고를 막는다. `X-Accel-Buffering: no`는 Nginx에게 "이 응답은 버퍼링하지 말고 즉시 흘려라"라고 말하는 헤더인데, 이것이 없으면 3-2절의 사고가 난다.

그리고 본문이 시작된다. **본문은 JSON도 XML도 아닌 SSE 고유의 줄 기반 텍스트 포맷**이다.

```
event: notification
id: 42
data: {"orderId":8471,"message":"결제가 완료되었습니다"}

: ping

event: notification
id: 43
data: {"orderId":8472,"message":"배송이 시작되었습니다"}

retry: 5000

```

포맷의 규칙은 다섯 줄로 끝난다.

| 필드 | 하는 일 |
|---|---|
| `data:` | 이벤트의 본문. 이 줄이 여러 개면 개행으로 이어 붙여 하나의 문자열이 된다 |
| `event:` | 이벤트 이름. 클라이언트가 `addEventListener("notification", ...)`로 골라 받는 근거 |
| `id:` | 이벤트 식별자. **브라우저가 이 값을 기억했다가 재연결 시 `Last-Event-ID` 헤더로 되돌려준다** |
| `retry:` | 연결이 끊겼을 때 몇 밀리초 뒤에 재연결할지. 서버가 클라이언트의 재연결 간격을 조종하는 수단 |
| `:` 로 시작하는 줄 | 주석. 클라이언트는 무시한다 — 그래서 **하트비트로 쓴다**(3-1절) |

그리고 **가장 중요한 규칙**: **빈 줄 하나가 이벤트 하나의 끝**이다. 위 예시에서 `data:` 다음의 빈 줄이 "여기까지가 한 이벤트"라는 신호이고, 그것을 본 브라우저가 그제서야 이벤트를 발생시킨다. 빈 줄을 안 보내면 브라우저는 계속 기다린다 — SSE 구현에서 "서버는 보냈다는데 클라이언트에 아무것도 안 온다"의 흔한 원인 중 하나가 `\n\n`을 `\n` 하나로 쓴 것이다.

#### `EventSource` — 자동 재연결과 `Last-Event-ID`가 표준에 들어 있다

**SSE의 최대 장점은 포맷이 아니라 클라이언트 API에 있다.** 브라우저 표준 API인 `EventSource`가 재연결과 유실 복구를 대신 해준다.

```javascript
const es = new EventSource("/api/notifications/stream");

es.addEventListener("notification", (e) => {
    render(JSON.parse(e.data));
});
// 재연결 코드가 없다. 브라우저가 알아서 한다.
```

이 여섯 줄에 무엇이 들어 있는지가 핵심이다.

**① 연결이 끊기면 브라우저가 자동으로 다시 연결한다.** 앱 코드에 재연결 로직이 한 줄도 없다. 대기 시간은 기본값을 쓰거나, 서버가 `retry:` 필드로 지정한 값을 쓴다.

**② 재연결할 때 마지막으로 받은 `id:` 값을 `Last-Event-ID` 요청 헤더에 실어 보낸다.** 이것이 유실 복구의 열쇠다. 브라우저가 자동으로 하는 일이라 클라이언트 코드가 관여하지 않는다.

이 둘이 합쳐지면 다음 흐름이 성립한다.

```
[서버 인스턴스 A]                          [브라우저]
  id: 41 전송  ────────────────────────────>  받음 (마지막 id = 41 기억)
  id: 42 전송  ────────────────────────────>  받음 (마지막 id = 42 기억)
  ★ 배포로 인스턴스 A 종료, 커넥션 끊김
                                              끊김 감지
  (이 사이 id 43, 44가 발생 — 아무도 못 받음)
                                              retry 값만큼 대기 후 자동 재연결
                                                  |
[서버 인스턴스 B]  <── GET /stream  Last-Event-ID: 42
  "42 이후"를 저장소에서 조회해 43, 44부터 다시 전송
  id: 43 전송  ────────────────────────────>  받음
  id: 44 전송  ────────────────────────────>  받음
```

**웹소켓이라면 이 그림 전체를 직접 만들어야 한다.** 끊김 감지, 백오프를 넣은 재연결 스케줄, "내가 어디까지 받았는지"를 기억하는 클라이언트 상태, 그 값을 서버로 보내는 자체 프로토콜 메시지, 서버 쪽 재전송 로직 — 전부 우리 코드다. SSE는 그중 클라이언트 쪽 절반을 브라우저가 해주고, 우리는 서버 쪽 재전송만 만들면 된다.

다만 **정직하게 짚을 것이 하나 있다.** `Last-Event-ID`가 오더라도 **"그 이후의 이벤트"를 서버가 실제로 갖고 있어야** 재전송이 가능하다. 이벤트를 메모리에서만 만들어 쏘고 버렸다면 되돌려줄 것이 없다. 그래서 유실 복구가 필요한 서비스는 최근 N건(또는 N분)의 이벤트를 사용자별로 보관하는 저장소를 함께 둔다. `EventSource`가 공짜로 주는 것은 **복구의 프로토콜**이지 복구의 데이터가 아니다.

#### 서버 구현 — 서블릿 스택(`SseEmitter`)

```java
// Before: 컨트롤러 안에서 직접 루프를 돌며 흘린다
@GetMapping(value = "/api/notifications/stream", produces = "text/event-stream")
public void streamBad(HttpServletResponse res) throws Exception {
    res.setContentType("text/event-stream");
    PrintWriter w = res.getWriter();
    while (true) {
        // 이 메서드가 반환되지 않는 동안 요청 스레드는 풀로 돌아가지 못한다.
        // 커넥션 1,000개 = 잠긴 톰캣 워커 스레드 1,000개.
        // 기본 스레드 풀이 200이므로 200번째 구독자부터는 아예 접속이 안 된다.
        w.write("data: " + nextEvent() + "\n\n");
        w.flush();
        Thread.sleep(1000);
    }
}
```

```java
// After: SseEmitter를 반환하고 요청 스레드는 즉시 놓아준다
@RestController
@RequiredArgsConstructor
class NotificationStreamController {

    private final EmitterRegistry registry;   // userId -> 열려 있는 emitter 목록
    private final EventStore eventStore;      // Last-Event-ID 재전송용 최근 이벤트 보관소

    @GetMapping(value = "/api/notifications/stream",
                produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public SseEmitter subscribe(
            @AuthenticationPrincipal Long userId,
            // 브라우저가 재연결할 때 자동으로 붙여 보내는 헤더. 최초 접속에는 없다.
            @RequestHeader(value = "Last-Event-ID", required = false) String lastEventId) {

        // 타임아웃을 명시한다. 지정하지 않으면 spring.mvc.async.request-timeout을 따라가는데,
        // 그 값이 짧으면 "아무 이유 없이 30초마다 끊기는 스트림"이 된다.
        // 여기서 지정한 시간이 지나면 onTimeout이 불리고 응답이 정상 종료되며,
        // 브라우저는 이것을 끊김으로 보고 자동 재연결한다 — 의도된 순환이다.
        SseEmitter emitter = new SseEmitter(Duration.ofMinutes(30).toMillis());

        registry.add(userId, emitter);

        // 종료 훅 셋을 반드시 다 건다. 하나라도 빠지면 이미 끊긴 커넥션의 emitter가
        // 레지스트리에 영원히 남아 (a) 메모리 누수, (b) 죽은 커넥션에 send()를 시도하며
        // 매번 IOException을 만드는 비용을 낳는다.
        emitter.onCompletion(() -> registry.remove(userId, emitter));
        emitter.onTimeout(()    -> registry.remove(userId, emitter));
        emitter.onError(e       -> registry.remove(userId, emitter));

        // 재연결이라면 놓친 구간부터 다시 보낸다. 이 코드가 없으면
        // Last-Event-ID 헤더는 그냥 버려지고 유실 복구는 일어나지 않는다.
        if (lastEventId != null) {
            eventStore.findAfter(userId, Long.parseLong(lastEventId))
                      .forEach(e -> send(emitter, e));
        }

        return emitter;   // ★ 여기서 요청 스레드는 풀로 반환된다 (서블릿 비동기)
    }

    private void send(SseEmitter emitter, NotificationEvent e) {
        try {
            emitter.send(SseEmitter.event()
                    .id(String.valueOf(e.seq()))    // → id:    브라우저가 기억할 값
                    .name("notification")           // → event: 클라이언트가 골라 받을 이름
                    .reconnectTime(5000)            // → retry: 끊기면 5초 뒤 재연결하라
                    .data(e.payload()));            // → data:
        } catch (IOException ex) {
            // 이미 끊긴 커넥션이다. 예외를 던져 올릴 일이 아니라 정리 대상이다.
            emitter.completeWithError(ex);
        }
    }
}
```

`return emitter`가 이 코드의 요점이다. 컨트롤러 메서드가 **즉시 반환되고 요청 스레드는 풀로 돌아가지만, HTTP 응답은 아직 끝나지 않은 상태**로 남는다. 이것이 서블릿 3.0의 비동기 요청 처리이고, `SseEmitter`는 그 위에 SSE 포맷을 씌운 것이다. 나중에 다른 스레드가 `emitter.send(...)`를 부르면 그 열린 응답에 조각이 추가된다.

#### 서버 구현 — 리액티브 스택(`Flux<ServerSentEvent>`)

```java
@GetMapping(value = "/api/notifications/stream",
            produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<NotificationPayload>> stream(@AuthenticationPrincipal Long userId) {

    Flux<ServerSentEvent<NotificationPayload>> events =
        notificationSink.asFlux()
            .filter(e -> e.userId().equals(userId))
            .map(e -> ServerSentEvent.<NotificationPayload>builder()
                    .id(String.valueOf(e.seq()))
                    .event("notification")
                    .data(e.payload())
                    .build());

    // 하트비트. 이벤트가 없어도 15초마다 주석 라인(": ping")을 흘려
    // 경로상의 유휴 타이머를 리셋한다 (3-1절). comment()는 data 없는
    // 주석 이벤트를 만드는 것이라 클라이언트 코드는 이것을 보지 못한다.
    Flux<ServerSentEvent<NotificationPayload>> heartbeat =
        Flux.interval(Duration.ofSeconds(15))
            .map(i -> ServerSentEvent.<NotificationPayload>builder()
                    .comment("ping")
                    .build());

    return Flux.merge(events, heartbeat);
}
```

리액티브 쪽이 이 영역에서 유리한 이유는 3-4절에서 다룬다.

#### SSE의 대가

**첫째, 단방향이다.** 클라이언트가 서버로 뭔가 보내려면 별도의 일반 HTTP 요청을 써야 한다. 다만 이것이 항상 단점인 것은 아니다 — 알림을 읽음 처리하는 정도의 간헐적 역방향 요청은 평범한 `POST /api/notifications/42/read` 한 방이면 충분하고, 그게 웹소켓 위에 자체 메시지 규약을 만드는 것보다 단순하다.

**둘째, 텍스트 기반이다.** 이벤트 스트림 포맷은 UTF-8 텍스트 줄들의 나열이므로 이진 데이터를 그대로 실을 수 없다. 굳이 보내려면 Base64로 인코딩해야 하는데 크기가 약 1.33배로 늘어난다.

**셋째, HTTP/1.1에서는 브라우저의 호스트당 동시 연결 수 제한(보통 6개)에 걸린다.** SSE 커넥션 하나가 그 6개 중 하나를 영구히 점유하므로, 같은 도메인에 탭을 여러 개 열면 어느 순간 새 요청이 줄을 서기 시작한다. **HTTP/2에서는 이 문제가 사실상 사라진다** — 멀티플렉싱(하나의 물리 연결에 스트림 ID로 구분되는 여러 논리 통로를 겹쳐 싣는 기법, [09번 문서](09-http1-http2-http3-hol-blocking.md) 2-2 참고) 덕에 SSE 스트림은 연결 하나가 아니라 스트림 하나만 쓰기 때문이다. **"SSE를 쓸 거면 HTTP/2를 켜라"는 실무 권고가 여기서 나온다.**

### 1-5. 웹소켓 — 프로토콜을 갈아타는 양방향 전용선

#### 동작 원리와 프로토콜 업그레이드

**프로토콜 업그레이드(protocol upgrade)**는 HTTP가 스스로를 위해 마련해 둔 탈출구다. **"지금 맺어져 있는 이 TCP 연결을 유지한 채, 이 위에서 말하는 규약만 다른 것으로 바꾸자"**고 합의하는 절차다. 연결을 새로 맺는 것이 아니라 **이미 맺어진 연결의 용도를 바꾸는 것**이 핵심이다.

왜 이런 방식을 택했는지 짚고 가면 이해가 쉽다. 웹소켓 전용 포트를 새로 뚫는 방법도 있었지만, 그러면 회사 방화벽과 프록시가 그 포트를 막아둔 환경에서 아예 못 쓴다. **80/443 포트에 HTTP로 들어가서 안에서 갈아타면 기존 인프라를 그대로 통과할 수 있다** — 적어도 이론상으로는. (실제로는 3-1절과 3-2절의 문제가 남는다.)

#### 회선 위에서 실제로 오가는 것

클라이언트가 보내는 것은 **평범한 GET 요청처럼 생긴 핸드셰이크**다.

```http
GET /ws/chat HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://app.example.com
```

네 헤더가 각자 역할을 한다.

- **`Upgrade: websocket`** — "웹소켓으로 갈아타고 싶다"는 요청.
- **`Connection: Upgrade`** — `Upgrade` 헤더가 **홉 단위(hop-by-hop) 헤더**, 즉 다음 중계 지점까지만 유효하고 그 너머로 전달되지 않는 헤더임을 선언한다. 프록시는 이 헤더를 보고 "업그레이드 협상은 나와 상대 사이의 일이지 그냥 통과시킬 것이 아니다"를 안다. **3-1절에서 Nginx 설정 두 줄이 필요한 이유가 정확히 이 성질 때문**이다.
- **`Sec-WebSocket-Key`** — 클라이언트가 만든 16바이트 난수를 Base64로 인코딩한 값. 보안용이 아니다. 서버가 이 값을 규정된 방식으로 변환해 돌려줘야 하므로, **"응답한 상대가 웹소켓을 진짜로 이해하고 의도적으로 승낙한 것"임을 확인하는 장치**다. 웹소켓을 모르는 캐시 서버가 어쩌다 200을 돌려주는 사고를 걸러낸다.
- **`Sec-WebSocket-Version: 13`** — 현재 표준 버전.

서버가 승낙하면 **`101 Switching Protocols`**로 답한다.

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

`Sec-WebSocket-Accept`는 클라이언트가 보낸 키에 표준이 정한 고정 문자열을 붙여 SHA-1 해시를 구하고 Base64로 인코딩한 값이다. 클라이언트는 자기가 보낸 키로 같은 계산을 해보고 값이 맞는지 확인한다.

**그리고 이 응답 이후의 모든 바이트는 HTTP가 아니다.**

이 문장이 웹소켓 이해의 분기점이다. 그림으로 보면 이렇다.

```
[하나의 TCP 연결]

 ├─ 101 이전 ────────────────────────────────────────────────
 │    HTTP/1.1 텍스트. 헤더가 있고, 요청-응답 한 쌍의 형태를 지킨다.
 │    중간 프록시가 읽고 해석하고 로그를 남기고 라우팅할 수 있다.
 │
 ├─ 101 Switching Protocols  ★ 여기가 경계선
 │
 └─ 101 이후 ────────────────────────────────────────────────
      웹소켓 프레임. HTTP 헤더도, 상태 코드도, 요청-응답 쌍도 없다.
      양쪽이 각자 원할 때 프레임을 보낸다 (full-duplex, 전이중).
      HTTP만 아는 중간 장비 입장에서는 "해석 불가능한 바이트 흐름"이다.
```

**중간 프록시가 이 연결을 이해하지 못하면 끊는다.** HTTP 프록시는 "요청 하나 받고 응답 하나 돌려주면 이 요청은 끝"이라는 모델로 만들어져 있으므로, 응답이 끝나지 않고 정체불명의 바이트가 양방향으로 흐르는 상황을 정상으로 보지 않는다. 그래서 웹소켓을 쓰려면 **경로상의 모든 중간 장비가 업그레이드를 인지하고 그 연결을 순수한 TCP 터널로 통과시키도록 설정해야 한다.** 3-1절의 Nginx 두 줄이 하는 일이 바로 이것이다.

#### 프레임 — 웹소켓이 회선 위에 쓰는 단위

101 이후로 오가는 것은 **프레임(frame)**이다. HTTP/2의 프레임과 같은 발상이다 — 가변 길이 데이터에 길이와 종류를 붙여 "여기부터 여기까지가 한 조각"을 정한다.

프레임 헤더에 담긴 것 중 실무에서 알아야 할 것은 셋이다.

**opcode(연산 부호)** — 이 프레임이 무엇인지 나타내는 번호다. 텍스트 메시지, 이진 메시지, 그리고 **제어 프레임인 ping / pong / close**가 있다. **ping과 pong이 프로토콜에 내장돼 있다는 점이 SSE와의 결정적 차이**다. SSE는 하트비트를 주석 라인이라는 편법으로 흉내 내지만, 웹소켓은 "살아 있냐"를 묻고 답하는 전용 프레임을 갖고 있다.

**FIN 비트** — 큰 메시지를 여러 프레임으로 쪼개 보낼 수 있는데, 마지막 조각인지 표시한다.

**마스킹(masking)** — 클라이언트가 서버로 보내는 프레임은 반드시 32비트 난수 키로 페이로드를 XOR 마스킹해야 한다. 암호화가 아니다(키가 프레임 안에 그대로 들어 있다). 목적은 **중간의 낡은 캐시 프록시를 속여 공격하는 것을 막는 것**이다 — 마스킹이 없으면 공격자가 웹소켓 프레임 안에 HTTP 요청처럼 생긴 바이트열을 심어 프록시가 그것을 별개의 요청으로 오인하게 만들 수 있었다. 서버→클라이언트 방향은 마스킹하지 않는다.

#### 웹소켓이 얻는 것

**진짜 양방향이다.** 클라이언트와 서버가 각자 원할 때 메시지를 보낸다. 채팅에서 "내가 보내는 메시지"와 "상대가 보낸 메시지"가 같은 연결 위를 반대 방향으로 흐른다.

**메시지 하나당 오버헤드가 작다.** HTTP 요청은 매번 헤더 수백 바이트~수 KB(쿠키, `User-Agent`, `Accept` 등)를 끌고 다니지만, 웹소켓 프레임 헤더는 몇 바이트다. **초당 수십 건씩 짧은 메시지를 주고받는 상황**에서 이 차이가 커진다. 협업 편집기의 커서 위치, 실시간 호가, 게임의 조작 입력처럼 "작고 잦은" 트래픽이 웹소켓의 본령이다.

#### 웹소켓이 치르는 대가

**첫째, HTTP가 아니게 되는 순간부터 인프라 비용이 시작된다.** LB와 프록시가 업그레이드를 통과시키도록 설정해야 하고, HTTP 단위로 동작하는 L7 기능들(경로 기반 라우팅, 요청 단위 접근 로그, HTTP 상태 코드 기반 모니터링, WAF의 요청 검사)이 101 이후로는 적용되지 않는다. **"HTTP 요청 수"나 "5xx 비율" 같은 평소의 지표로는 웹소켓 트래픽의 건강 상태를 볼 수 없다** — 별도의 관측 수단을 만들어야 한다.

**둘째, 재연결과 유실 복구가 표준에 없다.** 브라우저의 `WebSocket` API는 끊기면 `onclose`를 부르고 끝이다. 자동 재연결이 없다. 그래서 우리가 만들어야 하는 것이 최소 넷이다 — 끊김 감지, 지수 백오프와 지터를 넣은 재연결 스케줄(3-5절), "어디까지 받았는지"를 서버에 알리는 자체 프로토콜 메시지, 그리고 서버 쪽 재전송 로직. SSE에서 브라우저가 공짜로 해주던 절반이 전부 우리 몫이 된다.

**셋째, 서버가 상태를 들고 있는 stateful 서버가 된다.** 커넥션 목록이 인스턴스 메모리에 있으므로 아무 인스턴스나 껐다 켤 수 없고, scale-out하면 3-3절의 분산 문제가 생긴다.

## 2. 선택 기준 — 방향 → 실시간 수준 → 인프라 비용

### 2-1. 판단의 흐름

기술 스펙을 비교해서 고르는 것이 아니다. **질문을 순서대로 던져 내려가면 답이 나오는 구조**다.

```
              "실시간 알림이 필요합니다"
```

각 분기에서 무엇을 묻고 있는지 하나씩 풀어 보자.

### 2-2. Q1: "실시간"이라는 말이 실제로 몇 초를 뜻하는가

**이 질문을 되묻는 것이 이 답변 전체의 출발점이다.**

"실시간 알림이 필요하다"는 요구는 기획서에 자주 등장하지만, **그 문장 안에 허용 지연이 적혀 있는 경우는 거의 없다.** 그리고 실제로 파고들어 보면 요구되는 지연이 훨씬 느슨한 경우가 많다.

- "새 댓글 알림" → 사용자가 30초 뒤에 알아도 아무 문제가 없다. 사람이 화면을 계속 보고 있지도 않다.
- "주문 상태 뱃지" → 1분 주기 갱신이면 충분하다. 사용자는 그 화면에 몇 분씩 머물지 않는다.
- "결제 진행률 표시" → 여기는 몇 초 단위가 필요하다. 사용자가 화면을 응시하며 기다리고 있다.
- "채팅" → 1초를 넘으면 대화가 안 된다.

**허용 지연이 폴링 주기보다 크면 폴링이 정답이다.** 이것은 기술 후퇴가 아니라 설계 판단이다. 3초 폴링으로 충분한 요구에 웹소켓을 쓰면 다음을 전부 새로 지불한다 — 프록시·LB의 업그레이드 설정, 하트비트 설계, 재연결·백오프 클라이언트 코드, 유실 복구 프로토콜, scale-out용 백플레인, 배포 시 커넥션 드레인 절차, 그리고 HTTP 지표로 안 보이는 트래픽을 위한 별도 관측. **얻는 것은 "지연 3초가 지연 0.1초가 되는 것" 하나뿐인데, 사용자는 그 차이를 인지하지도 못한다.**

반대 방향의 계산도 해야 한다. 폴링의 비용은 **동시 접속자 수 ÷ 폴링 주기**로 나오는 초당 요청 수다.

```
동시 접속 1,000명, 5초 폴링   → 1,000 ÷ 5   =    200 req/s   (평범한 서버 한 대로 충분)
동시 접속 10,000명, 3초 폴링  → 10,000 ÷ 3  ≈  3,333 req/s   (조회가 싸다면 아직 감당 가능)
동시 접속 100,000명, 3초 폴링 → 100,000 ÷ 3 ≈ 33,333 req/s   (여기서부터는 다시 계산해야 한다)
```

여기서 갈리는 것은 요청 수 자체보다 **요청 하나의 조회 비용**이다. 조회가 캐시 히트로 끝나는 값싼 것이면 33,000 req/s도 감당할 수 있다. 반면 매 요청이 DB 조인 쿼리를 때린다면 3,000 req/s에서도 이미 위험하다. 그러므로 **"폴링이 비싸다"가 아니라 "폴링 주기 × 조회 비용이 감당 가능한가"로 물어야** 정확하다.

### 2-3. Q2: 데이터가 어느 방향으로 흐르는가

Q1을 통과했다면(수 초 이내가 정말 필요하다면) 다음 질문은 방향이다.

**서버가 밀어주기만 하면 되는 것**이 압도적으로 많다. 알림 스트림, 작업 진행률, 대시보드 지표 갱신, 새 댓글 스트림, 경매 현재가 표시, 배포 로그 tail. 이 전부가 SSE로 충분하다.

**단방향 요구에 웹소켓을 쓰는 것은 필요 없는 비용을 공짜로 떠안는 것**이다. 1-5절에서 본 세 가지 대가를 전부 내면서, 웹소켓이 주는 유일한 추가 능력(클라이언트가 아무 때나 보내기)은 쓰지 않는다. 게다가 SSE가 공짜로 주던 자동 재연결과 `Last-Event-ID` 복구까지 스스로 만들어야 하므로, **기능은 그대로인데 만들 것만 늘어난다.**

### 2-4. Q3: 역방향이 정말 고빈도인가

"클라이언트도 뭔가 보내야 하는데요"라는 반문이 여기서 나온다. 그때 물을 것은 **빈도**다.

알림을 읽음 처리하는 것, 대시보드의 필터를 바꾸는 것, 구독 대상을 변경하는 것 — 이런 것은 **사용자가 클릭할 때 한 번**이다. 분당 몇 건 수준이다. 이 정도는 평범한 `POST /api/notifications/42/read` 한 방으로 처리하는 것이, 웹소켓 위에 "이 메시지는 읽음 처리 요청이다"를 표현하는 자체 메시지 규약을 만들고 그것을 라우팅하는 서버 코드를 짜는 것보다 단순하다. **HTTP API는 이미 인증, 로깅, 에러 처리, 재시도, 모니터링이 다 갖춰져 있는 길이고, 웹소켓 메시지는 그 전부를 새로 만드는 길**이다.

반대로 채팅, 협업 편집(커서 위치와 편집 조작이 초당 여러 번), 실시간 게임, 실시간 호가 입력처럼 **역방향 메시지가 초 단위로 계속 나가는** 경우에만 웹소켓이 값을 한다. 이때는 매 메시지에 HTTP 헤더를 붙이는 오버헤드와 요청마다의 처리 비용이 실제로 부담이 되기 때문이다.

### 2-5. 정리 대조표

위 설명을 이미 읽었다는 전제로 한눈에 대조만 한다.

| 방향 | 클라 요청 반복 | 클라 요청 반복(보류) | 서버 → 클라 단방향 | 양방향 |

| 프로토콜 | HTTP | HTTP | HTTP (`text/event-stream`) | 101 이후 웹소켓 프레임 |

## 3. 실무의 함정 — 장수 커넥션은 인프라 전 계층의 문제가 된다

폴링에서 SSE나 웹소켓으로 넘어가는 순간, 커넥션의 수명이 **밀리초에서 분·시간 단위로** 바뀐다. 이 한 가지 변화가 경로상의 모든 계층에서 문제를 일으킨다. 아래 다섯 가지는 전부 같은 뿌리에서 나온다.

### 3-1. 중간 계층의 유휴 타임아웃이 커넥션을 끊는다

#### 왜 끊는가

경로상의 모든 중간 장비 — 클라우드 LB, Nginx, 회사 방화벽, NAT 게이트웨이 — 는 **유휴(idle) 타임아웃**을 갖고 있다. "이 커넥션으로 아무 바이트도 안 오간 지 N초가 지났으면 죽은 것으로 보고 정리한다"는 규칙이다.

이 규칙 자체는 합리적이다. 중간 장비는 커넥션마다 상태(NAT 매핑 테이블의 항목, 프록시의 버퍼)를 들고 있는데, 클라이언트가 노트북을 덮거나 지하철에서 신호가 끊기면 **FIN이 오지 않은 채 그냥 사라진다.** 그런 유령 커넥션을 청소하지 않으면 테이블이 가득 찬다. 그래서 시간으로 끊는다.

문제는 **정상적인 SSE·웹소켓 커넥션이 이 규칙에 걸린다**는 것이다. 알림 서비스에서 이벤트가 5분 동안 없는 것은 지극히 정상인데, 중간 장비 입장에서는 5분 동안 조용한 커넥션과 죽은 커넥션이 구분되지 않는다.

```
Nginx의 proxy_read_timeout 기본값 = 60초

t =   0s   웹소켓 핸드셰이크 성공, 채팅방 입장
t =  10s   메시지 몇 개 오감
t =  70s   조용한 채팅방. 60초간 무통신.
           ★ Nginx가 업스트림 응답 대기 상한 초과로 판단해 연결을 끊는다.
t =  70s   브라우저: onclose 발생. 사용자는 아무것도 안 했는데 연결이 끊겼다.
           서버 로그에는 정상 종료로만 남는다.
```

증상은 **"1분쯤 가만히 두면 연결이 끊긴다"**는 재현 가능한 패턴으로 나타나기도 하고, 계층마다 값이 달라 **"간헐적으로 끊긴다"**는 유령 현상으로 나타나기도 한다.

#### 대응 ① — 하트비트로 커넥션을 살려둔다

**하트비트(heartbeat, 심장 박동)**는 보낼 데이터가 없어도 주기적으로 의미 없는 바이트를 흘려 "나 살아 있다"를 알리는 기법이다. 중간 장비의 유휴 타이머는 **바이트가 오가면 리셋되므로**, 주기적으로 뭔가를 흘리면 타이머가 만료에 도달하지 못한다.

SSE는 **주석 라인**을 쓴다. `:`로 시작하는 줄은 클라이언트가 무시하므로, 애플리케이션 로직에 영향을 주지 않으면서 바이트만 흘릴 수 있다.

```java
// SseEmitter 스택의 하트비트: 스케줄러가 열려 있는 모든 emitter에 주석을 흘린다
@Scheduled(fixedRate = 15_000)
public void heartbeat() {
    for (SseEmitter emitter : registry.all()) {
        try {
            // comment()는 ": ping\n\n"을 내보낸다. 클라이언트는 이것을 보지 못하지만
            // 경로상의 모든 중간 장비의 유휴 타이머는 이 바이트로 리셋된다.
            emitter.send(SseEmitter.event().comment("ping"));
        } catch (IOException e) {
            // ★ 하트비트의 두 번째 값: 죽은 커넥션이 여기서 드러난다.
            //   보내보기 전에는 커넥션이 살았는지 알 방법이 없다 (10번 문서 3-3절과 같은 원리).
            emitter.completeWithError(e);
        }
    }
}
```

웹소켓은 **ping/pong 제어 프레임**을 쓴다. 프로토콜에 내장돼 있어 애플리케이션 메시지와 섞이지 않는다.

```java
// Spring WebSocket: 세션마다 주기적으로 ping 프레임을 보낸다
@Scheduled(fixedRate = 20_000)
public void ping() {
    ByteBuffer payload = ByteBuffer.wrap(new byte[0]);
    for (WebSocketSession session : sessionRegistry.all()) {
        if (!session.isOpen()) { sessionRegistry.remove(session); continue; }
        try {
            session.sendMessage(new PingMessage(payload));
            // 상대가 pong을 돌려주지 않으면 그 커넥션은 죽은 것이다.
            // pong 수신 시각을 기록해두고, 일정 시간 이상 pong이 없으면
            // 서버가 먼저 세션을 닫아 좀비 커넥션을 정리한다.
        } catch (IOException e) {
            sessionRegistry.remove(session);
        }
    }
}
```

STOMP를 얹었다면 프레임워크가 대신 해준다.

```java
@Configuration
@EnableWebSocketMessageBroker
class WebSocketConfig implements WebSocketMessageBrokerConfigurer {

    @Override
    public void configureMessageBroker(MessageBrokerRegistry registry) {
        registry.enableSimpleBroker("/topic")
                // {서버가 보내는 주기, 서버가 클라이언트에게 기대하는 주기} 밀리초.
                // 양쪽 모두 지정해야 어느 방향으로도 유휴가 생기지 않는다.
                .setHeartbeatValue(new long[]{15_000, 15_000})
                // 하트비트를 흘릴 스케줄러. 지정하지 않으면 하트비트가 동작하지 않는다.
                .setTaskScheduler(heartbeatScheduler());
    }
}
```

#### 대응 ② — 주기를 어떻게 정하는가

**하트비트 주기는 경로상 가장 짧은 유휴 상한보다 짧아야 한다.** 한 곳이라도 우리 하트비트보다 먼저 만료되는 장비가 있으면 그 장비가 커넥션을 끊는다.

```
경로:  브라우저 ── [클라우드 LB] ── [Nginx] ── [앱]
                    유휴 60초       proxy_read_timeout 60초

  가장 짧은 유휴 상한 = 60초
  → 하트비트 주기는 이보다 확실히 짧게. 여유를 봐서 절반 이하인 15~20초.

  왜 "조금만" 짧으면 안 되는가:
    · 하트비트 한 번이 유실되거나 지연되면 다음 하트비트까지 2주기가 벌어진다.
      55초 주기라면 한 번만 밀려도 110초 → 60초 상한 초과 → 끊김.
    · 스케줄러 지연, GC 정지, 스레드 풀 대기가 실제로 몇 초씩 밀 수 있다.
    · 그러므로 "상한의 절반 이하"가 실무 기준이 된다.
```

**이 논리는 [10번 문서](10-keepalive-connection-pool-time-wait.md) 3-3절의 "재사용하는 쪽의 유휴 상한을 닫는 쪽보다 짧게"와 정확히 같은 구조다.** 그쪽은 "상대가 끊기 전에 내가 먼저 정리한다"였고, 이쪽은 "상대가 끊기 전에 내가 먼저 살려낸다"다. **둘 다 "타이머 만료를 상대에게 맡기지 말고 내가 통제한다"는 하나의 원칙**에서 나온다. 이 연결을 면접에서 말할 수 있으면 좋다.

#### 대응 ③ — 실시간 경로만 타임아웃을 늘린다

하트비트를 걸어도 중간 계층의 상한을 실시간 경로에 맞게 조정해 두는 것이 안전하다. 다만 **전역으로 늘리면 안 된다** — 일반 API 경로까지 상한이 길어지면 느린 요청이 커넥션과 스레드를 오래 붙들게 허용하는 셈이 된다.

```nginx
# 일반 API 경로: 기본값을 유지한다
location /api/ {
    proxy_pass http://app;
    proxy_read_timeout 60s;
}

# 실시간 경로만 따로 잡는다
location /api/notifications/stream {
    proxy_pass http://app;
    proxy_read_timeout 3600s;   # 하트비트가 있어도 여유를 둔다
    proxy_send_timeout 3600s;
    proxy_buffering off;        # 3-2절
}
```

클라우드 LB의 유휴 타임아웃도 함께 확인한다. Nginx만 늘리고 그 앞의 LB를 그대로 두면 **LB가 먼저 끊으므로 아무 효과가 없다.** 경로상 가장 짧은 값이 실질 상한이라는 점은 [13번 문서](13-nginx-tomcat-timeout-buffer-mismatch.md)의 계층 정렬 원칙과 같다.

### 3-2. 프록시 버퍼링이 SSE를 무력화한다

#### 왜 버퍼링이 있는가

Nginx는 기본적으로 업스트림(뒤쪽 서버) 응답을 **버퍼에 모았다가** 클라이언트에게 내려보낸다(`proxy_buffering on`이 기본값). 이것은 훌륭한 기본값이다 — 느린 클라이언트가 응답을 다 받을 때까지 Tomcat 스레드가 붙들려 있는 것을 막아주기 때문이다([12번 문서](12-nginx-roles-and-event-driven-architecture.md) 2절). Tomcat은 빠른 로컬 네트워크로 Nginx에게 응답을 던지고 즉시 스레드를 놓아주고, 느린 클라이언트를 상대하는 일은 Nginx가 맡는다.

#### 왜 SSE에서는 재앙인가

SSE의 존재 이유는 **"조각을 생기는 즉시 흘리는 것"**이다. 버퍼링은 정확히 그 반대로 **"조각을 모았다가 한꺼번에 흘리는 것"**이다. 목적이 정면으로 충돌한다.

```
[proxy_buffering on 인 상태의 SSE]

  앱   → Nginx:  "event: notification\nid: 42\ndata: {...}\n\n"   (t=0s)
  Nginx:         버퍼에 담는다. 버퍼가 아직 안 찼으므로 안 내보낸다.
  앱   → Nginx:  "...id: 43..."                                    (t=12s)
  Nginx:         버퍼에 담는다. 아직 안 찼다.
  앱   → Nginx:  "...id: 44..."                                    (t=31s)
  Nginx:         버퍼가 찼다! → 42, 43, 44를 한꺼번에 클라이언트로

  결과: 브라우저는 t=31초에 이벤트 세 개를 몰아서 받는다.
        42번은 31초 늦게 도착한 것이다. 실시간이 사라졌다.

  더 나쁜 경우: 이벤트가 드문 서비스라면 버퍼가 몇 분 동안 안 차고,
        그 사이 3-1절의 유휴 타임아웃이 먼저 터진다 —
        "SSE가 아예 동작하지 않는다"로 보인다.
```

증상이 고약한 이유는 **로컬 개발 환경에서는 재현되지 않는다**는 것이다. 로컬에서는 앱에 직접 붙으므로 Nginx가 없다. 스테이징이나 운영에 올려야 처음 드러난다.

#### 대응 — 두 가지 방법

인프라 쪽에서 끄는 방법과 앱이 선언하는 방법이 있다.

```nginx
# 방법 ①: 인프라 설정 — 실시간 경로만 버퍼링을 끈다
location /api/notifications/stream {
    proxy_pass http://app;
    proxy_buffering off;        # 받는 즉시 클라이언트로 흘린다
    proxy_cache off;            # 캐시가 스트림을 저장하는 사고도 막는다
    proxy_read_timeout 3600s;
    proxy_http_version 1.1;     # 청크 전송을 쓰려면 1.1이 필요하다
}
```

```java
// 방법 ②: 앱이 응답 헤더로 선언한다 — 인프라 설정 변경 없이 앱 배포만으로 적용된다
@GetMapping(value = "/api/notifications/stream",
            produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public ResponseEntity<SseEmitter> subscribe(...) {
    return ResponseEntity.ok()
            // Nginx가 이 헤더를 보면 해당 응답만 버퍼링을 끈다.
            // 인프라 팀에 설정 변경을 요청하지 않아도 되므로 협업 비용이 낮다.
            .header("X-Accel-Buffering", "no")
            .header("Cache-Control", "no-cache")
            .body(emitter);
}
```

**전역으로 `proxy_buffering off`를 하면 안 된다.** 그것은 모든 응답에서 느린 클라이언트 격리 효과를 버리는 것이고, Tomcat 스레드가 전송 속도에 묶이게 만든다. 반드시 경로 단위로 한다.

같은 이유로 **응답 압축(gzip)도 실시간 경로에서는 주의 대상**이다. 압축기는 효율을 위해 입력을 일정량 모았다가 압축하므로 그 자체가 또 하나의 버퍼가 된다. 압축을 쓰려면 이벤트마다 압축 스트림을 플러시해야 하는데, 그러면 압축률이 크게 떨어져 얻는 것이 별로 없다. **실시간 경로는 압축을 끄는 것이 보통이다.** ([21번 문서](21-response-compression-tradeoffs.md)와 같은 판단 축이다.)

### 3-3. scale-out하는 순간 "누구에게 보낼지"가 분산 문제가 된다 (시니어 변별 포인트)

#### 문제의 발생

서버가 1대일 때는 아무 문제가 없다. 사용자 A의 커넥션이 그 서버의 메모리에 있고, 이벤트도 그 서버에서 발생하므로 `registry.get(userId).send(...)` 한 줄이면 끝난다.

**서버가 3대가 되는 순간 이 가정이 깨진다.**

```
[Before: 아무 대응이 없는 상태]

  사용자 A의 브라우저
        |
        | SSE 커넥션 (LB가 인스턴스 1로 배정)
        v
  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │ 인스턴스 1    │   │ 인스턴스 2    │   │ 인스턴스 3    │
  │ registry:    │   │ registry:    │   │ registry:    │
  │  A → emitter │   │  (비어 있음)  │   │  (비어 있음)  │
  └──────────────┘   └──────────────┘   └──────────────┘
                            ^
                            |
                    ★ 사용자 A에 대한 주문 완료 이벤트가
                      여기서 발생한다 (LB가 이 API 요청을
                      인스턴스 2로 배정했으므로)

  인스턴스 2:  registry.get(A) → 없음 → 아무것도 못 보낸다
  결과: 알림이 조용히 사라진다. 에러도 안 난다. 로그에도 안 남는다.
```

**이것이 무상태 서버와 stateful 서버의 갈림길이다.** 평범한 REST API 서버는 무상태라서 어느 인스턴스가 요청을 처리해도 결과가 같다. 반면 SSE·웹소켓 서버는 **커넥션이라는 상태를 메모리에 들고 있으므로**, "그 상태를 가진 인스턴스"가 특정된다. 7장의 무상태 서버 설계([07-traffic-performance/04](../07-traffic-performance/04-stateless-server-design-and-session.md))가 세션을 외부 저장소로 빼서 푼 문제와 같은 종류인데, **커넥션은 세션과 달리 외부 저장소로 뺄 수가 없다** — 살아 있는 TCP 소켓은 그 프로세스 안에만 존재하기 때문이다.

그래서 해법의 방향이 달라진다. **상태를 옮기는 대신, 이벤트를 상태가 있는 곳으로 배달한다.**

#### 해법 — 백플레인(backplane)

**백플레인**은 원래 여러 장비를 꽂아 서로 통신하게 해주는 뒷면 기판을 뜻하는데, 여기서는 **모든 인스턴스가 공유하는 이벤트 전파 채널**을 가리킨다. 이벤트가 어느 인스턴스에서 발생하든 일단 백플레인에 던지고, **모든 인스턴스가 그것을 받아 자기가 들고 있는 커넥션에만 흘린다.**

```
[After: Redis Pub/Sub 백플레인]

  사용자 A의 브라우저
        ^
        | SSE
  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │ 인스턴스 1    │   │ 인스턴스 2    │   │ 인스턴스 3    │
  │ registry:    │   │ registry:    │   │ registry:    │
  │  A → emitter │   │  (비어 있음)  │   │  (비어 있음)  │
  └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
         │ 구독              │ 구독 + 발행       │ 구독
         └──────────┬────────┴──────────────────┘
                    v
         ┌──────────────────────┐
         │  Redis 채널          │
         │  "notifications"     │
         └──────────────────────┘

  ① 인스턴스 2에서 이벤트 발생 → 채널에 PUBLISH
  ② Redis가 구독 중인 세 인스턴스 전부에게 전달
  ③ 각 인스턴스가 자기 registry를 확인:
       인스턴스 1: A가 있다 → emitter로 흘린다 ✓
       인스턴스 2: 없다 → 버린다
       인스턴스 3: 없다 → 버린다
```

**요점은 발행하는 쪽이 "누가 그 커넥션을 갖고 있는지"를 몰라도 된다는 것**이다. 그냥 전부에게 뿌리고, 아는 놈이 처리한다. 이 단순함이 이 구조의 값이다.

```java
// 발행 측: 이벤트가 발생한 인스턴스는 커넥션 보유 여부와 무관하게 무조건 채널로 던진다
@Service
@RequiredArgsConstructor
class NotificationPublisher {

    private final StringRedisTemplate redis;
    private final ObjectMapper mapper;

    public void publish(NotificationEvent event) {
        try {
            // 이 인스턴스에 해당 사용자의 커넥션이 있는지 확인하지 않는다.
            // 확인하려면 "누가 어디 붙어 있는지"라는 또 하나의 분산 상태가 필요해지고,
            // 그 상태는 커넥션이 끊길 때마다 갱신돼야 해서 관리 비용이 커진다.
            // 그냥 전부에게 뿌리는 편이 훨씬 단순하다.
            redis.convertAndSend("notifications", mapper.writeValueAsString(event));
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("이벤트 직렬화 실패", e);
        }
    }
}
```

```java
// 구독 측: 모든 인스턴스가 같은 채널을 구독하고, 자기가 가진 커넥션에만 흘린다
@Configuration
@RequiredArgsConstructor
class RedisFanoutConfig {

    @Bean
    RedisMessageListenerContainer notificationContainer(
            RedisConnectionFactory connectionFactory,
            NotificationRelayListener listener) {

        RedisMessageListenerContainer container = new RedisMessageListenerContainer();
        container.setConnectionFactory(connectionFactory);
        container.addMessageListener(listener, new ChannelTopic("notifications"));
        return container;
    }
}

@Component
@RequiredArgsConstructor
class NotificationRelayListener implements MessageListener {

    private final EmitterRegistry registry;
    private final ObjectMapper mapper;

    @Override
    public void onMessage(Message message, byte[] pattern) {
        NotificationEvent event = deserialize(message.getBody());

        // 이 인스턴스에 붙어 있는 커넥션만 조회한다. 없으면 조용히 버린다 —
        // 다른 인스턴스가 갖고 있을 것이므로 여기서 에러를 낼 일이 아니다.
        for (SseEmitter emitter : registry.get(event.userId())) {
            try {
                emitter.send(SseEmitter.event()
                        .id(String.valueOf(event.seq()))
                        .name("notification")
                        .data(event.payload()));
            } catch (IOException e) {
                emitter.completeWithError(e);
            }
        }
    }
}
```

#### Redis Pub/Sub의 성질과 한계

**Redis Pub/Sub은 fire-and-forget이다** — 발행한 메시지를 저장하지 않고, 그 순간 구독 중인 클라이언트에게만 전달하고 버린다. 이 성질이 장점이자 한계다.

**장점**: 극단적으로 단순하고 빠르다. 저장하지 않으므로 디스크도 안 쓰고, 컨슈머 그룹이나 오프셋 관리 같은 개념이 아예 없다. Redis를 이미 쓰고 있다면 추가 인프라가 0이다.

**한계**: **인스턴스가 잠깐이라도 Redis와 끊겨 있으면 그동안 발행된 메시지를 영영 못 받는다.** 재시작 중인 인스턴스, 네트워크 순단, Redis 페일오버 순간이 전부 유실 구간이다. 그리고 알림 그 자체는 유실되면 안 되는 데이터인 경우가 많다.

**그래서 실무의 정석은 두 경로를 분리하는 것이다.**

```
[영속 경로]  이벤트 발생 → DB에 알림 레코드 INSERT (진실의 원천)
                              ↓
[전파 경로]                Redis PUBLISH → 붙어 있는 커넥션에 즉시 전달 (편의)

  · 전파가 유실돼도 알림 자체는 DB에 남아 있다.
  · 사용자가 새로고침하거나 재연결하면 DB에서 조회해 복구된다.
  · Last-Event-ID 재전송의 데이터 출처도 이 DB다.
  · 즉 Redis Pub/Sub은 "빠르게 보이게 하는 수단"이지 "전달을 보장하는 수단"이 아니다.
```

이 분리를 설명할 수 있으면 좋다. **"Pub/Sub이 유실되면 어쩌나"의 답이 "유실돼도 되게 만든다"**라는 것이 설계의 핵심이다.

#### 브로커 릴레이 — 전달 보장이 필요할 때

유실을 감당할 수 없거나 인스턴스 수가 많아 Redis 채널의 팬아웃 부하가 부담이면, 메시지 브로커를 백플레인으로 쓴다. 이 저장소의 주 브로커인 **RabbitMQ**로 하면 이렇게 된다.

여기서 **반드시 짚어야 할 함정**이 하나 있다. 평소에 쓰는 작업 큐 구성 — 큐 하나에 컨슈머 여러 개 — 을 그대로 쓰면 **틀린다.** 그 구성은 메시지 하나를 컨슈머 **하나**에게만 주기 때문이다(부하 분산이 목적이므로). 백플레인은 반대로 **모든 인스턴스가 모든 메시지를 받아야** 한다.

```
[잘못된 구성 — 작업 큐 패턴]

   exchange ──> [큐 하나] ──┬──> 인스턴스 1   ← 메시지 42를 여기가 받으면
                            ├──> 인스턴스 2      나머지는 못 받는다
                            └──> 인스턴스 3   ← A의 커넥션이 여기 있어도 헛수고

[올바른 구성 — 팬아웃 + 인스턴스별 전용 큐]

                        ┌──> [큐 A] ──> 인스턴스 1   ✓ 전부 받는다
   fanout exchange ─────┼──> [큐 B] ──> 인스턴스 2   ✓
                        └──> [큐 C] ──> 인스턴스 3   ✓

   각 큐는 인스턴스가 뜰 때 만들어지고 죽을 때 사라지는 임시 큐다.
```

```java
@Configuration
class RabbitFanoutConfig {

    // 팬아웃 익스체인지: 바인딩된 모든 큐에 메시지를 복제해 넣는다.
    // 라우팅 키를 보지 않으므로 "전부에게"라는 백플레인 요구에 정확히 맞는다.
    @Bean
    FanoutExchange realtimeExchange() {
        return new FanoutExchange("realtime.fanout", true, false);
    }

    // AnonymousQueue: 이름이 자동 생성되고 non-durable + exclusive + auto-delete인 큐.
    // ★ 인스턴스마다 서로 다른 큐가 만들어지는 것이 요점이다.
    //   인스턴스가 죽으면 큐도 함께 사라지므로 유령 큐가 쌓이지 않는다.
    //   반대로 "재시작하는 동안의 메시지"는 받지 못한다 — Redis Pub/Sub과 같은 한계이며,
    //   그래서 영속 경로(DB)와의 분리는 여기서도 그대로 필요하다.
    @Bean
    Queue instanceQueue() {
        return new AnonymousQueue();
    }

    @Bean
    Binding realtimeBinding(FanoutExchange realtimeExchange, Queue instanceQueue) {
        return BindingBuilder.bind(instanceQueue).to(realtimeExchange);
    }
}

@Component
@RequiredArgsConstructor
class RabbitRelayListener {

    private final EmitterRegistry registry;

    // 이 인스턴스 전용 큐를 소비한다. 다른 인스턴스도 각자의 큐에서 같은 메시지를 받는다.
    @RabbitListener(queues = "#{instanceQueue.name}")
    public void onEvent(NotificationEvent event) {
        registry.get(event.userId()).forEach(emitter -> send(emitter, event));
    }
}
```

Spring의 STOMP 지원을 쓴다면 **브로커 릴레이**라는 이름의 기능이 이 구조를 통째로 대신해 준다. `enableSimpleBroker()`(인스턴스 메모리 안의 간이 브로커)를 `enableStompBrokerRelay()`로 바꾸면, 모든 인스턴스가 외부 브로커(STOMP를 지원하는 RabbitMQ 등)를 공유 브로커로 쓰게 되어 **구독·발행이 인스턴스 경계를 자동으로 넘는다.** 다만 브로커에 STOMP 지원을 켜야 하고, 브로커가 새로운 단일 장애점이 된다는 점은 고려해야 한다.

**정리하면 선택 기준은 이렇다.** 유실을 감당할 수 있고 이미 Redis가 있으면 Redis Pub/Sub이 압도적으로 싸다. 유실을 감당할 수 없거나 이미 브로커가 중심에 있으면 브로커 릴레이가 맞다. **어느 쪽이든 "영속 경로와 전파 경로를 분리한다"는 원칙은 동일하다.**

### 3-4. 스레드 모델 — 커넥션마다 스레드를 물면 안 된다

#### 전통적 서블릿 모델이 왜 걸리는가

Tomcat 같은 전통적 서블릿 컨테이너는 **요청 하나에 워커 스레드 하나**를 배정한다. 요청이 짧으면 이 모델이 훌륭하게 동작한다 — 스레드가 빠르게 회전하므로 200개짜리 풀로 초당 수천 건을 처리한다.

**장수 커넥션은 이 전제를 정면으로 깬다.** 1-4절의 Before 코드처럼 컨트롤러 안에서 루프를 돌며 흘리면, 그 메서드가 반환될 때까지 스레드가 반환되지 않는다.

```
Spring Boot 내장 Tomcat의 워커 스레드 기본값: server.tomcat.threads.max = 200

  구독자   1명 → 잠긴 스레드   1개
  구독자 100명 → 잠긴 스레드 100개
  구독자 200명 → 잠긴 스레드 200개  ★ 풀 고갈
  구독자 201번째 → 스레드를 못 얻는다.
                   그리고 이 시점부터 SSE만 막히는 게 아니다 —
                   같은 풀을 쓰는 일반 API 요청까지 전부 대기한다.
```

**마지막 줄이 핵심이다.** 실시간 기능 하나가 서비스 전체를 세운다. 7장의 벌크헤드([07-traffic-performance/18](../07-traffic-performance/18-cascading-failure-mechanism-and-bulkhead.md))가 다루는 자원 격리 실패의 전형적인 형태다.

#### 대응 ① — 비동기 서블릿으로 스레드를 놓아준다

서블릿 3.0의 비동기 요청 처리는 **"응답은 아직 안 끝났지만 요청 스레드는 반환하는"** 상태를 만든다. `SseEmitter`를 반환하는 1-4절의 After 코드가 정확히 그것이다.

```
[Before: 블로킹 루프]
  요청 도착 → 워커 스레드 배정 → while(true) { ... }
              스레드는 커넥션이 끊길 때까지 여기 묶여 있다

[After: SseEmitter 반환]
  요청 도착 → 워커 스레드 배정 → emitter 생성, 레지스트리에 등록, 즉시 return
              ↑
              스레드는 여기서 풀로 반환된다 (수 밀리초 점유)

  이후 이벤트 발생 시:
    Redis 리스너 스레드 또는 스케줄러 스레드가 emitter.send()를 호출 →
    열려 있는 응답에 조각을 써넣는다.
    커넥션과 스레드가 1:1로 묶이지 않는다.
```

이 구조에서 커넥션 하나가 소모하는 것은 **소켓 하나와 약간의 힙(emitter 객체, 소켓 버퍼)**이다. 스레드가 아니다. 그래서 수천~수만 커넥션이 200개 스레드 풀 위에서 유지될 수 있다.

이때 상한을 결정하는 것은 스레드가 아니라 다른 두 가지다.

- **Tomcat의 `maxConnections`** — 동시에 유지할 수 있는 커넥션 수. 워커 스레드 수와는 별개의 값이고 기본값이 훨씬 크다. 다만 배포 형태에 따라 다르니 **실제 설정을 확인해야 한다.**
- **OS의 파일 디스크립터 상한** — 소켓 하나가 파일 디스크립터 하나를 쓴다. 컨테이너 기본값이 낮게 잡혀 있는 경우가 많아, 수천 커넥션을 노린다면 `ulimit -n`을 반드시 확인한다.

#### 대응 ② — 그래도 남는 블로킹 지점

비동기 서블릿으로 바꿔도 완전히 해결되지 않는 지점이 하나 남는다. **`emitter.send()` 자체가 블로킹 쓰기라는 것**이다.

클라이언트가 느리거나(모바일 3G) 데이터를 안 읽고 있으면 소켓 송신 버퍼가 차고, 그러면 `send()`를 호출한 스레드가 그 자리에서 멈춘다. 3-1절의 하트비트 스케줄러가 이 상황을 만나면, **커넥션 하나 때문에 전체 하트비트 루프가 멈춰 나머지 커넥션이 전부 유휴 타임아웃으로 끊기는** 연쇄가 생긴다.

그래서 서블릿 스택에서는 방어를 걸어야 한다 — 전송을 별도의 제한된 스레드 풀에서 하고, 그 풀이 포화되면 해당 커넥션을 버리는(느린 소비자를 끊는) 정책이다. **이것이 백프레셔의 한 형태**다([07-traffic-performance/16](../07-traffic-performance/16-backpressure-and-application-points.md)).

#### 대응 ③ — WebFlux/Netty가 이 영역에서 유리한 이유

리액티브 스택이 유리한 이유는 "비동기라서"가 아니라 **쓰기까지 논블로킹이기 때문**이다.

Netty는 [12번 문서](12-nginx-roles-and-event-driven-architecture.md) 3절에서 본 Nginx와 같은 **이벤트 루프** 모델을 쓴다. 적은 수의 스레드(보통 CPU 코어 수)가 커널의 이벤트 통지(리눅스의 epoll)에 "이 소켓들 중 뭔가 읽거나 쓸 수 있게 되면 알려줘"라고 등록해 두고, 준비된 소켓만 처리하고 즉시 다음으로 넘어간다. **소켓이 아직 쓸 준비가 안 됐으면 기다리지 않고 다른 일을 하러 간다** — 이것이 블로킹 쓰기와의 결정적 차이다.

거기에 리액티브 스트림의 **백프레셔**가 얹힌다. `Flux`는 구독자가 "몇 개까지 받을 수 있다"를 요청(request)하는 구조라, 느린 클라이언트에게는 자연스럽게 덜 흘려보낸다. 서블릿 스택에서 직접 만들어야 했던 느린 소비자 방어가 프로그래밍 모델 안에 들어 있는 셈이다.

**다만 정직하게 짚을 것**: 이벤트 루프 모델의 급소도 똑같이 적용된다. 루프 안에서 블로킹 호출(JDBC 같은 블로킹 드라이버, 무거운 CPU 연산)을 하면 그 루프가 담당한 **모든 커넥션이 멈춘다.** 그래서 WebFlux로 갈아탄다는 것은 실시간 계층뿐 아니라 그 아래 데이터 접근까지 논블로킹으로 맞춰야 한다는 뜻이고, 그것은 작은 결정이 아니다.

**현실적인 결론은 이렇다.** 커넥션 수가 수백~수천 수준이면 비동기 서블릿(`SseEmitter`)으로 충분하고, 수만 단위이거나 느린 클라이언트가 지배적이면 리액티브 스택을 검토한다. 그리고 **실시간 엔드포인트만 별도 애플리케이션으로 분리하는 것**도 흔한 선택이다 — 그러면 실시간 계층의 스레드·커넥션 자원이 일반 API와 물리적으로 격리되고, 스케일링 정책도 따로 가져갈 수 있다.

### 3-5. L4 LB에서 장수 커넥션은 부하 편중을 만든다 (가산점 포인트)

#### 왜 편중되는가

[16번 문서](16-l4-vs-l7-load-balancer.md)에서 본 대로, **L4 로드밸런서는 커넥션 단위로 분배한다.** 클라이언트가 TCP 연결을 맺을 때 백엔드 하나를 고르고, 이후 그 커넥션의 모든 패킷은 계속 그 서버로 간다.

짧은 요청에서는 이것이 훌륭하게 동작한다. 커넥션이 초당 수천 개씩 새로 맺어지고 끊어지므로, **분배가 계속 다시 일어나면서 자연스럽게 고르게 퍼진다.**

**장수 커넥션에서는 이 자정 작용이 사라진다.** 커넥션이 한 번 배정되면 몇 시간 동안 그대로 있다. 그래서 분배는 "지금 이 순간의 배정"이 아니라 **"과거의 배정이 누적된 결과"**가 된다.

```
[스케일 아웃해도 새 인스턴스가 비어 있는 문제]

  t=0     인스턴스 1, 2 운영 중. 커넥션 각 5,000개씩.
  t=1h    트래픽 증가로 커넥션이 각 9,000개. 부하 경보.
  t=1h    오토스케일링이 인스턴스 3을 띄운다.

  ┌────────────┐  ┌────────────┐  ┌────────────┐
  │ 인스턴스 1  │  │ 인스턴스 2  │  │ 인스턴스 3  │
  │ 9,000개    │  │ 9,000개    │  │     0개    │  ← 새로 떴다
  └────────────┘  └────────────┘  └────────────┘

  ★ 기존 커넥션 18,000개는 옮겨가지 않는다. 이동할 방법이 없다.
    인스턴스 3은 "앞으로 새로 맺어지는 커넥션"만 받는다.
    커넥션 수명이 몇 시간이면, 몇 시간 동안 인스턴스 3은 거의 비어 있고
    1과 2는 계속 과부하 상태다.

    → 스케일 아웃이 즉시 효과를 내지 못한다.
      "인스턴스를 늘렸는데 왜 부하가 안 떨어지죠?"의 정체다.
```

배포에서도 같은 일이 반대로 일어난다. 롤링 배포로 인스턴스를 하나씩 교체하면, **먼저 뜬 인스턴스가 그 사이 재연결된 커넥션을 전부 받는다.** 마지막에 뜬 인스턴스는 거의 비어 있다. 배포가 끝나면 인스턴스마다 커넥션 수가 크게 다른 상태가 된다.

#### 대응

**커넥션에 최대 수명을 준다.** 서버가 일정 시간(예: 30~60분)마다 커넥션을 정상 종료하면, 클라이언트가 재연결하면서 LB의 분배를 다시 받는다. SSE라면 `EventSource`가 자동으로 재연결하므로 사용자 경험에 영향이 없고, 웹소켓이라면 우리가 만든 재연결 로직이 동작한다. **"강제로 섞어주는" 장치**인 셈이다. 1-4절의 `SseEmitter` 타임아웃을 30분으로 준 것에는 이 의미도 있다.

**재연결에는 반드시 지수 백오프와 지터를 넣는다.** 이것이 없으면 다음 사고가 난다.

```
[재연결 폭풍]

  t=0     인스턴스 1이 종료된다 (배포 또는 장애). 커넥션 9,000개가 동시에 끊긴다.
  t=0.1s  9,000개 클라이언트가 "끊겼다"를 동시에 감지한다.
  t=1.0s  전부 1초 뒤 재연결하도록 되어 있었다면 → 9,000건의 핸드셰이크가 한꺼번에
          남은 인스턴스 2대를 때린다.
  t=1.0s  인스턴스 2가 그 부하를 못 견디고 넘어간다.
  t=1.1s  이번엔 인스턴스 2의 커넥션까지 끊겨 재연결 대상이 더 늘어난다.
          → 연쇄 장애.
```

**지수 백오프(exponential backoff)**는 재시도 간격을 1초, 2초, 4초, 8초로 늘려가는 방식이고, **지터(jitter, 흔들림)**는 거기에 무작위 편차를 섞어 클라이언트들이 같은 순간에 몰리지 않게 하는 기법이다. 둘은 반드시 함께 쓴다 — 백오프만 있으면 "전부 똑같이 1초 뒤, 전부 똑같이 2초 뒤"가 되어 몰림이 그대로 남기 때문이다. 자세한 설계는 [07-traffic-performance/11](../07-traffic-performance/11-retry-storm-backoff-jitter.md)에 있다.

SSE는 `retry:` 필드로 **서버가 재연결 간격을 조종할 수 있다**는 점을 활용할 수 있다. 서버가 과부하 상태면 `retry` 값을 크게 실어 보내 클라이언트들이 천천히 돌아오게 만드는 식이다.

**배포는 커넥션을 서서히 빼는(drain) 방식으로 한다.** 인스턴스를 즉시 죽이는 대신, 먼저 LB의 분배 대상에서 제외해 새 커넥션을 안 받게 하고, 기존 커넥션은 순차적으로 종료하며 클라이언트가 재연결할 시간을 준다. **"커넥션 = 서버가 들고 있는 상태"라서 무상태 서버처럼 막 껐다 켤 수 없다**는 것이 이 절 전체의 인식이다.

## 4. 꼬리질문 대비 포인트

### "SSE가 웹소켓보다 나은 경우는 언제인가요?"

**데이터가 서버→클라이언트 단방향일 때다.** 알림 스트림, 작업 진행률, 대시보드 갱신, 배포 로그 tail이 대표적이다.

이때 SSE가 나은 이유는 두 가지인데, 둘 다 **"웹소켓의 기능이 필요 없는데 웹소켓의 비용을 낼 이유가 없다"**로 수렴한다.

**첫째, 여전히 HTTP다.** 응답 본문이 끝나지 않을 뿐 요청-응답의 형태를 지키므로, 인증 헤더·쿠키·CORS·접근 로그·경로 기반 라우팅 같은 기존 HTTP 인프라가 그대로 적용된다. 웹소켓은 101 이후로 HTTP가 아니게 되므로 이 전부를 다시 고민해야 한다.

**둘째, 재연결과 유실 복구가 표준에 들어 있다.** `EventSource`가 끊기면 자동으로 재연결하고, 마지막으로 받은 `id:` 값을 `Last-Event-ID` 헤더로 되돌려준다. 웹소켓이라면 끊김 감지, 백오프 재연결, 수신 위치 추적, 서버로의 위치 전달 프로토콜을 전부 직접 만들어야 한다. 다만 정직하게 덧붙이자면 **서버 쪽 재전송(그 id 이후의 이벤트를 실제로 갖고 있다가 다시 보내는 것)은 SSE에서도 우리 몫**이다 — 표준이 주는 것은 복구의 프로토콜이지 복구의 데이터가 아니다.

**클라이언트→서버 방향의 간헐적 요청은 일반 HTTP API로 보내면 된다.** 읽음 처리, 필터 변경, 구독 대상 변경 같은 것은 분당 몇 건 수준이므로 평범한 `POST` 한 방이 훨씬 단순하다. **양방향이 조금 필요하다고 바로 웹소켓으로 갈 이유는 없다.**

반대로 SSE를 피해야 하는 경우도 말할 수 있으면 좋다. **이진 데이터를 흘려야 할 때**(텍스트 포맷이라 Base64로 부풀려야 한다), 그리고 **HTTP/1.1 환경에서 같은 도메인에 SSE 스트림을 여러 개 열어야 할 때**(호스트당 동시 연결 6개 제한에 걸린다 — HTTP/2를 켜면 멀티플렉싱 덕에 사실상 해소된다).

### "웹소켓 서버를 scale-out하면 어떤 문제가 생기나요?" (시니어 변별 포인트)

**세 가지가 동시에 생긴다.** 하나만 말하면 절반의 답이다.

**① 메시지 라우팅** — 커넥션이 붙은 인스턴스와 이벤트가 발생한 인스턴스가 어긋난다. 사용자 A의 커넥션은 인스턴스 1에 있는데 A에 대한 이벤트는 인스턴스 2에서 발생하고, 인스턴스 2는 A를 모르므로 알림이 조용히 사라진다. **에러도 안 나고 로그에도 안 남는다**는 점이 고약하다.

해법은 백플레인이다. Redis Pub/Sub 채널이나 브로커의 팬아웃 익스체인지에 이벤트를 던지면 모든 인스턴스가 받고, 커넥션을 가진 인스턴스만 실제로 흘린다. 여기서 **RabbitMQ를 쓸 때 큐 하나에 컨슈머 여러 개로 구성하면 안 된다**는 함정을 짚으면 좋다 — 그 구성은 메시지를 컨슈머 하나에게만 주는 부하 분산용이라, 인스턴스마다 전용 큐를 만들어 팬아웃에 바인딩해야 전부가 받는다.

그리고 **Redis Pub/Sub은 fire-and-forget이라 인스턴스가 잠깐 끊겨 있으면 그 구간을 영영 못 받는다**는 한계까지 말할 수 있어야 한다. 대응은 "유실을 없애기"가 아니라 **"유실돼도 되게 만들기"**다 — 알림 자체는 DB에 남기고(영속 경로), Pub/Sub은 빠르게 보이게 하는 수단(전파 경로)으로만 쓴다. 재연결 시 `Last-Event-ID`로 복구되면 유실 구간이 자동으로 메워진다.

**② 재배포·장애 시 재연결 폭풍** — 인스턴스 하나를 내리면 그 인스턴스의 수천~수만 커넥션이 **동시에** 끊기고 일제히 재연결을 시도한다. 순간적인 핸드셰이크 폭주가 남은 인스턴스를 때리고, 그것이 다시 넘어가면 연쇄 장애가 된다. 대응은 재연결에 지수 백오프 + 지터를 넣는 것과, 배포 시 커넥션을 서서히 빼는(drain) 절차다.

**③ L4 LB의 부하 편중** — 커넥션 단위 분배 + 긴 커넥션 수명이 겹치면 스케일 아웃해도 새 인스턴스가 비어 있다. 기존 커넥션은 옮겨갈 방법이 없기 때문이다. 대응은 커넥션에 최대 수명을 줘서 주기적으로 재분배를 유도하는 것이다.

세 문제를 관통하는 인식은 하나다. **커넥션은 서버가 들고 있는 상태이고, 그 상태는 세션처럼 외부 저장소로 뺄 수가 없다** — 살아 있는 TCP 소켓은 그 프로세스 안에만 존재한다. 그래서 무상태 서버의 문법("아무 인스턴스나 껐다 켠다")이 통하지 않고, **상태를 옮기는 대신 이벤트를 상태가 있는 곳으로 배달하는** 구조가 필요해진다.

### "롱 폴링은 무엇이고, 지금도 쓸 이유가 있나요?"

**서버가 새 데이터가 생기거나 정해둔 시간이 지날 때까지 응답을 보류하는 폴링 변형**이다. 클라이언트는 응답을 받는 즉시 다시 요청을 건다.

일반 폴링보다 나은 점은 둘이다. 빈 응답이 "30초에 한 번" 수준으로 줄고, 소식이 생기면 폴링 주기를 기다리지 않고 거의 즉시 전달된다.

**그러면서도 개별 요청-응답이라는 HTTP의 형태를 유지한다**는 것이 이 방식의 유일무이한 값이다. 그래서 SSE나 웹소켓을 막는 아주 보수적인 네트워크 환경 — 응답을 끝까지 버퍼링하는 구형 프록시, 업그레이드를 차단하는 기업망 — 에서도 동작한다. 실시간 라이브러리들이 최후의 폴백 계층으로 롱 폴링을 두는 이유가 이것이다.

**단점이 명확하다.** 서버가 보류 중인 요청을 계속 물고 있어야 하므로 3절의 장수 커넥션 문제를 그대로 물려받는다 — 비동기 처리가 아니면 스레드를 잠식하고, 중간 계층의 유휴 타임아웃에 걸리며(그래서 보류 상한을 타임아웃보다 짧게 잡아야 한다), 커넥션 상태 관리가 필요하다. **사실상 장수 커넥션의 부담은 다 지면서 진짜 푸시의 효율은 못 얻는 중간 형태**다.

그래서 결론은 이렇다. **신규 설계에서 1순위로 고를 이유는 적지만, 폴백 계층으로서의 값은 여전히 있다.** 환경 제약이 확인되지 않은 상태에서 웹소켓 하나에 전부를 걸기보다, SSE를 기본으로 하고 실패 시 롱 폴링으로 내려가는 단계적 저하(graceful degradation)를 설계에 넣는 것이 안전하다.

### "LB/프록시 뒤에서 웹소켓·SSE를 쓸 때 확인할 설정은?"

**"앱 코드는 맞는데 중간 계층 설정 때문에 끊긴다"가 이 영역 장애의 대부분**이라는 인식에서 출발하면 좋다. 확인할 것이 넷이다.

**① 웹소켓의 업그레이드 통과.** 프록시가 `Upgrade`와 `Connection` 헤더를 업스트림으로 전달하도록 명시해야 한다. 이 헤더들은 홉 단위(hop-by-hop) 헤더 — 다음 중계 지점까지만 유효하고 그 너머로 자동 전달되지 않는 헤더 — 라서, **명시하지 않으면 프록시가 벗겨낸다.** 그러면 업스트림은 평범한 GET 요청을 받은 것으로 보고 101 대신 200이나 404를 돌려준다.

```nginx
# $http_upgrade가 비어 있을 때 "upgrade"를 하드코딩하면 안 되므로 map으로 분기한다.
# 같은 location에 웹소켓이 아닌 요청이 들어올 수 있기 때문이다.
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

location /ws/ {
    proxy_pass http://app;

    # 업그레이드는 HTTP/1.1의 기능이다. Nginx는 업스트림에 기본적으로 HTTP/1.0으로
    # 말하므로, 이 줄이 없으면 아래 두 줄을 넣어도 업그레이드가 성립하지 않는다.
    proxy_http_version 1.1;

    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection $connection_upgrade;

    # 101 이후로는 응답이 끝나지 않으므로 응답 대기 상한이 곧 커넥션 수명이 된다.
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}
```

`proxy_http_version 1.1`이 세트의 일부라는 점을 빠뜨리기 쉽다. **세 줄이 한 묶음**이다.

**② 유휴 타임아웃과 하트비트의 관계.** 경로상 모든 계층의 유휴 상한(클라우드 LB의 idle timeout, Nginx `proxy_read_timeout`, 방화벽·NAT의 세션 타임아웃)을 실시간 경로에 맞게 상향하고, **하트비트 주기를 그중 가장 짧은 값의 절반 이하로** 잡는다. 절반 이하인 이유는 하트비트 한 번이 밀리면 간격이 두 배로 벌어지기 때문이다. 그리고 **Nginx만 늘리고 그 앞의 LB를 그대로 두면 아무 효과가 없다** — 가장 짧은 값이 실질 상한이다.

**③ SSE의 버퍼링 해제.** `proxy_buffering off`를 실시간 경로에만 걸거나, 앱이 `X-Accel-Buffering: no` 헤더를 내려 선언한다. **전역 해제는 안 된다** — 느린 클라이언트로부터 WAS를 격리하는 버퍼링의 보호 효과를 통째로 버리는 것이기 때문이다. 응답 압축도 같은 이유로 실시간 경로에서는 끈다.

**④ LB의 계층과 커넥션 관리.** L4인지 L7인지에 따라 가능한 것이 다르다. L7이면 경로별로 다른 타임아웃을 줄 수 있고 웹소켓 업그레이드를 인지해 처리하지만, L4면 커넥션 단위 분배라 3-5절의 부하 편중이 생긴다. 그리고 **배포 시 커넥션 드레인을 지원하는지**를 반드시 확인한다 — 지원하지 않으면 배포마다 재연결 폭풍이 난다.

### "폴링이 오히려 정답인 경우를 말해보세요."

네 가지 조건 중 하나라도 해당하면 폴링을 진지하게 검토한다.

**① 허용 지연이 폴링 주기보다 크다.** 1분 안에 갱신되면 충분한 뱃지 카운트에 30초 폴링을 쓰면 요구를 완벽히 만족한다. 여기에 웹소켓을 쓰는 것은 지연을 30초에서 0.1초로 줄이는 대신 3절의 다섯 가지 비용을 전부 지불하는 것인데, **사용자는 그 차이를 인지하지 못한다.**

**② 조회 비용이 싸서 낭비가 무시할 수준이다.** 초당 요청 수보다 **요청 하나의 비용**이 중요하다. 캐시에서 바로 나오는 조회라면 수천 req/s도 문제가 안 된다. 반대로 매 요청이 DB 조인을 때리면 수백 req/s에서도 위험하다. **"폴링이 비싸다"가 아니라 "폴링 주기 × 조회 비용이 감당 가능한가"로 계산해야** 정확하다.

**③ 이벤트 발생 빈도가 매우 낮다.** 하루에 몇 번 있을까 말까 한 알림을 위해 사용자마다 커넥션을 몇 시간씩 유지하는 것은, 커넥션 유지 비용이 절약하는 요청 비용보다 큰 상황이다. 이때는 폴링이 총비용에서 이긴다.

**④ 인프라 제약이 장수 커넥션에 적대적이다.** 통제할 수 없는 프록시나 방화벽이 경로에 있고 설정을 바꿀 수 없다면, 웹소켓·SSE가 간헐적으로 끊기는 원인 불명 장애를 안고 가게 된다. 이 경우 폴링이 유일하게 예측 가능한 선택이다.

관통하는 인식은 이것이다. **실시간 수단은 요청 수를 줄이는 대신 "커넥션이라는 상태를 관리하는 책임"을 사는 거래다.** 절약하는 요청 비용보다 새로 사는 관리 비용이 크면 그 거래는 손해다. **단순한 수단으로 충분한 요구에 단순한 수단을 쓰는 것은 기술 후퇴가 아니라 비용 판단**이라고 정리하면 좋다.

## 한 줄 요약

폴링은 클라이언트가 반복해서 물어보는 보편·저비용 수단, SSE는 HTTP 응답을 끝내지 않고 서버가 `data:`/`id:`/`retry:` 줄을 이어 흘리며 `EventSource`의 자동 재연결과 `Last-Event-ID` 복구를 공짜로 얻는 단방향 푸시, 웹소켓은 `101 Switching Protocols` 이후 그 TCP 연결이 HTTP가 아니게 되는 양방향 전용선이다 — 선택은 "요구되는 실시간이 실제 몇 초인가"를 되묻는 데서 시작해 단방향이면 SSE, 역방향이 고빈도일 때만 웹소켓으로 올라가되, 장수 커넥션이 중간 계층 유휴 타임아웃(→ 하트비트를 가장 짧은 상한의 절반 이하로), 프록시 버퍼링(→ 경로 단위 해제), scale-out 시의 이벤트 전파(→ Redis Pub/Sub 또는 브로커 팬아웃 백플레인, 단 영속 경로와 분리), 커넥션당 스레드 점유(→ 비동기 서블릿 또는 이벤트 루프), L4 LB의 부하 편중(→ 커넥션 최대 수명과 드레인)이라는 인프라 비용을 동반한다는 것까지 계산에 넣는 판단이다.
