# HTTP 메서드 멱등성과 안전성 — "재시도해도 되는가"를 결정하는 계약

> 핵심 관전 포인트: **안전(safe)은 "서버 상태를 바꾸지 않는다"는 약속
> (GET, HEAD, OPTIONS), 멱등(idempotent)은 "여러 번 보내도 한 번 보낸
> 것과 서버 상태가 같다"는 약속(safe 전부 + PUT, DELETE)이다.
> POST는 둘 다 아니고, PATCH는 일반적으로 멱등이 아니다. 이 구분이
> 중요한 이유는 실무 그 자체다 — 네트워크 실패로 응답을 못 받았을 때
> "재시도해도 되는가"의 근거가 멱등성이고, 프록시·브라우저·캐시·크롤러
> 같은 중간 인프라가 이 규약을 믿고 동작하기 때문이다. GET으로 상태를
> 바꾸는 API는 프리페치나 크롤러가 데이터를 바꿔버리는 사고로 이어진다.**

---

## 0. 질문 + 의도

**질문**: "HTTP 메서드별 멱등성과 안전성(safe)을 설명해주세요."

**출제 의도**: 멱등성은 "네트워크 실패 시 재시도해도 되는가"라는
실무 질문의 근거다. GET을 상태 변경에 쓴 API가 프록시 프리페치로
데이터를 바꾸는 사고 — 규약 위반의 실제 대가를 아는지 본다.

## 1. 두 개념의 정의 — 무엇에 대한 약속인가

둘 다 "이 메서드를 쓰면 서버가 이렇게 동작한다"는 **HTTP 규약상의
약속**이다. 프로토콜이 강제하는 게 아니라 서버 구현자가 지켜야 하는
계약이고, 세상의 모든 HTTP 인프라가 이 계약을 전제로 만들어져 있다.

- **안전(safe)**: 요청이 서버의 상태(리소스)를 **바꾸지 않는다**.
  읽기 전용이라는 뜻. 클라이언트는 안전한 요청을 "몇 번을 보내든,
  안 보내든 서버에 아무 영향이 없다"고 가정할 수 있다.
- **멱등(idempotent)**: 같은 요청을 **1번 보내든 N번 보내든 서버의
  최종 상태가 같다**. 상태를 바꿀 수는 있지만, 반복해도 결과가
  누적되지 않는다는 뜻이다. 엘리베이터 버튼에 비유하면 — 한 번 누르든
  열 번 누르든 "호출됨" 상태는 같다.

안전하면 당연히 멱등이다(안 바꾸니까 반복해도 같다). 멱등이라고
안전한 건 아니다(DELETE는 상태를 바꾸지만 반복 결과는 같다).
즉 **안전 ⊂ 멱등**의 포함 관계다.

| 메서드 | 안전(safe) | 멱등 | 의미 |
|---|---|---|---|
| GET, HEAD, OPTIONS | O | O | 조회 — 서버 상태 불변 |
| PUT | X | O | 리소스 전체를 이 내용으로 **교체** — 반복해도 같은 내용 |
| DELETE | X | O | 리소스 삭제 — 반복해도 "없음" 상태는 같음 |
| POST | X | X | 새 리소스 생성/처리 — 반복하면 결과가 누적 |
| PATCH | X | X (일반적으로) | 부분 수정 — 수정 방식에 따라 다름 |

PUT이 멱등인 이유는 의미가 "**교체**"이기 때문이다. "이름을 A로
설정해라"는 열 번 해도 이름은 A다. 반면 POST는 "이걸 처리해라"이므로
주문 생성 POST를 두 번 보내면 주문이 두 건 생긴다. PATCH가 애매한
이유는 부분 수정의 내용에 달렸기 때문이다 — "이름을 A로 바꿔라"는
멱등이지만 "포인트를 100 증가시켜라"는 반복할수록 결과가 달라진다.

## 2. 왜 중요한가 — 이 계약을 믿고 움직이는 것들

### 재시도 판단의 근거

네트워크 세계에서 가장 흔한 곤란은 "요청을 보냈는데 **응답을 못
받았다**"이다. 이때 서버가 요청을 처리했는지 안 했는지 클라이언트는
알 수 없다(read timeout이 대표적 — 요청은 도달했고 처리됐을 수도
있다). 여기서 재시도 가능 여부를 갈라주는 것이 멱등성이다:

- **멱등한 요청**(GET, PUT, DELETE): 서버가 이미 처리했더라도 한 번
  더 보내면 같은 상태가 된다 → **안심하고 재시도할 수 있다.**
- **멱등하지 않은 요청**(POST): 이미 처리됐다면 재시도는 **중복
  실행**이다 → 결제 POST를 재시도하면 중복 결제가 난다.

HTTP 클라이언트 라이브러리·프록시·게이트웨이의 자동 재시도 기능이
"멱등 메서드만 재시도"를 기본 정책으로 삼는 이유가 이것이다. 규약을
어긴 API(예: 상태를 바꾸는 GET)는 이 자동화 앞에서 그대로 사고가 된다.

### 중간 인프라의 동작 가정

내 서버와 클라이언트 사이에는 내가 만들지 않은 소프트웨어가 잔뜩
끼어 있고, 전부 이 계약을 전제로 동작한다:

- **캐시(브라우저, CDN, 프록시)**: GET은 안전하다고 믿고 응답을
  캐시하고, 캐시된 응답을 서버에 안 물어보고 돌려준다.
- **브라우저**: 뒤로 가기·새로고침 시 GET은 조용히 재요청하지만
  POST는 "다시 제출하시겠습니까?"라고 묻는다 — 멱등성 구분이
  UX에까지 새겨져 있는 것이다.
- **크롤러·링크 프리페처**: "GET은 안전하니까" 페이지의 모든 링크를
  마음껏 따라가고 미리 가져온다.

### 규약 위반의 실제 대가 — GET으로 상태를 바꾸면

```java
// Before: 삭제를 GET으로 만든 API — 규약 위반
@GetMapping("/posts/{id}/delete")   // 링크 클릭만으로 삭제가 실행된다
public String deletePost(@PathVariable Long id) {
    postService.delete(id);
    return "redirect:/posts";
}
```

이 API는 기능 테스트는 통과한다. 사고는 인프라가 낸다 — 링크
프리페치 기능이 있는 브라우저 확장이나 메신저의 링크 미리보기,
검색엔진 크롤러가 관리 페이지의 삭제 링크들을 "안전한 GET"으로 믿고
전부 방문하면서 **데이터가 무더기로 삭제**된다. 실제로 과거 웹에서
반복적으로 일어난 유형의 사고다. 원인 추적도 어렵다 — 삭제 요청
로그에 남는 건 사용자가 아니라 크롤러의 User-Agent이기 때문이다.

```java
// After: 상태 변경은 반드시 비-safe 메서드로
@DeleteMapping("/posts/{id}")   // 크롤러·프리페처는 DELETE를 보내지 않는다
public ResponseEntity<Void> deletePost(@PathVariable Long id) {
    postService.delete(id);
    return ResponseEntity.noContent().build();
}
```

또 하나의 부수 피해: 상태를 바꾸는 GET은 **캐시에 걸릴 수 있다**.
"출석 체크 GET"이 CDN에 캐시되면 두 번째 사용자부터는 요청이 서버에
도달조차 하지 않아 출석이 안 찍히는, 로그에도 안 남는 유령 버그가 된다.

## 3. POST를 멱등하게 만들기 — 멱등성 키 (가산점 포인트)

결제·주문 생성처럼 본질적으로 POST일 수밖에 없는데 재시도는 꼭
필요한 경우, 규약 밖에서 멱등성을 **직접 구현**한다. 표준적인 방법이
**멱등성 키(Idempotency-Key)**다: 클라이언트가 요청마다 고유 키를
생성해 헤더로 보내고, 서버는 같은 키의 요청이 다시 오면 처리하지
않고 **저장해둔 첫 응답을 그대로 돌려준다.**

```java
// After: 멱등성 키로 POST에 멱등성을 부여
@PostMapping("/payments")
public ResponseEntity<PaymentResponse> pay(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody PaymentRequest request) {

    // 같은 키가 이미 처리됐으면 저장된 응답을 재반환 (중복 실행 차단)
    return idempotencyStore.findResponse(key)
            .map(saved -> ResponseEntity.ok(saved))
            .orElseGet(() -> {
                PaymentResponse response = paymentService.pay(request);
                idempotencyStore.save(key, response);  // 키-응답 저장
                return ResponseEntity.ok(response);
            });
}
```

주요 결제사 API들이 실제로 이 방식을 쓴다. 핵심은 "재시도가 안전한
API인가"를 클라이언트가 추측하게 두지 않고 **서버가 보장**해주는
것이다. 이것이 멱등성 개념의 실무 종착점이다 — 규약 암기가 아니라,
분산 환경에서 "정확히 한 번 처리"에 가까워지기 위한 설계 도구.

## 4. 꼬리질문 대비 포인트

### "DELETE가 멱등이라면서요 — 두 번째 DELETE는 404가 나오는데, 그래도 멱등인가요?"

멱등이다. 멱등성의 기준은 **응답 코드가 아니라 서버의 상태**다.
첫 DELETE 후에도 "리소스 없음", 두 번째 후에도 "리소스 없음" —
서버 상태는 동일하므로 멱등성은 지켜졌다. 응답이 204 → 404로
달라지는 것은 멱등성 위반이 아니다. 이 구분(상태 기준 vs 응답 기준)을
정확히 말하면 개념을 제대로 이해했다는 신호가 된다.

### "PUT과 POST는 어떻게 구분해서 쓰나요?"

의미로 구분한다. PUT은 "**이 URI의 리소스를 이 내용으로 교체하라**" —
클라이언트가 대상 URI를 알고 있고, 반복해도 같은 결과(멱등)다.
POST는 "**이 데이터를 처리하라(주로 하위 리소스 생성)**" — 결과
리소스의 URI를 서버가 정하고, 반복하면 여러 개가 생긴다.
`PUT /users/123/profile`(내 프로필을 이 내용으로)과
`POST /orders`(새 주문 생성)가 전형적인 대비다. 재시도 관점에서
"이 쓰기 연산이 자연스럽게 멱등일 수 있다면 PUT으로 설계하는 것이
클라이언트를 이롭게 한다"까지 말하면 좋다.

### "PATCH는 왜 멱등이 아닌가요? 멱등일 수도 있나요?"

PATCH는 "부분 수정"이라는 틀만 정하고 수정 내용의 성질은 정하지
않기 때문에, 규약상 멱등을 **보장하지 않는다**로 분류된다.
`{"name": "A"}`처럼 값을 지정하는 패치는 사실상 멱등이지만,
`{"op": "increment", "field": "point", "by": 100}`처럼 상대적 연산을
담으면 반복마다 결과가 달라진다. 그래서 "PATCH는 구현이 멱등할 수는
있으나, 클라이언트·인프라가 멱등이라고 **가정해서는 안 되는** 메서드"
라고 답하는 것이 정확하다.

### "read timeout이 났을 때 메서드별로 재시도 판단이 어떻게 달라지나요?"

read timeout은 요청이 서버에 도달해 **처리됐을 가능성이 있는**
실패다. GET/PUT/DELETE는 처리됐더라도 재전송 결과가 같으므로 즉시
재시도해도 된다. POST는 처리 여부를 모르는 채 재시도하면 중복
실행이므로, (1) 멱등성 키가 있으면 재시도, (2) 없으면 재시도 대신
조회 API로 처리 여부를 확인 후 판단해야 한다. 반면 connection
timeout은 요청이 서버에 도달하기 전의 실패이므로 POST라도 안전하게
재시도할 수 있다 — "어느 단계의 실패인가"까지 엮어 답하면
네트워크 이해가 드러난다.

### "멱등성 키를 실제로 구현할 때 고려할 점은?" (시니어 변별 포인트)

세 가지가 핵심이다. (1) **동시 요청 처리**: 같은 키의 요청 두 개가
동시에 도착하면 둘 다 "처리 이력 없음"으로 보고 중복 실행될 수 있다
— 키에 유니크 제약을 건 저장(INSERT 선점)이나 분산 락으로 첫 요청만
진입시키고, 두 번째는 첫 요청의 완료를 기다리거나 처리 중(예: 409)
응답을 준다. (2) **저장소와 TTL**: 키-응답 저장은 원자적 선점이
가능한 곳(DB 유니크 제약, Redis SETNX)에 하고, 무한히 쌓이지 않게
재시도 윈도우보다 긴 TTL을 둔다. (3) **키의 범위**: 키는 "동일한
논리적 요청"의 식별자여야 한다 — 같은 키에 다른 본문이 오면 재사용
오류로 거부해야 하며, 이를 위해 요청 본문 해시를 함께 저장해 비교하는
구현이 견고하다. 여기까지 말하면 실제로 만들어본 사람으로 보인다.

## 한 줄 요약

safe는 "서버 상태를 안 바꾼다"(GET/HEAD/OPTIONS), 멱등은 "반복해도
최종 상태가 같다"(safe + PUT/DELETE)는 계약이고, 이 계약이 네트워크
실패 시 재시도 가능 여부와 캐시·프리페치·크롤러 같은 중간 인프라의
동작 전제를 결정한다 — 규약을 어긴 API(상태 바꾸는 GET)는 인프라가
사고를 내고, 본질적으로 비멱등인 POST에는 멱등성 키로 서버가 직접
멱등성을 보장해준다.
