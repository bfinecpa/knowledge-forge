# HTTP 메서드 멱등성과 안전성 — "재시도해도 되는가"를 결정하는 계약

> 핵심 관전 포인트: **안전(safe)은 "이 요청은 서버의 상태를 바꾸지 않는다"는 약속(GET, HEAD, OPTIONS)이고, 멱등(idempotent)은 "같은 요청을 1번 보내든 N번 보내든 서버의 최종 상태가 같다"는 약속(안전한 메서드 전부 + PUT, DELETE)이다. 안전하면 자동으로 멱등이므로 안전 ⊂ 멱등의 포함 관계이고, POST는 둘 다 아니며 PATCH는 멱등을 보장하지 않는다. 여기서 가장 자주 오해되는 지점이 멱등성의 기준인데, 멱등성은 **응답이 같다**는 뜻이 아니라 **서버의 최종 상태가 같다**는 뜻이다 — 그래서 두 번째 DELETE가 404를 돌려줘도 멱등성은 깨지지 않는다. 이 구분이 실무에서 중요한 이유는 단 하나다. 네트워크에서 가장 흔한 곤란인 "요청은 보냈는데 응답을 못 받았다"(read timeout) 상황에서 재시도해도 되는지를 결정하는 근거가 멱등성이기 때문이다. 게다가 캐시·브라우저·크롤러·자동 재시도 라이브러리 같은 중간 인프라 전부가 이 계약을 참으로 믿고 동작하므로, 규약을 어긴 API(상태를 바꾸는 GET)는 내가 아니라 인프라가 사고를 낸다. 본질적으로 비멱등인 POST(결제·주문 생성)에는 멱등성 키(Idempotency-Key)로 서버가 직접 멱등성을 부여하며, 그 구현의 핵심은 유니크 제약으로 첫 요청을 원자적으로 선점하고, 처리 중(IN_PROGRESS) 상태를 별도로 응답하며, 첫 응답 본문을 저장해 재생하는 것이다.**

---

## 0. 질문 + 의도

**질문**: "HTTP 메서드별 멱등성과 안전성(safe)을 설명해주세요."

**출제 의도**: 멱등성은 "네트워크 실패 시 재시도해도 되는가"라는 실무 질문의 근거다. GET을 상태 변경에 쓴 API가 프록시 프리페치로 데이터를 바꾸는 사고 — 규약 위반의 실제 대가를 아는지 본다.

## 1. 두 개념의 정의 — 무엇에 대한 약속인가

### 1-1. 전제 지식 — 메서드는 "강제"가 아니라 "선언"이다

먼저 오해 하나를 걷어내자. HTTP 메서드는 프로그래밍 언어의 `final` 키워드처럼 컴파일러가 강제하는 것이 아니다. `@GetMapping`을 붙였다고 프레임워크가 DB 쓰기를 막아주지 않는다. GET 핸들러 안에서 `repository.delete()`를 호출하는 코드는 아무 경고 없이 잘 컴파일되고, 잘 실행되고, 데이터를 지운다.

그러면 메서드는 무엇인가. **메서드는 "이 요청이 어떤 성질의 작업인지"를 서버가 세상에 선언하는 라벨**이다. 그리고 이 선언을 참으로 믿고 동작하는 소프트웨어가 세상에 잔뜩 깔려 있다 — 브라우저, CDN, 프록시, 검색엔진 크롤러, HTTP 클라이언트 라이브러리의 자동 재시도 기능. 이들은 내가 만들지 않았고, 내 서버 코드를 읽어보지도 않았으며, 오직 메서드 이름만 보고 판단한다.

그래서 규약 위반의 대가는 내 코드에서 나타나지 않는다. **내 코드는 멀쩡히 도는데 인프라가 사고를 낸다.** 이 구조를 먼저 이해해야 아래 두 개념이 왜 "약속"이라고 불리는지 납득이 된다.

HTTP 명세(RFC 9110, HTTP Semantics)는 이 라벨의 성질을 두 축으로 정의한다. 안전(safe)과 멱등(idempotent)이다.

### 1-2. 안전(safe) — 서버 상태를 건드리지 않는다는 약속

**안전(safe)한 메서드는 "이 요청은 서버의 상태(리소스)를 바꾸지 않는다"는 약속을 담고 있다.** 읽기 전용이라는 뜻이다. 클라이언트는 안전한 요청을 "몇 번을 보내든, 아예 안 보내든 서버에는 아무 차이가 없다"고 가정하고 마음껏 다뤄도 된다.

이름이 "안전"인 이유는 **보내는 쪽 입장에서 부담이 없다**는 데서 왔다. 링크를 미리 눌러봐도, 페이지를 미리 받아둬도, 크롤러가 사이트 전체를 훑어도 아무것도 망가지지 않는다. 그래서 안전하다.

여기서 3년차가 자주 걸리는 질문이 하나 있다. **"GET을 처리하면서 조회수 카운터를 1 올리거나 접근 로그를 남기면 그건 안전하지 않은 것 아닌가?"**

명세의 답은 "그래도 안전하다"이다. 기준이 **"클라이언트가 무엇을 요청했는가"**이지 "서버 안에서 무슨 일이 일어났는가"가 아니기 때문이다. 클라이언트는 조회를 요청했을 뿐이고, 조회수 증가나 로그 적재는 서버가 스스로 부수적으로 한 일이다. 클라이언트는 그 결과에 책임이 없다. 반대로 `GET /posts/1/delete`는 클라이언트가 삭제를 요청한 것이므로 명백히 안전하지 않다.

실무 감각으로 옮기면 이렇다. **"이 GET이 크롤러에 의해 하루 만 번 호출돼도 괜찮은가?"**를 자문하면 된다. 조회수가 만 늘어나는 것은 대체로 참을 수 있는 부작용이지만, 게시글 만 건이 지워지는 것은 참을 수 없다. 이 감각의 경계가 곧 safe의 경계다.

### 1-3. 멱등(idempotent) — 반복해도 최종 상태가 같다는 약속

**멱등(idempotent)한 메서드는 "같은 요청을 1번 보내든 N번 보내든 서버의 최종 상태가 같다"는 약속을 담고 있다.** 상태를 바꿔도 되지만, 반복했을 때 그 변화가 **누적되지 않는다**는 뜻이다.

"멱등"이라는 낯선 한자어는 수학에서 왔다. 거듭할 멱(冪), 같을 등(等) — 거듭 적용해도 결과가 같다는 뜻이다. 함수로 쓰면 `f(f(x)) = f(x)`다. 절댓값 함수를 떠올리면 된다. `abs(-3)`은 3이고 `abs(abs(-3))`도 3이다. 몇 번을 씌워도 결과는 더 이상 변하지 않는다.

일상의 비유로는 **엘리베이터 호출 버튼**이 정확하다. 한 번 누르든 조급해서 열 번 누르든 엘리베이터의 상태는 "호출됨" 하나다. 버튼을 열 번 눌렀다고 엘리베이터가 열 대 오지 않는다. 반면 **자판기의 결제 버튼**은 멱등이 아니다. 열 번 누르면 열 번 결제된다.

그리고 안전한 메서드는 **자동으로 멱등**이다. 상태를 아예 안 바꾸는데 반복한다고 달라질 리가 없기 때문이다. 반대는 성립하지 않는다 — DELETE는 상태를 바꾸므로 안전하지 않지만, 반복해도 "없음"이라는 최종 상태는 같으므로 멱등이다.

```
                 ┌─────────────────────────────────────────┐
                 │            멱등(idempotent)             │
                 │  반복해도 서버의 최종 상태가 같다        │
                 │                                         │
                 │   ┌───────────────────────┐             │
                 │   │     안전(safe)        │             │
                 │   │  아예 안 바꾼다        │   PUT       │
                 │   │                       │   DELETE    │
                 │   │  GET  HEAD  OPTIONS   │             │
                 │   └───────────────────────┘             │
                 └─────────────────────────────────────────┘

                          POST     PATCH
                    (둘 다 아님 — 반복하면 결과가 누적될 수 있다)
```

즉 **안전 ⊂ 멱등**이다. 이 포함 관계를 "안전한 것은 전부 멱등이지만, 멱등한 것이 전부 안전하지는 않다"라고 말로 풀 수 있으면 개념이 정확히 잡힌 것이다.

### 1-4. 가장 중요한 구분 — 멱등성의 기준은 "응답"이 아니라 "서버의 최종 상태"다

이 절이 이 문서에서 가장 중요하다. 멱등성을 배운 사람 대부분이 여기서 한 번 넘어진다.

문제의 장면은 이렇다. DELETE는 멱등이라고 배웠다. 그런데 실제로 두 번 호출해 보면 응답이 다르다.

```
POST /orders 로 만든 주문 42번을 지운다고 하자.

  1번째  DELETE /orders/42   ->  204 No Content   (지웠다)
  2번째  DELETE /orders/42   ->  404 Not Found    (지울 게 없다)
  3번째  DELETE /orders/42   ->  404 Not Found
```

응답 코드가 204에서 404로 **달라졌다**. 그런데도 DELETE는 멱등이다. 모순처럼 보이는 이 지점이 개념의 핵심이다.

**멱등성은 "응답이 같다"는 약속이 아니라 "서버의 최종 상태가 같다"는 약속이기 때문이다.** 위 세 번의 호출 뒤 서버가 어떤 상태인지 보자.

```
                        요청 전 서버 상태     요청 후 서버 상태
  1번째 DELETE   ->     주문 42 존재    ->    주문 42 없음
  2번째 DELETE   ->     주문 42 없음    ->    주문 42 없음
  3번째 DELETE   ->     주문 42 없음    ->    주문 42 없음
                                             ─────────────
                                             전부 동일하다
```

몇 번을 호출하든 끝난 뒤의 서버는 "주문 42가 없는 상태"로 똑같다. **약속한 것은 이 열(列)이지 응답 코드가 아니다.** 응답 코드는 "이번 호출이 실제로 무엇을 했는지"를 알려주는 별개의 정보이고, 그것이 호출마다 달라지는 것은 멱등성 위반이 아니다.

같은 원리가 PUT에도 적용된다. `PUT /users/1` 로 이름을 "A"로 바꾸는 요청을 세 번 보내면, 첫 번째는 실제로 값을 바꾸고 나머지 두 번은 이미 "A"인 값을 다시 "A"로 쓴다. 서버가 `updated_at` 컬럼을 매번 갱신한다면 그 타임스탬프는 호출마다 달라진다. **이것도 멱등성 위반이 아니다.** 클라이언트가 요청한 의도된 효과는 "이름을 A로 만들어라"이고 그 효과는 세 번 모두 동일하게 달성됐다. `updated_at` 갱신이나 접근 로그 적재는 클라이언트가 요청한 것이 아닌 서버의 부수적 기록이다.

이 구분을 한 문장으로 압축하면 이렇다. **멱등성은 클라이언트가 요청한 "의도된 효과"에 대한 약속이지, 서버 안에서 벌어지는 모든 일에 대한 약속이 아니다.**

그렇다면 실무에서 왜 이 구분이 중요한가. **재시도 판단이 여기에 달려 있기 때문이다.** 클라이언트가 DELETE를 재시도했을 때 404가 오면, 그것은 "실패"가 아니라 "이미 원하는 상태에 도달했다"는 뜻이다. 이 사실을 모르는 클라이언트는 404를 에러로 처리해 사용자에게 "삭제 실패"를 띄우지만, 실제로는 삭제가 이미 성공한 상태다. **멱등성을 상태 기준으로 이해한 클라이언트만이 재시도 후의 404를 올바르게 해석한다.**

### 1-5. 메서드별로 왜 그 칸에 들어가는가

앞의 정의를 각 메서드에 하나씩 적용해 보자. 표를 먼저 던지지 않고 메서드마다 근거를 따져야 "왜"가 남는다.

**GET — 안전하고 멱등하다.** 의미가 "이 URI의 표현(내용)을 달라"는 순수한 조회이기 때문이다. 요청 자체가 서버에 아무것도 요구하지 않으므로 안전하고, 안전하면 자동으로 멱등이다. HTTP에서 압도적으로 많이 쓰이는 메서드이고, 캐시·프리페치·크롤링 같은 인프라 최적화가 전부 이 메서드를 전제로 만들어져 있다.

**HEAD — 안전하고 멱등하다.** GET과 완전히 동일하되 **응답 본문 없이 헤더만** 받는 메서드다. 파일을 실제로 받지 않고 `Content-Length`나 `Last-Modified`만 확인하고 싶을 때 쓴다. 하는 일이 GET의 부분집합이므로 성질도 GET과 같다.

**OPTIONS — 안전하고 멱등하다.** "이 URI에 어떤 메서드를 쓸 수 있는지 알려달라"고 묻는 메서드다. 실무에서 직접 호출할 일은 드물지만 매일 마주치고 있다 — 브라우저가 크로스 오리진 요청 전에 자동으로 보내는 **프리플라이트(preflight) 요청**이 바로 OPTIONS다. 서버에 "이 요청을 보내도 되느냐"고 미리 묻는 것이므로 아무것도 바꾸지 않는다.

**PUT — 안전하지 않지만 멱등하다.** 열쇠는 PUT의 의미가 **"교체(replace)"**라는 데 있다. `PUT /users/1`의 뜻은 "1번 사용자를 이 본문의 내용으로 만들어라"이지 "이 본문을 추가하라"가 아니다. "이름을 A로 만들어라"는 명령은 몇 번을 실행해도 결과가 "이름 = A"로 같다. 상태를 바꾸니 안전하지는 않지만, 반복해도 누적되지 않으니 멱등이다.

PUT이 멱등할 수 있는 더 근본적인 이유는 **요청 본문에 "최종 상태"가 통째로 담겨 있기 때문**이다. 목적지가 절대 좌표로 지정돼 있으면 몇 번을 이동해도 같은 자리에 도착한다. 상대 좌표("두 걸음 앞으로")로 지정하면 반복할수록 멀어진다 — 이것이 아래 PATCH가 멱등을 보장받지 못하는 이유와 정확히 같은 논리다.

**DELETE — 안전하지 않지만 멱등하다.** 근거는 1-4에서 이미 자세히 봤다. "이 리소스가 없는 상태로 만들어라"는 명령이므로, 몇 번을 실행해도 도달하는 최종 상태는 "없음" 하나다. 응답이 204에서 404로 바뀌는 것은 멱등성과 무관하다.

**POST — 안전하지도 멱등하지도 않다.** 의미가 **"이 데이터를 처리해라"**로, 처리 결과가 무엇일지는 서버가 정한다. 가장 흔한 용법인 "하위 리소스 생성"에서는 요청 한 번에 리소스가 하나씩 생긴다. `POST /orders`를 두 번 보내면 주문이 두 건 생긴다 — 각 요청이 **새 리소스를 만들고 서버가 그 URI를 정하기** 때문에 두 번째 요청은 첫 번째와 다른 대상을 만든다. 반복이 누적되므로 멱등이 아니다.

바로 이 성질 때문에 POST는 재시도가 가장 위험한 메서드이고, 동시에 결제·주문처럼 **꼭 재시도가 필요한** 작업이 몰려 있는 메서드다. 이 모순을 푸는 것이 3절의 멱등성 키다.

**PATCH — 안전하지 않고, 멱등을 보장하지 않는다.** PATCH는 "부분 수정"이라는 틀만 정하고 **수정 내용의 성질은 정하지 않는다.** 그래서 멱등일 수도 있고 아닐 수도 있는데, 클라이언트와 인프라는 어느 쪽인지 알 방법이 없으므로 명세는 **"멱등을 보장하지 않는다"**로 분류한다.

두 가지 본문을 나란히 보면 왜 그런지 한눈에 들어온다.

```
[멱등한 PATCH — 절대값을 지정한다]
  PATCH /users/1   {"name": "A"}
  1회 후 name=A,  2회 후 name=A,  3회 후 name=A   ->  최종 상태 동일

[멱등하지 않은 PATCH — 상대 연산을 지정한다]
  PATCH /users/1   {"op": "increment", "field": "point", "by": 100}
  1회 후 +100,    2회 후 +200,    3회 후 +300      ->  최종 상태가 달라진다
```

즉 "PATCH는 절대 멱등이 아니다"는 틀린 설명이고, **"구현이 멱등할 수는 있지만 클라이언트·인프라가 멱등이라고 가정해서는 안 되는 메서드"**가 정확한 설명이다.

지금까지 따진 것을 짧게 대조하면 이렇다.

| 메서드 | 안전 | 멱등 | 그 칸인 이유 |
|---|---|---|---|
| GET, HEAD, OPTIONS | O | O | 조회·질의만 요청한다 — 상태를 아예 안 바꾸므로 자동으로 멱등 |
| PUT | X | O | "교체" — 본문에 최종 상태가 통째로 담겨 있어 반복해도 같은 자리 |
| DELETE | X | O | "없는 상태로 만들어라" — 최종 상태는 언제나 "없음" 하나 |
| POST | X | X | "처리해라" — 반복하면 새 리소스가 하나씩 더 생긴다 |
| PATCH | X | X (보장 안 함) | 수정 내용의 성질을 규약이 정하지 않는다 — 상대 연산이면 누적된다 |

## 2. 왜 중요한가 — 이 계약을 믿고 움직이는 것들

### 2-1. 재시도 판단의 근거 — "응답을 못 받았다"는 상태

분산 환경에서 가장 흔하고 가장 곤란한 상황은 서버가 에러를 돌려주는 것이 **아니다.** 에러 응답은 오히려 다행이다 — 무엇이 잘못됐는지 알려주니까. 진짜 곤란한 것은 **아무 응답도 못 받은 상태**다.

```
[클라이언트가 아는 것과 모르는 것]

  클라이언트가 아는 것:  "내가 요청을 보냈고, 응답이 안 왔다"
  클라이언트가 모르는 것: "서버가 그 요청을 처리했는가?"

  가능한 세계가 셋이다.
    ① 요청이 서버에 도달조차 못 했다        -> 미처리
    ② 도달해서 처리됐는데 응답이 유실됐다    -> 처리됨
    ③ 지금 서버가 처리하는 중이다           -> 곧 처리됨

  이 셋을 구분할 방법이 클라이언트에게는 없다.
```

이 불확실성 앞에서 클라이언트가 할 수 있는 선택은 둘뿐이다. **포기하거나, 다시 보내거나.** 그런데 다시 보냈다가 ②였다면 같은 작업이 두 번 실행된다.

**멱등성이 정확히 이 갈림에서 답을 준다.** 요청이 멱등하다면 ②였더라도 한 번 더 보낸 결과가 같으므로 "모르는 채로 다시 보내도" 안전하다. 멱등하지 않다면 ②일 때 재시도는 곧 **중복 실행**이고, 결제 API에서는 그대로 중복 결제다.

HTTP 클라이언트 라이브러리, 프록시, API 게이트웨이의 자동 재시도 기능이 **"멱등 메서드만 재시도"를 기본 정책으로 삼는 이유**가 이것이다. 이들은 내 비즈니스 로직을 모르고, 오직 메서드 이름만 보고 판단할 수 있기 때문이다. 그래서 규약을 어긴 API — 예컨대 상태를 바꾸는 GET — 는 이 자동화 앞에서 그대로 사고가 된다.

### 2-2. read timeout과 connection timeout은 다르다 — 어느 단계의 실패인가

앞 절의 "가능한 세계 셋"은 실패의 **종류**에 따라 좁혀진다. 여기가 실무 판단의 핵심이다.

용어부터 정확히 하자. **connection timeout(연결 타임아웃)**은 TCP 연결을 맺는 단계, 즉 handshake가 제한 시간 안에 끝나지 않아 난 실패다. 아직 HTTP 요청 바이트를 **단 하나도 보내지 않은** 시점이다. **read timeout(읽기 타임아웃)**은 연결은 맺었고 요청도 다 보냈는데, 서버의 응답이 제한 시간 안에 오지 않아 난 실패다. 요청은 이미 서버 쪽으로 흘러갔다.

타임라인으로 보면 차이가 분명해진다.

```
[connection timeout — 요청 바이트가 아직 나가지 않았다]

  클라이언트                                        서버
     |                                               |
     |--- SYN --------------------X (도달 못 함)      |
     |    (재전송 몇 번 후)                           |
     |  X connect 타임아웃 만료                       |
     |                                               |
     ★ 서버는 이 요청의 존재조차 모른다.
       "가능한 세계"는 ① 하나로 좁혀진다  ->  POST여도 재시도 안전


[read timeout — 요청은 나갔고, 처리됐을 수도 있다]

  클라이언트                                        서버
     |                                               |
     |--- TCP 연결 성립 ---------------------------->|
     |--- POST /payments  (본문 전송 완료) --------->|  수신
     |                                               |  결제 INSERT
     |                                               |  COMMIT   ★ 상태 변경 확정
     |                                               |
     |  X read 타임아웃 만료                          |--- 200 OK --X (지연/유실)
     |                                               |
     ★ 서버 상태는 이미 바뀌었을 수 있다.
       "가능한 세계" ①②③ 이 전부 살아 있다  ->  POST 재시도 = 중복 결제
```

정리하면 이렇다. **connection timeout은 "확실히 미처리"에 가깝고, read timeout은 "결과 불명"이다.** 그리고 결과 불명 상태에서 재시도해도 되는지를 결정하는 것이 멱등성이다.

메서드별 판단을 표로 대조하면 이렇게 된다.

| 실패 유형 | 요청이 서버에 도달했나 | GET / HEAD / OPTIONS | PUT / DELETE | POST / PATCH |
|---|---|---|---|---|
| connection timeout | 아니오 (바이트 전송 전) | 재시도 | 재시도 | **재시도해도 안전** |
| read timeout | 예 (처리됐을 수 있음) | 재시도 | 재시도 | **재시도 금지** — 멱등성 키가 있거나 조회로 확인 후 판단 |
| 연결이 끊김(reset) | 시점에 따라 다름 | 재시도 | 재시도 | read timeout과 동일하게 취급 |

connection timeout에서 POST 재시도를 안전하다고 말할 때 조건을 정확히 붙이는 것이 중요하다. 안전한 진짜 조건은 "connection timeout이라서"가 아니라 **"요청 바이트를 한 바이트도 쓰지 않았음이 확실해서"**다. connection timeout은 그 조건을 만족하는 대표적인 경우일 뿐이다. 요청 전송 도중에 연결이 끊긴 경우는 서버가 요청을 부분적으로 받아 처리를 시작했을 수도 있으므로 read timeout과 같이 취급해야 한다.

POST가 read timeout을 만났을 때의 대응은 세 가지다. **첫째, 멱등성 키가 걸려 있으면 그냥 재시도한다**(3절). 서버가 중복을 막아주므로 클라이언트는 고민할 필요가 없다. **둘째, 키가 없으면 조회 API로 처리 여부를 먼저 확인**하고 판단한다 — 다만 이 방법은 조회 API가 따로 있어야 하고, 조회와 재시도 사이에 상태가 또 바뀔 수 있어 완전하지 않다. **셋째, 아무것도 못 하면 사용자에게 "결과를 확인해 달라"고 넘긴다** — 가장 나쁜 답이지만 중복 결제보다는 낫다. 이 셋 중 첫째만이 구조적인 해법이라는 것이 3절의 결론이다.

### 2-3. 중간 인프라의 동작 가정 — 내가 만들지 않은 소프트웨어들

재시도만큼이나 중요한 것이 **내 서버와 클라이언트 사이에 끼어 있는 소프트웨어들**이다. 이들은 전부 메서드의 계약을 참으로 믿고 동작한다.

**캐시(브라우저 캐시, CDN, 리버스 프록시)**는 GET이 안전하다고 믿기 때문에 응답을 저장해 두고, 다음 요청에는 **서버에 물어보지도 않고** 저장된 응답을 돌려준다. 캐시가 성립하는 전제가 바로 "GET은 서버 상태를 바꾸지 않으므로 서버에 안 보내도 서버에 아무 손해가 없다"이다.

**브라우저**는 뒤로 가기나 새로고침을 할 때 GET은 아무 말 없이 다시 요청하지만, POST로 만들어진 페이지에서는 "양식을 다시 제출하시겠습니까?"라고 사용자에게 묻는다. 멱등성 구분이 프로토콜 층을 넘어 **UX에까지 새겨져 있는 것**이다.

**크롤러와 링크 프리페처**는 "GET은 안전하니까"라는 전제로 페이지의 모든 링크를 자동으로 따라간다. 검색엔진 크롤러, 메신저의 링크 미리보기, 브라우저 확장의 프리페치 기능이 전부 여기 해당한다. 이들은 페이지에 있는 `<a href>`를 사람 대신 눌러보는 존재다.

**자동 재시도를 하는 프록시·게이트웨이**는 2-1에서 본 대로 멱등 메서드만 재시도한다.

이 네 부류를 한 문장으로 묶으면 이렇다. **메서드 규약은 나 혼자 지키는 코딩 컨벤션이 아니라, 내가 통제할 수 없는 소프트웨어들과 맺은 계약이다.**

### 2-4. 규약 위반의 실제 대가 — GET으로 상태를 바꾸면

```java
// Before: 삭제를 GET으로 만든 API — 규약 위반
@GetMapping("/posts/{id}/delete")   // 이 URL은 링크 클릭만으로 삭제를 실행한다
public String deletePost(@PathVariable Long id) {
    postService.delete(id);
    return "redirect:/posts";
}
```

이 코드는 기능 테스트를 전부 통과한다. 브라우저로 눌러보면 글이 잘 지워지고, 통합 테스트도 초록불이다. **사고는 코드가 아니라 인프라가 낸다.**

관리 페이지에 이런 삭제 링크가 목록으로 깔려 있다고 하자. 그리고 그 페이지 주소가 사내 메신저에 공유되거나, 크롤러가 접근 가능한 곳에 노출되거나, 링크 프리페치 기능이 켜진 브라우저 확장을 쓰는 관리자가 그 페이지를 열었다고 하자. 그 순간 **모든 삭제 링크가 "안전한 GET"으로 믿어져 한꺼번에 방문된다.** 게시글이 무더기로 지워진다.

원인 추적도 어렵다. 삭제 요청 로그에 남는 것은 관리자의 클릭이 아니라 **크롤러나 확장 프로그램의 User-Agent**이고, 애플리케이션 입장에서는 지극히 정상적인 요청 처리로 보인다. "아무도 안 눌렀는데 데이터가 사라졌다"는 상황이 만들어진다.

```java
// After: 상태 변경은 반드시 안전하지 않은 메서드로
@DeleteMapping("/posts/{id}")   // 크롤러·프리페처는 링크를 DELETE로 따라가지 않는다
public ResponseEntity<Void> deletePost(@PathVariable Long id) {
    postService.delete(id);
    // 204 No Content: 성공했고 돌려줄 본문이 없다는 뜻.
    // 클라이언트에게 "본문을 파싱하려 들지 마라"를 코드로 알려준다.
    return ResponseEntity.noContent().build();
}
```

`DELETE`로 바꾸는 것만으로 위 사고 경로가 통째로 사라진다. **`<a href>`를 따라가는 어떤 인프라도 DELETE를 보내지 않기 때문이다.** 링크 클릭은 언제나 GET이고, DELETE를 보내려면 자바스크립트나 API 클라이언트로 명시적으로 그 메서드를 지정해야 한다.

부수 피해가 하나 더 있다. **상태를 바꾸는 GET은 캐시에 걸릴 수 있다.** "출석 체크"를 GET으로 만들어 뒀는데 그 응답이 CDN에 캐시되면, 두 번째 사용자부터는 요청이 **서버에 도달조차 하지 않고** CDN이 캐시된 성공 응답을 돌려준다. 사용자 화면에는 "출석 완료"가 뜨는데 DB에는 아무것도 안 남는다.

이 버그의 악질적인 점은 **서버 로그에 흔적이 전혀 없다는 것**이다. 요청이 서버까지 오지 않았으니 접근 로그에도, 에러 로그에도, APM에도 아무것도 없다. 개발자는 "재현이 안 되는데요"라고 말하게 되고(개발 환경에는 CDN이 없으니 정말로 재현되지 않는다), 사용자만 계속 문의를 넣는다.

## 3. POST를 멱등하게 만들기 — 멱등성 키 (가산점 포인트)

### 3-1. 왜 필요한가 — 비멱등인데 재시도는 꼭 필요한 작업들

결제 승인, 주문 생성, 송금, 포인트 사용. 이런 작업은 **본질적으로 POST일 수밖에 없다.** 클라이언트가 결과 리소스의 URI를 미리 알 수 없고("결제 3821번을 만들어라"라고 말할 수 없다), 요청 한 번이 새 사건 하나를 만들기 때문이다. PUT으로 바꿔 멱등하게 만들 방법이 없다.

그런데 동시에 이런 작업이야말로 **재시도가 가장 절실하다.** 네트워크가 한 번 흔들렸다고 결제를 포기하면 매출이 날아가고, read timeout이 났다고 "확인해 주세요"를 띄우면 사용자는 결제 버튼을 다시 누른다. 그리고 그 두 번째 클릭이 중복 결제가 된다.

**비멱등인데 재시도해야 한다** — 이 모순을 규약 밖에서 푸는 것이 **멱등성 키(Idempotency-Key)**다. 원리는 간단하다.

```
클라이언트가 요청마다 고유한 키를 만들어 헤더에 실어 보낸다.
서버는 그 키를 기록해 두고, 같은 키의 요청이 다시 오면
새로 처리하지 않고 첫 요청의 결과를 그대로 돌려준다.

  1번째:  POST /payments   Idempotency-Key: k-9f3a...   ->  실제로 결제  ->  201
  2번째:  POST /payments   Idempotency-Key: k-9f3a...   ->  처리 안 함   ->  저장된 201 재생
  3번째:  POST /payments   Idempotency-Key: k-9f3a...   ->  처리 안 함   ->  저장된 201 재생

  서버의 최종 상태: 결제 1건.  ->  POST가 멱등해졌다.
```

핵심은 **"재시도가 안전한 API인가"를 클라이언트가 추측하게 두지 않고 서버가 보장해 주는 것**이다. 주요 결제 서비스들의 API가 실제로 이 방식을 쓴다. IETF에서 이 헤더를 표준화하려는 초안 논의가 있지만 아직 정식 표준은 아니고, 현재는 널리 퍼진 업계 관행에 가깝다.

여기서 클라이언트가 **키를 언제 새로 만드는지**가 결정적이다. 자주 틀리는 지점이다.

```
[올바른 키 생성 시점]

  사용자가 "결제하기"를 누름  ->  키 k1 생성
      네트워크 실패 -> 재시도            ->  k1 그대로 (같은 시도이므로)
      또 실패 -> 재시도                  ->  k1 그대로
      성공                               ->  결제 1건

  사용자가 다시 "결제하기"를 누름  ->  키 k2 새로 생성 (다른 시도이므로)

[흔한 실수]
  요청을 보낼 때마다 새 키를 만든다  ->  재시도마다 키가 달라져 중복 탐지 불가
  앱 실행 시 키를 한 번만 만들어 재사용  ->  두 번째 결제가 첫 결제 응답으로 막힘
```

**키의 단위는 "사용자의 한 번의 의도"**다. 재시도는 같은 의도의 반복이므로 같은 키를 쓰고, 새로 누른 결제는 새 의도이므로 새 키를 쓴다.

### 3-2. 순진한 구현이 왜 깨지는가

먼저 대부분의 사람이 처음 떠올리는 구현을 보자.

```java
// Before: 조회 후 처리 — 동시 요청 앞에서 무너진다
@PostMapping("/payments")
public ResponseEntity<PaymentResponse> pay(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody PaymentRequest request) {

    // ① 이 키가 이미 처리됐는지 "물어본다"
    Optional<PaymentResponse> saved = idempotencyStore.findResponse(key);
    if (saved.isPresent()) {
        return ResponseEntity.ok(saved.get());
    }

    // ② 실제 결제 실행
    PaymentResponse response = paymentService.pay(request);

    // ③ 키와 응답을 저장
    idempotencyStore.save(key, response);
    return ResponseEntity.ok(response);
}
```

단일 요청이 순서대로 들어올 때는 잘 동작한다. 문제는 **①과 ③ 사이에 열려 있는 창(window)**이다. 그 사이에 같은 키의 두 번째 요청이 들어오면 어떻게 되는지 타임라인으로 보자.

```
  요청 A (첫 시도)                     요청 B (클라이언트의 재시도)
  ────────────────────────────────────────────────────────────────
  t0  ① findResponse(k) -> 없음
  t1                                   ① findResponse(k) -> 없음  ★ 아직 저장 전이라 못 본다
  t2  ② 결제 실행 (9,900원 승인)
  t3                                   ② 결제 실행 (9,900원 승인)  ★ 중복 결제
  t4  ③ save(k, 응답A)
  t5                                   ③ save(k, 응답B)  또는 유니크 위반 예외
  ────────────────────────────────────────────────────────────────
  결과: 결제 2건.  멱등성 키를 붙였는데 중복 결제가 났다.
```

이 창이 왜 현실적인 위험인가 하면, **재시도가 도착하는 시점이 정확히 이 구간이기 때문이다.** 클라이언트가 재시도를 보내는 이유는 "응답이 안 와서"이고, 응답이 안 오는 이유는 대개 서버가 **아직 처리 중이어서**다. 즉 재시도는 첫 요청이 ②를 실행하고 있는 바로 그 순간에 도착할 확률이 높다. 가장 위험한 타이밍이 가장 자주 발생하는 타이밍이다.

**교훈은 "조회로 확인한 뒤 처리하는 구조는 동시성 앞에서 성립하지 않는다"**이다. 확인과 선점 사이에 틈이 있으면 그 틈으로 다른 요청이 들어온다. 확인과 선점이 **한 번에, 원자적으로** 일어나야 한다.

### 3-3. 테이블 설계 — 유니크 제약이 확인과 선점을 한 번에 처리한다

틈을 없애는 방법은 애플리케이션이 아니라 **DB에게 판정을 맡기는 것**이다. PostgreSQL의 유니크 제약은 두 트랜잭션이 같은 값을 동시에 INSERT하려 할 때 하나만 통과시키고 나머지를 막아준다. 이 판정은 DB 내부에서 원자적으로 일어나므로 틈이 없다.

```sql
CREATE TABLE idempotency_record (
    id               bigserial    PRIMARY KEY,

    -- 키의 유효 범위를 결정하는 세 컬럼 (3-6에서 왜 셋인지 설명)
    user_id          bigint       NOT NULL,
    endpoint         varchar(200) NOT NULL,
    idempotency_key  varchar(255) NOT NULL,

    -- 같은 키로 "다른 내용"이 오는 것을 잡기 위한 요청 본문 해시 (SHA-256 hex 64자)
    request_hash     char(64)     NOT NULL,

    -- IN_PROGRESS: 첫 요청이 선점했고 아직 처리 중
    -- COMPLETED  : 처리가 끝났고 아래 응답 컬럼이 채워져 있음
    status           varchar(20)  NOT NULL,

    -- 재시도에 그대로 돌려줄 첫 응답 (3-5)
    response_status  int,
    response_body    jsonb,

    created_at       timestamptz  NOT NULL DEFAULT now(),
    completed_at     timestamptz,
    -- 이 시각이 지나면 키를 폐기한다 (3-6)
    expires_at       timestamptz  NOT NULL,

    -- 이 제약 하나가 "이미 처리 중인가?"의 판정과 선점을 원자적으로 수행한다.
    -- 애플리케이션의 조회 + 분기로는 이 원자성을 만들 수 없다.
    CONSTRAINT uq_idempotency UNIQUE (user_id, endpoint, idempotency_key)
);

-- 만료 레코드 정리 배치가 풀스캔하지 않도록
CREATE INDEX idx_idempotency_expires ON idempotency_record (expires_at);
```

이 테이블로 처리 흐름을 다시 그리면 이렇게 된다. **"물어보고 처리"가 아니라 "일단 꽂아보고 결과로 판단"**이다.

```
INSERT INTO idempotency_record (..., status)
VALUES (..., 'IN_PROGRESS')
ON CONFLICT (user_id, endpoint, idempotency_key) DO NOTHING;

  삽입된 행이 1건  ->  내가 첫 요청이다. 선점 성공. 실제 결제를 실행한다.
  삽입된 행이 0건  ->  누군가 이미 선점했다. 그 행을 조회해 상태를 본다.
                        status = COMPLETED   ->  저장된 응답을 그대로 재생 (3-5)
                        status = IN_PROGRESS ->  아직 처리 중  ->  409 응답 (3-4)
```

`ON CONFLICT ... DO NOTHING`은 PostgreSQL에서 "충돌이 나면 예외를 던지지 말고 조용히 아무것도 하지 마라"는 지시다. 예외 처리 대신 **영향받은 행 수(0 또는 1)**로 분기할 수 있게 해 주므로, 정상 흐름을 `try/catch`로 표현하는 어색함이 사라진다.

여기서 놓치기 쉬운 결정적 디테일이 하나 있다. **`IN_PROGRESS` 행은 결제를 실행하기 전에 먼저 커밋되어야 한다.** 같은 트랜잭션 안에 두면 커밋 전까지 다른 트랜잭션이 그 행을 볼 수 없고(격리 수준이 그렇게 동작하도록 만들어져 있다), 그러면 두 번째 요청은 여전히 "선점자 없음"으로 판단하거나 유니크 제약에 걸려 대기하게 된다. 선점 표식은 **다른 요청에게 보여주기 위한 것**이므로 반드시 먼저 커밋한다.

```java
// 선점 전용 트랜잭션 — 바깥 트랜잭션과 분리해 즉시 커밋한다.
// REQUIRES_NEW는 "호출한 쪽에 트랜잭션이 있어도 새 트랜잭션을 따로 열어라"는 뜻이다.
@Transactional(propagation = Propagation.REQUIRES_NEW)
public boolean tryClaim(IdempotencyKeyScope scope, String requestHash) {
    // insertIfAbsent 내부는 위의 ON CONFLICT DO NOTHING.
    // 반환값은 실제로 삽입된 행 수다.
    return repository.insertIfAbsent(scope, requestHash, Status.IN_PROGRESS) == 1;
}
```

### 3-4. 동시에 같은 키가 들어왔을 때 — 처리 중(IN_PROGRESS)에는 무엇을 반환하는가

선점에 실패한 두 번째 요청이 마주하는 상황은 두 가지인데, 둘의 성격이 완전히 다르다.

**첫째, 선점자가 이미 처리를 끝낸 경우(COMPLETED).** 답이 명확하다. 저장된 응답을 그대로 돌려주면 된다. 클라이언트 입장에서는 재시도가 성공한 것처럼 보이고, 서버 상태는 결제 1건 그대로다. 이것이 멱등성 키의 정상 동작이다.

**둘째, 선점자가 아직 처리 중인 경우(IN_PROGRESS).** 여기가 설계 판단이 필요한 지점이다. 돌려줄 응답이 아직 존재하지 않는다. 선택지는 셋이다.

```
[선택지 ① 기다린다 — 선점자가 끝날 때까지 폴링하다가 응답을 재생]
  장점: 클라이언트가 결과를 한 번에 받는다.
  단점: 이 요청이 스레드를 붙잡고 대기한다. 선점자가 느리면 대기 요청도 같이 느려지고,
        재시도가 몰리면 대기 중인 스레드가 쌓여 스레드 풀이 고갈된다.
        (장애 중인 시스템에 대기 요청이 쌓이는 것은 전형적인 장애 증폭 경로다)

[선택지 ② 409 Conflict를 준다 — "같은 키가 처리 중이다. 잠시 후 다시 와라"]
  장점: 스레드를 즉시 놓아준다. 서버가 부하 상황에서도 무너지지 않는다.
        클라이언트에게 "중복 실행이 아니라 아직 진행 중"이라는 정확한 정보가 전달된다.
  단점: 클라이언트가 이 응답을 이해하고 재시도하도록 구현해야 한다.

[선택지 ③ 그냥 처리한다]
  중복 결제. 논외.
```

**실무의 기본값은 ②다.** 근거는 "대기는 부하를 흡수하지 못하고 이전할 뿐"이기 때문이다. 재시도가 오는 상황은 대체로 시스템이 이미 느린 상황이고, 거기서 요청을 대기시키면 느림이 대기 스레드 형태로 축적된다.

409를 고른 이유도 짚어두자. **409 Conflict는 "요청 자체는 유효한데 리소스의 현재 상태와 충돌한다"는 뜻**이다. 여기서 충돌하는 현재 상태가 바로 "같은 키의 요청이 처리 중"이다. 400(요청 형식이 틀림)도 아니고 500(서버 잘못)도 아닌, 정확히 상태 충돌이다. 그리고 `Retry-After` 헤더를 함께 내려주면 클라이언트가 언제 다시 와야 하는지까지 알려줄 수 있다.

```java
// After: 선점 결과에 따라 세 갈래로 분기한다
@PostMapping("/payments")
public ResponseEntity<?> pay(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody PaymentRequest request,
        @AuthenticationPrincipal Long userId) {

    IdempotencyKeyScope scope = IdempotencyKeyScope.of(userId, "POST /payments", key);
    String requestHash = Hashing.sha256Hex(request);   // 같은 키 + 다른 본문을 잡기 위한 지문

    // 조회하지 않고 곧바로 INSERT를 시도한다.
    // "이미 있나?"의 판정과 선점이 DB 안에서 한 번에 원자적으로 일어난다.
    if (!idempotencyService.tryClaim(scope, requestHash)) {
        // 선점 실패 = 누군가 먼저 왔다. 그 레코드를 보고 무엇을 돌려줄지 정한다.
        return replayOrConflict(scope, requestHash);
    }

    // 선점 성공 = 내가 첫 요청이다. 실제 결제를 실행한다.
    PaymentResponse response = paymentService.pay(request);

    // 결제 결과와 멱등 레코드 완료 처리는 반드시 한 트랜잭션이다 (3-5).
    idempotencyService.complete(scope, HttpStatus.CREATED.value(), response);

    return ResponseEntity.created(URI.create("/payments/" + response.id())).body(response);
}

private ResponseEntity<?> replayOrConflict(IdempotencyKeyScope scope, String requestHash) {
    IdempotencyRecord record = idempotencyService.get(scope);

    // 같은 키로 다른 내용이 왔다 = 클라이언트가 키를 잘못 재사용한 것.
    // 저장된 응답을 돌려주면 "다른 결제인데 남의 결과를 받는" 사고가 되므로 거부한다.
    if (!record.requestHash().equals(requestHash)) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
                HttpStatus.UNPROCESSABLE_ENTITY,
                "이미 다른 요청 본문에 사용된 Idempotency-Key입니다.");
        return ResponseEntity.unprocessableEntity().body(problem);
    }

    // 처리가 끝났다 = 저장해 둔 첫 응답을 그대로 재생한다. 이것이 멱등성의 실현이다.
    if (record.status() == Status.COMPLETED) {
        return ResponseEntity.status(record.responseStatus()).body(record.responseBody());
    }

    // 아직 처리 중이다 = 응답이 존재하지 않는다.
    // 대기하지 않고 409로 즉시 돌려보내 스레드를 놓아준다.
    ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.CONFLICT, "동일한 Idempotency-Key의 요청이 처리 중입니다.");
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .header(HttpHeaders.RETRY_AFTER, "1")   // 1초 뒤에 다시 오라는 안내
            .body(problem);
}
```

**`IN_PROGRESS`가 영원히 남는 경우**까지 생각해야 구현이 완성된다. 선점 직후 서버 인스턴스가 죽으면 그 레코드는 `IN_PROGRESS`인 채로 남고, 이후 모든 재시도가 영원히 409를 받는다. 결제는 실행되지 않았는데 클라이언트는 영영 성공할 수 없는 상태다.

대응은 **선점에 유효기간(lease)을 두는 것**이다. 일정 시간 이상 `IN_PROGRESS`인 레코드는 "죽은 선점"으로 보고 회수한다.

```sql
-- 30초 넘게 IN_PROGRESS인 레코드는 선점자가 죽은 것으로 간주하고 회수한다.
-- 이 UPDATE가 1행을 바꿨다면 회수에 성공한 것이고, 그 요청이 새 선점자가 된다.
-- (동시에 두 요청이 회수를 시도해도 UPDATE의 조건절이 한쪽만 통과시킨다)
UPDATE idempotency_record
   SET status = 'IN_PROGRESS', created_at = now(), request_hash = :newHash
 WHERE user_id = :userId AND endpoint = :endpoint AND idempotency_key = :key
   AND status = 'IN_PROGRESS'
   AND created_at < now() - interval '30 seconds';
```

유효기간의 길이는 **"이 API의 최대 처리 시간보다 충분히 길게"** 잡는다. 너무 짧으면 정상적으로 처리 중인 요청을 살아 있는데도 회수해 중복 실행이 나고, 너무 길면 죽은 선점이 오래 남아 클라이언트가 그동안 성공할 수 없다. 즉 **이 값은 안전과 복구 속도의 트레이드오프**이며, 안전 쪽으로 기울여 잡는 것이 원칙이다.

### 3-5. 응답 본문 캐싱 — 두 번째 요청에 무엇을 돌려주는가

멱등성 키가 "중복 실행만 막으면 되는" 장치라고 생각하면 절반만 이해한 것이다. **두 번째 요청에도 첫 번째와 같은 응답을 돌려줘야** 클라이언트 입장에서 재시도가 성공한 것이 된다.

왜 중요한지 반례로 보자. 중복 실행은 막았는데 두 번째 요청에 "이미 처리됨"이라는 빈 응답이나 에러를 준다면, 클라이언트는 결제 ID를 받지 못한다. 결제는 됐는데 클라이언트는 어떤 결제가 됐는지 모르는 상태가 되고, 결국 조회 API를 따로 호출해 찾아야 한다. **멱등성 키를 붙인 목적(클라이언트가 아무 고민 없이 재시도할 수 있게 하는 것)이 절반만 달성된다.**

그래서 첫 응답의 **상태 코드와 본문을 통째로 저장**한다. 위 DDL의 `response_status`, `response_body`가 그것이다. `jsonb`로 저장하면 PostgreSQL이 JSON 구조를 이해한 채로 보관하므로 나중에 운영 중 조회할 때 편하다.

**저장 시점이 핵심이다.** 결제 결과 커밋과 멱등 레코드 완료 처리는 **반드시 같은 트랜잭션**이어야 한다.

```
[잘못된 경우 — 결제 커밋과 레코드 완료가 다른 트랜잭션]

  t0  결제 INSERT + COMMIT            ★ 돈은 이미 빠져나갔다
  t1  서버 크래시
  t2  멱등 레코드는 IN_PROGRESS인 채로 남는다
  t3  lease 만료 -> 재시도가 회수에 성공 -> 결제를 다시 실행  ->  중복 결제

[올바른 경우 — 한 트랜잭션]

  BEGIN
    결제 INSERT
    UPDATE idempotency_record SET status='COMPLETED', response_body=... 
  COMMIT                              ★ 둘 다 남거나 둘 다 없다

  중간에 죽으면 결제도 롤백되므로, 재시도가 처음부터 다시 해도 안전하다.
```

```java
// 결제 확정과 멱등 레코드 완료를 한 트랜잭션으로 묶는다.
// 이 둘이 갈라지면 "결제는 됐는데 기록이 없어 다시 결제되는" 경로가 열린다.
@Transactional
public void complete(IdempotencyKeyScope scope, int status, Object body) {
    repository.markCompleted(scope, status, body);
}
```

다만 결제가 **외부 PG사 API 호출**이라면 그 호출은 우리 DB 트랜잭션에 묶이지 않는다. 이 경우에는 "외부 호출 직전에 시도 사실을 기록하고, 결과를 받으면 그것을 확정 기록한다"는 별도의 흐름이 필요하며, 그래도 남는 결과 불명 구간은 PG사의 조회 API로 대사(對査)해 메운다. **DB 트랜잭션으로 묶을 수 있는 범위와 그렇지 않은 범위를 구분하는 것**이 이 설계의 경계선이다.

### 3-6. 키의 유효 범위와 TTL — 어느 사용자, 어느 엔드포인트, 언제까지

유니크 제약을 `idempotency_key` 하나가 아니라 `(user_id, endpoint, idempotency_key)` 셋으로 건 이유를 이제 설명할 수 있다.

**`user_id`를 포함하는 이유는 키가 사용자 사이를 넘나들면 안 되기 때문이다.** 키는 클라이언트가 만든 문자열이고, 서버는 그것이 진짜 랜덤한지 검증할 방법이 없다. 만약 키가 전역 유일해야 한다면, 어떤 사용자가 (실수든 고의든) 다른 사용자가 쓴 키와 같은 값을 보냈을 때 **남의 결제 응답을 그대로 받아보게 된다.** 결제 ID, 금액, 카드 뒷자리 같은 것이 응답에 담겨 있다면 그대로 정보 유출이다. 사용자 범위로 가두면 이 경로가 원천 차단된다.

**`endpoint`를 포함하는 이유는 서로 다른 작업이 같은 키를 공유하면 안 되기 때문이다.** 클라이언트가 화면 진입 시 UUID 하나를 만들어 그 화면의 여러 API에 재사용하는 실수는 흔하다. 범위가 엔드포인트별로 나뉘어 있으면 `POST /payments`의 키와 `POST /refunds`의 키가 서로 간섭하지 않는다.

**`request_hash`는 유니크 제약이 아니라 검증용**이다. 같은 범위·같은 키인데 요청 본문이 다르다면, 그것은 "재시도"가 아니라 "클라이언트가 키를 잘못 재사용한 것"이다. 이때 저장된 응답을 재생하면 **9,900원 결제를 요청했는데 이전의 50,000원 결제 응답을 받는** 최악의 사고가 난다. 그래서 본문 해시가 다르면 재생하지 않고 명시적으로 거부한다(위 코드의 422 응답). 본문 전체를 저장해 비교할 수도 있지만 저장 비용이 크므로 SHA-256 같은 해시 지문으로 대신한다.

**TTL(유효기간)은 "클라이언트의 재시도 윈도우보다 충분히 길게"** 잡는다. 판단 기준을 순서대로 따라가 보자. 클라이언트의 재시도가 지수 백오프로 최대 몇 분까지 이어질 수 있는가. 사용자가 앱을 껐다 켜고 다시 시도하는 경우까지 감쌀 것인가. 배치나 서버 간 호출이라면 장애 복구 후 재처리까지 감쌀 것인가. 결제 서비스들이 하루 정도를 두는 사례가 흔한데, 이는 "사람이 개입해 재시도하는 시간까지 넉넉히 덮는다"는 판단이다.

TTL이 필요한 이유는 단순하다. **키 레코드가 무한히 쌓이면 테이블이 계속 커지고 인덱스가 무거워진다.** 그래서 만료된 레코드를 주기적으로 지운다.

```sql
-- 만료된 멱등 레코드 정리 (배치로 주기 실행)
-- expires_at 인덱스가 있으므로 풀스캔하지 않는다.
-- LIMIT을 둬서 한 번에 지우는 양을 제한하는 이유는, 대량 DELETE가
-- 긴 트랜잭션과 락을 만들어 운영 중인 결제 요청에 영향을 주지 않게 하기 위해서다.
DELETE FROM idempotency_record
 WHERE id IN (
    SELECT id FROM idempotency_record
     WHERE expires_at < now()
     LIMIT 1000
 );
```

TTL을 짧게 잡을 때의 위험을 정확히 알아두자. **TTL이 만료된 뒤에 도착한 재시도는 "처음 보는 키"가 되어 그대로 다시 실행된다.** 즉 짧은 TTL은 중복 실행의 창을 다시 여는 것이다. 저장 비용과 중복 방지 기간 사이의 트레이드오프이며, 돈이 걸린 API에서는 저장 비용 쪽을 감수하는 것이 원칙이다.

### 3-7. Redis로 하면 안 되는가

멱등성 키 저장소로 Redis를 떠올리는 것은 자연스럽다. `SET key value NX EX 86400` 한 줄이면 원자적 선점과 TTL이 동시에 해결되고, DB보다 빠르다.

**읽기 성격의 중복 방지에는 충분하다.** 다만 결제처럼 돈이 걸린 경로에서 판단 기준은 둘이다.

첫째, **결제 기록과 멱등 레코드를 한 트랜잭션으로 묶을 수 있는가.** 3-5에서 봤듯이 이 둘이 갈라지면 중복 실행 경로가 열린다. 결제 기록이 PostgreSQL에 있다면 멱등 레코드도 같은 DB에 둬야 한 트랜잭션이 된다. Redis에 두면 "DB는 커밋됐는데 Redis 기록이 실패"하는 이중 쓰기 문제가 그대로 생긴다.

둘째, **키가 유실돼도 되는가.** Redis의 기본 구성은 메모리 기반이고 영속화 설정에 따라 최근 쓰기가 유실될 수 있다. 키가 유실되면 그 키의 재시도는 "처음 보는 요청"으로 다시 실행된다.

정리하면 **정합성 요구가 낮은 중복 방지에는 Redis가 합리적이고, 돈이 걸린 경로에서는 비즈니스 데이터와 같은 DB에 두는 것이 안전하다.** "빠르니까 Redis"가 아니라 "무엇과 한 트랜잭션이어야 하는가"가 선택 기준이다.

## 4. 꼬리질문 대비 포인트

### "DELETE가 멱등이라면서요 — 두 번째 DELETE는 404가 나오는데, 그래도 멱등인가요?"

멱등이다. **멱등성의 기준은 응답 코드가 아니라 서버의 최종 상태**이기 때문이다. 첫 DELETE 후에도 "리소스 없음", 두 번째 후에도 "리소스 없음"이므로 서버 상태는 동일하고, 응답이 204에서 404로 달라지는 것은 멱등성 위반이 아니다. 명세가 약속하는 것은 "클라이언트가 요청한 의도된 효과"이지 "매번 같은 응답"이 아니다.

여기서 한 걸음 더 들어가면 설계 판단이 나온다. **두 번째 DELETE에 404를 줄 것인가 204를 줄 것인가**는 규약이 정해주지 않는, 선택의 문제다. 404를 주면 "이번 호출은 지울 게 없었다"는 사실을 정직하게 전달하지만, 재시도 로직이 404를 실패로 오해할 수 있다. 204를 주면 재시도 클라이언트가 다루기 편하지만 "실제로 있었는지"를 구분할 수 없어진다.

실무에서는 **"클라이언트가 원하는 것은 '없는 상태'이고 이미 그 상태이므로 204"**를 택하는 경우가 많고, 어느 쪽을 택하든 API 문서에 명시해 클라이언트가 재시도 시 404를 성공으로 처리하도록 안내하는 것이 중요하다. 규약이 정해주지 않는 지점을 알아보고 "그래서 팀에서 정해 문서화한다"까지 말하면 실무 감각이 드러난다.

### "PUT과 POST는 어떻게 구분해서 쓰나요?"

**의미로 구분한다.** PUT은 "이 URI의 리소스를 이 내용으로 교체하라"이고, POST는 "이 데이터를 처리하라(주로 하위 리소스 생성)"이다.

가장 실용적인 판별 기준은 **"결과 리소스의 URI를 누가 정하는가"**다. 클라이언트가 대상 URI를 알고 지정할 수 있으면 PUT이고, 서버가 정해서 알려줘야 하면 POST다. `PUT /users/123/profile`은 클라이언트가 "123번의 프로필"이라는 대상을 알고 있으므로 PUT이 자연스럽고, `POST /orders`는 주문 번호를 서버가 발급하므로 POST가 자연스럽다.

여기서 재시도 관점을 얹으면 답이 한 단계 올라간다. **어떤 쓰기 연산이 자연스럽게 멱등일 수 있다면 PUT으로 설계하는 것이 클라이언트를 이롭게 한다.** 예를 들어 "장바구니에 상품 A를 3개 담는다"를 `POST /cart/items {"productId": "A", "qty": 3}`(추가)로 만들면 재시도할 때마다 수량이 누적되지만, `PUT /cart/items/A {"qty": 3}`(교체)로 만들면 몇 번을 재시도해도 수량은 3이다. **같은 기능을 멱등한 형태로 표현할 수 있는지 먼저 따져보는 것**이 멱등성 키 같은 별도 장치를 도입하기 전의 순서다.

### "PATCH는 왜 멱등이 아닌가요? 멱등일 수도 있나요?"

PATCH는 "부분 수정"이라는 틀만 정하고 **수정 내용의 성질은 규약이 정하지 않기 때문에** 멱등을 보장하지 않는다로 분류된다. "보장하지 않는다"와 "멱등이 아니다"는 다른 말이라는 점이 핵심이다.

`{"name": "A"}`처럼 **절대값을 지정**하는 패치는 사실상 멱등이다. 반면 `{"op": "increment", "field": "point", "by": 100}`처럼 **상대 연산**을 담으면 반복할 때마다 결과가 달라진다. 구현자가 어느 쪽을 만드는지 클라이언트와 인프라는 알 수 없으므로, 규약은 안전한 쪽(보장하지 않음)으로 분류한다.

그래서 정확한 답변은 이것이다. **"PATCH는 구현이 멱등할 수는 있으나, 클라이언트와 중간 인프라가 멱등이라고 가정해서는 안 되는 메서드다."** 뒤집어 말하면, 내가 만든 PATCH가 멱등하더라도 자동 재시도 라이브러리는 그것을 모르므로 재시도해 주지 않는다 — 재시도가 필요하다면 API 문서로 명시하거나 멱등성 키를 붙여야 한다.

### "read timeout이 났을 때 메서드별로 재시도 판단이 어떻게 달라지나요?"

read timeout은 **요청이 서버에 도달해 처리됐을 가능성이 있는 실패**다. 즉 "결과 불명" 상태이고, 여기서 재시도해도 되는지를 결정하는 것이 멱등성이다.

GET, HEAD, OPTIONS, PUT, DELETE는 처리됐더라도 재전송 결과가 같으므로 **즉시 재시도해도 된다.** POST와 PATCH는 처리 여부를 모르는 채 재시도하면 중복 실행이므로, ① 멱등성 키가 걸려 있으면 재시도하고, ② 없으면 조회 API로 처리 여부를 확인한 뒤 판단하며, ③ 그것도 불가능하면 사용자에게 결과 확인을 요청한다.

여기에 **connection timeout과의 대비**를 얹으면 답변이 완성된다. connection timeout은 TCP 연결 수립 단계의 실패라 **요청 바이트가 아직 나가지 않았고**, 서버는 그 요청의 존재조차 모른다. 따라서 POST라도 안전하게 재시도할 수 있다. 다만 안전한 진짜 조건은 "connection timeout이라서"가 아니라 **"요청을 한 바이트도 쓰지 않았음이 확실해서"**이므로, 요청 전송 도중 끊긴 경우는 read timeout과 같이 취급해야 한다.

이 답을 상태 코드 지식과 연결하면 한 겹 더 깊어진다. **504 Gateway Timeout이 그 자체로 "재시도해도 되는 코드"가 아니다.** 504는 게이트웨이가 뒷단의 응답을 제때 못 받았다는 뜻이므로 **뒷단은 이미 처리했을 수 있다.** 코드가 5xx라는 사실보다 "요청이 어느 단계까지 갔는가"와 "그 요청이 멱등한가"가 재시도 가능 여부를 결정한다.

### "멱등성 키를 실제로 구현할 때 고려할 점은?" (시니어 변별 포인트)

다섯 가지로 답한다.

**(1) 확인과 선점은 원자적이어야 한다.** "조회해서 없으면 처리한다"는 구조는 동시 요청 두 건이 나란히 통과한다. 그리고 재시도는 첫 요청이 처리 중인 바로 그 순간에 도착할 확률이 높으므로, 이 창은 이론적 위험이 아니라 현실적 위험이다. PostgreSQL의 유니크 제약 + `ON CONFLICT DO NOTHING`으로 판정과 선점을 DB 안에서 한 번에 처리한다.

**(2) 처리 중(IN_PROGRESS) 상태를 별도로 다뤄야 한다.** 선점 실패에는 "이미 끝났다"와 "아직 하는 중이다" 두 경우가 있고, 후자에는 돌려줄 응답이 없다. 대기시키면 스레드가 쌓여 장애가 증폭되므로 `409 Conflict` + `Retry-After`로 즉시 돌려보내는 것이 기본값이다. 그리고 선점 직후 인스턴스가 죽으면 `IN_PROGRESS`가 영원히 남으므로 **선점에 유효기간을 둬서 회수**해야 한다.

**(3) 첫 응답을 저장해 재생해야 한다.** 중복 실행만 막고 두 번째 요청에 빈 응답을 주면, 클라이언트는 결제가 됐는지 어떤 결제가 됐는지 모른다. 상태 코드와 본문을 저장하고, **저장은 비즈니스 데이터 커밋과 같은 트랜잭션**이어야 한다 — 갈라지면 "결제는 됐는데 기록이 없어 다시 결제되는" 경로가 열린다.

**(4) 키의 범위와 TTL을 정해야 한다.** 키는 `(사용자, 엔드포인트, 키값)`으로 묶어 남의 응답을 받거나 다른 API의 응답이 섞이는 것을 막는다. 같은 키에 다른 본문이 오면 재생하지 말고 명시적으로 거부한다(요청 본문 해시 비교) — 재생하면 다른 금액의 결제 응답을 돌려주는 사고가 난다. TTL은 클라이언트의 재시도 윈도우보다 충분히 길게 두되, 만료 후 도착한 재시도는 다시 실행된다는 점을 알고 정한다.

**(5) 저장소는 "무엇과 한 트랜잭션이어야 하는가"로 고른다.** Redis의 `SET NX EX`는 원자적 선점과 TTL을 한 줄로 주지만 비즈니스 데이터와 트랜잭션을 공유하지 못하고 유실 가능성이 있다. 돈이 걸린 경로에서는 비즈니스 데이터와 같은 DB에 두는 것이 안전하다.

여기까지 말하면 개념을 아는 사람이 아니라 실제로 만들어 운영해 본 사람으로 보인다.

## 한 줄 요약

안전(safe)은 "서버 상태를 바꾸지 않는다"(GET/HEAD/OPTIONS), 멱등은 "반복해도 **서버의 최종 상태**가 같다"(안전한 메서드 + PUT/DELETE)는 계약이고 — 기준이 응답이 아니라 상태이므로 두 번째 DELETE의 404는 멱등성 위반이 아니다 — 이 계약이 read timeout처럼 결과가 불명한 실패에서 재시도 가능 여부를 결정하고 캐시·브라우저·크롤러·자동 재시도 같은 중간 인프라의 동작 전제가 되므로, 규약을 어긴 API(상태를 바꾸는 GET)는 내 코드가 아니라 인프라가 사고를 내고, 본질적으로 비멱등인 POST에는 유니크 제약으로 원자적 선점 + 처리 중(409) 응답 + 첫 응답 재생 + 범위·TTL 관리를 갖춘 멱등성 키로 서버가 직접 멱등성을 보장해 준다.
