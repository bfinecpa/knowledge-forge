# 502 vs 504 — 상태 코드 하나가 정해주는 장애 첫 1분의 방향

> 핵심 관전 포인트: **502와 504는 앱이 만든 코드가 아니라, 요청을 대신 전달하던 프록시(Nginx, 로드밸런서)가 "뒤쪽 백엔드와의 대화가 실패했다"며 스스로 만들어 붙인 코드다. 갈림길은 "백엔드가 응답을 시도할 수 있었는가"다 — 502 Bad Gateway는 연결이 거부됐거나 도중에 끊겼거나 HTTP로 해석할 수 없는 응답이 온 것이라 "백엔드가 죽었거나 깨졌다"는 가설로 배포 이력·프로세스 생존·프록시 에러 로그부터 보고, 504 Gateway Timeout은 프록시가 정한 대기 상한 안에 응답이 오지 않은 것이라 "백엔드가 살아 있는데 느리다"는 가설로 응답시간 지표와 그 뒤의 대기(DB, 외부 호출, 스레드 풀)부터 본다. 여기에 두 가지를 더 알아야 초동에서 헤매지 않는다 — 코드를 만든 주체가 프록시라서 앱 로그가 깨끗할 수 있다는 것, 그리고 504 뒤에는 프록시는 포기했는데 백엔드는 끝까지 처리해 커밋해버리는 "유령 성공"과 사용자 재시도로 인한 중복 처리 위험이 따라온다는 것이다.**

---

## 0. 질문 + 의도

**질문**: "502와 504의 차이 — 각각 발생했을 때 어디를 먼저 봐야 하나요?"

**출제 의도**: 상태 코드 하나가 "백엔드가 죽었다"와 "백엔드가 느리다"를 갈라준다. 장애 첫 1분에 보는 방향을 정해주는 지식 — 초동 대응 속도의 차이를 만드는지 확인하는 질문이다.

## 1. 공통 전제 — 이 코드들은 앱이 아니라 프록시가 만든다

### 1-1. 5xx 중에서 502와 504만 성격이 다르다

5xx는 전부 "서버 쪽 잘못"이라는 점에서 한 묶음이지만, **누가 그 코드를 만들어 냈는가**를 기준으로 보면 두 부류로 갈린다.

500 Internal Server Error는 애플리케이션 자신이 만든다. 컨트롤러 어딘가에서 예외가 터졌고, Spring이 그것을 잡아 "내가 처리하다 실패했다"고 응답한 것이다. 그러므로 500은 반드시 앱 로그에 스택 트레이스라는 형태의 물증을 남긴다.

**502와 504는 다르다. 이 둘은 요청을 대신 전달하던 중개자가 만든다.** 중개자란 Nginx, ALB 같은 로드밸런서, CloudFront 같은 CDN, API 게이트웨이처럼 클라이언트와 애플리케이션 사이에 서 있는 소프트웨어를 말한다. 이들이 "내가 뒤쪽 서버와 대화를 시도했는데 그 대화가 실패했다"고 판정해 **자기가 직접 만들어 반환하는 코드**가 502와 504다.

이 한 가지 전제에서 초동 대응의 큰 함정 하나가 바로 풀린다. **에러가 났다는데 앱 로그에 그 요청의 흔적이 아예 없을 수 있다는 것이다.** 502라면 요청이 앱에 도달조차 못 했을 수 있고, 504라면 앱은 아직 처리 중이었거나 뒤늦게 성공으로 끝냈을 수 있다. "사용자는 에러 화면을 봤다는데 우리 로그는 깨끗해요"는 모순이 아니라, **에러의 제조처가 앱이 아니라 프록시라는 힌트**다.

그래서 502/504의 1차 증거는 앱 로그가 아니다. **프록시의 에러 로그와 액세스 로그**다. 이 방향 전환을 첫 30초에 하느냐 마느냐가 초동 대응 속도를 가른다.

### 1-2. 업스트림(upstream)이란 무엇이고 왜 하필 "상류"인가

프록시 로그를 읽으려면 `upstream`이라는 단어를 먼저 넘어야 한다. 이 말이 정의 없이 던져지는 바람에 로그를 봐도 무슨 말인지 모르는 경우가 많다.

**업스트림은 프록시 관점에서 "요청을 넘겨받는 뒤쪽 서버", 즉 Nginx가 대신 요청을 보내주는 대상(보통 Tomcat, 애플리케이션 서버)을 가리킨다.** Nginx 설정에서 `upstream app { server 10.0.0.11:8080; }`이라고 쓰는 그 블록의 대상이 업스트림이다.

이름이 헷갈리는 이유는 "상류"라는 말의 직관과 반대로 느껴지기 때문이다. 사용자가 위에 있고 서버가 아래에 있는 그림을 그리면 백엔드는 "하류"여야 할 것 같다. 그런데 프록시의 관점은 다르다. **데이터가 흘러오는 방향을 기준으로 이름을 붙인 것이다.** 프록시가 클라이언트에게 내보낼 응답 데이터는 백엔드에서 흘러 내려온다. 강물이 상류에서 하류로 흐르듯, 응답이라는 물줄기의 발원지가 백엔드이므로 그쪽이 **upstream(상류)**이고, 프록시 자신과 클라이언트 쪽이 **downstream(하류)**이다.

```
      [클라이언트]  <----  [Nginx]  <----  [Tomcat]
       downstream            나            upstream
                                      (응답 데이터의 발원지)

      요청은 왼쪽에서 오른쪽으로 가지만,
      이름은 "응답이 흘러오는 방향" 기준으로 붙어 있다.
```

이 정의를 손에 쥐면 로그 문장이 그대로 읽힌다. `while connecting to upstream`은 "뒤쪽 서버에 연결하는 중에", `while reading response header from upstream`은 "뒤쪽 서버가 준 응답 헤더를 읽는 중에"라는 뜻이다. 그리고 **로그 문장의 이 부분이 502와 504를 진단하는 가장 중요한 단서**다. 실패가 연결 단계에서 났는지, 응답을 읽는 단계에서 났는지를 알려주기 때문이다.

### 1-3. 비유 — 프록시는 전화 교환원이다

프록시를 전화 교환원이라고 생각하면 두 코드의 차이가 한 번에 잡힌다.

고객(클라이언트)이 회사 대표번호로 전화를 건다. 교환원(프록시)이 받아서 담당 부서(백엔드)로 연결해 준다.

**502는 "연결해 드렸는데 상대가 전화를 안 받거나, 받자마자 끊거나, 알아들을 수 없는 소리만 냅니다"**에 해당한다. 대화 자체가 성립하지 않은 것이다.

**504는 "연결은 됐는데 제가 정한 시간 안에 답이 안 와서 제가 끊었습니다"**다. 상대는 살아 있고 아마 지금도 뭔가 찾고 있을 텐데, 교환원이 더 못 기다리고 끊은 것이다.

여기서 중요한 지점 하나. **두 경우 모두 고객에게 상황을 알린 것은 담당 부서가 아니라 교환원이다.** 담당 부서는 자기 앞에서 무슨 일이 벌어졌는지 모를 수도 있다. 특히 504의 경우, 담당 부서는 여전히 자료를 찾고 있고 잠시 후 "찾았습니다!"라고 말하겠지만 그때는 이미 아무도 듣고 있지 않다. 이것이 뒤에 나올 유령 성공의 정체다.

### 1-4. 503과는 무엇이 다른가 — 의도가 있는 거절

502/504와 자주 헷갈리는 것이 503 Service Unavailable이다. 셋을 가르는 기준은 **"거절에 의도가 있었는가"**다.

**503은 의도적인 거절이다.** 서버가 스스로 "지금은 처리할 수 없지만 나중엔 될 수 있다"고 말하는 코드다. 과부하를 막으려고 요청을 차단했거나, 점검 모드로 내려놓았거나, 헬스체크에 실패해 로드밸런서 대상 풀에서 스스로 빠진 상태가 여기 해당한다. 의도가 있으므로 **`Retry-After` 헤더로 "언제쯤 다시 오라"고 안내할 수 있고**, 재시도 라이브러리는 그 값을 존중해 대기한다.

**502/504에는 의도가 없다.** 프록시가 뒷단과 통신을 시도한 결과로 판정된 것이지, 누구도 "지금은 거절하겠다"고 결정하지 않았다. 그래서 502/504에는 "언제 다시 오라"고 말할 근거가 없다.

```
  503  "지금은 안 받겠습니다. 30초 뒤에 오세요."       <- 결정한 주체가 있다
  502  "연결이 안 되거나 대화가 깨졌습니다."           <- 사고의 보고
  504  "제한 시간 안에 답이 안 와서 제가 끊었습니다."  <- 사고의 보고
```

다만 실무에서는 **같은 상황에 제품마다 다른 코드를 매기는** 지점이 있어서 일반론만으로는 부족하다. 예를 들어 "살아 있는 백엔드가 하나도 없다"는 상황에서 Nginx는 `no live upstreams` 로그와 함께 **502**를 내지만, AWS ALB는 등록된 정상 대상이 없을 때 **503**을 낸다. 코드만 보고 제품 동작을 단정하지 말고, **"우리 인프라의 LB/게이트웨이가 어떤 상황에 몇 번을 내는지"를 미리 문서로 확인해두는 것**이 실전 대응력이다. (이 정리는 05번 문서의 5xx 절과 같은 기준으로 쓰였다.)

## 2. 502 Bad Gateway — "백엔드가 대화 자체를 못 했다"

### 2-1. 정의 — 유효한 응답을 아예 받지 못했다

502는 **프록시가 백엔드로부터 HTTP 응답으로 인정할 만한 것을 하나도 받지 못한** 경우다. "느리다"가 아니라 "못 받았다"이다. 구체적으로는 세 갈래다.

첫째, **연결 자체가 안 됐다.** TCP 연결을 맺으려 했는데 거부당했거나, 경로가 없거나, 넘길 수 있는 백엔드가 하나도 남아 있지 않은 경우다.

둘째, **연결은 됐는데 대화가 도중에 끊겼다.** 요청을 보냈는데 응답 헤더를 다 받기 전에 상대가 연결을 닫아버리거나(FIN), 강제로 끊어버린(RST) 경우다.

셋째, **응답이 오긴 왔는데 HTTP로 해석할 수 없다.** 상태 줄 형식이 깨졌거나, 응답 헤더가 프록시의 버퍼보다 커서 담을 수 없거나, 애초에 HTTP를 말하지 않는 포트에 붙은 경우다.

세 갈래 모두 공통점은 **"백엔드가 정상적으로 대화할 상태가 아니었다"**는 것이다. 그래서 502의 첫 가설은 언제나 **"백엔드가 죽었거나 깨졌다"**가 된다.

### 2-2. 원인별 지문 — Nginx error log 문구가 원인을 직접 말해준다

502는 원인이 여럿이라 "이것저것 다 봐야 한다"로 흐르기 쉽다. 그런데 **Nginx는 왜 502를 냈는지를 error log에 문장으로 남긴다.** 이 문구와 원인을 짝지어 외워두면 조사 범위가 한 번에 좁혀진다. 실무에서 가장 값이 나가는 지식이 이 매핑이다.

| Nginx error log 문구 | 실제로 일어난 일 | 첫 확인 대상 |
|---|---|---|
| `connect() failed (111: Connection refused) while connecting to upstream` | 그 IP:포트에 리슨 중인 프로세스가 없다 — 커널이 즉시 RST로 거절했다 | 백엔드 프로세스 생존, 배포/재시작 이력, `proxy_pass` 주소·포트 오타 |
| `connect() failed (113: No route to host)` 또는 `upstream timed out ... while connecting to upstream` | SYN이 아예 도달하지 못했다 — 라우팅 단절, 보안 그룹·방화벽 차단, 또는 백엔드의 accept 큐 포화 | 보안 그룹·네트워크 ACL, 서브넷/라우팅, 백엔드의 accept 백로그 |
| `upstream prematurely closed connection while reading response header from upstream` | 요청은 보냈는데 응답 헤더가 오기 전에 상대가 연결을 닫았다 | keep-alive 유휴 경쟁(2-4절), 처리 중 프로세스 크래시·OOM kill |
| `recv() failed (104: Connection reset by peer) while reading response header from upstream` | 상대가 RST로 강제 종료했다 | 프로세스 강제 종료, 백엔드 앞단의 방화벽이 유휴 연결을 RST로 끊는 구성 |
| `no live upstreams while connecting to upstream` | upstream 그룹의 서버가 전부 "실패 누적"으로 일시 제외된 상태다 | `max_fails`/`fail_timeout` 설정과, 전체 백엔드가 동시에 나간 원인 |
| `upstream sent too big header while reading response header from upstream` | 응답 헤더가 `proxy_buffer_size` 한 조각을 넘었다 | 응답에 실리는 쿠키·토큰 크기, `proxy_buffer_size` 값 (13번 문서 3절) |
| `upstream sent no valid HTTP/1.0 header` / `upstream sent invalid header` | 돌아온 바이트가 HTTP 응답 형식이 아니다 | 포트 착오(HTTP가 아닌 서비스에 붙음), 앱이 응답 앞에 이물질을 출력하는 버그 |

표를 외우기보다 **읽는 규칙 두 개**를 기억하는 편이 낫다.

**규칙 하나 — `while connecting`이면 연결 단계, `while reading response header`면 응답 단계다.** 앞의 것은 "백엔드에 닿지도 못했다"이므로 네트워크·프로세스 생존을 보고, 뒤의 것은 "닿긴 했는데 응답이 깨졌다"이므로 백엔드 내부 사정을 본다.

**규칙 둘 — 괄호 안 숫자는 리눅스 errno다.** 111은 `ECONNREFUSED`(거부), 104는 `ECONNRESET`(강제 종료), 110은 `ETIMEDOUT`(시간 초과), 113은 `EHOSTUNREACH`(경로 없음)다. 이 네 개만 알면 처음 보는 로그도 해석된다.

`no live upstreams`는 조금 더 설명이 필요하다. Nginx는 upstream 그룹의 서버가 `fail_timeout` 시간(기본 10초) 안에 `max_fails` 회(기본 1회) 실패하면 그 서버를 그 시간 동안 후보에서 뺀다. **그룹의 모든 서버가 이렇게 빠지면 보낼 곳이 없어져 `no live upstreams`가 되고 502가 된다.** 그러므로 이 로그는 "지금 이 순간 문제"가 아니라 **"조금 전에 전체 백엔드가 동시에 실패했다"는 과거의 흔적**으로 읽어야 한다. 진짜 원인은 그 직전 로그에 있다.

### 2-3. 최다 용의자 — 배포 시간대의 502 스파이크

502의 원인 중 압도적으로 빈도가 높은 것은 **롤링 배포 중에 생기는 짧은 502 스파이크**다. 원리를 타임라인으로 보면 왜 "잘 만든 무중단 배포"조차 502를 흘리는지가 보인다.

문제의 뿌리는 **"인스턴스를 내리는 일"과 "로드밸런서 대상 목록에서 빼는 일"이 서로 다른 주체가 하는 별개의 작업**이라는 데 있다. 이 둘의 순서가 어긋나면 틈이 생긴다.

```
  [나쁜 순서 — 종료가 먼저, 대상 제외가 나중]

  t = 0.0s   배포 시스템이 인스턴스 A에 SIGTERM 전송
  t = 0.0s   A의 Tomcat이 종료 절차 시작 — 리슨 소켓부터 닫는다
             ┃
             ┗━ 이 순간부터 A의 8080 포트는 새 연결을 받지 못한다

  t = 0.0s   그런데 Nginx/LB의 대상 목록에는 A가 아직 남아 있다.
             헬스체크 주기 5초 x 실패 임계 2회 = 최대 10초 동안
             LB는 A가 죽은 줄 모르고 계속 요청을 보낸다.

  t = 0.5s   Nginx -> A로 새 요청
             ┃
             ┗━ connect() failed (111: Connection refused)
                -> 사용자에게 502

  t = 10.0s  헬스체크 2회 실패 누적. 이제야 A가 대상 목록에서 빠진다.
             -> 이 10초 동안의 요청이 전부 502였다.
```

여기에 두 번째 틈이 겹친다. **새로 뜬 인스턴스 B를 "프로세스가 떴다"는 이유로 대상에 넣으면**, 아직 Spring 컨텍스트 초기화나 커넥션 풀 워밍업이 끝나지 않은 상태에서 요청을 받아 또 502나 타임아웃이 난다.

그래서 해결은 **두 틈을 각각 메우는 것**이고, 설정이 셋으로 나뉜다.

```yaml
# application.yml — 종료 쪽 틈 메우기 (1) 진행 중 요청을 마저 처리한다
server:
  # SIGTERM을 받으면 새 요청 수용은 멈추되, 처리 중인 요청은 끝까지 처리하고 종료한다.
  # 이 설정이 없으면 처리 중이던 요청의 연결이 그대로 끊겨 502가 된다.
  shutdown: graceful

spring:
  lifecycle:
    # 위 graceful shutdown이 진행 중 요청을 기다려 줄 최대 시간.
    # 이 시간을 넘기면 남은 요청을 버리고 종료하므로, 최장 요청보다 길게 잡는다.
    timeout-per-shutdown-phase: 30s

management:
  endpoint:
    health:
      probes:
        # liveness(살아 있나)와 readiness(요청 받을 준비가 됐나)를 분리해 노출한다.
        # 이 둘을 구분해야 "떴지만 아직 준비 안 됨" 상태에 트래픽을 안 보낼 수 있다.
        enabled: true
```

```yaml
# Kubernetes Deployment — 종료 쪽 틈 메우기 (2) 순서를 강제한다
lifecycle:
  preStop:
    exec:
      # 컨테이너 종료 신호와 "엔드포인트에서 제외" 전파는 병렬로 일어난다.
      # 여기서 잠깐 버텨 LB/Service가 나를 목록에서 빼는 것을 먼저 끝내게 만든다.
      # 이 sleep이 없으면 위의 graceful shutdown도 "이미 죽은 나에게 오는 요청"은 못 막는다.
      command: ["sh", "-c", "sleep 15"]

readinessProbe:
  httpGet:
    # 투입 쪽 틈 메우기: "프로세스 기동"이 아니라 "요청 처리 가능"을 확인한 뒤에만
    # 트래픽을 받는다. readiness가 통과하기 전에는 Service 엔드포인트에 등록되지 않는다.
    path: /actuator/health/readiness
    port: 8080
  periodSeconds: 2
```

면접에서 이 질문이 나오면 **"graceful shutdown을 켠다"까지만 말하는 사람과, "종료 신호와 대상 제외가 별개의 주체가 하는 병렬 작업이라 순서를 강제해야 한다"까지 말하는 사람의 차이**가 그대로 드러난다. 무중단 배포는 설정 한 줄이 아니라 **순서의 문제**다.

### 2-4. 백엔드는 멀쩡한데 나는 502 — keep-alive 유휴 경쟁

배포도 없었고 프로세스도 멀쩡한데 하루에 몇 번씩 무작위로 502가 나는 경우가 있다. 로그 문구는 대개 `upstream prematurely closed connection while reading response header from upstream`이다.

정체는 **연결 재사용의 경쟁 조건**이다. Nginx는 백엔드로 나가는 연결을 매번 새로 맺지 않고 풀에 넣어 재사용하는데, 그 유휴 연결을 **백엔드(Tomcat)가 먼저 닫는 순간과 Nginx가 그 연결에 새 요청을 실어 보내는 순간이 겹치면** 요청이 이미 끊긴 연결로 날아간다.

핵심은 **Nginx가 이것을 미리 알 방법이 없다는 것**이다. 상대가 보낸 FIN은 "내 송신 방향이 끝났다"는 통보일 뿐이라 Nginx의 송신 방향은 여전히 열려 있고, 그래서 요청을 쓰는 `write()`는 **성공해 버린다**. 실패는 응답을 읽으려는 순간에야 드러난다.

이 타임라인과 대응 규칙(재사용하는 쪽의 유휴 상한을 닫는 쪽보다 짧게)은 **10번 문서 3-3절에 한 단계씩 그려져 있으므로 여기서 반복하지 않는다.** 502 진단의 관점에서 기억할 것은 세 가지 증상이 한 세트로 나타난다는 점이다.

```
  (1) 간헐적이다 — 부하와 무관하게 하루에 몇 번, 재현이 안 된다
  (2) 백엔드 지표가 멀쩡하다 — CPU, 스레드, 응답시간 모두 정상
  (3) 로그가 upstream prematurely closed connection이다
```

이 3종 세트를 보고 keep-alive 경쟁을 즉시 꺼낼 수 있으면 실전 경험이 드러난다. Nginx와 Tomcat 사이의 구체적인 설정 정렬은 13번 문서 2절에서 다룬다.

### 2-5. 502의 조사 동선

지금까지의 내용을 실제로 움직이는 순서로 압축하면 이렇다. **순서가 중요한 이유는 앞쪽 단계가 압도적으로 빈도가 높기 때문**이다.

**1단계 — 시각을 먼저 본다.** 502가 시작된 시각에 배포·재시작·오토스케일링 이벤트가 있었는지 확인한다. 여기서 걸리면 조사가 5분 만에 끝난다.

**2단계 — 백엔드 프로세스의 생존을 본다.** 크래시, OOM kill(컨테이너 메모리 제한 초과 포함), 헬스체크 탈락으로 대상 풀에서 전부 빠졌는지. 컨테이너 환경이면 재시작 횟수(`RESTARTS`)와 종료 코드(OOM kill이면 137)가 단서다.

**3단계 — 프록시 error log의 문구를 읽는다.** 2-2절의 표로 원인을 특정한다. 여기까지 오면 대부분 답이 나온다.

**4단계 — 문구가 `prematurely closed`인데 1~3단계가 전부 정상이면** keep-alive 경쟁을 의심한다(2-4절).

## 3. 504 Gateway Timeout — "백엔드가 살아 있는데 느리다"

### 3-1. 어느 타임아웃이 터졌는가 — 504는 "느리다"만을 뜻하지 않는다

504는 프록시가 정한 대기 상한이 만료된 것이다. 그런데 프록시에는 **대기 상한이 하나가 아니라 여럿**이고, 어느 것이 터졌는지에 따라 조사 방향이 달라진다. 이 구분을 안 하면 "백엔드가 느린가 보다"라고 단정했다가 엉뚱한 곳을 파게 된다.

```nginx
location /api/ {
    proxy_pass http://app;

    # (1) 백엔드와 TCP 연결을 맺는 데까지의 상한.
    #     이게 터지면 "백엔드가 느린 것"이 아니라 "연결이 안 되는 것"이다.
    #     로컬 네트워크의 연결 수립은 밀리초 단위이므로 몇 초면 충분하다.
    proxy_connect_timeout 3s;

    # (2) 백엔드에 요청 본문을 쓰는 도중의 상한.
    #     주의: 전체 전송 시간이 아니라 "연속된 두 번의 쓰기 사이" 간격이다.
    proxy_send_timeout 10s;

    # (3) 백엔드의 응답을 읽는 도중의 상한. 504의 최다 발원지.
    #     주의: 전체 응답 시간이 아니라 "연속된 두 번의 읽기 사이" 간격이다.
    #     이 오해가 매우 흔하다 — 자세한 설명은 13번 문서 1절.
    proxy_read_timeout 10s;
}
```

세 값 모두 만료 시 504로 이어질 수 있지만 **원인은 완전히 다르다.**

`proxy_connect_timeout` 만료는 **"닿지 못했다"**이다. 백엔드는 느린 게 아니라 SYN에 답을 못 하고 있는 것이다. 보안 그룹이 막았거나, 라우팅이 끊겼거나, 백엔드의 accept 큐(연결 수락 대기열)가 꽉 차서 SYN을 흘리고 있는 경우다. **이때 "DB 슬로우 쿼리를 찾겠다"고 나서면 하루를 버린다.** 로그의 `while connecting to upstream`이 이것을 구분해 준다.

`proxy_read_timeout` 만료는 두 가지로 또 갈린다. `while reading response header from upstream`이면 **응답의 첫 바이트조차 오지 않은 것**으로, 백엔드가 아직 처리 중이라는 뜻이다. 우리가 흔히 말하는 "느린 백엔드"가 이것이다. 반면 `while reading upstream`이면 **응답 본문을 받다가 중간에 멈춘 것**이다.

여기에 실무에서 사람을 크게 헷갈리게 하는 사실 하나가 붙는다. **응답 헤더를 이미 클라이언트에게 내보낸 뒤에 읽기 타임아웃이 나면 프록시는 504를 낼 수 없다.** 상태 코드는 헤더에 실려 이미 나가버렸기 때문이다. 이 경우 클라이언트는 **200 OK인데 본문이 중간에 잘린 응답**을 받는다. "상태 코드는 200인데 JSON 파싱이 깨진다"는 제보가 오면 이 가능성을 떠올려야 한다.

### 3-2. 조사 동선 — 백엔드가 "무엇을 기다리는지"를 찾는다

로그가 `while reading response header`이고 백엔드가 정말 느린 것이 맞다면, 그다음은 **"백엔드가 왜 느린가"**다. 여기서 중요한 사고 전환이 하나 있다.

**애플리케이션이 느린 이유는 대부분 자기가 계산을 많이 해서가 아니라, 그 뒤의 무언가를 기다리기 때문이다.** CPU를 태우는 코드는 생각보다 드물고, 대부분은 어딘가에 대기하고 있다. 그러므로 조사는 "무엇을 기다리는가"를 찾는 일이 된다.

**첫째, 응답시간 지표의 모양을 본다.** p99가 언제부터 튀었는지, 그리고 **전체 API가 느린지 특정 API만 느린지**를 본다. 전체가 느리면 공용 자원(DB, 스레드 풀, GC)이 범인이고, 특정 API만 느리면 그 API가 부르는 것(특정 쿼리, 특정 외부 API)이 범인이다. 이 갈래 하나로 조사 범위가 절반이 된다.

**둘째, 스레드 덤프로 "지금 무엇을 기다리는지"를 직접 본다.** 이것이 가장 결정적인 증거다. 스레드가 소켓 읽기에서 멈춰 있으면 외부 호출 대기, DB 커넥션 획득에서 멈춰 있으면 커넥션 풀 고갈, 락 획득에서 멈춰 있으면 경합이다.

**셋째, 자주 나오는 범인 넷을 순서대로 확인한다.** DB 슬로우 쿼리와 락 대기, 외부 API 지연(특히 **타임아웃을 안 걸어둔 호출**은 무한정 기다린다), 커넥션 풀/스레드 풀 고갈, 그리고 GC 정지다.

**넷째, 트래픽 변화를 본다.** 급증으로 처리 능력을 넘어선 것이라면 **느려짐은 결과이지 원인이 아니다.** 이 경우 쿼리를 튜닝해도 근본이 안 풀린다.

### 3-3. 504의 함정 — 유령 성공과 중복 처리

504에는 상태 코드 진단과는 별개로, **데이터 정합성 사고로 번지는 함정**이 하나 붙어 있다. 이것을 아느냐가 이 주제에서 주니어와 시니어를 가른다.

전제는 한 문장이다. **프록시의 타임아웃은 프록시의 "기다림"을 중단시킬 뿐, 백엔드의 "처리"를 중단시키지 않는다.** 둘은 서로 다른 프로세스이고, 프록시가 포기했다는 사실이 백엔드에 전달되는 표준적인 경로는 없다.

```
  [유령 성공 타임라인 — proxy_read_timeout 10s인 결제 API]

  t =  0.0s  사용자: "결제하기" 클릭
             클라이언트 -> Nginx -> Tomcat : POST /orders
  t =  0.1s  Tomcat 스레드가 요청을 받아 처리 시작
             ┃ PG사 결제 승인 API 호출 -> 응답 대기 중

  t = 10.0s  ★ Nginx의 proxy_read_timeout 만료 ★
             ┃
             ┣━ Nginx -> 클라이언트 : 504 Gateway Timeout
             ┃                        사용자 화면: "오류가 발생했습니다"
             ┃
             ┗━ Nginx -> Tomcat : 업스트림 연결을 끊는다

  t = 10.0s  Tomcat 쪽에서 일어나는 일: ★ 아무것도 없다 ★
             끊긴 것은 소켓이지 스레드가 아니다.
             서블릿 스레드는 여전히 PG 응답을 기다리는 중이고,
             자기 요청이 취소됐다는 통보를 받지 못한다.

  t = 14.0s  PG 승인 성공 -> 주문 INSERT -> ★ COMMIT ★
             ┃ 트랜잭션은 여기서 이미 확정됐다.
             ┗━ 이제 200 응답을 쓰려 하지만 소켓은 이미 닫혀 있다
                -> ClientAbortException (또는 조용히 무시)

             앱 로그: "주문 생성 완료 orderId=8471"  <- 성공으로 남는다

  t = 20.0s  사용자가 "다시 시도" 클릭
             -> 두 번째 주문 생성, 두 번째 결제 승인
             -> ★ 이중 결제 ★
```

**t = 14.0s의 COMMIT이 응답 쓰기보다 먼저 일어난다는 것이 핵심**이다. 응답 전송이 실패해도 트랜잭션은 이미 커밋됐다. 그래서 데이터베이스에는 주문이 남고, 사용자 화면에는 실패가 떠 있는 어긋난 상태가 만들어진다.

여기서 **"504가 났는데 앱 로그에는 성공으로 남아 있다"**는 미스터리가 풀린다. 모순이 아니라 정상적인 귀결이다.

그리고 이 함정의 진짜 위험은 프록시가 아니라 **사용자와 재시도 로직**에 있다. 사용자는 실패 화면을 봤으므로 다시 누른다. 클라이언트 SDK나 앞단 게이트웨이에 재시도가 걸려 있다면 사람이 누르기도 전에 자동으로 다시 보낸다. **"응답을 못 받았다"는 상태는 "실패했다"와 다르다** — 성공했는데 결과를 못 받았을 수도 있는데, 재시도하는 쪽은 이 둘을 구분할 방법이 없다.

그래서 대응은 두 방향이다.

**첫째, 계층 간 타임아웃을 정렬한다.** 프록시의 대기 상한이 백엔드 작업의 최악 소요보다 길어야 유령 성공 자체가 안 생긴다. 구체적인 정렬 원칙과 숫자 예시는 13번 문서 2절에서 다룬다.

**둘째, 쓰기 API를 멱등하게 만든다.** 타임아웃은 아무리 정렬해도 완전히 없앨 수 없으므로, **같은 요청이 두 번 와도 결과가 한 번 실행한 것과 같도록** 만드는 것이 근본 방어다. 클라이언트가 요청마다 고유한 멱등성 키를 만들어 보내고 서버는 그 키에 유니크 제약을 걸어 두 번째 요청을 걸러낸다. 구현 상세(테이블 설계, 처리 중 상태에 무엇을 반환할지, 응답 본문 캐싱, 키의 유효 범위)는 **04번 문서 3절**에 있다.

**"504 조사"와 "멱등성 도입"은 별개의 후속 과제로 함께 열려야 한다**는 것이 이 절의 결론이다. 느린 원인을 고쳐도 이미 발생한 중복 데이터는 남아 있고, 앞으로도 타임아웃은 또 난다.

### 3-4. 한눈 비교 — 502, 504, 503

앞에서 설명한 것들을 짧게 대조하면 이렇다.

| | 502 Bad Gateway | 504 Gateway Timeout | 503 Service Unavailable |
|---|---|---|---|
| 무슨 일이 있었나 | 유효한 응답을 못 받음 | 제한 시간 안에 응답이 안 옴 | 서버가 의도적으로 거절 |
| 백엔드 상태 가설 | 죽었다 / 연결이 깨졌다 | 살아 있는데 느리다 | 살아 있는데 지금은 안 받는다 |
| 먼저 볼 곳 | 배포 이력, 프로세스 생존, 프록시 error log | 응답시간 지표, DB·외부 호출·스레드 풀, 스레드 덤프 | 과부하 차단·점검 모드 설정, 헬스체크 상태 |
| 요청의 행방 | 도달 못 했거나 도중에 끊김 | 처리 중이었고 뒤늦게 성공했을 수도(유령 성공) | 처리 시작조차 안 됨 |
| 재시도해도 되나 | 도달 전 실패면 안전, 도중 끊김이면 불확실 | 불확실 — 멱등성 없이는 위험 | 안전(`Retry-After` 존중) |

**"재시도해도 되나" 행이 실무에서 가장 자주 판단해야 하는 항목**이다. 502 중에서도 `connection refused`는 요청이 도달조차 못 했으므로 재시도가 안전하지만, `prematurely closed`는 백엔드가 요청을 받아 처리하다 끊긴 것일 수도 있어 안전하지 않다. **같은 502라도 로그 문구에 따라 재시도 안전성이 달라진다**는 것까지 말하면 이 표를 외운 게 아니라 이해한 것으로 들린다.

## 4. 꼬리질문 대비 포인트

### "502가 배포 시간대에만 몇 초씩 발생합니다. 원인과 해결은?"

롤링 재시작에서 **두 개의 틈**이 생기기 때문이다. **첫째, 내려가는 쪽의 틈** — 인스턴스가 리슨 소켓을 닫았는데 로드밸런서의 대상 목록에는 아직 남아 있어, 헬스체크가 실패를 감지할 때까지(주기 x 임계 횟수만큼) 죽은 인스턴스로 요청이 계속 간다. **둘째, 올라오는 쪽의 틈** — 프로세스가 떴다는 이유로 트래픽을 넣었는데 컨텍스트 초기화나 커넥션 풀 워밍업이 안 끝나 실패한다.

해결은 두 틈을 각각 메우는 것이다. 내려가는 쪽은 **graceful shutdown**(새 요청 수용은 멈추고 처리 중 요청은 끝까지 처리)과 **연결 드레이닝**(LB 대상에서 먼저 빼고 나서 종료 시작)이고, 올라오는 쪽은 **readiness 프로브**("프로세스 기동"이 아니라 "요청 처리 가능"을 확인한 뒤에만 트래픽 투입)다.

여기서 한 걸음 더 들어가면 변별이 된다. **종료 신호 전달과 "대상 목록에서 제외" 전파는 서로 다른 주체가 병렬로 하는 일이라, graceful shutdown만 켜도 순서는 보장되지 않는다.** 그래서 쿠버네티스라면 `preStop` 훅에 짧은 대기를 넣어 "제외가 먼저 끝나고 나서 종료가 시작되게" 순서를 강제한다. 무중단 배포는 설정 한 줄이 아니라 **순서 설계**라는 것이 이 질문의 채점 포인트다.

### "504가 났는데 백엔드 로그에는 그 요청이 성공으로 남아 있습니다. 어떻게 해석하나요?"

**모순이 아니라 정상적인 귀결이다.** 프록시의 타임아웃은 프록시의 기다림을 끊을 뿐 백엔드의 처리를 중단시키지 않는다. 프록시가 504를 내보낸 뒤에도 백엔드 스레드는 계속 일했고, 커밋까지 마친 뒤 응답을 쓰려다 이미 닫힌 소켓을 만난 것이다. **커밋이 응답 전송보다 먼저 일어난다**는 순서가 이 현상의 전부다.

증거로 삼을 것은 **프록시 타임아웃 값과 백엔드 처리 시간의 대소 관계**다. `$upstream_response_time`이 `proxy_read_timeout`에 정확히 붙어 있으면 "백엔드가 느렸다"가 아니라 "프록시가 못 기다렸다"는 뜻이므로, 계층 간 타임아웃 부정합이 확정된다.

대응은 세 갈래다. **(1)** 타임아웃 정렬 — 바깥 상한 안에 안쪽 작업의 최악 소요가 들어오게 한다. **(2)** 쓰기 API의 멱등성 키 도입 — 사용자가 재시도해도 중복 처리가 안 되게 한다. **(3)** 그 요청이 왜 그렇게 오래 걸렸는지를 별도 과제로 추적한다. **세 가지를 다 말하되 (2)를 빼먹지 않는 것**이 중요하다. (1)만 하면 다음 타임아웃 때 또 같은 사고가 난다.

### "503과는 어떻게 구분하나요?"

**기준은 "거절에 의도가 있었는가"다.** 503은 서버가 스스로 "지금은 처리할 수 없지만 나중엔 될 수 있다"고 판단해 내리는 코드다 — 과부하 차단, 점검 모드, 헬스체크 실패로 인한 풀 제외가 여기 해당한다. 의도가 있으므로 `Retry-After`로 재시도 시점을 안내할 수 있다. 반면 502/504는 프록시가 뒷단과 통신을 시도한 **결과**로 판정된 것이라 의도가 없고, 안내할 재시도 시점도 없다.

다만 실무에서는 **같은 상황에 제품마다 다른 코드를 매기는 지점**이 있다는 것을 덧붙여야 답이 완성된다. "살아 있는 백엔드가 하나도 없다"는 상황에서 Nginx는 `no live upstreams`와 함께 502를 내지만, ALB는 정상 대상이 없을 때 503을 낸다. 그러므로 일반론 위에 **"우리 인프라의 LB/게이트웨이가 어떤 상황에 몇 번을 내는지"를 미리 확인해두는 것**이 실전 대응력이다. (가산점 포인트)

### "간헐적 502가 'upstream prematurely closed connection' 로그와 함께 납니다. 백엔드는 멀쩡해 보이는데요?"

**keep-alive 유휴 타임아웃 경쟁의 전형이다.** 백엔드(Tomcat)가 유휴 연결을 닫는 순간과 프록시(Nginx)가 그 연결을 재사용하는 순간이 겹치면, 요청이 막 끊긴 연결에 실려 나가 502가 된다.

이 답변에서 반드시 짚어야 할 것은 **왜 Nginx가 미리 알 수 없는가**다. 상대가 보낸 FIN은 "상대 송신 방향이 끝났다"는 통보일 뿐이고 내 송신 방향은 여전히 열려 있으므로(half-close), **요청을 쓰는 write는 성공해 버린다.** 오류는 응답을 읽으려는 순간에야 드러난다. 즉 "보내기 전에 살아 있는지 확인"이라는 접근으로는 원천적으로 막을 수 없다.

그러므로 대응은 **"이 상황 자체가 안 생기게 순서를 정하는 것"** — 재사용하는 쪽(Nginx)의 유휴 상한을 닫는 쪽(Tomcat)의 유휴 상한보다 짧게 잡아, 닫는 결정을 우리가 통제하게 만든다(10번 문서 3-3절, 설정 정렬은 13번 문서 2절).

**"간헐적 + 백엔드 지표 정상 + premature close 로그"라는 3종 세트에서 이 가설을 즉시 꺼낼 수 있으면** 실전 경험이 드러난다. 원인을 모르면 몇 주씩 헤매는 종류의 장애이기 때문이다.

### "CDN → LB → Nginx → 앱처럼 프록시가 여러 층이면, 어느 층이 만든 502/504인지 어떻게 찾나요?" (시니어 변별 포인트)

**에러 코드는 "그것을 만든 층의 아래쪽"에 문제가 있다는 뜻이므로, 제조 층을 특정하는 순간 조사 범위가 절반씩 줄어든다.** 예를 들어 CDN이 만든 504라면 문제는 LB 이하 어딘가이고, Nginx가 만든 504라면 문제는 앱 이하다. 그래서 제일 먼저 할 일은 원인 찾기가 아니라 **층 특정**이다.

방법은 세 가지이고, 셋 다 **평시에 준비해 둬야 장애 당일에 쓸 수 있다**는 것이 이 질문의 진짜 포인트다.

**첫째, 요청 ID를 전 층에 전파해 하나의 요청을 층층이 추적한다.** 최전방에서 요청마다 고유 ID를 만들어 헤더로 붙이고, 각 층이 그것을 로그에 남기며 뒤로 전달한다. 그러면 한 번의 검색으로 **"이 요청이 어느 층까지 도달했는가"**가 나온다. 3층 로그에 있는데 4층 로그에 없으면 3층이 반려한 것이다.

```nginx
# Nginx — 요청 ID를 만들거나(없으면) 이어받아(있으면) 뒤로 전달한다
map $http_x_request_id $req_id {
    # 앞단(CDN/LB)이 이미 ID를 붙였으면 그것을 그대로 쓴다.
    # 층마다 새 ID를 만들면 층 간 연결이 끊겨 추적이 불가능해진다.
    default   $http_x_request_id;
    # 비어 있으면 Nginx가 만든 요청 고유 ID를 쓴다.
    ""        $request_id;
}

server {
    location /api/ {
        proxy_pass http://app;
        # 뒤쪽(Tomcat)에도 같은 ID를 넘겨 앱 로그와 이어 붙일 수 있게 한다.
        proxy_set_header X-Request-ID $req_id;
        # 응답에도 실어 보내면 사용자 문의 시 스크린샷의 ID로 바로 검색된다.
        add_header X-Request-ID $req_id always;
    }
}
```

**둘째, 액세스 로그에 "내가 받은 것"과 "내가 내보낸 것"을 나란히 남긴다.** 이게 층 특정의 결정적 증거다.

```nginx
log_format upstreamlog
    '$remote_addr "$request" '
    # 내가 클라이언트에게 내보낸 상태 코드
    'status=$status '
    # 업스트림이 나에게 준 상태 코드. 비어 있으면(-) 응답을 아예 못 받은 것이다.
    # status=504인데 upstream_status=- 이면 "내가 만든 504"가 확정된다.
    # status=502인데 upstream_status=502 이면 "뒤쪽이 준 502를 전달만 한 것"이다.
    'upstream_status=$upstream_status '
    # 연결 수립까지 걸린 시간. proxy_connect_timeout에 붙어 있으면 연결 단계 문제.
    'ucon=$upstream_connect_time '
    # 응답 헤더의 첫 바이트까지 걸린 시간. 백엔드 처리 시간의 실질적 지표.
    'uhdr=$upstream_header_time '
    # 업스트림 응답 전체에 걸린 시간. proxy_read_timeout 값에 딱 붙어 있으면
    # "백엔드가 느렸다"가 아니라 "내가 못 기다렸다"는 뜻이다.
    'ures=$upstream_response_time '
    # 실제로 어느 백엔드에 보냈는지. next_upstream 재시도가 있었으면 여러 개가 찍힌다.
    'uaddr=$upstream_addr '
    'req_id=$req_id';

access_log /var/log/nginx/access.log upstreamlog;
```

여기서 **`$status`와 `$upstream_status`의 조합을 읽는 법**이 핵심이다. `$upstream_status`가 비어 있으면(`-`) **응답을 아예 못 받았다는 뜻이므로 그 코드는 Nginx가 만든 것**이고, 값이 있으면 **뒤쪽이 만든 코드를 전달만 한 것**이다. 이 한 컬럼으로 "내가 범인인가 전달자인가"가 갈린다. `$upstream_addr`와 시간 지표들이 콤마나 콜론으로 여러 개 찍혀 있으면 `proxy_next_upstream` 재시도가 있었다는 뜻이다.

**셋째, 로그 접근 권한이 없거나 급할 때는 응답 자체의 지문을 읽는다.** 각 제품의 기본 에러 페이지와 헤더가 서로 다르기 때문에, 사용자가 보낸 스크린샷이나 `curl -i` 결과만으로도 층을 좁힐 수 있다.

| 응답의 지문 | 만든 층 |
|---|---|
| 본문에 `<center>nginx/1.x.x</center>` 푸터, `Server: nginx` | Nginx (단 `server_tokens off`면 버전은 안 보인다) |
| `Server: awselb/2.0`, 아주 간결한 HTML | AWS ALB |
| `X-Cache: Error from cloudfront`, `Via:` 헤더에 CloudFront | CloudFront |
| 우리 앱의 공통 에러 JSON 포맷 | 애플리케이션 (즉 이건 502/504가 아니라 500 계열) |

마지막 행이 중요하다. **응답 본문이 우리 앱의 에러 포맷이면 그것은 프록시가 만든 코드가 아니다.** 502/504인데 우리 에러 JSON이 나온다면 앱이 직접 그 코드를 반환한 것이므로(예: 앱이 다른 서비스를 부르는 게이트웨이 역할을 하는 경우) 조사 방향이 완전히 달라진다.

**평시에 이 준비(요청 ID 전파, 층별 로그 표준화)를 해둔 사람과, 장애 당일에 층층이 로그인해서 뒤지는 사람의 초동 속도 차이**가 이 질문이 재려는 것이다. 준비가 없으면 "어느 층이 만들었는지"를 알아내는 데만 30분을 쓰게 된다.

## 한 줄 요약

502와 504는 둘 다 프록시가 만드는 코드지만 세우는 가설이 다르다 — 502는 "백엔드가 대화 자체를 못 했다"이므로 배포 이력·프로세스 생존·프록시 error log 문구(`connection refused`인지 `prematurely closed`인지)부터 보고, 504는 "백엔드가 살아 있는데 느리다"이므로 응답시간 지표와 그 뒤의 대기(DB·외부 호출·스레드 풀)부터 본다. 여기에 코드를 만든 주체가 프록시라서 앱 로그가 깨끗할 수 있다는 것, 504 뒤에는 백엔드가 뒤늦게 커밋하는 유령 성공과 재시도로 인한 중복 처리 위험이 따라와 멱등성 키가 필요하다는 것, 그리고 프록시가 여러 층이면 요청 ID 전파와 `$upstream_status` 로깅으로 제조 층부터 특정해야 한다는 것까지가 초동 대응의 완성이다.
