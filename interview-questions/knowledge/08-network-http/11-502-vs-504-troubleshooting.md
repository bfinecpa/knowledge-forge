# 502 vs 504 — 상태 코드 하나가 정해주는 장애 첫 1분의 방향

> 핵심 관전 포인트: **둘 다 프록시(Nginx/LB)가 만들어 반환하는
> 코드이고, 갈림길은 "백엔드가 응답을 시도했는가"다. 502 Bad
> Gateway는 백엔드가 연결을 거부했거나 끊었거나 이상한 응답을 준 것
> — "백엔드가 죽었거나 깨졌다"이므로 프로세스 생존과 배포 이력부터
> 본다. 504 Gateway Timeout은 백엔드가 프록시의 대기 상한 안에 응답을
> 못 준 것 — "백엔드가 살아 있는데 느리다"이므로 응답 지연의 원인(DB,
> 외부 호출, 스레드 풀)을 본다. 코드를 만든 주체가 프록시라서 앱
> 로그에 아무 흔적이 없을 수 있다는 것까지 알아야 초동에서 헤매지
> 않는다.**

---

## 0. 질문 + 의도

**질문**: "502와 504의 차이 — 각각 발생했을 때 어디를 먼저 봐야 하나요?"

**출제 의도**: 상태 코드 하나가 "백엔드가 죽었다"와 "백엔드가
느리다"를 갈라준다. 장애 첫 1분에 보는 방향을 정해주는 지식 —
초동 대응 속도의 차이를 만드는지 확인하는 질문이다.

## 1. 공통 전제 — 이 코드들은 앱이 아니라 프록시가 만든다

5xx 중에서도 502/504는 성격이 다르다. 500은 애플리케이션 자신이
"내가 처리하다 터졌다"고 반환하는 코드지만, **502와 504는 요청을
대신 전달하던 중개자(Nginx, 로드밸런서, API 게이트웨이)가 "뒤쪽
백엔드와의 대화가 실패했다"며 자기가 만들어 반환하는 코드**다.

이 전제에서 초동 대응의 함정 하나가 바로 풀린다: **앱 로그에 그
요청의 흔적이 없을 수 있다.** 502라면 요청이 앱에 도달조차 못 했을
수 있고, 504라면 앱은 아직(혹은 뒤늦게 성공으로) 처리 중이었을 수
있다. "에러가 났다는데 앱 로그가 깨끗해요"는 모순이 아니라, 에러의
제조처가 프록시라는 힌트다. 그래서 502/504의 1차 증거는 앱 로그가
아니라 **프록시의 에러 로그와 액세스 로그**다.

비유하면 프록시는 전화 교환원이다. 502는 "연결해드렸더니 상대가
전화를 안 받거나 이상한 소리만 합니다", 504는 "연결은 됐는데
정해진 시간 안에 답이 안 와서 제가 끊었습니다" — 고객(클라이언트)에게
이 말을 전하는 것은 둘 다 교환원이다.

## 2. 502 Bad Gateway — "백엔드가 죽었거나 깨졌다"

프록시가 백엔드로부터 **유효한 응답을 아예 못 받은** 경우다.
연결 거부(connection refused), 전송 중 연결 끊김(reset/premature
close), HTTP로 해석 불가능한 응답 등.

**먼저 볼 곳 — 프로세스·연결 계층, 그리고 시각:**

1. **그 시각에 배포가 있었나** — 롤링 재시작 중 프로세스가 내려간
   틈에 트래픽이 들어오면 짧은 502 스파이크가 난다. 502의 최다 용의자.
2. **백엔드 프로세스가 살아 있나** — 크래시, OOM kill(컨테이너
   메모리 제한 초과 포함), 헬스체크 탈락으로 LB 대상에서 전부 빠진
   상태인지.
3. **프록시 에러 로그의 문구** — Nginx라면 원인을 문장으로 말해준다:

```
connect() failed (111: Connection refused) while connecting to upstream
  → 그 포트에 리슨 중인 프로세스가 없다: 죽었거나, 아직 안 떴거나, 포트/대상 설정 오류
upstream prematurely closed connection while reading response header
  → 백엔드가 응답 도중 연결을 끊었다: 처리 중 크래시, 또는 keep-alive 경합(4절)
```

즉 502의 질문은 "**백엔드가 왜 대화 자체를 못 했나**"이고, 동선은
배포 이력 → 프로세스/헬스체크 상태 → 프록시 에러 로그 순이다.

## 3. 504 Gateway Timeout — "백엔드가 살아 있는데 느리다"

연결은 됐지만 백엔드가 **프록시의 대기 상한 안에 응답을 못 준**
경우다. 프록시의 타임아웃 나사(Nginx의 `proxy_read_timeout` 등)가
터진 것이므로, 504의 발생 시각과 응답 시간이 프록시 타임아웃 값에
정확히 붙어 있는지부터 확인하면 판이 빨리 읽힌다.

**먼저 볼 곳 — 성능·의존성 계층:**

1. **백엔드 응답시간 지표** — p99가 언제부터 튀었나. 전체 요청이
   느린가, 특정 API만 느린가로 범위를 좁힌다.
2. **백엔드가 기다리는 것들** — 백엔드가 느린 이유는 대부분 그
   뒤의 무언가를 기다리기 때문이다: DB 슬로우 쿼리·락 대기, 외부 API
   지연(타임아웃 미설정이면 무한 대기), 스레드 풀 고갈(스레드 덤프로
   무엇을 기다리는지 확인), GC 정지.
3. **트래픽 변화** — 급증으로 처리 능력을 넘었는지(이 경우 느려짐은
   결과이지 원인이 아니다).

그리고 504에는 정합성 함정이 있다. 프록시는 포기했지만 **백엔드는
그 요청을 계속 처리해 뒤늦게 성공시켰을 수 있다** — 사용자는 실패를
봤는데 주문은 들어간 "유령 성공". 사용자가 재시도하면 중복 처리가
된다. 그래서 504가 잦은 구간은 조사와 별개로, 프록시 타임아웃 >
백엔드 내부 작업의 최악 소요가 되도록 계층 간 타임아웃을 정렬하고
쓰기 API에 멱등성을 갖추는 후속 과제가 따라온다.

```nginx
# 504를 만드는 나사들 — "어느 상한이 터졌나"를 알아야 지표와 대조할 수 있다
location /api/ {
    proxy_pass http://app;
    proxy_connect_timeout 3s;   # 백엔드 TCP 연결 수립까지의 대기
    proxy_read_timeout    10s;  # 응답(조각 사이) 대기 — 504의 최다 발원지
    proxy_send_timeout    10s;  # 요청 본문 전송 중 대기
}
```

### 한눈 비교

| | 502 Bad Gateway | 504 Gateway Timeout |
|---|---|---|
| 의미 | 백엔드가 유효한 응답을 못 줌 | 백엔드가 제시간에 응답을 못 줌 |
| 백엔드 상태 가설 | 죽었다 / 연결이 깨졌다 | 살아 있는데 느리다 |
| 먼저 볼 곳 | 배포 이력, 프로세스·헬스체크, 프록시 에러 로그 | 응답시간 지표, DB·외부 호출·스레드 풀 |
| 요청의 행방 | 도달 못 했거나 도중에 끊김 | 처리 중이었고 뒤늦게 성공했을 수도(유령 성공) |

## 4. 꼬리질문 대비 포인트

### "502가 배포 시간대에만 몇 초씩 발생합니다. 원인과 해결은?"

롤링 재시작 중 (1) 종료되는 인스턴스가 처리 중이거나 keep-alive로
물려 있던 연결을 끊고, (2) 새 인스턴스가 준비되기 전에 트래픽을
받는 두 틈에서 난다. 해결은 틈을 없애는 것: 종료 쪽은 graceful
shutdown(새 요청 차단 후 진행 중 요청 완료 대기)과 LB에서 먼저
빼는 연결 드레이닝, 투입 쪽은 "프로세스 기동"이 아니라 "요청 처리
가능"을 확인하는 readiness 헬스체크를 통과한 뒤에만 트래픽을 받게
하는 것이다. 무중단 배포의 실제 성립 조건을 아는지 보는 질문이다.

### "504가 났는데 백엔드 로그에는 그 요청이 성공으로 남아 있습니다. 어떻게 해석하나요?"

프록시가 자기 타임아웃에 걸려 클라이언트에게 504를 준 뒤에도
백엔드는 처리를 이어가 성공시킨 것이다 — 프록시 타임아웃 <
백엔드의 실제 처리 시간이라는 계층 간 부정합의 증거. 사용자는
실패로 인지하고 재시도할 수 있으므로 쓰기 요청이면 중복 처리
위험이 있다. 대응은 타임아웃 정렬(바깥 상한 안에 안쪽 작업의 최악
소요가 들어오게)과 쓰기 API의 멱등 키 도입이고, 근본적으로는 그
요청이 왜 그렇게 오래 걸렸는지를 별도로 추적한다.

### "503과는 어떻게 구분하나요?"

503 Service Unavailable은 "일시적으로 처리할 수 없음"의 표현으로,
서버 자신이 과부하·점검을 이유로 직접 반환하기도 하고, LB가 보낼
수 있는 정상 대상이 하나도 없을 때 반환하기도 한다. 다만 같은
상황이라도 프록시 제품에 따라 코드 매핑이 다를 수 있어(예: 살아있는
업스트림이 없을 때 어떤 제품은 502, 어떤 제품은 503), 일반론 위에
"우리 인프라의 LB/게이트웨이가 어떤 상황에 몇 번을 내는지"를 문서로
확인해두는 것이 실전 대응력이다. (가산점 포인트)

### "간헐적 502가 'upstream prematurely closed connection' 로그와 함께 납니다. 백엔드는 멀쩡해 보이는데요?"

keep-alive idle timeout 경합의 전형이다. 백엔드(Tomcat)가 유휴
연결을 닫는 순간과 프록시(Nginx)가 그 연결을 재사용하는 순간이
겹치면, 요청이 막 끊긴 연결에 실려 502가 된다 — 부하와 무관하게
드문드문 나는 것이 특징이다. 대응은 재사용하는 쪽(프록시)의 유휴
연결 유지 시간을 받는 쪽(백엔드)의 keep-alive timeout보다 짧게
정렬하는 것. "간헐 + 백엔드 정상 + premature close 로그"라는 3종
세트에서 이 가설을 꺼낼 수 있으면 실전 경험이 드러난다.

### "CDN → LB → Nginx → 앱처럼 프록시가 여러 층이면, 어느 층이 만든 502/504인지 어떻게 찾나요?" (시니어 변별 포인트)

에러 코드는 "그것을 만든 층의 아래쪽"이 문제라는 뜻이므로, 제조
층을 먼저 특정해야 조사 범위가 절반씩 줄어든다. 방법은 (1) 각 층의
액세스 로그를 대조 — 요청 ID(트레이스 헤더)를 전 층에 전파해두면 한
번의 검색으로 어느 층까지 도달했는지 나온다. Nginx라면 자신이 받은
업스트림 응답(`$upstream_status`)과 자신이 내보낸 응답(`$status`)을
로그에 나란히 남겨 "내가 만들었는지, 전달만 했는지"가 구분된다.
(2) 에러 응답의 형태 — 각 층의 기본 에러 페이지/헤더 서명이 다르다.
평시에 이 준비(요청 ID 전파, 층별 로그 표준화)를 해둔 사람과 장애
당일 층층이 로그인해서 뒤지는 사람의 초동 속도 차이가 이 질문의
핵심이다.

## 한 줄 요약

502와 504는 둘 다 프록시가 만드는 코드지만 가설이 다르다 — 502는
"백엔드가 대화를 못 했다"이므로 배포 이력·프로세스 생존·프록시 에러
로그부터, 504는 "백엔드가 살아 있는데 느리다"이므로 응답시간
지표와 그 뒤의 대기(DB·외부 호출·스레드 풀)부터 본다. 앱 로그에
흔적이 없을 수 있다는 것, 504 뒤에는 유령 성공과 중복 처리 위험이
따라온다는 것까지가 초동 대응의 완성이다.
