# Nginx의 역할과 이벤트 기반 아키텍처 — 요청이 앱에 도달하기 전 계층

> 핵심 관전 포인트: **Nginx는 클라이언트와 WAS(Tomcat) 사이에 서서
> 네 가지 일을 한다 — 리버스 프록시(단일 진입점·내부 은닉·TLS 종료),
> 정적 파일 서빙(비싼 WAS 스레드를 아낌), 버퍼링(느린 클라이언트로부터
> WAS를 격리), 로드밸런싱(여러 WAS로 분배). 이것이 가능한 이유가
> 이벤트 기반 아키텍처다 — 커넥션마다 스레드를 배정하는 대신 소수의
> 워커 프로세스가 이벤트 루프(epoll)로 수만 커넥션을 동시에 감시하므로,
> 커넥션이 많고 대부분이 "대기 중"인 일에 극단적으로 효율적이다.
> 운영 관점의 핵심: 이 계층에서 반려된 요청은 앱 로그에 아예 안 남는다 —
> Nginx를 모르면 "로그에 없는 장애" 앞에서 속수무책이 된다.**

---

## 0. 질문 + 의도

**질문**: "Nginx의 역할(reverse proxy, 정적 서빙, 버퍼링, LB)과 이벤트 기반 아키텍처를 설명해주세요."

**출제 의도**: 요청이 앱에 도달하기 전 계층에서 무슨 일이 벌어지는지
모르면, 앱 로그에 아무것도 없는 장애(Nginx에서 반려된 요청) 앞에서
속수무책이다. 후보자가 자기 애플리케이션 코드 바깥의 요청 경로까지
시야에 넣고 있는지, 그리고 "왜 Tomcat 앞에 굳이 Nginx를 두는가"를
아키텍처 원리(스레드 모델의 차이)로 설명할 수 있는지 확인한다.

## 1. Nginx가 서 있는 자리 — 리버스 프록시란

프록시(proxy)는 "대리인"이다. 방향에 따라 둘로 나뉜다.

| 구분 | 누구를 대리하나 | 서 있는 위치 | 예 |
|---|---|---|---|
| 포워드 프록시 | 클라이언트 | 클라이언트 쪽 출구 | 사내망 프록시, VPN |
| 리버스 프록시 | 서버 | 서버 쪽 입구 | Nginx, LB |

리버스 프록시는 **서버 쪽 대문**이다. 클라이언트는 Nginx의 주소만 알고,
뒤에 Tomcat이 몇 대인지, 어떤 포트인지 모른다. 요청은 항상
`클라이언트 → Nginx → Tomcat` 경로로 흐르고, 응답은 역방향으로 나간다.

대문을 하나로 모으면 얻는 것들:

- **단일 진입점**: 방화벽·보안 정책·접근 로그를 한 곳에서 관리한다.
  내부 서버들은 외부에 직접 노출되지 않는다.
- **TLS 종료(termination)**: HTTPS의 암복호화를 Nginx가 대신 처리하고,
  내부 구간은 평문 HTTP로 통신한다. 인증서 관리 지점이 한 곳이 된다.
- **공통 관심사의 앞단 처리**: 요청 크기 제한, 압축(gzip), 캐싱, 특정
  경로 차단 같은 일을 앱 코드 수정 없이 설정으로 해결한다.
- **무중단 배포의 지렛대**: 뒤쪽 서버를 하나씩 빼고 넣는 동안 대문은
  그대로이므로 클라이언트는 변화를 모른다.

**운영 관점에서 가장 중요한 함의**: 요청이 Nginx에서 반려되면(크기 초과
413, 뒤 서버 연결 실패 502, 응답 대기 초과 504 등) **그 요청은 Tomcat에
도달한 적이 없거나 응답을 전달받지 못한 것**이다. 앱 로그를 아무리 뒤져도
없다. "사용자는 에러를 봤다는데 우리 로그엔 없어요"라는 장애 보고를
받으면 첫 번째로 봐야 할 곳이 Nginx의 access log와 error log다.

## 2. 네 가지 역할

### (1) 정적 서빙 — 비싼 WAS 스레드를 아낀다

Tomcat의 요청 처리 단위는 스레드다. 스레드는 유한하고(워커 스레드 풀),
스택 메모리를 점유하는 비싼 자원이다. 이미지·JS·CSS 같은 정적 파일까지
Tomcat이 서빙하면, 비즈니스 로직을 처리해야 할 스레드가 파일 복사에
소모된다.

Nginx는 정적 파일 서빙에 특화되어 있다. `sendfile` 같은 커널 기능으로
파일을 유저 공간에 복사하지 않고 소켓으로 바로 흘려보내며(zero-copy),
이벤트 모델 덕에 스레드를 점유하지도 않는다.

```nginx
# 정적 파일은 Nginx가 직접, API만 Tomcat으로
server {
    location /static/ {
        root /var/www;          # 디스크에서 바로 서빙 — Tomcat 미경유
        expires 7d;             # 캐싱 헤더도 앞단에서
    }
    location /api/ {
        proxy_pass http://tomcat_upstream;   # 동적 요청만 뒤로
    }
}
```

(요즘은 정적 자산을 CDN에 두는 경우가 많지만, "정적/동적을 분리해
비싼 자원을 아낀다"는 원리는 동일하다 — CDN은 이 역할의 확장판이다.)

### (2) 버퍼링 — 느린 클라이언트로부터 WAS를 격리

인터넷 반대편의 클라이언트는 느리다(모바일 3G, 불안정한 와이파이).
버퍼링이 없다면 Tomcat 스레드는 느린 클라이언트의 속도에 맞춰
요청을 다 받을 때까지, 응답을 다 보낼 때까지 붙들려 있어야 한다.

Nginx는 중간에서 완충지대 역할을 한다:

- **요청 버퍼링**: 클라이언트의 요청 본문을 Nginx가 먼저 다 받아둔 뒤,
  로컬 네트워크의 빠른 속도로 Tomcat에 한 번에 전달한다.
- **응답 버퍼링**: Tomcat의 응답을 Nginx가 빠르게 받아 챙기고 Tomcat
  스레드를 즉시 해방시킨 뒤, 클라이언트에게는 그쪽 속도에 맞춰
  천천히 흘려보낸다.

비유하면 Tomcat 스레드는 시급이 비싼 전문가고, Nginx는 접수창구다.
전문가가 말 느린 고객을 직접 상대하면 시간이 낭비되므로, 접수창구가
서류를 다 받아서 한 번에 전달하고 결과도 대신 전달해 주는 구조다.
느린 클라이언트 수천 명이 붙어도 Tomcat 스레드는 "빠른 로컬 통신"만
하면 되니 회전율이 유지된다.

(이 버퍼의 크기·타임아웃 설정이 Tomcat 쪽 설정과 어긋나면 생기는
장애 패턴은 13번 문서에서 따로 다룬다.)

### (3) 로드밸런싱 — 여러 WAS로 분배

`upstream` 블록에 서버 여러 대를 등록하면 Nginx가 L7(HTTP 레벨)
로드밸런서로 동작한다.

```nginx
upstream tomcat_upstream {
    least_conn;                     # 활성 커넥션이 가장 적은 서버로
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    server 10.0.0.13:8080 backup;   # 평시엔 안 쓰고 전멸 시에만
}
```

- 분배 알고리즘: 라운드로빈(기본, 순서대로), `least_conn`(요청 처리
  시간 편차가 클 때 유리), `ip_hash`(같은 클라이언트를 같은 서버로 —
  세션 스티키니스가 필요할 때).
- 장애 감지: 오픈소스 Nginx는 **수동적(passive) 헬스체크**다 —
  요청을 보내봤다가 실패하면 그 서버를 일정 시간 제외한다. 즉 실패한
  실제 사용자 요청이 감지의 신호탄이라는 한계가 있다(능동적 헬스체크는
  상용판 또는 별도 모듈).

### (4) 그 외 앞단 공통 처리

접근 제어(IP 차단, rate limiting — `limit_req`), 응답 압축, 요청/응답
헤더 조작(클라이언트 IP를 뒤로 전달하는 `X-Forwarded-For` 부착 — 22번
문서), 간단한 응답 캐싱까지, "모든 요청이 지나는 길목"이라는 위치를
활용한 공통 관심사 처리가 이 계층의 일이다.

## 3. 이벤트 기반 아키텍처 — 왜 Nginx는 수만 커넥션을 버티나

### 스레드 모델의 대비

전통적인 웹서버(Apache prefork, Tomcat의 블로킹 커넥터)는
**커넥션(또는 요청)당 스레드/프로세스 하나**를 배정한다. 커넥션이
1만 개면 스레드도 그만큼 필요하다 — 스레드마다 스택 메모리를 점유하고,
스레드가 많아지면 컨텍스트 스위칭 비용이 처리량을 갉아먹는다.
이것이 유명한 **C10K 문제**(커넥션 1만 개를 어떻게 감당할 것인가)다.

Nginx의 답은 반대다. **워커 프로세스 몇 개(보통 CPU 코어 수만큼)가
각자 이벤트 루프를 돌리며 수만 개의 커넥션을 동시에 감시**한다.
커널의 이벤트 통지 메커니즘(리눅스의 epoll)에 "이 소켓들 중 뭔가
읽을/쓸 수 있게 되면 알려줘"라고 등록해 두고, 이벤트가 온 소켓만
꺼내서 처리하고 바로 다음 이벤트로 넘어간다.

핵심 통찰은 이것이다: **웹서버 일의 대부분은 "기다림"이다.** 클라이언트가
다음 바이트를 보내길, 뒤쪽 서버가 응답하길 기다리는 시간이 지배적이고
실제 CPU 작업은 짧다. 스레드-퍼-커넥션 모델은 이 기다림에 스레드라는
비싼 자원을 통째로 잠가두지만, 이벤트 모델은 기다림에는 자원을 거의
안 쓰고(커넥션 하나가 작은 상태 구조체 하나) 일이 생긴 순간에만 CPU를
쓴다.

비유: 스레드 모델은 손님마다 전담 웨이터를 붙이는 식당이다 — 손님이
메뉴판만 보고 있어도 웨이터는 옆에 서 있어야 한다. 이벤트 모델은
웨이터 몇 명이 홀 전체를 훑으며 "손짓한 테이블"만 응대하는 식당이다.
손님(커넥션) 수가 늘어도 웨이터(워커) 수는 늘릴 필요가 없다.

### 구조 요약

```
master process  ─ 설정 읽기, 워커 관리 (요청 처리 안 함)
 ├─ worker #1   ─ 이벤트 루프(epoll)로 수만 커넥션 처리
 ├─ worker #2   ─ (보통 worker_processes = CPU 코어 수)
 └─ ...
```

- master는 설정 리로드(`nginx -s reload`) 시 새 워커를 띄우고 기존
  워커는 처리 중 요청을 마치고 종료시킨다 — 무중단 설정 변경의 원리.
- 각 워커는 싱글 스레드 이벤트 루프이므로, **루프 안에서 블로킹되면
  그 워커가 담당한 모든 커넥션이 멈춘다.** 그래서 Nginx는 모든 I/O를
  논블로킹으로 하도록 설계되어 있고, 반대로 이것이 이벤트 모델의
  약점이기도 하다(꼬리질문 참고).

### Tomcat과의 궁합 (가산점 포인트)

이 대비가 "왜 Tomcat 앞에 Nginx를 두는가"의 아키텍처적 답이다.
Tomcat(전통적 구성)은 요청당 스레드 모델이라 **적은 수의 빠른 요청**에
알맞고, Nginx는 **많은 수의 느린 커넥션**에 알맞다. 그래서 인터넷의
느리고 수많은 클라이언트 커넥션은 Nginx가 물고(버퍼링·keep-alive 유지),
Tomcat에는 로컬 네트워크의 빠르고 짧은 커넥션만 흘려보낸다 — 두 스레드
모델이 각자 잘하는 구간을 맡는 분업이다.

## 4. 꼬리질문 대비 포인트

### "Tomcat도 HTTP 서버인데, 왜 굳이 앞에 Nginx를 두나요?"

기능이 겹쳐 보여도 스레드 모델이 다르기 때문이다. Tomcat은 요청당
스레드를 쓰므로 느린 클라이언트 커넥션 수만 개를 직접 물면 스레드 풀이
잠긴다. Nginx는 이벤트 루프라 그 커넥션들을 헐값에 유지하면서
버퍼링으로 Tomcat을 격리해 준다. 여기에 정적 서빙, TLS 종료, LB,
무중단 배포 지렛대, 공통 보안 정책까지 — 앱 코드 밖에서 해결하는 게
싼 일들을 모아 처리하는 계층이 생기는 것이다. 단, 클라우드 환경에서
ALB 같은 관리형 LB가 이 역할의 상당 부분을 대체하기도 한다는 점을
덧붙이면 시야가 넓어 보인다.

### "이벤트 루프 방식인데 워커 프로세스를 여러 개 두는 이유는?"

이벤트 루프 하나는 싱글 스레드라서 CPU 코어 하나만 쓴다. 멀티코어를
활용하려면 코어 수만큼 워커를 띄워 각자 독립적인 이벤트 루프를 돌리게
해야 한다(`worker_processes auto`). 또 프로세스 분리라서 워커 하나가
비정상 종료해도 나머지 워커와 master가 살아 있어 서비스가 유지된다.

### "Nginx가 반려한 요청은 어떻게 확인하나요?"

앱 로그가 아니라 Nginx의 access log(모든 요청의 상태 코드·응답 시간·
upstream 응답 시간)와 error log(반려 사유 — 크기 초과, upstream 연결
실패/타임아웃 등)를 본다. 특히 access log에 `$upstream_response_time`,
`$upstream_status`를 남기도록 로그 포맷을 잡아두면 "Nginx에서 끝난
요청"과 "Tomcat까지 갔다 온 요청"을 구분할 수 있어, 502/504 초동
대응에서 어느 계층 문제인지 바로 갈린다.

### "이벤트 기반 서버의 약점은 무엇인가요?" (시니어 변별 포인트)

이벤트 루프 안에서 하나라도 **블로킹**(오래 걸리는 CPU 연산, 블로킹
디스크 I/O)이 일어나면 그 워커가 담당한 수만 커넥션이 전부 멈춘다.
스레드 모델은 스레드 하나가 느려져도 다른 스레드가 돌지만, 이벤트
모델은 루프 자체가 급소다. 그래서 이벤트 기반 서버는 I/O 대기가
지배적인 프록시·정적 서빙에 최적이고, CPU 무거운 비즈니스 로직에는
스레드 모델(또는 워커 스레드 풀로의 오프로딩)이 맞다 — Node.js에서
CPU 작업이 이벤트 루프를 세우는 것과 같은 원리다. "그래서 Nginx와
Tomcat의 분업이 합리적"이라고 아키텍처 선택으로 연결하면 좋다.

### "정적 파일 서빙이 왜 그렇게 빠른가요?" (가산점 포인트)

`sendfile`(zero-copy) 덕이 크다. 일반적인 파일 전송은
`디스크 → 커널 버퍼 → 유저 공간 버퍼 → 소켓 버퍼`로 복사가 여러 번
일어나지만, sendfile은 유저 공간을 거치지 않고 커널 안에서
`파일 → 소켓`으로 바로 보낸다. 복사 횟수와 유저/커널 모드 전환이
줄어 CPU 사용량이 크게 준다. 카프카가 빠른 이유로도 등장하는,
계층을 관통하는 개념이다.

## 한 줄 요약

Nginx는 앱 앞 계층에서 리버스 프록시(진입점·TLS 종료)·정적 서빙·
버퍼링(느린 클라이언트로부터 WAS 격리)·로드밸런싱을 맡고, 이벤트
루프(epoll) 기반 워커 몇 개로 수만 커넥션을 감당하는 구조라서 이
역할에 최적이다 — 이 계층에서 반려된 요청은 앱 로그에 없으므로,
Nginx를 아는 것이 "로그 없는 장애"를 추적하는 출발점이다.
