# URL 입력 후 일어나는 일 — 요청이 지나는 전체 경로의 지도

> 핵심 관전 포인트: **URL 입력부터 화면 표시까지는 4개의 큰 관문을
> 순서대로 통과한다 — DNS 조회(도메인 이름 → IP 주소), TCP 3-way
> handshake(연결 수립), TLS handshake(암호화 채널 협상, HTTPS인 경우),
> HTTP 요청/응답(실제 데이터 교환). 각 관문은 실패할 때의 증상이
> 서로 다르다 — DNS 실패는 "주소를 못 찾음", TCP 실패는 "연결이 안 됨",
> TLS 실패는 "인증서/암호화 에러", HTTP 실패는 "상태 코드로 응답이 옴".
> 이 지도를 갖고 있으면 "안 돼요"라는 장애 신고를 "어느 구간에서
> 실패했는가"로 분해할 수 있다 — 모든 네트워크 디버깅의 밑그림이다.**

---

## 0. 질문 + 의도

**질문**: "브라우저에 URL을 입력했을 때 일어나는 일을 설명해주세요. (DNS → TCP → TLS → HTTP)"

**출제 의도**: 요청이 지나는 전체 경로의 지도를 갖고 있는지 보는
질문. 이 지도가 있어야 "어느 구간에서" 실패했는지 분해할 수 있다 —
모든 네트워크 디버깅의 밑그림이다.

## 1. 전체 지도 — 한눈에 보기

`https://example.com/page`를 입력하면 브라우저는 대략 이 순서로
움직인다.

```
[1] URL 파싱        스킴(https) / 호스트(example.com) / 경로(/page) 분리
[2] DNS 조회        example.com → 93.184.216.34  (이름 → 주소 번역)
[3] TCP 연결        3-way handshake — 왕복 1회 (RTT 1번)
[4] TLS 협상        암호화 채널 수립 — 왕복 1~2회 (HTTPS인 경우)
[5] HTTP 요청/응답  GET /page → 200 OK + HTML
[6] 렌더링          HTML 파싱 → 추가 리소스(CSS/JS/이미지)마다 [2]~[5] 반복
```

핵심 감각은 **[5]에 도달하기 전까지 이미 여러 번의 네트워크 왕복이
소모된다**는 것이다. 서버가 아무리 빨라도 [2]~[4]가 느리면 사용자는
느리다고 느낀다. 그래서 이 단계들을 줄이는 장치(DNS 캐시, keep-alive,
TLS 세션 재개)가 각각 존재한다 — 지도가 있어야 이 최적화들이 "왜
있는지"가 이해된다.

## 2. 단계별 상세

### [2] DNS 조회 — 이름을 주소로 번역하는 분산 전화번호부

컴퓨터는 `example.com`이라는 이름으로는 패킷을 보낼 수 없다.
IP 주소가 필요하고, 그 번역을 DNS가 맡는다. 조회는 **가까운 캐시부터**
순서대로 물어본다.

1. **브라우저 캐시** → **OS 캐시(+ hosts 파일)** — 있으면 즉시 끝.
2. 없으면 **재귀 리졸버**(통신사나 8.8.8.8 같은 공용 DNS)에게 묻는다.
3. 리졸버도 캐시에 없으면 계층을 타고 내려간다:
   **루트 서버**("com은 저쪽에 물어봐") → **TLD 서버**("example.com은
   저 네임서버가 관리해") → **권한 네임서버**("IP는 93.184.216.34다").
4. 응답에는 **TTL**(초 단위 유효기간)이 붙고, 경로상의 모든 캐시가
   그 시간만큼 결과를 기억한다.

비유하면 회사 대표번호를 알아내는 과정이다 — 내 연락처(브라우저 캐시)
→ 팀 공유 주소록(OS/리졸버 캐시) → 114 안내(루트부터 권한 서버까지).
한 번 알아낸 번호는 수첩에 적어두고(TTL 동안 캐시) 다시 묻지 않는다.

백엔드 관점에서 중요한 함의: **DNS 결과는 곳곳에 캐시되므로, 서버
IP를 바꿔도(배포/failover) TTL이 지나기 전까지 옛 주소로 트래픽이
계속 온다.** "DNS 바꿨는데 왜 아직 옛 서버로 오지?"의 정체다.

### [3] TCP 연결 — 대화 전에 회선부터 뚫는다

IP 주소를 알았으니 이제 그 서버의 443 포트(HTTPS)로 **TCP 연결**을
수립한다. SYN → SYN+ACK → ACK의 3-way handshake로, 네트워크 왕복
1회(1 RTT)가 든다. 여기서 확정되는 것은 "양쪽 모두 보내고 받을 수
있다"는 상호 확인이다. (상세한 절차와 종료는 별도 문서
`02-tcp-3way-4way-handshake.md`에서 다룬다.)

이 단계의 실패는 아직 HTTP의 세계에 들어가기 전의 실패다 — 서버
프로세스가 죽었거나(포트가 안 열림), 방화벽이 패킷을 버리거나,
네트워크가 단절된 경우다. 애플리케이션 로그에는 **아무것도 남지
않는다** — 요청이 애플리케이션까지 도달하지 못했기 때문이다.

### [4] TLS handshake — 암호화 채널 협상 (HTTPS)

TCP는 뚫렸지만 아직 평문이다. TLS handshake에서 클라이언트와 서버는
(1) 사용할 암호화 방식을 협상하고, (2) 서버가 **인증서**를 제시해
"내가 진짜 example.com이다"를 증명하고(브라우저는 신뢰하는 CA의
서명인지 검증), (3) **비대칭키 암호화로 대칭키를 안전하게 교환**한다.
이후의 실제 HTTP 본문은 그 대칭키로 암호화된다 — 비대칭은 느려서
키 전달에만 쓰고, 빠른 대칭키로 본문을 처리하는 이중 구조다.

이 단계도 왕복이 1~2회 추가로 든다. "HTTPS 첫 요청은 왜 느린가"라는
성능 질문의 답이 여기에 있다 — TCP 1 RTT + TLS 1~2 RTT가 본 요청
전에 선불로 나간다.

### [5] HTTP 요청/응답 — 드디어 본론

암호화 채널 위에서 브라우저가 요청을 보낸다.

```
GET /page HTTP/1.1
Host: example.com
Cookie: session=...
Accept: text/html
```

요청은 보통 로드밸런서/리버스 프록시(Nginx 등)를 거쳐 애플리케이션
서버(톰캣 등)에 도달하고, 애플리케이션이 DB 조회 등을 거쳐 상태 코드 +
본문으로 응답한다. **여기서부터가 백엔드 개발자의 코드가 실행되는
구간**이고, 앞의 [2]~[4]는 코드가 실행되기 전의 세계다 — 이 구분이
"앱 로그에 없는 장애"를 이해하는 열쇠다.

응답을 받은 커넥션은 바로 닫지 않고 **keep-alive**로 재사용한다 —
같은 페이지의 CSS/JS/이미지 요청이 [3][4]를 다시 치르지 않게 하기
위해서다.

### [6] 렌더링 — 그리고 반복

브라우저는 HTML을 파싱하며 DOM을 만들고, 만나는 리소스마다 추가
요청을 보낸다(같은 호스트면 기존 커넥션 재사용). 백엔드 면접에서는
이 단계는 간단히 언급하고, [2]~[5]를 정확히 설명하는 데 무게를 두는
편이 좋다.

## 3. 실무 활용 — 지도로 장애를 구간 분해하기

이 지도의 진짜 가치는 장애 신고가 왔을 때 드러난다. 단계별 실패는
**서로 다른 예외/증상**으로 나타나므로, 증상만 보고 어느 관문에서
막혔는지 역추적할 수 있다.

| 실패 구간 | 대표 증상 (Java 클라이언트 기준) | 먼저 볼 곳 |
|---|---|---|
| DNS | `UnknownHostException` | 도메인 설정, DNS 서버, TTL/전파 |
| TCP | `ConnectException`, connect timeout | 서버 프로세스 생존, 포트, 방화벽/보안그룹 |
| TLS | `SSLHandshakeException` | 인증서 만료/체인, TLS 버전 호환 |
| HTTP | 상태 코드 4xx/5xx, read timeout | 애플리케이션 로그, 업스트림 상태 |

```bash
# Before: "사이트가 안 열려요" — 어디가 문제인지 모른 채 앱 로그만 뒤짐

# After: curl 하나로 구간별 소요 시간을 분해해 병목/실패 지점을 특정
curl -o /dev/null -s -w '
DNS 조회:    %{time_namelookup}s
TCP 연결:    %{time_connect}s
TLS 완료:    %{time_appconnect}s
첫 바이트:   %{time_starttransfer}s
전체:        %{time_total}s
' https://example.com/page
```

예컨대 `time_connect`까지는 빠른데 `time_appconnect`가 튀면 TLS
구간(인증서 체인, 핸드셰이크 지연)을, `time_starttransfer`가 튀면
서버 처리(애플리케이션·DB)를 의심한다. `dig example.com`으로 DNS만,
`openssl s_client -connect example.com:443`으로 TLS만 따로 검증할
수도 있다. **도구를 아는 것보다 "구간을 나눠서 본다"는 사고가
핵심이다.**

## 4. 꼬리질문 대비 포인트

### "HTTPS 첫 요청은 왜 느리고, 두 번째 요청부터는 왜 빨라지나요?"

첫 요청은 본 요청 전에 DNS 조회 + TCP 1 RTT + TLS 1~2 RTT를 선불로
치른다. 두 번째부터는 (1) DNS는 캐시에서 즉시, (2) keep-alive로 기존
TCP 커넥션 재사용, (3) TLS도 세션 재개(session resumption)로 협상을
생략하거나 축약한다. 즉 준비 비용이 전부 캐시/재사용으로 사라지고
순수 요청-응답만 남는다. 서버 간 통신에서 커넥션 풀을 쓰는 이유도
정확히 같다 — 이 선불 비용을 요청마다 내지 않기 위해서다.

### "이 과정 중 어디가 실패하면 어떤 증상으로 나타나나요?"

DNS 실패는 `UnknownHostException`(주소 자체를 못 찾음), TCP 실패는
`ConnectException`/connect timeout(주소는 아는데 연결이 안 됨), TLS
실패는 `SSLHandshakeException`(연결은 됐는데 암호화 협상 실패, 흔한
원인은 인증서 만료), HTTP 단계 실패는 상태 코드가 있는 응답(4xx/5xx)
또는 read timeout으로 나타난다. 중요한 구분은 **TCP/TLS 단계 실패는
애플리케이션 로그에 안 남는다**는 것 — 요청이 코드에 도달하기 전이기
때문이다. 그래서 "앱 로그에 없다 = 요청이 안 왔다"가 아니라 "앞
구간에서 반려됐을 수 있다"로 읽어야 한다.

### "DNS 결과는 어디에 캐싱되고, 그게 배포/전환에 어떤 영향을 주나요?"

브라우저, OS, 재귀 리졸버까지 여러 계층에 TTL만큼 캐시된다. 그래서
서버 IP를 바꾸는 전환(failover, 마이그레이션)은 DNS 레코드를 바꾼
순간이 아니라 **각 캐시의 TTL이 만료된 뒤에야** 완료된다. 전환 작업
전에 TTL을 미리 짧게 줄여두는 것이 정석이고, 일부 리졸버나 JVM처럼
TTL을 무시하고 오래 캐시하는 계층(JVM의 InetAddress 캐시 등)도 있어
"DNS 전환은 즉시 반영된다"고 가정한 failover 계획은 현실에서 깨진다.

### "브라우저가 아니라 서버 간 호출이면 무엇이 다른가요?" (가산점 포인트)

거치는 관문은 동일하지만 최적화 주체가 달라진다. 브라우저는 이
비용들을 알아서 관리해주지만, 서버 간 호출에서는 개발자가 직접 챙겨야
한다 — HTTP 클라이언트의 **커넥션 풀**(TCP+TLS 재사용), 타임아웃
설정(connect/read 분리), JVM DNS 캐시 정책이 그것이다. 매 요청마다
클라이언트를 새로 만드는 코드는 요청마다 [2]~[4]를 전부 다시 치르는
코드다 — 커넥션 풀 없는 대량 호출이 TIME_WAIT 폭증과 포트 고갈로
이어지는 장애 패턴의 출발점이다.

### "이 경로에서 지연을 줄일 수 있는 지점은 각각 어디인가요?" (시니어 변별 포인트)

단계별로 공략 지점이 다르다는 걸 구조로 답하면 좋다. (1) DNS —
TTL 설계와 캐싱. (2) TCP/TLS — keep-alive와 커넥션 풀로 handshake
자체를 재사용하고, TLS 세션 재개로 협상을 축약. (3) 물리적 거리 —
handshake 비용은 RTT에 비례하므로 CDN/엣지로 사용자 가까이에서
종단시키는 것이 왕복 자체를 줄인다. (4) HTTP — 프로토콜 버전(HTTP/2의
멀티플렉싱), 캐싱 헤더로 요청 자체를 없애기. "서버 처리 시간만
줄이는 게 아니라 요청이 서버에 도달하기 전 구간에도 최적화 여지가
있다"는 시야를 보여주는 것이 포인트다.

## 한 줄 요약

URL 입력 후에는 DNS(이름→주소) → TCP(연결 수립) → TLS(암호화 협상) →
HTTP(요청/응답)의 관문을 차례로 지나며, 각 관문은 실패 증상이 서로
다르므로 이 지도를 갖고 있으면 "안 돼요"를 "어느 구간의 실패인가"로
분해할 수 있다 — 네트워크 디버깅과 성능 최적화 모두 이 밑그림에서
출발한다.
