# URL 입력 후 일어나는 일 — 요청이 지나는 전체 경로의 지도

> 핵심 관전 포인트: **URL 입력부터 화면 표시까지는 4개의 큰 관문을 순서대로 통과한다 — DNS 조회(도메인 이름 → IP 주소), TCP 3-way handshake(연결 수립), TLS handshake(암호화 채널 협상, HTTPS인 경우), HTTP 요청/응답(실제 데이터 교환). 이 관문들은 전부 **네트워크 왕복(RTT)을 소모**하며, 왕복 횟수는 서버 성능이나 대역폭으로 줄일 수 없다 — 물리적 거리가 정하는 값이기 때문이다. 그래서 본문이 1바이트여도 첫 요청은 DNS + TCP 1 RTT + TLS 1~2 RTT를 선불로 낸다. 그리고 각 관문은 실패할 때의 증상이 서로 다르다 — DNS 실패는 `UnknownHostException`(주소를 못 찾음), TCP 실패는 `ConnectException`이나 connect timeout(연결이 안 됨), TLS 실패는 `SSLHandshakeException`(인증서/암호화 협상 실패), HTTP 실패는 상태 코드가 붙은 응답이나 read timeout이다. 결정적으로 **TCP·TLS 단계의 실패는 애플리케이션 로그에 아무것도 남기지 않는다** — 요청이 내 코드에 도달하기 전에 반려됐기 때문이다. 이 지도를 갖고 있으면 "안 돼요"라는 장애 신고를 "어느 구간에서 실패했는가"로 분해할 수 있고, 개발자도구 Network 탭의 Timing 항목이나 `curl -w`의 타이밍 출력이 그 분해를 그대로 숫자로 보여준다 — 모든 네트워크 디버깅과 성능 최적화의 밑그림이다.**

---

## 0. 질문 + 의도

**질문**: "브라우저에 URL을 입력했을 때 일어나는 일을 설명해주세요. (DNS → TCP → TLS → HTTP)"

**출제 의도**: 요청이 지나는 전체 경로의 지도를 갖고 있는지 보는 질문. 이 지도가 있어야 "어느 구간에서" 실패했는지 분해할 수 있다 — 모든 네트워크 디버깅의 밑그림이다.

## 1. 전체 지도 — 관문 6개와 그 사이에 흐르는 시간

### 1-1. 브라우저가 하는 일을 한 문장으로 줄이면

`https://example.com/page`를 주소창에 치고 엔터를 누르면 브라우저가 하는 일은 결국 네 가지다. **이름을 주소로 바꾸고, 그 주소로 회선을 뚫고, 회선을 암호로 감싸고, 그 위에 요청을 써 보낸다.** 나머지는 전부 이 네 가지의 세부 사항이거나 반복이다.

이 네 가지가 왜 순서대로여야 하는지부터 짚고 가자. 뒤 단계는 앞 단계의 결과물 위에서만 성립한다. IP 주소를 모르면 어디로 패킷을 보낼지 정할 수 없으니 DNS가 먼저다. 연결이 없으면 암호화할 통로 자체가 없으니 TCP가 그다음이다. 암호화 채널이 없으면 HTTPS 요청을 평문으로 흘리게 되니 TLS가 그다음이다. **각 관문은 앞 관문이 끝나야 시작할 수 있고, 이 직렬 구조가 곧 지연의 누적이 된다.**

### 1-2. 전제 지식 — RTT가 무엇이고 왜 줄일 수 없는가

이 문서 전체를 관통하는 단위가 하나 있다. **RTT(round-trip time, 왕복 시간)는 내가 보낸 패킷이 상대에게 도착하고 그 응답이 나에게 돌아오기까지 걸리는 시간**이다. "왕복"이라는 이름 그대로, 편도가 아니라 갔다 오는 한 세트를 센다.

RTT를 결정하는 것은 두 가지다. 하나는 **물리적 거리**다. 신호는 광케이블 안에서 빛의 속도의 약 3분의 2로 움직이므로, 거리가 멀면 그만큼 시간이 든다. 다른 하나는 **중간에 거치는 장비의 수와 각 장비에서의 대기**다. 라우터·스위치·방화벽을 지날 때마다 패킷은 큐에 잠깐씩 줄을 선다.

여기서 반드시 붙잡아야 할 감각이 있다. **RTT는 서버를 좋은 걸로 바꾸거나 대역폭을 늘려도 줄어들지 않는다.** 대역폭은 "한 번에 얼마나 굵게 보낼 수 있나"이고 RTT는 "한 번 갔다 오는 데 얼마나 걸리나"라서, 8차선 도로를 16차선으로 넓혀도 서울에서 부산까지의 거리는 그대로인 것과 같다. 그래서 이 경로의 최적화는 거의 전부 **"왕복 횟수를 줄이거나, 왕복 거리를 줄이거나" 둘 중 하나**다. keep-alive와 커넥션 풀이 전자, CDN이 후자다.

대략적인 감각을 숫자로 잡아두면 이후 논의가 쉬워진다.

| 구간 | 대략적인 RTT |
|---|---|
| 같은 데이터센터 내부 (서버 ↔ DB) | 1ms 미만 |
| 같은 도시/리전 안 (사용자 ↔ 서울 서버) | 5~30ms |
| 국내 사용자 ↔ 미국 서부 서버 | 100~180ms |
| 모바일 셀룰러망 (기지국 구간이 더해짐) | 위 값 + 수십 ms |

미국 서부에 서버를 두고 RTT가 130ms라고 하자. TCP가 1 RTT, TLS 1.2가 2 RTT를 쓰면 그것만으로 `130 × 3 = 390ms`다. **서버 코드가 0ms에 끝나도 사용자는 이미 0.4초를 기다린 뒤다.** "우리 API 응답시간 30ms인데 왜 느리다고 하죠?"라는 질문의 답이 여기 있는 경우가 많다.

### 1-3. 지도 — 시간축으로 펼친 6개 관문

```
t=0    [1] URL 파싱 · 캐시 확인
       │  스킴(https) / 호스트(example.com) / 포트(생략 → 443) / 경로(/page) 분리
       │  브라우저 HTTP 캐시에 유효한 사본이 있으면 여기서 끝 (네트워크 0회)
       │
       ├─ [2] DNS 조회 ─────────────── example.com → 93.184.216.34
       │     캐시 적중이면 0 RTT / 완전 미적중이면 최대 3~4 왕복
       │
       ├─ [3] TCP 3-way handshake ──── SYN → SYN+ACK → ACK
       │     1 RTT  (여기까지는 아직 평문)
       │
       ├─ [4] TLS handshake ────────── 암호 방식 협상 + 인증서 검증 + 키 교환
       │     TLS 1.3 = 1 RTT / TLS 1.2 = 2 RTT / 세션 재개 = 0~1 RTT
       │
       ├─ [5] HTTP 요청/응답 ────────── GET /page → 200 OK + HTML
       │     0.5 RTT(요청 전달) + 서버 처리 시간 + 본문 전송 시간
       │
       └─ [6] 렌더링 + 서브리소스 반복  HTML 파싱 → CSS/JS/이미지마다 [2]~[5] 재실행
             (같은 호스트면 [2][3][4]는 재사용으로 건너뛴다)
```

이 그림에서 읽어야 할 핵심은 **[5]에 도달하기 전에 이미 여러 번의 왕복이 소모된다**는 것이다. 백엔드 개발자가 최적화할 수 있는 구간은 [5]의 "서버 처리 시간"뿐인데, 사용자가 체감하는 시간에서 그 조각이 차지하는 비율은 생각보다 작을 수 있다.

그리고 이 지도가 있어야 뒤에 나오는 최적화 장치들이 "왜 있는지"가 이해된다. DNS 캐시는 [2]를 없애기 위해, keep-alive와 커넥션 풀은 [3][4]를 없애기 위해, TLS 세션 재개는 [4]를 축약하기 위해, HTTP 캐시는 [2]~[5] 전부를 없애기 위해, CDN은 모든 관문의 RTT 자체를 줄이기 위해 존재한다.

### 1-4. 관문별 실패 증상 — 지도의 다른 쓰임새

지도의 두 번째 가치는 성능이 아니라 장애 진단에 있다. 각 관문은 **서로 다른 예외와 증상**으로 실패하므로, 증상만 보고 어느 관문에서 막혔는지 역추적할 수 있다.

| 실패 관문 | 대표 증상 (Java 클라이언트 기준) | 의미 |
|---|---|---|
| [2] DNS | `UnknownHostException` | 이름을 주소로 바꾸지 못했다 — 아직 패킷을 한 개도 못 보냈다 |
| [3] TCP | `ConnectException: Connection refused` | 주소까지는 갔는데 그 포트에 아무도 없다 |
| [3] TCP | connect timeout (`SocketTimeoutException`) | 보낸 SYN이 조용히 사라졌다 — 응답 자체가 없다 |
| [4] TLS | `SSLHandshakeException` | 연결은 됐는데 암호 채널 협상에 실패했다 |
| [5] HTTP | 4xx/5xx 상태 코드 | 서버가 요청을 받고 판단해서 답했다 |
| [5] HTTP | read timeout | 요청은 갔는데 응답이 제때 안 온다 |

여기서 시니어와 주니어가 갈리는 지점이 하나 있다. **[3]과 [4]의 실패는 애플리케이션 로그에 아무 흔적도 남기지 않는다.** 요청이 톰캣의 서블릿까지 도달하기 전에 커널이나 TLS 계층에서 반려됐기 때문이다. 그래서 "앱 로그를 다 뒤졌는데 그 요청이 없다"는 상황을 **"요청이 안 왔다"로 읽으면 안 되고 "앞 구간에서 반려됐을 수 있다"로 읽어야 한다.** 이 한 줄의 차이가 장애 조사 시간을 몇 시간씩 갈라놓는다.

## 2. 관문별 상세 — 각 구간에서 실제로 일어나는 일

### 2-1. [1] URL 파싱 — 그리고 네트워크를 아예 타지 않는 경우

URL은 문자열이 아니라 **구조**다. `https://example.com/page?id=1`을 브라우저는 이렇게 쪼갠다.

```
https  ://  example.com  [:443]  /page  ?id=1
  │           │            │       │       │
스킴        호스트        포트    경로    쿼리
  │           │            │
  │           │            └─ 생략되면 스킴의 기본값 (http=80, https=443)
  │           └─ [2] DNS 조회의 입력이 되는 값
  └─ TLS를 쓸지 말지, 기본 포트가 몇인지를 결정
```

스킴이 `https`라는 사실 하나가 관문 [4]의 존재 여부를 정한다는 점이 중요하다. `http://`면 [4]가 통째로 빠지고, 그래서 첫 요청이 눈에 띄게 빠르다 — 물론 평문이라는 대가를 치른다.

그리고 실무에서 자주 잊히는 사실이 하나 있다. **브라우저는 [2]로 넘어가기 전에 자신의 HTTP 캐시부터 확인한다.** `Cache-Control: max-age=3600`으로 받아둔 사본이 아직 유효하면 브라우저는 네트워크를 한 번도 타지 않고 그 사본을 그대로 쓴다. 개발자도구 Network 탭에서 크기 칸에 `(memory cache)` 또는 `(disk cache)`로 뜨는 것이 이 경우다. **모든 관문을 한꺼번에 0으로 만드는 유일한 최적화**이고, 그래서 캐싱 헤더 설계가 성능 작업에서 가장 큰 효과를 낸다. (헤더별 동작과 `304 Not Modified` 협상은 `20-http-caching-headers-and-304.md`에서 다룬다.)

### 2-2. [2] DNS 조회 — 이름을 주소로 바꾸는 계층형 전화번호부

#### 왜 이 단계가 필요한가

전제부터 깔자. **패킷의 헤더에는 도메인 이름이 들어갈 자리가 없다.** IP 패킷 헤더에 있는 것은 출발지 IP와 목적지 IP라는 숫자뿐이고, 중간의 라우터들은 그 숫자만 보고 다음 홉을 정한다. 라우터는 `example.com`이라는 문자열이 무엇인지 전혀 모른다.

그래서 사람이 기억하는 이름과 기계가 쓰는 숫자 사이에 번역기가 필요하고, 그 번역기가 **DNS(Domain Name System)**다.

#### 왜 하나의 큰 서버가 아니라 계층인가

여기가 대부분의 설명이 건너뛰는 지점이다. "루트 → TLD → 권한 네임서버"라는 순서만 외우면 왜 그렇게 나뉘어 있는지를 설명할 수 없다.

세상 모든 도메인의 IP를 한 대(또는 한 클러스터)의 서버가 전부 들고 있다고 상상해 보자. 세 가지 문제가 동시에 터진다. **첫째, 그 서버가 죽으면 인터넷 전체의 이름 조회가 죽는다.** 둘째, **모든 도메인의 등록·변경 권한을 한 조직이 독점**하게 된다 — 내 회사 도메인의 IP를 바꾸려면 그 조직에 요청해야 한다. 셋째, **전 세계의 초당 수억 건 질의를 한곳에서 받아야** 한다.

그래서 DNS는 이름 자체를 점(`.`)으로 쪼개 **관리 주체를 나눴다.** `www.example.com`을 오른쪽부터 읽으면 이렇게 된다.

```
www  .  example  .  com  .  (마지막 점 = 루트, 보통 생략해서 씀)
 │        │         │        │
 │        │         │        └─ 루트: "com을 관리하는 서버는 여기다"만 안다
 │        │         └────────── TLD(.com): "example.com을 관리하는 서버는 여기다"만 안다
 │        └──────────────────── 권한 네임서버: example.com 아래의 실제 레코드를 갖고 있다
 └───────────────────────────── 그 조직이 자유롭게 만들고 지우는 이름
```

각 계층은 **"내가 답을 아는 것이 아니라, 답을 아는 다음 서버가 누구인지를 안다"**는 구조다. 위임(delegation)이라고 부르는데, 이 위임 덕분에 `example.com`의 IP를 바꾸는 일은 그 회사가 자기 네임서버에서 혼자 처리하면 되고, 루트나 `.com` 서버는 아무것도 몰라도 된다.

용어를 하나씩 정의하고 넘어가자.

**재귀 리졸버(recursive resolver)**는 클라이언트를 대신해 답이 나올 때까지 계속 물어봐 주는 대리인이다. "재귀"라는 이름은 **답을 받을 때까지 자기가 반복해서 질의를 이어간다**는 뜻에서 왔다. 통신사가 자동으로 할당해 주는 DNS 서버나 `8.8.8.8` 같은 공용 DNS가 이 역할이다. 클라이언트는 "example.com의 IP 알려줘" 한 번만 물어보고 최종 답을 받는다.

**루트 네임서버**는 계층의 꼭대기다. 아는 것은 오직 "각 최상위 도메인(`.com`, `.net`, `.kr` 등)을 관리하는 서버들의 주소" 목록뿐이다.

**TLD 네임서버**의 TLD는 top-level domain, 즉 최상위 도메인이다. `.com`을 맡는 서버는 `.com`으로 끝나는 도메인들이 각각 어느 권한 네임서버에 위임돼 있는지를 안다.

**권한 네임서버(authoritative name server)**는 그 도메인에 대한 **최종 답을 낼 권한을 가진** 서버다. "권한"이라는 이름은 이 서버의 답이 다른 곳에서 복사해 온 캐시가 아니라 원본이라는 뜻이다. 회사가 직접 운영하거나 Route 53 같은 관리형 DNS 서비스에 맡긴다.

#### 실제 조회 흐름

```
[브라우저]
   │ ① 브라우저 자체 DNS 캐시 확인 ─── 있으면 여기서 끝 (0 RTT)
   │
[OS 스텁 리졸버]
   │ ② OS 캐시 + hosts 파일 확인 ──── 있으면 여기서 끝 (0 RTT)
   │
   ▼ 없으면 재귀 리졸버에게 질의 (UDP 53번 포트)
[재귀 리졸버]  ← 통신사 DNS 또는 8.8.8.8 등
   │ ③ 자기 캐시 확인 ──────────────── 있으면 여기서 응답 (1 RTT로 끝)
   │
   │ 없으면 계층을 타고 내려간다 (각 화살표가 1 RTT)
   │
   ├──▶ [루트 서버]        "com은 저 TLD 서버들에 물어봐"
   ├──▶ [.com TLD 서버]    "example.com은 ns1.example.com이 관리해"
   └──▶ [권한 네임서버]     "example.com의 A 레코드는 93.184.216.34다"
   │
   ▼ 결과를 자기 캐시에 TTL만큼 저장한 뒤 클라이언트에 반환
[브라우저] → IP 확보, 관문 [3]으로
```

**완전 미적중(cold) 조회는 최대 3~4번의 왕복**이 든다. 반대로 캐시가 적중하면 0 RTT다. 이 편차가 크기 때문에 "가끔씩만 첫 요청이 유난히 느린" 현상이 생긴다 — TTL이 만료돼 캐시가 비었던 그 한 번의 요청이 계층 전체를 다시 탄 것이다.

#### TTL과 캐시 — 백엔드가 실제로 부딪히는 지점

응답에는 **TTL(time to live)**이 함께 온다. 이름 그대로 "이 답이 살아 있는 시간"이고, 초 단위다. 경로상의 모든 캐시가 그 시간만큼 결과를 기억한다.

캐시 계층을 정리하면 이렇다.

| 캐시 계층 | 무효화 방법 | 백엔드가 겪는 문제 |
|---|---|---|
| 브라우저 DNS 캐시 | 브라우저 재시작 또는 내부 설정 화면 | 개발자 본인 PC에서만 안 바뀌어 혼란 |
| OS 캐시 / hosts 파일 | 캐시 플러시 명령, hosts 수정 | 로컬 테스트용 hosts 항목이 남아 오동작 |
| 재귀 리졸버 캐시 | 기다리는 수밖에 없음 (TTL 만료) | **IP 전환이 TTL만큼 지연된다** |
| JVM `InetAddress` 캐시 | JVM 옵션/보안 속성 | **TTL을 무시하고 오래 붙들 수 있다** |

여기서 백엔드 관점의 가장 중요한 함의가 나온다. **서버 IP를 바꿔도(배포, failover, 마이그레이션) TTL이 지나기 전까지는 옛 주소로 트래픽이 계속 온다.** "DNS 바꿨는데 왜 아직 옛 서버로 오지?"의 정체가 이것이다. 그래서 전환 작업 전에 TTL을 미리 짧게(예: 300초 → 60초) 줄여두고, 전환이 끝난 뒤 원래대로 되돌리는 것이 정석이다. (전환 전략 전반은 `19-dns-ttl-failover-traffic-switching.md`에서 다룬다.)

JVM은 별도로 조심해야 한다. Java의 `InetAddress`는 자체 DNS 캐시를 갖고 있고, **DNS 응답의 TTL이 아니라 JVM 자신의 정책**을 따른다. 정책 값은 JDK 버전과 보안 매니저 설정에 따라 달라지므로, 값을 짐작하지 말고 명시적으로 지정하는 편이 안전하다.

```java
// Before: DNS 캐시 정책을 손대지 않은 상태
// - RDS 엔드포인트나 내부 API 도메인이 failover로 IP가 바뀌어도
//   JVM이 옛 IP를 계속 붙들고 있어 재기동 전까지 장애가 이어질 수 있다.
// - 문제는 "가끔 몇몇 인스턴스만 안 붙는다"처럼 부분 장애로 나타나
//   DNS가 원인이라는 것을 알아채기 어렵다는 점이다.

// After: 애플리케이션 시작 시점에 캐시 수명을 명시한다
public class DnsCacheConfig {
    static {
        // 성공한 조회를 30초만 기억한다. failover 후 최대 30초 뒤에는
        // 새 IP로 붙는다는 상한을 코드로 보장하는 것이 목적이다.
        java.security.Security.setProperty("networkaddress.cache.ttl", "30");

        // 실패한 조회(NXDOMAIN 등)를 오래 기억하면, 잠깐의 DNS 장애가
        // 복구된 뒤에도 계속 실패한 상태로 남는다. 0으로 두어 매번 재시도한다.
        java.security.Security.setProperty("networkaddress.cache.negative.ttl", "0");
    }
}
```

#### 이 관문의 실패 증상

Java에서는 `UnknownHostException`이다. 이 예외의 의미를 정확히 읽으면 진단이 빨라진다 — **패킷을 한 개도 보내지 못한 상태**라는 뜻이다. 방화벽도 서버 상태도 아직 관련이 없다. 볼 곳은 도메인 오타, DNS 레코드 존재 여부, 사내 DNS 서버 자체의 장애다.

`dig`로 확인하면 두 가지 실패를 구분할 수 있다. `NXDOMAIN`은 "그런 이름은 없다"는 확정적 답변이고(레코드가 없거나 오타), `SERVFAIL`은 "물어봤는데 답을 못 받았다"는 뜻이다(DNS 서버 장애, DNSSEC 검증 실패 등). 전자는 우리 설정 문제, 후자는 조회 경로 문제로 갈린다.

### 2-3. [3] TCP 연결 — 대화 전에 회선부터 뚫는다

#### 전제 지식 — 연결은 4개의 숫자로 식별된다

TCP 연결을 이해하려면 먼저 **연결이 무엇으로 구분되는지**를 알아야 한다. 하나의 서버는 수만 개의 연결을 동시에 유지하는데, 도착한 패킷이 그중 어느 연결의 것인지를 어떻게 판별할까.

답은 **4-튜플(4-tuple)**이다. `(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)` 네 값의 조합이 연결 하나를 유일하게 식별한다. 웹 서버에 붙는 연결들은 목적지 IP와 목적지 포트(443)가 전부 같으므로, 실제로 연결들을 구분하는 것은 **출발지 IP와 출발지 포트**다.

여기서 **임시 포트(ephemeral port)**라는 개념이 나온다. 클라이언트는 자기 출발지 포트를 직접 고르지 않고 OS에게 맡기는데, OS는 미리 정해진 범위(리눅스는 보통 32768~60999)에서 아직 안 쓰는 번호를 하나 골라준다. "임시"라는 이름은 **연결이 끝나면 반납되고 다음 연결은 다른 번호를 받는다**는 뜻이다.

이 전제를 깔아두면 나중에 "임시 포트 고갈"이라는 장애를 이해할 수 있다. 한 대의 서버가 같은 목적지로 짧은 연결을 초당 수천 개씩 만들면, 4-튜플 중 세 개가 고정돼 있으므로 남는 변수는 임시 포트 하나뿐이고, 그 범위가 다 소진되면 새 연결을 만들 수 없게 된다. (`10-keepalive-connection-pool-time-wait.md`에서 TIME_WAIT과 함께 다룬다.)

#### 3-way handshake — 왜 세 번이고 왜 1 RTT인가

IP 주소를 알았으니 그 서버의 443 포트로 **TCP 연결**을 수립한다.

```
클라이언트                                     서버
    │  ── SYN ─────────────────────────────▶   │  "연결하자. 내 시퀀스 번호는 x부터"
    │                                          │
    │  ◀── SYN + ACK ──────────────────────    │  "좋다. 네 x 받았고, 내 번호는 y부터"
    │                                          │
    │  ── ACK ─────────────────────────────▶   │  "네 y도 받았다"
    │  ── (곧바로 데이터를 이어서 보낼 수 있다) ─▶  │
    │                                          │
 ESTABLISHED                              ESTABLISHED
```

세 번인 이유는 **양방향을 각각 확인해야 하기 때문**이다. SYN과 SYN+ACK 두 번으로 끝내면 클라이언트는 양방향이 통한다는 것을 알지만, 서버는 자기가 보낸 SYN+ACK이 도착했는지 모른다. 세 번째 ACK이 그 마지막 조각을 채운다.

지연 관점에서는 **1 RTT**로 센다. 클라이언트가 SYN을 보내고 SYN+ACK을 받기까지가 한 왕복이고, 마지막 ACK은 응답을 기다리지 않고 데이터와 함께 보낼 수 있어 추가 대기를 만들지 않기 때문이다. (수립·종료 절차의 상세와 TIME_WAIT은 `02-tcp-3way-4way-handshake.md`에서 다룬다.)

#### 이 관문의 실패 증상 — 두 가지를 반드시 구분한다

TCP 연결 실패는 겉보기에 "연결이 안 된다" 하나지만, 실제로는 성격이 완전히 다른 두 가지가 있다. **이 구분이 실무 진단에서 가장 값이 크다.**

**즉시 거절(`Connection refused`)**은 서버가 `RST` 패킷으로 명확히 거절한 경우다. 즉 **패킷은 그 기계까지 도달했다.** 다만 그 포트에서 대기 중인 프로세스가 없다. 애플리케이션이 죽었거나, 다른 포트에서 떠 있거나, 아직 부팅 중이라는 뜻이다. 특징은 **즉시 실패한다**는 것 — 밀리초 단위로 예외가 난다.

**connect timeout**은 보낸 SYN에 대해 아무 응답도 오지 않아 클라이언트가 기다리다 포기한 경우다. 즉 **패킷이 어딘가에서 조용히 버려졌다.** 방화벽이나 보안그룹이 DROP 정책으로 걸었거나, 경로가 없거나, 서버가 SYN을 처리하지 못할 만큼 과부하 상태다. 특징은 **설정한 타임아웃 시간을 꽉 채우고 실패한다**는 것이다.

```
Connection refused  →  "기계는 살아 있고 그 포트만 안 열렸다"
                       볼 곳: 프로세스 생존, 리스닝 포트, 바인딩 주소(0.0.0.0 vs 127.0.0.1)

connect timeout     →  "패킷이 중간에서 사라졌다"
                       볼 곳: 보안그룹/방화벽 규칙, 라우팅, 서버 과부하
```

이 두 가지 모두 **애플리케이션 로그에는 아무것도 남지 않는다.** 서버 쪽에서 보면 커널이 처리하거나 패킷이 아예 도달하지 않았으므로, 서블릿 필터도 인터셉터도 실행되지 않는다.

### 2-4. [4] TLS handshake — 평문 회선을 암호 채널로 바꾼다

#### 왜 필요한가

TCP는 뚫렸지만 **아직 평문**이다. 지금 상태에서 보내는 데이터는 카페 와이파이의 공유기, 통신사 장비, 중간의 모든 라우터가 그대로 읽을 수 있다. 쿠키에 담긴 세션 ID도, 로그인 폼의 비밀번호도 마찬가지다.

TLS(Transport Layer Security)는 이 회선 위에 암호 계층을 얹어 세 가지를 확보한다. **기밀성**은 중간에서 내용을 읽지 못하게 하는 것, **무결성**은 중간에서 내용을 바꾸면 들키게 하는 것, **신원 확인**은 지금 연결된 상대가 진짜 `example.com`이 맞는지 증명하는 것이다. 세 번째가 특히 중요한데, 암호화만 하고 상대가 누군지 확인하지 않으면 중간자가 자기와 암호 통신을 하게 만들 수 있기 때문이다.

#### handshake에서 실제로 합의하는 것

```
클라이언트                                            서버
    │ ── ClientHello ─────────────────────────────▶   │
    │    "내가 지원하는 TLS 버전과 암호 방식 목록은 이렇다"  │
    │    "SNI: 나는 example.com에 연결하려 한다"          │
    │                                                 │
    │ ◀── ServerHello + 인증서 + 키 교환 정보 ──────    │
    │    "이 버전과 이 암호 방식으로 하자"                 │
    │    "내가 example.com이라는 증명서는 이것이다"        │
    │                                                 │
    │ ── 인증서 검증 (클라이언트 내부 작업) ──             │
    │    ① 서명 체인이 신뢰하는 CA까지 이어지는가         │
    │    ② 유효기간이 지나지 않았는가                    │
    │    ③ 인증서의 도메인이 내가 접속한 호스트와 맞는가   │
    │                                                 │
    │ ── 키 교환 완료 + Finished ──────────────────▶   │
    │ ◀── Finished ────────────────────────────────   │
    │                                                 │
    └─ 이후 모든 HTTP 데이터는 합의한 대칭키로 암호화 ──┘
```

여기서 두 가지 용어를 정의하고 가자.

**SNI(Server Name Indication)**는 클라이언트가 handshake의 첫 메시지에서 "나는 이 도메인에 연결하려 한다"를 알려주는 확장이다. 왜 필요한가 하면, **하나의 IP에 여러 도메인이 붙어 있을 수 있기 때문**이다. 서버는 어느 도메인의 인증서를 제시해야 할지 알아야 하는데, HTTP의 `Host` 헤더는 암호화 이후에나 읽을 수 있어서 너무 늦다. 그래서 handshake 초반에 평문으로 도메인 이름을 알려주는 것이다. SNI를 보내지 않는 오래된 클라이언트가 여러 도메인이 붙은 서버에 접속하면 엉뚱한 인증서를 받아 검증에 실패한다.

**CA(Certificate Authority, 인증기관)**는 "이 공개키가 정말 이 도메인의 것"이라고 서명해 주는 제3자다. 브라우저와 OS는 신뢰하는 CA들의 목록(신뢰 저장소)을 미리 갖고 있고, 서버가 제시한 인증서의 서명을 따라가 그 목록의 CA에 닿으면 통과시킨다. 이 "따라가는 경로"를 **인증서 체인**이라고 부른다.

#### 대칭키와 비대칭키를 왜 둘 다 쓰는가

TLS가 두 가지 암호를 섞어 쓰는 이유는 각각의 장단점이 정확히 반대이기 때문이다.

**대칭키 암호**는 암호화와 복호화에 같은 열쇠를 쓴다. 빠르다 — 대용량 데이터를 처리하기에 충분히. 문제는 **그 열쇠를 어떻게 상대에게 안전하게 전달하느냐**다. 열쇠를 평문으로 보내면 중간에서 그것도 읽히므로 아무 의미가 없다.

**비대칭키 암호**는 공개키와 개인키가 짝을 이룬다. 공개키로 잠근 것은 개인키로만 열 수 있으므로, 공개키는 아무에게나 뿌려도 된다. **열쇠 전달 문제를 원천적으로 푸는 방식**이다. 문제는 느리다는 것이다 — 대칭키에 비해 계산 비용이 훨씬 크다.

그래서 TLS는 **비대칭키로 "대칭키를 합의하는 과정"만 보호하고, 실제 HTTP 본문은 그렇게 합의한 대칭키로 처리한다.** 무거운 자물쇠는 열쇠를 건네주는 순간에만 쓰고, 그 뒤의 대화는 가벼운 자물쇠로 이어가는 이중 구조다. (`06-tls-handshake-symmetric-asymmetric-keys.md`에서 상세히 다룬다.)

#### 왕복 비용

이 관문이 소모하는 왕복은 TLS 버전과 재접속 여부에 따라 다르다.

| 상황 | 추가 RTT | 설명 |
|---|---|---|
| TLS 1.2 최초 접속 | 2 | Hello 교환 1회 + 키 교환/Finished 1회 |
| TLS 1.3 최초 접속 | 1 | 키 교환 정보를 첫 메시지에 미리 실어 왕복을 하나 줄였다 |
| 세션 재개 (resumption) | 0~1 | 이전 접속의 협상 결과를 재사용해 협상을 축약 |

"HTTPS 첫 요청은 왜 느린가"라는 성능 질문의 답이 여기 있다. **TCP 1 RTT + TLS 1~2 RTT가 본 요청 전에 선불로 나간다.** RTT 130ms 환경에서 TLS 1.2면 390ms, TLS 1.3이면 260ms다.

#### 이 관문의 실패 증상

Java에서는 대부분 `SSLHandshakeException`으로 오지만, 메시지에 따라 원인이 갈린다.

| 메시지 조각 | 원인 |
|---|---|
| `PKIX path building failed` | 인증서 체인이 신뢰 저장소의 CA까지 이어지지 않음 — 중간 인증서 누락이거나 사설 CA를 신뢰 저장소에 안 넣음 |
| `certificate expired` | 인증서 유효기간 만료 — 갱신 자동화가 실패한 전형적 사고 |
| `No name matching ... found` | 인증서의 도메인과 접속한 호스트명이 다름 |
| `handshake_failure` | TLS 버전이나 암호 스위트 합의 실패 — 서버가 구버전 TLS를 껐는데 클라이언트가 신버전을 못 하는 경우 |

**이 실패들 역시 애플리케이션 로그에 남지 않는다.** TLS 종단이 로드밸런서에 있으면 애플리케이션 서버는 이런 요청이 있었다는 사실조차 모른다. (TLS를 어디서 종단할지의 판단은 `17-tls-termination-lb-vs-app.md`에서 다룬다.)

### 2-5. [5] HTTP 요청/응답 — 여기서부터 내 코드가 실행된다

암호 채널이 뚫렸으니 이제 그 위로 요청을 쓴다. HTTP/1.1의 요청은 텍스트다.

```
GET /page HTTP/1.1          ← 요청 라인: 메서드 / 경로 / 프로토콜 버전
Host: example.com           ← 어느 도메인에 대한 요청인지 (한 IP에 여러 사이트가 있을 수 있으므로 필수)
Cookie: session=abc123      ← 인증 상태를 실어 보내는 자리
Accept: text/html           ← 어떤 형식의 응답을 원하는지
User-Agent: Mozilla/5.0 ...
                            ← 빈 줄 = 헤더 끝 표시
```

요청은 곧장 애플리케이션에 닿지 않는다. 실제 경로는 대개 이렇게 여러 홉을 지난다.

```
브라우저 → [CDN 엣지] → [로드밸런서] → [Nginx] → [톰캣] → [내 코드] → [DB / 외부 API]
             │              │            │          │          │
          정적 캐시     TLS 종단·분배   리버스프록시  스레드풀   비즈니스 로직
```

사용자가 첫 바이트를 받기까지의 시간을 **TTFB(Time To First Byte)**라고 부르는데, TTFB 안에는 이 홉들을 지나는 시간과 각 홉에서의 대기가 전부 들어 있다. 그래서 "TTFB가 느리다"는 관찰만으로는 원인을 특정할 수 없고, 홉별로 다시 쪼개야 한다. (`07-traffic-performance/06-api-latency-bottleneck-investigation.md`의 구간 분해와 같은 사고다.)

응답이 오면 커넥션을 바로 닫지 않고 **keep-alive**로 열어둔다. 같은 페이지의 CSS·JS·이미지 요청이 [3]과 [4]를 다시 치르지 않게 하기 위해서다. HTTP/1.1은 keep-alive가 기본 동작이다.

이 구간의 실패는 앞 관문들과 성격이 다르다. **서버가 요청을 받고 판단해서 답한 것**이므로 상태 코드가 붙어 있고, 애플리케이션 로그에도 흔적이 남는다. 다만 프록시가 만들어 내는 5xx는 여전히 애플리케이션이 모를 수 있다 — `502 Bad Gateway`는 프록시가 업스트림에 붙지 못했다는 뜻이고, `504 Gateway Timeout`은 붙었지만 응답을 기다리다 포기했다는 뜻이라 의미가 완전히 다르다. (`11-502-vs-504-troubleshooting.md`, `13-nginx-tomcat-timeout-buffer-mismatch.md`)

### 2-6. [6] 렌더링 — 그리고 관문의 반복

브라우저는 받은 HTML을 위에서부터 파싱하며 DOM 트리를 만들고, 그 과정에서 `<link>`, `<script>`, `<img>` 같은 태그를 만날 때마다 추가 요청을 발생시킨다. 여기서 지도가 한 번 더 쓰인다.

**같은 호스트의 리소스**는 이미 열려 있는 커넥션을 재사용하므로 [2][3][4]를 건너뛰고 바로 [5]로 간다. 그래서 비용이 작다.

**다른 호스트의 리소스**는 [2]부터 전부 다시 탄다. 광고 스크립트, 분석 도구, 폰트 CDN처럼 서드파티 도메인을 하나 추가할 때마다 **DNS + TCP + TLS 한 세트가 통째로 추가된다.** 페이지에 서드파티 도메인이 다섯 개면 다섯 세트다. 프론트엔드 성능 논의에서 "서드파티 스크립트를 줄여라"가 반복되는 이유가 이 지도로 설명된다.

백엔드 면접에서는 렌더링 자체(레이아웃, 페인트, 리플로우)를 깊이 파고들 필요는 없다. **[2]~[5]가 반복된다는 구조**를 짚고 넘어가면 충분하다.

## 3. 실무 활용 — 지도로 장애와 지연을 구간 분해하기

### 3-1. 개발자도구 Network 탭 Timing — 지도가 그대로 화면에 있다

지도의 진짜 실용성은 브라우저 개발자도구에서 확인된다. Network 탭에서 요청 하나를 클릭하고 Timing 항목을 열면, **이 문서의 관문들이 그대로 항목별 시간으로 분해돼 있다.**

| Timing 항목 | 대응하는 관문 | 이 값이 튀면 의심할 것 |
|---|---|---|
| Queueing | 관문 이전 (브라우저 내부 대기) | 같은 호스트 동시 연결 수 상한(HTTP/1.1은 보통 6개)에 걸려 순서를 기다리는 중 |
| Stalled | 관문 이전 | 프록시 협상, 커넥션 슬롯 대기 — 실질적으로 Queueing과 같은 성격 |
| DNS Lookup | **[2] DNS 조회** | 캐시 미적중, 사내 DNS 서버 지연, 권한 네임서버 응답 지연 |
| Initial connection | **[3] TCP + [4] TLS 전체** | 크롬에서는 SSL 구간이 이 안에 포함돼 표시된다 — 값이 크면 아래 SSL 항목과 비교해 어느 쪽인지 가른다 |
| SSL | **[4] TLS handshake** | 인증서 체인이 길거나 중간 인증서 조회(OCSP 등)가 지연되는 경우 |
| Request sent | [5]의 요청 전송 | 거의 항상 0에 가깝다 — 여기가 크면 요청 본문이 매우 큰 경우 |
| Waiting for server response (TTFB) | **[5]의 서버 처리** | 애플리케이션 로직, DB 쿼리, 외부 API 호출 — 백엔드가 볼 구간 |
| Content Download | [5]의 본문 전송 | 응답 크기, 압축 미적용, 클라이언트 대역폭 |

읽는 법의 핵심은 **어느 항목이 큰지가 곧 어느 팀의 일인지를 정한다**는 것이다. TTFB만 크면 백엔드가 볼 문제고, Content Download가 크면 응답 크기와 압축(`21-response-compression-tradeoffs.md`)의 문제이며, Queueing이 크면 프로토콜 버전이나 리소스 개수의 문제(`09-http1-http2-http3-hol-blocking.md`)다. **"느려요"라는 신고를 받았을 때 이 화면 하나로 담당 구간을 가를 수 있다.**

한 가지 주의할 점이 있다. Timing의 값들은 **브라우저 기준**이라 서버가 재는 시간과 다르다. 서버 애플리케이션에서 재는 응답시간에는 DNS·TCP·TLS·네트워크 전송이 전부 빠져 있으므로, 같은 요청인데 서버 로그에는 30ms, 브라우저에는 480ms로 찍히는 것이 정상이다. **두 숫자가 다르다는 사실 자체가 "차이만큼이 네트워크 구간"이라는 정보다.**

### 3-2. `curl -w` — 서버에서도 같은 분해를 한다

브라우저가 없는 환경(운영 서버에서 외부 API를 호출하는 경우 등)에서는 `curl`의 `-w`(write-out) 옵션으로 같은 분해를 얻는다. `-w`는 전송이 끝난 뒤 지정한 변수들을 출력하는 옵션이고, 타이밍 변수들이 관문에 그대로 대응한다.

```bash
# Before: "사이트가 안 열려요" / "외부 API가 느려요"
#   → 앱 로그만 뒤진다. 앱 로그에는 [5]의 일부만 찍혀 있어 원인이 안 나온다.

# After: 관문별 누적 시각을 뽑아 어느 구간이 병목인지 특정한다
curl -o /dev/null -s -w '
time_namelookup:  %{time_namelookup}s   # [2] DNS 조회 완료 시각
time_connect:     %{time_connect}s      # [3] TCP 연결 완료 시각
time_appconnect:  %{time_appconnect}s   # [4] TLS handshake 완료 시각
time_pretransfer: %{time_pretransfer}s  # 요청 전송 직전 시각
time_starttransfer: %{time_starttransfer}s  # [5] 첫 응답 바이트 수신 시각 (TTFB)
time_total:       %{time_total}s        # 전체 완료 시각
' https://example.com/page
```

**여기서 반드시 알아야 할 것: 이 값들은 각 구간의 소요 시간이 아니라 시작 시점부터의 누적 시각이다.** 그래서 구간 시간은 직접 빼야 한다. 실제 출력이 이랬다고 하자.

```
time_namelookup:    0.052
time_connect:       0.164
time_appconnect:    0.389
time_pretransfer:   0.389
time_starttransfer: 0.712
time_total:         0.845
```

한 단계씩 빼서 구간 시간을 구한다.

```
[2] DNS 조회      = 0.052 - 0     = 0.052s   (52ms)
[3] TCP handshake = 0.164 - 0.052 = 0.112s   (112ms)  ← 이 값이 곧 1 RTT
[4] TLS handshake = 0.389 - 0.164 = 0.225s   (225ms)  ← 112ms × 2 ≈ 2 RTT
[5] 서버 처리     = 0.712 - 0.389 = 0.323s   (323ms)
[5] 본문 다운로드  = 0.845 - 0.712 = 0.133s   (133ms)
                                    ───────
                    합계             0.845s   (= time_total, 검산 완료)
```

이 숫자들이 말해주는 것을 읽어보자. **TCP handshake가 112ms라는 사실 하나로 이 경로의 RTT가 약 112ms임을 알 수 있다.** 그리고 TLS가 225ms로 그 두 배쯤 걸렸으므로 2 RTT를 쓴 셈이고, 이는 TLS 1.2 전체 handshake의 특징이다 — TLS 1.3으로 올리면 여기서 약 112ms를 줄일 수 있다는 실행 가능한 결론이 나온다. 서버 처리 323ms는 백엔드가 파고들 구간이고, 연결 준비(DNS+TCP+TLS)에만 389ms를 썼다는 사실은 **커넥션 재사용이 이 호출에서 가장 큰 개선 여지**라는 뜻이다.

구간별로 따로 검증하고 싶으면 도구를 나눠 쓴다.

```bash
# [2]만 검증 — 계층을 따라가며 어느 단계에서 답이 나오는지 본다
dig +trace example.com

# [2]만 검증 — 특정 DNS 서버에 직접 물어 캐시 영향을 배제한다
dig @8.8.8.8 example.com

# [3]만 검증 — TLS 이전에 포트가 열려 있는지만 확인한다
nc -zv example.com 443

# [4]만 검증 — 인증서 체인과 만료일, 협상된 TLS 버전을 확인한다
openssl s_client -connect example.com:443 -servername example.com </dev/null

# [5]만 검증 — 헤더만 받아 상태 코드와 응답 헤더를 확인한다
curl -I https://example.com/page
```

`openssl s_client`에 `-servername`을 붙이는 이유를 짚어두자. 2-4에서 설명한 **SNI**를 명시적으로 보내라는 옵션이다. 이걸 빼면 서버가 기본 인증서를 내주어, 실제 브라우저가 겪는 것과 다른 결과를 보게 된다.

**도구 이름을 아는 것보다 "구간을 나눠서 본다"는 사고가 핵심이다.** 도구는 바뀌어도 지도는 바뀌지 않는다.

### 3-3. 서버 간 호출에서 관문 비용을 없애기

브라우저는 DNS 캐시, keep-alive, TLS 세션 재개를 알아서 관리해 준다. **서버 간 호출에서는 그 관리를 개발자가 직접 해야 한다.** 이것을 안 하는 코드가 어떤 모양인지 보자.

```java
// Before: 요청마다 클라이언트를 새로 만든다
// - 새 클라이언트는 커넥션 풀도 비어 있으므로, 호출 한 번마다
//   [2] DNS + [3] TCP handshake + [4] TLS handshake를 전부 다시 치른다.
// - 위 계산대로면 요청당 389ms의 준비 비용을 매번 지불하는 셈이다.
// - 더 나쁜 것은 연결을 계속 새로 만들고 닫으면서 임시 포트를 소진해,
//   부하가 올라간 순간 "Cannot assign requested address"로 무너진다는 점이다.
public PaymentResult call(PaymentRequest req) {
    RestClient client = RestClient.create();          // 매 호출마다 새 클라이언트
    return client.post()
        .uri("https://pg.example.com/payments")
        .body(req)
        .retrieve()
        .body(PaymentResult.class);
}

// After: 커넥션 풀을 가진 클라이언트를 빈으로 한 번만 만들어 재사용한다
@Configuration
public class PaymentClientConfig {

    @Bean
    public RestClient paymentClient() {
        PoolingHttpClientConnectionManager pool = new PoolingHttpClientConnectionManager();
        // 전체 풀 크기: 이 애플리케이션이 동시에 유지할 연결의 상한이다.
        pool.setMaxTotal(100);
        // 목적지(라우트)당 상한: 기본값이 작아서(보통 한 자릿수) 이걸 안 올리면
        // 풀은 여유가 있는데 특정 호스트로의 호출만 줄을 서는 현상이 생긴다.
        pool.setDefaultMaxPerRoute(50);

        RequestConfig requestConfig = RequestConfig.custom()
            // connect timeout: [3] TCP 연결까지의 상한. 방화벽 DROP처럼
            // 응답이 아예 없는 상황에서 스레드가 무한정 묶이는 것을 막는다.
            .setConnectTimeout(Timeout.ofSeconds(2))
            // response timeout: [5] 응답을 기다리는 상한. connect와 분리해야
            // "연결은 되는데 느린" 문제와 "연결 자체가 안 되는" 문제를 구분할 수 있다.
            .setResponseTimeout(Timeout.ofSeconds(3))
            // 풀에서 연결을 빌려오기까지의 상한. 이게 없으면 풀 고갈 시
            // 호출 스레드가 조용히 쌓여 장애가 뒤늦게 드러난다.
            .setConnectionRequestTimeout(Timeout.ofSeconds(1))
            .build();

        CloseableHttpClient httpClient = HttpClients.custom()
            .setConnectionManager(pool)
            .setDefaultRequestConfig(requestConfig)
            .build();

        return RestClient.builder()
            .requestFactory(new HttpComponentsClientHttpRequestFactory(httpClient))
            .build();
    }
}
```

after 쪽이 하는 일을 지도의 언어로 다시 말하면 이렇다. **한 번 뚫어둔 [3]과 [4]를 여러 요청이 나눠 쓰게 만들어, 두 번째 요청부터는 [5]만 남긴다.** 커넥션 풀이 "성능 옵션"이 아니라 이 지도의 직접적인 귀결이라는 것을 알면, 풀 크기나 타임아웃 값을 감이 아니라 근거로 정할 수 있다. (풀 운영과 TIME_WAIT은 `10-keepalive-connection-pool-time-wait.md`, 타임아웃 계층 설계는 `07-traffic-performance/10-timeout-layers-and-budget.md`에서 다룬다.)

## 4. 꼬리질문 대비 포인트

### "HTTPS 첫 요청은 왜 느리고, 두 번째 요청부터는 왜 빨라지나요?"

첫 요청은 본론에 들어가기 전에 **준비 비용을 선불로 전부 치르기 때문**이다. DNS 조회(캐시가 비어 있으면 최대 3~4 왕복) + TCP handshake 1 RTT + TLS handshake 1~2 RTT가 요청을 보내기도 전에 나간다. RTT가 110ms인 경로에서 TLS 1.2를 쓰면 이 준비만으로 400ms 가까이 든다.

두 번째 요청부터 빨라지는 이유는 그 준비물이 **전부 캐시되거나 재사용되기 때문**이다. DNS는 브라우저·OS·리졸버 캐시에서 즉시 나오고, TCP 연결은 keep-alive로 그대로 살아 있으며, 연결이 끊겼더라도 TLS는 세션 재개로 협상을 축약한다. 그래서 두 번째 요청에 남는 것은 순수한 요청-응답 왕복뿐이다.

여기서 한 걸음 더 나가면 좋다. **서버 간 통신에서 커넥션 풀을 쓰는 이유가 정확히 같다.** 브라우저가 자동으로 해주는 이 재사용을 서버에서는 개발자가 명시적으로 구현하는 것이고, 그것을 안 하면 요청마다 [2]~[4]를 다시 치르는 코드가 된다.

### "이 과정 중 어디가 실패하면 어떤 증상으로 나타나나요?"

관문마다 증상이 다르다는 것을 예외 이름으로 짚는다. DNS 실패는 `UnknownHostException` — **아직 패킷을 한 개도 못 보낸 상태**다. TCP 실패는 두 가지로 갈리는데, `Connection refused`는 기계까지는 갔지만 그 포트에 프로세스가 없다는 뜻이고(즉시 실패), connect timeout은 SYN이 어딘가에서 조용히 버려졌다는 뜻이다(방화벽 DROP 의심, 타임아웃 시간을 꽉 채우고 실패). TLS 실패는 `SSLHandshakeException`이며 메시지에 따라 체인 문제(`PKIX path building failed`), 만료, 호스트명 불일치, 버전 협상 실패로 나뉜다. HTTP 단계는 상태 코드가 붙은 응답이나 read timeout이다.

**가장 중요한 구분은 이것이다: [3]과 [4]의 실패는 애플리케이션 로그에 남지 않는다.** 요청이 서블릿에 도달하기 전에 반려됐기 때문이다. 그래서 "앱 로그에 그 요청이 없다"를 "요청이 안 왔다"로 읽으면 안 되고, "앞 구간에서 반려됐을 수 있다"로 읽어야 한다. 이 경우 확인해야 할 곳은 애플리케이션이 아니라 로드밸런서 액세스 로그, 보안그룹 규칙, 인증서 만료일이다.

### "DNS 결과는 어디에 캐싱되고, 그게 배포/전환에 어떤 영향을 주나요?"

브라우저 캐시, OS 캐시(+hosts 파일), 재귀 리졸버 캐시까지 **경로상의 모든 계층에 TTL만큼 캐시된다.** 그래서 서버 IP를 바꾸는 전환(failover, 리전 마이그레이션)은 DNS 레코드를 수정한 순간이 아니라 **각 캐시의 TTL이 만료된 뒤에야** 완료된다. 레코드는 바뀌었는데 트래픽은 여전히 옛 서버로 오는 구간이 반드시 존재한다는 뜻이다.

그래서 정석은 **전환 작업 전에 TTL을 미리 짧게 줄여두는 것**이다. 평소 300초로 두다가 전환 며칠 전에 60초로 낮추고(기존 캐시가 옛 TTL로 만료되기를 기다려야 하므로 미리 해야 한다), 전환 후 안정되면 다시 올린다.

여기에 함정이 하나 더 있다. **TTL을 무시하는 계층이 존재한다.** JVM의 `InetAddress` 캐시가 대표적인데, DNS 응답의 TTL이 아니라 JVM 자신의 정책을 따르므로 짧은 TTL을 걸어둬도 애플리케이션이 옛 IP를 계속 붙들 수 있다. 일부 리졸버도 지나치게 짧은 TTL을 자체 하한으로 올려 잡는다. 결론적으로 **"DNS 전환은 즉시 반영된다"고 가정한 failover 계획은 현실에서 깨지므로**, DNS는 "빠른 전환 수단"이 아니라 "느리지만 확실한 전환 수단"으로 취급하고, 초 단위 전환이 필요하면 로드밸런서의 대상 그룹 교체처럼 DNS에 의존하지 않는 방법을 써야 한다.

### "브라우저가 아니라 서버 간 호출이면 무엇이 다른가요?" (가산점 포인트)

**거치는 관문은 완전히 동일하다.** 달라지는 것은 그 비용을 누가 관리하느냐다.

브라우저는 DNS 캐시, 커넥션 재사용, TLS 세션 재개, 동시 연결 수 제한을 전부 알아서 처리해 준다. 서버 간 호출에서는 이것들이 **HTTP 클라이언트의 설정 항목**이 되어 개발자에게 넘어온다. 커넥션 풀(전체 크기와 목적지당 크기), connect/read 타임아웃 분리, JVM DNS 캐시 정책이 그것이다.

이걸 놓쳤을 때의 전형적 장애 패턴을 함께 말하면 좋다. 요청마다 클라이언트를 새로 만드는 코드는 요청마다 [2]~[4]를 다시 치르므로 지연이 몇 배로 늘고, 더 심각하게는 **연결을 계속 새로 만들고 닫으면서 TIME_WAIT 소켓이 쌓여 임시 포트가 고갈된다.** 2-3에서 본 4-튜플 구조 때문인데, 같은 목적지로의 연결은 4개 값 중 세 개가 고정이라 임시 포트 하나가 유일한 변수이고, 그 범위(보통 2만~3만 개)를 다 쓰면 `Cannot assign requested address`로 새 연결이 아예 안 된다. **평소에는 멀쩡하다가 트래픽이 올라간 순간 급격히 무너지는** 형태로 나타나서 원인 파악이 늦어지는 것이 이 장애의 특징이다.

한 가지 더 얹으면 좋은 것은 **재시도의 위치**다. 서버 간 호출에서는 실패 시 재시도를 넣게 되는데, 어느 관문의 실패인지에 따라 재시도의 안전성이 다르다. connect timeout은 요청이 서버에 도달하지 않았을 가능성이 높아 재시도가 비교적 안전하지만, read timeout은 **서버가 이미 처리했을 수 있으므로** 멱등하지 않은 요청을 재시도하면 이중 처리가 된다. 지도가 있으면 이 판단도 근거를 갖고 할 수 있다.

### "이 경로에서 지연을 줄일 수 있는 지점은 각각 어디인가요?" (시니어 변별 포인트)

관문별로 공략 지점이 다르다는 것을 구조로 답하는 것이 핵심이다.

**[2] DNS**는 TTL 설계와 캐싱이다. 다만 이 구간은 절대값이 작아서(보통 수십 ms) 최적화 우선순위가 낮고, 오히려 TTL을 너무 길게 잡아 전환이 느려지는 쪽이 실무에서 더 자주 문제가 된다.

**[3][4] TCP·TLS**는 **handshake 자체를 재사용해 없애는 것**이 정답이다. keep-alive와 커넥션 풀로 연결을 살려 쓰고, TLS 세션 재개로 협상을 축약하고, TLS 1.3으로 올려 왕복을 하나 줄인다. 여기가 개선 효과가 가장 확실한 구간이다 — 3-2의 예에서 준비 비용이 389ms였던 것을 기억하면, 재사용은 그 전체를 0으로 만드는 조치다.

**물리적 거리**는 별도의 축이다. 앞의 모든 handshake 비용이 RTT에 비례하므로, **RTT 자체를 줄이면 모든 관문이 동시에 빨라진다.** CDN이나 엣지에서 TLS를 종단해 사용자 가까이에서 연결을 맺게 하는 것이 이 접근이고, 왕복 횟수를 줄이는 것보다 왕복 거리를 줄이는 쪽이 효과가 더 클 때도 많다.

**[5] HTTP**는 세 갈래다. 프로토콜 버전을 올려 요청들을 한 연결에 겹쳐 보내고(HTTP/2 멀티플렉싱), 캐싱 헤더로 **요청 자체를 없애며**(가장 강력하다 — 관문 전체가 0이 된다), 응답 압축으로 본문 전송 시간을 줄인다.

마지막으로 시야를 한 줄로 정리하면 좋다. **"서버 처리 시간만 줄이는 것이 성능 최적화가 아니다 — 요청이 서버에 도달하기 전 구간에도, 응답이 사용자에게 닿는 구간에도 최적화 여지가 있다."** 그리고 어디를 손댈지는 감이 아니라 3-1·3-2의 구간 분해로 측정한 뒤에 정한다는 순서까지 말하면 설계 감각이 드러난다.

## 한 줄 요약

URL 입력 후에는 DNS(이름 → 주소) → TCP(연결 수립) → TLS(암호 채널 협상) → HTTP(요청/응답)의 관문을 차례로 지나며, 각 관문은 RTT라는 줄일 수 없는 비용을 소모하고 실패 증상도 서로 다르므로 — 특히 TCP·TLS 실패는 애플리케이션 로그에 흔적을 남기지 않으므로 — 이 지도를 갖고 있으면 "안 돼요"를 "어느 구간의 실패인가"로 분해할 수 있고, 개발자도구 Timing과 `curl -w`가 그 분해를 그대로 숫자로 보여준다.
