# L4 vs L7 로드밸런서 — 어느 계층에서 보느냐가 기능·성능·장애 감지력을 가른다

> 핵심 관전 포인트: **L4 로드밸런서는 IP와 포트(TCP/UDP 헤더)까지만 보고
> 커넥션 단위로 트래픽을 분배한다 — 내용을 안 보니 빠르고 프로토콜을
> 가리지 않지만, "무슨 요청인지"는 모른다. L7 로드밸런서는 HTTP를
> 이해하는 리버스 프록시로서 요청을 일단 받아서 URL 경로·호스트·헤더·
> 쿠키를 보고 라우팅한다 — 경로 기반 분기, 카나리, 쿠키 스티키니스가
> 가능하지만 커넥션을 종단하는 비용이 든다. 장애 감지도 같은 구도다:
> L4는 "포트가 열리는가"(TCP 연결 성공)까지, L7은 "애플리케이션이
> 올바른 응답을 주는가"(HTTP 상태 코드·본문)까지 확인할 수 있다 —
> 포트는 살아있는데 500만 뱉는 좀비 서버를 걸러내려면 L7 헬스체크가
> 필요하다.**

---

## 0. 질문 + 의도

**질문**: "L4와 L7 로드밸런서의 차이와, 각각에서 가능한 라우팅/장애 감지 방식은?"

**출제 의도**: 어느 계층에서 라우팅하느냐가 가능한 기능(경로 기반
분기, 쿠키 스티키니스)과 성능을 결정한다. 인프라 팀과 트래픽 구성을
논의할 때 필요한 공용어 — "우리 LB가 L4냐 L7이냐"에 따라 백엔드가
기대할 수 있는 것(클라이언트 IP, 세션 고정, 헬스체크의 의미)이
달라진다는 것을 아는지 본다.

## 1. 계층이 다르다는 것의 의미 — 봉투만 보기 vs 편지 열어보기

OSI 모델에서 L4는 전송 계층(TCP/UDP), L7은 응용 계층(HTTP)이다.
로드밸런서 이름의 숫자는 **"트래픽의 어디까지 읽고 분배를 결정하는가"**를
뜻한다.

우편에 비유하면 L4는 **봉투 겉면(주소·번호)만 보고** 배달 트럭을
정하는 분류 센터고, L7은 **편지를 열어 내용을 읽고** "청구서는 경리팀,
광고는 폐기"처럼 내용 기반으로 처리하는 비서다.

- **L4 로드밸런서**: 패킷의 출발지/목적지 IP와 포트만 본다.
  클라이언트가 TCP 연결을 맺으면 그 **커넥션 단위로** 백엔드 하나를
  골라, 이후 같은 커넥션의 패킷을 계속 그 서버로 흘려보낸다(목적지
  주소를 바꿔치기하는 NAT 방식이 대표적). 스트림 안의 내용(HTTP인지,
  어떤 URL인지)은 해석하지 않는다.
- **L7 로드밸런서**: 클라이언트의 연결을 **자기 자신이 받아서 종단**하고,
  HTTP 요청을 파싱한 뒤 백엔드로 **별도의 연결**을 맺어 전달한다.
  즉 커넥션이 "클라이언트↔LB"와 "LB↔백엔드" 두 개로 나뉜다.
  TLS 종단, 요청 재작성, 응답 버퍼링도 이 지점에서 가능해진다.

| 구분 | L4 | L7 |
|---|---|---|
| 보는 정보 | IP, 포트 | + HTTP 메서드/경로/호스트/헤더/쿠키 |
| 분배 단위 | TCP/UDP 커넥션 | HTTP 요청 |
| 커넥션 | 클라이언트↔서버 사실상 직결 | LB에서 종단 후 2개로 분리 |
| 프로토콜 | 무엇이든(DB, Redis, gRPC, 게임 TCP) | HTTP(S) 계열 |
| 비용 | 낮음(패킷 전달 수준) | 파싱·종단·버퍼링 비용 |

클라우드로 옮기면 AWS의 NLB가 L4, ALB가 L7 계열이다. (가산점 포인트)

## 2. 라우팅 방식 — 각 계층에서 가능한 것과 불가능한 것

라운드 로빈, least-connections 같은 **분배 알고리즘 자체는 양쪽 다
쓸 수 있다**(알고리즘은 별도 주제). 계층이 가르는 것은 "**무엇을 근거로**
분기할 수 있는가"다.

**L4에서 가능한 라우팅** — 근거가 IP·포트뿐이므로:

- 포트 기반 분기(443은 웹 서버군, 5432는 DB군)
- 5-tuple(출발/목적 IP·포트·프로토콜) 해시로 커넥션을 서버에 고정
- 출발지 IP 해시 — 같은 클라이언트를 같은 서버로 보내는 원시적 스티키

**L7에서만 가능한 라우팅** — 요청 내용을 읽으므로:

- **호스트 기반**: `api.example.com`은 API 서버군, `img.example.com`은
  이미지 서버군
- **경로 기반**: `/api/`는 애플리케이션, `/static/`은 정적 서빙,
  마이크로서비스별 경로 분기
- **헤더/쿠키 기반**: 특정 헤더가 있으면 카나리 서버군으로, LB가 발급한
  쿠키로 같은 사용자를 같은 서버에 고정(쿠키 스티키니스)
- **가중치 분배**: 신버전에 5%만 흘리는 카나리 배포

```nginx
# L4로는 불가능하고 L7에서만 가능한 라우팅의 예 (Nginx)

# 경로 기반 분기 — 요청 URL을 읽어야 가능
location /api/    { proxy_pass http://api_servers; }
location /static/ { root /var/www; }

# 헤더 기반 카나리 — 특정 헤더가 있는 요청만 신버전으로
map $http_x_canary $upstream_pool {
    default  stable_servers;
    "on"     canary_servers;
}
```

L4만 있는 환경에서 "경로별로 다른 서비스로 보내달라"는 요구가 오면
구조적으로 불가능하다 — 이때 흔한 답이 **L4 뒤에 L7을 한 단 더 두는
2단 구성**(L4가 대량 트래픽을 L7 프록시들에 나눠주고, L7이 내용 기반
분기)이다.

## 3. 장애 감지 — "살아있다"의 정의가 계층마다 다르다

헬스체크는 로드밸런서가 "이 서버에 트래픽을 보내도 되는가"를 판단하는
근거다. 계층에 따라 확인할 수 있는 **생존의 깊이**가 다르다.

- **L4 헬스체크**: 대상 포트로 TCP 연결을 시도해서 **연결이 맺어지면
  정상**으로 판정한다. 확인하는 것은 "프로세스가 포트를 리스닝하고
  있는가"까지다.
- **L7 헬스체크**: `GET /health` 같은 HTTP 요청을 보내 **상태 코드
  (예: 200)와 필요하면 응답 본문까지** 확인한다. "애플리케이션이 요청을
  실제로 처리할 수 있는가"를 본다.

이 차이가 드러나는 대표 장애가 **좀비 서버**다: JVM 프로세스는 떠
있고 포트도 열려 있는데, DB 커넥션 풀 고갈이나 내부 의존성 장애로
**모든 요청에 500을 뱉는** 상태. L4 헬스체크(TCP 연결)는 멀쩡히
통과하므로 LB는 이 서버로 트래픽을 계속 보내고, 사용자 일부만 계속
에러를 보는 간헐 장애가 된다. L7 헬스체크였다면 500을 보고 즉시
분배 대상에서 제외했을 것이다.

헬스체크에는 두 방식이 있다는 것도 알아두면 좋다 (가산점 포인트):

- **active**: LB가 주기적으로 체크 요청을 직접 보낸다. 감지 주기 ×
  실패 임계치만큼 감지 지연이 있다.
- **passive**: 실제 사용자 요청의 실패(연결 거부, 5xx)를 관찰해서
  일정 비율을 넘으면 제외한다. 체크 트래픽이 없고 실사용 기준이지만,
  사용자가 먼저 실패를 겪은 뒤에야 반응한다.

한 가지 설계 주의점: 헬스체크 엔드포인트가 **깊게 검사할수록 좋은 것이
아니다** — 아래 꼬리질문에서 다룬다.

## 4. 꼬리질문 대비 포인트

### "L7이 기능이 더 많은데, L4는 언제 선택하나요?" (시니어 변별 포인트)

기능과 비용의 트레이드오프다. L4를 고르는 상황은 (1) **HTTP가 아닌
트래픽** — DB, Redis, MQTT, 자체 TCP 프로토콜은 L7이 파싱할 수 없다.
(2) **극단적 처리량/저지연** — 패킷 전달 수준으로 동작하는 L4가
파싱·종단을 하는 L7보다 같은 자원에서 훨씬 많은 트래픽을 감당한다.
(3) **TLS를 LB에서 풀면 안 되는 요구**(종단간 암호화) — L4는 암호화된
스트림을 내용을 모른 채 통과시킬 수 있다. 실무에서는 양자택일보다
**L4(대량 분배) → L7(내용 기반 분기) 2단 구성**이 흔하고, "요구사항에
따라 조합한다"고 답하는 것이 설계 감각을 보여준다.

### "스티키 세션은 각 계층에서 어떻게 구현하고, 각각의 함정은?"

L4는 **출발지 IP 해시**뿐이다 — 함정은 같은 NAT 뒤의 사용자들(회사망,
통신사 CGNAT)이 전부 같은 IP로 보여 **한 서버로 쏠리고**, 모바일처럼
IP가 바뀌면 세션이 끊긴다는 것. L7은 **LB가 쿠키를 발급**해 사용자
단위로 정확히 고정할 수 있다. 다만 어느 쪽이든 스티키는 "서버에 상태가
있다"는 문제의 증상 완화일 뿐이고, 근본 해법은 세션을 외부 저장소로
빼는 무상태 설계라고 덧붙이면 좋다.

### "헬스체크 엔드포인트가 DB까지 검사하면 어떤 일이 생기나요?"

DB가 잠깐 흔들리는 순간 **모든 서버의 헬스체크가 동시에 실패**해서,
LB가 전 서버를 분배 대상에서 제외한다 — DB 순단이 전면 장애로 증폭된다.
DB 없이도 응답할 수 있는 요청(정적 응답, 캐시된 조회)까지 전부 죽는
셈이다. 그래서 "트래픽을 받을 수 있는가"를 판정하는 헬스체크는 서버
자신의 상태 위주로 얕게 두고, 의존성 상태는 별도 모니터링으로 보는
것이 원칙이다(쿠버네티스의 liveness/readiness 구분과 같은 문제의식).

### "L7 LB가 커넥션을 종단하면 백엔드는 클라이언트 IP를 어떻게 아나요?"

백엔드에 도착하는 TCP 커넥션의 출발지는 LB의 IP다. 그래서 L7 LB는
원래 클라이언트 IP를 `X-Forwarded-For` 같은 HTTP 헤더에 실어 전달하고,
백엔드는 그것을 읽는다(신뢰할 수 있는 프록시가 붙인 값만 믿어야 한다는
검증 문제가 따라온다). L4 계층에서는 HTTP 헤더를 쓸 수 없으므로 proxy
protocol처럼 커넥션 앞에 원 출발지 정보를 붙이는 별도 규약을 쓴다.
(가산점 포인트)

## 한 줄 요약

L4는 IP·포트만 보고 커넥션 단위로 빠르게 분배하는 계층이라 라우팅
근거도 헬스체크도 "포트가 열리는가"까지이고, L7은 HTTP를 종단·해석하는
계층이라 경로·헤더·쿠키 기반 라우팅과 "200을 주는가"까지 확인하는
헬스체크가 가능하다 — 포트는 살아있는데 500만 뱉는 좀비 서버를 걸러낼
수 있느냐가 두 계층의 차이를 가장 선명하게 보여준다.
