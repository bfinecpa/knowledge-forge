# L4 vs L7 로드밸런서 — 어느 계층에서 보느냐가 기능·성능·장애 감지력을 가른다

> 핵심 관전 포인트: **L4 로드밸런서는 IP와 포트(TCP/UDP 헤더)까지만 보고 패킷을 전달하므로 TCP 연결의 두 끝은 여전히 클라이언트와 백엔드다 — 내용을 안 보니 빠르고 프로토콜을 가리지 않지만, 분배 단위가 "요청"이 아니라 "커넥션"이라서 keep-alive·gRPC·웹소켓처럼 커넥션이 오래 사는 트래픽에서는 한 번 정해진 백엔드에 그 커넥션의 모든 요청이 눌러앉아 편중이 생긴다. L7 로드밸런서는 클라이언트의 커넥션을 자기가 종단하고 백엔드로 별도의 커넥션을 새로 맺는다 — 이 "종단"이라는 한 가지 사실에서 나머지가 전부 파생된다: 요청 단위 분배와 경로·헤더·쿠키 기반 라우팅이 가능해지고, keep-alive·타임아웃·버퍼링 설정이 앞뒤로 두 벌 존재하게 되며, 백엔드가 보는 소켓 주소가 LB가 되어 `X-Forwarded-*` 헤더 계약이 필요해진다. 장애 감지도 같은 구도다: L4의 TCP 헬스체크는 커널이 handshake를 대신 끝내주므로 앱이 데드락에 빠져 있어도 계속 통과하는 반면, L7 헬스체크는 `/health`가 200을 주는지까지 본다 — 단, 그 헬스체크가 DB까지 검사하면 DB의 순간 장애가 전 인스턴스 동시 이탈로 증폭되므로 liveness와 readiness를 나눠야 한다.**

---

## 0. 질문 + 의도

**질문**: "L4와 L7 로드밸런서의 차이와, 각각에서 가능한 라우팅/장애 감지 방식은?"

**출제 의도**: 어느 계층에서 라우팅하느냐가 가능한 기능(경로 기반 분기, 쿠키 스티키니스)과 성능을 결정한다. 인프라 팀과 트래픽 구성을 논의할 때 필요한 공용어 — "우리 LB가 L4냐 L7이냐"에 따라 백엔드가 기대할 수 있는 것(클라이언트 IP, 세션 고정, 헬스체크의 의미)이 달라진다는 것을 아는지 본다.

## 1. 계층이 다르다는 것의 의미

### 1-1. 전제 — 계층 번호가 뜻하는 것

먼저 이름의 숫자부터 정리하자. **L4·L7의 숫자는 OSI 7계층 모델의 계층 번호**다. L4는 전송 계층(TCP·UDP), L7은 응용 계층(HTTP·gRPC 등)이다.

로드밸런서 이름에 이 숫자가 붙는 이유는 **"트래픽을 어디까지 읽고 분배를 결정하는가"**를 나타내기 때문이다. 네트워크를 흐르는 데이터는 껍질이 겹겹이 쌓인 구조다.

```
[이더넷 프레임 [ IP 헤더 [ TCP 헤더 [ HTTP 요청                          ] ] ] ]
                 └출발지 IP  └출발지 포트   └ GET /api/orders HTTP/1.1
                 └목적지 IP  └목적지 포트     Host: api.example.com
                                              Cookie: SESSION=abc...

     ←──────── L4 로드밸런서가 보는 범위 ────────┤
     ←──────────────── L7 로드밸런서가 보는 범위 ─────────────────────────→
```

L4는 IP 헤더와 TCP 헤더까지만 열어 본다. 그 안의 바이트는 HTTP인지 MySQL 프로토콜인지 게임 서버의 자체 규약인지 **해석하지 않는다.** L7은 그 안까지 열어 HTTP로 파싱한다.

**우편에 비유하면** L4는 봉투 겉면의 주소만 보고 배달 트럭을 정하는 분류 센터고, L7은 봉투를 열어 편지 내용을 읽고 "청구서는 경리팀, 이력서는 인사팀"으로 나눠 주는 비서다. 분류 센터는 하루에 수십만 통을 처리할 수 있지만 내용을 모르고, 비서는 내용에 맞게 정확히 배분하지만 편지 한 통마다 읽는 시간이 든다.

### 1-2. L4 — 패킷을 전달할 뿐, 연결의 끝이 아니다

L4 로드밸런서가 하는 일을 정확히 보자. 클라이언트가 TCP 연결을 맺으려고 SYN 패킷을 보내면, L4 LB는 그 패킷을 보고 **백엔드 하나를 고른 뒤 목적지 주소를 그 백엔드로 바꿔서 흘려보낸다.** 그리고 이 커넥션(출발지 IP·포트, 목적지 IP·포트, 프로토콜의 5개 값 조합, **5-튜플**)을 자기 연결 추적 테이블에 적어둔다. 이후 같은 5-튜플의 패킷은 매번 판단하지 않고 테이블을 보고 같은 백엔드로 보낸다.

여기서 **결정적인 사실**이 나온다. **TCP 연결의 양 끝은 여전히 클라이언트와 백엔드다.** 3-way handshake의 SYN-ACK를 만드는 것은 백엔드이고, 시퀀스 번호를 관리하는 것도 클라이언트와 백엔드다. L4 LB는 그 사이를 지나는 패킷의 주소를 갈아 끼우는 중계자일 뿐, **자기만의 TCP 상태 기계와 송수신 버퍼를 갖는 통신 주체가 아니다.**

그래서 L4 LB에는 이런 성질이 따라온다.

- **분배 결정은 커넥션당 한 번만 일어난다.** 커넥션이 맺어지는 첫 SYN에서 백엔드를 고르고 나면, 그 커넥션 위로 요청이 100건이 오가든 그 백엔드로 간다. **분배 단위가 "요청"이 아니라 "커넥션"**이라는 이 사실이 2-5절의 실무 함정을 만든다.
- **프로토콜을 가리지 않는다.** 안의 바이트를 해석하지 않으므로 HTTP든 PostgreSQL 프로토콜이든 Redis든 자체 TCP 규약이든 똑같이 분배한다.
- **비용이 낮다.** 패킷 헤더 몇 바이트를 고쳐 전달하는 수준이라, 같은 자원으로 훨씬 많은 트래픽을 감당한다.

### 1-3. L7 — "커넥션을 종단한다"는 말의 뜻

**이 절이 이 문서 전체의 뿌리다.** L7 로드밸런서는 앞의 방식으로는 동작할 수 없다. HTTP 요청 줄과 헤더를 읽으려면 **TCP 스트림을 재조립해야** 하고, 그러려면 자기가 TCP 연결의 한쪽 끝이 되어야 하기 때문이다.

**커넥션을 종단(terminate)한다는 것은 "내가 이 TCP 연결의 반대쪽 끝이 된다"는 뜻이다.** 클라이언트의 SYN에 SYN-ACK로 답하는 것도, 시퀀스 번호를 관리하고 재전송을 처리하고 수신 버퍼를 채우는 것도 LB 자신이다. 그리고 백엔드로 보낼 때는 **완전히 별개의 새 TCP 연결**을 맺는다.

```
[L4 — 커넥션 하나가 관통한다]

  클라이언트 ─────────── 하나의 TCP 연결 ─────────────── 백엔드
                    ↑
                [L4 LB] 주소만 갈아 끼워 패킷을 통과시킨다
                        (연결 추적 테이블은 갖지만 TCP 종단점은 아니다)

  · TCP 상태 기계: 클라이언트와 백엔드에 하나씩
  · 백엔드가 보는 소켓의 상대 주소: 클라이언트 IP (SNAT를 쓰지 않는 구성이면 그대로 보인다)


[L7 — 커넥션이 둘로 잘린다]

  클라이언트 ── TCP 연결 ① ──→ [L7 LB] ── TCP 연결 ② ──→ 백엔드
              (클라이언트↔LB)            (LB↔백엔드)
                                 │
                                 └─ HTTP 요청을 파싱하고, 어디로 보낼지 정하고,
                                    필요하면 헤더를 고쳐서, 연결 ②로 새로 써 보낸다

  · TCP 상태 기계: 총 네 개 (클라이언트 / LB의 앞쪽 / LB의 뒤쪽 / 백엔드)
  · 백엔드가 보는 소켓의 상대 주소: LB의 IP
```

### 1-4. 종단이 낳는 네 가지 귀결

"커넥션이 둘로 잘린다"는 한 문장에서 실무에서 부딪히는 것들이 전부 파생된다. 하나씩 짚자.

**첫째, 분배 단위가 요청이 된다.** LB는 연결 ①에서 HTTP 요청을 하나씩 꺼내 읽으므로, **요청마다 다른 백엔드를 고를 수 있다.** 같은 클라이언트 커넥션에서 온 요청 1은 서버 A로, 요청 2는 서버 B로 보낼 수 있다는 뜻이다. L4에서는 불가능한 일이고, 이것이 2-5절의 편중 문제를 L7이 겪지 않는 이유다.

**둘째, 앞뒤 커넥션의 설정이 각각 두 벌 존재한다.** 연결 ①과 연결 ②는 서로 독립적인 TCP 연결이므로, keep-alive 유휴 상한도, 타임아웃도, 버퍼도 각각 따로 있다.

| 나사 | 앞쪽 (클라이언트↔LB) | 뒤쪽 (LB↔백엔드) |
|---|---|---|
| keep-alive 유휴 상한 | `keepalive_timeout` (server 컨텍스트) | `keepalive_timeout` (upstream 컨텍스트) |
| 커넥션당 최대 요청 수 | `keepalive_requests` (server) | `keepalive_requests` (upstream) |
| 읽기 타임아웃 | `client_body_timeout` | `proxy_read_timeout` |
| 버퍼 | `client_body_buffer_size` | `proxy_buffers` |

**이 두 벌이 어긋나면 유령 현상이 생긴다.** 대표적인 것이 뒤쪽 keep-alive 경쟁으로 인한 간헐적 502다 — 백엔드가 유휴 커넥션을 닫는 순간과 LB가 그 커넥션을 재사용하려는 순간이 겹치면, LB의 `write()`는 성공했는데 응답을 읽으려는 순간 RST를 만난다. **재사용하는 쪽(LB)의 유휴 상한을 닫는 쪽(백엔드)보다 짧게** 두는 것이 규칙이다(10번 문서 3-3절, 13번 문서).

**셋째, 백엔드가 보는 소켓 주소가 LB가 된다.** 백엔드와 TCP 연결을 맺은 상대는 연결 ②의 반대쪽, 즉 LB다. 그래서 서블릿의 `request.getRemoteAddr()`은 **언제나 LB의 IP**를 돌려준다. 접근 로그의 클라이언트 IP가 전부 같은 값으로 찍히고, IP 기반 rate limit이 모든 트래픽을 하나의 키로 몰아 무의미해진다.

복원 수단은 **HTTP 헤더 계약**이다. LB가 자기가 소켓에서 관측한 클라이언트 IP를 `X-Forwarded-For`에 적어 전달하고, 백엔드가 그것을 읽는다. 같은 이유로 `X-Forwarded-Proto`(원래 스킴이 https였는지)도 필요하다 — 이걸 빠뜨리면 "https로 리다이렉트" 로직이 무한 루프에 빠진다. 헤더는 클라이언트가 위조할 수 있으므로 신뢰 경계 설정이 함께 필요하다(17번·22번 문서).

**여기서 L4와의 대비가 선명해진다.** L4는 커넥션을 종단하지 않으므로, **목적지 주소만 바꿔 넘기는 구성이라면 백엔드의 소켓에 클라이언트 IP가 그대로 보인다.** 헤더 계약이 애초에 필요 없다는 뜻이다.

다만 L4라고 항상 그런 것은 아니다. **응답이 돌아올 때도 반드시 LB를 거치게 하려고 출발지 주소까지 LB의 것으로 바꿔치는 구성(SNAT)**이 흔한데, 이러면 L4에서도 백엔드는 LB의 IP를 보게 된다. 이때 L4는 HTTP 헤더를 붙일 수단 자체가 없으므로 **PROXY protocol**이라는 별도 규약을 쓴다 — TCP 연결이 맺어진 직후 데이터 앞에 "원래 출발지는 1.2.3.4:5678이었다"는 한 줄을 먼저 흘려보내는 방식이고, 백엔드도 그 규약을 이해하도록 설정돼 있어야 한다.

**넷째, LB가 완충지대가 된다.** 앞뒤 커넥션의 속도가 분리되므로, 느린 클라이언트에게 응답을 흘려보내는 일을 LB가 떠맡고 백엔드는 빠른 로컬 통신만 하고 스레드를 반납할 수 있다. 이것이 12번 문서에서 다룬 **버퍼링에 의한 격리**이고, L7 종단이 있어야 성립한다. L4에서는 클라이언트와 백엔드가 직접 연결되어 있으므로 느린 클라이언트의 속도가 백엔드 스레드에 그대로 전파된다.

### 1-5. 한눈 대조

앞의 설명을 짧게 대조하면 이렇다.

| 구분 | L4 | L7 |
|---|---|---|
| 보는 정보 | IP, 포트 (+ TLS ClientHello의 SNI) | HTTP 메서드·경로·호스트·헤더·쿠키 |
| 분배 단위 | TCP/UDP 커넥션 (첫 SYN에서 한 번) | HTTP 요청 (요청마다) |
| TCP 연결 | 클라이언트↔백엔드 하나 | LB에서 종단 후 두 개로 분리 |
| 백엔드가 보는 IP | 클라이언트 IP (SNAT 구성이면 LB IP + PROXY protocol) | 항상 LB IP (`X-Forwarded-For`로 복원) |
| 프로토콜 | 무엇이든 (DB, Redis, 게임 TCP, TLS 그대로) | HTTP(S)·gRPC 계열 |
| 버퍼링 격리 | 없음 (클라이언트 속도가 백엔드에 전파) | 가능 |
| 비용 | 낮음 (패킷 전달 수준) | 파싱·종단·버퍼링 비용 |
| 헬스체크 깊이 | TCP 연결이 맺어지는가 | HTTP 응답이 정상인가 |

클라우드로 옮기면 **AWS의 NLB(Network Load Balancer)가 L4, ALB(Application Load Balancer)가 L7**이다. 이름 자체가 "네트워크 계층 수준"과 "애플리케이션 계층 수준"을 가리킨다. (가산점 포인트)

## 2. 라우팅과 분배 — 무엇을 근거로, 어디로 보내는가

### 2-1. 서로 다른 두 질문을 구분하자

"로드밸런싱"이라는 한 단어 안에 사실 **성격이 다른 두 질문**이 들어 있다. 이걸 섞어 말하면 논의가 흐려진다.

1. **라우팅**: "이 요청을 **어느 서버 그룹**으로 보낼 것인가?" — `/api/`는 API 서버군, `/static/`은 정적 서버군.
2. **분배 알고리즘**: "고른 그룹 **안에서 어느 인스턴스**에 보낼 것인가?" — 라운드로빈, 최소 연결, 해시.

**계층이 결정적으로 가르는 것은 1번이다.** 라우팅의 근거로 쓸 수 있는 정보가 계층에 따라 다르기 때문이다. 2번의 알고리즘 자체는 양쪽 다 쓸 수 있다 — 다만 **적용 단위가 다르다**(L4는 커넥션마다, L7은 요청마다). 그 차이가 2-5절에서 큰 사고를 만든다.

### 2-2. L7에서만 가능한 라우팅 — 요청 내용을 읽으므로

**호스트 기반 라우팅.** HTTP 요청의 `Host` 헤더를 읽어 `api.example.com`은 API 서버군으로, `admin.example.com`은 어드민 서버군으로 보낸다. 하나의 공인 IP·하나의 LB 뒤에 여러 서비스를 배치하는 구성의 전제다.

**경로 기반 라우팅.** 요청 줄의 URL 경로를 읽어 `/api/orders`는 주문 서비스, `/api/users`는 사용자 서비스로 보낸다. **마이크로서비스를 하나의 도메인 뒤에 숨기는 구성이 이것 없이는 성립하지 않는다.** 클라이언트 입장에서는 서비스가 몇 개로 쪼개져 있는지 몰라도 되고, 나중에 서비스를 더 쪼개도 클라이언트를 안 고쳐도 된다.

**헤더·쿠키 기반 라우팅.** 특정 헤더가 붙은 요청만 신버전 서버군으로 보낸다(내부 QA용 카나리), 또는 LB가 발급한 쿠키를 읽어 같은 사용자를 계속 같은 인스턴스로 보낸다(쿠키 스티키니스).

**가중치 기반 카나리·A/B 테스트.** 신버전 서버군에 5%만 흘려보고 지표가 정상이면 비중을 올린다. **이것이 L7에서만 되는 이유가 중요하다** — L4에서 "5%"는 커넥션의 5%다. keep-alive로 커넥션 하나가 요청 100건을 나르면 요청 기준 비율은 5%에서 크게 벗어난다. L7은 요청 단위로 세므로 비율이 정확하다.

**요청·응답 재작성.** 경로 앞부분을 떼고 백엔드로 보내거나(`/api/orders/1` → `/orders/1`), 응답에 보안 헤더를 붙이거나, gzip 압축을 앞단에서 처리하는 것. 전부 HTTP를 이해해야 가능하다.

```nginx
# L4로는 불가능하고 L7에서만 가능한 라우팅

# ① 호스트 기반 — Host 헤더를 읽어야 가능
server {
    server_name api.example.com;
    location / { proxy_pass http://api_servers; }
}
server {
    server_name admin.example.com;
    location / { proxy_pass http://admin_servers; }
}

# ② 경로 기반 — 요청 URL을 읽어야 가능
server {
    server_name api.example.com;
    location /api/orders/ { proxy_pass http://order_servers; }
    location /api/users/  { proxy_pass http://user_servers; }
    location /static/     { root /var/www; }        # 아예 뒤로 안 보낸다
}

# ③ 헤더 기반 카나리 — 특정 헤더가 있는 요청만 신버전으로
map $http_x_canary $upstream_pool {
    default  stable_servers;
    "on"     canary_servers;
}
server {
    location / { proxy_pass http://$upstream_pool; }
}

# ④ 가중치 기반 카나리 — 요청의 5%만 신버전으로
#    (split_clients는 주어진 문자열을 해시해 비율대로 나눈다.
#     $request_id를 쓰면 요청마다 무작위, $cookie_uid를 쓰면 사용자별로 고정된다.)
split_clients "${request_id}" $canary_pool {
    5%      canary_servers;
    *       stable_servers;
}
```

### 2-3. L4에서 가능한 라우팅 — 근거가 IP·포트뿐일 때

**포트 기반 분기**가 가장 기본이다. 443으로 들어온 것은 웹 서버군, 5432는 PostgreSQL 읽기 복제본 그룹, 6379는 Redis 그룹. **L4가 HTTP가 아닌 트래픽까지 분배할 수 있다는 것이 여기서 값을 한다.**

**5-튜플 해시**로 커넥션을 백엔드에 고정한다. 출발지 IP·포트, 목적지 IP·포트, 프로토콜을 해시해 백엔드를 고르는 방식이다. 같은 커넥션의 패킷은 항상 같은 값이 나오므로 자연스럽게 같은 백엔드로 간다.

**출발지 IP 해시**는 5-튜플에서 출발지 포트를 뺀 것이다. 같은 클라이언트의 서로 다른 커넥션까지 같은 백엔드로 보내므로 원시적인 세션 고정 수단이 된다. 함정은 2-4절에서 다룬다.

**그리고 예외가 하나 있다. TLS passthrough 상태에서도 SNI 기반 라우팅은 가능하다.** (가산점 포인트)

이게 왜 되는지가 재미있다. TLS handshake의 첫 메시지인 **ClientHello는 아직 암호화 전이라 평문**이다. 그리고 그 안에 **SNI(Server Name Indication)** 확장이 들어 있는데, 클라이언트가 "나는 `api.example.com`에 접속하려 한다"를 적어 보내는 필드다. 원래 목적은 하나의 IP에 여러 도메인의 인증서가 걸려 있을 때 서버가 어느 인증서를 내밀지 정하기 위한 것이다.

**LB가 암호를 풀지 않고도 이 필드를 읽을 수 있으므로, "도메인별로 다른 백엔드 그룹으로 보내기"까지는 passthrough에서도 된다.** 경로 기반 라우팅은 HTTP 안에 있어 암호화되므로 여전히 불가능하다. 17번 문서(TLS termination)에서 같은 사실을 다룬다.

```nginx
# Nginx의 stream 모듈 — L4(TCP) 수준으로 동작한다.
# TLS를 풀지 않고 ClientHello의 SNI만 보고 백엔드 그룹을 고른다.
stream {
    map $ssl_preread_server_name $backend_pool {
        api.example.com    api_tls_backend;
        admin.example.com  admin_tls_backend;
        default            api_tls_backend;
    }

    upstream api_tls_backend   { server 10.0.1.10:8443; server 10.0.1.11:8443; }
    upstream admin_tls_backend { server 10.0.2.10:8443; }

    server {
        listen 443;
        # ssl_preread: TLS를 종료하지 않고 ClientHello만 미리 훑어
        # $ssl_preread_server_name 같은 변수를 채운다.
        ssl_preread on;
        proxy_pass $backend_pool;   # 암호문은 그대로 통과시킨다
    }
}
```

### 2-4. 분배 알고리즘 — 그룹 안에서 어느 인스턴스로

이제 두 번째 질문이다. 그룹은 정해졌고, 그 안의 인스턴스 중 하나를 골라야 한다.

**라운드로빈(round robin)** — 순서대로 돌아가며 배정한다. 가장 단순하고 대부분의 LB 기본값이다. **전제는 "모든 요청의 처리 비용이 비슷하다"**는 것이다. 그 전제가 맞으면 균등 분배가 나온다.

**최소 연결(least connections)** — 지금 활성 커넥션이 가장 적은 인스턴스로 보낸다. **요청 처리 시간의 편차가 클 때 쓴다.** 라운드로빈은 요청 "개수"만 세므로, 어떤 인스턴스에 우연히 무거운 요청(대용량 리포트 생성 같은)이 몰려도 계속 같은 비율로 보낸다. 최소 연결은 "지금 몇 건을 붙들고 있는가"를 보므로 무거운 요청을 처리 중인 인스턴스에는 자연히 덜 간다.

**가중치(weight)** — 인스턴스 성능이 다를 때 쓴다. 스펙이 두 배인 서버에 두 배를 보낸다. 실무에서는 **성능 차이보다 배포 전략에 더 많이 쓴다** — 신버전 인스턴스에 가중치 1, 구버전에 19를 줘서 5%만 흘리는 식이다.

**해시(hash)** — 어떤 키를 해시해서 인스턴스를 고른다. **같은 키는 항상 같은 인스턴스로 간다**는 것이 목적이다. 키로 무엇을 쓰느냐로 갈린다.

- **IP 해시**: 클라이언트 IP를 키로 쓴다. 세션이 서버 메모리에 있을 때 쓰던 방식이다.
- **URL 해시 / 임의 키 해시**: 캐시 서버 앞단에서 유용하다. 같은 URL 요청이 항상 같은 캐시 서버로 가면 캐시 적중률이 크게 오른다.

여기서 **일반 해시와 일관성 해시(consistent hash)의 차이**를 알아야 한다. 일반 해시는 보통 `해시값 % 서버수`로 인스턴스를 고르는데, **서버가 한 대 늘거나 줄면 나눗셈의 분모가 바뀌어 거의 모든 키의 배정이 뒤집힌다.** 서버 4대에서 5대가 되면 키의 대략 80%가 다른 서버로 옮겨간다. 캐시 앞단이라면 그 순간 캐시가 거의 전부 무효화되어 뒤쪽 원본으로 요청이 쏟아진다.

**일관성 해시는 서버와 키를 같은 원형 공간(해시 링)에 배치하고, 키에서 시계 방향으로 가장 가까운 서버에 배정한다.** 서버 하나가 빠지면 그 서버가 담당하던 구간만 이웃에게 넘어가고 나머지는 그대로다. **서버 수가 N에서 N+1로 바뀔 때 재배치되는 키가 대략 1/(N+1)로 억제된다.** Nginx에서는 `hash <키> consistent;`로 켠다.

```nginx
# ① 라운드로빈 — 기본값. 지시자를 안 쓰면 이것이다.
upstream api_servers {
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
}

# ② 최소 연결 — 요청 처리 시간 편차가 클 때
upstream report_servers {
    least_conn;
    server 10.0.0.21:8080;
    server 10.0.0.22:8080;

    # ★ 워커 프로세스마다 독립적으로 커넥션 수를 세면 판단이 어긋난다.
    #   zone을 선언해야 워커들이 공유 메모리로 상태를 함께 본다.
    zone report_zone 64k;
}

# ③ 가중치 — 카나리 배포에 쓰는 형태
upstream canary_servers {
    server 10.0.0.31:8080 weight=19;   # 구버전 95%
    server 10.0.0.32:8080 weight=1;    # 신버전 5%
}

# ④ IP 해시 — 세션 고정용. 함정은 아래 참조.
upstream sticky_servers {
    ip_hash;
    server 10.0.0.41:8080;
    server 10.0.0.42:8080;
}

# ⑤ 일관성 해시 — 캐시 서버 앞단. 서버 증감 시 재배치를 최소화한다.
upstream cache_servers {
    hash $request_uri consistent;
    server 10.0.0.51:8080;
    server 10.0.0.52:8080;
    server 10.0.0.53:8080;
}
```

**IP 해시(그리고 L4의 출발지 IP 해시)에는 두 개의 큰 함정이 있다.** 알고리즘 이야기가 나오면 반드시 함께 말해야 하는 부분이다.

**첫째, 같은 NAT 뒤의 사용자들이 전부 같은 IP로 보인다.** 회사망이나 통신사의 CGNAT 뒤에 있는 사용자 수천 명이 하나의 공인 IP를 공유하면, **그 수천 명이 전부 한 인스턴스로 몰린다.** 분배가 아니라 집중이 된다. (참고로 Nginx의 `ip_hash`는 IPv4의 앞 세 옥텟만 해시에 쓰므로 같은 /24 대역이면 같은 인스턴스로 간다 — 쏠림이 더 커진다.)

**둘째, 모바일에서 IP가 바뀌면 고정이 깨진다.** 와이파이에서 LTE로 넘어가는 순간 다른 인스턴스로 배정되고, 그 인스턴스에는 세션이 없다.

그래서 **스티키 세션은 어느 계층에서 하든 "서버에 상태가 있다"는 문제의 증상 완화일 뿐**이다. 근본 해법은 세션을 Redis 같은 외부 저장소로 빼는 무상태 설계다. 스티키에 의존하는 구조는 인스턴스가 죽는 순간 그 인스턴스에 붙어 있던 사용자 전원이 로그아웃되는 위험을 계속 안고 간다.

### 2-5. L4의 커넥션 단위 분배 × keep-alive = 편중

**이것이 L4의 가장 실무적인 함정이고, gRPC나 웹소켓을 도입한 팀이 실제로 부딪히는 문제다.**

전제를 다시 확인하자. **L4는 커넥션이 맺어질 때 단 한 번 백엔드를 고른다.** 그 결정은 커넥션이 살아 있는 동안 바뀌지 않는다. 그러면 **커넥션이 얼마나 오래 사느냐가 곧 분배의 품질**이 된다.

커넥션이 짧게 살면 문제가 없다. HTTP/1.1 브라우저 트래픽은 커넥션이 수십 초 안에 정리되고 새 커넥션이 계속 생기므로, 커넥션 단위 분배도 통계적으로 고르게 퍼진다.

문제는 **커넥션이 오래 사는 트래픽**이다.

- **gRPC**: HTTP/2 위에서 동작하고, HTTP/2는 커넥션 하나에 여러 요청(스트림)을 다중화한다. 그래서 gRPC 클라이언트는 **커넥션 하나를 맺어두고 그 위로 초당 수백 건의 RPC를 흘려보낸다.** 커넥션은 몇 시간씩 산다.
- **웹소켓·SSE**: 애초에 "끊지 않고 유지하는" 것이 목적인 프로토콜이다. 커넥션 수명이 분~시간 단위다(14번 문서).
- **내부 서비스 간 HTTP 호출**: 커넥션 풀을 쓰면 풀에 잡아둔 커넥션이 계속 재사용된다(10번 문서).

이 상황에서 L4가 만드는 그림은 이렇다.

```
[gRPC 클라이언트 4대가 각각 커넥션 1개씩, L4 LB 뒤에 백엔드 2대]

  클라이언트 #1 ══ 커넥션 ══→ 백엔드 A
  클라이언트 #2 ══ 커넥션 ══→ 백엔드 B
  클라이언트 #3 ══ 커넥션 ══→ 백엔드 A
  클라이언트 #4 ══ 커넥션 ══→ 백엔드 B

  커넥션 수는 2:2 로 완벽하게 균등하다.
  그런데 클라이언트 #1이 초당 1,000 RPC, 나머지는 초당 10 RPC 를 보낸다면?
      백엔드 A: 1,010 RPC/s
      백엔드 B:    20 RPC/s
  → LB는 "균등하게 분배했다"고 보고하지만 실제 부하는 50배 차이 난다.
```

**LB가 세는 단위(커넥션)와 실제 부하의 단위(요청)가 다르다**는 것이 이 문제의 본질이다.

여기에 배포가 겹치면 더 나빠진다. **롤링 재시작이 편중을 고착시키는 과정**을 계산으로 따라가 보자. 인스턴스 3대(A·B·C)에 장수 커넥션 24개가 8개씩 균등하게 붙어 있는 상태에서 시작한다.

| 단계 | 일어나는 일 | A | B | C |
|---|---|---|---|---|
| 시작 | 균등 | 8 | 8 | 8 |
| ① A 재시작 | A의 8개가 끊겨 B·C로 재연결(4개씩) | **0** | 12 | 12 |
| ② B 재시작 | B의 12개가 끊겨 A·C로 재연결(6개씩) | 6 | **0** | 18 |
| ③ C 재시작 | C의 18개가 끊겨 A·B로 재연결(9개씩) | 15 | 9 | **0** |
| 최종 | | **15 (62.5%)** | **9 (37.5%)** | **0 (0%)** |

**배포가 끝난 시점에 가장 마지막으로 재시작한 인스턴스 C는 커넥션이 0개다.** 새 클라이언트가 붙기 전까지는 트래픽을 한 건도 안 받는다. 그리고 A는 전체의 62.5%를 떠안는다. **커넥션은 한 번 붙으면 스스로 옮겨가지 않으므로, 이 불균형은 저절로 회복되지 않는다.** 오토스케일로 인스턴스를 새로 띄워도 마찬가지다 — 새 인스턴스는 새 커넥션이 생길 때까지 논다.

**대응은 셋이다.**

**(1) L7 LB를 쓴다.** L7은 요청 단위로 분배하므로 커넥션이 얼마나 오래 살든 상관없다. gRPC를 지원하는 L7 LB(ALB의 gRPC 대상 그룹, Envoy, Nginx의 `grpc_pass`)를 쓰면 HTTP/2 스트림 단위로 나눠 보낸다. **가장 확실한 해법이다.**

**(2) 커넥션의 수명에 상한을 둔다.** 커넥션을 주기적으로 끊어 재분배 기회를 만든다. gRPC 서버에는 커넥션 최대 수명 설정이 있고, Nginx에는 커넥션당 요청 수 상한(`keepalive_requests`)이 있다. **커넥션이 짧게 살면 커넥션 단위 분배도 고르게 퍼진다**는 원리를 이용하는 것이다. 다만 끊고 다시 맺는 비용(handshake, TLS, slow start)을 내야 하므로 상한을 너무 짧게 두면 손해다.

**(3) 클라이언트 측 로드밸런싱.** 클라이언트가 백엔드 목록을 직접 알고 여러 인스턴스에 커넥션을 나눠 맺는다. LB를 안 거치므로 편중이 없지만, 클라이언트가 인스턴스 목록을 알아내는 서비스 디스커버리가 필요해진다.

### 2-6. 2단 구성 — 양자택일이 아니다

L4만 있는 환경에서 "경로별로 다른 서비스로 보내달라"는 요구가 오면 **구조적으로 불가능하다.** 근거로 쓸 정보가 애초에 없기 때문이다.

이때 흔한 답이 **L4 뒤에 L7을 한 단 더 두는 2단 구성**이다.

```
                    ┌── [L7 프록시 #1] ──┬──→ 주문 서비스 인스턴스들
 인터넷 ──→ [L4 LB] ─┤                    ├──→ 사용자 서비스 인스턴스들
                    └── [L7 프록시 #2] ──┴──→ 정적 서버들
              ↑                ↑
       대량 트래픽을      HTTP를 읽고
       L7 프록시들에      경로·헤더 기반으로
       커넥션 단위로      요청 단위 분기
       고르게 뿌린다
```

**각 계층이 자기가 잘하는 일만 한다.** L4는 값싼 패킷 전달로 대량 트래픽을 감당하고, L7은 내용 기반 분기를 담당한다. 그리고 L4 앞단에서 커넥션 편중이 생기더라도 **L7 프록시들은 동질적이고 상태가 없으므로** 조금 불균형해도 큰 문제가 안 된다 — 편중이 아픈 것은 실제 애플리케이션 인스턴스 쪽이다.

## 3. 장애 감지 — "살아있다"의 정의가 계층마다 다르다

헬스체크는 로드밸런서가 **"이 서버에 트래픽을 보내도 되는가"**를 판단하는 근거다. 그리고 계층에 따라 확인할 수 있는 **생존의 깊이**가 다르다.

### 3-1. L4 헬스체크가 실제로 확인하는 것

**L4 헬스체크는 대상 포트로 TCP 연결을 시도해서, 연결이 맺어지면 정상으로 판정한다.** 여기서 정확히 무슨 일이 일어나는지가 이 절의 핵심이다.

전제를 하나 깔자. 서버가 `listen()`을 호출하면 커널은 그 포트에 대해 **큐를 두 개** 만든다.

```
클라이언트의 SYN 도착
      │
      v
  [SYN 큐]  ─ handshake 진행 중인 연결들. 커널이 SYN-ACK를 보내고 ACK를 기다린다.
      │
      │ 클라이언트의 ACK 도착 → handshake 완료
      v
  [accept 큐] ─ handshake가 끝나 "완성된" 연결들. 애플리케이션이 가져가기를 기다린다.
      │            (큐 크기 = backlog. 스프링 부트 내장 Tomcat 기본값 100)
      │
      │ 애플리케이션이 accept() 를 호출
      v
  애플리케이션이 그 연결을 처리하기 시작
```

**결정적인 사실: 3-way handshake를 완료하는 것은 커널이다.** 애플리케이션이 `accept()`를 호출하든 말든, 커널은 SYN에 SYN-ACK로 답하고 ACK를 받아 연결을 완성해 accept 큐에 넣는다.

그래서 이런 결론이 나온다. **애플리케이션이 완전히 멈춰 있어도 TCP 연결은 성립한다.** L4 헬스체크는 연결을 맺고 바로 끊는 것이 전부이므로, **커널이 살아 있으면 통과한다.** 확인되는 것은 "프로세스가 그 포트를 리스닝하고 있는가"까지이고, 그마저도 정확히는 "커널의 리스닝 소켓이 존재하는가"다.

### 3-2. 그래서 생기는 사고 — 데드락에 빠진 좀비 서버

구체적인 장애 시나리오로 보자.

```
[상황] JVM 인스턴스 4대, L4 LB, TCP 헬스체크(5초 주기)
       인스턴스 #2 에서 데드락 발생 —
       워커 스레드 200개가 전부 어떤 락을 기다리며 잠들었다.

  t=0     데드락 발생. 이후 인스턴스 #2 는 어떤 요청도 응답하지 못한다.

  t=5     L4 헬스체크: TCP 연결 시도
          → 커널이 handshake 완료, accept 큐에 넣음
          → LB: 연결 성공 = ✓ 정상
          ★ JVM 스레드는 하나도 안 움직였는데 통과했다.

  t=5~    사용자 요청이 계속 인스턴스 #2 로 배정된다.
          · 이미 맺어진 keep-alive 커넥션 위의 요청 → 응답이 영영 안 온다.
            TCP 수준에서는 아무 이상 신호도 없다. 그냥 조용하다.
          · 새 연결 요청 → 커널이 handshake를 완료해 accept 큐에 쌓는다.
            큐(기본 100)가 찰 때까지는 클라이언트 입장에서 "연결은 됐다".

  t=10    헬스체크 ✓ (여전히 통과)
  t=15    헬스체크 ✓
  ...

  → 사용자의 4분의 1이 타임아웃까지 기다렸다가 실패한다.
    LB의 대시보드에는 "4대 전부 정상"이라고 찍혀 있다.
```

**"프로세스는 살아 있는데 서비스는 죽어 있는" 상태를 L4는 원리적으로 구분할 수 없다.** 같은 일이 데드락뿐 아니라 **DB 커넥션 풀 고갈**, **긴 Full GC**, **스레드 풀 포화**에서도 벌어진다.

가장 고약한 것은 **keep-alive 커넥션 위의 요청**이다. 새 연결을 맺을 필요가 없으니 accept 큐와 무관하고, 요청을 보내도 응답이 안 올 뿐 TCP 연결은 멀쩡하다. **클라이언트는 자기 쪽 타임아웃이 터질 때까지 기다릴 수밖에 없다.**

### 3-3. L7 헬스체크 — "200을 주는가"

**L7 헬스체크는 `GET /health` 같은 실제 HTTP 요청을 보내고, 상태 코드(그리고 필요하면 응답 본문)를 확인한다.**

위 시나리오에 L7 헬스체크를 적용하면 t=5의 체크에서 **응답이 아예 안 오므로 타임아웃**으로 실패 판정이 난다. 연속 실패 임계치를 넘기면 인스턴스 #2가 분배 대상에서 빠지고, 나머지 3대가 트래픽을 나눠 받는다.

앞서 말한 **좀비 서버** — JVM 프로세스는 떠 있고 포트도 열려 있는데, DB 커넥션 풀 고갈이나 내부 의존성 장애로 **모든 요청에 500을 뱉는** 상태 — 도 마찬가지다. L4 헬스체크는 멀쩡히 통과하지만 L7 헬스체크는 500을 보고 즉시 제외한다.

**"포트는 열려 있는데 500만 뱉는 서버를 걸러낼 수 있느냐"가 두 계층의 차이를 가장 선명하게 보여주는 지점**이고, 면접에서 이 한 문장으로 정리하면 좋다.

```nginx
# 오픈소스 Nginx는 능동적 헬스체크가 없다 — 수동적(passive) 방식만 지원한다.
# 실제 사용자 요청을 보내봤다가 실패하면 그 서버를 일정 시간 제외하는 방식이다.
upstream api_servers {
    # fail_timeout(10초) 안에 max_fails(3회)만큼 실패하면
    # 그 서버를 fail_timeout 동안 분배 대상에서 뺀다.
    server 10.0.0.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=10s;
}

server {
    location / {
        proxy_pass http://api_servers;

        # "실패"의 정의. 기본값은 error timeout 뿐이라 백엔드가 500을 주면
        # Nginx는 그것을 정상 응답으로 보고 그대로 클라이언트에게 전달한다.
        # 즉 500만 뱉는 좀비 서버를 기본 설정으로는 못 걸러낸다.
        # http_500을 넣어야 500 응답도 실패로 세고 다음 서버로 재시도한다.
        proxy_next_upstream error timeout http_502 http_503 http_504 http_500;

        # ★ 재시도가 무한정 일어나면 느린 장애가 전 인스턴스로 번진다.
        #   재시도 횟수와 총 시간 예산에 반드시 상한을 둔다.
        proxy_next_upstream_tries 2;
        proxy_next_upstream_timeout 5s;
    }
}
```

**`proxy_next_upstream`의 기본값에 `http_500`이 없다**는 것은 실무에서 자주 놓치는 부분이다. 기본 설정으로는 Nginx가 "연결 실패"와 "타임아웃"만 실패로 세므로, 백엔드가 꼬박꼬박 500을 돌려주는 상태는 **정상 동작으로 간주되어 계속 트래픽을 받는다.**

### 3-4. 능동적 헬스체크와 수동적 헬스체크

헬스체크에는 두 방식이 있고, 각각의 한계가 다르다. (가산점 포인트)

**능동적(active)** — LB가 주기적으로 체크 요청을 직접 보낸다. 사용자 트래픽과 무관하게 상태를 알 수 있는 것이 장점이다. 단점은 **감지 지연**이다. 서버가 죽어도 다음 체크 주기가 올 때까지, 그리고 연속 실패 임계치를 채울 때까지는 계속 트래픽이 간다.

이 지연을 계산해 보자. 체크 주기 5초, 응답 타임아웃 2초, 연속 실패 임계치 3회인 경우다.

| 시각 | 일어나는 일 |
|---|---|
| t = 0.0s | 직전 체크가 성공한 직후 인스턴스가 죽는다 (최악의 타이밍) |
| t = 5.0s | 1차 체크 시작 → 응답 없음 |
| t = 7.0s | 타임아웃(2초) → 실패 1회 기록 |
| t = 10.0s | 2차 체크 시작 → 응답 없음 |
| t = 12.0s | 타임아웃 → 실패 2회 |
| t = 15.0s | 3차 체크 시작 → 응답 없음 |
| t = 17.0s | 타임아웃 → 실패 3회 = 임계치 도달 → **분배 대상에서 제외** |

**최악의 경우 약 17초 동안 죽은 인스턴스가 트래픽을 계속 받는다.** 전체 트래픽이 초당 1,000건이고 인스턴스가 4대라면, 그 인스턴스로 가는 것은 초당 250건이다.

```
250건/초 × 17초 = 약 4,250건의 요청이 실패한다
```

**주기와 임계치를 줄이면 감지가 빨라지지만 오탐이 늘어난다.** 일시적인 GC 정지나 순간적인 네트워크 지연 때문에 멀쩡한 인스턴스가 빠지고, 남은 인스턴스들에 부하가 몰려 그것들도 느려지고, 그래서 또 빠지는 연쇄가 생길 수 있다. **감지 속도와 안정성의 트레이드오프**이고, 정답은 서비스의 요청 특성에 따라 다르다.

**수동적(passive)** — 실제 사용자 요청의 실패(연결 거부, 5xx)를 관찰해서 일정 비율을 넘으면 제외한다. 별도 체크 트래픽이 없고 실사용 기준이라는 것이 장점이다. 단점은 명확하다 — **사용자가 먼저 실패를 겪은 뒤에야 반응한다.** 오픈소스 Nginx가 이 방식이다(위 설정의 `max_fails`).

**실무에서는 둘을 같이 쓴다.** 능동적으로 주기적 상태를 확인하되, 수동적 관찰로 "체크는 통과하는데 실제 요청은 실패하는" 경우를 잡는다.

### 3-5. 헬스체크를 깊게 하면 생기는 사고 — liveness와 readiness

**헬스체크 엔드포인트는 깊게 검사할수록 좋은 것이 아니다.** 이것이 이 주제에서 가장 시니어 변별력이 있는 부분이다.

`/health`에서 DB 연결을 확인하는 것은 얼핏 합리적으로 보인다. "DB에 못 붙으면 어차피 요청을 처리 못 하니 트래픽을 받으면 안 된다"는 논리다. 그런데 이 논리에는 **"각 인스턴스가 독립적으로 판단한다"는 암묵적 전제**가 깔려 있고, 그 전제가 틀렸다.

```
[DB가 2초간 흔들린 순간]

  t=0.0   DB에서 순간적인 failover 또는 커넥션 리셋 발생

  t=0~2   인스턴스 #1 헬스체크 → DB 검사 실패 → ✗
          인스턴스 #2 헬스체크 → DB 검사 실패 → ✗
          인스턴스 #3 헬스체크 → DB 검사 실패 → ✗
          인스턴스 #4 헬스체크 → DB 검사 실패 → ✗
          ★ 같은 DB를 보고 있으므로 전원이 동시에 실패한다.

  t=2     LB: 정상 인스턴스 0대 → 모든 트래픽이 503
          쿠버네티스라면: readiness 실패로 전 파드가 서비스 엔드포인트에서 이탈

  t=2     DB 복구. 그런데 서비스는 아직 안 돌아온다 —
          헬스체크가 "연속 성공 임계치"를 채워야 다시 편입되기 때문이다.
          여기에 쿠버네티스의 liveness 프로브까지 DB를 검사하고 있었다면
          컨테이너가 재시작까지 되어 JVM 웜업부터 다시 한다.

  → DB의 2초짜리 순단이 서비스의 수십 초~수 분짜리 전면 장애로 증폭됐다.
```

**핵심은 "공통 의존성을 헬스체크에 넣으면 그 의존성의 장애가 전 인스턴스에 동시에 전파된다"**는 것이다. 인스턴스별 판단처럼 보이지만 실제로는 전원이 같은 신호를 보고 같은 판정을 내린다. DB 없이도 응답할 수 있는 요청(정적 응답, 캐시된 조회, 헬스 대시보드)까지 전부 죽는다.

참고로 이런 사고가 워낙 흔해서 **일부 관리형 LB는 "전 대상이 비정상이면 오히려 전부에게 보낸다"는 fail-open 동작을 넣어 뒀다.** AWS ALB가 그렇게 동작한다. 안전장치이긴 하지만, 이걸 믿고 설계하면 안 된다.

**해법은 검사의 목적을 두 가지로 나누는 것이다.** 쿠버네티스가 이 구분을 프로브 이름으로 못 박아 뒀다.

| | liveness (살아 있는가) | readiness (트래픽을 받을 준비가 됐는가) |
|---|---|---|
| 묻는 것 | 프로세스가 스스로 복구 불가능한 상태인가 | 지금 이 인스턴스가 요청을 처리할 수 있는가 |
| 실패 시 조치 | **컨테이너 재시작** | **서비스 엔드포인트에서 일시 제외** (재시작 안 함) |
| 검사 범위 | 자기 자신만. **외부 의존성을 넣으면 안 된다** | 자기 자신 + 재시작으로 해결될 수 있는 상태 |
| DB를 넣으면? | DB 순단에 전 파드가 재시작 = 최악 | 전 파드 동시 이탈 = 여전히 나쁨 |

**원칙은 이렇다.** liveness는 "재시작하면 나아지는가"를 묻는 것이므로, **재시작해도 안 나아지는 것(DB 장애)을 넣으면 안 된다.** readiness는 트래픽 수용 여부이므로 조금 더 넣을 수 있지만, **모든 인스턴스가 공유하는 의존성**은 역시 신중해야 한다.

스프링 부트 액추에이터는 이 구분을 **헬스 그룹**으로 지원한다.

```yaml
# Before: 기본 /actuator/health 하나를 LB와 쿠버네티스 프로브가 함께 쓴다.
#         이 엔드포인트는 등록된 모든 HealthIndicator(db, redis, diskSpace, ...)를
#         집계하므로, DB가 흔들리면 전 인스턴스가 동시에 DOWN이 된다.
management:
  endpoints:
    web:
      exposure:
        include: health

---
# After: 목적별로 그룹을 나눠 검사 범위를 다르게 한다.
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      # 이 옵션을 켜면 /actuator/health/liveness 와 /actuator/health/readiness가 열린다.
      # (쿠버네티스 환경이 감지되면 자동으로 켜지지만, 명시하는 편이 안전하다.)
      probes:
        enabled: true
      group:
        liveness:
          # livenessState만 본다. "애플리케이션 컨텍스트가 살아 있는가"만 확인하며
          # 외부 의존성은 일부러 넣지 않는다 — 실패하면 컨테이너가 재시작되는데,
          # DB 장애는 재시작으로 해결되지 않기 때문이다.
          include: livenessState
        readiness:
          # 트래픽 수용 여부. 자기 자신의 준비 상태만 본다.
          # DB를 여기 넣을지는 판단이 필요하다 — 넣으면 DB 순단에
          # 전 인스턴스가 동시에 이탈한다(위 타임라인).
          # "DB 없이는 어떤 요청도 처리 못 한다"가 확실할 때만 넣는다.
          include: readinessState
      show-details: never   # 헬스체크 응답에 내부 구조를 노출하지 않는다
```

```yaml
# 쿠버네티스 프로브 — 두 그룹을 각각 다른 프로브에 연결한다.
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  # ★ 임계치를 넉넉히 둔다. 여기서 실패하면 컨테이너가 재시작되므로
  #   일시적인 GC 정지로 재시작이 걸리는 것이 훨씬 나쁘다.
  periodSeconds: 10
  failureThreshold: 6

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  # 이쪽은 짧게. 실패해도 트래픽에서만 빠지고 재시작은 안 되므로 되돌리기 쉽다.
  periodSeconds: 5
  failureThreshold: 2
```

**그리고 "의존성 상태를 아예 안 보는 것"이 아니라는 점을 덧붙여야 한다.** DB·Redis의 상태는 **모니터링과 알림**으로 본다. 헬스체크는 "트래픽 배분 판단"이라는 자동 조치의 방아쇠이므로 얕게 두고, 관측은 사람이 보는 별도 채널로 분리하는 것이다. **자동 조치의 방아쇠와 관측 지표를 같은 것으로 쓰면, 관측하려던 장애가 자동 조치를 통해 증폭된다.**

### 3-6. 클라우드 관리형 LB에서의 대응

지금까지의 개념이 AWS에서 어떻게 나타나는지 대응시켜 두면 인프라 팀과 대화할 때 바로 쓸 수 있다.

| 개념 | NLB (L4) | ALB (L7) |
|---|---|---|
| 처리 프로토콜 | TCP, UDP, TLS | HTTP, HTTPS, gRPC |
| 분배 단위 | 커넥션(플로우) | HTTP 요청 |
| 라우팅 근거 | 포트, (TLS 리스너면) SNI | 호스트·경로·헤더·메서드·쿼리·소스 IP |
| 백엔드가 보는 IP | 클라이언트 IP 보존 가능, 또는 PROXY protocol v2 | ALB IP (`X-Forwarded-For`로 전달) |
| 헬스체크 | TCP, HTTP, HTTPS 선택 가능 | HTTP, HTTPS만 |
| 스티키 세션 | 5-튜플/출발지 IP 기반 | LB가 발급한 쿠키 기반 |

**주의할 점이 둘 있다.**

**첫째, NLB도 헬스체크는 HTTP로 할 수 있다.** "L4 LB니까 TCP 헬스체크만 된다"는 것은 오해다. NLB는 대상 그룹의 헬스체크 프로토콜을 TCP 대신 HTTP로 지정할 수 있고, 그러면 3-3절의 이점을 얻는다. **트래픽 분배는 L4로 하면서 헬스체크만 L7로 하는 조합**이 가능하다는 뜻이고, L4를 쓸 수밖에 없는 상황에서 좀비 서버 문제를 완화하는 실용적인 방법이다. (다만 TLS passthrough 구성이면 헬스체크도 HTTPS로 해야 하고, 커넥션 편중 문제는 헬스체크와 무관하게 그대로 남는다.)

**둘째, 인스턴스를 뺄 때도 시간이 필요하다.** 배포로 인스턴스를 내릴 때 LB가 즉시 트래픽을 끊으면 처리 중이던 요청이 끊긴다. 그래서 **연결 드레이닝(등록 해제 지연)**을 둔다 — "새 요청은 안 보내되 처리 중인 것은 마칠 때까지 기다린다"는 유예 시간이다. 이 값이 애플리케이션의 최대 응답 시간보다 짧으면 배포 때마다 일정 비율의 요청이 502로 실패한다. **애플리케이션 쪽의 graceful shutdown(`server.shutdown: graceful`)과 짝으로 설정해야 한다.**

## 4. 꼬리질문 대비 포인트

### "L7이 기능이 더 많은데, L4는 언제 선택하나요?" (시니어 변별 포인트)

**기능과 비용의 트레이드오프**이고, L4를 고르는 상황이 셋이다.

**(1) HTTP가 아닌 트래픽.** PostgreSQL, Redis, MQTT, 게임 서버의 자체 TCP 프로토콜은 L7이 파싱할 수 없다. **"L7이 이해할 수 있는 프로토콜인가"가 첫 번째 관문**이고, 여기서 걸리면 선택의 여지가 없다.

**(2) 극단적 처리량과 저지연.** L4는 패킷 헤더를 고쳐 전달하는 수준이고 L7은 TCP를 종단해 HTTP를 파싱하고 버퍼링까지 한다. 같은 자원에서 감당하는 트래픽 규모가 다르다. 다만 **"성능 때문에 L4"는 신중해야 한다** — 대부분의 서비스는 L7의 오버헤드가 병목이 되기 한참 전에 다른 곳에서 먼저 막힌다. 실측 없이 성능을 근거로 대면 오히려 감점이다.

**(3) TLS를 LB에서 풀면 안 되는 요구.** 규제나 제로 트러스트 정책으로 종단간 암호화가 필요하면 LB가 내용을 볼 수 없으므로 L4 passthrough가 된다. 이때도 SNI 기반 라우팅까지는 된다는 것을 함께 말하면 정확도가 올라간다(17번 문서).

**그리고 반드시 덧붙여야 할 것이 L4의 대가다.** 커넥션 단위 분배라서 **장수 커넥션(gRPC, 웹소켓, 커넥션 풀)에서 편중이 생기고 저절로 회복되지 않는다**는 것, **헬스체크가 TCP 연결 확인으로 후퇴해 좀비 서버를 못 거른다**는 것, **버퍼링에 의한 격리가 없어 느린 클라이언트의 속도가 백엔드 스레드에 그대로 전파된다**는 것이다.

실무에서는 양자택일보다 **L4(대량 분배) 뒤에 L7(내용 기반 분기)을 두는 2단 구성**이 흔하다. "요구사항에 따라 조합한다"고 답하면서 각 계층이 무엇을 맡는지 말할 수 있으면 설계 감각이 드러난다.

### "L4 LB 뒤에서 gRPC를 쓰는데 특정 인스턴스만 CPU가 높습니다. 원인이 뭘까요?" (시니어 변별 포인트)

**L4의 분배 단위가 커넥션이고, gRPC의 커넥션은 오래 살기 때문이다.**

gRPC는 HTTP/2 위에서 동작하고, HTTP/2는 커넥션 하나에 여러 스트림을 다중화한다. 그래서 클라이언트는 **커넥션 하나를 맺어두고 그 위로 초당 수백~수천 건의 RPC를 흘려보낸다.** L4는 그 커넥션이 처음 맺어질 때 백엔드를 한 번 고르고 끝이므로, **LB가 세는 커넥션 수는 균등한데 실제 RPC 수는 크게 어긋난다.**

여기에 롤링 배포가 겹치면 편중이 고착된다. 인스턴스가 재시작될 때마다 그 인스턴스의 커넥션이 살아 있는 인스턴스들로 흩어지고, **커넥션은 스스로 옮겨가지 않으므로 배포가 끝나면 마지막에 재시작한 인스턴스는 커넥션 0개, 처음 재시작한 인스턴스는 과반을 떠안는 상태**가 된다(2-5절의 표).

**대응은 셋이다.** ① 요청 단위로 분배하는 **L7 LB**로 바꾼다(ALB의 gRPC 대상 그룹, Envoy, Nginx `grpc_pass`) — 가장 확실한 해법이다. ② **커넥션 수명에 상한**을 둬서 주기적으로 재분배 기회를 만든다 — 커넥션이 짧게 살면 커넥션 단위 분배도 고르게 퍼진다는 원리다. ③ **클라이언트 측 로드밸런싱** — 클라이언트가 백엔드 목록을 직접 알고 여러 인스턴스에 커넥션을 나눠 맺는다(서비스 디스커버리가 필요하다).

같은 문제가 **웹소켓·SSE**(14번 문서)와 **커넥션 풀을 쓰는 내부 서비스 간 호출**(10번 문서)에서도 똑같이 생긴다고 일반화하면 원리를 아는 것으로 보인다.

### "스티키 세션은 각 계층에서 어떻게 구현하고, 각각의 함정은?"

**L4는 출발지 IP 해시뿐이다.** 근거로 쓸 수 있는 정보가 IP밖에 없기 때문이다. 함정이 둘인데, 하나는 **같은 NAT 뒤의 사용자들**(회사망, 통신사 CGNAT)이 전부 같은 IP로 보여 수천 명이 한 인스턴스로 몰린다는 것이고, 다른 하나는 **모바일에서 IP가 바뀌면 고정이 깨진다**는 것이다. 와이파이에서 LTE로 넘어가는 순간 세션이 없는 인스턴스로 배정된다.

**L7은 LB가 쿠키를 발급해 사용자 단위로 정확히 고정할 수 있다.** IP와 무관하므로 NAT 문제도 IP 변경 문제도 없다.

**다만 어느 쪽이든 스티키는 "서버에 상태가 있다"는 문제의 증상 완화일 뿐**이라고 착지시켜야 한다. 스티키에 의존하면 인스턴스 하나가 죽는 순간 거기 붙어 있던 사용자 전원이 세션을 잃고, 오토스케일로 인스턴스를 늘려도 기존 사용자는 옮겨가지 않아 부하가 안 퍼진다. **근본 해법은 세션을 Redis 같은 외부 저장소로 빼는 무상태 설계**이고, 스티키는 그리로 가기 전의 임시방편이다.

### "헬스체크 엔드포인트가 DB까지 검사하면 어떤 일이 생기나요?"

**DB의 순간 장애가 서비스 전면 장애로 증폭된다.**

메커니즘이 핵심이다. **모든 인스턴스가 같은 DB를 보고 있으므로, DB가 흔들리는 순간 전 인스턴스의 헬스체크가 동시에 실패한다.** 인스턴스별 독립 판정처럼 보이지만 실제로는 전원이 같은 신호를 보고 같은 판정을 내린다. LB는 정상 인스턴스가 0대가 되고, DB 없이도 응답할 수 있는 요청(정적 응답, 캐시 조회)까지 전부 죽는다.

**복구도 더 느리다.** DB가 2초 만에 돌아와도 헬스체크가 연속 성공 임계치를 채워야 다시 편입되고, liveness 프로브까지 DB를 검사하고 있었다면 컨테이너가 재시작되어 JVM 웜업부터 다시 한다. **DB의 2초짜리 순단이 서비스의 수십 초~수 분짜리 장애가 되는 것이다.**

**원칙은 목적별로 나누는 것이다.** liveness는 "재시작하면 나아지는가"를 묻는 것이므로 **재시작해도 안 나아지는 외부 의존성을 넣으면 안 된다.** readiness는 트래픽 수용 여부이므로 조금 더 넣을 수 있지만, 모든 인스턴스가 공유하는 의존성은 역시 신중해야 한다. 스프링 부트라면 `management.endpoint.health.group.liveness/readiness`로 검사 범위를 나누고, 쿠버네티스 프로브를 각각 연결한다.

마지막에 한 문장을 붙이면 정리가 완성된다. **"의존성 상태를 안 본다는 것이 아니라, 자동 조치의 방아쇠와 관측 지표를 분리한다는 것"** — DB 상태는 모니터링과 알림으로 보고, 헬스체크는 트래픽 배분이라는 자동 조치의 근거이므로 얕게 둔다.

### "L7 LB가 커넥션을 종단하면 백엔드는 클라이언트 IP를 어떻게 아나요?" (가산점 포인트)

**모른다 — 헤더로 전달받아야 한다.**

L7 LB는 클라이언트의 커넥션을 종단하고 백엔드로 **별도의 새 TCP 연결**을 맺으므로, 백엔드가 보는 소켓의 상대 주소는 언제나 LB의 IP다. 서블릿의 `request.getRemoteAddr()`이 전부 같은 값으로 나온다.

그래서 L7 LB는 자기가 소켓에서 관측한 클라이언트 IP를 **`X-Forwarded-For`** 헤더에 실어 전달하고, 백엔드가 그것을 읽는다. 같은 이유로 원래 스킴을 알려주는 `X-Forwarded-Proto`도 함께 붙인다.

**여기에 반드시 따라붙는 경고가 있다.** `X-Forwarded-For`는 클라이언트가 처음부터 위조해 보낼 수 있는 평범한 HTTP 헤더다. 그대로 믿으면 rate limit·IP 차단·관리자 allowlist가 헤더 한 줄로 우회된다. **신뢰할 프록시 목록을 정의하고 체인의 오른쪽부터 걷어내는 해석**이 필요하고, 최전선 프록시에서 클라이언트가 보낸 값을 반드시 덮어써야 한다(22번 문서).

**L4는 반대다.** 커넥션을 종단하지 않으므로 **목적지 주소만 바꿔 넘기는 구성이라면 백엔드의 소켓에 클라이언트 IP가 그대로 보인다** — 헤더 계약이 애초에 필요 없다. 다만 응답 경로를 LB로 되돌리려고 출발지 주소까지 바꾸는 구성(SNAT)이면 L4에서도 클라이언트 IP를 잃고, 이때는 HTTP 헤더를 쓸 수단이 없으므로 **PROXY protocol**이라는 별도 규약을 쓴다. TCP 연결이 맺어진 직후 데이터 앞에 "원래 출발지는 1.2.3.4:5678이었다"는 한 줄을 먼저 흘려보내는 방식이고, **백엔드도 그 규약을 이해하도록 설정돼 있어야 한다**(안 그러면 그 한 줄이 HTTP 요청의 일부로 파싱되어 400이 난다).

### "L4 LB를 쓰는데 좀비 서버를 걸러내고 싶습니다. 방법이 있나요?" (가산점 포인트)

**"L4 LB니까 TCP 헬스체크만 된다"는 것이 흔한 오해다.** 트래픽 분배 계층과 헬스체크 계층은 별개로 정할 수 있다.

AWS NLB는 대상 그룹의 헬스체크 프로토콜을 TCP 대신 **HTTP/HTTPS로 지정할 수 있다.** 그러면 **트래픽은 L4로 커넥션 단위 분배하면서, 헬스체크는 `/health`가 200을 주는지까지 확인**하는 조합이 된다. 백엔드에 별도의 헬스체크용 HTTP 포트를 열어두는 방식으로도 같은 효과를 낼 수 있다.

왜 이게 필요한지를 함께 말하면 좋다. **TCP 헬스체크는 커널이 handshake를 대신 완료해 주기 때문에, 애플리케이션 스레드가 전부 데드락에 빠져 있어도 통과한다.** 확인되는 것은 "커널의 리스닝 소켓이 존재하는가"까지다. 그래서 프로세스는 살아 있고 서비스는 죽어 있는 상태를 원리적으로 구분할 수 없다.

**다만 헬스체크를 L7으로 올려도 남는 문제가 있다는 것까지 말해야 정확하다.** 2-5절의 **커넥션 편중**은 헬스체크와 무관하게 그대로 남고, **버퍼링에 의한 격리**도 여전히 없다. 그리고 **TLS passthrough 구성이면 헬스체크도 HTTPS로 해야 하며, 그러려면 헬스체크 주체가 인증서를 검증할 수 있어야 한다.**

## 한 줄 요약

L4는 IP·포트만 보고 패킷을 전달하므로 TCP 연결의 두 끝이 여전히 클라이언트와 백엔드이고, 그래서 프로토콜을 안 가리고 빠르며 클라이언트 IP도 그대로 보이지만 **분배 단위가 커넥션**이라 keep-alive·gRPC·웹소켓처럼 커넥션이 오래 사는 트래픽에서 저절로 회복되지 않는 편중이 생기고 헬스체크도 "커널이 handshake를 완료하는가"까지밖에 못 본다. L7은 커넥션을 종단해 클라이언트↔LB와 LB↔백엔드 두 개의 독립적인 연결을 만들며, 이 한 가지 사실에서 요청 단위 분배와 경로·헤더·쿠키 라우팅, 앞뒤로 두 벌인 keep-alive·타임아웃·버퍼 설정, 백엔드가 보는 소켓 주소가 LB가 되어 필요해지는 `X-Forwarded-*` 계약, 그리고 느린 클라이언트로부터의 버퍼링 격리가 전부 파생된다 — 포트는 열려 있는데 500만 뱉는 좀비 서버를 걸러낼 수 있느냐가 두 계층의 차이를 가장 선명하게 보여주지만, 그 헬스체크를 DB까지 깊게 파면 이번에는 DB 순단이 전 인스턴스 동시 이탈로 증폭되므로 liveness와 readiness를 나눠 "자동 조치의 방아쇠"와 "관측 지표"를 분리하는 것까지가 완성형이다.
