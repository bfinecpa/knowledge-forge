# 취소·환불 상태 머신 — 취소는 결제의 되감기가 아니라 또 하나의 결제다

> 핵심 관전 포인트: **취소를 결제 상태에 CANCELED 하나 얹는 것으로 모델링하면 부분 취소가 등장하는 순간 붕괴한다 — 취소는 여러 번 일어날 수 있고, 취소 자체가 실패하거나 타임아웃될 수 있으며, 같은 취소 요청이 중복 도착할 수 있기 때문이다. 그래서 취소 요청 1건을 별도 엔티티 1행으로 모델링하고, 취소 엔티티에 REQUESTED → IN_PROGRESS → APPROVED/FAILED/UNKNOWN이라는 자체 상태 머신을 준다. 결제 쪽에는 잔여 취소가능금액(cancelable_amount)을 두고 조건부 UPDATE로 원자적 차감해 "취소 합계 ≤ 결제 금액" 불변식을 DB가 지키게 하며, 중복 취소 요청은 클라이언트 생성 취소요청 키의 유니크 제약으로 멱등 처리한다. 시니어 변별점은 취소 실패 시의 금액 원복 — FAILED 확정이면 원복하고 UNKNOWN이면 절대 원복하지 않는다는 구분이다.**

---

## 0. 질문 + 의도

**질문**: "결제 취소/부분 취소/환불의 상태 머신을 설계해보세요."

**출제 의도**: 취소는 결제보다 경우의 수가 많다 — 부분 취소, 중복 취소 요청, 그리고 취소 자체의 실패까지. 상태 머신으로 불가능한 전이를 차단하는 설계를 하는지, 그리고 엣지 케이스를 스스로 열거하는 능력 자체를 평가한다.

---

## 1. 왜 취소가 결제보다 어려운가

### 1-1. 출발점 — 결제 상태 머신에서 무엇을 이어받는가

이 문서는 결제 상태 머신(1번 문서)을 전제로 한다. 거기서 가져오는 개념 세 가지만 짧게 복습하고 시작하자.

**상태 머신**은 "가질 수 있는 상태의 목록"과 "어느 상태에서 어느 상태로 갈 수 있는가의 목록"으로 시스템을 서술하는 방식이다. 목록에 없는 전이는 전부 금지다.

**조건부 UPDATE**는 "기대하는 현재 값"을 WHERE 절에 넣어 UPDATE하는 기법이다. `WHERE id = 1 AND status = 'IN_PROGRESS'`처럼 쓰면, 그 사이 다른 누군가가 상태를 바꿨을 때 갱신 행 수가 0이 되어 내가 졌다는 사실을 알 수 있다.

**UNKNOWN**은 "결과를 모른다"를 담는 상태다. PG에 요청을 보냈는데 타임아웃이 나면 승인이 났는지 안 났는지 우리는 알 수 없고, 이걸 FAILED(안 됐음이 확정)로 적는 순간 이중 결제가 시작된다.

이 문서의 주제는 **같은 문제가 취소 쪽에서 훨씬 나쁜 형태로 반복된다**는 것이다. 결제의 UNKNOWN을 잘못 다루면 고객이 두 번 결제하고, 취소의 UNKNOWN을 잘못 다루면 **회사가 두 번 환불한다.**

### 1-2. 경우의 수를 먼저 열거해본다

결제는 "1건이 성공하거나 실패하거나"다. 취소는 다르다. 무엇이 다른지 먼저 전부 나열해보자. 설계는 그 다음이다.

**부분 취소가 N번 온다.** 100,000원 결제에서 옵션 반품으로 30,000원을 취소하고, 다음 주에 또 20,000원을 추가로 취소한다. 즉 취소는 결제 1건에 대해 **여러 건**이다. "결제 1 : 취소 N" 관계라는 것 하나만으로도 이미 결제 테이블의 컬럼 하나로는 감당이 안 된다는 게 드러난다.

**취소 자체가 실패한다.** PG 취소 API도 타임아웃이 나고 거절당한다. 이미 정산이 마감돼서 승인 취소가 불가능한 경우, 카드사 시스템 점검, 단순 5xx 등이 있다. 즉 **"취소의 UNKNOWN"** 이 존재한다. 취소를 걸었는데 그게 됐는지 안 됐는지 모르는 상태다.

**중복 취소 요청이 온다.** CS 담당자가 어드민에서 버튼을 두 번 누르거나, 고객 앱이 응답이 느려 재시도한다. 30,000원 취소가 두 번 실행되면 60,000원이 환불된다.

**불가능한 요청이 온다.** 이미 전액 취소된 결제에 또 부분 취소 요청이 오거나, 잔여 금액이 70,000원인데 80,000원 취소 요청이 오거나, 아직 승인도 안 난 결제에 취소 요청이 온다.

### 1-3. 왜 `payment.status`에 값을 더하는 방식으로는 안 되는가

이 조합을 결제 상태 컬럼에 CANCELED, PARTIAL_CANCELED 같은 값을 추가하는 것만으로 감당하려 하면 즉시 막힌다. 구체적으로 어디서 막히는지 보자.

100,000원 결제에서 30,000원을 취소했다고 하자. `payment.status = 'PARTIAL_CANCELED'`로 바꿨다. 이제 다음 질문들에 답해보라.

| 질문 | 상태 컬럼 하나로 답할 수 있나 |
|---|---|
| 얼마가 취소됐나? | 아니다. `PARTIAL_CANCELED`는 금액을 모른다 |
| 몇 번에 걸쳐 취소됐나? | 아니다 |
| 각 취소의 사유는? | 아니다 |
| 지금 진행 중인 취소가 있나? | 아니다. 결제 상태는 "확정된 결과"만 담는다 |
| 방금 그 취소가 타임아웃 났는데 어디에 적나? | 적을 곳이 없다 |

마지막 두 줄이 결정적이다. 결제 상태 컬럼은 값이 하나뿐이라 **"확정된 결과"밖에 담지 못한다.** 그런데 취소는 진행 중인 것, 실패한 것, 결과를 모르는 것이 **동시에 여러 개 존재할 수 있다.** 값 하나로 여러 개를 표현할 방법은 없다.

결론은 이렇다. 표현해야 할 대상이 여러 개면 행도 여러 개여야 한다.

### 1-4. 비유 — 영수증에 줄을 긋지 말고 반품 전표를 끊어라

매장에서 반품을 받을 때 원래 영수증에 볼펜으로 줄을 긋는 가게는 없다. **반품 전표를 새로 끊는다** — 언제, 얼마를, 왜 돌려줬는지가 적힌 별도 문서다.

부분 반품이면 전표가 여러 장 쌓이고, 원 영수증 금액에서 전표 합계를 빼면 잔여 금액이 나온다. 반품이 실패해도 원 영수증은 멀쩡하다. 전표 한 장이 잘못됐을 뿐이다.

취소 엔티티 분리는 정확히 이 구조다. **원 결제는 불변의 사실로 남기고, 취소는 각각 독립된 기록으로 쌓는다.**

## 2. 설계 — 취소 엔티티, 잔액 불변식, 멱등성

### 2-1. 취소 요청 1건 = 1행, 자체 상태 머신을 가진다

```sql
-- PostgreSQL
CREATE TABLE payment_cancellation (
    id                 bigserial PRIMARY KEY,
    payment_id         bigint      NOT NULL REFERENCES payment(id),
    cancel_request_id  varchar(64) NOT NULL,  -- 멱등 키 (2-5에서 설명)
    -- 금액은 절대 float/double로 두지 않는다. 0.1+0.2가 0.3이 안 되는
    -- 부동소수점 오차가 돈에 섞이면 대사가 영원히 안 맞는다.
    amount             numeric(12) NOT NULL CHECK (amount > 0),
    reason             text        NOT NULL,
    status             varchar(20) NOT NULL,  -- REQUESTED/IN_PROGRESS
                                              -- /APPROVED/FAILED/UNKNOWN
    requested_by       varchar(50) NOT NULL,  -- 'user:1042', 'admin:kim'
    created_at         timestamptz NOT NULL DEFAULT now(),
    UNIQUE (cancel_request_id)                -- 중복 요청 차단 (2-5)
);
```

취소의 상태 머신은 결제의 축소판이다.

```
REQUESTED ──> IN_PROGRESS ──> APPROVED
                   ├────────> FAILED
                   └────────> UNKNOWN ──> APPROVED / FAILED
```

| 상태 | 뜻 | 금액은 어떻게 되나 |
|---|---|---|
| `REQUESTED` | 취소 요청을 접수만 함 | 아직 아무 일 없음 |
| `IN_PROGRESS` | PG 취소 API를 부른 중 | 잔여 금액에서 **선점(차감)** 된 상태 |
| `APPROVED` | 취소 성공 확정 | 차감 확정 |
| `FAILED` | 취소 실패 **확정** | 차감을 **원복** |
| `UNKNOWN` | 취소가 됐는지 모름 | 차감된 채 **동결** |

맨 오른쪽 열이 이 문서에서 가장 중요한 부분이고, 2-4에서 자세히 다룬다.

### 2-2. 원본과 파생 — 결제 상태는 취소 행들의 집계 결과다

취소를 별도 테이블로 뺐으면, 결제 쪽 상태(`CANCELED` / `PARTIAL_CANCELED`)는 어디서 오는가?

여기서 **원본(source of truth)** 과 **파생값(derived value)** 이라는 구분이 필요하다. 원본은 "사실이 기록된 유일한 자리"이고, 파생값은 "원본에서 계산해 낸 편의용 값"이다. 캐시와 비슷한 개념인데, 중요한 건 **틀렸을 때 누가 맞는지가 미리 정해져 있다**는 점이다.

이 설계에서 방향은 이렇다.

- **원본** = `payment_cancellation` 테이블의 행들
- **파생** = `payment.status`의 취소 관련 값

계산 규칙은 단순하다.

| 승인된 취소 금액의 합계 | 결제 상태 |
|---|---|
| 0 | `APPROVED` (취소 없음) |
| 0 < 합계 < 결제 금액 | `PARTIAL_CANCELED` |
| 합계 = 결제 금액 | `CANCELED` |

```sql
-- 파생 상태를 원본에서 재계산하는 쿼리. 상태가 꼬였을 때의 복구 수단이다.
SELECT COALESCE(SUM(amount), 0)
  FROM payment_cancellation
 WHERE payment_id = 4211
   AND status = 'APPROVED';   -- 확정된 취소만 센다. IN_PROGRESS는 제외
```

이렇게 방향을 정해두면 얻는 게 하나 있다. **상태가 꼬여도 복구가 가능하다.** 결제 상태가 이상하면 취소 행들을 다시 집계해서 덮어쓰면 된다. 어느 쪽이 맞는지 고민할 필요가 없다 — 항상 원본이 맞다.

반대로 원본과 파생을 구분하지 않고 양쪽을 각각 갱신하는 설계는, 둘이 어긋났을 때 **어느 쪽을 믿어야 할지 결정할 근거가 없다.** 이게 진짜 위험한 설계다.

### 2-3. 잔여 취소가능금액 — 검사가 아니라 원자적 차감

"취소 합계가 결제 금액을 넘으면 안 된다"는 규칙을 어떻게 지킬 것인가. 이게 설계의 심장이다.

#### 전제 지식 — check-then-act가 왜 뚫리는가

가장 자연스러운 구현은 "먼저 검사하고, 통과하면 실행한다"이다. 영어로 **check-then-act(검사 후 행동)** 라고 부르는 패턴이다.

```java
// Before: check-then-act — 동시 취소 요청 두 건에 뚫린다
@Transactional
public void cancel(long paymentId, long amount, String reason) {
    Payment p = paymentRepository.findById(paymentId);
    long canceled = cancellationRepository
            .sumApprovedAmount(paymentId);          // ① 합계 조회
    if (canceled + amount > p.getAmount()) {        // ② 검사
        throw new ExceedsCancelableAmountException();
    }
    pgClient.cancel(p.getPgTransactionId(), amount); // ③ PG 취소
    cancellationRepository.save(/* APPROVED 행 */);  // ④ 기록
}
```

이 코드가 왜 뚫리는지 시간축으로 보자. 100,000원 결제에서 이미 30,000원이 취소돼 잔여가 70,000원인데, 70,000원 취소 요청이 동시에 두 건 들어왔다.

```
시각   [요청 A]                          [요청 B]
 t1    ① 합계 조회 → 30,000
 t2                                      ① 합계 조회 → 30,000
 t3    ② 30,000+70,000 <= 100,000 → 통과
 t4                                      ② 30,000+70,000 <= 100,000 → 통과
 t5    ③ PG 취소 70,000  (성공)
 t6                                      ③ PG 취소 70,000  (성공)
 t7    ④ 취소 행 INSERT
 t8                                      ④ 취소 행 INSERT
                                         → 총 140,000원 환불
```

두 요청 모두 검사를 통과했다. 각자가 조회한 시점에는 정말로 잔여가 70,000원이었기 때문이다. **검사와 행동 사이에 시간이 있다는 것 자체가 취약점**이다. 이 시간 동안 세상이 바뀌었는데 검사 결과는 그대로 들고 있다.

이 코드에는 문제가 하나 더 있다. **PG 호출(③)이 DB 트랜잭션 안에 있다.** PG 취소는 수 초가 걸릴 수 있는데, 그동안 이 트랜잭션은 DB 커넥션과 행 락을 쥔 채 멈춰 있다. 타임아웃이라도 나면 긴 트랜잭션과 결과 불명이 한꺼번에 겹친다.

#### 해법 — 검사를 없애고 차감으로 바꾼다

핵심 아이디어는 이것이다. **"검사한 뒤 실행한다"를 "실행 조건을 SQL에 넣어 한 번에 실행한다"로 바꾼다.**

이를 위해 결제 행에 `cancelable_amount`(잔여 취소가능금액) 컬럼을 둔다. 승인 시점에 결제 금액과 같은 값으로 시작해서, 취소가 일어날 때마다 줄어드는 카운터다.

여기서 **원자적(atomic)** 이라는 말의 뜻을 짚고 가자. 원자적 연산이란 "쪼개서 관찰될 수 없는 연산"이다. `UPDATE ... SET x = x - 30000 WHERE x >= 30000`은 DB가 그 행에 락을 걸고 읽기·비교·쓰기를 한 덩어리로 처리하므로, 중간에 다른 트랜잭션이 끼어들 틈이 없다. 앞의 check-then-act에 있던 t1~t5 사이의 틈이 **구조적으로 사라진다.**

```java
// After: 잔여 금액을 조건부 UPDATE로 선점한 뒤 PG를 부른다
public CancelResult cancel(long paymentId, long amount,
                           String cancelRequestId, String reason) {
    // ① 짧은 트랜잭션 하나로 "선점"을 끝낸다.
    //    잔여 금액 차감 + 취소 행 INSERT가 함께 커밋되거나 함께 롤백된다.
    //    PG 호출은 여기 들어오지 않는다.
    Cancellation c = txTemplate.execute(tx -> {
        int updated = jdbc.update("""
            UPDATE payment
               SET cancelable_amount = cancelable_amount - ?
             WHERE id = ?
               AND status IN ('APPROVED', 'PARTIAL_CANCELED')
               AND cancelable_amount >= ?
            """, amount, paymentId, amount);
        // 0건이 나오는 경우는 두 가지다.
        //  (a) 잔여 금액이 부족하다 (동시 요청에 밀렸거나 애초에 초과 요청)
        //  (b) 결제가 취소 가능한 상태가 아니다 (READY/FAILED/전액취소 완료)
        // 어느 쪽이든 "이 취소는 진행할 수 없다"이므로 여기서 끝낸다.
        if (updated == 0) {
            throw new ExceedsCancelableAmountException();
        }
        // 중복 cancel_request_id면 유니크 제약에 걸려
        // DuplicateKeyException이 나고, 위 차감도 함께 롤백된다.
        return cancellationRepository
                .insert(paymentId, cancelRequestId, amount,
                        reason, Status.IN_PROGRESS);
    });

    // ② 트랜잭션 밖에서 PG 취소 호출.
    //    수 초가 걸릴 수 있는 외부 호출을 트랜잭션에 넣지 않는다.
    try {
        pgClient.cancel(c.pgTransactionId(), amount, cancelRequestId);
        cancellationRepository.markApproved(c.id());
    } catch (PgDeclinedException e) {
        // PG가 "이 취소는 안 됐다"고 명시적으로 답한 경우.
        // 안 나간 게 확실하므로 선점했던 금액을 되돌려준다.
        cancellationRepository.markFailed(c.id(), e.getCode());
        restoreCancelableAmount(paymentId, amount);
    } catch (PgTimeoutException e) {
        // 결과 불명. 환불이 나갔을 수도 있으므로 절대 원복하지 않는다.
        // 금액은 차감된 채 두고, 해소는 배치에 맡긴다. (2-4)
        cancellationRepository.markUnknown(c.id());
    }
    recalculatePaymentStatus(paymentId);  // 파생 상태 재계산 (2-2)
    return CancelResult.of(c);
}
```

설계 포인트를 하나씩 풀어보자.

**불변식의 집행자는 DB다.** `cancelable_amount >= ?` 조건이 붙은 UPDATE는 원자적이므로, 동시 취소 두 건 중 한 건은 반드시 0건 갱신으로 실패한다. 애플리케이션이 아무리 여러 대여도, 스레드가 아무리 많아도 이 사실은 변하지 않는다. 보험으로 `CHECK (cancelable_amount >= 0)` 제약을 걸어두면 어떤 경로로도(어드민 스크립트, 마이그레이션 등) 음수가 될 수 없다.

**선점 후 호출.** 금액을 먼저 차감(선점)하고 나서 PG를 부른다. 순서를 뒤집어 PG를 먼저 부르면, "PG에서는 취소가 됐는데 우리 DB에는 아무 기록이 없는" 구간이 생긴다. 그 구간에서 서버가 죽으면 그 취소는 영원히 미아가 된다.

**PG 호출은 트랜잭션 밖.** 외부 API를 DB 트랜잭션 안에서 부르면 타임아웃 동안 커넥션과 락을 쥔 채 멈춘다. 취소 요청이 몰리는 상황(이벤트 전체 환불 등)에서는 이것 하나로 커넥션 풀이 말라 서비스 전체가 죽는다.

### 2-4. 취소 실패의 두 얼굴 — FAILED는 원복, UNKNOWN은 동결

위 코드에서 가장 중요한 분기가 catch 두 개의 차이다. 둘 다 "취소가 성공하지 못했다"인데 처리가 정반대다.

| | FAILED (거절 확정) | UNKNOWN (타임아웃) |
|---|---|---|
| PG가 한 말 | "이 취소는 안 됐다" | (아무 말도 못 들음) |
| 실제로 환불이 나갔나 | 확실히 안 나갔다 | **나갔을 수도 있다** |
| `cancelable_amount` | **원복한다** | **동결한다 (그대로 둔다)** |
| 고객에게 보여줄 문구 | "취소 실패, 다시 시도해주세요" | "취소 확인 중입니다" |
| 다음에 할 일 | 없음 (고객이 재시도 가능) | 배치가 PG에 조회해 해소 |

왜 UNKNOWN에서 원복하면 안 되는지를 시나리오로 보자. 30,000원 취소가 타임아웃 났고, 우리가 잔여 금액을 원복했다고 하자.

```
t1  고객: 30,000원 취소 요청
t2  우리: cancelable_amount 70,000 → 40,000 차감, PG 호출
t3  PG:  취소 성공 (환불 30,000원 나감)  ← 우리는 이걸 모른다
t4  우리: 응답 타임아웃 → cancelable_amount 40,000 → 70,000 원복  (실수)
t5  고객: "취소 실패"를 보고 다시 30,000원 취소 요청
t6  우리: 잔여 70,000 >= 30,000 이므로 통과 → PG 호출
t7  PG:  취소 성공 (환불 30,000원 또 나감)
    → 총 60,000원 환불. 회사가 30,000원 손해
```

t4의 원복이 t6의 통과를 만들었다. **원복은 "다시 취소해도 된다"는 허가증**이고, 첫 취소가 사실 성공이었다면 그 허가증이 곧 이중 환불이 된다.

올바른 처리는 **동결**이다. 금액은 차감된 채로 두고 취소 행만 UNKNOWN으로 표시한다. 그러면 t6에서 잔여가 40,000원이므로 30,000원 요청은 통과하겠지만... 여기서 한 걸음 더 필요하다. 애초에 고객 화면에 "취소 실패"가 아니라 "취소 확인 중"이 떠야 하고, 같은 취소 요청 키로 재시도하면 2-5의 멱등 처리가 "처리 중"으로 막아준다.

그리고 UNKNOWN은 영원히 UNKNOWN으로 두면 안 된다. 배치가 PG 취소 조회 API로 실제 결과를 확인해서 해소한다.

- 조회 결과 **취소 성공** → 취소 행을 APPROVED로. 동결된 차감이 그대로 확정된다.
- 조회 결과 **취소 안 됨** → 취소 행을 FAILED로. **이때 비로소 원복**한다.

즉 원복은 사라지는 게 아니라 **"확인된 뒤로 미뤄지는" 것**이다.

### 2-5. 중복 취소 요청의 멱등 처리

#### 멱등성이 무엇인가

**멱등성(idempotency)** 은 "같은 요청을 몇 번 보내도 결과가 한 번 보낸 것과 같은 성질"이다. 수학에서 f(f(x)) = f(x)인 함수를 멱등이라고 부르는 데서 온 말이다.

왜 필요한가. 네트워크가 있는 세상에서는 **클라이언트가 재시도를 멈출 방법이 없기 때문**이다. 응답을 못 받은 클라이언트는 요청이 서버에 도달했는지 아닌지 알 수 없고, 도달했을 수도 있다는 이유로 재시도를 포기하면 진짜 유실됐을 때 손해가 난다. 그래서 클라이언트는 재시도하게 되어 있고, **중복을 걸러내는 책임은 서버에 있다.**

#### 어떻게 구현하나

취소 요청에도 결제와 동일한 멱등성 키 패턴을 쓴다.

1. **클라이언트(또는 어드민 화면)가 "취소 시도 1건"마다 `cancelRequestId`를 생성한다.** 서버가 만들면 안 된다 — 서버가 만들면 요청이 두 번 오면 키도 두 개가 되어 아무것도 못 막는다. UUID 같은 걸 클라이언트가 만들어 보내고, 재시도할 때는 **같은 값**을 다시 보낸다.
2. **`payment_cancellation.cancel_request_id`에 UNIQUE 제약을 건다.** 여기가 실제 방어선이다. 애플리케이션이 여러 대로 떠 있어도, 동시에 두 요청이 들어와도, DB의 유니크 인덱스는 둘 중 하나만 INSERT를 통과시킨다.
3. **중복 키로 들어온 요청은 기존 행을 조회해서 그 결과를 재생한다.**

```java
try {
    return doCancel(paymentId, amount, cancelRequestId, reason);
} catch (DuplicateKeyException e) {
    // 같은 취소 요청이 이미 접수돼 있다. 새로 처리하지 않고
    // 기존 행의 현재 상태에 맞는 응답을 돌려준다.
    Cancellation prev = cancellationRepository
            .findByRequestId(cancelRequestId);
    return switch (prev.status()) {
        // 이미 끝난 건 — 첫 요청과 똑같은 응답을 재생한다.
        // 클라이언트 입장에선 "한 번만 처리된" 것처럼 보인다.
        case APPROVED, FAILED -> CancelResult.of(prev);
        // 아직 진행 중이거나 결과 불명 — 결과를 지어내면 안 된다.
        // 409로 "처리 중"을 알리고 클라이언트가 나중에 조회하게 한다.
        case IN_PROGRESS, UNKNOWN -> throw new CancelInProgressException();
        default -> throw new IllegalStateException();
    };
}
```

#### 멱등성은 한 구간만으로 부족하다

여기서 끝이 아니다. 지금까지 막은 것은 **클라이언트 → 우리 서버** 구간의 중복이다. 그런데 **우리 서버 → PG** 구간에도 같은 문제가 있다.

우리 서버가 PG 취소를 부르다 타임아웃이 나서 재시도하면, PG 입장에서는 취소 요청이 두 번 온 것이다. 그래서 PG 취소 API에도 같은 키(또는 PG가 제공하는 취소 멱등 장치)를 전달해서 PG가 중복을 걸러내게 해야 한다.

```
[클라이언트] ──cancelRequestId──> [우리 서버] ──같은 키──> [PG]
              1구간: UNIQUE 제약        2구간: PG의 멱등 처리
```

**멱등성은 호출 체인 전 구간에서 각각 보장돼야 한다.** 한 구간만 막으면 나머지 구간에서 중복이 새어 나간다.

### 2-6. 취소 가능 조건은 상태 머신 + 도메인 규칙 이중으로

취소 요청을 받으면 "이 취소가 가능한가"를 판단해야 한다. 이 판단은 두 층으로 나뉜다.

**1차 — 상태 머신이 막는 것.** 2-3의 조건부 UPDATE에 있던 `status IN ('APPROVED', 'PARTIAL_CANCELED')`가 이미 많은 것을 차단한다.

| 결제 상태 | 결과 | 이유 |
|---|---|---|
| `READY` | 0건 → 거부 | 아직 승인도 안 됐다 |
| `FAILED` | 0건 → 거부 | 애초에 돈이 안 나갔다 |
| `CANCELED` | 0건 → 거부 | 이미 전액 취소됐다 |
| `APPROVED` / `PARTIAL_CANCELED` | 통과 | 취소 가능 |

여기서 눈여겨볼 게 하나 있다. **"전액 취소 후 부분 취소 불가"를 별도 if문으로 짜지 않았다.** 전액 취소되면 상태가 `CANCELED`가 되고 `cancelable_amount`도 0이 되므로, 조건 두 개가 자동으로 막는다. 상태 머신을 제대로 세우면 이렇게 규칙이 **저절로 따라오는** 경우가 많다.

**2차 — 도메인 정책이 막는 것.** 상태 머신으로 표현되지 않는, 업무 규칙 층의 조건들이다.

- **정산 마감 후**: 승인 취소가 불가능하므로 PG 취소가 아니라 별도 환불 이체 흐름으로 전환해야 한다.
- **이용권을 이미 소진**: 취소 불가로 막거나, 소진분을 차감한 나머지만 부분 취소한다.
- **프로모션 결제**: 할인이 여러 상품에 배분돼 있으면 배분을 역산해야 취소 금액이 나온다.

이 둘을 계층으로 나눠 답하는 게 좋다. **"상태 머신이 1차, 도메인 정책이 2차"** — 1차는 데이터 정합성을 지키고, 2차는 사업 규칙을 지킨다. 1차를 도메인 정책으로 대신하려 들면(예: if문으로 잔액 검사) 2-3에서 본 check-then-act 함정에 빠진다.

## 3. 실무 사례 — 취소 설계가 뚫리는 구멍들

### 사례 1: 어드민 더블 클릭으로 이중 환불

CS 담당자가 어드민에서 30,000원 취소 버튼을 눌렀는데 화면이 3초간 멈추자 한 번 더 눌렀다.

취소요청 멱등 키가 없어서 서버는 두 요청을 완전히 독립적인 취소로 처리했다. 원 결제 60,000원에서 30,000원 취소 두 건이 모두 성공했고, 고객에게 60,000원 전액이 환불됐다. 이용권은 절반만 회수됐다.

여기서 짚어야 할 점은 **잔여 검사 코드가 있었다**는 것이다. 개발자는 "합계가 결제 금액을 넘으면 예외"를 분명히 짰다. 그런데 그게 2-3의 check-then-act 형태라 동시 요청을 막지 못했다. 두 요청이 각각 "지금까지 취소 0원 + 이번 30,000원 = 30,000원 ≤ 60,000원"으로 계산해 둘 다 통과한 것이다.

교훈은 두 가지다.

**어드민도 클라이언트다.** 내부 도구라서, 쓰는 사람이 몇 명 안 되니까 괜찮다는 생각이 사고를 만든다. 사람이 두 번 누르는 것과 앱이 재시도하는 것은 서버 입장에서 구분되지 않는다. 취소 버튼을 누르는 순간 `cancelRequestId`를 발급해야 한다.

**검사는 방어선이 아니다.** 유니크 제약과 조건부 차감이 최종 방어선이어야 하고, 애플리케이션 검사는 좋은 에러 메시지를 주기 위한 앞단일 뿐이다.

### 사례 2: 취소 타임아웃을 실패로 간주해 이중 환불

취소 API 타임아웃을 FAILED로 기록하고 `cancelable_amount`를 즉시 원복하는 코드였다. 2-4에서 본 실수를 그대로 저지른 것이다.

고객 화면에 "취소 실패, 다시 시도해주세요"가 떴고 고객이 재시도해 두 번째 취소가 성공했다. 그런데 첫 취소도 PG에서는 성공해 있었다 — **45,000원 결제에 45,000원 환불이 두 번** 나갔다.

여기서 "PG가 막아줬어야 하는 것 아닌가"라는 의문이 자연스럽게 든다. PG에도 잔액 검사가 있으니, 첫 취소로 잔액이 0이 됐다면 두 번째는 거절됐어야 한다. 실제로는 거절되지 않았는데, 이유가 중요하다.

**우리가 보낸 취소 요청 식별자가 매번 달랐다.** 그래서 PG는 두 요청을 별개의 취소 건으로 접수했다. 그리고 이 결제는 부분취소가 가능한 건이라 PG의 검증은 "요청 금액이 남은 금액 이하인가" 수준의 금액 단위 검증만 했고, 그 시점에는 아직 첫 취소의 정산 반영이 끝나기 전이라 통과해버렸다.

교훈: **취소의 타임아웃은 UNKNOWN이며 금액 동결이 원칙이다.** 그리고 이 사고는 코드만이 아니라 화면 문구까지 함께 고쳐야 한다 — "취소 실패"는 고객에게 재시도를 시키는 문구다. "취소 확인 중"이어야 한다. 상태 설계의 정확성은 UI 문구까지 내려와야 완결된다.

### 사례 3: 파생 상태 재계산 누락으로 전액 취소 건이 부분 취소로 남음

취소 행은 APPROVED로 잘 쌓였는데, 결제 상태 재계산(`recalculatePaymentStatus`)이 특정 예외 경로에서 빠졌다.

100,000원 결제가 60,000원 + 40,000원 취소로 전액 환불됐는데 결제 상태는 `PARTIAL_CANCELED`로 남았다. 월말 정산 대사 배치가 "우리 장부상 잔여 0원인데 상태는 부분취소"인 건 200여 건을 찾아냈다.

**돈은 새지 않았다.** 취소 행이 원본이고 그건 정확했기 때문이다. 그런데 2차 피해가 있었다 — 부분취소 상태를 조건으로 도는 CS 자동화가 이 건들에 "잔여 금액에 대한 안내" 메일을 보냈다. 이미 전액 환불받은 고객 200명이 이상한 메일을 받은 것이다.

교훈은 두 가지다.

**파생 상태는 반드시 원본에서 재계산 가능해야 한다.** 이 사고에서 복구는 재집계 쿼리 한 번으로 끝났다(2-2의 SELECT를 돌려 상태를 다시 써주면 된다). 원본-파생 구조를 지켰기 때문에 가능했던 일이다. 만약 취소 정보가 결제 상태 컬럼에만 있었다면 복구할 근거 자체가 없었다.

**대사 배치에 정합성 검증 항목을 넣어 자동 탐지한다.** "승인 취소 합계 vs 결제 상태"가 맞는지 정기적으로 확인하는 쿼리를 두면, 다음번에는 월말이 아니라 다음 날 아침에 발견된다.

## 4. 꼬리질문 대비 포인트

### "취소가 UNKNOWN일 때 취소가능금액을 원복하나요?" (시니어 변별 포인트)

절대 원복하지 않는다.

UNKNOWN은 "PG에서 환불이 나갔을 수 있다"는 뜻이다. 원복한다는 것은 곧 "같은 금액의 취소가 한 번 더 통과할 수 있는 창을 연다"는 뜻이고, 첫 취소가 사실 성공이었다면 그 창으로 이중 환불이 나간다. 2-4의 t4~t7 시나리오가 정확히 그 경로다.

올바른 처리는 **동결**이다. 금액은 차감된 채 두고 취소 행만 UNKNOWN으로 표시한다. 그 뒤 배치가 PG 취소 조회 API로 결과를 확인해 APPROVED(동결 확정) 또는 FAILED(그때 원복)로 해소한다.

여기서 원칙 하나를 뽑아 말하면 변별력이 생긴다. **"돈 문제에서 결과 불명은 항상 돈이 나간 쪽으로 보수적으로 취급한다."** 결제의 UNKNOWN에서는 "승인이 났을 수 있다"고 보고 재시도를 막았고, 취소의 UNKNOWN에서는 "환불이 나갔을 수 있다"고 보고 재취소를 막는다. 방향은 같다 — 모를 때는 **돈이 이미 움직였다고 가정**한다.

### "취소를 별도 엔티티로 빼면 결제 상태와 어긋날 수 있지 않나요?"

어긋날 수 있다. 사례 3이 실제로 그랬다.

그래서 **방향을 미리 정한다** — 취소 행이 원본(source of truth)이고, 결제의 `CANCELED`/`PARTIAL_CANCELED`는 파생값이다. 이 방향이 정해져 있으면 어긋났을 때 할 일이 명확하다. 원본에서 다시 계산해 파생을 덮어쓴다. 고민할 게 없다.

운영에서는 두 겹으로 관리한다. 파생값은 취소가 확정될 때마다 재계산하고, 그래도 생기는 어긋남은 대사 배치가 "승인 취소 합계 vs 결제 상태" 검증으로 잡아 재계산으로 복구한다.

**원본과 파생을 구분하지 않고 양쪽을 각각 갱신하는 설계가 진짜 위험한 설계다.** 어긋났을 때 어느 쪽이 맞는지 판단할 근거가 없어서, 결국 사람이 건별로 PG 내역을 열어보며 손으로 맞춰야 한다.

### "부분 취소의 합계 제약을 DB CHECK만으로 걸 수는 없나요?"

걸 수 없다. `CHECK` 제약은 **단일 행 안의 조건만** 검사할 수 있기 때문이다. `CHECK (amount > 0)`처럼 그 행의 컬럼들만 보는 조건은 되지만, "이 payment_id를 가진 다른 행들의 amount 합계"처럼 **다른 행을 봐야 하는 조건**은 표현할 수 없다.

이걸 **행 간 불변식(cross-row invariant)** 이라고 부른다. 여러 행에 걸쳐 성립해야 하는 규칙이고, 표준 SQL의 제약 문법으로는 직접 표현할 방법이 없다.

그래서 우리가 쓴 기법이 이것이다 — **행 간 불변식을 단일 행 갱신의 원자성 문제로 바꾼다.** 결제 행에 `cancelable_amount`라는 잔여 카운터를 하나 두면, "여러 취소 행의 합계 ≤ 결제 금액"이라는 행 간 규칙이 "이 한 행의 카운터가 음수가 되지 않는다"는 단일 행 규칙으로 번역된다. 단일 행 규칙은 조건부 UPDATE의 원자성으로 완벽하게 지킬 수 있다.

방어는 세 겹이다.

1. 조건부 UPDATE의 `cancelable_amount >= ?` — 실시간 집행
2. `CHECK (cancelable_amount >= 0)` — 모든 경로에 대한 최후 보험
3. 대사 배치의 `SUM(amount)` 재검증 — 사후 탐지

### "환불과 취소는 뭐가 다른가요?"

말로는 섞어 쓰지만 실제 처리 경로가 다르다.

**승인 취소(cancel)** 는 카드 승인 자체를 무효화하는 것이다. 보통 매입·정산 **전에** 가능하고, 고객에게는 승인 내역이 사라지는 형태로 반영된다. 카드 명세서에 애초에 안 찍히거나, 승인과 취소가 나란히 찍혔다가 상계된다. 처리가 빠르다.

**환불(refund)** 은 이미 매입·정산이 끝난 거래의 돈을 **역방향 이체**로 돌려주는 것이다. 이미 우리 계좌로 들어온 돈을 다시 내보내는 것이므로 별도 정산 주기를 타고, 고객 계좌에 들어오기까지 며칠 걸릴 수 있다.

상태 머신 관점에서는 같은 골격(요청/진행/확정/실패/불명)을 쓴다. 다만 두 가지가 추가된다.

- 환불에는 **"이체 완료"라는 비동기 확정 신호를 기다리는 상태**가 하나 더 붙는다. 취소는 API 응답으로 끝나지만 환불은 며칠 뒤 이체 결과가 별도로 온다.
- **정산 마감 시각을 기준으로 취소 경로에서 환불 경로로 자동 전환하는 분기**가 필요하다. 같은 "취소해주세요" 요청이라도 마감 전이면 승인 취소, 마감 후면 환불 이체로 갈라진다.

### "취소 요청이 몰리면(이벤트 종료 직후 등) 이 설계의 병목은 어디인가요?"

먼저 병목처럼 보이지만 병목이 아닌 것부터. `UPDATE payment SET cancelable_amount = ...`는 결제 행 단위로 행 락을 잡는다. 그래서 **같은 결제**에 대한 동시 취소는 줄을 서서 처리된다(직렬화된다).

이건 문제가 아니라 **의도된 동작**이다. 애초에 같은 결제의 잔여 금액을 두 요청이 동시에 만지면 안 되니까 직렬화하는 것이다. 그리고 서로 다른 결제끼리는 다른 행이라 아무 경합이 없으므로, 결제 건수가 늘어나는 방향으로는 얼마든지 확장된다.

**진짜 병목은 PG 취소 API의 응답 시간과 호출량 제한이다.** PG는 초당 호출 수를 제한하고, 취소 API는 보통 승인 API보다 느리다. 이벤트 전체 환불처럼 수만 건을 한꺼번에 취소해야 하는 상황에서 동기 API 호출을 반복하면, 우리 스레드가 PG 응답을 기다리며 전부 묶인다.

그래서 대량 취소는 구조를 바꾼다.

```
[대량 취소 요청]
      │
      ▼
취소 행을 REQUESTED로 대량 INSERT   ← 여기까지가 동기. 즉시 응답.
      │
      ▼
[워커] REQUESTED 행을 꺼내 PG 호출량 제한에 맞춰 소비
      │  (초당 N건씩, 실패 시 재시도, UNKNOWN은 조회 배치로)
      ▼
취소 행을 APPROVED/FAILED/UNKNOWN으로 갱신
```

취소 요청을 받는 것과 PG를 부르는 것을 분리하면, 우리 API의 응답 속도가 PG의 처리 속도에 묶이지 않는다. 이미 취소를 별도 엔티티로 만들어뒀기 때문에 이 전환이 자연스럽다는 점도 짚으면 좋다 — **취소 행이 곧 큐의 항목**이 된다.

## 한 줄 요약

취소는 결제 1건에 여러 번, 그것도 실패·타임아웃·중복 요청을 동반하며 일어나므로 **취소 요청 1건 = 별도 엔티티 1행**으로 모델링해 자체 상태 머신(REQUESTED→IN_PROGRESS→APPROVED/FAILED/UNKNOWN)을 주고, 잔여 취소가능금액을 조건부 UPDATE로 원자적으로 선점·차감해 합계 불변식을 DB가 지키게 하며, 취소요청 키 유니크로 중복을 멱등 처리한다 — 그리고 취소의 UNKNOWN에서 금액을 원복하지 않는 것이 이중 환불을 막는 마지막 선이다.
