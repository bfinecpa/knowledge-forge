# 비동기 승인 결제 수단 — 가상계좌의 "완료"는 응답이 아니라 웹훅으로 온다

> 핵심 관전 포인트: **카드 결제는 요청-응답 한 사이클 안에 승인이 확정되는 동기 모델이지만, 가상계좌·계좌이체·후불 결제는 "결제 요청 성공"과 "돈이 실제로 들어옴" 사이가 몇 시간에서 며칠까지 벌어지는 비동기 모델이다. 그래서 상태 머신에 입금 대기(WAITING_DEPOSIT)와 기한 만료(EXPIRED)라는 새 상태가 필수로 추가되고, 승인의 유일한 완료 신호가 API 응답이 아니라 PG의 입금 통보 웹훅이 된다 — 웹훅은 중복되고, 유실되고, 만료 배치와 경합하므로 멱등 처리·조회 API 보완 대사·조건부 UPDATE가 설계의 중심이 된다. 여기에 금액 불일치 입금, 기한 후 입금, 부분 입금이라는 카드에는 없던 케이스와 "입금 대기 중 재고를 선점할 것인가"라는 주문 도메인과의 결합 문제까지 답할 수 있어야 한다.**

---

## 0. 질문 + 의도

**질문**: "가상계좌처럼 승인이 비동기로 완료되는 결제 수단은 상태 설계가 어떻게 달라지나요?"

**출제 의도**: "결제 = 즉시 승인"이라는 카드 중심 모델이 깨지는 지점이다. 입금 대기, 기한 만료, 금액 불일치 입금이라는 새로운 상태들을 기존 상태 머신에 수용할 수 있는지 본다.

---

## 1. 무엇이 다른가 — 동기 승인과 비동기 승인

### 1-1. 카드: 요청-응답 안에 승인이 끝난다

카드 결제의 시간 구조는 짧다. 우리 서버가 PG사(결제대행사)의 승인 API를 부르면, 수 초 안에 카드사까지 다녀온 확정 결과(승인 또는 거절)가 HTTP 응답으로 돌아온다.

이걸 **동기(synchronous)** 라고 부른다. 동기란 "요청을 보낸 쪽이 결과가 나올 때까지 기다렸다가 같은 자리에서 결과를 받는" 방식이다. 우리 코드로 보면 `pgClient.approve(...)`라는 메서드 호출 한 줄이 리턴될 때 결과가 손에 들어와 있다.

그래서 카드 결제의 상태 머신에서 `IN_PROGRESS`의 수명은 **몇 초**다. 응답을 받는 순간 APPROVED 또는 FAILED가 확정된다. 타임아웃 때문에 생기는 `UNKNOWN`은 어디까지나 **예외 상황**이고, 정상 흐름이 아니다.

### 1-2. 가상계좌: "계좌 발급 성공"은 결제 성공이 아니다

**가상계좌(virtual account)** 는 주문 1건을 위해 임시로 발급되는 1회용 입금 전용 계좌다. "가상"이라고 부르는 이유는 실제 은행 계좌를 새로 개설하는 게 아니라, PG사가 가진 모계좌 아래에 주문마다 구분용 번호를 하나씩 찍어주는 구조이기 때문이다. 그 번호로 돈이 들어오면 PG는 "아, 이건 4211번 주문 건이구나"를 알 수 있다.

흐름이 카드와 근본적으로 다르다.

```
[우리 서버]        [PG사]         [고객]        [은행]
     │               │              │             │
  ① 계좌 발급 요청 ─> │              │             │
     │ <── 계좌번호 ── │              │             │
     │  (즉시 응답)    │              │             │
     │               │              │             │
     │ ······ 여기서 시간이 흐른다. 10분? 이틀? 영영? ······
     │               │              │             │
     │               │              │ ② 입금 ───> │
     │               │ <────────────────── 입금 통지 ──│
     │ <── ③ 입금 통보 웹훅 ─────────│             │
     │               │              │             │
  ④ 금액 검증 후 결제 완료 처리       │             │
```

①의 응답은 "입금받을 준비가 됐다"일 뿐, **돈에 관한 어떤 사실도 확정하지 않는다.** 이 지점이 이 문서의 출발점이다.

카드와 나란히 놓고 보면 차이가 선명해진다.

| | 카드 | 가상계좌 |
|---|---|---|
| 승인을 결정하는 주체 | 카드사 (우리 요청에 응답) | **고객의 손가락과 은행** |
| 완료 신호가 오는 방향 | 우리가 보낸 요청의 응답 | **저쪽에서 먼저 걸어오는 웹훅** |
| "진행 중" 상태의 수명 | 몇 초 | 몇 시간 ~ 며칠 |
| 가장 흔한 종결 상태 | APPROVED | **EXPIRED (입금 없이 만료)** |
| 돈이 안 들어올 수 있나 | 거절되면 애초에 아무 일 없음 | 고객이 그냥 안 보낼 수 있음 |

### 1-3. 무엇이 뒤집히는가 — 완료 신호의 방향

위 표에서 두 번째 줄이 설계를 가장 크게 바꾼다.

카드 결제 코드를 짤 때 우리는 **결과를 기다리는 쪽**이다. `try { 결과 = 호출(); } catch { ... }` 구조에 모든 게 들어간다. 성공도 실패도 그 메서드 호출 한 줄의 결과다.

가상계좌에서는 그 구조가 통째로 사라진다. 결제 요청 API는 계좌번호만 받고 리턴하고, **진짜 결과는 완전히 다른 스레드, 다른 요청, 어쩌면 다른 서버 인스턴스에서** 처리된다. 우리 코드는 결과를 받는 게 아니라 **결과를 받을 창구(웹훅 엔드포인트)를 열어두고 기다리는** 쪽이 된다.

**웹훅(webhook)** 이 바로 그 창구다. 우리가 상대를 호출하는 게 아니라 상대가 우리 서버의 특정 URL로 먼저 HTTP 요청을 보내오는 방식이다. "결과 나오면 여기로 알려주세요" 하고 연락처를 남겨두는 것과 같다.

여기서 파생되는 문제들이 이 문서의 나머지 전부다.

- 그 창구는 **공개 URL**이다. 누구나 요청을 보낼 수 있다. → 서명 검증이 필요하다
- 상대는 우리 응답을 못 받으면 **다시 보낸다**. → 중복 처리를 막아야 한다
- 상대의 요청이 **유실될 수도 있다**. → 웹훅에만 의존하면 안 된다
- 그동안 우리 배치는 계속 돈다. → **경합**이 생긴다

계좌이체(고객이 인증 후 이체하면 완료 통보가 오는 구조)와 후불 결제(한도 심사 후 확정 통보)도 정도만 다를 뿐 같은 비동기 구조다.

### 1-4. 비유 — 카운터 결제와 무통장 거래

카드는 카운터에서 카드를 긁고 그 자리에서 영수증을 받는 현장 결제다. 손님이 돌아설 때 이미 거래가 끝나 있다.

가상계좌는 시장 도매상의 무통장 거래다. "이 계좌로 보내주세요" 하고 주문서만 받아둔 상태다. 사장님은 **입금 문자가 올 때까지 물건을 부치지 않는다.** 사흘 안에 입금이 없으면 주문서를 폐기한다. 입금 문자(웹훅)가 유일한 출고 신호고, "주문서 접수"를 "판매 완료"로 착각하는 순간 돈 없이 물건이 나간다.

카드 모델 그대로 가상계좌를 끼워 넣은 시스템이 정확히 이 착각을 저지른다 — 발급 응답이 성공했다고 상태를 APPROVED로 기록해서, 89,000원이 들어오지도 않았는데 주문을 완료 처리하는 것이다.

## 2. 설계 — 새 상태, 웹훅 중심 완료, 만료 배치

### 2-1. 상태 머신에 입금 대기와 만료가 추가된다

```
READY ──> WAITING_DEPOSIT ──> APPROVED ──> CANCELED / REFUNDED
               │                  ▲
               │                  │ (입금 통보 웹훅)
               └──> EXPIRED       │
                     │            │
                     └── 기한 후 입금 ──> [예외 큐 → 자동 환불]
```

| 상태 | 뜻 | 체류 시간 | 정상인가 |
|---|---|---|---|
| `WAITING_DEPOSIT` | 계좌 발급 완료, 입금 기다리는 중 | 시간~일 | **정상** |
| `EXPIRED` | 기한까지 입금 없음 | 종결 | **정상** (가장 흔한 종결) |
| `APPROVED` | 입금 확인 완료 | — | 정상 |
| `REFUNDED` | 이체로 돈을 돌려줌 | — | 정상 |

**WAITING_DEPOSIT(입금 대기)** 는 가상계좌 발급이 성공한 시점의 상태다. 카드의 `IN_PROGRESS`가 초 단위인 것과 달리 이 상태는 **시간~일 단위로 체류하는 정상 상태**다.

이 "정상"이라는 말이 중요하다. 조회 화면·CS 도구·통계·알림이 전부 이 상태를 정규 상태로 다뤄야 한다. 예를 들어 "결제 성공률" 지표를 낼 때 입금 대기 건을 실패로 세면 지표가 망가진다. 장애 알림을 걸 때 "10분 넘게 진행 중인 결제"를 조건으로 잡으면 가상계좌 건이 전부 알림을 울린다. **상태 하나를 추가한다는 건 그 상태를 아는 코드를 전부 고친다는 뜻이다.**

**EXPIRED(기한 만료)** 는 입금 기한(예: 발급 후 48시간)까지 입금이 없을 때 배치가 전이시키는 종결 상태다. 카드에는 사실상 없던 상태인데, 가상계좌에서는 **가장 흔한 종결 상태**가 된다 — 가상계좌 주문의 상당수는 입금 없이 그냥 만료된다. 고객이 마음을 바꾸거나, 잊어버리거나, 다른 수단으로 다시 결제하기 때문이다.

**APPROVED** 는 입금 통보 웹훅을 검증·반영한 시점이다. 여기서부터는 카드와 같은 흐름(취소·환불)에 합류한다. 단 한 가지가 다르다 — 가상계좌의 "취소"는 카드 승인 취소처럼 승인 자체를 없애는 게 아니라 **고객 계좌로 돈을 다시 보내는 이체**다. 그래서 며칠 걸리는 `REFUNDED` 경로를 탄다.

### 2-2. 웹훅의 세 가지 성질 — 이걸 전제로 설계해야 한다

웹훅 핸들러를 짜기 전에, 웹훅이 어떤 물건인지부터 정확히 알아야 한다. 세 가지 성질이 있고 셋 다 설계에 직접 영향을 준다.

**성질 1 — 중복 도착한다.** PG는 웹훅을 보내고 우리 서버가 200을 돌려주면 "전달 성공"으로 간주한다. 200을 못 받으면 **재발송한다.** 그런데 200을 못 받는 이유가 "우리가 처리를 못 해서"만은 아니다. 우리는 정상 처리하고 200을 보냈는데 그 응답이 네트워크에서 유실될 수도 있다. 그러면 PG 입장에서는 실패로 보이고, 우리는 이미 처리한 통보를 또 받는다.

이 성질을 업계 용어로 **at-least-once 전달(최소 한 번은 전달)** 이라고 한다. "정확히 한 번"은 분산 시스템에서 사실상 불가능하기 때문에, 보내는 쪽은 "최소 한 번"을 보장하고 **중복 제거는 받는 쪽 책임**으로 넘긴다.

**성질 2 — 위조될 수 있다.** 웹훅 엔드포인트는 인터넷에 열린 공개 URL이다. 주소만 알면 누구나 "10만원 입금됐어요"라는 JSON을 POST할 수 있다. 그래서 **서명 검증**이 필수다.

서명 검증은 이렇게 동작한다. PG와 우리만 아는 비밀키가 있고, PG는 보낼 본문에 그 키를 섞어 해시(HMAC)를 계산해 헤더에 담아 보낸다. 우리도 받은 본문에 같은 키로 같은 해시를 계산해서 헤더 값과 비교한다. 일치하면 "비밀키를 아는 쪽이 보냈고, 본문이 중간에 변조되지 않았다"가 증명된다.

**성질 3 — 유실·지연될 수 있다.** PG 장애, 우리 서버 배포 중 다운, 은행 점검 시간대의 지연 등으로 웹훅이 아예 안 오거나 몇 시간 뒤에 올 수 있다. 그래서 **웹훅을 유일한 경로로 삼으면 안 된다** — 이건 3절 사례 1의 주제다.

그리고 성질 하나 더. 웹훅은 우리 만료 배치와 **같은 행을 두고 경합한다.** 웹훅이 APPROVED로 바꾸려는 순간 배치가 EXPIRED로 바꾸려 할 수 있다.

### 2-3. 웹훅 핸들러가 설계의 본체다

```java
// Before: 발급 응답에서 완료 처리 + 웹훅은 받는 대로 반영
public PaymentResponse payByVirtualAccount(PaymentRequest req) {
    VirtualAccount va = pgClient.issueVirtualAccount(req);
    payment.transitionTo(APPROVED, "가상계좌 발급 성공"); // 치명적 오류
    orderService.complete(payment.getOrderId());  // 입금 전에 완료!
    return PaymentResponse.of(va);
}

@PostMapping("/webhooks/deposit")
public void onDeposit(@RequestBody DepositNotification n) {
    Payment p = paymentRepository.findByOrderId(n.orderId());
    p.setStatus(APPROVED);            // 중복 웹훅이면 두 번 실행
    benefitService.grant(p);          // 이용권 이중 지급
    // 서명 검증 없음, 금액 검증 없음, 상태 전이 검증 없음
}
```

이 코드에는 독립적인 사고 원인이 네 개 들어 있다.

1. **발급 응답을 승인으로 취급** — 입금 없이 주문이 완료된다
2. **서명 검증 없음** — 아무나 가짜 입금 통보를 보내 물건을 받을 수 있다
3. **금액 검증 없음** — 1,000원만 입금해도 89,000원 주문이 완료된다
4. **상태 전이 검증 없음** — 중복 웹훅마다 이용권이 나간다

이제 하나씩 막아보자.

```java
// After: 발급은 WAITING_DEPOSIT까지만, 완료는 웹훅이 결정
public PaymentResponse payByVirtualAccount(PaymentRequest req) {
    VirtualAccount va = pgClient.issueVirtualAccount(
            req, Duration.ofHours(48));   // 입금 기한을 명시적으로 지정
    payment.transitionTo(WAITING_DEPOSIT, "가상계좌 발급");
    payment.setDepositDeadline(va.dueDate());   // 만료 배치가 쓸 기준 시각
    return PaymentResponse.waiting(va);  // 화면 문구도 "입금 대기"여야 한다
}

@PostMapping("/webhooks/deposit")
public ResponseEntity<Void> onDeposit(
        @RequestHeader("X-Signature") String sig,
        @RequestBody DepositNotification n) {

    // ① 서명 검증 — 이 요청이 정말 PG에서 왔는지 확인한다.
    //    공개 URL이므로 이 줄이 없으면 누구나 가짜 입금을 통보할 수 있다.
    webhookVerifier.verify(sig, n);

    // ② 통보 내용을 믿지 말고 PG 조회 API로 재확인한다.
    //    서명이 맞아도 키 유출이나 구현 실수의 여지는 남으므로,
    //    "얼마가 들어왔나" 같은 돈의 사실은 우리가 PG에 직접 물어서 확정한다.
    PgTransaction tx = pgClient.getTransaction(n.pgTxId());

    // ③ 금액 검증 — 주문 금액과 입금액이 다르면 승인하지 않는다. (2-5)
    Payment p = paymentRepository.findByPgTxId(n.pgTxId());
    if (tx.amount().compareTo(p.getAmount()) != 0) {
        depositExceptionService.register(p, tx);
        // 200을 준다. 우리가 접수해서 예외 처리로 보냈으므로,
        // PG가 같은 통보를 계속 재발송하게 둘 이유가 없다.
        return ResponseEntity.ok().build();
    }

    // ④ 조건부 UPDATE — 중복 웹훅과 만료 배치와의 경합을 한 번에 처리한다.
    //    "지금도 여전히 WAITING_DEPOSIT일 때만" APPROVED로 바꾼다.
    int updated = jdbc.update("""
        UPDATE payment SET status = 'APPROVED', approved_at = now()
         WHERE id = ? AND status = 'WAITING_DEPOSIT'
        """, p.getId());

    if (updated == 1) {
        // 갱신에 성공한 요청은 이 세상에 하나뿐이다.
        // 그러므로 이용권 지급도 정확히 한 번만 실행된다.
        // (지급 로직 자체도 결제 ID 유니크 제약으로 멱등하게 만들어두면 이중 방어)
        benefitService.grant(p);
    } else if (reloadStatus(p.getId()) == EXPIRED) {
        // 만료 배치가 먼저 이겼다 = 기한 후 입금.
        // 돈은 이미 들어와 있으므로 버리면 안 되고 환불 파이프라인으로 보낸다. (2-4)
        depositExceptionService.registerLateDeposit(p, tx);
    }
    // 그 외의 0건은 이미 APPROVED인 중복 웹훅이다. 조용히 200으로 끝낸다.
    return ResponseEntity.ok().build();
}
```

④의 조건부 UPDATE가 이 설계의 심장이다. 왜 이 한 줄이 그렇게 중요한지 정리하면 이렇다.

이 시점에 이 웹훅 요청이 처한 상황은 세 가지 중 하나다 — (a) 정상적인 첫 통보, (b) 이미 처리한 건의 중복 통보, (c) 만료 배치에 진 기한 후 입금. 그런데 애플리케이션 코드가 이 셋을 미리 구분할 방법은 없다. 지금 상태를 SELECT로 읽어본다 해도, 읽은 다음 UPDATE하기까지의 사이에 상태가 또 바뀔 수 있기 때문이다.

조건부 UPDATE는 이 구분을 **DB에게 맡긴다.** 갱신 행 수라는 단 하나의 숫자가 "내가 이 전이의 승자인가"에 대한 확정적인 답을 준다.

| 갱신 행 수 | 이후 상태 | 상황 | 후속 처리 |
|---|---|---|---|
| 1 | APPROVED | 정상 첫 통보 | 이용권 지급 |
| 0 | 이미 APPROVED | 중복 웹훅 | 아무것도 안 함, 200 |
| 0 | EXPIRED | 기한 후 입금 | 예외 큐 → 자동 환불 |

**이용권 지급이 `updated == 1` 블록 안에만 있다는 게 핵심이다.** 웹훅이 열 번 와도 갱신에 성공하는 건 한 번뿐이므로, 지급도 한 번뿐이다. 별도의 중복 체크 로직이 필요 없다.

### 2-4. 기한 만료 배치 — 그리고 웹훅과의 레이스

만료 배치는 주기적으로(예: 5분) 기한 지난 입금 대기 건을 정리한다.

```sql
UPDATE payment
   SET status = 'EXPIRED'
 WHERE status = 'WAITING_DEPOSIT'
   AND deposit_deadline < now();
-- 여기도 조건부 UPDATE다. 만료 시각 직전에 웹훅이 먼저 APPROVED로
-- 바꿔놨다면 status 조건에 안 걸려서 이 행을 건드리지 못한다.
```

#### 레이스 컨디션이 무엇인가

**레이스 컨디션(race condition)** 은 두 개 이상의 작업이 같은 자원을 두고 경쟁할 때, **어느 쪽이 먼저 도착하느냐에 따라 결과가 달라지는** 상황이다. 경주(race)에 비유한 이름이다.

여기서 경쟁자는 만료 배치와 입금 웹훅이고, 자원은 결제 행 하나다. 그리고 이 경주에는 **한쪽만 이겨야 한다** — 둘 다 성공하면 "만료된 승인 건"이라는 말이 안 되는 상태가 만들어진다.

#### 방향 1 — 웹훅이 이기는 경우 (문제없음)

```
23:59:58  [웹훅] UPDATE ... status='APPROVED' WHERE status='WAITING_DEPOSIT'  → 1건
00:00:00  [배치] UPDATE ... status='EXPIRED'  WHERE status='WAITING_DEPOSIT'  → 0건
```

배치의 UPDATE가 0건으로 끝난다. 배치는 "이 건은 그새 입금됐구나" 하고 넘어가면 된다. 아무 문제 없다.

#### 방향 2 — 배치가 이기는 경우 (처리가 필요하다)

문제는 반대 방향이다. 배치가 EXPIRED로 바꾼 **직후** 입금 웹훅이 도착하는 경우, 즉 **기한 후 입금**이다.

```
00:00:00  [배치] UPDATE ... status='EXPIRED'   → 1건. 재고도 해제.
00:03:12  [웹훅] UPDATE ... WHERE status='WAITING_DEPOSIT' → 0건
          하지만 고객 돈 158,000원은 이미 PG 계좌에 들어와 있다.
```

이 케이스는 **반드시 발생한다.** 피할 수 없는 이유가 있다 — 고객이 은행 앱에서 이체 버튼을 누르는 순간과 우리 배치가 UPDATE를 실행하는 순간은 서로 다른 시스템에서 일어나고, 두 시스템은 원자적으로 동기화되지 않는다. 고객이 23:59:59에 이체를 눌러도 은행→PG→우리로 통보가 오는 데 몇 분이 걸릴 수 있다.

조건부 UPDATE 덕분에 **이중 승인은 없다.** 하지만 그것만으로는 부족하다. 돈은 이미 우리 쪽(PG 계좌)에 들어와 있는데 주문은 없는 상태이기 때문이다. 이건 고객 입장에서 최악의 상황이다.

그래서 EXPIRED 상태에 대한 입금은 **예외 큐**에 적재하고 자동 환불(계좌 이체 반환) 흐름으로 보낸다. 예외 큐란 정상 흐름으로 처리할 수 없는 건을 버리지 않고 모아두는 별도 테이블 또는 메시지 큐다. 핵심은 "처리 못 하는 건을 로그만 남기고 버리지 않는다"는 것이다.

#### 그리고 창 자체를 줄인다

사후 처리도 필요하지만, 애초에 이 창이 열리는 시간을 줄이는 게 더 낫다. PG에 따라 **만료 시점에 가상계좌 자체를 닫아주는 옵션**(계좌 만료 처리)이 있다. 계좌가 닫히면 그 뒤의 입금 시도는 **은행 단에서 거절**되므로, 애초에 우리 쪽으로 돈이 들어오지 않는다.

여기서 원칙 하나 — **예외 처리를 코드로 감당하기 전에, 예외가 발생할 수 있는 창 자체를 줄일 방법이 있는지 먼저 본다.**

### 2-5. 금액 불일치 입금·부분 입금 — 승인하지 말고 예외 큐로

고객이 49,000원 주문의 가상계좌에 40,000원을 보내거나 94,000원을 보내는 일이 실제로 일어난다. 이유는 단순하다 — 일부 은행 앱은 이체 화면에서 금액을 직접 입력하게 되어 있어서, 고객이 숫자를 잘못 치면 그대로 나간다.

원칙은 하나다. **주문 금액과 정확히 일치하지 않는 입금은 절대 APPROVED로 만들지 않는다.**

왜 그런지는 대안을 하나씩 검토해보면 알 수 있다.

**대안 A — 부족해도 승인한다?** 40,000원 입금에 49,000원짜리 이용권을 지급하는 것이다. 회사가 9,000원 손해를 보고, 이게 알려지면 악용된다. 명백히 안 된다.

**대안 B — "9,000원만 더 보내세요"라고 안내하고 합산한다?** 그럴듯해 보이지만, 이걸 하려면 상태 머신에 "부분 입금됨(누적 40,000 / 49,000)"이라는 상태가 필요하다. 그리고 이 상태 하나가 시스템 전체로 번진다.

- **상태**: 입금 횟수와 누적 금액을 추적해야 하고, 만료 시점의 처리 규칙이 새로 필요하다
- **대사**: PG 거래 내역과 맞출 때 1:1이 아니라 N:1 매칭이 된다
- **환불**: 만료됐을 때 여러 건의 입금을 각각 되돌려야 한다
- **초과 입금**: 94,000원이 들어오면 45,000원을 부분 환불해야 하는데, 이건 또 다른 흐름이다

이 복잡도 때문에 **대부분의 커머스는 부분 입금 합산을 지원하지 않는다.**

**채택 — 예외 큐 + 전액 자동 환불.** 불일치 입금은 예외 큐에 적재해서 들어온 금액 전액을 자동으로 되돌려주고, 주문은 입금 대기를 유지하거나(고객이 정확한 금액으로 다시 보낼 수 있게) 만료시킨다.

**예방책이 더 중요하다.** PG의 **고정금액 가상계좌 옵션**을 켜면, 지정한 금액과 다른 입금은 은행 단에서 거절된다. 고객은 이체 화면에서 애초에 다른 금액을 넣을 수 없거나, 넣어도 실패한다.

즉 예외 케이스를 코드가 아니라 **입구에서** 제거하는 것이다. 2-4의 계좌 만료 옵션과 같은 발상이다 — 처리해야 할 예외의 종류를 줄이는 게 예외 처리를 잘 짜는 것보다 낫다.

### 2-6. 재고·주문 선점 — 입금 대기 동안 재고를 잡아둘 것인가

가상계좌는 결제 도메인 밖으로도 파문을 만든다. 카드 결제에서는 "결제 성공 = 즉시" 이므로 재고 처리에 고민할 게 없었는데, 입금 대기가 48시간이면 그동안 재고를 어떻게 할지 결정해야 한다.

선택지는 둘뿐이고 둘 다 부작용이 있다.

**선택지 A — 선점한다.** 발급 시점에 재고를 잡아둔다. 문제는 **입금 없이 만료되는 다수의 주문이 그동안 재고를 잠근다**는 것이다. 앞서 봤듯 가상계좌 주문의 상당수는 입금 없이 만료된다. 한정 수량 상품이면 "품절인데 아무도 안 산" 상태가 되고, 진짜 살 고객이 못 산다. 악의적으로 가상계좌 주문을 대량 생성해 상품을 품절시키는 공격도 가능하다.

**선택지 B — 선점하지 않는다.** 입금이 확인될 때 재고를 잡는다. 문제는 **고객이 이틀 뒤 입금했는데 그새 품절**인 경우다. 돈은 받았는데 물건이 없으니 자동 환불해야 하고, 고객은 "돈 보냈는데 왜 취소냐"고 화를 낸다. CS 부담이 크다.

정답은 도메인 정책이지 기술이 아니다. 다만 실무에서 자주 쓰는 기본 조합은 있다.

1. **재고는 선점하되 입금 기한을 짧게** 잡는다(48시간이 아니라 24시간). 재고가 잠기는 시간을 절반으로 줄인다.
2. **만료 배치가 EXPIRED 전이와 함께 재고를 해제**한다. 이때 재고 해제와 상태 전이가 **항상 같이 일어나도록** 같은 트랜잭션에 넣거나, 상태 전이 후 발행되는 이벤트로 묶는다. 둘이 따로 놀면 "만료됐는데 재고는 계속 잠긴" 건이 조용히 쌓인다.
3. **한정판·타임세일 상품은 가상계좌 결제 수단 자체를 막는다.** 재고 경쟁이 치열한 상품에서는 어느 선택지를 골라도 사고가 나므로, 애초에 비동기 수단을 허용하지 않는 게 낫다.

3번이 특히 실무적인 답이다 — **모든 상품에 같은 결제 수단을 열어줘야 할 이유가 없다.**

## 3. 실무 사례 — 비동기 승인이 뚫리는 구멍들

### 사례 1: 웹훅 유실 — 입금했는데 3일째 "입금 대기"

은행 점검 시간대에 걸친 입금 건들의 통보가 PG에서 지연·유실됐다.

고객은 **137,000원**을 입금했는데 주문은 WAITING_DEPOSIT에 머물렀다. 그리고 이틀 뒤 만료 배치가 정상적으로 동작해서 그 건을 EXPIRED로 넘기고 재고까지 풀어버렸다. **돈은 PG에 있고 주문은 만료된** 최악의 CS다.

여기서 중요한 건 우리 코드에 버그가 없었다는 점이다. 웹훅 핸들러도 만료 배치도 설계대로 정확히 동작했다. 문제는 **설계가 웹훅 하나에만 의존했다**는 것이다.

교훈: 웹훅은 **유일한 경로여선 안 된다.** 완료 신호를 받는 경로를 두 개로 만든다.

- **밀어주는 경로(push)**: PG가 보내는 웹훅. 빠르지만 유실될 수 있다.
- **당겨오는 경로(pull)**: 우리가 WAITING_DEPOSIT 건을 주기적으로 PG 입금 조회 API로 확인하는 대사 배치. 느리지만 유실되지 않는다.

웹훅이 유실돼도 조회 배치가 입금 사실을 회수한다. 이 구조를 일반화하면 **"상대가 알려주기를 기다리는 설계는 상대가 안 알려주면 영원히 멈춘다. 그래서 우리가 직접 물어보는 경로를 항상 하나 둔다"** 가 된다.

여기에 하나 더 — **만료 전이 직전에 한 번 더 조회하는 "만료 전 최종 확인"** 이 이 사고를 막는 결정적 안전판이다. 만료는 되돌리기 어려운 종결 전이(재고 해제까지 동반)이므로, 그 직전에 PG에 한 번 더 물어보는 비용은 충분히 값어치가 있다.

### 사례 2: 중복 웹훅으로 이용권 이중 지급

PG는 웹훅 응답으로 200을 받지 못하면 재발송한다(2-2의 성질 1).

이 시스템은 이용권 지급 로직이 무거워서 웹훅 핸들러의 처리 시간이 PG의 응답 타임아웃을 넘겼다. PG는 응답을 못 받았으니 실패로 간주해 같은 입금 통보를 세 번 보냈다. 상태 전이 검증이 없던 핸들러는 세 번 모두 지급을 실행했고, **59,000원 결제에 이용권 3개**가 나갔다.

주목할 점은 이게 "네트워크가 이상해서" 생긴 사고가 아니라는 것이다. **우리 핸들러가 느린 것 자체가 원인**이었다. 느린 핸들러는 재발송을 유발하고, 재발송은 다시 느린 핸들러를 여러 개 띄운다.

교훈 세 가지다.

1. **조건부 UPDATE로 최초 1회만 후속 처리를 실행한다.** 2-3의 ④가 이것이다. 몇 번 오든 갱신에 성공하는 건 한 번뿐이다.
2. **무거운 후속 작업은 웹훅 응답과 분리한다.** 상태 전이만 동기로 처리하고 200을 빠르게 돌려준 뒤, 지급·알림 같은 작업은 비동기(메시지 큐, 이벤트 발행)로 넘긴다. **웹훅 핸들러의 목표는 빠른 접수이지 완전한 처리가 아니다.**
3. **지급 로직 자체도 멱등하게 만든다.** 지급 테이블에 결제 ID 유니크 제약을 걸면, 어떤 경로로 두 번 호출돼도 두 번째는 DB가 막는다. 조건부 UPDATE가 뚫려도 여기서 걸린다.

3번이 **심층 방어(defense in depth)** 다. 방어선 하나에 모든 걸 걸지 않고, 하나가 뚫려도 다음이 막도록 층을 쌓는 사고방식이다. 결제 시스템에서는 방어선 하나가 반드시 언젠가 뚫린다고 가정하는 편이 안전하다.

### 사례 3: 만료 5분 뒤 입금 — 돈은 왔는데 주문이 없다

23:58에 만료 배치가 **158,000원** 주문을 EXPIRED로 정리하고 재고를 해제했는데, 00:03에 입금 웹훅이 도착했다. 2-4에서 본 "방향 2" 레이스가 실제로 일어난 것이다.

조건부 UPDATE는 있어서 이중 승인은 없었다. 그런데 **0건일 때의 처리가 없었다.** 핸들러는 "상태 전이 실패"라는 로그 한 줄만 남기고 요청을 버렸다.

결과: 고객 돈 158,000원이 PG의 미매칭 잔액(어느 주문에도 연결되지 않은 입금)으로 3주간 방치되다가 월말 대사에서야 발견됐다. 고객은 그동안 아무 연락도 받지 못했다.

교훈: **기한 후 입금은 로그가 아니라 자동 환불 파이프라인으로 들어가야 한다.** 설계 범위를 명확히 하면 이렇다.

```
EXPIRED 건에 대한 입금 통보 도착
        ↓
예외 테이블에 적재 (금액, PG 거래 ID, 고객 정보, 사유)
        ↓
환불 이체 실행 (실패 시 재시도, 결과 불명 시 UNKNOWN 처리)
        ↓
고객 안내 (문자·메일: "기한 후 입금으로 자동 환불되었습니다")
        ↓
대사 배치에서 "미환불 예외 건" 잔량 0 확인
```

여기까지가 하나의 설계 범위다. "웹훅 핸들러를 잘 짰다"로 끝나는 게 아니다.

그리고 세 사례를 관통하는 한 문장 — **"0건 갱신"을 조용히 삼키는 코드가 사고의 씨앗이다.** 1번 문서에서도 같은 이야기가 나왔고, 여기서도 같은 자리에서 터졌다. 갱신 행 수가 0이라는 건 "내가 예상한 세상과 실제 세상이 다르다"는 신호이고, 그 신호를 버리면 그 차이는 며칠 뒤 돈 문제로 돌아온다.

## 4. 꼬리질문 대비 포인트

### "만료 배치와 입금 웹훅이 같은 순간에 실행되면요?" (시니어 변별 포인트)

양쪽 모두 `WHERE status = 'WAITING_DEPOSIT'` 조건부 UPDATE이므로, DB의 행 락 위에서 **직렬화되어 정확히 한쪽만 성공한다.**

"직렬화된다"는 말을 풀면 이렇다. PostgreSQL은 한 행을 UPDATE할 때 그 행에 락을 건다. 두 트랜잭션이 같은 행을 UPDATE하려 하면 나중에 온 쪽이 앞의 트랜잭션이 끝날 때까지 대기한다. 그리고 대기가 풀린 뒤 **다시 조건을 확인한다.** 그래서 앞 트랜잭션이 상태를 바꿔놨다면 뒤 트랜잭션의 WHERE 조건은 이제 맞지 않게 되어 0건이 된다.

결과는 어느 쪽이 이기든 정의된 경로로 간다.

| 승자 | 패자에게 일어나는 일 | 최종 결과 |
|---|---|---|
| 웹훅 | 배치의 UPDATE가 0건 | 정상 승인. 배치는 그냥 넘어감 |
| 배치 | 웹훅의 UPDATE가 0건 | 기한 후 입금 예외 경로 → 자동 환불 |

여기서 답의 핵심은 특정 쪽이 이기게 만드는 게 아니다.

> **레이스를 없애는 게 아니라, 어느 승자든 안전한 결과가 되게 설계한다.**

이 문장이 시니어 변별 지점이다. 주니어의 흔한 답변은 "배치 실행 전에 상태를 한 번 더 확인한다"거나 "웹훅 처리 중에는 배치가 못 돌게 플래그를 둔다"처럼 **애플리케이션 레벨 if문으로 순서를 조율하려는** 방향인데, 이건 확인과 실행 사이의 틈을 없애지 못해서 결국 같은 문제가 남는다. 순서를 통제하려 들지 말고, 순서가 어떻게 되든 결과가 안전하도록 만드는 쪽이 맞다.

### "웹훅 내용을 왜 그대로 믿지 않고 조회 API로 재확인하나요?"

웹훅 엔드포인트는 공개 URL이라 위조 요청이 가능하다. 서명 검증이 1차 방어인데, 서명이 있어도 완전하지 않다 — 비밀키가 유출될 수 있고, 검증 구현에 실수가 있을 수 있다(예: 서명 비교를 문자열 `equals`로 해서 타이밍 공격에 노출되거나, 특정 경로에서 검증을 건너뛰거나).

그래서 통보는 **"입금이 있었을 수 있다"는 트리거로만** 쓴다. 금액·상태 같은 **돈에 관한 사실은 우리가 PG에 직접 발신하는 조회 API의 응답으로 확정**한다.

핵심은 **신뢰의 방향을 뒤집는 것**이다.

| | 수신(웹훅 본문) | 발신(조회 API 응답) |
|---|---|---|
| 누가 보냈나 | 인터넷의 누군가 (서명으로 추정만 가능) | 우리가 PG 도메인으로 직접 물어봄 |
| 신뢰 근거 | 서명이 맞더라. 아마도 PG겠지 | TLS로 PG 서버와 직접 연결해 받은 답 |
| 결론 | 트리거로만 사용 | **사실로 채택** |

한 문장으로: **"누가 뭘 보냈는지"가 아니라 "우리가 누구에게 물어봤는지"를 신뢰의 근거로 삼는다.** 주요 PG들이 공식 가이드에서 권장하는 패턴이기도 하다.

### "입금 대기 중 고객이 주문을 취소하면 어떻게 되나요?"

`WAITING_DEPOSIT → CANCELED` 전이를 상태 머신에 추가한다. 여기까지는 쉽다.

핵심은 **PG 쪽 가상계좌를 함께 만료(입금 불가) 처리하는 것**이다. 우리 DB의 상태만 바꾸고 계좌를 열어둔 채로 두면, 고객이(또는 고객의 자동이체가) 그 계좌로 돈을 보낼 수 있다. 그러면 "취소된 주문에 입금"이라는, 2-4의 기한 후 입금과 완전히 동일한 예외가 생긴다.

즉 **우리 상태와 PG 쪽 계좌 상태가 같이 움직여야 한다.** 한쪽만 닫으면 그 틈이 곧 사고다.

그런데 여기서 한 걸음 더 나가야 시니어의 답이 된다. **계좌 만료 처리 자체가 실패하거나 타임아웃될 수 있다.** PG API도 외부 호출이라 언제든 실패한다. 재시도를 걸어도 결국 안 되는 건이 생긴다.

그래서 결론은 이렇다 — 계좌를 닫으려고 최선을 다하되, **취소 이후 도착하는 입금 통보도 결국 자동 환불 경로로 수렴하게 예외 파이프라인은 항상 살려둔다.** 예방(계좌 닫기)과 수습(예외 환불)을 둘 다 갖추는 것이지, 예방이 되니까 수습을 빼는 게 아니다.

### "WAITING_DEPOSIT과 카드의 UNKNOWN은 뭐가 다른가요?"

둘 다 "확정 전"이라는 점은 같지만 성격이 정반대다.

| | `UNKNOWN` (카드) | `WAITING_DEPOSIT` (가상계좌) |
|---|---|---|
| 결과가 정해졌나 | **이미 정해졌다.** 우리가 모를 뿐 | **아직 안 정해졌다** |
| 정상인가 | **비정상** (사고의 흔적) | **정상** (설계된 흐름) |
| 적정 체류 시간 | 수 분 | 수 시간 ~ 수 일 |
| 쌓이면 | **알림을 울려야 한다** | 아무 문제 없다 |
| 담당 처리기 | 분 단위 해소 배치 (PG 거래 조회) | 기한 만료 배치 + 입금 대사 배치 |
| 해소 수단 | 조회로 확정, 안 되면 망취소 | 웹훅 또는 조회로 입금 확인 |

이 구분이 운영에 그대로 반영된다는 점을 강조하면 좋다. 같은 "중간 상태"라도 **SLA와 처리기가 완전히 다르다.**

구체적으로: UNKNOWN이 10분 넘게 남아 있으면 담당자를 깨워야 하지만, WAITING_DEPOSIT이 30시간째 남아 있는 건 지극히 정상이다. 이 둘을 같은 "미확정 결제" 대시보드에 섞어놓으면 알림이 무의미해진다 — 정상 건이 경보를 계속 울리면 사람은 곧 경보를 무시하게 되고, 그때 진짜 UNKNOWN이 묻힌다.

### "카드/가상계좌 상태 머신을 하나의 enum으로 관리하나요, 분리하나요?"

먼저 양 극단을 보자.

**완전 통합** — 하나의 enum에 모든 수단의 상태를 다 넣고 전이 규칙도 하나로 합친다. 문제는 **의미 없는 조합을 걸러낼 수 없다**는 것이다. 카드 결제가 `WAITING_DEPOSIT`으로 전이하는 건 명백한 버그인데, 전이 규칙이 하나로 합쳐져 있으면 그게 정상 전이로 통과한다. 컴파일 단계에서도 검증 단계에서도 못 잡고, 운영에서 이상한 데이터로 발견된다.

**완전 분리** — 수단마다 상태 enum을 따로 만든다. 문제는 공통 처리가 전부 중복된다는 것이다. 취소·환불·대사·이력 기록은 수단과 무관하게 같은 로직인데, 타입이 다르면 코드를 수단 수만큼 복사하게 된다.

그래서 실무적인 절충은 이렇다. **공통 골격(READY, APPROVED, 취소·환불 계열, UNKNOWN)은 공유하되, 수단별 고유 상태(WAITING_DEPOSIT, EXPIRED)를 포함한 허용 전이 테이블을 결제수단별로 분리한다.**

```java
// 상태 값 자체는 하나의 enum으로 공유하고,
// "어떤 전이가 허용되는가"만 수단별로 다르게 둔다.
public interface PaymentStateMachine {
    boolean canTransition(PaymentStatus from, PaymentStatus to);
}

// 카드: WAITING_DEPOSIT으로 가는 전이 자체가 정의돼 있지 않다.
class CardStateMachine implements PaymentStateMachine { /* ... */ }

// 가상계좌: IN_PROGRESS 대신 WAITING_DEPOSIT을 쓴다.
class VirtualAccountStateMachine implements PaymentStateMachine { /* ... */ }
```

이러면 카드 결제 경로에서 실수로 `WAITING_DEPOSIT` 전이를 시도해도 즉시 예외로 막힌다. 그리고 수단이 더 늘면(에스크로, 후불, 해외 결제) 구현체를 하나 추가하는 것으로 끝난다.

이건 1번 문서에서 말한 **"상태 폭발은 상태 머신을 쪼개라는 신호"** 의 실전 적용이다. 상태가 늘어난다고 enum에 값을 계속 더하는 게 아니라, **상태의 성격이 갈리는 축(여기서는 결제 수단)을 찾아서 그 축으로 쪼갠다.**

## 한 줄 요약

가상계좌는 "발급 성공"과 "입금 완료" 사이가 며칠씩 벌어지는 비동기 승인 모델이므로 WAITING_DEPOSIT·EXPIRED라는 새 상태를 상태 머신에 추가하고, 완료의 유일한 신호인 입금 웹훅을 서명 검증 + 조회 API 재확인 + 조건부 UPDATE 멱등 처리로 받아내며, 기한 만료 배치와의 레이스·금액 불일치 입금·기한 후 입금은 전부 자동 환불 예외 파이프라인으로 수렴시켜야 한다 — 발급 응답을 승인으로 착각하는 순간 돈 없이 이용권이 나간다.
