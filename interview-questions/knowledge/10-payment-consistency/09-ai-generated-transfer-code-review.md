# AI 생성 이체 코드의 머지 전 검증 — 테스트 통과는 행복 경로의 증명일 뿐이다

> 핵심 관전 포인트: **"테스트 전부 통과"는 "작성자가 상상한 시나리오 안에서는 맞다"는 뜻이지 검증이 아니다. AI가 생성한 테스트는 행복 경로(happy path)에 편향돼 있고, 테스트까지 같은 AI가 짰다면 구현이 놓친 맹점을 테스트도 똑같이 놓친다. 돈이 움직이는 코드의 사고는 대부분 동시 실행·부분 실패·중복 요청에서 나는데, 이 셋은 단일 스레드로 도는 보통의 테스트에 구조적으로 담기지 않는다. 그래서 검증 순서는 (1) 동시성 — 같은 계좌 동시 이체 시 잔액 음수·갱신 유실 가능성, 락 또는 조건부 UPDATE 확인 (2) 트랜잭션 경계 — 차감과 지급이 한 트랜잭션인지, 외부 호출이 트랜잭션 안에 있는지 (3) 멱등성 — 재시도 시 이중 이체 (4) 예외 경로 — 부분 실패 시 상태 (5) 금액 타입과 도메인 검증(음수 이체, 자기 이체) 순이다. 피해가 크고 테스트로 안 잡히는 것부터 본다.**

---

## 0. 질문 + 의도

**질문**: "AI가 생성한 '포인트 이체' 코드가 테스트를 전부 통과했습니다. 머지 전에 무엇을 어떤 순서로 검증하나요?"

**출제 의도**: AI 산출물 검증 역량을 돈 도메인에서 시뮬레이션하는 질문이다. "테스트 통과"가 왜 검증이 아닌지(동시 실행, 부분 실패, 중복 요청은 보통 테스트에 없다)를 알고, 동시성 → 트랜잭션 경계 → 멱등성 → 예외 경로 순의 검증 우선순위를 갖고 있는지 — AI 시대 리뷰어의 실전 역량을 돈이 걸린 상황으로 압박해 본다.

## 1. 왜 "테스트 통과"가 검증이 아닌가

### 1-0. 먼저 용어 세 개를 맞추고 시작하자

이 문서에서 계속 나올 말이라 미리 정의해 둔다. 셋 다 "혼자 돌릴 때는 절대 안 보이는" 종류의 개념이다.

**행복 경로(happy path)**는 모든 것이 예상대로 흘러가는 실행 경로를 말한다. 입력이 유효하고, 네트워크가 안 끊기고, 요청이 한 번만 오고, 다른 사용자가 같은 데이터를 건드리지 않는 경우다. "행복"이라는 이름이 붙은 이유는 개발자가 기능을 만들 때 머릿속에 그리는 그림이 대개 이것뿐이기 때문이다. 그리고 장애는 여기서 나지 않는다.

**동시(concurrent) 실행**은 두 요청이 "정확히 같은 순간에" 실행된다는 뜻이 아니다. 요청 A가 여러 단계(조회 → 계산 → 저장)로 이뤄져 있을 때, 그 단계들 **사이사이에** 요청 B의 단계가 끼어들 수 있다는 뜻이다. 이 끼어듦을 **인터리빙(interleaving, 실행 순서 겹침)**이라고 부른다. 서버가 요청마다 스레드를 하나씩 쓰기 때문에, 초당 수십 건이 들어오는 서비스에서 인터리빙은 예외 상황이 아니라 기본 상태다.

**원자적(atomic)**은 "쪼갤 수 없다"는 뜻의 물리학 용어에서 왔다. 어떤 연산이 원자적이라는 것은, 밖에서 볼 때 그 연산이 **완전히 끝난 상태이거나 아예 시작도 안 한 상태 둘 중 하나로만 관찰된다**는 뜻이다. 중간 상태가 남에게 보이지 않으므로, 원자적 연산의 한가운데로는 인터리빙이 끼어들 수 없다. 동시성 문제를 푸는 방법은 결국 "쪼개져 있어서 끼어들 수 있던 것을 원자적으로 만드는" 것 하나다.

### 1-1. AI 테스트의 행복 경로 편향

AI에게 "포인트 이체 기능을 만들고 테스트도 작성해줘"라고 하면 보통 이런 테스트가 나온다 — 정상 이체 성공, 잔액 부족 시 예외, 존재하지 않는 계좌 예외.

셋 다 훌륭한 테스트지만, 공통점이 하나 있다. 전부 **한 스레드에서, 한 번씩, 순서대로** 실행되는 시나리오다. 즉 위에서 말한 인터리빙이 하나도 없다. 테스트를 아무리 늘려도 이 축에서는 0건이다.

프롬프트에 명시하지 않는 한 "같은 계좌에 이체 요청 두 건이 동시에 도착하면", "차감은 됐는데 지급 직전에 프로세스가 죽으면", "타임아웃으로 같은 요청이 다시 오면" 같은 시나리오는 나오지 않는다. AI가 게을러서가 아니라, 이런 시나리오는 "기능 명세"가 아니라 "운영 환경의 물리적 조건"이라서 요구사항 문장에 등장하지 않기 때문이다.

그런데 돈 도메인의 사고는 정확히 이 세 지점 — **동시 실행, 부분 실패, 중복 요청** — 에서 난다. 기능이 틀려서 나는 사고보다, 기능은 맞는데 조건이 겹쳐서 나는 사고가 압도적으로 많다.

### 1-2. 구현과 테스트가 같은 맹점을 공유한다

더 근본적인 문제는 **검증의 독립성**이다. 검증이란 "만든 것"을 "만든 것과 무관한 기준"에 비춰보는 행위인데, 구현과 테스트를 같은 모델이 같은 문맥에서 생성했다면 그 무관함이 사라진다.

구현이 요구사항을 잘못 이해했다면, 같은 문맥에서 나온 테스트도 **같은 오해를 기준으로** 만들어진다. 테스트는 "구현이 스스로를 채점하는" 순환 구조가 되고, 전부 초록불이어도 요구사항 충족과는 무관해진다.

비유하면 **답안지를 쓴 사람이 채점 기준표까지 쓴 시험**이다. 문제를 잘못 이해했다면 답안과 기준표가 같은 방향으로 틀려서 100점이 나온다. 점수가 의미를 가지려면 기준표(테스트의 시나리오 목록)는 답안(구현)과 독립적으로 — 즉 리뷰어의 머리에서 — 나와야 한다.

그래서 리뷰어의 역할은 "코드가 테스트를 통과했는가"가 아니라 "**테스트에 없는 시나리오 중 돈이 새는 것이 있는가**"를 찾는 것이다. 아래 순서는 그 시나리오들을 피해 크기 × 테스트로 안 잡히는 정도 순으로 배열한 것이다.

## 2. 검증 순서 — 동시성부터 보는 이유가 곧 답이다

### 2-1. 1순위: 동시성 — check-then-act를 찾아라

#### 결함의 이름부터

AI가 이체 코드에서 가장 흔히 내는 결함이 **검사 후 실행(check-then-act)** 패턴이다. 이름 그대로 "**검사(check)**한 결과를 믿고 **실행(act)**한다"는 구조다. 조회한 잔액으로 검사하고, 조회한 그 값으로 계산해서 저장한다.

여기서 위험한 것은 검사 자체가 아니라 **검사와 실행 사이의 시간**이다. 그 사이에 다른 트랜잭션이 같은 데이터를 바꿔버리면, 검사 결과는 이미 과거의 사실이 되는데 실행은 그 과거를 근거로 진행된다.

```java
// Before: AI가 낸 전형적 결함 — 단일 실행에선 완벽해 보인다
@Transactional
public void transfer(Long fromId, Long toId, long amount) {
    Account from = accountRepository.findById(fromId).orElseThrow();
    Account to = accountRepository.findById(toId).orElseThrow();

    // ① 검사: 이 시점의 balance는 "방금 읽어온 값"이지 "지금 DB의 값"이 아니다.
    //    평범한 SELECT는 행에 락을 걸지 않으므로, 읽은 직후부터 이 값은 낡을 수 있다.
    if (from.getBalance() < amount) {
        throw new InsufficientBalanceException();
    }

    // ② 실행: DB에게 "빼라"가 아니라 "2,000으로 만들어라"라고 지시하는 것과 같다.
    //    최종 값을 자바가 미리 확정해버려서, DB는 그 사이 무슨 일이 있었는지 알 수 없다.
    from.setBalance(from.getBalance() - amount);
    to.setBalance(to.getBalance() + amount);
}
```

#### 시간축으로 펼쳐 보기

말로는 잘 안 와닿으니, 잔액 10,000원 계좌 A에서 8,000원 이체 요청 두 건이 겹쳤을 때 실제로 무슨 일이 벌어지는지 시간 순서대로 늘어놓는다. T1과 T2는 각각 다른 요청을 처리하는 스레드이자 트랜잭션이다.

```
 시각   T1 (A → B, 8,000원)                  T2 (A → C, 8,000원)
──────────────────────────────────────────────────────────────────────────
  t1   SELECT balance FROM account
       WHERE id = A          →  10,000
  t2                                        SELECT balance FROM account
                                            WHERE id = A          →  10,000
  t3   if (10,000 < 8,000) → 거짓, 통과
  t4                                        if (10,000 < 8,000) → 거짓, 통과
  t5   자바에서 계산: 10,000 - 8,000
                          = 2,000
  t6                                        자바에서 계산: 10,000 - 8,000
                                                                = 2,000
  t7   UPDATE account SET balance = 2000
       WHERE id = A                          ← 여기서 A 행에 배타 락을 잡는다
  t8                                        UPDATE account SET balance = 2000
                                            WHERE id = A
                                            ← T1이 락을 쥐고 있어 여기서 "대기"
  t9   COMMIT  (락 해제, A = 2,000)
  t10                                       대기 해제 → balance = 2000 적용
                                            COMMIT   (A = 2,000)
──────────────────────────────────────────────────────────────────────────
 결과: A = 2,000  /  B = +8,000  /  C = +8,000
```

t8에서 T2가 **대기했다는 사실이 함정이다.** 락 때문에 순서가 지켜졌으니 안전할 것 같지만, T2가 쓰려는 값 `2000`은 t6에 자바 메모리에서 이미 확정된 숫자다. T2는 깨어나서 다시 계산하지 않고, 낡은 숫자를 그대로 덮어쓴다. T1의 차감은 존재한 적도 없는 것처럼 사라진다.

이렇게 **먼저 커밋된 갱신이 나중 갱신에 덮여 사라지는 현상**을 **갱신 유실(lost update)**이라고 부른다.

#### 얼마가 새는가 — 합계로 검산한다

돈 시스템의 검산은 항상 "**시스템 전체 잔액의 합**"으로 한다. 이체는 돈을 옮길 뿐 만들거나 없애지 않으므로, 이체 전후의 총합은 반드시 같아야 한다. 이것이 이 도메인의 **불변식(invariant, 언제나 참이어야 하는 조건)**이다.

| 계좌 | 이체 전 | 정상 동작(1건만 성공) | 실제(갱신 유실) |
|---|---|---|---|
| A (출금) | 10,000 | 2,000 | 2,000 |
| B (수취) | 0 | 8,000 | 8,000 |
| C (수취) | 0 | 0 | 8,000 |
| **합계** | **10,000** | **10,000** | **18,000** |

총합이 10,000에서 18,000으로 늘었다. **8,000포인트가 무에서 생겼다.** 회사 장부에서 이 8,000은 누구도 지불하지 않은 부채이고, 결국 회사가 물어낸다.

수취인이 같은 경우(더블 클릭)는 증상이 반대 방향으로 나타난다는 점도 알아두면 좋다. 위 코드는 지급 쪽도 `to.getBalance() + amount`라는 똑같은 check-then-act이므로, B의 잔액도 양쪽이 0을 읽고 둘 다 8,000을 써서 **B는 8,000만 받는다.** 합계는 우연히 맞지만 두 번째 이체가 통째로 증발한 것이고, 사용자에게는 "두 번 보냈는데 상대는 한 번만 받았다"로 나타난다. 같은 결함이 계좌 조합에 따라 돈을 만들기도 하고 없애기도 한다.

#### @Transactional을 붙였는데 왜 안 막히나

주니어가 가장 많이 하는 오해가 여기다. `@Transactional`은 **원자성**(전부 커밋되거나 전부 롤백되거나)과 **격리 수준에 따른 읽기 규칙**을 주는 것이지, "내가 읽은 값이 커밋할 때까지 그대로일 것"을 보장하지 않는다.

PostgreSQL의 기본 격리 수준은 **READ COMMITTED**다. 이 수준의 약속은 딱 하나 — "커밋되지 않은 남의 변경은 안 보여준다"이다. 위 시나리오에서 t1과 t2의 SELECT는 둘 다 커밋된 값 10,000을 읽었으므로, 규칙을 하나도 어기지 않았다. 격리 수준은 **읽기의 규칙**이지 **쓰기 순서의 보호**가 아니다.

락도 마찬가지다. 평범한 `SELECT`는 행에 락을 걸지 않는다. 락은 `UPDATE`가 실행되는 t7·t8에 가서야 잡히는데, 그때는 이미 값이 정해진 뒤다. 즉 **락이 필요한 구간(t1~t7)과 락이 걸리는 구간(t7~t9)이 어긋나 있는 것**이 이 결함의 본질이다.

#### 해법: 검사와 실행을 DB 안에서 한 문장으로 합친다

끼어들 틈을 없애는 방법은 "검사와 실행 사이의 시간"을 0으로 만드는 것이다. 자바에서 값을 계산해 내려보내는 대신, **조건과 연산을 통째로 DB에 넘겨** 한 문장으로 실행시킨다.

```java
// After: 검사·차감을 DB가 원자적으로 수행하는 조건부 UPDATE
public interface AccountRepository extends JpaRepository<Account, Long> {

    // balance = balance - :amount 는 "빼라"는 지시다. 자바가 최종값을 정하지 않으므로
    // DB가 락을 잡은 시점의 최신 balance를 기준으로 계산한다.
    // WHERE 절의 balance >= :amount 가 곧 잔액 검사다 — 검사와 차감이 한 문장 안에 있다.
    @Modifying
    @Query("UPDATE Account a SET a.balance = a.balance - :amount "
         + "WHERE a.id = :id AND a.balance >= :amount")
    int withdraw(Long id, long amount);   // 반환값 = 조건을 만족해 실제로 바뀐 행 수

    @Modifying
    @Query("UPDATE Account a SET a.balance = a.balance + :amount "
         + "WHERE a.id = :id")
    int deposit(Long id, long amount);
}

@Transactional
public void transfer(Long fromId, Long toId, long amount) {
    validate(fromId, toId, amount);                  // 2-5 참고

    // 영향 행이 0이면 WHERE 조건이 거짓이었다는 뜻 = 잔액 부족(또는 계좌 없음).
    // "조회해서 확인 후 차감"이 아니라 "차감을 시도하고 결과로 판단"하는 구조다.
    if (accountRepository.withdraw(fromId, amount) == 0) {
        throw new InsufficientBalanceException(fromId, amount);
    }
    accountRepository.deposit(toId, amount);
}
```

이제 앞의 시간축을 다시 그려보면 t3~t6이 통째로 사라진다.

```
 시각   T1 (A → B, 8,000원)                  T2 (A → C, 8,000원)
──────────────────────────────────────────────────────────────────────────
  t1   UPDATE ... balance = balance - 8000
       WHERE id = A AND balance >= 8000
       → A 행에 배타 락, 10,000 >= 8,000 참
       → balance = 2,000, 영향 행 1
  t2                                        같은 UPDATE 실행 → A 행 락 대기
  t3   COMMIT (락 해제)
  t4                                        대기 해제 → WHERE 조건을 "다시" 평가
                                            2,000 >= 8,000 → 거짓
                                            → 영향 행 0 → 잔액 부족 예외
──────────────────────────────────────────────────────────────────────────
 결과: A = 2,000 / B = +8,000 / C = 0  → 합계 10,000 보존
```

t4가 이 해법의 심장이다. PostgreSQL은 READ COMMITTED에서 `UPDATE`가 잠긴 행을 만나면, 락이 풀린 뒤 **가장 최근 커밋된 버전으로 WHERE 조건을 다시 평가한다**(내부적으로 EvaluatePlanQual이라 부르는 동작이다). 자바 변수에 박아둔 낡은 값과 달리, WHERE 절의 `balance`는 대기가 끝난 시점에 새로 읽힌다. 그래서 조건부 UPDATE는 "검사 후 실행"이 아니라 "실행하면서 검사"가 된다.

**대안 1 — 비관적 락(pessimistic lock).** "충돌이 날 것이라고 비관적으로 가정하고 미리 잠근다"는 뜻이다. `SELECT ... FOR UPDATE`(JPA에서는 `@Lock(PESSIMISTIC_WRITE)`)로 조회 시점에 아예 락을 잡아버려, 락 구간을 t1까지 앞당긴다. 검사와 실행 사이에 아무도 못 들어온다.

단, 비관적 락에는 반드시 따라오는 규칙이 하나 있다. **락 획득 순서를 계좌 id 오름차순으로 정렬**해야 한다. A→B 이체와 B→A 이체가 동시에 오면 T1은 A를 잡고 B를 기다리고, T2는 B를 잡고 A를 기다려 영원히 서로를 기다린다. 이 상태가 **교착(deadlock)**이다. "항상 작은 id부터 잠근다"는 전역 규칙을 두면, 두 트랜잭션 모두 A를 먼저 노리므로 한쪽은 그냥 기다리다 순서대로 진행된다 — 순환이 생길 수 없다.

**대안 2 — 낙관적 락(optimistic lock).** "충돌은 드물 것이라고 낙관적으로 가정하고 잠그지 않는다"는 뜻이다. 엔티티에 `@Version` 컬럼을 두고, UPDATE의 WHERE에 읽어온 버전을 넣어 그 사이 아무도 안 건드렸을 때만 성공시킨다. 바뀌었으면 예외를 던지고 호출자가 재시도한다. 충돌이 잦은 계좌 잔액에는 부적합한데, 이유는 4장 꼬리질문에서 다룬다.

**마지막 방어선 — DB 제약.** 어떤 방식을 고르든 PostgreSQL에 `CHECK (balance >= 0)`를 걸어둔다. 애플리케이션의 어떤 경로가 뚫려도, 심지어 운영자가 콘솔에서 직접 UPDATE를 날려도 음수 잔액은 커밋 자체가 불가능해진다. 코드 리뷰가 실패했을 때를 위한 층이다.

#### 리뷰어가 눈으로 찾는 시그니처

**"조회 → if 검사 → 조회값으로 산술 → set"** 시퀀스가 보이면, **"이 두 줄 사이에 다른 트랜잭션이 끼면?"** 을 기계적으로 물어라. 이 질문에 코드가 답하지 못하면 결함이다.

### 2-2. 2순위: 트랜잭션 경계 — 차감과 지급은 한 몸인가

**트랜잭션 경계**란 "어디서부터 어디까지가 전부 성공하거나 전부 실패하는 한 덩어리인가"를 가리키는 말이다. 이체에서 이 경계가 잘못 그어지면, 차감은 됐는데 지급은 안 된 상태가 **정상 종료로** 남는다. 예외도 안 나고 로그도 안 남는다.

**차감과 지급이 한 `@Transactional` 안인가.** AI가 서비스를 깔끔하게 분리하려다 차감·지급을 별도 메서드로 쪼개고 `Propagation.REQUIRES_NEW`를 붙이는 일이 있다. `REQUIRES_NEW`는 "기존 트랜잭션을 잠시 멈추고 **새 트랜잭션을 따로 시작**한다"는 뜻이라, 차감이 자기만의 트랜잭션으로 먼저 커밋된다. 이후 지급이 실패해도 차감은 되돌아가지 않는다. 차감 후 이벤트를 발행해 리스너가 지급하는 구조도 같은 문제를 만든다. 분리 자체가 나쁜 게 아니라, **분리하는 순간 부분 실패 창이 열린다는 사실을 코드가 인지하고 있는지**가 리뷰 포인트다.

**자기 호출(self-invocation) 함정.** 스프링의 `@Transactional`은 원본 객체를 감싼 **프록시(proxy, 대리 객체)**가 메서드 진입 시 트랜잭션을 열어주는 방식으로 동작한다. 그런데 같은 클래스 안에서 `this.withdraw()`를 부르면 프록시를 거치지 않고 원본 객체의 메서드로 곧장 들어가므로, **애노테이션이 있어도 트랜잭션이 열리지 않는다.** 컴파일 오류도 경고도 없어서 눈으로만 잡을 수 있고, AI 코드에 자주 나온다.

**외부 호출이 트랜잭션 안에 있는가.** 이체 완료 푸시 알림이나 타 시스템 API 호출이 트랜잭션 안에 있으면 두 가지가 동시에 망가진다. 첫째, 외부 응답을 기다리는 시간만큼 DB 커넥션과 계좌 행 락을 붙잡는다 — 트랜잭션이 열려 있는 동안 커넥션은 반납되지 않기 때문이다. 둘째, 알림은 이미 나갔는데 그 뒤 트랜잭션이 롤백되면 "이체 완료" 알림만 받고 돈은 안 들어온 **유령 알림**이 생긴다.

해법은 외부 호출을 커밋 이후로 미루는 것이다. `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`은 "이 트랜잭션이 실제로 커밋에 성공한 뒤에만 이 리스너를 실행하라"는 선언이라, 롤백된 이체는 알림도 나가지 않는다.

### 2-3. 3순위: 멱등성 — 같은 요청이 두 번 오면?

**멱등성(idempotency)**은 "같은 연산을 몇 번 반복해도 결과가 한 번 실행한 것과 같다"는 성질이다. 수학에서 온 말인데(1을 몇 번 곱해도 그대로다), 분산 시스템에서 중요한 이유는 **네트워크가 "실패"와 "응답 유실"을 구분해주지 않기 때문**이다. 클라이언트는 타임아웃이 나면 서버가 처리를 안 한 건지 처리하고 응답만 못 보낸 건지 알 수 없고, 그래서 재시도한다.

클라이언트 타임아웃 후 재시도나 더블 클릭으로 같은 이체 요청이 두 번 도착하면, 앞의 조건부 UPDATE 코드는 **두 번 다 정상적으로 성공한다.** 잔액도 충분하고 검사도 통과하니 시스템 입장에서는 서로 다른 두 건의 정당한 이체다. 8,000원 이체가 16,000원 이체가 된다.

리뷰에서 확인할 것은 두 가지다. 첫째, 이체 요청에 **클라이언트가 만든 식별자**(`transferId` 또는 HTTP 헤더의 `Idempotency-Key`)가 있는가. 서버가 만든 id는 요청마다 새로 생기므로 재시도를 구분할 수 없고, 재시도임을 아는 쪽은 클라이언트뿐이라 클라이언트가 만들어야 한다.

둘째, 그 식별자에 **유니크 제약**이 걸려 있는가. `if (exists(transferId)) return;` 같은 검사는 2-1의 check-then-act와 정확히 같은 결함이라, 두 요청이 동시에 오면 둘 다 "없음"을 보고 둘 다 진행한다. 유니크 제약을 걸고 INSERT를 먼저 시도하면, DB가 두 번째 INSERT를 원자적으로 거부한다. **검사가 아니라 유니크 제약에 의한 원자적 선점**이 핵심이다. 상세 설계는 멱등성 키 문서(09-rest-api/06)와 같다.

### 2-4. 4순위: 예외 경로 — 실패의 모양을 확인한다

지금까지가 "성공이 잘못되는" 경로였다면, 여기는 "실패가 잘못되는" 경로다.

**체크 예외(checked exception)에서 롤백이 안 된다.** 자바의 예외는 두 종류다. `RuntimeException`을 상속한 **언체크 예외**는 컴파일러가 처리를 강제하지 않고, `Exception`을 직접 상속한 **체크 예외**는 `throws` 선언이나 try-catch를 강제한다. 스프링의 `@Transactional`은 기본적으로 **언체크 예외에서만 롤백한다.** 체크 예외는 "예상된 업무 흐름"으로 간주해 롤백하지 않고 그대로 커밋한다. 그래서 이체 코드가 체크 예외를 던지는데 `@Transactional(rollbackFor = Exception.class)`가 없으면, 차감만 커밋되고 지급은 안 된 상태가 **정상 종료**로 남는다. AI 코드의 단골 함정이다.

**예외를 삼키는 catch 블록.** `catch (Exception e) { log.error(...); }`처럼 예외를 잡아 로그만 찍고 정상 흐름으로 복귀하는 코드가 있는가. 이체에서 예외를 삼키면 "차감됐는데 지급 안 된" 상태가 호출자에게 **성공으로** 보고된다. 게다가 스프링은 예외가 트랜잭션 경계 밖으로 나가야 롤백을 판단하므로, 안에서 삼켜버리면 롤백 기회 자체가 사라진다.

**이체 자체에 상태가 있는가.** REQUESTED → COMPLETED / FAILED 같은 상태 컬럼 없이 계좌 잔액만 바꾸는 구현은, 장애로 프로세스가 중간에 죽었을 때 "어디까지 됐는지"를 복구할 근거가 없다. 잔액만 봐서는 그 값이 이체 반영 전인지 후인지 판별할 방법이 없기 때문이다. 이체 이력 테이블은 감사 목적이기 전에 **복구 목적**이다.

### 2-5. 5순위: 금액 타입과 도메인 검증

마지막이지만 발견하기는 제일 쉬운, 그래서 리뷰에서 놓치면 아까운 항목들이다.

**음수 금액.** `transfer(from = A, to = B, amount = -8000)`이 들어오면 어떻게 되는지 계산해 보자. 조건부 UPDATE의 WHERE는 `balance >= -8000`이라 항상 참이고, `balance = balance - (-8000)`은 **덧셈**이 된다. A의 잔액은 8,000 늘고, `deposit`의 `balance + (-8000)`은 B에서 8,000을 뺀다. 즉 A가 B의 돈 8,000원을 **빼앗아 오는** 기능이 된다. `amount > 0` 검증은 입력 편의가 아니라 보안 통제다.

**자기 자신에게 이체.** `from == to`면 구현에 따라 결과가 달라진다. JPA 더티 체킹 방식이라면 같은 엔티티에 차감과 지급이 순서대로 적용돼 상쇄되거나, 마지막 쓰기만 남아 잔액이 늘어난다. 비관적 락 방식이라면 같은 행에 락을 두 번 잡으려 한다. 어느 쪽이든 의미 없는 연산이므로 명시적으로 거부한다.

**금액 타입.** 파라미터가 `double`이나 `float`이면 그 자체로 리젝 사유다. 이진 부동소수점은 0.1조차 정확히 담지 못해서, 금액을 저장하는 순간부터 오차가 시작된다(11번 문서에서 상세히 다룬다). 최소 화폐 단위 정수(`long`, 원·센트) 또는 `BigDecimal`이어야 한다.

### 2-6. 동시성 테스트는 이렇게 추가한다 — CountDownLatch

리뷰 코멘트로 끝내면 다음 사람이 같은 코드를 다시 쓴다. 결함을 **재현하는 테스트를 머지 조건으로** 걸어야 재발이 막힌다.

문제는 동시성 테스트가 잘 실패하지 않는다는 데 있다. 스레드 두 개를 그냥 띄우면 첫 번째가 시작해서 끝날 때까지 두 번째가 준비도 못 끝내는 일이 흔해서, 정작 겹쳐야 할 구간이 안 겹친다. 그래서 두 스레드를 **출발선에 세워놓고 동시에 출발시키는** 장치가 필요하다.

`CountDownLatch`가 그 장치다. "카운트가 0이 될 때까지 기다리는 문(latch)"이라는 뜻으로, 정해진 숫자로 만들어 두면 `await()`를 부른 스레드는 그 숫자가 `countDown()`으로 0이 될 때까지 멈춰 선다. 아래 테스트는 이걸 세 개 쓴다 — 전원이 준비됐음을 알리는 문, 출발 총성 역할의 문, 전원이 끝났음을 알리는 문이다.

```java
@Test
void 잔액_1만원_계좌에_8천원_동시_이체_2건은_1건만_성공한다()
        throws Exception {
    int threads = 2;
    ExecutorService pool = Executors.newFixedThreadPool(threads);

    CountDownLatch ready = new CountDownLatch(threads); // 2가 0이 되면 전원 준비 완료
    CountDownLatch start = new CountDownLatch(1);       // 1이 0이 되면 출발 총성
    CountDownLatch done  = new CountDownLatch(threads); // 2가 0이 되면 전원 종료
    AtomicInteger success = new AtomicInteger();        // 여러 스레드가 함께 세므로 원자적 카운터

    for (int i = 0; i < threads; i++) {
        pool.submit(() -> {
            try {
                ready.countDown();   // "나 준비됐다"
                start.await();       // 총성이 울릴 때까지 대기 — 이 줄이 겹침을 만든다
                transferService.transfer(FROM, TO, 8_000L);
                success.incrementAndGet();
            } catch (InsufficientBalanceException expected) {
                // 잔액 부족 실패는 기대한 결과다. 성공 카운트만 올리지 않는다.
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();   // 인터럽트 상태 복원
            } finally {
                done.countDown();    // 성공이든 실패든 반드시 내려야 본 스레드가 안 멈춘다
            }
        });
    }
    ready.await();       // 두 스레드가 출발선에 설 때까지 기다린다
    start.countDown();   // 총성 — 여기서 두 스레드가 거의 같은 순간 transfer()에 진입한다
    done.await();        // 둘 다 끝날 때까지 기다린 뒤 검증한다

    assertThat(success.get()).isEqualTo(1);          // 두 건 중 정확히 한 건만 성공
    assertThat(balanceOf(FROM)).isEqualTo(2_000L);   // 10,000 - 8,000
    assertThat(balanceOf(TO)).isEqualTo(8_000L);     // 8,000 × 1건. 16,000이면 갱신 유실
}
```

주의할 점이 하나 있다. 이 테스트는 **실제 PostgreSQL 위에서** 돌려야 한다. H2 같은 인메모리 DB는 편하지만 락 동작과 격리 수준의 세부 구현이 PostgreSQL과 달라서, 결함이 재현되지 않은 채 초록불이 나올 수 있다 — 그러면 이 테스트는 안전하다는 착각만 늘린다. **Testcontainers**(테스트 실행 시 도커로 진짜 DB 컨테이너를 띄웠다가 끝나면 지우는 라이브러리)로 운영과 같은 PostgreSQL 버전을 띄우는 것이 정석이다.

이 다섯 단계를 팀의 **돈 코드 리뷰 체크리스트**로 고정하면, AI 산출물 리뷰가 사람의 감이 아니라 재현 가능한 절차가 된다.

## 3. 실무 사례 — 테스트 전부 통과 후에 터지는 방식

### 사례 1: 프로모션 트래픽에서 드러난 갱신 유실

포인트 선물하기 기능을 AI로 생성해 배포했다. 테스트 34건 전부 통과, 스테이징 QA도 통과했다. 스테이징이 통과한 이유는 명확했다 — 거기엔 동시 요청이 없었다. QA 담당자 한 명이 순서대로 눌러보는 환경에서 인터리빙은 발생하지 않는다.

이벤트 당일, 잔액 10,000포인트 계좌에서 더블 클릭으로 8,000포인트 선물 요청 2건이 30ms 간격으로 도착했다. 두 트랜잭션 모두 잔액 검사를 통과했다. 이 시스템은 차감만 check-then-act였고 지급은 `balance = balance + :amount` 증분 UPDATE였던 탓에, 지급 두 건은 모두 반영되고 차감 한 건만 사라졌다.

결과를 합계로 검산하면 이렇다.

| 항목 | 이벤트 전 | 정상이었다면 | 실제 |
|---|---|---|---|
| 보내는 계좌 | 10,000 | 2,000 | 2,000 |
| 받는 계좌 | 0 | 8,000 | 16,000 |
| **합계** | **10,000** | **10,000** | **18,000** |

차이 8,000포인트가 발행 근거 없이 생성된 부채다. 하루 집계에서 발행 포인트 총액과 차감 포인트 총액이 맞지 않아 발견됐고, 건별 대사로 8,000포인트 × 수백 건을 수작업 회수했다. 결함은 check-then-act 한 줄이었고, 34건의 테스트 중 두 스레드를 동시에 돌린 것은 하나도 없었다.

### 사례 2: 트랜잭션 안의 알림 호출이 이체 전체를 세웠다

AI가 생성한 코드는 이체 커밋 전에 알림 API를 호출했다. 평소엔 응답이 50ms라 아무도 문제를 못 느꼈다.

알림사 장애로 응답이 5초로 늘어난 날, 각 이체 트랜잭션이 5초씩 DB 커넥션과 계좌 행 락을 붙잡았다. 트랜잭션이 열려 있는 동안 커넥션은 반납되지 않으므로, 기본 10개짜리 커넥션 풀이 곧바로 고갈됐다. 알림과 아무 관련 없는 이체 요청까지 전부 커넥션을 못 받아 타임아웃 — **외부사 장애가 코어 이체 장애로 전파됐다.**

여기에 두 번째 피해가 겹쳤다. 타임아웃으로 롤백된 이체들에서도 알림은 이미 나간 뒤였다. 고객은 "8,000포인트 이체 완료" 알림을 받았는데 포인트는 안 들어왔고, CS가 함께 터졌다. 알림을 `AFTER_COMMIT` 이벤트로 빼는 한 줄 리뷰로 둘 다 막을 수 있었던 장애다.

### 사례 3: 맞이체 교착 — PostgreSQL이 한쪽을 강제 롤백

동시성 결함을 고치면서 비관적 락으로 바꿨는데, 락 획득 순서를 정하지 않았다. A→B 8,000원 이체와 B→A 5,000원 이체가 동시에 실행됐다.

```
 시각   T1 (A → B)                   T2 (B → A)
────────────────────────────────────────────────────────────
  t1   A 행 락 획득
  t2                                 B 행 락 획득
  t3   B 행 락 요청 → T2가 쥠, 대기
  t4                                 A 행 락 요청 → T1이 쥠, 대기
       ─── 서로가 서로를 영원히 기다린다 = 교착 ───
```

PostgreSQL은 이런 순환 대기를 주기적으로 탐지해 한쪽을 `ERROR: deadlock detected`로 강제 롤백한다. DB가 알아서 풀어주는 셈이지만, 애플리케이션에 재시도 로직이 없어 사용자에게는 500 에러가 그대로 노출됐다.

수정은 **락 획득을 계좌 id 오름차순으로 정렬**하는 것이었다. 두 트랜잭션 모두 작은 id를 먼저 노리므로 t1에서 한쪽이 이기고 다른 쪽은 처음부터 기다린다 — 순환이 만들어질 수 없으니 교착이 발생 자체를 안 한다. "두 자원을 잠그는 코드는 잠그는 순서가 전역적으로 일정한가"도 그 뒤로 체크리스트 항목이 됐다.

## 4. 꼬리질문 대비 포인트

### "AI가 테스트도 잘 짜던데, 커버리지 90%면 부족한가요?"

커버리지는 "테스트가 실행한 라인의 비율"이지 "검증된 시나리오의 비율"이 아니다. 이 둘의 차이가 동시성에서 극단적으로 드러난다.

2-1의 check-then-act 코드는 라인 커버리지 100%에서도 초록불이다. 결함이 특정 라인에 있는 게 아니라 **라인들 사이의 실행 순서 겹침(인터리빙)** 에 있기 때문이다. 단일 스레드 테스트는 인터리빙을 하나도 만들지 않으므로, 아무리 여러 번 실행해도 이 축의 커버리지는 영원히 0이다.

게다가 구현과 테스트가 같은 출처면 맹점을 공유하므로, 커버리지가 높을수록 "충분히 검증됐다"는 착시만 강해진다. 숫자 대신 **시나리오 목록**(동시 2건, 재시도, 부분 실패, 음수 금액)의 유무로 판단한다고 답한다.

### "동시성 결함을 코드 리뷰에서 눈으로 어떻게 찾나요?"

감이 아니라 패턴 매칭이다. 네 가지 형태만 외워두면 대부분 걸린다.

1. **조회 → if 검사 → 조회값 산술 → set** 시퀀스 (check-then-act)
2. 잔액·재고·쿠폰 수량처럼 **공유되는 숫자를 읽어서 계산 후 쓰는** 모든 지점
3. `existsBy...` 검사 후 `save` — 유니크 제약 없는 중복 검사 (2-3의 멱등성과 같은 결함)
4. 두 자원을 잠그는데 **순서 규칙이 없는** 코드 (교착 후보)

이런 지점마다 던지는 질문은 하나다. "**이 줄과 저 줄 사이에 똑같은 코드가 한 번 더 끼어들면 어떻게 되나?**" 답이 "돈이 새거나 불변식이 깨진다"면, 원자적 연산(조건부 UPDATE, 유니크 제약, 락)으로 바꾸게 한다.

### "비관적 락, 낙관적 락, 조건부 UPDATE 중 뭘 고르나요?" (시니어 변별 포인트)

세 가지가 서로 다른 가정 위에 서 있다는 것부터 정리하면 답이 나온다. 낙관적 락은 "충돌이 드물다", 비관적 락은 "충돌이 잦으니 미리 막는다", 조건부 UPDATE는 "충돌 여부와 무관하게 검사와 실행을 붙여버린다"는 가정이다. 그래서 선택 기준은 **충돌 빈도와 실패 비용**이다.

계좌 잔액은 인기 계좌(hot row, 쓰기가 몰리는 한 행)에 요청이 집중되고 실패 비용(음수 잔액)이 크다. 그래서 **낙관적 락은 부적합**하다 — 충돌할 때마다 예외를 던지고 재시도하는데, 충돌이 잦으면 재시도가 또 충돌해서 처리량이 오히려 무너진다. 낙관적 락은 충돌이 드물 때만 이득인 구조다.

기본기는 **조건부 UPDATE**다. 락 점유 시간이 SQL 한 문장 실행 시간으로 최소화되고, 검사와 갱신이 원자적이다. 단점은 도메인 로직이 SQL로 새어나가고 JPA 더티 체킹과 결이 안 맞는다는 점이라, **잔액 같은 핵심 불변식만** `@Modifying` 쿼리로 내리고 나머지는 평범한 엔티티로 다루는 절충을 쓴다.

여러 행을 함께 잠그고 그 위에서 복잡한 검증을 해야 하면 **비관적 락 + id 오름차순 잠금**이다. 그리고 어떤 선택을 하든 `CHECK (balance >= 0)`를 DB에 두는 것까지 말하면, 방어선을 하나가 아니라 층으로 설계한다는 인상을 준다.

### "차감과 지급을 다른 마이크로서비스가 담당하면요?"

"한 DB 트랜잭션"이라는 전제가 통째로 무너진다. 서로 다른 DB를 쓰는 두 서비스에 `@Transactional`을 걸어봐야 각자의 트랜잭션일 뿐, 한쪽 롤백이 다른 쪽을 되돌리지 못한다.

이때는 두 가지 도구가 필요하다. 첫째 **아웃박스(outbox) 패턴** — "차감"과 "지급 요청 메시지 저장"을 같은 DB의 한 트랜잭션으로 묶어 커밋한 뒤, 별도 프로세스가 그 메시지 테이블을 읽어 실제로 발행한다. DB 커밋과 메시지 발행이 따로 놀아서 생기는 유실을 없애는 장치다. 둘째 **보상 트랜잭션(사가, saga)** — 지급이 최종 실패하면 차감을 되돌리는 반대 방향 연산을 실행한다. 되돌리는 것이지 롤백이 아니므로, 이미 커밋된 차감 위에 "차감 취소"라는 새 기록이 쌓인다.

그러면 이체는 REQUESTED → WITHDRAWN → COMPLETED / COMPENSATED의 **상태 머신**이 되고, 각 단계는 반드시 멱등해야 한다(메시지는 중복 전달될 수 있으므로). 이 질문의 핵심은 "`@Transactional`을 어디에 붙이나"가 아니라 "**원자성 경계가 프로세스를 넘는 순간 설계가 통째로 달라진다**"를 아는지다.

### "이 검증을 팀 프로세스로 만든다면 어떻게 하나요?" (시니어 변별 포인트)

개인기를 절차로 바꾸는 것이 답이다. 사람의 집중력에 의존하는 리뷰는 바쁜 날 반드시 뚫린다.

1. **PR 템플릿으로 체크리스트를 강제한다.** 돈을 다루는 모듈의 PR에는 5단계(동시성·트랜잭션 경계·멱등성·예외 경로·금액 검증) 항목을 체크하지 않으면 리뷰 요청이 안 되게 한다.
2. **동시성 테스트를 머지 조건으로 둔다.** CountDownLatch + Testcontainers 테스트가 없는 잔액 변경 PR은 CI에서 막는다.
3. **사람이 놓치는 것은 정적 규칙으로 내린다.** ArchUnit(자바 코드의 구조 규칙을 테스트로 검증하는 라이브러리)으로 "트랜잭션 메서드 안에서 외부 HTTP 클라이언트 호출 금지", "money 패키지에서 double·float 타입 금지" 같은 규칙을 CI에 넣으면, 리뷰어의 기억력이 아니라 빌드가 막아준다.
4. **DB 레벨 CHECK·유니크 제약을 항상 요구한다.** 앞의 셋이 전부 실패했을 때의 마지막 방어선이다.

마무리로 "AI가 코드 생산 속도를 높일수록, 리뷰는 사람의 눈이 아니라 자동화된 관문에 얹혀야 지속 가능하다"까지 말하면 좋다. 생산량이 10배가 되면 사람 리뷰는 10배가 될 수 없다는 것이 이 문제의 구조적 본질이다.

## 한 줄 요약

AI 이체 코드의 "테스트 전부 통과"는 행복 경로의 증명일 뿐이므로, 테스트에 원천적으로 없는 것 — **동시성(check-then-act, 잔액 음수) → 트랜잭션 경계(차감·지급 원자성, 트랜잭션 안 외부 호출) → 멱등성(재시도 이중 이체) → 예외 경로(부분 실패 상태) → 금액 검증(음수·자기 이체)** — 순으로 리뷰하고, 결함은 코멘트가 아니라 CountDownLatch 동시성 테스트와 DB 제약으로 재발 불가능하게 박아 넣은 뒤에 머지한다.
