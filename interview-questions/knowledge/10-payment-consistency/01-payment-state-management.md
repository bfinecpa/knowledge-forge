# 결제 상태 관리 — 결제의 본질은 성공/실패가 아니라 "그 사이"다

> 핵심 관전 포인트: **결제를 `is_paid` 같은 이진(boolean) 값으로 모델링한 시스템은 타임아웃 앞에서 반드시 무너진다 — 결제는 "요청한 순간"과 "확정된 순간" 사이에 시간이 존재하는 작업이고, 그 사이 어디서든 서버는 죽고 네트워크는 끊긴다. 그래서 상태를 READY → IN_PROGRESS → APPROVED/FAILED처럼 열거형으로 명시하고, "어느 상태에서 어느 상태로 갈 수 있는가"(허용 전이)를 코드와 DB 양쪽에서 강제해야 한다. 특히 결과를 모르는 UNKNOWN 같은 중간 상태를 일급 시민으로 두는 것이 핵심이다 — 모르는 것을 실패로 기록하는 순간 이중 결제가 시작된다. 상태 컬럼은 조건부 UPDATE(또는 낙관적 락)로 동시 변경을 차단하고, 모든 전이는 append-only 이력 테이블에 남겨 "이 결제가 왜 이 상태인가"를 언제든 재구성할 수 있어야 한다.**

---

## 0. 질문 + 의도

**질문**: "결제 흐름(요청 → 승인 → 완료)을 설계할 때 상태 관리는 어떻게 하나요?"

**출제 의도**: 결제는 "요청과 완료 사이"의 중간 상태가 본질이다. 상태를 성공/실패 이진으로 모델링한 시스템은 타임아웃과 지연 승인 앞에서 반드시 무너진다 — 돈을 다루는 시스템 설계의 첫 관문으로, 지원자가 중간 상태와 상태 전이를 어떻게 다루는지 본다.

---

## 1. 왜 이진 모델은 반드시 무너지는가

### 1-1. 먼저 등장인물부터 — 결제 문장에 나오는 다섯 단어

결제 이야기는 낯선 명사가 한꺼번에 쏟아지기 때문에, 설계를 보기 전에 용어부터 한 문장씩 정리하고 가자. 이 다섯 개만 알면 이 문서 전체를 읽을 수 있다.

**PG사(Payment Gateway, 결제대행사)** 는 우리 서버와 카드사 사이에 서서 카드사 연동을 대신 해주는 회사다. 토스페이먼츠·나이스페이먼츠·KG이니시스 같은 곳이다. 카드사와 직접 연동하려면 카드사마다 규격이 다르고 보안 심사도 따로 받아야 하는데, PG사가 그 복잡함을 하나의 HTTP API로 감싸준다. 우리 코드 입장에서 "결제"란 대부분 **PG사의 API를 호출하는 일**이다.

**승인(authorization)** 은 카드사가 "이 카드로 이 금액을 결제해도 좋다"고 확인해주고, 그 금액만큼 고객의 카드 한도를 잡아두는 절차다. 고객 휴대폰에 뜨는 "50,000원 승인" 문자가 바로 이 시점이다. 이 문서에서 "결제가 성공했다"는 말은 거의 항상 "승인이 났다"는 뜻이다.

**매입(capture)·정산(settlement)** 은 승인된 건을 실제 청구로 확정하고(매입), 며칠 뒤 가맹점 계좌로 돈이 들어오는(정산) 후속 절차다. 자세한 내용은 이 문서의 범위 밖이지만 딱 하나만 기억하면 된다 — **승인 직후에는 취소가 쉽고, 정산이 끝난 뒤에는 어렵다.** 뒤에 나오는 망취소와 환불 이야기가 이 차이에서 나온다.

**웹훅(webhook)** 은 우리가 상대 서버를 호출하는 게 아니라, 상대 서버가 우리 서버의 특정 URL로 **먼저 HTTP 요청을 보내오는** 방식이다. "결과가 나오면 이 번호로 전화 주세요" 하고 연락처를 남겨두는 것과 같다. PG사는 승인 결과나 입금 사실을 이 방식으로 우리에게 알려준다.

**배치(batch)** 는 사용자 요청과 무관하게 주기적으로(예: 1분마다) 도는 백그라운드 작업이다. 이 문서에서는 "결과를 모르는 결제를 다시 확인하는 배치", "오래된 결제를 정리하는 배치"가 계속 등장한다. 배치가 중요한 이유는 뒤에서 보겠지만, **배치도 결제 행을 UPDATE하는 또 하나의 경쟁자**이기 때문이다.

### 1-2. 결제는 "한순간의 사건"이 아니라 "구간이 있는 과정"이다

CRUD API를 만들 때 우리는 보통 요청 하나가 성공 아니면 실패로 끝난다고 전제한다. `POST /articles`가 200을 주면 글이 저장된 것이고, 500을 주면 저장 안 된 것이다. 다시 누르면 그만이다.

결제는 이 전제가 성립하지 않는다. 결제 한 건이 지나가는 경로를 시간축에 펼쳐보면 이렇다.

```
[클라이언트]        [우리 서버]              [PG사]            [카드사]
     │                  │                     │                 │
  ① 결제 요청 ────────> │                     │                 │
     │             결제 행 생성                │                 │
     │                  │ ── ② 승인 API ────> │ ── 승인 요청 ──> │
     │                  │                     │                 │
     │                  │                     │ <── 승인 응답 ── │
     │                  │ <── ③ 승인 결과 ─── │                 │
     │             ④ 주문 완료 처리            │                 │
     │ <── 결과 응답 ─── │                     │                 │
```

여기서 중요한 건 화살표가 아니라 **화살표 사이의 빈칸**이다. ①과 ② 사이, ②와 ③ 사이, ③과 ④ 사이에는 전부 실제 시간이 흐르고, 그 틈마다 사고가 난다.

| 사고 지점 | 벌어지는 일 | 그때 우리 DB의 상태 | 실제 세상의 상태 |
|---|---|---|---|
| ② 직후 서버 재시작 | 배포·OOM·인스턴스 교체 | 아무 결과도 안 적힘 | PG는 승인을 냈을 수 있음 |
| ③ 응답 타임아웃 | 10초 안에 응답이 안 옴 | 결과 모름 | 승인됐는지 아닌지 우리는 모름 |
| ④ 주문 처리 중 예외 | 재고 부족·NPE·커넥션 부족 | 결제는 승인, 주문은 없음 | 카드에서 돈이 빠져나감 |

세 칸 모두 공통점이 하나 있다. **우리 DB가 아는 사실과 카드사가 아는 사실이 어긋나 있다.** 그리고 그 어긋남을 표현할 수 있느냐가 이 문서 전체의 주제다.

### 1-3. `is_paid boolean`은 "모른다"를 적을 칸이 없다

가장 흔한 첫 설계는 주문 테이블에 `is_paid boolean` 컬럼 하나를 두는 것이다. 이게 왜 무너지는지 구체적으로 보자.

PG 승인 호출이 10초 타임아웃으로 끊겼다고 하자. 우리 코드는 `catch` 블록에서 뭔가를 적어야 한다. 선택지는 둘뿐이다.

**선택지 A — `is_paid = false`로 적는다.** 화면에는 "결제 실패"가 뜬다. 그런데 실제로는 카드에서 50,000원이 빠져나갔을 수 있다. 응답이 안 온 것과 승인이 안 난 것은 전혀 다른 사실인데, 이 컬럼은 둘을 구분할 수 없다. 고객은 실패 화면을 보고 다시 결제한다. **이중 결제의 탄생이다.**

**선택지 B — 낙관적으로 `is_paid = true`로 적는다.** 이번엔 반대 방향으로 터진다. 승인이 실제로 실패했다면 돈은 안 나갔는데 이용권은 지급된다. 회사가 손해를 본다.

즉 이진 모델에서는 타임아웃을 만난 순간 **어느 쪽으로 적어도 틀린다.** 문제의 뿌리는 컬럼의 이름이나 타입이 아니다.

> **이진 모델의 진짜 문제는 "모른다"를 표현할 자리가 없다는 것이다.**

이걸 표로 보면 명확하다. 세로가 실제 세상의 사실, 가로가 우리가 기록한 값이다.

| | 우리 기록: false | 우리 기록: true |
|---|---|---|
| **실제: 승인됨** | 이중 결제 (고객이 재시도) | 정상 |
| **실제: 승인 안 됨** | 정상 | 미수금 (돈 없이 혜택 지급) |
| **실제: 모름** | 적을 칸이 없음 → 도박 | 적을 칸이 없음 → 도박 |

마지막 줄이 핵심이다. 세상에는 세 가지 사실이 있는데 우리 모델에는 두 칸밖에 없다. 칸이 모자라면 사람은 반드시 아무 칸에나 밀어 넣게 되고, 그 순간부터 그 데이터는 거짓말을 하기 시작한다.

### 1-4. 비유 — 택배 조회에 "배송됨/안 됨" 두 칸만 있다면

택배 조회 화면이 "배송 완료 / 미배송" 둘뿐이라고 상상해보라. 물건이 간선 터미널에서 이동 중일 때 시스템은 뭐라고 말해야 하나. "미배송"이라고 하면 고객은 재주문하고, "완료"라고 하면 못 받은 고객이 항의한다.

그래서 실제 택배 시스템은 접수·집화·이동중·배송출발·완료라는 **중간 상태들을 일급으로** 둔다. 여기서 "일급(first-class)"이란 그 상태가 "임시로 끼워 넣은 예외"가 아니라 **조회 화면·통계·알림·정산이 모두 정식으로 취급하는 정규 상태**라는 뜻이다.

결제도 완전히 같다 — 돈이 "이동 중"인 구간을 표현할 상태가 반드시 필요하고, 그 상태는 예외가 아니라 정상 설계의 일부여야 한다.

## 2. 설계 — 상태 열거, 허용 전이, 그리고 강제

### 2-1. 상태 머신이 무엇인지부터

**상태 머신(state machine)** 은 시스템을 두 개의 목록으로 서술하는 방식이다.

1. 이 시스템이 가질 수 있는 **상태의 목록** (유한하고, 전부 이름이 있다)
2. 어떤 상태에서 어떤 상태로 갈 수 있는가라는 **허용 전이의 목록**

이 두 목록에 없는 것은 전부 금지다. 이게 상태 머신의 힘이다. "무엇을 허용할지"만 적으면 나머지 전부가 자동으로 금지되므로, 개발자가 미처 상상하지 못한 이상한 전이까지 한꺼번에 막힌다.

신호등이 교과서 예시다. 상태는 빨강·노랑·초록 셋이고, 허용 전이는 빨강→초록, 초록→노랑, 노랑→빨강 셋뿐이다. 빨강에서 노랑으로 바로 가는 전이는 "정의되지 않았으므로 불가능"이다. 별도의 if문으로 막는 게 아니라, **허용 목록에 없다는 사실 자체가 금지**다.

### 2-2. 결제의 상태를 열거하고 허용 전이를 그린다

카드 결제 기준 최소 상태 집합과 전이는 다음과 같다.

```
                      ┌────────> APPROVED ──────> CANCELED
                      │             ▲
READY ──> IN_PROGRESS ┼────────> FAILED
  │                   │             ▲
  │                   └──> UNKNOWN ─┴──> APPROVED
  │
  └──> EXPIRED
```

화살표만으로는 각 상태가 "돈의 관점에서 무슨 뜻인지"가 안 보이므로 표로 한 번 더 정리한다.

| 상태 | 돈의 관점에서의 의미 | 누가 이 상태로 바꾸나 | 다음 가능 상태 |
|---|---|---|---|
| `READY` | 아직 돈과 무관. 결제 행만 만들어둠 | 결제 요청 API | `IN_PROGRESS`, `EXPIRED` |
| `IN_PROGRESS` | **지금 돈이 움직이고 있을지 모름** | 승인 API 호출 직전 | `APPROVED`, `FAILED`, `UNKNOWN` |
| `APPROVED` | 승인 확정. 돈이 나갔음 | 승인 응답 / 웹훅 / 조회 배치 | `CANCELED` |
| `FAILED` | 거절 **확정**. 돈이 안 나갔음 | 승인 응답 / 조회 배치 | 없음 (종결) |
| `UNKNOWN` | **났는지 안 났는지 모름** | 타임아웃·5xx 처리 경로 | `APPROVED`, `FAILED` |
| `CANCELED` | 승인을 되돌림 | 취소 API | 없음 (종결) |
| `EXPIRED` | 결제창만 띄우고 이탈 | 정리 배치 | 없음 (종결) |

각 상태를 하나씩 풀어보자.

**READY** 는 결제 행을 DB에 만들었지만 아직 PG를 부르기 전이다. 돈과 아무 관계가 없는 안전한 상태다. 이 상태가 왜 필요하냐면, 우리 결제 식별자(payment id)를 **PG를 부르기 전에** 확보해두어야 나중에 "그 호출이 어떤 결제였는지"를 되짚을 수 있기 때문이다.

**IN_PROGRESS** 는 승인 API를 호출한 순간부터 응답을 반영하기 전까지의 상태다. 이 상태의 존재 자체가 곧 **"지금 이 건의 돈이 움직이고 있을지도 모른다"는 표식**이다. 서버가 이 순간 죽어도, 재기동 후 IN_PROGRESS로 남아 있는 행을 보고 "얘는 확인이 필요하다"를 알 수 있다.

**APPROVED** 는 PG가 승인을 확정한 상태다. 여기서 갈 수 있는 유일한 다음 상태는 CANCELED뿐이다 — 승인된 결제가 다시 IN_PROGRESS로 돌아가는 일은 존재할 수 없다.

**FAILED** 는 PG가 거절을 **확정**한 상태다. 잔액 부족, 한도 초과, 카드 정지 같은 명시적 거절 사유가 왔을 때만 여기로 간다. 재시도는 이 행을 다시 살리는 게 아니라 **새 결제 행**으로 한다. 이유는 단순하다. 한 행이 FAILED에서 APPROVED로 갔다가 또 FAILED로 가면, 그 행의 이력은 더 이상 하나의 사실을 가리키지 않는다.

**UNKNOWN** 이 이 문서 전체에서 가장 중요한 상태다. 타임아웃, 5xx, 커넥션 끊김처럼 **결과를 모르는** 상황이 여기로 온다. FAILED와 절대 섞으면 안 된다.

- `FAILED` = "안 됐음이 **확정**됐다"
- `UNKNOWN` = "됐는지 안 됐는지 **모른다**"

한국어로는 둘 다 "결제 안 됐다"로 말하게 되지만, 시스템이 해야 할 후속 행동이 정반대다. FAILED는 아무것도 안 해도 되고, UNKNOWN은 **반드시 누군가 다시 확인해야 한다.** UNKNOWN은 이후 PG 거래 조회 API로 실제 결과를 물어봐서 APPROVED 또는 FAILED로 **해소(resolve)** 된다.

**EXPIRED** 는 결제창만 띄우고 이탈한 건을 배치로 정리하는 종결 상태다. 이게 없으면 READY 행이 영원히 쌓인다.

핵심 규칙 하나: **전이는 화살표가 그려진 방향만 허용한다.** APPROVED에서 IN_PROGRESS로 되돌아가는 전이, FAILED에서 APPROVED로 건너뛰는 전이는 코드가 물리적으로 거부해야 한다. "설마 그런 코드를 짜겠어"라고 생각하기 쉽지만, 실제로는 배치·웹훅 핸들러·어드민 API가 각자 상태를 바꾸다 보면 반드시 벌어진다(3절 사례 2가 정확히 그 이야기다).

### 2-3. 상태 머신을 코드로 강제한다

가장 흔한 실패는 상태를 "그냥 세터로 바꿀 수 있는 필드"로 두는 것이다.

```java
// Before: 상태가 그냥 문자열 필드 — 어디서든 아무 값으로나 바뀐다
@Entity
public class Payment {
    @Enumerated(EnumType.STRING)
    private PaymentStatus status;

    public void setStatus(PaymentStatus status) {  // 무방비
        this.status = status;
    }
}

// 어딘가의 서비스 코드
payment.setStatus(PaymentStatus.APPROVED);
// 웹훅 핸들러, 배치, 관리자 API가 각자 setStatus를 부른다.
// APPROVED였던 건을 배치가 EXPIRED로 덮어써도 컴파일러도 DB도 모른다.
```

이 코드의 문제를 정확히 짚자. `setStatus`는 **"현재 상태가 무엇인지"를 전혀 보지 않는다.** 인자로 받은 값을 그대로 대입할 뿐이다. 그래서 이 메서드를 부르는 모든 호출부가 각자 알아서 "지금 상태가 바꿔도 되는 상태인지"를 검사해야 하는데, 호출부는 시간이 지나면서 계속 늘어난다. 검사를 빠뜨린 호출부가 **하나만 있어도** 상태 머신은 뚫린다.

해결의 방향은 이렇다 — **검사를 호출부에서 거둬들여 상태 자신에게 맡긴다.** 허용 전이 목록을 enum이 소유하고, 엔티티는 검사를 통과해야만 지나갈 수 있는 전이 메서드 하나만 외부에 연다.

```java
// After: enum이 허용 전이를 소유하고, 엔티티는 전이 메서드만 연다
public enum PaymentStatus {
    // 괄호 안이 "여기서 갈 수 있는 다음 상태" 목록.
    // 이 목록에 없으면 전부 금지 — 화이트리스트 방식이다.
    READY(Set.of("IN_PROGRESS", "EXPIRED")),
    IN_PROGRESS(Set.of("APPROVED", "FAILED", "UNKNOWN")),
    UNKNOWN(Set.of("APPROVED", "FAILED")),
    APPROVED(Set.of("CANCELED")),
    // 아래 셋은 종결 상태 — 빈 집합이라 어디로도 못 나간다
    FAILED(Set.of()), CANCELED(Set.of()), EXPIRED(Set.of());

    private final Set<String> nextStates;

    PaymentStatus(Set<String> nextStates) {
        this.nextStates = nextStates;
    }

    public boolean canTransitionTo(PaymentStatus next) {
        return nextStates.contains(next.name());
    }
}

@Entity
public class Payment {
    @Enumerated(EnumType.STRING)
    private PaymentStatus status;

    @Version
    private long version;   // 낙관적 락. 왜 필요한지는 2-4에서

    // 상태를 바꾸는 유일한 통로. 이름부터 "전이"라고 못박아
    // 호출부가 "그냥 값 대입"으로 착각하지 못하게 한다.
    public void transitionTo(PaymentStatus next, String reason) {
        if (!status.canTransitionTo(next)) {
            // 조용히 무시하지 않고 예외를 던진다.
            // 잘못된 전이가 소리 없이 성공하면 며칠 뒤 정산에서 발견되고,
            // 그때는 이미 원인 추적이 불가능하다.
            throw new IllegalPaymentStateException(
                "%s -> %s 전이 불가 (paymentId=%d)"
                    .formatted(status, next, id));
        }
        this.status = next;
        // 이력 기록은 2-5에서 추가한다
    }
    // setStatus는 존재하지 않는다 — 우회로를 아예 만들지 않는다
}
```

이렇게 하면 "취소 배치가 승인 건을 만료 처리"하는 류의 버그가 런타임 예외로 즉시 드러난다. 여기서 원칙을 하나 뽑을 수 있다.

> 잘못된 전이가 **조용히 성공하는 것**이 결제 시스템 최악의 버그다. 시끄럽게 실패하게 만들어야 한다.

왜 "조용한 성공"이 최악인가. 시끄러운 실패는 에러 로그와 알림을 남기고, 그날 안에 누군가 본다. 조용한 성공은 아무 흔적도 없이 잘못된 데이터를 남기고, 보통 **한 달 뒤 정산 대사에서** 발견된다. 그때는 관련 로그도 지워졌고, 영향받은 건수는 수백 건으로 불어나 있다.

### 2-4. DB에서도 강제한다 — 애플리케이션 검증만으론 부족하다

여기서 많은 사람이 "enum으로 막았으니 끝난 거 아닌가?"라고 생각한다. 아니다. 그 이유를 이해하려면 먼저 lost update를 봐야 한다.

#### 전제 지식 — lost update(갱신 유실)

두 요청이 같은 행을 동시에 읽고 각자 UPDATE하면, 뒤에 커밋한 쪽이 앞 쪽의 결과를 통째로 덮어쓴다. 앞의 갱신이 사라지므로 **lost update**라고 부른다.

시간축으로 보면 이렇다. 결제 4211번이 지금 IN_PROGRESS라고 하자.

```
시각   [웹훅 핸들러 트랜잭션]            [조회 배치 트랜잭션]
 t1    SELECT status → IN_PROGRESS
 t2                                     SELECT status → IN_PROGRESS
 t3    canTransitionTo(APPROVED) → true
 t4                                     canTransitionTo(FAILED) → true
 t5    UPDATE ... SET status='APPROVED'
 t6    COMMIT
 t7                                     UPDATE ... SET status='FAILED'
 t8                                     COMMIT   ← APPROVED를 덮어씀
```

두 트랜잭션 **모두 애플리케이션 검증을 통과했다.** 각자가 t1, t2에서 읽은 시점에는 정말로 IN_PROGRESS였기 때문이다. 검증 자체는 틀리지 않았는데 결과가 틀렸다. 이게 애플리케이션 검증의 한계다.

> 애플리케이션 검증은 **"읽은 시점의 상태"** 에 대한 검증이다. 우리에게 필요한 건 **"쓰는 시점의 상태"** 에 대한 검증이다.

읽기와 쓰기 사이의 틈을 없앨 수 있는 곳은 DB뿐이다. DB는 UPDATE 한 문장을 실행하는 동안 그 행에 락을 걸어 다른 트랜잭션을 줄 세우기 때문이다. 그래서 마지막 방어선은 DB고, 방법은 두 가지다.

#### 방법 1 — 낙관적 락(optimistic lock)

**낙관적 락**은 "충돌은 잘 안 날 거야"라고 낙관하고 일단 진행하되, **쓰는 순간에 충돌이 있었는지 확인하는** 방식이다. 이름의 '낙관'은 "미리 막지 않는다"는 뜻이다.

동작 원리는 단순하다. 행마다 `version` 숫자를 하나 두고, UPDATE할 때 "내가 읽었을 때의 버전과 지금 DB의 버전이 같을 때만" 갱신한다.

```sql
-- JPA가 @Version 필드를 보고 실제로 만들어 보내는 UPDATE
UPDATE payment
   SET status = 'APPROVED', version = 8
 WHERE id = 4211
   AND version = 7;   -- 내가 읽었을 때 7이었다는 사실을 조건으로 건다
```

위 시나리오에서 웹훅이 먼저 커밋하면 version이 7에서 8로 올라간다. 뒤이어 배치가 `AND version = 7`로 UPDATE를 시도하면 **조건에 맞는 행이 없어 0건**이 되고, JPA는 이를 감지해 `OptimisticLockException`을 던진다. 한쪽이 진 것이다.

장점은 JPA 표준이라 `@Version` 필드 하나면 끝난다는 것이다. 단점은 엔티티를 거쳐야만 동작한다는 것 — JDBC로 직접 UPDATE 하는 배치나 웹훅 핸들러에는 자동으로 적용되지 않는다.

#### 방법 2 — 조건부 UPDATE

**조건부 UPDATE**는 "기대하는 현재 상태"를 WHERE 절에 직접 넣는 방식이다. 버전 숫자 대신 상태 값 자체를 조건으로 쓴다.

```sql
-- PostgreSQL: IN_PROGRESS인 경우에만 APPROVED로 전이
UPDATE payment
   SET status = 'APPROVED', approved_at = now()
 WHERE id = 4211
   AND status = 'IN_PROGRESS';   -- 이 조건 한 줄이 방어선 전체다
-- 영향받은 행이 0이면 "이미 다른 경로가 상태를 바꿨다"는 뜻.
-- 0건을 성공으로 취급하지 말고 반드시 분기 처리한다.
```

이 패턴은 컴퓨터과학에서 **compare-and-set(비교 후 설정)** 이라고 부르는 것과 같은 구조다. "값이 여전히 X일 때만 Y로 바꿔라"를 한 연산으로 처리하기 때문에, 비교와 설정 사이에 다른 누가 끼어들 수 없다.

이 방식에는 장점이 하나 더 있다. **엔티티를 거치지 않는 경로에서도 그대로 쓸 수 있다.** 웹훅 핸들러, 정리 배치, 어드민 스크립트는 보통 JPA 영속성 컨텍스트 밖에서 돌아가는데, 조건부 UPDATE는 SQL 한 줄이라 어디서든 동일하게 작동한다.

#### 그리고 가장 흔한 구멍 — 0건을 무시하는 코드

```java
// Before: 갱신 결과를 안 본다 — 실무에서 가장 흔한 구멍
jdbc.update("UPDATE payment SET status='APPROVED' " +
            "WHERE id=? AND status='IN_PROGRESS'", paymentId);
benefitService.grant(paymentId);   // 갱신이 0건이어도 그냥 실행된다
```

```java
// After: 갱신 행 수가 곧 "내가 이 전이의 승자인가"에 대한 답이다
int updated = jdbc.update(
        "UPDATE payment SET status='APPROVED', approved_at=now() " +
        "WHERE id=? AND status='IN_PROGRESS'", paymentId);

if (updated == 1) {
    // 이 전이를 성사시킨 것은 나 하나뿐이다. 후속 처리는 여기서만.
    benefitService.grant(paymentId);
} else {
    // 0건. 누군가 먼저 상태를 바꿨다는 뜻이므로, 지금 상태를 다시 읽어
    // "이미 APPROVED인 중복 요청인지 / EXPIRED로 끝난 건인지"를 판단한다.
    handleTransitionLost(paymentId);
}
```

영향 행 수 0을 무시하는 코드가 실무에서 가장 흔한 구멍인 이유는 `UPDATE`의 성질 때문이다 — **조건에 맞는 행이 없어도 예외를 던지지 않고, 아무 일도 안 한 채 0을 조용히 반환한다.** 개발자가 반환값을 안 보면 실패가 성공처럼 흘러간다.

### 2-5. 상태 변경 이력 테이블 — 현재 상태만으론 과거를 설명 못 한다

`payment.status`는 "지금"만 말해준다. 그런데 CS가 들어오면 필요한 건 "언제, 누가, 왜 이 상태가 됐나"다. 상태 컬럼은 덮어쓰기(UPDATE)로 바뀌므로 이전 값은 사라진다 — 즉 **상태 컬럼에는 과거가 없다.**

그래서 전이할 때마다 이력 행을 하나씩 남긴다.

```sql
CREATE TABLE payment_state_history (
    id          bigserial PRIMARY KEY,
    payment_id  bigint      NOT NULL REFERENCES payment(id),
    from_status varchar(20) NOT NULL,
    to_status   varchar(20) NOT NULL,
    reason      text        NOT NULL,  -- 'PG 승인 응답', '타임아웃' 등
    actor       varchar(50) NOT NULL,  -- 'api', 'webhook', 'batch',
                                       -- 'admin:kim' 등 전이 주체
    created_at  timestamptz NOT NULL DEFAULT now()
);
-- UPDATE/DELETE 없는 append-only. 결제의 블랙박스다.
```

**append-only** 는 "덧붙이기만 한다"는 뜻으로, 이 테이블에는 INSERT만 하고 UPDATE·DELETE는 절대 하지 않는다는 운영 규칙이다. 과거를 기록하는 테이블인데 과거를 수정할 수 있으면 기록의 의미가 없기 때문이다.

`actor`와 `reason` 두 컬럼이 특히 중요한데, "어떤 경로가 이 전이를 일으켰는가"를 특정할 수 있어야 하기 때문이다. 실제 이력을 조회해 보면 이런 모습이 된다.

| payment_id | from | to | reason | actor | created_at |
|---|---|---|---|---|---|
| 4211 | READY | IN_PROGRESS | 승인 요청 전송 | api | 14:02:11.031 |
| 4211 | IN_PROGRESS | UNKNOWN | PG 응답 타임아웃(10s) | api | 14:02:21.044 |
| 4211 | UNKNOWN | APPROVED | 거래조회 결과 승인 확인 | batch:unknown-resolver | 14:05:00.512 |

이력이 있으면 "이 50,000원 결제가 왜 UNKNOWN에 3분 머물렀다가 APPROVED가 됐는지"를 초 단위로 재구성할 수 있다. 그리고 **대사(reconciliation)** 배치 — PG가 준 거래 내역과 우리 DB를 한 줄씩 맞춰보며 차이를 찾는 정기 작업 — 가 불일치를 발견했을 때, 원인 추적의 출발점이 바로 이 테이블이다.

이력 기록은 상태 전이와 **같은 트랜잭션 안에서** 일어나야 한다. 전이는 커밋됐는데 이력만 빠지면 이력의 신뢰도가 무너져 조사 도구로 쓸 수 없게 된다.

### 2-6. 전부 합쳐보기 — 승인 요청 한 건의 실제 흐름

앞의 조각들이 실제 코드에서 어떻게 맞물리는지 한 번에 보자. 여기에는 아직 명시적으로 말하지 않은 원칙 하나가 더 들어 있다 — **PG 호출은 DB 트랜잭션 밖에서 한다.**

```java
public PaymentResult approve(long paymentId) {
    // ① 트랜잭션 1 — READY -> IN_PROGRESS 선점.
    //    PG를 부르기 "전에" 상태를 옮겨두는 이유:
    //    이 UPDATE에 성공한 프로세스만 PG를 부르게 되므로,
    //    같은 결제에 대한 동시 요청이 둘 다 PG로 나가는 일을 막는다.
    int started = jdbc.update("""
        UPDATE payment SET status = 'IN_PROGRESS', requested_at = now()
         WHERE id = ? AND status = 'READY'
        """, paymentId);
    if (started == 0) {
        // 이미 누군가 진행 중이거나 끝난 건. 새로 PG를 부르면 이중 결제다.
        return PaymentResult.alreadyHandled(loadStatus(paymentId));
    }
    historyRepository.append(paymentId, READY, IN_PROGRESS,
                             "승인 요청 전송", "api");

    // ② 트랜잭션 "밖에서" PG 호출.
    //    이 호출은 수 초가 걸린다. 트랜잭션 안에서 하면 그동안 DB 커넥션과
    //    행 락을 쥔 채 멈춰 있게 되고, 트래픽이 몰리면 커넥션 풀이 말라
    //    결제와 무관한 API까지 전부 죽는다.
    PgApproval approval;
    try {
        approval = pgClient.approve(paymentId, /* ... */);
    } catch (PgDeclinedException e) {
        // PG가 "안 됐다"고 명시적으로 답한 경우에만 FAILED.
        transition(paymentId, IN_PROGRESS, FAILED,
                   "PG 거절: " + e.getCode(), "api");
        return PaymentResult.failed(e.getCode());
    } catch (PgTimeoutException | PgServerErrorException e) {
        // 결과를 모르는 모든 경우는 UNKNOWN. 여기가 이 문서의 핵심이다.
        // 이 한 줄을 FAILED로 적는 순간 3절 사례 1이 재현된다.
        transition(paymentId, IN_PROGRESS, UNKNOWN,
                   "결과 불명: " + e.getClass().getSimpleName(), "api");
        return PaymentResult.pending();   // 화면 문구도 "확인 중"이어야 한다
    }

    // ③ 트랜잭션 2 — 결과 반영. 조건부 UPDATE로 웹훅과의 경합을 흡수한다.
    transition(paymentId, IN_PROGRESS, APPROVED, "PG 승인 응답", "api");
    return PaymentResult.approved(approval);
}

// 전이 + 이력 기록을 한 트랜잭션으로 묶는 공통 메서드
@Transactional
void transition(long id, PaymentStatus from, PaymentStatus to,
                String reason, String actor) {
    int updated = jdbc.update(
        "UPDATE payment SET status = ? WHERE id = ? AND status = ?",
        to.name(), id, from.name());
    if (updated == 0) {
        // 내가 지는 것 자체는 정상이다(웹훅이 먼저 반영했을 수 있다).
        // 다만 조용히 넘기지 않고 기록은 남긴다.
        log.info("전이 경합 패배 id={} {}->{}", id, from, to);
        return;
    }
    historyRepository.append(id, from, to, reason, actor);
}
```

각 조각이 맡은 역할을 정리하면 이렇다.

| 조각 | 막아주는 사고 |
|---|---|
| ① READY→IN_PROGRESS 조건부 선점 | 동시 요청이 PG를 두 번 부르는 것 |
| ② PG 호출을 트랜잭션 밖으로 | 커넥션 풀 고갈로 인한 서비스 전체 장애 |
| ② catch 분기의 FAILED / UNKNOWN 구분 | 이중 결제 |
| ③ 조건부 UPDATE | 웹훅·배치와의 경합으로 인한 상태 역행 |
| `transition()`의 이력 기록 | 사후 조사 불가 |

## 3. 실무 사례 — 상태 설계가 뚫리는 구멍들

### 사례 1: 타임아웃을 FAILED로 기록해 이중 결제

PG 승인 호출이 10초 타임아웃으로 끊기자 코드가 `catch` 블록에서 일괄적으로 FAILED를 찍었다. 문제의 코드는 이렇게 생겼었다.

```java
// 사고를 낸 코드
try {
    pgClient.approve(...);
    payment.setStatus(APPROVED);
} catch (Exception e) {          // 모든 예외를 한 덩어리로 취급
    payment.setStatus(FAILED);   // "예외 = 실패"라는 착각
}
```

`catch (Exception e)` 한 줄에 **성격이 완전히 다른 두 종류의 예외**가 섞여 들어온다. "PG가 거절했다"(결과가 확정된 실패)와 "응답을 못 받았다"(결과를 모름)가 같은 블록에서 같은 처리를 받는다.

결과는 이랬다. 고객 화면에 "결제 실패"가 떠서 고객이 다시 결제했고, 사실 첫 승인은 성공해 있었다 — **79,000원이 두 번 승인됐다.** 더 나빴던 건 후속 과정이다. FAILED로 기록된 첫 건은 "실패한 결제"이므로 어떤 배치도 다시 들여다보지 않았고, 고객 항의가 올 때까지 아무도 몰랐다. 즉 **FAILED로 잘못 적는 순간 그 건은 시스템의 시야에서 사라진다.**

교훈: **타임아웃·5xx·커넥션 끊김은 전부 UNKNOWN이다.** 그리고 UNKNOWN을 만들었으면 그것을 없애는 장치가 반드시 따라와야 한다.

- **해소 배치**: UNKNOWN 건만 골라 PG 거래 조회 API로 실제 결과를 확인하고 APPROVED/FAILED로 전이시킨다. 주기는 보통 1분 수준이다.
- **망취소(net cancellation)**: 조회로도 결과 확인이 안 되면, 승인 자체를 무효화해달라고 PG에 요청해 "승인이 났더라도 없던 일로" 만든다. 결과를 모를 때 **돈이 안 나간 쪽으로 확정시키는** 수단이다.

### 사례 2: 웹훅과 배치의 경합으로 상태 역행

만료 배치가 "30분 지난 READY/IN_PROGRESS를 EXPIRED로" 정리하는 일을 하고 있었다. 그런데 UPDATE에 조건이 없었다.

```sql
-- 사고를 낸 배치의 UPDATE
UPDATE payment SET status = 'EXPIRED' WHERE id = ?;
-- 대상 id는 몇 초 전 SELECT로 뽑아둔 목록에서 왔다.
```

여기서 놓친 것은 **SELECT로 대상을 뽑은 시점과 UPDATE를 실행하는 시점 사이에 시간이 흐른다**는 사실이다. 배치는 보통 수천 건을 뽑아 한 건씩 처리하므로, 목록 맨 뒤의 건은 뽑힌 지 수십 초가 지난 상태일 수 있다.

```
시각    [만료 배치]                       [지연 도착한 PG 웹훅]
 t1     SELECT id FROM payment
        WHERE status IN ('READY','IN_PROGRESS')
          AND created_at < now()-'30 min'
        → 4211 포함 3,000건 확보
 t2                                        UPDATE ... status='APPROVED'
                                           WHERE id=4211        (성공)
 t3     ... 앞의 2,999건 처리 중 ...
 t4     UPDATE payment SET status='EXPIRED'
        WHERE id=4211                      ← APPROVED를 덮어씀
```

결과: 고객 카드에서 **128,000원**이 나갔는데 우리 시스템은 "만료된 결제"라며 이용권을 지급하지 않았다. 게다가 EXPIRED는 종결 상태라 아무 배치도 이 건을 다시 보지 않았다.

교훈: 배치·웹훅·API처럼 **서로 다른 경로가 같은 행을 만지는 시스템**에서는 조건부 UPDATE가 필수다.

```sql
-- 고친 배치의 UPDATE
UPDATE payment SET status = 'EXPIRED'
 WHERE id = ?
   AND status IN ('READY', 'IN_PROGRESS');
-- t4 시점에 4211은 이미 APPROVED이므로 조건에 안 걸려 0건.
-- 배치는 "이 건은 그새 처리됐구나" 하고 넘어가면 된다.
```

조건이 있었다면 배치의 UPDATE는 0건으로 끝났을 것이고, 128,000원짜리 사고는 애초에 없었을 것이다. 조건 한 줄의 차이다.

### 사례 3: 이력 없이 상태만 남겨 장애 조사가 불가능

정산 대사에서 "PG는 승인인데 우리는 FAILED"인 건이 월 수십 건씩 발견됐다. 그런데 상태 필드만 있고 이력이 없어서 **언제 어떤 경로가 FAILED를 찍었는지** 알 수 없었다.

조사팀이 세운 원인 후보는 세 가지였다.

1. 타임아웃 처리 버그 (사례 1과 같은 유형)
2. 웹훅 순서 역전 (실패 웹훅이 승인 웹훅보다 늦게 도착)
3. 수동 조작 (어드민에서 누군가 상태를 바꿈)

세 후보 중 무엇인지 가리려면 "그 전이를 누가 일으켰는가"만 알면 됐는데, 그 정보가 어디에도 없었다. 애플리케이션 로그는 보존 기간(30일)이 지나 이미 지워진 뒤였다. 결국 후보를 좁히지 못해 조사가 몇 주를 끌었고, 그동안 사고는 계속 났다.

교훈: 이력 테이블은 "있으면 좋은 감사 로그"가 아니라 **장애 조사의 전제 조건**이다. 특히 `actor`(누가)와 `reason`(왜)까지 남겨야 경로를 특정할 수 있다. 앞의 세 후보는 actor 값 하나로 `api` / `webhook` / `admin:kim`으로 즉시 갈렸을 것이다.

여기서 한 가지 더 — 로그와 이력 테이블은 다르다. 로그는 보존 기간이 있고, 포맷이 자유롭고, 조인해서 집계할 수 없다. 이력은 결제 데이터와 같은 수명을 가지며 SQL로 질의할 수 있다. **돈의 흐름은 로그가 아니라 테이블에 적어야 한다.**

## 4. 꼬리질문 대비 포인트

### "UNKNOWN 상태는 언제, 어떻게 해소하나요?"

두 경로가 있다.

**(1) 능동 조회.** UNKNOWN 건을 주기적으로 스캔해 PG 거래 조회 API로 실제 결과를 확인하고 APPROVED/FAILED로 전이시키는 배치다. 우리가 먼저 물어보는 방식이라 "능동"이다. 이쪽이 주 경로여야 한다 — 상대가 알려주기를 기다리는 설계는 상대가 안 알려주면 영원히 멈추기 때문이다.

**(2) 수동 신호.** 지연 도착한 PG 웹훅이 결과를 알려주는 경우다. 우리가 가만히 있어도 알려주니 "수동"이다.

둘이 **동시에** 도착할 수 있다는 점이 중요하다. 배치가 조회 결과로 APPROVED를 쓰려는 순간 웹훅도 같은 걸 쓰려 할 수 있다. 그래서 해소 전이도 반드시 조건부 UPDATE로 보호해서 한쪽만 이기게 한다.

그리고 운영 장치가 하나 더 필요하다 — **"일정 시간(예: 24시간) 내에 해소되지 않은 UNKNOWN"에 알림을 걸어 사람이 본다.** 조회 API가 계속 실패하거나 PG 쪽에도 기록이 없는 건은 결국 사람이 판단해야 한다. UNKNOWN이 조용히 쌓이는 시스템은 대사 때 폭탄이 된다.

### "상태 검증을 애플리케이션에서 하면 충분하지 않나요?"

불충분하다. 2-4에서 본 lost update가 그 이유다. 애플리케이션 검증은 "내가 읽은 시점"의 상태에 대한 검증이라, 읽기와 쓰기 사이에 다른 트랜잭션이 끼어들면(웹훅과 배치의 동시 도착 등) 둘 다 검증을 통과하고 나중 커밋이 먼저 것을 덮어쓴다.

그래서 낙관적 락 또는 조건부 UPDATE로 **쓰는 순간의 상태**를 DB가 확인하게 해야 한다. 둘 다 두는 이유는 역할이 다르기 때문이다.

| | 애플리케이션 검증(enum) | DB 검증(조건부 UPDATE·@Version) |
|---|---|---|
| 언제 걸리나 | 읽은 직후, DB 가기 전 | 실제 쓰는 순간 |
| 무엇을 막나 | 개발자의 논리 실수 | 동시성으로 인한 덮어쓰기 |
| 강점 | 빠른 실패, 좋은 에러 메시지 | 정합성의 최후 방어선 |
| 혼자 두면 | 동시성에 뚫림 | 원인 파악이 어려운 0건만 남음 |

"둘 중 뭐가 맞나요"가 아니라 **"층이 다르니 둘 다 둔다"** 가 정답이다.

### "낙관적 락과 비관적 락 중 결제에는 뭘 쓰나요?" (시니어 변별 포인트)

먼저 **비관적 락(pessimistic lock)** 의 정의부터. 낙관적 락이 "일단 진행하고 쓸 때 확인"이라면, 비관적 락은 **"애초에 남이 못 건드리게 미리 잠그고 시작"** 하는 방식이다. PostgreSQL에서는 `SELECT ... FOR UPDATE`가 그것으로, 이 SELECT가 읽은 행은 트랜잭션이 끝날 때까지 다른 트랜잭션이 수정할 수 없고 시도하면 그쪽이 대기한다.

결제 **상태 전이**에는 낙관적 락(또는 조건부 UPDATE)이 기본이다. 이유는 두 가지다.

1. **경합이 드물다.** 결제 한 건의 상태를 동시에 바꾸려는 주체는 많아야 웹훅과 배치 정도다. 대부분의 시도는 충돌 없이 끝나는데, 그걸 위해 매번 미리 잠그는 건 비용만 크다.
2. **충돌 시 처리가 자연스럽다.** 진 쪽은 "재조회해서 지금 상태를 보고 판단"하면 되는데, 이건 결제 도메인에서 어차피 필요한 로직이다.

반면 비관적 락은 **경합이 잦고 반드시 직렬화해야 하는 지점**에 쓴다. 포인트 잔액 차감이 전형적인 예다 — 같은 사용자 행에 요청이 몰리고, "읽고 계산하고 쓰기"를 통째로 원자적으로 만들어야 하기 때문이다.

여기에 결제 도메인 특유의 함정을 덧붙이면 변별력이 생긴다. **결제 상태에 비관적 락을 남발하면 PG 호출(수 초) 동안 행 락을 쥔 채 대기하게 되어 커넥션 고갈로 번진다.** 커넥션 풀이 20개인데 20건의 결제가 각각 PG 응답을 기다리며 락과 커넥션을 붙잡고 있으면, 그 순간 그 서버의 모든 API가 커넥션을 못 받아 죽는다. **"외부 API 호출을 락 안에서 하지 않는다"** 는 원칙과 함께 말하면 설계 감각을 보여줄 수 있다.

### "상태 이력은 왜 UPDATE가 아니라 INSERT로만 쌓나요?"

이력의 존재 이유가 "과거의 재구성"이므로, 과거가 수정 가능하면 존재 이유 자체가 사라진다. append-only의 이득은 세 가지다.

1. **감사(audit) 요구를 그대로 충족한다.** 금융 관련 시스템은 "기록이 사후에 변경되지 않았음"을 요구받는데, 구조적으로 변경이 없으면 그 요구가 자동으로 만족된다.
2. **버그로 현재 상태가 오염돼도 복구할 수 있다.** 이력을 처음부터 순서대로 다시 적용(replay)하면 올바른 현재 상태가 나온다. 사례 2 같은 사고에서 실제로 이 방법으로 복구한다.
3. **쓰기 경합이 없다.** 서로 다른 행을 INSERT할 뿐이라 같은 행을 두고 다투는 일이 없다.

더 나아가면 **이벤트 소싱(event sourcing)** 관점까지 연결할 수 있다. 이벤트 소싱은 "현재 상태를 저장하는 대신 변화의 기록만 저장하고, 현재 상태는 그 기록을 재생해서 얻는다"는 설계다. 이 관점에서 보면 `payment.status` 컬럼은 원본이 아니라 **이력에서 파생된 캐시**다. 캐시라고 부르는 순간 "캐시가 틀렸으면 원본에서 다시 계산한다"는 복구 전략이 자연스럽게 따라 나온다.

### "상태가 늘어나면 전이 조합이 폭발하지 않나요?"

상태 수 n에 대해 이론적으로 가능한 전이는 n²이다. 상태가 7개면 49가지. 얼핏 관리 불가능해 보인다.

그런데 **허용 전이는 극히 일부**라는 게 상태 머신의 요점이다. 2-2의 표에서 실제 허용 전이를 세어보면 10개 남짓이다. 나머지 39가지는 우리가 하나씩 금지한 게 아니라, **명시하지 않았으므로 자동으로 금지**된 것이다. 화이트리스트 방식이 주는 이득이 바로 이것 — 관리해야 할 것은 n²가 아니라 실제로 존재하는 전이의 수뿐이다.

그래도 상태가 정말 많아지는 경우가 있다. 가상계좌·에스크로·후불처럼 결제 수단마다 고유 상태가 생길 때다. 이때 하나의 거대 enum에 전부 넣는 건 나쁜 선택인데, 이유는 **의미 없는 조합이 컴파일 타임에 걸러지지 않기 때문**이다. 카드 결제가 `WAITING_DEPOSIT`(입금 대기)으로 전이하는 건 명백한 버그인데, 하나의 전이 테이블에 다 섞여 있으면 그 버그가 정상적인 전이처럼 통과한다.

대안은 두 가지다.

- **결제수단별로 상태 머신을 분리한다.** 공통 골격은 공유하되 허용 전이 테이블은 수단별로 따로 둔다.
- **성격이 다른 흐름은 별도 엔티티로 쪼갠다.** 취소가 대표적이다 — 취소는 여러 번 일어나고 각각이 자기 생애주기를 갖기 때문에, 결제 상태에 값을 추가하는 대신 별도 엔티티의 별도 상태 머신으로 만든다(6번 문서의 주제다).

**"상태 폭발은 상태 머신을 쪼개라는 신호"** 라고 답하면 좋다.

## 한 줄 요약

결제는 요청과 확정 사이에 시간이 존재하는 과정이므로 READY → IN_PROGRESS → APPROVED/FAILED에 결과 불명의 **UNKNOWN까지 포함한 상태 열거와 허용 전이**를 정의하고, enum 전이 검증 + 낙관적 락·조건부 UPDATE로 코드와 DB 양쪽에서 잘못된 전이를 차단하며, 모든 전이를 append-only 이력으로 남겨야 한다 — "모른다"를 실패로 기록하는 순간 이중 결제가 시작된다.
