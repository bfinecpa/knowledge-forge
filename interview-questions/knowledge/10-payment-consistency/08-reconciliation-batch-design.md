# 대사(Reconciliation) 배치 설계 — 두 장부는 반드시 어긋난다, 문제는 그걸 언제 아느냐다

> 핵심 관전 포인트: **우리 서버의 DB와 PG사의 DB는 서로 다른 두 개의 장부다. 인터넷 너머에 있는 남의 회사 DB를 우리 트랜잭션에 묶을 방법은 없으므로, 멱등성 키·상태 머신·웹훅 검증을 아무리 잘 갖춰도 두 기록은 반드시 어긋난다 — 웹훅은 유실되고, 타임아웃 뒤에 승인이 도착하고, 취소 호출은 한쪽에서만 성공하기 때문이다. 대사(reconciliation)는 이 현실을 인정하고 두 장부를 건 단위로 대조하는 최후의 안전망이다. 설계의 뼈대는 [PG 대사 파일 수령 → 정규화(스테이징 적재) → 키 매칭(거래ID 기준) → 차이 분류(우리에만 있음 / PG에만 있음 / 금액 불일치) → 자동 보정 또는 수동 처리 큐 → 리포트·알림]의 파이프라인이고, 실무 디테일은 마감(cut-off) 기준 통일, 부분 취소를 흡수하는 순액 비교, 보정 작업 자체의 멱등성, 그리고 "대사 배치가 정상인지"를 검증하는 메타 모니터링이다. 대사가 없는 결제 시스템은 어긋난 채로 몇 달을 모르고 지나가는 시스템이다.**

---

## 0. 질문 + 의도

**질문**: "정산/대사(reconciliation) 배치는 왜 필요하고 어떻게 설계하나요?"

**출제 의도**: 실시간 정합성 장치가 아무리 완벽해도 대사는 필요하다 — "우리 기록과 PG 기록은 반드시 어긋난다"는 현실 인정에서 출발하는지를 본다. 결제를 만들어본 사람과 사후 검증 체계까지 갖춘 시스템을 만들어본 사람이 이 질문에서 갈린다.

## 1. 왜 대사가 필요한가 — 두 장부는 반드시 어긋난다

### 1-1. 전제 지식 — 우리 DB와 PG의 DB는 서로 다른 두 장부다

이 문서의 나머지가 전부 여기서 나온다. 딱 하나만 먼저 머리에 넣고 가자. **결제 한 건의 기록은 두 군데에 각각 따로 남는다.**

먼저 등장인물부터. **PG(Payment Gateway, 결제대행사)** 는 우리 서비스와 카드사·은행 사이에 끼어 결제 요청을 중계해 주는 회사다. 토스페이먼츠, NHN KCP, 나이스페이먼츠 같은 곳이 여기에 해당한다. 우리가 카드사 수십 곳과 각각 계약하고 각각의 규격에 맞춰 연동하는 대신, PG 한 곳과만 연동하면 되도록 중간에서 표준화해 주는 존재라고 보면 된다.

그리고 **장부(帳簿, ledger)** 라는 말을 이 문서에서 계속 쓸 텐데, 장부는 돈이 오간 사건을 한 줄씩 시간 순으로 적어 둔 기록 전체를 뜻한다. 은행 앱의 거래내역 화면을 떠올리면 정확하다 — 잔액이라는 숫자 하나만 덩그러니 있는 게 아니라 "3월 2일 입금 50,000원", "3월 3일 출금 49,000원" 같은 줄이 계속 쌓이고, 잔액은 그 줄들의 합으로 계산된다.

결제를 한 건 처리하면 이 장부가 두 곳에 생긴다.

- **우리 서비스의 DB**: `payment` 테이블에 주문번호, 금액, 상태(PENDING → APPROVED → CANCELED), PG가 발급한 거래ID가 저장된다.
- **PG사의 DB**: 우리는 들여다볼 수 없는 그쪽 원장에 승인 일시, 승인 금액, 카드사 승인번호, 취소 이력이 저장된다.

문제는 여기다. **이 두 장부는 하나의 트랜잭션으로 묶을 수 없다.** 우리가 CRUD API를 만들며 습관적으로 붙이는 `@Transactional`은 하나의 DB 커넥션 위에서만 동작한다. 같은 DB 안의 두 테이블은 한꺼번에 커밋되거나 한꺼번에 롤백되지만, 인터넷 너머 남의 회사 DB는 우리 트랜잭션 안으로 들어오지 않는다. 우리가 할 수 있는 것은 HTTP 요청을 하나 보내고 응답을 기다리는 것뿐이고, 그 요청과 응답 사이 어디서든 네트워크는 끊어질 수 있다.

```
      우리 서비스                              PG사
 ┌───────────────────┐                ┌───────────────────┐
 │ payment 테이블     │ ── 승인 요청 ──▶│ 거래 원장          │
 │  order_no ORD-2201 │                │  tid    T-8891     │
 │  amount   49,000   │ ◀─ 승인 응답 ──│  amount 49,000     │
 │  status   PENDING  │                │  status 승인        │
 │                    │ ◀─ 웹훅 통지 ──│                    │
 └───────────────────┘                └───────────────────┘
       장부 A          (이 선은 언제든 끊길 수 있다)         장부 B

  같은 사건을 두 곳에 각각 적는다.
  두 기록을 한 트랜잭션으로 묶을 수단은 존재하지 않는다.
  → 두 장부가 달라지는 것은 "버그"가 아니라 구조적 필연이다.
```

두 상자를 잇는 것은 신뢰할 수 없는 선 하나뿐이다. 그 선이 끊기면 두 장부는 서로 다른 내용을 갖게 되고, 그 순간 우리 시스템은 그 사실을 **알지 못한다**. 대사는 이 선이 끊겼던 흔적을 나중에 찾아내는 작업이다.

### 1-2. 용어부터 — 대사와 정산은 다른 것이다

면접에서 이 두 단어를 섞어 쓰면 실무 경험을 의심받는다. 이름의 유래부터 알면 헷갈리지 않는다.

- **대사(對査, reconciliation)**: 한자 그대로 "마주 대고(對) 조사한다(査)"는 뜻이다. 우리 시스템의 결제 기록과 PG사·카드사의 기록을 나란히 놓고 **건 단위로 한 줄씩 대조**해서 차이를 찾아내는 사후 검증 절차를 말한다. 영어 reconciliation도 "서로 어긋난 둘을 화해시킨다"는 뜻이니 방향이 같다.
- **정산(settlement)**: PG사가 일정 주기(보통 영업일 기준 며칠 뒤)로 결제 수수료를 떼고 판매 대금을 **가맹점 계좌에 실제로 입금**하는 절차다. 여기서 **가맹점(merchant)** 은 PG와 계약해서 카드 결제를 받는 사업자, 즉 우리 회사를 가리킨다.

둘은 순서 관계다. 정산 입금액이 맞는지 검증하려면 "그 입금이 어떤 거래들의 합인지"를 건 단위로 맞춰봐야 하고, 그게 대사다.

비유하면 이렇다. 대사 없이 정산만 받는 것은 **명세서 없이 청구서 총액만 보고 이체하는 것**과 같다. "이번 달 1,284만 원 입금"이라는 숫자 하나만 받아 들면, 그 안에 빠진 거래가 있는지 수수료가 잘못 적용됐는지 알 방법이 영원히 없다.

### 1-3. "어긋날 리 없다"는 전제가 왜 틀렸는가

결제 시스템에는 실시간 정합성을 지키는 장치들이 있다. 이 문서에서 계속 언급될 것들이니 각각 한 줄로 정리하고 넘어가자.

- **멱등성 키(idempotency key)**: 같은 요청을 두 번 보내도 결과가 한 번 보낸 것과 같아지도록, 요청마다 붙이는 고유 식별자.
- **상태 머신(state machine)**: 결제 상태가 PENDING → APPROVED처럼 미리 정해진 전이 경로로만 움직이도록 강제하는 구조. APPROVED에서 다시 APPROVED로 가는 전이는 아예 거부된다.
- **웹훅(webhook)**: PG가 처리 결과를 우리 서버의 특정 URL로 HTTP POST 해서 알려주는 콜백. 우리가 물어보러 가는 게 아니라 상대가 전화를 걸어오는 방식이다.

이 장치들은 **요청 하나하나를 올바르게 처리하기 위한 것**이지, 두 시스템이 가진 **기록 전체의 집합이 서로 같음**을 보장하지 않는다. 그리고 어긋나는 경로는 우연이 아니라 구조적이다.

**경로 1 — 웹훅 유실.** PG는 승인을 끝내고 웹훅을 쐈지만 우리 서버가 배포 중이라 5xx로 응답했고, PG의 재시도 3회가 모두 소진됐다. PG 장부엔 승인 49,000원이 남고, 우리 장부엔 PENDING이 남는다. 웹훅은 "상대가 걸어오는 전화"이므로 우리가 못 받으면 그 정보는 그냥 사라진다.

**경로 2 — 타임아웃 후 뒤늦은 승인.** 여기서 **타임아웃**은 "정해진 시간 안에 응답이 오지 않아 우리 쪽에서 기다리기를 포기한 것"이지, "상대가 처리하지 않았다"는 뜻이 아니다. 우리가 3초 타임아웃으로 FAILED 처리한 뒤 PG가 5초 만에 승인을 완료하면, 우리 장부엔 실패가 적히고 고객 카드는 실제로 결제된다.

**경로 3 — 취소 누락.** 우리 DB에는 취소 27,500원을 기록했는데 PG 취소 API 호출이 실패했고, 실패했을 때 우리 기록을 되돌리는 보상 처리도 누락됐다. 우리는 취소로 알고, PG는 승인을 유지한다.

**경로 4 — 시간대·마감 경계.** 우리는 결제 요청 시각(KST)을 기준 날짜로 삼지만, PG 파일은 카드사 매입일 또는 PG 영업일 마감 기준으로 날짜를 매긴다. 여기서 **마감(cut-off)** 은 "이 시각 이후의 거래는 다음 날짜로 넘긴다"고 정해 둔 하루의 경계선이다. 그래서 23:59:57 결제는 두 장부에서 서로 다른 날짜에 실릴 수 있다.

비유하면 대사는 **월말에 가계부와 통장 내역을 맞춰보는 일**이다. 지출할 때마다 아무리 꼼꼼히 적어도(실시간 정합성), 자동이체 누락과 취소 반영 지연, 카드 승인일과 매입일 차이 때문에 월말 대조 없이는 두 기록이 같다고 확신할 수 없다.

가계부와 결정적으로 다른 점은 하나다. 결제 시스템에서 차이 1건은 곧 고객 돈 또는 회사 돈의 유실이다.

## 2. 대사 배치 설계 — 수령 → 정규화 → 매칭 → 분류 → 처리

세부로 들어가기 전에 전체 그림을 한 번 보고 가자. 대사 배치는 단계마다 실패 방식이 다른 파이프라인이고, 각 단계에는 "여기서 막지 못하면 뒤 단계가 전부 거짓말이 되는" 관문이 하나씩 있다.

```
[1] 수령 (Receive)
    PG가 D+1 새벽에 올려 준 전일 거래 파일을 SFTP로 내려받는다
    └ 관문: 파일이 오기는 했는가?
            헤더에 적힌 건수·합계가 실제 내용과 맞는가?
            아니면 여기서 배치를 실패시킨다 (→ 사례 3)
                       │
                       ▼
[2] 정규화 (Normalize)
    파일을 파싱해 스테이징 테이블에 "원본 그대로" 적재한다
    └ 인코딩(EUC-KR), 금액 단위, PG 코드 → 우리 코드 변환은
      적재 이후에 SQL로. 원본을 남겨야 나중에 "파싱 버그"와
      "데이터 자체가 틀림"을 구분할 수 있다
                       │
                       ▼
[3] 매칭 (Match)
    PG 거래ID(tid)를 열쇠로 우리 기록과 PG 기록을 짝지운다
    └ FULL OUTER JOIN 한 번 = 어느 한쪽 기준이 아니라
      양쪽 모두를 빠짐없이 훑는다
                       │
                       ▼
[4] 분류 (Classify)
    짝이 없거나 금액이 다른 건을 세 유형으로 나눈다
    └ OURS_ONLY / PG_ONLY / AMOUNT_MISMATCH
                       │
                       ▼
[5] 처리 (Resolve)
    ├ 자동 보정: 사실 재확인이 가능하고 보정 방향이 유일한 것만
    ├ 수동 큐  : 나머지 전부. 담당자·기한·에이징 알림까지 포함
    └ 리포트   : 차이가 0건인 날에도 반드시 남긴다
```

### 2-1. 수령과 마감(cut-off) — D+1, 그리고 기준 시각 통일

대부분의 PG는 영업일 마감 후 **D+1 새벽**에 전일 거래 내역 파일을 SFTP로 내려주거나 대사 전용 조회 API를 제공한다. 여기서 **D+1**은 거래가 일어난 날을 D라고 할 때 그 다음 날을 가리키는 표기다. D+2면 이틀 뒤다.

왜 실시간이 아니라 D+1일까. PG 입장에서도 그날의 거래는 카드사 매입과 취소 반영이 끝나야 확정되기 때문이다. 즉 **PG 파일은 그쪽이 "이제 이게 최종본입니다"라고 선언한 확정본**이고, 대사가 신뢰할 수 있는 기준선이 되는 이유가 여기에 있다.

설계 결정은 두 가지다.

**첫째, 대사 기준일은 PG의 마감 기준을 따른다.** 우리 DB의 결제 시각이 아니라 PG 파일에 적힌 거래 일자를 기준 축으로 삼아야 경계 오탐이 줄어든다. 그래도 경계에 걸친 건은 남는데, 이런 건은 즉시 차이로 확정하지 말고 다음 회차까지 기다리는 **미확정(pending) 상태**를 따로 둔다.

**둘째, 파일 도착 자체를 감시한다.** 파일이 아예 안 왔는데 배치가 "대상 0건, 차이 0건"으로 성공 처리하는 것이 이 파이프라인의 최악의 실패다. 검증을 안 한 것과 검증해서 문제가 없는 것이 겉보기에 똑같아지기 때문이다(사례 3 참고).

### 2-2. 정규화 — 원본을 스테이징 테이블에 그대로 적재

PG 파일은 생각보다 거칠다. 고정 길이 텍스트일 수도 있고, CSV일 수도 있고, 인코딩이 UTF-8이 아니라 EUC-KR인 경우도 흔하다.

이걸 파싱해서 곧바로 우리 데이터와 비교하고 싶은 유혹이 있는데, 그러면 안 된다. 먼저 **스테이징 테이블에 원본 그대로 적재**한다. 여기서 **스테이징(staging) 테이블**은 "가공 전 원본을 잠시 받아 두는 임시 저장용 테이블"을 말한다. 무대에 올리기 전에 짐을 풀어 두는 대기 공간이라는 뜻이다.

PostgreSQL이면 `COPY` 명령으로 파일을 통째로 밀어 넣는다. `COPY`는 INSERT를 한 줄씩 날리는 것보다 훨씬 빠른, 파일과 테이블 사이의 대량 적재 전용 명령이다. 코드 값 변환(PG의 승인 코드를 우리 상태 코드로 바꾸는 일)과 금액 단위 통일은 적재가 끝난 뒤 SQL로 처리한다.

왜 굳이 원본을 남기는가. 이유는 둘이다.

- **책임 소재 구분.** 나중에 값이 이상하면 "우리 파싱이 잘못된 건지, PG가 보낸 데이터 자체가 틀린 건지"를 원본과 대조해 판정할 수 있다. 원본이 없으면 이 논쟁은 영원히 안 끝난다.
- **재실행 가능.** 배치가 중간에 죽어도 파일을 다시 받을 필요 없이 스테이징에서부터 다시 돌릴 수 있다. PG 파일은 보통 하루가 지나면 다시 받기가 번거롭다.

### 2-3. 키 매칭과 차이 분류 — FULL OUTER JOIN 한 방

**매칭 키**는 두 장부에서 "이 줄과 저 줄이 같은 거래"라고 판정할 때 쓰는 열쇠다. **PG 거래ID(tid, transaction id)** 를 1순위로 쓰고, 우리 주문번호는 보조로 쓴다.

왜 주문번호가 1순위가 아닐까. 한 주문에 결제 시도가 여러 번 붙을 수 있기 때문이다. 고객이 실패하고 다시 시도해서 한 주문에 승인이 2건 생기면, 주문번호만으로는 어느 승인이 우리 쪽 어느 기록에 대응하는지 구분할 수 없다. tid는 PG가 거래 시도마다 하나씩 발급하므로 이런 모호함이 없다.

```java
// Before: 우리 DB를 기준으로만 순회 — 반쪽짜리 대사
public void reconcile(LocalDate date) {
    List<Payment> ours = paymentRepository.findByApprovedDate(date);
    Map<String, PgRecord> pgMap = pgFileParser.parse(date).stream()
            .collect(toMap(PgRecord::tid, r -> r));

    // 순회의 출발점이 "우리 기록"이다. 즉 우리 DB에 행이 없는
    // 거래는 이 for 문에 애초에 들어오지 못한다.
    for (Payment p : ours) {
        PgRecord pg = pgMap.get(p.getPgTid());
        if (pg == null) {
            report.oursOnly(p);            // 우리에만 있음
        } else if (pg.amount() != p.getAmount()) {
            report.amountMismatch(p, pg);  // 금액 불일치
        }
    }
    // 문제 1: 루프가 끝난 뒤 pgMap에 남아 있는 항목들 —
    //   즉 "PG에만 있는" 거래 — 를 아무도 검사하지 않는다.
    //   웹훅 유실로 우리 기록이 없는 승인이 여기 해당하는데,
    //   고객 돈만 빠져나간 가장 위험한 유형이 조용히 통과된다.
    // 문제 2: 양쪽 수십만 건을 통째로 JVM 힙에 올린다.
    // 문제 3: 중간에 죽으면 어디까지 비교했는지 알 방법이 없다.
}
```

여기서 SQL의 JOIN을 잠깐 정리하고 가자. JOIN은 두 테이블에서 특정 열의 값이 같은 행끼리 옆으로 붙이는 연산이다. 종류에 따라 "짝이 없는 행"을 어떻게 처리할지가 달라진다.

- **INNER JOIN**: 양쪽 모두에 짝이 있는 행만 남긴다.
- **LEFT JOIN**: 왼쪽 테이블의 행은 전부 남기고, 오른쪽에 짝이 없으면 오른쪽 컬럼을 NULL로 채운다.
- **FULL OUTER JOIN**: 양쪽 행을 **모두** 남긴다. 왼쪽에만 있으면 오른쪽이 NULL이고, 오른쪽에만 있으면 왼쪽이 NULL이다.

위 Before 코드가 저지른 잘못이 바로 "LEFT JOIN만 한 셈"이라는 것이다. 대사는 어느 한쪽을 기준으로 삼으면 안 되고 **두 집합의 합집합**을 봐야 하므로, FULL OUTER JOIN이 정확히 이 문제의 모양에 들어맞는다.

```sql
-- After: 스테이징에 적재한 뒤 FULL OUTER JOIN으로 세 유형을
-- 한 번에 분류한다. 어느 쪽 기준도 아닌 "합집합 기준" 대사다.
INSERT INTO recon_diff
       (recon_date, diff_type, pg_tid, order_no,
        our_amount, pg_amount)
SELECT :recon_date,
       CASE
         -- 우리 행은 있는데 PG 쪽이 통째로 NULL → PG엔 없다
         WHEN pg.tid IS NULL                THEN 'OURS_ONLY'
         -- PG 행은 있는데 우리 쪽이 통째로 NULL → 우리에겐 없다
         WHEN o.pg_tid IS NULL              THEN 'PG_ONLY'
         -- 양쪽 다 있는데 순액이 다르다
         WHEN o.net_amount <> pg.net_amount THEN 'AMOUNT_MISMATCH'
       END,
       -- 한쪽이 NULL일 수 있으므로 값이 있는 쪽을 집어 온다
       COALESCE(o.pg_tid, pg.tid),
       COALESCE(o.order_no, pg.order_no),
       o.net_amount, pg.net_amount
FROM   our_daily_txn o
FULL OUTER JOIN pg_staging pg ON pg.tid = o.pg_tid
-- 정상 매칭(양쪽 존재 + 금액 동일)은 저장하지 않는다.
-- recon_diff에는 "차이 나는 건"만 쌓인다.
WHERE  pg.tid IS NULL
   OR  o.pg_tid IS NULL
   OR  o.net_amount <> pg.net_amount;
```

여기 나온 **순액(net amount)** 은 "승인 금액에서 취소 금액을 뺀 나머지", 즉 결국 얼마가 남았느냐다. 87,000원 승인에 27,500원 부분 취소가 붙었으면 순액은 59,500원이다. 왜 총액이 아니라 순액으로 비교하는지는 2-5에서 이어서 설명한다.

세 유형을 나란히 놓으면 각각이 어떤 사고를 뜻하는지가 선명해진다.

| 유형 | 우리 장부 | PG 장부 | 대표 원인 | 돈은 어느 방향으로 새는가 |
|---|---|---|---|---|
| `OURS_ONLY`<br>(우리에만 있음) | 승인 있음 | 해당 거래 없음 | 승인 응답을 못 받았는데 우리가 성공으로 잘못 확정 | 고객에게 물건·이용권은 나갔는데 돈은 안 들어옴 → **회사 손실** |
| `PG_ONLY`<br>(PG에만 있음) | 기록 없음 또는 PENDING | 승인 있음 | 웹훅 유실, 타임아웃 후 뒤늦은 승인 | 고객 돈은 빠져나갔는데 물건은 못 받음 → **고객 피해·CS·분쟁** |
| `AMOUNT_MISMATCH`<br>(금액 불일치) | 순액 59,500원 | 순액 32,000원 | 부분 취소 누락 또는 이중 반영 | 방향은 조사해 봐야 안다 → **조사 비용이 가장 큰 유형** |

이 표에서 읽어야 할 핵심은 마지막 열이다. 세 유형은 단순히 패턴이 다른 게 아니라 **피해자가 다르다**. PG_ONLY는 고객이 피해자라 시간이 지날수록 CS와 카드사 분쟁으로 번지고, OURS_ONLY는 회사가 조용히 손실을 흡수한다. 그래서 알림의 긴급도와 처리 기한을 유형별로 다르게 잡는 것이 자연스럽다.

### 2-4. 자동 보정 vs 수동 처리 큐

차이를 찾는 것보다 "찾은 다음 무엇을 하느냐"가 설계의 나머지 절반이다. 판단 기준은 하나로 요약된다 — **PG 거래 조회 API로 사실을 재확인할 수 있고, 보정 방향이 기계적으로 하나로 정해지는가.**

여기서 **PG 거래 조회 API**는 tid나 주문번호를 주면 "그 거래가 지금 승인 상태인지, 취소됐는지, 아예 없는지"를 알려주는 조회 엔드포인트다. 웹훅이 PG가 걸어오는 전화라면 이건 우리가 거는 전화다. 웹훅이 유실돼도 이쪽 경로는 살아 있다는 점이 중요하다.

**자동 보정이 가능한 경우.** PG_ONLY인데 우리 쪽에 같은 tid의 PENDING 기록이 남아 있는 경우가 대표적이다. PG 조회 API로 승인 사실을 재확인한 다음 우리 상태를 APPROVED로 확정한다. 웹훅 유실을 사후에 복구하는 셈이다.

단, 여기에 반드시 붙어야 하는 제약이 있다. 보정 로직은 평소의 결제 승인 처리와 **같은 코드 경로**, 즉 같은 상태 머신 전이를 타야 한다. 대사 배치가 `UPDATE payment SET status = 'APPROVED'` 같은 쿼리로 상태를 직접 바꾸기 시작하면 결제 상태를 바꾸는 경로가 둘이 되고, 상태 머신의 규칙이 한쪽에서만 적용된다. 이걸 **제2의 진실 경로**라고 부른다 — 진실이 두 갈래가 되는 순간 어느 쪽도 믿을 수 없어진다.

**수동 처리 큐로 보내야 하는 경우.** AMOUNT_MISMATCH는 전부, 그리고 원인을 특정할 수 없는 OURS_ONLY가 여기 해당한다. `recon_diff` 테이블에 담당자 배정·처리 상태·처리 기한 컬럼을 붙여 운영 큐로 만들고, 며칠째 미처리로 남아 있는 건을 알림으로 끌어올린다. 이렇게 "오래 묵은 건을 별도로 추려 올리는 것"을 **에이징(aging) 알림**이라고 한다. 실무에서 가장 흔한 운영 실패가 "차이를 찾긴 찾았는데 아무도 안 본" 상태다.

**보정 작업 자체도 멱등해야 한다.** 대사 배치는 반드시 재실행된다 — 파일을 다시 받거나, 장애에서 복구하거나, 담당자가 수동으로 다시 돌린다. 보정 이력 테이블에 `(recon_date, pg_tid, diff_type)` 유니크 제약을 걸어 같은 차이에 대한 보정이 두 번 실행되지 않게 막는다. 이 제약이 없으면 어떤 일이 벌어지는지는 사례 2에서 본다.

### 2-5. 부분 취소·환불 — 건 단위가 아니라 순액과 이벤트 단위

승인 87,000원에 부분 취소 27,500원이 붙는 순간, 지금까지 전제한 "우리 1건 vs PG 1건" 비교가 깨진다. 한 주문에 딸린 기록이 여러 줄이 되기 때문이다. 그래서 축을 두 개 쓴다.

**축 1 — 원거래 기준 순액(net) 비교.** 원거래 tid로 승인과 취소를 한 묶음으로 만든 뒤, 순액(87,000 − 27,500 = 59,500원)을 양쪽에서 각각 계산해 비교한다. 총액이 맞는지 빠르게 확인하는 용도다.

**축 2 — 이벤트 단위 대사.** 승인 1건, 취소 1건을 각각 독립된 레코드로 놓고 1:1로 대조한다.

왜 축 하나로는 부족한가. 순액만 보면 **서로 상쇄되는 오류를 놓치기 때문**이다. 취소 1건이 누락되고 다른 취소 1건이 이중 반영돼서 금액이 우연히 같아지면, 순액 비교는 "차이 없음"으로 통과시킨다.

반대 방향으로도 차이가 난다. 취소가 우리 장부엔 1건인데 PG엔 2건일 때, 순액 비교는 "금액이 27,500원 다르다"까지만 알려주지만 이벤트 대사는 "PG_ONLY 취소 1건"이라고 원인의 형태까지 드러낸다. 빠른 총량 검증은 순액으로, 원인 분해는 이벤트로. 두 축을 함께 돌리는 것이 정답이다.

### 2-6. 리포트와 알림 — "차이 0건"도 반드시 보고한다

대사 결과는 매일 리포트로 남긴다. 담아야 할 항목은 대상 건수·총액, 매칭 성공 건수, 차이 유형별 건수와 금액, 자동 보정 건수, 수동 큐 잔여 건수다.

여기서 초심자가 잘 빠뜨리는 규칙이 하나 있다. **차이가 0건인 날에도 "대상 12,847건 대조 완료, 차이 0건"을 남겨야 한다.** 리포트가 없는 날과 차이가 없는 날을 구분할 수 없으면, 배치가 죽어서 아무것도 안 한 날을 "평화로운 날"로 착각하게 된다. 알림 설계의 일반 원칙 하나 — 무소식이 희소식이 되는 시스템은 만들면 안 된다.

## 3. 실무 사례 — 대사 배치 자체가 뚫리는 구멍들

### 사례 1: 시간대 경계 — 월말 밤 결제가 오탐 폭풍을 만든다

3월 31일 23:59:57에 승인된 49,000원 결제가 PG 마감 기준으로는 4월 1일 거래로 실렸다. 우리 DB의 결제 시각을 기준 축으로 3월 31일 자 대사를 돌리자, 이 건은 "우리 DB엔 있는데 그날 PG 파일엔 없다"는 이유로 OURS_ONLY로 분류됐다.

문제는 월말이라 같은 유형이 수십 건 쏟아졌다는 것이다. 담당자는 오탐 더미를 훑다 지쳤고, 그 안에 섞여 있던 진짜 차이 1건을 놓쳤다. 여기서 **오탐(false positive)** 은 실제로는 문제가 아닌데 경보가 울린 경우를 말한다.

**대응.** 두 가지를 동시에 했다.

1. 대사 기준 축을 우리 결제 시각이 아니라 **PG 거래 일자로 통일**했다. 판정의 기준선은 확정본을 가진 쪽에 맞춘다.
2. OURS_ONLY와 PG_ONLY는 **1회차 유예 후 확정**하도록 바꿨다. 발견 즉시 차이로 확정하지 않고 "미확정" 상태로 하루를 들고 있다가, 다음 날 파일에서 매칭되면 자동 소멸시키고, 그래도 남으면 그때 진짜 차이로 올린다.

경계 오탐을 구조적으로 없애야 알림의 신뢰도가 유지된다. 오탐이 많은 알림은 결국 아무도 안 보게 되고, 그러면 알림이 없는 것과 같아진다.

### 사례 2: 재실행에서 보정이 두 번 — 대사가 사고를 만든다

배치가 후반부에서 실패해 담당자가 재실행했다. 그런데 앞부분에서 이미 수행했던 자동 보정 — 웹훅 유실 건의 승인 확정과 그에 딸린 이용권 지급 — 이 처음부터 다시 실행됐다. 고객 한 명에게 이용권이 두 번 지급됐다.

대사가 잡아내라고 만든 이중 지급을, 대사 배치가 직접 만들어낸 셈이다. 안전망이 사고의 원인이 되는 이 구도가 특히 위험한 이유는 사람들이 대사 결과를 의심하지 않기 때문이다.

**대응.** 방어선을 두 겹으로 뒀다.

1. **보정 이력 테이블에 유니크 제약.** `(recon_date, pg_tid, diff_type)` 조합에 유니크 인덱스를 걸어, 같은 차이에 대한 보정 INSERT가 두 번째부터는 DB 레벨에서 튕기게 했다. 보정 자체를 멱등하게 만든 것이다.
2. **보정이 결제 도메인의 정규 상태 전이 API를 호출하게.** 그러면 상태 머신이 APPROVED → APPROVED 같은 불가능한 전이를 거부하고, 전이가 거부되면 그 뒤에 달린 이용권 지급도 실행되지 않는다.

배치 안쪽(유니크 제약)과 도메인 쪽(상태 머신) 양쪽에 겹으로 두는 것이 핵심이다. 한 겹이 뚫려도 다른 겹이 남는다.

### 사례 3: 파일이 안 왔는데 "차이 0건 완료"

PG 쪽 장애로 대사 파일이 정상 파일이 아니라 **빈 파일**로 내려왔다. 배치는 스테이징에 0건을 적재했다.

이때 무슨 일이 벌어지는지는 구현에 달렸는데, 어느 쪽이든 나쁘다. FULL OUTER JOIN을 그대로 돌렸다면 우리 쪽 전 건이 OURS_ONLY로 분류돼 수천 건짜리 오탐 폭탄이 된다. 반대로 "비교 대상이 없으니 할 일 없음"으로 성공 처리했다면, 어긋난 하루가 통째로 검증 없이 지나간다. 후자가 훨씬 위험하다 — 아무도 이상을 눈치채지 못하기 때문이다.

**대응.** 비교를 시작하기 전에 **컨트롤 토탈(control total) 검증**을 관문으로 세웠다. 컨트롤 토탈은 파일 맨 앞(헤더)이나 맨 뒤(트레일러)에 "이 파일에는 총 12,847건, 합계 641,235,000원이 들어 있다"고 적어 두는 요약 값이다. 파일이 잘리거나 전송이 끊겼는지를 받는 쪽에서 스스로 확인하라고 넣어 주는 장치다.

검증 항목은 셋이다.

- 헤더·트레일러의 건수·합계 vs 실제 적재된 건수·합계 대조.
- 전일 대비 건수 급감 감지(예: 전일의 80% 미만이면 이상으로 본다).
- 위 둘 중 하나라도 걸리면 대사를 진행하지 않고 **배치를 실패로 처리하고 알림**을 보낸다.

"입력이 정상일 때만 대사 결과를 신뢰한다"는 전제 검증이 파이프라인의 첫 단계여야 한다. 쓰레기를 넣으면 쓰레기가 나오는데, 대사에서는 그 쓰레기가 "이상 없음"이라는 얼굴로 나온다.

## 4. 꼬리질문 대비 포인트

### "정산과 대사는 뭐가 다른가요?"

정산은 돈이 실제로 들어오는 절차, 대사는 그 돈이 맞는지 건 단위로 검증하는 절차다.

실무에선 여기서 한 겹 더 들어가 **3자 대조**까지 말하면 좋다. 우리 거래 기록과 PG 거래 내역을 맞추는 것이 **거래 대사**이고, 그 결과와 실제 입금액·수수료 명세를 맞추는 것이 **정산 대사**다. 두 층을 따로 두는 이유는 거래 대사가 완벽히 맞아도 수수료율이 잘못 적용되면 입금액이 어긋날 수 있기 때문이다. "건은 다 맞는데 돈이 덜 들어왔다"는 상황은 실제로 일어난다.

### "차이가 발견되면 자동으로 고치나요?"

조건부다. PG 거래 조회 API로 사실을 재확인할 수 있고 보정 방향이 하나로 정해지는 유형 — 대표적으로 웹훅 유실로 인한 상태 지연 — 만 자동 보정하고, 그마저도 정규 상태 전이 경로를 태운다.

금액 불일치는 무조건 수동 큐다. 이유를 붙여 말하는 게 중요하다. 자동 보정이 잘못 판단하면 대사가 오히려 장부를 오염시키는데, 그 오염은 **다음 대사에서 "정상"으로 보인다**. 우리가 PG에 맞춰 고쳐 놨으니 다음 날엔 두 장부가 사이좋게 같아지기 때문이다. 스스로 만든 오류를 스스로 못 잡는 구조라서, 잘못된 자동 보정은 일반 버그보다 발견이 훨씬 어렵다.

### "대사는 D+1 배치면 충분한가요? 실시간 대사는요?"

역할이 다르다는 것을 계층으로 나눠 말하면 된다.

D+1 파일 대사는 PG가 마감한 확정본을 기준으로 하는 **완결성 검증**이다. "그날 있었던 모든 거래가 양쪽에 빠짐없이 있는가"를 본다. 반면 실시간에 가까운 검증은 대사가 아니라 **능동 조회**로 푼다 — PENDING이 30분을 넘긴 건을 골라 PG 조회 API로 상태를 확인하는 배치다.

둘의 관계는 이렇다. 능동 조회가 촘촘할수록 D+1 대사에서 잡히는 차이 건수가 줄고, 대사는 "능동 조회조차 놓친 것"을 잡는 최후 안전망으로 물러난다. 대사에서 차이가 많이 잡힌다는 건 그 자체로 앞단 감지 계층이 부실하다는 신호다.

### "부분 취소가 섞이면 매칭 키를 어떻게 잡나요?"

원거래 tid로 승인·취소 이벤트를 그룹핑해 순액을 비교하고, 동시에 이벤트 단위로도 1:1 대조한다. 순액 비교는 빠른 총량 검증, 이벤트 대사는 원인 분해용이다.

여기에 한 가지를 덧붙이면 답이 완성된다. 이벤트 단위 대사가 가능하려면 **취소에도 가맹점 취소 번호(멱등 키)를 부여해 둬야** 한다. 그래야 "우리 취소 1건 = PG 취소 1건"의 대응 관계가 명확해진다. 취소마다 고유 번호가 없으면 27,500원짜리 취소 두 줄이 같은 취소의 중복 기록인지 서로 다른 두 번의 취소인지 구분할 방법이 없다.

이 대목이 흥미로운 이유는 **대사 설계가 거꾸로 결제 요청 설계에 요구사항을 만들어 낸다**는 점이다. 사후 검증을 제대로 하려면 사전 기록 방식부터 바꿔야 한다는 것을 알고 있다는 신호가 된다.

### "대사 배치가 정상 동작하는지는 어떻게 아나요?" (시니어 변별 포인트)

대사의 대사, 즉 **메타 모니터링**을 말할 수 있어야 한다. 네 층으로 정리하면 다음과 같다.

1. **입력 검증**: 파일이 도착했는가, 컨트롤 토탈이 맞는가, 전일 대비 건수가 정상 범위인가.
2. **실행 검증**: 대사 완료 시각 SLA — 예를 들어 오전 7시까지 완료되지 않으면 알림. 배치가 조용히 안 돈 것을 잡는 층이다.
3. **출력 검증**: "차이 0건"도 리포트로 남겨 무소식과 정상을 구분한다.
4. **잔여 관리**: 수동 큐의 에이징 알림 — 며칠째 아무도 손대지 않은 차이를 위로 끌어올린다.

마무리는 이 한 문장이다. 대사는 최후 안전망인데, 그 안전망이 끊겼을 때 즉시 알 수 있는 장치가 없다면 그건 안전망이 아니다. 사후 검증 체계를 실제로 운영해 본 사람만이 자연스럽게 하는 말이다.

## 한 줄 요약

우리 DB와 PG의 DB는 하나의 트랜잭션으로 묶을 수 없는 서로 다른 두 장부이고 웹훅 유실·뒤늦은 승인·취소 누락·마감 경계 때문에 반드시 어긋나므로, 수령(컨트롤 토탈 검증) → 스테이징 정규화 → 거래ID 매칭 → 3유형 분류(우리에만/PG에만/금액 불일치) → 멱등한 자동 보정 + 수동 큐 → 리포트로 이어지는 D+1 대사 파이프라인을 최후 안전망으로 세워야 하며, 대사 배치 자체의 실패까지 감시해야 비로소 "어긋남을 하루 안에 아는" 시스템이 된다.
