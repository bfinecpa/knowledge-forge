# 차감과 지급의 정합성 — 순서를 정하는 기준은 "복구 가능성"이다

> 핵심 관전 포인트: **포인트 차감(돈이 나감)과 이용권 지급(권리가 생김)이 같은 DB에 있다면 답은 단순하다 — 단일 트랜잭션으로 묶고, 잔액은 `balance = balance - ? WHERE balance >= ?` 조건부 UPDATE로 음수를 원천 차단한다. 서로 다른 시스템이라면 두 동작의 원자성은 포기하고 "실패해도 복구 가능한 순서"를 설계한다 — 차감을 먼저 하고 지급이 실패하면 환급(보상)한다. 환급은 더하기 연산이라 언제든 성공시킬 수 있지만, 지급을 먼저 하면 차감 실패를 메우려고 이미 소비됐을지 모르는 권리를 회수해야 한다. 여기에 **트랜잭셔널 아웃박스**(보낼 메시지를 같은 DB의 테이블에 INSERT해서 "커밋"과 "메시지 발행"을 한 몸으로 만드는 기법)로 발행 누락을 막고, 모든 돈의 이동을 **append-only 원장**(고치지도 지우지도 않고 추가만 하는 거래 내역 테이블)에 남겨 어느 지점에서 죽어도 복구와 대사가 가능하게 만든다. 면접관이 보는 것은 "중간에서 죽는 지점을 몇 개나 열거하고, 각각의 복구를 말할 수 있는가"다.**

---

## 0. 질문 + 의도

**질문**: "포인트/캐시 차감과 콘텐츠 이용권 지급을 하나의 흐름에서 처리할 때 정합성을 어떻게 보장하나요?"

**출제 의도**: 돈이 나가는 동작과 권리가 생기는 동작 사이의 원자성을 설계할 수 있는지 본다. 한 DB면 트랜잭션으로 끝나지만, 서로 다른 시스템에 걸쳐 있으면 순서(차감 먼저? 지급 먼저?)를 정한 근거와 실패 시 복구까지 말해야 한다 — 정합성 설계를 구체적 실패 시나리오로 검증하는 습관이 있는지가 관전 포인트다.

## 1. 왜 문제인가 — 실패가 만들 수 있는 네 가지 세계

### 1-1. 두 동작 사이에서 죽으면 어떤 세계가 남는가

5,000P짜리 웹툰 이용권을 구매하는 흐름을 보자. 해야 할 동작은 둘이다 — ① 포인트 5,000P 차감, ② 이용권 1장 지급. 이 둘 사이 어딘가에서 서버가 죽거나 네트워크가 끊기면, 시스템은 아래 네 가지 세계 중 하나에 놓인다.

| 차감 | 지급 | 결과 |
|---|---|---|
| 성공 | 성공 | 정상 |
| 실패 | 실패 | 구매는 안 됐지만 정합 — 재시도하면 된다 |
| 성공 | 실패 | **"5,000P 빠졌는데 이용권이 없어요"** — CS 폭탄 |
| 실패 | 성공 | **공짜 이용권** — 회사 손실 + 어뷰징 통로 |

1·2번 세계는 아무 문제가 없다. 둘 다 실행됐거나 둘 다 실행되지 않았고, 사용자가 보는 화면과 DB의 내용이 일치한다. 문제는 3·4번, 즉 **한쪽만 실행된 세계**다.

정합성 설계란 결국 3·4번 세계를 (1) 애초에 생기지 않게 하거나, (2) 일시적으로 생기더라도 **자동으로 1·2번으로 수렴**시키는 일이다. 여기서 "수렴"이란 시스템이 스스로 뒷정리를 해서 결국 정상 상태에 도달한다는 뜻이다. 사람이 매번 DB를 열어 고쳐야 한다면 그건 설계가 아니라 운영 부채다.

면접에서 "에러 나면 롤백하면 되죠"라는 답이 부족한 이유가 여기 있다. 그 답은 두 동작이 **한 트랜잭션 안에 있을 때만** 성립한다. 면접관은 그 다음 — 트랜잭션이 닿지 않는 구간 — 을 묻고 있다. 그래서 먼저 "트랜잭션이 정확히 어디까지 보장해주는가"를 짚고 가야 한다.

### 1-2. 전제 지식 — `@Transactional`이 보장하는 것과 못 하는 것

**트랜잭션(transaction)**은 여러 개의 DB 작업을 "전부 성공 아니면 전부 없던 일"로 묶는 단위다. 이 성질을 **원자성(atomicity)**이라고 부른다 — 더 이상 쪼갤 수 없는 원자처럼 중간 상태로 남지 않는다는 뜻이다.

Spring에서 메서드에 `@Transactional`을 붙이면 메서드 시작 시 `BEGIN`, 정상 종료 시 `COMMIT`, 예외 발생 시 `ROLLBACK`이 자동으로 실행된다. 롤백이 가능한 이유는 DB가 변경 전 값을 별도 공간(PostgreSQL은 이전 버전 튜플, MySQL InnoDB는 언두 로그)에 남겨두기 때문이다. 즉 **롤백은 DB 엔진이 자기 데이터에 대해 제공하는 기능**이다.

여기서 경계가 드러난다. 트랜잭션이 되돌릴 수 있는 것은 **같은 DB 커넥션으로 실행한 SQL뿐**이다. 아래 것들은 `@Transactional` 안에서 실행해도 롤백 대상이 아니다.

- 다른 서비스로 보낸 HTTP 요청 (상대방은 이미 처리했다)
- Kafka로 발행한 메시지 (컨슈머가 이미 읽었을 수 있다)
- 파일 쓰기, 메일 발송, 외부 결제사 승인
- Redis 캐시 갱신

그래서 포인트 서비스와 콘텐츠 서비스가 **각자 다른 DB를 쓰는** 순간, 두 동작을 한 트랜잭션으로 묶는 길은 사라진다. 포인트 서비스가 `COMMIT`을 끝낸 시점에 그 차감은 **그쪽 DB에서 이미 확정된 과거**다. 나중에 콘텐츠 서비스에서 지급이 실패했다고 해서 우리가 "아까 그거 취소"라고 말할 수 있는 롤백 명령은 존재하지 않는다. 커밋된 트랜잭션을 되돌리는 표준 SQL은 없다.

이 문장 하나가 이 문서 전체의 출발점이다. **다른 시스템의 커밋은 되돌릴 수 없다. 되돌릴 수 없다면, 반대 방향의 새 작업으로 메우는 수밖에 없다.** 이 "반대 방향의 새 작업"을 **보상(compensation)**이라고 부른다 — 차감(-5,000P)의 보상은 환급(+5,000P)이다. 취소가 아니라 새 거래라는 점이 중요하다. 회계에서 잘못 적은 장부를 지우개로 지우지 않고 반대 분개를 새로 적는 것과 같은 사고방식이다.

### 1-3. 비유 — 자판기

**자판기**를 떠올리면 이 문서의 설계가 통째로 들어온다.

자판기는 반드시 동전을 먼저 받고(차감), 그다음 음료를 배출한다(지급). 배출이 실패하면 반환 레버가 있다 — 이게 보상(환급)이다. 반대로 음료를 먼저 주고 돈을 나중에 받는 자판기는 세상에 없다. 이미 딴 음료(소비된 권리)는 회수할 방법이 없기 때문이다. 그리고 자판기 안에는 동전 계수기가 있어서 나중에 "판매된 재고 수 × 가격 = 수금액"이 맞는지 맞춰볼 수 있다 — 이게 원장(ledger)과 대사(reconciliation)다.

순서(차감 먼저), 보상(반환 레버), 기록(동전 계수기). 이 세 가지가 아래 2절의 전부다.

## 2. 설계 — 같은 DB, 다른 시스템, 그리고 원장

### 2-1. 같은 DB라면: 단일 트랜잭션 + 조건부 UPDATE

포인트 지갑 테이블과 이용권 테이블이 같은 PostgreSQL 안에 있다면 원자성은 DB가 공짜로 준다. `@Transactional` 하나면 끝이다.

그런데 이때 진짜 시험대는 원자성이 아니라 **동시성**이다. 같은 사용자의 요청 두 개가 **동시에** 들어왔을 때 잔액이 어떻게 되는지가 문제다. 이걸 이해하려면 먼저 lost update를 알아야 한다.

#### 먼저 짚고 갈 것 — lost update(갱신 유실)란 무엇인가

**lost update**는 두 트랜잭션이 같은 값을 읽어 각자 계산한 뒤 차례로 저장할 때, **나중 저장이 먼저 저장을 덮어써서 한쪽의 갱신이 사라지는** 현상이다. 이름 그대로 "갱신이 유실된다".

잔액 5,000P인 사용자가 결제 버튼을 더블 클릭했다고 하자.

```
시각   요청 A                      요청 B                  DB의 balance
----   ------------------------    --------------------    ------------
t0                                                          5000
t1     SELECT balance -> 5000                                5000
t2                                 SELECT balance -> 5000    5000
t3     계산: 5000 - 5000 = 0                                 5000
t4                                 계산: 5000 - 5000 = 0     5000
t5     UPDATE balance = 0                                    0
t6                                 UPDATE balance = 0        0
```

결과: 5,000P만 빠졌는데 이용권은 2장 나갔다. B의 UPDATE가 A의 UPDATE를 덮어썼고, A가 만든 "5,000P 차감"이라는 변화가 사라졌다 — 이것이 lost update다.

"트랜잭션 안에 넣었는데 왜 이런 일이?"라는 의문이 들 수 있다. 이유는 대부분의 DB 기본 격리 수준인 **READ COMMITTED**에서 SELECT가 **아무것도 잠그지 않기** 때문이다. READ COMMITTED는 "커밋된 값만 읽는다"만 보장할 뿐, "내가 읽은 값이 그대로 있을 것"은 보장하지 않는다. 트랜잭션은 원자성을 주지, 동시성 제어를 자동으로 해주지 않는다.

이렇게 **읽고(check) → 판단하고 → 쓰는(act)** 구조를 check-then-act라고 부르며, 읽기와 쓰기 사이의 틈이 그대로 사고 지점이 된다.

```java
// Before: 조회 후 갱신(check-then-act) — 두 가지 사고를 품고 있다
@Transactional
public void purchase(long userId, long orderId, long productId) {
    int balance = pointRepository.findBalance(userId);     // ① 조회
    if (balance < 5000) throw new InsufficientPointException();
    pointRepository.setBalance(userId, balance - 5000);    // ② 갱신
    ticketRepository.insert(orderId, userId, productId);   // ③ 지급
}
// 사고 1(lost update): ①에서 두 요청이 모두 5000을 읽으면 둘 다
//         잔액 검사를 통과하고, ②의 덮어쓰기로 차감은 1번만 남는다.
// 사고 2: ①의 SELECT는 행을 잠그지 않는다. 트랜잭션으로 감쌌다고
//         동시성이 해결되는 게 아니라는 점이 이 코드의 교훈이다.
```

#### 해법 — 검사와 차감을 UPDATE 한 문장으로 합친다

틈이 문제라면 틈을 없애면 된다. 잔액 검사를 애플리케이션의 if문이 아니라 **UPDATE의 WHERE 절**로 옮기는 것이다.

```java
// After: 검사와 차감을 UPDATE 한 문장으로 합친다
@Transactional
public void purchase(long userId, long orderId, long productId) {
    int updated = pointRepository.deduct(userId, 5000);
    // 갱신된 행 수가 0이면 WHERE의 balance >= 5000이 거짓이었다는 뜻
    // — 즉 잔액 부족이다. rowcount 확인이 곧 잔액 검사 역할을 한다.
    if (updated == 0) throw new InsufficientPointException();
    ledgerRepository.append(orderId, userId, -5000, EntryType.DEDUCT);
    ticketRepository.insert(orderId, userId, productId);
    // 같은 DB이므로 이 셋은 한 트랜잭션이다. 커밋되면 차감·원장·
    // 이용권이 전부 남고, 어디서든 예외가 나면 전부 사라진다.
}
```

```java
@Modifying
@Query("""
    UPDATE PointWallet w
       SET w.balance = w.balance - :amount
     WHERE w.userId = :userId AND w.balance >= :amount
    """)
int deduct(@Param("userId") long userId, @Param("amount") int amount);
```

이 한 문장이 왜 안전한지 단계별로 보자.

1. `balance = balance - :amount`는 **DB가 현재 값을 읽어서 빼는** 연산이다. 애플리케이션이 미리 읽어둔 옛날 값(5000)을 쓰지 않는다.
2. UPDATE는 대상 행에 **배타 잠금(exclusive lock)**을 건다. 같은 행을 건드리려는 다른 UPDATE는 첫 번째가 커밋/롤백할 때까지 대기한다. 즉 DB가 두 요청을 자동으로 줄 세운다.
3. 두 번째 요청이 대기에서 풀려 실행될 때 보는 잔액은 이미 0이다. `balance >= 5000` 조건이 거짓이 되어 **0건 갱신**으로 끝난다.
4. 애플리케이션은 반환된 갱신 행 수(rowcount)가 0인지만 보면 된다.

즉 **검사·잠금·갱신이 SQL 한 문장 안에서 원자적으로 일어나므로 틈이 원천적으로 없다.** 이것이 조건부 UPDATE가 돈 도메인의 기본기로 불리는 이유다.

- **잔액 음수는 애플리케이션 if문이 아니라 SQL이 막는다.** 방어를 한 겹 더 두고 싶으면 컬럼에 `CHECK (balance >= 0)` 제약을 추가한다. 어떤 경로(배치, 어드민 툴, 수동 SQL)로 들어오든 음수 잔액은 DB가 거부한다.
- 이 패턴은 잔액뿐 아니라 재고 차감, 쿠폰 발급 수량 제한 등 "한정된 수량을 깎는" 모든 곳에 그대로 쓰인다.

### 2-2. 다른 시스템이라면: 순서가 설계의 절반이다

포인트 서비스와 콘텐츠(이용권) 서비스가 DB를 따로 쓰는 순간, 1-2에서 본 대로 두 동작을 한 트랜잭션에 넣을 방법은 없다. 이제 질문은 **"어느 쪽을 먼저 실행하는가"**로 바뀐다.

여기서 초보와 경험자가 갈린다. 초보는 사용자 경험을 기준으로 고른다("이용권부터 주면 사용자가 빨리 볼 수 있잖아요"). 경험자는 **실패했을 때 되돌리기 쉬운 쪽**을 기준으로 고른다. 이 기준을 복구 가능성이라고 부르자.

두 순서를 나란히 놓고 보자.

**① 차감 먼저 → 지급 나중.** 지급이 실패하면 보상은 **환급**이다. 환급이 좋은 보상인 이유는 두 가지다.

- 환급은 잔액에 **더하기**다. 더하기에는 "잔액이 모자라서 못 한다" 같은 논리적 실패 조건이 없다. 네트워크 장애로 일시 실패할 수는 있어도 재시도하면 언젠가 반드시 성공한다.
- 포인트는 우리 시스템이다. 환급 API의 스펙과 배포 일정을 우리가 통제한다. 외부 회사에 "취소 좀 해주세요"라고 부탁할 필요가 없다.

**② 지급 먼저 → 차감 나중.** 차감이 실패하면(잔액 부족을 뒤늦게 발견, 포인트 서비스 장애) 보상은 **이용권 회수**다. 여기엔 세 개의 지뢰가 있다.

- 사용자가 이미 웹툰을 열람했다면? 소비된 권리는 회수해도 이미 본 것을 되돌리지 못한다.
- 콘텐츠 서비스에 애초에 회수 API가 없다면? 지급만 있고 회수는 없는 API는 실무에서 흔하다.
- 지급과 차감 실패 사이의 몇 초, 그리고 회수가 완료되기까지의 몇 초 동안 **공짜 열람 창**이 열린다.

정리하면 원칙은 이렇게 된다.

> **보상이 확실한 동작(돈이 나가는 쪽)을 먼저 하고, 보상이 불확실한 동작(권리가 생기는 쪽)을 나중에 한다.**

| 순서 | 실패 시 보상 | 보상의 성격 | 최악의 결과 |
|---|---|---|---|
| 차감 → 지급 | 환급(더하기) | 논리적 실패 없음, 내부 API | 잠시 돈이 빠졌다가 돌아옴 |
| 지급 → 차감 | 권리 회수 | 소비되면 불가능, 회수 API 부재 가능 | 공짜 이용권 영구 확정 |

부가 효과도 있다. 실패 확률이 가장 높은 검증(잔액 부족)을 첫 단계에서 겪게 되므로 **보상이 필요한 상황 자체가 줄어든다.** 지급 단계까지 도달한 흐름은 이미 잔액 검증을 통과한 흐름이라 대부분 성공한다.

### 2-3. 이중 쓰기 문제와 트랜잭셔널 아웃박스

순서를 정했다. 차감을 커밋하고, 콘텐츠 서비스에 지급을 요청한다. 그런데 여기 아직 구멍이 하나 남아 있다.

#### 이중 쓰기(dual write)란 무엇인가

**이중 쓰기(dual write)**는 하나의 논리적 작업을 위해 **서로 다른 두 저장소에 각각 써야 하는** 상황을 말한다. 여기서는 ① 우리 DB에 차감을 커밋하고, ② Kafka(또는 HTTP)로 지급 요청을 보내는 것 — 두 개의 쓰기다.

두 쓰기는 원자적일 수 없다. 서로 다른 시스템이고, 둘을 묶어줄 공통 트랜잭션이 없기 때문이다. 그래서 **그 사이에서 죽으면** 문제가 생긴다.

```
BEGIN
  UPDATE point_wallet ...   (차감)
COMMIT                      <- 여기까지 성공. 5,000P는 이미 빠졌다.
                            <- ★ 이 틈에서 서버가 죽으면?
kafkaTemplate.send(...)     <- 이 줄이 영영 실행되지 않는다.
```

커밋 직후, 발행 직전에 프로세스가 죽으면 "차감만 된 세계"가 소리 없이 남는다. 사용자 요청을 처리하던 스레드는 사라졌고, 이 주문을 이어서 처리할 주체가 아무 데도 없다. 며칠 뒤 CS로 발견된다.

반대 순서(먼저 발행하고 나중에 커밋)도 답이 아니다. 발행은 됐는데 커밋이 실패하면 콘텐츠 서비스가 존재하지도 않는 주문에 대해 이용권을 지급하게 된다.

#### 아웃박스(outbox) — 보낼 편지함

**아웃박스(outbox)는 말 그대로 "보낼 편지함"이다.** 메시지를 Kafka로 바로 쏘는 대신 **같은 DB의 outbox 테이블에 INSERT**해 둔다. 그러면 비즈니스 데이터 변경(차감)과 메시지 발행 기록이 **같은 트랜잭션 안의 두 쓰기**가 되므로, 둘 다 커밋되거나 둘 다 롤백된다 — 이중 쓰기가 단일 쓰기로 바뀐 것이다.

실제 발행은 **릴레이(relay)**라는 별도 프로세스가 맡는다. 릴레이는 outbox 테이블에서 아직 안 보낸 행을 읽어 Kafka로 발행하고, 성공하면 그 행을 발행 완료로 표시한다. 릴레이가 outbox를 읽는 방식은 둘 중 하나다.

- **폴링(polling)**: 몇 백 밀리초마다 `SELECT ... WHERE published_at IS NULL`로 미발행 행을 긁어간다. 구현이 단순해 대부분 여기서 시작한다.
- **CDC(Change Data Capture, 변경 데이터 캡처)**: DB의 복제 로그(PostgreSQL의 WAL)를 구독해 INSERT를 실시간으로 감지한다. Debezium이 대표적이다. 폴링 부하가 없고 지연이 짧지만 인프라가 하나 늘어난다.

이 구조를 **트랜잭셔널 아웃박스(transactional outbox)** 패턴이라고 부른다.

```
[요청 스레드]
  |
  |  BEGIN
  |    UPDATE point_wallet ...       (차감)
  |    INSERT INTO point_ledger ...  (원장 기록)
  |    UPDATE orders SET status=...  (주문 상태 DEDUCTED)
  |    INSERT INTO outbox ...        (보낼 메시지 예약)
  |  COMMIT   <- 네 줄이 전부 남거나 전부 없다. 틈이 없다.
  v
[outbox 테이블] <--- 릴레이가 폴링 또는 CDC로 읽는다
                         |
                         v
                     [Kafka] ---> [콘텐츠 서비스: 이용권 지급]
```

```sql
CREATE TABLE outbox (
    id            bigserial   PRIMARY KEY,
    aggregate_id  bigint      NOT NULL,   -- 여기서는 order_id
    event_type    varchar(60) NOT NULL,   -- ticket.grant.requested
    payload       jsonb       NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    published_at  timestamptz              -- NULL이면 아직 미발행
);
-- 미발행 행만 빠르게 긁기 위한 부분 인덱스.
-- 발행이 끝난 수백만 행까지 매번 훑지 않게 해준다.
CREATE INDEX idx_outbox_unpublished
    ON outbox (id) WHERE published_at IS NULL;
```

```java
@Transactional
public void deductAndRequestGrant(long userId, long orderId) {
    int updated = pointRepository.deduct(userId, 5000);
    if (updated == 0) throw new InsufficientPointException();

    ledgerRepository.append(orderId, userId, -5000, EntryType.DEDUCT);
    orderRepository.updateStatus(orderId, OrderStatus.DEDUCTED);

    // 카프카로 직접 보내지 않고 같은 DB의 테이블에 "예약"만 한다.
    // 이 INSERT는 위의 차감·원장·상태변경과 같은 트랜잭션이다.
    outboxRepository.save(OutboxMessage.of(
        "ticket.grant.requested", orderId, payload(userId, orderId)));

    // 커밋되면 차감·원장·주문상태·발행예약이 전부 남거나 전부 없다.
    // 커밋 직후 서버가 죽어도 outbox 행은 DB에 남아 있으므로
    // 되살아난 릴레이가 이어서 발행한다 — 흐름이 끊기지 않는다.
}
```

#### at-least-once — 최소 1회, 즉 2회 이상일 수도 있다

릴레이는 발행에 성공할 때까지 재시도한다. 덕분에 메시지 유실은 없어진다. 대신 새로운 성질이 생긴다.

릴레이가 Kafka 발행에 성공했는데 `published_at`을 찍기 직전에 죽으면 어떻게 될까? 되살아난 릴레이는 그 행이 아직 미발행이라고 보고 **한 번 더 발행한다.** 이것이 **at-least-once(최소 1회)** 전달이다. "적어도 한 번은 도착한다"는 보장이지 "정확히 한 번"이 아니다.

그래서 규칙이 하나 따라붙는다. **at-least-once로 보내는 쪽이 있으면, 받는 쪽은 반드시 멱등해야 한다.** 멱등성이 무엇이고 어떻게 구현하는지는 바로 다음 절과 3절 사례 3에서 다룬다.

### 2-4. 원장(ledger) — 잔액은 "현재", 원장은 "역사"

잔액 컬럼만 갱신하면 사고가 났을 때 **"왜 이 잔액이 됐는지"**를 재구성할 수 없다. 3,200P라는 숫자만 남아 있을 뿐, 언제 무엇 때문에 얼마가 오갔는지는 어디에도 없다.

그래서 모든 증감을 **원장(ledger)**에 남긴다. 원장은 회계에서 빌려온 말로, 돈의 모든 이동을 시간 순으로 적어 두는 장부다. 그리고 그 장부는 **append-only**여야 한다 — 이미 적은 줄은 고치지도 지우지도 않고 새 줄만 추가한다는 뜻이다. 잘못 적었으면 반대 방향으로 한 줄 더 적는다(1-2에서 말한 보상과 같은 사고방식이다).

```sql
CREATE TABLE point_ledger (
    id         bigserial    PRIMARY KEY,
    order_id   bigint       NOT NULL,
    user_id    bigint       NOT NULL,
    amount     int          NOT NULL,  -- 차감은 음수, 환급은 양수
    entry_type varchar(20)  NOT NULL,  -- DEDUCT / REFUND
    created_at timestamptz  NOT NULL DEFAULT now(),
    UNIQUE (order_id, entry_type)  -- 주문당 차감 1번, 환급 1번
);
```

`UNIQUE (order_id, entry_type)`이 이 테이블의 핵심이다. 이 한 줄이 차감과 환급을 **저절로 멱등하게** 만든다.

**멱등성(idempotency)**이란 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"이다. 전등의 "끄기" 버튼 같은 것이다 — 이미 꺼진 전등에 끄기를 열 번 눌러도 결과는 꺼진 상태 하나다.

원장에서 이게 어떻게 작동하는지 보자. 재시도 때문에 주문 8471의 환급이 두 번 실행됐다고 하자. 첫 번째 INSERT는 성공한다. 두 번째 INSERT는 `(8471, 'REFUND')`가 이미 존재하므로 **유니크 제약 위반으로 거부**된다. 애플리케이션이 이 예외를 "이미 처리됨"으로 해석하면 "환급 2번 = 공짜 5,000P" 사고가 DB 레벨에서 차단된다.

멱등성을 애플리케이션 if문(`if (이미 환급됐나?) return;`)으로 구현하지 않고 유니크 제약으로 구현한 점에 주목하자. if문은 2-1에서 본 check-then-act이므로 동시 요청 두 건이 나란히 통과할 수 있다. 유니크 제약은 DB 엔진이 쓰기 시점에 원자적으로 판정하므로 틈이 없다.

원장의 또 다른 쓸모는 **대사(reconciliation)**다. 대사란 서로 다른 곳에 기록된 숫자를 맞춰 보고 어긋난 부분을 찾아내는 회계 작업을 말한다. 잔액 컬럼과 `SUM(amount)`를 비교해 다르면 어딘가에서 사고가 난 것이다. 그래서 원장은 복구의 근거이자 **진실의 원본(source of truth)**이 된다 — 이 부분은 4절 꼬리질문에서 더 깊이 다룬다.

## 3. 실무 사례 — 중간에서 죽는 지점별 시나리오

앞 절의 부품들이 실제로 어떤 사고를 막는지, 사고 순간의 타임라인과 함께 본다. 이 세 가지를 즉석에서 열거할 수 있으면 "실패 지점을 설계 단계에서 세어보는 사람"으로 보인다.

### 사례 1: 차감 성공 → 지급 호출 타임아웃 (결과 불명)

```
시각   요청 스레드                     우리가 아는 사실
----   --------------------------      ------------------------------
t0     차감 트랜잭션 COMMIT             잔액 -5,000 / 원장 DEDUCT 기록
                                        / 주문 DEDUCTED
t1     지급 API 호출 (HTTP)             요청은 나갔다
t2     3초 타임아웃 발생                ??? <- 아는 것이 없다
```

**타임아웃은 실패가 아니라 결과 불명이다.** 이 구분이 핵심이다. 타임아웃이 났을 때 실제로 가능한 상황은 최소 셋이다.

- 요청이 상대에게 도착조차 못 했다 → 지급 안 됨
- 상대가 처리 중인데 아직 안 끝났다 → 곧 지급될 예정
- 상대가 지급을 끝냈는데 응답이 오는 길에 유실됐다 → 이미 지급됨

여기서 "실패했으니 환급하자"로 직행하면 세 번째 경우에 사고가 난다. 이용권도 받고 5,000P도 돌려받은 **공짜 세계**가 만들어진다.

**대응: 결과 불명은 확정부터 한다.**

1. 콘텐츠 서비스에 `orderId`로 **지급 여부 조회 API**를 호출해 현재 상태를 확인한다. 조회 API가 있다면 이게 가장 명확하다.
2. 조회 API가 없다면, 지급이 멱등하다는 전제 아래 **같은 orderId로 재시도**한다. 이미 지급됐다면 "이미 있음"이 돌아오고, 아직 안 됐다면 이번에 지급된다. 어느 쪽이든 상태가 확정된다.
3. 재시도 한도까지 갔는데도 **실패가 확정**된 경우에만 환급을 실행하고, 주문 상태를 `GRANT_FAILED` → `REFUNDED`로 전이시킨다.

주문 상태를 이렇게 전이시키는 이유는, 이 흐름이 어디까지 왔는지를 **DB에 남겨야** 다른 주체(배치, 다른 인스턴스, 운영자)가 이어받을 수 있기 때문이다. 상태 머신으로 그리면 이렇다.

```
CREATED
   |
   |  차감 성공
   v
DEDUCTED ------ 지급 성공 ------> COMPLETED
   |
   |  지급 확정 실패
   v
GRANT_FAILED
   |
   |  환급 성공
   v
REFUNDED

   (환급 재시도 한도 초과 시)
GRANT_FAILED -----> COMPENSATION_FAILED  ->  수동 개입 큐 + 알림
```

### 사례 2: 차감 커밋 직후 서버 크래시 — 아무도 모르는 미완결 흐름

차감을 커밋한 직후, 지급 요청을 보내기 직전에 파드가 재시작됐다. 아웃박스가 없는 구식 구현(커밋 후 코드에서 직접 HTTP 호출)이라면 주문은 `DEDUCTED`에서 **영원히** 멈춘다. 요청을 처리하던 스레드는 프로세스와 함께 사라졌고, 이 주문을 이어서 처리할 주체가 아무 데도 없다. 며칠 뒤 "5,000P 빠졌는데 이용권이 없다"는 CS로 발견된다.

**대응은 두 겹이다.**

**(1) 아웃박스를 쓰면 이 시나리오 자체가 사라진다.** 발행 예약이 차감과 같은 트랜잭션으로 DB에 남아 있으므로 릴레이가 되살아나 발행을 이어간다. 요청 스레드의 생사와 무관하게 흐름이 전진한다.

**(2) 그래도 안전망으로 미완결 주문 스캔 배치를 둔다.** 릴레이 자체가 장시간 죽어 있거나, 컨슈머 쪽에서 메시지가 처리되지 못하고 사라지는 경우까지 대비하는 층이다. `DEDUCTED` 상태로 N분 이상 머문 주문을 주기적으로 찾아 지급을 재개하거나 환급으로 종결한다.

```sql
-- 안전망 배치가 찾아내는 대상: 차감만 되고 5분 넘게 멈춘 주문
SELECT order_id, user_id, updated_at
  FROM orders
 WHERE status = 'DEDUCTED'
   AND updated_at < now() - interval '5 minutes'
 ORDER BY updated_at
 LIMIT 500;
```

핵심 교훈은 이것이다. **요청 스레드가 죽어도 흐름을 이어갈 주체(릴레이·배치)가 설계 안에 존재해야 한다.** 그리고 그 주체가 "어디까지 진행됐는지" 판단할 근거가 주문 상태와 원장이다. 상태를 DB에 남기지 않으면 이어받을 방법 자체가 없다.

### 사례 3: 지급은 됐는데 응답 유실 → 재시도로 이용권 2장

콘텐츠 서비스가 지급을 끝내고 응답을 보내는 중에 커넥션이 끊겼다. 요청 쪽은 사례 1의 절차대로 재시도한다. 그런데 지급 로직이 멱등하지 않으면 — 즉 그냥 `INSERT INTO ticket ...`이면 — 이용권이 2장 발급된다. 1장에 5,000P니까 사용자에게 5,000P어치 이익이고, 이런 경로가 알려지면 프로모션 어뷰징 통로가 된다.

**대응: 수신 쪽을 멱등하게 만든다.** 이용권 테이블에 `UNIQUE (order_id)`를 걸고 INSERT를 다음처럼 쓴다.

```sql
CREATE UNIQUE INDEX uq_ticket_order ON ticket (order_id);

INSERT INTO ticket (order_id, user_id, product_id)
VALUES (:orderId, :userId, :productId)
ON CONFLICT (order_id) DO NOTHING;  -- 이미 있으면 조용히 성공 취급
```

`ON CONFLICT ... DO NOTHING`은 PostgreSQL 문법으로, 유니크 충돌이 나면 예외를 던지는 대신 아무 일도 하지 않고 넘어간다. 두 번째 요청은 에러 없이 "성공"으로 응답되고, 이용권은 여전히 1장이다.

여기서 얻는 규칙 하나가 있다.

> **발신 쪽 재시도(at-least-once)와 수신 쪽 멱등성은 반드시 세트다.** 어느 한쪽만 있으면 유실(재시도가 없어서)이나 중복(멱등성이 없어서)이 남는다.

## 4. 꼬리질문 대비 포인트

### "왜 차감을 먼저 하나요? 지급 먼저가 사용자 경험엔 낫지 않나요?"

순서의 기준은 사용자 경험이 아니라 **보상의 확실성**이다.

차감의 보상(환급)은 잔액에 더하는 연산이라 논리적 실패 조건이 없고, 우리 시스템 안에서 끝난다. 지급의 보상(권리 회수)은 이미 소비됐으면 불가능하고, 회수 API가 없을 수도 있으며, 지급과 회수 사이의 틈에 공짜 사용이 가능하다.

사용자 경험 관점에서 봐도 결론은 같다. "차감됐다가 환급된" 고객은 안내와 사과로 정리되지만, "공짜로 지급된" 건은 회사 손실이자 어뷰징 통로이고 회수하려면 고객과 다퉈야 한다. 덧붙여 잔액 부족이라는 최다 실패 사유를 첫 단계에서 걸러내므로 **보상 빈도 자체가 줄어든다**는 점까지 말하면 좋다.

### "잔액을 SELECT ... FOR UPDATE로 잠그고 검사하면 안 되나요?"

된다. `SELECT ... FOR UPDATE`는 조회하면서 그 행에 배타 잠금을 거는 문법이라, 행을 먼저 잠가두면 2-1에서 본 check-then-act의 틈이 사라진다. 두 번째 요청은 첫 번째가 커밋할 때까지 SELECT 단계에서 대기하고, 깨어났을 때는 갱신된 잔액을 본다.

다만 조건부 UPDATE와 비교하면 두 가지가 아쉽다.

- **왕복이 2회다.** SELECT로 잠그고 UPDATE로 갱신하므로 DB 왕복이 두 번이고, 그 사이 애플리케이션 로직이 도는 동안에도 잠금을 쥐고 있다. 잠금 보유 시간이 길어지면 같은 행에 몰리는 요청의 대기 시간도 같이 길어진다.
- **검사와 갱신이 코드에서 분리된다.** 나중에 누군가 UPDATE 앞에 다른 로직을 끼워 넣거나, 다른 경로에서 FOR UPDATE 없이 조회 후 갱신하는 코드를 짜면 다시 뚫린다.

`FOR UPDATE`가 정당한 경우는 **차감 전에 잔액 외 여러 값을 읽어 복잡한 판단을 해야 할 때**다. 예를 들어 등급별 한도, 일일 사용 누적액, 보유 쿠폰을 함께 보고 차감액을 계산해야 한다면 한 문장의 UPDATE로 표현할 수 없으니 잠그고 읽는 편이 맞다. 단순 차감이라면 조건부 UPDATE가 기본기다.

### "외부 서비스 호출을 @Transactional 안에 두면 무슨 일이 생기나요?"

세 가지가 생긴다.

**(1) 커넥션 풀 고갈.** 외부 호출이 3초 걸리는 동안 DB 커넥션과 행 잠금을 쥔 채 기다린다. 커넥션 풀이 20개인 서비스에서 초당 30건 요청이 들어오면 순식간에 풀이 마르고, 결제와 무관한 다른 API까지 같이 죽는다. 외부 장애가 우리 서비스 전체 장애로 번지는 전형적인 경로다.

**(2) 외부 부수효과는 롤백되지 않는다.** 외부 호출(지급)은 성공했는데 그 뒤 커밋이 실패하면 DB는 롤백되지만 상대 시스템의 지급은 그대로 남는다. 즉 "차감 없이 지급된" 세계가 **트랜잭션 안에서** 만들어진다. `@Transactional`이 붙어 있어서 안전하다고 믿게 만드는 점이 오히려 위험하다.

**(3) 커밋 전에 이벤트를 발행하면 수신 쪽이 못 본다.** 반대로 커밋 전에 Kafka로 먼저 쏘면, 컨슈머가 즉시 우리 DB를 조회했을 때 아직 커밋되지 않은 주문이 보이지 않아 "그런 주문 없음"으로 실패한다. 커밋보다 이벤트가 빠른 경합이다.

세 문제 모두 **"커밋 후 발행"을 구조적으로 보장**하면 사라진다. 그것이 2-3의 트랜잭셔널 아웃박스다.

### "잔액 컬럼과 원장이 어긋나면 어느 쪽이 진실인가요?" (시니어 변별 포인트)

**원장이 진실이고 잔액은 파생값(캐시)이다.**

근거를 말할 수 있어야 한다. 원장은 append-only라 한 번 적힌 줄이 바뀌지 않으므로 조작·유실의 흔적이 남고, 모든 증감의 사유(`order_id`, `entry_type`, `created_at`)를 담고 있다. 반면 잔액 컬럼은 그 원장의 합계를 미리 계산해 둔 성능용 값일 뿐이고, UPDATE 한 번으로 과거 흔적 없이 덮어써진다.

그래서 대사 배치는 `SUM(amount)`와 잔액 컬럼을 비교해 불일치를 찾고, 불일치가 나오면 **원장 기준으로 잔액을 보정**한다.

```sql
-- 원장 합계와 잔액이 어긋난 사용자 찾기
SELECT w.user_id, w.balance, COALESCE(SUM(l.amount), 0) AS ledger_sum
  FROM point_wallet w
  LEFT JOIN point_ledger l ON l.user_id = w.user_id
 GROUP BY w.user_id, w.balance
HAVING w.balance <> COALESCE(SUM(l.amount), 0);
```

여기서 한 걸음 더 나가면 회계적 사고가 드러난다. "그럼 아예 잔액 컬럼을 없애고 매번 SUM 하면 되지 않나요?"에 대한 답은 — 원장이 수백만 행으로 자라면 조회마다 전체 합산은 감당할 수 없다. 그래서 실무에서는 **스냅샷 + 이후분 합산**으로 절충한다. 월말 시점의 잔액을 스냅샷 행으로 확정해 두고, 조회 시에는 "스냅샷 잔액 + 스냅샷 이후 원장 합계"만 계산한다. 원본과 파생을 구분하되 파생을 성능을 위해 유지한다는 구도다.

### "환급(보상)마저 실패하면 어떻게 하나요?"

환급은 더하기라 잔액 부족 같은 **논리적** 실패는 없지만, 포인트 서비스 장애나 네트워크 단절 같은 **일시적** 실패는 얼마든지 난다.

3단으로 답한다.

1. 환급 요청도 아웃박스나 재시도 큐에 태워 **지수 백오프**(재시도 간격을 1초, 2초, 4초... 로 늘려 이미 힘든 상대 시스템에 부하를 더 주지 않는 방식)를 두고 자동 재시도한다.
2. 재시도 한도(예: 5회)를 넘기면 주문을 `COMPENSATION_FAILED`로 전이시킨다. 이 상태의 의미는 "시스템이 자동으로 해결하지 못했고, 그 사실을 알고 있다"이다.
3. 동시에 **수동 개입 큐** — 운영자가 보는 보정 대기 목록 테이블 — 에 `orderId`, 금액, 실패 사유, 마지막 시도 시각을 적재하고 알림을 쏜다.

핵심 원칙은 이것이다. **돈이 붕 뜬 상태를 시스템이 "모르는 채" 두지 않는다.** 자동 복구가 실패하는 것 자체는 어쩔 수 없지만, 실패했다는 사실이 아무 데도 기록되지 않는 것은 설계 결함이다. 반드시 사람 눈에 닿는 경로를 만들어 두는 것 — 이것이 돈 도메인에서 재시도의 끝단이다.

## 한 줄 요약

같은 DB면 단일 트랜잭션 + 조건부 UPDATE(`balance = balance - ? WHERE balance >= ?`)로 차감·지급을 한 몸으로 묶어 lost update까지 막고, 다른 시스템이면 **보상이 확실한 차감을 먼저** 실행한 뒤 지급 실패 시 환급으로 수렴시킨다 — 그 수렴을 실제로 굴리는 부품이 트랜잭셔널 아웃박스(같은 트랜잭션에 메시지를 예약해 커밋과 발행을 한 몸으로), 멱등한 지급·환급(유니크 제약으로 중복 실행 차단), append-only 원장(복구와 대사의 근거)이며, 설계의 완성도는 "중간에서 죽는 지점마다 복구 경로가 있는가"로 검증된다.
