# 웹훅 수신 처리 — 위조되고, 중복 오고, 순서가 뒤집힌다는 전제로 설계한다

> 핵심 관전 포인트: **웹훅은 인터넷 어디서든 열려 있는 내 엔드포인트로 날아오는 HTTP 요청일 뿐이다. 그래서 세 가지를 전제해야 한다 — (1) 위조될 수 있다: HMAC 서명 검증으로 발신자를 확인하고, 그래도 페이로드의 금액·상태를 믿지 말고 거래 조회 API로 재확인한다. (2) 중복 온다: 발신측 재시도는 at-least-once이므로 이벤트 ID에 유니크 제약을 걸어 두 번째부터는 조용히 버린다. (3) 순서가 뒤집힌다: 취소 웹훅이 승인 웹훅보다 먼저 도착할 수 있으므로, 도착 순서가 아니라 상태 머신의 전이 규칙으로 반영 여부를 정한다. 여기에 운영 원칙 두 가지 — 검증·저장만 하고 빠르게 200을 준 뒤 처리는 비동기로 분리하고, 웹훅이 아예 유실될 경우를 대비해 보정 폴링(조회 API 기반 대사)을 깔아둔다. 셋 중 하나라도 빼먹으면 각각 보안 사고, 이중 지급, 상태 꼬임으로 직결된다.**

---

## 0. 질문 + 의도

**질문**: "웹훅(callback) 수신 처리 시 주의할 점은 무엇인가요? (검증, 멱등성, 순서)"

**출제 의도**: 웹훅은 위조 가능하고(검증), 중복으로 오고(멱등성), 순서가 뒤집힌다(상태 머신 검증). 셋 중 하나라도 빼먹으면 각각 보안 사고, 이중 지급, 상태 꼬임이 된다 — 결제 웹훅 수신부 설계의 필수 체크리스트를 갖췄는지 본다.

## 1. 왜 문제인가 — 웹훅은 "믿을 수 없는 전화 통보"다

### 1-1. 전제 지식 — 폴링과 웹훅은 "내가 물어보기" vs "상대가 알려주기"

웹훅 이야기를 하기 전에, 애초에 남의 시스템에서 벌어진 일을 알아내는 방법이 몇 가지나 되는지부터 정리하자. 근본적으로 두 가지뿐이다.

첫 번째는 **폴링(polling)** 이다. 내가 주기적으로 상대에게 전화를 걸어 "그 결제 끝났어?"라고 물어보는 방식이다. 영어 poll이 "여론 조사하다, 물어보다"라는 뜻이라 붙은 이름이다. 구현이 단순하고, 전적으로 내 통제 아래 있다는 장점이 있다. 상대가 아무 연락을 안 해도 내가 물어보면 되니까.

폴링의 대가는 "지연이냐 부하냐"의 맞바꿈이다. 1분에 한 번 물으면 최악의 경우 결제가 끝나고 59초 뒤에야 알게 되고, 1초에 한 번 물으면 지연은 줄지만 아무 일도 없는데 상대 서버를 초당 한 번씩 두드리게 된다. 결제 건수가 늘면 이 낭비가 그대로 곱해진다.

두 번째가 **웹훅(webhook)** 이다. 상대 시스템에 "이런 일이 생기면 이 URL로 알려줘"라고 미리 등록해두면, 사건이 났을 때 상대가 내 URL로 HTTP 요청을 보내주는 방식이다. 이름은 웹(HTTP)에 걸어두는 훅(hook, 갈고리 — 프로그래밍에서 "특정 사건이 났을 때 불려나갈 자리"를 뜻한다)에서 왔다. 내가 코드를 걸어두면 사건이 그 코드를 잡아당겨 준다는 그림이다.

웹훅의 대가는 **통제권이 상대에게 넘어간다**는 것이다. 언제 올지, 몇 번 올지, 어떤 순서로 올지, 아예 오기는 할지를 내가 정하지 못한다. 이 문서가 다루는 문제는 전부 이 한 줄에서 파생된다.

| | 폴링 | 웹훅 |
|---|---|---|
| 트리거 | 내가 건다 | 상대가 건다 |
| 지연 | 폴링 주기만큼 | 거의 즉시 |
| 낭비 요청 | 많다(대부분 "변화 없음") | 없다 |
| 통제권 | 나 | 상대 |
| 유실 시 | 다음 주기에 자동 복구 | 복구 수단이 없다 |
| 위조 위험 | 없음(내가 건 요청의 응답) | 있음(남이 건 요청) |

마지막 두 줄이 핵심이다. 폴링은 느리지만 스스로 복구되고 위조될 일이 없다. 웹훅은 빠르지만 유실되면 끝이고 위조가 가능하다. 그래서 결론을 미리 말하면 — 실무는 둘 중 하나를 고르는 게 아니라 **웹훅을 1차 트리거로 쓰고 폴링을 안전망으로 까는** 조합을 쓴다(2-6절).

### 1-2. 결제 도메인에서 웹훅이 나르는 것

결제에서 웹훅으로 오는 대표적인 사건은 이런 것들이다.

- **승인 완료**: 카드 결제가 최종 승인됐다.
- **가상계좌 입금**: 고객이 발급받은 계좌로 실제로 돈을 넣었다.
- **결제 취소·환불 완료**: 취소 처리가 PG사 원장에 반영됐다.
- **정기결제 청구 결과**: 매달 자동 청구의 성공·실패.

이 중 가상계좌는 웹훅 없이는 사실상 성립하지 않는다. 고객이 언제 입금할지 아무도 모르기 때문이다. 10분 뒤일 수도 있고 사흘 뒤일 수도 있다. "돈이 들어왔는지"를 폴링으로만 확인하려면 모든 미입금 주문을 며칠 동안 계속 조회해야 한다. 그래서 웹훅이 필요하다.

### 1-3. 비유 — 은행에서 걸려온 "입금됐습니다" 전화

웹훅을 한 문장으로 비유하면 **은행이 전화로 "입금됐습니다"라고 알려주는 것**이다. 편리하다. 내가 계좌를 계속 들여다볼 필요가 없으니까. 그런데 이 전화를 그대로 믿고 장부에 적으면 세 가지 사고가 난다.

- 전화한 사람이 진짜 은행 직원인지 알 수 없다 — **위조**. 사기꾼이 "입금됐어요"라고 전화하면 물건을 공짜로 내주게 된다.
- 은행이 "아까 전화가 잘 갔는지 확실치 않아서요" 하며 같은 내용을 두 번 전화한다 — **중복**. 두 번 다 입금 처리하면 잔액이 이중으로 늘어난다.
- 통신 사정으로 "입금 취소" 전화가 "입금 완료" 전화보다 먼저 도착한다 — **순서 역전**. 나중에 온 "완료" 전화가 이미 취소된 거래를 완료 상태로 되살린다.

이 세 가지가 웹훅 수신부 설계의 전부다. 이제 각각이 왜 "재수 없는 예외"가 아니라 **정상적으로 일어나는 일**인지를 기술적으로 짚자.

### 1-4. 왜 위조가 가능한가 — 엔드포인트는 공개 인터넷에 열려 있다

웹훅 엔드포인트는 PG사 서버가 호출해야 한다. PG사 서버는 우리 사내망 안에 있지 않다. 따라서 이 URL은 **공개 인터넷에서 접근 가능한 상태로 열어둘 수밖에 없다.** 여기까지는 선택의 여지가 없는 구조적 사실이다.

그런데 HTTP 요청은 누구나 만들 수 있다. URL만 알면 공격자도 `curl`로 똑같은 형식의 JSON을 던질 수 있고, 서버 입장에서 그 요청은 PG사가 보낸 요청과 바이트 단위로 구분되지 않는다. "출처가 PG사인지"를 확인해주는 장치가 HTTP 자체에는 없기 때문이다.

URL을 아무도 모르게 하면 되지 않느냐고 할 수 있다. 이걸 보안 용어로 **모호성에 의한 보안(security by obscurity)** 이라고 부르는데, 웹훅에서는 특히 위험하다. URL은 PG사 관리자 콘솔, 연동 문서, 우리 쪽 설정 파일, 로그, 스크린샷 등 여러 곳을 돌아다닌다. 게다가 주문번호처럼 규칙성 있는 값이 URL이나 페이로드에 들어 있으면 공격자가 형식을 추측하기도 쉽다. 비밀 URL은 방어가 아니라 운이다.

### 1-5. 왜 중복이 오는가 — at-least-once가 무슨 뜻인가

발신측(PG사)은 우리에게 요청을 보내고 응답을 기다린다. 2xx 응답을 받으면 "전달 성공"으로 표시하고, 못 받으면 실패로 보고 잠시 후 다시 보낸다. 여기까지는 상식적이다.

문제는 **응답을 못 받은 것이 "처리가 안 됐다"는 뜻은 아니라는** 점이다. 우리가 적립금을 지급하고 200을 반환하는 그 찰나에 로드 밸런서 커넥션이 끊기면, 우리는 처리를 끝냈는데 발신측은 실패로 안다. 그리고 재전송한다. 우리는 같은 이벤트를 두 번 받는다.

이 상황은 원리적으로 피할 수 없다. 발신측이 취할 수 있는 태도는 둘뿐이기 때문이다.

- **at-most-once(최대 1회)**: 응답을 못 받아도 재전송하지 않는다. 중복은 없지만 **유실**이 생긴다. 결제 승인 통보가 사라지는 것을 허용하는 셈이니 결제에서는 쓸 수 없다.
- **at-least-once(최소 1회)**: 확실해질 때까지 재전송한다. 유실은 없지만 **중복**이 생긴다.

"정확히 한 번(exactly-once)"은 없느냐고 물으면, 서로 다른 두 시스템 사이의 네트워크 위에서는 만들 수 없다. 마지막 메시지가 도착했는지를 확인하는 메시지 역시 도착 여부를 알 수 없어서, 확인의 확인이 무한히 필요해지기 때문이다. 그래서 실무의 exactly-once는 **"at-least-once 전달 + 수신측 중복 제거"** 의 조합을 부르는 이름이다. 즉 **중복 제거는 수신측 책임**이다. 이걸 발신측 탓으로 돌리면 설계가 시작되지 않는다.

### 1-6. 왜 순서가 뒤집히는가 — 재시도가 순서를 흩뜨린다

이벤트가 발생한 순서와 도착한 순서가 다를 수 있는 이유는 여러 가지다. 발신측이 여러 워커로 병렬 발송하거나, 네트워크 경로가 달라지거나, 우리 쪽 여러 인스턴스가 각각 다른 속도로 처리하거나. 하지만 실무에서 압도적으로 흔한 원인은 **재시도**다.

한 이벤트가 재시도 대기열에 들어가 몇 분을 기다리는 동안, 그 뒤에 발생한 이벤트는 한 번에 성공해 먼저 도착한다. 이건 우연이 아니라 재시도 메커니즘이 있는 한 반드시 생기는 구조적 현상이다.

```
[ 이벤트 발생 순서 — PG사 서버 기준 ]
  10:00:00.000  승인 이벤트(evt-A) 발생   결제 승인됨 120,000원
  10:00:03.000  취소 이벤트(evt-B) 발생   고객이 즉시 취소

[ 발신측의 전송 시도 ]
  10:00:00.010  evt-A 1차 발송  ──X  타임아웃 (우리 서버 순간 지연)
                                     → 재시도 큐로 이동, 1분 뒤 예약
  10:00:03.010  evt-B 1차 발송  ──>  200 OK  (성공)
  10:01:00.010  evt-A 2차 발송  ──>  200 OK  (재시도 성공)

[ 우리 수신부가 실제로 본 순서 ]
  ① 10:00:03  취소(evt-B) 도착  →  주문 상태 CANCELLED
  ② 10:01:00  승인(evt-A) 도착  →  ???

     "마지막에 온 게 최신"으로 처리하면  →  주문이 PAID로 되살아난다
     환불은 나갔는데 상품은 출고된다. 120,000원 손실.
```

여기서 얻어야 할 결론은 하나다. **도착 순서는 사건의 순서에 대한 아무 정보도 주지 않는다.** "승인 → 취소" 순으로 발생한 사건이 "취소 → 승인" 순으로 도착하는 것은 장애가 아니라 정상 상황이며, 수신부는 이 상황에서도 올바른 상태를 유지해야 한다.

## 2. 수신부 설계 — 검증, 멱등, 순서, 그리고 분리

### 2-1. 1차 방어: 발신자 검증 — HMAC 서명이 본체, IP 화이트리스트는 보조

결론에 앞서 선택지부터 보자. "이 요청이 진짜 PG사에서 왔는가"를 확인하는 방법은 크게 두 갈래뿐이다.

- (a) **어디서 왔는지 본다** — 발신 IP를 확인한다.
- (b) **아무나 못 만드는 증거물을 요구한다** — 서명을 검증한다.

상호 TLS(mTLS, 클라이언트도 인증서를 제시하는 방식)라는 세 번째 길도 있지만, PG사가 지원해야 쓸 수 있고 인증서 관리 부담이 커서 일반적인 웹훅 연동에서는 표준이 아니다. 실무에서 실제로 고르는 것은 (a)와 (b)이고, 정답은 "(b)가 본체, (a)는 보조"다. 왜 그런지 순서대로 보자.

먼저 해시가 무엇인지부터. 해시 함수는 임의 길이의 입력을 고정 길이의 값으로 뭉개는 단방향 함수다. 같은 입력은 항상 같은 출력을 내지만, 출력에서 입력을 되돌릴 수는 없다. 그래서 "이 데이터의 지문"으로 쓰인다 — 본문이 한 글자만 바뀌어도 지문이 완전히 달라지므로, 지문을 비교하면 본문이 변조됐는지 알 수 있다.

그런데 지문만 붙여 보내면 소용이 없다. 공격자도 같은 해시 함수를 돌릴 수 있어서, 본문을 위조한 뒤 그에 맞는 지문을 새로 계산해 붙이면 그만이기 때문이다. 지문을 **발신자만 만들 수 있게** 해야 한다. 여기서 비밀키가 등장한다.

**HMAC(Hash-based Message Authentication Code)은 "비밀키를 섞어 만든 지문"이다.** 발신자와 우리만 아는 비밀값(시크릿)을 본문과 함께 해싱하기 때문에, 시크릿을 모르는 제3자는 본문을 위조해도 같은 지문을 만들 수 없다. PG사는 `HMAC-SHA256(시크릿, 타임스탬프 + 본문)`을 계산해 `X-Signature` 같은 헤더에 실어 보내고, 우리는 우리가 가진 같은 시크릿으로 같은 계산을 해서 값이 일치하는지 본다.

비유하자면 인감도장이다. 도장 자국(서명)은 누구나 볼 수 있지만, 도장 자체(시크릿)를 가진 사람만 같은 자국을 찍을 수 있다. 그래서 HMAC은 **발신자가 누구인지(인증)** 와 **본문이 변조되지 않았는지(무결성)** 를 한 번에 증명한다.

비교할 때 `equals`를 쓰면 안 되는 이유도 짚어야 한다. 자바의 문자열 비교는 앞에서부터 한 글자씩 보다가 다른 글자를 만나면 즉시 끝난다. 그래서 첫 글자부터 틀린 값은 빨리 실패하고, 앞 열 글자가 맞는 값은 조금 더 오래 걸린다. 이 미세한 시간 차이가 "몇 글자까지 맞췄는지"를 공격자에게 알려주는 통로가 된다.

공격자는 첫 글자를 0부터 f까지 바꿔가며 응답 시간이 미세하게 늘어나는 값을 찾고, 그 자리를 확정한 뒤 다음 글자로 넘어가는 식으로 서명을 한 글자씩 복원할 수 있다. 이것을 **타이밍 공격(timing attack)** 이라 한다. 그래서 서명 비교는 **길이와 무관하게 항상 같은 시간이 걸리는** 상수 시간 비교 함수로 해야 한다. 자바에서는 `MessageDigest.isEqual`이 그 역할을 한다 — 중간에 끊지 않고 모든 바이트를 끝까지 훑어 차이를 누적한 뒤 마지막에 한 번 판정하기 때문에 실행 시간이 입력에 따라 달라지지 않는다.

타임스탬프가 서명에 들어가야 하는 이유도 같은 맥락이다. 서명이 유효하다는 것은 "PG사가 만든 요청"이라는 뜻이지 "지금 만든 요청"이라는 뜻이 아니다. 공격자가 네트워크 중간에서 정상 요청 하나를 통째로 복사해 뒀다가 나중에 그대로 다시 보내면, 서명은 여전히 유효하다. 이것이 **재전송 공격(replay attack)** 이다. 승인 웹훅 하나를 백 번 재생해 적립금을 백 번 받는 식의 공격이 가능해진다.

막는 방법은 요청에 "언제 만들어졌는지"를 넣고 그 값까지 서명에 포함시키는 것이다. 그러면 공격자는 타임스탬프를 고칠 수 없고(고치면 서명이 깨진다), 우리는 타임스탬프가 현재 시각에서 허용 오차(보통 5분)를 벗어나면 거부하면 된다. 5분이라는 값은 "발신·수신 서버의 시계 오차와 정상적인 네트워크 지연은 흡수하되, 공격자가 재생을 시도할 창은 최대한 좁힌다"는 절충이다.

그럼 IP 화이트리스트만으로는 왜 부족한가. 세 가지 이유가 있다.

- PG사가 발신 인프라를 클라우드·CDN으로 옮기면 발신 IP 대역이 예고 없이 바뀐다. 그 순간 정상 웹훅이 전부 차단되는 가용성 사고가 난다. 즉 IP 제한은 보안 장치이면서 동시에 **장애 유발 장치**다.
- 클라우드 NAT나 공유 프록시 뒤에서는 같은 IP 대역을 제3자도 쓸 수 있다. "이 IP = PG사"라는 등식이 성립하지 않는다. 실제로 IP 대역이 넓어졌을 때 운영팀이 장애를 피하려 대역 전체를 허용하는 순간, 그 대역의 다른 고객도 우리 엔드포인트를 두드릴 수 있게 된다.
- 무엇보다 IP는 **본문이 변조되지 않았다는 보장을 전혀 주지 못한다.** 발신 위치만 말해줄 뿐이다.

그래서 정리는 이렇다. **서명 검증이 필수 방어, IP 제한은 공격 표면을 줄이는 보조 방어.** IP 제한을 걸면 무작위 스캐너가 우리 엔드포인트에 닿는 것 자체를 막을 수 있으니 없는 것보다는 낫다. 다만 그것만 믿어서는 안 된다.

구현에서 자주 밟는 함정이 하나 있다. **서명은 반드시 원문 바이트로 검증해야 한다.** JSON을 객체로 파싱했다가 다시 문자열로 직렬화하면 필드 순서, 공백, 숫자 표기(`1.0` vs `1.00`)가 달라질 수 있다. 한 바이트만 달라도 해시는 완전히 달라지므로 정상 요청의 서명이 깨진다. 그래서 컨트롤러는 DTO가 아니라 `String rawBody`(또는 `byte[]`)로 받아 그 원문으로 검증한 뒤에 파싱해야 한다.

### 2-2. 2차 방어: 페이로드를 믿지 말고 거래 조회 API로 재확인한다

서명 검증까지 통과했으면 이제 본문을 믿어도 될까. 결제 도메인의 관례는 "아니오"다. 이유는 서명이 증명해주는 범위가 생각보다 좁기 때문이다.

서명이 증명하는 것은 **"이 바이트열은 시크릿을 가진 쪽이 만들었고 전송 중 변조되지 않았다"** 까지다. 다음 것들은 증명하지 않는다.

- 우리 쪽 서명 검증 구현에 실수가 없다는 것(재직렬화 본문으로 검증하고 있었다거나, 검증 실패를 로그만 남기고 통과시키고 있었다거나).
- 시크릿이 유출되지 않았다는 것(설정 파일이 git에 올라갔거나, 로그에 찍혔거나, 퇴사자가 들고 나갔거나).
- 발신측이 버그로 잘못된 값을 보내지 않았다는 것.

돈이 걸린 값 — 금액과 상태 — 에 대해서는 이 정도 확률도 감당하기 어렵다. 그래서 신뢰 경계(trust boundary, 시스템이 "여기서부터는 믿지 않는다"라고 선을 긋는 지점)를 한 겹 더 둔다.

패턴은 이렇다. **웹훅 본문에서는 키(거래 ID, 이벤트 ID)만 취하고, 금액·상태는 PG사의 거래 조회 API를 호출해 받아온 값으로 확정한다.** 위조된 5만원짜리 승인 통보가 들어와도, 조회 API가 "그 거래는 아직 READY(승인 전)입니다"라고 답하면 아무 일도 일어나지 않는다. 어떤 경로로 이상한 페이로드가 들어와도 최종 반영되는 값은 PG사 원장에서 직접 읽은 값이기 때문이다.

한 문장으로 요약하면 **"웹훅은 초인종, 진실은 조회 API"** 다. 웹훅의 역할을 "지금 조회해보라고 알려주는 신호"로 격하시키는 것이다. 이렇게 보면 앞서 1-1절에서 본 폴링과 웹훅의 구도가 다시 나타난다 — 정합성은 조회(폴링)가 책임지고, 웹훅은 조회 타이밍을 앞당기는 최적화다.

비용은 물론 있다. 이벤트마다 외부 API 호출이 한 번씩 늘어난다. 이 호출은 수백 ms가 걸릴 수 있고 PG사 장애 시 실패할 수도 있다. 그래서 조회는 웹훅 응답을 돌려주는 동기 구간이 아니라 **비동기 워커 안에서** 한다(2-5절). 급한 것은 응답이고, 정확한 것은 나중에 해도 된다.

### 2-3. 3차 방어: 멱등성 — 이벤트 ID + 유니크 제약으로 중복을 제거한다

**멱등(idempotent)** 은 "여러 번 해도 한 번 한 것과 결과가 같다"는 성질이다. 수학에서 온 말인데(같은 연산을 거듭 적용해도 값이 변하지 않는다는 뜻), 분산 시스템에서는 재시도를 안전하게 만드는 핵심 성질로 쓰인다.

엘리베이터 버튼이 멱등하다. 열 번 눌러도 엘리베이터는 한 번 온다. 반대로 "잔액에 3,000원 더하기"는 멱등하지 않다. 두 번 하면 6,000원이 늘어난다. 웹훅 처리는 재시도로 여러 번 도착하므로, 반드시 멱등하게 만들어야 한다.

그럼 어떻게 만드는가. 방법은 "이미 처리한 이벤트인지 기억하고 두 번째부터는 건너뛴다"이다. 기억할 열쇠가 필요한데, 그게 발신측이 이벤트마다 부여하는 고유 ID(`event_id`)다. 재시도할 때도 같은 ID를 유지하는 것이 웹훅 발신측의 기본 계약이다.

여기서 초보적인 구현이 하나 있다. "먼저 조회해서 없으면 INSERT 한다"는 방식인데, 이게 동시 도착에 뚫린다. 왜 뚫리는지 시간축으로 보자.

```
     스레드 1 (1차 도착)              스레드 2 (재전송 도착)
t1   SELECT ... WHERE event_id='e1'
     → 없음
t2                                    SELECT ... WHERE event_id='e1'
                                      → 없음  (스레드 1이 아직 INSERT 전)
t3   INSERT event_id='e1'
t4   적립금 3,000원 지급
t5                                    INSERT event_id='e1'
                                      (유니크 제약이 없으면 성공한다)
t6                                    적립금 3,000원 또 지급  ← 이중 지급
```

이 구조를 **check-then-act(확인하고 나서 행동하기)** 라고 부른다. 확인과 행동 사이에 틈이 있고, 그 틈에 남이 끼어들 수 있다. 웹훅 재전송은 보통 수십 초 뒤에 오니 괜찮지 않냐고 생각하기 쉽지만, 발신측 장애가 복구되면서 밀린 재전송이 한꺼번에 쏟아지면 밀리초 단위로 겹쳐 도착한다. 그때 이 틈이 열린다.

해결은 확인과 선점을 한 문장으로 합치는 것이다. DB의 유니크 제약은 엔진 수준에서 직렬화되므로, 같은 키로 동시에 두 개가 들어오면 반드시 하나만 성공한다. 즉 INSERT의 성공 여부 자체가 "내가 처음이다"의 증거가 된다.

```sql
-- PostgreSQL: 수신한 웹훅 이벤트를 그대로 적어두는 원장 테이블
CREATE TABLE webhook_event (
    event_id     text PRIMARY KEY,           -- PG사가 준 이벤트 고유 ID.
                                             -- PK = 유니크 제약이므로
                                             -- 같은 ID의 두 번째 INSERT는
                                             -- DB가 막아준다 (중복 제거의 근거)
    event_type   text        NOT NULL,       -- APPROVED, CANCELLED ...
    payment_key  text        NOT NULL,       -- 거래 식별자. 조회 API 호출용 키
    payload      jsonb       NOT NULL,       -- 원문 보관. 나중에 "그때 뭐가
                                             -- 왔길래 이렇게 처리됐지"를
                                             -- 되짚거나 재처리할 때 필요하다
    status       text        NOT NULL DEFAULT 'RECEIVED',
                                             -- RECEIVED → PROCESSED | FAILED.
                                             -- 워커가 죽어도 여기 남아 있어야
                                             -- 재처리 배치가 다시 집는다
    received_at  timestamptz NOT NULL DEFAULT now()
);
```

```sql
-- 검사와 선점을 한 문장으로: 이미 있으면 아무것도 하지 않고 넘어간다
INSERT INTO webhook_event (event_id, event_type, payment_key, payload)
VALUES (:eventId, :eventType, :paymentKey, :payload::jsonb)
ON CONFLICT (event_id) DO NOTHING;
-- 반환된 "영향받은 행 수"가 1이면 최초 도착, 0이면 중복이다.
-- 이 판정이 원자적이라는 게 핵심 — SELECT로 확인하는 순간과
-- INSERT하는 순간 사이에 틈이 없다.
```

중복일 때 어떤 상태 코드를 줘야 하는가도 중요하다. 답은 **200**이다. 409나 4xx를 주면 발신측이 "전달 실패"로 해석해 계속 재전송하거나, 재시도 한도를 소진하고 데드레터로 보내 상대 운영팀에 알람을 울린다. 중복은 우리 입장에서 "이미 반영이 끝난 정상 상황"이므로, 성공을 알려 재시도를 끝내주는 것이 맞다.

### 2-4. 4차 방어: 순서 역전 — 도착 순서가 아니라 상태 머신이 정한다

1-6절에서 봤듯 도착 순서는 믿을 수 없다. 그럼 무엇을 근거로 "이 이벤트를 반영할지 말지"를 정해야 할까. 선택지를 늘어놓고 보자.

- (a) **도착 순서대로 덮어쓴다(last-write-wins)**: 늦게 온 승인이 취소를 덮어써서 사고가 난다. 탈락.
- (b) **이벤트의 발생 시각을 비교해 더 최신 것만 반영한다**: 방향은 맞지만 두 가지 문제가 있다. 발신측 서버의 시계를 우리가 검증할 수 없고(서버 간 시계는 늘 조금씩 어긋난다), 같은 초에 발생한 두 이벤트는 구분이 안 되며, 애초에 발생 시각을 안 주는 PG사도 있다.
- (c) **현재 상태에서 그 전이가 허용되는지로 판단한다**: 외부 시계에 의존하지 않고, 우리 DB에 있는 현재 상태만으로 결정할 수 있다.

정답은 (c)이고, (b)는 (c)를 보조하는 근거로만 쓴다. (c)를 구현하는 장치가 **상태 머신(state machine)** 이다.

상태 머신은 두 가지로 정의된다 — **가질 수 있는 상태의 목록**과 **어떤 상태에서 어떤 상태로 갈 수 있는지의 목록(전이 규칙)**. 여기 없는 전이는 일어날 수 없다고 선언하는 것이 핵심이다. 보드게임의 말과 같다. 말이 놓일 수 있는 칸이 정해져 있고, 각 칸에서 갈 수 있는 다음 칸도 정해져 있다. 규칙에 없는 이동은 "그런 수는 없다"며 거부한다.

```
[ 결제 상태 머신 ]

  READY ──────> IN_PROGRESS ──────> PAID ──────> CANCELLED
    │                                 │
    │                                 └──> PARTIAL_CANCELLED ──> CANCELLED
    │
    └──────> EXPIRED

  종결 상태(어떤 전이도 나가지 않는다): CANCELLED, EXPIRED

  ※ 화살표가 없는 이동은 전부 거부한다.
    특히 CANCELLED ─X─> PAID  (취소된 결제는 되살아나지 않는다)
```

이 규칙을 1-6절의 타임라인에 적용하면 이렇게 갈린다.

| 시각 | 도착한 이벤트 | last-write-wins | 상태 머신 검증 |
|---|---|---|---|
| 10:00:03 | 취소(evt-B) | READY → CANCELLED | READY → CANCELLED (허용) |
| 10:01:00 | 승인(evt-A) | CANCELLED → **PAID** | CANCELLED → PAID는 규칙에 없음 → **무시, 200 응답** |
| 결과 | | 환불했는데 상품 출고 | 취소 상태 유지, 정상 |

"버린다"는 것이 무슨 뜻인지 정확히 하자. 예외를 던져 4xx를 주는 게 아니다. 상태는 바꾸지 않고, 이벤트는 `webhook_event`에 그대로 남기고(감사 추적용), 로그에 "역전 이벤트 무시" 기록을 남긴 뒤 **200을 응답**한다. 상태 코드는 "잘 받았다"의 의미이지 "반영했다"의 의미가 아니기 때문이다. 여기서 4xx를 주면 발신측이 영원히 재시도한다.

반대 방향, 즉 승인보다 취소가 먼저 오는 경우는 조금 더 미묘하다. `READY` 상태인 주문에 취소 웹훅이 왔다는 뜻인데, 두 가지 전략이 있다.

- (가) `READY → CANCELLED`를 허용 전이로 정의하고 바로 종결한다. 단순하고, 이후 승인 웹훅이 와도 CANCELLED가 종결 상태라 막힌다.
- (나) "아직 승인도 안 됐는데 취소가 왔다"를 이상 신호로 보고 보류 큐에 넣은 뒤, 잠시 후 조회 API로 PG사의 최종 상태를 확인해 확정한다. 느리지만, PG사가 실제로는 승인 후 취소한 건인지 아니면 애초에 승인이 안 된 건인지를 구분할 수 있다.

어느 쪽을 택하든 공통 원칙은 같다 — **도착 순서에 상태를 맡기지 않는다.** 발생 시각과 시퀀스 번호가 페이로드에 있으면 보조 판단 근거로는 쓰되, 그것만으로 결정하지는 않는다.

### 2-5. 운영 원칙 하나: 빠른 200 + 비동기 처리 — 수신과 처리의 분리

발신측은 응답이 일정 시간(보통 5~10초) 안에 오지 않으면 타임아웃으로 간주하고 재전송한다. 그런데 수신 핸들러 안에서 조회 API 호출, 포인트 적립, 알림 발송, 정산 반영까지 다 하면 처리 시간이 쉽게 그 한계를 넘는다.

여기서 벌어지는 일이 고약하다. **정상 처리를 다 해놓고도 응답이 늦어 타임아웃 → 재전송 → 또 처리 → 또 타임아웃**의 루프가 생긴다. 장애를 우리가 스스로 만드는 셈이다. 게다가 재전송이 쌓일수록 처리 부하가 늘어 응답은 더 느려진다.

그래서 동기 구간과 비동기 구간을 나눈다. 나누는 기준은 한 가지 질문이다 — **"이 작업을 안 하면 이벤트가 영영 사라지는가?"**

- 서명 검증: 안 하면 위조가 들어온다. 동기 구간에 필수.
- 이벤트 DB 저장: 안 하면 200을 준 뒤 이벤트가 증발한다. 동기 구간에 필수.
- 조회 API 호출, 상태 반영, 적립, 알림: 이벤트가 DB에 남아 있으면 나중에 해도 된다. 비동기로.

그래서 동기 구간은 "검증 + 저장"까지만 하고 즉시 200을 준다. 여기서 **저장은 반드시 내구성 있는 저장(DB)이어야 한다.** 인메모리 큐에 넣고 200을 주면 프로세스가 재시작될 때 이벤트가 통째로 사라지고, 발신측은 이미 200을 받았으니 재전송하지 않는다.

```java
// Before: 검증 없음 + 페이로드 신뢰 + 동기 처리 + 중복 무방비
@PostMapping("/webhooks/pg")
public ResponseEntity<Void> onWebhook(@RequestBody PgEvent e) {
    if ("APPROVED".equals(e.status())) {
        // 위조된 요청이 보낸 금액을 그대로 결제 완료로 반영한다.
        // 공격자가 임의 주문번호로 이 요청을 만들면 무료 구매가 된다.
        orderService.markPaid(e.orderId(), e.amount());

        // 같은 event_id가 재전송되면 이 줄이 다시 실행된다 = 이중 적립.
        pointService.accrue(e.orderId());

        // 알림 발송이 3초 걸리면 응답이 3초 늦어지고,
        // 발신측 타임아웃을 넘기면 재전송이 온다 = 스스로 만든 중복.
        notificationService.send(e.orderId());
    }
    return ResponseEntity.ok().build();
}
```

```java
// After: 서명 검증 → 원자적 저장(중복 제거) → 즉시 200 → 처리는 비동기
@PostMapping("/webhooks/pg")
public ResponseEntity<Void> onWebhook(
        @RequestHeader("X-Signature") String sig,
        @RequestHeader("X-Timestamp") String ts,
        @RequestBody String rawBody) {
    // ↑ DTO가 아니라 원문 문자열로 받는다.
    //   파싱 후 재직렬화한 본문으로 서명을 계산하면 필드 순서·공백이
    //   달라져 정상 요청의 서명까지 깨지기 때문이다.

    // ① 발신자 확인. 내부에서 상수 시간 비교(MessageDigest.isEqual)와
    //    타임스탬프 허용 오차(5분) 검사를 함께 수행한다.
    if (!signatureVerifier.verify(rawBody, ts, sig)) {
        return ResponseEntity.status(401).build();
    }

    PgEvent e = parse(rawBody);

    // ② ON CONFLICT DO NOTHING으로 "검사 + 선점"을 한 문장에.
    //    true = 이번이 최초 도착, false = 재전송된 중복.
    boolean firstArrival = eventRepository.insertIfAbsent(e);

    if (firstArrival) {
        // ③ 실제 반영은 워커에게 넘긴다. 여기서는 큐에 넣기만 해도
        //    안전하다 — 이벤트 본문은 이미 ②에서 DB에 남았으므로
        //    큐가 유실돼도 재처리 배치가 다시 집을 수 있다.
        eventQueue.enqueue(e.eventId());
    }

    // ④ 중복이어도 200. 목적은 "반영했다"를 알리는 게 아니라
    //    발신측의 재시도를 멈추는 것이다. 4xx를 주면 영원히 재시도한다.
    return ResponseEntity.ok().build();
}
```

```java
// 비동기 워커: 페이로드가 아니라 조회 API의 값으로 최종 확정한다
void process(String eventId) {
    WebhookEvent e = eventRepository.findById(eventId);

    // ⑤ 신뢰 경계. 웹훅 본문에서는 거래 키만 취했고,
    //    금액·상태는 PG사 원장을 직접 읽어 확정한다.
    //    이 호출이 수백 ms 걸려도 괜찮다 — 여기는 동기 응답 경로가 아니다.
    PgPayment truth = pgClient.getPayment(e.paymentKey());

    // ⑥ 전이 규칙 위반이면 상태를 바꾸지 않고 무시한다.
    //    (CANCELLED 상태에 뒤늦은 APPROVED가 도착한 경우 등)
    payment.transitionTo(truth.status(), truth.amount());

    // ⑦ 여기까지 왔을 때만 처리 완료로 표시한다.
    //    ⑥과 ⑦ 사이에 크래시가 나면 이벤트는 RECEIVED로 남아
    //    재처리된다 — 그래서 ⑥의 반영 로직 자체도 멱등해야 한다.
    eventRepository.markProcessed(eventId);
}
```

### 2-6. 운영 원칙 둘: 웹훅 유실 대비 — 보정 폴링(대사)

지금까지의 방어는 전부 "웹훅이 오기는 온다"를 전제로 한다. 그런데 웹훅은 **아예 안 올 수도 있다.**

- PG사 발신 시스템 장애로 이벤트가 통째로 유실된 경우.
- 우리 서비스가 배포·장애로 길게 다운돼 재시도 한도를 모두 소진한 경우(발신측은 데드레터로 보내고 포기한다).
- 엔드포인트 URL 설정 실수, 방화벽 규칙 변경, 인증서 만료.

웹훅만 믿는 시스템은 이때 주문이 `IN_PROGRESS`에 영원히 머문다. 고객은 돈을 냈는데 주문은 미완료인 상태로 남고, 이 건은 아무도 발견하지 못한다. 아무 이벤트도 오지 않았으니 트리거될 코드가 없기 때문이다.

그래서 **보정 폴링(reconciliation polling)** 을 깐다. 배치로 "결제 진행 중 상태가 N분 이상 지속된 거래"를 골라내 PG사 조회 API로 실제 상태를 확인하고 따라잡는 작업이다.

```sql
-- PostgreSQL: 보정 대상 뽑기 — "진행 중인데 오래 멈춰 있는" 건만
SELECT payment_key
FROM payment
WHERE status IN ('READY', 'IN_PROGRESS')          -- 아직 종결되지 않았고
  AND updated_at < now() - interval '10 minutes'  -- 10분 넘게 그대로다
ORDER BY updated_at
LIMIT 500;
-- 조건 두 개가 모두 필요한 이유:
--   상태 조건이 없으면 이미 끝난 거래까지 매번 조회하게 되고,
--   시간 조건이 없으면 방금 시작한 정상 결제까지 붙잡아
--   PG사 조회 API에 불필요한 부하를 준다.
-- (status, updated_at) 복합 인덱스로 커버한다.
```

역할 분담을 한 문장으로 정리하면 — **웹훅은 지연을 줄이는 최적화이고, 폴링이 정합성의 최후 보루다.** 웹훅이 정상 동작하면 폴링은 아무것도 발견하지 못한 채 조용히 돌고, 웹훅에 구멍이 뚫린 날에만 일한다. 평소에 아무 일도 안 하는 것처럼 보이는 게 정상이다.

## 3. 실무 사례 — 셋 중 하나를 빼먹으면 생기는 일

### 사례 1: IP 화이트리스트만 믿다가 위조 웹훅으로 무료 구매

서명 검증 없이 IP 제한만 걸어둔 가맹점이 있었다. 처음에는 PG사 발신 IP가 몇 개뿐이라 잘 동작했다.

문제는 PG사가 발신 인프라를 클라우드로 옮기면서 시작됐다. IP 대역이 넓어져 웹훅이 간헐적으로 차단되기 시작했고, 운영팀은 결제 누락 장애를 피하려고 대역 전체를 허용해버렸다. 보안 장치가 가용성 사고를 일으켰고, 그걸 피하려다 보안 장치가 무력화된 것이다.

같은 클라우드를 쓰는 공격자가 이 구멍을 찾았다. 결제창에서 주문번호 채번 규칙을 관찰한 뒤, 89,000원짜리 주문에 대해 `status: "APPROVED"`로 채운 위조 웹훅을 쏘았다. 요청은 허용된 대역에서 왔으므로 통과했고, 주문은 실제 결제 승인 없이 `PAID`로 바뀌어 상품이 발송됐다.

이 사고는 두 방어 중 하나만 있었어도 막혔다. HMAC 서명 검증이 있었다면 시크릿을 모르는 공격자의 요청은 401에서 끝났다. 서명이 없더라도 조회 API 재확인이 있었다면, PG사는 "그 거래는 READY(승인 전)입니다"라고 답했을 것이다. 계층 방어가 왜 필요한지를 보여주는 사례다.

### 사례 2: 처리 후 응답 유실 → 재전송 → 적립금 이중 지급

승인 웹훅을 받아 적립금 3,000원을 지급하고 200을 반환하는 순간 로드 밸런서 커넥션이 끊겼다. 우리 쪽 처리는 완료됐지만 발신측은 응답을 못 받았다.

PG사는 규정대로 실패로 판정하고 1분 뒤 같은 `event_id`로 재전송했다. 이벤트 ID 중복 제거가 없던 수신부는 적립 로직을 다시 실행했고, 고객 계정에 6,000원이 쌓였다.

건당으로는 3,000원이라 사소해 보인다. 실제로 이 팀도 초기에는 "드물게 생기는 일"로 넘겼다. 그런데 그날 밤 PG사 발신 서버 장애가 복구되면서 밀렸던 재전송이 한꺼번에 쏟아졌고, 수천 건의 이중 적립이 동시에 발생했다. 회수 공지를 내보내고 CS 문의를 처리한 비용이 실제 지급액을 넘었다.

`webhook_event(event_id PRIMARY KEY)` 한 줄과 `ON CONFLICT DO NOTHING` 한 줄이 막아주는 사고다. 그리고 이 사례는 왜 "드물게 생기는 일"로 넘기면 안 되는지도 보여준다 — 분산 시스템의 중복은 고르게 흩어져 오지 않고 **장애 복구 시점에 몰려서** 온다.

### 사례 3: 순서 역전 — 취소된 주문이 다시 "결제 완료"로

고객이 120,000원을 결제한 직후 마음을 바꿔 곧바로 취소했다. PG사는 승인 이벤트와 취소 이벤트를 몇 초 간격으로 연달아 발신했다.

승인 웹훅의 첫 전송이 우리 서버의 순간적인 지연으로 타임아웃 나서 재시도 큐로 빠졌고, 그 사이 취소 웹훅이 먼저 도착해 정상 처리됐다. 1분 뒤 재시도된 승인 웹훅이 뒤늦게 도착했다.

수신부는 "마지막에 도착한 게 최신 상태"라는 전제로 상태를 덮어쓰는 구조였다. 뒤늦게 도착한 승인 웹훅이 `CANCELLED`였던 주문을 `PAID`로 되돌렸고, 출고 시스템은 `PAID` 주문을 정상 주문으로 보고 상품을 내보냈다. 고객은 환불을 받았는데 상품도 받았다 — 120,000원 손실에 회수 비용이 더해졌다.

상태 머신이 `CANCELLED`를 종결 상태로 선언하고 `CANCELLED → PAID` 전이를 거부했다면, 늦게 온 승인 웹훅은 로그 한 줄만 남기고 200과 함께 버려졌을 것이다. 코드로는 조건문 하나 차이지만, "도착 순서를 믿는가 아닌가"라는 설계 전제의 차이다.

## 4. 꼬리질문 대비 포인트

### "IP 화이트리스트로는 왜 부족한가요?"

세 가지로 답한다. (1) 발신 IP는 PG사 인프라 변경으로 예고 없이 바뀌어 정상 트래픽을 차단하는 가용성 리스크가 있다 — 보안 장치가 장애 유발 장치가 된다. (2) 클라우드 공유 대역에서는 IP가 발신자 신원을 보장하지 못한다. (3) IP는 본문이 변조됐는지를 전혀 증명하지 못한다.

반면 HMAC 서명은 발신자 인증 + 본문 무결성 + (타임스탬프를 서명에 포함하면) 재전송 방지까지 준다. 그래서 서명이 필수 방어이고 IP는 공격 표면을 줄이는 보조 방어라고 정리한다.

### "서명 검증까지 했는데 왜 조회 API로 또 확인하나요?"

서명이 증명하는 범위를 정확히 말하는 것이 답의 핵심이다. 서명은 "시크릿을 가진 쪽이 만든 바이트열이고 전송 중 변조되지 않았다"까지만 증명한다. 우리 쪽 검증 구현의 실수(원문이 아닌 재직렬화 본문으로 검증했다거나), 시크릿 유출, 발신측 버그는 서명으로 걸러지지 않는다.

금액·상태는 돈에 직결되므로 신뢰 경계를 한 겹 더 둔다 — 웹훅에서는 키만 취하고 PG사 원장을 직접 조회한 값으로 확정한다. **"웹훅은 초인종, 진실은 조회 API"** 라는 한 문장으로 패턴을 요약하면 좋다.

### "중복 웹훅에는 어떤 상태 코드를 줘야 하나요?"

200이다. 409나 4xx를 주면 발신측이 전달 실패로 간주해 계속 재전송하거나, 재시도 한도를 소진한 뒤 데드레터로 보내 상대 운영팀에 알람을 울린다. 중복은 우리 입장에서 "이미 반영이 끝난 정상 상황"이므로 성공으로 응답해 재시도를 종료시키는 것이 맞다.

같은 논리가 순서 역전으로 버리기로 판단한 이벤트에도 적용된다. **상태 코드는 "잘 받았다"의 의미이지 "반영했다"의 의미가 아니다**라고 정리하면 두 경우를 한 원칙으로 묶어 설명할 수 있다.

### "비동기 처리 중에 워커가 실패하면 이벤트가 유실되지 않나요?"

유실되지 않는다. 수신 시점에 이벤트를 DB에 `RECEIVED` 상태로 먼저 저장했기 때문이다. 워커는 처리에 성공했을 때만 `PROCESSED`로 바꾸므로, 실패하면 `RECEIVED`로 남아 재처리 배치가 다시 집는다.

여기서 짚어야 할 전제가 하나 있다 — **"빠른 200"의 전제는 인메모리 큐가 아니라 내구성 있는 저장 후 응답이다.** 메모리 큐에 넣고 200을 주면 프로세스 재시작 시 이벤트가 사라지고, 발신측은 이미 200을 받았으니 다시 보내주지도 않는다.

한 가지 더 덧붙이면 완결된다. 처리 완료 표시 직전에 크래시가 나면 같은 이벤트가 재처리되므로, **반영 로직 자체도 멱등해야 한다.** 전송 계층에서 중복을 걸렀다고 도메인 로직의 멱등성이 면제되는 것은 아니다.

### "PG사가 이벤트 ID를 안 주면 중복 제거를 어떻게 하나요?" (시니어 변별 포인트)

페이로드 안의 값들을 조합해 **자연 키(natural key, 데이터 자체에 이미 들어 있는 식별 정보로 만든 키)** 를 만든다. 예를 들어 `거래ID + 이벤트타입 + 상태 + 발생시각`의 해시를 유니크 키로 쓴다.

단서가 하나 있다. 발신측이 재전송할 때 발생시각을 갱신해 보내는지 원본 그대로 보내는지에 따라 키 구성이 달라진다. 갱신해서 보낸다면 발생시각은 키에서 빼야 하고, 대신 다른 값으로 유일성을 만들어야 한다. 이건 연동 문서와 실측으로 확인할 일이지 추측할 일이 아니다.

어떤 조합으로도 유일성이 안 만들어지는 경우가 있다. 그때는 마지막 수단으로 **상태 머신 자체의 멱등성**에 기댄다 — 같은 거래의 같은 상태 전이는 상태 머신이 어차피 두 번 적용하지 않는다(이미 `PAID`인 주문에 `PAID` 전이가 또 와도 아무 변화가 없다). 다만 적립·알림 같은 **부수효과**는 상태 전이와 별개로 실행되므로, 거래ID 기준 실행 이력 테이블로 따로 막아야 한다.

이 답의 변별 포인트는 **전송 계층의 중복 제거와 도메인 계층의 멱등성을 구분해 말하는 것**이다. 앞의 것은 `event_id` 유니크 제약, 뒤의 것은 상태 머신과 실행 이력이며, 앞이 없으면 뒤가 대신할 수는 있어도 완전히 대체하지는 못한다.

### "웹훅과 폴링 중 하나만 쓴다면요?"

정합성만 놓고 보면 폴링만으로도 시스템은 성립한다. 느릴 뿐이다. 반대로 웹훅만 쓰는 시스템은 유실 시 복구 수단이 아예 없으므로 성립하지 않는다. 이 비대칭이 답의 핵심이다.

그래서 실무 답은 **"웹훅으로 빠르게, 폴링으로 빠짐없이"** 다. 웹훅을 1차 트리거로 쓰고, 오래 미결 상태인 거래를 조회 API로 따라잡는 보정 폴링을 안전망으로 깐다.

여기에 폴링 대상을 좁히는 조건(진행 중 상태 + 경과 시간)과 주기 설정 기준(PG사 조회 API의 호출 한도, 미결 건이 방치돼도 되는 최대 시간)까지 말하면 운영 감각을 보여줄 수 있다.

### "웹훅을 여러 인스턴스가 나눠 받는데, 같은 거래의 이벤트가 동시에 처리되면요?" (시니어 변별 포인트)

`event_id` 유니크 제약은 **같은 이벤트**의 중복만 막는다. 서로 **다른 이벤트**(승인과 취소)가 같은 거래에 대해 서로 다른 인스턴스에서 동시에 처리되는 것은 막지 못한다. 두 워커가 동시에 현재 상태를 읽고 각자 전이를 적용하면, 상태 머신 검증을 통과한 채로 마지막 쓰기가 이기는 상황이 다시 만들어진다.

해결은 거래 단위 직렬화다. 방법은 세 가지가 있고 각각 대가가 다르다. (1) 처리 시작 시 해당 결제 행을 `SELECT ... FOR UPDATE`로 잠근다 — 가장 단순하지만 트랜잭션이 길어지면 경합이 생긴다. (2) 낙관적 락(버전 컬럼)을 두고 충돌 시 재시도한다 — 경합이 드물면 효율적이다. (3) 큐를 쓴다면 거래 ID를 파티션 키로 삼아 같은 거래의 이벤트가 항상 같은 컨슈머로 가게 한다 — 순서까지 함께 얻지만 큐 인프라가 필요하다.

"멱등성 키는 이벤트 중복을, 락은 동시성을 막는다. 둘은 다른 문제다"라고 구분해 말하는 것이 변별 포인트다.

## 한 줄 요약

웹훅 수신부는 "위조·중복·역전"을 정상 상황으로 전제하고 — HMAC 서명(+ 조회 API 재확인)으로 위조를, 이벤트 ID 유니크 제약으로 중복을, 상태 머신 전이 검증으로 순서 역전을 각각 방어하며 — 동기 구간은 검증·저장 후 빠른 200까지로 줄이고 실제 반영은 비동기 워커가, 유실은 보정 폴링이 받치는 구조로 만들어야 보안 사고·이중 지급·상태 꼬임을 모두 막을 수 있다.
