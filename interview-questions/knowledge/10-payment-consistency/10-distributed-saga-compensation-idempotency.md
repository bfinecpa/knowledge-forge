# 분산 Saga와 보상 설계 — 롤백이 없는 세계에서 돈을 옮기는 법

> 핵심 관전 포인트: **잔액 차감·주문 생성·이용권 지급이 서로 다른 서비스(각자의 DB)에 있으면 전역 롤백은 존재하지 않는다. 2PC는 잠금을 쥔 채 코디네이터를 기다리는 블로킹 구조라 실무에서 배제되고, 답은 Saga다 — 각 서비스의 로컬 트랜잭션을 순서대로 실행하고, 중간 실패 시 이미 커밋된 단계를 보상 트랜잭션(차감의 보상 = 환급)으로 되돌린다. 돈 도메인에서는 흐름의 현재 위치를 한곳에서 추적할 수 있는 오케스트레이션 방식이 유리하고, 오케스트레이터의 상태 전이와 커맨드 발행은 **트랜잭셔널 아웃박스**(보낼 메시지를 같은 DB의 테이블에 INSERT해 상태 변경과 발행 예약을 한 트랜잭션으로 묶는 기법)로 한 몸이 되게 만든다. 모든 단계는 orderId 기반 멱등성 키를 전파받아 유니크 제약으로 중복 실행을 막고(재전송 안전), 보상도 실패한다는 전제로 재시도 + 수동 개입 큐를 끝단에 둔다. Saga에는 격리성(I)이 없으므로 중간 상태는 PENDING으로 감춘다 — 교과서의 Saga를 "보상 실패·중복 전달·중간 상태 노출"이라는 돈의 현실에 착지시키는 것이 이 질문의 본체다.**

---

## 0. 질문 + 의도

**질문**: "분산 환경에서 '잔액 차감 + 주문 생성 + 이용권 지급'이 서로 다른 서비스에 있을 때 트랜잭션을 어떻게 설계하나요? (Saga, 보상, 멱등성)"

**출제 의도**: Saga의 교과서 지식을 돈 도메인의 현실 — 보상 실패 시 수동 개입 큐, 멱등성 키 전파 — 에 착지시킬 수 있는지 본다. 아키텍처 패턴과 도메인 요구를 동시에 쥐고 설계하는 시니어급 종합 문제다.

## 1. 왜 문제인가 — 분산에는 롤백 버튼이 없다

### 1-1. 전제 지식 — 단일 DB의 `@Transactional`이 왜 여기선 안 통하는가

`@Transactional`은 여러 SQL을 "전부 성공 아니면 전부 없던 일"로 묶어준다. 이게 가능한 이유는 DB 엔진이 변경 전 값을 별도로 보관하고 있다가 `ROLLBACK` 신호를 받으면 되돌려 주기 때문이다. 즉 **롤백은 하나의 DB가 자기 데이터에 대해 제공하는 기능**이다.

포인트 서비스, 주문 서비스, 콘텐츠 서비스가 **각자 자기 PostgreSQL을 쓰는** 구조에서는 이 전제가 무너진다. 포인트 서비스가 `COMMIT`을 끝낸 순간, 그 차감은 **그쪽 DB에서 이미 확정된 과거**다. 나중에 콘텐츠 서비스에서 지급이 실패했다고 해서, 우리가 남의 DB를 향해 "아까 그거 롤백해"라고 보낼 수 있는 명령은 존재하지 않는다. 커밋된 트랜잭션을 취소하는 표준 SQL은 없다.

그래서 분산 환경의 실패 처리는 **"되돌리기"가 아니라 "반대 방향의 새 작업으로 메우기"**가 된다.

```java
// Before: REST 3연쇄 — 실패 지점마다 다른 세계가 남는다
public void order(OrderRequest req) {
    pointClient.deduct(req.userId(), 9900);            // ① 차감
    orderClient.create(req);                           // ② 주문 생성
    ticketClient.grant(req.userId(), req.productId()); // ③ 지급
    // ②에서 실패하면? ①은 남의 DB에 이미 커밋됐다.
    // catch에서 pointClient.refund()를 부르면? 그 refund가
    // 타임아웃 나면? 부르기 직전에 이 서버가 죽으면?
    // — "지금 어디까지 진행됐는지"가 어디에도 기록돼 있지 않다.
}
```

이 코드의 진짜 결함은 예외 처리가 없다는 것이 아니다. **진행 상태가 메모리(스레드의 스택)에만 있다**는 것이다. 스레드가 죽으면 "①까지는 했고 ②에서 실패했다"는 사실이 이 세상에서 사라진다. 누구도 이어받을 수 없다.

### 1-2. 2PC는 왜 실무에서 배제되는가

"분산 트랜잭션"이라는 말을 들으면 먼저 떠오르는 것이 **2단계 커밋(2PC, two-phase commit)**이다. 먼저 무엇인지 알고 넘어가자.

2PC에는 **코디네이터(coordinator, 조정자)**라는 중앙 심판이 있다. 절차는 두 단계다.

```
[1단계 prepare]  코디네이터 --"준비됐나?"--> 참여자 A, B, C
                 각 참여자는 자기 몫을 실행하되 커밋하지 않고,
                 잠금을 쥔 채 "예, 언제든 커밋 가능합니다"로 답한다.

[2단계 commit]   전원 OK  -> 코디네이터가 "커밋하라" 전파
                 하나라도 NO -> "중단하라" 전파
```

이론상 완벽하다. 전원이 커밋하거나 전원이 중단하므로 분산 원자성이 성립한다. 그런데 실무의 결제 시스템에서는 배제된다. 이유가 셋이다.

**(1) prepare 후 참여자가 블로킹된다.** "준비됐다"고 답한 참여자는 코디네이터의 최종 결정이 올 때까지 **행 잠금을 쥔 채 기다린다.** 잠금을 풀 수 없다 — 커밋하라고 할지 중단하라고 할지 모르니까. 이때 코디네이터가 죽으면 모든 참여자의 잠금이 그대로 묶인 채 남는다. **한 지점의 장애가 전 시스템의 잠금 정체로 번지는 구조**다.

**(2) 처리량이 가장 느린 참여자에 묶인다.** 전체 트랜잭션 시간 = 가장 느린 참여자 + 코디네이터 왕복 2회다. 참여자 하나가 200ms 걸리면 그동안 다른 참여자들의 행도 전부 잠겨 있다. 결제 트래픽을 이 구조로 감당하기 어렵다.

**(3) 참여자 전원이 XA를 지원해야 한다.** XA는 분산 트랜잭션을 위한 표준 인터페이스로, prepare와 commit을 나눠 받을 수 있는 자원만 참여할 수 있다. 그런데 Kafka, 외부 PG사 API, 다른 팀의 HTTP API는 XA를 지원하지 않는다. 현대적 아키텍처의 구성 요소 대부분이 애초에 참여 자격이 없다.

그래서 답은 **"원자성을 시간축으로 풀어낸"** 방식 — Saga다.

### 1-3. Saga = 로컬 트랜잭션의 연쇄 + 보상의 연쇄

**Saga**는 전체 작업을 각 서비스의 **로컬 트랜잭션 T1 → T2 → T3**으로 쪼개 순서대로 실행하고, 중간에 Ti가 실패하면 이미 커밋된 앞 단계들을 **보상 트랜잭션(compensating transaction) C(i-1) → ... → C1**으로 되돌리는 패턴이다.

핵심은 **보상은 롤백이 아니라 "반대 방향의 새 트랜잭션"**이라는 점이다. 차감(-9,900P)의 보상은 환급(+9,900P)이라는 **새로운 원장 기록**이다. 차감 기록이 지워지는 게 아니라, 차감 기록 아래에 환급 기록이 한 줄 더 쌓인다. 회계에서 잘못된 분개를 지우개로 지우지 않고 반대 분개를 새로 적는 것과 같다.

성공 경로와 보상 경로를 그림으로 보면 이렇다.

```
[정상 경로]
  T1: 포인트 차감      T2: 주문 생성        T3: 이용권 지급
  (-9,900P 커밋)  ->  (PENDING 커밋)  ->  (INACTIVE 커밋)  ->  COMPLETED
      성공                 성공                  성공

[T3에서 실패했을 때의 보상 경로]
  T1 ---> T2 ---> T3
  성공    성공    실패!
                  |
                  v
           보상을 역순으로 태운다
                  |
   C2: 주문 취소  <--+
   (CANCELLED로 전이)
        |
        v
   C1: 포인트 환급
   (+9,900P 새 원장 기록)
        |
        v
   COMPENSATED (Saga 종료)
```

보상이 **역순**인 이유는 의존 관계 때문이다. 주문이 존재해야 그 주문에 대한 지급이 성립하므로, 되돌릴 때는 안쪽(나중 단계)부터 푼다. 그리고 실패한 T3 자신은 보상하지 않는다 — 커밋되지 않았으니 되돌릴 것이 없다.

Saga 상태를 상태 머신으로 쓰면 이렇게 된다.

```
DEDUCT_REQUESTED --성공--> ORDER_CREATED --성공--> GRANT_REQUESTED
                                                        |
                                                     성공 |
                                                        v
                                                    COMPLETED

GRANT_REQUESTED --실패--> COMPENSATING --환급 성공--> COMPENSATED
                              |
                              | 환급 재시도 한도 초과
                              v
                     COMPENSATION_FAILED  ->  수동 개입 큐 + 알림
```

### 1-4. 비유 — 여행사 패키지 예약

**여행사 패키지 예약**을 떠올리면 구조가 한 번에 들어온다.

항공권, 호텔, 렌터카는 서로 다른 회사(서비스)라 한 번에 묶어 예약할 수 없다. 그래서 여행사 직원(오케스트레이터)이 **예약 대장(Saga 상태 테이블)**을 펴놓고 항공권부터 순서대로 예약해 나간다.

호텔이 만실이면 이미 발권된 항공권을 **취소(보상)**한다. 이 취소는 "예약이 없던 일이 되는 것"이 아니다 — 취소 수수료와 취소 기록이 남는 **새로운 거래**다.

취소 전화가 불통이면(보상 실패) 직원은 대장에 "항공 취소 미처리"라고 적어두고 될 때까지 다시 건다. 대장에 적어두는 것이 중요하다 — 직원이 퇴근해도 다음 직원이 대장을 보고 이어서 처리할 수 있다.

## 2. 설계 — 오케스트레이션, 보상, 멱등성 전파

### 2-1. 코레오그래피 vs 오케스트레이션 — 왜 선택지가 이 둘뿐인가

Saga를 구현하려면 반드시 답해야 하는 질문이 하나 있다. **"T1이 끝났다는 것을 누가 알고, 누가 T2를 시작시키는가?"**

이 질문의 답은 논리적으로 두 개뿐이다. **다음 단계를 맡은 서비스가 스스로 알아채고 시작하거나**, **중앙의 누군가가 알려주고 시작시키거나.** 이 갈림이 그대로 두 방식이 된다.

**코레오그래피(choreography, 안무)**는 전자다. 이름 그대로 안무 — 무용수들이 지휘자 없이 음악과 서로의 동작을 보고 각자 자기 차례에 움직이는 방식이다. 각 서비스는 앞 단계가 발행한 이벤트를 구독하고 있다가, 그 이벤트가 오면 자기 일을 하고 다시 이벤트를 발행한다.

```
포인트 서비스 --PointDeducted--> 주문 서비스 --OrderCreated--> 콘텐츠 서비스
                (구독)                          (구독)
```

**오케스트레이션(orchestration, 지휘)**은 후자다. 오케스트라의 지휘자처럼 **오케스트레이터**가 Saga 상태를 자기 DB에 들고 있으면서 각 서비스에 커맨드(명령)를 보내고, 응답을 받아 상태를 전이시키고, 다음 커맨드를 보낸다.

```
                 [오케스트레이터]  (saga_instance 테이블 보유)
                   |    ^    |    ^    |
          "차감해" |    | 완료 |    | 완료
                   v    |    v    |    v
            포인트 서비스  주문 서비스  콘텐츠 서비스
```

둘의 차이를 표로 보면 이렇다.

| | 코레오그래피 | 오케스트레이션 |
|---|---|---|
| 흐름 지식 | 각 서비스의 구독 관계에 분산 | 오케스트레이터 한곳에 집중 |
| 결합도 | 낮음 (서로를 직접 모름) | 높음 (오케스트레이터가 전부 앎) |
| "지금 어디서 멈췄나?" | 여러 서비스 로그를 모아야 앎 | 테이블 한 번 조회로 앎 |
| 단계 추가 | 구독만 추가하면 됨 | 오케스트레이터 수정 필요 |
| 보상 경로 | 이벤트로 얽혀 순환 구독이 생기기 쉬움 | 상태 머신에 명시적으로 정의 |

**돈 도메인에서는 오케스트레이션이 유리하다.** 이유는 결합도가 아니라 운영 요구에서 나온다.

- CS 문의가 들어오면 "주문 8471번, 상태 COMPENSATING, 환급 재시도 2회째"를 **한 테이블 조회로** 답해야 한다.
- 멈춘 Saga를 찾아 개입하는 운영(타임아웃 스캔, 수동 재개)도 상태가 한곳에 있어야 성립한다.
- 감사(audit) 요구 — "이 돈이 언제 어떤 경로로 움직였는가"를 증명해야 한다.

즉 **추적성·개입 가능성이 결합도 우려를 이긴다.** 이 판단 근거를 말할 수 있어야 한다.

### 2-2. Saga 상태를 DB에 남긴다

Saga의 진행 상황은 반드시 영속화한다. 이유는 1-1에서 본 그대로다 — 메모리에만 있으면 오케스트레이터 인스턴스가 죽는 순간 흐름이 사라진다. 상태가 DB에 있어야 **다른 인스턴스나 배치가 테이블을 보고 이어받을 수** 있다.

```sql
CREATE TABLE saga_instance (
    saga_id     bigserial    PRIMARY KEY,
    order_id    bigint       NOT NULL UNIQUE,  -- 주문당 Saga 1개
    step        varchar(30)  NOT NULL,
    -- DEDUCT_REQUESTED -> ORDER_CREATED -> GRANT_REQUESTED
    -- -> COMPLETED | COMPENSATING -> COMPENSATED
    -- | COMPENSATION_FAILED (수동 개입 대기)
    retry_count int          NOT NULL DEFAULT 0,
    updated_at  timestamptz  NOT NULL DEFAULT now()
);
-- updated_at 인덱스: "오래 멈춰 있는 Saga" 스캔(2-7)을 위한 것
CREATE INDEX idx_saga_stuck ON saga_instance (step, updated_at);
```

`order_id`에 `UNIQUE`를 건 이유는 **같은 주문에 Saga가 두 개 생기는 것을 DB가 막게** 하기 위해서다. 애플리케이션의 "이미 있나?" 검사는 동시 요청 두 건이 나란히 통과할 수 있지만, 유니크 제약은 DB가 쓰기 시점에 원자적으로 판정한다.

`retry_count`는 단순한 카운터처럼 보이지만 중요한 역할을 한다. **"몇 번까지 자동으로 해보고 사람을 부를 것인가"**의 근거가 된다(3절 사례 1).

### 2-3. 트랜잭셔널 아웃박스 — 상태 전이와 커맨드 발행을 한 몸으로

오케스트레이터가 하는 일은 매번 두 가지다 — ① 자기 DB의 Saga 상태를 전이시키고, ② 다음 서비스에 커맨드를 발행한다. 이 둘은 **반드시 함께 일어나거나 함께 일어나지 않아야** 한다.

왜 그런지 어긋나는 경우를 보면 안다.

- **전이만 커밋되고 발행 전에 죽으면**: 상태는 `GRANT_REQUESTED`인데 지급 커맨드는 아무도 못 받았다. 흐름이 조용히 멈춘다.
- **발행은 됐는데 전이가 롤백되면**: 콘텐츠 서비스는 지급을 했는데 오케스트레이터는 아직 이전 단계라고 알고 있다. 나중에 커맨드를 또 보내거나, 잘못된 보상을 태운다.

그런데 DB 쓰기와 Kafka 발행은 서로 다른 시스템이라 한 트랜잭션으로 묶을 수 없다. 이것을 **이중 쓰기(dual write) 문제**라고 부른다.

#### 아웃박스가 무엇인가

**아웃박스(outbox)는 말 그대로 "보낼 편지함"이다.** 메시지를 Kafka로 바로 쏘는 대신, **같은 DB의 outbox 테이블에 INSERT**해 둔다. 그러면 Saga 상태 변경과 메시지 발행 기록이 **같은 트랜잭션 안의 두 쓰기**가 되므로, 둘 다 커밋되거나 둘 다 롤백된다. 이중 쓰기가 단일 쓰기로 바뀐 것이다.

실제 발행은 **릴레이(relay)**라는 별도 프로세스가 맡는다. outbox 테이블에서 미발행 행을 읽어 Kafka로 발행하고 발행 완료를 표시한다. 읽는 방식은 두 가지다.

- **폴링**: 짧은 주기로 `WHERE published_at IS NULL`을 조회한다. 단순해서 대부분 여기서 시작한다.
- **CDC(Change Data Capture)**: DB 복제 로그(PostgreSQL의 WAL)를 구독해 INSERT를 실시간 감지한다. Debezium이 대표적이다.

이 구조 전체를 **트랜잭셔널 아웃박스(transactional outbox)** 패턴이라고 부른다.

```
[오케스트레이터 인스턴스]
  |
  |  BEGIN
  |    UPDATE saga_instance SET step='GRANT_REQUESTED' ...
  |    INSERT INTO outbox (event_type='ticket.grant', ...)
  |  COMMIT   <- 상태 전이와 발행 예약이 함께 남거나 함께 없다
  v
[outbox 테이블] <--- 릴레이가 폴링 또는 CDC로 읽는다
                        |
                        v
                    [Kafka] ---> [콘텐츠 서비스]
```

참여 서비스가 오케스트레이터로 돌려보내는 **응답 이벤트도 같은 방식**으로 나온다. 콘텐츠 서비스도 "이용권 INSERT + 응답 이벤트 outbox INSERT"를 한 트랜잭션으로 커밋한다. 그래야 "지급은 됐는데 응답이 영영 안 오는" 상태가 생기지 않는다.

### 2-4. 상태 머신 가드 — 오케스트레이터 자신의 멱등성

릴레이와 Kafka는 모두 **at-least-once(최소 1회)** 전달이다. "적어도 한 번은 도착한다"는 보장이지 "정확히 한 번"이 아니다. 릴레이가 발행 성공 직후 발행 완료 표시 전에 죽으면 같은 메시지를 한 번 더 보낸다.

따라서 오케스트레이터도 **같은 이벤트를 두 번 받을 각오**를 해야 한다. 그 방어가 상태 머신 가드다.

```java
// After: 응답 이벤트 핸들러 — 전이 + 발행이 원자적이고 멱등하다
@Transactional
public void onDeductSucceeded(DeductSucceeded event) {
    // FOR UPDATE로 Saga 행을 잠근다. 같은 주문의 이벤트 두 개가
    // 동시에 도착해도 한 번에 하나씩만 상태를 전이시키기 위해서다.
    Saga saga = sagaRepository.findByOrderIdForUpdate(event.orderId());

    // 상태 머신 가드: "지금 상태에서 유효한 이벤트인가"만 받아들인다.
    // 이미 ORDER_CREATED로 넘어갔다면 이 이벤트는 중복 배달이므로
    // 조용히 버린다 — 이것이 오케스트레이터 자신의 멱등성이다.
    if (saga.step() != Step.DEDUCT_REQUESTED) return;

    saga.moveTo(Step.ORDER_CREATED);   // 주문은 이미 PENDING으로 생성됨
    saga.moveTo(Step.GRANT_REQUESTED);

    // 카프카로 직접 보내지 않는다. 위의 상태 전이와 같은 트랜잭션에
    // 남겨야 "전이만 되고 발행은 안 된" 상태가 생기지 않는다.
    outbox.save(Command.of("ticket.grant", event.orderId()));
}

@Transactional
public void onGrantFailed(GrantFailed event) {
    Saga saga = sagaRepository.findByOrderIdForUpdate(event.orderId());
    if (saga.step() != Step.GRANT_REQUESTED) return;

    saga.moveTo(Step.COMPENSATING);
    // 보상 커맨드도 똑같이 아웃박스로 나간다. 보상이야말로
    // 유실되면 안 되는 메시지이기 때문이다.
    outbox.save(Command.of("point.refund", event.orderId()));
}
```

`if (saga.step() != ...) return;` 이 한 줄이 하는 일을 정확히 짚자. **현재 상태에서 유효한 이벤트만 받아들이고 나머지는 조용히 버린다.** 같은 이벤트가 Kafka에서 두 번 배달돼도 두 번째는 상태가 이미 바뀌어 있으므로 가드에 걸려 무시된다. 예외를 던지지 않고 `return`하는 이유는, 중복 배달은 오류가 아니라 **정상적으로 예상되는 상황**이기 때문이다. 예외를 던지면 컨슈머가 재시도를 반복하며 무한 루프에 빠진다.

### 2-5. 멱등성 키를 전 단계에 전파한다

오케스트레이터만 멱등해서는 부족하다. **모든 참여 서비스의 쓰기가 멱등**해야 한다. 커맨드도 at-least-once로 전달되기 때문이다.

여기서 **멱등성(idempotency)**은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"이다. 그리고 "같은 작업"인지 판단하려면 기준이 되는 식별자가 필요한데, 그것이 **멱등성 키**다.

키는 **오케스트레이터가 만들어 모든 커맨드에 실어 보낸다.** 자연스러운 선택은 `orderId`다. 한 주문에 성격이 다른 쓰기가 둘 이상이면(차감과 환급) `orderId + 단계명`으로 구분한다.

```sql
-- 포인트 서비스: 주문당 차감 1건·환급 1건 (원장 유니크)
ALTER TABLE point_ledger
    ADD CONSTRAINT uq_ledger UNIQUE (order_id, entry_type);

-- 콘텐츠 서비스: 주문당 이용권 1건
CREATE UNIQUE INDEX uq_ticket_order ON ticket (order_id);
```

각 서비스는 커맨드를 받으면 **INSERT-first**로 처리한다 — "이미 처리했나?"를 조회로 확인하지 않고, 일단 INSERT를 시도한다. 조회 후 INSERT는 그 사이 틈에 다른 요청이 끼어들 수 있지만, INSERT는 유니크 제약과 결합해 확인과 선점이 DB 안에서 한 번에 원자적으로 일어난다.

유니크 위반이 나면 그것은 "이미 처리된 커맨드"라는 뜻이다. 이때 **반드시 성공으로 응답해야 한다.**

```java
// 콘텐츠 서비스: 지급 커맨드 핸들러
@Transactional
public GrantResult handle(GrantCommand cmd) {
    int inserted = ticketRepository.insertIfAbsent(
        cmd.orderId(), cmd.userId(), cmd.productId());
    // insertIfAbsent는 ON CONFLICT (order_id) DO NOTHING.
    // inserted == 0 이면 이미 지급된 주문이라는 뜻이다.

    // 여기서 에러를 응답하면 오케스트레이터가 "지급 실패"로 오판해
    // 불필요한 보상(환급)을 태운다 — 이미 지급된 이용권을 그대로 둔 채
    // 돈만 돌려주는 최악의 결과가 된다. 그래서 성공으로 응답한다.
    return GrantResult.success(cmd.orderId());
}
```

이 "이미 처리됨 = 성공 응답" 규칙이 왜 중요한지 한 번 더 짚자. 멱등성이 참여자 전원에 깔려 있어야 오케스트레이터가 **"확신이 없으면 그냥 재전송한다"**는 단순한 복구 전략을 쓸 수 있다. 그렇지 않으면 재전송할 때마다 "이미 했나 안 했나"를 확인하는 조회 API와 분기 로직이 필요해지고, 상태 공간이 폭발한다.

**멱등성은 Saga의 전제 조건이지 부가 옵션이 아니다.**

### 2-6. 격리성 부재 — 중간 상태는 PENDING으로 감춘다

Saga는 ACID 중 **격리성(I, Isolation)이 없다.** 이것이 단일 트랜잭션과의 가장 큰 차이이고, 자주 놓치는 지점이다.

단일 트랜잭션에서는 커밋 전까지 다른 트랜잭션이 중간 상태를 볼 수 없다. Saga에서는 T1(차감)이 **커밋된 순간부터** 그 결과가 세상에 공개된다. T2, T3이 아직 안 끝났는데도 말이다.

구체적으로 어떤 일이 생기는가.

- 사용자가 잔액을 조회하면 이미 9,900P 줄어든 잔액이 보인다. 그런데 주문은 아직 확정 전이다.
- 최악의 경우 이후 보상이 실행되어, 사용자 눈에는 "결제도 안 됐는데 잔액이 줄었다가 다시 늘어나는" 움직임이 보인다.
- 그 사이 사용자가 같은 상품을 또 주문하면 이중 차감·이중 지급 경합이 생긴다.

대응은 **의미적 잠금(semantic lock)**이다. DB의 락처럼 물리적으로 접근을 막는 것이 아니라, **데이터에 "아직 확정 아님" 표식을 붙여 확정처럼 보이지 않게** 하는 기법이라 "의미적"이라고 부른다.

- **주문은 `PENDING`으로 생성**하고 Saga 완료 시에만 `COMPLETED`로 전이시킨다. 사용자 화면에는 "결제 처리 중"으로 노출한다.
- **이용권도 지급 시 `INACTIVE`로 넣고** Saga 완료 커맨드에서 활성화한다.
- **PENDING 주문이 존재하는 동안 같은 상품 재주문을 차단**한다.

이용권을 `INACTIVE`로 넣는 부분은 특히 중요하다. 만약 지급 즉시 활성화한다면, 나중에 보상해야 할 때 **이미 사용자가 열람해버린 이용권을 회수**해야 한다 — 소비된 권리는 회수가 불가능하다. `INACTIVE`로 두면 보상은 그냥 그 행을 삭제하거나 `REVOKED`로 바꾸는 일이 된다. **최악의 보상 시나리오를 설계로 미리 제거한 것**이다.

### 2-7. 타임아웃 — 응답이 안 오는 단계의 처리

`GRANT_REQUESTED`에서 3분째 응답이 없다면 어떻게 하는가.

먼저 스케줄러가 **오래 멈춘 Saga를 스캔**한다.

```sql
-- 3분 이상 같은 단계에 머물러 있는 Saga 찾기
SELECT saga_id, order_id, step, retry_count
  FROM saga_instance
 WHERE step IN ('DEDUCT_REQUESTED', 'GRANT_REQUESTED', 'COMPENSATING')
   AND updated_at < now() - interval '3 minutes'
 ORDER BY updated_at
 LIMIT 200;
```

찾은 Saga에는 **커맨드를 재전송**한다. 참여자가 2-5의 규칙대로 멱등하므로 안전하다. 이미 처리됐다면 "처리됨" 성공 응답이 다시 오고, 미처리였다면 이번에 처리된다.

재전송 한도를 넘으면 실패로 간주하고 보상 경로로 전이시킨다. 단, 여기에 함정이 하나 있다.

**"실패 응답"과 "무응답"은 다르다.** 명시적 실패 응답은 "확실히 안 됐다"는 사실이지만, 무응답은 **결과 불명**이다. 무응답 후 실패로 간주해 보상을 태웠는데, 뒤늦게 성공 응답이 도착할 수 있다.

```
t0   GRANT_REQUESTED, 지급 커맨드 발행
t1   콘텐츠 서비스가 실제로는 지급을 완료 (응답 이벤트가 늦게 감)
t2   타임아웃 -> COMPENSATING 전이, 환급 커맨드 발행
t3   환급 완료 -> COMPENSATED
t4   ★ 뒤늦은 GrantSucceeded 이벤트 도착
     -> 이용권은 살아있는데 돈은 돌려준 상태
```

그래서 **지급 성공 이벤트가 `COMPENSATING`이나 `COMPENSATED` 상태에 도착하는 경우**까지 상태 머신에 정의해 둔다. 이때는 추가 보상(이용권 비활성화 → 회수)을 태워야 한다. 2-6에서 이용권을 `INACTIVE`로 넣어둔 설계가 여기서 다시 값을 한다 — 회수가 가능한 상태이기 때문이다.

이렇게 "늦게 도착한 이벤트"까지 상태 머신에 자리를 만들어 두는 것이, 교과서 Saga와 실무 Saga의 차이다.

## 3. 실무 사례 — 교과서가 말하지 않는 세 가지

### 사례 1: 보상도 실패한다 — 환급 커맨드가 죽은 컨슈머를 만났을 때

이용권 지급이 콘텐츠 서비스 배포와 겹쳐 5xx로 확정 실패했다. 오케스트레이터는 `COMPENSATING`으로 전이하고 환급(+9,900P) 커맨드를 발행했다. **그런데 포인트 서비스 컨슈머도 장애 중이다.**

이 순간 사용자 돈 9,900P는 어느 쪽 권리로도 연결되지 않은 채 붕 떠 있다. 이용권도 없고 포인트도 없다.

**대응은 3단이다.**

**(1) 환급 커맨드는 끝까지 살아남는다.** 아웃박스에 커밋됐으므로 사라지지 않고, Kafka가 재전달을 계속하므로 컨슈머가 복구되면 처리된다. 멱등하므로 그 사이 중복 배달이 있어도 안전하다.

**(2) 백오프를 두고 재시도한다.** **지수 백오프(exponential backoff)**는 재시도 간격을 1초, 2초, 4초, 8초처럼 늘려가는 방식이다. 이미 힘들어하는 상대 시스템에 재시도 폭풍으로 부하를 더 얹지 않기 위한 것이다.

**(3) 한도를 넘으면 사람을 부른다.** 재시도 한도(예: 5회)를 넘기면 Saga를 `COMPENSATION_FAILED`로 전이시키고 **수동 개입 큐** — 운영자가 보는 보정 대기 테이블 — 에 `orderId`, 금액, 실패 사유, 마지막 시도 시각을 적재하고 알림을 쏜다.

```sql
CREATE TABLE manual_intervention_queue (
    id           bigserial   PRIMARY KEY,
    order_id     bigint      NOT NULL,
    saga_step    varchar(30) NOT NULL,
    amount       int         NOT NULL,
    reason       text        NOT NULL,
    last_tried_at timestamptz NOT NULL,
    resolved_at  timestamptz              -- NULL이면 미처리
);
```

**돈 도메인 Saga의 끝단은 언제나 "재시도 → 그래도 안 되면 사람"이다.** 자동 복구가 실패하는 것 자체는 막을 수 없지만, 실패했다는 사실이 아무 데도 기록되지 않는 것은 설계 결함이다.

### 사례 2: 지급 커맨드 2회 배달 — 멱등성이 빠진 참여자

컨슈머가 지급을 끝내고 **오프셋 커밋 전에** 재시작됐다.

Kafka 컨슈머는 "어디까지 읽었는지"를 오프셋(offset)이라는 숫자로 기록한다. 메시지를 처리한 뒤 오프셋을 커밋해야 다음부터 그 메시지를 안 받는데, 처리와 오프셋 커밋 사이에 죽으면 재시작 후 **같은 메시지를 다시 받는다.** 이것이 at-least-once 전달의 실체다.

`UNIQUE (order_id)`가 없던 초기 구현은 이용권을 2장 발급했다. 장당 9,900P짜리 권리가 공짜로 한 장 더 나간 것이다. 그리고 **대사 배치가 "차감 1건 : 이용권 2장" 불일치를 찾아내기 전까지 아무도 몰랐다.**

**대응은 3종 세트다.**

1. 유니크 제약 (`UNIQUE (order_id)`)
2. `ON CONFLICT DO NOTHING`으로 예외 없이 흡수
3. "이미 처리됨 = 성공 응답" (2-5 참고)

여기서 한 줄로 이어 말할 수 있어야 하는 것은 이것이다. **at-least-once 전달을 쓰는 순간 참여자 멱등성은 전원 필수이고, 그것이 빠졌을 때 발견하는 수단이 대사다.** 예방과 탐지가 짝이라는 구조를 보여주는 사례다.

### 사례 3: 오케스트레이터 크래시 — "차감했나 안 했나" 불명

차감 커맨드를 발행한 직후 오케스트레이터 인스턴스가 죽었다. 재기동 후 다른 인스턴스가 `DEDUCT_REQUESTED`에 멈춘 Saga를 타임아웃 스캔으로 발견했다.

그런데 **차감이 실행됐는지 아닌지 알 수 없다.** 가능한 상황이 셋이다.

- 커맨드가 아직 컨슈머에 도달하지 않았다 → 미처리
- 처리는 됐는데 응답 이벤트가 유실됐다 → 처리됨
- 지금 처리 중이다 → 곧 처리됨

**대응: 알 필요가 없게 만든다.** 차감이 멱등하므로 **그냥 커맨드를 재전송한다.**

- 이미 처리됐다면 포인트 서비스가 원장 유니크 위반을 만나 "처리됨" 성공 이벤트를 다시 내준다.
- 미처리였다면 이번에 처리되고 성공 이벤트가 온다.

어느 쪽이든 Saga는 다음 단계로 전진한다.

이 접근을 대안과 비교해 보면 값이 분명해진다. "결과 불명이면 조회 API로 확인 후 분기"는 조회 API를 각 참여자마다 만들어야 하고, 조회 자체가 실패하는 경우, 조회와 재전송 사이에 상태가 바뀌는 경우까지 다뤄야 한다. **"멱등 재전송으로 수렴"은 상태 공간이 훨씬 작다.**

멱등성이 왜 Saga의 전제 조건인지를 이 사례가 증명한다.

## 4. 꼬리질문 대비 포인트

### "2PC를 쓰면 안 되는 이유를 다시 정리해주면요? Saga가 항상 답인가요?"

2PC 배제 근거는 셋이다.

1. prepare 후 참여자가 **행 잠금을 쥔 채 블로킹**된다 — 코디네이터 장애가 전 참여자의 잠금 정체로 전파된다.
2. 전체 처리 시간이 **가장 느린 참여자 + 코디네이터 왕복**에 종속된다.
3. Kafka·외부 PG·타 팀 HTTP API는 **XA를 지원하지 않는다** — 참여 자격 자체가 없다.

다만 **"항상 Saga"도 아니다.** 이 부분을 말할 수 있어야 설계 감각이 드러난다.

**분산 트랜잭션이 필요 없게 서비스 경계를 다시 긋는 것이 첫 번째 답이다.** 차감과 주문이 한 서비스·한 DB로 묶일 수 있다면 로컬 트랜잭션 하나가 Saga보다 백 배 단순하다. Saga에는 상태 테이블, 아웃박스, 릴레이, 타임아웃 스캐너, 보상 경로, 수동 개입 큐가 전부 딸려 온다.

**Saga는 "경계를 합칠 수 없다는 결론이 난 뒤"의 도구**라는 순서를 밝히면 좋다. 실제로 "마이크로서비스로 쪼갰더니 Saga가 필요해졌다"는 상황의 상당수는 경계를 잘못 그은 결과다 — 한 트랜잭션으로 묶여야 하는 데이터는 대체로 같은 서비스에 있어야 한다.

### "보상 트랜잭션이 실패하면 어떻게 하나요?" (시니어 변별 포인트)

3단 구조로 답한다.

**(1) 보상은 실패 확률이 낮게 설계한다.** 이것이 첫 번째이자 가장 중요한 답이다.

- 차감의 보상을 **환급(더하기)**으로 두면 "잔액이 모자라서 못 한다" 같은 논리적 실패가 없다. 남는 것은 일시적 장애뿐이다.
- 회수가 필요한 권리(이용권)는 Saga 완료 전 `INACTIVE`로 둬서 **"이미 소비돼서 회수 불가"라는 보상 불능 상황을 구조적으로 없앤다.**
- 즉 보상 실패에 대한 최선의 대비는 대응 절차가 아니라, **보상이 실패할 수 없는 형태로 순서와 상태를 설계하는 것**이다.

**(2) 남는 실패는 일시 장애이므로 아웃박스 + 백오프 재시도로 흡수한다.** 아웃박스에 커밋된 보상 커맨드는 유실되지 않고, 컨슈머가 복구되면 반드시 처리된다.

**(3) 한도 초과 시 `COMPENSATION_FAILED` + 수동 개입 큐 + 알림.** 돈이 붕 뜬 상태를 시스템이 모르는 채 두지 않는다.

**"보상은 실패하지 않는다고 가정한다"고 답하는 순간 탈락 신호다.** 교과서의 Saga는 보상 성공을 가정하고 논의를 전개하지만, 돈의 현실은 정확히 그 가정의 바깥에서 터진다.

### "코레오그래피가 결합도는 더 낮지 않나요? 왜 오케스트레이션인가요?"

맞다는 것부터 인정하고 시작한다. 코레오그래피는 서비스 간 직접 참조가 없어 단계 추가가 쉽고, 오케스트레이터라는 단일 지점에 지식이 몰리지 않는다.

그런데 **돈 도메인의 지배적 요구는 결합도가 아니라 추적성·개입 가능성**이다.

- "이 주문 어디서 멈췄나"를 즉답해야 하는 CS
- 멈춘 Saga의 타임아웃 스캔
- 보상 실패의 수동 재개

이 셋은 전부 **상태가 한 테이블에 있어야** 성립한다.

결정적인 반론은 이것이다. **코레오그래피에서 같은 것을 하려면 결국 모든 이벤트를 모아 흐름을 재구성하는 추적 저장소를 따로 지어야 하고, 그게 사실상의 오케스트레이터다.** 결합도를 줄인 대신 관측 인프라를 하나 더 짓게 되는 셈이다.

절충안까지 말하면 좋다. **"주변부 알림성 흐름은 코레오그래피, 돈이 걸린 핵심 경로는 오케스트레이션"**이라는 분리 기준이다. 결제 완료 후 푸시 알림·포인트 적립 이벤트 같은 것은 실패해도 보상이 필요 없으니 코레오그래피로 충분하다.

### "Saga 진행 중에 사용자가 잔액이나 주문을 조회하면요?"

**격리성 부재** 문제로 연결해 답한다(2-6).

T1(차감) 커밋 직후부터 잔액은 이미 줄어 있고 주문은 미확정이다. 이 중간 상태를 확정처럼 보여주면 안 된다.

- 주문을 `PENDING`("결제 처리 중")으로 노출한다.
- 이용권은 Saga 완료까지 `INACTIVE`로 둔다.
- **PENDING 주문이 존재하는 동안 같은 상품 재주문을 차단**한다. 이걸 안 하면 "처리 중인데 또 사기"로 인한 이중 차감·이중 지급 경합이 생긴다.

이런 기법을 **의미적 잠금(semantic lock)**이라 부른다는 용어까지 얹으면 정리가 깔끔하다. DB 락이 아니라 **데이터의 의미(상태값)로 접근을 제한한다**는 뜻이다.

### "멱등성 키는 어느 단위로 만들어 전파하나요?"

**오케스트레이터가 생성한 `orderId`(또는 `sagaId`)를 모든 커맨드에 실어 보내고, 각 참여자는 그것을 자기 테이블의 유니크 제약 컬럼으로 쓴다.**

차감·환급처럼 한 주문에 성격이 다른 쓰기가 둘이면 `(order_id, entry_type)`으로 단계까지 키에 포함한다. 그러지 않으면 차감이 이미 있다는 이유로 환급이 거부된다.

중요한 것은 **"참여자가 각자 키를 만들면 안 된다"**는 점이다. 재전송된 커맨드에 매번 새 키가 붙으면 중복 탐지가 원천적으로 불가능해진다. 키는 흐름의 시작점에서 한 번 만들어 **끝까지 같은 값으로 전파**돼야 한다.

마지막으로 두 개의 멱등성 장치를 구분해 말하면 정리가 완성된다.

| | 담당 구간 | 흡수하는 중복 |
|---|---|---|
| API 앞단의 `Idempotency-Key` | 클라이언트 ↔ 우리 API | 브라우저·게이트웨이의 재시도 |
| Saga 내부의 `orderId` 전파 | 오케스트레이터 ↔ 참여 서비스 | 커맨드 재전달, 이벤트 중복 배달 |

구간이 다른 **별개의 장치**이므로 하나가 다른 하나를 대체하지 않는다.

## 한 줄 요약

분산된 차감·주문·지급에 전역 롤백은 없으므로, 로컬 트랜잭션의 연쇄(T1→T2→T3)를 오케스트레이터가 상태 테이블 + 아웃박스로 추적하며 이끌고 실패 시 역순 보상(C2→C1, 차감의 보상 = 환급)으로 되돌리는 Saga로 설계한다 — 단, orderId 멱등성 키를 전 단계에 전파해 재전송을 안전하게 만들고(멱등성은 Saga의 전제 조건), 중간 상태는 PENDING·INACTIVE로 감추며(격리성 부재 대응이자 보상 불능 예방), 보상도 실패한다는 전제로 재시도의 끝에 수동 개입 큐를 두는 것까지가 돈 도메인에서의 완성형이다.
