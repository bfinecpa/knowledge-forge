# 이중 지급 심층 방어 — 모든 방어선은 뚫린다는 전제로 쌓는다

> 핵심 관전 포인트: **이중 지급/이중 차감 방어는 한 층으로 끝나지 않는다 — UI(버튼 비활성화)는 두 번째 탭을 모르고, API 멱등성 키는 "새 키로 온 새 시도"를 못 막고, 분산 락은 TTL 만료·페일오버로 새며, 애플리케이션의 exists 검사는 레이스 컨디션의 틈이 있다. 그래서 방어는 계층별로 쌓는다: UI(빈도 감소) → API 멱등성 키(같은 시도의 재전송 흡수) → 분산 락(줄 세우기) → **DB 유니크 제약 + 조건부 UPDATE(최후의 방어선)** → 대사 배치(사후 탐지·보정). 최후의 방어선이 DB 제약이어야 하는 이유는, 상위 계층은 전부 배포 실수나 레이스로 뚫릴 수 있지만 DB 제약은 모든 쓰기 경로(API·배치·어드민)가 반드시 통과하는 단일 관문이고 원자성을 DB 엔진이 보장하기 때문이다. "주문당 승인 결제 1건" 같은 도메인 불변식(항상 참이어야 하는 업무 규칙)을 제약으로 새겨 넣는 것 — 그것이 이 질문의 정답 한 줄이다.**

---

## 0. 질문 + 의도

**질문**: "이중 지급/이중 차감을 막기 위한 방어선을 계층별로 나열해주세요. (UI → API → DB 제약)"

**출제 의도**: 단일 방어(프론트 버튼 비활성화)만 믿는 사람과, UI → API 멱등성 → DB 유니크 제약까지 다층으로 쌓는 사람의 차이를 본다. "각 방어선은 뚫린다"는 전제로 설계하는 심층 방어(defense in depth) 사고가 있는지가 관전 포인트다.

## 1. 왜 한 층으로는 안 되는가

### 1-1. 이중 결제가 실제로 일어나는 여섯 가지 경로

월 구독 9,900원이 두 번 결제되는 경로를 먼저 나열해 보자. 이 목록이 곧 방어 설계의 요구사항이다.

| # | 경로 | 무엇이 일어나는가 |
|---|---|---|
| 1 | 더블 클릭 | 사용자가 응답이 느리자 버튼을 두 번 누른다 |
| 2 | 두 번째 브라우저 탭 | 결제 페이지를 두 탭에 열고 각각 결제한다 |
| 3 | 타임아웃 후 클라이언트 자동 재시도 | HTTP 라이브러리나 게이트웨이가 응답 없는 요청을 스스로 다시 보낸다 |
| 4 | 실패 화면에서 사용자가 "다시 시도" | 사실은 성공했는데 응답만 유실됐고, 사용자는 실패한 줄 안다 |
| 5 | 웹훅 중복 수신 / 대사 배치의 재승인 | 서버 대 서버 경로라 애초에 브라우저를 거치지 않는다 |
| 6 | 어드민 툴에서 수동 재처리 | 운영자가 별도 API를 통해 같은 주문을 다시 밀어 넣는다 |

여섯 경로의 성격이 전부 다르다는 점이 중요하다. 1번은 한 화면 안의 문제이고, 3번은 네트워크 계층의 문제이며, 4번은 사용자 의도의 문제이고, 5·6번은 아예 브라우저를 거치지 않는다. **성격이 다른 여섯 개의 문제를 한 가지 장치로 막을 수는 없다.**

그래서 "프론트에서 버튼 막았는데요"라는 답이 낙제가 된다. 그 답은 1번 하나만 막고 나머지 다섯에는 무방비다.

반대로 "DB 제약 하나면 되죠"도 절반의 답이다. 막히긴 하지만, 매 중복 요청이 PG(결제대행사) 승인까지 갔다가 취소되는 비용과 사용자에게 보이는 에러 화면을 누군가는 흡수해줘야 한다. **각 층의 역할이 다르다** — 상위 층은 빈도를 줄이고, 최하층은 발생 자체를 0으로 만든다.

### 1-2. 비유 — 스위스 치즈 모델

항공 안전에서 쓰는 **스위스 치즈 모델**이 이 구조의 정확한 비유다.

스위스 치즈는 한 장 한 장에 구멍이 뚫려 있다. 구멍 없는 완벽한 한 장은 존재하지 않는다. 사고는 여러 장의 구멍이 **일직선으로 겹치는 순간**에만 관통한다. 그래서 안전 설계의 목표는 "구멍 없는 한 장"을 만드는 것이 아니라 — 그런 것은 없으므로 — **구멍의 위치가 서로 다른 치즈를 여러 장 겹치는 것**이다.

이 사고방식을 **심층 방어(defense in depth)**라고 부른다. 원래 군사 용어로, 전선 하나에 모든 병력을 두지 않고 종심 깊게 여러 겹의 방어선을 두어 하나가 뚫려도 다음 선이 막게 하는 전술이다.

1-1의 여섯 경로가 서로 다른 층의 구멍을 통과한다는 것이 이제 보인다. 각 층은 자기가 아는 범위 안에서만 판단할 수 있고, 그 범위 밖이 곧 그 층의 구멍이다.

### 1-3. 전제 지식 — 레이스 컨디션과 check-then-act

아래에서 "레이스 컨디션 때문에 뚫린다"는 표현이 반복해서 나오므로 먼저 정의하고 간다.

**레이스 컨디션(race condition, 경쟁 상태)**은 두 개 이상의 실행 흐름이 같은 데이터를 동시에 건드릴 때, **누가 먼저 도착하느냐에 따라 결과가 달라지는** 상황이다. 경주(race)에서 이름을 따왔다.

결제 코드에서 가장 흔한 형태는 **check-then-act**다 — 먼저 확인하고(check), 그 결과에 따라 실행하는(act) 구조다.

```java
if (!이미_결제됐나(orderId)) {   // check
    결제한다(orderId);            // act
}
```

이 코드는 혼자 실행되면 완벽하다. 그런데 두 요청이 동시에 들어오면 이렇게 된다.

```
시각   요청 A                         요청 B
----   ---------------------------    ---------------------------
t1     check: 결제 없음 확인
t2                                    check: 결제 없음 확인  <- A가 아직 안 썼다
t3     act: 결제 실행 (9,900원)
t4                                    act: 결제 실행 (9,900원)
```

t1과 t3 사이의 틈에 B가 끼어들었다. **check와 act 사이에 시간 간격이 있는 한, 그 사이에 세상이 바뀔 수 있다.** 이 틈을 없애는 방법은 두 가지뿐이다 — 그 구간을 잠금으로 독점하거나(2-3), 검사와 실행을 하나의 원자적 연산으로 합치거나(2-4). 아래 계층 설계는 결국 이 둘의 조합이다.

## 2. 계층별 방어선 — 각 층이 막는 것과 새는 것

전체 그림을 먼저 보자. 위쪽 층일수록 사용자에 가깝고 값이 싸며, 아래로 갈수록 확실해진다.

```
   결제 요청
       |
       v
 [1선] UI 버튼 비활성화 / PRG              성격: 빈도 감소
       |  막는 것: 더블 클릭
       |  새는 곳: 다른 탭, API 직접 호출
       v
 [2선] API 멱등성 키 (Idempotency-Key)     성격: 재전송 흡수
       |  막는 것: 같은 시도의 자동 재전송
       |  새는 곳: 사용자가 누른 "다시 시도"(새 키)
       v
 [3선] 분산 락 (Redis)                      성격: 줄 세우기
       |  막는 것: 동시 요청의 충돌 빈도
       |  새는 곳: TTL 만료, 페일오버, 해제 순서 버그
       v
 [4선] DB 유니크 제약 + 조건부 UPDATE       성격: 최종 판정 (원자적)
       |  막는 것: 위를 전부 통과한 모든 중복
       |  새는 곳: 우리 DB 밖의 사실(PG에만 남은 승인)
       v
 [5선] 대사 배치                            성격: 사후 탐지·보정
          찾는 것: "우리 1건 : PG 2건" 같은 외부와의 불일치
```

1~4선은 **예방**이고 5선은 **탐지·보정**이다. 이 성격 차이는 4절 꼬리질문에서 다시 다룬다.

### 2-1. 1선 UI: 빈도를 줄이는 층 (정합성 보장이 아니다)

할 일은 세 가지다.

- 결제 버튼 클릭 즉시 비활성화 + 로딩 오버레이 — 같은 화면에서의 연타를 끊는다.
- 결제 진행 중 페이지 이탈 경고 — 사용자가 중간에 새로고침하는 것을 줄인다.
- 완료 후 결과 페이지로 **redirect**. 이를 **PRG(Post/Redirect/Get) 패턴**이라 부른다. POST 응답을 그대로 화면에 그리면 사용자가 새로고침했을 때 브라우저가 "양식을 다시 제출하시겠습니까?"를 띄우고 POST가 재전송된다. POST 처리 후 즉시 GET 페이지로 리다이렉트해 두면 새로고침해도 GET만 반복된다.

이 층의 가치는 명확하다. **최다 빈도 경로(더블 클릭)를 끊어 하위 층의 부하와 CS를 줄인다.** 하지만 정합성 보장은 아니다.

**새는 곳**: 두 번째 탭, 새로고침, 앱 강제 종료 후 재실행, JS 오류로 비활성화 코드 미실행, 그리고 API 직접 호출. UI는 **자기 화면 하나의 상태만** 알기 때문에 구조적으로 여기까지다.

### 2-2. 2선 API: 멱등성 키 — 같은 시도의 재전송을 흡수

#### 멱등성과 멱등성 키가 무엇인가

**멱등성(idempotency)**은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"이다. 전등의 끄기 버튼을 열 번 눌러도 결과는 꺼진 상태 하나인 것과 같다. HTTP에서 GET·PUT·DELETE는 멱등하고 POST는 멱등하지 않다고 말하는 것도 이 뜻이다 — POST는 부를 때마다 새 자원이 생긴다.

결제는 본질적으로 POST다. 그래서 **인위적으로 멱등하게 만들어야** 한다. 그 장치가 **멱등성 키(idempotency key)**다.

클라이언트가 **결제 시도 1건마다** 고유한 키를 하나 만들어(보통 UUID) `Idempotency-Key` 헤더에 실어 보낸다. 서버는 이 키를 유니크 제약이 걸린 저장소에 **먼저 INSERT해서 자리를 선점**하고(INSERT-first), 선점에 성공한 최초 요청만 실제 결제를 수행한다. 같은 키가 다시 오면 저장해 둔 최초 응답을 그대로 재생해 돌려준다.

여기서 **INSERT-first**란 "일을 하기 전에 먼저 DB에 자리를 잡는" 순서를 말한다. 검사부터 하지 않고 INSERT부터 하는 이유는, 1-3에서 본 check-then-act의 틈을 없애기 위해서다. INSERT는 유니크 제약과 결합하면 "확인과 선점"이 DB 안에서 한 번에 원자적으로 일어난다.

이 층이 흡수하는 것은 **"같은 시도의 재전송"**이다 — 1-1의 3번(타임아웃 후 자동 재시도)과 중간 게이트웨이의 재전송이 여기서 전부 걸린다.

> 멱등성 키의 상세 설계(키 스코프, 응답 저장 형식, TTL, 동시 요청 처리)는 `09-rest-api/06` 문서가 다룬다. 이 문서에서는 계층 구조 안에서의 **위치와 한계**만 짚는다.

#### 새는 곳 — 멱등성 키의 관할 밖

멱등성 키는 **전송 계층의 중복**만 막는다. 사용자가 실패 화면에서 의도적으로 "다시 시도"를 누르면 클라이언트는 **새 키**를 만든다. 그리고 그건 클라이언트 입장에서 올바른 동작이다 — 사용자가 새 시도를 했으니까.

문제는 첫 결제가 사실은 성공해 있었던 경우다. 키가 다르니 서버는 이걸 정당한 신규 요청으로 보고 그대로 통과시킨다. 이것이 1-1의 4번 경로다.

그 밖에 운영 실수로도 뚫린다.

- 키 스코프 버그 — 사용자별로 격리해야 할 키를 전역으로 쓰거나 그 반대
- TTL(키 보관 기간) 만료 후 도착한 늦은 재시도
- API 게이트웨이 교체 배포에서 `Idempotency-Key` 헤더 전파 누락

### 2-3. 3선 애플리케이션: 분산 락 — 줄 세우기이지, 보장이 아니다

#### 왜 DB 락이 아니라 "분산" 락인가

한 프로세스 안이라면 `synchronized`로 줄을 세우면 된다. 그런데 결제 서버는 보통 여러 대다. 서버 A와 서버 B에 각각 요청이 들어오면 `synchronized`는 서로를 모른다. 그래서 **모든 서버가 공유하는 외부 저장소**에 "지금 이 주문은 내가 처리 중"이라는 표식을 두는데, 이것이 **분산 락(distributed lock)**이다. Redis가 흔히 쓰인다.

```
SET lock:payment:order:8471 <소유자ID> NX PX 3000
```

`NX`는 "키가 없을 때만 설정"(먼저 잡은 쪽이 이긴다), `PX 3000`은 **TTL(Time To Live) 3초** — 3초 뒤 자동 소멸이라는 뜻이다. TTL이 필요한 이유는, 락을 잡은 서버가 죽어버리면 아무도 락을 풀어주지 않아 그 주문이 영원히 처리 불가가 되기 때문이다.

이 층은 유효하다. 같은 주문의 동시 요청을 직렬화해 하위 층의 충돌 빈도와 불필요한 PG 호출을 줄인다.

#### 새는 곳 — 이것만 믿으면 안 되는 세 가지 이유

**(1) TTL 만료.** 락 TTL이 3초인데 소유자가 5초 걸리면? TTL은 이미 만료됐고 두 번째 요청이 락을 새로 획득한다. 첫 번째 스레드는 자기가 락을 잃은 줄 모르고 계속 실행한다 — **둘이 동시에 실행된다.**

여기서 "5초 걸릴 일이 있나?"라는 의문이 들 수 있다. 있다. 대표적인 것이 **GC 멈춤(stop-the-world pause)**이다. JVM이 가비지 컬렉션을 하는 동안 애플리케이션 스레드가 전부 멈추는데, 힙이 크고 full GC가 걸리면 수 초가 걸릴 수 있다. 멈춘 스레드는 자기가 멈춘 줄도 모른다. PG 응답 지연도 같은 결과를 만든다.

**(2) 페일오버 시 락 유실.** Redis 마스터가 죽어 레플리카로 승격(failover)될 때, 마스터에만 있고 레플리카에 아직 복제되지 않은 락 정보는 사라진다. 그 순간 같은 락을 두 요청이 동시에 쥔다. Redis 복제는 비동기이므로 이 창은 구조적으로 존재한다.

**(3) 해제와 커밋의 순서 버그.** 락을 먼저 풀고 나중에 커밋하는 코드가 있다면, 그 사이에 들어온 다음 요청은 아직 커밋되지 않아 보이지 않는 데이터를 검사하고 통과한다.

```java
// Before: 락 해제가 커밋보다 먼저 — 그 틈에 다음 요청이 통과한다
lock.acquire(key);
try {
    paymentService.pay(orderId);   // @Transactional 안에서 커밋
} finally {
    lock.release(key);             // 커밋 완료 전에 풀릴 수 있다
}

// After: 트랜잭션 커밋이 끝난 뒤에 푼다
lock.acquire(key);
try {
    paymentService.pay(orderId);
    // pay()가 반환된 시점 = 커밋 완료 시점이 되도록
    // 트랜잭션 경계를 pay() 내부에 두고, 락 획득/해제는 그 바깥에 둔다.
} finally {
    lock.release(key);
}
```

결론은 하나다. **락은 원자성의 출처가 될 수 없다.** 락은 "대부분의 경우 줄을 잘 세워주는" 확률적 장치다. 원자성의 출처는 다음 층이다.

### 2-4. 4선(최후) DB: 유니크 제약 + 조건부 UPDATE

#### 도메인 불변식을 DB에 새긴다

**도메인 불변식(domain invariant)**이란 그 업무에서 **언제나 참이어야 하는 규칙**이다. 여기서의 불변식은 이것이다.

> **"하나의 주문에는 살아있는(진행 중이거나 승인된) 결제가 1건만 존재한다."**

이 규칙을 코드의 if문이 아니라 **DB 제약**으로 새기는 것이 4선의 전부다. 이유는 명확하다. 애플리케이션 코드는 경로마다 따로 짜여 있어서(결제 API, 웹훅 핸들러, 배치, 어드민 툴) 한 곳에서 빠뜨리면 뚫린다. DB 제약은 **모든 쓰기가 반드시 통과하는 단일 관문**이다.

PostgreSQL은 이 불변식을 **부분 유니크 인덱스(partial unique index)**로 정확히 표현할 수 있다. 부분 인덱스란 `WHERE` 조건을 만족하는 행에 대해서만 만들어지는 인덱스를 말한다.

```sql
-- 주문당 PENDING/APPROVED 결제는 1건만. FAILED는 여러 건 쌓여도
-- 되므로(재시도 이력을 남겨야 한다) 인덱스 대상에서 제외한다.
CREATE UNIQUE INDEX uq_payment_active_per_order
    ON payment (order_id)
 WHERE status IN ('PENDING', 'APPROVED');
```

단순 `UNIQUE (order_id)`로는 안 되는 이유가 여기 있다. 그러면 실패한 결제 이력조차 2건 이상 남길 수 없게 되어, 재시도 자체가 불가능해진다.

#### Before/After — exists 검사에서 INSERT-first로

```java
// Before: 애플리케이션 exists 검사 — 1-3의 레이스에 그대로 뚫린다
public Payment start(long orderId, long amount) {
    if (paymentRepository.existsActiveByOrderId(orderId)) {  // ① 검사
        throw new DuplicatePaymentException(orderId);
    }
    Payment p = paymentRepository.save(
        Payment.pending(orderId, amount));                   // ② 생성
    pgClient.approve(p);                                     // ③ 승인
    return p;
    // 두 요청이 동시에 ①에서 "없음"을 보면 둘 다 ③까지 간다 —
    // 9,900원이 PG에서 두 번 승인된다. ①과 ② 사이 틈이 곧 사고다.
}
```

```java
// After: INSERT-first 선점 — 유니크 인덱스가 심판을 본다
public Payment start(long orderId, long amount) {
    Payment p;
    try {
        // PG 승인 "전"에 PENDING 행을 넣어 자리를 선점한다.
        // saveAndFlush로 즉시 INSERT를 날려야 여기서 제약 위반이 난다.
        // (save만 하면 트랜잭션 종료 시점까지 INSERT가 미뤄질 수 있다)
        p = paymentRepository.saveAndFlush(
                Payment.pending(orderId, amount));
    } catch (DataIntegrityViolationException e) {
        // 유니크 위반 = 누군가 먼저 선점했다는 뜻.
        // 중요한 건 "여기서 끝나면 PG에는 돈이 안 나갔다"는 점이다.
        throw new PaymentAlreadyInProgressException(orderId);
    }

    pgClient.approve(p);            // 최초 1건만 여기 도달한다

    int updated = paymentRepository.approve(p.getId());
    // rowcount 0 = 그 사이 누군가(웹훅/배치) 이미 상태를 바꿨다는 뜻.
    // 조용히 덮어쓰지 않고 예외로 드러내 조사 대상으로 만든다.
    if (updated == 0) throw new IllegalPaymentStateException(p.getId());
    return p;
}

// 상태 전이도 조건부 UPDATE — PENDING일 때만 APPROVED가 된다
@Modifying
@Query("UPDATE Payment p SET p.status = 'APPROVED' " +
       "WHERE p.id = :id AND p.status = 'PENDING'")
int approve(@Param("id") long id);
```

두 가지가 포인트다.

**첫째, 선점을 PG 승인 앞에 둔다.** 승인 후 INSERT에서 유니크 위반이 나는 구조라면, 그 시점엔 이미 두 번째 9,900원이 PG에서 승인된 뒤다. 그러면 즉시 취소를 호출해야 하고, 취소마저 실패하면 보정 큐로 넘겨야 하는 뒤처리가 줄줄이 붙는다. 승인 전에 걸러지면 **돈이 아예 안 나간다.** 순서 하나로 사고 처리 비용이 사라진다.

**둘째, 상태 전이를 조건부 UPDATE로 잠근다.** `WHERE status = 'PENDING'`이 붙어 있으면, 웹훅과 폴링이 동시에 같은 결제를 승인 확정하려 해도 rowcount 1을 얻는 쪽은 하나뿐이다. 늦게 온 쪽은 0건을 받고 자기가 졌다는 것을 안다. 05번 문서의 잔액 차감(`UPDATE wallet SET balance = balance - 9900 WHERE user_id = ? AND balance >= 9900`)과 정확히 같은 원리다 — **검사 조건을 WHERE에 넣어 검사와 실행 사이의 틈을 없앤다.**

### 2-5. 5선(사후) 대사: 예방이 아니라 탐지·보정

4선까지 쌓아도 남는 것이 있다. 4선이 지키는 것은 **우리 DB의 상태**이지, PG 쪽 상태가 아니기 때문이다.

예컨대 우리 DB에는 결제가 1건인데 PG에는 2건이 승인돼 있는 경우가 생긴다. 승인은 됐는데 우리 쪽 기록 직전에 죽었거나, 취소 API 호출이 유실된 채 잊힌 케이스다. 우리 DB만 봐서는 이상이 없어 보인다.

그래서 **대사(reconciliation)** 배치를 둔다. 대사란 서로 다른 곳에 기록된 숫자를 맞춰 보고 어긋난 부분을 찾아내는 회계 작업이다. 매일 PG가 내려주는 거래 내역 파일과 우리 `payment` 테이블·원장을 `orderId` 기준으로 돌려 맞춰 "우리 1건 : PG 2건" 같은 불일치를 찾아내고, 자동 취소를 걸거나 운영자 보정 큐로 넘긴다.

성격이 다르다는 점을 분명히 하자. 이것은 방어선이라기보다 **그물 아래의 그물**이다. 막지는 못하지만, 뚫린 것을 며칠 안에 반드시 발견한다는 보장 장치다.

### 2-6. 다섯 층 요약

| 층 | 장치 | 성격 | 막는 경로 | 새는 곳 |
|---|---|---|---|---|
| 1선 | UI 비활성화 / PRG | 빈도 감소 | 더블 클릭, 새로고침 | 다른 탭, API 직접 호출 |
| 2선 | 멱등성 키 | 재전송 흡수 | 자동 재시도, 게이트웨이 재전송 | 새 키로 온 새 시도 |
| 3선 | 분산 락 | 줄 세우기 | 동시 요청 충돌 | TTL 만료, 페일오버, 순서 버그 |
| 4선 | 유니크 제약 + 조건부 UPDATE | 최종 판정 | 위를 통과한 모든 중복 | 우리 DB 밖의 사실 |
| 5선 | 대사 배치 | 탐지·보정 | (예방 아님) 외부와의 불일치 발견 | 발견까지 시간 지연 |

## 3. 실무 사례 — 방어선이 실제로 뚫리는 순간들

### 사례 1: 두 탭 결제 — UI가 막았다고 믿었던 팀

사용자가 결제 페이지를 두 탭에 열어두고 각각 결제 버튼을 눌렀다.

각 탭의 버튼은 성실하게 비활성화됐다. 하지만 탭들은 서로의 존재를 모른다. 멱등성 키도 탭마다 새로 생성돼 서로 다르다 — 1선·2선을 나란히 통과한다. 3선 분산 락이 있었다면 둘 중 하나는 대기했겠지만, 첫 번째가 PG 승인을 마치고 락을 푼 뒤에는 두 번째가 그대로 진행한다(락은 "동시"만 막지 "순차 중복"은 못 막는다).

4선이 없었다면 9,900원이 2건 승인된다. 부분 유니크 인덱스가 있었다면 두 번째 INSERT가 `PaymentAlreadyInProgressException`으로 끝나고 **PG 호출 자체가 발생하지 않는다.**

교훈: **상위 층의 방어는 "한 클라이언트 인스턴스" 스코프까지만 유효하다.** 탭이 둘이면 클라이언트도 둘이다.

### 사례 2: "다시 시도" 새 키 — 멱등성 키의 관할 밖

첫 결제 요청이 PG 승인까지 정상적으로 끝났는데 응답이 유실됐다. 사용자는 실패 화면을 보고 "다시 시도"를 눌렀고, 클라이언트는 새 멱등성 키를 만들었다. 클라이언트 입장에서는 **새 시도이므로 새 키가 올바른 동작**이다.

그래서 2선은 이 요청을 설계대로 통과시킨다. 버그가 아니다. 이 요청을 멈출 수 있는 것은 "주문당 승인 결제 1건"이라는 도메인 불변식(4선)뿐이다.

이 사례 하나가 두 개념의 경계를 정확히 보여준다.

- **전송 계층 중복 제거(transport-level dedup)** = 멱등성 키. "같은 메시지가 두 번 왔는가"를 본다.
- **비즈니스 중복 제거(business-level dedup)** = 도메인 불변식. "이 업무가 이미 완료됐는가"를 본다.

서로 다른 질문에 답하는 장치이므로 대체 관계가 아니다.

### 사례 3: GC 멈춤 8초가 만든 이중 차감 — 락의 배신

포인트 30,000P 차감을 처리하던 중 애플리케이션이 full GC로 8초 멈췄다.

```
시각   스레드 A (락 소유)              Redis 락                스레드 B
----   ---------------------------    -------------------    ------------------
t0     락 획득 (TTL 3초)               lock=A (3초)
t1     차감 처리 시작
t2     full GC로 멈춤 (8초)
t3                                     TTL 만료 -> 락 소멸
t4                                     lock=B (3초)           락 획득
t5                                                            30,000P 차감 실행
t6     GC 종료, 자기가 락을 잃은
       줄 모르고 차감 실행
       -> 합계 60,000P 차감
```

30,000P가 두 번 빠져 합계 60,000P가 차감됐다. 원장에 `UNIQUE (order_id, entry_type)`이 있었다면 두 번째 INSERT가 유니크 위반으로 실패하며 그 차감 트랜잭션 전체가 롤백됐을 것이다.

**락은 줄을 세울 뿐이고, 최종 심판은 DB 제약**이라는 것을 돈으로 배운 사례다.

## 4. 꼬리질문 대비 포인트

### "분산 락을 걸었는데 왜 유니크 제약이 또 필요한가요?" (시니어 변별 포인트)

락과 제약은 **역할이 다르다**는 것부터 말한다.

**락은 가용성·효율 장치다.** 동시 요청을 줄 세워 충돌 빈도와 불필요한 PG 호출을 줄인다. 사고를 "덜 일어나게" 만드는 확률적 장치다. 그러나 그 보장은 TTL 만료(GC 멈춤·처리 지연), 페일오버 시 락 유실, 해제와 커밋의 순서 버그로 깨질 수 있고, 이 깨짐은 낮은 확률로 **반드시** 일어난다. 결제 트래픽이 하루 수십만 건이면 0.01%도 매일 수십 건이다.

**제약은 정합성 장치다.** DB 엔진이 쓰기 시점에 원자적으로 판정하므로, 상위에서 무엇이 새어 들어와도 최종 상태의 불변식은 지켜진다.

이 꼬리질문의 변별 지점은 **"락이 뚫리는 세 가지 경로를 즉석에서 열거할 수 있는가"**다. 2-3의 세 가지(TTL 만료, 페일오버, 해제 순서)를 구체적으로 말할 수 있어야 한다.

한 걸음 더 나가려면 **fencing token**을 언급한다. 락을 줄 때 단조 증가하는 세대 번호를 함께 발급하고, 실제 쓰기에 그 번호를 실어 보내 저장소가 "지금까지 본 것보다 낮은 번호의 쓰기는 거부"하게 하는 기법이다. 2-3의 (1) TTL 만료 시나리오에서 깨어난 옛 소유자의 쓰기를 거부할 수 있다. 다만 결론은 같다 — **최종 판정은 데이터 저장소에서 한다.**

### "유니크 위반이 났을 때 이미 PG 승인이 떨어진 뒤라면요?"

선점(INSERT)을 승인 앞에 두면 대부분 예방된다. 하지만 **웹훅 기반 확정**처럼 승인 사실을 나중에 아는 경로에서는 "PG 승인 2건, 우리 DB 1건"이 여전히 생길 수 있다.

이때의 절차는 이렇다.

1. 탐지 즉시 **두 번째 승인 건을 PG 취소 API로 자동 취소**한다.
2. 취소 호출마저 실패하면 보정 큐에 적재해 재시도 + 운영자 알림으로 넘긴다.
3. 고객 카드에 9,900원이 이중 청구된 상태는 **분 단위로 해소돼야 하는 장애**로 취급한다. 하루 뒤 배치로 처리하면 이미 카드사 청구가 나간다.

여기서 **망취소(net cancellation)**를 알면 실무 경험이 드러난다. 승인 직후 같은 날 안에 취소하면 승인 자체를 없던 것으로 처리해 매입(청구)이 아예 발생하지 않게 해주는 PG가 있다. 이 경우 고객 명세서에 승인·취소 두 줄이 남지 않아 CS가 크게 줄어든다.

### "멱등성 키가 있는데 도메인 불변식이 왜 또 필요한가요?"

멱등성 키의 **관할은 "같은 키 = 같은 시도의 재전송"까지**다.

새 키로 오는 새 시도 — 사용자의 의도적 재시도, 다른 탭, 어드민 재처리 — 는 키 입장에서 전부 정당한 신규 요청이다. 키는 "이 요청이 아까 그 요청과 같은 것인가"만 판단할 수 있고, "이 업무가 이미 완료됐는가"는 판단할 수 없다.

후자를 아는 것은 도메인 규칙뿐이다. 그래서 "주문당 승인 결제 1건"을 제약으로 새긴다.

요약하면 **멱등성 키는 재시도 폭풍을 흡수하는 완충재, 도메인 불변식은 최종 관문**이다. 층이 다르므로 서로 대체가 안 된다. 3절 사례 2가 이 답변의 구체적 근거가 된다.

### "대사 배치도 방어선이라고 할 수 있나요?"

성격이 다르다는 것을 짚어야 한다.

1~4선은 **예방**이다 — 사고가 데이터에 기록되기 전에 차단한다. 대사는 **탐지·보정**이다 — 이미 벌어진 불일치를 찾아 되돌린다.

예방이 완벽할 수 없다는 전제를 받아들이면 탐지는 선택이 아니라 필수가 된다. 돈 도메인에서 최악은 사고가 나는 것이 아니라 **"뚫렸는지조차 모르는 상태"**이기 때문이다. 사고는 보상하면 되지만, 모르는 사고는 규모가 계속 자란다.

한 가지 더 붙이면 좋다. **대사가 잡은 불일치는 금액·건수와 함께 지표로 쌓아야 한다.** 이 지표가 평소 0인데 어느 날부터 0이 아니라면, 상위 방어선 어딘가에 구멍이 새로 생겼다는 뜻이다 — 대사 결과는 사후 보정 도구인 동시에 **상위 층의 조기 경보**로 쓰인다.

### "PostgreSQL에서 '주문당 승인 결제 1건'을 정확히 어떻게 표현하나요?"

단순 `UNIQUE (order_id)`는 틀린다. 실패한 결제(FAILED)가 이력으로 여러 건 남아야 하는데 그것까지 막아버려 재시도가 불가능해진다.

**부분 유니크 인덱스**로 조건을 좁힌다.

```sql
CREATE UNIQUE INDEX uq_payment_active_per_order
    ON payment (order_id)
 WHERE status IN ('PENDING', 'APPROVED');
```

"살아있는 결제만 1건"이라는 불변식이 그대로 SQL이 된다. 부가 이점으로, 인덱스가 진행 중인 결제만 담으므로 크기가 작게 유지된다.

MySQL에는 부분 인덱스가 없다는 것까지 알면 DB별 차이를 아는 사람으로 보인다. 같은 요구를 MySQL에서 풀려면 "살아있으면 order_id, 아니면 NULL"을 담는 생성 칼럼(generated column)을 만들고 거기에 유니크를 건다 — MySQL의 유니크 인덱스는 NULL을 중복으로 치지 않기 때문에 FAILED 행은 얼마든지 쌓인다.

```sql
-- MySQL 우회: 살아있는 결제만 값을 갖는 생성 칼럼에 유니크를 건다
ALTER TABLE payment
  ADD COLUMN active_order_id BIGINT
      GENERATED ALWAYS AS (
        CASE WHEN status IN ('PENDING','APPROVED') THEN order_id END
      ) STORED,
  ADD UNIQUE KEY uq_payment_active (active_order_id);
```
