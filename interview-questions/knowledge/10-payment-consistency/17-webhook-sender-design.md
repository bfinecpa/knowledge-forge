# 웹훅 발신 설계 — 내 이벤트의 소비자가 겪을 문제까지가 내 설계 범위다

> 핵심 관전 포인트: **웹훅 발신은 "HTTP POST 한 번"이 아니라 배달 시스템 하나를 만드는 일이다. 비즈니스 트랜잭션과 같은 트랜잭션으로 발송 이벤트를 outbox 테이블에 먼저 기록하고(커밋됐으면 반드시 발송, 롤백됐으면 발송 안 함), 별도 디스패처가 비동기로 발송한다. 재시도는 지수 백오프 + 최대 횟수 + 데드레터로 관리하되, 재시도가 곧 수신측에 중복 도착을 의미하므로 이벤트 ID·발생 시각·HMAC 서명을 반드시 실어 수신측이 검증·중복 제거·순서 판단을 할 수 있게 해준다. 발송 큐는 수신사별로 격리해 한 수신사의 장애가 다른 수신사의 웹훅을 밀리게 하지 못하게 하고, 순서는 보장하지 않는다고 계약(문서)에 명시한 뒤 시퀀스로 판단 근거만 제공한다. 실패 이벤트 재발송 콘솔까지 있어야 운영이 성립한다 — 상대가 겪을 위조·중복·역전 문제를 발신자가 미리 준비해주는 시야를 본다.**

---

## 0. 질문 + 의도

**질문**: "웹훅을 발신하는 쪽은 어떻게 설계하나요? (서명, 재시도와 백오프, 순서 역전, 수신측 장애 시 격리)"

**출제 의도**: 수신측 설계(기본 문항)의 거울상이다. 수신사 한 곳의 장애가 내 발송 큐 전체를 밀리게 하지 않도록 격리하고, 재시도가 상대에게 중복으로 도착함을 전제로 서명과 이벤트 ID를 실어주는지 — "내가 만든 API의 소비자가 겪을 문제"까지 설계하는 시야로, 파트너 연동 경험의 진위를 가른다.

## 1. 왜 문제인가 — 발신은 "보내면 끝"이 아니다

### 1-1. 언제 우리가 발신자가 되는가

앞 문항([03. 웹훅 수신 처리](./03-webhook-reception-handling.md))에서는 우리가 PG사의 웹훅을 받는 쪽이었다. 이번에는 입장이 바뀐다.

우리가 PG사·결제대행 플랫폼을 만들거나, 가맹점·파트너사에 "정산이 완료됐다", "결제가 승인됐다" 같은 이벤트를 통지하는 서비스를 운영하면 우리가 발신자다. 사내 마이크로서비스 사이의 이벤트 통지도 구조는 같다.

이때 순진한 구현은 이렇다 — **"이벤트가 생기면 그 자리에서 상대 URL로 POST 한다."** 코드로는 세 줄이면 된다. 그런데 이 구조는 네 방향에서 무너진다. 하나씩 보자.

### 1-2. 무너지는 방향 ① 원자성 — 두 시스템에 쓰는 순간 생기는 문제

먼저 전제를 하나 짚자. 우리 코드가 "결제 상태를 PAID로 바꾸고 웹훅을 보낸다"를 할 때, 이건 **서로 다른 두 시스템에 쓰기를 하는 것**이다. 하나는 우리 DB, 하나는 상대 서버다.

`@Transactional`은 우리 DB에 대해서만 작동한다. HTTP 호출은 트랜잭션의 관리 대상이 아니다. 롤백해도 이미 나간 HTTP 요청은 되돌아오지 않는다. 이렇게 **트랜잭션이 하나로 묶지 못하는 두 곳에 써야 하는 상황**을 이중 쓰기 문제(dual write problem)라고 부른다.

무엇이 문제인지 시간축으로 보면 두 가지 실패가 대칭적으로 나타난다.

```
[ 실패 ① — 이벤트 유실 : 커밋은 됐는데 발송을 못 했다 ]

  t1  BEGIN
  t2  payment 상태를 PAID로 UPDATE
  t3  COMMIT                    ← 우리 DB에는 승인이 확정됐다
  t4  X  프로세스 종료 (배포, OOM, 인스턴스 회수, 서버 재시작)
      → 발송 코드가 실행되지 못했다.
      → 더 나쁜 건, "보내야 한다"는 사실 자체가 어디에도 기록돼
        있지 않다는 것이다. 재시도할 근거가 없다.
      → 수신사는 이 승인을 영영 모른다.

[ 실패 ② — 유령 이벤트 : 발송은 됐는데 커밋이 안 됐다 ]

  t1  BEGIN
  t2  payment 상태를 PAID로 UPDATE
  t3  HTTP POST 발송 → 200 OK   ← 수신사는 "승인됨"으로 믿고 처리 시작
  t4  이후 로직에서 예외 발생 (재고 부족, 검증 실패 등)
  t5  ROLLBACK                  ← 우리 DB에는 승인이 없다
      → 수신사만 승인됐다고 믿는다.
      → 그쪽이 출고까지 진행했다면 되돌릴 방법이 없다.
```

두 실패는 순서를 바꿔도 사라지지 않는다. "커밋 먼저"면 ①이 나고 "발송 먼저"면 ②가 난다. 어느 쪽을 먼저 하든 그 사이의 틈에서 사고가 난다는 것이 이중 쓰기 문제의 본질이다.

### 1-3. 무너지는 방향 ② 장애 전파 — 남의 장애가 내 장애가 된다

발송을 결제 트랜잭션 안에서 동기로 하면, 우리 스레드가 상대 서버의 응답을 기다리며 멈춰 선다. 상대가 30초 걸리면 우리 스레드도 30초 묶인다.

여기서 두 자원이 동시에 고갈된다. **톰캣 스레드 풀**(요청을 처리할 스레드가 없어 새 요청이 대기)과 **DB 커넥션 풀**(트랜잭션이 안 끝났으니 커넥션을 반납하지 못한다). 후자가 특히 치명적이다. 발송과 아무 관계 없는 조회 API까지 커넥션을 못 받아 함께 죽는다.

즉 **남의 서버가 느려진 것이 내 결제 API 전체의 장애로 번역된다.** 이건 상대를 신뢰할 수 있느냐의 문제가 아니라, 동기 호출이라는 구조가 장애를 전파하는 통로라는 문제다.

### 1-4. 무너지는 방향 ③ 수신사 간 간섭 — 한 집이 온 동네를 막는다

발송을 비동기로 바꿔 큐에 넣었다고 해보자. 장애 전파는 막았다. 그런데 큐가 하나면 새로운 문제가 생긴다.

대형 수신사 하나가 점검에 들어가 5xx를 뿜기 시작하면, 그쪽으로 갈 이벤트가 계속 실패하고 재시도로 큐에 다시 쌓인다. 이 물량이 큐 앞머리를 점령하면 뒤에 있는 다른 수신사의 신규 이벤트가 앞으로 나오지 못한다.

이 현상을 **head-of-line blocking(줄 맨 앞이 막혀 뒤가 전부 대기하는 현상)** 이라고 부른다. 계산대 맨 앞 손님이 가격 확인을 기다리는 동안 뒤에 열 명이 서 있는 상황과 같다. 뒤 사람들은 아무 문제가 없는데도 못 지나간다.

### 1-5. 무너지는 방향 ④ 소비자 문제 전가 — 내 설계 부실이 파트너의 사고가 된다

여기가 이 문항의 출제 의도와 가장 맞닿은 지점이다.

재시도를 하는 순간 수신측에는 **중복**이 도착한다. 병렬로 발송하거나 재시도가 끼는 순간 **순서**가 뒤집힌다. 이건 우리가 재시도를 도입한 대가로 상대에게 넘기는 부담이다.

그런데 우리가 이벤트 ID를 안 실어주면 상대는 중복 제거를 할 수 없다. 무엇이 같은 이벤트인지 판별할 열쇠가 없기 때문이다. 서명을 안 실어주면 상대는 그 요청이 정말 우리에게서 온 것인지 확인할 수 없다. 발생 시각과 시퀀스를 안 주면 어느 게 최신인지 판단할 근거가 없다.

즉 **우리 발신 설계의 부실이 모든 파트너사의 사고가 된다.** 상대가 아무리 잘 만들어도 재료가 없으면 방어할 수가 없다.

### 1-6. 비유 — 웹훅 발신 시스템은 우체국이다

지금까지의 네 문제를 한 그림으로 묶으면 **우체국**이다.

우체국은 편지를 받자마자 직원이 배달하러 뛰어나가지 않는다. 먼저 접수 대장에 기록한다(**outbox**). 그래야 직원이 중간에 사고를 당해도 편지가 사라지지 않는다.

수취인이 부재중이면 정해진 일정으로 재방문한다(**백오프**). 첫날엔 몇 시간 뒤, 그다음엔 다음 날, 그다음엔 사흘 뒤 식으로 간격을 벌린다. 계속 못 만나면 반송 보관소에 넣고 별도 처리한다(**데드레터**).

한 동네 도로가 막혔다고 다른 동네 배달을 멈추지도 않는다(**수신사별 격리**). 그리고 모든 우편물에는 등기번호(**이벤트 ID**)와 소인(**서명과 발생 시각**)이 찍혀 있어, 받는 쪽이 "이거 아까 받은 그 편지네", "이건 진짜 우체국 소인이네"를 확인할 수 있다.

## 2. 발신 시스템 설계 — 기록, 서명, 재시도, 격리

### 2-1. Outbox 패턴 — DB에 먼저 기록하고, 발송은 비동기로

1-2절의 이중 쓰기 문제로 돌아가자. 두 시스템에 원자적으로 쓰고 싶은데 방법이 없었다. 선택지를 늘어놓아 보자.

- (a) **분산 트랜잭션(2단계 커밋, 2PC)**: DB와 HTTP 호출을 하나의 트랜잭션으로 묶는다. 이론상 가능하지만 HTTP API가 2PC를 지원해야 하고(거의 없다), 코디네이터가 죽으면 참가자들이 락을 잡은 채 멈추며, 성능도 나쁘다. 실무에서 웹훅 발신에 쓰지 않는다.
- (b) **커밋 후 발송**: 커밋이 끝난 뒤 발송한다. 유령 이벤트(실패 ②)는 막지만 유실(실패 ①)은 못 막는다.
- (c) **발송해야 한다는 사실을 DB에 함께 커밋한다**: 두 시스템에 원자적으로 쓰는 걸 포기하고, **한 시스템(우리 DB)에만 원자적으로 쓴 뒤 나머지를 나중에 따라오게 한다.**

(c)가 **아웃박스 패턴(transactional outbox)** 이다. outbox는 "보낼 편지함"이라는 뜻이고, 발송할 이벤트를 우리 DB의 테이블에 적어두는 것이 전부다.

핵심은 이 INSERT가 **비즈니스 상태 변경과 같은 트랜잭션 안에 있다**는 점이다. 그래서 두 가지가 동시에 보장된다.

- 커밋됐으면 상태 변경과 이벤트 기록이 **둘 다** 남는다 → 유실 없음. 크래시가 나도 기록이 남아 있으니 다른 프로세스가 이어서 보낸다.
- 롤백됐으면 **둘 다** 사라진다 → 유령 이벤트 없음.

실제 HTTP 발송은 별도의 **디스패처(dispatcher, 배차 담당)** 가 맡는다. outbox 테이블을 주기적으로 읽어 아직 못 보낸 것을 골라 보내는 워커다.

```sql
-- PostgreSQL: outbox 겸 발송 상태 추적 테이블
CREATE TABLE webhook_outbox (
    event_id      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
                                    -- 수신측이 중복 제거에 쓸 열쇠.
                                    -- 재시도해도 이 값은 절대 바뀌지 않는다
    receiver_id   bigint      NOT NULL,  -- 수신사. 엔드포인트와 시크릿의 주인이자
                                         -- 격리(2-4절)의 기준 축
    event_type    text        NOT NULL,  -- payment.approved 등
    resource_key  text        NOT NULL,  -- 거래 식별자. 같은 거래의 이벤트들을
                                         -- 묶는 축(순서 판단·직렬 발송에 쓰인다)
    sequence_no   bigint      NOT NULL,  -- 그 거래 안에서 몇 번째 이벤트인지.
                                         -- 도착 순서가 뒤집혔을 때 수신측이
                                         -- 신·구를 판단할 근거
    payload       jsonb       NOT NULL,
    occurred_at   timestamptz NOT NULL,  -- 발송 시각이 아니라 "사건이 일어난" 시각.
                                         -- 재시도로 늦게 도착해도 이 값은 그대로다
    status        text NOT NULL DEFAULT 'PENDING',
                                    -- PENDING → SENDING → DELIVERED | DEAD
    attempt_count int  NOT NULL DEFAULT 0,       -- 백오프 간격 계산과
                                                 -- 최대 횟수 판정에 쓴다
    next_attempt_at timestamptz NOT NULL DEFAULT now()
                                    -- "이 시각 전에는 집지 마라". 백오프를
                                    -- 스케줄러 없이 테이블 한 컬럼으로 구현한다
);

-- 발송 대상 조회 전용 인덱스
CREATE INDEX idx_outbox_due
    ON webhook_outbox (receiver_id, next_attempt_at)
    WHERE status IN ('PENDING', 'SENDING');
-- WHERE 절이 붙은 부분 인덱스(partial index)다.
-- 완료된 이벤트는 인덱스에 아예 들어가지 않으므로,
-- 테이블에 수억 건이 쌓여도 폴링 쿼리가 훑는 범위는 "미결 건"뿐이다.
-- 큐로 쓰는 테이블에서 이게 성능의 거의 전부다.
```

```java
// Before: 비즈니스 트랜잭션 안에서 동기 발송 — 원자성도 격리도 없다
@Transactional
public void approvePayment(Payment p) {
    p.transitionTo(PaymentStatus.PAID);
    paymentRepository.save(p);

    // 문제 1: 수신사가 30초 걸리면 이 트랜잭션이 30초 열려 있다.
    //         DB 커넥션도 30초 반납되지 않는다 → 커넥션 풀 고갈.
    // 문제 2: 여기서 예외가 나면 결제 승인까지 롤백된다.
    //         남의 서버 장애가 우리 결제 실패가 된다.
    // 문제 3: 발송에 성공하고 이 아래에서 예외가 나면 롤백되는데,
    //         이미 나간 HTTP 요청은 되돌아오지 않는다 → 유령 이벤트.
    restClient.post().uri(receiver.url()).body(toEvent(p)).retrieve();
}
```

```java
// After: 같은 트랜잭션에는 outbox INSERT까지만. 발송은 디스패처가 맡는다
@Transactional
public void approvePayment(Payment p) {
    p.transitionTo(PaymentStatus.PAID);
    paymentRepository.save(p);

    // 같은 트랜잭션 = 원자적.
    // 커밋되면 "보내야 한다"는 사실이 반드시 남고,
    // 롤백되면 이 기록도 함께 사라진다.
    // 외부 호출이 없으므로 트랜잭션은 여전히 짧다.
    outboxRepository.save(WebhookOutbox.of(
        p.receiverId(), "payment.approved", p.paymentKey(), p.snapshot()));
}
```

```java
// 디스패처: 수신사별로 도는 워커. 발송 대상을 원자적으로 집어 보낸다
void dispatch(long receiverId) {
    List<WebhookOutbox> due = outboxRepository.claimDue(receiverId, 100);
    // 내부 쿼리:
    //   SELECT * FROM webhook_outbox
    //    WHERE receiver_id = :receiverId
    //      AND status = 'PENDING'
    //      AND next_attempt_at <= now()   ← 백오프 대기 중인 건은 제외
    //    ORDER BY next_attempt_at
    //    LIMIT 100
    //    FOR UPDATE SKIP LOCKED;

    for (WebhookOutbox e : due) {
        try {
            sender.send(e);        // 서명 헤더 포함, 연결 3초 / 응답 5초 타임아웃
            e.markDelivered();     // 2xx만 성공으로 인정한다
        } catch (Exception ex) {
            // 실패하면 다음 시도 시각을 뒤로 밀고 시도 횟수를 올린다.
            // 최대 횟수를 넘으면 내부에서 DEAD로 전환된다.
            e.scheduleRetry(backoff(e.attemptCount()));
        }
    }
}
```

`FOR UPDATE SKIP LOCKED`를 짚고 넘어가자. `FOR UPDATE`는 조회한 행에 락을 걸어 다른 트랜잭션이 손대지 못하게 하는 구문이다. 여기에 `SKIP LOCKED`를 붙이면 **이미 다른 워커가 잡고 있는 행은 기다리지 않고 건너뛴다.**

이 조합이 큐 테이블의 관용구인 이유는, 워커를 여러 대로 늘려도 서로 같은 이벤트를 집지 않으면서(락) 서로를 기다리지도 않기(SKIP) 때문이다. `SKIP LOCKED` 없이 `FOR UPDATE`만 쓰면 워커 2번이 워커 1번이 잡은 행 앞에서 대기하게 되어, 워커를 늘려도 처리량이 안 늘어난다.

마지막으로 outbox의 한계도 정확히 알아야 한다. 디스패처가 **발송에 성공한 직후, `DELIVERED`로 표시하기 전에** 죽으면 그 이벤트는 여전히 `PENDING`으로 남아 재발송된다. 즉 **발신도 at-least-once**다. 정확히 한 번은 만들 수 없고, 그래서 이벤트 ID를 실어 수신측이 중복 제거할 수 있게 하는 것이 계약의 일부가 된다.

### 2-2. 서명과 메타데이터 — 수신측이 검증할 재료를 실어준다

1-5절에서 말했듯, 수신측이 방어하려면 재료가 필요하다. 발송 요청에 최소한 다음을 싣는다.

**HMAC 서명 헤더.** `서명 = HMAC-SHA256(시크릿, 타임스탬프 + "." + 원문 바디)`로 계산한다. HMAC은 "비밀키를 섞어 만든 지문"으로, 시크릿을 모르는 제3자는 본문을 위조해도 같은 지문을 만들 수 없다(자세한 원리는 [03. 웹훅 수신 처리](./03-webhook-reception-handling.md) 2-1절).

여기서 발신자가 신경 써야 할 것은 **타임스탬프를 서명 대상에 포함시키는 것**이다. 안 넣으면 공격자가 정상 요청을 통째로 복사해 나중에 재생하는 재전송 공격을 수신측이 막을 방법이 없다. 서명은 "우리가 만든 요청"임은 증명하지만 "지금 만든 요청"임은 증명하지 못하기 때문이다.

**키 ID(`X-Key-Id`)와 시크릿 로테이션.** 시크릿은 반드시 바꾸게 된다. 유출 의심, 담당자 퇴사, 정기 교체 정책 등의 이유로.

문제는 교체 순간이다. 우리가 새 시크릿으로 서명하기 시작하는 시점과 수신사가 새 시크릿으로 검증하기 시작하는 시점은 절대 정확히 일치하지 않는다. 수신사가 열 곳이면 열 곳의 배포 일정이 다 다르다. 그 틈에 보낸 웹훅은 전부 서명 불일치로 401이 난다.

해결은 **키 ID + 유예 기간(grace period)** 이다. 수신사별로 시크릿을 두 개까지 동시에 유효하게 두고, 헤더에 "이번 서명은 어느 시크릿으로 만들었다"를 밝힌다. 수신사는 키 ID로 해당 시크릿을 찾아 검증하면 되므로, 각자 편한 시점에 새 키를 등록하고 옮겨갈 수 있다. 유예 기간이 끝나면 구 키를 폐기한다.

**이벤트 ID.** 수신측 중복 제거의 유일한 근거다. 여기서 절대 어기면 안 되는 규칙이 하나 있다 — **재시도할 때도 같은 ID를 유지한다.** 재시도마다 새 ID를 발급하면 수신측 입장에서는 서로 다른 이벤트 세 개가 온 것과 구별되지 않아, 중복 제거가 원리적으로 불가능해진다. 코드로는 `UUID.randomUUID()`를 발송 시점이 아니라 outbox INSERT 시점에 한 번만 호출한다는 뜻이다.

**발생 시각(`occurred_at`)과 시퀀스(`sequence_no`).** 도착 순서가 뒤집혔을 때 수신측이 신·구를 판단할 근거다. `occurred_at`은 발송 시각이 아니라 사건이 실제로 일어난 시각이어야 한다 — 재시도로 6시간 늦게 도착해도 이 값은 원래 시각 그대로다.

시퀀스는 리소스(거래) 단위로 단조 증가하는 값으로 준다. 전역 시퀀스가 아니라 거래 단위인 이유는, 전역으로 만들면 발급 지점이 병목이 되고 여러 인스턴스에서 발급할 때 순서가 어차피 깨지기 때문이다. 그리고 수신측이 실제로 알고 싶은 것도 "이 거래 안에서 뭐가 먼저인가"이지 전체 이벤트의 절대 순서가 아니다.

**이벤트 타입과 스키마 버전.** 페이로드 구조를 언젠가 바꾸게 되는데, 모든 수신사가 동시에 따라올 수는 없다. 버전 필드가 있으면 수신측이 분기할 수 있고, 우리도 구버전을 언제까지 지원할지 계약으로 명시할 수 있다.

### 2-3. 재시도 정책 — 지수 백오프 + 지터 + 상한 + 데드레터

**왜 고정 간격이 나쁜가**부터 보자. "1분마다 재시도"는 단순해서 매력적이지만 두 가지로 무너진다.

첫째, 장애의 지속 시간 분포와 안 맞는다. 수신측 장애는 크게 두 종류다 — 배포 실수나 재시작 같은 **수 분짜리**, 그리고 정기 점검이나 인프라 장애 같은 **수 시간짜리**. 1분 간격은 앞의 것에는 적절하지만 뒤의 것에는 재앙이다. 6시간 점검이면 이벤트 한 건당 360번을 시도한다.

둘째, 그 360번이 전부 큐에 부하로 쌓인다. 수신사에는 이미 죽어 있는 서버에 초당 요청을 퍼붓는 셈이고, 우리에게는 워커가 타임아웃 대기로 낭비되는 셈이다.

그래서 **지수 백오프(exponential backoff)** 를 쓴다. 실패할 때마다 대기 시간을 배수로 늘리는 방식이다. "상대가 아직 안 고쳐졌다면 다음엔 더 오래 기다려도 된다"는 직관을 그대로 구현한 것이다.

```
[ 고정 간격 1분, 무한 재시도 ]

  수신사 A가 6시간 점검  →  이벤트 1건당 360회 시도
  시각    00:01  00:02  00:03  00:04  ...  06:00
  시도      1      2      3      4     ...   360
  → 이벤트가 1만 건 밀려 있으면 시도 총량은 360만 회.
    큐는 계속 재적재되어 줄어들지 않고, 다른 수신사가 뒤에서 굶는다.

[ 지수 백오프 + 지터, 최대 7회 ]

  시도   대기 시간    누적 경과      이 간격이 노리는 장애
  ────────────────────────────────────────────────────────
   1차   즉시         0             (이벤트 발생 직후 첫 발송)
   2차   1분          1분           순간적인 네트워크 오류
   3차   5분          6분           배포·재시작 수준의 짧은 장애
   4차   30분         36분          중간 규모 장애
   5차   2시간        2시간 36분    정기 점검
   6차   6시간        8시간 36분    긴 장애
   7차   12시간       20시간 36분   마지막 시도
  ────────────────────────────────────────────────────────
   실패  →  status = DEAD 전환
            + 수신사에 별도 채널(이메일·대시보드)로 통보
            + 운영 콘솔에서 수동 재발송 대기 (2-6절)

  → 같은 6시간 장애에서 시도는 건당 6회 이하.
    앞은 촘촘해서 짧은 장애를 빠르게 흡수하고,
    뒤는 성겨서 긴 장애에도 큐를 좀먹지 않는다.
```

**지터(jitter)** 도 반드시 붙인다. 지터는 "흔들림"이라는 뜻으로, 계산된 대기 시간에 무작위 오차(예: ±20%)를 더하는 것이다.

왜 필요한가. 수신사가 6시간 만에 복구됐다고 하자. 그동안 밀린 이벤트 1만 건의 다음 시도 시각이 전부 정확히 같은 순간으로 계산돼 있으면, 복구되자마자 1만 건이 동시에 날아간다. 방금 일어난 서버가 그 순간 다시 쓰러진다. 이것을 **thundering herd(우르르 몰려드는 소떼)** 라고 한다. 지터를 넣으면 그 1만 건이 몇 분에 걸쳐 흩어져 나간다.

**성공 판정은 2xx만.** 그리고 **3xx 리다이렉트는 따라가지 않는다.** 이유가 중요하다 — 서명된 요청을 리다이렉트 대상 URL로 그대로 재전송하면, 수신사 설정이 잘못됐거나 탈취당했을 때 우리 서명이 붙은 요청을 제3자 서버로 배달해주는 꼴이 된다. 리다이렉트는 설정 오류로 보고 실패 처리하는 게 안전하다.

**타임아웃은 짧게.** 연결 3초, 응답 5초 수준이 무난하다. 이유는 느린 수신사 하나가 워커를 오래 붙잡아 처리량을 갉아먹는 것을 막기 위해서다. 어차피 우리는 재시도를 하므로, 오래 기다려서 성공률을 조금 높이는 것보다 빨리 포기하고 나중에 다시 보내는 편이 전체 처리량에 유리하다.

**4xx와 5xx는 다르게 다룬다.** 재시도의 전제는 "지금은 실패했지만 나중엔 될 수도 있다"인데, 이 전제가 성립하지 않는 실패가 있다.

- **5xx, 타임아웃, 연결 실패**: 상대의 일시적 문제일 가능성이 높다. 재시도한다.
- **400, 401, 403, 404**: 잘못된 URL, 시크릿 불일치, 페이로드 형식 오류 같은 **설정 문제**일 가능성이 높다. 백 번 재시도해도 똑같이 실패한다. 빠르게 데드레터로 보내고 수신사에 알리는 편이 낫다.
- **429 (Too Many Requests)**: 상대가 "너무 빠르다"고 말하는 것이므로 재시도하되, `Retry-After` 헤더가 있으면 그 값을 존중해 대기 시간을 늘린다.
- **410 (Gone)**: "이 엔드포인트는 폐기됐다"는 뜻으로 해석해 등록 자체를 비활성화하는 관례가 있다. 사라진 주소로 며칠간 재시도하는 낭비를 막는다.

**데드레터(dead letter).** 우편에서 온 말로, 수취인 불명이라 배달도 반송도 못 하는 편지를 모아두는 곳을 뜻한다. 여기서는 최대 횟수를 소진한 이벤트를 `DEAD` 상태로 옮겨 재시도를 멈추는 것이다.

무한 재시도를 하지 않는 이유는 명확하다. 영원히 안 될 것에 자원을 쓰면 큐가 계속 부풀고, 진짜 처리해야 할 이벤트가 밀린다. 대신 **DEAD로 옮기는 순간 반드시 사람에게 알려야 한다.** 조용히 버리면 그건 유실과 다를 게 없다.

### 2-4. 수신사별 격리 — 한 집 장애가 온 동네를 못 막게

1-4절에서 본 head-of-line blocking을 실제로 어떻게 막는지 보자. 그림으로 먼저.

```
[ 단일 큐 — 한 줄로 서 있다 ]

  큐 앞 ────────────────────────────────────────> 큐 뒤
  [A재시도][A재시도][A재시도] ... [A재시도][B신규][C신규]
   └────── 수신사 A 장애로 쌓인 수십만 건 ──────┘  └─ 대기 ─┘

  B, C는 아무 문제가 없는데 A 때문에 최대 몇 시간 지연된다.

[ 수신사별 레인 — 줄을 나눈다 ]

  A 레인:  [A][A][A][A][A] ...    ← A만 쌓인다.
                                    그리고 7회 실패하면 DEAD로 빠져
                                    이 레인도 언젠가 비워진다.
  B 레인:  [B]                    ← 즉시 발송
  C 레인:  [C]                    ← 즉시 발송

  A의 장애가 A의 레인 안에 갇힌다. 이것이 격리(bulkhead)다.
```

마지막 줄의 **격벽(bulkhead)** 은 배에서 온 비유다. 선체 안을 여러 칸으로 나눠두면 한 칸에 물이 차도 배 전체가 가라앉지 않는다. 자원을 미리 나눠두어 한쪽의 고갈이 다른 쪽으로 번지지 않게 하는 설계를 그렇게 부른다.

구체적인 격리 수단은 세 가지다.

**수신사별 큐 또는 파티션.** 앞의 outbox 스키마처럼 `receiver_id`를 기준으로 워커를 나누거나, 메시지 큐를 쓴다면 수신사를 파티션 키로 삼는다. 수신사 수가 많아 워커를 일대일로 둘 수 없다면, 최소한 **동시 발송 슬롯에 수신사별 상한**을 둔다(예: 수신사당 동시 10건). 그러면 한 수신사가 전체 워커 풀을 삼키지 못한다.

**수신사별 서킷 브레이커(circuit breaker).** 전기 회로의 차단기에서 온 이름이다. 과전류가 흐르면 차단기가 스스로 내려가 회로를 끊듯, 특정 수신사로의 연속 실패가 임계치를 넘으면 그쪽 발송을 잠시 완전히 끊는다(**open** 상태). 일정 시간 뒤 소수의 요청만 흘려보내 회복됐는지 확인하고(**half-open**), 성공하면 다시 연다(**closed**).

굳이 이게 필요한 이유는 타임아웃 비용 때문이다. 죽은 서버에 5초씩 타임아웃을 태우면 워커 하나가 1분에 12건밖에 처리하지 못한다. 서킷이 열려 있으면 그 시도 자체를 건너뛰므로 워커가 낭비되지 않는다.

**모니터링 분리.** 발송 성공률과 지연을 반드시 **수신사별로** 집계한다. 전체 성공률만 보면 "99%"라 정상으로 보이지만, 실제로는 수신사 30곳 중 한 곳이 0%인 상황일 수 있다. 그 한 곳에게는 100% 장애다.

### 2-5. 순서 보장의 한계 — 못 지키는 약속은 하지 않는다

재시도와 병렬 발송이 있는 한 도착 순서 보장은 사실상 불가능하다. 승인 이벤트가 재시도 대기 중일 때 취소 이벤트가 한 번에 성공하면 순서가 뒤집힌다. 이건 버그가 아니라 재시도 메커니즘의 필연적 결과다.

그럼 어떻게 해야 하나. 선택지는 셋이다.

- (a) **순서를 보장한다고 문서에 쓴다**: 지킬 수 없는 약속이다. 수신사가 그 약속을 믿고 순서 검증 없이 구현하면, 뒤집힘이 발생했을 때 사고의 원인이 우리 문서가 된다. 최악의 선택.
- (b) **아무 말도 안 한다**: 수신사가 "당연히 순서대로 오겠지"라고 가정하고 구현한다. 결과는 (a)와 같고, 발견이 더 늦어진다.
- (c) **보장하지 않는다고 명시하고, 판단 근거를 실어준다**: 정직하고, 수신사가 올바르게 방어할 수 있다.

정답은 (c)다. 구체적으로는 세 가지를 한다. 연동 문서에 "이벤트 도착 순서는 보장되지 않습니다"를 명시하고, 페이로드에 `occurred_at`과 `sequence_no`를 실어주고, 수신측 가이드에 "상태 머신으로 전이를 검증하고 페이로드 대신 조회 API로 최종 상태를 확정하라"를 적어준다.

즉 [수신측 문항](./03-webhook-reception-handling.md)에서 다룬 방어책을 **발신자가 문서로 가르쳐주는** 셈이다. 파트너사 개발자가 그 문서를 읽고 올바르게 구현하는 것까지가 우리 설계 범위라는 시각이 이 문항의 핵심이다.

### 2-6. 운영 도구 — 실패 이벤트 재발송 콘솔

데드레터에 들어간 이벤트는 결국 사람이 처리한다. 그리고 이 일은 예외적 상황이 아니라 **연동 운영의 일상**이다. 수신사가 "저희 어제 오후 2시부터 4시까지 장애였는데 그 시간대 웹훅 다시 쏴주실 수 있나요"라고 요청하는 일은 정기적으로 생긴다.

콘솔이 없으면 그때마다 개발자가 운영 DB에 직접 `UPDATE webhook_outbox SET status = 'PENDING'`을 날리게 된다. 조건절 하나 잘못 쓰면 전 수신사에 수십만 건이 재발송되는 사고가 난다. 그래서 콘솔은 편의 기능이 아니라 안전장치다.

최소 요건은 이렇다.

- **검색**: 수신사, 기간, 이벤트 타입, 상태로 필터링.
- **상세 조회**: 페이로드 원문과 발송 이력(각 시도의 시각, 응답 코드, 응답 본문 일부).
- **재발송**: 선택한 건 또는 기간 단위 일괄 재발송. 실행 전에 대상 건수를 보여주고 확인을 받아야 한다.
- **동일 이벤트 ID 유지**: 재발송할 때도 원래 이벤트 ID를 그대로 쓴다. 새 ID를 발급하면 수신사가 이미 처리한 건까지 다시 처리해버린다.
- **감사 로그**: 누가 언제 무엇을 재발송했는지 기록.

## 3. 실무 사례 — 발신 설계 부재가 만드는 장애

### 사례 1: 동기 발송이 결제 API 전체를 멈추다

웹훅 발송을 결제 승인 트랜잭션 안에서 동기 호출로 구현한 팀이 있었다. 평소에는 수신사들이 100ms 안에 응답했고, 아무 문제가 없어 보였다.

어느 저녁 대형 수신사 한 곳이 배포에 실패해 응답을 30초씩 물기 시작했다. 결제 스레드들이 하나씩 발송 대기에 묶였다. 톰캣 스레드 풀이 먼저 차고, 각 스레드가 트랜잭션을 열어둔 채였으므로 DB 커넥션 풀도 함께 고갈됐다.

그 결과 **그 수신사와 아무 관계도 없는 모든 가맹점의 결제**가 8분간 실패했다. 분당 결제액 기준으로 수천만원 규모의 기회 손실이었다.

outbox + 비동기 디스패처였다면 결제는 정상 처리되고 해당 수신사의 웹훅만 지연됐을 일이다. 여기서 배울 점은 "외부 호출을 트랜잭션 안에 넣지 마라"라는 규칙 자체보다, **그 규칙이 왜 있는지** — 동기 호출은 남의 응답 시간을 내 자원 점유 시간으로 번역하는 장치라는 것 — 이다.

### 사례 2: 단일 큐 + 무한 재시도 — 한 수신사가 큐를 점령

발송을 단일 큐 + 고정 간격(1분) 재시도로 운영하던 플랫폼이 있었다. 수신사가 늘어나는 동안에도 이 구조를 바꾸지 않았다.

수신사 A가 반나절 정기 점검에 들어갔다. A로 갈 이벤트가 실패하고, 1분 뒤 큐에 다시 실리고, 또 실패하고를 반복했다. 재적재가 신규 유입보다 빨라지면서 큐 깊이가 수십만 건으로 불었다.

그 뒤에 서 있던 다른 수신사들의 승인 웹훅이 최대 4시간 지연됐다. 그중 수신사 B는 웹훅을 받아 출고를 트리거하는 구조였는데, 당일 출고 마감 시각을 넘겨 배상 이슈로 번졌다. 자기 시스템은 멀쩡했는데 남의 장애 때문에 손해를 본 것이다.

수신사별 파티션 + 지수 백오프 + 데드레터였다면 세 겹으로 막혔다. A의 물량은 A의 레인 안에만 쌓이고(파티션), 시도 횟수는 반나절에 6회 이하로 줄고(백오프), 7회 실패 후에는 DEAD로 빠져 큐에서 사라졌을 것이다(데드레터).

### 사례 3: 시크릿 일괄 교체 — 모든 수신사의 검증이 깨지다

보안 점검에서 "웹훅 시크릿을 교체하라"는 지시가 내려왔다. 키 ID 체계가 없던 팀은 시크릿을 새로 만들어 일괄 교체하고, 수신사들에게 "새 시크릿으로 바꿔주세요"라고 공지했다.

문제는 교체가 원자적으로 일어날 수 없다는 것이다. 우리는 배포 즉시 새 시크릿으로 서명하기 시작했지만, 수신사들은 각자의 일정에 따라 며칠에 걸쳐 반영했다. 그 사이에 나간 웹훅은 전 수신사에서 서명 불일치로 401이 났다.

401은 4xx라 우리 재시도 정책상 "설정 오류"로 분류돼 빠르게 데드레터로 빠졌다. 결국 며칠간 발생한 이벤트 상당수가 DEAD 상태로 쌓였고, 수신사별 반영 시점을 확인해가며 수동으로 재발송해야 했다.

키 ID 헤더와 "신·구 시크릿 동시 유효 기간"을 애초에 계약에 넣어뒀다면, 수신사가 각자 일정으로 갈아타는 동안 발송은 한 건도 깨지지 않았을 것이다. **시크릿 교체는 언젠가 반드시 하게 되는 일이므로, 처음부터 교체 가능한 구조로 만들어야 한다**는 것이 교훈이다.

## 4. 꼬리질문 대비 포인트

### "outbox 대신 트랜잭션 커밋 후 바로 발송하면 안 되나요?"

"커밋 후 발송"(예: `@TransactionalEventListener(AFTER_COMMIT)`에서 HTTP 호출)은 절반만 맞는 답이다. 유령 이벤트는 막지만 **유실은 못 막는다.**

커밋 직후, 발송 코드가 실행되기 전에 프로세스가 죽으면 그 이벤트는 어디에도 기록이 없다. 재시도할 근거 자체가 없는 것이다. 배포 중 인스턴스 종료처럼 흔한 상황에서 조용히 사라진다.

outbox는 **"발송해야 한다는 사실" 자체를 커밋에 포함시킨다.** 그래서 크래시가 나도 다른 프로세스의 디스패처가 이어서 보낸다.

대신 정직하게 한계도 말해야 한다. 디스패처가 발송 성공 직후 상태 갱신 전에 죽으면 중복 발송이 되므로, 전달 보장은 at-least-once다. **"정확히 한 번은 못 주니, 최소 한 번 + 중복 제거 재료(이벤트 ID)를 준다"** 로 정리하면 답이 닫힌다.

### "재시도 간격과 횟수는 어떻게 정하나요?"

**수신측 장애의 지속 시간 분포에 맞춘다**가 원칙이다. 배포 실수나 재시작은 수 분, 정기 점검이나 인프라 장애는 수 시간 단위다. 그래서 앞은 촘촘히(1분, 5분), 뒤는 성기게(30분, 2시간, 6시간) 잡는 지수 백오프가 표준이고, 여기에 지터를 더해 복구 직후 재시도가 몰리는 것을 막는다.

총 재시도 창(마지막 시도까지의 누적 시간)은 다른 기준으로 정한다 — **"이 이벤트가 N시간 늦게 도착해도 비즈니스가 성립하는가."**

예를 들어 웹훅이 출고를 트리거하는 용도라면 24시간 넘게 끌 이유가 없다. 그 시점엔 이미 배송 약속을 어겼으므로, 자동 재시도보다 사람이 개입해 처리하는 편이 낫다. 반대로 정산 데이터 통지처럼 하루 이틀 늦어도 무방한 이벤트는 재시도 창을 길게 잡아도 된다.

즉 **간격은 기술적 근거로, 총 창 길이는 비즈니스 근거로 정한다**고 답하면 좋다. 그 뒤는 데드레터 + 알림 + 콘솔 재발송으로 넘긴다.

### "수신사가 200을 주고도 처리에 실패했다면 발신자 책임인가요?"

전달 보장의 경계를 묻는 질문이다. 발신자의 계약은 **"2xx 응답을 받을 때까지 최소 1회 전달"** 이고, 200 이후의 처리 실패는 수신측 책임 영역이다.

다만 여기서 끝내면 반쪽이다. 성숙한 발신자는 두 가지를 더 한다.

첫째, 경계를 문서로 명확히 한다 — **"200은 수신 확인이지 처리 완료가 아닙니다"** 를 연동 가이드에 쓴다. 이게 없으면 수신사가 "우리 200 줬는데 왜 데이터가 없냐"고 물어올 때 대화가 시작되지 않는다.

둘째, 수신측이 스스로 복구할 수단을 제공한다. 기간을 지정한 재발송 API나, 이벤트 목록 조회 API가 그것이다. 그러면 수신사가 자기 장애를 스스로 메울 수 있고, 우리 운영팀에 요청이 오지 않는다.

**경계는 긋되 복구 수단은 제공한다**는 두 축으로 답하면 된다.

### "순서 보장을 요구하는 수신사가 있으면 어떻게 하나요?" (시니어 변별 포인트)

단칼에 "불가능합니다"라고 하지 말고 트레이드오프를 제시한다.

**기본 답**은 "보장하지 않음 + 시퀀스 제공 + 수신측 상태 머신 가이드"다. 처리량과 격리를 지키는 선택이며, 대부분의 수신사는 상태 머신 검증만 제대로 하면 순서 보장이 필요 없다는 것을 설명하면 납득한다.

**정말 필요한 경우**를 위해서는 **리소스(거래) 단위 직렬 발송**을 옵션으로 제공할 수 있다. 같은 `resource_key`를 가진 이벤트는 앞 건이 `DELIVERED`가 되기 전에 다음 건을 보내지 않는 방식이다.

이때 대가를 정확히 말하는 것이 변별 포인트다.

- 한 이벤트의 실패가 **그 거래의 후속 이벤트를 전부 막는다.** 승인 이벤트가 재시도 중이면 취소 이벤트도 대기한다.
- 앞 건이 데드레터로 빠지면 결정을 해야 한다 — 후속 이벤트를 영원히 막을 것인가, 아니면 건너뛰고 보낼 것인가. 후자를 택하는 순간 순서 보장이라는 약속 자체가 깨진다.
- 발송 병렬도가 리소스 단위로 제한되므로 처리량이 떨어진다.

그리고 두 가지를 못 박는다. **전역 순서는 불가능하고 리소스 내 순서만 가능하다**는 것, 그리고 **순서 보장은 가용성·처리량과 교환된다**는 것. 이 둘을 짚으면 파트너 연동을 실제로 운영해본 티가 난다.

### "outbox 테이블이 계속 커지는데 어떻게 관리하나요?"

핵심 인식은 **`DELIVERED`와 `DEAD` 상태의 행은 더 이상 큐가 아니라 이력이라는 것**이다. 발송 대상 조회는 이 행들을 볼 필요가 없다.

그래서 두 방향으로 관리한다.

첫째, **조회가 미결 건만 보게 한다.** 앞의 스키마처럼 `WHERE status IN ('PENDING','SENDING')` 조건이 붙은 부분 인덱스(partial index)를 쓰면, 테이블에 수억 건이 쌓여도 인덱스에는 미결 건만 들어 있어 폴링 쿼리가 느려지지 않는다.

둘째, **완료 건을 물리적으로 치운다.** N일 보관 후 아카이브 테이블로 옮기거나, `occurred_at` 기준 범위 파티셔닝을 걸어두고 오래된 파티션을 통째로 드롭한다. PostgreSQL에서 대량 DELETE는 죽은 튜플을 남겨 VACUUM 부담과 테이블 팽창(bloat)을 만들지만, 파티션 드롭은 파일 단위 제거라 그런 비용이 없다.

**"큐로 쓰는 테이블은 인덱스가 미결 건만 보게 하라"** 가 요지다.

### "이벤트 페이로드에 어디까지 담아야 하나요?" (시니어 변별 포인트)

이건 웹훅 발신 설계에서 자주 놓치는 축인데, 선택지가 둘이다.

- **전체 상태를 담는다(state transfer)**: 결제 금액, 상태, 고객 정보까지 전부 페이로드에 넣는다. 수신측이 추가 조회 없이 바로 처리할 수 있어 편하다.
- **식별자와 이벤트 종류만 담는다(notification only)**: "결제 pay_123이 승인됐다"만 보내고, 상세는 수신측이 조회 API로 가져가게 한다.

전자의 문제는 세 가지다. (1) 페이로드가 커지고 스키마 변경 시 모든 수신사가 영향받는다. (2) 재시도로 6시간 뒤에 도착한 페이로드는 **그 시점의 오래된 값**이라, 수신측이 그대로 반영하면 최신 상태를 덮어쓴다. (3) 개인정보나 민감 정보가 로그·프록시를 거쳐 유통된다.

후자의 문제는 수신측 조회 API 호출이 늘어난다는 것이다. 이벤트 폭주 시 조회 API가 병목이 된다.

실무의 절충은 **"판단에 필요한 최소 정보 + 조회를 위한 키"** 다. 이벤트 타입, 리소스 키, 발생 시각, 시퀀스, 그리고 수신측이 "이 이벤트를 처리할지 말지" 판단할 정도의 요약 필드만 담고, 금액·상태 같은 확정값은 조회 API로 가져가게 한다. 이게 수신측 문항의 **"웹훅은 초인종, 진실은 조회 API"** 와 정확히 짝을 이룬다.

한 문장으로 말하면 — **페이로드에 무엇을 담을지는 발신자 편의가 아니라 "수신측이 뒤늦게 도착한 이벤트를 안전하게 처리할 수 있는가"로 정한다.** 여기까지 말하면 발신과 수신을 한 시스템으로 보고 있다는 게 드러난다.

## 한 줄 요약

웹훅 발신은 비즈니스 트랜잭션과 원자적으로 outbox에 기록한 뒤 비동기 디스패처가 지수 백오프·데드레터로 재시도하는 배달 시스템으로 만들고, 재시도는 곧 수신측 중복이므로 이벤트 ID·발생 시각·시퀀스·HMAC 서명(키 ID로 로테이션 지원)을 실어 수신측이 검증·중복 제거·역전 판단을 할 수 있게 하며 — 수신사별 큐·서킷 브레이커로 한 곳의 장애를 격리하고, 순서 비보장은 문서로 계약하고, 재발송 콘솔로 운영을 마감해야 파트너 연동이 성립한다.
