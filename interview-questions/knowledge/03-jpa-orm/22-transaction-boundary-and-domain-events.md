# 트랜잭션 경계와 도메인 이벤트 — "한 트랜잭션에 Aggregate 하나"는 성능 규칙이 아니라 정합성 규칙이다

> 핵심 관전 포인트: **`@Transactional` 한 줄은 네 개의 경계를 동시에 긋는다 — 정합성 경계 = 락 경합 범위 = 실패 파급 범위 = 커넥션 점유 시간.** 넷이 같은 선인 이유는 물리적이다: 락은 커밋·롤백 시점에만 풀리고, 커넥션은 트랜잭션이 끝나야 반납되며, 롤백은 트랜잭션 전체를 되돌리기 때문이다. 애그리거트를 하나 더 넣는 것은 이 넷을 한꺼번에 키우는 결정이고, DDD의 "트랜잭션 하나에 애그리거트 하나" 원칙의 근거가 바로 이것이다. 그래서 이 코드에서 가장 위험한 것은 **쿼리가 몇 개 나가느냐가 아니라 메일 API 응답을 기다리는 동안 재고 행의 배타 락을 쥐고 있다는 사실**이다(명시적 락이 없어도 **`UPDATE` 문 자체가 커밋까지 배타 락을 유지**한다). 무엇을 남기고 뺄지는 성능이 아니라 **정합성 요구 수준**이 정한다 — **① 트랜잭션 안에 블로킹 I/O가 있는가 ② 이게 실패하면 주문 자체를 취소해야 하는가.** 재고는 남기고 포인트·쿠폰·메일은 이벤트로 뺀다. 블로킹 I/O가 하나도 없어도 큰 트랜잭션은 **락 순서 역전으로 데드락**을 만들며, 처방은 **자원 획득 순서를 전역으로 고정하는 것**(Hibernate가 안 지켜주므로 코드로 고정)이다. 마지막으로 **분리는 공짜가 아니다** — 즉시 일관성, 추적 가능성, 보상 로직 비용을 내주고 사는 것이며, 그 대가를 갚는 장치가 **Outbox + 재처리 + 멱등성** 세트다.

## 0. 질문 + 의도

**질문**: "하나의 트랜잭션에서 여러 Aggregate를 수정하면 왜 문제가 되나요? 도메인 이벤트 기반으로 어떻게 분리하나요?"

제시된 코드는 이것 하나로 고정한다. 이 문서 끝까지 같은 무대를 쓴다.

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional
    public void completeOrder(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();

        order.complete();                                    // ① 주문 상태 변경
        stockService.decrease(order.getItems());             // ② 재고 차감
        pointService.accumulate(order.getUserId(), order.getAmount());  // ③ 포인트 적립
        couponService.use(order.getCouponId());              // ④ 쿠폰 사용 처리
        notificationService.sendCompleteMail(order);         // ⑤ 완료 메일 발송 (외부 API)
    }
}
```

**출제 의도**: rationale은 이렇게 적고 있다 — "**트랜잭션 경계 = 정합성 경계 = 락 경합 범위라는 연결을 이해하는지. 큰 트랜잭션이 데드락과 경합의 온상임을 알고 도메인 이벤트로 쪼개는 설계는, 모놀리스에서 MSA로 가는 사고의 전 단계다.**" 즉 이 문항은 스프링 이벤트 API 사용법을 묻는 자리가 아니다. **① `@Transactional`이라는 한 줄이 실제로 무엇을 결정하는지 ② 무엇을 남기고 무엇을 뺄지 판단하는 기준을 갖고 있는지 ③ 쪼갠 뒤에 새로 생기는 문제(유실·중복·순서·추적)를 알고 그 값을 치를 준비가 되어 있는지** — 이 셋을 본다.

**함정 세 개**:

- **성능 문제부터 답하는 것.** "`getItems()`에서 N+1이 날 수 있습니다"는 사실일 수 있지만, **fetch join 한 줄로 끝나는 국소 문제**다. 반면 메일 API가 트랜잭션 안에 있는 것은 **장애 하나가 서비스 전체를 마비시키는 구조 문제**다. 열린 질문에서 국소 문제를 먼저 꺼내면 "코드는 읽지만 구조는 안 보는 사람"으로 읽힌다(§1-1).
- **"무조건 쪼개야 합니다"로 답하는 것.** 교과서 답이지만 실무 감각이 없어 보인다. 모놀리스에서 이벤트로 쪼개는 순간 **추적이 어려워지고 보상 로직이 생긴다.** 얻는 것과 포기하는 것을 같은 호흡에 말해야 한다(§3-9).
- **`@Async`로 빼는 것.** 가장 흔한 오답이고, **트랜잭션이 롤백돼도 메일은 이미 나간다.** 커밋 이후로 옮기는 것과 비동기로 미루는 것은 전혀 다른 이야기다(§2-5).

**DB는 PostgreSQL을 기준으로 쓴다.** 락·데드락·타임아웃은 벤더마다 기본값과 진단 도구가 다른 영역이라, MySQL 이야기를 할 때는 그렇게 명시한다.

## 1. 문제를 보는 틀 — 열린 질문을 훑는 순서와 네 개의 경계

### 1-1. 열린 질문을 받았을 때 훑는 순서 — 구조 → 경계 → 성능

"이 구조의 문제는?"은 **답의 범위를 면접자가 정하라는 질문**이다. 이때 가장 최근에 공부한 주제(대개 성능)로 먼저 뛰어드는 것이 전형적인 실수다. 순서를 고정해두면 흔들리지 않는다.

> **큰 것부터 훑는 3단 스캔**
> **① 구조** — 이 메서드가 건드리는 것이 몇 개의 **다른 도메인**인가? 그중 **되돌릴 수 없는 것**(메일, 결제, 외부 시스템)이 있는가?
> **② 경계** — 트랜잭션이 언제 열리고 언제 닫히는가? 그 안에 **DB 밖 자원**이 들어와 있는가? 락은 언제부터 언제까지 잡히는가?
> **③ 성능** — 그다음에야 쿼리 수, N+1, 인덱스.

이 순서를 이 코드에 대보면 답이 저절로 나온다.

```text
① 구조 : Order / Stock / Point / Coupon / Mail  → 서로 다른 애그리거트 5개.
         그중 ⑤ 메일은 "발송 취소"가 없는 비가역 작업이다.  ← 여기서 이미 걸린다
② 경계 : ①~⑤ 전부가 하나의 @Transactional 안.
         메일 API 응답을 기다리는 동안 ②의 재고 행 배타 락이 그대로 유지된다. ← 최대 위험
③ 성능 : order.getItems() 지연 로딩 → N+1 가능.  ← 사실이지만 fetch join 한 줄로 끝난다
```

**가장 위험한 것은 쿼리 수가 아니라, 메일 API가 트랜잭션 안에 있다는 사실이다.** 메일 서버가 느려져 응답이 3초 걸리는 날, 이 코드는 **재고 행 락과 DB 커넥션을 3초씩 붙잡는다.** 주문이 초당 수백 건이면 커넥션 풀은 몇 초 만에 고갈되고, **재고와 아무 상관 없는 로그인 API까지 함께 죽는다.** 메일 서버 장애가 주문 서비스 장애가 아니라 **전사 장애**로 번지는 경로다.

면접에서 첫 문장으로 말할 형태는 이것이다.

> "**문제를 세 층으로 보겠습니다. 가장 큰 문제는 서로 다른 애그리거트 다섯 개가 한 트랜잭션에 묶여 있다는 것이고, 그중에서도 치명적인 것은 외부 메일 API가 트랜잭션 안에 있다는 점입니다.** 메일 응답을 기다리는 동안 재고 행의 배타 락과 DB 커넥션을 계속 쥐고 있어서, **메일 서버가 느려지면 그 지연이 그대로 락 대기와 커넥션 고갈로 번집니다.** 다음 층은 실패 파급 범위입니다 — 쿠폰 처리 하나가 실패하면 이미 성공한 재고·포인트까지 전부 롤백됩니다. 성능 문제(`getItems()`의 N+1)도 있지만 그건 fetch join으로 끝나는 국소 문제라 우선순위가 가장 낮습니다."

**세 층을 순서대로 말하고, 스스로 우선순위를 매긴다.** 이것만으로 답의 질이 달라진다.

### 1-2. 전제 지식 — 애그리거트(Aggregate)가 무엇인가

질문에 나오는 "Aggregate"부터 정의하고 가야 나머지가 읽힌다.

**애그리거트(aggregate)는 "함께 변경되어야 하는 엔티티들을 하나로 묶은 덩어리"**다. 단어 자체가 "모아 놓은 것, 집합체"라는 뜻이고, 도메인 주도 설계(DDD)에서 **정합성을 지키는 최소 단위**로 쓴다. 각 덩어리에는 대표 엔티티가 하나 있는데 이것을 **애그리거트 루트(root)**라고 부르고, 바깥에서는 항상 루트를 통해서만 안쪽 엔티티를 만진다.

이 코드에 대보면 이렇게 갈린다.

```text
[Order 애그리거트]        [Stock 애그리거트]   [Point 애그리거트]   [Coupon 애그리거트]
  루트: Order                루트: Stock          루트: Point          루트: Coupon
   ├ OrderItem
   └ ShippingAddress

  ↑ 루트를 통해서만 만진다        ↑ 서로 다른 덩어리는 서로의 내부를 직접 만지지 않는다
```

**경계를 어디에 그을지 정하는 기준은 하나다** — **"이 둘은 항상 같은 순간에 서로 맞아떨어져야 하는가?"** 주문의 총액과 주문항목 금액의 합계는 **단 한 순간도 어긋나면 안 되므로** 같은 덩어리다. 반면 주문과 포인트 잔액은 **몇 초 늦게 맞아도 업무적으로 아무 문제가 없으므로** 다른 덩어리다.

> 비유하자면 **서류철**이다. 한 서류철 안의 장들은 항상 앞뒤가 맞아야 하니 함께 결재를 받는다. 다른 서류철은 오늘 결재하고 내일 맞춰도 된다. 애그리거트 경계는 "어디까지를 한 서류철로 묶어 함께 결재할 것인가"를 정하는 선이다.

### 1-3. 척추 — 트랜잭션 경계는 네 개의 경계를 동시에 긋는다

`@Transactional` 한 줄은 "여기부터 여기까지가 하나의 원자 단위"라는 선언처럼 보인다. 그런데 그 선 하나가 실제로는 **네 개의 서로 다른 경계를 동시에** 긋는다. 이 문항의 모든 답이 여기서 파생된다.

```text
        @Transactional  ────────────────────────────────────────┐
        │                                                       │
        ├─ ① 정합성 경계   : 전부 성공하거나 전부 실패하는 범위       │
        ├─ ② 락 경합 범위   : 이 안에서 만진 행은 커밋까지 잠긴다      │
        ├─ ③ 실패 파급 범위 : 여기 있는 것 중 하나가 죽으면 전부 죽는다 │
        └─ ④ 커넥션 점유 시간: 시작~끝 동안 커넥션 1개를 독점한다     │
        ────────────────────────────────────────────────────────┘
```

**애그리거트를 하나 더 넣는다는 것은 네 개를 동시에 키운다는 뜻이다.** "관련 있으니까 같이 처리하자"는 판단이 실제로는 **락 범위와 장애 반경을 함께 늘리는 결정**인데, 코드에서는 그 사실이 전혀 보이지 않는다는 게 이 함정의 본질이다.

아래 네 소절에서 하나씩 뜯어보고, §1-9에서 **왜 이 넷이 결국 같은 선인지**를 정리한다.

### 1-4. ① 정합성 경계 — 유일하게 원해서 그은 선

유일하게 **내가 원해서 그은** 경계다. **정합성(consistency)은 여기서 "여러 데이터가 서로 모순되지 않는 상태"를 뜻한다.** "주문 완료와 재고 차감은 함께 성립하거나 함께 실패해야 한다"는 요구가 있으면 둘을 한 트랜잭션에 넣는다. 그래야 "주문은 완료됐는데 재고는 그대로"라는 모순된 상태가 **어느 순간에도 존재하지 않는다.**

`@Transactional`을 붙일 때 개발자가 머릿속에 그리는 것은 대개 이 경계 하나뿐이다. 문제는 나머지 셋이 **요청하지도 않았는데 덤으로 따라온다**는 것이다.

### 1-5. ② 락 경합 범위 — 명시적 락이 없어도 락은 잡힌다

여기가 이 문항에서 가장 자주 흔들리는 지점이다. 코드 어디에도 `@Lock`이나 `select ... for update`가 없으니 "락은 안 잡혀 있다"고 생각하기 쉽다. **틀렸다.**

먼저 용어. **배타 락(exclusive lock)은 "내가 이 행을 쥐고 있는 동안 다른 누구도 이 행을 바꿀 수 없다"는 표시**다. 배타적이라는 이름 그대로, 같은 행에 대해 동시에 하나만 존재할 수 있다.

> **`UPDATE` 문이 실행되는 순간, 그 행에는 배타 락이 걸리고 커밋 또는 롤백까지 유지된다.** 이건 애플리케이션이 하는 일이 아니라 **DB가 하는 일**이고, PostgreSQL도 MySQL(InnoDB)도 마찬가지다. `select ... for update`는 그 락을 **SELECT 시점에 미리 앞당겨 잡는 것**일 뿐, 없다고 락이 없는 게 아니다.

왜 그래야 하는지 생각해보면 당연하다. 락을 커밋까지 안 잡으면 **아직 커밋되지 않은 값을 다른 트랜잭션이 덮어쓸 수 있고**, 그러면 롤백했을 때 무엇으로 되돌려야 하는지 알 수 없다. **커밋 전까지 락을 유지하는 것은 롤백 가능성을 지키기 위한 필연**이다.

이 사실의 실무적 귀결이 이것이다.

```text
UPDATE 가 나간 시각 ────────────────────────────▶ COMMIT
                    이 전 구간 내내 그 행은 잠겨 있다
                    = 커밋이 늦어질수록 락도 그만큼 길어진다
                    = 트랜잭션 끝에 무엇을 매달아 두었느냐가 락 시간을 결정한다
```

그래서 **"트랜잭션 끝에 메일 API를 매달아 둔다"는 것은 "재고 행 락 시간에 메일 API 응답 시간을 더한다"는 것과 같은 말**이다. 잠깐 더 정확히 하면, JPA에서는 `UPDATE`가 나가는 시점이 **코드에서 setter를 호출한 순간이 아니라 flush 시점**이므로 실제 락 구간은 조금 더 짧을 수 있다. 하지만 **flush 이후 커밋까지의 구간은 여전히 통째로 락 구간**이고, 지연 로딩이나 JPQL 조회가 중간에 끼면 auto-flush로 락이 더 일찍 잡히기도 한다([flush 시점과 SQL 실행 순서](15-flush-timing-and-sql-ordering.md)). **트랜잭션을 짧게 만드는 것 외에 이 구간을 줄이는 방법은 없다.**

### 1-6. 락 점유 타임라인 — 메일을 기다리는 동안 다른 요청은 무엇을 하는가

말로만 하면 "락이 좀 길다" 정도로 들린다. **같은 상품을 사는 다른 주문이 그 구간에 들어오면 무슨 일이 벌어지는지**를 그려야 위험이 보인다.

```text
T1: 주문 A 완료 (원본 코드)                       T2: 같은 상품(id=77)을 사는 주문 B
────────────────────────────────────────────────────────────────────────────────
t0  BEGIN
t1  UPDATE stock SET qty=qty-1 WHERE id=77
      └ 77번 행 배타 락 획득 ───────────────┐
t2  UPDATE point ...                        │
t3  UPDATE coupon ...                       │ 락
t4  메일 API 호출 ─┐                        │ 보유    t4  BEGIN
t5      응답 대기  │  (3초)                 │ 구간    t5  UPDATE stock ... WHERE id=77
t6      응답 대기  │                        │              └ 락을 못 얻는다 → 대기 시작
t7      응답 대기  │                        │         t6      대기 (커넥션 1개 점유한 채)
t8      응답 도착 ─┘                        │         t7      대기
t9  COMMIT ────────────────────────────────┘         t8      대기
      락 해제                                        t9  락 획득 → 여기서야 진행
```

**주문 B가 하는 일은 "아무것도 안 하면서 커넥션 하나를 붙잡고 기다리는 것"**이다. 주문이 초당 수백 건이고 인기 상품이 하나 있으면, 그 상품을 사려는 요청이 전부 이 대기열에 쌓인다. **커넥션 풀은 이렇게 마른다** — 느린 쿼리 하나 없이, 슬로우 쿼리 로그에도 안 잡히면서.

**대기가 무한정 이어지지는 않는다. 대신 그 한계가 벤더마다 다르다.**

| | 락 대기 상한 | 기본값 | 초과하면 |
|---|---|---|---|
| PostgreSQL | `lock_timeout` | **0 (무한 대기)** | 기본 설정에서는 실패하지 않고 계속 기다린다 |
| MySQL (InnoDB) | `innodb_lock_wait_timeout` | 50초 | 대기 중이던 트랜잭션이 에러로 실패한다 |

**PostgreSQL의 기본값이 무한 대기라는 사실이 오히려 더 무섭다.** 실패해서 시끄럽게 알려주는 대신 **조용히 쌓이기 때문**이다. 그래서 증상이 "특정 API 에러율 증가"가 아니라 **"서비스 전체가 느려짐 → 커넥션 풀 고갈 → 전면 장애"** 순서로 나타난다. 운영 중인 서비스라면 `lock_timeout`을 유한한 값으로 설정해 **"오래 기다리면 실패하게" 만들어 두는 것**이 진단 가능성 면에서 낫다.

### 1-7. ③ 실패 파급 범위 — 성공한 것까지 되돌린다

원본 코드에서 ④ 쿠폰 사용이 실패하면 어떻게 되나? **①②③이 전부 롤백된다.** 주문 상태도, 재고 차감도, 포인트 적립도 없던 일이 된다.

여기서 물어야 할 것은 "그게 맞는 동작인가?"다. 쿠폰 적용에 실패했다고 **주문 자체를 없던 일로 만드는 것이 비즈니스적으로 옳은가?** 대개는 아니다. 쿠폰은 나중에 복구하거나 고객센터가 처리하면 되는 일인데, 지금 구조는 **"모두 함께 죽는다"는 정책을 코드가 임의로 정해버린 것**이다.

**트랜잭션 경계를 넓게 잡는 것은 "이 안에 있는 모든 것은 서로의 실패에 함께 죽는다"고 선언하는 일이다.** 그런 선언을 할 때는 그것이 진짜 요구인지 확인해야 한다.

### 1-8. ④ 커넥션 점유 시간 — 남의 API를 죽이는 경로

`@Transactional`은 시작 시점에 커넥션 풀에서 커넥션을 하나 빌리고 **끝날 때까지 반납하지 않는다.** 트랜잭션 안에서 3초짜리 메일 API를 기다린다면 **커넥션 하나를 3초 동안 아무 일도 안 시키면서 붙잡고 있는 것**이다.

**왜 중간에 반납할 수 없는지**도 같이 알아두면 좋다. 트랜잭션은 **커넥션에 묶여 있는 상태**다. `BEGIN`부터 `COMMIT`까지의 모든 문장이 같은 커넥션에서 실행돼야 하고, 커넥션을 돌려주는 순간 그 트랜잭션은 끝난다. 그러니 "잠깐 반납했다가 다시 빌린다"는 선택지가 애초에 없다.

커넥션은 **서비스 전체가 공유하는 자원**이라, 여기가 마르면 주문과 무관한 모든 API가 함께 멈춘다. 이것이 앞서 말한 "메일 서버 장애 → 전사 장애" 경로의 정확한 메커니즘이다. 같은 성질의 문제를 다른 각도에서 다룬 것이 [OSIV의 트레이드오프](09-osiv-tradeoff-and-migration.md)다 — 거기서는 "컨트롤러에서 외부 API를 호출하는 동안 놀고 있는 커넥션을 점유한다"가 문제였고, 여기서는 "서비스 안에서" 같은 일이 벌어진다.

### 1-9. 넷은 왜 같은 선인가

네 경계를 따로 설명했지만, 정말 중요한 것은 **이 넷이 왜 하나의 선으로 겹치느냐**다. 우연이 아니라 **세 가지 물리적 사실 때문**이다.

**① 락은 커밋 또는 롤백 시점에만 풀린다.** 중간에 미리 놓아줄 방법이 없다(§1-5). 그래서 **락 보유 구간의 끝 = 트랜잭션의 끝**이다.

**② 커넥션은 트랜잭션이 끝나야 반납된다.** 트랜잭션이 커넥션에 묶여 있기 때문이다(§1-8). 그래서 **커넥션 점유 구간의 끝 = 트랜잭션의 끝**이다.

**③ 롤백은 트랜잭션 전체를 되돌린다.** 부분 롤백은 없다(세이브포인트를 명시적으로 쓰지 않는 한). 그래서 **실패 파급 범위 = 트랜잭션의 범위**다.

시작점도 마찬가지다. 트랜잭션이 열리는 순간 커넥션을 빌리고, 그 안에서 첫 `UPDATE`가 나가는 순간 락이 잡히기 시작한다.

```text
      BEGIN                                                    COMMIT
        │                                                        │
  ① 정합성 경계  ├────────────────────────────────────────────────┤
  ② 락 경합 범위  ├──────(첫 UPDATE 이후)──────────────────────────┤
  ③ 실패 파급    ├────────────────────────────────────────────────┤
  ④ 커넥션 점유  ├────────────────────────────────────────────────┤
        │                                                        │
        └── 시작점이 같고 끝점이 같다 = 하나의 선을 네 이름으로 부르는 것 ──┘
```

결론은 이렇다. **`@Transactional`의 시작과 끝을 옮기면 네 개가 함께 움직인다.** "정합성만 조금 넓히고 락은 그대로 두겠다"는 선택지가 존재하지 않는다. 그래서 트랜잭션 안에 무언가를 하나 더 넣는 결정은 **언제나 네 배로 계산해야 하는 결정**이다.

### 1-10. 그래서 "한 트랜잭션에 애그리거트 하나" — 성능 규칙이 아니라 정합성 규칙

DDD가 "하나의 트랜잭션은 하나의 애그리거트만 수정한다"고 말하는 이유가 여기서 나온다. 그건 미학적 취향이 아니라 **위 네 경계를 최소로 유지하기 위한 실용적 규칙**이다.

**이 규칙이 성능 규칙이 아니라는 점을 정확히 해야 한다.** 오해는 이렇게 생긴다 — "트랜잭션을 작게 쪼개면 빨라진다더라". 그런데 실제 논리는 반대 방향이다.

- **규칙의 출발점은 "정합성이 즉시 보장되어야 하는 최소 단위는 어디까지인가"라는 질문이다.** 그 답이 애그리거트다. 주문 총액과 주문항목 합계는 한 순간도 어긋나면 안 되니 같은 트랜잭션, 주문과 포인트 잔액은 몇 초 늦어도 되니 다른 트랜잭션.
- **그 기준으로 경계를 그으면 결과적으로 트랜잭션이 작아지고, 락 경합과 장애 반경도 따라서 줄어든다.** 성능 개선은 **부산물**이지 목적이 아니다.
- **거꾸로 하면 사고가 난다.** "빠르게 하려고" 재고 차감을 주문 트랜잭션 밖으로 빼면, **재고 없이 성립한 주문**이 만들어질 수 있다. 성능을 이유로 정합성 경계를 옮기는 것은 규칙을 지키는 게 아니라 어기는 것이다.

한 문장으로: **"애그리거트 경계는 성능 예산이 정하는 것이 아니라 업무 규칙이 정한다. 성능은 그렇게 정한 경계를 지킨 결과로 따라온다."**

그리고 애그리거트 밖의 것들은 **결과적 일관성(eventual consistency)** 으로 맞춘다. 이름 그대로 **"지금 당장은 어긋나 있어도 결국에는 맞아떨어진다"는 보장**이고, 그 "결국"을 실제로 보장해 주는 장치가 §3의 Outbox와 재처리다.

면접에서는 이 한 문장이 척추가 된다.

> "**트랜잭션 경계는 정합성 경계이면서 동시에 락 경합 범위이고, 실패 파급 범위이고, 커넥션 점유 시간입니다.** 애그리거트를 하나 더 넣는 것은 이 넷을 한꺼번에 키우는 결정입니다. DDD의 '한 트랜잭션에 한 애그리거트' 원칙은 이 넷을 최소로 유지하라는 실용적 규칙이고요."

## 2. 분리 설계 — 무엇을 남기고 무엇을 뺄 것인가

"쪼개라"는 말은 쉽지만, 진짜 질문은 **어디를 자르느냐**다. 기준 두 개면 충분하고, 그 기준으로 자른 결과를 §2-4~2-7에서 세 단계로 실제 코드에 적용한다. §2-8부터는 자르는 도구인 `@TransactionalEventListener`를 정확히 쓰는 법이다.

### 2-1. 기준 ① 트랜잭션 안에 블로킹 I/O가 있는가

먼저 용어. **블로킹 I/O(blocking I/O)는 "응답이 올 때까지 그 스레드가 아무것도 못 하고 멈춰 서 있는 입출력"**이다. HTTP 호출, 파일 업로드, 다른 팀 API 호출이 전부 여기 해당한다.

**DB 밖 자원을 기다리는 작업은 무조건 트랜잭션 밖으로.** 메일·SMS·푸시·외부 결제·S3 업로드·다른 팀 API. 이유는 §1-5와 §1-8이다 — **응답 시간이 곧 락 시간이자 커넥션 점유 시간이 되고, 그 시간은 내가 통제할 수 없다.**

이 기준의 좋은 점은 **판단이 기계적**이라는 것이다. 논쟁의 여지가 없고 정적 분석으로 강제할 수도 있다(§3-10의 ArchUnit 룰).

### 2-2. 기준 ② 이게 실패하면 주문 자체를 취소해야 하는가

기준 ①만으로는 부족하다. **블로킹 I/O가 하나도 없고 전부 단순 DB 변경이어도** 여전히 남는 질문이 있다. 그때 묻는 것이 이것이다.

> **"이 작업이 실패했을 때, 방금 완료한 주문을 없던 일로 되돌려야 하는가?"**
> 답이 **예**면 같은 트랜잭션. **아니오**(나중에 보정 가능)면 이벤트로 분리.

원본 코드의 다섯 작업에 대보면 이렇게 갈린다.

| 작업 | 실패하면 주문을 취소해야 하나? | 결론 |
|---|---|---|
| ① 주문 상태 변경 | — (주문 자신) | 트랜잭션 안 |
| ② 재고 차감 | **예** — 재고 없이 성립하는 주문은 없다 | 트랜잭션 안 |
| ③ 포인트 적립 | 아니오 — 나중에 적립해주면 된다 | 이벤트 |
| ④ 쿠폰 사용 | 아니오 — 보정 가능(재사용 차단은 별도 안전장치로) | 이벤트 |
| ⑤ 메일 발송 | 아니오 — 재발송하면 된다 | 이벤트(+커밋 후) |

**여기서 핵심은 이 표를 만든 기준이 성능이 아니라는 점이다.** "재고 차감이 무겁다/가볍다"로 나눈 게 아니라 **"재고가 없으면 그 주문은 애초에 성립하지 않는다"** 는 비즈니스 규칙으로 나눴다. **경계를 정하는 것은 성능이 아니라 정합성 요구 수준이다.** §1-10에서 말한 그대로다.

### 2-3. 그리고 세 번째 질문 — "정말 쪼개야 하나?"

기준 두 개를 통과했다고 **자동으로 쪼개는 것은 아니다.** 단순 DB 변경 몇 개를 이벤트로 흩어놓으면 **한 화면에서 보이던 흐름이 리스너 여러 개로 흩어져 추적이 어려워진다.** 트래픽이 낮고 데드락 이력이 없는 관리자 기능이라면, 한 트랜잭션에 두는 편이 유지보수에 낫다는 판단도 충분히 타당하다.

**분리의 정당한 근거는 세 가지 중 하나다.** ① 트랜잭션 안에 블로킹 I/O가 있다 ② 이 작업의 실패가 주문을 되돌릴 이유가 안 된다 ③ **트래픽이 높아 락 경합·데드락이 실제로 관측된다.** 셋 중 아무것도 해당하지 않는데 "이론적으로 옳으니까" 쪼개면, **얻는 것 없이 §3-9의 비용만 지불하는 설계**가 된다.

### 2-4. 1단계 (원본) — 전부 한 트랜잭션

이제 같은 `completeOrder`를 세 번 고쳐 쓰면서 **매번 ① 코드 ② 락·커넥션 점유 타임라인 ③ 실패 파급 범위**를 같이 본다.

```java
@Transactional
public void completeOrder(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();
    stockService.decrease(order.getItems());
    pointService.accumulate(order.getUserId(), order.getAmount());
    couponService.use(order.getCouponId());
    notificationService.sendCompleteMail(order);   // 외부 API — 3초 걸릴 수도
}
```

**타임라인** (숫자는 설명용 가정이다)

```text
       ┌─ 커넥션 점유 ─────────────────────────────────────────────────────┐
BEGIN  │                                                                   │ COMMIT
  │    ├ order UPDATE  ══════════════════════════════════════════════════╗ │  │
  │    │       ├ stock UPDATE  ═══════════════════════════════════════╗  ║ │  │
  │    │       │       ├ point UPDATE  ═══════════════════════════╗   ║  ║ │  │
  │    │       │       │      ├ coupon UPDATE ═══════════════╗    ║   ║  ║ │  │
  │    │       │       │      │        ├─ 메일 API 대기 3초 ─┤    ║   ║  ║ │  │
  └────┴───────┴───────┴──────┴──────────────────────────────┴────┴───┴──┴─┘
                                                     ═══ = 배타 락 유지 구간
  총 커넥션 점유: 약 3초 + α        락을 쥔 테이블: order, stock, point, coupon 네 개
```

**실패 파급 범위**: 어느 하나라도 실패 → 전부 롤백. 단, **메일은 이미 나갔을 수도 있다**(메일 발송 후 커밋 직전 예외). 즉 **롤백이 되어도 정합성이 안 맞는 최악의 조합**까지 가능하다.

### 2-5. 2단계 — 메일만 커밋 후 이벤트로

가장 먼저 잘라야 할 것은 **비가역이면서 블로킹인 메일**이다.

**도메인 이벤트(domain event)는 "도메인에서 의미 있는 일이 일어났다는 사실을 담은 값 객체"**다. `OrderCompletedEvent`는 "주문이 완료되었다"는 과거의 사실을 나타내며, 특별한 인터페이스를 구현할 필요도 없다.

```java
// 도메인 이벤트 (그냥 값 객체다. 특별한 인터페이스 구현이 필요 없다)
public record OrderCompletedEvent(Long orderId, Long userId, int amount, Long couponId) {}
```

```java
@Transactional
public void completeOrder(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();
    stockService.decrease(order.getItems());
    pointService.accumulate(order.getUserId(), order.getAmount());
    couponService.use(order.getCouponId());

    eventPublisher.publishEvent(new OrderCompletedEvent(   // 발행만 한다. 아직 아무 일도 안 일어난다
            order.getId(), order.getUserId(), order.getAmount(), order.getCouponId()));
}
```

```java
@Component
@RequiredArgsConstructor
public class OrderMailListener {

    private final NotificationService notificationService;

    @Async                                                       // 커밋 후 + 별도 스레드
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void onOrderCompleted(OrderCompletedEvent event) {
        notificationService.sendCompleteMail(event.orderId());
    }
}
```

**타임라인**

```text
       ┌─ 커넥션 점유 ────────────────────────┐
BEGIN  │                                      │ COMMIT ─▶ (커밋 후) 메일 API 3초
  │    ├ order  ═════════════════════════════╗│           ↑ 락 없음, 커넥션 없음
  │    │   ├ stock  ══════════════════════╗  ║│
  │    │   │   ├ point  ═══════════════╗  ║  ║│
  │    │   │   │   ├ coupon ═══════╗   ║  ║  ║│
  └────┴───┴───┴───┴───────────────┴───┴──┴──┴┘
  총 커넥션 점유: 수 ms          락을 쥔 테이블: 여전히 네 개
```

**이 한 단계로 없어진 것**: 메일 API 응답 시간이 **락 구간과 커넥션 점유 구간에서 완전히 빠졌다.** 메일 서버가 아무리 느려도 DB는 영향을 받지 않는다. **가장 큰 위험이 한 번의 수정으로 제거된다.**

**여기서 `@Async`만 쓰면 왜 안 되는가** — `@Async`만 붙이면 메일은 **커밋 여부와 무관하게 즉시 다른 스레드로 나간다.** 그 직후 `couponService.use()`에서 예외가 나 트랜잭션이 롤백되면, **DB에는 아무 일도 없는데 고객에게는 "주문이 완료되었습니다" 메일이 도착한다.** 메일에는 롤백이 없다. `@TransactionalEventListener(AFTER_COMMIT)`은 **커밋이 실제로 끝난 뒤에만** 리스너를 부르므로 이 조합이 원천 차단된다. `@Async`는 그 위에 얹어 **커밋 후 처리도 호출 스레드를 막지 않게** 하는 용도다.

**남은 문제 두 개**: ① 재고·포인트·쿠폰이 여전히 한 트랜잭션이라 **락 경합과 실패 파급이 그대로다** ② `AFTER_COMMIT` 리스너가 실패하면(서버 재시작, 메일 서버 장애) **그 이벤트는 그냥 사라진다.** 커밋은 이미 끝났으니 롤백도 없고, 어디에도 기록이 남지 않는다.

### 2-6. 3단계 — 포인트·쿠폰까지 도메인 이벤트 + Outbox

§2-2의 표대로 재고만 남기고 나머지를 뺀다. 그리고 2단계에서 남은 "이벤트가 사라진다"는 문제를 **Outbox**로 막는다(§3-8).

```java
@Transactional
public void completeOrder(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();

    order.complete();                          // ① 주문 자신
    stockService.decrease(order.getItems());   // ② 실패하면 주문이 성립 불가 → 남긴다

    outbox.save(OutboxMessage.of(              // ③④⑤ → 이벤트로. 같은 트랜잭션에서 "저장만" 한다
            "OrderCompleted", order.getId(), toJson(OrderCompletedEvent.from(order))));
}   // 커밋: order + stock + outbox 세 INSERT/UPDATE 가 원자적으로 함께 확정된다
```

**타임라인**

```text
       ┌ 커넥션 ┐
BEGIN  │        │ COMMIT ─▶ 릴레이가 outbox 를 읽어 발행 ─▶ 포인트 / 쿠폰 / 메일 (각자 별도 트랜잭션)
  │    ├ order ╗│              ↑ 여기부터는 주문 트랜잭션과 완전히 무관
  │    │ ├stock║│
  │    │ ├outbox INSERT
  └────┴───────┴┘
  총 커넥션 점유: 수 ms        락을 쥔 테이블: order, stock  (+ outbox 는 자기 새 행이라 경합 없음)
```

### 2-7. 세 단계를 한 장으로

| | 락을 쥔 테이블 | 락 유지 시간 | 하나가 실패하면 | 이벤트 유실 가능성 |
|---|---|---|---|---|
| 1단계 원본 | order, stock, point, coupon | 외부 API 응답 시간에 비례 | 전부 롤백 (+메일은 이미 나감) | — |
| 2단계 메일만 분리 | order, stock, point, coupon | 수 ms | 전부 롤백 | 있음 (리스너 실패 시 소실) |
| 3단계 이벤트+Outbox | order, stock | 수 ms | 주문+재고만 롤백 | 없음 (커밋과 원자적) |

**주목할 점**: 2단계와 3단계는 **락 유지 시간이 비슷하다.** 3단계가 추가로 얻는 것은 **락을 쥐는 테이블 수(경합 지점)의 감소**와 **실패 파급 범위의 축소**, 그리고 **이벤트 유실 차단**이다. 즉 **"성능을 위해 3단계로 간다"가 아니라 "경합 지점과 장애 반경을 줄이려고 간다"** 는 것 — 다시 §2-2의 결론이다.

### 2-8. `@TransactionalEventListener` — phase 네 가지와 선택 기준

| phase | 실행 시점 | 쓰는 자리 |
|---|---|---|
| `BEFORE_COMMIT` | 커밋 직전, **아직 같은 트랜잭션 안** | 이벤트 결과도 함께 롤백되어야 할 때(파생 데이터 저장) |
| `AFTER_COMMIT` (기본) | 커밋이 확정된 뒤 | **성공했을 때만 해야 하는 일** — 메일, 알림, 외부 연동 |
| `AFTER_ROLLBACK` | 롤백된 뒤 | 실패 통계, 보상 트리거 |
| `AFTER_COMPLETION` | 성공/실패 무관하게 끝난 뒤 | 정리 작업 |

기준은 한 문장이다. **"이 작업이 원 트랜잭션과 운명을 같이해야 하나?"** — 같이해야 하면 `BEFORE_COMMIT`(사실상 같은 트랜잭션), 성공했을 때만 해야 하면 `AFTER_COMMIT`.

### 2-9. 함정 — `AFTER_COMMIT` 리스너에서 DB를 바꾸면 조용히 사라진다

이게 실무에서 가장 자주 밟는 지뢰다.

```java
// before — 조용히 반영되지 않는다
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderCompleted(OrderCompletedEvent event) {
    Point point = pointRepository.findByUserId(event.userId()).orElseThrow();
    point.accumulate(event.amount());     // 변경 감지에 기대고 있다
}   // 이 변경을 커밋해 줄 트랜잭션이 없다. 예외도 안 난다.
```

**원인**: 이름 그대로 `AFTER_COMMIT`은 **원 트랜잭션이 이미 커밋된 뒤**다. 커밋된 트랜잭션은 더 이상 무언가를 커밋해 줄 수 없다. 변경 감지가 UPDATE를 만들려면 flush가 일어나야 하고, flush를 일으키는 것은 커밋인데 **그 커밋이 이미 지나갔다.** 그래서 **예외 하나 없이 조용히 아무 일도 일어나지 않는다** — 가장 나쁜 종류의 버그다.

```java
// after — 새 트랜잭션을 명시적으로 연다
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)   // 이 한 줄이 전부다
public void onOrderCompleted(OrderCompletedEvent event) {
    Point point = pointRepository.findByUserId(event.userId()).orElseThrow();
    point.accumulate(event.amount());
}   // 새 트랜잭션이 여기서 커밋된다
```

**`REQUIRES_NEW`여야 하는 이유를 정확히 알아두자.** "그 시점에는 트랜잭션이 없으니 기본값 `REQUIRED`가 알아서 새로 열어주지 않나?"라고 생각하기 쉬운데, **그게 함정이다.**

`REQUIRED`의 의미는 **"진행 중인 트랜잭션이 있으면 거기 참여하고, 없으면 새로 연다"**이다. 그런데 `AFTER_COMMIT` 콜백이 실행되는 시점은 **커밋은 끝났지만 트랜잭션 자원(커넥션, 영속성 컨텍스트)은 아직 스레드에 묶여 있는 상태**다. 정리는 그다음 단계에서 일어난다. 그래서 `REQUIRED`는 "진행 중인 트랜잭션이 있다"고 판단해 **이미 커밋이 끝난 그 트랜잭션에 참여해 버린다.** 참여했으니 새 커밋은 일어나지 않고, **변경은 그대로 버려진다.**

스프링 문서가 이 동작을 명시적으로 경고하고 있다 — `AFTER_COMMIT`·`AFTER_ROLLBACK`·`AFTER_COMPLETION` 단계에서는 "트랜잭션은 이미 커밋되거나 롤백되었지만 **트랜잭션 자원은 여전히 살아 있고 접근 가능**하므로, 이 시점에 실행되는 데이터 접근 코드는 원 트랜잭션에 **'참여'는 하지만 변경 사항이 커밋되지는 않는다"**는 문장이다.

**`REQUIRES_NEW`는 "진행 중인 트랜잭션이 있든 없든 무조건 새로 연다"** 이므로 이 함정을 피해 간다. 대신 **커넥션을 하나 더 쓴다**는 비용은 계산에 넣어야 한다.

**그리고 여기서 실패하면 아무도 모른다.** 새 트랜잭션에서 예외가 나도 원 트랜잭션은 이미 커밋돼 끝났으므로 되돌릴 것이 없고, 리스너의 예외는 호출자에게 전파되지도 않는다(`@Async`까지 붙어 있으면 아예 다른 스레드다). **"주문은 완료됐는데 포인트만 없다"는 상태가, 기록 한 줄 없이 만들어진다.** 이 구멍이 §3-8의 Outbox가 필요한 이유로 곧장 이어진다.

> **또 하나의 함정**: `@TransactionalEventListener`는 **트랜잭션이 없는 상태에서 발행된 이벤트는 아예 받지 않는다.** 스프링 문서의 표현은 "활성 트랜잭션 안에서 발행되지 않은 이벤트는 `fallbackExecution` 플래그를 명시적으로 켜지 않는 한 폐기된다"이다. 배치나 테스트에서 트랜잭션 없이 발행하면 리스너가 조용히 안 돌고, 이때도 예외가 없다. 트랜잭션 밖 호출도 처리해야 하면 `fallbackExecution = true`를 명시한다.

### 2-10. 이벤트를 어디서 발행할 것인가

서비스에서 `publishEvent`를 직접 부르는 대신, **엔티티가 자기 상태 변화와 함께 이벤트를 등록**하게 하면 "상태가 바뀌었는데 이벤트를 안 보냈다"는 누락이 구조적으로 줄어든다. Spring Data JPA의 `AbstractAggregateRoot`가 그 용도다.

```java
@Entity
public class Order extends AbstractAggregateRoot<Order> {

    public void complete() {
        if (this.status != OrderStatus.PAID) throw new IllegalStateException();
        this.status = OrderStatus.COMPLETED;
        registerEvent(OrderCompletedEvent.from(this));   // 상태 변경과 이벤트 등록이 한 자리에
    }
}
```

등록된 이벤트는 **`repository.save()`가 호출될 때 발행**된다. 이 성질이 곧 한계이기도 하다 — **변경 감지만으로 수정하고 `save()`를 부르지 않으면 이벤트가 나가지 않는다.** "JPA는 save 안 해도 된다"는 지식과 정면으로 부딪히는 지점이라, 팀에 도입한다면 **이 규칙을 명시적으로 합의**해야 한다.

### 2-11. 그래도 남는 구멍 — 이것이 Outbox로 가는 다리

`AFTER_COMMIT` + `REQUIRES_NEW`까지 갖췄다고 끝이 아니다. **커밋 직후 리스너가 실행되기 전에 서버가 죽으면 그 이벤트는 세상에서 사라진다.** 이벤트는 애플리케이션 메모리 위의 객체일 뿐이고, **주문 커밋과 이벤트 실행 사이에는 원자성이 없다.**

```text
주문 COMMIT 성공 ──────╳ (서버 재시작 / OOM / 배포) ─── 리스너 실행 안 됨
                        주문은 완료됐는데 포인트는 영원히 없다. 기록도 없다.
```

**주문이 완료됐다는 사실과, 포인트를 적립해야 한다는 사실이 함께 저장되지 않는 한 이 구멍은 못 막는다.** 그게 Outbox다(§3-8).

## 3. 대가와 안전망 — 데드락, Outbox, 그리고 분리의 비용

여기부터가 이 문항의 두 번째 봉우리다. 다룰 것이 넷이다. **블로킹 I/O를 다 뺐는데도 남는 데드락**(§3-1~3-7), **이벤트 분리의 나머지 절반인 Outbox**(§3-8), **분리가 새로 만드는 비용**(§3-9), 그리고 **이 모든 것을 사람의 주의력이 아니라 장치로 고정하는 법**(§3-10)이다.

### 3-1. 데드락 — 블로킹 I/O가 하나도 없어도 벌어지는 일

"메일을 뺐으니 됐다"고 생각한 순간, **전부 단순 DB 변경인데도** 터지는 문제가 남아 있다.

용어부터. **데드락(deadlock, 교착)은 "둘 이상의 트랜잭션이 서로가 쥔 자원을 기다리느라 아무도 진행하지 못하는 상태"**다. 핵심은 **순환**이다 — 내가 기다리는 상대가 나를 기다리고 있으면, 시간이 아무리 지나도 풀리지 않는다.

### 3-2. 전제 확인 — 락은 이미 잡혀 있다

§1-5를 다시 못 박고 간다. **`@Lock`도 `for update`도 없지만, `UPDATE`가 나가는 순간 그 행은 커밋까지 잠긴다.** 따라서 한 트랜잭션에서 재고·포인트·쿠폰을 순서대로 UPDATE하면 **락을 세 개 순차적으로 쥔 채 커밋을 향해 간다.** 이 그림이 머리에 있어야 다음이 보인다.

### 3-3. 재현 시나리오 — 주문 흐름 vs 정산 배치

조건은 이것이다. 주문 완료는 **재고 → 포인트** 순으로 갱신하고, 관리자 정산 배치는 **포인트 → 재고** 순으로 갱신한다. 둘 다 정상 코드이고, 각자 혼자 돌면 아무 문제가 없다.

```text
        T1: 주문 완료 (재고 → 포인트)          T2: 정산 배치 (포인트 → 재고)
──────────────────────────────────────────────────────────────────────────────
 t1     UPDATE stock                          
          └ stock 락 획득 ──────┐             
                                │             
 t2                             │             UPDATE point
                                │               └ point 락 획득 ──────┐
                                │ 보유                                │ 보유
 t3     UPDATE point            │                                     │
          └ point 락 요청 ──────┼──── 대기 ──▶ (T2가 쥐고 있다)        │
                                │                                     │
 t4                             │             UPDATE stock            │
                                └ ◀── 대기 ────  └ stock 락 요청       │
                                                                      │
        T1은 T2를 기다리고, T2는 T1을 기다린다 → 순환 성립 = 교착
        어느 쪽도 커밋할 수 없으므로 어느 쪽의 락도 풀리지 않는다
        DB가 감지해 한쪽을 희생자로 골라 강제 롤백시킨다
```

같은 내용을 표로도 보자.

| 시각 | T1: 주문 완료 | T2: 정산 배치 | DB 상태 |
|---|---|---|---|
| t0 | `BEGIN` | `BEGIN` | |
| t1 | `UPDATE stock ...` → **stock 락 획득** | | T1이 stock 보유 |
| t2 | | `UPDATE point ...` → **point 락 획득** | T2가 point 보유 |
| t3 | `UPDATE point ...` → **대기** (T2가 쥠) | | T1 대기 |
| t4 | | `UPDATE stock ...` → **대기** (T1이 쥠) | **교착 성립** |
| t5 | DB가 교착을 감지하고 **한쪽을 희생자로 골라 강제 롤백** | | |

**핵심은 t3에서 끝나지 않는다는 것이다.** t3만 보면 "T1이 좀 기다리다 T2가 커밋하면 진행되겠지"로 보인다. 그런데 **t4에서 T2도 T1을 기다리기 시작하는 순간, 둘 다 상대의 커밋을 기다리므로 어느 쪽도 커밋할 수 없다.** 단순 대기와 교착을 가르는 것은 **"내가 기다리는 상대가 나를 기다리는가"** 하나다.

**단순 대기와 데드락의 차이**를 한 줄로: **대기는 시간이 지나면 풀리고, 교착은 시간이 지나도 안 풀린다.** 그래서 DB는 기다리지 않고 **한쪽을 죽인다.**

**트래픽이 데드락 확률을 키운다.** 초당 수천 건이면 t1~t4의 겹칠 기회가 계속 생긴다. 그래서 **개발·스테이징에서는 절대 재현되지 않다가 프로덕션 피크에만 터지는** 전형적 패턴이 된다.

### 3-4. 로그에서 알아보는 법

**PostgreSQL에서 희생자가 된 트랜잭션은 SQLSTATE `40P01`과 함께 이런 에러를 받는다.**

```text
ERROR: deadlock detected
DETAIL: Process 4321 waits for ShareLock on transaction 987; blocked by process 4322.
        Process 4322 waits for ShareLock on transaction 986; blocked by process 4321.
HINT: See server log for query details.
```

**MySQL이면 SQLSTATE `40001`과 함께 이 예외가 온다.**

```text
com.mysql.cj.jdbc.exceptions.MySQLTransactionRollbackException:
    Deadlock found when trying to get lock; try restarting transaction
```

**두 경우 모두 스프링에서는 `CannotAcquireLockException`으로 번역된다.** 경로를 알아두면 좋다 — 하이버네이트 6.6의 `PostgreSQLDialect`가 `40P01`을 `LockAcquisitionException`으로 바꾸고(MySQL의 `40001`은 공통 변환기가 처리한다), 스프링이 그것을 `CannotAcquireLockException`으로 옮긴다. 이 타입은 `PessimisticLockingFailureException`의 하위 타입이므로, **재시도 대상을 잡을 때 상위 타입으로 잡아도 함께 걸린다.**

**"try restarting transaction"이라는 MySQL의 문구가 좋은 단서다** — DB가 직접 "재시도하면 된다"고 알려주는 것이고, 이는 **데드락이 재시도 가능한(retryable) 예외**라는 뜻이다. PostgreSQL의 `HINT: See server log for query details`도 같은 성격의 안내다.

**원인을 캐려면 예외 한 줄로는 부족하다. 두 트랜잭션이 각각 무엇을 쥐고 무엇을 기다렸는지**를 봐야 하는데, 그 정보가 있는 곳이 벤더마다 다르다.

| | 상세 정보 위치 | 상시 수집 설정 | 주의 |
|---|---|---|---|
| PostgreSQL | **서버 에러 로그에 자동 기록** — 관련 프로세스와 각자의 SQL, 대기 관계가 전부 남는다 | 별도 설정 없이 항상 기록된다. 대기 자체를 보려면 `log_lock_waits = on` | 감지까지 `deadlock_timeout`(기본 1초)만큼 걸린다 |
| MySQL (InnoDB) | `SHOW ENGINE INNODB STATUS`의 `LATEST DETECTED DEADLOCK` 절 | `innodb_print_all_deadlocks = ON`을 켜야 모든 데드락이 에러 로그에 남는다 | **가장 최근 데드락 하나만** 보관하며 다음 데드락이 덮어쓴다 |

MySQL의 `LATEST DETECTED DEADLOCK` 절에서는 **세 가지**를 읽는다.

- **`*** (1) TRANSACTION` / `*** (2) TRANSACTION`** — 두 트랜잭션이 각각 **실행 중이던 SQL 문**. 어느 코드 경로인지 여기서 특정한다.
- **`*** (1) WAITING FOR THIS LOCK TO BE GRANTED` / `*** (2) HOLDS THE LOCK(S)`** — 누가 무엇을 쥐고 무엇을 기다렸는지. **인덱스 이름과 잠긴 레코드**까지 나온다.
- **`*** WE ROLL BACK TRANSACTION (N)`** — 어느 쪽이 희생자로 선택됐는지.

PostgreSQL 로그에서도 읽어야 할 것은 같다 — **두 프로세스의 SQL을 나란히 놓고 "둘이 만지는 테이블 순서가 반대인가"** 를 보면 대개 그 자리에서 원인이 드러난다.

**주의**: MySQL에서 `innodb_print_all_deadlocks`를 켜두지 않았다면 **"터졌는데 왜 터졌는지 알 방법이 없는 상태"** 로 운영하는 것이다. 이건 코드 문제가 아니라 운영 준비의 문제다.

### 3-5. 처방 ① — 자원 획득 순서를 전역으로 고정한다 (근본 처방)

데드락은 **순환 대기**가 성립할 때만 생긴다. 순환이 생기려면 **누군가는 반대 방향으로 가야 한다.** 그러니 **모두가 같은 방향으로 가게 만들면 순환 자체가 만들어지지 않는다.**

일방통행 도로에서는 정면 충돌이 없는 것과 같다. 차를 더 조심히 몰게 하는 게 아니라 **길의 방향을 고정하는 것**이 처방이다.

**층위가 둘이다.**

**(a) 테이블(자원) 사이의 순서를 팀 규약으로 고정한다.**

```java
// before — 서비스마다 편한 순서로 만진다
// OrderService    : stock  → point
// SettlementBatch : point  → stock      ← 반대 방향. 데드락 성립.

// after — "재고 → 포인트 → 쿠폰" 순서를 전역 규약으로 정하고 모두가 따른다
// OrderService    : stock  → point
// SettlementBatch : stock  → point      ← 같은 방향. 뒤에 온 쪽은 그냥 대기할 뿐이다.
```

말로만 정하면 지켜지지 않으므로 **규약을 코드가 강제하는 형태**로 만드는 편이 낫다. 여러 도메인을 함께 갱신하는 자리를 하나의 조율 지점(퍼사드/유스케이스)으로 모으고, 그 안에서만 순서를 정의하면 규약이 한 곳에만 존재한다.

**(b) 같은 테이블 안 여러 행은 PK 오름차순으로 정렬한 뒤 처리한다.**

```java
// before — 요청이 준 순서 그대로 → 트랜잭션마다 락 순서가 달라진다
public void decrease(List<OrderItem> items) {
    for (OrderItem item : items) {
        Stock stock = stockRepository.findByProductId(item.getProductId()).orElseThrow();
        stock.decrease(item.getQuantity());
    }
}
// 주문 A: 상품 [10, 20] → 락 10 → 20
// 주문 B: 상품 [20, 10] → 락 20 → 10      ← 장바구니 담은 순서만 달라도 데드락

// after — 항상 같은 기준으로 정렬한 뒤 처리한다
public void decrease(List<OrderItem> items) {
    List<OrderItem> ordered = items.stream()
            .sorted(Comparator.comparing(OrderItem::getProductId))   // 순서를 고정한다
            .toList();
    for (OrderItem item : ordered) { ... }
}
```

**Hibernate는 이 순서를 지켜주지 않는다.** flush 시점에 나가는 UPDATE 순서는 **영속성 컨텍스트에 올라온 순서**에 좌우되고, 그 순서는 요청마다 얼마든지 달라진다. `HashSet` 순회, `ORDER BY` 없는 SELECT의 반환 순서, `Set`으로 매핑한 연관관계 — 순서가 흔들리는 경로는 많다. **정렬은 프레임워크가 아니라 내가 코드로 고정해야 한다.** 자세한 메커니즘은 [flush 시점과 쓰기 지연 SQL 실행 순서](15-flush-timing-and-sql-ordering.md) §5에 있다.

(`hibernate.order_updates=true`가 있지 않느냐고 물을 수 있는데, 그건 **JDBC 배치로 묶기 좋게 문장을 그룹핑하는 설정**이지 **애플리케이션이 원하는 락 순서를 보장하는 장치가 아니다.** 목적이 다르므로 데드락 대책으로 쓸 수 없다.)

### 3-6. 처방 ② — 트랜잭션을 줄이면 데드락도 줄어든다

**이 문항의 앞뒤가 여기서 연결된다.** §2-6에서 포인트·쿠폰을 이벤트로 뺐다면, 주문 트랜잭션은 **order와 stock 두 개만** 잠근다. 정산 배치와 겹칠 자원이 애초에 줄어들고, 락을 쥔 시간도 짧아져 **t1~t4가 겹칠 확률 자체가 떨어진다.**

> **도메인 이벤트로 쪼개는 것은 성능 최적화가 아니라 데드락 대책이기도 하다.** 잠그는 자원 수와 잠그는 시간, 이 둘이 데드락 확률을 결정하는 변수이고 트랜잭션 분리는 그 둘을 동시에 줄인다.

다만 **분리만으로는 부족하다.** 자원이 두 개만 남아도 두 코드 경로가 반대 순서로 잡으면 데드락이다. **§3-5가 근본 처방이고 §3-6은 확률을 낮추는 보조**라는 순서를 헷갈리면 안 된다.

### 3-7. 처방 ③ — 재시도 (짜여진 안전망)

데드락은 **완전히 없앨 수 없다.** 인덱스 락, 옵티마이저의 실행 계획 변경, 외래키 제약이 만드는 부모 행 락처럼 **코드에 안 보이는 경로**가 있기 때문이다. 그래서 예방과 별개로 **재시도를 갖춰둔다.**

```java
@Retryable(
    retryFor = CannotAcquireLockException.class,          // 데드락 희생자만
    maxAttempts = 3,
    backoff = @Backoff(delay = 50, multiplier = 2, random = true))  // 지수 백오프 + 지터
public void completeOrder(Long orderId) {
    orderTransactionService.completeOrder(orderId);       // @Transactional 은 이쪽 빈에
}
```

**두 가지를 반드시 지킨다.**

- **재시도는 트랜잭션 밖에서.** `@Transactional` 메서드 안에서 `for` 루프로 감싸면, 이미 롤백된 트랜잭션 위에서 재시도하는 꼴이라 커밋 시점에 `UnexpectedRollbackException`이 난다. **재시도 담당 빈과 트랜잭션 담당 빈을 분리**해서 매번 새 트랜잭션·새 영속성 컨텍스트로 다시 들어가야 한다. (같은 구조를 낙관적 락 재시도에서도 쓴다 — [동시성 갱신 4가지 접근](20-concurrency-update-four-approaches.md))
- **지터를 넣는다.** **지터(jitter)는 재시도 대기 시간에 섞는 무작위 값**이다. 지연이 고정값이면 충돌했던 요청들이 정확히 같은 시각에 깨어나 또 부딪힌다.

**그리고 재시도가 예방을 대신할 수는 없다.** 재시도 횟수는 **메트릭으로 노출해 감시**해야 하고, 그 수치가 오르면 그건 "재시도가 잘 동작하고 있다"가 아니라 **"어딘가에 순서 역전이 있다"는 경보**다.

### 3-8. Outbox 패턴 — 이벤트 분리의 나머지 절반

**Outbox 패턴은 이 장에서 정의와 필요성까지만 다룬다.** 릴레이 운영, CDC, 보상 트랜잭션, Saga와의 관계 같은 깊은 이야기는 [결제·정합성 장의 차감·지급 정합성](../10-payment-consistency/05-deduction-grant-consistency.md)과 [분산 Saga와 보상 설계](../10-payment-consistency/10-distributed-saga-compensation-idempotency.md)가 본론이다. 여기서 알아야 할 것은 **"왜 이벤트 분리에 이게 반드시 따라붙는가"** 하나다.

**문제를 정확히 다시 진술한다.** §2-11에서 본 구멍은 이것이다. **주문 커밋과 이벤트 처리 사이에 원자성이 없다.** 서로 다른 두 개의 일(하나는 DB 커밋, 하나는 메모리 위 리스너 실행)이고, 둘을 한 몸으로 묶어 줄 장치가 없다. 그래서 "주문은 완료됐는데 포인트는 없다"가 발생하고, **더 나쁜 것은 그 사실을 아무도 모른다**는 점이다. 기록이 없으니 재처리할 대상 목록조차 만들 수 없다.

**Outbox(아웃박스)는 말 그대로 "보낼 편지함"이다.** 이벤트를 곧바로 발행하는 대신 **주문과 같은 DB의 테이블에 한 줄 INSERT해 둔다.** 그러면 주문 UPDATE와 이벤트 저장이 **같은 트랜잭션 안의 두 쓰기**가 되어, 둘 다 커밋되거나 둘 다 롤백된다.

```text
주문 커밋 = 이벤트 저장    ← 이 등식이 Outbox 의 전부다
둘 중 하나만 성공하는 상태가 물리적으로 존재하지 않는다
```

**"주문에 포인트 적립 여부 플래그를 둔다"는 발상은 방향이 정확하다** — 원자성이 보장되는 곳에 "해야 할 일"을 기록해두자는 것이고, 그게 Outbox의 본질이다. 다만 **거기서 끝나면 절반**이다. 나머지 절반이 **누가 그 기록을 보고 재처리하는가**와 **재처리가 중복을 만들지 않게 하는 장치**다.

```sql
-- PostgreSQL 기준. 핵심은 "주문과 같은 DB"에 있다는 것이다.
CREATE TABLE outbox_message (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    aggregate_id bigint       NOT NULL,        -- 주문 ID
    event_type   varchar(100) NOT NULL,        -- 'OrderCompleted'
    payload      jsonb        NOT NULL,        -- 이벤트 본문
    status       varchar(20)  NOT NULL,        -- PENDING / SENT / FAILED
    retry_count  int          NOT NULL DEFAULT 0,
    created_at   timestamptz  NOT NULL,
    sent_at      timestamptz  NULL
);

-- 미처리 건만 스캔하면 되므로 부분 인덱스가 가장 알맞다
CREATE INDEX idx_outbox_pending ON outbox_message (created_at)
    WHERE status = 'PENDING';
```

**핵심은 저장 위치다.** outbox 테이블은 **주문과 같은 DB**에 있어야 한다. 그래야 `order` UPDATE와 `outbox_message` INSERT가 **하나의 로컬 트랜잭션으로 함께 커밋**된다. 메시지 브로커에 직접 발행하지 않고 굳이 테이블을 거치는 이유가 이것이다 — **DB 커밋과 브로커 발행은 서로 다른 시스템이라 원자적으로 묶을 수 없다**(그걸 억지로 묶는 게 2단계 커밋인데, 성능과 운영 복잡도 때문에 실무에서 거의 안 쓴다). **원자성이 보장되는 하나의 DB 안으로 문제를 끌고 들어오는 것**이 Outbox의 아이디어다.

**재처리 주체 — 릴레이.** 저장만 하고 아무도 안 읽으면 그냥 로그다. **미처리 건을 긁어 발행하는 주체**가 반드시 있어야 한다.

```java
@Component
@RequiredArgsConstructor
public class OutboxRelay {

    @Scheduled(fixedDelay = 1000)
    public void publishPending() {
        List<OutboxMessage> pending =
                outboxRepository.findTop100ByStatusOrderByIdAsc(Status.PENDING);
        //                                              ↑ ID 순 = 발행 순서를 안정적으로 유지

        for (OutboxMessage message : pending) {
            try {
                eventPublisher.publish(message);          // 브로커 발행 또는 직접 호출
                message.markSent();                       // 별도 트랜잭션으로 커밋
            } catch (Exception e) {
                message.markFailed(e.getMessage());       // retry_count++ 후 다음 주기에 재시도
                log.warn("outbox publish failed: id={}", message.getId(), e);
            }
        }
    }
}
```

**릴레이에서 챙겨야 할 것 넷** (각 항목의 상세 설계는 10장에 있다).

- **멀티 인스턴스 중복 처리** — 서버가 3대면 같은 행을 셋이 함께 집는다. `SELECT ... FOR UPDATE SKIP LOCKED`로 서로 다른 행을 가져가게 하거나, 샤드 키로 인스턴스를 나누거나, 릴레이만 단일 인스턴스(리더 선출)로 돌린다.
- **재시도 상한과 DLQ** — `retry_count`가 임계치를 넘으면 `FAILED`로 격리하고 **알림을 보낸다.** 무한 재시도는 정상 메시지 처리까지 막는다.
- **정리(purge)** — `SENT` 행이 무한히 쌓이면 인덱스가 비대해진다. 보관 기간을 정해 주기적으로 삭제한다.
- **폴링 지연** — 1초 주기면 최대 1초 지연이다. 이 지연이 곧 §3-9의 "즉시 일관성 상실"이다. 규모가 커지면 Debezium 같은 CDC 도구로 **DB 트랜잭션 로그를 읽어** outbox INSERT를 감지하는 방식으로 가는데, 대신 **인프라가 하나 늘어난다.** **(가산점 포인트)**

**멱등성 — 재처리의 필연적 짝.** Outbox는 **at-least-once**(최소 한 번) 전달이다. **정확히 한 번은 보장하지 않는다.** 발행에 성공했는데 `markSent()` 직전에 서버가 죽으면, 다음 주기에 같은 메시지를 **다시** 발행한다.

**그래서 중복 방지는 발행 쪽이 아니라 소비 쪽 책임이다.** 그리고 가장 확실한 장치는 애플리케이션 조건문이 아니라 **DB 제약**이다.

```sql
CREATE TABLE point_history (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id  bigint NOT NULL,
    order_id bigint NOT NULL,
    amount   int    NOT NULL,
    CONSTRAINT uk_point_history_order UNIQUE (order_id)   -- 한 주문에 적립은 딱 한 번
);
```

```java
@Transactional
public void accumulate(PointAccumulateCommand command) {
    try {
        pointHistoryRepository.save(PointHistory.of(command));   // 유니크 제약이 두 번째를 막는다
        pointRepository.findByUserId(command.userId())
                       .orElseThrow()
                       .accumulate(command.amount());
    } catch (DataIntegrityViolationException e) {
        log.info("이미 적립된 주문입니다. orderId={}", command.orderId());
        // 중복은 정상 흐름이다. 조용히 성공 처리하고 넘어간다.
    }
}
```

**"먼저 조회해서 있으면 건너뛴다"로 하면 안 되는 이유**: 같은 메시지가 두 스레드에 동시에 들어오면 둘 다 "없음"을 읽고 둘 다 INSERT한다. **check-then-act는 동시성 아래에서 깨진다.** 유니크 제약은 **DB가 원자적으로 판정**하므로 이 창이 없다. 예외 처리 시 `rollback-only` 마킹 문제까지 포함한 자세한 내용은 [복합 유니크 제약과 동시 INSERT](14-unique-constraint-concurrent-insert.md)에 있다.

**순서 보장 — 되는 것과 안 되는 것.** Outbox가 **한 애그리거트 안의 순서**는 지켜준다(같은 `aggregate_id`의 메시지를 ID 순으로 처리). 하지만 **서로 다른 애그리거트 사이의 전역 순서는 보장하지 않는다.** 병렬 소비를 하면 같은 애그리거트 안에서도 순서가 뒤집힐 수 있다. **처방 두 갈래**: ① **순서가 중요하면 같은 키(예: 주문 ID)의 메시지를 같은 파티션·같은 소비자로** 보낸다 ② **애초에 순서에 의존하지 않게 설계한다** — 이벤트에 상태 전이의 결과(최종 상태)를 담아 늦게 온 이벤트를 소비자가 버전으로 판단해 버릴 수 있게 한다.

### 3-9. 분리는 공짜가 아니다 — 포기하는 것 네 가지

여기까지 읽으면 "쪼개면 다 좋아지네"로 읽히기 쉽다. **아니다.** 이벤트로 쪼개는 순간 없던 문제가 넷 생긴다. 면접에서는 **이걸 스스로 붙이는 사람이 시니어로 읽힌다.**

**① 즉시 일관성을 잃는다.** 주문 완료 화면에서 포인트 잔액을 조회하면 **아직 안 들어와 있을 수 있다.** 사용자에게는 "포인트가 안 들어왔어요"라는 문의로 나타난다. UI에서 "적립 처리 중입니다"로 표기하거나, 예상 적립액을 미리 보여주고 확정은 나중에 하는 식의 **UX 설계가 함께 필요하다.** 기술 결정이 화면 문구까지 바꾼다.

**② 추적이 어려워진다.** 한 화면에서 순서대로 읽히던 흐름이 **발행자와 리스너 여러 개로 흩어진다.** "포인트가 왜 안 들어왔지?"를 조사하려면 주문 로그, outbox 테이블, 릴레이 로그, 포인트 서비스 로그를 각각 봐야 한다. **처방은 상관관계 ID 전파** — 이벤트 payload에 traceId를 넣어 리스너의 MDC에 복원하면 흩어진 로그를 하나로 꿸 수 있다. 비동기 경계를 넘을 때 MDC는 자동으로 넘어가지 않으므로 **명시적으로 넘겨야 한다.**

**③ 보상 트랜잭션을 설계해야 한다.** **보상 트랜잭션(compensating transaction)은 "이미 커밋된 작업을 되돌리는 반대 방향의 새 작업"**이다. 롤백이 사라진 자리를 이것이 대신한다. 쿠폰 사용 처리가 실패하면 쿠폰을 복구하는 로직, 포인트가 잘못 적립되면 회수하는 로직. **그리고 보상 자체도 실패할 수 있어서** 재시도와 수동 개입 창구가 또 필요하다. 이게 실무에서 가장 크게 드는 비용이다.

**④ 순서와 중복을 다뤄야 한다.** §3-8에서 본 그대로다. **한 트랜잭션이 공짜로 주던 것**(원자성, 순서, 정확히 한 번)을 **전부 직접 구현**해야 한다.

**그래서 판단은 이렇게 정리된다.**

> "**분리는 공짜가 아닙니다.** 즉시 일관성·추적 가능성·롤백의 단순함을 내주고, 락 경합 축소와 장애 격리를 사는 거래입니다. 그래서 **블로킹 I/O가 들어있거나, 실패해도 주문을 되돌릴 이유가 없거나, 실제로 락 경합이 관측되는 경우**에만 분리합니다. 단순 DB 변경 몇 개를 이론적으로 옳다는 이유만으로 쪼개면, **얻는 것 없이 추적 난이도와 보상 로직 비용만 지불하게 됩니다.**"

### 3-10. 관측과 안전망 — "지키자"가 아니라 "못 어기게"

이 문항의 문제들은 전부 **평소에는 안 보이다가 피크에만 터지는** 종류다. 그래서 코드 리뷰에서 눈으로 잡겠다는 계획은 실패한다. **장치로 고정한다.**

**(a) 트랜잭션 안 외부 API 호출을 빌드 단계에서 막는다.** 이 문항 최대의 위험(§1-1)을 **구조 규칙으로 못 박는다.**

```java
@AnalyzeClasses(packages = "com.example.order")
class TransactionBoundaryRulesTest {

    @ArchTest
    static final ArchRule 트랜잭션_안에서_외부_클라이언트를_호출하지_않는다 =
        noMethods().that().areAnnotatedWith(Transactional.class)
            .should().callMethodWhere(target(owner(
                nameMatching(".*(MailClient|PaymentClient|SlackClient|RestTemplate|WebClient).*"))))
            .because("외부 API 응답 시간이 그대로 행 락 유지 시간과 커넥션 점유 시간이 된다");
}
```

**완벽하지 않다** — 인터페이스 뒤에 숨거나 여러 단계를 거쳐 호출하면 못 잡는다. 그래도 **가장 흔한 형태(서비스에서 클라이언트를 직접 부르는 것)를 막고, 무엇보다 팀에 규칙의 존재를 알린다.** 룰을 우회해야 하는 상황이 생기면 그때 논의가 일어나는 것 자체가 이득이다.

**(b) 트랜잭션 길이를 숫자로 본다.** "트랜잭션이 길다"는 말은 측정하지 않으면 감상이다.

- **트랜잭션 소요 시간을 Micrometer 타이머로** — `TransactionSynchronization`에 훅을 걸어 시작~완료 시간을 메서드 이름 태그와 함께 기록한다. **p99가 예상 밖으로 긴 트랜잭션**이 다음 사고 후보다.
- **임계치 초과 시 경고 로그가 아니라 알림으로** — 로그는 아무도 안 본다. 경보로 승격해야 신호가 된다.
- **커넥션 풀 대기 시간(HikariCP `hikaricp.connections.acquire`)** — 이 값이 오르면 **어딘가에 긴 트랜잭션이 있다**는 뜻이다. 원인 추적의 출발점.

**(c) 데드락과 outbox를 감시한다.**

- **데드락 발생을 알림으로.** PostgreSQL은 데드락을 서버 에러 로그에 자동으로 남기므로 그 로그를 알림으로 연결하고, MySQL이면 `innodb_print_all_deadlocks`를 먼저 켜야 한다. 그리고 애플리케이션 쪽에서는 `CannotAcquireLockException` 발생 건수를 카운터로 노출한다. **데드락이 조용히 재시도로 흡수되고 있다면 그건 문제가 없는 게 아니라 문제가 안 보이는 것**이다.
- **outbox 미처리 건수와 최고 지연(age)** — `PENDING` 상태 건수와 가장 오래된 `PENDING`의 나이를 게이지로 노출한다. 이 두 숫자가 오르면 **릴레이가 죽었거나 소비 측이 계속 실패하고 있다.** `FAILED` 건수는 0이 아니면 즉시 알림 대상이다.

**(d) 테스트로 고정한다.**

- **`@Transactional` 테스트에서는 `AFTER_COMMIT` 리스너가 안 돈다.** 테스트 트랜잭션은 끝에 롤백되므로 커밋이 없고, 따라서 리스너도 안 불린다. **"테스트가 통과했는데 운영에서 안 도는" 게 아니라 그 반대 — 테스트에서 안 돌아 검증 자체가 비어 있다.** `@Commit`을 쓰거나, `TestTransaction`으로 명시적으로 커밋하거나, `@SpringBootTest` + `@Transactional` 없이 실제 커밋시켜 검증한다.
- **데드락 재현 테스트.** `CountDownLatch`로 두 스레드를 **반대 순서로 동시에 출발**시키면 데드락을 의도적으로 만들 수 있다. 이 테스트가 **정렬 처방을 넣기 전에는 실패하고 넣은 뒤에는 통과**하는 것을 한 번 확인하면, 그 처방이 회귀 테스트로 고정된다.
- **H2가 아니라 Testcontainers로.** 데드락 감지, 락 타임아웃, `SKIP LOCKED`, 유니크 제약 동작은 **DB 벤더마다 다르다.** §1-6의 표에서 봤듯 락 대기 기본값부터 다르다. H2에서 통과한 동시성 테스트는 보장의 근거가 되지 못한다.

**(가산점 포인트)** 이 장치들의 공통점은 **"조심하자"를 "못 어기게"로 바꾼 것**이다. 트랜잭션 경계 문제는 사람의 주의력으로 지킬 수 있는 종류가 아니다 — 코드는 정상으로 보이고, 문제는 부하가 걸릴 때만 나타나며, 그때는 이미 장애다.

## 4. 꼬리질문 대비 포인트

### "이 메서드가 도는 동안 커넥션과 행 락은 언제부터 언제까지 잡혀 있나요?"

**커넥션은 트랜잭션 시작부터 종료까지 통째로**, **행 락은 각 `UPDATE`가 나간 시점부터 커밋까지** 잡혀 있다. 원본 코드는 마지막에 메일 API가 있으므로 **메일 응답 시간이 그대로 락 유지 시간과 커넥션 점유 시간에 더해진다.**

여기서 되물을 가치가 있는 것은 **"명시적 락을 쓰는 곳이 있느냐"** 인데, **답이 '없다'여도 결론은 달라지지 않는다는 것**을 함께 말해야 완성이다.

> "명시적 락이 없어도 마찬가지입니다. **`UPDATE` 문 자체가 대상 행에 배타 락을 걸고 커밋까지 유지**하기 때문입니다. 이건 애플리케이션이 아니라 DB가 하는 일이고, `select ... for update`는 그 락을 SELECT 시점으로 앞당기는 것일 뿐입니다. **커밋 전까지 락을 유지하는 건 롤백 가능성을 지키기 위한 필연**이라서, 커밋이 늦어지면 락도 그만큼 길어집니다."

**다른 요청은 그동안 무엇을 하는지까지 붙이면 완성이다.** 같은 행을 건드리는 요청은 **락을 못 얻어 대기**하며, 그 대기 시간 동안에도 **커넥션은 계속 쥐고 있다.** PostgreSQL은 `lock_timeout` 기본값이 0(무한 대기)이라 실패하지 않고 조용히 쌓이고, MySQL은 `innodb_lock_wait_timeout` 기본 50초가 지나면 에러로 실패한다. **PostgreSQL 쪽이 더 위험한 이유가 여기 있다 — 시끄럽게 실패하는 대신 서비스 전체가 느려지는 형태로 나타난다.**

### "메일 발송을 `@Async`로 뺐습니다. 그런데 그 뒤 `couponService.use()`에서 예외가 나 롤백됐습니다. 무슨 일이 벌어지나요?"

**DB에는 아무 일도 안 일어났는데 고객에게는 "주문이 완료되었습니다" 메일이 도착한다.** `@Async`는 실행을 다른 스레드로 옮길 뿐 **커밋을 기다리지 않기 때문**이고, 메일에는 롤백이 없기 때문이다.

처방은 **`@TransactionalEventListener(phase = AFTER_COMMIT)`** — 커밋이 확정된 뒤에만 리스너가 실행되므로 이 조합이 원천 차단된다. `@Async`는 버리는 게 아니라 **그 위에 얹어** 커밋 후 처리가 호출 스레드를 막지 않게 한다.

**한 줄로 정리하면**: *비동기와 커밋 후는 다른 축이다. `@Async`는 "언제 실행할지"가 아니라 "누가 실행할지"를 바꾼다.*

### "블로킹 I/O를 전부 뺐고 남은 건 단순 DB 변경뿐입니다. 그래도 쪼갤 이유가 있나요?" (시니어 변별 포인트)

**있다. 두 가지다.**

**① 데드락.** 주문은 재고→포인트 순으로, 정산 배치는 포인트→재고 순으로 갱신하면 **서로 상대가 쥔 락을 기다려 교착**이 된다. 블로킹 I/O와 무관하고, **트래픽이 높을수록 겹칠 기회가 늘어난다.** DB가 한쪽을 희생자로 골라 강제 롤백시키므로 **정상 주문이 이유 없이 실패하기 시작한다.** 근본 처방은 **자원 획득 순서를 전역으로 고정**하는 것이고(테이블 순서 규약 + 같은 테이블 안은 PK 오름차순 정렬), **트랜잭션을 쪼개 잠그는 자원 수와 시간을 줄이는 것**이 확률을 함께 낮춘다.

**② 실패 파급 범위.** 쿠폰 처리 하나가 실패했다고 **이미 성공한 주문·재고·포인트를 전부 되돌리는 것이 옳은 정책인지**를 물어야 한다. 한 트랜잭션에 묶는 것은 "여기 있는 모두가 서로의 실패에 함께 죽는다"고 **코드가 임의로 선언한 것**이다.

**그리고 반대편도 붙인다** — 트래픽이 낮고 데드락 이력이 없다면 **한 트랜잭션에 두는 편이 유지보수에 낫다.** 이벤트로 흩으면 흐름 추적과 보상 로직 비용이 생기므로, **분리의 근거는 이론이 아니라 관측된 문제여야 한다.**

### "포인트 적립을 이벤트로 뺐는데, 주문 커밋 직후 서버가 재시작돼 적립이 안 됐습니다. 어떻게 다루시겠습니까?"

**근본 원인부터 짚는다** — 주문 커밋과 이벤트 처리 사이에 **원자성이 없기** 때문이다. 이벤트는 메모리 위의 객체라 프로세스가 죽으면 함께 사라지고, **기록이 없으니 재처리 대상 목록조차 만들 수 없다.**

**처방은 Outbox 패턴이고, 세 조각이 세트다.**

**① 원자적 기록** — 이벤트를 **주문과 같은 트랜잭션에서 같은 DB의 outbox 테이블에 INSERT**한다. 그러면 "주문 커밋 = 이벤트 저장"이 되어 **둘 중 하나만 성공한 상태가 물리적으로 존재하지 않는다.**

**② 재처리 주체** — 별도 프로세스(주기 폴링 배치 또는 CDC)가 `PENDING` 건을 읽어 발행하고 `SENT`로 표시한다. 서버가 죽었다 살아나도 **다음 주기에 자동으로 이어서 처리**된다.

**③ 멱등성** — 재처리는 필연적으로 중복을 만든다(발행 성공 직후 상태 갱신 전에 죽는 경우). **적립 이력 테이블에 주문 ID 유니크 제약**을 걸어 두 번째 시도가 DB 레벨에서 실패하게 하고, 그 예외를 정상 흐름으로 처리한다. **조회 후 분기(check-then-act)는 동시 실행에서 깨지므로 반드시 제약이어야 한다.**

**전달 보증은 at-least-once이지 exactly-once가 아니다** — 그래서 중복 방지는 발행 쪽이 아니라 **소비 쪽 책임**이라는 점을 함께 말하면 좋다.

### "`AFTER_COMMIT` 리스너 안에서 엔티티를 수정했는데 DB에 반영이 안 됩니다. 예외도 안 납니다." (시니어 변별 포인트)

**이름 그대로다 — 원 트랜잭션이 이미 커밋된 뒤라서 그 변경을 커밋해 줄 트랜잭션이 없다.** 변경 감지가 UPDATE를 만들려면 flush가 필요하고 flush를 일으키는 건 커밋인데, **그 커밋이 이미 지나갔다.** 그래서 **예외 없이 조용히 아무 일도 안 일어난다.**

**처방은 리스너에 `@Transactional(propagation = REQUIRES_NEW)`를 붙여 새 트랜잭션을 명시적으로 여는 것.** 기본값 `REQUIRED`로는 안 되는 이유까지 말하면 확실히 갈린다 — `AFTER_COMMIT` 시점에는 **커밋은 끝났지만 트랜잭션 자원이 아직 스레드에 묶여 있어서**, `REQUIRED`가 "진행 중인 트랜잭션이 있다"고 보고 **이미 끝난 그 트랜잭션에 참여해 버린다.** 참여했으니 커밋은 다시 일어나지 않고 변경은 버려진다. 스프링 문서도 이 단계에서는 "데이터 접근 코드가 원 트랜잭션에 참여는 하지만 변경이 커밋되지는 않는다"고 명시적으로 경고한다. **`REQUIRES_NEW`는 "무조건 새로 연다"** 이므로 이 판정 자체를 건너뛴다. 대가는 **커넥션을 하나 더 쓴다**는 것.

**같은 계열의 함정 둘을 덧붙이면 가산점이다.** ① `@TransactionalEventListener`는 **트랜잭션 없이 발행된 이벤트를 아예 받지 않는다**(필요하면 `fallbackExecution = true`). ② **`@Transactional` 테스트에서는 이 리스너가 실행되지 않는다** — 테스트가 끝에 롤백하므로 커밋이 없기 때문이고, 그래서 **검증이 통째로 비어 있는 채 통과**한다. `@Commit`이나 `TestTransaction`으로 실제 커밋시켜야 한다.

**그리고 여기서 한 걸음 더 나가면 Outbox로 이어진다.** `REQUIRES_NEW`로 새 트랜잭션을 열었어도 **그 안에서 실패하면 아무도 모른다** — 원 트랜잭션은 이미 커밋돼 되돌릴 것이 없고, 예외는 호출자에게 전파되지 않는다. **"조용히 사라진다"는 문제가 형태만 바꿔 남아 있는 것**이고, 그걸 막으려면 해야 할 일을 원 트랜잭션과 함께 DB에 적어두는 수밖에 없다.

### "이렇게 쪼개면 결국 MSA로 가자는 말인가요? 모놀리스에서 이벤트로 쪼개는 게 무슨 의미가 있죠?" (가산점 포인트)

**MSA로 가자는 말이 아니라, 갈 수 있는 상태를 만들어두자는 말이다.**

모놀리스에서 도메인 이벤트로 분리하는 순간 **각 도메인이 "같은 트랜잭션 안에 있다"는 전제 없이 동작하도록 강제**된다. 포인트 서비스는 주문 트랜잭션에 얹혀 가는 대신 **자기 트랜잭션으로 자기 정합성을 책임지고**, 실패하면 **재처리와 멱등성으로 스스로 복구**한다. 이건 서비스를 물리적으로 분리할 때 **어차피 반드시 해야 하는 일**이다.

**그래서 이건 MSA 전환의 예행연습이 아니라 전제 조건이다.** 트랜잭션으로 묶여 있는 모듈은 분리 자체가 불가능하다 — 프로세스가 갈리는 순간 하나의 트랜잭션이 성립하지 않기 때문이다. **결과적 일관성으로 동작할 수 있게 만들어 두면, 나중에 물리적으로 떼는 일은 배포 단위를 바꾸는 문제로 축소된다.**

**동시에 반대편도 분명히 한다.** *모놀리스에서 이벤트로 쪼개는 것 자체가 목적이 되면 안 된다.* 지금 당장 얻는 것(락 경합 축소, 장애 격리, 데드락 감소)이 없는데 "언젠가 MSA로 갈지 모르니까" 쪼개는 건 **오늘 비용을 내고 오지 않을 미래를 사는 것**이다. **오늘의 문제로 정당화되지 않는 분리는 하지 않는다.**

### "이벤트가 두 번 처리되는 걸 왜 소비 쪽에서 막나요? 발행 쪽에서 한 번만 보내면 되지 않나요?"

**한 번만 보내는 것이 원리적으로 불가능하기 때문이다.** 발행에 성공했다는 사실을 outbox에 `SENT`로 기록하는 순간과 실제로 발행한 순간 사이에는 **항상 틈이 있다.** 발행 후 기록 전에 죽으면 재발행되고, 기록 후 발행 전에 죽으면 **유실**된다. 둘 중 하나를 골라야 하고, **유실보다 중복이 낫기 때문에 at-least-once를 고른다.**

**중복은 감지할 수 있고 유실은 감지할 수 없다** — 이게 선택의 이유다. 중복은 유니크 제약이 잡아주지만, 사라진 이벤트는 아무 흔적도 남기지 않는다.

**그리고 멱등성은 "중복을 막는 장치"가 아니라 "중복이 와도 결과가 같게 만드는 성질"** 이다. 적립 이력에 주문 ID 유니크 제약을 거는 것은 두 번째 요청을 실패시키는 게 아니라, **두 번 와도 최종 상태가 한 번 온 것과 똑같게 만드는 것**이다. 그래서 소비 쪽에서 `DataIntegrityViolationException`을 잡아 **정상 흐름으로 조용히 넘기는 것**이 올바른 처리다.

## 한 줄 요약

**`@Transactional` 한 줄은 정합성 경계 하나가 아니라 네 개의 경계를 동시에 긋는다 — 정합성 경계 = 락 경합 범위 = 실패 파급 범위 = 커넥션 점유 시간.** 넷이 같은 선인 이유는 물리적이다 — **락은 커밋·롤백 시점에만 풀리고, 커넥션은 트랜잭션이 끝나야 반납되며, 롤백은 트랜잭션 전체를 되돌린다.** 그래서 애그리거트(함께 변경되어야 하는 엔티티들의 덩어리)를 하나 더 넣는 것은 이 넷을 함께 키우는 결정이고, DDD의 "한 트랜잭션에 한 애그리거트"는 **성능 규칙이 아니라 "즉시 정합해야 하는 최소 단위가 어디까지인가"를 묻는 정합성 규칙**이다(성능 개선은 그 규칙을 지킨 부산물이다). 그래서 이 코드의 최대 위험은 쿼리 수가 아니라 **메일 API 응답을 기다리는 동안 재고 행 락과 커넥션을 쥐고 있다는 사실**이며(명시적 락이 없어도 **`UPDATE`가 곧 커밋까지 유지되는 배타 락**이고, 같은 행을 건드리는 다른 요청은 커넥션을 쥔 채 대기한다 — PostgreSQL은 `lock_timeout` 기본값이 무한이라 실패 대신 조용히 쌓인다), 열린 질문에는 **구조 → 경계 → 성능** 순으로 답한다. **무엇을 남길지는 성능이 아니라 정합성 요구 수준이 정한다** — ① 트랜잭션 안에 블로킹 I/O가 있는가 ② 실패했을 때 주문을 취소해야 하는가. 재고는 남기고 포인트·쿠폰·메일은 이벤트로 뺀다. **블로킹 I/O가 하나도 없어도** 큰 트랜잭션은 **락 순서 역전으로 데드락**을 만들며(주문은 재고→포인트, 배치는 포인트→재고로 t1~t4에 순환이 성립한다), 근본 처방은 **자원 획득 순서를 전역으로 고정**하는 것 — 테이블 순서를 규약으로, 같은 테이블 안은 **PK 오름차순 정렬로. Hibernate가 지켜주지 않으므로 코드로 고정한다.** 분리의 도구는 `@TransactionalEventListener(AFTER_COMMIT)`이고 **리스너에서 DB를 바꾸려면 `REQUIRES_NEW`가 필수**다 — `AFTER_COMMIT` 시점에는 커밋이 끝났는데도 **트랜잭션 자원이 아직 스레드에 묶여 있어서** 기본값 `REQUIRED`가 이미 끝난 트랜잭션에 참여해 버리고 **변경이 조용히 버려지기** 때문이다. 그리고 그 새 트랜잭션이 실패해도 아무도 모르므로, 커밋 직후 유실까지 막으려면 **Outbox 3종 세트**(같은 트랜잭션에서 outbox INSERT + 릴레이 재처리 + 주문 ID 유니크 제약에 의한 멱등성)가 필요하다(상세 설계는 [10장](../10-payment-consistency/05-deduction-grant-consistency.md)). 마지막으로 **분리는 공짜가 아니다** — 즉시 일관성·추적 가능성·롤백의 단순함을 내주고 락 경합 축소와 장애 격리를 사는 거래이므로, **이론이 아니라 관측된 문제가 분리를 정당화해야 한다.** 그리고 이 모든 것은 **트랜잭션 길이 메트릭, 데드락 알람, outbox 미처리 게이지, `@Transactional` 안 외부 호출 금지 ArchUnit 룰**로 고정되기 전까지는 주장일 뿐이다.
