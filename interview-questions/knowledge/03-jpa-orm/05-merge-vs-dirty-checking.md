# merge vs dirty checking — "계산해서 고치기"와 "모르니까 전부 덮기"

> 핵심 관전 포인트: **변경 감지(dirty checking)는 무엇이 바뀌었는지 스냅샷과 비교해 계산한다. `merge`는 무엇이 바뀌었는지 모르니 넘어온 객체의 모든 필드를 덮어쓴다. `merge`도 결국 변경 감지를 타지만 덮어쓰기가 끝난 상태로 타기 때문에, 채우지 않은 필드의 `null`까지 "변경"으로 잡혀 UPDATE에 실려 나간다. 그래서 `new Member()`에 id와 두 필드만 채워 `save()`하면 예외 없이, 로그도 정상인 채로 나머지 컬럼이 전부 `null`이 된다. 이 사고의 방아쇠는 Spring Data의 `save()`가 id 유무로 `persist`와 `merge`로 갈린다는 점이다 — id가 있으면 "중복 에러"가 아니라 조용한 UPDATE다. 처방은 하나뿐이다: 조회해서 영속 상태로 만든 뒤 필요한 필드만 바꾼다. `merge`가 정당한 자리는 값을 덮어쓰는 것이 곧 요구사항인 재부착(reattach) 뿐이고, 그조차 실무에서는 거의 없다.**

---

## 0. 질문 + 의도

**질문**: "`merge`와 dirty checking의 차이는?"

**출제 의도**: `merge`의 오해(detached 엔티티 전체 덮어쓰기)는 "안 바꾼 필드가 null로 덮이는" 데이터 유실 사고를 만든다. 미묘하지만 사고 유형이 명확한 지식이다.

**함정**: 이 질문은 "정답 코드를 쓰는가"를 묻지 않는다. 대부분의 개발자는 관례상 "조회해서 setter로 바꾼다"를 이미 쓰고 있다. 묻는 것은 **왜 그게 옳은지 아는가**다. 이유를 모른 채 관례를 따르는 사람은 DTO를 엔티티로 변환하는 코드를 작성하는 순간, 또는 팀에 들어온 후배의 `save()` 코드를 리뷰하는 순간에 사고를 통과시킨다.

## 1. 원리 — 엔티티의 상태 네 가지와, 변경 감지가 하는 "계산"

### 1-1. 먼저 상태 전이를 그림으로 본다

`merge`를 이해하려면 **엔티티가 지금 어느 상태에 있는지**부터 구분할 수 있어야 한다. 상태는 넷이고, 상태를 바꾸는 것은 특정 메서드 호출이거나 트랜잭션의 끝이다.

```text
                        new Member()
                             │
                             ▼
                     ┌────────────────┐
                     │     비영속      │  컨텍스트가 모르는 객체. 보통 id도 없다
                     │  (transient)   │
                     └───────┬────────┘
                             │  persist(e)  /  save(e) ※ id가 없을 때
                             ▼
  find(id) ─────────▶┌────────────────┐──── remove(e) ───▶┌────────────────┐
  JPQL·QueryDSL 조회 ─▶│      영속      │                   │      삭제       │
  merge()의 반환값 ───▶│   (managed)    │                   │   (removed)    │
                     └───────┬────────┘                   └───────┬────────┘
                             │                                    │ flush
    detach(e)                │                                    ▼
    clear()                  │                               DELETE 실행
    close()                  │
    트랜잭션 종료              │
                             ▼
                     ┌────────────────┐
                     │     준영속      │─── merge(e) ───▶ 영속 "사본"이 새로 생긴다.
                     │   (detached)   │                   넘긴 e 자신은 준영속 그대로다.
                     └────────────────┘
                             ▲
                             │  new Member() 뒤에 setId(1L)로 id만 채운 객체도
                             │  JPA 입장에서는 여기에 준한다 ("id가 있는 낯선 객체")
```

이 그림에서 읽어야 할 것이 둘이다. 첫째, **영속 상태로 들어가는 문은 세 개뿐이다** — `persist`, 조회, `merge`의 반환값. 둘째, **`merge`의 화살표는 준영속에서 나가지만 그 화살표가 가리키는 것은 넘긴 객체가 아니라 새로 만들어진 사본**이다. 이 두 번째 사실이 3-1의 함정을 만든다.

### 1-2. 각 상태의 정의

| 상태 | 뜻 | 특징 |
|---|---|---|
| 비영속 (transient/new) | 방금 `new`로 만들었고 영속성 컨텍스트가 모른다 | id가 없다(보통) |
| **영속 (managed)** | 영속성 컨텍스트가 추적 중이다 | **필드를 바꾸면 flush 때 UPDATE가 나간다** |
| **준영속 (detached)** | 한때 영속이었거나 id는 있지만, 지금은 추적 대상이 아니다 | **필드를 바꿔도 아무 일도 일어나지 않는다** |
| 삭제 (removed) | 삭제 예약된 상태 | flush 시점에 DELETE가 나간다 |

**영속성 컨텍스트**란 트랜잭션 동안 엔티티를 담아 추적하는 메모리 공간이다. 여기에 들어 있는 동안만 "내가 이 객체를 바꾸면 DB에 반영된다"가 성립한다. 자세한 구조는 [영속성 컨텍스트와 변경 감지](02-persistence-context-dirty-checking.md) 문서에 있다.

주목할 것은 **영속과 준영속의 차이가 "객체 자체"에는 없다**는 점이다. 같은 클래스, 같은 필드값을 가진 객체 두 개가 있을 때 하나는 영속이고 하나는 준영속일 수 있다. 차이는 **영속성 컨텍스트가 그 인스턴스를 자기 1차 캐시에 담고 있느냐**뿐이다. 객체를 아무리 들여다봐도 자기가 어느 상태인지 알 수 없다는 것 — 이것이 이 주제가 헷갈리는 근본 이유다.

### 1-3. 준영속은 왜 생기는가 — 이 사고의 진짜 출발점

"준영속이 문제의 온상"이라는 말을 하기 전에, **준영속 상태가 왜 애초에 생기는지**를 먼저 봐야 한다. 경로가 셋이다.

**① 트랜잭션이 끝나서.** 이것이 가장 흔하다. Spring에서는 트랜잭션 하나가 영속성 컨텍스트 하나에 대응하므로, `@Transactional` 메서드가 끝나면 컨텍스트가 닫히고 그 안에 있던 엔티티들은 전부 준영속이 된다. 서비스에서 조회해 컨트롤러로 리턴한 엔티티는 이미 준영속이다. 그 객체의 필드를 컨트롤러에서 바꿔봐야 아무 일도 일어나지 않는다.

**② 컨텍스트에서 명시적으로 떼어내서.** `em.detach(entity)`는 그 하나를, `em.clear()`는 전부를 준영속으로 만든다. 벌크 연산 뒤에 `clear()`를 부르라고 하는 것이 이 경우다.

**③ 애초에 컨텍스트를 거친 적이 없어서.** 이것이 이 문서가 다루는 사고의 경로다. 컨트롤러에서 요청 DTO를 받아 `new Member()`로 객체를 만들고 거기에 id를 채워 넣으면, 그 객체는 **비영속처럼 보이지만 JPA 입장에서는 "id가 있는 낯선 객체"**다.

```java
// 이 객체는 무엇인가?
Member member = new Member();   // 방금 new 했으니 비영속처럼 보이는데,
member.setId(1L);               // id가 있으니 DB에 이미 존재하는 행을 가리킨다.
member.setName("홍길동");
// JPA는 이 객체를 추적한 적이 없다. "1번 회원"을 뜻하지만 컨텍스트와 연결돼 있지 않다.
```

세 경로 모두 결론은 같다. **DB에 반영하려면 어떻게든 영속 상태와 연결해야 하고, 그 연결 작업이 바로 `merge`다.** 그리고 `merge`가 그 연결을 어떻게 수행하는지가 2절의 내용이다.

### 1-4. 변경 감지 — "무엇이 바뀌었는지 계산한다"

영속 상태 엔티티를 고치는 정상 경로다.

```java
@Transactional
public void changeContact(Long id, String name, String phone) {
    Member member = memberRepository.findById(id).orElseThrow();  // ① SELECT → 영속 상태
    member.setName(name);                                          // ② 필드만 변경
    member.setPhone(phone);
    // ③ save() 호출 없음 — 커밋 시점에 flush가 알아서 UPDATE를 만든다
}
```

일어나는 일을 순서대로 보면 이렇다.

1. `findById`가 DB에서 읽어오면서 **그 시점의 필드값 복사본(스냅샷)**을 따로 보관한다.
2. `setName`/`setPhone`은 **엔티티 인스턴스 자체**를 바꾼다. 스냅샷은 그대로 남는다.
3. 커밋 직전 flush에서 **인스턴스와 스냅샷을 필드별로 비교**해 달라진 것을 찾아낸다.
4. 달라진 게 있으면 UPDATE를 만든다.

핵심은 3번이다. **JPA는 "무엇이 바뀌었는지"를 알고 있다** — 정확히는 계산해서 알아낸다. 스냅샷이라는 기준선이 있기 때문에 가능한 일이다.

```text
                 스냅샷(조회 시점)          인스턴스(커밋 시점)      판정
  name          "김철수"          vs      "홍길동"          →   변경됨
  phone         "010-0000-0000"  vs      "010-1111-2222"  →   변경됨
  email         "a@x.com"        vs      "a@x.com"        →   그대로
  grade         "GOLD"           vs      "GOLD"           →   그대로
  point         12000            vs      12000            →   그대로
  ...
```

`name`과 `phone`만 손댔으니 나머지 필드는 스냅샷과 동일하고, 따라서 "변경되지 않았다"고 판정된다. **손대지 않은 값이 살아남는 이유가 여기에 있다.**

### 1-5. 미리 짚어둘 것 — UPDATE 문에는 원래 전 컬럼이 들어간다

여기서 오해가 하나 생기기 쉬우니 미리 정리한다. 기본 설정에서 Hibernate가 만드는 UPDATE 문의 `SET` 절에는 **변경된 컬럼만이 아니라 전 컬럼이 들어간다.**

```sql
-- name, phone만 바꿨는데도 SET 절에는 전 컬럼이 나열된다
update member set name=?, phone=?, email=?, address=?, grade=?, point=?, ... where id=?
```

왜 이렇게 하는가. **UPDATE 문의 모양을 엔티티마다 하나로 고정해 두면 매번 SQL 문자열을 다시 만들 필요가 없고, DB 쪽의 실행 계획 캐시에도 유리하기 때문**이다.

그렇다면 손대지 않은 컬럼은 어떻게 되는가. **스냅샷과 같은 값, 즉 원래 그 컬럼에 있던 값이 그대로 실린다.** 그러므로 결과는 바뀌지 않는다. `email=?`가 SQL에 있어도 그 자리에 들어가는 값은 DB에 원래 있던 `a@x.com`이다.

이 구분 — **"SQL에 컬럼이 실린다"와 "값이 바뀐다"는 다른 문제** — 가 3-2에서 `@DynamicUpdate` 오해를 푸는 열쇠가 된다.

## 2. merge — 무엇이 바뀌었는지 모르니 전부 덮는다

### 2-1. 동작 다섯 단계

준영속 객체를 넘겼을 때 일어나는 일이다.

```java
Member detached = new Member();
detached.setId(1L);
detached.setName("홍길동");
detached.setPhone("010-1111-2222");

Member managed = em.merge(detached);
```

1. **id로 1차 캐시를 찾는다.** 없으면 **DB에서 SELECT**한다. 즉 `merge`는 항상 조회가 선행된다.
2. **DB에도 행이 없으면** 새 엔티티를 만들어 **INSERT 경로**로 간다(flush 시점에 INSERT). `merge`는 "수정"만이 아니라 "없으면 삽입"까지 한다는 뜻이다.
3. 찾아온 **영속 엔티티에 넘어온 객체의 모든 필드를 복사한다.** 여기가 전부다.
4. **그 영속 엔티티를 반환한다.** 넘긴 `detached`는 **끝까지 준영속으로 남는다.**
5. flush 시점에 변경 감지가 돌아 UPDATE를 만든다.

3단계에 주목하자. `merge`는 넘어온 객체의 어느 필드가 "사용자가 의도적으로 바꾼 값"이고 어느 필드가 "그냥 안 채운 값"인지 **구분할 수단이 없다.** 넘어온 것은 자바 객체 하나이고, 거기에는 "이 필드는 건드리지 마세요"라는 표시를 담을 자리가 없다. 그래서 **전부 덮는다.**

1-4의 변경 감지와 정확히 대비된다. 변경 감지에는 **스냅샷이라는 기준선**이 있어서 무엇이 바뀌었는지 계산할 수 있었다. `merge`에게는 그 기준선이 없다 — 넘어온 객체는 언제 어디서 만들어졌는지 알 수 없는 물건이기 때문이다.

### 2-2. 그래서 사고가 난다 — 누락된 필드가 null로 덮인다

회원 엔티티에 필드가 10개 있고, 수정 화면은 이름과 전화번호 2개만 보낸다고 하자. 흔한 요구사항이다.

```java
// before — 조용한 데이터 유실
@Transactional
public void updateMember(MemberUpdateRequest request) {
    Member member = new Member();                 // ① 비어 있는 객체를 만든다
    member.setId(request.getId());                // ② id를 채운다 → "1번 회원"을 가리키게 된다
    member.setName(request.getName());            // ③ 요청에 온 두 필드만 채운다
    member.setPhone(request.getPhone());
    // ④ 나머지 8개 필드는 자바 기본값 그대로다 — 참조 타입이므로 전부 null이다
    memberRepository.save(member);                // ⑤ id가 있으므로 내부에서 merge가 호출된다
}
```

④번 주석이 이 사고의 전부다. `email`, `address`, `grade`, `point`는 **"안 건드리겠다"는 의미로 비워둔 것인데, 자바 객체 안에서 그것은 `null`이라는 값**이다. 그리고 `merge`는 그 `null`을 "사용자가 이 필드를 비우겠다는 의도"와 구분하지 못한다.

실행되는 SQL은 이렇다.

```sql
-- ① merge가 먼저 읽는다 (1차 캐시에 없으므로 DB에서)
select m.id, m.name, m.phone, m.email, m.address, m.birth_date,
       m.grade, m.point, m.created_at, m.updated_at
  from member m where m.id = 1;

-- ② 읽어온 영속 엔티티에 넘어온 객체의 전 필드를 복사한 뒤 flush
update member
   set name       = '홍길동',
       phone      = '010-1111-2222',
       email      = null,       -- 유실: 원래 a@x.com 이었다
       address    = null,       -- 유실
       birth_date = null,       -- 유실
       grade      = null,       -- 유실: 원래 GOLD 였다
       point      = null,       -- 유실: 원래 12000 이었다
       created_at = null,       -- 유실
       updated_at = null        -- 유실
 where id = 1;
```

DB 행이 어떻게 되는지 나란히 놓으면 피해가 분명해진다.

```text
컬럼          실행 전                실행 후          비고
────────────────────────────────────────────────────────────────
id            1                     1
name          "김철수"               "홍길동"          의도한 변경
phone         "010-0000-0000"       "010-1111-2222"  의도한 변경
email         "a@x.com"             null             의도한 적 없음
address       "서울시 ..."           null             의도한 적 없음
birth_date    1990-01-01            null             의도한 적 없음
grade         "GOLD"                null             등급 소실
point         12000                 null             포인트 소실
created_at    2023-05-01 10:00      null             가입 이력 소실
updated_at    2024-11-02 14:31      null
```

**예외가 나지 않는다.** 트랜잭션은 정상 커밋되고, HTTP 응답은 200이고, 애플리케이션 로그에는 아무 이상이 없다. `NOT NULL` 제약이 걸린 컬럼이 하나라도 있었다면 그나마 예외로 드러났겠지만, nullable한 컬럼들은 조용히 비워진다. 등급과 포인트가 사라지고, 며칠 뒤 고객센터로 문의가 들어온다.

고치는 방법은 하나뿐이다. **조회해서 영속 상태로 만든 뒤, 필요한 필드만 바꾼다.**

```java
// after — 조회 후 필요한 필드만
@Transactional
public void updateMember(MemberUpdateRequest request) {
    // 조회해 온 이 객체는 영속 상태다. 나머지 8개 필드에는 DB의 실제 값이 들어 있다.
    Member member = memberRepository.findById(request.getId())
            .orElseThrow(() -> new MemberNotFoundException(request.getId()));
    // 바꿀 두 필드만 건드린다. 나머지는 스냅샷과 같은 값이므로 "변경 없음"으로 판정된다.
    member.changeContact(request.getName(), request.getPhone());
    // save() 호출 불필요 — 변경 감지가 처리한다
}
```

```java
// 엔티티: setter를 열지 않고 "바뀔 수 있는 것"을 메서드로 고정한다
public class Member {
    public void changeContact(String name, String phone) {
        this.name = name;
        this.phone = phone;
    }
}
```

`setName`/`setPhone`을 public setter로 열어두면 다음 사람이 또 전체를 만진다. **변경 가능한 범위를 메서드 시그니처로 고정하는 것**이 이 사고를 구조적으로 막는 방법이다. 사고 예방을 사람의 주의력이 아니라 컴파일러에게 맡기는 것이기 때문이다. (가산점 포인트)

### 2-3. 두 방식을 나란히 놓으면

| | 변경 감지 | `merge` |
|---|---|---|
| 출발점 | **영속** 엔티티 | **준영속** 객체 |
| "무엇이 바뀌었나" | 스냅샷과 비교해 **계산** | **모른다 → 전부 덮는다** |
| 기준선 | 조회 시점의 스냅샷이 있다 | 없다 |
| 안 건드린 필드 | 스냅샷과 같으므로 값이 유지된다 | **넘어온 값(주로 `null`)으로 덮인다** |
| 선행 SELECT | 이미 조회한 상태 | **항상 발생**(1차 캐시에 없으면) |
| 반환값 | 없음 (그 객체가 곧 영속) | **새 영속 인스턴스** |

**한 문장으로 정리하면 이렇다.** `merge`도 결국 변경 감지를 탄다. 다만 **덮어쓰기가 이미 끝난 상태로** 타기 때문에, 변경 감지는 `null`을 "정당한 변경"으로 인식한다. **변경 감지가 잘못된 게 아니라 입력이 이미 오염된 것이다.**

이 문장이 왜 중요한가. "변경 감지를 끄면 되나요" 같은 잘못된 방향의 처방을 막아주기 때문이다. 문제는 감지 단계가 아니라 그 앞의 복사 단계에 있다.

### 2-4. 방아쇠 — `save()`는 id 유무로 갈린다

이 사고의 출발점은 **`merge`를 직접 호출한 적이 없다는 점**이다. 2-2의 코드 어디에도 `merge`라는 글자가 없다. `repository.save()`를 썼을 뿐이다.

```java
// Spring Data JPA — SimpleJpaRepository
@Transactional
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
        entityManager.persist(entity);   // 신규 → INSERT
        return entity;
    } else {
        return entityManager.merge(entity);   // 신규가 아니면 → merge
    }
}
```

`save()`는 **INSERT 전용 메서드가 아니다.** 이름 때문에 "저장한다"로만 읽히지만 실제로는 "신규인가?"를 판정해 두 갈래로 나뉘는 분기문이다. 그리고 그 판정 기준을 개발자가 모르면, 어느 갈래로 갈지도 모르는 채 코드를 쓰게 된다.

### 2-5. `isNew()`는 무엇을 보고 판정하는가

기본 판정(`AbstractEntityInformation`)은 **id를 본다.**

- id 타입이 **래퍼 타입**(`Long`, `String` 등)이면 → `id == null`일 때 신규
- id 타입이 **원시 타입**(`long`, `int`)이면 → `0`일 때 신규

그런데 **`@Version` 필드가 있으면 판정 기준이 바뀐다**(`JpaMetamodelEntityInformation`). 버전 속성이 있고 그 타입이 원시 타입이 아니면, **id가 아니라 버전 필드가 `null`인지**로 신규를 판정한다. 낙관적 락을 쓰는 엔티티에서 "id를 채웠는데도 `persist`가 불렸다"는 현상이 여기서 나온다.

반대 방향의 문제도 있다. UUID처럼 **애플리케이션이 id를 미리 만들어 넣는** 전략에서는 신규 엔티티인데도 id가 항상 채워져 있으므로 기본 판정이 "신규가 아니다"로 오판한다. 그러면 진짜 신규 저장인데도 `merge`로 가서 **불필요한 SELECT가 매번 나간다.** 이때는 `Persistable<ID>` 인터페이스를 구현해 `isNew()`를 직접 정의하는 것이 정석이다. (가산점 포인트)

> 확인 범위: `save()`와 `isNew()`의 분기 구조는 Spring Data JPA의 공개된 구현으로 널리 알려진 내용이다. 다만 세부 클래스명과 판정 순서는 버전에 따라 변동이 있을 수 있으므로, 팀에서 쓰는 버전의 `SimpleJpaRepository`·`JpaMetamodelEntityInformation`을 직접 열어 확인하는 것을 권한다.

### 2-6. "id를 채워서 save 하면 중복 에러가 나지 않나요?"

**나지 않는다.** 그리고 이 오해가 위험한 이유는 **오해의 방향** 때문이다.

"에러가 날 것"이라고 믿는 사람은 그 코드를 **안전하다고 판단한다.** 잘못됐으면 터질 테니 안 터지면 맞는 것이라고 생각하는 것이다. 실제로는 에러가 나지 않고 UPDATE가 조용히 성공한다.

**사고는 예외가 날 때 나는 게 아니라 조용히 성공할 때 난다.** 이 문서의 사고가 발견까지 며칠씩 걸리는 이유가 정확히 이것이다.

## 3. 처방 — 남은 함정 셋과, `merge`가 정당한 자리

### 3-1. 함정 ① 반환값을 버리면 아무 일도 일어나지 않는다

```java
// before
Member member = new Member();
member.setId(1L);
memberRepository.save(member);
member.setName("변경");        // member는 여전히 준영속 — 이 변경은 어디에도 반영되지 않는다

// after
Member managed = memberRepository.save(member);   // 반환된 것이 영속 인스턴스다
managed.setName("변경");                            // 이것만 반영된다
```

1-1의 다이어그램에서 확인한 그대로다. **`merge`는 넘긴 객체를 영속 상태로 만들지 않는다.** 새 인스턴스를 만들어 값을 복사하고 그것을 반환한다. 넘긴 객체는 화살표의 출발점에 그대로 남아 있다.

"수정이 반영되지 않는다"는 문의의 상당수가 이것이다. 그리고 이 함정도 예외를 내지 않는다.

### 3-2. 함정 ② `@DynamicUpdate`로는 막을 수 없다

`@DynamicUpdate`는 **변경된 컬럼만 `SET` 절에 넣도록** 만드는 옵션이다. 1-5에서 본 "SET 절에 전 컬럼이 들어간다"는 기본 동작을 바꾸는 것이다. 그러니 이름만 보면 `null` 덮어쓰기를 막아줄 것처럼 보인다. **막지 못한다.**

이유는 단순하다. `merge`가 `email`을 `null`로 덮은 시점에 **그 필드는 실제로 변경된 것**이다(`a@x.com` → `null`). 변경 감지는 이것을 정당한 변경으로 판정하고, `@DynamicUpdate`는 "변경된 컬럼"을 넣으라는 옵션이므로 `email = null`을 **정확히 포함시킨다.**

```sql
-- @DynamicUpdate 적용 후에도
update member set name=?, phone=?, email=null, address=null, ... where id=?
--                                 ^^^^^^^^^^ 여전히 나간다
```

`@DynamicUpdate`가 줄여주는 것은 **"안 바뀐 컬럼"**이다. 그런데 `merge` 사고에서는 안 바뀐 컬럼이 없다 — 전부 바뀌었기 때문이다. 줄일 대상이 애초에 존재하지 않는다.

1-5에서 미리 구분해 둔 것이 여기서 쓰인다. **"SQL에 컬럼이 실리느냐"와 "값이 바뀌느냐"는 다른 문제**이고, `@DynamicUpdate`는 앞쪽만 건드린다. 흔한 오해이므로 면접에서 반대로 짚으면 가산점이다.

### 3-3. 함정 ③ 연관관계와 cascade가 얽히면 컬렉션이 통째로 사라질 수 있다

`merge`는 `CascadeType.MERGE`(또는 `ALL`)가 설정된 연관에만 전파된다. 문제는 그 전파가 **컬렉션까지 덮는다**는 점이다.

```java
// 위험한 조합
@OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
private List<OrderItem> items = new ArrayList<>();
```

요청 DTO로부터 `new Order()`를 만들면 `items`는 **빈 `ArrayList`**다. 필드 초기화식이 그렇게 돼 있기 때문이다. 이 객체를 `merge`하면 벌어지는 일이 이렇다.

```text
DB 상태            주문 1번, 항목 3건
넘긴 객체          new Order(id=1), items = []   ← 비어 있는 리스트
merge 3단계        영속 엔티티의 items 컬렉션을 빈 컬렉션으로 덮는다
orphanRemoval      "컬렉션에서 빠진 자식은 삭제한다"는 규칙이 발동한다
결과               delete from order_item where order_id = 1  → 항목 3건 전부 DELETE
```

`orphanRemoval = true`는 원래 "부모의 컬렉션에서 뺀 자식은 고아이므로 지운다"는 편리한 옵션이다. 그런데 `merge`가 컬렉션을 통째로 비워 놓으면 **모든 자식이 고아로 판정된다.**

정상 경로(조회 후 필요한 것만 수정)를 쓰면 이 문제가 애초에 생기지 않는다. 조회해 온 `Order`의 `items`에는 실제 3건이 들어 있기 때문이다. `merge`를 피하는 근거가 하나 더 늘어나는 셈이다.

> 확인 범위: cascade·orphanRemoval과 `merge`의 상호작용은 매핑 설정과 컬렉션의 초기화 상태(빈 컬렉션인지 미초기화 프록시인지)에 따라 결과가 갈린다. 위 시나리오는 "DTO에서 새로 만든 엔티티의 컬렉션은 빈 `ArrayList`"인 경우를 전제한 것이다. 실제 프로젝트에서는 반드시 쿼리 로그로 DELETE가 나가는지 직접 확인할 것.

### 3-4. 그래서 `merge`가 정당한 자리는 어디인가

거의 없다. 정확히는 **"넘어온 값으로 전부 덮는 것이 곧 요구사항인 경우"**뿐이다.

**재부착(reattach)**이 그 자리다. 세션이나 캐시에 엔티티를 통째로 보관해 두었다가 꺼내 쓰거나, 원격 호출로 엔티티의 전체 상태를 받아온 뒤 다시 영속 상태로 붙이는 상황을 말한다. 이때는 **"받은 것이 전체다"라는 전제가 실제로 참**이므로, 전부 덮는 동작이 요구사항과 정확히 일치한다.

그 외에는 전부 조회 후 변경 감지가 맞다.

### 3-5. "그래도 값을 전부 바꿔야 할 때는 merge가 맞지 않나요?"

그조차 안전하지 않다. 이유는 `merge`가 **두 가지 `null`을 구분할 수 없다**는 데 있다.

| 클라이언트의 의도 | 요청에 담긴 값 |
|---|---|
| "이 필드는 안 건드릴게" | 필드가 아예 없거나 `null` |
| "이 필드를 비워줘" | `null` |

`merge`에게는 둘 다 똑같은 `null`이다. 즉 **`merge`로는 PATCH 시맨틱을 구현할 수 없다.** PATCH 시맨틱이란 "요청에 온 필드만 부분 수정하고 나머지는 건드리지 않는다"는 HTTP PATCH의 의미론을 말한다. 부분 수정 API를 만들 때 이 구분이 곧 요구사항이 되고, 그래서 실무에서는 DTO로 받아 "온 것만 적용"하는 코드를 직접 쓴다.

```java
// PATCH — "온 것만 적용"을 명시적으로 표현한다
@Transactional
public void patchMember(Long id, MemberPatchRequest request) {
    Member member = memberRepository.findById(id).orElseThrow();
    // null이면 "안 보냈다"로 해석해 건너뛴다. merge가 못 하는 판단을 여기서 사람이 한다.
    if (request.getName() != null)  member.changeName(request.getName());
    if (request.getPhone() != null) member.changePhone(request.getPhone());
    // "비워달라"까지 표현해야 하면 Optional<T>나 JsonNullable 같은 3-상태 타입을 쓴다.
    // 값 있음 / 명시적 null / 필드 없음 — 세 상태를 구분할 수 있는 타입이어야 한다.
}
```

### 3-6. 부수 비용 — `merge`는 조회를 한 번 더 유발한다

`merge`는 **항상 SELECT가 선행된다**(1차 캐시에 없으면). 2-1의 1단계다. 건별 수정이 많은 배치에서는 이 조회 쿼리가 그대로 배로 붙는다.

반면 변경 감지 경로는 어차피 조회를 하고 **그 조회해 온 객체를 그대로 쓰므로** 추가 조회가 없다. 즉 "`merge`가 조회를 아껴준다"는 인상은 사실과 반대다.

## 4. 꼬리질문 대비 포인트

### "`save()`를 호출하지 않았는데 UPDATE가 나갔습니다. 왜죠?"

영속 상태 엔티티의 필드를 바꿨기 때문이다. 영속성 컨텍스트가 스냅샷과 비교해 변경을 찾아내고 flush 시점에 UPDATE를 만든다.

`save()`는 **비영속 객체를 영속화하거나 준영속 객체를 병합할 때** 필요한 것이고, 이미 영속 상태인 엔티티에는 불필요하다. 1-1의 다이어그램에서 이미 "영속" 박스 안에 있는 객체에게 화살표를 한 번 더 그을 필요가 없는 것과 같다.

반대로 조회 전용 트랜잭션에서 의도치 않은 UPDATE가 나가는 문제는 [영속성 컨텍스트와 변경 감지](02-persistence-context-dirty-checking.md)의 진단 절차를 쓴다.

### "그럼 `save()`는 언제 호출해야 하나요?"

**신규 저장**(비영속 → 영속)에만 필요하다.

수정 로직에서 `save()`를 부르는 코드는 대개 둘 중 하나다. ① 습관적으로 붙였고 실제로는 아무 효과가 없다 — 이미 영속 상태라 `merge`가 같은 인스턴스를 찾아 반환한다. ② 준영속 객체를 넘기고 있어서 위험하다 — 2-2의 사고다.

후자를 걸러내는 리뷰 포인트는 하나다. **`save()`의 인자가 `new`로 만든 객체인가, 조회해 온 객체인가.** 인자를 따라 올라가 보면 5초 안에 판별된다.

### "`merge` 대신 `find` + setter를 쓰면 SELECT가 한 번 더 나가서 손해 아닌가요?"

**아니다.** `merge`도 내부에서 SELECT를 한다(2-1의 1단계). 쿼리 수는 같고, `find` + setter 쪽이 **의도가 코드에 드러난다**는 이점이 있다.

오히려 `merge`가 불리한 경우도 있다. `getReferenceById`로 프록시만 얻어 필드 하나만 바꾸는 최적화가 가능한데(SELECT 없이 UPDATE만 나갈 수 있다), `merge`는 값을 복사해야 하므로 반드시 실체를 읽어야 한다 — **그 선택지를 없앤다.**

### "엔티티에 setter를 열지 말라는 말은 자주 듣는데, 이 사고와 무슨 관계인가요?" (시니어 변별 포인트)

관계가 직접적이다. 이 사고의 본질은 **"바뀌어도 되는 필드"와 "바뀌면 안 되는 필드"가 코드에 표현되어 있지 않다**는 것이다.

setter가 전부 열려 있으면 `merge`가 전부 덮는 것을 문법적으로 막을 수 없고, 리뷰에서 사람이 눈으로 찾아야 한다. 반면 `member.changeContact(name, phone)` 같은 도메인 메서드만 열어두면 "연락처 변경"이라는 연산의 범위가 타입으로 고정되고, 그 밖의 필드를 건드리는 코드는 **컴파일되지 않는다.**

사고 예방을 사람의 주의력에서 타입 시스템으로 옮기는 것 — 이게 "setter를 닫아라"의 실제 값이다. "캡슐화가 좋으니까"라고 답하는 것과는 설득력이 다르다.

### "그럼 `merge`는 왜 JPA 명세에 있는 건가요?" (시니어 변별 포인트)

`merge`는 **분리된 계층 사이에서 엔티티가 오갔던 시대의 도구**다.

원격 호출로 엔티티를 직렬화해 보내고 받아서 다시 붙이는(detach → 전송 → reattach) 구조에서는 "받은 것이 전체 상태"라는 전제가 실제로 참이었고, 그때 `merge`는 정확히 필요한 연산이었다. 3-4에서 본 유일한 정당한 자리가 그것이다.

지금은 계층 간에 DTO를 주고받고 엔티티는 트랜잭션 안에 머무르는 구조가 표준이 되어 그 전제가 깨졌다. 즉 **`merge`는 잘못된 API가 아니라 전제가 달라진 API**다.

이렇게 답하면 "왜 쓰지 말라는지"를 금기가 아니라 원리로 이해하고 있음을 보일 수 있다.

## 한 줄 요약

변경 감지는 **조회 시점의 스냅샷이라는 기준선이 있어 무엇이 바뀌었는지 계산해 그것만 고치고**, `merge`는 **그 기준선이 없어 무엇이 바뀌었는지 모르니 넘어온 객체로 전부 덮는다** — 그래서 `new` 엔티티에 id만 채워 `save()`하면(Spring Data의 `save()`는 id 유무로 `persist`와 `merge`로 갈린다) 예외도 경고도 없이 나머지 컬럼이 `null`이 되고, `@DynamicUpdate`로도 막히지 않으며, cascade가 걸려 있으면 자식 컬렉션까지 지워진다. 처방은 언제나 **"조회해서 영속 상태로 만든 뒤 필요한 필드만 바꾸기"**이고, 그 범위를 도메인 메서드로 고정해 컴파일러가 지키게 하는 것이 상위 처방이다.
