# 연관관계의 주인과 mappedBy — 참조는 둘, FK는 하나

> 핵심 관전 포인트: **객체 세계에서 양방향 연관은 참조가 두 개지만, 테이블 세계에는 FK가 하나뿐이다. 이 비대칭 때문에 두 참조가 어긋났을 때 어느 쪽을 따를지 정해야 하고, 그 기준이 연관관계의 주인이다. 주인은 FK를 가진 쪽이고 다대일 관계에서는 항상 다(N)쪽이다. `mappedBy`는 "나는 주인이 아니고 상대의 이 필드가 FK를 관리한다"는 읽기 전용 선언이며, 그래서 `team.getMembers().add(member)`만 하고 커밋하면 UPDATE가 한 줄도 나가지 않고 FK는 `null`로 남는다. 여기서 한 층 더 들어가면 — 연관관계 편의 메서드가 필요한 진짜 이유는 DB가 아니라 1차 캐시다. 주인만 세팅하면 DB의 FK는 정확히 갱신되지만, 같은 트랜잭션에서 이미 로딩된 컬렉션은 갱신 전 상태로 남아 "DB는 맞는데 화면은 틀린" 현상이 난다. 그리고 양방향을 둘지 말지의 판단 축은 "조회가 편한가"가 아니라 "생명주기를 공유하는가"다.**

---

## 0. 질문 + 의도

**질문**: "연관관계의 주인(owner)이란? `mappedBy`는 왜 필요한가요?"

**출제 의도**: FK 갱신이 "왜 안 되는지" 헤매는 신입 단골 이슈. 이걸 명확히 설명하면 JPA 매핑을 눈감고도 다루는 수준임을 시사한다.

**함정**: 정의를 맞히는 것으로는 부족하다. 이 질문의 변별력은 두 곳에 있다 — ① **왜 주인이라는 개념이 애초에 필요한가**(설계 의도) ② **양방향을 쓸지 말지를 무엇으로 판단하는가**(설계 판단). "보통 단방향으로 씁니다"에서 멈추면 근거 없는 관례로 들린다.

## 1. 원리 — 개수가 안 맞아서 주인이 필요해진다

### 1-1. 두 세계를 나란히 놓고 본다

이 문서 전체가 딱 하나의 비대칭에서 나온다. **객체는 관계를 참조 두 개로 표현하는데, 테이블은 컬럼 하나로 표현한다.** 문장으로 읽으면 당연해 보이지만, 그림으로 보면 왜 문제가 되는지가 눈에 들어온다.

`Team`과 `Member`를 양방향으로 매핑했다고 하자.

```text
            객체 세계 (메모리)                          테이블 세계 (DB)
   ───────────────────────────────────      ───────────────────────────────────

    ┌─────────────────────┐                   team
    │       Team          │                   ┌──────┬─────────┐
    │  id = 1             │                   │  id  │  name   │
    │  name = "개발팀"     │                   ├──────┼─────────┤
    │  members ●──────────┼──── 참조 ①         │   1  │ 개발팀   │
    └─────────────────────┘        │           └──────┴─────────┘
              ▲                    │
              │                    ▼
              │ 참조 ②          [ Member, Member, ... ]
              │
    ┌─────────┴───────────┐                   member
    │      Member         │                   ┌──────┬─────────┬───────────┐
    │  id = 10            │                   │  id  │  name   │  team_id  │
    │  name = "홍길동"     │                   ├──────┼─────────┼───────────┤
    │  team ●─────────────┘                   │  10  │ 홍길동   │     1     │
    └─────────────────────┘                   └──────┴─────────┴───────────┘
                                                                     ▲
                                                                     │
    관계를 표현하는 것: 참조 2개                 관계를 표현하는 것: 컬럼 1개
    Team.members  와  Member.team                        member.team_id
```

오른쪽 표에서 `team` 테이블을 보면 관계에 대한 정보가 **아무것도 없다.** 팀이 어떤 멤버를 갖는지는 `member.team_id`를 거꾸로 읽어서(`WHERE team_id = 1`) 알아내는 것이지, 팀 쪽에 저장된 값이 아니다. **관계는 오직 `member.team_id` 컬럼 하나에만 적혀 있다.**

반면 왼쪽 객체 그래프에는 관계가 **두 군데에 따로 적혀 있다.** `Team.members` 리스트에도 있고 `Member.team` 필드에도 있다.

**2 대 1.** 여기서 문제가 시작된다.

### 1-2. 개수가 안 맞으면 무슨 일이 생기나

저장할 자리가 하나뿐인데 진술이 둘이면, 둘이 어긋났을 때 답이 없다.

```java
member.setTeam(teamA);              // 참조 ②의 주장: 이 멤버는 A팀 소속이다
teamB.getMembers().add(member);     // 참조 ①의 주장: 이 멤버는 B팀 소속이다

// 커밋 시점에 member.team_id 컬럼에 무엇을 넣어야 하는가?
// A팀의 id인가, B팀의 id인가?
```

컴파일러는 이 코드를 아무 불평 없이 통과시킨다. 자바 입장에서는 두 객체의 필드를 각각 바꾼 정상적인 코드이기 때문이다. 그러나 **DB에 옮겨 적는 순간 둘 중 하나는 버려야 한다.**

이런 상황을 프레임워크가 매번 "적당히" 처리하면 어떻게 될까. 두 참조를 모두 반영하려 하면 같은 컬럼에 UPDATE가 두 번 나가고, 어느 쪽이 나중에 나가느냐에 따라 결과가 달라진다. **호출 순서에 따라 결과가 바뀌는 비결정적 동작**이 되는 것이다. 테스트로 잡기도 어렵고, 운영에서 간헐적으로만 틀린다.

### 1-3. 그래서 "주인"은 편의 장치가 아니라 모호성 제거 장치다

JPA는 이 문제를 규칙 하나로 잘라 푼다. **한쪽만 FK를 관리한다.** 그 한쪽이 **연관관계의 주인(owner)**이고, 나머지 한쪽은 **읽기 전용**이 된다.

```text
   ┌──────────────────────────────────────────────────────────────┐
   │  Member.team      ──▶  주인이다.  이 필드의 값이 곧 team_id다.  │
   │  Team.members     ──▶  주인이 아니다. 읽기만 한다.              │
   │                        여기에 무엇을 넣든 DB는 반응하지 않는다.  │
   └──────────────────────────────────────────────────────────────┘
```

즉 주인 개념은 "이렇게 하면 편하다"는 편의 장치가 아니라, **애초에 결정 불가능한 상황을 결정 가능하게 만드는 장치**다. 왜 이런 개념이 있는지를 이렇게 설명할 수 있으면 정의를 외운 사람과 구분된다.

> 면접에서 이 답을 만들 때: "객체는 참조가 둘인데 테이블은 FK가 하나라서, 둘이 어긋났을 때 따를 기준이 필요합니다. 주인이 그 기준입니다." — 여기까지 말하면 정의를 외운 게 아니라 이유를 이해한 것으로 들린다.

## 2. 주인은 누구이고, `mappedBy`는 무엇을 하는가

### 2-1. 규칙 — FK 컬럼을 가진 쪽이 주인이다

**FK 컬럼이 있는 테이블에 매핑된 엔티티가 주인**이다. 그리고 다대일 관계에서 FK는 언제나 다(N)쪽 테이블에 있으므로, 결론이 하나로 정해진다.

왜 FK가 항상 다쪽에 있는가. 한 팀에 멤버가 100명이라면 팀 테이블의 컬럼 하나에 100개의 id를 넣을 수 없기 때문이다. 관계형 모델에서 "여러 개"를 표현하는 유일한 방법은 **행을 여러 개 두는 것**이고, 그러려면 참조를 여러 쪽이 들고 있어야 한다.

```java
class Team {
    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "team")          // 주인이 아니다. 읽기 전용이다
    private List<Member> members = new ArrayList<>();
}

class Member {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)     // 주인이다
    @JoinColumn(name = "team_id")          // 자기가 관리할 FK 컬럼을 직접 지정한다
    private Team team;
}
```

읽을 점이 셋이다.

**`@ManyToOne`이 붙은 쪽이 주인이고, `@OneToMany`가 `mappedBy`를 갖는다.** 다대일 관계에서 예외가 없다. 그래서 "주인이 누구냐"는 질문은 사실상 "FK가 어느 테이블에 있느냐"와 같은 질문이다.

**`mappedBy = "team"`의 `"team"`은 주인 엔티티의 필드 이름**이다. 컬럼 이름이 아니다. "내 반대편은 `Member.team` 필드이고, FK 관리는 그쪽이 한다"는 뜻이다. 필드명을 리팩터링할 때 이 문자열도 함께 바꿔야 한다는 뜻이기도 하다.

**`@ManyToOne`의 기본 로딩 전략은 EAGER**이므로 `fetch = LAZY`를 손으로 붙여야 한다. 붙이지 않으면 `Member`를 조회할 때마다 `Team`까지 조인해 읽어 온다. 이유와 대응은 [EAGER vs LAZY 기본 전략](03-eager-vs-lazy-fetch-strategy.md)에 있다.

### 2-2. 일대일은 규칙이 정해주지 않는다 — 설계 선택이다

1:1 관계에서는 FK를 어느 테이블에 둬도 관계가 성립한다. 양쪽 다 "하나"이므로 컬럼 하나로 표현할 수 있기 때문이다. 그래서 **주인이 규칙으로 정해지지 않고 설계자가 골라야 한다.**

- **주 테이블(예: `member`)에 FK를 두면** 조회가 잦은 쪽에서 조인 없이 접근할 수 있다. `member` 행만 읽어도 사물함 id를 알 수 있다.
- **대상 테이블(예: `locker`)에 FK를 두면** 나중에 1:N으로 바뀔 때 스키마 변경이 작다. 한 회원이 사물함을 여러 개 갖게 되어도 컬럼 구조를 바꿀 필요가 없다.

선택의 대가가 하나 더 있다. **주인이 아닌 쪽은 지연 로딩이 걸리지 않는다.** 이유는 이렇다. 지연 로딩은 진짜 객체 대신 프록시를 넣어두는 방식인데, 연관이 아예 없는 경우(`null`)에는 프록시가 아니라 `null`을 넣어야 한다. 그런데 FK가 상대 테이블에 있으면 **내 행만 읽어서는 상대가 존재하는지조차 알 수 없다.** 그래서 확인하러 SELECT를 나가게 되고, 결국 즉시 로딩이 된다. 자세한 내용은 [EAGER vs LAZY](03-eager-vs-lazy-fetch-strategy.md) 문서에 있다.

### 2-3. `mappedBy`가 하는 일 — "나는 읽기만 한다"는 선언

`mappedBy`는 "이 필드는 관계를 **읽기만** 한다"는 표시다. 더 정확히 말하면 **JPA에게 "이 컬렉션의 변경은 flush 대상에서 제외하라"고 지시하는 것**이다.

그래서 다음 코드는 아무 일도 하지 않는다.

```java
// before — FK가 갱신되지 않는다
@Transactional
public void joinTeam(Long teamId, Long memberId) {
    Team team = teamRepository.findById(teamId).orElseThrow();
    Member member = memberRepository.findById(memberId).orElseThrow();

    team.getMembers().add(member);   // 주인이 아닌 쪽만 변경했다
    // 커밋
}
```

### 2-4. 무엇이 안 나가는지를 로그로 확인한다

"반영이 안 된다"는 말은 추상적이다. **실제로 무슨 쿼리가 나가는지**를 보면 납득이 빠르다.

```text
-- 이 트랜잭션에서 실제로 실행되는 SQL 전부
select t.id, t.name
  from team t where t.id = 1;                              -- teamRepository.findById

select m.id, m.name, m.team_id
  from member m where m.id = 10;                           -- memberRepository.findById

-- team.getMembers().add(member) 실행
--   → 쿼리 없음. 메모리 안의 리스트에 원소가 하나 추가됐을 뿐이다.

-- 커밋 (flush)
--   → 쿼리 없음. UPDATE가 한 줄도 나가지 않는다.
```

트랜잭션이 끝난 뒤 DB를 직접 확인하면 이렇다.

```sql
select id, name, team_id from member where id = 10;
--  id | name   | team_id
--  10 | 홍길동  |  null     ← add() 호출 전과 완전히 동일하다
```

**예외도 경고도 로그 한 줄도 없다.** JPA는 `mappedBy`가 붙은 컬렉션의 변경을 flush 대상에서 아예 제외하기 때문에, 그 컬렉션에 무엇을 넣든 "할 일이 없다"고 판단한다. 신입이 반나절 헤매는 대표 지점이 여기다 — 로그를 켜도 나오는 게 없으니 무엇을 찾아야 할지조차 알 수 없다.

**진단의 핵심은 "무슨 쿼리가 잘못 나갔나"가 아니라 "나가야 할 쿼리가 안 나갔다"를 인지하는 것**이다. 이 관점 전환이 되면 곧바로 `mappedBy`를 의심하게 된다.

고침은 주인 쪽을 건드리는 것이다.

```java
// after — 주인 쪽을 세팅한다
@Transactional
public void joinTeam(Long teamId, Long memberId) {
    Team team = teamRepository.findById(teamId).orElseThrow();
    Member member = memberRepository.findById(memberId).orElseThrow();

    member.setTeam(team);   // 주인 쪽 → 이 필드가 곧 team_id 컬럼이다
}
```

```sql
-- 이제 커밋 시점에 UPDATE가 나간다
update member set team_id = 1 where id = 10;
```

### 2-5. `mappedBy`를 아예 빼면 어떻게 되는가

`@OneToMany`만 두고 `mappedBy`도 `@JoinColumn`도 쓰지 않으면, JPA는 이 관계를 **조인 테이블(`team_member` 같은 중간 테이블)**로 매핑한다.

이유를 생각해 보면 자연스럽다. `mappedBy`가 없다는 것은 "이 컬렉션이 관계를 관리한다"는 뜻인데, `Team` 쪽에는 관계를 적을 컬럼이 없다(1-1의 그림에서 본 대로다). 그러면 관계를 적을 자리를 **새로 만드는 수밖에 없고**, 그것이 중간 테이블이다.

그러므로 양방향을 만들면서 `mappedBy`를 빼먹으면 **테이블이 하나 더 생기는** 증상으로 드러난다. 스키마 자동 생성을 쓰는 개발 환경에서는 조용히 만들어지고, 운영 스키마와 달라지는 순간 문제가 된다.

`@OneToMany` + `@JoinColumn`(단방향, `mappedBy` 없음)이라는 조합도 가능하다. 이때 FK는 자식 테이블에 생기지만 **관리 주체는 부모**가 된다. 이 조합의 대가는 쿼리 수다.

```sql
-- 자식을 INSERT하는 시점에는 부모가 아직 자기 컬렉션을 처리하기 전이라 FK를 채우지 못한다
insert into member (id, name, team_id) values (?, ?, null);
-- 이후 부모 컬렉션 처리 단계에서 FK를 채우는 UPDATE가 별도로 나간다
update member set team_id = ? where id = ?;
```

INSERT 하나로 끝날 일이 INSERT + UPDATE가 된다. 자식이 100건이면 쿼리가 200번이다. 그래서 실무에서는 이 조합보다 **다대일 단방향** 또는 **양방향 + `mappedBy`**를 쓴다.

> 확인 범위: 조인 테이블 생성과 추가 UPDATE는 JPA/Hibernate의 오래된 표준 동작이다. 다만 구체적인 쿼리 순서와 개수는 배치 설정·id 생성 전략에 따라 달라질 수 있으므로, 실제 프로젝트에서는 쿼리 로그로 확인하는 것을 권한다.

## 3. 판단 — 편의 메서드의 진짜 이유, 그리고 양방향을 열지 말지

### 3-1. 흔한 설명이 왜 틀렸는가

여기가 이 주제에서 가장 자주 잘못 설명되는 부분이다.

흔한 설명은 **"양쪽 다 세팅해야 DB에 반영된다"**인데, **틀렸다.** 2-4에서 확인한 대로 주인만 세팅해도 `update member set team_id = 1`은 정확히 나간다. DB는 맞다.

그렇다면 왜 "양쪽을 세팅하라"는 관례가 있는가. 이유가 DB가 아니라 **메모리에 있기 때문**이다.

### 3-2. 증상 재현 — 같은 트랜잭션 안에서 숫자가 틀린다

```java
@Transactional
public void joinTeamAndCount(Long teamId, Long memberId) {
    Team team = teamRepository.findById(teamId).orElseThrow();
    int before = team.getMembers().size();   // ① 이 순간 컬렉션이 DB에서 로딩된다 (예: 3)

    Member member = memberRepository.findById(memberId).orElseThrow();
    member.setTeam(team);                    // ② 주인을 세팅했다 → FK는 정확히 갱신된다

    int after = team.getMembers().size();    // ③ 몇이 나올까?
}
```

`after`는 **여전히 3**이다. `4`가 아니다.

무슨 일이 벌어졌는지 시간순으로 펼치면 이렇다.

```text
시각   코드                                메모리(1차 캐시)                 DB
─────────────────────────────────────────────────────────────────────────────
t1    findById(teamId)                   Team#1 적재                     team_id: null
t2    team.getMembers().size()           members = [A, B, C]  ← 3건 로딩   (변화 없음)
t3    findById(memberId)                 Member#10 적재
t4    member.setTeam(team)               Member#10.team = Team#1          (아직 flush 전)
                                         Team#1.members 는 손대지 않았다  ← 핵심
t5    team.getMembers().size()           members = [A, B, C]  → 3         (변화 없음)
t6    커밋 (flush)                                                        update member
                                                                          set team_id=1
```

t4에 붙은 "핵심" 표시가 전부다. 바꾼 것은 `Member#10.team` 필드 하나이고, **이미 메모리에 올라와 있는 `Team#1.members` 리스트에는 아무도 손대지 않았다.** JPA가 알아서 리스트에 넣어주지 않는다 — 자바 객체의 필드를 대신 수정해 주는 기능은 없기 때문이다.

여기서 "다시 조회하면 되지 않나"라는 생각이 들 수 있는데, 그것도 안 된다. 같은 트랜잭션 안에서 `teamRepository.findById(teamId)`를 다시 불러도 **1차 캐시가 같은 인스턴스를 돌려주므로** 컬렉션도 그대로다. 1차 캐시가 여기서는 정확히 방해로 작용한다.

즉 **DB는 맞고 메모리는 틀린 상태**가 된다. 이 트랜잭션 안에서 그 컬렉션을 근거로 개수를 세거나 응답 DTO를 만들면 결과가 어긋난다. "DB를 직접 조회하면 맞는데 화면에는 안 보인다"는 문의가 여기서 나온다.

### 3-3. 처방 — 연관관계 편의 메서드

한쪽을 바꿀 때 반대쪽도 함께 맞춰 주는 메서드를 만들어 두는 것이 관례다. 이것을 **연관관계 편의 메서드**라고 부른다.

```java
// 주인 쪽 엔티티에 두는 것이 관례다
public class Member {
    public void setTeam(Team team) {
        // 팀을 옮기는 경우, 기존 팀의 컬렉션에서 자신을 먼저 빼야 한다.
        // 이걸 빠뜨리면 옛 팀의 members에 유령 멤버가 남는다.
        if (this.team != null) {
            this.team.getMembers().remove(this);
        }
        this.team = team;                    // ① FK를 관리하는 쪽 — DB를 위한 코드
        if (team != null) {
            team.getMembers().add(this);     // ② 객체 그래프 일관성 — 메모리를 위한 코드
        }
    }
}
```

**①이 DB를 위한 코드, ②가 메모리를 위한 코드**다. 목적이 서로 다르다는 것을 구분해서 말하면 이 개념을 이해한 것으로 들린다. ②를 빼도 DB는 멀쩡하고, ①을 빼면 DB가 안 바뀐다.

주의할 것이 하나 있다. 편의 메서드를 **양쪽 엔티티에 다 두면 안 된다.** `member.setTeam(team)`이 `team.getMembers().add(this)`를 부르고, `team.addMember(member)`가 다시 `member.setTeam(this)`를 부르면 서로를 무한히 호출하거나 컬렉션에 같은 원소가 두 번 들어간다. **한쪽에만 두고 팀 내에서 규칙으로 정하는 것**이 관례다.

### 3-4. 함정 — 편의 메서드는 `equals`/`hashCode`에 의존한다

편의 메서드 안의 `remove(this)`는 컬렉션을 훑어 **자기 자신과 같은 원소를 찾아야** 한다. "같다"의 판정은 `equals`가 한다. 그래서 엔티티의 `equals`/`hashCode` 구현이 여기에 영향을 준다.

- **id 기준으로 구현하면** → 아직 저장되지 않은 엔티티는 id가 `null`이라, 저장 전 객체들끼리 서로 같다고 판정되거나 컬렉션에서 자신을 찾지 못한다.
- **기본 구현(참조 동일성)을 쓰면** → 같은 트랜잭션 안에서는 1차 캐시가 동일 인스턴스를 보장하므로 대체로 동작한다. 하지만 트랜잭션을 넘나들면 인스턴스가 달라져 깨진다.

실무 해법은 **비즈니스 키(자연키)로 `equals`/`hashCode`를 구현**하거나, 컬렉션을 `Set` 대신 `List`로 두고 참조 동일성에 의존하는 것이다. 이 주제는 [엔티티의 equals와 hashCode](25-entity-equals-and-hashcode.md)에서 더 깊이 다룬다. (가산점 포인트)

### 3-5. 단방향이 기본값이어야 하는 이유

이제 설계 판단으로 넘어간다. 양방향에는 유지 비용이 붙는다.

**편의 메서드를 계속 관리해야 한다.** 연관이 하나 늘 때마다, 팀 이동 같은 케이스가 생길 때마다 손이 간다. 그리고 3-4에서 봤듯 `equals` 구현까지 딸려 온다.

**무한 순환 참조가 생긴다.** `Team → members → Member → team → members …`로 끝없이 이어지므로 JSON 직렬화, `toString()`, `equals()`에서 스택 오버플로가 난다. `@JsonIgnore`나 DTO 변환으로 막아야 하는데, **그 대응 자체가 양방향의 대가**다.

```java
// before — 엔티티를 그대로 응답으로 내보내면 순환 참조로 터진다
@GetMapping("/teams/{id}")
public Team getTeam(@PathVariable Long id) {
    return teamRepository.findById(id).orElseThrow();
}

// after — DTO로 끊는다. 변환 지점에서 순환이 잘린다
@GetMapping("/teams/{id}")
public TeamResponse getTeam(@PathVariable Long id) {
    return TeamResponse.from(teamRepository.findById(id).orElseThrow());
}
```

**테스트에서 양쪽 정합성을 신경 써야 한다.** 3-2에서 본 "FK는 맞는데 컬렉션이 안 맞는" 상태가 구조적으로 가능하므로 검증 지점이 늘어난다.

그리고 결정적으로, **양방향이 주는 이점 대부분은 리포지토리 쿼리로 대체된다.**

```java
// 팀 상세 화면의 소속 멤버 목록 — 양방향 매핑 없이도 충분히 얻을 수 있다
List<Member> members = memberRepository.findByTeamId(teamId);
```

즉 **"조회가 편해서" 양방향을 두는 것은 근거가 약하다.** 조회는 쿼리로 해결되기 때문이다. 근거가 약한 이유를 이렇게 말할 수 있어야 다음 절의 기준이 힘을 얻는다.

### 3-6. 그럼 언제 양방향인가 — 생명주기를 공유할 때

판단 축은 이것이다. **부모를 저장·삭제할 때 자식도 함께 저장·삭제되어야 하는가?**

**그렇다면** 둘은 같은 **Aggregate**(항상 함께 일관성을 유지해야 하는 하나의 덩어리)에 속한다. 이때는 `cascade`(부모의 영속화·삭제를 자식에게 전파)와 `orphanRemoval`(부모 컬렉션에서 빠진 자식을 삭제)이 의미를 갖는데, **그 옵션들을 쓰려면 부모가 자식 컬렉션을 들고 있어야 한다.** 즉 컬렉션이 필요한 이유가 조회가 아니라 생명주기 관리다. 예를 들어 `Order`와 `OrderItem`이 그렇다 — 주문 항목은 주문 없이 존재할 이유가 없고, 주문을 지우면 항목도 지워져야 한다.

**아니라면** 둘은 각자 독립적인 생명주기를 갖는다. 조회 요구가 있어도 쿼리로 푼다. `Member`와 `Team`이 그렇다 — 멤버를 지운다고 팀을 지우지 않고, 팀을 지운다고 멤버를 지우지 않는다.

```text
   부모를 지울 때 자식도 지워져야 하는가?
             │
      ┌──────┴──────┐
     예              아니오
      │                │
  같은 Aggregate     독립적 생명주기
  cascade / orphanRemoval 필요   조회는 쿼리로 해결
      │                │
  양방향(또는 최소한    단방향
  부모 → 자식 컬렉션)
      │                │
  예: Order ↔ OrderItem   예: Member → Team
```

> 면접에서 이렇게 답하면 근거가 선다: "기본은 단방향으로 둡니다. 양방향은 편의 메서드 유지·순환 참조 대응 같은 비용이 붙는데, 조회 요구는 대부분 리포지토리 쿼리로 해결되기 때문입니다. 양방향을 여는 기준은 조회 편의가 아니라 **생명주기를 공유하는지** — 부모를 지울 때 자식도 지워져야 하는 관계, 즉 cascade가 의미를 갖는 Aggregate 경계 안에서만 양방향을 둡니다."

## 4. 꼬리질문 대비 포인트

### "`team.getMembers().add(member)`만 했는데 왜 FK가 안 바뀌나요?"

`@OneToMany(mappedBy = ...)`가 붙은 필드는 **읽기 전용**이라 flush 대상에서 제외되기 때문이다. FK를 관리하는 것은 주인(`Member.team`)이므로 `member.setTeam(team)`을 호출해야 UPDATE가 나간다.

**예외도 경고도 로그도 없다는 점**이 이 버그의 특징이다. 잘못된 쿼리가 나가는 것이 아니라 나가야 할 쿼리가 안 나가는 것이므로, "무엇이 안 나갔는지"를 보는 관점으로 로그를 읽어야 발견된다.

### "그럼 주인이 아닌 쪽은 왜 매핑하나요? 없어도 되는 거 아닌가요?"

**없어도 된다 — 그게 단방향이다.** 매핑을 안 하면 컬렉션 필드가 없고, 3-2의 불일치도 애초에 생기지 않는다.

그럼에도 주인이 아닌 쪽을 매핑하는 이유는 둘이다. ① **객체 그래프를 따라가는 코드가 자연스러워진다**(`order.getItems()`). ② **`cascade`/`orphanRemoval`을 걸 수 있다** — 부모가 자식 컬렉션을 들고 있어야 생명주기를 함께 관리할 수 있기 때문이다.

이 두 이유가 없으면 매핑하지 않는 것이 낫다. 특히 ①만을 이유로 여는 것은 3-5에서 본 대로 근거가 약하다.

### "양쪽 다 FK를 관리하게 하면 안 되나요?" (설계 의도)

**두 참조가 어긋났을 때 어느 쪽을 따를지 결정할 수 없다.** 1-2에서 본 그대로다.

게다가 양쪽이 각자 갱신을 시도하면 같은 컬럼에 UPDATE가 중복으로 나가고, 어느 쪽이 나중에 나가느냐에 따라 결과가 달라지는 **비결정적 동작**이 된다. 테스트로도 잡히지 않고 운영에서 간헐적으로만 틀리는 종류의 버그다.

JPA는 이를 "주인 한쪽만 쓴다"는 규칙으로 원천 차단했다. **불일치를 잘 해결하는 대신 불일치가 발생할 수 없게 만든 것**이다.

### "편의 메서드를 안 쓰고 주인만 세팅하면 DB는 맞잖아요. 그래도 문제인가요?" (시니어 변별 포인트)

**DB는 맞다.** 이 전제를 먼저 인정하고 시작하는 것이 중요하다. 흔한 설명("양쪽 다 세팅해야 반영된다")이 틀렸다는 것을 알고 있다는 신호이기 때문이다.

문제는 **같은 트랜잭션 안의 메모리 상태**다. 컬렉션이 이미 로딩되어 1차 캐시에 올라와 있으면 그 리스트는 갱신 전 상태로 남고, 1차 캐시는 같은 트랜잭션에서 같은 인스턴스를 돌려주므로 다시 조회해도 고쳐지지 않는다. 그 컬렉션을 근거로 개수를 세거나 응답을 만들면 결과가 틀린다.

**"편의 메서드는 영속화를 위한 장치가 아니라 객체 그래프 일관성을 위한 장치"**라고 말할 수 있으면 이 개념을 정확히 이해한 것이다.

### "그럼 편의 메서드 없이도 안전하게 만드는 방법이 있나요?" (시니어 변별 포인트)

방향이 둘이다.

① **연관 변경의 진입점을 하나로 모은다.** 부모의 도메인 메서드(`order.addItem(item)`)만 공개하고 자식의 `setOrder`는 패키지 전용으로 닫는다. 진입점이 하나면 양쪽 세팅을 빠뜨릴 수가 없다. 3-4에서 본 대로 사람의 주의력이 아니라 접근 제어자가 지키게 만드는 것이다.

② **애초에 양방향을 두지 않는다.** 컬렉션이 없으면 불일치할 대상도 없다. 단방향 + 쿼리 조합이 가장 안전한 구성인 이유가 이것이다.

즉 **"편의 메서드를 잘 쓰자"보다 "불일치가 가능한 구조를 만들지 말자"가 상위 처방**이다. 이 순서로 답하면 도구가 아니라 구조로 사고한다는 인상을 준다.

### "다대다(`@ManyToMany`)는 주인을 어떻게 정하나요?"

`@ManyToMany`도 한쪽에 `mappedBy`를 두어 주인을 정한다. 여기까지는 다대일과 같다.

다만 **실무에서는 `@ManyToMany` 자체를 쓰지 않는 편이 정석**이다. 이유가 둘이다. ① 중간 테이블에 컬럼(가입 일시, 상태, 권한 등)을 추가할 수 없다 — 그런 요구는 반드시 생긴다. ② 컬렉션을 변경하면 중간 테이블의 관련 행이 전부 삭제되고 다시 삽입되는 동작이 있어, 항목 하나만 바꿔도 쿼리가 대량으로 나간다.

권장 구성은 **중간 엔티티를 명시적으로 만들어 `@ManyToOne` 두 개로 푸는 것**이다(`Member` ← `MemberTeam` → `Team`). 그러면 컬럼도 자유롭게 추가할 수 있고, 주인 문제도 다대일 두 개로 환원되어 자연히 사라진다. (가산점 포인트)

## 한 줄 요약

객체에는 참조가 둘, 테이블에는 FK가 하나 — 그 비대칭에서 "어느 쪽을 진실로 볼지"를 정하는 것이 연관관계의 주인(FK 컬럼을 가진 쪽, 다대일에서는 항상 다쪽)이고, `mappedBy`는 "나는 읽기만 한다"는 선언이라 그쪽 컬렉션을 아무리 건드려도 **UPDATE가 한 줄도 나가지 않는다.** 주인만 세팅하면 DB는 맞지만 1차 캐시에 이미 로딩된 컬렉션은 갱신 전 상태로 남으므로 편의 메서드가 필요하고(그 목적은 영속화가 아니라 객체 그래프 일관성이다), 양방향을 열지 말지는 조회 편의가 아니라 **생명주기를 공유하는지 — cascade가 의미를 갖는 Aggregate 경계인지**로 판단한다.
