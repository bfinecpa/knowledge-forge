# 방어적 복사와 컬렉션 노출 — 캡슐화는 참조 공유 수준에서 깨진다

> 핵심 관전 포인트: **방어적 복사는 가변 객체를 주고받을 때 복사본을
> 만들어 참조 공유를 끊는 기법이다. getter로 내부 컬렉션을 그대로
> 반환하면, 필드가 private이어도 외부가 그 참조로 `add/remove/clear`를
> 호출해 객체의 상태를 마음대로 바꿀 수 있다 — 도메인 객체가 생성자와
> 메서드에서 아무리 검증해도 그 불변식(invariant)을 전부 우회당한다.
> 캡슐화는 접근 제어자(private)가 아니라 "내부 가변 상태의 참조가
> 밖으로 새지 않는가"에서 완성된다.**

---

## 0. 질문 + 의도

**질문**: "방어적 복사(defensive copy)란? getter로 내부 컬렉션을 그대로
반환하면 어떤 문제가 생기나요?"

**출제 의도**: getter로 내부 List를 그대로 반환하면 외부가 도메인 객체의
불변식을 우회해 상태를 바꿀 수 있다 — 캡슐화가 메서드 시그니처가 아니라
참조 공유 수준에서 깨지는 지점을 아는지 본다. 불변을 기본값으로 두는
설계 습관(String 불변성 문항)의 실전 검증이다.

## 1. 방어적 복사란 — "참조 공유"가 문제의 본질

Java에서 객체를 넘기고 반환하는 것은 전부 **참조(주소) 복사**다.
가변 객체(List, Map, 배열, `Date` 등)의 참조를 외부와 공유하는 순간,
그 객체의 상태는 더 이상 나 혼자 통제할 수 없다.

방어적 복사(defensive copy)는 이 공유를 끊는 기법이다:

- **들어올 때(생성자/수정자)**: 외부에서 받은 가변 객체를 복사해서 보관
  — 호출자가 나중에 원본을 바꿔도 내 내부 상태는 안전
- **나갈 때(접근자/getter)**: 내부 가변 객체를 복사(또는 불변 뷰)로 반환
  — 호출자가 반환값을 바꿔도 내 내부 상태는 안전

비유하면, 원본 서류를 건네주는 게 아니라 **사본을 떼어 주는 것**이다.
사본에 낙서해도 원본 대장은 멀쩡하다.

## 2. getter로 내부 컬렉션을 그대로 반환하면 생기는 문제

### 2-1. 불변식 우회 — 검증 로직이 전부 무력화된다

```java
// Before: private 필드 + 검증 메서드까지 갖췄지만... 뚫려 있다
public class Order {
    private final List<OrderLine> lines = new ArrayList<>();

    public void addLine(OrderLine line) {
        if (lines.size() >= 100) {                  // 불변식: 최대 100줄
            throw new IllegalStateException("주문 항목 초과");
        }
        lines.add(line);
    }

    public List<OrderLine> getLines() {
        return lines;                               // 내부 참조를 그대로 노출!
    }
}

// 외부 코드 — 검증을 전부 우회
Order order = ...;
order.getLines().clear();                           // 주문 항목 전부 삭제
order.getLines().add(무검증_항목);                    // addLine의 검증을 건너뜀
```

- 필드는 `private final`이고 수정 메서드는 검증까지 하지만,
  **getter가 내부 참조를 넘겨준 순간 그 문은 전부 우회 가능**하다.
- `final`은 "참조를 못 바꾼다"는 뜻이지 "내용물을 못 바꾼다"가 아니다
  (String 불변성 문항과 이어지는 지점).

### 2-2. 버그가 "엉뚱한 곳에서, 나중에" 터진다

이 유형이 특히 위험한 이유는 **변경한 곳과 터지는 곳이 다르기 때문**이다.

- 어느 서비스가 `getLines()`로 받은 리스트를 "정렬 좀 하려고"
  `sort()` 하거나, 화면용으로 필터링하며 `removeIf()`를 호출한다.
- 그 순간 도메인 객체의 상태가 조용히 바뀌고, 한참 뒤 총액 계산·재고
  차감·영속화 시점에 "왜 값이 이래?"로 나타난다. 스택트레이스는 범인을
  가리키지 않는다.

### 2-3. 동시성 문제까지 얹힌다

내부 컬렉션 참조가 여러 스레드로 퍼지면, 한쪽이 순회하는 중에 다른 쪽이
수정해 `ConcurrentModificationException`이 나거나, 그보다 나쁘게는
예외 없이 일관성 없는 상태를 읽는다. 참조를 밖으로 내보내지 않으면
동기화 범위를 객체 내부로 한정할 수 있다.

### 2-4. 올바른 코드

```java
// After: 상황에 맞는 세 가지 방어
public class Order {
    private final List<OrderLine> lines;

    public Order(List<OrderLine> lines) {
        this.lines = new ArrayList<>(lines);        // ① 들어올 때 복사
        validate(this.lines);                       //    복사 '후' 검증 (§4 참고)
    }

    public List<OrderLine> getLines() {
        return List.copyOf(lines);                  // ② 나갈 때 불변 스냅샷
        // 또는
        // return Collections.unmodifiableList(lines);  // ③ 불변 '뷰' (§3 비교)
    }
}
```

외부가 반환값을 수정하려 하면 `UnsupportedOperationException`이 즉시
터진다 — **조용히 틀어지는 버그를 시끄러운 예외로 바꾸는 것**이 핵심 효과다.

## 3. 반환 방식 비교 — copy vs unmodifiable view

| 방식 | 성격 | 내부가 바뀌면 반환값도 바뀌나 | 비용 |
|---|---|---|---|
| `new ArrayList<>(lines)` | 가변 복사본 | 아니오 (스냅샷) | 호출마다 복사 |
| `List.copyOf(lines)` | **불변** 스냅샷 | 아니오 | 호출마다 복사 (이미 불변이면 재사용) |
| `Collections.unmodifiableList(lines)` | 불변 **뷰**(창문) | **예** — 원본을 들여다보는 창 | 래퍼 객체 하나 |

- **unmodifiable은 "복사"가 아니라 "뷰"다.** 밖에서 수정은 막지만, 내부가
  바뀌면 이미 나간 반환값의 내용도 함께 바뀐다. 반환받은 쪽이 그걸 오래
  들고 있으면 "받았을 때와 내용이 달라지는" 혼란이 생길 수 있다.
- `List.copyOf`는 진짜 스냅샷이라 그 시점의 상태가 고정된다. 도메인
  객체의 getter라면 대부분 이쪽이 의도에 맞는다. (가산점 포인트:
  `List.copyOf`는 인자가 이미 불변 리스트면 복사 없이 그대로 반환하는
  최적화가 있고, **null 원소를 허용하지 않는다**는 차이도 있다.)
- 컬렉션이 아주 크고 호출이 빈번하면 복사 비용이 문제될 수 있는데,
  그때는 뷰를 쓰되 "이 반환값은 라이브 뷰"임을 문서화하거나, 애초에
  컬렉션을 통째로 노출하지 않는 설계(§4 꼬리질문 3)로 푼다.

### 컬렉션만의 문제가 아니다 — 가변 객체 전반

```java
// Date는 가변 — getter로 그대로 반환하면 같은 문제 (Effective Java의 고전 예제)
public Date getStart() { return start; }            // 밖에서 start.setTime(...) 가능

// 배열도 마찬가지 — length만 final이고 원소는 바뀐다
public String[] getTags() { return tags; }          // 밖에서 tags[0] = "해킹" 가능
```

현대 Java라면 근본 해법은 **애초에 불변 타입을 쓰는 것**이다:
`Date` → `LocalDateTime/Instant`(불변), 상태 컬렉션 → 생성 시점에
`List.copyOf`로 고정. 불변 타입은 방어적 복사 자체가 필요 없다 —
"불변을 기본값으로"라는 설계 습관이 방어 코드의 양을 줄인다.

## 4. 꼬리질문 대비 포인트

### "생성자에서 받은 컬렉션도 복사해야 하나요? 검증과 복사의 순서는?"

해야 한다. getter만 막으면 절반이다 — 호출자가 생성자에 넘긴 리스트의
참조를 계속 들고 있다가 나중에 수정하면 내부 상태가 함께 바뀐다.
그리고 순서는 반드시 **복사 → 검증**이다. 검증 → 복사 순서면, 검증을
통과한 뒤 복사하기 전 찰나에 다른 스레드가 원본을 바꿔치기할 수 있다
(TOCTOU, time-of-check to time-of-use 공격/버그 — Effective Java가
명시적으로 경고하는 지점, 가산점 포인트). 복사본을 만든 뒤 그 복사본을
검증하면 검증된 것과 보관되는 것이 같은 객체임이 보장된다.

### "매 호출마다 복사하면 성능이 걱정되지 않나요?" (시니어 변별 포인트)

트레이드오프 판단 문제다. 대부분의 도메인 객체 컬렉션은 수십~수백
원소라 복사 비용이 무시 가능하고, 참조 공유 버그의 추적 비용이 훨씬
비싸다. 실제로 병목이 측정되면 선택지는: ① `unmodifiableList` 뷰로
래퍼 비용만 지불(라이브 뷰임을 감수), ② 내부 표현 자체를 불변
컬렉션으로 바꿔 getter가 그대로 반환해도 안전하게 만들기, ③ 컬렉션을
통째로 노출하지 말고 `Stream<OrderLine> lines()`, `int lineCount()`,
`forEachLine(Consumer)` 같은 **질의 메서드로 좁혀서 노출**하기 —
③이 가장 캡슐화다운 해법이고, "getter를 어떻게 방어하나"에서 "왜
컬렉션을 통째로 줘야 하나"로 질문을 되돌리는 답변이 시니어답다.

### "record를 쓰면 이 문제가 해결되나요?"

아니다. record는 필드 재대입만 막지(**얕은 불변**), 컴포넌트가 가변
객체면 참조 공유 문제는 그대로다. `record Order(List<OrderLine> lines)`의
자동 생성 접근자는 내부 참조를 그대로 반환한다. 그래서 record에서도
컴팩트 생성자에서 `lines = List.copyOf(lines);`로 방어적 복사를 해주는
것이 관용구다 — 이렇게 하면 저장 시점에 불변이 되므로 접근자는 그대로
둬도 안전해진다.

### "JPA 엔티티의 컬렉션 필드에도 방어적 복사를 적용하나요?"

주의가 필요하다. JPA는 지연 로딩·변경 감지(dirty checking)를 위해
엔티티의 컬렉션을 자기 구현체(PersistentBag 등)로 바꿔치기해 관리하므로,
필드 자체를 함부로 새 컬렉션으로 교체하면 변경 감지가 깨질 수 있다.
그래서 엔티티에서는 필드 교체 대신 **getter에서
`Collections.unmodifiableList(lines)`로 감싸 반환**하고, 추가/삭제는
`addLine()/removeLine()` 같은 의도가 드러나는 메서드로만 열어주는
패턴이 일반적이다. 반환이 뷰라는 점(내부 변경이 비쳐 보임)은 엔티티
생명주기 안에서는 오히려 자연스럽다.

### "Kotlin의 `List`는 읽기 전용인데, 그러면 안전한가요?"

절반만 안전하다. Kotlin의 `List`는 **읽기 전용 인터페이스**일 뿐 불변
보장이 아니다 — 실제 객체가 `ArrayList`면 `MutableList`로 캐스팅하거나
Java 코드로 넘어가는 순간 수정 가능하다. 타입 시스템이 "수정할 의도
없음"을 표현해주는 큰 진전이지만, 진짜 격리가 필요하면 Kotlin에서도
`toList()`(복사)를 반환하는 것이 방어적 복사에 해당한다.

## 한 줄 요약

`private`은 필드 이름을 숨길 뿐 상태를 지키지 못한다 — 가변 객체의
참조가 밖으로 새는 순간 캡슐화는 끝난 것이므로, 들어올 때 복사하고
나갈 때는 복사본이나 불변 뷰만 내보내며, 가장 좋은 방어는 애초에
내부 상태를 불변으로 만들어 복사가 필요 없게 하는 것이다.
