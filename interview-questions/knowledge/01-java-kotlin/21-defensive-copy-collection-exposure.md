# 방어적 복사와 컬렉션 노출 — getter가 돌려주는 것은 복사본이 아니라 주소값이다

> 핵심 관전 포인트: **문제의 본질은 "참조 공유"다. `return lines;`가 돌려주는 것은 리스트의 복사본이 아니라 같은 ArrayList 객체를 가리키는 주소값이므로, 호출자와 도메인 객체가 하나의 리스트를 함께 들게 된다. 그 결과 필드가 `private final`이고 `addLine()`이 최대 개수를 검증해도, 외부는 `getLines().add(...)`로 그 검증을 통째로 건너뛴다 — 캡슐화는 접근 제어자가 아니라 "내부 가변 상태의 참조가 밖으로 새지 않는가"에서 완성된다. 실무에서 이 버그가 무서운 이유는 예외가 안 나기 때문이다. 외부가 리스트를 수정한 시점과 불변식이 깨진 채로 저장·정산되는 시점이 멀리 떨어져 있어서 스택트레이스가 범인을 가리키지 못한다. 방어는 반환 방식 3종의 트레이드오프로 갈린다 — 방어적 복사(`new ArrayList<>`, 매번 비용·완전 독립), 수정 불가 뷰(`unmodifiableList`, 싸지만 원본이 바뀌면 뷰도 바뀐다), 불변 복사본(`List.copyOf`, null 원소 불가). 여기에 얕은 복사의 한계(원소가 가변이면 원소를 통해 여전히 뚫린다), 생성자 인자도 복사해야 한다는 것, 그리고 복사한 뒤 복사본을 검증해야 TOCTOU가 안 생긴다는 순서까지가 이 주제의 전부다.**

---

## 0. 질문 + 의도

**질문**: "방어적 복사(defensive copy)란? getter로 내부 컬렉션을 그대로 반환하면 어떤 문제가 생기나요?"

**출제 의도**: getter로 내부 List를 그대로 반환하면 외부가 도메인 객체의 불변식을 우회해 상태를 바꿀 수 있다 — 캡슐화가 메서드 시그니처가 아니라 참조 공유 수준에서 깨지는 지점을 아는지 본다. 불변을 기본값으로 두는 설계 습관(String 불변성 문항)의 실전 검증이다.

## 1. 문제의 본질 — 참조 공유

### 1-1. 전제 지식 — 변수 칸에 들어 있는 것은 객체가 아니라 주소다

이 문서의 모든 내용이 이 한 가지 사실에서 나온다. 먼저 이것부터 확정하고 가자.

자바에서 **객체를 담은 변수에 실제로 들어 있는 것은 객체 자체가 아니라 그 객체가 힙 어디에 있는지를 가리키는 주소값**이다. 이 주소값을 참조(reference)라고 부른다.

```text
List<OrderLine> lines = new ArrayList<>();

  변수 lines                      힙
  +--------------+               +--------------------------+
  | 0x4b2a...    | ------------> | ArrayList 객체            |
  +--------------+               |   [0] ...                |
  주소가 여기 있다                |   [1] ...                |
                                 +--------------------------+
                                 객체는 힙에 따로 있다
```

그리고 **대입도, 인자 전달도, 메서드 반환도 전부 이 주소값을 한 벌 더 복사해 주는 것**이다. 객체가 복제되는 일은 어디에서도 일어나지 않는다. `new`를 부르거나 명시적으로 복사를 하지 않는 한, 힙의 객체는 계속 하나다.

(같은 사실을 `==` 비교의 관점에서 다룬 것이 `30-integer-cache-boxed-equality.md`다. 거기서는 "두 변수가 같은 객체를 가리키는가"가 문제였고, 여기서는 "두 코드가 같은 객체를 함께 만지게 되는가"가 문제다. 뿌리는 같다.)

### 1-2. getter가 실제로 하는 일 — 주소를 한 벌 더 건네준다

이제 문제의 코드를 보자.

```java
public class Order {
    private final List<OrderLine> lines = new ArrayList<>();

    public List<OrderLine> getLines() {
        return lines;      // 이 한 줄이 무슨 일을 하는가?
    }
}
```

`return lines;`는 리스트를 복제해서 주는 것이 **아니다.** 변수 `lines`에 들어 있는 주소값을 그대로 호출자에게 건네준다.

```text
[Order 객체]                              [힙의 ArrayList 객체 — 하나뿐이다]
+---------------------+                   +--------------------------+
| lines : 0x4b2a...   | ----------------> | ArrayList                |
+---------------------+              +--> |   [0] OrderLine(사과)     |
                                     |    |   [1] OrderLine(우유)     |
[getLines()를 부른 쪽의 지역 변수]    |    +--------------------------+
+---------------------+              |
| got   : 0x4b2a...   | -------------+
+---------------------+

  화살표가 둘이지만 상자는 하나다.
  Order와 외부 코드가 '같은 리스트'를 함께 들고 있는 상태가 되었다.
```

**이 그림이 이 문서의 전부다.** 앞으로 나올 불변식 우회, 시점이 어긋난 버그, 동시성 문제, 얕은 복사의 한계는 전부 이 그림에서 따라 나온다.

비유하면 서류 대장을 다루는 방식의 차이다. 사본을 떼어 주면 상대가 사본에 무엇을 적든 원본 대장은 멀쩡하다. 그런데 지금 코드는 **원본 대장을 통째로 건네주고 있다.** 상대가 거기에 한 줄을 적으면 우리 대장에 적힌 것이다.

### 1-3. `private final`이 왜 못 막는가

여기서 자연스러운 반문이 나온다. **"필드가 `private final`인데 어떻게 밖에서 바꾸나?"**

두 키워드가 각각 무엇을 막는지 정확히 보면 답이 나온다.

**`private`은 이름을 감춘다.** 외부 코드가 `order.lines`라고 직접 쓰는 것을 막는다. 그런데 우리는 `getLines()`라는 공개 통로로 그 주소값을 **자발적으로 건네주고 있다.** 이름은 감췄지만 물건은 내줬다.

**`final`은 주소값을 고정한다.** `this.lines = 다른리스트;`처럼 그 변수 칸의 주소값을 바꾸는 것을 막는다. 그런데 우리가 하려는 것은 주소값을 바꾸는 게 아니라 **그 주소가 가리키는 객체의 내용물을 바꾸는 것**이다.

```text
final List<OrderLine> lines

  +--------------+               +--------------------------+
  | 0x4b2a...    | ------------> | ArrayList                |
  +--------------+               |   [0] ...  ← 여기는 자유롭게 바뀐다
   ↑                             |   [1] ...
   final이 고정하는 것은 여기     +--------------------------+
   (이 칸의 값을 못 바꾼다)        final은 이 안쪽에 아무 영향이 없다
```

**`final`은 "참조를 못 바꾼다"는 뜻이지 "내용물을 못 바꾼다"는 뜻이 아니다.** `final List`는 불변 리스트가 아니다. 이 구분은 String 불변성 문항과 같은 뿌리이고, 자바에서 가장 자주 오해되는 지점 중 하나다.

### 1-4. 불변식 우회 — 검증 메서드가 통째로 건너뛰어진다

도메인 객체가 지키려는 규칙을 **불변식(invariant)**이라고 부른다. "언제 봐도 변하지 않고 참이어야 하는 조건"이라는 뜻이다. "주문 항목은 최대 100개", "주문에는 최소 1개의 항목이 있어야 한다", "합계 금액은 항목 금액의 합과 같다" 같은 것들이다.

객체지향에서 불변식을 지키는 방법은 **상태를 감추고, 상태를 바꾸는 통로를 메서드로 좁히고, 그 메서드에서 검증하는 것**이다. 그런데 그 노력이 getter 한 줄로 무력화된다.

```java
// Before: private 필드 + 검증하는 수정 메서드까지 갖췄지만 뚫려 있다
public class Order {
    private final List<OrderLine> lines = new ArrayList<>();

    public void addLine(OrderLine line) {
        if (lines.size() >= 100) {                    // 불변식: 최대 100줄
            throw new IllegalStateException("주문 항목 초과");
        }
        lines.add(line);
    }

    public List<OrderLine> getLines() {
        return lines;                                 // 내부 참조를 그대로 내준다
    }
}
```

```java
// 외부 코드 — 검증을 전부 우회한다
Order order = ...;

order.addLine(line);          // 통로 ① — 여기는 검증을 통과해야 한다
order.getLines().add(line);   // 통로 ② — 검증이 아예 실행되지 않는다
order.getLines().clear();     // 주문 항목 전부 삭제. 아무도 막지 않는다
```

`addLine`은 문이고 `getLines`는 벽에 난 구멍이다. **문에 아무리 좋은 자물쇠를 달아도 옆에 구멍이 뚫려 있으면 의미가 없다.**

주목할 점은 `getLines()`를 만든 사람의 의도가 순수했다는 것이다. "주문 항목을 화면에 보여줘야 하니 조회용 getter를 하나 두자"는 지극히 평범한 판단이었다. **읽기 위해 만든 통로가 쓰기 통로로도 작동한다는 사실이 코드 모양에 전혀 드러나지 않는다.** 반환 타입이 `List<OrderLine>`이라고만 적혀 있을 뿐, 그것이 살아 있는 내부 상태라는 표시는 어디에도 없다.

**캡슐화는 접근 제어자가 아니라 "내부 가변 상태의 참조가 밖으로 새지 않는가"에서 완성된다.**

### 1-5. 버그가 엉뚱한 곳에서 나중에 터진다

이 유형이 실무에서 특히 위험한 이유는 우회 자체가 아니다. **예외가 안 나기 때문**이다.

`getLines().removeIf(...)`는 완벽히 합법적인 자바 코드다. 컴파일러도, 런타임도, 로그도 아무 말을 하지 않는다. 그래서 **잘못된 시점에 아무 일도 일어나지 않고, 한참 뒤 전혀 다른 곳에서 결과만 드러난다.**

전형적인 흐름을 타임라인으로 보자.

```text
t0  [화면 조립 계층]
      List<OrderLine> lines = order.getLines();
      lines.removeIf(l -> l.isHidden());     ← 화면에서 감출 항목을 걸러내려던 코드
                                                작성자는 "받아온 리스트를 가공한다"고 생각했다

    ★ 이 순간 Order 내부의 lines에서 항목이 실제로 삭제된다.
      예외도, 경고도, 로그도 없다. 화면은 의도대로 잘 나온다.

t1  ... 같은 요청 안에서 다른 코드들이 order를 계속 사용한다 ...

t2  [금액 계산]
      order.totalAmount()   -> 삭제된 항목이 빠진 금액이 계산된다
                               계산 로직 자체는 완벽히 정상이다

t3  [영속화]
      트랜잭션 커밋          -> 항목이 빠진 상태가 DB에 저장된다

t4  (며칠 뒤) [정산 대사]
      "주문 금액 합계와 결제 금액이 안 맞는 건이 있습니다"

    ★ 여기서 처음으로 사람이 인지한다.
      스택트레이스를 떠도 t0의 removeIf는 없다. 그 코드는 며칠 전에 이미 끝났다.
      대사 배치의 스택트레이스만 나오는데, 대사 배치는 아무 잘못이 없다.
```

**변경한 곳(t0)과 증상이 나타난 곳(t4)이 시간으로도 코드 위치로도 멀리 떨어져 있다.** 이것이 이 버그의 본질적 어려움이다.

일반적인 버그는 스택트레이스가 범인을 가리킨다. NPE가 나면 그 줄을 보면 된다. 그런데 이 버그는 **범인이 흔적을 남기지 않고 떠난 뒤 피해자만 발견되는** 구조다. 디버깅은 "누가 이 리스트를 건드렸는가"를 코드 전체에서 역추적하는 일이 되고, `getLines()`를 호출하는 모든 지점을 하나씩 검토해야 한다.

그리고 t0의 코드를 짠 사람에게는 책임을 묻기도 어렵다. **받아온 리스트를 가공하는 것은 지극히 자연스러운 행동**이기 때문이다. 정렬 좀 하려고 `sort()`를 부르는 것, 화면용으로 걸러내려고 `removeIf()`를 부르는 것 — 전부 평범한 코드다. 잘못은 그런 코드를 짠 사람이 아니라 **살아 있는 내부 리스트를 내준 설계**에 있다.

### 1-6. 동시성이 얹히면 더 나빠진다

내부 컬렉션의 참조가 여러 스레드로 퍼지면 문제가 한 겹 더 쌓인다.

한 스레드가 리스트를 순회하는 중에 다른 스레드가 그 리스트를 수정하면 `ConcurrentModificationException`이 난다. 이건 그나마 나은 경우다 — **예외가 나므로 문제를 알아챌 수 있기 때문**이다. 더 나쁜 경우는 예외 없이 일관성 없는 상태를 읽어 가는 것이다.

참조를 밖으로 내보내지 않으면 이 문제 자체가 다르게 다뤄진다. **동기화를 걸어야 할 범위를 객체 내부로 한정할 수 있기 때문**이다. 리스트를 만지는 코드가 이 클래스 안에만 있다면 이 클래스 안에서 동기화를 완결할 수 있다. 반면 참조가 밖으로 나가면 그 리스트를 만지는 코드가 어디까지 퍼졌는지 알 수 없으므로, 동기화 범위를 확정하는 것 자체가 불가능해진다.

## 2. 막는 법 — 반환 방식 3종과 그 한계

### 2-1. 방어적 복사란

**방어적 복사(defensive copy)**는 가변 객체를 주고받을 때 원본 대신 복사본을 써서 **참조 공유를 끊는** 기법이다. 1-2의 그림에서 화살표 두 개가 같은 상자를 가리키던 상황을, 상자를 하나 더 만들어 각자 자기 것을 가리키게 바꾸는 것이다.

방어할 지점은 두 곳이다.

- **나갈 때(getter)**: 내부 객체를 복사하거나 수정 불가 형태로 반환한다. 호출자가 반환값을 바꿔도 내 상태는 안전하다.
- **들어올 때(생성자·수정자)**: 외부에서 받은 객체를 복사해서 보관한다. 호출자가 나중에 원본을 바꿔도 내 상태는 안전하다.

들어올 때도 막아야 하는 이유는 2-4에서 따로 다룬다. 먼저 나갈 때의 선택지부터 보자.

### 2-2. 세 가지 반환 방식과 트레이드오프

세 가지 선택지가 있고 성격이 전부 다르다.

| 반환 방식 | 무엇을 돌려주나 | 원본이 바뀌면 반환값은 | 반환값을 수정하려 하면 | 비용 |
|---|---|---|---|---|
| `new ArrayList<>(items)` | 그 시점의 **가변 복사본** | 안 바뀐다 | 그냥 된다 (복사본만 바뀜) | 호출마다 원소 수만큼 복사 |
| `List.copyOf(items)` | 그 시점의 **불변 복사본** | 안 바뀐다 | `UnsupportedOperationException` | 호출마다 복사 |
| `Collections.unmodifiableList(items)` | 원본을 들여다보는 **뷰** | **같이 바뀐다** | `UnsupportedOperationException` | 래퍼 객체 하나 |

표의 세 번째 열이 가장 중요한데 자주 오해되는 부분이라 풀어서 보자.

**`new ArrayList<>(items)`는 새 리스트 객체를 만들어 원소들을 옮겨 담는다.** 그 시점의 스냅샷이 되므로 이후 원본이 어떻게 바뀌든 반환된 리스트는 그대로다. 다만 돌려준 것이 평범한 `ArrayList`이므로 호출자가 거기에 `add`를 할 수 있다. 다만 그 `add`는 복사본에만 반영되고 원본에는 영향이 없다. **조용히 아무 효과가 없다**는 뜻이라, 호출자 입장에서는 "왜 추가가 안 되지?"라는 다른 종류의 혼란이 생길 수 있다.

**`List.copyOf(items)`도 복사본이지만 불변이다.** 호출자가 수정하려 하면 그 자리에서 `UnsupportedOperationException`이 터진다. **조용히 틀어지는 버그를 시끄러운 예외로 바꾸는 것**이 이 방식의 핵심 가치다. 1-5의 타임라인에서 t0에 즉시 예외가 나므로 t4까지 갈 일이 없어진다. 도메인 객체의 getter라면 대부분 이쪽이 의도에 맞는다.

`List.copyOf`에는 알아둘 특성이 둘 있다 (가산점 포인트). 인자가 **이미 불변 리스트면 복사하지 않고 그대로 돌려주는 최적화**가 있어서, 내부 표현이 이미 불변이면 반복 호출 비용이 사라진다. 그리고 **null 원소를 허용하지 않아서** 리스트에 null이 하나라도 있으면 `NullPointerException`이 난다. 기존 코드에 이걸 적용할 때 걸리는 함정이므로 알아둬야 한다.

**`Collections.unmodifiableList(items)`는 복사가 아니라 뷰다.** 이 차이가 실무에서 가장 자주 오해되는 지점이다.

```text
[복사 — List.copyOf]                     [뷰 — unmodifiableList]

 원본 리스트     복사본 리스트             원본 리스트  <---- 뷰 래퍼
  +------+       +------+                  +------+       +----------+
  | A, B |       | A, B |                  | A, B | <---- | 읽기만    |
  +------+       +------+                  +------+       | 허용하는  |
   서로 아무 관계가 없다                     ↑             | 창문      |
                                            |             +----------+
   원본에 C를 추가해도                       원본에 C를 추가하면
   복사본은 A, B 그대로                      뷰를 통해서도 A, B, C가 보인다
```

**뷰는 원본을 들여다보는 창문**이다. 수정은 막지만 내용이 고정되지는 않는다. 원본이 바뀌면 이미 나간 반환값의 내용도 함께 바뀐다.

이게 왜 문제가 되는가. 반환받은 쪽이 그 리스트를 오래 들고 있다가 나중에 다시 읽으면 **"받았을 때와 내용이 다른"** 상황을 만난다. 심지어 반환값을 순회하는 중에 원본이 수정되면 `ConcurrentModificationException`까지 난다 — 호출자는 "수정 불가 리스트라고 해서 받았는데 왜 동시 수정 예외가 나지?"라는 상황에 빠진다.

**그럼 뷰는 왜 쓰는가.** 비용 때문이다. 복사는 원소 수에 비례한 비용이 매번 들지만, 뷰는 래퍼 객체 하나를 만드는 것으로 끝난다. 컬렉션이 아주 크고 getter 호출이 빈번하면 이 차이가 의미를 갖는다. 그리고 뒤에서 볼 JPA 엔티티처럼 **뷰가 오히려 옳은 자리**도 있다.

정리하면 선택 기준은 이렇다. **기본값은 `List.copyOf`** — 스냅샷이라 예상대로 동작하고, 잘못된 수정 시도를 즉시 예외로 알려 준다. **성능이 실제로 측정된 병목이면 뷰**를 쓰되, "이 반환값은 원본을 비추는 라이브 뷰"라는 사실을 문서화한다. **`new ArrayList<>`는 호출자가 받은 리스트를 자유롭게 가공해야 하는 경우**에 쓴다.

### 2-3. 얕은 복사의 한계 — 원소가 가변이면 여전히 뚫린다

여기까지 하면 다 막은 것 같지만 아니다. **리스트를 복사해도 그 안의 원소는 복사되지 않는다.**

```java
List<OrderLine> copy = new ArrayList<>(lines);
copy.get(0).changeQuantity(999);   // 원본 리스트의 [0]도 함께 바뀐다
```

왜 그런지는 1-1의 사실을 다시 적용하면 된다. **리스트에 들어 있는 것도 객체가 아니라 주소값**이다. 리스트를 복사한다는 것은 그 주소값들을 새 상자에 옮겨 담는 것이지, 주소가 가리키는 객체들까지 복제하는 것이 아니다.

```text
                        +--> OrderLine #1 <--+
[원본 lines]            |                    |     [new ArrayList<>(lines)]
 +------------+         |                    |      +------------+
 | [0] 주소 ──|---------+                    +------|─ 주소 [0]  |
 | [1] 주소 ──|---------+                    +------|─ 주소 [1]  |
 +------------+         |                    |      +------------+
                        +--> OrderLine #2 <--+

  리스트 상자는 두 개가 됐지만, OrderLine 객체는 여전히 하나씩이다.
  어느 쪽 리스트를 통해 꺼내든 같은 객체에 도달한다.
```

이렇게 **한 겹만 복사하는 것을 얕은 복사(shallow copy)**, 원소까지 재귀적으로 복사하는 것을 **깊은 복사(deep copy)**라고 한다. `new ArrayList<>(...)`, `List.copyOf(...)`, `clone()`, 스트림의 `toList()` — **자바의 컬렉션 복사는 전부 얕은 복사다.**

그러니 방어의 완성도는 **원소 타입이 가변인지 불변인지**에 달려 있다.

- 원소가 `String`, `Integer`, `LocalDate`, `BigDecimal` 같은 **불변 타입**이면 얕은 복사로 충분하다. 원소를 통해 바꿀 수 있는 것이 애초에 없기 때문이다.
- 원소가 **세터를 가진 가변 객체**면 리스트를 아무리 잘 막아도 원소를 통해 뚫린다.

그럼 깊은 복사를 해야 하는가. **대부분의 경우 답은 아니다.** 깊은 복사는 비용이 크고, 원소가 다른 객체를 참조하면 어디까지 복사해야 하는지의 경계가 모호해지며, 순환 참조가 있으면 무한 루프에 빠진다.

**현실적인 답은 원소 타입을 불변으로 만드는 것이다.** `OrderLine`에서 세터를 없애고, 수량을 바꿔야 하면 `withQuantity(999)`처럼 **새 인스턴스를 만들어 돌려주는** 방식으로 설계한다. 그러면 원소를 통한 우회가 원천적으로 불가능해지고, 리스트 한 겹만 방어하면 끝난다.

**"불변을 기본값으로"라는 설계 습관이 방어 코드의 양을 줄인다**는 원칙이 여기서 구체적인 이득으로 나타난다.

### 2-4. 들어올 때도 복사한다 — 그리고 검증과 복사의 순서

지금까지는 나가는 쪽만 봤다. 그런데 **들어오는 쪽도 똑같이 뚫려 있다.**

```java
// Before: 생성자에서 받은 리스트를 그대로 보관한다
public Order(List<OrderLine> lines) {
    this.lines = lines;      // 호출자가 넘긴 리스트를 그대로 들고 있는다
}
```

```java
// 호출하는 쪽
List<OrderLine> myLines = new ArrayList<>();
myLines.add(line1);
Order order = new Order(myLines);

myLines.add(line2);   // ★ 호출자는 여전히 이 리스트의 참조를 들고 있다
                      //   여기서 추가하면 order 내부의 리스트에도 추가된다
myLines.clear();      //   order의 항목이 전부 사라진다
```

**호출자가 넘긴 참조를 계속 들고 있다**는 것이 핵심이다. `new Order(myLines)`로 소유권이 넘어간 것처럼 보이지만 실제로는 주소값을 한 벌 나눠 가진 것뿐이고, 호출자의 변수도 여전히 같은 객체를 가리킨다. getter를 아무리 잘 막아도 이 통로가 열려 있으면 절반만 막은 것이다.

그래서 생성자에서도 복사한다. 그런데 여기서 **순서**가 문제가 된다.

```java
// Before: 검증 -> 복사 (틀린 순서)
public Order(List<OrderLine> lines) {
    validate(lines);                        // ① 넘겨받은 원본을 검증한다
    this.lines = new ArrayList<>(lines);    // ② 그 원본을 복사해서 보관한다
}
```

```java
// After: 복사 -> 검증 (올바른 순서)
public Order(List<OrderLine> lines) {
    this.lines = new ArrayList<>(lines);    // ① 먼저 내 것으로 복사하고
    validate(this.lines);                   // ② 그 복사본을 검증한다
}
```

두 줄의 순서만 바뀌었는데 왜 중요한가. **①과 ② 사이에 원본이 바뀔 수 있기 때문**이다.

```text
[검증 -> 복사 순서일 때]

  스레드 A (생성자)                    스레드 B (호출자가 참조를 들고 있다)
  ---------------------------------    ------------------------------------
  t0  validate(lines)  -> 통과
                                       t1  lines.add(불법항목)   ★ 여기
  t2  new ArrayList<>(lines)
      -> 검증되지 않은 불법 항목이 포함된 채로 복사된다

  결과: 검증을 통과했다고 기록됐지만 실제로 보관된 것은 검증되지 않은 데이터다
```

**검증한 대상과 실제로 보관되는 대상이 다른 객체**라는 것이 문제의 뿌리다. 검증은 호출자의 원본에 했는데 보관은 그 이후 상태를 복사한 것이다.

이런 종류의 결함을 **TOCTOU(time-of-check to time-of-use, 검사 시점과 사용 시점의 불일치)**라고 부른다. "검사할 때는 맞았는데 실제로 쓸 때는 달라져 있는" 상황을 가리키는 이름이다. 보안 취약점의 고전적 유형이기도 하다 — 파일 권한을 검사한 뒤 실제로 여는 사이에 그 파일을 심볼릭 링크로 바꿔치기하는 공격이 같은 구조다.

**복사를 먼저 하면 이 틈이 사라진다.** 복사가 끝난 순간 그 복사본은 우리만 아는 객체이고 아무도 손댈 수 없으므로, 그것을 검증하면 **검증한 것과 보관되는 것이 같은 객체임이 보장된다.**

여기서 주의할 점이 하나 있다. **복사도 얕은 복사라는 것**이다(2-3). 리스트 자체는 스냅샷이 됐지만 원소가 가변이면 원소를 통한 바꿔치기는 여전히 가능하다. 완전한 방어는 원소까지 불변일 때 성립한다.

### 2-5. 컬렉션만의 문제가 아니다

지금까지 컬렉션으로 설명했지만 원인이 "참조 공유"이므로 **가변 객체 전반에 똑같이 적용된다.**

```java
// Date는 가변이다 — setTime()으로 시각을 바꿀 수 있다
public Date getStart() { return start; }
// 외부에서 order.getStart().setTime(0) 하면 주문 시각이 바뀐다

// 배열도 마찬가지 — length만 고정이고 원소는 얼마든지 바뀐다
public String[] getTags() { return tags; }
// 외부에서 order.getTags()[0] = "조작됨" 이 가능하다
```

배열은 특히 놓치기 쉽다. **배열에는 `unmodifiableList` 같은 방어 수단이 없다.** 복사(`Arrays.copyOf`, `clone()`)하거나, 애초에 배열 대신 `List`로 노출하는 수밖에 없다.

근본 해법은 여기서도 같다. **애초에 불변 타입을 쓰는 것이다.**

- `Date` 대신 `LocalDateTime`·`Instant` — 자바 8의 날짜 타입은 전부 불변이라 방어적 복사가 필요 없다.
- 상태를 담는 컬렉션은 생성 시점에 `List.copyOf`로 고정해 **내부 표현 자체를 불변으로** 만든다. 이렇게 하면 getter가 그대로 반환해도 안전해지고, 매 호출 복사 비용도 사라진다.

**"getter를 어떻게 방어할까"보다 "내부 상태를 애초에 불변으로 둘 수 없을까"가 먼저 물어야 할 질문**이다.

### 2-6. 가장 캡슐화다운 해법 — 컬렉션을 통째로 주지 않기

한 걸음 더 나가면 질문 자체를 되돌릴 수 있다. **"이 컬렉션을 통째로 밖에 줘야 하는 이유가 무엇인가?"**

호출자가 실제로 원하는 것은 대개 리스트 자체가 아니라 그것으로 얻으려는 결과다. 개수를 세거나, 순회하거나, 특정 조건의 항목을 찾거나, 합계를 구하는 것이다. 그렇다면 **그 결과를 주는 메서드를 노출하면 된다.**

```java
// Before: 컬렉션을 통째로 노출하고, 그 위에서 방어를 고민한다
public List<OrderLine> getLines() { return List.copyOf(lines); }

// After: 호출자가 실제로 필요로 하는 질의만 노출한다
public int lineCount() { return lines.size(); }
public BigDecimal totalAmount() { ... }
public Stream<OrderLine> lines() { return lines.stream(); }   // 순회만 가능, 원본 수정 불가
public boolean contains(ProductId id) { ... }
```

이 방식의 이점은 방어 비용이 사라지는 것만이 아니다. **계산 로직이 데이터를 가진 객체 쪽으로 옮겨 온다.** 기존에는 외부가 리스트를 받아 가서 합계를 계산했는데, 이제 `Order`가 자기 항목으로 합계를 계산한다. 데이터와 그것을 다루는 로직이 한곳에 모이는 것이 객체지향 설계의 지향점이고, 방어적 복사 고민은 그 결과로 자연히 없어진다.

물론 화면에 목록을 그려야 하는 등 컬렉션 자체가 필요한 자리도 있다. 그때는 2-2의 세 방식 중에서 고르면 된다. **다만 "통째로 줄 필요가 있는가"를 먼저 물어보는 순서가 중요하다.**

## 3. 실무 경계 — 자동으로 해결되지 않는 것들

### 3-1. record는 이 문제를 풀어주지 않는다

`record`는 불변 데이터를 담기 위해 나온 문법이므로 "record를 쓰면 방어적 복사가 필요 없지 않나"라는 기대가 자연스럽다. **아니다.**

record가 보장하는 것은 **얕은 불변(shallow immutability)**이다. 필드에 다시 대입하는 것만 막을 뿐, 컴포넌트가 가변 객체면 그 객체의 내용은 얼마든지 바뀐다. 2-3에서 본 얕은 복사의 한계와 정확히 같은 구조다.

```java
// Before: record라서 안전할 것 같지만 뚫려 있다
public record Cart(List<Item> items) { }

List<Item> myItems = new ArrayList<>();
Cart cart = new Cart(myItems);

myItems.add(item);           // 생성자로 넘긴 참조를 통해 내부가 바뀐다
cart.items().add(item);      // 자동 생성된 접근자가 내부 참조를 그대로 돌려준다
```

**record가 자동 생성하는 접근자는 `return items;`와 동일하다.** 1-2의 문제가 그대로 재현된다.

```java
// After: 컴팩트 생성자에서 방어적 복사를 한다
public record Cart(List<Item> items) {
    public Cart {
        items = List.copyOf(items);   // 저장되기 전에 불변 복사본으로 바꿔치기한다
    }
}
```

컴팩트 생성자는 필드에 대입되기 **직전**에 실행되는 블록이라, 여기서 파라미터 변수를 바꾸면 그 바뀐 값이 필드에 저장된다. **저장 시점에 이미 불변이 되므로 접근자는 손대지 않아도 안전해진다** — 불변 객체의 참조는 아무리 공유해도 문제가 없기 때문이다.

이것이 record에서의 관용구다. `29-record-use-cases.md`에서 같은 내용을 record의 관점으로 다룬다.

### 3-2. JPA 엔티티의 컬렉션은 복사해서 반환하면 안 된다

지금까지의 원칙에 정면으로 예외가 되는 자리가 있다. **JPA 엔티티다.**

이유는 JPA의 동작 방식에 있다. **하이버네이트는 엔티티를 영속 상태로 만들 때 컬렉션 필드를 자기 구현체(`PersistentBag`, `PersistentSet` 등)로 바꿔치기한다.** 그 구현체가 "어떤 원소가 추가됐고 삭제됐는지"를 기록하고 있다가, 트랜잭션 커밋 시점에 그 기록을 보고 INSERT/DELETE SQL을 만든다. 이것이 **변경 감지(dirty checking)**의 실체다.

여기서 두 가지 결론이 나온다.

**첫째, 필드 자체를 새 컬렉션으로 교체하면 안 된다.**

```java
// Before: 엔티티에서 컬렉션 필드를 통째로 갈아 끼운다
public void replaceLines(List<OrderLine> newLines) {
    this.lines = new ArrayList<>(newLines);   // 하이버네이트가 추적하던 인스턴스를 버렸다
}
```

하이버네이트가 추적하던 그 인스턴스가 사라졌으므로 변경 감지가 끊긴다. `orphanRemoval`이나 `cascade = ALL`이 걸려 있으면 아예 예외가 난다 — "cascade가 걸린 컬렉션이 더 이상 소유 엔티티에서 참조되지 않는다"는 취지의 `HibernateException`이다. 항목을 통째로 바꿔야 한다면 필드를 교체하는 대신 **같은 인스턴스에 대고 `clear()` 후 `addAll()`**을 해야 한다.

**둘째, getter가 복사본을 반환하면 그 복사본에 대한 수정은 DB에 반영되지 않는다.**

이건 사실 우리가 원하던 보호이기도 하다. 다만 결과가 조용하다는 것이 문제다. 호출자가 `order.getLines().add(line)`을 했는데 예외도 안 나고 DB에도 안 들어가면, "왜 저장이 안 되지?"를 한참 헤매게 된다.

그래서 엔티티에서 일반적으로 쓰는 패턴은 이렇다.

```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();

    // 조회: 뷰로 감싸 반환한다. 복사가 아니라 뷰인 것이 여기서는 오히려 맞다 —
    // 엔티티의 생명주기 안에서는 "지금 상태를 비춘다"가 자연스러운 의미이고,
    // 하이버네이트가 추적하는 원본 인스턴스는 그대로 유지된다.
    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);
    }

    // 수정: 의도가 드러나는 메서드로만 열어 준다.
    // 원본 인스턴스에 직접 add/remove 하므로 변경 감지가 정상 동작한다.
    public void addLine(OrderLine line) {
        if (lines.size() >= 100) throw new IllegalStateException("주문 항목 초과");
        lines.add(line);
        line.assignTo(this);      // 양방향 연관관계의 반대편도 맞춰 준다
    }

    public void removeLine(OrderLine line) {
        lines.remove(line);       // orphanRemoval이 DELETE를 만들어 준다
    }
}
```

정리하면 **"엔티티에서는 뷰로 반환하고 수정은 메서드로만"**이다. 2-2에서 뷰의 단점으로 지적한 "원본이 바뀌면 뷰도 바뀐다"는 성질이, 엔티티의 생명주기 안에서는 오히려 원하는 동작이 된다. **원칙이 통째로 뒤집히는 게 아니라 프레임워크의 제약 때문에 선택지가 하나로 좁혀지는 것**이라고 이해하면 된다.

### 3-3. Kotlin의 `List`는 절반만 안전하다

Kotlin으로 넘어가면 타입 시스템이 도와주지만 완전하지는 않다.

Kotlin은 `List`와 `MutableList`를 나눠 두었고, `List`에는 `add`나 `remove`가 아예 선언되어 있지 않다. 그래서 `List`를 반환하면 호출자가 수정 메서드를 부를 방법이 없다 — 타입 시스템이 "수정할 의도가 없다"를 표현해 준다는 점에서 자바보다 큰 진전이다.

그런데 **`List`는 읽기 전용 인터페이스이지 불변 보장이 아니다.**

```kotlin
class Order {
    private val _lines = mutableListOf<OrderLine>()
    val lines: List<OrderLine> get() = _lines   // 읽기 전용 타입으로 노출
}

// 실제 객체는 여전히 MutableList다
(order.lines as MutableList).add(item)   // 캐스팅하면 수정된다
```

그리고 자바 코드로 넘어가는 순간 이 구분은 사라진다 — 자바에서는 그냥 `java.util.List`이므로 `add`를 부를 수 있다.

더 중요한 것은 **원본이 바뀌면 반환값도 바뀐다**는 점이다. `_lines`를 그대로 노출한 것이므로 `unmodifiableList` 뷰와 같은 성격이다. 진짜 격리가 필요하면 Kotlin에서도 `toList()`로 복사해서 반환해야 하고, 그것이 방어적 복사에 해당한다.

## 4. 꼬리질문 대비 포인트

### "생성자에서 받은 컬렉션도 복사해야 하나요? 검증과 복사의 순서는?"

**해야 한다. getter만 막으면 절반이다.** 호출자가 생성자에 넘긴 리스트의 참조를 계속 들고 있다가 나중에 수정하면 내부 상태가 함께 바뀐다. `new Order(myLines)`로 소유권이 넘어간 것처럼 보이지만 실제로는 주소값을 나눠 가진 것뿐이다.

순서는 반드시 **복사 먼저, 그다음 검증**이다.

검증을 먼저 하면 **검증한 객체와 실제로 보관하는 객체가 다른 객체**가 된다. 그 사이에 호출자(또는 다른 스레드)가 원본을 바꾸면, 검증을 통과했다는 기록만 남고 실제로는 검증되지 않은 데이터가 보관된다. 이런 결함을 **TOCTOU(time-of-check to time-of-use)**라고 부르며, 파일 권한을 검사한 뒤 여는 사이에 심볼릭 링크로 바꿔치기하는 고전적 보안 취약점과 같은 구조다.

복사를 먼저 하면 그 복사본은 아무도 손댈 수 없는 우리만의 객체이므로, **검증한 것과 보관되는 것이 같은 객체임이 보장된다.** Effective Java가 명시적으로 경고하는 순서이기도 하다 (가산점 포인트).

여기에 한계까지 덧붙이면 좋다 — **복사는 얕은 복사이므로 원소가 가변이면 원소를 통한 바꿔치기는 여전히 가능하다.** 완전한 방어는 원소 타입까지 불변일 때 성립한다.

### "매 호출마다 복사하면 성능이 걱정되지 않나요?" (시니어 변별 포인트)

트레이드오프 판단 문제이므로 **양쪽 비용을 견줘서** 답하는 것이 좋다.

대부분의 도메인 객체 컬렉션은 원소가 수십에서 수백 개다. 그 정도 크기의 얕은 복사는 참조 값을 옮겨 담는 것뿐이라 비용이 사실상 무시 가능하다. 반면 **참조 공유 버그의 추적 비용은 훨씬 비싸다** — 변경 시점과 증상 시점이 떨어져 있어 스택트레이스가 범인을 가리키지 않으므로, 며칠에 걸친 역추적이 되기 쉽다. 측정되지 않은 성능 우려로 확정된 안전을 포기하는 거래는 대체로 손해다.

그래도 실제로 병목이 **측정되면** 선택지가 셋이다.

**① `unmodifiableList` 뷰로 바꿔 래퍼 비용만 지불한다.** 대신 "원본이 바뀌면 반환값도 바뀐다"는 성질을 받아들이고 문서화해야 한다.

**② 내부 표현 자체를 불변 컬렉션으로 바꾼다.** 생성 시점에 `List.copyOf`로 고정해 두면 getter는 그대로 반환해도 안전하고, `List.copyOf`가 이미 불변인 인자를 그대로 돌려주는 최적화까지 얹히므로 매 호출 복사가 사라진다. **가장 근본적인 해법**이다.

**③ 컬렉션을 통째로 노출하지 않는다.** `lineCount()`, `totalAmount()`, `Stream<OrderLine> lines()` 같은 질의 메서드로 좁힌다.

**③이 가장 캡슐화다운 해법**이고, "getter를 어떻게 방어하나"에서 **"왜 컬렉션을 통째로 줘야 하나"로 질문을 되돌리는** 답변이 설계 감각을 보여준다. 계산 로직이 데이터를 가진 객체 쪽으로 옮겨 오면서 방어 고민이 자연히 사라지기 때문이다.

### "`Collections.unmodifiableList`로 감싸 반환하면 충분한가요?"

**목적에 따라 다르다.** 뷰와 복사의 차이를 아는지가 이 질문의 핵심이다.

`unmodifiableList`는 **복사가 아니라 뷰(원본을 들여다보는 창문)**다. 호출자의 수정은 `UnsupportedOperationException`으로 막지만, **원본이 바뀌면 이미 나간 반환값의 내용도 함께 바뀐다.** 반환받은 쪽이 그 리스트를 오래 들고 있다가 다시 읽으면 "받았을 때와 내용이 다른" 상황을 만나고, 순회 중에 원본이 수정되면 `ConcurrentModificationException`까지 난다.

그래서 **"밖에서 못 고치게 한다"가 목적이면 충분하고, "받은 시점의 상태를 보장한다"가 목적이면 부족하다.** 후자에는 `List.copyOf`가 맞다.

비용 대비로 정리하면, 뷰는 래퍼 객체 하나만 만들면 되므로 싸고, 복사는 원소 수에 비례한 비용이 든다. 그리고 **JPA 엔티티에서는 뷰가 오히려 정답**이다 — 하이버네이트가 추적하는 원본 인스턴스를 유지해야 변경 감지가 동작하고, 엔티티의 생명주기 안에서는 "지금 상태를 비춘다"는 성질이 자연스럽기 때문이다.

### "record를 쓰면 이 문제가 해결되나요?"

**아니다. record가 보장하는 것은 얕은 불변이다.**

필드 재대입만 막을 뿐, 컴포넌트가 가변 객체(List, 배열, `Date`)면 참조 공유 문제는 그대로다. `record Cart(List<Item> items)`의 **자동 생성 접근자는 내부 참조를 그대로 반환**하고, 생성자에 넘긴 리스트의 참조도 호출자가 계속 들고 있다.

그래서 record에서도 **컴팩트 생성자에서 `items = List.copyOf(items);`로 방어적 복사를 하는 것이 관용구**다. 컴팩트 생성자는 필드에 대입되기 직전에 실행되므로, 여기서 바꿔 두면 **저장 시점에 이미 불변**이 된다. 불변 객체의 참조는 공유해도 안전하므로 접근자는 손대지 않아도 된다.

"record니까 불변"이라는 말을 무비판적으로 받아들이지 않고 **얕은 불변과 깊은 불변을 구분하는지**가 이 질문의 확인 포인트다.

### "JPA 엔티티의 컬렉션 필드에도 방어적 복사를 적용하나요?"

**여기서는 원칙이 아니라 프레임워크 제약이 선택지를 좁힌다.**

하이버네이트는 엔티티를 영속 상태로 만들 때 컬렉션 필드를 자기 구현체(`PersistentBag` 등)로 바꿔치기하고, 그 구현체가 추가·삭제를 기록했다가 커밋 시점에 SQL로 바꾼다. 이게 변경 감지다. 그래서 두 가지 제약이 생긴다.

**필드 자체를 새 컬렉션으로 교체하면 안 된다.** 하이버네이트가 추적하던 인스턴스를 잃어 변경 감지가 끊기고, `orphanRemoval`이나 `cascade = ALL`이 걸려 있으면 "cascade가 걸린 컬렉션이 더 이상 소유 엔티티에서 참조되지 않는다"는 취지의 예외가 난다. 통째로 바꿔야 하면 같은 인스턴스에 `clear()` 후 `addAll()`을 한다.

**getter가 복사본을 반환하면 그 복사본에 대한 수정이 DB에 반영되지 않는다.** 보호로는 맞지만 호출자에게는 "예외도 안 나고 저장도 안 되는" 혼란이 된다.

그래서 실무 패턴은 **getter는 `Collections.unmodifiableList`로 감싸 반환하고, 추가·삭제는 `addLine()`/`removeLine()` 같은 의도가 드러나는 메서드로만 열어 주는 것**이다. 그 메서드 안에서는 원본 인스턴스에 직접 `add`/`remove`를 하므로 변경 감지가 정상 동작하고, 불변식 검증도 그 자리에서 할 수 있다. 반환이 뷰라 내부 변경이 비쳐 보이는 것은 엔티티 생명주기 안에서는 오히려 자연스럽다.

## 한 줄 요약

`private`은 필드 이름을 숨길 뿐이고 `final`은 참조를 고정할 뿐이라 상태를 지켜 주지 못한다 — `return lines;`가 돌려주는 것은 복사본이 아니라 같은 객체를 가리키는 주소값이므로 그 순간 도메인 객체의 검증 메서드는 전부 우회 가능해지고, 게다가 그 우회는 예외 없이 조용히 일어나 며칠 뒤 정산에서야 드러나기 때문에 스택트레이스가 범인을 가리키지 못한다. 그러니 **들어올 때는 복사한 뒤 복사본을 검증하고(TOCTOU 방지), 나갈 때는 `List.copyOf` 같은 불변 스냅샷을 내보내되(뷰는 원본이 바뀌면 함께 바뀐다는 것을 알고 고르고), 원소가 가변이면 얕은 복사로는 못 막는다는 한계까지 인지하는 것**이 이 주제의 완성이며, 가장 좋은 방어는 애초에 내부 상태를 불변으로 만들어 복사가 필요 없게 하거나 컬렉션을 통째로 노출하지 않는 것이다.
