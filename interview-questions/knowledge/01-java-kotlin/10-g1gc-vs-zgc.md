# G1GC vs ZGC — 어느 단계를 멈추고 하느냐가 모든 차이를 만든다

> 핵심 관전 포인트: **모든 GC는 결국 같은 세 가지 일(살아있는 객체 표시 = Mark, 죽은 객체 회수 = Sweep, 살아남은 객체를 한쪽으로 몰아 빈틈 제거 = Compact)을 한다. G1과 ZGC의 차이는 이 일들을 "애플리케이션을 멈춰 세우고 하느냐(STW), 애플리케이션이 도는 채로 하느냐(concurrent)"의 배치 하나뿐이고, 그 배치 차이가 나머지 모든 특징을 파생시킨다. G1은 Mark만 동시로 빼고 **객체 복사와 포인터 수정은 여전히 STW**로 하되 그 STW를 region 단위로 잘게 쪼개 pause 목표를 맞추는 절충이다. ZGC는 **컬러 포인터**(64비트 주소에서 실제로 안 쓰는 상위 비트에 마킹 상태를 심는 기법)와 **로드 배리어**(참조를 읽을 때마다 끼어드는 검사 코드)를 대가로 지불하고 복사까지 동시로 빼낸 극단이다. 그래서 G1의 pause는 힙과 live set 크기를 따라 커지지만 상시 오버헤드가 싸고, ZGC의 pause는 힙이 테라바이트급이어도 밀리초 미만이지만 모든 참조 읽기에 배리어 세금을 낸다. "지연에 민감하면 ZGC"라고 단답하는 대신 **"tail latency를 위해 throughput을 얼마나 낼 것인가"**의 교환으로 답하는 것이 이 질문의 본체다.**

---

## 0. 질문 + 의도

**질문**: "G1 GC와 ZGC의 차이를 설명해주세요. 지연시간(latency)에 민감한 서비스라면 무엇을 선택하겠습니까?"

**출제 의도**: GC 선택은 서비스 특성(처리량형 배치 vs p99 민감 API)에 따른 의사결정이고, 잘못 고르면 하드웨어를 늘려도 해결이 안 된다. "선택의 근거를 말할 수 있는가"로 인프라 결정에 참여할 수 있는 연차인지 가늠한다.

## 1. GC의 기본형 — STW는 어디서 생기는가

### 1-1. 전제 지식 — 참조가 무엇이고, 왜 GC를 어렵게 만드는가

GC 이야기를 시작하기 전에 **참조(reference)**가 메모리에 어떤 모습으로 존재하는지부터 확인하자. 이것이 뒤에 나올 모든 어려움의 출발점이다.

```java
User user = new User("철수");
```

이 한 줄에서 두 가지 일이 일어난다. `new User("철수")`가 힙(heap, 객체가 저장되는 메모리 영역) 어딘가 — 예를 들어 `0x7f3a00` 번지 — 에 실제 객체 데이터를 만든다. 그리고 변수 `user`에는 **객체 자체가 아니라 그 객체가 놓인 주소값 `0x7f3a00`이 담긴다.**

```
  변수 user             힙(heap)
 ┌──────────┐         ┌──────────────────┐
 │0x7f3a00  │ ──────> │ User 객체         │  <- 0x7f3a00 번지
 └──────────┘         │  name = "철수"    │
  (주소값을 담음)      └──────────────────┘
```

C/C++에서는 이것을 **포인터(pointer)**라 부르고 Java에서는 **참조(reference)**라 부른다. 이름은 다르지만 JVM 내부에 실제로 저장되는 값은 결국 객체의 주소이므로 본질은 같다. 이 문서에서 "포인터"와 "참조"는 같은 것을 가리킨다.

**여기서 GC의 근본 난제가 나온다.** GC는 단편화(memory fragmentation, 빈 공간이 여기저기 작은 조각으로 흩어져 실제 여유는 있는데 큰 객체를 넣을 연속 공간이 없는 상태)를 없애기 위해 살아남은 객체를 한쪽으로 몰아 붙인다. 즉 **객체를 옮긴다.** `0x7f3a00`에 있던 객체를 `0x9c1200`으로 이사시키는 것이다.

그런데 그 객체를 가리키던 변수·필드·배열 원소는 전부 옛 주소 `0x7f3a00`을 값으로 들고 있다. 이사한 순간 이 값들은 전부 **아무것도 없는 자리를 가리키는 쓰레기 값**이 된다.

```
[이사 전]                          [이사 후 — 갱신하지 않으면]
 필드 A ─┐                          필드 A ─┐
 필드 B ─┼─> 0x7f3a00 : User        필드 B ─┼─> 0x7f3a00 : (빈 자리)
 배열[7] ┘                          배열[7] ┘        User는 0x9c1200으로 이사함
```

**그래서 객체를 옮기려면 그 객체를 가리키던 모든 참조를 찾아내 새 주소로 고쳐 써야 한다.** 그리고 고쳐 쓰는 도중에 애플리케이션 스레드가 옛 주소를 읽어버리면 프로그램이 깨진다. 그러니 가장 단순한 해법은 **"고쳐 쓰는 동안 애플리케이션을 전부 멈추는 것"** — 이것이 STW가 생기는 근본 이유다.

**STW(Stop-The-World)**란 GC가 애플리케이션 스레드를 **전부 멈춰 세우고** 자기 일을 하는 구간이다. 그동안 세상(애플리케이션)이 멈춘다고 해서 Stop-The-World라고 부른다. 이 구간에는 요청 처리도, 응답 전송도, 타이머도 전부 정지한다. 사용자 입장에서는 그냥 서버가 응답하지 않는 시간이다.

이 문서 전체를 관통하는 질문은 하나다. **"객체를 옮기고 참조를 고치는 이 위험한 작업을, 세상을 멈추고 할 것인가 돌아가는 채로 할 것인가."** G1과 ZGC는 이 질문에 서로 다르게 답한 두 개의 설계다.

### 1-2. GC의 3대 작업 — Mark / Sweep / Compact

고전적인 GC는 세 가지 작업으로 이루어진다. 각각이 무엇인지 정확히 구분해 두어야 뒤의 비교가 읽힌다.

| 작업 | 하는 일 |
|---|---|
| **Mark**(표시) | root에서 출발해 참조 그래프를 따라가며 도달 가능한 객체에 "살아있음" 표시를 남긴다 |
| **Sweep**(쓸어내기) | 표시가 안 된(= 아무도 안 가리키는) 객체의 메모리를 **제자리에서** 회수해 빈 공간 목록에 등록한다 |
| **Compact**(다지기) | 살아남은 객체를 한쪽으로 밀어붙여 단편화를 없앤다. 객체가 움직이므로 포인터를 전부 수정해야 한다 |

**root(루트)**는 참조 추적의 출발점이다. 각 스레드의 스택에 있는 지역 변수, CPU 레지스터, static 필드 같은 "프로그램이 지금 확실히 손에 쥐고 있는 참조"들의 집합이다. root에서 출발해 참조를 따라가 닿을 수 있으면 살아있는 객체, 닿을 수 없으면 아무도 쓸 수 없는 쓰레기다.

root의 개수는 **스레드 수와 클래스 수에 비례하고 힙 크기와는 무관하다.** 힙이 100GB든 1TB든 스레드가 200개면 root는 200개 스택 분량이다. 이 사실이 나중에 ZGC의 pause가 왜 힙 크기와 무관한지를 설명한다. 지금 기억해 두자.

### 1-3. 기본형의 문제 — pause가 힙 크기에 정비례한다

가장 단순한 형태(Serial GC나 Parallel GC의 Full GC)는 세 작업을 전부 하나의 STW 안에서 처리한다.

```
[앱 실행 중...] ── 힙 부족! ──> [STW 시작]
                                  (1) Mark  (2) Sweep  (3) Compact
                                [STW 끝] ──> [앱 재개]
```

이 구조의 문제는 명확하다. **pause 시간이 살아있는 객체 수에 정비례한다.** Mark는 살아있는 객체 전부를 순회해야 하고, Compact는 살아있는 객체 전부를 옮기고 그것을 가리키는 참조 전부를 고쳐야 한다. 그리고 살아있는 객체 수는 대체로 힙 크기를 따라 늘어난다.

힙 8GB면 Full GC 한 번에 수 초, 힙 수십 GB면 수십 초가 나온다. HTTP 요청 타임아웃이 3초인 서비스에서 5초 STW가 걸리면 그 순간의 모든 요청이 실패한다. **GC의 역사 전체가 이 하나의 문제를 푸는 과정이었다고 봐도 된다.**

### 1-4. 첫 번째 답 — 세대 가설

첫 번째 돌파구는 알고리즘이 아니라 관찰이었다.

> "대부분의 객체는 생성 직후 금방 죽는다."

이것을 **세대 가설(generational hypothesis)**이라고 부른다. 요청 처리 중에 만든 DTO, 문자열, 임시 리스트는 요청이 끝나면 전부 쓰레기가 된다. 반대로 커넥션 풀이나 캐시처럼 한번 오래 산 객체는 앞으로도 오래 살 확률이 높다.

그래서 힙을 두 구역으로 나눈다.

- **Young(젊은 세대)**: 새로 만든 객체가 들어가는 곳. 자주, 그러나 빠르게 수거한다.
- **Old(늙은 세대)**: Young에서 여러 번 살아남은 객체가 옮겨 가는 곳. 가끔 수거한다.

Young 수거가 빠른 이유가 중요하다. Young 영역은 대부분이 쓰레기라 **살아남는 소수만 골라 다른 곳으로 복사하면 나머지 영역은 통째로 비워버릴 수 있다.** 죽은 객체를 하나씩 확인할 필요가 없다. 작업량이 "죽은 객체 수"가 아니라 "살아남은 객체 수"에 비례하는 것이다.

Young에서 몇 번 살아남은 객체를 Old로 옮기는 것을 **승격(promotion)**이라고 한다.

그런데 이 최적화는 문제를 절반만 푼다. **Old 영역 수거는 여전히 무겁고 느리다.** 그리고 Old를 어떻게 다루느냐가 정확히 G1과 ZGC를 가르는 지점이다.

### 1-5. 두 번째 답 — region과 복사

두 번째 돌파구는 힙을 잘게 나누는 것이다. **region(리전)**은 힙을 일정 크기의 여러 조각으로 나눈 그 조각 하나를 말한다. 힙 전체를 한 덩어리로 보지 않고 수천 개의 region으로 나눠 관리한다.

region으로 나누면 무엇이 가능해지는가. **부분 수거**가 가능해진다. "지금은 이 region 20개만 치우겠다"고 고를 수 있다. 힙 전체를 대상으로 하면 작업량을 조절할 수 없지만, region 단위면 이번에 몇 개를 처리할지 정해서 pause 시간을 통제할 수 있다.

그리고 region 안에서는 Sweep과 Compact가 하나로 합쳐진다. 이것을 **복사(evacuation, 대피)**라고 부른다.

```
[수거 전]  region A: [살][죽][죽][살][죽][죽][죽][살]
                       |            |              |
                       └── 살아있는 3개만 퍼낸다 ──┘
                                    ↓
[수거 후]  region B: [살][살][살]...       region A: 통째로 반납 (내용 확인 없이)
```

살아있는 객체만 다른 region으로 퍼내고 나면, 원래 region에 남은 것은 전부 쓰레기다. **그러니 그 region은 내용을 하나도 들여다보지 않고 통째로 비운다.** 죽은 객체를 개별적으로 회수하는 Sweep 작업이 사라지고, 퍼내는 행위 자체가 곧 Compact(빈틈 없이 몰아붙이기)가 된다.

방식별로 3대 작업이 어떻게 대응되는지 정리하면 이렇다.

| 방식 | Mark | Sweep | Compact |
|---|---|---|---|
| Mark-Sweep (CMS) | 함 | 함 | 안 함 — 단편화가 고질병 |
| Mark-Sweep-Compact (Serial/Parallel의 Full GC) | 함 | 함 | 함 |
| **Mark-Evacuate (G1, ZGC)** | 함 | 복사에 흡수 | 복사에 흡수 |

정리하면 G1과 ZGC는 **"세대 가설 + region + 복사"라는 뼈대를 공유한다.** 여기까지는 같다. 남은 질문은 하나뿐이다 — **그 복사를, 세상을 멈추고 할 것인가 돌아가는 채로 할 것인가.**

## 2. G1GC — "STW로 하되, 잘게 나눠서"

**G1의 전략: 복사를 동시에 하는 건 너무 어렵다. STW로 하되, 한 번에 조금씩만 하자.**

### 2-1. 힙을 동일 크기 region으로 쪼갠다

G1은 힙을 **크기가 전부 같은** region으로 나눈다. region 크기는 1MB에서 32MB 사이의 2의 거듭제곱이고, JVM이 "region 개수가 대략 2048개가 되도록" 힙 크기를 보고 자동으로 정한다. 8GB 힙이면 4MB짜리 region 약 2048개가 된다. `-XX:G1HeapRegionSize`로 직접 지정할 수도 있다.

각 region은 고정된 역할을 갖지 않고 **그때그때 역할을 부여받는다.** Eden(새 객체가 할당되는 곳), Survivor(Young GC를 한 번 이상 버틴 객체가 머무는 곳), Old, Humongous(2-6에서 설명) 중 하나가 된다. 어제 Eden이던 region이 오늘 Old일 수 있다.

```
[G1의 힙 — 역할이 흩어져 있다]
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ E  │ O  │ E  │ S  │ O  │ 빈 │ H  │ H  │   E=Eden  S=Survivor
├────┼────┼────┼────┼────┼────┼────┼────┤   O=Old   H=Humongous
│ O  │ 빈 │ E  │ O  │ E  │ S  │ O  │ 빈 │
└────┴────┴────┴────┴────┴────┴────┴────┘
```

Young 영역과 Old 영역이 힙에서 연속된 한 덩어리가 아니라 **역할 라벨이 붙은 region의 집합**이라는 점이 기존 GC와의 차이다. 이 덕분에 "Young을 몇 MB로 할지"를 미리 못 박지 않고 GC 때마다 유연하게 조절할 수 있다.

### 2-2. Remembered Set — 부분 수거를 가능하게 하는 장치

여기서 먼저 풀어야 할 문제가 하나 있다. **"Young region만 수거하겠다"고 정했을 때, Young 객체를 가리키는 참조를 어떻게 다 찾아낼 것인가?**

root(스택, static)에서 출발해 그래프를 순회하면 찾을 수 있다. 그런데 Old region에 있는 어떤 객체가 Young 객체를 가리키고 있을 수도 있다. 그것을 놓치면 살아있는 객체를 죽은 것으로 오판해 회수해 버린다. 그렇다고 그 참조를 찾겠다고 Old 영역 전체를 스캔하면, 부분 수거를 하는 의미가 없어진다. **Young만 치우려고 힙 전체를 읽는 꼴**이기 때문이다.

그래서 **Remembered Set(RSet, 기억 집합)**을 둔다. RSet은 각 region마다 하나씩 딸려 있는 자료구조로, **"이 region 안의 객체를 바깥에서 가리키는 참조들이 어디에 있는가"**를 기록한다. 이름 그대로 "누가 나를 가리키는지 기억해 두는 표"다.

```
Old region X          Young region Y
┌──────────────┐      ┌──────────────┐
│ 객체 P ──────┼─────>│ 객체 Q       │
└──────────────┘      │              │
                      │ RSet: "Old X │  <- Y를 수거할 때 Old 전체를 뒤지지 않고
                      │  안에 나를 가 │     RSet에 적힌 자리만 확인하면 된다
                      │  리키는 곳 있 │
                      │  음"          │
                      └──────────────┘
```

RSet은 공짜가 아니다. 애플리케이션이 `a.field = b` 같은 참조 대입을 할 때마다 "이게 region 경계를 넘는 참조인가?"를 확인하고 넘으면 기록해야 한다. 이렇게 **참조를 쓸 때마다 끼어드는 코드**를 **write barrier(쓰기 배리어)**라고 부른다. 문 앞에 세워둔 검문소(barrier)처럼 모든 참조 쓰기가 이곳을 통과한다는 뜻이다.

write barrier의 비용이 G1의 상시 오버헤드다. 그리고 **힙이 커지고 region이 많아질수록 region 간 참조가 늘어 RSet이 비대해지고 스캔 비용도 올라간다.** 이 사실은 뒤에서 "G1의 pause가 왜 힙 크기의 영향을 받는가"의 답 중 하나가 된다.

### 2-3. Young GC — 전부 STW로

Eden region들이 가득 차면 Young GC가 돈다.

```
Eden이 가득 참
  [STW 시작]
     (1) root 스캔 + RSet 스캔  — 살아있는 young 객체를 찾을 출발점 확보
     (2) 살아있는 객체를 Survivor 또는 Old region으로 복사(evacuation)
     (3) 그 객체를 가리키던 포인터를 전부 새 주소로 수정
  [STW 끝]
```

**복사와 포인터 수정이 전부 STW 안에서 일어난다.** 1-1에서 본 그대로다 — 옮기는 동안 애플리케이션이 옛 주소를 읽지 못하게 하는 가장 단순한 방법이 멈추는 것이기 때문이다.

따라서 pause 시간은 **살아남은 young 객체의 양(live set)**에 비례한다. G1은 이 pause를 목표치 안에 넣기 위해 **다음 GC에 쓸 young region 개수를 조절한다.** 목표치는 `-XX:MaxGCPauseMillis`이고 기본값은 200ms다. 이번 GC가 목표보다 오래 걸렸으면 다음번엔 young을 작게 잡고, 여유가 있었으면 크게 잡는다.

여기서 짚어야 할 제약이 하나 있다. **Young GC는 대상을 쪼갤 수 없다.** 수거하기로 한 young region은 전부 한 번의 STW에서 처리해야 한다. young을 작게 잡아 pause를 줄일 수는 있지만, 그러면 GC 빈도가 올라가 처리량이 떨어진다. pause와 throughput은 여기서 정면으로 맞바꾸는 관계다.

### 2-4. 동시 마킹 사이클과 SATB

Old 영역 점유율이 임계치를 넘으면 G1은 Old를 치울 준비에 들어간다. 임계치는 `-XX:InitiatingHeapOccupancyPercent`(IHOP)이고 초기값은 힙의 45%다. 요즘 JDK의 G1은 실행 통계를 보고 이 시점을 자동 조정한다.

여기서 하는 일은 **"각 Old region에 살아있는 객체가 얼마나 있는지" 통계를 내는 것**이다. 이 통계가 있어야 다음 단계에서 "가성비 좋은 region"을 고를 수 있다.

이 마킹은 대부분 애플리케이션과 **동시에** 진행된다.

```
[STW] Initial Mark  : root가 직접 가리키는 old 객체만 마킹. Young GC에 얹혀 실행돼 추가 비용이 거의 없다
[동시] Concurrent Mark : 참조 그래프를 순회하며 살아있는 old 객체를 마킹. 앱이 도는 채로 진행
[STW] Remark        : 마킹 도중 앱이 바꾼 참조를 마무리 반영
[STW] Cleanup       : region별 live 비율 집계. 살아있는 객체가 하나도 없는 region은 이 자리에서 즉시 회수
```

**마킹을 앱과 동시에 하면 문제가 생긴다.** 마킹하는 도중에 애플리케이션이 참조를 바꿔버리면, 이미 지나간 자리에 새로 연결된 객체를 놓칠 수 있다. 살아있는데 안 표시된 객체가 생기고, 그 객체는 회수되어 프로그램이 깨진다.

G1의 해법은 **SATB(Snapshot-At-The-Beginning, 시작 시점의 스냅샷)**다. 이름 그대로 **"마킹을 시작한 순간의 객체 그래프 사진을 기준으로 판정한다"**는 원칙이다. 마킹 시작 시점에 살아있던 객체는 도중에 참조가 끊겨도 이번 사이클에서는 살아있는 것으로 취급한다.

구현은 write barrier로 한다. 애플리케이션이 참조 필드를 덮어쓰기 **직전에**, 원래 들어 있던 옛 참조 값을 로그 버퍼에 기록해 둔다. 마커는 나중에 그 로그를 읽어 "끊겼지만 스냅샷 시점엔 살아있던" 객체까지 마저 방문한다.

```java
// 애플리케이션 코드
node.next = newNode;

// JVM이 실제로 실행하는 것 (개념상)
// 덮어쓰기 전의 값을 먼저 챙겨둔다. 이 참조가 사라지면
// 마커가 old 객체로 가는 유일한 길을 잃을 수 있기 때문이다.
satbBuffer.record(node.next);
node.next = newNode;
```

이 방식의 대가는 **floating garbage(떠다니는 쓰레기)**다. 마킹 도중에 죽은 객체는 스냅샷 기준으로는 살아있으므로 이번 사이클에서 회수되지 않고 다음 사이클로 넘어간다. 정확도를 조금 포기하고 동시성을 얻은 것이다. 다음 사이클에 회수되므로 누수는 아니다.

### 2-5. Mixed GC — "Garbage-First"라는 이름의 유래

마킹이 끝나면 "어느 region에 쓰레기가 많은지" 통계가 손에 들어온다. 이제 실제 수거다.

```
  [STW 시작]
     (1) 쓰레기 비율이 가장 높은 old region부터 고른다
         (= 살아있는 객체가 가장 적다 = 복사할 양이 가장 적다 = 가성비 최고)
     (2) pause 목표 안에 처리할 수 있는 만큼만 CSet(Collection Set, 수거 대상 집합)에 담는다
     (3) young region 전부 + CSet에 담긴 old region의 살아있는 객체를 복사
     (4) 포인터 수정
  [STW 끝]     <- 이 과정을 여러 번 반복해 Old를 조금씩 비워 나간다
```

young과 old를 **섞어서** 수거하기 때문에 **Mixed GC**라고 부른다.

그리고 여기가 **"Garbage-First"라는 이름의 유래**다. 힙 전체를 순서대로 치우는 대신 **쓰레기(garbage)가 가장 많은 region을 먼저(first) 치운다.** 살아있는 객체가 적은 region일수록 복사할 것이 적으니 같은 시간에 더 많은 공간을 회수한다. 쓰레기가 90% 찬 region 하나를 치우면 region 크기의 90%를 벌지만, 쓰레기가 10%인 region은 같은 노력에 10%밖에 못 번다. **한정된 pause 예산을 가장 수익률 높은 곳에 쓰는 전략**이고, 이 아이디어 자체가 컬렉터의 이름이 되었다.

### 2-6. humongous 객체 — G1의 아픈 곳

**humongous(거대) 객체**는 크기가 region 하나의 절반 이상인 객체를 말한다. region이 4MB면 2MB 이상인 객체가 여기 해당한다. 큰 배열, 파일을 통째로 읽은 바이트 배열, 수십만 건 조회 결과 리스트가 대표적이다.

이런 객체는 일반 region에 넣을 수 없어서 **Humongous region이라는 별도 취급을 받는다.** 객체 하나를 위해 연속된 region 여러 개를 통째로 이어 붙여 쓴다.

```
객체 크기 10MB, region 크기 4MB인 경우

┌────┬────┬────┬────┬────┐
│ O  │ H  │ H  │ H  │ O  │   H 세 칸(12MB)을 이어 붙여 10MB 객체 하나를 담는다
└────┴────┴────┴────┴────┘   남는 2MB는 그냥 버려진다
              ↑
   반드시 "연속된" 빈 region이어야 한다
```

문제는 두 가지다. 첫째, **연속된 빈 region을 찾아야 한다.** 힙에 빈 공간이 총 20MB 있어도 여기저기 흩어져 있으면 10MB 객체를 못 넣는다. 둘째, humongous 객체는 **복사 대상에서 제외되고 제자리에서 다뤄지므로** 단편화를 정리하는 손길이 닿지 않는다.

그래서 humongous 할당은 G1이 Full GC로 추락하는 대표적인 원인이 된다. 힙에 여유가 있어 보이는데도 "연속 공간이 없어서" GC가 터지는 상황이다.

### 2-7. 실패 모드 — Full GC 낭떠러지

G1의 정상 경로는 Young GC와 Mixed GC다. **Full GC는 정상 경로가 아니라 실패 시의 fallback(대비책)**이다. 다음 상황에서 발생한다.

- **evacuation failure (복사 실패)**: 살아있는 객체를 복사해 넣을 빈 region이 없다. GC 로그에는 `to-space exhausted`(옮겨 갈 공간 고갈)로 찍힌다.
- **동시 마킹이 할당 속도를 못 따라감**: 마킹이 끝나기 전에 힙이 다 차버린다.
- **humongous 할당 실패**: 연속된 빈 region을 확보하지 못한다.

Full GC로 떨어지면 **힙 전체를 대상으로 하는 단일 STW**가 걸린다. 1-3에서 본 기본형 그대로다. region 단위로 쪼개서 pause를 통제하던 모든 장치가 무력화되고, pause가 힙 크기에 정비례하는 최악의 시나리오로 돌아간다. 수 GB 힙에서 초 단위, 수십 GB에서 십 초 단위가 나온다.

**G1의 pause 특성을 논할 때 이 낭떠러지의 존재를 빼면 안 된다.** 평소에는 200ms를 잘 지키다가 어느 순간 8초짜리 pause 하나가 터지는 것이 G1의 실제 프로필이다.

### 2-8. G1의 한 사이클 — 타임라인

지금까지의 이야기를 시간축에 올리면 이렇게 된다.

```
시간 ──────────────────────────────────────────────────────────>

[앱]──█ Young ──[앱]──█ Young ──[앱]──█ Young ──[앱]── ...
       (STW)           (STW)           (STW)
                                          │
                            Old 점유율이 IHOP(초기 45%) 초과
                                          ↓
                       █ Initial Mark   (STW, Young GC에 편승)
                       ░░░░░░░░░░░░░░░  Concurrent Mark (앱과 동시)
                       █ Remark         (STW)
                       █ Cleanup        (STW, 완전히 빈 region은 즉시 회수)
                                          ↓
[앱]──█ Mixed ──[앱]──█ Mixed ──[앱]──█ Mixed ──[앱]── (몇 차례 반복 후 종료)
       (STW)          (STW)          (STW)
       young 전부 + 가성비 좋은 old region 몇 개씩

       ↓ 복사할 빈 공간이 없거나, 마킹이 할당을 못 따라가면
       ███████████████ Full GC (힙 전체 STW — 낭떠러지)

█ = STW    ░ = 앱과 동시(concurrent)
```

**한 줄로 요약하면**: Mark는 (대부분) 동시로 뺐지만, **복사와 포인터 수정은 언제나 STW**다. 대신 그 STW의 분량을 region 단위로 쪼개고 가성비 좋은 region부터 골라 pause 목표를 맞춘다.

## 3. ZGC — "복사까지 앱이 도는 채로"

**ZGC의 전략: 쪼개서 나눠 하는 것도 결국 한계가 있다. 복사 자체를 앱과 동시에 해버리자.**

### 3-1. 문제 정의 — 동시 복사를 하려면 무엇이 필요한가

1-1로 돌아가자. 복사를 STW로 하는 이유는 **"객체가 이사하는 도중에 애플리케이션이 옛 주소를 읽으면 프로그램이 깨지기 때문"**이었다.

그러면 동시 복사를 하려면 무엇이 필요한가. 조건은 하나로 정리된다.

> **애플리케이션이 참조를 읽는 그 순간에, 그 참조가 최신 주소인지 확인하고 아니면 고쳐서 건네줄 수 있어야 한다.**

이 조건만 만족하면 애플리케이션은 절대 옛 주소를 만지지 못하고, GC는 마음 놓고 객체를 옮길 수 있다. ZGC의 두 가지 핵심 장치는 정확히 이 조건을 만족시키기 위한 것이다.

- **컬러 포인터**: 참조 자체에 "이 참조가 어느 단계까지 처리됐는가"를 새겨 넣는다. 확인을 싸게 만드는 장치다.
- **로드 배리어**: 참조를 읽을 때마다 그 표식을 확인하고 필요하면 고친다. 실제로 고쳐 주는 장치다.

### 3-2. 컬러 포인터 — 64비트 주소의 남는 비트에 색을 심는다

**컬러 포인터(colored pointer)**는 포인터 값의 **남는 비트에 GC 처리 상태를 저장하는 기법**이다. 그 상태를 "색(color)"이라고 부르기 때문에 색칠된 포인터라는 이름이 붙었다.

왜 남는 비트가 있는가. 여기가 **64비트에서만 가능한 이유**다.

64비트 포인터로는 이론상 2의 64승 바이트, 즉 16엑사바이트를 주소로 지정할 수 있다. 그런데 그만한 메모리를 가진 기계는 존재하지 않는다. 실제 x86-64 CPU는 주소 비트를 48개만 의미 있게 쓰고, 나머지 상위 비트는 사실상 놀고 있다. **주소 표현에 비트를 다 안 쓰기 때문에 상위에 남는 자리가 생긴다.**

```
64비트 포인터 한 개

 63          48 47                                        0
┌──────────────┬───────────────────────────────────────────┐
│  안 쓰는 비트  │            실제 객체 주소                  │
│  ↑           │                                           │
│  ZGC가 여기에 │                                           │
│  색을 심는다   │                                           │
└──────────────┴───────────────────────────────────────────┘
```

32비트에서는 이것이 불가능하다. 4GB 주소 공간을 32비트가 빠듯하게 다 쓰고 있어 **비어 있는 비트가 없기 때문**이다. ZGC가 64비트 전용인 이유가 이것이다.

색의 종류는 개념적으로 셋이다.

- **marked0 / marked1**: "이 참조는 이번 마킹 주기에 처리했다"는 표식. 왜 두 개인지는 3-7에서 설명한다.
- **remapped**: "이 참조의 주소는 재배치 검사를 통과한 최신 주소다"라는 보증서.
- (여기에 finalizable 같은 보조 색이 더 붙는다. 실제 비트 배치는 JDK 버전에 따라 다르다.)

**색이 무엇을 나타내는지 정확히 짚어야 한다.** 색은 **객체가 살았는지 죽었는지가 아니라, "이 참조가 현재 GC 단계의 처리를 통과했는가"라는 참조의 처리 상태**를 나타낸다. 같은 객체를 가리키는 두 참조가 서로 다른 색일 수 있다. 하나는 이미 검사를 통과했고 다른 하나는 아직 아무도 안 읽어서 옛 색인 채로 남아 있는 경우다.

색 비트를 쓰는 대가도 있다. 주소에 쓸 수 있는 비트가 줄어들어 **ZGC가 다룰 수 있는 힙 상한이 생긴다.** 현재 JDK의 ZGC는 최대 16TB 힙을 지원한다. 실무에서 걸릴 일은 없는 상한이다.

그리고 기술적 걸림돌이 하나 더 있다. **CPU는 색 비트가 붙은 주소를 그대로 따라갈 수 없다.** 실제로는 없는 번지이기 때문이다. 초기 ZGC는 같은 물리 메모리를 색마다 다른 가상 주소에 겹쳐 매핑(multi-mapping)해서 어느 색으로 접근해도 같은 객체에 닿게 만들었고, 세대형 ZGC부터는 로드 배리어가 색 비트를 지운 주소를 넘겨주는 방식으로 바뀌었다. 어느 쪽이든 **색은 GC와 배리어만 보는 정보이고 애플리케이션 코드에는 보이지 않는다.**

### 3-3. 로드 배리어 — 참조를 읽을 때마다 끼어드는 검사

**로드 배리어(load barrier, 읽기 배리어)**는 애플리케이션 스레드가 **힙에서 참조를 읽을 때마다** 실행되는 작은 검사 코드다. G1의 write barrier가 참조를 **쓸 때** 끼어드는 것과 대칭이다.

```java
// 애플리케이션 코드
Node next = node.next;   // 힙에서 참조를 읽는다

// JVM이 실제로 실행하는 것 (개념상)
Node next = node.next;
if (colorOf(next) != currentGoodColor) {
    // 느린 경로: 필요한 처리를 하고 참조를 고쳐 쓴다
    next = slowPath(next);
}
```

판단 기준은 단 하나다. **"이 포인터의 색이 지금의 '좋은 색(good color)'인가?"**

- **맞으면** 그냥 통과한다. 비교 명령 몇 개라 비용이 거의 없다. 절대 다수의 읽기가 여기로 간다.
- **아니면** 느린 경로로 들어가 필요한 처리(마킹 또는 주소 교정)를 하고, **그 참조를 좋은 색으로 고쳐서 원래 자리에 다시 써 넣는다.**

이 "고쳐서 다시 써 넣는" 동작이 **self-healing(자가 치유)**이다. 이름 그대로, 한 번 만져진 참조는 스스로 최신 상태로 고쳐지므로 **다음번에 같은 참조를 읽을 때는 빠른 경로로 통과한다.** 느린 경로 비용은 참조마다 한 번씩만 낸다.

그리고 여기서 ZGC의 pause가 짧은 이유 하나가 더 나온다. GC 단계가 바뀔 때 **"좋은 색"의 정의만 바꾸면** 힙에 있는 모든 포인터가 자동으로 "검사 필요" 상태가 된다. **힙을 순회하며 플래그를 리셋하는 작업이 필요 없다.** 기준 하나를 바꾸는 것으로 수억 개 포인터의 상태를 한꺼번에 무효화하는 셈이다.

비유하자면 출입증 색깔 바꾸기다. 어제까지 파란 출입증이 유효했는데 오늘부터 초록만 유효하다고 선언하면, 파란 출입증 소지자를 일일이 찾아다닐 필요 없이 **검문소에 오는 사람만 그 자리에서 교체해 주면 된다.** 안 오는 사람은 애초에 문제가 안 된다.

### 3-4. Mark 단계

```
█ Pause Mark Start (STW, 1ms 미만) : root 스캔만. "좋은 색"을 markedX로 전환
░ Concurrent Mark  (앱과 동시)
     - 참조 그래프를 순회하며 살아있는 객체를 mark bitmap에 기록
     - 방문한 포인터는 "이번 주기 처리 완료" 색으로 색칠
     - 앱 스레드도 로드 배리어의 느린 경로를 통해 마킹에 참여한다
█ Pause Mark End   (STW, 1ms 미만) : 마킹 종료 동기화
```

**여기서 자주 헷갈리는 것을 정리하고 가자. 마킹과 색칠은 같은 것이 아니다.**

- **마킹(marking)**: 살아있는 객체를 찾아 **mark bitmap**(어느 주소에 살아있는 객체가 있는지 비트로 표시하는 별도의 표)에 기록하는 것. 모든 GC에 공통된 개념이다.
- **포인터 색칠(coloring)**: "이 참조는 이번 단계 처리를 마쳤다"를 포인터 비트에 새기는 것. ZGC 특유의 기법이다.

색칠은 마킹의 **부수 효과이자 중복 작업 방지 장치**이지 마킹의 정의가 아니다. 같은 참조를 두 번 읽어도 두 번째는 색이 맞으니 그냥 통과한다는 것이 색칠의 역할이다.

### 3-5. Relocate 단계 — 혁신의 핵심

마킹이 끝나면 mark bitmap 통계로 **"쓰레기가 많은 region"**을 골라 **relocation set**(재배치 대상 집합)으로 정한다. G1의 garbage-first와 같은 아이디어이고, 이 선정 작업 자체도 앱과 동시에 진행된다.

```
█ Pause Relocate Start (STW, 1ms 미만) : root가 가리키는 객체만 이동·수정.
                                         "좋은 색"을 remapped로 전환
░ Concurrent Relocate  (앱과 동시!)
     - GC 스레드가 relocation set의 살아있는 객체를 새 region으로 복사
     - 옛 주소 → 새 주소 대응을 forwarding table(포워딩 테이블)에 기록
     - 복사가 끝난 옛 region은 즉시 회수해 재사용
```

**forwarding table(포워딩 테이블)**은 "이 객체는 여기로 이사 갔습니다"를 적어 둔 전입신고서 모음이다. 우편물 주소 이전 서비스와 같다. 옛 주소로 온 접근을 새 주소로 안내한다. relocation set의 각 region마다 하나씩 만들어지고, 그 region의 모든 참조가 갱신되고 나면 테이블도 버려진다.

이 동안 애플리케이션이 참조를 읽으면 로드 배리어가 네 가지 중 하나로 처리한다.

| 읽은 포인터의 상태 | 배리어의 동작 |
|---|---|
| 색이 이미 remapped | 검사 완료된 참조 — 그냥 통과 |
| 옛 색 + 가리키는 객체가 relocation set 밖 | 주소는 여전히 유효 — **색만 remapped로** 바꿔 씀 |
| 옛 색 + relocation set 안 + 이미 복사됨 | forwarding table에서 새 주소를 찾아 **"새 주소 + remapped"로** 고쳐 씀 |
| 옛 색 + relocation set 안 + 아직 안 옮겨짐 | **읽으려던 앱 스레드가 그 자리에서 직접 객체를 복사**하고 테이블에 기록한 뒤 새 주소를 쓴다 |

마지막 줄이 결정적이다. **아직 안 옮겨진 객체를 읽으려 하면, GC 스레드를 기다리는 게 아니라 읽으려던 스레드가 직접 복사해 버린다.** 그래서 애플리케이션이 옛 주소의 객체를 만질 가능성이 **원천적으로 차단**된다. "언젠가는 옮겨지겠지"가 아니라 "읽는 순간 이미 옮겨져 있다"가 보장된다.

### 3-6. Remap — 다음 사이클에 무임승차

Relocate가 끝난 뒤에도 힙에는 **아무도 안 읽어서 옛 색인 채로 남은 포인터**가 있다. 이것들도 결국 새 주소로 갱신되어야 한다.

ZGC는 이 갱신을 위한 별도 순회 단계를 만들지 않는다. **다음 사이클의 Concurrent Mark가 어차피 참조 그래프를 전부 순회하므로, 그때 겸사겸사 새 주소로 고치면서 새 마킹 색을 칠한다.** 순회 비용 한 번을 통째로 아끼는 설계다.

```
[사이클 N]              [사이클 N+1]
Mark → Relocate         Mark (순회하면서 남은 옛 포인터를 remap까지 처리)
```

### 3-7. 색이 두 개인 이유 — marked0와 marked1

이제 "마킹 색이 왜 두 개인가"에 답할 수 있다.

```
        [사이클 N: mark]      [사이클 N: relocate]     [사이클 N+1: mark]
색:       marked0        →       remapped         →       marked1
의미:  "이번 주기 생존 확인"   "주소 최신 보증"        "새 주기 생존 재확인"
```

- **marked 색**이 보증하는 것은 "이번 주기에 살아있음을 확인했다"까지다. 마킹 시점에는 relocation set이 아직 정해지지 않았으므로 **주소가 최신인지는 보증하지 못한다.**
- **remapped 색**이 보증하는 것은 "재배치 검사를 통과한 최신 주소"다. 생사가 아니라 주소의 최신성에 대한 보증서다.

두 개가 필요한 이유는 3-6 때문이다. remap을 다음 마킹에 얹어 지연 처리하므로, **힙에 지난 주기의 마킹 색과 이번 주기의 마킹 색이 잠시 공존한다.** 색이 하나뿐이면 "이게 이번 것인지 지난 것인지"를 구분할 수 없다.

색을 두 개 두고 주기마다 뒤집으면(marked0 → marked1 → marked0 → ...) **지난 주기 색은 자동으로 "낡은 색"이 된다.** 힙을 순회하며 리셋할 필요도, 그 리셋을 위한 STW도 없다. 3-3에서 말한 "좋은 색 전환"의 실체가 이것이다.

### 3-8. ZGC의 한 사이클 — 타임라인

```
시간 ──────────────────────────────────────────────────────────>

█ Pause Mark Start        (STW, 1ms 미만 — root 스캔만)
░░░░░░░░░░░░░░░░░░░░░░░   Concurrent Mark            (앱과 동시)
█ Pause Mark End          (STW, 1ms 미만)
░░░░░░░░░░░              Concurrent Prepare          (앱과 동시 — relocation set 선정)
█ Pause Relocate Start    (STW, 1ms 미만 — root가 가리키는 객체만)
░░░░░░░░░░░░░░░░░░░░     Concurrent Relocate         (앱과 동시 — 여기가 핵심)
                                    ↓
              남은 옛 포인터의 갱신은 다음 사이클의 Concurrent Mark가 흡수

█ = STW    ░ = 앱과 동시(concurrent)
```

G1의 타임라인(2-8)과 나란히 놓고 보면 차이가 한눈에 들어온다. **G1은 검은 칸(STW) 안에서 복사를 하고, ZGC는 흰 칸(동시) 안에서 복사를 한다.** 그리고 ZGC의 검은 칸은 전부 root 처리 수준이라 힙이 아무리 커도 두께가 변하지 않는다.

**한 줄로 요약하면**: Mark도 동시, **복사와 포인터 수정까지 동시**다. STW는 root를 다루는 세 지점뿐이고, root 개수는 스레드 수에 비례하며 **힙 크기와 무관**하다.

### 3-9. 비교 — 단계별 STW 배치가 모든 것을 만든다

두 컬렉터가 같은 일을 어디서 하는지 나란히 놓으면 이렇다.

| 단계 | 기본형 (Parallel) | G1 | ZGC |
|---|---|---|---|
| Mark | STW | 대부분 동시 | 동시 |
| 수거 대상 선정 | (전체 대상) | STW 중, 가성비순 | 동시, 가성비순 |
| **객체 복사** | STW | **STW** | **동시** (결정적 차이) |
| **포인터 수정** | STW | **STW** | **동시** (self-healing) |
| 상시 오버헤드 | 없음 | write barrier (쓸 때) | **load barrier (읽을 때)** + 색 비트 |

이 표 한 장에서 나머지 특징이 전부 도출된다. 하나씩 따라가 보자.

#### G1의 pause는 힙과 live set 규모의 영향을 받는다

복사와 포인터 수정이 STW 안에 있으니, pause = 복사할 살아있는 객체의 양 + RSet 스캔 비용이다.

G1의 설계 의도 자체는 "pause 크기는 고정하고 횟수를 늘린다"가 맞다. Mixed GC는 실제로 그렇게 동작한다 — CSet 크기를 조절해 pause를 목표 안에 맞춘다. 그런데 현실에서는 힙이 커지면 pause도 커지는 경향이 나타난다. 이유가 셋이다.

첫째, **Young GC는 대상을 쪼갤 수 없다**(2-3). 수거하기로 한 young region은 한 번의 STW에서 전부 처리된다. 힙이 크면 young도 크게 잡히는 경향이 있어 복사량이 늘고, 줄이자니 GC 빈도가 급증해 처리량이 나빠진다.

둘째, **RSet 스캔 단가가 힙에 비례한다**(2-2). 힙이 크면 region이 많아지고 region 간 참조가 늘어 RSet이 비대해진다. CSet 크기를 조절해도 **region 하나를 처리하는 단가 자체가 올라간다.**

셋째, **Full GC 낭떠러지**(2-7)가 있다. 최악의 경우 힙 전체가 하나의 STW로 처리된다.

#### ZGC는 힙이 테라바이트급이어도 pause가 밀리초 미만이다

STW에서 하는 일이 root 처리뿐이기 때문이다. 1-2에서 짚은 대로 **root 개수는 스레드 수에 비례하고 힙 크기와 무관하다.** 무거운 일(마킹, 복사, 포인터 수정)은 전부 동시 단계로 밀어냈다.

다만 **"STW가 없다"는 표현은 틀렸다.** Mark Start, Mark End, Relocate Start 세 곳에 짧은 STW가 있다. 정확한 표현은 **"pause가 힙 크기에 비례하지 않는다"**이고, 면접에서는 이 문장으로 말하는 것이 좋다. 참고로 상용 JVM GC 중 STW가 완전히 0인 것은 없다.

#### ZGC의 대가는 throughput 세금이다

복사를 동시에 하려면 "앱이 옛 주소를 읽는 사고"를 막아야 하고, 그 대가가 **모든 참조 읽기에 붙는 로드 배리어**다.

여기가 핵심이다. **읽기는 쓰기보다 압도적으로 빈번하다.** 필드 접근, 배열 순회, 컬렉션 탐색 — 프로그램이 하는 일의 대부분이 읽기다. 그래서 G1의 write barrier보다 상시 비용이 크다.

**STW라는 뭉친 비용을 없앤 대신, 그 비용을 실행 시간 전체에 얇게 펴 바른 것**이라고 이해하면 정확하다. 총량이 사라진 게 아니라 분포가 바뀌었다. 여기에 컬러 포인터 관련 메모리 오버헤드도 더해진다.

#### G1은 균형형이고 여전히 기본값이다

Java 9부터 G1이 기본 GC다. 상시 배리어 비용이 상대적으로 싸고(write barrier만), STW 안에서 하는 복사는 구현이 단순하고 효율적이다. **수십 GB 이하 힙에 200ms급 pause가 허용되는 서비스라면 G1이 가장 좋은 절충**이다.

#### 실패 모드가 다르다

- **G1**: 수거가 할당을 못 따라가면 **전체 힙 STW인 Full GC 낭떠러지**로 떨어진다.
- **ZGC**: Full GC가 없다. 대신 회수가 할당을 못 따라가면 **할당하려는 스레드만 개별적으로 대기**한다. 이것을 **allocation stall(할당 지연)**이라고 부른다. 전체가 멈추지는 않지만 그 스레드의 지연은 발생한다.

할당률이 매우 높은 워크로드에서 allocation stall이 ZGC의 약점이었고, 이를 개선한 것이 세대형 ZGC다(3-11).

### 3-10. region 설계 비교

**둘 다 region 기반이다.** 이것은 취향이 아니라 복사 방식의 필연적 귀결이다. 부분 수거를 하려면 힙이 "골라낼 수 있는 단위"로 나뉘어야 하고, region별 live 비율을 집계해야 가성비 좋은 곳을 고를 수 있으며, 살아있는 객체를 퍼낸 뒤 통째로 반납할 대상도 region이다. G1이 확립한 뼈대를 ZGC가 그대로 계승했다.

다른 것은 region의 크기 정책이다.

| | G1 | ZGC |
|---|---|---|
| 크기 | **전부 동일** (1~32MB, 보통 힙/2048) | **세 가지 크기 클래스** — Small / Medium / Large |
| 큰 객체 | region 절반 이상이면 **humongous** — 연속 region 여러 개를 이어 붙임 | **Large region에 객체 하나만** 담고 복사하지 않음 |
| 역할 | Eden / Survivor / Old / Humongous를 동적으로 부여 | 세대형 ZGC에서 Young / Old 소속 |

이 차이가 만드는 실무적 결과가 humongous 문제다. G1은 큰 객체를 담으려면 **연속된 빈 region**을 확보해야 하고, 이것이 안 되면 evacuation failure에서 Full GC로 이어진다(2-6, 2-7). ZGC는 큰 객체 하나에 Large region 하나를 통째로 배정하고 복사하지 않으므로 "연속 공간을 못 구해서 터지는" 실패 양상이 구조적으로 완화된다.

### 3-11. 세대 설계 비교 — 두 개의 독립적인 축

여기서 자주 생기는 혼동을 정리하자. **"세대를 나누느냐"와 "복사를 언제 하느냐"는 서로 다른 축이다.**

```
축 1: 힙을 어떻게 나누고 무엇부터 수거하나
      → region, young/old, garbage-first        ← 두 GC가 같은 답으로 수렴했다

축 2: 수거 작업(특히 복사)을 언제 하나
      → STW냐 concurrent냐                      ← 두 GC를 가르는 본질
```

ZGC는 원래 세대 구분이 **없었다.** 힙 전체를 하나로 보고 동시에 마킹·복사했다. 그런데 3-9에서 본 allocation stall — 할당률이 높은 워크로드에서 회수가 할당을 못 따라가는 약점이 드러났다. 그래서 JDK 21에서 **세대형 ZGC(Generational ZGC)**가 도입되었다. `-XX:+ZGenerational`로 켜는 방식이었고, JDK 23부터는 세대형이 기본이 되었다. **세대 가설이 옳다는 것을 ZGC도 인정한 셈**이다.

세대를 도입하면 축 2도 같아지는가? 아니다. 구조가 같아져도 **실행 방식은 그대로 다르다.**

| Young 수거 | G1 | 세대형 ZGC |
|---|---|---|
| 방식 | STW 중에 복사 | **young 수거조차 동시에** |
| pause | young live set에 비례 (수 ms ~ 수십 ms) | root 처리만 STW — 여전히 1ms 미만 |
| 구조 | 하나의 컬렉터가 young/mixed를 번갈아 | 독립적인 동시 수집기 둘(young/old)이 각자의 주기로 돈다 |

세대형 ZGC는 Old에서 Young을 가리키는 참조를 추적하기 위해 remembered set이 필요해졌고, 이를 위해 **참조를 쓸 때 동작하는 store barrier가 추가**되었다. G1이 write barrier로 하던 일과 같은 목적이다. 즉 세대를 도입한 대가로 배리어가 하나 늘었다.

#### Survivor는 어디로 갔나

G1의 Eden과 Survivor는 **둘 다 young**이고, Survivor가 따로 있는 이유는 **나이(age) 추적**이다. Young GC를 한 번 버텼다고 바로 Old로 승격시키면 곧 죽을 객체가 Old를 오염시킨다. 그래서 Survivor에 몇 번 머물게 하며 나이를 세고, 임계 나이를 넘긴 객체만 승격시킨다.

ZGC의 region 라벨은 young과 old 둘뿐이지만 **나이를 세는 파이프라인은 그대로 존재한다.** 생존자를 복사해 넣는 **대상 young region 자체를 나이 그룹으로 묶는** 방식이다. region이 곧 나이표 역할을 한다.

Survivor라는 고정 명칭이 불필요해진 이유는 선정 방식의 차이에 있다. G1은 "다음에 어디를 비울지"를 region 역할 라벨로 정적으로 관리하지만, **ZGC는 매 사이클 mark bitmap 통계로 relocation set을 동적으로 고른다.** 어차피 통계를 보고 고를 것이므로 나이 정보만 있으면 충분하고, 고정 역할 이름은 필요 없다.

### 3-12. 최종 비교표와 선택 기준

| 항목 | G1 GC | ZGC |
|---|---|---|
| 목표 | 예측 가능한 pause (기본 목표 200ms) | pause 1ms 미만, 힙 크기와 무관 |
| 복사 실행 | STW | 동시(concurrent) |
| 상시 비용 | write barrier | load barrier + 색 비트 (throughput 세금) |
| 적정 힙 | 수 GB ~ 수십 GB | 수백 GB ~ 테라바이트급 |
| 실패 모드 | Full GC (전체 STW) | allocation stall (해당 스레드만 대기) |
| 채택 시점 | Java 9부터 기본 GC | JDK 15 production-ready, JDK 21 세대형 도입, JDK 23부터 세대형이 기본 |
| 활성화 | `-XX:+UseG1GC` | `-XX:+UseZGC` |

**선택 기준을 말할 때는 "무엇을 지불할 것인가"로 답해야 한다.**

- **G1을 고르는 경우**: 일반적인 웹 애플리케이션, 힙 수십 GB 이하, 200ms급 pause가 SLO 안에 들어오는 서비스. 상시 오버헤드가 작아 같은 하드웨어에서 처리량이 더 나온다. 대부분의 서비스는 기본값인 G1로 충분하다.
- **ZGC를 고르는 경우**: 초대형 힙을 쓰거나, GC pause 때문에 발생하는 tail latency(p99, p999 같은 꼬리 응답시간)를 반드시 억제해야 하는 서비스. 실시간 거래 시스템, 대규모 인메모리 캐시, 응답시간 SLA에 위약 조항이 걸린 서비스가 여기 해당한다.

질문이 "지연에 민감한 서비스면 무엇을 고르겠는가"라면 답은 ZGC 쪽으로 기울지만, **"지연 SLO를 지키기 위해 throughput을 몇 % 지불할 의사가 있는가"를 먼저 확인하겠다**고 덧붙이는 것이 정확한 답이다. 지연에 민감하다는 말이 곧 "처리량은 아무래도 좋다"는 뜻은 아니기 때문이다. 실제 판단은 두 GC로 각각 부하 테스트를 돌려 p99와 처리량을 나란히 재보고 결정한다.

## 4. 꼬리질문 대비 포인트

### "지연에 민감하면 무조건 ZGC 아닌가요?" (시니어 변별 포인트)

아니다. **바꿔치기하는 것이 무엇인지**를 말할 수 있어야 한다.

ZGC는 STW를 없앤 대신 **모든 참조 읽기에 로드 배리어라는 상시 비용**을 얹는다. 읽기는 프로그램에서 가장 빈번한 연산이므로 이 세금은 실행 시간 전체에 걸린다. 같은 하드웨어에서 처리량이 떨어지고, 그만큼 인스턴스를 더 띄워야 할 수 있다.

그래서 판단은 이렇게 간다.

- pause가 실제로 SLO를 깨고 있는지 먼저 확인한다. GC 로그와 응답시간 그래프의 스파이크가 시각적으로 겹치는지 본다. **GC가 원인이 아닌데 GC를 바꾸는 일이 흔하다.**
- 힙이 수십 GB 이하이고 p99 스파이크가 수십 ms 수준이면, G1의 pause 목표와 힙 크기를 조정하는 것이 먼저다.
- pause가 수백 ms 이상 튀고 그것이 SLO 위반의 직접 원인이며, 처리량 손실을 인스턴스 증설로 감당할 수 있다면 ZGC로 간다.
- **양쪽으로 부하 테스트를 돌려 p99와 처리량을 나란히 재본 뒤 결정한다**고 덧붙이면 좋다. 워크로드마다 배리어 비용의 체감이 다르기 때문이다.

한 가지 더 얹을 수 있다. **pause를 줄이는 가장 싼 방법은 GC를 바꾸는 것이 아니라 쓰레기를 덜 만드는 것**이다. 요청당 대량 객체 생성, 불필요한 중간 컬렉션, 거대 응답 객체를 줄이면 어느 GC에서든 효과가 있다.

### "G1은 region 크기가 일정하니 pause도 일정하고 횟수만 늘어나는 것 아닌가요?"

설계 의도는 그것이 맞고 Mixed GC는 실제로 그렇게 동작한다. CSet 크기를 조절해 pause 목표를 맞춘다. 하지만 현실에서는 큰 힙에서 pause가 커지는 경향이 나타나며, 이유가 셋이다.

1. **Young GC는 CSet을 쪼갤 수 없다.** 수거 대상 young region은 한 번의 STW에서 전부 처리된다. 힙이 크면 young도 크게 잡히는 경향이 있어 복사량이 늘어난다. 줄이면 GC 빈도가 급증해 처리량이 나빠지므로 무한정 줄일 수도 없다.
2. **RSet 스캔 단가가 힙에 비례한다.** region이 많아지면 region 간 참조가 늘고 RSet이 비대해져서, CSet 개수를 줄여도 region 하나당 처리 단가가 올라간다.
3. **Full GC fallback이 있다.** 복사할 빈 공간이 없거나 humongous 할당에 실패하면 힙 전체가 하나의 STW로 처리된다.

즉 **"pause 목표는 명령이 아니라 목표"**이고, G1의 실제 pause 프로필은 "대체로 목표 근처 + 가끔 튀는 꼬리"라는 점을 말할 수 있으면 좋다.

### "ZGC는 STW가 아예 없나요?"

없지 않다. **Mark Start, Mark End, Relocate Start** 세 곳에 짧은 STW가 있다.

다만 이 세 곳에서 하는 일이 전부 **root 처리 수준**이다. root는 스레드 스택과 static 필드 같은 것이라 개수가 스레드 수에 비례하고 힙 크기와 무관하다. 그래서 힙이 100GB든 1TB든 pause 길이가 거의 변하지 않고 1ms 미만에 머문다.

정확한 표현은 **"STW가 없다"가 아니라 "pause가 힙 크기에 비례하지 않는다"**다. 참고로 상용 JVM GC 중 STW가 완전히 0인 것은 없다.

### "ZGC의 마킹과 포인터 색칠은 같은 말인가요?" (가산점 포인트)

다르다. 이 구분을 정확히 말하면 원리를 이해하고 있다는 신호가 된다.

- **마킹**은 살아있는 객체를 찾아 **mark bitmap에 기록**하는 것이다. 모든 GC에 공통된 개념이고, 대상은 **객체**다.
- **색칠**은 "이 참조는 현 단계 처리를 마쳤다"를 **포인터 비트에 새기는** 것이다. ZGC 특유의 기법이고, 대상은 **참조**다.

그래서 **색은 객체의 생사가 아니라 참조의 처리 상태를 나타낸다.** 같은 객체를 가리키는 두 참조의 색이 서로 다를 수 있다. 하나는 이미 읽혀서 검사를 통과했고, 다른 하나는 아직 아무도 안 읽어 옛 색인 채로 남아 있는 경우다.

이어서 remapped 색까지 설명하면 완성된다. **marked 색은 "이번 주기에 살아있음"만 보증하고 주소가 최신인지는 보증하지 못한다.** 마킹 시점에는 어느 region을 재배치할지가 아직 안 정해졌기 때문이다. **remapped 색이 "재배치 검사를 통과한 최신 주소"를 보증**한다. 보증하는 내용이 다르므로 색이 따로 필요하다.

### "세대형 ZGC의 young/old는 G1과 같은 것 아닌가요? 그럼 차이가 뭔가요?"

**힙을 나누는 구조(축 1)는 같아졌다.** region으로 쪼개고, young/old로 나누고, 쓰레기 많은 곳부터 치운다 — 검증된 설계로 수렴한 것이다. 원래 세대가 없던 ZGC가 JDK 21에서 세대를 도입한 것 자체가 세대 가설이 옳다는 인정이다.

**다른 것은 실행 방식(축 2)이다.** G1은 young 수거를 STW 중에 하고, ZGC는 **young 수거조차 앱과 동시에** 한다. 그래서 G1의 young pause는 살아남은 young 객체 양에 비례해 수 ms에서 수십 ms까지 나오지만, ZGC는 root 처리만 STW라 여전히 1ms 미만이다. 구조가 아니라 **타이밍이 두 GC를 가른다.**

Survivor 이야기가 나오면 이렇게 답한다. ZGC에 Survivor라는 이름의 라벨은 없지만 **나이를 세는 기능은 그대로 있다** — 생존자를 복사해 넣는 young region 자체를 나이 그룹으로 묶는 방식이다. G1은 다음에 비울 곳을 역할 라벨로 정적으로 관리하지만 ZGC는 매 사이클 통계로 동적 선정하므로, 고정된 역할 이름 없이 나이 정보만 있으면 충분하다.

## 한 줄 요약

고전 GC의 3대 작업은 Mark(살아있는 것 표시) - Sweep(죽은 것 회수) - Compact(빈틈 제거)이고 기본형은 셋을 전부 STW로 하는데, G1과 ZGC는 region 단위 복사로 Sweep과 Compact를 하나로 합친 뒤 **"그 복사를 언제 하느냐"**에서 갈린다 — G1은 Mark만 동시로 빼고 복사는 STW로 하되 가성비 좋은 region부터 골라 잘게 쪼개는 절충(그래서 pause가 힙·live set을 따라 커지고 최악에는 Full GC 낭떠러지가 있지만 상시 비용이 싸다), ZGC는 컬러 포인터와 로드 배리어라는 상시 세금을 내고 복사까지 동시로 빼낸 극단(그래서 힙이 테라바이트급이어도 pause가 1ms 미만이지만 모든 참조 읽기에 비용을 낸다) — 따라서 답은 "지연에 민감하면 ZGC"가 아니라 **"tail latency를 위해 throughput을 얼마나 지불할 것인가"**다.
