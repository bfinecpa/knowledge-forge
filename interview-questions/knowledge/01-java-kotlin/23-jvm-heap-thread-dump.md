# JVM 힙 덤프 & 스레드 덤프 — 내용물, 형식, 운영 환경에서의 확보 전략

> 핵심 관전 포인트: **두 덤프는 "무엇을 찍는가"와 "비용"이 완전히 다르다. 힙 덤프는 객체 그래프 전체를 찍는 바이너리(HPROF)라 힙 크기에 비례하는 STW를 유발하고, 스레드 덤프는 스택만 찍는 텍스트라 밀리초면 끝난다. 그래서 운영 전략도 갈린다 — 힙 덤프는 "어떻게 안 뜨고 버티거나, 뜨더라도 트래픽을 뺀 뒤 뜰 것인가"의 문제고, 스레드 덤프는 "여러 장을 어떻게 제대로 떠서 어떻게 오독하지 않을 것인가"의 문제다.**

---

## 0. 질문 + 의도

**질문**: "OutOfMemoryError가 발생했습니다. 힙 덤프 분석부터 원인 규명까지의 과정을 구체적으로 설명해주세요."
"스레드 덤프에서 데드락을 어떻게 찾나요? 데드락의 4가지 조건과 실무적 예방 방법은?"

**출제 의도**: 실제 해본 사람과 아닌 사람의 답이 극명하게 갈리는 질문이다. 도구 이름(MAT, dominator tree)이 아니라 "덤프를 뜨면 서비스가 멈추는데 운영 중에 어떻게 뜰 건가" 같은 현실 제약을 언급하는지로 경험의 진위를 가린다. 두 덤프의 비용 차이를 알아야 장애 순간 어떤 덤프를 먼저 뜰지 판단할 수 있다.

## 1. 힙 덤프 — 무엇이 어떤 형태로 들어가는가

### 1-1. 전제 지식 — 덤프란 무엇이고, 왜 멈춰야 하는가

**덤프(dump)**는 말 그대로 **"쏟아내기"**다. 실행 중인 프로세스가 지금 이 순간 메모리에 들고 있는 것을 파일로 통째로 쏟아내는 것을 가리킨다. 로그가 "개발자가 미리 남기기로 결정한 것만" 보여주는 반면, 덤프는 **아무도 남기기로 결정하지 않은 것까지 전부** 보여준다. 장애 원인이 로그에 안 남는 종류일 때 마지막으로 기댈 수단이 덤프인 이유다.

JVM에는 성격이 다른 두 종류가 있다.

**힙 덤프(heap dump)**는 힙에 있는 **객체와 그 필드 값 전부**를 찍는다. "지금 메모리를 누가 얼마나 쓰고 있고 왜 안 죽고 있는가"에 답한다.

**스레드 덤프(thread dump)**는 각 스레드의 **호출 스택과 락 상태**를 찍는다. "지금 각 스레드가 어디서 무엇을 하고 있고 무엇을 기다리는가"에 답한다.

여기서 중요한 것은, 둘 다 찍으려면 **잠깐이라도 세상을 멈춰야 한다**는 점이다. 이유는 사진 촬영과 같다. 피사체가 움직이는 동안 찍으면 흐릿한 사진이 나오듯, 객체 그래프가 변하는 도중에 덤프를 뜨면 앞부분과 뒷부분이 서로 모순되는 파일이 나온다. A 객체를 찍을 때는 B를 가리키고 있었는데 B를 찍을 때쯤 그 참조가 사라졌다면, 그 덤프는 존재하지 않는 상태를 기록한 것이 된다.

그래서 JVM은 덤프 전에 **세이프포인트**로 전 스레드를 모은다. **세이프포인트(safepoint)**는 **"지금 이 스레드를 멈춰도 메모리 상태가 일관되게 보인다"고 JVM이 보증할 수 있는 실행 지점**이다. 스레드를 아무 데서나 멈출 수는 없다 — 객체 필드를 절반만 쓴 순간에 멈추면 덤프가 깨진 객체를 기록하게 된다. 그래서 JVM은 메서드 호출 지점이나 루프의 되돌아가는 지점 같은 안전한 자리에 "멈춤 신호를 확인하는 코드"를 미리 심어 두고, 정지가 필요하면 신호를 켠 뒤 **모든 스레드가 각자 가장 가까운 세이프포인트에 도달할 때까지 기다린다.**

전 스레드가 세이프포인트에 모여 멈춰 있는 구간이 곧 **STW(Stop-The-World)** — 애플리케이션의 시간이 완전히 정지하는 구간이다. **두 덤프의 운영 전략이 갈리는 지점이 정확히 이 STW의 길이다.** 스레드 덤프는 스택만 훑으면 되니 밀리초로 끝나지만, 힙 덤프는 힙 전체를 순회해 파일에 쓸 때까지 STW가 이어진다. 3-1에서 이 차이가 실제로 얼마나 벌어지는지 타임라인으로 본다.

### 1-2. HPROF 바이너리 포맷

힙 덤프의 표준 형식이 **HPROF**다. 덤프 시점에 힙에 살아있던 **모든 객체의 필드 값, 클래스 메타데이터, GC 루트, 스레드 스택**이 통째로 들어간다. 텍스트가 아니라 도구(MAT, VisualVM)로 여는 것이 전제이고, **파일 크기는 대략 힙 사용량과 같다.** 8GB 힙에서 6GB가 살아있었다면 파일도 6GB 언저리다.

실제 파일의 첫 부분을 hexdump로 열어 보면 이렇다.

```
00000000: 4a41 5641 2050 524f 4649 4c45 2031 2e30  JAVA PROFILE 1.0
00000010: 2e32 0000 0000 0800 0001 9f5f a859 ef01  .2........._.Y..
```

| 위치 | 내용 |
|---|---|
| `JAVA PROFILE 1.0.2\0` | 매직 헤더 (포맷 버전) |
| `00 00 00 08` | 식별자(포인터) 크기 = 8바이트 (64비트 JVM) |
| 8바이트 | 덤프 시각 (epoch millis) |
| 이후 | 레코드 반복: `[태그 1B][시각차 4B][길이 4B][본문]` |

**식별자 크기가 파일 맨 앞에 나오는 이유**를 짚으면 포맷의 성격이 보인다. 이 파일 안에서 객체는 이름이 아니라 **ID(사실상 메모리 주소)**로 서로를 가리킨다. 그 ID가 몇 바이트짜리인지 모르면 뒤에 이어지는 레코드를 한 바이트도 해석할 수 없다. 즉 HPROF는 **"객체 ID로 엮인 거대한 그래프를 직렬화한 것"**이고, 분석 도구가 하는 일의 절반은 이 ID들을 다시 이어 붙여 그래프를 복원하는 것이다.

### 1-3. 레코드 종류 — 파일 안에 실제로 무엇이 있는가

- **`0x01` UTF8** — 모든 심볼 문자열(클래스명·필드명·메서드명). 이후 레코드는 이름을 직접 쓰지 않고 이 항목의 ID로 참조한다. 같은 클래스명이 수백만 번 나와도 문자열은 한 번만 저장된다.
- **`0x02` LOAD_CLASS** — 로드된 클래스 목록 (클래스 ID ↔ 이름)
- **`0x04`/`0x05` STACK_FRAME / STACK_TRACE** — 덤프 시점의 스레드 스택. 힙 덤프 안에도 스택 정보가 일부 들어간다.
- **`0x0C`/`0x1C` HEAP_DUMP (SEGMENT)** — 파일의 95% 이상을 차지하는 본체. 안에 서브 레코드가 들어 있다.
  - **GC ROOT** — JNI 전역 참조, 스레드 로컬, static 필드, 모니터 락 등. **"이 객체가 왜 살아있는가"를 되짚어 올라갈 때의 종착점**이다. 이 정보가 있어야 Path to GC Roots(1-5)가 가능하다.
  - **CLASS_DUMP** — static 필드의 값 + 인스턴스 필드 레이아웃(어떤 필드가 몇 번째 자리에 몇 바이트로 있는지). 이 레이아웃이 있어야 아래 INSTANCE_DUMP의 raw 바이트를 필드별로 해석할 수 있다.
  - **INSTANCE_DUMP** — 객체 하나가 `[객체 ID][클래스 ID][필드 raw 바이트]` 형태로 들어간다. 참조 필드 자리에는 **상대 객체의 ID(주소)**가 들어간다.
  - **OBJECT_ARRAY_DUMP / PRIMITIVE_ARRAY_DUMP** — 배열 내용 전체. `byte[]`/`char[]`가 통째로 들어가므로 파일 크기의 대부분이 사실 여기다.

예를 들어 `map.put("session-42", new byte[1024])` 한 줄이 만든 것은 파일 안에서 이렇게 연결돼 저장된다.

```
HashMap$Node INSTANCE_DUMP          → String INSTANCE_DUMP        → byte[] PRIMITIVE_ARRAY_DUMP
  key   = 0x...(String의 ID) ────────►  value = 0x...(byte[]의 ID) ──►  "session-42"의 실제 바이트
  value = 0x...(byte[1024]의 ID) ─────────────────────────────────►  1024바이트 원본
```

**참조가 ID로만 저장된다**는 점이 중요하다. 파일 안에는 "누가 누구를 가리키는가"만 있고 "누가 얼마나 붙잡고 있는가"는 없다. 그 계산은 분석 도구가 파일을 다 읽은 뒤 그래프를 만들어서 직접 해야 하고, 그래서 큰 덤프를 여는 데 시간과 메모리가 든다.

### 1-4. 보안 함의 — 덤프 파일은 개인정보 그 자체다

`strings example.hprof`만 돌려도 힙에 있던 String 내용물이 그대로 쏟아진다. 도구도 필요 없다.

**비밀번호·세션 토큰·주민번호·카드번호가 힙에 있었다면 덤프에 평문으로 들어간다.** 요청을 처리 중이었다면 그 요청의 파라미터가 통째로 들어 있고, 캐시에 사용자 정보가 있었다면 그것도 전부 들어 있다.

그러므로 운영 덤프 파일은 로그와 같은 등급으로 다루면 안 되고 **민감 자료로 취급**해야 한다. 실무에서는 최소한 이 정도를 정해 둔다 — 어디에 저장할 것인가(암호화된 볼륨), 누가 내려받을 수 있는가(권한 통제), 어떻게 전달할 것인가(개인 노트북 반출 금지 여부), **언제 지울 것인가**(분석 종료 후 삭제 기한). 특히 마지막 항목이 잘 빠진다 — 장애 대응이 끝나고 나면 6GB짜리 개인정보 덩어리가 공용 디스크에 그대로 남아 있는 경우가 흔하다.

### 1-5. 분석 도구에서 보는 3대 뷰

덤프를 열면 결국 보는 화면은 세 가지다.

**Histogram(히스토그램)** — 클래스별 인스턴스 수와 총 바이트를 줄 세운 표다. "무엇이 많은가"에 답한다.

```
 num     #instances         #bytes  class name
   1:         16191        1214888  [B                  ← byte[] 배열
   3:         15935         382440  java.lang.String
   7:          4261         136352  java.util.HashMap$Node
```

**Dominator Tree(지배자 트리)** — "이 객체가 사라지면 메모리가 얼마나 회수되는가"(retained heap)를 기준으로 만든 트리다. 누수 용의자를 찾는 핵심 뷰이고, 왜 이 뷰가 핵심인지는 3-4와 3-5에서 자세히 본다.

**Path to GC Roots(GC 루트까지의 경로)** — 용의자 객체에서 출발해 GC 루트까지 참조를 거슬러 올라간 체인이다. **"누가 붙잡고 있어서 이게 못 죽는가"**에 답한다. 예를 들어 이런 체인이 나온다.

```
static cache  →  HashMap  →  Node[]  →  Node  →  byte[]
   ↑ 여기가 GC 루트. 즉 "static 필드가 잡고 있어서 이 6GB가 안 죽는다"가 결론이 된다.
```

세 뷰의 역할을 한 줄로 구분하면, **Histogram은 "무엇이", Dominator Tree는 "누구 때문에", Path to GC Roots는 "어디를 고쳐야"에 답한다.** 조사는 이 순서로 흐른다.

### 1-6. 힙 덤프를 뜨는 명령들

```bash
# 권장. JVM에 명령을 보내는 표준 도구. 기본적으로 살아있는 객체만 담는다.
jcmd <pid> GC.heap_dump /dumps/app.hprof

# 오래된 방식. live 옵션을 붙이면 살아있는 객체만 담는다.
jmap -dump:live,format=b,file=/dumps/app.hprof <pid>

# OOM 시점에 자동으로 덤프를 남기는 JVM 기동 옵션 (운영 기본값으로 넣어둘 것)
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps
```

`live` 옵션의 의미를 정확히 알아야 한다. **`live`는 "이미 쓰레기가 된 객체는 빼고 살아있는 것만 담아라"는 뜻인데, 무엇이 살아있는지 확정하려면 GC를 한 번 돌려야 한다.** 그래서 `jmap -dump:live`와 `jcmd GC.heap_dump`(기본 동작)는 **덤프 직전에 Full GC를 유발한다.** 파일이 작아지고 분석할 때 죽은 객체에 속지 않는다는 장점이 있지만, **정지 시간에 Full GC 시간이 통째로 더해진다.** 이 트레이드오프가 3-1 타임라인의 첫 번째 항목이다.

`-XX:+HeapDumpOnOutOfMemoryError`는 **OOM이 던져지는 순간 JVM이 스스로 힙 덤프를 파일로 남기게 하는 기동 옵션**이다. 운영에서 기본으로 켜두는 것이 정석인데, 두 가지 함정을 같이 알아 둬야 한다. 첫째, **한 프로세스에서 첫 번째 OOM 때 한 번만** 남는다. 둘째, `HeapDumpPath`가 컨테이너 안의 임시 경로면 컨테이너가 재시작되는 순간 덤프가 함께 사라진다 — **반드시 재시작을 견디는 볼륨을 지정해야 한다.** 힙 크기만 한 파일이 갑자기 생기므로 그 볼륨의 여유 용량도 미리 확보해 둔다.

## 2. 스레드 덤프 — 무엇이 어떤 형태로 들어가는가

### 2-1. 평문 텍스트, 전체 구조

힙 덤프와 달리 스레드 덤프는 사람이 그대로 읽는 텍스트다. 크기도 수십 KB 수준이다.

```
2026-07-14 17:22:05
Full thread dump OpenJDK 64-Bit Server VM (21.0.10 mixed mode, sharing):

Threads class SMR info: ...          ← JVM 내부 정보 (분석 시 무시)
"스레드이름" ... 스레드 항목 반복 ...   ← 본체
JNI global refs: ...
Found N Java-level deadlock(s)       ← 데드락 있으면 맨 뒤에 자동 감지 결과
```

맨 위의 타임스탬프가 중요하다. 스레드 덤프는 뒤에서 보듯 **여러 장을 떠서 비교**하는 것이 원칙이라, 어느 장이 언제 것인지 구분할 수 있어야 한다.

### 2-2. 스레드 항목 하나의 해부

```
"worker-blocked" #21 [26115] prio=5 os_prio=31 cpu=0.10ms elapsed=3.89s
    tid=0x...949925a00 nid=0x6603 waiting for monitor entry
   java.lang.Thread.State: BLOCKED (on object monitor)
	at ThreadDemo.lambda$main$1(ThreadDemo.java:10)
	- waiting to lock <0x000000070edf1c50> (a java.lang.Object)
```

**첫 줄**에는 이름과 식별자, 그리고 진단에 직접 쓰는 두 숫자가 있다.

- `cpu=0.10ms` — **이 스레드가 태운 누적 CPU 시간**이다. CPU 폭주 스레드를 찾을 때 가장 먼저 보는 값이다. 다른 스레드가 전부 수 ms인데 혼자 수십 초면 그놈이 범인이다.
- `[26115]`와 `nid=0x6603` — **둘 다 같은 값이다.** 이 스레드에 대응하는 **OS 네이티브 스레드 ID**이고, 대괄호 안은 10진수, `nid=`는 16진수 표기다(0x6603 = 26115). 이 값이 중요한 이유는 **`top -H`가 보여주는 OS 스레드 ID와 이것을 맞춰야** "CPU를 태우는 OS 스레드가 자바 코드의 어디인지"를 알 수 있기 때문이다.

**둘째 줄**은 스레드 상태다. `RUNNABLE`(실행 중이거나 실행 가능), `BLOCKED`(`synchronized` 진입을 기다리는 중), `WAITING`(누가 깨워주기를 무기한 대기), `TIMED_WAITING`(시간 제한을 두고 대기) 중 하나다.

**스택 중간에 끼어 있는 `- locked <주소>` / `- waiting to lock <주소>` 줄이 락 분석의 열쇠다.** 스택 트레이스는 원래 메서드 호출 목록인데, JVM이 그 사이사이에 "이 프레임에서 이 락을 쥐었다 / 기다린다"는 정보를 끼워 넣어 준다.

### 2-3. 락 경합이 보이는 방식 — 주소로 짝 맞추기

락 경합은 **같은 락 주소가 두 스레드에 교차로 나타나는 것**으로 드러난다.

```
"worker-holding-lock" ... TIMED_WAITING (sleeping)
	- locked <0x000000070edf1c50>          ← 락을 쥔 채 잠들어 있음

"worker-blocked" ... BLOCKED (on object monitor)
	- waiting to lock <0x000000070edf1c50> ← 같은 주소를 기다림
```

읽는 방법은 단순하다. **`waiting to lock` 주소를 복사해서 덤프 전체에서 검색하고, 같은 주소에 `locked`가 붙은 스레드를 찾는다.** 그 스레드가 범인이고, 그 스레드의 스택이 "왜 락을 오래 쥐고 있는지"를 말해 준다. 위 예에서는 락을 쥔 채 `sleep`하고 있다는 것이 그대로 보인다.

한 가지 헷갈리는 형태가 있다. `Object.wait()` 대기는 **락을 잡았다가 놓고 기다리는** 동작이라, `locked`와 `waiting on`이 **같은 주소로 함께** 나온다.

```
"consumer-waiting" ... WAITING (on object monitor)
	at java.lang.Object.wait0(Native Method)
	- waiting on <0x000000070edf1c70>
	at ThreadDemo.lambda$main$2(ThreadDemo.java:15)
	- locked <0x000000070edf1c70>
```

이것을 "락을 쥔 채 멈춰 있다"고 오독하면 안 된다. `wait()`에 들어가는 순간 락은 실제로 놓여 있고, 깨어날 때 다시 잡는다. `locked` 줄이 함께 보이는 것은 그 프레임에서 락을 획득했다는 이력을 표시한 것이다. **`waiting on`과 `locked`가 같은 주소로 짝지어 있으면 정상적인 `wait()` 대기**라고 읽으면 된다.

### 2-4. 데드락 자동 감지 — JVM이 답을 써 준다

**데드락(deadlock, 교착 상태)**은 **두 개 이상의 스레드가 서로가 쥔 자원을 기다리며 영원히 진행하지 못하는 상태**다. 좁은 복도에서 마주친 두 사람이 서로 "네가 먼저 비켜"라며 둘 다 안 움직이는 상황과 같다.

다행히 이건 직접 찾아 헤맬 필요가 없다. **JVM이 스레드 덤프를 뜰 때 락 대기 관계에 순환이 있는지 스스로 검사해서, 덤프 맨 끝에 결론까지 써 준다.**

```
Found one Java-level deadlock:
=============================
"deadlock-1":
  waiting to lock monitor ... (object 0x...c90), which is held by "deadlock-2"
"deadlock-2":
  waiting to lock monitor ... (object 0x...c80), which is held by "deadlock-1"
...
Found 1 deadlock.
```

**그러므로 "스레드 덤프에서 데드락을 어떻게 찾나요?"의 첫 답은 "덤프 맨 아래 `Found N Java-level deadlock(s)` 섹션을 본다"다.** 스택을 하나씩 대조하는 것은 그다음이다.

단, **여기 안 잡히는 데드락이 있다는 것까지 말할 수 있어야 한다.** 자동 감지는 `synchronized` 모니터와 `java.util.concurrent`의 `Lock` 구현체가 만든 순환을 대상으로 한다. 반면 **DB 레벨의 락 대기, 서로의 응답을 기다리는 두 스레드풀, `CountDownLatch`를 서로 기다리는 구조** 같은 논리적 교착은 JVM이 알 방법이 없다. 이런 경우는 3-3의 "여러 장 떠서 비교" 방식으로 직접 찾아야 한다.

### 2-5. 데드락의 4가지 조건과 실무적 예방

데드락이 성립하려면 **네 가지 조건이 동시에 만족돼야 한다.** 뒤집으면 **하나만 깨도 데드락은 성립하지 않는다** — 예방법이 여기서 전부 나온다.

| 조건 | 뜻 | 실무에서 깰 수 있는가 |
|---|---|---|
| **상호 배제** (mutual exclusion) | 자원을 한 번에 한 스레드만 쓸 수 있다 | 어렵다 — 락을 쓰는 이유 자체 |
| **점유와 대기** (hold and wait) | 이미 자원을 쥔 채로 다른 자원을 기다린다 | 가능 — 타임아웃 후 놓고 물러나기 |
| **비선점** (no preemption) | 남이 쥔 자원을 강제로 뺏을 수 없다 | 부분적으로 가능 — `tryLock`, `lockInterruptibly` |
| **순환 대기** (circular wait) | 대기 관계가 원을 이룬다 | 가장 실용적 — 락 순서 고정 |

**실무의 첫 번째 답은 순환 대기를 깨는 것, 즉 락 순서 고정(lock ordering)이다.** 모든 스레드가 **같은 전역 기준**으로 락을 잡으면 원이 만들어질 수 없다. 계좌 이체 예제가 교과서 사례다.

```java
// Before: 인자로 받은 순서대로 잠근다 — 순환 대기가 성립한다
public void transfer(Account from, Account to, long amount) {
    synchronized (from) {
        synchronized (to) {
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}
// transfer(A, B)와 transfer(B, A)가 동시에 실행되면:
//   스레드1: A를 쥐고 B를 기다림
//   스레드2: B를 쥐고 A를 기다림
// 대기 관계가 A -> B -> A로 원을 이룬다. 영원히 안 풀린다.

// After: 락 순서를 계좌 ID라는 전역 기준으로 고정한다
public void transfer(Account from, Account to, long amount) {
    // 어느 방향의 이체든 항상 "ID가 작은 계좌"를 먼저 잠근다.
    // 모든 스레드가 같은 순서를 따르므로 대기 그래프에 원이 생길 수 없다.
    Account first  = from.id() < to.id() ? from : to;
    Account second = from.id() < to.id() ? to   : from;
    // (from.id() == to.id()인 자기 이체는 호출 전에 걸러낸다 — 같은 락을 두 번 잡게 되므로)

    synchronized (first) {
        synchronized (second) {
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}
```

**두 번째 답은 점유와 대기를 깨는 것 — 타임아웃이 있는 락 획득이다.** `synchronized`는 한번 기다리기 시작하면 중간에 포기할 방법이 없다. `ReentrantLock`의 `tryLock(timeout)`은 정해진 시간 안에 못 잡으면 **이미 쥔 것을 놓고 물러날 기회**를 준다.

```java
if (lockA.tryLock(200, TimeUnit.MILLISECONDS)) {
    try {
        if (lockB.tryLock(200, TimeUnit.MILLISECONDS)) {
            try { /* 실제 작업 */ } finally { lockB.unlock(); }
        } else {
            // B를 못 잡았다 -> A까지 놓고 물러난다. 이 "놓고 물러남"이
            // 점유와 대기 조건을 깨서 데드락을 교착이 아니라 재시도로 바꾼다.
            return Result.retryLater();
        }
    } finally { lockA.unlock(); }
}
```

**세 번째 답은 애초에 락을 두 개 잡지 않는 설계다.** 잠글 대상을 하나로 합치거나(계좌 대신 "이체 배치" 단위 락), 락 구간을 좁혀 중첩이 생길 여지를 없애거나, 락 대신 낙관적 갱신(버전 컬럼 + `UPDATE ... WHERE version = ?`)으로 바꾸는 방향이다. **락을 안 겹치게 만든 설계가 락 순서 규칙보다 항상 안전하다** — 규칙은 사람이 어기지만 구조는 어길 수 없기 때문이다.

마지막으로 반드시 덧붙일 것이 하나 있다. **락 안에서 외부 호출(HTTP, DB, 다른 서비스)을 하지 않는다.** 락을 쥔 시간이 상대 시스템의 응답 시간에 종속되면, 상대가 느려지는 순간 우리 쪽 락 대기가 폭발한다. 이건 데드락 조건을 깨는 것은 아니지만, 실무에서 데드락과 구분이 안 되는 "사실상의 멈춤"을 만드는 가장 흔한 원인이다.

### 2-6. 힙 덤프와의 비교

| | 힙 덤프 | 스레드 덤프 |
|---|---|---|
| 형식 | HPROF 바이너리, 수 GB 가능 | 평문 텍스트, 수십 KB |
| 내용 | 객체·필드 값 전부 | 스레드별 스택 + 락 소유 관계 |
| 용도 | 메모리 릭, OOM | 행(hang), 데드락, CPU 폭주, 응답 지연 |
| 비용 | STW 길고 무거움 | 거의 즉시, 운영 중 부담 없음 |

장애 순간의 판단으로 옮기면 이렇다. **증상이 "메모리"면 힙 덤프, "멈춤"이나 "느림"이면 스레드 덤프다.** 그리고 애매하면 **스레드 덤프를 먼저 뜬다** — 비용이 사실상 0이라 틀려도 잃을 게 없고, 힙 덤프는 한 번 뜨는 순간 서비스가 멈추므로 확신이 선 뒤에 떠야 한다.

### 2-7. 스레드 덤프를 뜨는 명령들

```bash
jcmd <pid> Thread.print       # 권장. jstack -l과 같은 정보를 준다
jstack <pid>                  # 전통적인 도구
jstack -l <pid>               # -l: j.u.c 락 소유 정보까지 (3-3에서 왜 중요한지 설명)
kill -3 <pid>                 # SIGQUIT. 프로세스를 죽이지 않고 stdout에 덤프를 출력
```

`kill -3`이 프로세스를 죽이지 않는다는 점이 헷갈리기 쉽다. SIGQUIT를 받으면 **JVM이 그것을 "스레드 덤프를 출력하라"는 신호로 해석하도록 만들어져 있다.** 다만 출력이 파일이 아니라 **stdout**으로 나가므로, 그 stdout이 어디로 리다이렉트돼 있는지(`catalina.out`, 컨테이너 로그 등)를 모르면 덤프를 떠 놓고도 찾지 못한다.

## 3. 운영 환경에서의 확보 전략과 분석 기준

### 3-1. 운영 중 8GB 힙을 덤프하면 무슨 일이 벌어지는가

말로 "STW가 길다"고 하는 것과 실제로 무슨 일이 일어나는지 아는 것은 다르다. 타임라인으로 따라가 보자.

**가정** — 힙 `-Xmx8g`, 그중 살아있는 객체가 약 6GB. 덤프를 쓸 디스크는 로컬 SSD(쓰기 500MB/s). LB 헬스체크는 5초 주기이고 연속 2회 실패하면 노드를 제외한다. 쿠버네티스 liveness probe는 10초 주기이고 연속 3회 실패하면 컨테이너를 재시작한다.

```
──── JVM 안에서 일어나는 일 ─────────────────────────────────────────────────

t+0.00s   운영자가 실행:  jmap -dump:live,format=b,file=/dumps/app.hprof <pid>

t+0.00s   JVM이 세이프포인트 요청을 건다.
          모든 애플리케이션 스레드가 각자 가장 가까운 세이프포인트에 도달할 때까지 대기.

t+0.01s   전 스레드 정지 완료. 보통 수 ms면 끝난다.
          (예외: JNI 네이티브 호출에 오래 들어가 있거나 세이프포인트 확인 코드가
           없는 루프에 갇힌 스레드가 있으면 여기서만 수백 ms가 더 걸릴 수 있다.
           이것을 time-to-safepoint 지연이라고 부른다.)
          ★ 이 순간부터 애플리케이션의 시간이 멈춘다. 처리 중이던 요청 전부가 그대로 정지.

t+0.01s   live 옵션 때문에 Full GC가 먼저 한 번 돈다.
          8GB 힙의 Full GC = 컬렉터와 생존율에 따라 수 초. 여기서는 3초로 잡는다.

t+3.0s    힙 순회 시작. 살아있는 객체를 하나씩 직렬화해 파일에 기록한다.
          쓸 양 ≈ 살아있는 객체 총량 = 약 6GB
          6GB ÷ 500MB/s = 12초           ← 병목은 CPU가 아니라 디스크 쓰기다

t+15.0s   덤프 완료. 세이프포인트 해제, 스레드 재개.
          ★ 총 정지 시간 15초. GC pause와 달리 이 시간에는 상한을 지정할 방법이 없다.

──── 같은 시간, 바깥에서 일어나는 일 ────────────────────────────────────────

t+5.0s    LB 헬스체크 1차 실패.
          (헬스체크 엔드포인트도 결국 자바 스레드가 처리하는데, 그 스레드가 멈춰 있다)

t+10.0s   LB 헬스체크 2차 실패 → 이 노드를 풀에서 제외.
          트래픽이 남은 노드로 몰린다. 노드가 3대였다면 남은 2대가 1.5배를 받는다.

t+10.0s   k8s liveness probe 1차 실패.

t+15.0s   덤프 완료·스레드 재개. 그러나 15초치 요청은 이미 전부 타임아웃 났다.
          상류 서비스의 커넥션 풀이 그동안 응답 없는 커넥션으로 가득 차 있었다면
          상류도 함께 느려진다 — 장애 전파.

t+20.0s   (덤프가 더 길었다면) liveness probe 3차 실패 → 컨테이너 강제 종료.
          ★ 최악의 결말: 덤프 파일은 미완성으로 남고, 프로세스는 죽고, 장애만 커진다.
```

**디스크가 로컬 SSD가 아니라 NFS 같은 네트워크 볼륨(100MB/s)이라면** 쓰기만 6GB ÷ 100MB/s = **60초**다. 총 정지가 1분을 넘고, liveness probe에 확실히 걸려 프로세스가 죽는다. **덤프 파일을 어디에 쓰느냐가 정지 시간을 좌우한다**는 것이 여기서 나오는 실무 교훈이다.

정리하면 운영 중 힙 덤프의 위험은 셋이다. **① 힙 크기에 비례하는 STW(상한 지정 불가), ② 헬스체크 탈락으로 인한 트래픽 이동과 장애 전파, ③ liveness probe에 의한 프로세스 강제 종료.** 특히 ③은 "덤프도 못 얻고 장애만 키우는" 최악의 결과라 반드시 먼저 언급할 가치가 있다.

### 3-2. 힙 덤프 실제 확보 전략 (우선순위 순)

위 타임라인을 알고 나면 전략의 순서가 자연히 정해진다. **가장 좋은 것은 애초에 운영 중에 뜨지 않는 것이다.**

**1순위: 사전 설정으로 자동 확보 (최선).**

```
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps
```

이 옵션이 최선인 이유는 비용 구조가 완전히 다르기 때문이다. **OOM 시점에는 어차피 애플리케이션이 죽는 중이므로 STW 비용을 따질 이유가 없다.** 게다가 그 순간이 **누수가 최대치에 도달한 순간**이라 분석 대상으로도 가장 좋다. 운영 JVM의 기본 옵션으로 넣어 두는 것이 정석이고, 1-6에서 짚은 두 가지(재시작을 견디는 볼륨, 디스크 여유 용량)를 함께 챙긴다.

**2순위: 트래픽을 뺀 뒤 덤프.**

문제 인스턴스를 LB에서 먼저 빼고(drain) 덤프한다. 3-1 타임라인의 위험 ②와 ③이 통째로 사라진다. 이때 함께 할 일이 셋이다 — **liveness probe를 일시적으로 완화하거나 끄고**(안 그러면 여전히 죽는다), **빠른 로컬 디스크에 쓰고**, 덤프가 끝난 뒤 인스턴스를 재기동한다.

**3순위: 트래픽을 못 빼면 `gcore`.**

`gcore <pid>`는 프로세스의 메모리를 **코어 파일로 그대로 복사**한다. Full GC도 없고 객체 그래프 순회도 없이 메모리를 통째로 덤프하므로 정지가 짧아진다. 이후 **오프라인 분석 장비에서** `jmap -dump ... <core파일>` 형태로 hprof로 변환한다.

핵심은 **비용을 없애는 게 아니라 옮기는 것**이다. 가장 비싼 작업(그래프 순회와 hprof 직렬화)을 서비스 장비가 아니라 분석 장비로 이전한다. 다만 코어 파일은 힙만이 아니라 프로세스 메모리 전체라 **파일이 오히려 더 클 수 있다는 점**은 감안해야 한다.

**4순위: 풀 덤프 자체를 회피하는 대안.**

- `jmap -histo <pid>` — 클래스별 인스턴스 수와 바이트만 집계한다. **객체를 파일로 직렬화하지 않으므로 GB 단위 디스크 쓰기가 없다.** 몇 분 간격으로 두 번 떠서 **증가분을 비교**하면 "무엇이 계속 늘고 있는가"를 알 수 있고, 그것만으로 원인이 잡히는 경우가 의외로 많다. (`-histo:live`를 붙이면 Full GC가 선행되니 주의)
- **JFR(Java Flight Recorder)의 OldObjectSample** — 오버헤드가 매우 낮아 **상시 가동**할 수 있고, 오래 살아남은 객체를 표본으로 잡되 **그 객체가 할당된 스택 트레이스까지** 기록한다. 힙 덤프가 "지금 누가 붙잡고 있는가"를 보여준다면, 이건 **"어느 코드가 그걸 만들었는가"**를 보여준다. 누수 조사에서 두 정보는 상호 보완적이다.

**전체를 한 줄로 요약하면**: 힙 덤프는 힙 크기에 비례하는 STW와 헬스체크 연쇄 장애 위험을 안고 있으므로, ① OOM 자동 덤프를 미리 걸어두고 ② 꼭 떠야 하면 drain 후에 뜨며 ③ 그것도 안 되면 gcore·histo·JFR로 대체한다.

### 3-3. 스레드 덤프를 뜰 때의 주의점 — 무게가 아니라 방법과 해석

스레드 덤프는 스택만 걷으므로 정지가 보통 **밀리초 단위**다. 운영 중에 떠도 안전하다는 것이 원칙이다. **그래서 함정이 무게가 아니라 다른 데 있다.**

#### 뜨는 시점의 주의점

**`-F` 강제 모드의 함정.** `jstack -F`는 일반 방식이 실패했을 때 쓰는 옵션인데, 내부적으로 **디버거를 붙여 프로세스를 서스펜드**하는 훨씬 무거운 방식이고 상태 정보도 부정확하다. 습관적으로 붙이면 안 된다.

더 중요한 것은 **일반 모드가 안 먹힌다는 사실 자체가 진단 정보**라는 점이다. `jcmd`/`jstack`은 대상 JVM이 세이프포인트에 도달해야 응답할 수 있는데, 응답이 없다는 것은 **세이프포인트에 도달하지 못하는 스레드가 있다**는 뜻이다. 무한 루프에 갇혔거나 네이티브 호출에서 안 돌아오고 있다는 강한 단서다. 그때 비로소 `-F` → `kill -3` → `gcore` 순으로 단계적으로 전환한다.

**time-to-safepoint 지연.** 위와 같은 이유로, JNI 장기 실행이나 세이프포인트 확인 코드가 없는 루프에 갇힌 스레드가 있으면 스레드 덤프의 정지 시간도 예상보다 길어질 수 있다. "스레드 덤프는 항상 밀리초"가 아니라 "보통 밀리초, 단 전 스레드가 세이프포인트에 빨리 모일 때"가 정확하다.

**`kill -3`는 출력 위치를 먼저 확인한다.** 2-7에서 본 대로 stdout으로 나가므로, 리다이렉트 위치를 모르면 덤프를 유실한다.

**권한과 환경.** `jcmd`/`jstack`은 **JVM 프로세스와 같은 uid**로 실행해야 어태치할 수 있다. root라도 uid가 다르면 실패한다. 컨테이너 환경이면 같은 PID 네임스페이스 안에서 실행해야 하므로 `kubectl exec`로 파드 안에 들어가서 떠야 한다.

#### 확보 전략 — 한 장은 진단이 아니다

**3~5초 간격으로 3~5장을 연속으로 뜬다.** 이유는 단순하다. **한 장만으로는 "잠깐 대기 중"과 "영원히 갇힘"을 구분할 수 없다.** 어느 스레드가 DB 조회 중인 장면을 찍었다고 해서 그게 문제라는 뜻은 아니다. 여러 장에서 **같은 스레드가 같은 스택 위치에 계속 머물러 있으면** 그게 진범이다.

**CPU 폭주가 의심되면 `top -H -p <pid>`를 같은 시점에 함께 뜬다.** `-H`는 프로세스가 아니라 스레드 단위로 CPU 사용률을 보여주는 옵션이다. 표준 절차는 이렇다 — top에서 CPU를 태우는 스레드의 ID를 찾고, 그 값을 스레드 덤프의 `nid`와 맞춰 자바 스택을 확인한다. 2-2에서 봤듯 덤프에는 같은 값이 10진(`[26115]`)과 16진(`nid=0x6603`)으로 함께 찍히므로, 16진 쪽과 맞추려면 top의 10진 ID를 변환해야 한다.

**덤프마다 타임스탬프를 남긴다.** 그리고 한 가지 함정 — **락 주소는 GC로 객체가 이동하면 바뀔 수 있다.** 그러므로 2-3의 "주소로 짝 맞추기"는 **반드시 한 덤프 안에서만** 유효하다. 1장의 `waiting to lock` 주소를 3장의 `locked`와 맞춰 보면 안 된다.

#### 해석 시의 함정

**`java.util.concurrent` 락은 `- locked` 줄에 나오지 않는다.** 이것이 가장 흔한 오독의 원인이다.

`synchronized`는 JVM이 직접 아는 모니터 락이라 덤프에 락 소유 관계가 그대로 찍히지만, `ReentrantLock` 같은 `j.u.c` 락은 **자바 코드로 구현된 라이브러리**다. JVM 입장에서는 그냥 어떤 객체를 두고 스레드가 park(정지)해 있는 것으로만 보인다. 그래서 `ReentrantLock` 대기는 이렇게 나타난다.

```
"worker-3" ... WAITING (parking)          ← BLOCKED가 아니다
	at jdk.internal.misc.Unsafe.park(Native Method)
	- parking to wait for <0x...> (a java.util.concurrent.locks.ReentrantLock$NonfairSync)
	at java.util.concurrent.locks.AbstractQueuedSynchronizer.acquire(...)
```

**락 소유자를 알려면 `jstack -l`로 떠서 각 스레드 아래의 "Locked ownable synchronizers" 섹션을 봐야 한다.** 이걸 모르면 **"BLOCKED가 하나도 없으니 락 문제는 아니네요"라고 정반대로 오판한다.** 현대 자바 코드는 `synchronized`보다 `j.u.c`를 많이 쓰므로 이 오판이 나올 확률이 높다.

**수백 개의 WAITING 자체는 정상이다.** 스레드풀의 유휴 스레드는 전부 "다음 작업을 기다리는 중"이므로 WAITING이다. **비정상 신호는 상태가 아니라 스택의 위치**다. 예를 들어 수십 개 스레드가 전부 커넥션 풀의 `getConnection`에서 대기 중이라면, 상태가 WAITING이든 TIMED_WAITING이든 그건 명백한 이상 신호다.

**전체를 한 줄로 요약하면**: 스레드 덤프는 밀리초급이라 운영 중에도 안전하지만, ① `-F`를 습관적으로 쓰지 말고 정석 도구를 같은 uid로 실행하며 ② 반드시 여러 장을 뜨고 CPU 이슈면 `top -H`를 동시에 확보하고 ③ `j.u.c` 락은 BLOCKED로 안 보인다는 것을 알고 해석해야 한다.

### 3-4. 분석 기준 (1) — shallow size vs retained size

덤프를 열었을 때 무엇을 기준으로 줄 세울 것인가. 이 판단이 조사 시간을 몇 시간 단위로 좌우한다.

**단어 뜻 자체가 정의다.**

**shallow**는 "얕은"(deep의 반대)이다. 참조를 따라 깊이 들어가지 않고 객체의 **표면, 즉 자기 자신만** 잰다는 뜻이다. `shallow copy`(얕은 복사)의 그 shallow와 같은 용법이다.

**retained**는 "붙잡아 둔"이다(retain = 계속 쥐고 놓지 않다). 이 객체가 **붙잡아 두고 있는 바람에 GC가 회수하지 못하는** 메모리라는 뜻이다. customer retention(고객 유지)의 그 retain이다.

그러니 **shallow size = "얕게 잰 크기(자기 몸집만)"**, **retained size = "붙잡고 있는 크기(놓아주면 풀려날 총량)"**로 읽으면 된다.

**정확한 정의**는 이렇다.

**Shallow size** — 객체 **자신이 직접 차지하는 메모리**다. 객체 헤더(마크 워드 + 클래스 포인터) + 필드들의 크기 합이다. 여기서 결정적인 것은 **참조 필드를 포인터 크기(4~8바이트)로만 계산하고, 그 참조가 가리키는 대상은 포함하지 않는다**는 점이다.

**Retained size** — **"이 객체가 GC로 수거되면 함께 회수되는 총량"**이다. 자기 자신 + **오직 이 객체를 통해서만 도달 가능한**(다른 GC 루트 경로가 없는) 모든 객체의 shallow size 합이다.

"오직 이 객체를 통해서만"이라는 조건이 **지배(dominate)** 관계다. **"A를 지나지 않고는 B에 도달할 방법이 없을 때 A가 B를 지배한다"**고 말하고, MAT의 **Dominator Tree**는 이 지배 관계로 만든 트리다. 다리가 하나뿐인 섬을 생각하면 된다 — 그 다리를 끊으면 섬 전체가 고립되고, 다리가 두 개면 하나 끊어도 아무 일도 일어나지 않는다.

이 정의에서 미묘한 성질이 하나 나온다. **다른 곳에서도 참조되는 공유 객체는 어느 쪽 retained에도 포함되지 않는다.** 캐시 A와 캐시 B가 같은 객체를 참조하고 있다면, A를 없애도 그 객체는 B 때문에 살아남으므로 A의 retained에 넣을 수 없다. 이런 객체는 **둘의 공통 지배자(dominator)**에 귀속된다. 처음 볼 때 "숫자가 왜 안 맞지?" 싶은 지점이 대개 이것이다.

**예시로 확인해 보자.**

```java
static Map<String, byte[]> cache = new HashMap<>();  // 1MB 항목 × 1000개
```

| 객체 | shallow | retained |
|---|---|---|
| `HashMap` 인스턴스 | ~48 B | **~1 GB** |
| `Node[]` 테이블 | 수 KB | ~1 GB |
| `byte[]` 하나 | 1 MB | 1 MB |

`HashMap` 인스턴스 자체는 필드 몇 개짜리라 shallow로는 48바이트짜리 티끌이다. 그런데 그 48바이트를 없애면 1GB가 풀려난다. **누수의 원인은 언제나 이 티끌 쪽에 있다.**

### 3-5. 분석 기준 (2) — 왜 누수 분석은 retained 정렬인가

**첫째, shallow 정렬은 어떤 덤프에서든 항상 같은 용의자만 보여준다. 증상이지 원인이 아니다.**

어느 덤프를 열어도 shallow 상위권은 `byte[]`, `char[]`, `String`, `Object[]`다. 데이터가 실제로 담기는 곳이 결국 배열이기 때문이고, 이건 누수가 있든 없든 똑같다. **"byte[]가 3GB네요"는 동어반복일 뿐 누가 왜 그것을 붙잡고 있는지 아무것도 말해주지 않는다.**

**둘째, retained 정렬은 "소유자"를 직접 가리킨다.**

누수는 구조적으로 거의 항상 같은 형태다 — **작은 홀더(캐시 맵, 리스너 리스트, ThreadLocal, static 컬렉션)가 거대한 객체 그래프를 놓아주지 않는** 형태다. retained로 정렬하면 48바이트짜리 HashMap이 1GB를 달고 최상단으로 떠오른다.

**shallow는 작은데 retained는 거대한 비대칭이 곧 누수의 시그니처다.** 이 한 문장이 3-4와 3-5 전체의 결론이다.

**셋째, retained는 조치와 직결되는 숫자다.**

retained size는 **"이 참조를 끊으면 정확히 이만큼 회수된다"**는 의미다. 즉 고쳤을 때의 효과가 숫자로 나와 있다. 상위 항목을 골라 Path to GC Roots(1-5)로 거슬러 올라가면 그대로 **수정할 코드**에 도달한다. shallow 정렬로는 이 경로가 열리지 않는다.

**전체를 한 줄로 요약하면**: shallow는 자기 자신의 크기(참조는 포인터만 셈)이고 retained는 죽으면 함께 회수되는 총량(dominator 기준)인데, 누수는 "작은 홀더가 거대한 그래프를 쥔" 구조이므로 shallow 정렬은 증상(`byte[]`)만 보여주고 retained 정렬이 원인(홀더)을 최상단에 띄우며 그 숫자가 곧 회수량이라 조치로 직결된다.

### 3-6. OOM 발생부터 원인 규명까지 — 전체 순서

앞의 내용을 장애 대응 순서로 이어 붙이면 이렇게 된다.

```
[1] 어느 영역의 OOM인지 메시지로 확인
    Java heap space / GC overhead limit exceeded  → 힙 문제. 힙 덤프로 간다.
    Metaspace                                     → 클래스 로더 누수. 힙 덤프가 아니라
                                                    로딩 클래스 추이를 본다.
    unable to create new native thread            → 스레드 폭증. 스레드 덤프로 간다.

[2] 덤프 확보
    -XX:+HeapDumpOnOutOfMemoryError로 이미 떠 있으면 그것을 쓴다 (최선).
    없으면 3-2의 우선순위대로 — drain 후 덤프 / gcore / histo 2회 비교.

[3] Histogram으로 규모 파악
    "무엇이 많은가". 대개 byte[], String이 상위 — 여기서 멈추면 안 된다(3-5).

[4] Dominator Tree를 retained 정렬로 열어 홀더 특정
    shallow는 작은데 retained가 거대한 항목을 찾는다. 그게 홀더다.

[5] Path to GC Roots로 붙잡는 주체 확인
    static cache -> HashMap -> Node[] -> byte[] 같은 체인이 나온다.
    체인의 맨 위(GC 루트)가 곧 수정 대상 코드의 위치다.

[6] 원인 유형 판정 후 조치
    누수형    (참조가 안 끊김)      → 코드 수정. 상한·만료 있는 캐시로 교체, 리스너 해제,
                                     ThreadLocal remove.
    용량형    (정상인데 데이터가 큼) → 힙 증설 또는 페이징·스트리밍으로 처리 방식 변경.
    두 유형을 가르는 기준: "이 객체들이 살아있는 것이 정상인가?"
```

**[6]의 마지막 질문이 이 조사 전체의 결론이다.** 힙 덤프는 "무엇이 메모리를 쓰고 있는가"까지만 알려주고, "그게 정상인가"는 도구가 아니라 도메인 지식으로 판단해야 한다. 1GB짜리 캐시가 누수인지 정상 설계인지는 덤프에 적혀 있지 않다.

## 4. 꼬리질문 대비 포인트

### "운영 중인 인스턴스인데, 지금 힙 덤프 떠도 될까요?"

**"뜨면 그동안 서비스가 멈춥니다"부터 말하고 시작한다.** 3-1의 타임라인을 근거로 말하면 좋다 — 8GB 힙에 로컬 SSD 기준으로 Full GC 3초 + 6GB 쓰기 12초로 **총 15초 정지**이고, 그 사이 헬스체크가 연속 실패해 LB에서 빠지며, 더 길어지면 liveness probe가 프로세스를 죽여 **덤프도 못 얻고 장애만 커진다.**

그래서 답은 "된다/안 된다"가 아니라 **순서**다. ① 이미 `-XX:+HeapDumpOnOutOfMemoryError`로 떠 놓은 파일이 있는지부터 확인하고, ② 없으면 그 인스턴스를 LB에서 빼고 liveness probe를 완화한 뒤 로컬 디스크에 뜨고, ③ 트래픽을 못 빼는 상황이면 `gcore`로 정지 시간을 줄이거나 `jmap -histo`를 몇 분 간격 두 번 떠서 증가분만 비교한다.

**"떠도 됩니다"라고 바로 답하면 해본 적 없다는 신호로 읽힌다.**

### "MAT를 열면 뭘 먼저 보시나요?"

**Dominator Tree를 retained size 정렬로 연다.**

이유를 함께 말해야 답이 완성된다. Histogram을 shallow 기준으로 보면 어느 덤프든 상위권이 `byte[]`, `char[]`, `String`으로 똑같이 나온다 — 데이터가 담기는 곳이 결국 배열이라 누수 유무와 무관하기 때문이다. 이건 증상이지 원인이 아니다.

**누수는 구조적으로 "작은 홀더가 거대한 그래프를 놓아주지 않는" 형태**이므로, retained로 정렬하면 shallow 48바이트짜리 HashMap이 1GB를 달고 최상단으로 떠오른다. **shallow는 작은데 retained는 거대한 비대칭이 누수의 시그니처다.**

그다음 그 항목에서 **Path to GC Roots**로 거슬러 올라가 붙잡고 있는 주체(static 필드, ThreadLocal, 리스너 리스트)를 확인하면, 그 지점이 그대로 수정할 코드다.

### "스레드 덤프에 BLOCKED가 하나도 없는데 API가 전부 타임아웃 납니다. 어떻게 보시겠어요?" (시니어 변별 포인트)

**"BLOCKED가 없으니 락 문제가 아니다"가 오답이라는 것을 아는지가 이 질문의 전부다.**

`BLOCKED` 상태는 **`synchronized` 모니터 진입 대기에만** 붙는다. 현대 자바 코드가 훨씬 많이 쓰는 `ReentrantLock`, `Semaphore`, 커넥션 풀 내부의 `j.u.c` 락은 전부 자바 코드로 구현돼 있어서, 대기 중인 스레드가 `WAITING (parking)` + `AbstractQueuedSynchronizer` 스택으로 나타난다.

그래서 확인 순서는 이렇다.

**① `jstack -l`로 다시 뜬다.** `-l` 옵션이 각 스레드의 "Locked ownable synchronizers" 섹션을 함께 출력해 주므로, `j.u.c` 락의 소유자를 알 수 있다.

**② 상태가 아니라 스택의 위치를 본다.** 수십 개 스레드가 전부 같은 지점에 몰려 있는지가 핵심이다. 가장 흔한 형태가 **커넥션 풀의 `getConnection` 대기**다 — 이 경우 진짜 원인은 락이 아니라 "커넥션을 오래 붙잡는 느린 쿼리"나 "커넥션을 반납하지 않는 코드"이고, 스레드는 그 결과로 밀려 있을 뿐이다.

**③ 3~5장을 비교한다.** 같은 스레드가 같은 위치에 계속 있으면 갇힌 것이고, 위치가 조금씩 움직이면 느린 것이지 멈춘 것은 아니다.

**④ 외부 대기를 의심한다.** 스레드들이 소켓 read에서 `RUNNABLE`로 멈춰 있는 경우도 흔하다. `RUNNABLE`인데 CPU는 안 쓰고 있다면 대개 네트워크 응답 대기이고, 이건 우리 쪽 문제가 아니라 상대 시스템 문제다.

마지막으로 덧붙이면 좋은 것 — **JVM의 데드락 자동 감지에 안 잡히는 교착이 있다.** DB 락 대기, 서로의 응답을 기다리는 두 스레드풀, 응답을 기다리며 자기 스레드풀을 다 소진한 구조 같은 논리적 교착은 JVM이 알 방법이 없으므로, 여러 장의 덤프를 사람이 비교해서 찾아야 한다.

### "데드락의 4가지 조건과 실무적 예방 방법은?"

네 조건은 **상호 배제, 점유와 대기, 비선점, 순환 대기**이고, 핵심은 **네 개가 동시에 성립해야 데드락이 되므로 하나만 깨면 된다**는 것이다.

**실무에서 실제로 깨는 것은 순환 대기와 점유·대기 둘이다.**

**순환 대기를 깨는 법 = 락 순서 고정.** 모든 스레드가 같은 전역 기준(계좌 ID, 리소스 이름 등)으로 락을 잡으면 대기 그래프에 원이 만들어질 수 없다. 계좌 이체에서 `transfer(A,B)`와 `transfer(B,A)`가 만드는 고전적 데드락은 "항상 ID가 작은 쪽을 먼저 잠근다"는 한 줄로 사라진다.

**점유와 대기를 깨는 법 = 타임아웃 있는 락 획득.** `synchronized`는 기다리기 시작하면 포기할 수 없지만, `ReentrantLock.tryLock(timeout)`은 못 잡으면 **이미 쥔 것을 놓고 물러날 기회**를 준다. 교착이 재시도로 바뀐다.

**상호 배제와 비선점은 사실상 못 깬다.** 상호 배제를 없앤다는 건 락을 안 쓴다는 뜻이라 자원의 성질상 불가능한 경우가 많고, 비선점도 자바에서 남의 락을 강제로 뺏는 수단이 없다.

**가장 좋은 답은 조건 얘기 다음에 나온다 — 애초에 락을 두 개 잡지 않도록 설계하는 것이다.** 잠글 단위를 하나로 합치거나, 락 구간을 좁혀 중첩이 생길 여지를 없애거나, 락 대신 DB의 낙관적 갱신으로 옮기는 방향이다. **규칙은 사람이 어기지만 구조는 어길 수 없다.**

그리고 반드시 덧붙일 것 — **락 안에서 HTTP·DB 같은 외부 호출을 하지 않는다.** 데드락 조건을 깨는 것은 아니지만, 실무에서 데드락과 구분이 안 되는 "사실상의 멈춤"을 만드는 가장 흔한 원인이다.

### "덤프 파일을 로컬 노트북에 받아서 분석해도 되나요?"

**힙 덤프는 개인정보 덩어리라는 인식이 있는지를 보는 질문이다.**

`strings app.hprof`만 돌려도 힙에 있던 문자열이 그대로 나온다. 덤프 시점에 처리 중이던 요청의 파라미터, 세션 토큰, 캐시에 있던 사용자 정보가 **전부 평문으로** 들어 있다. 즉 운영 힙 덤프는 로그가 아니라 **운영 DB 덤프와 같은 등급의 자료**다.

그래서 답은 "회사의 개인정보 취급 정책을 따른다"로 시작하되, 실무적으로 정해 둬야 할 것을 열거하면 좋다 — 저장 위치(접근 통제된 볼륨), 반출 가능 여부(대개 개인 단말 반출 금지, 분석 전용 서버에서만 열람), 접근 권한, 그리고 **삭제 기한**이다.

**마지막 항목이 실무에서 가장 잘 빠진다.** 장애 대응이 끝나면 수 GB짜리 개인정보 파일이 공용 디스크에 그대로 남는다. "분석이 끝나면 언제 지웁니까"까지 말하면 운영을 해 본 사람으로 보인다.

(가산점 포인트) 이 문제를 근본적으로 줄이는 방법도 있다. 민감 값을 `String` 대신 `char[]`로 다뤄 사용 직후 덮어쓰는 방식이다 — `String`은 불변이라 GC될 때까지 힙에 그대로 남지만, `char[]`는 다 쓴 뒤 `Arrays.fill(pw, '\0')`로 지울 수 있다. `javax.security.auth.Destroyable`이나 `KeyStore`의 비밀번호 API가 `char[]`를 받는 이유가 바로 이것이다.

## 한 줄 요약

힙 덤프는 객체 그래프 전체를 HPROF 바이너리로 찍느라 **힙 크기에 비례하는 STW**(8GB 힙이면 Full GC + 수 GB 디스크 쓰기로 십수 초, 그 사이 헬스체크 탈락과 liveness kill까지)를 유발하므로 **OOM 자동 덤프를 미리 걸어두고 뜰 때는 트래픽을 뺀 뒤 뜨는 것**이 전략의 전부이고, 스레드 덤프는 밀리초라 언제든 뜰 수 있는 대신 **여러 장을 비교하고 `j.u.c` 락은 BLOCKED로 안 보인다는 것을 알고 읽는 것**이 전략이며, 분석은 언제나 **shallow가 아니라 retained 정렬**로 "작은 홀더가 거대한 그래프를 쥔" 비대칭을 찾아 Path to GC Roots로 수정할 코드까지 거슬러 올라가는 순서를 따른다.
