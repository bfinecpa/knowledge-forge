# JVM 메모리 구조 — Heap, Stack, Metaspace와 객체가 사는 곳

> 핵심 관전 포인트: **객체는 전부 Heap에 생성된다(정확히는 대부분 Young 영역의
> Eden). Stack에는 객체가 아니라 "객체를 가리키는 참조"와 기본형 값,
> 메서드 호출 프레임이 스레드별로 쌓인다. Metaspace는 클래스의 설계도
> (메타데이터)가 올라가는 네이티브 메모리 영역이다.
> 이 지도가 머릿속에 있어야 OOM 메시지를 보고 "어느 영역이 터졌고,
> 어떤 덤프를 떠야 하는지"를 바로 판단할 수 있다.**

---

## 0. 질문 + 의도

**질문**: "JVM 메모리 구조(Heap, Stack, Metaspace)를 설명해주세요.
객체는 어디에 생성되나요?"

**출제 의도**: 운영 중 메모리 지표(heap 사용률, Metaspace 증가)를 읽고
"정상인지 누수인지"를 판단하는 첫 관문. 이 지도가 없으면 모니터링
대시보드의 그래프가 그냥 그림이고, OOM 알람이 왔을 때 어느 영역 덤프를
떠야 할지조차 정할 수 없다.

## 1. 전체 지도 — 공유 영역 vs 스레드별 영역

JVM 메모리는 크게 두 부류로 나뉜다. **"모든 스레드가 함께 쓰는가,
스레드마다 따로 갖는가"**가 기준이다.

| 구분 | 영역 | 담기는 것 |
|---|---|---|
| 모든 스레드 공유 | **Heap** | 객체와 배열의 실체 (GC 대상) |
| 모든 스레드 공유 | **Metaspace** | 클래스 메타데이터 (클래스 구조, 메서드 바이트코드 등) |
| 스레드마다 하나 | **Stack** | 메서드 호출 프레임 — 지역변수(기본형 값 + 객체 참조), 리턴 주소 |
| 스레드마다 하나 | PC 레지스터, 네이티브 메서드 스택 | 현재 실행 위치, JNI 호출용 스택 |

비유하면 **Heap은 팀 전체가 함께 쓰는 공용 창고**이고,
**Stack은 각자 책상 위의 작업 메모지**다. 창고의 물건(객체)은 누구나
꺼내 쓸 수 있지만, 메모지(지역변수)는 그 사람 작업이 끝나면
(메서드가 리턴하면) 바로 버려진다. **Metaspace는 창고 물건들의
설계도 보관실**이다 — 물건(인스턴스)이 아니라 물건을 만드는 도면
(클래스 정보)이 있다.

이 구분이 실무에서 중요한 이유:

- Heap은 공유라서 **동시성 문제와 GC의 무대**가 된다.
- Stack은 스레드 전용이라서 **지역변수는 그 자체로 thread-safe**다.
- Metaspace는 힙 밖 **네이티브 메모리**라서 `-Xmx`를 아무리 줄여도
  Metaspace 누수는 못 막는다 (별도 축).

## 2. 영역별 상세

### 2-1. Heap — 객체가 태어나고 죽는 곳

`new`로 만드는 모든 객체와 배열은 Heap에 생성된다. GC가 관리하는
유일한 영역이며, 내부는 다시 **Young(Eden + Survivor 2개)**과
**Old**로 나뉜다 (분리 이유는 GC 문서에서 상세히 — 요지는
"대부분의 객체는 금방 죽으므로 젊은 객체만 모아 싸게 자주 수집").

- 크기는 `-Xms`(초기) / `-Xmx`(최대)로 지정한다.
- 여기가 가득 차서 GC로도 확보가 안 되면
  `OutOfMemoryError: Java heap space`.

### 2-2. Stack — 메서드 호출의 발자취

스레드가 메서드를 호출할 때마다 **프레임(frame)** 하나가 쌓이고,
리턴하면 걷힌다. 프레임 안에는 지역변수 테이블(기본형 값과 객체
**참조**), 피연산자 스택, 리턴 주소가 있다.

- **객체의 실체는 절대 Stack에 없다.** 스택에는 힙 객체의 주소값
  (참조)만 있다.
- 재귀가 너무 깊어 프레임이 스택 한도를 넘으면 `StackOverflowError`.
- 스택은 **스레드당 하나씩** 할당된다(`-Xss`로 스레드당 크기 지정).
  스레드를 수천 개 만들면 힙이 아니라 이쪽 네이티브 메모리가 먼저
  바닥난다.

### 2-3. Metaspace — 클래스의 설계도 보관실

클래스 로더가 클래스를 로딩하면 그 클래스의 구조(필드/메서드 정보,
메서드 바이트코드, 상수 풀 등)가 Metaspace에 올라간다.

- Java 8에서 기존 PermGen을 대체하며 도입됐다. 가장 큰 차이는
  **힙 안의 고정 영역이 아니라 네이티브 메모리를 쓴다**는 것 —
  기본적으로 OS 메모리가 허용하는 만큼 자동 확장된다
  (`-XX:MaxMetaspaceSize`로 상한 지정 가능).
- 가득 차면 `OutOfMemoryError: Metaspace`. 힙 덤프가 아니라
  **로딩된 클래스 목록**을 봐야 하는 상황이다.

### 자주 틀리는 포인트 — static 변수와 문자열 리터럴의 위치 (가산점 포인트)

"클래스 정보니까 static도 Metaspace"라고 답하기 쉽지만 틀렸다.

- **static 변수**: Java 8부터 힙에 있다 (클래스의 `Class` 객체와 함께).
- **String 상수 풀(리터럴)**: Java 7부터 힙에 있다.

즉 Metaspace에는 "클래스의 구조 정보"만 있고, **값을 담는 것들은
전부 힙**이라고 정리하면 정확하다. 이 두 가지를 구분해 말하면
PermGen 시절 지식과 현재를 구분하는 사람으로 보인다.

## 3. 코드 한 줄씩 따라가며 배치 확인

```java
public class OrderService {
    private static final String PREFIX = "ORD-";   // ① 리터럴: 힙(String pool), static 참조: 힙의 Class 객체

    public Order create(long amount) {             // ② amount: 스택 (기본형 값 그 자체)
        String id = PREFIX + amount;               // ③ id 참조: 스택 / String 객체 실체: 힙
        Order order = new Order(id, amount);       // ④ order 참조: 스택 / Order 객체 실체: 힙(Eden)
        return order;                              // ⑤ 프레임이 걷히며 참조는 사라지지만
    }                                              //    힙의 Order 객체는 호출자가 계속 참조 → 생존
}
```

핵심 정리 — **"객체는 어디에 생성되나요?"의 정답**:

- 객체의 실체는 **힙**, 그중에서도 새 객체는 **Young 영역의 Eden**에
  생성된다.
- 메서드가 리턴하면 스택의 참조는 사라지지만, 힙의 객체는
  **아무도 참조하지 않게 된 시점부터 GC 회수 후보**가 될 뿐
  즉시 사라지지 않는다.
- (가산점 포인트) 엄밀히는 JIT의 **탈출 분석(escape analysis)**이
  "이 객체는 메서드 밖으로 절대 안 나간다"고 판단하면 힙 할당을
  생략하고 스칼라 치환(필드를 지역변수처럼 분해)할 수 있다.
  다만 이는 JIT 최적화이고, 개념 모델로는 "객체는 힙"이 정답이다.

## 4. 실무 맥락 — OOM 메시지가 곧 영역 지도다

이 구조를 아는 사람과 모르는 사람의 차이는 OOM 알람이 왔을 때 드러난다.
**메시지가 어느 영역이 터졌는지 알려주므로, 첫 조치가 달라진다.**

| OOM 메시지 | 터진 영역 | 첫 조치 |
|---|---|---|
| `Java heap space` | Heap | 힙 덤프 분석 (어떤 객체가 점유 중인가) |
| `GC overhead limit exceeded` | Heap (GC가 일만 하고 확보 못 함) | 힙 덤프 + GC 로그 |
| `Metaspace` | Metaspace | 로딩된 클래스 수 추이, 클래스 로더 누수 의심 |
| `unable to create new native thread` | 스레드 스택(네이티브) | 스레드 덤프, 스레드 수 폭증 원인 |

모니터링 그래프를 읽는 기준도 이 지도에서 나온다:

- **힙 사용률이 톱니 모양**(차오르다 GC로 뚝 떨어짐)은 정상이다.
  문제는 **GC 직후의 바닥이 점점 올라가는 패턴** — 회수 안 되는
  객체가 쌓인다는 뜻이라 누수를 의심한다.
- **Metaspace가 꾸준히 우상향**하면 클래스가 계속 로딩되고 있다는 뜻 —
  리플렉션/동적 프록시(CGLIB) 남용, 스크립트 엔진, 핫 리로드 잔재 등
  클래스 로더 누수를 의심한다. 힙 튜닝으로는 절대 안 잡힌다.

## 5. 꼬리질문 대비 포인트

### "static 변수와 문자열 리터럴은 어디에 저장되나요?"

둘 다 **힙**이다. static 변수는 Java 8부터 해당 클래스의 `Class` 객체와
함께 힙에 있고, String 상수 풀은 Java 7부터 힙으로 옮겨졌다.
Metaspace에는 클래스의 구조 정보(필드/메서드 정의, 바이트코드)만 있다.
"Metaspace요"라고 답하면 PermGen 시절 지식으로 멈춰 있다는 인상을 준다.

### "지역변수로 선언한 객체도 힙에 생기나요? 그럼 스택에는 뭐가 있죠?"

그렇다. `Order order = new Order()`에서 Order 인스턴스는 힙(Eden)에
생기고, 스택의 지역변수 `order`에는 그 힙 주소(참조)만 담긴다.
기본형(`int`, `long` 등) 지역변수만 값 자체가 스택에 있다.
그래서 메서드 리턴으로 스택 프레임이 걷혀도 힙의 객체는 남으며,
참조가 끊긴 뒤 GC가 회수한다. (가산점: escape analysis에 의한
스택 할당/스칼라 치환 예외 언급)

### "Metaspace 사용량이 계속 증가하면 무엇을 의심하겠습니까?"

클래스가 계속 새로 로딩되고 있다는 신호이므로 **클래스 로더 누수**를
의심한다. 전형적 원인은 ① 리플렉션·CGLIB 프록시·람다를 루프 안에서
동적 생성, ② Groovy/스크립트 엔진의 반복 컴파일, ③ 애플리케이션
핫 리로드 후 이전 클래스 로더가 참조로 붙잡혀 언로드되지 않는 경우.
`-verbose:class`나 JFR로 로딩 클래스 추이를 확인하고, 상한을
`-XX:MaxMetaspaceSize`로 걸어 무한 확장으로 OS 메모리를 잠식하는
사태를 막는다.

### "PermGen에서 Metaspace로 왜 바뀌었나요?" (시니어 변별 포인트)

PermGen은 **힙 안의 고정 크기 영역**이라 두 가지 고질병이 있었다.
① 크기를 미리 맞추기 어려워 `PermGen space` OOM이 빈발했고
(특히 클래스를 많이 로딩하는 웹 컨테이너 재배포 환경),
② 힙 튜닝과 얽혀 관리가 복잡했다. Metaspace는 이를 네이티브
메모리로 옮겨 **기본 자동 확장**으로 풀었다. 대신 상한을 안 걸면
OS 메모리를 잠식할 수 있으므로 운영에서는 상한 설정과 모니터링이
관례다. "영역 이름이 바뀐 게 아니라 메모리의 출처(힙 → 네이티브)가
바뀐 것"이라고 말하면 정확하다.

### "스레드를 아주 많이 만들면 어떤 메모리가 부족해지나요?"

스택은 **스레드당 하나씩** 네이티브 메모리에 할당되므로(-Xss, 통상
수백 KB~1MB 수준), 스레드가 수천 개면 힙과 무관하게 네이티브 메모리가
바닥나 `unable to create new native thread`가 난다. 힙을 줄여서(-Xmx)
네이티브 여유를 확보하거나, 애초에 스레드를 무한 생성하는 구조
(요청마다 new Thread, 무경계 스레드풀)를 고치는 게 정공법이다.

## 한 줄 요약

객체의 실체는 **힙(새 객체는 Eden)**, 스택에는 스레드별 호출 프레임과
**참조**만, Metaspace에는 클래스 **설계도**만 있다 — 이 지도를 알아야
OOM 메시지와 메모리 그래프를 보고 "어느 영역의 문제인지"를
첫 수에 판단할 수 있다.
