# JVM 메모리 구조 — Heap, Stack, Metaspace와 객체가 사는 곳

> 핵심 관전 포인트: **객체는 전부 Heap에 생성된다(정확히는 대부분 Young 영역의 Eden). Stack에는 객체가 아니라 "객체를 가리키는 참조"와 기본형 값, 메서드 호출 프레임이 스레드별로 쌓인다. Metaspace는 클래스의 설계도(메타데이터)가 올라가는 네이티브 메모리 영역이다. 이 지도가 머릿속에 있어야 OOM 메시지를 보고 "어느 영역이 터졌고, 어떤 덤프를 떠야 하는지"를 바로 판단할 수 있다.**

---

## 0. 질문 + 의도

**질문**: "JVM 메모리 구조(Heap, Stack, Metaspace)를 설명해주세요. 객체는 어디에 생성되나요?"

**출제 의도**: 운영 중 메모리 지표(heap 사용률, Metaspace 증가)를 읽고 "정상인지 누수인지"를 판단하는 첫 관문. 이 지도가 없으면 모니터링 대시보드의 그래프가 그냥 그림이고, OOM 알람이 왔을 때 어느 영역 덤프를 떠야 할지조차 정할 수 없다.

## 1. 전제부터 — "참조"가 무엇인지 먼저 알아야 지도가 읽힌다

### 1-1. 전제 지식 — 변수에 담기는 것은 객체가 아니다

이 문서의 결론은 "객체는 힙에, 참조는 스택에"다. 그런데 이 문장이 **정말로** 이해되려면 그 전에 "참조가 뭔데?"에 답이 있어야 한다. 여기서 막힌 채로 뒤를 읽으면 문장은 외워지지만 그림은 안 그려진다.

Java에서 이렇게 쓸 때를 보자.

```java
Person p = new Person("한주덕", 30);
```

우리는 흔히 "변수 `p`에 Person 객체가 들어 있다"고 말한다. **그런데 실제로 `p`라는 변수 칸에 들어 있는 값은 Person 객체가 아니라 숫자 하나다.** 그 숫자는 "Person 객체의 실물이 놓여 있는 메모리 위치"를 가리키는 주소값이다. 이 주소값을 **참조(reference)**라고 부른다. 말 그대로 "저기를 참조하라"는 안내표지다.

비유하면 **참조는 택배 송장에 적힌 주소**다. 송장(변수)에 적힌 것은 집 자체가 아니라 "서울시 ○○구 ○○로 12"라는 짧은 문자열이고, 집(객체)은 그 주소가 가리키는 땅 위에 실제로 서 있다. 송장을 복사해서 열 장을 만들어도 집이 열 채가 되지는 않는다. 반대로 송장을 전부 찢어버리면 집은 여전히 그 자리에 있지만 **아무도 찾아갈 수 없는 집**이 된다.

이 마지막 문장이 GC를 이해하는 출발점이기도 하다. "아무도 찾아갈 수 없게 된 집"이 곧 GC가 회수하는 대상이다.

주소를 적어두는 종이(변수 칸)와 집이 서 있는 땅(객체 실물)은 **서로 다른 장소**에 있다. 종이는 작고 개수가 정해져 있고 금방 버려지지만, 집은 크고 오래 남을 수 있다. JVM은 이 성질 차이 때문에 둘을 아예 다른 메모리 영역에 나눠 담는다. 그 종이가 놓이는 곳이 **Stack**, 집이 서는 땅이 **Heap**이다.

여기까지 왔으면 "객체는 힙에, 참조는 스택에"라는 문장은 이제 암기가 아니라 당연한 결론이 된다.

기본형은 예외라는 것도 같이 짚자. `int age = 30;`의 `30`은 주소가 아니라 **값 그 자체**다. 30이라는 숫자는 집처럼 클 것이 없어서 굳이 땅에 세워놓고 주소를 적을 이유가 없다. 그래서 기본형(`int`, `long`, `double`, `boolean`, `char` 등)은 변수 칸에 값이 직접 들어간다. 참조형만 주소가 들어간다.

### 1-2. `Person p = new Person()` 한 줄이 실행되면 어디에 무엇이 생기는가

이제 그 한 줄을 실행할 때 스택과 힙에 각각 무엇이 생기는지 그림으로 보자. 메서드 하나가 실행 중이라고 가정한다.

```java
public class OrderService {
    public void register() {
        int discount = 30;                          // (1)
        Person p = new Person("한주덕", discount);   // (2)
    }
}
```

```
        [스레드 A 전용 Stack]                        [모든 스레드가 공유하는 Heap]

  ┌── register() 프레임 ──────────┐          ┌── Young / Eden ─────────────────────┐
  │                               │          │                                     │
  │ 지역변수 0: this   = 0x7f10 ──┼────────► │  0x7f30 ┌───────────────────────┐   │
  │ 지역변수 1: discount = 30     │          │         │ Person 인스턴스 (실물) │   │
  │             (값 그 자체)      │          │         ├───────────────────────┤   │
  │ 지역변수 2: p      = 0x7f30 ──┼────────► │         │ 헤더: 마크워드 +      │   │
  │             (주소값 = 참조)   │          │         │       클래스 포인터 ──┼───┼──┐
  │                               │          │         │ name = 0x7f88 ────────┼─┐ │  │
  │ 피연산자 스택 / 리턴 주소      │          │         │ age  = 30             │ │ │  │
  └───────────────────────────────┘          │         └───────────────────────┘ │ │  │
                                             │                                   │ │  │
  프레임은 register()가 리턴하는              │  0x7f88 ┌─────────────────────┐   │ │  │
  순간 통째로 걷힌다.                         │         │ String "한주덕"     │◄──┘ │  │
  discount(30)도, p에 담긴                    │         └─────────────────────┘     │  │
  주소값 0x7f30도 함께 사라진다.               └───────────────────────────────────┘  │
  ★ 사라지는 건 "주소를 적은 종이"이지                                                 │
    0x7f30의 Person 객체 자체가 아니다.        ┌── Metaspace (네이티브 메모리) ────┐  │
                                              │  Person 클래스의 설계도             │◄─┘
                                              │  (필드 목록, 메서드 바이트코드 …)   │
                                              └────────────────────────────────────┘
```

한 줄씩 따라가면 이렇다.

1. `new Person(...)`이 실행되면 JVM은 **힙에서 Person 하나가 들어갈 만큼의 공간을 확보**한다(위 그림의 0x7f30). 크기는 객체 헤더 + 필드들의 합으로 정해지는데, 이 크기를 계산할 수 있는 이유는 Metaspace에 있는 Person 클래스의 설계도에 "필드가 몇 개이고 각각 몇 바이트인지"가 적혀 있기 때문이다.
2. 생성자가 실행되며 필드가 채워진다. `age`에는 30이 값으로 직접 들어가고, `name`에는 String 객체의 **주소**가 들어간다. 즉 참조는 스택에만 있는 게 아니다 — **힙 객체의 참조형 필드 안에도 참조가 있다.** 객체가 객체를 가리키며 그래프를 이룬다.
3. 마지막으로 그 힙 주소값(0x7f30)이 **스택 프레임의 지역변수 칸 `p`에 대입된다.** 이 대입이 `=`의 정체다. 객체를 복사해 넣는 것이 아니라 주소를 적어 넣는 것이다.

그림의 별표 부분이 이 절의 핵심이다. `register()`가 리턴하면 프레임이 통째로 걷히면서 `p`가 사라진다. 그런데 사라진 것은 **주소를 적어둔 종이**일 뿐, 0x7f30의 Person 객체는 힙에 그대로 남아 있다. 다만 이제 그 객체를 가리키는 종이가 하나도 없으므로 **아무도 찾아갈 수 없는 상태**가 되고, 이 상태의 객체를 GC가 나중에 회수한다.

여기서 "**GC 대상**"이라는 말도 정의하고 넘어가자. GC(Garbage Collector, 쓰레기 수집기)는 더 이상 쓰이지 않는 객체를 찾아 메모리를 되돌려주는 JVM의 장치이고, **GC 대상 영역이란 "GC가 자동으로 청소해 주는 영역"**을 뜻한다. 힙이 그렇다. 스택은 GC가 청소하는 게 아니라 메서드가 리턴할 때 프레임이 걷히며 자동으로 정리된다 — 청소부가 필요 없는 구조다.

### 1-3. 전체 지도 — 공유 영역 vs 스레드별 영역

이제 지도 전체를 펼치자. JVM 메모리를 가르는 첫 번째 기준은 **"모든 스레드가 함께 쓰는가, 스레드마다 따로 갖는가"**다.

| 구분 | 영역 | 담기는 것 |
|---|---|---|
| 모든 스레드 공유 | **Heap** | 객체와 배열의 실체 (GC 대상) |
| 모든 스레드 공유 | **Metaspace** | 클래스 메타데이터 (클래스 구조, 메서드 바이트코드 등) |
| 스레드마다 하나 | **Stack** | 메서드 호출 프레임 — 지역변수(기본형 값 + 객체 참조), 리턴 주소 |
| 스레드마다 하나 | PC 레지스터, 네이티브 메서드 스택 | 현재 실행 위치, JNI 호출용 스택 |

비유하면 **Heap은 팀 전체가 함께 쓰는 공용 창고**이고, **Stack은 각자 책상 위의 작업 메모지**다. 창고의 물건(객체)은 주소만 알면 누구나 꺼내 쓸 수 있지만, 메모지(지역변수)는 그 사람 작업이 끝나면(메서드가 리턴하면) 바로 버려진다.

**Metaspace는 창고 물건들의 설계도 보관실**이다. 물건(인스턴스)이 아니라 물건을 만드는 도면(클래스 정보)이 있다. 여기서 **메타데이터(metadata)**란 "데이터에 대한 데이터"라는 뜻으로, 여기서는 **객체가 담고 있는 값이 아니라 그 객체가 어떻게 생겼는지를 설명하는 정보**를 가리킨다. `age = 30`이라는 값은 데이터고, "Person에는 age라는 int 필드가 두 번째 자리에 있다"는 것이 메타데이터다.

이 구분이 실무에서 갈리는 지점은 셋이다.

**Heap은 공유라서 동시성 문제와 GC의 무대가 된다.** 여러 스레드가 같은 주소를 들고 같은 객체를 동시에 건드릴 수 있으므로 `synchronized`나 락이 필요해지는 지점이 전부 여기다.

**Stack은 스레드 전용이라 지역변수는 그 자체로 thread-safe다.** 다른 스레드는 내 스택 프레임을 볼 방법이 아예 없다. 다만 주의할 것은 "지역변수가 안전"한 것이지 "지역변수가 가리키는 객체가 안전"한 것은 아니라는 점이다. 그 객체가 힙에 있고 다른 스레드도 같은 주소를 알고 있다면 그 객체는 공유 자원이다.

**Metaspace는 힙 밖의 네이티브 메모리라서 `-Xmx`로는 통제되지 않는다.** 여기서 **네이티브 메모리(native memory)**란 JVM이 힙으로 미리 떼어 관리하는 영역이 아니라, **JVM 프로세스가 운영체제에 직접 요청해서 받아 쓰는 메모리**를 말한다. C 프로그램이 `malloc`으로 받아 쓰는 그 메모리와 같은 것이라 "네이티브(원래의, 기본의)"라고 부른다. 힙과는 회계 장부가 완전히 다른 축이므로, `-Xmx`(힙 최대 크기)를 아무리 줄여도 Metaspace 누수는 막히지 않는다.

## 2. 영역별 상세

### 2-1. Heap — 객체가 태어나고 죽는 곳

`new`로 만드는 모든 객체와 배열은 Heap에 생성된다. GC가 관리하는 유일한 영역이며, 내부는 다시 **Young(Eden + Survivor 2개)**과 **Old**로 나뉜다.

분리 이유는 GC 문서에서 상세히 다루지만 요지만 미리 말하면 이렇다 — **대부분의 객체는 만들어지자마자 죽으므로, 젊은 객체만 모아둔 좁은 영역(Young)을 자주 싸게 수집하고 오래 살아남은 소수만 Old로 옮긴다.**

- 크기는 `-Xms`(시작 시 확보할 크기) / `-Xmx`(최대 크기)로 지정한다.
- 여기가 가득 차서 GC를 돌려도 공간이 확보되지 않으면 `OutOfMemoryError: Java heap space`가 난다.

새 객체가 Eden에 놓일 때 정확히 어떻게 자리를 잡는지도 알아두면 좋다. **(가산점 포인트)** JVM은 Eden을 통째로 두고 모든 스레드가 경쟁하게 두지 않는다. 그렇게 하면 객체를 하나 만들 때마다 "다음 빈 자리 포인터"를 두고 스레드끼리 원자적 연산으로 다퉈야 해서 할당이 비싸진다. 대신 스레드마다 Eden의 한 조각을 미리 통째로 떼어 준다. 이 조각을 **TLAB(Thread-Local Allocation Buffer, 스레드 전용 할당 버퍼)**이라고 부른다. 자기 조각 안에서는 경쟁자가 없으니 **포인터를 그냥 앞으로 밀기만 하면(bump-the-pointer)** 할당이 끝난다. 그래서 Java의 객체 생성은 흔한 오해와 달리 매우 싸다 — 보통 몇 개의 기계어 명령 수준이다. 조각을 다 쓰면 그때만 새 조각을 받아 온다.

### 2-2. Stack — 메서드 호출의 발자취

스레드가 메서드를 호출할 때마다 **프레임(frame)** 하나가 쌓이고, 리턴하면 걷힌다. 프레임 안에는 지역변수 테이블(기본형 값과 객체 **참조**), 계산 중간값을 올려두는 피연산자 스택, 리턴 주소가 있다.

프레임이 "쌓이고 걷힌다"는 표현이 곧 스택이라는 이름의 이유다. 가장 나중에 호출된 메서드가 가장 먼저 리턴하므로, 접시를 쌓았다가 위에서부터 걷어내는 구조(LIFO)와 정확히 같다.

- **객체의 실체는 절대 Stack에 없다.** 스택에는 힙 객체의 주소값(참조)만 있다.
- 재귀가 너무 깊어 프레임이 스택 한도를 넘으면 `StackOverflowError`가 난다. 힙과 무관한 에러이고, 힙을 늘려도 안 잡힌다.
- 스택은 **스레드당 하나씩** 네이티브 메모리에 할당된다(`-Xss`로 스레드당 크기 지정, 통상 수백 KB~1MB 수준). 그래서 스레드를 수천 개 만들면 힙이 아니라 이쪽 네이티브 메모리가 먼저 바닥난다.

### 2-3. Metaspace — 클래스의 설계도 보관실

클래스 로더가 클래스를 로딩하면 그 클래스의 구조(필드/메서드 정보, 메서드 바이트코드, 상수 풀 등)가 Metaspace에 올라간다. 인스턴스를 몇 개 만들든 설계도는 클래스당 한 벌이면 충분하므로, Person 인스턴스가 100만 개여도 Metaspace의 Person 항목은 하나다.

Java 8에서 **PermGen**을 대체하며 도입됐다. PermGen이 무엇이었는지부터 짚자. **PermGen(Permanent Generation, 영구 세대)은 Java 7까지 클래스 메타데이터가 올라가던 영역으로, 힙 안에 미리 잘라놓은 고정 크기 구획이었다.** "영구"라는 이름은 여기 올라간 것들이 애플리케이션이 사는 내내 남을 거라는(그래서 일반 객체와 달리 자주 청소할 필요가 없다는) 초기 가정에서 왔다.

Metaspace와 PermGen의 가장 큰 차이는 **힙 안의 고정 영역이 아니라 네이티브 메모리를 쓴다**는 것이다. 기본적으로 OS 메모리가 허용하는 만큼 자동 확장되며, 상한을 걸고 싶으면 `-XX:MaxMetaspaceSize`로 지정한다.

가득 차면 `OutOfMemoryError: Metaspace`가 난다. 이때는 힙 덤프가 아니라 **로딩된 클래스 목록**을 봐야 하는 상황이다 — 문제가 객체가 아니라 클래스이기 때문이다.

### 2-4. 자주 틀리는 포인트 — static 변수와 문자열 리터럴의 위치 (가산점 포인트)

"클래스에 딸린 정보니까 static도 Metaspace겠지"라고 답하기 쉽지만 틀렸다.

**static 변수는 Java 8부터 힙에 있다.** 정확히는 그 클래스를 대표하는 `Class` 객체(클래스 미러)와 함께 힙에 놓인다. 생각해 보면 자연스럽다 — static 필드에 담기는 것도 결국 **값 또는 다른 객체를 가리키는 참조**이고, 값을 담는 것들은 힙에 있어야 GC가 추적할 수 있다.

**String 상수 풀(리터럴)도 Java 7부터 힙에 있다.** 여기서 **String pool(문자열 상수 풀)**이란, 코드에 직접 쓴 문자열 리터럴(`"ORD-"` 같은 것)을 **같은 내용이면 하나만 만들어 두고 재사용하는 저장소**다. `"ORD-"`가 코드 수백 군데에 나와도 String 객체는 하나만 만들어지고 전부 그 하나의 주소를 참조한다. 문자열은 불변(immutable)이라 공유해도 서로 간섭할 일이 없으니 가능한 최적화다.

정리하면 **Metaspace에는 "클래스의 구조 정보"만 있고, 값을 담는 것들은 전부 힙**이다. 이 두 가지를 구분해 말하면 PermGen 시절 지식과 현재를 구분하는 사람으로 보인다.

## 3. 코드로 확인하고 운영으로 잇기

### 3-1. 코드 한 줄씩 따라가며 배치 확인

```java
public class OrderService {
    private static final String PREFIX = "ORD-";   // ① 리터럴 "ORD-"의 실체는 힙(String pool).
                                                   //    PREFIX라는 static 필드 칸도 힙(Class 객체 안).
                                                   //    Metaspace에는 "PREFIX라는 static String 필드가 있다"는 구조 정보만.

    public Order create(long amount) {             // ② amount는 기본형 → 값 자체가 스택 프레임에 들어감
        String id = PREFIX + amount;               // ③ 새 String 객체의 실체는 힙(Eden).
                                                   //    지역변수 id에는 그 힙 주소만 담긴다.
                                                   //    (연결로 만들어진 문자열은 리터럴이 아니라 새 객체다)
        Order order = new Order(id, amount);       // ④ Order 실체는 힙(Eden). order에는 주소만.
                                                   //    Order 안의 id 필드에도 ③ String의 주소가 들어간다.
        return order;                              // ⑤ 리턴은 "객체를 복사해 돌려주는" 게 아니라
    }                                              //    주소값을 호출자에게 넘기는 것이다.
}                                                  //    프레임은 걷히지만 호출자가 그 주소를 받아 들고 있으므로
                                                   //    힙의 Order 객체는 계속 살아 있다.
```

주석 ⑤가 1-1의 송장 비유와 정확히 이어진다. 프레임이 걷히며 이 메서드의 송장은 버려지지만, 호출자가 같은 주소가 적힌 송장을 새로 들고 있으므로 집은 여전히 찾아갈 수 있다.

**"객체는 어디에 생성되나요?"의 정답**을 정리하면 이렇다.

- 객체의 실체는 **힙**, 그중에서도 새 객체는 **Young 영역의 Eden**(정확히는 그 스레드의 TLAB)에 생성된다.
- 메서드가 리턴하면 스택의 참조는 사라지지만, 힙의 객체는 **아무도 참조하지 않게 된 시점부터 GC 회수 후보가 될 뿐** 즉시 사라지지 않는다. "참조가 끊긴다 = 즉시 메모리가 반환된다"가 아니라는 점이 C++의 `delete`와 다른 지점이다.
- **(가산점 포인트)** 엄밀히는 예외가 있다. JIT 컴파일러의 **탈출 분석(escape analysis)** — "이 객체가 만들어진 메서드 밖으로 새어 나가는가(escape)"를 컴파일 시점에 따져보는 최적화 — 이 "절대 안 나간다"고 판단하면, 힙 할당을 아예 생략하고 객체의 필드들을 지역변수처럼 분해해 버릴 수 있다. 이것을 **스칼라 치환(scalar replacement)**이라고 한다. 다만 이는 JIT가 상황을 봐서 하는 최적화이고, 개념 모델로는 "객체는 힙"이 정답이다.

### 3-2. OOM 메시지가 곧 영역 지도다

이 구조를 아는 사람과 모르는 사람의 차이는 OOM 알람이 왔을 때 드러난다. **`OutOfMemoryError`는 하나의 에러가 아니라 "어느 영역이 터졌는지"를 메시지로 알려주는 에러 집합이고, 영역마다 첫 조치가 완전히 다르다.**

| OOM 메시지 | 터진 영역 | 첫 조치 |
|---|---|---|
| `Java heap space` | Heap | 힙 덤프 분석 (어떤 객체가 점유 중인가) |
| `GC overhead limit exceeded` | Heap (GC가 일만 하고 확보 못 함) | 힙 덤프 + GC 로그 |
| `Metaspace` | Metaspace | 로딩된 클래스 수 추이, 클래스 로더 누수 의심 |
| `unable to create new native thread` | 스레드 스택(네이티브) | 스레드 덤프, 스레드 수 폭증 원인 |

표만 보면 암기 대상 같지만, 1절의 지도를 갖고 있으면 전부 유도된다.

`Java heap space`는 **객체가 너무 많거나 안 죽는다**는 뜻이다. 그래서 "어떤 객체가 얼마나 있고 누가 붙잡고 있는가"를 봐야 하고, 그 정보가 들어 있는 것이 힙 덤프다.

`GC overhead limit exceeded`는 조금 다르다. 힙이 완전히 찬 것은 아닌데 **GC가 계속 돌면서도 회수량이 거의 없는 상태**다. 애플리케이션은 일을 못 하고 GC만 CPU를 태우고 있으므로 JVM이 "이건 가망 없다"고 판단해 던지는 에러다. 곧 터질 `Java heap space`의 전조이므로 같은 조치를 취하되, GC 로그를 함께 봐서 언제부터 회수량이 떨어졌는지 확인한다.

`Metaspace`는 **객체가 아니라 클래스가 너무 많다**는 뜻이다. 힙 덤프를 아무리 뒤져도 원인이 안 보인다. 봐야 할 것은 로딩된 클래스 목록과 그 증가 추이다.

`unable to create new native thread`는 힙과 아예 무관하다. 2-2에서 봤듯 스택은 스레드마다 네이티브 메모리에 잡히므로, 스레드 수가 폭증하면 힙에 여유가 넘쳐도 이 에러가 난다. **여기서 `-Xmx`를 늘리는 것은 오히려 역효과다** — 힙이 커진 만큼 네이티브에 남는 여유가 줄기 때문이다.

### 3-3. 모니터링 그래프를 읽는 기준도 이 지도에서 나온다

**힙 사용률이 톱니 모양인 것은 정상이다.** 차오르다가 GC로 뚝 떨어지고 다시 차오르는 패턴이 건강한 상태다. 톱니를 보고 "메모리가 계속 차네요"라고 놀랄 필요가 없다.

문제 신호는 모양이 아니라 **바닥선**이다. **GC 직후의 바닥이 회차마다 조금씩 올라가는 패턴** — 즉 아무리 치워도 안 치워지는 잔량이 누적되는 모양 — 이 누수의 시그니처다. 참조가 끊기지 않아 회수되지 못하는 객체가 쌓이고 있다는 뜻이다.

**Metaspace가 꾸준히 우상향하면 클래스가 계속 새로 로딩되고 있다는 뜻이다.** 리플렉션이나 동적 프록시(CGLIB)를 반복 생성하는 코드, 스크립트 엔진의 반복 컴파일, 핫 리로드 후 남은 이전 클래스 로더 등 **클래스 로더 누수**를 의심한다. 이 축은 힙 튜닝으로 절대 안 잡힌다 — 애초에 다른 메모리이기 때문이다.

## 4. 꼬리질문 대비 포인트

### "static 변수와 문자열 리터럴은 어디에 저장되나요?"

둘 다 **힙**이다. static 변수는 Java 8부터 해당 클래스의 `Class` 객체와 함께 힙에 있고, String 상수 풀은 Java 7부터 힙으로 옮겨졌다. Metaspace에는 클래스의 구조 정보(필드/메서드 정의, 바이트코드)만 있다.

기준을 한 문장으로 말하면 **"값을 담는 것은 힙, 구조를 설명하는 것은 Metaspace"**다. "Metaspace요"라고 답하면 PermGen 시절 지식으로 멈춰 있다는 인상을 준다.

### "지역변수로 선언한 객체도 힙에 생기나요? 그럼 스택에는 뭐가 있죠?"

그렇다. `Order order = new Order()`에서 Order 인스턴스는 힙(Eden)에 생기고, 스택의 지역변수 `order`에는 그 힙 주소(참조)만 담긴다. **"지역변수로 선언했다"는 것은 그 변수 칸이 스택에 있다는 뜻일 뿐, 객체가 스택에 있다는 뜻이 아니다.**

기본형(`int`, `long` 등) 지역변수만 값 자체가 스택에 있다. 그래서 메서드 리턴으로 스택 프레임이 걷혀도 힙의 객체는 남으며, 참조가 전부 끊긴 뒤에야 GC가 회수한다. (가산점: escape analysis에 의한 스칼라 치환 예외를 덧붙이면 좋다)

### "Metaspace 사용량이 계속 증가하면 무엇을 의심하겠습니까?"

클래스가 계속 새로 로딩되고 있다는 신호이므로 **클래스 로더 누수**를 의심한다.

전형적 원인은 셋이다. ① 리플렉션·CGLIB 프록시·람다를 루프 안에서 동적 생성하는 코드, ② Groovy 같은 스크립트 엔진의 반복 컴파일, ③ 애플리케이션 핫 리로드 후 이전 클래스 로더가 어딘가에서 참조로 붙잡혀 언로드되지 않는 경우.

**③이 왜 누수인지는 한 번 짚고 넘어갈 만하다.** 클래스가 Metaspace에서 내려가려면 그 클래스를 로딩한 클래스 로더가 통째로 회수돼야 하는데, 클래스 로더는 자기가 로딩한 모든 클래스를 붙잡고 있고 그 클래스들의 인스턴스가 어딘가(예: 다른 로더가 관리하는 static 필드, ThreadLocal)에 남아 있으면 로더 전체가 회수되지 않는다. **클래스 하나가 아니라 로더 단위로 통째로 남는다**는 점이 이 누수를 크게 만든다.

조치는 `-verbose:class`나 JFR로 로딩 클래스 추이를 확인하는 것부터다. 그리고 상한을 `-XX:MaxMetaspaceSize`로 걸어, 무한 확장이 OS 메모리를 잠식해 프로세스가 OOM Killer에 죽는 사태를 막는 것이 운영 관례다.

### "PermGen에서 Metaspace로 왜 바뀌었나요?" (시니어 변별 포인트)

PermGen은 **힙 안의 고정 크기 영역**이라 두 가지 고질병이 있었다.

첫째, 크기를 미리 맞추기가 어려워 `PermGen space` OOM이 빈발했다. 특히 웹 컨테이너에 애플리케이션을 재배포하는 환경에서 심했다 — 재배포할 때마다 새 클래스 로더가 클래스를 다시 로딩하는데 이전 로더가 완전히 회수되지 않으면 PermGen이 조금씩 차올라, 몇 번 재배포하면 터졌다.

둘째, 힙 안에 있다 보니 힙 튜닝과 얽혀 관리가 복잡했다. 힙을 늘리면 그만큼 PermGen 몫이 어떻게 되는지까지 같이 고민해야 했다.

Metaspace는 이를 **네이티브 메모리로 옮기고 기본 자동 확장**으로 풀었다. 크기를 미리 맞출 필요 자체가 없어진 것이다. 대신 상한을 안 걸면 OS 메모리를 잠식할 수 있으므로 운영에서는 상한 설정과 모니터링이 관례가 됐다.

**"영역 이름이 바뀐 게 아니라 메모리의 출처(힙 → 네이티브)가 바뀐 것"**이라고 말하면 정확하다. 그리고 이 변경이 문제를 없앤 게 아니라 **"터지는 문제"를 "잠식하는 문제"로 성격을 바꾼 것**이라는 점까지 말하면 트레이드오프를 보는 사람으로 보인다.

### "스레드를 아주 많이 만들면 어떤 메모리가 부족해지나요?"

**힙이 아니라 네이티브 메모리**가 부족해진다.

스택은 스레드당 하나씩 네이티브 메모리에 할당되므로(`-Xss`, 통상 수백 KB~1MB 수준), 스레드가 수천 개면 힙에 여유가 넘쳐도 네이티브 메모리가 바닥나 `unable to create new native thread`가 난다.

**대응이 직관과 반대라는 점이 이 질문의 함정이다.** 메모리가 부족하다니까 `-Xmx`를 늘리면 오히려 악화된다 — 힙이 가져가는 몫이 커지면 같은 프로세스 안에서 네이티브에 남는 여유는 줄기 때문이다. 급한 불은 `-Xmx`를 **줄여서** 네이티브 여유를 확보하는 쪽으로 끄고, 정공법은 애초에 스레드를 무한 생성하는 구조(요청마다 `new Thread`, 큐 상한 없는 스레드풀)를 고치는 것이다.
