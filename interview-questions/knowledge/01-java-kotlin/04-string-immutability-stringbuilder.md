# String 불변성과 StringBuilder — 불변이 공짜로 주는 것, 그리고 그 비용

> 핵심 관전 포인트: **불변(immutable)이란 "객체가 만들어진 뒤로는 그 상태가 절대 바뀌지 않는다"는 뜻이고, 그래서 String에서 값을 바꾸는 것처럼 보이는 메서드는 전부 원본을 그대로 둔 채 새 String을 만들어 돌려준다. String은 내부 문자 배열을 `private final`로 감추고 밖으로 절대 내주지 않으며 클래스 자체가 `final`이라 상속으로도 뚫을 수 없게 만들어 이 성질을 지킨다. 여기서 나머지가 전부 따라 나온다 — 바뀌지 않으니 같은 리터럴을 여러 참조가 공유해도 안전하고, 그래서 JVM이 String pool에 하나만 만들어 재사용하며(Java 7부터 힙에 있다), 바뀌지 않으니 hashCode를 한 번 계산해 필드에 캐싱할 수 있어 HashMap 키로 최적이고, 바뀌지 않으니 여러 스레드가 동기화 없이 읽어도 되고, 바뀌지 않으니 보안 검증을 통과한 값이 사용 시점까지 그대로임이 보장된다. 비용은 "수정처럼 보이는 모든 연산이 새 객체 생성"이라는 것이고, 루프 안에서 `+=`로 누적하면 매 회전마다 지금까지의 전체를 복사하므로 총 복사량이 0+1+2+...+(n-1) = n(n-1)/2, 즉 O(n²)가 된다. 그래서 반복 누적 지점에서만 내부 배열을 고쳐 쓰는 StringBuilder로 비용을 지불한다 — 반대로 한 표현식 안의 `+` 연결은 컴파일러가 알아서 한 번에 처리하므로 손대지 않는다.**

---

## 0. 질문 + 의도

**질문**: "String이 불변(immutable)인 이유와 그로 인한 장점은 무엇인가요? `StringBuilder`는 언제 쓰나요?"

**출제 의도**: 불변 객체가 왜 스레드 안전과 캐싱(String pool)을 공짜로 주는지 이해하는지를 본다. 이 감각이 있는 사람은 도메인 객체 설계에서도 불변을 기본값으로 두어 동시성 버그의 반을 원천 차단한다.

## 1. 불변이란 무엇인가 — String이 불변이라는 말부터 정의하고 시작한다

### 1-1. 전제 지식 — 불변은 "변수를 못 바꾼다"가 아니다

"String은 불변이다"라는 문장을 외우기 전에 **불변이 무엇인지**부터 정해야 한다. 여기가 흐릿한 채로 넘어가면 뒤에 나오는 String pool도, 해시 캐싱도 전부 따로 노는 암기 항목이 된다.

**불변(immutable)이란 객체가 생성된 이후로 그 상태가 절대 바뀌지 않는다는 성질이다.** 한 번 `"hello"`라는 내용으로 태어난 String 객체는 세상이 끝날 때까지 `"hello"`다. 어떤 메서드를 불러도, 어떤 스레드가 건드려도 그 객체의 내용은 그대로다.

그러면 `toUpperCase()`나 `replace()` 같은 메서드는 뭘 하는 것인가. **원본은 손대지 않고 결과를 담은 새 String을 만들어 돌려준다.** 이 사실은 코드 한 줄로 손에 잡힌다.

```java
String s = "hello";

s.toUpperCase();   // 반환값을 아무 데도 안 받았다
System.out.println(s);
// 출력: hello
// 대문자로 바뀌지 않았다. toUpperCase()가 만든 "HELLO"는
// 어디에도 담기지 않은 채 버려졌고, s가 가리키는 객체는 그대로다.

String upper = s.toUpperCase();
System.out.println(s + " / " + upper);
// 출력: hello / HELLO
// "HELLO"는 별개의 새 객체다. s는 여전히 "hello"를 가리킨다.
```

Java를 막 시작한 사람이 가장 흔히 밟는 지뢰가 첫 번째 줄이다. `s.toUpperCase();`라고만 쓰고 s가 바뀌었을 거라 기대하는 것 — 이 코드가 아무 일도 안 하는 이유가 곧 불변의 정의다.

여기서 반드시 갈라야 하는 것이 하나 더 있다. **"참조를 다른 객체로 바꿔 끼우는 것"과 "객체의 내용을 바꾸는 것"은 완전히 다른 일이다.**

`String s = "hello";`에서 변수 `s`의 칸에 들어 있는 것은 문자열 자체가 아니라 **그 String 객체가 힙 어디에 있는지를 가리키는 주소값**이다(이 참조 개념은 `01-jvm-memory-structure.md` 참고). 그래서 `s = s.toUpperCase();`가 하는 일은 이렇게 그려진다.

```
[대입 전]
  변수 s ──────► ┌──────────────┐
                 │ String "hello"│   (힙)
                 └──────────────┘

[s = s.toUpperCase() 실행 후]
  변수 s ──┐     ┌──────────────┐
           │     │ String "hello"│   ← 내용이 바뀐 게 아니라 그대로 남아 있다
           │     └──────────────┘      (아무도 안 가리키면 나중에 GC 대상)
           │
           └───► ┌──────────────┐
                 │ String "HELLO"│   ← 새로 만들어진 별개의 객체
                 └──────────────┘
```

**바뀐 것은 화살표가 향하는 곳이지, 상자 안의 글자가 아니다.** 그래서 `s`를 다시 대입하는 것은 가능하고(그건 변수의 성질이다), 그것을 막고 싶으면 `final String s`로 재할당을 금지한다. `final`은 화살표를 고정하는 키워드이고, 불변은 상자 쪽의 성질이다. 둘은 서로 다른 층위의 이야기다.

### 1-2. String은 불변을 어떻게 지키는가 — 세 개의 자물쇠

"바꾸는 메서드를 안 만들었다"만으로는 불변이 지켜지지 않는다. 우회로가 여럿 있기 때문이다. String은 그 우회로를 하나씩 막아 놓았고, 그 방법 세 가지가 그대로 **불변 객체를 만드는 교과서 패턴**이다.

**(1) 상태를 `private final` 필드로 감춘다.** 실제로 `String` 클래스의 내부를 들여다보면 이렇게 되어 있다(리플렉션으로 필드 목록을 뽑아 확인한 결과다).

```
value : private final byte[]
coder : private final byte
hash  : private int
```

`value`가 실제 문자들이 담긴 배열이다. `private`이라 클래스 밖에서는 접근 자체가 안 되고, `final`이라 String 자기 코드조차 **다른 배열로 바꿔 끼울 수 없다.**

배열이 `char[]`가 아니라 `byte[]`인 이유도 짚어두면 좋다. **(가산점 포인트)** Java 9부터 **Compact Strings**라는 최적화가 들어가, 문자열이 라틴-1 범위(한 글자 1바이트로 표현 가능한 문자)로만 이루어져 있으면 글자당 2바이트가 아니라 1바이트로 저장한다. 어느 방식으로 저장했는지를 표시하는 것이 `coder` 필드다. 대부분의 실무 문자열(ID, 코드값, 영문 로그)이 라틴-1이라 힙 사용량이 눈에 띄게 준다. Java 8까지는 `private final char[] value`였다.

**(2) 내부 배열을 밖으로 절대 내주지 않는다.** 필드를 `private`으로 감춰도, 그 배열을 그대로 반환하는 메서드가 하나라도 있으면 불변이 무너진다. 받은 쪽에서 배열 원소를 바꾸면 String 내용이 바뀌기 때문이다.

```java
// 만약 String에 이런 메서드가 있었다면 (실제로는 없다)
char[] leaked = s.getInternalArray();  // 내부 배열을 그대로 반환
leaked[0] = 'X';                       // String 내용이 밖에서 바뀐다 — 불변 붕괴

// 실제 String의 toCharArray()는 항상 '복사본'을 만들어 준다
char[] copy = s.toCharArray();
copy[0] = 'X';                         // 복사본만 바뀐다. s는 무사하다
```

이것이 **방어적 복사(defensive copy)**다 — 내부에 든 가변 물건을 밖으로 내보낼 때 원본 대신 복제품을 주는 기법이고, 방어라는 이름은 "밖에서 원본을 건드리는 것을 미리 막는다"는 뜻이다.

**(3) 클래스를 `final`로 만들어 상속을 봉쇄한다.** 앞의 둘을 다 해도 구멍이 하나 남는다. 누군가 String을 상속해서 **가변인 하위 클래스**를 만들면, 그 객체는 String 타입 자리에 들어갈 수 있으면서 내용이 바뀐다.

```java
// 만약 String이 final이 아니었다면 가능했을 공격
class EvilString extends String {
    private String current;
    @Override public boolean equals(Object o) {
        current = flipEveryOtherCall();   // 부를 때마다 다른 답을 준다
        return ...;
    }
}

// 이 객체를 String 파라미터 자리에 넘기면, 받는 쪽은 "String이니까 안 바뀐다"고
// 믿고 검증 한 번 하고 그 값을 계속 쓴다 — 그 믿음이 깨진다.
```

`java.lang.String`은 실제로 `final class`다(`Modifier.isFinal(String.class.getModifiers())`가 `true`를 반환한다). 그래서 이 공격 코드는 애초에 컴파일되지 않는다.

**상태 은닉 + 수정 메서드 없음 + 상속 봉쇄.** 이 세 자물쇠가 세트다. 하나라도 빠지면 "불변인 척하는 객체"가 되고, 뒤에 나올 공유·캐싱·스레드 안전이 전부 근거를 잃는다. 그래서 이 셋은 그대로 불변 도메인 객체(Money, 기간, 좌표 같은 값 객체)를 설계할 때의 체크리스트가 된다.

## 2. 불변이 공짜로 주는 네 가지

여기서부터가 이 질문의 본체다. 앞 절의 "안 바뀐다"는 성질 하나에서 네 가지 이득이 파생되는데, **네 가지가 나란한 항목이 아니라 전부 같은 뿌리에서 나온다**는 점이 핵심이다.

### 2-1. 안전한 공유 — String pool은 원인이 아니라 결과다

String pool을 먼저 설명하고 "그래서 불변이어야 한다"고 말하는 순서를 자주 보는데, 인과가 거꾸로다. **불변이 먼저이고 pool이 나중이다.**

같은 내용의 문자열을 여러 곳이 하나의 객체로 공유한다고 해 보자. 만약 String이 가변이라면 어떤 일이 벌어지는가.

```
결제 모듈 ──┐
            ├──► ┌──────────┐
정산 모듈 ──┤     │ "KRW"    │   ← 세 모듈이 같은 객체를 본다
            │     └──────────┘
로깅 모듈 ──┘

가변이었다면: 로깅 모듈이 실수로 이 객체를 "USD"로 바꾸는 순간
             결제 모듈과 정산 모듈의 통화가 함께 바뀐다.
             누가 언제 바꿨는지 추적조차 불가능하다.
```

**공유를 하려면 "아무도 못 바꾼다"는 보장이 먼저 있어야 한다.** 그 보장이 있기 때문에 JVM은 마음 놓고 이 최적화를 할 수 있다 — 소스 코드에 등장하는 문자열 리터럴을 **같은 내용이면 하나만 만들어 두고 모두가 재사용**하게 하는 것이다. 이 저장소가 **String pool(문자열 상수 풀)**이다.

`"KRW"`라는 리터럴이 코드 수백 군데에 있어도 실제 String 객체는 하나뿐이고, 전부 그 하나의 주소를 참조한다. 문자열 리터럴은 애플리케이션이 다루는 객체 중 압도적으로 개수가 많으므로 절약 효과가 크다.

```java
String a = "hello";
String b = "hello";
System.out.println(a == b);        // 출력: true

String c = new String("hello");
System.out.println(a == c);        // 출력: false
System.out.println(a.equals(c));   // 출력: true

System.out.println(c.intern() == a);  // 출력: true
```

이 코드가 왜 그렇게 나오는지 한 줄씩 짚자.

`a == b`가 `true`인 것은 **두 변수가 pool에 있는 같은 하나의 객체를 가리키기 때문**이다. `==`는 값이 같은지 묻는 연산자가 아니라 **"두 참조가 같은 객체를 가리키는가"를 묻는 참조 비교**다(자세한 것은 `30-integer-cache-boxed-equality.md`). 여기서 `true`가 나온 것은 값이 같아서가 아니라 진짜로 같은 객체여서다.

`new String("hello")`는 그 pool 공유를 **일부러 건너뛰고** 힙에 새 객체를 하나 더 만든다. 그래서 `a == c`가 `false`다. 내용은 같은데 다른 객체인 것이다. **문자열 값 비교에 `==`를 쓰면 안 되는 이유**가 정확히 여기 있다 — 리터럴끼리는 우연히 맞고, 런타임에 만들어진 문자열(HTTP 파라미터, DB 조회 결과, `substring` 결과)이 끼는 순간 틀린다. 그리고 이 버그는 로컬 테스트에서는 잘 통과한다. 테스트 코드에 쓰는 문자열은 대부분 리터럴이기 때문이다.

`intern()`은 **"이 문자열과 같은 내용의 pool 대표 객체를 달라"**는 메서드다. pool에 없으면 넣고 그 객체를 준다. 그래서 `c.intern() == a`가 `true`다. 실무에서 직접 부를 일은 드물지만, 같은 값이 수백만 번 반복되는 대용량 파싱에서 메모리를 줄이려고 쓰는 경우가 있다.

**pool이 어디에 있는지도 알아두면 좋다.** Java 6까지는 PermGen(힙 안에 미리 잘라둔 고정 구획)에 있어서, 문자열을 과하게 `intern()`하면 `OutOfMemoryError: PermGen space`가 났다. **Java 7부터 String pool은 일반 힙으로 옮겨졌다.** 그래서 지금은 pool도 GC 대상이고, 아무도 참조하지 않게 된 interned 문자열은 회수된다. Metaspace에는 클래스의 구조 정보만 있고 값을 담는 것들은 전부 힙에 있다는 큰 그림과 일치한다(`01-jvm-memory-structure.md`).

### 2-2. 스레드 안전 — 동기화가 필요 없는 이유

동시성 버그의 근원을 한 문장으로 줄이면 **"공유된 가변 상태(shared mutable state)"**다. 여러 스레드가 같은 데이터를 보는데(공유) 그 데이터가 바뀔 수 있으면(가변), 읽는 도중에 바뀌거나 두 스레드의 수정이 서로를 덮어쓰는 사고가 생긴다.

불변은 이 조합에서 **'가변'을 제거한다.** 공유는 그대로 두되 바뀔 수가 없게 만드는 것이다. 그러면 경쟁 상태(race condition)가 성립할 여지 자체가 사라진다 — 아무리 여러 스레드가 동시에 읽어도 읽는 값은 언제나 같다.

그래서 String에는 락도, `volatile`도, 방어적 복사도 필요 없다. **문제를 해결한 게 아니라 문제가 생길 조건을 없앤 것**이고, 이것이 불변 설계의 가장 큰 값이다.

이 대비는 `22-static-simpledateformat-shared-mutable-state.md`에서 정확히 반대 사례로 나온다. `SimpleDateFormat`은 내부에 파싱 중간 상태를 들고 있는 **가변** 객체인데 `static` 필드에 담아 **공유**하는 순간, 두 요청이 서로의 중간 계산을 덮어써 엉뚱한 날짜가 나온다. 그 문제의 해법이 `DateTimeFormatter` — 불변 타입이다.

### 2-3. hashCode 캐싱 — 불변이 아니면 불가능한 최적화

HashMap의 키로 가장 많이 쓰이는 타입이 String이다. 그리고 HashMap은 조회할 때마다 키의 `hashCode()`를 호출한다(`03-equals-hashcode-contract.md`의 2단계 조회 중 1단계 — 해시값으로 버킷을 고르는 단계).

여기서 문제가 하나 보인다. **문자열의 해시는 글자를 전부 훑어야 계산된다.** 길이 100인 URL을 키로 쓰면 조회 한 번마다 100글자를 다 도는 셈이다. 그런데 String은 이 비용을 한 번만 낸다. **최초로 계산한 해시값을 `hash` 필드에 저장해 두고 다음부터는 그 값을 그냥 돌려주기 때문이다.**

계산 자체를 한 번 따라가 보자. String의 해시 함수는 각 글자의 코드값에 31을 곱해가며 누적하는 방식이다.

```
"hello"의 각 글자 코드값: h=104, e=101, l=108, l=108, o=111

1단계  h = 0
2단계  h = 31 * 0      + 104 = 104
3단계  h = 31 * 104    + 101 = 3325
4단계  h = 31 * 3325   + 108 = 103183
5단계  h = 31 * 103183 + 108 = 3198781
6단계  h = 31 * 3198781+ 111 = 99162322
```

```java
System.out.println("hello".hashCode());   // 출력: 99162322
```

직접 31 기반으로 손계산한 값과 `hashCode()`의 반환값이 정확히 일치한다.

이제 핵심 질문이다. **왜 이 캐싱이 불변일 때만 가능한가?**

내용이 바뀔 수 있는 객체라면, 저장해 둔 해시값은 내용이 바뀌는 순간 **틀린 값**이 된다. 그래서 가변 객체는 매번 다시 계산할 수밖에 없다. 게다가 문제는 성능만이 아니다 — 그런 객체를 HashMap 키로 넣은 뒤 내용을 바꾸면, 넣을 때의 해시로 정해진 버킷과 찾을 때의 해시가 가리키는 버킷이 달라져 **분명히 넣었는데 영영 못 찾는 유령 항목**이 된다. String은 애초에 내용이 안 바뀌므로 이 사고가 구조적으로 불가능하다.

`hash` 필드에 대해 두 가지를 덧붙이면 가산점이다. **(가산점 포인트)**

첫째, `hash` 필드는 앞의 필드 목록에서 봤듯 `private int hash`로 **`final`이 아니다.** 최초 호출 시점에 계산해 채우는 **지연 초기화(lazy initialization)** 방식이기 때문이다. 여러 스레드가 동시에 처음 `hashCode()`를 부르면 각자 계산해 각자 필드에 쓸 수 있는데, 이것이 문제가 안 되는 이유는 **어차피 계산 결과가 항상 같은 값이라 누가 써도 결과가 동일하기 때문**이다. 그래서 동기화 없이 둔다. 이런 형태를 무해한 경쟁, 즉 benign data race라고 부른다.

둘째, 필드 목록에 `hashIsZero`라는 `boolean`이 하나 더 있다. `hash`의 초기값이 0인데 **실제 해시가 0인 문자열도 존재하기 때문에**(빈 문자열이 그렇다) "아직 계산 안 함"과 "계산했더니 0"을 구분할 방법이 필요하다. 그 구분자가 이 필드다. 없으면 해시가 0인 문자열은 조회마다 계산을 반복하게 된다.

### 2-4. 보안 — 검증한 값이 사용 시점까지 그대로임을 보장한다

파일 경로, DB 접속 URL, 클래스 이름, 리다이렉트 대상 주소는 전부 String으로 오간다. 이런 값은 대개 **"검증하고 → 쓴다"**는 두 단계를 거친다.

```java
public void serve(String path) {
    if (!path.startsWith("/public/")) {   // ① 검증: 공개 디렉토리인가
        throw new AccessDeniedException();
    }
    // ... 다른 처리 ...
    Files.readAllBytes(Path.of(path));    // ② 사용: 실제로 파일을 연다
}
```

**만약 String이 가변이었다면 ①과 ② 사이가 공격 창구가 된다.** 검증을 통과한 직후 다른 스레드가 그 String 객체의 내용을 `/etc/passwd`로 바꿔 놓으면, ②는 검증받지 않은 경로를 연다. 검증한 값과 사용한 값이 다른 것이다.

이런 유형의 취약점을 **TOCTOU(Time-Of-Check to Time-Of-Use, 검사 시점과 사용 시점의 틈)**라고 부른다. 이름 그대로 "확인한 시점"과 "실제로 쓰는 시점" 사이에 대상이 바뀌어 버리는 공격이다.

String이 불변이므로 이 틈이 존재하지 않는다. **①에서 검사한 그 객체는 ②에서도 글자 하나 다르지 않다.** 그래서 자바 표준 라이브러리와 보안 매니저는 문자열 인자를 방어적 복사 없이 그대로 신뢰할 수 있다.

반대 방향의 예외도 알아두면 좋다. **(가산점 포인트)** 비밀번호는 오히려 `String`이 아니라 `char[]`로 다루라는 권고가 있다. 이유가 정확히 불변 때문이다 — String은 내용을 덮어쓸 수 없으므로, 다 쓰고 나서도 GC가 회수할 때까지 평문 비밀번호가 힙에 남는다. 그 사이에 힙 덤프를 뜨면 그대로 노출된다. `char[]`는 다 쓴 직후 `Arrays.fill(pw, '\0')`으로 지울 수 있다. `JPasswordField.getPassword()`나 `Console.readPassword()`가 `char[]`를 반환하는 것이 그래서다. **불변이 항상 이득인 것은 아니고, "지울 수 있어야 하는 값"에는 오히려 단점이 된다**는 것까지 말하면 도구의 양면을 보는 사람으로 읽힌다.

## 3. 불변의 비용 — 루프 누적이 O(n²)인 이유와 StringBuilder

### 3-1. 왜 O(n²)인가 — 복사량을 실제로 더해 본다

불변의 대가는 명확하다. **수정처럼 보이는 모든 연산이 새 객체를 만든다.** 대부분의 상황에서는 문제가 안 되는데, 딱 한 곳에서 심각해진다. 루프 안에서 문자열을 누적할 때다.

```java
String csv = "";
for (int i = 0; i < n; i++) {
    csv += "x";        // 매 회전마다 무슨 일이 일어나는가?
}
```

`csv += "x"`는 "csv 뒤에 x를 덧붙인다"처럼 읽히지만, 불변이므로 그런 일은 일어날 수 없다. 실제로 일어나는 일은 **지금까지의 csv 전체를 새 배열로 복사하고 그 뒤에 "x" 한 글자를 붙여 새 String을 만든 뒤, 변수 csv가 그 새 객체를 가리키게 하는 것**이다. 이전 객체는 버려져 GC 대상이 된다.

그러면 회전마다 몇 글자를 복사하는지 세어 보자.

| 회전 | 시작 시점의 길이 | 이번에 복사하는 글자 수 | 버려지는 객체 |
|---|---|---|---|
| 1회전 | 0 | 0 → 결과 길이 1 | 이전 "" |
| 2회전 | 1 | 1 | 길이 1짜리 |
| 3회전 | 2 | 2 | 길이 2짜리 |
| 4회전 | 3 | 3 | 길이 3짜리 |
| ... | ... | ... | ... |
| n회전 | n-1 | n-1 | 길이 n-1짜리 |

총 복사량을 더하면 이렇게 된다.

```
0 + 1 + 2 + 3 + ... + (n-1)  =  n(n-1)/2

n =    100  ->        4,950 글자
n =  1,000  ->      499,500 글자
n = 10,000  ->   49,995,000 글자
n = 50,000  -> 1,249,975,000 글자   (약 12.5억 글자)
```

**n이 10배가 되면 복사량은 100배가 된다.** 이것이 O(n²)라는 말의 실체다. 그리고 복사만 문제가 아니다 — 버려진 중간 객체가 n개 생기므로 GC에도 그만큼 압력이 간다.

실제로 재 보면 이렇다. 위 루프와 아래의 StringBuilder 버전을 같은 JVM(OpenJDK 21) 안에서 `n = 50000`으로 각각 한 번씩 돌린 결과다.

```
+= 누적        : 124 ms
StringBuilder :   0 ms   (밀리초 단위로는 측정되지 않는 수준)
```

이 수치 자체는 머신과 JIT 상태에 따라 달라지므로 절대값을 외울 이유는 없다. 중요한 것은 **자릿수가 다르다**는 것이고, n이 커질수록 격차가 제곱으로 벌어진다는 것이다.

### 3-2. StringBuilder — 내부 배열을 늘려가며 재사용한다

StringBuilder는 **불변 원칙을 의도적으로 버린 가변 문자 버퍼**다. 내부에 `char[]`(정확히는 `byte[]`) 하나를 들고 있고, `append()`는 새 객체를 만드는 대신 **그 배열의 뒤쪽 빈 자리에 글자를 써 넣는다.** 배열이 꽉 차면 더 큰 배열을 새로 만들어 옮기고, 이후에는 다시 그 배열을 계속 쓴다.

```java
// Before: 루프 안 += — 회전마다 지금까지의 전체를 복사한다
String csv = "";
for (Order o : orders) {          // 주문 1만 건이면
    csv += o.getId() + ",";       // 약 5천만 글자 복사 + 버려진 객체 1만 개
}

// After: StringBuilder — 하나의 버퍼에 이어 붙이고 마지막에 한 번만 String을 만든다
StringBuilder sb = new StringBuilder();
for (Order o : orders) {
    sb.append(o.getId()).append(',');   // 버퍼 끝에 쓰기만 한다. 복사 없음
}
String csv = sb.toString();             // 여기서 딱 한 번 String 객체가 생긴다
```

배열이 늘어나는 방식도 확인해 보면 이해가 굳는다.

```java
StringBuilder sb = new StringBuilder();
System.out.println(sb.capacity());              // 출력: 16   (기본 용량)

sb.append("0123456789ABCDEF");                  // 딱 16글자
System.out.println(sb.capacity());              // 출력: 16   (아직 안 넘침)

sb.append("G");                                 // 17번째 글자
System.out.println(sb.capacity());              // 출력: 34   (16*2+2로 확장)

System.out.println(new StringBuilder("abc").capacity());  // 출력: 19  (16 + 초기 문자열 길이)
```

확장이 일어날 때는 기존 내용을 새 배열로 옮기는 복사가 발생한다. 다만 **용량을 두 배씩 늘리므로 확장 횟수가 log 수준으로 억제되고, 총 복사량도 최종 길이에 비례하는 선에서 끝난다.** `+=` 누적이 매 회전마다 복사하는 것과 근본적으로 다른 지점이 여기다.

그래서 **최종 크기를 대충이라도 알면 초기 용량을 주는 것이 이득이다.** **(가산점 포인트)** `new StringBuilder(orders.size() * 20)`처럼 넉넉히 잡아 두면 확장 복사를 아예 없앨 수 있다. 다만 이건 수십만 건을 다루는 배치 같은 곳에서 의미 있는 최적화이고, 일반 요청 처리에서는 기본값으로 충분하다.

### 3-3. 한 표현식 안의 `+`는 그냥 써라 — 컴파일러가 처리한다

여기서 자주 나오는 과잉 반응이 있다. "문자열 연결은 무조건 StringBuilder로 바꿔야 한다"는 것인데, **틀렸다.** 한 표현식 안에서 끝나는 `+` 연결은 컴파일러가 이미 효율적인 코드로 바꿔 준다.

```java
String msg = "orderId=" + orderId + ", amount=" + amount;   // 이대로 두면 된다
```

실제로 바이트코드를 확인해 보면 이렇다.

```java
String one(String a, int b) { return "id=" + a + "-" + b; }
```

```
// javap -c 로 뽑은 결과 (OpenJDK 21)
0: aload_1
1: iload_2
2: invokedynamic #7,  0   // InvokeDynamic #0:makeConcatWithConstants:(Ljava/lang/String;I)Ljava/lang/String;
7: areturn
```

`makeConcatWithConstants`라는 이름이 보인다. **Java 9부터 문자열 연결은 `invokedynamic`이라는 바이트코드 명령으로 컴파일되고, 실행 시점에 JVM(`StringConcatFactory`)이 그 연결에 가장 맞는 코드를 만들어 준다.** 전체 길이를 미리 계산해 딱 맞는 버퍼를 한 번 잡고 채우는 식이라, 손으로 StringBuilder를 쓰는 것보다 나을 때도 있다. Java 8까지는 컴파일러가 `StringBuilder` 체인으로 바꿔 넣었는데, 어느 쪽이든 **개발자가 손으로 고칠 이유가 없다**는 결론은 같다.

그러면 **왜 루프는 안 구해주는가?** 최적화의 단위가 **하나의 표현식**이기 때문이다. 루프 버전의 바이트코드를 보면 이유가 그대로 드러난다.

```java
String loop(List<String> xs) { String s = ""; for (String x : xs) s += x + ","; return s; }
```

```
// 루프 본문 안에서
33: invokedynamic #31,  0  // InvokeDynamic #1:makeConcatWithConstants:(...)Ljava/lang/String;
38: astore_2               // 결과를 s에 다시 대입
39: goto  10               // 다음 회전으로
```

**`makeConcatWithConstants` 호출이 루프 안에 들어 있다.** 즉 회전마다 "지금까지의 s + 새 조각"을 처음부터 다시 만드는 일이 그대로 반복된다. 컴파일러는 한 회전 안의 `s + x + ","`를 효율적으로 만들어 줄 뿐, **회전과 회전 사이에 버퍼를 이어 쓰는 판단까지는 하지 않는다.** 그건 프로그램의 의도를 바꾸는 변형이기 때문이다.

정리하면 판단 기준은 이렇게 단순하다.

- **한 표현식 안에서 끝나는 연결** — 그냥 `+`. 가독성을 희생할 이유가 없다.
- **루프나 조건 분기를 넘나들며 누적** — StringBuilder. 컴파일러가 못 구해주는 유일한 구간이다.

### 3-4. StringBuffer와의 차이 — 왜 기본값이 StringBuilder인가

StringBuffer와 StringBuilder는 **API가 사실상 같은 가변 문자 버퍼**다. 차이는 딱 하나, **동기화 여부**다.

```java
// 리플렉션으로 확인한 결과
StringBuffer.class.getMethod("append", String.class)   // synchronized: true
StringBuilder.class.getMethod("append", String.class)  // synchronized: false
```

StringBuffer는 모든 메서드에 `synchronized`가 붙어 있어 한 번에 한 스레드만 들어갈 수 있고, StringBuilder는 그런 보호가 없다. 역사적으로 StringBuffer가 먼저(Java 1.0) 있었고, "대부분의 문자열 조립은 한 메서드 안의 지역 변수로 끝나 스레드 간 공유가 아예 없는데 왜 락 비용을 내야 하나"라는 반성에서 Java 5에 StringBuilder가 추가됐다.

그래서 **기본값은 StringBuilder다.** 공유되지 않는 객체에 락을 거는 것은 순수한 낭비다.

그러면 여러 스레드가 하나의 버퍼에 함께 써야 할 때는 StringBuffer인가? **그때는 StringBuffer가 아니라 설계를 다시 봐야 한다.** 이유는 StringBuffer가 보장하는 것이 "각 `append` 호출이 원자적"이라는 것뿐이기 때문이다. 여러 스레드가 번갈아 append하면 각 호출은 안전하게 처리되지만 **호출 순서는 뒤죽박죽**이 되어 결과 문자열이 의미를 잃는다. 동기화는 자료 구조가 깨지는 것을 막을 뿐 순서를 정해주지 않는다. 스레드마다 자기 StringBuilder로 조립한 뒤 마지막에 합치는 쪽이 옳다.

## 4. 꼬리질문 대비 포인트

### "`new String("hello")`과 리터럴 `"hello"`의 차이는? `intern()`은 언제 쓰나요?"

리터럴은 String pool에 있는 공유 객체를 재사용하고, `new String(...)`은 pool을 **일부러 건너뛰고** 힙에 새 객체를 하나 더 만든다. 그래서 리터럴끼리는 `==`가 `true`인데 `new`가 끼면 `false`가 된다.

여기서 반드시 이어 붙여야 할 결론은 **"그러니까 문자열 값 비교는 항상 `equals()`"**라는 것이다. `==`는 애초에 값을 비교하는 연산이 아니라 "같은 객체인가"를 묻는 참조 비교이고, 리터럴에서 우연히 맞아떨어질 뿐이다. 그리고 이 우연은 테스트 코드에서 특히 잘 맞는다 — 테스트에 쓰는 문자열은 대부분 리터럴이기 때문이다. HTTP 파라미터나 DB 조회 결과처럼 런타임에 만들어진 문자열이 들어오는 운영 환경에서만 틀리는 버그가 된다.

`intern()`은 "이 문자열과 같은 내용의 pool 대표 객체를 달라"는 메서드다. 실무에서 직접 쓸 일은 드물고, 쓴다면 **같은 값이 수백만 번 반복되는 대용량 파싱에서 중복 객체를 줄이려는 목적**이다. 다만 pool도 결국 해시 테이블이라 항목이 폭증하면 조회가 느려지므로 무턱대고 쓸 것은 아니다. 이 질문은 대개 "pool의 존재를 아는가"를 확인하는 것에 가깝다.

### "String이 불변인데 `s += "x"`는 왜 되나요?"

**변수가 다른 새 객체를 가리키도록 참조가 바뀐 것**이지, 원래 객체의 내용이 바뀐 것이 아니다. `s += "x"`는 "지금까지의 s와 x를 합친 새 String을 만들어, 그 주소를 s에 다시 대입하라"로 번역된다. 원래 객체는 손대지 않은 채 그대로 있다가 아무도 안 가리키게 되면 GC 대상이 된다.

**"참조의 재할당"과 "객체 상태의 변경"을 구분하는지** 보는 질문이다. 그래서 `final String s`는 재할당만 막을 뿐이고, 불변은 객체 쪽의 성질이라 서로 다른 층위라는 것까지 말하면 정리가 깔끔하다.

### "불변이면 매번 객체가 생기는데 성능이 더 나쁜 것 아닌가요?"

**반복 수정 지점에서는 맞다.** 루프 누적이 O(n²)가 되는 것이 그 증거이고, 그래서 StringBuilder가 존재한다.

하지만 전체 그림에서는 반대 이득이 훨씬 크다. 공유가 안전해져 같은 리터럴이 하나로 합쳐지고(pool), 방어적 복사가 필요 없어지고, 동기화 비용이 사라지고, 해시를 한 번만 계산한다. **"수정마다 새 객체"라는 비용은 눈에 잘 보이고, 그 대가로 사라진 비용들은 눈에 안 보일 뿐이다.**

객체 생성 자체가 생각보다 싸다는 점도 덧붙일 만하다. JVM은 스레드마다 Eden의 한 조각을 미리 떼어 주고(TLAB) 그 안에서는 포인터만 앞으로 밀어 할당하므로, 짧게 살다 죽는 객체는 생성도 회수도 저렴하다(`01-jvm-memory-structure.md`).

올바른 프레임은 이것이다. **불변으로 안전을 기본값으로 깔고, 측정으로 병목이 확인된 지점만 가변 버퍼로 푼다.**

### "비밀번호는 String에 담지 말라는 말은 무슨 뜻인가요?" (가산점 포인트)

불변의 이면이 드러나는 사례라 짚을 값이 있다.

String은 내용을 덮어쓸 수 없으므로 **다 쓰고 난 뒤에도 평문 비밀번호가 힙에 그대로 남는다.** 참조를 끊어도 GC가 실제로 회수하기 전까지는 메모리에 존재하고, 그 사이에 힙 덤프를 뜨거나 코어 덤프가 남으면 그대로 노출된다. 게다가 그 값이 리터럴이거나 `intern()`을 거쳤다면 pool에 남아 애플리케이션 수명 내내 살아 있을 수도 있다.

`char[]`는 다 쓴 직후 `Arrays.fill(pw, '\0')`으로 **직접 지울 수 있다.** 그래서 `Console.readPassword()`나 `JPasswordField.getPassword()`가 `String`이 아니라 `char[]`를 반환한다.

여기서 말할 수 있어야 하는 것은 **"불변이 항상 이득은 아니다"**라는 판단이다. 불변은 "아무도 못 바꾼다"는 보장을 주는데, 그 보장은 "내가 지우고 싶어도 못 지운다"와 같은 말이다. 지워야 하는 값에는 그것이 단점이 된다.

### "String에서 배운 불변을 도메인 객체 설계에 어떻게 적용하나요?" (시니어 변별 포인트)

Money, 기간, 좌표 같은 **값 객체(VO, Value Object)** — 식별자가 아니라 값 자체로 의미를 갖는 객체 — 를 String과 똑같은 방식으로 만든다. 1-2의 세 자물쇠를 그대로 옮기면 된다.

- 모든 필드 `private final`
- setter 없음. 수정은 새 객체를 반환하는 메서드로(`money.plus(other)`)
- 클래스 `final` (또는 `record` — 필드 final과 접근자 생성이 기본으로 딸려 온다)
- 가변 객체를 필드로 받거나 반환할 때는 방어적 복사(`21-defensive-copy-collection-exposure.md`)

효과는 String이 이미 증명한 그대로다. 스레드 간 공유가 안전하고, 해시 컬렉션의 키로 안전하고, "이 값을 누가 언제 바꿨나"를 추적할 일 자체가 없어진다. **동시성 버그를 잡는 게 아니라 생길 자리를 없애는 방식**이다.

트레이드오프까지 말할 수 있어야 답이 완성된다.

첫째, **수정이 아주 잦은 대형 객체**는 매 수정마다 전체를 복제하는 비용이 부담이 될 수 있다. 이때는 String과 StringBuilder의 관계를 그대로 흉내 내면 된다 — 불변 타입을 기본으로 두고, 조립 구간에만 가변 빌더를 붙이는 것이다.

둘째, **JPA 엔티티처럼 프레임워크가 상태 변경을 전제하는 곳**에는 그대로 적용하기 어렵다. 엔티티는 기본 생성자와 필드 변경을 요구하고, 애초에 식별자로 동일성을 판단하는 객체라 값 객체와 성격이 다르다.

그래서 실무의 답은 전부 불변으로 만드는 것이 아니라 **경계를 나누는 것**이다. "엔티티는 가변을 허용하되, 그 안에 담기는 값들(금액, 기간, 주소)은 불변 VO로 만들고 `@Embeddable`로 묻는다." 이렇게 하면 상태 변경 지점이 엔티티의 의미 있는 메서드 몇 개로 좁혀지고, 나머지는 전부 불변의 이득을 받는다. **불변을 기본값으로 두되 어디까지 밀어붙일지 선을 그을 줄 아는 것**이 이 질문이 확인하려는 감각이다.

## 한 줄 요약

불변이란 생성 이후 상태가 바뀌지 않는다는 뜻이고 String은 `private final` 배열 은닉·배열 미노출·`final class`라는 세 자물쇠로 그것을 지키는데, 여기서 안전한 공유(그 결과가 String pool, Java 7부터 힙)·동기화 없는 스레드 안전·hashCode 캐싱·TOCTOU 회피가 전부 파생된다 — 대가인 "수정마다 새 객체"는 루프 누적에서 총 복사량 n(n-1)/2의 O(n²)로 나타나므로 그 지점만 StringBuilder라는 가변 버퍼로 지불하고, 한 표현식 안의 `+`는 컴파일러가 `invokedynamic`으로 처리하므로 손대지 않는다.
