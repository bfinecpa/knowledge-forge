# String 불변성과 StringBuilder — 불변이 공짜로 주는 것, 그리고 그 비용

> 핵심 관전 포인트: **String은 한 번 만들어지면 내용이 절대 바뀌지 않는
> 불변 객체다. 불변이기에 (1) String pool로 같은 리터럴을 안전하게 공유해
> 메모리를 아끼고, (2) 여러 스레드가 동기화 없이 공유해도 안전하며,
> (3) hashCode를 한 번 계산해 캐싱할 수 있어 HashMap 키로 최적이고,
> (4) 파일 경로·클래스명 같은 보안 민감 값이 검증 후 바뀔 수 없다.
> 비용은 "수정처럼 보이는 모든 연산이 새 객체 생성"이라는 것 —
> 그래서 루프 안에서 문자열을 누적할 때는 내부 버퍼를 고쳐 쓰는
> StringBuilder를 쓴다.**

---

## 0. 질문 + 의도

**질문**: "String이 불변(immutable)인 이유와 그로 인한 장점은 무엇인가요?
`StringBuilder`는 언제 쓰나요?"

**출제 의도**: 불변 객체가 왜 스레드 안전과 캐싱(String pool)을 공짜로
주는지 이해하는지를 본다. 이 감각이 있는 사람은 도메인 객체 설계에서도
불변을 기본값으로 두어 동시성 버그의 반을 원천 차단한다.

## 1. 불변이란 무엇이고, String은 어떻게 불변을 지키는가

불변(immutable) = **생성 이후 상태가 절대 바뀌지 않는다.**
"바꾸는 것처럼 보이는" 모든 메서드는 사실 **새 String을 만들어 반환**한다.

```java
String s = "hello";
s.toUpperCase();          // 흔한 실수: s는 그대로 "hello" — 반환값을 버렸다
String upper = s.toUpperCase();  // "HELLO"는 새 객체, s는 여전히 "hello"
```

String이 불변을 지키는 방법: 내부 문자 배열을 private으로 감추고 밖으로
노출하지 않으며, 그 배열을 교체하는 메서드가 없고, 클래스 자체가
final이라 **가변인 하위 클래스를 만들어 불변을 우회하는 것도 막는다**.
(이 3종 세트 — 상태 은닉 + 수정 메서드 없음 + 상속 봉쇄 — 는 그대로
불변 도메인 객체 설계의 교과서 패턴이다.)

## 2. 불변이 "공짜로" 주는 네 가지

### ① String pool — 안전한 공유와 메모리 절약

JVM은 같은 문자열 리터럴을 **pool이라는 저장소에 하나만 만들어 모두가
공유**하게 한다. 코드 곳곳의 `"KRW"` 리터럴이 전부 한 객체다.

이 공유가 가능한 전제가 불변이다 — 누군가 공유 객체를 바꿀 수 있다면,
A가 바꾼 내용이 B에게도 보이는 재앙이 된다. **불변이니까 마음 놓고
공유(캐싱)할 수 있다.** "원본은 그대로 두고 복사본에 쓴다"가 아니라
아예 쓸 수 없으니 복사조차 필요 없는 것이다.

```java
String a = "hello";
String b = "hello";
a == b;                      // true — pool의 같은 객체를 참조

String c = new String("hello");  // pool을 안 거치고 힙에 새 객체 강제 생성
a == c;                      // false — 그래서 문자열 비교는 항상 equals()
a.equals(c);                 // true
```

### ② 스레드 안전 — 동기화 없이 공유

상태가 안 바뀌므로 여러 스레드가 동시에 읽어도 경쟁 상태(race condition)
자체가 성립하지 않는다. 락도, `volatile`도, 방어적 복사도 필요 없다.
**동시성 버그의 근원은 "공유된 가변 상태"인데, 불변은 그중 '가변'을
제거해 문제를 원천 차단한다.**

### ③ hashCode 캐싱 — HashMap 키로 최적

내용이 안 바뀌므로 hashCode도 영원히 같다. String은 이를 이용해
**최초 계산한 해시값을 필드에 저장해두고 재사용**한다. HashMap 키로
문자열이 압도적으로 많이 쓰이는 실무에서 조회마다 해시 재계산을 아끼고,
"컬렉션에 넣은 뒤 키가 변해 못 찾는" 유령 항목 문제(equals/hashCode
문서 참고)도 구조적으로 불가능하다.

### ④ 보안 — 검증 후 변조 불가

파일 경로, 네트워크 주소, 클래스 이름, DB 접속 문자열은 전부 String으로
전달된다. 만약 String이 가변이라면 **보안 검증을 통과한 직후 다른
스레드가 값을 바꿔치기하는 공격**(검증 시점과 사용 시점의 틈)이
가능해진다. 불변이라 "검증한 그 값"이 사용 시점까지 보장된다.

## 3. 불변의 비용과 StringBuilder — 언제 쓰나

비용: 연결·수정마다 새 객체가 생긴다. 특히 **루프 안 `+=` 누적**은
매 회전마다 지금까지의 전체 내용을 새 객체로 복사하므로, n번 누적이
O(n²) 복사가 되고 버려진 중간 객체가 전부 GC 대상이 된다.

```java
// Before: 루프 안 += — 회전마다 전체 복사 + 쓰레기 객체 양산
String csv = "";
for (Order o : orders) {          // 주문 1만 건이면
    csv += o.getId() + ",";       // 1만 번의 "이전 내용 전체 복사"
}

// After: StringBuilder — 내부 가변 버퍼에 이어 붙이고 마지막에 한 번만 String 생성
StringBuilder sb = new StringBuilder();
for (Order o : orders) {
    sb.append(o.getId()).append(',');
}
String csv = sb.toString();
```

StringBuilder는 **내부에 가변 문자 버퍼를 두고 고쳐 쓰는** 클래스다.
즉 String의 불변 원칙을 버리는 대신 반복 수정 성능을 얻는, 명확한
트레이드오프 도구다. 쓰는 기준:

- **루프/조건 분기를 넘나들며 문자열을 누적할 때** — StringBuilder.
- **한 문장 안의 단순 `+` 연결** — 그냥 `+`. 컴파일러가 한 줄 연결을
  StringBuilder 사용 또는 그에 준하는 효율적 코드로 변환해주므로
  가독성을 희생할 이유가 없다. 컴파일러 최적화는 **한 문장 단위**라서
  루프를 넘나드는 누적까지는 못 구해준다 — 그래서 루프에서만 직접 쓴다.
- 예상 크기를 안다면 `new StringBuilder(예상크기)`로 초기 용량을 주면
  버퍼 확장 복사를 줄인다. (가산점 포인트)

## 4. 꼬리질문 대비 포인트

### "`new String("hello")`과 리터럴 `"hello"`의 차이는?"

리터럴은 pool의 공유 객체를 재사용하고, `new`는 pool과 별개로 힙에
새 객체를 강제로 만든다. 그래서 `==` 비교가 리터럴끼리는 true,
new가 끼면 false — **문자열 값 비교는 항상 `equals()`** 라는 원칙의
근거다. `intern()`을 호출하면 pool의 대표 객체를 얻을 수 있지만,
실무에서 직접 쓸 일은 드물고 pool의 존재를 아는지 확인하는 질문에
가깝다.

### "StringBuffer와 StringBuilder의 차이는?"

둘은 같은 API의 가변 문자열 버퍼인데, StringBuffer는 모든 메서드가
`synchronized`로 동기화되어 있고 StringBuilder는 아니다. 문자열 조립은
거의 항상 한 메서드 안의 지역 변수로 끝나 스레드 간 공유가 없으므로,
**동기화 비용만 내는 StringBuffer 대신 StringBuilder가 기본값**이다.
여러 스레드가 하나의 버퍼에 동시에 쓰는 설계라면 StringBuffer보다
설계 자체를 다시 보는 게 맞다(호출 순서가 섞이는 문제는 동기화로
해결되지 않는다).

### "String이 불변인데 `s += "x"`는 왜 되나요?"

변수 `s`가 **다른 새 객체를 가리키도록 참조가 바뀐 것**이지, 원래
객체의 내용이 바뀐 게 아니다. "참조의 재할당"과 "객체 상태의 변경"을
구분하는지 보는 질문 — `final String s`는 재할당만 막고,
불변은 객체 쪽의 성질이다.

### "불변이면 매번 객체가 생기는데 성능이 더 나쁜 것 아닌가요?"

수정이 잦은 지점(루프 누적)에서는 맞고, 그래서 StringBuilder가 있다.
하지만 전체 그림에서는 반대 이득이 크다 — 공유·캐싱이 안전해져
같은 값을 재사용하고(pool), 방어적 복사가 필요 없고, 동기화 비용이
사라진다. **"불변으로 안전을 기본값으로 깔고, 병목으로 측정된 지점만
가변 버퍼로 푼다"** 가 올바른 프레임이다.

### "String에서 배운 불변을 도메인 객체 설계에 어떻게 적용하나요?" (시니어 변별 포인트)

Money, 좌표, 기간 같은 값 객체(VO)를 String과 같은 방식으로 만든다 —
모든 필드 final, setter 없음, 수정은 새 객체 반환
(`money.plus(other)`), 클래스 final(또는 record 사용). 효과는 String이
증명한 그대로다: 스레드 간 공유 안전, 해시 컬렉션 키로 안전, "누가
언제 바꿨나" 추적 자체가 불필요. 트레이드오프도 말할 수 있어야 한다 —
수정 빈도가 매우 높은 대형 객체는 생성 비용이 부담이 될 수 있고,
JPA 엔티티처럼 프레임워크가 상태 변경을 전제하는 곳에는 그대로 적용이
어려워 **"엔티티는 가변을 허용하되 내부의 값들은 불변 VO로"** 처럼
경계를 나눈다. 이 판단이 rationale이 말하는 "불변을 기본값으로 두는
감각"이다.

---

## 한 줄 요약

String의 불변성은 공유(pool)·스레드 안전·해시 캐싱·보안을 공짜로 주는
설계 결정이고, 그 비용인 "수정마다 새 객체"는 루프 누적 같은 반복 수정
지점에서만 StringBuilder라는 가변 버퍼로 지불한다 — 그리고 이 원칙은
그대로 도메인 객체 설계의 기본값이 된다.
