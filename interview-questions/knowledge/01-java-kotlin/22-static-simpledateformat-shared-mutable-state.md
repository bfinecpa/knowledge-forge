# static SimpleDateFormat과 공유 가변 상태 — 함정을 "목록"이 아니라 "유형"으로 찾기

> 핵심 관전 포인트: **`SimpleDateFormat`이 스레드 안전하지 않은 것은 우연이 아니라 구현 사실이다 — 내부에 `Calendar` 필드를 하나 두고 `format()`/`parse()`가 호출될 때마다 그 하나의 Calendar에 중간 결과를 쌓았다가 읽는 구조다. static으로 공유하면 톰캣의 동시 요청 스레드들이 그 Calendar를 서로 덮어써서, 예외 없이 남의 날짜가 응답에 실리거나 간헐적으로 `NumberFormatException`이 튄다. 예외가 항상 나는 게 아니라 가끔만 난다는 것이 이 버그를 무섭게 만든다 — 단일 스레드 테스트는 전부 통과하고, 운영에서도 에러율 그래프에 안 잡히며, 조용히 틀린 데이터만 쌓인다. 해법은 불변이라 공유해도 안전한 `java.time.DateTimeFormatter`로 교체하는 것이 1순위다. 그리고 이 문서의 진짜 주제는 `SimpleDateFormat`이 아니라 "static 필드에 가변 상태를 두는 것" 일반이다 — 스프링 빈은 싱글톤이라 그 인스턴스 필드도 사실상 static과 같은 공유이므로, 컨트롤러·서비스 빈에 요청 처리 중간 상태를 필드로 두면 정확히 같은 사고가 난다.**

---

## 0. 질문 + 의도

**질문**: "AI가 생성한 코드에서 `SimpleDateFormat`을 static 필드로 공유하고 있습니다. 무엇이 문제이고, 같은 유형(공유 가변 상태)의 함정을 코드베이스 어디에서 더 찾아보겠습니까?"

**출제 의도**: 스레드 안전하지 않은 객체의 공유는 테스트를 전부 통과하고 동시 요청에서만 값이 섞이는 유형이라, 리뷰어의 머릿속 모델만이 방어선이다. 한 사례를 같은 패턴(가변 static, 싱글턴 빈의 상태 필드)으로 일반화해 찾는지 — 함정을 "목록"이 아니라 "유형"으로 아는지, AI가 생성한 코드를 검증할 수 있는 사람인지를 본다.

## 1. 무엇이 문제인가 — 내부 Calendar에 중간 결과를 쌓기 때문이다

### 1-1. 전제 지식 — 내 코드는 여러 스레드가 동시에 실행한다

컨트롤러와 서비스를 짤 때 대개 의식하지 않는 사실부터 깔아야 한다. **톰캣은 요청마다 스레드를 새로 만들지 않는다.** 애플리케이션이 뜰 때 워커 스레드를 미리 만들어 풀에 담아두고, 요청이 오면 하나를 빌려주고, 응답이 끝나면 죽이지 않고 풀로 되돌려 다음 요청에 다시 빌려준다. 스프링 부트의 기본 최대 워커 수는 200개다.

그러니까 **같은 메서드를 최대 200개 스레드가 동시에 실행하고 있다.** 그런데도 평소에 동시성을 걱정하지 않는 이유는, 지역 변수와 파라미터가 **스레드마다 따로 있는 스택**에 올라가기 때문이다. 스레드 A의 지역 변수와 스레드 B의 지역 변수는 애초에 다른 메모리다. 섞일 수가 없다.

**스택 바깥에 있는 것만 공유된다.** `static` 필드는 클래스에 하나만 존재하므로 모든 스레드가 같은 것을 본다. 그래서 이 질문의 코드는 이렇게 읽어야 한다.

```java
// AI가 자주 생성하는 전형적 패턴 (오래된 코드에서 흔했던 관용구다)
public class DateUtils {
    private static final SimpleDateFormat SDF =
            new SimpleDateFormat("yyyy-MM-dd HH:mm:ss");

    public static String format(Date date) {
        // 이 SDF는 톰캣 워커 200개가 '같은 객체'를 동시에 두드린다
        return SDF.format(date);
    }
}
```

### 1-2. `static final`이 안전해 보이는 착각 — final은 참조만 고정한다

`static final`이라 상수처럼 보이고, 상수는 안전하다고 느낀다. 여기가 첫 번째 오해다.

**`final`은 "이 변수에 다른 객체를 다시 대입할 수 없다"는 뜻일 뿐, "이 객체의 내용이 바뀌지 않는다"는 뜻이 아니다.** 참조를 고정할 뿐 내용물을 얼리지 않는다.

```java
private static final List<String> NAMES = new ArrayList<>();

NAMES = new ArrayList<>();   // 컴파일 에러 — final이 막는다
NAMES.add("alice");          // 통과 — 내용물은 얼마든지 바꿀 수 있다
```

`SDF`도 마찬가지다. `SDF = new SimpleDateFormat(...)`으로 갈아 끼우지는 못하지만, **그 객체 안의 상태는 호출될 때마다 바뀐다.** 그리고 다음 절에서 볼 것처럼, `SimpleDateFormat`은 바로 그 "호출될 때마다 안이 바뀌는" 방식으로 동작한다.

### 1-3. SimpleDateFormat의 내부 — 왜 스레드 안전하지 않은가

"스레드 안전하지 않다"는 말을 외우는 것과 **왜 그런지 구현으로 아는 것**은 다르다. 후자여야 처음 보는 클래스를 만났을 때도 판단할 수 있다.

`SimpleDateFormat`(정확히는 부모인 `DateFormat`)은 인스턴스 필드로 **`Calendar calendar` 하나**를 들고 있다. 그리고 `format()`과 `parse()`는 이 하나의 Calendar를 **작업대(scratch space)로 쓴다.** 결과를 바로 만들어 반환하는 게 아니라, 중간 결과를 이 작업대에 쌓았다가 다시 읽어서 최종 결과를 만든다.

`format(Date)`의 동작은 두 단계다.

```
① calendar.setTime(date)          — 작업대에 날짜를 올린다
② calendar에서 연·월·일·시·분·초를 하나씩 읽어 패턴대로 문자열 조립
```

`parse(String)`은 방향만 반대다.

```
① 문자열을 훑어 연=2026, 월=1, 일=15 같은 조각들을 얻는다
② calendar를 clear()로 비우고 그 조각들을 하나씩 써넣는다
③ calendar.getTime()으로 최종 Date를 꺼낸다
```

두 경우 모두 **"쓰고 → 읽는다"는 2단계**이고, 그 사이에 상태가 작업대에 노출된 채로 남아 있다. 작업대가 인스턴스당 하나뿐이니, 그 인스턴스를 공유하면 작업대를 공유하는 것이다.

작업대는 하나 더 있다. `DateFormat`은 숫자 변환용으로 **`NumberFormat numberFormat`** 필드도 함께 들고 있는데, 그 실체인 `DecimalFormat` 역시 내부에 자릿수를 담는 가변 버퍼를 갖고 있다. 이 두 번째 작업대가 뒤에서 볼 `NumberFormatException`의 출처다.

### 1-4. 두 스레드가 동시에 들어오면 — 타임라인

**`format()`의 경우.** 결과가 조용히 뒤섞인다.

```
스레드 A: format(2026-01-15) 호출
스레드 B: format(2026-08-31) 호출

A: ① calendar.setTime(2026-01-15)    <- 작업대에 A의 날짜를 올린다
B: ① calendar.setTime(2026-08-31)    <- ★ A의 것을 덮어쓴다
A: ② calendar에서 연/월/일을 읽어 조립 -> "2026-08-31"
   ★ A는 자기가 넘긴 1월 15일이 아니라 B의 8월 31일을 돌려받는다
B: ② calendar에서 읽어 조립         -> "2026-08-31"  (B는 우연히 정상)
```

예외는 나지 않는다. A의 응답에 B의 날짜가 실려 나갈 뿐이다. **로그도 정상이고, 알람도 없고, 에러율도 0%다.**

**`parse()`의 경우.** 여기서는 예외가 튈 수도 있다.

```
스레드 A: parse("2026-01-15") 호출
스레드 B: parse("2026-08-31") 호출

A: ① 문자열에서 (연=2026, 월=1, 일=15) 를 뽑는다
A: ② calendar.clear() 후 써넣기 시작 — 연=2026 까지 썼다
B: ② calendar.clear()                <- ★ A가 쓰던 도중에 작업대를 통째로 비운다
B: ② (연=2026, 월=8, 일=31) 을 써넣는다
A: ③ calendar.getTime()              -> 2026-08-31 (B의 날짜) 를 받는다

   또는, 필드가 반쯤 지워진 상태에서 읽으면
A: ③ 필드가 비어 있거나 앞뒤가 안 맞아 -> 예외
```

숫자 파싱 쪽 작업대(`DecimalFormat`의 자릿수 버퍼)에서도 같은 경합이 일어난다. 한 스레드가 자릿수를 모으는 도중에 다른 스레드가 버퍼를 초기화하면 `"multiple points"`나 빈 문자열 같은 **말이 안 되는 입력을 파싱한 꼴이 되어 `NumberFormatException`이 튄다.** 배열 인덱스가 어긋나 `ArrayIndexOutOfBoundsException`이 나기도 한다.

여기서 중요한 것은 예외 자체가 아니다. **같은 코드가 어떤 때는 예외를 던지고, 어떤 때는 조용히 틀린 값을 돌려주고, 대부분의 경우에는 멀쩡히 동작한다**는 사실이다.

### 1-5. "가끔만 난다"는 것이 이 버그를 무섭게 만든다

경합이 실제로 겹치는 구간은 마이크로초 단위다. 두 스레드가 하필 그 짧은 구간에 겹쳐 들어와야 사고가 난다. 그래서 이런 성질이 나온다.

| 상황 | 결과 |
|---|---|
| 단위 테스트 (단일 스레드) | 100% 통과. 경합할 상대가 없다 |
| 로컬 수동 테스트 | 100% 통과. 요청을 한 번에 하나씩 보낸다 |
| 코드 리뷰 | 컴파일되고 테스트도 통과하니 그냥 넘어간다 |
| 운영 (초당 수십~수백 건) | 하루에 몇 건, 몇십 건씩 조용히 틀린다 |

**"가끔만 난다"가 왜 "항상 난다"보다 나쁜가.** 항상 틀리면 첫 요청에서 바로 발각되고 배포도 못 나간다. 가끔 틀리면 배포는 무사히 나가고, 문제는 몇 주 뒤 데이터가 이미 오염된 다음에 드러난다.

발견되는 경로도 나쁘다. **실패의 상당수는 예외조차 아니다.** 예외가 튀는 경우는 그나마 스택 트레이스가 남아 추적이라도 되는데, 조용히 틀린 날짜는 아무 흔적을 남기지 않는다. 정산 리포트의 숫자가 안 맞거나, 고객이 "주문 날짜가 이상해요"라고 문의할 때가 되어서야 알게 된다. 그 시점에 **이미 틀린 값으로 저장된 데이터를 어떻게 복구할지**가 새로운 문제로 따라온다.

간혹 나는 예외는 예외대로 위험하다. 재현이 안 되니 "일시적 오류"로 분류되어 재시도 로직에 묻히고, **아무도 원인을 찾지 않은 채 몇 달을 흘러간다.**

그래서 이 유형은 **테스트로 잡는 버그가 아니라 리뷰어의 머릿속 모델로 잡는 버그**다. 코드를 보는 순간 두 질문이 자동으로 떠올라야 한다. **"이 객체는 스레드 안전한가?"** 그리고 **"이 참조는 몇 개의 스레드가 공유하는가?"**

## 2. 어떻게 고치나 — 대안 셋과 트레이드오프

원인은 "가변 객체를 여러 스레드가 공유한다"이므로, 고치는 방향도 논리적으로 셋뿐이다. **가변을 없애거나, 공유를 없애거나, 스레드별로 격리하거나.**

### 2-1. 대안 ① DateTimeFormatter — 가변 상태 자체를 없앤다 (1순위)

```java
// After ①: java.time으로 교체 — 근본 해법
public class DateUtils {
    private static final DateTimeFormatter FMT =
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
    // DateTimeFormatter는 '불변' 객체다. 포맷 도중 자기 필드에 중간 결과를
    // 쌓지 않고 호출마다 지역 상태만 쓰므로, 여러 스레드가 동시에 불러도
    // 서로 덮어쓸 것이 없다. 그래서 static 공유가 오히려 권장된다.

    public static String format(LocalDateTime dt) {
        return dt.format(FMT);
    }
}
```

`java.time` 계열(`LocalDateTime`, `Instant`, `DateTimeFormatter`)은 **전부 불변으로 설계**됐다. 불변 객체란 생성된 뒤 내부 상태가 절대 바뀌지 않는 객체를 말한다. 상태가 안 바뀌면 덮어쓸 것도 없으니 **동시 접근이라는 개념 자체가 성립하지 않는다.**

여기서 짚어야 할 것이 있다. `DateTimeFormatter`도 똑같이 `static final`로 선언했는데 안전하다. **즉 static이 문제였던 게 아니다.** 문제는 "가변 + 공유"라는 조합이었고, 가변을 없애면 공유는 아무 문제가 아니게 된다. 오히려 매번 만드는 게 낭비라서 static 공유가 정석이다.

**트레이드오프**: 사실상 없다. 비용은 마이그레이션 노동뿐이다. `Date`를 쓰는 레거시 API 경계가 있으면 `Date.toInstant()` / `Date.from(Instant)`로 변환 계층을 두면 된다. 신규 코드에서는 고민할 이유가 없다.

### 2-2. 대안 ② 매번 새 인스턴스 — 공유를 없앤다 (가장 단순)

```java
// After ②: 호출할 때마다 새로 만든다 — 공유 자체를 제거
public static String format(Date date) {
    // 지역 변수이므로 스레드마다 각자의 스택에 각자의 인스턴스를 갖는다.
    // 다른 스레드가 접근할 경로가 아예 없다.
    return new SimpleDateFormat("yyyy-MM-dd").format(date);
}
```

가장 이해하기 쉽고 틀릴 여지가 없는 방법이다. 정확성만 보면 완벽하다.

**트레이드오프는 할당 비용이다.** `SimpleDateFormat` 생성자는 패턴 문자열을 파싱해 내부 구조를 만들고 `Calendar`와 `NumberFormat`까지 함께 생성하므로, 문자열 하나 만드는 것치고는 무거운 편이다.

다만 이 비용을 과대평가하지 않는 것도 중요하다. 요청당 몇 번 부르는 정도라면 **DB 조회 한 번에 비하면 무시할 수준**이고, 짧게 살다 죽는 객체는 GC가 가장 잘 처리하는 부류다. 실제로 문제가 되는 것은 **수만 건 루프 안에서 매번 만드는** 것 같은 핫 패스뿐이다.

**선택 기준**: 호출 빈도가 낮거나 보통이면 이걸로 충분하다. 측정해서 진짜 병목으로 확인됐을 때만 다음 대안을 검토한다.

### 2-3. 대안 ③ ThreadLocal — 스레드별로 격리한다 (레거시 핫패스용)

```java
// After ③: 스레드마다 자기 인스턴스를 갖게 한다
private static final ThreadLocal<SimpleDateFormat> SDF =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
        // withInitial: 각 스레드가 처음 get() 할 때 이 함수로 자기 인스턴스를 만든다

public static String format(Date date) {
    return SDF.get().format(date);   // 스레드마다 다른 인스턴스가 나온다
}
```

인스턴스를 재사용하면서도 공유는 하지 않으므로, 정확성과 할당 비용을 동시에 잡는 것처럼 보인다. 하지만 대가가 따라온다.

**트레이드오프 (1) 정리 문제.** ThreadLocal의 값은 `Thread` 객체 안에 저장되므로 **스레드가 살아 있는 한 값도 살아 있다.** 톰캣 워커는 재사용되며 계속 살아 있으니, `remove()`하지 않으면 워커 수만큼의 `SimpleDateFormat` 인스턴스가 애플리케이션 수명 내내 상주한다. 이 정도 크기의 객체 200개는 대개 감당할 만하지만, **웹 애플리케이션 재배포 시 그 값이 이전 클래스로더를 붙잡아 Metaspace 누수로 번지는** 문제가 남는다. (`16-threadlocal-thread-pool-risks.md`에서 자세히 다룬다.)

**트레이드오프 (2) 가상 스레드에서 전제가 무너진다.** "스레드당 하나씩 만들어 재사용해 비용을 아낀다"는 계산은 스레드가 200개일 때 성립한다. 가상 스레드처럼 스레드를 수십만 개 만드는 모델에서는 **인스턴스도 수십만 개**가 되어, 아끼려던 비용이 오히려 부담이 된다.

**트레이드오프 (3) 퇴행에 취약하다.** 이게 가장 실질적인 위험이다. 다음 사람이 코드를 정리하다가 "이 ThreadLocal 껍데기는 왜 있지" 하고 걷어내 그냥 static 필드로 되돌리는 순간 버그가 부활한다. 불변으로 만들어두면 그런 퇴행이 **원천적으로 불가능하다.**

**선택 기준**: `Date`/`SimpleDateFormat`을 당장 걷어낼 수 없는 레거시 경계이고, 측정 결과 매번 생성이 실제 병목인 핫 패스일 때. 이때도 `remove()` 정책을 어디서 어떻게 보장할지 함께 정해야 한다.

### 2-4. synchronized는 왜 답이 아닌가

"공유가 문제면 락을 걸면 되지 않나"는 자연스러운 발상이다.

```java
// 동작은 한다 — 그러나
public static synchronized String format(Date date) {
    return SDF.format(date);
}
```

정확성은 확보된다. 한 번에 한 스레드만 들어가므로 작업대를 덮어쓸 일이 없다.

**문제는 성능이 아니라 성능의 성격이다.** 이 메서드는 **JVM 전체에서 한 줄로 직렬화**된다. 워커 200개가 동시에 날짜를 포맷하려 하면 199개가 줄을 서서 기다린다. 서버를 8코어짜리로 바꿔도 이 구간의 처리량은 그대로다.

날짜 포맷은 애플리케이션 곳곳에서 아주 자주 호출되는 연산이라 **직렬화 구간으로 삼기에 최악의 후보**다. 게다가 이 락은 아무 이득을 사지 못한다 — 락으로 지키려는 공유 상태 자체가 애초에 필요 없는 것이었기 때문이다. **없어도 되는 공유를 만들어 놓고 락으로 지키는 구조**다.

### 2-5. 선택 순서

정리하면 우선순위는 이렇다.

| 순서 | 방법 | 성격 | 언제 |
|---|---|---|---|
| 1 | `DateTimeFormatter` | 가변을 제거 | 신규 코드는 무조건. 레거시도 목표 상태 |
| 2 | 매번 새 인스턴스 | 공유를 제거 | `Date` 경계를 못 걷어낼 때. 대부분 충분 |
| 3 | `ThreadLocal` | 스레드별 격리 | 측정된 핫 패스. `remove()` 정책 필수 |
| 4 | `synchronized` | 접근 직렬화 | 사실상 쓰지 않는다 |

원칙은 **"근본 → 대증"** 순이다. 위로 갈수록 문제를 없애고, 아래로 갈수록 문제를 안고 관리한다. 면접에서는 "①이 정답이고 ②③은 마이그레이션 경계에서만 쓴다"고 **순서와 이유를 함께** 말하는 것이 좋다.

## 3. 진짜 주제 — "static 필드에 가변 상태를 두는 것" 일반

면접의 진짜 배점은 여기다. `SimpleDateFormat` 하나를 고치는 것은 지식의 문제지만, **같은 유형이 코드베이스 어디에 또 있는지 찾아내는 것**은 모델의 문제다. 질문이 "어디에서 더 찾아보겠습니까"로 끝나는 이유다.

### 3-1. 공유 스코프는 둘이다 — static 필드와 싱글톤 빈의 인스턴스 필드

일반화의 첫 단계는 **"공유되는 자리"의 목록을 정확히 아는 것**이다. 자바 웹 애플리케이션에서 여러 스레드가 같은 객체를 보게 되는 경로는 크게 둘이다.

**(1) static 필드.** 클래스에 하나만 존재하므로 정의상 전역 공유다. 이건 눈에 보인다.

**(2) 싱글톤 스프링 빈의 인스턴스 필드.** 이게 눈에 잘 안 띈다. `@Service`, `@Component`, `@Repository`, `@RestController`는 전부 **기본 스코프가 싱글톤**이다. 즉 애플리케이션 전체에 인스턴스가 하나뿐이고, 모든 요청 스레드가 그 하나를 공유한다.

**빈의 인스턴스 필드는 사실상 static과 같은 공유다.** `private`이라고 안전한 게 아니다. `private`은 다른 클래스의 접근을 막는 것이지 다른 스레드의 접근을 막는 것이 아니다. 접근 제어자와 동시성은 아무 관계가 없다.

이 등가 관계를 알아채는 것이 이 문제의 핵심이다.

```
static 필드            -> 인스턴스가 하나 -> 모든 스레드가 공유
싱글톤 빈의 인스턴스 필드 -> 인스턴스가 하나 -> 모든 스레드가 공유   ★ 같다
```

### 3-2. 수색 1순위 — 가변 static 필드

```bash
# static 인데 final 이 아닌 필드 — 재대입까지 가능한 전역 상태
grep -rn --include='*.java' -E '(private|protected|public)[[:space:]]+static[[:space:]]' . \
  | grep -v ' final '

# final 이어도 '타입이 가변'이면 용의자다 (final은 참조만 고정 — 1-2 참고)
grep -rn --include='*.java' -E \
  'static +final +(SimpleDateFormat|DateFormat|Calendar|DecimalFormat|NumberFormat|MessageDigest|Matcher|StringBuilder|HashMap|ArrayList|HashSet)' .
```

grep은 후보를 넓게 뽑는 용도이고, 정확도는 IDE의 구조 검색(필드 선언만 대상으로 하는 검색)이 낫다. 중요한 것은 명령어가 아니라 **무엇을 용의자로 볼지의 기준**이다.

스레드 안전하지 않은 단골들을 유형별로 기억해두면 좋다.

- **포맷 계열 전반**: `SimpleDateFormat`, `DateFormat`, `Calendar`, `DecimalFormat`, `NumberFormat`. 전부 내부에 작업대를 두는 같은 구조다.
- **`MessageDigest`**: 해시를 계산할 때 데이터를 조금씩 흘려 넣고 마지막에 결과를 뽑는 **누적 상태**를 갖는다. 공유하면 두 스레드의 입력이 섞여 엉뚱한 해시가 나온다.
- **`Matcher`**: 정규식 매칭이 어디까지 진행됐는지를 담은 상태 객체다. (반면 `Pattern`은 불변이라 static 공유가 정석이다 — 4절 꼬리질문 참고.)
- **`StringBuilder`**: 문자를 이어붙이는 버퍼 자체가 가변 상태다.
- **`HashMap` / `ArrayList`**: `static final Map<...> CACHE = new HashMap<>()`가 전형이다. 동시에 `put`하면 값이 유실될 수 있고, 리사이징이 겹치면 자료구조가 깨진다. `ConcurrentHashMap`으로 교체 대상이다.

### 3-3. 수색 2순위 — 싱글톤 빈의 인스턴스 필드

`SimpleDateFormat`을 static으로 두는 것과 **정확히 같은 사고**가 여기서 난다. 다만 겉모습이 평범한 서비스 코드라 훨씬 발견하기 어렵다.

```java
// Before: 요청 처리 중간 상태를 필드에 둔 정산 서비스
@Service
public class SettlementService {

    private final MerchantRepository merchantRepository;

    // 여기부터가 문제다. @Service 는 싱글톤이므로 이 필드들은
    // 모든 요청 스레드가 공유하는 '하나의' 변수다 — static 과 다를 게 없다.
    private Merchant currentMerchant;      // 지금 처리 중인 가맹점
    private List<Row> buffer = new ArrayList<>();
    private long totalAmount;

    public Report build(SettlementRequest req) {
        currentMerchant = merchantRepository.find(req.merchantId());
        buffer.clear();                    // 다른 요청이 모아둔 행을 지운다
        totalAmount = 0;

        for (Payment p : loadPayments(req)) {
            buffer.add(toRow(p));          // 여러 스레드가 같은 리스트에 동시에 add
            totalAmount += p.amount();     // += 는 읽기-더하기-쓰기 3단계 (원자적이지 않다)
        }
        return new Report(currentMerchant, List.copyOf(buffer), totalAmount);
    }
}
```

무슨 일이 벌어지는지 타임라인으로 보자. 가맹점 A와 가맹점 B의 정산 요청이 동시에 들어온 상황이다.

```
스레드 A: currentMerchant = 가맹점A
스레드 A: buffer.clear(); totalAmount = 0
스레드 A: buffer 에 A의 결제 100건을 담는 중 (50건까지 담음)

스레드 B: currentMerchant = 가맹점B      <- ★ A의 값을 덮어쓴다
스레드 B: buffer.clear()                 <- ★ A가 담던 50건이 사라진다
스레드 B: totalAmount = 0                <- ★ A가 더하던 합계가 초기화된다

스레드 A: 나머지 50건을 담는다 (앞의 50건은 이미 없다)
스레드 A: Report 생성
   -> 가맹점 이름: 가맹점B          ★ 남의 가맹점 이름
   -> 행 목록: A와 B의 행이 뒤섞인 일부
   -> 합계: 어느 쪽 것도 아닌 숫자
```

결과는 `SimpleDateFormat` 사고와 같은 성질이다. **예외가 나지 않고, 조용히 틀린 리포트가 나가며, 심지어 다른 고객의 데이터가 섞여 나간다.** 정산 리포트에서 이건 사고 등급이 한 단계 더 높다.

`totalAmount += p.amount()` 한 줄도 별도의 문제다. `+=`는 **읽기 → 더하기 → 쓰기**의 3단계 복합 연산이라, 두 스레드가 같은 값을 읽고 각자 더해 쓰면 한쪽의 증가분이 통째로 사라진다.

고치는 방향은 단순하다. **중간 상태를 필드에서 스택으로 내린다.**

```java
// After: 요청 처리 중간 상태를 전부 지역 변수로 옮긴다
@Service
public class SettlementService {

    // 필드에는 '주입받은 협력자'와 '불변 설정'만 남긴다.
    // 이 둘은 생성 후 바뀌지 않으므로 공유되어도 안전하다.
    private final MerchantRepository merchantRepository;
    private static final DateTimeFormatter FMT =
            DateTimeFormatter.ofPattern("yyyy-MM-dd");   // 불변이라 static 공유 OK

    public Report build(SettlementRequest req) {
        // 지역 변수는 스레드마다 각자의 스택에 만들어진다.
        // 다른 스레드가 접근할 경로가 아예 없으므로 동기화가 필요 없다.
        Merchant merchant = merchantRepository.find(req.merchantId());
        List<Row> rows = new ArrayList<>();
        long total = 0;

        for (Payment p : loadPayments(req)) {
            rows.add(toRow(p, FMT));
            total += p.amount();
        }
        return new Report(merchant, rows, total);
    }
}
```

**점검 기준을 한 문장으로 만들면 이렇다. 싱글톤 빈의 필드에는 주입받은 협력자(불변 참조)와 설정값만 있어야 하고, 요청 처리 중간 상태가 필드에 있으면 즉시 용의자다.**

`@RestController`도 똑같은 싱글톤이라는 점을 덧붙여둔다. 컨트롤러에 `private String currentUserId` 같은 필드를 두는 코드는 같은 사고를 낸다.

진짜로 인스턴스 간에 공유해야 하는 값이 있다면(예: 전체 처리 건수 카운터) 필드에 그냥 두지 말고 `AtomicLong`이나 `ConcurrentHashMap` 같은 **동시성 안전 자료구조**로 옮기거나, 여러 인스턴스에 걸쳐 정확해야 한다면 아예 DB나 Redis로 내보낸다. 요청 스코프 빈(`@Scope("request")`)도 선택지지만, 대부분의 경우 **지역 변수로 내리는 것이 더 단순하고 더 빠르다.**

### 3-4. 수색 3순위 — 사람 눈 대신 CI가 잡게 한다 (가산점 포인트)

1-5에서 봤듯 이 유형은 테스트로 안 잡힌다. 그렇다고 리뷰어의 집중력에만 기대는 것도 방어선으로는 약하다. **패턴 자체를 자동으로 차단하는 것**이 가장 싸고 확실하다.

**SpotBugs의 `STCAL` 계열 룰**이 정확히 이 패턴(static `Calendar` / static `DateFormat` 인스턴스)을 잡는다. SonarQube와 Error Prone에도 대응 룰이 있다. CI에 붙여 두면 **같은 코드가 두 번 다시 머지되지 않는다.**

**AI 생성 코드가 늘수록 이 방어선의 가치가 커진다.** AI는 학습 데이터에 많았던 관용구를 자신 있게 재생산하는데, `static final SimpleDateFormat`은 `java.time` 이전 시대에 아주 흔했던 코드라 특히 잘 나온다. 그리고 이 코드는 **컴파일되고, 리뷰에서 그럴듯해 보이고, 테스트도 통과한다.** 정적 분석과 리뷰어의 모델 없이는 걸러지지 않는다.

면접에서 이 대목을 말할 때는 "AI가 틀린 코드를 준다"가 아니라 **"AI가 주는 코드 중 이 유형은 사람 눈으로 걸러지지 않으니 자동화된 관문이 필요하다"**로 정리하는 편이 낫다. 출제 의도가 AI 코드 검증 능력을 보는 것이기 때문이다.

### 3-5. 리뷰어의 2축 질문으로 요약

지금까지의 수색 전략은 결국 두 개의 질문으로 압축된다. 코드를 볼 때 이 둘이 자동으로 떠오르면 된다.

**질문 1: 이 객체는 스레드 안전한가?** Javadoc에 스레드 안전성이 명시돼 있는지 본다. 불변이면 통과다. 명시가 없으면 **가변으로 간주**하고 다음 질문으로 간다.

**질문 2: 이 참조는 몇 개의 스레드가 공유하는가?** static 필드인가, 싱글톤 빈의 필드인가, 스레드 간에 전달되는가. 지역 변수면 통과다.

```
        스레드 안전(불변)      가변
공유    안전                  ★ 여기가 전부 함정
비공유  안전                  안전
```

**두 답이 "가변 + 공유"로 만나는 지점이 전부 이 유형의 함정이다.** `SimpleDateFormat`은 그 지점의 한 사례일 뿐이고, 외워야 할 것은 사례 목록이 아니라 이 2축이다.

## 4. 꼬리질문 대비 포인트

### "왜 테스트에서는 안 잡히나요? 잡으려면 어떻게 해야 하나요?"

**단위 테스트가 단일 스레드로 돌기 때문이다.** 경쟁 상태는 두 스레드의 실행이 특정 구간에서 겹쳐야 드러나는데, 스레드가 하나뿐이면 겹칠 상대가 없다.

잡는 방법을 비용이 싼 순서대로 말하면 좋다.

1. **정적 분석으로 패턴 자체를 차단한다** (SpotBugs `STCAL` 등). 가장 싸고 가장 확실하다. 실행조차 필요 없다.
2. **동시성 유닛 테스트를 쓴다.** 수십 개 스레드로 같은 포맷터를 수천 번 두들기고 결과를 검증하면, `SimpleDateFormat` 정도의 좁은 경합 구간도 거의 확실히 재현된다.
3. **부하 테스트 단계에서 응답 데이터의 정합성까지 검증한다.** 보통 부하 테스트는 응답 시간과 에러율만 보는데, 이 유형은 **둘 다 정상으로 나온다.** 값이 맞는지까지 봐야 잡힌다.

마지막에 한 줄 덧붙이면 좋다. **"재현이 어려우니 운영 로그로 발견한다"는 것은 이미 데이터가 오염된 뒤라는 뜻**이다. 발견 시점이 곧 복구 비용이다.

### "ThreadLocal로 감싸면 되는데 왜 굳이 DateTimeFormatter로 바꾸나요?" (시니어 변별 포인트)

**둘의 성격이 다르다는 것부터 구분한다.** ThreadLocal은 "가변 상태를 스레드별로 격리"하는 대증요법이고, `DateTimeFormatter`는 "가변 상태 자체를 제거"하는 근본 해법이다. 문제를 안고 관리하느냐, 문제를 없애느냐의 차이다.

ThreadLocal이 치르는 대가를 셋으로 든다.

1. **정리 문제.** 스레드풀 환경에서 `remove()`하지 않으면 워커 수만큼의 인스턴스가 스레드 수명 내내 잔류하고, 재배포 시 이전 클래스로더를 붙잡아 누수로 번진다.
2. **가상 스레드에서 전제가 무너진다.** 스레드가 수십만 개가 되면 "스레드당 하나씩"이라는 절약 전략 자체가 낭비가 된다.
3. **퇴행에 취약하다.** 다음 수정자가 ThreadLocal 껍데기를 걷어내고 그냥 공유하도록 "정리"하는 순간 버그가 부활한다. **불변으로 만들면 그런 퇴행이 원천적으로 불가능하다.**

여기서 "그럼 `synchronized`로 감싸는 건요?"까지 이어지면 이렇게 답한다. 정확성은 얻지만 **모든 포맷 호출이 JVM 전체에서 한 줄로 직렬화**되어 다중 스레드의 의미가 없어진다. 날짜 포맷처럼 곳곳에서 자주 불리는 연산을 직렬화 구간으로 삼는 것은 최악의 선택이고, 무엇보다 **없어도 되는 공유를 만들어 놓고 락으로 지키는 구조**다.

### "`Pattern.compile()`을 static으로 두는 것도 위험한가요?"

**아니다. 그리고 이 대비가 이 주제의 이해도를 그대로 보여준다.**

`Pattern`은 컴파일된 정규식을 담은 **불변 객체**다. 매칭 과정에서 자기 상태를 바꾸지 않으므로 static 공유가 오히려 정석이다. 정규식 컴파일은 비싼 작업이라, 매 호출마다 `Pattern.compile()`을 부르는 쪽이 진짜 성능 문제다.

위험한 것은 `pattern.matcher(input)`이 돌려주는 **`Matcher`** 쪽이다. Matcher는 "지금 몇 번째 글자까지 매칭했는지", "그룹별로 무엇이 잡혔는지" 같은 **진행 상태를 담은 가변 객체**다. 공유하면 안 되고, 호출마다 새로 만들어 지역 변수로 쓴다.

```java
// 올바른 사용: Pattern은 static 공유, Matcher는 매번 새로
private static final Pattern EMAIL = Pattern.compile("^[\\w.]+@[\\w.]+$");

public boolean isValid(String input) {
    return EMAIL.matcher(input).matches();   // Matcher는 지역에서 만들어 지역에서 버린다
}
```

즉 규칙은 "static이 나쁘다"가 아니라 **"불변은 공유해도 되고, 가변은 공유하면 안 된다"**이다. 3-5의 2축 질문이 그대로 적용된 사례다.

### "스프링 싱글톤 빈은 인스턴스가 하나인데 왜 대부분 문제가 없나요?"

**빈이 상태를 갖지 않기 때문이다(stateless).** 싱글톤이라서 안전한 게 아니라 무상태라서 안전하다는 구분이 답의 핵심이다.

통상의 서비스 빈 필드에는 생성자로 주입받은 다른 빈 참조와 설정값만 있다. 둘 다 생성 후 바뀌지 않는 값이다. 요청 처리에 쓰이는 값들은 전부 **파라미터와 지역 변수**, 즉 스레드마다 따로 있는 스택 위에 있다. 그래서 여러 스레드가 같은 인스턴스의 메서드를 동시에 실행해도 서로 건드릴 것이 없다.

**필드에 요청 처리 상태를 넣는 순간 `static SimpleDateFormat`과 정확히 같은 유형의 함정이 된다.** 인스턴스가 하나이고 스레드가 여럿이라는 조건이 똑같기 때문이다.

상태가 꼭 필요하면 순서대로 검토한다. **지역 변수로 내리는 것이 1순위**, 그다음이 요청 스코프 빈, 진짜 공유해야 하는 값이라면 `AtomicLong`·`ConcurrentHashMap` 같은 동시성 안전 구조, 여러 인스턴스에 걸쳐 정확해야 한다면 DB나 Redis로 내보낸다.

### "AI 생성 코드에서 이런 유형을 리뷰할 때의 체크 순서를 말해주세요"

**개별 지적이 아니라 순서를 말하는 것**이 "유형으로 아는" 답변이다.

1. **공유 스코프부터 본다.** 새로 등장한 static 필드와 빈의 인스턴스 필드를 먼저 훑는다. 지역 변수는 볼 필요가 없으므로 검토 범위가 크게 줄어든다.
2. **그 타입이 가변인지 확인한다.** Javadoc에 스레드 안전성 명시가 없으면 가변으로 간주한다. "명시가 없으면 안전하지 않다고 본다"가 안전한 기본값이다.
3. **가변 + 공유가 확인되면 해법을 서열대로 고른다.** 불변 대체재(`java.time`, 불변 컬렉션) → 공유 제거(지역 변수화) → 격리(`ThreadLocal`) → 동기화 순이다. 위쪽일수록 문제를 없애고, 아래쪽일수록 문제를 안고 관리한다.
4. **재발을 막는다.** 같은 패턴이 다시 들어오지 않게 정적 분석 룰을 CI에 추가한다.

이 네 단계(스코프 → 가변성 → 해법 서열 → 재발 방지)를 말하면, 한 사례를 고치는 사람이 아니라 **유형을 관리하는 사람**으로 읽힌다.

## 한 줄 요약

`SimpleDateFormat`이 위험한 이유는 내부에 `Calendar` 작업대를 하나 두고 호출마다 거기에 중간 결과를 쌓았다 읽는 구조이기 때문이고, 이것을 static으로 공유하면 톰캣 워커들이 그 작업대를 서로 덮어써서 **예외 없이 남의 날짜가 응답에 실리거나 가끔씩만 `NumberFormatException`이 튀는** — 그래서 테스트로도 에러율 그래프로도 안 잡히는 — 사고가 난다. 해법은 격리(`ThreadLocal`)나 직렬화(`synchronized`)보다 가변 상태를 아예 없애는 `DateTimeFormatter`가 1순위이며, 무엇보다 이 문제의 정체는 static도 날짜도 아닌 **"가변 상태 × 공유 스코프"**라는 유형이므로 — 스프링 빈은 싱글톤이라 그 인스턴스 필드가 static과 같은 공유라는 점까지 포함해 — 코드베이스 전체를 그 2축으로 훑고, 마지막에는 정적 분석 룰로 재발을 막는다.
