# Virtual Thread(Java 21+) — 스레드 모델의 차이, Continuation 원리, pinning, @Transactional 함정

> 핵심 관전 포인트: **가상 스레드는 처리 속도가 아니라 "대기 중 동시성"을 높이는 기술이다. 스레드란 결국 "콜 스택 + 실행 위치"라는 데이터인데, 과거엔 블로킹이 커널 안에서 일어나 JVM이 개입할 타이밍이 없었기에 1:1일 수밖에 없었다. Loom은 JDK가 시스템 콜 직전 경로를 소유한다는 점을 이용해, 블로킹 대신 "epoll 등록 + 스스로 스택을 힙에 얼리고(freeze) 물러나기"로 바꿔치기했다 — 블로킹 스타일 코드 그대로 리액티브급 동시성을 얻는다. 도입 시 함정 두 가지: (1) JVM이 경로를 소유하지 못한 지점(`synchronized`·JNI)에서 블로킹하면 캐리어에 못박히는 pinning(JDK 24의 JEP 491에서 `synchronized`는 해소, 네이티브는 그대로), (2) 가상 스레드는 스레드만 해방시킬 뿐 DB 커넥션은 못 푼다 — `@Transactional` 안 외부 API 콜은 동시성이 폭증한 만큼 커넥션 풀 고갈로 더 크게 터진다.**

---

## 0. 질문 + 의도

**질문**: "Virtual Thread(Project Loom)는 기존 스레드 모델과 무엇이 다른가요? pinning 문제란?"

**출제 의도**: 새 기술 도입 판단의 시금석이다. "가상 스레드 쓰면 다 해결"이 아니라 pinning(synchronized 블록 내 블로킹) 같은 제약과 기존 코드베이스의 궁합을 먼저 따지는 사람인지 — 즉 하이프와 실제를 구분하는 습관이 있는지를 본다.

**이 문서가 다루는 버전 범위**: 기준선은 **JDK 21(가상 스레드가 정식 기능이 된 첫 LTS)**이다. JDK 24에서 pinning 동작이 크게 바뀌었으므로, 달라지는 지점마다 "JDK 21~23 기준 / JDK 24 이후"를 명시해 구분한다. 이 구분을 흐리게 말하면 면접에서 오답이 되기 쉬운 주제다.

## 1. 왜 필요한가 — 플랫폼 스레드 모델의 한계

### 1-1. 전제 지식 — 자바의 `Thread` 하나는 OS 스레드 하나다

지금까지 우리가 써 온 `new Thread()`, 톰캣의 워커 스레드, `Executors.newFixedThreadPool(200)`이 만드는 스레드는 전부 같은 종류다. **운영체제가 만들어 준 진짜 스레드 하나를 자바 객체로 얇게 감싼 것**이고, 가상 스레드와 구분하기 위해 이것을 **플랫폼 스레드(platform thread)**라 부른다. "플랫폼"은 그 아래 깔린 실행 플랫폼, 즉 OS의 스레드에 그대로 대응한다는 뜻이다.

여기서 중요한 건 **1:1**이라는 관계다. 자바 스레드 하나를 만들면 OS 스레드 하나가 생기고, 자바 스레드가 잠들면 OS 스레드가 잠든다. 자바가 스레드에 대해 할 수 있는 일은 전부 OS에 그대로 청구서로 넘어간다.

그래서 OS 스레드가 비싸다는 사실이 곧 자바 스레드가 비싸다는 뜻이 된다. 비싼 이유는 셋이다.

**(1) 스택을 위해 큰 메모리를 예약한다.** 스레드마다 자기 전용 콜 스택이 필요하고, 이 스택은 힙이 아니라 네이티브 메모리에 잡힌다. 크기는 JVM 옵션 `-Xss`로 정하는데, 기본값이 **플랫폼마다 다르다**. 이 문서를 쓰며 실제로 확인해 보면 이렇다.

```
$ java -XX:+PrintFlagsFinal -version | grep ThreadStackSize
     intx ThreadStackSize     = 2048     {pd product} {default}

# macOS / AArch64 / OpenJDK 21 기준 = 2048KB = 2MB
# 리눅스 x86-64에서는 통상 1024KB(1MB)가 기본값이다
```

플래그 옆의 `{pd product}`가 바로 **platform dependent(플랫폼 의존)**라는 표시다. 그러니 "스레드 하나에 1MB"라는 흔한 문장은 리눅스 기준의 어림값이고, 정확히 말하려면 **"수백 KB~2MB 수준이며 플랫폼과 JVM 설정에 따라 다르다"**가 맞다.

한 가지 오해를 미리 걷어내자. 이 크기는 **예약(reserve)**이지 처음부터 실제로 소모하는 물리 메모리가 아니다. OS는 그만큼의 주소 공간을 잡아두기만 하고, 스택이 실제로 깊어지는 만큼만 물리 페이지를 붙여 준다. 그래도 문제는 남는다 — **주소 공간과 커널 자료구조는 스레드 수에 정직하게 비례**하므로, 스레드 1만 개를 만들려 하면 힙에 여유가 넘쳐도 `unable to create new native thread`로 실패한다.

**(2) 만들고 없애는 데 커널이 개입한다.** 스레드 생성은 리눅스에서 `clone` 시스템 콜이다. 커널 안에 스레드 자료구조를 만들고 스택을 매핑하는 작업이라, 객체 하나 `new` 하는 것과는 비교가 안 되게 무겁다. 그래서 서버는 스레드를 요청마다 만들지 않고 **미리 만들어 풀에 담아 돌려 쓴다.**

**(3) 컨텍스트 스위칭에 값이 붙는다.** 여기서 **컨텍스트 스위칭(context switching)**이란 하나의 CPU 코어가 실행 중이던 스레드를 잠시 내리고 다른 스레드를 올리는 교체 작업이다. 교체하려면 지금 스레드의 레지스터 값을 전부 저장하고 다음 스레드의 것을 복원해야 하는데, 이 작업이 커널 모드로 들어갔다 나오는 것이라 비용이 든다. 눈에 덜 띄지만 더 아픈 비용은 **CPU 캐시 오염**이다 — 새로 올라온 스레드는 자기가 쓸 데이터가 캐시에 없어 메모리에서 다시 읽어야 하고, 그동안 코어는 사실상 놀게 된다.

### 1-2. 낭비의 구조 — 스레드가 "일하는 데"가 아니라 "기다리는 데" 쓰인다

이제 왜 이게 웹 서버에서 문제가 되는지 보자. 스프링 부트의 톰캣은 기본적으로 워커 스레드를 최대 200개까지 두고, 요청 하나에 워커 하나를 붙여 처리한다.

```java
// 톰캣 기본 스레드 풀 200개인 서버에서
public Order getOrder(Long id) {
    Member member = memberClient.get(id);   // 외부 API 호출 300ms — 응답이 올 때까지 이 워커는 잠들어 있다
    Order order = orderRepository.find(id); // DB 조회 50ms — 여기서도 잠들어 있다
    return order;                           // 계산은 몇 ms면 끝난다
}
```

이 요청이 워커 스레드를 붙잡고 있는 시간을 쪼개 보면 이렇게 된다.

```
요청 하나가 워커 #7을 점유하는 350ms

  0ms                                                          350ms
  ├─┬──────────────────────────┬─┬───────────┬─┐
  │█│  ░░░ 외부 API 대기 300ms ░│█│░ DB 50ms ░│█│
  └─┴──────────────────────────┴─┴───────────┴─┘
   █ = CPU를 실제로 쓰는 구간 (다 합쳐 5ms 남짓)
   ░ = 스레드가 잠든 채 응답만 기다리는 구간 (345ms)
```

**워커의 98%가 "기다림" 그 자체에 소모된다.** 그런데 앞에서 봤듯 이 워커는 OS 스레드이므로, 기다리는 동안 그 비싼 자원이 통째로 묶여 있다.

이게 처리량 상한으로 어떻게 이어지는지 한 단계씩 계산해 보자.

1. 워커가 200개이므로 **동시에 진행할 수 있는 요청도 최대 200건**이다.
2. 요청 하나가 워커를 350ms(=0.35초) 잡고 있다. 따라서 워커 하나는 1초에 `1 / 0.35 ≈ 2.86`건을 처리한다.
3. 서버 전체 처리량 상한 = `200 × 2.86 ≈ 571 req/s`.
4. 그 571건이 실제로 요구하는 CPU 시간 = `571 × 5ms ≈ 2.9초/초`. 코어 3개면 감당되는 양이다.

**8코어 서버라면 CPU 사용률이 36% 언저리에서 처리량이 막힌다.** CPU가 놀고 있는데 더 못 받는 이 상태가 문제의 본체다. 병목은 계산 능력이 아니라 **"기다림을 담아 둘 그릇"의 개수**이고, 그 그릇이 하필 OS 스레드라서 비싸다.

201번째 요청은 어떻게 되는가 — 워커가 빌 때까지 톰캣의 수락 큐에서 대기한다. 사용자 입장에서는 서버가 CPU를 놀리면서 응답을 늦추는, 설명하기 어려운 지연이 된다.

### 1-3. 기존 답이었던 리액티브와 그 대가

이 문제를 푸는 방향은 논리적으로 둘뿐이다. **기다림을 스레드에 담지 않도록 코드를 바꾸거나, 기다림을 담는 그릇을 싸게 만들거나.**

전자가 **리액티브(WebFlux, Reactor 등)**다. "결과를 기다렸다가 다음 줄로 간다" 대신 "결과가 오면 이 함수를 실행해 달라"고 콜백을 등록하고 스레드는 즉시 반납한다. 스레드 몇 개로 수만 건의 대기를 감당할 수 있다.

```java
// 리액티브: 기다리지 않고 "오면 이걸 해라"를 등록한다
public Mono<Order> getOrder(Long id) {
    return memberClient.get(id)
            .flatMap(member -> orderRepository.find(id))
            .map(this::toResponse);
}
```

대가가 만만치 않다. **호출 스택이 사라진다는 것이 핵심 대가다.** 예외가 터졌을 때 스택트레이스에는 내 비즈니스 로직 대신 리액터 내부 프레임이 잔뜩 찍히고, "어느 요청 처리 중이었는지"를 알려면 별도 장치가 필요하다. 디버거로 한 줄씩 따라가는 것도, `try-catch-finally`도, ThreadLocal 기반 도구(트랜잭션·MDC·SecurityContext)도 그대로는 안 통한다. 그리고 이 전염은 국소적이지 않다 — **경로 위의 라이브러리 하나라도 블로킹이면 전체가 무너지므로 스택 전체를 리액티브로 바꿔야 한다.**

후자, 즉 **그릇을 싸게 만드는 쪽**이 가상 스레드다. 코드는 그대로 두고 스레드의 구현만 갈아 끼운다.

## 2. 어떻게 동작하는가 — 캐리어 스레드와 Continuation

### 2-1. 2층 구조 — 가상 스레드와 캐리어 스레드

**가상 스레드(virtual thread)**는 OS 스레드와의 1:1 매핑을 끊고 **JVM이 직접 스케줄링하는 경량 스레드**다. 이걸 만든 OpenJDK 프로젝트의 코드명이 **Loom**이다. 2017년에 시작해 2023년 Java 21에 정식 기능으로 들어갔다. loom은 "베틀"이라는 뜻으로, 스레드(실)를 짜는 도구라는 말장난이다.

동작의 뼈대는 네 줄이다.

1. 소수의 OS 스레드가 **실행대** 역할을 한다. 이 스레드를 **캐리어 스레드(carrier thread)**라 부른다 — 가상 스레드를 태워 나른다(carry)는 뜻이다. 기본 개수는 CPU 코어 수다.
2. 가상 스레드는 캐리어 위에 **올라타서(mount)** 실행된다.
3. 블로킹 I/O를 만나면 JVM이 그 가상 스레드의 실행 상태를 힙에 떼어 저장하고 **캐리어에서 내린다(unmount)**.
4. 비워진 캐리어는 즉시 다른 가상 스레드를 태운다. I/O가 끝나면 그 가상 스레드는 **아무 캐리어에나** 다시 올라타 이어서 실행된다.

"JVM이 스케줄링한다"는 말은 OS 스케줄러가 교체됐다는 뜻이 아니다. **스케줄링이 2층으로 겹쳐졌다**는 뜻이다.

```
가상 스레드 수만 개  (힙에 사는 자바 객체들)
   │
   │  1층: JVM 스케줄러 — JDK 안의 ForkJoinPool, 그냥 자바 코드다
   │       "이 가상 스레드를 어느 캐리어에서 실행할까"
   ▼
캐리어 스레드 8개  (평범한 OS 스레드 = 플랫폼 스레드)
   │
   │  2층: OS 스케줄러 — 여전히 자기 일을 한다
   │       "이 OS 스레드를 어느 CPU 코어에서 실행할까"
   ▼
CPU 코어 8개
```

**OS는 가상 스레드의 존재를 전혀 모른다.** OS가 보는 것은 "이 자바 프로세스에 스레드가 8개 있네"뿐이다. 이 사실은 나중에 모니터링 지표를 볼 때 그대로 함정이 된다(3-4절).

여기서 얻는 결론이 이 기술의 전부다. **"스레드가 기다린다 = OS 스레드가 논다"라는 등식이 깨진다.** 기다림의 비용이 OS 스레드 하나에서 **힙에 저장된 몇 KB짜리 객체**로 줄어들고, 그래서 가상 스레드는 수백만 개까지 만들 수 있다.

코드에서는 이렇게 바뀐다.

```java
// before: 스레드가 비싸니 개수를 정해놓고 아껴 쓰는 모델
ExecutorService pool = Executors.newFixedThreadPool(200);

// after: 작업마다 가상 스레드 하나 — 아낄 이유가 없으니 풀링 자체가 없다
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> {
        Member member = memberClient.get(id);   // 블로킹처럼 '보이지만' 캐리어는 안 묶인다
        return orderRepository.find(id);
    });
}
// try-with-resources로 감싼 이유: ExecutorService가 AutoCloseable이라 블록을 나갈 때
// 제출된 작업이 끝날 때까지 기다려 준다. 풀을 반납하는 게 아니라 "작업 완료를 기다린다"는 의미다.

// Spring Boot 3.2+ 라면 설정 한 줄로 톰캣이 요청마다 가상 스레드를 쓴다
// spring.threads.virtual.enabled=true
```

**가장 큰 가치는 코드 스타일을 바꾸지 않아도 된다는 점이다.** 리액티브처럼 코드를 뒤집지 않고, 지금까지처럼 순차적·블로킹 스타일로 쓰면 JVM이 알아서 논블로킹처럼 굴려 준다. 스택트레이스도, 디버거도, `try-catch-finally`도 그대로 살아 있다.

주의할 오해를 여기서 한 번 못 박아 두자. **가상 스레드는 처리 속도를 높이는 게 아니라 "대기 중 동시성"을 높이는 기술이다.** 요청 하나가 350ms 걸리던 것이 300ms가 되지는 않는다. CPU 연산 위주 작업에는 이득이 아예 없다 — 어차피 코어 수만큼만 동시에 돌 수 있으니까.

### 2-2. 스레드의 정체 — 콜 스택 + 실행 위치라는 "데이터"

여기서부터가 이 문서의 핵심 난관인 **Continuation**이다. 결론부터 말하면 "스택을 힙에 저장했다가 되살린다"인데, 이 문장이 손에 잡히려면 먼저 **스택이 무엇으로 이루어져 있는지**를 다시 확인해야 한다.

JVM 메모리 구조에서 정리했던 사실을 그대로 가져오자. **스레드가 메서드를 호출할 때마다 스택 프레임(stack frame)이 하나씩 쌓인다.** 프레임 안에 들어 있는 것은 세 가지다.

- **지역변수 테이블** — 기본형 값과 객체 참조(주소값)
- **피연산자 스택** — 계산 중간값을 올려두는 임시 공간
- **리턴 주소** — 이 메서드가 끝나면 호출한 쪽의 어느 줄로 돌아갈지

그러니 실행 중인 스레드의 상태란 결국 두 가지로 요약된다.

1. **콜 스택** — 지금까지 어떤 메서드를 타고 들어왔고, 각 단계의 지역 변수가 무엇인지
2. **실행 위치** — 지금 어느 명령어까지 실행했는지 (프로그램 카운터, 레지스터)

여기서 결정적인 통찰이 나온다. **콜 스택은 신비로운 무언가가 아니라 그냥 메모리 덩어리이고, "프로그램이 어디까지 진행됐는가"라는 정보 전체가 그 안에 데이터로 들어 있다.**

```
handleRequest()를 처리하다 getUser() 안에 들어와 있는 상태의 스택 (아래에서 위로 쌓인다)

  │ getUser() 프레임        │ ← 지금 여기 실행 중 (지역변수: userId=42, conn=0x7f30)
  │ handleRequest() 프레임  │   (지역변수: request=0x7f10, 리턴 주소: 137번째 줄)
  │ run() 프레임            │
  └────────────────────────┘
```

실행 상태가 데이터라면, **데이터는 저장했다가 복원할 수 있다.** 이게 가상 스레드의 이론적 근거 전부다.

그럼 가상 스레드의 이 데이터는 어디에 저장되는가 — **언제냐에 따라 두 곳을 오간다.**

| 가상 스레드의 상태 | 콜 스택이 사는 곳 |
|---|---|
| 실행 중 (캐리어에 mount됨) | **캐리어의 진짜 스택** — 캐리어 스택을 빌려 쓰며, 그 순간엔 평범한 스레드와 완전히 동일하게 동작 |
| 대기 중 (unmount됨) | **힙**의 객체 (JVM 내부에서 StackChunk라 부른다) |

즉 **가상 스레드는 자기만의 스택을 상시 보유하지 않는다.** 플랫폼 스레드처럼 태어날 때 2MB를 예약받는 게 아니라, 실행할 때만 캐리어의 스택을 빌려 쓰고 물러날 때는 쓴 만큼만 힙으로 챙겨 간다. **"쓴 만큼만"**이 비용 차이의 정체다.

### 2-3. freeze와 thaw — 스택과 힙을 나란히 놓고 본다

이제 실제로 옮겨지는 그림을 보자. 캐리어 #3 위에서 가상 스레드 V-42가 돌다가 블로킹을 만나는 상황이다.

**[1단계] mount 중 — V-42의 프레임이 캐리어의 진짜 스택 위에 쌓여 있다**

```
   캐리어 #3 의 스택 (OS가 준 진짜 스택)         힙
  ┌──────────────────────────────────┐      ┌────────────────────────────────┐
  │ read()          프레임           │      │ VirtualThread V-42 객체         │
  │ getMember()     프레임           │      │   stackChunk = null             │
  │ handleRequest() 프레임           │      │   (아직 얼려 둔 게 없다)        │
  │ ── 여기까지가 V-42의 프레임 ──   │      │                                 │
  │ 캐리어의 실행 루프 프레임        │      │ Member, Request … 일반 객체들   │
  └──────────────────────────────────┘      └────────────────────────────────┘
```

이 순간 V-42는 평범한 스레드와 **기계어 수준에서 완전히 같다.** 캐리어 스택 위에서 그냥 돌 뿐이다.

**[2단계] freeze — V-42의 프레임을 힙으로 복사해 옮기고, 캐리어를 놓아준다**

```
   캐리어 #3 의 스택                           힙
  ┌──────────────────────────────────┐      ┌────────────────────────────────┐
  │                                  │      │ VirtualThread V-42 객체         │
  │        (V-42의 프레임이           │      │   stackChunk ──┐                │
  │         전부 걷혀 비었다)         │  ──► │                ▼                │
  │                                  │ 복사 │  ┌─ StackChunk (평범한 자바 객체)│
  │ 캐리어의 실행 루프 프레임        │      │  │  read() 프레임                │
  └──────────────────────────────────┘      │  │  getMember() 프레임           │
        캐리어 #3 은 자유다 —               │  │  handleRequest() 프레임       │
        곧바로 V-43 을 태울 수 있다          │  └───────────────────────────────│
                                            └────────────────────────────────┘
```

**freeze(얼리기)**란 이 복사 작업이다. 실행 중이던 프레임들을 힙의 객체로 옮겨 담고, 캐리어 스택은 원래대로 되감아(rewind) 캐리어에서 내려온다. 옮겨진 뒤의 V-42는 **힙에 사는 평범한 자바 객체 몇 KB**일 뿐이다.

**[3단계] thaw — 다시 캐리어에 올려 복원한다**

```
   캐리어 #5 의 스택 (아무 캐리어나 상관없다)     힙
  ┌──────────────────────────────────┐      ┌────────────────────────────────┐
  │ read()          프레임      ◄────┼──────┼── StackChunk 에서 되살림        │
  │ getMember()     프레임           │ 복원 │                                 │
  │ handleRequest() 프레임           │      │ VirtualThread V-42              │
  │ 캐리어의 실행 루프 프레임        │      │   stackChunk = null (비웠다)    │
  └──────────────────────────────────┘      └────────────────────────────────┘
       yield() 를 호출했던 다음 줄부터 재개
```

**thaw(녹이기)**는 그 반대다. 힙의 StackChunk를 다시 캐리어 스택 위에 펼쳐 놓으면 V-42는 멈췄던 그 자리에서 그대로 이어 달린다. **되살아난 캐리어가 #3이 아니라 #5여도 아무 상관 없다** — 데이터를 옮긴 것이므로 어느 실행대에 올려도 똑같이 복원된다.

여기까지가 **Continuation(이어가기)**이라는 이름의 뜻이다. "멈춘 지점부터 이어서 실행할 수 있게 통째로 챙겨 둔 실행 상태"라는 의미다.

비유하면 **게임 세이브 파일**이다. 진행 상태 전부를 파일로 저장해 두면 나중에, 심지어 **다른 컴퓨터에서도** 이어서 할 수 있다. 세이브 파일이 게임기 본체에 잠겨 있었다면 게임 수만큼 본체가 필요했겠지만, 이동식 카드가 되는 순간 본체 8대로 게임 100만 개를 이어 할 수 있게 된다.

"실행 위치"는 왜 따로 백업하지 않는지도 짚고 가자. freeze는 아무 데서나 일어나지 않고 **항상 `Continuation.yield()`라는 정해진 메서드 호출 지점에서** 일어난다. 메서드를 호출한 지점이라는 것은 곧 **"돌아올 위치가 이미 스택 프레임의 리턴 주소로 기록돼 있다"**는 뜻이다. 그래서 CPU 레지스터를 따로 챙길 필요가 없다.

이 점이 커널의 방식과 결정적으로 다르다. 커널은 언제든 스레드를 강제로 끊을 수 있고(선점, preemption) 그래서 끊긴 순간의 레지스터를 전부 저장해야 한다. 가상 스레드는 **본인이 정해진 지점에서 스스로 물러난다** — 이런 방식을 **협조적(cooperative) 스케줄링**이라 부른다. 기절한 사람의 기억을 꺼내는 게 아니라 **잠들기 전에 본인이 일기를 써 두는** 방식이다.

### 2-4. 블로킹 호출 한 번의 타임라인 — 플랫폼 스레드 vs 가상 스레드

애플리케이션 코드가 쓰는 문장은 양쪽 모두 똑같다.

```java
socket.getInputStream().read(buf);   // 응답 도착까지 300ms 걸린다고 하자
```

이 한 줄 아래에서 벌어지는 일이 완전히 다르다.

```
[플랫폼 스레드]  톰캣 워커 #7 (= OS 스레드 #7)

 t=0ms     handleRequest 시작 — 워커 #7 점유
 t=1ms     read() 호출 → 블로킹 시스템 콜로 커널에 진입
           → 커널이 #7을 '대기' 상태로 재운다
 t=1~300ms ░░░░░░░ 299ms 동안 OS 스레드 #7은 아무것도 못 한다 ░░░░░░░
 t=300ms   데이터 도착 → 커널이 #7을 깨움 → 다음 줄부터 실행
           (깨어날 때 컨텍스트 스위칭 비용 + 캐시 오염을 한 번 치른다)

 결론: 이 299ms 동안 서버의 동시 처리 능력에서 워커 하나가 통째로 빠져 있었다.
```

```
[가상 스레드]  캐리어 #3 (OS 스레드 8개 중 하나) 위의 V-42

 t=0ms     V-42가 캐리어 #3에 mount, handleRequest 시작
 t=1ms     read() 호출 → JDK 내부 구현이 실행된다 (아직 시스템 콜 안 함, 그냥 자바 코드)
           ① "지금 가상 스레드 위인가?" 확인 → 맞다
           ② 소켓을 논블로킹 모드로 epoll에 등록 — "데이터 오면 알려줘", 즉시 리턴
           ③ Continuation.yield() 호출 → freeze → 캐리어 #3에서 unmount
 t=1ms     캐리어 #3, 곧바로 V-43 을 태운다
 t=1~300ms 캐리어 #3 은 V-43, V-44, V-45 … 를 쉬지 않고 처리한다 (한순간도 안 잔다)
 t=300ms   데이터 도착 → epoll을 감시하던 JVM 내부 poller 스레드가 알림 수신
           → V-42를 JVM 스케줄러 대기열에 재등록
 t=301ms   비어 있는 캐리어(#5일 수도 있다)가 V-42를 thaw
           → yield() 다음 줄부터 재개 → 데이터가 이미 와 있으니 논블로킹 read로 즉시 읽고 리턴

 결론: 299ms 동안 OS 스레드는 단 하나도 놀지 않았다. 묶여 있던 것은 힙의 객체 몇 KB뿐이다.
```

여기서 **epoll**이 무엇인지 정의하고 가자. **리눅스 커널이 제공하는 "I/O 이벤트 알림 서비스"**다. 블로킹 방식이 주문마다 직원 한 명이 주방 앞에 서서 음식을 기다리는 것이라면, epoll은 **진동벨**이다. "이 소켓 1만 개 등록해 둘게, 데이터 도착한 놈 생기면 알려줘"라고 커널에 부탁해 두면 **스레드 하나가 소켓 1만 개를 감시**할 수 있다. macOS는 kqueue, 윈도우는 IOCP가 같은 역할을 한다.

정리하면, Loom의 결정적 아이디어는 이것이다. **가상 스레드는 블로킹 시스템 콜에 아예 들어가지 않는다.** 잠든 다음에 밖에서 상태를 꺼내 오는 게 아니라, 잠들 상황이 오면 **아직 멀쩡히 실행 중인 스레드가 자기 손으로 자기 스택을 힙에 복사하고 물러난다.**

캐리어에 대한 오해도 여기서 걷어내자. **캐리어는 마법이 아니다.** OS 입장에서 보면 `new Thread()`로 만든 것과 아무 차이 없는 평범한 OS 스레드이고, 특별한 커널 기능도 쓰지 않는다. 다만 그 스레드가 실행하는 **프로그램이** "대기열에서 얼려진 가상 스레드 꺼내기 → thaw → 실행 → yield하면 다음 것 꺼내기"라는 루프일 뿐이다. 목수 8명이 의뢰 10만 건을 처리하는 것은 작업대가 마법이어서가 아니라 "재료를 기다리게 된 작업은 하다 만 상태 그대로 서랍에 넣고 다른 의뢰를 꺼낸다"는 규칙 덕분이다. **마법은 작업대(캐리어)가 아니라 서랍(Continuation의 freeze/thaw)에 있다.**

### 2-5. 왜 과거엔 못 했나 — 장벽은 "메모리 소유"가 아니라 "개입 타이밍"이었다

흔한 오해가 하나 있다. "스택이 OS 소유라서 JVM이 못 읽는다" — **아니다.** OS 스레드의 스택은 **내 프로세스의 주소 공간 안에 있는 평범한 유저 메모리**이고, JVM은 언제든 읽고 쓸 수 있다.

OS가 진짜로 쥐고 있던 것은 메모리가 아니라 **두 가지 통제권**이다.

1. **스케줄링 권한** — 스레드를 언제 재우고 언제 깨울지는 커널만 결정한다.
2. **끊긴 순간의 실행 위치** — 커널이 선점으로 스레드를 끊으면 레지스터와 프로그램 카운터는 커널의 컨텍스트 저장소로 들어간다. JVM은 임의 시점의 이 정보에 접근할 수 없다.

그래서 과거의 진짜 장벽은 이것이었다. **`read()`를 호출하면 곧장 블로킹 시스템 콜로 들어가고, 잠드는 위치가 커널 안이라 JVM이 끼어들 지점이 0곳이었다.** "잠깐, 재우지 말고 그 스택만 나한테 줘"라고 말할 타이밍 자체가 없었던 것이다.

Loom이 한 일은 이 장벽을 뚫은 게 아니라 **장벽 앞에서 방향을 튼 것**이다. 커널에 들어간 뒤에 꺼내려 하지 말고, **애초에 들어가지 않는다.** 그리고 그게 가능한 이유는 시스템 콜 직전의 경로 — `Socket`, `InputStream`, `Thread.sleep`, `BlockingQueue`, JDBC 아래의 소켓 — 가 전부 **JDK가 소유한 자바 코드**이기 때문이다.

**1:1을 깬 본질은 "실행 상태의 소유권" 이동이다.** 소유권이란 "멈춘 작업을 이어가는 데 필요한 데이터를 누가 쥐고 있고, 재개 시점을 누가 결정하는가"를 말한다.

- 플랫폼 스레드가 블로킹하면 그 순간의 실행 상태는 **커널의 컨텍스트 저장소**에 들어가고, 깨우는 시점도 커널만 결정한다. 그 작업을 이어갈 수 있는 유일한 존재가 바로 그 OS 스레드가 된다 — 그래서 자바 스레드 100만 개를 원하면 OS 스레드도 100만 개가 필요했다(1:1 강제).
- 가상 스레드는 멈춘 상태가 **힙의 평범한 자바 객체**라서 아무 OS 스레드 위에서나 복원할 수 있는 **이동식 데이터**가 된다. 실행 상태 100만 개를 OS 스레드 8개가 돌려가며 재생할 수 있다(M:N).

### 2-6. 왜 JVM만 이걸 할 수 있나 — GC가 쓰던 능력의 재활용

스택 프레임을 힙으로 복사하려면 **스택 안에 뭐가 어디 있는지 완벽히 알아야** 한다. 어떤 4바이트가 `int` 값이고 어떤 4바이트가 객체를 가리키는 참조인지 구분하지 못하면, 옮긴 뒤에 GC가 그 참조를 추적하지 못해 살아 있는 객체를 회수해 버린다.

JVM은 이 정보를 이미 갖고 있다. **모든 프레임을 자기가 만들었고, 각 칸이 무엇인지 기록한 메타데이터를 들고 있다** — GC가 스택을 훑으며 살아 있는 참조를 찾을 때 쓰던 바로 그 능력이다. 그래서 힙의 StackChunk로 옮긴 뒤에도 GC가 그 안의 참조를 정상적으로 추적한다.

반면 **C로 컴파일된 네이티브(JNI) 프레임은 JVM이 내부 구조를 모른다.** 게다가 C 코드는 스택 주소 자체를 포인터로 들고 있을 수 있어서, 프레임을 다른 곳으로 옮기는 순간 그 포인터가 엉뚱한 곳을 가리키게 된다. **네이티브 프레임이 스택에 끼어 있으면 얼릴 수 없다** — 이것이 pinning의 근본 원인 하나다(3-1절).

또 하나. 블로킹을 "epoll 등록 + yield"로 바꿔치기하려면 그 경로가 전부 JDK 진영의 코드여야 한다고 했는데, 뒤집어 말하면 **블로킹이 일어나는 JDK의 모든 지점을 재작성해야 했다**는 뜻이다. 이것이 Loom이 6년(2017~2023) 걸린 가장 큰 이유다.

### 2-7. 역할 분담 — 만드는 건 아무나, 내리는 건 본인, 올리는 건 캐리어, 깨우는 건 poller

먼저 **만드는 것**은 아무 스레드나 한다. `Thread.ofVirtual().start()` 같은 생성 API를 호출한 스레드가 만든다. Spring Boot에서 `spring.threads.virtual.enabled=true`를 켜면 톰캣 내부 스레드가 요청마다 이걸 호출해 준다.

생성의 실체는 **커널 시스템 콜 없이 힙에 VirtualThread 객체 하나 할당 + 스케줄러 대기열 등록**이 전부다. 플랫폼 스레드 생성이 커널에 `clone` 시스템 콜을 하고 스택 몇 MB를 예약하는 것과 달리 **객체 `new` 수준으로 싸다** — "요청마다 만들고 버리는" 모델이 성립하는 근거가 여기 있다.

만들어진 뒤의 mount/unmount를 지휘하는 별도의 "관리자 스레드"는 없다. 역할이 셋으로 나뉜다.

1. **freeze + unmount → 가상 스레드 본인.** 블로킹 직전, 아직 멀쩡히 실행 중인 가상 스레드가 `Continuation.yield()`를 실행하며 자기 스택을 힙에 복사하고 스스로 물러난다. 외부의 누가 떼어 내는 게 아니다.
2. **다음 가상 스레드 mount → 캐리어 본인.** 캐리어(ForkJoinPool의 워커)가 도는 코드가 곧 무한 루프다: "대기열에서 가상 스레드 하나 꺼냄 → thaw → 실행 → 걔가 yield하거나 끝나면 → 다시 꺼냄". mount는 캐리어가 자기 일감을 집어 드는 행위 그 자체다.
3. **I/O 끝난 가상 스레드를 대기열에 재등록 → JVM 내부 poller 스레드.** epoll을 감시하다가 "데이터 도착" 알림을 받으면, 얼려져 있던 해당 가상 스레드를 스케줄러 대기열에 다시 넣는다.

### 2-8. 왜 한 번 버렸다가 돌아왔는가 — 그린 스레드의 실패와 부활

이 아이디어는 새것이 아니다. **자바 1.0~1.2 시절 "그린 스레드(green threads)"라는 이름으로 정확히 이 발상이 있었다.** OS 스레드 하나 위에서 JVM이 여러 자바 스레드를 스케줄링하는 방식, 즉 **M:1**이다. 1.3 즈음 이것을 걷어내고 OS 스레드 1:1로 갈아탔다. 버린 이유가 셋이다.

1. **멀티코어를 못 썼다.** OS 스레드 *하나* 위의 다중화(M:1)라서 코어가 몇 개든 하나만 쓸 수 있었다. 당시는 막 SMP(다중 프로세서) 서버가 퍼지던 시기라 치명적이었다.
2. **블로킹 시스템 콜 하나가 전체를 마비시켰다.** 그린 스레드 하나가 파일 읽기로 블로킹되면 유일한 OS 스레드가 잠들어 나머지 전부가 정지했다. 피하려면 모든 I/O를 논블로킹으로 감싸야 하는데, **당시 OS에는 epoll/kqueue 같은 논블로킹 I/O 인프라가 없거나 미성숙했다.**
3. **OS 스레드가 좋아졌다.** 리눅스 NPTL 등 커널 스레드 구현이 빨라지면서 "그냥 OS에 맡기는 게 단순하고 충분히 빠르다"가 당시로선 합리적인 결론이었다.

즉 **개념이 없어서가 아니라, 구현할 기반 기술이 없었고 당시 워크로드에선 필요도 크지 않았다.** 가상 스레드는 실패 원인이 전부 해소된 형태로 돌아온 부활이다.

| 그린 스레드가 실패한 이유 | 가상 스레드에서 해소된 방식 |
|---|---|
| M:1이라 멀티코어를 못 씀 | **M:N** — 캐리어를 코어 수만큼 두고 work-stealing 스케줄러(ForkJoinPool)로 분배 |
| 블로킹 콜 하나가 전체 마비 | **epoll/kqueue + 자바 NIO** 위에서 JDK 블로킹 API의 겉모습은 그대로 두고 속만 재작성 |
| (기술 부족) | 힙에 얼린 스택의 GC 추적, JIT 프레임 freeze/thaw 등 **Continuation을 감당할 JVM 기술**이 성숙 |
| 필요가 크지 않았음 | 마이크로서비스 시대에 **I/O 대기형 워크로드가 폭증**했고, Go의 고루틴이 M:N 모델이 실전에서 통함을 증명 |

### 2-9. 오버헤드는 없나 — "코드가 늘었으니 느려진 것 아닌가"

가상 스레드용 분기와 freeze/thaw 코드가 추가된 것은 사실이다. JDK 블로킹 API 내부가 개념적으로 이렇게 바뀌었다.

```java
// JDK 내부 read()의 개념적 모습
if (현재 스레드가 가상 스레드인가?) {
    소켓을 epoll에 등록;
    Continuation.yield();     // freeze하고 물러남
    // ... 깨어나면 여기부터 재개 — 데이터가 와 있으니 논블로킹 read
} else {
    기존 블로킹 시스템 콜;      // 플랫폼 스레드는 예전 경로 그대로
}
```

프록시처럼 앞뒤로 로직을 덧댄 게 맞다. 단, 덧댄 위치가 애플리케이션 코드가 아니라 **JDK 라이브러리 내부**다. 그래서 비용이 붙는 위치를 정확히 봐야 한다.

**CPU로 계산하는 동안엔 오버헤드가 0이다.** mount된 가상 스레드는 캐리어 스택 위에서 평범한 스레드와 똑같은 기계어로 돈다. 명령어마다 붙는 세금 같은 건 없다.

**비용은 블로킹 지점에만 붙는다.** 분기 체크 한 번과 freeze/thaw 복사다. 그런데 여기서 비교 대상을 정확히 잡아야 한다 — **플랫폼 스레드도 블로킹이 공짜가 아니다.** OS 컨텍스트 스위칭(커널 진입, 레지스터 저장, CPU 캐시 오염)이라는 비용을 치르며, freeze/thaw는 이와 비슷하거나 오히려 싸다.

정리하면, 대기가 전혀 없는 단일 작업이라면 이득은 없고 미세한 손해가 있을 수 있다. 이 기술은 요청 하나를 빠르게 하는 게 아니라 **"동시에 기다릴 수 있는 개수"를 폭증시키는 것**이다.

## 3. 실무 함정 — pinning, 트랜잭션, ThreadLocal, 도입 체크포인트

### 3-1. Pinning — 왜 캐리어에서 못 내려오는가

가상 스레드의 마법은 "블로킹 시 캐리어에서 내린다"인데, **내리지 못하는 경우**가 있다. 이걸 **pinning(고정, 못박힘)**이라고 한다. 가상 스레드가 캐리어에 못박히면 그 블로킹이 끝날 때까지 **캐리어(OS 스레드)가 통째로 잠든다** — 플랫폼 스레드 시절로 퇴행하는 것이다.

중요한 건 "왜 못 내려오는가"에 근거를 댈 수 있어야 한다는 점이다. 원인이 둘인데 성격이 완전히 다르다.

#### 원인 1: `synchronized` — 모니터가 OS 스레드에 묶여 있다 (JDK 21~23)

먼저 `synchronized`가 실제로 무엇을 하는지 짚자. 자바의 모든 객체에는 **모니터(monitor)**라는 잠금 장치가 하나씩 딸려 있고, `synchronized`는 그 모니터를 획득했다가 반납하는 문법이다. 모니터에는 최소한 두 가지가 기록된다 — **지금 누가 들어와 있는지(소유자)**와 **몇 번 중첩해 들어왔는지(재진입 횟수)**.

문제는 **JDK 21의 HotSpot이 이 소유자를 OS 스레드 단위로 기록한다**는 데 있다. 잠금 기록(락 레코드)도 그 OS 스레드의 스택 프레임 안에 자리 잡는다.

이제 freeze를 시도한다고 상상해 보자.

```
[JDK 21~23에서 synchronized 안의 블로킹을 freeze 한다면]

  캐리어 #3                                     모니터의 장부
  ├─ V-42가 lock 객체의 모니터를 획득           소유자 = 캐리어 #3
  ├─ synchronized 블록 안에서 HTTP 호출 (300ms)
  │
  └─ 만약 여기서 V-42의 프레임만 힙으로 옮기고
     캐리어 #3에 V-43을 태운다면?
                                                 소유자 = 캐리어 #3  ← 그대로 남는다
     그런데 캐리어 #3은 이제 V-43을 실행 중이다.
     ⇒ V-43이 같은 lock에 들어가려 하면 "어? 내가 이미 소유자네" 하고 통과해 버린다.
     ⇒ 락 소유자가 어긋난다 = 상호 배제가 깨진다 = 데이터가 깨진다.
```

**JVM은 이 어긋남을 만드는 대신, 옮기지 않는 쪽을 택했다.** 프레임을 캐리어 스택에 그대로 둔 채 캐리어를 붙잡고 블로킹한다. 그래서 "핀 된다"는 표현을 쓴다.

```java
// 1. synchronized 블록/메서드 안에서 블로킹 — JDK 21~23에서 핀 된다
synchronized (lock) {
    String result = httpClient.send(request);  // 이 300ms 동안 캐리어가 통째로 묶인다
}
```

#### 원인 2: 네이티브(JNI) 프레임 — JVM이 옮길 수가 없다

두 번째 원인은 2-6절에서 이미 깔아 둔 것이다. **네이티브 프레임은 JVM이 내부 구조를 모르는 C 스택이라 애초에 얼릴 수 없다.** 어떤 칸이 참조인지 알 수 없어 GC 추적이 불가능하고, C 코드가 스택 주소를 포인터로 들고 있을 수 있어 옮기는 순간 깨진다. 게다가 네이티브 코드의 블로킹은 커널로 직행하므로 "epoll 등록 + yield"로 바꿔치기할 지점도 없다.

**이 원인은 구조적이라 어떤 JDK 버전에서도 사라지지 않는다.** JDK 24 이후에도 그대로 남는다.

#### 왜 위험한가 — 캐리어는 코어 수만큼뿐이다

캐리어는 기본적으로 CPU 코어 수만큼만 존재한다(예: 8개). 가상 스레드 8개가 `synchronized` 안에서 긴 I/O에 핀 되면, **실행대 전원이 묶여서 대기열의 가상 스레드 수만 개가 전부 진행을 멈춘다.**

JEP 444(가상 스레드)도 이 점을 명시한다 — 핀이 잦고 오래 지속되면 캐리어를 붙잡아 애플리케이션의 확장성을 해친다. 여기에 커넥션 풀 대기 같은 것이 얽히면 **데드락**으로도 이어질 수 있다. 실제로 도입 초기에 커넥션 풀이나 낡은 JDBC 드라이버 내부의 `synchronized`가 문제로 지적됐다(구버전 MySQL Connector/J가 대표 사례로 거론됐다).

#### 회피 방법 (JDK 21~23 기준)

```java
// before: synchronized 안에서 I/O — 캐리어가 못박힌다
private final Object lock = new Object();

public void call() {
    synchronized (lock) {
        callExternalApi();          // 300ms 동안 캐리어 하나가 통째로 잠든다
    }
}

// after: ReentrantLock — 잠금 대기 중에도, 잠금 보유 중에도 unmount 가능하다
private final ReentrantLock lock = new ReentrantLock();

public void call() {
    lock.lock();                    // 소유자를 '자바 객체 안의 필드'로 기록하므로
                                    // 프레임을 힙으로 옮겨도 장부가 어긋나지 않는다
    try {
        callExternalApi();
    } finally {
        lock.unlock();              // synchronized와 달리 자동 반납이 없다 — finally가 필수다
    }
}
```

`ReentrantLock`이 괜찮은 이유가 정확히 원인 1의 뒤집힘이다. **`ReentrantLock`은 소유자를 힙의 자바 객체 필드에 기록**하므로, 가상 스레드가 캐리어를 갈아타도 소유권이 따라다닌다.

체크리스트로 정리하면 이렇다.

- **오래 블로킹하는 구간을 감싸는 `synchronized`만** `ReentrantLock`으로 교체한다. 짧은 인메모리 연산만 보호하는 `synchronized`는 실질적으로 문제가 없다 — 무조건 전부 바꾸는 것은 과잉이다.
- 의존 라이브러리(JDBC 드라이버, 커넥션 풀, HTTP 클라이언트)가 내부에서 `synchronized + I/O`를 하는지 점검한다. 소스를 다 뒤질 수는 없으니, 실제로는 아래의 탐지 도구로 잡는 편이 확실하다.

#### 버전 범위 — JDK 24의 JEP 491이 바꾼 것 (가산점 포인트)

**`synchronized`로 인한 pinning은 JDK 24의 JEP 491("Synchronize Virtual Threads without Pinning")에서 해소됐다.** 모니터 소유권을 OS 스레드가 아니라 **가상 스레드 단위로 추적**하도록 구현을 바꿔서, `synchronized` 블록 안에서 블로킹해도, `Object.wait()`로 대기해도 캐리어에서 내려올 수 있게 됐다.

그래서 이 주제는 반드시 **버전을 명시해서** 말해야 한다.

| | JDK 21~23 | JDK 24 이후 |
|---|---|---|
| `synchronized` 안 블로킹 | **핀 된다** — `ReentrantLock`으로 교체가 필요 | **핀 되지 않는다** — 교체 부담이 사라짐 |
| 네이티브(JNI)·VM 프레임 | 핀 된다 | **여전히 핀 된다** (구조적 제약) |
| 탐지 도구 | `-Djdk.tracePinnedThreads=full` 또는 JFR `jdk.VirtualThreadPinned` | **`-Djdk.tracePinnedThreads`는 제거됐다.** JFR `jdk.VirtualThreadPinned` 이벤트로 본다 |

`-Djdk.tracePinnedThreads`가 없어진 이유는 JEP 491이 밝혀 두었다 — 진단 옵션으로서 문제가 많았고 `synchronized` 핀이 사라진 뒤로는 쓸모도 없어졌다는 것이다. 대신 JFR의 `jdk.VirtualThreadPinned` 이벤트가 확장되어, **네이티브/VM 프레임 때문에 핀 된 상태에서 park하거나 모니터를 기다리거나 `Object.wait()` 하는 경우**를 기록한다. 즉 **JDK 24 이후 핀 조사는 JFR이 정식 경로**다.

여기서 한 걸음 더 나가면 시니어 답변이 된다. **핀이 사라졌다고 `synchronized`를 마음대로 써도 되는 것은 아니다.** JEP 491이 푼 것은 "캐리어가 묶이는 문제"일 뿐, **잠금 자체의 직렬화는 그대로 남는다.** 300ms짜리 외부 호출을 감싼 `synchronized`는 여전히 한 번에 하나씩만 통과시키므로, 가상 스레드가 1만 개여도 그 구간의 처리량은 초당 3건이다. 캐리어가 안 묶이니 장애 양상이 "서버 전체 멈춤"에서 "그 구간만 극심한 대기"로 바뀔 뿐이다.

### 3-2. `@Transactional` 안에서 외부 API 호출 — 가상 스레드가 풀어 주지 못하는 문제

이 절이 이 문서에서 가장 실무적인 대목이다. **가상 스레드가 값싸게 만든 것은 "자바 스레드"이지 "DB 커넥션"이 아니다.**

#### 원래 문제 — 가상 스레드와 무관하게 존재한다

```java
@Transactional
public void placeOrder(OrderRequest req) {
    orderRepository.save(order);          // 이 시점에 이미 DB 커넥션을 하나 쥐고 있다
    paymentClient.approve(req);           // 외부 API 300ms — 이 동안에도 커넥션은 반납되지 않는다
    orderRepository.update(order);
}
```

`@Transactional` 메서드는 시작할 때 커넥션 풀(HikariCP)에서 **DB 커넥션을 하나 꺼내 메서드가 끝날 때까지 쥐고 있다.** 트랜잭션이라는 개념 자체가 "하나의 커넥션 위에서 열리고 닫히는 것"이기 때문에 중간에 반납할 방법이 없다.

그래서 외부 API를 기다리는 300ms 동안 그 커넥션은 **아무 쿼리도 실행하지 않으면서 점유돼 있다.** HikariCP 기본 풀 크기는 10개뿐이다. "트랜잭션 안에서 외부 API 콜 금지"가 정석인 이유가 이것이다.

#### 가상 스레드를 도입하면 — 병목이 이동하며 증폭된다

대기 중 점유하는 자원이 **두 개**라는 것을 구분하는 게 핵심이다.

| 대기 중 점유하는 자원 | 플랫폼 스레드 | 가상 스레드 |
|---|---|---|
| 스레드 | 톰캣 워커 1개가 묶인다 | **해결됨** — unmount되어 캐리어는 다른 일을 한다 |
| DB 커넥션 | 1개가 묶인다 | **그대로 묶인다** — 커넥션은 스레드가 아니라 트랜잭션에 묶인 자원이다 |

타임라인으로 나란히 보면 차이가 분명해진다.

```
[플랫폼 스레드]  요청 하나
  워커 #7      ████████████████████████████  350ms 내내 묶임
  DB 커넥션    ████████████████████████████  350ms 내내 묶임

[가상 스레드]  요청 하나
  캐리어 #3    ██░░░░░░░░░░░░░░░░░░░░░░░░██  ░ 구간엔 다른 요청을 처리한다 (해방)
  DB 커넥션    ████████████████████████████  350ms 내내 묶임  ← 아무것도 안 바뀐다
```

이제 숫자로 확인해 보자. 커넥션 풀을 실무에서 흔한 20개로 올려 뒀다고 하고, 트랜잭션 하나가 커넥션을 350ms(외부 API 300ms + 쿼리 50ms) 점유한다고 하자.

1. 커넥션 하나가 1초에 처리할 수 있는 트랜잭션 = `1 / 0.35 ≈ 2.86`건
2. 풀 전체의 처리량 상한 = `20 × 2.86 ≈ 57 req/s` — **스레드를 몇 개로 늘리든 이 값은 변하지 않는다.**

여기에 초당 1,000건이 들어온다고 하면 이렇게 갈린다.

```
[플랫폼 스레드 200개]
  동시에 이 메서드에 진입할 수 있는 요청 = 최대 200건 (워커 수가 상한)
  → 커넥션을 기다리는 줄은 아무리 길어야 180건
  → 대기 시간 = 180 / 57 ≈ 3.2초
  → HikariCP 기본 connectionTimeout 30초 안이므로, 느리지만 죽지는 않는다
  → 201번째 요청부터는 톰캣 수락 큐에서 대기한다 (아직 커넥션을 요구하지도 않는다)

[가상 스레드]
  동시에 이 메서드에 진입하는 요청 = 들어오는 대로 전부 (상한이 사라졌다)
  → 초당 1,000건이 들어오고 57건만 빠지므로, 대기열이 매초 943건씩 쌓인다
  → 30초 뒤 대기 중인 요청 ≈ 28,000건
  → 대기 시간이 30초를 넘는 순간부터 전면 실패:
     "Connection is not available, request timed out after 30000ms"
```

**역설이 여기 있다.** 플랫폼 스레드 200개라는 제약은 사실 **공짜로 얻고 있던 부하 제한기(admission control)**였다. 톰캣이 "동시에 200건까지만"이라고 막아 주는 동안 커넥션 풀도 그 이상의 경쟁을 겪지 않았던 것이다. 가상 스레드는 그 제한기를 걷어낸다. 병목이 "스레드 부족"에서 "커넥션 부족"으로 **이동**하는 데 그치지 않고, 대기 행렬이 무한정 길어지면서 **피해가 증폭된다.**

한 문장으로 요약하면 이렇다. **가상 스레드는 요청을 더 많이 "받게" 해 줄 뿐, 더 많이 "처리하게" 해 주지 않는다.** 하류(DB, 외부 API)의 처리량이 그대로면 늘어난 것은 대기 행렬뿐이다.

#### pinning과도 얽힌다

**JDK 21~23 기준**으로는 트랜잭션 경로에 JDBC 드라이버나 커넥션 풀 내부의 `synchronized`가 끼어 있을 수 있다. 커넥션 하나를 여러 스레드가 동시에 쓰지 못하게 막는 가장 자연스러운 구현이 `synchronized`라, 드라이버들이 오랫동안 그렇게 만들어져 왔다. 이 경우 DB I/O 대기 중에 unmount조차 못 하고 캐리어가 핀 된다.

그래서 가상 스레드 + `@Transactional` 조합을 검토할 때는 **드라이버·커넥션 풀 버전 점검**과 **JFR `jdk.VirtualThreadPinned` 이벤트 감시**가 체크리스트에 들어간다. JDK 24 이후라면 이 걱정은 크게 줄어든다.

#### 올바른 설계는 가상 스레드가 있든 없든 동일하다

답은 하나다. **외부 API 콜을 트랜잭션 밖으로 뺀다.**

```java
// before: 하나의 트랜잭션이 외부 호출을 품고 있다 — 커넥션을 350ms 점유
@Transactional
public void placeOrder(OrderRequest req) {
    orderRepository.save(order);
    paymentClient.approve(req);           // 300ms 동안 커넥션이 놀면서 묶여 있다
    orderRepository.update(order);
}

// after: 트랜잭션 경계를 잘게 쪼갠다 — 커넥션 점유는 쿼리 시간만큼만
public void placeOrder(OrderRequest req) {
    orderService.saveOrder(order);        // @Transactional — 커넥션 점유 25ms
    paymentClient.approve(req);           // 트랜잭션 밖 — 커넥션을 안 쥔 채로 300ms 대기
    orderService.confirmOrder(order);     // @Transactional — 커넥션 점유 25ms
}
```

이렇게 바꾸면 커넥션 점유 시간이 350ms에서 50ms로 줄어, 같은 풀 20개로 `20 / 0.05 = 400 req/s`를 감당하게 된다. **가상 스레드보다 이 변경의 효과가 훨씬 크다는 점**을 짚을 수 있어야 한다.

다만 공짜는 아니다. **트랜잭션을 쪼갠 만큼 원자성이 깨지므로**, 중간 실패 시 보상 처리나 상태 기반 재시도 같은 정합성 설계가 반드시 따라와야 한다.

### 3-3. ThreadLocal — 동작은 안전한데 사용 패턴이 깨진다

이 절의 논지를 먼저 못 박자. **가상 스레드에서 ThreadLocal은 "고장 나지" 않는다. 고장 나는 것은 우리가 ThreadLocal을 써 온 방식이다.**

#### 3-3-1. 값은 캐리어가 아니라 "가상 스레드 객체"에 붙는다

먼저 안심할 근거부터. ThreadLocal은 값을 자기 안에 담고 있는 게 아니다. 실제 값은 **각 `Thread` 객체 안의 `ThreadLocalMap`**에 저장되고, ThreadLocal 인스턴스는 그 맵을 여는 **키** 역할만 한다.

```java
// ThreadLocal.get()이 내부적으로 하는 일 (개념적으로)
Thread t = Thread.currentThread();   // ① 지금 실행 중인 스레드가 누구인가?
return t.threadLocals.get(this);     // ② '그 스레드의' 맵에서 this를 키로 꺼낸다
```

그러니 질문은 ①로 좁혀진다. 가상 스레드가 캐리어 위에서 도는 동안 `currentThread()`는 누구를 돌려주는가 — **가상 스레드다.** mount하는 순간 JVM이 "현재 스레드" 정체성을 가상 스레드로 바꿔 끼우고, 캐리어 자신의 ThreadLocal은 그동안 가려져 아무도 보지 못한다.

```
캐리어 #3 (OS 스레드)
 ├─ 캐리어 자신의 threadLocals  ← mount 동안 가려져 있다
 │
 └─ 지금 올라탄 가상 스레드 V-42 (힙에 사는 객체)
      └─ V-42의 threadLocals   ← ThreadLocal.get()이 실제로 뒤지는 곳
```

가상 스레드의 실체는 힙 객체이므로(2-2절), 이 맵도 unmount 시 얼려진 스택과 함께 힙에 남아 **캐리어를 갈아타도 가상 스레드를 따라다닌다.** 만약 값이 캐리어에 붙어 있었다면 같은 캐리어를 번갈아 쓰는 가상 스레드 수만 개가 서로의 값(남의 `SecurityContext`!)을 봤을 것이다. 그런 일은 일어나지 않는다.

그래서 Spring Security의 `SecurityContext`, 로깅 MDC 같은 ThreadLocal 기반 프레임워크도 **"요청 하나 = 가상 스레드 하나"** 구도에서 그대로 동작한다.

덧붙여, 톰캣 스레드 풀 시절의 가장 무서운 사고였던 **"remove()를 안 해서 이전 요청의 인증 정보가 다음 사용자에게 보이는" 오염도 사라진다.** 그 사고는 스레드가 풀에서 **재사용**되기 때문에 생겼는데, 가상 스레드는 요청마다 새로 만들어지고 끝나면 버려지므로 재사용 자체가 없다. 요청이 끝나면 스레드와 맵과 값이 함께 회수된다.

#### 3-3-2. 그런데 왜 "주의"인가 — 스레드당 캐싱 패턴의 전제가 무너진다

문제는 다른 데서 터진다.

```java
// 플랫폼 스레드 풀 시절엔 합리적이었던 패턴
private static final ThreadLocal<SimpleDateFormat> FORMAT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
```

이 패턴은 "`SimpleDateFormat`은 thread-safe하지 않으니 스레드마다 하나씩 만들어 두고 계속 재사용하자"는 발상이다. **이게 이득이 되려면 전제가 두 개 필요하다.** 그리고 가상 스레드에서는 둘 다 무너진다.

| 전제 | 플랫폼 스레드 풀 | 가상 스레드 |
|---|---|---|
| 스레드 개수가 적다 | 200개 → 객체도 최대 200개 | **수만~수백만 개** → 객체도 그만큼 (메모리 폭탄) |
| 스레드가 오래 살며 재사용된다 | 풀에서 계속 재사용 → 초기화 비용을 상환 | **일회용** — 작업 하나 끝나면 죽음 → 캐시 적중이 아예 없음 |

가상 스레드는 풀링하지 않고 작업마다 새로 만드는 게 정석이므로(3-4절), **"스레드가 오래 살아 초기화 비용을 상환한다"는 캐싱의 근거 자체가 사라진다.** 만들어 봤자 한 번 쓰고 스레드와 함께 버려지며, 동시 요청이 수만 개면 그 비싼 객체가 수만 개 동시에 생긴다. **이득은 0, 비용만 폭증**한다.

그러니 대응은 이렇다. **문맥 전달용 ThreadLocal(traceId, 인증 정보)은 그대로 두고, 캐싱용 ThreadLocal은 걷어낸다.** `SimpleDateFormat` 같은 경우는 애초에 불변이라 공유해도 되는 `DateTimeFormatter`로 바꾸는 것이 정답이다.

#### 3-3-3. `InheritableThreadLocal` — 복사의 트리거는 요청이 아니라 "스레드 생성"

`InheritableThreadLocal`은 **스레드가 생성되는 순간** 부모(그 생성 코드를 실행한 스레드)의 값 테이블을 자식에게 복사해 주는 장치다. 이 복사 비용은 예전에도 있었다 — 달라지는 건 **생성 빈도**다.

| | 플랫폼 스레드 풀 | 가상 스레드 (요청당 생성) |
|---|---|---|
| 스레드 생성 시점 | 서버 시작 때 200개 만들고 끝 | 톰캣이 **요청마다** 새로 생성 |
| 복사 발생 횟수 | 시작 때 200번뿐 | **요청 수만큼** (부모에 값이 있는 한) |
| 요청 문맥 상속 | **무용지물** — 스레드가 요청보다 먼저 태어나 물려받을 게 없다 | 생성 시점의 부모 값이 상속된다 |

풀 모델에서는 복사가 시작 때 200번으로 끝나는데, 그 200번이 물려받는 건 풀을 만든 스레드(main 등)의 값이라 요청 문맥 전달용으로는 애초에 쓸모가 없었다. 그래서 풀 시대의 프레임워크는 상속 대신 요청마다 직접 `set`/`remove`하는 방식을 썼다.

가상 스레드 모델에서는 상황이 다르다. **내 코드가 가상 스레드를 안 만들어도** 톰캣이 요청마다 만들기 때문에, 부모에 inheritable 값이 있는 한 복사가 요청마다 일어난다. 판단 기준은 "내가 만들었나"가 아니라 **"요청마다 새 스레드가 태어나는 모델인가"**다.

#### 3-3-4. 후속 — `ScopedValue`

지금까지의 문제를 한 줄로 모으면 이렇다. **ThreadLocal의 손익은 스레드의 수명 모델에 종속된다** — 풀(재사용)에서는 오염과 누수를, 가상 스레드(대량 생성)에서는 개수 비용을 걱정해야 한다.

이 종속을 끊으려고 Loom 팀이 만든 후속 API가 **`ScopedValue`**다. 값의 수명을 스레드가 아니라 **코드 블록의 범위**에 매단다. JDK 21에 프리뷰로 처음 나와 JDK 25에서 정식 기능이 됐다(JEP 506).

```java
// before: ThreadLocal — 언제든 set 가능하고, 수명이 스레드와 같다
ThreadLocal<User> USER = new ThreadLocal<>();
USER.set(user);            // 아무 데서나 바꿀 수 있고, remove() 안 하면 계속 남는다

// after: ScopedValue — 불변 + 코드 블록 범위로 수명 한정
static final ScopedValue<User> USER = ScopedValue.newInstance();

ScopedValue.where(USER, user).run(() -> {
    handleRequest();       // 이 블록 안에서 호출되는 모든 코드가 USER.get()으로 읽을 수 있다
});                        // 블록을 벗어나면 바인딩이 자동으로 풀린다 — remove() 누락 사고가 원천 차단된다
```

값이 **불변**이라는 점이 개수 비용까지 해결한다. 값을 바꿀 수 없으니 자식 작업에 넘길 때 **복사가 아니라 참조 공유**로 끝난다. `StructuredTaskScope`로 만든 하위 작업이 부모의 `ScopedValue`를 공짜로 물려받는 것도 이 덕분이다. 수백만 스레드 규모를 전제로 설계된 대체재다.

### 3-4. 도입 체크포인트

앞의 논의를 실제 도입 판단으로 옮기면 다섯 가지다.

**(1) 커넥션 풀 크기를 다시 계산한다.** 3-2절의 결론이 그대로 여기 온다. 스레드 상한이 사라지면 다음 병목은 반드시 커넥션 풀이다. 다만 "그럼 풀을 1,000개로 늘리자"는 오답이다 — 커넥션은 DB 쪽에도 프로세스/메모리를 요구하는 자원이라, 무작정 늘리면 DB가 먼저 무너진다. **먼저 할 일은 트랜잭션 점유 시간을 줄이는 것**이고, 풀 크기 조정은 그다음이다.

**(2) 동시성 제한은 `Semaphore`로 건다.** 가상 스레드에는 개수 제한이 없으므로, 하류 자원(외부 API, 레거시 시스템)을 보호하려면 **별도의 문지기**가 필요하다. 스레드 풀이 하던 부하 제한 역할을 대신 맡길 도구가 `Semaphore`다.

```java
// Semaphore = "동시 통행증 N장" — 표를 받은 만큼만 안으로 들어갈 수 있다
private final Semaphore outboundLimit = new Semaphore(50);

public PaymentResult approve(OrderRequest req) throws InterruptedException {
    outboundLimit.acquire();          // 표가 없으면 여기서 대기한다.
                                      // 이 대기는 park 기반이라 가상 스레드가 unmount된다 — 캐리어는 안 묶인다.
    try {
        return paymentClient.approve(req);
    } finally {
        outboundLimit.release();      // 반드시 반납. 누락되면 통행증이 영구히 줄어 서서히 마비된다.
    }
}
```

**(3) 가상 스레드는 풀링하지 않는다.** 가상 스레드는 일회용이다. 풀에 넣어 재사용하면 (a) 재사용 오염이 다시 생기고 (b) 개수 상한이 다시 생겨 이점이 사라진다. **개수 제한이 목적이면 스레드 풀이 아니라 `Semaphore`를 쓴다**는 것이 (2)와 이어지는 원칙이다.

여기서 이름이 주는 오해를 하나 걷어내자. **`Executors.newVirtualThreadPerTaskExecutor()`는 스레드 풀이 아니다.** 반환 타입이 `ExecutorService`라 풀처럼 보이지만, 이 executor는 이름 그대로 **작업(task)마다 가상 스레드를 하나씩 새로 만들고 끝나면 버린다.** 재사용도 없고 개수 상한도 없다. 그래서 `close()`(또는 try-with-resources 블록 탈출)의 의미도 "풀을 접는다"가 아니라 **"제출된 작업이 전부 끝날 때까지 기다린다"**로 달라진다.

**(4) 모니터링 지표가 무의미해지는 것을 대비한다.** 2-1절에서 "OS는 가상 스레드를 모른다"고 했는데, 그 결과가 여기서 나타난다. `ThreadMXBean` 기반 지표(마이크로미터의 `jvm.threads.live` 등)는 **가상 스레드를 세지 않는다.** 캐리어만 세기 때문에 부하가 아무리 몰려도 항상 코어 수 근처에서 평평하다.

즉 **"스레드 풀 포화" 알람이 영원히 울리지 않게 된다.** 그동안 그 지표를 포화 감지에 써 왔다면 대체 지표를 먼저 세워야 한다.

- **커넥션 풀 대기** (`hikaricp.connections.pending`, `hikaricp.connections.acquire` 지연) — 새 병목이 여기로 옮겨 왔으므로 1순위다.
- **하류 응답 시간과 타임아웃/에러율** — 대기 행렬이 길어지는 것은 여기서 먼저 보인다.
- **JFR 이벤트** — `jdk.VirtualThreadPinned`(핀 발생), `jdk.VirtualThreadStart`/`End`(생성·종료 추이).
- **스레드 덤프도 방식이 다르다.** 전통적인 `jstack`은 가상 스레드를 보여주지 않는다. JDK 21+의 `jcmd <pid> Thread.dump_to_file`을 써야 한다.

**(5) CPU 바운드 작업에는 무의미하다.** 이득은 오직 **I/O 대기가 많은 워크로드**에서 나온다. 이미지 변환이나 암호 연산처럼 CPU를 계속 쓰는 작업은 어차피 코어 수만큼만 동시에 돌 수 있으므로, 가상 스레드로 바꿔도 얻는 게 없다(2-9절).

## 4. 꼬리질문 대비 포인트

### "가상 스레드를 도입하면 처리량이 몇 배 늘어나나요?"

**"워크로드에 따라 다르고, 늘어난다면 그 배수는 '대기 시간 / CPU 시간' 비율에서 나온다"**로 답하는 것이 정확하다.

1-2절의 예를 그대로 쓰면 계산이 보인다. 요청 하나가 350ms 중 5ms만 CPU를 쓴다면 대기 비중이 98%이고, 스레드 상한 200이 걷히는 순간 처리량은 **CPU가 감당하는 지점까지** 올라갈 수 있다. 반대로 CPU를 100% 쓰는 작업이라면 이론상 이득이 0이고, 분기·freeze/thaw 비용 때문에 미세하게 손해일 수도 있다.

여기에 **"단, 상류의 상한이 걷혔다고 하류도 늘어나는 것은 아니다"**를 붙이면 완성된다. DB, 외부 API, 커넥션 풀의 처리량이 그대로면 늘어나는 것은 처리량이 아니라 대기 행렬이다(3-2절).

### "pinning은 JDK 24에서 해결됐다는데, 이제 `synchronized`를 그냥 써도 되나요?" (시니어 변별 포인트)

**"핀은 사라졌지만 직렬화는 남는다"**가 핵심이다. 답을 3단으로 나눈다.

**(1) 무엇이 해결됐는지 정확히.** JEP 491(JDK 24)이 모니터 소유권을 OS 스레드가 아니라 가상 스레드 단위로 추적하도록 바꿔서, `synchronized` 안에서 블로킹해도 캐리어에서 내려올 수 있게 됐다. **"캐리어가 묶여 서버 전체가 멈추는"** 문제는 이것으로 해소된다.

**(2) 무엇이 남았는지.** 잠금은 여전히 잠금이다. 300ms짜리 외부 호출을 `synchronized`로 감쌌다면 그 구간의 처리량은 **초당 3건**이고, 가상 스레드가 1만 개여도 변하지 않는다. 장애의 모양이 "전체 멈춤"에서 "그 구간만 극심한 대기"로 바뀔 뿐이다. **긴 I/O를 잠금으로 감싸는 설계 자체가 잘못**이라는 점은 그대로다.

**(3) 네이티브 pinning은 구조적으로 남는다.** JNI 프레임은 JVM이 구조를 몰라 힙으로 옮길 수 없으므로 어떤 버전에서도 얼릴 수 없다. 그래서 JFR `jdk.VirtualThreadPinned` 이벤트는 JDK 24 이후에도 계속 필요하다 — 다만 이제 그 이벤트가 잡아 주는 것은 대체로 네이티브/VM 프레임이다.

마지막으로 **`-Djdk.tracePinnedThreads`가 JDK 24에서 제거됐다는 것**까지 말하면 버전 감각이 드러난다. 이 옵션을 그대로 붙여 둔 채 "핀이 안 잡히네" 하는 오해가 실제로 생긴다.

### "가상 스레드를 켰더니 오히려 장애가 늘었습니다. 왜일까요?" (시니어 변별 포인트)

**"부하 제한기가 사라졌기 때문"**이라고 답하는 것이 이 질문의 정답이다.

톰캣의 워커 200개는 성능 제약처럼 보였지만, 실제로는 **공짜로 얻고 있던 admission control**이었다. 동시에 200건까지만 안으로 들여보내 주었기 때문에 그 뒤의 모든 자원 — 커넥션 풀, 외부 API, 레거시 시스템 — 도 200 이상의 경쟁을 겪지 않았다. `spring.threads.virtual.enabled=true` 한 줄은 그 문을 활짝 여는 것이다.

구체적 증상은 셋으로 나온다.

1. **커넥션 풀 고갈** — `Connection is not available, request timed out after 30000ms`. 3-2절의 계산 그대로다.
2. **하류 서비스 과부하 전파** — 우리가 안 죽는 대신 외부 API나 레거시 시스템이 죽는다. 우리 서버가 던지던 백프레셔(더 못 받겠다는 신호)가 사라진 결과다.
3. **메모리 증가** — 요청 하나가 붙잡고 있던 객체들이 이제 수만 건 분량으로 힙에 동시에 존재한다.

대응은 **부하 제한을 명시적으로 다시 세우는 것**이다. `Semaphore`로 하류 호출의 동시성을 제한하고, 커넥션 풀 대기 지표를 감시하고, 타임아웃과 서킷 브레이커를 손본다. **"암묵적 제한이 명시적 제한으로 바뀌었다"**가 도입의 본질이다.

### "가상 스레드와 리액티브(WebFlux) 중 무엇을 고르겠습니까?"

**"둘 다 같은 문제를 푸는 다른 방법이고, 비용 구조가 다르다"**에서 출발한다.

푸는 문제는 같다 — "기다림 때문에 OS 스레드가 낭비되는 것"이다. 리액티브는 **코드를 바꿔서** 스레드를 안 붙잡고, 가상 스레드는 **스레드를 바꿔서** 붙잡아도 싸게 만든다.

비용이 갈리는 지점은 이렇다.

| | 리액티브 | 가상 스레드 |
|---|---|---|
| 코드 스타일 | 콜백/체이닝으로 전면 전환 | 기존 블로킹 코드 그대로 |
| 디버깅·스택트레이스 | 끊어져서 어렵다 | 그대로 살아 있다 |
| ThreadLocal 기반 도구 | 그대로는 안 통한다(Reactor Context 등 별도 장치) | 그대로 동작한다 |
| 전염성 | 경로 위 라이브러리 하나만 블로킹이어도 무너진다 | 블로킹 라이브러리를 그대로 써도 된다 |
| 스트림/배압 제어 | 연산자로 정교하게 표현된다 | 언어 차원의 도구가 없어 직접 만들어야 한다 |

**대부분의 CRUD·오케스트레이션 API라면 가상 스레드가 낫다.** 얻는 동시성은 비슷한데 학습·유지보수 비용이 비교가 안 되게 싸기 때문이다.

**리액티브가 여전히 유리한 영역**을 말하면 답이 균형을 얻는다 — SSE·WebSocket 같은 스트리밍, 백프레셔가 본질적인 파이프라인, 이미 Reactor로 잘 돌고 있는 시스템이다. 특히 마지막이 중요하다. **잘 돌아가는 리액티브 코드를 가상 스레드로 되돌릴 이유는 없다.**

### "가상 스레드 환경에서 ThreadLocal을 써도 되나요?"

**"써도 된다. 다만 용도를 나눠야 한다"**로 답한다.

**동작은 안전하다.** 값은 캐리어가 아니라 힙의 가상 스레드 객체에 붙으므로 캐리어를 갈아타도 따라다니고, 다른 가상 스레드에게 새지 않는다(3-3-1). 오히려 스레드 풀 시절의 최대 사고였던 **재사용 오염이 사라진다** — 스레드가 재사용되지 않으니까.

**깨지는 것은 "캐싱" 용도다.** "스레드가 적고 오래 산다"를 전제로 스레드마다 비싼 객체를 하나씩 만들어 두던 패턴은, 스레드가 수만 개 일회용이 되는 순간 **캐시 적중 0, 메모리만 수만 배**가 된다.

그래서 정리는 이렇다. **문맥 전달(traceId, 인증 정보)은 유지, 스레드당 캐싱은 제거.** 그리고 이 종속 자체를 끊으려는 후속이 불변·블록 범위의 `ScopedValue`(JDK 25 정식)라는 데까지 연결하면 좋다.

**`InheritableThreadLocal`은 다시 점검해야 한다** (가산점 포인트). 복사의 트리거가 요청이 아니라 **스레드 생성**이라, 풀 모델에서는 시작 때 200번으로 끝나던 복사가 요청당 생성 모델에서는 **요청마다** 일어난다.

### "`Executors.newVirtualThreadPerTaskExecutor()`는 결국 스레드 풀 아닌가요?" (가산점 포인트)

**아니다.** 반환 타입이 `ExecutorService`라 풀처럼 보이지만, 이름 그대로 **작업마다(per-task) 가상 스레드를 하나 새로 만들고 끝나면 버린다.** 재사용도 없고 개수 상한도 없다.

이 차이가 실무에서 드러나는 지점이 셋이다.

1. **개수 제한 수단이 아니다.** 하류를 보호하려면 `Semaphore`를 따로 걸어야 한다(3-4).
2. **`close()`의 의미가 다르다.** "풀을 접는다"가 아니라 "제출된 작업이 전부 끝날 때까지 기다린다"이다. `ExecutorService`가 `AutoCloseable`이 되면서 try-with-resources로 쓰는 것이 자연스러워졌다.
3. **가상 스레드를 풀링하려 드는 것은 안티패턴이다.** 풀링하는 순간 재사용 오염과 개수 상한이 함께 돌아와 이점이 사라진다.

## 한 줄 요약

가상 스레드는 "스레드가 기다린다 = 비싼 OS 스레드가 논다"는 등식을 깬 기술이다 — 스레드의 정체가 "콜 스택 + 실행 위치"라는 **데이터**임을 이용해, 블로킹 시스템 콜에 들어가는 대신 JDK가 소유한 시스템 콜 직전 경로에서 "epoll 등록 + 아직 깨어 있는 스레드가 스스로 자기 스택 프레임을 힙으로 복사(freeze)하고 캐리어에서 물러나기"로 바꿔치기했고, 데이터가 도착하면 아무 캐리어에나 다시 올려(thaw) 이어 달린다(내리는 건 본인, 올리는 건 캐리어, 깨우는 건 poller — 마법은 캐리어가 아니라 Continuation에 있다). 그 대가로 **JVM이 경로를 소유하지 못한 지점에서 pinning**이 생기는데, `synchronized`는 모니터 소유자가 OS 스레드에 묶여 있어 프레임만 옮기면 잠금 장부가 어긋나기 때문이고(**JDK 21~23에서는 `ReentrantLock`으로 교체, JDK 24의 JEP 491에서 해소 — 다만 잠금의 직렬화는 그대로 남는다**), JNI 프레임은 JVM이 구조를 몰라 옮길 수 없어 **어떤 버전에서도 남는다**(탐지는 JDK 24부터 `-Djdk.tracePinnedThreads`가 제거되고 JFR `jdk.VirtualThreadPinned`가 정식 경로다). 그리고 가장 실무적인 함정은 **가상 스레드가 값싸게 만든 것은 자바 스레드일 뿐 DB 커넥션이 아니라는 것** — 트랜잭션은 커넥션에 묶여 있고 풀은 여전히 20개라 처리량 상한 57 req/s는 그대로인데, 톰캣 200 스레드가 해 주던 암묵적 부하 제한만 사라져 대기 행렬이 무한정 길어지고 커넥션 타임아웃으로 더 크게 터진다. 그러니 도입의 본질은 **암묵적 제한을 명시적 제한으로 바꾸는 일**이다 — 외부 콜을 트랜잭션 밖으로 빼고, `Semaphore`로 동시성을 직접 제한하고, 스레드 수 대신 커넥션 풀 대기와 JFR 이벤트를 보도록 관측 지표를 다시 세우고, ThreadLocal은 문맥 전달만 남기고 스레드당 캐싱은 걷어낸다(후속은 불변·블록 범위의 `ScopedValue`, JDK 25 정식).
