# volatile — 가시성은 보장하지만, 원자성은 보장하지 않는다

> 핵심 관전 포인트: **volatile은 두 가지를 보장한다 — ① 가시성(한 스레드가 쓴 값이 다른 스레드에게 반드시 보인다), ② 그 변수를 기준으로 한 재배치 방지. 그러나 원자성은 보장하지 않는다 — `volatile int count`의 `count++`는 읽기·계산·쓰기 3단계로 이루어진 복합 연산이라, 그 사이에 다른 스레드가 끼어드는 것을 volatile은 전혀 막지 못한다. 그래서 volatile은 "한 스레드가 쓰고 여러 스레드가 읽는 플래그·상태 발행"에만 적합하고, 읽고-고치고-쓰는 복합 연산에는 `AtomicInteger`(CAS)나 락이 필요하다. 가시성 문제와 원자성 문제는 서로 다른 문제이며 volatile은 앞의 것만 해결한다는 것이 이 질문의 전부다.**

---

## 0. 질문 + 의도

**질문**: "`volatile` 키워드는 무엇을 보장하고, 무엇을 보장하지 못하나요? (가시성 vs 원자성)"

**출제 의도**: `volatile int counter++` 같은 코드가 왜 틀렸는지 즉시 보이는지를 확인한다. 동시성 버그는 테스트를 통과하고 운영에서만 터지므로, 코드 리뷰 단계에서 잡을 수 있는 사람의 가치가 특히 크다.

## 1. volatile이 보장하는 것 — 가시성과 재배치 방지

### 1-1. 전제 지식 — CPU는 왜 메인 메모리를 직접 읽지 않는가

"한 스레드가 쓴 값이 다른 스레드에게 안 보일 수 있다"는 말은 처음 들으면 납득이 안 된다. 같은 프로세스 안의 같은 변수인데 왜 안 보인다는 말인가. 답은 **CPU가 메인 메모리를 직접 읽고 쓰지 않는다**는 사실에 있다.

현대 CPU에게 메인 메모리(RAM)는 너무 느리다. L1 캐시 접근 비용을 1이라 치면 메인 메모리 접근은 수십에서 수백 배에 달한다. 그래서 CPU는 자주 쓰는 데이터를 자기 가까이에 복사해 두고 그 복사본으로 일한다. 이 복사본 저장소가 **캐시**이고, 속도와 크기를 절충해 여러 층으로 쌓여 있다.

```
   [코어 0]                          [코어 1]
  +-----------+                     +-----------+
  |  L1 캐시  |  가장 빠름, 가장 작음 |  L1 캐시  |   <- 코어 전용 (남이 못 봄)
  +-----------+                     +-----------+
  |  L2 캐시  |                     |  L2 캐시  |   <- 코어 전용 (남이 못 봄)
  +-----------+                     +-----------+
        \                                 /
         \                               /
       +---------------------------------+
       |          L3 캐시 (공유)         |          <- 같은 CPU의 코어들이 공유
       +---------------------------------+
                       |
       +---------------------------------+
       |      메인 메모리 (RAM)          |          <- 전부가 공유. 가장 느림, 가장 큼
       +---------------------------------+
```

핵심은 **L1과 L2가 코어 전용**이라는 점이다. 스레드 A가 코어 0에서 `stopRequested = true`를 실행하면 그 값은 일단 코어 0의 L1 캐시에 쓰인다. 코어 1에서 도는 스레드 B는 코어 0의 L1을 들여다볼 수 없다. B가 자기 L1에 갖고 있는 `stopRequested`의 옛 복사본을 계속 읽는다면, A의 변경은 B에게 **영영 도착하지 않을 수도 있다.**

여기에 문제 하나가 더 겹친다. **JIT 컴파일러의 최적화**다. 컴파일러가 "이 루프 안에서 `stopRequested`를 바꾸는 코드가 없네"라고 판단하면, 매번 메모리를 확인하는 대신 값을 레지스터에 한 번만 담아두고 계속 쓰도록 코드를 바꾼다. 단일 스레드 기준으로는 완벽하게 옳은 최적화지만, 다른 스레드가 그 값을 바꾼다는 사실은 컴파일러가 알 도리가 없다.

이렇게 **한 스레드가 쓴 값을 다른 스레드가 언제 볼지, 심지어 보기는 할지 보장되지 않는 성질**을 다루는 것이 **가시성(visibility)** 문제다.

비유하면 이렇다. 각 스레드는 원본 문서(메인 메모리)의 **복사본(캐시)을 자기 책상에 놓고 일한다.** 누가 원본을 고쳐도 내 책상의 복사본만 계속 들여다보면 알 길이 없다. `volatile`은 그 변수에 **"이건 복사본으로 처리하지 말고 항상 원본을 확인하고, 고쳤으면 즉시 원본에 반영해라"**는 표시를 붙이는 것이다.

### 1-2. before / after — 영원히 안 멈추는 스레드

```java
// (문제) volatile이 없어서 종료 신호가 워커에게 도달하지 않을 수 있다
class Worker implements Runnable {
    private boolean stopRequested = false;   // 잘못됨: volatile이 없다

    public void run() {
        while (!stopRequested) {   // JIT가 "이 루프 안에서 안 바뀌는 값"으로 판단해
            doWork();              // 읽기를 루프 밖으로 끌어올릴 수 있다.
        }                          // 그러면 사실상 while(true)로 컴파일된 것과 같아진다.
    }

    public void stop() { stopRequested = true; }  // 다른 스레드가 이걸 호출해도
}                                                 // 워커의 캐시/레지스터에는 안 보일 수 있다
```

이 코드가 특히 고약한 이유는 **로컬 테스트에서는 대부분 잘 멈추기 때문**이다. 짧게 도는 코드는 JIT가 아직 공격적으로 최적화하지 않은 인터프리터 단계에 머무르고, 그 상태에서는 매번 메모리를 읽으므로 정상 동작한다. **오래 돌면서 JIT가 충분히 최적화한 운영 서버에서만** 안 멈추는 스레드가 나타난다. 출제 의도가 짚는 "테스트를 통과하고 운영에서만 터지는" 버그의 전형이다.

```java
// (개선) volatile 하나로 가시성을 확보한다
private volatile boolean stopRequested = false;
// 쓰기는 즉시 다른 코어가 볼 수 있는 곳까지 발행되고,
// 읽기는 캐시된 옛 값이 아니라 최신 값을 가져오도록 강제된다.
// 컴파일러도 이 변수의 읽기를 루프 밖으로 끌어올리지 못한다.
```

### 1-3. 전제 지식 — 재배치(reordering)란 무엇인가

volatile의 두 번째 보장을 이해하려면 **재배치**를 먼저 알아야 한다.

**컴파일러와 CPU는 성능을 위해 명령의 실행 순서를 바꾼다.** 임의로 바꾸는 것은 아니고 지켜야 할 선이 하나 있다 — **단일 스레드에서 관측되는 결과가 같기만 하면 순서를 바꿔도 된다.** 이 규칙을 as-if-serial(마치 순차 실행한 것처럼) 원칙이라 부른다.

왜 바꾸는가. 이유는 층마다 다르다. 컴파일러는 메모리 접근을 모아서 처리하거나 레지스터 사용을 줄이려고 순서를 조정한다. CPU는 앞선 명령이 메모리를 기다리며 멈춰 있을 때 뒤의 명령을 먼저 실행해 파이프라인을 놀리지 않으려 한다. 쓰기 버퍼에 잠시 모아뒀다가 몰아서 메모리에 반영하는 것도 사실상 순서를 바꾸는 효과를 낸다.

```
// 프로그래머가 쓴 순서              // 실제로 실행될 수 있는 순서
data = 42;      // ①                ready = true;   // ② 가 먼저!
ready = true;   // ②                data = 42;      // ① 가 나중
```

두 문장 사이에 의존 관계가 없으므로 **단일 스레드에서는 어느 쪽으로 실행하든 결과가 같다.** 그래서 허용된다. 문제는 **다른 스레드가 그 중간을 들여다볼 때** 생긴다. 스레드 B가 `ready == true`를 보고 `data`를 읽었는데 `data`는 아직 0인 상황이 실제로 가능해진다.

정리하면, 재배치는 버그가 아니라 **다른 스레드의 존재를 고려하지 않는 최적화**이며, 그 최적화를 특정 지점에서 제한하는 장치가 필요해진다. 그 장치가 **메모리 배리어(memory barrier)** — "이 지점을 넘어 읽기·쓰기를 재배치하지 말고, 여기까지의 쓰기를 다른 코어가 볼 수 있게 하라"고 CPU에 지시하는 특수 명령이다. `volatile` 변수를 읽고 쓸 때 컴파일러가 이 배리어를 자동으로 끼워 넣는다.

### 1-4. 보장 ② — 재배치 방지와 안전 발행

volatile 변수에 대한 읽기·쓰기는 **그 앞뒤 코드가 이 변수를 넘어 재배치되는 것을 막는다.** 그래서 volatile 변수 하나가 "그 이전에 쓴 일반 변수들까지 통째로 발행하는" 다리 역할을 하게 된다.

```java
int data = 0;                    // 일반 변수 (volatile 아님)
volatile boolean ready = false;  // 발행 스위치 역할

// 스레드 A                       // 스레드 B
data = 42;      // ①              if (ready) {       // ready == true를 봤다면
ready = true;   // ② 발행              print(data);   // data == 42도 반드시 보인다
                                  }
```

`data`에는 volatile이 없는데도 42가 보장된다는 것이 이 패턴의 요점이다. `ready = true`라는 volatile 쓰기가 **그 이전의 모든 쓰기를 함께 밀어내고**, `ready`를 읽은 스레드는 **그 시점 이전의 쓰기를 전부 이어받기** 때문이다. 이렇게 완성된 데이터를 다른 스레드에게 안전하게 넘기는 것을 **안전 발행(safe publication)**이라 한다.

이 보장의 공식적인 근거는 happens-before 규칙과 그 이행성이며 `15-jmm-happens-before.md`에서 다룬다. 이 문서에서는 결론만 쥐고 가면 된다. **volatile 쓰기 이전의 모든 쓰기는, 그 volatile을 읽은 스레드에게 함께 보인다.**

## 2. volatile이 보장하지 못하는 것 — 원자성

### 2-1. `count++`가 깨지는 과정을 한 단계씩

**원자성(atomicity)**은 **여러 단계로 이루어진 연산이 중간에 끼어들 틈 없이 하나의 덩어리로 처리되는 성질**이다. 더 이상 쪼갤 수 없다는 뜻에서 "원자"라 부른다. 가시성이 "보이느냐"의 문제라면 원자성은 "끼어들 수 있느냐"의 문제다 — **완전히 다른 문제이고, volatile은 앞의 것만 해결한다.**

`count++`는 소스에서 한 줄이지만 실제로는 세 단계다.

```
① count 값 읽기  ->  ② 읽은 값에 +1 계산  ->  ③ 계산한 값을 count에 쓰기
```

volatile은 ①이 최신 값을 읽게 하고 ③이 즉시 발행되게 할 뿐, **①·②·③ 사이에 다른 스레드가 끼어드는 것은 전혀 막지 못한다.** `count`가 5인 상태에서 두 스레드가 동시에 증가시키는 과정을 시간순으로 따라가 보자.

| 시각 | 스레드 A | 스레드 B | 이 시점 count의 값 |
|---|---|---|---|
| t1 | ① 읽기 → 5 | | 5 |
| t2 | | ① 읽기 → 5 | 5 |
| t3 | ② 5 + 1 = 6 | | 5 |
| t4 | | ② 5 + 1 = 6 | 5 |
| t5 | ③ 6 쓰기 | | 6 |
| t6 | | ③ 6 쓰기 | 6 |

**두 스레드가 각각 1씩 더했으니 결과는 7이어야 하는데 6이다.** 증가 한 번이 사라졌다.

여기서 볼 대목은 t2다. B가 5를 읽은 것은 **틀린 값을 읽은 게 아니다.** 그 순간 `count`는 정말로 5였다. volatile은 자기 일(최신 값 보여주기)을 완벽히 했다. 문제는 A가 "읽고 계산한 뒤 쓰기까지"를 끝내기 전에 B가 읽어버렸다는 것 — **가시성이 아니라 끼어들기가 원인**이다. 이렇게 한쪽의 갱신이 다른 쪽에 덮여 사라지는 것을 **갱신 유실(lost update)**이라 한다.

volatile을 아무리 붙여도 이 표는 바뀌지 않는다. 필요한 것은 **①~③을 하나로 묶는 장치**다.

### 2-2. 복합 연산에는 CAS 또는 락

```java
// (개선 1) AtomicInteger — CAS로 원자적 증가
private final AtomicInteger count = new AtomicInteger();
count.incrementAndGet();
// CAS(Compare-And-Swap)는 "이 값이 내가 읽었던 값 그대로면 새 값으로 바꿔라"를
// CPU가 한 명령으로 처리하는 원자 연산이다. 위 표의 t5에서 A가 쓰는 순간
// "아직 5인가"를 확인하므로, B가 이미 6으로 바꿔놨다면 실패하고 다시 읽어 재시도한다.
// 실패해도 스레드가 잠들지 않아 락보다 싸다.

// (개선 2) synchronized — 상호배제로 끼어들기 자체를 차단
private int count = 0;
public synchronized void increment() { count++; }
// A가 ①~③을 끝낼 때까지 B는 아예 진입하지 못한다.
// 대신 락을 못 잡은 스레드는 잠들었다 깨어나는 비용(컨텍스트 스위칭)을 치른다.
```

둘의 갈림은 **경합의 정도**다. 경합이 짧고 드물면 CAS 쪽이 유리하고, 경합이 극심하면 CAS 재시도가 헛돌면서 CPU만 태우므로 락이 나을 수 있다. 갱신이 극단적으로 잦은 카운터라면 `LongAdder`가 더 나은 선택이다(`27-longadder-false-sharing.md`).

### 2-3. 검사 후 행동(check-then-act)도 같은 이유로 깨진다

원자성 문제는 `++`에만 있는 게 아니다. **"읽어서 판단하고, 그 판단에 따라 쓰는" 모든 코드**가 같은 구조다.

```java
// (문제) 검사와 행동 사이가 비어 있다
private volatile Connection conn;

public Connection get() {
    if (conn == null) {        // 검사(check)
        conn = create();       // 행동(act)
    }                          // 두 스레드가 나란히 null을 보면 create()가 두 번 실행된다.
    return conn;               // 커넥션 하나가 누수되고, 둘 중 하나만 살아남는다.
}
```

이 패턴을 **검사 후 행동(check-then-act)**이라 부른다. "null 검사 후 초기화", "잔액 확인 후 차감", "재고 확인 후 감소"가 전부 여기 해당한다. **개별 읽기·쓰기가 아니라 연산 묶음이 원자적이어야** 하므로 volatile로는 해결되지 않는다. 락으로 묶거나, CAS 루프로 만들거나, `AtomicReference.compareAndSet` 같은 원자적 연산으로 바꿔야 한다.

### 2-4. 예외 하나 — long/double의 64비트 접근 (가산점 포인트)

volatile이 원자성을 전혀 안 준다는 말에는 한 가지 예외가 있다.

`long`과 `double`은 64비트 값인데, JLS는 volatile이 없는 `long`/`double`에 대해 **읽기·쓰기 자체가 32비트씩 두 번으로 쪼개지는 것을 허용한다.** 그러면 한 스레드가 상위 32비트만 쓴 시점에 다른 스레드가 읽어서 **앞쪽은 새 값, 뒤쪽은 옛 값인 존재하지 않았던 숫자**를 얻을 수 있다. 이 현상을 값이 찢어진다는 뜻에서 **워드 티어링(word tearing)**이라 부른다.

`volatile long`을 붙이면 이 **단일 읽기·쓰기의 원자성은** 보장된다. 다만 여기서 멈추면 안 된다. 이것은 "읽기 한 번, 쓰기 한 번이 쪼개지지 않는다"는 보장일 뿐, `++`처럼 **읽고-고치고-쓰는 복합 연산의 원자성과는 아무 상관이 없다.** `volatile long counter`에 `counter++`를 하면 2-1의 표가 그대로 재현된다.

## 3. 실무 판단 기준 — volatile이 맞는 자리, 틀린 자리

### 3-1. 맞는 자리: "한 명이 쓰고, 여럿이 읽는" 구조

volatile이 정확히 들어맞는 조건은 **쓰기가 다른 변수나 현재 값에 의존하지 않는 단순 대입**일 때다. 대표적인 자리가 둘이다.

**종료·상태 플래그.** `volatile boolean shutdown`처럼 쓰는 쪽은 관리 스레드 하나, 읽는 쪽은 워커 여럿인 구조다. 쓰기가 `true` 대입 한 번이라 쪼개질 여지가 없고, 읽는 쪽은 값이 보이기만 하면 된다.

**불변 객체 참조 교체.** 설정 리로드처럼 새 객체를 통째로 만들어 참조만 바꿔치기하는 경우다.

```java
private volatile Config config;   // Config는 불변(immutable) 객체여야 한다

public void reload() {
    config = loadNewConfig();
    // 참조 대입 한 번 = 단일 쓰기이므로 원자적이다.
    // 읽는 쪽은 "온전한 옛 설정" 아니면 "온전한 새 설정"만 보고,
    // 필드 일부만 바뀐 중간 상태는 존재할 수 없다.
    // Config가 가변 객체라면 이 보장이 무너진다 — 읽는 쪽이 참조를 잡은 뒤
    // 그 내부 필드가 바뀌면 그건 volatile이 관여하지 않는 영역이다.
}
```

**double-checked locking의 인스턴스 필드**도 여기 속한다. 이 경우는 가시성보다 재배치 방지가 결정적인데, 4절 꼬리질문에서 다룬다.

### 3-2. 틀린 자리

**카운터, 누적 합계 등 읽고-고치고-쓰는 모든 것.** `Atomic*`이나 락으로 올라가야 한다.

**검사 후 행동.** null 체크 후 초기화, 조건 확인 후 갱신 등. 락 또는 CAS 루프가 필요하다.

**두 변수가 함께 일관돼야 하는 불변식.** 예를 들어 `balance`와 `history`가 항상 짝이 맞아야 한다면 volatile 두 개로는 안 된다. 각각의 읽기·쓰기는 원자적이지만 **"두 값을 함께" 읽거나 쓰는 것은 원자적이지 않으므로**, 다른 스레드가 그 사이를 관측해 잔액은 갱신됐는데 이력은 아직인 상태를 볼 수 있다. 이런 불변식은 락으로 묶어야 한다.

### 3-3. 코드 리뷰 체크리스트 (AI 생성 코드 검증 포함)

AI가 생성한 동시성 코드에서 특히 자주 보이는 오류가 **"동기화가 필요하다는 건 알았는데 volatile을 만능으로 쓴"** 형태다. 리뷰할 때 이 셋을 본다.

1. **volatile 변수에 `++`, `+=`, `--`가 있는가.** 있으면 그 자리에서 지적한다. 복합 연산이므로 무조건 틀렸다.
2. **volatile 변수를 `if`로 검사한 뒤 그 결과에 따라 쓰기를 하는가.** 검사 후 행동이다.
3. **쓰는 스레드가 정말 하나인가.** 둘 이상이 쓴다면 volatile로 충분한 경우가 드물다.

이 체크리스트가 유효한 이유는 **동시성 버그가 테스트로 잘 안 잡히기 때문**이다. 대부분의 경합은 타이밍이 맞아떨어져야 재현되고, 그 타이밍은 부하가 높은 운영 환경에서 훨씬 자주 만들어진다. 리뷰에서 잡지 못하면 그 다음 방어선은 장애다.

## 4. 꼬리질문 대비 포인트

### "`volatile int count`에 `count++`를 하면 정확히 무엇이 어떻게 깨지나요?"

`count++`는 "읽기 → 계산 → 쓰기" 3단계이고 volatile은 이 묶음을 원자적으로 만들지 않는다.

`count`가 5일 때 두 스레드가 나란히 5를 읽으면, 각자 6을 계산해서 각자 6을 쓴다. 두 번 증가시켰는데 결과는 7이 아니라 6이다. 이것이 **갱신 유실(lost update)**이다.

여기서 강조할 점은 **두 스레드 모두 최신 값을 정확히 읽었다**는 것이다. volatile은 자기 일을 했다. 문제는 한쪽이 읽고-계산하고-쓰기를 끝내기 전에 다른 쪽이 읽었다는 것, 즉 **가시성이 아니라 끼어들기**다.

해결은 `AtomicInteger.incrementAndGet()`(CAS)이나 `synchronized`다. 가시성 문제가 아니라 상호배제 문제이기 때문에 도구가 달라진다.

### "AtomicInteger는 락 없이 어떻게 원자성을 보장하나요?"

**CAS(Compare-And-Swap)** — "이 메모리 값이 내가 읽었던 값 그대로면 새 값으로 바꿔라"를 CPU가 **하나의 하드웨어 명령**으로 처리한다. 비교와 교체 사이에 다른 스레드가 끼어들 틈이 없다는 것을 소프트웨어가 아니라 CPU가 보장한다.

동작은 이렇다. 현재 값을 읽고, 새 값을 계산하고, "아직 아까 그 값이면 새 값으로" 교체를 시도한다. 그 사이 누가 값을 바꿨으면 교체가 실패하고, 실패하면 **잠들지 않고 곧바로 다시 읽어 재시도**한다.

락과의 결정적 차이가 이 지점이다. 락은 못 잡으면 스레드가 커널에 의해 대기 상태로 내려갔다가 깨워져야 해서 컨텍스트 스위칭 비용이 든다. CAS는 그게 없어 경합이 짧을 때 훨씬 싸다. 반대로 경합이 극심하면 재시도가 반복되며 CPU만 태우므로 항상 유리한 것은 아니다. 갱신이 극단적으로 잦은 카운터라면 `LongAdder`가 낫다(`27-longadder-false-sharing.md`).

### "volatile과 synchronized의 차이는? 언제 volatile로 충분한가요?" (시니어 변별 포인트)

**synchronized는 가시성과 상호배제 둘 다 주고, volatile은 가시성(과 재배치 방지)만 준다.** 락이 두 가지 일을 동시에 하기 때문에 흔히 "동기화 = 락"으로 뭉뚱그려지는데, 이 둘을 분리해서 볼 수 있느냐가 갈림길이다.

volatile로 충분한 조건은 셋이고, **하나라도 어긋나면 락이나 CAS로 올라가야 한다.**

1. 쓰기가 현재 값에 의존하지 않는다(단순 대입이지 `++`가 아니다).
2. 다른 변수와 함께 지켜야 하는 불변식이 없다.
3. 쓰는 스레드가 사실상 하나다.

이 조건을 만족하는 전형이 상태 플래그와 불변 객체 참조 교체다.

비용 관점을 덧붙이면 설계 판단으로 보인다. **volatile 읽기는 락 획득보다 훨씬 싸다** — 스레드를 재우지 않기 때문이다. 그래서 "쓰기는 드물고 읽기가 압도적으로 많은 발행·구독 구조"에서는 volatile을 고르는 것이 성능상 의미 있는 선택이 된다. 반대로 불변식을 지켜야 하는 자리에 비용을 이유로 volatile을 고르는 것은 선택이 아니라 오류다.

### "double-checked locking 싱글턴에서 volatile은 왜 필요한가요?"

```java
private static volatile Holder instance;   // 이 volatile이 없으면 깨진다

static Holder get() {
    if (instance == null) {                // ① 락 없이 하는 1차 검사 (빠른 경로)
        synchronized (Holder.class) {
            if (instance == null) {        // ② 락 안에서 하는 2차 검사
                instance = new Holder();   // ③ 이 한 줄이 사실은 3단계다
            }
        }
    }
    return instance;
}
```

이 패턴은 **매번 락을 잡는 비용을 피하려고 ①에서 락 없이 먼저 확인하는** 구조다. 그런데 락 없이 읽는 경로가 존재한다는 바로 그 이유 때문에 재배치에 취약해진다.

`new Holder()`는 실제로 "메모리 할당 → 생성자 실행 → 참조를 변수에 대입"의 3단계인데, **volatile이 없으면 생성자 실행과 참조 대입의 순서가 뒤바뀔 수 있다.** 단일 스레드에서는 결과가 같으므로 허용되는 재배치다.

문제는 그 사이를 다른 스레드가 ①에서 락 없이 들여다볼 때다. 참조는 이미 대입돼 null이 아닌데 필드는 아직 초기화 전인 **반쪽짜리 객체**를 받아 쓰게 된다. 필드가 전부 기본값(0, null)인 객체가 정상인 척 돌아다니는 것이다.

`volatile`은 두 가지 일로 이걸 막는다. **그 재배치를 금지하고**, **쓰기 이전의 모든 쓰기(생성자가 채운 필드들)를 함께 발행한다.**

(가산점 포인트) 요즘은 이 패턴을 직접 쓸 이유가 거의 없다. 클래스 로딩의 초기화 보장을 이용하는 **holder 클래스 관용구**나 **enum 싱글턴**이 더 단순하고 안전하며, 무엇보다 volatile을 빠뜨릴 여지가 없다. 스프링을 쓴다면 빈 스코프가 이미 이 문제를 대신 해결해 준다는 점도 짚을 만하다.

### "volatile 읽기·쓰기에는 비용이 없나요?"

**공짜는 아니다.** 두 가지 비용이 있다.

**최적화가 금지된다.** 값을 레지스터나 캐시에 오래 담아두고 재사용하는 최적화, 루프 밖으로 읽기를 끌어올리는 최적화가 막힌다. 매번 실제로 읽어야 한다.

**메모리 배리어가 들어간다.** 재배치 금지와 발행을 위해 CPU에 특수 명령이 삽입되고, 이는 CPU 파이프라인과 쓰기 버퍼 최적화를 제한한다.

다만 이 비용은 락과는 성격이 다르다. **volatile은 스레드를 블로킹하지도, 컨텍스트 스위칭을 유발하지도 않는다.** 그래서 일반적으로 락보다 훨씬 싸다.

결론은 "그러니 아무 데나 붙이자"가 아니다. **실제로 여러 스레드가 공유하는 변수에만 정확히 붙이는 것**이 맞다. 단일 스레드만 접근하는 필드에 붙은 volatile은 얻는 것 없이 최적화만 막는다.

## 한 줄 요약

volatile은 "쓴 값이 다른 스레드에게 반드시 보이고, 그 변수를 기준으로 순서가 뒤집히지 않는다"(가시성 + 재배치 방지)까지만 보장하는 도구라서, 한 스레드가 쓰고 여럿이 읽는 종료 플래그·불변 객체 참조 교체에는 정답이지만, `count++`처럼 읽고-고치고-쓰는 복합 연산은 두 스레드가 각각 최신 값을 정확히 읽고도 갱신이 유실되는 구조이므로 — 가시성 문제가 아니라 끼어들기 문제이므로 — 그 자리에는 CAS(`Atomic*`)나 락을 써야 한다.
