# 데드락 — 스레드 덤프에서 찾는 법, 성립 4조건, 코드 레벨 예방 전략

> 핵심 관전 포인트: **찾는 법은 쉽다 — JVM이 스레드 덤프 맨 끝에 `Found one Java-level deadlock`으로 답을 써 준다. 진짜 실력은 두 군데서 갈린다. 첫째, 4조건(상호 배제 / 점유와 대기 / 비선점 / 순환 대기)을 외운 목록이 아니라 **예방 전략을 뽑아내는 도구**로 쓸 수 있는가 — 넷이 동시에 성립해야 데드락이므로 하나만 깨면 되고, 실무에서 실제로 깰 수 있는 건 순환 대기(전역 락 순서 고정)와 점유·대기(tryLock 타임아웃 + 전부 반납 + 랜덤 백오프) 둘뿐이다. 둘째, **덤프에 deadlock 문구가 없는데 서비스가 멈춰 있는 경우**를 읽어낼 수 있는가 — JVM이 탐지하는 것은 소유자가 명확한 락(`synchronized` 모니터, `ReentrantLock`)이 만든 순환뿐이고, 세마포어 고갈·`CountDownLatch` 상호 대기·커넥션 풀 고갈·DB 행 락 대기는 탐지 대상 바깥이라 각각 `BLOCKED`·`WAITING (parking)`·`TIMED_WAITING`·`RUNNABLE`이라는 다른 얼굴로 나타난다.**

---

## 0. 질문 + 의도

**질문**: "스레드 덤프에서 데드락을 어떻게 찾나요? 데드락의 4가지 조건과 실무적 예방 방법은?"

**출제 의도**: 데드락은 서비스가 "죽지 않고 멈추는" 형태라 재시작으로 덮기 쉽고, 근본 원인을 못 찾으면 반복된다. 덤프를 읽어 락 순환을 찾는 능력은 반복 장애를 끊는 능력이며, 4조건과 예방 전략까지 답할 수 있는지로 재발 방지책을 설계할 수 있는 사람인지를 가린다.

## 1. 스레드 덤프에서 데드락 찾기

### 1-1. 전제 지식 — 데드락은 "죽는" 장애가 아니라 "멈추는" 장애다

**데드락(deadlock, 교착 상태)**은 **두 개 이상의 스레드가 서로가 쥔 자원을 기다리며 영원히 진행하지 못하는 상태**다. 좁은 복도에서 마주친 두 사람이 서로 "네가 먼저 비켜"라며 둘 다 안 움직이는 상황과 같다. 둘 다 살아 있고, 둘 다 상대만 움직여 주면 끝나는데, 그 조건이 서로를 가리키기 때문에 영원히 성립하지 않는다.

이 성질이 운영에서 특히 고약한 이유가 있다. **프로세스가 죽지 않는다.** CPU도 안 태운다(대기 중인 스레드는 잠들어 있으므로). 예외도 안 던진다. 로그도 안 남는다. 겉으로 드러나는 증상은 **"몇몇 API만 응답이 없다"** 뿐이고, 시간이 지나면 그 API를 처리하는 스레드가 하나씩 락에 걸려 쌓이다가 결국 스레드풀이 마르면서 **관련 없는 API까지 함께 죽는다.**

그리고 재시작하면 일단 풀린다. 이것이 데드락이 반복 장애가 되는 이유다 — 재시작으로 덮으면 그날은 넘어가지만, 원인이 그대로 남아 있으므로 트래픽이 비슷하게 몰리는 날 똑같이 재발한다. **증거는 재시작하는 순간 사라지므로, 재시작 전에 스레드 덤프를 뜨는 것이 사실상 유일한 기회다.** 스레드 덤프는 밀리초면 끝나고 운영 중에도 부담이 없으니(`23-jvm-heap-thread-dump.md`), "일단 3장 뜨고 재시작한다"를 장애 대응 절차에 못 박아 두는 것이 좋다.

### 1-2. 가장 빠른 방법 — JVM이 답을 써 준다

덤프를 뜨는 명령은 셋 중 아무거나 좋다.

```bash
jcmd <pid> Thread.print   # 권장
jstack -l <pid>           # -l: j.u.c 락의 소유자 정보까지 함께 출력
kill -3 <pid>             # SIGQUIT. 프로세스는 안 죽고 stdout으로 덤프가 나간다
```

`-l`을 습관으로 붙이는 이유는 1-5에서 설명한다. 여기서는 **뜬 덤프의 맨 아래부터 본다**는 것만 기억하면 된다. JVM은 덤프를 뜰 때 락 대기 관계에 순환이 있는지 스스로 검사해서 결론까지 적어 준다.

```
Found one Java-level deadlock:
=============================
"transfer-2":
  waiting to lock monitor 0x00007f9c0e00a900 (object 0x000000070fe11a48, a com.example.Account),
  which is held by "transfer-1"
"transfer-1":
  waiting to lock monitor 0x00007f9c0e00c8f0 (object 0x000000070fe11a70, a com.example.Account),
  which is held by "transfer-2"

Java stack information for the threads listed above:
===================================================
"transfer-2":
	at com.example.TransferService.transfer(TransferService.java:23)
	- waiting to lock <0x000000070fe11a48> (a com.example.Account)
	- locked <0x000000070fe11a70> (a com.example.Account)
	at com.example.TransferService.lambda$main$1(TransferService.java:12)

"transfer-1":
	at com.example.TransferService.transfer(TransferService.java:23)
	- waiting to lock <0x000000070fe11a70> (a com.example.Account)
	- locked <0x000000070fe11a48> (a com.example.Account)
	at com.example.TransferService.lambda$main$0(TransferService.java:11)

Found 1 deadlock.
```

읽는 순서는 이렇다.

**첫째, 앞부분의 두 문단이 서로를 가리키는지 확인한다.** `"transfer-2"`가 기다리는 락을 `transfer-1`이 쥐고 있고, `"transfer-1"`이 기다리는 락을 `transfer-2`가 쥐고 있다. 이 상호 참조가 곧 순환이다. 스레드가 셋 이상 얽힌 순환이면 A→B→C→A 형태로 이어져 나온다.

**둘째, 주소는 두 종류가 나오는데 뒤쪽을 본다.** `monitor 0x00007f9c...`는 JVM 내부의 모니터 구조체 주소이고, 괄호 안의 `object 0x000000070fe11a48`이 **자바 객체 자체의 주소**다. 아래 스택의 `- waiting to lock <0x...>`과 짝을 맞출 때 쓰는 것은 객체 주소 쪽이다.

**셋째, 괄호의 타입이 "무엇을 두고 싸우는가"를 말해 준다.** 위 예의 `a com.example.Account`는 계좌 객체 두 개를 서로 반대 순서로 잠갔다는 뜻이다. 여기가 `a java.lang.Object`처럼 무의미한 타입으로 나오면 락 객체에 이름이 없다는 뜻이라 조사에 품이 더 든다 — **락 전용 객체를 만들 때 `new Object()` 대신 이름 있는 전용 타입을 쓰면 덤프 가독성이 올라간다**는 실무 팁이 여기서 나온다.

**넷째, `Java stack information` 절의 파일명·줄번호가 곧 고칠 코드다.** 위 예에서는 두 스레드 모두 `TransferService.java:23`에 서 있고, `- locked`와 `- waiting to lock`의 주소가 **정확히 반대로 짝지어져** 있다. "같은 메서드에 두 스레드가 서로 반대 순서로 들어와 있다" — 락 순서 문제라는 진단이 이 한 화면에서 끝난다.

### 1-3. 수동으로 찾기 — 락 주소로 사이클 추적

자동 탐지가 있는데 왜 수동 추적을 알아야 하는가. **자동 탐지에 안 잡히는 교착(1-5)을 만났을 때 쓰는 방법이 이것**이기 때문이다. 절차는 세 단계다.

1. 상태가 `BLOCKED (on object monitor)`인 스레드를 모은다. `ReentrantLock` 대기는 `BLOCKED`가 아니라 `WAITING (parking)` + `parking to wait for <0x...>` 형태로 나오므로 함께 걷는다.
2. 각 스레드의 `- waiting to lock <주소>`(못 잡아서 기다리는 락)와 `- locked <주소>`(이미 쥔 락)를 뽑는다.
3. "A가 기다리는 락을 B가 쥐었고, B가 기다리는 락을 A가 쥐었다"는 고리가 생기는지 본다.

```
"Thread-A": BLOCKED (on object monitor)
    - waiting to lock <0x...c90>     (B가 쥔 락)
    - locked <0x...c80>              (A가 쥔 락)

"Thread-B": BLOCKED (on object monitor)
    - waiting to lock <0x...c80>     (A가 쥔 락)  -> 고리 성립
    - locked <0x...c90>
```

여기에 반드시 붙어 다니는 주의가 하나 있다. **락 주소 짝 맞추기는 한 덤프 안에서만 유효하다.** 주소는 객체의 현재 메모리 위치이고, GC가 객체를 옮기면 값이 바뀐다. 1장의 `waiting to lock` 주소를 3장의 `locked`와 대조하면 아무 의미 없는 비교가 된다.

### 1-4. 코드에 상시 탐지를 심어 두기

덤프는 "장애가 났을 때 사람이 뜨는 것"이라 한계가 있다. **재현이 어려운 데드락은 아무도 안 보는 새벽에 잠깐 걸렸다 재시작으로 풀리기를 반복한다.** 그래서 런타임에 스스로 감지하게 만들어 두는 편이 낫다.

```java
private static final ThreadMXBean MX = ManagementFactory.getThreadMXBean();

// 헬스체크나 1분 주기 스케줄러에서 호출한다. 비용은 스레드 수에 비례하는 정도라
// 이 주기에서는 사실상 무시할 수 있다.
public void checkDeadlock() {
    // 모니터 락과 j.u.c의 "소유자가 있는 락"이 만든 순환을 함께 본다.
    // (모니터 락만 보려면 findMonitorDeadlockedThreads())
    long[] ids = MX.findDeadlockedThreads();

    // 데드락이 없으면 빈 배열이 아니라 null을 돌려준다. 이 분기를 빠뜨리면
    // 곧바로 NPE가 나므로 자주 틀리는 지점이다.
    if (ids == null) return;

    // 걸린 스레드의 스택을 그 자리에서 로그로 남긴다.
    // 사람이 덤프를 뜨러 오는 시점에는 이미 재시작으로 증거가 사라졌을 수 있으므로,
    // "감지한 순간의 스택"을 확보해 두는 것이 이 코드의 핵심 가치다.
    for (ThreadInfo info : MX.getThreadInfo(ids, true, true)) {
        log.error("deadlocked thread: {}\n{}", info.getThreadName(), info);
    }
    alerting.fire("java-level deadlock detected");
}
```

**감지했다고 자동으로 풀 수는 없다는 점**은 분명히 해 둬야 한다. 자바에는 남이 쥔 락을 강제로 뺏는 수단이 없으므로(2-1의 비선점 조건), 이 코드가 하는 일은 **알림과 증거 확보**까지다. 그다음은 사람이 판단해 인스턴스를 교체하거나 롤백한다.

### 1-5. 함정 — 덤프에 deadlock 문구가 없는데 멈춰 있다 (시니어 변별 포인트)

여기가 이 문서에서 가장 중요한 절이다. **"Found deadlock이 없으니 데드락이 아니다"는 답이 오답인 이유**를 알아야 한다.

JVM의 자동 탐지가 하는 일은 **대기 그래프에서 순환을 찾는 것**이다. 그런데 그래프를 그리려면 화살표가 필요하고, 화살표를 그리려면 **"이 락을 지금 누가 쥐고 있는가"**를 알아야 한다. JVM이 그 소유자를 아는 것은 두 종류뿐이다.

- **`synchronized` 모니터** — JVM이 직접 구현한 락이라 소유 스레드를 자기가 안다.
- **`java.util.concurrent`의 배타 소유 락** — `ReentrantLock`, `ReentrantReadWriteLock`의 쓰기 락처럼 내부 동기화기가 `exclusiveOwnerThread` 필드에 소유자를 기록해 두는 것들. JVM이 이 필드를 읽어 화살표를 그린다.

**소유자라는 개념 자체가 없는 대기는 그래서 탐지 대상이 아니다.** 세마포어는 허가증(permit) 개수만 셀 뿐 "이 허가증은 누구 것"을 기록하지 않는다. `CountDownLatch`는 카운트가 0이 되기를 기다릴 뿐 특정 스레드를 기다리는 것이 아니다. DB의 행 락은 애초에 JVM 바깥, 다른 프로세스 안의 일이다. **화살표를 그릴 수 없으니 순환도 찾을 수 없다.**

그래서 "멈춰 있는데 문구가 없다"는 상황은 다음 중 하나다. 각각이 덤프에서 어떤 얼굴로 나타나는지가 판별의 열쇠다.

| 실제 원인 | 덤프에서의 모습 | 자동 탐지 |
|---|---|---|
| `synchronized` 순환 | `BLOCKED (on object monitor)` + `waiting to lock <0x..>` | 잡힌다 |
| `ReentrantLock` 순환 | `WAITING (parking)` + `parking to wait for <0x..> (a ...ReentrantLock$NonfairSync)` | 잡힌다 |
| 세마포어 고갈 | `WAITING (parking)` + `...Semaphore$NonfairSync` | 못 잡는다 |
| `CountDownLatch` 상호 대기 | `WAITING (parking)` + `...CountDownLatch$Sync` | 못 잡는다 |
| 커넥션 풀 고갈 | `TIMED_WAITING (parking)` + `HikariPool.getConnection` | 못 잡는다 |
| DB 행 락 대기 | `RUNNABLE` + `socketRead0` (JDBC 소켓 대기) | 못 잡는다 |
| 스레드풀 상호 대기 | `WAITING` + `Future.get` 또는 `LinkedBlockingQueue.take` | 못 잡는다 |

표를 세 갈래로 정리하면 이렇게 읽힌다.

**첫째, 상태값만 보고 판단하면 정확히 반대로 오판한다.** `BLOCKED`는 **`synchronized` 진입 대기에만** 붙는 상태다. 현대 자바 코드가 훨씬 많이 쓰는 `ReentrantLock`·세마포어·커넥션 풀은 전부 자바 코드로 구현된 라이브러리이고, 그 안에서 스레드는 `LockSupport.park()`로 멈춘다. JVM 입장에서는 그냥 "누가 어떤 객체를 두고 park 해 있다"로만 보이므로 **`WAITING (parking)`**으로 찍힌다. **"BLOCKED가 하나도 없으니 락 문제는 아니네요"가 가장 흔한 오답인 이유가 이것이다.**

**둘째, `parking to wait for` 뒤의 괄호 안 타입이 진짜 정보다.** `ReentrantLock$NonfairSync`인지 `Semaphore$NonfairSync`인지 `CountDownLatch$Sync`인지에 따라 원인도 대응도 완전히 달라진다. 상태값은 셋 다 똑같이 `WAITING (parking)`이다.

**셋째, `RUNNABLE`인데 멈춰 있는 경우를 반드시 의심한다.** DB에서 행 락을 기다리는 스레드는 JDBC 드라이버 안에서 소켓 응답을 기다리는 중이고, 소켓 읽기는 JVM이 `RUNNABLE`로 표시한다. **CPU는 하나도 안 쓰는데 상태는 RUNNABLE인 스레드 뭉치**가 보이면 대개 외부 대기다. 이 경우 답은 자바 쪽 덤프가 아니라 DB 쪽에 있다 — PostgreSQL이라면 `pg_locks`와 `pg_stat_activity`를 조인해 누가 누구를 막고 있는지 봐야 한다.

여기에 하나 더 붙는 것이 **라이브락(livelock)**이다. 데드락이 "둘 다 멈춰서 진전이 없는" 것이라면, 라이브락은 **"둘 다 계속 움직이는데 진전이 없는"** 상태다. 복도에서 마주친 두 사람이 서로 비켜 주려다 같은 쪽으로 계속 움직이는 상황이다. 스레드 상태는 `RUNNABLE`이고 CPU도 태우므로 데드락과 증상이 정반대다. **한 장으로는 절대 못 잡고, 3~5초 간격으로 여러 장을 떠서 "스택이 계속 바뀌는데 일은 안 끝난다"를 확인해야만 보인다.** 3-4의 tryLock 재시도에 백오프를 안 넣으면 데드락이 이 형태로 변질된다.

마지막으로 `jstack -l`을 습관으로 붙이라고 한 이유. `-l` 옵션은 각 스레드 아래에 **"Locked ownable synchronizers"** 섹션을 함께 출력한다. 여기에 그 스레드가 쥐고 있는 `j.u.c` 락 목록이 나오므로, `parking to wait for`의 주소를 이 섹션들과 대조해 **자동 탐지가 못 그린 화살표를 사람이 직접 그릴 수** 있다. `-l`이 없으면 "기다리는 쪽"만 보이고 "쥔 쪽"이 안 보여서 추적이 거기서 끊긴다.

## 2. 성립 4조건 — 외울 목록이 아니라 예방 전략을 뽑는 도구

### 2-1. 네 조건과 각각을 깨면 왜 데드락이 불가능해지는가

데드락이 성립하려면 **네 가지 조건이 동시에 만족돼야 한다.** 1971년 코프먼(Coffman)이 정리해서 **코프먼 조건**이라 부른다. 중요한 것은 개수나 이름이 아니라 **"동시에"**라는 단어다. 넷이 모두 있어야 성립하므로 **하나만 깨면 데드락은 구조적으로 불가능해진다.** 예방 전략은 전부 여기서 유도된다.

하나씩, "이걸 깨면 왜 불가능해지는가"와 함께 본다.

**상호 배제(mutual exclusion)** — 자원을 한 번에 한 스레드만 쓸 수 있다는 조건이다. 이게 없으면 애초에 **기다릴 일이 없으므로** 대기 그래프 자체가 만들어지지 않는다. 깨는 방법은 락을 안 쓰는 것 — 불변 객체를 쓰거나, CAS 기반 자료구조로 바꾸거나, 자원을 아예 스레드마다 하나씩 나눠 주는(스레드 한정) 방식이다.

**점유와 대기(hold and wait)** — 이미 자원을 쥔 채로 다른 자원을 기다린다는 조건이다. 이게 없으면, 즉 **필요한 락을 한 번에 다 얻거나 아니면 아무것도 안 쥐거나** 둘 중 하나만 가능하다면, "쥔 것이 있는 상태로 기다리는 스레드"가 존재하지 않는다. 대기 그래프의 화살표는 **쥔 것이 있는 스레드에서만 출발**하므로 화살표를 그릴 주체가 사라진다.

**비선점(no preemption)** — 남이 쥔 자원을 강제로 뺏을 수 없다는 조건이다. 뺏을 수 있다면 순환이 생겨도 심판이 하나를 뺏어서 고리를 끊을 수 있다. DB가 데드락을 만나면 하는 일이 정확히 이것이다 — 한쪽 트랜잭션을 강제로 abort 시켜 자원을 회수한다.

**순환 대기(circular wait)** — 대기 관계가 원을 이룬다는 조건이다. 이걸 깨면 왜 안전한지가 가장 덜 자명한데, 이유가 명확하다. **대기 그래프에 원이 없으면(방향 비순환 그래프이면) 아무도 기다리지 않는 스레드가 반드시 최소 하나 존재한다.** 그 스레드는 필요한 걸 다 쥐었으니 일을 끝내고 락을 놓을 수 있고, 그러면 그를 기다리던 스레드가 풀리고, 그렇게 도미노처럼 전부 풀린다. **원이 없으면 반드시 끝난다**는 것이 이 조건의 힘이다.

### 2-2. 조건과 대응 전략을 짝지어 보기

| 조건 | 뜻 | 이걸 깨는 방법 | 실무에서 깰 수 있는가 |
|---|---|---|---|
| 상호 배제 | 자원을 한 번에 한 스레드만 쓴다 | 불변 객체, CAS·동시성 컬렉션, 스레드 한정 | 거의 못 깬다 — 락을 쓰는 이유 자체를 부정하는 것 |
| 점유와 대기 | 쥔 채로 다른 것을 기다린다 | 필요한 락을 한 번에 전부 획득, 실패 시 전부 반납 | **가능 — 차선책의 본체(3-4)** |
| 비선점 | 남의 락을 뺏을 수 없다 | (자바에는 뺏는 수단이 없음) 타임아웃·인터럽트로 스스로 포기 | 부분적으로만 — "뺏기"가 아니라 "제 발로 물러나기" |
| 순환 대기 | 대기 관계가 원을 이룬다 | 전역 락 순서 고정 | **가능하고 가장 실용적(3-2)** |

**표의 오른쪽 칸이 이 절의 결론이다.** 조건 네 개를 나란히 나열하면 넷 다 선택지처럼 보이지만, 실제로 코드로 옮길 수 있는 것은 둘뿐이다.

**상호 배제는 사실상 못 깬다.** 여러 스레드가 동시에 고칠 수 없는 자원이라서 락을 거는 것이지, 락이 없어도 되는 자원이면 처음부터 안 걸었을 것이다. 다만 이 조건이 완전히 쓸모없는 것은 아니다 — **"이 자리에 정말 락이 필요한가"를 되묻는 체크포인트**로는 값을 한다. `ConcurrentHashMap`으로 바꾸거나 불변 객체로 만들어 락 자체를 없앨 수 있는 자리가 실무에는 꽤 있다.

**비선점도 자바에서는 못 깬다.** `Thread.stop()`은 오래전에 폐기됐고, 남이 쥔 `synchronized` 모니터를 강제로 회수하는 API는 존재하지 않는다. 대신 **"뺏기"를 "스스로 물러나기"로 바꾼 근사치**는 있다. `ReentrantLock.tryLock(timeout)`으로 시간 안에 못 잡으면 포기하거나, `lockInterruptibly()`로 다른 스레드가 인터럽트를 걸어 대기를 중단시키는 방식이다. 엄밀히는 점유·대기 조건을 깨는 쪽에 가깝다.

**그래서 실무의 답은 순환 대기와 점유·대기, 둘로 좁혀진다.** 순서를 통제할 수 있으면 순환 대기를 깨고(3-2), 통제할 수 없으면 점유·대기를 깬다(3-4). 이 우선순위까지 말할 수 있어야 조건을 외운 것이 아니라 쓸 줄 아는 것으로 보인다.

## 3. 실무 예방 — 락 순서 고정이 정석, tryLock이 차선책

### 3-1. 계좌 이체 — 데드락이 만들어지는 과정을 한 단계씩

교과서 사례가 계좌 이체인 이유는 **"인자로 받은 순서대로 잠그는" 지극히 자연스러운 코드가 그대로 데드락**이기 때문이다.

```java
// (문제) 인자로 받은 순서대로 잠근다 — 호출 방향에 따라 잠금 순서가 뒤집힌다
public void transfer(Account from, Account to, long amount) {
    synchronized (from) {
        synchronized (to) {
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}
```

이 코드 자체에는 아무 이상이 없어 보인다. 문제는 **누군가 반대 방향의 이체를 동시에 호출할 때** 드러난다. `transfer(A, B)`와 `transfer(B, A)`가 나란히 실행되는 순간을 시간순으로 따라가 보자.

```
시각      스레드 1: transfer(A, B)          스레드 2: transfer(B, A)          락 상태
─────────────────────────────────────────────────────────────────────────────────────
t1       A의 락 획득 (성공)                                                  A: 스레드1
t2                                          B의 락 획득 (성공)               A: 스레드1, B: 스레드2
t3       B의 락 요청 -> 스레드2가 쥠                                          스레드1 대기 시작
         (BLOCKED. A는 쥔 채로 기다린다)
t4                                          A의 락 요청 -> 스레드1이 쥠      스레드2 대기 시작
                                            (BLOCKED. B는 쥔 채로 기다린다)
t5       두 스레드 모두 "상대가 락을 놓으면" 진행할 수 있다.
         그런데 상대가 락을 놓는 조건은 "자기가 원하는 락을 얻는 것"이다.
         조건이 서로를 가리키므로 영원히 성립하지 않는다.
```

t3와 t4가 핵심이다. **두 스레드 모두 "이미 하나를 쥔 채로" 다른 하나를 기다린다**(점유와 대기). 그리고 그 기다림이 원을 이룬다(순환 대기). 대기 관계를 그림으로 그리면 원이 눈에 보인다.

```
        기다림                소유
스레드1 ───────► 락 B ───────► 스레드2
   ▲                              │
   │ 소유                         │ 기다림
   └───────── 락 A ◄──────────────┘
```

이 원을 없애는 방법이 두 가지고, 그것이 그대로 아래 두 절이다.

### 3-2. 정석 — 전역 락 순서 고정 (순환 대기 깨기)

규칙은 한 문장이다. **"어떤 스레드든 락 두 개를 모두 잡아야 한다면, 반드시 정해진 전역 순서로만 잡는다."**

이 규칙이 통하는 이유를 3-1의 그림으로 되짚어 보면 명확하다. 모든 스레드가 "번호가 작은 것 먼저"라는 같은 규칙을 따르면, **"큰 것을 쥐고 작은 것을 기다리는 스레드"가 존재할 수 없다.** 화살표가 전부 한 방향(작은 번호 → 큰 번호)으로만 그려지므로 원이 만들어질 수 없다.

문제는 계좌 이체처럼 **락 객체가 런타임에 정해지는 경우**다. `from`과 `to`가 매 호출마다 바뀌므로 소스 코드에 순서를 못 박을 수가 없다. 답은 **객체 자체가 아니라 객체가 가진 고유값으로 순서를 정하는 것**이다.

```java
// (개선) 락 순서를 계좌 ID라는 전역 기준으로 정규화한다
public void transfer(Account from, Account to, long amount) {
    // 자기 자신에게 보내는 이체는 여기서 걸러낸다.
    // 안 걸러내면 아래에서 같은 락을 두 번 잡게 되는데,
    // synchronized는 재진입 가능해서 데드락은 안 나지만
    // 출금과 입금이 같은 계좌에 일어나 잔액 계산이 꼬인다.
    if (from.id() == to.id()) {
        throw new IllegalArgumentException("self transfer");
    }

    // 이체 방향과 무관하게, 항상 "ID가 작은 계좌"를 먼저 잠근다.
    // 모든 스레드가 같은 기준을 쓰므로 대기 그래프에 원이 생길 수 없다.
    Account first  = from.id() < to.id() ? from : to;
    Account second = from.id() < to.id() ? to   : from;

    synchronized (first) {
        synchronized (second) {
            // 락을 잡는 순서와 실제 도메인 동작의 순서는 별개다.
            // 잠금은 first/second 순서로, 계산은 from/to 순서로 한다.
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}
```

**ID처럼 쓸 만한 고유값이 없다면** `System.identityHashCode(obj)`를 기준으로 삼는다. 이것은 **객체마다 JVM이 부여하는 신원 해시값**으로, 클래스가 `hashCode()`를 어떻게 재정의했든 상관없이 원본 신원 해시를 돌려준다(그래서 `identity`다). 그런데 여기에 함정이 하나 있다 — **서로 다른 객체의 identityHashCode가 같을 수 있다.** 32비트 값이라 개수가 많아지면 충돌이 난다.

동률이면 "작은 것 먼저"라는 규칙이 순서를 정해 주지 못하므로, 두 스레드가 다시 반대 순서로 잡을 수 있다. 그래서 정석 풀이는 **동률일 때만 쓰는 제3의 락(타이 브레이킹 락)을 하나 더 두는 것**이다.

```java
// 동률일 때만 잡는 전용 락. 클래스당 하나만 있으면 된다.
private static final Object TIE_LOCK = new Object();

public void transfer(Account from, Account to, long amount) {
    int fromHash = System.identityHashCode(from);
    int toHash   = System.identityHashCode(to);

    if (fromHash < toHash) {
        synchronized (from) { synchronized (to) { doTransfer(from, to, amount); } }
    } else if (fromHash > toHash) {
        synchronized (to) { synchronized (from) { doTransfer(from, to, amount); } }
    } else {
        // 해시가 같아 순서를 정할 수 없는 드문 경우.
        // 모든 스레드가 반드시 TIE_LOCK부터 잡게 만들면, 이 구간에는
        // 한 번에 한 스레드만 들어오므로 두 계좌를 어떤 순서로 잡든 안전하다.
        // 드물게만 타는 경로라 이 직렬화 비용은 문제가 되지 않는다.
        synchronized (TIE_LOCK) {
            synchronized (from) { synchronized (to) { doTransfer(from, to, amount); } }
        }
    }
}
```

이 패턴은 『Java Concurrency in Practice』의 정석 풀이다. 면접에서 여기까지 말하면 "락 순서 고정"을 구호가 아니라 구현 수준에서 이해하고 있다는 신호가 된다.

**규칙을 팀 전체에 강제하는 방법도 함께 생각해야 한다.** 락 순서 고정의 최대 약점은 **문서로만 존재하는 규칙이라는 점**이다. 새로 합류한 사람이 모르고 반대 순서로 잡으면 그대로 데드락이 부활한다. 그래서 실무에서는 규칙을 코드 구조로 바꾼다 — **락을 잡는 코드를 한 유틸리티에 캡슐화**해서 그 함수를 통해서만 두 락을 잡게 하거나(아래), 애초에 **락을 두 개 잡을 일이 없게 설계**한다(3-5).

```java
// 두 자원을 함께 잠그는 유일한 통로를 만들어 둔다.
// 호출자는 순서를 신경 쓸 수 없고, 신경 쓸 필요도 없다.
public static <T> void withOrderedLocks(Lockable a, Lockable b, Runnable body) {
    Lockable first  = a.lockKey() < b.lockKey() ? a : b;
    Lockable second = a.lockKey() < b.lockKey() ? b : a;
    synchronized (first) { synchronized (second) { body.run(); } }
}
```

**규칙은 사람이 어기지만 구조는 어길 수 없다.**

### 3-3. 락 순서를 통제할 수 없는 상황들

3-2가 항상 되는 것은 아니다. 순서를 코드로 강제할 수 없는 경우가 실제로 있다.

**서드파티 라이브러리가 내부에서 락을 잡을 때.** 우리 코드가 락 X를 쥔 채 라이브러리 메서드를 부르는데, 그 안에서 락 Y를 잡는다면 우리는 Y의 존재조차 모른다. 반대 방향의 호출 경로가 어딘가에 있으면 순환이 생긴다.

**콜백 안에서 락을 잡을 때.** 우리가 락을 쥔 채 남이 등록한 콜백을 부르면, 그 콜백이 무슨 락을 잡을지 우리는 통제할 수 없다. 이렇게 **락을 쥔 채로 우리가 제어하지 못하는 외부 코드를 호출하는 것**을 열린 호출의 반대말로 부르는데, 반대로 **락을 놓은 뒤에 외부를 호출하는 것을 열린 호출(open call)**이라 한다. 가능하면 항상 열린 호출로 만든다.

**락 객체가 프레임워크 내부에 있을 때.** ORM, 커넥션 풀, 캐시 라이브러리 내부 락은 우리 순서 규칙 바깥에 있다.

이런 상황에서 쓰는 것이 다음 절의 차선책이다.

### 3-4. 차선책 — tryLock 타임아웃 + 전부 반납 + 랜덤 백오프 (점유와 대기 깨기)

`synchronized`는 한번 기다리기 시작하면 **중간에 포기할 방법이 없다.** 인터럽트로 깨울 수도 없다. 그래서 이 전략을 쓰려면 도구를 `ReentrantLock`으로 바꿔야 한다.

```java
// (개선) 정해진 시간 안에 둘 다 못 잡으면, 쥔 것을 전부 놓고 물러났다가 다시 시도한다
public boolean transfer(Account from, Account to, long amount) throws InterruptedException {
    while (true) {
        if (from.lock().tryLock(200, TimeUnit.MILLISECONDS)) {
            try {
                if (to.lock().tryLock(200, TimeUnit.MILLISECONDS)) {
                    try {
                        from.withdraw(amount);
                        to.deposit(amount);
                        return true;           // 둘 다 잡았을 때만 실제 작업
                    } finally {
                        to.lock().unlock();
                    }
                }
                // 두 번째 락을 못 잡았다. 여기서 그냥 다시 시도하면 안 된다 —
                // 첫 번째 락은 여전히 쥔 채이므로 점유와 대기가 그대로 남는다.
            } finally {
                from.lock().unlock();          // 반드시 첫 번째 락까지 놓고 나간다
            }
        }
        // 놓았으면 잠깐 쉬었다 다시 온다. 이 sleep이 없으면 두 스레드가
        // 같은 박자로 잡았다 놨다를 무한 반복하는 라이브락이 된다.
        Thread.sleep(ThreadLocalRandom.current().nextLong(10, 50));
    }
}
```

이 코드에서 반드시 짚어야 할 것이 셋이다.

**첫째, 이것은 데드락을 예방하는 게 아니라 걸려도 빠져나오게 하는 전략이다.** 두 스레드가 여전히 반대 순서로 락을 잡으려 하고, 여전히 서로를 막는다. 다만 200ms 뒤에 스스로 포기하고 물러나므로 영구 교착이 되지 않을 뿐이다. **예방(3-2)이 가능하면 그쪽이 언제나 낫다.**

**둘째, 실패했을 때 쥐고 있던 락을 전부 놓아야 한다.** 위 코드의 `finally { from.lock().unlock(); }`이 그 일을 한다. 이 한 줄을 빠뜨리고 안쪽만 재시도하면 **점유와 대기 조건이 그대로 남아서** 아무것도 해결되지 않는다. 이것이 "점유와 대기를 깬다"는 말의 실체다.

**셋째, 랜덤 백오프가 없으면 라이브락으로 변질된다.** 두 스레드가 정확히 같은 타이밍에 실패하고 같은 타이밍에 재시도하면, 다시 같은 순서로 락을 잡고 다시 같이 실패한다. CPU만 태우면서 영원히 진전이 없다. **대기 시간에 무작위를 섞어 박자를 어긋나게 만드는 것**이 해법이고, 네트워크 재시도에 지수 백오프와 지터를 넣는 것과 같은 이유다.

그리고 실무에서는 **무한 루프 대신 재시도 횟수 상한**을 두는 편이 낫다. 몇 번 시도해도 안 되면 실패로 응답하고 로그를 남긴다 — 무한히 도는 것보다 "이체 요청 3건이 락 경합으로 실패했다"는 지표가 남는 편이 운영에 훨씬 유용하다.

### 3-5. 가장 좋은 답 — 애초에 락을 두 개 잡지 않는다

3-2와 3-4는 **락을 두 개 잡는다는 전제** 위에 서 있다. 그 전제를 없애는 것이 언제나 더 강한 해법이다.

**잠글 단위를 하나로 합친다.** 계좌 두 개를 각각 잠그는 대신, "이체"라는 상위 개념 하나를 잠근다. 동시성은 떨어지지만 데드락은 구조적으로 불가능해진다. 트래픽이 감당 가능한 수준이라면 이 단순함이 이긴다.

**접근을 단일 스레드로 직렬화한다.** 해당 자원에 대한 요청을 큐에 넣고 전담 스레드 하나가 순서대로 처리하는 방식이다. 락이 아예 없어지므로(상호 배제 조건 자체가 사라진다) 데드락도 없다. 액터 모델이나 이벤트 루프가 이 구조다.

**락 대신 DB의 낙관적 갱신으로 옮긴다.** 버전 컬럼을 두고 `UPDATE ... WHERE id = ? AND version = ?`로 갱신한 뒤, 갱신된 행이 0이면 다른 트랜잭션이 먼저 바꾼 것이므로 재시도한다. 애초에 아무것도 붙잡고 있지 않으므로 점유와 대기가 성립하지 않는다.

**락 구간을 좁혀 중첩이 생길 여지를 없앤다.** 락 안에서 하는 일이 적을수록 그 안에서 또 다른 락을 잡을 확률도 낮아진다.

그리고 마지막으로, 이건 데드락 조건을 깨는 것은 아니지만 반드시 함께 말해야 하는 규칙이 있다. **락을 쥔 채로 외부 호출(HTTP, DB, 다른 서비스, 남이 등록한 콜백)을 하지 않는다.** 락을 쥔 시간이 상대 시스템의 응답 시간에 종속되면, 상대가 느려지는 순간 우리 쪽 락 대기가 폭발한다. 3-3에서 본 대로 콜백 안에서 무슨 락을 잡을지도 예측할 수 없다. **실무에서 데드락과 구분이 안 되는 "사실상의 멈춤"을 만드는 가장 흔한 원인이 이것이다.**

### 3-6. DB의 데드락도 같은 원리다

**DB 레벨의 데드락도 본질은 똑같이 순환 대기다.** 트랜잭션 1이 행 A를 잠그고 행 B를 기다리는데, 트랜잭션 2가 행 B를 잠그고 행 A를 기다리는 상황이다. 자바 락의 자리에 행 락이 들어갔을 뿐 그림은 3-1과 동일하다.

```sql
-- (문제) 갱신 순서가 요청마다 달라진다
UPDATE account SET balance = balance - 1000 WHERE id = 7;   -- 트랜잭션 1: 7 -> 3
UPDATE account SET balance = balance + 1000 WHERE id = 3;

UPDATE account SET balance = balance - 500  WHERE id = 3;   -- 트랜잭션 2: 3 -> 7
UPDATE account SET balance = balance + 500  WHERE id = 7;

-- (개선) 어떤 요청이든 항상 PK 오름차순으로 잠근다.
-- 여러 행을 잠글 때도 마찬가지 — ORDER BY id로 정렬한 뒤 순서대로 잠근다.
SELECT * FROM account WHERE id IN (3, 7) ORDER BY id FOR UPDATE;
```

자바와 다른 점이 하나 있고, 그것이 오히려 중요하다. **DB는 데드락을 탐지할 뿐 아니라 직접 풀어 준다.** PostgreSQL은 락 대기가 `deadlock_timeout`(기본 1초)을 넘으면 그때 순환을 검사하고, 순환이 발견되면 **한쪽 트랜잭션을 강제로 abort 시킨다.** 애플리케이션은 `40P01 deadlock detected` 오류를 받는다.

이것이 2-1의 **비선점 조건을 DB가 깨는 방식**이다. 자바 JVM은 탐지만 하고 아무것도 못 하지만, DB는 자원을 강제 회수할 권한이 자기에게 있으므로 뺏을 수 있다.

그래서 애플리케이션 쪽 대응이 자바와 달라진다. **`40P01`은 재시도하면 대부분 성공하는 오류**다 — 한쪽이 죽었으니 다른 쪽은 이미 통과했고, 재시도하면 경합 상대가 없다. 다만 **재시도는 트랜잭션 전체를 다시 시작해야** 하고(abort된 트랜잭션 안에서는 아무 쿼리도 못 돈다), 여기에도 랜덤 백오프를 넣어야 하며, **재시도해도 부작용이 없는 멱등한 작업인지**를 먼저 확인해야 한다. 그리고 근본 해법은 언제나 **갱신 순서 통일**이다 — 재시도는 증상 완화이고 순서 고정이 원인 제거다.

## 4. 꼬리질문 대비 포인트

### "스레드 덤프에 `Found deadlock`이 없는데 API가 전부 타임아웃 납니다. 데드락이 아닌 거죠?" (시니어 변별 포인트)

**"문구가 없으니 데드락이 아니다"가 오답이라는 것을 아는지가 이 질문의 전부다.**

JVM의 자동 탐지는 **소유자를 알 수 있는 락**이 만든 순환만 찾는다. `synchronized` 모니터와 `ReentrantLock`처럼 소유 스레드를 기록하는 락은 화살표를 그릴 수 있지만, **세마포어(허가증에 주인이 없다), `CountDownLatch`(카운트를 기다릴 뿐 특정 스레드를 기다리는 게 아니다), 커넥션 풀, DB 행 락**은 화살표 자체를 그릴 수 없어 탐지 대상이 아니다.

그래서 확인은 상태값이 아니라 **스택의 위치**로 한다.

**`BLOCKED`가 없다고 락 문제가 아닌 게 아니다.** `BLOCKED`는 `synchronized` 진입 대기에만 붙는다. `ReentrantLock`·세마포어·커넥션 풀 대기는 전부 `WAITING (parking)`이나 `TIMED_WAITING (parking)`으로 나오고, 진짜 정보는 `parking to wait for <0x..>` 뒤의 **괄호 안 타입**(`ReentrantLock$NonfairSync`인지 `Semaphore$NonfairSync`인지)에 있다.

**`RUNNABLE`인데 멈춰 있는 뭉치를 의심한다.** DB 행 락을 기다리는 스레드는 JDBC 소켓 읽기에서 대기하므로 `RUNNABLE`로 찍힌다. CPU를 안 쓰는데 `RUNNABLE`이면 대개 외부 대기이고, 답은 자바가 아니라 DB 쪽에 있다 — PostgreSQL이면 `pg_locks`와 `pg_stat_activity`를 봐야 한다.

**여러 장을 뜬다.** 3~5초 간격 3~5장을 비교해서, 같은 스레드가 같은 위치에 계속 있으면 갇힌 것이고 위치가 조금씩 움직이는데 일이 안 끝나면 라이브락이다.

**`jstack -l`로 다시 뜬다.** `-l`이 각 스레드의 "Locked ownable synchronizers"를 출력해 주므로, 자동 탐지가 못 그린 화살표를 사람이 대조해 그릴 수 있다.

### "그럼 `tryLock` 타임아웃을 쓰면 데드락 걱정은 끝인가요?"

**아니다. 세 가지를 함께 말해야 답이 완성된다.**

**첫째, 이건 예방이 아니라 탈출이다.** 두 스레드는 여전히 반대 순서로 락을 잡으려 하고 여전히 서로를 막는다. 다만 정해진 시간 뒤에 스스로 물러날 뿐이다. **순서를 통제할 수 있는 상황이라면 락 순서 고정이 언제나 우선**이고, tryLock은 서드파티 라이브러리나 콜백처럼 순서를 강제할 수 없을 때의 차선책이다.

**둘째, 실패 시 쥔 락을 전부 놓아야 의미가 있다.** 두 번째 락을 못 잡았는데 첫 번째를 쥔 채로 재시도하면 점유와 대기 조건이 그대로 남아서 아무것도 나아지지 않는다.

**셋째, 랜덤 백오프가 없으면 라이브락이 된다.** 두 스레드가 같은 박자로 잡았다 놨다를 반복하며 CPU만 태우고 진전이 없는 상태로 변질된다. 데드락은 멈춰 있으니 덤프로 잡히기라도 하지만, 라이브락은 `RUNNABLE`로 계속 움직이므로 여러 장을 비교해야만 보인다. **어떤 의미로는 더 나쁘게 만든 셈**이라 백오프는 선택이 아니라 필수다.

덧붙여, tryLock으로 바꾸는 순간 **호출자가 실패를 처리해야 한다.** "락을 못 잡아서 못 했다"는 결과를 API 응답이나 재시도 큐로 어떻게 흘려보낼지가 함께 설계돼야 하고, 이 부분이 빠지면 조용히 유실되는 요청이 생긴다.

### "락 순서 고정이 정답이라면, 팀 전체가 그 순서를 지키게 어떻게 만드나요?"

**이 질문은 "규칙과 구조의 차이"를 아는지 보는 질문이다.**

락 순서 고정의 최대 약점은 **문서에만 존재하는 규칙이라는 점**이다. 규칙을 아는 사람이 있는 동안은 잘 돌아가고, 새로 합류한 사람이 모르고 반대 순서로 잡는 순간 데드락이 부활한다. 코드 리뷰로 잡으려 해도 두 락을 잡는 코드가 서로 다른 파일에 흩어져 있으면 사람 눈에 안 보인다.

그래서 답은 **규칙을 구조로 바꾸는 것**이다.

**락 획득을 한 곳에 캡슐화한다.** 두 자원을 함께 잠그는 유일한 통로가 되는 유틸리티 메서드를 만들고, 그 안에서 정렬을 처리한다. 호출자는 순서를 정할 기회 자체가 없다.

**락 두 개를 잡을 일 자체를 없앤다.** 잠글 단위를 상위 개념 하나로 합치거나, 접근을 단일 스레드 큐로 직렬화하거나, DB 낙관적 갱신으로 옮긴다. **규칙은 사람이 어기지만 구조는 어길 수 없다.**

**탐지를 상시로 돌린다.** `ThreadMXBean.findDeadlockedThreads()`를 헬스체크에 심어 두면, 규칙이 깨졌을 때 장애가 아니라 알림으로 먼저 알 수 있다. 감지해도 자동으로 풀 수는 없지만(자바에는 락을 뺏는 수단이 없다), **걸린 순간의 스택을 로그로 남겨 두는 것만으로도** 재현이 어려운 데드락 추적에서 결정적인 증거가 된다.

### "DB에서 나는 데드락도 같은 건가요? 자바 데드락과 대응이 어떻게 다른가요?"

**본질은 같고 대응은 다르다.**

본질이 같다는 것부터. 트랜잭션 1이 행 A를 잠그고 B를 기다리는데 트랜잭션 2가 B를 잠그고 A를 기다리면 순환 대기가 성립한다. 예방책도 동일하다 — **여러 행을 갱신할 때 항상 같은 순서(예: PK 오름차순)로 잠근다.** `SELECT ... FOR UPDATE`에 `ORDER BY id`를 붙이는 것이 그 구현이다.

대응이 다른 지점이 중요하다. **DB는 탐지만 하는 게 아니라 직접 풀어 준다.** PostgreSQL은 락 대기가 `deadlock_timeout`(기본 1초)을 넘으면 순환을 검사하고, 발견되면 한쪽 트랜잭션을 강제로 abort 시킨 뒤 `40P01 deadlock detected` 오류를 돌려준다. 4조건 중 **비선점을 DB가 깨는 것**이다 — 자원 회수 권한이 자기에게 있으니 뺏을 수 있다. 반면 JVM은 탐지만 하고 아무것도 못 한다.

그래서 애플리케이션 쪽 처리도 달라진다. `40P01`은 **재시도하면 대부분 성공하는 오류**다. 다만 세 가지를 챙겨야 한다 — abort된 트랜잭션 안에서는 아무 쿼리도 못 도니 **트랜잭션 전체를 다시 시작**해야 하고, 여기에도 **랜덤 백오프**를 넣어야 하며, **재시도해도 부작용이 없는 멱등한 작업인지**를 먼저 확인해야 한다.

그리고 마지막 한 줄. **재시도는 증상 완화이고 갱신 순서 통일이 원인 제거다.** 재시도율이 지표로 보이기 시작하면 순서 문제를 찾아 고쳐야 한다는 신호로 읽는다.

### "데드락은 왜 테스트로 잘 안 잡히나요? 어떻게 검증하나요?" (가산점 포인트)

**데드락은 스케줄링 타이밍이 정확히 맞아떨어져야만 재현되기 때문이다.** 3-1의 타임라인에서 t1과 t2 사이, t2와 t3 사이의 간격이 아주 좁아야 두 스레드가 서로를 막는 상태에 도달한다. 로컬에서 스레드 두 개로 몇 번 돌려서는 그 창을 거의 못 맞춘다. **경합이 심한 운영 환경에서만 재현되는 전형적인 동시성 버그**다.

검증에 쓸 수 있는 수단은 몇 가지다.

**부하를 걸어 창을 넓힌다.** 스레드 수를 코어 수보다 훨씬 크게 잡고 같은 자원에 반대 방향 요청을 섞어 오래 돌린다. 확률적이므로 "안 났다"가 "없다"를 증명하지는 못하지만, 있으면 잡힐 확률은 크게 올라간다.

**테스트 중 상시 탐지를 켠다.** 통합 테스트나 부하 테스트에 `ThreadMXBean.findDeadlockedThreads()` 폴링을 붙여 두면, 걸리는 순간 스택과 함께 실패로 떨어뜨릴 수 있다. 사람이 지켜보지 않아도 되므로 CI에 얹기 좋다.

**코드 리뷰의 체크리스트로 잡는 것이 가장 확실하다.** "락을 쥔 채 다른 락을 잡는 코드가 있는가", "락을 쥔 채 외부 호출·콜백을 하는가", "락 객체가 런타임에 정해지는데 순서 정규화가 없는가" — 이 셋이면 대부분 걸러진다. 동시성 버그는 테스트보다 리뷰에서 잡는 편이 훨씬 싸다.

## 한 줄 요약

데드락은 죽지 않고 멈추는 장애라 재시작으로 덮이며 반복되므로 **재시작 전에 스레드 덤프부터 뜨고**, 덤프 맨 끝의 `Found one Java-level deadlock` 블록에서 두 스레드가 서로를 가리키는 순환과 `- locked` / `- waiting to lock` 주소가 반대로 짝지어진 스택 위치를 읽어 고칠 코드를 특정한다 — 예방은 4조건(상호 배제 / 점유와 대기 / 비선점 / 순환 대기)이 **동시에** 성립해야 한다는 성질에서 유도되는데 상호 배제와 비선점은 실무에서 못 깨므로 **순환 대기를 깨는 전역 락 순서 고정(동적 락은 ID나 identityHashCode로 정규화하고 동률이면 타이 브레이킹 락)이 정석**이고 순서를 통제할 수 없을 때만 **점유와 대기를 깨는 tryLock 타임아웃 + 전부 반납 + 랜덤 백오프**로 내려가며, 무엇보다 **덤프에 deadlock 문구가 없어도 멈출 수 있다** — 세마포어·`CountDownLatch`·커넥션 풀·DB 행 락은 소유자를 알 수 없어 탐지 대상이 아니고 각각 `WAITING (parking)`·`TIMED_WAITING`·`RUNNABLE`이라는 다른 얼굴로 나타나므로 상태값이 아니라 스택 위치로 판별해야 한다.
