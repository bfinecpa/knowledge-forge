# parallelStream() — JVM에 하나뿐인 공용 작업반을 남과 나눠 쓰는 일

> 핵심 관전 포인트: **`parallelStream()`의 문제는 "병렬이라서"가 아니라 JVM 전체가 공유하는 단 하나의 `ForkJoinPool.commonPool()` 위에서 돈다는 데 있다. 그 풀의 크기는 기본적으로 `코어 수 - 1`이라 8코어 서버에서 워커는 7명뿐인데, 톰캣은 이미 요청 200개를 동시에 처리하고 있다. 그래서 요청 100개가 동시에 parallelStream을 부르면 서로의 작업을 큐에서 기다리게 되고(간섭), 누군가 그 위에 블로킹 I/O를 올리면 워커 7명이 전원 잠들어 아무 상관 없는 다른 기능의 parallelStream까지 통째로 멈춘다(전역 고갈). 게다가 람다를 실행하는 스레드가 톰캣 워커가 아니므로 `SecurityContext`·MDC·트랜잭션이 전부 유실된다. 이득이 나는 조건은 "CPU 바운드 + 충분히 큰 데이터 + 분할이 싼 소스 + 상태 없는 연산"이라는 좁은 교집합뿐이고, 웹 요청 경로에서 다루는 수백 건 DTO 변환은 여기에 하나도 해당하지 않는다.**

---

## 0. 질문 + 의도

**질문**: "Stream의 `parallelStream()`을 실무에서 함부로 쓰면 안 되는 이유는?"

**출제 의도**: 공용 ForkJoinPool을 웹 요청 처리에서 나눠 쓰면 한 기능의 부하가 전체 서비스를 굶긴다. "편해 보이는 API의 숨은 공유 자원"을 의식하는 습관이 있는지 본다.

## 1. 먼저 알아야 할 것 — 이 코드는 어느 스레드에서 도는가

### 1-1. 전제 지식 — 내 컨트롤러 코드는 이미 병렬로 돌고 있다

3년차쯤 되면 컨트롤러와 서비스를 하루에도 몇 개씩 만들지만, 그 코드가 **어느 스레드에서 실행되는지**를 의식하는 경우는 드물다. 이 질문은 정확히 그 지점을 건드린다.

톰캣은 요청마다 스레드를 새로 만들지 않는다. 애플리케이션이 뜰 때 워커 스레드를 미리 만들어 풀에 담아두고, 요청이 오면 하나를 빌려주고, 응답이 끝나면 죽이지 않고 풀로 되돌려 다음 요청에 다시 빌려준다. 스프링 부트의 기본 최대 워커 수는 200개다.

그러니까 **웹 애플리케이션은 이미 요청 단위로 병렬**이다. 200개 요청이 200개 스레드에서 동시에 돌고 있고, 요청 A가 느리든 말든 요청 B는 자기 스레드에서 자기 속도로 진행한다. **요청 사이의 격리가 웹 서버의 기본 모델**이고, 우리가 CRUD API를 짜면서 동시성을 걱정하지 않아도 되는 이유가 이 격리 덕분이다.

`parallelStream()`이 위험한 이유를 한 문장으로 미리 말하면 이것이다. **그 격리를 깬다.**

### 1-2. parallelStream()은 공용 ForkJoinPool에서 실행된다

```java
list.parallelStream().map(this::process).toList();
```

이 한 줄이 하는 일은 두 단계다. 먼저 `Spliterator`(분할 가능한 반복자, split + iterator를 합친 이름이다)로 원본 데이터를 **재귀적으로 반으로 쪼개** 작은 조각들을 만든다. 그다음 그 조각들을 **`ForkJoinPool.commonPool()`이라는 스레드 풀에 태스크로 던져** 병렬로 처리하고 결과를 병합한다.

여기서 이 문서의 모든 것이 걸린 사실이 나온다. **`commonPool()`은 JVM 전체에 딱 하나 있는 공용 풀이다.**

"공용(common)"이라는 이름이 그대로 성질을 말해준다. 우리가 만든 풀이 아니고, 요청별로 있는 풀도 아니고, 클래스별로 있는 풀도 아니다. **JVM 프로세스 안에서 `parallelStream()`을 부르는 모든 코드가 같은 풀 하나를 나눠 쓴다.**

**비유하면 JVM 안에 "공용 작업반"이 딱 하나 있는 것이다.** 요청 A가 부르든, 요청 B가 부르든, 우리가 쓰는 라이브러리 내부 코드가 몰래 부르든, 전부 같은 작업반에 일감을 맡긴다. 작업반은 들어온 일감을 큐에 넣고 순서대로 처리한다.

### 1-3. 그 작업반의 인원은 몇 명인가 — 코어 수 - 1

풀 크기는 기본적으로 **`Runtime.getRuntime().availableProcessors() - 1`**이다. 숫자를 직접 넣어 보면 감이 온다.

```
8코어 서버   -> 8 - 1 = 워커 스레드 7개
4코어 서버   -> 4 - 1 = 워커 스레드 3개
2코어 컨테이너 -> 2 - 1 = 워커 스레드 1개
1코어 컨테이너 -> 1 - 1 = 워커 스레드 0개
```

**왜 코어 수 기준인가.** 이 풀은 **CPU 바운드(CPU-bound) 작업 전용으로 설계**됐기 때문이다. CPU 바운드란 "일하는 동안 CPU를 계속 쓰는" 작업을 말한다 — 계산, 정렬, 문자열 가공 같은 것들이다. CPU 바운드 작업은 코어 수보다 스레드를 많이 만들어봐야 소용이 없다. 코어가 8개면 진짜로 동시에 실행되는 것은 8개뿐이고, 그 이상은 서로 번갈아 실행되며 컨텍스트 스위칭 비용만 더한다.

**왜 1을 빼는가.** `parallelStream()`을 호출한 스레드(예: 톰캣 워커)도 놀지 않고 태스크 처리에 참여하기 때문이다. 워커 7명 + 호출자 1명 = 8, 즉 코어 수에 맞춘 설계다.

여기서 실무적으로 자주 놓치는 함정이 하나 있다. **요즘 JVM은 컨테이너의 CPU 제한을 인식해 `availableProcessors()`에 반영한다.** 쿠버네티스에서 CPU를 1개로 제한한 파드라면 `availableProcessors()`가 1이 된다. 이때 `1 - 1 = 0`이지만 공용 풀은 병렬도의 하한을 1로 잡으므로 워커는 0명이 아니라 **1명**이다. 결국 일하는 주체는 워커 1 + 호출자 1인데 CPU가 하나뿐이라 그 둘이 진짜로 동시에 돌지도 못한다. **`parallelStream()`을 써도 병렬 이득은 없고 분할·병합 비용만 얹힌다.** 로컬 8코어 노트북에서 "빨라졌다"고 확인하고 배포했는데 운영에서는 이득이 없거나 오히려 느려지는 상황이 여기서 나온다.

### 1-4. 이 작업반을 같이 쓰는 사람이 또 있다

공용 풀을 두드리는 것은 우리가 명시적으로 부른 `parallelStream()`만이 아니다.

- **executor를 지정하지 않은 `CompletableFuture`의 async 메서드들.** `CompletableFuture.supplyAsync(task)`처럼 두 번째 인자를 생략하면 기본 실행기가 common pool이다. 두 번째 인자로 전용 executor를 넘기면 그쪽에서 돈다.
- **우리가 쓰는 라이브러리의 내부 코드.** 어떤 라이브러리가 내부에서 `parallelStream()`을 쓰고 있으면 우리 코드와 같은 작업반을 두드린다. 우리 코드를 아무리 뒤져도 안 보이는 부하다.

정리하면 이 그림이다.

```
[요청 A 스레드] --parallelStream()--+
[요청 B 스레드] --parallelStream()--+
[요청 C 스레드] --supplyAsync()-----+---> [ commonPool : 워커 7명 ] <-- JVM에 하나
[라이브러리 내부] --parallelStream()-+
```

**"전역 공유"와 "코어 수만큼의 작은 크기"라는 두 성질이 겹친 것**이 2절에서 볼 모든 사고의 근원이다.

## 2. 공용 풀이 만드는 세 가지 사고

### 2-1. 사고 ① 요청 간 간섭 — 내 응답 시간이 남의 요청에 좌우된다

1-1에서 본 요청 간 격리가 여기서 깨진다. 8코어(워커 7명) 서버의 타임라인이다.

```
10:00:00.000  요청 A: 10만 건 데이터를 parallelStream으로 가공 시작
              -> 데이터가 잘게 쪼개져 태스크 수천 개가 큐에 쌓인다
              -> 작업반 7명 전원이 A의 일감을 잡는다

10:00:00.050  요청 B: 고작 50건짜리 parallelStream 호출
              -> 작업반 7명이 전부 A의 일을 하는 중
              -> B의 태스크는 큐 뒤에 줄을 선다
              -> B는 자기 코드가 1ms짜리인데도 A가 끝날 때까지 기다린다

10:00:00.800  A 완료 -> 이제야 B의 태스크가 처리된다
              -> B의 응답 시간: 800ms (그중 799ms는 남의 일을 기다린 시간)
```

여기서 짚어야 할 것은 **B가 아무 잘못도 하지 않았다**는 점이다. B의 코드는 50건짜리 가공이고, 혼자 돌리면 1ms에 끝난다. 그런데 응답 시간이 800ms가 됐다.

이 상황의 성질을 한 문장으로 하면 이렇다. **요청 B의 응답 시간이 B 자신의 코드가 아니라 "그 순간 다른 요청이 뭘 하고 있었는가"에 의해 결정된다.**

운영에서 이것이 어떻게 보이는지가 더 중요하다.

- 같은 API의 응답 시간이 어제는 10ms, 오늘은 800ms로 튄다. 평균은 멀쩡한데 p99만 폭발한다.
- 지연의 원인이 그 API 코드 안에 없으므로, 그 API를 아무리 프로파일링해도 범인이 안 나온다.
- **혼자 테스트할 때는 절대 재현되지 않는다.** 부하가 없으면 작업반이 한가하므로 늘 빠르다.

성능 문제 중에 가장 잡기 어려운 부류다. 증상이 나타나는 곳과 원인이 있는 곳이 다르기 때문이다.

### 2-2. 사고 ② 블로킹 I/O — 작업반 전원이 잠들면 JVM 전체가 멈춘다

가장 흔하고 가장 치명적인 오용이다.

```java
// Before: 병렬로 외부 API를 호출하면 빨라질 것 같지만
orders.parallelStream()
      .map(order -> restClient.call(order))   // 네트워크 응답을 기다리는 블로킹 I/O
      .toList();
```

**블로킹 I/O(blocking I/O)**란 네트워크 응답이나 디스크 읽기처럼 **결과가 올 때까지 스레드가 아무것도 하지 않고 멈춰 서서 기다리는** 작업을 말한다. 기다리는 동안 그 스레드는 CPU를 쓰지 않는다. 일을 하는 게 아니라 **잠들어 있는** 것이다.

1-3에서 봤듯 common pool은 **CPU 바운드 전제로 코어 수만큼만 뽑은 인원**이다. 잠들어 있는 인원을 감안하지 않은 크기다. 여기에 블로킹 작업을 태우면 이렇게 된다.

```
t0   주문 20건에 대해 parallelStream + 외부 API 호출 시작

t1   워커 1~7 전원이 각자 외부 API 응답을 기다리며 잠든다
     -> 작업반에 깨어 있는 사람: 0명
     -> CPU 사용률: 거의 0% (아무도 계산을 안 하니까)
     -> 그런데 아무 일도 진행되지 않는다

t2   ★ 이 순간, JVM 안의 '모든' parallelStream이 멈춘다
     - 아무 상관 없는 다른 API의 parallelStream
     - executor를 안 넘긴 CompletableFuture.supplyAsync()
     - 라이브러리 내부의 parallelStream
     전부 큐에서 대기 상태가 된다

t3   외부 API가 평소 50ms에서 3초로 느려지면
     -> 작업반은 3초 동안 통째로 잠들어 있다
     -> 그동안 쌓인 태스크가 큐에 계속 밀린다
```

**무서운 것은 장애의 전파 범위다.** 실제로 느려진 것은 "주문 조회"라는 기능 하나인데, 공용 작업반이 통째로 잠들었으므로 아무 관계 없는 다른 기능들까지 같이 멈춘다. **격리가 없어서 국소 장애가 전역 장애가 된다.**

같은 코드를 전용 `ExecutorService`에서 돌렸다면 어땠을까. 그 기능 전용 작업반만 잠들고, 피해가 그 기능 안에 갇힌다. **격리가 해법인 이유**가 이 대비에서 나온다.

```java
// After: 전용 풀에 격리하고, 크기·타임아웃·모니터링을 독립적으로 관리한다
private final ExecutorService orderApiPool = Executors.newFixedThreadPool(20);

List<Result> results = orders.stream()
        // supplyAsync의 두 번째 인자로 executor를 '명시'하는 것이 핵심이다.
        // 생략하면 common pool로 돌아가 원래 문제가 그대로 재현된다.
        .map(o -> CompletableFuture.supplyAsync(() -> restClient.call(o), orderApiPool))
        .toList()
        .stream()
        .map(CompletableFuture::join)
        .toList();
```

전용 풀의 크기를 20으로 잡을 수 있는 이유도 짚어둘 만하다. I/O 대기 스레드는 CPU를 쓰지 않으므로 **코어 수에 묶일 필요가 없다.** CPU 바운드 전제로 크기가 정해지는 common pool과 요구가 애초에 다르다.

한 가지 더. **ForkJoinPool의 작업 훔치기(work-stealing) 구조 자체가 블로킹과 궁합이 최악이다.** 작업 훔치기란 자기 큐가 빈 워커가 바쁜 워커의 큐에서 일감을 훔쳐 오는 방식으로, "짧은 CPU 작업을 잘게 쪼개 골고루 나눠 갖는" 것을 전제로 한 최적화다. 워커가 잠들어 있으면 훔쳐 갈 워커도 없고 훔쳐 올 일감도 처리되지 않는다. `ForkJoinPool.ManagedBlocker`로 "지금 블로킹하니 보상 스레드를 하나 더 만들어달라"고 알려주는 장치가 있긴 하지만, `parallelStream()`의 람다 안에서 이걸 쓸 일은 사실상 없다.

### 2-3. 사고 ③ 컨텍스트 유실 — 남의 스레드는 내 주머니를 모른다

**비유부터 두면 이해가 빠르다. 일을 대신 해주는 사람은 내 주머니 속을 모른다.**

Java에는 "스레드마다 붙어 있는 개인 주머니"가 있다. `ThreadLocal`이라는 저장소인데, 값이 `ThreadLocal` 객체가 아니라 **`Thread` 객체 안에** 저장되기 때문에 붙은 이름이다. 요청을 처리하는 동안 인증 정보, 로그 추적 ID, DB 커넥션이 전부 **톰캣 워커 스레드의 주머니**에 들어 있다.

`parallelStream()` 안의 람다를 실행하는 것은 톰캣 워커가 아니라 **common pool의 워커 스레드**다. 그 스레드의 주머니는 이 요청에 대해 비어 있다.

```java
// Before: 트랜잭션 안에서 병렬로 저장하려는 시도
@Transactional
public void process(List<Item> items) {
    // 여기는 톰캣 워커 스레드 — 트랜잭션 있음, 인증 정보 있음, traceId 있음

    items.parallelStream().forEach(item -> {
        // 여기는 common pool 워커 스레드 — 위의 것이 하나도 없다
        SecurityContextHolder.getContext().getAuthentication();  // null
        log.info("processing {}", item);                         // traceId 없는 로그
        repository.save(item);                                   // 트랜잭션 '밖'에서 실행
    });
}
```

무엇이 유실되고 어떤 증상으로 나타나는지 정리하면 이렇다.

| 유실되는 것 | 증상 |
|---|---|
| 직접 만든 `ThreadLocal` | 요청 스레드에 담아둔 값이 워커에서 null |
| `SecurityContextHolder` | 인증 정보 없음 → 인가 검사 실패, 감사 로그에 사용자 누락 |
| MDC (로깅) | traceId 빠진 로그 → 분산 추적이 그 지점에서 끊김 |
| 트랜잭션 컨텍스트 | 워커의 DB 접근이 트랜잭션 밖 + 커넥션을 워커 수만큼 추가 점유 |

**넷 중 트랜잭션 유실이 압도적으로 위험하다.** 이유는 증상이 없기 때문이다.

`@Transactional`이 관리하는 DB 커넥션은 ThreadLocal에 바인딩되어 있다. common pool 워커는 그 바인딩이 없으므로 커넥션 풀에서 **자기 커넥션을 새로 빌려** 쓴다. 그 커넥션은 트랜잭션이 시작된 적이 없으니 auto-commit 상태다. 즉 **각 `save()`가 그 자리에서 개별 커밋된다.**

여기서 무슨 일이 벌어지는지 보자. 나중에 바깥 트랜잭션이 예외로 롤백되면, 톰캣 워커가 한 작업은 되돌아가지만 **common pool 워커들이 이미 커밋해버린 것은 돌아오지 않는다.** 예외도 안 나고 로그도 정상이다. 데이터만 조용히 어긋난다.

부수적으로, 워커 7명이 각자 커넥션을 빌리므로 **커넥션 풀 점유도 요청당 1개가 아니라 8개**가 된다. 커넥션 풀 크기를 요청 수 기준으로 계산해둔 설정이 예상치 못하게 고갈된다. 지연 로딩 프록시를 워커에서 건드리면 영속성 컨텍스트가 없어 `LazyInitializationException`이 간헐적으로 터지기도 한다.

한 가지 더 덧붙이면, common pool 워커는 데몬(daemon) 스레드다. 데몬 스레드란 "이 스레드만 남으면 JVM이 그냥 종료해도 되는" 배경 스레드를 말한다. 컨테이너 환경에서 클래스로더 관련 문제를 일으킬 수 있다는 점도 알아두면 좋다.

### 2-4. 우회책과 그 한계 — 커스텀 ForkJoinPool에 submit하기

"공용 풀이 문제라면 내 풀에서 돌리면 되지 않나"는 자연스러운 발상이고, 실제로 그렇게 하는 방법이 있다.

```java
ForkJoinPool dedicated = new ForkJoinPool(4);
try {
    // 핵심: parallelStream 자체를 이 풀의 태스크로 감싸 submit한다.
    // 파이프라인이 dedicated 풀의 워커 스레드 위에서 실행되기 시작하면,
    // 그 안에서 갈라지는 하위 태스크들도 '현재 스레드가 속한 풀'로 들어간다.
    List<Result> results = dedicated
            .submit(() -> list.parallelStream().map(this::heavy).toList())
            .get();
} finally {
    dedicated.shutdown();
}
```

동작은 한다. 하지만 **완전한 격리는 아니다.** 네 가지를 짚어야 한다.

**첫째, 공식 스펙에 명시된 동작이 아니다.** "하위 태스크는 현재 스레드가 속한 풀로 들어간다"는 것은 `ForkJoinTask`의 구현 동작이지 스트림 API가 문서로 보장한 계약이 아니다. JDK 구현이 바뀌면 조용히 common pool로 되돌아갈 수 있고, 그때 컴파일 에러도 테스트 실패도 나지 않는다.

**둘째, 블로킹 문제 자체는 사라지지 않는다.** 격리해도 전용 풀 역시 크기가 유한하므로, 여기에 블로킹 I/O를 태우면 이 풀이 고갈된다. 달라진 것은 **피해가 그 기능 안에 갇힌다는 것**뿐이다. 그것만 해도 큰 이득이지만, "격리했으니 블로킹 태워도 된다"는 뜻은 아니다.

**셋째, 호출 스레드는 여전히 묶인다.** `.get()`으로 결과를 기다리는 동안 톰캣 워커는 그냥 블로킹된다. 요청 스레드를 아끼는 효과는 없다.

**넷째, 의도가 코드에 드러나지 않는다.** `submit(() -> ...parallelStream()...)`을 처음 보는 사람은 왜 이렇게 감쌌는지 알 수 없다. 목적이 "격리된 풀에서 병렬 실행"이라면 `ExecutorService` + `CompletableFuture`로 **명시하는 편이 읽기에도 관리하기에도 낫다.**

같은 이유로 `-Djava.util.concurrent.ForkJoinPool.common.parallelism=N`으로 common pool 크기를 키우는 것도 근본 해결이 아니다. **전역 설정이라 여전히 모두가 나눠 쓰는 하나의 풀**이고, 크기만 커진 공용 자원은 블로킹 작업이 들어오면 결국 같은 방식으로 고갈된다.

## 3. 정확성 함정과 "언제 써도 되는가"

2절이 "공유 자원이라서 생기는 문제"였다면, 3절은 **"병렬 자체가 요구하는 조건"**이다. 공용 풀 문제를 완벽히 격리했더라도 아래 조건이 안 맞으면 병렬화는 느려지거나 틀린 답을 낸다.

### 3-1. 이미 병렬인 곳에서의 추가 병렬화는 이득이 없다

1-1로 돌아가 보자. 웹 서버는 이미 요청 단위로 병렬이다.

트래픽이 몰린 시점에는 요청 200개가 동시에 돌면서 **CPU 코어 8개가 이미 포화 상태**다. 여기서 요청 하나를 7개 스레드로 더 쪼개봐야 없던 CPU가 생기지는 않는다. **총 처리량은 늘지 않고 분할·태스크 스케줄링·결과 병합·컨텍스트 스위칭 비용만 추가된다.**

병렬화가 값을 하는 상황은 **한가한 CPU를 놀리고 있을 때**다. 그런데 웹 서버의 피크 타임은 정확히 그 반대 상황이다. **병렬화가 가장 절실해 보이는 순간이 병렬화가 가장 쓸모없는 순간**이라는 것이 이 항목의 요지다.

### 3-2. 분할 비용이 큰 소스에서는 이득이 없다

병렬 스트림은 먼저 데이터를 쪼개야 한다. 쪼개는 비용이 처리 비용보다 크면 남는 게 없다. 자료구조마다 분할 비용이 크게 다르다.

**배열과 `ArrayList`는 분할이 거의 공짜다.** 내부가 연속된 배열이고 크기를 알고 있으므로, "0번부터 4999번까지 / 5000번부터 9999번까지"처럼 **인덱스 범위만 계산하면 끝**이다. 원소를 하나도 건드리지 않는다.

**`LinkedList`는 분할이 비싸다.** 연결 리스트는 각 노드가 다음 노드의 주소만 알고 있는 구조다. 중간 지점을 찾으려면 **처음부터 노드를 하나씩 따라가야** 한다. 반으로 나누려면 절반을 순회해야 하고, 그 절반을 또 나누려면 또 순회해야 한다. 원소를 처리하기도 전에 순회 비용이 쌓인다.

**`Iterator`만 제공하는 소스는 크기조차 모른다.** `Stream.iterate`나 커스텀 `Spliterator` 없이 만든 스트림은 "다음 원소가 있는지"만 알 수 있어, 균등하게 쪼갤 기준이 없다. 일단 일정 개수씩 뽑아 버퍼에 담아가며 쪼개는데, 이 과정이 통째로 오버헤드다. `HashSet`이나 `TreeMap`도 배열만큼은 아니지만 중간 수준의 분할 비용이 든다.

**분할이 얼마나 필요한지는 데이터 크기가 정한다.** 원소 수 N과 원소당 연산 비용 Q의 곱이 충분히 커야 분할·병합 비용을 상회한다는 것이 흔히 인용되는 NQ 경험칙으로, 대략 **만 단위**를 넘어야 검토할 가치가 있다는 기준이 자주 쓰인다. 어디까지나 어림값이지 절대 기준이 아니다 — **실제 판단은 자기 데이터로 측정해서 해야 한다.** 다만 방향은 분명하다. 웹 요청에서 다루는 "DTO 수십~수백 건 변환"은 이 기준의 발끝에도 못 미치고, 순차 스트림이 오히려 빠른 경우가 흔하다.

### 3-3. 순서 의존 연산 — forEach와 forEachOrdered

순차 스트림은 원본의 순서(encounter order)대로 처리한다. **병렬 스트림의 `forEach`는 순서를 보장하지 않는다.** 데이터를 쪼개 여러 스레드가 동시에 처리하니 당연한 결과다.

```java
List<String> names = List.of("a", "b", "c", "d");

names.parallelStream().forEach(System.out::print);
// 출력 예: cadb — 실행할 때마다 다르다

names.parallelStream().forEachOrdered(System.out::print);
// 출력: abcd — 항상 원본 순서
```

문제는 `forEachOrdered`가 순서를 지키는 **방법**이다. 원본 순서대로 소비하려면 **뒤쪽 조각의 결과를 앞쪽 조각이 끝날 때까지 붙들고 있어야** 한다. 3번 조각이 먼저 끝나도 1번, 2번이 끝나기 전에는 내보낼 수 없다.

결과적으로 **최종 단계가 사실상 직렬화되고**, 그 앞의 `map`·`filter`는 병렬로 돌았더라도 순서를 맞추느라 기다린 시간이 이득을 상당 부분 깎아먹는다. 순서가 꼭 필요한 처리라면 애초에 병렬이 어울리지 않는 작업이라고 보는 게 맞다.

순서에 얽힌 연산들은 같은 이유로 병렬에서 비싸진다.

- `limit`, `skip`: 순서가 있는 스트림에서는 "앞에서 몇 개"를 세야 하므로 조각들 사이의 조율이 필요하다.
- `findFirst`: 진짜 첫 번째를 찾아야 한다. **순서가 상관없다면 `findAny`가 훨씬 싸다** — 아무 조각에서든 먼저 찾은 것을 바로 반환할 수 있기 때문이다.
- `sorted`, `distinct`: 전체를 봐야 하므로 중간 결과를 버퍼링해야 한다.

덧붙여, `stream().parallel()`과 `parallelStream()`은 같은 뜻이고 **파이프라인 전체 단위로 병렬/순차가 정해진다.** 중간의 특정 연산만 병렬로 돌릴 수는 없다. 파이프라인 어디에서 `parallel()`을 부르든 결과는 같다.

### 3-4. 스트림 안에서 공유 컬렉션을 바꾸면 원소가 사라진다

순차 스트림에서는 우연히 잘 돌던 코드가 병렬에서 터지는 대표적인 형태다.

```java
// Before: 스트림 밖의 컬렉션에 직접 담는다
List<String> result = new ArrayList<>();
items.parallelStream()
     .filter(this::isValid)
     .forEach(i -> result.add(i.name()));   // 여러 스레드가 같은 ArrayList를 동시에 변경
```

`ArrayList.add()`가 스레드 안전하지 않은 이유를 한 단계씩 보면 왜 원소가 사라지는지 알 수 있다. `add()`는 대략 세 동작이다.

```
① 현재 size 를 읽는다
② elementData[size] 자리에 원소를 쓴다
③ size 를 size + 1 로 갱신한다
```

두 스레드가 동시에 들어오면 이렇게 어긋난다.

```
size = 10 인 상태

스레드 A: ① size 읽음 -> 10
스레드 B: ① size 읽음 -> 10        ★ 같은 값을 읽었다
스레드 A: ② elementData[10] = "alice"
스레드 B: ② elementData[10] = "bob"  ★ alice 를 덮어썼다
스레드 A: ③ size = 11
스레드 B: ③ size = 11              ★ 2개를 넣었는데 size 는 11
```

결과는 **원소 유실**이다. 1000건을 넣었는데 리스트에 997건만 있고, 몇 건인지도 실행할 때마다 다르다.

더 나쁜 경우도 있다. 배열이 꽉 차서 한 스레드가 더 큰 배열로 복사(grow)하는 중에 다른 스레드가 옛 배열에 쓰면 그 원소는 새 배열에 반영되지 않고, 타이밍에 따라 `ArrayIndexOutOfBoundsException`이 튀거나 리스트 중간에 `null` 구멍이 생긴다. **예외가 항상 나는 게 아니라 가끔만 난다**는 점이 이 버그의 성질을 그대로 보여준다.

해법은 컬렉션을 동기화하는 것이 아니라 **애초에 공유 변경을 하지 않는 것**이다.

```java
// After: collect가 병합까지 책임진다
List<String> result = items.parallelStream()
        .filter(this::isValid)
        .map(Item::name)
        // 병렬 collect는 스레드마다 '자기 컨테이너'에 모은 뒤 마지막에 합친다.
        // 공유 자료구조를 동시에 건드리는 지점이 아예 없다.
        .collect(Collectors.toList());
```

`collect`가 안전한 이유는 동기화를 잘해서가 아니라 **공유 자체를 없앤 구조이기 때문**이다. 각 스레드가 자기 컨테이너에 담고, 마지막에 컨테이너들을 합친다. 이 차이가 병렬 프로그래밍의 일반 원칙이기도 하다 — **락으로 공유를 관리하는 것보다 공유를 없애는 쪽이 거의 항상 낫다.**

### 3-5. reduce는 결합법칙을 요구한다

`reduce`는 원소들을 하나로 접어 합치는 연산이다. 병렬에서 올바르게 동작하려면 **연산이 결합법칙(associativity)을 만족해야** 한다. 결합법칙이란 `(a op b) op c == a op (b op c)`, 즉 **묶는 순서를 바꿔도 결과가 같은** 성질이다.

왜 이게 필요한지는 병렬 `reduce`가 실제로 하는 일을 보면 안다. 데이터를 조각으로 나눠 각 조각을 따로 접은 다음, 그 결과들을 다시 접는다. **묶는 순서가 순차 실행과 달라진다.** 결합법칙이 성립하면 순서가 달라도 결과가 같고, 성립하지 않으면 답이 달라진다.

뺄셈으로 확인해 보자. `[1, 2, 3, 4]`를 `reduce(0, (a, b) -> a - b)`로 접는다.

```
[순차 실행]  왼쪽부터 차례대로 접는다
  0 - 1 = -1
 -1 - 2 = -3
 -3 - 3 = -6
 -6 - 4 = -10          결과: -10

[병렬 실행]  둘로 쪼개 각각 접은 뒤 합친다
  왼쪽 [1, 2]:  0 - 1 = -1,  -1 - 2 = -3
  오른쪽 [3, 4]: 0 - 3 = -3,  -3 - 4 = -7
  합치기:      -3 - (-7) = 4     결과: 4
```

**-10과 4.** 예외도 경고도 없이 그냥 다른 답이 나온다. 덧셈·곱셈·최댓값·문자열 이어붙이기는 결합법칙을 만족하므로 안전하지만, 뺄셈·나눗셈은 만족하지 않는다.

같은 이유로 **초깃값(identity)도 진짜 항등원이어야 한다.** `identity op x == x`가 성립해야 한다는 뜻이다. 덧셈의 항등원은 0, 곱셈은 1, 문자열은 빈 문자열이다. 여기에 0 대신 1을 넣고 덧셈을 하면, 순차에서는 결과가 1만큼 커지는 데 그치지만 **병렬에서는 조각 수만큼 더해져** 조각 개수에 따라 답이 달라진다. 실행할 때마다 결과가 바뀌는 최악의 버그다.

### 3-6. 결론 — 언제 써도 되는가

지금까지의 조건을 뒤집으면 `parallelStream()`을 써도 되는 교집합이 나온다. **네 가지가 전부 맞아야 한다.**

**(1) CPU 바운드 작업이다.** 원소마다 실제로 계산을 한다. 블로킹 I/O(HTTP 호출, DB 조회, 파일 읽기)가 섞이면 그 순간 2-2의 고갈이 시작된다. 이 조건 하나만 어겨도 나머지는 볼 필요가 없다.

**(2) 데이터가 충분히 크고 분할이 싼 소스다.** 배열이나 `ArrayList`처럼 인덱스로 쪼갤 수 있어야 하고, 원소 수 × 원소당 비용이 분할·병합 오버헤드를 넉넉히 넘어야 한다. `LinkedList`나 `Iterator` 기반 소스는 제외한다.

**(3) 연산에 상태가 없다.** 원소끼리 독립적이고, 람다가 바깥의 공유 자료구조를 변경하지 않으며, 순서에 의존하지 않는다. `reduce`를 쓴다면 결합법칙과 항등원 조건을 만족한다.

**(4) 웹 요청 처리 경로 밖이다.** 배치, CLI, 애플리케이션 초기화처럼 **공용 작업반을 독점해도 되는 환경**이어야 한다. 요청 스레드에서 직접 부르는 순간 2-1의 간섭이 시작된다.

넷이 다 맞는 곳에서는 코드 한 줄로 코어를 전부 쓰는 훌륭한 도구다. 그래서 결론은 "쓰지 마라"가 아니라 **"조건을 확인하고 써라"**다.

상황별로 정리하면 이렇다.

| 상황 | 올바른 선택 |
|---|---|
| 수십~수백 건 DTO 변환 등 일반 웹 로직 | 그냥 순차 `stream()`. 대부분 이걸로 충분하고 대개 더 빠르다 |
| 병렬 외부 API 호출 (I/O 바운드) | 전용 `ExecutorService` + `CompletableFuture.supplyAsync(task, executor)` |
| 진짜 CPU 바운드 대량 연산 (배치, 이미지, 암호화) | 요청 경로 밖(배치·비동기 잡)으로 분리하고 거기서 병렬화 |
| 대량 동시 I/O | 가상 스레드로 블로킹 I/O를 싸게 만드는 정공법. 단 CPU 바운드에는 이득 없음 |

## 4. 꼬리질문 대비 포인트

### "common pool의 크기는 얼마이고, 왜 하필 그 크기인가요?"

기본값은 **`availableProcessors() - 1`**이다. 8코어면 워커 7개다.

**코어 수 기준인 이유**는 이 풀이 CPU 바운드 작업 전용으로 설계됐기 때문이다. CPU를 계속 쓰는 작업은 코어 수보다 스레드를 늘려봐야 동시에 실행되는 수가 늘지 않고 컨텍스트 스위칭 비용만 붙는다.

**1을 빼는 이유**는 `parallelStream()`을 호출한 스레드도 태스크 처리에 참여하기 때문이다. 워커 7 + 호출자 1 = 코어 수 8에 맞춘 설계다.

여기까지 답한 뒤 **"그래서 블로킹 작업이 들어오면 곧바로 고갈된다"**는 결론까지 이어 붙이는 것이 중요하다. 크기 자체가 "아무도 잠들지 않는다"는 전제 위에 서 있는 숫자다.

컨테이너 이야기를 덧붙이면 가산점이다. 요즘 JVM은 컨테이너 CPU 제한을 인식하므로, CPU 1개짜리 파드에서는 `availableProcessors()`가 1이 되고 공용 풀 워커는 1명이 된다(`코어 수 - 1`이 0이 되어도 하한 1이 적용된다). CPU가 하나라 그 워커와 호출 스레드가 동시에 돌지도 못하므로 **병렬화 이득은 없고 분할·병합 비용만 붙는다.** 로컬에서 측정한 개선 효과가 운영에서 사라지는 흔한 원인이다.

### "커스텀 ForkJoinPool로 감싸면 되지 않나요?" (시니어 변별 포인트)

`pool.submit(() -> list.parallelStream()...).get()` 트릭이 실제로 동작한다는 것부터 인정하고 시작한다. 파이프라인이 그 풀의 워커 위에서 시작되면 하위 태스크도 같은 풀로 들어가기 때문이다.

그다음 **왜 완전한 격리가 아닌지**를 짚는다.

1. **공식 스펙이 아니라 구현 동작에 기댄다.** 스트림 API가 문서로 보장한 계약이 아니므로, JDK 구현이 바뀌면 조용히 common pool로 되돌아갈 수 있고 그때 아무 에러도 나지 않는다.
2. **블로킹 문제 자체는 남는다.** 전용 풀도 크기가 유한하므로 블로킹 I/O를 태우면 고갈된다. 달라지는 것은 피해 범위가 그 기능 안에 갇힌다는 점뿐이다.
3. **호출 스레드는 여전히 `.get()`에서 블로킹된다.** 요청 스레드를 아끼는 효과는 없다.
4. **의도가 코드에 드러나지 않는다.** 목적이 "격리된 풀에서의 병렬 실행"이라면 `ExecutorService` + `CompletableFuture`로 명시하는 편이 낫다.

`-Djava.util.concurrent.ForkJoinPool.common.parallelism=N`으로 크기를 키우는 것도 마찬가지다. **전역 설정이라 여전히 모두가 공유하는 하나의 풀**이고, 커진 공용 자원은 블로킹이 들어오면 같은 방식으로 고갈된다.

**우회로 문제를 덮는 것과 구조를 바꾸는 것의 차이**를 말할 수 있는지가 이 질문의 변별 지점이다.

### "@Transactional 메서드 안에서 parallelStream으로 DB에 접근하면 어떻게 되나요?"

트랜잭션의 DB 커넥션은 **ThreadLocal에 바인딩**되어 있는데, common pool 워커에는 그 바인딩이 없다. 그래서 워커는 커넥션 풀에서 자기 커넥션을 새로 빌려 쓰고, 그 커넥션은 트랜잭션이 시작된 적이 없으니 **auto-commit 상태**다.

결과는 셋이다.

- 각 쓰기가 그 자리에서 개별 커밋된다. 바깥 트랜잭션이 나중에 롤백돼도 **이미 커밋된 것은 돌아오지 않는다.**
- 커넥션 점유가 요청당 1개가 아니라 **워커 수만큼 추가**된다. 커넥션 풀 크기 계산이 어긋나 고갈로 이어질 수 있다.
- 영속성 컨텍스트가 없어 지연 로딩을 건드리면 `LazyInitializationException`이 간헐적으로 터진다.

**가장 위험한 것은 예외가 안 난다는 점**이다. 로그도 정상이고 알람도 없이 데이터만 조용히 어긋난다. 발견되는 시점은 보통 정합성 대사 배치가 숫자 차이를 잡아낼 때다.

### "CompletableFuture는 안전한가요?"

**executor를 지정하지 않으면 같은 common pool을 쓰므로 동일한 문제가 있다.**

```java
CompletableFuture.supplyAsync(task);            // common pool — 위험
CompletableFuture.supplyAsync(task, myPool);    // 전용 풀 — 안전
```

`thenApplyAsync`, `thenComposeAsync` 같은 `Async` 접미사 메서드들도 마찬가지로 executor를 생략하면 common pool로 간다.

`CompletableFuture`는 애초에 I/O 대기를 조합하는 데 자주 쓰이므로, executor를 생략하면 **"블로킹 작업을 CPU 바운드 전용 풀에 태우는" 가장 흔한 경로**가 된다. **두 번째 인자를 습관적으로 붙이는 것**이 실무 규칙이다.

### "가상 스레드가 나왔으니 parallelStream으로 I/O를 해도 되지 않나요?" (가산점 포인트)

**아니다. 둘은 서로 다른 층의 도구다.**

`parallelStream()`은 여전히 플랫폼 스레드 기반의 common pool에서 돈다. 가상 스레드가 생겼다고 이 풀이 가상 스레드로 바뀌지 않는다.

가상 스레드의 이득은 `Executors.newVirtualThreadPerTaskExecutor()` 같은 실행기에 **태스크를 직접 제출할 때** 얻는 것이다. 블로킹 I/O 동안 OS 스레드를 붙들지 않고 놓아주므로 스레드가 아주 싸지고, 그래서 수만 건의 동시 I/O를 감당할 수 있다.

역할을 구분해 말하면 정리가 깔끔하다. **가상 스레드는 I/O 대기를 싸게 만드는 도구이고, `parallelStream()`은 CPU 작업을 코어에 나눠 붙이는 도구다.** CPU 바운드 작업을 가상 스레드로 돌린다고 빨라지지 않고(코어 수는 그대로다), I/O를 `parallelStream()`으로 돌리면 공용 풀이 고갈된다. **서로를 대체하지 않는다.**

## 한 줄 요약

`parallelStream()`은 JVM에 단 하나뿐인 `ForkJoinPool.commonPool()`(기본 크기 `코어 수 - 1`) 위에서 돌기 때문에, 이미 요청 단위로 병렬인 웹 애플리케이션에서는 요청끼리 그 작은 공용 풀을 놓고 다투게 되어 응답 시간이 남의 요청에 좌우되고, 거기에 블로킹 I/O를 올리면 워커 전원이 잠들어 국소 장애가 JVM 전역 장애로 번지며, 실행 스레드가 바뀌므로 `SecurityContext`·MDC·트랜잭션이 예외 없이 조용히 유실된다 — 커스텀 ForkJoinPool에 submit하는 우회는 구현 동작에 기댄 부분 격리일 뿐이므로, 병렬 I/O는 전용 `ExecutorService`(또는 가상 스레드)로 명시하고 `parallelStream()`은 CPU 바운드 + 충분히 큰 데이터 + 분할이 싼 소스 + 상태 없는 연산 + 요청 경로 밖이라는 네 조건이 모두 맞을 때만 쓴다.
