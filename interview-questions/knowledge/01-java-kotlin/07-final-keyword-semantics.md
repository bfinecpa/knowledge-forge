# final 키워드의 세 가지 얼굴 — 변경 가능 지점을 의도적으로 줄이는 어휘

> 핵심 관전 포인트: **final은 붙는 위치마다 금지 대상이 다르다 — 클래스에 붙으면 상속 금지, 메서드에 붙으면 재정의 금지, 변수에 붙으면 재할당 금지. 셋의 공통 정신은 "여기는 바뀌지 않는다"를 컴파일러에게 선언해 나중에 코드를 읽는 사람과 최적화기와 프레임워크가 그 사실에 기댈 수 있게 만드는 것이다. 이 주제의 중심은 **"final 참조 ≠ 불변 객체"** 하나다 — 객체를 담은 변수 칸에 실제로 들어 있는 것은 객체가 아니라 힙 어딘가를 가리키는 주소값이고, **final이 잠그는 것은 그 주소 칸이지 그 주소가 가리키는 상자가 아니다.** 그래서 `final List`에도 `add`가 그대로 되고, 진짜 불변을 원하면 `final` 위에 불변 컬렉션 또는 방어적 복사를 얹고 클래스까지 `final`로 봉인하는 세 겹이 필요하다. 여기서 파생되는 세 가지가 실무 변별점이다 — 람다가 지역변수를 **값으로 복사**해 가기 때문에 원본이 바뀌면 어느 쪽이 진짜인지 정할 수 없어 effectively final을 요구한다는 것, CGLIB은 대상 클래스를 **상속한 자식**을 만들어 메서드를 재정의하는 방식이라 `final` 메서드에 붙은 `@Transactional`이 예외 하나 없이 조용히 무시된다는 것, 그리고 `final` 필드에는 JMM이 별도 보장을 주어 생성자가 정상 종료하면 `this`가 새지 않는 한 다른 스레드에도 완성된 값이 보인다는 것이다.**

---

## 0. 질문 + 의도

**질문**: "`final` 키워드가 클래스/메서드/변수에 붙었을 때 각각 어떤 의미인가요?"

**출제 의도**: 사소해 보이지만, "변경 가능 지점을 의도적으로 줄이는 습관"이 있는지를 드러낸다. 코드 리뷰에서 동료의 가변 상태를 지적할 수 있는 최소 어휘. 문법 암기를 넘어 "final 참조 ≠ 불변 객체" 구분과 불변이 주는 실익(스레드 안전, 추론 용이)까지 말할 수 있는지를 본다.

## 1. 위치별 의미 — 무엇이 금지되고, 그래서 무엇을 보장할 수 있게 되는가

### 1-1. 전제 지식 — 변수 칸에 들어 있는 것은 객체가 아니라 주소다

`final`이 정확히 무엇을 잠그는지 이해하려면 먼저 이 사실 하나를 확정해야 한다.

자바에서 **객체를 담은 변수에 실제로 들어 있는 것은 객체 자체가 아니라, 그 객체가 힙 어디에 있는지를 가리키는 주소값**이다. 이 주소값을 **참조(reference)**라고 부른다.

```text
List<OrderItem> items = new ArrayList<>();

  변수 items                        힙
  +--------------+                 +--------------------------+
  | 0x4b2a...    | --------------> | ArrayList 객체            |
  +--------------+                 |   [0] ...                |
   여기 들어 있는 건               |   [1] ...                |
   주소값이다                      +--------------------------+
                                    객체는 힙에 따로 있다
```

**변수 칸과 힙의 상자는 별개의 두 물건**이라는 것이 요점이다. `21-defensive-copy-collection-exposure.md`가 세운 그림과 같은 것이고, 이 문서의 §2는 전부 이 그림에서 따라 나온다.

### 1-2. 한눈에 보는 세 자리

| 붙는 위치 | 금지되는 것 | 그래서 보장할 수 있게 되는 것 |
|---|---|---|
| 클래스 | 상속 (`extends` 불가) | 이 타입의 동작·불변식을 자식이 못 바꾼다 |
| 메서드 | 자식의 재정의(override) | 이 메서드의 흐름·순서가 계층 전체에서 동일하다 |
| 변수 (필드/지역/파라미터) | 재할당 (딱 한 번만 대입) | 이 이름이 가리키는 대상이 도중에 바뀌지 않는다 |

오른쪽 열이 이 표의 요점이다. **final은 무언가를 못 하게 만드는 것이 목적이 아니라, 못 하게 만듦으로써 "이건 이렇다"고 단언할 수 있게 만드는 것이 목적이다.** 아래에서 자리마다 이 짝을 따로 본다.

### 1-3. 클래스의 final — 상속을 막아서 "이 타입의 동작은 내가 보장한다"를 얻는다

**금지되는 것**: 이 클래스를 `extends`할 수 없다.

**그래서 얻는 것**: 이 클래스가 지키기로 한 규칙을 **자식이 우회할 수 없다는 확신**이다.

왜 자식이 규칙을 깰 수 있는지부터 보자. 자식은 부모의 메서드를 재정의할 수 있고, 부모 타입 자리에는 어디든 자식이 들어갈 수 있다. 그래서 `String`을 받는 메서드가 실제로는 재정의된 가짜 `String`을 받게 되는 상황이 원리적으로 가능해진다.

`String`이 `final`인 이유가 정확히 이것이다. 만약 `String`을 상속해 **호출할 때마다 다른 값을 반환하는 가짜 String**을 만들 수 있다면 이런 것들이 전부 무너진다.

- **문자열 풀 캐싱**: 같은 리터럴이면 같은 객체를 재사용해도 안전하다는 전제가 "내용이 절대 안 바뀐다"는 데 기대고 있다.
- **HashMap 키로서의 안전성**: 키를 넣은 뒤 그 키의 `hashCode`가 바뀌면 그 항목은 영영 못 찾는다.
- **보안 검사**: 파일 경로를 검증한 뒤 실제로 여는 사이에 그 String이 다른 경로로 바뀌면 검증이 무의미해진다. 앞 문서에서 본 TOCTOU(검사 시점과 사용 시점의 불일치)와 같은 구조다.

**"String은 불변"이라는 보장은 필드가 `final`인 것만으로 완성되지 않고, 클래스가 `final`이어야 완성된다.** 자식이 가변성을 덧붙일 수 있으면 그 보장은 "이 클래스에 한해서"라는 단서가 붙어 버리기 때문이다.

### 1-4. 메서드의 final — 재정의를 막아서 "흐름의 이 부분은 고정"을 얻는다

**금지되는 것**: 자식이 이 메서드를 재정의할 수 없다. 상속 자체는 허용하되 특정 메서드만 잠그는 것이다.

**그래서 얻는 것**: 그 메서드가 정한 **순서와 절차가 상속 계층 전체에서 동일하다는 보장**이다.

대표적인 자리가 템플릿 메서드 패턴이다. 전체 흐름은 부모가 고정하고, 갈리는 부분만 `abstract` 메서드로 구멍을 낸다.

```java
public abstract class AbstractPaymentGateway {

    // final: "로깅 -> 호출 -> 검증 -> 변환" 이 순서 자체가 정책이다.
    // 자식이 로깅을 건너뛰거나 검증 순서를 바꾸면 감사 요구가 깨지므로 잠근다.
    public final PayResult pay(PayRequest request) {
        log(request);
        PgResponse response = callPgApi(request);   // 이 구멍만 자식 몫
        validate(response);
        return toResult(response);
    }

    protected abstract PgResponse callPgApi(PayRequest request);
}
```

`final`이 없으면 자식이 `pay`를 통째로 재정의해서 로깅과 검증을 빼먹을 수 있다. 그러면 부모가 "모든 PG 호출은 로그가 남는다"고 단언할 근거가 사라진다.

### 1-5. 변수의 final — 재할당을 막아서 "이 이름의 대상은 안 바뀐다"를 얻는다

**금지되는 것**: 이 변수에 값을 두 번 대입하는 것. 필드든 지역변수든 파라미터든, 선언 시점이나 생성자에서 정확히 한 번 대입되고 나면 그 뒤의 대입은 컴파일 에러다.

```java
private final OrderRepository orderRepository;      // 여기서는 값을 안 넣었다

public OrderService(OrderRepository orderRepository) {
    this.orderRepository = orderRepository;         // 생성자에서 딱 한 번 대입
}

public void reconfigure(OrderRepository other) {
    this.orderRepository = other;                   // 컴파일 에러 — 두 번째 대입은 불가
}
```

여기서 **정확히 무엇이 잠기는지**를 1-1의 그림 위에 얹어 봐야 한다. 변수 칸에 들어 있는 것은 주소값이었다. **`final`은 그 칸의 값을 못 바꾸게 한다.** 다시 말해 "다른 객체를 가리키게 만들 수 없다"는 뜻이다.

```text
final List<OrderItem> items

  +--------------+                 +--------------------------+
  | 0x4b2a...    | --------------> | ArrayList                |
  +--------------+                 |   [0] ...                |
   ^                               |   [1] ...                |
   |                               +--------------------------+
   final이 잠그는 것은 여기          이 안쪽은 final과 아무 상관이 없다
   (이 칸의 주소값을 못 바꾼다)
```

**그래서 얻는 것**은 "이 이름이 가리키는 대상이 도중에 바뀌지 않는다"는 보장이다. 이것은 유용하지만, **"그 대상의 내용물이 안 바뀐다"와는 전혀 다른 말**이다. 이 구분이 이 문서의 중심이라 절을 따로 뗀다(§2).

### 1-6. 람다·익명 클래스의 effectively final — 왜 강제되는가

지역변수를 람다나 익명 클래스 안에서 쓰려고 하면 **그 변수는 final이거나 사실상 final(effectively final)이어야 한다**는 제약을 만난다.

```java
public Runnable make() {
    int count = 0;
    Runnable r = () -> System.out.println(count);
    count = 1;        // 컴파일 에러: 람다에서 참조한 지역변수는 final이거나 사실상 final이어야 한다
    return r;
}
```

**effectively final**은 "`final` 키워드를 안 붙였지만 실제로 한 번도 재할당되지 않아서, 컴파일러가 final로 취급해 주는 변수"다(Java 8+). 사실상(effectively) final이라는 이름이 그 뜻 그대로다.

왜 이런 제약이 있는지는 **지역변수가 어디에 사는가**를 보면 나온다.

지역변수는 **스택 프레임** 안에 산다. 스택 프레임은 메서드 호출 하나마다 만들어졌다가 그 메서드가 끝나면 **통째로 사라지는** 메모리 구역이다. 반면 람다로 만든 객체는 힙에 살면서 메서드가 끝난 뒤에도 살아남는다 — 위 코드처럼 반환되기도 하고, 다른 스레드에서 나중에 실행되기도 한다.

```text
[메서드 실행 중]                      [메서드가 끝난 뒤]

 스택                 힙              스택                힙
 +------------+   +----------+       (프레임이 통째로     +----------+
 | count = 0  |   | 람다 객체 |        사라졌다)           | 람다 객체 |
 +------------+   +----------+                            +----------+
   메서드가 끝나면 사라진다              람다는 아직 살아 있는데
                                        참조할 원본 변수가 없다
```

**원본 변수가 사라진 뒤에도 람다는 그 값을 써야 한다.** 그래서 자바는 람다를 만드는 시점에 **지역변수의 값을 한 벌 복사해서** 람다 객체 안에 넣어 둔다. 이것을 **캡처(capture)**라고 부른다.

여기서 문제가 생긴다. **복사본이 만들어진 뒤에 원본이 바뀌면, 둘 중 어느 쪽이 진짜인가?**

```text
t0  int count = 0;
t1  Runnable r = () -> print(count);    <- 이 순간 값 0이 람다 안으로 복사된다
t2  count = 1;                          <- 원본만 1이 됐다. 복사본은 여전히 0이다
t3  r.run();                            <- 0을 출력할 것인가 1을 출력할 것인가?
```

어느 쪽을 택해도 헷갈린다. 0이면 "분명히 1로 바꿨는데 왜 0이지"가 되고, 1이면 값 복사가 아니라 원본을 계속 따라가는 것이라 스택 프레임이 사라진 뒤에는 성립할 수 없다. **정답이 없는 상황 자체를 만들지 않으려고 언어가 "캡처되는 지역변수는 재할당하지 마라"고 못 박은 것**이다.

인스턴스 필드와 static 필드에는 이 제약이 없다. 그것들은 스택이 아니라 힙에 살아서 메서드가 끝나도 사라지지 않고, 람다는 값을 복사하는 대신 그 객체의 참조를 통해 **원본 필드를 계속 읽기** 때문이다. 이 차이 때문에 "람다 안에서 필드는 자유롭게 바뀌는데 지역변수는 왜 안 되지?"라는 혼란이 자주 생긴다 — **사는 곳이 다르기 때문**이라고 정리하면 된다.

## 2. 가장 중요한 구분 — final 참조는 불변 객체가 아니다

### 2-1. final은 화살표를 잠그고, 상자 안은 놔둔다

1-5의 그림을 다시 한 문장으로 요약하면 이렇다. **`final`은 변수 칸의 주소값을 고정할 뿐, 그 주소가 가리키는 객체의 내용물에는 아무 힘도 미치지 않는다.**

```text
final List<OrderItem> items = new ArrayList<>();

  변수 칸                            힙의 ArrayList
  +--------------+                 +--------------------------+
  | 0x4b2a...    | ==============> |   [0] 사과                |
  +--------------+                 |   [1] 우유                |
   ^                               +--------------------------+
   |                                ^
   final이 잠근 곳                   여기는 안 잠겼다
   (다른 상자를 가리키게 못 한다)      (add / remove / clear 전부 된다)
```

그래서 이런 코드가 나온다.

```java
private final List<OrderItem> items = new ArrayList<>();

items = new ArrayList<>();   // 컴파일 에러 — 화살표를 다른 상자로 옮기는 행위. final이 막는 건 이것뿐이다
items.add(newItem);          // 통과 — 상자 안에 물건을 넣는 행위. final과 무관하다
items.clear();               // 통과 — 상자를 전부 비워도 final은 침묵한다
```

**`final List`는 불변 리스트가 아니다.** 코드 리뷰에서 가장 흔한 착각이고, 자바에서 가장 자주 오해되는 지점 중 하나다.

### 2-2. 진짜 불변 객체는 세 겹이다

그럼 밖에서 손댈 수 없는 객체를 만들려면 무엇이 더 필요한가. `final` 필드 위에 두 겹을 더 얹어야 한다.

```java
// Before: final만 믿고 내부 리스트를 그대로 주고받는다
public class Order {
    private final List<OrderItem> items;

    public Order(List<OrderItem> items) {
        this.items = items;                 // 호출자가 넘긴 리스트를 그대로 들고 있는다
    }                                       // 호출자도 같은 리스트의 참조를 계속 갖고 있다

    public List<OrderItem> getItems() {
        return items;                       // 내부 참조를 그대로 밖으로 내보낸다
    }
}

// 밖에서 이렇게 하면 주문 내용물이 증발한다
order.getItems().clear();
```

```java
// After: 들어올 때 복사해서 불변화하고, 클래스까지 봉인한다
public final class Order {                          // (3) 자식이 가변성을 못 덧붙인다
    private final List<OrderItem> items;            // (1) 화살표 고정

    public Order(List<OrderItem> items) {
        // (2) 들어오는 순간 복사해 불변 리스트로 만든다.
        //     복사이므로 호출자가 원본을 나중에 바꿔도 우리 것은 안 바뀌고,
        //     불변이므로 밖으로 나간 뒤 수정 시도는 예외로 즉시 드러난다.
        this.items = List.copyOf(items);
    }

    public List<OrderItem> getItems() {
        return items;                               // 이미 불변이라 그냥 반환해도 안전하다
    }
}
```

정리하면 **불변 객체 = ① 필드가 `final` + ② 필드가 가리키는 객체도 불변이거나 아예 노출하지 않음 + ③ 클래스가 `final`** — 이 셋이 세트다. `String`이 정확히 이 조합이다.

여기서 한 가지 한계를 짚어야 한다. **`List.copyOf`가 하는 복사는 얕은 복사(shallow copy)**다. 리스트라는 상자는 새로 만들어지지만, 그 안에 든 `OrderItem` 객체들은 복제되지 않고 주소값만 옮겨진다. 그래서 `OrderItem`에 세터가 있으면 `order.getItems().get(0).changeQuantity(999)`로 여전히 뚫린다. **완전한 방어는 원소 타입까지 불변일 때 성립한다.** 이 주제 전체는 `21-defensive-copy-collection-exposure.md`에서 따로 다룬다.

### 2-3. 그래서 final 필드가 실무에서 무엇을 벌어 주는가

**(1) 생성자 주입과 짝을 이뤄 의존성 누락을 컴파일 에러로 만든다.**

```java
@Service
public class SettlementService {
    private final OrderRepository orderRepository;   // final이라 반드시 대입돼야 한다

    public SettlementService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}
```

필드가 `final`이면 **모든 생성자에서 반드시 값을 채워야** 하므로, 의존성을 하나 추가하고 생성자에 넣는 것을 잊으면 그 자리에서 컴파일이 실패한다. 그리고 빈이 완성된 뒤에 누군가 의존성을 바꿔 끼울 가능성이 원천 차단된다.

**`@Autowired` 필드 주입은 `final`을 쓸 수 없다는 점 자체가 필드 주입을 피할 이유 중 하나다.** 필드 주입은 객체를 먼저 만들고 나중에 리플렉션으로 값을 밀어 넣는 방식이라, "생성자에서 한 번만 대입"이라는 `final`의 요구와 양립하지 않는다.

**(2) 읽는 사람의 추론 비용을 줄인다.**

`final` 필드는 "생성 시점의 값이 곧 이 객체의 평생 값"이다. 그래서 이 필드를 쓰는 코드를 읽을 때 **"이게 중간에 어디선가 바뀌지는 않나"를 추적할 필요가 없다.** 반대로 말하면, 코드 리뷰에서 **"이 필드 `final` 가능한데 안 붙어 있네요, 어딘가에서 재할당한다는 뜻인가요?"**는 숨은 가변 상태를 찾아내는 좋은 질문이 된다.

**(3) 스레드 안전의 절반을 가져간다.**

동시성 버그의 상당수는 **"공유 + 가변"의 조합**에서 나온다. 여러 스레드가 같은 객체를 보는데 그 객체가 도중에 바뀌기 때문이다. 상태가 아예 안 바뀌는 객체는 동기화 없이 마음껏 공유해도 안전하다. `final`은 이 조합에서 "가변" 쪽을 줄이는 도구다. 절반이라고 한 이유는 §2-1에서 본 그대로다 — `final`이 잠그는 것은 화살표뿐이라, 가리키는 객체가 가변이면 여전히 공유 가변 상태다.

### 2-4. final 필드의 JMM 특별 보장 (가산점 포인트)

`final` 필드에는 자바 메모리 모델(JMM)이 주는 **별도의 보장**이 하나 더 있다. 이것이 (3)의 "안전하다"를 실제로 떠받치는 근거다.

**보장의 내용은 이렇다. 어떤 객체의 생성자가 정상적으로 끝나면, 그 객체의 `final` 필드에 생성자에서 넣은 값은 다른 스레드에게도 완성된 상태로 보인다.** 그 객체의 참조를 어떤 방식으로 넘겨받든, 심지어 동기화 없이 넘겨받아도 그렇다.

왜 이런 보장이 따로 필요한지는 `new`가 실제로 어떻게 실행되는지를 보면 안다. `new Money(1000, "KRW")`는 한 덩어리의 동작이 아니라 **① 메모리 할당 → ② 생성자 실행(필드 채우기) → ③ 변수에 참조 대입**의 세 단계다. 그런데 컴파일러와 CPU는 성능을 위해 명령 순서를 바꿀 수 있고(**재배치**), 그 결과 다른 스레드에게는 ③이 ②보다 먼저 보일 수 있다.

```text
[재배치가 일어나면]

 스레드 A                              스레드 B
 ---------------------------------     ------------------------------------
 t0  메모리 할당
 t1  참조를 shared 변수에 대입  <- 순서가 앞당겨짐
                                       t2  shared를 읽는다 -> 참조가 있다
                                       t3  shared.amount를 읽는다 -> 0 (아직 안 채워짐)
 t4  생성자 실행 (amount = 1000)

     결과: B는 참조는 멀쩡한데 필드는 기본값인 "반쪽짜리 객체"를 잡았다
```

**`final` 필드에 대해서는 JMM이 이 재배치를 금지한다.** 그래서 참조가 보이는 시점에는 `final` 필드의 값도 이미 완성돼 있다. 이렇게 **다른 스레드가 완성된 객체만 보게 만드는 것**을 안전 발행(safe publication)이라 부르고, `final` 필드는 그 수단 중 하나다.

```java
public final class Money {
    private final long amount;      // final이라 안전 발행이 보장된다
    private final String currency;

    public Money(long amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }
}
```

**단, 조건이 하나 붙는다. 생성자가 끝나기 전에 `this` 참조가 밖으로 새어 나가면 안 된다.** 생성자 안에서 자기 자신을 리스너로 등록하거나, static 필드나 공유 컬렉션에 `this`를 넣거나, 내부 스레드를 시작하면서 `this`를 넘기는 경우가 여기 해당한다. 이런 코드는 **아직 완성되지 않은 객체를 다른 스레드가 볼 수 있게 만들기 때문에** 보장이 무너진다. 이 현상을 `this` 탈출(this escape)이라 부른다.

**"불변 객체는 동기화 없이 공유해도 안전하다"는 말의 JMM적 근거가 이것이라, 불변 객체의 필드는 습관적으로 `final`로 선언하는 것이 좋다.** 더 자세한 것은 `15-jmm-happens-before.md`에서 다룬다.

## 3. 실무 버그 — final 메서드와 Spring 프록시

### 3-1. 먼저 CGLIB이 무엇을 하는지 알아야 한다

스프링의 `@Transactional`, `@Cacheable`, `@Async` 같은 기능은 여러분이 만든 객체가 직접 수행하는 것이 아니다. 스프링이 **그 객체를 감싼 대역(프록시)**을 만들어 빈으로 등록하고, 호출은 전부 그 대역을 먼저 거치게 한다. 대역이 앞뒤에 트랜잭션 시작·커밋 코드를 끼워 넣고 가운데서 원본을 부르는 식이다.

대역을 만드는 방법은 두 가지인데, **스프링 부트의 기본값은 CGLIB**이다. CGLIB이 하는 일은 정확히 이것이다.

```text
[원본]                      [CGLIB이 런타임에 만들어 내는 대역]

class SettlementService     class SettlementService$$SpringCGLIB extends SettlementService {
  public void settle(...)     @Override
                              public void settle(...) {      <- 재정의해서 가로챈다
                                  트랜잭션 시작;
                                  원본 인스턴스의 settle 호출;
                                  커밋 또는 롤백;
                              }
                            }
```

**CGLIB은 대상 클래스를 상속한 자식 클래스를 만들어 메서드를 재정의한다.** 이 한 문장에서 이 절의 모든 함정이 기계적으로 따라 나온다.

### 3-2. final 메서드에 붙은 @Transactional은 조용히 무시된다

`final` 메서드는 재정의가 금지된다(1-4). 그런데 CGLIB의 개입 수단이 바로 그 재정의다. **가로챌 방법이 없어진다.**

```java
@Service
public class SettlementService {

    @Transactional
    public final void settle(Long orderId) {   // 문제 지점 — final이라 프록시가 재정의할 수 없다
        ...                                    // 트랜잭션 없이 그냥 실행된다
    }
}
```

무서운 것은 결과가 아니라 **아무 일도 일어나지 않는다는 점**이다. 프록시는 그 메서드만 건너뛰고, 나머지는 정상적으로 만들어진다. 예외도 나지 않고 기동도 성공한다(스프링 버전에 따라 "final이라 프록시할 수 없다"는 취지의 로그가 남기도 하지만, 애플리케이션 로그에 묻히기 쉬운 수준이다).

그래서 증상이 이렇게 나타난다.

```text
t0  배포. 아무 문제 없이 기동된다.
t1  평소 요청은 전부 정상 처리된다 — 예외가 안 나면 트랜잭션이 없어도 결과가 같기 때문이다.
    ★ 트랜잭션이 안 걸렸다는 사실이 아무 데도 드러나지 않는다.

t2  (며칠 뒤) settle 중간에서 예외가 터진다.
    앞부분에서 실행된 UPDATE는 이미 커밋돼 있고, 뒷부분은 실행되지 않았다.
    롤백이 없으므로 데이터가 반쪽만 반영된 상태로 남는다.

t3  정산 대사에서 "금액이 안 맞는 건이 있습니다"로 처음 발견된다.
```

**t2의 스택트레이스는 예외가 터진 그 줄을 가리킬 뿐, `final` 키워드를 가리키지 않는다.** 원인과 증상이 멀리 떨어져 있는 전형적인 조용한 버그다.

### 3-3. final 클래스는 오히려 낫다 — 기동할 때 터지기 때문이다

같은 원인인데 결과가 다른 경우가 하나 있다.

- **`final` 클래스**: CGLIB이 상속 자체를 못 하므로 **프록시 생성이 실패하고 기동 시점에 예외가 난다.** 배포가 실패하니 즉시 알 수 있다.
- **`final` 메서드**: 클래스 상속은 되므로 프록시는 만들어지고, **그 메서드만 조용히 원본 그대로 남는다.**

**시끄럽게 실패하는 쪽이 안전하다.** `final` 메서드가 더 위험한 이유는 문제의 크기가 아니라 **발견 시점이 늦다는 것**이다.

여기서 얻을 교훈은 "`final`을 쓰지 마라"가 아니다. **프록시 기반 프레임워크가 상속으로 개입하는 지점(스프링 빈의 public 메서드)에서는 `final`이 프레임워크 기능을 침묵 속에 꺼버릴 수 있다**는 것을 알고, 그 자리만 예외로 두라는 것이다.

같은 이유로 **Kotlin에서는 이 문제가 언어 차원의 기본값과 정면으로 충돌한다.** Kotlin은 클래스와 메서드가 기본적으로 `final`이고 `open`을 붙여야 상속·재정의가 가능하다. 그래서 스프링 부트의 Kotlin 지원 플러그인(`kotlin-allopen` 계열)이 `@Component`, `@Transactional` 등이 붙은 클래스를 **컴파일 시점에 자동으로 `open`으로 바꿔 준다.** 이 플러그인이 빠진 프로젝트에서 "코틀린으로 바꿨더니 트랜잭션이 안 걸린다"는 증상이 나오는 것이 이 구조 때문이다.

### 3-4. static final 상수의 컴파일 타임 인라이닝 (가산점 포인트)

`static final`에 **컴파일 타임 상수**(기본형이나 String 리터럴을 상수식으로 대입한 것)를 담으면, 컴파일러가 **그 값을 사용하는 쪽 바이트코드에 그대로 박아 넣는다.** 사용하는 쪽 `.class` 파일 안에는 "저 클래스의 그 필드를 읽어라"가 아니라 **숫자나 문자열 자체**가 들어간다.

이것이 무슨 결과를 낳는지는 실제로 해보면 분명하다.

```java
// Const.java (모듈 A)
public class Const {
    public static final int MAX = 100;
    public static final String NAME = "old";
    public static final Integer BOXED = 100;   // Integer는 컴파일 타임 상수가 아니다
}

// Use.java (모듈 B) — Const를 참조한다
System.out.println(Const.MAX);     // 100
System.out.println(Const.NAME);    // old
System.out.println(Const.BOXED);   // 100
```

이제 **`Const.java`만 고쳐서 다시 컴파일하고, `Use.java`는 재컴파일하지 않는다.**

```java
public class Const {
    public static final int MAX = 999;
    public static final String NAME = "new";
    public static final Integer BOXED = 999;
}
```

같은 `Use`를 그대로 실행하면 결과가 이렇게 갈린다.

```text
Const.MAX     -> 100     (999로 바꿨는데 옛날 값이 나온다)
Const.NAME    -> "old"   (마찬가지)
Const.BOXED   -> 999     (이건 새 값이 나온다)
```

`int`와 `String`은 컴파일 타임 상수라 `Use.class` 안에 값이 이미 박혀 있고, `Integer`는 박스 타입이라 상수로 취급되지 않아 실행 시점에 `Const` 클래스를 읽어 오기 때문이다.

**실무에서 이 함정이 걸리는 자리**는 여러 배포 단위가 상수를 공유할 때다. 공통 모듈에 `public static final int MAX_RETRY = 3;`을 두고 여러 서비스가 그 값을 쓰고 있다면, **공통 모듈만 새 버전으로 배포해도 각 서비스는 옛날 값으로 계속 동작한다.** 로그에는 "공통 모듈 v2.1 적용"이라고 찍히는데 동작은 v2.0이다.

**대응은 둘 중 하나다.** 상수를 바꿨으면 **의존하는 모든 모듈을 함께 재빌드·재배포**하거나, 애초에 **런타임에 읽히는 형태**(설정 파일, `static` 메서드 반환값, DB 값)로 빼는 것이다. 배포 없이 바뀌어야 하는 값이라면 후자가 맞다.

## 4. 꼬리질문 대비 포인트

### "`final List` 필드면 그 리스트는 불변인가요?"

**아니다.** `final`은 변수 칸에 든 **주소값**을 고정할 뿐이고, 그 주소가 가리키는 객체의 내용물에는 아무 힘이 없다. `items = new ArrayList<>()`는 컴파일 에러지만 `items.add(...)`, `items.clear()`는 전부 통과한다.

**진짜 불변을 만들려면 세 겹이 필요하다.** ① 필드를 `final`로 두고, ② 그 필드가 가리키는 객체를 불변 컬렉션(`List.copyOf`)으로 만들거나 방어적 복사를 하고, ③ 클래스를 `final`로 봉인해 자식이 가변성을 덧붙이지 못하게 한다.

**들어오는 쪽도 막아야 한다는 점**을 덧붙이면 좋다. 생성자에서 받은 리스트를 그대로 보관하면 호출자가 그 리스트의 참조를 계속 들고 있으므로, 나중에 호출자가 원본을 수정하면 내부 상태도 함께 바뀐다. 그래서 경계에서 복사한다.

한계까지 말하면 완성된다 — **컬렉션 복사는 얕은 복사라서 원소가 가변 객체면 원소를 통해 여전히 뚫린다.** 완전한 방어는 원소 타입까지 불변일 때 성립한다.

### "람다나 익명 클래스에서 지역변수는 왜 final(effectively final)이어야 하나요?"

**지역변수와 람다의 수명이 다르기 때문이다.**

지역변수는 스택 프레임에 살고 메서드가 끝나면 프레임과 함께 사라진다. 반면 람다 객체는 힙에 살면서 그보다 오래 살아남고, 나중에 다른 스레드에서 실행될 수도 있다. 그래서 자바는 람다를 만드는 시점에 **지역변수의 값을 한 벌 복사해서** 람다 안에 넣어 둔다(캡처).

복사본이 생긴 뒤에 원본이 바뀌면 **둘 중 어느 쪽이 진짜인지 정할 수 없다.** 복사본을 따르면 "분명히 바꿨는데 반영이 안 된다"가 되고, 원본을 따르려면 이미 사라진 스택 프레임을 읽어야 한다. **정답이 없는 상황 자체를 만들지 않으려고 재할당을 금지한 것**이다.

`effectively final`은 `final` 키워드가 없어도 재할당이 한 번도 없는 변수를 컴파일러가 final로 취급해 주는 것(Java 8+)이라, 실제로는 키워드를 안 붙여도 대부분 통과한다.

**인스턴스 필드에는 이 제약이 없다**는 대비까지 말하면 이해도가 드러난다. 필드는 스택이 아니라 힙에 살아서 사라지지 않으므로, 람다가 값을 복사하는 대신 객체 참조를 통해 원본 필드를 계속 읽기 때문이다.

### "final 필드가 멀티스레드 환경에서 주는 특별한 보장이 있나요?" (가산점 포인트)

**있다. 자바 메모리 모델이 `final` 필드에 한해 별도 보장을 준다.**

**객체의 생성자가 정상적으로 끝나면, 그 객체의 `final` 필드에 생성자에서 넣은 값은 다른 스레드에게도 완성된 상태로 보인다.** 참조를 동기화 없이 넘겨받아도 그렇다.

왜 이 보장이 필요한지는 `new`의 실체를 보면 안다. `new`는 **할당 → 생성자 실행 → 참조 대입**의 3단계인데, 재배치로 참조 대입이 생성자 실행보다 먼저 보일 수 있다. 그러면 다른 스레드가 **참조는 있는데 필드는 아직 기본값(0/null)인 반쪽짜리 객체**를 잡는다. `final` 필드에 대해서는 JMM이 이 재배치를 금지해 그 상태를 원천 차단한다. 이렇게 완성된 객체만 보이게 만드는 것을 **안전 발행(safe publication)**이라 한다.

**조건이 하나 붙는다는 것까지 말해야 정확하다** — 생성자가 끝나기 전에 `this` 참조가 밖으로 새면(생성자 안에서 자기를 리스너로 등록하거나 static 컬렉션에 넣거나 스레드에 넘기면) 보장이 무너진다. 이를 `this` 탈출(this escape)이라 한다.

**"불변 객체는 동기화 없이 공유해도 안전하다"는 말의 JMM적 근거가 이것**이므로, 불변 객체의 필드는 습관적으로 `final`로 선언하는 것이 좋다.

### "클래스에 final을 붙여 상속을 막는 설계는 언제 정당한가요?" (시니어 변별 포인트)

**트레이드오프 판단이므로 양쪽 근거를 다 대는 것이 좋다.**

**막는 쪽의 근거.** 상속을 안전하게 허용하려면 자식이 어느 메서드를 재정의해도 깨지지 않도록 **내부에서 자기 메서드를 어떻게 호출하는지(self-use) 구조까지 설계하고 문서화**해야 한다. 그 비용을 치르지 않았다면 봉인이 정직한 선택이다 — "상속을 위해 설계하고 문서화하지 않았으면 상속을 금지하라"는 원칙이 그 뜻이다. 그리고 불변 클래스는 자식이 가변성을 추가하는 순간 보장이 깨지므로 `final`이 사실상 필수다(1-3의 `String`).

**여는 쪽의 근거.** §3의 프록시 문제처럼 프레임워크가 상속으로 개입하는 클래스는 `final`이면 안 된다. 스프링 빈이 대표적이고, 테스트에서 라이브러리 클래스를 상속해 대역을 만들어야 하는 경우도 있다.

**정리하면 자리마다 기본값이 다르다.** 도메인 값 객체와 불변 객체는 `final` 기본, 프레임워크가 프록시할 빈은 열어 두고, 확장은 상속이 아니라 **인터페이스 + 합성**으로 제공한다. "상속을 봉인하는 대신 확장 지점을 다른 형태로 열어 준다"는 짝까지 말하면 답이 완성된다.

### "`static final` 상수는 그냥 final 필드와 무엇이 다른가요?" (가산점 포인트)

**컴파일 타임 상수는 사용하는 쪽 바이트코드에 값이 박힌다는 점이 다르다.**

`static final`에 기본형이나 String 리터럴을 상수식으로 대입하면, 컴파일러가 그 값을 **사용처의 `.class` 파일에 직접 써 넣는다.** 그래서 상수를 정의한 모듈만 새로 배포하고 사용하는 모듈을 재컴파일하지 않으면 **사용처는 옛날 값으로 계속 동작한다.** 실제로 `int MAX = 100`을 `999`로 바꾸고 정의 모듈만 재컴파일하면, 사용 모듈은 여전히 `100`을 출력한다.

**박스 타입은 다르게 동작한다는 것까지 알면 정확도가 올라간다** — `public static final Integer BOXED = 100;`은 컴파일 타임 상수가 아니라서 인라이닝되지 않고, 정의 모듈만 다시 빌드해도 새 값이 반영된다.

**운영 감각은 결론에서 드러난다.** 여러 배포 단위가 공유하는 상수를 바꿀 때는 **의존하는 모듈을 전부 재빌드·재배포해야 하고**, 배포 없이 바뀌어야 하는 값이라면 애초에 상수가 아니라 설정이나 DB로 빼는 것이 맞다.

## 한 줄 요약

`final`은 클래스에서 상속을, 메서드에서 재정의를, 변수에서 재할당을 막아 "여기는 바뀌지 않는다"를 컴파일러 수준에서 선언하는 어휘이지만, 변수의 `final`이 잠그는 것은 **주소값이 든 변수 칸이지 그 주소가 가리키는 객체가 아니므로** `final List`에 `add`는 그대로 되고 진짜 불변은 `final` + 불변 컬렉션(또는 방어적 복사) + 클래스 `final`의 세 겹으로만 완성된다 — 여기서 파생되는 세 가지가 실무 어휘의 시작이다. 람다는 지역변수의 **값을 복사**해 가는데 원본 스택 프레임은 메서드가 끝나면 사라지므로 원본이 바뀌면 어느 쪽이 진짜인지 정할 수 없어 effectively final을 요구하고, CGLIB은 **대상 클래스를 상속한 자식을 만들어 재정의**하는 방식이라 `final` 메서드에 붙은 `@Transactional`이 예외 하나 없이 조용히 꺼지며, `final` 필드에는 JMM이 별도 보장을 주어 **생성자가 정상 종료하고 `this`가 새지 않으면** 다른 스레드에도 완성된 값이 보인다.
