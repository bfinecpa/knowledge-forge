# GC 동작 원리와 세대별 수집 — Young/Old를 나누는 이유

> 핵심 관전 포인트: **GC는 "GC 루트에서 참조를 따라가 닿을 수 있는가(reachability)"로 살릴 객체를 표시(mark)하고, 닿지 않는 객체를 회수한다. Young/Old를 나누는 이유는 세대 가설 — "대부분의 객체는 만들어지자마자 죽는다" — 때문이다. 전체 힙을 매번 뒤지는 대신, 객체가 태어나는 좁은 Young만 자주·싸게 수집(Minor GC)하고 오래 살아남은 소수만 Old로 승격시키면, 비싼 전체 수집(Full GC)의 빈도를 극적으로 줄일 수 있다.**

---

## 0. 질문 + 의도

**질문**: "GC가 동작하는 원리를 설명해주세요. Young/Old 영역은 왜 나뉘어 있나요?"

**출제 의도**: GC 로그와 pause 그래프를 읽는 능력의 기초. "왜 트래픽 피크마다 응답이 200ms 튀는가"의 범인이 GC인지 아닌지를 가려내려면 세대별 수집의 동작을 알아야 한다. 또한 "객체를 오래 들고 있는 코드가 왜 비싼지"를 체감하는 사람만 캐시 크기 같은 결정을 제대로 한다.

## 1. GC의 기본 원리 — "쓰레기"를 어떻게 판정하는가

### 1-1. 전제 지식 — 진짜 어려운 문제는 "치우는 것"이 아니라 "판정하는 것"이다

C에서는 `malloc`으로 받은 메모리를 개발자가 `free`로 직접 돌려준다. Java에는 그런 게 없다. `new`만 있고 `delete`는 없다. 그럼 누가 언제 메모리를 돌려주는가 — 그 일을 하는 것이 **GC(Garbage Collector, 쓰레기 수집기)**다.

여기서 GC의 진짜 문제가 무엇인지를 정확히 짚어야 뒤가 풀린다. 메모리를 반환하는 것 자체는 어렵지 않다. **어려운 것은 "이 객체는 이제 아무도 안 쓴다"를 어떻게 확신하느냐다.** 하나라도 잘못 판정해서 아직 쓰는 객체를 회수해 버리면 프로그램은 즉시 죽는다. 그래서 GC는 반드시 **"확실히 안 쓴다"고 증명할 수 있는 객체만** 회수해야 한다.

그 증명을 어떻게 하는가. 앞선 JVM 메모리 구조 문서에서 봤듯이 **변수에 담기는 것은 객체가 아니라 객체가 있는 힙 주소값, 즉 참조**다. 그러니 "아무도 안 쓴다"는 것은 **"그 객체를 가리키는 참조를 따라 도달할 방법이 하나도 남지 않았다"**로 번역할 수 있다. 아무도 찾아갈 수 없는 집은, 그 집에 뭐가 들어 있든 프로그램에 아무 영향을 줄 수 없기 때문이다.

이 번역이 GC 전체를 지탱하는 아이디어다.

### 1-2. 도달 가능성(reachability) — GC의 유일한 질문

GC의 질문은 하나뿐이다. **"이 객체에 아직 닿을 수 있는가?"**

**도달 가능성(reachability)**이란 말 그대로 **"출발점에서 참조를 따라가면 그 객체에 도달(reach)할 수 있는가"**를 뜻한다. 도달할 수 있으면 살아있는 것으로 보고, 도달할 수 없으면 쓰레기로 판정한다.

지하철 노선도를 떠올리면 된다. 우리가 서 있는 역(출발점)에서 선로를 따라가 닿을 수 있는 역은 전부 "살아있는 역"이다. 어느 선로와도 이어져 있지 않아 그 안에 열차가 몇 대 있든 아무도 갈 수 없는 고립된 역이 있다면, 그 역과 그 안의 열차는 전부 없앨 수 있다. **역 안에 열차가 서로 오가고 있는지 없는지는 판정과 무관하다** — 바깥에서 들어갈 방법이 없다는 것만이 기준이다. 이 마지막 문장이 1-4의 순환 참조 이야기로 이어진다.

### 1-3. GC 루트 — 그 출발점이 무엇인가

그렇다면 "출발점"은 무엇인가. 이것이 **GC 루트(GC Root)**다. **프로그램이 지금 이 순간 확실히 붙잡고 있다고 말할 수 있는, 참조 그래프 탐색의 시작점**들을 가리킨다. 나무의 뿌리(root)에서 가지를 따라 뻗어나가듯 여기서부터 참조를 따라간다고 해서 루트다.

대표적인 GC 루트는 다음과 같다.

- 각 스레드 **스택의 지역변수·파라미터**가 쥔 참조 — 지금 실행 중인 코드가 손에 들고 있는 것들이다.
- **static 필드**가 쥔 참조 — 클래스가 로딩된 동안 계속 살아 있으므로 영구적인 출발점이 된다.
- JNI(네이티브 코드)가 쥔 참조, 실행 중인 스레드 객체 자체, 동기화 모니터를 쥔 객체 등.

이 목록에 공통점이 있다. **전부 "힙 바깥에서 힙 안을 가리키는 참조"**다. 힙 안의 객체가 다른 객체를 가리키는 것은 루트가 아니다 — 그 객체 자신이 살아 있다는 보장이 없기 때문이다.

```java
void handle() {
    Order order = new Order();   // 스택의 order가 루트다.
                                 // 루트 -> Order 경로가 있으므로 살아있음.
}                                // 리턴하면 프레임이 걷히며 order가 사라진다.
                                 // 루트에서 Order로 가는 경로가 끊김 -> 회수 후보.
```

여기서 실무적으로 중요한 사실 두 가지가 나온다.

**첫째, `order = null`을 굳이 대입할 필요가 없다.** 루트에서 닿는 경로가 끊기는 순간 이미 회수 후보다. 메서드 끝에서 지역변수를 `null`로 밀어 넣는 코드는 대부분 의미가 없다. (예외적으로 의미가 있는 경우는 아주 긴 메서드 안에서 거대한 객체를 다 쓰고 난 뒤, 메서드가 끝나기까지 한참 남았을 때 정도다.)

**둘째, static 컬렉션에 넣어둔 객체는 절대 회수되지 않는다.** static 필드가 루트이므로 루트에서 영원히 닿기 때문이다. 이것이 Java 메모리 누수의 가장 전형적인 형태다. Java에는 "누수"가 없다고들 하지만, 정확히는 **"실수로 참조를 놓치는 누수는 없고, 실수로 참조를 붙잡는 누수는 있다"**가 맞다.

### 1-4. 왜 참조 카운팅이 아닌가 — 순환 참조 (가산점 포인트)

도달 가능성 말고 다른 방법도 있다. **참조 카운팅(reference counting)**은 객체마다 "나를 가리키는 참조가 몇 개인가"를 세는 카운터를 두고, 누군가 나를 가리키면 +1, 참조를 끊으면 -1 하다가 **0이 되는 순간 즉시 회수**하는 방식이다. 구현이 단순하고, 쓰레기가 되는 즉시 회수되니 지연도 없다.

그런데 이 방식에는 원리적으로 못 푸는 구멍이 있다. **서로가 서로를 참조하는 순환 구조**다. 코드로 보면 한눈에 들어온다.

```java
class Node {
    String name;
    Node partner;          // 다른 Node를 가리키는 참조 필드
    Node(String name) { this.name = name; }
}

void makeCycle() {
    Node a = new Node("a");
    Node b = new Node("b");

    a.partner = b;         // a 객체가 b 객체를 가리킨다  -> b의 참조 카운트 = 2 (지역변수 b + a.partner)
    b.partner = a;         // b 객체가 a 객체를 가리킨다  -> a의 참조 카운트 = 2 (지역변수 a + b.partner)
}
// 메서드가 끝나면서 지역변수 a, b가 사라진다.
//
// [참조 카운팅이라면]
//   a의 카운트: 2 -> 1 (b.partner가 여전히 가리킴)
//   b의 카운트: 2 -> 1 (a.partner가 여전히 가리킴)
//   둘 다 0이 아니므로 영원히 회수되지 않는다. 서로가 서로를 살려주는 셈이다.
//
// [도달 가능성이라면]
//   루트(스택)에서 a, b로 들어가는 경로가 하나도 없다.
//   둘이 서로를 가리키고 있든 말든 바깥에서 못 들어가므로 통째로 회수된다.
```

그림으로 보면 왜 카운팅이 속는지 명확하다.

```
   [GC 루트: 스택]
         │
         │  makeCycle() 리턴 후 — 루트에서 나가는 화살표가 전부 사라졌다
         ×
    ┌────┴─────────────────────┐
    │   (고립된 섬)             │
    │    ┌───┐  partner  ┌───┐ │
    │    │ a │ ────────► │ b │ │   ← 서로를 가리키는 화살표는 남아 있다
    │    │   │ ◄──────── │   │ │      참조 카운팅: 둘 다 카운트 1  -> 회수 불가
    │    └───┘  partner  └───┘ │      도달 가능성: 루트에서 진입 불가 -> 섬째로 회수
    └──────────────────────────┘
```

**JVM이 도달 가능성 방식을 쓰는 핵심 이유가 이것이다.** 순환은 실무에서 드문 구조가 아니다 — 양방향 연관관계를 맺은 JPA 엔티티(`Order.items` ↔ `OrderItem.order`), 부모/자식 노드를 서로 참조하는 트리, 리스너를 등록하며 자기 자신을 넘기는 콜백 구조가 전부 순환이다. 참조 카운팅이었다면 이런 구조는 하나같이 누수가 됐을 것이다.

대신 도달 가능성은 대가를 치른다. **"카운트가 0이 되는 즉시"가 아니라 "GC가 돌 때 한꺼번에"** 판정하므로, 쓰레기가 된 뒤 실제 회수까지 시간차가 생긴다. 그리고 그래프를 순회해야 하므로 판정 자체가 비싸다. 이 두 가지 대가를 어떻게 줄이느냐가 2절의 세대별 수집으로 이어진다.

### 1-5. 회수의 3가지 기본 동작 — Mark, Sweep, Compact

살릴 것과 버릴 것을 가르고 나면 실제로 공간을 되찾아야 한다. 어떤 GC 알고리즘이든 이 세 동작의 조합이다.

**Mark(표시)** — 루트에서 참조 그래프를 순회하며 도달한 객체에 "살아있음" 표시를 남긴다. 앞의 판정 단계가 이것이다. 비용은 **살아있는 객체 수에 비례**한다(죽은 객체는 애초에 방문하지 않으므로).

**Sweep(쓸어내기)** — 표시되지 않은 객체가 있던 자리를 "빈 공간"으로 등록한다. 문제는 회수된 자리가 여기저기 흩어져 **빈틈(단편화, fragmentation)**으로 남는다는 것이다. 총 빈 공간은 100MB인데 연속된 자리는 최대 2MB뿐이라면, 10MB짜리 배열 하나를 할당하지 못해 OOM이 날 수도 있다.

**Compact(압축)** — 살아있는 객체를 한쪽 끝으로 밀어 모아 빈 공간을 뒤쪽에 하나의 연속 덩어리로 만든다. 단편화를 없애지만 객체를 실제로 **이동**시켜야 하고, 이동하면 그 객체를 가리키던 모든 참조의 주소값도 전부 고쳐 써야 하므로 비싸다.

**Copy(복사)** — Compact의 사촌이다. 살아있는 객체를 **다른 영역으로 옮겨 담고 원래 영역을 통째로 비운다.** 옮겨 담는 과정에서 자연히 한쪽으로 몰리므로 단편화가 없다. 2-4에서 이 방식이 왜 Young에서 극도로 저렴한지를 숫자로 본다.

### 1-6. Stop-The-World — GC가 응답시간 스파이크의 범인인 이유

이 작업들의 상당 부분은 **작업 도중 객체 그래프가 변하면 안 된다.** mark 중에 애플리케이션 스레드가 참조를 바꿔버리면 이미 지나간 객체가 새로 살아나거나, 살아있는 객체를 놓칠 수 있기 때문이다. compact 중이라면 더 심각하다 — 객체를 옮기는 중에 누가 옛 주소로 접근하면 그대로 깨진다.

그래서 GC는 **애플리케이션 스레드를 전부 멈춰 세우고** 자기 일을 하는 구간을 갖는다. 이 구간을 **Stop-The-World(STW)**라고 부른다. 그 순간 애플리케이션의 시간이 완전히 정지하고, 세상이 멈춘다고 해서 붙은 이름이다.

**"GC = 응답시간 스파이크"라는 등식이 성립하는 이유가 정확히 이 STW다.** 처리 중이던 요청은 STW 동안 아무것도 못 하고 그대로 서 있다가, 재개된 뒤 이어서 처리된다. 사용자 입장에서는 그 정지 시간이 통째로 응답시간에 더해진 것으로 보인다. GC가 CPU를 쓰는 것 자체는 별로 문제가 아니다 — 문제는 그 사이 아무도 일을 못 한다는 것이다.

그래서 GC 튜닝의 목표는 대개 "GC를 덜 돌리기"가 아니라 **"STW 시간을 짧게, 그리고 예측 가능하게 만들기"**다. 컬렉터가 세대를 나누고(2절), 동시(concurrent) 수행을 늘려온 역사가 전부 이 목표를 향한 것이다.

## 2. Young/Old를 나누는 이유 — 세대 가설

### 2-1. 관찰: 대부분의 객체는 요절한다

**약한 세대 가설(weak generational hypothesis)**은 실측에서 나온 경험칙이다. 내용은 두 문장이다. **대부분의 객체는 생성 직후 금방 죽는다. 그리고 오래 살아남은 객체는 앞으로도 계속 오래 산다.** "세대(generation)"라는 이름은 객체를 태어난 시기별로 묶어 다룬다는 뜻에서 왔다.

웹 서버로 생각하면 자명하다.

요청 하나를 처리하며 만드는 것들을 떠올려 보자. 파라미터를 담은 DTO, JSON 파싱 중간 산물, 조회 결과를 담은 엔티티 리스트, 응답 문자열, 로그 메시지. 이것들은 **응답을 내보내는 순간 전부 쓰레기**가 된다. 수명이 밀리초 단위다.

반면 커넥션 풀, 스프링 빈, 설정 객체, 캐시는 프로세스가 사는 내내 산다. 수명이 일 단위, 주 단위다.

그 사이 어중간한 수명의 객체는 상대적으로 드물다. **수명 분포가 양극단에 몰려 있다**는 것 — 이것이 세대 가설의 실체이고, 다음의 최적화가 성립하는 근거다.

### 2-2. 힙의 물리적 구획과 객체의 이동 경로

이 관찰을 어떻게 이용하는가. **죽을 확률이 높은 놈들만 좁은 곳에 몰아넣고 거기만 자주 치운다.** 그래서 힙을 이렇게 나눈다.

```
┌─────────────────── Heap ────────────────────────────────────────────┐
│                                                                     │
│  ┌──────────── Young ─────────────┐   ┌────────── Old ───────────┐  │
│  │                                │   │                          │  │
│  │  ┌─────────┐ ┌────┐ ┌────┐    │   │  오래 살아남은 소수       │  │
│  │  │  Eden   │ │ S0 │ │ S1 │    │──►│  (스프링 빈, 커넥션 풀,   │  │
│  │  │(새 객체)│ │    │ │    │    │승격│   장수 캐시 …)           │  │
│  │  └─────────┘ └────┘ └────┘    │   │                          │  │
│  │   Survivor 2개 ──────┘        │   │                          │  │
│  └────────────────────────────────┘   └──────────────────────────┘  │
│         ▲ Minor GC가 여기만 수집            ▲ 여기까지 수집하면      │
│           (자주, 싸게)                        Major / Full GC        │
└─────────────────────────────────────────────────────────────────────┘
```

용어를 하나씩 정의하고 가자.

**Eden(에덴)**은 새 객체가 태어나는 곳이다. `new`로 만든 객체는 예외적인 경우를 빼면 전부 여기 놓인다. 모든 것이 시작되는 동산이라는 뜻의 이름이다.

**Survivor(생존자 영역)**는 이름 그대로 **Minor GC에서 살아남은 객체가 잠시 머무는 대기실**이다. S0, S1 두 개가 있고 항상 하나는 비어 있다(이유는 2-5).

**Minor GC**는 **Young 영역만 대상으로 하는 수집**이다. "작은(minor)" 수집이라는 뜻이고, Young GC라고도 부른다.

**승격(promotion)**은 **Young에서 여러 번 살아남은 객체를 Old로 옮기는 것**이다. "이 객체는 요절하지 않는 부류인 것 같으니 이제 자주 검사하지 않는 곳으로 보내자"는 판단이다. 승진과 같은 단어를 쓰는 이유가 이것이다.

그 판단 기준이 **나이(age)**다. **객체가 Minor GC를 몇 번 살아남았는지를 세는 카운터**이고, 객체 헤더에 몇 비트로 기록된다. Minor GC를 한 번 견딜 때마다 1씩 오르고, 임계치(HotSpot 기본 상한은 15)를 넘으면 Old로 승격된다. 다만 실제 임계치는 고정이 아니다 — Survivor가 넘칠 것 같으면 JVM이 임계치를 그보다 낮춰 더 일찍 승격시키기도 한다.

**Old(구세대)**는 승격된 객체들이 사는 곳이다. **Major GC / Full GC**는 Old까지 포함해 수집하는 것을 가리키며, 훨씬 비싸다.

### 2-3. Eden → Survivor → Old 이동을 타임라인으로 보기

말로만 들으면 이동 경로가 잘 안 그려진다. 시간 순으로 따라가 보자. 알파벳 하나가 객체 하나이고, 뒤의 숫자는 나이다.

```
[t0] 기동 직후
  Eden [                    ]   S0 [        ]   S1 [        ]   Old [ 빈,풀,설정 ]
                                 (비어 있음)      (비어 있음)      (기동 시 만들어진 장수 객체)

[t1] 요청을 처리하며 새 객체가 계속 Eden에 쌓인다
  Eden [ A B C D E F G H I J ]   S0 [        ]   S1 [        ]   Old [ 빈,풀,설정 ]
                                                                  ↑ Old는 아무 일도 안 일어남

[t2] Eden이 꽉 참 → Minor GC #1 발생 (STW)
     루트에서 닿는 객체만 찾는다. A, D만 아직 참조되고 있고 나머지 8개는 이미 쓰레기.
     ┌ 하는 일: A, D를 S0으로 "복사"한다. 나이를 1로 올린다.
     └ 안 하는 일: B,C,E,F,G,H,I,J는 건드리지 않는다. 그냥 Eden 전체를 빈 것으로 선언.

  Eden [                    ]   S0 [ A1 D1  ]   S1 [        ]   Old [ 빈,풀,설정 ]
        ↑ 할당 포인터를 맨 앞으로 되돌리면 끝. 죽은 객체를 찾아다니지 않았다.

[t3] 다시 요청 처리 — 새 객체는 언제나 Eden에
  Eden [ K L M N O P Q R S T ]   S0 [ A1 D1  ]   S1 [        ]   Old [ 빈,풀,설정 ]

[t4] Eden이 다시 꽉 참 → Minor GC #2 (STW)
     이번 대상은 Eden + "현재 사용 중인 Survivor(S0)" 둘 다.
     생존자: Eden에서 M, S0에서 A (D는 그 사이 참조가 끊겨 죽음)
     생존자를 전부 "비어 있던 S1"으로 복사하고, S0과 Eden을 통째로 비운다.
     A는 또 살아남았으므로 나이가 2로 오른다.

  Eden [                    ]   S0 [        ]   S1 [ A2 M1  ]   Old [ 빈,풀,설정 ]
                                 ↑ 이제 S0이 빈 쪽,   ↑ 이제 S1이 사용 중인 쪽
                                   역할이 교대됐다

[t5] … 이 왕복이 반복된다. A는 갈 때마다 나이를 먹는다 …
     A3 → A4 → … → A15

[t6] A의 나이가 임계치를 넘음 → 승격(promotion)
     Minor GC 때 A를 Survivor가 아니라 Old로 복사한다.

  Eden [                    ]   S0 [ ...    ]   S1 [        ]   Old [ 빈,풀,설정, A ]
                                                                                ↑ 이제 Minor GC는
                                                                                  A를 쳐다보지 않는다
```

이 타임라인에서 꼭 붙잡아야 할 것은 t2와 t4의 "안 하는 일"이다. **Minor GC는 죽은 객체를 처리하지 않는다.** 살아있는 것만 들어내고 나면 나머지는 어차피 통째로 버릴 것이므로 개별적으로 손댈 이유가 없다.

### 2-4. Minor GC가 싼 진짜 이유 — 복사 방식을 숫자로 풀어 보기

"Minor GC는 싸다"는 말을 숫자로 확인하자. 아래 수치는 설명을 위해 **가정한 예시**이고 환경마다 다르지만, 자릿수의 차이가 어디서 오는지는 그대로다.

**전제**

- Eden 크기: 400MB
- 요청 처리 중 만들어지는 객체의 평균 크기: 100 바이트
- Young 생존율(Minor GC 시점에 아직 살아있는 비율): 2%

**Minor GC 한 번의 작업량을 단계별로 계산한다.**

1. Eden에 들어간 객체 수 = 400MB ÷ 100B = **400만 개**
2. 그중 살아남는 객체 수 = 400만 × 2% = **8만 개**
3. 죽은 객체 수 = 400만 − 8만 = **392만 개**
4. Mark 비용 = 살아있는 **8만 개**만 순회한다. 392만 개는 애초에 방문조차 하지 않는다.
5. Copy 비용 = 8만 개 × 100B = **8MB**를 Survivor로 옮긴다.
6. 죽은 392만 개를 처리하는 비용 = **0.** Eden의 할당 포인터를 맨 앞으로 되돌리는 것으로 끝난다.

**즉 400MB짜리 영역을 치우는데 실제로 만지는 것은 8MB, 400만 개 중 8만 개다.** 나머지 98%는 존재조차 확인하지 않는다. 이것이 "죽은 객체의 비용이 0"이라는 말의 정확한 의미다.

이제 같은 방식으로 Full GC를 계산해 비교하자.

**전제**

- Old 크기: 3GB
- Old의 생존율: 90% (Old에는 원래 오래 사는 것들만 있으므로 대부분 살아있다)
- 객체 평균 크기: 동일하게 100B

1. Old의 살아있는 객체 수 = 3GB × 90% ÷ 100B = **2,700만 개**
2. Mark 비용 = **2,700만 개** 전부 순회
3. Compact 비용 = **2.7GB**를 옮기고, 옮긴 객체들을 가리키던 참조를 전부 고쳐 씀

**두 작업의 mark 대상 객체 수 비율 = 2,700만 ÷ 8만 = 약 337배.** 옮기는 바이트로 보면 2.7GB ÷ 8MB로 약 337배다.

수치는 가정이지만 구조는 정확하다. **Young은 "거의 다 죽어 있는 좁은 영역"이라 만질 것이 거의 없고, Old는 "거의 다 살아 있는 넓은 영역"이라 만질 것이 전부다.** 세대 분리가 노리는 것은 이 비대칭이다.

여기에 하나 더 붙는 이점이 있다. 복사 방식은 살아있는 객체를 새 영역에 **차곡차곡 이어 붙이며** 옮기므로 결과가 자동으로 연속 공간이 된다. 즉 **단편화가 원천적으로 생기지 않는다.** Sweep 방식처럼 빈틈을 관리할 자료구조도 필요 없다.

### 2-5. Survivor가 왜 2개인가

복사 방식을 쓰기로 한 이상 **복사해 넣을 빈 공간이 반드시 있어야 한다.** 이것이 Survivor가 두 개인 이유다.

항상 한쪽(예: S1)을 완전히 비워 두고, Minor GC 때 **Eden + 사용 중인 Survivor(S0)**의 생존자를 전부 빈 쪽(S1)으로 몰아 복사한다. 복사가 끝나면 Eden과 S0을 통째로 비우고, 다음 회차에는 S1이 "사용 중", S0이 "빈 쪽"이 된다. 역할이 매번 교대된다.

Survivor가 하나뿐이라면 어떻게 되는가. 새 생존자를 넣을 자리를 그 안에서 골라야 하고, 죽은 객체가 남긴 빈틈을 관리해야 하며, 결국 단편화 처리가 필요해진다. **복사 방식의 이점이 통째로 사라진다.** "빈 공간을 하나 통째로 확보해 두는 것"이 이 알고리즘의 전제 조건이라, 그 대가로 Survivor 하나만큼의 공간을 항상 놀린다.

객체는 이 왕복을 견딜 때마다 나이를 먹고, 임계치를 넘으면 Old로 승격된다. 즉 **Survivor는 "이놈이 진짜 오래 살 놈인지" 몇 번 더 지켜보는 관찰 기간**이기도 하다. 이 관찰 없이 Eden에서 한 번 살아남았다고 바로 Old로 보내면, 잠깐 살다 죽을 객체까지 Old를 채우게 된다.

### 2-6. 정리 — 분리가 만드는 이득

| 항목 | Young (Minor GC) | Old (Full/Major GC) |
|---|---|---|
| 수집 빈도 | 잦음 | 드묾 (드물어야 정상) |
| 비용 | 쌈 — 생존 객체 수에 비례 | 비쌈 — 영역 크고 mark-sweep-compact 계열 |
| 전제 | 대부분 죽어 있음 | 대부분 살아 있음 |

세대 분리는 결국 **"싸게 자주 치울 수 있는 곳과 비싸서 아껴 치워야 하는 곳을 물리적으로 갈라놓은 것"**이고, 목표는 단 하나 — **Full GC 빈도의 최소화**다.

그러면 이런 질문이 자연스럽게 따라온다. **"Full GC를 늘리는 코드는 어떤 코드인가?"** 답은 3절이다.

## 3. 실무 맥락 — "객체를 오래 들고 있는 코드"가 비싼 이유

이 구조를 알면, 같은 메모리양을 쓰더라도 **객체의 수명 패턴**이 GC 비용을 좌우한다는 것이 보인다. 100MB를 쓰는 코드 두 개가 있을 때, 요청마다 만들고 버리는 100MB와 계속 붙잡고 있는 100MB는 GC 입장에서 전혀 다른 부담이다.

### 3-1. 사례: 트래픽 피크마다 응답이 200ms 튀는 서비스

트래픽이 늘면 요청당 임시 객체 생성 속도가 올라가 Eden이 빨리 차고 **Minor GC가 잦아진다.** 여기까지는 정상이다 — 2-4에서 봤듯 Minor GC는 싸므로, 자주 돌아도 각각이 짧으면 문제가 안 된다.

문제는 그다음이다. 요청 처리 중 객체를 **필요 이상으로 오래 들고 있으면** Minor GC 시점에 그 객체들이 아직 살아 있다. 생존율 2%를 전제로 잡았던 계산이 무너지고, Survivor로 복사되는 양이 늘어난다.

Survivor는 크지 않다. 복사해야 할 생존자가 Survivor 용량을 넘기면 JVM은 넘치는 분을 **나이가 어린데도 곧바로 Old로 보낸다.** 이것이 **조기 승격(premature promotion)**이다. "오래 살 놈인지 지켜보는" 관찰 기간을 건너뛰고, 곧 죽을 임시 객체가 Old로 들어가 버리는 것이다.

Old가 이런 임시 객체들로 차오르면 결국 **Full GC**가 돈다. 2-4의 계산대로 Full GC는 Minor GC보다 자릿수가 다르게 비싸고, 수백 ms의 STW가 응답시간 그래프에 그대로 스파이크로 찍힌다.

인과를 한 줄로 이으면 이렇다.

```
객체를 오래 쥠 → Minor GC 시점 생존율 상승 → Survivor 넘침
              → 조기 승격 → Old가 임시 객체로 차오름 → Full GC 빈발 → 응답 스파이크
```

"피크마다 200ms 튀는" 그래프의 전형적인 범인이 이 사슬이다. 그리고 이 사슬의 시작점이 **코드**이지 GC 옵션이 아니라는 점이 중요하다.

### 3-2. before/after — 무경계 캐시가 Old를 채우는 코드

가장 흔한 형태는 상한 없는 캐시다.

```java
// Before: 크기 제한 없는 static 캐시
public class ProductCache {
    // static 필드는 GC 루트다(1-3). 여기 담긴 것은 프로세스가 사는 내내 루트에서 닿는다.
    private static final Map<Long, Product> CACHE = new HashMap<>();

    public Product get(Long id) {
        return CACHE.computeIfAbsent(id, this::loadFromDb);
        // 한 번 들어온 Product는 참조가 영원히 끊기지 않는다 -> 절대 회수 불가.
        // Minor GC를 계속 살아남아 전부 Old로 승격되고, Old를 잠식한다.
        // 결과: Full GC 빈발 -> STW 누적 -> 최후에는 OutOfMemoryError: Java heap space.
        // 상품 수가 늘어나는 만큼 힙 사용량이 선형으로 늘어나는데, 상한이 없으므로
        // "언제 터질지"가 데이터 증가 속도에 달려 있다 — 시한폭탄에 가깝다.
    }
}

// After: 크기 상한 + 퇴출 정책이 있는 캐시 (예: Caffeine)
public class ProductCache {
    private final Cache<Long, Product> cache = Caffeine.newBuilder()
            .maximumSize(10_000)                       // 상한을 두면 Old 점유량의 최댓값을 미리 계산할 수 있다.
                                                       // 항목당 2KB라면 최대 20MB — 힙 예산에 넣을 수 있는 숫자가 된다.
            .expireAfterWrite(Duration.ofMinutes(10))  // 수명을 명시하면 만료된 항목의 참조가 실제로 끊긴다.
                                                       // 참조가 끊겨야 비로소 GC의 회수 대상이 된다(1-2).
            .build();

    public Product get(Long id) {
        return cache.get(id, this::loadFromDb);
    }
}
```

after가 나은 이유를 "메모리를 덜 쓴다"로 정리하면 절반만 맞다. 진짜 차이는 **점유량의 상한이 예측 가능해졌다**는 것이다. 상한이 있으면 Old에 상주할 양을 힙 크기 대비 몇 %로 계획할 수 있고, 그래야 Full GC 주기를 설계할 수 있다.

캐시 크기를 정하는 일이 곧 **"Old에 상주시킬 메모리를 얼마로 허락할 것인가"**라는 GC 설계 결정임을 아는 사람과, 그냥 Map에 쌓는 사람의 차이가 여기서 갈린다.

### 3-3. GC 로그를 읽는 첫 기준

**Minor GC가 잦은 것 자체는 문제가 아니다.** 각각이 짧고(수 ms~수십 ms) 회수량이 크면 건강한 상태다. 오히려 "Minor GC가 많네요, 줄여야겠어요"라며 Young을 무작정 키우면, 한 번의 Minor GC가 훑을 양이 늘어 개별 pause가 길어질 수 있다.

경계해야 할 신호는 셋이다.

**① Minor GC 후 Survivor 넘침과 조기 승격의 흔적.** GC 로그에서 Minor GC 직후 Old 사용량이 눈에 띄게 뛰었다면 승격이 일어난 것이다. 매 회차마다 이런 패턴이면 3-1의 사슬이 돌고 있다.

**② Full GC 빈도 증가.** Full GC는 드물어야 정상이다. 빈도가 오르는 추세라면 Old가 차는 속도가 빨라졌다는 뜻이다.

**③ Full GC 후에도 Old 사용량의 바닥이 계속 올라가는 패턴.** 이것이 가장 명확한 누수 신호다. 가장 비싼 수집을 다 하고도 안 치워지는 잔량이 회차마다 늘고 있다면, 참조가 끊기지 않는 코드가 있다는 뜻이다. ①·②는 튜닝으로도 완화되지만 ③은 코드를 고치기 전에는 절대 안 잡힌다.

## 4. 꼬리질문 대비 포인트

### "GC 루트에는 구체적으로 뭐가 있나요?"

스레드 스택의 지역변수·파라미터가 쥔 참조, static 필드, JNI 전역/지역 참조, 살아있는 스레드 객체 등이다.

목록을 외우기보다 **공통 성질**로 답하는 편이 낫다. **"힙 바깥에서 힙 안을 가리키는, 프로그램이 지금 확실히 붙잡고 있는 출발점"**이라는 것이다. 실행 중인 코드가 손에 쥐고 있거나(스택), 클래스가 로딩된 동안 영구히 쥐고 있는(static) 것들이 여기 해당한다.

그래서 **static 컬렉션에 쌓기만 하는 코드가 누수의 단골**이 된다. 루트에 직접 매달려 있으므로 아무리 GC를 돌려도 닿지 않을 방법이 없다. 같은 이유로 `ThreadLocal`에 담아 두고 `remove()`를 안 하는 코드도 위험하다 — 스레드 객체가 살아있는 동안 루트에서 닿기 때문인데, 스레드풀에서는 스레드가 재사용되며 사실상 영구히 산다.

### "Survivor 영역은 왜 하나가 아니라 2개인가요?"

**복사 방식을 쓰기 때문이다.** 복사해 넣을 빈 공간이 반드시 하나 있어야 한다.

항상 한쪽을 완전히 비워 두고, Minor GC 때 Eden + 사용 중 Survivor의 생존자를 빈 쪽으로 몰아 복사한 뒤 역할을 바꾼다. 이렇게 하면 생존자가 항상 연속된 공간에 몰려 **단편화가 원천적으로 없고**, sweep 없이 원본 영역을 통째로 비울 수 있다.

하나뿐이면 그 안에서 생존자를 골라내며 빈틈을 관리해야 해서 복사 방식의 이점이 전부 사라진다. **Survivor 하나만큼의 공간을 늘 놀리는 것이 이 알고리즘의 비용**이라는 점까지 말하면 트레이드오프를 보는 답이 된다.

### "Minor GC도 Stop-The-World인가요?"

**그렇다.** 다만 2-4에서 계산한 대로 생존 객체 수에 비례하는 복사 작업이라 대개 매우 짧아 체감이 적을 뿐이다. "Minor는 STW 없음"은 흔한 오답이다.

Old를 다루는 수집도 컬렉터에 따라 상당 부분을 애플리케이션과 **동시(concurrent)**에 수행하지만(G1, ZGC 등), mark의 시작·종료 지점처럼 그래프가 고정돼야 하는 구간의 STW는 여전히 남는다.

한 문장 덧붙이면 좋다. **컬렉터 진화의 역사가 곧 "STW를 얼마나 줄이느냐"의 역사다.** Serial → Parallel → CMS → G1 → ZGC의 흐름은 처리량을 올린 역사라기보다, 멈추는 시간을 짧게 그리고 **힙 크기와 무관하게 예측 가능하게** 만들어 온 역사다.

### "Old의 객체가 Young의 객체를 참조하고 있으면, Young만 수집하는 Minor GC는 그걸 어떻게 알죠?" (시니어 변별 포인트)

이 질문은 세대 분리의 구멍을 정확히 찌른다. 먼저 문제 상황을 그려 보자.

```java
// Old에 있는 장수 객체(캐시)가, 방금 Eden에 만들어진 객체를 참조한다
oldCache.put(key, new Product(...));   // Product는 Eden에 있고, 참조는 Old에서 온다
```

이때 Minor GC가 Young만 보고 판정하면, 이 Product는 "루트에서 닿지 않는다"고 오판돼 회수된다. 그러면 `oldCache`가 들고 있던 참조는 이미 없어진 객체를 가리키게 되고 프로그램이 깨진다.

그러니 Minor GC는 **"Old에서 Young으로 들어오는 참조"도 루트처럼 취급**해야 한다. 문제는 그걸 찾겠다고 Old 전체를 스캔하면 세대 분리의 의미가 통째로 사라진다는 것이다 — 싸게 하려고 나눴는데 매번 Old를 다 훑으면 남는 게 없다.

그래서 JVM은 **그런 참조가 생길 때마다 미리 기록해 둔다.** 이 기록을 일반적으로 **remembered set(기억 집합)**이라고 부른다. **"수집 대상 영역 바깥에서 안으로 들어오는 참조가 어디에 있는지를 기억해 두는 자료구조"**라는 뜻이다.

HotSpot의 전통적인 구현이 **카드 테이블(card table)**이다. Old를 작은 구획으로 나누고 — 이 구획 하나를 카드(card)라고 부른다 — 구획마다 1바이트짜리 표시 자리를 둔 배열이 카드 테이블이다. Old 객체의 참조 필드가 수정될 때마다 **쓰기 배리어(write barrier)**가 개입해 해당 카드를 "더러움(dirty)"으로 표시한다. 쓰기 배리어란 **참조 대입이 일어날 때마다 JVM이 몰래 끼워 넣는 짧은 코드**로, 문 앞을 지키는 장벽(barrier)처럼 모든 참조 쓰기를 통과시키며 기록을 남긴다는 뜻이다.

그러면 Minor GC는 Old 전체가 아니라 **dirty로 표시된 카드만** 훑으면 된다.

이 질문의 진짜 관전 포인트는 마지막 한 문장이다. **세대 분리는 공짜가 아니라 "모든 참조 대입마다 쓰기 배리어를 실행하는 상시 비용"을 치르고 산 최적화다.** 애플리케이션이 평소에 조금씩 대가를 내고, GC 때 크게 아끼는 거래다. 이 거래 구조를 말할 수 있으면 "GC 옵션을 아는 사람"이 아니라 "GC 설계를 아는 사람"으로 보인다.

### "Full GC가 자주 발생하면 코드에서 무엇부터 의심하겠습니까?"

Old가 빨리 차는 원인을 세 유형으로 나눠 보고, **유형을 먼저 가린 다음** 조치를 정한다.

**① 누수형** — static 컬렉션이나 무경계 캐시처럼 참조가 영원히 안 끊기는 코드다. 판별 기준은 **Full GC 후에도 Old 사용량의 바닥이 계속 상승하는가**다. 가장 비싼 수집을 하고도 안 줄어든다면 회수 불가능한 객체가 쌓이는 것이다. 힙 덤프를 떠서 무엇이 얼마나 붙잡고 있는지 확인한다.

**② 조기 승격형** — 요청 처리 중 대형 임시 객체(거대한 List, 대용량 응답 버퍼)를 만들거나 객체를 오래 쥐고 있어 Survivor가 넘치는 경우다(3-1). 판별 기준은 **Minor GC 직후 Old가 눈에 띄게 증가하는가**다. Full GC 후에는 Old가 잘 줄어든다는 점에서 ①과 구분된다.

**③ 설정형** — Young이 너무 작아 정상 부하에서도 승격이 과다한 경우다. 코드에 문제가 없는데 ②와 비슷한 증상이 나오면 이쪽을 본다.

**핵심은 순서다.** 세 유형은 조치가 완전히 다르다 — ①은 코드 수정, ②는 코드 수정 또는 Survivor 크기 조정, ③은 힙 영역 비율 조정이다. 그래서 GC 옵션을 먼저 만지는 것이 아니라 **GC 로그로 유형을 가리는 것이 먼저다.** 유형을 안 가리고 힙만 키우면 ①은 터지는 시점만 미뤄지고, 그동안 Full GC 한 번의 STW는 오히려 길어진다.

## 한 줄 요약

GC는 **GC 루트에서 참조를 따라가 닿지 않는 객체를 회수**하는 장치이고(그래서 순환 참조도 섬째로 회수된다), Young/Old 분리는 **"대부분 금방 죽는다"는 세대 가설에 기대 좁은 Young을 복사 방식으로 싸게 자주 치우고 비싼 전체 수집을 아끼는 전략**이다 — 그러므로 객체를 필요 이상 오래 쥐는 코드는 그 전제를 깨뜨려 조기 승격과 Full GC를 부르는, GC 관점에서 가장 비싼 코드다.
