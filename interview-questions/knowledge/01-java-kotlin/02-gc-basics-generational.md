# GC 동작 원리와 세대별 수집 — Young/Old를 나누는 이유

> 핵심 관전 포인트: **GC는 "GC 루트에서 참조를 따라가 닿을 수 있는가
> (reachability)"로 살릴 객체를 표시(mark)하고, 닿지 않는 객체를
> 회수한다. Young/Old를 나누는 이유는 세대 가설 —
> "대부분의 객체는 만들어지자마자 죽는다" — 때문이다.
> 전체 힙을 매번 뒤지는 대신, 객체가 태어나는 좁은 Young만 자주·싸게
> 수집(Minor GC)하고 오래 살아남은 소수만 Old로 승격시키면,
> 비싼 전체 수집(Full GC)의 빈도를 극적으로 줄일 수 있다.**

---

## 0. 질문 + 의도

**질문**: "GC가 동작하는 원리를 설명해주세요. Young/Old 영역은 왜
나뉘어 있나요?"

**출제 의도**: GC 로그와 pause 그래프를 읽는 능력의 기초. "왜 트래픽
피크마다 응답이 200ms 튀는가"의 범인이 GC인지 아닌지를 가려내려면
세대별 수집의 동작을 알아야 한다. 또한 "객체를 오래 들고 있는 코드가
왜 비싼지"를 체감하는 사람만 캐시 크기 같은 결정을 제대로 한다.

## 1. GC의 기본 원리 — 도달 가능성(reachability)

GC의 질문은 하나다: **"이 객체에 아직 닿을 수 있는가?"**

출발점이 되는 **GC 루트(GC Root)**에서 참조를 따라가며 닿는 객체를
전부 "살아있음"으로 표시(mark)하고, 표시되지 않은 객체를 회수한다.
GC 루트의 대표는:

- 각 스레드 **스택의 지역변수·파라미터**가 쥔 참조
- **static 필드**가 쥔 참조
- JNI(네이티브 코드)가 쥔 참조, 실행 중인 스레드 객체 자체

```java
void handle() {
    Order order = new Order();   // 스택의 order가 루트에서 닿는 경로 → 살아있음
}                                // 리턴 → 경로 끊김 → 다음 GC의 회수 후보
```

즉 `order = null`을 굳이 대입하지 않아도, **루트에서 닿는 경로가
끊기는 순간** 회수 후보가 된다. 반대로 static 컬렉션에 넣어두면
루트에서 영원히 닿으므로 절대 회수되지 않는다 — 이게 Java 메모리
누수의 전형이다.

### 왜 참조 카운팅이 아닌가 (가산점 포인트)

"참조 수를 세다가 0이 되면 회수"하는 참조 카운팅은 **서로가 서로를
참조하는 순환 구조**를 영원히 회수하지 못한다 (A→B, B→A면 둘 다
카운트 1). 도달 가능성 방식은 루트에서 출발하므로, 순환끼리 고립돼
있어도 루트에서 안 닿으면 통째로 회수한다. JVM이 이 방식을 쓰는
핵심 이유다.

### 회수의 3가지 기본 동작

- **Mark**: 루트에서 참조 그래프를 순회하며 생존 객체 표시
- **Sweep**: 표시 안 된 객체의 공간 회수 → 빈틈(단편화)이 남는 문제
- **Compact**(또는 Copy): 생존 객체를 한쪽으로 몰아 단편화 제거

그리고 이 작업의 상당 부분은 객체 그래프가 변하면 안 되므로
**애플리케이션 스레드를 멈추고(Stop-The-World, STW)** 수행한다.
"GC = 응답시간 스파이크"라는 등식이 성립하는 이유가 이 STW다.

## 2. Young/Old를 나누는 이유 — 세대 가설

### 관찰: 대부분의 객체는 요절한다

**약한 세대 가설(weak generational hypothesis)**: 대부분의 객체는
생성 직후 금방 죽고, 오래 살아남은 객체는 계속 오래 산다.

웹 서버로 생각하면 자명하다 — 요청 하나를 처리하며 만드는 DTO,
임시 문자열, 컬렉션은 **응답을 보내는 순간 전부 쓰레기**가 된다.
반면 커넥션 풀, 스프링 빈, 캐시는 프로세스가 사는 내내 산다.
중간 수명의 객체는 상대적으로 드물다.

### 그래서: 죽을 놈들만 모아둔 좁은 영역을 자주 수집한다

전체 힙을 매번 mark하면 힙이 클수록 STW가 길어진다. 대신:

- **Young(Eden + Survivor 2개)**: 새 객체는 전부 Eden에 생성.
  Eden이 차면 **Minor GC** — Young만 수집한다.
- **Old**: Minor GC를 여러 번 살아남은(나이가 임계치를 넘은) 객체만
  **승격(promotion)**되어 넘어온다.
- Old까지 포함해 수집하는 것이 Major/**Full GC**이며, 훨씬 비싸다.

### Minor GC가 싼 진짜 이유 — 복사 방식 (가산점 포인트)

Minor GC는 sweep이 아니라 **살아있는 객체만 Survivor로 복사**하고
Eden을 통째로 비우는 복사(copying) 방식이다. 비용이 **생존 객체
수에만 비례**하고, 죽은 객체는 그냥 버려지므로 **죽은 객체의 비용은
0**이다. "대부분 금방 죽는" Young에서는 생존자가 극소수 → 수집이
매우 싸다. 덤으로 복사하면서 자연히 한쪽으로 몰리므로 단편화도 없다.

Survivor가 2개(S0/S1)인 것도 이 복사 방식 때문이다 — 한쪽을 비워둔
채 Eden+사용 중 Survivor의 생존자를 빈쪽으로 복사하고 역할을 교대한다.
객체는 이 왕복에서 살아남을 때마다 나이를 먹고, 임계치를 넘으면
Old로 승격된다.

### 정리: 분리가 만드는 이득

| 항목 | Young (Minor GC) | Old (Full/Major GC) |
|---|---|---|
| 수집 빈도 | 잦음 | 드묾 (드물어야 정상) |
| 비용 | 쌈 — 생존 객체 수에 비례 | 비쌈 — 영역 크고 mark-sweep-compact 계열 |
| 전제 | 대부분 죽어 있음 | 대부분 살아 있음 |

즉 분리는 **"싸게 자주 치울 수 있는 곳과 비싸서 아껴 치워야 하는
곳을 물리적으로 갈라놓은 것"**이고, 목표는 Full GC 빈도 최소화다.

## 3. 실무 맥락 — "객체를 오래 들고 있는 코드"가 비싼 이유

이 구조를 알면, 같은 메모리양이라도 **객체의 수명 패턴**이 GC 비용을
좌우한다는 게 보인다.

### 사례: 트래픽 피크마다 응답이 튀는 서비스

트래픽이 늘면 요청당 임시 객체 생성 속도가 올라가 Eden이 빨리 차고
Minor GC가 잦아진다. 여기까진 정상(Minor GC는 싸다). 문제는 요청
처리 중 객체를 **필요 이상으로 오래 들고 있으면** Minor GC 시점에
아직 살아있어 Survivor를 채우고, Survivor가 넘치면 나이가 어린데도
Old로 조기 승격(premature promotion)된다. Old가 임시 객체로 차오르면
결국 **Full GC** — 이때 수백 ms의 STW가 응답시간 그래프에 스파이크로
찍힌다. "피크마다 200ms 튀는" 그래프의 전형적 범인이다.

### before/after — 무경계 캐시가 Old를 채우는 코드

```java
// Before: 크기 제한 없는 static 캐시 — GC 루트에서 영원히 닿음
public class ProductCache {
    private static final Map<Long, Product> CACHE = new HashMap<>();

    public Product get(Long id) {
        return CACHE.computeIfAbsent(id, this::loadFromDb);
        // 문제: 한 번 들어온 객체는 절대 회수 불가 →
        // 전부 Old로 승격돼 Old를 잠식 → Full GC 빈발 → 최후엔 OOM
    }
}

// After: 크기 상한 + 퇴출 정책이 있는 캐시 (예: Caffeine)
public class ProductCache {
    private final Cache<Long, Product> cache = Caffeine.newBuilder()
            .maximumSize(10_000)                       // 상한 → Old 점유량 예측 가능
            .expireAfterWrite(Duration.ofMinutes(10))  // 수명 명시 → 참조가 끊겨 회수 가능
            .build();

    public Product get(Long id) {
        return cache.get(id, this::loadFromDb);
    }
}
```

캐시 크기를 정하는 일이 곧 **"Old에 상주시킬 메모리를 얼마로
허락할 것인가"**라는 GC 설계 결정임을 아는 사람과, 그냥 Map에 쌓는
사람의 차이가 여기서 갈린다.

### GC 로그를 읽는 첫 기준

- **Minor GC가 잦은 것 자체는 문제가 아니다** — 짧고(수~수십 ms)
  회수량이 크면 건강한 상태다.
- 경계할 신호: ① Minor GC 후 **Survivor 넘침/조기 승격** 흔적,
  ② **Full GC 빈도 증가**, ③ Full GC 후에도 Old 사용량 바닥이
  계속 올라가는 패턴(누수).

## 4. 꼬리질문 대비 포인트

### "GC 루트에는 구체적으로 뭐가 있나요?"

스레드 스택의 지역변수·파라미터가 쥔 참조, static 필드, JNI 전역/지역
참조, 살아있는 스레드 객체 등. 핵심은 "실행 중인 코드가 직접 쥐고
있거나(스택), 클래스가 영구히 쥐고 있는(static) 출발점"이라는 것.
그래서 static 컬렉션에 쌓기만 하는 코드가 누수의 단골이 된다.

### "Survivor 영역은 왜 하나가 아니라 2개인가요?"

복사 방식 때문이다. 항상 한쪽을 완전히 비워두고, Minor GC 때
Eden + 사용 중 Survivor의 생존자를 빈 쪽으로 몰아 복사한 뒤 역할을
바꾼다. 이렇게 하면 생존자가 항상 연속된 공간에 몰려 **단편화가
원천적으로 없고**, sweep 없이 원본 영역을 통째로 비울 수 있다.
하나뿐이면 그 안에서 생존자를 골라내며 빈틈을 관리해야 해서 복사
방식의 이점이 사라진다.

### "Minor GC도 Stop-The-World인가요?"

그렇다. 다만 생존 객체 수에 비례하는 복사 작업이라 대개 매우 짧아
체감이 적을 뿐이다. "Minor는 STW 없음"은 흔한 오답. Old를 다루는
수집도 컬렉터에 따라 상당 부분을 동시(concurrent) 수행하지만
(G1, ZGC 등), mark 시작·종료 등 일부 구간의 STW는 여전히 있다 —
컬렉터 진화의 역사가 곧 "STW를 얼마나 줄이느냐"의 역사다.

### "Old의 객체가 Young의 객체를 참조하고 있으면, Young만 수집하는 Minor GC는 그걸 어떻게 알죠?" (시니어 변별 포인트)

Minor GC가 정말 Young만 보려면 "Old에서 Young으로 들어오는 참조"도
루트처럼 취급해야 하는데, 그렇다고 Old 전체를 스캔하면 분리의 의미가
없다. 그래서 JVM은 **카드 테이블(card table)**을 둔다 — Old를 작은
구획(카드)으로 나누고, Old 객체의 참조 필드가 수정될 때마다 쓰기 배리어
(write barrier)가 해당 카드를 "더러움(dirty)"으로 표시한다. Minor GC는
dirty 카드만 훑으면 된다. 이 질문은 "세대 분리가 공짜가 아니라
쓰기 배리어라는 상시 비용을 치르고 산 최적화"임을 아는지를 가른다.

### "Full GC가 자주 발생하면 코드에서 무엇부터 의심하겠습니까?"

Old가 빨리 차는 원인을 순서대로 본다. ① **누수형**: static
컬렉션·무경계 캐시처럼 참조가 영원히 안 끊기는 코드 (Full GC 후에도
Old 바닥이 상승하면 이쪽 — 힙 덤프로 확인). ② **조기 승격형**:
요청 처리 중 대형 임시 객체(거대 List, 대용량 응답 버퍼)를 만들거나
객체를 오래 쥐고 있어 Survivor가 넘치는 경우. ③ **설정형**: Young이
너무 작아 정상 부하에서도 승격이 과다한 경우. 원인 유형에 따라
조치(코드 수정 vs 힙/영역 크기 조정)가 완전히 달라지므로, 튜닝 옵션을
먼저 만지는 게 아니라 GC 로그로 유형을 가리는 게 먼저다.

---

## 한 줄 요약

GC는 **루트에서 닿지 않는 객체를 회수**하는 장치이고, Young/Old 분리는
**"대부분 금방 죽는다"는 세대 가설에 기대 좁은 Young만 싸게 자주 치우고
비싼 전체 수집을 아끼는 전략**이다 — 그래서 객체를 필요 이상 오래 쥐는
코드는 이 전략의 전제를 깨뜨리는, GC 관점에서 가장 비싼 코드다.
