# ConcurrentHashMap 내부 메커니즘 — 버킷 단위 락 + CAS, 무락 읽기

> 핵심 관전 포인트: **동시성 자료구조의 설계는 결국 "락의 범위를 얼마나 좁히고, 어디까지 락 없이 처리하느냐"의 문제다. `Collections.synchronizedMap`은 맵 전체에 락 하나를 걸어 동시에 한 스레드만 들여보내지만, `ConcurrentHashMap`은 쓰기를 "빈 버킷이면 CAS, 노드가 이미 있으면 그 버킷의 첫 노드에 `synchronized`"로 나눠 락의 범위를 버킷 1개까지 좁혔고, 읽기는 `volatile`이 만드는 가시성 보장에 기대어 락을 아예 없앴다. 그 대가가 약한 일관성(weak consistency) — 순회는 진행 중인 변경을 볼 수도 안 볼 수도 있고 `size()`는 근사값이다. 그리고 맵이 thread-safe해도 "읽고 판단해서 쓰는" 복합 연산은 여전히 원자적이지 않다는 것이 이 질문의 본체다.**

---

## 0. 질문 + 의도

**질문**: "`ConcurrentHashMap`은 어떻게 thread-safe를 보장하나요? `Collections.synchronizedMap`과의 차이는?"

**출제 의도**: "thread-safe 컬렉션을 쓰면 안전하다"는 착각(복합 연산은 여전히 원자적이지 않음)을 갖고 있는지 검사한다. 이 착각은 부하가 걸려야만 드러나는 최악의 버그를 만들기에, 내부 락 구조까지 정확한 동작 모델을 갖고 있는지를 본다.

## 1. 전제와 구조 — 락을 왜, 어디까지 좁히려 하는가

### 1-1. 전제 지식 — 왜 락을 피하고 싶은가

`ConcurrentHashMap`의 설계를 이해하려면 먼저 **락이 정확히 무엇을 비싸게 만드는지**를 알아야 한다. 여기를 건너뛰면 뒤에 나오는 CAS가 "그냥 뭔가 빠른 것" 정도로만 남는다.

`synchronized`는 한 번에 한 스레드만 들여보내는 문이다. 문이 비어 있을 때 들어가는 비용 자체는 크지 않다. 문제는 **문이 닫혀 있을 때** 생긴다. 이미 다른 스레드가 안에 있으면, 뒤에 온 스레드는 CPU를 계속 붙잡고 기다리는 게 아니라 **커널에 의해 대기 상태로 내려간다.** 잠드는 것이다.

이때 일어나는 일을 순서대로 보면 비용이 어디서 나오는지 보인다.

```
스레드 B가 락을 못 잡았을 때
  1. B를 실행 대기 큐에서 빼고 대기 큐로 옮긴다        (커널 진입)
  2. B가 쓰던 레지스터·스택 포인터를 저장한다           (컨텍스트 저장)
  3. CPU 코어에 다른 스레드 C를 올려 실행한다
     -> 이 순간 코어의 캐시에 남아 있던 B의 데이터는 C의 데이터로 밀려난다
  4. A가 락을 놓으면 커널이 B를 깨워 실행 대기 큐로 되돌린다
  5. B가 다시 코어에 올라간다 -> 캐시가 비어 있어 메모리에서 다시 읽어온다
```

이 왕복 한 번을 **컨텍스트 스위칭(context switching)**이라 부른다. 스레드를 갈아 끼우느라 드는 비용인데, 눈에 보이는 저장·복원 비용보다 **캐시가 식는 비용**이 더 크다는 것이 실무의 감각이다.

여기서 문제의식이 나온다. `map.put(key, value)` 한 번이 실제로 하는 일은 "배열 칸 하나에 노드를 꽂는" 몇 나노초짜리 작업이다. **그 짧은 갱신 하나를 지키자고 스레드를 재우고 깨우는 것은 배보다 배꼽이 크다.** 그래서 나온 발상이 "락 없이, 잠들지 않고, 실패하면 그냥 다시 해보자"다. 그 도구가 CAS다.

### 1-2. CAS — 예상값이 맞을 때만 바꾸는 원자 연산

**CAS(Compare-And-Swap, 비교 후 교체)는 "이 메모리 위치의 값이 내가 예상한 값과 같으면 새 값으로 바꿔라. 다르면 아무것도 하지 마라"를 CPU가 단 하나의 명령으로 처리해 주는 원자 연산이다.** x86의 `CMPXCHG` 같은 하드웨어 명령이 실체이고, 자바에서는 `Atomic*` 클래스나 `VarHandle`을 통해 쓴다.

"원자(atomic)"라는 말은 **더 쪼갤 수 없다**는 뜻이다. 비교와 교체 사이에 다른 스레드가 끼어들 틈이 없다는 것이 핵심이며, 그 틈 없음을 소프트웨어가 아니라 CPU가 보장한다.

```
CAS(메모리 위치 V, 예상값 A, 새 값 B)
  -> V의 현재 값이 A와 같으면   : B로 교체하고 true 반환
  -> V의 현재 값이 A와 다르면   : 아무것도 안 하고 false 반환
                                  (다르다 = 그 사이 누군가 이미 바꿨다)
```

비유하면 **화이트보드에 적힌 숫자를 고치는 상황**이다. 락 방식은 화이트보드 앞에 줄을 서서 한 명씩 들어가는 것이고, CAS 방식은 줄을 서지 않고 그냥 다가가되 "내가 아까 본 값이 아직 그대로면 고치고, 누가 이미 바꿔놨으면 손대지 않고 물러나서 다시 본다"는 규칙으로 움직이는 것이다. 아무도 없을 때는 CAS가 압도적으로 빠르고, 사람이 몰리면 물러났다 다시 오기를 반복하게 된다.

`count++`가 왜 CAS를 필요로 하는지 보면 쓰임새가 분명해진다. `count++`는 한 줄이지만 실제로는 "현재 값 읽기 → +1 계산 → 결과 쓰기" 세 단계이고, 두 스레드가 같은 값을 읽어버리면 증가 한 번이 사라진다. 락으로 감싸면 해결되지만 위에서 본 블로킹 비용을 매번 치른다. CAS는 이렇게 푼다.

```java
// AtomicInteger.incrementAndGet()의 동작 원리 (개념 코드)
int current, next;
do {
    current = value;              // 1. 현재 값을 읽는다
    next = current + 1;           // 2. 새 값을 계산한다
} while (!compareAndSet(current, next));
// 3. "아직 current 그대로면 next로 바꿔라"를 시도한다.
//    false = 그 사이 다른 스레드가 값을 바꿨다는 뜻이므로
//    잠들지 않고 곧바로 루프를 돌아 다시 읽고 다시 시도한다.
```

여기서 나오는 성질이 셋이다.

**실패해도 스레드가 잠들지 않는다.** 그래서 이 방식을 **논블로킹(non-blocking) 또는 락 프리(lock-free)**라 부른다. 컨텍스트 스위칭이 없다는 것이 락 대비 이득의 실체다.

**경합이 적으면 락보다 훨씬 싸고, 경합이 극심하면 오히려 손해다.** 재시도 루프가 계속 헛돌면서 CPU만 태우기 때문이다. "CAS가 락보다 항상 빠르다"는 명제는 틀렸고, 이것을 아는 것이 뒤에 나올 `ConcurrentHashMap`의 설계(빈 버킷은 CAS, 충돌하면 락)를 이해하는 열쇠다.

**`AtomicInteger`, `AtomicReference`, `LongAdder`가 전부 이 위에 서 있다.** 내부적으로 `Unsafe`나 `VarHandle`의 compareAndSet 계열을 호출한다.

CAS에는 알려진 함정이 하나 있다. **ABA 문제**다. 값이 A였다가 B로 바뀌었다가 다시 A로 돌아오면, CAS는 "예상값 A와 현재 값 A가 같으니 아무 일도 없었다"고 판단한다. 실제로는 두 번의 변경이 있었는데도 말이다.

단순 카운터나 참조 교체에서는 대개 문제가 되지 않는다. 값이 같으면 결과도 같기 때문이다. 그러나 "그 사이에 아무 일도 없었어야" 정확한 로직(예: 락 프리 스택에서 팝한 노드를 재활용하는 경우)이라면 깨진다. 해결은 **값에 버전 스탬프를 붙여 함께 비교**하는 것이고, `AtomicStampedReference`가 그 용도다. 값이 A로 돌아와도 스탬프는 되돌아오지 않으므로 변경을 감지할 수 있다.

### 1-3. 비교 대상 — `Collections.synchronizedMap`은 무엇을 하는가

질문이 짝지어 물어보는 `Collections.synchronizedMap(new HashMap<>())`은 구조가 훨씬 단순하다. **평범한 `HashMap`을 감싸는 래퍼(wrapper)를 만들고, 모든 메서드를 `synchronized` 블록으로 덮은 것**이다.

```java
// Collections.SynchronizedMap의 실제 구조 (요지)
public V get(Object key) {
    synchronized (mutex) { return m.get(key); }   // mutex = 맵 하나당 락 객체 하나
}
public V put(K key, V value) {
    synchronized (mutex) { return m.put(key, value); }
}
```

여기서 놓치면 안 되는 지점은 `mutex`가 **맵 전체에 단 하나**라는 것이다. 서로 아무 관련 없는 키 두 개를 서로 다른 스레드가 건드려도, 심지어 둘 다 읽기만 해도 같은 락을 다툰다. 코어를 아무리 늘려도 이 맵을 통과하는 처리량은 늘지 않는다. 이런 구조를 **직렬화된 접근**이라 부른다.

`ConcurrentHashMap`이 하는 일을 한 문장으로 요약하면 **"이 하나뿐인 락을 잘게 쪼개고, 읽기는 그 대열에서 아예 빼낸 것"**이다.

### 1-4. Java 7의 세그먼트 락에서 Java 8의 버킷 락으로

`ConcurrentHashMap`의 내부는 `HashMap`과 마찬가지로 `Node<K,V>[] table` 배열 하나다. 배열의 각 칸을 **버킷(bucket)**이라 부르고, 해시가 같은 칸에 걸린 키들은 그 칸에서 연결 리스트로 이어진다. 여기까지는 `HashMap`과 같다. 다른 것은 **그 위에 락을 어떻게 얹느냐**뿐이다.

Java 7까지의 답은 **락 스트라이핑(lock striping)**이었다. 스트라이프(stripe)는 줄무늬라는 뜻으로, 테이블을 여러 구획으로 나누고 각 구획에 별도의 락을 두는 기법을 말한다. 구획 하나를 `Segment`라 불렀고 기본 개수는 16이었다.

Java 8은 세그먼트라는 중간 계층을 없애고, **버킷의 첫 노드(head node) 객체 자체를 락으로 쓰는** 방식으로 바꿨다. 별도의 락 객체를 만들 필요 없이 이미 거기 있는 노드에 `synchronized`를 걸면 되므로 메모리도 덜 쓰고 락 단위도 최소가 된다.

두 방식의 락 범위를 그림으로 대조하면 차이가 한눈에 들어온다.

```
[Java 7까지 — 세그먼트 락 (lock striping), 기본 16구획]

   Segment 0            Segment 1                  Segment 15
  +-----------------+  +-----------------+        +-----------------+
  |  락 객체 1개    |  |  락 객체 1개    |  ...   |  락 객체 1개    |
  |  버킷 0,1,2,3   |  |  버킷 4,5,6,7   |        |  버킷 60..63    |
  +-----------------+  +-----------------+        +-----------------+
        ^
        +-- 버킷 0에 쓰든 버킷 3에 쓰든 같은 락을 다툰다
            동시에 쓸 수 있는 스레드 수 = 세그먼트 수 (기본 16)

[Java 8부터 — 버킷 단위 락]

   table[0]     table[1]     table[2]     table[3]
  +--------+   +--------+   +--------+   +--------+
  |  null  |   |  head  |   |  head  |   |  null  |
  +--------+   +---+----+   +---+----+   +--------+
       ^           |            |             ^
       |           v            v             |
    CAS로       이 노드가     이 노드가     CAS로
    락 없이      곧 락        곧 락         락 없이
    삽입         (버킷 1 전용) (버킷 2 전용)  삽입

            동시에 쓸 수 있는 스레드 수 = 이론상 버킷 수만큼
```

| | Java 7까지 | Java 8부터 |
|---|---|---|
| 락 구조 | `Segment` 배열 (기본 16개, 락 스트라이핑) | Segment 제거, 버킷의 head 노드 자체가 락 |
| 락 단위 | 테이블의 1/16 | 버킷 1개 |
| 동시 쓰기 상한 | 세그먼트 수 (기본 16) | 이론상 버킷 수 |

한 버킷의 연결 리스트가 길어지면 레드-블랙 트리(`TreeBin`)로 바꿔 최악의 탐색 성능을 O(n)에서 O(log n)으로 방어하는 것도 `HashMap`과 같다. 기준도 같아서, 한 버킷의 노드 수가 8에 이르렀을 때 트리화를 시도하되 **테이블 길이가 64 미만이면 트리로 바꾸는 대신 테이블을 2배로 늘린다.** 테이블이 작아서 생긴 충돌은 트리화가 아니라 확장으로 푸는 것이 맞기 때문이다. 트리로 바뀐 버킷에서는 락이 `TreeBin` 노드에 걸린다.

(가산점 포인트) Java 8 이후에도 소스 코드에는 `Segment` 클래스가 껍데기로 남아 있다. 동작에는 쓰이지 않고, 예전 버전에서 직렬화한 맵을 읽을 수 있게 하는 호환용이다. "Segment가 아직 있던데요"라는 반문이 나오면 이렇게 답하면 된다.

## 2. 동작 — 쓰기는 좁은 락, 읽기는 무락

### 2-1. 쓰기 ① 빈 버킷이면 CAS로 끝낸다 (락 없음)

`putVal()`은 버킷의 상태를 먼저 보고 두 전략 중 하나를 고른다. 첫 번째는 그 칸이 비어 있는 경우다.

```java
if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
    // 그 슬롯이 "여전히 null이면" 새 노드를 꽂는다 — 비교와 교체가 한 덩어리.
    // 락을 잡지 않으므로 컨텍스트 스위칭 비용이 0이다.
    if (casTabAt(tab, i, null, new Node<>(hash, key, value)))
        break;   // 성공. 여기서 put이 끝난다.
    // 실패했다면 그 찰나에 다른 스레드가 먼저 꽂았다는 뜻이므로
    // 루프를 다시 돌아 아래의 락 경로로 넘어간다.
}
```

"슬롯이 null인지 확인하고, null이면 노드를 꽂는다"는 두 동작을 따로 하면 그 사이에 다른 스레드가 끼어들 수 있다. CAS는 이 확인과 선점을 하나로 묶어 CPU가 원자적으로 처리하게 만든다. 이 구조 덕분에 **키가 골고루 흩어진 맵에서는 대부분의 put이 락을 한 번도 잡지 않는다.**

### 2-2. 쓰기 ② 노드가 이미 있으면 그 첫 노드에 synchronized

버킷이 비어 있지 않다면 체인을 순회하며 같은 키를 찾아 값을 덮어쓰거나 꼬리에 노드를 붙여야 한다. 이건 여러 단계를 거치는 작업이라 CAS 한 번으로는 안 된다. 이때만 락을 잡는다.

```java
synchronized (f) {            // f = 이 버킷의 첫 노드. 락의 범위가 곧 이 버킷 하나다.
    if (tabAt(tab, i) == f) { // 락을 얻기까지 기다리는 동안 head가 그대로였는지 재확인
        // 체인을 순회하며 같은 키면 덮어쓰고, 없으면 꼬리에 새 노드를 붙인다
    }
}
```

락의 대상이 맵도 아니고 세그먼트도 아니라 **그 버킷의 첫 노드 객체**라는 점이 핵심이다. 서로 다른 버킷을 건드리는 스레드들은 서로 다른 객체에 락을 걸므로 아무도 기다리지 않는다.

`tabAt(tab, i) == f`를 다시 확인하는 이유는 짚고 넘어갈 만하다. **락을 얻기 위해 기다리는 동안에도 맵은 계속 변한다.** 그 사이 리사이즈가 일어나 이 슬롯이 다른 노드로 교체됐거나, 트리화로 head가 `TreeBin`으로 바뀌었을 수 있다. 그렇게 되면 내가 잡은 락은 **이미 버려진 옛 노드에 걸린 무효한 락**이다. 그 상태로 체인을 수정하면 아무도 안 보는 자료구조를 고치는 셈이 된다. 그래서 락을 잡은 직후 "내가 락을 건 그 노드가 아직 이 슬롯의 head가 맞나"를 확인하고, 아니면 락을 풀고 처음부터 다시 시도한다.

### 2-3. 읽기 — get에 락이 전혀 없는 이유

```java
public V get(Object key) {
    // synchronized도 없고, CAS 재시도 루프도 없다. 그냥 읽는다.
    Node<K,V> e = tabAt(tab, (n - 1) & h);
    // ... 체인/트리를 따라가며 키를 비교하고 값을 반환
}
```

락을 안 잡는데 어떻게 안전한가. 근거는 **가시성(visibility)을 락 대신 `volatile`로 확보했다**는 데 있다.

여기서 가시성이란 **한 스레드가 메모리에 쓴 값을 다른 스레드가 볼 수 있는가**의 문제다. CPU 코어마다 자기 캐시를 갖고 있고 컴파일러도 값을 레지스터에 눌러 담아두는 최적화를 하기 때문에, 아무 표시 없는 일반 필드는 한 스레드가 바꾼 값이 다른 스레드에게 **언제 보일지, 심지어 보이기는 할지** 보장되지 않는다. 락이 이 문제도 함께 해결해 주기 때문에 흔히 "동기화 = 락"으로 뭉뚱그리지만, 사실 락은 **상호배제(한 번에 하나만)와 가시성**이라는 두 가지 일을 동시에 하는 도구다.

`ConcurrentHashMap`은 이 둘을 분리했다. **가시성만 필요한 읽기 경로에는 `volatile`을, 상호배제까지 필요한 쓰기 경로에만 락을** 쓴다.

| 필드 | 선언 | 그 선언이 하는 일 |
|---|---|---|
| `Node.val`, `Node.next` | `volatile` | 쓰기 스레드의 갱신이 읽기 스레드에 반드시 보인다 |
| `table` | `volatile` + 슬롯 접근은 `tabAt()` | 새 테이블·새 노드의 발행이 읽기 스레드에 보인다 |
| `Node.key`, `Node.hash` | `final` | 생성 후 절대 안 바뀜 — 안전 발행(safe publication)이 보장된다 |

`table` 줄에 설명이 하나 필요하다. **자바에서는 배열의 원소 하나하나에 `volatile`을 붙일 수 없다.** `volatile Node[] table`은 "table이라는 참조 변수"가 volatile일 뿐, `table[3]`을 읽는 것까지 volatile 읽기가 되지는 않는다. 그래서 `ConcurrentHashMap`은 슬롯을 직접 읽지 않고 `tabAt(tab, i)`라는 헬퍼를 통해 읽는다. 이 헬퍼가 저수준 API를 써서 **원소 하나에 대한 volatile 읽기에 준하는 접근**을 수행한다. 슬롯에 값을 꽂을 때 쓰는 `casTabAt`, `setTabAt`도 같은 계열이다.

`key`와 `hash`가 `final`인 것도 우연이 아니다. **`final` 필드는 생성자가 끝나는 시점에 다른 스레드에게도 완성된 값으로 보인다는 특별한 보장**을 JMM으로부터 받는다. 그래서 다른 스레드가 갓 만들어진 노드를 발견하더라도 "참조는 보이는데 key는 아직 null인" 반쪽짜리 상태를 볼 수 없다.

결론적으로 읽기 스레드가 하는 일은 **어느 시점엔가 실제로 유효했던 노드들을 따라가는 것**뿐이고, 쓰는 쪽과 다툴 것이 없다. 그래서 get은 쓰기 경합이 아무리 심해도 절대 블로킹되지 않는다.

### 2-4. size 집계 — 카운터를 일부러 쪼갠다 (CounterCell)

원소 개수를 세는 방법으로 가장 단순한 것은 `int count` 필드 하나를 두고 put·remove마다 갱신하는 것이다. 그런데 이 맵에서는 그게 곧바로 병목이 된다.

이유는 1-2에서 본 CAS의 성질에 있다. 모든 스레드가 **같은 하나의 필드**를 CAS로 갱신하면, 버킷을 아무리 잘게 쪼개 놓았어도 결국 전원이 이 필드 하나 앞에서 재시도 경쟁을 벌인다. 버킷 락을 없앤 자리에 카운터라는 새 병목을 세우는 꼴이다.

그래서 `ConcurrentHashMap`은 **`LongAdder`와 같은 원리로 카운터 자체를 쪼갠다.** `baseCount` 하나에 `CounterCell[]` 배열을 더해 두고, 경합이 감지되면 스레드마다 서로 다른 셀에 더하게 분산시킨다. 서로 다른 셀을 건드리면 CAS가 충돌하지 않으므로 재시도가 사라진다.

```
경합이 없을 때 : baseCount 하나에 CAS로 누적
경합이 생기면  : CounterCell[0], CounterCell[1], ... 로 흩어서 누적

size() 호출    : baseCount + 모든 CounterCell 값을 순회하며 합산
```

여기서 자연스럽게 따라오는 결론이 있다. **합산하는 동안에도 다른 스레드는 계속 put·remove를 한다.** 그래서 `size()`가 돌려주는 값은 어떤 순간의 정확한 스냅샷이 아니라 근사값이다. 이것은 다음 절의 약한 일관성과 한 몸이다.

(가산점 포인트) `size()`는 반환 타입이 `int`라 원소가 `Integer.MAX_VALUE`를 넘으면 표현할 수 없다. Java 8부터는 `long`을 반환하는 `mappingCount()`가 있고, 대용량 맵에서는 그쪽이 권장된다.

### 2-5. 협력적 리사이즈 — 기다리는 대신 함께 옮긴다 (helpTransfer)

맵이 커지면 테이블을 2배로 늘리고 모든 노드를 새 테이블로 옮겨야 한다. 이 이사 작업은 시간이 걸리는데, 그동안 다른 스레드를 전부 세워두면 그 순간만큼은 맵 전체에 락을 건 것과 다를 바 없어진다.

`ConcurrentHashMap`은 이 구간을 **협력 작업**으로 만들었다.

이사가 끝난 버킷 자리에는 `ForwardingNode`라는 표지판 노드를 꽂아둔다. 해시값이 `MOVED`라는 특수한 음수 값이라 일반 노드와 구별되고, 새 테이블을 가리키는 참조를 들고 있다.

- **put 하러 온 스레드가 `ForwardingNode`를 만나면** 리사이즈가 끝나기를 기다리지 않는다. `helpTransfer()`를 호출해 **아직 안 옮긴 버킷 구간을 자기 몫으로 받아 함께 이사를 진행한다.** 일손이 늘어나 리사이즈가 빨리 끝나고, 기다리는 스레드도 없어진다.
- **get 하러 온 스레드가 `ForwardingNode`를 만나면** 그 표지판을 따라 새 테이블로 넘어가 읽기를 계속한다. 리사이즈 중에도 읽기는 한 번도 멈추지 않는다.

```
[리사이즈 진행 중인 옛 테이블]
  table[0]  table[1]  table[2]  table[3]
  [FWD]     [FWD]     [head]    [head]
    |         |          ^         ^
    |         |          +---------+-- 아직 안 옮긴 구간
    +---------+-- 이미 옮김. get은 이 표지판을 따라 새 테이블로 간다.
                  put은 여기서 helpTransfer()로 이사에 합류한다.
```

## 3. 대가와 함정

### 3-1. 약한 일관성(weakly consistent) — 버그가 아니라 설계 선택

락 없는 읽기에는 대가가 따른다. `ConcurrentHashMap`의 읽기 계열 동작은 **약한 일관성(weakly consistent)**을 가진다. 구체적으로 셋이다.

**get은 "지금 이 순간"이 아니라 "어느 시점엔가 유효했던" 값을 반환할 수 있다.** get이 값을 반환하고 호출자에게 돌아가는 사이에 다른 스레드가 그 키를 지웠을 수 있다.

**iterator는 순회 중 일어난 변경을 볼 수도, 못 볼 수도 있다.** 그리고 `ConcurrentModificationException`을 던지지 않는다. `HashMap`의 반복자는 순회 중 맵이 수정되면 이 예외를 던지는데(fail-fast), `ConcurrentHashMap`은 그러지 않는다(fail-safe).

**size()는 근사값이다.** 2-4에서 본 대로 분산 카운터를 합산하는 방식이라 합산 도중에도 맵이 변한다.

이 셋을 "덜 만들어진 자료구조의 한계"로 이해하면 안 된다. **의도된 교환**이다. 왜 그런지 반대로 생각해 보면 분명해진다.

정확한 크기와 강한 일관성 순회를 보장하려면 **집계하거나 순회하는 동안 맵 전체의 변경을 막아야 한다.** 그 순간 `Collections.synchronizedMap`으로 되돌아간다. 무락 읽기라는 이 자료구조의 존재 이유를 `size()` 하나를 정확하게 만들자고 포기하는 셈이다.

게다가 **동시에 변하는 맵에서 "정확한 크기"라는 값은 애초에 의미가 희박하다.** 락을 걸고 정확히 1,000이라는 값을 얻어냈다 해도, 그 값이 호출자에게 반환되는 순간 이미 999거나 1,002다. 비싼 값을 치르고 얻은 정확함이 반환 즉시 과거가 된다.

`ConcurrentModificationException`을 안 던지는 것도 같은 논리다. 그 예외는 **"단일 스레드용 컬렉션인데 순회 중 수정이 일어났다 — 이건 버그다"**라는 신고다. 그런데 `ConcurrentHashMap`에서는 순회 중 다른 스레드가 수정하는 것이 **정상적이고 의도된 사용법**이다. 정상 동작에 예외를 던질 이유가 없다.

그래서 판단 기준은 이렇게 정리된다. **"정확한 스냅샷이 필요한가"를 먼저 묻는다.** 모니터링 지표, 대략적인 캐시 크기 로그처럼 근사값으로 충분한 곳에는 그대로 쓴다. "정확히 N개일 때만 처리를 시작한다" 같은 판단의 근거로 `size()`를 쓰고 있다면 그건 자료구조 선택이 잘못된 것이고, 별도의 동기화 장치나 다른 설계가 필요하다.

### 3-2. thread-safe 맵인데도 깨지는 것 — 복합 연산

이 문서에서 실무 사고와 가장 가까운 지점이다. **`ConcurrentHashMap`이 보장하는 것은 "메서드 하나하나가 원자적"이라는 것뿐이지, "내가 쓴 코드 블록이 원자적"이라는 것이 아니다.**

```java
// Before: 맵은 thread-safe인데 코드는 깨진다
ConcurrentHashMap<String, Integer> counter = new ConcurrentHashMap<>();

Integer c = counter.get(key);                     // ① 이 호출은 원자적이다
counter.put(key, (c == null ? 0 : c) + 1);        // ② 이 호출도 원자적이다
// 그런데 ①과 ② 사이는 아무도 지켜주지 않는다.
// 두 스레드가 나란히 ①에서 5를 읽으면 둘 다 6을 쓰고,
// 두 번 증가시켰는데 결과는 6이 된다 — 갱신 유실(lost update).
```

각 메서드가 원자적인 것과 **여러 메서드를 이어 붙인 흐름이 원자적인 것은 완전히 다른 문제**다. 이 패턴을 일반적으로 **검사 후 행동(check-then-act)** 또는 **읽고-고치고-쓰기(read-modify-write)**라 부른다.

`Collections.synchronizedMap`도 사정은 똑같다. 다만 그쪽은 락이 맵 하나에 하나뿐이라 `synchronized (map) { ... }`로 외부에서 같은 락을 잡아 묶는 우회가 가능하다. **`ConcurrentHashMap`에는 그 우회가 통하지 않는다.** 내부 락이 버킷 단위로 흩어져 있어서, 외부에서 맵 객체에 락을 걸어봐야 그 락을 존중하는 것은 나뿐이고 다른 스레드의 put은 그대로 통과한다.

해법은 우회가 아니라 **원자적으로 설계된 전용 메서드를 쓰는 것**이다.

```java
// After: 읽고-고치고-쓰기를 맵 내부의 한 번의 원자적 연산으로 넘긴다
counter.merge(key, 1, Integer::sum);
// "없으면 1로 넣고, 있으면 기존 값과 1을 sum으로 합쳐라"가 버킷 락 안에서 한 번에 일어난다

// 값이 없을 때만 무거운 초기화를 하고 싶다면
Session s = sessions.computeIfAbsent(id, k -> loadSession(k));
// "확인하고 없으면 만든다"가 원자적이라 loadSession이 중복 호출되지 않는다

// 단순히 "선점한 쪽만 넣기"라면
Object prev = registry.putIfAbsent(key, value);
if (prev != null) { /* 다른 스레드가 이미 등록함 */ }

// 조건부 교체·삭제도 원자적 버전이 있다
map.replace(key, oldValue, newValue);   // 값이 oldValue일 때만 교체
map.remove(key, expectedValue);         // 값이 expectedValue일 때만 삭제
```

(시니어 변별 포인트) `compute`, `computeIfAbsent`, `merge`에 넘기는 람다는 **해당 버킷의 락을 쥔 채로 실행된다.** 따라서 두 가지 금기가 따라온다. **오래 걸리는 작업(원격 호출, 파일 I/O)을 넣으면 그 버킷이 그동안 막힌다.** 그리고 **람다 안에서 같은 맵을 다시 수정하면 안 된다** — 이미 쥔 락과 얽혀 교착이나 무한 대기로 갈 수 있다. `computeIfAbsent`에 DB 조회를 그대로 넣은 코드는 실무에서 흔히 보이는데, 그것이 락 구간을 늘린다는 사실은 인지하고 써야 한다.

## 4. 꼬리질문 대비 포인트

### "`Collections.synchronizedMap`과 정확히 무엇이 다른가요?"

**락의 개수와 범위, 그리고 읽기의 처리 방식**이 다르다.

`synchronizedMap`은 평범한 `HashMap`을 감싸 모든 메서드를 하나의 락으로 덮은 래퍼다. 읽기든 쓰기든, 서로 무관한 키든, 이 맵을 지나는 모든 스레드가 락 하나를 다툰다. 코어를 늘려도 처리량이 늘지 않는다.

`ConcurrentHashMap`은 쓰기의 락 범위를 **버킷 1개**로 좁혔고(빈 버킷은 CAS로 락조차 잡지 않는다), 읽기는 `volatile`이 주는 가시성 보장에 기대어 **락 없이** 수행한다.

한 가지 덧붙일 것은 **둘 다 복합 연산의 원자성은 보장하지 않는다**는 점이다. 차이는 대응 방법에 있다. `synchronizedMap`은 `synchronized (map)`으로 외부에서 같은 락을 잡아 묶을 수 있지만, `ConcurrentHashMap`은 내부 락이 흩어져 있어 그 우회가 통하지 않으므로 `merge`·`compute`·`putIfAbsent` 같은 원자적 메서드를 써야 한다.

### "get이 락 없이도 안전한 근거를 설명해주세요."

**가시성을 락이 아니라 `volatile`로 확보했기 때문**이다.

락은 상호배제와 가시성 두 가지를 함께 제공하는 도구인데, 읽기에는 상호배제가 필요 없고 가시성만 필요하다. 그래서 `Node.val`과 `Node.next`를 `volatile`로 선언해 쓰기 스레드의 갱신이 읽기 스레드에 반드시 보이게 만들었다. `table` 슬롯 접근도 `tabAt()` 헬퍼를 통해 volatile 읽기에 준하는 방식으로 이루어진다 — 자바에서는 배열 원소 하나에 `volatile`을 붙일 수 없기 때문에 헬퍼가 필요하다.

여기에 `Node.key`와 `hash`가 `final`이라는 점이 더해진다. `final` 필드는 생성자가 끝나면 다른 스레드에게도 완성된 값으로 보인다는 보장이 있어서, 갓 만들어진 노드를 다른 스레드가 발견해도 반쪽짜리 상태를 볼 수 없다(안전 발행).

읽기 스레드는 어느 시점엔가 유효했던 노드를 따라가기만 하면 되므로 쓰기와 충돌할 일이 없고, 그래서 경합이 아무리 심해도 get은 블로킹되지 않는다.

### "CAS가 락보다 항상 빠른가요?" (시니어 변별 포인트)

**아니다.** 이 질문의 정답은 "경합의 정도에 따라 뒤집힌다"이다.

CAS는 실패해도 스레드를 재우지 않기 때문에 컨텍스트 스위칭 비용이 없다. 그래서 경합이 적으면 락보다 훨씬 싸다. 그런데 경합이 극심하면 재시도 루프가 계속 헛돌면서 CPU를 태우기만 한다. 이때는 차라리 잠들었다가 깨어나는 락이 낫다.

`ConcurrentHashMap`의 설계가 이 판단을 그대로 코드로 옮겨 놓았다. **빈 버킷은 경합이 거의 없을 자리이므로 CAS를 한 번 시도하고, 실패하거나 이미 노드가 있으면(= 경합이 있다는 신호) 곧바로 `synchronized`로 내려간다.** 둘 중 하나를 고르는 게 아니라 상황에 따라 섞어 쓴다는 것이 요점이다.

같은 이유로 `size()` 카운터도 CAS 하나로는 안 됐다. 모든 스레드가 같은 필드를 CAS하면 그 자체가 병목이라 `CounterCell[]`로 대상을 흩어야 했다.

### "`size()`가 근사값이고 순회 중 예외도 안 나는데, 이건 문제 아닌가요?"

**설계상의 의도된 교환**이다. 이유는 두 가지다.

첫째, 정확한 크기를 보장하려면 집계 동안 맵 전체의 변경을 막아야 하고, 그 순간 무락 읽기라는 이 자료구조의 존재 이유가 사라진다. `Collections.synchronizedMap`으로 되돌아가는 셈이다.

둘째, **동시에 변하는 맵에서 정확한 크기는 반환되는 순간 이미 과거다.** 비싼 락을 치르고 얻은 정확함이 즉시 무의미해진다.

`ConcurrentModificationException`을 안 던지는 것도 같은 맥락이다. 그 예외는 "단일 스레드용 컬렉션인데 순회 중 수정이 일어났다"는 버그 신고인데, `ConcurrentHashMap`에서는 순회 중 다른 스레드의 수정이 정상적인 사용법이다.

실무 기준은 이렇다. 모니터링 지표나 로그처럼 근사값으로 충분한 곳에는 그대로 쓴다. "정확히 N개일 때만 처리 시작" 같은 판단 근거로 `size()`를 쓰고 있다면 자료구조 선택이 잘못된 것이다. (가산점: 대용량 맵에서는 `int`를 넘길 수 있으므로 `long`을 반환하는 `mappingCount()`를 쓴다.)

### "리사이즈 중에는 다른 스레드가 멈추나요?"

**멈추지 않는다. 오히려 이사를 돕는다.**

이사가 끝난 버킷에는 `ForwardingNode`(해시값 `MOVED`)라는 표지판이 꽂힌다. put 하러 온 스레드가 이 표지판을 만나면 리사이즈가 끝나기를 기다리는 대신 `helpTransfer()`를 호출해 **아직 안 옮긴 버킷 구간을 나눠 받아 함께 옮긴다.** 일손이 늘어 리사이즈가 빨리 끝나고, 대기하는 스레드도 생기지 않는다.

get 하러 온 스레드는 표지판이 가리키는 새 테이블로 넘어가 읽기를 계속하므로 리사이즈 중에도 읽기는 한 번도 멈추지 않는다.

이것을 한 줄로 요약하면 **"긴 작업 구간을 락으로 보호하는 대신, 참여자 전원이 나눠 처리하도록 만들었다"**는 것이고, 이 설계 감각이 이 자료구조 전체를 관통한다.

---

## 한 줄 요약

`ConcurrentHashMap`은 쓰기를 "빈 버킷이면 CAS, 노드가 있으면 그 버킷의 첫 노드에 `synchronized`"로 나눠 락 범위를 버킷 1개까지 좁히고, 읽기는 `volatile`(`val`·`next`·`table`)과 `final`(`key`·`hash`)이 주는 가시성·안전 발행 보장에 기대어 락 없이 수행함으로써, 맵 전체에 락 하나를 거는 `Collections.synchronizedMap`과 처리량에서 갈린다 — 그 대가로 순회·`size()`는 약한 일관성을 갖지만 이는 무락 읽기를 지키기 위한 의도된 교환이고, 정작 실무에서 사고를 내는 것은 "thread-safe 맵이니 안전하다"고 믿고 get 후 put 하는 복합 연산이므로 그 자리에는 `merge`·`compute`·`putIfAbsent` 같은 원자적 메서드를 써야 한다.
