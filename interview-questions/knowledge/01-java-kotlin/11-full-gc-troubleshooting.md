# Full GC 빈발 원인 추적 — 찍지 말고, 순서대로 배제하라

> 핵심 관전 포인트: **Full GC 추적은 감이 아니라 배제의 순서다 — "최근 변경 확인 → GC 로그 확보 → **Full GC가 끝난 직후에도 Old 영역이 비었는지**로 유형 분기 → 유형별 가설 검증(누수 / 승격 폭주 / 명시적 호출 / Metaspace / 거대 객체) → 힙 덤프로 확정"의 다섯 단계로 좁혀 들어간다. 결정적 분기점은 하나다 — **청소를 다 하고도 Old가 안 비면 살아있는 객체가 너무 많다는 뜻(메모리 누수 또는 진짜 용량 부족)이고, 잘 비면 죽을 객체가 Old까지 밀려 올라오고 있다는 뜻(승격 폭주 또는 특이 원인)**이다. 그리고 튜닝은 원인 규명 뒤의 일이다 — **GC는 죽은 객체만 치울 수 있고 살아있는 객체는 어떤 옵션으로도 치우지 못하므로, "죽어야 할 객체가 안 죽는" 문제는 정의상 코드로만 풀린다.** 튜닝으로 덮으면 장애 시각만 뒤로 미뤄진다.**

---

## 0. 질문 + 의도

**질문**: "GC 튜닝 경험이 있나요? Full GC가 자주 발생할 때 어떤 순서로 원인을 추적하나요?"

**출제 의도**: 전형적인 "AI에 물어볼 수 없는" 상황 — 원인이 코드 어딘가에 있고, 로그·덤프·최근 배포 이력을 조합해 좁혀야 한다. 추적의 '순서'를 묻는 이유는 방법론 없이 찍는 사람과 체계적으로 배제해가는 사람을 구분하기 위해서다.

> GC 알고리즘 자체(G1/ZGC의 동작)는 `10-g1gc-vs-zgc.md`, 힙 덤프를 뜨고 읽는 법은 `23-jvm-heap-thread-dump.md` 참고. 이 문서는 그 사이 — **"어떤 순서로 좁혀 들어가는가"**만 다룬다.

## 1. 전제 — Full GC가 왜 '사건'인가

### 1-1. Young GC와 Full GC는 급이 다르다

먼저 용어를 정리하고 시작하자. 이 문서 전체가 이 구분 위에 서 있다.

JVM은 힙을 두 구역으로 나눠 관리한다. **Young**은 새로 만든 객체가 들어가는 곳이고, **Old**는 Young에서 여러 번 살아남은 객체가 옮겨 가는 곳이다. Young에서 살아남은 객체를 Old로 옮기는 것을 **승격(promotion)**이라고 부른다.

이렇게 나누는 근거는 **"대부분의 객체는 만들어지고 금방 죽는다"**는 관찰이다. 요청 하나를 처리하며 만든 DTO·문자열·임시 리스트는 응답을 내보내는 순간 전부 쓰레기가 된다. 그래서 Young 수거는 **살아남는 소수만 골라 옮기고 나머지 영역은 통째로 비우면** 끝난다. 작업량이 "죽은 객체 수"가 아니라 "살아남은 객체 수"에 비례하므로 빠르다.

**Young GC는 그래서 자주 일어나는 정상 동작이다.** 초당 몇 번씩 돌아도 이상하지 않다.

**Full GC는 다르다.** 힙 전체(Young + Old + 경우에 따라 Metaspace까지)를 대상으로 정리하는 최후 수단이다. 그래서 **"Full GC가 자주 일어난다"는 것 자체가 JVM이 보내는 조난 신호**다.

- G1에서 Full GC는 정상 경로가 아니라 **fallback(실패 시의 대비책)**이다. 동시 마킹이 할당 속도를 못 따라가거나, 살아남은 객체를 옮겨 넣을 빈 공간이 없을 때(GC 로그에 `to-space exhausted`, "옮겨 갈 공간 고갈"로 찍힌다) 터진다.
- **STW 시간이 Young GC와 자릿수가 다르다.** STW(Stop-The-World)는 GC가 애플리케이션 스레드를 **전부 멈춰 세우고** 자기 일을 하는 구간이다. 그동안 요청 처리도 응답 전송도 전부 정지한다. 수 GB 힙의 Full GC면 초 단위 멈춤이 나오고, 그것이 요청 타임아웃 → 헬스체크 실패 → 인스턴스 재시작 연쇄로 번진다.

### 1-2. 증상은 GC 그래프가 아니라 응답시간으로 먼저 온다

실무에서 "Full GC 빈발"이 처음 눈에 띄는 형태는 GC 대시보드가 아닌 경우가 많다.

- p99 응답시간 스파이크 (평소 50ms인데 가끔 4초)
- 간헐적 타임아웃 (재현이 안 되고 특정 시간대에만)
- 이유 없는 인스턴스 재시작 (헬스체크가 STW 중에 응답을 못 받아 죽었다고 판정)

그래서 **추적의 첫 관문은 "이 증상이 정말 GC 때문인가"의 확인**이다. GC 로그의 pause 발생 시각과 응답시간 스파이크 시각이 겹치는지 본다. 안 겹치면 GC가 아니라 DB 락, 외부 API 지연, 스레드 풀 고갈 같은 다른 원인을 봐야 한다. **GC가 원인이 아닌데 GC 옵션을 만지느라 시간을 버리는 일이 흔하다.**

### 2-1. Step 0. 최근 변경부터 — "어제까지 멀쩡했다면 범인은 어제와 오늘의 차이"

코드를 열기 전에 먼저 묻는다. 이 단계를 건너뛰고 힙 덤프부터 뜨는 것이 가장 흔한 시간 낭비다.

| 확인 항목 | 전형적 시나리오 |
|---|---|
| 최근 배포 | 새 기능이 대량 조회나 캐시 적재를 추가했다 |
| 설정 변경 | 힙 크기 축소, 캐시 TTL 연장, 배치 주기 변경 |
| 트래픽 변화 | 이벤트나 프로모션으로 초당 할당량 자체가 급증 |
| 데이터 변화 | 특정 고객의 데이터가 비정상적으로 커짐 (한 주문에 항목 10만 개) |

배포 직후부터 시작됐다면 **롤백이 가장 빠른 진단이자 조치**다. 롤백해서 증상이 사라지면 원인은 그 diff 안에 있다 — 탐색 공간이 코드베이스 전체에서 커밋 몇 개로 줄어든다. "원인을 다 밝힌 뒤에 롤백하겠다"는 순서는 장애 시간을 늘릴 뿐이다.

마지막 줄, **데이터 변화**를 특히 놓치기 쉽다. 코드도 설정도 그대로인데 어느 고객사의 데이터 규모만 열 배가 되면, 같은 코드가 열 배의 객체를 만든다. 배포 이력에는 아무것도 안 남는다.

### 2-2. Step 1. 증거 확보 — GC 로그가 없으면 추적도 없다

```bash
# Java 9+ : 통합 로깅. 5개 파일을 20MB씩 돌려쓰며 시각과 uptime을 함께 남긴다
-Xlog:gc*:file=/var/log/gc.log:time,uptime:filecount=5,filesize=20m

# Java 8 : 레거시 플래그
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/var/log/gc.log
```

GC 로그의 오버헤드는 미미하다. 그래서 **운영에서 상시로 켜두는 것이 정석**이다. 사고가 난 뒤에 켜면 "다음 재현"을 기다려야 하는데, 그 다음 재현이 새벽 3시일 수도 있고 한 달 뒤일 수도 있다.

로그가 없는 지금 이 순간 관찰해야 한다면 재시작 없이 붙는 도구를 쓴다.

```bash
jstat -gcutil <pid> 1000    # 1초 간격으로 영역별 사용률과 GC 횟수를 출력
jcmd <pid> GC.heap_info     # 현재 힙 스냅샷
```

`jstat -gcutil`의 출력에서 볼 컬럼은 세 개다.

- **O** — Old 영역 사용률(%). GC를 거치며 어떻게 움직이는지가 Step 2의 판단 재료다.
- **M** — Metaspace 사용률(%). 이 값이 계속 우상향이면 클래스 메타데이터 누수다(2-5).
- **FGC** — Full GC 누적 횟수. **얼마나 빨리 증가하는가**가 심각도를 말해 준다.

여기서 이미 절반은 판별된다. `O`가 Full GC 뒤에도 안 내려가면 Step 3-A, 뚝 떨어지면 Step 3-B다.

### 2-3. Step 2. 결정적 분기 — Full GC 직후 Old 잔량

**이 문서에서 가장 중요한 한 단계다.** GC 로그에서 Full GC 라인의 **before → after 힙 크기**를 본다.

"Full GC 직후 Old 잔량"이란 **청소를 다 하고도 여전히 힙에 남아 있는 양**을 말한다. Full GC는 지금 죽어 있는 객체를 전부 회수하고 끝나므로, **그 뒤에 남은 것은 정의상 전부 살아있는 객체**다. 그래서 이 숫자 하나가 "살아있는 객체가 얼마나 되는가"를 직접 알려 준다. 이 값을 **live set(라이브 셋)**이라고 부른다.

```text
# 유형 A: 청소해도 안 비는 경우
Pause Full (G1 Compaction Pause) 7800M->7400M(8192M)
                                 ^^^^^   ^^^^^
                                 청소 전  청소 후 — 400M밖에 못 줄였다

# 유형 B: 청소하면 잘 비는 경우
Pause Full (G1 Compaction Pause) 7800M->1200M(8192M)
                                         ^^^^^
                                         6600M이 전부 죽은 객체였다
```

두 유형은 그래프 모양으로도 구분된다.

```
[유형 A — 우상향 계단]              [유형 B — 톱니]
힙                                  힙
 |        _/‾                        |  /|  /|  /|  /|
 |    _/‾‾                           | / | / | / | / |
 |_/‾‾                               |/  |/  |/  |/  |
 +----------------- 시간             +----------------- 시간
 Full GC를 해도 바닥이 높아진다      Full GC마다 바닥까지 떨어진다
```

- **유형 A — 우상향 계단**: 청소해도 바닥이 점점 높아진다. **살아있는 객체(live set)가 계속 늘고 있다**는 뜻이다. 원인은 **메모리 누수**이거나, **live set에 비해 힙이 정말로 작은 것**이다. → Step 3-A
- **유형 B — 톱니**: Full GC마다 뚝 떨어진다. 객체 대부분이 이미 죽어 있었는데도 Full GC까지 갔다는 뜻이다. **죽을 객체가 Old에 쌓이는 속도가 문제**다. 원인은 **승격 폭주**이거나 **특이 원인**이다. → Step 3-B

두 유형을 나누는 것이 왜 이렇게 중요한가. **조치 방향이 정반대**이기 때문이다. 유형 A에서 Young 영역을 키우는 것은 아무 효과가 없고, 유형 B에서 힙을 증설하는 것도 대부분 헛수고다. 이 분기를 안 하고 옵션부터 만지는 것이 "찍는 사람"의 전형이다.

### 2-4. Step 3-A. "안 비는" 경우 — 누수인가, 진짜 부족인가

힙 덤프를 떠서 **무엇이 live set을 차지하고 있는지** 확인한다. 뜨는 법과 retained size(그 객체를 지웠을 때 함께 사라지는 메모리의 총량) 분석은 `23-jvm-heap-thread-dump.md`에 있다.

**누수라면**: dominator tree(어떤 객체가 사라지면 어떤 객체들이 함께 회수되는지 보여주는 지배 관계 트리) 상위에 **무한히 자라는 컬렉션**이 보인다. 전형적인 범인이 셋이다.

- 넣기만 하고 빼는 로직이 없는 static Map 캐시
- 리스너·콜백을 등록만 하고 해제하지 않은 경우
- ThreadLocal 미정리 — 스레드 풀에서는 스레드가 죽지 않으므로 값이 영구히 남는다

```java
// before: 넣기만 하고 빼는 코드가 없는 static 캐시 — 전형적 누수
private static final Map<Long, UserSession> CACHE = new HashMap<>();
public void onLogin(UserSession s) { CACHE.put(s.getUserId(), s); }
// static이라 GC의 root에 직접 매달려 있다. 즉 이 Map 안의 모든 세션은
// 프로세스가 죽을 때까지 "살아있는 객체"로 판정된다. GC가 손댈 수 없다.

// after: 상한과 만료가 있는 캐시로 교체 (Caffeine 등)
private static final Cache<Long, UserSession> CACHE = Caffeine.newBuilder()
        .maximumSize(10_000)                      // 상한 — live set의 최대치를 코드로 못 박는다
        .expireAfterWrite(Duration.ofMinutes(30)) // 만료 — 세션 수명과 캐시 수명을 일치시킨다
        .build();
```

**누수가 아니라면**: 덤프에 나온 객체들이 전부 "있어야 할" 객체다. 캐시 설계상의 크기이고, 실제 동시 세션 수만큼의 세션 객체다. 이건 버그가 아니라 **용량 문제**다. 힙 증설이나 캐시를 외부(Redis 등)로 빼는 구조 변경이 답이다.

**둘을 구분하는 기준은 시간축이다.** 시간이 지나도 계속 자라면 누수, 어느 수준에서 평형에 도달하면 용량 문제다. 한 시점의 덤프만으로는 구분이 안 되므로, 시간 간격을 두고 두 번 떠서 비교하거나 `jstat`의 O 컬럼 추이를 본다.

### 2-5. Step 3-B. "잘 비는" 경우 — GC cause로 특이 원인부터 배제

GC 로그의 각 이벤트에는 **원인(cause)**이 함께 찍힌다. **GC cause란 "이 GC를 촉발한 사건이 무엇인가"를 JVM이 스스로 기록해 둔 라벨**이다. 이걸 먼저 읽으면 몇 가지 원인은 추적 없이 즉시 판별된다. 힙 덤프를 뜨기 전에 반드시 확인한다.

| 로그의 cause | 의미 | 조치 방향 |
|---|---|---|
| `System.gc()` | 코드나 라이브러리가 GC를 명시적으로 요청 | 호출부 제거, `-XX:+DisableExplicitGC` |
| `Metadata GC Threshold` | Metaspace가 임계치에 도달 | 동적 클래스 생성 누수 확인 |
| `G1 Humongous Allocation` | region 절반 이상 크기의 객체를 할당하려다 실패 | 거대 객체 생성부 수정 |
| `Allocation Failure` / `to-space exhausted` | 할당·승격 속도가 GC를 추월 | 승격 폭주 분석으로 (아래) |

각 항목이 무슨 뜻인지 하나씩 풀어 보자.

#### `System.gc()` — 코드가 GC를 직접 부르는 경우

`System.gc()`는 **"지금 Full GC를 해 달라"고 JVM에 요청하는 자바 API**다. 이 호출이 있으면 힙이 여유롭든 말든 Full GC가 돈다.

직접 짠 코드에 있는 경우는 오히려 찾기 쉽다. 까다로운 것은 **라이브러리가 부르는 경우**다. RMI(원격 메서드 호출) 기반 기능은 분산 GC를 위해 주기적으로 호출하고, 다이렉트 버퍼(힙 밖 메모리)를 쓰는 라이브러리가 그 정리를 유도하려고 호출하기도 한다.

**판별 단서는 규칙성**이다. Full GC가 트래픽과 무관하게 **정확히 일정한 시간 간격으로** 발생하면 이걸 의심한다. 부하가 원인인 GC는 트래픽 곡선을 따라가지 시계를 따라가지 않는다.

#### `Metadata GC Threshold` — Metaspace가 유발하는 Full GC

**Metaspace**는 힙과 별개의 영역으로, **클래스의 메타데이터**(클래스 구조, 메서드 정보, 상수 풀 등)를 담는다. 우리가 만드는 객체가 아니라 "클래스 그 자체"가 저장되는 곳이다.

여기가 임계치에 차면 JVM은 **Full GC를 돌려 안 쓰는 클래스를 언로드하려고 시도한다.** 그래서 **힙에는 아무 문제가 없는데 Full GC가 도는** 상황이 만들어진다. 이 유형은 힙을 아무리 늘려도 해결되지 않는다.

원인은 대개 **클래스를 런타임에 계속 만들어 내는 코드**다. 리플렉션 프록시, CGLIB 같은 바이트코드 생성 라이브러리, 스크립트 엔진, 요청마다 클래스로더를 새로 만드는 구조가 전형이다. `jstat`의 M 컬럼이 우상향이면 이쪽이다.

#### `G1 Humongous Allocation` — 거대 객체

G1은 힙을 **region**이라는 같은 크기의 조각(보통 1~32MB) 수천 개로 나눠 관리한다. 이때 **크기가 region 하나의 절반 이상인 객체를 humongous(거대) 객체**라고 부르고 특별 취급한다. 일반 region에 안 들어가므로 **연속된 region 여러 개를 이어 붙여** 담는다.

문제는 "연속된"이다. 힙에 빈 공간이 총 20MB 있어도 여기저기 흩어져 있으면 10MB짜리 객체는 못 들어간다. 그래서 humongous 할당은 **힙에 여유가 있어 보이는데도 Full GC를 부르는** 대표적 원인이 된다.

전형적인 발생원은 파일을 통째로 읽은 바이트 배열, 수십만 건 조회 결과 리스트, 거대한 응답 JSON 문자열이다. `-XX:G1HeapRegionSize`를 키워 humongous 판정 경계를 올릴 수는 있지만, **그런 객체를 안 만드는 것**(스트리밍 처리, 페이징)이 근본 조치다.

#### `Allocation Failure` / `to-space exhausted` — 승격 폭주

**`Allocation Failure`는 "새 객체를 할당할 공간이 없어서 GC를 시작했다"**는 뜻으로, GC의 가장 평범한 이유다. 이것만으로는 정보가 별로 없다.

**`to-space exhausted`(옮겨 갈 공간 고갈)는 더 구체적이다.** G1은 살아있는 객체를 다른 region으로 복사해 수거하는데, **복사해 넣을 빈 region이 없어서 복사에 실패했다**는 뜻이다. 이것을 **evacuation failure(복사 실패)**라고 부르고, Young에서 Old로 올리려다 실패한 경우를 특히 **promotion failure(승격 실패)**라고 부른다. 둘 다 G1을 Full GC로 떨어뜨리는 직행 경로다.

특이 원인이 전부 아니라면 남는 것은 **승격 폭주** — 객체가 Young에서 충분히 죽지 못하고 Old로 밀려 들어가는 상황이다.

왜 이게 문제인가. 1-1에서 본 대로 Young 수거는 "대부분 죽는다"는 전제 위에서 싸게 동작한다. 그런데 객체가 **Young GC 몇 번을 버틸 만큼 오래 참조되고 있으면** JVM은 "이건 오래 살 객체구나"로 판단해 Old로 승격시킨다. 실제로는 곧 죽을 객체인데도 말이다. 그렇게 Old가 죽을 객체로 빠르게 차고, Old를 비우려면 무거운 GC가 필요해진다.

원인은 대개 코드에 있다.

```java
// before: 요청 하나가 수십만 row를 한 번에 메모리로 올린다
List<Order> all = orderRepository.findAllByMonth(month);  // 50만 건
return all.stream().map(this::toDto).toList();
// 이 리스트는 메서드가 끝날 때까지 참조가 살아 있다.
// 그동안 Young GC가 여러 번 돌고, 그때마다 이 50만 건이 "아직 살아있음"으로
// 판정돼 결국 전부 Old로 승격된다. 잠시 뒤 전부 죽을 객체인데도.

// after: 페이지 단위로 끊어 처리한다
Page<Order> page;
Pageable pageable = PageRequest.of(0, 1000);
do {
    page = orderRepository.findAllByMonth(month, pageable);
    process(page.getContent());
    // 이 스코프를 벗어나면 이번 페이지를 가리키는 참조가 사라진다.
    // 다음 Young GC에서 곧바로 회수되므로 Old로 올라갈 일이 없다.
    pageable = pageable.next();
} while (page.hasNext());
```

승격 폭주의 전형적 범인은 셋이다. **대량 배치 처리**, **응답 전체를 메모리에 모으는 API**, 그리고 **수명이 어중간한(수 초에서 수 분) 캐시**다. 마지막 것이 특히 까다롭다 — 너무 짧아서 Old에 있을 이유가 없는데 Young에서 죽기에는 너무 길다.

### 2-6. Step 4. 원인 확정 후 조치

| 판별된 원인 | 조치 |
|---|---|
| 메모리 누수 | 코드 수정. **튜닝으로는 절대 해결되지 않는다** |
| 승격 폭주 | 대량 로딩 코드 수정이 먼저, 그다음에야 Young 영역 조정 |
| 진짜 용량 부족 | 힙 증설 또는 구조 변경(캐시를 Redis 등 외부로) |
| `System.gc()` | 호출부 제거 또는 `-XX:+DisableExplicitGC` |
| Metaspace | 동적 클래스 생성 지점 수정 |
| humongous | 거대 객체를 만들지 않도록 스트리밍·페이징으로 전환 |

## 3. 튜닝 절차 — 원인을 안 뒤에 하는 일

### 3-1. 왜 코드가 1순위이고 튜닝이 2순위인가

결론부터 외우지 말고 이유부터 보자. 근거는 GC의 능력 범위에 있다.

**GC가 할 수 있는 일은 "죽은 객체를 회수하는 것" 하나뿐이다.** 어떤 객체가 root(스레드 스택, static 필드 등)에서 참조로 닿을 수 있으면 GC는 그 객체를 절대 건드리지 않는다. 그것이 GC의 계약이고, 어겼다가는 프로그램이 깨진다.

**그리고 GC 옵션이 바꾸는 것은 "GC가 일하는 방식·시점·예산"이지 "객체의 생사"가 아니다.** 힙 크기를 키우면 GC 간격이 늘고, pause 목표를 낮추면 GC가 잘게 자주 돈다. 하지만 **어떤 옵션도 살아있는 객체를 죽여 주지는 않는다.**

여기서 두 종류의 문제가 갈린다.

- **죽어야 할 객체가 안 죽고 있다** → 참조를 끊는 코드가 없다는 뜻이다. 참조를 끊을 수 있는 것은 코드뿐이므로 **정의상 튜닝으로 풀리지 않는다.** 누수, 대량 일괄 로딩, 거대 객체 생성, 불필요한 `System.gc()`가 전부 여기 해당한다.
- **살아야 할 객체를 다룰 자원·설정이 부족하다** → live set이 정당하게 큰데 힙이 작거나, pause 목표가 워크로드와 안 맞는 경우다. **이쪽은 튜닝의 영역이다.**

누수 상황에서 힙을 두 배로 늘리면 어떻게 되는가. live set은 계속 자라므로 **차는 데 걸리는 시간만 두 배가 된다.** 장애가 사라진 게 아니라 다음 장애 시각이 뒤로 밀린 것이다. 그동안 지표는 좋아 보이니 아무도 코드를 안 고치고, 결국 새벽에 터진다.

**그래서 순서는 항상 "원인 규명 → 코드 수정 → 그래도 남는 부분을 튜닝"이다.** 다만 실무에서는 택일이 아니라 시간차 병행인 경우가 많다 — **즉시 완화는 튜닝으로, 근본 조치는 코드로** 하고, 튜닝으로 번 시간에 코드를 고친다.

### 3-2. 철칙: 목표 정의 → 한 번에 하나 → 같은 부하로 재측정

**목표 지표를 먼저 정한다.** "p99 pause 200ms 이하"인지 "배치 전체 처리량 최대"인지에 따라 손잡이를 돌리는 방향이 정반대가 된다. 지연이 목표면 pause 목표를 줄이고(GC가 잘게 자주 돈다), 처리량이 목표면 GC 빈도를 줄인다(한 번의 pause가 길어진다). **목표 없이 튜닝하면 한쪽을 개선하면서 다른 쪽을 망가뜨리고도 모른다.**

**옵션은 한 번에 하나만 바꾼다.** 두 개를 같이 바꾸면 무엇이 효과였는지 영영 알 수 없다. 다음번 비슷한 상황에서 재사용할 수 있는 지식이 하나도 안 남는다.

**같은 부하로 재측정한다.** 트래픽이 다른 시간대끼리 비교하면 결론이 오염된다. 같은 맥락에서 **JIT 워밍업 구간을 측정에 넣지 않는 것**도 중요하다. JVM은 기동 직후 코드를 인터프리터로 실행하다가 자주 쓰이는 코드만 기계어로 컴파일하므로, 처음 몇 분은 정상 상태보다 느리고 객체 생성 패턴도 다르다.

### 3-3. 자주 만지는 손잡이 (G1 기준)

각 옵션이 **무엇을 조절하는 손잡이인지** 한 줄로 이해하고 쓴다.

**`-Xms` = `-Xmx` (힙 시작 크기 = 최대 크기)**
힙 크기를 고정한다. 기본 동작은 필요에 따라 힙을 늘렸다 줄였다 하는 것인데, 그 리사이즈 자체에 비용이 들고 GC 동작도 불안정해진다. 둘을 같은 값으로 못 박는 것이 운영 서버의 기본기다.

**`-XX:MaxGCPauseMillis` (pause 목표)**
G1에게 "한 번의 STW를 이 시간 안에 끝내 달라"고 **목표를 제시**한다. 기본값은 200ms다. G1은 이 목표에 맞춰 다음 GC에서 처리할 region 개수를 스스로 조절한다. **명령이 아니라 목표**라는 점이 중요하다 — 지켜지지 않을 수 있고, 너무 낮게 잡으면 GC가 잘게 자주 돌아 처리량이 떨어진다.

**`-XX:InitiatingHeapOccupancyPercent` (동시 마킹 시작 시점)**
Old 점유율이 몇 %가 되면 동시 마킹을 시작할지 정한다. 초기값은 45%다. **마킹이 할당 속도를 못 따라가 Full GC로 추락하는 상황이면 이 값을 낮춰 더 일찍 시작하게 한다.** 마킹을 일찍 시작할수록 여유는 생기지만 마킹 자체의 CPU 비용을 더 자주 낸다.

**`-XX:G1HeapRegionSize` (region 크기)**
힙을 나누는 조각 하나의 크기를 지정한다. 기본은 JVM이 힙 크기를 보고 자동 결정한다. 이 값을 키우면 **humongous 판정 경계(region의 절반)가 함께 올라가서** 거대 객체 문제를 임시로 피할 수 있다. 근본 조치가 아니라 **시간 벌기**임을 인지하고 써야 한다.

**`-XX:+DisableExplicitGC` (명시적 GC 무력화)**
`System.gc()` 호출을 무시하게 만든다. 원인이 명시적 호출로 확정됐는데 호출부가 우리 코드가 아니어서 못 고칠 때 쓴다. 다만 **다이렉트 버퍼 정리를 `System.gc()`에 의존하는 코드가 있으면 그쪽이 망가질 수 있으므로** 부작용을 검토하고 적용한다.

**주의할 직관 오류가 하나 있다. 힙을 키우는 것은 공짜가 아니다.** Full GC 빈도는 줄지만 **한 번의 Full GC가 더 오래 걸린다.** 치울 면적이 넓어지기 때문이다. "GC 횟수는 줄었는데 p99는 더 나빠졌다"가 여기서 나온다.

또 하나, **G1에서는 `-Xmn`으로 Young 크기를 못 박지 않는다.** G1은 pause 목표에 맞춰 young 크기를 매번 적응적으로 조절하는데, `-Xmn`을 주면 그 적응 기능이 꺼진다. 손으로 고정한 값이 항상 옳을 리 없으므로 대개 손해다.

### 3-4. "GC 튜닝 경험" 답변의 구조 (가산점 포인트)

이 질문에 옵션 이름을 나열하는 것으로 답하면 감점이다. 면접관이 듣고 싶은 구조는 정해져 있다.

1. **증상** — 무엇이 어떻게 아팠는가 (p99가 50ms에서 4초로, 시간당 Full GC 12회)
2. **추적** — 위 런북의 어느 분기를 탔는가 (로그의 cause가 무엇이었고 Old 잔량이 어땠는가)
3. **원인** — 코드였는가 설정이었는가, 그것을 어떻게 확정했는가
4. **조치와 검증** — 무엇을 바꿨고, **같은 지표가 어떻게 변했는가**

"튜닝했더니 좋아졌어요"가 아니라 **"원인을 특정했고, 조치 후 지표로 확인했다"**가 경험의 증거다. 4번의 검증까지 말하는 사람이 드물기 때문에 여기서 변별이 난다.

## 4. 꼬리질문 대비 포인트

### "GC 로그에서 구체적으로 어떤 항목부터 봅니까?"

세 가지를 순서대로 본다.

**첫째, GC cause다.** `System.gc()`, `Metadata GC Threshold`, `G1 Humongous Allocation` 중 하나면 그 즉시 원인 계열이 특정된다. 힙 덤프를 뜨기 전에 반드시 확인해야 하는 이유는, 이 셋은 **힙 덤프를 봐도 안 보이기 때문**이다. Metaspace는 힙 밖이고, 명시적 호출은 코드에 있으며, humongous는 "연속 공간이 없다"는 배치의 문제다.

**둘째, Full GC 전후 힙 크기다.** after가 안 줄면 누수/용량, 잘 줄면 승격·할당 문제로 갈라진다(2-3).

**셋째, 빈도와 간격의 패턴이다.** 정확히 일정한 간격이면 명시적 호출을 의심하고, 트래픽 피크와 동기화되면 할당률 문제이며, **점점 잦아지면 누수의 말기 증상**이다. 마지막 패턴이 중요하다 — 누수는 처음엔 하루에 한 번이다가 나중엔 분 단위가 된다.

### "힙을 2배로 늘렸는데도 Full GC가 계속됩니다. 왜 그럴까요?"

힙 증설이 해결하는 것은 **"live set은 그대로인데 여유 공간이 부족한"** 경우뿐이다. 계속된다면 가능성이 셋이다.

1. **누수** — live set 자체가 계속 자라므로 늘린 공간도 반드시 다시 찬다. 시간문제일 뿐이다.
2. **힙 크기와 무관한 트리거** — Metaspace는 힙 밖 영역이고, humongous는 "총량"이 아니라 "연속 공간"의 문제이며, `System.gc()`는 힙 상태와 아무 상관이 없다.
3. **할당률이 너무 높음** — 동시 마킹이 여전히 할당을 못 따라간다. 이 경우 `InitiatingHeapOccupancyPercent`를 낮춰 마킹을 일찍 시작하게 하는 것이 방향이지만, 근본 원인은 대개 코드의 할당량이다.

답의 핵심은 여기다. **"늘렸는데도 그대로"는 실패가 아니라 유용한 배제 증거다.** 원인이 용량이 아니라는 사실을 확인했으므로 탐색 공간이 줄었다. 이런 식으로 배제를 쌓아 가는 것이 이 질문 전체가 묻는 태도다.

### "운영 중이라 재시작할 수 없는데 GC 로그도 안 켜져 있었다면?"

재시작 없이 붙는 도구로 대체한다.

- `jstat -gcutil <pid> 1000` — 영역별 사용률과 FGC 증가 속도를 실시간 관찰한다. Step 2의 분기 판단은 이것만으로도 가능하다.
- `jcmd <pid> GC.heap_info` — 현재 힙 스냅샷을 뜬다.
- `jcmd <pid> GC.class_histogram` — 클래스별 인스턴스 수를 본다. 힙 덤프보다 가볍다.

그리고 인스턴스가 여러 대인 환경이면 **한 대만 로드밸런서에서 빼서** GC 로그를 켜고 재기동한 뒤 다시 투입하는 방법이 있다. 서비스 영향 없이 다음 재현 때 증거를 확보할 수 있다.

답의 핵심은 "로그가 없으니 못 한다"가 아니라 **대체 수단과 현실 제약(운영 중에 할 수 있는 조치의 범위)을 아는 것**이다.

### "Young GC는 정상인데 Full GC만 문제일 때, Young 영역을 키우는 게 도움이 되나요?"

**될 수 있다 — 단, 승격 폭주가 원인인 경우에 한해서다.**

Young이 작으면 Young GC가 자주 돌고, 객체가 "충분히 죽을 시간"을 못 벌고 나이만 먹어 Old로 밀려난다. Young을 키우면(또는 G1이 pause 목표 안에서 알아서 키우게 두면) **"Young에서 죽을 운명"의 객체가 실제로 Young에서 죽어** Old 유입이 줄어든다.

하지만 누수·Metaspace·humongous·명시적 호출이 원인이면 **아무 효과가 없다.** 누수 객체는 Young을 아무리 키워도 어차피 죽지 않고, Metaspace는 힙 밖이며, humongous는 처음부터 Old 취급이다.

그래서 답의 핵심은 조치가 아니라 순서다. **어느 유형인지 Step 2에서 먼저 판별한 뒤에 만질 손잡이**라는 것. 그리고 G1에서는 `-Xmn`으로 못 박기보다 pause 목표를 조정해 G1이 스스로 young을 키우게 두는 편이 낫다(3-3).

### "어디까지가 튜닝으로 풀 문제이고, 어디부터가 코드를 고칠 문제인가요?" (시니어 변별 포인트)

기준은 한 문장으로 정리된다. **"죽어야 할 객체가 못 죽고 있는가(코드), 살아야 할 객체를 다룰 자원·설정이 부족한가(튜닝)."**

근거는 3-1에서 본 GC의 능력 범위다. **GC는 죽은 객체만 회수할 수 있고, 옵션은 GC가 일하는 방식만 바꿀 뿐 객체의 생사를 바꾸지 못한다.** 그러므로 참조가 살아 있어서 안 죽는 문제는 참조를 끊는 코드로만 풀린다.

- **코드 쪽**: 메모리 누수, 대량 일괄 로딩으로 인한 승격 폭주, 거대 객체 생성, 불필요한 `System.gc()`, 동적 클래스 무한 생성. 튜닝은 증상 완화일 뿐이고 트래픽이 늘면 반드시 재발한다.
- **튜닝 쪽**: live set이 정당하게 큰 서비스의 힙 크기, pause 목표와 처리량의 균형점, 동시 마킹 시작 시점.

여기에 실무 감각을 하나 얹으면 답이 완성된다. **둘은 택일이 아니라 시간차 병행이다.** 장애 대응에서는 즉시 완화(힙 증설, 마킹 조기 시작)로 시간을 벌고, 그렇게 번 시간에 근본 조치(코드 수정)를 한다. 다만 **완화를 하고 나면 지표가 좋아져서 근본 조치가 잊히는 것**이 진짜 위험이므로, 완화 시점에 코드 수정 티켓과 기한을 함께 남기는 것까지가 시니어의 대응이다.

## 한 줄 요약

Full GC 추적은 감이 아니라 배제의 순서다 — **최근 변경 / GC cause / Full GC 직후 Old 잔량**이라는 세 갈림길로 원인 유형을 좁히고(안 비면 누수·용량, 잘 비면 승격 폭주·특이 원인), **GC는 죽은 객체만 치울 수 있으므로 "죽어야 할 객체가 안 죽는" 문제는 코드로만 풀린다**는 것을 알고, 튜닝은 목표 지표를 정한 뒤 한 번에 하나씩 바꿔 같은 부하로 재측정하는 보조 수단으로 쓰는 사람이 "GC 튜닝 경험자"다.
