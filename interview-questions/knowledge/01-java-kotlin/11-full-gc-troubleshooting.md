# Full GC 빈발 원인 추적 — 찍지 말고, 순서대로 배제하라

> 핵심 관전 포인트: **Full GC 추적은 "최근 변경 확인 → GC 로그 확보 →
> Full GC 직후 Old 영역 잔량으로 유형 분기 → 유형별 가설 검증(누수 /
> 승격 폭주 / 명시적 호출 / Metaspace / humongous) → 힙 덤프로 확정"
> 순서다. 결정적 분기점은 하나 — **Full GC가 끝난 뒤에도 Old가 안 비면
> 누수(또는 힙 부족), 비면 객체 수명·할당 패턴 문제**다.
> 튜닝은 원인 규명 뒤의 일이고, 한 번에 옵션 하나씩 바꿔 재측정한다.
> 누수를 튜닝으로 덮으면 장애 시각만 미뤄질 뿐이다.**

---

## 0. 질문 + 의도

**질문**: "GC 튜닝 경험이 있나요? Full GC가 자주 발생할 때 어떤 순서로
원인을 추적하나요?"

**출제 의도**: 전형적인 "AI에 물어볼 수 없는" 상황 — 원인이 코드 어딘가에
있고, 로그·덤프·최근 배포 이력을 조합해 좁혀야 한다. 추적의 '순서'를 묻는
이유는 방법론 없이 찍는 사람과 체계적으로 배제해가는 사람을 구분하기
위해서다.

> GC 알고리즘 자체(G1/ZGC의 동작)는 `10-g1gc-vs-zgc.md`,
> 힙 덤프를 뜨고 읽는 법은 `23-jvm-heap-thread-dump.md` 참고.
> 이 문서는 그 사이 — **"어떤 순서로 좁혀 들어가는가"**만 다룬다.

## 1. 먼저: Full GC가 왜 '사건'인가

Young GC는 설계상 자주 일어나는 정상 동작이다. 반면 **Full GC는 힙 전체를
멈추고 청소하는 최후 수단**이라, 이게 "자주" 일어난다는 것 자체가
JVM이 보내는 조난 신호다.

- G1에서 Full GC는 정상 경로가 아니라 **fallback**이다 — 동시 마킹이
  할당 속도를 못 따라가거나, 객체를 옮길 빈 공간이 없을 때
  (`to-space exhausted`) 터진다.
- STW(Stop-The-World) 시간이 Young GC와 자릿수가 다르다. 수 GB 힙이면
  초 단위 멈춤 → 타임아웃 → 헬스체크 실패 → 재시작 연쇄로 번진다.
- 그래서 "Full GC 빈발"의 실제 증상은 GC 그래프가 아니라
  **p99 응답시간 스파이크, 간헐적 타임아웃, 이유 없는 인스턴스 재시작**으로
  먼저 나타나는 경우가 많다. 추적의 출발은 "이 증상이 정말 GC 때문인가"의
  확인이다.

## 2. 추적 순서 — 5단계 런북

### Step 0. 최근 변경부터 — "어제까지 멀쩡했다면 범인은 어제와 오늘의 차이"

코드를 열기 전에 먼저 묻는다:

| 확인 항목 | 전형적 시나리오 |
|---|---|
| 최근 배포 | 새 기능이 대량 조회/캐시 적재를 추가 |
| 설정 변경 | 힙 크기 축소, 캐시 TTL 연장, 배치 주기 변경 |
| 트래픽 변화 | 이벤트/프로모션으로 할당률 자체가 급증 |
| 데이터 변화 | 특정 고객의 데이터가 비정상적으로 커짐 (한 주문에 항목 10만 개) |

배포 직후 시작됐다면 롤백이 가장 빠른 진단이자 조치다. 롤백해서 사라지면
원인은 그 diff 안에 있다 — 탐색 공간이 코드베이스 전체에서 diff 하나로
줄어든다.

### Step 1. 증거 확보 — GC 로그가 없으면 추적도 없다

```bash
# Java 9+ : 통합 로깅
-Xlog:gc*:file=/var/log/gc.log:time,uptime:filecount=5,filesize=20m

# Java 8 : 레거시 플래그
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/var/log/gc.log
```

GC 로그의 오버헤드는 미미하므로 **운영에서 상시로 켜두는 것**이 정석이다.
사고가 난 뒤에 켜면 "다음 재현"을 기다려야 한다.

로그가 없는 지금 이 순간 관찰해야 한다면:

```bash
jstat -gcutil <pid> 1000    # 1초 간격: E(den), O(ld), M(etaspace) 사용률과 YGC/FGC 횟수
jcmd <pid> GC.heap_info     # 현재 힙 스냅샷
```

`jstat`에서 볼 것은 두 가지 — **FGC 카운트가 얼마나 빨리 증가하는가**,
그리고 **O(Old 사용률)가 GC를 거치며 어떻게 움직이는가**.

### Step 2. 결정적 분기 — Full GC 직후 Old 잔량

GC 로그에서 Full GC 라인의 **before → after 힙 크기**를 본다.
여기서 추적이 두 갈래로 갈라진다.

```text
# 유형 A: 청소해도 안 비는 경우
Pause Full (G1 Compaction Pause) 7800M->7400M(8192M)   ← 회수량이 거의 없음

# 유형 B: 청소하면 잘 비는 경우
Pause Full (G1 Compaction Pause) 7800M->1200M(8192M)   ← 다 죽은 객체였음
```

그래프 모양으로 비유하면:

- **유형 A — 우상향 계단**: Full GC를 해도 바닥이 점점 높아진다.
  살아있는 객체(live set)가 계속 늘고 있다는 뜻 →
  **메모리 누수** 또는 **live set 대비 힙이 정말 작은 것**.
- **유형 B — 톱니**: Full GC마다 뚝 떨어진다. 객체 대부분이 죽어
  있었는데도 Full GC까지 간 것 → 죽은 객체가 Old에 쌓이는 속도가
  문제다. **승격(promotion) 폭주** 또는 **특이 원인**(Step 3-B).

### Step 3-A. "안 비는" 경우 — 누수 vs 진짜 부족

힙 덤프를 떠서 무엇이 live set을 차지하는지 확인한다
(뜨는 법·retained size 분석은 `23-jvm-heap-thread-dump.md`).

- **누수라면**: dominator tree 상위에 무한히 자라는 컬렉션이 보인다.
  전형적 범인 — 제거 로직 없는 static Map 캐시, 리스너/콜백 등록 후
  해제 누락, ThreadLocal 미정리(스레드풀에서 스레드가 안 죽으므로 영구
  잔류).

```java
// before: 넣기만 하고 빼는 코드가 없는 static 캐시 — 전형적 누수
private static final Map<Long, UserSession> CACHE = new HashMap<>();
public void onLogin(UserSession s) { CACHE.put(s.getUserId(), s); }

// after: 상한과 만료가 있는 캐시로 교체 (Caffeine 등)
private static final Cache<Long, UserSession> CACHE = Caffeine.newBuilder()
        .maximumSize(10_000)                     // 상한 — 무한 성장 차단
        .expireAfterWrite(Duration.ofMinutes(30)) // 만료 — 세션 수명과 일치
        .build();
```

- **누수가 아니라면**: 덤프에 나온 객체들이 전부 "있어야 할" 객체다
  (캐시 설계상 크기, 실제 동시 세션 수). 이건 버그가 아니라 용량 문제 —
  힙 증설 또는 캐시를 외부(Redis 등)로 빼는 구조 변경이 답이다.
  구분 기준: **시간이 지나도 계속 자라면 누수, 어느 수준에서 평형이면
  용량 문제.**

### Step 3-B. "잘 비는" 경우 — GC cause로 특이 원인부터 배제

GC 로그의 각 이벤트에는 **원인(cause)이 명시**된다. 이걸 먼저 읽으면
몇 가지 원인은 즉시 판별된다.

| 로그의 cause | 의미 | 조치 방향 |
|---|---|---|
| `System.gc()` | 코드/라이브러리가 명시적 호출 | 호출부 제거, `-XX:+DisableExplicitGC` |
| `Metadata GC Threshold` | Metaspace 임계 도달 | 동적 클래스 생성 누수 확인 |
| `G1 Humongous Allocation` | region 절반보다 큰 객체 할당 | 거대 객체 생성부 수정 |
| `Allocation Failure` / `to-space exhausted` | 할당·승격이 GC를 추월 | 승격 폭주 분석으로 (아래) |

- **`System.gc()`**: 직접 짠 코드 외에, RMI 기반 기능이나 일부
  라이브러리(다이렉트 버퍼 정리 목적 등)가 주기적으로 호출하는 사례가
  유명하다. Full GC가 **일정한 시간 간격으로 규칙적으로** 발생하면 이걸
  의심한다.
- **Metaspace**: 리플렉션 프록시·동적 클래스 생성(CGLIB, 스크립트 엔진
  등)을 반복하면 클래스 메타데이터가 계속 쌓여 Metaspace 임계로 Full GC를
  유발한다. `jstat`의 M 컬럼이 우상향이면 이쪽.
- **Humongous (G1)**: 파일 통째 로딩, 수십만 건 조회 결과 리스트처럼
  region 절반을 넘는 객체는 특별 취급되어 힙을 파편화시키고 Full GC를
  부른다. `-XX:G1HeapRegionSize`를 키우는 것보다 **그런 객체를 안 만드는
  것**(스트리밍, 페이징)이 근본 조치다.

특이 원인이 전부 아니면 남는 것은 **승격 폭주** — 객체가 Young에서 충분히
죽지 못하고 Old로 밀려 들어가는 상황이다. 원인은 대개 코드에 있다:

```java
// before: 요청 하나가 수십만 row를 한 번에 메모리로 — 처리 동안 살아남아 전부 Old로 승격
List<Order> all = orderRepository.findAllByMonth(month);  // 50만 건
return all.stream().map(this::toDto).toList();

// after: 페이지 단위로 끊어 처리 — 각 페이지는 Young에서 생겼다 죽는다
Page<Order> page;
Pageable pageable = PageRequest.of(0, 1000);
do {
    page = orderRepository.findAllByMonth(month, pageable);
    process(page.getContent());   // 이 스코프를 벗어나면 곧바로 수거 대상
    pageable = pageable.next();
} while (page.hasNext());
```

객체가 "Young GC 몇 번을 버틸 만큼" 오래 잡혀 있으면 승격된다.
대량 배치, 응답 전체를 모으는 API, 수명이 어중간한(수 초~수 분) 캐시가
전형적 범인이다.

### Step 4. 원인 확정 후 조치 — 코드가 1순위, 튜닝은 2순위

- 누수 → 코드 수정. 튜닝으로는 절대 해결 안 됨.
- 승격 폭주 → 대량 로딩 코드 수정이 먼저, 그다음에야 Young 영역 조정.
- 진짜 용량 부족 → 힙 증설 또는 구조 변경(외부 캐시).
- 특이 원인 → 각 항목의 조치(호출 제거, 클래스 생성 누수 수정, 거대 객체
  분할).

## 3. 튜닝 절차 — 원인을 안 뒤에 하는 일

### 3-1. 철칙: 목표 정의 → 한 번에 하나 → 재측정

- **목표 지표를 먼저 정한다**: "p99 pause 200ms 이하"인지 "배치 처리량
  최대"인지에 따라 방향이 반대가 된다 (지연 목표면 pause 목표를 줄이고,
  처리량 목표면 GC 빈도를 줄인다).
- **옵션은 한 번에 하나만** 바꾼다. 두 개를 같이 바꾸면 무엇이 효과였는지
  영영 모른다.
- **같은 부하로 재측정**한다. 트래픽이 다른 시간대끼리 비교하면 결론이
  오염된다. JIT 워밍업 전 구간을 측정에 넣지 않는 것도 같은 맥락이다.

### 3-2. 자주 만지는 손잡이 (G1 기준)

| 옵션 | 용도 | 주의 |
|---|---|---|
| `-Xms` = `-Xmx` | 힙 고정 — 런타임 힙 리사이즈 비용 제거 | 운영 서버의 기본기 |
| `-XX:MaxGCPauseMillis` | G1에게 pause 목표 제시 | 명령이 아니라 목표. 너무 낮추면 GC가 잘게 자주 돌아 처리량 하락 |
| `-XX:InitiatingHeapOccupancyPercent` | 동시 마킹 시작 시점을 앞당김 | 마킹이 할당을 못 따라가 Full GC로 추락할 때 낮춘다 |
| `-XX:G1HeapRegionSize` | region 크기 조정 | humongous 판정 경계가 바뀜 — 임시방편임을 인지 |
| `-XX:+DisableExplicitGC` | `System.gc()` 무력화 | 다이렉트 버퍼 정리에 의존하는 코드가 있으면 부작용 검토 |

주의할 직관 오류 하나: **힙을 키우는 것은 공짜가 아니다**. Full GC 빈도는
줄지만 한 번의 Full GC가 더 오래 걸린다(치울 면적이 넓어지므로). 누수
상황에서 힙 증설은 "장애 간격 연장"일 뿐이다. 또 G1에서 `-Xmn`으로 Young
크기를 못 박으면 pause 목표 기반의 적응형 조정이 꺼지므로 지양한다.

### 3-3. "GC 튜닝 경험" 답변의 구조 (가산점 포인트)

이 질문에 옵션 이름 나열로 답하면 하수다. 면접관이 듣고 싶은 구조는:

1. **증상** — 무엇이 어떻게 아팠는가 (p99 스파이크, 시간당 Full GC N회)
2. **추적** — 위 런북의 어느 분기를 탔는가 (로그의 cause, Old 잔량)
3. **원인** — 코드였는가 설정이었는가
4. **조치와 검증** — 무엇을 바꿨고, 같은 지표가 어떻게 변했는가

"튜닝했더니 좋아졌어요"가 아니라 "원인을 특정했고, 조치 후 지표로
확인했다"가 경험의 증거다.

## 4. 꼬리질문 대비 포인트

### "GC 로그에서 구체적으로 어떤 항목부터 봅니까?"

세 가지 순서로 본다. ① **GC cause** — `System.gc()`, `Metadata GC
Threshold`, `G1 Humongous Allocation`이면 그 즉시 원인 계열이 특정된다.
② **Full GC 전후 힙 크기** — after가 안 줄면 누수/용량, 잘 줄면
승격·할당 문제로 분기한다. ③ **빈도와 간격의 패턴** — 정확히 일정
간격이면 명시적 호출 의심, 트래픽 피크와 동기화되면 할당률 문제,
점점 잦아지면 누수의 말기 증상이다.

### "힙을 2배로 늘렸는데도 Full GC가 계속됩니다. 왜 그럴까요?"

힙 증설이 해결하는 것은 "live set은 그대로인데 여유가 부족한" 경우뿐이다.
계속된다면 ① 누수 — live set 자체가 자라므로 시간문제일 뿐 반드시 다시
찬다, ② Metaspace·humongous처럼 **힙 크기와 무관한 트리거**, ③ 할당률이
너무 높아 동시 마킹이 여전히 추월당하는 경우다. "늘렸는데도 그대로"는
오히려 원인이 용량이 아니라는 **유용한 배제 증거**로 쓴다.

### "운영 중이라 재시작할 수 없는데 GC 로그도 안 켜져 있었다면?"

재시작 없이 붙는 도구로 대체한다 — `jstat -gcutil`로 영역별 사용률과
FGC 증가 속도를 실시간 관찰하고, `jcmd GC.heap_info`로 스냅샷을 뜬다.
그리고 다수 인스턴스 환경이면 **한 대만 트래픽에서 빼서** 로그를 켜 재투입
하는 방법이 있다. 답의 핵심은 "로그가 없으니 못 한다"가 아니라 대체 수단과
현실 제약(운영 중 조치 가능 범위)을 아는 것이다.

### "Young GC는 정상인데 Full GC만 문제일 때, Young 영역을 키우는 게 도움이 되나요?"

될 수 있다 — 승격 폭주가 원인인 경우다. Young이 작으면 객체가 충분히 죽을
시간을 못 벌고 Old로 밀려난다. Young을 키우면(또는 G1이 pause 목표 안에서
알아서 키우게 두면) "Young에서 죽을 운명"의 객체가 실제로 Young에서 죽어
Old 유입이 준다. 단, 누수·humongous·명시적 호출이 원인이면 아무 효과가
없다. **어느 유형인지 먼저 판별한 뒤에 만질 손잡이**라는 점이 답의 핵심이다.

### "어디까지가 튜닝으로 풀 문제이고, 어디부터가 코드를 고칠 문제인가요?" (시니어 변별 포인트)

기준은 **"죽어야 할 객체가 못 죽고 있는가(코드), 살아야 할 객체를 다룰
자원·설정이 부족한가(튜닝)"**다. 누수, 대량 일괄 로딩, 거대 객체 생성,
불필요한 `System.gc()`는 전부 전자 — 튜닝은 증상 완화일 뿐이고 트래픽이
늘면 반드시 재발한다. live set이 정당하게 큰 서비스의 힙 크기, pause 목표와
처리량의 균형, 마킹 시작 시점은 후자다. 실무 감각으로는 **튜닝으로 버는
시간에 코드를 고치는 것** — 즉 둘은 택일이 아니라 "즉시 완화(튜닝) + 근본
조치(코드)"의 시간차 병행이 정답인 경우가 많다.

---

## 한 줄 요약

Full GC 추적은 감이 아니라 배제의 순서다 — 최근 변경, GC cause,
Full GC 직후 Old 잔량이라는 세 개의 갈림길로 원인 유형을 좁히고,
코드 수정이 근본 조치·튜닝은 목표 지표를 정한 뒤 한 번에 하나씩
바꾸는 보조 수단임을 아는 사람이 "GC 튜닝 경험자"다.
