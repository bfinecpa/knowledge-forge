# JIT 컴파일러 — 지켜본 다음 번역하고, 틀리면 무른다

> 핵심 관전 포인트: **JVM은 "빨리 시작하기"와 "빨리 돌기"를 동시에 만족시킬 수 없어서 **둘 다 조금씩 취하는 계층 구조**를 택했다 — 처음엔 인터프리터로 즉시 실행하면서 어느 메서드가 뜨거운지 세고, 임계치를 넘으면 C1이 빠르게 대충 번역하며 관찰 기록을 쌓고, 충분히 뜨거워지면 C2가 그 관찰 기록을 근거로 공격적으로 번역한다. C2의 최적화가 정적 컴파일러보다 과감할 수 있는 이유는 하나다 — **"실제로 이렇게만 돌더라"는 관찰에 베팅하고, 틀리면 무를 수 있기 때문**(역최적화)이다. 인라이닝으로 메서드 경계를 지워 분석 시야를 열고, 한 타입만 오는 호출 지점은 직접 호출로 바꾸고(탈가상화), 밖으로 새나가지 않는 객체는 아예 안 만든다(스칼라 치환). 대가는 실무에서 그대로 체감된다 — **기동 직후엔 느리고(워밍업 → 배포 직후 타임아웃), 베팅이 틀리면 순간 느려지고(역최적화), 타입이 셋 이상 섞이면 최적화를 포기하고(메가모픽), 번역본 보관함이 차면 성능이 서서히 죽는다(코드 캐시 고갈).** 그리고 이 모든 것이 **성능 측정을 오염시킨다** — 예열 없이 잰 숫자는 인터프리터의 속도이고, 결과를 안 쓰는 벤치마크는 측정 코드 자체가 통째로 삭제된 뒤의 0에 가까운 숫자다. JMH를 쓰는 이유가 그것이다.**

---

## 0. 질문 + 의도

**질문**: "JIT 컴파일러의 동작(C1/C2, 인라이닝, 탈최적화)이 성능에 미치는 영향을 설명해주세요."

**출제 의도**: 배포 직후 latency 상승, 부하 테스트의 워밍업 필요성 같은 "측정을 오염시키는 요인"을 아는지 본다. 이걸 모르면 성능 측정 자체를 잘못해서 잘못된 결론으로 튜닝한다.

## 1. 왜 인터프리터 다음에 C1이고, 그다음이 C2인가

주니어에게 가장 불친절한 지점이 여기다. "C1은 빠른 컴파일러, C2는 좋은 컴파일러"라고 외우면 아무것도 설명되지 않는다. **왜 컴파일러를 두 개나 두고, 왜 그 앞에 인터프리터까지 두는가**부터 풀어야 한다.

### 1-1. 전제 지식 — 자바 코드가 실행되기까지

먼저 CPU가 무엇을 실행하는지 확인하자. CPU가 이해하는 것은 **기계어(machine code)** — 그 CPU 전용의 이진 명령뿐이다. 자바 소스는 물론이고 `javac`가 만든 `.class` 파일의 **바이트코드(bytecode)**도 CPU는 이해하지 못한다.

```
User.java  --javac-->  User.class (바이트코드)  --???-->  CPU가 실행하는 기계어
                        JVM이 이해하는 중간 언어           CPU가 이해하는 언어
```

바이트코드는 "JVM이라는 가상의 컴퓨터를 위한 기계어"다. 이 중간 단계를 둔 덕분에 같은 `.class` 파일이 x86에서도 ARM에서도 돈다. 대신 **바이트코드를 실제 기계어로 바꾸는 일이 실행 시점에 남는다.** 이 남은 일을 처리하는 방식이 두 가지 있고, 그 선택이 이 문서 전체의 주제다.

### 1-2. 두 극단 — 통역사와 번역가

문서 하나를 외국어로 읽어야 한다고 하자. 방법이 두 가지다.

**인터프리터(interpreter) = 동시통역사.** 문장을 만날 때마다 그 자리에서 한 줄씩 통역한다. **준비 시간이 0이라 즉시 시작할 수 있다.** 대신 같은 문장을 100번 만나면 100번 다시 통역한다. 바이트코드 명령 하나를 실행할 때마다 "이 명령이 뭐지"를 해석하는 비용을 매번 낸다. 느리다.

**컴파일러 = 번역가.** 문서를 통째로 번역해서 종이에 적어 둔다. **번역하는 동안은 읽기를 시작조차 못 한다.** 대신 번역이 끝나면 그냥 읽기만 하면 되니 압도적으로 빠르다.

여기서 **"빨리 시작하기 vs 빨리 돌기"**의 트레이드오프가 나온다.

| | 시작까지 | 최고 속도 | 문제 |
|---|---|---|---|
| 전부 인터프리트 | 즉시 | 낮음 | 오래 도는 서버가 영원히 느리다 |
| 전부 미리 컴파일 | 오래 걸림 | 높음 | 한 번만 실행할 코드까지 번역하느라 시간을 버린다 |

실행 전에 전부 번역해 두는 방식을 **AOT(Ahead-Of-Time, 미리 컴파일)**라고 부른다. C나 Go가 이 방식이다. JIT의 반대말로 기억하면 된다.

두 극단 모두 자바가 원하는 답이 아니다. 자바 프로그램은 **켜자마자 응답해야 하고 동시에 몇 달을 돌아야 하기** 때문이다.

### 1-3. 절충 — 뜨거운 곳만 번역한다

돌파구는 관찰에서 나왔다. **실행 시간의 대부분은 극히 일부 코드가 차지한다.** 만 개의 메서드가 있어도 CPU 시간의 90%는 그중 수십 개에서 쓰인다. 초기화 코드는 딱 한 번 돌고, 예외 처리 분기는 평생 안 탈 수도 있다.

그러면 **전부 번역하지 말고, 실제로 뜨거운 곳에만 번역 비용을 집중**하면 된다.

**JIT(Just-In-Time) 컴파일**은 이름 그대로 "필요해지는 바로 그때" 번역하는 방식이다. JVM은 처음엔 전부 인터프리터로 실행하면서, 각 메서드가 몇 번 호출됐고 각 루프가 몇 번 돌았는지를 센다. 이 카운터를 **프로파일링 카운터(profiling counter)**라고 부른다. 메서드 호출 횟수를 세는 카운터와 루프가 뒤로 점프한 횟수(back-edge)를 세는 카운터 두 종류가 있다.

```
메서드 A 호출 1회   -> 카운터 1
메서드 A 호출 2회   -> 카운터 2
...
메서드 A 호출 N회   -> 카운터가 임계치 도달! -> 컴파일 큐에 등록
                     (등록만 하고 실행은 계속 인터프리터로 진행한다.
                      컴파일러 스레드가 백그라운드에서 번역한다)
                     -> 번역 완료 후부터의 호출은 기계어로 실행
```

카운터가 넘어야 하는 값을 **핫스팟 임계치(compile threshold)**라고 하고, 임계치를 넘어 컴파일 대상이 된 코드를 **핫스팟(hotspot, 뜨거운 지점)**이라고 부른다. **HotSpot이라는 JVM 이름 자체가 여기서 왔다.** 임계치는 `-XX:CompileThreshold` 등으로 조정할 수 있고, 아래에서 설명할 계층형 컴파일에서는 계층별로 별도의 임계치를 쓴다.

**중요한 것은 컴파일이 백그라운드 스레드에서 일어난다는 점**이다. 임계치를 넘었다고 실행이 멈추고 번역을 기다리는 것이 아니다. 번역이 끝날 때까지는 인터프리터로 계속 돌고, 끝난 시점부터 기계어 버전으로 갈아탄다.

### 1-4. 그런데 왜 컴파일러가 두 개인가 — 계층형 컴파일

여기까지만 보면 컴파일러는 하나면 충분해 보인다. 왜 C1과 C2가 따로 있는가.

이유는 **좋은 번역을 하려면 시간과 정보가 둘 다 필요한데, 둘 다 처음엔 없기 때문**이다.

- **시간**: 공격적인 최적화는 분석이 오래 걸린다. 뜨거워진 즉시 최고 품질로 번역하려 하면 그동안 계속 느린 인터프리터로 돌아야 한다.
- **정보**: 최고의 최적화는 "이 호출 지점엔 항상 `Circle`만 온다" 같은 **실행 패턴 관찰**에 기반한다. 그런데 인터프리터가 남기는 관찰 기록은 정밀하지 않다. 정밀하게 관찰하려면 관찰용 코드가 들어간 상태로 한동안 돌려 봐야 한다.

그래서 **중간 단계**를 둔다. 이것이 **계층형 컴파일(tiered compilation)**이고, 현재 JVM의 기본 동작이다.

| 계층 | 담당 | 하는 일 |
|---|---|---|
| Level 0 | 인터프리터 | 즉시 실행. 기본적인 호출/루프 카운터를 센다 |
| Level 1~3 | **C1** 컴파일러 | 빠르게 번역해 일단 인터프리터보다 훨씬 빠르게 만든다. 동시에 **관찰용 계측 코드를 심어** 정밀한 프로파일을 수집한다 |
| Level 4 | **C2** 컴파일러 | 느리지만 공격적으로 번역한다. C1이 모아 둔 관찰 기록을 근거로 과감한 베팅 최적화를 건다 |

C1이 하는 일을 두 가지로 나눠 보는 것이 핵심이다. **하나는 "일단 빨라지게 하는 것"이고, 다른 하나는 "C2가 쓸 자료를 모으는 것"이다.** 두 번째 역할 때문에 C1 코드는 순수하게 빠른 코드보다 조금 느리다 — 계측 코드가 들어 있기 때문이다. 그 대신 C2가 훨씬 좋은 코드를 만든다.

```
시간 ────────────────────────────────────────────────────>

Level 0 (인터프리터)   Level 3 (C1 + 계측)      Level 4 (C2)
느림, 즉시 시작   ->   중간 속도, 관찰 수집  ->  최고 속도
     |                      |                      |
   호출 카운터 임계치      더 뜨거워짐           관찰 기록을 근거로
   돌파                                          공격적 최적화
```

정리하면 **"빨리 시작하기 vs 빨리 돌기"의 트레이드오프를 시간축에 펼쳐서, 시간이 지날수록 후자로 옮겨 가게 만든 것**이 계층형 컴파일이다. 어느 한쪽을 고르는 대신 순서대로 둘 다 취한다.

### 1-5. OSR — 메서드가 아직 안 끝났는데 뜨거워졌다면

여기서 자연스럽게 생기는 문제가 하나 있다.

```java
public void batchProcess() {
    for (int i = 0; i < 100_000_000; i++) {   // 1억 번 도는 루프
        compute(i);
    }
}
```

`batchProcess()`는 **딱 한 번 호출된다.** 호출 카운터는 1에서 멈춘다. 그런데 이 메서드는 몇 분간 CPU를 독점한다. 호출 횟수 기준으로는 영원히 컴파일 대상이 되지 못하고, 설령 대상이 되더라도 **다음 호출이 없으니 컴파일된 코드를 쓸 기회 자체가 없다.**

그래서 JVM은 루프의 back-edge(반복이 끝나고 처음으로 되돌아가는 지점)도 별도로 센다. 이 카운터가 임계치를 넘으면 **루프 본문을 컴파일한 뒤, 이미 실행 중인 그 메서드의 스택 프레임을 컴파일된 버전으로 갈아 끼운다.**

이것을 **OSR(On-Stack Replacement, 스택 위에서의 교체)**이라고 부른다. 이름 그대로 **스택 위에서 실행 중인 상태를 그대로 유지한 채 코드만 바꿔치기하는 것**이다. 달리는 자동차의 엔진을 달리면서 교체하는 셈이라, 루프 변수와 지역 변수의 현재 값을 컴파일된 코드의 대응 위치로 전부 옮겨 담는 작업이 필요하다.

OSR이 없으면 **"오래 도는 루프 하나로 이루어진 배치 작업"은 영원히 인터프리터로 돈다.** 배치 성능을 이야기할 때 알아 두면 좋은 장치다.

## 2. JIT가 빠르게 만드는 방법 — 지켜본 다음 베팅한다

JIT의 진짜 무기는 번역 자체가 아니다. **실제로 프로그램이 어떻게 돌아가는지 지켜본 다음에 번역한다**는 점이다.

미리 번역하는 AOT 방식은 "이 호출 지점에 어떤 타입이 오는지", "이 조건문이 실제로는 항상 참인지"를 알 수 없다. 모든 가능성에 대비한 코드를 만들어야 한다. **JIT는 관찰한 사실에 베팅하고, 틀리면 무를 수 있기 때문에 훨씬 과감해질 수 있다.**

### 2-1. 메서드 인라이닝 — 가장 중요한 최적화

**인라이닝(inlining)**은 메서드를 호출하는 대신 **그 메서드의 내용을 호출한 자리에 그대로 복사해 넣는 것**이다. 안쪽(in)에 펼쳐 넣는다는 뜻이다.

```java
// 개발자가 쓴 코드
String name = user.getName();   // getName()을 "호출"

// JIT가 바꾼 코드 (개념상)
String name = user.name;        // 호출 없이 내용물을 그 자리에 박아 넣음
```

1차 이득은 **호출 비용 제거**다. 메서드 호출에는 인자를 스택에 쌓고, 점프하고, 새 스택 프레임을 만들고, 돌아올 주소를 기억하고, 반환값을 넘겨받는 일이 따른다. getter 본체가 필드 읽기 한 줄이라면 이 부대비용이 본체보다 크다. **getter/setter를 마음껏 써도 느려지지 않는 이유가 인라이닝이다.**

**하지만 진짜 이득은 "다른 최적화의 문을 여는 것"이다.**

JIT는 코드를 한 덩어리 단위로 분석한다. 중간에 메서드 호출이 있으면 **그 너머가 안 보여서 분석이 거기서 끊긴다.** 호출된 메서드가 무슨 값을 반환할지, 어떤 필드를 건드릴지 모르니 아무 가정도 못 한다.

```java
// 인라이닝 전: check() 안에서 무엇을 하는지 몰라 손을 못 댄다
if (check(x)) { doSomething(); }

// 인라이닝 후: check()의 내용이 펼쳐지자 비로소 보인다
// "x는 위에서 항상 양수로 확정 -> 이 조건은 항상 true
//  -> if 검사 자체를 삭제하고 doSomething()만 남긴다"
```

인라이닝은 그래서 **최적화의 촉매**다. 인라이닝 → 상수 전파 → 조건 제거 → 죽은 코드 제거로 연쇄가 일어난다.

다만 무한정 펼칠 수는 없다. 다 펼치면 코드가 폭발해 CPU의 명령 캐시에 안 들어가고 오히려 느려진다. 그래서 **크기 제한**이 있다 — 호출 빈도가 특별히 높지 않은 메서드는 바이트코드 35바이트, 뜨거운 메서드는 325바이트가 기본 상한이다(`-XX:MaxInlineSize`, `-XX:FreqInlineSize`). 거대한 메서드는 인라이닝이 안 되므로, **핫 루프 안의 메서드를 작게 유지하는 것**이 실제로 성능에 영향을 준다.

### 2-2. 단형성 인라인 캐시와 탈가상화

```java
for (Shape s : shapes) {
    s.draw();    // <- 이 줄이 call site (호출 지점)
}
```

**call site(호출 지점)**란 메서드를 호출하는 **코드의 그 줄**을 말한다. 같은 `draw()` 메서드라도 프로그램 안의 서로 다른 줄에서 호출되면 서로 다른 call site이고, JIT는 **call site별로 따로 관찰하고 따로 최적화한다.**

`s.draw()`는 `s`가 `Circle`이냐 `Square`냐에 따라 실제 실행되는 코드가 달라지는 **가상 메서드 호출(virtual call)**이다. 오버라이딩 때문에 컴파일 시점에는 어느 구현이 불릴지 알 수 없고, 실행 시점에 객체의 실제 타입을 보고 결정해야 한다. 이 타입 조회 과정이 직접 호출보다 느리고, 무엇보다 **어느 메서드가 불릴지 모르므로 인라이닝을 할 수 없다.**

여기서 JIT가 쓰는 장치가 **인라인 캐시(inline cache)**다. call site마다 **"지난번에 실제로 온 타입이 무엇이었는지"를 기억해 두는 작은 캐시**를 코드 안에(inline) 심어 둔다.

관찰 결과에 따라 call site는 세 부류로 나뉜다.

- **단형성(monomorphic)** — 실제로 오는 타입이 **한 개**뿐이다.
- **이형성(bimorphic)** — 두 개가 온다.
- **다형성(megamorphic)** — 세 개 이상이 온다. "거대하게 여러 형태"라는 뜻이다.

단형성 call site를 만나면 JIT는 **베팅**한다.

```java
// JIT의 베팅: "지금까지 전부 Circle이었으니 앞으로도 Circle일 것이다"
if (s.getClass() == Circle.class) {
    // 빠른 경로: Circle.draw()를 직접 호출로 확정하고 인라이닝까지 한다.
    // 타입 조회가 사라졌고, 본문이 펼쳐졌으니 추가 최적화의 문도 열렸다.
    ...Circle.draw()의 본문...
} else {
    // 베팅 실패. 여기로 오면 최적화된 코드를 버리고 되돌아간다 (2-3)
    deoptimize();
}
```

가상 호출을 직접 호출로 바꾸는 이 변환을 **탈가상화(devirtualization)**라고 부른다. 그리고 이렇게 **확실하지 않지만 관찰을 근거로 빠른 길을 미리 만들어 두는 것**을 **추측 실행(speculative execution)**이라고 한다.

앞의 `if`는 **가드(guard)**라고 부른다. 베팅이 여전히 유효한지 확인하는 최소한의 검사다. 검사 하나로 타입 조회 + 인라이닝 불가라는 큰 비용을 걷어내므로 남는 장사다.

이형성까지는 가드를 두 개 두는 방식으로 여전히 인라이닝이 가능하다. **문제는 세 개 이상일 때인데, 이건 3-4에서 다룬다.**

### 2-3. 역최적화와 uncommon trap — 무를 수 있어야 베팅할 수 있다

베팅 최적화가 성립하려면 **베팅이 틀렸을 때 안전하게 되돌리는 장치**가 반드시 있어야 한다. 그 장치가 **역최적화(deoptimization)**다.

JIT는 최적화된 코드에서 "여기 오면 가정이 깨진 것"인 지점에 **uncommon trap(드문 경우 함정)**을 심는다. 이름 그대로 "거의 안 일어날 일이 일어났을 때 걸리는 덫"이다. 2-2의 `else` 분기가 바로 그것이다. 여기에는 정상 처리 코드가 아니라 **"JVM으로 제어를 넘기라"는 표시**만 들어 있다.

트랩이 걸리면 벌어지는 일은 이렇다.

```
[C2로 컴파일된 코드 실행 중]
        |
   가드 실패 (예상 못 한 타입이 왔다)
        |
   uncommon trap 발동
        |
   (1) 컴파일된 코드의 레지스터 상태를 인터프리터 프레임으로 되돌린다
       — 실행 중이던 지점의 지역 변수 값을 그대로 옮겨 담는다
   (2) 그 지점부터 인터프리터로 실행을 이어 간다
   (3) 문제의 컴파일 코드는 "더 이상 진입 불가(made not entrant)"로 표시한다
   (4) 새 관찰 기록이 쌓이면 다시 컴파일한다 (이번엔 더 보수적으로)
```

**(1)이 기술적으로 어려운 부분**이다. 컴파일된 코드는 최적화 때문에 변수 배치가 원본과 전혀 다르다. 어떤 변수는 레지스터에 있고, 어떤 변수는 아예 사라졌으며(스칼라 치환된 객체 등), 명령 순서도 뒤바뀌어 있다. 그래서 JIT는 컴파일 시점에 **"이 지점에서 되돌아가려면 각 변수의 원래 값을 어디서 가져와야 하는지"를 기록한 지도**를 함께 만들어 둔다.

역최적화는 실패가 아니라 **설계의 일부**다. 이 장치가 있기 때문에 C2가 정적 컴파일러는 절대 못 할 과감한 가정을 걸 수 있다. **다만 발생하면 순간적인 성능 저하와 재예열이 따르고, 반복되면 실제 장애가 된다**(3-3).

### 2-4. 탈출 분석과 스칼라 치환 — 객체를 아예 안 만들기

**탈출 분석(escape analysis)**은 **"이 객체가 자기를 만든 메서드 밖으로 새나가는가"를 조사하는 것**이다. 밖으로 나가는 것을 "탈출한다(escape)"고 표현한다.

객체가 탈출하는 경로는 정해져 있다. 필드에 대입되거나, 다른 메서드에 인자로 넘어가거나, 반환되거나, 다른 스레드에서 보이게 되면 탈출이다. **이 중 아무것도 안 하면 그 객체는 메서드 안에서 태어나 메서드 안에서 죽는다.**

그런 객체는 **힙에 만들 필요가 없다.** 아무도 밖에서 볼 수 없으니 "객체가 존재했다"는 사실 자체를 관측할 방법이 없기 때문이다. 그래서 JIT는 객체를 **구성 필드 낱개로 분해**해 버린다.

```java
// 개발자가 쓴 코드
Point p = new Point(3, 5);
return p.x + p.y;

// JIT가 바꾼 코드 (개념상): 객체가 사라지고 값만 남는다
int x = 3;    // 힙 할당 없음 -> GC가 나중에 회수할 일도 없음
int y = 5;    // 두 값은 대개 레지스터에 그대로 올라간다
return x + y;
```

객체(여러 값의 묶음)를 스칼라(int 같은 낱개 값)로 바꿔치기한다고 해서 **스칼라 치환(scalar replacement)**이라고 부른다.

**"루프 안에서 임시 객체를 좀 만들어도 생각보다 괜찮다"는 통념의 근거가 이것**이다. 다만 조건부다 — 탈출하지 않아야 하고, 인라이닝이 충분히 되어 JIT의 시야에 전체가 들어와야 한다. 그래서 인라이닝(2-1)이 여기서도 전제 조건이 된다.

탈출 분석은 락에도 적용된다. 탈출하지 않는 객체로 잡는 락은 다른 스레드가 경쟁할 수 없으므로 **락 자체를 삭제**한다. 이것을 **락 제거(lock elision)**라고 한다.

### 2-5. 나머지 최적화들

- **루프 최적화** — 반복문을 여러 번 펼쳐 반복 검사 횟수를 줄이고(**언롤링, unrolling**), 배열 인덱스가 범위를 벗어날 수 없음이 증명되면 매 접근마다 하던 범위 검사를 지우며(**범위 검사 제거**), 여러 원소를 CPU의 한 명령으로 묶어 처리한다(**벡터화**).
- **인트린식(intrinsic)** — `System.arraycopy`, `Math.min`, `String.indexOf` 같이 잘 알려진 메서드는 **자바 구현을 무시하고 그 CPU 전용의 최적 명령열로 통째로 치환**한다. "본질적으로 JVM이 아는 메서드"라는 뜻이다.

이 최적화들이 겹쳐서, 충분히 예열된 JVM의 핫 코드는 C/C++에 근접한 처리량을 낸다.

## 3. 대가와 실무 — 워밍업, 측정, 운영

### 3-1. 워밍업 — 배포 직후가 느리다

**워밍업(warm-up, 예열)**은 **번역이 충분히 쌓여 제 속도가 날 때까지의 구간**이다. 기동 직후엔 모든 코드가 Level 0(인터프리터)에서 시작하므로 느리고, 그 위에 **컴파일 작업 자체가 CPU를 쓴다.** 느린 상태인데 CPU까지 뺏기는 이중고다.

**실무 증상은 명확하다. 배포나 재시작 직후 몇 분간 레이턴시가 튀고, 첫 요청들이 타임아웃 난다.** 롤링 배포 중 새 파드에 트래픽이 몰리면 그 파드만 응답이 밀리고, 헬스체크가 실패해 재시작되는 악순환까지 갈 수 있다.

대응은 두 갈래다.

- **트래픽을 서서히 올린다(램프업).** 새 인스턴스에 처음부터 100%를 주지 않고 가중치를 점진적으로 올린다.
- **헬스체크 통과 전에 예열 요청을 태운다.** 기동 스크립트에서 주요 엔드포인트를 수백 번 호출해 핫스팟을 미리 만든 뒤 준비 완료를 선언한다.

근본 대안(CDS, AOT 캐시, Native Image, CRaC)은 3-8 이후에서 다룬다.

### 3-2. 벤치마크가 거짓말하는 이유 — dead code elimination과 JMH

**출제 의도가 정면으로 겨냥하는 지점이 여기다.** JIT를 모르면 성능 측정 자체를 틀리고, 틀린 숫자로 잘못된 결론을 내린다.

가장 흔한 함정을 보자.

```java
// before: 이 벤치마크는 아무것도 측정하지 못한다
public static void main(String[] args) {
    long start = System.nanoTime();
    for (int i = 0; i < 100_000_000; i++) {
        Math.sqrt(i);        // 결과를 아무도 안 쓴다
    }
    System.out.println((System.nanoTime() - start) / 1_000_000 + "ms");
}
```

이 코드는 "1억 번의 제곱근 연산"을 재는 것처럼 보인다. 실제로는 0에 가까운 숫자가 나온다. 이유는 이렇다.

`Math.sqrt`는 부작용이 없는 순수 계산이고, **그 결과를 아무도 쓰지 않는다.** JIT 입장에서 이 계산은 **결과가 관측되지 않으므로 실행하든 안 하든 프로그램의 동작이 같다.** 그래서 계산을 통째로 지운다. 이것을 **dead code elimination(죽은 코드 제거)**이라고 부른다. 본문이 비면 루프도 의미가 없으므로 루프까지 사라진다.

```
[JIT가 실제로 실행하는 코드]
long start = System.nanoTime();
// (루프가 통째로 삭제됨)
System.out.println(...);        // -> 0ms 또는 1ms
```

여기에 워밍업 문제까지 겹친다. 반대로 루프를 짧게 잡으면 **아직 컴파일되지 않은 인터프리터 상태의 속도**를 재게 된다. 같은 코드가 측정 방식에 따라 0ms도 나오고 실제보다 열 배 느린 숫자도 나온다.

그래서 **JMH(Java Microbenchmark Harness)**를 쓴다. JMH는 OpenJDK 팀이 만든 마이크로벤치마크 프레임워크로, **JIT가 측정을 망치는 방식들을 하나씩 막아 주는 도구**다.

```java
// after: JMH — JIT의 개입을 막고 정상 상태를 측정한다
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)      // 5초간 예열만 하고 그 결과는 버린다.
                                       // C2 컴파일이 끝난 정상 상태에 도달시키기 위한 것
@Measurement(iterations = 10, time = 1)
@Fork(1)                               // 별도 JVM에서 실행한다. 다른 벤치마크가 남긴
                                       // 프로파일이 섞이는 것을 막는다 (3-6 프로파일 오염)
@State(Scope.Benchmark)
public class SqrtBenchmark {

    // final이 아닌 필드로 둔다. final 상수면 JIT가 컴파일 시점에
    // sqrt(42.0)을 미리 계산해 버려(상수 폴딩) 측정할 연산이 사라진다.
    private double x = 42.0;

    @Benchmark
    public double sqrt() {
        return Math.sqrt(x);   // 반환하면 JMH가 그 값을 소비한다.
                               // "결과가 쓰인다"가 보장되므로 죽은 코드 제거가 불가능해진다
    }
}
```

결과를 소비하는 다른 방법으로 `Blackhole`이 있다. 값을 여러 개 만들어 내는 벤치마크에서는 `blackhole.consume(value)`로 각각을 소비시킨다. Blackhole은 JIT가 "이 값은 쓰였다"고 판단하게 만들면서도 실제 비용은 거의 들지 않도록 설계돼 있다.

**정리하면 JMH가 막아 주는 것은 셋이다.** 죽은 코드 제거(결과 소비), 워밍업 미달(예열 반복 강제), 프로파일 오염(별도 JVM 포크). 손으로 짠 `System.nanoTime()` 루프는 이 셋 중 무엇도 막지 못한다.

**부하 테스트도 같은 원리다.** 예열 구간의 응답시간을 결과에 섞으면 실제보다 나쁜 숫자가 나오고, 그 숫자를 근거로 엉뚱한 튜닝을 하게 된다.

### 3-3. 역최적화 폭풍 — 베팅이 계속 틀릴 때

역최적화 자체는 정상 동작이다(2-3). 문제는 **반복될 때**다.

가정이 깨지는 대표적 계기가 **새 클래스의 로딩**이다. JIT는 "지금까지 로딩된 클래스 중 `Shape`의 구현은 `Circle`뿐이니 `draw()`는 항상 `Circle.draw()`"라는 가정으로 최적화할 수 있다. 그런데 나중에 `Square`가 처음 로딩되는 순간 이 가정이 무너지고, 그 가정에 의존하던 컴파일 코드가 전부 무효화된다.

**최적화 → 역최적화 → 재컴파일 → 다시 역최적화가 반복되는 상태를 deopt storm(역최적화 폭풍)**이라고 부른다. 이 상태에 빠지면 컴파일러 스레드가 CPU를 계속 쓰면서도 코드는 계속 느린 경로로 돈다. 지속적인 성능 저하로 나타나고, 원인을 모르면 추적이 매우 어렵다.

관측은 `-XX:+PrintCompilation`으로 한다. 로그에 `made not entrant`(더 이상 진입 불가) 표시가 같은 메서드에 대해 반복적으로 찍히면 이 상황이다.

### 3-4. 메가모픽 — 다형성의 숨은 비용

2-2에서 미뤄 둔 이야기다. call site에 오는 타입이 **한 개(단형성)나 두 개(이형성)까지는** 가드를 붙여 베팅과 인라이닝이 가능하다. 인라인 캐시가 기억할 수 있는 타입 개수가 거기까지이기 때문이다.

**세 개 이상(메가모픽)이 되면 JIT는 가정 자체를 포기한다.** 어느 타입이 올지 예측할 수 없으니 가드를 붙일 수도 없다. 그러면 **매번 실제 타입을 조회해 호출**하는 원래 방식으로 돌아가고, **인라이닝도 불가능해지므로 그 너머의 최적화 연쇄도 전부 끊긴다.**

```
[단형성]  타입 확인 1회 -> 직접 호출 -> 인라이닝 -> 추가 최적화 연쇄
[메가모픽] 매번 타입 조회 -> 간접 호출 -> 인라이닝 불가 -> 최적화 벽
```

실무에서는 **같은 인터페이스의 구현체 여러 개가 섞여 지나가는 핫 루프**가 위험하다. 전략 패턴으로 핸들러 열 개를 만들어 하나의 디스패치 루프에서 돌리는 구조가 전형이다. 코드는 깔끔한데 그 한 줄이 성능 절벽이 된다.

다만 **설계를 먼저 훼손하지는 않는다.** 다형성은 유지보수성의 핵심이고, 대부분의 코드에서 이 비용은 무시할 수 있다. **프로파일링으로 그 call site가 실제 병목임을 확인한 뒤에** 핫 경로만 분리하는 것이 순서다.

### 3-5. 코드 캐시 고갈 — 번역본 보관함이 가득 차면

**코드 캐시(code cache)**는 JIT가 번역한 기계어를 보관하는 **전용 메모리 영역**이다. 힙과는 별개이고, 크기가 정해져 있다(계층형 컴파일 기본 설정에서 240MB, `-XX:ReservedCodeCacheSize`로 조정).

여기가 가득 차면 이런 경고가 뜬다.

```
CodeCache is full. Compiler has been disabled.
```

그리고 **그 시점부터 컴파일이 중단된다.** 이미 컴파일된 코드는 계속 쓰이지만, 새로 뜨거워진 코드는 영원히 인터프리터로 돈다. 그래서 증상이 특이하다 — **갑자기 죽는 게 아니라 성능이 서서히 나빠진다.** 재시작하면 잠시 괜찮아졌다가 며칠 뒤 다시 나빠지는 패턴으로 나타난다.

**클래스를 동적으로 대량 생성하는 프레임워크**(프록시 남발, 스크립트 엔진, 요청마다 람다를 새로 만드는 구조)에서 실제로 발생하는 장애 유형이다. 상태 확인은 `jcmd <pid> Compiler.codecache`로 한다.

### 3-6. 프로파일 오염 — 잘못 지켜보고 번역하면

JIT의 최적화는 관찰에 기반하므로, **관찰이 실제와 다르면 최적화도 틀린다.**

공용 유틸 메서드가 기동 초기에 특정 패턴으로만 호출되면 그 관찰 기록을 근거로 컴파일된다. 이후 다른 패턴이 들어오면 역최적화되거나, 역최적화까지는 안 가더라도 그 워크로드에 최적이 아닌 코드로 계속 돈다.

이것을 **프로파일 오염(profile pollution)**이라고 한다. 실무에서 걸리는 자리가 두 곳이다.

- **예열 트래픽이 실제 트래픽과 다를 때.** 기동 시 헬스체크 URL만 수천 번 때리면, 실제 API 경로가 아니라 헬스체크 경로가 최적화된다.
- **벤치마크를 한 JVM에서 여러 개 돌릴 때.** 앞 벤치마크가 남긴 타입 프로파일이 뒤 벤치마크의 컴파일에 영향을 준다. JMH가 `@Fork`로 JVM을 분리하는 이유다(3-2).

### 3-7. 관측 수단

| 수단 | 무엇을 보는가 |
|---|---|
| `-XX:+PrintCompilation` | 어느 메서드가 언제 어느 계층으로 컴파일됐는지, 그리고 역최적화(`made not entrant`) 이벤트 |
| `-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining` | 각 호출이 인라이닝됐는지, 안 됐다면 그 이유(too big, not compilable 등) |
| JFR의 Compilation 이벤트 | 운영 환경에서 낮은 오버헤드로 컴파일 활동 기록. JITWatch로 시각화 |
| `jcmd <pid> Compiler.codecache` | 코드 캐시 사용량 — 3-5의 고갈 여부 확인 |

`PrintCompilation`은 출력이 매우 많으므로 운영 상시 사용에는 부적합하다. 재현 환경에서 문제 구간만 잡아 보는 용도로 쓴다.

### 3-8. 워밍업의 근본 대안 — 무엇을 저장하는가

문제의 본질은 하나다. **JVM은 재시작할 때마다 지난번에 했던 일을 전부 처음부터 다시 한다.** 번역가 비유로 말하면, 서버를 껐다 켤 때마다 **번역본과 관찰 노트를 전부 버리고 백지에서 시작**하는 것이다.

세 가지 대안이 있고, 발상은 전부 같다 — **"어차피 매번 똑같이 하는 일이면 한 번 해서 저장해 두고 재사용하자."** 다른 것은 **어디까지 저장하느냐**뿐이다.

#### CDS / AppCDS — "책 준비 작업"을 저장

JVM이 기동할 때 번역 이전에 하는 일이 있다. 수천 개의 `.class` 파일을 **읽고, 검증하고, JVM 내부용 자료구조로 조립**하는 클래스 로딩이다. 그리고 **이 조립 결과물은 매번 100% 똑같다.**

**CDS(Class Data Sharing)**는 이 조립 결과를 한 번 만들어 아카이브 파일로 저장해 두고, 다음 기동부터는 조립을 생략하고 메모리에 그대로 얹는다. 즉석밥과 같은 원리다 — 밥 짓는 과정을 생략하고 데우기만 한다.

- **CDS**: JDK 기본 클래스(String, HashMap 등)만 대상. 요즘 JDK에는 기본 탑재돼 있다.
- **AppCDS**: 대상을 **내 애플리케이션 클래스까지** 확장한 것(App + CDS).

**한계가 분명하다. "책 준비"만 빨라진다.** 번역(JIT)과는 무관하므로 기동 후 코드는 여전히 인터프리터에서 시작한다. **기동 시간은 줄지만 워밍업 구간은 그대로다.**

#### AOT 캐시 / Project Leyden — "관찰 노트"까지 저장

**Project Leyden**은 "런타임에 하던 일을 앞 시점으로 옮기자"를 목표로 하는 OpenJDK 공식 프로젝트다. **훈련 실행(training run)** 방식을 쓴다.

```
1. 배포 전에 앱을 한 번 실제로 돌려 본다 (녹화 모드)
2. "어떤 클래스가 로딩됐고, 어떤 메서드가 뜨거웠고,
    어떤 타입이 지나갔는지"를 AOT 캐시 파일로 저장
3. 실제 기동 때 그 캐시를 얹고 시작
   -> 지난 실행의 기억을 이어받은 상태로 출발한다
```

단계적으로 확장되고 있다.

- **JDK 24** — 클래스 로딩·링킹 결과를 캐시한다. AppCDS의 강화판 수준이다.
- **JDK 25** — **JIT의 관찰 노트(프로파일)까지 캐시한다.** 기동 직후부터 "어디가 핫스팟이고 어떤 타입이 오는지"를 이미 알고 있으므로, 다시 지켜보는 기간 없이 곧바로 고품질 컴파일에 들어간다. **워밍업 구간 자체가 짧아진다.**

핵심 특징은 **여전히 보통의 JIT JVM이라는 점**이다. 최고 속도(피크 성능)는 그대로이고 **거기 도달하는 시간만 단축된다.** 잃는 것이 거의 없는 접근이다.

#### GraalVM Native Image — 아예 "출판 전에 전부 번역"

가장 급진적인 방식이다. **빌드 시점에 자바 코드를 통째로 기계어로 번역해 JVM 없이 혼자 도는 네이티브 실행 파일**을 만든다. 통역사도 번역가도 배에 태우지 않는다.

**얻는 것**은 기동 속도와 메모리다. JVM 기동과 워밍업이 통째로 없어져 **밀리초 단위로 뜨고** 메모리 사용량이 크게 준다. **서버리스**(요청마다 새로 뜨는 환경), CLI 도구, 수시로 스케일 아웃하는 쿠버네티스 환경에 어울린다.

**잃는 것**이 두 가지다.

첫째, **"지켜본 다음 최적화"를 포기한다.** 번역이 실행 전에 끝나므로 관찰 기반 베팅(탈가상화 등)이 원천적으로 불가능하다. 그래서 **충분히 예열된 JIT에 비해 피크 성능은 대체로 낮다.**

둘째, **"닫힌 세계(closed world)" 가정이 필요하다.** 빌드 시점에 실행될 모든 코드가 확정돼야 하므로, 리플렉션·동적 프록시·런타임 클래스 생성은 설정 파일로 미리 알려 줘야 한다. 스프링이 별도의 AOT 처리 단계를 지원하는 이유가 이것이다. 빌드 시간도 매우 길다.

보완책으로 **PGO(profile-guided optimization)**가 있다. 계측용 빌드를 한 번 돌려 프로파일을 수집한 뒤 반영해 재빌드하는 방식으로, **"지켜본 다음 번역"을 빌드 단계에서 흉내 내는 것**이다. 그래도 실행 중에 계속 관찰하고 고쳐 쓰는 JIT만큼 유연하지는 않다.

#### 셋을 나란히 놓고 보면

| | 저장하는 것 | 기동 속도 | 워밍업 단축 | 피크 성능 |
|---|---|---|---|---|
| **CDS/AppCDS** | 클래스 조립 결과 | 조금 개선 | 없음 | 그대로 |
| **Leyden AOT 캐시** | 클래스 + **관찰 노트(프로파일)** | 크게 개선 | 크게 단축 | 그대로 |
| **Native Image** | **번역 완제품(실행 파일)** | 밀리초 | 개념 자체가 없음 | **대체로 더 낮음** |

선택 기준은 한 줄로 정리된다. **오래 떠서 최고 처리량이 중요한 서버라면 JIT + Leyden 방향, 수시로 켜지고 꺼지는 서버리스라면 Native Image**다.

### 3-9. AOT 캐시와 파드 오토스케일링

오토스케일링에는 고질적인 문제가 하나 있다. 새 파드가 뜰 때마다 JVM이 백지에서 시작하므로, **스케일 아웃이 필요한 순간(트래픽 급증)에 하필 제일 느린 파드가 투입된다.** 부하를 나눠 지려고 띄운 파드가 오히려 p99를 끌어올린다.

AOT 캐시가 정확히 이 시나리오를 겨냥한다. 핵심은 **AOT 캐시가 "실행 중인 서버"가 아니라 "파일"이라는 것**이다. 파일이니까 컨테이너 이미지에 구울 수 있다.

```
[CI/CD 파이프라인]
1. 앱 빌드
2. 훈련 실행: 앱을 잠깐 띄우고 대표 트래픽을 태워 app.aot 캐시 파일 생성
3. 캐시 파일을 컨테이너 이미지에 포함시켜 빌드

[운영 - 오토스케일링 발생]
새 파드 기동 -> 이미지 안의 캐시를 얹고 시작
-> 클래스 로딩 생략 + 핫스팟을 이미 아는 상태로 출발 -> 바로 고품질 컴파일
```

**훈련은 빌드 때 한 번, 혜택은 스케일 아웃으로 뜨는 모든 파드가 받는다.** 100번째 파드도 첫 파드와 똑같이 "예열된 기억"을 갖고 시작한다.

현실적인 조건과 한계가 넷이다.

1. **"줄인다"이지 "없앤다"가 아니다.** 컴파일 자체는 여전히 기동 후에 일어난다. 관찰 기간을 건너뛸 뿐이고 JVM 프로세스 기동 시간도 남는다. 기대치는 "몇 분 예열 → 수십 초" 수준이다. 밀리초 기동이 필요하면 Native Image나 CRaC의 영역이다.
2. **훈련 트래픽이 실제 트래픽과 비슷해야 한다.** 3-6의 프로파일 오염이 그대로 적용된다. 다만 치명적이지는 않다 — 여전히 JIT JVM이므로 실행하면서 계속 다시 관찰하고 재컴파일한다. 최악의 경우에도 "캐시 없는 것과 비슷한 수준"으로 떨어질 뿐이다.
3. **캐시는 환경에 묶인다.** 같은 JDK 버전, 같은 클래스패스, 같은 주요 JVM 옵션에서만 유효하다. 코드가 바뀌면 캐시도 재생성해야 하므로 **"빌드마다 훈련 실행"을 파이프라인에 넣는 것이 전제**이고, 그만큼 빌드 시간이 늘어난다.
4. **JDK 버전 제약.** 클래스 캐시는 24부터, 알맹이인 프로파일 캐시는 25부터다. JDK 17이나 21에서는 아직 못 쓴다.

### 3-10. 운영 파드에서 캐시 수확하기 — CI 훈련의 대안

"오토스케일링은 같은 환경의 파드를 늘리는 것이니, 훈련 없이 **기존 파드가 만든 캐시**를 새 파드가 받으면 되지 않나?"

맞는 직관이고 실제로 가능하다. 같은 이미지이므로 캐시 호환성이 자동으로 보장되고, 기존 파드가 받던 트래픽은 **진짜 운영 트래픽**이라 프로파일 대표성이 CI의 합성 트래픽보다 좋다. 프로파일 오염 걱정이 원천적으로 없다.

다만 걸림돌이 둘 있다.

**캐시는 아무 때나 못 꺼낸다.** 실행 중인 JVM에서 즉석으로 뽑는 것이 아니라, 파드를 **녹화 모드로 시작**해 두어야 하고(`-XX:AOTMode=record` 계열), **파일은 JVM이 정상 종료될 때 기록된다.** 쿠버네티스의 SIGTERM과 grace period를 활용해 정상 종료 타이밍을 확보해야 한다.

**전달 배관이 필요하다.** 캐시는 파드 로컬에 떨어지는데 파드는 죽으면 사라지므로, 공유 저장소(S3나 PVC)와 init container 구성이 필요하다.

```
[1세대 파드] 녹화 모드로 기동 -> 운영 트래픽 처리
     |  (종료 또는 롤링 시)
     v
캐시 파일 생성 -> 공유 저장소 업로드

[새 파드] init container가 캐시 다운로드 -> 얹고 기동 (-XX:AOTMode=on)
```

제약이 하나 더 있다. **새 버전 배포 직후에는 캐시가 없다.** 캐시는 빌드에 묶이므로 구버전 파드의 캐시를 신버전에 쓸 수 없다. 배포 직후 1세대 파드들은 캐시 없이 뜨고, 그 이후 파드부터 혜택을 받는다.

| | CI 훈련 (이미지에 굽기) | 운영 파드에서 수확 |
|---|---|---|
| 프로파일 품질 | 합성 트래픽 — 대표성에 한계 | **진짜 운영 트래픽 — 최상** |
| 첫 파드부터 혜택 | **받는다** (이미지에 이미 있음) | 못 받는다 (1세대는 캐시 없음) |
| 필요한 배관 | 파이프라인에 훈련 단계 추가 | 공유 저장소 + init container + 종료 훅 |
| 재현성·단순성 | 빌드 산출물이라 단순 | 런타임 상태에 의존 — 관리 포인트 증가 |

정석은 **하이브리드**다. CI 훈련 캐시를 이미지에 구워 첫 파드를 커버하고, 운영 수확 캐시가 저장소에 생기면 그것을 우선 사용해 품질을 올린다.

### 3-11. CRaC — "예열된 파드 복제"를 끝까지 밀어붙인 것

**CRaC(Coordinated Restore at Checkpoint)**는 "기존 파드가 이미 예열돼 있으니 결과물을 복제하자"는 발상을 프로파일 **파일** 수준이 아니라 **프로세스 전체** 수준으로 밀어붙인 방식이다.

**예열이 끝난 JVM 프로세스를 통째로 스냅샷(메모리 덤프)으로 찍어 두고, 새 파드는 그 스냅샷을 복원하며 시작한다.** 번역본과 관찰 노트뿐 아니라 **커넥션 풀, 캐시 같은 애플리케이션 상태까지** 예열된 채로 밀리초에서 초 단위에 기동한다.

대가와 주의점이 있다.

- **스냅샷 전에 열린 리소스(소켓, 파일)를 정리했다가 복원 후 다시 여는 코드가 필요하다.** 스냅샷 안의 소켓 핸들은 복원 시점에 이미 죽어 있기 때문이다. Spring Boot 3.2 이상이 프레임워크 차원에서 이 훅을 지원한다.
- **스냅샷에 힙이 통째로 들어가므로 비밀번호나 토큰이 파일에 남는다.** 힙 덤프와 똑같은 보안 문제이므로 저장소 접근 통제가 필요하다.
- JDK 25를 아직 못 쓰는 환경(17, 21)에서 오토스케일링 워밍업을 줄이는 현실적인 대안이다.

| 상황 | 추천 방향 |
|---|---|
| JDK 25 이상 사용 가능 | **AOT 캐시** — 코드 수정 없이 파이프라인에 훈련 단계만 추가 |
| JDK 17/21 + Spring Boot | **CRaC** 검토, 또는 쿠버네티스 레벨 완화(readiness probe + 예열 요청, startupProbe) |
| 서버리스급 즉시 기동이 필요 | Native Image (피크 성능 트레이드오프 감수) |

## 4. 꼬리질문 대비 포인트

### "부하 테스트에서 워밍업을 왜 해야 하나요? 안 하면 어떤 숫자가 나오나요?"

**예열 없이 재면 인터프리터의 속도를 재게 된다.**

JVM은 기동 직후 모든 코드를 Level 0(인터프리터)에서 시작한다. 자주 호출되는 메서드만 C1을 거쳐 C2로 올라가는데, 여기까지 도달하려면 그 코드가 수천 번은 실행돼야 한다. 그 전에 측정하면 **정상 상태보다 몇 배 느린 숫자**가 나온다.

게다가 예열 구간에는 **컴파일 작업 자체가 CPU를 쓴다.** 애플리케이션과 컴파일러 스레드가 CPU를 나눠 쓰므로 이중으로 불리한 조건이다.

실무에서 이것이 왜 위험한지가 답의 핵심이다. **예열 구간을 섞어 잰 숫자로 용량 산정을 하면 필요한 인스턴스 수를 과대 추정하고, 반대로 예열된 상태만 재고 배포 직후를 고려하지 않으면 롤링 배포 때마다 타임아웃이 난다.** 둘 다 재고 구분해서 봐야 한다.

마이크로벤치마크라면 JMH를 쓴다고 답한다. 이유를 셋으로 말하면 좋다 — **예열 반복을 강제하고, 결과를 소비시켜 죽은 코드 제거를 막고, `@Fork`로 JVM을 분리해 프로파일 오염을 막는다.**

### "결과를 안 쓰는 벤치마크가 왜 0에 가까운 숫자를 내나요?" (가산점 포인트)

**dead code elimination(죽은 코드 제거)** 때문이다.

JIT는 "결과가 관측되지 않는 계산"은 실행해도 프로그램의 동작이 달라지지 않는다고 판단한다. `Math.sqrt(i)`의 결과를 아무도 안 쓰면 그 호출을 지우고, 본문이 빈 루프는 루프째로 지운다. 그래서 1억 번 도는 루프가 0ms에 끝난다.

여기에 하나 더 얹으면 좋다. **상수 폴딩(constant folding)**도 같은 함정이다. 입력이 `static final` 상수면 JIT가 컴파일 시점에 결과를 미리 계산해 버려서 실행 시점에는 아무 연산도 남지 않는다. JMH 예제에서 `@State` 필드를 `final`이 아닌 일반 필드로 두는 이유가 이것이다.

대응은 **결과를 소비시키는 것**이다. `@Benchmark` 메서드에서 값을 반환하거나 `Blackhole.consume()`으로 넘긴다. JMH는 이 값을 JIT가 지울 수 없는 형태로 소비해 준다.

### "역최적화는 왜 일어나고, 자주 일어나면 어떻게 확인하나요?"

**역최적화는 실패가 아니라 설계의 일부**라는 것부터 말한다. C2의 최적화는 "이 호출 지점엔 `Circle`만 온다" 같은 관찰 기반 베팅인데, 무를 수 있어야 베팅을 걸 수 있다. **무르는 장치가 있어서 정적 컴파일러보다 과감할 수 있는 것**이다.

가정이 깨지는 계기는 셋이다.

- **예상 밖의 타입이 들어옴** — 가드에 걸린다.
- **새 클래스 로딩** — "구현체가 하나뿐"이라는 가정이 깨진다.
- **예외 경로가 처음으로 실행됨** — "여긴 안 온다"고 가정하고 코드를 안 만들어 뒀던 분기다.

그러면 컴파일된 코드가 `made not entrant`(더 이상 진입 불가)로 표시되고, 실행은 인터프리터 프레임으로 되돌아가 이어진다(2-3의 uncommon trap).

**확인 수단은 `-XX:+PrintCompilation`이다.** 같은 메서드에 대해 컴파일과 `made not entrant`가 번갈아 반복적으로 찍히면 deopt storm이다. 운영에서는 JFR의 Compilation 이벤트로 낮은 오버헤드로 관찰한다.

### "인터페이스 구현체를 여러 개 두는 설계가 성능에 영향을 주나요?" (시니어 변별 포인트)

**영향은 있지만, 그것 때문에 설계를 먼저 바꾸지는 않는다.** 이 두 가지를 다 말해야 한다.

영향의 실체는 **메가모픽 call site**다. JIT는 호출 지점별로 "여기 실제로 오는 타입"을 기억하는데, **한두 개까지는 가드를 붙여 직접 호출로 바꾸고 인라이닝까지 한다.** 세 개 이상이 되면 예측이 불가능해 **매번 타입을 조회하는 간접 호출로 돌아가고, 인라이닝이 막히면서 그 너머의 최적화 연쇄도 전부 끊긴다.**

중요한 것은 **"구현체가 몇 개인가"가 아니라 "하나의 호출 지점에 몇 종류가 지나가는가"**라는 점이다. 구현체가 열 개여도 각 호출 지점에는 한 종류만 온다면 전부 단형성이다. 반대로 구현체가 셋인데 하나의 디스패치 루프에서 전부 돌면 그 한 줄이 메가모픽이 된다.

판단 순서는 이렇다.

1. 대부분의 코드에서 이 비용은 무시할 수 있다. **다형성의 유지보수 이득이 훨씬 크다.**
2. 프로파일링으로 **그 call site가 실제 병목임을 확인**한 뒤에 손댄다. `-XX:+PrintInlining`으로 인라이닝이 실제로 막혔는지 확인할 수 있다.
3. 손댈 때도 다형성을 없애기보다 **핫 경로만 분리**하는 방식을 먼저 고려한다.

"성능 때문에 인터페이스를 쓰지 않겠다"는 답은 감점이다. **측정 없이 하는 최적화가 문제**라는 태도가 이 질문이 보려는 것이다.

### "배포 직후 타임아웃이 나는데, GC 문제인지 JIT 워밍업인지 어떻게 구분하나요?"

증상이 비슷해서 헷갈리는 실제 상황이다. 구분 기준이 몇 가지 있다.

**시간 패턴이 다르다.** JIT 워밍업은 **기동 직후부터 시작해 시간이 지나며 단조롭게 좋아진다.** GC 문제는 특정 시점에 스파이크가 뾰족하게 튀고 그 사이는 정상이다. 응답시간 그래프의 모양이 "우하향 곡선"이면 워밍업, "평평하다가 가끔 뾰족"이면 GC 쪽이다.

**증거를 대조한다.** GC 로그의 pause 발생 시각과 느린 요청의 시각이 겹치는지 본다. 안 겹치면 GC가 아니다. 반대로 `-XX:+PrintCompilation`의 컴파일 활동이 그 구간에 집중돼 있으면 워밍업 쪽이다.

**CPU 사용 양상도 단서다.** 워밍업 구간에는 컴파일러 스레드가 CPU를 쓰므로, 요청 처리량 대비 CPU가 비정상적으로 높다.

**대응이 다르다는 점까지 말하면 좋다.** 워밍업이면 램프업이나 예열 요청으로, 나아가 AOT 캐시나 CRaC로 접근한다(3-8 이후). GC면 힙 크기나 GC 선택의 문제로 접근한다. **원인을 구분하지 않고 양쪽 옵션을 동시에 만지는 것**이 가장 흔한 실수다.

## 한 줄 요약

JVM은 "빨리 시작하기"와 "빨리 돌기"를 동시에 못 가지므로 **인터프리터 → C1(빠른 번역 + 관찰 수집) → C2(관찰 기반 공격적 최적화)**로 시간축에 펼쳐 둘 다 취하고, C2가 정적 컴파일러보다 과감할 수 있는 근거는 **베팅하고 틀리면 무를 수 있다는 것(역최적화)** 하나다 — 인라이닝으로 분석 시야를 열고, 한 타입만 오는 호출은 직접 호출로 바꾸고(탈가상화), 안 새나가는 객체는 낱개 변수로 분해하는(스칼라 치환) 대신, **기동 직후엔 느리고(워밍업 → 램프업·예열 요청, 근본 대안은 AOT 캐시·CRaC), 베팅이 틀리면 무르고 다시 하며(역최적화), 타입이 셋 이상 섞이면 포기하고(메가모픽), 번역본 보관함이 차면 서서히 죽는다(코드 캐시 고갈)** — 그리고 이 모든 것이 성능 측정을 오염시키므로 **예열 없이 잰 숫자와 결과를 안 쓰는 벤치마크의 숫자는 둘 다 거짓이고, 그래서 JMH를 쓴다.**
