# JIT 컴파일러 — 동작 원리와 성능 영향 (쉬운 용어 버전)

> 핵심 관전 포인트: **JIT는 "일단 통역으로 시작하고, 자주 실행되는 코드만
> 실행을 지켜본 뒤 그 관찰 결과를 근거로 기계어로 번역"하는 방식이다.
> 덕분에 예열된 후의 성능은 매우 좋지만, 대가로 ① 시동 직후엔 느리고(워밍업)
> ② 관찰 기반 베팅이 틀리면 순간 느려지며(역최적화) ③ 번역본 보관함이 차면
> 성능이 서서히 죽는다(코드 캐시 고갈). 면접 포인트는 최적화 이름 나열이 아니라
> "런타임 관찰 → 베팅 → 틀리면 무르기"라는 원리와 실무 증상(배포 직후 스파이크)을
> 연결하는 것.**

---

## 0. 질문 + 의도

**질문**: "JIT 컴파일러의 동작(C1/C2, 인라이닝, 탈최적화)이 성능에 미치는
영향을 설명해주세요."

**출제 의도**: 배포 직후 latency 상승, 부하 테스트의 워밍업 필요성 같은
"측정을 오염시키는 요인"을 아는지 본다. 이걸 모르면 성능 측정 자체를
잘못해서 잘못된 결론으로 튜닝한다.

## 용어 사전 — 본문 읽기 전에

| 용어 | 쉬운 말로 |
|---|---|
| 인터프리터 | 바이트코드를 한 줄씩 그때그때 해석해 실행하는 방식 (동시통역사) |
| JIT 컴파일 | 자주 쓰는 코드를 기계어로 미리 번역해 두는 것 (번역가) |
| 핫스팟(hotspot) | 자주 실행되는 뜨거운 코드 구간 |
| call site (호출 지점) | 메서드를 호출하는 코드의 "그 줄" |
| 인라이닝 | 호출 대신 메서드 내용을 그 자리에 복사해 넣기 |
| 가상 메서드 호출 | 실제 타입에 따라 실행 코드가 달라지는 호출 (오버라이딩) |
| 모노/바이/메가모픽 | 그 호출 줄에 실제로 오는 타입이 1개 / 2개 / 3개 이상 |
| 탈가상화 | "매번 타입 확인"을 "한 타입으로 가정한 직접 호출"로 바꾸기 |
| 추측 실행 | 관찰 결과를 근거로 "아마 이럴 것"이라 베팅하고 빠른 길 만들기 |
| 역최적화(deoptimization) | 베팅이 틀렸을 때 번역본을 버리고 통역 모드로 복귀 |
| 탈출 분석 | 객체가 메서드 밖으로 새나가는지 조사 |
| 스칼라 치환 | 안 새나가는 객체를 힙에 안 만들고 낱개 변수(int 등)로 분해 |
| 워밍업 | 번역이 쌓여서 제 속도가 날 때까지의 예열 구간 |
| 코드 캐시 | 번역된 기계어를 보관하는 전용 메모리 |
| AOT (Ahead-Of-Time) | 실행 전에 미리 번역하는 방식 (JIT의 반대말) |
| 훈련 실행 (training run) | 캐시를 만들기 위해 배포 전에 앱을 한 번 돌려보는 것 |
| AOT 캐시 | 훈련 실행의 클래스 로딩 결과 + 관찰 노트를 저장한 파일 (JDK 24/25, Leyden) |
| CRaC | 예열 끝난 JVM 프로세스를 통째로 스냅샷 → 복원하며 기동하는 기술 |

## 1. 기본 동작 — 통역사와 번역가

자바 프로그램 실행을 "외국어 문서 읽기"에 비유하면:

- **인터프리터 = 동시통역사.** 문장을 만날 때마다 그 자리에서 한 줄씩 통역.
  바로 시작할 수 있지만, 같은 문장을 100번 만나면 100번 다시 통역한다. 느리다.
- **JIT 컴파일러 = 번역가.** 자주 나오는 페이지를 발견하면 아예 번역해서
  붙여둔다. 번역하는 데 시간은 걸리지만, 다음부터는 읽기만 하면 되니 빠르다.

JVM은 둘을 섞어 쓴다. **처음엔 전부 통역(인터프리트)으로 시작**하면서
메서드 호출 횟수·루프 반복 횟수를 세고, 임계치를 넘은 **핫스팟만 골라
기계어로 번역(컴파일)**한다.

왜 전부 번역하지 않는가 — 실행 시간의 대부분은 극히 일부 코드가 차지하므로
(파레토), **실제로 뜨거운 곳에만 번역 비용을 집중**하는 게 이득이기 때문.

### 계층형 컴파일 (Tiered Compilation) — 2단 로켓

"빨리 어느 정도 빨라지게 → 데이터가 쌓이면 최대로 빠르게"의 2단계. 현재 기본값.

| 단계 | 담당 | 특징 |
|---|---|---|
| Level 0 | 인터프리터 | 즉시 실행 + "어떻게 실행되는지" 기록 시작 |
| Level 1~3 | **C1** 컴파일러 | 빠르게 번역, 가벼운 최적화 + 관찰 코드 삽입 |
| Level 4 | **C2** 컴파일러 | 느리게 번역, 관찰 기록을 근거로 공격적 최적화 |

## 2. JIT가 빠르게 만드는 방법 — 핵심은 "지켜본 다음 번역한다"

JIT의 진짜 무기는 번역 자체가 아니라, **실제로 프로그램이 어떻게 돌아가는지
지켜본 다음에 번역한다**는 점. 미리 번역하는 방식(AOT)은 "실제로 어떻게
쓰이는지"를 모르니 아래의 과감한 최적화들을 못 한다.

### 2-1. 인라이닝 — 가장 중요한 최적화

메서드를 호출하는 것 자체에 비용이 든다(점프했다 돌아오기). 짧은 메서드는
호출하는 대신 **내용을 호출한 자리에 복사해 붙여넣는다**.

```java
// 개발자가 쓴 코드
String name = user.getName();   // getName()을 "호출"

// JIT가 바꾼 코드 (개념상)
String name = user.name;        // 호출 없이 내용물을 그 자리에 박아넣음
```

getter/setter를 마음껏 써도 느려지지 않는 이유.

**진짜 이득은 "다른 최적화의 문을 여는 것".** JIT는 코드를 한 덩어리 단위로
분석하는데, 메서드 호출이 있으면 저 너머가 안 보여서 분석이 끊긴다.
인라이닝으로 다 펼쳐 놓으면 전부 한 덩어리가 되어, 그제서야 보이는 낭비를
지울 수 있다:

```java
// 인라이닝 전: check() 안에서 뭘 하는지 몰라 손을 못 댐
if (check(x)) { ... }

// 인라이닝 후: "x는 위에서 항상 양수 → 이 if는 항상 true → if 자체를 삭제"
```

### 2-2. 탈가상화 — "매번 타입 확인"을 베팅으로 없애기

```java
for (Shape s : shapes) {
    s.draw();    // ← 이 줄이 call site (호출 지점)
}
```

`s.draw()`는 `s`가 `Circle`이냐 `Square`냐에 따라 실행되는 코드가 달라지는
**가상 메서드 호출**(오버라이딩). 매번 "실제 타입이 뭐지?"를 확인해야 하니
직접 호출보다 느리다.

JIT가 지켜봤더니 이 줄에 **실제로는 `Circle`만 계속 온다**(= 모노모픽)면,
이렇게 **베팅**한다:

```java
// JIT의 베팅: "지금까지 전부 Circle이었으니 앞으로도 Circle일 거야"
if (s instanceof Circle) {
    // Circle.draw()를 직접 실행 + 인라이닝까지 (빠름)
} else {
    // 베팅 실패! 번역본 버리고 원래 방식으로 복귀 (역최적화)
}
```

확실하진 않지만 관찰을 근거로 빠른 길을 만들어두는 것 — 이게 **추측 실행**.

### 2-3. 탈출 분석 + 스칼라 치환 — 객체를 아예 안 만들기

객체가 **메서드 안에서 태어나 밖으로 나가지 않고 안에서 죽는다**면
(= 탈출하지 않으면), 힙에 만들 필요가 없다. **낱개 변수로 분해**해 버린다:

```java
// 개발자가 쓴 코드
Point p = new Point(3, 5);
return p.x + p.y;

// JIT가 바꾼 코드 (개념상): 객체가 사라지고 낱개 값만 남음
int x = 3;                       // 힙 할당 없음, GC 부담 없음
int y = 5;
return x + y;
```

객체(값의 묶음)를 스칼라(int 같은 낱개 값)로 바꿔치기해서 **스칼라 치환**.
"루프 안에서 임시 객체 좀 만들어도 생각보다 괜찮다"의 근거.
탈출 안 하는 객체로 잡는 락도 지워준다(락 제거, lock elision).

### 2-4. 나머지 최적화들

- **루프 최적화** — 반복문 펼치기(언롤링), 배열 범위 검사 제거,
  CPU의 묶음 연산 명령 활용(벡터화)
- **인트린식** — `System.arraycopy`, `Math.min` 같은 유명 메서드를
  CPU 전용 명령으로 통째로 치환

이 덕분에 충분히 예열된 JVM의 핫 코드는 C/C++에 근접한 처리량을 낸다.

## 3. [면접] 대가와 부작용 — 실무에서 체감하는 5가지

### 3-1. 워밍업 — 배포 직후가 느리다

기동 직후엔 모든 코드가 통역 모드라 느리고, 번역 작업 자체도 CPU를 쓴다.

- **실무 증상: 배포/재시작 직후 몇 분간 레이턴시 스파이크, 첫 요청들 타임아웃**
- 대응: 배포 시 트래픽을 서서히 올리기(램프업), 헬스체크 통과 전 예열 요청 태우기
- **벤치마크는 반드시 예열 후 측정** — JMH가 워밍업 반복을 강제하는 이유.
  예열 없이 재면 통역사의 속도를 재는 것
- 근본 대안: CDS/AppCDS, AOT 캐시(Project Leyden), GraalVM Native Image
  (→ 4장에서 상세히)

### 3-2. 역최적화 — 베팅이 틀리는 순간

C2의 최적화는 추측(베팅)에 기반한다. 새 클래스가 로딩되거나 예상 밖 타입이
들어와 **가정이 깨지면 번역본을 찢고 통역 모드로 복귀** 후 재번역.
순간 성능 저하 + 재예열이 발생하고, 반복되면(deopt storm) 지속적 성능 문제.

### 3-3. 메가모픽 — 다형성의 숨은 비용

한 호출 지점에 오는 타입이 1개(모노모픽)·2개(바이모픽)까지는 베팅 + 인라이닝이
되지만, **3개 이상(메가모픽)이면 "가정 자체가 불가능"이라 최적화를 포기**하고
매번 타입 조회로 간다. 같은 인터페이스의 구현체가 여럿 섞여 지나가는 핫 루프는
눈에 안 보이는 성능 절벽이 될 수 있다.

### 3-4. 코드 캐시 고갈 — 번역본 보관함이 가득 차면

번역된 기계어는 **코드 캐시**(기본 240MB, `-XX:ReservedCodeCacheSize`)에
보관된다. 가득 차면 `CodeCache is full. Compiler has been disabled` 경고와
함께 **이후 번역이 중단** → 새로 뜨거워진 코드가 전부 통역 모드로 돌아
전체 성능이 서서히 떨어진다. 클래스를 동적 생성하는 프레임워크(프록시 남발)
에서 실제 발생하는 장애 유형.

### 3-5. 프로파일 오염 — 잘못 지켜보고 번역하면

공용 유틸 메서드가 초기에 특정 패턴으로만 호출되면 그 관찰 기록으로 번역되고,
이후 다른 패턴이 오면 역최적화되거나 최적이 아닌 코드로 돈다.
예열 트래픽이 실제 트래픽과 다르면 같은 문제.

## 4. [면접] 워밍업의 근본 대안 — CDS vs Leyden vs Native Image

문제의 본질: JVM은 재시작할 때마다 지난번에 했던 일을 전부 처음부터 다시 한다.
번역가 비유로, 서버를 껐다 켤 때마다 **번역본과 관찰 노트를 전부 버리고
백지에서 시작**하는 것. 세 대안은 전부 "어차피 매번 똑같이 하는 일이면
한 번 해서 저장해두고 재사용하자"인데, **어디까지 저장하느냐**가 다르다.

### 4-1. CDS / AppCDS — "책 준비 작업"을 저장

JVM이 기동할 때 번역 이전에 하는 일: 수천 개의 `.class` 파일을
**읽고 → 검증하고 → JVM 내부용 자료구조로 조립**하는 클래스 로딩.
결과물은 매번 100% 똑같다.

**CDS(Class Data Sharing)** 는 이 조립 결과물을 한 번 만들어 파일(아카이브)로
저장해두고, 다음 기동부터는 조립을 생략하고 메모리에 그대로 얹는다.
즉석밥 원리 — 밥 짓는 과정(로딩·검증)을 생략하고 데우기만.

- **CDS**: JDK 기본 클래스(String, HashMap 등)만 대상. 요즘 JDK엔 기본 탑재
- **AppCDS**: 대상을 **내 애플리케이션 클래스까지** 확장 (App + CDS)

한계: **"책 준비"만 빨라진다.** 번역(JIT)과는 무관해서, 기동 후 코드는 여전히
통역 모드에서 시작 → **기동 시간은 줄지만 워밍업은 그대로**.

### 4-2. AOT 캐시 / Project Leyden — "번역가의 관찰 노트"까지 저장

**Project Leyden** = OpenJDK 공식 프로젝트. 목표를 한 문장으로:
"런타임에 하던 일을 앞 시점으로 옮기자". **훈련 실행(training run)** 방식을 쓴다:

1. 배포 전에 앱을 **한 번 실제로 돌려본다** (녹화 모드)
2. "어떤 클래스가 로딩됐고, 어떤 메서드가 뜨거웠고, 어떤 타입이 지나갔는지"를
   **AOT 캐시 파일로 저장**
3. 실제 기동 때 캐시를 얹고 시작 → **지난 실행의 기억을 이어받은 상태로 출발**

단계적 확장:

- **JDK 24** — 클래스 로딩·링킹 결과를 캐시 (AppCDS의 강화판 수준)
- **JDK 25** — **JIT의 관찰 노트(프로파일)까지 캐시.** 기동 직후부터
  "어디가 핫스팟인지, 어떤 타입이 오는지"를 이미 알고 있으니 다시 지켜보는
  기간 없이 바로 고품질 번역(C2)에 들어간다 → **워밍업 구간 자체가 단축**

핵심 특징: **여전히 보통의 JIT JVM이다.** 최고 속도(피크 성능)는 그대로,
거기 **도달하는 시간만 단축** — 잃는 게 거의 없는 접근.

### 4-3. GraalVM Native Image — 아예 "출판 전에 전부 번역"

가장 급진적. **빌드 시점에 자바 코드를 통째로 기계어로 번역해서, JVM 없이
혼자 도는 네이티브 실행 파일**을 만든다. 통역사도 번역가도 배에 안 태운다.

**얻는 것:**

- 기동 **밀리초 단위** (JVM 기동 + 워밍업이 통째로 없음), 메모리 대폭 감소
- 어울리는 곳: **서버리스**(요청마다 새로 뜨는 환경), CLI 도구,
  수시로 스케일 아웃하는 k8s 환경

**잃는 것:**

- **"지켜본 다음 최적화"를 포기.** 번역이 실행 전에 끝나므로 관찰 기반
  베팅(탈가상화 등)이 불가 → 충분히 예열된 JIT 대비 **피크 성능은 보통 낮다**
- **"닫힌 세계" 가정** — 빌드 시점에 모든 코드가 확정돼야 하므로 리플렉션·
  동적 프록시·런타임 클래스 생성은 설정으로 미리 알려줘야 함.
  스프링이 별도 AOT 처리를 지원하는 이유
- 빌드가 매우 느림 (수 분)

보완책 **PGO**(profile-guided optimization): 계측용 빌드를 한 번 돌려
프로파일을 수집한 뒤 반영해 재빌드 — "지켜본 다음 번역"을 빌드 단계에서
흉내 내는 것. 그래도 실행 중 계속 관찰·수정하는 JIT만큼 유연하진 않다.

### 4-4. 비교 — 무엇을 저장하는가

| | 저장하는 것 | 기동 속도 | 워밍업 단축 | 피크 성능 |
|---|---|---|---|---|
| **CDS/AppCDS** | 클래스 조립 결과 | 조금 개선 | ✕ (없음) | 그대로 |
| **Leyden AOT 캐시** | 클래스 + **관찰 노트(프로파일)** | 크게 개선 | ◯ (크게 단축) | 그대로 |
| **Native Image** | **번역 완제품** (실행 파일) | 밀리초 | 개념 자체가 없음 | **보통 더 낮음** |

> 선택 기준: "오래 떠서 최고 처리량이 중요한 서버 → JIT + Leyden 방향,
> 수시로 켜지고 꺼지는 서버리스 → Native Image"

### 4-5. [실전] AOT 캐시 × 파드 오토스케일링

오토스케일링의 고질병: 새 파드가 뜰 때마다 JVM이 백지에서 시작 →
**스케일 아웃이 필요한 순간(트래픽 급증)에 하필 제일 느린 파드가 투입**된다.
AOT 캐시가 딱 이 시나리오를 겨냥한다.

핵심은 **AOT 캐시가 "실행 중인 서버"가 아니라 "파일"** 이라는 것.
파일이니까 컨테이너 이미지에 구울 수 있다:

```
[CI/CD 파이프라인]
1. 앱 빌드
2. 훈련 실행: 앱을 잠깐 띄우고 대표 트래픽 태움 → app.aot 캐시 파일 생성
3. 캐시 파일을 컨테이너 이미지에 포함시켜 빌드

[운영 - 오토스케일링 발생]
새 파드 기동 → 이미지 안의 캐시를 얹고 시작
→ 클래스 로딩 생략 + 핫스팟을 이미 아는 상태로 출발 → 바로 C2 번역
```

**훈련은 빌드 때 1번, 혜택은 스케일 아웃으로 뜨는 모든 파드가** 받는다.
100번째 파드도 첫 파드와 똑같이 "예열된 기억"을 갖고 시작.

현실적인 조건과 한계 4가지:

1. **"줄인다"이지 "없앤다"가 아니다** — 컴파일 자체는 여전히 기동 후에
   일어난다(관찰 기간을 건너뛸 뿐). JVM 프로세스 기동 시간도 남는다.
   기대치는 "몇 분 예열 → 수십 초" 수준. 밀리초 기동이 필요하면
   Native Image나 CRaC의 영역
2. **훈련 트래픽이 실제 트래픽과 비슷해야 한다** — 3-5절 프로파일 오염이
   그대로 적용. 단 치명적이진 않다: 여전히 JIT JVM이라 실행하면서 계속
   다시 관찰·재번역하므로, 최악에도 "캐시 없는 것과 비슷한 수준"으로 떨어질 뿐
3. **캐시는 환경에 묶인다** — 같은 JDK 버전·클래스패스·주요 JVM 옵션에서만
   유효. 코드가 바뀌면 캐시도 재생성 → "빌드마다 훈련 실행"을 파이프라인에
   넣는 게 전제 (그만큼 빌드 시간 증가)
4. **JDK 버전 제약** — 클래스 캐시는 24부터, 알맹이인 프로파일 캐시는 25부터.
   JDK 17/21에서는 아직 못 쓴다

### 4-6. [실전] 운영 파드에서 캐시 수확하기 — CI 훈련의 대안

"오토스케일링은 같은 환경의 파드를 늘리는 것이니, 훈련 없이 **기존 파드가
만든 캐시**를 새 파드가 받으면 되지 않나?" — 맞는 직관이고 실제로 가능하다.
같은 이미지라 캐시 호환성이 자동 보장되고, 기존 파드가 받던 트래픽은
**진짜 운영 트래픽**이라 프로파일 대표성이 CI 합성 트래픽보다 좋다
(프로파일 오염 걱정이 원천적으로 없음).

다만 걸림돌 두 가지:

- **캐시는 아무 때나 못 꺼낸다** — 실행 중인 JVM에서 즉석으로 뽑는 게 아니라,
  ① 파드를 **녹화 모드로 시작**해야 하고 (`-XX:AOTMode=record` 계열)
  ② 파일은 **JVM이 정상 종료될 때** 기록된다. k8s의 SIGTERM + grace period
  정상 종료 타이밍을 활용
- **전달 배관이 필요하다** — 캐시는 파드 로컬에 떨어지는데 파드는 죽으면
  사라지므로 공유 저장소(S3/PVC) + init container 다운로드 구성이 필요:

```
[1세대 파드] 녹화 모드 기동 → 운영 트래픽 처리
     ↓ (종료/롤링 시)
캐시 생성 → 공유 저장소 업로드

[새 파드] init container가 캐시 다운로드 → 얹고 기동(-XX:AOTMode=on)
```

제약: **새 버전 배포 직후에는 캐시가 없다.** 캐시는 빌드에 묶이므로 구버전
파드의 캐시는 신버전에 못 쓴다 → 배포 직후 1세대 파드들은 캐시 없이 뜨고,
이후 파드부터 혜택.

| | CI 훈련 (이미지에 굽기) | 운영 파드에서 수확 |
|---|---|---|
| 프로파일 품질 | 합성 트래픽 — 대표성 한계 | **진짜 운영 트래픽 — 최상** |
| 첫 파드부터 혜택 | **◯** (이미지에 이미 있음) | ✕ (1세대는 캐시 없음) |
| 필요한 배관 | 파이프라인에 훈련 단계 | 공유 저장소 + init container + 종료 훅 |
| 재현성/단순성 | 빌드 산출물 — 단순 | 런타임 상태 의존 — 관리 포인트 증가 |

정석은 **하이브리드**: CI 훈련 캐시를 이미지에 구워 첫 파드를 커버하고,
운영 수확 캐시가 저장소에 생기면 그걸 우선 사용(품질 업그레이드).

### 4-7. CRaC — "예열된 파드 복제"를 끝까지 밀어붙인 것

**CRaC**(Coordinated Restore at Checkpoint): "기존 파드가 이미 예열돼 있으니
결과물을 복제하자"는 발상을 프로파일 **파일** 수준이 아니라 **프로세스 전체**
수준으로 밀어붙인 방식.

- **예열이 끝난 JVM 프로세스를 통째로 스냅샷**(메모리 덤프) 찍어두고,
  새 파드는 스냅샷을 **복원**하며 시작 — 번역본·관찰 노트뿐 아니라
  **커넥션 풀·캐시 등 애플리케이션 상태까지** 예열된 채 밀리초~초 단위 기동
- 대가: 스냅샷 전에 열린 리소스(소켓·파일)를 정리했다가 복원 후 다시 여는
  코드가 필요 — Spring Boot 3.2+가 프레임워크 차원에서 지원
- 주의: 스냅샷에 힙이 통째로 들어가므로 **비밀번호·토큰이 파일에 남는**
  보안 이슈 관리 필요 (힙 덤프와 같은 문제)
- JDK 25를 못 쓰는 환경(17/21)에서 오토스케일링 워밍업을 줄이는 현실적 대안

| 상황 | 추천 방향 |
|---|---|
| JDK 25+ 사용 가능 | **AOT 캐시** — 코드 수정 없이 파이프라인에 훈련만 추가 |
| JDK 17/21 + Spring Boot | **CRaC** 검토, 또는 k8s 레벨 완화(readiness probe + 예열 요청, startupProbe) |
| 서버리스급 즉시 기동 | Native Image (피크 성능 트레이드오프 감수) |

## 5. 관측 방법

- `-XX:+PrintCompilation` — 번역/역최적화(`made not entrant`) 이벤트 로그
- `-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining` — 인라이닝 성공/실패 이유
- JFR의 Compilation 이벤트, JITWatch로 시각화
- 코드 캐시 상태: `jcmd <pid> Compiler.codecache`

---

> 한 줄 요약: "JIT는 '자주 실행되는 코드만, 실행을 지켜본 관찰 기록을 근거로'
> 기계어로 번역한다. 인라이닝(내용을 그 자리에 펼침)·탈가상화(한 타입이라고
> 베팅)·스칼라 치환(안 새나가는 객체는 낱개 변수로 분해)으로 예열 후 성능을
> 끌어올리는 대신, 시동 직후엔 느리고(워밍업 → 배포 램프업으로 대응),
> 베팅이 틀리면 무르고 다시 하며(역최적화), 타입이 3개 이상 섞이면 포기하고
> (메가모픽), 번역본 보관함이 차면 서서히 죽는다(코드 캐시 고갈)"
