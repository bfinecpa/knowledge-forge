# 고경합 카운터 설계 — AtomicLong의 한계, LongAdder, false sharing

> 핵심 관전 포인트: **락이 없어도 "경합 지점이 하나"면 느리다. AtomicLong은
> 극한 경합에서 CAS 재시도 폭증으로 처리량이 꺾이고, 해법은 경합 지점
> 자체를 여러 개로 쪼개는 것 — 쓰기는 스레드별 셀에 분산하고 읽을 때만
> 합산한다(LongAdder). 그런데 셀을 쪼개 놓아도 그 셀들이 메모리상 같은
> 캐시 라인에 나란히 붙으면 하드웨어 차원의 간접 경합(false sharing)으로
> 도로 느려진다. 그래서 LongAdder의 Cell에는 @Contended 패딩이 붙어 있다.
> 이 두 층(논리적 경합 분산 + 물리적 캐시 라인 분리)을 함께 설명하면
> 만점이다.**

---

## 0. 질문 + 의도

**질문**: "False sharing이란 무엇이고 어떻게 회피하나요?"

**출제 의도**: 극한 성능 최적화가 필요한 순간(집계 카운터, 고빈도 이벤트
처리)에 프로파일러에도 잘 안 잡히는 병목의 정체를 아는지 본다. 락도 없고
경합 지점을 쪼갰는데도 느린 이유를 캐시 라인까지 내려가 설명할 수 있는지 —
하드웨어까지 내려가본 깊이의 표본 검사에 가깝다.

## 1. AtomicLong이 극한 경합에서 느려지는 이유 — CAS 재시도 폭증

`AtomicLong.incrementAndGet()`은 내부적으로 CAS(Compare-And-Swap) 루프다.
CAS는 "현재 값이 내가 알던 A가 맞으면 B로 바꿔줘, 아니면 실패 알려줘"를
하드웨어가 원자적으로 처리하는 연산이다.

```java
// AtomicLong 내부 동작 (개념 코드)
do {
    long current = value;          // 현재 값 읽기
    long next = current + 1;
} while (!compareAndSwap(current, next));  // 그 사이 다른 스레드가 바꿨으면 실패 → 재시도
```

스레드가 수십 개면 **모두가 단 하나의 메모리 주소를 두고 경쟁**한다.
한 스레드가 CAS에 성공하는 순간 나머지 전원의 CAS는 실패해서 다시 읽고
다시 시도한다. 스레드가 늘수록 실패 확률이 올라가서, CPU는 바쁘게 도는데
실제로 증가에 성공하는 건 한 번에 하나뿐 — 재시도 폭증으로 처리량이
오히려 꺾인다. 락이 없을 뿐이지 **"경합 지점이 하나"라는 문제는 그대로**다.

---

## 2. 해법의 아이디어 — 쓰기는 분산, 읽기는 합산

"모두가 하나의 값을 갱신한다"는 전제를 버리는 게 답이다.

- 카운터를 **여러 개의 셀(cell)로 분산**시키고, 각 스레드는 자기에게
  배정된 셀만 증가시킨다.
- 서로 다른 스레드가 서로 다른 셀을 건드리므로 **CAS가 충돌할 일 자체가
  사라진다.**
- 전체 값이 필요할 때만 모든 셀을 **합산(sum)** 해서 읽는다.

"정확한 현재 값"을 매 순간 유지하는 걸 포기하는 대신 쓰기 처리량을 얻는
트레이드오프다. 집계 카운터는 어차피 "가끔 읽고 끊임없이 쓰는" 용도라
이 트레이드오프가 딱 맞는다.

## 3. JDK의 구현 — LongAdder

```java
// before: 하나의 값에 수십 개 스레드가 몰림
AtomicLong counter = new AtomicLong();
counter.incrementAndGet();   // 극한 경합 시 CAS 재시도 폭증

// after: 셀 분산으로 경합 자체가 사라짐
LongAdder counter = new LongAdder();
counter.increment();         // 스레드마다 다른 셀에 기록
long total = counter.sum();  // 읽을 때만 셀들을 합산
```

`LongAdder`(Java 8+, `Striped64` 기반)의 동작:

1. 경합이 없으면 단일 `base` 값에 CAS — AtomicLong과 동일하게 가볍게 동작
2. CAS 실패(=경합 감지)가 발생하면 그때부터 `Cell[]` 배열을 만들어
   스레드를 셀에 분산
3. 경합이 계속되면 셀 배열을 CPU 코어 수까지 확장
4. 각 `Cell`은 `@Contended`로 패딩되어 있어 false sharing까지 방지 (4절)

### AtomicLong vs LongAdder 트레이드오프

| | AtomicLong | LongAdder |
|---|---|---|
| 쓰기 (고경합) | CAS 재시도 폭증 | 셀 분산으로 거의 선형 확장 |
| 읽기 | 정확한 스냅샷, O(1) | `sum()`은 셀 순회 — 합산 중 다른 셀이 변할 수 있어 **순간 스냅샷이 아님** |
| 메모리 | 8바이트 | 셀당 패딩 포함 수백 바이트 × 코어 수 |
| CAS 연산 지원 | `compareAndSet` 가능 | 불가 (단순 누적 전용) |

선택 기준: **정확한 값을 자주 읽어야 하거나 CAS 연산이 필요하면
AtomicLong, 쓰기가 압도적으로 많은 집계/통계 카운터면 LongAdder.**
같은 원리를 임의의 누적 함수(max, min 등)로 일반화한 것이
`LongAccumulator`다.

## 4. false sharing — 변수를 쪼개도 캐시 라인이 붙어 있으면 느리다

### 전제: CPU는 변수 단위가 아니라 "캐시 라인" 단위로 메모리를 다룬다

CPU 코어는 메인 메모리를 직접 읽지 않고 자기 캐시(L1/L2)에 복사해서
쓰는데, 복사 단위가 변수 하나가 아니라 **캐시 라인(cache line), 보통
64바이트 덩어리**다. long 하나는 8바이트이므로 long 8개가 한 라인에 같이
실려 다니는 셈이다.

여러 코어의 캐시가 같은 데이터를 들고 있을 때 일관성을 맞추는
프로토콜(MESI 등)의 규칙: **어떤 코어가 캐시 라인의 일부라도 수정하면,
그 라인을 들고 있던 다른 모든 코어의 복사본은 무효화(invalidate)된다.**

### 현상

스레드별로 변수를 분리해서 **논리적으로는 공유가 없는데**, 그 변수들이
우연히 **같은 캐시 라인에 나란히 붙어 있어서 물리적으로는 공유되는** 현상.

```java
// 스레드별 카운터를 분리했다 — 논리적 경합은 0
long[] counters = new long[8];

// 스레드 0: counters[0]++
// 스레드 1: counters[1]++
// ...서로 다른 변수인데도 느리다!
```

`counters[0]`~`counters[7]`은 총 64바이트, 즉 **한 캐시 라인에 전부
들어간다.** 이후 벌어지는 일:

1. 코어 A가 `counters[0]`을 증가 → 라인 전체를 "내가 수정 중" 상태로
   가져감 → 코어 B의 복사본 무효화
2. 코어 B가 `counters[1]`을 증가하려는데 자기 복사본이 무효화됨 →
   라인을 다시 가져옴 → 이번엔 코어 A의 복사본 무효화
3. 매 증가마다 반복 — 캐시 라인이 코어 사이를 **핑퐁**

각 스레드는 자기 변수만 건드리는데도 하드웨어 입장에서는 하나의 라인을
두고 쟁탈전을 벌이는 것과 똑같다. "공유하지 않는데 공유의 비용을 낸다"는
뜻으로 **false**(거짓) sharing이다. 락도 없고 CAS 실패도 없어서
프로파일러에 잘 안 잡히는 대표적인 숨은 병목이다.

## 5. false sharing 회피 — 뜨거운 변수마다 캐시 라인을 독점시킨다

### 방법 1: 패딩(padding) — 변수 사이에 안 쓰는 공간 끼워 넣기

```java
// before: value들이 한 라인에 붙어 앉음
class Counter {
    volatile long value;
}

// after: value 앞뒤로 56바이트씩 채워 라인을 독점
class PaddedCounter {
    long p1, p2, p3, p4, p5, p6, p7;  // 앞 패딩
    volatile long value;
    long q1, q2, q3, q4, q5, q6, q7;  // 뒤 패딩
}
```

주의: 수동 패딩은 JVM이 "안 쓰는 필드"라고 최적화로 제거해버릴 수 있고,
필드 배치 순서도 JVM 마음이라 깨지기 쉽다.

### 방법 2: @Contended — JVM에게 맡기기

```java
@jdk.internal.vm.annotation.Contended   // JVM이 자동으로 패딩을 넣어줌
volatile long value;
```

JDK 내부 전용 어노테이션이라 애플리케이션 코드에서 쓰려면
`-XX:-RestrictContended` 플래그가 필요하다. JDK 자신은 적극 활용하는데,
**`LongAdder`의 `Cell` 클래스가 정확히 `@Contended`가 붙어 있는 예**다 —
셀 분산으로 논리적 경합을 없애 놓고도, 셀들이 배열에 나란히 붙으면
false sharing으로 도로 느려지기 때문이다.

### 방법 3: 자료구조 차원의 회피

- 배열 기반이라면 스레드마다 인덱스를 8칸(64바이트)씩 띄워 배정(stride)
- `ThreadLocal`로 아예 스레드별 독립 객체 사용 — 객체가 각각 힙에
  흩어지므로 같은 라인에 붙을 가능성이 낮아짐

### 트레이드오프

패딩은 변수 하나에 64~128바이트를 쓰는 메모리 낭비다. 아무 데나 붙이는
게 아니라 **여러 스레드가 각자 초고빈도로 쓰는(write) 필드**에만 선별
적용한다. 읽기만 하는 데이터는 여러 코어가 복사본을 공유해도 무효화가
안 일어나므로 false sharing이 문제되지 않는다.

---

## 6. 한 줄 요약

- **AtomicLong → LongAdder**: 경합은 "모두가 같은 주소를 갱신"해서
  생기므로, 쓰기를 스레드별 셀로 분산하고 읽을 때 합산하면 경합 자체가
  사라진다.
- **false sharing**: CPU가 메모리를 64바이트 캐시 라인 단위로 관리하기
  때문에, 분리한 변수라도 같은 라인에 붙어 있으면 한쪽의 쓰기가 다른 쪽
  캐시를 계속 무효화시켜 라인 쟁탈전이 벌어진다 — 패딩이나 `@Contended`로
  뜨거운 변수마다 라인을 독점시켜 회피하며, `LongAdder`의 Cell이 두 기법을
  모두 담은 실전 예다.
