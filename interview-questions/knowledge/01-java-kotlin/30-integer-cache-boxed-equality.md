# Integer 캐시와 == 비교 — 127은 true, 128은 false인 이유

> 핵심 관전 포인트: **박싱된 `Integer`는 primitive가 아니라 힙에 놓인 객체이고, 객체끼리의 `==`는 처음부터 "같은 객체를 가리키는가"를 묻는 참조 비교다. `Integer a = 127`은 컴파일러가 `Integer.valueOf(127)` 호출로 바꾸는데, `valueOf`는 -128~127 범위의 객체를 미리 만들어 둔 캐시에서 꺼내 주므로 두 변수가 같은 객체가 되어 `==`가 우연히 true가 된다. 128은 캐시 범위 밖이라 매번 새 객체이므로 false다. 위험은 여기 있다 — `==`는 애초에 값을 비교한 적이 없는데 작은 값에서만 우연히 맞으므로, id가 1, 2, 3으로 도는 테스트와 개발 환경은 전부 통과하고 운영 데이터가 127을 넘는 순간에만 틀리는 재현 불가능한 버그가 된다. 래퍼 타입 비교는 예외 없이 `equals`(null이 섞이면 `Objects.equals`)를 쓴다.**

---

## 0. 질문 + 의도

**질문**: "`Integer a = 127, b = 127`일 때 `a == b`는 true인데 128이면 false인 이유는? 이런 코드의 위험은 무엇인가요?"

**출제 의도**: `==`와 `equals` 혼동이 만드는 "작은 값 테스트는 전부 통과하고 운영 데이터에서만 틀리는" 버그의 대표 사례. 언어의 미묘한 규칙이 재현 안 되는 버그로 나타나는 전형을 아는지 본다.

## 1. 전제 — 박싱된 값은 객체이고, `==`는 참조 비교다

"127은 true, 128은 false"라는 현상부터 외우면 캐시 범위를 암기하는 데서 끝난다. 그러면 `Long`으로 바뀌거나, 조건 연산자가 끼거나, `Map`의 키 타입이 어긋나는 변형 앞에서 다시 막힌다. 현상보다 먼저 깔아야 할 전제가 둘 있다.

### 1-1. primitive와 래퍼는 서로 다른 종류의 값이다

자바의 값에는 두 종류가 있다.

**primitive(기본형)**는 `int`, `long`, `boolean`처럼 **값 자체가 변수 자리에 그대로 들어 있는** 타입이다. `int a = 127;`이면 a라는 변수 칸에 숫자 127이 놓여 있다. 객체가 아니므로 메서드도 없고 null도 될 수 없다.

**래퍼(wrapper) 타입**은 `Integer`, `Long`, `Boolean`처럼 그 값을 **객체 안에 담아 놓은** 타입이다. 이름 그대로 primitive를 한 겹 싸맨(wrap) 것이다. 이 경우 변수 칸에 들어 있는 것은 숫자가 아니라 **그 객체가 힙 어디에 있는지를 가리키는 참조(reference)**다.

```text
[primitive]                      [래퍼]

  int a                            Integer a
  +-------+                        +----------+          +-------------------+
  |  127  |                        | 0x7f3a.. | -------> | Integer 객체       |
  +-------+                        +----------+          |   value = 127     |
  값이 여기 있다                    주소가 여기 있다        +-------------------+
                                                          객체는 힙에 따로 있다
```

래퍼가 필요한 이유는 두 가지다. **제네릭에 primitive를 쓸 수 없어서**(`List<int>`는 문법 오류다) 컬렉션에 담으려면 래퍼가 필요하고, **null로 "값 없음"을 표현해야 하는 자리**(아직 저장 안 한 엔티티의 id, 선택 입력 필드)가 있기 때문이다.

### 1-2. `==`는 무엇을 비교하는가 — 그리고 왜 컴파일 에러가 아닌가

`==`가 하는 일은 피연산자의 종류에 따라 달라진다.

**피연산자가 primitive면 값을 비교한다.** `int a = 128, b = 128;`에서 `a == b`는 변수 칸에 든 숫자 128과 128을 견주므로 당연히 true다.

**피연산자가 둘 다 참조면 참조를 비교한다.** 즉 **"두 변수가 힙의 같은 객체를 가리키는가"**를 묻는다. 위 그림에서 두 화살표가 같은 상자를 향하는지만 본다. 상자 안의 숫자는 쳐다보지도 않는다.

여기서 반드시 짚고 넘어갈 질문이 하나 있다. **그럼 왜 `Integer a == Integer b`는 컴파일 에러가 아닌가?**

에러가 아닌 이유는 **그것이 문법적으로 완전히 유효한 연산이기 때문**이다. 자바에서 참조끼리의 `==`는 "같은 객체인지" 묻는 정상적인 질문이고, 실제로 그 질문이 필요한 자리도 있다(싱글턴 인스턴스 확인, `enum` 상수 비교 등). 컴파일러 입장에서 `a == b`는 **"이 둘이 같은 객체인가?"라는 올바르게 쓰인 문장**이다. 우리가 그것으로 "값이 같은가"를 물으려 했다는 의도는 컴파일러가 알 도리가 없다.

반대로, **문법적으로 성립하지 않는 조합은 실제로 컴파일 에러가 난다.** 이 대비를 보면 컴파일러가 무엇을 검사하고 무엇을 검사하지 않는지가 분명해진다.

```java
Integer i = 1;
Long    l = 1L;
i == l;   // 컴파일 에러: incomparable types: Integer and Long
          // Integer와 Long은 서로 형변환이 불가능한 별개의 클래스라
          // "같은 객체인가"라는 질문 자체가 성립하지 않는다.

Integer a = 1, b = 1;
a == b;   // 컴파일 통과. 같은 타입이니 "같은 객체인가"는 성립하는 질문이다.
          // 다만 우리가 알고 싶었던 것은 그 질문이 아니었을 뿐이다.
```

**컴파일러는 질문이 성립하는지만 검사하고, 그 질문이 우리가 하려던 질문인지는 검사하지 않는다.** 이 버그가 조용한 이유의 절반이 여기에 있다.

### 1-3. 오토박싱은 `Integer.valueOf()` 호출로 컴파일된다

전제가 하나 더 남았다. `Integer a = 127;`이라고 쓰면 우변은 `int` 리터럴인데 좌변은 `Integer`다. 타입이 다른데 어떻게 대입이 되는가.

컴파일러가 중간에 변환 코드를 끼워 넣기 때문이다. primitive를 래퍼로 자동 변환하는 것을 **오토박싱(autoboxing)**, 그 반대를 **언박싱(unboxing)**이라 한다. 그리고 오토박싱의 실체는 **`valueOf` 정적 메서드 호출**이다.

```java
// 우리가 쓴 소스
Integer a = 127;

// 컴파일러가 실제로 만들어 내는 것 (바이트코드 수준)
Integer a = Integer.valueOf(127);
```

이 한 줄이 이 문서의 열쇠다. **박싱은 `new Integer(...)`가 아니라 `Integer.valueOf(...)`로 번역된다.** 그리고 `valueOf`는 그냥 객체를 만들어 주는 메서드가 아니다.

### 1-4. `valueOf` 안의 캐시 — 여기서 127과 128이 갈린다

`Integer.valueOf`의 구현은 대략 이렇게 생겼다.

```java
public static Integer valueOf(int i) {
    // 캐시 범위 안이면 미리 만들어 둔 배열에서 "이미 존재하는 객체"를 꺼내 준다.
    // 새로 만들지 않는다는 것이 핵심 — 같은 값이면 매번 똑같은 객체가 나온다.
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];

    // 범위 밖이면 그때그때 새 객체를 만든다. 호출할 때마다 다른 객체다.
    return new Integer(i);
}
```

`IntegerCache`는 클래스가 처음 로딩될 때 **-128부터 127까지의 `Integer` 객체 256개를 미리 만들어 배열에 채워 두는** 내부 클래스다. 작은 정수는 루프 인덱스, 상태 코드, 소량의 id 등으로 압도적으로 자주 쓰이므로, 미리 만들어 재사용하면 객체 생성과 GC 부담을 줄일 수 있다는 판단에서 나온 최적화다.

이제 현상을 설명할 수 있다.

```java
Integer a = 127, b = 127;
// 둘 다 Integer.valueOf(127) 호출 -> 캐시 배열의 같은 칸을 반환
a == b;      // true  — 두 변수가 힙의 "같은 객체 하나"를 가리킨다

Integer c = 128, d = 128;
// 둘 다 Integer.valueOf(128) 호출 -> 캐시 범위 밖이라 각각 new
c == d;      // false — 값은 같지만 서로 다른 객체 둘이다
c.equals(d); // true  — equals는 안에 든 값을 비교하므로 당연히 같다
```

```text
[a = 127, b = 127]                    [c = 128, d = 128]

  a ---+                                c ------> [Integer 128]  (첫 번째 객체)
       |
       +--> [캐시의 Integer 127]        d ------> [Integer 128]  (두 번째 객체)
       |
  b ---+                                a == b 는 화살표가 같은 상자를 향한다 -> true
                                        c == d 는 다른 상자를 향한다        -> false
```

**정리하면, 127에서 true가 나온 것은 `==`가 값을 비교해서가 아니다.** `==`는 시종일관 참조만 비교했다. **캐시 덕분에 우연히 같은 객체였을 뿐**이다.

### 1-5. 캐시 범위는 어디까지 믿을 수 있는가

여기서 "그럼 -128~127만 조심하면 되겠네"로 끝내면 안 된다. 캐시 범위는 고정된 상수가 아니다.

**(가산점 포인트) 언어 명세가 보장하는 부분이 있다.** 자바 언어 명세(JLS)는 박싱 결과가 항상 같은 객체여야 하는 범위를 규정한다 — `boolean`의 true/false, `byte` 전체, `char`의 0~127, 그리고 `short`와 `int`의 -128~127이다. 즉 JVM 구현이 마음대로 정하는 디테일이 아니라 **명세가 요구하는 동작**이다. 다만 **`Long`은 이 목록에 없다** — `Long.valueOf`가 -128~127을 캐시하는 것은 표준 라이브러리 구현의 선택이지 명세의 보장이 아니다. 실무적 결론은 같지만("어느 쪽도 `==`로 비교하지 않는다"), 근거의 층위가 다르다는 것을 아는 편이 정확하다.

**상한은 JVM 옵션으로 바뀐다.** `-XX:AutoBoxCacheMax=<n>`을 주면 `Integer` 캐시의 상한이 올라간다. 실제로 확인해 보면 이렇다.

```text
$ java V                                 # 기본값
Integer 1000 == : false

$ java -XX:AutoBoxCacheMax=2000 V        # 상한을 2000으로
Integer 1000 == : true                   # 같은 코드의 결과가 뒤집혔다
```

**같은 소스가 실행 옵션에 따라 다른 답을 낸다는 것**이 이 옵션의 진짜 의미다. 그러니 이것은 해결책이 될 수 없다 — 로컬에서는 통과하고 운영 JVM 옵션이 다르면 틀리는, 원래 버그보다 더 나쁜 형태가 된다. 참고로 이 옵션은 `Integer`에만 적용되며 `Long`에는 영향을 주지 않는다(위 실험에서 `Long 1000 == :`는 옵션을 줘도 false 그대로였다).

**다른 래퍼 타입의 캐시 범위**도 알아 두면 좋다.

| 래퍼 타입 | 캐시 범위 |
|---|---|
| `Byte` | -128~127 (byte의 전 범위) |
| `Short`, `Integer`, `Long` | -128~127 |
| `Character` | 0~127 |
| `Boolean` | true, false 두 개 |
| `Float`, `Double` | **캐시 없음** |

`Float`/`Double`에 캐시가 없는 이유는 실수에서는 "자주 쓰이는 값 구간"을 정의하기 어렵기 때문이다. 실무에서 중요한 것은 **id 타입으로 가장 흔한 `Long`이 `Integer`와 똑같은 함정을 갖는다**는 점이다. 3-1의 사고가 정확히 이 지점에서 터진다.

## 2. 반대 방향의 함정 — 언박싱과 NPE

`==` 문제만 알고 끝내면 절반이다. 오토박싱에는 짝이 되는 언박싱이 있고, 언박싱은 **NullPointerException**이라는 다른 계열의 사고를 만든다. 원인은 하나다 — **래퍼는 null이 될 수 있는데 primitive는 될 수 없다.**

### 2-1. null인 래퍼를 primitive에 대입하면

```java
// 잘못됨: 조회 결과가 null일 수 있는데 primitive로 받았다
Integer stock = stockMap.get("A-001");   // 없는 키면 null이 반환된다
int quantity = stock;                     // 여기서 NullPointerException
```

컴파일러는 `int quantity = stock;`을 **`int quantity = stock.intValue();`**로 번역한다. 즉 언박싱은 **래퍼 객체의 메서드를 호출하는 일**이고, 대상이 null이면 그 자리에서 NPE다.

이 NPE가 특히 불친절한 이유는 **소스 코드에 메서드 호출이 보이지 않는다**는 점이다. `stock.intValue()`라고 쓰여 있으면 "아 null 체크를 해야겠다"고 생각하지만, `int quantity = stock;`은 그냥 대입문처럼 보인다. 스택 트레이스도 이 줄을 가리킬 뿐 왜 여기서 NPE가 나는지 설명해 주지 않는다.

```java
// 이렇게: null일 수 있음을 코드에 드러내고 기본값을 정한다
Integer stock = stockMap.get("A-001");
int quantity = (stock != null) ? stock : 0;

// 또는 조회 단계에서 없앤다 — 의도가 더 명확하다
int quantity = stockMap.getOrDefault("A-001", 0);
```

### 2-2. 래퍼와 primitive를 섞어 `==`하면 값 비교가 된다

`==`의 규칙에는 세 번째 경우가 있다. **한쪽이 primitive면 다른 쪽이 언박싱되어 값 비교가 된다.**

```java
Integer boxed = 128;
int primitive = 128;
boxed == primitive;   // true — boxed가 언박싱되어 int 128 == int 128 이 된다
```

캐시 범위와 무관하게 항상 값 비교이므로 이것 자체는 문제가 아니다. 문제는 **여기에도 언박싱이 숨어 있다**는 것이다.

```java
Integer boxed = null;
int primitive = 128;
boxed == primitive;   // NullPointerException — 비교하기 전에 언박싱부터 한다
```

그래서 `==`를 정확히 설명하려면 세 경우를 나눠 말해야 한다.

- **래퍼 == 래퍼**: 참조 비교. 캐시 범위 안에서만 우연히 맞는다.
- **래퍼 == primitive**: 언박싱 후 값 비교. 정확하지만 래퍼가 null이면 NPE.
- **primitive == primitive**: 값 비교. 안전하다.

### 2-3. 조건 연산자가 몰래 언박싱을 시킨다

가장 발견하기 어려운 형태다. 조건 연산자 `? :`의 **두 갈래가 래퍼와 primitive로 섞이면**, 자바는 전체 표현식의 타입을 primitive로 정하고 래퍼 쪽을 언박싱한다.

```java
// 잘못됨: 두 갈래가 Integer와 int로 섞였다
Integer discount = hasCoupon ? coupon.getAmount() : 0;
// getAmount()의 타입은 Integer, 반대편 0은 int 리터럴이다.
// 이때 조건 연산자 전체의 타입이 int로 정해지고, Integer 쪽이 언박싱된다.
// hasCoupon이 true이고 getAmount()가 null이면 바로 그 지점에서 NPE.
```

**보이는 것은 삼항 연산자와 대입뿐이고, 어디에도 메서드 호출이 없다.** 좌변이 `Integer`라 null을 받을 수 있어 보이는 것도 착시를 키운다. 실제로 확인해 보면 이 코드는 NPE로 떨어진다.

```java
// 이렇게 1: 양쪽 갈래의 타입을 래퍼로 맞춰 언박싱 자체를 없앤다
Integer discount = hasCoupon ? coupon.getAmount() : Integer.valueOf(0);

// 이렇게 2: null 가능성을 명시적으로 처리하고 primitive로 확정한다 (권장)
int discount = (hasCoupon && coupon.getAmount() != null) ? coupon.getAmount() : 0;
```

**규칙으로 기억할 것**: 조건 연산자의 두 갈래에 래퍼와 primitive를 섞지 않는다. 섞이는 순간 언박싱이 끼어들고, 그 언박싱은 소스 어디에도 보이지 않는다.

## 3. 실무 사고와 방어

### 3-1. 사고 1 — 소유자 검증이 "테스트를 전부 통과한 채로" 뚫린다

일반적인 버그는 실행하면 틀린다. 이 버그는 **작은 값에서는 맞는다.** 그래서 위험하다.

```java
// 잘못됨: 주문 소유자 검증 — userId가 Long 래퍼 타입이다
public void validateOwner(Order order, Long currentUserId) {
    if (order.getUserId() != currentUserId) {   // 참조 비교!
        throw new AccessDeniedException();
    }
}
```

이 코드가 어떤 경로를 밟는지 시간순으로 보자.

```text
[개발/테스트 환경]
  유저 id가 1, 2, 3 ...  -> 전부 Long 캐시(-128~127) 범위 안
  같은 값이면 항상 같은 객체 -> != 가 false -> 검증 통과
  단위 테스트도 userId = 1L 로 쓴다 -> 통과
  코드 리뷰에서도 "소유자 검증 있네" 하고 넘어간다

[운영 초기]
  가입자 100명 남짓 -> 여전히 캐시 범위 안 -> 아무 일도 안 일어난다

[가입자가 128명을 넘는 순간]
  id 128번 유저부터 Long.valueOf(128)이 매번 새 객체를 반환한다
  order.getUserId() 와 currentUserId 는 값이 같아도 다른 객체
  -> != 가 true -> 본인 주문인데 AccessDeniedException
```

두 가지가 이 사고를 어렵게 만든다.

**첫째, 배포와 증상 발생 사이에 시차가 있다.** 문제의 코드는 몇 달 전에 배포됐고, 오늘 터진 이유는 가입자 수가 어떤 선을 넘었기 때문이다. "최근 배포한 게 뭐지"로 시작하는 통상적인 장애 추적이 통하지 않는다.

**둘째, 증상이 간헐적으로 보인다.** JPA 1차 캐시에서 같은 인스턴스가 나오는 경로에서는 참조가 같아 통과하고, 새로 조회한 경로에서는 실패한다. 같은 유저가 어떤 화면에서는 되고 어떤 화면에서는 안 되는 식이라 로그만 봐서는 규칙을 못 찾는다.

**이처럼 입력 데이터의 크기에 따라 정답 여부가 갈리는 버그**는 재현 조건을 못 찾아 며칠을 태우는 유형의 대표다.

### 3-2. 사고 2 — `Map<Long, ?>`에 `int` 키로 조회해 못 찾는다

같은 뿌리에서 나오지만 증상이 다른 사고다.

```java
// 잘못됨: 키 타입은 Long인데 int 리터럴로 조회한다
Map<Long, Order> byId = new HashMap<>();
byId.put(1L, order);

byId.get(1);    // null!   — 분명 넣었는데 못 찾는다
byId.get(1L);   // order   — 이렇게 해야 나온다
```

**왜 컴파일 에러가 안 나는가.** `Map.get`의 시그니처가 `V get(Object key)`이기 때문이다. 제네릭 타입 `K`가 아니라 `Object`를 받는다. 그래서 `int 1`이 오토박싱으로 `Integer` 1이 되어 아무 불평 없이 들어간다.

**왜 못 찾는가.** HashMap의 조회는 "hashCode로 칸을 고르고 equals로 대조"하는 2단계인데, 여기서는 2단계에서 갈린다.

```text
1단계: Long.valueOf(1L).hashCode() = 1
       Integer.valueOf(1).hashCode() = 1     -> 해시가 같아서 같은 칸으로 간다

2단계: 칸 안의 후보 Long(1) 과 찾는 키 Integer(1) 을 equals로 대조
       Long.equals(Object o) 의 첫 줄은 "o가 Long인가?" 검사다
       Integer는 Long이 아니다 -> false      -> "없음"으로 판정
```

**같은 칸까지 정확히 찾아가 놓고 마지막 타입 검사에서 탈락한다.** 그래서 디버거로 봐도 맵 안에 값이 멀쩡히 들어 있고, `get`만 null을 반환한다.

```java
// 이렇게: 키 타입을 코드에 명시한다
byId.get(1L);
byId.get(orderId);                 // orderId가 Long이면 그대로

// 또는 조회 지점에서 변환을 강제한다
byId.get(Long.valueOf(someInt));
```

실무에서는 **컨트롤러가 `int`로 받은 파라미터를 `Map<Long, ?>` 캐시에 그대로 넘기는 경로**에서 자주 나온다. 타입 경계를 넘을 때 래퍼 타입을 통일하는 것이 예방책이다.

### 3-3. 올바른 비교 — before / after 정리

```java
// Before: 래퍼 타입을 == 로 비교 — 캐시 범위에서만 우연히 정답
if (order.getUserId() == currentUserId) { ... }

// After 1: equals — 값을 비교한다. 단 좌변이 null이면 NPE
if (order.getUserId().equals(currentUserId)) { ... }

// After 2: Objects.equals — 양쪽 모두 null 안전. 실무 기본값으로 권장
//          내부에서 (a == b) || (a != null && a.equals(b)) 를 수행한다
if (Objects.equals(order.getUserId(), currentUserId)) { ... }

// After 3: null이 아님이 확실하면 primitive로 꺼내 비교한다
//          longValue() 를 명시했으므로 "여기서 언박싱한다"가 코드에 보인다
if (order.getUserId().longValue() == currentUserId.longValue()) { ... }
```

세 가지 모두 정답이지만 성격이 다르다. **`Objects.equals`가 기본값인 이유는 null 처리를 잊어도 NPE가 아니라 false로 수렴하기 때문**이고, 반대로 **"null이면 안 되는 자리"라면 `After 3`처럼 언박싱을 명시해 NPE로 빨리 터뜨리는 편이 나을 수도 있다.** 어느 쪽이 맞는지는 그 필드에 null이 정상 값인지에 달렸다.

`compareTo`도 같은 계열의 답이다. `a.compareTo(b) == 0`은 값 기준 비교이므로 안전하다. 정렬이나 대소 비교가 함께 필요한 자리에서는 이쪽을 쓴다.

### 3-4. 방어 전략 — 사람의 주의력에 맡기지 않는다

**첫째, 컨벤션으로 못을 박는다.** 래퍼 타입 비교는 `Objects.equals`로 통일하고, **null 표현이 필요 없는 필드는 처음부터 primitive로 선언한다**(`long id`). 래퍼를 쓰는 자리를 줄이면 실수할 자리 자체가 줄어든다.

**둘째, 정적 분석에 맡긴다.** 이 패턴은 기계가 훨씬 잘 잡는다.

- IntelliJ의 "Number comparison using ==" 인스펙션
- ErrorProne의 `BoxedPrimitiveEquality` 검사
- SonarQube의 해당 룰

**"사람의 주의력 대신 도구로 강제한다"고 답하면 가산점이다.** 이유는 분명하다 — 이 버그는 코드 리뷰에서 눈에 잘 안 띄고(참조 비교라는 사실이 코드에 드러나지 않는다), 테스트도 통과하므로(3-1) **사람과 테스트라는 두 방어선이 동시에 뚫리는 유형**이다. 남는 방어선은 컴파일 타임 도구뿐이다.

**셋째, AI 생성 코드 리뷰의 체크포인트로 삼는다.** 이런 코드는 생성 시점에 그럴듯하고 테스트도 통과하므로, 리뷰에서 **"래퍼 타입 + `==`" 조합 자체를 기계적으로 걸러내는 눈**이 필요하다. 의미를 따지기 전에 형태로 먼저 거른다.

## 4. 꼬리질문 대비 포인트

### "왜 하필 -128~127만 캐시하나요?"

작은 정수는 압도적으로 자주 쓰인다 — 루프 인덱스, 상태 코드, 소량의 id. 그 구간만 미리 만들어 재사용하면 객체 생성과 GC 부담을 눈에 띄게 줄일 수 있다.

범위를 이렇게 잡은 근거는 **`byte` 하나로 표현되는 범위가 정확히 -128~127**이라는 점이다. 자연스러운 경계선이라 기본값으로 채택됐다.

상한은 `-XX:AutoBoxCacheMax`로 올릴 수 있지만 **하한 -128은 고정**이다. 그리고 이 옵션은 `Integer`에만 적용되고 `Long` 등 다른 래퍼에는 영향을 주지 않는다(1-5의 실행 결과). 무엇보다 **옵션에 따라 같은 코드의 결과가 뒤집히므로 이 옵션은 해결책이 아니다.**

### "Integer 말고 다른 래퍼 타입도 캐시가 있나요?"

`Byte`는 -128~127(byte의 전 범위), `Short`와 `Long`도 -128~127, `Character`는 0~127, `Boolean`은 true/false 두 개를 캐시한다. 반면 **`Float`와 `Double`은 캐시가 없다** — 실수에서는 "자주 쓰이는 값 구간"을 정의하기 어렵기 때문이다.

실무에서 짚어야 할 것은 **id 타입으로 가장 흔한 `Long`에 같은 함정이 그대로 있다**는 점이다. 3-1의 사고가 `Integer`가 아니라 `Long`에서 난다.

(가산점 포인트: `boolean`, `byte`, `char`의 0~127, `short`와 `int`의 -128~127은 **언어 명세가 동일 객체를 보장하는 범위**다. 반면 `Long`의 캐시는 표준 라이브러리 구현의 선택일 뿐 명세의 보장이 아니다. 실무 결론은 "어느 쪽도 `==`로 비교하지 않는다"로 같지만, 근거의 층위가 다르다는 것까지 구분하면 정확한 답이 된다.)

### "`new Integer(127) == new Integer(127)`은 어떻게 되나요?"

false다. `new`는 **정의상 반드시 새 객체를 만드는 연산**이므로 캐시를 거치지 않는다. 두 번 호출하면 반드시 서로 다른 객체 둘이 나온다.

이것이 래퍼 생성자가 deprecated된 이유 중 하나다. `valueOf`(또는 오토박싱)를 쓰면 캐시를 활용해 불필요한 객체 생성을 피할 수 있고, 동시에 **"어차피 참조를 믿으면 안 된다"는 사실**을 코드에서 덜 헷갈리게 만든다.

다만 여기서 잘못된 교훈을 얻으면 안 된다. **`valueOf`를 쓴다고 `==`가 안전해지는 것이 아니다.** 128 이상에서는 `valueOf`도 새 객체를 만든다. 참조를 비교한다는 사실 자체는 그대로다.

### "String의 `==` 비교와 같은 문제인가요?"

**같은 뿌리다** — 참조 비교와 값 비교의 혼동, 그리고 "특정 조건에서만 우연히 같은 객체가 되는" 최적화가 겹쳐 만든 착시다.

String은 컴파일 타임 리터럴을 **String pool**이라는 공용 저장소에 모아 재사용하므로, 리터럴끼리는 `==`가 true다. 반면 `new String(...)`이나 런타임에 조합된 문자열(사용자 입력, DB 조회 결과, 문자열 연결의 결과)은 별개의 객체라 false다.

```java
String a = "order", b = "order";
a == b;                      // true  — 둘 다 pool의 같은 객체

String c = new String("order");
a == c;                      // false — c는 pool 밖의 새 객체
a.equals(c);                 // true
```

**"리터럴이나 작은 값으로 도는 테스트에서는 통과하고 실데이터에서 틀린다"는 버그 패턴까지 완전히 동일하다.** 두 사례를 연결해 설명하면 캐시 범위를 암기한 것이 아니라 원리를 이해했다는 신호가 된다.

(가산점 포인트: 같은 계열의 오토박싱 함정이 하나 더 있다. `List<Integer> list`에서 `list.remove(1)`은 **값 1을 지우는 것이 아니라 인덱스 1번을 지운다.** `remove(int index)`와 `remove(Object o)` 두 오버로드가 있는데, primitive `int`는 오버로드 해석에서 박싱보다 정확한 일치가 우선이라 `remove(int)`가 선택되기 때문이다. 값으로 지우려면 `list.remove(Integer.valueOf(1))`이라고 명시해야 한다. **박싱은 자동으로 일어나지만, 자동으로 일어나는 것과 우리가 의도한 것이 항상 같지는 않다**는 같은 교훈이다.)

### "그럼 처음부터 primitive를 쓰면 되지 않나요? 래퍼는 언제 필요한가요?" (시니어 변별 포인트)

**성능과 안전 면에서 primitive가 기본값인 것은 맞다.** 객체 생성이 없고, null이 될 수 없어 언박싱 NPE도 없고, `==`가 애초에 값 비교다. 세 가지 함정이 전부 사라진다.

그러나 래퍼가 반드시 필요한 자리가 둘 있다.

**(1) null이 의미를 갖는 필드.** JPA 엔티티의 id는 영속화 전까지 값이 없어야 하고, "입력하지 않음"과 "0을 입력함"을 구분해야 하는 DTO 필드도 마찬가지다. **primitive는 0과 "없음"을 구분하지 못한다.** `int discountRate = 0`이 "할인 없음"인지 "아직 안 정함"인지 알 방법이 없다.

**(2) 제네릭.** `List<int>`는 문법 오류다. 타입 파라미터 자리에는 참조 타입만 올 수 있으므로 컬렉션에 담으려면 래퍼여야 한다.

**따라서 답은 "primitive만 쓴다"가 아니라 "래퍼를 쓰는 자리를 의도적으로 한정한다"가 된다.** 그리고 그 자리에는 **`==` 금지와 null 처리라는 비용이 따라온다는 것을 인지하고 설계한다**고 말하면 트레이드오프를 아는 답이 된다.

(가산점 포인트: 성능 쪽 이야기를 얹으면 좋다. 컬렉션이나 루프에서 박싱이 반복되면 **매 연산마다 객체가 하나씩 생겨 GC 압력이 된다.** 대표적인 안티패턴이 합계 계산에 `Long sum`을 쓰는 것이다.

```java
// 잘못됨: 반복마다 언박싱 -> 덧셈 -> 다시 박싱. 원소 수만큼 Long 객체가 생긴다
Long sum = 0L;
for (Order o : orders) sum += o.getAmount();

// 이렇게: 누적 변수는 primitive로 — 객체가 하나도 안 생긴다
long sum = 0L;
for (Order o : orders) sum += o.getAmount();
```

한 글자 차이지만 100만 건 루프에서는 100만 개의 임시 객체가 생기느냐 마느냐의 차이다.)

## 한 줄 요약

`==`는 처음부터 끝까지 참조만 비교했고, 127에서 true가 나온 것은 오토박싱이 `Integer.valueOf`로 번역되면서 -128~127 캐시의 같은 객체를 재사용한 **우연**일 뿐이다 — 그런데 참조 비교는 문법적으로 유효하므로 컴파일러가 막아 주지 않고 작은 값 테스트도 전부 통과하니, 래퍼 타입 비교는 예외 없이 `equals`/`Objects.equals`(또는 `compareTo`)로 쓰고 그 규칙을 정적 분석 도구로 강제하는 데까지 가야 한다.
