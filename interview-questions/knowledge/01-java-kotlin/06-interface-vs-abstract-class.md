# 인터페이스 vs 추상 클래스 — 확장 지점을 어디에, 어떻게 설계하는가

> 핵심 관전 포인트: **둘은 경쟁 관계가 아니라 공통점이 훨씬 많다 — 둘 다 "미구현 메서드를 자식에게 강제하는 상위 타입"이고, 그 자체로는 인스턴스를 만들 수 없다. 갈리는 지점은 딱 둘이다. 추상 클래스만 인스턴스 필드(상태)와 생성자를 가질 수 있고, 인터페이스만 한 클래스에 여러 개를 동시에 붙일 수 있다. 그리고 이 둘은 같은 뿌리에서 나온 하나의 사실이다 — 클래스 다중 상속이 금지된 진짜 이유는 메서드가 겹쳐서가 아니라 **물려받을 상태가 두 벌 생기기 때문**이고(다이아몬드 문제), 상태가 없는 인터페이스는 애초에 그 문제가 없어서 여러 개를 붙여도 안전하다. default 메서드끼리 겹치는 경우는 컴파일 에러로 "어느 쪽인지 명시하라"고 강제하는 것으로 기계적으로 해결된다. 관계의 의미도 여기서 갈린다 — 인터페이스는 can-do(이 타입은 이걸 할 수 있다), 추상 클래스는 is-a(이 타입은 저 계열의 일종이다). 실무 기본값은 인터페이스로 계약을 끊고, 구현체들 사이에 중복이 실제로 생기면 그때 계약 아래에 골격 구현(추상 클래스)을 끼우는 것이다. 이 주제의 진짜 실무 핵심은 **이미 배포된 구현체가 있는 인터페이스에 메서드를 추가할 때** 벌어지는 일이다 — 추상 메서드를 추가하면 남의 저장소에 있는 구현체까지 전부 깨지고, Java 8의 default 메서드가 정확히 그 문제(Stream 도입 때 `Collection`에 `stream()`을 추가해야 했던 상황)를 풀려고 나왔지만, 구현체가 알 수 없는 기본 동작을 조용히 물려받아 틀린 결과를 내는 새로운 위험을 함께 들여온다.**

---

## 0. 질문 + 의도

**질문**: "인터페이스와 추상 클래스의 차이, 각각 언제 사용하나요?"

**출제 의도**: 실제로는 "확장 지점을 어떻게 설계하는가"의 질문. 외부 연동(PG사가 3곳)처럼 구현이 여럿인 지점에서 추상화 경계를 어디에 둘지 결정해본 사람인지를 본다. 문법 차이 암기가 아니라, 새 구현체가 추가될 때 기존 코드를 안 건드리는 구조를 만들 수 있는지가 관건이다.

## 1. 공통점부터 — 둘 다 "구현을 강제하는 상위 타입"이다

### 1-1. 전제 지식 — 상위 타입이 하는 일은 호출부에서 구현을 지우는 것이다

인터페이스든 추상 클래스든, 존재 이유는 하나로 같다. **호출하는 쪽이 "누가 이 일을 하는지" 모르게 만드는 것**이다.

`PaymentService`가 `TossGateway`를 직접 알고 있으면, 카카오페이가 추가되는 순간 `PaymentService`를 고쳐야 한다. 반면 `PaymentService`가 `PaymentGateway`라는 상위 타입만 알고 있으면, 카카오페이 구현을 새로 만들어 끼워 넣어도 `PaymentService`는 한 글자도 안 바뀐다. 이것이 **"확장에는 열려 있고 수정에는 닫혀 있다"**는 개방-폐쇄 원칙(OCP, Open-Closed Principle)의 실체다.

이 효과를 얻으려면 상위 타입이 두 가지를 해줘야 한다.

- **호출부가 부를 메서드의 이름과 시그니처를 미리 못 박아 둘 것** — 그래야 구현이 아직 없어도 호출 코드를 쓸 수 있다.
- **그 메서드를 자식이 반드시 채우도록 강제할 것** — 안 채우면 컴파일이 안 되게.

**인터페이스와 추상 클래스는 둘 다 이 둘을 해준다.** 여기까지는 차이가 없다.

### 1-2. 공통점을 먼저 확정하자

구체적으로 두 가지가 같다.

**첫째, 둘 다 그 자체로는 `new` 할 수 없다.** 미완성이기 때문이다. `new PaymentGateway()`도, `new AbstractPaymentGateway()`도 컴파일 에러다.

**둘째, 둘 다 미구현 메서드를 자식에게 강제한다.** 인터페이스의 메서드 선언(`PayResult pay(PayRequest r);`)과 추상 클래스의 `abstract` 메서드는 이 점에서 완전히 같은 일을 한다. 구현하지 않은 자식은 컴파일 에러가 난다.

```java
// 이 둘은 "자식에게 pay 구현을 강제한다"는 점에서 동일하다
interface PaymentGateway {
    PayResult pay(PayRequest request);              // 몸통 없음 = 자식이 채워라
}

abstract class AbstractPaymentGateway {
    public abstract PayResult pay(PayRequest request);  // 역시 자식이 채워라
}
```

그래서 **"인터페이스는 계약이고 추상 클래스는 골격이다"라는 요약부터 외우면 오히려 헷갈린다.** 골격을 물려주는 능력은 갈리는 지점 중 하나의 결과일 뿐이고, 계약을 거는 능력은 양쪽 모두 갖고 있다. 진짜 차이는 아래 두 가지뿐이다.

### 1-3. 갈리는 지점 ① — 상태(인스턴스 필드)를 가질 수 있는가

**추상 클래스는 인스턴스 필드를 가질 수 있고, 인터페이스는 가질 수 없다.**

여기서 **인스턴스 필드**란 "인스턴스마다 따로 존재하는 값을 담는 칸"이다. `TossGateway` 인스턴스와 `KakaoGateway` 인스턴스가 각각 자기 몫의 로거·설정값·연결 정보를 들고 있으려면 인스턴스 필드가 필요하다.

인터페이스에도 필드를 쓸 수는 있지만, 거기 쓴 것은 전부 **암묵적으로 `public static final`** 이 붙는다. 즉 인스턴스마다 따로 있는 값이 아니라 타입 전체가 하나만 공유하는 **상수**다.

```java
interface PaymentGateway {
    int TIMEOUT_MS = 3000;   // 이렇게만 써도 public static final이 자동으로 붙는다
                             // 인스턴스별 상태가 아니라 타입이 하나만 갖는 상수다
}
```

상태를 가질 수 있다는 것에서 **생성자를 가질 수 있다**는 성질이 따라 나온다. 필드가 있으니 그것을 초기화할 시점이 필요하기 때문이다. 그리고 생성자가 있으면 **자식에게 초기화를 강제**할 수 있다 — 자식의 생성자는 부모 생성자를 반드시 호출해야 하므로, 부모가 요구하는 값을 안 넘기면 컴파일이 안 된다.

```java
public abstract class AbstractPaymentGateway implements PaymentGateway {
    private final PgApiLogger logger;      // 인스턴스 필드 = 상태

    // 생성자가 있으니 "로거 없이는 이 계열의 게이트웨이를 만들 수 없다"를 강제한다
    protected AbstractPaymentGateway(PgApiLogger logger) {
        this.logger = logger;
    }
}
```

### 1-4. 갈리는 지점 ② — 여러 개를 동시에 붙일 수 있는가

**클래스는 하나만 상속할 수 있고(`extends`는 한 개), 인터페이스는 여러 개를 구현할 수 있다(`implements A, B, C`).**

이것을 실무 감각으로 옮기면 이렇다. **상속은 슬롯이 하나뿐인 희소 자원**이다. 어떤 클래스에 추상 클래스를 상속시키는 순간 그 클래스는 다른 어떤 클래스도 상속할 수 없게 된다. 반면 인터페이스는 몇 개를 붙이든 서로 자리를 뺏지 않는다.

```java
// 슬롯이 하나뿐인 extends는 여기서 끝이다
class TossGateway extends AbstractPaymentGateway { }   // 다른 클래스는 더 못 붙인다

// implements는 몇 개든 붙는다
class TossGateway implements PaymentGateway, HealthCheckable, Closeable { }
```

### 1-5. 두 지점은 사실 하나다 — 다이아몬드 문제

여기서 자연스러운 질문이 나온다. **"왜 클래스는 하나만 상속되는데 인터페이스는 여러 개가 되는가?"** 답은 1-3에 이미 있다. **상태 때문이다.**

클래스 다중 상속을 허용했다고 가정해 보자. 두 부모가 각각 같은 이름의 필드를 갖고 있으면 자식 인스턴스에는 그 필드가 몇 벌 있어야 하는가.

```text
[클래스 다중 상속을 허용했다면 — 상태가 두 벌이 된다]

     class Account                    class Wallet
     +---------------------+          +---------------------+
     | long balance = 0    |          | long balance = 0    |
     | Account() { ... }   |          | Wallet() { ... }    |
     +---------------------+          +---------------------+
                \                            /
                 \                          /
                  +----------------------+
                  |  class SuperAccount  |
                  |                      |
                  |  balance가 한 벌인가  |
                  |  두 벌인가?           |
                  |  생성자는 어느 쪽을   |
                  |  먼저 돌리는가?       |
                  +----------------------+
                       답이 없다
```

`this.balance = 100`이 어느 쪽 `balance`를 건드리는지, 두 부모의 생성자 중 무엇을 어떤 순서로 돌려야 하는지, `super.foo()`가 어느 부모를 가리키는지 — 전부 언어가 임의로 정해야 하는 규칙이 된다. 상속 계층이 마름모(다이아몬드) 모양이 되면서 생기는 이 모호함이라 **다이아몬드 문제(diamond problem)**라고 부른다. C++는 가상 상속이라는 문법으로 이걸 프로그래머에게 떠넘겼고, Java는 **아예 금지**하는 쪽을 택했다.

인터페이스에는 이 문제가 없다. **물려받을 상태가 애초에 없기 때문**이다.

```text
[인터페이스 다중 구현 — 물려받을 상태가 없다]

   interface Payable            interface Refundable
   +---------------------+      +---------------------+
   | 메서드 선언만        |      | 메서드 선언만        |
   | (인스턴스 필드 없음) |      | (인스턴스 필드 없음) |
   +---------------------+      +---------------------+
                \                       /
                 +---------------------+
                 |  class Order        |
                 |  상태는 Order 자신의 |
                 |  필드가 전부다       |
                 +---------------------+
                   겹칠 상태가 없다
```

**Java 8에서 default 메서드가 생기면서 인터페이스도 "구현"을 실어 나를 수 있게 됐지만, 다이아몬드 문제는 여전히 생기지 않는다.** default 메서드는 동작만 있고 상태가 없기 때문이다. 그래서 겹치는 것은 "어느 메서드 몸통을 쓸 것인가" 하나뿐이고, 이건 컴파일러가 기계적으로 처리할 수 있다 — **컴파일 에러를 내고 명시적 선택을 강제**한다.

```java
// default 메서드가 겹치면 컴파일 에러가 난다
interface A { default String name() { return "A"; } }
interface B { default String name() { return "B"; } }

class C implements A, B { }
// error: types A and B are incompatible;
//   class C inherits unrelated defaults for name() from types A and B
```

```java
// 해소 방법: 자식이 재정의해서 어느 쪽인지 명시한다
class C implements A, B {
    @Override
    public String name() {
        return A.super.name();   // 인터페이스명.super.메서드() 로 특정 부모를 지목한다
    }
}
```

**여기가 핵심이다.** 상태 충돌은 언어가 자동으로 해결할 방법이 없어서 금지됐고, 동작 충돌은 "네가 골라라"로 넘길 수 있어서 허용됐다. **금지와 허용을 가른 것은 상태의 유무다.**

### 1-6. 문법 차이 — 결정적인 것만 추리면

위의 두 갈림에서 나머지 문법 차이가 전부 따라 나온다.

| 구분 | 인터페이스 | 추상 클래스 |
|---|---|---|
| 인스턴스 필드(상태) | 불가 (`public static final` 상수만 가능) | 가능 |
| 생성자 | 없음 | 있음 (자식에게 초기화 강제 가능) |
| 한 클래스에 붙는 개수 | 여러 개 구현 가능 | 하나만 상속 가능 |
| 구현이 담긴 메서드 | `default` / `static` / `private`(Java 9+) | 제한 없음 |
| 멤버 접근 제어 | 기본이 public | `protected` 등 세밀한 제어 가능 |

표에서 마지막 줄이 실무에서 은근히 크다. 추상 클래스는 `protected` 헬퍼 메서드를 둘 수 있어서 **"자식만 쓰는 도구"**를 외부에 노출하지 않고 물려줄 수 있다. 인터페이스는 (Java 9의 `private` 메서드로 default끼리 코드를 공유하는 것 말고는) 자식에게 물려주는 것이 곧 세상에 공개하는 것이다.

### 1-7. 관계의 의미 — can-do와 is-a

이 문법 차이는 두 상위 타입이 표현하는 **관계의 성격**으로 이어진다.

**인터페이스는 can-do — "이 타입은 이 일을 할 수 있다"**를 뜻한다. `Comparable`은 "비교될 수 있다", `Closeable`은 "닫힐 수 있다", `PaymentGateway`는 "결제를 처리할 수 있다"는 능력의 선언이다. 능력은 여러 개를 동시에 가질 수 있다 — 어떤 클래스가 비교도 되고 닫히기도 하는 데 아무 모순이 없다. **다중 구현이 허용되는 것이 이 의미와 정확히 맞아떨어진다.**

**추상 클래스는 is-a — "이 타입은 저 계열의 일종이다"**를 뜻한다. `ArrayList extends AbstractList`는 "ArrayList는 리스트 계열의 한 종류다"라는 분류 선언이다. 분류는 본질적으로 하나다 — 어떤 것이 동시에 두 계열의 일종이라는 말은 대체로 분류를 잘못 그었다는 신호다. **단일 상속만 허용되는 것 역시 이 의미와 맞는다.**

그래서 설계할 때 이렇게 자문하면 판단이 빨라진다. **"이건 이 타입이 할 수 있는 일인가(can-do), 아니면 이 타입의 정체 자체인가(is-a)?"**

## 2. 언제 무엇을 쓰나 — 확장 지점 설계 관점

### 2-1. 기본값은 인터페이스 — 계약을 먼저 끊는다

구현이 여럿이거나 여럿이 될 지점 — 외부 연동, 알림 채널, 저장소 — 에서는 인터페이스로 계약을 끊는다. 왜 그런지는 분기문이 어떻게 번지는지를 보면 안다.

```java
// Before: 분기 산탄 — PG사가 늘 때마다 이 메서드를 수정해야 한다
public PayResult pay(Order order, String pgType) {
    if ("TOSS".equals(pgType)) {
        // 토스 API 호출...
    } else if ("KAKAO".equals(pgType)) {
        // 카카오 API 호출...
    } else if ("NICE".equals(pgType)) {
        // 나이스 API 호출...
    }
    ...
}
```

문제는 이 메서드 하나가 아니다. **같은 모양의 분기가 취소·조회·정산 리포트에도 하나씩 생긴다.** PG사를 하나 추가하는 작업이 "코드베이스 곳곳에 흩어진 분기를 전부 찾아 고치기"가 되고, 하나라도 빠뜨리면 그 기능만 조용히 새 PG사를 지원하지 않는 상태가 된다. 이렇게 **하나의 변경을 위해 여러 곳을 흩어서 고쳐야 하는 구조**를 산탄총으로 쏜 자국 같다고 해서 **산탄 수술(shotgun surgery)**이라 부른다.

```java
// After: 계약(인터페이스) + 구현체 — 새 PG사 추가 = 클래스 하나 추가로 끝난다
public interface PaymentGateway {
    PayResult pay(PayRequest request);
    CancelResult cancel(String transactionId);

    // 어떤 PG 요청을 감당하는지 구현체가 스스로 선언한다.
    // 이 한 줄이 있어야 호출부에 "어느 구현을 고를지"의 분기가 남지 않는다.
    boolean supports(PgType type);
}

@Component class TossGateway  implements PaymentGateway { ... }
@Component class KakaoGateway implements PaymentGateway { ... }

@Service
public class PaymentService {
    // 스프링은 같은 인터페이스를 구현한 빈을 전부 모아 List로 주입해 준다.
    // 새 구현체가 @Component로 등록되기만 하면 이 리스트에 자동으로 합류한다.
    private final List<PaymentGateway> gateways;

    public PaymentService(List<PaymentGateway> gateways) {
        this.gateways = gateways;
    }

    public PayResult pay(Order order, PgType type) {
        return gateways.stream()
                .filter(g -> g.supports(type))   // 어느 구현이 맡을지 구현체에게 묻는다
                .findFirst()
                .orElseThrow(() -> new UnsupportedPgException(type))
                .pay(PayRequest.from(order));
    }
}
```

**`PaymentService`는 어떤 PG사가 존재하는지 모른다.** 새 PG사가 추가돼도 이 클래스는 한 글자도 바뀌지 않는다. 1-1에서 말한 OCP가 실제 코드로 성립한 상태다.

### 2-2. 구현체들 사이의 중복이 보이면 그때 골격 구현을 끼운다

위 구조를 운영하다 보면 구현체마다 같은 코드가 반복되기 시작한다 — 요청/응답 로깅, 타임아웃 처리, 공통 응답 검증. 이때 **계약(인터페이스)은 그대로 두고, 계약과 구현체 사이에 추상 클래스를 한 겹 끼운다.**

이렇게 "공통 뼈대만 미리 채워 두고 다른 부분만 구멍으로 남긴 부분 구현"을 **골격 구현(skeletal implementation)**이라고 부른다. 뼈대(skeleton)만 있고 살은 자식이 붙인다는 뜻이다.

```java
public abstract class AbstractPaymentGateway implements PaymentGateway {

    private final PgApiLogger logger;   // 상태 — 인터페이스로는 가질 수 없는 것

    protected AbstractPaymentGateway(PgApiLogger logger) {
        this.logger = logger;           // 생성자로 초기화를 강제한다
    }

    // final을 붙여 흐름 자체를 못 바꾸게 고정한다.
    // "로깅 -> 호출 -> 검증 -> 변환" 순서는 정책이므로 자식이 건드리면 안 된다.
    @Override
    public final PayResult pay(PayRequest request) {
        logger.request(request);
        PgResponse response = callPgApi(request);   // PG사마다 다른 부분만 자식에게 위임
        validate(response);
        logger.response(response);
        return toResult(response);
    }

    // 자식이 채울 유일한 구멍
    protected abstract PgResponse callPgApi(PayRequest request);
}

class TossGateway extends AbstractPaymentGateway {
    @Override
    protected PgResponse callPgApi(PayRequest request) { /* 토스 API 호출만 작성 */ }
}
```

**계약과 코드 재사용은 층이 다르다.** 인터페이스는 "호출부와의 약속"이고, 추상 클래스는 "구현체들끼리 나눠 쓰는 코드"다. 둘은 경쟁하는 것이 아니라 위아래로 쌓인다.

JDK가 정확히 이 구조를 쓴다 (가산점 포인트).

```text
List (인터페이스)          <- 계약: "이건 리스트다"
  ^
  |
AbstractList (추상 클래스)  <- 골격: get/size만 채우면 나머지가 따라온다
  ^
  |
ArrayList (구체 클래스)     <- 구현: 배열로 저장한다
```

`AbstractList`는 `get(int)`과 `size()`만 자식이 채우면 `contains`, `indexOf`, `iterator`, `equals`, `hashCode`를 전부 대신 만들어 준다. 새 리스트 구현을 만드는 사람이 **인터페이스의 모든 메서드를 처음부터 쓰지 않아도 되게** 하는 것이 골격 구현의 값이다.

### 2-3. 템플릿 메서드 패턴 vs 전략 패턴 — 상속으로 끼울 것인가, 합성으로 끼울 것인가

2-2의 `AbstractPaymentGateway`가 쓴 기법에는 이름이 있다. **템플릿 메서드 패턴**이다. 그리고 2-1에서 `PaymentGateway` 구현체를 갈아 끼운 것은 **전략 패턴**이다. 둘 다 "공통 흐름은 두고 다른 부분만 갈아 끼운다"는 같은 목적을 가지는데, 끼우는 **메커니즘**이 다르다.

**템플릿 메서드는 상속으로 끼운다.** 부모가 전체 흐름을 `final` 메서드로 고정해 두고, 갈리는 부분만 `abstract` 메서드로 구멍을 뚫는다. 자식은 그 구멍만 채운다.

```java
// 템플릿 메서드 — 흐름이 부모에 있고, 구멍만 자식이 채운다
public abstract class AbstractSettlementJob {

    // final: 이 순서는 정책이므로 자식이 못 바꾼다
    public final void run(LocalDate date) {
        List<Order> orders = load(date);
        BigDecimal fee = calculateFee(orders);   // 여기만 갈린다
        report(date, orders, fee);
    }

    protected abstract BigDecimal calculateFee(List<Order> orders);
}

class TossSettlementJob extends AbstractSettlementJob {
    @Override protected BigDecimal calculateFee(List<Order> orders) { ... }
}
```

**전략 패턴은 합성으로 끼운다.** 갈리는 부분을 별도 인터페이스로 뽑아 두고, 그 구현체를 **필드로 주입받아** 사용한다. 상속이 아니라 "가지고 있음(has-a)"의 관계다.

```java
// 전략 — 갈리는 부분이 독립된 타입이 되고, 인스턴스를 갈아 끼운다
public interface FeePolicy {
    BigDecimal calculate(List<Order> orders);
}

public class SettlementJob {

    private final FeePolicy feePolicy;   // 갈아 끼울 부분을 필드로 들고 있는다

    public SettlementJob(FeePolicy feePolicy) {
        this.feePolicy = feePolicy;
    }

    public void run(LocalDate date) {
        List<Order> orders = load(date);
        BigDecimal fee = feePolicy.calculate(orders);
        report(date, orders, fee);
    }
}

// 사용: 무엇을 끼울지 생성 시점에 고른다. 런타임에 바꿔 끼울 수도 있다.
new SettlementJob(new TossFeePolicy()).run(date);
new SettlementJob(new FlatFeePolicy()).run(date);
```

차이를 짧게 견주면 이렇다.

| | 템플릿 메서드 (상속) | 전략 (합성) |
|---|---|---|
| 끼우는 시점 | 컴파일 타임 (클래스가 곧 조합) | 런타임 (인스턴스를 바꿔 끼움) |
| 단일 상속 슬롯 | 소비한다 | 소비하지 않는다 |
| 부모의 `protected` 상태 접근 | 가능 | 불가능 (공개 API로만) |
| 갈리는 축이 둘 이상일 때 | 서브클래스 수가 곱으로 폭발 | 전략을 축마다 따로 주입 |
| 테스트 | 자식을 만들어야 함 | 가짜 전략을 넣으면 끝 |

**언제 템플릿 메서드가 맞는가.** 흐름의 순서 자체가 지켜야 할 정책이고(예: 로깅 → 호출 → 검증), 갈리는 부분이 그 흐름 밖에서는 아무 의미가 없으며, 자식이 부모의 보호된 도구(`protected` 헬퍼, 공유 로거)를 써야 할 때다. `callPgApi`는 PG 호출 흐름 밖에 따로 떼어 놓으면 의미가 없는 조각이므로 여기가 맞다.

**언제 전략이 맞는가.** 갈리는 부분이 그 자체로 이름을 가진 독립된 개념이고(수수료 정책, 할인 정책, 재시도 정책), 다른 곳에서도 재사용되거나, 런타임 조건에 따라 골라야 하거나, **갈리는 축이 둘 이상**일 때다.

마지막 조건이 결정적이다. 수수료 정책이 3가지, 리포트 형식이 2가지라면 상속으로는 서브클래스가 3 × 2 = 6개 필요하다. 전략이면 정책 3개 + 형식 2개 = 5개를 만들어 두고 조합해 쓴다. 축이 하나 더 늘면 상속은 곱하기로, 합성은 더하기로 늘어난다. **"상속보다 합성을 선호하라"는 격언의 구체적 근거가 이 곱셈과 덧셈의 차이다.**

실무에서는 둘을 겹쳐 쓰는 경우가 많다. 2-1과 2-2가 정확히 그 예다 — **바깥 계약은 전략(인터페이스 주입)으로 끊고, 구현체들 내부의 중복은 템플릿 메서드로 걷어낸다.**

### 2-4. 선택 기준 요약

- 구현이 여럿이거나 여럿이 될 확장 지점 → **인터페이스** (기본값)
- 그 구현체들이 상태나 흐름을 실제로 공유하기 시작함 → 인터페이스 아래에 **추상 클래스(골격 구현)** 추가
- **추상 클래스 단독 사용**은 계약을 외부에 노출할 필요가 없고 상속 계층 내부 전용일 때 정도로 제한한다 — 자식의 단일 상속 슬롯을 영구히 소비하므로 비용이 크다

### 2-5. Spring에서 인터페이스를 둘 것인가 — 구현체가 하나뿐일 때

실무에서 가장 자주 부딪히는 판단이 이것이다. `OrderService` 하나에 `OrderServiceImpl` 하나. 이 인터페이스는 값을 하는가.

**먼저 흔한 오해 하나를 걷어내야 한다.** "스프링 AOP가 인터페이스를 요구한다"는 말은 요즘 기준으로 틀렸다.

스프링이 `@Transactional` 같은 부가 기능을 붙이는 방법은 두 가지다. **JDK 동적 프록시**는 대상이 구현한 인터페이스를 똑같이 구현한 객체를 리플렉션으로 만들어 대신 넘긴다 — 그래서 **인터페이스가 반드시 있어야 한다.** **CGLIB**은 대상 클래스를 상속한 자식 클래스를 런타임에 만들어 메서드를 재정의한다 — 인터페이스가 없어도 된다.

**스프링 부트의 기본값은 CGLIB이다**(`proxyTargetClass=true`). 인터페이스가 있든 없든 상속 방식으로 프록시를 만든다. 그래서 "트랜잭션을 걸려면 인터페이스가 필요하다"는 근거는 성립하지 않는다. (부트가 CGLIB을 기본으로 고른 이유 중 하나가 JDK 프록시의 함정이다 — JDK 프록시로 만들어진 객체는 **인터페이스 타입이지 구현 클래스 타입이 아니라서**, `@Autowired OrderServiceImpl`처럼 구체 타입으로 주입받으면 주입에 실패한다. 자세한 내용은 `02-spring/10-aop-jdk-dynamic-proxy-vs-cglib.md`.)

**테스트 대역도 자동 정당화가 되지 않는다.** Mockito는 바이트코드를 생성해 구체 클래스도 mock 할 수 있으므로, mock을 쓸 목적이라면 인터페이스가 없어도 된다. 다만 mock이 아니라 **손으로 만든 가짜 구현(fake)** — 예를 들어 `HashMap`으로 동작하는 `InMemoryOrderRepository` — 을 쓰고 싶다면 갈아 끼울 상위 타입이 필요하므로 이때는 인터페이스가 값을 한다.

그럼 인터페이스가 실제로 값을 하는 조건은 무엇인가. 셋이다.

**(1) 두 번째 구현이 실제로 예정돼 있다.** "언젠가 생길지도 모른다"가 아니라 "다음 분기에 카카오페이가 붙는다" 수준의 구체성이어야 한다.

**(2) 아키텍처 경계에서 의존 방향을 뒤집어야 한다.** 이것이 가장 강한 근거다. 멀티모듈에서 `domain` 모듈이 `infra` 모듈을 컴파일 의존하면 안 되는데, 도메인은 저장을 해야 한다. 이때 `OrderRepository` 인터페이스를 **domain 모듈에 두고** 구현체를 infra 모듈에 두면, 화살표가 infra → domain 한 방향으로만 흐른다. 이것이 의존성 역전 원칙(DIP, Dependency Inversion Principle)이고, 여기서 인터페이스는 파일 하나가 아니라 **모듈 의존 그래프의 방향을 결정하는 장치**다.

**(3) 갈아 끼울 가짜 구현이 테스트에 실제로 필요하다.** 느린 외부 API, 결제 승인, 메일 발송처럼 테스트에서 진짜로 부르면 안 되는 의존이다.

**이 셋 중 하나도 해당하지 않는데 서비스마다 1:1로 `Impl`을 찍어내는 것은 파일 수와 탐색 비용만 늘리는 관례적 낭비다.** 인터페이스를 타고 들어가면 구현이 하나뿐인 경험이 반복되면 개발자는 인터페이스를 신뢰하지 않게 되고, 결국 IDE의 "구현으로 이동"만 누르게 된다.

그리고 **"지금은 클래스로 두고, 두 번째 구현이 생기는 순간 인터페이스를 추출한다"**가 유효한 전략이라는 점까지 말할 수 있으면 좋다. IDE의 Extract Interface 리팩터링은 호출부를 자동으로 바꿔 주므로 나중에 뽑는 비용이 거의 없다. **미래를 위한 추상화는 대체로 틀린 추상화가 되고, 두 번째 구현이 생긴 뒤에 뽑은 인터페이스가 정확한 인터페이스다.**

## 3. 실무 함정 — 인터페이스에 메서드 추가하기

이 절이 이 주제의 실무 핵심이다. 인터페이스를 쓰기 시작한 순간부터 계속 부딪히게 되는 문제이고, Java 8이 default 메서드를 도입한 이유 자체가 여기 있다.

### 3-1. 추상 메서드를 추가하면 이미 배포된 구현체가 전부 깨진다

운영 중인 인터페이스에 메서드를 하나 추가한다고 하자.

```java
public interface PaymentGateway {
    PayResult pay(PayRequest request);
    CancelResult cancel(String transactionId);

    RefundResult partialCancel(String txId, Money amount);   // 새로 추가
}
```

**이 인터페이스를 구현한 모든 클래스가 그 순간 컴파일 에러가 된다.** 구현하지 않은 추상 메서드가 생겼기 때문이다.

우리 저장소 안에 구현체가 셋뿐이라면 셋을 고치면 된다. 문제는 **구현체가 우리 손 밖에 있을 때**다.

```text
[우리 모듈]                        [다른 팀 저장소]        [사내 라이브러리 사용자들]
common-payment-api                 settlement-batch        alpha, beta, gamma 서비스
  interface PaymentGateway   <---- implements  <---------- implements
        |
        +-- 여기에 추상 메서드 하나를 추가하면
            화살표로 연결된 저 코드들이 전부 컴파일 불가가 된다.
            우리는 저 코드를 고칠 권한도, 배포할 권한도 없다.
```

이것을 **하위 호환 파괴**라고 부른다. 라이브러리나 공통 모듈을 만드는 입장에서는 사실상 손발이 묶인 상태가 된다 — **인터페이스를 한번 공개하면 다시는 메서드를 못 늘린다.**

### 3-2. default 메서드가 정확히 이 문제를 풀려고 나왔다

Java 8이 Stream API를 도입하면서 정확히 이 벽에 부딪혔다. `collection.stream()`을 쓰려면 `Collection` 인터페이스에 `stream()` 메서드가 있어야 하는데, `Collection`은 **세상에 존재하는 모든 자바 코드가 구현하고 있는 인터페이스**다. 여기에 추상 메서드를 추가하는 것은 지구상의 모든 자바 프로그램을 깨는 일이다.

그래서 나온 것이 **default 메서드** — **인터페이스가 메서드의 기본 구현까지 함께 제공해서, 구현체가 재정의하지 않으면 그 기본 구현이 실행되게 하는 문법**이다. 구현체 입장에서는 아무것도 안 해도 메서드가 생긴 셈이라 **재컴파일 없이 그대로 동작한다.**

```java
public interface PaymentGateway {
    PayResult pay(PayRequest request);

    // 새 기능을 default로 추가한다. 기존 구현체는 손대지 않아도 컴파일되고,
    // 호출하면 아래 기본 구현이 실행된다.
    default boolean supportsPartialCancel() {
        return false;   // 보수적 기본값 — 부분 취소를 지원하는 구현체만 재정의한다
    }
}
```

이 기본값이 왜 `false`인지가 중요하다. **기존 구현체는 부분 취소를 구현한 적이 없으므로 "지원하지 않는다"가 사실이다.** 기본값이 `true`였다면, 아무것도 안 한 기존 구현체들이 갑자기 "부분 취소를 지원한다"고 거짓말을 하게 되고 호출부는 그 말을 믿고 부분 취소를 시도한다.

**default 메서드의 기본값은 "기능을 켜는 쪽"이 아니라 "끄는 쪽"으로 잡는 것이 원칙**인 이유가 이것이다.

### 3-3. default 메서드는 만능이 아니다 — 조용히 틀린 동작을 물려준다

여기서 멈추면 절반만 아는 것이다. **default 메서드는 하위 호환을 지키는 대신 다른 위험을 들여온다.**

문제의 뿌리는 이렇다. **default 메서드는 구현체가 "요청한 적 없는 동작"을 물려받게 만든다.** 추상 메서드였다면 구현체 작성자가 반드시 그 메서드를 보고 직접 판단해서 코드를 썼을 텐데, default라서 **아무도 보지 않은 채 동작이 생긴다.**

구체적으로 어떤 일이 생기는지 보자.

```java
// 위험한 default: 구현체가 알 수 없는 값을 기본 구현이 마음대로 정한다
public interface PaymentGateway {
    PayResult pay(PayRequest request);

    default Money fee(Money amount) {
        // "대부분의 PG가 3%니까 기본으로 3%를 계산해 주자"
        return amount.multiply(new BigDecimal("0.03"));
    }
}
```

```java
// 수수료가 1.8%인 PG사 구현체 — fee()를 재정의하지 않았다.
// 작성자는 이 메서드가 인터페이스에 생겼다는 사실 자체를 모른다.
class NiceGateway implements PaymentGateway {
    @Override public PayResult pay(PayRequest request) { ... }
    // fee()를 안 썼는데 컴파일이 된다. 그리고 3%를 반환한다.
}
```

이제 정산 배치가 `gateway.fee(amount)`를 호출하면 **NICE 건에 대해 1.8%가 아니라 3%가 계산된다.** 예외는 나지 않는다. 컴파일 에러도 없다. 숫자만 틀린다. **정산 대사에서 차액이 발견되기 전까지 아무도 모른다.** 추상 메서드였다면 `NiceGateway` 작성자가 `fee`를 구현하도록 강제됐을 것이고, 그 순간 1.8%를 적었을 것이다.

같은 위험이 갖는 다른 얼굴도 있다. **default 메서드는 상태에 접근할 수 없다.** 인터페이스에는 인스턴스 필드가 없으므로(1-3), default 메서드가 뭔가 계산하려면 같은 인터페이스의 다른 추상 메서드를 호출하는 수밖에 없다.

```java
public interface Cart {
    List<Item> items();                        // 추상

    default Money total() {
        return items().stream()                // 자기 인터페이스의 다른 메서드를 부른다
                      .map(Item::amount)
                      .reduce(Money.ZERO, Money::plus);
    }
}
```

이렇게 **어떤 메서드가 같은 타입의 다른 메서드를 호출하는 구조**를 자기 사용(self-use)이라고 부른다. 문제는 이 호출 관계가 **문서에 적지 않으면 구현체 작성자에게 보이지 않는다**는 점이다. `items()`를 매번 DB에서 새로 읽어 오도록 구현한 사람은 `total()`이 그것을 호출한다는 사실을 모른 채, 합계를 구할 때마다 쿼리가 나가는 코드를 만들게 된다.

**정리하면 default 메서드는 이렇게 쓴다.**

- **용도는 "인터페이스 진화"이지 "구현 재사용"이 아니다.** 코드를 나눠 쓰고 싶으면 추상 클래스(골격 구현)를 쓰는 것이 맞다.
- **기본값은 보수적으로.** "기능 없음", "지원 안 함", "빈 결과"처럼 **틀릴 수 없는 값**을 준다. 도메인 값을 추측해서 채우지 않는다.
- **구현체가 반드시 자기 사정에 맞게 판단해야 하는 것은 default로 만들지 않는다.** 컴파일 에러를 감수하고 추상 메서드로 두는 것이 안전한 경우가 있다.
- **자기 사용(self-use) 구조는 문서화한다.** 어떤 추상 메서드를 호출하는지 적어야 구현체가 성능·동시성 측면을 판단할 수 있다.

### 3-4. 바이너리 호환과 소스 호환은 다르다 (가산점 포인트)

메서드 추가의 영향을 정확히 말하려면 두 종류의 호환성을 구분해야 한다.

- **소스 호환(source compatibility)**: 기존 소스 코드를 **다시 컴파일**했을 때 성공하는가
- **바이너리 호환(binary compatibility)**: 이미 컴파일된 `.class` 파일을 **재컴파일 없이** 그대로 실행했을 때 링크가 되는가

인터페이스에 추상 메서드를 추가하면 **소스 호환은 즉시 깨진다**(구현체를 다시 컴파일하면 에러). 그런데 **바이너리 호환은 유지된다** — 이미 컴파일된 구현체 `.class`는 새 인터페이스와 링크가 되고, JVM이 기동될 때 아무 문제도 발생하지 않는다.

문제는 **그 메서드를 실제로 호출하는 순간**이다. 구현체에 그 메서드의 몸통이 없으므로 `AbstractMethodError`가 터진다. 즉 **기동은 멀쩡히 되고 배포도 성공하는데, 그 코드 경로를 처음 타는 요청에서 런타임 에러가 나는** 형태가 된다. 라이브러리 버전만 올렸는데 특정 API에서만 `AbstractMethodError`가 나는 상황이 대개 이 구조다.

반대로 **default 메서드 추가는 소스 호환과 바이너리 호환이 모두 유지된다.** 재컴파일하지 않은 구현체를 호출하면 인터페이스의 default 구현이 실행된다. 그래서 **공개된 인터페이스를 진화시킬 때는 default 메서드 + 보수적 기본값이 정석**이다.

## 4. 꼬리질문 대비 포인트

### "Java 8부터 인터페이스도 default 메서드로 구현을 가질 수 있는데, 이제 추상 클래스는 필요 없는 것 아닌가요?"

**아니다. 남는 차이가 셋이다.**

**(1) 인스턴스 필드.** default 메서드는 상태를 가질 수 없다. 공유 캐시, 로거, 커넥션 설정처럼 인스턴스마다 들고 있어야 하는 것이 필요한 공통 로직은 추상 클래스만 가능하다. 인터페이스의 필드는 전부 `public static final` 상수라 인스턴스별 상태가 아니다.

**(2) 생성자.** 자식에게 초기화를 강제하고 불변 필드를 세팅할 수 있다. "로거 없이는 이 계열의 객체를 만들 수 없다"를 컴파일러가 지키게 하려면 생성자가 필요하다.

**(3) 접근 제어와 `final`.** `protected` 헬퍼로 자식에게만 도구를 물려주는 것, `final` 메서드로 템플릿 흐름을 고정해 자식이 순서를 못 바꾸게 하는 것 — 둘 다 추상 클래스의 영역이다.

그리고 결론으로 이걸 붙이면 좋다. **default 메서드의 진짜 용도는 "구현 재사용"이 아니라 "이미 배포된 구현체를 깨지 않고 인터페이스를 진화시키는 것"이다.** 목적이 다르기 때문에 추상 클래스를 대체하지 못한다.

### "왜 클래스 다중 상속은 안 되는데 인터페이스는 여러 개 구현할 수 있나요?"

**다이아몬드 문제의 핵심은 메서드 충돌이 아니라 상태(필드) 충돌이기 때문이다.**

두 부모 클래스가 각자 필드를 갖고 있으면 자식 인스턴스에 그 필드가 한 벌인지 두 벌인지, 어느 생성자를 어떤 순서로 돌려야 하는지, `super`가 어느 쪽을 가리키는지 — 언어가 임의로 정하지 않으면 답이 없다. Java는 이 모호함을 문법으로 떠넘기는 대신 아예 금지했다.

인터페이스에는 **물려받을 상태가 없으므로** 이 문제가 발생하지 않는다. 겹칠 수 있는 것은 default 메서드의 몸통뿐이고, 그건 컴파일 에러(`inherits unrelated defaults`)로 자식에게 명시적 선택을 강제하면 끝난다 — `A.super.name()`처럼 어느 부모인지 지목하면 된다.

**"금지와 허용을 가른 것은 상태의 유무"**라고 한 문장으로 정리하면 깔끔하다.

### "구현체가 하나뿐인데도 인터페이스를 미리 만들어야 하나요?" (시니어 변별 포인트)

**기계적으로 만들면 안 된다. 그리고 흔히 대는 근거 두 개는 요즘 기준으로 성립하지 않는다.**

먼저 오해를 걷어낸다. **"스프링 AOP 때문에 필요하다"는 틀렸다** — 스프링 부트의 기본 프록시는 CGLIB(대상 클래스를 상속)이라 인터페이스 없이도 `@Transactional`이 걸린다. 인터페이스가 반드시 필요한 것은 JDK 동적 프록시 쪽인데 부트의 기본값이 아니다. **"테스트 때문에 필요하다"도 절반만 맞다** — Mockito는 구체 클래스도 mock 할 수 있다. 다만 mock이 아니라 손으로 만든 fake(`InMemoryOrderRepository` 같은)를 끼우고 싶다면 상위 타입이 필요하다.

**인터페이스가 실제로 값을 하는 조건은 셋이다.**

1. **두 번째 구현이 구체적으로 예정돼 있다** — "언젠가"가 아니라 "다음 분기에 PG사 하나 더".
2. **아키텍처 경계에서 의존 방향을 뒤집어야 한다** — 도메인 모듈에 `OrderRepository`를 두고 구현을 인프라 모듈에 두면 컴파일 의존이 인프라 → 도메인 한 방향이 된다(DIP). 여기서 인터페이스는 파일 하나가 아니라 모듈 의존 그래프의 방향을 결정하는 장치다. **가장 강한 근거는 이것이다.**
3. **갈아 끼울 가짜 구현이 테스트에 실제로 필요하다** — 느린 외부 API, 결제 승인, 메일 발송.

이 셋에 해당 없이 서비스마다 1:1로 `Impl`을 찍어내는 것은 파일 수와 탐색 비용만 늘린다. **"지금은 클래스로 두고, 두 번째 구현이 생기는 순간 IDE의 Extract Interface로 뽑는다"**가 유효한 전략이라고 말할 수 있으면 설계 감각을 보여준다. 미래를 위해 미리 만든 추상화는 대체로 틀린 추상화가 되고, 두 번째 구현을 보고 뽑은 인터페이스가 정확한 인터페이스이기 때문이다.

### "템플릿 메서드 패턴과 전략 패턴의 차이는 무엇인가요?"

**목적은 같고 끼우는 메커니즘이 다르다.** 템플릿 메서드는 **상속** — 추상 클래스가 흐름을 `final`로 고정하고 `abstract` 구멍만 자식이 채운다. 전략은 **합성** — 갈리는 부분을 인터페이스로 뽑아 구현체를 필드로 주입받아 갈아 끼운다.

전략이 유리한 지점은 셋이다. 런타임에 바꿔 끼울 수 있고, 단일 상속 슬롯을 소비하지 않으며, 테스트에서 가짜 전략만 넣으면 된다.

**결정적인 차이는 갈리는 축이 둘 이상일 때 나온다.** 수수료 정책 3가지 × 리포트 형식 2가지를 상속으로 표현하면 서브클래스가 6개 필요하지만, 전략으로는 3 + 2 = 5개를 만들어 조합한다. 축이 하나 늘 때 상속은 곱하기로, 합성은 더하기로 늘어난다. **"상속보다 합성"이라는 격언의 구체적 근거가 이 곱셈과 덧셈의 차이다.**

반대로 템플릿 메서드가 맞는 자리도 분명하다. 흐름의 순서 자체가 지켜야 할 정책이고, 갈리는 조각이 그 흐름 밖에서는 의미가 없으며, 자식이 부모의 `protected` 상태를 써야 할 때다.

실무에서는 겹쳐 쓴다 — **바깥 계약은 전략(인터페이스 주입), 구현체들 내부의 중복 제거는 템플릿 메서드.**

### "인터페이스에 default 메서드를 추가하면 이미 배포된 구현체에는 무슨 일이 생기나요?" (가산점 포인트)

**소스 호환과 바이너리 호환을 나눠서 답하면 정확해진다.**

**default 메서드 추가는 둘 다 유지된다.** 재컴파일 없이 링크가 되고, 구현체가 재정의하지 않았으면 호출 시 인터페이스의 default 구현이 실행된다.

**추상 메서드 추가는 소스 호환이 즉시 깨진다** — 구현체를 다시 컴파일하면 컴파일 에러다. 그런데 **바이너리 호환은 유지되므로** 기존 `.class` 파일은 링크가 되고 기동도 정상적으로 된다. 문제는 그 메서드를 실제로 호출하는 순간 `AbstractMethodError`가 터진다는 것이다. **배포는 성공하는데 특정 코드 경로를 처음 타는 요청에서만 죽는** 형태라 발견이 늦다.

그래서 공개 인터페이스의 진화는 **default 메서드 + 보수적 기본값**이 정석이다. 다만 default가 만병통치는 아니라는 점까지 덧붙이면 좋다 — **구현체가 자기 사정에 맞게 반드시 판단해야 하는 값(수수료율 같은)을 default로 채워 두면, 재정의하지 않은 구현체가 조용히 틀린 값을 반환하고 예외 없이 잘못된 결과가 흘러간다.** 기본값은 "기능 없음", "지원 안 함", "빈 결과"처럼 틀릴 수 없는 쪽으로 잡는다.

## 한 줄 요약

인터페이스와 추상 클래스는 둘 다 "미구현 메서드를 자식에게 강제하는 상위 타입"이라는 점에서 같고, 갈리는 지점은 **상태(인스턴스 필드)를 가질 수 있는가**와 **여러 개를 동시에 붙일 수 있는가** 둘뿐이며, 이 둘은 사실 하나의 사실이다 — 다중 상속이 금지된 진짜 이유가 물려받을 상태가 두 벌 생기는 다이아몬드 문제이고 상태 없는 인터페이스에는 그 문제가 없기 때문이다. 그래서 실무 기본형은 **확장 지점을 인터페이스(can-do 계약)로 끊고 구현체들의 중복이 실제로 생기면 그 아래에 골격 구현(추상 클래스)을 끼우는 것**이며, 여기서 한 걸음 더 들어가는 지점은 **이미 배포된 구현체가 있는 인터페이스에 메서드를 추가할 때** — 추상 메서드는 소스 호환을 즉시 깨고 바이너리로는 `AbstractMethodError`를 남기며, 그것을 풀려고 나온 default 메서드조차 구현체가 알 수 없는 기본 동작을 조용히 물려줘 틀린 결과를 낼 수 있으므로 기본값은 "틀릴 수 없는 값"으로만 잡는다는 것까지가 이 주제의 완성이다.
