# equals()와 hashCode() 동시 재정의 — "분명 넣었는데 못 찾는" 버그의 뿌리

> 핵심 관전 포인트: **HashMap/HashSet은 값을 찾을 때 두 단계를 밟는다 — 먼저 `hashCode()`로 버킷(저장 칸)을 하나 고르고, 그 칸 안에 든 후보들만 `equals()`로 대조한다. 1단계에서 다른 칸을 열면 2단계는 아예 실행되지 않으므로, `equals()`만 재정의하고 `hashCode()`를 그대로 두면 "논리적으로 같은 객체"가 서로 다른 칸으로 흩어져 영영 못 찾는다. 여기서 규약이 도출된다 — `equals()`가 true인 두 객체는 반드시 같은 `hashCode()`를 반환해야 한다. 이 규약 위반은 컴파일 에러도 예외도 내지 않고 조용히 틀리기 때문에, 중복 처리 실패나 캐시 미스 폭증처럼 원인과 동떨어진 증상으로만 드러난다.**

---

## 0. 질문 + 의도

**질문**: "`equals()`와 `hashCode()`를 함께 재정의해야 하는 이유는 무엇인가요?"

**출제 의도**: HashMap/Set에 넣은 객체가 "분명 넣었는데 못 찾는" 버그는 재현이 어렵고 증상이 엉뚱한 곳(중복 처리 실패, 캐시 미스 폭증)에서 나타난다. 이 규약을 모르면 그 버그를 몇 시간씩 엉뚱한 데서 찾는다. AI가 생성한 엔티티/VO 코드에서 이 실수를 리뷰로 잡아낼 수 있는지도 본다.

## 1. 전제 — 해시 컬렉션은 어떻게 값을 찾는가

결론("hashCode를 같이 재정의해라")부터 외우면 응용이 안 된다. HashMap이 값을 찾는 절차를 먼저 보고, 그 절차의 어느 지점이 무너지는지를 짚는 순서로 간다.

### 1-1. 출발점 — `Object`가 기본으로 주는 두 메서드

모든 클래스는 `Object`를 상속하므로, 아무것도 안 써도 `equals()`와 `hashCode()`를 이미 갖고 있다. 문제는 그 기본 구현이 무엇을 기준으로 삼느냐다.

**`Object.equals()`의 기본 구현은 `this == obj` 한 줄이다.** 즉 "메모리에서 같은 객체를 가리키는가"만 본다. 이것을 **참조 동일성(reference identity)**이라 부른다. 필드 값이 아무리 똑같아도 `new`를 두 번 했으면 다른 객체이므로 false다.

**`Object.hashCode()`의 기본 구현은 객체마다 고유하게 부여되는 정수 하나를 돌려준다.** JVM이 객체마다 한 번 만들어 객체 헤더에 기록해 두는 이 값을 **식별 해시(identity hash)**라고 한다. 값을 어떻게 만드는지는 JVM 구현에 달렸지만(주소를 그대로 쓴다는 설명은 정확하지 않다), 우리에게 중요한 성질은 하나뿐이다.

**필드 값이 완전히 같아도 서로 다른 객체면 hashCode도 서로 다르다.**

```java
Money a = new Money("KRW", 1000);
Money b = new Money("KRW", 1000);

a.hashCode();  // 예: 1173230247
b.hashCode();  // 예: 856419764   -- 값이 같아도 다른 객체라 다른 수가 나온다
```

이 성질이 이 문서 전체 문제의 출발점이다. `equals()`만 "필드 값이 같으면 같다"로 바꾸면, **동등성의 정의는 값 기준으로 바뀌었는데 hashCode는 여전히 객체 기준**인 어긋난 상태가 된다. 왜 이 어긋남이 치명적인지는 조회 절차를 봐야 보인다.

### 1-2. 조회의 2단계 — 칸을 고르고, 칸 안에서 대조한다

`HashMap`의 본체는 **배열 하나**다. 각 칸을 **버킷(bucket, 양동이)**이라 부른다. 값을 찾을 때 배열 전체를 훑으면 O(n)이라 아무 이득이 없으므로, HashMap은 **"이 key라면 몇 번 칸에 있을 것"을 계산으로 알아내고 그 칸 하나만 열어본다.** 이 계산에 쓰는 것이 `hashCode()`다.

그런데 hashCode는 32비트 정수라 값의 범위가 배열 길이보다 훨씬 넓다. 그래서 배열 길이로 접어 넣는다(길이 16이면 0~15 사이로). 그 결과 **서로 다른 key가 같은 칸을 배정받는 일**이 반드시 생긴다. 이것을 **해시 충돌(collision)**이라 한다. 그래서 한 칸에는 여러 후보가 매달릴 수 있고, 그중 진짜를 골라내는 마지막 확인이 `equals()`다.

정리하면 조회는 항상 이 두 단계다.

```text
map.get(key) / set.contains(key)

  [1단계] key.hashCode() 로 정수를 얻고, 그것으로 배열 인덱스를 계산한다
          -> "5번 칸을 열어본다"는 결정. 이 칸 하나만 본다.

      table [0] [1] [2] [3] [4] [5] [6] [7] ...
                                  |
                                  v
  [2단계] 5번 칸에 매달린 후보들을 앞에서부터 꺼내 key.equals(후보) 로 대조

      table[5] -> Node(A) -> Node(B) -> Node(C)
                  (불일치)   (일치!)      -- 여기서 반환하고 종료

          5번 칸이 비어 있으면? -> 2단계는 아예 실행되지 않고 즉시 "없음"
```

마지막 줄에 밑줄을 그어야 한다. **1단계가 엉뚱한 칸을 열면, equals는 단 한 번도 호출되지 않는다.** equals를 아무리 정확하게 구현해도 호출될 기회 자체가 없다.

### 1-3. 그래서 hashCode를 빼먹으면 어디서 무너지는가

이제 1-1의 사실을 1-2의 절차에 대입해 보자.

`equals()`만 재정의한 `Money` 두 개, `new Money("KRW", 1000)`을 각각 만들어 하나는 `Set`에 넣고 다른 하나로 `contains`를 부른다.

```text
[넣을 때]  넣는 객체 a.hashCode() = 1173230247 (identity hash)
           1173230247 을 접어 인덱스 계산 -> 7번 칸
           table[7] -> Node(a)

[찾을 때]  찾는 객체 b.hashCode() = 856419764  (다른 객체이므로 다른 값)
           856419764 을 접어 인덱스 계산 -> 4번 칸
           table[4] -> (비어 있음)

           1단계에서 4번 칸으로 갔고, 그 칸은 비어 있다.
           -> equals는 호출되지 않는다. -> false
```

**무너지는 지점은 2단계(비교)가 아니라 1단계(칸 선택)다.** a와 b는 equals로는 완벽히 같지만, 애초에 만나지를 못한다. 우리가 정의한 동등성은 "값이 같으면 같다"인데, 칸 배정은 여전히 "객체마다 다르다" 기준으로 돌아가고 있기 때문이다.

**두 기준이 같은 필드를 보도록 맞춰야 조회가 성립한다.** 이것이 규약의 실체다.

### 1-4. 규약 — equals가 같으면 hashCode도 같아야 한다

`Object` 클래스의 Javadoc이 명시하는 계약(contract)은 이것이다.

- `equals()`가 **true**인 두 객체는 **반드시 같은** `hashCode()`를 반환해야 한다.
- 반대 방향은 강제가 아니다 — `hashCode()`가 같아도 `equals()`는 다를 수 있다.

왜 한쪽 방향만 강제되는지도 위 그림에서 읽힌다. **같은 hashCode는 "같은 칸에 모인다"는 뜻일 뿐**이고, 같은 칸에 모여도 2단계에서 equals가 걸러 준다. 즉 hashCode가 겹치는 것은 정확성에 아무 해가 없다(성능만 나빠진다). 반대로 **equals가 true인데 hashCode가 다르면 칸부터 갈리므로 복구할 방법이 없다.** 비대칭의 이유가 여기 있다.

비유하면 hashCode는 **도서관의 서가 번호**, equals는 **책 제목 대조**다. 같은 책인데 서가 번호를 매번 다르게 매기면, 사서(HashMap)는 엉뚱한 서가만 뒤지고 "그런 책 없다"고 답한다. 반대로 한 서가에 여러 책이 꽂혀 있는 것은 문제가 아니다 — 가서 제목을 하나씩 확인하면 되고, 조금 느려질 뿐이다.

## 2. 코드로 확인 — before / after

### 2-1. equals만 재정의한 클래스

```java
// Before: equals만 재정의 — hashCode 누락 (AI 생성 코드에서 흔한 형태)
public class Money {
    private final String currency;
    private final long amount;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money)) return false;
        Money m = (Money) o;
        return amount == m.amount && currency.equals(m.currency);
    }
    // hashCode() 재정의 없음 -> Object의 identity hash를 그대로 쓴다.
    // 즉 "값이 같으면 같다"는 equals의 선언과 칸 배정 기준이 어긋난 상태.
}

Set<Money> paid = new HashSet<>();
paid.add(new Money("KRW", 1000));
paid.contains(new Money("KRW", 1000));  // false — 다른 칸을 열어봤다
```

여기서 `false`가 나오는 이유를 "equals가 잘못돼서"로 설명하면 틀린 진단이다. equals는 정확하다. **호출되지 않았을 뿐이다.**

### 2-2. 두 메서드를 같은 필드로 묶는다

```java
// After: equals가 보는 필드와 hashCode가 쓰는 필드를 정확히 일치시킨다
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Money)) return false;
    Money m = (Money) o;
    return amount == m.amount && currency.equals(m.currency);
}

@Override
public int hashCode() {
    // equals가 비교에 쓰는 필드(currency, amount)와 반드시 같은 집합이어야 한다.
    // 여기에 필드를 하나라도 더 넣거나 빼면 규약이 다시 깨진다.
    return Objects.hash(currency, amount);
}
```

`Objects.hash(...)`는 넘긴 값들을 조합해 정수 하나를 만들어 주는 헬퍼다. 중요한 것은 함수의 종류가 아니라 **입력 필드 집합이 equals와 같은가**다. equals는 `currency, amount`를 보는데 hashCode는 `amount`만 쓰면, 값이 다른 두 객체가 같은 칸에 모일 뿐이라 정확성은 유지된다. 반대로 hashCode가 equals에 없는 필드까지 쓰면 **equals는 true인데 hashCode가 다른** 상황이 만들어져 규약이 깨진다.

### 2-3. 가변 필드로 hashCode를 만들면 — 컬렉션 안의 유령

규약을 지켰어도 무너지는 경우가 하나 더 있다. **컬렉션에 넣은 뒤 그 필드를 바꾸는 것**이다.

HashSet은 원소를 넣는 순간의 hashCode로 칸을 정하고, 그 뒤로는 아무것도 다시 계산하지 않는다. **필드가 바뀌었다는 통지를 받는 장치가 없다.** 그래서 객체는 "옛 해시값 기준 칸"에 남아 있는데, 조회는 "새 해시값 기준 칸"을 열어본다.

```java
Money m = new Money("KRW", 1000);   // amount가 final이 아닌 가변 버전이라고 하자
Set<Money> set = new HashSet<>();
set.add(m);
m.setAmount(2000);                  // 넣은 뒤에 필드를 바꿨다
```

이때 벌어지는 일을 시간순으로 따라가면 이렇다(칸 번호는 용량 16 기준의 예시값이다).

```text
t0  set.add(m)
    m.hashCode() = 8721  ->  8721 % 16 = 1   ->  1번 칸에 넣는다
    table[1] -> Node(m)
    table[4] -> (비어 있음)

t1  m.setAmount(2000)                      // 필드만 바꿨다
    m.hashCode() = 9012  ->  9012 % 16 = 4   ->  이제 "정답 칸"은 4번이다
    그러나 set은 아무 통지도 받지 않았다. m은 여전히 1번 칸에 매달려 있다.

    table[1] -> Node(m)      <- 아무도 열어보지 않게 된 칸
    table[4] -> (비어 있음)   <- 앞으로 조회가 열어볼 칸

t2  set.contains(m)   ->  4번 칸을 연다 -> 비어 있음        -> false
    set.remove(m)     ->  4번 칸을 연다 -> 없음            -> 삭제 실패
    set.size()        ->  1    (원소는 분명히 들어 있다)
    for (Money x : set) ...   ->  m이 나온다 (순회는 배열을 훑으므로 보인다)
```

**찾을 수도 지울 수도 없는데 크기에는 잡히고 순회에는 나오는 원소** — 이것이 "유령 항목"이다. 심지어 `set.contains(m)`이 자기 자신을 넣어서 물어봐도 false다.

```java
// After: 해시 컬렉션의 key/원소로 쓸 타입은 불변으로 만든다
public record Money(String currency, long amount) {}
// record는 모든 컴포넌트가 final이고 equals/hashCode를 쌍으로 자동 생성한다.
// 필드를 바꿀 방법 자체가 없으므로 위 시나리오가 성립하지 않는다.
```

값 객체(VO)를 불변으로 설계하라는 조언의 근거 중 하나가 정확히 이것이다. 불변으로 만들 수 없다면 최소한 **컬렉션에 담겨 있는 동안에는 equals/hashCode가 보는 필드를 건드리지 않는다**는 규율이 필요한데, 이 규율은 코드로 강제할 수 없어 언제든 깨진다.

## 3. 실무에서 나타나는 증상 — 예외가 안 나서 더 무섭다

이 버그의 공통점은 **컴파일도 되고 예외도 없다**는 것이다. 증상은 원인과 동떨어진 곳에서 나타난다.

- **중복 처리 실패**: "이미 처리한 주문인지" `Set`으로 걸렀는데, 같은 주문이 매번 새 객체로 들어와 검사를 전부 통과한다. 결과는 중복 결제, 중복 발송이다.
- **캐시 미스 폭증**: `HashMap<CacheKey, V>` 캐시에서 매번 못 찾아 적중률이 사실상 0%가 된다. 캐시는 "동작"하고 응답도 정상이라, 모니터링 그래프를 열어보기 전까지 아무도 모른다.
- **`Map.put` 덮어쓰기 실패**: 같은 키로 put했는데 기존 값이 안 바뀌고 항목이 계속 늘어난다. 사실상 메모리 누수다.
- 반대 방향 실수 — equals 없이 hashCode만 재정의하거나, 두 메서드가 서로 다른 필드를 보는 경우 — 도 같은 계열의 버그를 만든다.

**재현이 어려운 이유는 테스트가 통과하기 때문이다.** 단위 테스트는 대개 같은 참조를 넣고 같은 참조로 검증한다. 이러면 `equals`의 첫 줄 `if (this == o) return true;`가 걸리고 hashCode도 당연히 같으므로 전부 통과한다. 이 버그가 드러나는 것은 **값은 같지만 참조는 다른 객체가 만들어지는 순간** — 즉 DB 조회로 엔티티를 다시 읽거나, JSON/직렬화 데이터를 역직렬화하거나, 다른 요청에서 새로 생성한 객체가 들어올 때뿐이다. 그 조건은 대개 운영에서만 갖춰진다.

## 4. 꼬리질문 대비 포인트

### "hashCode만 같고 equals가 다르면 어떻게 되나요?"

규약 위반이 아니다. 그것이 바로 **해시 충돌**이고, 충돌은 오류가 아니라 유한한 배열에 무한한 값을 넣는 이상 반드시 생기는 정상 현상이다.

같은 칸에 여러 객체가 모이면 2단계에서 equals 비교 횟수가 늘어난다. 즉 **동작은 정확하고 성능만 저하된다.** 극단적으로 모든 객체가 `hashCode()`에서 상수를 반환하면 전부 한 칸에 몰려 HashMap이 사실상 연결 리스트가 되고, 조회가 O(1)에서 O(n)으로 나빠진다.

(가산점 포인트: 자바 8부터 HashMap은 한 버킷에 항목이 일정 수 이상 쌓이면 그 버킷만 연결 리스트에서 레드-블랙 트리로 바꿔(트리화) 최악을 O(log n)으로 완화한다. "정확성은 유지되고 성능만 나빠지며, 그 최악조차 어느 정도는 방어된다"까지 말하면 비대칭 규약의 이유가 완성된다.)

### "가변 필드로 hashCode를 만들면 무슨 일이 생기나요?"

`Set`에 넣은 뒤 그 필드를 수정하면 hashCode는 바뀌지만 객체는 **옛 해시값 기준 칸에 그대로** 남는다. 컬렉션은 필드 변경을 통지받는 장치가 없기 때문이다.

이후 `contains`는 새 해시값의 칸을 열어보므로 못 찾고, `remove`도 같은 이유로 실패한다. 그런데 `size()`에는 잡히고 순회에는 나온다 — **찾을 수도 지울 수도 없는 유령 항목**이 된다(2-3의 타임라인).

그래서 equals/hashCode의 기준 필드는 **불변**이거나, 최소한 컬렉션에 담긴 동안 바뀌지 않아야 한다. `record`나 final 필드로 값 객체를 설계하는 이유 중 하나가 이것이다.

### "JPA 엔티티에서는 equals/hashCode를 어떻게 재정의하나요?" (시니어 변별 포인트)

엔티티는 일반 값 객체와 사정이 다르다. 함정이 둘 겹친다.

**함정 1 — id는 영속화 전까지 null이다.** `@GeneratedValue`로 id를 받는 엔티티는 `persist` 전에는 id가 없다. 여기서 "id로 equals/hashCode를 만들면 된다"는 단순한 답이 두 방향으로 깨진다.

```java
// 잘못됨: id만으로 equals/hashCode — 영속화 전후로 정체성이 흔들린다
@Override public boolean equals(Object o) { /* id끼리 비교 */ }
@Override public int hashCode() { return Objects.hash(id); }
```

```text
[깨지는 경로 A] 아직 저장 안 한 엔티티 두 개
    new Order()  id = null
    new Order()  id = null
    -> id가 둘 다 null이라 "같다"고 판정된다. 서로 다른 주문인데.
       Set에 두 개를 넣으면 하나만 들어간다.

[깨지는 경로 B] Set에 먼저 넣고 나중에 저장
    t0  order.id = null,  hashCode = 0    -> 0번 칸에 들어간다
        set.add(order)
    t1  em.persist(order) -> id = 8471 이 채워진다
        hashCode = 8471 기준으로 바뀐다   -> 정답 칸이 이동
    t2  set.contains(order) -> false      -> 2-3에서 본 유령 항목과 동일
```

경로 B는 **가변 필드 문제의 특수한 형태**다. id는 "우리가 안 바꾸는 필드"처럼 보이지만, 실제로는 JPA가 저장 시점에 채워 넣는 가변 필드다.

**대응은 두 갈래고, 둘 다 트레이드오프가 있다.**

첫째, **비즈니스 키(자연 키)를 쓴다.** 주문번호, 사업자등록번호, 이메일처럼 **DB가 만들어 주는 것이 아니라 도메인이 태어날 때부터 갖고 있고 이후 바뀌지 않는 값**이 있다면 그것으로 equals/hashCode를 구성한다. 이것이 가장 깨끗한 답이다 — 영속화 전후로 값이 변하지 않으므로 두 함정이 모두 사라진다.

```java
// After: 생성 시점에 정해지고 이후 불변인 비즈니스 키를 쓴다
@Entity
public class Order {
    @Id @GeneratedValue private Long id;          // 대리 키(surrogate key)
    @Column(unique = true, updatable = false)
    private String orderNo;                        // 비즈니스 키: 주문 생성 시 부여, 이후 불변

    @Override
    public boolean equals(Object o) {
        // getClass() 대신 instanceof: 아래 '함정 2' 참고
        if (!(o instanceof Order other)) return false;
        return orderNo != null && orderNo.equals(other.orderNo);
    }

    @Override
    public int hashCode() {
        // 영속화 전후로 절대 변하지 않는 값만 쓴다. id를 넣으면 안 되는 이유가 경로 B.
        return Objects.hash(orderNo);
    }
}
```

둘째, 마땅한 비즈니스 키가 없을 때 쓰는 절충이 **hashCode는 클래스 단위의 고정값을 반환하고, equals는 id가 있을 때만 id로 비교**하는 방식이다. hashCode가 항상 같은 값이면 같은 타입의 엔티티가 전부 한 칸에 몰리므로 해시 분산은 포기하게 되지만, **값이 변하지 않으므로 규약 위반은 없다.** 4절 첫 꼬리질문에서 본 "hashCode가 겹쳐도 정확성은 유지된다"는 성질을 의도적으로 활용하는 설계다. 컬렉션에 담기는 엔티티 개수가 적다면 실무에서 감당할 만한 절충이다.

**함정 2 — 지연 로딩 프록시.** JPA는 지연 로딩을 위해 엔티티를 상속한 **프록시(proxy) 클래스**를 만들어 대신 넘겨준다. 그래서 `getClass()`로 타입을 비교하면 실제 엔티티와 프록시가 다른 클래스로 판정돼 실패한다. `instanceof`는 상속 관계를 인정하므로 안전하다. 또한 프록시 안에서는 필드에 직접 접근하면 아직 로딩되지 않은 빈 값이 나올 수 있으므로 **getter를 거쳐야** 프록시가 실제 데이터를 채워 넣는다.

**전형적인 리뷰 지적 대상은 모든 필드를 넣는 Lombok `@EqualsAndHashCode`나 IDE 자동 생성을 엔티티에 그대로 붙이는 것이다.** 연관 관계 필드까지 포함되면 equals 한 번에 지연 로딩 쿼리가 줄줄이 나가고, `updatedAt` 같은 가변 필드가 섞이면 컬렉션 안에서 유령 항목이 생긴다.

### "record나 Lombok을 쓰면 신경 안 써도 되나요?"

`record`는 모든 컴포넌트를 기준으로 equals와 hashCode를 **항상 쌍으로** 자동 생성하고 필드가 전부 final이므로, 값 객체에는 가장 안전한 선택이다. "쌍으로 만드는 것"과 "불변인 것" 두 조건을 언어가 강제해 준다.

Lombok `@EqualsAndHashCode`도 쌍은 보장한다. 다만 **어떤 필드를 기준으로 삼을지는 여전히 사람의 판단**이고(기본값은 모든 필드), 그 판단이 틀리면 위 엔티티 함정으로 그대로 들어간다.

AI 생성 코드 리뷰에서 기계적으로 볼 지점은 셋이다. equals만 있고 hashCode가 없는 클래스, 두 메서드가 서로 다른 필드 집합을 보는 클래스, 해시 컬렉션의 키로 쓰이는데 setter가 열려 있는 클래스.

### "equals 재정의 시 지켜야 할 일반 규약은 무엇인가요?"

다섯 가지다. **반사성**(자기 자신과는 항상 같다), **대칭성**(a가 b와 같으면 b도 a와 같다), **추이성**(a=b이고 b=c면 a=c), **일관성**(필드가 안 변하면 몇 번을 호출해도 결과가 같다), **null과는 항상 false**.

실무에서 가장 자주 깨지는 것은 **대칭성**이고, 깨지는 자리는 거의 항상 **상속**이다. 부모 `Point`와 자식 `ColorPoint`가 있을 때, 부모의 equals는 좌표만 보고 자식의 equals는 좌표와 색을 본다고 하자.

```text
Point      p  = new Point(1, 2);
ColorPoint cp = new ColorPoint(1, 2, RED);

p.equals(cp)   -> true   (부모 기준: 좌표만 같으면 같다)
cp.equals(p)   -> false  (자식 기준: 색까지 봐야 하는데 p에는 색이 없다)
```

방향에 따라 답이 달라진다. 컬렉션은 어느 방향으로 비교할지 보장하지 않으므로, 이 상태에서는 `contains`의 결과가 원소 순서에 따라 달라지는 예측 불가능한 동작이 된다.

(가산점 포인트: 그래서 `instanceof`로 비교할 것인가 `getClass()`로 비교할 것인가라는 오래된 트레이드오프가 나온다. `getClass()`는 대칭성을 지키는 대신 하위 클래스를 영영 같지 않게 만들어 리스코프 치환 원칙과 충돌하고, `instanceof`는 그 반대다. 값 객체라면 **상속 자체를 피하고 클래스를 final로 막는 것**이 정석이고, 자바에서 `record`가 암묵적으로 final인 이유이기도 하다. 다만 JPA 엔티티는 프록시 때문에 `getClass()`를 쓸 수 없으므로 `instanceof` 쪽을 택할 수밖에 없다.)

## 한 줄 요약

해시 컬렉션은 hashCode로 칸을 고르고 equals로 대조하는 2단계이고 1단계가 어긋나면 2단계는 호출조차 되지 않으므로, 동등성의 정의를 값 기준으로 바꿨다면(equals 재정의) 칸 배정 기준(hashCode)도 정확히 같은 필드로 함께 바꿔야 한다 — 그리고 그 기준 필드는 컬렉션에 담긴 동안 절대 변하지 않아야 한다. 한쪽만 바꾸거나 나중에 값이 변하면 "넣었는데 못 찾는" 버그가 예외 하나 없이 조용히 시작된다.
