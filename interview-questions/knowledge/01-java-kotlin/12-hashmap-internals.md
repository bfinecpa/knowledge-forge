# HashMap 내부 동작 — 해시 충돌 처리, 리사이징, 트리화

> 핵심 관전 포인트: **HashMap은 "배열(버킷) + 충돌 시 연결 리스트, 심하면 레드-블랙 트리"다. key의 hashCode를 상위 비트와 섞어(spread) `(n-1) & hash`로 배열 인덱스를 정하고, 같은 칸에 충돌하면 리스트로 연결해 equals로 찾는다. 원소 수가 용량 × 0.75를 넘으면 배열을 2배로 늘려 전체 재배치하며(그래서 대량 삽입 전 초기 용량 지정이 유효한 최적화), 한 버킷의 리스트가 8을 넘고 테이블이 64 이상이면 그 버킷만 트리로 바꿔 최악 성능을 O(n)에서 O(log n)으로 방어한다.**

---

## 0. 질문 + 의도

**질문**: "`HashMap`의 내부 동작(해시 충돌 처리, 리사이징, 트리화)을 설명해주세요."

**출제 의도**: 자료구조 하나를 끝까지 파본 적 있는지의 표본 검사. 리사이징 비용을 아는 사람은 초기 용량 지정 같은 사소하지만 대량 처리에서 유의미한 최적화를 자연스럽게 한다.

## 1. 전체 구조와 인덱스 계산 — 비트를 한 자리씩 따라간다

### 1-1. 본체는 Node 배열 하나

HashMap의 본체는 **Node 배열 하나**다(내부 필드 이름이 그대로 `table`이다). 각 칸을 **버킷(bucket, 양동이)**이라 부른다.

비유하면 아파트 우편함이다. key의 hashCode는 "몇 호 우편함에 넣을지"를 정하는 주소 계산이고, `get`은 그 우편함 한 칸만 열어보는 것이다. 배열 전체를 뒤지지 않으니 평균 O(1)이다 — HashMap의 존재 이유가 이 한 줄이다.

```java
// put(key, value)의 뼈대 (개념 코드)
int hash  = spread(key.hashCode());     // ① 해시 보정 (1-4)
int index = (table.length - 1) & hash;  // ② 버킷 인덱스 결정 (1-2)
// ③ table[index]가 비었으면 새 Node, 있으면 충돌 처리 (2절)
```

이 세 줄 중 ①과 ②가 전부 비트 연산이다. 이 문서에서 가장 중요한 부분이고, 동시에 눈으로만 훑으면 절대 이해되지 않는 부분이다. 비트를 실제로 늘어놓고 한 단계씩 계산해 보자.

### 1-2. `(n-1) & hash`가 왜 `hash % n`과 같은가

hashCode는 32비트 정수라서 값의 범위가 배열 길이보다 훨씬 넓다. 예를 들어 `"apple".hashCode()`는 93029210인데 배열 길이는 16이다. 그러니 **넓은 값을 0~15 사이로 접어 넣어야** 한다. 이 "접기"의 교과서적 방법이 나머지 연산 `hash % 16`이다.

그런데 HashMap의 실제 코드는 `%`를 쓰지 않는다. `(n-1) & hash`를 쓴다. 이 둘이 같은 값이 나오는 이유부터 보자.

**먼저 10진수로 감을 잡는다.** `12345 % 100`은 얼마인가. 계산기가 필요 없다. **45다 — 뒤 두 자리를 그대로 떼어내면 된다.** 100이 10의 거듭제곱(10^2)이고 우리가 10진수를 쓰기 때문에 성립하는 일이다.

**2진수에서도 똑같다.** 배열 길이가 16 = 2^4이면, **16으로 나눈 나머지는 하위 4비트를 그대로 떼어낸 값**이다. hash가 23일 때 직접 따라가 보자.

```text
23을 2진수로 쓰면      0001 0111

16으로 나눈다 = 오른쪽으로 4칸 민다
    몫    0001              = 1
    나머지     0111         = 7      <- 밀려 나간 하위 4비트가 곧 나머지다

검산: 23 = 16 x 1 + 7      나머지 7. 맞다.
```

즉 우리가 원하는 것은 **"하위 4비트만 남기고 위쪽은 전부 버리기"**다. 그리고 비트 AND가 정확히 그 일을 한다. 어떤 비트든 0과 AND하면 0이 되고, 1과 AND하면 원래 값이 그대로 남기 때문이다.

```text
n = 16 이므로  n - 1 = 15 = 0000 1111   <- 하위 4비트만 1인 "마스크"

    hash      0001 0111   (23)
  & mask      0000 1111   (15)
  ----------------------
    결과      0000 0111   = 7

위쪽 비트는 0과 AND되어 전부 지워지고, 하위 4비트만 살아남았다.
23 % 16 = 7 과 정확히 같은 값이다.
```

**여기서 `n - 1`의 정체가 드러난다.** 2의 거듭제곱에서 1을 빼면 자릿수가 하나 내려가면서 **하위 비트가 전부 1인 형태**가 된다. 10진수로 100 - 1 = 99가 되는 것과 같은 원리다.

```text
n = 16  = 0001 0000   ->  n-1 = 15  = 0000 1111
n = 32  = 0010 0000   ->  n-1 = 31  = 0001 1111
n = 64  = 0100 0000   ->  n-1 = 63  = 0011 1111
```

**그래서 HashMap의 용량은 항상 2의 거듭제곱이다.** 생성자에 17을 넘겨도 내부에서 32로 올려 잡는다. 2의 거듭제곱이 아니면 `n-1`이 깔끔한 마스크가 되지 않아 이 트릭 자체가 성립하지 않는다.

바꾸는 이유는 둘이다.

**(1) 속도.** 정수 나눗셈은 CPU에서 가장 비싼 산술 연산 중 하나로 수십 사이클이 걸리는 반면, 비트 AND는 1사이클이다. `get`/`put` 한 번마다 반드시 통과하는 자리이므로 이 차이가 그대로 처리량에 반영된다.

**(2) 음수 처리.** hashCode는 음수일 수 있다. 자바의 `%`는 음수 피연산자에 대해 음수를 반환하므로 `-23 % 16`은 `-7`이고, 이 값을 배열 인덱스로 쓰면 그 자리에서 예외가 난다. 반면 AND는 부호 비트까지 그냥 지워 버리므로 **결과가 항상 0 이상**이다.

```text
-23 의 32비트 표현 (2의 보수)  ... 1111 1110 1001
                     & 마스크  ... 0000 0000 1111
                     -------------------------
                       결과              1001  = 9    <- 유효한 인덱스
```

### 1-3. 하위 비트만 쓰는 데서 생기는 약점

방금 본 계산에는 대가가 있다. `(n-1) & hash`는 **hash의 하위 몇 비트만 보고 상위 비트는 통째로 버린다.** 테이블이 16이면 하위 4비트, 나머지 28비트는 결과에 아무 영향도 주지 못한다.

그래서 **상위 비트만 다르고 하위 비트가 같은 key들**이 있으면 전부 같은 칸으로 몰린다. 두 hash를 나란히 놓고 대조해 보면 한눈에 보인다.

```text
hashA = 23        0000 0000 0000 0000  0000 0000 0001 0111
hashB = 39        0000 0000 0000 0000  0000 0000 0010 0111
                                                    ^^^
                                        여기(5번째 비트)가 다르다

& 마스크 1111                                       0111  -> A는 7번 칸
                                                    0111  -> B도 7번 칸

두 hash는 분명히 다른 값인데 같은 칸에 들어간다.
마스크가 하위 4비트만 보므로, 그보다 위에서 아무리 달라도 결과는 같다.
```

이것이 우연한 사고가 아니라 **패턴으로 발생한다는 것**이 문제다. 극단적인 예를 보자. hashCode가 65536의 배수로 나오는 클래스가 있다고 하자(직접 만든 hashCode가 어떤 값에 큰 상수를 곱하는 형태면 충분히 생길 수 있다).

```text
0            0000 0000 0000 0000  0000 0000 0000 0000   & 1111 -> 0
65536        0000 0000 0000 0001  0000 0000 0000 0000   & 1111 -> 0
131072       0000 0000 0000 0010  0000 0000 0000 0000   & 1111 -> 0
196608       0000 0000 0000 0011  0000 0000 0000 0000   & 1111 -> 0

전부 0번 칸. 하위 16비트가 모두 0이기 때문이다.
서로 다른 값 수십만 개가 한 칸에 매달린다 -> HashMap이 연결 리스트가 된다.
```

hashCode 자체는 잘 흩어져 있는데도, **인덱스 계산이 하위 비트만 보는 바람에** 분산이 통째로 무너진 것이다. 이 약점을 메우는 장치가 spread다.

### 1-4. spread — 상위 비트의 정보를 하위로 끌어내린다

HashMap은 인덱스를 계산하기 전에 hashCode를 한 번 가공한다. 이 가공을 **spread(퍼뜨리기)**라고 부른다.

```java
static final int hash(Object key) {
    int h;
    // key.hashCode()를 그대로 쓰지 않고, 상위 16비트를 하위 16비트에 XOR로 섞는다.
    // 인덱스 계산이 하위 비트만 보므로, 버려질 상위 비트의 정보를
    // 미리 하위로 끌어내려 반영해 두는 것이다.
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

두 연산자의 뜻을 짚고 가자. `>>>`는 **부호를 무시하고 오른쪽으로 미는 시프트**다. `h >>> 16`은 32비트 값을 16칸 오른쪽으로 밀어서, **원래 상위 16비트를 하위 16비트 자리로 옮긴** 값이다. `^`는 **XOR(배타적 논리합)**로, 두 비트가 다르면 1 같으면 0을 내놓는다. 정보를 섞는 데 쓰는 이유는 **한쪽 비트가 바뀌면 결과 비트도 반드시 바뀌기** 때문이다(AND나 OR는 한쪽이 0이나 1로 고정되면 다른 쪽 변화를 삼켜 버린다).

1-3에서 전부 0번 칸으로 몰렸던 값들에 spread를 적용해 보자.

```text
[h = 65536]
h            0000 0000 0000 0001  0000 0000 0000 0000
h >>> 16     0000 0000 0000 0000  0000 0000 0000 0001   <- 상위 16비트가 내려왔다
XOR          0000 0000 0000 0001  0000 0000 0000 0001
& 1111                                          0001   -> 1번 칸

[h = 131072]
h            0000 0000 0000 0010  0000 0000 0000 0000
h >>> 16     0000 0000 0000 0000  0000 0000 0000 0010
XOR          0000 0000 0000 0010  0000 0000 0000 0010
& 1111                                          0010   -> 2번 칸

[h = 196608]
h            0000 0000 0000 0011  0000 0000 0000 0000
h >>> 16     0000 0000 0000 0000  0000 0000 0000 0011
XOR          0000 0000 0000 0011  0000 0000 0000 0011
& 1111                                          0011   -> 3번 칸
```

전부 0번 칸에 몰리던 값들이 0, 1, 2, 3번 칸으로 흩어졌다. **"어차피 하위 비트만 볼 거라면, 상위 비트의 정보도 하위에 반영해 두자"**는 발상이고, 비용은 시프트 한 번과 XOR 한 번이 전부다.

주의할 점은 spread가 **완전한 해결책이 아니라 값싼 보정**이라는 것이다. 상위 16비트를 하위에 섞을 뿐이므로, 애초에 hashCode가 전부 같은 값이면 spread를 해도 전부 같다. 근본적인 분산 품질은 여전히 hashCode 구현의 책임이다.

(key가 null이면 hash가 0이 되어 항상 0번 칸으로 간다. HashMap이 null key를 하나 허용하는 방식이 이것이다.)

## 2. 해시 충돌 처리 — 같은 칸이면 리스트로 이어 붙인다

### 2-1. 분리 연결법(separate chaining)

서로 다른 key가 같은 인덱스를 받는 일은 — hashCode가 같아서든, 달라도 1-3처럼 하위 비트가 같아서든 — 반드시 생긴다. 유한한 배열에 무한한 값을 넣는 이상 피할 수 없다. 이것을 **해시 충돌**이라 하고, HashMap의 대응은 **그 칸의 노드들을 연결 리스트로 이어 붙이는 것**이다. 칸 하나에 여러 개를 매달아 둔다고 해서 **분리 연결법(separate chaining)**이라 부른다.

```text
table[5] -> Node("apple") -> Node("grape") -> Node("melon")
```

- **put**: 리스트를 순회하며 `hash가 같고 equals도 true`인 노드가 있으면 value를 교체하고, 없으면 **리스트 끝에 추가**한다(tail insert).
- **get**: 인덱스로 칸을 찾고, 그 칸의 리스트를 순회하며 equals로 확인한다.

### 2-2. equals/hashCode 규약이 여기서 도출된다

이 구조에서 두 가지 실무 규칙이 그대로 따라 나온다.

**첫째, equals를 재정의하면 hashCode도 재정의해야 하는 이유가 여기 있다.** hashCode가 다르면 **애초에 다른 칸을 열어보므로** equals가 true여도 영영 만나지 못한다. 조회는 "칸 고르기 → 칸 안에서 대조"의 2단계이고, 1단계에서 갈리면 2단계는 실행조차 되지 않는다. "분명 넣었는데 없다" 버그의 정체다(자세한 것은 `03-equals-hashcode-contract.md`).

**둘째, 가변 객체를 key로 쓰면 안 된다.** 넣은 뒤 key의 필드를 바꿔 hashCode가 달라지면, 그 엔트리는 "옛 주소의 우편함"에 남아 있는데 조회는 새 주소의 우편함을 연다. HashMap은 필드 변경을 통지받는 장치가 없으므로 되돌릴 방법이 없다.

```java
// before: 가변 객체를 key로 — 시한폭탄
Member m = new Member("kim");   // hashCode가 name 기반이라고 하자
map.put(m, profile);
m.setName("lee");               // key의 해시가 바뀌었다
map.get(m);                     // null — 새 해시로 계산된 다른 칸을 열어본다
map.remove(m);                  // 삭제도 실패 — 지울 수도 찾을 수도 없는 유령이 된다

// after: key는 불변으로 (불변 필드만으로 equals/hashCode를 구성한다)
record MemberKey(String id) {}  // record = 모든 필드 final + equals/hashCode 자동 생성
map.put(new MemberKey("kim-001"), profile);
```

### 2-3. (가산점 포인트) Java 7의 무한 루프 — 삽입 위치가 바뀐 이유

Java 7까지는 충돌 시 리스트의 **머리에** 삽입했다(head insert). 새 노드를 맨 앞에 꽂는 편이 리스트 끝까지 걸어가지 않아도 되어 빨랐기 때문이다.

문제는 리사이징과 겹칠 때였다. 리사이징은 각 칸의 리스트를 새 배열로 옮기는데, head insert 방식에서는 옮기는 과정에서 **리스트의 순서가 뒤집힌다.** 두 스레드가 같은 리스트를 동시에 옮기면 한쪽이 뒤집는 도중에 다른 쪽이 끼어들어 **노드 A의 next가 B를 가리키고 B의 next가 다시 A를 가리키는 고리**가 만들어질 수 있었다.

```text
정상:      table[3] -> A -> B -> null        (끝이 있으므로 순회가 종료된다)
사고 후:   table[3] -> A -> B -> A -> B ...  (null을 영영 만나지 못한다)
```

이 상태에서 `get`을 호출하면 **리스트를 끝없이 도는 무한 루프**에 빠진다. 증상은 특정 스레드의 CPU가 100%에 고정된 채 응답이 없는 것이었고, 원인 규명이 어려워 유명한 장애 패턴으로 남았다.

Java 8에서 tail insert로 바뀌면서 순서가 뒤집히지 않게 되어 **이 형태의 무한 루프는 사라졌다.** 하지만 여기서 결론을 잘못 내리면 안 된다. **HashMap은 여전히 동기화가 전혀 없는 thread-unsafe 자료구조**이고, 동시 쓰기에서 put이 유실되거나 `size`가 실제 원소 수와 어긋나는 일은 그대로 일어난다. 동시 접근이 있으면 `ConcurrentHashMap`을 쓴다(→ `13-concurrenthashmap-internals.md`).

## 3. 성능을 지키는 두 장치 — 리사이징과 트리화

1절과 2절을 합치면 HashMap의 성능은 한 가지 조건에 걸려 있다. **한 칸에 매달린 리스트가 짧아야 한다.** 리스트가 길어지면 2단계 순회 비용이 그대로 올라가 O(1)이 무너진다.

리스트가 길어지는 원인은 둘이고, 원인이 다르니 처방도 다르다.

- **원소가 늘어서 전체적으로 리스트가 길어진다** → 칸 수를 늘려 흩뜨린다. **리사이징**.
- **hashCode가 나쁘거나 공격을 받아 특정 칸에만 몰린다** → 칸을 늘려도 소용없다. 그 칸의 자료구조 자체를 바꾼다. **트리화**.

### 3-1. 리사이징 — 언제 늘리는가

기준은 **`원소 수 > 용량 × load factor`**다. load factor(적재율)는 "배열이 얼마나 차면 늘릴 것인가"의 기준값이고 기본값은 **0.75**다. 이 곱셈 결과를 내부에서는 **threshold(임계값)**라 부른다.

```text
기본 용량 16, load factor 0.75  ->  threshold = 12

put 12번째까지: size 12 <= 12   -> 확장 없음
put 13번째:     size 13 >  12   -> resize! 용량 16 -> 32, threshold 12 -> 24
```

확장 폭은 **정확히 2배**다. 1-2에서 본 대로 용량이 2의 거듭제곱이어야 마스크 트릭이 성립하므로, 늘릴 때도 2의 거듭제곱을 유지해야 한다.

비용은 **O(n)**이다. 새 배열을 만들고 **기존 노드 전부를 새 인덱스로 옮겨야** 하기 때문이다. 이 비용이 3-4의 실무 최적화로 이어진다.

### 3-2. load factor 0.75는 왜 그 값인가

공간과 시간의 절충점이다.

**낮추면**(예: 0.5) 배열이 절반만 차도 확장하므로 칸이 널널해 충돌이 줄어든다. 조회는 빨라지지만 빈 칸이 많아 메모리가 낭비되고, 확장이 더 자주 일어나 리사이징 비용이 늘어난다.

**높이면**(예: 0.95) 배열을 거의 꽉 채워 쓰므로 메모리 효율은 좋지만, 칸당 평균 원소 수가 올라가 리스트 순회 비용이 커진다.

0.75는 **"충돌 확률을 충분히 낮게 유지하면서 공간 낭비도 참을 만한"** 지점으로 잡은 기본값이다. 그리고 이 값은 3-6의 트리화 임계값 8과 연결되어 있다 — 0.75라는 전제 위에서 계산했기 때문에 8이라는 숫자가 의미를 갖는다.

실무에서 이 값을 바꿀 일은 사실상 없다. 조정할 것이 있다면 load factor가 아니라 **초기 용량**이다. 리사이징 횟수를 줄이는 쪽이 실익이 훨씬 크다.

### 3-3. 재배치의 묘수 — 비트 하나만 보면 된다

리사이징에서 노드를 옮길 때, 각 노드의 새 인덱스를 다시 계산해야 할 것 같다. 그런데 Java 8은 **재계산하지 않는다.** 비트 하나만 확인한다. 왜 그것으로 충분한지 실제 비트로 확인해 보자.

용량이 16에서 32로 늘어나면 마스크가 한 비트 늘어난다.

```text
n = 16  ->  마스크 n-1 = 15 =  0 1111
n = 32  ->  마스크 n-1 = 31 =  1 1111
                              ^
                    새로 보게 된 비트가 딱 하나 늘었다
```

**늘어난 그 비트 자리의 값이 정확히 oldCap(=16)이다.** 16 = `1 0000`이므로, "새로 보게 된 비트"만 1이고 나머지는 0인 값이다.

그러면 새 인덱스는 **옛 인덱스에 그 비트 값(있으면 16, 없으면 0)을 더한 것**이 된다. 1-3에서 같은 7번 칸에 있던 hash 23과 39로 따라가 보자.

```text
[hash = 23]
                    0001 0111
옛 인덱스  & 0 1111  0000 0111  = 7
새 인덱스  & 1 1111  0001 0111  = 23        =  7 + 16   -> 옮겨야 한다

판정에 쓰는 연산:  hash & oldCap
                    0001 0111
                  & 0001 0000   (= 16)
                  -----------
                    0001 0000   != 0   -> "새 비트가 1이다" -> index + oldCap

[hash = 39]
                    0010 0111
옛 인덱스  & 0 1111  0000 0111  = 7
새 인덱스  & 1 1111  0000 0111  = 7         =  제자리     -> 안 옮겨도 된다

판정에 쓰는 연산:  hash & oldCap
                    0010 0111
                  & 0001 0000   (= 16)
                  -----------
                    0000 0000   == 0   -> "새 비트가 0이다" -> 제자리
```

두 노드가 같은 칸(7번)에 있었는데 확장 후에는 7번과 23번으로 깔끔하게 갈렸다. 그리고 그 판정에 필요한 것은 **`hash & oldCap`이 0인지 아닌지, 단 한 번의 AND 연산**이다.

```text
hash & oldCap == 0  ->  제자리 (index 그대로)
hash & oldCap != 0  ->  index + oldCap 으로 이동
```

그래서 Java 8의 리사이징은 각 칸의 리스트를 순회하며 **lo(제자리) 리스트와 hi(+oldCap) 리스트 둘로 쪼개기만** 하고, 각각을 새 배열의 `index`와 `index + oldCap`에 통째로 걸어 둔다. 해시를 다시 계산할 필요도, 노드를 하나씩 새 위치에 삽입할 필요도 없다. 통계적으로 절반은 이사조차 하지 않는다.

**다만 오해하면 안 되는 것이 있다.** 재배치가 값싸졌다는 것이지 공짜가 된 것이 아니다. **전체 노드를 한 번씩 만져 lo/hi를 판정해야 하므로 O(n) 비용 자체는 그대로 남는다.**

### 3-4. 실무 최적화 — 대량 삽입 전 초기 용량 지정

리사이징 비용을 아는 사람이 자연스럽게 하는 한 줄짜리 최적화가 있다.

```java
// before: 기본 용량 16에서 시작 -> 10만 건 넣는 동안 리사이징이 십수 회 일어난다
Map<String, Order> map = new HashMap<>();
for (Order o : orders) map.put(o.getId(), o);   // 확장 때마다 전체 노드 재배치

// after: 예상 원소 수를 0.75로 나눈 값을 초기 용량으로 준다 -> 리사이징 0회
Map<String, Order> map = new HashMap<>((int) (orders.size() / 0.75f) + 1);

// Java 19 이상이면 같은 계산을 대신 해주는 팩토리 메서드가 있다
Map<String, Order> map = HashMap.newHashMap(orders.size());
```

**왜 원소 수를 그대로 넣으면 안 되는가.** 생성자 인자는 "담을 원소 수"가 아니라 **용량(배열 길이)**이기 때문이다. 여기에 load factor가 다시 곱해진다.

```text
new HashMap<>(100_000) 을 쓴 경우

  용량은 2의 거듭제곱으로 올림된다  ->  131,072
  threshold = 131,072 x 0.75       =  98,304
  10만 건을 넣으면 98,304를 넘는다  ->  결국 리사이징이 한 번 일어난다

new HashMap<>((int)(100_000 / 0.75f) + 1) 을 쓴 경우

  인자 133,334  ->  용량 262,144 로 올림
  threshold = 262,144 x 0.75       =  196,608
  10만 건은 여유롭게 들어간다       ->  리사이징 0회
```

트레이드오프도 같이 말할 수 있어야 한다. 리사이징을 없앤 대가로 **배열을 더 크게 잡아 메모리를 더 쓴다.** 원소 수를 미리 알 수 있는 대량 적재에서는 남는 장사지만, 실제로는 훨씬 적게 들어올 Map에 큰 초기 용량을 박아 두면 빈 배열만 낭비하는 셈이 된다.

### 3-5. 트리화 — 리스트의 최악을 O(log n)으로 방어

리사이징으로도 해결되지 않는 경우가 있다. **원소가 특정 칸에만 몰릴 때**다. 칸을 아무리 늘려도 전부 한 칸으로 간다면 아무 소용이 없다.

이런 상황은 두 경로로 생긴다.

- **hashCode 품질이 나쁠 때.** 극단적으로 `return 1;` 같은 상수를 반환하는 hashCode가 있으면 모든 원소가 한 칸에 매달린다.
- **공격받을 때.** 해시가 충돌하는 key를 의도적으로 대량 주입하는 공격을 **해시 플러딩(hash-flooding) DoS**라고 한다. 요청 파라미터가 그대로 Map의 key가 되는 웹 서버에서 실제 공격 사례가 있었다. 파라미터 수백 개짜리 요청 몇 개로 CPU를 태울 수 있다.

두 경우 모두 리스트 하나에 전부 매달려 조회가 O(n)으로 전락한다. Java 8부터는 여기에 방어선을 하나 둔다. **한 버킷이 임계를 넘으면 그 버킷만 레드-블랙 트리로 바꾼다.**

**레드-블랙 트리**는 삽입·삭제 때 스스로 균형을 잡아 한쪽으로 치우치지 않게 유지하는 이진 탐색 트리다. 어떤 순서로 넣어도 높이가 대략 log n으로 유지되므로, 탐색이 O(log n)을 보장한다. 원소 100만 개면 리스트는 최악 100만 번 비교인데 트리는 20번 남짓이다.

바뀌는 것은 **그 칸 하나뿐**이라는 점이 중요하다. HashMap 전체가 트리가 되는 것이 아니라, 문제가 생긴 버킷만 국소적으로 자료구조를 교체한다.

### 3-6. 트리화 조건 — 8, 6, 64라는 숫자의 근거

| 전환 | 조건 |
|---|---|
| 리스트 → 트리 | 한 버킷의 노드가 8개를 넘어설 때 **그리고** 테이블 길이가 64 이상일 때 |
| (테이블이 64 미만이면) | 트리화 대신 **리사이징**을 한다 |
| 트리 → 리스트 | 리사이징 등으로 그 버킷이 6개 이하로 줄면 해제한다(untreeify) |

세 숫자에 각각 이유가 있다.

**왜 8인가 — 정상 상황에서는 절대 도달하지 않는 선이다.**

hashCode가 제대로 흩어져 있다면, 원소들은 버킷에 랜덤하게 떨어진다. 이때 "한 버킷에 k개가 들어갈 확률"은 **포아송 분포**(드물게 일어나는 사건이 정해진 구간 안에 몇 번 일어날지의 확률 분포)를 따른다.

이 분포의 평균값 λ는 **칸 하나당 평균 원소 수**다. load factor가 0.75이므로 확장 직전에는 칸당 0.75개, 막 2배로 확장한 직후에는 절반인 0.375개다. 즉 실제 운영 중 평균은 **대략 0.5 언저리**를 오간다. λ = 0.5로 계산한 확률표가 JDK 소스 주석에 그대로 실려 있다.

```text
한 버킷에 들어가는 노드 수     확률
        0                  0.60653066     <- 절반 이상의 칸은 비어 있다
        1                  0.30326533
        2                  0.07581633
        3                  0.01263606
        4                  0.00157952
        5                  0.00015795
        6                  0.00001316
        7                  0.00000094
        8                  0.00000006     <- 1억 번에 6번 꼴
```

**8개가 쌓일 확률은 1억분의 6이다.** 즉 8이라는 숫자는 성능 임계값이라기보다 **신호선**이다. "정상 hashCode라면 사실상 일어나지 않는 일이 일어났다 = 나쁜 해시이거나 공격이다"를 판정하는 선인 것이다.

이 선을 낮게 잡으면 안 되는 이유도 분명하다. 트리 노드는 부모·좌우 자식·이전 노드·색깔 정보를 들고 있어야 해서 **일반 노드보다 대략 두 배 무겁다.** 정상 상황에서는 만들지 않는 편이 이득이다.

**왜 해제는 6인가 — 경계에서의 진동을 막기 위해서다.**

임계값이 8 하나뿐이라면, 노드 수가 7과 8 사이를 오갈 때마다 트리화와 해제가 반복된다. 넣었다 뺐다 하는 한 번마다 자료구조 전체를 바꾸는 비싼 작업이 일어나는 것이다.

```text
[임계가 8 하나뿐이라면]
   7개 -> put -> 8개: 트리화(비쌈) -> remove -> 7개: 해제(비쌈) -> put -> 트리화...

[트리화 8, 해제 6으로 벌려 놓으면]
   8개에서 트리가 되고, 7개로 줄어도 트리를 유지한다.
   6개까지 내려가야 비로소 리스트로 돌아간다. 왕복하려면 2칸을 움직여야 한다.
```

이렇게 **켜는 기준과 끄는 기준을 벌려 놓아 경계 진동을 막는 기법**을 히스테리시스(hysteresis)라고 한다. 온도 조절기가 설정 온도 정확히에서 껐다 켰다 하지 않고 위아래로 여유를 두는 것과 같은 발상이다.

**왜 테이블 64 이상이라는 조건이 붙는가 — 원인 진단이 다르기 때문이다.**

테이블이 작을 때(16, 32) 한 칸에 8개가 몰리는 것은 **hashCode가 나빠서가 아니라 칸이 부족해서**일 가능성이 높다. 칸이 16개뿐인데 원소가 12개면, 해시가 아무리 좋아도 어딘가는 몰린다.

이 경우 올바른 처방은 트리화가 아니라 **칸을 늘리는 것**이다. 그래서 HashMap은 임계를 넘겨도 테이블 길이가 64 미만이면 트리화 대신 리사이징을 한다. 리사이징으로 흩어지면 문제가 자연히 해소되고, **리사이징으로도 안 흩어진다면 그때야말로 진짜 나쁜 해시라는 진단이 선다.**

정리하면 세 숫자는 각각 "비정상 판정선(8)", "진동 방지(6)", "오진 방지(64)"를 담당한다.

### 3-7. (가산점 포인트) 트리 안에서는 무엇을 기준으로 정렬하는가

이진 탐색 트리는 원소 사이에 **순서**가 있어야 성립한다. 그런데 Map의 key는 아무 타입이나 될 수 있고, 순서가 정의돼 있으리라는 보장이 없다. HashMap은 이 문제를 3단계로 푼다.

1. 먼저 **hash 값끼리 비교**한다. 같은 칸에 있어도 hash가 다를 수 있기 때문이다(1-3의 경우).
2. hash까지 같으면, key가 `Comparable`을 구현했을 때 **`compareTo`로 비교**한다.
3. 그것도 안 되면 `System.identityHashCode`로 임의의 일관된 순서를 만든다(tie-break).

실무적 함의는 2번에 있다. **hashCode가 전부 같아도 key가 `Comparable`이면 O(log n)이 온전히 보장된다.** 해시 플러딩 공격의 주된 표적인 `String`이 `Comparable`이므로, 이 방어가 가장 필요한 자리에서 가장 잘 작동한다.

### 3-8. 흐름 한 장 정리 — put이 겪는 일

```text
put(key, value)
 |
 +- hash  = key.hashCode() ^ (h >>> 16)     // 상위 비트를 하위로 섞는 보정 (1-4)
 +- index = (n-1) & hash                     // 하위 k비트만 남겨 칸 결정 (1-2)
 |
 +- 그 칸이 비었나?      -> 새 Node를 놓고 끝
 +- 같은 key가 있나?     -> hash 같고 equals true면 value만 교체
 +- 아니면 리스트 끝에 추가 (tail insert) -> 그 칸이 8개를 넘었나?
 |        |
 |        +- 테이블 < 64  -> resize (칸 부족이 원인일 가능성이 높다) (3-6)
 |        +- 테이블 >= 64 -> treeify (그 칸만 레드-블랙 트리로) (3-5)
 |
 +- size > 용량 x 0.75 ?  -> resize (2배 확장 + 전체 재배치, hash & oldCap로 lo/hi 분리) (3-3)
```

## 4. 꼬리질문 대비 포인트

### "용량이 왜 하필 2의 거듭제곱이어야 하나요?"

인덱스 계산 `(n-1) & hash` 때문이다. n이 2^k이면 `n-1`이 하위 k비트가 전부 1인 마스크가 되어, **나머지 연산을 비트 AND 한 번으로 대체**할 수 있다(1-2). 나눗셈은 수십 사이클, AND는 1사이클이고 이 자리는 모든 조회가 반드시 통과하는 자리다. 덤으로 음수 hash에서도 항상 0 이상의 인덱스가 나온다.

리사이징에서도 값을 한다. 용량을 정확히 2배로 늘리면 마스크에 비트가 정확히 하나 늘어나므로, **"새로 보게 된 비트 하나"만 확인해 제자리/+oldCap 두 그룹으로 쪼개는 값싼 재배치**가 가능해진다(3-3).

대신 하위 비트만 쓰게 되는 약점이 생기는데, 그것을 메우는 장치가 상위 16비트를 XOR로 섞는 spread다. **세 설계(2^k 용량, & 인덱싱, spread)는 따로 고른 것이 아니라 한 몸**이라고 말하면 이해했다는 신호가 된다.

### "hashCode가 전부 같은 key 100만 개를 넣으면 어떻게 되나요?"

전부 한 칸으로 몰린다. spread를 거쳐도 입력이 같으면 출력도 같으므로 소용이 없다.

Java 7이라면 리스트 하나에 노드 100만 개가 매달린다. get/put이 O(n)이라 사실상 서비스 불능이고, 이것이 해시 플러딩 DoS가 노린 지점이다.

Java 8 이상이라면 8개를 넘는 순간 그 칸이 트리화되어 O(log n)으로 방어된다. 다만 여기에 조건이 하나 붙는다는 것까지 말해야 정확하다 — **트리 안에서 순서를 정할 수 있어야** 하고, hash가 전부 같은 상황에서는 key가 `Comparable`인지에 달려 있다. `String`처럼 `Comparable`이면 온전히 O(log n)이 보장된다(3-7).

그리고 결론은 "방어된다"이지 "괜찮다"가 아니다. **정상 O(1)로 돌아오지는 않으므로, 근본 해법은 hashCode 품질**이다. 외부 입력이 그대로 Map의 key가 되는 경로라면 key 개수 상한을 두는 것도 함께 검토한다.

### "리사이징 도중 다른 스레드가 접근하면 무슨 일이 생기나요?" (시니어 변별 포인트)

HashMap은 동기화가 전혀 없으므로 **동작이 정의되지 않는다.**

Java 7에서는 head insert 방식 탓에 동시 리사이징이 리스트에 **순환 고리**를 만들어, `get`이 null을 영영 만나지 못하고 무한 루프에 빠지는 장애가 있었다(2-3). CPU가 100%에 고정된 채 응답이 멎는 증상이다.

Java 8에서 tail insert로 바뀌며 그 형태는 사라졌지만, **put 유실, size 불일치는 여전히 일어난다.** 두 스레드가 같은 칸에 동시에 tail insert하면 한쪽 노드가 통째로 사라질 수 있고, `size`는 그냥 `++`이라 갱신이 겹치면 실제 원소 수와 어긋난다.

핵심은 "Java 8이라 괜찮다"가 아니라 **규약 위반이므로 어떤 버전에서도 동시 사용 자체가 버그**라는 것이다. 동시 접근이 있으면 `ConcurrentHashMap`을 쓴다.

여기에 한 마디 덧붙이면 좋다. **"어쩌다 한 번의 동시 쓰기쯤은 괜찮겠지"라는 타협이 가장 나쁘다.** 평상시 트래픽에서는 겹칠 확률이 낮아 몇 달간 멀쩡하다가, 부하가 몰리는 날에만 재현되는 최악의 버그가 된다.

### "load factor 0.75는 왜 그 값인가요? 바꿔도 되나요?"

공간과 시간의 절충점이다. 낮추면 칸이 널널해 충돌이 줄지만 빈 칸이 많아 메모리를 낭비하고 확장이 잦아진다. 높이면 메모리 효율은 좋아지지만 칸당 평균 원소 수가 올라가 리스트 순회가 길어진다(3-2).

바꿀 수는 있지만 **실무에서 바꿀 일은 거의 없다.** 조정할 것이 있다면 load factor가 아니라 **초기 용량** 쪽이 답인 경우가 대부분이다 — 리사이징 횟수를 줄이는 쪽이 실익이 훨씬 크기 때문이다(3-4).

(가산점 포인트: 0.75를 함부로 바꾸면 안 되는 이유가 하나 더 있다. **트리화 임계값 8이 load factor 0.75를 전제로 계산된 값**이라는 점이다(3-6). load factor를 크게 올리면 칸당 평균 원소 수가 올라가 8개가 쌓일 확률도 함께 올라가고, "8 = 비정상 신호"라는 전제가 흔들려 정상 상황에서도 트리화가 일어나기 시작한다.)

### "HashMap 순회 순서는 왜 보장되지 않고, 순서가 필요하면 뭘 쓰나요?"

순회는 배열을 0번 칸부터 훑는 방식이고, 각 원소의 저장 위치는 **hashCode와 현재 용량의 함수**다. 따라서 순회 순서는 우리가 넣은 순서와 아무 관계가 없고, **리사이징 한 번이면 순서가 통째로 바뀐다**(3-3에서 본 대로 절반이 다른 칸으로 이사하기 때문이다).

순서가 필요하면 용도에 맞는 구현을 쓴다. **삽입 순서**가 필요하면 `LinkedHashMap`(각 노드를 이중 연결 리스트로도 꿰어 둔다), **정렬 순서**가 필요하면 `TreeMap`(전체가 레드-블랙 트리, 조회 O(log n))이다.

실무 사례를 곁들이면 좋다. **"HashMap 순회 결과를 그대로 비교하는 테스트"가 JDK 버전이나 데이터 양이 바뀌면 갑자기 깨진다.** 순서가 보장되지 않는데 우연히 맞아 왔을 뿐인 테스트다. 검증할 때는 순서에 의존하지 않는 비교를 쓰거나 정렬한 뒤 비교해야 한다.

## 한 줄 요약

HashMap은 "spread로 상위 비트를 섞은 hash를 2^k 배열에 `(n-1) &`로 인덱싱하고, 충돌은 리스트로 이어 붙이며, 0.75를 넘으면 2배 리사이징(`hash & oldCap` 한 번으로 lo/hi 분리), 한 칸이 8을 넘고 테이블이 64 이상이면 그 칸만 레드-블랙 트리"라는 한 문장으로 요약된다 — 그리고 이 내부를 아는 사람은 초기 용량 지정, 불변 key, 동시 접근 금지라는 실무 습관이 왜 필요한지를 관행이 아니라 원리로 설명할 수 있다.
