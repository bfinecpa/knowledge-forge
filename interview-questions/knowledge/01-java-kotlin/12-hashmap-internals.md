# HashMap 내부 동작 — 해시 충돌 처리, 리사이징, 트리화

> 핵심 관전 포인트: **HashMap은 "배열(버킷) + 충돌 시 연결 리스트,
> 심하면 레드-블랙 트리"다. key의 hashCode를 상위 비트와 섞어(spread)
> `(n-1) & hash`로 배열 인덱스를 정하고, 같은 칸에 충돌하면 리스트로
> 연결해 equals로 찾는다. 원소 수가 용량 × 0.75를 넘으면 배열을 2배로
> 늘려 전체 재배치(그래서 대량 삽입 전 초기 용량 지정이 유효한 최적화),
> 한 버킷의 리스트가 8을 넘고 테이블이 64 이상이면 트리로 바꿔 최악
> 성능을 O(n) → O(log n)으로 방어한다.**

---

## 0. 질문 + 의도

**질문**: "`HashMap`의 내부 동작(해시 충돌 처리, 리사이징, 트리화)을
설명해주세요."

**출제 의도**: 자료구조 하나를 끝까지 파본 적 있는지의 표본 검사.
리사이징 비용을 아는 사람은 초기 용량 지정 같은 사소하지만 대량 처리에서
유의미한 최적화를 자연스럽게 한다.

## 1. 전체 구조 — 우편함 배열에 편지 꽂기

HashMap의 본체는 **Node 배열 하나**다(내부 이름 `table`). 각 칸을
**버킷(bucket)**이라 부른다.

비유: 아파트 우편함. key의 hashCode는 "몇 호 우편함에 넣을지"를 정하는
주소 계산이고, get은 그 우편함 한 칸만 열어보는 것이다. 배열 전체를
뒤지지 않으니 평균 O(1) — HashMap의 존재 이유가 이 한 줄이다.

```java
// put(key, value)의 뼈대 (개념 코드)
int hash = spread(key.hashCode());   // ① 해시 보정
int index = (table.length - 1) & hash; // ② 버킷 인덱스 결정
// ③ table[index]가 비었으면 새 Node, 있으면 충돌 처리(2절)
```

### 1-1. 인덱스 계산이 `%`가 아니라 `&`인 이유 — 용량은 항상 2의 거듭제곱

HashMap의 용량(배열 길이)은 **항상 2의 거듭제곱**(16, 32, 64, …)이다.
길이가 2^k이면 `n - 1`은 하위 k비트가 전부 1인 비트마스크가 된다
(예: 16 - 1 = `0b1111`). 그래서:

```text
hash % 16      == hash & 15        // 수학적으로 동일한 결과
(나눗셈 연산)     (비트 AND 한 번)     // AND가 훨씬 싸다
```

나머지 연산을 비트 연산으로 대체하기 위한 설계다. 생성자에 17을 넘겨도
내부에서 32로 올림한다.

### 1-2. spread — 상위 비트를 하위로 끌어내리는 보정

`(n-1) & hash`는 **hash의 하위 비트만 사용**한다(테이블이 16이면 하위
4비트만). 그런데 hashCode 구현에 따라 하위 비트가 비슷하고 상위 비트만
다른 key들이 있을 수 있다 — 그대로 쓰면 전부 같은 버킷에 몰린다.

그래서 HashMap은 인덱스 계산 전에 상위 16비트를 하위에 XOR로 섞는다:

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
    //                          상위 16비트를 하위로 끌어내려 섞음
}
```

"어차피 하위 비트만 볼 거라면, 상위 비트의 정보도 하위에 반영해두자"는
싼 비용의 분산 개선이다. (key가 null이면 hash 0 → 항상 0번 버킷 —
HashMap이 null key를 하나 허용하는 방식이다.)

## 2. 해시 충돌 처리 — 같은 칸이면 리스트로 연결 (separate chaining)

서로 다른 key가 같은 인덱스를 받으면(해시가 같거나, 다르지만 하위 비트가
같거나) 그 버킷의 노드들을 **연결 리스트**로 이어 붙인다.

```text
table[5] → Node("apple") → Node("grape") → Node("melon")
```

- **put**: 리스트를 순회하며 `hash가 같고 && equals가 true`인 노드가
  있으면 value 교체, 없으면 **끝에 추가**(tail insert).
- **get**: 인덱스로 버킷을 찾고 → 리스트를 순회하며 equals로 확인.

여기서 두 가지 규약이 도출된다:

1. **equals를 재정의하면 hashCode도 재정의해야 하는 이유가 이 구조에
   있다** — hashCode가 다르면 애초에 **다른 버킷을 열어보므로** equals가
   true여도 영영 못 찾는다 ("분명 넣었는데 없다" 버그의 정체).
2. **가변(mutable) key 금지** — 넣은 뒤 key의 필드를 바꿔 hashCode가
   달라지면, 그 엔트리는 "옛 주소의 우편함"에 남아 있어 조회 불능이 된다.

```java
// before: 가변 객체를 key로 — 시한폭탄
Member m = new Member("kim");          // hashCode는 name 기반
map.put(m, profile);
m.setName("lee");                       // key의 해시가 바뀜!
map.get(m);                             // null — 새 해시로 다른 버킷을 열어봄

// after: key는 불변으로 (불변 필드만으로 equals/hashCode 구성)
record MemberKey(String id) {}          // record = 불변 + equals/hashCode 자동
map.put(new MemberKey("kim-001"), profile);
```

(가산점 포인트) Java 7까지는 충돌 시 리스트 **머리에** 삽입(head insert)
했는데, 멀티스레드에서 리사이징이 겹치면 리스트가 고리를 만들어
`get`이 **무한 루프**에 빠지는 유명한 장애 패턴이 있었다. Java 8에서 tail
insert로 바뀌며 그 형태는 사라졌지만, 여전히 데이터 유실 등이 발생하는
**thread-unsafe 자료구조**라는 본질은 그대로다 — 동시 접근이면
`ConcurrentHashMap`(→ `13-concurrenthashmap-internals.md`)을 쓴다.

## 3. 리사이징 — 0.75를 넘으면 2배로, 전원 이사

버킷당 리스트가 길어지면 O(1)이 무너지므로, **적당히 차면 배열을 키워
분산을 회복**한다.

- 기준: `원소 수 > 용량 × load factor(기본 0.75)` 가 되면 발동.
  기본 용량 16이면 13번째 put에서 32로 확장.
- 확장 폭: **정확히 2배** (2의 거듭제곱 유지를 위해).
- 비용: 새 배열을 만들고 **기존 노드 전부를 새 인덱스로 재배치** — O(n).

### 3-1. 재배치의 묘수 — 비트 하나만 보면 된다

용량이 2배가 되면 인덱스 마스크가 1비트 늘어난다(15 = `1111` → 31 =
`11111`). 즉 노드의 새 위치는 **hash의 "새로 보게 된 비트 하나"**로
결정된다:

```text
hash & oldCap == 0  →  제자리 (index 그대로)
hash & oldCap != 0  →  index + oldCap 으로 이동
```

그래서 Java 8은 재해싱 없이 각 버킷 리스트를 lo(제자리)/hi(+oldCap) 두
리스트로 쪼개기만 한다. 통계적으로 절반은 이사조차 안 한다 — 하지만
**전 노드를 한 번씩 만져야 하는 O(n) 비용 자체는 사라지지 않는다.**

### 3-2. 실무 최적화 — 대량 삽입 전 초기 용량 지정

리사이징 비용을 아는 사람이 자연스럽게 하는 한 줄 최적화:

```java
// before: 기본 용량 16에서 시작 → 10만 건 넣는 동안 리사이징 십수 회
Map<String, Order> map = new HashMap<>();
for (Order o : orders) map.put(o.getId(), o);   // 확장 때마다 전체 재배치

// after: 예상 원소 수 / 0.75 로 초기 용량 지정 → 리사이징 0회
Map<String, Order> map = new HashMap<>((int) (orders.size() / 0.75f) + 1);
// 또는 Java 19+: HashMap.newHashMap(orders.size())  — 같은 계산을 대신 해줌
```

주의: 생성자 인자는 "원소 수"가 아니라 **용량**이다. 10만을 넣고 싶다고
`new HashMap<>(100_000)`을 쓰면 0.75 × 131072 = 98304에서 결국 한 번 더
확장한다. 그래서 `기대 원소 수 / 0.75`로 계산해 넘긴다.

## 4. 트리화(treeify) — 최악의 경우를 O(log n)으로 방어

### 4-1. 왜 필요한가 — 리스트의 최악은 O(n)

hashCode가 나쁘거나(전부 같은 값 반환), 공격자가 **의도적으로 해시가
충돌하는 key를 대량 주입**하면(hash-flooding DoS — 요청 파라미터가 Map의
key가 되는 웹 서버에서 실제 공격 사례가 있다) 모든 원소가 한 버킷 리스트에
매달려 조회가 O(n)으로 전락한다.

Java 8부터는 한 버킷이 임계를 넘으면 그 버킷만 **레드-블랙 트리**(균형
이진 탐색 트리)로 바꿔 최악을 O(log n)으로 눌러 놓는다.

### 4-2. 조건 — 8에서 트리로, 6에서 다시 리스트로, 단 테이블 64 이상일 때만

| 전환 | 조건 |
|---|---|
| 리스트 → 트리 | 한 버킷의 노드 8개 초과 도달 **그리고** 테이블 길이 ≥ 64 |
| (테이블 < 64면) | 트리화 대신 **리사이징** — 작은 테이블의 충돌은 분산 부족이 원인일 가능성이 높아서 |
| 트리 → 리스트 | 리사이징 등으로 그 버킷이 6개 이하로 줄면 해제(untreeify) |

- **왜 8인가**: hashCode가 정상이라면 노드들이 버킷에 대략 고르게(포아송
  분포) 흩어지고, 한 버킷에 8개가 몰릴 확률은 사실상 0에 가깝다. 즉 8은
  "정상 상황에선 절대 안 일어나니, 일어났다면 비정상(나쁜 해시/공격)"
  이라는 신호선이다. 트리 노드는 일반 노드보다 무겁기 때문에 정상
  상황에서는 만들지 않는 게 이득이다.
- **왜 해제는 6인가**: 임계가 8 하나뿐이면 7↔8 경계에서 넣고 뺄 때마다
  트리화↔해제가 반복될 수 있다. 두 값을 벌려(히스테리시스) 경계 진동을
  막는다.

(가산점 포인트) 트리 안에서의 정렬 기준: 같은 버킷 안에서도 hash 값으로
먼저 비교하고, hash까지 같으면 key가 `Comparable`일 때 `compareTo`로
비교한다. 그래서 **hashCode가 전부 같아도 key가 Comparable이면**(예:
String) O(log n)이 온전히 보장된다 — hash-flooding 방어가 String key에서
특히 잘 작동하는 이유다.

## 5. 흐름 한 장 정리 — put이 겪는 일

```text
put(key, value)
 ├─ hash = key.hashCode() ^ (h >>> 16)        // 보정
 ├─ index = (n-1) & hash                       // 버킷 결정
 ├─ 버킷이 빔          → 새 Node
 ├─ 같은 key 존재      → value 교체 (hash 같고 equals true)
 ├─ 리스트에 tail 추가  → 8 초과?
 │        ├─ 테이블 < 64 → resize (2배 확장)
 │        └─ 테이블 ≥ 64 → treeify (레드-블랙 트리)
 └─ size > 용량 × 0.75  → resize (2배 확장 + 전체 재배치)
```

## 6. 꼬리질문 대비 포인트

### "용량이 왜 하필 2의 거듭제곱이어야 하나요?"

인덱스 계산 `(n-1) & hash` 때문이다. n이 2^k이면 n-1이 하위 k비트
마스크가 되어 나머지 연산(%)을 비트 AND 한 번으로 대체할 수 있고,
리사이징 때도 "새로 늘어난 비트 하나"만 보고 제자리/+oldCap 두 그룹으로
쪼개는 값싼 재배치가 가능해진다. 대신 하위 비트만 쓰는 약점이 생기는데,
그걸 메우는 장치가 상위 16비트를 XOR로 섞는 spread다 — 세 설계(2^k 용량,
& 인덱싱, spread)는 한 몸이다.

### "hashCode가 전부 같은 key 100만 개를 넣으면 어떻게 되나요?"

전부 한 버킷으로 몰린다. Java 7이라면 리스트 하나가 100만 노드 —
get/put이 O(n)이라 사실상 서비스 불능(hash-flooding DoS가 노린 지점).
Java 8+는 8개를 넘는 순간 트리화되어 O(log n)으로 방어되고, key가
Comparable(String 등)이면 트리 내 비교도 온전해 성능이 보장된다. 다만
"방어된다"일 뿐 정상 O(1)은 아니므로, 근본적으로는 hashCode 품질이 답이다.

### "리사이징 도중 다른 스레드가 접근하면 무슨 일이 생기나요?" (시니어 변별 포인트)

HashMap은 동기화가 전혀 없어 결과가 정의되지 않는다. Java 7에서는 head
insert 방식 탓에 동시 리사이징이 리스트에 **순환 고리**를 만들어 get이
무한 루프(CPU 100%)에 빠지는 유명한 장애가 있었다. Java 8에서 tail
insert로 그 형태는 사라졌지만 put 유실, size 불일치 등은 여전하다.
핵심은 "Java 8이라 괜찮다"가 아니라 **규약 위반이므로 어떤 버전에서도
동시 사용 자체가 버그**라는 것 — 동시 접근이면 ConcurrentHashMap을 쓰고,
"어쩌다 한 번의 동시 쓰기쯤은"이라는 타협이 부하 상황에서만 터지는 최악의
버그를 만든다고 답하면 된다.

### "load factor 0.75는 왜 그 값인가요? 바꿔도 되나요?"

공간과 시간의 절충점이다. 낮추면 버킷이 널널해 충돌이 줄지만(빠름) 빈
칸이 많아 메모리 낭비, 높이면 그 반대다. 0.75는 "충돌 확률을 낮게
유지하면서 공간 낭비도 참을 만한" 기본값으로, 실무에서 이 값을 바꿀 일은
거의 없다 — 조정한다면 load factor가 아니라 **초기 용량** 쪽이 정답인
경우가 대부분이다(리사이징 횟수 절감이 실익이 더 크므로).

### "HashMap 순회 순서는 왜 보장되지 않고, 순서가 필요하면 뭘 쓰나요?"

저장 위치가 hashCode에서 계산된 배열 인덱스이므로 순회 순서는 해시와 현재
용량의 함수다 — 리사이징 한 번이면 순서가 통째로 바뀐다. 삽입 순서가
필요하면 `LinkedHashMap`(각 노드를 이중 연결 리스트로도 꿰어 둠), 정렬
순서가 필요하면 `TreeMap`(레드-블랙 트리, O(log n))을 쓴다. "HashMap
순서에 의존한 테스트가 JDK 버전/데이터 양에 따라 깨진다"는 실무 사례를
곁들이면 좋다.

## 한 줄 요약

HashMap은 "spread로 보정한 hash를 2^k 배열에 & 인덱싱, 충돌은 리스트,
0.75 초과 시 2배 리사이징, 버킷 8 초과 + 테이블 64 이상이면 레드-블랙
트리"라는 한 문장으로 요약되며 — 이 내부를 아는 사람은 초기 용량 지정,
불변 key, 동시 접근 금지라는 실무 습관이 왜 필요한지를 원리로 설명할 수
있다.
