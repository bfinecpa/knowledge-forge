# 고경합 카운터 설계 — AtomicLong의 한계, LongAdder, false sharing

> 핵심 관전 포인트: **락이 없어도 "경합 지점이 하나"면 느리다. `AtomicLong`이 극한 경합에서 꺾이는 진짜 이유는 "CAS 재시도가 많아서"가 아니라, **실패 한 번이 캐시 라인 하나를 코어 사이로 옮기는 비용**을 매번 유발하기 때문이다 — 어떤 코어가 메모리를 고치려면 그 라인을 배타적으로 소유해야 하고, 그 순간 다른 코어들의 복사본은 전부 무효화된다. 그래서 해법은 경합 지점 자체를 쪼개는 것이다. `LongAdder`는 쓰기를 스레드별 셀로 분산하고 읽을 때만 합산하는데, 그 대가로 **`sum()`이 정확한 스냅샷이 아니다**(합산 중에도 다른 셀이 갱신된다) — 통계·모니터링 카운터에는 맞고 잔액·재고에는 쓰면 안 되는 이유다. 그런데 셀을 쪼개 놓아도 그 셀들이 메모리상 같은 캐시 라인에 나란히 앉으면 **공유하지 않는데 공유의 비용을 내는** false sharing으로 도로 느려진다. 그래서 `LongAdder`의 `Cell`에는 `@Contended` 패딩이 붙어 있다. 논리적 경합 분산과 물리적 캐시 라인 분리, 이 두 층을 이어서 설명하는 것이 이 질문의 전부다.**

---

## 0. 질문 + 의도

**질문**: "False sharing이란 무엇이고 어떻게 회피하나요?"

**출제 의도**: 극한 성능 최적화가 필요한 순간(집계 카운터, 고빈도 이벤트 처리)에 프로파일러에도 잘 안 잡히는 병목의 정체를 아는지 본다. 락도 없고 경합 지점을 쪼갰는데도 느린 이유를 캐시 라인까지 내려가 설명할 수 있는지 — 하드웨어까지 내려가본 깊이의 표본 검사에 가깝다.

## 1. AtomicLong이 극한 경합에서 느려지는 이유

### 1-1. 전제 지식 — CAS가 무엇이고 왜 락 대신 쓰는가

**CAS(Compare-And-Swap)**는 **"이 메모리 값이 내가 읽었던 값 그대로면 새 값으로 바꿔라"를 CPU가 하나의 명령으로 처리하는 원자 연산**이다. 비교와 교체 사이에 다른 스레드가 끼어들 틈이 없다는 것을 소프트웨어가 아니라 하드웨어가 보장한다.

이걸 락 대신 쓰는 이유는 **실패했을 때 무엇을 하느냐**가 다르기 때문이다. 락은 못 잡으면 스레드가 커널에 의해 대기 상태로 내려갔다가 나중에 깨워져야 하고, 그 재우고 깨우는 비용(컨텍스트 스위칭)이 만만치 않다. CAS는 실패해도 **잠들지 않고 곧바로 다시 시도한다.** 경합이 짧을 때 락보다 훨씬 싼 이유가 여기 있다(`14-volatile-visibility-vs-atomicity.md`).

`AtomicLong.incrementAndGet()`의 속은 그래서 이런 루프다.

```java
do {
    long current = get();          // ① 현재 값을 읽고
    long next = current + 1;       // ② 새 값을 계산한 뒤
} while (!compareAndSet(current, next));
//        ③ "아직 current인가?"를 확인하면서 교체를 시도한다.
//        그 사이 누가 값을 바꿨으면 실패하고, 실패하면 ①부터 다시.
```

여기까지가 교과서다. 문제는 스레드가 많아졌을 때 이 루프가 어떻게 되는가다.

### 1-2. 스레드 8개가 같은 변수에 CAS를 걸면

값이 100인 카운터에 스레드 8개가 동시에 `incrementAndGet()`을 호출하는 순간을 따라가 보자.

```
시각   무슨 일이 일어나는가                                        카운터 값
────────────────────────────────────────────────────────────────────────────
t1     스레드 1~8이 전부 값을 읽는다 -> 여덟 개 모두 100을 손에 쥔다.   100

t2     여덟 개가 전부 "100이면 101로" CAS를 건다.
       하드웨어가 순서를 세워 딱 하나만 통과시킨다.
         스레드3 성공                                                 101
         나머지 7개 실패 — 읽었던 100이 이미 아니기 때문

t3     실패한 7개가 다시 읽는다 -> 전부 101.                          101

t4     7개가 "101이면 102로" CAS -> 하나 성공, 6개 실패.              102

t5     6개가 다시 읽고 다시 시도 -> 하나 성공, 5개 실패.              103
 ...
t15    마지막 하나가 성공.                                            108

────────────────────────────────────────────────────────────────────────────
증가 8번을 끝내는 데 든 CAS 시도: 8 + 7 + 6 + 5 + 4 + 3 + 2 + 1 = 36회
그중 성공 8회, 실패 28회. 헛일이 실제 일의 3.5배다.
```

물론 실제 실행이 이렇게 딱딱 맞아떨어지지는 않는다. 이건 **스레드들이 같은 박자로 몰릴 때의 극단**이다. 다만 **경합이 심해질수록 이 모습에 가까워지고, 스레드 수가 늘수록 실패 비율이 올라간다**는 구조 자체는 그대로다. 스레드가 N개면 성공 한 번마다 실패가 최대 N-1번 나온다.

여기서 겉으로 보이는 증상이 특히 고약하다. **CPU 사용률은 100%인데 처리량은 오히려 떨어진다.** 스레드들이 잠들지 않고 계속 돌기 때문에 시스템은 바빠 보이는데, 실제로 성사되는 증가는 한 번에 하나뿐이다. 그리고 스레드 덤프를 떠 봐야 전부 `RUNNABLE`이라 **락 경합처럼 `BLOCKED`나 `parking`으로 드러나지도 않는다.** 락이 없을 뿐, **"경합 지점이 하나"라는 문제는 락을 쓸 때와 똑같이 남아 있다.**

### 1-3. 실패의 진짜 비용은 재시도가 아니라 캐시 라인 소유권 이동

여기서 한 걸음 더 들어가야 한다. 위 표만 보면 "실패 28번 = 명령어 몇 개를 28번 더 실행" 정도로 읽히는데, **실제 비용은 그것보다 자릿수 단위로 크다.**

이유를 알려면 CPU가 메모리를 어떻게 다루는지 봐야 한다. 코어는 메인 메모리를 직접 읽고 쓰지 않는다. 자기 전용 캐시(L1·L2)에 복사본을 두고 그 복사본으로 일한다. 여러 코어가 같은 데이터의 복사본을 들고 있을 수 있으므로, 그 복사본들이 서로 모순되지 않게 맞추는 규칙이 필요하다. 이것이 **캐시 일관성 프로토콜(cache coherence protocol, MESI 등)**이다.

이 프로토콜의 핵심 규칙 하나만 알면 된다. **어떤 코어가 데이터를 고치려면, 그 데이터가 든 캐시 라인을 자기가 배타적으로 소유한 상태로 만들어야 한다. 그러려면 그 라인을 들고 있던 다른 모든 코어의 복사본을 먼저 무효화(invalidate)해야 한다.**

**그리고 CAS는 읽기가 아니라 쓰기 시도다.** 성공하든 실패하든 "고치겠다"고 나서는 동작이므로 배타 소유가 필요하다. 그래서 1-2의 표는 실제로 이런 일이 벌어지고 있는 것이다.

```
[코어3이 CAS에 성공하는 순간]
  코어3: 카운터가 든 라인을 배타 소유로 가져온다
         -> 코어1,2,4,5,6,7,8의 복사본이 전부 무효(Invalid)가 된다

[실패한 코어1이 다시 읽으려는 순간]
  코어1: 자기 캐시의 복사본이 무효다. 자기 L1에서 못 읽는다.
         -> 라인을 다시 끌어온다 (메인 메모리 또는 코어3의 캐시에서)
         -> 그리고 CAS를 걸려면 또 배타 소유가 필요하므로
            다시 다른 코어들의 복사본을 무효화한다
         -> 그 무효화가 또 다른 코어의 재시도를 유발한다
```

**즉 CAS 실패 한 번의 값은 "명령 몇 개 더"가 아니라 "캐시 라인 하나가 코어 사이를 한 번 왕복하는 것"이다.** 자기 L1에서 읽는 것과 다른 코어의 캐시에서 끌어오는 것은 비용의 자릿수가 다르다. 그리고 스레드가 많을수록 이 왕복이 곱절로 늘어난다. **처리량이 스레드 수에 비례해 늘지 않고 어느 지점부터 오히려 꺾이는 이유가 이것이다.**

**이 문단이 3절 false sharing의 전제다.** 지금은 여덟 스레드가 **진짜로 같은 변수**를 두고 라인을 뺏고 뺏기는 중이다. 3절에서는 **서로 다른 변수를 쓰는데도** 똑같은 일이 벌어지는 경우를 본다.

## 2. LongAdder — 쓰기는 분산, 읽기는 합산

### 2-1. 아이디어 — 경합 지점을 여러 개로 쪼갠다

1절의 진단이 "모두가 하나의 주소를 두고 싸운다"였으므로, 해법은 그 전제를 버리는 것이다. **각 스레드가 자기 몫의 주소에만 더하게 하고, 총합이 필요할 때만 전부 더해서 읽는다.**

```
[AtomicLong]                              [LongAdder]

 스레드1 ─┐                                base   ....... 경합이 없을 때만 여기에 더한다
 스레드2 ─┤                                        (경합이 감지되면 아래 셀로 흩어진다)
 스레드3 ─┤                                스레드1 ──────► Cell[0]  += 1
 스레드4 ─┼──► value (주소 하나)           스레드2 ──────► Cell[1]  += 1
 스레드5 ─┤                                스레드3 ──────► Cell[2]  += 1
 스레드6 ─┤                                  ...
 스레드7 ─┤                                스레드8 ──────► Cell[7]  += 1
 스레드8 ─┘
                                           읽을 때만:
 성공 1건마다 실패 최대 7건.                sum() = base + Cell[0] + Cell[1] + ... + Cell[7]
 라인이 코어 사이를 계속 왕복한다.          쓰기끼리는 부딪힐 일이 없다.
```

**서로 다른 스레드가 서로 다른 주소를 건드리므로 CAS가 충돌할 일 자체가 없어진다.** 1-3에서 본 캐시 라인 왕복도 함께 사라진다.

포기하는 것은 **"매 순간 정확한 현재 값"**이다. 총합은 이제 한 곳에 있지 않고 여러 셀에 흩어져 있으므로, 읽으려면 돌아다니며 더해야 하고 그 사이에도 값은 계속 변한다. **쓰기 처리량을 사기 위해 읽기의 정확성을 파는 거래**이고, 이 거래가 맞는 자리와 안 맞는 자리를 가르는 것이 2-3이다.

### 2-2. JDK의 구현 — LongAdder

```java
// (문제) 하나의 값에 수십 개 스레드가 몰린다
AtomicLong counter = new AtomicLong();
counter.incrementAndGet();   // 극한 경합에서 CAS 재시도 + 캐시 라인 왕복

// (개선) 셀 분산으로 경합 자체를 없앤다
LongAdder counter = new LongAdder();
counter.increment();         // 스레드마다 서로 다른 셀에 기록한다
long total = counter.sum();  // 읽을 때만 셀들을 순회해 합산한다
```

`LongAdder`(Java 8부터, 내부적으로 `Striped64`를 상속)의 동작은 네 단계로 정리된다.

**첫째, 경합이 없으면 `AtomicLong`처럼 동작한다.** 셀 배열을 만들지 않고 `base`라는 단일 값에 CAS를 건다. 스레드가 하나뿐이라면 `AtomicLong`과 비용이 사실상 같다. **셀 분산은 공짜가 아니므로 필요해질 때까지 미룬다**는 설계다.

**둘째, `base`에 대한 CAS가 실패하면 그것을 경합 신호로 읽는다.** 그때부터 `Cell[]` 배열을 만들고 스레드를 셀에 나눠 배정한다. 배정 기준은 스레드마다 갖고 있는 난수 같은 값이라, 대체로 고르게 흩어진다.

**셋째, 그래도 충돌이 계속되면 배열을 키운다.** 배열 크기는 2의 거듭제곱으로 두 배씩 늘어나고, **CPU 코어 수 언저리에서 성장을 멈춘다.** 코어보다 셀을 더 많이 만들어 봐야 동시에 쓰는 주체가 코어 수를 넘지 못하므로 의미가 없기 때문이다.

**넷째, 각 `Cell`에는 `@Contended`가 붙어 있다.** 셀을 쪼개 놓고도 그 셀들이 메모리상 붙어 있으면 3절의 false sharing으로 도로 느려지기 때문이다. **논리적 분산(2절)과 물리적 분리(3절)가 둘 다 있어야 완성된다**는 것이 `LongAdder`가 몸으로 보여주는 사실이다.

### 2-3. sum()은 정확한 스냅샷이 아니다 — 이 트레이드오프가 선택 기준이다

여기가 이 절에서 가장 중요한 대목이다. **`sum()`은 "어느 한 순간의 총합"을 돌려주지 않는다.**

이유는 구현을 보면 자명하다. `sum()`은 `base`를 읽고, `Cell[0]`을 읽고, `Cell[1]`을 읽고... 하며 순회하면서 더한다. **이 순회 전체를 원자적으로 묶는 장치가 없다.** 락도 안 잡고 스냅샷도 안 뜬다 — 그렇게 하는 순간 쓰기 성능을 위해 만든 구조가 무너지기 때문이다.

```
sum() 실행 중에 벌어지는 일

  t1   base 읽음        -> 100
  t2   Cell[0] 읽음     -> 5      (누적 105)
  t3        ★ 이 사이에 스레드2가 Cell[0]을 6으로 올린다
             -> 이미 지나간 셀이므로 이번 sum()에는 반영되지 않는다
  t4   Cell[1] 읽음     -> 3      (누적 108)
  t5        ★ 이 사이에 스레드5가 Cell[3]을 9로 올린다
             -> 아직 안 지나간 셀이므로 이번 sum()에 반영된다
  t6   Cell[2] 읽음     -> 2      (누적 110)
  t7   Cell[3] 읽음     -> 9      (누적 119)   <- t5의 갱신이 들어왔다
  ...
  결과: t3의 갱신은 빠지고 t5의 갱신은 들어간 값.
        어느 한 시점에도 "실제로 이 값이었던" 순간이 없을 수 있다.
```

**갱신이 완전히 멈춘 상태에서 부르면 정확하다.** 그러니 "틀린 값을 준다"가 아니라 **"갱신이 진행 중일 때는 어느 시점의 값인지 특정할 수 없다"**가 정확한 표현이다.

여기서 선택 기준이 곧바로 나온다.

**맞는 자리 — 통계·모니터링 카운터.** 요청 수, 에러 수, 처리 건수, 캐시 히트 수. 이런 값은 애초에 **주기적으로 긁어가서 추세를 보는 용도**다. 1초에 수만 건 올라가는 카운터에서 몇 건 오차가 대시보드의 그래프 모양이나 알람 임계값 판단을 바꾸지 않는다. 그리고 이 자리는 **쓰기가 압도적으로 많고 읽기는 가끔**이라 트레이드오프의 방향이 정확히 맞는다.

**틀린 자리 — 잔액, 재고, 한도 카운터.** 이유가 둘이다.

첫째, **읽은 값으로 판단해서 쓰기를 하는 자리이기 때문이다.** "잔액이 충분하면 차감한다", "재고가 남았으면 감소시킨다"는 검사 후 행동(check-then-act)인데, `sum()`이 어느 시점의 값인지 특정할 수 없다면 그 판단의 근거가 무너진다. `sum()`을 읽고 판단하는 사이에 다른 셀이 갱신될 수도 있다.

둘째, **`LongAdder`에는 `compareAndSet`이 없다.** `AtomicLong`이라면 "내가 읽은 값이 그대로면 차감"을 원자적으로 시도할 수 있지만, 값이 여러 셀에 흩어져 있는 구조에서는 그런 연산 자체가 성립하지 않는다. **`LongAdder`는 단순 누적 전용 도구**다.

정리하면 이렇다.

| | AtomicLong | LongAdder |
|---|---|---|
| 고경합 쓰기 | CAS 재시도 + 캐시 라인 왕복으로 꺾인다 | 셀 분산으로 거의 선형 확장 |
| 읽기 | 정확한 스냅샷, 값 하나만 읽으면 끝 | 셀 순회 합산, 어느 시점인지 특정 불가 |
| 메모리 | 값 하나 | 셀마다 패딩까지 붙어 코어 수만큼 |
| CAS 연산 | `compareAndSet` 가능 | 불가 (누적 전용) |

**선택 기준 한 줄: 정확한 값을 자주 읽어야 하거나 CAS 연산이 필요하면 `AtomicLong`, 쓰기가 압도적으로 많은 집계·통계 카운터면 `LongAdder`.**

(가산점 포인트) 같은 원리를 임의의 누적 함수로 일반화한 것이 **`LongAccumulator`**다. 생성자에 결합 함수를 넘기면 `max`, `min`, 곱셈 같은 누적도 셀 분산으로 처리할 수 있다. 단, 셀별로 부분 결과를 만들었다가 나중에 합치는 구조이므로 **결합 함수는 순서에 무관해야 한다** — 순서에 따라 결과가 달라지는 함수를 넘기면 실행할 때마다 값이 달라진다.

## 3. false sharing — 공유하지 않는데 공유의 비용을 낸다

### 3-1. 전제 지식 — CPU는 변수가 아니라 캐시 라인 단위로 메모리를 다룬다

1-3에서 "캐시 라인"이라는 말을 이미 썼다. 이제 그 단위가 무엇인지 정확히 짚는다.

CPU가 메모리에서 데이터를 가져올 때, **필요한 8바이트만 가져오지 않는다.** 그 주변까지 포함한 일정 크기의 덩어리를 통째로 가져온다. 이 덩어리가 **캐시 라인(cache line)**이다. 그렇게 하는 이유는 **프로그램이 쓴 데이터 근처를 곧 또 쓸 확률이 높기 때문**이다(지역성). 배열을 순회하면 다음 원소가 바로 옆에 있으니, 미리 함께 가져오면 다음 접근이 공짜가 된다.

**일반적인 x86-64(인텔·AMD) CPU에서 캐시 라인은 64바이트다.** `long` 하나가 8바이트이므로 **`long` 여덟 개가 한 라인에 함께 실려 다니는** 셈이다.

**단, 64라는 숫자를 상수처럼 외우면 안 된다.** 캐시 라인 크기는 아키텍처와 캐시 계층마다 다르고, 일부 ARM 계열은 128바이트를 쓰기도 한다. HotSpot JVM이 `@Contended` 패딩 폭을 지정하는 옵션 `-XX:ContendedPaddingWidth`의 기본값을 128바이트로 잡아 둔 것도 **라인 크기를 넉넉히 잡아 어느 환경에서든 안전하게 만들려는** 것이다. 그러니 64바이트는 "이 문서의 그림을 그리기 위한 대표값"으로 받아들이고, **외울 것은 숫자가 아니라 "한 번에 옮겨지는 덩어리가 있고 그 안에 여러 변수가 함께 실린다"는 구조**다.

그리고 1-3의 규칙을 여기에 다시 붙인다. **캐시 일관성 프로토콜은 변수 단위가 아니라 라인 단위로 동작한다.** 어떤 코어가 **라인의 일부라도** 수정하면, 그 라인을 들고 있던 다른 모든 코어의 복사본은 통째로 무효화된다. **"일부라도"와 "통째로"가 이 절 전체의 열쇠다.**

### 3-2. 정의와 그림

**false sharing**은 **서로 다른 스레드가 서로 다른 변수를 쓰고 있어서 논리적으로는 아무것도 공유하지 않는데, 그 변수들이 우연히 같은 캐시 라인 안에 있어서 하드웨어 차원에서는 공유하는 것과 똑같은 비용을 내는 현상**이다. 공유가 아닌데 공유의 대가를 치른다는 뜻에서 **false**(거짓) sharing이다.

```
                      한 캐시 라인 (일반적인 x86-64에서 64바이트)
   +----------+----------+----------+----------+----------+----------+----------+----------+
   | counterA | counterB |          |          |          |          |          |          |
   +----------+----------+----------+----------+----------+----------+----------+----------+
     8바이트     8바이트
        ^          ^
        |          └── 코어1만 쓴다
        └───────────── 코어0만 쓴다

   두 변수 사이에는 아무 관계도 없다. 코드상 공유되는 것이 하나도 없다.
   그런데 캐시 일관성은 "라인" 단위이므로,
   코어0이 counterA를 1 올리는 순간 코어1이 들고 있던 이 라인 복사본이
   counterB를 포함해 통째로 무효화된다.
```

코드로 보면 더 억울하다.

```java
// 스레드별로 카운터를 분리했다 — 논리적 경합은 0이다
long[] counters = new long[8];

// 스레드 0은 counters[0]만, 스레드 1은 counters[1]만 증가시킨다.
// 서로의 변수를 건드리는 코드가 단 한 줄도 없다.
// 그런데 느리다.
```

**배열의 원소는 메모리에 연속으로 놓인다.** `long[8]`이면 데이터만 64바이트이고, 여기에 배열 객체의 헤더(64비트 JVM에서 대략 16바이트)가 앞에 붙는다. 그래서 **여덟 개가 정확히 한 라인에 딱 맞아떨어지지는 않고, 대개 두 라인에 걸쳐 앞쪽 여섯 개 정도가 한 라인을 공유하는 형태**가 된다. 객체가 라인 경계에 맞춰 배치된다는 보장도 없으므로 정확한 분할은 실행마다 달라질 수 있다.

**중요한 것은 정확한 개수가 아니다.** 여덟 개가 한 라인이든 여섯 개가 한 라인이든, **여러 스레드가 같은 라인을 두고 부딪힌다는 결론은 똑같다.**

### 3-3. 핑퐁 — 무슨 일이 벌어지는가

```
시각   코어0 (counters[0]을 증가)              코어1 (counters[1]을 증가)
──────────────────────────────────────────────────────────────────────────────
t1     라인을 배타 소유로 가져온다
       -> 코어1의 복사본이 무효화된다
       counters[0]++ 실행

t2                                            counters[1]을 고치려는데
                                              자기 복사본이 무효다.
                                              -> 라인을 다시 끌어온다
                                              -> 코어0의 복사본이 무효화된다
                                              counters[1]++ 실행

t3     counters[0]을 또 고치려는데
       자기 복사본이 무효다.
       -> 라인을 다시 끌어온다
       -> 코어1의 복사본이 또 무효화된다

t4                                            (t2 반복)
...    증가할 때마다 이 왕복이 반복된다.
       캐시 라인 하나가 두 코어 사이를 계속 오간다 — 핑퐁.
```

**각 스레드는 자기 변수만 건드리는데, 하드웨어 입장에서는 하나의 라인을 두고 쟁탈전을 벌이는 것과 완전히 똑같다.** 1-3에서 `AtomicLong` 여덟 스레드가 겪던 것과 같은 일이, 이번에는 **공유하는 변수가 하나도 없는데도** 벌어진다.

**이것이 프로파일러에 잘 안 잡히는 병목의 대표 사례인 이유**도 여기서 나온다. 락이 없으니 락 경합 뷰에 안 뜨고, CAS 실패도 없으니 재시도 카운터도 안 오른다. 스레드 상태는 전부 `RUNNABLE`이다. 코드 어디에도 이상한 곳이 없다. 겉으로 보이는 것은 **"코어를 늘렸는데 처리량이 안 늘거나 오히려 줄었다"**는 결과뿐이다.

### 3-4. 회피 1 — 패딩으로 라인을 독점시킨다

원인이 "다른 변수와 같은 라인에 앉아 있는 것"이므로, 해법은 **뜨거운 변수 주위를 쓰지 않는 공간으로 채워 그 라인을 혼자 차지하게 만드는 것**이다. 이것을 **패딩(padding, 채워 넣기)**이라 한다.

```java
// (문제) 여러 Counter 객체의 value들이 한 라인에 나란히 앉을 수 있다
class Counter {
    volatile long value;
}

// (개선) value 앞뒤를 각각 56바이트로 채워 라인을 독점하게 한다
class PaddedCounter {
    long p1, p2, p3, p4, p5, p6, p7;   // 앞 패딩 8바이트 x 7 = 56바이트
    volatile long value;               // 실제로 쓰는 값
    long q1, q2, q3, q4, q5, q6, q7;   // 뒤 패딩 56바이트
    // 앞뒤로 56바이트씩 두는 이유: 라인 경계가 어디에 떨어지든
    // value가 속한 64바이트 안에는 이 클래스의 패딩 말고는 아무것도 못 들어온다.
}
```

**수동 패딩에는 두 가지 약점이 있다.**

**첫째, JVM은 필드를 선언한 순서대로 배치한다고 보장하지 않는다.** 객체 레이아웃은 JVM이 정하고, 크기별로 묶어 재배치하는 것이 일반적이다. 그래서 `p1~p7`과 `q1~q7`이 의도대로 `value`를 감싸 준다는 보장이 없다. 소스만 봐서는 실제 레이아웃을 알 수 없고, 확인하려면 객체 레이아웃을 출력하는 도구를 따로 써야 한다.

**둘째, 계산의 전제가 환경에 따라 바뀐다.** 객체 헤더 크기는 압축 참조(compressed oops) 사용 여부 같은 JVM 옵션에 따라 달라지고, 3-1에서 본 대로 캐시 라인 크기 자체도 아키텍처마다 다르다. **한 환경에 맞춰 손으로 계산한 패딩은 다른 환경에서 어긋난다.**

그래서 수동 패딩은 "원리를 이해하기 위한 예제"에 가깝고, 실제로는 다음 방법이 낫다.

### 3-5. 회피 2 — @Contended로 JVM에 맡긴다

JVM에게 **"이 필드는 다른 것과 같은 라인에 두지 마라"**고 선언하는 어노테이션이 있다. 이름 그대로 경합(contended)이 예상되는 필드라는 표시다.

```java
// JVM이 이 필드 주위에 알아서 패딩을 넣는다.
// 패딩 폭은 -XX:ContendedPaddingWidth로 정해지며 기본값은 128바이트다.
// (라인이 64바이트인 환경에서도 넉넉히 잡으려는 값이다)
@jdk.internal.vm.annotation.Contended
volatile long value;
```

**JVM이 계산하므로 3-4의 두 약점이 사라진다.** 헤더 크기도, 필드 재배치도, 라인 폭도 JVM이 알고 있으니 손으로 맞출 필요가 없다.

**문제는 애플리케이션 코드에서 쓰기가 상당히 까다롭다는 점이다.** 세 가지 벽이 있다.

**첫째, 패키지가 내부 전용이다.** Java 8에서는 `sun.misc.Contended`였는데 이후 **`jdk.internal.vm.annotation.Contended`**로 옮겨졌다. 이름이 말하듯 JDK 내부용이며, 모듈 시스템이 `jdk.internal.*` 접근을 기본적으로 막는다. 우리 코드에서 쓰려면 컴파일과 실행 양쪽에 `--add-exports java.base/jdk.internal.vm.annotation=ALL-UNNAMED` 같은 예외를 열어야 한다.

**둘째, 기본적으로 무시된다.** JVM은 신뢰할 수 없는 코드의 `@Contended`를 그냥 무시하도록 되어 있고, 효과를 보려면 **`-XX:-RestrictContended`** 플래그로 그 제한을 풀어야 한다. 이걸 모르고 어노테이션만 붙여 놓으면 **아무 일도 일어나지 않는데 조치했다고 착각하게 된다** — 가장 위험한 실패 방식이다.

**셋째, 이 모든 설정이 실행 환경에 묶인다.** 라이브러리로 배포한다면 사용자의 JVM 옵션에 의존하게 되고, 그 옵션이 없으면 성능 특성이 조용히 달라진다.

**정리하면, `@Contended`는 JDK 자신이 적극적으로 쓰는 도구이고 애플리케이션 코드가 직접 쓰기에는 문턱이 높다.** 그래서 실무에서 더 현실적인 답은 "**`@Contended`가 이미 적용된 JDK 클래스를 쓰는 것**"이다. `LongAdder`의 `Cell`이 정확히 그 예다 — 셀 분산으로 논리적 경합을 없애 놓고, 셀들이 배열에 나란히 붙으면 false sharing으로 도로 느려지므로 각 `Cell`에 `@Contended`를 붙여 물리적으로도 분리해 둔 것이다.

### 3-6. 회피 3 — 자료구조 배치로 피한다

어노테이션 없이 **데이터를 놓는 방식만 바꿔서** 피하는 방법도 있다.

**배열이라면 인덱스를 띄운다.** 스레드 8개가 `long[]`을 쓴다면 `counters[0], counters[1], ...` 대신 `counters[0], counters[8], counters[16], ...`처럼 **한 라인 폭만큼 건너뛰어(stride) 배정**한다. 배열 크기는 여덟 배로 늘어나지만 각 스레드의 카운터가 서로 다른 라인에 놓인다.

```java
// (문제) 이웃한 인덱스 -> 같은 라인
long[] counters = new long[threadCount];
counters[threadId]++;

// (개선) 8칸씩 띄워 배정 -> 각자 다른 라인
// (8은 "64바이트 / long 8바이트" 기준의 대표값이다. 라인이 128바이트인
//  환경까지 감안하려면 16으로 잡는 편이 안전하다)
long[] counters = new long[threadCount * 8];
counters[threadId * 8]++;
```

**아예 스레드별 독립 객체를 쓴다.** `ThreadLocal`로 스레드마다 카운터 객체를 따로 두면, 객체들이 힙에 흩어져 할당되므로 같은 라인에 붙을 가능성이 낮아진다. **다만 "낮아진다"이지 "없다"가 아니다** — 같은 시점에 연달아 할당된 작은 객체들은 힙에서 나란히 놓이는 경우가 흔하고, GC가 객체를 옮기면서 배치가 바뀌기도 한다. 확실한 보장이 필요하면 패딩과 함께 써야 한다.

### 3-7. 어디에 적용하고 어디에 적용하지 않는가

**패딩은 공짜가 아니다.** 변수 하나를 위해 64바이트에서 128바이트를 쓰는 메모리 낭비이고, 그만큼 캐시에 담을 수 있는 유효 데이터가 줄어든다. 캐시 효율을 위해 한 짓이 캐시 효율을 떨어뜨리는 역설이 생길 수 있다.

그래서 **적용 기준을 명확히 잡아야 한다.**

**적용할 자리 — 여러 스레드가 각자 초고빈도로 "쓰는" 필드.** 카운터 셀, 링 버퍼의 생산자·소비자 인덱스처럼 서로 다른 스레드가 각자 자기 것을 미친 듯이 갱신하는 자리다.

**적용하지 않을 자리 — 읽기만 하는 데이터.** **여러 코어가 같은 라인의 복사본을 공유해서 읽는 것은 아무 문제도 없다.** 무효화는 **누군가 쓸 때만** 일어나기 때문이다. 읽기 전용 설정값이나 불변 객체가 한 라인에 몰려 있는 것은 오히려 캐시 효율에 이롭다.

**적용하지 않을 자리 — 갱신 빈도가 낮은 필드.** 초당 몇 번 갱신되는 필드에 패딩을 붙이는 것은 메모리만 쓰고 얻는 것이 없다.

**그리고 무엇보다, 측정 없이 붙이지 않는다.** false sharing은 존재를 알고 나면 어디에나 있을 것처럼 보이는데, 실제로 처리량을 꺾을 만큼 문제가 되는 자리는 드물다. **먼저 "스레드를 늘렸는데 처리량이 안 는다"는 현상을 관측하고, 그다음에 원인을 확인하고, 그다음에 붙인다.**

## 4. 꼬리질문 대비 포인트

### "false sharing이 실제로 일어나고 있는지 어떻게 확인하나요?" (시니어 변별 포인트)

**"프로파일러에는 안 잡힌다"는 사실을 먼저 말하는 것이 이 질문의 핵심이다.** 락도 없고, CAS 실패도 없고, 스레드는 전부 `RUNNABLE`이다. 애플리케이션 레벨의 어떤 지표도 이상을 가리키지 않는다.

**그래서 첫 단서는 증상 쪽에서 온다.** 스레드 수나 코어 수를 늘렸는데 **처리량이 비례해서 늘지 않거나 오히려 줄어드는 것**이 전형적인 신호다. 스레드 1개 대비 8개의 처리량이 8배는커녕 2배도 안 되면서 CPU 사용률은 꽉 차 있다면 의심할 만하다.

**두 번째는 하드웨어 카운터다.** 리눅스라면 `perf stat`으로 캐시 미스와 코어 간 전송 관련 이벤트를 보고, 더 직접적으로는 **`perf c2c`**를 쓴다. 이 도구는 이름 그대로 cache-to-cache 전송을 추적해서 **어느 캐시 라인이 어느 코어들 사이에서 얼마나 왕복했는지, 그 라인 안의 어느 오프셋에 접근이 몰렸는지**까지 보여준다. false sharing을 확정하기에 가장 직접적인 증거다.

**세 번째는 대조 실험이다.** 의심되는 필드에 패딩을 넣은 버전과 안 넣은 버전을 만들어 같은 조건에서 벤치마크를 돌린다. JMH로 스레드 수를 1, 2, 4, 8로 바꿔 가며 확장성 곡선을 그려 보면, 패딩 유무에 따라 곡선 모양이 확연히 갈린다. **"패딩을 넣었더니 스레드 8개에서 처리량이 몇 배가 됐다"는 수치가 있어야 근거 있는 최적화가 된다.**

**마지막으로, 코드만 보고 후보를 좁힐 수도 있다.** "여러 스레드가 각자 자기 인덱스만 쓰는 배열", "여러 스레드가 각자 갱신하는 인접 필드들"이라는 패턴 자체가 강한 후보다.

### "그럼 카운터는 전부 `LongAdder`로 바꾸면 되는 것 아닌가요?"

**아니다. 세 가지 이유로 `AtomicLong`이 더 나은 자리가 있다.**

**첫째, `sum()`이 정확한 스냅샷이 아니다.** 값이 여러 셀에 흩어져 있고 순회하며 더하는 동안에도 다른 셀이 갱신되므로, **어느 한 시점의 총합이라고 말할 수 없다.** 갱신이 멈춘 상태에서는 정확하지만, 돌아가는 중에는 특정 시점을 지목할 수 없다. 잔액이나 재고처럼 **읽은 값으로 판단해서 쓰기를 하는 자리**에는 쓸 수 없다.

**둘째, `compareAndSet`이 없다.** "내가 읽은 값이 그대로면 차감"을 원자적으로 시도하는 연산이 아예 제공되지 않는다. `LongAdder`는 단순 누적 전용이다.

**셋째, 저경합에서는 손해다.** 셀 배열과 패딩 때문에 메모리를 코어 수만큼 더 쓰고, 읽을 때마다 셀을 순회해야 한다. 경합이 없다면 `AtomicLong`이 메모리도 적고 읽기도 값 하나만 보면 끝이다. `LongAdder`도 경합이 없을 때는 단일 `base`에 CAS를 걸도록 만들어져 있지만, 그래도 읽기 비용과 메모리 비용은 남는다.

**정리하면 기준은 이렇다. 쓰기가 압도적으로 많고 읽기는 가끔이며 몇 건의 오차가 의사결정을 바꾸지 않는 통계·모니터링 카운터면 `LongAdder`, 정확한 값을 자주 읽거나 CAS 연산이 필요하면 `AtomicLong`.**

### "`AtomicLong`의 CAS 실패가 왜 단순한 재시도보다 비싼가요?"

**"명령 몇 개를 더 실행하는 것"이 아니라 "캐시 라인 하나가 코어 사이를 왕복하는 것"이기 때문이다.** 이 대답이 나오는지가 이 질문의 전부다.

배경은 캐시 일관성 프로토콜이다. **어떤 코어가 메모리를 고치려면 그 데이터가 든 캐시 라인을 배타적으로 소유해야 하고, 그러려면 그 라인을 들고 있던 다른 모든 코어의 복사본을 먼저 무효화해야 한다.** 그리고 **CAS는 읽기가 아니라 쓰기 시도**이므로, 성공하든 실패하든 배타 소유를 요구한다.

그래서 스레드 여덟 개가 같은 카운터에 CAS를 걸면 이렇게 된다. 하나가 성공하는 순간 나머지 일곱 코어의 복사본이 무효화되고, 실패한 일곱은 **자기 L1에서 값을 못 읽어서** 라인을 다시 끌어와야 하며, 다시 CAS를 걸려면 또 배타 소유가 필요해 또 무효화가 돈다. **자기 L1을 읽는 것과 다른 코어의 캐시에서 끌어오는 것은 비용의 자릿수가 다르다.**

그래서 **스레드를 늘릴수록 처리량이 비례해 늘기는커녕 어느 지점부터 꺾인다.** 락이 없어서 스레드가 잠들지는 않지만, **경합 지점이 하나라는 문제는 락을 쓸 때와 똑같이 남아 있다.**

여기까지 말하면 `LongAdder`가 왜 답인지도 자연히 이어진다 — **주소를 여러 개로 쪼개면 라인 왕복 자체가 사라진다.** 그리고 그 셀들이 같은 라인에 앉으면 다시 같은 문제가 생기므로 `@Contended`가 필요하다는 것까지 연결된다.

### "`@Contended`를 우리 애플리케이션 코드에 붙여도 되나요?"

**붙일 수는 있지만 문턱이 높고, 조용히 실패할 위험이 있다는 점을 알아야 한다.**

세 가지 벽이 있다. **패키지가 `jdk.internal.vm.annotation`으로 옮겨져** 모듈 시스템이 접근을 막으므로 컴파일·실행에 `--add-exports java.base/jdk.internal.vm.annotation=ALL-UNNAMED`가 필요하다(Java 8에서는 `sun.misc.Contended`였다). **`-XX:-RestrictContended` 플래그가 없으면 JVM이 그냥 무시한다.** 그리고 **이 설정들이 실행 환경에 묶이므로**, 라이브러리로 배포하면 사용자의 JVM 옵션에 따라 성능 특성이 달라진다.

**가장 위험한 것은 두 번째다.** 플래그를 모르고 어노테이션만 붙여 놓으면 아무 효과도 없는데 조치했다고 믿게 된다. **효과를 확인하는 벤치마크 없이 붙이면 안 되는 이유**가 이것이다.

그래서 실무적인 답은 셋 중 하나다. **`@Contended`가 이미 적용된 JDK 클래스를 쓴다**(`LongAdder`가 대표적이다). **자료구조 배치로 피한다** — 배열이라면 인덱스를 한 라인 폭만큼 띄워 배정하는 것이 어노테이션 없이도 확실하다. 그것도 안 되면 **수동 패딩**인데, JVM이 필드를 선언 순서대로 배치한다는 보장이 없어서 의도대로 됐는지 객체 레이아웃을 확인해야 한다.

### "`LongAdder`를 잔액 관리에 쓰면 정확히 무엇이 깨지나요?"

**두 단계로 깨진다.**

**첫째, 읽는 값의 시점을 특정할 수 없다.** `sum()`은 `base`와 셀들을 하나씩 순회하며 더하는데 그 전체가 원자적이지 않다. 순회 도중에 이미 지나간 셀이 갱신되면 그 갱신은 빠지고, 아직 안 지나간 셀이 갱신되면 그 갱신은 들어간다. 결과적으로 **"어느 한 순간에도 실제로 이 값이었던 적이 없는 총합"**이 나올 수 있다. 대시보드의 요청 수라면 상관없지만, 잔액이라면 이 값을 근거로 판단할 수 없다.

**둘째, 판단과 갱신을 원자적으로 묶을 방법이 없다.** 잔액 차감은 "잔액이 충분한가 확인하고, 충분하면 뺀다"는 검사 후 행동이다. `AtomicLong`이라면 `compareAndSet`으로 "내가 읽은 값이 그대로면 새 값으로"를 원자적으로 시도할 수 있지만, **`LongAdder`에는 그런 연산이 없다.** 값이 여러 셀에 흩어져 있는 구조에서는 성립할 수가 없다. 그래서 `sum()`으로 읽고 판단한 뒤 `add()`로 빼는 사이가 통째로 비어 있고, 그 사이에 다른 스레드가 끼어들면 잔액이 음수로 내려간다.

**정리하면 `LongAdder`는 "누적만 하고, 정확한 값은 갱신이 멈춘 뒤에 읽는" 용도로 설계된 도구**다. 돈이나 재고처럼 **읽은 값이 곧 의사결정의 근거가 되는 자리**는 설계 의도 자체가 다르다. 그 자리에는 `AtomicLong`의 CAS 루프를 쓰거나, 애초에 DB 트랜잭션과 락으로 올라가는 것이 맞다.

## 한 줄 요약

`AtomicLong`이 고경합에서 꺾이는 이유는 CAS 재시도 횟수 자체가 아니라 **CAS가 쓰기 시도라서 실패할 때마다 캐시 라인의 배타 소유권이 코어 사이를 왕복하기 때문**이고(스레드 N개면 성공 1건마다 실패 최대 N-1건, 그 실패마다 라인 왕복), 그래서 해법은 경합 지점을 쪼개는 것 — `LongAdder`는 쓰기를 스레드별 셀로 분산하고 읽을 때만 합산하되 **`sum()`이 어느 시점의 값인지 특정할 수 없고 `compareAndSet`도 없으므로** 통계·모니터링 카운터 전용이고 잔액·재고에는 쓰면 안 된다 — 그리고 셀을 쪼개도 그것들이 같은 캐시 라인(일반적인 x86-64에서 64바이트이며 아키텍처마다 다르다)에 앉으면 **공유하지 않는데 무효화만 주고받는** false sharing으로 도로 느려지므로, 뜨겁게 **쓰는** 필드에 한해 패딩·`@Contended`(`-XX:-RestrictContended` 필요, `jdk.internal.vm.annotation`이라 애플리케이션 코드에서는 문턱이 높다)·인덱스 띄우기로 라인을 독점시키며, 읽기만 하는 데이터는 무효화가 없으므로 애초에 대상이 아니다.
