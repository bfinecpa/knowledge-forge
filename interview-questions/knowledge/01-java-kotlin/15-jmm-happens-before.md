# Java Memory Model의 happens-before 관계 — "먼저 실행된다"가 아니라 "반드시 보인다"

> 핵심 관전 포인트: **happens-before는 시간 순서가 아니라 가시성 보장이다. "A happens-before B"는 "A가 시계상 먼저 실행된다"는 뜻이 아니라 "A에서 한 모든 메모리 쓰기가 B에서 반드시 보인다"는 뜻이며, 이 오해를 깨는 것이 이 질문의 절반이다. 나머지 절반은 왜 이런 규칙이 필요한가다 — CPU 캐시와 컴파일러·CPU의 재배치 때문에 스레드 간 가시성은 기본적으로 보장되지 않고, 하드웨어마다 그 규칙마저 다르기 때문에, 자바는 "어떤 하드웨어에서 돌아도 이만큼은 보장한다"는 최소선을 JMM(Java Memory Model)이라는 언어 차원의 명세로 정의했다. happens-before는 그 최소선을 표현하는 언어이고, 프로그램 순서·모니터 락·volatile·start/join 규칙이 이 관계를 만들며, 이행성으로 이어 붙여 안전 발행(safe publication)을 완성한다. 이 관계가 없는 공유 접근이 곧 데이터 레이스다.**

---

## 0. 질문 + 의도

**질문**: "Java Memory Model에서 happens-before 관계란 무엇인가요?"

**출제 의도**: 동시성 코드의 정확성을 "돌려보니 되던데요"가 아니라 규칙으로 논증할 수 있는지를 본다. 이게 되는 사람만 lock-free 코드나 AI가 생성한 동시성 코드를 검증할 수 있다.

## 1. 왜 이런 규칙이 필요한가 — 그리고 happens-before가 실제로 뜻하는 것

### 1-1. 전제 지식 ① — 가시성: 쓴 값이 안 보일 수 있다

```java
// 스레드 A                        // 스레드 B
sharedFlag = true;                 while (!sharedFlag) { }   // 영원히 안 끝날 수 있다
```

이 코드가 안 끝날 수 있다는 말은 처음 들으면 납득이 안 된다. 같은 프로세스, 같은 변수인데 왜 안 보인다는 말인가.

이유는 **CPU가 메인 메모리를 직접 읽고 쓰지 않기 때문**이다. 메인 메모리는 CPU 입장에서 너무 느려서, 코어마다 자기 전용 캐시(L1, L2)에 데이터를 복사해 두고 그 복사본으로 일한다. 스레드 A가 코어 0에서 쓴 값은 일단 코어 0의 캐시에 있고, 코어 1에서 도는 스레드 B는 그 캐시를 들여다볼 수 없다. 값이 언제 아래 계층으로 내려가 B에게 도달할지는 하드웨어 사정이다.

여기에 컴파일러 최적화가 겹친다. JIT가 "이 루프 안에서 `sharedFlag`를 바꾸는 코드가 없다"고 판단하면 값을 레지스터에 한 번만 담고 계속 재사용하도록 코드를 바꾼다. 단일 스레드 기준으로는 완벽하게 옳은 최적화다. 그 결과 B는 메모리를 아예 다시 읽지 않게 되고, A의 변경은 **영영 도착하지 않는다.**

이렇게 **한 스레드가 쓴 값을 다른 스레드가 언제 볼지, 보기는 할지 보장되지 않는** 문제를 **가시성(visibility)** 문제라 한다.

### 1-2. 전제 지식 ② — 재배치: 순서가 뒤집혀 보일 수 있다

```
// 프로그래머가 쓴 순서              // 실제로 실행될 수 있는 순서
data = 42;      // ①                ready = true;   // ② 가 먼저!
ready = true;   // ②                data = 42;      // ① 가 나중
```

**컴파일러와 CPU는 성능을 위해 명령의 실행 순서를 바꾼다.** 다만 지켜야 할 선이 하나 있다 — **단일 스레드에서 관측되는 결과가 같기만 하면 순서를 바꿔도 된다.**

위 두 문장은 서로 의존 관계가 없다. `data`를 먼저 쓰든 `ready`를 먼저 쓰든 그 스레드 혼자 보기에는 결과가 같다. 그래서 컴파일러는 메모리 접근을 모으려고, CPU는 앞선 명령이 메모리를 기다리며 멈춘 사이 뒤 명령을 먼저 처리하려고 순서를 바꾼다.

단일 스레드에서는 아무 문제가 없다. 문제는 **다른 스레드가 그 중간을 들여다볼 때** 생긴다. B가 `ready == true`를 보고 `data`를 읽었는데 `data`는 아직 0인 상황이 실제로 일어난다.

이것을 **재배치(reordering)** 문제라 한다. 버그가 아니라 **다른 스레드의 존재를 고려하지 않는 최적화**라는 점이 중요하다.

### 1-3. 왜 언어 차원의 명세가 필요한가 — 하드웨어마다 규칙이 다르다

여기까지가 "왜 동기화가 필요한가"인데, JMM이 왜 존재하는지는 한 걸음 더 들어가야 나온다.

**재배치를 어디까지 허용하는지가 CPU 아키텍처마다 다르다.**

x86 계열은 메모리 순서 규칙이 비교적 엄격해서, 쓰기와 쓰기 사이의 순서를 잘 뒤집지 않는다. 반면 ARM 계열은 훨씬 느슨해서 같은 코드가 훨씬 자유롭게 재배치된다. (가산점 포인트) 그래서 **동기화가 빠진 똑같은 코드가 개발자의 x86 장비에서는 몇 년째 멀쩡히 돌다가, ARM 기반 서버로 옮기는 순간 터지는** 일이 실제로 벌어진다. 로컬은 x86인데 운영은 ARM 인스턴스라면, "여기선 잘 되는데요"가 정확성의 근거가 될 수 없는 구체적인 이유가 하나 더 생긴 셈이다.

만약 자바가 "메모리 가시성은 하드웨어가 하는 대로 따른다"고 했다면, **"이 코드가 맞는가"라는 질문의 답이 배포 대상 CPU에 따라 달라진다.** Write Once, Run Anywhere가 무너진다.

그래서 자바는 언어 차원에서 선을 하나 긋는다. **"어떤 하드웨어에서 돌아가든 이만큼은 보장한다"는 최소선**을 명세로 정의하고, JVM 구현체가 각 하드웨어에서 그 선을 지키도록 필요한 메모리 배리어를 알아서 끼워 넣게 하는 것이다.

여기서 **메모리 배리어(memory barrier)**는 "이 지점을 넘어 읽기·쓰기를 재배치하지 말고, 여기까지의 쓰기를 다른 코어가 볼 수 있게 하라"고 CPU에 지시하는 특수 명령이다. `volatile` 쓰기 하나가 x86에서는 가벼운 명령으로, ARM에서는 더 무거운 배리어로 번역될 수 있는데, 그 차이를 감춰주는 것이 JVM의 역할이다.

**이 최소선을 정의한 명세가 JMM(Java Memory Model)이고, 그 보장을 표현하는 언어가 happens-before다.**

```
[개발자가 쓰는 코드]   동기화 도구 (volatile, synchronized, start/join, Atomic)
        |
        v
[JMM 명세]             "이 도구를 쓰면 이런 happens-before가 성립한다"는 최소 보장
        |
        v
[JVM 구현]             각 CPU에 맞는 메모리 배리어와 컴파일 제약으로 번역
        |
        v
[하드웨어]             x86 / ARM / ... 각자 다른 재배치 규칙
```

### 1-4. happens-before의 정확한 뜻 — 이 오해부터 깬다

이름이 오해를 부른다. happens-before를 직역하면 "먼저 일어난다"이므로, 십중팔구 **시간 순서**로 읽게 된다. **그 독해가 틀렸다.**

> 연산 A **happens-before** 연산 B라는 것은,
> **A가 수행한 모든 메모리 쓰기가 B에서 반드시 보이고,**
> **A와 B의 순서가 B의 관점에서 뒤집혀 관측되지 않는다**는 뜻이다.

즉 **시간에 대한 진술이 아니라 가시성과 순서 관측에 대한 보장**이다. 두 방향 모두 오해가 생기므로 양쪽을 다 짚어야 한다.

**"시계상 먼저 실행되면 happens-before다" — 틀렸다.** 스레드 A가 밀리초 단위로 먼저 `data = 42`를 실행했더라도, A와 B 사이에 happens-before를 만드는 규칙이 하나도 걸려 있지 않으면 B는 그 42를 **영영 못 볼 수도 있다.** 1-1의 캐시와 1-2의 재배치가 그대로 작동하기 때문이다. 시간은 보장을 만들지 않는다.

**"happens-before면 시계상 먼저 실행된다" — 이것도 정확한 진술이 아니다.** JMM이 요구하는 것은 "그렇게 보인다"이지 "실제로 그 순서로 실행된다"가 아니다. JVM과 CPU는 보장만 지켜진다면 내부적으로 얼마든지 재배치할 수 있다.

굳이 이름을 다시 짓는다면 **"is-visible-to(에게 보인다)"** 쪽이 실체에 가깝다. 면접에서 이 한 줄을 먼저 말하고 시작하면 나머지 설명이 전부 제자리를 찾는다.

주의할 성질이 하나 더 있다. happens-before는 **부분 순서(partial order)**다. 모든 연산 쌍에 순서가 정해져 있는 게 아니라, **2절의 규칙에 해당하는 쌍에만** 관계가 생긴다. 관계가 없는 두 연산은 서로에게 어떤 순서로든 보일 수 있고, 그 상태가 곧 데이터 레이스다(3-2).

## 2. 규칙 하나씩 — 정의와, 그 규칙이 없으면 깨지는 코드

happens-before 관계는 저절로 생기지 않는다. **JLS §17.4.5가 정한 규칙에 해당할 때만** 생긴다. 목록을 먼저 보고, 각각을 코드와 짝지어 보자.

| 규칙 | 성립하는 관계 |
|---|---|
| 프로그램 순서 | 한 스레드 안에서, 코드에 먼저 나온 연산 HB 뒤에 나온 연산 |
| 모니터 락 | `synchronized` 블록의 unlock HB **같은 락**의 이후 lock |
| volatile | volatile 변수에 대한 쓰기 HB **같은 변수**의 이후 읽기 |
| 스레드 시작 | `thread.start()` 호출 HB 그 스레드 안의 모든 연산 |
| 스레드 종료 | 스레드 안의 모든 연산 HB 그 스레드에 대한 `join()`의 반환 |
| 인터럽트 | `interrupt()` 호출 HB 대상 스레드가 인터럽트를 감지하는 시점 |
| finalizer | 객체 생성자의 끝 HB 그 객체의 `finalize()` 시작 |
| 이행성 | A HB B이고 B HB C이면 A HB C |

### 2-1. 프로그램 순서 — 그리고 그 함정

**한 스레드 안에서는 코드에 먼저 나온 연산이 뒤에 나온 연산보다 happens-before다.**

이 규칙만 보면 "그럼 재배치는 안 일어나는 것 아닌가" 싶지만 아니다. **이 보장은 그 스레드 자신의 관점에서만 유효하다.** 재배치는 여전히 일어나며, 단지 그 스레드 혼자 볼 때 결과가 코드 순서와 같을 뿐이다.

```java
// 한 스레드 안
data = 42;      // ①
ready = true;   // ②
// ① HB ② 는 성립한다. 이 스레드가 ② 이후에 data를 읽으면 반드시 42다.
// 그러나 다른 스레드는 ②의 결과를 먼저 보고 ①의 결과를 나중에 볼 수 있다.
```

**다른 스레드가 끼어드는 순간 재배치가 관측된다.** 그래서 스레드 사이에는 아래 규칙들로 별도의 "다리"를 놓아야 한다. 프로그램 순서 규칙은 다리의 양쪽 끝을 연결하는 데 쓰이지, 그 자체로 스레드를 건너가지 못한다.

### 2-2. 모니터 락 — unlock HB 그 다음 lock

**`synchronized` 블록을 빠져나가는 것(unlock)이, 같은 락 객체에 대한 이후의 진입(lock)보다 happens-before다.**

락이 상호배제만 하는 도구라고 생각하면 이 규칙을 놓친다. 락은 **상호배제와 가시성 두 가지를 함께** 제공한다. A가 락 안에서 한 모든 쓰기는, 그 락을 이어받은 B에게 전부 보인다.

**"같은 락"이라는 조건이 결정적이다.** 이게 빠지면 규칙이 성립하지 않는다.

```java
// (문제) 두 스레드가 서로 다른 락을 잡는다 — HB가 성립하지 않는다
private final Object lockA = new Object();
private final Object lockB = new Object();
private int data = 0;

void writer() { synchronized (lockA) { data = 42; } }
void reader() { synchronized (lockB) { print(data); } }
// 둘 다 synchronized를 썼으니 안전해 보이지만, 락 객체가 다르므로
// unlock HB lock 이 성립하지 않는다. reader는 0을 볼 수 있다.
// 상호배제도 안 된다 — 서로 다른 문이라 동시에 들어간다.

// (개선) 같은 락으로 묶어야 관계가 생긴다
private final Object lock = new Object();
void writer() { synchronized (lock) { data = 42; } }
void reader() { synchronized (lock) { print(data); } }
```

이 실수는 실무에서 생각보다 자주 나온다. 여러 메서드에 `synchronized`를 붙였는데 어떤 것은 인스턴스 메서드(락 = `this`)이고 어떤 것은 static 메서드(락 = 클래스 객체)인 경우가 대표적이다. **둘은 서로 다른 락이므로 아무 관계도 만들지 못한다.**

### 2-3. volatile — 쓰기 HB 그 다음 읽기

**volatile 변수에 대한 쓰기가, 같은 변수에 대한 이후의 읽기보다 happens-before다.**

락 없이 happens-before를 만들 수 있는 가장 가벼운 수단이다. 상호배제는 주지 않고 가시성과 순서만 준다.

```java
// (문제) ready에 volatile이 없다
int data = 0;
boolean ready = false;

// 스레드 A                   // 스레드 B
data = 42;                    if (ready)        // true를 볼 수도 있는데
ready = true;                     print(data);  // data는 0일 수 있다

// (개선) volatile 하나가 다리를 놓는다
int data = 0;                    // 이 변수는 volatile이 아니어도 된다
volatile boolean ready = false;  // 다리 역할을 하는 것은 이 변수 하나
```

`data`에 volatile이 없는데도 42가 보장된다는 것이 이 패턴의 묘미인데, 그 근거가 이행성이다(2-6).

### 2-4. Thread.start() — 호출 이전의 모든 것 HB 새 스레드 내부

**`thread.start()`를 호출하기 전에 그 스레드가 한 모든 연산이, 새로 시작된 스레드 안의 모든 연산보다 happens-before다.**

새 스레드에 작업 데이터를 넘기는 일이 매번 가능한 것이 이 규칙 덕분이다.

```java
config = loadConfig();        // ① 일반 필드에 대한 평범한 쓰기 (volatile 아님)
Thread t = new Thread(() -> {
    use(config);              // ② ①이 반드시 보인다 — start() 규칙 덕분
});
t.start();
```

이 규칙이 없다면 어떻게 되는지 상상해 보면 값이 분명해진다. **새 스레드는 다른 코어에서 시작될 수 있으므로, 부모 스레드가 준비해 둔 데이터가 안 보일 수 있다.** 그러면 스레드에 데이터를 넘길 때마다 volatile이나 락으로 일일이 다리를 놓아야 한다. JMM이 이 관계를 보장해 주기 때문에 우리는 그냥 필드에 값을 채우고 `start()`를 부르면 된다.

한 가지 흔한 오해를 덧붙이면, 이 규칙은 **`start()` 호출 이전**의 쓰기에만 적용된다. `start()` 이후에 부모가 바꾼 값은 이 규칙과 무관하며, 그건 다시 일반적인 가시성 문제다.

### 2-5. join() — 스레드 내부의 모든 것 HB join()의 반환

**어떤 스레드 안의 모든 연산이, 다른 스레드에서 그 스레드에 대해 호출한 `join()`이 반환되는 시점보다 happens-before다.**

`start()`의 반대 방향이다. 자식 스레드가 만든 결과를 부모가 안전하게 받아오는 통로다.

```java
// (개선) join()이 결과의 가시성까지 보장한다
Worker w = new Worker();
Thread t = new Thread(w);
t.start();
t.join();
print(w.result);   // 워커가 채운 result가 반드시 보인다. result가 volatile이 아니어도 된다.

// (문제) join() 대신 직접 기다리면 그 보장이 사라진다
t.start();
while (t.isAlive()) { }        // 스레드가 끝난 것은 알 수 있지만
print(w.result);               // result의 가시성을 보장하는 규칙이 없다

// 더 나쁜 경우
t.start();
Thread.sleep(1000);            // "1초면 끝났겠지"
print(w.result);               // 끝났다는 보장도, 결과가 보인다는 보장도 없다
```

**"끝난 것을 아는 것"과 "그 결과가 보이는 것"은 별개**라는 점이 이 규칙의 교훈이다. `isAlive()` 폴링이나 `sleep`으로 대체하면 앞의 것만 얻고 뒤의 것은 잃는다. `join()`(또는 `Future.get()`, `CountDownLatch.await()` 같은 문서화된 대체물)을 써야 하는 이유가 여기 있다.

### 2-6. 이행성 — 규칙들을 이어 붙이는 접착제

**A HB B이고 B HB C이면 A HB C다.**

목록의 마지막 줄에 붙은 한 줄짜리 규칙이지만, **실무에서 happens-before가 쓸모 있어지는 이유의 전부**가 여기 있다. 앞의 규칙들은 각각 특정 지점 하나만 연결하는데, 이행성이 그것들을 이어 붙여 **스레드를 가로지르는 긴 다리**를 만든다.

2-3의 예제를 규칙으로 논증해 보자.

```java
int data = 0;                    // 일반 변수 (volatile 아님)
volatile boolean ready = false;

// 스레드 A                     // 스레드 B
data = 42;      // ①            if (ready) {          // ③
ready = true;   // ②                print(data);      // ④ 반드시 42
                                }
```

```
① HB ②   : 프로그램 순서 (같은 스레드 A 안, ①이 코드상 먼저)
② HB ③   : volatile 규칙 (같은 변수 ready에 대한 쓰기 -> 읽기)
③ HB ④   : 프로그램 순서 (같은 스레드 B 안, ③이 코드상 먼저)
--------------------------------------------------------------
∴ ① HB ④ : 이행성으로 연결 -> data = 42가 ④에서 반드시 보인다
```

이 유도가 보여주는 것을 말로 옮기면 이렇다. **volatile 쓰기는 "그 이전에 쓴 모든 것"을 함께 발행하고, volatile 읽기는 "그 이후 읽는 모든 것"의 가시성 기준점이 된다.** volatile 변수 하나가 일반 변수 여럿을 실어 나르는 화물칸 역할을 하는 셈이다.

`synchronized`도 구조가 같다. unlock 이전의 모든 쓰기가 같은 락의 lock 이후에 전부 보인다. 다리를 놓는 도구가 volatile이냐 락이냐만 다르다.

### 2-7. 나머지 규칙들

**인터럽트**: `interrupt()` 호출이 대상 스레드가 인터럽트를 감지하는 시점(`InterruptedException`을 받거나 `isInterrupted()`가 true를 반환하는 시점)보다 happens-before다. 인터럽트를 신호로 쓸 때 그 이전에 준비한 데이터가 함께 보인다.

**finalizer**: 객체 생성자의 끝이 그 객체의 `finalize()` 시작보다 happens-before다. `finalize()` 자체가 폐기 대상이라 실무에서 의미는 없고, 목록의 완결성을 위해 알아두는 정도면 된다.

**`java.util.concurrent` 전반**: 이 패키지의 클래스들은 API 문서에 자신이 제공하는 happens-before를 명시한다. 이것이 중요한 이유는 **직접 volatile이나 락을 쓰지 않아도 이 클래스들을 통과하는 것만으로 다리가 놓인다**는 뜻이기 때문이다.

- `BlockingQueue`에 원소를 `put`하기 이전의 연산 HB 다른 스레드가 그 원소를 `take`한 이후의 연산
- `ExecutorService.submit()` 이전의 연산 HB 그 태스크의 실행
- 태스크 안의 모든 연산 HB `Future.get()`의 반환
- `CountDownLatch.countDown()` 이전의 연산 HB `await()`의 반환

생산자-소비자 구조를 `BlockingQueue`로 짜면 큐에 넣는 객체에 volatile을 붙일 필요가 없는 것이 이 보장 덕분이다.

## 3. 실전 — 안전 발행, 데이터 레이스, final 필드

### 3-1. 안전 발행(safe publication) — 다리 놓기 패턴

2-6에서 본 구조에 이름이 있다. **안전 발행(safe publication)** — 완성된 데이터를 다른 스레드가 반쪽짜리로 보지 않게 넘기는 것이다.

패턴은 일정하다. **일반 변수들에 값을 다 채워 넣은 다음, 마지막에 동기화 연산(volatile 쓰기 또는 unlock)을 한다.** 받는 쪽은 그 동기화 연산(volatile 읽기 또는 lock)을 먼저 통과한 뒤 데이터를 읽는다. 그러면 앞서 채운 값이 전부 함께 건너온다.

```
[보내는 쪽]                          [받는 쪽]
일반 쓰기들 ...                       동기화 읽기 (volatile read / lock)
동기화 쓰기 (volatile write / unlock) ------> 일반 읽기들
    ^                                            ^
    +-- 이 지점 이전의 모든 쓰기가 -----------> 여기서 전부 보인다
```

객체를 발행하는 안전한 방법은 실무적으로 넷으로 정리된다.

- static 초기화로 만든다(클래스 초기화가 JVM에 의해 동기화된다).
- volatile 필드나 `AtomicReference`에 대입한다.
- `final` 필드에 대입한다(3-3).
- 락으로 보호되는 필드에 대입한다(또는 `ConcurrentHashMap` 같은 스레드 안전 컬렉션에 넣는다).

### 3-2. 다리가 없으면 — 데이터 레이스의 정의

```java
int data = 0;
boolean ready = false;        // volatile이 아니다

// 스레드 A                   // 스레드 B
data = 42;      // ①          if (ready)        // ③ true를 볼 수도 있는데
ready = true;   // ②              print(data);  // ④ data는 0일 수 있다
```

②와 ③ 사이에 happens-before를 만드는 규칙이 하나도 없다. 결과는 둘 다 가능해진다. ①과 ②가 재배치되어 B가 `ready == true`를 먼저 볼 수 있고, `data = 42`는 영영 안 보일 수도 있다.

이 상태를 **데이터 레이스(data race)**라 부르며, 정의는 세 조건의 합이다.

1. 서로 다른 스레드의 두 접근이 **같은 변수**를 대상으로 하고,
2. 그중 **적어도 하나가 쓰기**이며,
3. 두 접근 사이에 **happens-before 관계가 없다.**

세 번째 조건이 핵심이다. 여러 스레드가 같은 변수를 건드리는 것 자체는 레이스가 아니다. **관계가 없이 건드리는 것**이 레이스다. 그리고 데이터 레이스가 있는 프로그램에 대해 **JMM은 읽기 결과를 사실상 보장하지 않는다.** "가끔 이상한 값이 나온다"가 아니라 "무슨 값이 나와도 명세 위반이 아니다"에 가깝다.

그래서 동시성 코드의 정확성을 논증한다는 것은 결국 이 질문에 답하는 일이다. **"공유되는 이 변수의 읽기와 쓰기 사이에 happens-before를 만드는 규칙이 무엇인가?"** 답할 수 없으면 그 코드는 테스트를 통과했더라도 틀렸다.

### 3-3. final 필드의 특별 보장

`final`은 happens-before 규칙 목록에 없는데도 안전 발행의 수단으로 쓰인다. 별도의 보장이 따로 있기 때문이다.

**객체의 생성자가 정상적으로 끝나면, 그 객체의 `final` 필드에 생성자에서 넣은 값은 다른 스레드에게도 완성된 상태로 보인다.** 그 객체의 참조를 어떤 방식으로 넘겨받든, 심지어 동기화 없이 넘겨받아도 그렇다.

이 보장이 왜 필요한지는 volatile 없는 double-checked locking이 깨지는 이유와 같다. `new Holder()`는 "메모리 할당 → 생성자 실행 → 참조 대입"의 3단계인데, 재배치로 참조 대입이 생성자 실행보다 먼저 보일 수 있다. 그러면 다른 스레드가 **참조는 있는데 필드는 아직 기본값인 반쪽짜리 객체**를 잡게 된다. `final` 필드에 대해서는 JMM이 이 재배치를 금지해 그런 상태를 원천 차단한다.

```java
// 불변 객체가 동기화 없이도 안전하게 공유되는 근거가 바로 이것이다
public final class Money {
    private final long amount;      // final
    private final String currency;  // final
    public Money(long amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }
    // 이 객체의 참조를 어떤 방식으로 다른 스레드에 넘겨도
    // amount가 0이거나 currency가 null인 상태로는 보이지 않는다.
}
```

단, **조건이 하나 붙는다. 생성자가 끝나기 전에 `this` 참조가 밖으로 새어 나가면 안 된다.** 생성자 안에서 자신을 리스너로 등록하거나, 자기 참조를 static 필드나 컬렉션에 넣거나, 내부 스레드를 시작해 `this`를 넘기는 경우가 여기 해당한다. 이런 코드는 **아직 완성되지 않은 객체를 다른 스레드가 볼 수 있게 만들기 때문에** final의 보장이 무너진다. 이 현상을 `this` 탈출(this escape)이라 부른다.

### 3-4. 도구별 정리 — 무엇이 어떤 보장을 만드는가

| 도구 | 만들어지는 happens-before | 상호배제(원자성) |
|---|---|---|
| `synchronized` | unlock HB 같은 락의 lock | 있음 |
| `volatile` | 같은 변수의 쓰기 HB 읽기 | 없음 (가시성·순서만) |
| `Atomic*` / `VarHandle` CAS | volatile과 같은 시맨틱 | 해당 연산에 한해 있음 |
| `Thread.start()` / `join()` | 호출 전 HB 스레드 내부 / 스레드 내부 HB join 반환 | 해당 없음 |
| `java.util.concurrent` | 문서에 명시된 HB (put HB take 등) | 구현마다 다름 |
| `final` 필드 | HB 규칙은 아니지만 생성자 완료 후 안전 발행을 보장 | 해당 없음 |

이 표에서 반드시 붙잡아야 할 것은 **가시성과 원자성이 별개의 축**이라는 사실이다. `volatile int count`의 `count++`는 여전히 깨진다 — 읽기·계산·쓰기 3단계 사이에 다른 스레드가 끼어드는 것을 volatile은 막지 않기 때문이다(`14-volatile-visibility-vs-atomicity.md`). happens-before는 **"보이느냐"**에 대한 보장이지 **"끼어들 수 있느냐"**에 대한 보장이 아니다.

### 3-5. 실전 연결 — ConcurrentHashMap의 무락 읽기

`13-concurrenthashmap-internals.md`에서 본 "get이 락 없이도 안전한 이유"가 정확히 이 문서의 내용이다.

- `Node.val`, `Node.next`, `table`이 **volatile**이다 → put 스레드의 쓰기 HB get 스레드의 읽기가 성립하므로, 락 없이도 최신 값이 보인다.
- `Node.key`, `Node.hash`는 **final**이다 → 생성자 완료 후 안전 발행이 보장되므로, 갓 만들어진 노드를 다른 스레드가 발견해도 key가 null인 반쪽짜리 상태를 볼 수 없다.

여기서 읽어낼 설계 감각은 **"락 = 동기화"라는 등식을 깼다**는 것이다. 락은 가시성과 상호배제를 함께 주는 도구인데, 읽기 경로에는 가시성만 필요하다. 그래서 **가시성은 volatile로, 상호배제는 정말 필요한 버킷 하나에만 synchronized/CAS로** 분리했다. 이 분리가 가능하려면 "무엇이 무엇을 보장하는가"를 규칙 수준에서 알아야 하고, 그것이 이 질문을 묻는 이유다.

## 4. 꼬리질문 대비 포인트

### "happens-before가 '시간상 먼저 일어난다'는 뜻 아닌가요?"

**아니다. 이름이 오해를 부르지만 시간에 대한 진술이 아니라 가시성에 대한 보장이다.**

"A happens-before B"는 **"A에서 한 모든 메모리 쓰기가 B에서 반드시 보이고, 두 연산의 순서가 B의 관점에서 뒤집혀 관측되지 않는다"**는 뜻이다.

양방향으로 오해가 생기므로 둘 다 짚는 게 좋다. **시계상 먼저 실행됐더라도** happens-before 관계가 없으면 다른 스레드에게 그 결과가 안 보일 수 있다 — 캐시와 재배치가 그대로 작동하기 때문이다. 반대로 **happens-before가 성립한다고 해서** 실제 실행이 그 순서라는 뜻도 아니다. JVM과 CPU는 보장만 지켜지면 얼마든지 재배치한다.

이름을 다시 짓는다면 "is-visible-to"에 가깝다고 말하면 이해했다는 신호가 된다.

### "한 스레드 안에서는 재배치가 안 일어나나요?"

**일어난다.** 프로그램 순서 규칙은 "재배치가 없다"가 아니라 **"그 스레드 혼자 볼 때 결과가 코드 순서대로 보인다"**는 뜻이다.

컴파일러와 CPU는 단일 스레드의 관측 결과만 같으면 순서를 자유롭게 바꾼다. 그 재배치는 **다른 스레드가 중간을 들여다볼 때 관측된다.** `data = 42; ready = true;`가 뒤집혀 실행되면, 다른 스레드는 `ready == true`인데 `data == 0`인 상태를 볼 수 있다.

그래서 스레드 사이에는 반드시 volatile이나 락으로 별도의 다리를 놓아야 한다. 프로그램 순서 규칙은 다리의 양쪽 끝을 잇는 데 쓰일 뿐, 그 자체로는 스레드 경계를 넘지 못한다.

### "volatile 변수 하나로 일반 변수 여러 개의 가시성을 보장할 수 있는 근거는?" (시니어 변별 포인트)

**이행성(transitivity)이다.** 규칙 세 개를 이어 붙여 논증할 수 있어야 한다.

```
① data = 42       (스레드 A)
② ready = true    (스레드 A, volatile 쓰기)
③ if (ready)      (스레드 B, volatile 읽기)
④ print(data)     (스레드 B)

① HB ② : 프로그램 순서
② HB ③ : volatile 쓰기 HB 같은 변수의 읽기
③ HB ④ : 프로그램 순서
∴ ① HB ④ : 이행성 -> data = 42가 반드시 보인다
```

말로 옮기면 **volatile 쓰기는 그 이전의 모든 쓰기를 함께 발행하고, volatile 읽기는 그 이후 읽기의 가시성 기준점이 된다.** 이 패턴이 **안전 발행(safe publication)**이고, `synchronized`도 unlock/lock으로 구조가 같다.

한 걸음 더 나가면 좋은 지점이 있다. **이 보장은 "먼저 데이터를 다 채우고 마지막에 발행한다"는 순서를 지킬 때만 성립한다.** 발행 이후에 데이터를 더 채우면 그 쓰기는 다리 위에 실리지 않는다. 발행이 마지막이어야 한다는 것이 이 패턴의 유일한 규율이다.

### "데이터 레이스의 정확한 정의는 무엇인가요?"

세 조건이 동시에 성립하는 상태다.

1. 서로 다른 스레드의 두 접근이 **같은 변수**를 대상으로 하고,
2. 그중 **적어도 하나가 쓰기**이며,
3. 두 접근 사이에 **happens-before 관계가 없다.**

세 번째가 정의의 중심이다. 여러 스레드가 같은 변수를 건드리는 것 자체는 레이스가 아니다 — 관계 없이 건드리는 것이 레이스다. 반대로 모두가 읽기만 한다면 관계가 없어도 레이스가 아니다.

그리고 JMM은 데이터 레이스가 있는 프로그램의 읽기 결과를 **사실상 보장하지 않는다.** "가끔 오래된 값이 보인다" 수준이 아니라 "어떤 값이 나와도 명세 위반이 아니다"에 가깝다는 것을 알고 있으면 좋다. 그래서 "돌려보니 되던데요"는 정확성의 근거가 되지 못한다.

### "빈 synchronized 블록도 happens-before 효과가 있나요?"

이론적으로는 **있다.** 두 스레드가 같은 락을 잡는다면 블록 안이 비어 있어도 unlock HB lock이 성립하므로, 앞선 쓰기들이 뒤에 보인다.

그런데 **실무에서 이 용법에 의존하면 안 된다.** 이유가 둘이다.

첫째, JIT가 **아무 효과 없어 보이는 락을 제거(lock elision)**할 수 있다. 락 객체가 그 스레드 밖으로 새지 않는다고 판단하면 락 자체를 지워버린다. 의도한 배리어가 사라진다.

둘째, **의도가 코드에 드러나지 않는다.** 다음 사람이 "비어 있으니 지워도 되겠네"라고 판단할 여지가 크고, 그 순간 재현이 극히 어려운 버그가 들어온다.

목적이 가시성이라면 **그 목적에 정확히 대응하는 도구인 volatile을 쓰는 것**이 맞다. 코드가 의도를 말하게 된다.

(가산점 포인트) 같은 논리가 대기 수단 선택에도 적용된다. `join()`·`Future.get()`·`CountDownLatch.await()`·`BlockingQueue.take()`는 **문서에 happens-before 보장이 명시돼 있어서** 안전하지만, `isAlive()` 폴링이나 `Thread.sleep()`으로 "이쯤이면 끝났겠지" 하고 기다리는 코드에는 그런 규칙이 없다. **"끝난 것을 아는 것"과 "그 결과가 보이는 것"은 별개**이므로, 후자를 쓰면 결과 필드 읽기가 그대로 데이터 레이스가 된다.

## 한 줄 요약

happens-before는 JMM이 정의한 연산 간의 부분 순서로, "A happens-before B"는 **A가 시간적으로 먼저 실행된다는 뜻이 아니라 A에서 한 모든 메모리 쓰기가 B에서 반드시 보인다는 가시성 보장**이며 — 하드웨어마다 재배치 규칙이 다르기 때문에 자바가 "어떤 CPU에서도 이만큼은 보장한다"는 최소선을 언어 차원에서 명세한 것이 그 배경이다 — 프로그램 순서·모니터 락(unlock HB lock)·volatile(write HB read)·`start()`·`join()` 같은 규칙으로 만들어지고 이행성으로 이어 붙여 안전 발행 패턴을 완성하며, 이 관계 없이 이루어지는 공유 변수 접근이 곧 데이터 레이스이고 그 결과에 대해 JMM은 아무것도 보장하지 않는다.
