대량 INSERT와 JDBC batch
IDENTITY가 배치를 무력화하는 이유, 그리고 JPA 안에서 조여가는 4단계

면접 질문: "대량 데이터 INSERT 시 JPA의 한계와 JDBC batch로 우회하는 방법(IDENTITY 전략의 문제 포함)을 설명해주세요."

핵심 관전 포인트 — 100만 건이 2시간 걸리는 이유는 한 갈래가 아니라 두 갈래다 — ① 왕복 100만 번(건별 INSERT) ② 영속성 컨텍스트에 엔티티 100만 개 + 스냅샷 100만 벌이 그대로 누적(힙이 밀리고, flush마다 비교 대상이 늘어 뒤로 갈수록 느려진다). 첫 처방으로 "JPQL 벌크 INSERT"를 말하면 그 자리에서 끝난다 — JPQL에는 INSERT 문이 없다(insert into ... select 제외). 그리고 hibernate.jdbc.batch_size를 켜도 @GeneratedValue(IDENTITY)면 단 한 건도 묶이지 않는다: 1차 캐시의 키가 식별자라서 id 없이는 영속 상태를 만들 수 없고, 그래서 persist()가 그 자리에서 INSERT를 날려 키를 받아온다 → 쓰기 지연이 성립하지 않으니 묶을 대상 자체가 없다. 처방은 JPA를 버리는 것이 아니라 JPA 안에서 순서대로 조이는 것이다 — ① ID 전략을 SEQUENCE(PostgreSQL) 또는 TABLE(MySQL) + 큰 allocationSize로 바꿔 채번을 미리 받아오고 ② batch_size + order_inserts로 같은 테이블끼리 모으고 ③ 배치 크기마다 flush() + clear()로 힙을 비우고 ④ 그래도 부족할 때 JdbcTemplate.batchUpdate 또는 벌크 적재 명령(PostgreSQL COPY, MySQL LOAD DATA INFILE)으로 내려간다. 여기서 드라이버 층을 반드시 확인해야 한다 — PostgreSQL은 배치를 파이프라이닝으로 밀어 보내지만 문장은 행마다 실행되므로 reWriteBatchedInserts=true가 있어야 multi-values 한 문장으로 합쳐지고, MySQL은 rewriteBatchedStatements=true가 없으면 아예 문장을 하나씩 보낸다. 이건 Hibernate 로그로는 절대 확인되지 않는다. 마지막으로 100만 건을 트랜잭션 하나로 묶지 않는다 — 청크 단위 커밋 + (정산일자, 거래ID) 유니크 키 기반 멱등성이 있어야 어디서 끊겨도 재실행할 수 있다. 그리고 내려가는 데에는 대가가 있다 — Auditing·엔티티 검증·영속성 컨텍스트 정합성·타입 안전성을 함께 내려놓는 것이지, 공짜로 빨라지는 것이 아니다.
  • 1
    원인을 두 갈래로 쪼개서 말한다 — ① 왕복 100만 번(비용이 왕복 횟수에 비례하므로 하드웨어로는 안 움직인다) ② 영속성 컨텍스트 누적(엔티티 + 스냅샷이 쌓여 flush마다 대조 대상이 커진다). "쿼리가 100만 번 나가서"까지만 말하면 처방도 절반만 나온다 — 배치만 켜고 clear()를 빼먹는다.
  • 2
    batch_size는 안 켜진 게 아니라 켜졌는데 할 일이 없는 것이다 — 1차 캐시는 식별자를 키로 갖는 Map이라 id 없이는 영속 상태를 만들 수 없고, IDENTITY는 DB가 INSERT를 실행해야 id를 준다. 그래서 persist()가 즉시 INSERT를 날리고 쓰기 지연 저장소가 비어 있다. (같은 이유로 영속성 컨텍스트가 없는 JdbcTemplate은 같은 auto_increment에서도 잘 묶인다.)
  • 3
    처방은 "버릴까 말까"가 아니라 순서다 — ① ID 전략 → ② batch_size + order_inserts → ③ flush() + clear() → ④ JdbcTemplate / COPY. 각 단계에서 측정하고 충분하면 멈춘다. 그리고 드라이버 재작성 옵션과 청크 커밋 + 멱등성까지 붙여야 배치로서 완성된다.

0. 질문 + 출제 의도 · 하나의 예제

질문: "대량 데이터 INSERT 시 JPA의 한계와 JDBC batch로 우회하는 방법(IDENTITY 전략의 문제 포함)을 설명해주세요."

출제 의도: "JPA로 짰더니 100만 건에 2시간"이라는, 실무에서 반드시 한 번은 만나는 상황이다. 원인(건별 INSERT, IDENTITY의 batch 무력화)을 알고 우회로를 설계할 수 있는지를 본다. 더 깊게는 ORM의 한계를 인정하고 내려갈 줄 아는 유연함 — ORM을 신봉해 끝까지 붙들지도 않고, 조금 느리다고 곧장 던져버리지도 않는 균형 감각을 확인하는 질문이다.

함정은 세 갈래다 ① 느린 이유를 한 갈래만 본다. "쿼리가 100만 번 나가서"는 절반이다. 나머지 절반인 영속성 컨텍스트 누적을 말하지 못하면 "왜 앞의 10만 건은 3분인데 뒤의 10만 건은 40분인가"를 설명할 수 없다.
② 처방이 JPQL로 샌다. "JPQL 벌크로 바꾸겠다"는 JPQL에 INSERT가 없다는 사실 하나로 무너진다(2절).
③ JPA 안에서 조여가는 단계가 통째로 비어 있다. IDENTITY가 문제라는 걸 알면서 곧장 "그럼 JPA를 버리겠다"로 점프하는 것 — 가장 흔하고, 가장 아쉬운 감점이다. 실무자는 그 사이에 카드를 세 장 더 갖고 있다(4절).
이 문서는 하나의 예제를 끝까지 끌고 간다 외부 정산 시스템에서 받아온 하루치 거래 100만 건을 우리 DB에 적재하는 배치다. 그리고 DB는 PostgreSQL을 기준으로 쓴다 — 이 문항은 드라이버와 DB 벤더에 따라 동작이 실제로 갈리는 자리가 많아서, 벤더가 다르면 그때마다 "MySQL은 이렇다"고 명시한다. "DB는 대체로 이렇다"는 식의 서술이 이 문항에서 가장 위험하다.
예제 엔티티 문제의 한 줄이 여기 있다
@Entity
@Table(name = "settlement")
public class Settlement {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)  3절의 전부
    private Long id;

    private LocalDate      settlementDate;  // 정산일자
    private String         txId;            // 외부 거래 ID
    private BigDecimal     amount;          // 금액
    private Long           merchantId;      // 가맹점
    private LocalDateTime  createdAt;
}
문제의 코드 100만 건에 2시간
@Transactional
public void load(List<SettlementDto> dtos) {   // size == 1_000_000
    for (SettlementDto dto : dtos) {
        settlementRepository.save(Settlement.from(dto));
    }
}

// 여기서 실제로 벌어지는 일 두 가지
//  ① save() 1회 = SQL 1문장 = 왕복 1회      → 100만 왕복
//  ② 저장한 엔티티가 트랜잭션 끝까지 상자에 남는다
//     → 엔티티 100만 + 스냅샷 100만이 힙에 살아 있다

1. 왜 2시간인가 — 원인은 두 갈래다

첫 답변에서 "쿼리가 100만 번 나가서"까지만 말하고 멈추는 것이 이 문항의 가장 흔한 모습이다. 진단이 틀린 건 아니지만 절반이고, 나머지 절반을 놓치면 처방도 절반만 나온다 — 배치만 켜고 flush/clear를 빼먹는다.

3초 암기 — 두 갈래는 왕 · 누

왕복 100만 번→일정하게 느리다→처방: 묶어 보낸다 (batch)
누적 (엔티티+스냅샷)→갈수록 느려진다→처방: 주기적으로 비운다 (clear)

한 갈래만 말하면 처방도 한 개만 나온다. 이 문항에서 실점의 절반이 여기서 발생한다.

1-1. 누적 비용을 숫자로 — clear()가 하는 일은 "메모리 절약"이 아니다

"뒤로 갈수록 느려진다"를 감으로만 말하면 잘 와닿지 않는다. 1,000건마다 flush()만 하고 clear()를 빼먹으면 매 회차의 비교 대상이 1,000건씩 늘어난다. 100만 건에 그대로 계산해 보자.

이 갈래를 놓치는 것이 왜 아까운가 — "아는 개념을 새 상황에 옮겨 붙이기" 조회 전용 DTO 프로젝션 문항에서는 "1차 캐시에 적재하는 행위 자체가 비용"이라고 정확히 말할 수 있는 사람이, 대량 INSERT 상황에서는 같은 축을 떠올리지 못하는 경우가 많다. 개념을 모르는 것이 아니라, 개념이 붙는 상황의 목록이 좁은 것이다. 그래서 기억해야 할 것은 사실이 아니라 트리거다.
"엔티티를 루프에서 대량으로 다룬다"는 말이 나오면 반사적으로 영속성 컨텍스트 누적을 의심한다
읽기든 쓰기든 똑같다 — 읽기는 DTO 프로젝션으로 애초에 안 올리고, 쓰기는 flush + clear로 비운다

2. 첫 처방이 헛나가는 세 자리 — JPQL · saveAll() · 벌크 연산

진단을 마치면 처방으로 넘어가는데, 여기서 세 갈래로 새는 답이 정해져 있다. 셋 다 "벌크"라는 단어에 끌려간 결과이고, 셋 다 왕복 횟수를 1도 줄이지 못한다.

여기서 말하면 그 자리에서 끝나는 세 문장

"JPQL 벌크 INSERT로"
JPQL에 INSERT 문이 없다. 지원하는 벌크 연산은 UPDATE와 DELETE 둘뿐이고, 예외는 하이버네이트 HQL의 insert into … select 하나다.
"saveAll() 로 바꾸면"
내부는 결국 리스트를 순회하며 save()를 부른다. 이름이 복수형이라고 SQL이 하나가 되지 않는다. 왕복 횟수는 그대로다.
"@Modifying 벌크 연산으로"
그건 다른 문항의 도구다. 대상이 이미 DB에 있는 행이고 문제도 컨텍스트 불일치다. 이 문항의 대상은 아직 DB에 없는 데이터다.

2-1. JPQL에 INSERT가 없는 이유까지 말한다

용어부터. JPQL(Java Persistence Query Language)은 테이블이 아니라 엔티티를 대상으로 쓰는 질의 언어다. select s from Settlement s where s.amount > 1000처럼 클래스 이름과 필드 이름으로 쓰고, 하이버네이트가 그걸 실제 SQL로 번역한다. 이 사실 하나를 모르면 면접에서 첫 처방이 통째로 무효가 된다.

없다 파싱 단계에서 실패한다
// 존재하지 않는 문법
em.createQuery(
  "insert into Settlement (settlementDate, txId, amount) " +
  "values (?1, ?2, ?3)");

// 왜 없는가 ─ 단순 암기가 아니라는 신호가 되는 지점
//  JPQL은 "이미 DB에 존재하는 엔티티"를 대상으로 한다.
//  UPDATE·DELETE는 where 로 대상을 지정할 수 있지만,
//  INSERT는 대상이 DB가 아니라 애플리케이션 메모리에 있다.
//  값을 SQL 문자열로 옮기는 것은 질의가 아니라 "직렬화"이므로
//  JPA는 그 역할을 persist() 에 맡긴다.
예외 하나 HQL의 insert into … select
-- 이건 된다: 출처가 "이미 DB에 있는 행"이라 질의로 표현 가능
insert into Settlement (settlementDate, txId, amount)
select s.settlementDate, s.txId, s.amount
from StagingSettlement s where ...

-- 그런데 이 예외가 오늘 문제를 풀어주지는 않는다.
-- 우리 데이터는 외부에서 받아온 것이라 아직 DB 어디에도 없다.
-- 다만 4-5에서 되살아난다 →
--   ① 벌크 적재 명령으로 스테이징 테이블에 통째로 밀어 넣고
--   ② 거기서 insert … select 로 정제해 본 테이블로 옮긴다
가산점 연결 "JPQL에 INSERT가 없다"에서 멈추지 말고 "단, 스테이징 테이블을 두면 insert … select가 설계로 되살아난다"까지 이어 말하면, 제약을 외운 사람이 아니라 제약을 우회 설계로 바꿔본 사람으로 읽힌다.

2-2. @Modifying 벌크 연산과 축이 정반대다

같은 "벌크"라는 단어를 쓰지만 대상도 문제도 처방도 반대다
벌크 UPDATE/DELETE (@Modifying)대량 INSERT (이 문항)
대상이미 DB에 있는 행아직 DB에 없는 새 데이터
영속성 컨텍스트우회한다 → 불일치가 문제통과한다 → 누적이 문제
핵심 처방실행 후 clear() (또는 순서 조정)배치 묶기 + 주기적 flush/clear

2-3. saveAll()이 답이 아닌 이유, 그리고 진짜 스위치

"루프 대신 saveAll(list)을 쓰면 되지 않나"는 자연스러운 발상이지만, saveAll() 내부는 결국 리스트를 순회하며 save()를 부르는 것이다. 여러 건을 한 문장으로 묶는 일은 saveAll()이 아니라 JDBC 배치 계층이 한다.

JDBC 배치(batch)가 무엇인가 — 한 번 짚고 간다 JDBC에는 PreparedStatement.addBatch()로 파라미터 세트를 여러 벌 쌓아 두었다가 executeBatch() 한 번으로 몰아 보내는 API가 있다. 하이버네이트는 hibernate.jdbc.batch_size를 보고 이 API를 쓴다. 그런데 그 스위치를 켜도 IDENTITY면 아무 일도 일어나지 않는다. 다음 절이 그 이야기다.

3. IDENTITY가 배치를 무력화하는 메커니즘

이 문항에서 가장 중요한 지점이고, "auto_increment라 INSERT 전엔 id를 알 수 없어서"라고 답할 수 있으면 절반은 통과다. 나머지 절반은 "그래서 무슨 일이 연쇄적으로 일어나는가"다.

1
1차 캐시는 식별자를 키로 갖는 Map이다. 영속성 컨텍스트의 1차 캐시는 개념적으로 @Id 값 → 엔티티 인스턴스의 Map 하나다. 같은 트랜잭션에서 같은 id를 두 번 조회하면 같은 인스턴스가 돌아오는 것(동일성 보장)이 이 구조 때문이다. Map이므로 키가 없는 항목은 넣을 수 없다.
2
그래서 id 없이는 엔티티를 영속 상태로 만들 수 없다. persist()의 계약은 "이 엔티티를 관리 대상으로 만든다"이고, 관리 대상이 된다는 것은 곧 1차 캐시에 들어간다는 뜻이다. 키가 정해지기 전에는 그 일이 물리적으로 불가능하다.
3
IDENTITY는 DB가 INSERT를 실행해야 id를 준다. 키 생성을 DB의 자동 증가 컬럼에 맡긴다는 뜻이다(PostgreSQL의 GENERATED … AS IDENTITY·serial, MySQL의 auto_increment). 그 값은 INSERT 문이 실제로 실행되는 순간에야 정해진다.
4
따라서 persist()가 그 자리에서 INSERT를 날려야 한다. ②가 요구하는 키를 얻을 유일한 방법이 ③의 INSERT이므로, 하이버네이트는 persist() 시점에 INSERT를 보내고 getGeneratedKeys로 id를 받아온다. 그 결과 쓰기 지연(write-behind)이 성립하지 않는다 — 쌓아 둘 것이 애초에 생기지 않는다.
배치는 "쌓인 것을 묶어 보내는" 기술인데 쌓인 것이 없으니 할 일이 없다
batch_size가 안 켜진 것이 아니라, 켜져 있는데 묶을 것이 없는 것 — 이 구분이 "설정을 외운 사람"과 "동작을 아는 사람"을 가른다

3-1. 로그로 확인하는 장면 — 켰는데 아무 변화가 없다

# batch_size 를 켰다
spring.jpa.properties.hibernate:
  show_sql: true
  jdbc:
    batch_size: 1000

# 그런데 로그는 전혀 달라지지 않는다
Hibernate: insert into settlement (...) values (?,?,?,?,?)
Hibernate: insert into settlement (...) values (?,?,?,?,?)
... (100만 줄, 소요 시간도 그대로)

주의: 이 로그만으로 "배치가 안 됐다"고 단정하면 안 된다. show_sql은 배치 여부를 보여주는 도구가 아니다 — 배치가 잘 될 때도 문장은 한 줄씩 찍힌다(5절). 여기서 증거는 "로그 줄 수"가 아니라 "소요 시간이 그대로"다.

3-2. 그럼 JdbcTemplate은 왜 같은 auto_increment에서 잘 묶이나

테이블은 그대로 자동 증가 컬럼인데 JdbcTemplate.batchUpdate는 잘 묶인다. 왜 JPA에서 문제였던 것이 여기서는 문제가 안 되는가 —

JDBC에는 영속성 컨텍스트가 없기 때문이다

JPA가 id를 필요로 했던 이유는 DB에 넣기 위해서가 아니라 1차 캐시에 넣기 위해서였다(①②). JDBC는 애초에 캐시할 대상이 없으므로 id를 몰라도 아무 지장이 없다. 값만 addBatch로 쌓았다가 executeBatch로 한 번에 보내면 되고, id는 DB가 알아서 채운다.

이 설명까지 붙일 수 있으면 "우회로를 아는 것"이 아니라 "우회로가 통하는 이유를 아는 것"이 된다 — 암기와 이해가 갈리는 지점이다.

비유로 한 번 더 — 사물함과 번호표

IDENTITY
1차 캐시는 번호가 붙은 사물함이고, 물건을 넣으려면 번호가 먼저 있어야 한다. 그런데 번호는 물건을 DB 창구에 맡겨야만 발급된다 → 한 개 넣을 때마다 창구까지 다녀와야 한다.
SEQUENCE + allocationSize
창구에서 번호표 1000장 묶음을 미리 받아온다. 그다음부터는 자리에서 번호를 매기고, 물건은 수레에 모아 두었다가 한 번에 창구로 민다. 창구 방문이 1/1000이 된다.

4. 처방 — JPA를 버리는 것이 아니라 순서대로 조인다

핵심은 "JPA를 버릴까 말까"의 이분법이 아니라 순서다. 아래 네 단계는 위험도와 포기하는 것이 순서대로 커진다. 실무자는 위에서부터 하나씩 열어보고, 효과가 충분한 지점에서 멈춘다.

순서 암기 — 아 · 배 · 비 · 내

아이디 전략→배치 묶기→비우기(flush+clear)→내려가기(JdbcTemplate·COPY)

순서를 바꾸면 앞 단계가 무효가 된다 — ID 전략을 안 고치고 batch_size만 켜면 아무 일도 일어나지 않고, clear() 없이 배치만 켜면 뒤로 갈수록 느려지는 곡선이 그대로 남는다.

4-1. ① ID 전략 교체 — 채번을 미리 받아와 INSERT를 미룬다

3절에서 확인한 대로 막힌 것은 배치가 아니라 쓰기 지연이다. 그러니 첫 카드는 "INSERT 전에 id를 알 수 있게 만드는 것"이다. PostgreSQL이라면 SEQUENCE가 정답이다 — 진짜 시퀀스 오브젝트가 있어서 nextval로 INSERT 없이 번호를 받아올 수 있다.

Before persist() 마다 즉시 INSERT
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

// 쓰기 지연 불가 → 묶을 대상이 없다
After (PostgreSQL) 채번 1회로 1000개 선점
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE,
                generator = "settlement_seq")
@SequenceGenerator(
        name = "settlement_seq",
        sequenceName = "settlement_seq",  // DB에 실제로 만들 이름
        allocationSize = 1000)             한 번에 1000개 선점
private Long id;
반드시 함께 DB 시퀀스의 증가폭을 allocationSize와 맞춘다
create sequence settlement_seq start with 1 increment by 1000;

-- 맞추지 않으면 애플리케이션이 아예 안 뜬다 (Hibernate 6.6 메시지)
--   The increment size of the [settlement_seq] sequence is set to [1000]
--   in the entity mapping while the associated database sequence
--   increment size is [1].
이 예외는 고마운 예외다 allocationSize가 1보다 크면 하이버네이트는 pooled 최적화기를 쓰는데, 이 방식은 시퀀스가 한 번에 allocationSize만큼 건너뛴다는 것을 전제로 구간을 계산한다. 그래서 기동 시점에 실제 DB 시퀀스의 증가폭을 조회해 매핑값과 비교하고, 다르면 예외를 던진다(기본 정책 hibernate.id.sequence.increment_size_mismatch_strategy = EXCEPTION). 조용히 넘어갔다면 두 인스턴스가 같은 id를 발급해 PK 충돌이 났을 것이다.
MySQL은 사정이 다르다 — 벤더를 뭉뚱그리지 않는다 MySQL에는 시퀀스 오브젝트가 없다. 그래서 GenerationType.SEQUENCE를 지정해도 하이버네이트는 테이블 기반 제너레이터로 대체한다(6.6의 SequenceStyleGenerator가 방언에 시퀀스 지원 여부를 물어보고, 없으면 테이블 구조로 만든다). 결과적으로 MySQL에서는 TABLE 제너레이터를 명시적으로 쓰는 것이 동작과 의도가 일치해 혼란이 적다. (AUTO는 하이버네이트 버전과 설정에 따라 매핑이 달라질 수 있으므로 배치 성능이 걸린 자리에서는 전략을 명시한다.) 
// After (MySQL): TABLE 제너레이터 + 큰 allocationSize
@Id
@GeneratedValue(strategy = GenerationType.TABLE, generator = "settlement_seq")
@TableGenerator(name = "settlement_seq", table = "id_sequences",
                pkColumnName = "seq_name", valueColumnName = "next_val",
                pkColumnValue = "settlement", allocationSize = 1000)
private Long id;
이 단계가 못 해결하는 것 — 반드시 같은 호흡에 말할 것 · id에 구멍이 생긴다. 재시작하면 선점 구간의 남은 번호는 버려진다. PK는 연속일 필요가 없으므로 대개 문제가 아니지만, id를 업무 일련번호로 노출하고 있다면 문제가 된다.
· 채번 지점이 경합 지점이 된다. 여러 인스턴스가 동시에 채번하면 그 지점에 경합이 생긴다. MySQL의 TABLE 제너레이터는 채번 테이블의 행에 락이 걸리므로 특히 그렇다. allocationSize가 크면 방문 횟수가 적어 경합도 줄지만, allocationSize가 1이면 오히려 병목이다. (PostgreSQL 시퀀스는 트랜잭션 밖에서 원자적으로 증가하므로 락 경합은 훨씬 덜하다.)
· 기존 테이블의 마이그레이션이 필요하다. 이미 자동 증가 컬럼으로 운영 중이라면 시퀀스·채번 테이블의 시작값을 현재 최대 id보다 크게 잡아야 한다. "코드 한 줄 바꾸면 끝"이 아니다.
· 왕복 횟수 자체는 아직 그대로다. 이 단계는 묶을 수 있는 상태를 만든 것일 뿐이고, 실제로 묶는 건 ②다.

4-2. ② batch_size + order_inserts / order_updates

Before 쓰기 지연은 되지만 한 문장씩
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 0
After 묶어 보낸다 + 묶일 수 있게 정렬한다
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 1000
        order_inserts: true   # 기본값 false
        order_updates: true   # 기본값 false

order_inserts가 왜 필요한가. JDBC 배치는 "연속된 같은 SQL 문장"만 묶는다. 쓰기 지연 저장소에 Settlement → Merchant → Settlement → Merchant처럼 섞여 있으면, 문장이 바뀔 때마다 배치가 끊겨 크기 1짜리 배치가 줄줄이 만들어진다. order_inserts는 flush 직전에 같은 엔티티끼리 모아 배치가 실제로 묶이게 한다.

정확히 말하면 하이버네이트 6.6의 정렬기(ActionQueue.InsertActionSorter)는 엔티티 이름으로 그룹을 만들고, 연관관계로 인한 선후 의존을 지키면서 그룹 단위로 스케줄한다. 단순히 이름순으로 줄 세우는 것이 아니라 "부모를 먼저, 자식을 나중에"라는 제약을 지키면서 묶는 것이라, 순환 참조가 있으면 정렬에 실패했다는 경고를 남기고 그대로 내보낸다.

"묶기 스위치를 켰는데 왜 안 빨라지지"의 원인 세 개를 순서대로 나열할 수 있으면 실제로 겪어본 사람으로 읽힌다
① IDENTITY (3절) → ② order_inserts 누락 (4-2) → ③ 드라이버 재작성 옵션 (5절)

4-3. "켰는데 왜 안 묶이나" 체크리스트

hibernate.jdbc.batch_size는 켠다고 항상 묶이는 스위치가 아니다. 하이버네이트 6.6은 여러 조건을 확인해서 하나라도 걸리면 조용히 배치를 포기하고 건별 실행으로 되돌아간다. 예외도 경고도 없다. 그래서 아래를 위에서부터 확인하는 것이 빠르다.

위 3개는 빈도순, 4~7번은 하이버네이트가 "배치 키 없음"을 돌려주는 조건이다
#원인확인 방법처방
1ID 전략이 IDENTITY엔티티의 @GeneratedValueSEQUENCE(PostgreSQL) / TABLE(MySQL)로 교체 (4-1)
2여러 엔티티가 섞여 배치가 끊김p6spy/datasource-proxy에서 배치 크기가 1로 찍힘hibernate.order_inserts=true, order_updates=true (4-2)
3드라이버가 도로 풀어서 보냄서버 측 쿼리 로그PostgreSQL reWriteBatchedInserts=true / MySQL rewriteBatchedStatements=true (5절)
4@DynamicInsert / @DynamicUpdate가 붙어 있음엔티티 클래스 애너테이션매번 SQL 문장이 달라지므로 배치 불가 — 배치 경로에서는 뗀다
5@OptimisticLocking(type = ALL 또는 DIRTY)엔티티 클래스 애너테이션where 절이 행마다 달라져 배치 불가 — @Version 방식으로
6트랜잭션 없이 실행 중@Transactional 유무배치는 트랜잭션이 열려 있어야 성립한다
7@Version 엔티티인데 배치를 껐음hibernate.jdbc.batch_versioned_data6.x 기본값은 true이므로 대개 문제 없다. 명시적으로 false로 꺼두지 않았는지만 본다
8flush() 없이 트랜잭션 끝까지 감힙 사용량 곡선묶이기는 하지만 힙이 터진다 — flush() + clear() (4-4)
4번과 5번이 왜 배치를 막는지는 한 문장으로 설명된다 JDBC 배치는 "SQL 문자열은 같고 파라미터만 다른" 경우에만 성립한다. @DynamicInsert는 null이 아닌 컬럼만 골라 INSERT를 만들므로 행마다 문장이 달라지고, ALL/DIRTY 방식의 낙관적 락은 where 절에 이전 값들을 나열하므로 역시 행마다 달라진다. 문장이 달라지면 묶을 수가 없다. (4~7번은 AbstractMutationCoordinator.resolveBatchKeyAccess() 한 곳에서 판정되고, "배치 키 없음"을 돌려주는 순간 배치 경로가 통째로 닫힌다.)

4-4. ③ 배치 크기마다 flush() + clear()

Before 트랜잭션 끝까지 100만 개가 힙에 남는다
@Transactional
public void load(List<SettlementDto> dtos) {
    for (SettlementDto dto : dtos) {
        settlementRepository.save(Settlement.from(dto));
    }
}
// 힙: 엔티티 100만 + 스냅샷 100만
// flush 대조량: 5억 500만 건 (1-1의 붉은 곡선)
After batch_size 와 같은 주기로 내보내고 비운다
@PersistenceContext private EntityManager em;

@Transactional
public void load(List<SettlementDto> dtos) {
    int batchSize = 1000;   hibernate.jdbc.batch_size 와 맞춘다
    for (int i = 0; i < dtos.size(); i++) {
        em.persist(Settlement.from(dtos.get(i)));

        if ((i + 1) % batchSize == 0) {
            em.flush();   // 쌓인 INSERT 1000건을 배치로 내보낸다
            em.clear();   // 1차 캐시 + 스냅샷을 비운다 → 힙이 평평해진다
        }
    }
    em.flush(); em.clear();   // 1000의 배수가 아닌 꼬리
}

둘은 역할이 다르고 둘 다 필요하다 — 가장 흔한 반쪽 처방

flush()
쌓인 SQL을 DB로 내보낸다. 이게 없으면 트랜잭션 끝에 100만 건이 한꺼번에 몰린다.
clear()
영속성 컨텍스트를 비운다. flush()만 하면 SQL은 나가지만 엔티티는 그대로 남아 힙 문제도, 전건 대조 문제도 전혀 해결되지 않는다. 1-1의 500.5배가 정확히 이 차이다.
그리고 flush()는 커밋이 아니다 — SQL을 보낸 것일 뿐이라 롤백하면 전부 사라진다
100만 건이 여전히 한 트랜잭션에 묶여 있다는 사실은 그대로다 → 6절

batchSize를 hibernate.jdbc.batch_size와 맞추는 이유는 단순하다. 주기가 어긋나면 flush 시점에 쌓인 개수가 배치 크기와 맞지 않아 자투리 배치가 계속 생긴다.

이 단계가 새로 만드는 위험 — clear()는 컨텍스트를 통째로 비운다 같은 트랜잭션에서 다루던 다른 엔티티들도 함께 준영속(detached)이 된다. 준영속이란 "한때 관리 대상이었지만 지금은 상자 밖으로 나온 상태"다. 루프 안에서 조회해 둔 가맹점 엔티티를 clear() 뒤에 만지면 지연 로딩이 터지거나 변경 감지가 사라진다. → 배치 로직은 다른 엔티티 조작과 섞지 않는 것이 안전하고, 꼭 필요하면 clear() 이후 id로 다시 조회한다. (7절 꼬리질문에서 자세히)

4-5. ④ 그래도 부족하면 — JdbcTemplate.batchUpdate / COPY / LOAD DATA INFILE

①~③으로 대개 충분하지만, 엔티티 매핑 자체가 무거운 경우(연관관계가 많다, 컨버터가 여럿이다, 리스너가 붙어 있다)에는 건당 객체 생성·매핑 비용이 남는다. 이때 비로소 아래로 내려간다.

Before JPA — 건마다 엔티티 + 컨텍스트 통과 비용
for (SettlementDto dto : dtos)
    em.persist(Settlement.from(dto));
After JdbcTemplate — 값만 보낸다
private static final String SQL = """
        insert into settlement (settlement_date, tx_id, amount,
                                merchant_id, created_at)
        values (?, ?, ?, ?, ?)
        """;

public void load(List<SettlementDto> dtos) {
    for (List<SettlementDto> chunk : Lists.partition(dtos, 1000)) {
        jdbcTemplate.batchUpdate(SQL, chunk, chunk.size(), (ps, dto) -> {
            ps.setObject(1, dto.settlementDate());
            ps.setString(2, dto.txId());
            ps.setBigDecimal(3, dto.amount());
            ps.setLong(4, dto.merchantId());
            ps.setObject(5, LocalDateTime.now());  Auditing 이 안 붙으므로 직접
        });
    }
}

벌크 적재 명령은 한 단계 더 아래다

데이터를 파일이나 스트림으로 만들어 DB가 직접 읽게 하는 방식으로, INSERT 문 파싱조차 건너뛰므로 가장 빠르다.

  • PostgreSQL — COPY: COPY settlement (…) FROM STDIN (FORMAT csv). JDBC에서는 드라이버의 CopyManager로 스트림을 그대로 밀어 넣을 수 있어 중간 파일 없이도 된다.
  • MySQL — LOAD DATA INFILE: 파일을 만들어 서버(또는 클라이언트)에서 읽게 한다. 서버 설정(로컬 파일 읽기 허용)이 열려 있어야 하고, 파일을 만들고 옮길 경로가 필요하다.

두 방식 모두 애플리케이션 코드에서 SQL로 표현되지 않아 추적이 어렵다는 대가가 있다.

두 경로를 절충하는 좋은 설계 가산점

2-1에서 예고한 insert … select가 여기서 되살아난다.

① 벌크 적재 명령→스테이징 테이블→② insert … select→본 테이블

가장 무거운 구간(파일 → DB)은 DB에게 맡기고, 변환 로직은 SQL로 남겨 검증할 수 있게 된다. "JPQL에 INSERT가 없다"는 제약이 설계로 우회되는 지점이라, 이 연결을 말하면 제약을 외운 사람과 설계해본 사람이 갈린다.

4-6. 종합 — 각 단계가 무엇을 해결하고 무엇을 못 해결하는가

단계해결하는 것못 해결하는 것포기하는 것
① ID 전략 교체쓰기 지연이 성립 → 묶을 대상이 생긴다왕복 횟수, 힙 누적id 연속성, 마이그레이션 비용
② batch_size + order_inserts하이버네이트 층의 왕복 횟수힙 누적, 드라이버 단 전송(5절)실패 지점 특정이 어려워짐
③ flush() + clear()힙 누적, 전건 대조 폭증트랜잭션 크기(6절)컨텍스트 통째 비움의 부작용
④ JdbcTemplate / COPY매핑·객체 생성 비용(성능은 끝, 이제 정합성이 과제)Auditing·검증·타입 안전성(6-4)

5. 드라이버 층과 관측의 3층 — 로그가 정상인데 안 빨라지는 자리

①~③을 다 하고도 시간이 기대만큼 줄지 않는 일이 흔하다. 원인은 하이버네이트 아래 한 층, JDBC 드라이버에 있다. 하이버네이트가 성실히 묶어서 넘겨도, 그것을 실제로 어떻게 전송할지는 드라이버가 정한다.

전송에서 줄일 수 있는 비용은 둘이고, 벤더가 이 둘을 다르게 처리한다

① 네트워크 왕복
문장 하나 보내고 응답을 기다리기를 반복할 것인가, 몰아서 한 번에 보낼 것인가.
② 서버 측 실행 횟수
서버가 문장을 100만 번 실행할 것인가, values (…),(…),(…) 형태의 multi-values 한 문장으로 합쳐 적게 실행할 것인가.
Before 옵션 없는 JDBC URL
# PostgreSQL
jdbc:postgresql://host:5432/settlement?...

# MySQL
jdbc:mysql://host:3306/settlement?...
After 철자가 서로 다르다 — 그대로 외운다
# PostgreSQL — 드라이버 기본값은 false
jdbc:postgresql://host:5432/settlement?reWriteBatchedInserts=true&...

# MySQL
jdbc:mysql://host:3306/settlement?rewriteBatchedStatements=true&...

이 두 이름은 헷갈리라고 만든 것 같은 이름이다 — 갈라 외우는 장치

reWriteBatchedInserts
PostgreSQL · W가 대문자이고 대상이 Inserts(INSERT만). "PG는 W를 크게 쓴다, 그리고 INSERT만 다시 쓴다"
rewriteBatchedStatements
MySQL · 전부 소문자이고 대상이 Statements(문장 일반). "MySQL은 소문자로, 문장 전부를 다시 쓴다"

둘 다 URL에서 한 글자만 빠져도 조용히 사라지는 설정이고, 사라져도 애플리케이션은 정상 동작하고 배치만 느려진다.

5-1. 무엇으로 확인하나 — 관측의 3층

show_sql이나 org.hibernate.SQL 로그는 하이버네이트가 만든 문장을 찍는다. JDBC 드라이버가 그 아래에서 무엇을 어떻게 보냈는지는 찍지 않는다. 관측 도구가 문제 지점을 덮지 못하면 아무리 열심히 봐도 안 보인다.

5-2. 이 성질을 코드로 고정하기

재작성 옵션은 URL에서 한 글자만 빠져도 조용히 사라지는 설정이다. 누군가 DataSource 설정을 정리하다 옵션을 지워도 애플리케이션은 정상 동작하고 배치만 느려진다 — 즉 테스트로 잡지 않으면 언젠가 반드시 되돌아온다.

After 로그로 확인되지 않는 것을 테스트로 붙잡는다
@Test
void 정산_적재는_배치로_묶여_나간다() {
    SQLStatementCountValidator.reset();

    loader.load(fixture(1_000));                     // 1000건 적재

    // 건별 INSERT 라면 1000이 된다. 배치가 살아 있으면 그보다 훨씬 작아야 한다.
    SQLStatementCountValidator.assertInsertCount(1);
}

@Test
void JDBC_URL에_배치_재작성_옵션이_켜져있다() {
    // 로그로는 확인할 수 없는 설정이라, 존재 자체를 단정해 붙잡아 둔다.
    assertThat(dataSourceUrl()).contains("reWriteBatchedInserts=true");
}
두 번째 테스트는 우스워 보이지만 유일한 장치다 그리고 여기서 DB는 실제 PostgreSQL이어야 한다 — H2로는 드라이버 동작도, 배치 재작성도 검증되지 않으므로 Testcontainers를 쓴다.
"문제를 만나면 잘 푼다"와 "문제가 오기 전에 잡는 장치를 만든다"는 다른 능력이다
증상이 '조금 느림'뿐이고 로그에는 아무 흔적도 남지 않는 이 자리에서 그 차이가 가장 선명하다

6. 성능이 잡힌 뒤에 남는 것 — 트랜잭션 · 멱등성 · 대가

①~④로 시간을 줄였다고 이 문항이 끝나는 게 아니다. 남는 것이 셋이다. 트랜잭션을 어떻게 쪼갤 것인가, 아래로 내려가면서 무엇을 포기했는가, 그리고 "차라리 id를 밖에서 받아오면 되지 않느냐"는 흔한 반문을 어떻게 정리할 것인가.

6-1. 100만 건을 트랜잭션 하나로 묶지 않는다

Before 실패 시 전부 소멸
@Transactional
public void load(List<SettlementDto> dtos) { ... }
// 100만 건이 트랜잭션 하나
After 청크마다 독립 트랜잭션 — 성공한 청크는 남는다
public void load(List<SettlementDto> dtos) {
    for (List<SettlementDto> chunk : Lists.partition(dtos, 1_000)) {
        chunkLoader.loadChunk(chunk);   별도 빈이어야 한다
    }
}

@Transactional                       // 트랜잭션 경계가 청크가 된다
public void loadChunk(List<SettlementDto> chunk) {
    for (SettlementDto dto : chunk) em.persist(Settlement.from(dto));
    // 메서드 종료 = flush + commit. clear 는 컨텍스트가 닫히며 함께 정리된다
}
주의 — 같은 클래스 메서드를 부르면 트랜잭션이 아예 안 걸린다 (self-invocation) @Transactional은 그 메서드의 코드를 바꾸는 것이 아니라 빈을 감싼 프록시가 트랜잭션을 열고 닫는 구조이고, this.loadChunk(...)는 그 프록시를 건너뛴다. 청크 로더를 별도 빈으로 분리해야 한다. 이 실수는 "느려진다"가 아니라 "청크 커밋이 통째로 사라진다"로 나타나서 더 위험하다.
Spring Batch를 쓰면 이 구조가 기본값이다 chunk(1000)으로 읽기·처리·쓰기를 묶고 청크마다 커밋하며, 어디까지 처리했는지를 JobRepository가 기록해 실패 지점부터 재시작할 수 있다. "배치 프레임워크가 실제로 해주는 일"은 이렇게 설명하면 좋다 —
청크 커밋재시작 지점 관리실패 건 격리(skip/retry)

6-2. 멱등성 — 재실행 가능해야 진짜 배치다

용어부터. 멱등성(idempotency)은 "같은 작업을 여러 번 해도 결과가 한 번 한 것과 같은 성질"이다. 배치에서 이게 왜 필요하냐면, 청크 커밋을 하는 순간 "어디까지 들어갔는지 모르는 상태에서 다시 돌리는 상황"이 생기기 때문이다.

전제 자연 키에 유니크 제약을 건다
-- 같은 정산일자의 같은 거래는 한 번만
alter table settlement
  add constraint uk_settlement_date_tx unique (settlement_date, tx_id);
PostgreSQL 재실행해도 안전한 적재
insert into settlement (settlement_date, tx_id, amount,
                        merchant_id, created_at)
values (?, ?, ?, ?, ?)
on conflict (settlement_date, tx_id) do nothing;

-- on conflict (컬럼) 은 그 조합에 유니크 인덱스가
-- 실제로 있어야만 동작한다 → 구문 자체가 제약을 전제로 성립
MySQL 같은 목적의 구문
insert into settlement (settlement_date, tx_id, amount,
                        merchant_id, created_at)
values (?, ?, ?, ?, ?)
on duplicate key update tx_id = tx_id;  -- no-op upsert

-- "어느 제약에서 충돌했는지"를 지정할 수 없다 →
-- 유니크 인덱스가 여럿이면 의도치 않은 제약에서의 충돌을
-- 성공으로 오인할 수 있다
MySQL의 INSERT IGNORE가 더 짧지만 권하지 않는다 중복뿐 아니라 데이터 잘림이나 타입 변환 실패까지 경고로 낮춰 조용히 통과시키기 때문이다. 배치는 사람이 안 보는 새벽에 도는 코드라, 조용히 잘못된 데이터를 넣는 것이 실패보다 훨씬 나쁘다.

세 가지가 한 줄로 연결된다 — 성능 질문에 운영 감각으로 답하는 지점

유니크 제약→upsert→재실행 가능

중복을 DB가 막는다 → 중복이 예외가 아니라 정상 흐름이 된다 → 어디서 끊겨도 그냥 다시 돌리면 된다.

6-3. 내려갈 때 포기하는 것 — "한계를 인정한다"는 "대가 없이 내려간다"가 아니다

이 문항이 보는 것은 "ORM의 한계를 인정하고 내려갈 줄 아는 유연함"인데, 여기서 자주 생기는 오해가 있다. 유연함은 "쉽게 버리는 것"이 아니라 "무엇을 내려놓는지 알고 버리는 것"이다.

④로 내려가면 함께 잃는 다섯 가지

  • JPA Auditing이 안 붙는다. @CreatedDate·@LastModifiedDate·@CreatedBy는 엔티티 생명주기 이벤트에 걸린 기능이라 SQL을 직접 쓰면 전혀 동작하지 않는다. created_at이 통째로 null인 100만 행이 남는 사고가 여기서 나온다.
  • 엔티티의 검증·도메인 로직을 우회한다. 생성자의 금액 부호 검사, 상태 초기화, @PrePersist 훅이 전부 건너뛰어진다 → "엔티티를 거치면 절대 만들 수 없는 데이터"가 테이블에 들어갈 수 있다.
  • 영속성 컨텍스트와 어긋난다. 같은 트랜잭션에서 JPA로 조회한 데이터가 있다면, JDBC로 밀어 넣은 행은 그 컨텍스트에 없다. @Version도 증가하지 않고, 2차 캐시가 낡은 상태로 남는다.
  • 타입 안전성을 잃는다. ps.setString(2, …)의 인덱스가 컬럼 순서와 어긋나도 컴파일은 통과한다. 컬럼을 하나 추가하는 순간 조용히 밀린다.
  • 테스트 방식이 달라진다. @DataJpaTest의 롤백에 기대던 방식이 통하지 않고, 벤더 종속 SQL이라 H2로는 검증되지 않는다 → Testcontainers가 사실상 필수.

균형점은 전면 교체가 아니라 경계 좁히기

대량 적재 경로만 SettlementBulkWriter 같은 별도 클래스로 격리하고 나머지는 JPA를 유지한다. 그 클래스 안에서만 위 다섯 가지를 신경 쓰면 되고, 위험이 코드베이스 전체로 번지지 않는다.

방어 장치도 짝지어 둔다.

6-4. "차라리 id를 밖에서 받아오면 되지 않느냐" — 외부 채번과 UUID

외부 채번(Redis INCR · 스노우플레이크)이 정당한 경우

DB가 아니라 별도 시스템이 번호를 발급하는 방식이다 — Redis INCR로 카운터를 올리거나, 스노우플레이크처럼 시각 + 장비 번호 + 순번을 비트로 조합해 64비트 정수를 만든다.

  • DB를 샤딩했다. 샤드마다 자동 증가를 돌리면 충돌하거나 범위를 쪼개 관리해야 한다 → 전역 유일 id 발급기가 요구사항 자체다.
  • DB에 넣기 전에 id가 필요하다. 이벤트를 먼저 발행하거나, 여러 저장소에 같은 식별자로 기록해야 하는 경우.
  • id로 규모를 추정당하면 곤란하다. 자동 증가 값은 연속이라 노출하면 건수가 드러난다 → 성능이 아니라 보안 요구사항.

정당하지 않은 경우 — "이 배치 하나가 느려서"

  • 가용성이 결합된다. Redis가 죽으면 채번이 막혀 배치가 못 돈다. 원래 DB만 있으면 되던 일에 장애 지점이 하나 늘어난다.
  • 운영 대상이 늘어난다. 모니터링·백업·업그레이드·장애 대응이 따라 붙는다 — 배치 하나의 성능이 인프라 팀의 상시 부담으로 바뀌는 것은 비싼 거래다.
  • 정합성 사고의 복구가 어렵다. 리셋이나 페일오버로 카운터가 되감기면 중복 id가 발급된다. 다른 테이블에서 이미 그 id를 참조했다면 데이터 정정이 필요해진다.
  • 무엇보다 SEQUENCE/TABLE + allocationSize가 같은 문제를 인프라 추가 없이 푼다. 인프라를 늘리지 않고 되는 일을 늘려서 하는 것은 설계에서 감점 요인이다.

"UUID를 쓰면 채번 왕복이 없으니 최고 아닌가요" 가산점

UUID는 128비트(16바이트) 난수 기반 식별자라 채번 왕복이 아예 없다 — 애플리케이션이 혼자 만들어 낸다. 문제는 무작위라는 성질이 인덱스에 나쁘다는 것이고, 나쁜 방식이 벤더마다 다르다.

MySQL(InnoDB) — 테이블 자체가 흔들린다
PK 순서로 데이터를 물리 정렬해 저장하는 클러스터드 인덱스 구조라서, 무작위 값이 PK가 되면 새 행이 인덱스 중간중간에 끼어들어 페이지 분할이 잦아진다. 대량 적재에서 특히 비싸다.
PostgreSQL — 테이블이 아니라 인덱스가 흔들린다
테이블은 힙 구조라 새 행이 그냥 뒤에 붙는다. 대신 PK B-트리 삽입 지점이 전 구간에 흩어져 캐시 적중률이 떨어지고 더티 페이지와 WAL 기록이 늘어난다. "PostgreSQL은 힙이라 괜찮다"는 절반만 맞는 말.

정렬 가능한 형태(시간 순서가 앞에 오는 UUID 변형이나 스노우플레이크 계열)를 쓰면 양쪽 모두 완화되지만, PK 폭이 8바이트에서 16바이트로 커져 모든 보조 인덱스가 함께 커진다는 대가는 남는다.

한 문장으로 — 외부 채번은 분산 ID가 요구사항일 때의 답이지, 배치가 느릴 때의 답은 아니다

7. 인출 카드 · 꼬리질문 셀프 테스트

7-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

100만 건이 2시간인 이유 두 갈래?
왕 · 누 — 왕복 100만 번(일정하게 느림) / 영속성 컨텍스트 누적(갈수록 느림). 한 갈래만 말하면 처방도 한 개만 나온다.
IDENTITY 연쇄 한 문장?
키를 DB만 안다 → 키 없이는 1차 캐시(Map)에 못 넣는다 → persist()가 즉시 INSERT → 쓰기 지연 저장소가 빈다 → 묶을 대상 자체가 없다.
처방 순서 4단계?
아 · 배 · 비 · 내 — 아이디 전략 → 배치(batch_size+order_inserts) → 비우기(flush+clear) → 내려가기(JdbcTemplate/COPY).
첫 처방이 새는 세 자리?
JPQL 벌크 INSERT(문법 자체가 없다) · saveAll()(내부는 루프) · @Modifying 벌크(대상이 이미 DB에 있는 행이라 다른 문항).
clear()가 하는 일?
"메모리 절약"이 아니라 "곡선을 직선으로 만드는 것". flush()만 하면 SQL은 나가지만 엔티티는 그대로 남는다 → 500.5배 차이.
누적 대조량의 형태?
건수 n의 n²에 비례(정확히는 n(n+k)/2k). 건수 2배 → 비용 4배. 그래서 테스트 1만 건에서는 안 보인다.
"켰는데 안 묶임" 상위 3원인?
① IDENTITY ② order_inserts 누락(배치 크기 1) ③ 드라이버 재작성 옵션. 그 다음이 @DynamicInsert · ALL/DIRTY 락 · 트랜잭션 부재.
배치가 성립하는 조건 한 줄?
"SQL 문자열은 같고 파라미터만 다를 것." 문장이 행마다 달라지면(@DynamicInsert, ALL/DIRTY 락) 묶을 수가 없다.
reWriteBatchedInserts
PostgreSQL · W가 대문자, 대상은 Inserts. 왕복은 이미 파이프라이닝으로 줄어 있고, 이 옵션은 서버 실행 횟수를 줄인다.
rewriteBatchedStatements
MySQL · 전부 소문자, 대상은 Statements. 없으면 드라이버가 배치를 도로 풀어 하나씩 보낸다 → 사실상 필수.
관측 3층과 담당 문제?
Statistics(문장 수 → IDENTITY) → p6spy(배치 크기 → order_inserts) → 서버 로그(실제 문장 → 재작성 옵션). 층을 내려가야만 보이는 문제가 있다.
show_sql로 판단하면 안 되는 이유?
배치가 잘 될 때도 문장은 한 줄씩 찍힌다. 근거는 로그 줄 수가 아니라 실행 시간과 Statistics 카운트여야 한다.
배치 설계 한 세트?
청크 커밋 + 유니크 제약 + upsert. 청크 커밋을 하는 순간 "어디까지 들어갔는지 모름"이 생기므로 멱등성과 한 세트다.
④로 내려가며 포기하는 것?
Auditing · 엔티티 검증 · 컨텍스트 정합성 · 타입 안전성 · 테스트 방식. 그래서 답은 전면 교체가 아니라 배치 전용 클래스로 경계 좁히기.

7-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

왜 앞의 10만 건은 3분인데 뒤의 10만 건은 40분인가요? 필수힌트: 왕복 비용만이라면 속도가 일정해야 한다. 그럼 무엇이 달라졌나

범인은 왕복이 아니라 영속성 컨텍스트 누적이다. 왕복 비용은 건당 일정하므로 그것만으로는 뒤로 갈수록 느려질 수 없다.

메커니즘은 둘이다. ① flush 한 번의 비용이 커진다 — flush는 관리 중인 엔티티 전건 × 전 필드를 스냅샷과 대조해 SQL을 만든다. 50만 건째의 flush는 그 순간 50만 개를 훑는다. ② 힙이 밀린다 — 엔티티 100만 + 스냅샷 100만이 강한 참조로 붙들려 GC가 회수하지 못하므로 Full GC가 반복되고, 운이 나쁘면 OutOfMemoryError로 2시간 뒤에 끝난다.

그래서 1,000건마다 flush()만 하고 clear()를 빼면 누적 대조량이 5억 500만 건, clear()까지 하면 100만 건 — 500.5배다.

원인은 "힙이 부족한 것"이 아니라 "컨텍스트를 안 비운 것"이다
그래서 힙을 키우는 처방은 시간을 벌 뿐 n² 곡선의 모양을 바꾸지 못한다
그럼 JPQL로 벌크 INSERT를 쓰면 한 방에 끝나지 않나요? 함정힌트: 있는지부터 확인한다. 그리고 "왜 없는지"까지 말한다

그런 문법이 없다. JPQL이 지원하는 벌크 연산은 UPDATE와 DELETE 둘뿐이고, INSERT 구문은 파싱 단계에서 실패한다.

왜 없는지까지 말하면 단순 암기가 아니라는 신호가 된다. JPQL은 이미 DB에 존재하는 엔티티를 대상으로 하는 질의 언어다. UPDATE·DELETE는 where로 대상을 지정할 수 있지만, INSERT는 대상이 DB가 아니라 애플리케이션 메모리에 있다. 값을 SQL 문자열로 옮기는 순간 그건 질의가 아니라 직렬화이므로, JPA는 그 역할을 persist()에 맡긴다.

예외는 하나 — 하이버네이트 HQL의 insert into … select다. 출처가 "이미 DB에 있는 행"이므로 질의로 표현 가능하기 때문이다. 다만 우리 데이터는 외부에서 받아온 것이라 아직 DB 어디에도 없어서 오늘 문제를 풀어주지는 않는다.

여기서 한 걸음 더 — 벌크 적재 명령으로 스테이징 테이블에 통째로 밀어 넣고
insert … select로 정제해 본 테이블로 옮기면 이 예외가 설계로 되살아난다 가산점
saveAll()로 바꾸면 SQL이 하나로 합쳐지지 않나요?힌트: 이름과 동작을 분리해서 본다

합쳐지지 않는다. saveAll() 내부는 리스트를 순회하며 save()를 부르는 것이라 왕복 횟수가 그대로다. 이름이 복수형이라고 SQL이 하나가 되지는 않는다.

여러 건을 한 문장으로 묶는 일은 saveAll()이 아니라 JDBC 배치 계층이 한다 — PreparedStatement.addBatch()로 파라미터 세트를 쌓아 두었다가 executeBatch()로 몰아 보내는 API이고, 하이버네이트는 hibernate.jdbc.batch_size를 보고 이 API를 쓴다.

다만 그 스위치를 켜도 IDENTITY면 아무 일도 일어나지 않는다는 것이 이 문항의 본론이다.

batch_size를 켰는데 로그에 insert가 100만 줄 그대로입니다. 무엇부터 보시겠어요? 필수힌트: 순서에 이유가 있다. 그리고 "로그 100만 줄"이라는 근거 자체를 의심한다

세 가지를 순서대로 확인한다.

1
ID 생성 전략 — IDENTITY면 여기서 끝이다. 배치가 안 켜진 게 아니라 묶을 대상이 없는 것이므로 다른 걸 아무리 봐도 소용없다.
2
order_inserts — 여러 종류의 엔티티를 함께 저장한다면 문장이 섞여 배치가 잘게 끊긴다. p6spy에서 배치 크기가 1로 찍히는지 본다.
3
JDBC URL의 재작성 옵션 — PostgreSQL reWriteBatchedInserts, MySQL rewriteBatchedStatements. 하이버네이트 로그로는 확인되지 않으므로 서버 측 로그나 p6spy/datasource-proxy로 층을 내려가야 한다.

여기까지 다 봤는데도 안 묶이면 4-3의 체크리스트로 넘어간다 — @DynamicInsert가 붙어 있거나, 낙관적 락이 ALL/DIRTY거나, 트랜잭션이 없는 경로였거나. 하이버네이트가 예외 없이 조용히 배치를 포기하는 자리라서, 알고 있지 않으면 찾는 데 오래 걸린다.

추가로 짚을 것 — "로그에 100만 줄"이라는 관측 자체가 근거로는 약하다
show_sql은 배치 여부를 보여주는 도구가 아니라서 배치가 잘 될 때도 문장은 한 줄씩 찍힌다. 판단 근거는 실행 시간과 Statistics 카운트여야 한다
SEQUENCE/TABLE로 바꾸면 id에 구멍이 생기는데 괜찮나요?힌트: "괜찮다"로 끝내지 말고 "안 괜찮은 경우"를 특정한다

대개 괜찮고, 안 괜찮은 경우가 언제인지 아는 것이 핵심이다. allocationSize만큼 미리 선점하므로 재시작하면 남은 번호가 버려진다 — id가 1000, 1001, … 1523, 2001, …처럼 뛴다.

  • PK는 유일하기만 하면 되므로 기술적으로는 문제가 없다. 조인·인덱스·조회 성능 어디에도 영향이 없다.
  • 문제가 되는 경우는 id를 업무적으로 해석할 때다. "id로 건수를 센다", "id 순서가 곧 접수 순서다", "고객에게 보여주는 번호다" 같은 사용이 있으면 곤란해진다. 그런 요구가 있다면 PK와 별도로 업무 번호 컬럼을 두는 것이 정석이다 — 기술 식별자와 업무 식별자를 겸용하던 것이 애초의 문제이기 때문이다.
  • 정산 배치의 자연 키는 어차피 (정산일자, 거래ID)다. PK가 무엇이든 업무적 동일성은 그 조합이 판단하므로 구멍은 무해하다.

같이 말할 것: DB 시퀀스의 increment by를 allocationSize와 맞추지 않으면 기동 시점에 예외로 막힌다. 이건 고마운 예외다 — 안 막아주면 두 인스턴스가 같은 id를 발급해 PK 충돌이 난다.

그럼 allocationSize를 10만으로 올리면 더 빨라지나요? 한계는 어디죠? 시니어 변별힌트: 효과와 대가가 같은 속도로 커지지 않는다

효과는 금방 포화하고, 대가는 계속 커진다.

채번 왕복은 건수 / allocationSize이므로 1 → 1000에서 이미 1/1000이 된다(100만 → 1000회). 1000 → 10만으로 더 올려봐야 줄어드는 왕복은 1000번에서 10번으로, 전체 소요 시간에서 차지하는 비중이 이미 무의미한 수준이다.

최적화는 지배적인 비용에 해야 하는데, 이 지점에서 지배적인 비용은 더 이상 채번이 아니다

반면 대가는 커진다.

  • 재시작마다 버려지는 구간이 커진다. 매일 배포하는 서비스라면 id가 빠르게 소진되고, int 범위를 쓰고 있었다면 한계 도달 시점이 앞당겨진다.
  • 여러 인스턴스의 구간이 크게 엇갈린다. 정렬성이 나빠져 인덱스 삽입 지역성이 떨어질 수 있다.
  • 채번 지점의 경합은 이미 해결된 상태라 더 얻을 것이 없다.

여기서 진짜 보고 싶은 것은 숫자가 아니라 판단 방식이다 — "어느 비용이 지배적인지 측정하고, 지배적인 것만 건드린다." ①~③을 다 하고 나면 지배적인 비용은 대개 DB 측의 인덱스 유지와 로그 기록으로 옮겨가 있고, 그때부터는 애플리케이션 설정이 아니라 적재 중 보조 인덱스를 잠시 떼고 나중에 붙이는 것 같은 DB 작업이 다음 카드가 된다.

batch_size는 클수록 좋은 것 아닌가요? 10,000으로 잡으면?힌트: 실패했을 때 무슨 일이 생기는지도 함께 본다

크게 잡을수록 이기는 값이 아니다. 이유가 셋이다.

  • 패킷이 커진다. 한 번에 보내는 양이 커져 DB의 최대 패킷 크기 제한에 걸릴 수 있다. 특히 드라이버 재작성으로 multi-values 한 문장이 되면 더 그렇다.
  • 실패 지점을 좁히기 어려워진다. 배치 하나가 실패했을 때 어느 건이 문제인지 알아내는 비용이 커진다.
  • 재작성 상한에 부딪힌다. PostgreSQL은 확장 질의 프로토콜에서 65,535 / 행당 파라미터 수를 넘을 수 없고(컬럼 5개면 13,107 → 2의 거듭제곱으로 내려 8,192행), 32,768행 상한도 있다. 그 위로 올린 숫자는 그냥 안 쓰인다.

수백~수천 사이에서 측정해 정하는 값이고, flush()/clear() 주기를 같은 값으로 맞춰 자투리 배치를 없애는 것이 함께 가야 한다.

flush()/clear()를 넣었더니 이번엔 엉뚱한 곳에서 예외가 납니다. 왜죠? 필수힌트: clear()의 사정거리를 생각한다. 그리고 예외조차 안 나는 경우가 더 위험하다

clear()가 영속성 컨텍스트를 통째로 비우기 때문이다. 배치와 무관하게 그 트랜잭션에서 다루던 엔티티들도 함께 준영속(detached)이 된다.

  • 지연 로딩이 터진다. clear() 이전에 조회해 둔 가맹점 엔티티의 연관을 이후에 건드리면 LazyInitializationException.
  • 변경 감지가 사라진다. clear() 전에 수정해 둔 값이 flush 대상에서 빠져 UPDATE가 조용히 사라진다. 예외조차 안 나서 더 위험하다.
  • 동일성이 깨진다. clear() 후 같은 id를 다시 조회하면 다른 인스턴스가 나온다. == 비교에 의존한 코드가 조용히 오동작한다.

처방은 둘이다. ① 배치 로직을 다른 엔티티 조작과 섞지 않는다 — 청크 로더는 "DTO를 받아 엔티티를 만들어 저장한다"만 하게 한다. ② 꼭 참조가 필요하면 엔티티를 들고 다니지 말고 id(또는 값 객체)를 들고 다니다가 필요한 시점에 다시 조회한다.

이 성질은 벌크 연산의 clearAutomatically가 만드는 부작용과 정확히 같은 것이다(11-bulk-operation-persistence-context.md).

청크 커밋으로 바꿨는데 실패해도 여전히 전부 롤백됩니다. 왜죠? 함정힌트: @Transactional이 어떻게 동작하는지로 돌아간다

같은 클래스의 메서드를 호출해서 프록시를 타지 않았을 가능성이 가장 높다(self-invocation).

@Transactional은 그 메서드의 코드를 바꾸는 것이 아니라, 빈을 감싼 프록시가 트랜잭션을 열고 닫는 구조다. 그래서 this.loadChunk(...)처럼 내부에서 직접 부르면 프록시를 건너뛰어 트랜잭션 경계가 아예 만들어지지 않는다. 그러면 바깥 load()의 트랜잭션(있다면)에 그대로 참여하므로 청크 커밋이 통째로 사라진다.

처방은 청크 로더를 별도 빈으로 분리하는 것이다. 그리고 이 실수는 "느려진다"가 아니라 "설계가 사라진다"로 나타나기 때문에 로그만 봐서는 눈치채기 어렵다 — 중간에 강제로 실패시키고 앞의 청크가 남는지 확인하는 테스트로 고정해 두는 편이 안전하다.

Spring Batch를 쓰면 이 구조가 기본값이라는 점도 함께 말하면 좋다 — chunk(1000) + JobRepository의 재시작 지점 관리 + 실패 건 격리(skip/retry)가 프레임워크가 실제로 해주는 일이다.

청크 커밋을 하면 중간에 끊겼을 때 중복 적재가 나지 않나요? 필수힌트: 이 질문의 답은 "조심한다"가 아니라 "DB가 막게 만든다"이다

그래서 청크 커밋과 멱등성은 한 세트다. 청크 커밋을 하는 순간 "어디까지 들어갔는지 모르는 상태에서 다시 돌리는 상황"이 반드시 생긴다.

설계는 세 단계로 연결된다.

① 자연 키에 유니크 제약
(정산일자, 거래ID)→② upsert
on conflict do nothing→③ 재실행 가능
그냥 다시 돌리면 된다

벤더 차이도 짚는다. PostgreSQL의 on conflict (컬럼)은 그 조합에 유니크 인덱스가 실제로 있어야만 동작하므로 구문 자체가 제약을 전제한다. MySQL은 "어느 제약에서 충돌했는지"를 지정할 수 없어서 유니크 인덱스가 여럿인 테이블에서는 의도하지 않은 제약에서의 충돌을 성공으로 오인할 수 있다.

그리고 INSERT IGNORE는 피한다 — 중복뿐 아니라 데이터 잘림·타입 변환 실패까지 경고로 낮춰 조용히 통과시킨다. 배치는 사람이 안 보는 새벽에 도는 코드라, 조용히 잘못된 데이터를 넣는 것이 실패보다 훨씬 나쁘다.

JdbcTemplate으로 내려가면 정말 끝인가요? 그래도 느리면요? 시니어 변별힌트: 튜닝 대상이 어디로 이동했는지를 먼저 말한다

아니다. 그 지점에서 병목은 애플리케이션을 떠나 DB로 이동해 있다. 여기서부터 튜닝 대상이 바뀐다는 것을 아는지가 변별점이다.

  • 인덱스 유지 비용이 지배적이 된다(행마다 모든 보조 인덱스를 갱신). 그래서 적재 전에 보조 인덱스를 떼고 적재 후 다시 만드는 전략을 쓴다 — 다만 그 사이 해당 테이블의 조회 성능이 무너지므로 신규 테이블이거나 적재 중 조회가 없는 배치 윈도우에서만 가능하다.
  • PK 순서가 중요해진다. 정렬된 순서로 넣으면 인덱스 삽입 지역성이 좋아지고, MySQL이면 페이지 분할도 줄어든다. 입력 데이터를 PK 기준으로 정렬해서 넣는 것만으로 개선되는 경우가 있다.
  • 벌크 적재 명령이 다음 카드다. PostgreSQL COPY, MySQL LOAD DATA INFILE은 INSERT 문 파싱 자체를 건너뛴다.
  • 트랜잭션 로그·복제 지연도 본다. 대량 적재는 WAL(또는 binlog) 생성량을 급증시켜 복제 지연을 만들고 읽기 replica를 보는 서비스에 영향을 준다. 그래서 배치 윈도우를 나누거나 속도를 일부러 제한(throttling)하기도 한다.
"가장 빠른 것"이 아니라 "다른 트래픽을 안 죽이는 선에서 충분히 빠른 것"이 배치의 목표
그리고 DB 층의 카드들은 대부분 다른 사용자에게 영향을 주는 결정이라 혼자 정할 수 없다
이 배치가 몇 달 뒤 다시 느려지는 것을 어떻게 막나요? 가산점힌트: 이 문항의 성능은 대부분 "설정"으로 얻은 것이다. 설정은 어떻게 사라지나

설정으로 얻은 성능은 설정이 지워지면 사라지고, 그 사실은 로그에 남지 않는다. 그래서 세 가지를 코드로 고정한다.

1
쿼리 수 단정 테스트 — SQLStatementCountValidator.assertInsertCount(…)나 Statistics.getPrepareStatementCount()로 1000건 적재 시 문장 수가 임계 이하임을 단정한다. 누군가 ID 전략을 IDENTITY로 되돌리면 테스트가 즉시 실패한다.
2
설정 존재 자체를 단정 — JDBC URL의 재작성 옵션, hibernate.jdbc.batch_size, order_inserts 값을 검사한다. 우스운 테스트지만 로그로 확인할 수 없는 설정을 잡는 유일한 장치다.
3
실제 DB로 검증 — H2에서는 배치 재작성도, 벤더 특유의 동작도 재현되지 않는다. Testcontainers로 실제 PostgreSQL을 띄운다.

여기에 운영 관측을 하나 더 붙이면 완성이다 — 배치 잡의 처리 건수와 소요 시간을 매 실행 기록하고, 임계치를 넘으면 알림. 성능 회귀는 어느 날 갑자기가 아니라 서서히 오기 때문에, 추세를 보는 지표가 없으면 "원래 이렇게 오래 걸렸나?"로 넘어간다.

이 문항에서 배울 수 있는 가장 이식성 높은 교훈
주장으로 남긴 설계 원칙은 언젠가 지워지고, 테스트로 고정한 원칙만 살아남는다
Redis INCR나 스노우플레이크로 id를 미리 받아오면 더 깔끔하지 않나요? 함정힌트: "안 된다"가 아니라 "언제 정당한가"로 답한다

분명히 유효한 선택지다. 다만 이 문항의 답으로는 순서가 뒤바뀐 선택이라, "언제 정당한가"를 구분하는 것이 핵심이다.

정당한 경우 — 분산 ID가 실제로 요구사항일 때. ① DB를 샤딩했다(전역 유일 id 발급기가 요구사항 자체다) ② DB에 넣기 전에 id가 필요하다(이벤트 선발행, 여러 저장소에 같은 식별자로 기록) ③ id로 규모를 추정당하면 곤란하다(성능이 아니라 보안 요구사항).

정당하지 않은 경우 — "이 배치 하나가 느려서". ① 가용성이 결합된다(Redis가 죽으면 채번이 막혀 배치가 못 돈다 — 장애 지점이 하나 늘어난다) ② 운영 대상이 늘어난다(배치 하나의 성능이 인프라 팀의 상시 부담으로 바뀐다) ③ 페일오버로 카운터가 되감기면 중복 id가 발급된다.

SEQUENCE/TABLE + allocationSize가 같은 문제를 인프라 추가 없이 푼다
인프라를 늘리지 않고 되는 일을 늘려서 하는 것은 설계에서 감점 요인이다
UUID를 PK로 쓰면 채번 왕복이 아예 없으니 제일 빠르지 않나요? 시니어 변별힌트: 채번은 사라지지만 다른 비용이 생긴다. 그리고 그 비용의 위치가 벤더마다 다르다

채번 왕복은 사라지지만, 무작위라는 성질이 인덱스에 나쁘다. 그리고 나쁜 방식이 벤더마다 다르다는 것까지 말하면 변별이 된다.

MySQL(InnoDB) — 테이블 자체가 흔들린다. PK 순서로 데이터를 물리 정렬해 저장하는 클러스터드 인덱스 구조라서, 무작위 값이 PK가 되면 새 행이 인덱스 중간중간에 끼어들어 페이지 분할이 잦아진다. 대량 적재에서 이 비용이 특히 크다.

PostgreSQL — 테이블이 아니라 인덱스가 흔들린다. 테이블은 힙 구조라 새 행이 그냥 뒤에 붙으므로 테이블 자체에는 이 문제가 없다. 대신 PK B-트리 인덱스의 삽입 지점이 전 구간에 흩어져 캐시 적중률이 떨어지고 더티 페이지와 WAL 기록이 늘어난다. "PostgreSQL은 힙이라 괜찮다"는 절반만 맞는 말이다.

정렬 가능한 형태(시간 순서가 앞에 오는 UUID 변형이나 스노우플레이크 계열)를 쓰면 양쪽 모두 완화되지만, PK 폭이 8바이트에서 16바이트로 커져 모든 보조 인덱스가 함께 커진다는 대가는 남는다.

그럼 대량 INSERT는 처음부터 JdbcTemplate으로 짜는 게 낫지 않나요? 시니어 변별힌트: 질문의 전제("성능만 보면 된다")를 먼저 거부한다

"내려가는 것"과 "대가 없이 내려가는 것"은 다르다. JdbcTemplate이나 벌크 적재 명령으로 가면 다섯 가지를 함께 잃는다 — JPA Auditing(created_at이 통째로 null인 100만 행이 여기서 나온다), 엔티티 검증·@PrePersist("엔티티를 거치면 절대 만들 수 없는 데이터"가 들어갈 수 있다), 영속성 컨텍스트 정합성(@Version이 안 오르고 2차 캐시가 낡는다), 타입 안전성(ps.setString(2, …)의 인덱스가 밀려도 컴파일은 통과한다), 테스트 방식(H2로는 검증되지 않아 Testcontainers가 필수가 된다).

그래서 실무의 균형점은 "전면 교체"가 아니라 "경계 좁히기"다. 대량 적재 경로만 SettlementBulkWriter 같은 별도 클래스로 격리하고 나머지는 JPA를 유지한다 — 그 클래스 안에서만 다섯 가지를 신경 쓰면 되고, 위험이 코드베이스 전체로 번지지 않는다.

그리고 대개는 ①~③으로 충분하다. ④가 필요한 것은 엔티티 매핑 자체가 무거운 경우(연관관계가 많다, 컨버터가 여럿이다, 리스너가 붙어 있다)이지, "JPA라서"가 아니다.

100만 건이 2시간인 이유는 두 갈래 — 왕복 100만 번과 영속성 컨텍스트에 엔티티·스냅샷 100만 벌이 누적되어 뒤로 갈수록 느려지는 것(1,000건마다 flush()만 하고 clear()를 빼면 누적 대조량 5억 500만 건, clear()까지 하면 100만 건 — 500.5배이고 이 곡선은 건수의 제곱으로 자란다). 첫 처방으로 "JPQL 벌크 INSERT"는 성립하지 않고(JPQL에 INSERT 문이 없다, insert into … select 제외), saveAll()도 내부는 루프다. batch_size를 켜도 IDENTITY면 한 건도 묶이지 않는다 — 1차 캐시가 식별자를 키로 갖는 Map이라 id 없이는 영속 상태를 만들 수 없고, IDENTITY는 DB가 INSERT를 실행해야 id를 주므로 persist()가 즉시 INSERT를 날려 쓰기 지연 자체가 성립하지 않기 때문이다(같은 이유로 영속성 컨텍스트가 없는 JdbcTemplate은 같은 auto_increment에서도 잘 묶인다). 처방은 JPA를 버리는 것이 아니라 순서대로 조이는 것 — ① ID 전략을 SEQUENCE/TABLE + 큰 allocationSize(시퀀스 increment by를 안 맞추면 기동 시점에 예외) ② batch_size + order_inserts로 같은 엔티티끼리 모아 실제로 묶고 ③ 배치 크기마다 flush() + clear()로 힙과 전건 대조를 잘라내고 ④ 그래도 부족하면 JdbcTemplate.batchUpdate / COPY / LOAD DATA INFILE. 그래도 안 묶이면 @DynamicInsert·ALL/DIRTY 낙관적 락·트랜잭션 부재를 의심한다 — 하이버네이트가 예외 없이 조용히 배치를 포기하는 조건들이다. 드라이버 층도 반드시 본다 — PostgreSQL은 파이프라이닝으로 왕복이 이미 줄어 있고 reWriteBatchedInserts=true가 서버 실행 횟수를 줄이며, MySQL은 rewriteBatchedStatements=true가 없으면 드라이버가 문장을 하나씩 보낸다. 그리고 이건 하이버네이트 로그로는 절대 확인되지 않으므로 Statistics → p6spy → 서버 측 로그로 관측의 층을 내려가야 한다. 성능이 잡혀도 설계가 남는다 — 100만 건을 트랜잭션 하나로 묶지 않고(죽은 행 회수 지연·락 보유·전량 롤백), 청크 단위 커밋 + (정산일자, 거래ID) 유니크 키 기반 upsert로 재실행 가능하게 만든다. 아래로 내려가는 데에는 대가가 있다 — Auditing 미적용, 엔티티 검증 우회, 컨텍스트 불일치, 타입 안전성 상실, 테스트 방식 변경. 그래서 실무의 답은 전면 교체가 아니라 배치 전용 클래스로 경계를 좁히고, 그 경계를 테스트로 고정하는 것이다.
