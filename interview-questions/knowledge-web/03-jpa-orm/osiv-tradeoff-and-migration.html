3. JPA / ORM

OSIV 트레이드오프와 전환 — 트랜잭션 경계와 영속성 컨텍스트 경계는 다른 것이다

📖 약 33분 🧩 7개 섹션 0/7 섹션 이해
🎯 핵심 관전 포인트

먼저 정의를 한 문장으로 못 박는다 — spring.jpa.open-in-view는 Spring Boot 기본값 true이고, 트랜잭션은 서비스 메서드에서 끝나도 EntityManager(영속성 컨텍스트)는 HTTP 응답이 완료될 때까지 열어둔다. 즉 트랜잭션 경계와 영속성 컨텍스트 경계는 별개이며, OSIV는 둘을 일부러 어긋나게 만드는 장치다. 그래서 컨트롤러·JSON 직렬화 단계의 지연 로딩이 통과한다. 켰을 때의 대가를 "커넥션을 오래 잡는다"고 말하면 절반만 맞다. 정확한 표현은 "아무 일도 하지 않는 커넥션을 잡는다" 이다 — 컨트롤러·응답 단계에 외부 API 호출 같은 느린 I/O가 있으면 그 시간 내내 DB 커넥션이 놀면서 점유된다. 풀 20개에 300ms 외부 호출이면 이론 처리량이 400 req/s에서 54 req/s로 무너지고, 외부 시스템의 지연이 우리 DB 커넥션 풀을 타고 전파된다. 껐을 때의 의미는 불편이 아니라 설계 강제다 — "엔티티는 트랜잭션 밖으로 나가지 않는다"를 프레임워크가 강제하고, 그래서 fetch join과 DTO 변환을 명시적으로 쓰게 된다. 마지막이 이 문항의 진짜 관문이다: 3년치 코드에서 어디가 터질지는 정적 검색으로 절대 보장할 수 없다(Jackson 직렬화·toString()·프록시 경유는 게터 호출이 코드에 없다). 보장하는 방법은 두 개다 — open-in-view=false로 프로파일만 바꿔 기존 컨트롤러 통합 테스트를 통째로 한 번 더 돌려 예외를 배포 전에 표면화시키고, ArchUnit으로 "컨트롤러 반환 타입에 엔티티 금지"를 못 박아 재발을 차단한다. 그리고 순서가 중요하다 — 끄는 것은 마지막이다. ① DTO 경계 수립 → ② 서비스 트랜잭션 안에서 변환 완료 → ③ 그때 끈다.

면접 질문

"OSIV(Open Session In View)를 켰을 때와 껐을 때의 트레이드오프는? 대용량 트래픽 서비스에서는 어떻게 설정하겠습니까?"

출제 의도rationale은 이렇게 적고 있다 — "기본값(켜짐)이 커넥션을 뷰 렌더링까지 물고 있게 한다는 사실은 대용량 트래픽에서 커넥션 고갈의 숨은 원인이다. 프레임워크 기본값을 의심해본 적 있는지를 본다." 즉 채점 지점은 OSIV의 정의 암기가 아니라 ① 기본값이 왜 그렇게 정해졌는지를 해석할 수 있는가 ② 그 기본값이 우리 서비스의 트래픽 특성과 맞는지 판단할 수 있는가 ③ 이미 그 기본값 위에 쌓인 코드를 안전하게 되돌릴 수 있는가다.

함정 두 개:

  • "트레이드오프"를 물었는데 한쪽만 말하는 것. "커넥션을 오래 잡으니 끈다"까지만 말하면 절반이다. 끄면 무엇을 잃는지, 그리고 그럼에도 왜 기본값이 true인지를 같이 말해야 트레이드오프 서술이 성립한다.
  • "어떻게 설정하겠습니까"를 설정값 한 줄로 답하는 것. false는 결론이지 답이 아니다. 이 질문의 실질은 이미 돌아가는 서비스에서 그 한 줄을 어떻게 안전하게 바꾸느냐다. 면접관이 시나리오 꼬리질문("3년치 코드 중 어디가 터질지 어떻게 찾겠나")을 붙이는 이유가 이것이다.
1

정의를 한 문장으로 고정한다

▾

먼저 외울 한 문장.

💡

OSIV(spring.jpa.open-in-view)는 Spring Boot 기본값 true이며, 트랜잭션이 서비스에서 끝난 뒤에도 EntityManager(영속성 컨텍스트)를 HTTP 응답 완료 시점까지 열어둔다.

이 한 문장에 이 문항의 절반이 들어 있다. 나머지 절반은 여기서 자동으로 따라 나온다 — 열어둔다는 것은 뭔가를 계속 붙잡고 있다는 뜻이고, 그 뭔가가 DB 커넥션이다.

1-1. 이름을 뜯어보면 정의가 나온다

  • Open — 연다
  • Session — Hibernate 용어로 세션, JPA 표준 용어로는 EntityManager. 영속성 컨텍스트(1차 캐시 + 변경 감지 스냅샷)를 담고 있는 객체다.
  • In View — 뷰(화면) 렌더링 시점까지

합치면 "세션을 뷰 렌더링 시점까지 열어둔다" 다. JSP·Thymeleaf 같은 서버 사이드 렌더링 시절에 붙은 이름이라 "View"라고 되어 있지만, JSON API에서는 Jackson이 응답을 직렬화하는 시점이 그 자리를 대신한다.

1-2. 두 개의 경계가 다르다 — 그림으로 고정

이 문항에서 가장 흔한 오해가 "트랜잭션 = 영속성 컨텍스트"다. 둘은 보통 같이 시작하고 같이 끝나지만, 반드시 그런 것은 아니다. OSIV는 정확히 그 어긋남을 만드는 장치다.

text
시간 ─────────────────────────────────────────────────────────────────────▶

  요청 수신 ── 컨트롤러 ── 서비스(@Transactional) ── 컨트롤러 ── JSON 직렬화 ── 응답 완료
      │           │        │                   │        │           │           │
TX    ·           ·        ■■■■■■■■■■■■■■■■■■■■■        ·           ·           ·
      │           │        └── 커밋 ───────────┘        │           │           │
      │           │                                     │           │           │
EM    ·           ·        ■■■■■■■■■■■■■■■■■■■■■        ·           ·           ·   ← OSIV = false
      │           │                                     │           │           │
EM    ■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■■   ← OSIV = true
  • TX = 트랜잭션 경계. @Transactional이 붙은 서비스 메서드 구간. OSIV 설정과 무관하게 이 구간은 변하지 않는다.
  • EM = EntityManager(영속성 컨텍스트) 수명.
  • false면 두 막대가 겹친다. 서비스 메서드가 끝나는 순간 세션도 닫히므로, 컨트롤러로 넘어온 엔티티의 지연 로딩은 LazyInitializationException이다.
  • true면 아래 막대가 요청 전체로 늘어난다. 트랜잭션은 이미 커밋됐는데 세션은 살아 있다. 그래서 컨트롤러와 직렬화 단계의 지연 로딩이 통과한다.

이 그림이 LazyInitializationException의 원인을 "트랜잭션이 끝나서"가 아니라 "세션이 닫혀서" 라고 말해야 하는 이유이기도 하다. 트랜잭션이 끝났는데도 지연 로딩이 되는 상태가 실재하고, 그게 Spring Boot의 기본값이다.

1-3. 누가 그 일을 하는가

Spring이 OpenEntityManagerInViewInterceptor(또는 필터)를 웹 요청 앞단에 걸어둔다. 동작은 단순하다.

text
요청 시작 → EntityManager 생성해서 현재 스레드에 바인딩
             ↓
           (컨트롤러 → 서비스 → @Transactional 은 "이미 바인딩된" EM 을 그대로 씀)
             ↓
응답 완료 → 바인딩 해제하고 EntityManager close()

핵심은 "@Transactional이 EntityManager를 새로 만들지 않고, 이미 열려 있는 것에 참여한다" 는 점이다. 그래서 트랜잭션이 끝나도 세션은 안 닫힌다 — 세션을 연 주체가 트랜잭션이 아니라 인터셉터이기 때문이다. 이걸 말할 수 있으면 "왜 트랜잭션이 끝났는데 세션이 살아 있나"라는 꼬리질문이 통째로 해결된다. (가산점 포인트)

1-4. 코드로 보는 차이

java
// 서비스 — 두 경우 모두 코드가 동일하다. 설정만 다르다.
@Transactional(readOnly = true)
public Order findOrder(Long id) {
    return orderRepository.findById(id).orElseThrow();
}   // ← 트랜잭션 종료. OSIV=false 면 EntityManager 도 여기서 닫힌다.

// 컨트롤러
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable Long id) {
    Order order = orderService.findOrder(id);
    return new OrderResponse(
            order.getId(),
            order.getItems().size()   // @OneToMany(LAZY) 를 여기서 초기화
    );
}
  • OSIV = true → getItems()에서 세션이 살아 있으므로 추가 SELECT가 나가고 정상 동작한다. 문제는 그 쿼리가 서비스 계층 밖에서 나간다는 것이다.
  • OSIV = false → getItems()에서 LazyInitializationException.

여기서 이미 켰을 때의 숨은 비용 하나가 보인다. 서비스 코드만 읽어서는 이 API가 쿼리를 몇 개 쓰는지 알 수 없다. 응답 필드를 하나 추가한 것만으로 N+1이 생기고, 그게 서비스 계층 코드리뷰에서는 안 보인다. OSIV는 LazyInitializationException을 막는 대신 N+1을 보이지 않는 곳으로 밀어넣는다(N+1 탐지와 해결).

2

켰을 때의 대가 — "오래 잡는다"가 아니라 "놀고 있는 커넥션을 잡는다"

▾

2-1. 표현 하나를 정확히 바꾼다

많은 답변이 여기서 멈춘다: "OSIV를 켜면 커넥션을 요청이 끝날 때까지 오래 잡는다." 틀린 말은 아니지만, 이 표현으로는 왜 그렇게 치명적인지가 설명되지 않는다. 커넥션을 오래 잡는 게 문제라면, 원래 쿼리가 오래 걸리는 API도 똑같은 문제여야 한다.

정확한 표현은 이것이다.

💡

아무 일도 하지 않는 커넥션을 잡는다.

DB 커넥션을 300ms 동안 잡고 그 300ms 내내 쿼리를 실행했다면, 그건 필요한 점유다. 그런데 OSIV가 만드는 점유는 DB에게 아무것도 시키지 않으면서 자리만 차지하는 시간이다. 식당에 비유하면, 주문을 다 받고 음식도 다 나갔는데 손님이 자리에서 통화를 30분 하는 것과 같다. 주방(DB)은 놀고 있는데 테이블(커넥션)은 회전하지 않는다.

2-2. 최악의 조합 — 응답 단계의 외부 API 호출

이 점유가 실제로 얼마나 길어지는지는 트랜잭션이 끝난 뒤에 무슨 일을 하느냐에 달렸다. 가장 나쁜 것이 컨트롤러·응답 조립 단계의 외부 API 호출이다.

java
// ❌ BEFORE — OSIV 켜진 상태에서 이 코드는 커넥션을 인질로 잡는다
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable Long id) {
    Order order = orderService.findOrder(id);      // 트랜잭션 종료. 그러나 EM 은 열려 있음
                                                   // → 커넥션이 아직 풀로 안 돌아감

    Delivery d = deliveryApiClient.track(order.getTrackingNo());   // 외부 API 300ms
                                                   // ↑ 이 300ms 동안 DB 커넥션은
                                                   //   아무 일도 안 하면서 점유돼 있다

    return new OrderResponse(order, d);            // 직렬화 중 지연 로딩까지 가능
}

2-3. 숫자로 계산하면 이렇게 무너진다

가정을 잡아보자.

항목값
HikariCP 풀 크기20
서비스 트랜잭션 구간(실제 DB 작업)50ms
컨트롤러의 외부 API 호출300ms
직렬화·응답 조립20ms
요청 하나의 총 응답 시간370ms (두 경우 동일)

커넥션 하나가 초당 처리할 수 있는 요청 수는 1 / 점유시간이고, 풀 전체의 이론 처리량은 풀 크기 / 점유시간이다(대기행렬 이론의 리틀의 법칙 L = λ × W를 커넥션에 적용한 것).

text
OSIV = false  →  커넥션 점유 = 50ms
                 이론 최대 처리량 = 20 / 0.05초 = 400 req/s

OSIV = true   →  커넥션 점유 = 50 + 300 + 20 = 370ms
                 이론 최대 처리량 = 20 / 0.37초 ≈ 54 req/s

같은 코드, 같은 응답 시간인데 처리 가능한 트래픽이 7배 이상 차이 난다.

이걸 반대로 읽으면 장애 시나리오가 나온다. 트래픽이 100 req/s로 들어온다고 하자. 필요한 커넥션 수는 초당 요청 수 × 점유 시간이다.

text
OSIV = false  →  100 × 0.05  =  5개 필요   →  풀 20개로 여유 (25% 사용)
OSIV = true   →  100 × 0.37  = 37개 필요   →  풀 20개로 부족 ⇒ 대기 발생

풀이 부족해지는 순간부터는 선형이 아니라 절벽이다. 커넥션을 못 얻은 스레드는 connectionTimeout(HikariCP 기본 30초)만큼 대기하고, 그동안 톰캣 워커 스레드도 함께 묶인다. 응답 시간이 370ms에서 수 초로 튀고 → 클라이언트 타임아웃 → 재시도 → 요청량 증가 → 더 심한 고갈. 후보자가 정확히 짚은 "커넥션 점유 → 풀 고갈 → 응답 지연 → 타임아웃 전파" 연쇄가 이 지점에서 시작된다.

2-4. 진짜 무서운 부분 — 장애 격리가 깨진다

위 계산에서 한 걸음 더 나가면 이 문항의 시니어 포인트가 나온다.

외부 API가 느려지는 순간, 우리 DB 커넥션 풀이 같이 죽는다.

외부 배송 조회 API가 300ms에서 3초로 느려졌다고 하자. OSIV가 꺼져 있으면 그 API를 쓰는 엔드포인트만 느려진다 — 피해가 격리된다. 그런데 OSIV가 켜져 있으면 점유 시간이 3,070ms가 되어 커넥션 풀이 순식간에 고갈되고, 그 API와 아무 상관 없는 로그인·결제 API까지 커넥션을 못 얻어 전면 장애가 된다.

즉 OSIV는 성능 설정이 아니라 장애 전파 경로다. "남의 장애가 우리 DB 커넥션 풀을 타고 들어온다"는 문장으로 정리하면 면접관에게 강하게 남는다. (가산점 포인트)

💡

확인 범위: 커넥션이 정확히 언제 풀로 반환되는지는 Hibernate의 커넥션 릴리스 모드(hibernate.connection.handling_mode)와 트랜잭션 종류(resource-local / JTA)에 따라 달라질 수 있다. 위 계산은 "트랜잭션 밖에서 지연 로딩이 일어나는 구간 동안 커넥션이 세션 종료 시점까지 유지된다"는 널리 통용되는 최악 케이스를 전제로 한 모델링이다. 우리 서비스의 실제 값을 알고 싶다면 계산이 아니라 측정이다 — HikariCP의 활성 커넥션 수(hikaricp.connections.active)와 요청 처리 시간을 함께 보면, 커넥션 점유 시간이 트랜잭션 구간보다 얼마나 긴지가 그대로 드러난다. 면접에서도 "정확한 값은 릴리스 모드에 따라 다르므로 지표로 확인한다"고 붙이면 오히려 신뢰도가 올라간다.

2-5. 켰을 때의 부작용 하나 더 — 조용한 UPDATE

컨트롤러나 DTO 변환 코드에서 엔티티의 setter를 호출하는 경우가 있다. OSIV가 켜져 있으면 그 엔티티는 아직 영속 상태다. 여기서 같은 요청 안에 두 번째 @Transactional 호출이 있으면, 그 트랜잭션이 커밋될 때 변경 감지가 아까 바꾼 값까지 같이 flush한다. 아무도 save()를 부르지 않았는데 UPDATE가 나가는 "유령 UPDATE"의 원인 중 하나가 이것이다(영속성 컨텍스트와 변경 감지).

OSIV를 끄면 이 부류의 버그가 구조적으로 불가능해진다. 컨트롤러에 도달한 엔티티는 이미 준영속(detached)이라 아무리 setter를 불러도 DB에 반영되지 않는다.

3

껐을 때 — 불편이 아니라 설계 강제다

▾

3-1. 프레임워크가 규칙을 대신 지켜준다

껐을 때 개발자가 치르는 대가를 "트랜잭션 경계를 직접 신경 써야 하는 불편"이라고 말하면 답변으로는 성립하지만, 한 층 낮다. 정확한 프레임은 이것이다.

💡

OSIV를 끄는 것은 "엔티티는 트랜잭션 밖으로 나가지 않는다"는 설계 원칙을 프레임워크가 강제하게 만드는 일이다.

원칙은 원래부터 있었다. 다만 OSIV가 켜져 있으면 그 원칙을 어겨도 아무 일이 일어나지 않아서 지켜지지 않을 뿐이다. 끄는 순간 위반이 즉시 예외로 드러난다. 즉 "불편해진다"가 아니라 "규칙을 어길 수 없게 된다" 가 정확하다.

그 결과 개발자가 하게 되는 일은 두 가지로 수렴한다.

java
// ❌ BEFORE — 엔티티를 컨트롤러로 올려보내고, 필요한 건 거기서 알아서 꺼낸다
@Transactional(readOnly = true)
public Order findOrder(Long id) {
    return orderRepository.findById(id).orElseThrow();
}
// 컨트롤러에서 order.getItems() → OSIV 덕에 통과. 쿼리는 눈에 안 보임.

// ✅ AFTER 1 — 필요한 연관을 조회 시점에 명시적으로 함께 읽는다 (fetch join)
@Query("select o from Order o join fetch o.items where o.id = :id")
Optional<Order> findWithItems(@Param("id") Long id);

// ✅ AFTER 2 — 트랜잭션 안에서 DTO 로 변환해 내보낸다 (근본 처방)
@Transactional(readOnly = true)
public OrderResponse findOrder(Long id) {
    Order order = orderRepository.findWithItems(id).orElseThrow();
    return OrderResponse.from(order);   // 세션이 살아 있는 동안 전부 꺼내 담는다
}   // ← 여기서 세션이 닫히지만, 밖으로 나가는 건 이미 순수 자바 객체다

어느 쪽이든 "이 API가 무엇을 함께 읽는가"가 코드에 드러난다. OSIV를 끄는 진짜 이득이 커넥션 절약만이 아니라 쿼리의 가시성 회복이라는 점까지 말하면 답변이 완성된다.

3-2. 중급 문항 "엔티티 직접 노출 금지"와 같은 원칙의 다른 얼굴

같은 3장 중급에 "엔티티를 API 응답으로 직접 노출하면 안 되는 이유"라는 문항이 따로 있다. 그 답은 보통 ① API 스펙이 DB 스키마에 종속된다 ② 지연 로딩 직렬화 폭탄 ③ 순환 참조로 정리된다.

OSIV를 끄는 것과 엔티티 노출을 금지하는 것은 결국 같은 한 줄로 수렴한다 — "엔티티는 영속성 컨텍스트가 살아 있는 구간 안에서만 존재한다." 엔티티 노출 금지는 그 규칙을 사람의 규율로 지키는 것이고, OSIV 끄기는 같은 규칙을 런타임이 강제하게 만드는 것이다. 두 문항이 사실 하나의 원칙을 양쪽에서 묻고 있다는 걸 짚으면, 개별 지식이 아니라 설계 관점을 갖고 있다는 신호가 된다. (가산점 포인트)

3-3. 그래도 대가는 실재한다 — 트레이드오프를 양쪽 다 말하기

껐을 때 잃는 것을 정직하게 나열해야 트레이드오프 서술이 된다.

  • 화면별 DTO와 변환 코드가 늘어난다. 필드 하나 추가에 DTO·매핑·테스트가 따라온다.
  • 트랜잭션 경계를 의식하며 코드를 짜야 한다. "이 로직이 트랜잭션 안인가"를 매번 확인해야 하고, 신입이 이 감각을 얻기 전까지는 예외를 자주 만난다.
  • 서버 사이드 렌더링(Thymeleaf 등)에서 특히 손해가 크다. 템플릿에서 연관을 자연스럽게 순회하는 구조가 통째로 막히므로, 뷰에 넘길 모델을 전부 미리 만들어야 한다.
  • 레거시 전환 비용이 크다. 이게 §4~5 전체의 주제다.

3-4. 그럼 왜 기본값이 true인가

기본값 해석은 이렇게 정리하면 정확하다.

프레임워크의 기본값은 "최적"이 아니라 "가장 덜 놀라는 값"으로 정해진다. 만약 기본값이 false였다면, JPA를 처음 쓰는 사람이 튜토리얼 수준의 코드를 짜자마자 LazyInitializationException을 만난다. 프레임워크 입장에서 그건 최악의 첫인상이다. 그래서 입문 난이도와 즉시 동작(works out of the box)을 우선한 방어적 기본값을 골랐다. 반대로 대용량 트래픽은 "그 단계에 도달한 팀이 직접 판단할 일"로 남겨둔 것이다.

그 판단을 미뤄뒀다는 사실 자체를 Spring Boot가 로그로 알려준다. 프로퍼티를 명시하지 않고 애플리케이션을 띄우면 시작 시 이런 경고가 뜬다.

text
spring.jpa.open-in-view is enabled by default. Therefore, database queries may be
performed during view rendering. Explicitly configure spring.jpa.open-in-view to
disable this warning

주목할 것은 마지막 문장이다. "끄면 경고가 사라진다"가 아니라 "명시적으로 설정하면 경고가 사라진다" 이다. true라고 적어도 경고는 없어진다. 즉 프레임워크가 요구하는 것은 끄는 게 아니라 의식적으로 선택하는 것이다. 이 해석을 말하면 rationale이 묻는 "프레임워크 기본값을 의심해본 적 있는가"에 정면으로 답하는 셈이 된다.

💡

확인 범위: 위 경고 문구는 Spring Boot의 JPA 자동 설정이 출력하는 메시지이고, 세부 표현은 버전에 따라 조금씩 달라질 수 있다. 면접에서는 문구를 그대로 외워 읊기보다 "명시적으로 설정하라고 경고한다"는 취지를 말하는 편이 안전하다. 기본값이 true라는 사실 자체는 Spring Boot 2.x·3.x에서 유지되고 있으나, 실제 프로젝트에서는 application.yml에 명시해두는 것이 정답이라 버전을 기억할 필요 자체가 없어진다.

3-5. 결론: 대용량 트래픽에서는 어떻게 설정하나

yaml
spring:
  jpa:
    open-in-view: false   # 값보다 '명시했다'는 사실이 중요하다

다만 답을 이 한 줄로 끝내면 안 된다. "끈다. 단, 끄는 건 마지막 단계다" 까지가 답이다. 그 앞에 무엇이 와야 하는지가 §4와 §5다.

4

"3년치 코드 중 어디가 터질지 어떻게 찾나" — 이 문항의 진짜 관문

▾

면접관이 붙이는 시나리오는 대개 이렇다. *OSIV가 켜진 채로 3년치 코드가 쌓인 운영 서비스에서 커넥션 풀 고갈이 실제로 발생했다. 끄기로 결정했다. false로 배포하면 무슨 일이 벌어지나? 그 사고를 배포 전에 막으려면 무엇을 하겠나?*

방향은 누구나 안다 — "트랜잭션 밖에서 지연 로딩하는 곳을 찾아야 한다." 변별은 "구체적으로 어떻게 찾을 것이며, 놓친 게 없다는 걸 무엇으로 보장하느냐" 에서 난다.

4-1. 먼저 못을 박자 — 정적 검색은 보장 수단이 될 수 없다

흔한 답이 "지연 로딩 필드의 게터 사용처를 검색한다" 이다. 탐색 범위를 좁히는 발상으로는 합리적이지만, 보장 수단으로는 성립하지 않는다. 이유는 하나다.

💡

지연 로딩을 트리거하는 코드의 상당수는 게터 호출이 소스에 존재하지 않는다.

터지는데 검색에 안 걸리는 경로들:

  • Jackson의 JSON 직렬화 — 컨트롤러가 Order 엔티티를 그대로 반환하면 Jackson이 리플렉션으로 모든 게터를 호출한다. 코드 어디에도 getItems()가 없는데 직렬화 단계에서 초기화가 일어난다. 검색으로는 절대 안 나온다.
  • toString() — Lombok @Data·@ToString이 만든 toString()은 모든 필드를 건드린다. 로그 한 줄(log.debug("order={}", order))이 지연 로딩을 트리거한다. 소스에 getItems()는 없다.
  • equals()/hashCode() — 역시 Lombok이 생성한 것이 연관 필드를 포함하면 컬렉션에 담는 순간 초기화된다.
  • 템플릿 엔진 — Thymeleaf의 ${order.items}는 자바 코드가 아니라 문자열이다. IDE의 "사용처 찾기"에 잡히지 않는다.
  • 프록시 경유 / 상속 계층 — 부모 타입 변수로 접근하거나 ModelMapper·MapStruct 같은 매핑 라이브러리가 리플렉션으로 접근하는 경우.
  • 매핑 라이브러리·직렬화 커스터마이저 — @JsonSerialize, 커스텀 MessageConverter 등 프레임워크가 대신 호출하는 지점 전부.

정리하면 정적 검색이 못 잡는 축은 "프레임워크가 리플렉션으로 부르는 호출" 이고, 하필 실무에서 가장 흔한 사고 유형이 바로 그 축이다. "컨트롤러가 엔티티를 그대로 반환한다"는 케이스가 정확히 여기에 속한다.

그래서 답변의 방향을 이렇게 바꿔야 한다.

💡

찾는 것이 아니라, 터지게 만들어서 세는 것이다. 사람이 코드를 읽어 목록을 만드는 대신, OSIV를 끈 환경에서 코드를 실제로 실행시켜 예외가 나는 지점을 기계가 수집하게 한다.

4-2. 보장 장치 ① — open-in-view=false 프로파일로 기존 통합 테스트를 통째로 한 번 더 돌린다

핵심 아이디어는 새 테스트를 쓰는 게 아니라, 이미 있는 컨트롤러 통합 테스트를 설정만 바꿔 한 번 더 실행하는 것이다.

Spring은 시스템 프로퍼티를 Environment의 상위 우선순위 프로퍼티 소스로 읽는다. 그래서 테스트 코드를 한 줄도 고치지 않고 JVM 옵션만으로 OSIV를 끌 수 있다.

kotlin
// build.gradle.kts — 기존 테스트를 OSIV 끈 상태로 한 번 더 도는 태스크
tasks.register<Test>("osivOffTest") {
    useJUnitPlatform()
    // Spring 은 시스템 프로퍼티를 application.yml 보다 우선해서 읽는다
    systemProperty("spring.jpa.open-in-view", "false")

    // 컨트롤러부터 DB 까지 관통하는 통합 테스트만 대상으로
    filter { includeTestsMatching("*ControllerTest") }

    // 이 태스크의 실패는 '지금은' 빌드를 깨지 않게 두고, 리포트만 수집한다
    ignoreFailures = true   // 전환이 끝나면 false 로 바꿔 회귀 방지선으로 승격
}
text
$ ./gradlew osivOffTest

OrderControllerTest > 주문_상세조회 FAILED
    org.hibernate.LazyInitializationException:
        could not initialize proxy [Order.items] - no Session
MemberControllerTest > 회원_목록 FAILED
    ...
    → 실패 목록이 곧 '고쳐야 할 지점 목록'이다.

이 리포트가 사람이 만든 어떤 검색 결과보다 정확하다. Jackson 직렬화든 toString()이든 템플릿이든, 경로를 가리지 않고 실제로 터지는 곳만 정확히 나온다.

반드시 함께 말해야 할 함정 세 가지 — 이걸 짚으면 "해본 사람"으로 읽힌다.

  1. 테스트 클래스에 @Transactional이 붙어 있으면 이 방법이 무력화된다. 테스트에 트랜잭션이 걸리면 테스트 메서드 전체 구간에서 세션이 살아 있어, OSIV를 꺼도 지연 로딩이 통과한다. 통과했다는 결과가 거짓 안심이 된다. 컨트롤러 통합 테스트에서는 @Transactional을 빼고 데이터 정리는 별도 방식(테이블 truncate 등)으로 해야 한다.
  2. @WebMvcTest 슬라이스 테스트는 이 검증에 쓸 수 없다. 서비스가 모킹돼 있어 JPA가 아예 개입하지 않는다. 필요한 것은 @SpringBootTest + 실제 DB로 컨트롤러 → 서비스 → 리포지토리 → 직렬화까지 관통하는 테스트다. (MockMvc를 써도 전체 컨텍스트로 띄우면 인터셉터와 메시지 컨버터가 실제로 동작하므로 직렬화 단계의 예외까지 잡힌다.)
  3. hibernate.enable_lazy_load_no_trans가 켜져 있으면 예외 대신 조용히 쿼리가 나간다. 이 옵션은 세션 밖 지연 로딩을 임시 세션으로 처리해주는데, 문제를 숨기는 대신 요청마다 세션을 새로 여는 최악의 성능 특성을 갖는다. 전환 작업 전에 이 값이 꺼져 있는지부터 확인해야 검증이 유효하다. (가산점 포인트)
java
// ✅ 검증에 쓸 수 있는 형태
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureMockMvc
// @Transactional  ← 절대 붙이지 않는다. 붙는 순간 세션이 살아 있어 검증이 무의미해진다.
class OrderControllerTest {

    @Autowired MockMvc mockMvc;

    @Test
    void 주문_상세조회() throws Exception {
        mockMvc.perform(get("/orders/{id}", savedOrderId))
               .andExpect(status().isOk());
        // OSIV 를 끄고 이 테스트를 돌리면, 직렬화 단계의 지연 로딩이 여기서 터진다
    }
}

그리고 여기서 프레임 하나가 완성된다.

💡

통합 테스트 커버리지가 곧 안전망의 크기다. 이 방법이 잡아낼 수 있는 범위는 테스트가 실제로 통과하는 코드 경로까지다. 테스트가 없는 엔드포인트는 "안전한 것"이 아니라 "확인되지 않은 것" 이다.

그래서 전환 작업의 첫 단계는 사실 코드 수정이 아니라 커버리지 확보다. 현실적인 순서는 이렇다.

  1. 컨트롤러 엔드포인트 전수 목록을 뽑는다(RequestMappingHandlerMapping에서 런타임에 추출하거나, OpenAPI 문서에서 뽑으면 누락이 없다).
  2. 그중 통합 테스트가 한 번도 태우지 않는 엔드포인트를 가려낸다 — 이게 사각지대다.
  3. 사각지대를 트래픽 순으로 정렬해 위에서부터 테스트를 채운다. 전수 커버리지를 목표로 잡으면 끝나지 않으므로, "상위 N개 엔드포인트가 전체 트래픽의 90%"라는 식의 기준을 세워 그만큼만 먼저 덮는다.
  4. 남은 사각지대는 배포 방식으로 방어한다 — §5-3의 카나리.

4-3. 보장 장치 ② — ArchUnit으로 재발까지 막는다

통합 테스트는 지금 있는 위반을 찾아준다. 하지만 다음 주에 누군가 다시 컨트롤러에서 엔티티를 반환하면 똑같은 일이 반복된다. 그래서 원인 쪽에 못을 하나 박는다 — "컨트롤러는 엔티티를 반환할 수 없다" 를 빌드에서 강제한다.

java
@AnalyzeClasses(
        packages = "com.example",
        importOptions = ImportOption.DoNotIncludeTests.class)
class WebLayerRulesTest {

    @ArchTest
    static final ArchRule 컨트롤러는_엔티티를_반환하면_안_된다 =
            methods()
                .that().areDeclaredInClassesThat()
                       .areAnnotatedWith(RestController.class)
                .and().arePublic()
                .should(new ArchCondition<JavaMethod>("반환 타입에 @Entity 가 없어야 한다") {
                    @Override
                    public void check(JavaMethod method, ConditionEvents events) {
                        flatten(method.getReturnType())
                            .filter(type -> type.isAnnotatedWith(Entity.class))
                            .forEach(type -> events.add(SimpleConditionEvent.violated(
                                    method,
                                    method.getFullName() + " 가 엔티티 "
                                        + type.getSimpleName() + " 를 반환한다"
                                        + " (OSIV 를 끄면 직렬화 시점에 터진다)")));
                    }
                });

    /**
     * ResponseEntity<List<Order>> 처럼 제네릭 안쪽에 숨은 엔티티까지 찾아내려면
     * 타입 인자를 재귀적으로 펼쳐야 한다. 겉 타입만 보면 ResponseEntity 라서 통과해버린다.
     */
    private static Stream<JavaClass> flatten(JavaType type) {
        Stream<JavaClass> self = Stream.of(type.toErasure());
        if (type instanceof JavaParameterizedType parameterized) {
            return Stream.concat(self,
                    parameterized.getActualTypeArguments().stream()
                                 .flatMap(WebLayerRulesTest::flatten));
        }
        return self;
    }
}

이 룰의 핵심은 flatten이다. 대부분의 위반은 Order를 직접 반환하는 형태가 아니라 ResponseEntity<List<Order>>, Page<Order>처럼 제네릭 안에 숨어 있다. 겉 타입만 검사하는 룰은 이걸 전부 놓치므로 사실상 무용지물이 된다.

더 거칠지만 더 강력한 대안도 있다. 계층 자체를 막는 방식이다.

java
@ArchTest
static final ArchRule 웹_계층은_엔티티에_의존하지_않는다 =
        noClasses().that().resideInAPackage("..api..")
                   .should().dependOnClassesThat().resideInAPackage("..domain.entity..");

이쪽은 반환 타입뿐 아니라 파라미터·지역 변수·import까지 전부 막는다. 강력한 만큼 기존 코드가 대량으로 걸리므로, 신규 모듈부터 적용하고 레거시는 아래 방식으로 푼다.

레거시 도입 요령 — 기존 위반이 200개인 상태에서 룰을 켜면 빌드가 안 돌아 결국 룰을 지우게 된다. ArchUnit의 FreezingArchRule.freeze(rule) 로 현재 위반을 동결하면 기존 것은 통과시키고 신규 위반만 실패시킬 수 있다. 동결 목록을 조금씩 줄여나가는 방식이 현실적이다. (가산점 포인트)

java
@ArchTest
static final ArchRule 컨트롤러_엔티티_반환_금지 =
        FreezingArchRule.freeze(컨트롤러는_엔티티를_반환하면_안_된다);
// 첫 실행에서 현재 위반을 파일로 기록 → 이후엔 새 위반만 빌드를 깬다
💡

확인 범위: methods(), ArchCondition, SimpleConditionEvent, JavaParameterizedType, FreezingArchRule은 모두 ArchUnit의 공개 API이지만, 정확한 시그니처(특히 getReturnType()이 JavaClass를 반환하던 구버전과 JavaType을 반환하는 신버전)는 버전에 따라 다르므로 프로젝트에서 컴파일로 확인해야 한다. 면접에서는 "제네릭 타입 인자까지 재귀로 펼쳐야 한다"는 설계 포인트를 말하는 것이 API 이름을 정확히 대는 것보다 중요하다.

4-4. 세 층을 함께 놓고 본다

층수단언제 걸리나잡는 것못 잡는 것
정적게터 사용처 검색즉시명시적 호출직렬화·toString·프록시·템플릿
구조ArchUnit 룰빌드컨트롤러의 엔티티 반환서비스가 엔티티를 반환하고 컨트롤러가 소비하는 경우
실행OSIV off 통합 테스트CI실제로 터지는 모든 경로테스트가 없는 경로

정적 검색은 지워도 되는 층이 아니라, 셋 중 유일하게 "보장"이라는 단어를 붙일 수 없는 층이다. 작업 대상을 빠르게 훑는 데는 쓰되, "다 찾았다"의 근거로 쓰면 안 된다. 보장은 실행 층에서만 나온다.

그리고 이 표는 이 카테고리 전체에서 반복되는 구조와 같다. N+1 탐지에서도 결론이 같았다 — "주의 깊게 보겠다"는 대책이 아니고, 회귀는 사람이 아니라 CI가 막는다. N+1 탐지와 해결의 쿼리 수 단정 테스트, fetch join + 페이징의 경고를 예외로 승격시키는 설정, 그리고 여기의 OSIV off 프로파일 테스트는 전부 같은 도구 상자다.

5

안전한 전환 순서 — 끄는 것은 마지막이다

▾

5-1. 순서

text
① 컨트롤러가 엔티티를 반환하지 않도록 DTO 경계를 세운다   ← OSIV 는 아직 true
② 서비스 트랜잭션 안에서 DTO 변환을 끝낸다                ← OSIV 는 아직 true
③ 그때 open-in-view: false 로 끈다                        ← 마지막

5-2. 왜 이 순서인가

되돌릴 수 있는 변경을 먼저 하고, 되돌리기 어려운 변경을 마지막에 한다.

  • ①②는 OSIV가 켜진 상태에서도 동작이 완전히 동일하다. 컨트롤러가 엔티티 대신 DTO를 반환하도록 바꾸는 것은 OSIV와 무관한 리팩터링이라, 한 엔드포인트씩 나눠 배포할 수 있고 문제가 생기면 그 하나만 되돌리면 된다. 위험 단위가 작다.
  • ③은 전역 스위치다. 한 번에 모든 엔드포인트의 동작이 바뀌고, 되돌리는 것도 전부 아니면 전무다. 위험 단위가 서비스 전체다.

순서를 뒤집으면 어떻게 되는지가 명확하다. 끄기부터 하면 "터지는 걸 줍는" 방식이 되고, 줍는 장소가 운영이 된다. 그리고 장애 대응 중에는 원인 하나를 고칠 때마다 배포해야 하는데, 남은 지점이 몇 개인지도 모르는 상태다. 롤백하면 원래 문제(커넥션 고갈)로 돌아간다 — 어느 쪽으로도 갈 수 없는 상태가 된다.

①②를 먼저 하면 ③은 "이미 아무도 의존하지 않는 기능을 끄는 일"이 된다. 이상적인 경우 ③은 아무 일도 일어나지 않는 배포다. 그게 목표다.

각 단계를 §4의 장치와 짝지으면 이렇게 된다.

단계작업완료를 무엇으로 판단하나
0사각지대 파악엔드포인트 목록 대비 통합 테스트 커버리지
①컨트롤러 반환 타입을 DTO로ArchUnit 룰 위반 0 (동결 목록이 비는 것)
②서비스 트랜잭션 안에서 변환osivOffTest 실패 0
③open-in-view: false카나리에서 예외 발생률 0

"완료 판단 기준이 사람의 확인이 아니라 CI 결과" 라는 점이 이 표의 요지다.

5-3. ③단계의 마지막 안전장치 — 카나리

테스트 커버리지가 100%가 아니라면(현실적으로 아니다) 사각지대가 남는다. 마지막 방어는 배포 방식으로 만든다.

bash
# 인스턴스 1대에만 환경변수로 OSIV 를 끈다 (코드·설정 파일 변경 없이)
SPRING_JPA_OPEN_IN_VIEW=false

한 대에만 적용하고 LazyInitializationException 발생 건수를 모니터링한다. 일정 기간 0이면 범위를 넓히고, 뜨면 그 스택트레이스가 곧 남은 작업 목록이다. 영향 범위가 전체 트래픽의 1/N로 줄어들고, 되돌리는 데 배포가 필요 없다.

동시에 반대편 지표도 봐야 목적을 달성했는지 알 수 있다 — HikariCP 활성 커넥션 수와 커넥션 획득 대기 시간이 카나리 인스턴스에서 눈에 띄게 줄어야 한다. 그게 줄지 않으면 애초에 OSIV가 병목이 아니었다는 뜻이므로, 원인을 다시 찾아야 한다.

6

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

대체로 아니다. 요청 하나만 놓고 보면 하는 일이 같으므로 응답 시간은 거의 그대로다. 바뀌는 것은 동시에 처리 가능한 요청 수(처리량) 다. §2-3의 계산에서 응답 시간은 370ms로 두 경우가 동일했고, 달라진 것은 400 req/s와 54 req/s였다.

오히려 끄면 개별 응답이 느려지는 경우도 있다. 지연 로딩으로 나가던 쿼리를 fetch join으로 합치면서 조인 결과가 커질 수 있기 때문이다. 그래서 정확한 표현은 "성능이 좋아진다"가 아니라 "커넥션이라는 한정 자원의 회전율이 올라가 같은 하드웨어로 더 많은 트래픽을 견딘다" 이다. 이 구분을 하면 "성능"이라는 단어를 뭉뚱그리지 않는 사람으로 보인다.

spring.jpa.open-in-view는 애플리케이션 전역 스위치라 URL 단위로 켜고 끌 수 없다(직접 인터셉터를 등록해 경로별로 적용하는 것은 기술적으로 가능하지만, "어떤 엔드포인트는 엔티티가 트랜잭션 밖으로 나가도 된다"는 예외를 공식화하는 셈이라 권하지 않는다).

그런데 이 질문은 사실 방향이 반대다. 필요한 것은 "OSIV를 켠 엔드포인트"가 아니라 "세션을 명시적으로 연장할 방법" 이고, 그 답이 fetch join·@EntityGraph·DTO 변환이다. 전역 설정으로 예외를 만드는 대신 지점별 처방으로 푸는 것이 원칙이다 — LazyInitializationException의 "처방의 범위를 문제의 범위에 맞춘다"와 같은 이야기다.

있다. OSIV는 웹 요청 스코프에만 작용하므로 그 밖에서는 무력하다 — 테스트 코드, @Async·@Scheduled·별도 스레드(세션은 스레드에 묶여 있다), 배치, 응답 직렬화가 끝난 뒤의 코드, 엔티티를 캐시에 담아 다음 요청에서 재사용하는 경우.

이 목록이 실무적으로 중요한 이유가 있다. "우리는 OSIV로 잘 돌아가고 있다"는 팀도 사실은 이미 이 예외를 만나고 있다. 다만 발생 지점이 웹 요청 밖이라 원인을 OSIV와 연결하지 못했을 뿐이다. 그런 팀에게 OSIV 끄기를 설득할 때 쓸 수 있는 근거이기도 하다.

동작은 한다. 초기화되지 않은 프록시를 예외 대신 null로 직렬화해주므로 예외는 사라진다. 그런데 이건 해결이 아니라 은폐이고, 은폐 중에서도 나쁜 쪽이다.

이유는 실패 방식이 바뀌기 때문이다. 예외는 시끄럽게 터져서 즉시 발견되지만, null은 조용히 잘못된 응답을 내보낸다. 클라이언트는 "주문 항목이 없는 주문"을 정상 응답으로 받는다. 데이터가 틀린 채 200 OK가 나가는 것은 500 에러보다 훨씬 늦게 발견되고 훨씬 비싸게 수습된다.

정리하면 이 모듈은 엔티티를 직렬화하겠다는 잘못된 전제를 편하게 만들어주는 도구다. 전제 자체를 없애는 것(DTO 반환)이 답이다. (가산점 포인트)

줄일 수 있는 근거가 생기는 것은 맞지만, 끄자마자 줄이는 건 위험하다. 필요한 커넥션 수는 초당 요청 수 × 커넥션 점유 시간이고, OSIV를 끄면 점유 시간이 줄어드니 같은 트래픽에 더 적은 커넥션으로 충분해진다(§2-3에서 37개 → 5개).

다만 순서가 있다. 먼저 끄고, 실제 활성 커넥션 지표를 관찰한 뒤, 그 데이터로 줄인다. 계산값만 믿고 줄이면 트래픽 스파이크나 느린 쿼리 한 건에 여유가 사라진다.

한 걸음 더 나가면 좋은 지적이 하나 있다. 커넥션 풀은 크게 잡을수록 좋은 게 아니다. DB의 max_connections는 유한하고, 커넥션이 많아지면 DB 쪽 컨텍스트 스위칭과 락 경합이 늘어 오히려 전체 처리량이 떨어진다. "OSIV를 켜둔 채 풀을 늘려서 버틴다"는 대응이 왜 지속 가능하지 않은지가 여기서 나온다 — 풀을 늘리는 것은 문제를 애플리케이션에서 DB로 옮기는 것일 뿐이다. (가산점 포인트)

전수 커버리지를 목표로 잡으면 프로젝트가 끝나지 않는다. 위험을 계층화해서 순서를 만드는 것이 답이다.

  1. 위험이 높은 교집합부터 찾는다. 두 축을 곱한다 — ⓐ 컨트롤러가 엔티티를 반환하는 엔드포인트(ArchUnit 룰을 리포트 모드로 한 번 돌리면 목록이 즉시 나온다) ⓑ 트래픽 상위 엔드포인트(액세스 로그나 APM에서 뽑는다). 교집합이 "터지면 가장 아픈 곳"이다. 여기부터 테스트를 쓴다.
  2. ①②단계(DTO 경계 수립)는 테스트를 기다리지 않고 진행한다. 이 리팩터링은 OSIV가 켜진 상태에서 동작이 동일하므로 지금 배포해도 위험이 낮다. 안전망이 없다는 이유로 멈출 이유가 없고, 오히려 이걸 진행할수록 ③단계의 위험이 계속 줄어든다.
  3. ArchUnit 룰을 FreezingArchRule로 먼저 걸어 출혈을 멈춘다. 기존 200개는 동결하되 신규 위반은 즉시 빌드를 깨게 한다. 고치는 속도보다 늘어나는 속도가 빠르면 영원히 못 끝난다 — 그래서 신규 차단이 기존 정리보다 먼저다.
  4. 커버리지 사각지대는 배포 방식으로 메운다. §5-3의 카나리로 영향 범위를 1/N로 줄이고, LazyInitializationException을 알림으로 걸어 남은 지점을 운영에서 수집한다. 테스트로 못 덮은 만큼을 배포 전략으로 갚는 구조다.

핵심 메시지는 이것이다. "안전망이 없으니 못 한다"가 아니라 "안전망의 크기에 맞춰 한 번에 바꾸는 범위를 줄인다." 커버리지가 낮으면 카나리 비중을 낮추고 관찰 기간을 늘리면 된다. 이 교환 관계를 말할 수 있으면 전환 작업을 실제로 해본 사람처럼 들린다.

✅ 한 줄 요약

OSIV는 트랜잭션이 끝난 뒤에도 EntityManager를 응답 완료까지 열어두는 Spring Boot의 기본값(true) 이고, 그 대가는 "커넥션을 오래 잡는 것"이 아니라 아무 일도 하지 않는 커넥션을 잡아 외부 시스템의 지연까지 우리 DB 풀로 끌어들이는 것이다 — 그래서 대용량 서비스는 끄되, 끄는 것은 마지막 단계이고 그 앞에 DTO 경계 수립과 open-in-view=false 통합 테스트·ArchUnit 룰이라는 기계적 보장 장치가 먼저 와야 한다. 어디가 터질지는 검색으로 찾는 게 아니라, 터지게 만들어서 세는 것이다.
