동시성 갱신 4가지 접근 비교
낙관적 락 · 비관적 락 · 원자적 UPDATE · 분산 락 — "임계 구간에 무엇을 넣을 것인가"

면접 질문: "재고 차감/포인트 차감 같은 동시성 갱신 문제를 네 가지 방식으로 풀 때의 트레이드오프를 비교하고, 어떤 상황에서 무엇을 고를지 말해주세요."

핵심 관전 포인트 — 이 질문은 정답이 없는 문제이고, 그래서 트레이드오프를 정리해 말하는 능력 자체가 채점 대상이다. 흔한 답은 "충돌이 드물면 낙관적, 잦으면 비관적"인데 그건 정의를 바꿔 말한 것에 가깝다. 더 정확한 축은 "임계 구간(critical section)에 무엇이 들어가는가"다. 읽고·계산하고·쓰는 과정이 SQL 한 문장으로 압축되면 원자적 UPDATE가 기본값이고, 여러 필드를 읽어 애플리케이션에서 계산해야 하는데 충돌이 드물면 낙관적 락, 계산이 복잡하고 충돌이 잦아 재시도 비용이 크면 비관적 락(대가는 커넥션 점유·데드락), 임계 구간에 DB 밖 자원이 끼어 있으면(외부 결제 호출, 여러 DB에 걸친 갱신, 멀티 인스턴스 스케줄러) 분산 락이다. 그리고 반드시 붙여야 할 두 문장이 있다. ① Redis 분산 락은 정합성 보증 장치가 아니라 부하 최적화 장치다 — TTL 만료·노드 장애·GC 정지로 언제든 두 스레드가 동시에 임계 구간에 들어갈 수 있으므로 정합성의 최종 보증은 항상 DB(where qty >= 1 + CHECK (qty >= 0))여야 한다. ② 이건 사지선다가 아니다 — 실무의 답은 대개 분산 락으로 대기를 밀어내고, 원자적 UPDATE로 갱신하고, CHECK 제약으로 바닥을 막는 층 쌓기다.
  • 1
    축을 먼저 세운다 — "충돌 빈도"가 아니라 "임계 구간의 내용물"이다 — 충돌 빈도는 운영에 올려야 알 수 있고 시간에 따라 변하는 값이지만, 임계 구간에 무엇이 들어 있는지는 코드를 읽으면 지금 알 수 있고 배포하지 않는 한 변하지 않는다. 그래서 판단은 가능성(Q1: DB 밖 자원이 있는가) → 구조(Q2: SQL 한 문장으로 압축되는가) → 양(Q3: 충돌이 잦은가) 순으로 좁힌다.
  • 2
    네 방식은 서열이 아니라 서로 다른 자원을 소모하는 도구다 — 낙관적 락은 CPU와 재실행 비용, 비관적 락은 DB 커넥션과 열린 트랜잭션, 원자적 UPDATE는 영속성 컨텍스트 일관성과 도메인 모델, 분산 락은 인프라 의존과 정합성 보증 자체를 내준다. "무엇이 가장 좋은가"로 답하면 선택 회의를 해본 적 없는 사람으로 읽힌다.
  • 3
    그리고 이건 사지선다가 아니라 층 쌓기다 — 1층 분산 락(대기를 커넥션 풀 밖으로), 2층 원자적 UPDATE(where qty >= ?), 3층 CHECK 제약(모든 경로의 마지막 그물). 각 층은 위층이 실패했다고 가정하고 설계된다 — Redis 분산 락은 원리적으로 뚫리므로 정합성의 최종 보증은 언제나 DB다.

0. 질문 + 출제 의도

질문: "재고 차감/포인트 차감 같은 동시성 갱신 문제를 ① 낙관적 락(@Version) ② 비관적 락(select ... for update) ③ 원자적 UPDATE(update ... set qty = qty - 1 where id = ? and qty >= 1) ④ 분산 락(Redis) 각각으로 풀 때의 트레이드오프를 비교하고, 어떤 상황에서 무엇을 고를지 말해주세요."

출제 의도: 정답이 없는 문제에서 트레이드오프(충돌률, 처리량, 데드락 위험, 인프라 의존)를 정리해 말하는 능력 자체를 평가한다. 실무의 기술 선택 회의를 15분으로 압축한 질문이며, 결제 도메인 채용에서는 사실상 필수 검증 항목이다.

이 문항이 실제로 요구하는 것은 세 가지뿐이다 ① 네 방식을 하나의 축으로 꿰어 비교할 수 있는가  ② 자기가 고른 것의 대가까지 같은 호흡에 말할 수 있는가  ③ 그 대가를 감당할 수 있는 이유를 근거로 댈 수 있는가
네 가지 기법의 정의 암기는 이 질문의 채점 대상이 아니다.
이 페이지가 겨냥하는 함정 세 개 ① "무엇이 가장 좋은가"로 답하는 것 → "분산 락이 제일 낫습니다"라고 답하면 기법을 아는 사람이 아니라 선택 회의를 해본 적 없는 사람으로 읽힌다. 3절에서 "무슨 자원을 소모하는가" 축으로 넷을 나란히 세운다.
② "충돌 빈도" 하나로 선택 기준을 잡는 것 → 방향은 맞지만 절반이다. 2절에서 충돌이 하루 한 번이어도 틀리는 사례(임계 구간 안의 외부 PG 호출 = 이중 결제)로 축을 하나 더 세운다.
③ 가장 좋아 보이는 선택지의 대가를 안 붙이는 것 → 면접관이 "그거 좋네요"라고 인정해준 순간 양면 서술이 멈추는 패턴이 흔하다. 4절 전체가 원자적 UPDATE가 포기하는 것과 낙관적 락이 청구하는 재시도 비용이다.
이 문서의 위치 — 10번 문서와의 분담 낙관적 락과 비관적 락의 기본 메커니즘(@Version이 만드는 SQL, 영향 행 수 0의 의미, PESSIMISTIC_WRITE 락 모드 3종, 락 타임아웃, 데드락 회피, 재시도 코드 전문)은 10-optimistic-vs-pessimistic-lock.md에서 이미 다뤘다. 이 페이지의 주제는 그 메커니즘이 아니라 네 방식의 비교와 선택 판단이므로, 개별 메커니즘은 비교에 필요한 만큼만 짚고 "무엇을 근거로 고르는가"에 무게를 싣는다.

1. 문제의 정의 — lost update와 임계 구간

lost update(갱신 손실)는 두 트랜잭션이 같은 행을 읽어 각자 계산한 뒤 각자 쓰면, 나중에 쓴 쪽이 앞의 갱신을 덮어써서 앞의 갱신이 조용히 사라지는 현상이다. 에러도 예외도 나지 않는다는 점이 무섭다 — 두 트랜잭션 각각은 완벽하게 정상이고, 합쳐놓았을 때만 결과가 틀린다.

임계 구간(critical section)이란

동시에 한 주체만 들어가야 하는 코드 구간

둘 이상이 겹쳐 들어가면 결과가 깨지기 때문에 "위태로운(critical)" 구간이라는 이름이 붙었다. 이 문서의 네 가지 방식은 전부 "이 구간에 한 명만 들어가게 만드는" 서로 다른 방법이다. 그렇게 보면 넷이 서열이 아니라 같은 문제에 대한 네 가지 설계 선택이라는 것이 분명해진다.

1-1. 비유 — 임계 구간은 1인용 화장실이다

① 낙관적 락
문을 안 잠그고 들어갔다가, 나올 때 "그새 누가 들어왔었나"를 확인한다. 누가 다녀갔으면 처음부터 다시.
② 비관적 락
들어가면서 문을 잠근다. 뒤에 온 사람은 문 앞에서 기다린다 — 재실행은 없지만 줄이 생긴다.
③ 원자적 UPDATE
볼일을 문 앞에서 한 동작으로 끝내 아예 들어갈 필요를 없앤다. 그래서 문을 잠글 일도 없다.
④ 분산 락
화장실이 여러 건물에 흩어져 있을 때, 건물 밖에 정리원을 세워 줄을 세운다. 줄이 건물 안에 안 생긴다.

1-2. 무대 고정 — 같은 재고 차감을 네 번 구현한다

비교를 말로만 하면 흐려진다. 똑같은 재고 차감을 네 번 구현해놓고, 매번 같은 다섯 칸을 채우는 방식으로 간다.

대칭 비교를 위한 다섯 칸 — 어떤 방식을 설명하든 이 순서로

① 코드→ ② 나가는 SQL→ ③ 락이 잡히는 구간→ ④ 충돌 시 무슨 일이→ ⑤ 얻는 것 / 포기하는 것

⑤를 빼먹는 순간 비교가 아니라 소개가 된다. 면접에서 한 방식을 설명할 때도 이 다섯 칸을 순서대로 밟으면 "양면 서술"이 자동으로 나온다.

무대 공통 엔티티 — 네 방식이 전부 이것을 갱신한다
@Entity
public class Stock {
    @Id @GeneratedValue
    private Long id;

    private Long productId;
    private int qty;          // 남은 수량

    @Version
    private Long version;     // ①번 방식에서만 의미가 있다

    public void decrease(int amount) {
        if (this.qty < amount) throw new OutOfStockException();
        this.qty -= amount;
    }
}
항상 무슨 방식을 쓰든 이 제약은 깔고 간다
-- 3층 방어선의 맨 아래 (7절에서 이유를 설명한다)
ALTER TABLE stock
    ADD CONSTRAINT ck_stock_qty CHECK (qty >= 0);

-- 이 한 줄의 값어치:
--   락이 뚫려도
--   조건을 빠뜨린 새 코드가 배포돼도
--   운영자가 콘솔에서 실수해도
--   배치가 락을 안 거치고 들어와도
--   → 재고는 절대 음수가 되지 않는다

-- 비용은 사실상 0. 어떤 선택을 하든 마지막 그물이 된다.

2. 선택의 축 — 왜 "충돌 빈도"가 1차 기준이면 안 되나

흔한 선택 기준은 "충돌이 드물면 낙관적, 잦으면 비관적"이다. 방향은 맞다. 그런데 이걸 1차 기준으로 쓰면 두 가지가 어긋난다.

어긋남 ① — 충돌 빈도는 지금 알 수 없는 값이다

충돌률은 운영에 올려 관측해야 나온다. 설계 회의에서 이 값을 근거로 쓰면 결국 "느낌상 드물 겁니다"가 되고, 그건 근거가 아니다.

어긋남 ② — 알아낸 값도 오래 가지 않는다

트래픽·프로모션·신규 호출자·데이터 분포가 바뀌면 함께 바뀐다. 평소 하루 3건 충돌하던 재고 차감이 타임세일 한 번에 초당 500건이 된다. 선택의 근거가 시간에 따라 변하는 값이면, 그 선택이 언제 무효가 되는지 알 수 없다.

반대로 임계 구간의 내용물은 지금 코드를 읽으면 알 수 있고, 배포하지 않는 한 변하지 않는다. 메서드 안에 외부 PG 호출이 있는지, 계산이 자바에 있는지 SQL에 있는지, 여러 테이블을 만지는지는 전부 정적으로 확인되는 사실이다.

2-1. 결정적 사례 — 빈도 축이 원리적으로 잡아내지 못하는 오류

bad 충돌은 하루에 한 번뿐이다. "드무니까 낙관적 락"이라고 판단하면?
@Transactional
public void purchase(Long stockId, Long userId) {
    Stock stock = stockRepository.findById(stockId).orElseThrow();
    paymentGateway.charge(userId, 10_000);     // ← 임계 구간 안의 외부 결제 호출. 되돌릴 수 없다
    stock.decrease(1);
}   // ← 여기서 충돌 → 재시도 → charge()가 또 호출된다
낙관적 락의 재시도는 UPDATE 한 번의 재실행이 아니라 비즈니스 로직 전체의 재실행이다 그래서 하루 한 번의 충돌이 하루 한 건의 이중 결제가 된다. "빈도가 낮다"는 사실은 이 선택이 틀렸다는 것을 전혀 알려주지 못했다. 반면 "임계 구간 안에 되돌릴 수 없는 외부 호출이 있다"는 것은 코드를 읽으면 즉시 보이는 사실이다.

2-2. 두 축을 나란히 놓으면 왜 순서를 바꿔야 하는지가 보인다

같은 문제를 보는 두 개의 축 — 무엇이 1차 기준이 되어야 하는가
충돌 빈도임계 구간의 내용물
언제 알 수 있나운영에 올려 관측해야 안다코드를 읽으면 지금 안다
시간에 따라변한다 (프로모션·신규 호출자·데이터 증가)배포하지 않으면 안 변한다
판단의 종류양적 — 얼마나 잦은가구조적 — 무엇이 들어 있는가
놓치는 것빈도가 낮아도 틀린 선택 (위의 이중 결제)같은 구조 안에서의 정도 차이

축의 사용 규칙 — 버리는 게 아니라 순서를 지키는 것이다

구조를 먼저 보고, 구조가 같은 것들 사이에서 마지막에 빈도를 본다

충돌 빈도 축이 쓸모없다는 뜻이 아니다. 마지막 분기(§5의 Q3)에서 반드시 필요한 축이고, 다만 그 앞의 두 질문을 대신할 수 없을 뿐이다. 이 순서에는 실용적 이점도 있다 — 관측이 필요한 질문이 마지막 하나로 줄어든다. 빈도부터 물으면 설계 회의가 "그건 봐야 알 것 같은데요"에서 멈춘다.

3. 한 무대, 네 가지 풀이 — 임계 구간 지도와 대칭 비교

3-1. 각 방식이 한 문장으로 무엇을 하는 물건인가

비교표로 바로 들어가면 "모르는 것들끼리의 비교"가 된다. 네 방식의 정체를 먼저 한 문장씩 세워둔다.

① 낙관적 락 @Version
아무것도 잠그지 않고, 쓸 때 "그 사이 아무도 안 바꿨는지"를 확인하는 방식. UPDATE의 WHERE에 and version = <읽었을 때의 값>을 붙이고, 조건이 거짓이면 영향 행 수 0 → 충돌 판정 → 예외. "충돌은 드물 것"이라고 낙관해서 미리 잠그지 않는다.
막는(prevention) 것이 아니라 감지(detection)한다.
② 비관적 락 select ... for update
읽는 순간부터 DB에게 그 행을 잠가달라고 요청하는 방식. 커밋할 때까지 다른 트랜잭션은 같은 행을 잠글 수 없어 대기한다. "충돌이 날 것"이라고 비관해서 미리 잠근다.
실패하는 요청이 없는 대신 기다리는 요청이 생긴다.
③ 원자적 UPDATE
읽기·검증·계산·쓰기를 SQL 한 문장으로 압축해, 애플리케이션이 임계 구간에 들어가지 않게 만드는 방식. 값을 자바로 가져오지 않으므로 "읽고 계산하는 동안 누가 바꿀 틈" 자체가 없다.
원자적 = 더 쪼갤 수 없는 한 덩어리로 실행된다.
④ 분산 락 (Redis)
DB 밖의 조정자에게 "이 키는 지금 내가 쓴다"고 등록하고, 등록에 성공한 하나만 들여보내는 방식. 락이 DB 밖에 있으므로 DB 한 대의 범위를 넘는 조정이 가능하다 — 여러 DB, 외부 API, 여러 인스턴스.
대신 상호 배제를 보장하지는 못한다(6절).

3-2. 임계 구간 지도 — 네 방식이 같은 축 위에 어디에 선을 긋는가

③에 대해 정직하게 덧붙일 것 — "한 문장이면 락이 마이크로초"는 정확하지 않다 행 락은 문장이 끝날 때가 아니라 커밋할 때 풀린다. 줄어드는 것은 락 보유 구간에 들어 있던 왕복 횟수와 애플리케이션 처리 시간이고, 그 효과가 온전히 나려면 이 트랜잭션이 UPDATE 하나만 하고 즉시 커밋해야 한다. 같은 트랜잭션에서 뒤에 외부 API를 호출하면 락은 그 시간만큼 그대로 잡혀 있다.

3-4. 충돌이 나면 각각 무슨 일이 벌어지는가 — 100개 재고에 동시 100건

① 재시도 폭풍
1라운드: 100건이 전부 version=0을 읽고 계산 후 UPDATE → 1건만 성공, 99건 예외. 2라운드: 99건이 SELECT부터 다시. 성공 1건당 낭비 작업량이 대기 요청 수에 비례하고, 그 비용은 비즈니스 로직 전체의 재실행이다.
② 대기 (재실행 없음)
99건은 재실행하지 않고 그냥 기다린다 — 재시도 폭풍이 사라지는 건 낫다. 문제는 기다리는 동안 무엇을 붙잡고 있느냐다: 스레드 + DB 커넥션 + 열린 트랜잭션. 커넥션 풀이 20인데 대기가 21이면 락과 무관한 로그인·조회 API까지 마비된다.
③ 충돌 개념 자체가 없다
DB가 행 단위로 UPDATE를 직렬화하므로 100건이 순서대로 처리되고, qty가 0이 된 뒤 도착한 요청은 where qty >= 1에 걸리지 않아 영향 행 수 0을 받는다. 재시도 폭풍이 발생할 여지가 구조적으로 사라진다.
④ Redis에서 순서 대기
99건은 애플리케이션 스레드만 쥔 채 Redis에서 순서를 기다린다(Redisson은 pub/sub으로 깨우므로 폴링 부하도 낮다). waitTime을 넘기면 즉시 실패 응답 — 대기 상한을 커넥션과 무관하게 정할 수 있다. 그리고 뚫린다(6절).

같은 "영향 행 수 0"인데 의미가 정반대다 — 여기서 자주 헷갈린다

① 낙관적 락의 영향 행 수 0

"누가 먼저 갔다. 다시 해봐라"
→ 재시도 대상. 사용자에게 실패로 보이면 안 되는 경우가 많다.

③ 원자적 UPDATE의 영향 행 수 0

"재고가 없다"
→ 최종 결론. 즉시 품절 응답. 재시도하면 영원히 실패한다.

같은 신호를 반대로 해석하면 정확히 반대의 사고가 난다 — 낙관적 락의 0을 품절로 처리하면 재고가 있는데 품절 응답을, 원자적 UPDATE의 0을 충돌로 처리하면 품절 상품에 무한 재시도를 하게 된다.

4. 각 선택지가 치르는 대가

임계 구간이 가장 짧고, 재시도가 없고, 코드도 짧다. 그렇다면 왜 모든 재고·포인트 갱신을 원자적 UPDATE로만 처리하지 않는가? 4-1 ~ 4-4가 그 대답이고, 4-5부터는 낙관적 락을 고르면 따라오는 재시도 비용을 같은 잣대로 계산한다.

4-1. 원자적 UPDATE가 포기하는 넷 — 뿌리는 하나다

4-2. 1차 캐시 불일치 — 그리고 clearAutomatically라는 함정

bad DB는 바뀌었는데 조회는 옛날 값

    Stock stock = stockRepository.findById(stockId).orElseThrow();  // qty = 100, 1차 캐시에 적재
    stockRepository.decrease(stockId, 1);                           // DB: qty = 99

    log.info("남은 수량 = {}", again.getQty());   // → 99 가 아니라 100 이 찍힌다
    //   findById 는 1차 캐시에 이미 있는 엔티티를 그대로 돌려준다 (SELECT 자체가 안 나간다)

    if (again.getQty() == 0) notifySoldOut();   // 이 판단은 옛날 값 기준이다

비유 영속성 컨텍스트는 "내가 아까 복사해 둔 서류철"이고, 벌크/원자적 UPDATE는 그 서류철을 안 거치고 원본 장부를 직접 고치는 것이다. 원본은 바뀌었는데 내 손의 사본은 옛날 그대로다.
함정 처방 1: clearAutomatically — 다른 엔티티의 변경이 증발한다
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update Stock s set s.qty = s.qty - :amount where s.id = :id and s.qty >= :amount")

// clearAutomatically = 실행 "후에" 영속성 컨텍스트를 통째로 비운다

    //   커밋해도 order.status 는 UPDATE 되지 않는다. 예외도 안 난다. 조용히 사라진다.

4-3. 갱신 결과를 엔티티에 반영하려면 다시 읽어야 한다

앞 절의 규칙("다시 읽지 않는다")은 지키기가 쉽지 않다. 차감 후 남은 수량으로 무언가를 해야 하는 요구가 자연스럽게 따라붙기 때문이다 — "0이 되면 품절 알림", "10 이하가 되면 재입고 요청", "응답에 남은 수량을 실어달라". 문제는 원자적 UPDATE가 돌려주는 것이 영향 행 수뿐이라는 데 있다.

@Transactional
public int decreaseAndGetRemaining(Long stockId, int amount) {
    int affected = stockRepository.decrease(stockId, amount);
    if (affected == 0) throw new OutOfStockException();

    // ① 1차 캐시에 남아 있으면 SELECT 조차 안 나가고 옛 값을 준다 (4-2)
    // ② em.clear() 로 비우고 다시 읽으면 SELECT 가 한 번 더 나간다
    //    → 왕복 1회로 압축했던 이점이 그만큼 되돌아간다
    // ③ 그 재조회 시점에는 다른 트랜잭션이 또 차감했을 수 있다
    //    → "내가 차감한 뒤의 값"이 아니라 "지금 값"을 읽는다

       "        when :promo = true then :amount * 2 " +
       "        else :amount end) " +
       " where s.id = :id " +
       "   and s.qty - (case when :grade = 'VIP' then :amount " +
       "                     when :promo = true then :amount * 2 " +
       "                     else :amount end) >= :reserved")
int decrease(...);

여기서 잃는 것 셋

  • 단위 테스트가 불가능해진다 — case when 안의 규칙은 DB를 띄워야만 검증된다. 엔티티 메서드였다면 new Stock(...).decrease(VIP, 2) 한 줄로 끝났다.
  • 재사용이 안 된다 — 같은 정책이 주문 취소·관리자 수동 조정·배치 정산에도 필요하면 쿼리를 복붙하게 되고, 셋 중 하나만 고치는 사고가 난다.
  • 규칙이 어디 있는지 아무도 모른다 — 도메인 규칙을 찾으려면 엔티티가 아니라 리포지토리 인터페이스의 문자열을 뒤져야 한다.
good 규칙은 엔티티에, SQL에는 "최소한의 원자성 조건"만
public class Stock {
    public int calcDecreaseAmount(Grade grade, boolean promo, int base) {
        // 정책은 여기 산다. 테스트도 여기서 끝난다.
        if (grade == VIP) return base;
        return promo ? base * 2 : base;
    }
}

// 계산은 자바에서, 원자성만 DB 에서
int amount = stock.calcDecreaseAmount(grade, promo, base);   // 순수 계산 (락 불필요)
int affected = stockRepository.decrease(stockId, amount);    // 원자적 갱신

누수를 막는 규칙

계산을 SQL로 옮기는 게 아니라, 계산 결과를 파라미터로 넘기고
SQL에는 where qty >= :amount라는 원자성 조건만 남긴다
한계선 계산에 그 행의 현재 값이 필요해지면 분리가 깨진다
// "남은 수량이 10 이하면 2배로 차감한다" — 이 규칙은 위의 분리로 표현할 수 없다
int amount = (stock.getQty() <= 10) ? base * 2 : base;
//                 ↑ 이 값을 읽는 순간, 읽기와 쓰기 사이에 틈이 생긴다
//                   그 틈에 다른 트랜잭션이 qty 를 11에서 9로 바꾸면
//                   내 계산은 이미 틀린 전제 위에 서 있다
int affected = stockRepository.decrease(stockId, amount);
이 순간이 곧 락으로 넘어갈 신호다 필요한 것은 읽기와 계산이 임계 구간 안에 들어가는 것이고, 그것이 바로 낙관적/비관적 락이 제공하는 것이다. 판단 플로우의 Q2가 "아니오"로 떨어지는 지점(5절)이다.

4-5. 표현력이 급락하는 네 가지 모양

원자적 UPDATE가 잘 맞는 모양은 "단일 행의 숫자 필드 하나를, 그 필드에 대한 단순 조건으로 증감"이다. 여기서 한 발짝만 벗어나도 급격히 나빠진다.

여러 필드를 함께 갱신
재고 차감 + 예약 수량 증가 + 최종 판매일 갱신 — 한 문장에 다 넣을 수는 있지만 읽을 수 없는 쿼리가 된다.
다른 테이블의 상태에 조건
"상품이 판매중이고, 이벤트 기간이고, 회원이 구매 자격이 있을 때만" — 서브쿼리로 밀어 넣으면 성능도 가독성도 무너진다.
차감 결과에 따라 분기
"0이 되면 품절 이벤트 발행" — 영향 행 수만으로는 "0이 됐는지"를 알 수 없다(4-3).
@Version을 안 올린다
같은 엔티티를 낙관적 락으로도 보호 중이라면, 이 UPDATE는 버전을 올리지 않아 다른 트랜잭션이 이 변경을 감지하지 못한다.
처방 마지막 항목만은 해결책이 있다 — Hibernate HQL의 update versioned
@Modifying
@Query("update versioned Stock s set s.qty = s.qty - :amount " +
       "where s.id = :id and s.qty >= :amount")
int decreaseVersioned(@Param("id") Long id, @Param("amount") int amount);
// 벌크 UPDATE 가 @Version 컬럼을 함께 증가시키도록 지시한다.
// 이 키워드가 없으면 SQL 에 s.version = s.version + 1 을 직접 써야 한다.
// 주의: JPA 표준이 아니라 하이버네이트 확장이고, @Version 필드를 가진 엔티티에만 쓸 수 있다.
원자적 UPDATE는 "읽고 계산하고 쓴다"가 정말로 한 문장으로 압축될 때만 최고의 선택이다
압축이 안 되는 걸 억지로 압축하면, 압축한 것은 SQL이 아니라 도메인 모델이다

4-6. 낙관적 락이 청구하는 비용 — 재시도는 무엇에 비례하는가

재시도 비용 = 비즈니스 로직 전체의 재실행 비용이다. UPDATE 한 번을 다시 하는 것이 아니다. 낙관적 락은 커밋 시점에 충돌을 알게 되므로, 그 트랜잭션에서 한 일이 전부 무효가 되고 처음부터 다시 해야 한다.

여기서 네 방식 비교의 핵심 통찰이 나온다 재시도 비용은 임계 구간의 길이에 비례한다. 그리고 임계 구간의 내용물은 2절에서 본 것처럼 지금 코드를 읽으면 아는 값이다. 즉 재시도 비용은 관측하지 않고도 지금 추정할 수 있다.
임계 구간의 내용물 → 1회 재시도 비용 → 낙관적 락 적합도
임계 구간의 내용물1회 재시도 비용낙관적 락 적합도
필드 하나 읽고 빼기수십 마이크로초매우 적합 — 사실 이 경우는 ③이 더 낫다
여러 필드 읽고 자바 계산수백 마이크로초 ~ 밀리초적합 — ①의 전형
무거운 조회 + 여러 테이블수 ~ 수십 밀리초충돌이 잦으면 ②로 — 재시도가 DB 부하를 증폭
외부 API 호출 포함API 지연 + 부수 효과 반복부적합 — 중복 결제 (4-8)

두 번째 비례 관계가 있다. 낭비되는 총 작업량은 동시에 대기 중인 요청 수에도 비례한다. 100건이 동시에 들어오면 1건이 성공할 때마다 나머지 전부가 재실행되므로, 총 재실행 횟수가 요청 수의 제곱에 가깝게 자란다. 이것이 "충돌이 잦으면 낙관적 락이 나쁘다"의 정확한 이유다 — 나쁜 이유는 실패해서가 아니라, 실패가 자원을 소모하기 때문이다.

낙관적 락은 CPU와 DB 쿼리를 낭비하고, 비관적 락은 커넥션을 낭비한다
비관적 락에서 대기하는 99건은 아무 일도 하지 않고 기다린다 — CPU도 DB도 쓰지 않는다

4-7. 재시도 코드가 부르는 숙제 — 결론 세 줄

낙관적 락을 고르면 재시도 코드를 써야 하고, 여기가 실무에서 가장 많이 틀리는 코드다. 메커니즘과 올바른 코드 전문은 10-optimistic-vs-pessimistic-lock.md §1-8 ~ §1-11에 있으므로 여기서는 결론 세 줄만 옮긴다 — 이 문서의 관심사는 "재시도가 필요한 방식을 고른다는 것이 무슨 비용을 부르는가"이기 때문이다.

1
재시도는 트랜잭션보다 바깥에 있어야 한다. 낙관적 락 예외는 커밋 시점에 터지므로 @Transactional 메서드 안의 for 루프는 예외를 잡을 기회조차 없다. 게다가 하이버네이트가 찍은 rollback-only 표시는 catch로 예외를 삼켜도 지워지지 않아, 루프가 성공한 것처럼 보여도 커밋에서 UnexpectedRollbackException이 터진다.
2
매 회차가 새 영속성 컨텍스트여야 한다. 트랜잭션만 밖으로 빼고 컨텍스트를 그대로 두면, findById가 1차 캐시의 옛 version 엔티티를 그대로 돌려줘 몇 번을 돌아도 같은 실패를 반복한다.
3
재시도 담당 빈과 트랜잭션 담당 빈을 분리한다. @Retryable과 @Transactional을 같은 메서드에 붙이면 프록시 순서라는 눈에 안 보이는 규칙에 정확성을 맡기게 되고, 같은 클래스 안에서 this.decrease()로 부르면 둘 다 아예 동작하지 않는다.

비교 맥락에서 강조할 것 — 이 세 줄은 낙관적 락을 고른 대가로 팀이 떠안는 숙제 목록이다

원자적 UPDATE에는 이 숙제가 아예 없고(재시도 자체가 없으므로), 비관적 락에도 없다(대기가 재실행을 대신하므로).

"낙관적 락은 평시 비용이 0"이라는 말은 런타임 비용에 한정된 이야기이고,
설계·구현·리뷰 비용은 네 방식 중 가장 크다

이 문서 고유의 각도로 둘만 덧붙인다. ① 재시도 상한과 포기 경로(@Recover)는 반드시 둔다 — 없으면 고경합에서 재시도가 스스로를 먹여 살리는 부하가 된다. ② 트랜잭션 경계를 밖으로 뺄 수 없다면 REQUIRES_NEW로 매 회차를 독립 트랜잭션으로 열어도 되지만, 부모가 커넥션을 쥔 채 자식이 또 하나를 빌리므로 커넥션을 2개씩 쓴다 — 커넥션이 병목인 시스템에서는 이 선택이 비관적 락과 같은 결말로 간다.

4-8. 재시도가 아예 정당하지 않은 경우 — 방식 선택 자체가 틀린 것

재시도는 부수 효과가 없는 로직에만 안전하다. 2절에서 본 그 코드(임계 구간 안의 paymentGateway.charge())가 정확히 이 경우이며, 충돌 빈도가 아무리 낮아도 이 선택은 틀렸다. 해법은 세 갈래다.

1
외부 호출을 트랜잭션 밖으로 빼고 멱등키로 보호한다. 같은 멱등키로 두 번 요청해도 결제는 한 번만 일어나게 만든다. 재시도가 안전해지는 것이 아니라 재시도가 무해해지는 것이다.
2
재고 확보를 먼저 하고 결제를 나중에 한다. 순서를 바꿔 임계 구간에서 외부 호출을 빼낸다. 대신 "재고는 잡았는데 결제가 실패한" 상태를 되돌리는 보상 로직이 필요해진다.
3
분산 락으로 넘어간다. 임계 구간에 DB 밖 자원(PG)이 들어 있다는 것이 확정됐으므로 판단 플로우의 Q1이 "예"가 된다. 다른 세 방식은 이 구간을 조정할 능력이 원리적으로 없다.

5. 판단 플로우 — 가능성 → 구조 → 양의 순서로 좁힌다

판단 3문 3초 암기 — 밖 · 압 · 잦

밖 — DB 밖 자원이 있나?→있으면 ④ 분산 락
압 — 한 문장으로 압축되나?→되면 ③ 원자적 UPDATE (기본값)
잦 — 충돌이 잦은가?→잦으면 ② 비관적 락/드물면 ① 낙관적 락

밖 → 압 → 잦 세 글자가 곧 가능성 → 구조 → 양이다. 순서를 뒤집으면 그 자체가 오답이 되는 구조라, 순서까지 함께 외워야 의미가 있는 암기 장치다.

5-2. Q3의 "잦다"를 감으로 말하지 않는 법 — 행당 초당 건수로 환산한다

Q3까지 왔다면 이제는 양적 판단이 필요하고, 여기서 "느낌상 드뭅니다"로 답하면 2절에서 지적한 문제로 되돌아간다. 필요한 숫자는 세 개다.

① 대상 행의 개수
요청이 몇 개의 행에 흩어지는가
② 초당 쓰기 요청 수
전체 쓰기 트래픽
③ 행을 붙잡는 시간
트랜잭션 하나가 그 행을 붙잡는 시간 = 임계 구간의 길이

사례 A — 회원 10만 명의 포인트 차감

초당 쓰기 1,000건 ÷ 10만 행 = 행당 0.01건/초
임계 구간 1ms → 같은 행에 두 요청이 겹칠 확률이 사실상 0

→ ① 낙관적 락. 재시도 코드가 거의 실행되지 않는다.

사례 B — 한정판 상품 1개 행

초당 쓰기 500건 ÷ 1 행 = 행당 500건/초
임계 구간 1ms → 이론상 초당 1,000건 처리 가능하지만 도착이 균등하지 않으므로 충돌은 예외가 아니라 기본값

→ 낙관적 락은 재시도 폭풍. ② 비관적 락 또는 ③ 원자적 UPDATE.

포화 판정식 — 감을 숫자로 바꾸는 한 줄

행당 초당 건수 × 임계 구간 길이 = 평균적으로 몇 명이 겹치는가

사례 B는 500 × 0.001 = 0.5 — 평균 0.5명이 항상 대기 중이라는 뜻이고, 이 값이 1에 근접하면 시스템이 포화 상태다. 이 계산을 할 수 있으면 "잦다/드물다"가 감이 아니라 숫자가 된다.

6. 분산 락의 정확한 효능과 원리적 한계

6-1. 실질 이점은 "DB 부하 감소"가 아니라 "대기를 커넥션 풀 밖으로 밀어내는 것"

흔한 반론 — 그리고 이 반론은 절반 맞다 "분산 락을 걸어도 UPDATE는 그대로 DB로 나가지 않나요? 그런데 왜 'DB에 영향을 주지 않는다'고 합니까?"
나가는 쿼리 수는 줄지 않는다. 줄어드는 것은 쿼리 수가 아니라 커넥션 점유 시간이다.
분산 락의 이점은 "DB 부하가 준다"가 아니라,
락을 트랜잭션 밖에서 잡음으로써 대기 비용을 DB 커넥션 풀 밖으로 밀어내는 것이다

임계 구간이 아무리 짧아도 요청이 순간에 몰리면 커넥션을 물고 있을 수밖에 없고, 커넥션은 서비스 전체가 공유하는 자원이라 재고 API 하나의 경합이 로그인·조회까지 마비시킨다. 분산 락은 그 대기 줄을 커넥션을 빌리기 전 단계로 옮긴다. 이게 "다른 API를 지킨다"의 정확한 의미다. 비유하자면 은행 번호표 기계다 — 창구(커넥션) 앞에 사람을 세우지 않고 입구에서 번호를 뽑아 기다리게 한다. 창구 수가 한정돼 있어도 다른 업무를 보러 온 사람이 막히지 않는다.

그런데 이 이점은 조건부다 — 락을 트랜잭션 안에서 잡으면 통째로 사라진다 대기 시간이 커넥션 점유 구간 안으로 들어와 비관적 락과 똑같이 풀이 고갈되고, Redis 왕복 2회만 더 붙은 순수한 손해가 된다.
bad 분산 락의 이점이 0이 되는 코드
@Transactional          // ① 트랜잭션 시작 = 여기서 커넥션을 빌린다
public void decrease(Long stockId, int amount) {
    RLock lock = redisson.getLock("lock:stock:" + stockId);
    lock.tryLock(3, 5, TimeUnit.SECONDS);  // ② 커넥션을 쥔 채로 기다린다!
    try {
        Stock stock = stockRepository.findById(stockId).orElseThrow();
        stock.decrease(amount);
    } finally {
        lock.unlock();                       // ③ 락 해제 — 커밋보다 먼저다!
    }
}                                          // ④ 커밋
good 락 획득 → 트랜잭션 시작 → 커밋 → 락 해제
@Service
public class StockFacade {          // @Transactional 없음

    private final RedissonClient redisson;
    private final StockService stockService;   // 이쪽에만 @Transactional

    public void decrease(Long stockId, int amount) {
        RLock lock = redisson.getLock("lock:stock:" + stockId);
        boolean acquired = false;
        try {
            acquired = lock.tryLock(3, 5, SECONDS);  // ① 커넥션은 아직 안 빌렸다
            if (!acquired) throw new LockAcquisitionException();
            stockService.decrease(stockId, amount);   // ② 트랜잭션 시작~커밋이 여기서 끝난다
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        } finally {
            if (acquired && lock.isHeldByCurrentThread()) lock.unlock();  // ③ 커밋 후
        }
    }
}

순서가 틀리면 — unlock()이 커밋보다 먼저면 락을 걸고도 lost update가 난다

6-2. 순서를 정확히 지켜도 분산 락은 뚫린다 — 구현 버그가 아니라 원리적 한계

경로 2 — Redis 노드 장애와 페일오버

Redis의 복제는 비동기다. 마스터는 레플리카의 확인을 기다리지 않고 SET NX에 성공을 먼저 돌려준다. 그 직후 마스터가 죽고 레플리카가 승격되면 승격된 노드에는 그 락이 없다. 그래서 B의 SET NX도 성공한다.

"마스터가 응답했다"가 "그 데이터가 살아남는다"를 뜻하지 않는다. 여러 Redis 노드에 동시에 락을 거는 Redlock이 이 경로를 겨냥해 제안됐지만, 경로 1(프로세스 정지)은 여전히 닫지 못한다.

경로 3 — 락을 아예 거치지 않는 경로 가장 자주 실현된다

애플리케이션 인스턴스는 락을 확인하고 DB에 간다. 그런데 배치 잡, 운영자의 콘솔 SQL, 다른 팀의 마이크로서비스는 락을 안 거치고 곧장 DB로 간다.

락은 "모두가 지키기로 한 약속"일 뿐이고, DB가 강제하는 것이 아니다. 약속을 모르는 참가자를 막을 방법이 없다 — 새로 합류한 팀원이 락 없이 부르는 코드를 추가하는 것만으로도 뚫린다.

뚫리는 3경로 암기 — 만 · 복 · 밖

만료 — TTL/leaseTime (GC 정지) 복제 — 비동기 복제 중 페일오버 밖 — 락을 아예 안 거치는 경로
이것이 이른바 Redlock 논쟁의 핵심이다
요지는 "Redis 락이 쓸모없다"가 아니라 — 프로세스 정지와 시계 오차가 존재하는 이상 타임아웃 기반 락은 상호 배제를 보장할 수 없으므로, 정확성이 걸린 곳에는 쓰지 말라는 것
Redis 분산 락은 "대부분의 요청이 줄을 서게 해서 경합을 줄이는" 최적화 장치다
정합성의 최종 보증은 항상 DB가 해야 한다

두 겹의 최후 방어선을 반드시 같이 건다

good 조건부 UPDATE + CHECK 제약 — 둘 다 거는 이유가 다르다
-- 1) 조건부 UPDATE — 애초에 음수가 될 UPDATE 를 성립시키지 않는다
update stock set qty = qty - ? where id = ? and qty >= ?;
--                                            ^^^^^^^^^^ 락이 뚫려도 이 조건은 DB 가 원자적으로 판정한다

-- 2) CHECK 제약 — 위 조건을 빠뜨린 코드 경로(수동 SQL, 배치, 신규 기능)까지 막는다
ALTER TABLE stock ADD CONSTRAINT ck_stock_qty CHECK (qty >= 0);
왜 두 개를 다 걸어야 하는가 — 막는 범위가 다르다
뚫리는 경로where qty >= ?가 막나?CHECK 제약이 막나?
1) TTL 만료막는다막는다
2) 노드 장애·페일오버막는다막는다
3) 락을 안 거치는 경로못 막는다 (그 쿼리를 안 쓰므로)막는다 (DB 엔진이 강제하므로)

락이 뚫려도, 조건을 빠뜨린 새 코드가 배포돼도, 운영자가 콘솔에서 실수해도 재고는 음수가 되지 않는다. 이것이 "DB를 최후 보루로 삼는다"의 구체적 형태다.

6-3. fencing token — 늦게 도착한 쓰기를 저장소가 스스로 거부하게 만든다 가산점

경로 1(락 만료로 인한 "유령 작업자")을 원리적으로 막는 방법이 있다. 락 서비스가 락을 줄 때마다 단조 증가하는 번호(fencing token)를 함께 발급하고, 실제 저장소가 자기가 본 것보다 작은 번호의 쓰기를 거부하게 하는 것이다. 울타리(fence)를 세워 뒤늦은 것을 걸러낸다는 뜻에서 붙은 이름이다.

흐름 유령 작업자 A(token=33)가 조용히 거부되는 과정
t=0     A 가 락 획득 → token = 33
t=0.3   A 가 GC 로 정지
t=5.0   락 만료
t=5.1   B 가 락 획득 → token = 34
t=5.5   B 가 UPDATE (fence_token 을 34 로 기록)
t=6.3   A 가 깨어나 UPDATE 시도 (token = 33)
        → DB 의 fence_token 은 이미 34
        → where fence_token < 33 이 거짓
        → 영향 행 수 0 → 조용히 거부된다
SQL 저장소가 스스로 판정한다
update stock
   set qty = qty - ?, fence_token = ?      -- 34
 where id = ?
   and qty >= ?
   and fence_token < ?;                  -- 34
도입 비용도 같이 말하는 편이 낫다 락 서비스가 단조 증가 번호를 발급해야 하고(Redis INCR로 만들 수 있다), 모든 테이블에 fence_token 컬럼과 조건이 추가되며, 그 조건을 빠뜨린 경로는 여전히 뚫린다. 경로 3은 fencing token으로도 안 막힌다 — CHECK 제약이 마지막 방어선이라는 결론은 그대로다.
이 개념을 알고 있으면 답변의 단계가 하나 올라간다 "분산 락은 뚫린다"에서 멈추지 않고 "그래서 어떻게 하느냐"까지 답할 수 있다. 다만 "원리적 해법 → 도입 비용 → 그래도 남는 구멍(경로 3) → 그래서 CHECK"까지 한 호흡으로 가야 도구 자랑이 아니라 판단으로 들린다.

7. 사지선다가 아니다 — 층 쌓기와, 층으로도 안 되는 트래픽

질문이 "각각으로 풀 때"라서 네 개 중 하나를 고르는 문제로 오해하기 쉬운데, 실무의 답은 대개 조합이다. 각 층이 막는 것이 다르기 때문이다.

3층 방어 암기 — 락 · 조건 · 제약

락 = 진입 제어 (장애 격리)→ 조건 = where qty >= ? (초과 차감 차단)→ 제약 = CHECK (qty >= 0) (마지막 그물)
층은 §5의 판단 플로우가 요구하는 만큼만 쌓는다 — 다만 3층(DB 제약)만은 언제나 깐다

7-2. 트래픽이 극단적이면 네 가지 모두 답이 아닐 수 있다 가산점

선착순 1,000명 이벤트에 초당 5만 요청이 들어온다고 하자. 네 방식 중 무엇을 써도 결국 DB의 그 행 하나에 요청이 직렬화된다.

초당 처리량 ≒ 1 ÷ 임계 구간 길이
임계 구간이 0.5ms면 1 / 0.0005 = 2,000 — 초당 2,000건이 상한이다. 5만 건은 애초에 DB 앞에 세울 물량이 아니다.

이때는 질문을 바꾼다 — "어떤 락을 쓸까"가 아니라 "DB를 때리지 않고 수량을 선점할 수 있나"로.

good Redis를 "락"이 아니라 "카운터"로 쓴다
Long remaining = redisTemplate.opsForValue().decrement("event:stock:1");
if (remaining == null || remaining < 0) {
    redisTemplate.opsForValue().increment("event:stock:1");   // 되돌리고
    return SOLD_OUT;                                          // 즉시 품절 응답
}
// 여기까지 온 요청만 "당첨". 확정은 큐에 넣어 비동기로 처리한다
eventPublisher.publish(new StockReservedEvent(userId, productId, remaining));

왜 되는가

  • DECR는 Redis 단일 스레드에서 원자적으로 실행되므로 락 없이도 정확히 센다. 락이 아니라 카운터로 쓰는 것이 핵심이다 — 락은 "구간을 보호하는" 물건이고 카운터는 "수량을 세는" 물건인데, 이 문제에서 실제로 필요했던 것은 후자였다.
  • 당첨자 1,000명만 DB로 흘러간다. 나머지 49,000건은 Redis에서 끝난다. DB에 도달하는 트래픽 자체를 1/50로 줄인 것이지, 락을 더 빠르게 만든 게 아니다.
  • 최종 확정은 여전히 DB 제약이 지킨다. Redis 카운터도 장애로 어긋날 수 있으므로, 비동기 확정 단계에서 update ... where qty >= 1 + CHECK를 그대로 통과시킨다 — 7-1의 3층 구조가 여기서도 유지된다.

포기하는 것

  • 응답이 "당첨됐습니다(처리 중)"라는 잠정 상태가 되므로 UX와 후속 알림 설계가 필요하다.
  • Redis와 DB 사이에 정합성 보정 로직이 생긴다 — 미확정 건 재처리, 실패 시 카운터 복구.
  • 이 복잡도를 감당할 만큼 트래픽이 극단적일 때만 정당한 선택이다. 평상시 재고 차감에 이 구조를 쓰면 과한 설계다.

8. 검증 — 말이 아니라 테스트로 고정한다

"이 방식이 동시성에 안전합니다"를 말로 하면 아무 보장이 안 된다. 동시성 버그는 평소에 안 나고 트래픽이 몰릴 때만 나기 때문이다. 네 방식을 비교했다면 비교 결과를 테스트로 고정하는 데까지 가야 한다.

good 네 방식을 같은 테스트로 돌려 숫자로 비교한다
@SpringBootTest
class StockConcurrencyComparisonTest {

    @Autowired StockRetryFacade optimistic;         // ① 낙관적 락 + 재시도
    @Autowired StockPessimisticService pessimistic;  // ②
    @Autowired StockAtomicService atomic;           // ③
    @Autowired StockFacade distributed;             // ④
    @Autowired TransactionTemplate txTemplate;      // 테스트에 @Transactional 을 붙이지 않는다

    @BeforeEach
    void setUp() {
        // 픽스처는 "커밋되는" 트랜잭션으로 만들어야 다른 스레드에서 보인다
        stockId = txTemplate.execute(s -> stockRepository.save(new Stock(1L, 100)).getId());
    }

    @ParameterizedTest @MethodSource("approaches")
    void 어떤_방식이든_재고는_정확히_0이_되고_음수가_되지_않는다(String name, Consumer<Long> decrease) throws Exception {
        int threads = 100;
        ExecutorService pool = Executors.newFixedThreadPool(32);
        CountDownLatch ready = new CountDownLatch(threads);
        CountDownLatch start = new CountDownLatch(1);       // ← 동시 출발 신호
        CountDownLatch done  = new CountDownLatch(threads);
        AtomicInteger success = new AtomicInteger(), failure = new AtomicInteger();

        for (int i = 0; i < threads; i++) {
            pool.submit(() -> {
                ready.countDown();
                try {
                    start.await();                  // 전원이 여기서 대기하다가 한꺼번에 출발
                    decrease.accept(stockId);
                    success.incrementAndGet();
                } catch (OutOfStockException | StockConflictException | LockAcquisitionException e) {
                    failure.incrementAndGet();      // 실패는 버그가 아니라 관측 대상이다
                } finally { done.countDown(); }
            });
        }
        ready.await();
        long t0 = System.nanoTime();
        start.countDown();                           // 동시 출발!
        assertThat(done.await(60, TimeUnit.SECONDS)).isTrue();
        long elapsedMs = (System.nanoTime() - t0) / 1_000_000;

        // 테스트 스레드의 1차 캐시가 아니라 DB 의 최종 상태를 읽는다
        int finalQty = txTemplate.execute(s -> stockRepository.findById(stockId).orElseThrow().getQty());

        assertThat(finalQty).isEqualTo(100 - success.get());          // 초과 차감이 없다
        assertThat(finalQty).isNotNegative();                         // 음수가 되지 않는다
        assertThat(success.get() + failure.get()).isEqualTo(threads); // 사라진 요청이 없다
        log.info("[{}] 성공={} 실패={} 소요={}ms", name, success.get(), failure.get(), elapsedMs);
    }
}
① 초과 차감이 있는가
@Version을 떼고 돌리면 최종 재고가 0보다 훨씬 크게 남는다 — 그게 lost update의 모습이고, 1절의 그림이 100건 규모로 재현된 것이다. 테스트를 한 번 실패시켜 보는 것까지가 세트다.
② 조용히 사라진 요청이 있는가
성공 + 실패 = 전체가 깨지면 어딘가에서 예외가 삼켜지고 있다.
③ 각 방식의 실제 소요 시간
말로 한 트레이드오프를 숫자로 확인한다. 원자적 UPDATE와 비관적 락의 차이가 실제로 몇 배인지 보고 나면, 면접에서도 근거를 갖고 말할 수 있다.
④ 재시도는 몇 번 만에 끝났는가
이건 단정이 아니라 메트릭으로 노출할 대상이다.

동시성 테스트의 함정 세 가지

1
테스트 클래스에 @Transactional을 붙이면 재현이 안 된다. 픽스처가 커밋되지 않아 다른 스레드에서 안 보이고, 마지막 검증도 테스트 스레드의 1차 캐시에서 옛 값을 읽는다 — DB는 0인데 테스트는 100을 본다. TransactionTemplate으로 커밋되는 픽스처를 만들고 @AfterEach에서 지운다.
2
H2로 검증하면 안 된다. for update의 동작, 데드락 감지, 락 타임아웃, CHECK 제약 지원은 DB 벤더마다 다르다. 동시성 테스트만큼은 Testcontainers로 운영과 같은 엔진을 띄운다. H2에서 통과한 동시성 테스트는 보장의 근거가 되지 못한다.
3
커넥션 풀 크기를 의식한다. 스레드 100개가 전부 FOR UPDATE를 하면 풀 크기만큼만 진입한다. 테스트가 이유 없이 느리다면 그건 버그가 아니라 3-4에서 설명한 커넥션 고갈을 테스트가 그대로 재현한 것이다. 그 시간을 임계값으로 고정해두면 성능 회귀 테스트가 된다.
운영에서는 메트릭으로 이어 붙인다 가산점 어떤 방식을 골랐든 ① 재시도 횟수 ② 충돌률(실패/전체) ③ 락 획득 대기 시간 ④ 락 획득 실패율을 Micrometer 카운터/타이머로 노출한다. 2절에서 "충돌 빈도는 시간에 따라 변한다"고 했던 것이 여기서 실무 처방으로 돌아온다 — "충돌이 드물다"는 전제로 낙관적 락을 골랐다면, 그 전제가 계속 참인지 감시하는 장치가 있어야 선택이 완성된다. 전제가 깨졌을 때(충돌률이 임계치를 넘었을 때) 알림이 오는 것이 선택을 재검토할 신호다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

선택의 1차 기준은?
충돌 빈도가 아니라 임계 구간의 내용물. 빈도는 관측해야 알고 시간에 따라 변하지만, 내용물은 코드를 읽으면 지금 알고 배포 전까지 안 변한다.
판단 3문?
밖 · 압 · 잦 — 밖(DB 밖 자원 → ④) → 압(한 문장 압축 → ③) → 잦(잦으면 ② / 드물면 ①). = 가능성 → 구조 → 양.
네 방식이 지불하는 화폐?
① CPU·DB 쿼리(재실행) / ② DB 커넥션(대기) / ③ 도메인 모델·영속성 컨텍스트 / ④ 인프라 의존·정합성 보증.
②와 ③을 가르는 결정적 차이?
락 보유 구간에 애플리케이션 왕복이 포함되느냐. ②는 SELECT~커밋 전체, ③은 왕복 1회.
영향 행 수 0의 두 얼굴?
① 낙관적 = "누가 먼저 갔다. 다시 해봐라"(재시도) / ③ 원자적 = "재고가 없다"(최종 결론, 즉시 품절).
③이 포기하는 넷의 뿌리?
영속성 컨텍스트를 우회한다. → 1차 캐시 옛 값 / 결과 미수신 / 로직이 SQL로 누수 / 표현력 급락(+ @Version 미갱신).
낙관적 락의 재시도 비용은?
비즈니스 로직 전체의 재실행. 임계 구간 길이에 비례하고 대기 요청 수에도 비례(제곱에 가깝게 자란다).
분산 락 순서 규칙?
락 획득 → 트랜잭션 시작 → 커밋 → 락 해제. 트랜잭션 안에서 잡으면 이점 0 + unlock이 커밋보다 앞서 lost update.
분산 락이 뚫리는 3경로?
만 · 복 · 밖 — TTL 만료(GC 정지) / 비동기 복제 중 페일오버 / 락을 안 거치는 바깥 경로.
3층 방어?
락 · 조건 · 제약 — 분산 락(커넥션 고갈 차단) → where qty >= ?(초과 차감 차단) → CHECK (qty >= 0)(모든 경로).
포화 판정식?
행당 초당 건수 × 임계 구간 길이 = 평균 겹치는 인원. 1에 가까우면 포화. (초당 500건 × 1ms = 0.5)
처리량 상한 공식?
1 ÷ 임계 구간 길이. 0.5ms면 초당 2,000건. 5만 건이면 락 문제가 아니라 "DB 앞에 세울 물량이 아니다" → Redis 카운터.
동시성 테스트 3함정?
테스트에 @Transactional 금지 / H2 금지(Testcontainers) / 커넥션 풀 크기가 결과를 바꾼다.
답변 구조 한 세트?
고른다 → 얻는 것 → 포기하는 것 → 감당할 수 있는 이유 → 이 선택이 깨지는 신호. 이 문항은 지식이 아니라 이 구조를 본다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

네 가지 중 하나만 고르라면 무엇을 고르시겠습니까? 필수힌트: "상황에 따라 다릅니다"만으로 끝내면 회피로 들린다. 기본값 + 깨지는 조건

"상황을 하나 정해주시면 고르겠습니다"가 정직한 첫 반응이지만, 그것만으로 끝내면 회피로 들린다. 기본값을 밝히고, 그 기본값이 깨지는 조건을 같이 말하는 것이 정답 형태다.

모범 답변 "기본값은 원자적 UPDATE입니다. 재고 차감처럼 '읽고 검증하고 계산하고 쓴다'가 SQL 한 문장으로 압축되는 모양이면, 임계 구간이 가장 짧고 재시도가 아예 필요 없기 때문입니다. 대신 포기하는 것은 영속성 컨텍스트와의 일관성, 갱신 결과를 엔티티로 받지 못하는 것, 그리고 도메인 로직이 SQL로 새어 나갈 위험입니다. 그 대가를 감당할 수 있는 이유는 이 쿼리를 쓴 트랜잭션에서 그 엔티티를 다시 읽지 않는다는 규칙 하나로 관리되고, 차감 정책은 엔티티에 두고 계산 결과만 파라미터로 넘기면 누수도 막을 수 있기 때문입니다. 다만 정책이 그 행의 현재 값에 의존하기 시작하면 그 분리가 깨지므로, 그때 낙관적/비관적 락으로 넘어갑니다."
고른다→얻는 것→포기하는 것→감당할 수 있는 이유→이 선택이 깨지는 신호

이 다섯 마디를 한 호흡에 넣는 것이 핵심이다. 이 문항은 지식이 아니라 이 구조를 보는 자리다.

원자적 UPDATE가 임계 구간도 가장 짧고 재시도도 없다면, 왜 모든 재고·포인트 갱신을 그걸로만 처리하지 않나요? 필수힌트: 네 가지를 나열하기 전에 "뿌리는 하나"라고 먼저 말한다

네 가지를 포기하기 때문이고, 뿌리는 하나다 — 영속성 컨텍스트를 우회한다는 것.

① 1차 캐시가 옛 값을 들고 있다. 벌크 연산과 같은 성질이라 변경 감지를 거치지 않고 바로 DB로 나가고, 같은 트랜잭션에서 그 엔티티를 다시 읽으면 1차 캐시의 옛 값이 나온다(SELECT 자체가 안 나간다). @Modifying(clearAutomatically = true)로 해결할 수 있어 보이지만, 컨텍스트를 통째로 비우기 때문에 같은 트랜잭션에서 수정 중이던 다른 엔티티의 변경분까지 조용히 사라진다. 실무적 처방은 벌크성 쿼리를 트랜잭션 마지막에 두거나 별도 트랜잭션으로 분리하는 것이다.

② 갱신 결과를 엔티티로 받을 수 없다. 돌아오는 것은 영향 행 수뿐이라 "차감 후 몇 개 남았는지"를 모른다. 재조회하면 왕복 1회로 압축한 이점이 되돌아가고, 게다가 재조회는 원자적이지 않아 "내가 차감한 결과"가 아니라 "지금 값"을 읽게 된다. PostgreSQL이면 update ... returning qty가 정확한 해법이고, 그 외에는 "성공/실패"만으로 응답을 설계하는 편이 낫다.

③ 자바에서 도메인 규칙을 검증할 수 없어 로직이 SQL로 새어 나간다. 등급별 차감량·프로모션 배수 같은 규칙이 쿼리 문자열의 case when으로 들어가면 단위 테스트가 불가능해지고, 재사용이 안 되고, 규칙이 어디 있는지 아무도 모르게 된다. 처방은 계산은 엔티티에서, SQL에는 where qty >= :amount라는 원자성 조건만. 단 계산에 그 행의 현재 값이 필요해지면 이 분리가 깨지고, 그때가 락으로 넘어갈 신호다.

④ 표현력이 급락한다. 여러 필드 동시 갱신, 다른 테이블 상태 조건, 차감 결과에 따른 분기는 한 문장에 담을 수 없다. 그리고 @Version을 올리지 않아 같은 엔티티를 낙관적 락으로도 보호 중이라면 그 변경이 감지되지 않는다(하이버네이트의 update versioned HQL로 올릴 수는 있다).

비관적 락과 원자적 UPDATE는 둘 다 결국 DB 행 락을 쓰는데, 무엇이 다른가요? 시니어 변별힌트: "락을 언제 잡느냐"가 아니라 "락을 쥐고 있는 동안 무엇을 하느냐"

맞다 — 둘 다 같은 종류의 배타적 행 락을 쓰고, 둘 다 커밋에서 풀린다. 차이는 락을 쥐고 있는 동안 무엇을 하느냐다.

② 비관적 락 — 락 구간에 왕복이 들어간다

SELECT ... FOR UPDATE로 락을 잡은 뒤 값을 애플리케이션으로 가져와 자바에서 계산하고 다시 UPDATE를 보낸다. 그 사이 왕복 2~3회 + JVM 처리 시간 + (재수 없으면) GC 정지가 전부 락 구간 안에 있다.

③ 원자적 UPDATE — 락 구간에 왕복이 1회다

조건 판단과 계산이 DB 엔진 안에서 끝나므로 락 구간에서 "값 전송 + 자바 계산 + UPDATE 전송"이 통째로 빠진다.

결정적 차이는 "락을 거느냐"가 아니라 "락 보유 구간에 애플리케이션 왕복이 포함되느냐"다

그리고 정직하게 덧붙일 것이 하나 있다. 행 락은 문장이 끝날 때가 아니라 커밋할 때 풀린다. 그러니 "한 문장이면 락이 마이크로초만 걸린다"는 정확하지 않다. 줄어드는 것은 락 구간에 들어 있던 왕복 횟수와 애플리케이션 처리 시간이고, 그 효과가 온전히 나려면 이 트랜잭션이 UPDATE 하나만 하고 즉시 커밋해야 한다.

같은 트랜잭션에서 뒤에 외부 API를 호출하면 락은 그 시간만큼 그대로 잡혀 있다 — 원자적 UPDATE를 쓰고도 비관적 락과 다를 바 없는 락 구간이 만들어진다.

영향 행 수 0을 받았습니다. 재시도해야 하나요? 함정힌트: 질문 자체에 정보가 빠져 있다. 무엇을 되물어야 하나

"어느 방식의 0인지에 따라 정반대"라고 되물어야 하는 질문이다.

① 낙관적 락의 0

where version = ?가 거짓이 된 것 = "그 사이 누가 바꿨다". 재시도 대상이다. 이걸 품절로 처리하면 재고가 멀쩡히 있는데 품절 응답을 준다.

③ 원자적 UPDATE의 0

where qty >= ?가 거짓이 된 것 = "재고가 없다". 최종 결론이고 즉시 품절 응답이다. 이걸 충돌로 처리하면 품절 상품에 무한 재시도를 건다.

그래서 코드에서도 이 둘을 다른 예외 타입으로 구분해야 한다. OutOfStockException(최종 실패, 재시도 금지)과 ObjectOptimisticLockingFailureException(일시 실패, 재시도 대상)을 같은 catch로 묶으면 둘 중 하나는 반드시 잘못 처리된다.

주의할 조합이 하나 더 있다. 원자적 UPDATE에 where qty >= ? and version = ?를 같이 걸면 0의 의미가 다시 섞인다 — 재고가 없어서 0인지 버전이 어긋나서 0인지 구분할 수 없다. 두 조건을 한 쿼리에 섞을 때는 실패 원인을 따로 판별할 방법을 반드시 마련해야 한다.

분산 락을 걸었는데 재고가 음수가 됐습니다. 어떻게 된 거죠? 시니어 변별힌트: "구현이 잘못됐나 봅니다"로 시작하면 안 된다. 인식의 출발점부터 다르다

"분산 락은 뚫린다. 그게 정상이다"라는 인식에서 출발해야 한다. Redis 분산 락은 정합성 보증 장치가 아니라 부하 최적화 장치이기 때문이다.

뚫리는 경로는 셋이다(만 · 복 · 밖). ① TTL 만료 — 락을 잡은 스레드가 GC 정지나 DB 지연으로 leaseTime을 넘기면 Redis가 락을 만료시키고 다른 요청이 같은 락을 잡는다. 원래 스레드는 그 사실을 알 방법이 없어 아무것도 모른 채 UPDATE를 실행한다. ② 노드 장애·페일오버 — Redis 복제는 비동기라 마스터가 SET NX에 성공 응답을 준 뒤 복제 전에 죽으면, 승격된 레플리카에는 그 락이 없다. ③ 락을 안 거치는 경로 — 배치, 운영자 수동 SQL, 다른 팀 서비스. 락은 "모두가 지키기로 한 약속"일 뿐이라 약속을 모르는 참가자를 막지 못한다.

여기에 락 획득을 트랜잭션 안에서 해서 unlock()이 커밋보다 먼저 일어난 경우도 흔한 원인이다 — 다음 요청이 커밋 전 값을 읽는다.

그래서 정합성의 최종 보증은 항상 DB여야 한다

두 겹으로 건다 — update ... where qty >= ?(경로 1·2는 막지만 그 쿼리를 안 쓰는 경로 3은 못 막는다)와 CHECK (qty >= 0)(어떤 경로로 들어오든 지킨다). 이 둘이 있으면 락이 몇 번 뚫려도 재고는 음수가 되지 않고, 뚫린 요청은 영향 행 수 0 = 품절로 안전하게 실패한다. (가산점) 원리적으로 막고 싶다면 fencing token — 락 발급 시 단조 증가 번호를 주고 저장소가 and fence_token < ?로 늦게 도착한 쓰기를 스스로 거부하게 한다. 다만 이것도 경로 3은 못 막으므로 CHECK가 마지막 방어선이라는 결론은 그대로다.

낙관적 락 재시도를 @Transactional 메서드 안에서 for 루프로 감쌌습니다. 문제가 있나요? 시니어 변별힌트: 문제가 두 겹이다. 하나만 고치면 여전히 안 된다

두 가지 문제가 겹쳐 있고, 하나만 고치면 여전히 안 된다.

첫째, rollback-only 마킹. 트랜잭션 도중 낙관적 락 예외가 나면 트랜잭션에 "롤백만 가능" 표시가 찍힌다. catch로 삼켜도 표시는 지워지지 않아, 루프가 성공한 것처럼 보여도 커밋 시점에 UnexpectedRollbackException이 터진다. 예외를 잡았다고 없던 일이 되지 않는다. 게다가 낙관적 락 예외는 원래 커밋 시점에 터지므로, saveAndFlush()로 앞당기지 않으면 애초에 잡을 기회조차 없다.

둘째, 1차 캐시에 남은 옛 version. rollback-only를 피하려고 트랜잭션을 루프 밖으로 빼도, 영속성 컨텍스트가 같으면 findById가 DB로 SELECT를 보내지 않고 캐시의 옛 엔티티를 그대로 돌려준다. 그래서 두 번째 시도에서도 version = 3으로 UPDATE를 날리고, 다섯 번을 돌아도 똑같은 실패를 반복한다.

올바른 형태는 새 트랜잭션 + 새 영속성 컨텍스트다. 재시도 담당 빈(@Retryable, @Transactional 없음)과 트랜잭션 담당 빈(@Transactional)을 분리하면, 실패 시 트랜잭션이 롤백되면서 영속성 컨텍스트가 통째로 폐기되고 다음 호출이 정말로 DB에서 최신 version을 읽는다 — 두 문제가 동시에 풀린다. 여기에 지수 백오프 + 지터(실패한 요청들이 정확히 같은 시각에 깨어나 또 부딪히는 thundering herd 방지)와 재시도 상한 + @Recover 포기 경로를 붙인다. REQUIRES_NEW로도 같은 효과를 낼 수 있지만 커넥션을 2개씩 쓴다는 점을 계산에 넣어야 한다.

네 방식 비교의 관점에서 한 줄 덧붙이면 좋다 — 이 숙제 목록은 낙관적 락을 고른 대가다. 원자적 UPDATE와 비관적 락에는 이 숙제가 아예 없으므로, "낙관적 락은 평시 비용 0"이라는 말은 런타임 비용에 한정된 이야기이고 설계·구현·리뷰 비용은 네 방식 중 가장 크다. (코드 전문과 프록시 순서 문제는 10-optimistic-vs-pessimistic-lock.md §1-8 ~ §1-11.)

분산 락을 걸어도 UPDATE는 그대로 DB로 나갑니다. "DB 부하가 준다"는 게 정확히 무슨 뜻인가요? 시니어 변별힌트: 반론을 절반 인정하고 시작한다. 줄어드는 것은 쿼리 수가 아니다

반론이 절반 맞다 — 쿼리 수는 줄지 않는다. 줄어드는 것은 커넥션 점유 시간이다. 정확한 표현은 "락을 트랜잭션 밖에서 잡음으로써 대기 비용을 DB 커넥션 풀 밖으로 밀어내는 것"이다.

임계 구간이 아무리 짧아도 순간에 요청이 몰리면 커넥션을 물고 있을 수밖에 없고, 커넥션은 서비스 전체가 공유하는 자원이라 재고 API 하나의 경합이 로그인·조회까지 마비시킨다. 분산 락은 대기 줄을 커넥션을 빌리기 전 단계로 옮겨 그 전파를 끊는다. 부수적으로 대기 상한(waitTime)을 커넥션과 무관하게 정할 수 있다는 이점도 생긴다.

이건 "DB를 편하게 해주는 장치"가 아니라 "장애 격리 장치"다

그리고 이 이점은 조건부다. 락을 @Transactional 안에서 잡으면 대기 시간이 커넥션 점유 구간 안으로 들어와 비관적 락과 똑같이 풀이 고갈되고, Redis 왕복 2회만 더 붙은 순수한 손해가 된다. 게다가 unlock()이 커밋보다 먼저 일어나 다음 요청이 커밋 전 값을 읽는 lost update까지 생긴다. 순서는 반드시 락 획득 → 트랜잭션 시작 → 커밋 → 락 해제여야 한다.

선착순 1,000명 이벤트에 초당 5만 요청이 예상됩니다. 네 가지 중 무엇을 쓰시겠습니까? 가산점힌트: 질문의 전제부터 거부한다. 그리고 계산으로 근거를 댄다

"네 가지 중에는 답이 없습니다"가 출발점이다. 무엇을 쓰든 DB의 그 행 하나에 요청이 직렬화되고, 처리량 상한은 대략 1 ÷ 임계 구간 길이다. 임계 구간이 0.5ms면 초당 2,000건이 한계이므로 5만 건은 애초에 DB 앞에 세울 물량이 아니다.

그래서 질문을 바꾼다 — "어떤 락을 쓸까"가 아니라 "DB를 때리지 않고 수량을 선점할 수 있나"로. Redis DECR로 수량을 선점하고(단일 스레드에서 원자적으로 실행되므로 락 없이도 정확히 센다), 음수가 나오면 INCR로 되돌리고 즉시 품절 응답을 준다. 여기까지 온 1,000건만 큐에 실려 DB로 흘러가고, 나머지 49,000건은 Redis에서 끝난다. 락을 빠르게 만든 게 아니라 DB에 도달하는 트래픽 자체를 1/50로 줄인 것이다.

여기서 Redis는 락이 아니라 카운터로 쓰인다는 점이 핵심이다 — 락은 구간을 보호하는 물건이지만 이 문제에서 필요했던 것은 수량을 세는 물건이었다. 최종 확정은 여전히 where qty >= 1 + CHECK 제약이 지킨다.

포기하는 것도 같이 말해야 한다 — 응답이 "처리 중"이라는 잠정 상태가 되어 UX와 알림 설계가 필요해지고, Redis와 DB 사이 정합성 보정 로직(미확정 건 재처리, 실패 시 카운터 복구)이 생긴다. 이 복잡도를 감당할 만큼 트래픽이 극단적일 때만 정당하다. 평상시 재고 차감에 이 구조를 쓰면 과한 설계다.

이 네 가지는 서로 배타적인가요? 필수힌트: "각 층이 무엇을 막고 무엇을 못 막는지"를 짝으로 말한다

아니다. 실무의 답은 대개 층을 쌓는 것이다. 각 층이 막는 것이 다르기 때문이다.

1
1층 진입 제어(분산 락 또는 Redis 카운터) — 커넥션 풀이 대기로 고갈되는 것을 막지만 정합성은 못 지킨다.
2
2층 원자적 갱신(where qty >= ?) — 1층이 뚫렸을 때의 초과 차감을 막지만 그 쿼리를 안 쓰는 경로는 못 막는다.
3
3층 DB 제약(CHECK, 유니크) — 모든 경로를 막는 마지막 방어선.

각 층은 위층이 실패했다고 가정하고 설계된다. 여기에 두 가지를 더 붙이면 좋다.

첫째, 과한 층 쌓기도 나쁜 설계다. 충돌이 하루 몇 건인 관리자 화면에 분산 락을 도입하면 인프라 의존과 실패 모드만 늘어난다. 층은 판단 플로우가 요구하는 만큼만 쌓는다.

둘째, 그럼에도 3층만은 언제나 깐다 — CHECK 제약은 비용이 사실상 0이고 어떤 선택을 하든 마지막 그물이 되기 때문이다.

충돌 빈도로 고르면 안 된다면, 그 축은 아예 쓸모없는 건가요?힌트: "쓸모없다"가 아니라 "순서"의 문제로 답한다

아니다. 순서의 문제다. 충돌 빈도는 마지막 분기에서 필요한 축이고, 그 앞의 두 질문을 대신할 수 없을 뿐이다.

빈도 축을 1차 기준으로 쓰면 안 되는 이유는 셋이다. ① 지금 알 수 없다 — 운영에 올려 관측해야 나오므로 설계 회의에서는 "느낌상"이 된다. ② 알아낸 값도 변한다 — 프로모션 한 번, 신규 호출자 하나로 하루 3건이 초당 500건이 된다. 선택의 근거가 변하는 값이면 그 선택이 언제 무효가 되는지 알 수 없다. ③ 결정적으로, 빈도가 낮아도 틀린 선택이 있다 — 임계 구간에 외부 PG 호출이 있으면 하루 한 번의 충돌이 하루 한 건의 이중 결제가 된다. 빈도 축은 이 오류를 원리적으로 발견하지 못한다.

반면 임계 구간의 내용물은 지금 코드를 읽으면 알 수 있고 배포하지 않는 한 변하지 않는다. 그래서 가능성(Q1) → 구조(Q2) → 양(Q3) 순으로 좁힌다. 이 순서를 지키면 관측이 필요한 질문이 마지막 하나로 줄어든다는 실용적 이점도 있다.

그리고 Q3까지 왔다면 감으로 말하지 말고 환산한다 — "행 하나당 초당 몇 건인가"다. 회원 10만 명의 포인트 차감은 행당 0.01건/초라 충돌이 사실상 없고, 한정판 상품 1개 행에 초당 500건이면 충돌이 기본값이다. 여기에 임계 구간 길이를 곱하면 평균 몇 명이 겹치는지가 나오고, 그 값이 1에 근접하면 포화다.

원자적 UPDATE로 바꿨더니, 같은 엔티티를 낙관적 락으로 보호하던 다른 기능이 충돌을 감지하지 못합니다. 시니어 변별힌트: 이 UPDATE는 무엇을 건드리지 않는가

원자적 UPDATE는 @Version 컬럼을 올리지 않기 때문이다. 낙관적 락은 "내가 읽은 뒤로 이 행이 바뀌었는가"를 version 값으로 판정하는데, 원자적 UPDATE가 qty만 바꾸고 version은 그대로 두면 다른 트랜잭션 입장에서는 "아무도 안 바꿨다"로 보인다. 그 트랜잭션의 UPDATE는 버젓이 성공하면서 원자적 UPDATE의 결과를 덮어쓴다.

처방은 둘이다. ① 하이버네이트 HQL 확장인 update versioned Stock s set ...를 쓰면 벌크 UPDATE가 @Version을 함께 증가시킨다. JPA 표준이 아니라 하이버네이트 확장이고 @Version 필드를 가진 엔티티에만 쓸 수 있다. ② 네이티브 쿼리라면 set version = version + 1을 직접 쓴다.

다만 더 근본적인 질문을 먼저 해야 한다 — 같은 행을 두 방식으로 보호하고 있다는 사실 자체가 설계 신호다. 한 엔티티에 대한 동시성 전략은 한 가지로 통일하거나, 최소한 "어느 경로가 어느 방식을 쓰는지"가 문서화되고 리뷰에서 강제돼야 한다. 보호 방식이 경로마다 다르면, 새로 추가되는 경로는 거의 확실히 어느 쪽도 안 지킨다 — 이건 6-2의 경로 3(락을 안 거치는 경로)과 같은 종류의 문제다.

3층 방어선의 CHECK 제약에 걸려 예외가 터지면, 사용자에게는 뭐라고 보여주나요? 함정힌트: 이 질문은 UX가 아니라 "각 층의 임무 분담"을 묻고 있다

이 질문의 핵심은 "각 층의 임무가 다르다"는 것이다. CHECK 제약은 마지막 그물이지 사용자 경험을 담당하는 층이 아니다. 사용자에게 보여줄 "품절입니다"라는 정중한 응답은 2층(where qty >= ?의 영향 행 수 0)이 만들어야 한다.

그래서 정상 경로에서는 CHECK 위반이 절대 발생하지 않아야 한다. 발생했다면 그것은 "위층이 실패했다"는 사실을 알려주는 알람이다 — 조건을 빠뜨린 새 코드가 배포됐거나, 락을 안 거치는 경로가 생겼거나, 배치가 직접 UPDATE를 날렸다는 뜻이다.

실무 처방은 이렇다. ① 제약 위반 예외(DataIntegrityViolationException)를 일반적인 500으로 흘려보내지 말고 별도로 잡아 경보를 울린다. ② 사용자에게는 일반적인 실패 응답을 주되, ③ "이 예외가 났다"는 사실 자체를 지표로 만들어 0이 아니면 조사한다. 3층이 발동했다는 것은 데이터가 지켜졌다는 좋은 소식이자, 위층에 구멍이 있다는 나쁜 소식이다 — 두 가지를 동시에 다뤄야 한다.

네 방식 중 사용자에게 실패를 노출하게 되는 것은 무엇인가요?힌트: "실패가 없다"는 방식은 사실 없다. 실패의 성격이 다를 뿐이다

정도의 차이는 있어도 "실패가 아예 없는 방식"은 없다. 성격이 다를 뿐이다.

① 낙관적 락 — 충돌 실패
재시도 상한을 넘기면 "다시 시도해 주세요". 재고가 있는데도 실패하는 것이라 사용자 입장에서 납득이 어렵다.
② 비관적 락 — 대기로 흡수
대부분 기다렸다가 성공하므로 실패가 안 보인다. 대신 응답이 느려지고, 락 타임아웃을 넘기면 그때 실패로 노출된다.
③ 원자적 UPDATE — 품절(정당한 실패)
영향 행 수 0은 "진짜 재고가 없다"는 뜻이라 사용자에게 설명 가능한 실패다. 네 방식 중 실패의 의미가 가장 깨끗하다.
④ 분산 락 — 락 획득 실패
waitTime을 넘기면 "잠시 후 다시 시도해 주세요". 다만 대기 상한을 커넥션과 무관하게 우리가 정할 수 있어 응답 시간을 통제하기 쉽다.

여기서 설계상의 함의가 나온다. ①과 ④의 실패는 "시스템 사정"이고 ③의 실패는 "사실"이다. 전자는 재시도 안내와 백오프가 필요하고, 후자는 즉시 확정적인 안내(품절, 재입고 알림 신청)를 주는 것이 맞다. 이 둘을 같은 에러 화면으로 처리하면 사용자는 "될 때까지 새로고침"을 하게 되고, 그 자체가 고경합 상황을 악화시킨다.

한 줄 요약
선택의 기준은 "충돌 빈도"가 아니라 "임계 구간에 무엇이 들어가는가"다 — 임계 구간은 동시에 한 주체만 들어가야 하는 코드 구간이고, 그 내용물은 코드를 읽으면 지금 알 수 있고 배포하지 않는 한 변하지 않는 반면 충돌 빈도는 관측해야 알 수 있고 시간에 따라 변한다. 임계 구간에 DB 밖 자원(외부 PG·여러 DB·멀티 인스턴스)이 있으면 분산 락, 없다면 읽고·계산하고·쓰는 과정이 SQL 한 문장으로 압축되는지를 묻고 압축되면 원자적 UPDATE가 기본값, 압축이 안 되면 충돌이 잦을 때 비관적 락(대가는 커넥션 점유·데드락), 드물 때 낙관적 락(대가는 로직 전체 재실행과 재시도 코드)이다. 네 방식은 무슨 자원을 소모하는가로 갈린다 — 낙관적 락은 스레드와 재실행 비용, 비관적 락은 커넥션과 열린 트랜잭션, 원자적 UPDATE는 영속성 컨텍스트 일관성과 도메인 모델(1차 캐시가 옛 값을 들고 있고, 갱신 결과를 엔티티로 못 받고, 검증이 SQL 문자열로 새어 나간다), 분산 락은 인프라 의존과 정합성 보증 자체를 내준다. 그래서 Redis 분산 락은 안전장치가 아니라 부하 최적화 장치이며 — TTL 만료(GC 정지), 비동기 복제 중 노드 장애, 락을 아예 안 거치는 경로 셋으로 뚫린다 — 그 이점도 락을 트랜잭션 밖에서 잡을 때만(락 획득 → 트랜잭션 → 커밋 → 락 해제) 성립한다. 정합성의 최종 보증은 언제나 DB — where qty >= ?와 CHECK (qty >= 0)을 함께 걸어 어떤 경로로 뚫려도 음수가 되지 않게 만든다. 그리고 이건 사지선다가 아니라 층 쌓기이며, 그 층이 실제로 작동하는지는 CountDownLatch로 동시 출발시킨 테스트를 실제 DB(Testcontainers)에서 돌려보기 전까지 주장일 뿐이다.
