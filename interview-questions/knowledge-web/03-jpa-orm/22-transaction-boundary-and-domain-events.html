트랜잭션 경계와 도메인 이벤트
"한 트랜잭션에 Aggregate 하나"는 성능 규칙이 아니라 정합성 규칙이다

면접 질문: "하나의 트랜잭션에서 여러 Aggregate를 수정하면 왜 문제가 되나요? 도메인 이벤트 기반으로 어떻게 분리하나요?"

핵심 관전 포인트 — @Transactional 한 줄은 네 개의 경계를 동시에 긋는다 — 정합성 경계 = 락 경합 범위 = 실패 파급 범위 = 커넥션 점유 시간. 넷이 같은 선인 이유는 물리적이다: 락은 커밋·롤백 시점에만 풀리고, 커넥션은 트랜잭션이 끝나야 반납되며, 롤백은 트랜잭션 전체를 되돌리기 때문이다. 애그리거트를 하나 더 넣는 것은 이 넷을 한꺼번에 키우는 결정이고, DDD의 "트랜잭션 하나에 애그리거트 하나" 원칙의 근거가 바로 이것이다. 그래서 이 코드에서 가장 위험한 것은 쿼리가 몇 개 나가느냐가 아니라 메일 API 응답을 기다리는 동안 재고 행의 배타 락을 쥐고 있다는 사실이다 — 명시적 락이 없어도 UPDATE 문 자체가 커밋까지 배타 락을 유지한다. 무엇을 남기고 뺄지는 성능이 아니라 정합성 요구 수준이 정한다: ① 트랜잭션 안에 블로킹 I/O가 있는가 ② 이게 실패하면 주문 자체를 취소해야 하는가. 재고는 남기고 포인트·쿠폰·메일은 이벤트로 뺀다. 블로킹 I/O가 하나도 없어도 큰 트랜잭션은 락 순서 역전으로 데드락을 만들며, 처방은 자원 획득 순서를 전역으로 고정하는 것(Hibernate가 안 지켜주므로 코드로 고정)이다. 마지막으로 분리는 공짜가 아니다 — 즉시 일관성, 추적 가능성, 보상 로직 비용을 내주고 사는 것이며, 그 대가를 갚는 장치가 Outbox + 재처리 + 멱등성 세트다.
  • 1
    선은 하나인데 이름이 넷이다 — @Transactional은 정합성 경계 · 락 경합 범위 · 실패 파급 범위 · 커넥션 점유 시간을 동시에 긋는다. 개발자가 원해서 그은 것은 첫 번째 하나뿐이고 나머지 셋은 덤으로 따라온다. 그래서 애그리거트를 하나 더 넣는 결정은 언제나 네 배로 계산해야 하는 결정이다.
  • 2
    그래서 최대 위험은 쿼리 수가 아니라 "메일 API가 트랜잭션 안에 있다"는 사실이다 — @Lock도 for update도 없지만 UPDATE가 나가는 순간 그 행은 커밋까지 잠긴다. 메일 응답이 3초 걸리면 재고 행 락 3초 + 커넥션 점유 3초이고, 그 지연은 재고와 무관한 API까지 죽이는 커넥션 풀 고갈로 번진다.
  • 3
    경계는 성능이 아니라 정합성 요구가 정하고, 분리는 공짜가 아니다 — 블로킹 I/O가 있는가 / 실패하면 주문을 취소해야 하는가 두 질문으로 자른다. 그리고 쪼갠 대가로 즉시 일관성·추적 가능성·롤백의 단순함을 내놓으므로, Outbox + 재처리 + 멱등성으로 그 값을 갚아야 한다.

0. 질문 + 출제 의도

질문: "하나의 트랜잭션에서 여러 Aggregate를 수정하면 왜 문제가 되나요? 도메인 이벤트 기반으로 어떻게 분리하나요?"

출제 의도: "트랜잭션 경계 = 정합성 경계 = 락 경합 범위"라는 연결을 이해하는지. 큰 트랜잭션이 데드락과 경합의 온상임을 알고 도메인 이벤트로 쪼개는 설계는, 모놀리스에서 MSA로 가는 사고의 전 단계다. 즉 이 문항은 스프링 이벤트 API 사용법을 묻는 자리가 아니다.

보는 것은 셋이다 ① @Transactional이라는 한 줄이 실제로 무엇을 결정하는지  ② 무엇을 남기고 무엇을 뺄지 판단하는 기준을 갖고 있는지  ③ 쪼갠 뒤에 새로 생기는 문제(유실·중복·순서·추적)를 알고 그 값을 치를 준비가 되어 있는지.
함정 세 개 — 이 페이지가 겨냥하는 지점 ① 성능 문제부터 답하는 것 — "getItems()에서 N+1이 날 수 있습니다"는 사실이지만 fetch join 한 줄로 끝나는 국소 문제다. 메일 API가 트랜잭션 안에 있는 것은 장애 하나가 서비스 전체를 마비시키는 구조 문제다(→ 1절).
② "무조건 쪼개야 합니다"로 답하는 것 — 교과서 답이지만 실무 감각이 없어 보인다. 얻는 것과 포기하는 것을 같은 호흡에 말해야 한다(→ 9절).
③ @Async로 빼는 것 — 가장 흔한 오답이고, 트랜잭션이 롤백돼도 메일은 이미 나간다. 커밋 이후로 옮기는 것과 비동기로 미루는 것은 전혀 다른 이야기다(→ 5절).
무대 이 문서 끝까지 같은 코드를 쓴다
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional
    public void completeOrder(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();

        order.complete();                                    // ① 주문 상태 변경
        stockService.decrease(order.getItems());             // ② 재고 차감
        pointService.accumulate(order.getUserId(), order.getAmount());  // ③ 포인트 적립
        couponService.use(order.getCouponId());              // ④ 쿠폰 사용 처리
        notificationService.sendCompleteMail(order);         // ⑤ 완료 메일 발송 (외부 API)
    }
}
벤더 표기 규칙 DB는 PostgreSQL을 기준으로 쓴다. 락·데드락·타임아웃은 벤더마다 기본값과 진단 도구가 다른 영역이라, MySQL 이야기를 할 때는 그렇게 명시한다.

1. 훑는 순서 — 구조 → 경계 → 성능

"이 구조의 문제는?"은 답의 범위를 면접자가 정하라는 질문이다. 이때 가장 최근에 공부한 주제(대개 성능)로 먼저 뛰어드는 것이 전형적인 실수다. 순서를 고정해두면 흔들리지 않는다.

큰 것부터 훑는 3단 스캔 — 구 · 경 · 성

① 구조→② 경계→③ 성능
① 구조
이 메서드가 건드리는 것이 몇 개의 다른 도메인인가? 그중 되돌릴 수 없는 것(메일·결제·외부 시스템)이 있는가?
② 경계

③ 성능
그다음에야 쿼리 수, N+1, 인덱스. 순서를 뒤집으면 "코드는 읽지만 구조는 안 보는 사람"이 된다.
면접에서 첫 문장으로 말할 형태 "문제를 세 층으로 보겠습니다. 가장 큰 문제는 서로 다른 애그리거트 다섯 개가 한 트랜잭션에 묶여 있다는 것이고, 그중에서도 치명적인 것은 외부 메일 API가 트랜잭션 안에 있다는 점입니다. 메일 응답을 기다리는 동안 재고 행의 배타 락과 DB 커넥션을 계속 쥐고 있어서, 메일 서버가 느려지면 그 지연이 그대로 락 대기와 커넥션 고갈로 번집니다. 다음 층은 실패 파급 범위입니다 — 쿠폰 처리 하나가 실패하면 이미 성공한 재고·포인트까지 전부 롤백됩니다. 성능 문제(getItems()의 N+1)도 있지만 그건 fetch join으로 끝나는 국소 문제라 우선순위가 가장 낮습니다."

2. 전제 — 애그리거트는 "함께 결재하는 서류철"

질문에 나오는 "Aggregate"부터 정의하고 가야 나머지가 읽힌다. 애그리거트(aggregate)는 "함께 변경되어야 하는 엔티티들을 하나로 묶은 덩어리"다. 단어 자체가 "모아 놓은 것, 집합체"라는 뜻이고, 도메인 주도 설계(DDD)에서 정합성을 지키는 최소 단위로 쓴다. 각 덩어리에는 대표 엔티티가 하나 있는데 이것을 애그리거트 루트(root)라고 부르고, 바깥에서는 항상 루트를 통해서만 안쪽 엔티티를 만진다.

3. 척추 — @Transactional 한 줄이 긋는 네 개의 경계

@Transactional 한 줄은 "여기부터 여기까지가 하나의 원자 단위"라는 선언처럼 보인다. 그런데 그 선 하나가 실제로는 네 개의 서로 다른 경계를 동시에 긋는다. 이 문항의 모든 답이 여기서 파생된다.

"관련 있으니까 같이 처리하자"는 판단이 실제로는 락 범위와 장애 반경을 함께 늘리는 결정인데, 코드에서는 그 사실이 전혀 보이지 않는다

3-1. ② 락 경합 범위 — 명시적 락이 없어도 락은 잡힌다

여기가 이 문항에서 가장 자주 흔들리는 지점이다. 코드 어디에도 @Lock이나 select ... for update가 없으니 "락은 안 잡혀 있다"고 생각하기 쉽다. 틀렸다.

먼저 용어. 배타 락(exclusive lock)은 "내가 이 행을 쥐고 있는 동안 다른 누구도 이 행을 바꿀 수 없다"는 표시다. 배타적이라는 이름 그대로, 같은 행에 대해 동시에 하나만 존재할 수 있다.

이 한 문장을 외운다

UPDATE 문이 실행되는 순간, 그 행에는 배타 락이 걸리고 커밋 또는 롤백까지 유지된다

이건 애플리케이션이 하는 일이 아니라 DB가 하는 일이고, PostgreSQL도 MySQL(InnoDB)도 마찬가지다. select ... for update는 그 락을 SELECT 시점에 미리 앞당겨 잡는 것일 뿐, 없다고 락이 없는 게 아니다.

왜 그래야 하는지 생각해보면 당연하다. 락을 커밋까지 안 잡으면 아직 커밋되지 않은 값을 다른 트랜잭션이 덮어쓸 수 있고, 그러면 롤백했을 때 무엇으로 되돌려야 하는지 알 수 없다. 커밋 전까지 락을 유지하는 것은 롤백 가능성을 지키기 위한 필연이다.

JPA에서의 정확한 시점 — 조금 짧아질 수는 있지만 성질은 같다 JPA에서는 UPDATE가 나가는 시점이 코드에서 setter를 호출한 순간이 아니라 flush 시점이므로 실제 락 구간은 조금 더 짧을 수 있다. 하지만 flush 이후 커밋까지의 구간은 여전히 통째로 락 구간이고, 지연 로딩이나 JPQL 조회가 중간에 끼면 auto-flush로 락이 더 일찍 잡히기도 한다. 트랜잭션을 짧게 만드는 것 외에 이 구간을 줄이는 방법은 없다.

3-2. 락 점유 타임라인 — 메일을 기다리는 동안 다른 요청은 무엇을 하는가

말로만 하면 "락이 좀 길다" 정도로 들린다. 같은 상품을 사는 다른 주문이 그 구간에 들어오면 무슨 일이 벌어지는지를 그려야 위험이 보인다.

대기가 무한정 이어지지는 않는다. 대신 그 한계가 벤더마다 다르다.

락 대기 상한 — 기본값이 다르다는 사실 자체가 진단 난이도를 가른다
락 대기 상한 설정기본값초과하면
PostgreSQLlock_timeout0 (무한 대기)기본 설정에서는 실패하지 않고 계속 기다린다
MySQL (InnoDB)innodb_lock_wait_timeout50초대기 중이던 트랜잭션이 에러로 실패한다
PostgreSQL의 기본값이 무한 대기라는 사실이 오히려 더 무섭다 실패해서 시끄럽게 알려주는 대신 조용히 쌓이기 때문이다. 그래서 증상이 "특정 API 에러율 증가"가 아니라 "서비스 전체가 느려짐 → 커넥션 풀 고갈 → 전면 장애" 순서로 나타난다. 운영 중인 서비스라면 lock_timeout을 유한한 값으로 설정해 "오래 기다리면 실패하게" 만들어 두는 것이 진단 가능성 면에서 낫다.

3-3. ③ 실패 파급 범위 · ④ 커넥션 점유 시간

③ 실패 파급 — 성공한 것까지 되돌린다

원본 코드에서 ④ 쿠폰 사용이 실패하면 ①②③이 전부 롤백된다. 주문 상태도, 재고 차감도, 포인트 적립도 없던 일이 된다.

여기서 물어야 할 것은 "그게 맞는 동작인가?"다. 쿠폰은 나중에 복구하거나 고객센터가 처리하면 되는 일인데, 지금 구조는 "모두 함께 죽는다"는 정책을 코드가 임의로 정해버린 것이다.

트랜잭션 경계를 넓게 잡는 것은 "이 안에 있는 모든 것은 서로의 실패에 함께 죽는다"고 선언하는 일이다.

④ 커넥션 점유 — 남의 API를 죽이는 경로

@Transactional은 시작 시점에 커넥션을 하나 빌리고 끝날 때까지 반납하지 않는다. 3초짜리 메일 API를 기다린다면 커넥션 하나를 3초 동안 아무 일도 안 시키면서 붙잡고 있는 것이다.

왜 중간에 반납할 수 없나 — 트랜잭션은 커넥션에 묶여 있는 상태다. BEGIN부터 COMMIT까지의 모든 문장이 같은 커넥션에서 실행돼야 하고, 커넥션을 돌려주는 순간 그 트랜잭션은 끝난다. "잠깐 반납했다 다시 빌린다"는 선택지가 애초에 없다.

커넥션은 서비스 전체가 공유하는 자원이라, 여기가 마르면 주문과 무관한 모든 API가 함께 멈춘다.

3-4. 넷은 왜 같은 선인가 — 세 가지 물리적 사실

네 경계를 따로 설명했지만, 정말 중요한 것은 이 넷이 왜 하나의 선으로 겹치느냐다. 우연이 아니라 세 가지 물리적 사실 때문이다.

① 락은 커밋·롤백 시점에만 풀린다
중간에 미리 놓아줄 방법이 없다. → 락 보유 구간의 끝 = 트랜잭션의 끝
② 커넥션은 트랜잭션이 끝나야 반납된다
트랜잭션이 커넥션에 묶여 있기 때문이다. → 커넥션 점유 구간의 끝 = 트랜잭션의 끝
③ 롤백은 트랜잭션 전체를 되돌린다
부분 롤백은 없다(세이브포인트를 명시적으로 쓰지 않는 한). → 실패 파급 범위 = 트랜잭션의 범위

3-5. 그래서 "한 트랜잭션에 애그리거트 하나" — 성능 규칙이 아니라 정합성 규칙

DDD가 "하나의 트랜잭션은 하나의 애그리거트만 수정한다"고 말하는 이유가 여기서 나온다. 그건 미학적 취향이 아니라 위 네 경계를 최소로 유지하기 위한 실용적 규칙이다. 다만 이 규칙이 성능 규칙이 아니라는 점을 정확히 해야 한다.

흔한 오해 — "쪼개면 빨라진다더라"

  • 출발점을 성능에 둔다
  • 그러면 "빠르게 하려고" 재고 차감을 주문 트랜잭션 밖으로 빼는 판단이 나온다
  • 결과: 재고 없이 성립한 주문이 만들어진다
  • 성능을 이유로 정합성 경계를 옮기는 것은 규칙을 지키는 게 아니라 어기는 것이다

실제 논리 — 방향이 반대다

  • 출발점은 "정합성이 즉시 보장되어야 하는 최소 단위는 어디까지인가"라는 질문이다
  • 그 답이 애그리거트다 — 주문 총액과 항목 합계는 한 순간도 어긋나면 안 되니 같은 트랜잭션
  • 그 기준으로 경계를 그으면 결과적으로 트랜잭션이 작아지고 락 경합·장애 반경이 따라서 줄어든다
  • 성능 개선은 부산물이지 목적이 아니다
애그리거트 경계는 성능 예산이 정하는 것이 아니라 업무 규칙이 정한다.
성능은 그렇게 정한 경계를 지킨 결과로 따라온다

그리고 애그리거트 밖의 것들은 결과적 일관성(eventual consistency)으로 맞춘다. 이름 그대로 "지금 당장은 어긋나 있어도 결국에는 맞아떨어진다"는 보장이고, 그 "결국"을 실제로 보장해 주는 장치가 8절의 Outbox와 재처리다.

면접에서 이 한 문장이 척추가 된다 "트랜잭션 경계는 정합성 경계이면서 동시에 락 경합 범위이고, 실패 파급 범위이고, 커넥션 점유 시간입니다. 애그리거트를 하나 더 넣는 것은 이 넷을 한꺼번에 키우는 결정입니다. DDD의 '한 트랜잭션에 한 애그리거트' 원칙은 이 넷을 최소로 유지하라는 실용적 규칙이고요."

4. 무엇을 남기고 무엇을 뺄 것인가 — 기준 두 개 + 한 번 더 묻기

"쪼개라"는 말은 쉽지만, 진짜 질문은 어디를 자르느냐다. 기준 두 개면 충분하고, 거기에 "정말 쪼개야 하나?"를 한 번 더 물으면 실무 감각이 붙는다.

자르는 기준 — 두 개로 자르고, 세 번째로 되묻는다

기준 ① 블로킹 I/O가 있는가
DB 밖 자원을 기다리는 작업은 무조건 밖으로. 메일·SMS·푸시·외부 결제·S3 업로드·다른 팀 API. 응답 시간이 곧 락 시간이자 커넥션 점유 시간이 되고, 그 시간은 내가 통제할 수 없다.
판단이 기계적이라 논쟁의 여지가 없고, 정적 분석으로 강제할 수도 있다(9절 ArchUnit)
기준 ② 실패하면 주문을 취소해야 하는가
"이 작업이 실패했을 때, 방금 완료한 주문을 없던 일로 되돌려야 하는가?"
예 → 같은 트랜잭션. 아니오(나중에 보정 가능) → 이벤트로 분리.
블로킹 I/O가 하나도 없고 전부 단순 DB 변경이어도 남는 질문이다
그리고 세 번째 — "정말 쪼개야 하나?"
기준 둘을 통과했다고 자동으로 쪼개는 것은 아니다. 트래픽이 낮고 데드락 이력이 없는 관리자 기능이라면 한 트랜잭션에 두는 편이 유지보수에 낫다는 판단도 충분히 타당하다.
분리의 정당한 근거는 셋 중 하나 — ① 블로킹 I/O가 있다 ② 실패가 주문을 되돌릴 이유가 안 된다 ③ 트래픽이 높아 락 경합·데드락이 실제로 관측된다
셋 중 아무것도 해당하지 않는데 "이론적으로 옳으니까" 쪼개면, 얻는 것 없이 9절의 비용만 지불하는 설계가 된다
원본 코드의 다섯 작업에 기준 ②를 대보면 — 이 표를 만든 기준이 성능이 아니라는 점이 핵심이다
작업실패하면 주문을 취소해야 하나?결론근거
① 주문 상태 변경— (주문 자신)트랜잭션 안애그리거트 루트 자신
② 재고 차감예트랜잭션 안재고 없이 성립하는 주문은 없다 — 비즈니스 규칙
③ 포인트 적립아니오이벤트나중에 적립해주면 된다
④ 쿠폰 사용아니오이벤트보정 가능(재사용 차단은 별도 안전장치로)
⑤ 메일 발송아니오이벤트(+커밋 후)재발송하면 된다 · 기준 ①에도 걸린다
이 표에서 놓치면 안 되는 것 "재고 차감이 무겁다/가볍다"로 나눈 게 아니다. "재고가 없으면 그 주문은 애초에 성립하지 않는다"는 비즈니스 규칙으로 나눴다. 경계를 정하는 것은 성능이 아니라 정합성 요구 수준이다 — 3-5절의 결론 그대로다.

5. 세 단계 리팩터링 — 락 구간이 줄어드는 과정

같은 completeOrder를 세 번 고쳐 쓰면서 매번 ① 코드 ② 락·커넥션 점유 타임라인 ③ 실패 파급 범위를 같이 본다.

5-1. 1 → 2단계 — 비가역이면서 블로킹인 메일을 커밋 후로

도메인 이벤트(domain event)는 "도메인에서 의미 있는 일이 일어났다는 사실을 담은 값 객체"다. OrderCompletedEvent는 "주문이 완료되었다"는 과거의 사실을 나타내며, 특별한 인터페이스를 구현할 필요도 없다.

이벤트 그냥 값 객체다
public record OrderCompletedEvent(Long orderId, Long userId, int amount, Long couponId) {}
before 트랜잭션 안에서 메일을 부른다
@Transactional
public void completeOrder(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();
    stockService.decrease(order.getItems());
    pointService.accumulate(order.getUserId(), order.getAmount());
    couponService.use(order.getCouponId());
    notificationService.sendCompleteMail(order);
}   // ↑ 이 3초가 그대로 락 시간 + 커넥션 점유 시간
after 발행만 하고, 리스너를 커밋 뒤로 옮긴다
@Transactional
public void completeOrder(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();
    stockService.decrease(order.getItems());
    pointService.accumulate(order.getUserId(), order.getAmount());
    couponService.use(order.getCouponId());
    eventPublisher.publishEvent(new OrderCompletedEvent(...));
}   // 발행만 한다. 아직 아무 일도 안 일어난다
good 리스너 — 커밋 후 + 별도 스레드
@Component
@RequiredArgsConstructor
public class OrderMailListener {

    private final NotificationService notificationService;

    @Async                                                       // 호출 스레드를 막지 않게
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)  // 커밋 확정 뒤에만
    public void onOrderCompleted(OrderCompletedEvent event) {
        notificationService.sendCompleteMail(event.orderId());
    }
}

5-2. @Async만 쓰면 왜 안 되는가 가장 흔한 오답

5-3. 2 → 3단계 — 포인트·쿠폰까지 이벤트로, 그리고 Outbox

after 4절 표대로 재고만 남기고, 나머지는 outbox에 "저장만" 한다
@Transactional
public void completeOrder(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();

    order.complete();                          // ① 주문 자신
    stockService.decrease(order.getItems());   // ② 실패하면 주문이 성립 불가 → 남긴다

    outbox.save(OutboxMessage.of(              // ③④⑤ → 같은 트랜잭션에서 "저장만"
            "OrderCompleted", order.getId(), toJson(OrderCompletedEvent.from(order))));
}   // 커밋: order + stock + outbox 세 쓰기가 원자적으로 함께 확정된다

5-4. 이벤트를 어디서 발행할 것인가 가산점

서비스에서 publishEvent를 직접 부르는 대신, 엔티티가 자기 상태 변화와 함께 이벤트를 등록하게 하면 "상태가 바뀌었는데 이벤트를 안 보냈다"는 누락이 구조적으로 줄어든다. Spring Data JPA의 AbstractAggregateRoot가 그 용도다.

@Entity
public class Order extends AbstractAggregateRoot<Order> {

    public void complete() {
        if (this.status != OrderStatus.PAID) throw new IllegalStateException();
        this.status = OrderStatus.COMPLETED;
        registerEvent(OrderCompletedEvent.from(this));   // 상태 변경과 이벤트 등록이 한 자리에
    }
}
이 편의의 정확한 한계 — 팀 규칙으로 합의해야 한다 등록된 이벤트는 repository.save()가 호출될 때 발행된다. 그래서 변경 감지만으로 수정하고 save()를 부르지 않으면 이벤트가 나가지 않는다. "JPA는 save 안 해도 된다"는 지식과 정면으로 부딪히는 지점이라, 도입한다면 이 규칙을 명시적으로 합의해야 한다.

6. @TransactionalEventListener 정확히 쓰기

phase 네 가지 — 기준은 한 문장, "이 작업이 원 트랜잭션과 운명을 같이해야 하나?"
phase실행 시점쓰는 자리
BEFORE_COMMIT커밋 직전, 아직 같은 트랜잭션 안이벤트 결과도 함께 롤백되어야 할 때(파생 데이터 저장)
AFTER_COMMIT (기본)커밋이 확정된 뒤성공했을 때만 해야 하는 일 — 메일, 알림, 외부 연동
AFTER_ROLLBACK롤백된 뒤실패 통계, 보상 트리거
AFTER_COMPLETION성공/실패 무관하게 끝난 뒤정리 작업
운명을 같이해야 하면 BEFORE_COMMIT(사실상 같은 트랜잭션), 성공했을 때만 해야 하면 AFTER_COMMIT

6-1. 함정 — AFTER_COMMIT 리스너에서 DB를 바꾸면 조용히 사라진다 시니어 변별

이게 실무에서 가장 자주 밟는 지뢰다.

before 예외도 안 나고, 반영도 안 된다
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onOrderCompleted(OrderCompletedEvent event) {
    Point point = pointRepository.findByUserId(event.userId())
                                 .orElseThrow();
    point.accumulate(event.amount());   // 변경 감지에 기대고 있다
}
// 이 변경을 커밋해 줄 트랜잭션이 없다. 예외도 안 난다.
// = 가장 나쁜 종류의 버그: 조용히 아무 일도 일어나지 않는다
after 새 트랜잭션을 명시적으로 연다
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)  // 이 한 줄이 전부다
public void onOrderCompleted(OrderCompletedEvent event) {
    Point point = pointRepository.findByUserId(event.userId())
                                 .orElseThrow();
    point.accumulate(event.amount());
}   // 새 트랜잭션이 여기서 커밋된다
// 대가: 커넥션을 하나 더 쓴다 — 계산에 넣어야 한다
같은 계열의 함정 둘 — 셋 다 "예외 없이 조용히"가 공통점이다 ① @TransactionalEventListener는 트랜잭션이 없는 상태에서 발행된 이벤트를 아예 받지 않는다. 스프링 문서의 표현은 "활성 트랜잭션 안에서 발행되지 않은 이벤트는 fallbackExecution 플래그를 명시적으로 켜지 않는 한 폐기된다"이다. 배치나 테스트에서 트랜잭션 없이 발행하면 리스너가 조용히 안 돌고, 이때도 예외가 없다. 트랜잭션 밖 호출도 처리해야 하면 fallbackExecution = true를 명시한다.
② @Transactional 테스트에서는 AFTER_COMMIT 리스너가 아예 실행되지 않는다. 테스트 트랜잭션은 끝에 롤백되므로 커밋이 없고, 따라서 리스너도 안 불린다. "운영에서 안 도는" 게 아니라 그 반대 — 테스트에서 안 돌아 검증 자체가 통째로 비어 있는 채 통과한다. @Commit이나 TestTransaction으로 실제 커밋시켜야 한다.

6-2. 그래도 남는 구멍 — 이것이 Outbox로 가는 다리

AFTER_COMMIT + REQUIRES_NEW까지 갖췄다고 끝이 아니다. 구멍이 두 개 남는다.

구멍 ① 새 트랜잭션이 실패해도 아무도 모른다

원 트랜잭션은 이미 커밋돼 끝났으므로 되돌릴 것이 없고, 리스너의 예외는 호출자에게 전파되지도 않는다(@Async까지 붙어 있으면 아예 다른 스레드다).

"주문은 완료됐는데 포인트만 없다"는 상태가, 기록 한 줄 없이 만들어진다.

구멍 ② 커밋 직후 서버가 죽으면 이벤트가 증발한다

이벤트는 애플리케이션 메모리 위의 객체일 뿐이고, 주문 커밋과 이벤트 실행 사이에는 원자성이 없다.

주문 COMMIT 성공 ──╳ (재시작 / OOM / 배포) ── 리스너 실행 안 됨
주문은 완료됐는데 포인트는 영원히 없다. 기록도 없다.
주문이 완료됐다는 사실과, 포인트를 적립해야 한다는 사실이 함께 저장되지 않는 한 이 구멍은 못 막는다 — 그게 Outbox다

7. 데드락 — 블로킹 I/O가 하나도 없어도 터진다

"메일을 뺐으니 됐다"고 생각한 순간, 전부 단순 DB 변경인데도 터지는 문제가 남아 있다.

데드락(deadlock, 교착)은 "둘 이상의 트랜잭션이 서로가 쥔 자원을 기다리느라 아무도 진행하지 못하는 상태"다. 핵심은 순환이다 — 내가 기다리는 상대가 나를 기다리고 있으면, 시간이 아무리 지나도 풀리지 않는다. 그리고 3-1절을 다시 못 박고 간다 — @Lock도 for update도 없지만 UPDATE가 나가는 순간 그 행은 커밋까지 잠긴다.

7-1. 로그에서 알아보는 법 — 벤더마다 다르다

PostgreSQL — SQLSTATE 40P01

ERROR: deadlock detected
DETAIL: Process 4321 waits for ShareLock on
        transaction 987; blocked by process 4322.
        Process 4322 waits for ShareLock on
        transaction 986; blocked by process 4321.
HINT: See server log for query details.

MySQL (InnoDB) — SQLSTATE 40001

com.mysql.cj.jdbc.exceptions
    .MySQLTransactionRollbackException:
  Deadlock found when trying to get lock;
  try restarting transaction

"try restarting transaction"이 좋은 단서다 — DB가 직접 "재시도하면 된다"고 알려주는 것이고, 이는 데드락이 재시도 가능한(retryable) 예외라는 뜻이다.

예외 타입 경로 — 재시도 대상을 잡을 때 필요하다

40P01 / 40001→Hibernate LockAcquisitionException→Spring CannotAcquireLockException

두 벤더 모두 스프링에서는 CannotAcquireLockException으로 번역된다. 하이버네이트 6.6의 PostgreSQLDialect가 40P01을 LockAcquisitionException으로 바꾸고(MySQL의 40001은 공통 변환기가 처리한다), 스프링이 그것을 옮긴다. 이 타입은 PessimisticLockingFailureException의 하위 타입이므로, 상위 타입으로 잡아도 함께 걸린다.

원인을 캐려면 예외 한 줄로는 부족하다 — 두 트랜잭션이 각각 무엇을 쥐고 무엇을 기다렸는지가 필요하다
상세 정보 위치상시 수집 설정주의
PostgreSQL서버 에러 로그에 자동 기록 — 관련 프로세스와 각자의 SQL, 대기 관계가 전부 남는다별도 설정 없이 항상 기록된다. 대기 자체를 보려면 log_lock_waits = on감지까지 deadlock_timeout(기본 1초)만큼 걸린다
MySQL (InnoDB)SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK 절innodb_print_all_deadlocks = ON을 켜야 모든 데드락이 에러 로그에 남는다가장 최근 데드락 하나만 보관하며 다음 데드락이 덮어쓴다
MySQL의 LATEST DETECTED DEADLOCK 절에서 읽는 것 셋 ① *** (1) TRANSACTION / *** (2) TRANSACTION — 두 트랜잭션이 각각 실행 중이던 SQL 문. 어느 코드 경로인지 여기서 특정한다.
② *** (1) WAITING FOR THIS LOCK TO BE GRANTED / *** (2) HOLDS THE LOCK(S) — 누가 무엇을 쥐고 무엇을 기다렸는지. 인덱스 이름과 잠긴 레코드까지 나온다.
③ *** WE ROLL BACK TRANSACTION (N) — 어느 쪽이 희생자로 선택됐는지.
PostgreSQL 로그에서도 읽어야 할 것은 같다 — 두 프로세스의 SQL을 나란히 놓고 "둘이 만지는 테이블 순서가 반대인가"를 보면 대개 그 자리에서 원인이 드러난다.
주의: MySQL에서 innodb_print_all_deadlocks를 켜두지 않았다면 "터졌는데 왜 터졌는지 알 방법이 없는 상태"로 운영하는 것이다. 이건 코드 문제가 아니라 운영 준비의 문제다.

7-2. 처방 세 개 — 순서가 중요하다

데드락 처방 3단 — 고 · 줄 · 재

① 고정 — 자원 획득 순서를 전역으로
근본 처방
모두가 같은 방향으로 가게 만들면 순환 자체가 만들어지지 않는다. 일방통행 도로에는 정면 충돌이 없다 — 차를 더 조심히 몰게 하는 게 아니라 길의 방향을 고정하는 것이 처방이다.
② 줄이기 — 트랜잭션 축소
확률을 낮추는 보조
포인트·쿠폰을 이벤트로 빼면 주문 트랜잭션은 order와 stock 두 개만 잠근다. 잠그는 자원 수와 잠그는 시간이 데드락 확률의 변수이고, 분리는 그 둘을 동시에 줄인다.
③ 재시도 — 짜여진 안전망
예방을 대신할 수 없다
데드락은 완전히 없앨 수 없다(인덱스 락, 실행 계획 변경, 외래키가 만드는 부모 행 락처럼 코드에 안 보이는 경로가 있다). 그래서 예방과 별개로 갖춰둔다.
순서를 헷갈리면 안 된다 — ①이 근본 처방이고 ②는 확률을 낮추는 보조, ③은 그래도 남는 것을 받는 그물
자원이 두 개만 남아도 두 코드 경로가 반대 순서로 잡으면 여전히 데드락이다

① 고정 (a) — 테이블 사이의 순서를 팀 규약으로

before 서비스마다 편한 순서로 만진다
// OrderService    : stock  → point
// SettlementBatch : point  → stock   ← 반대 방향. 데드락 성립.
after "재고 → 포인트 → 쿠폰"을 전역 규약으로
// OrderService    : stock  → point
// SettlementBatch : stock  → point   ← 같은 방향. 뒤에 온 쪽은 그냥 대기할 뿐.

말로만 정하면 지켜지지 않으므로 규약을 코드가 강제하는 형태로 만드는 편이 낫다. 여러 도메인을 함께 갱신하는 자리를 하나의 조율 지점(퍼사드/유스케이스)으로 모으고, 그 안에서만 순서를 정의하면 규약이 한 곳에만 존재한다.

① 고정 (b) — 같은 테이블 안 여러 행은 PK 오름차순으로

before 요청이 준 순서 그대로
public void decrease(List<OrderItem> items) {
    for (OrderItem item : items) {          // 정렬 없음
        Stock stock = stockRepository
            .findByProductId(item.getProductId()).orElseThrow();
        stock.decrease(item.getQuantity());
    }

// 주문 A: 상품 [10, 20] → 락 10 → 20
// 주문 B: 상품 [20, 10] → 락 20 → 10
//   ↑ 장바구니에 담은 순서만 달라도 데드락
after 항상 같은 기준으로 정렬한 뒤 처리
public void decrease(List<OrderItem> items) {
    List<OrderItem> ordered = items.stream()
        .sorted(Comparator.comparing(OrderItem::getProductId))
        .toList();                            // 순서를 고정한다
    for (OrderItem item : ordered) { ... }
}
// 주문 A: [10, 20] → 락 10 → 20
// 주문 B: [10, 20] → 락 10 → 20
//   ↑ 같은 방향이므로 뒤에 온 쪽은 대기만 한다
Hibernate는 이 순서를 지켜주지 않는다 flush 시점에 나가는 UPDATE 순서는 영속성 컨텍스트에 올라온 순서에 좌우되고, 그 순서는 요청마다 얼마든지 달라진다. HashSet 순회, ORDER BY 없는 SELECT의 반환 순서, Set으로 매핑한 연관관계 — 순서가 흔들리는 경로는 많다. 정렬은 프레임워크가 아니라 내가 코드로 고정해야 한다.
(hibernate.order_updates=true가 있지 않느냐고 물을 수 있는데, 그건 JDBC 배치로 묶기 좋게 문장을 그룹핑하는 설정이지 애플리케이션이 원하는 락 순서를 보장하는 장치가 아니다. 목적이 다르므로 데드락 대책으로 쓸 수 없다.)

③ 재시도 — 두 가지를 반드시 지킨다

    retryFor = CannotAcquireLockException.class,          // 데드락 희생자만
    maxAttempts = 3,
    backoff = @Backoff(delay = 50, multiplier = 2, random = true))  // 지수 백오프 + 지터
public void completeOrder(Long orderId) {
    orderTransactionService.completeOrder(orderId);       // @Transactional 은 이쪽 빈에
}
재시도는 트랜잭션 밖에서
@Transactional 메서드 안에서 for 루프로 감싸면, 이미 롤백된 트랜잭션 위에서 재시도하는 꼴이라 커밋 시점에 UnexpectedRollbackException이 난다. 재시도 담당 빈과 트랜잭션 담당 빈을 분리해서 매번 새 트랜잭션·새 영속성 컨텍스트로 다시 들어가야 한다.
지터(jitter)를 넣는다
지터는 재시도 대기 시간에 섞는 무작위 값이다. 지연이 고정값이면 충돌했던 요청들이 정확히 같은 시각에 깨어나 또 부딪힌다.
재시도가 예방을 대신할 수는 없다 재시도 횟수는 메트릭으로 노출해 감시해야 하고, 그 수치가 오르면 그건 "재시도가 잘 동작하고 있다"가 아니라 "어딘가에 순서 역전이 있다"는 경보다.

8. Outbox — 이벤트 분리의 나머지 절반

이 절의 범위 Outbox는 정의와 필요성까지만 다룬다. 릴레이 운영, CDC, 보상 트랜잭션, Saga와의 관계 같은 깊은 이야기는 결제·정합성 장이 본론이다. 여기서 알아야 할 것은 "왜 이벤트 분리에 이게 반드시 따라붙는가" 하나다.

문제를 정확히 다시 진술한다. 6-2절에서 본 구멍은 이것이다 — 주문 커밋과 이벤트 처리 사이에 원자성이 없다. 서로 다른 두 개의 일(하나는 DB 커밋, 하나는 메모리 위 리스너 실행)이고, 둘을 한 몸으로 묶어 줄 장치가 없다. 그래서 "주문은 완료됐는데 포인트는 없다"가 발생하고, 더 나쁜 것은 그 사실을 아무도 모른다는 점이다 — 기록이 없으니 재처리할 대상 목록조차 만들 수 없다.

Outbox(아웃박스)는 말 그대로 "보낼 편지함"이다 — 이벤트를 곧바로 발행하는 대신 주문과 같은 DB의 테이블에 한 줄 INSERT해 둔다
주문 커밋 = 이벤트 저장  ·  둘 중 하나만 성공하는 상태가 물리적으로 존재하지 않는다
-- PostgreSQL 기준. 핵심은 "주문과 같은 DB"에 있다는 것이다.
CREATE TABLE outbox_message (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    aggregate_id bigint       NOT NULL,        -- 주문 ID
    event_type   varchar(100) NOT NULL,        -- 'OrderCompleted'
    payload      jsonb        NOT NULL,        -- 이벤트 본문
    status       varchar(20)  NOT NULL,        -- PENDING / SENT / FAILED
    retry_count  int          NOT NULL DEFAULT 0,
    created_at   timestamptz  NOT NULL,
    sent_at      timestamptz  NULL
);

-- 미처리 건만 스캔하면 되므로 부분 인덱스가 가장 알맞다
CREATE INDEX idx_outbox_pending ON outbox_message (created_at)
    WHERE status = 'PENDING';
릴레이 저장만 하고 아무도 안 읽으면 그냥 로그다
@Component
@RequiredArgsConstructor
public class OutboxRelay {

    @Scheduled(fixedDelay = 1000)
    public void publishPending() {
        List<OutboxMessage> pending =
                outboxRepository.findTop100ByStatusOrderByIdAsc(Status.PENDING);
        //                                       ↑ ID 순 = 발행 순서를 안정적으로 유지

        for (OutboxMessage message : pending) {
            try {
                eventPublisher.publish(message);          // 브로커 발행 또는 직접 호출
                message.markSent();                       // 별도 트랜잭션으로 커밋
            } catch (Exception e) {
                message.markFailed(e.getMessage());       // retry_count++ 후 다음 주기에 재시도
                log.warn("outbox publish failed: id={}", message.getId(), e);
            }
        }
    }
}

릴레이에서 챙겨야 할 것 넷

멀티 인스턴스 중복 처리
서버가 3대면 같은 행을 셋이 함께 집는다. SELECT ... FOR UPDATE SKIP LOCKED로 서로 다른 행을 가져가게 하거나, 샤드 키로 인스턴스를 나누거나, 릴레이만 단일 인스턴스(리더 선출)로 돌린다.
재시도 상한과 DLQ
retry_count가 임계치를 넘으면 FAILED로 격리하고 알림을 보낸다. 무한 재시도는 정상 메시지 처리까지 막는다.
정리(purge)
SENT 행이 무한히 쌓이면 인덱스가 비대해진다. 보관 기간을 정해 주기적으로 삭제한다.
폴링 지연 가산점
1초 주기면 최대 1초 지연이다. 이 지연이 곧 9절의 "즉시 일관성 상실"이다. 규모가 커지면 Debezium 같은 CDC 도구로 DB 트랜잭션 로그를 읽어 outbox INSERT를 감지하는 방식으로 가는데, 대신 인프라가 하나 늘어난다.

8-1. 멱등성 — 재처리의 필연적 짝

Outbox는 at-least-once(최소 한 번) 전달이다. 정확히 한 번은 보장하지 않는다. 발행에 성공했는데 markSent() 직전에 서버가 죽으면, 다음 주기에 같은 메시지를 다시 발행한다. 그래서 중복 방지는 발행 쪽이 아니라 소비 쪽 책임이고, 가장 확실한 장치는 애플리케이션 조건문이 아니라 DB 제약이다.

CREATE TABLE point_history (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id  bigint NOT NULL,
    order_id bigint NOT NULL,
    amount   int    NOT NULL,
    CONSTRAINT uk_point_history_order UNIQUE (order_id)   -- 한 주문에 적립은 딱 한 번
);
before check-then-act — 동시성 아래에서 깨진다
@Transactional
public void accumulate(PointAccumulateCommand command) {
    if (pointHistoryRepository.existsByOrderId(command.orderId())) {

    }

멱등성은 "중복을 막는 장치"가 아니라 "중복이 와도 결과가 같게 만드는 성질"이다
유니크 제약은 두 번째 요청을 실패시키는 게 아니라, 두 번 와도 최종 상태가 한 번 온 것과 똑같게 만드는 것

8-2. 순서 보장 — 되는 것과 안 되는 것

보장되는 것

한 애그리거트 안의 순서 — 같은 aggregate_id의 메시지를 ID 순으로 처리하면 지켜진다.

보장되지 않는 것

서로 다른 애그리거트 사이의 전역 순서. 그리고 병렬 소비를 하면 같은 애그리거트 안에서도 순서가 뒤집힐 수 있다.

처방 ① 키로 묶는다
순서가 중요하면 같은 키(예: 주문 ID)의 메시지를 같은 파티션·같은 소비자로 보낸다.
처방 ② 애초에 의존하지 않게 설계한다
이벤트에 상태 전이의 결과(최종 상태)를 담아, 늦게 온 이벤트를 소비자가 버전으로 판단해 버릴 수 있게 한다.

9. 분리의 대가와 안전망

여기까지 읽으면 "쪼개면 다 좋아지네"로 읽히기 쉽다. 아니다. 이벤트로 쪼개는 순간 없던 문제가 넷 생긴다. 면접에서는 이걸 스스로 붙이는 사람이 시니어로 읽힌다.

분리가 새로 만드는 비용 — 즉 · 추 · 보 · 순

① 즉시 일관성을 잃는다
주문 완료 화면에서 포인트 잔액을 조회하면 아직 안 들어와 있을 수 있다. 사용자에게는 "포인트가 안 들어왔어요"라는 문의로 나타난다.
처방은 UX 설계 — "적립 처리 중입니다"로 표기하거나, 예상 적립액을 먼저 보여주고 확정은 나중에. 기술 결정이 화면 문구까지 바꾼다.
② 추적이 어려워진다
한 화면에서 순서대로 읽히던 흐름이 발행자와 리스너 여러 개로 흩어진다. "포인트가 왜 안 들어왔지?"를 조사하려면 주문 로그 · outbox 테이블 · 릴레이 로그 · 포인트 서비스 로그를 각각 봐야 한다.
처방은 상관관계 ID 전파 — payload에 traceId를 넣어 리스너의 MDC에 복원한다. 비동기 경계를 넘을 때 MDC는 자동으로 넘어가지 않으므로 명시적으로 넘겨야 한다.
③ 보상 트랜잭션을 설계해야 한다
보상 트랜잭션은 "이미 커밋된 작업을 되돌리는 반대 방향의 새 작업"이다. 롤백이 사라진 자리를 이것이 대신한다. 쿠폰 사용이 실패하면 쿠폰을 복구하는 로직, 포인트가 잘못 적립되면 회수하는 로직.
그리고 보상 자체도 실패할 수 있어서 재시도와 수동 개입 창구가 또 필요하다. 실무에서 가장 크게 드는 비용이다.
④ 순서와 중복을 다뤄야 한다
8절에서 본 그대로다. 한 트랜잭션이 공짜로 주던 것(원자성, 순서, 정확히 한 번)을 전부 직접 구현해야 한다.
분리는 즉시 일관성 · 추적 가능성 · 롤백의 단순함을 내주고 락 경합 축소 · 장애 격리를 사는 거래다
그래서 이론이 아니라 관측된 문제가 분리를 정당화해야 한다
면접에서 이렇게 정리한다 "분리는 공짜가 아닙니다. 즉시 일관성·추적 가능성·롤백의 단순함을 내주고, 락 경합 축소와 장애 격리를 사는 거래입니다. 그래서 블로킹 I/O가 들어있거나, 실패해도 주문을 되돌릴 이유가 없거나, 실제로 락 경합이 관측되는 경우에만 분리합니다. 단순 DB 변경 몇 개를 이론적으로 옳다는 이유만으로 쪼개면, 얻는 것 없이 추적 난이도와 보상 로직 비용만 지불하게 됩니다."

9-1. 관측과 안전망 — "지키자"가 아니라 "못 어기게"

이 문항의 문제들은 전부 평소에는 안 보이다가 피크에만 터지는 종류다. 그래서 코드 리뷰에서 눈으로 잡겠다는 계획은 실패한다. 장치로 고정한다.

a
트랜잭션 안 외부 API 호출을 빌드 단계에서 막는다 — 이 문항 최대의 위험(1절)을 구조 규칙으로 못 박는다. 
@AnalyzeClasses(packages = "com.example.order")
class TransactionBoundaryRulesTest {

    @ArchTest
    static final ArchRule 트랜잭션_안에서_외부_클라이언트를_호출하지_않는다 =
        noMethods().that().areAnnotatedWith(Transactional.class)
            .should().callMethodWhere(target(owner(
                nameMatching(".*(MailClient|PaymentClient|SlackClient|RestTemplate|WebClient).*"))))
            .because("외부 API 응답 시간이 그대로 행 락 유지 시간과 커넥션 점유 시간이 된다");
}

완벽하지 않다 — 인터페이스 뒤에 숨거나 여러 단계를 거쳐 호출하면 못 잡는다. 그래도 가장 흔한 형태(서비스에서 클라이언트를 직접 부르는 것)를 막고, 무엇보다 팀에 규칙의 존재를 알린다. 룰을 우회해야 하는 상황이 생기면 그때 논의가 일어나는 것 자체가 이득이다.

b
트랜잭션 길이를 숫자로 본다 — "트랜잭션이 길다"는 말은 측정하지 않으면 감상이다.
  • 트랜잭션 소요 시간을 Micrometer 타이머로 — TransactionSynchronization에 훅을 걸어 시작~완료 시간을 메서드 이름 태그와 함께 기록한다. p99가 예상 밖으로 긴 트랜잭션이 다음 사고 후보다.
  • 임계치 초과 시 경고 로그가 아니라 알림으로 — 로그는 아무도 안 본다. 경보로 승격해야 신호가 된다.
  • 커넥션 풀 대기 시간(HikariCP hikaricp.connections.acquire) — 이 값이 오르면 어딘가에 긴 트랜잭션이 있다는 뜻이다. 원인 추적의 출발점.
c
데드락과 outbox를 감시한다
  • 데드락 발생을 알림으로. PostgreSQL은 데드락을 서버 에러 로그에 자동으로 남기므로 그 로그를 알림으로 연결하고, MySQL이면 innodb_print_all_deadlocks를 먼저 켜야 한다. 애플리케이션 쪽에서는 CannotAcquireLockException 발생 건수를 카운터로 노출한다. 데드락이 조용히 재시도로 흡수되고 있다면 그건 문제가 없는 게 아니라 문제가 안 보이는 것이다.
  • outbox 미처리 건수와 최고 지연(age) — PENDING 건수와 가장 오래된 PENDING의 나이를 게이지로 노출한다. 이 두 숫자가 오르면 릴레이가 죽었거나 소비 측이 계속 실패하고 있다. FAILED 건수는 0이 아니면 즉시 알림 대상이다.
d
테스트로 고정한다
  • @Transactional 테스트에서는 AFTER_COMMIT 리스너가 안 돈다. 테스트 트랜잭션은 끝에 롤백되므로 커밋이 없고, 따라서 리스너도 안 불린다. "테스트가 통과했는데 운영에서 안 도는" 게 아니라 그 반대 — 테스트에서 안 돌아 검증 자체가 비어 있다. @Commit을 쓰거나, TestTransaction으로 명시적으로 커밋하거나, @Transactional 없이 실제 커밋시켜 검증한다.
  • 데드락 재현 테스트. CountDownLatch로 두 스레드를 반대 순서로 동시에 출발시키면 데드락을 의도적으로 만들 수 있다. 이 테스트가 정렬 처방을 넣기 전에는 실패하고 넣은 뒤에는 통과하는 것을 한 번 확인하면, 그 처방이 회귀 테스트로 고정된다.
  • H2가 아니라 Testcontainers로. 데드락 감지, 락 타임아웃, SKIP LOCKED, 유니크 제약 동작은 DB 벤더마다 다르다(3-2절의 표에서 봤듯 락 대기 기본값부터 다르다). H2에서 통과한 동시성 테스트는 보장의 근거가 되지 못한다.
이 장치들의 공통점은 "조심하자"를 "못 어기게"로 바꾼 것이다 가산점
트랜잭션 경계 문제는 사람의 주의력으로 지킬 수 있는 종류가 아니다 — 코드는 정상으로 보이고, 문제는 부하가 걸릴 때만 나타나며, 그때는 이미 장애다

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

한 줄이 긋는 경계 넷?
정 · 락 · 실 · 커 — 정합성 경계 / 락 경합 범위 / 실패 파급 범위 / 커넥션 점유 시간. 원해서 그은 건 첫 번째 하나뿐, 나머지 셋은 덤이다.
넷이 왜 같은 선인가?
물리적 사실 셋 — ① 락은 커밋·롤백 시점에만 풀린다 ② 커넥션은 트랜잭션이 끝나야 반납된다 ③ 롤백은 트랜잭션 전체를 되돌린다.
명시적 락이 없으면 락도 없나?
있다. UPDATE가 나가는 순간 그 행에 배타 락이 걸리고 커밋까지 유지된다. for update는 그걸 SELECT 시점으로 앞당길 뿐이다.
열린 질문 훑는 순서?
구 · 경 · 성 — 구조(애그리거트 몇 개·비가역 있나) → 경계(트랜잭션 안에 DB 밖 자원 있나) → 성능(N+1). 순서를 뒤집으면 구조를 못 보는 사람이 된다.
무엇을 남기고 뺄지 정하는 기준?
① 블로킹 I/O가 있는가 ② 실패하면 주문을 취소해야 하는가. 그리고 세 번째로 되묻는다 — "관측된 문제가 있는가". 성능이 아니라 정합성 요구가 정한다.
@Async만 쓰면?
롤백돼도 메일은 이미 나간다. @Async는 "언제"가 아니라 "누가" 실행할지를 바꾼다. 답은 @TransactionalEventListener(AFTER_COMMIT) + @Async.
AFTER_COMMIT에서 엔티티 수정?
REQUIRES_NEW 필수. 그 시점엔 커밋은 끝났는데 트랜잭션 자원이 아직 스레드에 묶여 있어 기본값 REQUIRED가 끝난 트랜잭션에 참여해 버린다 → 예외 없이 변경이 버려진다.
데드락 처방 순서?
고 · 줄 · 재 — ① 자원 획득 순서 전역 고정(근본) ② 트랜잭션 축소(확률↓) ③ 재시도(안전망). Hibernate는 순서를 지켜주지 않으므로 PK 오름차순 정렬을 코드로.
락 대기 기본값?
PostgreSQL lock_timeout = 0(무한 대기) / MySQL innodb_lock_wait_timeout = 50초. PG가 더 위험한 이유는 실패 대신 조용히 쌓이기 때문.
데드락 예외 타입?
PG 40P01 / MySQL 40001 → Hibernate LockAcquisitionException → Spring CannotAcquireLockException(PessimisticLockingFailureException의 하위 타입).
Outbox 3종 세트?
① 같은 트랜잭션에서 outbox INSERT(원자적 기록) ② 릴레이 재처리 ③ 주문 ID 유니크 제약에 의한 멱등성. 전달 보증은 at-least-once — 중복 방지는 소비 쪽 책임.
분리의 대가 넷?
즉 · 추 · 보 · 순 — 즉시 일관성 상실 / 추적 난이도 / 보상 트랜잭션 / 순서·중복 직접 구현. 이론이 아니라 관측된 문제가 분리를 정당화해야 한다.

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

이 메서드가 도는 동안 커넥션과 행 락은 언제부터 언제까지 잡혀 있나요? 필수힌트: "명시적 락이 없다"는 반문을 미리 처리하고, 다른 요청이 그동안 무엇을 하는지까지 붙인다

커넥션은 트랜잭션 시작부터 종료까지 통째로, 행 락은 각 UPDATE가 나간 시점부터 커밋까지 잡혀 있다. 원본 코드는 마지막에 메일 API가 있으므로 메일 응답 시간이 그대로 락 유지 시간과 커넥션 점유 시간에 더해진다.

여기서 되물을 가치가 있는 것은 "명시적 락을 쓰는 곳이 있느냐"인데, 답이 '없다'여도 결론은 달라지지 않는다는 것을 함께 말해야 완성이다.

이렇게 말한다"명시적 락이 없어도 마찬가지입니다. UPDATE 문 자체가 대상 행에 배타 락을 걸고 커밋까지 유지하기 때문입니다. 이건 애플리케이션이 아니라 DB가 하는 일이고, select ... for update는 그 락을 SELECT 시점으로 앞당기는 것일 뿐입니다. 커밋 전까지 락을 유지하는 건 롤백 가능성을 지키기 위한 필연이라서, 커밋이 늦어지면 락도 그만큼 길어집니다."

다른 요청은 그동안 무엇을 하는지까지 붙이면 완성이다. 같은 행을 건드리는 요청은 락을 못 얻어 대기하며, 그 대기 시간 동안에도 커넥션은 계속 쥐고 있다. PostgreSQL은 lock_timeout 기본값이 0(무한 대기)이라 실패하지 않고 조용히 쌓이고, MySQL은 innodb_lock_wait_timeout 기본 50초가 지나면 에러로 실패한다. PostgreSQL 쪽이 더 위험한 이유가 여기 있다 — 시끄럽게 실패하는 대신 서비스 전체가 느려지는 형태로 나타난다.

메일 발송을 @Async로 뺐습니다. 그런데 그 뒤 couponService.use()에서 예외가 나 롤백됐습니다. 무슨 일이 벌어지나요? 함정힌트: 두 축을 분리해서 말한다 — "언제 실행할지"와 "누가 실행할지"

DB에는 아무 일도 안 일어났는데 고객에게는 "주문이 완료되었습니다" 메일이 도착한다. @Async는 실행을 다른 스레드로 옮길 뿐 커밋을 기다리지 않기 때문이고, 메일에는 롤백이 없기 때문이다.

처방은 @TransactionalEventListener(phase = AFTER_COMMIT) — 커밋이 확정된 뒤에만 리스너가 실행되므로 이 조합이 원천 차단된다. @Async는 버리는 게 아니라 그 위에 얹어 커밋 후 처리가 호출 스레드를 막지 않게 한다.

한 줄로 정리하면 — 비동기와 커밋 후는 다른 축이다. @Async는 "언제 실행할지"가 아니라 "누가 실행할지"를 바꾼다
블로킹 I/O를 전부 뺐고 남은 건 단순 DB 변경뿐입니다. 그래도 쪼갤 이유가 있나요? 시니어 변별힌트: 이유 두 개를 대고, 마지막에 반대편도 붙인다

있다. 두 가지다.

① 데드락. 주문은 재고→포인트 순으로, 정산 배치는 포인트→재고 순으로 갱신하면 서로 상대가 쥔 락을 기다려 교착이 된다. 블로킹 I/O와 무관하고, 트래픽이 높을수록 겹칠 기회가 늘어난다. DB가 한쪽을 희생자로 골라 강제 롤백시키므로 정상 주문이 이유 없이 실패하기 시작한다. 근본 처방은 자원 획득 순서를 전역으로 고정하는 것이고(테이블 순서 규약 + 같은 테이블 안은 PK 오름차순 정렬), 트랜잭션을 쪼개 잠그는 자원 수와 시간을 줄이는 것이 확률을 함께 낮춘다.

② 실패 파급 범위. 쿠폰 처리 하나가 실패했다고 이미 성공한 주문·재고·포인트를 전부 되돌리는 것이 옳은 정책인지를 물어야 한다. 한 트랜잭션에 묶는 것은 "여기 있는 모두가 서로의 실패에 함께 죽는다"고 코드가 임의로 선언한 것이다.

그리고 반대편도 붙인다 — 트래픽이 낮고 데드락 이력이 없다면 한 트랜잭션에 두는 편이 유지보수에 낫다. 이벤트로 흩으면 흐름 추적과 보상 로직 비용이 생기므로, 분리의 근거는 이론이 아니라 관측된 문제여야 한다.

재고 차감까지 이벤트로 빼면 트랜잭션이 더 짧아지지 않나요? 함정힌트: 질문이 은근히 기준을 바꿔치기하고 있다. 무엇에서 무엇으로?

짧아진다. 그런데 그건 이 규칙의 기준이 아니다. 질문이 슬쩍 기준을 "정합성 요구"에서 "트랜잭션 길이"로 바꿔치기하고 있다는 점을 먼저 짚어야 한다.

재고를 빼면 "재고 없이 성립한 주문"이 만들어질 수 있다. 주문 완료가 커밋되고 재고 차감이 나중에 실패하면, 그 순간부터 팔 수 없는 물건을 판 주문이 시스템에 존재한다. 이건 나중에 보정해서 될 일이 아니라 고객에게 취소를 통보해야 하는 사고다. 4절 표의 기준으로 답이 이미 나와 있다 — "실패하면 주문을 취소해야 하는가?" → 예 → 같은 트랜잭션.

성능을 이유로 정합성 경계를 옮기는 것은 규칙을 지키는 게 아니라 어기는 것이다

다만 한 걸음 더 갈 수 있다. 정말 재고 차감을 동기 경로에서 빼야 할 규모(초당 수만 건의 선착순 등)라면, 그때 바꾸는 것은 구현이 아니라 업무 모델이다 — "주문 완료"를 "주문 접수"로 바꾸고, 재고 확정 후에 완료로 승격시키며, 사용자 화면과 알림도 그 모델을 따라가게 만든다. 같은 업무를 몰래 비동기로 만드는 것과, 업무의 의미 자체를 바꾸는 것은 전혀 다른 결정이고, 후자는 기획과 합의해야 하는 사안이다.

포인트 적립을 이벤트로 뺐는데, 주문 커밋 직후 서버가 재시작돼 적립이 안 됐습니다. 어떻게 다루시겠습니까? 필수힌트: 근본 원인 한 문장 → 처방 세 조각. 세 조각이 세트라는 점이 핵심

근본 원인부터 짚는다 — 주문 커밋과 이벤트 처리 사이에 원자성이 없기 때문이다. 이벤트는 메모리 위의 객체라 프로세스가 죽으면 함께 사라지고, 기록이 없으니 재처리 대상 목록조차 만들 수 없다.

처방은 Outbox 패턴이고, 세 조각이 세트다.

① 원자적 기록
이벤트를 주문과 같은 트랜잭션에서 같은 DB의 outbox 테이블에 INSERT. "주문 커밋 = 이벤트 저장"이 되어 둘 중 하나만 성공한 상태가 물리적으로 존재하지 않는다.
② 재처리 주체
별도 프로세스(주기 폴링 배치 또는 CDC)가 PENDING을 읽어 발행하고 SENT로 표시. 서버가 죽었다 살아나도 다음 주기에 자동으로 이어서 처리된다.
③ 멱등성
재처리는 필연적으로 중복을 만든다(발행 성공 직후 상태 갱신 전에 죽는 경우). 적립 이력에 주문 ID 유니크 제약을 걸고, 그 예외를 정상 흐름으로 처리한다.

조회 후 분기(check-then-act)는 동시 실행에서 깨지므로 반드시 제약이어야 한다. 그리고 전달 보증은 at-least-once이지 exactly-once가 아니다 — 그래서 중복 방지는 발행 쪽이 아니라 소비 쪽 책임이라는 점을 함께 말하면 좋다.

AFTER_COMMIT 리스너 안에서 엔티티를 수정했는데 DB에 반영이 안 됩니다. 예외도 안 납니다. 시니어 변별힌트: "REQUIRES_NEW 붙이세요"로 끝내면 절반. 기본값으로는 왜 안 되는지가 갈림길

이름 그대로다 — 원 트랜잭션이 이미 커밋된 뒤라서 그 변경을 커밋해 줄 트랜잭션이 없다. 변경 감지가 UPDATE를 만들려면 flush가 필요하고 flush를 일으키는 건 커밋인데, 그 커밋이 이미 지나갔다. 그래서 예외 없이 조용히 아무 일도 안 일어난다.

처방은 리스너에 @Transactional(propagation = REQUIRES_NEW)를 붙여 새 트랜잭션을 명시적으로 여는 것. 기본값 REQUIRED로는 안 되는 이유까지 말하면 확실히 갈린다 — AFTER_COMMIT 시점에는 커밋은 끝났지만 트랜잭션 자원이 아직 스레드에 묶여 있어서, REQUIRED가 "진행 중인 트랜잭션이 있다"고 보고 이미 끝난 그 트랜잭션에 참여해 버린다. 참여했으니 커밋은 다시 일어나지 않고 변경은 버려진다. 스프링 문서도 이 단계에서는 "데이터 접근 코드가 원 트랜잭션에 참여는 하지만 변경이 커밋되지는 않는다"고 명시적으로 경고한다. REQUIRES_NEW는 "무조건 새로 연다"이므로 이 판정 자체를 건너뛴다. 대가는 커넥션을 하나 더 쓴다는 것.

같은 계열의 함정 둘을 덧붙이면 가산점이다. ① @TransactionalEventListener는 트랜잭션 없이 발행된 이벤트를 아예 받지 않는다(필요하면 fallbackExecution = true). ② @Transactional 테스트에서는 이 리스너가 실행되지 않는다 — 테스트가 끝에 롤백하므로 커밋이 없기 때문이고, 그래서 검증이 통째로 비어 있는 채 통과한다. @Commit이나 TestTransaction으로 실제 커밋시켜야 한다.

그리고 여기서 한 걸음 더 나가면 Outbox로 이어진다. REQUIRES_NEW로 새 트랜잭션을 열었어도 그 안에서 실패하면 아무도 모른다 — 원 트랜잭션은 이미 커밋돼 되돌릴 것이 없고, 예외는 호출자에게 전파되지 않는다. "조용히 사라진다"는 문제가 형태만 바꿔 남아 있는 것이고, 그걸 막으려면 해야 할 일을 원 트랜잭션과 함께 DB에 적어두는 수밖에 없다.

BEFORE_COMMIT을 쓰면 유실도 없고 원자적인데, 왜 굳이 Outbox가 필요한가요? 시니어 변별힌트: 반은 맞는 말이다. 무엇을 얻고 무엇이 그대로 남는지 가른다

절반은 맞다. BEFORE_COMMIT은 아직 같은 트랜잭션 안이므로 리스너에서 한 DB 변경이 원 트랜잭션과 함께 커밋되거나 함께 롤백된다. 즉 원자성은 얻는다.

그런데 그게 곧 "한 트랜잭션에 전부 넣는 것"과 같다는 게 문제다. 리스너 안의 작업이 여전히 같은 트랜잭션 경계 안에 있으므로, 3절의 네 경계가 하나도 줄지 않는다 — 락 경합 범위 그대로, 실패 파급 범위 그대로, 커넥션 점유 시간 그대로. 코드가 리스너로 옮겨져 보기에만 분리된 것이지, 경계는 그대로다. 더 나쁜 경우로 외부 메일 API를 BEFORE_COMMIT에 넣으면 원본 코드로 정확히 회귀한다.

BEFORE_COMMIT은 "정말 함께 롤백돼야 하는 것"(파생 데이터 저장)에 쓰고,
"성공했을 때만 해야 하는 일"에는 AFTER_COMMIT + Outbox를 쓴다

두 선택지는 목적이 다르다. BEFORE_COMMIT은 원자성을 사고 경계 축소를 포기하는 것이고, AFTER_COMMIT + Outbox는 경계 축소를 사고, 잃어버린 원자성을 outbox 테이블로 되사오는 것이다. 공짜로 둘 다 갖는 선택지는 없다.

이렇게 쪼개면 결국 MSA로 가자는 말인가요? 모놀리스에서 이벤트로 쪼개는 게 무슨 의미가 있죠? 가산점힌트: "예행연습"이 아니라 더 강한 단어가 있다. 그리고 반대편도 반드시 붙인다

MSA로 가자는 말이 아니라, 갈 수 있는 상태를 만들어두자는 말이다.

모놀리스에서 도메인 이벤트로 분리하는 순간 각 도메인이 "같은 트랜잭션 안에 있다"는 전제 없이 동작하도록 강제된다. 포인트 서비스는 주문 트랜잭션에 얹혀 가는 대신 자기 트랜잭션으로 자기 정합성을 책임지고, 실패하면 재처리와 멱등성으로 스스로 복구한다. 이건 서비스를 물리적으로 분리할 때 어차피 반드시 해야 하는 일이다.

그래서 이건 MSA 전환의 예행연습이 아니라 전제 조건이다

트랜잭션으로 묶여 있는 모듈은 분리 자체가 불가능하다 — 프로세스가 갈리는 순간 하나의 트랜잭션이 성립하지 않기 때문이다. 결과적 일관성으로 동작할 수 있게 만들어 두면, 나중에 물리적으로 떼는 일은 배포 단위를 바꾸는 문제로 축소된다.

동시에 반대편도 분명히 한다. 모놀리스에서 이벤트로 쪼개는 것 자체가 목적이 되면 안 된다. 지금 당장 얻는 것(락 경합 축소, 장애 격리, 데드락 감소)이 없는데 "언젠가 MSA로 갈지 모르니까" 쪼개는 건 오늘 비용을 내고 오지 않을 미래를 사는 것이다. 오늘의 문제로 정당화되지 않는 분리는 하지 않는다.

이벤트가 두 번 처리되는 걸 왜 소비 쪽에서 막나요? 발행 쪽에서 한 번만 보내면 되지 않나요?힌트: "구현이 어렵다"가 아니라 "원리적으로 불가능하다"에서 출발한다

한 번만 보내는 것이 원리적으로 불가능하기 때문이다. 발행에 성공했다는 사실을 outbox에 SENT로 기록하는 순간과 실제로 발행한 순간 사이에는 항상 틈이 있다.

발행 후 → 기록 전에 죽으면

재발행된다 = 중복

기록 후 → 발행 전에 죽으면

유실된다 = 영영 사라짐

둘 중 하나를 골라야 하고, 유실보다 중복이 낫기 때문에 at-least-once를 고른다.

중복은 감지할 수 있고 유실은 감지할 수 없다 — 이게 선택의 이유다

중복은 유니크 제약이 잡아주지만, 사라진 이벤트는 아무 흔적도 남기지 않는다. 그리고 멱등성은 "중복을 막는 장치"가 아니라 "중복이 와도 결과가 같게 만드는 성질"이다. 적립 이력에 주문 ID 유니크 제약을 거는 것은 두 번째 요청을 실패시키는 게 아니라, 두 번 와도 최종 상태가 한 번 온 것과 똑같게 만드는 것이다. 그래서 소비 쪽에서 DataIntegrityViolationException을 잡아 정상 흐름으로 조용히 넘기는 것이 올바른 처리다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

PostgreSQL과 MySQL 중 락 대기·데드락에서 어느 쪽이 더 위험한가요? 함정힌트: "어느 쪽이 위험한가"는 두 개의 질문이다 — 대기와 진단

축을 둘로 나눠야 답이 정확해진다. 대기에서는 PostgreSQL이 더 위험하고, 진단에서는 MySQL이 더 위험하다.

대기 — PostgreSQL이 위험

lock_timeout 기본값이 0(무한 대기)이라 실패하지 않고 조용히 쌓인다. 증상이 "특정 API 에러율 증가"가 아니라 "서비스 전체가 느려짐 → 커넥션 풀 고갈 → 전면 장애" 순서로 나타난다. MySQL은 innodb_lock_wait_timeout 기본 50초 후 에러로 실패하므로 시끄럽게 알려준다.

처방: lock_timeout을 유한한 값으로 설정해 "오래 기다리면 실패하게" 만들어 둔다.

진단 — MySQL이 위험

PostgreSQL은 데드락 상세를 서버 에러 로그에 자동 기록한다(설정 불필요). MySQL은 SHOW ENGINE INNODB STATUS에 가장 최근 하나만 남고 다음 데드락이 덮어쓴다. innodb_print_all_deadlocks = ON을 켜두지 않았다면 "터졌는데 왜 터졌는지 알 방법이 없는 상태"로 운영하는 것이다.

이건 코드 문제가 아니라 운영 준비의 문제다.

이 답변의 값은 "PG가 위험합니다"가 아니라 "위험의 성격이 다릅니다"를 말하는 데 있다. 한쪽은 실패로 나타나는 위험이고 다른 쪽은 지연으로 나타나는 위험인데, 모니터링 관점에서는 조용한 쪽이 더 나쁘다.

팀에서 AbstractAggregateRoot 도입을 제안받았습니다. 뭐라고 답하시겠습니까? 가산점힌트: 찬반이 아니라 "무엇을 해결하고 무엇은 여전히 남는가"로 답한다

얻는 것이 분명하다. registerEvent()를 엔티티의 상태 변경 메서드 안에 두면 "상태는 바꿨는데 이벤트를 안 보냈다"는 누락이 구조적으로 줄어든다. 발행 책임이 서비스에 흩어져 있으면 새로 추가된 경로에서 빠뜨리기 쉬운데, 상태 변경과 이벤트 등록이 한 자리에 있으면 같이 눈에 들어온다.

대신 정확히 하나의 함정을 팀 규칙으로 합의해야 한다. 등록된 이벤트는 repository.save()가 호출될 때 발행된다. 그래서 변경 감지만으로 수정하고 save()를 부르지 않으면 이벤트가 나가지 않는다. "JPA에서는 조회한 엔티티에 save()를 부를 필요가 없다"는 널리 알려진 상식과 정면으로 충돌하므로, 도입한다면 "이벤트를 등록하는 엔티티는 명시적으로 save()를 호출한다"는 규칙을 문서화하고 리뷰에서 확인해야 한다.

그리고 범위를 분명히 한다. 이건 "발행 누락"을 줄이는 장치이지 "커밋 후 유실"을 막는 장치가 아니다. 커밋 직후 프로세스가 죽는 경우는 여전히 Outbox의 몫이다. 두 문제를 같은 것으로 착각하면 "이제 안전하다"고 잘못 결론 내린다.

"트랜잭션이 길다"를 어떻게 증명하나요? 무엇부터 보시겠습니까? 가산점힌트: 증상 → 원인 후보 → 코드 경로 특정. 순서가 있다

측정하지 않으면 "트랜잭션이 길다"는 감상이다. 순서를 정해두면 진단이 재현 가능해진다.

1
증상 — 커넥션 풀 대기 시간(HikariCP hikaricp.connections.acquire). 이 값이 오르면 "어딘가에 긴 트랜잭션이 있다"는 뜻이다. 느린 쿼리가 하나도 없어도 이 값은 오를 수 있다 — 그 자체가 이 문항의 문제를 가리키는 신호다.
2
원인 후보 — 트랜잭션 소요 시간 p99. TransactionSynchronization에 훅을 걸어 시작~완료 시간을 메서드 이름 태그와 함께 Micrometer 타이머로 기록한다. 평균이 아니라 p99를 본다 — 외부 API 지연은 평균에 묻히고 꼬리에만 나타나기 때문이다.
3
코드 경로 특정 — 데드락 카운터와 outbox 지표. CannotAcquireLockException 발생 건수가 오르면 어딘가에 순서 역전이 있다는 경보이고, outbox PENDING 건수·최고 지연(age)이 오르면 릴레이가 죽었거나 소비 측이 계속 실패 중이다.

그리고 임계치 초과는 로그가 아니라 알림으로 올린다. 로그는 아무도 안 본다 — 경보로 승격해야 신호가 된다. 이 문항의 문제들은 전부 "피크에만 터지는" 종류라, 사람이 눈으로 지키는 계획은 실패한다.

outbox 테이블을 Redis나 별도 DB에 두면 안 되나요? 주문 DB가 무거워질 텐데요.힌트: 이 패턴이 성립하는 조건 딱 하나를 떠올린다

안 된다. 그 순간 Outbox가 Outbox가 아니게 된다.

이 패턴이 성립하는 조건은 오직 하나 — order UPDATE와 outbox_message INSERT가 하나의 로컬 트랜잭션으로 함께 커밋되는 것이다. 저장소를 분리하면 "주문은 커밋됐는데 이벤트 기록은 실패"가 다시 가능해지고, 그건 Outbox를 도입하기 전과 정확히 같은 문제다. 브로커에 직접 발행하지 않는 이유와 똑같은 이유로 별도 저장소도 안 된다 — 서로 다른 시스템 두 개는 원자적으로 묶을 수 없다.

Outbox의 아이디어는 "원자성이 보장되는 하나의 DB 안으로 문제를 끌고 들어오는 것"이다

"주문 DB가 무거워진다"는 걱정 자체는 타당하고, 그건 다른 방법으로 푼다. ① SENT 행을 보관 기간을 정해 주기적으로 삭제(purge)하고 ② PENDING만 걸리는 부분 인덱스를 써서 스캔 비용을 미처리 건에만 한정하며 ③ 규모가 더 커지면 CDC(Debezium 등)로 트랜잭션 로그를 읽어 폴링 부하 자체를 없앤다. 저장 위치를 옮기는 것만은 선택지가 아니다.

한 줄 요약
@Transactional 한 줄은 정합성 경계 하나가 아니라 네 개의 경계를 동시에 긋는다 — 정합성 경계 = 락 경합 범위 = 실패 파급 범위 = 커넥션 점유 시간이고, 넷이 같은 선인 이유는 물리적이다(락은 커밋·롤백 시점에만 풀리고, 커넥션은 트랜잭션이 끝나야 반납되며, 롤백은 트랜잭션 전체를 되돌린다). 그래서 애그리거트를 하나 더 넣는 것은 이 넷을 함께 키우는 결정이고, DDD의 "한 트랜잭션에 한 애그리거트"는 성능 규칙이 아니라 "즉시 정합해야 하는 최소 단위가 어디까지인가"를 묻는 정합성 규칙이다(성능 개선은 부산물이다). 이 코드의 최대 위험은 쿼리 수가 아니라 메일 API 응답을 기다리는 동안 재고 행 락과 커넥션을 쥐고 있다는 사실이며 — 명시적 락이 없어도 UPDATE가 곧 커밋까지 유지되는 배타 락이고, PostgreSQL은 lock_timeout 기본값이 무한이라 실패 대신 조용히 쌓인다 — 열린 질문에는 구조 → 경계 → 성능 순으로 답한다. 무엇을 남길지는 성능이 아니라 정합성 요구 수준이 정한다(블로킹 I/O가 있는가 / 실패하면 주문을 취소해야 하는가). 블로킹 I/O가 하나도 없어도 큰 트랜잭션은 락 순서 역전으로 데드락을 만들며, 근본 처방은 자원 획득 순서를 전역으로 고정하는 것이다(Hibernate가 지켜주지 않으므로 PK 오름차순 정렬을 코드로). 분리의 도구는 @TransactionalEventListener(AFTER_COMMIT)이고 리스너에서 DB를 바꾸려면 REQUIRES_NEW가 필수다 — 그 시점엔 커밋이 끝났는데도 트랜잭션 자원이 아직 스레드에 묶여 있어 기본값 REQUIRED가 이미 끝난 트랜잭션에 참여해 변경이 조용히 버려지기 때문이다. 커밋 직후 유실까지 막으려면 Outbox 3종 세트(같은 트랜잭션에서 outbox INSERT + 릴레이 재처리 + 주문 ID 유니크 제약에 의한 멱등성)가 필요하다. 마지막으로 분리는 공짜가 아니다 — 즉시 일관성·추적 가능성·롤백의 단순함을 내주고 락 경합 축소와 장애 격리를 사는 거래이므로, 이론이 아니라 관측된 문제가 분리를 정당화해야 한다.
