OSIV 트레이드오프와 전환
트랜잭션 경계와 영속성 컨텍스트 경계는 다른 것이다

면접 질문: "OSIV(Open Session In View)를 켰을 때와 껐을 때의 트레이드오프는? 대용량 트래픽 서비스에서는 어떻게 설정하겠습니까?"

핵심 관전 포인트 — 먼저 정의를 한 문장으로 못 박는다: spring.jpa.open-in-view는 Spring Boot 기본값 true이고, 트랜잭션은 서비스 메서드에서 끝나도 EntityManager(영속성 컨텍스트)는 HTTP 응답이 완료될 때까지 열어둔다. 즉 트랜잭션 경계와 영속성 컨텍스트 경계는 별개이며, OSIV는 둘을 일부러 어긋나게 만드는 장치다. 켰을 때의 대가를 "커넥션을 오래 잡는다"고 말하면 절반만 맞다. 정확한 표현은 "아무 일도 하지 않는 커넥션을 잡는다"이다 — 컨트롤러·응답 단계에 외부 API 호출 같은 느린 I/O가 있으면 그 시간 내내 DB 커넥션이 놀면서 점유된다. 풀 20개에 300ms 외부 호출이면 이론 처리량이 400 req/s에서 54 req/s로 무너지고, 외부 시스템의 지연이 우리 DB 커넥션 풀을 타고 전파된다. 껐을 때의 의미는 불편이 아니라 설계 강제다 — "엔티티는 트랜잭션 밖으로 나가지 않는다"를 프레임워크가 강제하고, 그래서 fetch join과 DTO 변환을 명시적으로 쓰게 된다. 마지막이 이 문항의 진짜 관문이다: 3년치 코드에서 어디가 터질지는 정적 검색으로 절대 보장할 수 없다(Jackson 직렬화·toString()·프록시 경유는 게터 호출이 코드에 없다). 보장하는 방법은 두 개다 — open-in-view=false로 프로파일만 바꿔 기존 컨트롤러 통합 테스트를 통째로 한 번 더 돌려 예외를 배포 전에 표면화시키고, ArchUnit으로 "컨트롤러 반환 타입에 엔티티 금지"를 못 박아 재발을 차단한다. 그리고 순서가 중요하다 — 끄는 것은 마지막이다. ① DTO 경계 수립 → ② 서비스 트랜잭션 안에서 변환 완료 → ③ 그때 끈다.
  • 1
    정의부터 한 문장으로 못 박는다 — OSIV는 트랜잭션이 끝난 뒤에도 EntityManager를 응답 완료까지 열어두는 Spring Boot 기본값(true)이고, 요점은 트랜잭션 경계와 영속성 컨텍스트 경계가 별개라는 것이다. 그래서 컨트롤러·JSON 직렬화 단계의 지연 로딩이 통과한다.
  • 2
    대가는 "오래 잡는다"가 아니라 "노는 커넥션을 잡는다"다 — 렌더링·외부 API 호출 구간에는 DB로 나가는 쿼리가 0건인데 커넥션은 풀에서 빠져 있다. 풀 10개·렌더링 200ms면 처리량 상한이 500 → 45 req/s, 풀 20개·외부 호출 300ms면 400 → 54 req/s. 게다가 남의 서비스 지연이 우리 DB 풀을 타고 전면 장애로 번진다.
  • 3
    그래서 대용량에서는 끄되, "끄는 것은 마지막 단계"다 — 어디가 터질지는 검색으로 찾는 게 아니라 터지게 만들어서 센다. open-in-view=false 프로파일로 기존 통합 테스트 재실행(현재 위반 수집) + ArchUnit 룰(재발 차단) + 카나리(사각지대 방어)를 깔고, ① DTO 경계 → ② 트랜잭션 안 변환 → ③ 끄기 순서로 간다.

0. 질문 + 출제 의도 — 이 문항의 진짜 관문

질문: "OSIV(Open Session In View)를 켰을 때와 껐을 때의 트레이드오프는? 대용량 트래픽 서비스에서는 어떻게 설정하겠습니까?"

출제 의도: 기본값(켜짐)이 커넥션을 뷰 렌더링까지 물고 있게 한다는 사실은 대용량 트래픽에서 커넥션 고갈의 숨은 원인이다. 프레임워크 기본값을 의심해본 적 있는지를 본다. 즉 채점 지점은 정의 암기가 아니라 ① 기본값이 왜 그렇게 정해졌는지 해석할 수 있는가 ② 그 기본값이 우리 서비스의 트래픽 특성과 맞는지 판단할 수 있는가 ③ 이미 그 기본값 위에 쌓인 코드를 안전하게 되돌릴 수 있는가다.

함정 두 개 — 이 문항은 여기서 갈린다 ① "트레이드오프"를 물었는데 한쪽만 말하는 것. "커넥션을 오래 잡으니 끈다"까지만 말하면 절반이다. 끄면 무엇을 잃는지, 그리고 그럼에도 왜 기본값이 true인지를 같이 말해야 트레이드오프 서술이 성립한다. → 5절
② "어떻게 설정하겠습니까"를 설정값 한 줄로 답하는 것. false는 결론이지 답이 아니다. 이 질문의 실질은 이미 돌아가는 서비스에서 그 한 줄을 어떻게 안전하게 바꾸느냐다. 면접관이 "3년치 코드 중 어디가 터질지 어떻게 찾겠나"라는 시나리오 꼬리질문을 붙이는 이유가 이것이다. → 6·7·8절

이 페이지는 셋으로 간다. 1~4절: 무엇을 열어두고 그 대가로 무엇을 붙잡는가(원리와 비용) · 5절: 껐을 때 무엇이 달라지는가(트레이드오프의 반대편) · 6~8절: 이미 돌아가는 서비스에서 그것을 어떻게 안전하게 끄는가(처방과 절차). 무게는 뒤쪽 절반에 있다.

1. 전제 — 커넥션 풀이라는 좁은 목, 그리고 정의 한 문장

1-1. 왜 커넥션이 아껴야 하는 자원인가

OSIV 이야기를 시작하기 전에 DB 커넥션 풀을 짧게 깔고 가야 한다. 이 전제가 없으면 뒤의 계산이 전부 공허해진다.

애플리케이션이 DB에 쿼리를 보내려면 커넥션이 하나 필요하다. 커넥션은 애플리케이션과 DB 서버 사이에 열려 있는 TCP 연결이고, 새로 여는 데 수십 밀리초가 든다(TCP 핸드셰이크 + DB 인증). 요청마다 새로 열면 그 비용을 매번 치르므로 미리 몇 개를 만들어두고 돌려쓴다. 이 묶음이 커넥션 풀이고, Spring Boot의 기본 구현이 HikariCP다.

여기서 중요한 성질이 하나 나온다. 풀의 크기는 유한하고, 대개 생각보다 작다. Spring Boot의 HikariCP 기본 최대 크기는 10개다. 스레드가 200개여도 동시에 DB와 이야기할 수 있는 요청은 10개뿐이고, 11번째 요청은 커넥션이 반납될 때까지 기다린다.

스레드 수가 아니라 커넥션 점유 시간이 이 서버의 초당 처리 건수를 결정한다
OSIV가 성능 논의의 주제가 되는 이유가 정확히 이것이다 — OSIV는 커넥션을 잡고 있는 시간의 길이를 바꾼다

1-2. 정의를 한 문장으로 고정한다

먼저 외울 한 문장 — 면접 첫 답변으로 그대로 쓴다

OSIV(spring.jpa.open-in-view)는 Spring Boot 기본값 true이며,
트랜잭션이 서비스에서 끝난 뒤에도 EntityManager(영속성 컨텍스트)를 HTTP 응답 완료 시점까지 열어둔다.

이 한 문장에 문항의 절반이 들어 있다. 나머지 절반은 여기서 자동으로 따라 나온다 — 열어둔다는 것은 뭔가를 계속 붙잡고 있다는 뜻이고, 그 뭔가가 1-1에서 본 DB 커넥션이다.

이름을 뜯으면 정의가 그대로 나온다 — "세션을 뷰 렌더링 시점까지 열어둔다." JSP·Thymeleaf 같은 서버 사이드 렌더링 시절에 붙은 이름이라 "View"라고 되어 있지만, 이름은 옛날 것이어도 가리키는 자리는 지금도 유효하다.

1-3. 누가 세션을 열고 닫는가 가산점

Spring이 OpenEntityManagerInViewInterceptor(또는 필터)를 웹 요청 앞단에 걸어둔다. 동작은 단순하다.

요청 시작 — EntityManager 생성해 현재 스레드에 바인딩→ 컨트롤러 · 서비스 · @Transactional은 "이미 바인딩된" EM을 그대로 쓴다→ 응답 완료 — 바인딩 해제하고 close()
"왜 트랜잭션이 끝났는데 세션이 살아 있나"가 여기서 통째로 해결된다 핵심은 @Transactional이 EntityManager를 새로 만들지 않고, 이미 열려 있는 것에 참여한다는 점이다. 트랜잭션은 자기가 연 것만 닫을 수 있고, 세션은 자기가 연 것이 아니기 때문에 손대지 않는다. 세션을 연 주체가 트랜잭션이 아니라 인터셉터이기 때문이다.

1-4. 같은 코드, 다른 결과 — 설정만 다르다

Java 서비스와 컨트롤러 — 두 경우 모두 코드가 동일하다
// 서비스
@Transactional(readOnly = true)
public Order findOrder(Long id) {
    return orderRepository.findById(id).orElseThrow();
}   // ← 트랜잭션 종료. OSIV=false 면 EntityManager 도 여기서 닫힌다.

// 컨트롤러
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable Long id) {
    Order order = orderService.findOrder(id);
    return new OrderResponse(order.getId(), order.getItems().size());
    //                                        ↑ @OneToMany(LAZY) 를 여기서 초기화
}

OSIV = true — 통과한다

getItems()에서 세션이 살아 있으므로 추가 SELECT가 나가고 정상 동작한다. 문제는 그 쿼리가 서비스 계층 밖에서 나간다는 것이다.

OSIV = false — 터진다

getItems()에서 LazyInitializationException. 세션이 서비스 메서드 끝에서 이미 닫혔기 때문이다.

여기서 이미 "켰을 때의 숨은 비용" 하나가 보인다 서비스 코드만 읽어서는 이 API가 쿼리를 몇 개 쓰는지 알 수 없다. 응답 필드를 하나 추가한 것만으로 N+1이 생기고, 그게 서비스 계층 코드리뷰에서는 안 보인다. OSIV는 LazyInitializationException을 막는 대신 N+1을 보이지 않는 곳으로 밀어넣는다.

2. 대가의 정확한 표현 — "오래 잡는다"가 아니라 "노는 커넥션을 잡는다"

많은 답변이 여기서 멈춘다: "OSIV를 켜면 커넥션을 요청이 끝날 때까지 오래 잡는다." 틀린 말은 아니지만 이 표현으로는 왜 그렇게 치명적인지가 설명되지 않는다. 커넥션을 오래 잡는 게 문제라면, 원래 쿼리가 5초 걸리는 무거운 통계 API도 똑같은 문제여야 한다. 그런데 그건 "필요해서 오래 잡는 것"이라 성격이 다르다.

한 단어만 바꾸면 답변의 층이 올라간다

커넥션을 오래 잡는다  →  아무 일도 하지 않는 커넥션을 잡는다

식당 비유 — 주문을 다 받고 음식도 다 나갔는데 손님이 자리에서 통화를 30분 하는 것과 같다. 주방(DB)은 놀고 있는데 테이블(커넥션)은 회전하지 않는다. 매출을 결정하는 것은 주방의 능력이 아니라 테이블 회전율이다.

같은 내용을 구간별로 — 서비스 DB 작업 20ms, 렌더링(또는 JSON 직렬화) 200ms인 화면
요청 구간걸리는 시간이 구간에서 DB로 나가는 쿼리OSIV = false 커넥션OSIV = true 커넥션
컨트롤러 진입~0ms없음안 잡음안 잡음
서비스 @Transactional20msSELECT 몇 건잡음 — 일한다잡음 — 일한다

3. 숫자로 — 처리량 상한과 필요 커넥션 수

외울 공식 두 개 — 둘은 같은 식을 양방향으로 읽은 것이다

① 이 서버가 견디는 트래픽
이론 최대 처리량 = 풀 크기 ÷ 커넥션 점유 시간
커넥션 하나가 초당 1 / 점유시간건을 처리하므로
② 이 트래픽에 필요한 커넥션
필요 커넥션 = 초당 요청 수 × 커넥션 점유 시간
대기행렬 이론의 리틀의 법칙(L = λ × W)을 커넥션에 적용한 것

OSIV는 이 두 식에서 오직 하나, "점유 시간"만 바꾼다. 풀 크기도 트래픽도 그대로인데 점유 시간만 11배가 되면 결과도 그대로 11배 나빠진다. 설정 한 줄이 곱셈의 한 항을 바꾸는 구조라는 것이 이 문항의 골자다.

3-1. 계산 ① — 풀 10개, 렌더링 200ms

처리량 상한으로 읽기

  • false — 점유 20ms → 10 / 0.020 = 500 req/s
  • true — 점유 220ms → 10 / 0.220 ≈ 45 req/s

설정 한 줄로 처리량 상한이 약 11배 떨어진다. 코드도, 사용자가 체감하는 응답 시간(220ms)도 같은데 견딜 수 있는 트래픽만 11분의 1이 된다.

필요 커넥션으로 읽기 — 트래픽 100 req/s

  • false — 100 × 0.020 = 2개 → 풀 10개로 충분(20% 사용)
  • true — 100 × 0.220 = 22개 → 풀 10개로 부족 ⇒ 대기 발생

기본 풀 10개로 시작한 서비스가 100 req/s에서 이미 무너진다. "우리는 트래픽이 그렇게 많지 않은데요"가 위험한 이유 — 임계치가 생각보다 훨씬 낮다.

3-2. 계산 ② — 최악의 조합은 응답 단계의 외부 API 호출

렌더링 200ms도 나쁘지만 가장 나쁜 것은 컨트롤러·응답 조립 단계의 외부 API 호출이다. 렌더링은 우리가 통제할 수 있지만 남의 서버 응답 시간은 통제할 수 없기 때문이다.

4. 진짜 무서운 부분 — 장애 격리가 깨진다 시니어 변별

위 계산에서 한 걸음 더 나가면 이 문항의 시니어 포인트가 나온다. 외부 배송 조회 API가 300ms에서 3초로 느려졌다고 하자.

확인 범위 — 정직하게 붙여야 오히려 신뢰도가 올라가는 단서 커넥션이 정확히 언제 풀로 반환되는지는 Hibernate의 커넥션 릴리스 모드(hibernate.connection.handling_mode)와 트랜잭션 종류(resource-local / JTA)에 따라 달라질 수 있다. 위 계산은 "트랜잭션 밖에서 지연 로딩이 일어나는 구간 동안 커넥션이 세션 종료 시점까지 유지된다"는 널리 통용되는 최악 케이스 모델링이다. 우리 서비스의 실제 값을 알고 싶다면 계산이 아니라 측정이다 — HikariCP의 활성 커넥션 수(hikaricp.connections.active)와 요청 처리 시간을 함께 보면 커넥션 점유 시간이 트랜잭션 구간보다 얼마나 긴지가 그대로 드러난다. 면접에서도 "정확한 값은 릴리스 모드에 따라 다르므로 지표로 확인한다"고 붙이면 좋다.

4-1. 켰을 때의 부작용 하나 더 — 조용한 UPDATE

커넥션 말고 하나가 더 있다. 컨트롤러나 DTO 변환 코드에서 엔티티의 setter를 호출하는 경우가 있는데, OSIV가 켜져 있으면 그 엔티티는 아직 영속 상태다. 영속 상태라는 것은 영속성 컨텍스트가 원본 스냅샷을 들고 변경 감지(dirty checking) 대상으로 계속 지켜보고 있다는 뜻이다.

OSIV = true — 유령 UPDATE의 경로

같은 요청 안에 두 번째 @Transactional 호출이 있으면, 그 트랜잭션이 커밋될 때 변경 감지가 아까 컨트롤러에서 바꾼 값까지 같이 flush한다. 아무도 save()를 부르지 않았는데 UPDATE가 나간다.

OSIV = false — 구조적으로 불가능해진다

컨트롤러에 도달한 엔티티는 이미 준영속(detached) — 영속성 컨텍스트의 관리에서 벗어난 상태 — 이라 아무리 setter를 불러도 DB에 반영되지 않는다. 이 부류의 버그가 발생할 수 없는 코드가 된다.

5. 껐을 때 — 불편이 아니라 설계 강제다

껐을 때 개발자가 치르는 대가를 "트랜잭션 경계를 직접 신경 써야 하는 불편"이라고 말하면 답변으로는 성립하지만 한 층 낮다. 정확한 프레임은 이것이다.

프레임을 한 단계 올리는 문장

OSIV를 끄는 것은 "엔티티는 트랜잭션 밖으로 나가지 않는다"는 설계 원칙을
프레임워크가 강제하게 만드는 일이다

원칙은 원래부터 있었다. 다만 OSIV가 켜져 있으면 그 원칙을 어겨도 아무 일이 일어나지 않아서 지켜지지 않을 뿐이다. 끄는 순간 위반이 즉시 예외로 드러난다. 즉 "불편해진다"가 아니라 "규칙을 어길 수 없게 된다"가 정확하다.

5-1. 강제되는 것의 정체 — 트랜잭션 안에서 다 꺼내거나, DTO로 바꿔 나가거나

끄면 개발자가 하게 되는 일은 두 가지로 수렴한다. 둘 다 "세션이 살아 있는 동안 필요한 걸 다 끝내라"는 같은 요구의 두 형태다.

BEFORE 엔티티를 컨트롤러로 올려보낸다
@Transactional(readOnly = true)
public Order findOrder(Long id) {
    return orderRepository.findById(id).orElseThrow();
}

// 컨트롤러에서 order.getItems()
// → OSIV 덕에 통과. 쿼리는 눈에 안 보인다.
//
// 이 서비스 메서드만 읽어서는
// 이 API 가 쿼리를 1개 쓰는지 51개 쓰는지
// 알 방법이 없다.
AFTER 필요한 것을 트랜잭션 안에서 끝낸다
// ① 필요한 연관을 조회 시점에 명시적으로 함께 읽는다
@Query("select o from Order o join fetch o.items where o.id = :id")
Optional<Order> findWithItems(@Param("id") Long id);

// ② 트랜잭션 안에서 DTO 로 변환해 내보낸다 (근본 처방)
@Transactional(readOnly = true)
public OrderResponse findOrder(Long id) {
    Order order = orderRepository.findWithItems(id).orElseThrow();
    return OrderResponse.from(order);  // 세션이 살아 있는 동안 전부 꺼내 담는다
}   // ← 여기서 세션이 닫히지만, 밖으로 나가는 건 이미 순수 자바 객체다

5-2. 왜 이쪽이 오히려 더 나은 설계인가 — 네 가지

여기서 멈추면 "OSIV를 끄면 코드를 더 써야 한다"로 읽힌다. 이득 쪽을 네 가지로 짚어야 트레이드오프 서술이 된다.

① 이 API가 무슨 쿼리를 쓰는지가 코드에 드러난다
BEFORE는 컨트롤러 + 응답 DTO + Jackson 직렬화 동작까지 전부 머릿속에서 이어붙여야 판단할 수 있다. AFTER는 join fetch가 쿼리에 적혀 있고, 그것 말고는 나갈 쿼리가 없다는 것이 "세션이 닫힌다"는 사실로 보장된다. 코드리뷰에서 성능 문제를 잡을 수 있는지가 여기서 갈린다.
② 응답 스펙이 DB 스키마에서 분리된다
엔티티는 DB 테이블의 모양이고 응답은 클라이언트와의 계약인데, 둘이 같은 객체면 DB 리팩터링이 곧 API 스펙 변경이 된다. 컬럼 하나 추가에 응답 JSON이 조용히 바뀐다. DTO를 세우면 그 연결이 끊긴다.
③ 성능 튜닝의 대상이 명확해진다
"이 화면이 느리다"는 신고에 대해 AFTER는 고칠 곳이 그 DTO를 만드는 쿼리 하나다. 필요하면 엔티티를 거치지 않고 DTO로 직접 프로젝션하도록 바꿀 수도 있다. BEFORE는 어디서 쿼리가 나가는지부터 찾아야 한다.
④ 테스트가 쉬워진다
DTO는 순수 자바 객체라 어떤 컨텍스트에서든 값을 검증할 수 있다. 엔티티를 반환하면 테스트에서도 세션이 살아 있어야 하고, 그래서 테스트에 @Transactional을 붙이게 되고, 그 순간 테스트가 운영과 다른 환경이 된다 — 이 함정이 7절에서 그대로 다시 나온다.
OSIV를 끄는 진짜 이득은 커넥션 절약만이 아니라 쿼리와 경계의 가시성 회복이다
커넥션은 부수적인 이득이고, 설계가 본론이다

5-3. 같은 원칙의 다른 얼굴 — "엔티티 직접 노출 금지" 가산점

같은 3장 중급에 "엔티티를 API 응답으로 직접 노출하면 안 되는 이유"라는 문항이 따로 있다. 그 답은 보통 ① API 스펙이 DB 스키마에 종속된다 ② 지연 로딩 직렬화 폭탄 ③ 순환 참조로 정리된다. 두 문항은 결국 같은 한 줄로 수렴한다.

엔티티 노출 금지

같은 규칙을 사람의 규율로 지킨다 — 리뷰와 컨벤션으로. 어기면 아무 일도 안 일어나므로 시간이 지나면 새어 나간다.

OSIV 끄기

같은 규칙을 런타임이 강제한다. 어기는 순간 예외가 나므로 배포 전에 드러난다.

두 문항이 묻는 하나의 원칙 — "엔티티는 영속성 컨텍스트가 살아 있는 구간 안에서만 존재한다"

5-5. 그럼 왜 기본값이 true인가 — 기본값 해석이 곧 출제 의도에 대한 답

프레임워크의 기본값은 "최적"이 아니라 "가장 덜 놀라는 값"으로 정해진다 만약 기본값이 false였다면, JPA를 처음 쓰는 사람이 튜토리얼 수준의 코드를 짜자마자 LazyInitializationException을 만난다. 프레임워크 입장에서 그건 최악의 첫인상이다. 그래서 입문 난이도와 즉시 동작(works out of the box)을 우선한 방어적 기본값을 골랐고, 대용량 트래픽은 "그 단계에 도달한 팀이 직접 판단할 일"로 남겨뒀다.

그 판단을 미뤄뒀다는 사실 자체를 Spring Boot가 로그로 알려준다. 프로퍼티를 명시하지 않고 애플리케이션을 띄우면 시작 시 이런 경고가 뜬다.

LOG 기동 시 경고 — 마지막 문장을 주목한다
spring.jpa.open-in-view is enabled by default. Therefore, database queries may be
performed during view rendering. Explicitly configure spring.jpa.open-in-view to
disable this warning

이 경고의 진짜 뜻 — 출제 의도("프레임워크 기본값을 의심해본 적 있는가")에 정면으로 답하는 지점

"끄면 경고가 사라진다"  →  "명시적으로 설정하면 경고가 사라진다"

true라고 적어도 경고는 없어진다. 즉 프레임워크가 요구하는 것은 끄는 게 아니라 의식적으로 선택하는 것이다. 그래서 값보다 "명시했다"는 사실이 중요하다는 말이 성립한다.

확인 범위 위 경고 문구는 Spring Boot의 JPA 자동 설정이 출력하는 메시지이고, 세부 표현은 버전에 따라 조금씩 달라질 수 있다. 면접에서는 문구를 그대로 외워 읊기보다 "명시적으로 설정하라고 경고한다"는 취지를 말하는 편이 안전하다. 기본값이 true라는 사실 자체는 Spring Boot 2.x·3.x에서 유지되고 있으나, 실제 프로젝트에서는 application.yml에 명시해두는 것이 정답이라 버전을 기억할 필요 자체가 없어진다.

6. 터질 곳 찾기 — 정적 검색은 "보장" 수단이 될 수 없다

면접관이 붙이는 시나리오: "OSIV가 켜진 채로 3년치 코드가 쌓인 운영 서비스에서 커넥션 풀 고갈이 실제로 발생했다. 끄기로 결정했다. false로 배포하면 무슨 일이 벌어지나? 그 사고를 배포 전에 막으려면 무엇을 하겠나?"

방향은 누구나 안다 — "트랜잭션 밖에서 지연 로딩하는 곳을 찾아야 한다." 변별은 "구체적으로 어떻게 찾을 것이며, 놓친 게 없다는 걸 무엇으로 보장하느냐"에서 난다.

흔한 답이 "지연 로딩 필드의 게터 사용처를 검색한다"이다. 탐색 범위를 좁히는 발상으로는 합리적이지만, 보장 수단으로는 성립하지 않는다. 이유는 하나다.

지연 로딩을 트리거하는 코드의 상당수는 게터 호출이 소스에 존재하지 않는다

암기 — 검색에 안 걸리는 6종을 "동사"로 외운다

나가면서 (Jackson 직렬화) 찍히면서 (toString 로그) 담기면서 (equals/hashCode)
그려지면서 (템플릿) 갈아타면서 (프록시·상속) 옮겨지면서 (매핑 라이브러리)
엔티티가 나가고 · 찍히고 · 담기고 · 그려지고 · 갈아타고 · 옮겨질 때 전부 터진다

그래서 답변의 방향을 통째로 바꿔야 한다

찾는 것이 아니라, 터지게 만들어서 세는 것이다

사람이 코드를 읽어 목록을 만드는 대신, OSIV를 끈 환경에서 코드를 실제로 실행시켜 예외가 나는 지점을 기계가 수집하게 한다. 이 한 문장이 6~7절 전체의 설계 원리이고, 이걸 말하는 순간 답변의 성격이 "노력하겠다"에서 "장치를 건다"로 바뀐다.

7. 보장 장치 두 개 — 지금 있는 위반을 세고, 앞으로의 위반을 막는다

7-1. 장치 ① — 새 테스트를 쓰는 게 아니라, 있는 테스트를 설정만 바꿔 한 번 더 돌린다

Spring은 시스템 프로퍼티를 Environment의 상위 우선순위 프로퍼티 소스로 읽는다. 그래서 테스트 코드를 한 줄도 고치지 않고 JVM 옵션만으로 OSIV를 끌 수 있다.

Gradle build.gradle.kts — 기존 테스트를 OSIV 끈 상태로 한 번 더 도는 태스크
tasks.register<Test>("osivOffTest") {
    useJUnitPlatform()
    // Spring 은 시스템 프로퍼티를 application.yml 보다 우선해서 읽는다
    systemProperty("spring.jpa.open-in-view", "false")

    // 컨트롤러부터 DB 까지 관통하는 통합 테스트만 대상으로
    filter { includeTestsMatching("*ControllerTest") }

    // 이 태스크의 실패는 '지금은' 빌드를 깨지 않게 두고, 리포트만 수집한다
    ignoreFailures = true   // 전환이 끝나면 false 로 바꿔 회귀 방지선으로 승격
}

반드시 함께 말해야 할 함정 세 가지 — 암기 "트 · 슬 · 옵"

트
테스트 클래스에 @Transactional이 붙어 있으면 이 방법이 통째로 무력화된다. 테스트에 트랜잭션이 걸리면 테스트 메서드 전체 구간에서 세션이 살아 있어, OSIV를 꺼도 지연 로딩이 통과한다. 통과했다는 결과가 거짓 안심이 된다 — 가장 위험한 실패 방식이다. 컨트롤러 통합 테스트에서는 @Transactional을 빼고 데이터 정리는 별도 방식(테이블 truncate 등)으로 한다.
슬
@WebMvcTest 슬라이스 테스트는 이 검증에 쓸 수 없다. 서비스가 모킹돼 있어 JPA가 아예 개입하지 않는다. 필요한 것은 @SpringBootTest + 실제 DB로 컨트롤러 → 서비스 → 리포지토리 → 직렬화까지 관통하는 테스트다. (MockMvc를 써도 전체 컨텍스트로 띄우면 인터셉터와 메시지 컨버터가 실제로 동작하므로 직렬화 단계의 예외까지 잡힌다.)
옵
hibernate.enable_lazy_load_no_trans가 켜져 있으면 예외 대신 조용히 쿼리가 나간다. 이 옵션은 세션 밖 지연 로딩을 임시 세션으로 처리해주는데, 문제를 숨기는 대신 요청마다 세션을 새로 여는 최악의 성능 특성을 갖는다. 전환 작업 전에 이 값이 꺼져 있는지부터 확인해야 검증 자체가 유효하다. 가산점

7-2. 장치 ② — ArchUnit으로 재발까지 막는다

통합 테스트는 지금 있는 위반을 찾아준다. 하지만 다음 주에 누군가 다시 컨트롤러에서 엔티티를 반환하면 똑같은 일이 반복된다. 그래서 원인 쪽에 못을 하나 박는다 — "컨트롤러는 엔티티를 반환할 수 없다"를 빌드에서 강제한다.

ArchUnit은 아키텍처 규칙을 테스트 코드로 표현해 빌드에서 검사하게 해주는 라이브러리다. "이 패키지는 저 패키지를 참조하면 안 된다" 같은, 컴파일러는 모르지만 팀은 합의한 규칙을 기계가 지키게 만든다.

Java 컨트롤러의 엔티티 반환 금지 룰
@AnalyzeClasses(packages = "com.example", importOptions = ImportOption.DoNotIncludeTests.class)
class WebLayerRulesTest {

    @ArchTest
    static final ArchRule 컨트롤러는_엔티티를_반환하면_안_된다 =
            methods()
                .that().areDeclaredInClassesThat().areAnnotatedWith(RestController.class)
                .and().arePublic()
                .should(new ArchCondition<JavaMethod>("반환 타입에 @Entity 가 없어야 한다") {
                    @Override
                    public void check(JavaMethod method, ConditionEvents events) {
                        flatten(method.getReturnType())
                            .filter(type -> type.isAnnotatedWith(Entity.class))
                            .forEach(type -> events.add(SimpleConditionEvent.violated(
                                    method,
                                    method.getFullName() + " 가 엔티티 "
                                        + type.getSimpleName() + " 를 반환한다"
                                        + " (OSIV 를 끄면 직렬화 시점에 터진다)")));
                    }
                });

    /**
     * ResponseEntity<List<Order>> 처럼 제네릭 안쪽에 숨은 엔티티까지 찾아내려면
     * 타입 인자를 재귀적으로 펼쳐야 한다. 겉 타입만 보면 ResponseEntity 라서 통과해버린다.
     */
    private static Stream<JavaClass> flatten(JavaType type) {
        Stream<JavaClass> self = Stream.of(type.toErasure());
        if (type instanceof JavaParameterizedType parameterized) {
            return Stream.concat(self,
                    parameterized.getActualTypeArguments().stream()
                                 .flatMap(WebLayerRulesTest::flatten));
        }
        return self;
    }
}
이 룰의 핵심은 flatten이다 — 여기를 빠뜨리면 룰이 사실상 무용지물이 된다 대부분의 위반은 Order를 직접 반환하는 형태가 아니라 ResponseEntity<List<Order>>, Page<Order>처럼 제네릭 안에 숨어 있다. 겉 타입만 검사하는 룰은 이걸 전부 놓친다 — 검사는 초록불인데 배포하면 터지는, 7-1의 @Transactional 함정과 같은 종류의 거짓 안심이다.
Java 더 거칠지만 더 강력한 대안 — 계층 자체를 막는다
@ArchTest
static final ArchRule 웹_계층은_엔티티에_의존하지_않는다 =
        noClasses().that().resideInAPackage("..api..")
                   .should().dependOnClassesThat().resideInAPackage("..domain.entity..");

이쪽은 반환 타입뿐 아니라 파라미터·지역 변수·import까지 전부 막는다. 강력한 만큼 기존 코드가 대량으로 걸리므로, 신규 모듈부터 적용하고 레거시는 아래 방식으로 푼다.

레거시 도입 요령 — FreezingArchRule로 "출혈부터 멈춘다" 가산점

기존 위반이 200개인 상태에서 룰을 켜면 빌드가 안 돌아 결국 룰을 지우게 된다. ArchUnit의 FreezingArchRule.freeze(rule)로 현재 위반을 동결하면 기존 것은 통과시키고 신규 위반만 실패시킬 수 있다.

@ArchTest
static final ArchRule 컨트롤러_엔티티_반환_금지 =
        FreezingArchRule.freeze(컨트롤러는_엔티티를_반환하면_안_된다);
// 첫 실행에서 현재 위반을 파일로 기록 → 이후엔 새 위반만 빌드를 깬다
고치는 속도보다 늘어나는 속도가 빠르면 영원히 못 끝난다
그래서 신규 차단이 기존 정리보다 먼저다. 동결 목록이 0이 되는 것이 ①단계의 완료 기준이 된다
확인 범위 methods(), ArchCondition, SimpleConditionEvent, JavaParameterizedType, FreezingArchRule은 모두 ArchUnit의 공개 API이지만, 정확한 시그니처(특히 getReturnType()이 JavaClass를 반환하던 구버전과 JavaType을 반환하는 신버전)는 버전에 따라 다르므로 프로젝트에서 컴파일로 확인해야 한다. 면접에서는 "제네릭 타입 인자까지 재귀로 펼쳐야 한다"는 설계 포인트를 말하는 것이 API 이름을 정확히 대는 것보다 중요하다.

7-3. 세 층을 함께 놓고 본다 — "보장"이라는 단어는 한 층에만 붙는다

층수단언제 걸리나잡는 것못 잡는 것"보장"을 붙일 수 있나
정적게터 사용처 검색즉시명시적 호출직렬화 · toString · 프록시 · 템플릿 · 매핑 라이브러리아니오 — 탐색용

실행OSIV off 통합 테스트CI실제로 터지는 모든 경로테스트가 없는 경로예 — 커버리지 범위 안에서
이 표는 이 카테고리 전체에서 반복되는 구조와 같다 N+1 탐지에서도 결론이 같았다 — "주의 깊게 보겠다"는 대책이 아니고, 회귀는 사람이 아니라 CI가 막는다. N+1의 쿼리 수 단정 테스트, fetch join + 페이징에서 경고를 예외로 승격시키는 설정, 그리고 여기의 OSIV off 프로파일 테스트는 전부 같은 도구 상자다. 정적 검색은 지워도 되는 층이 아니라, 셋 중 유일하게 "보장"이라는 단어를 붙일 수 없는 층일 뿐이다.

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

OSIV 한 문장 정의?
Spring Boot 기본값 true. 트랜잭션이 서비스에서 끝난 뒤에도 EntityManager를 응답 완료까지 열어둔다. 요점은 트랜잭션 경계 ≠ 영속성 컨텍스트 경계.
대가의 정확한 표현?
"커넥션을 오래 잡는다" → "아무 일도 하지 않는 커넥션을 잡는다." 렌더링·외부 호출 구간에 쿼리는 0건인데 커넥션은 풀에서 빠져 있다.
외울 숫자 두 쌍?
풀 10 · 렌더 200ms → 500 → 45 req/s(11배) / 풀 20 · 외부 300ms → 400 → 54 req/s(7배). 응답 시간은 두 경우 동일하다는 게 핵심.
공식 두 개?
처리량 = 풀 크기 ÷ 점유 시간 / 필요 커넥션 = 초당 요청 수 × 점유 시간(리틀의 법칙). OSIV는 "점유 시간"이라는 한 항만 바꾼다.
시니어 포인트 한 문장?
"남의 장애가 우리 DB 커넥션 풀을 타고 들어온다." 외부 API가 3초로 느려지면 점유 3,070ms → 풀 고갈 → 무관한 로그인·결제까지 전면 장애. OSIV는 성능 설정이 아니라 장애 전파 경로.
껐을 때의 진짜 의미?
불편이 아니라 설계 강제 — "엔티티는 트랜잭션 밖으로 나가지 않는다"를 런타임이 강제한다. 이득은 커넥션 절약보다 쿼리와 경계의 가시성 회복.
왜 기본값이 true인가?
기본값은 "최적"이 아니라 "가장 덜 놀라는 값". 그리고 경고 문구는 "끄라"가 아니라 "명시적으로 설정하라" — 값보다 명시했다는 사실이 중요하다.
검색이 못 잡는 6종?
엔티티가 나가고(Jackson) · 찍히고(toString) · 담기고(equals/hashCode) · 그려지고(템플릿) · 갈아타고(프록시·상속) · 옮겨질 때(매핑 라이브러리). 전부 게터가 소스에 없다.
보장은 어디서 나오나?
찾는 게 아니라 터지게 만들어서 세는 것. osivOffTest(실행 층)만 "보장"을 붙일 수 있고, ArchUnit은 재발 차단, 정적 검색은 탐색용일 뿐.
테스트 함정 3종?
트 · 슬 · 옵 — 테스트에 @Transactional 금지 / @WebMvcTest 슬라이스로는 검증 불가 / enable_lazy_load_no_trans가 켜져 있으면 예외 대신 조용히 쿼리.
전환 순서와 완료 기준?
세 · 옮 · 끈 — ① DTO 경계(ArchUnit 위반 0) → ② 트랜잭션 안 변환(osivOffTest 실패 0) → ③ 끄기(카나리 예외 0). 끄는 것은 마지막.
카나리에서 볼 지표 두 개?
① LazyInitializationException 발생 건수(사고가 나는가) ② 활성 커넥션 수·획득 대기 시간(목적을 달성했는가). 후자가 안 줄면 OSIV가 병목이 아니었던 것.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

OSIV를 끄면 API 응답이 빨라지나요? 필수힌트: "성능"이라는 단어를 뭉뚱그리지 않는 것이 채점 지점이다

대체로 아니다. 요청 하나만 놓고 보면 하는 일이 같으므로 응답 시간은 거의 그대로다. 바뀌는 것은 동시에 처리 가능한 요청 수(처리량)다. 3-2의 계산에서 응답 시간은 370ms로 두 경우가 동일했고, 달라진 것은 400 req/s와 54 req/s였다.

오히려 끄면 개별 응답이 느려지는 경우도 있다. 지연 로딩으로 나가던 쿼리를 fetch join으로 합치면서 조인 결과가 커질 수 있기 때문이다.

정확한 표현 — "성능이 좋아진다" → "커넥션이라는 한정 자원의 회전율이 올라가, 같은 하드웨어로 더 많은 트래픽을 견딘다"
특정 엔드포인트만 OSIV를 켤 수는 없나요?힌트: 기술적 가능 여부보다, 이 질문의 방향이 반대라는 점을 짚는다

spring.jpa.open-in-view는 애플리케이션 전역 스위치라 URL 단위로 켜고 끌 수 없다. (직접 인터셉터를 등록해 경로별로 적용하는 것은 기술적으로 가능하지만, "어떤 엔드포인트는 엔티티가 트랜잭션 밖으로 나가도 된다"는 예외를 공식화하는 셈이라 권하지 않는다.)

그런데 이 질문은 사실 방향이 반대다. 필요한 것은 "OSIV를 켠 엔드포인트"가 아니라 "세션을 명시적으로 연장할 방법"이고, 그 답이 fetch join · @EntityGraph · DTO 변환이다.

전역 설정으로 예외를 만드는 대신 지점별 처방으로 푸는 것이 원칙이다 — LazyInitializationException 문서의 "처방의 범위를 문제의 범위에 맞춘다"와 같은 이야기다.

OSIV가 켜져 있는데도 LazyInitializationException이 나는 경우가 있나요? 필수힌트: OSIV가 작용하는 범위가 어디까지인지를 먼저 말한다

있다. OSIV는 웹 요청 스코프에만 작용하므로 그 밖에서는 무력하다.

테스트 코드@Async · @Scheduled · 별도 스레드배치응답 직렬화가 끝난 뒤의 코드엔티티를 캐시에 담아 다음 요청에서 재사용

별도 스레드가 목록에 있는 이유는 세션이 스레드에 바인딩되어 있기 때문이다(1-3). 요청 스레드가 연 세션은 @Async로 넘어간 다른 스레드에서는 보이지 않는다.

이 목록이 실무적으로 중요한 이유 — "우리는 OSIV로 잘 돌아가고 있다"는 팀도 사실은 이미 이 예외를 만나고 있다. 다만 발생 지점이 웹 요청 밖이라 원인을 OSIV와 연결하지 못했을 뿐이다. 그런 팀에게 OSIV 끄기를 설득할 때 쓸 수 있는 근거이기도 하다.

컨트롤러에서 엔티티를 반환할 때 Hibernate5Module 같은 Jackson 모듈을 쓰면 되지 않나요? 함정힌트: 동작은 한다. 그런데 무엇이 바뀌는지 — "실패 방식"을 보라

동작은 한다. 초기화되지 않은 프록시를 예외 대신 null로 직렬화해주므로 예외는 사라진다. 그런데 이건 해결이 아니라 은폐이고, 은폐 중에서도 나쁜 쪽이다.

이유는 실패 방식이 바뀌기 때문이다.

예외 — 시끄러운 실패

즉시 터져서 바로 발견된다. 500 에러는 아프지만 정직하다.

null — 조용한 실패

조용히 잘못된 응답을 내보낸다. 클라이언트는 "주문 항목이 없는 주문"을 정상 200 OK로 받는다.

데이터가 틀린 채 200 OK가 나가는 것은 500 에러보다 훨씬 늦게 발견되고 훨씬 비싸게 수습된다.

정리하면 이 모듈은 "엔티티를 직렬화하겠다"는 잘못된 전제를 편하게 만들어주는 도구다. 전제 자체를 없애는 것(DTO 반환)이 답이다. 같은 이유로 enable_lazy_load_no_trans도 답이 아니다 — 이쪽은 조용히 쿼리를 더 쏘는 방식으로 숨긴다.

OSIV를 끄면 커넥션 풀 크기를 줄여도 되나요? 가산점힌트: 근거는 생긴다. 그런데 순서가 있다. 그리고 반대 방향의 함정도 하나

줄일 수 있는 근거가 생기는 것은 맞지만, 끄자마자 줄이는 건 위험하다. 필요한 커넥션 수는 초당 요청 수 × 커넥션 점유 시간이고, OSIV를 끄면 점유 시간이 줄어드니 같은 트래픽에 더 적은 커넥션으로 충분해진다(3-2에서 37개 → 5개).

다만 순서가 있다. 먼저 끄고 → 실제 활성 커넥션 지표를 관찰하고 → 그 데이터로 줄인다. 계산값만 믿고 줄이면 트래픽 스파이크나 느린 쿼리 한 건에 여유가 사라진다.

한 걸음 더 나가면 좋은 지적이 하나 있다 — 커넥션 풀은 크게 잡을수록 좋은 게 아니다. DB의 max_connections는 유한하고, 커넥션이 많아지면 DB 쪽 컨텍스트 스위칭과 락 경합이 늘어 오히려 전체 처리량이 떨어진다.

"OSIV를 켜둔 채 풀을 늘려서 버틴다"가 지속 가능하지 않은 이유
풀을 늘리는 것은 문제를 애플리케이션에서 DB로 옮기는 것일 뿐이다
통합 테스트가 거의 없는 3년치 레거시입니다. 테스트부터 다 쓰면 반년이 걸립니다. 무엇부터 하시겠습니까? 시니어 변별힌트: "전수 커버리지"를 목표로 잡는 순간 이 프로젝트는 끝나지 않는다. 위험을 계층화한다
1
위험이 높은 교집합부터 찾는다. 두 축을 곱한다 — ⓐ 컨트롤러가 엔티티를 반환하는 엔드포인트(ArchUnit 룰을 리포트 모드로 한 번 돌리면 목록이 즉시 나온다) ⓑ 트래픽 상위 엔드포인트(액세스 로그나 APM에서 뽑는다). 교집합이 "터지면 가장 아픈 곳"이고, 여기부터 테스트를 쓴다.
2
①②단계(DTO 경계 수립)는 테스트를 기다리지 않고 진행한다. 이 리팩터링은 OSIV가 켜진 상태에서 동작이 동일하므로 지금 배포해도 위험이 낮다. 안전망이 없다는 이유로 멈출 이유가 없고, 오히려 이걸 진행할수록 ③단계의 위험이 계속 줄어든다.
3
ArchUnit 룰을 FreezingArchRule로 먼저 걸어 출혈을 멈춘다. 기존 200개는 동결하되 신규 위반은 즉시 빌드를 깨게 한다. 고치는 속도보다 늘어나는 속도가 빠르면 영원히 못 끝난다 — 그래서 신규 차단이 기존 정리보다 먼저다.
4
커버리지 사각지대는 배포 방식으로 메운다. 카나리로 영향 범위를 1/N로 줄이고, LazyInitializationException을 알림으로 걸어 남은 지점을 운영에서 수집한다. 테스트로 못 덮은 만큼을 배포 전략으로 갚는 구조다.
핵심 메시지 — "안전망이 없으니 못 한다"가 아니라 "안전망의 크기에 맞춰 한 번에 바꾸는 범위를 줄인다"
커버리지가 낮으면 카나리 비중을 낮추고 관찰 기간을 늘린다. 이 교환 관계를 말할 수 있으면 전환 작업을 실제로 해본 사람처럼 들린다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

OSIV를 끄면 지연 로딩을 아예 못 쓰게 되나요?힌트: 무엇이 바뀌고 무엇이 안 바뀌는지를 경계로 잘라 말한다

아니다. 트랜잭션 안에서는 지금까지와 똑같이 동작한다. OSIV는 지연 로딩 기능을 끄는 스위치가 아니라, 세션이 언제 닫히는지를 바꾸는 스위치다.

안 바뀌는 것 — 트랜잭션 안

서비스 메서드 안에서의 order.getItems()는 그대로 추가 SELECT가 나가고 잘 동작한다. N+1이 생길 수 있다는 것도 그대로다.

바뀌는 것 — 트랜잭션 밖

컨트롤러·직렬화·템플릿 단계의 지연 로딩만 예외로 막힌다. 즉 "경계를 넘어간 뒤의 로딩"만 금지된다.

그래서 정확한 표현은 "지연 로딩을 못 쓴다"가 아니라 "지연 로딩의 사용 구간이 트랜잭션 안으로 제한된다"이다. 이 구분을 하면 OSIV를 끄는 것과 FetchType.EAGER로 바꾸는 것을 혼동하지 않는다는 신호가 된다 — EAGER는 로딩 전략을 바꾸는 것이고, OSIV는 세션 수명을 바꾸는 것으로 축이 완전히 다르다.

OSIV를 껐더니 @Transactional 없이 리포지토리만 호출하던 조회 코드에서 예외가 납니다. 왜죠? 가산점힌트: Spring Data JPA 리포지토리 메서드가 스스로 무엇을 여는지 떠올린다

Spring Data JPA의 리포지토리 구현체는 메서드마다 자체 트랜잭션을 갖는다. 그래서 조회 자체는 트랜잭션 없이도 성공한다 — 여기서 사람들이 "트랜잭션이 없어도 잘 되네"라고 착각한다.

문제는 그 트랜잭션이 리포지토리 메서드가 끝나는 순간 닫힌다는 것이다. OSIV가 꺼져 있으면 영속성 컨텍스트도 거기서 함께 닫히므로, 반환된 엔티티는 받는 즉시 준영속(detached)이다. 그래서 바로 다음 줄의 지연 로딩이 터진다.

OSIV가 켜져 있을 때는 이게 안 보였다. 인터셉터가 연 세션에 리포지토리의 트랜잭션이 참여했을 뿐이라, 트랜잭션이 끝나도 세션은 요청 내내 살아 있었기 때문이다(1-3).

그래서 처방은 "트랜잭션을 붙이는 것"이 아니라 "트랜잭션 안에서 필요한 것을 다 끝내는 것"
서비스 메서드에 @Transactional(readOnly = true)를 붙이고 그 안에서 fetch join 또는 DTO 변환까지 마친다 — 5-1의 AFTER 그대로다
①②(DTO 경계 수립)만 다 해두고 ③(끄기)은 안 하면 안 되나요? 함정힌트: 얻는 것 중 무엇이 남고 무엇이 사라지는지 갈라 본다

절반만 얻고 절반은 못 얻는다. 두 이득을 갈라 봐야 답이 나온다.

①②만으로 얻는 것 — 설계 이득

응답 스펙과 스키마의 분리, 쿼리 가시성 회복. 이건 OSIV 설정과 무관하게 유효하다.

③ 없이는 못 얻는 것 — 자원 이득과 강제력

커넥션 점유 시간은 1밀리초도 줄지 않는다. 세션을 닫는 것은 ③뿐이기 때문이다. 그리고 규칙이 강제되지 않으므로 시간이 지나면 다시 새어 나간다.

강제력이 없다는 점이 특히 중요하다. ArchUnit 룰은 "컨트롤러가 엔티티를 반환하는 것"을 막을 뿐, "서비스가 엔티티를 반환하고 컨트롤러가 그걸 소비하며 지연 로딩하는 것"은 못 막는다(7-3 표의 "못 잡는 것"). 그 구멍을 런타임에서 막아주는 것이 ③이다.

정리하면 ①②는 ③을 안전하게 만들기 위한 준비이고, ③은 ①②를 영구히 유지시키는 자물쇠다. 둘 중 하나만 하면 나머지 하나의 가치도 시간이 지나며 깎인다.

우리 서비스가 실제로 커넥션을 얼마나 오래 잡는지 어떻게 확인하나요? 시니어 변별힌트: 계산이 아니라 측정. 그리고 "무엇과 무엇을 나란히 보는가"가 핵심이다

계산은 최악 케이스 모델링이고, 실제 값은 측정으로 얻는다. 커넥션이 정확히 언제 반환되는지는 Hibernate의 커넥션 릴리스 모드(hibernate.connection.handling_mode)와 트랜잭션 종류에 따라 달라질 수 있기 때문이다.

보는 방법의 핵심은 "두 시간을 나란히 놓는 것"이다.

① 커넥션 점유 시간

HikariCP의 활성 커넥션 수(hikaricp.connections.active)와 커넥션 획득 대기 시간. 활성 수가 트래픽 대비 비정상적으로 높으면 점유가 길다는 신호다.

② 실제 DB 작업 시간

트랜잭션 구간의 길이와 요청 전체 처리 시간. 둘의 차이가 곧 "노는 점유" 후보 구간이다.

판정 기준은 간단하다 — 활성 커넥션 수 ÷ 초당 요청 수로 역산한 평균 점유 시간이 트랜잭션 구간보다 뚜렷하게 길면, 그 초과분이 OSIV가 잡고 있는 시간이다. 카나리 인스턴스에서 이 값이 줄어드는지가 8-2의 두 번째 지표이기도 하다.

면접에서의 사용법 — 숫자를 단정하지 말고 "정확한 값은 릴리스 모드에 따라 다르므로 지표로 확인한다"고 붙이면 오히려 신뢰도가 올라간다. 계산은 의사결정의 방향을 잡는 데 쓰고, 근거는 측정에서 가져오는 것이 순서다.

한 줄 요약
OSIV는 트랜잭션이 끝난 뒤에도 EntityManager를 응답 완료까지 열어두는 Spring Boot의 기본값(true)이고, 그 대가는 "커넥션을 오래 잡는 것"이 아니라 렌더링·외부 호출처럼 DB에 아무 일도 시키지 않는 구간 내내 커넥션을 잡아 외부 시스템의 지연까지 우리 DB 풀로 끌어들이는 것이다 — 풀 10개에 렌더링 200ms면 처리량 상한이 500 req/s에서 45 req/s로 주저앉는다. 그래서 대용량 서비스는 끄되, 끄는 것은 마지막 단계이고 그 앞에 DTO 경계 수립과 open-in-view=false 통합 테스트·ArchUnit 룰이라는 기계적 보장 장치가 먼저 와야 한다. 어디가 터질지는 검색으로 찾는 게 아니라, 터지게 만들어서 세는 것이다.
