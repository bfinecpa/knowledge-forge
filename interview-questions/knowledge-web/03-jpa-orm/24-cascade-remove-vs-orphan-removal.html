CascadeType.REMOVE와 orphanRemoval
삭제의 방아쇠가 몇 개인가

면접 질문: "Post 1:N Attachment에서 cascade = CascadeType.REMOVE와 orphanRemoval = true의 차이는? 각각의 사고 위험은?"

핵심 관전 포인트 — 둘 다 "부모를 지우면 자식도 지운다"를 해주지만 방아쇠(트리거)의 개수가 다르다. CascadeType.REMOVE의 방아쇠는 하나 — 부모에 remove()가 호출될 때뿐이다. orphanRemoval = true는 방아쇠가 둘 — 부모 삭제에 더해 "부모와의 연결이 끊긴 순간"에도 자식을 지운다. 즉 post.getAttachments().remove(a) 한 줄이 곧 delete from attachment where id = ?가 된다. 컬렉션에서 빼는 행위가 삭제 명령이 되는 것이 결정적 차이다. 사고는 이 비대칭에서 나온다 — ① orphanRemoval은 "목록을 갈아끼우려던" 코드(clear() + addAll(), 컬렉션 필드 재할당)가 전건 DELETE가 된다. 변경 감지가 만드는 "안 시킨 UPDATE"의 삭제판이고, UPDATE와 달리 되돌릴 수 없다. ② CascadeType.REMOVE는 자식이 다른 엔티티와 공유되는 참조일 때 부모 삭제가 공유 자원을 지운다. 그리고 이게 대부분 CascadeType.ALL에 REMOVE가 들어 있어서 의도치 않게 켜진다. 공통 비용은 자식 수만큼 DELETE 문이 만들어진다는 것이고(1,000건이면 DELETE 1,000번), 벌크 DELETE로 내려가면 영속성 컨텍스트 불일치가 따라온다. 판단 기준은 하나다 — 자식이 부모 없이는 존재 의미가 없는 종속 관계(Aggregate 안쪽)일 때만 켠다. 마지막으로 이 유형은 안전망으로 원천 차단할 수 있다 — 컬렉션을 unmodifiableList로만 노출하고 addAttachment/removeAttachment만 열면 clear()도 재할당도 애초에 불가능해진다.
  • 1
    차이를 "방아쇠의 개수"로 말한다 — CascadeType.REMOVE는 부모 삭제 하나, orphanRemoval은 거기에 연결 해제가 하나 더. 그래서 post.getAttachments().remove(a) 한 줄이 전자에서는 아무 일도 안 일어나고, 후자에서는 곧 DELETE다. "orphanRemoval이 더 강력하다" 같은 형용사가 아니라 이 비대칭이 답이다.

0. 질문 + 출제 의도

질문: "Post 1:N Attachment에서 cascade = CascadeType.REMOVE와 orphanRemoval = true의 차이는? 각각의 사고 위험은?"

출제 의도: "편의 설정 하나가 '부모를 지웠더니 공유되던 자식까지 사라지는' 연쇄 삭제 사고를 만든다. 파급 범위를 모르는 편의 기능은 쓰지 않는 신중함을 본다."

즉 이 문항이 재는 것은 애노테이션 두 개의 뜻이 아니다. "동작을 자동화하는 옵션을 켤 때, 그 자동화가 어디까지 번지는지를 확인하고 켜는 사람인가"를 본다. cascade와 orphanRemoval은 켜기는 한 단어인데 파급은 데이터 유실인 전형적인 비대칭 옵션이라, 신중함을 재기에 딱 맞는 소재다.

채점 지점 네 층

① 차이를 트리거로 말하는가
"더 강력하다" 같은 형용사가 아니라 "REMOVE는 부모 삭제 하나, orphanRemoval은 거기에 연결 해제까지"라는 방아쇠의 개수로.
② 사고를 코드 한 줄로 대는가
attachments.clear(), this.attachments = newList. 문장이 아니라 줄로 지목할 수 있어야 관찰해 본 사람이다.
③ ALL에 REMOVE가 있음을 아는가
실무 사고의 대부분은 REMOVE를 명시적으로 켠 사람이 아니라 ALL을 관성으로 쓴 사람에게서 난다.
④ 켜는 기준을 말할 수 있는가
"종속 관계일 때만"이라는 Aggregate 경계 감각. 기준 없이 켜면 그것은 결정이 아니라 습관이다.
이 페이지가 겨냥하는 함정 세 개 ① "둘 다 자식을 지웁니다"에서 멈추는 것 — 맞는 말이지만 언제 지우는지가 이 질문의 전부다(2·3절). 차이를 못 대면 옵션을 켜본 적은 있어도 그 결과를 관찰한 적은 없는 것으로 들린다.
② "orphanRemoval이 더 안전하다/위험하다"로 단정하는 것 — 안전·위험은 자식이 어떤 성격인지에 달렸고 옵션 자체의 속성이 아니다(8절). 종속 자식에게는 orphanRemoval이 정답이고, 공유 자식에게는 둘 다 오답이다.
③ DB의 ON DELETE CASCADE와 같은 것이라고 말하는 것 — 이름은 닮았지만 동작 주체가 다르다(7절). 이 둘을 구분 못 하면 "JPA를 껐다 켰다 하는 삭제"의 부작용을 설명할 수 없다.

기준 환경: Hibernate 6.x / Jakarta Persistence 3.x, DB는 PostgreSQL. 예외 메시지와 실행 순서는 Hibernate 6.6 코드를 근거로 한다.

1. 개념 세우기 — cascade는 "SQL"이 아니라 "호출"의 자동화

이 절은 개념을 처음부터 쌓는다. cascade를 한 번도 안 켜봤어도 2절부터 읽을 수 있게 만드는 것이 목적이다. 등장인물은 둘 — Post(게시글)와 Attachment(첨부파일)다.

1-1. 전제 — cascade가 없을 때의 코드

@Entity
public class Post {
    @Id @GeneratedValue
    private Long id;
    private String title;

    @OneToMany(mappedBy = "post")           // cascade 없음, orphanRemoval 없음
    private List<Attachment> attachments = new ArrayList<>();
}

@Entity
public class Attachment {
    @Id @GeneratedValue
    private Long id;
    private String fileName;

    @ManyToOne(fetch = FetchType.LAZY)      // 연관관계의 주인 (FK를 가진 쪽)
    @JoinColumn(name = "post_id")
    private Post post;
}
before 자식마다 리포지토리를 직접 호출한다
@Transactional
public void write(String title, List<String> fileNames) {
    Post post = new Post(title);
    postRepository.save(post);                       // ① 부모 저장

    for (String name : fileNames) {
        Attachment a = new Attachment(name, post);
        attachmentRepository.save(a);                // ② 자식마다 저장 — 빠뜨리면 조용히 안 들어간다
    }
}

부모만 save()하고 자식을 빠뜨리면 첨부파일은 아무 예외 없이 그냥 저장되지 않는다. 영속성 컨텍스트는 save()(정확히는 persist())를 호출한 엔티티만 관리 대상으로 삼기 때문이다. 자식이 늘어날수록 이 "리포지토리를 하나씩 부르는 코드"가 서비스 계층에 쌓인다.

1-2. cascade = "부모에 한 작업을 자식에게도 전파한다"

cascade(영속성 전이)는 이 반복을 없애는 장치다. 이름은 "폭포처럼 아래로 흘러내린다"는 뜻에서 왔다 — 부모에 부은 작업이 자식으로 흘러내리는 그림이다.

after 부모만 저장하면 컬렉션에 담긴 자식이 함께 저장된다
@OneToMany(mappedBy = "post", cascade = CascadeType.PERSIST)
private List<Attachment> attachments = new ArrayList<>();

// ---- 서비스 ----
@Transactional
public void write(String title, List<String> fileNames) {
    Post post = new Post(title);
    for (String name : fileNames) {
        post.addAttachment(new Attachment(name));    // 컬렉션에 담기만 한다
    }
    postRepository.save(post);                       // 자식까지 INSERT
}

"전파"의 정확한 뜻 — 여기서 이 문서 전체가 갈린다

cascade는 SQL을 만들어내는 기능이 아니라, EntityManager의 메서드 호출을 자식에게 대신 호출해주는 기능이다. persist(post)를 부르면 JPA가 post.attachments를 순회하며 각 자식에 대해 persist(child)를 호출해준다 — 그뿐이다. 사람이 손으로 부르던 걸 대신 불러주는, 호출의 자동화다.

따름정리 ① — 애플리케이션 레벨의 기능이다
DB는 이런 설정이 있는지도 모른다. JPA를 거치지 않는 경로(네이티브 쿼리, 벌크 연산, DBA가 콘솔에서 친 SQL)에는 전혀 적용되지 않는다.
따름정리 ② — 자식이 메모리에 올라와 있어야 한다
부모의 컬렉션이 지연 로딩 상태면 JPA는 전파하기 위해 먼저 자식을 SELECT로 다 읽는다. 6절의 성능 문제가 여기서 출발한다.

1-3. CascadeType 여섯 가지 — 그리고 이 문서의 출발점

전파되는 것은 "SQL"이 아니라 EntityManager의 메서드 호출이다
값전파하는 작업언제 일어나나
PERSIST저장(persist)부모를 새로 저장할 때 자식도 INSERT
MERGE병합(merge)준영속 부모를 다시 붙일 때 자식도 함께
REMOVE삭제(remove)부모를 삭제할 때 자식도 DELETE
REFRESH새로고침(refresh)부모를 DB에서 다시 읽을 때 자식도
DETACH분리(detach)부모를 영속성 컨텍스트에서 뗄 때 자식도
ALL위 다섯 개 전부 — 그중 하나가 REMOVE다

다섯 개 암기 — 저 · 병 · 삭 · 새 · 분

저장 PERSIST병합 MERGE삭제 REMOVE새로고침 REFRESH분리 DETACH

가운데(세 번째)가 삭제다. ALL은 편의 옵션이 아니라 이 다섯을 한꺼번에 켜는 선언이고, 그 한가운데에 데이터를 지우는 것이 들어 있다.

사고는 REMOVE를 켠 사람이 아니라 ALL을 쓴 사람에게서 난다

"저장할 때 편하니까" 하는 이유로 cascade = CascadeType.ALL을 쓴 사람에게서 난다. 저장 편의를 원해서 켠 옵션에 삭제 전파가 딸려 들어온 것이고, 그 사실은 코드 어디에도 안 적혀 있다. 몇 달 뒤 누군가 postRepository.delete(post)를 호출하는 순간에야 드러난다.

옵션을 켠 시점과 사고가 난 시점이 몇 달 떨어져 있다 — 리뷰에서 ALL 한 단어를 넘기면 몇 달 뒤 다른 사람이 대가를 치른다
bad 한 줄에 삭제 전파가 숨어 있다
@OneToMany(mappedBy = "post", cascade = CascadeType.ALL)
private List<Attachment> attachments = new ArrayList<>();

// 저장 편의만 원했는데
// REMOVE·REFRESH·DETACH까지 딸려 왔다
good 필요한 전파만 명시한다
@OneToMany(mappedBy = "post",
    cascade = {CascadeType.PERSIST, CascadeType.MERGE})
private List<Attachment> attachments = new ArrayList<>();

// 삭제 전파가 필요하면 그때 손으로 적는다
// → 적는 순간 그것은 "결정"이 되고 리뷰 대상이 된다
면접에서 먼저 꺼내면 좋은 한 문장 "CascadeType.ALL은 편의가 아니라 다섯 개 옵션을 한꺼번에 켜는 선언이고, 그중 하나가 삭제 전파입니다. 그래서 저는 필요한 타입만 골라서 켭니다."

1-4. cascade는 연관관계의 주인과 무관하다

헷갈리기 쉬운 지점 — "읽기 전용인데 왜 삭제가 되지?" mappedBy가 붙은 쪽은 FK 관리에 대해서만 읽기 전용이다. cascade와 orphanRemoval은 FK 관리가 아니라 생명주기 전파라서, mappedBy 쪽(Post.attachments)에 붙이는 것이 정상이고 정상적으로 동작한다. 두 개념은 다른 축이다.

1-5. 고아(orphan)란 무엇인가 — 판정 기준이 FK가 아니다

부모가 더 이상 자신을 참조하지 않게 된 자식 엔티티를 고아라고 부른다. 여기서 "참조하지 않는다"의 판정 기준이 결정적이다.

판정 기준은 DB의 FK 값이 아니라 "부모의 컬렉션에서 빠졌는가"
post_id 컬럼에 값이 남아 있어도, 메모리상의 post.attachments 리스트에서 빠지면 고아다
code 삭제 API를 호출한 적이 없다
@OneToMany(mappedBy = "post", orphanRemoval = true)
private List<Attachment> attachments = new ArrayList<>();

// ---- 서비스 ----
@Transactional
public void deleteAttachment(Long postId, Long attachmentId) {
    Post post = postRepository.findById(postId).orElseThrow();
    Attachment target = post.getAttachments().stream()
            .filter(a -> a.getId().equals(attachmentId))
            .findFirst().orElseThrow();

    post.getAttachments().remove(target);   // 이 한 줄이 DELETE다
}
sql flush 시점(대개 커밋 직전)에 나가는 SQL
-- attachmentRepository.delete(...) 를 부른 적이 없다.
-- 컬렉션에서 원소를 뺀 것이 곧 삭제 명령이 되었다.

delete from attachment where id = 42;
이것이 orphanRemoval의 전부이자, 사고의 원천 "목록 정리"의 의도로 쓴 컬렉션 조작이 삭제 명령이 되는 통로가 열려 있다는 뜻이다.

2. 갈림길 — 방아쇠의 개수

두 옵션을 가르는 축은 하나다. 무엇이 삭제를 일으키는가, 그런 것이 몇 개인가. 이 그림 한 장이 이 문서의 답이다.

같은 사건, 다른 결과 — 이 표가 답변의 뼈대다
무슨 일이 일어났을 때CascadeType.REMOVEorphanRemoval = true
부모에 remove() 호출 (postRepository.delete(post))자식 DELETE자식 DELETE
컬렉션에서 자식 하나 제거 (getAttachments().remove(a))아무 일도 안 일어남그 자식 DELETE
컬렉션 clear()아무 일도 안 일어남전건 DELETE
컬렉션 필드 재할당 (this.attachments = newList)아무 일도 안 일어남예외 또는 전건 DELETE
방아쇠 개수1개 (부모 삭제)2개 (부모 삭제 + 연결 해제)
개념부모의 삭제 작업을 전파자식의 생명주기를 부모가 소유

한 문장 인출 — 이 문장만 외워도 이 질문은 통과한다

CascadeType.REMOVE의 방아쇠는 "부모의 remove()" 하나뿐이고,
orphanRemoval은 거기에 "부모와의 연결 해제"가 하나 더 붙는다

2-1. 의미의 차이 — "작업 편의" vs "도메인 선언"

CascadeType.REMOVE = 건물 철거 허가

건물을 철거할 때만 안의 붙박이 가구도 함께 철거된다. 방아쇠는 '철거 명령' 하나. 가구를 건물 도면에서 지운다고 가구가 없어지지는 않는다.

= "부모를 지울 때 딸린 것도 같이 치워줘"라는 작업 편의

orphanRemoval = 자산 대장

물건은 대장(부모 컬렉션)에 줄이 올라 있어야 존재가 인정된다. 대장에서 줄을 지우면 그 물건은 곧바로 폐기장으로 간다. 그래서 대장을 새로 인쇄해서 갈아끼우면 기존 자산이 전원 폐기된다(4절).

= "이 자식은 부모의 소유물"이라는 도메인 선언 — 더 강한 주장이고, 그래서 더 위험하다

2-2. 포함 관계 — orphanRemoval만 켜도 부모 삭제가 전파된다

자주 나오는 꼬리질문이다. orphanRemoval = true는 부모가 삭제될 때의 자식 삭제도 포함한다. 부모가 사라지면 그 자식들은 전원 고아가 되는 셈이니 개념적으로도 자연스럽다. Hibernate 내부를 열어보면 이 포함 관계가 그대로 코드에 있다 — orphanRemoval = true는 내부적으로 delete-orphan이라는 cascade 스타일로 변환되는데, 그 스타일의 판정 함수가 REMOVE 작업을 전파 대상에 포함하고 있다.

// org.hibernate.engine.spi.CascadeStyles (Hibernate 6.6)
public static final CascadeStyle DELETE_ORPHAN = new BaseCascadeStyle() {
    @Override
    public boolean doCascade(CascadingAction action) {
        return action == CascadingActions.REMOVE          // 부모 삭제도 전파한다
            || action == CascadingActions.SAVE_UPDATE
            || action == CascadingActions.PERSIST_ON_FLUSH
            || action == CascadingActions.CHECK_ON_FLUSH;
    }
    @Override
    public boolean hasOrphanDelete() { return true; }     // 여기에 두 번째 방아쇠가 있다
};
삭제 동작만 보면 이 둘은 사실상 같다
@OneToMany(mappedBy = "post",
    cascade = CascadeType.REMOVE, orphanRemoval = true)  // REMOVE는 잉여

@OneToMany(mappedBy = "post", orphanRemoval = true)      // 이걸로 충분
그럼 왜 실무에서 ALL + orphanRemoval을 같이 쓰나 가산점 ALL 안의 PERSIST/MERGE가 필요해서지 REMOVE 때문이 아니다. 이 구분을 말할 수 있으면 관성으로 붙인 것이 아님이 드러난다.

hibernate.jdbc.batch_size는 만들어진 SQL을 DB로 보낼 때 여러 개를 묶어 한 번에 전송하는 설정이다. DELETE 1,000개는 그대로 1,000개지만, 왕복이 1000 ÷ 50 = 20회로 줄어든다. 왕복 1회에 1ms가 걸린다면 1초가 20ms가 되는 셈이다.

대가와 한계 문장 수 자체가 줄지 않으므로 DB 쪽 작업량은 그대로다. 락 점유 시간도 크게 안 줄어든다. 즉 이 처방은 네트워크가 병목일 때만 효과가 있다. 그리고 @Version이 붙은 엔티티도 배치에 포함할지는 hibernate.jdbc.batch_versioned_data가 정하는데, Hibernate 6에서는 기본값이 true라 별도 설정 없이 함께 묶인다.

이름이 비슷해서 자주 혼동되는 둘 — 겨냥하는 곳이 다르다

hibernate.jdbc.batch_size — 쓰기

이미 만들어진 DELETE/INSERT를 묶어 보내 네트워크 왕복 횟수를 줄인다. 문장 수는 그대로.

@BatchSize (Hibernate 애노테이션) — 읽기

게시글 100개를 지울 때 각 컬렉션을 초기화하느라 SELECT가 100번 나가는 문제(N+1)를 where post_id in (?, ?, ...) 한 번으로 묶는다.

@BatchSize(size = 100)      // 컬렉션 초기화 SELECT를 IN 절로 묶는다
@OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Attachment> attachments = new ArrayList<>();

대량 삭제에서는 둘 다 필요하다 — 읽기 횟수와 쓰기 왕복은 별개의 병목이다.

6-2. 처방 ② — 벌크 DELETE로 한 문장으로 내린다

good 1,002문장 → 2문장

delete from attachment where post_id = 1;   -- 한 문장

@Transactional
public void deletePost(Long postId) {
    Post post = postRepository.findById(postId).orElseThrow();
    post.getAttachments().size();              // ① 자식 3건이 1차 캐시에

    post.getAttachments().size();              // ③ 여전히 3 — 1차 캐시가 답한다
    postRepository.delete(post);               // ④ 캐시에 남은 자식에 또 DELETE 시도
}
cascade의 성능 문제를 벌크로 풀면, 벌크의 정합성 문제가 따라온다 — 둘은 세트로 온다
"성능 때문에 벌크로 내렸습니다"까지만 답하면 절반이고, "그러면 1차 캐시와 DB가 어긋나므로 컨텍스트를 비우거나 벌크를 트랜잭션 끝으로 밉니다"까지 붙여야 완성이다

6-3. 처방 ③ — DB에 위임한다 (ON DELETE CASCADE)

ddl FK 제약 자체에 삭제 규칙을 심는다
-- PostgreSQL
alter table attachment
  add constraint fk_attachment_post
  foreign key (post_id) references post(id)
  on delete cascade;
jpa Hibernate에게 이 DDL을 생성하게 하려면
@OneToMany(mappedBy = "post")
@OnDelete(action = OnDeleteAction.CASCADE)     // org.hibernate.annotations
private List<Attachment> attachments = new ArrayList<>();

얻는 것

  • delete from post where id = 1 한 문장으로 끝난다.
  • 자식을 SELECT할 필요도, DELETE를 1,000개 만들 필요도 없다.
  • 대량 삭제에서는 압도적으로 빠르다.

포기하는 것 — 이쪽이 더 중요하다

  • JPA가 모르는 삭제가 된다. 1차 캐시에 자식이 남아, 같은 트랜잭션에서 사라진 행이 조회된다.
  • Auditing·엔티티 리스너가 전부 건너뛰어진다. @PreRemove, soft delete를 위한 @SQLDelete, 이력 적재가 조용히 안 돈다. 감사 요구가 있으면 곧 컴플라이언스 구멍이다.
  • 애플리케이션 코드를 읽어도 삭제 파급이 안 보인다. 파급이 DDL에 있어서 코드 리뷰로는 절대 발견되지 않는다.
  • 후처리가 안 돈다. 스토리지 파일 삭제, 캐시 무효화, 이벤트 발행 — 아무것도 실행되지 않는다.
@OnDelete와 cascade = REMOVE를 함께 쓰면 어떻게 되나 (Hibernate 6.6 문서 기준)
설정자식을 SELECT로 읽나영속성 컨텍스트에서 삭제 표시2차 캐시에서 축출실제 삭제 주체
@OnDelete(CASCADE) 단독안 읽는다안 한다안 한다DB
@OnDelete(CASCADE) + cascade = REMOVE읽는다한다한다DB (JPA는 표시만)

즉 함께 쓰면 "빠르지만 메모리는 어긋나는" 단점을 어느 정도 상쇄할 수 있다 — 자식 개별 DELETE는 안 나가고 DB가 한 번에 지우되, 영속성 컨텍스트와 2차 캐시는 그 사실을 안다. 대신 자식을 읽어오는 SELECT는 다시 나가므로 "완전 공짜"는 아니다. 어느 조합을 택하든 실제 프로젝트에서는 SQL 로그로 확인하고 넘어가는 것을 권한다.

세 갈래를 한 표로 — "작은 Aggregate는 JPA에 맡기고, 대량 삭제는 벌크로 내리되 그때는 정합성을 손으로 챙긴다"가 실무의 기본형
방식나가는 SQL리스너·후처리정합성적합한 규모
cascade / orphanRemovalSELECT + 자식 수만큼 DELETE정상 동작안전자식 수십 건까지
벌크 DELETE (@Modifying)한 문장동작 안 함1차 캐시 불일치 관리 필요수백~수만 건
DB ON DELETE CASCADE부모 한 문장동작 안 함코드에 파급이 안 보임대량, 또는 성능이 최우선

7. JPA cascade vs DB ON DELETE CASCADE

이름이 닮아서 같은 것으로 착각하기 쉬운데, 세 가지 축에서 전부 다르다. — 누가 지우는가, 몇 개의 SQL이 나가는가, JPA가 그 삭제를 아는가.

@Transactional
public void demo(Long postId) {
    Post post = postRepository.findById(postId).orElseThrow();
    post.getAttachments().size();       // 자식 3건이 1차 캐시에 올라온다

    postRepository.delete(post);        // DB의 ON DELETE CASCADE 로 자식까지 삭제됨
    em.flush();

    // DB에는 자식이 없다. 그런데 1차 캐시에는 남아 있다.
    System.out.println(post.getAttachments().size());   // 3 (DB와 불일치)
}
세 축 + 실무에서 갈리는 두 항목
JPA CascadeType.REMOVEDB ON DELETE CASCADE
누가 지우나애플리케이션(Hibernate)DB 엔진
SQL 개수 (자식 1,000건)SELECT 1 + DELETE 1,001DELETE 1
1차 캐시가 아나안다 (삭제 표시됨)모른다 (사라진 행이 조회된다)
적용 범위JPA를 통한 삭제만모든 삭제(콘솔 SQL, 배치, 다른 애플리케이션)
리스너·Auditing동작함동작 안 함
어디에 적혀 있나엔티티 코드DDL(스키마)
DB 쪽의 유일한 우위는 "적용 범위"다 시니어 변별 DBA가 콘솔에서 친 delete from post, 다른 팀 배치, 다른 언어로 만든 애플리케이션 — 어느 경로로 지워도 DB 규칙은 지켜진다. JPA의 cascade는 JPA를 지나간 삭제에만 적용되므로, 정합성 보장의 강도만 놓고 보면 DB 쪽이 더 강하다.

둘을 동시에 켜는 것도 가능하지만(6-3의 조합 표), "코드를 봐도, DDL을 봐도 어느 쪽이 실제로 지우는지 모르는 상태"가 되기 쉬우므로 하나로 정하고 팀에 명시하는 편이 낫다.

8. 켜는 기준과 안전망 네 층

8-1. 기준 — 부모 없이 존재 의미가 없는가

자식이 부모 없이는 존재 의미가 없는 종속 관계일 때만 켠다

이는 DDD의 Aggregate 경계와 같은 판단이다. Aggregate는 "함께 변경되고 함께 정합성이 지켜져야 하는 객체 묶음"이고, 그 묶음의 대표를 Aggregate 루트라고 부른다. 루트(부모)가 자식의 생명주기를 소유하고, 자식은 루트를 통해서만 접근한다.

켜도 되는 예 — 종속

  • Order → OrderItem — 주문 항목은 주문 없이 존재할 이유가 없다.
  • Post → Attachment — 게시글 전용 첨부라면(다른 글이 공유하지 않는다면) 종속이다.
  • Survey → Question → Choice — 설문 밖의 선택지는 무의미하다.

켜면 안 되는 예 — 공유·독립

  • Team → Member — 팀을 없앤다고 사람을 지우지 않는다.
  • Post → Category, Tag — 공유되고 독립적으로 관리된다.
  • Order → Product — 상품은 주문보다 오래 산다.
  • 자식이 독립적으로 조회·수정되는 화면이 있는 경우 — 자체 리포지토리와 API가 있다는 것은 독립 생명주기를 갖는다는 증거다.

빠른 자가진단 — 셋 중 하나라도 "예"면 끄는 쪽이다

① 자식만 따로 조회하는 API가 있나?
있다면 종속이 아니다.
② 자식을 다른 부모에게 옮기는 요구가 생길 수 있나?
있다면 orphanRemoval은 금물이다(4-4).
③ 자식을 참조하는 제3의 엔티티가 있나?
있다면 공유 자원이다(5절).

8-2. 켜서 얻는 것과 포기하는 것

얻는 것

  • 도메인이 자식의 생명주기를 소유한다. 서비스에서 attachmentRepository를 직접 다룰 일이 없어지고, 자식 조작이 부모의 도메인 메서드 안으로 모인다.
  • Aggregate 경계가 코드로 드러난다. cascade = ALL, orphanRemoval = true는 문서로 적을 필요 없는 "이 자식은 이 부모의 것" 선언이다.
  • 서비스 코드가 짧아진다. 자식 저장을 빠뜨려 데이터가 반만 들어가는 실수가 구조적으로 사라진다.

포기하는 것

  • 삭제 파급이 코드에 안 보인다. postRepository.delete(post) 한 줄만 봐서는 몇 개 테이블이 영향받는지 알 수 없다.
  • 성능을 포기한다. SELECT + 자식 수만큼 DELETE(6절).
  • 실수 한 줄의 대가가 데이터 유실이다. UPDATE 사고와 달리 복구 수단이 백업뿐이다.
  • 코드 리뷰의 난이도가 올라간다. 컬렉션을 만지는 모든 코드가 잠재적 DELETE라서, 리뷰어가 매핑을 기억하고 있어야 한다.
면접용 한 호흡 서술 — 얻는 것 → 대가 → 기준 → 장치 순서 "orphanRemoval을 켜면 자식의 생명주기를 도메인이 소유하게 되어 서비스에서 자식 리포지토리를 다룰 일이 없어지고 Aggregate 경계가 코드에 드러납니다. 대신 삭제 파급이 호출부에서 안 보이고, 자식 수만큼 DELETE가 나가며, 컬렉션을 잘못 만진 한 줄이 곧 데이터 유실이 됩니다. 그 대가를 감당할 수 있는 경우는 자식이 부모 없이 존재 의미가 없을 때뿐이라, 저는 종속 관계에만 켜고 컬렉션은 캡슐화해서 잘못 만질 수 없게 막습니다."

8-3. 안전망 — "조심한다"가 아니라 "못 하게 만든다"

"조심하자"는 처방은 사람이 바뀌면 사라진다. 네 층을 겹치면 같은 실수가 점점 더 이른 시점에 잡힌다.

안전망 ① — 컬렉션을 밖으로 내보내지 않는다

before 컬렉션 원본이 밖으로 나간다
public class Post {
    @OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<Attachment> attachments = new ArrayList<>();

    public List<Attachment> getAttachments() { return attachments; }          // 위험
    public void setAttachments(List<Attachment> a) { this.attachments = a; }  // 더 위험
}

// 호출자 누구나 post.getAttachments().clear() 를 칠 수 있다.
// setter는 4-1 갈래 A(재할당 예외)로 가는 문이다.
after 읽기는 읽기 전용 뷰로, 쓰기는 의도가 드러나는 메서드로만
public class Post {
    // final: 필드 재할당을 컴파일 단계에서 막는다
    @OneToMany(mappedBy = "post", cascade = CascadeType.ALL, orphanRemoval = true)
    private final List<Attachment> attachments = new ArrayList<>();

    public List<Attachment> getAttachments() {
        // 밖에서 clear()/add()를 부르면 즉시 UnsupportedOperationException
        return Collections.unmodifiableList(attachments);
    }

    public void addAttachment(Attachment a) {
        attachments.add(a);
        a.setPost(this);          // 연관관계 편의 메서드 (양쪽 일관성)
    }

    public void removeAttachment(Attachment a) {
        attachments.remove(a);    // 이 메서드를 통해야만 DELETE가 일어난다
        a.setPost(null);
    }
}
조용한 유실 → 시끄러운 실패
clear()·removeIf()·addAll()이 런타임에 즉시 예외로 막힌다.
재할당은 컴파일 단계에서 불가
필드를 final로 두면 4-1 갈래 A 예외를 만날 일 자체가 없어진다.
DELETE 진입점이 하나로 좁혀진다
리뷰에서 removeAttachment 호출부만 보면 되고, 파일 실체 삭제 같은 후처리도 여기 한 곳에 붙일 수 있다.

안전망 ② — 삭제 쿼리 수를 테스트로 단정한다

주의 — @DataJpaTest는 문제를 숨길 수 있다 기본적으로 테스트 후 롤백하므로 커밋 시점에만 드러나는 문제를 숨긴다. em.flush()를 명시하거나 @Commit/TestTransaction으로 실제 커밋을 일으켜야 한다. Hibernate Statistics의 getEntityDeleteCount()로도 같은 단정을 만들 수 있다. 핵심은 "몇 건이 지워지는가"를 숫자로 못 박아두는 것이다.

안전망 ③ — CascadeType.ALL을 구조 룰로 막는다

@Test
void OneToMany에_CascadeType_ALL을_쓰지_않는다() {
    ArchRule rule = fields()
        .that().areAnnotatedWith(OneToMany.class)
        .should(new ArchCondition<JavaField>("CascadeType.ALL을 쓰지 않는다") {
            @Override
            public void check(JavaField field, ConditionEvents events) {
                OneToMany a = field.reflect().getAnnotation(OneToMany.class);
                if (Arrays.asList(a.cascade()).contains(CascadeType.ALL)) {
                    events.add(SimpleConditionEvent.violated(field,
                        field.getFullName() + " : CascadeType.ALL은 REMOVE를 포함합니다. "
                        + "필요한 타입만 명시하세요 (PERSIST/MERGE). "
                        + "삭제 전파가 의도라면 orphanRemoval=true를 명시하고 리뷰를 받으세요."));
                }
            }
        });

    rule.check(new ClassFileImporter().importPackages("com.example.domain"));
}

이 룰의 목적은 "금지"가 아니라 "명시 강제"다

삭제 전파가 진짜로 필요하면 orphanRemoval = true를 손으로 적게 만든다. 적는 순간 그것은 결정이 되고, 리뷰 대상이 된다. 같은 방식으로 @OneToMany 필드에 setter가 있는지, 컬렉션 필드가 final인지도 룰로 만들 수 있다.

안전망 ④ — 실제 SQL을 눈으로 본다

p6spy나 datasource-proxy로 바인딩 값까지 찍힌 실제 SQL을 개발 환경에서 상시 노출한다. "제목만 바꿨는데 로그에 delete from attachment가 세 줄 찍히는" 장면을 한 번 보면, 그 다음부터는 매핑을 열어보게 된다. 관측이 습관을 만든다.

8-4. soft delete와의 상호작용

삭제를 물리 삭제가 아니라 deleted_at 컬럼으로 다루는 것을 soft delete(논리 삭제)라고 한다. cascade와의 조합에 함정이 있다.

@Entity
@SQLDelete(sql = "update attachment set deleted_at = now() where id = ?")
@SQLRestriction("deleted_at is null")     // Hibernate 6.3부터 @Where 대신 이것을 쓴다
public class Attachment { ... }
JPA를 거치는 삭제
cascade·orphanRemoval은 @SQLDelete를 타므로 DELETE가 UPDATE로 치환된다. 여기까지는 의도대로다.
벌크 DELETE · DB CASCADE
@SQLDelete를 우회한다. 같은 도메인에서 어떤 경로로 지웠느냐에 따라 물리 삭제와 논리 삭제가 섞인다 — 발견하기 매우 어려운 상태다.
유니크 제약을 계속 점유
"지운 파일과 같은 이름으로 다시 못 올린다" 같은 증상이 여기서 나온다.
결론 — 삭제 경로를 하나로 통일한다 가산점 JPA로 지우기로 했으면 ON DELETE CASCADE를 걸지 않고, 벌크 삭제를 쓰기로 했으면 그 쿼리도 deleted_at을 갱신하도록 손으로 맞춰야 한다.

버전 두 가지도 알아두면 좋다. ① @Where는 Hibernate 6.3부터 폐기 예정(deprecated)이고 @SQLRestriction이 대체한다 — 기능은 같고 이름과 속성 형태만 바뀌었다. ② Hibernate 6.4부터 @SoftDelete 전용 애노테이션이 생겼다. 다만 이것은 deleted_at 같은 시각 컬럼이 아니라 참·거짓 표시 컬럼을 쓰는 방식이라 "언제 지웠는지"를 남겨야 하는 요구에는 그대로 대응하지 못하고, 아직 실험적(@Incubating) 단계다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

두 옵션 차이 한 문장?
방아쇠의 개수 — REMOVE는 부모 삭제 1개, orphanRemoval은 거기에 연결 해제까지 2개.
CascadeType 다섯 개?
저 · 병 · 삭 · 새 · 분(PERSIST·MERGE·REMOVE·REFRESH·DETACH). ALL은 다섯을 한꺼번에 켜는 선언이고 가운데가 삭제다.
고아 판정 기준은?
DB의 FK 값이 아니라 "부모 컬렉션에서 빠졌는가". post_id가 남아 있어도 리스트에서 빠지면 고아다.
orphanRemoval 3금(禁)?
클리어(clear()+addAll()) · 재할당(setter) · 이사(다른 부모로 옮기기). 셋 다 삭제 의도가 없는 코드다.
⑤ "조용한 방치"란?
REMOVE만 켠 채 컬렉션에서 빼면 SQL이 하나도 안 나간다. 화면에서는 사라졌다가 새로고침하면 되살아난다.
비용 숫자?
자식 1,000건 → 1,002문장(SELECT 1 + DELETE 1,000 + 부모 1). 삭제 단위는 언제나 엔티티 1건이다.
켜기 전 자가진단 3문?
① 자식만 조회하는 API가 있나 ② 다른 부모로 옮길 일이 있나 ③ 자식을 참조하는 제3자가 있나 — 하나라도 예면 끈다.
JPA vs DB cascade, 결정적 축?
1차 캐시가 아는가(JPA는 안다 / DB는 모른다)와 적용 범위(JPA는 JPA 경로만 / DB는 모든 경로).
UPDATE 사고와 무엇이 다른가?
UPDATE는 원본을 알면 되돌릴 여지가 있지만, DELETE는 무엇이 있었는지조차 안 남는다 — 복구는 백업뿐.
안전망 네 층?
막(캡슐화) · 센다(쿼리 수 테스트) · 룰(ArchUnit) · 본다(p6spy). "조심한다"가 아니라 "못 하게 만든다".

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

cascade = CascadeType.ALL을 그냥 쓰면 안 되나요? 편한데요. 필수힌트: "위험하다"가 아니라 "무엇을 켜는 선언인지"부터 정정한다

ALL은 편의 옵션이 아니라 다섯 개 전파를 한꺼번에 켜는 선언이고, 그중 REMOVE는 데이터를 지웁니다. 저장 편의가 목적이었다면 {PERSIST, MERGE}만 켜면 됩니다.

실무 사고의 대부분이 "저장이 편하려고 켰는데 삭제까지 딸려온" 경로로 발생하고, 켠 시점과 사고 시점이 몇 달 떨어져 있어서 원인 추적도 어렵습니다 — 코드 리뷰에서 ALL 한 단어를 넘기면 몇 달 뒤 다른 사람이 대가를 치릅니다.

그래서 저는 필요한 타입만 명시하고, @OneToMany에 ALL이 붙는 것을 ArchUnit 룰로 막습니다. 목적은 금지가 아니라 명시 강제입니다 — 삭제 전파가 정말 필요하면 orphanRemoval = true를 손으로 적게 하고, 적는 순간 그것은 결정이 되어 리뷰 대상이 됩니다.

orphanRemoval = true를 켜면 CascadeType.REMOVE는 따로 안 써도 되나요? 필수힌트: 포함 관계다. 그리고 "그럼 왜 실무에서 둘을 같이 쓰나"까지 답해야 완성

네. orphanRemoval은 부모 삭제 시의 자식 삭제도 포함합니다 — 부모가 사라지면 자식은 전부 고아가 되니 개념적으로도 자연스럽습니다.

Hibernate 내부에서도 orphanRemoval은 delete-orphan cascade 스타일로 변환되는데, 그 스타일의 doCascade()가 REMOVE 전파를 이미 포함하고 있고 hasOrphanDelete()가 true를 돌려줍니다. 그래서 cascade = REMOVE, orphanRemoval = true에서 REMOVE는 잉여입니다.

실무에서 cascade = ALL, orphanRemoval = true를 함께 쓰는 이유는 ALL 안의 PERSIST/MERGE가 필요해서지 REMOVE 때문이 아닙니다. 이 구분을 말할 수 있으면 관성으로 붙인 것이 아님이 드러납니다.

첨부를 다른 게시글로 옮기려고 컬렉션에서 뺐는데 삭제됐습니다. 왜 그런가요? 함정힌트: "버그를 고친다"가 아니라 "이 옵션의 의미가 그렇다"로 답한다

orphanRemoval은 "부모 컬렉션에서 빠졌다"만 보고 판단합니다. 같은 트랜잭션에서 다른 부모에 다시 붙였는지는 고려하지 않습니다. 그래서 이동이 삭제가 되거나, 삭제 후 재삽입으로 id가 바뀝니다.

이건 버그라기보다 orphanRemoval의 의미가 그렇다는 신호입니다 — "이 자식은 이 부모의 소유"라고 선언해놓고 다른 부모에게 넘기는 것은 모순이니까요.

자식이 부모 사이를 이동하는 도메인이라면 orphanRemoval을 켜면 안 됩니다 — 그리고 이건 켜기 전 자가진단 ②번 항목입니다
게시글에 첨부가 10만 건이면 어떻게 지우나요? 필수힌트: 선택지 두 개 + 각각의 대가. 마지막에 질문의 전제를 되묻는다

orphanRemoval에 맡기면 SELECT 한 번 + DELETE 10만 문장이 만들어지고, 그 전부가 한 트랜잭션 안에서 락을 잡습니다. 현실적이지 않습니다. 선택지는 둘입니다.

① 벌크 DELETE

@Modifying으로 delete from Attachment a where a.post.id = :id 한 문장. 대신 영속성 컨텍스트를 우회하므로 1차 캐시와 DB가 어긋납니다. 처방은 벌크를 트랜잭션 끝이나 별도 트랜잭션으로 밀거나, 이후 컨텍스트를 비우는 것입니다.

② DB FK의 ON DELETE CASCADE

부모 DELETE 한 문장으로 끝나 가장 빠릅니다. 대신 JPA 리스너·Auditing·soft delete·후처리가 전부 건너뛰어지고, 삭제 파급이 애플리케이션 코드에 안 보입니다.

그리고 규모가 이 정도면 애초에 동기 삭제가 맞는지를 되묻습니다. 부모만 지우고 자식은 배치로 나눠 지우는 비동기 정리가 운영에서 더 안전합니다 — 삭제 버튼 하나가 사용자를 10초 기다리게 하고 그동안 다른 트랜잭션을 밀어내는 것보다 낫습니다.

DB에 ON DELETE CASCADE를 걸면 JPA 설정은 필요 없는 것 아닌가요? 시니어 변별힌트: 반은 인정하고 시작한다. DB가 이기는 축이 하나 있다

동작 주체가 다릅니다. DB 규칙은 모든 경로(콘솔 SQL, 배치, 다른 애플리케이션)에 적용되므로 정합성 보장은 더 강력합니다 — 이 축은 인정하고 시작하는 게 맞습니다. 대신 포기하는 것이 셋입니다.

① 엔티티 리스너·Auditing·@SQLDelete가 안 돕니다 — 감사 이력이 조용히 비고, soft delete가 우회됩니다. ② 1차 캐시에는 자식이 그대로 남아 같은 트랜잭션에서 사라진 행이 조회됩니다. ③ 삭제 파급이 DDL에만 있어서 코드 리뷰로는 절대 발견되지 않습니다.

그래서 저는 "작은 Aggregate는 JPA에, 대량 삭제는 DB나 벌크에"로 나누고, 어느 쪽이든 한 도메인 안에서는 경로를 하나로 통일합니다. 둘을 섞으면 "어떤 경로로 지웠느냐에 따라 이력이 남기도 하고 안 남기도 하는" 상태가 되는데, 이건 발견이 거의 불가능한 종류의 문제입니다.

그럼 애초에 이런 사고가 안 나게 하려면 뭘 하시겠어요? 시니어 변별힌트: "조심하겠습니다"는 답이 아니다. 층으로 나눠 말한다

조심하는 게 아니라 못 하게 만듭니다. 세 층입니다.

① 캡슐화 — 컬렉션 필드를 final로 두고(재할당 불가), getter는 Collections.unmodifiableList로 반환하고(clear() 시 예외), addAttachment/removeAttachment만 공개합니다. DELETE가 일어나는 진입점이 한 곳으로 좁혀집니다.

② 테스트로 회귀 고정 — SQLStatementCountValidator.assertDeleteCount(0) 같은 단정을 수정 시나리오에 걸어둡니다. 누가 매핑을 바꾸면 테스트가 먼저 깨집니다.

③ 구조 룰 — @OneToMany에 CascadeType.ALL 금지 ArchUnit 룰. 금지가 목적이 아니라 삭제 전파를 쓰려면 orphanRemoval = true를 손으로 적게 만드는 것이 목적입니다.

그리고 개발 환경에서는 p6spy로 실제 SQL을 상시 노출합니다. "제목만 바꿨는데 delete가 세 줄 찍히는" 걸 한 번 보면 그 다음부터는 매핑을 열어보게 됩니다. 관측이 습관을 만듭니다.

@ElementCollection은 어떤가요? 가산점힌트: 켜지 않아도 고아 제거처럼 동작한다. 그리고 그보다 나쁜 특성이 하나 더 있다

@ElementCollection으로 매핑한 값 타입은 애초에 독립된 생명주기가 없어서, orphanRemoval을 켜지 않아도 항상 고아 제거처럼 동작합니다. 부모에서 빠지면 행이 사라집니다.

게다가 더 나쁜 특성이 하나 있습니다. 순서 컬럼(@OrderColumn)이 없는 List(Hibernate 용어로 백, bag)는 요소 하나만 바꿔도 그 부모의 행을 전부 지우고 다시 넣습니다. Hibernate 코드에도 그대로 있는 판정입니다 — PersistentBag.needsRecreate()가 "일대다 연관이 아니면 참"을 돌려주고, 값 타입 컬렉션이 여기에 해당합니다. 요소가 100개인 컬렉션에 하나를 추가하면 delete where owner_id = ? 한 번과 insert 101번이 나가는 셈입니다.

그래서 실무에서는 값 타입 컬렉션 대신 엔티티로 승격시키고 @OneToMany + orphanRemoval로 다루는 것이 권장 구성입니다 — 그때 비로소 삭제 파급을 우리가 통제할 수 있게 됩니다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

cascade = REMOVE만 켠 상태에서 컬렉션에서 뺐는데 아무 일도 안 일어납니다. 버그인가요? 함정힌트: 이유가 두 겹이다. 그리고 매핑 형태에 따라 결과가 또 갈린다

버그가 아니라 설계대로입니다. 이유가 두 겹입니다. ① CascadeType.REMOVE의 방아쇠는 부모의 remove() 하나뿐인데 부모를 지운 적이 없고, ② Post.attachments는 mappedBy가 붙은 읽기 전용 쪽이라 컬렉션 변경 자체가 flush 대상에서 제외됩니다.

그 결과 attachment 행은 post_id = 1을 그대로 들고 DB에 남습니다. 개발자는 "첨부를 뗐다"고 믿지만 다음 요청에서 다시 읽으면 그 첨부는 되살아나 있습니다 — 화면에서는 사라졌다가 새로고침하면 돌아오는 버그로 보고됩니다.

한 겹 더. 이 연관이 @OneToMany + @JoinColumn(부모가 FK를 관리하는 단방향)이었다면 이번엔 update attachment set post_id = null이 나갑니다. NOT NULL이면 제약 위반으로 터지고, NULL 허용이면 어느 게시글에도 안 붙은 유령 행이 남습니다. orphanRemoval은 바로 이 "연결이 끊긴 자식을 어떻게 할 것인가"에 대한 답을 강제하려고 만들어진 장치입니다.

@ManyToOne 쪽(자식 → 부모)에 cascade = CascadeType.REMOVE를 걸면 어떻게 되나요? 함정힌트: cascade에는 방향이 있다. 그 방향이 뒤집히면 무슨 일이 일어나나

자식을 지우면 부모가 지워집니다. cascade는 "이 연관을 타고 작업을 전파한다"는 뜻이고, @ManyToOne에 걸면 그 방향이 자식 → 부모가 되기 때문입니다. 첨부파일 한 건을 삭제했더니 게시글이 통째로 사라지는 동작이 됩니다.

여기에 게시글 쪽에도 자식으로 향하는 cascade = REMOVE가 걸려 있다면 연쇄가 한 바퀴 더 돕니다 — 첨부 1건 삭제 → 게시글 삭제 → 그 게시글에 딸린 나머지 첨부까지 전부 삭제. "파일 하나 지웠는데 글이 없어졌다"는 사고의 전형적인 형태입니다.

cascade가 향하는 방향은 소유여야 한다 — 부분이 전체를 지우는 방향으로는 걸지 않는다

@ManyToOne에 정당하게 쓸 수 있는 타입은 대개 PERSIST 정도입니다(자식을 저장할 때 아직 저장 안 된 부모를 함께 저장). 그마저도 부모의 생명주기를 자식이 만들어도 되는 관계인지를 먼저 확인해야 합니다.

orphanRemoval = true인데 컬렉션에서 뺐는데도 DELETE가 안 나갑니다. 어디부터 보시겠어요? 시니어 변별힌트: "안 나간다"에는 원인이 네 가지 있고, 그중 하나는 이 문서 밖(엔티티의 equals)에 있다

순서대로 넷을 확인합니다.

① flush가 일어났는가. orphanRemoval의 DELETE는 flush 시점(대개 커밋 직전)에 나갑니다. 테스트가 @DataJpaTest로 롤백되고 있으면 SQL을 볼 수 없으니, em.flush()를 명시하거나 실제 커밋을 일으켜야 합니다.

② 정말로 컬렉션에서 빠졌는가. list.remove(target)은 equals()로 대상을 찾습니다. 엔티티의 equals/hashCode가 잘못 구현돼 있으면(또는 프록시가 섞여 있으면) remove()가 아무것도 못 지우고 조용히 false를 돌려줍니다. 컬렉션 크기를 전후로 찍어보면 바로 드러납니다.

③ orphanRemoval이 붙은 필드가 지금 만지는 그 컬렉션이 맞는가. 양방향 연관이나 중간 엔티티가 있으면 실제로 소유권을 가진 컬렉션은 다른 필드인 경우가 있습니다.

④ 그 자식이 다른 곳에서 여전히 참조되고 있지 않은가. 다른 부모의 컬렉션에 들어가 있으면 고아가 아닙니다(4-4의 "이사"가 반대로 작용한 경우).

리뷰에서 cascade = CascadeType.ALL을 발견했습니다. 무엇부터 물어보시겠어요? 가산점힌트: "바꾸세요"가 아니라 질문 네 개로 판단 근거를 끌어낸다

바꾸라고 하기 전에 네 가지를 묻습니다. 이 옵션은 맞고 틀림이 자식의 성격에 달려 있어서, 코드만 보고는 판정할 수 없기 때문입니다.

① "이 자식이 다른 엔티티와 공유되나요?" — 공유되면 REMOVE는 즉시 제거 대상입니다(5절). ② "자식만 따로 조회·수정하는 API나 화면이 있나요?" — 있으면 독립 생명주기이므로 종속이 아닙니다. ③ "자식이 최대 몇 건까지 늘어날 수 있나요?" — 수백 건을 넘길 수 있으면 삭제 시 문장 수와 락 점유를 먼저 계산해야 합니다(6절). ④ "삭제 전파가 의도인가요, 저장 편의가 목적인가요?" — 후자라면 {PERSIST, MERGE}로 충분합니다.

그리고 답이 "삭제 전파가 의도다"라면 ALL 대신 orphanRemoval = true를 명시하도록 요청합니다. 같은 동작이지만 의도가 코드에 적히기 때문입니다. 리뷰의 목적은 이 줄을 고치는 것이 아니라, 몇 달 뒤 "게시글 삭제" 기능을 붙일 사람이 이 파일을 열어보게 만드는 것입니다.

removeIf()는 remove()와 다른가요? 써도 되나요?힌트: 동작은 같다. 위험한 지점이 다르다

고아 판정 관점에서는 같습니다. removeIf()도 결국 컬렉션에서 원소를 빼는 조작이므로, 빠진 자식은 똑같이 고아가 되어 DELETE 대상이 됩니다.

다른 것은 위험의 모양입니다. remove(a)는 대상 하나가 눈에 보이지만, removeIf(조건)는 조건식 한 줄이 몇 건을 지울지 코드만 봐서는 알 수 없습니다. 조건이 true에 가깝게 잘못 짜이면 clear()와 같은 결과가 됩니다.

그래서 처방은 "쓰지 마라"가 아니라 "위치를 정하라"입니다 — 4-3의 syncAttachments처럼 엔티티 안쪽의 도메인 메서드에서만 쓰고, 밖으로는 unmodifiableList만 내보내 서비스 계층에서는 아예 호출할 수 없게 만듭니다(8-3). 그러면 "몇 건이 지워지는가"를 테스트로 단정할 지점도 그 메서드 하나로 좁혀집니다.

한 줄 요약
CascadeType.REMOVE의 방아쇠는 "부모 삭제" 하나뿐이고, orphanRemoval = true는 거기에 "부모와의 연결 해제"가 하나 더 붙어 getAttachments().remove(a) 한 줄이 곧 DELETE가 된다. 그래서 orphanRemoval은 목록을 갈아끼우려던 clear()가 전건 삭제가 되고(그리고 UPDATE 사고와 달리 복구 수단이 백업뿐이다), CascadeType.REMOVE는 대개 ALL에 딸려 들어와 공유되는 자식까지 지운다. 비용은 자식 수만큼 DELETE(1,000건이면 1,000문장)이고, 벌크나 DB ON DELETE CASCADE로 내리면 빨라지는 대신 JPA가 그 삭제를 모르게 된다. 자식이 부모 없이 존재 의미가 없는 종속 관계에만 켜고, ALL을 습관으로 쓰지 않으며, 컬렉션은 unmodifiableList + 전용 메서드로 캡슐화해 잘못 만질 수 없게 막는다.
