컬렉션 fetch join + 페이징
limit이 SQL에서 사라지고 힙에서 잘린다

면접 질문: "fetch join과 페이징을 함께 쓸 때의 문제(메모리에서 페이징)와 해결책은?"

핵심 관전 포인트 — 문제는 fetch join 전체가 아니라 컬렉션(ToMany) fetch join + 페이징이라는 조합 하나다. 판별 축은 딱 하나 — 조인 결과의 행 수가 루트 엔티티 수와 같은가. ToOne(@ManyToOne, @OneToOne)은 부모 1행 대 연관 1행이라 행이 안 늘고 limit이 SQL에 정상 부착되지만, 컬렉션은 부모 1행이 자식 수만큼 불어나 limit 10이 "게시글 10건"이 아니라 "조인 결과 10행"을 자른다. 그러면 마지막 게시글의 댓글이 잘린 채 들어와 데이터가 틀린다. 그래서 Hibernate는 정합성을 지키는 쪽을 택한다 — SQL에서 limit/offset을 아예 빼고, 조건에 맞는 전체를 힙에 올린 뒤 자바에서 subList로 잘라낸다. 그 결과가 이 문항의 본질이다: 예외도 안 나고 결과도 맞는데 데이터가 늘면 OOM으로 죽는다. 사전 신호는 경고 로그 한 줄뿐이고, 개발 DB에서는 증상이 0이다. 그래서 해법 3종(ToOne은 fetch join / 컬렉션은 default_batch_fetch_size / 조회 전용은 DTO 프로젝션)만큼 중요한 것이 배포 전에 잡는 장치다 — hibernate.query.fail_on_pagination_over_collection_fetch: true 한 줄로 경고를 예외로 승격시키는 것이 첫 방어선이다.
  • 1
    범위를 먼저 좁힌다 — 문제는 조합 하나다 — "fetch join과 페이징은 같이 못 쓴다"는 틀린 요약이다. 판별 축은 "조인해도 행 수가 루트 엔티티 수와 같은가" 하나뿐이고, ToOne은 몇 개를 겹쳐도 안전하며 컬렉션 하나가 끼는 순간 limit이 "게시글 N건"이 아니라 "조인 결과 N행"을 자르게 된다.
  • 2
    Hibernate의 선택은 정확성이고, 청구서는 메모리다 — limit을 붙이면 마지막 부모의 자식이 잘려 엔티티 상태가 거짓이 되므로, Hibernate는 SQL에서 limit을 떼고 조건에 맞는 전체를 힙에 올린 뒤 자바 subList로 자른다. 그래서 예외도 없고 결과도 맞는데, 게시글 100만 건이면 1,000만 행을 읽어 20건만 남기고 버린다.
  • 3
    해법 3종보다 중요한 것은 배포 전에 실패시키는 장치다 — 토·컬·조(ToOne은 fetch join / 컬렉션은 default_batch_fetch_size / 조회 전용은 DTO 프로젝션)로 고치되, 예외 없음 · 결과 정상 · 개발 환경 무증상이라 사람 눈으로는 절대 안 잡힌다. fail_on_pagination_over_collection_fetch: true 한 줄이 경고를 예외로 승격시켜 데이터가 적어도 잡아준다.

0. 질문 + 출제 의도

질문: "fetch join과 페이징을 함께 쓸 때의 문제(메모리에서 페이징)와 해결책은?"

출제 의도: limit이 쿼리에 안 붙고 전체를 메모리에 올리는 이 함정은 데이터가 적을 땐 멀쩡하다가 데이터 증가와 함께 OOM으로 터진다. 즉 "지금은 되는데 나중에 터지는" 코드를 미리 알아보는 눈을 검사한다. 채점 지점은 "fetch join과 페이징은 같이 못 쓴다"는 암기가 아니라 — 실패가 어떤 모습으로 드러나는지(예외가 아니라 경고 한 줄)와 그것을 운영 전에 어떻게 붙잡는지다.

함정 — 해결책 나열로 끝내면 이 문항을 통과하지 못한다 질문 형식이 "문제와 해결책"이라 fetch join / @EntityGraph / batch size를 읊고 끝내기 쉽다. 그런데 해결책은 N+1 문항에서 이미 다루는 내용이고, 이 문항이 따로 존재하는 이유는 "쿼리는 성공하는데 나중에 죽는다"는 실패 양식 자체에 있다. 해결책은 절반이고, 나머지 절반은 6절의 탐지 장치다.
이 페이지가 겨냥하는 약점 세 가지 ① "fetch join + 페이징은 금지"로 뭉뚱그리는 것 → 1절에서 판별 축 하나(조인 후 행 수)로 ToOne/컬렉션의 경계를 긋는다.
② "메모리 페이징이 된다"는 결과만 아는 것 → 2·3절에서 왜 limit을 못 붙이는지를 조인 결과의 행 단위까지 내려가서 세우고, Hibernate가 무엇과 무엇 중 무엇을 택했는지로 잇는다.
③ "리뷰에서 잘 보겠다"로 답하는 것 → 6절에서 사람이 안 봐도 실패하는 4층 장치와 도입 순서까지 간다.
버전 기준 버전에 의존하는 서술은 Hibernate 6.x / Spring Boot 3.x 기준이고, 소스 확인이 필요한 부분은 hibernate-core:6.6.53.Final에서 직접 대조한 것이다. Hibernate 7.4부터는 동작 자체가 바뀌었다(파생 테이블로 밀어넣어 DB에서 페이징) — 그래도 이 지식이 여전히 필요한 이유는 7절 마지막 꼬리질문에 있다.

1. 판별 축은 하나 — ToOne이냐 컬렉션이냐

"fetch join과 페이징은 같이 못 쓴다"는 흔한 요약은 틀렸다. 정확히는 컬렉션을 fetch join할 때만 문제다. 그리고 그것을 가르는 축은 연관의 이름표(@OneToOne이냐 @OneToMany냐)가 아니라 조인 결과의 행 수 하나다.

전제 — join과 join fetch는 다르다 일반 join은 SQL 조인만 만들고 select 목록에는 부모만 올린다. 그래서 연관은 여전히 프록시이고 N+1이 그대로다. join fetch여야 연관의 컬럼까지 함께 읽어 한 번에 채운다. 이 문항의 주인공은 join fetch이고, 문제의 씨앗은 "연관 컬럼이 같은 결과 집합에 함께 실린다"는 바로 그 지점에 있다.
안전 ToOne은 몇 개를 겹쳐도 된다
@Query("""
       select p from Post p
       join fetch p.author      // @ManyToOne → 1행 : 1행
       join fetch p.category    // @ManyToOne → 1행 : 1행
       join fetch p.thumbnail   // @OneToOne  → 1행 : 1행
       """)
Page<Post> findPageWithToOnes(Pageable pageable);

// 조인 결과 = Post 20행. limit 20 이 SQL 에 그대로 붙고,
// 원하는 대로 Post 20건이 온다.            행 증폭 없음
위험 컬렉션 하나만 끼면 성질이 바뀐다
@Query("select p from Post p join fetch p.comments")
Page<Post> findPage(Pageable pageable);  @OneToMany

// Post 1건에 댓글 10개면 조인 결과는 10행.
// limit 20 을 붙이면 Post 2건만 온다.
//
// → 그래서 Hibernate 는 limit 을 붙이지 않는다.
//   대신 전체를 힙에 올린 뒤 자바에서 자른다. (3절)

판별 규칙 — 한 문장으로 외운다

조인해도 "결과 1행 = 루트 엔티티 1건"이 유지되면 안전, 깨지면 금지
ToOne = 단일 값
@ManyToOne · @OneToOne — 몇 개를 겹쳐도 행이 안 는다. 목록 화면의 작성자 닉네임 · 카테고리 이름처럼 건당 하나씩 붙는 값은 전부 여기.
ToMany = 컬렉션
@OneToMany · @ManyToMany — 하나만 끼어도 부모 행이 자식 수만큼 복제된다. 페이징과 만나는 순간 금지 구간.

면접에서 "1:1은 괜찮다"가 아니라 "ToOne(단일 값 연관)은 괜찮고 ToMany(컬렉션)만 문제다"라고 말하는 것 — 이 한 단어 차이가 "겪어서 아는 사람"과 "외운 사람"을 가른다.

2. 행 뻥튀기를 눈으로 본다 — limit이 "틀리는" 이유

말로 "행이 늘어난다"고 하면 잘 안 와닿는다. 아주 작은 데이터로 실제 조인 결과를 그려보자. 회원 2명이 각각 주문 3건을 가진 상황에서 select m from Member m join fetch m.orders를 실행하고, 거기에 "회원 2명만 주세요"(limit 2)를 붙이면 무슨 일이 벌어지는가.

비유 — 식당에 "2팀만 받으세요"라고 했는데 직원이 셀 수 있는 단위가 '의자'뿐이라면

요구: 팀 단위 2팀↔직원이 셀 수 있는 단위: 의자→의자 2개를 세면 4인 가족의 절반만 앉는다

부모(팀)와 자식(사람)이 한 줄로 섞여 나오는 명부에서는 "팀 2개"라는 요구를 셀 수 없다. 의자 2개를 세면 ①팀 수도 틀리고(1팀) ②그 팀의 인원도 틀린다(4명인데 2명). 그래서 Hibernate가 택한 방법은 "자르면 사람이 잘리니, 일단 전부 들여보낸 뒤 밖에서 팀 단위로 자르는 것"이다 — 그것이 3절의 메모리 페이징이다.

2-1. 잘린 엔티티는 영속성 컨텍스트에서 한 단계 더 나빠진다

②(내용이 틀림)가 특히 위험한 이유가 하나 더 있다. 오염된 엔티티가 영속성 컨텍스트에 올라가기 때문이다.

스냅샷 자체가 거짓으로 찍힌다 변경 감지는 로딩 시점의 스냅샷과 커밋 시점의 상태를 비교한다. 그런데 스냅샷이 "주문 2건"으로 찍혀 있으므로 Hibernate는 원래 3건이었다는 사실을 알지 못한다. 여기에 orphanRemoval = true가 걸려 있고 누군가 이 컬렉션을 조작하면 실제 DELETE로 이어질 여지까지 생긴다. 조회 하나가 데이터 삭제로 번질 수 있는 경로가 열린다는 뜻이다.

2-2. 조금 더 큰 데이터로 보면 — limit 25가 만드는 "5개짜리 게시글"

Post 1 (댓글 10개) → 조인 결과  1~10행
Post 2 (댓글 10개) → 조인 결과 11~20행
Post 3 (댓글 10개) → 조인 결과 21~30행

여기에 limit 25 를 붙이면 25행까지만 읽는다.
  → Post 1: 댓글 10개 (정상)
  → Post 2: 댓글 10개 (정상)
  → Post 3: 댓글 5개  실제로는 10개인데 5개짜리 게시글로 조립된다
즉 limit을 SQL에 붙이는 선택은 건수를 틀리게 하는 데서 끝나지 않고 엔티티의 상태를 거짓으로 만든다

참고 — 윈도우 함수 row_number()로 부모별 순번을 매겨 흉내 낼 수는 있는데, 그건 LIMIT이 아니라 아예 다른 쿼리다. 7절에서 언급하는 Hibernate 7.4의 파생 테이블 방식이 정확히 이 발상이다.

3. Hibernate의 선택 — limit을 떼고 힙에 올린 뒤 subList

2절까지 오면 Hibernate 앞에 놓인 선택지가 둘뿐이라는 것이 보인다. 그리고 어느 쪽을 골라도 대가가 있다.

컬렉션 fetch join + 페이징을 만났을 때 Hibernate가 고를 수 있는 것
선택지하는 일대가
(A) limit을 붙인다SQL에 limit을 그대로 부착결과가 틀린다 (2절의 ①②)
(B) limit을 뗀다 ← 채택조건에 맞는 전체를 읽어 조립한 뒤 자바에서 자른다메모리를 지불한다

Hibernate는 (B)를 택했다. 결과 오염을 허용하지 않겠다는 판단이다. 이 선택을 알고 나면 아래 동작이 "이상한 버그"가 아니라 의도된 트레이드오프로 읽힌다 — 정확성을 지키기 위해 메모리를 지불한 것이다.

3-1. 기대한 SQL과 실제로 나가는 SQL

기대 limit 이 붙을 거라고 생각한 SQL
select p.*, c.* from post p
left join comment c on c.post_id = p.id
where p.status = 'PUBLISHED'
order by p.created_at desc
limit 20 offset 0;          -- 이 줄이
실제 통째로 사라진 SQL
select p.*, c.* from post p
left join comment c on c.post_id = p.id
where p.status = 'PUBLISHED'
order by p.created_at desc;
-- limit / offset 이 통째로 사라졌다힙으로 이동
status = 'PUBLISHED'가 100만 건이면 — 1,000만 행을 읽어 게시글 100만 개 + 댓글 1,000만 개를 힙에 올린 뒤 앞의 20개만 남기고 버린다

4. 신호는 경고 한 줄 — 그리고 없는 신호 셋

4-1. 로그 한 줄을 토막 내서 읽는다

이 모든 일을 알려주는 신호는 딱 한 줄이다. 애플리케이션 로그에 이렇게 찍힌다.

WARN 21472 --- [nio-8080-exec-3] org.hibernate.orm.query                  :
HHH90003004: firstResult/maxResults specified with collection fetch; applying in memory
이 한 줄을 "아는 사람만 알아듣게" 두면 안 된다 — 토막을 나눠 푼다
토막뜻
firstResult / maxResultsJPA 표준 API Query.setFirstResult(int) / setMaxResults(int)의 이름이다. Spring Data의 Pageable은 결국 이 둘로 번역된다. → "페이징을 걸었다"는 뜻
specified with collection fetch그 쿼리에 컬렉션 fetch join이 함께 걸려 있다
applying in memory그래서 페이징을 DB가 아니라 메모리에서 적용하겠다
HHH90003004Hibernate의 메시지 번호. 로거는 org.hibernate.orm.query, 레벨은 WARN
일상어로 옮기면 — "당신은 20건만 달라고 했지만,
나는 조건에 맞는 전체를 힙에 올린 다음 거기서 20건을 잘라주겠다"

게시글이 100만 건이면 지금 100만 건을 힙에 올리는 중이라는 통보다. 이 한 줄이 그 뜻이라는 것만 알아도 이 문항의 절반은 답한 셈이다.

그런데 이 경고를 찾는 방법에 함정이 하나 더 있다 가산점

인터넷에 널리 인용되는 코드는 HHH000104인데, 이건 Hibernate 5.x의 코드다. 6.6.53 소스에서 확인한 내용은 다음과 같다.

Hibernate 5.x
HHH000104: ... applying in memory!
끝에 느낌표가 있다
Hibernate 6.x 이후
문구는 거의 같지만 id가 90003004라 HHH90003004로 찍히고 느낌표가 없다. 로거 org.hibernate.orm.query, 레벨 WARN
로그를 HHH000104로 grep 하면 6.x 프로젝트에서는 하나도 안 걸린다

검색·알람 룰은 코드가 아니라 문구로 잡는 것이 버전에 안전하다 — firstResult/maxResults specified with collection fetch. 이 원칙은 6절의 테스트 코드에도 그대로 적용된다.

4-2. 이 문항의 진짜 위험 — 평범한 버그의 신호 셋이 전부 없다

① 예외가 안 난다
컴파일도 되고 런타임 예외도 없다. 기본 설정에서는 경고 로그만 찍고 호출은 성공한다.
② 결과가 맞다
반환된 게시글 20건은 정확하고 각 게시글의 댓글도 온전하다. QA가 화면을 봐도 이상한 곳이 없고 페이지 번호와 총 건수까지 다 맞는다.
③ 개발 환경 무증상
로컬 DB 게시글이 200건이면 200건을 힙에 올리는 건 아무 일도 아니다. 부하 테스트를 해도 안 잡힌다 — 요청 수가 아니라 데이터 양의 문제라서.
그래서 이 코드는 정상적으로 리뷰를 통과하고 정상적으로 배포된다 그리고 데이터가 임계점을 넘는 어느 날, 갑자기 죽는다. 죽는 방식도 고약하다 — OutOfMemoryError는 힙을 채운 그 요청이 아니라 옆 요청에서 날 수 있다.

5. 해법 3종 — 토 · 컬 · 조

해법 3종 3초 암기 — 토 · 컬 · 조

토One 연관→fetch join 으로 함께 끌고 온다 (행이 안 느니까)
컬렉션→fetch 에서 빼고 default_batch_fetch_size 에 맡긴다
조회 전용 화면→아예 DTO 프로젝션 (컬렉션은 2단 조회)

면접에서 한 문장으로: "ToOne은 fetch join으로 함께 끌고, 컬렉션은 fetch에서 빼고 batch fetch size에 맡깁니다. 조회 전용 화면이면 아예 DTO 프로젝션으로 갑니다."

5-1. 토 — ToOne 연관은 fetch join으로 함께 가져온다

1절에서 확인한 대로 행이 안 늘어나므로 페이징과 아무 갈등이 없다. 여러 개를 겹쳐도 된다. 목록 API에서 작성자 닉네임, 카테고리 이름처럼 건당 하나씩 붙는 값은 전부 여기서 처리한다.

토 ToOne은 조인으로 끌고 온다 — 쿼리 1개, limit 정상 부착
@Query("select p from Post p join fetch p.author")
Page<Post> findPageWithAuthor(Pageable pageable);
join과 join fetch를 반드시 구분해서 말한다 일반 join은 SQL 조인만 만들고 select 목록에는 부모만 올라가므로 연관은 여전히 프록시이고 N+1이 그대로다. join fetch여야 연관의 컬럼까지 함께 읽는다.

5-2. 컬 — 컬렉션은 default_batch_fetch_size에 맡긴다 (표준 해법)

컬렉션은 쿼리에서 fetch하지 않는다. LAZY로 두고, 실제로 접근하는 순간 Hibernate가 여러 부모의 컬렉션을 묶어서 한 번에 가져오게 한다.

BEFORE 페이징이 메모리로 넘어간다
@Query("select p from Post p join fetch p.comments")
Page<Post> findPage(Pageable pageable);

// limit 이 SQL 에서 사라지고 전량이 힙에 올라간다
AFTER 컬렉션 fetch 를 빼면 끝
Page<Post> findAll(Pageable pageable);  fetch 없음

// limit 이 SQL 에 정상 부착된다.
// p.getComments() 에 접근하는 순간 batch fetch 발동

설정은 한 줄인데, 위치를 틀리는 사람이 아주 많다 가산점

틀림 조용히 무시된다
spring:
  jpa:
    hibernate:            properties 단계가 없다
      default_batch_fetch_size: 100

# 에러도 경고도 없이 그냥 안 먹는다
맞음 Hibernate 로 전달된다
spring:
  jpa:
    properties:           이 단계가 반드시 필요
      hibernate:
        default_batch_fetch_size: 100

Spring Boot에는 이 설정을 위한 전용 프로퍼티가 없어서 spring.jpa.properties. 아래로 넘겨야 Hibernate에 전달된다. "설정했는데 안 먹는다"의 단골 원인이다. 특정 연관만 다르게 주려면 필드에 @BatchSize(size = 200)을 붙인다.

왜 이게 해법이 되는가 — 배치 기능이 특별해서가 아니라, 조인을 안 하기 때문이다

쿼리 수는 1 + N에서 1 + ceil(N / size)로 떨어진다 페이지 크기 20에 size 100이면 1 + ceil(20/100) = 2, 즉 총 2쿼리다. 눈치챘겠지만 이건 "부모를 페이징해 조회 → 그 id들로 컬렉션 일괄 조회 → 애플리케이션에서 조합"이라는 2쿼리 설계를 Hibernate가 대신 해주는 것이다. 손으로 짜던 패턴에 이름이 붙어 있는 것뿐이다.

size는 어떻게 정하나

하한
페이지 크기 이상이 최소선. 페이지 크기가 20인데 size가 5면 컬렉션 쿼리가 4번 나간다.
상한
size만큼 IN 파라미터가 늘어 SQL이 길어지고, DB에 따라 IN 목록의 최대 항목 수 제한에 걸릴 수 있다.
실무 기본값
전역에 100 정도를 깔아 안전망으로 쓰고, 유독 큰 페이지를 쓰는 화면의 연관만 @BatchSize로 올린다. 100~1000 범위를 벗어날 일은 드물다.

공존의 조건을 정확히 말해야 한다 — @EntityGraph를 붙이면 그대로 재현된다

batch fetch가 페이징과 공존하는 이유는 그 기능이 특별해서가 아니라 페이징 쿼리가 컬렉션을 fetch하지 않기 때문이다. 위 (B)의 ①에 조인이 없다는 사실이 전부다.

그래서 default_batch_fetch_size를 켜두고도 @EntityGraph(attributePaths = "comments")를 붙이면 메모리 페이징이 그대로 재현된다 — @EntityGraph는 fetch join과 같은 SQL로 번역되어 (A)로 돌아가기 때문이다.

지켜야 할 규칙은 설정값이 아니라
"페이징 쿼리에서 컬렉션을 fetch하지 않는다"

한계도 정직하게 말한다. 쿼리가 1개가 되는 것은 아니고, N+1을 없애는 게 아니라 1+N을 1+몇 개로 낮추는 완화책이다. 그리고 가장 큰 부작용은 성능이 아니라 은폐다 — 증상이 옅어져서 문제의 존재 자체를 모르게 된다. 그래서 6절의 탐지 장치와 반드시 짝으로 깔아야 한다.

5-3. 조 — 조회 전용 화면이면 애초에 DTO 프로젝션

앞의 둘은 엔티티를 만든다는 전제를 공유한다. 목록 API처럼 읽기만 하는 화면이라면 그 전제를 버리는 게 가장 근본적이다. 엔티티를 안 만들면 프록시도 스냅샷도 없다.

public Page<PostView> page(Pageable pageable) {
    // ① 부모를 필요한 컬럼만, 페이징으로 — 조인이 없으니 limit 정상
    Page<PostRow> posts = postRepository.findRows(pageable);                    // 쿼리 1

    List<Long> postIds = posts.getContent().stream().map(PostRow::id).toList();

    // ② 자식을 id 목록으로 한 번에 — 5-2 (B)②와 같은 모양의 IN 조회다
    Map<Long, List<CommentRow>> byPost = commentRepository.findRowsByPostIdIn(postIds)
            .stream().collect(groupingBy(CommentRow::postId));                  // 쿼리 2

    // ③ 애플리케이션에서 조합 — 총 2쿼리, 페이징 정상, 행 증폭 없음
    return posts.map(p -> new PostView(p, byPost.getOrDefault(p.id(), List.of())));
}
5-2와 5-3은 같은 전략이고, 누가 수행하느냐만 다르다 5-2는 Hibernate가 알아서 해주는 것이고, 5-3은 내가 손으로 쓰는 것이다. 손으로 쓰면 엔티티를 안 만들 수 있다는 이득이 추가된다.

주의 — "DTO를 반환한다"와 "DTO 프로젝션"은 다르다

반환 타입이 DTO여도 엔티티를 조회해서 자바에서 변환하면 아무것도 달라지지 않는다. 엔티티는 이미 다 만들어졌고 영속성 컨텍스트에도 올라갔다. DTO가 쿼리의 결과여야 효과가 있다.

5-4. "id만 먼저 페이징하고 다시 조회"는 언제 필요한가

select distinct p.id from Post p join p.comments c ... limit 20으로 id를 먼저 뽑는 2단계 방식도 자주 언급된다. 방향은 맞지만 조건을 정확히 붙여야 한다.

이때만 필요하다 — 컬렉션에 검색 조건이 걸린 경우

  • 예: "댓글에 특정 키워드가 달린 게시글 목록"
  • 이때는 조인이 불가피하고, 행이 불어나므로 distinct가 SQL에 반드시 있어야 한다.
  • distinct를 붙이면 결과 집합이 다시 "게시글 1건 = 1행"이 되므로 limit이 의미를 되찾는다 — 이것이 이 기법의 원리다.

이때는 그 조인 자체가 불필요하다

  • 컬렉션이 그냥 화면에 필요할 뿐이고 조건은 게시글에만 걸려 있는 경우.
  • select p from Post p where ... limit 20으로 끝이고, 컬렉션은 5-2나 5-3의 방식으로 채우면 된다.
  • 조인을 걷어내는 게 id 서브쿼리보다 낫다.

distinct — 두 경우를 뭉뚱그리면 틀린다 가산점

엔티티 fetch join의 distinct
Hibernate 6부터 불필요하고 오히려 손해. 부모 중복 제거를 Hibernate가 항상 해주는데, distinct를 쓰면 SQL로도 나가서 DB가 중복 제거 비용을 낸다.
id만 프로젝션하는 쿼리의 distinct
여전히 필수. 여기서는 결과 집합을 "1건 = 1행"으로 되돌리는 것 자체가 목적이라 SQL에 나가야 한다.

5-5. 선택 기준 — 상황에서 바로 답으로

상황선택근거
ToOne 연관 (페이징 유무 무관)fetch join / @EntityGraph조인해도 행이 안 늘어 limit 정상
컬렉션 1개 + 페이징 없음fetch join쿼리 1개. 6+ 에서 distinct는 빼는 게 낫다
컬렉션 + 페이징batch fetch sizefetch join 금지 구간
컬렉션 2개 이상batch fetch sizefetch join은 카테시안 곱
조회 전용 목록 APIDTO 프로젝션 (컬렉션은 2단 조회)엔티티·프록시를 아예 안 만든다
전 구간 안전망전역 default_batch_fetch_size놓친 지점의 피해를 낮춘다

6. 배포 전에 잡는 4층 방어선 — 이 문항의 실제 관문

4절에서 확인한 대로 이 버그는 예외 없음 / 결과 정상 / 개발 환경 무증상이 동시에 성립한다. 사람의 주의력으로 잡을 수 있는 조건이 하나도 없다는 뜻이다.

그래서 이 답변들은 여기서 미달로 기록된다 "코드 리뷰에서 잘 보겠다" · "쿼리 로그를 확인하겠다" — 둘 다 사람의 주의력에 기대는 장치다. 필요한 것은 사람이 안 봐도 실패하는 장치다.

6-1. 1층 — 경고를 예외로 승격시킨다 (가장 먼저 할 일)

Hibernate에는 이 상황을 경고 대신 예외로 만드는 설정이 있다. 아는 사람이 드물다.

1층 이 한 줄이 문제의 성격을 바꾼다
spring:
  jpa:
    properties:
      hibernate:
        query:
          fail_on_pagination_over_collection_fetch: true   기본값 false
확인 범위 6.6.53 소스에서 확인했다. 프로퍼티 이름은 hibernate.query.fail_on_pagination_over_collection_fetch이고 기본값은 false, Hibernate 5.2.13부터 존재한다(org.hibernate.cfg.QuerySettings). true면 AbstractSqmSelectionQuery.errorOrLogForPaginationWithCollectionFetch()가 로그 대신 HibernateException을 던진다. 
org.hibernate.HibernateException: setFirstResult() or setMaxResults() specified with
collection fetch join (in-memory pagination was about to be applied, but
'hibernate.query.fail_on_pagination_over_collection_fetch' is enabled)

in-memory pagination was about to be applied가 이 메시지의 요지다 — "막 메모리 페이징을 하려던 참이었는데, 당신이 그걸 하지 말라고 켜뒀으므로 대신 실패한다." 4-1의 경고와 완전히 같은 상황을 가리키는데, 로그 한 줄이 아니라 예외로 온다는 것만 다르다.

켜는 순간 달라지는 것

  • 배포 전에 테스트가 빨간불로 실패한다. 목록 API를 한 번이라도 호출하는 테스트가 있으면 그 자리에서 잡힌다.
  • 데이터가 적어도 잡힌다. 이 검사는 데이터 양이 아니라 쿼리의 모양을 보기 때문이다 — 4-2의 세 번째 조건(개발 환경 무증상)을 정면으로 무력화한다.

주의점 둘

  • 예외는 부팅 시점이 아니라 그 쿼리를 실행하는 시점에 난다. 그러므로 "켜두면 안전하다"가 아니라 "켜두고 그 쿼리를 타는 테스트가 있어야 안전하다"이다.
  • Hibernate 7.4 이상에서는 파생 테이블로 밀어넣기가 가능한 경우 애초에 메모리 페이징이 아니므로 발동하지 않는다.

기본값이 false라는 사실이 이 문항의 핵심을 그대로 말해준다

아무 조치도 안 하면 조용히 메모리 페이징이 된다

6-2. 2층 — 경고 로그를 테스트에서 실패로 만든다

1층을 운영에 켜는 것이 부담스러운 팀도 있다(7절 꼬리질문 참고). 그런 경우에도 테스트에서는 경고 자체를 실패로 다룰 수 있다. 로그 어펜더를 붙여 WARN을 수집한 뒤 단정하면 된다.

// Hibernate 쿼리 로거의 WARN 을 수집해 "한 건도 없어야 한다" 로 못 박는다
class NoInMemoryPaginationTest {

    private ListAppender<ILoggingEvent> appender;
    private Logger queryLogger;

    @BeforeEach
    void attach() {
        // 6.x 의 로거 이름. 5.x 는 org.hibernate 하위의 다른 이름이므로,
        // 버전이 다르면 실제 로그 한 줄을 찍어보고 로거 이름을 확인해 맞춘다.
        queryLogger = (Logger) LoggerFactory.getLogger("org.hibernate.orm.query");
        appender = new ListAppender<>();
        appender.start();
        queryLogger.addAppender(appender);
    }

    @AfterEach
    void detach() { queryLogger.detachAppender(appender); }

    @Test
    void 게시글_목록은_메모리_페이징을_하지_않는다() {
        postService.list(PageRequest.of(0, 20));

        // 메시지 코드(HHH000104 / HHH90003004)는 버전마다 달라지므로 문구로 잡는다
        assertThat(appender.list)
                .noneMatch(e -> e.getFormattedMessage()
                        .contains("firstResult/maxResults specified with collection fetch"));
    }
}
메시지 코드가 아니라 문구로 매칭하는 것이 핵심 — HHH000104는 5.x 코드라서 6.x에서는 절대 안 걸린다
운영 로그 알람 룰도 같은 이유로 문구 기준이어야 한다

6-3. 3층 — 쿼리 수를 단정한다

batch fetch로 고친 뒤에는 "이 API는 쿼리 몇 개인가"를 테스트로 고정한다. 이게 있어야 다음 PR에서 누군가 @EntityGraph(attributePaths = "comments")를 붙여 원상 복구시키는 것을 막을 수 있다.

@Test
void 목록_API_는_쿼리_2개로_끝난다() {
    Statistics stats = entityManagerFactory.unwrap(SessionFactory.class).getStatistics();
    stats.clear();
    entityManager.clear();          // 1차 캐시가 남아 있으면 쿼리 수가 줄어 통과해버린다

    postService.list(PageRequest.of(0, 20));   // 부모 1 + 컬렉션 배치 1

    assertThat(stats.getPrepareStatementCount()).isEqualTo(2);
}
사소하지만 자주 틀리는 것 둘 메서드 이름은 getPrepareStatementCount()다(Prepared가 아니다). 그리고 Statistics를 쓰려면 spring.jpa.properties.hibernate.generate_statistics=true가 필요하다.

6-4. 4층 — "로컬에서 안 터진다"를 안전 신호로 읽지 않는다

가장 중요한데 코드가 아닌 항목이다. 개발 DB에 데이터가 적다는 사실은 검증이 아니라 사각지대다. 이 인식을 픽스처 설계 규칙으로 바꿔야 한다.

BEFORE 데이터는 많은데 통과한다
Post post = savePost();                       부모 1건
IntStream.range(0, 100).forEach(i -> saveComment(post));

// 게시글 1건에 댓글 100개.
// 페이징이 발동을 안 해 문제가 재현되지 않는다
AFTER 두 조건을 동시에 만족시킨다
IntStream.range(0, 50).forEach(i -> {   50 > 페이지 20
    Post p = savePost();
    IntStream.range(0, 3).forEach(j -> saveComment(p)); 3 > 1
});

재현 조건 두 개 — 하나만 만족하는 픽스처는 문제를 통과시킨다

부모 수 > 페이지 크기
페이징이 실제로 잘라야 한다. 부모가 페이지 크기보다 적으면 limit이 아무것도 자르지 않아 차이가 안 난다.
자식 수 > 1
행이 실제로 불어나야 한다. 자식이 1개뿐이면 조인해도 행이 안 늘어 ToOne과 구분이 안 된다.

2절의 표를 떠올리면 왜 두 조건이 다 필요한지가 보인다. 이건 N+1 재현 실패의 원인과 정확히 같은 함정이다 — "픽스처는 건수가 아니라 카디널리티로 설계한다."

여기에 운영 관점의 습관을 하나 더 붙이면 완성된다 "운영 데이터가 지금의 10배가 되면 이 코드는 어떻게 되나"를 목록·검색 API에 대해 배포 전에 한 번씩 묻는 것. 이 문항은 그 질문을 안 하면 절대 안 걸리는 유형이다.
층별 정리 — 무엇이 언제 잡히고 얼마짜리인가
층장치언제 잡히나비용
1fail_on_pagination_over_collection_fetch: true그 쿼리를 실행하는 순간설정 한 줄
2로그 어펜더로 WARN 단정테스트 실행 시테스트 유틸 1개
3Statistics 쿼리 수 단정PR 단계테스트당 3줄
4카디널리티 픽스처위 셋의 전제 조건픽스처 규칙

7. 인출 카드 · 꼬리질문 셀프 테스트

7-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

판별 축 한 문장?
조인해도 "결과 1행 = 루트 엔티티 1건"이 유지되는가. ToOne은 안전 / ToMany만 문제. "1:1이라 안전"이 아니라 "단일 값이라 안전".
Hibernate가 택한 것과 대가?
정확성을 택하고 메모리를 지불했다 — SQL에서 limit을 떼고 전량을 힙에 올린 뒤 자바 subList로 자른다.
grep 기준은?
코드가 아니라 문구 — firstResult/maxResults specified with collection fetch. HHH000104는 5.x 코드라 6.x에선 안 걸린다.
해법 3종 약어?
토·컬·조 — 토One은 fetch join / 컬렉션은 default_batch_fetch_size / 조회 전용은 DTO 프로젝션.
설정 위치 함정?
spring.jpa.properties.hibernate.default_batch_fetch_size. properties를 빼면 에러도 경고도 없이 무시된다.
1층 방어선 이름과 기본값?
hibernate.query.fail_on_pagination_over_collection_fetch — 기본 false. true면 로그 대신 예외.
없는 신호 셋?
예외 없음 · 결과 정상 · 개발 환경 무증상. 그래서 리뷰를 통과하고 정상 배포된다.
재현 조건 둘?
부모 수 > 페이지 크기 AND 자식 수 > 1. 하나만 만족하는 픽스처는 문제를 통과시킨다.
쿼리 수 공식?
1 + N → 1 + ceil(N / size). 페이지 20 · size 100이면 2쿼리.
distinct 두 경우?
엔티티 fetch join의 distinct는 6+ 에서 불필요·손해, id만 프로젝션하는 쿼리의 distinct는 여전히 필수.
컬렉션 둘 + 페이징?
fetch join은 후보에서 탈락(카테시안 곱). ToOne만 fetch join, 컬렉션 둘은 batch → 곱이 아니라 합(총 3쿼리).
한 문장 결론?
"결과가 맞다는 것이 안전하다는 뜻이 아니다." 정확성 문제가 아니라 자원 문제고, 자원 문제는 데이터가 자라야만 드러난다.

7-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

결과는 정확하게 나온다면서요. 그럼 뭐가 문제인가요? 필수힌트: "정확성"과 "자원"을 갈라 말한다

정확성의 문제가 아니라 자원의 문제이기 때문이다. 반환되는 20건은 완벽하지만, 그 20건을 얻기 위해 조건에 맞는 전체를 읽어 엔티티로 조립한다.

비용은 세 군데서 난다 — DB에서 전체 행을 스캔하고 네트워크로 전송하는 I/O, 그것을 엔티티로 만드는 CPU, 그리고 힙 사용량이다.

그리고 이 비용은 데이터 양에 비례해 자란다. 오늘 200건이면 무해하고 내년 200만 건이면 치명적이다.

즉 이건 "버그가 있다/없다"의 문제가 아니라 시한폭탄이 있다/없다의 문제다
페이지 정보(전체 건수, 마지막 페이지)는 왜 정상으로 보이나요? 가산점힌트: Page가 쏘는 쿼리는 하나가 아니다

Page를 반환할 때 총 건수를 세는 count 쿼리는 별도로 나가고, 거기엔 조인 fetch가 없으므로 정상이기 때문이다. 그래서 화면의 페이지네이션 UI는 완벽하게 동작하고, 내용도 맞다.

관측 가능한 모든 지표가 정상을 가리키는데 힙만 조용히 차오르는 상태 — 4-2에서 말한 "신호가 없다"는 것의 구체적인 모습이다. 이 질문에 "count는 정상이라 더 헷갈린다"고 답하면 실제로 겪어본 사람으로 읽힌다.

@EntityGraph(attributePaths = "comments")로 바꾸면 안전한가요? 함정힌트: 무엇으로 "번역"되는지를 본다

아니다. 완전히 같은 문제가 재현된다. @EntityGraph는 fetch join과 같은 SQL로 번역되기 때문이다 — 5-2 도식의 (A)로 그대로 돌아간다.

default_batch_fetch_size를 켜 두었더라도 마찬가지다. batch fetch가 페이징과 공존하는 이유는 그 설정이 특별해서가 아니라 "페이징 쿼리가 컬렉션을 fetch하지 않기 때문"인데, @EntityGraph가 그 전제를 깨버린다.

지켜야 할 것은 설정값이 아니라 규칙이다 —
"페이징 쿼리에서 컬렉션을 fetch하지 않는다"
Page 대신 Slice로 바꾸면 해결되나요? 함정힌트: Slice가 없애는 것은 어느 쿼리인가

해결되지 않는다. Slice가 Page와 다른 점은 총 건수를 세는 count 쿼리를 생략한다는 것뿐이다.

본체 쿼리는 여전히 Pageable을 setFirstResult() / setMaxResults()로 번역해서 실행한다. 그리고 Hibernate가 보는 것은 정확히 그 둘 + 컬렉션 fetch의 조합이다. 그래서 같은 경고가 그대로 찍히고 같은 메모리 페이징이 일어난다.

이 질문의 교훈은 "반환 타입을 바꾸는 것은 쿼리의 모양을 바꾸는 것이 아니다"이다. 고쳐야 할 것은 컬렉션 fetch를 쿼리에서 빼는 것 하나다.

그럼 컬렉션 fetch join은 언제 써도 되나요? 필수힌트: 이 문항이 금지하는 것은 fetch join이 아니라 조합이다

페이징이 없으면 써도 된다. 이 문항이 금지하는 것은 fetch join 자체가 아니라 "컬렉션 fetch join + 페이징"이라는 조합이다.

  • 상세 화면(단건 조회) — where p.id = ?로 부모가 하나면 행이 불어나도 총량이 뻔하다. 쿼리 1개로 끝나는 가장 좋은 선택이다.
  • 결과 전체가 작다는 것이 보장되는 조회 — 조건이 강해서 부모가 수십 건 이하로 닫히는 경우.
  • 단, 컬렉션은 하나만. 둘 이상이면 페이징이 없어도 카테시안 곱이다.

덧붙여 Hibernate 6부터는 이때 distinct를 빼는 게 낫다 — 부모 중복 제거는 Hibernate가 항상 해주는데 distinct를 쓰면 SQL로도 나가서 DB가 중복 제거 비용을 낸다.

default_batch_fetch_size를 전역으로 1000처럼 크게 두면 부작용은 없나요? 필수힌트: 셋인데, 가장 큰 것은 성능이 아니다

세 가지가 있다.

1
IN 파라미터가 그만큼 늘어난다. SQL 길이가 커지고, DB에 따라 IN 목록 항목 수 제한에 걸릴 수 있다.
2
한 번에 올라오는 엔티티 수가 커진다. 배치 크기가 곧 한 쿼리로 힙에 올리는 자식 수의 상한이므로, 자식이 무거운 엔티티면 큰 값이 그 자체로 메모리 압력이 된다.
3
가장 큰 부작용은 은폐다. 값이 크면 N+1이 1+2쯤으로 줄어 로그가 조용해지고, 문제가 있는지조차 모르게 된다.
전역 batch fetch size는 "안전망"이지 "해결"이 아니다
6절의 탐지 장치와 함께 깔지 않으면 "조용한 1 + 수십 쿼리" 상태로 굳는다
컬렉션이 두 개고 페이징도 필요한 화면은 어떻게 푸나요? 필수힌트: List 둘과 Set 둘이 다르게 실패한다

fetch join은 아예 후보에서 빠진다 — 컬렉션 둘을 조인하면 카테시안 곱이 되기 때문이다(각각 100개면 10,000행). 2절 표에서 자식이 한 종류일 때 이미 6행이 됐는데, 두 종류를 동시에 조인하면 두 자식 수를 곱한 만큼으로 불어난다.

그리고 List 둘이면 MultipleBagFetchException으로 크게 실패하지만 Set 둘이면 예외도 경고도 없이 조용히 곱해진다.

정답은 ToOne만 fetch join하고 컬렉션 둘은 batch fetch size에 맡기는 것이다. 각 컬렉션이 독립적인 IN 쿼리로 나가므로 곱이 아니라 합이 되고(총 3쿼리), 페이징도 정상이다.

가산점 흔한 요령인 "List를 Set으로 바꾸면 된다"는
예외를 없애는 것이지 카테시안 곱을 없애는 게 아니다 — 큰 소리로 실패하던 것을 조용한 성능 문제로 바꾸는, 감지 장치를 끄는 행위에 가깝다
쿼리 수를 2로 단정했는데 3이 나옵니다. 테스트가 틀린 건가요? 가산점힌트: 의심할 곳이 둘 있다 — 하나는 반환 타입, 하나는 1차 캐시

먼저 반환 타입을 본다. Page를 반환하면 총 건수를 세는 count 쿼리가 별도로 나간다. 즉 부모 1 + 컬렉션 배치 1 + count 1 = 3이 정상일 수 있다. Slice로 바꾸면 count가 빠져 2가 된다.

반대 방향의 함정도 있다. entityManager.clear()를 안 하면 1차 캐시가 남아 쿼리 수가 오히려 줄어들어 잘못된 코드가 통과해 버린다. 그래서 6-3의 테스트에 stats.clear()와 entityManager.clear()가 함께 들어 있는 것이다.

단정값은 외워서 쓰는 게 아니라 실제 쿼리 로그로 확정한 뒤 고정하는 것이다. 이 테스트의 목적은 "절대값이 몇이냐"가 아니라 "다음 PR에서 이 숫자가 변하면 알아차리는 것"이다.

실제로 limit이 빠졌는지 어떻게 확인하나요? 가산점힌트: 볼 것이 두 군데다 — 로그 한 줄과 SQL 한 줄

두 곳을 본다.

① 애플리케이션 로그의 WARN 한 줄 — firstResult/maxResults specified with collection fetch. 문구로 찾는다(코드는 버전마다 다르다).

② 실제로 나간 SQL — 개발 환경에서 SQL 로깅을 상시 켜두고, 그 목록 쿼리 끝에 limit ? offset ?이 있는지 없는지를 눈으로 확인한다. 3-1의 두 SQL을 나란히 놓고 보면 차이는 마지막 한 줄뿐이다.

다만 이 확인은 사람이 하는 일이라 언젠가 뚫린다. 그래서 답을 여기서 끝내지 말고 "그래서 6절의 1층(fail_on_pagination_over_collection_fetch)을 켜서 사람이 안 봐도 실패하게 만들겠다"까지 이어야 한다.

DTO로 받으면 엔티티가 아니니까 이 문제는 안 생기는 것 아닌가요? 함정힌트: 문제의 원인은 "무엇을 담느냐"가 아니라 "결과 집합의 모양"이다

반환 타입이 아니라 쿼리의 모양이 원인이다. DTO로 받더라도 부모와 컬렉션을 한 번에 조인해서 읽으면 행 증폭은 똑같이 일어난다. 그 결과 집합에 limit을 붙이면 여전히 "부모 N건"이 아니라 "행 N개"를 자른다.

DTO에서 달라지는 것은 얻는 이득이다 — 엔티티·프록시·스냅샷을 안 만들므로 메모리와 CPU가 가벼워진다. 하지만 부모 단위로 자를 수 없다는 문제는 그대로다.

그래서 5-3의 DTO 해법이 굳이 2단 조회 형태인 것이다 — 부모를 페이징으로 먼저 읽고, 자식은 id 목록으로 따로 읽어 애플리케이션에서 조합한다. "DTO라서 안전한 것"이 아니라 "조인을 안 나눠서 안전한 것"이라고 말해야 정확하다.

fail_on_pagination_over_collection_fetch를 운영에도 켜는 게 맞나요? 시니어 변별힌트: "켠다/안 켠다"가 아니라 순서로 답한다

기본 입장은 켜는 쪽이고, 근거는 "예외가 OOM보다 싸다"는 것이다. 이 설정이 없으면 장애는 OOM으로, 무관한 API에서, 원인 불명으로 온다. 켜두면 문제가 그 API 하나의 500 에러로, 스택 트레이스와 함께 온다. 피해 범위와 진단 시간이 비교가 안 된다.

다만 조건 없이 "무조건 켜세요"는 정확한 답이 아니다. 켜는 순간 지금까지 조용히 잘 돌던 API가 즉시 실패하기 때문이다. 그래서 순서를 말하는 편이 낫다.

1
로컬·CI·테스트 프로파일에 먼저 켠다. 여기엔 반대 이유가 없다. 신규 코드가 이 함정에 빠지는 것을 그날로 막는다.
2
스테이징에서 켜고 전 화면을 돌려 기존 위반 지점을 전수로 뽑는다. 이 단계가 운영 적용 전의 조사에 해당한다.
3
위반 지점을 다 정리한 뒤 운영에 켠다. 이때부터는 회귀 방지 장치로 작동한다.
답변의 형태는 "켠다/안 켠다"가 아니라
"어느 환경에 어떤 순서로 켜서, 켜는 행위 자체를 조사 도구로 쓴다"
spring.jpa.open-in-view: false를 켜서 숨어 있던 LazyInitializationException을 드러내는 것과 완전히 같은 전략이다
Hibernate 7.4에서 고쳐졌다면 이 지식은 이제 필요 없는 것 아닌가요? 시니어 변별힌트: 셋인데, 세 번째가 이 문항의 진짜 값이다

세 가지 이유로 여전히 필요하다.

① 버전이 안 따라온다. Spring Boot 3.x는 Hibernate 6.x이고, 현업 프로젝트의 다수가 여기 있다. 프레임워크 메이저 업그레이드는 몇 년 단위로 밀린다.

② 7.4의 개선에도 조건이 있다. 파생 테이블 방식은 DB가 서브쿼리 안의 limit/offset을 지원해야 하고 루트 엔티티가 하나여야 한다. 조건을 못 맞추면 옛 동작으로 떨어지는데, 그때 필요한 지식이 정확히 이것이다. (옛 동작으로 되돌리는 쿼리 힌트가 org.hibernate.limitInMemory다.)

③ 더 중요한 건 원리 쪽이다. 이 문항이 가르치는 것은 limit 부착 여부가 아니라 "조인은 행을 증폭시키고, 페이징의 단위와 조인 결과의 단위는 다르다"는 관계다. 이건 JPA 밖에서도 똑같이 나온다 — MyBatis에서 1:N 조인 결과에 limit을 붙일 때, 리포트 쿼리에서 상세 조인 후 상위 N건을 자를 때 전부 같은 함정이다.

도구가 막아주는 범위가 넓어졌을 뿐, 판단해야 하는 사람은 그대로다
한 줄 요약
컬렉션 fetch join에 페이징을 걸면 조인이 부모 행을 자식 수만큼 복제해 limit이 "부모 N건"을 셀 수 없게 되고, Hibernate는 결과가 틀어지는 것을 막으려 SQL에서 limit을 빼고 전체를 힙에 올린 뒤 자바에서 잘라내며, 예외도 없고 결과도 맞고 개발 환경에선 증상도 없기 때문에 — 해법 3종(토·컬·조 = ToOne은 fetch join / 컬렉션은 batch fetch size / 조회 전용은 DTO)만큼이나 fail_on_pagination_over_collection_fetch로 경고를 예외로 승격시켜 배포 전에 실패하게 만드는 것이 이 문항의 진짜 답이다.
