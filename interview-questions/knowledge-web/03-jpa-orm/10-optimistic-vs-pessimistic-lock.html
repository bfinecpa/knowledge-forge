낙관적 락(@Version)과 비관적 락
잠그지 않고 사후에 감지하는 것 vs 먼저 잠그는 것

면접 질문: "JPA의 낙관적 락(@Version)과 비관적 락의 차이, 각각 언제 사용하나요?"

핵심 관전 포인트 — 첫 문장에서 오해부터 부순다: 낙관적 락은 락이 아니다. 아무것도 잠그지 않고, 충돌을 사후에 감지할 뿐이다. 흔한 오해가 "업데이트 직전에 다시 조회해서 값이 같은지 확인한 뒤 갱신한다"(check-then-act)인데, 별도 SELECT는 존재하지 않는다. 하이버네이트가 날리는 것은 UPDATE ... SET (필드들), version = ? WHERE id = ? AND version = ? 한 문장이고, 확인이 WHERE절 안에 들어가 있기 때문에 확인과 갱신 사이에 틈이 없다. 충돌 판정 근거는 값 비교가 아니라 영향받은 행 수(affected rows)가 0인지이고, 0이면 OptimisticLockException(Spring 계층에서는 ObjectOptimisticLockingFailureException)이 난다. 비관적 락(PESSIMISTIC_WRITE = SELECT ... FOR UPDATE)은 반대로 조회 시점부터 DB가 실제로 행을 잠근다. 선택 기준은 충돌 빈도 × 재시도 비용이지만, 여기에 두 가지를 더 붙여야 답이 완성된다. ① 재시도는 반드시 새 트랜잭션에서 해야 한다 — 같은 트랜잭션에서 재시도하면 1차 캐시에 옛 버전 엔티티가 남아 영원히 실패한다. ② 비관적 락의 숨은 대가는 스레드가 아니라 DB 커넥션이다 — 락 대기 시간 내내 커넥션을 점유하므로 가상 스레드로도 풀 고갈은 해결되지 않는다. 그리고 마지막 축 하나: "기다리느냐 마느냐"가 아니라 "얼마나 오래 기다리게 하느냐"다. 같은 로우를 치는 이상 직렬화는 피할 수 없지만, 락 보유 구간에서 네트워크 왕복과 자바 계산을 걷어내면 임계 구간의 자릿수가 달라진다.
  • 1
    낙관적 락은 락이 아니다 — 잠그지 않고 사후에 감지한다 — 별도 SELECT 없이 UPDATE ... SET ..., version=? WHERE id=? AND version=? 한 문장을 날리고, 영향 행 수가 0인지로 충돌을 판정한다. 확인이 WHERE절 안에 있으므로 확인과 갱신 사이에 틈이 없다.
  • 2
    비관적 락은 조회 시점부터 DB가 진짜로 잠근다 — PESSIMISTIC_WRITE는 SELECT ... FOR UPDATE로 번역되어 사전 차단한다. 대신 락 대기 내내 애플리케이션 스레드 + DB 커넥션 + 열린 트랜잭션을 함께 붙잡으므로, 가상 스레드로도 커넥션 풀 고갈은 해결되지 않는다.
  • 3
    선택 기준은 충돌 확률 × 재시도 비용 × 실패를 노출해도 되는가다 — 낙관적을 고르면 재시도는 반드시 새 트랜잭션에서(같은 트랜잭션이면 1차 캐시 때문에 영원히 실패), 비관적을 고르면 락 타임아웃이 세트다. 둘 다 답이 아닌 고경합에서는 임계 구간의 길이라는 축을 먼저 본다.

0. 질문 + 출제 의도

질문: "JPA의 낙관적 락(@Version)과 비관적 락의 차이, 각각 언제 사용하나요?"

출제 의도: rationale은 이렇게 적고 있다 — "동시 수정 시나리오(같은 회차를 두 관리자가 편집)에서 충돌 빈도와 재시도 비용을 따져 선택하는 판단력. '락이 필요하다'까지는 다 알지만 '어떤 락인지'의 근거를 대는 사람은 적다."

채점 지점 ①
각각이 DB 레벨에서 실제로 무슨 SQL을 만드는가를 아는가
채점 지점 ②
그 차이가 어떤 부작용(재시도 폭풍 / 커넥션 점유)으로 이어지는가를 연결할 수 있는가
채점 지점 ③
우리 서비스의 트래픽 특성에 맞춰 근거를 대며 고를 수 있는가
함정 ① — "낙관적 락"이라는 이름에 속아 "가벼운 락"으로 이해하는 것 낙관적 락은 가벼운 락이 아니라 락이 아예 아니다. 이 차이를 놓치면 "확인과 갱신 사이에 틈이 있으니 결국 안전하지 않다 → 비관적 락밖에 없다"는 오결론까지 자동으로 따라온다.
함정 ② — "충돌이 드물면 낙관적, 잦으면 비관적"에서 멈추는 것 방향은 맞지만 이건 정의를 바꿔 말한 것에 가깝다. 면접관이 원하는 건 "드물다"를 무엇으로 판단하고, 틀렸을 때 각각 어떤 모습으로 무너지는가다.
이 페이지가 가는 길 1~5절은 낙관적 락이 무엇을 하고 무엇을 안 하는가(그리고 세트로 따라오는 재시도), 6~7절은 비관적 락이 대신 치르는 비용과 그것을 줄이는 축, 8~9절은 무엇을 고르고 그 선택을 어떻게 테스트로 보장하는가다.

1. 막으려는 사고부터 — lost update, 갱신 하나가 조용히 증발하는 현상

락 이야기를 시작하기 전에 락으로 막으려는 사고가 무엇인지부터 봐야 한다. 그 사고의 이름이 lost update(갱신 유실)다.

두 트랜잭션이 같은 행을 각자 읽고, 각자 계산해서, 각자 쓰면,
나중에 쓴 쪽이 먼저 쓴 쪽의 갱신을 덮어써서 갱신 하나가 사라진다

"유실"이라는 이름은 여기서 왔다 — 에러도 안 나고 로그도 안 남는데 결과만 틀려 있다. 상품 1번의 재고가 100이고, 두 주문 요청이 동시에 "1개 차감"을 처리하는 장면을 초 단위로 펼치면 사고 지점이 보인다.

1-1. "격리 수준을 올리면 되지 않나요?" — 막히지 않는다

여기서 자연스럽게 나오는 반문이 "트랜잭션 격리 수준을 올리면 되는 것 아닌가"다. 대부분의 서비스가 쓰는 기본 격리 수준에서는 막히지 않는다.

기본 격리 수준에서는 그대로 통과한다

  • MySQL(InnoDB) 기본값 REPEATABLE READ → 통과
  • PostgreSQL·Oracle 기본값 READ COMMITTED → 통과

읽기도 정상이고 쓰기도 정상이며, 둘을 이어붙인 애플리케이션의 판단만 낡았기 때문이다.

SERIALIZABLE이면 막히지만

대가가 전면적이다 — 모든 트랜잭션이 직렬화 비용을 낸다. 이 문제 하나 때문에 꺼낼 선택지가 아니다.

그래서 읽고 쓰는 그 구간을 애플리케이션이 직접 보호해야 한다.

2. 대책은 원리상 두 갈래뿐 — 사전 차단 vs 사후 감지

보호하는 방법은 원리상 두 갈래뿐이다. 이 표가 이 문항 전체의 뼈대다.

두 갈래 — 이름의 유래까지 붙여 두면 정의를 외울 필요가 없다
사전 차단사후 감지
발상남이 못 끼어들게 미리 잠근다끼어들면 나중에 알아채고 실패시킨다
t1에서 하는 일읽으면서 그 행을 잠근다. B는 t2에서 대기그냥 읽는다. B도 그냥 읽는다
충돌 시 모습B가 기다렸다가 최신 값으로 다시 계산B의 UPDATE가 실패하고 예외
이름비관적 락(pessimistic)낙관적 락(optimistic)
이름의 유래"충돌이 날 것"이라고 비관하고 미리 대비"충돌은 안 날 것"이라고 낙관하고 사후 확인
평시 비용잠금·해제 비용을 항상 낸다0 — 충돌이 없으면 아무 추가 비용이 없다
"어느 쪽이 좋은가"가 아니라 "우리 상황에서 충돌이 예외인가 기본값인가"가 선택을 가른다

3. 낙관적 락 — 실제로 나가는 SQL과, 충돌을 감지하는 방식

3-1. 첫 번째 못 — 낙관적 락은 락이 아니다

낙관적 락을 설명할 때 가장 먼저 부숴야 할 오해가 있다. 많은 사람이 @Version의 동작을 "확인하고(check) 나서 행동한다(act)", 즉 check-then-act로 상상한다. 그리고 이 모델이 맞다면 정말로 안전하지 않다.

3-2. @Version이 만드는 SQL — 한 줄이 전부다

엔티티 붙이는 것은 필드 하나
@Entity
public class Product {
    @Id @GeneratedValue
    private Long id;

    private String name;
    private int stock;

    @Version                 // ← 이 한 줄이 전부다
    private Long version;
}
서비스 코드는 평소와 완전히 같다
@Transactional
public void rename(Long id, String newName) {
    Product p = productRepository.findById(id)
                    .orElseThrow();   // version = 3 을 읽음
    p.setName(newName);          // 변경 감지(dirty checking)
}   // ← 커밋 시점에 flush → 아래 UPDATE 가 나간다

// 개발자가 쓰는 코드에는 락에 대한 언급이 전혀 없다.
// 그래서 "무슨 SQL이 나가는가"를 아는 것이 채점 지점이 된다.
SQL 로그 spring.jpa.show-sql=true + 바인딩 파라미터
-- 사람들이 있을 거라고 생각하는 "재확인 SELECT" — 이런 건 나가지 않는다.
-- select version from product where id=?      ← 존재하지 않음

-- 실제로 나가는 것은 이 한 줄뿐이다.
update
    product
set
    name=?,
    stock=?,
    version=?          -- 바인딩 값 = 읽어온 버전 + 1  (즉 4)
where
    id=?
    and version=?      -- 바인딩 값 = 읽어온 버전      (즉 3)
before @Version 없는 엔티티
update product set name=?, stock=?
  where id=?
--      ↑ id 만 본다.
--        남이 뭘 바꿨든 그냥 덮어쓴다
--        = 1절의 lost update
after @Version 붙인 엔티티
update product set name=?, stock=?, version=?
  where id=? and version=?
--                ↑ "내가 읽었을 때
--                   그대로일 때만 써라"

AND version = 3이라는 조건 하나가 하는 일을 말로 풀면 이렇다 — "내가 t1에 읽었던 그 상태가 지금도 유지되고 있을 때만 이 UPDATE를 적용하라." 1절 t4에서 B의 UPDATE가 그냥 통과해버린 이유는 조건이 WHERE id = 1 하나뿐이었기 때문이고, AND version = 3을 붙이면 그 UPDATE는 한 행도 못 고치고 0을 리턴한다. 그 0이 곧 충돌 신호다.

가산점 한 줄 — 로그에는 version + 1이 아니라 version=?로 찍힌다 가산점

하이버네이트는 새 버전 값을 메모리에서 계산해(읽은 값 + 1) 파라미터로 바인딩한다. 개념적으로는 version + 1이 맞지만, 실제 SQL 문자열을 물으면 version=?라고 답하는 편이 정확하다. "직접 로그를 본 사람"과 "책으로만 읽은 사람"이 갈리는 지점이다.

3-3. 충돌은 무엇으로 감지하는가 — 값 비교가 아니라 "영향 행 수"

이 부분이 이 문항의 채점 포인트다. 하이버네이트는 UPDATE 결과로 돌아온 영향받은 행 수(affected rows)만 본다. JDBC의 PreparedStatement.executeUpdate()가 리턴하는 그 정수다.

낙관적 락 3단 인출 — 한 · 영 · 새

한 문장→별도 SELECT 없이 UPDATE ... WHERE id=? AND version=?
영향 행 수 0→값 비교가 아니라 숫자 0으로 사후 감지
새 트랜잭션→재시도는 반드시 트랜잭션 바깥에서 (5절)
낙관적 락은 잠그지 않는다. "충돌하지 않을 것"에 베팅하고, 틀렸을 때 예외를 받는다.

4. @Version 실전 — 예외의 타입과 위치, 그리고 주의점 4가지

4-1. 같은 사건인데 계층마다 이름이 다르다

계층타입언제 보게 되나
JPA 표준jakarta.persistence.OptimisticLockException순수 JPA(EntityManager) 사용 시
하이버네이트org.hibernate.StaleObjectStateException하이버네이트가 내부에서 던지는 원본
Springorg.springframework.orm.ObjectOptimisticLockingFailureExceptionSpring Data JPA 사용 시 실무에서 보는 것
잡는 타입을 틀리면 재시도가 통째로 무력화된다 Spring은 예외 변환(exception translation)을 거쳐 벤더별 예외를 자기 계층의 DataAccessException 계열로 바꾼다. 그래서 Spring Data JPA를 쓰는 코드에서 잡아야 할 것은 ObjectOptimisticLockingFailureException(또는 그 부모인 OptimisticLockingFailureException)이다. catch (OptimisticLockException e)만 걸어두면 안 잡히는 경우가 생긴다.

4-2. 실무에서 더 중요한 것 — 예외가 터지는 위치

착각 "메서드 안에서 try-catch 하면 되겠지"
@Transactional
public void rename(Long id, String newName) {
    Product p = productRepository.findById(id).orElseThrow();
    p.setName(newName);
    // ← 여기서는 아무 일도 안 일어난다. UPDATE 는 아직 안 나갔다.
}   // ← 커밋 직전 flush 에서 UPDATE 가 나가고, 여기서 예외가 터진다
    //   즉 예외는 "메서드 본문 밖", 트랜잭션 경계에서 발생한다

변경 감지는 flush 시점에 UPDATE를 만들고, flush는 보통 커밋 직전이다. 따라서 메서드 안에서 try-catch로 감싸도 이 예외는 안 잡힌다. 예외를 메서드 안에서 보고 싶다면 saveAndFlush()나 entityManager.flush()로 flush를 앞당겨야 한다. 이 사실이 5절(재시도)의 전제가 된다.

4-3. 주의점 ① 엔티티가 실제로 바뀌어야 검사된다

변경된 필드가 없으면 UPDATE 자체가 안 나가고, UPDATE가 없으면 버전 검사도 없다. "읽기만 하고 다른 엔티티를 바꾼" 경우 그 읽은 엔티티는 보호되지 않는다.

before Product를 읽기만 하고 조건으로 삼는다
Product p = productRepository.findById(id)
                .orElseThrow();   // stock = 5 확인
if (p.getStock() >= 1) {
    orderRepository.save(new Order(...));  // Order 만 INSERT
}
// Product 는 안 바뀌었으니 UPDATE 도 없고, version 검사도 없다.
// 그 사이 다른 트랜잭션이 stock 을 0으로 만들어도 우리는 모른다.
after 읽기만 한 엔티티에도 락 모드를 명시한다
// 커밋 시 version 을 확인만 한다
Product p = entityManager.find(Product.class, id,
        LockModeType.OPTIMISTIC);

// 또는 "이 엔티티를 건드렸다"고 버전을 강제로 올린다
        LockModeType.OPTIMISTIC_FORCE_INCREMENT;
// → version 을 +1 해서 UPDATE 를 강제 발행
OPTIMISTIC_FORCE_INCREMENT는 애그리거트 루트 보호에 쓴다 애그리거트란 "함께 변경되고 함께 일관성을 지켜야 하는 엔티티 묶음"이고, 그 대표가 루트다. 자식(OrderItem)만 바뀌었는데 부모(Order)의 버전을 올려서 "이 주문 전체가 변경됐다"고 표시하는 식이다.

4-4. 주의점 ② 벌크 연산은 버전을 올리지 않는다

@Modifying JPQL이나 네이티브 UPDATE는 영속성 컨텍스트와 @Version을 모두 우회한다. 버전을 올려야 한다면 SQL에 직접 써야 한다.

before version이 그대로 남는다
@Modifying
@Query("update Product p set p.stock = p.stock - 1 " +
       "where p.id = :id")
int decrease(@Param("id") Long id);
// → 다른 트랜잭션의 낙관적 락이 이 변경을 감지하지 못한다
after 벌크에서도 버전을 직접 올린다
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update Product p set p.stock = p.stock - 1, " +
       "p.version = p.version + 1 " +
       "where p.id = :id and p.stock >= 1")
int decrease(@Param("id") Long id);

4-5. 주의점 ③ 버전 필드 타입  /  ④ 준영속 엔티티

③ 타입은 정수 계열로
JPA 스펙이 보장하는 것은 정수 계열(int·Integer·short·Short·long·Long)과 java.sql.Timestamp다. 타임스탬프는 피하는 게 좋다 — 시계 정밀도가 낮으면 서로 다른 두 수정이 같은 값이 되어 충돌을 놓칠 수 있다. 숫자를 쓰면 그런 여지가 없다.
④ 준영속 엔티티에도 버전이 실린다
준영속(detached)은 한 번 영속 상태였다가 영속성 컨텍스트의 관리에서 벗어난 객체다. 화면에서 받은 DTO에 version을 담아 merge()하면 "화면을 연 시점" 기준의 충돌 검사가 된다 — 두 관리자 동시 편집 시나리오를 푸는 정석이다. 다만 merge()는 전 필드를 덮어쓰므로 PATCH 용도로는 쓸 수 없다.

@Version을 붙였는데 충돌이 감지되지 않는 4가지 — 안 · 벌 · 다 · 인

안
안 바뀜
엔티티가 변경되지 않으면 UPDATE도 버전 검사도 없다 → LockModeType.OPTIMISTIC 명시
벌
벌크 연산
@Modifying·네이티브 SQL은 version을 우회한다 → SQL에 직접 version + 1
다
다른 행
@Version은 그 엔티티 행 하나만 보호한다. 자식만 바뀌면 부모 버전은 그대로 → OPTIMISTIC_FORCE_INCREMENT
인
INSERT
낙관적 락은 "이미 있는 행"의 갱신 충돌만 다룬다. 동시 INSERT 중복은 DB 유니크 제약이 막아야 한다

네 가지의 공통점은 하나다 — "버전이 실린 UPDATE가 그 행에 나가지 않았다." 이 문장으로 되짚으면 네 케이스를 외우지 않아도 즉석에서 재구성할 수 있다.

5. 재시도의 함정 — 같은 트랜잭션에서 재시도하면 영원히 실패한다 시니어 변별

낙관적 락은 "실패할 수 있다"를 전제로 하는 구조다. 그러니 재시도가 세트로 따라온다. 그런데 여기가 실무에서 가장 많이 틀리는 지점이고, 이 문항의 백미이기도 하다.

before 절대 성공하지 않는 재시도 — 100번으로 늘려도 100번 다 실패한다
@Transactional                                  // ← 루프가 이 안에 있다
public void decrease(Long id) {
    for (int i = 0; i < 3; i++) {
        try {
            Product p = productRepository.findById(id).orElseThrow();
            p.setStock(p.getStock() - 1);
            productRepository.flush();      // 여기서 UPDATE + 충돌 감지
            return;
        } catch (ObjectOptimisticLockingFailureException e) {
            // 다시 시도 → 그런데 findById 가 DB 를 다시 읽지 않는다
        }
    }
}

얼핏 보면 문제가 없어 보인다. 실패하면 다시 조회하고 다시 계산해서 다시 쓰겠다는 것이니 직관에도 맞는다. 그런데 이 코드는 3번 다 실패한다. 이유가 두 겹이다.

문제의 두 축(1차 캐시와 롤백 표시)이 모두 "트랜잭션 하나"에 묶여 있다
→ 그것들을 버리려면 트랜잭션 자체를 끝내야 한다 → 재시도는 트랜잭션 바깥에서 일어나야 한다

5-1. 올바른 형태 — 재시도의 매 회차가 새 트랜잭션이어야 한다

after ① 재시도만 담당하는 빈 — @Transactional 없음
@Service
@RequiredArgsConstructor
public class StockFacade {

    private final StockService stockService;

    @Retryable(
        retryFor = ObjectOptimisticLockingFailureException.class,
        maxAttempts = 5,
        backoff = @Backoff(delay = 50, multiplier = 2.0,
                           maxDelay = 500, random = true)
    )
    public void decrease(Long id) {
        stockService.decrease(id);   // 호출마다 새 트랜잭션
    }

    @Recover                          // ← 포기 경로. 필수다.
    public void recover(ObjectOptimisticLockingFailureException e,
                        Long id) {
        throw new StockConflictException("잠시 후 다시 시도해 주세요", e);
    }
}
after ② 트랜잭션만 담당하는 빈
@Service
@RequiredArgsConstructor
public class StockService {

    private final ProductRepository productRepository;

    @Transactional                   // ← 트랜잭션만 담당
    public void decrease(Long id) {
        Product p = productRepository.findById(id).orElseThrow();
        if (p.getStock() < 1) throw new OutOfStockException();
        p.setStock(p.getStock() - 1);
    }
    // ← 커밋. 충돌이면 여기서 예외
    //    → 트랜잭션 롤백 → 영속성 컨텍스트도 함께 폐기
}

// 달라진 것은 "재시도 루프의 위치" 하나뿐이다.
// BEFORE: 루프가 @Transactional 안
// AFTER : 루프(@Retryable)가 @Transactional 바깥

5-2. 왜 굳이 빈을 분리했나 — 프록시(AOP) 순서 문제 가산점

@Retryable과 @Transactional을 같은 메서드에 붙이면 순서가 어긋날 위험이 있다. 둘 다 스프링이 프록시로 가로채 동작하는 기능이라, 어느 프록시가 바깥에 오느냐로 결과가 완전히 달라진다.

덤 — 자기 호출(self-invocation) 함정도 같이 막힌다 같은 클래스 안에서 this.decrease()처럼 자기 메서드를 호출하면 프록시를 거치지 않아 @Retryable도 @Transactional도 아예 동작하지 않는다. 빈 분리는 이 함정도 함께 제거한다.

5-3. 재시도를 안전하게 만드는 것들, 그리고 남는 한계

재시도 3종 세트 — 새 트랜잭션 · 백오프+지터 · 상한과 포기 경로

새 트랜잭션
매 회차가 새 영속성 컨텍스트여야 findById가 DB를 다시 읽는다. 빈을 분리해 강제한다.
지수 백오프 + 지터
대기를 회차마다 곱해 늘리고(50→100→200→400ms) 난수를 섞는다. 지터가 없으면 실패한 요청들이 정확히 같은 시각에 깨어나 또 같이 부딪힌다(thundering herd).
상한 + 포기 경로
maxAttempts와 @Recover. 상한이 없으면 6절의 커넥션 고갈과 똑같은 결말로 간다.
그래도 남는 한계 — 재시도 폭풍(retry storm) 한정판 재고처럼 초당 500건이 전부 같은 로우 하나를 치면 이야기가 달라진다.
1라운드 500건 → 1건 성공, 499건 영향 행 수 0→ 2라운드 499건 전부 처음부터 재실행 → 1건 성공→ 3라운드 498건 …

성공 1건당 낭비되는 작업량이 대기 중인 요청 수에 비례한다. 낙관적 락의 전제("충돌은 드물다")가 깨진 상황이고, 여기서 낙관적 락은 틀린 도구다. 게다가 재시도 비용은 UPDATE 한 번이 아니라 비즈니스 로직 전체의 재실행이다 — 로직 안에 외부 API 호출이라도 있으면 재시도는 곧 그 API를 5배 때리는 것이 된다.

6. 비관적 락 — 진짜로 잠그고, 대신 커넥션을 붙잡는다

6-1. 무엇이 어떤 SQL로 나가는가

코드 리포지토리 메서드에 락 모드를 건다
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select p from Product p where p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}
SQL 위 메서드가 만드는 것 (MySQL/PostgreSQL 기준)
select p.id, p.name, p.stock, p.version
  from product p
 where p.id = ?
 for update
--  ↑ 이 행은 지금부터 내 트랜잭션이 커밋/롤백할 때까지
--    다른 트랜잭션이 못 건드린다

FOR UPDATE가 붙는 순간 1절의 타임라인이 달라진다. t2에서 B가 같은 행을 읽으려 하면 B는 거기서 멈춰 서서 A의 커밋을 기다리고, A가 커밋한 뒤에야 99라는 최신 값을 읽는다. 그러면 B의 계산은 99 - 1 = 98이 되어 lost update가 애초에 성립하지 않는다. "사전 차단"이라는 표현이 이 뜻이다.

락 모드 3종 — 실무에서 쓰는 건 사실상 PESSIMISTIC_WRITE 하나다
모드하는 일전형적 SQL
PESSIMISTIC_READ공유 락 — 남의 읽기는 허용, 쓰기는 차단for share (구버전 MySQL은 lock in share mode)
PESSIMISTIC_WRITE배타 락 — 읽기·쓰기 모두 차단for update
PESSIMISTIC_FORCE_INCREMENT배타 락 + version 강제 증가for update + version UPDATE
모르면 PESSIMISTIC_WRITE를 쓰는 게 안전하다 PESSIMISTIC_READ는 DB와 방언에 따라 지원 범위가 다르고, 공유 락을 지원하지 않는 DB에서는 배타 락으로 강등되어 결과적으로 PESSIMISTIC_WRITE와 같아질 수 있다. 또 공유 락은 "둘 다 읽고 둘 다 쓰려고 하는" 전형적인 데드락 패턴을 만들기 쉽다. PESSIMISTIC_FORCE_INCREMENT는 잠금과 동시에 버전을 올려서, 비관적 락으로 보호한 변경을 낙관적 락 진영(준영속 화면 편집 등)에도 알려야 할 때 쓴다.

6-2. 숨은 대가 — 붙잡히는 건 스레드가 아니라 커넥션이다 시니어 변별

"비관적 락으로 바꾸면 재시도 폭풍은 사라진다"는 맞다. 499건은 재실행하지 않고 그냥 기다린다. 문제는 기다리는 동안 무엇을 붙잡고 있느냐다.

가장 자주 나오는 오해 — "가상 스레드를 쓰면 되지 않나요?" 시니어 변별

가상 스레드가 싸게 만든 것

스레드다. 스레드를 수만 개 만들어도 부담이 없어졌다.

그런데 이 상황의 병목

커넥션 풀 크기이고, 그건 그대로 20개다. 오히려 스레드가 싸져서 동시 요청을 더 많이 받아들이면 커넥션을 기다리는 줄만 더 길어진다.

게다가 락 대기는 DB 서버 안에서 일어나는 블로킹이라 JVM이 스레드를 언마운트해 다른 일을 시킬 수도 없다.

답은 "가상 스레드로 해결하겠다"가 아니라 — "자원의 종류를 구분하고 격리하겠다"
락 타임아웃으로 점유 시간의 상한을 못 박고, 가능하면 별도 커넥션 풀로 벌크헤드를 만든다

6-3. 락 타임아웃 — 무한정 기다리게 두지 않는다

기본값으로 두면 요청은 DB가 정한 시간만큼 하염없이 기다린다. 락 대기 시간에 상한을 걸어야 커넥션 점유 시간의 최댓값이 정해진다.

6-4. 데드락과 락 획득 순서

두 트랜잭션이 서로 다른 순서로 두 행을 잠그면 교착 상태가 된다. 데드락은 "서로가 상대가 쥔 것을 기다려 둘 다 영원히 진행하지 못하는 상태"를 말한다.

before 요청마다 잠그는 순서가 다르다
// A: 계좌 1 잠금 → 계좌 2 잠금 시도
// B: 계좌 2 잠금 → 계좌 1 잠금 시도  ⇒ 순환 대기 = 데드락
public void transfer(Long fromId, Long toId, long amount) {
    Account from = repo.findByIdForUpdate(fromId).orElseThrow();
    Account to   = repo.findByIdForUpdate(toId).orElseThrow();
    ...
}
after 항상 같은 기준(id 오름차순)으로 잠근다
public void transfer(Long fromId, Long toId, long amount) {
    List<Long> ordered = Stream.of(fromId, toId).sorted().toList();
    Map<Long, Account> locked = ordered.stream()
            .map(id -> repo.findByIdForUpdate(id).orElseThrow())
            .collect(toMap(Account::getId, identity()));
    // 모든 트랜잭션이 작은 id 부터 잠그므로 순환 대기가 성립할 수 없다
    ...
}
여러 행을 잠가야 한다면, 시스템 전체가 합의한 하나의 순서로 잠근다 — 순환이 없으면 데드락도 없다

DB는 데드락을 감지하면 한쪽을 희생시켜 예외를 던진다. 이 경우는 재시도가 정당하다 — 상대가 이미 물러났으므로 다시 하면 성공할 가능성이 높다. 낙관적 락 재시도와 같은 원칙(새 트랜잭션 + 백오프 + 상한)이 그대로 적용된다.

7. 놓치기 쉬운 축 — "기다리느냐"가 아니라 "얼마나 오래 기다리느냐" 가산점

"어떤 방법을 써도 같은 로우를 1씩 깎는 이상, 어딘가에서는 순서대로 처리될 수밖에 없다" — 이 직관은 완전히 옳다. 낙관적 락이든 비관적 락이든 Redis 분산 락이든, 직렬화 지점을 없앨 수는 없고 위치만 옮길 뿐이다.

그래서 축을 바꾼다 — 임계 구간(critical section)의 길이

임계 구간은 "한 번에 하나만 들어갈 수 있는 구간"이다. 직렬화를 없애는 게 아니라 직렬화되는 구간을 짧게 만드는 것이 목표다.

처리량 ≈ 1 / 임계 구간
줄을 없앨 수 없다면 창구 처리 시간을 줄이는 것이 유일한 개선 축

같은 "줄 서기"인데 앞사람이 창구에서 5분 있느냐 5초 있느냐의 차이다.

정직하게 덧붙일 것 — 행 락은 문장이 끝날 때가 아니라 커밋할 때 풀린다 그러니 "한 문장이면 락이 마이크로초만 걸린다"는 말은 정확하지 않다. 줄어드는 것은 락 보유 구간 안에 들어 있던 왕복 횟수와 애플리케이션 처리 시간이다. 이 트랜잭션이 그 UPDATE 하나만 하고 즉시 커밋하는 형태여야 효과가 온전히 난다.

7-1. 부수 효과 — 같은 숫자 0인데 의미가 다르다

good 영향 행 수 0 = "재고 없음"이라는 최종 결론

if (affected == 0) {
    throw new OutOfStockException();   // 재시도 아님 — 즉시 품절 응답

→ 재시도가 필요하다

원자적 UPDATE의 0

AND stock >= 1이 거짓 → "재고가 없다"는 최종 결론
→ 재시도 자체가 필요 없다 = 재시도 폭풍이 구조적으로 사라진다

이 문항에서의 만점 선 — 딱 여기까지 가산점 이 방식도 공짜는 아니다 — 영속성 컨텍스트를 우회하고, 도메인 로직이 SQL로 새어 나가며, "몇 개 남았는지"를 알려면 다시 읽어야 한다. 낙관적 락 / 비관적 락 / 원자적 UPDATE / 분산 락 4종의 본격적인 비교는 고난이도 전용 문항("재고 차감/포인트 차감 같은 동시성 갱신 문제를 … 각각으로 풀 때의 트레이드오프")에서 다룬다. 이 문항에서는 "임계 구간의 길이라는 축이 존재한다"는 것을 아는 선까지가 만점이고, 면접에서도 딱 여기까지 말하고 "자세한 비교는 케이스에 따라"로 넘기는 게 깔끔하다.

노 — 실패 노출 가능성

9. 보장은 테스트에서 나온다 — CountDownLatch로 출발선 만들기

동시성 버그는 평소에 안 나고, 트래픽이 몰릴 때만 난다. 그래서 "이 코드는 동시성에 안전합니다"를 말로 하면 아무 보장이 안 된다. 재현하는 테스트를 코드로 고정하는 것이 유일한 방법이다.

good 동시 출발 테스트 — @Transactional이 없다는 점에 주목
@SpringBootTest
// @Transactional 을 붙이지 않는다 (9-2 참고)
class StockConcurrencyTest {

    @Autowired StockFacade stockFacade;            // 재시도 포함 진입점
    @Autowired ProductRepository productRepository;
    @Autowired TransactionTemplate txTemplate;

    Long productId;

    @BeforeEach
    void setUp() {
        // 테스트 트랜잭션이 아니라 "커밋되는" 트랜잭션으로 픽스처를 만든다
        productId = txTemplate.execute(status ->
                productRepository.save(new Product("한정판", 100)).getId());
    }

    @Test
    void 동시에_100건이_차감해도_재고는_정확히_0이_된다() throws Exception {
        int threadCount = 100;
        ExecutorService pool = Executors.newFixedThreadPool(32);

        CountDownLatch ready = new CountDownLatch(threadCount);   // 전원 준비 완료 대기
        CountDownLatch start = new CountDownLatch(1);             // 출발 신호
        CountDownLatch done  = new CountDownLatch(threadCount);   // 전원 종료 대기

        AtomicInteger success  = new AtomicInteger();
        AtomicInteger conflict = new AtomicInteger();

        for (int i = 0; i < threadCount; i++) {
            pool.submit(() -> {
                ready.countDown();
                try {
                    start.await();          // ← 전원이 대기하다가 동시에 출발
                    stockFacade.decrease(productId);
                    success.incrementAndGet();
                } catch (ObjectOptimisticLockingFailureException
                         | StockConflictException e) {
                    conflict.incrementAndGet();  // 충돌은 "실패"가 아니라 관측 대상이다
                } catch (Exception e) {
                    throw new RuntimeException(e);
                } finally {
                    done.countDown();
                }
            });
        }

        ready.await();                              // 100개가 전부 출발선에 설 때까지
        start.countDown();                         // 동시 출발!
        assertThat(done.await(30, TimeUnit.SECONDS)).isTrue();
        pool.shutdown();

        // 테스트의 영속성 컨텍스트가 아니라 DB 의 최종 상태를 읽어야 한다
        int finalStock = txTemplate.execute(status ->
                productRepository.findById(productId).orElseThrow().getStock());

        assertThat(finalStock).isEqualTo(100 - success.get());  // ① 초과 차감이 없다
        assertThat(success.get() + conflict.get()).isEqualTo(threadCount);  // ②
        assertThat(finalStock).isZero();                          // ③ 재시도가 제대로 돌았다면 0
    }
}

단정할 것 세 가지

① 산술이 맞는가
최종 재고 = 초기 − 성공 건수. 초과 차감·lost update가 없는가
② 합계가 맞는가
성공 + 충돌 = 전체 요청 수. 조용히 사라진 요청이 없는가
③ 최종 수렴하는가
재시도를 붙였다면 최종적으로 전부 성공했는가
@Version을 일부러 떼고 돌려서 먼저 실패시켜 보는 것까지가 세트다
최종 재고가 0이 아니라 한참 큰 값으로 남는다 — 그게 1절에서 그린 lost update의 모습이고, 테스트가 진짜 동작한다는 증거다

동시성 테스트에는 @Transactional을 붙이지 않는다
대신 TransactionTemplate으로 커밋되는 픽스처를 만들고 @AfterEach에서 직접 지운다

10-1. 문서가 직접 다루는 꼬리질문

확인하는 순간과 업데이트하는 순간 사이에 다른 트랜잭션이 끼어들면 어떻게 되나요? 필수힌트: "그런 일이 생기면"으로 답하지 말고, 전제 자체를 부순다

그 '사이'가 존재하지 않는다는 것이 답이다. 확인이 별도 SELECT가 아니라 UPDATE ... WHERE id = ? AND version = ?의 조건절 안에 있기 때문이다. DB는 한 문장을 원자적으로 처리하고, 그 행에 대해 UPDATE는 내부적으로 직렬화된다. 두 트랜잭션이 동시에 같은 조건으로 UPDATE를 날리면 한쪽만 영향 행 수 1을 받고, 나머지는 0을 받는다.

일반화하면 이렇다 — check-then-act가 위험한 이유는 "두 문장"이기 때문이고, 해결책은 락을 거는 것만이 아니라 두 문장을 한 문장으로 합치는 것이다.

@Version — 확인을 WHERE로 유니크 제약 — 중복 체크 대신 제약 위반을 잡기 원자적 UPDATE — 조건을 WHERE로 (7절) Redis SETNX

네 가지가 전부 같은 원리다. 이 연결을 말하면 "암기한 사람"이 아니라 "원리를 잡은 사람"으로 들린다.

낙관적 락 재시도를 걸었는데 예외가 계속 나거나 아예 안 잡힙니다. 왜죠? 필수힌트: 세 가지를 순서대로 의심한다
1
재시도가 트랜잭션 안에 있다. 낙관적 락 예외는 커밋 시점에 터지므로, 트랜잭션 안쪽의 try-catch나 @Retryable은 잡을 기회조차 없다. 잡히더라도 1차 캐시 때문에 무한 실패한다. → 재시도 빈과 트랜잭션 빈을 분리한다.
2
잡는 예외 타입이 틀렸다. Spring Data JPA에서는 OptimisticLockException이 아니라 ObjectOptimisticLockingFailureException으로 변환되어 올라온다.
3
자기 호출(self-invocation)이다. 같은 클래스 안에서 this.method()로 부르면 프록시를 안 거쳐 @Retryable이 아예 적용되지 않는다.

세 가지 모두 "예외가 어디서 터지고, 누가 그것을 감싸고 있는가"라는 하나의 질문으로 수렴한다.

비관적 락을 쓰면 대기하는 요청들이 스레드를 붙잡습니다. 가상 스레드로 해결되나요? 시니어 변별힌트: "무엇이 싸졌는가"와 "무엇이 병목인가"를 갈라 말한다

해결되지 않는다. 가상 스레드가 싸게 만든 자원은 스레드지만, 이 상황의 병목은 DB 커넥션 풀이다. SELECT ... FOR UPDATE로 대기 중인 요청은 커넥션과 열린 트랜잭션을 함께 붙잡고 있고, 풀 크기는 가상 스레드와 무관하게 그대로다. 오히려 스레드가 싸져서 동시 유입이 늘면 커넥션 대기 줄만 길어진다.

그리고 더 나쁜 건 영향 범위다. 커넥션은 서비스 전체가 공유하는 자원이라, 재고 API 하나의 경합이 로그인·조회 등 락과 아무 관계 없는 API까지 마비시킨다.

그래서 답은 이렇게 맺는다 — 반드시 락 타임아웃으로 커넥션 점유 시간의 상한을 못 박고, 가능하면 별도 커넥션 풀(또는 별도 인스턴스)로 격리해 벌크헤드를 만든다. "가상 스레드로 해결하겠다"가 아니라 "자원의 종류를 구분하고 격리하겠다"가 답이다.

그럼 Redis 분산 락을 쓰면 되지 않나요? 시니어 변별힌트: "개선되는 것"을 먼저 인정하고, 그 다음에 한계를 댄다

DB 커넥션을 대기에서 떼어낸다는 점에서는 개선이 맞다. 대기 줄이 DB 밖으로 나가므로 커넥션 풀이 락 대기로 고갈되지는 않는다. 다중 인스턴스 환경에서 JVM 락으로는 불가능한 조정을 해주는 것도 사실이다.

다만 이 문항의 시나리오를 근본적으로 풀지는 못한다. 500건이 여전히 줄을 서고, 임계 구간은 오히려 Redis 왕복까지 더해져 길어질 수 있다. 게다가 락과 데이터가 서로 다른 시스템에 있으므로 Redis 장애 시 정합성 보장이 통째로 사라지고, TTL이 만료됐는데 작업이 아직 안 끝난 경우 같은 새로운 실패 모드가 생긴다.

① 임계 구간 자체를 줄일 수 있는가 (7절)→ ② 단일 DB로 해결되면 분산 락 불필요→ ③ 여러 시스템에 걸친 자원 조정이 필요할 때만
분산 락은 "성능 해법"이 아니라 "경계를 넘는 조정이 필요할 때의 도구"다
@Version을 붙였는데 충돌이 감지되지 않는 경우가 있나요? 필수힌트: 안·벌·다·인

있다. 네 가지가 대표적이다.

  • 안 — 엔티티가 변경되지 않은 경우. UPDATE가 안 나가면 버전 검사도 없다. 읽기만 한 엔티티를 보호하려면 LockModeType.OPTIMISTIC이나 OPTIMISTIC_FORCE_INCREMENT를 명시해야 한다.
  • 벌 — 벌크 연산(@Modifying)이나 네이티브 SQL로 우회한 경우. version을 직접 올리지 않으면 다른 트랜잭션은 그 변경을 감지하지 못한다.
  • 다 — 다른 행을 바꾼 경우. @Version은 그 엔티티 행 하나만 보호한다. 자식 컬렉션만 바뀌었다면 부모의 버전은 그대로다 → OPTIMISTIC_FORCE_INCREMENT로 애그리거트 단위 보호를 건다.
  • 인 — 애초에 없던 행을 만드는 경우(INSERT). 낙관적 락은 "이미 있는 행"의 갱신 충돌만 다룬다. 동시 INSERT로 인한 중복은 DB 유니크 제약이 막아야 한다 — 별도 문항의 주제다.

네 가지를 따로 외우지 말고 "버전이 실린 UPDATE가 그 행에 나갔는가?" 하나로 되짚으면 즉석에서 재구성된다.

낙관적 동시성 제어를 HTTP API 계층에서는 어떻게 표현하나요? 가산점힌트: @Version과 정확히 같은 구조가 HTTP 명세에도 있다

서버가 응답에 ETag(리소스의 현재 버전 식별자)를 실어 보내고, 클라이언트는 수정 요청에 If-Match: <그 ETag>를 담아 보낸다. 서버는 현재 버전과 다르면 412 Precondition Failed를 돌려준다.

DB 계층

UPDATE ... WHERE id=? AND version=?
→ 영향 행 수 0 → OptimisticLockException

HTTP 계층

PUT /notices/1 + If-Match: "3"
→ 버전 불일치 → 412 Precondition Failed

ETag를 엔티티의 @Version 값으로 만들면 DB의 낙관적 락이 API 계약으로 그대로 번역된다. "두 관리자가 같은 화면을 편집"하는 시나리오를 안전하게 만드는 표준적인 방법이고, 이 연결을 말할 수 있으면 계층을 넘나드는 설계 감각을 보여주게 된다.

10-2. 한 칸씩 더 파고드는 꼬리질문

PESSIMISTIC_WRITE를 걸었는데도 갱신이 유실됐습니다. 어떻게 그럴 수 있죠? 함정힌트: 락은 "그 락을 잡는 경로들끼리만" 유효하다

같은 행을 건드리는 다른 경로가 락을 잡지 않고 지나갔기 때문이다. 비관적 락은 모든 접근 경로가 같은 규약을 지킬 때만 성립하는 협조적 장치다.

전형적인 구멍은 이렇다. 주문 API는 findByIdForUpdate()로 잠그고 차감하는데, 관리자 재고 조정 화면은 평범한 findById()로 읽어 계산하고 저장한다. 관리자 쪽은 락 없이 읽은 낡은 값으로 UPDATE를 날리므로 1절의 lost update가 그대로 재현된다 — 심지어 그 UPDATE는 행 락을 기다렸다가 순서대로 얌전히 덮어쓴다.

"이 행을 어떻게 잠글까"가 아니라 "이 행을 바꾸는 코드 경로가 전부 몇 개인가"를 먼저 센다

여기서 @Version의 값어치가 드러난다. 낙관적 락은 규약을 안 지킨 경로도 결국 UPDATE는 해야 하므로, 그 UPDATE에 버전 조건이 실려 있는 한 "누가 어디서 바꿨든" 감지된다. 그래서 실무에서는 비관적 락을 쓰는 엔티티에도 @Version을 함께 두는 선택이 흔하다 — 비관적 락은 경합 경로를 직렬화하고, @Version은 규약을 벗어난 경로에 대한 안전망이 된다.

운영 중인 테이블에 @Version 컬럼을 나중에 추가하려고 합니다. 주의할 점은? 함정힌트: 기존 행의 version 값이 무엇이 되는지 생각한다

기존 행의 version을 NULL로 두면 두 가지가 동시에 깨진다.

  • 버전 조건이 아무 행에도 매치되지 않는다. SQL에서 NULL과의 = 비교는 참이 되지 않으므로, WHERE id = ? AND version = NULL은 영향 행 수가 항상 0이다. 즉 아무도 안 건드렸는데도 항상 충돌로 판정된다.
  • 새 엔티티로 오인될 수 있다. Spring Data JPA는 (원시 타입이 아닌) 버전 필드가 null이면 그 엔티티를 "아직 저장된 적 없는 새 엔티티"로 판단한다. save() 호출이 UPDATE가 아니라 INSERT 경로를 타면서 엉뚱한 실패로 이어진다.
컬럼 추가 마이그레이션은 NOT NULL DEFAULT 0 + 기존 행 백필이 세트다

배포 순서도 함께 말하면 좋다 — ① 컬럼을 nullable로 추가하고 기존 행을 0으로 채운 뒤 ② NOT NULL로 조이고 ③ 그 다음에 @Version이 붙은 애플리케이션을 배포한다. 반대로 하면 구버전 인스턴스가 version을 채우지 않고 INSERT하는 창이 생긴다.

낙관적 락 충돌이 났을 때, 자동으로 재시도해야 하나요 아니면 사용자에게 물어야 하나요? 시니어 변별힌트: "재실행해도 사용자의 의도가 그대로인가"를 기준으로 가른다

기준은 하나다 — 최신 값으로 다시 실행했을 때 사용자의 의도가 그대로 유지되는가.

자동 재시도해도 되는 것

재고 1개 차감, 포인트 적립. 사용자의 의도는 "1개 줄여라"라는 상대적 연산이므로, 최신 값 99에 다시 적용해도 의도가 그대로다. 사용자는 충돌이 있었다는 사실조차 알 필요가 없다.

물어봐야 하는 것

공지사항 본문 편집. 의도가 "본문을 이 내용으로 바꿔라"라는 절대적 치환이라, 자동 재시도하면 그 사이 남이 저장한 수정을 조용히 덮어쓴다 — 막으려던 lost update를 재시도로 되살리는 셈이다.

그래서 편집 화면에서는 충돌을 숨기지 말고 노출하는 것이 올바른 동작이다. 좋은 안내는 세 가지를 담는다 — ① 무슨 일이 일어났는지(다른 사용자가 먼저 저장함) ② 무엇이 달라졌는지(가능하면 변경된 필드 표시) ③ 무엇을 하면 되는지(새로고침 후 다시 작성 / 내 내용으로 덮어쓰기 선택).

이 구분은 8절의 세 번째 축("실패를 노출해도 되는가")을 화면 단위로 내려서 판단하는 것과 같다.

재시도 횟수는 몇 번이 적당한가요? 시니어 변별힌트: 숫자를 말하기 전에 그 숫자를 어디서 끌어오는지를 말한다

정해진 정답 숫자는 없고, 두 가지에서 역산한다.

위에서 — 응답 시간 예산
(1회 시도 시간 + 백오프 대기)의 누적 합이 그 API의 응답 SLA를 넘지 않아야 한다. 지수 백오프는 뒤로 갈수록 대기가 급격히 커지므로, 실제로 넣을 수 있는 횟수는 생각보다 적다.
아래에서 — 충돌 확률
충돌이 정말 드물다면 1~2회로도 대부분 성공한다. 횟수를 늘려야만 성공률이 맞춰진다면 그건 "낙관적 락이 틀린 도구"라는 신호다 — 횟수를 올릴 게 아니라 8절로 돌아가 도구를 다시 고른다.

그리고 횟수보다 중요한 것이 세 가지다 — 지터(없으면 실패한 요청들이 같은 시각에 깨어나 또 부딪힌다), 포기 경로(@Recover로 사용자에게 돌려줄 응답), 관측(충돌률과 재시도 횟수를 지표로 남겨야 "드물다"를 숫자로 말할 수 있다).

충돌률 지표가 없으면 8절의 첫 번째 축("확률")을 영원히 감으로 말하게 된다. 재시도를 넣는 김에 카운터를 함께 넣는 것이 정석이다.

그냥 격리 수준을 SERIALIZABLE로 올리면 안 되나요? 함정힌트: "막힌다/안 막힌다"가 아니라 "대가의 범위"로 답한다

막히기는 한다. 문제는 대가의 범위다.

먼저 정리할 것 — 기본 격리 수준에서는 lost update가 막히지 않는다. MySQL(InnoDB)의 REPEATABLE READ에서도, PostgreSQL·Oracle의 READ COMMITTED에서도 1절의 시나리오는 그대로 통과한다. 읽기도 정상, 쓰기도 정상이고, 둘을 이어붙인 애플리케이션의 판단만 낡았기 때문이다.

SERIALIZABLE로 올리면 막히지만, 그것은 "이 한 줄의 문제"를 "데이터소스 전체의 문제"로 키우는 선택이다. 그 커넥션을 쓰는 모든 트랜잭션이 직렬화 비용을 낸다 — 문제와 아무 상관 없는 조회까지 포함해서. 반면 @Version은 그 엔티티에만 적용되고 평시 비용이 0이다.

보호 범위는 필요한 만큼만, 가능한 한 좁게 — 이것이 격리 수준 대신 락을 고르는 이유다
낙관적 락과 비관적 락을 한 시스템에서 같이 쓸 수 있나요? 가산점힌트: 락 모드는 엔티티가 아니라 "조회 경로"에 건다

쓸 수 있고, 실무에서 자주 그렇게 한다. @Version은 엔티티에 붙는 속성이지만, @Lock(LockModeType.PESSIMISTIC_WRITE)는 리포지토리 메서드(= 조회 경로)에 붙는 지시다. 그래서 같은 엔티티라도 경로마다 다른 전략을 쓸 수 있다.

  • 일반 수정 경로(관리자 정보 편집 등) → findById() + @Version의 사후 감지
  • 고경합 차감 경로(주문 시 재고 차감) → findByIdForUpdate()로 사전 차단 + 락 타임아웃

둘을 잇는 지점이 PESSIMISTIC_FORCE_INCREMENT다. 비관적 락으로 보호한 변경도 version을 올려주므로, 그 사이 화면을 열어두고 있던 준영속 편집자(낙관적 진영)에게도 "이미 바뀌었다"가 전달된다.

앞의 "PESSIMISTIC_WRITE를 걸었는데도 갱신이 유실됐다" 질문과 짝지어 말하면 더 좋다 — @Version은 락 규약을 벗어난 경로에 대한 안전망 역할을 하므로, 비관적 락을 쓰는 엔티티에도 함께 두는 것이 방어적이다.

"충돌이 드물다"를 어떻게 숫자로 판단하나요? 필수힌트: 세 개의 숫자를 하나의 지표로 환산한다

필요한 숫자는 셋이다 — 대상 행의 개수, 초당 쓰기 요청 수, 트랜잭션 하나가 그 행을 붙잡는 시간. 이 셋을 "행 하나당 초당 몇 건이 오는가"로 환산하는 것이 핵심이다.

회원 10만 명의 프로필 수정

요청이 10만 개 행에 흩어진다. 같은 행이 동시에 겹칠 확률이 사실상 0 → 낙관적 락. 평시 비용 0으로 안전망만 얻는다.

한정판 상품 1개 행에 초당 500건

전부 같은 행 하나로 몰린다. 충돌은 예외가 아니라 기본값 → 낙관적 락은 재시도 폭풍, 비관적 락은 커넥션 점유. 7절의 임계 구간 축을 먼저 검토한다.

그리고 추정으로 시작하되 지표로 끝낸다. 충돌 예외 발생 건수와 재시도 횟수를 카운터로 남겨두면, 다음 논의에서는 "드문 것 같습니다"가 아니라 "지난주 충돌률이 이 정도였습니다"로 말할 수 있다. 같은 API인데 이벤트 기간에만 도구가 틀려지는 경우도 이 지표로만 잡힌다.

한 줄 요약
락 이야기의 출발점은 lost update — 두 트랜잭션이 같은 행을 각자 읽고 각자 계산해 각자 쓰면 갱신 하나가 조용히 증발한다 — 이고, 그것을 막는 길은 사전 차단(비관적)과 사후 감지(낙관적) 둘뿐이다. 낙관적 락은 락이 아니다 — 별도 SELECT 없이 UPDATE ... SET ..., version = ? WHERE id = ? AND version = ? 한 문장을 날리고 영향 행 수가 0인지로 충돌을 사후 감지할 뿐이며, 그래서 평시 비용이 0인 대신 충돌 시 로직 전체를 새 트랜잭션에서 재시도해야 한다(같은 트랜잭션에서 재시도하면 1차 캐시와 롤백 표시 때문에 영원히 실패한다). 반면 비관적 락은 진짜로 잠그는 대신 락 대기 시간 내내 DB 커넥션을 붙잡아 가상 스레드로도 못 막는 풀 고갈을 부른다 — OSIV의 "놀고 있는 커넥션" 문제와 같은 축이다. 선택 기준은 충돌 확률 × 재시도 비용 × 실패를 노출해도 되는가이고, 둘 다 답이 아닌 고경합 구간에서는 "기다림을 없앨 수 있나"가 아니라 "기다리는 구간을 짧게 만들 수 있나"를 물어야 한다. 그리고 이 모든 판단은 CountDownLatch로 동시 출발시킨 테스트로 재현해 고정하기 전까지는 주장일 뿐이다.
