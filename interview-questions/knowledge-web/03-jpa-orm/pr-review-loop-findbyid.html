루프 건별 findById PR 리뷰 — "지금은 빠릅니다"의 반박은 성능이 아니라 계약이다

📖 약 36분 🧩 8개 섹션 0/8 섹션 이해
🎯 핵심 관전 포인트

이 문항은 N+1을 아는지 묻는 게 아니다. 잘 돌아가고 테스트도 통과하는 코드를 보고 "데이터가 늘면 터진다"를 배포 전에 말할 수 있는가, 그리고 그것을 동료가 납득할 문장으로 조립할 수 있는가를 본다. 그래서 세 지점에서 갈린다. ① 반박의 축 — "느려집니다"로 들어가면 "지금 빠른데요"에 진다. 정확한 지적은 성능이 아니라 계약이다: 이 메서드는 쿼리 수를 호출자가 정하는 API가 됐고, 비용이 호출자에 따라 결정되는 구조 자체가 결함이다. 그래서 6개월 뒤 정산 배치가 재사용하는 순간 터진다. 성능 논쟁을 설계 논쟁으로 옮겨야 설득이 된다. ② 코멘트의 형식 — 좋은 리뷰 코멘트는 네 조각이다. 무엇이 문제인지 / 언제 터지는지(조건) / 대안 코드 / blocking인지 아닌지. ②가 없으면 "지금 문제 없는데요"를 막을 수 없고, ④가 없으면 리뷰가 마비된다. ③ 미룬 결정의 처리 — 동료의 "오버엔지니어링" 반박은 타당할 수 있다. 그러면 IN 절은 blocking으로 요구하고 청킹은 미루되, 미룬 결정을 코드로 못 박는다: if (ids.size() > MAX) throw ... 한 줄과 그것을 검증하는 테스트. 배치 개발자는 주석을 안 읽어도 첫 실행에서 즉시 실패하고, 그 시점에 청킹이냐 배치 전용 경로냐를 결정한다. TODO는 소망이고 상한 검증은 장치다. 그리고 한 층 더 — 배치가 정말 10만 건이면 청킹도 답이 아니다. id 목록을 받는 API 자체가 잘못이고 커서·범위 조회로 가야 한다.

면접 질문

"동료의 PR: List<Long> ids를 루프 돌며 건별 findById로 조회합니다. 지금 데이터 규모에서는 빠릅니다. 어떤 리뷰 코멘트를 남기나요?"

출제 의도rationale은 이 문항을 "상황 인지 능력의 검사 형식" 으로 규정한다 — "N+1 개념을 아는 것과, 지금 잘 돌아가는 코드에서 '데이터가 늘면 터진다'를 배포 전에 말할 수 있는 것은 다르다." 그리고 형식이 코멘트인 이유를 이렇게 덧붙인다 — "리뷰 코멘트라는 형식은 지적의 정확성뿐 아니라 대안 제시(IN 절 일괄 조회)와 전달 방식까지 함께 드러낸다." 즉 이 문항의 채점표에는 지식 항목이 하나뿐이고(IN 절 일괄 조회), 나머지가 전부 판단과 서술이다. N+1의 메커니즘·탐지 도구·해결책 선택 기준은 n-plus-one-detection-and-fixes.md에 있으므로 이 문서는 반복하지 않는다. 이 문서의 주제는 리뷰 코멘트라는 산출물과 재발 방지 장치다.

면접에 제시된 코드: @Transactional(readOnly = true) 메서드가 orderIds를 for 루프로 돌며 orderRepository.findById(id).orElseThrow(OrderNotFoundException::new) 후 OrderSummary.from(order)를 리스트에 담아 반환한다. 관리자 화면에서 체크박스로 선택한 주문 몇 건만 조회하는 용도이고, 테스트도 통과하며 실제로 빠르다.

1

"지금 규모에선 빠릅니다"의 정확한 반박 — 성능이 아니라 계약이다

▾

1-1. 성능으로 들어가면 상대의 홈그라운드에서 싸우는 것이다

가장 흔한 리뷰 코멘트는 이렇다.

💡

"루프 안에서 findById를 호출하면 쿼리가 많이 나가서 느려집니다. IN 절로 바꾸는 게 좋습니다."

지적 자체는 맞다. 그런데 이 문장은 동료를 설득하지 못한다. 동료에게는 반박 카드가 이미 있기 때문이다 — "관리자가 체크박스로 고르는 거라 많아도 20~30건이고, 실측해봤는데 30ms입니다." 여기서 대화가 끝난다. 리뷰어가 "그래도 느려집니다"를 반복하면 근거 없는 취향 싸움이 되고, 리뷰어가 물러서면 코드가 그대로 나간다.

문제는 비교의 기준을 상대가 정하게 뒀다는 것이다. "느리다/빠르다"는 지금 데이터로 측정되고, 지금 데이터에서는 동료가 옳다. 성능 축에서는 리뷰어가 이길 방법이 없다.

1-2. 결함의 정확한 이름 — "비용이 호출자에 의해 결정되는 API"

축을 바꿔야 한다. 이 메서드의 문제는 30ms가 아니라 시그니처가 약속하는 내용이다.

java
List<OrderSummary> getOrderSummaries(List<Long> orderIds)

이 시그니처를 보는 호출자는 "id 목록을 주면 요약을 돌려주는 조회" 라고 읽는다. 개수 제한에 대한 언급이 없으므로 개수는 호출자가 정한다고 읽는 것이 자연스럽다. 그런데 구현은 입력 1건당 SELECT 1개를 보낸다. 그러면 이 메서드의 실제 성질은 이렇게 정리된다.

💡

이 메서드가 DB에 가하는 부하는 이 메서드가 아니라 호출자가 결정한다.

여기서 결정적인 전환이 일어난다. "지금 빠르다"는 코드의 성질이 아니라 현재 호출자의 성질이다. 코드는 아무 보장도 하지 않는다. 관리자 화면이 20건을 넣기로 선택했을 뿐이고, 그 선택은 코드 어디에도 적혀 있지 않다.

그래서 리뷰 코멘트의 핵심 문장은 "느려집니다"가 아니라 이것이 된다.

💡

"이 메서드는 쿼리 수를 호출자가 정하는 구조입니다. 지금 빠른 건 화면이 20건만 넣기 때문이고, 그 제약은 코드에 없습니다."

이 문장에는 동료가 반박할 카드가 없다. 사실 진술이고, 실측으로 부정할 수 없다. 그리고 이 문장은 자동으로 다음 질문을 낳는다 — "그럼 다른 호출자가 생기면?"

1-3. 그래서 6개월 뒤 배치가 터진다 — 조건을 말하면 반박이 멈춘다

좋은 리뷰 코멘트에는 "언제 터지는지" 가 반드시 들어간다. 이게 빠지면 "지금 문제 없는데요"를 막을 수 없다. 이 코드가 터지는 조건은 시간이 아니라 호출자의 변경이다.

  • 정산 배치가 "미정산 주문 id를 모아 요약을 뽑는" 일을 하게 되고, 이미 있는 getOrderSummaries를 찾아 쓴다. orderIds가 10만 건이 된다.
  • CS 도구가 "특정 기간 주문 전체"를 조회하는 화면을 만들면서 같은 메서드를 쓴다.
  • 화면 기획이 "전체 선택" 버튼을 추가한다. 코드는 한 줄도 안 바뀌었는데 입력이 20건에서 5,000건이 된다.

셋 다 PR 승인 시점에는 존재하지 않는 변경이고, 셋 다 이 메서드의 구현을 열어보지 않는다. 열어볼 이유가 없다 — 잘 작동하는 메서드이기 때문이다.

이 층까지 말하면 리뷰가 성능 지적에서 설계 지적으로 올라간다. 그리고 실무에서 훨씬 중요한 효과가 하나 더 있다 — 동료가 방어할 필요가 없어진다. "네 코드가 느리다"는 사람에 대한 지적으로 들리지만, "이 시그니처의 계약이 구현보다 넓다"는 코드에 대한 관찰이다. 리뷰가 반박전이 되지 않는 이유가 여기에 있다.

▾

면접에서 "실제로 쓸 문장 그대로"를 요구했을 때 사실 진술("쿼리가 많이 나간다, IN을 써라")로 답하면 감점된다. 아는 것과 상대가 납득할 형태로 조립하는 것은 다른 능력이고, 이 문항은 후자를 본다.

2-1. 좋은 리뷰 코멘트의 4조각

조각없으면 생기는 일
① 무엇이 문제인가(대개 있다)
② 언제 터지는가 — 조건"지금 문제 없는데요"에서 대화가 끝난다
③ 대안 코드상대가 대안을 찾아야 해서 반영률이 떨어진다
④ blocking인가 아닌가상대가 우선순위를 모르고, 사소한 지적까지 머지를 막는다

②와 ④가 이 문항의 채점 지점이다. ②는 §1-3의 내용이고, ④는 리뷰어의 판단력이 드러나는 자리다. 지적을 전부 blocking으로 만드는 리뷰어는 팀의 속도를 죽이고, 전부 non-blocking으로 만드는 리뷰어는 아무것도 바꾸지 못한다. 무엇을 지금 요구하고 무엇을 미룰지 선을 긋는 것이 리뷰의 실력이다.

이 코드에서 선은 이렇게 그어진다.

  • findAllById 전환 = blocking. 변경이 한 줄이고 리스크가 없다. 지금 넣는 비용이 사실상 0인데, 나중에 넣으려면 호출자가 늘어난 뒤라 더 비싸다.
  • 청킹 구현 = non-blocking. 입력이 20~30건인 지금은 실제로 과잉이다(§6).
  • 입력 상한 검증 = 그 사이. 청킹을 미룰 거라면 미룬 위험을 봉쇄하는 한 줄은 같이 들어가는 것이 맞다(§4). 팀 문화에 따라 blocking으로 요구해도 무리가 없다.

2-2. 예문 A — blocking

text

다만 시그니처가 List<Long> 이라 개수를 정하는 주체가 호출자입니다. 즉 지금
빠른 건 이 코드의 성질이 아니라 현재 호출자의 성질이고, 그 제약은 코드
어디에도 적혀 있지 않습니다. 정산·CS 쪽에서 이 메서드를 재사용하거나 화면에
"전체 선택"이 추가되면, 이 코드를 한 줄도 안 고쳤는데 쿼리 수가 그 호출자의
입력 크기로 결정됩니다.

■ 대안

orElseThrow 가 하던 존재 검증은 "요청한 id 수 vs 결과 수" 비교로 옮기면 되고,
덤으로 없는 id 를 한 번에 알려줄 수 있어서 관리자가 20건 중 3건이 없을 때

아래 남긴 입력 상한 코멘트는 non-blocking 입니다.

2-3. 예문 B — non-blocking

text
[non-blocking / 다음 PR도 괜찮습니다] orderIds 개수에 상한을 걸어두면 어떨까요?

■ 무엇
findAllById 로 바꾸면 쿼리는 1개가 되지만, in (?, ?, …) 의 파라미터 개수는

관리자 화면 경로에서는 안 터집니다. 터지는 건 큰 입력으로 재사용될 때인데,
그때는 (a) DB 쪽 파라미터 개수·패킷 한계에 걸려 실패하거나 (b) 통과해도
엔티티가 수만 개 영속성 컨텍스트에 쌓여 힙을 밀어냅니다. readOnly = true 는

있으면, 나중에 큰 입력으로 호출하는 사람이 주석을 읽지 않아도 첫 실행에서 바로
실패하고 그 자리에서 "청킹이냐 배치 전용 경로냐"를 결정하게 됩니다.
결정을 미루는 것과 미룬 결정을 아무도 모르게 두는 것은 다른 문제라고 봅니다.

■ blocking 여부
non-blocking. 다음 PR로 빼도 좋습니다. 다만 MAX_IDS 값은 화면 최대 선택 수를

2-4. 짧은 버전 — 실무 리뷰는 이 길이가 현실적이다

위 두 예문은 구조를 보이기 위한 완전체다. 실제 리뷰에서는 아래 정도로 압축하고, 반박이 오면 §1-3의 조건을 펼친다. 면접에서도 이 길이로 말하는 편이 낫다.

text

나갑니다. 화면에선 20건이라 빠른 게 맞지만, 이 메서드는 쿼리 수를 호출자가 정하는
구조라 배치나 다른 화면이 재사용하는 순간 그쪽 입력 크기로 결정됩니다.
존재 검증은 결과 수 비교로 대체 가능합니다. (입력 상한은 아래 별도 코멘트에
non-blocking 으로 남겼습니다.)

전달 방식에서 지킨 것 세 가지를 의식적으로 말할 수 있으면 좋다. ① 주어를 사람이 아니라 코드로 둔다("이 메서드는 …" / "네가 …"가 아니다). ② 동료의 관찰을 먼저 인정한다("지금 빠른 게 맞습니다") — 인정하고 나서 축을 옮기는 것이 반박을 없앤다. ③ blocking 라벨을 문장 맨 앞에 둔다. 상대는 코멘트를 다 읽기 전에 우선순위를 알아야 한다.

3

단계별 before/after — 각 단계가 막아주는 사고

▾

네 단계다. ①→② 는 성능 수정, ②→③ 은 계약 명시, ③→④ 는 요구사항 재해석이고, 성질이 서로 다르다.

3-1. ① 현재 — 루프 건별 findById

java
@Transactional(readOnly = true)
public List<OrderSummary> getOrderSummaries(List<Long> orderIds) {
    List<OrderSummary> result = new ArrayList<>();
    for (Long id : orderIds) {
        Order order = orderRepository.findById(id)
                .orElseThrow(OrderNotFoundException::new);   // 존재 검증이 루프 안에 있다
        result.add(OrderSummary.from(order));
    }
    return result;
}

나가는 SQL — 입력 20건이면 20개, 10만 건이면 10만 개다.

sql
select o.* from orders o where o.id = ?    -- ×  orderIds.size()

막아주는 사고: 없다. 이 단계의 유일한 장점은 존재 검증이 자연스럽다는 것인데, 그것은 ②에서 더 나은 형태로 대체된다. (findById의 존재 검증 성질과 getReferenceById와의 차이는 find-by-id-vs-get-reference-by-id.md 참고.)

3-2. ② findAllById + 결과 수 비교로 존재 검증

java
@Transactional(readOnly = true)
public List<OrderSummary> getOrderSummaries(List<Long> orderIds) {
    if (orderIds.isEmpty()) {
        return List.of();                       // 빈 입력에 쿼리를 보내지 않는다
    }

    List<Order> orders = orderRepository.findAllById(orderIds);   // SELECT 1개

    Set<Long> requested = new LinkedHashSet<>(orderIds);          // 중복 입력 정규화
    if (orders.size() != requested.size()) {
        Set<Long> found = orders.stream().map(Order::getId).collect(toSet());
        requested.removeAll(found);
        throw new OrderNotFoundException(requested);              // 없는 id 전부를 담아서
    }

    Map<Long, Order> byId = orders.stream()
            .collect(toMap(Order::getId, Function.identity()));
    return orderIds.stream()                                      // 입력 순서 복원
            .map(id -> OrderSummary.from(byId.get(id)))
            .toList();
}

나가는 SQL — 입력 개수와 무관하게 1개다.

sql
select o.* from orders o where o.id in (?, ?, ?, …)

세 가지 디테일이 들어갔다.

  • 중복 입력 정규화: 입력에 같은 id가 두 번 있으면 결과는 1건이므로, 단순히 orders.size() != orderIds.size()로 비교하면 존재하는데 없다고 예외를 던진다. Set으로 정규화한 개수와 비교해야 한다. 개수 비교로 검증을 옮길 때 가장 흔한 버그다.
  • 없는 id 전부 보고: 루프 버전은 첫 번째로 없는 id에서 중단한다. 관리자가 20건 중 3건이 이미 삭제된 상태라면 세 번 재시도해야 한다. 개수 비교 방식은 없는 id 집합을 한 번에 만들 수 있으므로, 이건 성능 개선의 부수효과가 아니라 UX 개선이다. 리뷰 코멘트에 넣기 좋은 카드다.
  • 입력 순서 복원: findAllById가 입력 순서를 보장하지 않는다. 화면이 선택 순서나 특정 정렬을 기대한다면 Map으로 되돌리거나 order by를 명시해야 한다. 루프 버전에서는 순서가 공짜였기 때문에 놓치기 쉬운 회귀다.

막아주는 사고: 쿼리 수가 입력 개수에서 분리된다. 호출자가 몇 건을 넣든 SELECT는 1개다. 배치가 10만 건을 넣어도 쿼리 폭주는 일어나지 않는다.

막지 못하는 사고: IN 파라미터가 10만 개인 SQL 자체의 문제(§5)와, 엔티티 10만 개가 힙에 올라오는 문제. 그리고 하나 더 — OrderSummary.from(order)이 LAZY 연관을 만지면 여기서 N+1이 새로 태어난다. order.getMember().getName()이 있으면 1 + N이 된다. 루프를 없앴다고 쿼리 1개가 보장되는 게 아니라서, 이 단계는 §4-4의 쿼리 수 테스트와 세트로만 신뢰할 수 있다.

3-3. ③ 입력 상한 검증 — 계약을 코드에 적는다

public class OrderSummaryQuery {

    static final int MAX_IDS = 200;   // 관리자 화면 최대 선택 수(100)의 2배

            throw new TooManyIdsException(orderIds.size(), MAX_IDS,
                    "대량 조회는 OrderBatchReader 의 커서 기반 경로를 사용하세요");
        }
        // … ② 와 동일
    }
}

나가는 SQL — 상한 초과 시 아무것도 나가지 않는다. DB에 도달하기 전에 끝난다.

막아주는 사고: 6개월 뒤 배치 개발자가 10만 건을 넣는 사고. 그가 주석을 읽지 않아도, 리뷰 스레드를 못 봐도, 첫 실행에서 즉시 실패한다. 그리고 예외 메시지가 다음 행동을 지시하므로 그 자리에서 결정이 이뤄진다.

검증을 어디에 두는가가 이 단계의 핵심이다. 흔한 오답은 컨트롤러다.

✕ BEFORE컨트롤러에만 검증. 외부 요청은 막지만 내부 호출자는 그냥 통과한다.
@PostMapping("/admin/orders/summaries")
public List<OrderSummary> summaries(@Valid @RequestBody SummaryRequest request) { … }

record SummaryRequest(@Size(max = 200) List<Long> orderIds) {}
✓ AFTER서비스에도 둔다. 6개월 뒤의 배치는 컨트롤러를 지나가지 않는다.
//         Bean Validation 은 HTTP 경계의 방어, 서비스 검증은 메서드 계약의 방어다.
if (orderIds.size() > MAX_IDS) throw new TooManyIdsException(…);

이 코드가 터지는 경로는 HTTP가 아니라 자바 메서드 호출이다. 컨트롤러 검증만 넣으면 정작 막아야 할 호출자를 못 막는다. 둘은 대체 관계가 아니라 층이 다른 방어다 — 컨트롤러 검증은 사용자에게 400을 빠르게 돌려주고, 서비스 검증은 모든 호출자에게 계약을 강제한다.

3-4. ④ 배치 요구가 실제로 오면 — 커서·범위 기반으로 분리한다

여기가 대부분의 답변이 도달하지 못하는 층이다. 배치가 10만 건을 넣는다는 요구가 실제로 오면, 자연스러운 반응은 "그럼 1,000건씩 청킹하자"다. 그런데 청킹은 잘못된 API를 연장하는 처방이다.

문제를 다시 읽어야 한다. 배치가 하려는 일은 "이 10만 개 id를 조회"가 아니라 "미정산 주문을 전부 처리"다. id 목록을 먼저 메모리에 모으는 단계 자체가 불필요하고, 그 단계가 있는 한 10만 개 Long을 담은 리스트와 그것을 만들기 위한 선행 조회가 계속 존재한다.

✕ BEFORE청킹. id 10만 개는 여전히 메모리에 있고, API 오용도 그대로 남는다.
for (List<Long> chunk : Lists.partition(allIds, 1_000)) {
    orderSummaryQuery.getOrderSummaries(chunk);
}
✓ AFTER배치 전용 경로. id 목록을 받지 않는다.
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("select o from Order o where o.id > :lastId and o.settledAt is null order by o.id")
    List<Order> findUnsettledAfter(@Param("lastId") Long lastId, Pageable pageable);
}

// 커서를 들고 전진한다
Long lastId = 0L;
while (true) {
    List<Order> page = orderRepository.findUnsettledAfter(lastId, PageRequest.of(0, 1_000));
    if (page.isEmpty()) break;

    page.forEach(this::settle);

    lastId = page.get(page.size() - 1).getId();
    em.flush();
    em.clear();      // ← 이 줄이 없으면 청킹해도 힙은 계속 자란다
}
sql
select o.* from orders o
 where o.id > ? and o.settled_at is null
 order by o.id
 limit 1000

막아주는 사고 네 개. ① IN 파라미터가 아예 없으므로 벤더 한계와 실행계획 캐시 문제가 사라진다(§5-1, §5-2). ② em.clear()로 영속성 컨텍스트가 청크 단위로 비워져 힙이 일정하게 유지된다. ③ offset 페이징의 뒷페이지 성능 저하가 없다 — id > ?는 인덱스를 타고 바로 시작 지점으로 간다. ④ 관리자 화면용 API를 배치가 재사용하는 구조 자체가 없어진다.

그리고 청킹의 효능 범위를 정확히 말할 수 있어야 한다. 청킹은 §5의 실패 모드 중 벤더 한계와 실행계획 캐시 오염만 해결하고, 엔티티 적재로 인한 힙 압박은 해결하지 못한다. 같은 트랜잭션·같은 영속성 컨텍스트에서 청크를 반복하면 조회한 엔티티가 계속 누적되기 때문이다. em.clear() 없는 청킹은 절반만 고친 처방이다. "청킹 = 정답"으로 외우면 이 구분을 못 하고, 그래서 10만 건에서 여전히 OOM이 난다.

4

TODO 주석 vs 코드로 강제 — 미룬 결정도 코드로 못 박는다

▾

§2-1에서 청킹을 non-blocking으로 미루기로 했다. 그러면 질문이 남는다. 6개월 뒤의 사고를 무엇이 막아주는가? "나중에 하자"를 리뷰 스레드에 적는 것 말고, 사람의 기억과 선의에 의존하지 않는 방법이 있는가.

가장 흔한 답이 TODO 주석이다. 그리고 그건 답이 아니다.

4-1. TODO가 실패하는 구체적 경로

java
// TODO: orderIds 가 많아지면 청킹 필요 (2026-08 리뷰 논의)
@Transactional(readOnly = true)
public List<OrderSummary> getOrderSummaries(List<Long> orderIds) { … }

6개월 뒤 배치 개발자의 실제 행동을 따라가 보면 왜 실패하는지 보인다.

  1. 그는 IDE 자동완성으로 시그니처만 본다. List<Long>을 받는 조회 메서드다.
  2. 구현을 열지 않는다. 열 이유가 없다 — 이미 프로덕션에서 잘 돌고 있는 메서드이고, 그가 하려는 일은 "이걸 고치기"가 아니라 "이걸 쓰기"다.
  3. 열어도 TODO는 스크롤 위쪽의 회색 주석이다. IDE가 흐리게 렌더링하고, 대부분의 저장소에는 이미 TODO가 수백 개 있어서 신호가 아니라 배경이다.
  4. 리뷰 스레드는 머지된 PR 안에 묻힌다. 검색으로도 잘 안 나온다.

그리고 TODO가 읽혔더라도 실패한다. 작동 시점이 틀렸기 때문이다. 주석은 사람이 코드를 읽는 시점에만 작동하는데, 위험이 실제로 발생하는 시점은 런타임에 입력이 10만 건이 되는 순간이다. 입력 크기는 컴파일 타임에 알 수 없다. 주석은 원리적으로 이 시점에 개입할 수 없다.

4-2. 판단 기준 — 소망인가 장치인가

남기는 방식언제 작동하나무시할 수 있나
TODO 주석 / 리뷰 스레드 / 위키사람이 읽을 때만예 (기본값이 무시다)
입력 상한 검증위험한 호출이 실행될 때아니오
쿼리 수 단정 테스트CI 빌드마다아니오

기준은 한 줄로 정리된다. "이 장치는 아무도 아무것도 기억하지 않아도 작동하는가?" 답이 "아니오"면 그것은 장치가 아니라 소망이다.

💡

TODO는 소망이고, 상한 검증은 장치다.

4-3. 미룬 결정을 코드로 남기는 3단 공식

TODO를 버리는 게 아니라 실행 가능한 형태로 옮기는 것이다. 형식은 늘 같다.

  1. 지금 안전한 범위를 상수로 선언한다 — 범위가 코드에 적히는 순간, 암묵적 가정이 명시적 계약이 된다. 상수 이름과 옆의 한 줄 주석이 근거를 남긴다.
  2. 범위를 벗어나면 즉시 실패시킨다 — 조용히 느려지는 것보다 시끄럽게 실패하는 것이 낫다. 조용한 열화는 발견이 늦고, 늦은 발견은 곧 장애다.
  3. 실패 메시지에 다음 결정지점을 적는다 — 여기가 TODO의 내용이 들어갈 자리다. 주석은 안 읽히지만 스택트레이스는 반드시 읽힌다.
✕ BEFORE소망
// TODO: 나중에 청킹
✓ AFTER장치. TODO 의 내용이 예외 메시지로 이사했다.
static final int MAX_IDS = 200;   // 관리자 화면 최대 선택 수(100)의 2배. 근거: 2026-08 리뷰

if (orderIds.size() > MAX_IDS) {
    throw new TooManyIdsException(
            "orderIds 가 %d 건입니다(상한 %d). 이 메서드는 화면 선택 조회용이라 %d 건까지만 보장합니다. "
          + "대량 조회는 커서 기반 배치 경로(OrderBatchReader)를 쓰거나, "
          + "이 경로를 확장해야 하면 청킹 도입을 먼저 논의해주세요."
                    .formatted(orderIds.size(), MAX_IDS, MAX_IDS));
}

배치 개발자가 만나는 것은 회색 주석이 아니라 자기 코드가 첫 실행에서 던진 예외와 그 메시지다. 그 시점에 그는 두 선택지를 알고 있고, 결정할 사람이 그 자리에 있다. 이것이 리뷰에서 미룬 결정을 미룬 채로 안전하게 만드는 방법이다.

그리고 상한 검증이 못 하는 것도 말해야 한다. ① MAX_IDS = 200이 적절한 값인지는 알려주지 않는다 — 값의 근거는 화면 계약에서 와야 하고, 그래서 §4-5의 테스트로 화면 상한과 묶는다. ② 상한 아래에서도 IN 200개가 무거울 수 있다. 상한은 파국을 막는 장치이고 최적화가 아니다. ③ 이 메서드에만 걸린다. 같은 패턴이 다른 메서드에 또 생기는 것은 못 막는다(§4-6).

4-4. 쿼리 수를 테스트로 고정해 CI에 넘긴다

상한 검증이 런타임 장치라면, 쿼리 수 단정은 빌드 타임 장치다. 둘은 막는 사고가 다르다 — 상한은 큰 입력을 막고, 쿼리 수 단정은 누가 다시 루프로 되돌리거나 OrderSummary.from에 LAZY 접근을 추가하는 것을 막는다.

java
@DataJpaTest
@Import(OrderSummaryQuery.class)
class OrderSummaryQueryTest {

    @Autowired OrderSummaryQuery query;
    @Autowired OrderRepository orderRepository;
    @Autowired MemberRepository memberRepository;
    @Autowired EntityManager em;

    List<Long> ids = new ArrayList<>();

    @BeforeEach
    void setUp() {
        for (int i = 0; i < 30; i++) {
            Member member = memberRepository.save(new Member("회원" + i));  // ① 카디널리티
            Order order = orderRepository.save(new Order(member, "상품" + i));
            ids.add(order.getId());
        }
        em.flush();
        em.clear();                       // ② 픽스처 컨텍스트를 측정에서 분리
        SQLStatementCountValidator.reset();
    }

    @Test
    void 주문_30건_요약_조회는_SELECT_1개로_끝난다() {
        query.getOrderSummaries(ids);

        SQLStatementCountValidator.assertSelectCount(1);   // 루프로 되돌리면 30, LAZY 접근이 생기면 31
    }
}

①과 ②가 이 테스트의 생사를 가른다. 주문 30건을 전부 같은 회원에 매달면 OrderSummary.from이 회원을 만져도 추가 SELECT가 1개뿐이라 1 + 1로 통과한다. em.clear()가 없으면 방금 저장한 회원들이 1차 캐시에 살아 있어 추가 SELECT가 0개가 되고, 역시 통과한다. 픽스처를 건수가 아니라 카디널리티로 설계해야 하는 이유는 n-plus-one-detection-and-fixes.md §1에 자세히 있다. 장치가 있는데 아무것도 못 잡는 상태가 가장 위험하다.

상수 1에 묶지 않는 형태가 더 튼튼하다. 이 메서드의 계약은 "쿼리 1개"가 아니라 "쿼리 수가 입력 개수에 비례하지 않는다" 이므로, 그 성질을 직접 단정한다.

java
@Test
void 입력_개수를_3배로_늘려도_쿼리_수는_그대로다() {
    long q10 = countQueries(() -> query.getOrderSummaries(ids.subList(0, 10)));
    long q30 = countQueries(() -> query.getOrderSummaries(ids));

    assertThat(q30)
            .as("입력이 3배인데 쿼리가 늘었다 = 쿼리 수가 호출자에 의해 결정된다")
            .isEqualTo(q10);
}

private long countQueries(Runnable action) {
    Statistics stats = em.unwrap(Session.class).getSessionFactory().getStatistics();
    em.clear();                                        // 측정마다 캐시 초기화
    long before = stats.getPrepareStatementCount();
    action.run();
    return stats.getPrepareStatementCount() - before;
}

이 형태는 리팩터링으로 쿼리가 1개에서 2개가 되어도 깨지지 않고, 입력 비례가 되살아나면 반드시 깨진다. 고정하려는 성질만 정확히 고정한다. 테스트 이름 자체가 §1-2의 결함 이름과 같다는 점도 의미가 있다 — 테스트가 계약의 문서가 된다.

확인 범위: SQLStatementCountValidator는 Vlad Mihalcea의 db-util 라이브러리가 제공하고 datasource-proxy로 감싼 DataSource를 요구한다. Statistics 쪽은 hibernate.generate_statistics=true가 켜져 있어야 값이 잡힌다. 두 API의 정확한 좌표는 프로젝트에서 확인할 것.

4-5. 상한을 검증하는 테스트 — 값의 근거까지 고정한다

java
@Test
void 상한을_넘는_입력은_DB_에_가기_전에_거부된다() {
    List<Long> tooMany = LongStream.rangeClosed(1, MAX_IDS + 1).boxed().toList();
    SQLStatementCountValidator.reset();

    assertThatThrownBy(() -> query.getOrderSummaries(tooMany))
            .isInstanceOf(TooManyIdsException.class)
            .hasMessageContaining("커서");           // 다음 결정지점이 메시지에 있는지까지 검증

    SQLStatementCountValidator.assertSelectCount(0);  // 쿼리가 단 하나도 안 나갔다
}

@Test
void 상한은_화면_최대_선택_수보다_커야_한다() {
    assertThat(MAX_IDS)
            .as("화면 최대 선택 수를 올렸다면 이 상한도 함께 올려야 한다")
            .isGreaterThanOrEqualTo(AdminOrderPage.MAX_SELECTABLE);
}

두 번째 테스트가 실무에서 진짜 값을 한다. 상한은 넣어놓고 잊히면 정상 사용을 막는 장애물이 된다. 화면 기획이 최대 선택 수를 100에서 500으로 올리는 날, 운영에서 TooManyIdsException이 터지는 대신 CI가 먼저 빨간불이 된다. 그리고 hasMessageContaining("커서")는 사소해 보이지만, 예외 메시지가 문서 역할을 한다는 설계 의도를 테스트가 지켜주는 장치다. 메시지에서 안내를 지우면 테스트가 깨진다.

4-6. 한 층 더 — 같은 패턴의 재발을 막는 층

여기까지는 이 메서드의 장치다. 같은 패턴이 다른 메서드에 또 생기는 것은 못 막는다. 현실적인 순서는 이렇다.

  1. 개발·스테이징에 요청 단위 쿼리 카운터를 깐다. 같은 SQL이 수십 번 반복되는 요청을 로그로 드러내므로, 어느 메서드에 이 패턴이 있는지 현황이 나온다. 코드를 한 줄도 안 고치고 작업 목록을 얻는 게 이 장치의 값이다(구현은 n-plus-one-detection-and-fixes.md §3-3).
  2. 컬렉션을 받는 public 조회 메서드를 ArchUnit으로 열거해 리스트로 뽑는다. "상한 검증이 있는지"를 정적으로 판정하는 건 어렵지만, 후보 목록을 자동으로 유지하는 것만으로도 리뷰 대상이 명확해진다. 룰을 실패로 만들기보다 목록을 출력하는 용도로 시작하는 편이 현실적이다.
  3. 컨벤션 한 줄을 PR 템플릿에 넣는다 — "컬렉션을 파라미터로 받는 조회 메서드는 입력 상한을 명시한다." 사람이 읽어야 작동하니 §4-2 기준으로는 소망이지만, 1·2번과 함께 있으면 왜 그 룰이 있는지를 설명하는 역할을 한다.

관통하는 원칙은 §4-2와 같다 — 결과를 고정하고(쿼리 수 테스트), 위험한 입력을 거부하고(상한), 신규 유입을 드러낸다(카운터·목록). 세 층 다 사람의 기억을 요구하지 않는다.

5

10만 건 IN의 실패 모드 — "무겁다"를 다섯 개의 이름으로 쪼갠다

▾

findAllById로 고친 뒤 배치가 10만 건을 넣으면 in (?, ?, … ×100000)이 나간다. "너무 무겁다"에서 멈추면 어떤 처방이 무엇을 고치는지 판단할 수 없다. 실패는 다섯 갈래이고, 처방의 효능 범위가 서로 다르다.

5-1. 벤더의 하드 리밋 — 그나마 나은 실패

  • Oracle: IN 리스트의 표현식 개수가 1,000개를 넘으면 ORA-01795로 에러다. 1,000개 단위로 or로 쪼개는 우회가 관용구로 쓰인다.
  • PostgreSQL: 확장 프로토콜의 바인드 파라미터 개수 상한이 65,535개다. 10만 개는 이 벽에 그대로 부딪힌다.
  • MySQL: 개수 자체보다 max_allowed_packet(전송 패킷 크기) 에 먼저 걸린다. SQL 문자열이 그만큼 길어지기 때문이다.

이 셋은 즉시 실패하므로 오히려 다행이다. 배포하면 첫 배치 실행에서 터지고, 스택트레이스에 원인이 적혀 있다. 진짜 위험한 것은 아래 넷이다 — 조용히 나빠진다.

5-2. 실행계획 캐시 오염 — 가장 은밀한 실패

이게 가산점 포인트다. IN 절의 파라미터 개수가 SQL 문자열에 그대로 반영된다.

sql
where id in (?, ?, ?)                -- 3건 요청 → SQL 문자열 A
where id in (?, ?, ?, ?)             -- 4건 요청 → SQL 문자열 B (다른 쿼리로 취급된다)
where id in (?, ?, ?, ?, ?)          -- 5건 요청 → SQL 문자열 C

DB와 드라이버·ORM 계층은 SQL 문자열을 키로 파싱 결과와 실행계획을 캐시한다. 요청마다 개수가 달라지면 캐시 엔트리가 개수만큼 생겨서, ① 캐시가 다른 쿼리를 밀어내 엔트리 재사용률이 떨어지고 ② 매번 새로 파싱(하드 파싱)하며 ③ 캐시 자체를 지키는 내부 락 경합이 늘어난다. 개별 쿼리는 여전히 빠르므로 슬로우 쿼리 로그에는 안 잡힌다. 증상은 특정 쿼리가 아니라 DB 전반의 CPU 상승으로 나타나서 원인 추적이 어렵다.

Hibernate에는 이걸 완화하는 설정이 있다.

properties
hibernate.query.in_clause_parameter_padding=true

파라미터 개수를 2의 거듭제곱으로 올려 맞추고 남는 자리를 마지막 값으로 채운다. 3건이면 4개, 5건이면 8개, 9건이면 16개짜리 SQL이 된다. 결과가 달라지지 않는 이유는 in (1, 2, 3, 3)이 in (1, 2, 3)과 같은 집합이기 때문이다. 효과는 SQL 문자열 종류가 개수에 비례하는 데서 로그 스케일로 줄어드는 것 — 1~1,000건 범위에서 문자열 1,000종이 10종이 된다. 다만 이건 완화이고 해결이 아니다. 10만 건이라는 크기 자체는 그대로다.

5-3. 1차 캐시 적재 — readOnly가 막아주지 않는 것

@Transactional(readOnly = true)가 붙어 있으니 안전하다고 생각하기 쉽다. readOnly가 줄여주는 것은 변경 감지용 스냅샷 유지와 dirty checking, 그리고 flush다. 그런데 조회한 엔티티가 영속성 컨텍스트에 들어가는 것 자체는 막지 않는다.

10만 개 Order 엔티티 인스턴스가 컨텍스트에 담긴다. 트랜잭션이 끝날 때까지 GC 대상이 아니므로 힙을 그대로 밀어낸다. 부하가 높을 때 이 요청 하나가 다른 요청의 GC 압박을 올리고, 최악에는 OOM이다. readOnly는 비용을 줄이는 옵션이고 상한을 만드는 옵션이 아니다. (readOnly=true가 남기는 비용 세 가지는 dto-projection-for-read-only.md 참고.)

여기서 §3-4의 결론이 다시 나온다. 청킹은 5-1과 5-2를 고치고 5-3은 고치지 못한다. 같은 트랜잭션에서 1,000건씩 100번 돌면 컨텍스트에는 결국 10만 개가 쌓인다. em.clear()가 붙어야 비로소 힙이 일정해진다.

5-4. 결과 크기와 직렬화

OrderSummary 10만 개를 만들어 리스트에 담고 JSON으로 직렬화한다. 응답 본문이 수십 MB가 되고, 직렬화 버퍼가 또 힙을 먹는다. 조회 계층을 고쳐도 이 층은 남는다 — "10만 건을 한 번에 응답으로 내보내는 API"라는 요구 자체가 잘못이라는 신호다.

5-5. 한 방의 길이 — 커넥션과 트랜잭션 점유

왕복은 10만 번에서 1번으로 줄지만, 그 1번이 길다. 그 시간 동안 커넥션 하나를 점유하고 트랜잭션이 열려 있다. 커넥션 풀이 10개인 애플리케이션에서 이런 요청 몇 개가 겹치면 관계없는 API가 커넥션을 못 받아 함께 느려진다. 장애가 배치에서 시작해 온라인 트래픽으로 번지는 전형적인 경로다.

정리하면 이렇게 말할 수 있다. "10만 건 IN은 (a) 벤더 한계에 걸려 즉시 실패하거나 (b) 통과하면 실행계획 캐시 오염·힙 압박·커넥션 장기 점유로 조용히 나빠집니다. 청킹은 (a)와 캐시 오염을 고치지만 힙은 clear() 없이는 못 고치고, 애초에 id 10만 개를 모으는 단계가 필요 없으므로 커서 기반으로 가는 것이 맞습니다."

6

반대편도 말한다 — 동료가 옳은 경우

▾

동료가 "관리자가 체크박스로 고르는 거라 많아도 20~30건이다. 청킹까지 넣는 건 오버엔지니어링이고 코드도 복잡해진다. 문제가 생기면 그때 고치면 되지 않나"라고 반박한다. 이 반박은 조건이 맞으면 옳다. 리뷰어가 이걸 인정하지 못하면 "모든 가능성에 대비하라고 요구하는 리뷰어"가 되고, 그때부터 리뷰가 무시된다.

동료가 옳은 조건 세 개.

  1. 입력이 구조적으로 상한이 있다 — 화면이 한 페이지에 최대 100건만 보여주고 전체 선택이 없다면, 100건이 실제 상한이다. 가정이 아니라 구조다.
  2. API가 외부에 노출되지 않는다 — 내부 관리자 화면 전용이고 공개 API 스펙에 없다면, 임의 크기 입력이 들어올 경로가 없다.
  3. 호출자가 하나이고 늘릴 계획이 없다 — 재사용 경로가 실제로 없다.

세 조건이 다 맞으면 청킹의 비용이 이득을 넘는다. 그 비용은 코드 줄 수만이 아니다 — 청크 경계에서 일부만 성공했을 때의 처리, 청크 크기라는 새 설정값, 그에 딸린 테스트 케이스, 그리고 이후 모든 리뷰어가 읽어야 하는 복잡도다. 쓰이지 않을 유연성에 지불하는 값이다.

그래서 양면을 한 호흡에 말하면 이렇게 된다.

💡

"IN 절 전환은 blocking으로 요구합니다. 얻는 것은 쿼리 수를 입력 개수에서 분리하는 것이고, 포기하는 것은 사실상 없습니다 — 한 줄 변경에 존재 검증 방식만 바뀝니다. 반면 청킹은 미룹니다. 얻을 것은 큰 입력에 대한 대비인데 지금 그 입력이 존재하지 않고, 대신 청크 경계 처리와 설정값·테스트가 늘어납니다. 미루면서 감수하는 위험은 '6개월 뒤 누가 큰 입력으로 호출하는 것'이고, 그 위험은 입력 상한 검증 한 줄로 봉쇄됩니다. 그래서 감당 가능하다고 판단합니다."

일반화하면 YAGNI가 유효한 조건이 나온다. "나중에 고치는 비용이 지금 넣는 비용보다 작을 때" 미루는 것이 옳다. 그런데 그 비교에는 숨은 항이 하나 있다 — 나중에 문제를 발견하는 시점이다. 발견이 장애로 온다면 나중 비용에 장애 비용이 더해져 계산이 뒤집힌다. 그래서 정확한 처방은 "미루지 말라"가 아니라 "미루되, 발견을 장애가 아니라 즉시 실패로 만들어 두라" 다. 이것이 §4의 상한 검증이 하는 일이고, 동료의 YAGNI와 리뷰어의 안전 요구가 양쪽 다 만족되는 유일한 지점이다.

"무겁다"로 답하면 절반이다. 다섯 갈래로 쪼개서 말한다(§5). ① Oracle은 IN 항목 1,000개 초과 시 에러, PostgreSQL은 바인드 파라미터 65,535개 상한, MySQL은 패킷 크기 제한 — 여기 걸리면 즉시 실패라 오히려 낫다. ② 통과하면 실행계획 캐시가 오염된다 — 파라미터 개수가 SQL 문자열에 드러나 요청마다 다른 쿼리로 취급되고, 개별 쿼리는 빨라서 슬로우 쿼리 로그에 안 잡히며 DB 전반의 CPU로 나타난다. in_clause_parameter_padding이 개수를 2의 거듭제곱으로 맞춰 문자열 종류를 로그 스케일로 줄여준다. ③ readOnly=true여도 엔티티 10만 개가 영속성 컨텍스트에 쌓여 힙을 밀어낸다 — readOnly는 스냅샷·dirty checking을 줄이지만 적재는 안 막는다. ④ OrderSummary 10만 개 직렬화. ⑤ 그 한 방이 길어서 커넥션을 장시간 점유해 관계없는 API까지 느려진다.

여기서 한 걸음 더 나가면 좋다. "이 목록의 절반은 청킹으로 안 고쳐집니다" — 청킹은 ①②를 고치고 ③은 em.clear()가 있어야 고쳐진다(§5-3).

approve한다. 단, 선을 그어서. IN 절 전환은 blocking으로 요구하고, 청킹은 non-blocking으로 미룬다. 근거를 양면으로 붙인다(§6) — "IN 절은 한 줄이고 얻는 게 크고 포기하는 게 없다. 청킹은 지금 존재하지 않는 입력에 대비하는 비용이고, 그 비용은 줄 수가 아니라 청크 경계 처리·설정값·테스트·이후 리뷰어의 인지 부담이다."

그리고 미룬 위험의 처리 방법을 같이 낸다. 이게 없으면 approve가 그냥 양보가 된다. "청킹은 미루지만, 상한 검증 한 줄은 이번에 넣어주시면 좋겠습니다. 그러면 나중에 큰 입력으로 호출하는 사람이 첫 실행에서 실패하고, 그 시점에 청킹이냐 배치 전용 경로냐를 결정할 수 있습니다." YAGNI를 지키면서 발견 시점만 앞으로 당기는 것이라 동료도 거절할 이유가 거의 없다.

TODO 주석은 답이 아니다. 작동 시점이 틀렸기 때문이다(§4-1) — 주석은 사람이 코드를 읽는 시점에만 작동하는데, 위험은 런타임에 입력이 커지는 순간 발생하고 입력 크기는 컴파일 타임에 알 수 없다. 게다가 6개월 뒤의 배치 개발자는 시그니처만 보고 구현을 열지 않는다.

답은 두 층이다. ① 런타임 장치 — 입력 상한 검증. if (orderIds.size() > MAX_IDS) throw ... 한 줄. 컨트롤러의 @Size가 아니라 서비스에 둔다. 터지는 경로가 HTTP가 아니라 자바 메서드 호출이기 때문이다(§3-3). 그리고 예외 메시지에 다음 결정지점을 적는다 — 주석은 안 읽히지만 스택트레이스는 반드시 읽힌다. ② 빌드 타임 장치 — 쿼리 수 단정 테스트. SQLStatementCountValidator.assertSelectCount(1) 또는 Statistics.getPrepareStatementCount(). 상수 1에 묶기보다 "입력을 3배로 늘려도 쿼리 수가 같다" 를 단정하면 리팩터링에 내구성이 생기고, 테스트 이름이 계약의 문서가 된다(§4-4).

한 문장으로 남길 것: "TODO는 소망이고 상한 검증은 장치다." 판단 기준은 "아무도 아무것도 기억하지 않아도 작동하는가" 하나다.

아니다. 세 가지 함정이 있다.

  • 복합 키에서는 루프로 되돌아간다. Spring Data JPA의 기본 구현은 엔티티가 복합 식별자(@EmbeddedId/@IdClass)를 가지면 IN 절을 만들지 않고 id마다 findById를 호출하는 경로를 탄다. 즉 findAllById로 바꿨는데 SQL은 그대로 N개인 상황이 가능하다. 이건 §4-4의 쿼리 수 테스트가 없으면 절대 발견되지 않는다.
  • 순서를 보장하지 않는다. 결과는 DB가 주는 순서다. 화면이 선택 순서를 기대하면 Map으로 되돌리거나 정렬을 명시해야 한다(§3-2).
  • 없는 id를 조용히 누락한다. 예외가 없으므로 존재 검증을 반드시 직접 해야 하고, 그 검증은 중복 입력을 고려해 Set 기준으로 개수를 비교해야 한다.

그리고 하나 더 — findAllById는 IN 절 크기를 제한하지 않는다. "Spring Data가 알아서 쪼개줄 것"이라는 기대는 근거가 없다. IN 절 상한 관리는 여전히 호출하는 쪽 책임이다.

두 경로를 구분해야 한다는 것이 답의 핵심이다.

  • HTTP 경로(관리자 화면) — 클라이언트 잘못이므로 400이다. 컨트롤러 DTO의 @Size(max = 200)가 Bean Validation으로 걸러 400을 내는 게 가장 깔끔하고, 메시지에 상한을 담아 화면이 안내할 수 있게 한다.
  • 내부 호출 경로(배치) — 여기서는 500이 나는 게 오히려 옳다. 배치는 사용자 입력이 아니라 프로그램의 오용이고, 조용히 처리되는 것보다 시끄럽게 실패하는 것이 낫다. 도메인 예외(TooManyIdsException)를 정의해 던지고, IllegalArgumentException 같은 일반 예외로 두지 않는 이유는 로그에서 이 실패를 이름으로 검색·집계할 수 있어야 하기 때문이다.

여기서 자주 나오는 실수는 예외 대신 상한까지만 자동으로 잘라서 처리하는 것이다. orderIds.subList(0, MAX_IDS)는 최악의 선택이다 — 배치는 성공했다고 보고하고, 정산이 빠진 주문은 아무도 모른다. 조용한 부분 성공보다 시끄러운 실패가 항상 낫다.

리뷰가 잘못된 게 아니라, 리뷰에 맡길 일이 아닌 것을 리뷰에 맡긴 것이다. 코드 리뷰는 확장되지 않는 장치다 — 리뷰어의 컨디션·시간·인원에 비례하고, 리뷰어가 바뀌면 기준이 바뀌고, 급한 릴리스에서 가장 먼저 생략된다. 같은 지적이 세 번 반복되면 그건 개인의 학습 문제가 아니라 프로세스의 결함 신호로 읽어야 한다.

옮기는 순서가 있다.

  1. 반복되는 지적을 먼저 자동 장치로 옮긴다 — 쿼리 수 단정 테스트가 CI에 있으면 리뷰어가 이 지적을 할 필요가 없다. 사람이 판단해야만 하는 것에 리뷰 시간을 쓰는 것이 목적이다.
  2. 자동화가 어려운 것만 컨벤션으로 남긴다 — "컬렉션을 받는 조회 메서드는 입력 상한을 명시한다"처럼 한 줄로, PR 템플릿의 체크 항목으로. 컨벤션은 사람이 읽어야 작동하므로 §4-2 기준으로는 소망이지만, 자동 장치가 왜 있는지를 설명하는 역할을 한다.
  3. 현황을 먼저 뽑고 상위부터 고정한다 — 전면 도입은 분량에 압사당해 중단된다. 요청 단위 쿼리 카운터로 현황 목록을 만들고, 트래픽 × 입력 크기가 큰 것부터 테스트를 붙인다(§4-6).

한 문장으로: 좋은 리뷰어는 지적을 잘하는 사람이 아니라, 같은 지적을 두 번 하지 않도록 장치를 옮기는 사람이다. 그리고 이 원칙은 이 문항의 §4와 정확히 같은 사고다 — 사람의 주의력에 의존하는 것을 코드로 옮기기.

✅ 한 줄 요약

"지금 규모에선 빠릅니다"에 대한 정확한 반박은 성능이 아니라 계약이다 — 이 메서드는 쿼리 수를 호출자가 정하는 API가 됐고 비용이 호출자에 따라 결정되는 구조 자체가 결함이라서, 6개월 뒤 정산 배치가 재사용하는 순간 터진다. 그래서 리뷰 코멘트는 ① 무엇이 문제 / ② 언제 터지는지(조건) / ③ 대안 코드(findAllById + 결과 수 비교로 존재 검증) / ④ blocking 여부 네 조각으로 쓰고, 동료의 "오버엔지니어링" 반박에는 IN 절은 blocking, 청킹은 non-blocking으로 선을 그어 approve하되 — 미룬 결정을 반드시 코드로 못 박는다: if (ids.size() > MAX) throw ... 한 줄을 컨트롤러가 아니라 서비스에 두고(배치는 HTTP를 지나가지 않는다) 예외 메시지에 다음 결정지점을 적고, 쿼리 수 단정 테스트로 입력 비례 복귀를 CI가 잡게 한다. TODO는 소망이고 상한 검증은 장치다 — 판단 기준은 "아무도 아무것도 기억하지 않아도 작동하는가" 하나다. 그리고 배치가 정말 10만 건이면 청킹도 답이 아니다 — 청킹은 벤더 한계와 실행계획 캐시 오염만 고치고 em.clear() 없이는 힙을 못 고치며, 애초에 id 목록을 받는 API가 잘못이므로 커서·범위 조회로 분리해야 한다.
