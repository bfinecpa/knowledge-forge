3. JPA / ORM

대량 INSERT와 JDBC batch — IDENTITY가 배치를 무력화하는 이유, 그리고 JPA 안에서 조여가는 4단계

📖 약 40분 🧩 10개 섹션 0/10 섹션 이해
🎯 핵심 관전 포인트

100만 건이 2시간 걸리는 이유는 한 갈래가 아니라 두 갈래다 — ① 왕복 100만 번(건별 INSERT) ② 영속성 컨텍스트에 엔티티 100만 개 + 스냅샷 100만 벌이 그대로 누적(힙이 밀리고, flush마다 비교 대상이 늘어 뒤로 갈수록 느려진다). 첫 처방으로 "JPQL 벌크 INSERT"를 말하면 그 자리에서 끝난다 — JPQL에는 INSERT 문이 없다(insert into ... select 제외). 그리고 hibernate.jdbc.batch_size를 켜도 @GeneratedValue(IDENTITY)면 단 한 건도 묶이지 않는다: 1차 캐시의 키가 식별자라서 id 없이는 영속 상태를 만들 수 없고, 그래서 persist()가 그 자리에서 INSERT를 날려 키를 받아온다 → 쓰기 지연이 성립하지 않으니 묶을 대상 자체가 없다. 처방은 JPA를 버리는 것이 아니라 JPA 안에서 순서대로 조이는 것이다 — ① ID 전략을 SEQUENCE/(MySQL이면) TABLE + 큰 allocationSize 로 바꿔 채번을 미리 받아오고 ② batch_size + order_inserts/order_updates 로 같은 테이블끼리 모으고 ③ 배치 크기마다 flush() + clear() 로 힙을 비우고 ④ 그래도 부족할 때 JdbcTemplate.batchUpdate 또는 LOAD DATA INFILE로 내려간다. MySQL이라면 여기에 JDBC URL의 rewriteBatchedStatements=true 가 반드시 붙어야 하는데, 이건 Hibernate 로그로는 절대 확인되지 않는다 — 로그에는 묶인 것처럼 보이고 드라이버는 하나씩 보낸다. 마지막으로 100만 건을 트랜잭션 하나로 묶지 않는다: 청크 단위 커밋 + (정산일자, 거래ID) 유니크 키 기반 멱등성이 있어야 어디서 끊겨도 재실행할 수 있다. 그리고 내려가는 데에는 대가가 있다 — Auditing·엔티티 검증·영속성 컨텍스트 정합성·타입 안전성을 함께 내려놓는 것이지, 공짜로 빨라지는 것이 아니다.

면접 질문

"대량 데이터 INSERT 시 JPA의 한계와 JDBC batch로 우회하는 방법(IDENTITY 전략의 문제 포함)을 설명해주세요."

출제 의도"JPA로 짰더니 100만 건에 2시간"이라는, 실무에서 반드시 한 번은 만나는 상황이다. 원인(건별 INSERT, IDENTITY의 batch 무력화)을 알고 우회로를 설계할 수 있는지를 본다. 더 깊게는 ORM의 한계를 인정하고 내려갈 줄 아는 유연함 — ORM을 신봉해 끝까지 붙들지도 않고, 조금 느리다고 곧장 던져버리지도 않는 균형 감각을 확인하는 질문이다.

함정은 세 갈래다.

  1. 느린 이유를 한 갈래만 본다. "쿼리가 100만 번 나가서"는 절반이다. 나머지 절반인 영속성 컨텍스트 누적을 말하지 못하면, "왜 앞의 10만 건은 3분인데 뒤의 10만 건은 40분인가"를 설명할 수 없다.
  2. 처방이 JPQL로 샌다. "JPQL 벌크로 바꾸겠다"는 말은 JPQL에 INSERT가 없다는 사실 하나로 무너진다(§2).
  3. JPA 안에서 조여가는 단계가 통째로 비어 있다. IDENTITY가 문제라는 걸 알면서 곧장 "그럼 JPA를 버리겠다"로 점프하는 것 — 가장 흔하고, 가장 아쉬운 감점이다. 실무자는 그 사이에 카드를 세 장 더 갖고 있다(§4).

이 문서는 하나의 예제를 끝까지 끌고 간다.

java
@Entity
@Table(name = "settlement")
public class Settlement {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // ← 이 한 줄이 §3의 전부다
    private Long id;

    private LocalDate settlementDate;   // 정산일자
    private String    txId;             // 외부 시스템의 거래 ID
    private BigDecimal amount;          // 금액
    private Long      merchantId;       // 가맹점
    private LocalDateTime createdAt;

    // ...
}
java
@Transactional
public void load(List<SettlementDto> dtos) {          // dtos.size() == 1_000_000
    for (SettlementDto dto : dtos) {
        settlementRepository.save(Settlement.from(dto));
    }
}

왜 2시간인가 — 느린 이유는 두 갈래다

▾

첫 답변에서 "쿼리가 100만 번 나가서"까지만 말하고 멈추는 것이 이 문항의 가장 흔한 모습이다. 진단이 틀린 건 아니지만 절반이고, 나머지 절반을 놓치면 처방도 절반만 나온다(배치만 켜고 flush/clear를 빼먹는다).

1-1. 갈래 ① — 네트워크 왕복 100만 번

save() 한 번은 SQL 한 문장이고, 한 문장은 애플리케이션 → DB → 애플리케이션 왕복 한 번이다. 왕복 한 번에 드는 시간이 작아 보여도 100만을 곱하면 시간 단위가 된다.

여기서 중요한 건 숫자가 아니라 성질이다 — 이 비용은 CPU도 디스크도 아니고 왕복 횟수에 비례한다. 그래서 처방의 방향이 정해진다: 쿼리를 빠르게 만드는 것이 아니라, 왕복 횟수를 줄이는 것. 인덱스를 손보거나 서버를 키워도 이 축은 거의 움직이지 않는다.

💡

비유하면 택배 100만 개를 한 개씩 트럭에 실어 왕복하는 것이다. 트럭을 빠르게 만드는 것(하드웨어 증설)보다 한 번에 여러 개 싣는 것(배치)이 압도적으로 효과가 크다. 이 문항의 절반은 그 "묶어 싣기"가 왜 IDENTITY에서 불가능한지에 관한 이야기다.

1-2. 갈래 ② — 영속성 컨텍스트 누적, 그래서 뒤로 갈수록 느려진다

save()(정확히는 persist())로 저장한 엔티티는 트랜잭션이 끝날 때까지 영속성 컨텍스트가 계속 붙들고 있다. 100만 건을 넣으면 트랜잭션 끝에 엔티티 100만 개 + 스냅샷 100만 벌이 힙에 살아 있다.

  • 메모리가 사실상 2배다. 영속성 컨텍스트는 엔티티 인스턴스와 로드/등록 시점의 필드값 복사본(스냅샷) 을 따로 갖는다. 무엇이 바뀌었는지는 대조해봐야만 알 수 있기 때문이다(→ 영속성 컨텍스트와 변경 감지).
  • flush마다 비교 대상이 늘어난다. 변경 감지는 관리 중인 엔티티 전건 × 전 필드 대조다. 50만 건째에 flush가 일어나면 그 순간 50만 개를 훑는다. 즉 누적량에 비례해 flush 비용이 커진다.
  • GC가 회수하지 못한다. 영속성 컨텍스트가 강한 참조로 붙들고 있으므로, 힙이 차도 버릴 수 있는 것이 없다. Full GC가 반복되며 애플리케이션 전체가 멎고, 운이 나쁘면 OutOfMemoryError로 끝난다 — 2시간 뒤에.

이 갈래가 만드는 관측 가능한 신호는 "뒤로 갈수록 느려진다" 이다. 왕복 비용만 문제라면 처리 속도는 처음부터 끝까지 일정해야 한다. 앞의 10만 건은 몇 분인데 뒤의 10만 건이 수십 분이라면, 그건 왕복이 아니라 누적이 범인이다.

1-3. 이 갈래를 놓치는 것이 왜 아까운가 — "아는 개념을 새 상황에 옮겨 붙이기"

조회 전용 DTO 프로젝션 문항에서는 "1차 캐시에 적재하는 행위 자체가 비용" 이라고 정확히 말할 수 있는 사람이, 대량 INSERT 상황에서는 같은 축을 떠올리지 못하는 경우가 많다(→ 조회 전용 DTO 프로젝션).

개념을 모르는 것이 아니라, 개념이 붙는 상황의 목록이 좁은 것이다. 그래서 기억해야 할 것은 사실이 아니라 트리거다.

💡

"엔티티를 루프에서 대량으로 다룬다"는 말이 나오면 반사적으로 영속성 컨텍스트 누적을 의심한다. 읽기든 쓰기든 똑같다 — 읽기에서는 DTO 프로젝션으로 애초에 안 올리고, 쓰기에서는 flush() + clear()로 주기적으로 비운다.

첫 처방이 자주 틀리는 지점 — "JPQL 벌크 INSERT"는 존재하지 않는다

▾

2-1. JPA 표준 JPQL에는 INSERT 문이 없다

이 사실 하나를 모르면 면접에서 첫 처방이 통째로 무효가 된다. JPQL이 지원하는 벌크 연산은 UPDATE와 DELETE 둘뿐이다.

java
// 존재하지 않는 문법 — 파싱 단계에서 실패한다
em.createQuery("insert into Settlement (settlementDate, txId, amount) values (?1, ?2, ?3)");

왜 없는가를 함께 말하면 단순 암기가 아니라는 신호가 된다. JPQL은 이미 DB에 존재하는 엔티티를 대상으로 하는 질의 언어다. UPDATE·DELETE는 "어떤 행을 대상으로 할지" where로 지정할 수 있지만, INSERT는 대상이 DB에 없고 애플리케이션 메모리에 있다. 값을 SQL 문자열로 옮기는 순간 그건 질의가 아니라 직렬화이므로, JPA는 그 역할을 persist()에 맡긴다.

예외가 하나 있다 — 하이버네이트 HQL의 insert into ... select다.

sql
-- 이건 된다: 출처가 "이미 DB에 있는 행"이므로 질의로 표현 가능
insert into Settlement (settlementDate, txId, amount)
select s.settlementDate, s.txId, s.amount from StagingSettlement s where ...

그런데 이 예외가 오늘 문제를 풀어주지는 않는다. 우리 데이터는 외부 시스템에서 받아온 것이라 아직 DB 어디에도 없기 때문이다. (다만 §4-4에서 "먼저 스테이징 테이블에 LOAD DATA INFILE로 통째로 밀어 넣고, 거기서 insert ... select로 옮긴다"는 설계로 되살아난다 — 이 연결을 말하면 가산점이다.)

2-2. @Modifying 벌크 연산과 혼동하지 말 것

"벌크 연산"이라는 단어 때문에 @Modifying + JPQL을 떠올리기 쉬운데, 그건 다른 문항의 도구다. @Modifying은 UPDATE/DELETE를 영속성 컨텍스트를 우회해 DB로 바로 보내는 것이고, 여기서 문제되는 것은 DB와 1차 캐시의 불일치다 (→ 벌크 연산과 영속성 컨텍스트).

두 문항의 축이 정반대라는 점을 알아두면 헷갈리지 않는다.

벌크 UPDATE/DELETE (@Modifying)대량 INSERT (이 문항)
대상이미 DB에 있는 행아직 DB에 없는 새 데이터
영속성 컨텍스트우회한다 → 불일치가 문제통과한다 → 누적이 문제
핵심 처방실행 후 clear() (또는 순서 조정)배치 묶기 + 주기적 flush/clear

2-3. saveAll()로 바꾸는 것도 답이 아니다

"루프 대신 saveAll(list)을 쓰면 되지 않나"는 자연스러운 발상이지만, saveAll() 내부는 결국 리스트를 순회하며 save()를 부르는 것이다. 왕복 횟수는 그대로다.

이름이 복수형이라고 SQL이 하나가 되지는 않는다. 여러 건을 한 문장으로 묶는 일은 saveAll()이 아니라 JDBC 배치 계층이 하고, 그걸 켜는 스위치가 hibernate.jdbc.batch_size다. 그런데 그 스위치를 켜도 IDENTITY면 아무 일도 일어나지 않는다. 다음 장이 그 이야기다.

3

IDENTITY가 배치를 무력화하는 메커니즘

▾

이 문항에서 가장 중요한 지점이고, "auto_increment라 INSERT 전엔 id를 알 수 없어서" 라고 답할 수 있으면 절반은 통과다. 나머지 절반은 "그래서 무슨 일이 연쇄적으로 일어나는가" 다.

3-1. 1차 캐시의 키가 식별자다 — 키가 없으면 넣을 수 없다

영속성 컨텍스트의 1차 캐시는 @Id 값 → 엔티티 인스턴스의 Map 하나다. 그러니 엔티티를 영속 상태로 만들려면 키가 반드시 있어야 한다.

IDENTITY는 키를 DB의 auto_increment가 만든다. 즉 INSERT를 실제로 보내기 전에는 애플리케이션이 그 값을 알 방법이 없다.

3-2. 그래서 persist()가 그 자리에서 INSERT를 날린다

java
Settlement s = Settlement.from(dto);
em.persist(s);
// IDENTITY:
//   ① 즉시 INSERT 실행 (왕복 1회)
//   ② JDBC의 생성 키 반환으로 id를 받아옴
//   ③ 그 id를 키로 1차 캐시에 등록
//   → "쓰기 지연"이 아예 성립하지 않는다
//
// SEQUENCE/TABLE:
//   ① 제너레이터에서 id를 먼저 받아온다 (미리 확보해 둔 값이면 왕복 0회)
//   ② 즉시 1차 캐시에 등록
//   ③ INSERT는 쓰기 지연 저장소에 쌓아만 둔다
//   → flush 시점에 한꺼번에 내보낼 수 있다 = 묶을 대상이 생긴다

연쇄를 한 문장으로: IDENTITY → 키를 DB만 안다 → 키 없이는 1차 캐시에 못 넣는다 → persist()가 즉시 INSERT를 보낸다 → 쓰기 지연 저장소가 비어 있다 → 묶을 대상 자체가 없다 → batch_size는 아무것도 하지 않는다.

즉 batch_size가 안 켜진 것이 아니라, 켜져 있는데 묶을 것이 없는 것이다. 이 구분을 말하면 "설정을 외운 사람"과 "동작을 아는 사람"이 갈린다.

3-3. 로그로 확인하는 장면 — 설정을 켰는데 아무 변화가 없다

✕ BEFOREbatch_size 없이 — insert 문장이 건별로 100만 줄
spring:
  jpa:
    properties:
      hibernate:
        show_sql: true
✓ AFTERbatch_size 를 켰다 — 그런데 로그는 전혀 달라지지 않는다
spring:
  jpa:
    properties:
      hibernate:
        show_sql: true
        jdbc:
          batch_size: 1000

Hibernate: insert into settlement (amount, created_at, merchant_id, settlement_date, tx_id) values (?, ?, ?, ?, ?)
Hibernate: insert into settlement (amount, created_at, merchant_id, settlement_date, tx_id) values (?, ?, ?, ?, ?)
Hibernate: insert into settlement (amount, created_at, merchant_id, settlement_date, tx_id) values (?, ?, ?, ?, ?)
... (100만 줄, 소요 시간도 그대로)

주의할 점이 하나 있다. 이 로그만으로 "배치가 안 됐다"고 단정하면 안 된다 — show_sql은 배치 여부를 보여주는 도구가 아니기 때문이다. 배치가 잘 동작할 때도 문장은 한 줄씩 찍힌다(§5-2). 여기서는 "로그 줄 수"가 아니라 "소요 시간이 그대로"가 증거이고, 확실히 하려면 §5-3의 관측 도구를 써야 한다.

3-4. 그러면 JdbcTemplate은 왜 같은 auto_increment인데 되는가

테이블은 그대로 auto_increment인데 JdbcTemplate.batchUpdate는 잘 묶인다. 왜 JPA에서 문제였던 것이 여기서는 문제가 안 되는가 — JDBC에는 영속성 컨텍스트가 없기 때문이다.

JPA가 id를 필요로 했던 이유는 DB에 넣기 위해서가 아니라 1차 캐시에 넣기 위해서였다. JDBC는 애초에 캐시할 대상이 없으므로 id를 몰라도 아무 지장이 없다. 그래서 값만 addBatch로 쌓았다가 executeBatch로 한 번에 보내면 되고, id는 DB가 알아서 채운다.

이 설명까지 붙일 수 있으면 "우회로를 아는 것"이 아니라 "우회로가 통하는 이유를 아는 것" 이 된다 — 암기와 이해가 갈리는 지점이다.

4

개선 순서 — 이 문항의 척추

▾

핵심은 "JPA를 버릴까 말까"의 이분법이 아니라 순서다. 아래 네 단계는 위험도와 포기하는 것이 순서대로 커진다. 실무자는 위에서부터 하나씩 열어보고, 효과가 충분한 지점에서 멈춘다.

4-1. ① ID 전략 교체 — 채번을 미리 받아와 INSERT를 미룬다

§3에서 확인한 대로 막힌 것은 배치가 아니라 쓰기 지연이다. 그러니 첫 카드는 "INSERT 전에 id를 알 수 있게 만드는 것" 이다.

✕ BEFOREIDENTITY — persist() 마다 즉시 INSERT, 쓰기 지연 불가
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
✓ AFTERTABLE 제너레이터 + 큰 allocationSize — 채번 1회로 1000개를 미리 확보
@Id
@GeneratedValue(strategy = GenerationType.TABLE, generator = "settlement_seq")
@TableGenerator(
        name = "settlement_seq",
        table = "id_sequences",       // 채번용 테이블
        pkColumnName = "seq_name",
        valueColumnName = "next_val",
        pkColumnValue = "settlement",
        allocationSize = 1000)        // ← 한 번 다녀올 때 1000개를 선점한다
private Long id;

allocationSize가 무엇을 하는가. 채번을 한 건씩 받아오면 왕복이 또 100만 번이라 아무 이득이 없다. allocationSize = 1000이면 하이버네이트가 한 번 채번해 1000개 구간을 통째로 선점하고, 그 다음 999건은 메모리에서 번호를 매긴다. 즉 채번 왕복이 1/1000로 줄고, INSERT는 전부 쓰기 지연 저장소로 들어간다.

💡

비유하자면 번호표를 한 장씩 뽑으러 가는 것 대신 1000장짜리 묶음을 받아오는 것이다. 창구에 가는 횟수가 1/1000이 된다.

MySQL 이야기를 정확히 할 것. MySQL에는 시퀀스 오브젝트가 없다. 그래서 GenerationType.SEQUENCE를 지정해도 하이버네이트는 테이블 기반 제너레이터로 대체한다. 결과적으로 MySQL에서는 TABLE 제너레이터를 명시적으로 쓰는 것이 동작과 의도가 일치해 혼란이 적다. (AUTO는 하이버네이트 버전과 설정에 따라 매핑이 달라질 수 있으므로 배치 성능이 걸린 자리에서는 전략을 명시하는 편이 안전하다.)

이 단계가 못 해결하는 것 — 반드시 같은 호흡에 말할 것.

  • id에 구멍이 생긴다. 애플리케이션을 재시작하면 선점 구간의 남은 번호는 버려진다. PK는 연속일 필요가 없으므로 대개 문제가 아니지만, id를 업무 일련번호로 노출하고 있다면 문제가 된다.
  • 채번 테이블이 경합 지점이 된다. 여러 인스턴스가 동시에 채번하면 그 행에 락이 걸린다. allocationSize가 크면 방문 횟수가 적어 경합도 줄지만, allocationSize가 1이면 오히려 병목이 된다.
  • 기존 테이블의 마이그레이션이 필요하다. 이미 auto_increment로 운영 중인 테이블이라면 채번 테이블의 시작값을 현재 최대 id보다 크게 잡아야 한다. "코드 한 줄 바꾸면 끝"이 아니다.
  • 왕복 횟수 자체는 아직 그대로다. 이 단계는 묶을 수 있는 상태를 만든 것일 뿐이고, 실제로 묶는 건 ②다.

4-2. ② batch_size + order_inserts / order_updates

✕ BEFORE이제 쓰기 지연은 되지만 여전히 한 문장씩 나간다
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 0
✓ AFTER묶어서 보낸다 + 묶일 수 있게 정렬한다
spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 1000
        order_inserts: true            # 같은 테이블 INSERT 끼리 모은다
        order_updates: true            # 같은 테이블 UPDATE 끼리 모은다
        jdbc.batch_versioned_data: true  # @Version 이 있는 엔티티도 배치 대상으로

order_inserts가 왜 필요한가. JDBC 배치는 연속된 같은 SQL 문장만 묶는다. 쓰기 지연 저장소에 Settlement → Merchant → Settlement → Merchant처럼 섞여 있으면, 문장이 바뀔 때마다 배치가 끊겨 크기 1짜리 배치가 줄줄이 만들어진다. order_inserts는 flush 직전에 같은 테이블끼리 모아 배치가 실제로 묶이게 한다.

💡

"묶기 스위치를 켰는데 왜 안 빨라지지"의 두 번째 단골 원인이 이것이다. 첫 번째는 §3의 IDENTITY이고, 세 번째는 §5의 rewriteBatchedStatements다. 이 세 가지를 순서대로 나열할 수 있으면 실제로 겪어본 사람으로 읽힌다.

정렬이 개입한다는 사실은 SQL 실행 순서가 코드 순서와 다르다는 더 큰 성질의 한 사례다(→ flush 시점과 쓰기 지연 SQL 실행 순서).

이 단계가 못 해결하는 것.

  • 힙 누적은 그대로다. 배치로 내보내도 엔티티는 여전히 영속성 컨텍스트에 남는다. 100만 개 + 스냅샷 100만 벌은 그대로이며, flush마다 대조 대상도 계속 커진다. 그래서 ③이 필요하다.
  • MySQL이면 아직 아무 일도 안 일어났을 수 있다 — §5.
  • batch_size가 클수록 좋은 것은 아니다. 한 번에 보내는 패킷이 커지므로 DB의 최대 패킷 크기 제한에 걸릴 수 있고, 배치 하나가 실패했을 때 어느 건이 실패했는지 좁히기 어려워진다. 수백~수천 사이에서 측정해 정하는 값이지, 크게 잡을수록 이기는 값이 아니다.

4-3. ③ 배치 크기마다 flush() + clear()

여기가 §1-2의 갈래를 실제로 없애는 단계다.

✕ BEFORE트랜잭션이 끝날 때까지 100만 개가 힙에 남는다
@Transactional
public void load(List<SettlementDto> dtos) {
    for (SettlementDto dto : dtos) {
        settlementRepository.save(Settlement.from(dto));
    }
}
✓ AFTERbatch_size 와 같은 주기로 내보내고 비운다
@PersistenceContext
private EntityManager em;

@Transactional
public void load(List<SettlementDto> dtos) {
    int batchSize = 1000;                       // hibernate.jdbc.batch_size 와 맞춘다
    for (int i = 0; i < dtos.size(); i++) {
        em.persist(Settlement.from(dtos.get(i)));

        if ((i + 1) % batchSize == 0) {
            em.flush();   // 쌓인 INSERT 1000건을 배치로 내보낸다
            em.clear();   // 1차 캐시 + 스냅샷을 비운다 → 힙이 평평해진다
        }
    }
    em.flush();
    em.clear();           // 나머지 (1000의 배수가 아닌 꼬리)
}

flush()와 clear()는 역할이 다르고 둘 다 필요하다.

  • flush() — 쌓인 SQL을 DB로 내보낸다. 이게 없으면 트랜잭션 끝에 100만 건이 한꺼번에 몰린다.
  • clear() — 영속성 컨텍스트를 비운다. flush()만 하면 SQL은 나가지만 엔티티는 그대로 남아 있어서 힙 문제도, 전건 대조 문제도 전혀 해결되지 않는다. 이 구분을 못 하고 flush()만 넣는 코드가 실제로 흔하다.

batchSize를 hibernate.jdbc.batch_size와 맞추는 이유는 단순하다. 주기가 어긋나면 flush 시점에 쌓인 개수가 배치 크기와 맞지 않아 자투리 배치가 계속 생긴다.

이 단계가 못 해결하는 것 — 그리고 새로 만드는 위험.

  • clear()는 컨텍스트를 통째로 비운다. 같은 트랜잭션에서 다루던 다른 엔티티들도 함께 준영속(detached)이 된다. 루프 안에서 조회해 둔 가맹점 엔티티를 clear() 뒤에 만지면 지연 로딩이 터지거나 변경 감지가 사라진다. 배치 로직은 다른 엔티티 조작과 섞지 않는 것이 안전하고, 꼭 필요하면 clear() 이후 id로 다시 조회해야 한다.
  • 트랜잭션은 여전히 하나다. flush()는 커밋이 아니다. 100만 건이 여전히 한 트랜잭션에 묶여 있고 중간에 실패하면 전부 롤백된다 → §6.

4-4. ④ 그래도 부족하면 — JdbcTemplate.batchUpdate / LOAD DATA INFILE

①~③으로 대개 충분하지만, 엔티티 매핑 자체가 무거운 경우(연관관계가 많다, 컨버터가 여럿이다, 리스너가 붙어 있다)에는 건당 객체 생성·매핑 비용이 남는다. 이때 비로소 아래로 내려간다.

✕ BEFOREJPA — 엔티티 생성 + 영속성 컨텍스트 통과 비용이 건마다 붙는다
for (SettlementDto dto : dtos) em.persist(Settlement.from(dto));
✓ AFTERJdbcTemplate — 엔티티도 영속성 컨텍스트도 없이 값만 보낸다
private static final String SQL = """
        insert into settlement (settlement_date, tx_id, amount, merchant_id, created_at)
        values (?, ?, ?, ?, ?)
        """;

public void load(List<SettlementDto> dtos) {
    for (List<SettlementDto> chunk : Lists.partition(dtos, 1000)) {
        jdbcTemplate.batchUpdate(SQL, chunk, chunk.size(), (ps, dto) -> {
            ps.setObject(1, dto.settlementDate());
            ps.setString(2, dto.txId());
            ps.setBigDecimal(3, dto.amount());
            ps.setLong(4, dto.merchantId());
            ps.setObject(5, LocalDateTime.now());   // ← Auditing 이 안 붙으므로 직접
        });
    }
}

LOAD DATA INFILE은 한 단계 더 아래다. 데이터를 파일로 만들어 MySQL이 직접 읽게 하는 방식으로, INSERT 문 파싱조차 건너뛰므로 가장 빠르다. 대신 파일을 만들고 옮길 경로가 필요하고, 서버 설정(로컬 파일 읽기 허용)이 열려 있어야 하며, 애플리케이션 코드에서 SQL로 표현되지 않아 추적이 어렵다.

두 경로를 절충하는 좋은 설계가 §2-1에서 예고한 것이다 — LOAD DATA INFILE로 스테이징 테이블에 원본을 통째로 밀어 넣고, insert into ... select로 정제해 본 테이블로 옮긴다. 가장 무거운 구간(파일 → DB)은 DB에게 맡기고, 변환 로직은 SQL로 남겨 검증할 수 있게 된다. (가산점 포인트)

4-5. 종합 — 각 단계가 무엇을 해결하고 무엇을 못 해결하는가

단계해결하는 것못 해결하는 것포기하는 것
① ID 전략 교체쓰기 지연이 성립 → 묶을 대상이 생긴다왕복 횟수, 힙 누적id 연속성, 마이그레이션 비용
② batch_size + order_inserts왕복 횟수힙 누적, 드라이버 단 전송(§5)실패 지점 특정이 어려워짐
③ flush() + clear()힙 누적, 전건 대조 폭증트랜잭션 크기(§6)컨텍스트 통째 비움의 부작용
④ JdbcTemplate / LOAD DATA매핑·객체 생성 비용(성능은 끝, 이제 정합성이 과제)Auditing·검증·타입 안전성(§7)

면접에서 이 표를 말로 풀 때의 순서: "저는 ①부터 열어보고, 각 단계에서 실제로 측정한 다음 충분하면 멈춥니다. ④는 마지막 카드지 첫 카드가 아닙니다 — 얻는 것이 큰 만큼 포기하는 것도 크기 때문입니다."

5

MySQL이면 반드시 확인할 것 — rewriteBatchedStatements=true

▾

5-1. 없으면 드라이버가 결국 하나씩 보낸다

①~③을 다 하고도 시간이 거의 줄지 않는 일이 흔하다. MySQL JDBC 드라이버는 기본 상태에서 executeBatch()를 받아도 문장을 하나씩 서버로 전송한다. 즉 하이버네이트는 성실히 묶어서 넘겼는데, 드라이버가 도로 풀어서 보내는 것이다.

✕ BEFORE
jdbc:mysql://host:3306/settlement?...
✓ AFTER
jdbc:mysql://host:3306/settlement?rewriteBatchedStatements=true&...

이 옵션을 켜면 드라이버가 배치를 insert into settlement (...) values (...), (...), (...) 형태의 multi-values 한 문장으로 재작성해 보낸다. 왕복 횟수가 진짜로 줄어드는 지점이 여기다.

주의할 점 두 가지. ① 재작성된 문장이 커지므로 서버의 최대 패킷 크기 제한에 걸릴 수 있다(배치 크기와 함께 조절한다). ② 재작성된 multi-values INSERT에서는 생성 키 반환이 기대대로 동작하지 않을 수 있다 — 배치 적재 후 생성된 id가 필요한 로직이 있다면 반드시 검증해야 한다.

5-2. 이 함정이 악질인 이유 — 하이버네이트 로그로는 확인되지 않는다

show_sql이나 org.hibernate.SQL 로그는 하이버네이트가 만든 문장을 찍는다. JDBC 드라이버가 그 아래에서 무엇을 어떻게 보냈는지는 찍지 않는다. 그래서 배치가 정상 동작하든 아니든 로그 모양이 똑같다.

💡

"로그를 봤는데 정상인 것 같은데 안 빨라져요" 가 이 함정의 표준 증상이다. 로그가 관측하는 층과 문제가 발생하는 층이 다르기 때문이며, 관측 도구가 문제 지점을 덮지 못하면 아무리 열심히 봐도 안 보인다.

5-3. 그러면 무엇으로 확인하나 — 관측의 3층

무엇을 알고 싶은가도구한계
하이버네이트가 문장을 몇 개 준비·실행했나Statistics.getPrepareStatementCount(), SQLStatementCountValidator배치로 묶였는지는 알려주지 않음
JDBC API 수준에서 addBatch/executeBatch가 실제로 쓰였나, 배치 크기는 얼마인가p6spy, datasource-proxy드라이버 내부의 재작성은 이 아래에서 일어나 보이지 않음
드라이버가 서버로 실제 보낸 문장MySQL general log (또는 서버 측 쿼리 로그)운영에서 상시로 켜기 곤란 → 성능 검증 환경에서 확인

세 층이 각각 다른 것을 본다는 점이 핵심이다. rewriteBatchedStatements의 효과는 맨 아래 층에서만 보이고, order_inserts 누락은 가운데 층(배치 크기가 1로 찍힌다) 에서 잡히며, IDENTITY 문제는 맨 위 층(문장 수가 안 줄어든다) 에서 드러난다.

5-4. 이 성질을 코드로 고정하기

rewriteBatchedStatements는 URL에서 한 글자만 빠져도 조용히 사라지는 설정이다. 누군가 DataSource 설정을 정리하다 옵션을 지워도 애플리케이션은 정상 동작하고 배치만 느려진다 — 즉 테스트로 잡지 않으면 언젠가 반드시 되돌아온다.

java
@Test
void 정산_적재는_배치로_묶여_나간다() {
    SQLStatementCountValidator.reset();

    loader.load(fixture(1_000));                     // 1000건 적재

    // 건별 INSERT 라면 1000이 된다. 배치가 살아 있으면 그보다 훨씬 작아야 한다.
    SQLStatementCountValidator.assertInsertCount(1);
}

@Test
void JDBC_URL에_rewriteBatchedStatements가_켜져있다() {
    assertThat(dataSourceUrl()).contains("rewriteBatchedStatements=true");
}

두 번째 테스트는 우스워 보이지만 "로그로는 확인되지 않는 설정"을 붙잡아 두는 유일한 장치다. 그리고 여기서 DB는 실제 MySQL이어야 한다 — H2로는 드라이버 동작도, 배치 재작성도 검증되지 않으므로 Testcontainers를 쓴다.

💡

일반화하면: "문제를 만나면 잘 푼다"와 "문제가 오기 전에 잡는 장치를 만든다"는 다른 능력이다. 이 문항에서 그 차이가 가장 선명하게 드러나는 곳이 §5다 — 증상이 '조금 느림'뿐이고 로그에는 아무 흔적도 남지 않기 때문이다.

6

100만 건을 트랜잭션 하나로 처리하지 않는다

▾

성능이 해결돼도 설계가 남는다. ①~④를 다 해도 @Transactional 하나가 100만 건을 감싸고 있으면 배치로서는 여전히 부실하다.

6-1. 큰 트랜잭션이 만드는 세 가지 문제

  • undo 로그가 계속 커진다. DB는 롤백에 대비해 변경 전 이미지를 보관하는데, 트랜잭션이 끝나지 않으면 정리(purge)가 밀린다. 이 배치와 무관한 다른 트랜잭션의 조회 성능까지 함께 떨어진다.
  • 락 보유 시간이 배치 전체 길이가 된다. 새 행에 대한 락, 인덱스 갱신에 따른 락이 커밋 전까지 전부 유지된다. 같은 테이블을 만지는 온라인 트랜잭션이 있다면 그대로 대기한다.
  • 99만 9999건째에서 실패하면 전부 롤백된다. 두 시간 일하고 아무것도 남지 않으며, 롤백 자체도 오래 걸린다. 그리고 다시 돌려도 같은 데이터에서 또 실패한다.

6-2. 청크 단위 커밋

✕ BEFORE100만 건이 트랜잭션 하나 — 실패 시 전부 소멸
@Transactional
public void load(List<SettlementDto> dtos) { ... }
✓ AFTER청크마다 독립 트랜잭션 — 성공한 청크는 남는다
public void load(List<SettlementDto> dtos) {
    for (List<SettlementDto> chunk : Lists.partition(dtos, 1_000)) {
        chunkLoader.loadChunk(chunk);        // 별도 빈: @Transactional 이 청크 단위로 걸린다
    }
}

@Transactional                                // ← 트랜잭션 경계가 청크
public void loadChunk(List<SettlementDto> chunk) {
    for (SettlementDto dto : chunk) em.persist(Settlement.from(dto));
    // 메서드 종료 = flush + commit. clear 는 컨텍스트가 닫히며 함께 정리된다
}

주의: 같은 클래스의 메서드를 호출하면 프록시를 타지 않아 트랜잭션이 걸리지 않는다(self-invocation). 청크 로더를 별도 빈으로 분리해야 한다.

Spring Batch를 쓰면 이 구조가 기본값이다. chunk(1000)으로 읽기·처리·쓰기를 묶고 청크마다 커밋하며, 어디까지 처리했는지를 JobRepository가 기록해 실패 지점부터 재시작할 수 있다. "배치 프레임워크가 실제로 해주는 일"을 이렇게 설명하면 좋다 — 청크 커밋 + 재시작 지점 관리 + 실패 건 격리(skip/retry) 다.

6-3. 멱등성 — 재실행 가능해야 진짜 배치다

청크 커밋을 하면 "어디까지 들어갔는지 모르는 상태에서 다시 돌리는 상황" 이 생긴다. 그래서 청크 커밋과 멱등성은 한 세트다.

sql
-- 자연 키에 유니크 제약을 건다: 같은 정산일자의 같은 거래는 한 번만
alter table settlement
  add constraint uk_settlement_date_tx unique (settlement_date, tx_id);
sql
-- 재실행해도 안전한 적재: 이미 있는 행은 조용히 건너뛴다
insert into settlement (settlement_date, tx_id, amount, merchant_id, created_at)
values (?, ?, ?, ?, ?)
on duplicate key update tx_id = tx_id;   -- 아무것도 바꾸지 않는 no-op upsert

INSERT IGNORE가 더 짧지만 권하지 않는다 — 중복뿐 아니라 데이터 잘림이나 타입 변환 실패까지 경고로 낮춰 조용히 통과시키기 때문이다. 배치는 사람이 안 보는 새벽에 도는 코드라, 조용히 잘못된 데이터를 넣는 것이 실패보다 훨씬 나쁘다 (→ 복합 유니크 제약과 동시 INSERT).

세 가지가 한 줄로 연결된다: 유니크 제약(중복을 DB가 막는다) → upsert(중복이 예외가 아니라 정상 흐름이 된다) → 재실행 가능(어디서 끊겨도 그냥 다시 돌리면 된다). 이걸 말하면 성능 질문에 운영 감각으로 답한 것이 된다.

7

내려갈 때 포기하는 것 — "한계를 인정한다" ≠ "대가 없이 내려간다"

▾

이 문항이 보는 것은 "ORM의 한계를 인정하고 내려갈 줄 아는 유연함" 인데, 여기서 자주 생기는 오해가 있다. 유연함은 "쉽게 버리는 것"이 아니라 "무엇을 내려놓는지 알고 버리는 것" 이다. JdbcTemplate/LOAD DATA INFILE로 가면 아래를 함께 잃는다.

  • JPA Auditing이 안 붙는다. @CreatedDate·@LastModifiedDate·@CreatedBy는 엔티티 생명주기 이벤트에 걸린 기능이라 SQL을 직접 쓰면 전혀 동작하지 않는다. created_at 컬럼이 통째로 null인 100만 행이 남는 사고가 여기서 나온다. → 컬럼을 직접 채우고, 테스트로 고정한다.
  • 엔티티의 검증·도메인 로직을 우회한다. 생성자에서 하던 금액 부호 검사, 상태 초기화, @PrePersist 훅이 전부 건너뛰어진다. "엔티티를 거치면 절대 만들 수 없는 데이터"가 테이블에 들어갈 수 있다.
  • 영속성 컨텍스트와 어긋난다. 같은 트랜잭션에서 JPA로 조회한 데이터가 있다면, JDBC로 밀어 넣은 행은 그 컨텍스트에 없다. @Version도 증가하지 않고, 2차 캐시를 쓰고 있다면 캐시가 낡은 상태로 남는다.
  • 타입 안전성을 잃는다. ps.setString(2, ...)의 인덱스가 컬럼 순서와 어긋나도 컴파일은 통과한다. 컬럼을 하나 추가하는 순간 조용히 밀린다. → 컬럼 순서를 단정하는 통합 테스트나 QueryDSL SQL 같은 타입 안전 계층으로 방어한다.
  • 테스트 방식이 달라진다. @DataJpaTest의 롤백에 기대던 방식이 통하지 않고, DB 벤더 종속 SQL이라 H2로는 검증되지 않는다. Testcontainers가 사실상 필수가 된다.

그래서 실무의 균형점은 "전면 교체"가 아니라 "경계 좁히기" 다. 대량 적재 경로만 SettlementBulkWriter 같은 별도 클래스로 격리하고 나머지는 JPA를 유지한다. 그 클래스 안에서만 위 다섯 가지를 신경 쓰면 되고, 위험이 코드베이스 전체로 번지지 않는다.

💡

8

외부 채번(Redis INCR, 스노우플레이크)은 언제 정당한가

▾

id를 애플리케이션 밖에서 발급받는 것도 분명히 유효한 선택지다. 다만 이 문항의 답으로는 순서가 뒤바뀐 선택이라, "언제 정당한가"를 정확히 구분하는 것이 중요하다.

정당한 경우 — 분산 ID가 실제로 필요한 상황.

  • DB를 샤딩했다. 샤드마다 auto_increment를 돌리면 id가 충돌하거나 범위를 쪼개 관리해야 한다. 이때는 전역 유일 id 발급기가 요구사항 자체다.
  • DB에 넣기 전에 id가 필요하다. 이벤트를 먼저 발행하거나, 여러 저장소에 같은 식별자로 기록해야 하는 경우다.
  • id로 규모를 추정당하면 곤란하다. auto_increment는 연속이라 외부에 노출하면 건수가 드러난다. 이때는 id 전략이 성능이 아니라 보안 요구사항이다.

정당하지 않은 경우 — "이 배치 하나가 느려서".

  • 가용성이 결합된다. Redis가 죽으면 채번이 막혀 배치가 못 돈다. 원래 DB만 있으면 되던 일에 장애 지점이 하나 늘어난다.
  • 운영 대상이 늘어난다. 모니터링, 백업, 버전 업그레이드, 장애 대응 절차가 따라 붙는다. 배치 하나의 성능이 인프라 팀의 상시 부담으로 바뀌는 것은 비싼 거래다.
  • 정합성 사고의 복구가 어렵다. Redis가 리셋되거나 페일오버 과정에서 카운터가 되감기면 중복 id가 발급된다. PK 충돌이면 그나마 낫고, 다른 테이블에서 이미 그 id를 참조했다면 데이터 정정이 필요해진다.
  • 무엇보다 TABLE 제너레이터 + allocationSize가 같은 문제를 인프라 추가 없이 푼다(§4-1). 인프라를 늘리지 않고 되는 일을 늘려서 하는 것은 설계에서 감점 요인이다.

UUID를 쓰면 되지 않느냐는 흔한 반문인데, 여기엔 성능 축의 함정이 있다. MySQL InnoDB는 PK 순서로 데이터를 물리 정렬해 저장하므로, 무작위 값이 PK가 되면 새 행이 인덱스 중간중간에 끼어들어 페이지 분할이 잦아진다. 대량 적재에서는 이 비용이 특히 크게 나타난다. 정렬 가능한 형태(시간 순서가 앞에 오는 UUID 변형이나 스노우플레이크 계열)를 쓰면 완화되지만, PK 폭이 커져 모든 보조 인덱스가 함께 커진다는 대가는 남는다. (가산점 포인트)

한 문장으로: "외부 채번은 분산 ID가 요구사항일 때의 답이지, 배치가 느릴 때의 답은 아니다."

9

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

세 가지를 순서대로 확인한다. 순서에 이유가 있다.

  1. ID 생성 전략 — IDENTITY면 여기서 끝이다. 배치가 안 켜진 게 아니라 묶을 대상이 없는 것이므로 다른 걸 아무리 봐도 소용없다(§3).
  2. order_inserts — 여러 종류의 엔티티를 함께 저장한다면 문장이 섞여 배치가 잘게 끊긴다(§4-2).
  3. JDBC URL의 rewriteBatchedStatements — MySQL이면 반드시. 그리고 이건 하이버네이트 로그로는 확인되지 않으므로, 서버 측 로그나 p6spy/datasource-proxy로 층을 내려가 봐야 한다(§5).

추가로 짚을 것: "로그에 100만 줄"이라는 관측 자체가 근거로는 약하다. show_sql은 배치 여부를 보여주는 도구가 아니라서, 배치가 잘 될 때도 문장은 한 줄씩 찍힌다. 그래서 판단 근거는 로그 줄 수가 아니라 실행 시간과 Statistics 카운트여야 한다.

대개 괜찮고, 안 괜찮은 경우가 언제인지 아는 것이 핵심이다.

allocationSize만큼 미리 선점하므로, 애플리케이션을 재시작하면 남은 번호는 버려진다. 즉 id가 1000, 1001, ... 1523, 2001, ...처럼 뛴다.

  • PK는 유일하기만 하면 되므로 기술적으로는 문제가 없다. 조인·인덱스·조회 성능 어디에도 영향이 없다.
  • 문제가 되는 경우는 id를 업무적으로 해석할 때다. "id로 건수를 센다", "id 순서가 곧 접수 순서다", "고객에게 보여주는 번호다" 같은 사용이 있으면 곤란해진다. 그런 요구가 있다면 PK와 별도로 업무 번호 컬럼을 두는 것이 정석이다 — 기술 식별자와 업무 식별자를 겸용하던 것이 애초의 문제이기 때문이다.
  • 정산 배치의 자연 키는 어차피 (정산일자, 거래ID) 다(§6-3). PK가 무엇이든 업무적 동일성은 그 조합이 판단하므로 구멍은 무해하다.

효과는 금방 포화하고, 대가는 계속 커진다.

채번 왕복은 건수 / allocationSize이므로 1 → 1000에서 이미 1/1000이 된다. 1000 → 10만으로 더 올려봐야 줄어드는 왕복은 1000번에서 10번으로, 전체 소요 시간에서 차지하는 비중이 이미 무의미한 수준이다. 최적화는 지배적인 비용에 해야 하는데, 이 지점에서 지배적인 비용은 더 이상 채번이 아니다.

반면 대가는 커진다.

  • 재시작마다 버려지는 구간이 커진다. 매일 배포하는 서비스라면 id가 빠르게 소진되고, int 범위를 쓰고 있었다면 한계에 도달하는 시점이 앞당겨진다.
  • 여러 인스턴스가 도는 경우 구간이 크게 엇갈린다. 정렬성이 나빠져 인덱스 삽입 지역성이 떨어질 수 있다.
  • 채번 테이블 경합은 이미 해결된 상태라 더 얻을 것이 없다.

여기서 진짜 보고 싶은 것은 숫자가 아니라 판단 방식이다 — "어느 비용이 지배적인지 측정하고, 지배적인 것만 건드린다." ①~③을 다 하고 나면 지배적인 비용은 대개 DB 측의 인덱스 유지와 로그 기록으로 옮겨가 있고, 그때부터는 애플리케이션 설정이 아니라 적재 중 보조 인덱스를 잠시 떼고 나중에 붙이는 것 같은 DB 작업이 다음 카드가 된다.

clear()가 영속성 컨텍스트를 통째로 비우기 때문이다. 배치와 무관하게 그 트랜잭션에서 다루던 엔티티들도 함께 준영속(detached) 이 된다.

  • 지연 로딩이 터진다. clear() 이전에 조회해 둔 가맹점 엔티티의 연관을 이후에 건드리면 LazyInitializationException이 난다.
  • 변경 감지가 사라진다. clear() 전에 수정해 둔 값이 flush 대상에서 빠져 UPDATE가 조용히 사라진다. 예외조차 안 나서 더 위험하다.
  • 동일성이 깨진다. clear() 후 같은 id를 다시 조회하면 다른 인스턴스가 나온다. == 비교에 의존한 코드가 조용히 오동작한다.

처방은 두 가지다. ① 배치 로직을 다른 엔티티 조작과 섞지 않는다 — 청크 로더는 "DTO를 받아 엔티티를 만들어 저장한다"만 하게 한다. ② 꼭 참조가 필요하면 엔티티를 들고 다니지 말고 id(또는 값 객체)를 들고 다니다가 필요한 시점에 다시 조회한다.

이 성질은 벌크 연산의 clearAutomatically가 만드는 부작용과 정확히 같은 것이다(→ 벌크 연산과 영속성 컨텍스트).

아니다. 그 지점에서 병목은 애플리케이션을 떠나 DB로 이동해 있다. 여기서부터는 튜닝 대상이 바뀐다는 것을 아는지가 변별점이다.

  • 인덱스 유지 비용이 지배적이 된다. 행마다 모든 보조 인덱스를 갱신해야 하기 때문이다. 그래서 대량 적재 전에 보조 인덱스를 떼고 적재 후 다시 만드는 전략을 쓴다 — 다만 그 사이 해당 테이블의 조회 성능이 무너지므로, 신규 테이블이거나 적재 중 조회가 없는 배치 윈도우에서만 가능하다.
  • PK 순서가 중요해진다(§8). 정렬된 순서로 넣으면 페이지 분할이 줄어든다. 입력 데이터를 PK 기준으로 정렬해서 넣는 것만으로 개선되는 경우가 있다.
  • LOAD DATA INFILE이 다음 카드다. INSERT 문 파싱 자체를 건너뛴다(§4-4).
  • 트랜잭션 로그·복제 지연도 본다. 대량 적재는 복제 지연을 만들어 읽기 replica를 보는 서비스에 영향을 준다. 그래서 배치 윈도우를 나누거나 속도를 일부러 제한 (throttling)하기도 한다 — "가장 빠른 것"이 아니라 "다른 트래픽을 안 죽이는 선에서 충분히 빠른 것"이 배치의 목표라는 감각이다.

정리하면: 애플리케이션 층의 카드(①~④)를 다 쓴 다음의 카드는 DB 층의 카드이며, 그 카드들은 대부분 다른 사용자에게 영향을 주는 결정이라 혼자 정할 수 없다.

설정으로 얻은 성능은 설정이 지워지면 사라지고, 그 사실은 로그에 남지 않는다. 그래서 세 가지를 코드로 고정한다.

  1. 쿼리 수 단정 테스트 — SQLStatementCountValidator.assertInsertCount(...)나 Statistics.getPrepareStatementCount()로 1000건 적재 시 문장 수가 임계 이하임을 단정한다. 누군가 ID 전략을 IDENTITY로 되돌리면 테스트가 즉시 실패한다.
  2. 설정 존재 자체를 단정 — JDBC URL의 rewriteBatchedStatements=true, hibernate.jdbc.batch_size, order_inserts 값을 검사한다(§5-4). 우스운 테스트지만, 로그로 확인할 수 없는 설정을 잡는 유일한 장치다.
  3. 실제 DB로 검증 — H2에서는 배치 재작성도, MySQL 특유의 동작도 재현되지 않는다. Testcontainers로 실제 MySQL을 띄운다.

여기에 운영 관측을 하나 더 붙이면 완성이다 — 배치 잡의 처리 건수와 소요 시간을 매 실행 기록하고, 임계치를 넘으면 알림. 성능 회귀는 어느 날 갑자기가 아니라 서서히 오기 때문에, 추세를 보는 지표가 없으면 "원래 이렇게 오래 걸렸나?"로 넘어간다.

💡

이것이 이 문항에서 배울 수 있는 가장 이식성 높은 교훈이다 — 주장으로 남긴 설계 원칙은 언젠가 지워지고, 테스트로 고정한 원칙만 살아남는다.

✅ 한 줄 요약

100만 건이 2시간인 이유는 두 갈래다 — 왕복 100만 번과 영속성 컨텍스트에 엔티티·스냅샷 100만 벌이 누적되어 뒤로 갈수록 느려지는 것. 첫 처방으로 "JPQL 벌크 INSERT"는 성립하지 않고(JPQL에 INSERT 문이 없다, insert into ... select 제외), saveAll()도 내부는 루프라 왕복이 그대로다. hibernate.jdbc.batch_size를 켜도 IDENTITY면 한 건도 묶이지 않는다 — 1차 캐시의 키가 식별자라 id 없이는 영속 상태를 만들 수 없고, 그래서 persist()가 즉시 INSERT를 날려 쓰기 지연 자체가 성립하지 않기 때문이다(같은 이유로, 영속성 컨텍스트가 없는 JdbcTemplate은 같은 auto_increment에서도 배치가 잘 된다). 처방은 JPA를 버리는 것이 아니라 순서대로 조이는 것이다 — ① ID 전략을 SEQUENCE/(MySQL이면) TABLE + 큰 allocationSize 로 바꿔 채번을 미리 받아 INSERT를 미루고 ② batch_size + order_inserts/ order_updates 로 같은 테이블끼리 모아 실제로 묶고 ③ 배치 크기마다 flush() + clear() 로 힙과 전건 대조를 잘라내고 ④ 그래도 부족하면 JdbcTemplate.batchUpdate 또는 LOAD DATA INFILE. MySQL이면 JDBC URL의 rewriteBatchedStatements=true 가 없는 한 드라이버가 문장을 하나씩 보내는데, 이건 하이버네이트 로그로는 절대 확인되지 않으므로(로그는 배치 여부를 보여주지 않는다) Statistics → p6spy → 서버 측 로그로 관측의 층을 내려가야 한다. 성능이 잡혀도 설계가 남는다 — 100만 건을 트랜잭션 하나로 묶지 않고(undo 로그 팽창, 락 보유, 전량 롤백), 청크 단위 커밋 + (정산일자, 거래ID) 유니크 키 기반 upsert로 재실행 가능하게 만든다. 그리고 아래로 내려가는 데에는 대가가 있다 — Auditing 미적용, 엔티티 검증·도메인 로직 우회, 영속성 컨텍스트 불일치, 타입 안전성 상실, 테스트 방식 변경. 그래서 실무의 답은 전면 교체가 아니라 배치 전용 클래스로 경계를 좁히고, 그 경계를 테스트로 고정하는 것이다.
