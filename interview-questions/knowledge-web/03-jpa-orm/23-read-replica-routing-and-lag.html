read replica 라우팅과 replication lag
코드에는 버그가 없는데 "쓰고 바로 읽으면 없어요"

면접 질문: "멀티 DB(read replica) 환경에서 @Transactional(readOnly = true) 기반 라우팅을 어떻게 구현하나요? replication lag은 어떻게 다루나요?"

핵심 관전 포인트 — 라우팅의 골격은 세 조각이다: AbstractRoutingDataSource를 상속해 determineCurrentLookupKey()에서 TransactionSynchronizationManager.isCurrentTransactionReadOnly()를 읽고 마스터/리플리카 키를 돌려준다. 그런데 이것만 붙이면 대개 동작하지 않는다. 스프링은 트랜잭션을 시작하는 처리(doBegin) 안에서 커넥션을 먼저 확보하는데, readOnly 플래그를 트랜잭션 동기화에 올리는 것은 그 다음 단계(prepareSynchronization)라서, 라우팅 판단이 항상 플래그가 서기 전에 일어나 기본값(마스터)으로 잡힌다. LazyConnectionDataSourceProxy로 감싸 실제 쿼리가 나가는 순간까지 커넥션 획득을 미뤄야 비로소 라우팅이 걸린다 — "리플리카로 안 가는데요"의 1순위 원인이다. 그리고 @Transactional이 아예 없는 조회는 라우팅 자체를 못 탄다 — 트랜잭션 밖에는 readOnly 정보가 존재하지 않기 때문이다. 그래서 규율이 필요하고, 규율은 사람이 아니라 ArchUnit 룰과 런타임 카운터로 고정한다. lag 쪽은 "애플리케이션이 지연을 알 수 없다"는 전제부터 틀렸다 — PostgreSQL은 pg_stat_replication.replay_lag, pg_last_xact_replay_timestamp(), 그리고 더 정확하게는 하트비트 테이블로 밀리초 단위 실측이 가능하고, 그 값이 곧 임계치를 넘으면 마스터로 우회하는 라우팅 재료가 된다. 마지막이 결론이다 — 읽기 일관성은 하나의 처방이 아니라 층으로 쌓는다: ① 쓰기 응답에 결과를 담아 재조회를 없애고 ② 쓴 직후 몇 초간 그 사용자의 요청만 마스터로 보내고 ③ 정합성 필수 조회만 마스터를 강제하고 ④ 지연 초과 리플리카를 풀에서 뺀다. 단, ④에는 반드시 상한과 폴백이 함께 와야 한다 — 리플리카를 다 빼면 그 부하를 마스터가 전부 받는다. 장애 대응이 장애를 만드는 전형이다.
  • 1
    라우팅 골격은 네 조각이고, 네 번째가 관문이다 — AbstractRoutingDataSource 상속 → determineCurrentLookupKey()로 키 반환 → isCurrentTransactionReadOnly()를 읽고 판단 → 전체를 LazyConnectionDataSourceProxy로 감싼다. 감싸지 않으면 커넥션이 doBegin() 안에서 잡히고 플래그는 그 뒤에 서기 때문에 전부 마스터로 간다.
  • 2
    복제 지연은 "어쩔 수 없는 것"이 아니라 측정 대상이다 — 프라이머리의 replay_lag, 스탠바이의 pg_last_xact_replay_timestamp(), 그리고 하트비트 테이블로 ms 단위 실측이 가능하다. 측정되면 헬스체크 지표가 되고, 지표가 되면 "임계치 초과 시 마스터 우회"라는 라우팅 결정에 쓸 수 있다.
  • 3
    읽기 일관성은 층으로 쌓는다 — 응·창·강·제 — 응답에 결과를 담아 재조회 제거 → 쓴 직후 창(N초) 동안 그 사용자만 마스터로 → 정합성 필수 조회만 마스터 강제 → 지연 초과 리플리카 제외. 어느 층도 나머지를 대체하지 못하고, 마지막 층에는 반드시 상한과 폴백이 함께 온다.

0. 질문 + 출제 의도

질문: "멀티 DB(read replica) 환경에서 @Transactional(readOnly = true) 기반 라우팅을 어떻게 구현하나요? replication lag은 어떻게 다루나요?"

출제 의도: "쓰고 바로 읽었는데 없어요"라는, 코드에는 버그가 없는 버그. 인프라 구조가 애플리케이션 로직에 스며드는 지점을 다뤄본 경험을 확인하며, 대용량 서비스는 replica 없이 운영이 불가능하므로 사실상 필수 경험 검증이다.

"코드에는 버그가 없는 버그"
재현이 안 되고, 로컬에서는 절대 안 나오고, 테스트도 전부 통과한다. 증상에서 인프라 구조로 거슬러 올라가는 진단 능력을 본다.
"인프라가 로직에 스며드는 지점"
마스터/리플리카 분리는 인프라 결정인데, 그 결과로 코드에 readOnly 규율이 생기고, 세션에 마지막 쓰기 시각을 기록하는 로직이 생기고, 헬스체크 스케줄러가 생긴다. "인프라는 인프라 팀이 알아서"가 성립하지 않는 영역이다.
"사실상 필수 경험 검증"
일정 규모 이상에서 리플리카는 옵션이 아니다. 경험이 없다면 최소한 구현 장치의 이름과 함정은 알고 있어야 한다는 뜻이다.
함정 ① — "readOnly를 보고 DB를 고르면 됩니다"에서 멈추는 것 방향은 맞지만 이건 요구사항을 다시 말한 것에 가깝다. 면접관은 바로 "그 판단을 정확히 어디서 하나? 어떤 클래스인가?"로 들어오고, 그 다음이 진짜 관문인 LazyConnectionDataSourceProxy다.
함정 ② — lag을 "어쩔 수 없는 것"으로 두는 것 "복제 지연은 DB 특성이라 애플리케이션이 할 수 있는 게 없다"고 답하면 절반이 날아간다. 지연은 측정 가능하고, 측정되면 라우팅 결정에 쓸 수 있다. 그리고 그 조치가 새 장애를 만들지 않도록 상한을 두는 것까지가 답이다.
이 문서의 기준 환경 DB는 PostgreSQL(스트리밍 복제), 애플리케이션은 스프링 프레임워크 6.x / 스프링 부트 3.x + Hibernate 6.x를 전제로 쓴다. MySQL 고유의 지표나 어휘를 쓸 때는 그때마다 "MySQL 계열"이라고 명시한다.

1. 라우팅의 골격 — 상 · 키 · 읽 · 감

1-1. 전제 — 무엇을 나누고, 애플리케이션이 무엇을 풀어야 하나

용어부터 세운다. 마스터(master, primary, 프라이머리)는 쓰기를 받는 DB 서버다. INSERT·UPDATE·DELETE는 전부 여기로 간다. 리플리카(replica, standby, 스탠바이)는 마스터의 변경 내역을 계속 넘겨받아 자기 데이터를 같은 상태로 따라 만드는 읽기 전용 복사본 서버다. 리플리카에는 직접 쓸 수 없고, 마스터를 통해 들어온 변경만 재생(replay)한다.

왜 나누나. 대부분의 서비스는 읽기가 쓰기보다 압도적으로 많다. 상품 목록·상세·검색은 초당 수천 번 조회되지만 주문 생성은 그보다 두세 자릿수 적다. 그런데 DB 서버 한 대의 CPU와 디스크는 유한하다. 읽기만 여러 대에 나눠 태우면 마스터는 쓰기에 집중할 수 있고, 리플리카를 늘리는 것만으로 읽기 처리량을 늘릴 수 있다.

여기서 애플리케이션이 풀어야 할 문제가 생긴다. "이 SQL을 어느 서버로 보낼 것인가"를 매 쿼리마다 정해야 한다. 이 결정을 자동화하는 장치가 라우팅(routing)이고, 판단의 재료는 이미 코드에 있다 — @Transactional(readOnly = true)다. 원래 성능 힌트였던 애너테이션이 라우팅 신호로 승격되는 것이 이 문항의 출발점이다.

라우팅 골격 4조각 — 상 · 키 · 읽 · 감

상 — AbstractRoutingDataSource 상속→ 키 — determineCurrentLookupKey() 구현→ 읽 — isCurrentTransactionReadOnly()→ 감 — LazyConnectionDataSourceProxy로 감싸기

앞의 세 조각(상·키·읽)까지가 대부분이 아는 답이고, 그 상태로는 동작하지 않는다. 네 번째 감이 이 문항의 관문이다. 면접에서 세 이름(AbstractRoutingDataSource / determineCurrentLookupKey / TransactionSynchronizationManager.isCurrentTransactionReadOnly)을 정확히 말하면 "구현 장치를 안다"는 신호가 전달되고, 네 번째까지 말하면 "실제로 붙여봤다"가 된다.

1-2. 판단이 일어나는 정확한 지점

스프링에는 "커넥션을 달라고 할 때마다 어느 DataSource에서 꺼낼지 그 자리에서 고르는" DataSource가 있다. AbstractRoutingDataSource다. 구조를 보면 이 클래스가 하는 일이 놀랄 만큼 단순하다는 걸 알 수 있다.

Spring 6.2 AbstractRoutingDataSource — 핵심만 옮긴 실제 구조
public abstract class AbstractRoutingDataSource extends AbstractDataSource {

    private Map<Object, DataSource> resolvedDataSources;   // 키 → 실제 DataSource
    private DataSource resolvedDefaultDataSource;          // 키를 못 찾았을 때 쓸 기본값
    private boolean lenientFallback = true;                // 기본값에 기대도 되는가

    @Override
    public Connection getConnection() throws SQLException {
        return determineTargetDataSource().getConnection();
    }

    protected DataSource determineTargetDataSource() {
        Object lookupKey = determineCurrentLookupKey();     // ← 우리가 구현하는 곳
        DataSource dataSource = this.resolvedDataSources.get(lookupKey);
        if (dataSource == null && (this.lenientFallback || lookupKey == null)) {
            dataSource = this.resolvedDefaultDataSource;    // 조용히 기본값으로 눕는다
        }
        if (dataSource == null) {
            // lenientFallback = false 이고 키가 맵에 없으면 여기서 터진다
            throw new IllegalStateException(
                    "Cannot determine target DataSource for lookup key [" + lookupKey + "]");
        }
        return dataSource;
    }

    protected abstract Object determineCurrentLookupKey();   // 이 한 메서드가 전부다
}

핵심은 이 구조가 Map<키, DataSource> + "지금 키가 뭔지 알려주는 함수" 하나로 되어 있다는 것이다. 우리가 할 일은 그 함수를 채우는 것뿐이다.

lenientFallback — 편하지만 위험한 기본값 (짚고 넘어갈 값어치가 있다) 기본값이 true라서 키가 맵에 없으면 조용히 기본 DataSource(우리 구성에서는 마스터)로 눕는다. 즉 오타 난 키나 등록을 빠뜨린 리플리카가 아무 예외 없이 전부 마스터로 흘러간다. 목적지를 반드시 명시적으로 통제하고 싶다면 setLenientFallback(false)로 틀린 키를 시끄럽게 실패하도록 바꿀 수 있다. 다만 그러면 폴백 경로도 함께 사라지므로, 6절의 "리플리카가 다 빠졌을 때" 처리를 코드에서 직접 해야 한다.

그러면 "지금 이 트랜잭션이 읽기 전용인가"는 어디서 알 수 있나. 스프링은 트랜잭션의 현재 상태를 스레드에 묶인 전역 저장소(ThreadLocal)에 올려두는데, 그 창구가 TransactionSynchronizationManager다. 이름 그대로 "트랜잭션 동기화 관리자" — 트랜잭션에 관한 정보를 한 스레드 안의 모든 코드가 공유할 수 있게 해주는 자리다.

isCurrentTransactionReadOnly()
현재 스레드에서 진행 중인 트랜잭션이 @Transactional(readOnly = true) 인가? → 라우팅 판단의 재료
isActualTransactionActive()
애초에 트랜잭션이 열려 있기는 한가? → 3절에서 "트랜잭션 없는 조회"를 잡는 카운터의 재료가 된다
Java 두 조각을 합치면 라우팅 판단부가 나온다 (여기까지가 "동작하지 않는" 상태)
public class RoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        return TransactionSynchronizationManager.isCurrentTransactionReadOnly()
                ? DataSourceKey.REPLICA
                : DataSourceKey.MASTER;
    }
}
여기까지가 틀린 답이다 — 정확히는 "여기까지만 하면 동작하지 않는다." 그 이유가 2절이다

1-3. 설정 ① — DataSource 빈과, 조용히 늘어나는 커넥션 총량

먼저 물리 DataSource를 만든다. Spring Boot의 자동 설정에 맡기면 DataSource가 하나만 만들어지므로 직접 만든다.

      password: ${DB_PASSWORD}

      jdbc-url: jdbc:postgresql://replica-2.internal:5432/shop

Java DataSourceConfig — 물리 DataSource 세 개
public enum DataSourceKey { MASTER, REPLICA1, REPLICA2 }

@Configuration
public class DataSourceConfig {

    @Bean @ConfigurationProperties("datasource.master")
    public DataSource masterDataSource() {
        return DataSourceBuilder.create()
                .type(HikariDataSource.class).build();
    }

    @Bean @ConfigurationProperties("datasource.replicas.replica1")
    public DataSource replica1DataSource() { /* 동일 */ }

    @Bean @ConfigurationProperties("datasource.replicas.replica2")
    public DataSource replica2DataSource() { /* 동일 */ }
}
설계 포인트 — 안전망을 코드가 아니라 권한으로 거는 층 리플리카 계정을 읽기 전용 권한(app_ro)으로 따로 파는 것을 권한다. 라우팅 버그로 쓰기가 리플리카로 흘러가면 DB가 거부해서 시끄럽게 실패한다. 조용히 잘못 동작하는 것보다 낫다. (PostgreSQL 스탠바이는 애초에 읽기 전용이라 쓰기가 cannot execute INSERT in a read-only transaction으로 거부되지만, 권한을 따로 파두면 승격(failover)으로 그 서버가 쓰기 가능해진 뒤에도 같은 보호가 유지된다.)

1-4. 설정 ② — 라우팅 DataSource의 세 갈래, 그리고 순서

Java RoutingDataSource — 판단은 세 갈래이고 순서가 의미를 가진다
public class RoutingDataSource extends AbstractRoutingDataSource {

    private final ReplicaRegistry replicaRegistry;   // 건강한 리플리카 목록 + 순번

    @Override
    protected Object determineCurrentLookupKey() {
        DataSourceKey key = decide();
        MDC.put("dsKey", key.name());          // 로그로 어디로 갔는지 남긴다 (7-1)
        RoutingMetrics.count(key);             // 마스터로 새는 조회 비율 관측 (7-5)
        return key;
    }

    private DataSourceKey decide() {
        // ① 명시적 마스터 강제가 걸려 있으면 무조건 마스터 (5-3, 5-4)
        if (MasterRouteContext.isForced()) {
            return DataSourceKey.MASTER;
        }
        // ② 읽기 전용 트랜잭션이 아니면 마스터
        if (!TransactionSynchronizationManager.isCurrentTransactionReadOnly()) {
            return DataSourceKey.MASTER;
        }
        // ③ 건강한 리플리카 중 하나. 하나도 없으면 마스터로 폴백 (6절 전체를 부르는 한 줄)
        return replicaRegistry.next().orElse(DataSourceKey.MASTER);
    }
}
①
마스터 강제가 맨 앞인 이유 — "이 조회만은 반드시 최신값이어야 한다"는 요구는 readOnly 여부보다 강하다. readOnly = true 트랜잭션이면서도 마스터로 가야 하는 경우가 실재한다(5-4의 잔액 조회).
②
읽기 전용이 아니면 마스터 — 판단 재료가 isCurrentTransactionReadOnly() 하나이므로, 트랜잭션이 없으면 이 값도 false가 되어 자동으로 마스터행이다(3절).
③
orElse(MASTER)가 부르는 것 — 리플리카가 전부 빠졌을 때 조회를 실패시키는 대신 마스터로 보낸다. 가용성을 택한 것이고, 그 대가가 6-1의 "마스터가 전부 받는다"이다. 이 한 줄이 폴백 설계 전체를 부르는 지점이라 그냥 지나치면 안 된다.
Java 빈 등록 — 키 → DataSource 맵과 기본값
@Bean
public DataSource routingDataSource(DataSource masterDataSource,
                                    DataSource replica1DataSource,
                                    DataSource replica2DataSource,
                                    ReplicaRegistry replicaRegistry) {

    RoutingDataSource routing = new RoutingDataSource(replicaRegistry);

    Map<Object, Object> targets = new EnumMap<>(DataSourceKey.class);
    targets.put(DataSourceKey.MASTER,   masterDataSource);
    targets.put(DataSourceKey.REPLICA1, replica1DataSource);
    targets.put(DataSourceKey.REPLICA2, replica2DataSource);

1-5. 설정 ③ — 리플리카가 여러 대일 때 고르기

리플리카 2대를 번갈아 쓰려면 순번을 도는 선택기가 필요하다. 헬스체크(4-5)와 붙여 "건강한 것 중에서만 고르는" 형태로 만든다.

Java ReplicaRegistry — 초고빈도 경로라 락을 걸 수 없다
@Component
public class ReplicaRegistry {

    private static final List<DataSourceKey> ALL =
            List.of(DataSourceKey.REPLICA1, DataSourceKey.REPLICA2);

    /** 헬스체크 스케줄러가 갱신한다. 읽기는 초당 수천 번이므로 락 없이 읽어야 한다. */
    private volatile List<DataSourceKey> healthy = ALL;

    private final AtomicInteger cursor = new AtomicInteger();

    public Optional<DataSourceKey> next() {
        List<DataSourceKey> candidates = this.healthy;    // 스냅샷을 한 번만 읽는다
        if (candidates.isEmpty()) {
            return Optional.empty();
        }
        // getAndIncrement 는 Integer.MAX_VALUE 를 넘으면 음수가 된다 → floorMod 로 방어
        int i = Math.floorMod(cursor.getAndIncrement(), candidates.size());
        return Optional.of(candidates.get(i));
    }

    void updateHealthy(List<DataSourceKey> next) {        // 4-5 의 헬스체커가 호출
        this.healthy = List.copyOf(next);                 // 통째로 갈아끼운다
    }
}

volatile + 통째 교체 가산점

목록을 그 자리에서 수정하지 않고 새 불변 리스트로 갈아끼운다. 라우팅 경로는 모든 쿼리마다 지나가는 초고빈도 경로라 락을 걸면 안 되고, 읽는 쪽이 중간 상태를 보면 안 된다.

candidates를 지역 변수로 한 번만 읽기 가산점

healthy.isEmpty()와 healthy.get(i) 사이에 스케줄러가 목록을 바꾸면 IndexOutOfBoundsException이 난다. "필드를 두 번 읽지 않는다"는 습관이 여기서 값을 한다.

분배 방식으로 라운드로빈이면 충분한가? 대부분 충분하다. 요청 하나하나가 짧고 균질하면 순번 분배가 곧 균등 분배다. 지연이 큰 리플리카에 가중치를 낮게 주는 방식도 가능하지만, 지연이 큰 리플리카는 애초에 4-5에서 목록에서 빠지므로 "제외 아니면 균등"이라는 이진 정책이 운영상 단순하고 예측 가능하다. 복잡한 가중치는 장애 시 "왜 이 리플리카로 갔나"를 설명하기 어렵게 만든다.

2. 최대 함정 — 라우팅 판단이 플래그보다 먼저 일어난다

1절까지 만들고 배포하면 대개 이런 일이 생긴다.

"라우팅을 붙였는데 리플리카 쪽 QPS가 0입니다. 전부 마스터로 갑니다."

코드는 맞다. readOnly = true도 잘 붙어 있다. 그런데 안 간다. 원인은 "판단 로직"이 아니라 "판단 시점"이다. determineCurrentLookupKey()는 누군가 getConnection()을 부를 때 실행된다. 그러니 질문은 하나로 좁혀진다 — 스프링은 커넥션을 정확히 언제 가져가는가?

답은 스프링의 트랜잭션 매니저 골격 코드에 그대로 적혀 있다.

원인 AbstractPlatformTransactionManager (스프링 6.2) — 트랜잭션을 새로 시작하는 경로
private TransactionStatus startTransaction(TransactionDefinition definition, Object transaction, ...) {

    DefaultTransactionStatus status = newTransactionStatus(...);

    doBegin(transaction, definition);           // ① 여기서 커넥션이 잡힌다
    prepareSynchronization(status, definition); // ② readOnly 플래그는 여기서 올라간다

    return status;
}

protected void prepareSynchronization(DefaultTransactionStatus status, TransactionDefinition definition) {
    if (status.isNewSynchronization()) {
        TransactionSynchronizationManager.setActualTransactionActive(status.hasTransaction());
        TransactionSynchronizationManager.setCurrentTransactionIsolationLevel(...);
        TransactionSynchronizationManager.setCurrentTransactionReadOnly(definition.isReadOnly());  // 이 줄
        ...
    }
}
doBegin()이 prepareSynchronization()보다 먼저다 — 즉 라우팅 판단 시점에는 isCurrentTransactionReadOnly()가 아직 false이고, 결과는 언제나 마스터다

2-1. JPA에서 doBegin() 안에 커넥션이 잡히는 경로는 둘이고, 둘 다 걸린다

경로 A — readOnly "때문에"

스프링의 HibernateJpaDialect.beginTransaction()은 definition.isReadOnly()가 참이면 커넥션을 가져와 Connection.setReadOnly(true)를 걸어둔다. DB에도 "이 커넥션은 읽기 전용"이라고 알려주기 위해서다.

아이러니 — readOnly = true를 붙였다는 사실 자체가 커넥션 획득을 앞당긴다.

경로 B — 오토커밋을 끄기 위해

Hibernate의 트랜잭션 begin()은 Connection.setAutoCommit(false)를 호출하는데, 그러려면 커넥션이 있어야 한다.

읽든 쓰든 이 경로는 항상 지난다.

2-2. 두 줄 타임라인 — 이 문항의 전부

2-3. 처방 — 커넥션 획득을 실제 쿼리 시점까지 미룬다

스프링에는 이 문제를 위해 만들어진 데코레이터가 있다. LazyConnectionDataSourceProxy — 이름 그대로 "게으른 커넥션 데이터소스 프록시", 커넥션 확보를 최대한 미루는 대리인이다.

getConnection() 호출→ 껍데기 프록시만 즉시 반환→ setAutoCommit·setReadOnly는 기억만→ 첫 prepareStatement에서 물리 커넥션 획득 + 기억한 설정 일괄 적용
Before 라우팅만 등록 — 전부 마스터로 간다
@Bean
@Primary
public DataSource dataSource(DataSource routingDataSource) {
    // 커넥션이 doBegin() 안에서 잡힌다
    return routingDataSource;
}

// 증상: 리플리카 QPS = 0
// 예외 없음 · 테스트 통과 · 로그에도 아무 흔적 없음
// → "에러가 아니라 지표로만 알 수 있는" 종류의 버그
After lazy 프록시로 감싼다 — 순서가 뒤집힌다
@Bean
@Primary
public DataSource dataSource(DataSource routingDataSource) {
    return new LazyConnectionDataSourceProxy(routingDataSource);
}

// 바깥에서 보이는 DataSource = lazy 프록시
//   그 안에 라우팅 DataSource
//     그 안에 물리 DataSource 세 개
// 순서를 뒤집으면(Routing 이 Lazy 를 감싸면) 아무 의미가 없다

덤으로 따라오는 이득 — 놀고 있는 커넥션이 사라진다 가산점

LazyConnectionDataSourceProxy는 라우팅이 없어도 그 자체로 쓸 만한 도구다. 트랜잭션은 열렸지만 아직 쿼리를 하나도 안 한 구간에서 커넥션을 점유하지 않기 때문이다.

@Transactional
public void register(SignupCommand cmd) {
    validate(cmd);                           // 순수 검증 로직 300ms
    externalClient.verifyEmail(cmd);         // 외부 API 200ms
    memberRepository.save(cmd.toEntity());   // 커넥션은 여기서 처음 필요하다
}

lazy 프록시가 없으면 이 메서드는 첫 줄부터 커넥션을 잡고 500ms 동안 아무 일도 안 하면서 자리를 차지한다.

OSIV 문서와 정확히 같은 축이다 — OSIV가 트랜잭션 뒤쪽의 낭비를 만든다면, lazy 프록시가 없는 상태는 트랜잭션 앞쪽의 낭비를 만든다
두 문항을 이렇게 연결해 말하면 개별 지식이 아니라 "커넥션 점유 시간"이라는 하나의 축을 갖고 있다는 신호가 된다

2-4. lazy 프록시가 치르는 값 — "붙여봤다"로 읽히는 세 가지

커넥션을 한 번도 안 잡는 트랜잭션이 생긴다
쿼리를 하나도 실행하지 않고 끝나는 트랜잭션은 물리 커넥션을 아예 안 쓴다. 대개 이득이지만 "트랜잭션 = 커넥션 1개"를 전제로 만든 대시보드는 숫자의 의미가 달라진다. 같은 이유로 쿼리가 없었던 트랜잭션의 커밋·롤백 호출은 그냥 무시된다.
기본 커넥션 속성 확인을 위해 커넥션을 한 번 연다
껍데기 상태에서도 getAutoCommit()·getTransactionIsolation()에 답해야 하는데, 기본값을 모르면 대상 DataSource에서 커넥션을 하나 열어 확인한다. 스프링 6.1.2부터 이 확인은 기동 시가 아니라 첫 getConnection() 때 일어난다.
예외가 나는 위치가 뒤로 밀린다
DB가 죽어 있으면 원래는 트랜잭션 시작에서 즉시 실패하는데, lazy 프록시가 있으면 첫 쿼리 지점에서 실패한다. 스택트레이스가 가리키는 자리가 달라지므로 장애 분석 시 헷갈릴 수 있다.
Java 기본값을 명시하면 "확인하려고 커넥션을 여는" 과정 자체를 건너뛴다
LazyConnectionDataSourceProxy proxy = new LazyConnectionDataSourceProxy();
proxy.setTargetDataSource(routingDataSource);
// 두 값을 명시하면 기본값 조회용 커넥션을 열지 않는다
proxy.setDefaultAutoCommit(false);
proxy.setDefaultTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED);

2-5. 스프링 6.1.2의 지름길 — 그리고 그것으로 안 되는 것 가산점

LazyConnectionDataSourceProxy에 setReadOnlyDataSource(...)가 추가되어, 읽기 전용 트랜잭션이면 그 DataSource에서 커넥션을 가져오는 동작이 프레임워크에 내장됐다.

Spring 6.1.2+ 단순한 읽기/쓰기 분리는 프레임워크가 직접 지원한다
@Bean @Primary
public DataSource dataSource(DataSource masterDataSource, DataSource replicaDataSource) {
    LazyConnectionDataSourceProxy proxy = new LazyConnectionDataSourceProxy();
    proxy.setTargetDataSource(masterDataSource);        // 기본(쓰기) 경로
    proxy.setReadOnlyDataSource(replicaDataSource);     // 읽기 전용 트랜잭션이면 이쪽
    return proxy;
}

원리는 앞의 설명과 정확히 같다. 읽기 전용 트랜잭션이면 스프링이 껍데기에 setReadOnly(true)를 걸어두고, 첫 쿼리에서 물리 커넥션을 가져올 때 그 표시를 보고 읽기 전용 DataSource를 고른다.

다만 이것만으로는 이 문항이 요구하는 것을 다 못 한다 리플리카가 여러 대일 때의 분배(1-5), 지연 감시에 따른 제외(4-5), "이 조회만 마스터로"라는 예외 처리(5-4)가 전부 빠져 있다. 그래서 실무 구성은 setReadOnlyDataSource에 라우팅 DataSource를 물리거나, 앞서 만든 Lazy(Routing(...)) 구조를 그대로 쓴다. 답변에서는 "프레임워크가 단순한 읽기/쓰기 분리는 이제 직접 지원하지만, 리플리카 선택과 지연 대응은 여전히 우리 몫"이라고 정리하면 정확하다.
확인 범위 — 추론이 아니라 관측으로 확정한다 시니어 변별 위 타임라인은 스프링 6.2 / Hibernate 6.6의 AbstractPlatformTransactionManager, HibernateJpaDialect, LogicalConnectionManagedImpl 코드를 근거로 쓴 것이다. 다만 정확한 호출 순서는 트랜잭션 매니저 종류(DataSourceTransactionManager / JpaTransactionManager)와 Hibernate의 커넥션 획득 모드(hibernate.connection.handling_mode), hibernate.connection.provider_disables_autocommit 설정에 따라 달라질 수 있다. 우리 환경에서 실제로 어떻게 도는지는 7-1의 "라우팅 키를 MDC에 넣어 로그로 찍기"로 5분이면 끝난다. 면접에서도 "정확한 순서는 매니저 구현에 따라 다를 수 있어 라우팅 키를 로그로 확인한다"고 붙이면 오히려 신뢰도가 올라간다.

3. 규율은 사람이 아니라 빌드가 지킨다

3-1. @Transactional이 없는 조회는 라우팅을 못 탄다

라우팅 판단의 재료가 isCurrentTransactionReadOnly() 하나다. 그런데 트랜잭션이 아예 없으면 이 값은 그냥 false다. "읽기 전용이 아니다"가 아니라 "읽기 전용이라는 정보 자체가 없다"이고, 결과는 마스터행이다.

Before 라우팅을 못 탄다
@Service
public class PostQueryService {

    // @Transactional 없음 → readOnly 정보가 존재하지 않는다
    public List<PostSummary> list(Pageable pageable) {
        return postRepository.findSummaries(pageable);
    }
}
After 조회 서비스 메서드에는 반드시 붙인다
@Service
public class PostQueryService {

    @Transactional(readOnly = true)
    public List<PostSummary> list(Pageable pageable) {
        return postRepository.findSummaries(pageable);
    }
}
흔한 오해 — "Spring Data JPA 리포지토리 메서드는 내부적으로 트랜잭션이 걸려 있지 않나?" 걸려 있다. SimpleJpaRepository에 @Transactional이 붙어 있어서 리포지토리 메서드 호출은 자체 트랜잭션에서 돈다. 하지만 그건 리포지토리 메서드마다 각각 열리는 트랜잭션이고, 서비스 메서드에 아무것도 안 붙었다면 그 서비스는 한 요청에서 여러 개의 짧은 트랜잭션을 쓰는 셈이다.
  • 조회 메서드 상당수는 기본 구현의 readOnly = true 덕에 어쩌다 리플리카로 갈 수도 있다. 하지만 @Query로 직접 만든 메서드나 QueryDSL 커스텀 구현에는 그 보장이 없다.
  • 더 나쁜 것은 결과가 균일하지 않다는 것이다. 어떤 조회는 리플리카로, 어떤 조회는 마스터로 가는데 그 차이가 코드에 드러나지 않는다. "의도한 대로 도는가"를 사람이 볼 수 없는 상태가 가장 나쁘다.
readOnly = true의 무게가 달라졌다 — 이제 성능 힌트가 아니라 "어느 DB로 갈지"를 결정하는 라우팅 신호다

3-2. ArchUnit — 두 방향을 모두 거는 것이 핵심이다

"조회 메서드에는 readOnly = true를 붙이자"는 컨벤션은 팀이 커지고 시간이 지나면 반드시 새는 종류의 약속이다. 그리고 이 약속이 새면 에러가 나지 않고 조용히 마스터 부하가 늘어난다. 발견 경로가 없다. 그래서 빌드에서 막는다. ArchUnit은 구조 규칙을 테스트로 작성해 빌드에서 검사하게 해주는 라이브러리다.

정방향 — 조회에 readOnly 강제

잡는 것: 마스터로 새는 조회. 에러가 안 나므로 기계가 아니면 발견되지 않는다.

역방향 — 쓰기에 readOnly 금지 (더 무서운 쪽)

쓰기 메서드에 실수로 readOnly = true가 붙으면 변경 감지 기반 수정이 flush 자체를 건너뛰어 조용히 사라진다. 예외도 로그도 없다. 게다가 라우팅까지 붙은 지금은 그 트랜잭션이 리플리카로 가서 INSERT/UPDATE가 거부되거나, 최악의 경우 리플리카 승격 후 직접 쓰기가 들어가 복제가 깨진다.

Java DataSourceRoutingRulesTest — 빌드가 규율을 지킨다
@AnalyzeClasses(packages = "com.example",
                importOptions = ImportOption.DoNotIncludeTests.class)
class DataSourceRoutingRulesTest {

    private static final Pattern QUERY_METHOD = Pattern.compile(
            "^(find|get|search|list|count|exists|load)[A-Z].*|^(find|get|list|count)$");

    @ArchTest   // 정방향 — 조회는 readOnly 여야 한다
    static final ArchRule 조회_메서드는_readOnly_트랜잭션이어야_한다 =
            methods().that().areDeclaredInClassesThat().resideInAPackage("..service..")
                .and().arePublic()
                .and().haveNameMatching(QUERY_METHOD.pattern())
                .should(readOnlyTransactional());

    @ArchTest   // 역방향 — 쓰기에 readOnly 를 붙이면 안 된다 (더 무서운 쪽)
    static final ArchRule 쓰기_메서드에_readOnly를_붙이면_안_된다 =
            methods().that().areDeclaredInClassesThat().resideInAPackage("..service..")
                .and().arePublic()
                .and().haveNameMatching("^(save|create|register|update|modify|delete|remove|cancel)[A-Z].*")
                .should(notReadOnlyTransactional());

    private static ArchCondition<JavaMethod> readOnlyTransactional() {
        return new ArchCondition<>("@Transactional(readOnly = true) 여야 한다") {
            @Override public void check(JavaMethod method, ConditionEvents events) {
                boolean ok = method.tryGetAnnotationOfType(Transactional.class)
                                   .map(Transactional::readOnly).orElse(false);
                if (!ok) {
                    events.add(SimpleConditionEvent.violated(method,
                            method.getFullName() + " 은(는) 조회 메서드인데 "
                          + "@Transactional(readOnly = true) 가 없다 "
                          + "→ 리플리카로 라우팅되지 않고 마스터 부하가 된다"));
                }
            }
        };
    }
}

ArchUnit 룰의 한계도 같이 말해야 트레이드오프 서술이 된다

이름 규칙 기반이라 완전하지 않다
retrieveOrderHistory() 같은 이름은 패턴에 안 걸린다. 룰은 탐지율 100%가 목표가 아니라, 흔한 실수를 기계가 대신 보게 하는 장치다.
"조회처럼 생겼지만 쓰는" 메서드를 못 가른다
findOrCreate...류가 대표적이다. 이런 건 룰을 예외 처리하는 것보다 이름을 바꾸는 것이 낫다.
기존 위반이 대량이면 동결한다
FreezingArchRule.freeze(...)로 현재 위반을 동결하고 신규 위반만 빌드를 깨게 한다. 고치는 속도보다 늘어나는 속도가 빠르면 영원히 못 끝난다.

3-3. 이름 규칙이 못 잡는 것은 런타임이 잡는다

Java "트랜잭션 없이 실행된 쿼리"를 세는 카운터
@Aspect @Component
public class NonTransactionalQueryDetector {

    @Before("execution(* com.example..repository..*(..))")
    public void detect(JoinPoint jp) {
        if (!TransactionSynchronizationManager.isActualTransactionActive()) {
            Metrics.counter("db.query.no_transaction",
                            "method", jp.getSignature().toShortString())
                   .increment();
            // 운영에서는 로그 폭탄이 되므로 샘플링하거나 메트릭만 남긴다
        }
    }
}

정적 룰과 런타임 카운터는 대체 관계가 아니라 보완 관계다

ArchUnit → "규칙을 어긴 코드"를 잡는다 + 런타임 카운터 → "규칙이 미처 다루지 못한 코드"를 잡는다

이 카운터가 0이 아니면 라우팅을 못 타는 조회가 실재한다는 증거이고, 태그에 그 메서드 이름이 그대로 찍힌다. 라우팅은 틀려도 에러가 안 나는 기능이라, 이런 장치 없이 도입하는 것 자체가 설계 결함이다.

4. 복제 지연 — 정의 · 원인 · 측정

4-1. 복제 지연(replication lag)이란 정확히 무엇인가

복제 지연은 마스터에 커밋된 변경이 리플리카에서 조회 가능해지기까지 걸리는 시간차다

"지연"이라는 이름 때문에 네트워크 왕복 시간 같은 것으로 오해하기 쉬운데, 그보다 넓다. 전송에 걸린 시간 + 리플리카가 그 변경을 자기 데이터에 반영(재생)하는 데 걸린 시간을 합친 값이다. PostgreSQL의 스트리밍 복제는 세 구간을 거치는데, 각 구간의 이름을 알아두면 뒤에서 볼 측정 지표가 그대로 이해된다.

MySQL 계열이라면 — 구조는 같고 어휘만 갈아끼운다 WAL 대신 binlog, walreceiver 대신 I/O 스레드와 relay log, startup 프로세스 대신 SQL(적용) 스레드다.

4-2. "등록했는데 목록에 없어요" — 타임라인으로 보는 사고

이 버그의 성질이 고약하다 — 그래서 운영에서 처음 발견된다

로컬·개발에서 재현 불가
대개 DB가 한 대다
재현율이 낮다
사용자가 조금 느리게 움직이면 안 나타난다 → "가끔 그래요"라는 제보로만 들어온다
테스트가 전부 통과
통합 테스트도 단일 DB면 이 경로를 아예 안 지난다(7-6이 이 사각지대를 푼다)
트래픽이 늘수록 심해진다
지연은 마스터의 쓰기량에 비례 → 서비스가 잘될수록 나빠진다

4-3. 지연은 왜 커지나 — 원인 쪽도 처방 대상이다

평소 50ms가 갑자기 초 단위로 벌어지는 전형적 원인 5종 — 배 · 긴 · 조 · D · 약

배 — 대량 쓰기 배치
100만 건 INSERT가 WAL로 쏟아지면 리플리카의 재생이 못 따라간다. 새벽 배치 시간대에 지연이 튀는 이유다.
긴 — 마스터의 긴 단일 트랜잭션
한 트랜잭션이 큰 변경을 담으면 리플리카에서도 통째로 재생되어야 한다.
조 — 리플리카에서 도는 무거운 조회
통계·리포트 쿼리가 리플리카의 CPU/IO를 먹으면 재생이 밀린다 — 읽기 부하 분산이 지연을 만드는 자기모순. PostgreSQL에서는 더 직접적이다(아래 참조).
D — DDL · 스키마 변경
큰 테이블의 인덱스 추가 같은 작업.
약 — 리플리카 하드웨어가 약함
비용 절감으로 흔히 벌어진다. PostgreSQL의 재생은 단일 startup 프로세스가 순차로 수행하므로, 마스터가 여러 세션으로 병렬 처리한 쓰기를 리플리카는 한 줄로 따라잡아야 한다. 구조적으로 리플리카가 불리하다.
그래서 답변의 완성은
"지연을 어떻게 다루나"에 애플리케이션 처방만 말하면 절반이다. 지연을 만드는 쪽(배치 쓰기를 나눠 커밋, 리포트 전용 리플리카 분리)을 같이 말해야 원인과 증상을 모두 다룬 답이 된다.
PostgreSQL 고유 — 긴 조회 하나가 재생을 직접 붙잡는다 가산점 스탠바이에서 오래 도는 조회가 재생하려는 변경과 부딪히면(예: 그 조회가 보고 있는 행 버전을 VACUUM이 정리하려는 경우) PostgreSQL은 둘 중 하나를 택해야 하는데, max_standby_streaming_delay(기본 30초)만큼은 재생을 미루고 기다린다. 즉 긴 조회 하나가 그 시간만큼 지연을 직접 만든다. 그 시간이 지나면 이번엔 조회 쪽이 ERROR: canceling statement due to conflict with recovery로 취소된다. "리포트는 전용 리플리카로 떼어놓으라"는 권고가 여기서 나온다.

4-4. 오해를 깬다 — 지연은 측정할 수 있다

여기가 이 문항에서 가장 자주 틀리는 전제다. "애플리케이션은 지연을 알 수 없다"는 말은 사실이 아니다. 알 수 있다. 그것도 꽤 정확하게. 그리고 알 수 있으면 라우팅 결정에 쓸 수 있다 — 이 연결이 이 문항의 변별 지점이다.

측정 창구 3종 — 프 · 스 · 하

프 — 프라이머리의 pg_stat_replication.replay_lag 스 — 스탠바이의 pg_last_xact_replay_timestamp() 하 — 하트비트 테이블 (직접 심는 시계)

셋 중 하나를 고르는 문제가 아니다. 라우팅 판단에는 하트비트 값을 쓰고, 복제 중단이나 스탠바이 이탈 같은 굵은 이상은 pg_stat_replication으로 함께 확인하는 것이 실무 구성이다.

방법 ① — 프라이머리에서 pg_stat_replication을 본다

SQL 프라이머리에서 실행한다 — 스탠바이 하나당 한 행
SELECT application_name,
       client_addr,
       state,            -- streaming 이면 정상 스트리밍 중
       sync_state,       -- async / sync / quorum
       write_lag,        -- 스탠바이가 WAL을 받아 쓸 때까지의 시간
       flush_lag,        -- 디스크에 확정할 때까지의 시간
       replay_lag        -- 실제로 재생해 조회에 보이기까지  ← 우리가 쓸 값
  FROM pg_stat_replication;

세 지표가 4-1에서 그린 세 구간에 하나씩 대응한다는 점이 핵심이다. 세 값은 interval 타입이고, PostgreSQL 10부터 제공된다. 주의할 점이 둘이다.

프라이머리가 한가하면 값이 갱신되지 않는다

보낼 WAL이 없으면 잴 것도 없기 때문이다. (하트비트가 이 문제를 통째로 없앤다 — 4-5)

상세 컬럼을 보려면 권한이 필요하다

일반 계정은 자기 것 외의 행에서 대부분의 컬럼이 NULL로 보이므로, 모니터링 계정에 pg_monitor 역할을 부여해두어야 한다.

방법 ② — 스탠바이에서 마지막으로 재생한 트랜잭션의 시각을 본다

SQL 각 스탠바이에서 실행한다
SELECT pg_is_in_recovery() AS is_standby,          -- 여기가 스탠바이가 맞는지
       pg_last_xact_replay_timestamp() AS last_replayed_at,
       EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp())) * 1000 AS lag_ms;

pg_last_xact_replay_timestamp()는 이 스탠바이가 마지막으로 재생한 트랜잭션이 프라이머리에서 커밋된 시각을 돌려준다. 지금 시각에서 빼면 "이 리플리카는 몇 ms 전의 세상을 보고 있는가"가 나온다. 이 값의 함정을 같이 말해야 그대로 임계치에 쓰는 위험을 안다는 신호가 된다.

함정 — 프라이머리가 한가하면 지연이 계속 늘어나는 것처럼 보인다 새 트랜잭션이 없으면 마지막 재생 시각이 그대로 멈춰 있는데 now()는 계속 흐른다. 밀린 게 아니라 밀릴 것이 없는 상태인데 숫자만 보면 구분이 안 된다. 가르려면 LSN(Log Sequence Number, WAL 안의 위치)을 함께 본다 — "받은 위치"와 "재생한 위치"가 같다면 밀린 것이 없다. 
SELECT CASE
         WHEN pg_last_wal_receive_lsn() = pg_last_wal_replay_lsn() THEN 0
         ELSE EXTRACT(EPOCH FROM (now() - pg_last_xact_replay_timestamp())) * 1000
       END AS lag_ms;
NULL은 반드시 최악(제외)으로 취급해야 한다
스탠바이가 막 기동해 아무것도 재생하지 않았으면 값이 NULL이다. 숫자 비교만 하는 코드는 NULL을 조용히 무시하고 "정상"으로 판단하기 쉽다.
MySQL 계열이라면 — Seconds_Behind_Source의 세 가지 한계 SHOW REPLICA STATUS(구 명칭 SHOW SLAVE STATUS)의 Seconds_Behind_Source(구 명칭 Seconds_Behind_Master)가 같은 자리에 있다. 가장 쉽게 얻히지만 ① 해상도가 초 단위라 우리가 다루려는 1초 미만 구간에서는 전부 0으로 보이고, ② 아직 받아오지도 못한 이벤트는 계산에 안 들어가 네트워크가 막힌 가장 위험한 순간에 과소평가하며, ③ 복제가 멈추면 NULL이 된다.

4-5. 더 정확한 쪽 — 하트비트 테이블, 그리고 그것을 쓰는 헬스체커

앞의 두 방법은 DB가 알려주는 값을 그대로 받는 방식이다. 세 번째는 우리가 직접 시계를 심는 것이다. 원리는 단순하다 — 마스터에 "지금 몇 시"를 계속 적고, 리플리카에서 그 값을 읽어 현재 시각과 비교한다. 심장 박동처럼 규칙적으로 신호를 보낸다고 해서 하트비트(heartbeat)라고 부른다.

SQL · 마스터 1초마다 한 행을 갱신한다
-- 이 변경이 복제를 타고 리플리카로 흘러간다
INSERT INTO replication_heartbeat (id, beat_at)
VALUES (1, clock_timestamp())
ON CONFLICT (id) DO UPDATE
   SET beat_at = EXCLUDED.beat_at;

now()가 아니라 clock_timestamp()를 쓰는 이유가 있다. PostgreSQL에서 now()·CURRENT_TIMESTAMP는 트랜잭션이 시작된 시각을 돌려준다. 지연을 밀리초 단위로 재는 도구에서는 "측정 시점의 실제 벽시계"를 뜻하는 clock_timestamp()가 의미상 정확하다.

SQL · 각 리플리카 복제되어 온 시각과 지금을 비교
SELECT EXTRACT(EPOCH FROM
         (clock_timestamp() - beat_at)) * 1000 AS lag_ms
  FROM replication_heartbeat
 WHERE id = 1;

하트비트는 덤을 준다. 마스터가 한가해도 1초마다 쓰기가 발생하므로 4-4에서 본 "유휴 시 지연 값이 이상해지는" 문제가 사라지고, 복제 자체가 멈췄는지도 즉시 드러난다(값이 갱신되지 않으면 lag이 선형으로 증가한다).

Java 측정값을 라우팅에 쓴다 — 지연 감시 헬스체커
@Component @RequiredArgsConstructor
public class ReplicaLagHealthChecker {

    private static final long THRESHOLD_MS = 500;     // 라우팅 풀에서 뺄 기준
    private static final int  FAIL_STREAK  = 3;       // 연속 3회 초과 시 제외
    private static final int  OK_STREAK    = 5;       // 연속 5회 정상 시 복귀 (더 빡빡하게)

    private final Map<DataSourceKey, JdbcTemplate> perReplica;   // 리플리카 직결 템플릿
    private final ReplicaRegistry registry;
    private final Map<DataSourceKey, Streak> streaks = new EnumMap<>(DataSourceKey.class);

    @Scheduled(fixedDelay = 1000)
    public void check() {
        List<DataSourceKey> healthy = new ArrayList<>();

        for (var entry : perReplica.entrySet()) {
            DataSourceKey key = entry.getKey();
            long lagMs = measure(entry.getValue());       // 실패·NULL 이면 Long.MAX_VALUE
            Metrics.gauge("db.replica.lag_ms", List.of(Tag.of("replica", key.name())), lagMs);

            Streak s = streaks.computeIfAbsent(key, k -> new Streak());
            if (s.record(lagMs <= THRESHOLD_MS, FAIL_STREAK, OK_STREAK)) {
                healthy.add(key);
            }
        }
        registry.updateHealthy(capExclusion(healthy));    // 6-2 — 제외에 상한을 건다
    }
}
① 연속 횟수(streak)로 판단한다 — 히스테리시스
한 번 튄 값으로 리플리카를 빼면 깜빡이는(flapping) 라우팅이 된다. 나갔다 들어왔다 하면서 커넥션 풀이 흔들리고 원인 분석도 불가능해진다. 들어올 때의 조건을 나갈 때보다 빡빡하게 두는 것이 정석이고, 이렇게 나가는 기준과 들어오는 기준을 다르게 두는 방식을 히스테리시스(hysteresis)라고 부른다 — 온도 조절기가 설정 온도 근처에서 계속 켜졌다 꺼졌다 하지 않게 하는 것과 같은 장치다.
② 측정 실패는 최악으로 친다
쿼리가 타임아웃 나거나 NULL이면 Long.MAX_VALUE. "모르면 건강하다"는 기본값은 헬스체크에서 가장 흔한 사고 원인이다.
③ 헬스체크는 라우팅을 타면 안 된다
리플리카 각각에 직접 붙는 JdbcTemplate을 써야 한다. 라우팅 DataSource로 헬스체크를 하면 어느 리플리카를 재고 있는지 알 수 없다.
④ 지표는 반드시 리플리카별로 남긴다
태그에 replica를 달아두면 "한 대만 아픈지, 전부 아픈지"가 그래프에서 즉시 갈린다 — 6-2의 판단(개별 문제 vs 시스템 문제)이 이 태그 하나에 달려 있다.

하트비트의 전제와 한계도 정직하게 말한다

시계 동기화가 전제다
시각을 비교하는 방식이므로 NTP 동기화가 전제다. 시계가 어긋나면 지연이 음수로 나오는데, 음수가 나온다는 것 자체가 시계 문제의 탐지 신호이므로 그대로 알람을 걸어두면 된다.
해상도는 하트비트 주기가 결정한다
1초마다 찍으면 측정 오차도 최대 1초 수준이다. 더 정밀하게 보려면 주기를 줄여야 하고, 그만큼 마스터 쓰기와 WAL이 늘어난다.

널리 쓰이는 표준 기법이라 Percona Toolkit의 pt-heartbeat 같은 도구가 있다. 직접 만들기 전에 이미 있는 도구를 먼저 보는 것도 답변에 넣을 만하다.

5. 읽기 일관성은 층으로 쌓는다 — 응 · 창 · 강 · 제

여기가 이 문항의 결론부다. "lag은 어떻게 다루나"에 처방을 하나만 대면 반드시 구멍이 남는다.

"층으로 쌓는다"는 말이 추상적으로 들릴 수 있으니 먼저 뜻을 못 박자. 각 처방은 서로 다른 상황을 덮고, 어느 하나도 나머지를 대체하지 못한다. 그래서 우선순위대로 겹쳐 깔고, 아래 층이 못 막은 것을 위 층이 받는 구조로 만든다는 뜻이다. 방수 공사에서 한 겹으로 안 되면 여러 겹을 겹쳐 바르는 것과 같다.

5-1. 층 ① — 쓰기 응답에 결과를 담는다

가장 먼저 시도할 처방이다. lag을 우회하는 게 아니라 lag을 만나는 상황 자체를 없앤다.

Before 쓰고 나서 다시 읽는다 — 그 사이에 lag이 끼어든다
@PostMapping("/posts")
public ResponseEntity<Void> create(
        @RequestBody PostCreateRequest req) {
    postService.create(req);
    return ResponseEntity.created(...).build();   // 본문 없음
}

// 클라이언트: 201 을 받고 GET /posts 를 호출
//   → readOnly → 리플리카 → 새 글 없음
//   → "등록했는데 목록에 없어요"
After 쓰기 응답이 결과를 그대로 돌려준다
@PostMapping("/posts")
public ResponseEntity<PostResponse> create(
        @RequestBody PostCreateRequest req) {
    // 마스터 트랜잭션 안에서 만든 응답을 그대로 돌려준다
    PostResponse created = postService.create(req);
    return ResponseEntity.created(...).body(created);
}

// 클라이언트: 응답의 데이터를 목록 맨 위에 끼워 넣는다
//   → 재조회 없음 → lag 무관

이 처방의 좋은 점은 읽기 일관성 문제를 "해결"하는 게 아니라 "발생시키지 않는다"는 것이다. 마스터 부하도 안 늘고, 라운드트립도 하나 줄어든다. 대신 못 덮는 범위가 분명하다 — 목록 전체를 보여주는 화면, 다른 화면으로 이동한 뒤의 조회, 집계·카운트가 함께 바뀌는 경우("내 글 수 12 → 13"), 다른 기기·다른 탭, 그리고 결정적으로 개발자가 매 API마다 이걸 판단해야 한다는 것. 판단이 누락된 화면은 지연이 커지는 순간 조용히 깨진다.

①은 훌륭한 첫 층이지만 마지막 층일 수 없다

5-2. 층 ② — 쓴 직후 N초간, 그 사용자의 요청만 마스터로

이 문항 전체에서 가장 값어치 있는 한 줄 "방금 쓴 사람만" 잠깐 마스터로 보낸다. 전체 트래픽에서 그런 사용자는 극소수라 마스터 부하는 거의 안 늘고, 정작 문제가 되는 사용자 경험은 전부 사라진다. 이렇게 특정 사용자의 요청을 한동안 같은 곳으로 붙여두는 방식을 스티키(sticky, 끈끈한) 라우팅이라고 부르고, 목표를 부르는 이름이 read-your-writes(자기가 쓴 것은 자기가 읽을 수 있다)다.
Java (1/3) 쓰기가 커밋되면 그 시각을 기록한다
@Aspect @Component
public class WriteMarkAspect {

    /** 쓰기 트랜잭션이 '커밋된 뒤'에 표시를 남긴다. 롤백되면 남기지 않는다. */
    @Around("@annotation(org.springframework.transaction.annotation.Transactional) "
          + "&& within(com.example..service..*)")
    public Object mark(ProceedingJoinPoint pjp) throws Throwable {
        Object result = pjp.proceed();

        if (TransactionSynchronizationManager.isSynchronizationActive()
                && !TransactionSynchronizationManager.isCurrentTransactionReadOnly()) {
            TransactionSynchronizationManager.registerSynchronization(
                new TransactionSynchronization() {
                    @Override public void afterCommit() {
                        RecentWriteMarker.mark();     // 응답 쿠키에 커밋 시각을 심는다
                    }
                });
        }
        return result;
    }
}
afterCommit에서 기록하는 것이 핵심이다 — 롤백된 트랜잭션까지 마스터 강제를 걸면 아무 이유 없이 마스터 부하만 늘어난다
Java (2/3) 다음 요청에서 표시가 유효하면 마스터 강제
@Component
public class ReadYourWritesFilter extends OncePerRequestFilter {

    private final Duration window;   // = 관측된 지연의 p99 + 여유

    @Override
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain) {
        try {
            RecentWriteMarker.lastWriteAt(req)    // 서명된 쿠키
                .filter(at -> Duration.between(at, Instant.now())
                                      .compareTo(window) < 0)
                .ifPresent(at -> MasterRouteContext.force());

            chain.doFilter(req, res);
        } finally {
            MasterRouteContext.clear();   // 반드시 정리
        }
    }
}
Java (3/3) 요청 범위 플래그
public final class MasterRouteContext {

    private static final ThreadLocal<Boolean> FORCED
            = new ThreadLocal<>();

    public static void force() { FORCED.set(Boolean.TRUE); }

    public static boolean isForced() {
        return Boolean.TRUE.equals(FORCED.get());
    }

    public static void clear() { FORCED.remove(); }
}

// 1-4 의 decide() 가 이 플래그를 가장 먼저 본다

놓치면 사고가 되는 세부 네 가지

① ThreadLocal은 finally에서 반드시 지운다
톰캣은 스레드를 재사용하므로 안 지우면 다음 사용자의 요청까지 마스터로 간다. 트래픽이 많을수록 조용히 번지고, 증상은 "마스터 부하가 왜 안 줄지" 하나뿐이라 원인을 찾기 매우 어렵다.
② 판단은 트랜잭션이 열리기 전(필터)에 끝나야 한다
2절에서 봤듯 커넥션이 한 번 잡히면 트랜잭션 도중에는 바꿀 수 없다. 필터가 맞는 자리다.
③ 세션이 아니라 쿠키를 권한다 가산점
인스턴스가 여러 대인 환경에서 세션은 스티키 설정이나 세션 저장소가 필요하다. 쿠키는 그런 게 없다. 다만 클라이언트가 값을 조작하면 마스터로 무한히 보낼 수 있으므로 서명(HMAC)이 필요하고, 그마저 신뢰가 어렵다면 Redis에 userId → lastWriteAt을 짧은 TTL로 두는 방식이 낫다.
④ 창(window)의 길이는 감이 아니라 지표로 정한다
4-4~4-5에서 재는 지연의 상위 백분위수 + 여유를 쓰고, 지연 분포가 변하면 창도 조정한다. 창이 짧으면 문제가 남고, 길면 마스터 부하가 는다 — 이 교환 관계를 수치로 관리한다는 것이 답변의 완성이다.

층 ②가 못 덮는 것도 분명히 말한다. "다른 사용자가 즉시 봐야 하는 경우"는 여전히 남는다. 상담원이 고객의 방금 변경사항을 봐야 하는 화면이라면 쓴 사람과 읽는 사람이 달라 이 기법이 작동하지 않는다. 그런 화면은 층 ③으로 내려간다.

5-3. 층 ③ — 정합성이 필수인 조회만 마스터를 강제한다

Java 애너테이션 + 애스펙트
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequiresMaster {}

@Aspect @Component
// @Transactional 보다 먼저 실행돼야 한다
@Order(Ordered.HIGHEST_PRECEDENCE)
public class RequiresMasterAspect {

    @Around("@annotation(com.example.routing.RequiresMaster)")
    public Object around(ProceedingJoinPoint pjp)
            throws Throwable {
        boolean alreadyForced = MasterRouteContext.isForced();
        if (!alreadyForced) MasterRouteContext.force();
        try {
            return pjp.proceed();
        } finally {
            if (!alreadyForced) MasterRouteContext.clear();
        }
    }
}
Java 사용하는 쪽
@RequiresMaster
@Transactional(readOnly = true)
public Balance currentBalance(Long accountId) {
    // 잔액은 최신이어야 한다
    return accountRepository.findBalance(accountId);
}

@Order(HIGHEST_PRECEDENCE)가 중요하다. 트랜잭션이 열리기 전에 플래그가 서야 2절의 순서 문제에 걸리지 않는다. 이 애스펙트가 @Transactional보다 늦게 돌면 아무 효과가 없고 — 그리고 아무 에러도 안 난다. 관측(7-1) 없이는 발견 불가능한 부류의 버그다.

중첩 호출을 고려한 alreadyForced 처리도 놓치기 쉽다. 마스터 강제 메서드 안에서 또 다른 마스터 강제 메서드를 부르면, 안쪽이 끝날 때 플래그를 지워버려 바깥쪽의 나머지 조회가 리플리카로 샌다.

이 층의 근본 한계 — 개발자가 붙이는 것을 잊으면 아무 일도 일어나지 않는다

그래서 "정합성이 중요한 조회는 마스터로"라는 답만 단독으로 내면 부족하다. 어떤 조회가 정합성 필수인지 판별하는 기준을 함께 말해야 한다. 실무 기준은 대개 이렇다.

금전·권한처럼 되돌리기 비싼 것

관리자·상담원 화면 — 층 ②가 구조적으로 못 덮는 자리다.

5-4. 층 ④ — 지연이 큰 리플리카를 뺀다 (성격만 못 박는다)

4-5의 헬스체커가 이미 만들어둔 층이다. 이 층은 read-your-writes를 해결하지 않는다. 임계치를 500ms로 잡아도 4-2의 55ms 지연은 그대로 남아 있고, "등록했는데 목록에 없어요"는 여전히 발생한다. ④가 막는 것은 "새벽 배치 때 5초"처럼 정상 범위를 벗어난 상황에서 전체 조회 품질이 무너지는 것이다. 그리고 이 층은 혼자 두면 위험하다. 그 이유가 6절이다.

(1) 상한 전체 리플리카의 절반 미만까지만 제외한다
private List<DataSourceKey> capExclusion(List<DataSourceKey> healthy) {
    int total = ALL.size();
    if (healthy.size() >= (total + 1) / 2) {
        return healthy;                        // 정상 경로 — 아픈 것만 뺀다
    }
    // 절반 이상을 빼야 하는 상황 = 개별 리플리카 문제가 아니라 시스템 전체 문제다.
    // 이때는 "지연을 감수하고 계속 리플리카를 쓴다"가 더 나은 선택인 경우가 많다.
    Alerts.critical("복제 지연이 광범위하다. 지연 허용 모드로 전환한다.");
    Metrics.counter("db.replica.degraded_mode").increment();
    return ALL;              // 전부 되돌린다 — 느린 데이터가 없는 데이터보다 낫다
}

조건식 검산 — (total + 1) / 2가 뜻하는 것

2대
(2+1)/2 = 1 → 1대만 남아도 진행, 0대가 되면 전부 되돌림
3대
(3+1)/2 = 2 → 2대 이상 건강할 때만 제외 허용
4대
(4+1)/2 = 2 → 2대 이상 남는 선까지
판단의 근거 한 문장 — "몇 대가 아픈가"가 아니라 "무엇이 아픈가"를 보고 갈린다
한 대만 이상하면 그 리플리카의 문제이므로 빼는 게 맞고, 전부 이상하면 복제 전체의 문제이고 마스터도 이미 아프다는 뜻이므로 빼면 안 된다
(2) 마스터 폴백에 서킷 브레이커
서킷 브레이커는 실패나 부하가 임계치를 넘으면 호출 자체를 차단해 대상이 더 망가지는 것을 막는 장치다(전기 두꺼비집과 같은 발상). 폴백으로 마스터에 가는 조회가 일정 비율·건수를 넘으면 차단하고, 조회는 실패시키거나 캐시로 돌린다. 폴백은 무한 통로가 아니라 좁은 비상구여야 한다.
(3) 저하 응답을 미리 정의해둔다
장애 시 선택지를 "정확한 데이터 아니면 에러"로 두면 답이 없다. 미리 정할 것 — ① 캐시된 값 허용("3분 전 기준" 표시와 함께) ② 일부 기능 차단(실시간성 낮은 통계·추천 먼저) ③ 읽기 제한(페이지 크기 축소, 무거운 정렬/검색 차단).
(4) 사람에게 알린다
자동 조치는 시간을 벌어주는 것이지 문제를 해결하지 않는다. 제외가 발생했다는 사실 자체가 알람이어야 하고, "지연 허용 모드"로 전환됐다면 그건 최고 등급 알람이다.

6-3. 애초에 부하 이동이 감당 가능한 크기인지 계산해둔다 가산점

설계 시점에 해둘 계산이 하나 있다. 리플리카 1대가 빠지면 남은 곳에 얼마가 얹히는가? 리플리카 2대로 읽기를 나누고 있었다면, 1대가 빠지는 순간 남은 1대의 부하가 2배다. 평소 사용률이 60%였다면 120%가 되어 그 리플리카도 곧 지연이 커지고 함께 빠진다 — 연쇄 제외다.

암기할 산수 — 리플리카 N대에서 1대 이탈을 견디려면 평상시 사용률이 (N-1)/N 이하

50%
2대 구성
≈67%
3대 구성
75%
4대 구성
80%
5대 구성

대수를 늘릴수록 1대 이탈의 충격이 작아진다 — 이것이 "리플리카는 2대보다 3대"라는 운영 상식의 산수적 근거다. 2대 구성에서 각 리플리카 사용률이 50%를 넘으면 이미 여유가 없다는 뜻이고, 제외 로직을 켜둘 자격이 없는 구성이다.

이 계산을 말하면 "제외 로직을 짜봤다"를 넘어 "제외가 가능한 구성을 설계해봤다"로 읽힌다

7. 라우팅이 포기하는 것 · 관측 · 테스트

읽기 부하를 나누는 이득은 명확하다. 그 대가도 명확하다. 얻는 것만 말하면 트레이드오프 서술이 아니다.

7-1. 포기하는 것 ① — 목적지가 코드에서 안 보인다

가장 큰 대가가 이것이다. 라우팅은 개발자 눈에 안 보이게 만드는 것이 목적인 장치라, 문제가 생겼을 때도 안 보인다. 그래서 관측을 코드로 심는 것이 선택이 아니라 필수다.

Java + 로그 1-4에 이미 넣어둔 두 줄이 여기서 값을 한다
// RoutingDataSource.determineCurrentLookupKey() 안
MDC.put("dsKey", key.name());
RoutingMetrics.count(key);

# 로그 패턴에 %X{dsKey} 를 넣어두면 모든 쿼리 로그에 목적지가 찍힌다
2026-08-10 02:11:04.221 [http-nio-8080-exec-3] [dsKey=REPLICA2] DEBUG ... select p1_0.id ...

MDC(Mapped Diagnostic Context)는 로깅 프레임워크가 스레드마다 들고 다니는 작은 키-값 저장소다. 여기에 값을 넣어두면 그 스레드에서 찍히는 모든 로그 줄에 자동으로 따라붙는다.

MDC의 함정 — ThreadLocal 정리 규율과 정확히 같은 이야기 MDC는 스레드에 묶이므로 @Async나 별도 스레드로 넘어가면 값이 따라가지 않는다. 그리고 요청이 끝날 때 정리하지 않으면 다음 요청 로그에 이전 값이 남는다.

7-2. 포기하는 것 ② — 한 트랜잭션에 읽기와 쓰기를 섞을 수 없다

라우팅은 트랜잭션 단위로 결정된다. 그래서 이런 코드가 문제가 된다.

Before 무거운 조회가 쓰기 트랜잭션에 묶여 전부 마스터로
@Transactional
public void settle(Long sellerId) {
    List<Order> orders =
        orderRepository.findAllForSettlement(sellerId);  // 수십만
    // readOnly 가 아니므로 마스터.
    // 리플리카로 뺄 수 있었던 부하가 마스터에 남는다
    settlementRepository.save(calculate(orders));
}
After 조회 트랜잭션과 쓰기 트랜잭션을 분리
// 클래스 레벨 @Transactional 없음
public void settle(Long sellerId) {
    // readOnly = true → 리플리카로 간다
    List<Order> orders =
            orderQueryService.findAllForSettlement(sellerId);

    // 쓰기 트랜잭션 → 마스터로 간다
    settlementCommandService.save(calculate(orders));
}
대신 분리하면서 잃는 것 — 무조건 쪼개라고 말하면 안 된다 조회와 쓰기가 다른 트랜잭션이 되므로 그 사이에 데이터가 바뀔 수 있다. 즉 이 리팩터링은 "성능을 위해 정합성 보장 구간을 줄이는" 선택이고, 바뀌면 안 되는 경우에는 버전 검증(낙관적 락) 같은 장치가 따라와야 한다. 부하 분산과 정합성이 정면으로 부딪히는 지점이다.

7-3. 포기하는 것 ③ — readOnly를 잘못 붙이면 조용히 실패한다

변경 감지 기반 수정 — 가장 나쁜 형태

readOnly = true면 flush 자체를 건너뛰므로 예외도 없이 변경이 사라진다. 로그도, 에러도 없다.

명시적 INSERT/UPDATE — 오히려 낫다

리플리카로 라우팅된 상태라면 DB가 거부해 예외가 난다. 시끄럽게 실패한다. 1-3에서 리플리카 계정을 읽기 전용으로 파라고 한 이유가 이것이다 — 조용한 실패를 시끄러운 실패로 바꾸는 장치.

7-4. 포기하는 것 ④ — 테스트, 스키마 변경, 운영 유연성

테스트가 복잡해진다
로컬·CI에서 실제 복제 구성을 띄우는 것은 비용이 크다. 그래서 대부분의 테스트는 단일 DB로 돌고, 라우팅 경로는 테스트가 한 번도 지나지 않는다. 이 사각지대를 푸는 방법이 7-6이다.
스키마 변경 중 두 쪽의 스키마가 잠시 다르다
컬럼을 추가하면 리플리카에 반영되기 전까지 조회가 깨질 수 있다. 컬럼 추가 → 코드 배포의 순서와 하위 호환 변경만 하는 규율이 더 중요해진다.
커넥션 총량이 늘어난다
DataSource마다 풀이 따로 생긴다(1-3의 계산).
리플리카 추가·제거가 배포를 부른다
운영 중 리플리카 목록 변경이 애플리케이션 설정 변경을 요구한다. 인프라 변경이 배포를 부르는 구조가 되고, 여기서 "관리형 DB의 리더 엔드포인트를 쓰면 되지 않나"라는 꼬리질문이 나온다(8-2).

7-5. 봐야 할 지표 네 개 — 틀려도 에러가 안 나는 기능이므로

"돌아가는지"를 사람의 확인이 아니라 기계가 말해줘야 한다
지표정상 신호이상하면 의심할 것
리플리카별 지연(ms)평소 수준에서 안정배치 · 롱 트랜잭션 · 리플리카 리소스 (4-3의 다섯 원인)
라우팅 키별 쿼리 수 비율읽기 대부분이 리플리카2절의 lazy 프록시 누락, @Transactional 누락 — 이 문항의 핵심 안전망
마스터 폴백 발생 수0에 가깝게리플리카 제외가 실제로 일어나고 있다 (6-1의 시작점)
마스터 강제(force) 비율낮고 안정적ThreadLocal 미정리(5-2), 창(window) 과다
두 번째 지표가 핵심 안전망이다 — "리플리카로 가는 조회 비율"이 배포 이후 갑자기 0에 가까워졌다면 2절의 함정에 다시 빠진 것이고, 그 사실을 에러가 아니라 지표로만 알 수 있다

7-6. 통합 테스트에서 "정말 리플리카를 탔는지" 단정하는 법

실용적인 요령 — 복제를 흉내 내려 하지 말고, 복제를 아예 하지 않는다 마스터용 DB와 리플리카용 DB를 각각 띄우되 복제를 걸지 않고, 두 DB에 서로 다른 데이터를 넣는다. 그리고 조회 결과가 어느 쪽 데이터인지로 라우팅을 판정한다.
Test 데이터로 목적지를 판정하는 통합 테스트
@SpringBootTest
// 주의: 테스트 클래스에 @Transactional 을 붙이지 않는다 (아래 함정 참고)
class ReadRoutingTest {

    // Testcontainers 로 두 개의 DB 를 띄운다. 복제는 설정하지 않는다.
    @Autowired PostQueryService postQueryService;
    @Autowired @Qualifier("masterDataSource")   DataSource master;
    @Autowired @Qualifier("replica1DataSource") DataSource replica;

    @BeforeEach
    void setUp() {
        new JdbcTemplate(master) .update("insert into post(id, title) values (1, 'FROM-MASTER')");
        new JdbcTemplate(replica).update("insert into post(id, title) values (1, 'FROM-REPLICA')");
    }

    @Test void 읽기전용_트랜잭션은_리플리카로_간다() {
        assertThat(postQueryService.findTitle(1L)).isEqualTo("FROM-REPLICA");
    }

    @Test void 마스터_강제_조회는_마스터로_간다() {
        assertThat(postQueryService.findTitleRequiringMaster(1L)).isEqualTo("FROM-MASTER");
    }

    @Test void 쓰기_트랜잭션의_조회는_마스터로_간다() {
        assertThat(postCommandService.readInsideWriteTx(1L)).isEqualTo("FROM-MASTER");
    }
}

이 테스트의 가치는 2절의 함정을 CI가 잡아준다는 데 있다. 누군가 DataSource 설정을 리팩터링하다 LazyConnectionDataSourceProxy를 빼면, 운영에 나가기 전에 이 테스트가 빨갛게 된다. "리플리카로 안 갑니다"를 운영에서 발견하지 않는 유일한 방법이다.

반드시 함께 말할 함정 — 테스트 클래스에 @Transactional을 붙이면 안 된다 가산점

테스트 자체가 트랜잭션을 열어버리면 서비스 메서드의 readOnly 설정이 그 바깥 트랜잭션에 흡수되어(REQUIRED 전파) 라우팅 판단이 테스트의 트랜잭션 기준으로 정해진다. 결과가 항상 마스터로 나오면서 "라우팅이 안 된다"는 거짓 실패를 보게 된다.

OSIV 문서의 "테스트에 @Transactional을 붙이면 검증이 무의미해진다"와 똑같은 함정의 다른 얼굴이다
이 도구 상자는 3장 전체에서 반복된다 쿼리 수 단정 테스트, 경고 로그를 실패로 승격, ArchUnit 구조 룰, 프로파일을 바꿔 다시 돌리는 통합 테스트, 그리고 여기의 라우팅 키 로그·데이터로 판정하는 통합 테스트는 전부 같은 계열이다. 문제를 만나면 잘 푸는 것과, 문제가 오기 전에 잡는 장치를 만드는 것은 다른 능력이다. 라우팅은 특히 후자가 없으면 틀린 채로 몇 달을 돌 수 있는 기능이라, 안전망 없이 도입하는 것 자체가 설계 결함이다.

8. 인출 카드 · 꼬리질문 셀프 테스트

8-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

라우팅 골격 네 조각?
상·키·읽·감 — AbstractRoutingDataSource 상속 / determineCurrentLookupKey()로 키 / isCurrentTransactionReadOnly()를 읽기 / LazyConnectionDataSourceProxy로 감싸기.
"리플리카로 안 갑니다" 1순위 원인?
lazy 프록시 누락. 커넥션은 doBegin()에서 잡히고 readOnly 플래그는 그 뒤 prepareSynchronization()에서 선다 → 판단이 항상 플래그보다 이르다.
@Transactional이 없으면?
isCurrentTransactionReadOnly()가 false → 마스터행. "읽기 전용이 아니다"가 아니라 "정보 자체가 없다"이다.
지연 측정 창구 셋?
프·스·하 — 프라이머리의 pg_stat_replication.replay_lag / 스탠바이의 pg_last_xact_replay_timestamp() / 하트비트 테이블. 봐야 할 구간은 replay(받았다 ≠ 보인다).
읽기 일관성 네 층?
응·창·강·제 — 응답에 결과 담기 / 쓴 뒤 창(N초) 동안 그 사용자만 마스터 / 정합성 필수만 강제 / 지연 초과 제외. 서로 대체 불가.
층 ④의 대가?
리플리카를 다 빼면 마스터가 전부 받는다 → 풀 고갈 → 배치 지연 → WAL 밀림 → 복귀 조건 영원히 불충족. 상한 (total+1)/2 + 서킷 브레이커 + 저하 응답 + 알람.
리플리카 N대의 사용률 상한?
(N-1)/N — 2대 50%, 3대 67%, 4대 75%. 1대 이탈을 견디는 조건이고, "2대보다 3대"의 산수적 근거다.
가장 중요한 지표 하나?
라우팅 키별 쿼리 수 비율. 배포 후 리플리카 비율이 0에 가까워지면 lazy 프록시 누락이다 — 에러가 아니라 지표로만 알 수 있다.

8-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

@Transactional(readOnly = true)를 붙였는데 리플리카로 안 갑니다. 무엇부터 확인하나요? 필수힌트: 순서를 정해놓고 위에서부터 훑는다. 첫 항목이 가장 중요하다
1
LazyConnectionDataSourceProxy로 감쌌는가. 1순위다. 없으면 커넥션이 트랜잭션 시작 처리(doBegin) 안에서 잡혀 항상 기본 DataSource(마스터)로 간다.
2
감싸는 순서가 맞는가. Lazy(Routing(...))이어야 한다. 반대로 되어 있으면 효과가 없다.
3
JPA가 실제로 그 DataSource를 쓰는가. 자동 설정이 만든 DataSource가 @Primary로 남아 우리가 만든 게 무시되고 있을 수 있다.
4
트랜잭션이 실제로 걸려 있는가. 같은 클래스 안에서 메서드를 직접 호출하면(self-invocation) 프록시를 안 타서 @Transactional이 아예 적용되지 않는다. 이 경우 isActualTransactionActive()가 false다.
5
readOnly가 전파 과정에서 흡수되지 않았는가. 바깥에 readOnly = false 트랜잭션이 이미 열려 있으면 REQUIRED로 참여하면서 안쪽의 readOnly = true는 무시된다.
6
확인 수단 — 추측하지 말고 7-1의 MDC 로그를 본다. 어느 키로 갔는지가 즉시 나온다.

4번과 5번이 "라우팅 자체는 맞는데 안 가는" 두 경우라, 1~3번을 다 확인하고도 안 될 때 여기서 답이 나오는 일이 많다.

쓰기 트랜잭션 안에서 무거운 조회를 하면 그것도 마스터로 갑니다. 어떻게 하나요? 필수힌트: "쪼갠다"로 끝내면 절반이다. 쪼개면서 잃는 것이 있다

7-2 그대로다. 트랜잭션을 쪼개 조회를 별도의 readOnly 트랜잭션으로 뺀다. 다만 답을 여기서 끝내면 안 된다. 쪼개면서 잃는 것은 "조회 시점과 쓰기 시점 사이의 원자성"이다. 그 사이에 데이터가 바뀌어도 모른 채 쓰게 된다. 그래서 처방이 상황에 따라 갈린다.

조회 결과가 쓰기의 근거가 아닌 경우
정산 대상 목록을 읽어 리포트를 만드는 등 → 그냥 쪼갠다. 잃는 것이 없다.
조회 결과를 근거로 값을 계산해 쓰는 경우

마스터 풀과 리플리카 풀 크기는 어떻게 잡나요? 가산점힌트: 계산의 출발점 셋 + 이 문항 고유의 함정 하나

계산의 출발점은 세 가지다.

  • 필요 커넥션 수 = 초당 요청 수 × 커넥션 점유 시간. 읽기와 쓰기를 각각 계산한다. 읽기가 초당 1,000건이고 건당 점유가 10ms라면 1000 × 0.01 = 10개가 이론적 하한이고, 여기에 변동을 흡수할 여유를 얹는다.
  • DB 서버가 받을 수 있는 커넥션 수 ≥ (인스턴스 수 × 그 DB를 가리키는 풀 크기). 라우팅을 도입하면 이 곱셈이 DataSource 개수만큼 늘어난다는 걸 놓치기 쉽다(1-3의 800개 계산).
  • 읽기가 쓰기보다 훨씬 많으므로 리플리카 풀이 마스터 풀보다 크게 잡히는 것이 보통이다.
이 문항 고유의 함정 — 리플리카가 빠지면 그 조회가 전부 마스터로 가는데, 마스터 풀은 쓰기 기준으로 잡혀 있어 그 부하를 못 받는다

① 마스터 풀에 폴백 여유를 미리 얹는다

평상시 낭비가 생기고, 풀을 키워 버티는 방식은 DB 쪽 경합으로 문제를 옮길 뿐이다.

② 폴백에 서킷 브레이커를 건다 (정석)

애초에 다 못 들어오게 한다(6-2). 폴백은 무한 통로가 아니라 좁은 비상구여야 한다.

동기 복제로 바꾸면 lag이 없어지지 않나요? 가산점힌트: "없어진다"와 "없어지지 않는다"가 설정값에 따라 갈린다. 4-1의 세 구간을 그대로 쓴다

복제가 "어느 단계까지 기다리는지"를 나눠서 답해야 한다. 4-1에서 그린 세 구간(전송 → 확정 → 재생)이 여기서 그대로 쓰인다. PostgreSQL의 synchronous_commit 설정이 정확히 그 "어디까지 기다릴지"를 정한다.

설정값커밋이 기다리는 지점그 스탠바이에서 바로 읽으면
local / off프라이머리 자신만안 보일 수 있다
remote_write스탠바이가 WAL을 받아 쓸 때까지안 보일 수 있다
on (기본값)스탠바이가 WAL을 디스크에 확정할 때까지안 보일 수 있다
remote_apply스탠바이가 재생까지 마칠 때까지보인다
핵심 — on(기본값)조차 "받아서 저장했다"까지만 보장한다. 데이터 유실은 막아주지만 그 시점에 스탠바이의 SELECT에는 아직 안 보일 수 있다

MySQL 계열의 반동기 복제(semi-synchronous replication)도 정확히 이 자리에 있다 — 보장하는 것은 "리플리카가 이벤트를 받았다"까지이고, 적용까지는 아니다.

remote_apply만이 우리 문제를 실제로 없앤다. 그리고 그 값은 비싸다.

  • 모든 커밋이 스탠바이의 재생 완료를 기다린다. 커밋 지연 = 왕복 시간 + 스탠바이의 재생 시간. 쓰기 처리량이 직접 떨어진다.
  • 스탠바이가 느려지면 프라이머리의 쓰기 전체가 느려진다. 읽기 부하를 나누려고 둔 서버가 이제 쓰기의 성능 한계가 된다.
  • 동기 스탠바이가 응답하지 않으면 커밋이 멈춘다. synchronous_standby_names에 정족수(quorum)를 설정해 완화할 수 있지만 구성이 복잡해진다.
  • 보장 범위가 동기 스탠바이로 한정된다. 비동기로 붙은 나머지는 여전히 밀린다 — 우리 라우팅은 여러 리플리카에 분배하므로, 한 대에만 보장이 생겨도 전체 문제는 안 풀린다.

결론 한 문장: 복제 설정으로 읽기 일관성을 얻는 길이 PostgreSQL에는 존재하지만(remote_apply), 쓰기 지연과 가용성을 대가로 내야 하고 그 보장은 동기 스탠바이에만 미친다. 그래서 실무의 기본 선택은 여전히 5절의 층을 애플리케이션에서 쌓는 것이고, remote_apply는 "이 데이터만은 절대 밀리면 안 된다"는 좁은 범위에 국소적으로 쓰는 카드다.

관리형 DB(예: Aurora)는 리더 엔드포인트가 알아서 분산해주는데, 애플리케이션 라우팅이 필요한가요? 가산점힌트: 인프라가 해주는 것과 해주지 못하는 것을 갈라서 말한다

부하 분산은 인프라가 해준다. 그러나 이 문항이 다루는 문제의 대부분은 해결해주지 않는다.

인프라 엔드포인트가 해주는 것

  • 여러 리플리카에 연결을 분산한다 → 1-5의 라운드로빈이 필요 없어진다
  • 장애 난 인스턴스를 목록에서 뺀다 → "죽었는지" 판정은 대신 해준다

해주지 못하는 것

  • "이 요청은 마스터로"를 표현하지 못한다. 5-2·5-3의 read-your-writes와 마스터 강제는 애플리케이션만이 아는 정보(방금 이 사용자가 썼다 / 이 조회는 정합성이 필수다)에 기반한다
  • "살아 있지만 지연이 큰" 리플리카를 빼주지 않는 경우가 많다. 헬스체크는 대개 응답 가능 여부를 보지, 우리 서비스가 감당 가능한 지연 임계치를 보지 않는다
  • @Transactional(readOnly = true)와 연결되지 않는다. 결국 읽기용·쓰기용 DataSource를 코드에서 나눠 써야 하고, 그 판단을 자동화하는 것이 1절의 라우팅이다
정리 — "관리형을 쓰니 라우팅이 필요 없다"가 아니라 "라우팅의 대상이 개별 리플리카 주소에서 읽기 엔드포인트 하나로 바뀔 뿐"
인프라 엔드포인트는 1-5와 4-5의 일부를 대신해주고, 5절의 층 전체는 그대로 우리 몫이다
지금 리플리카 지연이 5초입니다. 무엇을 하시겠습니까? 시니어 변별힌트: 손대기 전에 확인할 것이 하나 있고, 그다음 원인을 세 갈래로 가른다

자동 조치가 이미 돌고 있다는 전제에서 시작한다. 헬스체커가 리플리카를 뺐거나(5-4), 광범위해서 지연 허용 모드로 갔거나(6-2) 둘 중 하나다. 먼저 어느 쪽인지 확인하는 것이 1번이다 — 지금 트래픽이 어디로 가고 있는지 모르는 상태로 손대면 안 된다.

그다음은 원인을 세 갈래로 가른다. 처방이 완전히 다르기 때문이다.

1
마스터의 쓰기량이 튀었나(배치·이벤트·마이그레이션) → 원인 쪽을 조절한다. 배치의 커밋 단위를 줄이거나 속도를 낮춘다. 가장 빠르고 확실한 처방인데, 애플리케이션 조치만 생각하면 이 선택지를 놓친다.
2
리플리카가 무거운 조회에 눌렸나(리포트·통계) → 그 조회를 차단하거나 전용 리플리카로 분리한다. PostgreSQL이라면 pg_stat_activity에서 그 스탠바이의 장기 실행 쿼리를 먼저 확인한다 — 4-3에서 봤듯 긴 조회 하나가 재생을 직접 붙잡고 있을 수 있다.
3
리플리카 자체 문제인가(디스크·CPU·복제 프로세스 정지) → 그 한 대를 빼고 교체한다. 1·2와 달리 한 대만의 문제이므로 제외가 정확히 맞는 처방이다.
그리고 판단해야 할 것 하나 — 지금 지연된 데이터를 보여주는 것이 더 나쁜가, 마스터를 위험에 빠뜨리는 것이 더 나쁜가?

서비스 성격에 따라 답이 다르다. 커머스의 상품 목록은 5초 전 데이터를 보여주는 편이 낫고, 결제 잔액은 틀린 값을 보여주느니 에러가 낫다. 그래서 5-3의 마스터 강제 목록이 평소에 정리돼 있어야 이 순간에 판단이 빨라진다.

마지막으로 재발 방지 항목을 남긴다. 원인이 배치였다면 배치의 쓰기 속도 상한, 리포트였다면 전용 리플리카, 공통으로 지연 지표에 사전 경보 임계치(제외 임계치보다 낮은 값)를 걸어 "빼기 직전"에 사람이 먼저 알게 만든다. 자동 조치가 발동한 것 자체가 이미 늦은 신호라는 프레임을 말하면 운영 감각으로 읽힌다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

조회 메서드에 readOnly = true를 붙였는데 그 안에서 엔티티를 수정하면 어떻게 되나요? 함정힌트: 실패 방식이 두 갈래로 갈리고, 그중 한쪽이 훨씬 나쁘다

실패 방식이 두 갈래로 갈리고, 조용한 쪽이 훨씬 나쁘다.

변경 감지로 수정한 경우 — 조용한 실패

readOnly = true면 flush 자체를 건너뛰므로 UPDATE가 아예 나가지 않는다. 예외도 로그도 없이 변경이 사라진다. 라우팅이 붙기 전에도 존재하던 함정이다.

명시적 INSERT/UPDATE인 경우 — 시끄러운 실패

리플리카로 라우팅된 상태라면 DB가 거부해 예외가 난다(cannot execute INSERT in a read-only transaction). 발견되므로 오히려 낫다.

여기에 라우팅이 얹히면서 위험이 한 단계 올라갔다는 것이 이 문항의 추가분이다. 예전에는 "변경이 안 나간다"로 끝났지만, 지금은 그 트랜잭션이 리플리카로 가버린다. 최악의 경우 리플리카가 승격된 뒤 직접 쓰기가 들어가 복제가 깨질 수 있다.

그래서 처방이 두 겹이다. ① ArchUnit 역방향 룰로 "쓰기 메서드에 readOnly 금지"를 빌드에서 막고(3-2), ② 리플리카 계정을 읽기 전용 권한으로 파서 조용한 실패를 시끄러운 실패로 바꾼다(1-3). "안전망을 코드가 아니라 권한으로도 건다"는 층 구분을 말하면 좋다.

헬스체커가 1초마다 재는데, 한 번 임계치를 넘었다고 바로 빼지 않는 이유는? 가산점힌트: 이름이 붙어 있는 장치다. 온도 조절기를 떠올린다

한 번 튄 값으로 리플리카를 빼면 "깜빡이는(flapping) 라우팅"이 되기 때문이다. 나갔다 들어왔다를 반복하면 커넥션 풀이 계속 흔들리고, 트래픽이 초 단위로 이동하며, "그때 그 요청이 어디로 갔는지"를 사후에 설명할 수 없어 원인 분석이 불가능해진다.

그래서 연속 횟수(streak)로 판단하고, 들어올 때의 조건을 나갈 때보다 빡빡하게 둔다(예: 연속 3회 초과 시 제외, 연속 5회 정상 시 복귀). 이렇게 나가는 기준과 들어오는 기준을 다르게 두는 방식을 히스테리시스(hysteresis)라고 부른다 — 온도 조절기가 설정 온도 근처에서 계속 켜졌다 꺼졌다 하지 않도록 하는 것과 같은 장치다.

같은 원리가 서킷 브레이커의 half-open, 오토스케일링의 쿨다운에도 들어 있다 — "판정 경계 근처에서 진동하지 않게 만든다"는 하나의 패턴

여기에 두 가지를 더 붙이면 답이 완성된다. ① 측정 실패·NULL은 최악으로 친다 — "모르면 건강하다"는 기본값은 헬스체크에서 가장 흔한 사고 원인이다. ② 헬스체크는 라우팅을 타면 안 된다 — 리플리카 각각에 직접 붙는 JdbcTemplate을 써야 어느 리플리카를 재고 있는지가 확정된다.

read-your-writes 창(window)을 쿠키로 두라고 했는데, 사용자가 쿠키를 조작하면요? 창 길이는 어떻게 정하나요? 가산점힌트: 두 질문 모두 "무엇을 신뢰하는가"로 수렴한다

조작 위험은 실재한다. 쿠키의 lastWriteAt을 계속 현재 시각으로 바꿔 보내면 그 클라이언트의 모든 조회가 영구히 마스터로 간다. 악의가 아니어도 버그 하나로 같은 일이 벌어질 수 있고, 증상은 "마스터 부하가 왜 안 줄지" 하나뿐이다.

  • 1차 방어 — 서명(HMAC). 서버 비밀키로 서명해 값이 변조되면 무효로 만든다. 쿠키를 쓰는 이유(인스턴스가 여러 대여도 세션 저장소·스티키 설정이 필요 없다)를 유지하면서 조작만 막는다.
  • 2차 방어 — 서버가 값을 갖는다. 신뢰가 어렵다면 Redis에 userId → lastWriteAt을 짧은 TTL로 둔다. 클라이언트는 자기 식별자만 들고 오고 판단 재료는 서버가 갖는다.
  • 공통 상한 — 마스터 강제 비율을 지표로 본다(7-5의 네 번째 지표). 비율이 튀면 조작이든 ThreadLocal 미정리든 즉시 드러난다.

창 길이는 감이 아니라 지표로 정한다. 4-4~4-5에서 재는 지연의 상위 백분위수(p99 등) + 여유를 쓰고, 지연 분포가 변하면 창도 조정한다.

그리고 창은 고정 상수가 아니라 지연 지표에 연동되는 값이라고 말하면 한 단계 위로 읽힌다
AbstractRoutingDataSource의 lenientFallback이 뭔가요? 기본값을 그대로 두면 어떤 일이 생기나요? 함정힌트: 기본값이 true다. 편하다는 것과 안전하다는 것은 다르다

lenientFallback은 "조회한 키가 맵에 없을 때 기본 DataSource로 눕는 것을 허용할지"를 정하는 스위치이고, 기본값이 true다. 즉 오타 난 키, 등록을 빠뜨린 리플리카, 리팩터링으로 사라진 enum 값이 전부 아무 예외 없이 기본 DataSource(우리 구성에서는 마스터)로 흘러간다.

이 문항 맥락에서 이게 왜 무서운가. 라우팅은 틀려도 에러가 안 나는 기능인데, lenientFallback은 틀린 것을 한 겹 더 조용하게 만든다. 증상은 "리플리카 QPS가 생각보다 낮다" 하나뿐이고, 그건 2절의 lazy 프록시 누락과 증상이 구분되지 않는다.

true로 둔다 (기본)

가용성 우선. 키가 틀려도 조회는 성공한다. 대신 7-5의 "라우팅 키별 비율" 지표가 유일한 발견 경로가 되므로 그 지표를 반드시 봐야 한다.

setLenientFallback(false)

정확성 우선. 틀린 키는 IllegalStateException으로 시끄럽게 실패한다. 대신 폴백 경로도 함께 사라지므로 "리플리카가 다 빠졌을 때"를 코드에서 직접 처리해야 한다(1-4의 orElse(MASTER)).

실무적 정리: 우리 구성은 키를 enum으로 고정하고 폴백을 코드에서 명시했으므로, 맵에 없는 키가 나올 여지 자체를 줄이는 것이 먼저다. 어느 쪽을 택하든 "조용한 마스터행"을 지표로 볼 수 있게 만들어 두는 것이 실제 방어다.

리플리카가 2대뿐인데 제외 로직을 켜도 되나요? 시니어 변별힌트: 6-3의 산수를 그대로 적용하면 답이 나온다. "켠다/끈다"의 이분법이 아니다

구성이 조건을 만족하는지 먼저 계산해야 한다. 계산 없이 켜는 것이 6-1의 시나리오를 만든다.

리플리카 N대에서 1대 이탈을 견디려면 평상시 사용률이 (N-1)/N 이하여야 한다. 2대면 50%다. 즉 각 리플리카가 평소 50%를 넘게 쓰이고 있다면, 1대를 빼는 순간 남은 1대가 100%를 넘어 곧 함께 빠진다 — 연쇄 제외다. 그리고 둘 다 빠지면 orElse(MASTER)로 읽기 전량이 마스터에 얹힌다.

2대 구성에서 사용률이 50%를 넘으면 "제외 로직을 켜둘 자격이 없는 구성"이다

그래서 답은 "켠다/끈다"가 아니라 세 갈래다.

여유가 있으면(≤50%) 켠다
단, 상한 (total+1)/2은 반드시 함께. 2대에서는 1대까지만 제외되고 0대가 되면 전부 되돌린다(6-2).
여유가 없으면 대수를 늘린다
3대면 상한이 67%로 올라간다. "리플리카는 2대보다 3대"의 근거가 이 산수다.
그래도 2대라면 — 제외 대신 알람
지연 임계치를 제외 트리거가 아니라 경보 트리거로만 쓴다. 자동 조치가 감당 불가능한 부하 이동을 만든다면, 사람이 판단하도록 남기는 편이 낫다.

이 답의 핵심은 태도다 — "제외는 부하 이동 장치이므로, 이동한 부하를 받을 여력이 계산돼 있을 때만 켠다." 자동화는 여력이 있을 때만 안전하고, 여력 없는 자동화는 장애 증폭기다.

한 줄 요약
@Transactional(readOnly = true) 기반 라우팅은 AbstractRoutingDataSource의 determineCurrentLookupKey()에서 TransactionSynchronizationManager.isCurrentTransactionReadOnly()를 읽어 키를 고르고, 그 전체를 LazyConnectionDataSourceProxy로 감싸 커넥션 획득을 실제 쿼리 시점까지 미루는 것이 골격이다. 감싸지 않으면 커넥션이 doBegin() 안에서 잡히고 readOnly 플래그는 그 뒤 prepareSynchronization()에서야 서기 때문에 판단이 항상 플래그보다 일러 전부 마스터로 간다. 조회에 readOnly = true를 붙이는 규율은 ArchUnit 룰(양방향)과 런타임 카운터로 고정하고, 복제 지연은 replay_lag·pg_last_xact_replay_timestamp()나 하트비트 테이블로 밀리초 단위 실측이 가능하며, 측정되면 "임계치 초과 시 마스터 우회"라는 라우팅 결정에 쓸 수 있다. 그리고 읽기 일관성은 하나의 처방이 아니라 응·창·강·제 — 쓰기 응답으로 재조회 제거 → 쓴 직후 그 사용자만 마스터로 → 정합성 필수 조회만 마스터 강제 → 지연 초과 리플리카 제외 — 라는 층으로 쌓되, 마지막 층에는 반드시 상한과 폴백이 함께 와야 한다. 리플리카를 다 빼면 그 부하를 마스터가 전부 받는다.
