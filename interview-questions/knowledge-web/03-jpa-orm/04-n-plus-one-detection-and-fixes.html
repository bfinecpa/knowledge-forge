N+1 문제
N의 정체, 해결책 선택 기준, 그리고 사람에 의존하지 않는 탐지 장치

면접 질문: "N+1 문제란 무엇이고 어떻게 해결하나요? (fetch join, @EntityGraph, batch size)"

핵심 관전 포인트 — 정의("목록을 조회했더니 각 행의 연관을 채우느라 쿼리가 더 나간다")는 출발점일 뿐이고, 실제로 갈리는 건 셋이다. ① N의 정체 — 추가 SELECT는 "결과 행 수"만큼이 아니라 아직 1차 캐시에 없는 서로 다른 연관 id 수만큼 나간다. 그래서 회원 1명에게 주문 1,000건을 붙인 픽스처로는 1 + 1로 끝나 재현이 안 된다. 픽스처는 건수가 아니라 카디널리티로 설계하고, 측정 직전에 컨텍스트를 비워야 한다. ② 해결책 선택 기준 — 도구 이름 4개를 외우는 게 아니라 축 하나로 정리된다. 조인 계열(fetch join·@EntityGraph)은 쿼리 1개지만 행이 뻥튀김되므로 컬렉션 + 페이징에서 금지되고 컬렉션 둘 이상도 못 쓴다. 분리 조회 계열(default_batch_fetch_size, DTO 두 번 조회 후 조합)은 쿼리가 2개 이상이지만 행이 늘지 않아 페이징과 공존한다. ③ 자동 탐지 장치 — 이 문항의 실제 관문은 여기다. "쿼리 로그를 잘 보자"는 답이 아니다. 테스트에서 쿼리 수를 단정하고, 개발·스테이징에 요청 단위 쿼리 카운터를 깔고, ArchUnit으로 EAGER 자체를 금지한다. 결론은 사고의 전환이다 — N+1은 성능 문제가 아니라 회귀(regression)다.
  • 1
    N은 "결과 행 수"가 아니다 — 추가 SELECT는 1차 캐시에 없는 서로 다른 연관 id 수만큼 나간다. 그래서 건수를 늘린 픽스처로는 재현되지 않고, 픽스처는 카디널리티로 설계하고 측정 직전에 flush() + clear()를 해야 한다. 이걸 틀리면 해결을 맞게 해도 테스트가 거짓으로 통과한다.
  • 2
    해결책은 축 하나로 갈린다 — "행이 뻥튀김되는가" — 조인 계열은 쿼리 1개지만 행이 늘어 컬렉션 + 페이징 금지 / 컬렉션 둘 이상 금지, 분리 조회 계열은 쿼리가 2개 이상이지만 행이 안 늘어 페이징과 공존한다. 그래서 기준은 "컬렉션 + 페이징이면 fetch join을 버리고 batch fetch size로 간다"이고, to-one 여럿이면 fetch join, 조회 전용이면 DTO 프로젝션이다.
  • 3
    실제 채점 지점은 "운영 전에 어떻게 발견하는가"다 — 쿼리 로그·리뷰·슬로우 쿼리 로그는 전부 사람에 의존하거나 사후다. 답은 테스트에서 쿼리 수 단정(Hibernate Statistics) + 요청 단위 쿼리 카운터(같은 SQL의 반복이 N+1의 지문) + ArchUnit으로 EAGER 금지. 프레임은 "N+1은 성능 문제가 아니라 회귀"다.

0. 질문 + 출제 의도

질문: "N+1 문제란 무엇이고 어떻게 해결하나요? (fetch join, @EntityGraph, batch size)"

출제 의도: rationale은 이 문항을 "JPA 성능 문제의 8할"로 규정하면서, 정작 채점 지점은 다른 데 둔다 — "중요한 건 해결책 암기가 아니라 '운영 전에 어떻게 발견하는가'까지 말하는지". 즉 이 질문은 지식 확인 문항의 외형을 하고 있지만 실제로는 품질을 시스템으로 고정해본 경험을 재는 문항이다.

함정 — "fetch join으로 해결합니다"에서 멈추는 것 fetch join을 아는 것은 최소 요건이다. 변별은 "그 지식이 팀의 빌드 파이프라인에 장치로 박혀 있는가"에서 일어난다. rationale이 예시하는 답변의 3단계가 이것이다.
1단계 "fetch join으로 해결합니다"→ 2단계 "쿼리 로그로 배포 전에 잡습니다"→ 3단계 "테스트에서 쿼리 수를 검증합니다" ★
이 페이지가 겨냥하는 약점 세 가지 ① N을 "행 수"로 아는 것 → 1·2절에서 N의 계산식을 세우고, 같은 건수로 카디널리티만 바꾼 픽스처 두 벌을 나란히 놓는다. 이걸 틀리면 뒤의 모든 장치가 무력해진다.
② 도구 4개를 따로 외우는 것 → 3~5절에서 "행이 뻥튀김되는가"라는 축 하나로 묶고, 제약 셋이 전부 그 하나에서 파생됨을 보인다.
③ "쿼리 로그를 봅니다"로 끝내는 것 → 6·7절에서 사람 의존 방식이 반드시 실패하는 이유 넷과 다섯 관문의 자동 장치, 그리고 회귀 프레임까지 간다. 분량도 여기가 가장 두껍다.
이 문서의 위치 N+1이 EAGER 매핑에서 JPQL 번역 원리 때문에 벌어지는 과정은 03-eager-vs-lazy-fetch-strategy.md가, 1차 캐시가 왜 성능 캐시가 아닌지는 02-persistence-context-dirty-checking.md가 다룬다. 이 문서는 그 위에서 탐지와 선택만 다룬다.

1. N의 정체 — 왜 운영에서만 터지고 테스트에서는 재현되지 않는가

1-1. 정의는 한 줄로 끝난다

부모를 목록으로 조회한 쿼리 1개 뒤에, 각 부모의 연관을 채우려고 추가 쿼리가 더 나가는 것

이름이 "N+1"인 이유도 그대로다 — 앞의 1은 부모 목록을 가져오는 쿼리 1개, 뒤의 N은 그 뒤에 줄줄이 따라 나가는 추가 쿼리 수다. 먼저 장면을 눈으로 보자. 주문 목록을 조회하고 각 주문의 주문자 이름을 꺼내는, 아주 평범한 코드다.

문제 코드 어디에도 이상한 구석이 없다
List<Order> orders = orderRepository.findAll();          // ① 주문 목록 조회 — 쿼리 1개
for (Order o : orders) {
    System.out.println(o.getMember().getName());         ② 여기서 추가 쿼리가 나간다
}
왜 ②에서 쿼리가 나가나 — 프록시 초기화 연관이 LAZY로 매핑돼 있으면 o.getMember()가 돌려주는 것은 진짜 Member 객체가 아니라 껍데기 대역(프록시)이다. 이 대역은 id만 들고 있고 나머지 필드는 비어 있다. 그래서 getName()처럼 실제 값을 요구하는 순간, 대역이 그때서야 DB로 SELECT를 쏴서 자기 속을 채운다. 이것을 프록시 초기화라고 부른다.
쿼리 로그 "1"과 "N"이 로그에서 어떻게 보이는가
-- ① 부모 목록 — 이게 "N+1"의 1이다
select o.id, o.order_date, o.member_id from orders o;

-- ② 프록시 초기화 — 이게 "N+1"의 N이다. 같은 모양의 쿼리가 파라미터만 바뀌며 반복된다
select m.id, m.name from member m where m.id = ?;
select m.id, m.name from member m where m.id = ?;
select m.id, m.name from member m where m.id = ?;
   ...                                            (6-5절에서 이 "같은 SQL의 반복"이 탐지의 지문이 된다)

여기까지는 대부분 정확히 답한다. 문제는 그다음이다. N이 몇인지를 잘못 알면, 해결은 맞게 해놓고도 테스트가 통과해버린다. 이것이 N+1이 운영에서만 터지는 실제 이유다.

1-2. N은 "결과 행 수"가 아니다

가장 흔한 오해는 "부모를 1,000건 조회하면 추가 쿼리가 1,000개 나간다"는 것이다. 틀렸다. Hibernate는 프록시를 초기화할 때 곧장 SELECT를 쏘지 않는다. 먼저 영속성 컨텍스트를 뒤지고, 거기 없을 때만 SELECT를 쏜다.

전제 지식 보충 — 영속성 컨텍스트(1차 캐시) 하나의 트랜잭션 동안 조회·저장한 엔티티를 id를 키로 삼아 보관하는 자바 쪽 저장소다. "캐시"라는 이름 때문에 성능 최적화 장치로 오해하기 쉬운데, 본래 목적은 같은 트랜잭션 안에서 같은 id는 항상 같은 자바 객체로 보이게 만드는 동일성 보장이고, 그 부수 효과로 "이미 갖고 있는 id는 다시 조회하지 않는다"가 따라온다.

N의 계산식 — 이 한 줄이 이 문서 전체의 뿌리다

N = | { 조회된 부모 행들이 가리키는 서로 다른 연관 id }  −  { 이미 1차 캐시에 있는 id } |

행 수(M)는 이 식에 직접 등장하지 않는다. M은 "서로 다른 연관 id가 최대 몇 개까지 나올 수 있는가"의 상한일 뿐이다. 이 식의 첫 항을 결정하는 것이 2절의 카디널리티이고, 둘째 항을 0으로 만드는 것이 2절의 clear()다.

비유 하나 — 반 학생 30명의 생일 케이크

학생 30명이 있다. 생일이 전부 같은 날이면 케이크는 1개만 사면 되고, 전부 다른 날이면 30개를 사야 한다. 학생 수(=행 수)는 케이크 개수를 결정하지 않는다. 결정하는 것은 생일의 종류 수(=카디널리티)다.

학생 수 = 부모 행 수 (M)≠ 생일 종류 수 = 카디널리티 (N의 상한)− 이미 사둔 케이크 = 1차 캐시

2. 픽스처 설계 — 건수가 아니라 카디널리티로, 그리고 측정 직전에 clear()

2-1. 픽스처 두 벌 — 건수를 고정하고 카디널리티만 바꾼다

말로 하면 잘 안 와닿으니, 주문 건수를 1,000건으로 똑같이 고정하고 회원 수만 바꾼 픽스처 두 벌을 나란히 놓자. 조회 코드는 한 글자도 다르지 않고, 데이터 분포만 다르다.

픽스처 A "1,000건 넣고 성능 테스트했습니다"
// 가장 흔한 방식이고, 재현되지 않는다.
@BeforeEach
void setUpA() {
    Member member = memberRepository.save(new Member("홍길동"));   회원은 단 1명
    for (int i = 0; i < 1_000; i++) {
        orderRepository.save(new Order(member, "상품" + i));       // 전부 이 회원 것
    }
    em.flush();
    em.clear();
}
픽스처 B 건수는 그대로, 회원만 100명으로 흩뜨린다
// 주문 건수는 A 와 똑같이 1,000건.
@BeforeEach
void setUpB() {
    for (int i = 0; i < 100; i++) {                        회원 100명 — id 가 전부 다르다
        Member member = memberRepository.save(new Member("회원" + i));
        for (int j = 0; j < 10; j++) {
            orderRepository.save(new Order(member, "상품" + i + "-" + j));
        }
    }
    em.flush();
    em.clear();
}

2-2. 두 번째 함정 — 측정 직전에 컨텍스트를 비우지 않으면 거짓 통과한다

카디널리티를 제대로 잡아도 아직 끝이 아니다. 함정이 하나 더 있고, 이쪽이 N+1 테스트가 조용히 통과하는 원인 1위다. 1-2절의 식을 다시 보자 — 픽스처를 save()로 만들면 그 회원 엔티티들은 테스트 트랜잭션의 1차 캐시에 그대로 살아 있다. 그러면 식의 두 번째 항이 첫 번째 항만큼 커져서 N이 0이 된다. 카디널리티는 완벽한데도 추가 SELECT가 한 건도 안 나간다.

테스트 A clear()를 빠뜨렸다 — 영원히 초록불
@BeforeEach
void setUp() {
    for (int i = 0; i < 50; i++) {
        Member m = memberRepository.save(new Member("회원" + i));   // 카디널리티 50 — 완벽하다
        orderRepository.save(new Order(m, "상품" + i));
    }
    em.flush();      // INSERT 100건을 DB로 내보낸다
    // em.clear() 가 없다                                A와 B의 유일한 차이
}

@Test
void 주문목록_API는_쿼리_두_개_이내여야_한다() {
    Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
    stats.clear();
    orderService.list();
    assertThat(stats.getPrepareStatementCount()).isLessThanOrEqualTo(2);
}

// 총 1개 → 통과. N+1 이 있어도 없어도 영원히 초록불이다.

왜 clear()가 없으면 안 되는가 — 한 문장

운영의 조회 요청은 항상 빈 영속성 컨텍스트에서 시작한다

HTTP 요청이 들어오면 새 트랜잭션이 열리고 1차 캐시는 비어 있는 상태로 출발한다. 반면 테스트는 픽스처를 잔뜩 채워 넣은 컨텍스트를 그대로 물고 측정에 들어간다. 이 비대칭을 없애야 테스트가 운영을 대표한다.

em.flush()도 그냥 붙인 게 아니다. flush를 생략하면 쓰기 지연 저장소에 쌓여 있던 INSERT 100건이 측정 구간 안에서 뒤늦게 나가 쿼리 카운트에 섞인다(JPQL 실행 직전에 자동 flush가 걸리기 때문이다). 그러면 단정이 깨지긴 하는데 N+1 때문이 아니라 INSERT 때문에 깨지는 것이라 원인을 잘못 짚게 된다.

flush — INSERT를 밖으로→ clear — 캐시를 비우고→ 카운터 초기화→ 측정

2-3. 픽스처는 건수가 아니라 카디널리티로 설계한다

2-1과 2-2를 한 표로 합치면 설계 원칙이 그대로 나온다

건수를 20배 줄인 세 번째가 유일하게 재현한다. 재현에 필요한 건 규모가 아니라 조건이다.

픽스처 3규칙 — 다르게 · 작게 · 비우고

다르게
부모마다 서로 다른 연관을 갖게 만든다. 최악을 상정하는 것이고, 목록 API의 운영 데이터는 대개 최악에 가깝다.
작게
건수는 작게 유지한다. 재현에 필요한 건 분포이고, 건수는 테스트를 느리게만 만든다. 50건이면 충분하다.
비우고
측정 직전에 flush() + clear(). 픽스처를 만든 컨텍스트와 측정하는 컨텍스트를 분리한다.

이 셋이 6절의 자동 탐지 장치가 작동하기 위한 전제다. 픽스처가 재현하지 못하면 아무리 정교한 쿼리 수 단정도 항상 통과한다.

장치가 있는데 아무것도 못 잡는 상태 — 장치가 없는 것보다 나쁘다 픽스처를 잘못 만들면 테스트는 있고 감지력은 0인 상태가 된다. 이 상태가 아예 없는 것보다 나쁜 이유는, "쿼리 수 테스트가 있으니 안심"이라는 잘못된 신뢰까지 얹히기 때문이다. 이 문장은 이 페이지에서 세 번 더 반복된다(6-3 Statistics, 6-4 DataSource 미프록시, 6-4 비동기 경로) — 같은 실패 모드가 층마다 모양만 바꿔 나타난다.

3. 해결책의 유일한 축 — "행이 뻥튀김되는가"

해결책이라며 이름 넷이 등장한다. fetch join, @EntityGraph, default_batch_fetch_size, DTO 프로젝션. 넷을 따로 외우면 "언제 뭘 쓰죠?"에서 막힌다. 그런데 물리적 사실 하나가 이 넷을 딱 둘로 가른다. 그 사실부터 세우고 시작하자.

전제 지식 — SQL 조인은 행을 만들어낸다 부모 1행에 자식 3행이 매칭되면 결과는 3행이 되고, 부모의 컬럼값은 그 3행에 똑같이 복제돼 들어간다. DB에게는 지극히 정상적인 동작이지만, "부모 목록을 달라"고 요청한 애플리케이션 입장에서는 원하지도 않은 행이 불어난 것이다. 이 문서에서는 이것을 행 뻥튀김이라고 부른다. 반대로 자식이 항상 1행뿐이면 행은 안 늘어난다 — @ManyToOne·@OneToOne 같은 to-one 연관이 그렇다.
넷에 이름을 붙여 두 갈래로 묶으면, 선택 기준이 저절로 따라 나온다
갈래발상도구쿼리 수결과 행 수페이징
조인 계열"조인으로 한 번에 가져온다"fetch join, @EntityGraph1부모 × 자식으로 뻥튀김컬렉션이면 불가
분리 조회 계열"따로 다 가져와서 애플리케이션에서 조합한다"default_batch_fetch_size/@BatchSize, DTO 두 번 조회2 이상부모는 부모 수 그대로가능

표에서 봐야 할 칸은 "쿼리 수"가 아니라 "결과 행 수"다

"쿼리 수"는 언뜻 조인 계열의 승리처럼 보인다. 그러나 쿼리 1개가 100만 행을 메모리에 올리는 것보다, 쿼리 2개가 각각 20행·60행을 가져오는 편이 압도적으로 낫다.

왕복 횟수보다 읽어 올리는 데이터량이 먼저다

join과 join fetch의 차이 — "조인을 걸었는데 N+1이 그대로다"의 원인 1위

join (fetch 없음)

  • SQL 조인만 만든다
  • select 목록에는 부모 컬럼만 남는다
  • 조인은 걸렸지만 연관은 여전히 프록시
  • N+1이 그대로다

join fetch

  • 연관 엔티티의 컬럼까지 select 목록에 올린다
  • 한 번에 채우므로 프록시가 남지 않는다
  • N+1이 사라진다

List<Order> findAllWithToOnes(Pageable pageable);

벽 2 — 컬렉션은 하나만 fetch join 할 수 있다

컬렉션 둘을 동시에 fetch join하면 두 컬렉션의 카테시안 곱이 나온다. 카테시안 곱은 조인 조건 없이 두 집합의 모든 조합이 만들어지는 것을 말하는데, 한 부모 안에서 상품 3개와 배송이력 4개가 서로 짝지어지면 3 × 4 = 12행이 된다. 애플리케이션이 중복을 걷어내긴 하지만 DB에서 읽어 네트워크로 실어 나르는 데이터량 자체가 3×4로 곱해진다.

확인 범위 — Hibernate가 막아주는 경우와 조용히 통과시키는 경우가 갈리는데, 이 구분이 정확히 알려져 있지 않다 (6.6·7.4 소스와 회귀 테스트에서 확인)
컬렉션 조합Hibernate의 반응실제로 일어나는 일
bag 둘
bag = @OrderColumn이 없는 List — 순서 정보도 중복 제거도 없는 "그냥 가방"이라 이런 이름		예외 — org.hibernate.loader.MultipleBagFetchException
메시지: cannot simultaneously fetch multiple bags: [tags, comments]
가드는 if (collectionClassification == CollectionClassification.BAG) 한 군데뿐		카테시안 곱이 발생하기 전에 막힌다
Set 둘
(LIST + @OrderColumn, MAP도 동일)		예외도 경고도 없다
Hibernate에는 fetch join의 카테시안 곱을 감지하거나 로그로 알려주는 코드가 아예 없다 — 완전히 조용하다		rows(A) × rows(B)가 그대로 발생하고 메모리에서 중복만 걷어낸다
던져지는 시점이 늦다 쿼리 실행 시점(SQM → SQL AST 변환 중)이다. 부트스트랩도, createQuery 파싱 시점도 아니다. Hibernate 6에서는 EAGER List 두 개를 가진 엔티티로도 SessionFactory가 정상 부팅된다(회귀 테스트가 그것을 단정한다). 즉 시작할 때 크게 실패해주지 않고, 실제로 둘 다 fetch하는 쿼리를 타는 순간에만 뒤늦게 터진다.
JPA 경로에서는 예외가 바뀌어 올라온다 ExceptionConverterImpl이 MultipleBagFetchException을 IllegalArgumentException으로 변환한다. 그래서 EntityManager나 Spring Data를 쓰는 코드는 IllegalArgumentException을 잡고 getCause()로 풀어야 원인이 보인다.
진단 그대로 MultipleBagFetchException을 잡으려 하면 안 잡힌다
try {
    orderRepository.findAllWithItemsAndHistories();
} catch (IllegalArgumentException e) {                                변환된 타입으로 잡는다
    if (e.getCause() instanceof MultipleBagFetchException cause) {
        log.error("bag 두 개를 동시에 fetch 했다: {}", cause.getBagRoles());
    }
    throw e;
}

"List를 Set으로 바꾸면 된다"는 실무 요령의 정체

예외를 없애는 것이지 카테시안 곱을 없애는 게 아니다

rows(A) × rows(B)는 그대로 발생하고 Hibernate가 메모리에서 중복만 걷어낸다(6.0부터 자동 — 아래 distinct 항목과 같은 메커니즘). @OrderColumn을 붙여 LIST로 만드는 것도 결과가 같다.

큰 소리로 실패하던 것→조용한 성능 문제

감지 장치를 끄는 행위에 가깝다. 컬렉션이 둘 이상이면 정답은 4-3의 batch fetch size다. 참고로 hibernate.mapping.default_list_semantics의 기본값은 BAG이다 — 즉 아무 설정도 안 한 List 필드는 6.x·7.x에서도 5.x와 똑같이 bag이고, 이 예외를 만날 수 있는 상태다.

distinct — Hibernate 6부터는 오히려 빼야 한다

Before Hibernate 5 시절의 관행

List<Order> findAllWithItems();
// 6.x 에서는 불필요하고 비용만 든다
After Hibernate 6+
@Query("select o from Order o join fetch o.items")
List<Order> findAllWithItems();
// distinct 없이도 부모 중복은 제거된다
확인 범위 / 통설 교정 — Hibernate 6.0 마이그레이션 가이드 6부터 fetch join의 부모 엔티티 중복은 항상 Hibernate가 걸러낸다. 그래서 distinct가 필요 없어졌고, 5.2에서 도입된 hibernate.query.passDistinctThrough(SQL로 distinct를 넘기지 않게 하는 설정)는 6.0에서 제거됐다. 중요한 귀결이 있다 — 6부터 distinct를 쓰면 항상 SQL의 select distinct로 나가고 이를 막을 방법이 없다. 조인으로 뻥튀김된 전체 행에 대해 DB가 정렬·해시 중복 제거를 하게 되므로 실제 비용이 발생한다.
6.x에서 distinct는 "안전하게 붙여두는 것"이 아니라 불필요한 DB 비용이다

4-2. ② @EntityGraph — 선언적 fetch join, 그래서 벽도 그대로다

fetch join과 같은 SQL로 번역되는 선언형 표기다. "선언형"이란 쿼리 문장을 쓰는 대신 애너테이션으로 "이 연관들을 같이 가져와라"라고 적어만 두는 방식을 말한다. 번역 결과가 같으므로 4-1의 두 벽이 그대로 적용된다 — 컬렉션 + 페이징 금지, 컬렉션 둘 이상 금지.

"@EntityGraph를 쓰면 페이징이 된다"는 오해 — 메커니즘까지 확인했다

확인 범위: Hibernate 6.6이 페이징을 메모리로 돌리는 판정은 hasLimit && containsCollectionFetches인데, 이 containsCollectionFetches가 "HQL 문장에 컬렉션 fetch가 있는가" 또는 "적용된 EntityGraph에 컬렉션이 EAGER 노드로 들어 있는가"의 논리합이다.

문장이 아니라 그래프에 적힌 것도 똑같이 판정에 걸린다
// join fetch 를 한 글자도 쓰지 않았는데도 인메모리 페이징 + HHH90003004 경고가 그대로 난다
@EntityGraph(attributePaths = "items")     items 가 컬렉션이면 여기서 걸린다
Page<Order> findByStatus(OrderStatus status, Pageable pageable);

jakarta.persistence.fetchgraph / loadgraph 힌트를 직접 주는 경우도 같다. 반대로 EAGER 노드가 전부 단일 값 연관(to-one)인 EntityGraph는 이 판정에 걸리지 않아 페이징이 정상 동작한다 — 3절에서 "to-one은 조인해도 행이 안 늘어난다"고 한 것과 같은 이야기다.

그럼 @EntityGraph를 왜 쓰나. fetch join이 못 하는 일을 하나 하기 때문이다 — 쿼리 문장을 쓰지 않고도 붙일 수 있다.

쓰임새 문장이 없는 자리에 fetch를 먹인다
public interface OrderRepository extends JpaRepository<Order, Long> {

    // ① 메서드 이름 파생 쿼리에 붙인다 — JPQL 을 쓸 수 없는 자리
    @EntityGraph(attributePaths = {"member", "delivery"})
    List<Order> findByStatus(OrderStatus status);

    // ② 상속받은 메서드를 오버라이드해 붙인다 — findAll() 에 fetch 를 먹인다
    @Override
    @EntityGraph(attributePaths = "member")
    List<Order> findAll();

    // ③ 중첩 경로도 된다 — 점 표기로 depth 를 내려간다
    @EntityGraph(attributePaths = {"member", "member.team"})
    Optional<Order> findWithMemberAndTeamById(Long id);
}
type 속성 — FETCH와 LOAD Spring Data의 기본값은 FETCH다. FETCH는 그래프에 적지 않은 연관을 LAZY로 취급하고, LOAD는 적지 않은 연관을 매핑의 기본값 그대로 둔다. 그래서 EAGER 매핑이 남아 있는 프로젝트에서 FETCH 그래프는 이론상 EAGER를 쿼리 단위로 끄는 수단이 되지만, 실무에서 이걸 EAGER 허용의 근거로 삼기는 어렵다.
쿼리를 직접 쓰는 자리(JPQL/QueryDSL)에서는 fetch join · 파생 쿼리나 상속 메서드처럼 문장이 없는 자리에서는 @EntityGraph
성능 차이가 아니라 표기 위치의 문제다

4-3. ③ default_batch_fetch_size / @BatchSize — 페이징과 공존하는 유일한 도구

여기서부터 분리 조회 계열이다. 3절의 표에서 "행이 늘지 않는다" 칸에 있던 쪽이고, "따로 다 가져와서 애플리케이션에서 조합한다"는 발상을 Hibernate가 자동으로 해주는 버전이다.

원리와 비유 — 심부름을 주문서로 모은다

프록시(또는 아직 채워지지 않은 컬렉션) 하나를 초기화해야 하는 순간, Hibernate는 그 하나만 채우지 않는다. 같은 종류의 미초기화 프록시를 최대 size개까지 긁어모아 where id in (?, ?, ...) 한 방으로 함께 채운다.

심부름 시킬 때마다 가게에 한 번씩 다녀오기→주문서를 100장까지 모았다가 한 번에 다녀오기
1  +  ceil( 서로 다른 미해결 연관 id 수 / batch size )

size = 100이면 1 + 1000이 1 + 10(총 11개)이 된다.

전역 실무의 정석 안전망
# 100~1000 사이에서 고른다
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
개별 특정 연관만 다르게
@Entity
public class Order {
    @BatchSize(size = 500)
    @OneToMany(mappedBy = "order")
    private List<OrderItem> items = new ArrayList<>();
}
Before 컬렉션 fetch join + 페이징
@Query("select o from Order o join fetch o.items")
Page<Order> findPage(Pageable pageable);
// limit 이 SQL 에 안 붙고 전체를 메모리에 올린다
After 쿼리에서 컬렉션을 fetch하지 않는다
Page<Order> findAll(Pageable pageable);   limit 정상
// items 접근 시 where order_id in (?,?,...) 로 묶여 나간다
// → 총 1 + ceil(20/100) = 2개

공존의 조건을 정확히 말해야 한다

batch fetch가 페이징과 공존하는 이유는 "batch fetch가 특별해서"가 아니라 페이징 쿼리가 컬렉션을 fetch하지 않기 때문이다. 그리고 그 조건은 join fetch뿐 아니라 컬렉션을 EAGER로 지정한 @EntityGraph/fetchgraph 힌트로도 깨진다(4-2).

지켜야 할 규칙은 "컬렉션은 쿼리에서 fetch하지 않는다"
batch fetch size는 그 규칙을 지켰을 때 N+1을 대신 막아주는 장치다
확인 범위 — 회귀 테스트로 확인 이 동작은 Hibernate 회귀 테스트 BatchPaginationTest(HHH-16005, 6.2·6.6·7.4 브랜치에 존재)에서 직접 확인했다 — @ManyToMany @BatchSize(size = 20) 컬렉션에 join fetch 없는 쿼리 + setMaxResults(20)으로, 전체 요소를 순회해도 총 쿼리 2개(루트 1 + 배치 1)다. 다만 HHH-16005는 @ManyToMany에 @BatchSize가 무시되던 버그였고 수정 버전이 6.1.7 / 6.2.0이므로, 버전을 특정해 말한다면 "6.1.7 이상 / 6.2 이상"으로 한정하는 것이 정확하다.
확인 범위 / 통설 교정 — "size를 100으로 주면 100개씩 묶인다"는 설명은 Hibernate 5에서는 사실이 아니었다 (소스에서 확인)
버전배치 크기 산정 방식1 + ceil(N/size) 공식
5.x지정한 수를 그대로 쓰지 않고 내림차순 배치 크기 계열을 미리 만들어 재사용했다(ArrayHelper.getBatchSizes). size 32면 실제 배치 크기는 32, 16, 10, 9, 8, 7, ... 1이고, 미해결 id 50개는 32 + 16 + 2 → 쿼리 3개. 프리페어드 스테이트먼트 재사용을 위해 파라미터 개수가 다른 SQL 종류를 제한하려는 설계였다.어긋난다
ceil(50/32) = 2와 다름
6.2부터
HHH-16441		dialect가 SQL 배열 타입을 지원하고 id가 단일 컬럼 기본 타입이면 파라미터 하나에 배열을 바인딩해 SQL 한 개(PostgreSQL 등), 그렇지 않으면 정확히 size개의 플레이스홀더를 가진 in (?,?,...) 하나를 쓰고 남는 자리를 null로 채운다(MySQL, H2 등). SQL 모양이 하나로 고정된다.실제와 맞는다

설정이 조용히 무시되는 오타 — "설정했는데 안 먹는다"의 단골 원인

틀림 조용히 무시된다
spring.jpa.hibernate.default_batch_fetch_size
맞음 properties 아래로
spring.jpa.properties.hibernate.default_batch_fetch_size

프로퍼티 이름은 6.x·7.x에서 hibernate.default_batch_fetch_size 그대로이고, Spring Boot에는 이 설정을 위한 전용(1급) 프로퍼티가 없다. 반드시 spring.jpa.properties.*로 넘겨야 한다. 그리고 hibernate.query.in_clause_parameter_padding은 이 배치 fetch와 무관한 설정이다(HQL의 IN 목록 확장과 다중 id 로딩에 적용된다) — 두 개를 섞어 말하면 틀린다.

한계 — 그리고 가장 중요한 부작용은 성능이 아니라 은폐다 쿼리가 1개가 되는 것은 아니다. 왕복이 2회 이상 남고, N+1을 없애는 게 아니라 1+N을 1+몇 개로 낮추는 완화책이다. 그리고 1+1000이 1+10이 되면서 증상이 옅어져, N+1이 있는지조차 모르게 된다.
전역 batch fetch size는 6절의 탐지 장치와 반드시 세트로 깐다
안전망만 깔면 "조용한 1 + 수십 쿼리" 상태로 굳는다

4-4. ④ DTO 프로젝션 / 두 번 조회 후 조합 — 조회 전용 화면의 정답

앞의 셋은 모두 엔티티를 만든다는 전제를 공유한다. 조회 전용 화면이라면 그 전제 자체를 버리는 것이 가장 근본적이다. 엔티티를 안 만들면 프록시도 없고 변경 감지용 스냅샷도 없고 N+1이라는 문제 범주 자체가 사라진다.

Before 반환 타입만 DTO — N+1은 그대로다
public List<OrderDto> list() {
    return orderRepository.findAll().stream()
            .map(o -> new OrderDto(o.getId(), o.getMember().getName()))  여기서 N+1
            .toList();
}
After DTO를 쿼리가 만든다
@Query("""
       select new com.example.OrderDto(o.id, m.name)
       from Order o join o.member m
       """)
List<OrderDto> findAllDto();
// 조인 1개, 필요한 컬럼만
"DTO를 쓴다"와 "DTO 프로젝션"은 다르다 — DTO가 쿼리의 결과여야 효과가 있다
이 구분을 못 하면 "DTO로 바꿨는데 왜 여전히 느리죠"에 갇힌다

컬렉션이 있는 화면은 한 번에 안 된다. 여기서 3절이 말한 "분리 조회 계열"의 원형이 정식 해법으로 등장한다 — 부모를 페이징으로 조회하고, 자식을 id 목록으로 한 번에 조회한 뒤, 애플리케이션에서 조합한다.

정식 해법 총 쿼리 2개 · 페이징 정상 · 카테시안 곱 없음
public Page<OrderView> page(Pageable pageable) {
    // ① 부모만 페이징 — 조인이 없으니 limit 이 SQL 에 그대로 붙는다
    Page<OrderRow> orders = orderRepository.findRows(pageable);              // 쿼리 1

    List<Long> orderIds = orders.getContent().stream().map(OrderRow::id).toList();

    // ② 자식을 id 목록으로 한 번에 — IN 절 하나
    Map<Long, List<ItemRow>> itemsByOrder = itemRepository.findRowsByOrderIdIn(orderIds)
            .stream().collect(groupingBy(ItemRow::orderId));                 // 쿼리 1

    // ③ 애플리케이션에서 조합
    return orders.map(o -> new OrderView(o, itemsByOrder.getOrDefault(o.id(), List.of())));
}

4-3과 4-4의 관계 — 원리가 하나다

default_batch_fetch_size= Hibernate가 ①②③을 엔티티 세계에서 자동으로 해주는 것
위 코드= 같은 일을 DTO 세계에서 손으로 하는 것

그래서 "따로 가져와서 조합한다"는 직관 하나가 두 도구를 동시에 설명한다. 손으로 하는 대가로 얻는 것은 필요한 컬럼만 읽는다는 것과 조합 규칙을 내가 통제한다는 것이다.

5. 선택 기준 — 표 하나와 결정 흐름

같은 내용을 표로 — 면접에서 바로 꺼낼 수 있는 형태
상황선택근거
to-one 연관 1~여러 개 (페이징 유무 무관)fetch join / @EntityGraph조인해도 행이 안 늘어 limit이 정상 동작
컬렉션 1개 + 페이징 없음fetch join / @EntityGraph쿼리 1개. Hibernate 6+ 에서 distinct는 붙이지 않는다
컬렉션 + 페이징batch fetch sizefetch join 금지 구간(메모리 페이징). @EntityGraph로 컬렉션을 지정해도 같은 함정
컬렉션 2개 이상batch fetch sizefetch join은 카테시안 곱. bag 둘이면 예외, Set 둘이면 조용히 곱해진다
조회 전용 화면·목록 APIDTO 프로젝션 (컬렉션은 두 번 조회 후 조합)엔티티·프록시·스냅샷을 아예 만들지 않는다
전 구간 안전망전역 default_batch_fetch_size 100~1000놓친 지점의 피해를 1+N에서 1+몇 개로 낮춘다

면접에서 한 문장으로 — "컬·페 → 배치"

"컬렉션에 페이징이 붙으면 fetch join은 후보에서 빠지고 batch fetch size로 갑니다.
to-one 여러 개면 fetch join, 조회 전용이면 DTO 프로젝션이고,
전역 batch fetch size는 안전망으로 항상 깔아둡니다."

컬·페 → 배치 넉 자만 기억하면 표 전체가 복원된다. 나머지는 "그 반대면 조인"이기 때문이다.

6. 자동 탐지 장치 — 이 문항의 실제 관문

여기가 채점 지점이다. rationale이 재려는 것은 "운영 전에 어떻게 발견하는가"이고, "쿼리 로그를 보고 성능 테스트를 한다"는 답은 여기서 미달로 기록된다. 이유는 그 방법이 나쁘기 때문이 아니라 사람에 의존하기 때문이다.

6-1. 사람에게 의존하는 방식이 반드시 실패하는 네 가지 이유

1
픽스처가 재현하지 못한다. 1·2절이 통째로 그 내용이다. 건수를 늘리는 방식의 성능 테스트는 카디널리티가 낮아 N+1을 그냥 통과시킨다. 게다가 clear()를 빠뜨리면 카디널리티가 맞아도 통과한다.
2
로그는 흘러간다. 실패한 요청의 로그는 읽지만, 성공한 요청이 쿼리 40개를 쓴 사실은 아무도 보지 않는다. N+1은 예외를 던지지 않고 200 OK를 돌려주므로, 로그에 남아 있어도 그 로그를 열어볼 이유가 생기지 않는다.
3
리뷰는 diff만 본다. N+1은 두 파일 사이에서 태어난다. 매핑 파일의 fetch 누락과 서비스 파일의 getMember() 한 줄이 결합될 때 생기는데, PR의 diff에는 보통 한쪽만 올라온다. 리뷰어가 diff에 없는 다른 파일을 기억해내야만 잡히는 구조라서, 팀이 커지고 PR이 늘면 확률적으로 반드시 새어나간다.
4
한 번 고쳐도 재발한다. 이게 결정적이고 7절의 원칙으로 이어진다. fetch join을 넣어 고친 API에 다음 달 필드 하나가 추가되면서 o.getDelivery().getAddress() 한 줄이 붙으면 N+1이 되살아난다. 고친 사람의 의도는 코드에 남지 않는다.
필요한 것은 더 열심히 보는 것이 아니라, 사람이 안 봐도 실패하는 장치다

6-2. 장치는 층으로 쌓는다 — 다섯 관문 지도

6-3. 1층 — 테스트에서 쿼리 수를 단정한다 (Hibernate Statistics)

가장 적은 비용으로 가장 큰 효과를 내는 장치다. 라이브러리를 추가할 필요가 없다 — Hibernate가 이미 내장하고 있는 통계 카운터를 켜서 읽기만 하면 된다.

1단계 테스트 프로파일에서 카운터를 켠다 — 기본값이 false다
# application-test.yml — 켜지 않으면 카운터가 항상 0 이다
spring:
  jpa:
    properties:
      hibernate:
        generate_statistics: true
2단계 목록 API마다 쿼리 수를 못 박는다
import org.hibernate.SessionFactory;
import org.hibernate.stat.Statistics;

@SpringBootTest
@Transactional
class OrderQueryCountTest {

    @Autowired EntityManagerFactory emf;
    @Autowired EntityManager em;
    @Autowired OrderService orderService;
    @Autowired MemberRepository memberRepository;
    @Autowired OrderRepository orderRepository;

    @BeforeEach
    void setUp() {
        // 2-3 의 규칙 그대로: 부모마다 서로 다른 연관 + 건수는 작게
        for (int i = 0; i < 50; i++) {
            Member m = memberRepository.save(new Member("회원" + i));
            orderRepository.save(new Order(m, "상품" + i));
        }
        em.flush();   INSERT 를 측정 구간 밖으로
        em.clear();   이 줄이 없으면 2-2 처럼 영원히 통과한다
    }

    @Test
    @DisplayName("주문 목록 API 는 쿼리 2개 이내여야 한다")
    void 주문목록_API는_쿼리_두_개_이내여야_한다() {
        Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
        stats.clear();   전역·누적 카운터다 — 측정 전 초기화 필수

        orderService.list();

        assertThat(stats.getPrepareStatementCount())
                .as("N+1 회귀 — 연관을 fetch 하지 않는 코드가 들어왔다")
                .isLessThanOrEqualTo(2);
    }
}
확인 범위 — 메서드 이름의 오타처럼 보이는 부분 메서드 이름은 getPrepareStatementCount()다 — Prepared가 아니라 Prepare이고 오타처럼 보이지만 이게 실제 이름이다(Hibernate 6·7 소스와 공식 유저 가이드에서 확인). SessionFactory가 getStatistics()를 노출하며, JPA 표준 타입인 EntityManagerFactory에서는 emf.unwrap(SessionFactory.class)로 꺼낸다. 활성화 프로퍼티는 hibernate.generate_statistics이고 기본값은 false다.

이 장치가 못 잡는 것 — 함정 세 개를 알고 써야 한다

① 전역 · 누적이다
SessionFactory 단위이고 스레드 단위가 아니다. 그래서 측정 전 clear()가 필수이고, JUnit을 병렬로 돌리면 다른 테스트가 쏜 쿼리가 섞여 들어와 단정이 무작위로 깨진다. 병렬 실행 팀은 순차 실행 그룹으로 격리해야 한다.
② Hibernate 경유만 센다
같은 트랜잭션 안에서 JdbcTemplate이나 MyBatis로 쏜 쿼리는 이 카운터에 안 잡힌다. ORM과 SQL을 병용하는 프로젝트라면 실제보다 작게 보인다.
③ 픽스처가 전제다
2-3을 지키지 않으면 이 테스트는 영원히 통과한다. 장치가 있는데 아무것도 못 잡는 상태가 가장 위험하다 — 잘못된 신뢰까지 만들어내기 때문이다.

가산점 한 줄 가산점 — Statistics에는 다른 카운터도 있어서 함께 단정하면 진단력이 올라간다. getEntityUpdateCount()를 0으로 단정하면 조회 API의 유령 UPDATE까지 같이 잡힌다.

카운터의 저장 범위가 Statistics와 정반대라서, 함정도 정반대다

확인 범위: datasource-proxy(1.8·1.11.0) 소스에서 확인했다. 내부 QueryCountHolder는 static ThreadLocal<ConcurrentMap<String, QueryCount>>이고 getGrandTotal()은 현재 스레드의 맵만 합산한다. 데이터소스 이름으로 키를 잡을 뿐 스레드 간 집계는 하지 않는다. 귀결이 둘이다.

① 병렬 테스트에 안전하다

스레드마다 카운터가 분리되므로 Statistics와 달리 다른 테스트의 쿼리가 섞이지 않는다. 단 JUnit 5의 @Execution(CONCURRENT)는 ForkJoinPool 워커를 재사용하므로 같은 워커에서 앞서 돌았던 테스트의 잔여 상태가 남는다 → reset()은 반드시 @BeforeEach여야 한다. 이 하나를 틀리면 단정이 무작위로 깨진다.

② 다른 스레드의 쿼리는 조용히 0

@Async, CompletableFuture.supplyAsync, DB를 타는 parallel stream, executor로 넘긴 트랜잭션이 전부 해당한다. 에러가 나지 않고 그냥 통과한다. 비동기 경로를 검증하려면 datasource-proxy의 SingleQueryCountHolder(스레드 공유 전략)로 바꿔야 하는데, 이때 reset()이 사실상 동작하지 않는다는 함정이 따라온다(QueryCountHolder.clear()가 현재 스레드의 참조만 버리고 공유 카운터를 0으로 만들지 않는다). 이 도구는 동기 요청 경로 검증용으로 쓰는 것이 안전하다.

Statistics와 어느 쪽을 쓸까 라이브러리 없이 지금 당장 시작하려면 Statistics, 유형별 분리·Hibernate 밖 쿼리·병렬 테스트 안전성이 필요하면 이쪽이다. 실무에서는 대개 한쪽만 팀 표준으로 정해 헬퍼로 감싸 쓴다.
중요한 건 도구 선택이 아니라 목록 API마다 쿼리 수 단정이 하나씩 붙어 있는 상태다

6-5. 3층 — 요청 단위 쿼리 카운터 (개발·스테이징의 모든 경로를 덮는다)

1·2층의 한계는 명확하다. 테스트가 있는 경로만 지킨다. 새로 만든 API, 테스트를 안 쓴 관리자 화면, 특정 조건 분기로만 타는 경로는 전부 무방비다. 그래서 코드를 수정하지 않고 모든 요청을 감시하는 층이 필요하다.

파라미터만 다른 동일한 SQL이 수십 번 반복된다.

그래서 총량 임계치보다 정규화된 SQL별 반복 횟수를 보는 편이 거짓 경보가 훨씬 적다.

스니퍼 "누가 그랬는지"를 알려준다 — 반복 시점의 스택을 찍는다
// 개발·스테이징 전용. 같은 SQL 이 임계치만큼 반복되면 그 순간의 스택을 찍는다.
@Slf4j
@Component
@Profile({"local", "dev", "staging"})       운영에는 넣지 않는다
public class NPlusOneSniffer implements QueryExecutionListener {

    private static final int REPEAT_THRESHOLD = 10;

    // 요청 1건 = 스레드 1개라는 가정 위에서 동작한다
    private static final ThreadLocal<Map<String, Integer>> COUNTS =
            ThreadLocal.withInitial(HashMap::new);

    @Override
    public void beforeQuery(ExecutionInfo exec, List<QueryInfo> queries) { }

    @Override
    public void afterQuery(ExecutionInfo exec, List<QueryInfo> queries) {
        for (QueryInfo q : queries) {
            String sql = q.getQuery();                    // 파라미터 바인딩 전의 원형 SQL
            int n = COUNTS.get().merge(sql, 1, Integer::sum);
            if (n == REPEAT_THRESHOLD) {                  == 로 딱 한 번만 (>= 면 로그 폭주)
                log.warn("N+1 의심 — 같은 SQL 이 {}회 반복됐다: {}", n, sql,
                        new Throwable("이 스택의 어딘가가 루프에서 연관을 건드리고 있다"));
            }
        }
    }

    static void reset() { COUNTS.remove(); }
}
필터 "이 요청이 무겁다"를 알려준다 — 요청 경계에서 카운터를 초기화한다
@Slf4j
@Component
@Profile({"local", "dev", "staging"})
public class QueryCountGuardFilter extends OncePerRequestFilter {

    private static final int TOTAL_THRESHOLD = 50;        // 팀 합의값

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        NPlusOneSniffer.reset();
        QueryCountHolder.clear();
        try {
            chain.doFilter(req, res);
        } finally {
            QueryCount count = QueryCountHolder.getGrandTotal();
            if (count != null && count.getSelect() >= TOTAL_THRESHOLD) {
                log.warn("QUERY-GUARD {} {} — SELECT {}건 (임계치 {})",
                        req.getMethod(), req.getRequestURI(), count.getSelect(), TOTAL_THRESHOLD);
            }
            // 스레드가 풀로 반납되므로 반드시 비운다 — 안 비우면 다음 요청에 잔여값이 섞인다
            NPlusOneSniffer.reset();
            QueryCountHolder.clear();
        }
    }
}

이 장치가 못 잡는 것 첫째, 사람이 경고 로그를 읽어야 조치된다. 빌드를 깨뜨리지 않으므로 예방 장치가 아니라 조기 발견 장치다. 둘째, 스테이징에 흘러간 트래픽이 닿은 경로만 나온다 — 아무도 호출하지 않은 API는 여전히 무방비다.
운영에 넣지 않는 이유도 말할 수 있어야 한다 모든 쿼리마다 맵 갱신과 문자열 키 해싱이 붙고, 경고마다 스택트레이스 생성 비용(스택 프레임을 통째로 채워 넣는 작업이라 결코 싸지 않다)이 든다. 배포 전에 잡는 것이 목적이므로 프로파일로 가둔다. 운영에서 같은 정보가 필요하면 6-8의 APM 쪽으로 간다.
확인 범위 — 스레드 가정 QueryCountHolder가 static ThreadLocal 기반이고 getGrandTotal()이 현재 스레드만 합산한다는 것은 소스에서 확인했다(6-4). 그래서 위 필터는 요청 1건이 스레드 1개에서 처리된다는 가정에서 정확하게 동작한다 — Spring MVC의 기본 모델이 그렇다. 반대로 @Async나 WebFlux처럼 다른 스레드로 넘어가는 경로에서는 카운트가 나뉘거나 0이 되므로, 요청 스코프 빈이나 MDC 기반 컨텍스트 전파로 바꿔야 한다. QueryExecutionListener·QueryInfo#getQuery()의 정확한 시그니처는 프로젝트 버전에서 컴파일로 확인할 것.

6-6. 4층 — ArchUnit으로 원인 자체를 못 박는다

지금까지의 층은 전부 결과(쿼리 수)를 검사한다. 한 층 더 앞에서 원인(매핑)을 막을 수도 있다. @ManyToOne·@OneToOne의 기본값이 EAGER이므로, fetch를 안 적은 것 자체가 EAGER 선언이다. 이걸 빌드에서 실패시킨다. ArchUnit은 프로덕션 코드의 바이트코드를 읽어 "이런 구조여야 한다"를 JUnit 테스트로 단정하는 라이브러리이고, 규칙을 어기면 빌드가 깨진다.

규칙 to-one 연관은 LAZY로 명시해야 한다
@AnalyzeClasses(packages = "com.example.domain")
class EntityMappingRulesTest {

    @ArchTest
    static final ArchRule to_one_연관은_LAZY로_명시해야_한다 =
            fields().that().areAnnotatedWith(ManyToOne.class)
                    .or().areAnnotatedWith(OneToOne.class)
                    .should(new ArchCondition<JavaField>("fetch = LAZY 로 명시돼 있어야 한다") {
                        @Override
                        public void check(JavaField field, ConditionEvents events) {
                            // 애너테이션의 fetch 속성을 읽는다. 적지 않았으면 기본값 EAGER 가 읽힌다
                            FetchType fetch = field.isAnnotatedWith(ManyToOne.class)
                                    ? field.getAnnotationOfType(ManyToOne.class).fetch()
                                    : field.getAnnotationOfType(OneToOne.class).fetch();
                            if (fetch != FetchType.LAZY) {
                                events.add(SimpleConditionEvent.violated(field,
                                        field.getFullName() + " 의 fetch 가 EAGER 다"
                                        + " (명시하지 않은 경우도 기본값이 EAGER 라 여기서 걸린다)"));
                            }
                        }
                    });
}

이 룰의 진짜 이득 — 그리고 레거시 도입 요령 가산점

EAGER를 일부러 적은 사람을 잡는 게 아니라 fetch를 적는 것을 잊은 사람을 잡는 것
후자가 압도적으로 많고, 애너테이션의 기본값을 읽어 판정하므로 두 경우가 자동으로 같이 걸린다

기존 위반이 200개면 룰을 켜는 순간 빌드가 안 돌아 결국 룰을 지우게 된다. ArchUnit의 FreezingArchRule.freeze(rule)로 현재 위반을 동결하면 기존 것은 통과시키고 신규 위반만 실패시킬 수 있다. 동결 목록을 스프린트마다 조금씩 줄여나가는 방식이 현실적이다.

확인 범위 fields()·ArchCondition·SimpleConditionEvent·FreezingArchRule은 ArchUnit의 공개 API이지만 정확한 시그니처는 버전별로 다를 수 있어 프로젝트에서 컴파일로 확인할 것.
이 장치가 못 잡는 것 — 분명히 알아야 한다 매핑이 전부 LAZY여도 N+1은 사용처에서 태어난다. LAZY 연관을 루프 안에서 건드리는 코드 한 줄이면 그만이고, ArchUnit은 그 코드를 보지 않는다. 즉 ArchUnit은 원인 하나를 봉쇄할 뿐이고, 실제 방어의 주력은 여전히 1·2층의 쿼리 수 단정이다.

6-8. APM·슬로우 쿼리 로그는 "예방"이 아니라 "사후 발견"이다

APM(트랜잭션 트레이스)은 잡는다 — 다만 성질이 다르다 APM은 요청 하나의 타임라인 위에 그 요청이 실행한 모든 쿼리를 늘어놓으므로 동일 쿼리가 수백 개 쌓인 그림이 그대로 보인다. 문제는 APM이 계측하는 대상이 "실제 운영 트래픽"이라는 점이다. 관측 대상이 존재하려면 그 코드가 이미 배포되어 사용자 요청을 받고 있어야 한다. 구조상 배포보다 앞설 수가 없다.
APM의 유용한 사용법 하나 가산점 트랜잭션 목록을 응답 시간 순이 아니라 쿼리 수 순으로 정렬하는 것이다. N+1은 데이터가 적은 동안에는 빠르기 때문에 응답 시간 정렬에서는 한참 아래에 묻혀 있고, 쿼리 수 정렬에서는 1등으로 올라온다.

세 가지를 같은 층으로 말하면 안 된다

예방 — 빌드와 테스트· 조기 발견 — 스테이징 카운터· 사후 발견 — APM

셋을 같은 층으로 말하면 "장치를 갖췄다"가 아니라 "운영에서 발견하는 팀"이라는 뜻이 된다.

7. 원칙 — N+1은 성능 문제가 아니라 회귀다

이 문항의 결론은 도구 목록이 아니라 문제의 분류를 바꾸는 것이다. 성능 문제는 한 번 고치면 끝난다. 인덱스를 걸면 그 인덱스는 남아 있고, 다음 PR이 인덱스를 지우지는 않는다. 그런데 N+1은 고쳐도 재발한다.

재발하는 구조적 이유 셋

① 원인과 발생 지점이 멀다
매핑 파일에서 태어나고 서비스 파일에서 터진다. 두 파일을 동시에 보는 사람이 없다.
② 기본값이 위험한 쪽이다
to-one의 기본값이 EAGER라서 아무것도 안 하면 위험한 상태가 된다. 안전을 위해 매번 능동적으로 한 줄을 적어야 하는 구조는 확률적으로 반드시 새어나간다.
③ 기능 추가만으로 되살아난다
fetch join으로 고친 API에 "배송지도 보여달라"는 요구가 오면 한 줄이 붙는다. 그 PR의 diff에는 fetch join이 없다.
재발하는 문제에 대한 올바른 대응은 "더 잘 보기"가 아니라 "테스트로 고정하기"다

이건 N+1만의 이야기가 아니고 회귀 일반의 처방이다. 버그를 고칠 때 재현 테스트를 먼저 쓰는 것과 정확히 같은 논리다 — 다만 N+1은 예외를 던지지 않아서 "실패하는 테스트"를 자연스럽게 얻지 못하고, 쿼리 수라는 관측 지표를 직접 단정해야만 실패를 만들 수 있다. 6절의 장치들이 전부 그 한 가지 일을 한다.

면접에서는 이 프레임을 결론으로 놓는다
"N+1은 성능 문제로 분류하면 계속 재발합니다.
회귀로 분류하고, 목록 API마다 쿼리 수를 단정하는 테스트를 둬서
다음 PR에서 되살아나면 빌드가 깨지게 만듭니다."

8. 인출 카드 · 꼬리질문 셀프 테스트

8-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

N의 정확한 정의?
결과 행 수가 아니라 {서로 다른 연관 id} − {이미 1차 캐시에 있는 id}. 행 수는 상한일 뿐 식에 등장하지 않는다.
픽스처 3규칙?
다르게 · 작게 · 비우고 — 부모마다 다른 연관 / 건수는 50건이면 충분 / 측정 직전 flush() + clear().
테스트가 조용히 통과하는 원인 1위?
clear() 누락. 픽스처를 save()로 만들면 그 엔티티가 1차 캐시에 살아 있어 N = 0이 된다. 카디널리티가 완벽해도 통과한다.
측정 직전 순서 4단계?
flush → clear → 카운터 초기화 → 측정. flush를 빼면 INSERT가 측정 구간에 섞여 엉뚱한 이유로 단정이 깨진다.
도구 4종을 가르는 유일한 축?
행이 뻥튀김되는가. 조인 계열은 쿼리 1개·행 폭증, 분리 조회 계열은 쿼리 2개 이상·행 그대로. 페이징·다중 컬렉션·중복 제약이 전부 여기서 파생된다.
선택 기준 한 문장?
컬·페 → 배치. 컬렉션 + 페이징이면 fetch join을 버리고 batch fetch size. to-one 여럿이면 fetch join, 조회 전용이면 DTO.
컬렉션 fetch join + 페이징의 버전별 동작?
5.x·6.0~7.3 메모리 페이징(6.x 메시지 코드는 HHH90003004), 7.4부터 파생 테이블로 밀어넣어 DB에서 페이징. Boot 3.x는 여전히 옛 동작.
컬렉션 둘을 fetch join하면?
bag 둘이면 MultipleBagFetchException(쿼리 실행 시점, JPA 경로에서는 IllegalArgumentException으로 변환), Set 둘이면 예외도 경고도 없이 조용히 곱해진다.
batch fetch 쿼리 수 공식?
1 + ceil(미해결 id 수 / size). 이 공식이 실제와 맞는 것은 6.2부터(5.x는 내림차순 배치 계열이라 어긋난다).
탐지 장치 4층?
빌드(ArchUnit) → PR(쿼리 수 단정 ★주력) → 스테이징(요청 단위 카운터) → 운영(APM). 슬로우 쿼리 로그는 사실상 그물이 아니다.
N+1의 "지문"은?
총 쿼리 수가 아니라 같은 SQL의 반복. 서로 다른 쿼리 60개는 N+1이 아니고, 파라미터만 다른 동일 SQL 수십 개가 N+1이다.
결론 프레임 한 문장?
N+1은 성능 문제가 아니라 회귀다. 한 번 고쳐도 다음 PR에서 되살아나므로 사람의 주의력이 아니라 테스트로 고정한다.

8-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

쿼리 수를 못 박는 테스트는 리팩터링마다 깨진다. 유지보수 비용이 이득보다 크지 않나요? 시니어 변별힌트: "그래도 해야 한다"로 밀면 감점. 세 단계로 다룬다 — 대상 / 형태 / 그리고 매직 넘버를 없애는 방법

타당한 지적이고, "그래도 해야 한다"로 밀면 감점이다. 세 단계로 다룬다.

1
대상을 좁힌다. 전 API가 아니라 목록·검색 API에만 붙인다. N+1은 컬렉션이나 연관을 순회하는 목록에서 터지고 단건 조회에서는 거의 안 터진다. 대상이 좁으면 유지보수량 자체가 작다.
2
정확한 수보다 상한을 쓴다. isEqualTo(1)은 정당한 변경에도 깨진다. isLessThanOrEqualTo(3)이면 의도를 표현하면서 여유가 생긴다. 다만 상한을 너무 크게 잡으면 감지력이 죽으니 "정상일 때의 쿼리 수 + 1~2" 정도가 적당하다.
3
가장 좋은 형태는 절대 수가 아니라 "비례하지 않음"을 단정하는 것이다. N+1의 정의가 "쿼리 수가 데이터 건수에 비례한다"이므로, 정의를 그대로 테스트로 옮기면 매직 넘버가 사라진다.
// 측정 헬퍼 — flush/clear 와 카운터 초기화를 한 자리에 모은다 (2-2 의 순서를 강제한다)
private int countQueries(Runnable action) {
    em.flush();
    em.clear();                                  1차 캐시가 남아 있으면 측정이 무의미
    Statistics stats = emf.unwrap(SessionFactory.class).getStatistics();
    stats.clear();
    action.run();
    return (int) stats.getPrepareStatementCount();
}

// 회원 n 명에게 주문을 1건씩 붙인다 — 카디널리티가 곧 n 이 된다 (2-3)
private void 서로_다른_회원의_주문을_추가한다(int n) {
    for (int i = 0; i < n; i++) {
        Member m = memberRepository.save(new Member("회원" + UUID.randomUUID()));
        orderRepository.save(new Order(m, "상품"));
    }
}

// 건수를 두 배로 늘려도 쿼리 수가 같아야 한다 — N+1 의 정의를 그대로 단정한다
@Test
void 쿼리_수가_데이터_건수에_비례하지_않는다() {
    서로_다른_회원의_주문을_추가한다(10);          // 총 10명
    int q10 = countQueries(() -> orderService.list());

    서로_다른_회원의_주문을_추가한다(10);          // 10명 더 — 총 20명
    int q20 = countQueries(() -> orderService.list());

    assertThat(q20)
            .as("건수를 2배로 늘렸는데 쿼리가 늘었다 = N+1")
            .isEqualTo(q10);
}
이 형태는 리팩터링으로 쿼리 수가 1개에서 2개로 바뀌어도 깨지지 않고, N+1이 생기면 반드시 깨진다
정확히 원하는 성질만 고정하므로 유지보수 비용이 가장 낮다 — 여기까지 말하면 이 꼬리질문은 오히려 가점이 된다
컬렉션이 둘 이상이고 페이징까지 필요한 화면은 어떻게 푸나요? 필수힌트: fetch join은 벽 둘에 동시에 걸려 애초에 후보가 아니다. 그리고 마지막에 "도구가 아닌 답"이 하나 더 있다

fetch join은 4-1의 벽 둘에 동시에 걸려서 애초에 후보가 아니다. 순서대로 푼다.

1
부모만 페이징으로 조회한다. 조인이 없으니 limit/offset이 SQL에 정상 적용된다. 이것이 출발점이고, 여기서 흔들리면 나머지가 다 무너진다.
2
컬렉션은 default_batch_fetch_size에 맡긴다. 각 컬렉션이 별도의 IN 쿼리로 채워지므로 카테시안 곱이 없고, 총 쿼리는 1 + (컬렉션 종류 수 × ceil(부모 수 / size)) 수준이다. 부모 20건에 컬렉션 2종, size 100이면 1 + (2 × 1) = 총 3개다.
3
조회 전용이면 두 번(또는 세 번) 조회 후 조합(4-4)이 더 낫다. 필요한 컬럼만 읽고 엔티티를 안 만든다.
4
요구사항을 되짚는 단계도 답에 포함시킨다. 컬렉션 둘이 진짜로 필요한 경우보다, 하나는 개수만 필요한 경우가 많다. 그러면 컬렉션 fetch가 아니라 집계 프로젝션(count)으로 끝난다. 도구로 밀어붙이기 전에 이걸 확인하는 게 가장 저렴한 해결이다.
default_batch_fetch_size를 전역 1000으로 두면 부작용은? 트레이드오프 판단힌트: 성능 쪽 부작용 셋. 그런데 가장 중요한 부작용은 성능이 아니다

성능 쪽 부작용 셋과, 그보다 중요한 부작용 하나가 있다.

  • IN 파라미터 수 한계 — DB마다 상한이 있다(오라클의 1000이 대표적). Hibernate가 dialect의 파라미터 한계를 보고 배치를 잘라주므로 설정값이 그대로 SQL에 나가는 건 아니지만, 설정값을 키운 만큼 효과가 나지 않는 구간이 생긴다.
  • 한 번에 올라오는 행 수 — size 1000이면 컬렉션 초기화 한 번에 수천~수만 행이 메모리로 올라올 수 있다. 응답 지연이 특정 요청에 몰리는 스파이크가 된다.
  • 실행 계획 캐시 — 바인딩 파라미터 개수가 다른 SQL이 여러 개 생기면 캐시가 나뉜다. 다만 6.2 이후로는 SQL 모양이 고정(정확히 size개 플레이스홀더 + null 패딩, 또는 배열 파라미터 1개)되어 이 압박이 이전보다 줄었다(4-3).
가장 중요한 부작용은 성능이 아니라 은폐다 — 1+1000이 1+1이 되면서 N+1이 있다는 사실 자체를 팀이 모르게 된다

그 상태로 코드가 쌓이면 나중에 fetch 전략을 손볼 때 어디부터 봐야 하는지 알 수 없다. 그래서 답은 "전역 batch fetch size는 깔되, 6절의 탐지 장치와 세트로 깐다"이다. 안전망은 피해를 줄이는 장치이고 탐지는 원인을 드러내는 장치라서, 안전망만 깔면 조용히 나빠지는 시스템이 된다. 값은 100~1000 범위에서 시작하고, 실측 없이 1000으로 올리지 않는다.

이미 운영 중인 서비스에서 N+1이 어디 있는지 전수로 찾으려면? 필수힌트: 새로 만드는 팀이 아니라 "물려받은 팀"의 질문이다. 답의 순서가 곧 실행력
1
스테이징에 6-5 스니퍼를 켜고 트래픽을 흘린다. e2e 스크립트, 부하 테스트 스크립트, 또는 운영 트래픽 미러링. 나오는 것은 "같은 SQL이 몇 번 반복됐는가" 상위 목록이고, 이게 곧 작업 목록이다. 코드를 한 줄도 안 고치고 현황이 나오는 것이 이 방법의 장점이다.
2
APM을 쿼리 수 순으로 정렬한다(6-8). 응답 시간 순으로 보면 안 보인다.
3
Statistics를 Micrometer로 노출해 비율 지표를 만든다. 쿼리 실행 수 / 요청 수를 대시보드에 올리면, 특정 배포 이후 비율이 튀는 것으로 회귀를 잡을 수 있다.
4
정적으로도 좁힌다. ArchUnit·grep으로 to-one EAGER 매핑과 목록을 반환하는 리포지토리 메서드를 교차하면 후보가 나온다. 다만 정적 탐색은 사용처에서 태어나는 유형을 못 잡으므로 보조 수단이다.

우선순위는 트래픽 × 카디널리티가 큰 API부터다. 하루 10회 호출되는 관리자 화면의 1+300은 급하지 않고, 초당 100회 호출되는 목록의 1+20이 훨씬 급하다. 그리고 고친 API마다 6-3의 테스트를 남긴다 — 이게 없으면 같은 작업을 1년 뒤에 또 한다.

이 장치들을 팀에 도입한다면 어느 순서로 넣나요? 시니어 변별힌트: 전부 한 번에 넣으면 실패한다. 기준은 도입 비용 · 거짓 경보 · 즉시 이득
1
전역 default_batch_fetch_size — 설정 한 줄, 코드 수정 0, 즉시 피해 감소. 단독으로 두면 4-3의 은폐가 생기므로 2번과 같은 스프린트에 넣는다.
2
요청 단위 스니퍼(개발·스테이징) — 기존 코드 수정이 0이고 프로파일로 격리돼 위험이 낮은데, 현황 목록이 나온다. 무엇을 고칠지 모르는 상태에서 테스트를 먼저 쓰는 것은 순서가 거꾸로다.
3
쿼리 수 단정 테스트 — 2번에서 나온 상위 API부터 붙인다. 전면 도입을 시도하면 분량에 압사당해 중단된다. "새로 만드는 목록 API에는 반드시 붙인다"를 컨벤션으로 추가하면 시간이 지나면서 커버리지가 자동으로 올라간다.
4
ArchUnit EAGER 금지 — 기존 위반이 많으면 FreezingArchRule로 동결해 신규 유입만 차단하고, 동결 목록을 스프린트마다 줄인다.
5
APM 대시보드에 쿼리 수/요청 지표 — 마지막 그물. 앞의 넷이 없는 상태에서 이것만 있으면 "운영에서 발견하는 팀"이다.
관통하는 원칙 — 현황 파악 → 상위부터 고정 → 신규 유입 차단

그리고 3번과 4번은 성질이 다르다는 점을 말하면 좋다 — 3번은 결과를 고정하고 4번은 원인을 봉쇄한다. 둘 중 하나만 고르라면 3번이다. 매핑이 완벽해도 N+1은 사용처에서 태어나기 때문이다.

조인을 걸었는데 N+1이 그대로입니다. 왜 그런가요? 함정힌트: JPQL에 join이라고만 썼는지 확인한다. SQL에서 무엇이 달라지는가

fetch가 빠졌을 가능성이 가장 크다.

일반 join은 SQL 조인만 만들고 select 목록에는 부모 컬럼만 남는다. 조인은 걸렸지만 연관은 여전히 프록시이므로, 값을 꺼내는 순간 프록시 초기화가 그대로 나간다 — N+1이 사라지지 않는다.

join fetch는 연관 엔티티의 컬럼까지 select 목록에 올려 한 번에 채운다. 그래서 프록시가 남지 않는다.

그대로 조인만 걸린다
"select o from Order o join o.member m"
해결 연관 컬럼까지 올린다
"select o from Order o join fetch o.member"

@EntityGraph를 붙였는데도 그대로라면 다른 원인을 본다 — type이 FETCH인지, 경로 문자열의 속성 이름 오타가 아닌지, 그리고 N+1이 그 쿼리가 아니라 다른 경로에서 나고 있는지다. 6-5의 스니퍼가 찍는 스택트레이스가 이 판별을 즉시 끝내준다.

N+1이라고 하는데 쿼리가 1 + 1 두 개만 나갑니다. N+1이 아닌 건가요? 함정힌트: 1절의 계산식으로 돌아간다. "지금 안 터진다"와 "구조적으로 안전하다"는 다르다

N+1이 맞다. 다만 지금 데이터의 카디널리티가 1일 뿐이다. 코드는 연관 id 종류 수만큼 쿼리를 쏘는 구조 그대로이고, 운영 데이터가 흩어지는 순간 1+800이 된다.

이 상황이 정확히 2-1의 픽스처 A다. 그리고 목록 API의 운영 데이터는 대체로 카디널리티가 높다(주문 목록의 주문자는 거의 다 다른 사람이다). 즉 "지금 두 개"는 데이터가 우연히 그런 것이지 코드가 안전한 게 아니다.

판정 기준을 "지금 쿼리가 몇 개인가"에서 "건수를 늘리면 쿼리가 늘어나는가"로 바꾼다
이 판정을 그대로 테스트로 옮긴 것이 8-2 첫 질문의 "비례하지 않음" 테스트다
픽스처의 카디널리티도 맞췄고 clear()도 했는데 쿼리 수 테스트가 계속 통과합니다. 어디를 봐야 하나요? 함정힌트: "장치가 있는데 아무것도 못 잡는 상태"의 원인은 픽스처 말고도 넷 더 있다

이 페이지에 흩어져 있는 "조용한 실패" 원인들을 체크리스트로 모으면 이렇다.

  • hibernate.generate_statistics가 꺼져 있다 — 기본값이 false라서 카운터가 항상 0이다. 단정이 무조건 통과한다(6-3).
  • DataSource를 프록시로 감싸지 않았다 — SQLStatementCountValidator 계열은 자체 상태가 없어서 모든 카운트가 0이 된다(6-4).
  • 테스트 프로파일에 전역 default_batch_fetch_size가 켜져 있다 — 1+50이 1+1로 줄어 상한 단정을 통과해버린다. 안전망이 그대로 탐지 장치를 무력화한 경우다(4-3의 은폐).
  • 검증 대상이 다른 스레드에서 쿼리를 쏜다 — @Async·CompletableFuture·parallel stream이면 조용히 0으로 집계된다(6-4).
  • 측정 구간이 실제 운영 경로와 다르다 — 테스트가 리포지토리만 부르고 DTO 변환(=연관을 실제로 건드리는 지점)을 안 태우면 프록시가 초기화되지 않는다. 서비스 메서드 단위로 태워야 한다.

가장 빠른 자가 진단은 일부러 N+1을 만들어 테스트가 실패하는지 확인하는 것이다 — fetch join을 잠깐 지워보고 빨간불이 뜨지 않으면 그 테스트는 아무것도 지키고 있지 않다. 가산점

List를 Set으로 바꿨더니 MultipleBagFetchException이 사라졌습니다. 해결된 건가요? 함정힌트: 예외가 사라진 것과 문제가 사라진 것은 다르다

아니다. 예외를 없앤 것이지 카테시안 곱을 없앤 게 아니다.

rows(A) × rows(B)는 그대로 발생하고, Hibernate가 메모리에서 중복만 걷어낸다. 즉 DB에서 읽어 네트워크로 실어 나르는 데이터량 자체는 그대로 곱해진다. 컬렉션이 각각 100개면 10,000행이다. @OrderColumn을 붙여 LIST로 만드는 것도 결과가 같다.

감지 장치를 끄는 행위에 가깝다. 컬렉션이 둘 이상이면 정답은 batch fetch size다 — 각 컬렉션이 별도의 IN 쿼리로 채워지므로 곱셈 자체가 일어나지 않는다. 그리고 예외가 던져지는 시점이 부트스트랩이 아니라 쿼리 실행 시점이라는 점도 함께 말하면 좋다 — 시작할 때 크게 실패해주지 않으므로 이 코드는 테스트가 없으면 배포된다.

distinct는 붙여두면 안전한 것 아닌가요? 함정힌트: Hibernate 5의 관행이다. 6에서 무엇이 바뀌었고, 무엇이 제거됐는가

Hibernate 6부터는 붙이면 손해다.

6부터 fetch join의 부모 엔티티 중복은 항상 Hibernate가 걸러낸다. 그래서 distinct가 필요 없어졌고, 5.2에서 도입된 hibernate.query.passDistinctThrough(SQL로 distinct를 넘기지 않게 하는 설정)는 6.0에서 제거됐다.

중요한 귀결은 이것이다 — 6부터 distinct를 쓰면 항상 SQL의 select distinct로 나가고 이를 막을 방법이 없다. 조인으로 뻥튀김된 전체 행에 대해 DB가 정렬·해시 중복 제거를 하게 되므로 실제 비용이 발생한다.

6.x에서 distinct는 "안전하게 붙여두는 것"이 아니라 불필요한 DB 비용이다
@EntityGraph를 쓰면 컬렉션에도 페이징이 되지 않나요? 함정힌트: 판정에 걸리는 것이 "문장"인지 "그래프"인지를 생각한다

되지 않는다. fetch join과 같은 SQL로 번역되므로 두 벽이 그대로 적용된다.

메커니즘까지 말하면 확실하다. Hibernate 6.6이 페이징을 메모리로 돌리는 판정은 hasLimit && containsCollectionFetches인데, 이 containsCollectionFetches가 "HQL 문장에 컬렉션 fetch가 있는가" 또는 "적용된 EntityGraph에 컬렉션이 EAGER 노드로 들어 있는가"의 논리합이다.

문장이 아니라 그래프에 적힌 것도 똑같이 판정에 걸린다 — fetchgraph/loadgraph 힌트도 같다

반대로 EAGER 노드가 전부 to-one인 EntityGraph는 이 판정에 걸리지 않아 페이징이 정상 동작한다. 그리고 실무에서 더 위험한 조합이 하나 있다 — @EntityGraph(attributePaths = "items")를 붙인 채 batch fetch size만 키우는 것이다. 인메모리 페이징은 그대로 남는다. 지켜야 할 규칙은 "컬렉션은 쿼리에서 fetch하지 않는다"이고, batch fetch size는 그 규칙을 지켰을 때만 대신 막아준다.

default_batch_fetch_size를 설정했는데 쿼리가 그대로입니다. 함정힌트: 원인 네 가지. 하나는 프로퍼티 경로, 하나는 버전, 하나는 쿼리 쪽
  • 프로퍼티 경로 오타 — spring.jpa.hibernate.default_batch_fetch_size는 조용히 무시된다. Spring Boot에는 전용(1급) 프로퍼티가 없으므로 반드시 spring.jpa.properties.hibernate.default_batch_fetch_size로 넘겨야 한다. "설정했는데 안 먹는다"의 단골 원인이다.
  • 쿼리가 이미 컬렉션을 fetch하고 있다 — join fetch나 컬렉션을 지정한 @EntityGraph가 붙어 있으면 batch fetch가 개입할 여지가 없고, 인메모리 페이징도 그대로다.
  • 버전 — 1 + ceil(N/size) 공식은 6.2부터 실제와 맞는다. 5.x는 내림차순 배치 크기 계열을 써서 쿼리 수가 공식과 어긋난다. 또 @ManyToMany에 @BatchSize가 무시되던 버그(HHH-16005)의 수정 버전이 6.1.7 / 6.2.0이다.
  • 다른 설정과 혼동 — hibernate.query.in_clause_parameter_padding은 이 배치 fetch와 무관한 설정이다(HQL의 IN 목록 확장과 다중 id 로딩에 적용된다). 두 개를 섞어 말하면 틀린다.

슬로우 쿼리 로그와 APM이 있는데 왜 부족한가요? 필수힌트: 하나는 "판정 단위", 하나는 "계측 시점". 서로 다른 이유로 부족하다

부족한 이유가 서로 다르다. 이 구분을 말하면 답변의 층이 확실히 올라간다.

슬로우 쿼리 로그는 N+1을 거의 잡지 못한다. 판정 단위가 "쿼리 1건의 실행 시간"이기 때문이다. N+1이 쏟아내는 개별 쿼리는 select * from member where id = ? 같은 기본 키 단건 조회라서 인덱스를 정확히 타고 1ms 미만으로 끝난다. 임계치가 보통 1초이므로 1,000건이 나가도 한 건도 걸리지 않는다. 느린 것은 개별 쿼리가 아니라 왕복 횟수의 누적인데, 슬로우 쿼리 로그에는 "이 요청이 쿼리를 몇 번 왕복했는가"를 세는 개념 자체가 없다.

APM은 잡는다. 다만 성질이 다르다. 요청 하나의 타임라인 위에 모든 쿼리를 늘어놓으므로 동일 쿼리가 수백 개 쌓인 그림이 그대로 보인다. 문제는 계측 대상이 "실제 운영 트래픽"이라는 점이다 — 관측 대상이 존재하려면 그 코드가 이미 배포되어 사용자 요청을 받고 있어야 한다. 구조상 배포보다 앞설 수가 없다.

슬로우 쿼리 로그는 판정 단위가 어긋나서, APM은 계측 시점이 배포 이후라서 부족하다
예방은 빌드·테스트에서, 조기 발견은 스테이징 카운터에서, 사후 발견은 APM에서
N+1을 왜 "성능 문제"가 아니라 "회귀"라고 부르나요? 시니어 변별힌트: 분류를 바꾸면 처방이 바뀐다. 인덱스와 비교해서 말한다

분류가 처방을 결정하기 때문이다.

성능 문제는 한 번 고치면 끝난다. 인덱스를 걸면 그 인덱스는 남아 있고, 다음 PR이 인덱스를 지우지는 않는다. 그래서 처방이 "측정하고 고친다"로 끝난다.

N+1은 고쳐도 재발한다. 구조적 이유가 셋이다 — ① 원인과 발생 지점이 멀다(매핑 파일에서 태어나고 서비스 파일에서 터진다) ② 기본값이 위험한 쪽이다(to-one 기본값이 EAGER라 아무것도 안 하면 위험해진다) ③ 기능 추가만으로 되살아난다(o.getDelivery().getAddress() 한 줄).

재발하는 문제의 처방은 "더 잘 보기"가 아니라 "테스트로 고정하기"이고, 이건 N+1만의 이야기가 아니라 회귀 일반의 처방이다. 버그를 고칠 때 재현 테스트를 먼저 쓰는 것과 정확히 같은 논리다 — 다만 N+1은 예외를 던지지 않아서 "실패하는 테스트"를 자연스럽게 얻지 못하고, 쿼리 수라는 관측 지표를 직접 단정해야만 실패를 만들 수 있다.

"N+1은 성능 문제로 분류하면 계속 재발합니다. 회귀로 분류하고, 목록 API마다 쿼리 수를 단정하는 테스트를 둬서 다음 PR에서 되살아나면 빌드가 깨지게 만듭니다."
한 줄 요약
N+1의 N은 결과 행 수가 아니라 1차 캐시에 없는 서로 다른 연관 id 수라서 건수만 늘린 픽스처로는 재현되지 않고(픽스처는 카디널리티로 설계하고 측정 직전에 clear()한다), 해결책은 행이 뻥튀김되는 조인 계열(fetch join·@EntityGraph — 컬렉션 + 페이징 금지, 컬렉션 둘 이상 금지)과 행이 늘지 않는 분리 조회 계열(batch fetch size·DTO 두 번 조회 — 페이징과 공존)로 갈리므로 "컬렉션 + 페이징이면 fetch join을 버린다"가 선택 기준의 핵심이며, 무엇보다 N+1은 성능 문제가 아니라 회귀여서 한 번 고쳐도 다음 PR에서 되살아나므로 — 쿼리 로그를 잘 보는 습관이 아니라 쿼리 수를 단정하는 테스트 · 요청 단위 카운터 · ArchUnit이라는 자동 장치로 고정해야 한다.
