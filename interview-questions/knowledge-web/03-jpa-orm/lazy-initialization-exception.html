3. JPA / ORM

LazyInitializationException — 처방의 범위를 문제의 범위에 맞춘다

📖 약 15분 🧩 6개 섹션 0/6 섹션 이해
🎯 핵심 관전 포인트

원인을 정확히 말하면 "트랜잭션이 끝나서"가 아니라 EntityManager(세션)가 닫힌 뒤에 프록시 초기화를 요청해서다. 이 구분이 결정적인 이유는 OSIV가 정확히 그 틈을 이용하는 장치이기 때문이다 — 트랜잭션은 서비스에서 끝났는데 EntityManager는 응답이 끝날 때까지 열어둔다. Spring Boot에서 spring.jpa.open-in-view가 기본 true 라서, 많은 팀이 이 예외를 거의 못 보고 지나간다. 해결책은 네 가지인데 중요한 것은 목록이 아니라 범위다: fetch join / @EntityGraph 는 그 쿼리 한 곳에만 듣는 지점별 처방, 트랜잭션 안에서 DTO 변환은 엔티티가 계층을 넘지 않게 하는 근본 처방, 트랜잭션 범위 확대는 커넥션 보유 시간을 늘려 대용량에서 금지, EAGER 전환과 OSIV는 전역 스위치로 덮는 증상 은폐다. 예외는 한 지점에서 났는데 EAGER는 모든 쿼리를 바꾼다 — 처방의 범위가 문제의 범위보다 크면 그건 해결이 아니라 이동이다.

0

질문 + 의도

▾
면접 질문

"LazyInitializationException은 왜 발생하나요? 해결 방법들(트랜잭션 범위 조정, fetch join, DTO 변환 시점)과 각각의 트레이드오프는?"

출제 의도JPA 입문자가 가장 먼저 부딪히는 예외이고, 해결책의 선택(트랜잭션 연장? fetch join? DTO 변환 시점 이동?)이 곧 계층 설계 이해를 드러낸다. "무조건 EAGER로" 또는 "OSIV 켜서" 같은 답은 증상 은폐임을 아는지 — 예외 하나로 영속성 컨텍스트의 생명주기 전체를 검증하는 효율 높은 질문이다.

함정: 해결책을 나열하는 것만으로는 변별이 안 된다. 각 해결책이 어느 범위에 작용하는지, 그리고 그 범위가 문제의 범위와 맞는지를 말해야 한다.

1

정확한 원인 — 트랜잭션이 아니라 EntityManager

▾

전형적인 예외 메시지는 이렇게 생겼다.

text
org.hibernate.LazyInitializationException:
    could not initialize proxy [com.example.Team#1] - no Session

no Session이라는 문구가 핵심이다. 트랜잭션이 아니라 세션(JPA 용어로는 EntityManager)이 없다고 말하고 있다.

1-1. 지연 로딩의 실체는 프록시

java
Member member = memberRepository.findById(1L).orElseThrow();
// member.team 필드에는 실제 Team이 아니라 '프록시'가 들어 있다

프록시란 Hibernate가 런타임에 만든 가짜 객체다. 겉모습은 Team이지만 속은 비어 있고, "내가 실제로 필요해지는 순간 DB에서 읽어오겠다"는 약속만 들고 있다. 그래서 member.getTeam().getName()처럼 실제 값을 요구하는 순간에 초기화 쿼리가 나간다.

문제는 그 쿼리를 누가 실행하느냐다. 프록시는 자기를 만들어준 EntityManager를 붙들고 있고, 그 EntityManager가 닫혀 있으면 쿼리를 실행할 방법이 없다. 그때 던지는 것이 LazyInitializationException이다.

java
// ❌ BEFORE — 트랜잭션(과 EntityManager)이 서비스 메서드에서 끝난다
@Transactional(readOnly = true)
public Member findMember(Long id) {
    return memberRepository.findById(id).orElseThrow();
}   // ← 여기서 EntityManager가 닫힌다

// 컨트롤러
Member member = memberService.findMember(1L);
String teamName = member.getTeam().getName();   // 💥 LazyInitializationException

1-2. 왜 "트랜잭션이 끝나서"라고 말하면 부정확한가

두 개의 생명주기가 보통은 같이 끝나지만, 반드시 같이 끝나는 것은 아니다.

상황트랜잭션EntityManager지연 로딩
기본(OSIV 끔)서비스에서 종료서비스에서 종료❌ 예외
OSIV 켬서비스에서 종료응답 완료까지 유지✅ 동작
트랜잭션 확대컨트롤러까지 유지컨트롤러까지 유지✅ 동작

가운데 줄이 이 예외를 이해하는 열쇠다. 트랜잭션은 끝났는데 지연 로딩이 되는 상태가 실재하며, 그것이 Spring Boot의 기본값이다.

2

OSIV — 예외가 안 나던 이유

▾

2-1. 무엇인가

OSIV(Open Session In View) 는 EntityManager를 HTTP 요청이 시작될 때 열고 응답이 끝날 때 닫는 장치다. 트랜잭션 경계(@Transactional)와 무관하게 세션을 살려두므로, 컨트롤러나 뷰 템플릿, JSON 직렬화 단계에서도 지연 로딩이 동작한다.

Spring Boot에서 spring.jpa.open-in-view의 기본값은 true 다. 그래서 애플리케이션을 띄우면 이런 경고가 뜬다.

text
spring.jpa.open-in-view is enabled by default. Therefore, database queries may be
performed during view rendering. Explicitly configure spring.jpa.open-in-view to
disable this warning

"기본으로 켜져 있으니, 뷰 렌더링 중에 DB 쿼리가 나갈 수 있다"는 안내다. 프레임워크가 이건 알고 쓰라고 경고하는 설정이라는 점이 이미 성격을 말해준다.

2-2. 대가 — 커넥션 보유 시간

OSIV의 비용은 커넥션을 오래 붙잡는 것이다.

트랜잭션이 끝난 뒤 컨트롤러에서 지연 로딩을 하면, 그 쿼리를 위해 커넥션이 필요하다. 그리고 그 커넥션은 EntityManager가 닫힐 때까지 — 즉 응답이 완료될 때까지 — 풀로 돌아가지 않는다. 뷰 렌더링이나 JSON 직렬화가 느린 요청, 응답 크기가 큰 API, 외부 API 호출이 뒤에 붙은 흐름에서 이 시간이 길어진다.

커넥션 풀은 유한하다(HikariCP 기본 10개 수준). 요청당 커넥션 보유 시간이 늘어나면 동시 처리량이 그만큼 줄고, 트래픽이 늘면 커넥션 풀 고갈 → 요청 대기 → 타임아웃의 연쇄가 생긴다. 대용량 트래픽 서비스에서 OSIV를 끄는 이유가 이것이다.

부작용이 하나 더 있다. 컨트롤러·직렬화 단계에서 지연 로딩이 자유롭게 일어나면 쿼리가 서비스 계층 밖에서 나간다. 서비스 코드만 읽어서는 총 몇 개의 쿼리가 나가는지 알 수 없고, 응답 필드를 하나 추가한 것만으로 N+1이 생긴다. 즉 OSIV는 LazyInitializationException을 막는 대신 N+1을 보이지 않는 곳으로 밀어넣는다. 탐지 방법은 N+1 탐지와 해결에 있다.

💡

확인 범위: 커넥션이 정확히 언제 풀로 반환되는지는 Hibernate의 커넥션 릴리스 모드와 트랜잭션 종류(resource-local / JTA)에 따라 달라진다. 위 설명은 "트랜잭션 밖에서 지연 로딩을 하면 그 커넥션이 세션 종료 시점까지 유지된다"는, 널리 통용되는 동작을 전제로 한 것이다. 팀의 설정에서 실제 보유 시간을 재려면 HikariCP의 활성 커넥션 지표와 요청 처리 시간을 함께 보는 것이 확실하다.

2-3. OSIV가 켜져 있어도 예외가 나는 자리

"켜져 있는데 왜 나는가"는 좋은 꼬리질문이다. OSIV는 웹 요청 스코프에만 작용하므로 그 밖에서는 무력하다.

  • 테스트 코드 — 웹 요청이 없으므로 인터셉터가 걸리지 않는다. @DataJpaTest나 단위 테스트에서 서비스 메서드 반환값의 연관을 만지면 바로 터진다.
  • @Async·@Scheduled·별도 스레드 — EntityManager는 스레드에 묶여 있다. 다른 스레드로 엔티티를 넘기면 그 스레드에는 세션이 없다.
  • 배치 처리 — 웹 요청 밖이다.
  • 응답 직렬화가 끝난 뒤 — 인터셉터가 세션을 닫은 이후 코드(일부 필터, 로깅 AOP).
  • 엔티티를 캐시나 정적 필드에 담아 재사용 — 다음 요청에서는 이미 닫힌 세션의 프록시다.

"자주 봤다"는 사람이 OSIV의 존재를 몰랐다면, 실제로 본 자리는 대개 위 목록 중 하나다. 이걸 짚어내면 원인 분석 능력을 보일 수 있다.

3

해결책 네 가지 — 목록이 아니라 범위로 본다

▾

3-1. fetch join / @EntityGraph — 지점별 처방 (표준)

필요한 연관을 조회하는 그 쿼리에서 함께 가져온다.

java
// ✅ JPQL fetch join
@Query("select m from Member m join fetch m.team where m.id = :id")
Optional<Member> findWithTeam(@Param("id") Long id);

// ✅ @EntityGraph — 선언적으로
@EntityGraph(attributePaths = "team")
Optional<Member> findById(Long id);
  • 범위: 이 쿼리 하나. 다른 조회에는 영향이 없다.
  • 트레이드오프: 컬렉션을 fetch join하면 페이징과 함께 쓸 수 없고(전체를 메모리에 올려 자르는 동작), bag 성격의 컬렉션을 둘 이상 fetch join하면 예외가 난다. 이 제약과 대안(배치 fetch size)은 N+1 탐지와 해결에 정리되어 있다.
  • 왜 표준인가: 문제가 난 지점에만 정확히 작용하고, 무엇을 함께 가져오는지가 코드에 드러난다.

3-2. 트랜잭션 안에서 DTO로 변환 — 근본 처방

엔티티가 계층을 넘어가지 못하게 만든다.

java
// ❌ BEFORE — 엔티티를 컨트롤러로 반환한다
@Transactional(readOnly = true)
public Member findMember(Long id) {
    return memberRepository.findById(id).orElseThrow();
}

// ✅ AFTER — 트랜잭션 안에서 DTO로 변환해 반환한다
@Transactional(readOnly = true)
public MemberResponse findMember(Long id) {
    Member member = memberRepository.findById(id).orElseThrow();
    return new MemberResponse(
            member.getId(),
            member.getName(),
            member.getTeam().getName()   // 세션이 살아 있으므로 안전
    );
}
  • 범위: 계층 경계 전체. 이 방식을 규칙으로 세우면 이 예외가 구조적으로 발생할 수 없다 — 컨트롤러에 프록시가 도달하지 않기 때문이다.
  • 트레이드오프: 화면별 DTO와 변환 코드가 늘어난다. 다만 이 비용은 대가라기보다 다른 이득을 함께 가져온다 — 엔티티 스펙 변경이 API 응답에 새어나가지 않고, 응답에 무엇이 담기는지가 타입으로 고정된다.
  • 더 나아가 DTO 프로젝션(처음부터 필요한 컬럼만 조회)을 쓰면 엔티티를 영속성 컨텍스트에 올리지 않으므로 스냅샷·변경 감지 비용까지 없앤다. 조회 전용 화면의 정답이다.

3-3. 트랜잭션 범위 확대 — 대용량에서 금지

@Transactional을 컨트롤러까지 올리거나 트랜잭션을 길게 잡는 방식이다.

  • 범위: 해당 요청 흐름 전체.
  • 트레이드오프: 커넥션 보유 시간이 그만큼 늘어난다. OSIV와 같은 문제인데, 여기에 더해 쓰기 트랜잭션이 길어지면 DB 락 보유 시간도 늘어난다. 뷰 렌더링이나 외부 API 호출 시간까지 트랜잭션 안에 들어가면, 트래픽이 조금 늘어도 커넥션 풀과 락 경합이 동시에 터진다.
  • 실무 원칙은 반대 방향이다: 트랜잭션은 짧게, 경계는 서비스 메서드 하나에.

3-4. EAGER 전환 — 증상 은폐

fetch = FetchType.EAGER로 바꾸면 예외는 사라진다. 그런데 이건 해결이 아니다.

범위가 맞지 않는다. 예외는 특정 화면 한 곳에서 났는데, EAGER는 그 연관을 쓰는 모든 쿼리를 바꾼다. 그 연관이 필요 없던 조회에서도 조인이나 추가 쿼리가 나가고, 연관이 겹치면 조인 깊이가 누적된다. 게다가 쿼리 단위로 되돌리기가 어렵다 — LAZY를 필요할 때 fetch join으로 켜는 건 쉬운데, EAGER를 특정 쿼리에서만 끄는 것은 훨씬 번거롭다. 자세한 근거는 EAGER vs LAZY 기본 전략에 있다.

한 문장으로: 예외는 한 지점에서 났는데 처방은 전역에 적용된다. 이 비대칭을 지적할 수 있으면 이 문항의 핵심 판단을 통과한 것이다.

3-5. 비교 정리

처방작용 범위주된 대가권장도
fetch join / @EntityGraph그 쿼리 하나컬렉션+페이징 제약표준
트랜잭션 안 DTO 변환계층 경계 전체DTO·변환 코드 증가근본
트랜잭션 범위 확대요청 흐름 전체커넥션·락 보유 시간 증가지양
OSIV애플리케이션 전역커넥션 보유 시간, N+1 은닉대용량은 끔
EAGER 전환애플리케이션 전역되돌리기 어려움, 조인 폭탄지양
4

실무에서의 조합

▾

대용량 트래픽 서비스의 표준 구성은 이렇다.

yaml
spring:
  jpa:
    open-in-view: false   # 명시적으로 끈다

끄면 그동안 숨어 있던 LazyInitializationException이 드러난다. 그게 목적이다 — 어디서 지연 로딩이 계층을 넘고 있었는지가 전부 노출된다. 그 지점들을 하나씩 fetch join 또는 DTO 변환으로 정리한다.

정리 순서를 정하는 실용적 기준:

  1. 응답 DTO 변환을 서비스 계층으로 내린다. 이것만으로 대부분이 사라진다.
  2. 남은 곳 중 연관을 반드시 함께 읽어야 하는 조회에 fetch join / @EntityGraph를 붙인다.
  3. 컬렉션 + 페이징이 얽힌 곳은 fetch join을 쓰지 못하므로 배치 fetch size로 푼다.
  4. 조회 전용 화면은 아예 DTO 프로젝션으로 바꿔 엔티티를 올리지 않는다.

그리고 4단계를 끝낸 뒤에도 회귀를 막으려면 쿼리 수를 테스트로 고정해야 한다 — N+1 탐지와 해결의 자동 탐지 장치가 그대로 쓰인다.

5

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

불편해진다. 그리고 그 불편이 비용을 드러내는 역할을 한다. OSIV가 켜져 있으면 "컨트롤러에서 연관을 만지면 쿼리가 나간다"는 사실이 코드에 보이지 않아, 응답 필드를 하나 추가하는 작업이 조용히 쿼리 100개를 늘린다. 끄면 그 순간 컴파일이 아니라 예외로 알려주므로, 개발자가 의도적으로 fetch 전략을 선택하게 된다. 즉 OSIV를 끄는 것은 편의를 버리는 게 아니라 결정을 앞당기는 것이다.

동작은 한다. 하지만 두 가지가 틀어진다. ① 트랜잭션 경계가 컨트롤러로 올라가면 커넥션·락 보유 시간이 요청 전체로 늘어난다 ② 트랜잭션 경계와 비즈니스 단위가 어긋난다 — "무엇이 하나의 원자적 작업인가"를 표현해야 하는 자리가 웹 계층으로 번지면, 나중에 그 서비스를 다른 진입점(배치, 메시지 컨슈머)에서 재사용할 때 경계가 없다. 트랜잭션은 서비스 메서드에 두는 것이 원칙이다.

트랜잭션 안에서 Hibernate.initialize(member.getTeam())을 호출하면 예외는 막힌다. 다만 이건 fetch join과 같은 목적을 쿼리를 한 번 더 써서 달성하는 것이다(조인 대신 추가 SELECT). 초기화 대상이 컬렉션이고 대상이 여러 건이면 그 자체로 N+1이 된다. "연관을 명시적으로 로딩한다"는 의도는 맞으니, 목적이 같다면 처음 조회에서 함께 가져오는 fetch join / @EntityGraph가 우선이다.

프록시가 초기화 쿼리를 실행하려면 자기를 만든 세션(EntityManager)이 열려 있어야 한다. no Session은 그 세션이 이미 닫혔다는 뜻이다. 여기서 파생되는 정확한 표현이 하나 있다 — 이 예외는 "트랜잭션 밖에서 났다"가 아니라 "세션 밖에서 났다" 이다. OSIV는 트랜잭션 없이 세션만 열어두는 구성이므로, 트랜잭션 밖에서도 지연 로딩이 되는 상태가 실제로 존재한다.

운영은 웹 요청이므로 OSIV가 세션을 열어두지만, 테스트는 웹 요청 스코프가 없어 서비스 메서드가 끝나는 순간 세션이 닫히기 때문이다. 그리고 이 현상은 버그가 아니라 경고로 읽어야 한다 — 테스트가 알려주는 것은 "이 코드는 OSIV에 의존하고 있다"는 사실이다. OSIV를 끄는 순간 운영에서도 똑같이 터진다. 즉 테스트가 미래의 장애를 미리 보여주고 있는 것이므로, @Transactional을 테스트에 붙여 덮지 말고 DTO 변환을 서비스로 내려 근본을 고치는 것이 맞다.

세 조건이 겹칠 때다. ① 트래픽이 크지 않아 커넥션 보유 시간이 병목이 아니다 ② 서버 사이드 렌더링(Thymeleaf 등)을 써서 뷰에서 엔티티를 자연스럽게 순회하는 구조다 ③ 팀이 작아 DTO 계층을 유지하는 비용이 상대적으로 크다. 즉 소규모 사내 시스템이나 어드민 페이지가 전형적인 자리다. 반대로 트래픽이 큰 공개 API에서는 켜둘 이유가 거의 없다 — API는 어차피 JSON DTO를 만들어야 하므로 OSIV가 주는 이점 자체가 작다. "무조건 끄세요"보다 이렇게 조건으로 답하는 편이 정확하다.

✅ 한 줄 요약

LazyInitializationException은 트랜잭션이 아니라 세션이 닫힌 뒤 프록시를 초기화하려 해서 나는 예외이고, Spring Boot가 OSIV를 기본으로 켜두기 때문에 많은 팀이 이 예외를 못 보고 지나간다 — 해결의 기준은 목록 암기가 아니라 처방의 범위를 문제의 범위에 맞추는 것이다.
