조회 전용 DTO 프로젝션
"이 조회의 목적이 변경인가, 표시인가"

면접 질문: "조회 전용 화면(상품 목록, 주문 내역)에서 엔티티 대신 DTO로 직접 프로젝션하는 이유는? 어떤 방법으로 구현하나?"

핵심 관전 포인트 — 이 질문은 결합도 질문이 아니라 조회 비용 질문이다. "엔티티를 노출하면 안 된다"(계층 경계)와 결론이 비슷해 보여도 근거의 층이 다르므로, 첫 답변에서 초점을 맞춰야 한다. 이유는 세 층이다. 1층 조회 컬럼 — 엔티티 조회는 매핑된 컬럼을 전부 읽으므로 목록에 쓰지도 않는 description TEXT, detail_html까지 DB에서 읽어 네트워크로 실어 온다. 2층 영속성 컨텍스트 비용 — 엔티티는 1차 캐시에 적재되고 변경 감지용 스냅샷이 복사되어 메모리가 사실상 2배가 되며, 커밋 시점에 엔티티 수 × 필드 수만큼 비교가 돈다. 3층 결합도 — 화면 요구와 엔티티 구조는 변경의 이유가 다르다. 여기서 @Transactional(readOnly = true)는 대체가 아니라 병행 수단이다 — 없어지는 것은 스냅샷과 변경 감지뿐이고, ① 1차 캐시 적재 ② 불필요 컬럼·전송 ③ 지연 로딩 프록시(뒤에서 누가 건드리면 쿼리 폭발)는 그대로 남는다. 구현은 JPQL select new / QueryDSL Projections·@QueryProjection / Spring Data 인터페이스 프로젝션 / 네이티브+@SqlResultSetMapping 네 가지이고, @QueryProjection은 파라미터 개수와 타입만 잡는다. 같은 타입끼리의 순서 교체는 못 잡는다 — 순서를 원천 차단하는 것은 이름 기반 매핑이다. 그리고 반드시 포기하는 것도 함께 말한다 — 1:N 조인 시 행 중복, 변경 감지 불가, 연관 탐색 불가, 도메인 메서드 사용 불가, DTO 클래스 증식. 판단 기준은 한 문장이다 — "변경이 목적이면 엔티티, 표시가 목적이면 DTO."
  • 1
    이유를 세 층으로 나눠 말한다 — 증명 가능한 것부터: ① 조회 컬럼(SELECT 절이 달라진다 — 목록 20건에 약 643KB를 읽어와 2.7KB만 쓴다) ② 영속성 컨텍스트(1차 캐시 적재 + 스냅샷 복사로 메모리 2배 + 커밋 시 전 필드 비교) ③ 결합도. 3층부터 말하면 "엔티티로 조회한 뒤 서비스에서 변환하면 되지 않나요?" 한마디에 논거가 전부 무력화된다.
  • 2
    readOnly = true는 대체가 아니라 병행 수단이다 — 없어지는 것은 스냅샷 복사와 커밋 시 변경 감지 둘뿐이고, 1차 캐시 적재 · 불필요 컬럼 전송 · LAZY 프록시 셋은 그대로 남는다. readOnly는 select 절을 한 글자도 바꾸지 않는다. 그래서 답변은 "readOnly는 붙입니다. 그리고 DTO 프로젝션도 합니다. 둘은 서로 다른 비용을 지웁니다."
  • 3
    구현은 네 가지를 알고 상황에 따라 고르되, 포기하는 것을 같은 호흡에 말한다 — 단순 조회는 인터페이스 프로젝션, 동적 조건·집계는 QueryDSL. @QueryProjection은 개수·타입만 잡고 동일 타입 순서 교체는 못 잡으므로 이름 기반 매핑과 값 단정 테스트가 마지막 안전망이다. 대가는 1:N 행 중복 · 변경 감지 불가 · 연관 탐색 불가 · 도메인 메서드 불가 · DTO 증식.

0. 질문 + 출제 의도

질문: "조회 전용 화면(상품 목록, 주문 내역)에서 엔티티 대신 DTO로 직접 프로젝션하는 이유는? 어떤 방법으로 구현하나?"

출제 의도: 목록 조회에 엔티티를 쓰면 필요 없는 컬럼까지 읽고 영속성 컨텍스트 관리 비용(스냅샷 유지)까지 지불한다. "변경이 목적인 조회"와 "표시가 목적인 조회"를 구분해 도구를 달리 쓰는지 — 조회 성능 최적화의 첫 단추이자 CQRS로 이어지는 사고의 출발점이다.

낯선 용어부터 — 프로젝션(projection)이란 관계형 대수에서 온 말로 "테이블에서 필요한 컬럼만 골라 뽑는 연산"을 가리킨다. SQL의 select 절이 하는 일이 정확히 그것이다. 그러니 DTO 프로젝션 = 엔티티 전체가 아니라 화면이 쓸 컬럼만 골라 DTO에 바로 담는 조회다. "투영"이라는 번역어처럼, 넓은 원본에 빛을 비춰 필요한 그림자만 받아내는 이미지로 생각하면 된다.
함정 두 개 — 미리 못 박아 둔다 ① 결합도 축으로 답하고 멈추는 것. "화면이 바뀌면 엔티티를 고쳐야 한다"는 참이지만 이 질문의 답이 아니다. 그 축으로는 "그럼 엔티티로 조회한 뒤 서비스에서 DTO로 변환해도 되지 않나요?" 한마디에 논거가 전부 무력화된다.
② 구현 방법을 하나만 대는 것. Projections.constructor 하나만 말하면 "그 방식을 써봤다"는 정보만 전달된다. 이 문항의 후반부는 네 가지를 알고 상황에 따라 고르는가를 본다.
이 페이지가 겨냥하는 약점 세 가지 ① "비용이 크다"를 크기 없이 말하는 것 → 2절에서 컬럼별 바이트를 직접 곱해 643KB·하루 2.6TB까지 계산하고, 커지는 조건 네 가지를 세운다.
② "readOnly면 되지 않나요?"에 무너지는 것 → 4절에서 없어지는 둘 / 남는 셋을 표와 도식으로 못 박는다. 이 문항의 심장이다.
③ 도구의 효능만 알고 경계를 모르는 것 → 6절에서 @QueryProjection이 못 잡는 것(동일 타입 순서 교체)까지 가고, 8절에서 도구가 못 막는 자리에 놓을 안전망을 세운다.
이 문서의 위치 — 12-entity-exposure-and-dto-boundary와 무엇이 다른가 두 문서는 결론이 똑같이 "DTO를 쓰라"로 끝나지만 묻는 것이 다르다. 12번은 "무엇을 내보낼 것인가"(계층 경계·보안)이고, 이 문서는 "무엇을 가져올 것인가"(컬럼·메모리·쿼리)다. 그래서 이 문서는 결합도 이야기를 반복하지 않고, DB에서 애플리케이션까지 오는 구간의 비용만 다룬다.

1. 경계선이 다르다 — "무엇을 내보낼까"가 아니라 "무엇을 가져올까"

두 질문을 나란히 놓으면 결론이 똑같이 "DTO를 쓰라"로 끝난다. 그래서 하나로 뭉쳐 기억하기 쉬운데, 묻는 것이 다르다. 이 구분을 못 하면 답변이 통째로 빗나간다.

같은 결론, 다른 근거 — 두 문항의 좌표
엔티티 직접 노출 금지 (12번)조회 전용 DTO 프로젝션 (이 문서)
묻는 것무엇을 내보낼지무엇을 가져올지
근거의 층계층 경계 · 결합도 · 보안조회 비용(컬럼 · 메모리 · 쿼리)
경계선의 위치서비스 → 컨트롤러DB → 애플리케이션
A 계층 경계는 지켰다. 그런데 조회 비용은 그대로다 — "엔티티 노출 금지" 질문에는 만점, 이 질문에는 0점
@Transactional(readOnly = true)
public Page<ProductListDto> findProducts(Pageable pageable) {
    return productRepository.findAll(pageable)          // 엔티티 20건을 전부 읽는다① 경계 위반
            .map(ProductListDto::from);                 // 밖으로는 DTO만 나간다 → ② 경계는 지켰다
}

1-1. 이 질문에 답하는 3층 골격 — 순서에 이유가 있다

3층 골격 암기 — 컬 · 컨 · 결 (컬럼 → 컨텍스트 → 결합도)

1층 · 컬
조회 컬럼
SELECT 절이 달라진다. 불필요 컬럼을 DB가 읽고 네트워크로 실어 온다. → SQL 로그로 증명
2층 · 컨
영속성 컨텍스트
1차 캐시 적재 + 스냅샷 복사(메모리 2배) + 커밋 시 엔티티 수 × 필드 수 비교. → 힙·Statistics로 증명
3층 · 결
결합도 · 설계
화면 요구와 엔티티 구조는 변경의 이유가 다르다. → 설계 취향이 개입한다

왜 이 순서인가. 1·2층은 SQL 로그와 메모리로 증명되는 사실이고, 3층은 설계 취향이 개입한다. 증명 가능한 것부터 말하면 반론이 붙어도 근거가 남고, 취향부터 말하면 "우리 팀은 다르게 봅니다"로 끝난다. 실제 면접에서 결합도만 말했다가 "A로도 되지 않나요?"에 막히는 이유가 정확히 이것이다.

1-2. 예시 고정 — 이 문서 전체가 쓰는 하나의 화면

엔티티 Product — 목록이 쓰는 필드는 넷뿐
@Entity
public class Product {
    @Id @GeneratedValue
    private Long id;

    private String name;           // 목록에 필요
    private BigDecimal price;      // 목록에 필요
    private String thumbnailUrl;   // 목록에 필요

    @Column(columnDefinition = "TEXT")
    private String description;    // 상세에만. 평균 2KB

    @Column(columnDefinition = "TEXT")
    private String detailHtml;     // 상세에만. 수십 KB

    @Enumerated(EnumType.STRING)
    private ProductStatus status;

    @ManyToOne(fetch = FetchType.LAZY)
    private Category category;     // 카테고리명만 필요

    @OneToMany(mappedBy = "product", fetch = FetchType.LAZY)
    private List<ProductOption> options = new ArrayList<>();
}

화면의 조건 — 이 셋이 판단을 결정한다

  • 목록 화면은 상품명 · 가격 · 썸네일 · 카테고리명만 쓴다.
  • 페이징 20건.
  • 이 화면이 전체 호출량을 지배한다 — 메인 진입 화면이라 초당 호출 수가 가장 많다.

마지막 조건이 중요하다. 최적화 판단은 "단건 비용 × 호출 빈도"로 하는 것이고, "20건 조회가 얼마나 무겁겠나"는 곱하기 전의 이야기다.

비유 — 옷 한 벌 꺼내려고 옷장을 통째로 싣는다 엔티티 조회는 "완성된 Product 인스턴스를 만들어 주겠다"는 약속이다. 완성된 인스턴스에는 detailHtml 필드도 채워져 있어야 한다. 내 화면이 그 필드를 안 쓴다는 사실을 Hibernate는 알 방법이 없다. 그래서 옷 한 벌이 필요해도 옷장이 통째로 트럭에 실려 온다.

2. 1층 — SELECT 절의 실제 크기 (643KB의 정체)

"필요 없는 컬럼까지 읽는다"는 문장은 크기를 붙이기 전까지 아무것도 알려주지 않는다. 직접 계산해 보자. 아래에서 1KB = 1,024바이트로 계산하고, description은 평균 2KB(2,048 B), detailHtml은 평균 30KB(30,720 B)로 잡는다.

상품 목록 20건 조회 — 컬럼별 전송량
컬럼목록에서 쓰나행당 평균 크기20행 합계
id (bigint)쓴다8 B160 B
name (varchar)쓴다40 B800 B
price (numeric)쓴다8 B160 B
thumbnail_url (varchar)쓴다60 B1,200 B
category.name (조인)쓴다20 B400 B
status (varchar)안 쓴다10 B200 B
description (TEXT)안 쓴다2,048 B40,960 B
detail_html (TEXT)안 쓴다30,720 B614,400 B
행당 합계—32,914 B658,280 B
검산 한 줄씩 직접 곱해 본다 — 이 숫자를 면접에서 그대로 말한다
목록이 실제로 쓰는 컬럼   8 + 40 + 8 + 60 + 20        =     136 B/행
목록이 안 쓰는 컬럼      10 + 2,048 + 30,720          =  32,778 B/행
                                                        ─────────────
                                                          32,914 B/행

20행이면
  쓰는 것    136 B × 20    =      2,720 B  (약 2.7 KB)
  안 쓰는 것 32,778 B × 20 =  655,560 B  (약 640 KB)
  합계       32,914 B × 20 =  658,280 B  (약 643 KB)

  → 목록 조회 한 번에 643 KB 를 읽어와서 그중 2.7 KB 만 쓴다.
  → 낭비가 유효분의 655,560 ÷ 2,720 ≒ 241 배.
  → 유효 비율은 2,720 ÷ 658,280 ≒ 0.41%.

2-1. 이 비용이 걸리는 지점은 한 군데가 아니다 — 세 군데다

① DB의 버퍼·디스크 읽기
넓은 행은 데이터 페이지를 더 많이 만진다. 특히 TEXT/BLOB 계열은 벤더에 따라 행 밖(off-page)에 따로 저장되어 별도 페이지 접근을 추가로 유발한다.
② DB ↔ 애플리케이션 네트워크
위 계산의 그 숫자다. 643KB × 초당 50회 = 약 31.4 MB/s가 목록 화면 하나에서 나온다.
③ JVM의 객체 생성과 GC
30KB짜리 문자열 20개를 매 요청마다 새로 만들고 버린다. 곧바로 쓰레기가 되므로 GC가 그만큼 더 돈다.

여기서 반드시 붙여야 하는 단서 — "항상 크다"고 말하면 오히려 감점이다

이 숫자는 detail_html 같은 대형 컬럼이 있을 때의 숫자다. 컬럼이 전부 수십 바이트짜리 작은 값이라면 차이가 이렇게 나지 않는다. 그래서 판단 기준은 "컬럼 수"가 아니다.

판단 기준은 "대형 컬럼 유무 × 호출 빈도"

여기에 커지는 조건을 두 개 더 얹으면 답변이 완성된다 — ③ 커버링 인덱스가 가능해진다(select 절이 좁아지면 필요한 값이 전부 인덱스 안에 들어 있어 테이블 본체를 안 읽어도 되는 경우가 생긴다. "몇 %" 수준이 아니라 접근 방식이 바뀌는 차이다) ④ 건수가 늘어난다(엑셀 다운로드·배치 집계처럼 수만 건을 훑는 경로에서는 1차 캐시 적재만으로도 힙이 위험해진다).

3. 2층 — 조회 한 번이 영속성 컨텍스트에 만드는 것

A 코드(엔티티로 조회하고 서비스에서 변환)에서 실제로 일어나는 일을 항목별로 뜯는다. 1층이 "DB와 네트워크"의 비용이었다면, 2층은 애플리케이션 힙 안쪽의 비용이다.

A 가장 흔한 코드 — 네 가지 일이 동시에 일어난다
@Transactional
public Page<ProductListDto> findProducts(Pageable pageable) {
    return productRepository.findAll(pageable)
            .map(p -> new ProductListDto(
                    p.getId(), p.getName(), p.getPrice(), p.getThumbnailUrl(),
                    p.getCategory().getName()));   // LAZY 프록시 초기화 = 추가 쿼리N+1
}
1
SQL — 매핑된 컬럼 전부. description, detail_html까지 읽는다. §2에서 계산한 643KB가 이 한 번의 쿼리로 넘어온다. 왜 이렇게 되는가는 엔티티 매핑의 정의에서 곧장 따라 나온다 — Product를 반환한다는 것은 "완성된 인스턴스를 만들어 주겠다"는 약속이고, 완성된 인스턴스에는 description도 채워져 있어야 한다.
2
N+1 — getCategory().getName(). Category가 LAZY이므로 행마다 프록시 초기화 쿼리가 나간다. 20건이면 1 + 20번이다. DTO 변환 코드가 연관을 건드리는 순간 N+1은 그대로 발생한다 — DTO로 감싸는 것 자체가 N+1을 없애주지 않는다.
3
영속성 컨텍스트 — 적재 + 스냅샷. Product 20개 + Category 최대 20개가 1차 캐시에 들어가고, 각각에 대해 변경 감지용 원본 스냅샷이 한 부 더 복사된다. (아래 도식)
4
커밋 시점 — 변경 감지가 돈다. 트랜잭션이 끝날 때 1차 캐시의 모든 엔티티에 대해 스냅샷과 현재 값을 필드 단위로 비교한다. 비용은 대략 엔티티 수 × 필드 수이고, 아무것도 수정하지 않았어도 비교는 전부 돈다. 여기에 의도하지 않은 UPDATE 위험까지 얹힌다 — 컨버터의 왕복 비대칭이나 BigDecimal scale 차이 때문에 "안 시킨 UPDATE"가 조회 화면에서 나가는 사고가 실제로 있다.
스냅샷(snapshot)이란 — 그 자리에서 정의하고 간다 엔티티를 DB에서 읽어온 직후의 필드 값들을 그대로 복사해 둔 사본이다. 트랜잭션이 끝날 때 "지금 값"과 "읽어올 때의 값"을 비교해 달라진 필드만 UPDATE하기 위해 필요하다. 사진을 찍어 두었다가 나중에 대조하는 것과 같아서 붙은 이름이다. Hibernate는 이 사본을 깊은 복사(deep copy)로 만든다 — 참조만 복사하면 원본을 고칠 때 사본도 같이 바뀌어 비교가 무의미해지기 때문이다.

3-1. B — 조회 자체를 DTO로. "일어나지 않는 일의 목록"으로 설명한다

A 엔티티 조회 후 변환 — 나가는 SQL
-- 매핑된 컬럼 전부. 목록은 아래 두 컬럼을 쓰지 않는다.
select p.id, p.name, p.price, p.thumbnail_url,
       p.description, p.detail_html,
       p.status, p.category_id
  from product p
 limit 20;

-- 그리고 카테고리명을 만질 때마다
select c.* from category c where c.id = ?;   -- × 20회

-- 합계: 쿼리 21회, 약 643 KB
B DTO 프로젝션 — 나가는 SQL
-- SELECT 절에 화면이 쓰는 것만 있다. 쿼리 1회.
select p.id, p.name, p.price, p.thumbnail_url, c.name
  from product p
  join category c on c.id = p.category_id
 where p.status = 'ON_SALE'
 limit 20;




-- 합계: 쿼리 1회, 약 2.7 KB
B QueryDSL 구현 — 조회 시점부터 DTO. 목적이 "표시"임을 쿼리가 알고 있다
List<ProductListDto> content = queryFactory
        .select(new QProductListDto(
                product.id, product.name, product.price,
                product.thumbnailUrl, category.name))
        .from(product)
        .join(product.category, category)      // 조인 한 번, 추가 쿼리 없음
        .where(product.status.eq(ProductStatus.ON_SALE))
        .offset(pageable.getOffset())
        .limit(pageable.getPageSize())
        .fetch();

B에서 "일어나지 않는" 다섯 가지

  • description·detailHtml을 읽지 않는다 — 640KB가 사라진다.
  • 영속성 컨텍스트에 아무것도 적재되지 않는다 — DTO는 영속 객체가 아니다.
  • 스냅샷도, 커밋 시점 비교도 없다.
  • 반환 객체 안에 프록시가 없다 — 미래의 N+1 표면이 없다.
  • 카테고리명은 조인으로 함께 오므로 1 + N이 1이 된다.

그런데 A가 옳은 경우도 있다 — 양면으로 말한다

목적이 변경이면 A가 정답이다. 아니, A만 가능하다.

@Transactional
public void raisePrice(Long id, BigDecimal rate) {
    Product p = repo.findById(id).orElseThrow();
    p.raisePrice(rate);   // 변경 감지 → UPDATE
}

DTO로 가져오면 영속 객체가 아니므로 값을 바꿔도 DB에 반영되지 않는다. 지금 "비용"이라 부른 스냅샷과 1차 캐시가 바로 이 기능의 대가다.

스냅샷과 1차 캐시는 낭비가 아니라 변경 감지라는 기능의 대가다
조회 화면에서는 그 기능을 안 쓰니 대가만 남는 것이다

4. 이 문서의 심장 — readOnly로 없어지는 둘, 남는 셋

이 문항은 유도성 반론과 세트로 나온다. "readOnly를 걸면 스냅샷이 안 만들어지는데, 그럼 DTO 프로젝션은 필요 없는 거 아닌가요?" — 여기서 무너지면 앞의 이유가 전부 되돌려진다. 정답은 "없어지는 것과 남는 것을 나눠서 말하기"다.

@Transactional(readOnly = true)를 걸었을 때 — 항목별 결과와 그 이유
비용 항목readOnly를 걸면왜 그런가
변경 감지용 스냅샷 복사없어진다read-only로 로드된 엔티티는 원본 상태를 아예 보관하지 않는다. Hibernate 6.6 소스에서 엔티티 항목이 read-only가 되는 순간 스냅샷을 담는 loadedState가 null로 비워진다.
커밋 시점 변경 감지 비교없어진다비교할 원본(스냅샷)이 없으므로 flush가 UPDATE 후보를 만들 근거 자체가 없다. "안 시킨 UPDATE" 위험도 함께 사라진다.
1차 캐시 적재그대로 남는다스냅샷을 안 만드는 것과 엔티티 인스턴스를 보관하는 것은 별개다. 인스턴스는 여전히 영속성 컨텍스트의 Map에 들어가고 트랜잭션이 끝날 때까지 강하게 참조된다.
불필요 컬럼 읽기·전송그대로 남는다readOnly는 select 절을 한 글자도 바꾸지 않는다. 반환 타입이 엔티티인 이상 매핑된 컬럼을 전부 읽는다. §2의 643KB가 통째로 남는다.
지연 로딩 프록시그대로 남는다반환 객체가 엔티티인 이상 그 안의 LAZY 연관 필드는 프록시 그대로다. 누군가 건드리면 그 자리에서 쿼리가 나간다.

암기 — 없어지는 것 "스 · 감" / 남는 것 "캐 · 컬 · 프"

스냅샷 복사변경 감지 비교→readOnly가 지운다 (2)
1차 캐시 적재불필요 컬럼 전송LAZY 프록시→그대로 남는다 (3)

"2 대 3"이라는 숫자만 기억해도 반론을 받아칠 수 있다. 없어지는 둘은 메모리와 CPU 쪽이고, 남는 셋은 네트워크·힙·미래의 실수 쪽이다.

확인 범위 — 면접에서는 전제를 붙여 말하는 편이 정확하다 이 최적화는 JPA 표준이 보장하는 것이 아니라 Hibernate 구현에 기댄 동작이다. JPA 표준에서 readOnly는 힌트에 가깝다. 그러니 "Spring + Hibernate 조합에서는"이라는 전제를 붙이자.
그럼에도 readOnly는 조회 전용 메서드에 어차피 붙인다 — 이유가 하나 더 있다 스냅샷 절감만이 이유가 아니라, readOnly 플래그가 읽기 전용 리플리카로 라우팅하는 스위치로 쓰이기 때문이다(LazyConnectionDataSourceProxy + AbstractRoutingDataSource 조합). 이 라우팅 축은 3장 고난이도 문항(읽기/쓰기 분리)으로 그대로 이어진다.
답변은 이렇게 닫는다 — "readOnly는 붙입니다. 그리고 DTO 프로젝션도 합니다. 둘은 서로 다른 비용을 지웁니다."

5-2. QueryDSL — Projections 3종 + @QueryProjection

QueryDSL은 매핑 방식이 네 가지라서 이 문항의 중심이다. 무엇을 기준으로 값을 꽂는가가 각각 다르다.

4종 값을 꽂는 기준이 다르다 — 위치인가, 이름인가
// (1) constructor — 생성자 파라미터에 순서대로 꽂는다 (위치 기준)
Projections.constructor(ProductListDto.class,
        product.id, product.name, product.price, product.thumbnailUrl, category.name)

// (2) fields — 필드 이름으로 꽂는다 (리플렉션으로 필드에 직접 대입, setter 불필요)
Projections.fields(ProductListDto.class,
        product.id, product.name, product.price, product.thumbnailUrl,
        category.name.as("categoryName"))   // 이름이 다르면 별칭으로 맞춘다

// (3) bean — setter 이름으로 꽂는다 (기본 생성자 + setter 필요)
Projections.bean(ProductListDto.class, ...)

// (4) @QueryProjection — DTO 생성자에 애노테이션을 붙여 Q타입을 생성
new QProductListDto(product.id, product.name, product.price,
        product.thumbnailUrl, category.name)
DTO 애노테이션 프로세서가 QProductListDto를 생성한다
public class ProductListDto {
    private final Long id;
    private final String name;
    private final BigDecimal price;
    private final String thumbnailUrl;
    private final String categoryName;

    @QueryProjection   // 이 한 줄이 Q타입을 만든다
    public ProductListDto(Long id, String name, BigDecimal price,
                          String thumbnailUrl, String categoryName) { ... }
}

이점 — 컴파일 타임 검증

생성자 시그니처가 컴파일 타임에 검증된다. 파라미터 개수를 틀리거나 Long이 갈 자리에 String을 넣으면 빌드가 깨진다. Projections.constructor는 이 검증을 런타임까지 미룬다.

대가 — DTO가 QueryDSL에 컴파일 의존한다

DTO를 API 응답 타입으로 쓰면서 웹 모듈에 두는 구조라면 웹 모듈이 QueryDSL을 알아야 한다. 멀티 모듈에서 이걸 피하려고 Projections.constructor를 택하는 팀도 있다 — 의존 방향을 지키려고 컴파일 안전성을 포기하는 트레이드오프다.

한계 — 6절이 통째로 이 이야기다 @QueryProjection은 같은 타입끼리의 순서 교체를 못 잡는다. "컴파일 시점에 잡힙니다"까지만 말하면 절반이다.

5-3. Spring Data 인터페이스 프로젝션 — 이름 기반, 코드가 가장 짧다

    name = "ProductListMapping",
    classes = @ConstructorResult(
        targetClass = ProductListDto.class,
        columns = {
            @ColumnResult(name = "id",    type = Long.class),
            @ColumnResult(name = "name",  type = String.class),
            @ColumnResult(name = "price", type = BigDecimal.class)
        }))
@Entity

쓰는 이유 / 대가

  • 쓰는 이유 — 윈도 함수, 벤더 전용 힌트, 재귀 CTE 등 JPQL이나 QueryDSL로 표현할 수 없는 SQL이 필요할 때.
  • 대가 — 벤더 종속이 생기고, 컬럼명이 문자열이며, 애노테이션이 엔티티 클래스에 얹혀 지저분해진다.
  • 숨은 대가 — 네이티브 쿼리는 실행 직전 auto-flush를 유발하므로, 같은 트랜잭션의 쓰기 지연 SQL이 예상치 못한 시점에 나갈 수 있다.

6. 순서 교체 함정 — 도구가 못 막는 것까지 안다 시니어 변별

여기서부터가 시니어 변별 지점이다. 도구의 효능만 아는 사람과 효능의 경계를 아는 사람이 여기서 갈린다. 먼저 무슨 순서가 왜 바뀌는가부터 정확히 하자 — 생성자 프로젝션에는 순서가 두 군데에 있다.

전제 서로 다른 파일에 있고, 서로를 참조하지 않는 두 개의 순서
순서 ①  쿼리에서 값을 나열한 순서

6-1. @QueryProjection — 개수·타입은 잡는다. 순서는 못 잡는다

잡는다 둘 다 빌드를 깬다

// constructor QProductListDto cannot be applied to given types

// (b) 타입 불일치 → 컴파일 에러

// StringPath는 NumberExpression<Long> 자리에 들어갈 수 없다
못 잡는다 같은 타입끼리의 순서 교체

//   → 여전히 (NumberExpression<Long>, StringExpression, StringExpression)
new QProductListDto(product.id, product.name, product.thumbnailUrl);
// 컴파일 통과. constructor 방식과 결과가 똑같다.
// 컴파일러가 보는 것은 "타입의 나열"이고, 그건 하나도 바뀌지 않았다.

6-2. 처방 — 순서를 매핑의 변수에서 아예 빼버린다

순서 때문에 생기는 문제이므로, 순서라는 개념이 없는 매핑 방식을 쓰면 문제 자체가 성립하지 않는다.

7. 포기하는 것 다섯 — 장점만 말하면 감점

"장점만 말하고 멈추면 감점"이 이 문항의 채점 방식이다. 얻는 것을 말한 만큼 포기하는 것도 같은 호흡에 말한다.

포기하는 것 5종 암기 — 행 · 변 · 연 · 도 · 증

행 — 1:N 조인 시 행 중복 변 — 변경 감지 불가 연 — 연관 탐색 불가 도 — 도메인 메서드 사용 불가 증 — DTO 클래스 증식

구조로 묶으면 외우기 쉽다 — 행은 쿼리 구조상의 한계 하나, 변·연·도는 전부 "DTO는 영속 객체가 아니다" 한 가지 사실에서 파생되는 셋, 증은 관리 비용 하나. 1 + 3 + 1이다.

7-1. 행 — 1:N 컬렉션을 조인해 담으면 행이 중복된다

잘못된 시도 목록에 옵션명까지 보여달라는 요구가 붙었다
queryFactory
        .select(new QProductListDto(
                product.id, product.name, option.name))   // option 은 1:N
        .from(product)
        .join(product.options, option)
        .limit(20)
        .fetch();
처방 루트 페이징 + in 절 2차 쿼리 + 애플리케이션 그룹핑
@Transactional(readOnly = true)
public Page<ProductListDto> findListPage(Pageable pageable) {

    // (1) 루트만 페이징 조회 — limit 20 = 상품 20건이 보장된다.
    List<ProductListDto> content = queryFactory
            .select(new QProductListDto(
                    product.id, product.name, product.price,
                    product.thumbnailUrl, category.name))
            .from(product)
            .join(product.category, category)        // ToOne 조인은 행이 늘지 않아 안전
            .where(product.status.eq(ProductStatus.ON_SALE))
            .offset(pageable.getOffset())
            .limit(pageable.getPageSize())
            .fetch();

    // (2) 방금 가져온 20개의 id로 자식을 한 번에 조회 — in 절 쿼리 1회
    List<Long> productIds = content.stream().map(ProductListDto::id).toList();

    Map<Long, List<String>> optionNames = queryFactory
            .select(option.product.id, option.name)
            .from(option)
            .where(option.product.id.in(productIds))
            .fetch().stream()
            .collect(groupingBy(
                    t -> t.get(option.product.id),
                    mapping(t -> t.get(option.name), toList())));

    // (3) 애플리케이션에서 조립 — 새 인스턴스를 만든다(불변 유지)
    content = content.stream()
            .map(dto -> dto.withOptionNames(
                    optionNames.getOrDefault(dto.id(), List.of())))
            .toList();

    // count 쿼리는 필요할 때만
    JPAQuery<Long> countQuery = queryFactory
            .select(product.count()).from(product)
            .where(product.status.eq(ProductStatus.ON_SALE));

    return PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne);
}
이 구조를 어디서 봤는가 — default_batch_fetch_size가 하는 일과 정확히 같다 Hibernate는 LAZY 컬렉션을 in (…)으로 묶어 1 + ceil(N/size)로 줄이는데, 여기서는 그 묶음을 내가 손으로 만든 것이다. 그래서 답변에 이 문장을 붙이면 좋다 — "컬렉션은 조인으로 한 번에 담지 않고, 루트를 페이징한 뒤 id 목록으로 in 절 한 번을 더 나가서 애플리케이션에서 묶습니다. default_batch_fetch_size가 자동으로 해주는 것과 같은 구조를 DTO 세계에서 손으로 하는 겁니다."
가산점 — 언제 이 수고를 하지 않는가 컬렉션 개수가 작고 상한이 확실하면(예: 옵션이 상품당 최대 3개) 루트에 string_agg(PostgreSQL) / group_concat(MySQL) 같은 집계 함수로 한 컬럼에 밀어 넣는 방법도 있다. 대가는 벤더 종속과 길이 제한이며, "대표 옵션 3개만"처럼 상한이 요구사항에 이미 있을 때만 정당하다.

7-2. 변 · 연 · 도 — 셋 다 "DTO는 영속 객체가 아니다" 하나에서 나온다

변 DTO를 고쳐도 DB에는 아무 일도 없다 — 예외조차 없다
@Transactional
public void discount(Long productId) {
    ProductListDto dto = queryRepository.findOne(productId);
    dto.setPrice(dto.getPrice().multiply(new BigDecimal("0.9")));
    // 커밋. UPDATE 없음. 로그에도 아무것도 없다.
}
변 변경이 목적이면 엔티티로 가져온다
@Transactional
public void discount(Long productId) {
    Product product = productRepository.findById(productId).orElseThrow();
    product.discount(new BigDecimal("0.9"));   // 변경 감지 → UPDATE
}
변 — 변경 감지 불가
Hibernate가 UPDATE를 만드는 근거는 "읽어올 때의 스냅샷"과 "지금 값"의 차이인데, DTO는 영속성 컨텍스트에 등록되지 않아 스냅샷 자체가 없다. 비교할 원본이 없으니 UPDATE를 만들 근거가 없다.
대책 — 애초에 setter 없는 불변 객체(레코드)로 만들어 그 실수 표면을 없앤다.
연 — 연관 탐색 불가
엔티티의 연관 필드는 "건드리는 순간 DB를 다시 읽는" 프록시인데, DTO 필드는 조회 시점에 select 절의 값을 복사해 담은 순수한 값이라 다시 읽어올 장치가 붙어 있지 않다. 필요하면 쿼리의 select 절을 고치는 것이 유일한 방법이다.
뒤집으면 장점 — 미래의 N+1 표면이 없다.
도 — 도메인 메서드 불가
DTO는 화면에 뿌릴 값을 모아둔 자료 묶음일 뿐이라 엔티티의 불변식 검증과 상태 전이 규칙(product.discount(...), order.cancel())이 애초에 들어 있지 않다. 그 규칙을 DTO에 복사해 넣으면 같은 규칙이 두 곳에 살게 되어 한쪽만 고치는 사고가 난다.

7-3. 증 — 화면 수만큼 DTO 클래스가 늘어난다

목록, 상세, 관리자 목록, 엑셀 다운로드, 검색 결과, 추천 위젯. 화면마다 필요한 컬럼이 다르면 DTO도 갈라진다. "클래스가 너무 많다"는 불만은 정당한 비용 지적이다.

해서는 안 되는 절충 두 개

  • 큰 DTO 하나로 합치기 — 필드를 다 채우려면 컬럼을 다 읽어야 하고, 그러면 엔티티와 다를 게 없다. 1층 이점이 통째로 사라진다.
  • "필드를 null로 두고 안 쓰는 화면은 무시한다" — 최악이다. 어느 필드가 채워졌는지 코드로 알 수 없어져 NPE와 오표시가 늘어난다.

현실적인 관리 방법 네 가지

  • 패키지를 화면 단위로 나눈다 — product.query.list, product.query.detail. 클래스 수가 많아도 찾는 비용이 늘지 않는다.
  • DTO는 쿼리 코드 옆에 둔다 — 화면 요구가 바뀌면 쿼리와 DTO를 같이 고치므로 변경이 한 디렉터리에서 끝난다.
  • 공통 조각은 상속이 아니라 컴포지션으로 — 상속으로 필드를 물려받으면 안 쓰는 필드가 다시 따라온다.
  • 레코드를 쓴다 — 보일러플레이트가 줄면 체감 부담이 크게 줄고, 불변이라 7-2의 실수 표면도 사라진다.
최종 판단 기준은 한 문장이다 — "이 조회의 목적이 변경이면 엔티티, 표시면 DTO."
이 한 문장이 CQRS(명령과 조회의 모델을 분리한다)의 출발점이다 — 별도 저장소나 이벤트 소싱까지 가지 않아도, 같은 테이블 위에서 쓰기 모델(엔티티)과 읽기 모델(DTO)을 분리하는 것만으로 실익 절반은 이미 얻는다

8. 확인 절차와 회귀를 막는 테스트 3층

앞의 모든 이야기는 눈으로 확인하기 전까지 "그럴 것이다"로 남는다 — 프로젝션은 SQL을 보기 전까지 최적화가 아니다
설정 개발 프로파일에만 — show-sql 대신 로거로 켠다
# 개발 프로파일에만
spring:
  jpa:
    properties:
      hibernate:
        format_sql: true
logging:
  level:
    org.hibernate.SQL: DEBUG
    org.hibernate.orm.jdbc.bind: TRACE   # 바인딩 값까지

왜 show-sql: true가 아닌가

show-sql은 표준 출력으로 직접 뿌리므로 로깅 프레임워크를 우회한다. 파일로 남지도 않고 레벨 조절도 안 되므로 로거 레벨로 켜는 편이 낫다.

그 위에 p6spy(또는 datasource-proxy)를 얹으면 바인딩 값이 채워진 완성된 SQL 한 줄과 실행 시간을 볼 수 있다. 이 문항에서 특히 유용하다 — select 절에 description이 있는지 없는지가 한눈에 보이는 것이 목적이기 때문이다.

확인 체크리스트 — 실제로 이 순서로 본다

1
select 절에 화면이 안 쓰는 컬럼이 있는지. 있으면 프로젝션이 안 걸린 것이다(열린 프로젝션이거나, 반환 타입이 엔티티이거나).
2
쿼리가 몇 번 나가는지. 목록 조회에서 같은 형태의 SELECT가 반복되면 N+1이다.
3
limit이 붙어 있는지. 없으면 페이징이 메모리에서 처리되고 있다.
4
HHH000104 경고가 있는지(fetch join + 페이징 신호).

8-1. 회귀는 사람이 아니라 테스트가 막는다 — 세 층으로 고정한다

(1) 쿼리 수 단정 — N+1이 생기면 여기서 깨진다
@Test
void 상품목록은_쿼리_두_번만_나간다() {
    SQLStatementCountValidator.reset();

    productQueryService.findListPage(PageRequest.of(0, 20));

    // 루트 1회 + 옵션 in 절 1회
    SQLStatementCountValidator.assertSelectCount(2);
}
(2) 영속성 컨텍스트에 아무것도 안 올라왔는지 단정 — 이 문항 전용 안전망
@Test
void DTO_프로젝션은_엔티티를_적재하지_않는다() {
    Statistics stats = entityManagerFactory.unwrap(SessionFactory.class).getStatistics();
    stats.clear();

    productQueryService.findListPage(PageRequest.of(0, 20));

    // 누군가 "간편하게" 엔티티 조회 + 변환으로 되돌리면 이 단정이 깨진다.
    assertThat(stats.getEntityLoadCount()).isZero();
}
이 테스트가 특히 값진 이유 §1의 A/B 구분을 코드로 못 박는 유일한 방법이기 때문이다. "DTO로 조회한다"는 규약은 리뷰에서 지키기 어렵지만, entityLoadCount == 0은 누구도 우회할 수 없다.
(3) 값의 내용을 단정 — 6절의 순서 교체 대비
@Test
void 목록_DTO의_각_필드가_제자리에_들어간다() {
    var dto = productQueryService.findListPage(PageRequest.of(0, 20)).getContent().get(0);

    // 타입이 같은 필드들을 서로 구별되는 값으로 단정한다
    assertThat(dto.name()).isEqualTo("무선 이어폰");
    assertThat(dto.thumbnailUrl()).startsWith("https://cdn.");
    assertThat(dto.categoryName()).isEqualTo("음향기기");
}

픽스처 설계가 곧 테스트의 감도다

모든 문자열 필드에 "test"를 넣으면 순서가 뒤바뀌어도 통과한다. 이 유형의 회귀를 잡는 실질적 조건은 딱 하나다.

같은 타입 필드끼리는 서로 절대 헷갈리지 않는 값을 넣는다

(4) 가산점 — 조회 컬럼 자체를 단정한다. datasource-proxy의 리스너로 실행된 SQL 문자열을 수집하면 assertThat(capturedSql).doesNotContain("detail_html"); 같은 단정도 가능하다. 과하다고 느낄 수 있지만, "대형 컬럼을 목록 쿼리에서 절대 읽지 않는다"가 성능 요구사항인 화면이라면 이 한 줄이 그 요구사항의 유일한 문서이자 집행 장치다.

이 도구 상자는 3장 전체에서 반복된다 N+1 탐지의 쿼리 수 단정, fetch join + 페이징의 경고 승격, 영속성 컨텍스트의 Statistics 활용. 결론은 하나다 — "조심하겠다"는 대책이 아니다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

이 질문의 축은?
결합도가 아니라 조회 비용. 3층 컬 · 컨 · 결(컬럼 → 컨텍스트 → 결합도), 증명 가능한 것부터 말한다.
1층 숫자 한 세트?
20건에 643 KB를 읽어 2.7 KB만 쓴다 → 낭비 241배, 유효 0.41%. 초당 50회면 하루 2.6 TB vs 10.9 GB.
2층 비용 셋?
1차 캐시 적재 + 스냅샷 복사(메모리 2배) + 커밋 시 엔티티 수 × 필드 수 비교. 여기에 "안 시킨 UPDATE" 위험.
readOnly는 2 대 3
없어짐 = 스냅샷 · 변경 감지. 남음 = 캐(1차 캐시) · 컬(컬럼 전송) · 프(LAZY 프록시). select 절을 한 글자도 안 바꾼다.
구현 4종?
새 · 큐 · 인 · 네 — select new / QueryDSL / 인터페이스 프로젝션 / 네이티브. 단순=인터페이스, 동적·집계=QueryDSL.
@QueryProjection이 못 잡는 것?
동일 타입 순서 교체. 개수·타입은 잡지만 시그니처가 그대로라 컴파일러가 볼 것이 없다. 예외 없이 값만 뒤바뀐다.
순서를 없애는 법?
이름 기반 매핑(fields/bean/인터페이스 프로젝션) + 레코드 + 서로 헷갈리지 않는 픽스처로 필드별 값 단정.
포기하는 것 5종?
행 · 변 · 연 · 도 · 증 — 구조는 1(쿼리 구조) + 3(영속 객체 아님) + 1(관리 비용).
1:N 처방?
루트만 페이징 → id 목록으로 in 절 2차 쿼리 → 애플리케이션 그룹핑 = 1 + 1. default_batch_fetch_size의 수동 버전.
판단 기준 한 문장?
"변경이 목적이면 엔티티, 표시가 목적이면 DTO." 스냅샷·1차 캐시는 낭비가 아니라 변경 감지의 대가다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

@Transactional(readOnly = true)를 걸면 스냅샷도 안 만들고 변경 감지도 안 하니, 엔티티로 조회해도 되지 않나요? 필수힌트: "없어지는 것"과 "남는 것"을 나눠서. 숫자로는 2 대 3

없어지는 것은 정확히 두 개다 — 스냅샷 복사와 커밋 시점 변경 감지. 남는 것은 세 개다.

  1. 1차 캐시 적재 — 스냅샷을 안 만들어도 엔티티 인스턴스는 영속성 컨텍스트에 들어가고 트랜잭션이 끝날 때까지 강한 참조가 유지된다. 배치로 수천 건을 훑으면 그대로 힙에 쌓인다.
  2. 불필요 컬럼 전송 — readOnly는 select 절을 바꾸지 않는다. description, detail_html은 그대로 읽히고 그대로 전송된다.
  3. 지연 로딩 프록시 — 엔티티를 손에 들고 있으면 LAZY 연관이 살아 있는 뇌관으로 남는다. 오늘은 안 건드려도 내일 누가 게터 한 줄을 추가하면 N+1이 생긴다.
결론은 "대체가 아니라 병행"

덧붙이면 좋은 한마디 — "조회 전용 메서드에는 readOnly를 어차피 붙입니다. 스냅샷 절감만이 이유가 아니라 읽기 리플리카로 라우팅하는 스위치로도 쓰이기 때문입니다." 그리고 정확성을 위해 "Spring + Hibernate 조합에서"라는 전제를 붙인다 — JPA 표준에서 readOnly는 힌트에 가깝다.

컬럼 몇 개 덜 읽는 게 그렇게 큰 차이인가요? 어차피 인덱스로 찾은 20건인데요. 함정힌트: "항상 크다"고 답하면 오히려 감점이다

"커지는 조건"을 말하는 게 답이다. 차이가 작은 경우부터 인정하고 시작한다 — 컬럼이 다 작고(수십 바이트), 건수가 적고, 호출 빈도도 낮으면 측정 가능한 차이가 안 난다. 이때는 코드가 짧은 쪽(A + readOnly)이 낫다.

차이가 커지는 조건은 네 가지다.

① 대형 컬럼이 있다
TEXT/BLOB은 벤더에 따라 행 밖에 저장되어 추가 페이지 접근을 유발한다. description 2KB + detail_html 30KB면 20건에 약 643KB가 실려 오고 화면이 쓰는 건 3KB가 안 된다.
② 호출 빈도가 높다
메인 진입 화면처럼 호출량을 지배하면 단건 차이 × 빈도가 네트워크와 DB 버퍼에 그대로 누적된다. 초당 50회면 하루 2.6TB와 11GB의 차이.
③ 커버링 인덱스가 가능해진다
select 절이 좁아지면 필요한 값이 전부 인덱스 안에 들어 있어 테이블 본체를 안 읽어도 되는 경우가 생긴다. "몇 %"가 아니라 접근 방식이 바뀌는 차이다.
④ 건수가 늘어난다
엑셀 다운로드·배치 집계처럼 수만 건을 훑는 경로에서는 1차 캐시 적재만으로도 힙이 위험해진다.

마무리 문장 — "그래서 저는 '컬럼 수'로 판단하지 않고 대형 컬럼 유무 × 호출 빈도로 판단합니다. 그리고 판단이 애매하면 p6spy로 실제 SQL을 보고 응답 시간을 재서 결정합니다." 측정 없이 최적화를 주장하지 않는 태도가 이 답의 핵심이다.

@QueryProjection을 쓰면 컴파일 시점에 잡히니까 안전하지 않나요? 시니어 변별힌트: 무엇을 잡고 무엇을 못 잡는지로 갈라 답한다

절반만 안전하다.

잡는 것

파라미터 개수 오류, 타입 불일치. 둘 다 빌드를 깬다.

못 잡는 것

같은 타입끼리의 순서 교체. (Long, String, String) 생성자에서 두 String의 순서를 바꿔도 시그니처는 그대로이므로 컴파일러가 볼 것이 없다.

결과는 Projections.constructor와 동일하게 값이 바뀐 채 조용히 통과한다. 상품명 칸에 썸네일 URL이 찍히고, 예외도 로그도 없다.

순서를 원천 차단하는 것은 이름 기반 매핑이다 — Projections.fields/bean은 프로퍼티 이름으로 꽂으므로 순서가 매핑의 변수가 아니고, Spring Data 인터페이스 프로젝션은 게터 이름이 곧 속성이라 순서라는 축이 아예 없다.

단, 이름 기반도 완전하지 않다 — 별칭 누락(category.name을 .as("categoryName") 없이 넘기면 name 필드에 카테고리명이 덮인다)과 필드명 오타는 여전히 런타임 문제다.

그래서 최종 답은 이렇게 닫는다 — "어느 도구도 완전하지 않으므로 결과를 테스트로 고정합니다. 같은 타입 필드들을 서로 헷갈리지 않는 값으로 픽스처를 만들고 필드별로 단정합니다." 도구의 한계를 알고 그 자리에 안전망을 놓는 것이 이 질문의 만점 답이다.

DTO 프로젝션을 쓰면 항상 이득인가요? 포기하는 게 뭔가요? 시니어 변별힌트: 행 · 변 · 연 · 도 · 증 — 1 + 3 + 1 구조로 묶는다

한 호흡에 말한다. 크게 묶으면 기억하기 쉽다 — 쿼리 구조상의 한계 하나, "영속 객체가 아니다"에서 파생되는 셋, 관리 비용 하나.

  1. 1:N 컬렉션을 담을 수 없다(행). 조인하면 행이 상품 × 옵션으로 늘어나 DTO 하나로 안 떨어지고, limit 20이 상품 20건을 의미하지 않게 된다. fetch join + 페이징과 같은 구조의 문제지만 경고조차 없다는 점이 더 나쁘다. 처방은 루트만 페이징하고 자식은 id 목록으로 in 절 2차 쿼리 후 애플리케이션에서 그룹핑이다.
  2. 변경 감지가 안 된다(변). DTO는 영속성 컨텍스트에 등록되지 않아 스냅샷이 없고, 비교할 원본이 없으니 UPDATE를 만들 근거가 없다. 값을 바꿔도 예외조차 안 난다. 애초에 setter 없는 불변 객체(레코드)로 만들어 실수 표면을 없애는 편이 낫다.
  3. 연관을 따라갈 수 없다(연). DTO 필드는 조회 시점의 값을 복사해 담은 것이라 프록시가 아니고, 프록시가 아니면 "필요할 때 다시 읽어오는" 장치가 없다. 다만 뒤집으면 미래의 N+1 표면이 없다는 장점이다.
  4. 도메인 메서드를 못 쓴다(도). DTO는 표시용 값 묶음이라 불변식 검증과 상태 전이 규칙이 들어 있지 않고, 그 규칙을 DTO에 복사하면 같은 규칙이 두 곳에 살게 되어 한쪽만 고치는 사고가 난다.
  5. 화면 수만큼 DTO가 늘어난다(증). 큰 DTO 하나로 합치면 컬럼을 다 읽어야 해서 이 기법의 이점이 사라지고, 필드를 null로 비워두는 절충은 최악이다.

그리고 판단 기준으로 닫는다 — "그래서 기준은 하나입니다. 이 조회의 목적이 변경이면 엔티티, 표시면 DTO. 스냅샷과 1차 캐시는 낭비가 아니라 변경 감지의 대가이고, 조회 화면은 그 기능을 안 쓰니까 대가만 남는 겁니다."

인터페이스 프로젝션이 코드가 가장 짧다면 왜 QueryDSL을 쓰나요?힌트: 두 축으로 자른다 — 조건의 동적 여부, 그리고 표현력

인터페이스 프로젝션이 이기는 곳: 조건이 고정된 단순 조회. 인터페이스 하나와 반환 타입 변경으로 끝나고, 이름 기반이라 순서 함정도 없고, 중첩 프로젝션도 된다.

QueryDSL이 필요한 곳은 셋이다.

  • 동적 조건 — 검색 필터가 조합되면 파생 쿼리 메서드 이름이 폭발한다. QueryDSL은 BooleanExpression 메서드로 쪼개 where(nameEq(x), statusEq(y))처럼 나열하면 null이 조용히 무시되어 if가 사라진다.
  • 집계 · 서브쿼리 · case when — 게터 목록으로는 표현할 수 없다.
  • count 쿼리 최적화 — PageableExecutionUtils.getPage(...)로 count를 생략하거나, count 쿼리에서 join을 떼는 조정이 필요할 때.

그리고 한 프로젝트에서 둘을 섞어 쓰는 게 정상이다. "하나로 통일"이 목표가 아니라 단순한 곳은 짧게, 복잡한 곳은 통제 가능하게가 목표다.

그럼 조회 전용 코드는 어디에 두시나요? 가산점힌트: 파일을 가르는 실익이 "코드 정리"가 아니라는 점까지

쓰기와 읽기를 같은 클래스에 두지 않는다. 실무 구조는 보통 이렇게 간다.

ProductRepository
JpaRepository. 쓰기와 단건 조회(변경 목적)용. 엔티티를 반환한다.
ProductQueryRepository
QueryDSL 구현. 표시 목적 조회 전용. DTO만 반환한다.
Service도 둘로
ProductService(명령)와 ProductQueryService(조회).

이렇게 가르는 실익은 코드 정리가 아니라 규칙을 파일 단위로 강제할 수 있다는 것이다. ProductQueryRepository의 모든 메서드가 DTO를 반환한다는 규약은 ArchUnit 룰로 검사할 수 있고, @Transactional(readOnly = true)를 클래스 단위로 걸 수 있고, 읽기 리플리카 라우팅도 이 경계에서 갈린다.

이것이 CQRS의 가장 값싼 형태다 — 저장소를 두 개로 나누거나 이벤트 소싱을 도입하지 않고 같은 테이블 위에서 모델만 두 개로 가르는 것. 여기까지만 해도 "조회 성능을 조회 쪽에서만 최적화할 수 있게 되는" 이점을 얻는다. 읽기 모델을 별도 저장소로 물리 분리하는 판단은 그 다음 단계이고, 그때의 기준은 정합성 지연(eventual consistency)을 화면이 감당할 수 있느냐다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

인터페이스 프로젝션을 썼는데 SQL 로그에 description이 그대로 보입니다. 왜죠? 함정힌트: 그 인터페이스에 계산 게터를 하나 넣지 않았는지 본다

열린(open) 프로젝션이 되었을 가능성이 가장 높다. 게터가 엔티티 속성과 1:1로 대응하는 닫힌(closed) 프로젝션이면 어떤 컬럼이 필요한지 정적으로 알 수 있어 그 컬럼만 SELECT한다. 그런데 @Value("#{target.price * 1.1}")처럼 SpEL로 계산하는 게터가 하나라도 끼면, 그 식이 어떤 속성을 참조할지 미리 알 수 없으므로 루트 엔티티를 전부 로드한 뒤 그 위에서 식을 평가한다.

부가세 계산 같은 사소한 편의 한 줄이 1층 이점(640KB)을 통째로 되돌린다

처방은 단순하다 — 계산은 프로젝션이 아니라 DTO나 화면 계층에서 한다. 그리고 이 회귀는 눈으로 못 잡으므로 assertThat(capturedSql).doesNotContain("detail_html") 같은 단정으로 고정해 둔다. 다른 원인도 함께 점검한다 — 반환 타입이 실제로는 엔티티인 경로가 섞여 있거나, 정렬·조건에 다른 연관을 걸어 조인이 늘어난 경우.

엔티티 필드에 @Basic(fetch = FetchType.LAZY)를 걸어 큰 컬럼만 지연 로딩하면, DTO 프로젝션 없이도 1층 문제가 풀리지 않나요? 시니어 변별힌트: 동작 조건 하나, 그리고 목록 화면에서 생기는 새 문제 하나

부분적으로는 맞지만, 목록 화면의 해법으로는 약하다. 이유가 세 가지다.

  1. 동작하려면 바이트코드 인핸스먼트가 필요하다. 빌드 플러그인으로 엔티티 클래스를 가공해야 하고, 켜지 않으면 애노테이션이 조용히 무시된다. "걸어뒀는데 왜 안 되지"의 전형적 원인이다.
  2. 켜더라도 그 필드에 접근하는 순간 추가 쿼리가 나간다. 목록 20건에서 누군가 getDescription()을 부르면 지연 로딩의 새로운 N+1 축이 생긴다. 1층 비용을 없앤 게 아니라 다른 시점으로 옮긴 것이다.
  3. 전역 결정이라는 점이 더 중요하다. 이 설정은 그 엔티티를 쓰는 모든 경로에 영향을 준다. 반면 DTO 프로젝션은 조회 하나하나에 대해 국소적으로 결정되므로 어떤 화면이 무엇을 읽는지 쿼리만 보면 알 수 있다.

정리하면 — "상세 화면에서도 대부분 안 쓰는 초대형 컬럼"을 엔티티 차원에서 떼어내고 싶다면 검토할 수 있지만, 목록 화면의 조회 비용 문제는 그 조회의 select 절을 직접 통제하는 DTO 프로젝션이 더 정확하고 더 통제 가능한 답이다.

DTO 프로젝션은 1차 캐시에 안 올라간다고 했는데, 그럼 같은 트랜잭션에서 같은 조회를 두 번 하면 어떻게 되나요?힌트: "적재되지 않는다"의 반대급부를 정직하게 말한다

쿼리가 두 번 나간다. 1차 캐시는 영속 엔티티를 식별자 기준으로 보관하는 장치인데 DTO는 영속 객체가 아니므로 보관 대상이 아니기 때문이다. 반대로 findById로 같은 엔티티를 두 번 조회하면 두 번째는 1차 캐시에서 나와 쿼리가 안 나간다.

이것은 §4에서 "장점"으로 말한 것과 같은 성질의 뒷면이다 — 적재하지 않으니 힙도 안 쓰고 스냅샷도 없지만, 반복 조회에 대한 공짜 캐시도 없다.

실무 대응은 셋 중 하나다. ① 애초에 한 요청에서 같은 목록을 두 번 조회하지 않도록 호출부를 정리한다(대부분 이게 진짜 문제다). ② 조회 결과를 메서드 안에서 변수로 들고 재사용한다. ③ 정말로 반복 조회가 필요하고 데이터가 잘 안 바뀌면 애플리케이션 캐시나 Redis 같은 명시적 캐시 계층을 둔다 — 1차 캐시를 캐시로 기대하지 않는 것이 중요하다. 1차 캐시는 트랜잭션 범위의 동일성 보장 장치이지 성능 캐시가 아니다.

DTO를 레코드로 만들라고 하셨는데, 그러면 순서 교체를 막아주는 Projections.fields는 못 쓰는 것 아닌가요? 시니어 변별힌트: 맞다. 그래서 무엇으로 메우는지가 답이다

맞다. 그 지적이 정확하다. Projections.fields는 리플렉션으로 필드에 직접 대입하는 방식이라 모든 필드가 final인 레코드와는 맞지 않는다. 그래서 레코드를 쓰면 생성자 계열(Projections.constructor 또는 @QueryProjection)로 가게 되고, 순서라는 축이 다시 살아난다.

그럼 왜 레코드를 권하는가. 레코드가 없애는 것은 "순서" 자체가 아니라 "어긋남"이기 때문이다. 일반 클래스에서는 필드 선언과 생성자가 따로 있어서 "필드만 옮기고 생성자는 안 고쳤다"는 상태가 가능하지만, 레코드는 선언 순서 = 생성자 순서 = 접근자 이름이 한 줄에 묶여 있어 그 어긋남이 생길 수 없고, 순서를 바꾸려면 그 한 줄을 고치게 되므로 리뷰 diff에 크게 드러난다.

정리 — 순서를 없애고 싶으면 인터페이스 프로젝션, 순서를 눈에 띄게 만들고 싶으면 레코드

그리고 어느 쪽을 고르든 마지막 안전망은 같다 — 같은 타입 필드들을 서로 헷갈리지 않는 값으로 픽스처를 만들고 필드별로 값을 단정하는 테스트. "도구로 못 막는 자리에 테스트를 놓는다"가 이 문항 전체의 결론이다.

DTO 프로젝션으로 페이징할 때 count 쿼리는 어떻게 하시나요? 가산점힌트: count는 "안 나가게 하는 것"과 "가볍게 만드는 것" 두 갈래다

두 갈래로 답한다.

① 아예 안 나가게 한다. PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne)는 count 쿼리를 즉시 실행하지 않고, 내용 크기만으로 전체 개수를 알 수 있는 경우에는 생략한다(예: 첫 페이지인데 결과가 페이지 크기보다 작을 때, 마지막 페이지일 때). 목록 화면의 쿼리 수를 그냥 절반으로 줄이는 효과가 난다.

② 나가야 한다면 가볍게 만든다. count 쿼리에는 표시용 조인이 필요 없다. 위 코드에서 본문 쿼리는 category를 조인하지만 count 쿼리는 product만 센다 — 조건에 쓰이지 않는 조인은 count에서 떼는 것이 원칙이다. 정렬도 마찬가지로 의미가 없다.

여기서 한 걸음 더 나가면 설계 판단이다. 데이터가 아주 많고 필터가 넓으면 정확한 총 건수 자체가 비싼 요구가 된다. 그럴 때는 "총 몇 건"을 화면에서 빼고 "다음 페이지 존재 여부"만 제공하는 방식(Slice, 또는 페이지 크기 + 1건을 조회해 더 있는지 판단)으로 요구사항 쪽을 조정한다. 쿼리 튜닝으로 못 이기는 비용은 요구사항에서 빼는 것이 정답일 때가 있다.

한 줄 요약
조회 전용 화면에 DTO 프로젝션을 쓰는 이유는 결합도가 아니라 조회 비용이다 — 엔티티 조회는 목록에 안 쓰는 description·detail_html까지 읽어 전송하고(1층: 상품 20건 조회 한 번에 약 643KB를 읽어 그중 2.7KB만 쓰는 셈이고, 초당 50회면 하루 2.6TB와 11GB의 차이가 된다), 1차 캐시에 적재하며 변경 감지용 스냅샷으로 메모리를 두 배 쓰고 커밋마다 전 필드를 비교한다(2층). @Transactional(readOnly = true)는 스냅샷과 변경 감지만 없애고 1차 캐시 적재·불필요 컬럼 전송·지연 로딩 프록시는 남기므로 대체가 아니라 병행 수단이다. 구현은 JPQL select new, QueryDSL Projections/@QueryProjection, Spring Data 인터페이스 프로젝션, 네이티브+@SqlResultSetMapping 네 가지이며 단순 조회는 인터페이스 프로젝션, 동적 조건·집계는 QueryDSL이다. @QueryProjection은 파라미터 개수와 타입만 잡고 동일 타입 순서 교체는 못 잡으므로(상품명 칸에 썸네일 URL이 찍힌 채 예외 없이 배포된다) 순서를 없애려면 이름 기반 매핑과 레코드를, 그마저 못 잡는 것은 서로 헷갈리지 않는 픽스처로 만든 필드별 값 단정 테스트로 막는다. 대신 포기하는 것도 함께 말한다 — 1:N 조인 시 행 중복(루트 페이징 + in 절 2차 쿼리 + 그룹핑으로 처방), 변경 감지 불가(스냅샷이 없어 비교할 원본이 없다), 연관 탐색 불가(값이지 프록시가 아니다), 도메인 메서드 사용 불가(규칙이 엔티티에 있다), DTO 클래스 증식. 기준은 한 문장이다 — "변경이 목적이면 엔티티, 표시가 목적이면 DTO."
