복합 유니크 제약과 동시 INSERT
JPA는 방어선이 아니다

면접 질문: "복합 유니크 제약이 있는 테이블에 동시 INSERT가 몰릴 때 JPA 레벨에서 어떤 문제가 생기나요?"

핵심 관전 포인트 — 첫 문장에서 오해부터 부순다. JPA는 유니크 제약을 검사하지 않는다. 1차 캐시(영속성 컨텍스트)는 @Id, 즉 기본 키(PK)만을 키로 갖는 Map이라 (user_id, coupon_id) 같은 유니크 컬럼 조합은 애초에 관리 대상이 아니다. persist()는 "쓰기 지연 SQL 저장소"에 INSERT 문을 쌓아둘 뿐이고, 중복 확인 SELECT를 날리지도, 락을 잡지도 않는다. 검증은 flush 시점에 전적으로 DB가 하고, DB가 던진 ConstraintViolationException을 Spring이 DataIntegrityViolationException으로 번역해 올려줄 뿐이다. 그래서 if (exists()) throw; save(); 같은 애플리케이션 사전 검사는 UX용(친절한 에러 메시지)이지 정합성 보장 수단이 아니다 — 두 스레드가 모두 false를 받고 통과하는 틈이 반드시 존재한다. 여기서 가장 크게 헛디디는 지점이 하나 더 있다. 예외를 try/catch로 잡아도 트랜잭션은 살아나지 않는다. 제약 위반이 나는 순간 하이버네이트 세션이 오염 상태가 되고 Spring 트랜잭션에 rollback-only 플래그가 찍히므로, catch 블록 안에서 이력을 저장하고 정상 종료시켜도 커밋 시점에 UnexpectedRollbackException이 터지며 그 이력 저장까지 함께 롤백된다. 처방은 후속 작업을 REQUIRES_NEW로 분리하거나 예외를 트랜잭션 경계 밖에서 잡는 것. 그리고 마지막 원칙: 락을 아무리 잘 걸어도 DB 유니크 제약은 절대 빼지 않는다 — 락은 TTL 만료·네트워크 분단·노드 페일오버·락 해제와 커밋의 순서 역전에서 뚫리고, 무엇보다 배치 잡·운영자 수동 SQL·데이터 마이그레이션처럼 락 획득 코드를 아예 거치지 않는 진입 경로를 전혀 덮지 못한다. 모든 진입 경로를 덮는 것은 DB 제약뿐이다.
  • 1
    JPA는 유니크 제약을 검사하지 않는다 — 1차 캐시는 @Id를 키로 하는 Map이라 (user_id, coupon_id) 조합은 물어볼 수 있는 키 자체가 아니고, 게다가 캐시는 트랜잭션 하나의 범위라 다른 스레드의 행은 보이지도 않는다. persist()는 INSERT를 쌓아둘 뿐 SELECT도 락도 없고, 검증은 flush 시점에 전적으로 DB가 한다.
  • 2
    그래서 exists() → save() 사전 검사는 정합성 장치가 아니라 UX 장치다 — 확인과 행동 사이에 틈(window)이 있어 두 스레드가 나란히 "없음"을 받고 통과한다. 이 틈은 격리 수준을 올려도 사라지지 않는다(스냅샷은 상대의 미커밋 INSERT를 정의상 보여주지 않는다). 사전 검사는 지우지 말고 역할을 주석으로 명시한다.
  • 3
    뚫린 한 건의 예외는 잡아도 트랜잭션을 살리지 못하고, 락은 제약을 대체하지 못한다 — 제약 위반 순간 rollback-only가 찍혀 catch 안의 저장까지 함께 사라진다(UnexpectedRollbackException) → REQUIRES_NEW 분리 또는 경계 밖 catch. 그리고 배치·수동 SQL·마이그레이션은 락 코드를 아예 지나가지 않으므로 모든 경로를 덮는 것은 DB 제약뿐이다.

0. 질문 + 출제 의도

질문: "복합 유니크 제약이 있는 테이블에 동시 INSERT가 몰릴 때 JPA 레벨에서 어떤 문제가 생기나요?"

관련 질문 — "(user_id, coupon_id) 복합 유니크 제약이 걸린 쿠폰 발급 테이블에 같은 사용자의 발급 요청이 동시에 들어올 때, JPA 레벨에서 어떤 문제가 생기고 어떻게 대응하겠습니까?" · "분산 락으로 동시 진입을 확실히 막았다면 DB 유니크 제약은 빼도 되나요?"

출제 의도: 중복 체크 후 저장(check-then-act) 패턴이 동시성에서 깨지는 것을 아는지. 회원가입·쿠폰 발급 등에서 반복 출제되는 실전 상황으로, DB 제약을 최후 방어선으로 쓰는 설계 습관을 본다.

채점 지점은 세 층이다 ① persist()와 flush 사이에서 누가 무엇을 검사하는가를 사실로 아는가(= JPA는 검사하지 않는다)
② 사전 검사가 깨지는 시간 순서를 말할 수 있는가
③ 방어선을 여러 겹으로 쌓되 가장 아래는 항상 DB라는 설계 습관이 있는가
이 페이지가 겨냥하는 함정 세 개 ① "영속성 컨텍스트가 알아서 걸러준다"는 전제 → 이 전제 위에서는 "그럼 JPA가 락을 잡겠네 → 커넥션이 고갈되겠네"까지 틀린 결론이 자동으로 따라온다. 커넥션 대기는 실제로 일어날 수 있으나 이유가 완전히 다르다(4-1절).
② try/catch로 잡으면 끝났다고 믿는 것 → 예외를 잡는 것과 트랜잭션을 살리는 것은 별개다. 실무 사고를 가르는 지점이 여기다(5절).
③ "락을 걸었으니 제약은 없어도 된다"는 최적화 → 유니크 인덱스는 성능 부담이 아니라 마지막 안전망이고, 락이 덮지 못하는 경로가 반드시 존재한다(6절).

1. JPA는 검사하지 않는다 — 1차 캐시는 @Id를 키로 하는 Map

이 문항은 사실 확인 하나에서 시작한다. 많은 사람이 save()(내부적으로 persist()) 안에서 하이버네이트가 중복을 확인해 줄 것이라고 상상하는데, 그 일은 일어나지 않는다.

그럼 이 오해는 왜 생기나 — 하이버네이트가 PK 중복은 실제로 걸러주기 때문 같은 트랜잭션 안에서 이미 관리 중인 id로 persist()를 부르면 DB에 가기 전에 EntityExistsException이 나기도 한다. 이 경험이 "유니크도 걸러주겠지"로 일반화된다. 핵심은 PK와 유니크 제약은 하이버네이트에게 전혀 다른 지위라는 것이다 — PK는 1차 캐시의 키이고, 유니크 컬럼은 그냥 필드 값이다.

1-1. 자료구조로 보면 왜 불가능한지가 즉시 보인다

비유 — 1차 캐시는 "내 책상"이다 1차 캐시는 "내가 이번 회의에서 꺼낸 서류들을 사번으로 정리해 둔 내 책상"이다. ① 옆자리 동료가 지금 무슨 서류를 쓰고 있는지 내 책상은 알 수 없고(트랜잭션 격리), ② 애초에 "이름+부서 조합으로 찾기"라는 색인이 없다(@Id만 키). 두 가지 이유가 겹쳐 있다는 점을 같이 말하면 답변이 단단해진다.

암기 — JPA가 INSERT 경로에서 하지 않는 것 3가지

중복 확인 SELECT
유니크 컬럼을 조회하는 쿼리는 존재하지 않는다.
락 획득
persist()는 어떤 락도 잡지 않는다.
유니크 제약 검증
애노테이션은 DDL 생성용 메타데이터일 뿐이다.
한 문장으로 — "JPA는 INSERT를 쌓아둘 뿐이고, 검증은 flush 시점에 전적으로 DB가 한다."

1-2. 언제 INSERT가 나가는가 — PK 생성 전략이 예외가 터지는 줄을 바꾼다

persist()가 INSERT를 쌓아둔다고 했지만, "언제 DB로 나가는가"는 PK 생성 전략에 따라 갈린다. 이 차이가 예외가 터지는 코드 줄의 위치를 바꾸기 때문에 실무 디버깅에서 중요하다.

2. 검증은 flush 시점의 DB가 한다 — 예외가 올라오는 3층 구조

flush가 일어나면 쌓아둔 INSERT가 DB로 나가고, 그때 DB의 유니크 인덱스가 중복을 발견한다. 그런데 DB가 낸 에러가 우리 코드까지 그대로 올라오지는 않는다. 중간에 두 번 번역된다. 번역이 있는 이유는 단순하다 — 위층 코드가 아래층 기술에 묶이지 않게 하려는 것이다. 서비스 코드가 "MySQL 에러 코드 1062"를 알아야 한다면 그 코드는 PostgreSQL로 못 옮기고, "하이버네이트 예외"를 알아야 한다면 ORM을 못 바꾼다.

ConstraintViolationException이라는 이름의 클래스는 두 개다 가산점

DB 제약 위반 — 지금 이 문항

org.hibernate.exception.ConstraintViolationException

Bean Validation 위반 — 전혀 다른 층

jakarta.validation.ConstraintViolationException (@NotNull 등)

전혀 다른 층의 예외인데 IDE 자동 임포트가 엉뚱한 쪽을 잡아 "분명 catch 했는데 안 잡힌다"는 상황이 실제로 자주 생긴다. 면접에서 이 구분을 짚으면 실제로 겪어본 사람이라는 신호가 된다.

2-1. 무엇을 catch할 것인가 — 3층은 너무 넓다

DataIntegrityViolationException은 유니크 위반뿐 아니라 NOT NULL 위반, 외래 키 위반, 길이 초과까지 포괄하는 넓은 타입이다. 너무 넓게 잡으면 전혀 다른 버그를 "이미 발급됨"으로 오인해 삼켜버린다.

before 넓게 잡아 다른 무결성 오류까지 "중복"으로 취급
catch (DataIntegrityViolationException e) {
    return IssueResult.ALREADY_ISSUED;   // NOT NULL 위반도, FK 위반도 여기로 들어온다진짜 버그가 조용히 삼켜진다
}
"그럼 DuplicateKeyException으로 좁혀 잡으면 되지 않나?" — JPA 경로에서는 기본 설정으로 그 예외가 오지 않는다 하이버네이트의 ConstraintViolationException은 HibernateJpaDialect에서 DataIntegrityViolationException으로 변환될 뿐이고, 그보다 좁은 DuplicateKeyException으로 내려가려면 SQLSTATE를 보고 판단하는 JDBC용 예외 변환기가 끼어 있어야 하는데 그 자리가 기본값으로 비어 있기 때문이다. (JdbcTemplate이나 Spring Data JDBC 경로에서는 그 변환기가 기본으로 동작하므로 DuplicateKeyException이 온다 — 같은 Spring인데 경로에 따라 다르다는 것이 헷갈리는 지점이다.)
after A 좁은 타입이 오도록 변환기를 켠다
// SQLExceptionTranslator 빈이 하나 있으면 Spring Boot가
// 그것을 JPA 예외 변환 경로에 꽂아준다.
@Bean
SQLExceptionTranslator sqlExceptionTranslator() {
    return new SQLExceptionSubclassTranslator();
}

// 그 뒤로는 SQLSTATE 23505(PostgreSQL) /
// 23000+1062(MySQL) 가 좁혀져 올라온다.
catch (DuplicateKeyException e) {
    return IssueResult.ALREADY_ISSUED;   // 중복만 정확히
}

설정 한 번으로 코드가 깔끔해진다.

after B 설정 없이, 원인 예외의 제약 이름으로 좁힌다
catch (DataIntegrityViolationException e) {
    if (e.getCause() instanceof
            org.hibernate.exception.ConstraintViolationException ce
        && "uk_coupon_issue_user_coupon".equals(ce.getConstraintName())) {
        return IssueResult.ALREADY_ISSUED;
    }
    throw e;   // 그 외 무결성 오류는 그대로 올려보낸다삼키지 않는다
}

설정 없이 되지만 문자열 비교라 제약 이름을 바꾸는 마이그레이션에 취약하다.

어느 쪽이든 — "그냥 DataIntegrityViolationException을 통째로 삼키는" 코드보다는 낫다
확인 범위 (원본 문서의 검증 기록) 위 서술은 spring-orm 6.2.19(HibernateJpaDialect), spring-jdbc 6.2.19(SQLExceptionSubclassTranslator, SQLStateSQLExceptionTranslator.indicatesDuplicateKey), spring-boot-autoconfigure 3.5.16(HibernateJpaConfiguration.createJpaVendorAdapter) 소스를 직접 확인한 것이다. Spring Boot는 컨텍스트에 SQLExceptionTranslator 빈이 유일하게 하나 있을 때 그것을 주입한다(ifUnique). 버전에 따라 동작이 다를 수 있으니 실제 프로젝트에서는 통합 테스트로 어떤 예외가 오는지 한 번 확인하고 쓰는 편이 안전하다.

3. check-then-act — "확인하고 나서 행동한다"의 사이에 틈이 있다

이 문항의 핵심 용어가 여기서 나온다. check-then-act는 말 그대로 "확인(check)하고 나서 행동(act)한다"는 뜻이고, 그 둘이 분리된 두 개의 문장이라는 데 문제가 있다.

if (!repo.existsByUserIdAndCouponId(userId, couponId)) {   // ← check (확인)
    repo.save(new CouponIssue(userId, couponId));          // ← act  (행동)
}

확인이 끝나고 행동이 시작되기까지는 아무리 짧아도 시간이 걸린다. 그 사이에 다른 스레드가 끼어들 수 있고, 끼어든 스레드가 행을 만들어 버리면 내가 방금 받은 "없다"는 답은 이미 낡은 정보가 된다. 이 "끼어들 수 있는 시간 구간"을 틈(window)이라고 부른다.

비유 — 빈 회의실

빈 회의실을 확인하고 걸어가는 사이에 다른 팀이 먼저 들어가 앉는 것과 같다. "비어 있다"를 본 것은 사실이지만, 그 사실이 내가 문을 여는 순간까지 유지된다는 보장은 없다.

그래서 필요한 것이 예약 시스템 = 원자적 연산이다(7절 upsert).

원자적(atomic)이라는 말의 정의

확인과 행동이 쪼개질 수 없는 한 덩어리로 실행되면 그 사이에 아무도 끼어들 수 없다.

exists() + save()는 두 덩어리라 원자적이지 않다. 반대로 INSERT ... ON CONFLICT는 확인과 삽입이 DB의 한 문장 안에서 일어나므로 원자적이다.

3-1. 격리 수준을 올려도 이 틈은 사라지지 않는다

여기서 사람들이 마지막으로 붙잡는 희망이 "트랜잭션 격리 수준을 올리면 되지 않나"인데, 막을 수 없다.

전제부터 깔자. 격리 수준(isolation level)은 "동시에 도는 트랜잭션들이 서로의 작업을 얼마나 볼 수 있는가"를 정하는 설정이다. 그런데 그 규정의 대상이 "이미 존재하는 행을 어떻게 보느냐"이지, "아직 존재하지 않는 행을 남이 만들려 하는 것"이 아니다.

직관과 정반대인 지점 — 격리 수준이 높아질수록 상대의 작업이 더 안 보인다

REPEATABLE READ에서 두 트랜잭션은 각자의 스냅샷을 보고 둘 다 "없다"고 판단한다 — 스냅샷은 상대의 미커밋 INSERT를 정의상 보여주지 않기 때문이다.

"격리를 강하게 걸었으니 안전하다"가 아니라 — "격리를 강하게 걸수록 서로를 못 봐서 나란히 통과한다"

SERIALIZABLE은 이야기가 달라지는데(직렬화 실패나 데드락으로 한쪽을 실패시킨다), 그래도 실무 답이 아닌 이유는 9절 꼬리질문에서 따로 다룬다.

5-1. rollback-only 마킹이란 무엇인가 — 예외 객체와 상태 플래그는 다른 층위다

rollback-only 마킹이란, 트랜잭션 객체에 "이건 무슨 일이 있어도 커밋하면 안 된다"는 표시를 박아두는 것이다. 스프링 트랜잭션은 커밋할지 롤백할지를 마지막에 한 번 결정하는데, 그 결정 직전에 이 표시를 확인한다. 표시가 켜져 있으면 개발자가 아무리 정상 리턴을 해도 커밋하지 않는다. "이 트랜잭션은 커밋 대상에서 제외한다"는 낙인이라고 이해하면 된다.

5-2. 누가 그 표시를 켰는가 — 근거가 두 층에 있다

첫째, JPA 명세 차원의 규칙이다. EntityManager 연산이 예외를 던지면 영속성 제공자(하이버네이트)는 그 트랜잭션을 롤백 대상으로 표시해야 한다고 명세가 규정한다(조회 결과 없음이나 락 타임아웃 같은 소수 예외를 제외하고). 하이버네이트의 예외 변환 코드가 실제로 그렇게 되어 있다.

hibernate org.hibernate.internal.ExceptionConverterImpl
private void rollbackIfNecessary(PersistenceException e) {
    if ( !( e instanceof NoResultException          // 이 넷만 예외적으로 봐준다
            || e instanceof NonUniqueResultException
            || e instanceof LockTimeoutException
            || e instanceof QueryTimeoutException ) ) {
        try {
            sharedSessionContract.markForRollbackOnly();   // ← 여기서 낙인이 찍힌다
        }
        catch (Exception ne) { ... }
    }
}
왜 그렇게까지 하는가 — 세션이 오염됐기 때문 제약 위반이 난 시점에 하이버네이트 세션 안의 상태와 DB의 상태가 어긋났고, 하이버네이트는 어긋난 정도를 정확히 알 수 없다. 쓰기 지연 저장소에 남은 SQL 중 무엇이 나갔고 무엇이 안 나갔는지, 1차 캐시의 어떤 엔티티가 유효한지 보장할 수 없으므로 "이 세션은 오염됐다. 더 쓰지 말고 버려라"가 유일하게 안전한 선택이다.

둘째, 그 표시를 Spring이 커밋 직전에 읽는다. JPA/하이버네이트 조합에서는 커밋 요청을 받은 하이버네이트가 rollback-only 표시를 보고 아무 예외도 던지지 않고 조용히 롤백한 뒤 정상 리턴한다. 그래서 Spring이 미리 기록해 둔 "이건 커밋될 수 없는 트랜잭션이었다"는 사실을 근거로 뒤늦게 예외를 만들어 던진다. 즉 catch 블록 안에서 한 모든 DB 작업이 성공한 것처럼 보이다가 마지막에 통째로 사라진다.

로그 메시지가 조금 다르게 보일 수도 있다 JDBC/MyBatis처럼 트랜잭션 관리자가 다른 경로에서는 Transaction rolled back because it has been marked as rollback-only(silently가 빠진 형태)로 나온다. 둘은 같은 사건의 다른 경로일 뿐이므로 진단은 같다 — "안쪽에서 rollback-only가 찍혔고 누군가 예외를 삼켰다"부터 의심한다.

확인 범위: 두 메시지는 spring-tx 6.2.19의 AbstractPlatformTransactionManager에 각각 processCommit(silently 포함)·processRollback(silently 없음)으로 존재하는 문자열이다. JPA가 앞쪽 경로를 타는 이유는 spring-orm 6.2.19의 JpaTransactionManager.shouldCommitOnGlobalRollbackOnly()가 true이고, hibernate-core 6.6.53.Final의 JdbcResourceLocalTransactionCoordinatorImpl이 JPA 준수 모드가 꺼져 있을 때 rollback-only 트랜잭션의 commit을 예외 없이 롤백 처리하기 때문이다.

처방 ① 후속 작업을 REQUIRES_NEW로 분리

        // 바깥이 롤백돼도 독립적으로 커밋되어 살아남는다.

전파(propagation)는 "이미 열려 있는 트랜잭션이 있을 때 이 메서드가 어떻게 행동할지"를 정하는 설정이다. 기본값 REQUIRED가 "있으면 합류"인 반면 REQUIRES_NEW는 "있어도 무시하고 새로 연다"이다.

처방 ② 예외를 트랜잭션 경계 밖에서 잡기
// [안쪽] 트랜잭션 담당 — 예외를 잡지 않고 그대로 올려보낸다
@Service @RequiredArgsConstructor
public class CouponIssueService {
    private final CouponIssueRepository repo;

    @Transactional

// [바깥] 트랜잭션 없음 — 여기서 잡으면 이미 롤백이 끝난 뒤라 안전
@Service @RequiredArgsConstructor
public class CouponIssueFacade {
    private final CouponIssueService couponIssueService;
    private final IssueLogService issueLogService;

    // @Transactional 을 붙이지 않는 것이 포인트다.
    public IssueResult issue(Long userId, Long couponId) {
        try {
            couponIssueService.issue(userId, couponId);
            return IssueResult.SUCCESS;
        } catch (AlreadyIssuedException e) {          // 흔한 경우
            return IssueResult.ALREADY_ISSUED;
        } catch (DataIntegrityViolationException e) { // 뚫린 경우
            // 안쪽 트랜잭션이 이미 롤백 완료 상태다.
            // 여기서 시작하는 DB 작업은 새 트랜잭션에서 깨끗하게 돈다.
            issueLogService.logDuplicated(userId, couponId);
            return IssueResult.ALREADY_ISSUED;
        }
    }
}

커넥션 2배
바깥 커넥션을 붙잡은 채 새 커넥션을 빌린다. 트래픽 경로에서 남발하면 풀 고갈로 교착.
자기 호출 무효
this.logDuplicated(...)는 프록시를 안 거쳐 @Transactional이 통째로 무시된다. 반드시 다른 빈으로.
정합성 역전
바깥이 롤백돼도 안쪽은 남는다 — 목적이 아닌 곳에 붙이면 "주문은 실패했는데 결제 이력만 남는" 사고.

붙이기 전에 자문한다 — "이 기록은 바깥이 실패해도 남아야 하는가?"

어느 쪽을 고를까 — 기본은 ②, ①은 "증거"에만

기본값 — ② 경계 밖에서 잡기

트랜잭션 경계를 단순하게 유지하는 쪽이 언제나 유지보수에 유리하고, 커넥션도 추가로 쓰지 않는다. 게다가 "트랜잭션 경계"와 "예외를 응답으로 번역하는 경계"가 클래스로 분리되어, 나중에 누가 파사드에 @Transactional을 붙이면 문제가 되살아난다는 것도 이름만으로 드러난다.

예외적으로 — ① REQUIRES_NEW

"바깥의 성패와 무관하게 반드시 남아야 하는 기록"에만 쓴다. 감사 로그, 부정 사용 탐지 이력, 외부 결제사 응답 원문처럼 롤백돼서는 안 되는 증거가 여기 해당한다.

암기 문장 — "새로 열거나(REQUIRES_NEW), 밖에서 잡거나(파사드). 그 자리에서 삼키는 것만은 안 된다."

6. 락은 최후 방어선이 아니다 — 심층 방어

"Redis 분산 락으로 완벽히 막았으니 유니크 인덱스는 빼서 INSERT 성능을 아끼자"는 제안은 실무에서 실제로 나온다. 답은 항상 '안 된다'이고, 중요한 것은 그 근거를 구체적으로 대는 것이다. 근거는 두 종류인데, 성격이 완전히 다르다.

6-1. 뚫리는 경로 ① — 락 로직 자체의 실패 (확률을 낮출 수는 있다)

암기 — 락이 뚫리는 다섯 경로 "티 · 분 · 페 · 키 · 순"

티 = TTL 만료분 = 네트워크 분단페 = 노드 페일오버키 = 락 키 네이밍 변경순 = 순서 역전
티 — TTL 만료
작업이 TTL보다 오래 걸리면(GC 정지, DB 지연, 외부 API 지연) 락이 저절로 풀리고 두 번째 요청이 들어온다. 첫 요청은 자기 락이 풀린 줄도 모르고 계속 진행한다.
분 — 네트워크 분단
해제 명령이 Redis에 닿지 못하거나, 반대로 락 획득 실패를 "락 없이 진행"으로 처리하는 폴백이 걸려 있으면 그 순간 무방비가 된다.
페 — 노드 장애·페일오버
복제가 비동기라면 마스터가 락 정보를 복제본에 넘기기 전에 죽을 수 있다. 승격된 새 마스터에는 그 락이 아예 없으므로 두 번째 요청이 같은 락을 새로 획득한다.
키 — 배포 중 키 네이밍 변경
coupon:issue:{userId} → coupon-issue:v2:{userId}:{couponId} 같은 변경이 롤링 배포로 나가면 구버전·신버전이 서로 다른 키를 잡아 둘 다 통과한다.
순 — 락 해제와 커밋의 순서 역전 (가장 흔한 실수) — 락을 완벽히 구현해도 감싸는 순서를 틀리면 그대로 뚫린다
before 락이 트랜잭션 안쪽에 있다
@Transactional
public void issue(Long userId, Long couponId) {
    lock.acquire(key);
    try {
        if (repo.existsByUserIdAndCouponId(userId, couponId))
            throw new AlreadyIssuedException();
        repo.save(new CouponIssue(userId, couponId));
    } finally {
        lock.release(key);      // ← 여기서 락이 풀린다
    }
}   // ← 커밋은 그 다음이다. 이 틈에 다음 요청이 통과한다.아직 INSERT가 안 보인다

두 번째 요청은 아직 커밋되지 않은 첫 요청의 INSERT를 보지 못해 exists()에서 false를 받는다.

after 락이 트랜잭션을 완전히 감싼다
// 이 메서드에는 @Transactional 이 없다
public void issue(Long userId, Long couponId) {
    lock.acquire(key);
    try {
        // 이 안에서 @Transactional 이 시작되고 커밋된다
        couponIssueService.issue(userId, couponId);
    } finally {
        lock.release(key);      // 커밋이 끝난 뒤에야 풀린다
    }
}

5절의 "파사드에 @Transactional을 붙이지 않는다"와 정확히 같은 구조다 — 트랜잭션 경계를 안쪽으로 밀어 넣는 설계가 두 문제를 동시에 푼다.

6-2. 뚫리는 경로 ② — 락을 아예 거치지 않는 진입 경로 (확률이 0이 되지 않는다)

위 다섯 가지는 락 로직을 잘 짜면 확률을 낮출 수 있다. 그러나 다음은 락 로직을 아무리 잘 짜도 확률이 0이 되지 않는다. 애초에 그 코드를 지나가지 않기 때문이다.

위층은 "대부분의 경우를 싸고 친절하게 처리"하고, 맨 아래층은 "무슨 일이 있어도 데이터를 지킨다"는 역할 분담이다. 어느 층이든 뚫릴 수 있다는 전제로 쌓는 것이 심층 방어(defense in depth)이고, 이 문항이 실제로 보려는 설계 습관이 그것이다.

7. 제3의 선택지 — 원자적 upsert로 예외 자체를 없앤다

"락으로 막느냐, 예외를 잡느냐"는 이분법에는 세 번째 답이 있다. DB에게 "있으면 무시하고 없으면 넣어라"를 한 문장으로 시키는 것이다. 3절에서 정의한 틈이 여기서는 존재하지 않는다 — 확인과 삽입이 한 문장 안에서 일어나기 때문이다.

upsert라는 이름은 update + insert를 합친 말이다. "이미 있으면 갱신, 없으면 삽입"이라는 뜻이고, "있으면 아무것도 안 함"까지 포함해 부른다.

SQL 벤더별 구문 — 의미는 같고 문법은 다르다
-- PostgreSQL (이 저장소의 기준 DB) — 어떤 제약에서 충돌할지 명시할 수 있다
INSERT INTO coupon_issue (user_id, coupon_id, issued_at)
VALUES (?, ?, ?)
ON CONFLICT (user_id, coupon_id) DO NOTHING;

-- PostgreSQL — "있으면 갱신"이 요구사항일 때. EXCLUDED 는 "넣으려다 충돌한 그 행"을 가리키는 특수 별칭
INSERT INTO coupon_issue (user_id, coupon_id, issued_at)
VALUES (?, ?, ?)
ON CONFLICT (user_id, coupon_id)
DO UPDATE SET issued_at = EXCLUDED.issued_at;

-- MySQL — 중복이면 조용히 넘어가는 관용구 (아무것도 바꾸지 않는다)
INSERT INTO coupon_issue (user_id, coupon_id, issued_at)
VALUES (?, ?, ?)
ON DUPLICATE KEY UPDATE user_id = user_id;

-- MySQL — 더 짧지만 위험한 버전 (7-3 참고)
INSERT IGNORE INTO coupon_issue (user_id, coupon_id, issued_at) VALUES (?, ?, ?);
여기서 "제약을 빼도 되나"라는 질문에 대한 또 하나의 답이 나온다 PostgreSQL의 ON CONFLICT (user_id, coupon_id)는 그 컬럼 조합에 유니크 인덱스가 실제로 있어야만 동작한다. 즉 이 방식조차도 유니크 제약을 전제로 성립한다.

7-1. Spring Data JPA에서 쓰는 법

JPQL에는 이런 구문이 없으므로 네이티브 쿼리로 쓴다. 네이티브 쿼리란 JPQL로 번역하지 않고 DB에 그대로 보내는 SQL을 말한다.

repository 네이티브 upsert
public interface CouponIssueRepository
        extends JpaRepository<CouponIssue, Long> {

    @Modifying   // 조회가 아니라 "변경" 쿼리라는 표시
    @Query(value = """
            INSERT INTO coupon_issue (user_id, coupon_id, issued_at)
            VALUES (:userId, :couponId, now())
            ON CONFLICT (user_id, coupon_id) DO NOTHING
            """, nativeQuery = true)
    int insertIfAbsent(@Param("userId") Long userId,
                       @Param("couponId") Long couponId);
}
service 영향 행 수로 결과를 판정한다
@Transactional
public IssueResult issue(Long userId, Long couponId) {
    int affected = repo.insertIfAbsent(userId, couponId);
    // PostgreSQL 의 ON CONFLICT ... DO NOTHING 은
    //   1 = 새로 INSERT 됨
    //   0 = 충돌해서 아무것도 하지 않음
    return affected == 1 ? IssueResult.SUCCESS
                        : IssueResult.ALREADY_ISSUED;
}

MySQL은 영향 행 수의 의미가 다르다 — 1 = 새로 INSERT, 2 = 실제로 UPDATE, 0 = 값이 그대로라 변경 없음. 위의 "아무것도 바꾸지 않는" 관용구를 쓰면 중복일 때 0이 돌아온다.

upsert가 얻는 것 두 가지

① 왕복 1회 · 락 비용 0
확인과 삽입이 DB의 한 문장이라 네트워크 왕복이 한 번이고, 애플리케이션 락 인프라가 필요 없다.
② 예외가 아예 발생하지 않는다
그러므로 5절의 rollback-only 문제까지 통째로 우회된다. 예외 처리 설계 자체가 사라진다 — 이 효과가 특히 크다.

7-2. 대가 — 영속성 컨텍스트를 우회한다

네이티브 쿼리는 1차 캐시를 지나치지 않고 곧장 DB로 간다. 이것은 벌크 연산(@Modifying UPDATE/DELETE)과 정확히 같은 성질이며, 같은 함정을 가진다.

before 방금 넣었는데 조회하면 없다(혹은 옛 값이 보인다)
@Transactional
public void issueAndNotify(Long userId, Long couponId) {
    repo.insertIfAbsent(userId, couponId);      // DB 에는 들어갔다
    long count = repo.countByUserId(userId);  // 1차 캐시 상태와 어긋날 수 있다
    CouponIssue issue = repo.findByUserIdAndCouponId(userId, couponId).orElseThrow();캐시본이 반환될 수 있다
    // ↑ 1차 캐시에 같은 id 의 엔티티가 있었다면 DB 결과가 아니라 캐시본이 온다
}
after 경계를 명확히 한다
@Transactional
public IssueResult issue(Long userId, Long couponId) {
    int affected = repo.insertIfAbsent(userId, couponId);
    return affected == 1 ? IssueResult.SUCCESS : IssueResult.ALREADY_ISSUED;
    // 이 트랜잭션에서는 결과 코드만 쓰고, 엔티티를 다시 읽지 않는다.
    // 방금 넣은 행이 꼭 필요하면 별도 트랜잭션에서 조회하거나
    // 같은 트랜잭션이라면 명시적으로 컨텍스트를 비운 뒤 조회한다.
}
@Modifying(flushAutomatically = true, clearAutomatically = true)는 만능이 아니다 "실행 전에 flush, 실행 후에 컨텍스트 비우기"를 자동화할 수는 있다. 다만 컨텍스트를 비우면 관리 중이던 다른 엔티티의 변경 감지도 함께 날아가므로, 옵션을 켜는 것보다 애초에 이 트랜잭션에서 엔티티를 다시 읽지 않도록 경계를 좁게 잡는 편이 안전하다.

추가로 잃는 것들: 하이버네이트의 엔티티 리스너·감사(@CreatedDate 등)·@Version 증가가 동작하지 않고, SQL이 DB 벤더에 묶인다. 그래서 upsert는 "엔티티 생명주기가 단순한 관계 테이블"에 가장 잘 맞는다 — 쿠폰 발급 이력, 좋아요, 팔로우, 조회 기록처럼 "있으면 그만, 없으면 만든다"가 전부인 행이 그렇다.

7-3. INSERT IGNORE의 함정 가산점

MySQL INSERT IGNORE — 무시하는 범위가 중복만이 아니다

데이터 잘림, 타입 변환 실패 같은 다른 오류까지 경고로 낮춰 조용히 통과시킨다. "쿠폰 코드가 잘려서 저장됐는데 아무도 몰랐다" 같은 사고가 여기서 나온다.

의도가 "중복만 무시"라면

MySQL은 ON DUPLICATE KEY UPDATE를 쓰는 편이 안전하다. PostgreSQL의 ON CONFLICT ... DO NOTHING은 애초에 충돌만 다루므로 이 문제가 없다.

유니크 인덱스가 여러 개인 테이블에서의 함정 upsert 구문이 "어느 제약에서 충돌했는지"를 구분해 주는지가 벤더마다 다르다. PostgreSQL은 ON CONFLICT (컬럼)으로 대상 제약을 지정할 수 있어 의도한 제약에서만 무시하도록 만들 수 있지만, MySQL은 지정 수단이 없어 어느 유니크 키에서 충돌해도 똑같이 무시된다. 그 경우 의도한 제약이 아닌 다른 제약에서 충돌한 것을 성공으로 오인할 수 있다.

8-1. 실무에서 이 문항이 나타나는 네 가지 얼굴

① 회원가입 이메일 중복
가장 고전적인 사례. 가입 버튼을 두 번 빠르게 누르거나 응답이 느려 새로고침하면 그대로 재현된다. exists 검사만 있고 유니크 인덱스가 없으면 같은 이메일로 계정이 두 개 생기고, 이후 findByEmail이 예외를 뿜기 시작한다 — 원인과 증상이 멀어 추적이 어려운 전형이다.
② 좋아요 · 팔로우 토글
클라이언트에 재시도 로직이 있으면 같은 요청이 두 번 도착하는 것이 정상 상황이다. upsert가 가장 잘 맞는 자리 — "이미 좋아요면 그냥 성공으로 응답"이 곧 요구사항이기 때문이다.
③ 결제 · 주문 이중 처리 가산점
여기서 유니크 제약은 멱등성 키(idempotency key)로 쓰인다. 클라이언트가 만든 요청 식별자를 유니크 컬럼으로 두면, 네트워크 재시도로 같은 요청이 두 번 와도 두 번째는 DB가 막고 첫 번째 결과를 돌려준다. 이 패턴을 언급하면 "DB 제약을 단순 검증이 아니라 설계 도구로 쓴다"는 신호가 된다.
④ Soft delete와의 충돌 가산점
탈퇴를 deleted_at 표시로만 처리하면 삭제된 행이 유니크 값을 계속 점유해 "탈퇴했는데 재가입이 안 됩니다"가 된다. 흔한 우회는 유니크 키에 삭제 시각·시퀀스를 포함시키는 것인데, NULL 처리라는 함정이 따라온다 — 표준 SQL에서 유니크 인덱스는 NULL을 서로 다른 값으로 취급하므로 deleted_at이 NULL인 행은 아무리 많아도 중복으로 걸리지 않는다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

JPA는 왜 못 막나?
1차 캐시는 @Id를 키로 하는 Map이라 (7,3)은 물어볼 키가 아니고, 캐시는 트랜잭션 하나의 범위다. persist()는 SELECT도 락도 없이 INSERT를 쌓는다.
사전 검사의 역할은?
UX + 비용 절감이지 정합성이 아니다. 지우지 말고 주석으로 역할을 명시한다 — 안 적으면 exists나 유니크 제약 중 하나가 잘못 지워진다.
틈(window)이란?
check와 act 사이의 구간. 격리 수준을 올려도 안 사라진다 — 스냅샷은 상대의 미커밋 INSERT를 정의상 안 보여주기 때문에 오히려 더 안 보인다.
예외 3층은?
DB(23505 / 1062) → 하이버네이트 ConstraintViolationException → Spring DataIntegrityViolationException. 잡을 것은 3층, 단 너무 넓다는 문제가 남는다.
catch 했는데 왜 실패?
제약 위반 순간 rollback-only 낙인 → 커밋 시 UnexpectedRollbackException. catch 안의 저장까지 사라진다. 처방: REQUIRES_NEW 분리 / 경계 밖 catch.
락이 뚫리는 5경로?
티 · 분 · 페 · 키 · 순 — TTL 만료 · 네트워크 분단 · 페일오버 · 키 네이밍 변경 · 락 해제와 커밋의 순서 역전.
락이 못 덮는 경로?
배 · 수 · 마 — 배치 잡 · 운영자 수동 SQL · 마이그레이션(+타 팀 백오피스, 테스트 시드). 애초에 락 코드를 지나가지 않는다.
세 가지 선택은?
드물면 예외 · 잦으면 락 · "있으면 무시"면 upsert. 셋 다 DB 유니크 제약은 유지한다. 락은 측정 후 마지막에 붙인다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

save()를 부르는 그 줄에서 바로 예외가 나나요, 아니면 나중인가요? 필수힌트: "때에 따라 다르다"로 시작하되, 무엇에 따라 다른지를 정확히 짚는다

PK 생성 전략에 따라 다르다.

IDENTITY(MySQL AUTO_INCREMENT, PostgreSQL identity 컬럼)는 id를 DB가 만들어주므로 INSERT를 해봐야 id를 알 수 있다. 따라서 쓰기 지연이 원천적으로 불가능하고, save() 호출 즉시 INSERT가 나가 그 줄에서 바로 예외가 터진다.

SEQUENCE/TABLE은 id를 미리 확보할 수 있어 INSERT를 쌓아둔다. 예외는 커밋 직전 flush 시점에 터지고, 스택 트레이스가 save() 호출부를 가리키지 않아 원인 파악이 어렵다.

진단하려다 헷갈리기 쉬운 점: saveAndFlush()나 중간의 JPQL 실행은 강제로 flush를 유발하므로 엉뚱한 줄에서 예외가 터진 것처럼 보인다. "코드상 순서와 실제 SQL 실행 순서가 다르다"는 것이 영속성 컨텍스트의 기본 성질이다(15-flush-timing-and-sql-ordering.md).

분산 락으로 동시 진입을 확실히 막았다면 DB 유니크 제약은 빼도 되나요? 필수힌트: "안 됩니다"로 끝내지 말고 근거를 두 종류로 나눠 댄다 — 성격이 다르다

안 된다. 근거는 두 종류이고 성격이 다르다는 점을 나눠 말하는 것이 핵심이다.

① 락 로직 자체가 실패하는 경로 — "티·분·페·키·순": TTL 만료(작업이 TTL보다 길어지면 락이 저절로 풀리고 첫 요청은 그것도 모른 채 진행), 네트워크 분단(해제 명령 유실, 혹은 "락 획득 실패 시 그냥 진행" 폴백), 노드 페일오버(비동기 복제라 승격된 새 마스터에 락이 없다), 배포 중 키 네이밍 변경(롤링 배포로 구·신 버전이 다른 키를 잡는다), 락 해제와 커밋의 순서 역전(락이 트랜잭션 안쪽에 있으면 락이 먼저 풀리고 커밋이 나중이라 그 틈에 두 번째 요청이 exists()에서 false를 받는다). 이 다섯은 잘 짜면 확률을 낮출 수 있다.

② 락을 아예 거치지 않는 진입 경로 — "배·수·마": 배치 잡·스케줄러(별도 모듈이라 락 획득 코드를 지나가지 않는다), 운영자의 수동 SQL(장애 대응·CS 요청으로 콘솔에서 직접 INSERT), 데이터 마이그레이션·백필 스크립트, 그리고 타 팀 백오피스·테스트 시드 데이터. 이쪽은 락 로직을 아무리 잘 짜도 확률이 0이 되지 않는다.

락은 "우리 애플리케이션의 특정 코드 경로"를, 유니크 제약은 "그 테이블에 값을 쓰는 모든 경로"를 지킨다

지키는 범위 자체가 다르므로 하나가 다른 하나를 대체할 수 없다. 덧붙여, upsert(ON CONFLICT)조차 유니크 인덱스가 있어야 동작하므로 제약을 빼면 그 선택지까지 사라진다.

유니크 위반 예외를 try/catch로 잡아 이력을 남기고 정상 응답했는데, 메서드 끝에서 UnexpectedRollbackException이 납니다. 왜죠? 함정힌트: "예외 객체를 잡는 것"과 "트랜잭션 플래그를 끄는 것"은 다른 층위다

예외는 잡혔지만 트랜잭션은 이미 사형 선고를 받은 상태였다. 제약 위반이 나는 순간 하이버네이트가 트랜잭션에 rollback-only 표시를 켜기 때문이다(ExceptionConverterImpl.rollbackIfNecessary — NoResultException·NonUniqueResultException·LockTimeoutException·QueryTimeoutException 넷만 예외로 봐준다).

이유는 세션 오염이다. 제약 위반 시점에 하이버네이트 세션의 상태와 DB의 상태가 어긋났고, 쓰기 지연 저장소의 어떤 SQL이 나갔는지·1차 캐시의 어떤 엔티티가 유효한지 보장할 수 없으므로 "이 세션은 버려라"가 유일하게 안전한 선택이다.

그리고 catch는 이 플래그를 지울 수 없다. 잡은 것은 예외 객체이고, rollback-only는 트랜잭션 객체의 상태 플래그라 층위가 다르다. 그래서 catch 안에서 저장한 이력까지 커밋 시점에 통째로 사라진다. 비유하면 — 경보기 소리를 손으로 막았다고 이미 내려온 방화 셔터가 열리지는 않는다.

처방은 둘이다. ① 살아남아야 하는 기록을 REQUIRES_NEW로 별도 트랜잭션(별도 커넥션)에 분리한다. ② 더 근본적으로는 트랜잭션 안에서 잡지 않고 그대로 터뜨린 뒤, 롤백이 끝난 다음 파사드(트랜잭션 없는 계층)에서 잡는다. 기본은 ②이고, ①은 감사 로그처럼 바깥이 실패해도 반드시 남아야 하는 증거에만 쓴다.

덧붙이면 좋은 디테일: 메시지는 경로에 따라 silently가 붙기도(JPA) 안 붙기도(JDBC/MyBatis) 한다. 둘은 같은 사건이므로 진단은 같다 — "안쪽에서 rollback-only가 찍혔고 누군가 예외를 삼켰다"부터 의심한다.

유니크 위반이 나면 재시도를 걸면 되지 않나요? 시니어 변별힌트: 재시도해도 되는 실패와 안 되는 실패를 가르는 기준 하나

안 된다. 유니크 위반은 재시도 대상이 아니다. 여기서 일시적 실패(transient)와 결정적 실패(deterministic)를 구분해야 한다.

일시적 실패 — 재시도가 정답

데드락, 락 타임아웃, 낙관적 락 충돌. 같은 작업을 다시 하면 이번엔 성공할 수 있다.

결정적 실패 — 재시도가 무의미

유니크 위반. 같은 값으로 다시 INSERT하면 100% 다시 실패한다 — 앞선 트랜잭션이 커밋해 그 행은 이미 존재하기 때문이다.

따라서 올바른 처리는 재시도가 아니라 "결과 해석"이다. "이미 존재한다"는 것은 대개 원하던 상태가 이미 달성됐다는 뜻이므로, 요구사항에 따라 성공(멱등)으로 응답하거나 "이미 발급됨"으로 응답한다.

(주의) @Retryable을 DataIntegrityViolationException에 걸어두는 코드가 실제로 존재하는데, rollback-only 문제와 겹치면 "영원히 실패하며 커넥션만 소모하는 루프"가 된다. 재시도 대상 예외는 일시적 실패로 한정해야 한다.

트랜잭션 격리 수준을 SERIALIZABLE로 올리면 유니크 제약 없이 막을 수 있나요? 시니어 변별힌트: "막힌다/안 막힌다"가 아니라 "막았다가 아니라 실패시켰다"로 표현이 갈린다

이론적으로는 막히지만, 실무적으로는 답이 아니다.

먼저 REPEATABLE READ로는 못 막는다. 격리 수준은 "이미 존재하는 행을 어떻게 볼 것인가"를 규정할 뿐, "아직 없는 행을 남이 만드는 것"을 다루지 않는다. 두 트랜잭션은 각자의 스냅샷에서 "없다"를 읽고 둘 다 통과한다.

SERIALIZABLE로 올리면 동작 방식이 달라진다. PostgreSQL은 직렬화 이상(serialization anomaly)을 탐지해 한쪽에 직렬화 실패 예외를 던지고, MySQL(InnoDB)은 일반 SELECT를 잠금 읽기로 승격시켜 두 트랜잭션이 서로의 공유 락 때문에 진행하지 못해 데드락으로 한쪽이 죽는다 — 어느 쪽도 "막았다"기보다 "실패시켰다"에 가깝다.

실무 답이 아닌 이유 셋: ① 격리 수준은 트랜잭션 전체에 걸리므로 이 한 줄을 지키려고 무관한 모든 쿼리의 동시성까지 희생한다. ② 데드락·직렬화 실패는 재시도 로직을 강제하므로 유니크 제약보다 처리가 복잡해진다. ③ 무엇보다 "락을 안 거치는 경로(배·수·마)"는 여전히 안 막힌다 — 격리 수준은 트랜잭션을 쓰는 코드에만 적용되기 때문이다.

한 문장으로 — "SERIALIZABLE은 이 문제를 풀 수 있지만, 유니크 인덱스 하나로 되는 일을 서비스 전체의 동시성을 팔아서 하는 것이라 선택지가 아니다."
예외를 잡았을 때, 여러 유니크 제약 중 어느 것이 깨진 건지 구분할 수 있나요? 가산점힌트: "할 수 있다"로 끝내지 말고, 그 방법이 왜 지저분한지까지 말한다

할 수 있지만 방법이 지저분하다. 하이버네이트의 org.hibernate.exception.ConstraintViolationException에는 getConstraintName()이 있어 위반된 제약 이름을 얻을 수 있다.

catch (DataIntegrityViolationException e) {
    Throwable cause = e.getCause();
    if (cause instanceof org.hibernate.exception.ConstraintViolationException ce) {
        String name = ce.getConstraintName();   // 예: "uk_coupon_issue_user_coupon"
        if ("uk_coupon_issue_user_coupon".equals(name)) return IssueResult.ALREADY_ISSUED;
        if ("uk_coupon_issue_serial".equals(name))      return IssueResult.SERIAL_TAKEN;
    }
    throw e;
}

두 가지가 전제된다. ① 제약에 사람이 읽을 수 있는 이름을 붙여야 한다 — 이름을 안 주면 DB가 자동 생성한 이름이 붙어 코드가 그 이름에 묶인다. ② 결국 문자열 비교라 취약하다 — 제약 이름을 바꾸는 마이그레이션에 분기가 조용히 깨진다.

예외 타입만으로는 구분이 안 된다는 점도 짚으면 좋다. DuplicateKeyException까지 좁혀 잡아도 그것은 "유니크/PK 중복"이라는 사실만 알려줄 뿐 어느 제약인지는 알려주지 않는다. 게다가 그 좁은 타입 자체가 JPA 경로에서는 기본 설정으로 오지 않는다.

그래서 실무에서는 분기가 필요할 만큼 제약이 여러 개라면, 애초에 예외 분기 대신 사전 검사(UX 층)에서 케이스를 나눠 메시지를 만드는 편을 택하는 경우가 많다. 예외 처리는 "뚫린 소수 케이스의 안전한 마무리"에만 쓰는 것이다.

@Table(uniqueConstraints = ...)를 붙였는데 운영 DB엔 제약이 없었습니다. 왜죠? 함정힌트: 이 애노테이션이 언제 쓰이는지 + 제약을 뒤늦게 추가할 때의 현실

이 애노테이션은 DDL 자동 생성에만 쓰이는 메타데이터이기 때문이다. 운영 환경은 보통 spring.jpa.hibernate.ddl-auto=none(또는 validate)이므로 하이버네이트가 테이블을 만들지 않는다. 즉 애노테이션은 문서로만 남고 실제 인덱스는 생기지 않는다.

처방: 실제 제약은 Flyway/Liquibase 같은 마이그레이션 도구로 DDL을 명시해 만든다. 그리고 ddl-auto=validate로 두면 기동 시 엔티티 매핑과 실제 스키마가 어긋나면 실패하게 만들 수 있다 — "선언은 있는데 실물이 없다"를 배포 전에 잡는 안전망이다.

여기에 실무에서 반드시 부딪히는 문제가 하나 더 있다 가산점

이미 중복 데이터가 쌓인 테이블에는 유니크 인덱스를 만들 수 없다 — 마이그레이션이 통째로 실패한다. 그래서 순서가 이렇게 된다: ① 중복 행을 조회해 파악 → ② 비즈니스 규칙에 따라 정리(가장 오래된 것만 남기기 등) → ③ 그 다음에 인덱스 생성. "제약을 지금 추가하면 되지 않나"라는 말이 대형 테이블에서는 며칠짜리 작업이라는 감각까지 보여주면 좋다.

이 동시성 상황을 테스트로 어떻게 고정하나요? 가산점힌트: 가장 흔한 실패 하나를 먼저 말하고, 도구 하나의 이름을 댄다

가장 흔한 실패는 @Transactional 테스트로 재현을 시도하는 것이다. 테스트 메서드에 @Transactional이 붙으면 모든 작업이 한 트랜잭션에 묶여 애초에 동시성이 존재하지 않고, 게다가 테스트가 끝나며 롤백되므로 다른 스레드가 커밋된 데이터를 볼 수도 없다. 동시성 테스트에서는 @Transactional을 떼고 뒷정리를 직접 해야 한다.

@Test
void 동시_요청_중_한_건만_성공한다() throws Exception {
    int threads = 10;
    var ready = new CountDownLatch(threads);   // 전원 준비 완료 대기
    var start = new CountDownLatch(1);         // 동시 출발 신호
    var done  = new CountDownLatch(threads);
    var success = new AtomicInteger();
    var pool = Executors.newFixedThreadPool(threads);

    for (int i = 0; i < threads; i++) {
        pool.submit(() -> {
            ready.countDown();
            try {
                start.await();                 // ← 여기서 전원이 동시에 출발한다
                facade.issue(USER_ID, COUPON_ID);
                success.incrementAndGet();
            } catch (Exception ignored) {
            } finally { done.countDown(); }
        });
    }
    ready.await();
    start.countDown();                         // 출발 신호
    done.await();

    assertThat(success.get()).isEqualTo(1);                                   // 성공은 정확히 1건
    assertThat(repo.countByUserIdAndCouponId(USER_ID, COUPON_ID)).isEqualTo(1); // DB에도 1행
}

CountDownLatch가 핵심이다. 스레드를 그냥 띄우면 먼저 뜬 스레드가 이미 끝난 뒤에 다음이 시작돼 경합이 재현되지 않는다. 전원이 준비될 때까지 붙잡아 뒀다가 동시에 출발시켜야 3절의 시간축이 실제로 만들어진다.

그리고 이 테스트의 진짜 가치는 회귀 방지다. 누군가 "유니크 인덱스가 성능에 부담이니 빼자"거나 "락이 있으니 제약은 없어도 된다"고 판단하는 순간, 이 테스트가 실패해서 막아준다. 주장으로 남겨둔 설계 원칙은 언젠가 지워지고, 테스트로 고정한 원칙만 살아남는다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

"동시 INSERT가 몰리면 커넥션이 고갈된다"고 답했는데, 맞는 답인가요? 함정힌트: 현상은 맞을 수 있다. 그런데 원인을 어디로 짚었는가

현상은 일어날 수 있지만, 흔히 붙이는 이유가 틀렸다. "JPA가 중복 확인을 위해 락을 잡아서"가 아니다 — JPA는 락을 잡지 않는다.

진짜 원인은 DB 쪽에 있다. DB는 유니크 인덱스에 값을 넣기 전에 같은 값이 이미 있는지 인덱스를 확인하는데, 그 값을 만든 트랜잭션이 아직 커밋도 롤백도 안 했다면 결과를 확정할 수 없다(커밋되면 중복, 롤백되면 중복 아님). 그래서 뒤에 온 INSERT는 앞 트랜잭션이 끝날 때까지 대기한다. PostgreSQL은 앞 트랜잭션의 트랜잭션 ID에 걸린 락이 풀릴 때까지, MySQL(InnoDB)은 해당 인덱스 레코드의 락을 기다린다 — 표현은 달라도 "앞이 끝나야 내 운명이 정해진다"는 구조는 같다.

원인이 다르면 처방도 달라진다. "JPA 락을 없애자"가 아니라 "INSERT를 포함한 트랜잭션을 짧게 유지하고, 외부 API 호출을 트랜잭션 밖으로 빼자"가 된다. 같은 이야기가 비관적 락의 진짜 대가는 커넥션 점유(10-optimistic-vs-pessimistic-lock.md)와 정확히 겹친다.

사전 검사를 SELECT ... FOR UPDATE로 바꾸면 틈이 없어지지 않나요? 시니어 변별힌트: 잠글 대상이 무엇인지부터 따진다

기본적으로 안 된다. 존재하지 않는 행에는 잠글 대상이 없기 때문이다. SELECT ... FOR UPDATE는 조회된 행에 락을 거는 것인데, 첫 발급이라면 조회 결과가 0행이라 잠글 것이 없다. 두 스레드 모두 "0행, 락 없음"을 받고 나란히 통과한다 — 3절의 틈이 그대로 남는다.

DB에 따라 "없는 행이 생기는 것"까지 잠그는 장치(인덱스 구간에 거는 락)가 동작해 우연히 막히는 경우가 있지만, 격리 수준과 인덱스 구성에 의존하고 데드락 위험이 함께 따라온다. "우연히 막히는 것"에 정합성을 맡기는 설계라 근거로 삼기 어렵다.

확실히 직렬화하려면 이미 존재하는 다른 행을 잠그는 우회가 필요하다 — 예를 들어 coupon 테이블의 해당 쿠폰 행을 FOR UPDATE로 잠근 뒤 발급 여부를 확인하는 방식이다. 이건 사실상 비관적 락이고, 그 쿠폰의 모든 발급 요청을 한 줄로 세운다(처리량 희생, 커넥션 점유 증가).

그리고 어느 쪽이든 "배·수·마" 경로는 여전히 못 막는다. 결론은 같다 — 이 우회를 쓰더라도 DB 유니크 제약은 남긴다.

REQUIRES_NEW만 붙이면 다 해결되는 것 아닌가요? 함정힌트: 대가가 셋이다. 그중 하나는 "붙였는데 아무 일도 안 일어난다"

해결되지만 공짜가 아니다. 대가가 셋이다.

① 커넥션을 하나 더 쓴다. 바깥 트랜잭션의 커넥션을 붙잡은 채 새 커넥션을 빌리므로 요청당 커넥션 사용량이 2배가 된다. 트래픽이 몰리는 경로에서 남발하면 풀 고갈로 교착 상태가 될 수 있다.

② 같은 클래스 안에서 호출하면 적용되지 않는다. this.logDuplicated(...)는 Spring 프록시를 거치지 않아 @Transactional이 통째로 무시된다(자기 호출 문제). 반드시 다른 빈으로 분리해야 한다. "붙였는데 여전히 롤백된다"의 90%가 이것이다.

③ 바깥이 롤백돼도 안쪽은 남는다. 이게 목적이지만, 목적이 아닌 곳에 붙이면 "주문은 실패했는데 결제 이력만 남는" 정합성 사고가 된다.

그래서 기본 선택은 REQUIRES_NEW가 아니라 "경계 밖에서 잡기"다. 트랜잭션 경계를 단순하게 유지하는 쪽이 유지보수에 유리하고 커넥션도 추가로 쓰지 않는다. REQUIRES_NEW는 감사 로그·부정 사용 탐지 이력·외부 결제사 응답 원문처럼 "롤백돼서는 안 되는 증거"에만 쓴다. 붙이기 전 자문: "이 기록은 바깥이 실패해도 남아야 하는가?"

ON CONFLICT DO NOTHING을 쓰면 예외도 없고 편한데, 왜 기본 선택지가 아닌가요?힌트: 얻는 것 둘, 잃는 것 넷. 그리고 전제 하나

얻는 것은 크다. ① 왕복 1회 · 락 비용 0이고 ② 예외가 아예 발생하지 않아 rollback-only 문제까지 통째로 우회된다.

그런데 네이티브 쿼리는 영속성 컨텍스트를 우회한다. 이건 벌크 연산과 정확히 같은 성질이다(11-bulk-operation-persistence-context.md). 그래서 잃는 것이 넷이다 — ① 같은 트랜잭션에서 방금 넣은 행을 다시 읽으면 1차 캐시본이 반환될 수 있고, ② 엔티티 리스너·감사(@CreatedDate)가 동작하지 않고, ③ @Version 증가가 일어나지 않으며, ④ SQL이 DB 벤더에 묶인다(PostgreSQL과 MySQL 구문이 다르고, 영향 행 수의 의미까지 다르다).

그래서 upsert는 "엔티티 생명주기가 단순한 관계 테이블"에 가장 잘 맞는다 — 쿠폰 발급 이력, 좋아요, 팔로우, 조회 기록처럼 "있으면 그만, 없으면 만든다"가 전부인 행이다.

그리고 전제가 하나 있다 — PostgreSQL의 ON CONFLICT (user_id, coupon_id)는 그 컬럼 조합에 유니크 인덱스가 실제로 있어야만 동작한다. 즉 upsert조차 유니크 제약을 전제로 성립한다. (MySQL의 INSERT IGNORE는 중복 외에 데이터 잘림·타입 변환 실패까지 조용히 무시하므로 ON DUPLICATE KEY UPDATE 쪽이 안전하다.)

Soft delete를 쓰는 테이블인데 "탈퇴 후 재가입이 안 된다"는 문의가 옵니다. 가산점힌트: 원인 하나, 우회 하나, 그리고 우회에 따라오는 함정 하나

원인: 탈퇴를 deleted_at 표시로만 처리하면 삭제된 행이 유니크 값을 계속 점유한다. 그 이메일로 다시 가입하려 하면 DB가 정상적으로 막는다 — 제약은 제 일을 하고 있고, 요구사항과 스키마가 어긋난 것이다.

흔한 우회: 유니크 키에 삭제 시각이나 삭제 시퀀스를 포함시켜 UNIQUE (email, deleted_seq) 같은 형태로 만든다. 살아 있는 행은 deleted_seq = 0, 삭제된 행은 삭제될 때마다 다른 값을 갖게 해서 살아 있는 행끼리만 유일하도록 만드는 것이다.

여기에 따라오는 함정 — 표준 SQL에서 유니크 인덱스는 NULL을 서로 다른 값으로 취급한다

그래서 UNIQUE (email, deleted_at)처럼 nullable 컬럼을 넣으면 deleted_at이 NULL인 행은 아무리 많아도 중복으로 걸리지 않는다 — 제약을 걸어놨는데 아무것도 막지 않는 상태가 된다. 복합 유니크 키에 nullable 컬럼을 넣을 때 반드시 확인해야 할 사실이다. (자세한 내용은 26-soft-delete-unique-and-associations.md)

한 줄 요약
JPA는 유니크 제약을 검사하지 않는다 — 1차 캐시는 @Id를 키로 하는 Map이라 유니크 컬럼 조합은 관리 대상이 아니고, persist()는 쓰기 지연 저장소에 INSERT를 쌓을 뿐 SELECT도 락도 없으며, 검증은 flush 시점에 전적으로 DB가 한다. 그래서 exists() → save() 사전 검사는 UX용이지 정합성 보장 수단이 아니고(확인과 행동 사이의 틈은 격리 수준을 올려도 사라지지 않는다), 뚫린 한 건에서 나는 예외는 잡아도 트랜잭션을 살리지 못한다(rollback-only 마킹 → 커밋 시 UnexpectedRollbackException, catch 안의 저장까지 소멸 → REQUIRES_NEW 분리 또는 트랜잭션 경계 밖에서 catch). 대응은 충돌 빈도 × 실패 비용으로 고르되 — 드물면 예외 처리, 잦으면 사전 차단, "있으면 무시"면 원자적 upsert(INSERT ... ON CONFLICT DO NOTHING)가 예외 자체를 없앤다 — 어느 쪽을 고르든 DB 복합 유니크 제약은 항상 남긴다. 락은 티·분·페·키·순(TTL 만료·네트워크 분단·노드 페일오버·키 네이밍 변경·락 해제와 커밋의 순서 역전)에서 뚫리고, 무엇보다 배·수·마(배치 잡·운영자 수동 SQL·마이그레이션)처럼 락 코드를 거치지 않는 경로를 전혀 덮지 못하기 때문이다. 그리고 이 원칙은 CountDownLatch로 동시 출발시킨 테스트로 고정하기 전까지는 언젠가 지워질 주장일 뿐이다.
