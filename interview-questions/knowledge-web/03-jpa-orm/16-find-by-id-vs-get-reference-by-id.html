findById vs getReferenceById
축은 "존재 검증을 어디서 하느냐"다

면접 질문: "findById와 getReferenceById의 차이는? 프록시 반환이 유용한 경우는 언제인가요?"

핵심 관전 포인트 — findById는 즉시 SELECT를 날려 실제 엔티티를 가져오고, getReferenceById는 SELECT 없이 id만 든 가짜 객체(프록시)를 돌려준다. 프록시가 이득이 되는 자리는 엔티티의 필드 값이 전혀 필요 없고 연관관계의 외래 키(FK)만 채우면 되는 경우 — 이때 order.setMember(proxy) 후 저장하면 SQL이 SELECT + INSERT에서 INSERT 하나로 줄어든다. 같은 낭비가 숨어 있는 두 번째 자리가 deleteById다. Spring Data의 deleteById는 내부적으로 findById로 한 번 읽고 지우므로 SELECT + DELETE가 나가는데, delete(getReferenceById(id))로 바꾸면 DELETE 한 문장이 된다(단 Hibernate가 이 최적화를 켤 수 있는 조건이 있다). 대가는 하나다 — 실패 지점이 호출 지점에서 멀어진다. 없는 id였다는 사실이 프록시를 실제로 건드리는 순간에야 드러나고, 그 순간이 트랜잭션 안이면 EntityNotFoundException, 영속성 컨텍스트가 닫힌 뒤면 LazyInitializationException이라는 전혀 다른 이름으로 나타난다. 그래서 선택 기준은 성능이 아니라 "존재 검증을 어디서 하느냐" 한 축이다 — 단건 API는 findById로 호출 지점에서 즉시 검증하고, 대량 처리는 IN 절로 존재를 한 번에 검증한 뒤 getReferenceById로 SELECT를 제거한다. 그리고 배치라면 여기서 멈추면 안 된다. SELECT 10만 번을 없애도 INSERT 10만 번이 남고, IDENTITY 전략이면 JDBC 배치가 아예 작동하지 않는다.

출제 의도: "연관관계 설정만 필요한데 SELECT를 날리는 낭비를 프록시로 없앨 수 있는지 — JPA를 '동작하게' 쓰는 수준과 '쿼리를 통제하며' 쓰는 수준을 가르는 디테일이다." 즉 API 두 개의 차이를 묻는 것처럼 보이지만, 실제 채점 지점은 "내가 쓴 코드에서 SQL이 몇 개 나가는지 머릿속에 그림이 있는가"다.

이 페이지가 겨냥하는 약점 세 가지 ① "프록시를 준다"까지만 알고 이득 나는 자리를 못 짚는 것 → 1·2절에서 SQL 개수를 세어 보여주고, 코드에 흔적조차 없는 deleteById의 숨은 SELECT까지 같이 잡는다.
② 성능 이득만 말하고 대가를 저울에 못 올리는 것 → 4·5절에서 예외 이름이 둘로 갈리는 이유와 스택 트레이스가 진짜 원인 줄을 가리키지 않는다는 사실을 실물로 확인한다.
③ 전제가 바뀌었을 때(단건 → 10만 건) 판단을 못 갈아타는 것 → 7·8절에서 IN 절 일괄 검증 + 프록시라는 완성형 패턴과, 그다음 병목(IDENTITY와 JDBC 배치)까지 내려간다.
버전 기준 버전에 의존하는 서술은 Hibernate ORM 6.6 / Spring Data JPA 3.5 / Spring Boot 3.x 기준이다. 내부 동작은 실제 클래스 이름과 함께 적었으니 의심스러우면 소스에서 직접 확인하면 된다.

1. 프록시란 무엇인가 — 두 메서드가 갈리는 지점

먼저 용어부터 세운다. 프록시(proxy)는 "대리인"이라는 뜻으로, 여기서는 Hibernate가 런타임에 만들어 낸 Member의 가짜 자식 클래스 인스턴스다. 겉모습은 Member지만 속은 비어 있고 id와 "나는 아직 안 채워졌다"는 표시만 들고 있다. 그러다 getName() 같은 실제 필드 접근이 처음 일어나는 순간 DB로 SELECT를 날려 자기 속을 채운다. 이것을 프록시 초기화라고 부른다.

비유 — 프록시는 식당의 진동벨이다

벨에는 주문번호 하나만 적혀 있고 음식은 들어 있지 않다. 그런데 번호만 있으면 되는 일(자리 배정, 영수증에 주문번호 적기)은 카운터에 가지 않고도 처리된다 — 이게 FK만 채우면 되는 자리다. 음식이 필요해지는 순간에야 카운터로 간다 — 이게 프록시 초기화(SELECT)다.

번호만 필요 → 카운터에 안 감=SELECT 0회 / 음식이 필요 → 카운터로 감=SELECT 1회

그리고 이 비유는 두 가지 사고까지 그대로 설명한다. 없는 번호의 벨을 들고 카운터에 가면 "그런 주문 없는데요"를 그제야 듣고(EntityNotFoundException), 가게 문이 닫힌 뒤에 가면 물어볼 창구조차 없다(LazyInitializationException). 벨을 받은 순간이 아니라 카운터에 간 순간에 문제가 드러난다는 것이 프록시의 성질 전부다.

이 성질 위에서 두 메서드가 갈린다.

findById(id)getReferenceById(id)
반환Optional<T> — 실제 엔티티T — id만 채워진 프록시
호출 즉시 SELECT난다안 난다
없는 id일 때Optional.empty() — 호출 지점에서 즉시 알 수 있다아무 일도 안 일어난다. 나중에 프록시를 건드릴 때 터진다
밑바탕EntityManager.find()EntityManager.getReference()

프록시가 절대 초기화를 일으키지 않는 유일한 호출 — getId()

id는 프록시를 만들 때 이미 알고 있던 값이라 DB에 물어볼 필요가 없다. 초기화를 일으키는 것은 id 이외의 필드에 접근할 때다. 프록시를 쓰는 이유가 정확히 여기에 있다.

order.getMember().getId()만 쓰는 DTO 변환은 회원 테이블을 전혀 읽지 않는다
뒤집으면 — DTO에 memberName 한 줄을 추가하는 순간 조용히 N+1이 시작된다. "필드 하나 추가"가 성능 변경인 지점이다.

2. SQL이 줄어드는 두 자리 — createOrder와 deleteById

프록시가 이득이 되는 자리는 딱 하나의 조건으로 정리된다 — 엔티티의 필드 값이 전혀 필요 없고, id만 있으면 되는 작업. 실무에서 그런 자리가 정확히 두 곳이다.

2-1. 자리 ① — 연관관계 FK만 채우는 저장

before 이름도 등급도 안 쓰는데 회원 한 줄을 통째로 읽는다
@Transactional
public Long createOrder(Long memberId, int amount) {
    Member member = memberRepository.findById(memberId)   SELECT 발생
            .orElseThrow(MemberNotFoundException::new);
    Order order = new Order(member, amount);
    // member는 FK 값(id)으로만 쓰인다
    return orderRepository.save(order).getId();
}
-- 나가는 SQL 2개
select m.id, m.name, m.email, m.grade, m.created_at
  from member m where m.id = ?
insert into orders (member_id, amount) values (?, ?)
after FK만 필요하므로 "id를 든 껍데기"만 받아 연결한다
@Transactional
public Long createOrder(Long memberId, int amount) {
    Member member = memberRepository
            .getReferenceById(memberId);   SELECT 없음
    Order order = new Order(member, amount);

    return orderRepository.save(order).getId();
}
-- 나가는 SQL 1개
insert into orders (member_id, amount) values (?, ?)
대가는 이미 여기서 시작된다 getReferenceById(999L)에서 999번이 DB에 없어도 그 줄에서는 아무 일도 일어나지 않는다. 프록시를 초기화하지 않고 FK로만 쓰면 예외조차 안 난다. DB에 FK 제약이 있으면 flush 시점에 DataIntegrityViolationException으로 잡히지만, FK 제약이 없는 테이블이면 존재하지 않는 회원을 가리키는 주문이 조용히 저장된다. 이게 최악이다 — 며칠 뒤 조인 결과가 비어 있는 것으로 발견된다.

2-2. 자리 ② — deleteById의 숨은 SELECT

Spring Data JPA의 구현체(SimpleJpaRepository)는 이렇게 생겼다. 여기에 findById가 들어 있다.

Spring Data JPA SimpleJpaRepository — 코드에 흔적이 없던 SELECT의 정체
@Transactional
public void deleteById(ID id) {
    Assert.notNull(id, ID_MUST_NOT_BE_NULL);
    findById(id).ifPresent(this::delete);   여기서 SELECT가 한 번 나간다
}
before 코드는 한 줄인데 쿼리는 두 개다
@Transactional
public void cancel(Long orderId) {
    orderRepository.deleteById(orderId);
}
select o.id, o.member_id, o.amount, o.status, o.created_at
  from orders o where o.id = ?
delete from orders where id = ?
after 프록시로 지운다. 지우는 데 필요한 것은 id뿐이다
@Transactional
public void cancel(Long orderId) {
    orderRepository.delete(
        orderRepository.getReferenceById(orderId));
}
delete from orders where id = ?

왜 SELECT가 사라지는가는 두 단계로 갈린다. 두 층이 모두 통과해야 SELECT가 실제로 없어진다.

1
Spring Data 쪽 — delete(T entity)는 준영속 엔티티를 받았을 경우를 대비해 find로 존재를 확인한 뒤 merge하는 경로를 갖고 있다. 그런데 getReferenceById가 만든 프록시는 이미 영속성 컨텍스트에 등록된 상태이므로 contains가 true고, 아래쪽의 추가 SELECT를 타지 않는다.
Spring Data JPA SimpleJpaRepository.delete (요지)
if (entityManager.contains(entity)) {
    entityManager.remove(entity);   프록시는 이미 영속 상태라 여기로 빠진다
    return;
}
Class<?> type = ProxyUtils.getUserClass(entity);
// 준영속 엔티티였다면 아래에서 find 로 존재를 확인한 뒤 merge → remove
T existing = (T) entityManager.find(type, entityInformation.getId(entity));   추가 SELECT
if (existing != null) {
    entityManager.remove(entityManager.merge(entity));
}
2
Hibernate 쪽 — Hibernate에는 "초기화되지 않은 프록시를 로딩 없이 바로 지우는" 최적화 경로가 실제로 구현되어 있다(DefaultDeleteEventListener.optimizeUnloadedDelete). 이 경로를 타면 프록시를 초기화하지 않고 EntityDeleteAction만 큐에 등록한다. 다만 이 경로는 항상 켜지지 않는다 — 다음 절이 그 얘기다.

3. 그 최적화가 조용히 꺼지는 조건 — 그리고 딸려오는 동작 변경

항상 되는 게 아니다. Hibernate는 canBeDeletedWithoutLoading()이 참일 때만 로딩 없이 지운다. 이 메서드는 아래 조건을 전부 확인하고, 하나라도 걸리면 프록시를 초기화하고(= SELECT를 날리고) 평소 경로로 지운다.

3-1. 최적화가 꺼지는 여덟 가지 조건

조건 (이걸 만족해야 최적화가 켜진다)실무에서 언제 걸리나부류
세션에 커스텀 Interceptor가 없을 것직접 등록한 Interceptor가 있을 때엿보는 자
엔티티가 Hibernate Lifecycle 인터페이스를 구현하지 않을 것레거시 코드에서 드물게엿보는 자
@PreRemove / @PostRemove 콜백이 없을 것콜백에 엔티티를 넘겨야 하니 로딩이 필요하다엿보는 자
PRE_DELETE / POST_DELETE 이벤트 리스너가 없을 것실무에서 가장 자주 걸린다 — 아래 참고엿보는 자
엔티티에 상속 서브클래스가 없을 것@Inheritance 매핑이 걸려 있으면 탈락딸린 것
cascade delete 설정이 없을 것자식까지 지워야 하면 부모 상태를 알아야 하므로딸린 것
@NaturalId가 없을 것자연 키를 선언한 엔티티딸린 것
PK를 참조하지 않는 컬렉션이 없을 것@JoinColumn이 PK가 아닌 컬럼을 가리킬 때딸린 것

여덟 개를 외우지 말고 두 부류로 접는다 — "엿보는 자 · 딸린 것"

엿보는 자 — 삭제를 가로채는 쪽

Interceptor · Lifecycle · @PreRemove/@PostRemove · PRE/POST_DELETE 리스너. 이들에게 엔티티를 넘겨줘야 하니 껍데기로는 안 된다.

딸린 것 — 이 행에 매달린 쪽

상속 서브클래스 · cascade delete · @NaturalId · PK 아닌 컬렉션. 같이 처리할 것이 있으니 실제 상태를 알아야 한다.

한 줄 규칙 — "엔티티의 속을 봐야 하는 이유가 하나라도 있으면 Hibernate는 읽는다"
가장 자주 걸리는 항목 — Bean Validation과 Envers Hibernate 소스의 hasCustomEventListeners() 위에 달린 주석이 두 가지를 콕 집어 언급한다 — "Bean Validation adds a PRE_DELETE listener and Envers adds a POST_DELETE listener." 즉 spring-boot-starter-validation이 클래스패스에 있는 흔한 프로젝트에서는 이 최적화가 꺼져 있을 수 있다.

그래서 결론은 "외우지 말고 로그로 확인하라"다

delete(getReferenceById(id))로 바꿨으면 p6spy나 spring.jpa.show-sql로 SELECT가 실제로 사라졌는지 눈으로 확인하고, 성능이 중요한 경로라면 쿼리 수를 단정하는 테스트로 고정한다.

// 최적화가 꺼져도 아무도 모르게 되는 것을 막는다 — 기계가 지키게 한다
SQLStatementCountValidator.reset();
orderService.cancel(orderId);
SQLStatementCountValidator.assertSelectCount(0);   여기가 깨지면 최적화가 꺼진 것
SQLStatementCountValidator.assertDeleteCount(1);

최적화 조건이 Hibernate 버전과 프로젝트 설정에 따라 갈리는 종류의 것이라면, 사람의 기억이 아니라 기계가 지켜야 한다.

3-2. 딸려오는 동작 변경 — "없는 id를 조용히 넘긴다"가 사라진다

바꾸기 전에 알아야 할 의미 차이가 하나 있다. 현재 Spring Data의 CrudRepository.deleteById javadoc은 이렇게 적고 있다 — "If the entity is not found in the persistence store it is silently ignored." 코드에서도 findById(id).ifPresent(...)이므로 없는 id를 지우려 하면 아무 일도 없이 끝난다.

deleteById(999L) — 없는 id

조용히 무시된다. 예외 없음. 같은 요청을 두 번 보내도 둘 다 성공이다 — 멱등한 삭제 API가 자연스럽게 성립한다.

delete(getReferenceById(999L)) — 없는 id

예외가 난다. 최적화 경로면 영향 행 0 → ObjectOptimisticLockingFailureException, 초기화 경로면 EntityNotFoundException. 두 번째 호출이 500이 된다.

deleteById → delete(getReferenceById(id)) 치환은 순수한 성능 개선이 아니라 동작 변경이다
"없는 id를 조용히 넘길 것인가, 예외로 만들 것인가" — 멱등한 삭제 API를 쓰고 있었다면 이 치환이 재시도를 깨뜨린다.
버전 주의 — EmptyResultDataAccessException은 옛날 이름이다 이 자리에서 EmptyResultDataAccessException을 기억하는 사람이 많은데, 그건 예전 Spring Data에서 없는 id를 삭제할 때 던지던 예외다. 지금은 위와 같이 조용히 무시하는 쪽으로 바뀌었다. "내가 아는 예외 이름이 지금 이 버전에서도 유효한가"를 확인하는 습관이 필요한 대표적인 지점이고, 이건 바로 다음 절의 주제이기도 하다.

4. 함정 ① 같은 실수인데 예외 이름이 갈린다

6. 함정 ③ 프록시는 getClass()와 ==를 배신한다

//    상대가 프록시면 필드는 비어 있어 null이 나온다
//    (실제 값은 프록시 내부 target 객체에 있다)
// ② hashCode를 Objects.hash(id)로 두면 안 된다
//    Set에 넣은 뒤 저장돼 id가 채워지면 해시가 바뀌어
//    컬렉션에서 영영 못 찾게 된다
after (2) "실질 클래스(effective class)" 비교 — 상속 매핑이 있어 타입 구분이 꼭 필요할 때의 정석 템플릿
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null) return false;
    if (effectiveClass(this) != effectiveClass(o)) return false;
    Long thatId = ((Member) o).getId();
    return id != null && id.equals(thatId);
}

@Override
public int hashCode() {
    return effectiveClass(this).hashCode();
}

private static Class<?> effectiveClass(Object o) {
    return (o instanceof HibernateProxy hp)
            ? hp.getHibernateLazyInitializer().getPersistentClass()  프록시 → 원래 클래스
            : o.getClass();
}
Hibernate.unproxy() · Hibernate.getClass()를 equals 안에서 쓰면 본말전도 둘 다 정답처럼 보이고 실제로 프록시를 벗겨 실제 클래스를 돌려주지만, 둘 다 프록시를 초기화하므로 SELECT가 나갈 수 있다. SELECT를 없애려고 프록시를 쓰는 마당에 equals 안에서 SELECT를 유발하면 이득이 통째로 사라진다. 그래서 equals/hashCode 안에서는 초기화를 일으키지 않는 위 두 방식을 쓴다.

"JPA 엔티티의 equals/hashCode를 어떻게 구현하나요?" — 답의 뼈대 셋

① 무엇으로 비교하나
비즈니스 키가 있으면 그것으로, 없으면 id로.
② 타입은 어떻게 비교하나
getClass() 대신 instanceof 또는 실질 클래스 — 프록시 때문에.
③ hashCode는
id에 의존하지 않는 고정값 — 저장 전후로 해시가 바뀌면 안 되므로.

이 문서에서 본 프록시의 성질이 그 문항의 ②를 그대로 설명한다. 두 문항은 뿌리가 같다.

단건 API → findById

대량 처리 → IN 검증 + getReferenceById

검증은 유지하되 N번의 SELECT를 1번으로 접는다. 프록시의 대가(발현 지점이 멀어짐)를 사전 리포트로 상쇄한다.

같은 말을 다르게 하면 이렇다 — findById를 쓰는 진짜 이유는 "엔티티를 가져오려고"가 아니라 "존재를 확인하려고"인 경우가 대부분이다. 그렇다면 그 확인을 더 싸게 할 방법이 있으면 findById를 버려도 되고, 없으면 버리면 안 된다.

after 배치의 정석 — 존재 검증은 쿼리 1번으로, 연결은 SELECT 0번으로
@Transactional
public ImportResult importOrders(List<OrderCsvRow> rows) {

    // ── 1) 필요한 회원 id를 중복 제거해 모은다
    //       10만 행이라도 실제 회원 수는 수천일 수 있다. 중복 제거가 첫 번째 절약이다.
    Set<Long> memberIds = rows.stream()
                              .map(OrderCsvRow::memberId)
                              .collect(Collectors.toSet());

    // ── 2) 존재 검증을 한 번의 쿼리로 끝낸다 (엔티티를 로딩하지 않고 id 컬럼만)
    Set<Long> existingIds = findExistingMemberIds(memberIds);

    // ── 3) 누락분은 조용히 넘기지 말고 리포트로 남긴다
    Set<Long> missing = new HashSet<>(memberIds);
    missing.removeAll(existingIds);
    if (!missing.isEmpty()) {
        log.warn("존재하지 않는 회원 {}건 — 해당 행을 건너뜁니다. 예시: {}",
                 missing.size(), missing.stream().limit(20).toList());
        // 정책에 따라 셋 중 하나: 전체 실패시키기 / 해당 행만 스킵 / 오류 파일로 분리 적재
    }

    // ── 4) 검증이 끝났으므로 이제 SELECT 없이 프록시로 연결한다
    int saved = 0;
    for (OrderCsvRow row : rows) {
        if (!existingIds.contains(row.memberId())) continue;   // 검증에서 걸러진 행

        Member ref = memberRepository.getReferenceById(row.memberId());  SELECT 없음
        em.persist(new Order(ref, row.amount()));

        if (++saved % 1000 == 0) {   // ── 5) 청크마다 비워 준다
            em.flush();
            em.clear();              // 프록시·엔티티가 무한히 쌓이는 것을 막는다
        }
    }
    return new ImportResult(saved, missing);
}

/** id가 많으면 IN 절도 쪼갠다 (Oracle의 1000개 제한, 파서 부하 회피) */
private Set<Long> findExistingMemberIds(Set<Long> ids) {
    Set<Long> result = new HashSet<>();
    for (List<Long> chunk : Lists.partition(new ArrayList<>(ids), 1000)) {
        result.addAll(memberRepository.findExistingIds(chunk));
    }
    return result;
}

public interface MemberRepository extends JpaRepository<Member, Long> {

7-1. 설계 포인트 네 개

① 왜 findAllById가 아니라 id 프로젝션인가
findAllById(ids)도 쿼리 한 번이지만 엔티티를 통째로 로딩해 1차 캐시에 올린다. 회원이 수천 명이면 findAllById가 실용적이고(이미 로딩됐으므로 이후 getReferenceById가 실제 엔티티를 그대로 돌려준다 — 9절), 수십만이면 id만 뽑는 편이 안전하다. 판단 기준은 "검증 대상 집합의 크기"다.
② 왜 누락분을 예외로 끝내지 않는가
10만 건 중 3건 때문에 전체를 실패시키면 재실행 비용이 크다. 어떤 id가 왜 빠졌는지 리포트로 남기고 나머지를 처리하는 편이 대개 낫다. 이것이 프록시의 대가(발현 지점이 멀어짐)를 실질적으로 상쇄하는 장치다.
③ 검증과 사용 사이에 시간 차가 있다
검증 쿼리 이후 다른 트랜잭션이 회원을 지우면 프록시는 다시 유령이 된다. 최후 방어선은 여전히 DB의 FK 제약이다 — 일괄 검증은 FK 제약을 대체하는 것이 아니라 "장애를 조기에, 읽기 쉬운 형태로 드러내는 층"을 하나 더 얹는 것이다.
④ em.clear() 이후에도 안전한가
안전하다. 컨텍스트를 비우면 기존 프록시는 준영속이 되지만, 다음 루프에서 getReferenceById를 다시 부르면 새 프록시가 만들어진다. 다만 clear() 이전에 만든 프록시를 clear() 이후에 초기화하려 하면 LazyInitializationException이다(4절 표의 세 번째 행과 같은 상황).

8. 그다음 병목 — IDENTITY가 JDBC 배치를 무력화한다

10만 건 CSV 적재에서 getReferenceById로 SELECT 10만 번을 없앴다고 하자. 그래서 얼마나 빨라지는가? 절반은 줄었다. 그러나 남은 10만 번의 INSERT가 여전히 한 건씩 네트워크를 왕복한다. 이게 실제 병목이다.

JDBC에는 여러 문장을 한 번에 보내는 배치(batch) 기능이 있고, Hibernate도 hibernate.jdbc.batch_size로 이를 지원한다. 그런데 PK 생성 전략이 IDENTITY(MySQL의 AUTO_INCREMENT)면 이 기능이 작동하지 않는다.

before 아무리 batch_size를 키워도 INSERT가 한 건씩 나간다
@Entity
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)   배치가 죽는 원인
    private Long id;
}
after 시퀀스로 바꾸면 id를 미리 확보해 INSERT를 모을 수 있다
@Entity
@SequenceGenerator(name = "order_seq", sequenceName = "order_seq",
                   allocationSize = 100)   한 번 호출해 100개 확보
public class Order {
    @Id @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq")
    private Long id;
}
설정 그리고 배치를 실제로 켠다
spring:
  jpa:
    properties:
      hibernate:
        jdbc.batch_size: 100
        order_inserts: true      # 같은 테이블 INSERT끼리 모아야 배치가 먹는다
        order_updates: true
MySQL 사용자를 위한 함정 — 설정을 다 켰는데 안 빨라졌다면 MySQL은 시퀀스를 지원하지 않아 보통 별도 테이블 기반 전략을 쓰게 되고, 그마저도 JDBC URL에 rewriteBatchedStatements=true를 붙이지 않으면 드라이버가 문장을 실제로 합쳐 보내지 않는다. Hibernate 쪽 설정만 보고 "배치를 켰다"고 결론 내리는 것이 가장 흔한 오진이다.

8-1. 그래도 안 되면 ORM 밖으로 내려간다

수십만 건 이상의 순수 적재라면 JPA를 고집할 이유가 없다. 엔티티 인스턴스 10만 개 + 스냅샷 10만 개를 메모리에 만드는 비용 자체가 부담이고, 변경 감지(dirty checking)는 애초에 필요 없는 기능이다.

after 적재 전용 경로는 JdbcTemplate 벌크로 내린다
jdbcTemplate.batchUpdate(
    "insert into orders (member_id, amount) values (?, ?)",
    rows, 1000,
    (ps, row) -> { ps.setLong(1, row.memberId()); ps.setInt(2, row.amount()); }
);

이 선택에는 반드시 붙여야 하는 트레이드오프가 있다

JdbcTemplate으로 내려가면 엔티티 생명주기·검증·감사 로그(@CreatedDate 등)가 전부 우회된다. 그래서 이 선택은 "적재 전용 경로"로 격리해 두는 것이 조건이다.

일반 도메인 로직과 같은 서비스에 섞으면 — 어떤 경로로 들어온 데이터는 감사 컬럼이 채워지고 어떤 경로는 안 채워지는 상태가 되어
나중에 원인 불명의 데이터 불일치로 돌아온다.

배치 최적화 순서 — 측 · 배 · 비 · 내

측정한다→JDBC 배치를 켠다 (IDENTITY 확인)→청크마다 비운다 (flush + clear)→ORM 밖으로 내려간다

순서가 중요하다. 측정 없이 다음 단계로 넘어가지 않는다 — 병목이 DB 왕복이 아니라 CSV 파싱이었을 수도 있다. 그리고 청크마다 비우지 않으면 배치를 켜도 메모리에서 무너진다.

면접에서 이 절을 붙이는 법 "getReferenceById로 SELECT를 없앤다"까지 말한 뒤 "다만 그건 절반이고, 남은 INSERT는 IDENTITY면 배치가 안 걸리므로 시퀀스나 JdbcTemplate으로 내려가야 합니다"를 덧붙이면, 두 문항을 하나로 꿴 사람이라는 신호가 된다.

9. 알아두면 이기는 네 가지 가산점

9-1. 이름이 두 번 바뀐 이유 — getOne → getById → getReferenceById

getOne (deprecated)→ getById (deprecated)→ getReferenceById (현재)

실제로 SimpleJpaRepository에서 getOne과 getById는 둘 다 getReferenceById(id)를 그대로 호출하는 한 줄짜리 메서드다. 이유는 순전히 이름이 거짓말을 했기 때문이다 — getOne/getById는 "하나 가져온다"로 읽히므로 findById와 같은 것인데 Optional만 안 씌운 버전이라고 오해하기 딱 좋았고, 실제로 그렇게 쓰다가 LazyInitializationException을 만나는 사례가 끊이지 않았다. 그래서 이름에 Reference(참조)를 박아 "이건 실제 값이 아니라 참조를 준다"를 API 이름만으로 알 수 있게 만든 것이다.

오래된 코드에서 getOne을 보면 그건 "옛날 findById"가 아니라 지금의 getReferenceById와 정확히 같은 것이다
즉 4·5·6절의 지뢰를 그대로 안고 있다는 뜻이다.

9-2. 이미 1차 캐시에 있으면 getReferenceById는 프록시를 주지 않는다

9-3. @ManyToOne(fetch = LAZY) 필드가 사실 같은 물건이다

getReferenceById를 별개의 기능으로 기억하면 절반만 아는 것이다. @ManyToOne(fetch = LAZY) 연관 필드에 Hibernate가 넣어 두는 것이 정확히 같은 프록시다.

확인 내가 getReferenceById를 부른 적이 없어도 프록시는 이미 도처에 있다
@Transactional(readOnly = true)
public void demo3(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();  // orders만 SELECT
    Member m = order.getMember();      // 프록시. 여기까지 SELECT 없음
    Long id  = m.getId();              // 여전히 SELECT 없음 (FK 값은 orders 행에 이미 있었다)
    String n = m.getName();            여기서 member SELECT 발생 (프록시 초기화)
}
getMember().getId()는 쿼리를 유발하지 않는다
DTO를 만들 때 memberId만 필요하면 fetch join도 필요 없다.
4절의 예외 표가 그대로 적용된다
LAZY 연관을 트랜잭션 밖에서 건드리면 LazyInitializationException.
6절의 equals 함정이 그대로 적용된다
오히려 이쪽이 더 자주 터진다 — 개발자가 getReferenceById를 부른 적 없어도 프록시는 이미 도처에 있다.
N+1의 정체가 바로 이것이다
프록시들이 루프에서 하나씩 초기화되는 현상이 N+1이다.
getReferenceById는 "LAZY 연관에서 자동으로 일어나는 일을 개발자가 직접 손으로 하는 것"이다

9-4. 프록시를 만들 수 없는 엔티티도 있다 — final과 Kotlin

Hibernate는 엔티티 클래스를 상속해서 프록시를 만든다(6절에서 본 Member$HibernateProxy가 그 결과물이다). 그래서 클래스가 final이면 상속할 수 없어 프록시를 못 만들고, getReferenceById가 그냥 SELECT를 날려 실제 엔티티를 반환한다. 메서드가 final인 경우에도 그 메서드는 가로채지 못한다.

"분명 LAZY로 걸었는데 SELECT가 다 나간다"의 원인 후보 Kotlin 클래스는 기본적으로 final이라, kotlin-allopen(kotlin-jpa) 플러그인 없이 JPA 엔티티를 쓰면 지연 로딩이 통째로 무력화된다. 원인이 같다 — 상속할 수 없으면 프록시도 없다.

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 면접에서 말할 순서 다섯 문장

1
"findById는 즉시 SELECT, getReferenceById는 id만 든 프록시입니다."
2
"연관관계 FK만 채우면 되는 경우에 SELECT + INSERT가 INSERT 하나로 줄어듭니다. deleteById도 내부적으로 findById를 하므로 같은 치환이 가능합니다."
3
"대가는 실패 지점이 멀어지는 것입니다. 없는 id는 프록시를 실제로 쓸 때, 트랜잭션 안이면 EntityNotFoundException, 밖이면 LazyInitializationException으로 늦게 드러납니다."
4
"그래서 선택 기준은 존재 검증을 어디서 하느냐입니다. 단건 API는 findById로 호출 지점에서, 대량 처리는 IN 절로 한 번에 검증한 뒤 getReferenceById로 SELECT를 없앱니다."
5
"다만 배치라면 SELECT를 없앤 건 절반이고, 남은 INSERT는 IDENTITY 전략에서 배치가 안 걸리므로 시퀀스나 JdbcTemplate까지 봐야 합니다."

10-2. 3초 인출 카드 — 보기 전에 먼저 답해보기

두 메서드 한 문장 차이?
findById = 즉시 SELECT · 실제 엔티티 · Optional / getReferenceById = 쿼리 0회 · id만 든 프록시. 밑바탕은 find()와 getReference().
프록시가 이득인 자리 둘?
① 연관관계 FK만 채우는 저장(SELECT+INSERT → INSERT) ② deleteById의 숨은 SELECT(SELECT+DELETE → DELETE).
초기화를 안 일으키는 유일한 호출?
getId(). id는 이미 알고 있는 값이다. 그래서 order.getMember().getId()는 쿼리가 없다.
두 예외의 갈림길?
"세션이 먼저" — 트랜잭션 안이면 EntityNotFoundException, 밖이면 LazyInitializationException. 행의 유무는 그다음 질문이다.
가장 무서운 경우는?
초기화 안 함 + FK 제약 없음 → 예외가 아예 안 난다. 유령 FK가 조용히 저장되고 며칠 뒤 빈 조인 결과로 발견된다.
delete 최적화 꺼지는 조건 압축?
엿보는 자 · 딸린 것 — 훅(Interceptor·콜백·이벤트 리스너)이 있거나, 딸린 것(상속·cascade·@NaturalId·컬렉션)이 있으면 읽고 지운다.
deleteById 치환의 숨은 비용?
성능 개선이 아니라 동작 변경. "없으면 조용히 무시"가 예외로 바뀐다 → 멱등한 삭제 API의 두 번째 호출이 500이 된다.
엔티티 equals 3원칙?
① 비즈니스 키 없으면 id ② getClass() 대신 instanceof·실질 클래스 ③ hashCode는 id에 의존하지 않는 고정값.
선택 기준 한 축?
성능이 아니라 "존재 검증을 어디서 하느냐". 단건 = findById(호출 지점), 대량 = IN 일괄 검증 + getReferenceById.
배치 최적화 순서?
측·배·비·내 — 측정 → JDBC 배치(IDENTITY면 무력) → 청크마다 비움 → ORM 밖으로 내려감.
getOne·getById는?
둘 다 deprecated이고 지금의 getReferenceById와 정확히 같은 것. 이름이 거짓말을 해서 Reference를 박아 넣었다.
이미 1차 캐시에 있으면?
getReferenceById가 프록시가 아니라 실제 엔티티를 준다. 반대 순서면 findById가 프록시를 준다(동일성 보장).

10-3. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

createOrder에서 findById → getReferenceById로 바꾸면 SQL이 어떻게 달라지나요? 필수힌트: 개수만 말하지 말고 "왜 SELECT가 필요 없는지"를 붙인다

SELECT + INSERT 두 개에서 INSERT 한 개로 줄어든다.

이유는 INSERT가 필요로 하는 것이 member_id 컬럼 값 하나뿐이기 때문이다. 그 값은 프록시가 이미 들고 있다(프록시를 만들 때 넘긴 id가 그것이다). 그래서 Hibernate는 프록시를 초기화할 이유가 없고, 회원 테이블을 읽지 않는다.

여기에 조건을 붙일 수 있으면 답이 완성된다 — 이 이득은 "엔티티의 필드 값을 전혀 읽지 않는다"가 확실할 때만 성립한다. 나중에 member.getGrade()로 할인율을 계산하는 코드가 한 줄 추가되는 순간 SELECT는 그대로 돌아오고, 대신 실패 지점만 멀어진 상태가 남는다.

getReferenceById(999L)인데 999번이 DB에 없으면 어떻게 되나요? 예외가 난다면 언제·어디서 나나요? 필수힌트: "예외가 난다"로 시작하면 절반은 틀린다. 경우가 셋이다

그 줄에서는 아무 일도 일어나지 않는다. getReferenceById는 DB에 물어보지 않으므로 행이 있는지조차 모른다. 이후 무엇을 하느냐에 따라 셋으로 갈린다.

① 트랜잭션 안에서 초기화

EntityNotFoundException — SELECT는 나갔는데 행이 비었다. 스택은 getName()을 부른 자리를 가리키고 진짜 원인 줄은 없다.

② 트랜잭션 밖에서 초기화

LazyInitializationException — 물어볼 창구가 없다. 행이 있어도 난다. 원인은 "행"이 아니라 "세션"이다.

③ 초기화하지 않고 FK로만 사용 — 여기가 진짜 함정

FK 제약이 있으면 flush 시점에 DataIntegrityViolationException으로 잡히지만, FK 제약이 없는 테이블이면 아무 예외도 나지 않고 유령 FK가 저장된다. 며칠 뒤 조인 결과가 비어 있는 것으로 발견된다.

한 줄로 정리하면 — "없는 id였다"는 사실이 프록시를 실제로 건드리는 순간까지 미뤄지고, 안 건드리면 영영 드러나지 않는다."

프록시에서 getId()를 부르면 SELECT가 나가나요? 필수힌트: 답은 짧다. 대신 "그래서 실무에서 뭐가 달라지는지"를 붙인다

안 나간다. id는 프록시를 만들 때 이미 알고 있던 값이라 DB에 물어볼 필요가 없다. 초기화를 일으키는 것은 id 이외의 필드에 접근할 때다.

이 성질이 실무에서 갖는 의미가 크다. order.getMember().getId()만 쓰는 DTO 변환은 회원 테이블을 전혀 읽지 않는다. 즉 memberId만 필요한 응답에는 fetch join도 필요 없다.

반대로 말하면 — DTO에 memberName 하나를 추가하는 순간 조용히 N+1이 시작된다. 코드 변경량은 한 줄인데 쿼리는 N배가 된다. "필드 하나 추가"가 성능 변경인 지점을 알아보는 것이 이 질문의 노림수다.

그럼 항상 getReferenceById를 쓰면 되지 않나요? 어차피 필요하면 알아서 SELECT하는데. 함정힌트: "결국 초기화할 거라면"으로 시작한다. 나빠지는 경우가 셋 있다

결국 초기화할 거라면 이득이 0이고 위험만 남는다. 프록시를 채우는 SELECT나 findById의 SELECT나 같은 쿼리 한 번이다. 오히려 나빠지는 경우가 셋이다.

① 여러 건이면 N+1이 된다. findAllById로 10건을 한 번에 읽는 대신 프록시 10개를 각각 초기화하면 SELECT가 10번 나간다. 프록시 초기화에는 IN 절로 묶는 기능이 기본으로 붙어 있지 않다(@BatchSize나 default_batch_fetch_size를 켜야 한다).

② 실패가 늦게, 엉뚱한 자리에서 드러난다. findById는 없는 id를 그 줄에서 알려 준다.

③ 코드를 읽는 사람이 SQL을 예측할 수 없게 된다. getReferenceById가 곳곳에 뿌려져 있으면 어느 줄에서 쿼리가 나가는지 추적하기 어려워진다.

원칙 — "기본은 findById, getReferenceById는 '이 객체의 필드를 절대 읽지 않는다'가 확실한 자리에만"
서비스에서 getReferenceById 결과를 컨트롤러로 넘기면 무슨 일이 나나요? 필수힌트: "예외가 난다"가 아니다. OSIV 설정에 따라 갈리고, 켜져 있을 때가 더 위험하다

OSIV 설정에 따라 동작이 갈린다. Spring Boot 기본값(spring.jpa.open-in-view=true)에서는 트랜잭션이 끝난 뒤에도 EntityManager가 응답 완료까지 열려 있으므로 컨트롤러에서 초기화가 되고 코드가 잘 돌아간다.

문제는 그게 "잘 돌아가는 게 아니라 문제가 숨은 것"이라는 점이다 — 커넥션을 뷰 렌더링까지 붙잡고, 나중에 OSIV를 끄면 그동안 쌓인 모든 지뢰가 LazyInitializationException으로 한꺼번에 터진다. 그것도 애플리케이션 코드가 스택에 한 줄도 없는 직렬화 단계에서 터지므로 진단이 특히 어렵고, 응답이 이미 커밋된 뒤라면 클라이언트는 200에 잘린 JSON을 받는다.

그래서 처방은 예외를 잡는 것이 아니라 경계를 세우는 것이다. 프록시는 트랜잭션 안에서 소비하고, 밖으로 나가는 것은 DTO뿐으로 규칙을 정하고, open-in-view=false 프로파일로 도는 통합 테스트를 하나 붙여 기계가 이 규칙을 지키게 한다.

deleteById도 SELECT가 나간다는데 왜 그런가요? 없앨 수 있나요? 가산점힌트: 구현체 한 줄을 인용할 수 있으면 확실해진다

Spring Data의 SimpleJpaRepository.deleteById가 내부적으로 findById(id).ifPresent(this::delete)이기 때문이다. 즉 읽고 나서 지운다. 그래서 코드는 한 줄인데 SQL은 SELECT + DELETE 두 개다.

delete(getReferenceById(id))로 바꾸면 DELETE 한 문장이 될 수 있다. 두 층이 모두 통과해야 한다 — ① Spring Data: 프록시는 이미 영속 상태라 entityManager.contains()가 true고 준영속용 find 경로를 타지 않는다. ② Hibernate: DefaultDeleteEventListener.optimizeUnloadedDelete가 초기화되지 않은 프록시를 로딩 없이 삭제한다.

여기서 멈추지 말고 두 가지를 덧붙여야 한다 — 이 최적화는 조건부로 꺼지고(다음 질문), 없는 id에 대한 동작이 달라진다(그다음 질문).

delete(getReferenceById(id))로 바꿨는데 로그를 보니 SELECT가 그대로 나갑니다. 왜 그럴까요? 함정힌트: 여덟 개를 외우려 하지 말고 두 부류로 접는다

Hibernate는 canBeDeletedWithoutLoading()이 참일 때만 로딩 없이 지운다. 조건을 하나라도 어기면 조용히 프록시를 초기화하고(= SELECT를 날리고) 평소 경로로 지운다.

커스텀 Interceptor · Lifecycle 구현 · @PreRemove/@PostRemove · PRE/POST_DELETE 이벤트 리스너. 이들에게 엔티티를 넘겨야 하니 껍데기로는 안 된다.

딸린 것 — 이 행에 매달린 쪽

상속 서브클래스 · cascade delete · @NaturalId · PK를 참조하지 않는 컬렉션. 같이 처리할 것이 있으니 실제 상태를 알아야 한다.

실무에서 가장 자주 걸리는 것이 이벤트 리스너다. Hibernate 소스 주석이 두 가지를 콕 집는다 — "Bean Validation adds a PRE_DELETE listener and Envers adds a POST_DELETE listener." 즉 spring-boot-starter-validation이 클래스패스에 있는 흔한 프로젝트에서는 이 최적화가 꺼져 있을 수 있다.

그래서 결론은 "외우지 말고 확인하라"다. p6spy나 show-sql로 눈으로 확인하고, 중요한 경로면 SQLStatementCountValidator.assertSelectCount(0)으로 기계가 지키게 한다. 버전·설정에 따라 갈리는 종류의 지식은 사람의 기억에 맡기지 않는다.

deleteById를 delete(getReferenceById(id))로 바꾸면, 없는 id일 때 동작도 같나요? 함정힌트: 이 치환은 순수한 성능 개선이 아니다

같지 않다. 이건 동작 변경이다. CrudRepository.deleteById의 javadoc은 "If the entity is not found in the persistence store it is silently ignored."라고 적고 있고, 구현도 findById(id).ifPresent(...)이므로 없는 id는 조용히 무시된다.

반면 delete(getReferenceById(id))는 예외가 난다. 최적화 경로를 타서 DELETE가 나갔는데 영향 받은 행이 0개면 Hibernate는 "누가 먼저 지웠다"고 판단해 stale state 계열 예외를 올리고 Spring이 ObjectOptimisticLockingFailureException으로 번역한다. 최적화가 꺼져 프록시가 초기화되는 경로였다면 EntityNotFoundException이다.

멱등한 삭제 API(같은 요청을 두 번 보내도 200)를 쓰고 있었다면 이 치환이 두 번째 호출을 500으로 바꾼다

참고로 EmptyResultDataAccessException은 옛날 이름이다 — 예전 Spring Data가 없는 id 삭제 시 던지던 예외이고, 지금은 조용히 무시하는 쪽으로 바뀌었다. "내가 아는 예외 이름이 이 버전에서도 유효한가"를 확인하는 습관이 필요한 대표적 지점이다.

그냥 existsById로 존재만 확인하고 getReferenceById를 쓰면 되지 않나요?힌트: 단건과 대량에서 답이 다르다. 왕복 횟수를 세어 본다

단건에서는 실익이 거의 없다. existsById도 DB 왕복 한 번이므로 findById와 쿼리 개수가 같다. 전송되는 컬럼 수가 줄어드는 정도의 차이인데, 그걸 얻자고 "검증한 객체"가 아니라 "다른 객체(프록시)"를 쓰는 구조를 만들면 코드만 한 겹 늘어난다. 단건이면 그냥 findById + orElseThrow가 가장 짧고 정확하다.

대량에서는 방향은 맞지만 방법이 틀렸다. 루프 안에서 existsById를 부르면 결국 SELECT가 N번이라 findById 루프와 왕복 횟수가 같다. 그래서 정답은 "건별 확인"이 아니라 "IN 절 한 방 확인"이다 — select m.id from Member m where m.id in :ids로 N번을 1번으로 접는다.

그리고 어느 쪽이든 남는 한계가 하나 있다 — 확인과 사용 사이에 시간 차가 있다는 것. 검증 이후 다른 트랜잭션이 그 행을 지우면 프록시는 다시 유령이 된다. 그래서 DB의 FK 제약은 계속 최후 방어선으로 남겨 둔다.

FK 제약이 있으면 DB가 막아 줍니다. "DB를 최후 방어선으로"라는 원칙대로면 getReferenceById가 낫지 않나요? 시니어 변별힌트: "최후 방어선"과 "유일한 방어선"을 가른다. 그리고 이건 양자택일이 아니다

"최후 방어선"과 "유일한 방어선"은 다르다. DB 제약은 데이터가 깨지는 것을 막는 장치이고, 애플리케이션의 조기 검증은 문제를 읽을 수 있는 형태로 드러내는 장치다. 역할이 다르므로 하나가 다른 하나를 대체하지 않는다.

① 진단 가능성. FK 위반은 DataIntegrityViolationException과 벤더별 에러 코드로 올라온다. 여기서 "몇 번 회원이 없었는지"를 알아내려면 SQL 로그와 바인딩 파라미터를 뒤져야 한다. 반면 findById의 orElseThrow는 어떤 id가 왜 없었는지를 도메인 언어로 알려 준다.

② 응답 품질. 클라이언트에게 404 존재하지 않는 회원을 주는 것과 500 데이터 무결성 위반을 주는 것은 다른 API다.

③ FK 제약이 항상 있다는 보장이 없다. 성능이나 샤딩 때문에 FK를 걸지 않는 테이블이 흔하고, 그런 테이블에서는 아무 예외도 나지 않고 유령 데이터가 그대로 저장된다.

결정적으로 이 둘은 양자택일이 아니다 — 일괄 검증으로 조기에 읽기 쉽게 드러내고, FK 제약은 그대로 두어 최후 방어선으로 남긴다
성능(SELECT 제거)과 진단 가능성(조기 검증)을 둘 다 가져가는 방법이 있는데 한쪽을 포기할 이유가 없다.

① 먼저 측정한다. SELECT를 없앤 뒤 실제로 얼마나 줄었는지 확인하지 않고 다음 최적화로 넘어가지 않는다. p6spy로 실제 나가는 문장 수를, Statistics로 쿼리 횟수를 본다. 병목이 DB 왕복이 아니라 CSV 파싱이었을 수도 있다.

③ 영속성 컨텍스트를 청크마다 비운다. flush() + clear(). 이걸 안 하면 배치를 켜도 메모리에서 무너진다.

④ 그래도 부족하면 ORM 밖으로 내려간다. 순수 적재에 변경 감지는 필요 없는 기능인데 스냅샷 비용은 그대로 낸다. JdbcTemplate.batchUpdate, 물량이 정말 크면 DB의 벌크 로더(LOAD DATA INFILE, COPY)까지 간다.

마지막에 트레이드오프를 명시한다 — JdbcTemplate으로 내려가면 엔티티 생명주기·검증·감사 로그가 전부 우회된다
그래서 "적재 전용 경로"로 격리하는 것이 조건이다. 일반 도메인 로직에 섞으면 경로에 따라 감사 컬럼이 채워지고 안 채워지는 상태가 되어 원인 불명의 불일치로 돌아온다.
엔티티의 equals/hashCode를 구현할 때 프록시 때문에 주의할 점은? 필수힌트: 범인은 IDE가 만들어 준 한 줄이다. 그리고 처방에 함정이 하나 있다

IDE가 생성한 getClass() != o.getClass() 비교가 프록시에서 깨진다. 프록시의 실제 클래스는 Member$HibernateProxy(Hibernate 5.x라면 뒤에 무작위 접미사가 더 붙는다)라 Member.class와 같지 않아서, 같은 행을 가리키는 실제 엔티티와 프록시가 서로 다르다고 판정된다. Set에 중복으로 들어가고 contains가 실패한다.

처방은 instanceof 기반 비교 또는 실질 클래스 비교(HibernateProxy면 getHibernateLazyInitializer().getPersistentClass())다. 여기에 두 가지를 함께 지켜야 한다 — ① 상대 객체의 필드를 직접 읽지 말고 getId()로 읽을 것(프록시의 필드는 비어 있다), ② hashCode는 id에 의존하지 않는 고정값일 것(저장되며 id가 채워지면 해시가 바뀌어 컬렉션에서 못 찾게 된다).

Hibernate.unproxy()·Hibernate.getClass()도 정답처럼 보이지만 프록시를 초기화하므로 equals 안에서 쓰면 의도치 않은 SELECT를 부른다
같은 트랜잭션에서 findById를 먼저 부르고 getReferenceById를 부르면 무엇이 나오나요? 반대 순서는요? 가산점힌트: 두 경우 모두 "같은 인스턴스"가 나온다. 그게 핵심이다

순서 A(findById 먼저) — getReferenceById가 프록시가 아니라 아까 그 실제 엔티티를 그대로 돌려준다. 프록시는 "아직 안 읽은 것을 미루기 위한 장치"인데 이미 읽었으니 미룰 것이 없다. 추가 SELECT도 없다.

순서 B(getReferenceById 먼저) — findById인데 프록시가 나온다. SELECT는 나가지만 반환되는 인스턴스는 앞서 만든 그 프록시(초기화된 상태)다. 버그가 아니라 동일성 보장 때문이다 — JPA는 "같은 트랜잭션에서 같은 id를 조회하면 항상 같은 인스턴스를 준다"를 보장하므로, 앞에서 이미 내준 인스턴스와 다른 것을 줄 수 없다.

실무적 함의 두 개. ① getReferenceById를 썼으니 반드시 프록시일 것이라 가정하고 코드를 짜면 안 된다 — equals 문제가 어떤 실행 경로에서는 재현되고 어떤 경로에서는 안 되는 이유가 이것이다. ② 반대로 검증 단계에서 findAllById로 미리 로딩해 두면 이후 getReferenceById는 자동으로 실제 엔티티를 준다 — 배치에서 회원 수가 적을 때 쓸 만한 성질이다.

getReferenceById를 한 번도 안 썼는데도 프록시 관련 예외가 납니다. 왜죠? 가산점힌트: 프록시는 내가 만들지 않아도 이미 도처에 있다

@ManyToOne(fetch = LAZY) 연관 필드에 Hibernate가 넣어 두는 것이 정확히 같은 프록시이기 때문이다. getReferenceById는 "LAZY 연관에서 자동으로 일어나는 일을 개발자가 직접 손으로 하는 것"일 뿐이다.

그래서 이 문서의 내용이 그대로 전이된다 — order.getMember().getId()는 쿼리를 유발하지 않고, LAZY 연관을 트랜잭션 밖에서 건드리면 LazyInitializationException이며, equals 함정은 오히려 이쪽에서 더 자주 터진다(개발자가 프록시를 만든 기억이 없으니 원인을 떠올리기 더 어렵다).

그리고 N+1의 정체가 바로 이 프록시들이 루프에서 하나씩 초기화되는 현상이다. "프록시"라는 한 개념이 getReferenceById · LAZY · N+1 · LazyInitializationException · equals 함정을 전부 관통한다는 것을 보여주면 개별 지식이 아니라 구조를 아는 사람으로 보인다.

Kotlin으로 엔티티를 짰더니 LAZY로 걸었는데도 SELECT가 다 나갑니다. 가산점힌트: 프록시를 만드는 방법을 떠올린다

Hibernate는 엔티티 클래스를 상속해서 프록시를 만든다. 그런데 Kotlin 클래스는 기본이 final이라 상속할 수 없고, 상속할 수 없으면 프록시도 없다. 그래서 kotlin-allopen(kotlin-jpa) 플러그인 없이 JPA 엔티티를 쓰면 지연 로딩이 통째로 무력화된다.

같은 원리로 Java에서도 엔티티 클래스를 final로 선언하면 프록시를 못 만들어 getReferenceById가 그냥 SELECT를 날려 실제 엔티티를 반환한다. 메서드가 final인 경우에는 그 메서드를 가로채지 못한다.

"분명 LAZY로 걸었는데 SELECT가 다 나간다"의 원인 후보로 한 번은 의심해 볼 지점이다.

SQLStatementCountValidator.assertSelectCount(0);
SQLStatementCountValidator.assertInsertCount(1);

여기에 두 가지를 더 붙이면 좋다 — ① 개발 환경의 SQL 로깅(p6spy 등)으로 평소에 쿼리가 보이게 하고, ② open-in-view=false 프로파일 통합 테스트로 프록시가 트랜잭션 경계를 넘는 코드를 CI에서 잡는다. 규칙을 문서에 적어 두는 것과 테스트로 강제하는 것은 다르다 — 조건이 버전·의존성·매핑에 따라 갈리는 종류라면 더욱 그렇다.

한 줄 요약
findById는 즉시 SELECT로 실제 엔티티를, getReferenceById는 SELECT 없이 id만 든 프록시를 주므로 FK만 채우면 되는 자리에서 SELECT + INSERT를 INSERT 하나로 줄이고 deleteById의 숨은 SELECT도 같은 방식으로 없앨 수 있지만, 그 대가는 "없는 id였다"는 사실이 프록시를 실제로 쓰는 순간까지 미뤄지는 것 — 트랜잭션 안이면 EntityNotFoundException, 밖이면 LazyInitializationException이라는 다른 이름으로 — 이므로 선택의 축은 성능이 아니라 "존재 검증을 어디서 하느냐"이고, 단건 API는 findById로 호출 지점에서 즉시, 대량 처리는 IN 절 일괄 검증 후 getReferenceById로 SELECT를 제거하되 거기서 멈추지 말고 남은 INSERT의 IDENTITY·JDBC 배치 문제까지 내려가야 한다.
