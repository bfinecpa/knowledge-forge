엔티티의 equals/hashCode
id는 저장돼야 생기고, 클래스는 프록시에 가려진다

면접 질문: "JPA 엔티티의 equals/hashCode는 어떻게 구현해야 하나요? 프록시와 id 생성 시점 문제는?"

핵심 관전 포인트 — Set에 넣은 엔티티가 save() 후 사라지는 이유는 hashCode가 id로 만들어졌고 그 id가 저장 시점에 null → 1로 바뀌기 때문이다. HashSet은 넣을 때 계산한 해시로 버킷(칸)을 정하고 그 해시를 노드에 적어 둔다. 그래서 해시가 바뀌면 contains()는 엉뚱한 칸을 뒤지고 equals까지 가보지도 못한 채 false를 돌려준다. 여기에 JPA 고유의 두 번째 함정이 겹친다 — 지연 로딩이 만든 프록시는 Member가 아니라 Member$HibernateProxy라서 IDE가 생성해 주는 getClass() != o.getClass() 비교가 깨지고, 프록시의 필드를 직접 읽으면 비어 있어 null이 나온다. 그래서 정석 구현은 넷이다 — ① getClass()가 아니라 instanceof로 타입 비교 ② 상대의 id는 other.id가 아니라 other.getId()로 ③ id != null && id.equals(...)로 미저장끼리는 절대 같다고 하지 않기 ④ hashCode()는 id와 무관한 상수. hashCode 상수 반환이 이상해 보이지만 규약이 요구하는 것은 "같은 객체는 항상 같은 값" 하나뿐이고, 버킷이 하나가 되는 대가는 엔티티를 수천 개씩 Set에 넣는 일이 거의 없으므로 감수할 만하다. 그리고 진짜 정답은 그 위에 있다 — 엔티티를 Set·Map 키로 쓰지 않는 것, 그리고 엔티티에 Lombok @Data를 붙이지 않는 것이다. 후자는 모든 필드 기반 equals를 만들어 이 사고를 그대로 재현하는 데다, equals 한 번이 지연 로딩 연관을 전부 초기화해 쿼리 폭탄이 된다.
  • 1
    원인은 equals가 아니라 hashCode다 — 그리고 equals는 호출조차 되지 않는다 — HashSet은 넣을 때 계산한 해시를 노드에 박제하고 찾을 때는 키 객체에서 매번 새로 계산한다. id 기반 해시는 save() 시점에 값이 바뀌므로 그 둘이 영구히 어긋나고, 조회는 엉뚱한 칸을 열어 비교 후보 없이 false를 낸다.
  • 2
    JPA는 여기에 변수를 둘 더 밀어 넣는다 — "나중에 생기는 식별자"와 "프록시" — 지연 로딩 프록시는 Member를 상속한 대역이라 instanceof는 통과하지만 getClass() 비교는 깨지고, 필드를 직접 읽으면 null이다. 값은 getId()로만 나오며 식별자 getter는 프록시를 초기화하지 않는다.
  • 3
    그래서 정석은 넷이고, 진짜 정답은 그 위에 있다 — instanceof · other.getId() · id != null && · 상수 hashCode. 다만 최선은 equals가 필요 없는 구조다 — 컬렉션은 List로, Map 키는 id로, 엔티티에 @Data 금지. 기본값은 "오버라이드하지 않는 것"이다.

0. 질문 + 출제 의도

질문: "JPA 엔티티의 equals/hashCode는 어떻게 구현해야 하나요? 프록시와 id 생성 시점 문제는?"

실제로 이어진 꼬리질문 넷

Set에 넣고 save()하면 contains가 false인 이유는? 불변 자연키가 아예 없는 엔티티는 무엇을 기준으로? 그 조건에서 hashCode()는 무엇을 반환해야 규약을 지키나? getClass() != o.getClass()가 깨지는 상황은?

출제 의도: "프록시 클래스 비교, id가 저장 전엔 null인 시점 문제로 Set/Map에서 엔티티가 사라지는 미묘한 버그. 1장의 equals 규약이 JPA라는 구체 환경에서 어떻게 꼬이는지 아는 응용 깊이." 즉 이 문항은 규약을 외웠는지 묻지 않는다. 규약은 안다고 전제하고, 거기에 JPA가 새 변수 둘(프록시 · 나중에 생기는 식별자)을 넣었을 때 규약이 어떻게 무너지는지를 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "id로 비교하면 된다"에서 멈추는 것 → 2·3절에서 버킷에 박제된 해시와 프록시의 네 가지 성질을 그림으로 세워 왜 그 답이 정답인지를 만든다.
② "필드를 final로 하고 새 객체를 만들면 된다" → 4절. 틀린 답이 아니라 대상을 잘못 고른 답이다. 값 객체에는 100% 정답이고 엔티티에는 성립하지 않는다.
③ 상수 hashCode를 "규약 위반"으로 오해하는 것 → 6절. 규약은 "잘 분산된 값"을 요구하지 않는다. 해시는 후보를 좁힐 뿐 판정은 언제나 equals가 한다.
버전 기준하이버네이트 동작 서술은 Hibernate ORM 6.x 기준이다. 프록시 클래스 이름 규칙처럼 5.x와 달라진 부분은 그 자리에서 표시한다.

1. 사고 현장 — "안에 있는데 없다고 하고, 지울 수도 없다"

먼저 사고 코드부터 본다. 이상한 곳이 한 군데도 없어 보이는 것이 이 버그의 성질이다.

before 어디에도 이상한 곳이 없어 보인다
@Entity
public class Member {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @Override public boolean equals(Object o) { /* id 비교 */ }
    @Override public int hashCode() { return Objects.hash(id); }   // 여기가 폭탄이다
}

IDENTITY 전략은 DB의 auto increment 컬럼에 식별자 생성을 맡기는 방식이다. 그래서 new Member(...)로 만든 순간에는 id가 null이고, INSERT가 실제로 실행돼야 값이 생긴다. 이 "나중에 생긴다"가 이 문서 전체의 출발점이다.

Set<Member> members = new HashSet<>();
Member member = new Member("주덕");

members.add(member);           // 아직 저장 전 — id는 null
memberRepository.save(member); // 저장 — DB가 id에 1을 채워 준다

members.contains(member);      // false   분명 그 객체인데 없다고 한다
members.size();                // 1       그런데 크기는 1이다
members.iterator().next() == member;  // true   꺼내 보면 그 객체가 맞다
members.remove(member);        // false   지우지도 못한다

이 버그의 지문(指紋) — "있 · 없 · 못 · 둘"

있

size()는 1, iterator에서 그 객체가 나온다
없

모순처럼 보이는 첫 신호

그래서 메모리에서도 안 빠진다
둘

같은 인스턴스가 한 Set 안에 두 번

네 줄이 서로 모순돼 보이지만 모순이 아니다. HashSet이 물건을 두는 방식과 찾는 방식이 서로 다른 정보를 쓰기 때문이다. 이 넷 중 하나라도 보이면 해시 기반 컬렉션 + 가변 키를 의심한다.

members.add(member);   // true  — 0번 칸이 비어 있으니 "새 원소"로 들어간다
members.size();        // 2     — 같은 객체가 15번 칸과 0번 칸에 하나씩

1-1. 이 버그가 유독 늦게 발견되는 이유

테스트에 안 걸린다
테스트는 보통 save()부터 하고 그 결과를 컬렉션에 담는다. "저장 전에 컬렉션에 넣는" 순서가 되어야만 재현된다.
증상이 원인에서 멀다
"중복 등록이 안 걸러진다", "장바구니 삭제가 안 된다", "캐시 적중률 0%" 같은 엉뚱한 얼굴로 나타난다.
메모리에서 안 빠진다
remove가 실패하므로, 오래 사는 컬렉션(세션·로컬 캐시)이면 지웠다고 믿는 원소가 계속 쌓여 누수가 된다.

2. 원리 — 사물함, 박제된 해시, 그리고 바뀐 번호표

HashSet은 내부적으로 HashMap이고, HashMap은 배열 하나 + 각 칸에 매달린 연결 리스트다. 이 배열의 한 칸을 버킷(bucket)이라 부른다. 원래 "양동이"라는 뜻인데, 같은 번호를 배정받은 원소들을 한 칸에 몰아 담는다는 이미지에서 온 이름이다.

비유 — 번호표가 붙은 사물함물건을 맡길 때 직원이 규칙에 따라 칸 번호를 정해 넣고, 찾을 때도 같은 규칙으로 칸 번호를 다시 계산해서 그 칸만 열어 본다. 사물함 전체를 뒤지지 않기 때문에 빠른 것이고, 그래서 "규칙이 매번 같은 답을 낸다"는 것이 이 자료구조의 생명줄이다.

2-1. 칸 번호를 정하는 규칙

1) h = key.hashCode()                       -- 객체가 스스로 내놓는 정수
2) h = h ^ (h >>> 16)                       -- 상위 비트를 하위로 섞는다(스프레드)
                                               작은 값에서는 결과가 그대로다
3) 버킷 번호 = h & (배열 길이 - 1)           -- 배열 길이가 2의 거듭제곱이라
                                               나머지 연산 대신 비트 AND 로 자른다

기본 배열 길이는 16이므로 & 15, 즉 해시의 하위 4비트만 보고 칸을 고른다. 그리고 결정적인 사실이 하나 더 있다.

이 문항 전체를 여는 열쇠 한 문장

넣을 때의 해시는 노드에 박제되고, 찾을 때의 해시는 키 객체에서 매번 새로 계산된다

HashMap.Node에는 final int hash 필드가 있고, 한 번 적히면 다시 계산하지 않는다. 배열이 커져 원소를 재배치할 때(리사이즈)도 노드에 적힌 그 값을 쓴다. 그래서 그 사이에 객체의 해시가 바뀌면 둘은 영원히 어긋난 채로 남고, 스스로 복구되지 않는다.

2-2. 세 시점으로 나눠 그려 본다

Objects.hash(id)는 내부적으로 31 * 1 + (id == null ? 0 : id.hashCode())를 계산한다. Long.hashCode(1L)은 1이므로 id가 null이면 31, 1이면 32다. 딱 1 차이인데 하위 4비트를 보면 31 = 0b11111, 32 = 0b100000이라 & 15의 결과가 15와 0으로 완전히 갈린다.

2-4. 규약은 그대로다 — JPA가 전제를 깰 뿐

이 문서에서 필요한 규약은 딱 두 줄

① 같으면 같은 해시
a.equals(b)가 true면 a.hashCode() == b.hashCode()여야 한다.
② 항상 같은 값 (여기가 깨졌다)
같은 객체에 대해 hashCode()는 (비교에 쓰는 정보가 안 바뀌는 한) 항상 같은 값을 돌려줘야 한다.

id가 비교에 쓰이는데 그 id가 도중에 바뀌었으니, 엄밀히 말하면 자바 규약을 어긴 것도 아니다 — 규약이 "안 바뀐다"를 전제하는데 JPA가 그 전제를 깨는 것이다.

3. JPA가 밀어 넣는 두 변수 — 프록시의 해부

규약이 무너지는 이유는 JPA가 일반 자바 객체에는 없는 성질을 엔티티에 얹기 때문이다. 새 변수는 둘인데, 그 결과 성질은 셋이 달라진다.

일반 자바 객체JPA 엔티티
식별자처음부터 있다저장돼야 생긴다 (IDENTITY/SEQUENCE)
런타임 타입getClass()가 그 클래스프록시면 Member$HibernateProxy
필드 읽기그냥 읽으면 값이 있다프록시의 필드는 비어 있다 — getter로 읽어야 한다

두 번째와 세 번째는 같은 뿌리다. @ManyToOne(fetch = LAZY) 연관이든 getReferenceById든, JPA는 원본 클래스를 상속한 대역 객체를 만들어 끼워 넣는다. 겉모습은 Member인데 속은 비어 있고, id와 "나는 아직 안 채워졌다"는 표시만 들고 있다.

버전 함정 — 프록시 클래스 이름 규칙이 5.x와 6.x에서 다르다

하이버네이트 6.x는 프록시 클래스 이름을 원본클래스의_정규화된_이름 + "$" + "HibernateProxy"로 짓는다(ByteBuddyProxyHelper의 PROXY_NAMING_SUFFIX). 즉 com.example.Member의 프록시는 언제나 com.example.Member$HibernateProxy다.

5.x에서 보던 Member$HibernateProxy$aB3xK1 같은 난수 접미사 형태가 아니다
이름을 문자열로 판별하던 코드가 5.x에서 넘어왔다면 이 지점에서 깨진다

3-1. getId()가 SELECT 없이 값을 내놓는 근거

프록시의 메서드 호출을 가로채는 BasicLazyInitializer.invoke()는 호출된 메서드가 식별자 getter이고 프록시가 아직 미초기화 상태면, 보관 중인 id를 그대로 돌려주고 끝낸다. 다른 메서드였다면 대상 객체를 로딩해 위임했을 텐데, 식별자만은 프록시가 이미 들고 있으므로 DB에 갈 이유가 없다. 이 사실이 뒤에 나올 최종형 equals의 비용을 0으로 만드는 근거다.

주의할 예외 둘 ① @Id 필드에 대응하는 getter 메서드가 실제로 있어야 한다. 하이버네이트는 필드 접근 매핑이어도 이름 규칙으로 getId()를 찾아 두는데(ReflectHelper.findGetterMethodForFieldAccess), getter 자체가 없으면 이 지름길이 없다.
② hibernate.jpa.compliance.proxy=true로 JPA 프록시 호환 모드를 켜면 식별자 접근에서도 프록시를 초기화한다. 기본값은 꺼짐이다.

4. 엔티티와 값 객체(VO) — "같다"의 기준이 다르다

이번 면접에서 갈린 지점"불변 자연키가 아예 없다면 무엇을 기준으로 하나?"에 대한 답 — "필드를 final로 하고, 변경할 때는 새 객체를 만들면 된다. 그럼 그 필드들로 hashCode를 만들어도 상관없다."
이 답은 틀린 답이 아니라 대상을 잘못 고른 답이다. 값 객체(VO)에는 정확한 처방이고, 엔티티에는 성립하지 않는다.
엔티티(Entity)값 객체(Value Object)
예시Member, Order, PostMoney, Address, Period, Email
"같다"의 기준식별자가 같으면 같다값이 전부 같으면 같다

4-1. 엔티티에 final을 적용하면 무너지는 것 둘

① 도메인 의미가 무너진다

이름을 바꾸려고 새 Member 객체를 만들면 JPA 입장에서 그건 다른 행이다. id가 없는 새 객체를 save()하면 UPDATE가 아니라 INSERT가 나간다. 회원이 개명할 때마다 회원 테이블에 행이 하나씩 늘어난다.

② JPA의 기본 동작이 무너진다

변경 감지는 "스냅샷과 현재 필드 값을 비교해 달라진 것을 UPDATE로 내보낸다"는 메커니즘이라 필드가 바뀌는 것을 전제로 설계됐다. 애초에 JPA는 기본 생성자를 요구하고 리플렉션으로 필드를 채우므로 final 필드로는 매핑 자체가 어렵다.

before 엔티티에 VO의 논리를 적용 — 도메인도 JPA도 무너진다
@Entity
public class Member {
    @Id @GeneratedValue private Long id;
    private final String name;    // 리플렉션으로 못 채운다
    private final String email;

    public Member withName(String newName) {   // 변경 = 새 객체
        return new Member(newName, this.email);
        // 저장하면 UPDATE 가 아니라 INSERT
        // = 개명할 때마다 회원 행이 하나씩 는다
    }
    @Override public int hashCode() {
        return Objects.hash(name, email); // 가변 필드
    }
}
after VO에는 정확히 이 논리가 맞다
@Embeddable
public class Money {
    private BigDecimal amount;    // JPA가 리플렉션으로 채워서
    private String currency;      // 문법적 final 은 못 쓴다.
                              // 대신 "setter 금지" 규율

    protected Money() {}          // JPA 전용 기본 생성자

    public Money plus(Money other) {        // 변경이 아니라 생성
        return new Money(
                this.amount.add(other.amount), this.currency);
    }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money m)) return false;
        return currency.equals(m.currency)
            && amount.compareTo(m.amount) == 0;  equals 아님
        // BigDecimal.equals 는 스케일까지 봐서 1000 != 1000.00
    }
    @Override public int hashCode() {
        // equals가 스케일을 무시하니 hashCode도 지워야 한다
        return Objects.hash(currency,
                            amount.stripTrailingZeros());
    }
}
그래서 VO의 equals/hashCode는 아무 문제가 없다값이 안 변하므로 해시도 안 변하고, @Embeddable은 엔티티가 아니라 지연 로딩 대상이 아니므로 프록시가 만들어지지 않아 타입 비교도 안전하다. "필드를 불변으로 두고 모든 값으로 equals를 만든다"는 처방은 여기서는 100% 정답이다.

5-4. 올바른 최종형

after 함정 넷을 모두 막은 형태
@Entity
@Getter                                     // @Data가 아니라 @Getter만
public class Member {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;                      ① 미저장도 자기 자신과는 같다
        if (!(o instanceof Member other)) return false;  ② 프록시 통과
        return id != null && id.equals(other.getId());   ③ 미저장끼리 오판 차단 ④ getter
    }

    @Override
    public int hashCode() {

①
this == o가 맨 앞에 있어야 하는 이유 — id가 아직 null인 미저장 엔티티도 자기 자신과는 같아야 한다. 세 번째 줄의 id != null 때문에 미저장 엔티티는 모든 비교에서 false가 되는데, 그러면 set.contains(theSameInstance)조차 실패한다. 그것을 이 첫 줄이 막는다.
②
instanceof가 프록시를 통과시킨다 — 하이버네이트 프록시는 Member를 상속하므로 o instanceof Member는 true다. 대칭성 걱정은 9절 꼬리질문에서 따로 다룬다.
③
id != null &&가 미저장끼리의 오판을 막는다 — 저장 전에는 자기 자신을 제외한 모든 비교가 false가 된다. 도메인적으로도 옳다 — 아직 회원가입하지 않은 두 사람이 같은 사람인지 시스템은 알 수 없다.
④
other.getId()로 읽어야 프록시에서도 값이 나온다 — 이 한 글자 차이가 실무에서 가장 자주 터지는 지점이다. 그리고 3-1에서 봤듯 식별자 getter는 프록시를 초기화하지 않으므로 공짜다.

    return (o instanceof HibernateProxy hp)
            ? hp.getHibernateLazyInitializer().getPersistentClass()
            : o.getClass();
}
이 템플릿의 한계를 정확히 알아야 한다getPersistentClass()가 돌려주는 것은 그 프록시가 만들어질 때 선언돼 있던 타입이다. @ManyToOne Member member 연관의 프록시라면 실제 행이 AdminMember여도 Member가 나온다. 초기화 없이 실제 서브클래스를 구분하는 것은 원리적으로 불가능하다 — 어느 서브클래스인지는 DB를 읽어야만 알 수 있는 정보이기 때문이다. 그러니 상속 매핑에서는 타입을 엄밀히 따지기보다 식별자 비교로 충분한지를 먼저 확인하는 편이 낫다. @Inheritance의 세 전략 모두 식별자는 계층 전체에서 유일하므로 보통은 충분하다.

6. 상수 hashCode — 규약이 요구하지 않는 것과, 그 대가

꼬리질문에서 막힌 지점이다. 힌트는 "항상 같은 값을 유지한다만 만족하면 된다"였다. 반직관적으로 들리므로 순서대로 푼다.

규약이 요구하는 것은 두 가지뿐이다

일관성
같은 객체는 항상 같은 값을 돌려줄 것
equals와의 정합
equals가 true인 두 객체는 같은 값을 돌려줄 것
"다른 객체는 다른 값을 돌려줄 것"은 규약이 아니다 — 성능을 위한 권고이고, 안 지켜도 프로그램은 정확하게 동작한다

6-1. 세 가지 다 유효하다 — 다만 하나에는 조건이 붙는다

@Override public int hashCode() { return 31; }                              // 가장 단순 · 가장 안전
@Override public int hashCode() { return getClass().hashCode(); }           // 타입별로 분산
@Override public int hashCode() { return effectiveClass(this).hashCode(); } // 프록시까지 고려
두 번째를 그냥 쓰면 오히려 규약 위반이 된다getClass().hashCode()를 그대로 쓰면 Member와 Member$HibernateProxy가 서로 다른 값을 내놓는다. 그러면 real.equals(proxy)는 true인데 해시는 다른 상태가 되어 규약 ①(같으면 같은 해시)이 깨진다. getClass().hashCode()를 택할 거라면 프록시를 벗기는 처리(effectiveClass)가 반드시 함께 가야 한다. return 31;은 이 문제 자체가 없다는 점에서 실무적으로 가장 안전하다.

6-2. 대가와, 그 대가를 감수하는 근거

O(n)
버킷이 하나 → HashSet이 사실상 연결 리스트
n²/2
원소 n개를 차례로 넣을 때의 비교 횟수
n=100 → 5,000회 · n=1,000 → 50만회
그런데
엔티티를 수천 개씩 Set에 담는 코드가 실무에 거의 없다

엔티티를 담는 컬렉션은 대개 한 주문의 주문상품 몇 개, 한 게시글의 첨부 몇 개 수준이고, 그 규모에서 O(1)과 O(n)의 차이는 측정되지 않는다. 거래의 성격을 정확히 보면 이렇다.

id 기반 해시는 빠르지만 정확성이 깨지고, 상수 해시는 정확하지만 느리다
깨진 정확성은 데이터 유실이라 회복 불가능이고, 느린 정확성은 문제가 될 때 측정해 개선할 수 있다
그래도 규모가 커지는 자리가 하나 있다연관관계를 Set으로 매핑했고 자식이 수천 건인 경우다. 하이버네이트가 그 컬렉션을 로딩할 때 원소를 하나씩 Set에 넣는데, 상수 해시면 전부 한 버킷에 쌓이면서 로딩 자체가 O(n²)이 된다. 그래서 답은 "상수 해시를 포기하자"가 아니라 "그런 컬렉션을 Set으로 매핑하지 말자"(8절)로 간다.

6-3. 프록시 초기화는 "메서드 본문"이 아니라 "호출 지점"에서 갈린다

이것은 상수 반환의 장점이 아니라 한계이고, 소스에 근거가 있다. BasicLazyInitializer.invoke()는 엔티티가 equals를 오버라이드하지 않은 경우에만 hashCode를 System.identityHashCode(proxy)로, equals를 args[0] == proxy로 가로채 초기화 없이 끝낸다. 반대로 오버라이드했다면 두 호출 모두 대상 객체로 위임되고, 그 위임 과정에서 프록시가 초기화된다.

7-1. 근본 해법 — id를 저장 전에 갖는다 가산점

상수 해시가 찜찜한 이유는 결국 id가 저장돼야 생기기 때문이다. 그렇다면 id를 애플리케이션이 직접 만들면 이 문제 전체가 사라진다.

after 생성자에서 id를 만든다 — 저장 전에도 id가 있고, 저장돼도 안 바뀐다
@Entity

얻는 것

  • Set/Map 문제 소멸
  • 저장 전후 일관성, 미저장 객체끼리도 정확한 구분
  • JDBC 배치 INSERT가 열린다 — IDENTITY는 INSERT를 실제로 실행해야 식별자를 알 수 있어 쓰기 지연 자체가 성립하지 않는데, 애플리케이션이 식별자를 만들면 그 제약이 사라진다
  • Lombok @EqualsAndHashCode(onlyExplicitlyIncluded = true)가 이때는 완전한 해답이 된다

포기하는 것

  • 랜덤 UUID는 값이 뒤죽박죽이라 B-Tree 인덱스에서 삽입 위치가 흩어진다 — 페이지 분할이 잦아지고 최근 쓴 페이지가 캐시에 남을 확률도 떨어진다
  • 저장 공간도 bigint(8바이트)보다 크다(16바이트)
  • 그래서 실무에서는 시간순으로 증가하는 형태의 식별자(UUIDv7, TSID 같은 정렬 가능한 ID)를 쓴다
  • 초기 설계에서 결정할 사항 — 운영 중인 테이블을 바꾸는 것은 마이그레이션 비용이 크다

8. 처방과 안전망 — equals가 필요 없는 구조로 간다

지금까지의 모든 함정은 "엔티티를 해시 기반 자료구조에 넣는다"는 전제 위에 있다. 그 전제를 없애면 문제 자체가 사라진다.

8-1. 컬렉션은 List로, Map 키는 id로

before 정확성을 equals/hashCode에 의존하게 된다
@OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
private Set<OrderItem> items = new HashSet<>();

// 엔티티가 Map 키 → 해시 함정을 전부 상속한다
Map<Member, List<Order>> ordersByMember = orders.stream()
        .collect(groupingBy(Order::getMember));
// 게다가 그룹핑 과정에서 프록시를 수신자로 hashCode()가
// 호출되므로 회원마다 SELECT 가 나갈 수 있다 (6-3)
after 특별한 이유가 없으면 List, 키는 id
@OneToMany(mappedBy = "order", cascade = CascadeType.ALL)
private List<OrderItem> items = new ArrayList<>();

// id를 키로 쓰면 equals/hashCode를 신경 쓸 일이 없다
Map<Long, List<Order>> ordersByMemberId = orders.stream()
        .collect(groupingBy(o -> o.getMember().getId()));
// 보너스: getMember()가 프록시를 돌려줘도
// getId()는 초기화를 일으키지 않아 SELECT 가 없다 (3-1)

List는 순서만 유지할 뿐 해시를 쓰지 않으므로, equals/hashCode를 오버라이드하지 않아도 추가·순회·인덱스 접근이 전부 정상이다.

다만 "무조건 List"는 아니다 — 두 가지를 함께 알아야 한다 ① 중복을 막아야 한다면 Set이 아니라 DB의 유니크 제약이 맡아야 한다. 애플리케이션 컬렉션은 동시성 상황에서 중복을 못 막는다 — 두 요청이 동시에 각자의 컬렉션에 넣으면 각자의 Set 안에서는 유일하지만 DB에는 두 행이 들어간다. Set으로 중복을 막고 있다고 믿는 코드는 대개 이미 뚫려 있다.
② @ManyToMany나 조인 테이블 컬렉션에서는 List(bag) 매핑이 "전부 삭제 후 재삽입"으로 동작하는 알려진 문제가 있어 Set이 권장되기도 한다. 그런 자리에서 Set을 쓰기로 했다면 5-4의 equals/hashCode를 반드시 함께 구현해야 한다 — 이 두 선택은 세트다.

8-2. 실무 최대 함정은 Lombok이다 — 생성되는 코드를 펼쳐 본다

equals/hashCode를 손으로 잘못 쓰는 사람보다, Lombok이 대신 잘못 써 주는 경우가 압도적으로 많다. 애노테이션 한 줄이라 리뷰에서 눈에 안 띄고, 붙인 사람도 equals를 만들었다는 자각이 없다.

@Data의 구성 요소 중 @EqualsAndHashCode가 static도 transient도 아닌 모든 인스턴스 필드를 기준으로 두 메서드를 만든다. 그리고 getter가 있으면 필드가 아니라 getter를 호출하도록 생성한다(lombok.equalsAndHashCode.doNotUseGetters 기본값이 false).

delombok 실제로 만들어지는 코드 (읽기 쉽게 정리)
public boolean equals(final Object o) {
    if (o == this) return true;
    if (!(o instanceof Member)) return false;
    final Member other = (Member) o;
    if (!other.canEqual(this)) return false;          (1) 상대에게 되묻는다

    final Object this$id = this.getId();              (2) 필드가 아니라 getter
    final Object other$id = other.getId();
    if (this$id == null ? other$id != null : !this$id.equals(other$id)) return false;
    //  ^^^ (3) 둘 다 null 이면 "같다"로 통과한다

    final Object this$name = this.getName();
    final Object other$name = other.getName();
    if (this$name == null ? other$name != null : !this$name.equals(other$name)) return false;

    final Object this$team = this.getTeam();          (4) LAZY 연관의 getter
    final Object other$team = other.getTeam();
    if (this$team == null ? other$team != null : !this$team.equals(other$team)) return false;
    //                                            ^^^ (5) 연관의 equals — 프록시가 수신자

    final Object this$orders = this.getOrders();      (6) 컬렉션 연관까지
    final Object other$orders = other.getOrders();
    if (this$orders == null ? other$orders != null : !this$orders.equals(other$orders)) return false;
    return true;
}

protected boolean canEqual(final Object other) { return other instanceof Member; }

public int hashCode() {
    final int PRIME = 59;
    int result = 1;
    final Object $id = this.getId();
    result = result * PRIME + ($id == null ? 43 : $id.hashCode());   (7) null 이면 상수 43
    final Object $name = this.getName();
    result = result * PRIME + ($name == null ? 43 : $name.hashCode());
    // team, orders 도 같은 방식으로 섞인다
    return result;
}

getter를 쓰므로 프록시 필드 직접 접근 함정(5-3 ②)은 피해 간다. 이건 Lombok이 잘한 부분이다.
(1)(4)(5)(6)
그 대신 프록시를 초기화하는 경로가 넷이나 열린다. canEqual은 평범한 메서드라 상대가 프록시면 위임을 위해 초기화되고, getTeam()이 돌려준 프록시는 다음 줄에서 수신자로 equals가 불려 초기화되며, getOrders()의 PersistentBag은 equals 한 번에 컬렉션 전체가 로딩된다.
(7)
저장 시점 해시 변동이 그대로 남는다. null이면 43을 섞고 값이 생기면 그 해시를 섞으므로 save() 전후로 hashCode()가 달라진다 — 2절의 사고 그대로.
(3)
미저장 엔티티 두 개가 같다고 판정된다. id가 둘 다 null이면 통과하고 나머지 필드가 우연히 같으면 equals가 true다 — 5-3의 함정 ③.
비교 한 번에 SELECT가 여러 개 — "조회 화면 하나에서 쿼리가 수백 개"의 원인을 추적하다 equals에서 발견하는 유형이 이것이다

toString도 같이 정리해야 한다. 엔티티에 @ToString을 붙이면 양방향 연관을 타고 무한 순환하거나 지연 로딩을 전부 초기화한다. 꼭 필요하면 @ToString.Exclude로 연관을 전부 빼야 한다. 같은 이유로 엔티티를 JSON으로 직렬화하는 것도 금지다.

8-3. 절충안(onlyExplicitlyIncluded)과 그 한계

@Entity @Getter
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
public class Member {
    @Id @GeneratedValue
    @EqualsAndHashCode.Include                     // 이 필드만 사용
    private Long id;

    private String name;
    @ManyToOne(fetch = LAZY) private Team team;    // 비교에서 제외 → 초기화 안 됨
}

막아 주는 것

  • 연관 getter 호출로 인한 지연 로딩 초기화(쿼리 폭탄)
  • 사용자가 수정하는 필드로 인한 해시 변동

여전히 못 막는 것 — 이게 핵심이다

  • id가 null이던 시점과 저장 후의 해시가 다르다. onlyExplicitlyIncluded는 어떤 필드를 쓸지만 정할 뿐 그 필드가 언제 채워지는지는 건드리지 않는다
  • 미저장 엔티티 두 개가 같다고 판정된다((3)의 구조가 그대로)
  • canEqual 호출은 남는다 — 상대가 프록시면 여기서 초기화된다
결론@Data보다는 훨씬 낫지만 정답은 아니다. Lombok으로는 id != null && 조건도, 상수 hashCode도 표현할 수 없다. 그래서 선택지는 셋뿐이다 — 직접 작성(5-4) · 아예 오버라이드하지 않기(7 C) · 식별자를 애플리케이션에서 생성하기(7-1). 세 번째를 택하면 그때는 onlyExplicitlyIncluded가 완전한 해답이 된다.

8-4. 안전망 ① 구조 규칙 — 엔티티에 @Data를 금지한다

이 버그의 특징은 리뷰에서 안 보이고 테스트에서 안 걸린다는 것이다. 그래서 규칙을 코드로 고정한다.

@AnalyzeClasses(packages = "com.example.domain")
class EntityConventionTest {

    @ArchTest
    static final ArchRule 엔티티에는_Data와_EqualsAndHashCode를_붙이지_않는다 =
        noClasses().that().areAnnotatedWith(Entity.class)
            .should().beAnnotatedWith(Data.class)
            .orShould().beAnnotatedWith(EqualsAndHashCode.class)
            .orShould().beAnnotatedWith(ToString.class)
            .because("모든 필드 기반 equals/hashCode/toString은 해시 변동·쿼리 폭탄·무한 순환을 만든다");
}
이 룰의 진짜 가치"지금 잘못된 코드를 잡는 것"이 아니라 "6개월 뒤 새로 들어온 사람이 습관적으로 붙이는 것을 막는 것"이다. @Data는 편해서 반드시 다시 들어온다.

8-5. 안전망 ② 동작 테스트 세 개

@DataJpaTest
class MemberEqualityTest {

    @Test
    void 저장_전에_Set에_넣은_엔티티는_저장_후에도_찾을_수_있다() {   // 2절의 사고
        Set<Member> set = new HashSet<>();
        Member member = new Member("주덕");
        set.add(member);

        memberRepository.save(member);
        em.flush();                             // id가 채워지는 실제 시점을 만든다

        assertThat(set).contains(member);       // 상수 hashCode 덕에 통과
        assertThat(set.remove(member)).isTrue();
    }

    @Test
    void 미저장_엔티티_두_개는_같다고_판정되지_않는다() {            // 5-3 함정 ③
        Set<Member> set = new HashSet<>();
        set.add(new Member("주덕"));
        set.add(new Member("영희"));
        assertThat(set).hasSize(2);             // 하나로 합쳐지면 실패
    }

    @Test
    void 프록시와_실제_엔티티는_같다고_판정된다() {                  // 5-3 함정 ①②
        Long id = memberRepository.save(new Member("주덕")).getId();
        em.flush();

        // 순서가 중요하다. 실제 엔티티를 먼저 확보한 뒤 컨텍스트를 비워야
        // 그다음 getReference 가 진짜 프록시를 돌려준다.
        Member real = memberRepository.findById(id).orElseThrow();
        em.clear();                             // real 은 준영속, 1차 캐시는 비워진다
        Member proxy = em.getReference(Member.class, id);

        assertThat(real.getClass()).isNotEqualTo(proxy.getClass());  // 전제 확인
        assertThat(real).isEqualTo(proxy);       // 인자의 getId()만 부른다 — SELECT 0
        assertThat(proxy).isEqualTo(real);       // 대칭성 확인 — 여기선 초기화 SELECT 1회
    }

세 번째 테스트에서 순서를 뒤집으면 테스트가 무의미해진다em.clear() 직후에 getReference부터 부르면 영속성 컨텍스트에 프록시가 등록되고, 그 뒤의 findById는 DB를 읽어 그 프록시를 초기화한 다음 같은 프록시 인스턴스를 돌려준다. 그러면 real과 proxy가 같은 객체라 equals 구현이 무엇이든 통과한다. 둘을 서로 다른 영속성 컨텍스트 상태에서 얻어야 실제 엔티티와 프록시를 나란히 놓을 수 있다.

@DataJpaTest는 기본적으로 테스트 끝에 롤백하므로 커밋 시점에만 드러나는 문제는 숨는다. 첫 번째 테스트처럼 저장 시점의 id 부여가 관건이면 save() 뒤에 flush()를 명시해 실제 시점을 만들어 줘야 한다. IDENTITY는 save() 안에서 곧바로 INSERT가 나가지만 전략에 따라 시점이 다르므로, flush()를 넣어 두는 편이 안전하다.

8-6. 안전망 ③ equals가 쿼리를 유발하지 않는지 단정한다

쿼리 폭탄은 테스트가 통과하면서도 느려지는 종류라 기능 테스트로는 안 잡힌다. 쿼리 수를 직접 단정한다. 여기서 6-3의 사실이 그대로 설계에 반영돼야 한다 — 수신자를 프록시로 두면 구현이 무엇이든 SELECT가 한 번 나가므로, 단정해야 할 것은 "프록시를 인자로 넘겼을 때 추가 쿼리가 없는가"다.

@Test
void equals_비교는_연관을_초기화하지_않는다() {
    Member real = memberRepository.findById(id).orElseThrow();
    em.clear();
    Member proxy = em.getReference(Member.class, id);   // 미초기화 프록시

    SQLStatementCountValidator.reset();
    real.equals(proxy);        // 수신자가 실제 엔티티 → 인자의 getId()만
    real.hashCode();           // 상수 반환이면 아무 일도 하지 않는다
    SQLStatementCountValidator.assertSelectCount(0);   // 하나라도 나가면 실패

    // 참고: proxy.equals(real) 은 수신자가 프록시라 초기화 SELECT 1회가 정상이다.
    //      이 줄을 위 구간에 넣으면 구현과 무관하게 테스트가 깨진다.
}

이 테스트 하나가 누군가 equals에 name 비교를 슬쩍 추가하거나 @Data를 붙이는 순간 빨간불을 켠다. "문제를 만나면 잘 푸는 것"과 "문제가 오기 전에 잡는 장치를 만드는 것"의 차이가 여기에 있다.

실제로 만났을 때의 진단 순서 5단계

1
지문 확인 — "있·없·못·둘"(1절) 또는 "Set에 넣었는데 개수가 예상보다 적다"(미저장끼리 같다고 판정된 반대 방향 사고). 하나라도 보이면 해시 기반 컬렉션 + 가변 키를 의심한다.
2
키 객체의 equals/hashCode를 확인한다 — 엔티티인가? @Data가 붙어 있는가? hashCode가 id나 가변 필드를 쓰는가?
3
넣은 시점과 찾은 시점 사이에 save()나 setter 호출이 있었는지 본다. 있으면 그게 원인이다.
4
재현 테스트를 먼저 쓴다 — 8-5의 첫 번째 테스트가 그대로 재현 코드다. 고치기 전에 실패하는 테스트를 만들어야 고쳤다는 것을 증명할 수 있고, 그것이 그대로 회귀 방지 장치로 남는다.
5
고친 뒤 안전망을 건다 — ArchUnit 룰(8-4) + 쿼리 수 단정(8-6). 이 버그는 한 번 고쳐도 다음 사람이 @Data를 붙이면 그대로 돌아온다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

save 후 contains가 false인 이유?
넣을 때 해시는 노드에 박제, 찾을 때는 객체에서 새로 계산. 31 → 32로 바뀌어 칸이 15 → 0으로 갈리고, equals는 호출조차 안 된다.
이 버그의 지문?
있·없·못·둘 — 순회하면 있고, contains는 없다 하고, remove를 못 하고, 다시 넣으면 둘이 된다.
정석 구현 네 가지?
인·겟·널·상 — instanceof / other.getId() / id != null && / 상수 hashCode. 여기에 맨 앞 this == o가 세트.
hashCode 규약 두 줄?
① equals가 true면 같은 해시 ② 같은 객체는 항상 같은 값. "다르면 다른 값"은 규약이 아니다 — 성능 권고일 뿐.
왜 상수여도 정확한가?
해시는 후보를 좁힐 뿐이고 판정은 언제나 equals가 한다. 잃는 것은 성능뿐, 정확성은 그대로.
프록시 네 가지 성질?
instanceof true / getClass() 비교 false / getId()는 초기화 없이 값 / 필드 직접 접근은 null.
6.x 프록시 클래스 이름?
타입명$HibernateProxy 고정 접미사. 5.x의 난수 접미사 형태가 아니다 — 이름을 문자열로 판별하던 코드는 여기서 깨진다.
엔티티 vs VO 한 문장?
엔티티는 식별자가 고정되고 내용은 변하는 객체, 값 객체는 값 전체가 곧 정체성이라 변하면 다른 것.
전략 셋과 기본값?
자·아·안 — 자연키 / 아이디+상수 / 안 한다. 기본값은 "안 한다"이고, 그 전에 구조로 요구를 없앨 수 있는지부터 묻는다.
상수 해시가 진짜 위험한 자리?
연관을 Set으로 매핑했고 자식이 수천 건일 때 — 로딩이 O(n²). 답은 "해시를 분산"이 아니라 "Set으로 매핑하지 않기".
SELECT를 가르는 규칙?
수신자가 프록시면 SELECT 1회, 인자면 0회. 본문이 return 31;이어도 마찬가지 — 판단은 본문이 아니라 호출 지점에서 갈린다.
Lombok onlyExplicitlyIncluded가 못 막는 셋?
① 저장 시점 해시 변동 ② 미저장 둘이 같다고 판정 ③ canEqual의 프록시 초기화.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

Set<Member>에 넣은 미저장 엔티티를 save()한 뒤 contains(member)가 false가 된다. 왜인가? 필수힌트: "equals가 잘못돼서"라고 답하면 절반도 못 간다. equals는 호출조차 되지 않는다

hashCode가 id로 만들어졌고, 그 id가 저장 시점에 null에서 1로 바뀌기 때문이다. 핵심은 HashMap의 비대칭에 있다.

넣을 때: 계산한 해시를 노드에 박제↔찾을 때: 키 객체에서 매번 새로 계산

Objects.hash(id)는 id가 null이면 31, 1이면 32를 낸다. & 15를 적용하면 15번 칸과 0번 칸으로 완전히 갈린다. 그래서 0번 칸을 열어보는데 비어 있고, 비교할 후보가 없으니 equals는 단 한 번도 호출되지 않은 채 false가 나온다.

사물함에 물건을 넣어 두고 번호표만 바꿔 든 것 — 물건은 그 칸에 있는데 다른 칸을 연다

그래서 size()는 1이고(개수를 세는 정수 필드), 순회하면 그 객체가 나오며(배열을 0번부터 훑는다), remove()는 실패하고(조회와 같은 경로), 다시 add()하면 성공해 같은 인스턴스가 한 Set에 두 번 들어간다.

hashCode가 항상 같은 값이면 HashSet의 의미가 없지 않나요? 성능 문제 아닌가요? 필수힌트: "맞다"로 시작한 뒤, 감수하는 근거 둘과 예외 하나를 댄다

맞다. 버킷이 하나가 되어 조회가 O(1)에서 O(n)이 된다. 다만 그 대가를 감수하는 근거가 둘이다.

① 규약이 요구하는 것은 "항상 같은 값"이지 "잘 분산된 값"이 아니다. 해시는 후보를 좁히는 용도이고 "같다"의 최종 판정은 언제나 equals가 한다. 그래서 상수 반환은 정확성을 완전히 보장하고 잃는 것은 성능뿐이다. 반대로 id 기반 해시는 성능은 좋지만 저장 시점에 값이 바뀌므로 정확성이 깨진다.

깨진 정확성은 데이터 유실이라 회복 불가능이고, 느린 정확성은 필요하면 개선할 수 있다

② 엔티티를 대량으로 Set에 넣는 코드가 실무에 거의 없다. 한 주문의 주문상품 몇 개, 한 게시글의 첨부 몇 개 수준에서 O(n)은 측정되지 않는다.

단, 예외가 하나 있다 — 연관관계를 Set으로 매핑했고 자식이 수천 건이면 하이버네이트가 컬렉션을 로딩하며 전부 한 버킷에 밀어 넣어 O(n²)이 된다. 그럴 땐 답이 "해시를 분산시키자"가 아니라 "그 컬렉션을 Set으로 매핑하지 말자" 또는 "식별자를 애플리케이션에서 생성하자"다.

id != null 조건 때문에 미저장 엔티티는 자기 자신과도 다르다고 나오지 않나요? 함정힌트: equals의 첫 줄을 보라. 그리고 그것이 왜 첫 줄이어야 하는지

아니다. 맨 앞의 this == o가 잡는다. 그래서 equals의 첫 줄에 그것이 있어야 한다.

정리하면 미저장 엔티티의 판정은 이렇게 된다 — 자기 자신하고만 같고, 다른 모든 객체와는 다르다. 이건 결함이 아니라 의도된 설계다. 아직 식별자가 없다는 것은 "이 객체가 어느 행인지 시스템이 아직 모른다"는 뜻이고, 그 상태에서 두 객체가 같다고 단정할 근거는 없다. 이름이 같다고 같은 회원이라 판정해 버리면 Set에서 한 명이 조용히 사라진다.

상수 해시가 "칸을 고정"하고, this == o가 "그 칸에서 잡아낸다"
두 장치가 세트로 동작해야 2절의 사고가 완전히 해소된다 — 하나만 있으면 안 된다
name·email·phone을 사용자가 전부 바꿀 수 있다면? 변하지 않는 자연 키가 아예 없는 엔티티는 무엇을 기준으로 하나요? 함정힌트: "필드를 final로 하고 변경할 때 새 객체를 만든다"는 답은 틀린 답이 아니라 대상을 잘못 고른 답이다

먼저 "불변 필드 + 새 객체 교체"라는 처방이 어디에 맞는지를 갈라야 한다. 그것은 값 객체(VO)에는 100% 정답이고 엔티티에는 성립하지 않는다.

엔티티에 적용하면 둘이 무너진다. ① 도메인 의미 — 이름을 바꾸려고 새 Member를 만들면 JPA에겐 다른 행이라 UPDATE가 아니라 INSERT가 나가고, 개명할 때마다 회원 행이 늘어난다. ② JPA의 기본 동작 — 변경 감지는 필드가 바뀌는 것을 전제로 스냅샷과 대조하는 메커니즘이고, 애초에 JPA는 기본 생성자 + 리플렉션으로 필드를 채우므로 final 필드로는 매핑 자체가 어렵다.

그래서 답은 "id 기반 + 상수 hashCode"다(5-4). 자연키가 없다는 것은 도메인이 정체성을 주지 않았다는 뜻이고, 그러면 남은 근거는 DB가 준 식별자뿐이다.

엔티티는 식별자가 고정되고 내용은 변하는 객체, 값 객체는 값 전체가 곧 정체성이라 변하면 다른 것

한 걸음 더 나가면 가산점 — "주소·금액·기간처럼 값 자체가 의미의 전부인 것은 엔티티가 아니라 @Embeddable VO로 내리고, 거기서는 말씀하신 그 처방(모든 값 기반 equals)이 정확히 맞습니다"까지 말하면 두 개념을 구분해서 쓴다는 신호가 된다.

equals에서 getClass() 대신 instanceof를 쓰면 대칭성이 깨진다고 배웠는데요? 시니어 변별힌트: 일반론은 맞다. 그 규칙의 목적으로 돌아가면 프록시가 예외인 이유가 보인다

일반론으로는 맞는 지적이고, JPA 프록시에서는 적용되지 않는다. 이 구분이 이 질문의 핵심이다.

instanceof가 위험하다고 하는 이유는 상속으로 상태를 추가한 서브클래스 때문이다. Point와 ColorPoint가 있을 때 point.equals(colorPoint)는 좌표만 보고 true인데 colorPoint.equals(point)는 색까지 보므로 false가 된다 — 대칭성 위반이다.

그런데 하이버네이트 프록시는 "상태를 추가한 서브클래스"가 아니다. 같은 엔티티를 가리키는 대역이고 논리적으로는 Member 그 자체다. 도메인 필드를 새로 추가하지 않고(추가하는 것은 초기화기를 담을 내부 필드뿐), 개발자가 설계한 상속 계층도 아니며 런타임에 프레임워크가 몰래 끼워 넣은 것이다. 여기서 getClass()로 엄격하게 굴면 "같은 DB 행을 가리키는 두 객체가 다르다"는 훨씬 나쁜 결과가 나온다.

규칙의 목적으로 돌아가면 된다 — getClass() 비교의 목적은 "의미가 다른 두 타입이 섞이는 것을 막는 것"인데, 프록시는 의미가 다르지 않다

진짜로 상속 매핑(@Inheritance)을 쓴다면 원리적 한계까지 말해야 한다 — 미초기화 프록시로부터 실제 서브클래스를 알아내는 것은 DB를 읽지 않고는 불가능하다. getPersistentClass()는 선언된 타입만 알려주고 Hibernate.getClassLazy()는 서브클래스가 있으면 초기화한다. 그래서 실무적 결론은 "타입 구분을 equals에 맡기지 말고 식별자 비교로 끝내라"다 — 세 전략 모두 식별자가 계층 전체에서 유일하므로 id가 같으면 타입도 자동으로 같다.

Lombok @EqualsAndHashCode(onlyExplicitlyIncluded = true)로 id만 포함시키면 되지 않나요? 함정힌트: 막아 주는 것과 못 막는 것을 나눠서 말한다. 못 막는 것이 이 문항의 본론이다

@Data보다는 훨씬 낫지만 정답은 아니다.

막아 준다: 연관 getter 호출로 인한 지연 로딩 초기화(쿼리 폭탄), 사용자가 수정하는 필드로 인한 해시 변동.

못 막는다: ① id가 null이던 시점과 저장 후의 해시가 다르다 — Lombok의 hashCode는 id가 null이면 상수 43을, 값이 있으면 그 해시를 섞으므로 이 문항의 본론인 사고가 그대로 남는다 ② 미저장 엔티티 두 개가 id가 둘 다 null이라 같다고 판정된다 ③ canEqual 호출 때문에 상대가 프록시면 초기화된다.

onlyExplicitlyIncluded는 어떤 필드를 쓸지만 정할 뿐, 그 필드가 언제 채워지는지는 건드리지 않는다.

Lombok으로는 id != null && 조건도, 상수 hashCode도 표현할 수 없다

그래서 선택지는 셋뿐이다 — 직접 작성하거나(5-4), 아예 오버라이드하지 않거나(7 C), 식별자를 애플리케이션에서 생성해 id가 null인 시점을 없애거나(7-1). 세 번째를 택하면 그때는 onlyExplicitlyIncluded가 완전한 해답이 된다.

그럼 모든 엔티티에 이 equals/hashCode를 넣어야 하나요? 시니어 변별힌트: 기본값은 "넣는 것"이 아니다. 그리고 오버라이드는 공짜가 아니다

아니다. 기본은 "넣지 않는 것"이다. 필요할 때만 넣는다. 근거가 둘이다.

① JPA의 동일성 보장 — 같은 영속성 컨텍스트 안에서 같은 id를 조회하면 항상 같은 인스턴스가 돌아온다. 그래서 한 트랜잭션 안에서만 사는 엔티티라면 기본 equals(참조 비교)로도 "같은 행 = 같다"가 정확히 성립하고 틀릴 여지가 0이다.

② 성능 — 엔티티가 equals를 오버라이드하지 않으면 하이버네이트는 프록시의 equals/hashCode 호출을 가로채 참조 비교와 identity 해시로 끝내고 DB에 가지 않는다. 오버라이드하는 순간 그 지름길이 닫힌다 — 즉 오버라이드는 공짜가 아니다.

넣어야 하는 조건은 명확히 셋이다.

① Set에 담거나 Map 키로 쓴다 ② 영속성 컨텍스트 경계를 넘어 비교한다(준영속·다른 트랜잭션·직렬화 왕복) ③ 컬렉션 API 결과에 비즈니스 로직이 의존한다
셋 중 하나에 해당하면, 그다음 질문은 "이 구조를 바꿔서 조건 자체를 없앨 수 있는가"여야 한다
equals를 잘 쓰는 것보다 equals가 필요 없게 만드는 쪽이 항상 낫다
return 31;이 찜찜한데 getClass().hashCode()를 쓰면 안 되나요? 가산점힌트: 그냥 쓰면 규약 ①이 깨진다. 무엇과 무엇의 해시가 달라지는가

조건부로 된다. getClass().hashCode()를 그대로 쓰면 Member와 Member$HibernateProxy가 서로 다른 값을 내놓는다. 그런데 equals는 instanceof라 real.equals(proxy)가 true다. equals는 같은데 해시가 다른 규약 위반 상태가 된다.

그래서 이 형태를 택할 거라면 프록시를 벗기는 처리가 반드시 함께 가야 한다.

private static Class<?> effectiveClass(Object o) {
    return (o instanceof HibernateProxy hp)
            ? hp.getHibernateLazyInitializer().getPersistentClass()   // 초기화하지 않는다
            : o.getClass();
}
@Override public int hashCode() { return effectiveClass(this).hashCode(); }

얻는 것은 "타입별로 값이 갈려 버킷이 조금 분산된다"는 정도이고, 치르는 것은 코드 한 덩이와 실수 여지다. return 31;은 이 문제 자체가 없다는 점에서 실무적으로 가장 안전하다.

Map<Member, List<Order>>로 그룹핑했더니 회원 수만큼 SELECT가 나갔습니다. 왜죠? 가산점힌트: 그룹핑은 키 객체를 수신자로 무엇을 호출하는가

키가 프록시이고, 그 프록시를 수신자로 hashCode()가 호출되기 때문이다. groupingBy(Order::getMember)에서 getMember()는 LAZY 연관이라 미초기화 프록시를 돌려주고, HashMap에 넣으려면 그 프록시의 hashCode()를 불러야 한다. 엔티티가 equals를 오버라이드했다면 가로채기가 닫혀 있어 위임을 위해 초기화된다 — 회원마다 SELECT 한 번.

해법은 키를 id로 바꾸는 것이다.

// after — getId()는 초기화를 일으키지 않으므로 SELECT 가 없다
Map<Long, List<Order>> ordersByMemberId = orders.stream()
        .collect(groupingBy(o -> o.getMember().getId()));
수신자가 프록시면 SELECT 1회, 인자면 0회 — 판단은 메서드 본문이 아니라 호출 지점에서 갈린다
같은 사고의 반대 방향도 있습니다. Set에 넣었는데 개수가 예상보다 적다면? 가산점힌트: 이번엔 해시가 아니라 equals가 범인이다

미저장 엔티티 둘이 "같다"고 판정돼 하나로 합쳐진 것이다. Objects.equals(id, other.id)는 null == null을 true로 만든다. 아직 id가 없는 새 회원 두 명을 Set에 넣으면 한 명이 조용히 사라진다.

Lombok @Data가 생성하는 코드도 같은 구조다 — id가 둘 다 null이면 그 조건을 통과하고, 나머지 필드가 우연히 같으면 equals가 true가 된다.

그래서 id != null &&가 필요하다 — "아직 식별자가 없으므로 같다고 말할 근거가 없다"

두 사고를 짝으로 기억하면 좋다 — 해시가 바뀌면 있는데 못 찾고, equals가 헐거우면 없어야 할 병합이 일어난다. 둘 다 조용히 데이터를 잃는다는 점이 같다.

테스트에서 실제 엔티티와 프록시를 나란히 놓으려면 어떻게 해야 하나요? 가산점힌트: 순서를 뒤집으면 테스트가 통과하는데 아무것도 검증하지 못한다

실제 엔티티를 먼저 확보하고 em.clear()로 컨텍스트를 비운 뒤 getReference를 불러야 한다.

Member real = memberRepository.findById(id).orElseThrow();
em.clear();                                     // real 은 준영속, 1차 캐시는 비워진다
Member proxy = em.getReference(Member.class, id);   // 진짜 미초기화 프록시

순서를 뒤집으면 getReference가 만든 프록시가 영속성 컨텍스트에 등록되고, 그 뒤의 findById는 DB를 읽어 그 프록시를 초기화한 다음 같은 인스턴스를 돌려준다. 그러면 real == proxy라 equals 구현이 무엇이든 통과한다 — 통과하는데 아무것도 검증하지 못하는 테스트가 된다.

비용도 방향마다 다르다 — real.equals(proxy)는 인자의 getId()만 부르므로 SELECT가 없고, proxy.equals(real)은 수신자가 프록시라 초기화 SELECT가 한 번 나간다. 대칭성 검증에는 그 비용이 따라온다는 것을 알고 쓰면 된다.

@Embeddable 값 객체는 왜 이 문제가 없나요? 가산점힌트: 두 가지가 동시에 없다 — 하나는 시점, 하나는 타입

두 변수가 모두 없기 때문이다. ① 값이 안 변하므로 해시도 안 변한다(생성 시점에 값이 전부 확정되고, 변경은 새 객체 교체로 한다). ② @Embeddable은 엔티티가 아니라 지연 로딩 대상이 아니므로 프록시가 만들어지지 않는다 — getClass() 비교도, 필드 직접 접근도 안전하다.

그래서 VO에서는 "모든 값 필드로 equals/hashCode를 만든다"가 정확히 옳다.

다만 VO에는 VO의 함정이 있다 — BigDecimal은 equals가 스케일까지 비교해서 1000과 1000.00을 다르다고 한다. 금액 비교는 compareTo여야 하고, equals가 스케일을 무시한다면 hashCode에서도 스케일을 지워야(stripTrailingZeros()) 규약 ①이 유지된다.

이 버그를 실제로 만났다면 어떻게 진단하겠습니까? 필수힌트: 증상이 원인에서 멀다. 지문을 알아보는 것이 절반이고, 나머지 절반은 재발 방지다
1
지문 확인 — "size()는 1인데 contains()는 false", "순회하면 나오는데 remove()가 안 된다", "중복 등록이 안 걸러진다", "Set에 넣었는데 개수가 예상보다 적다". 이 넷 중 하나면 해시 기반 컬렉션 + 가변 키를 의심한다.
2
키 객체의 equals/hashCode를 확인 — 엔티티인가? @Data가 붙어 있는가? hashCode가 id나 가변 필드를 쓰는가?
3
넣은 시점과 찾은 시점 사이에 save()나 setter 호출이 있었는지 본다. 있으면 그게 원인이다.
4
재현 테스트를 먼저 쓴다 — 고치기 전에 실패하는 테스트를 만들어야 고쳤다는 것을 증명할 수 있고, 그것이 그대로 회귀 방지 장치로 남는다.
5
고친 뒤 안전망을 건다 — ArchUnit 룰 + 쿼리 수 단정. 한 번 고쳐도 다음 사람이 @Data를 붙이면 그대로 돌아온다.

이 답변의 변별점은 ①②③(진단)과 ④⑤(재발 방지)를 나눠서 말하는 것이다. 진단만 말하면 "고칠 줄 아는 사람", 재발 방지까지 말하면 "구조를 만드는 사람"으로 들린다.

한 줄 요약
Set에 넣은 엔티티가 save() 후 사라지는 것은 hashCode가 id 기반이라 저장 시점에 값이 바뀌면서 HashSet이 노드에 박제해 둔 해시와 어긋나 엉뚱한 칸을 뒤지고 equals까지 가보지도 못하기 때문이고, 여기에 지연 로딩 프록시가 getClass() 비교를 깨뜨리고(6.x의 프록시 이름은 타입명$HibernateProxy 고정 접미사다) 필드 직접 접근을 null로 만드는 함정이 겹치므로, 정석 구현은 instanceof + other.getId() + id != null && + 상수 hashCode다 — 규약이 요구하는 건 "잘 분산된 값"이 아니라 "같으면 같은 값"뿐이고 해시는 후보를 좁힐 뿐 판정은 equals가 하므로 상수는 정확성을 깨지 않으며, 버킷 하나의 대가는 엔티티를 대량으로 Set에 넣지 않으므로 감수한다. "필드를 final로 하고 새 객체를 만든다"는 처방은 값 객체(Money, Address)에는 정확하지만, DB 한 행에 대응하고 변경 감지가 필드 변경을 전제로 하는 엔티티에는 성립하지 않는다. 결국 가장 확실한 처방은 엔티티를 Set·Map 키로 쓰지 않고 컬렉션은 List로 매핑하며 엔티티에 Lombok @Data를 금지하는 것이고(onlyExplicitlyIncluded도 id가 null이던 시점 문제와 canEqual의 프록시 초기화는 못 막는다), 애초에 오버라이드하지 않으면 하이버네이트가 프록시의 equals/hashCode를 참조 비교로 가로채 DB에도 안 가므로 "필요할 때만 넣는다"가 기본값이며, 근본 해법은 식별자를 애플리케이션에서 생성해 "id가 나중에 생긴다"는 전제 자체를 없애는 것이다.
