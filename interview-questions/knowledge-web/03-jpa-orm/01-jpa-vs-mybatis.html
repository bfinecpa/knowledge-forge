JPA vs MyBatis
"결합도가 줄어든다"의 실체와, 그 대가

면접 질문: "JPA를 사용하는 이유는? SQL Mapper(MyBatis)와의 차이는?"

핵심 관전 포인트 — "JPA는 객체스럽게 쓸 수 있다"는 말만으로는 절반도 설명이 안 된다. 줄어드는 결합은 세 층이다 — ① 벤더/방언 종속(SQL을 Dialect가 생성하므로 페이징·시퀀스 문법이 코드에 박히지 않는다) ② SQL의 부재(컬럼 하나 추가가 XML 전수 검사로 번지지 않는다) ③ 도메인 로직의 거처(MyBatis의 VO는 결과셋을 담는 그릇이라 규칙이 서비스로 새어나가지만, JPA 엔티티는 상태와 규칙을 함께 가질 수 있다). 이 중 ③이 "객체스럽게"의 진짜 값이고, 그걸 가능하게 하는 엔진이 영속성 컨텍스트(변경 감지·1차 캐시·쓰기 지연·지연 로딩)다 — MyBatis에는 이에 대응하는 장치가 아예 없다. 대신 대가가 명확하다: 쿼리가 코드에 안 보인다. 그래서 N+1과 불필요한 UPDATE가 조용히 나가고, JPA를 쓰는 사람에게 쿼리 로그 확인은 취향이 아니라 의무가 된다. 그래서 실무의 결론은 "둘 중 하나"가 아니라 쓰기는 ORM, 복잡한 읽기는 SQL이라는 병용이며, 이 분리가 CQRS로 이어지는 첫 단추다.
  • 1
    "결합도가 줄어든다"를 세 층으로 쪼개서 말한다 — ① 방언 종속(페이징·시퀀스 문법이 코드에 없다) ② SQL의 부재(컬럼 추가의 파급이 필드 1개로 줄어든다) ③ 도메인 로직의 거처(엔티티가 상태와 규칙을 함께 가진다). 뭉뚱그리면 "QueryDSL 쓰면 MyBatis랑 똑같잖아요"에 그대로 무너진다.
  • 2
    세 층을 떠받치는 엔진은 영속성 컨텍스트다 — 변경 감지 · 1차 캐시 · 쓰기 지연 · 지연 로딩. save()를 부르지 않아도 UPDATE가 나가는 것이 이 장치이고, MyBatis에는 이에 대응하는 장치가 없다(MyBatis의 캐시는 조회 캐시일 뿐 변경을 추적하지 않는다).
  • 3
    대가는 "쿼리 비가시성"이고, 그래서 답은 둘 중 하나가 아니다 — 편의를 만드는 그 기능이 그대로 N+1과 의도치 않은 UPDATE를 만든다. 그래서 실무의 구도는 쓰기는 ORM, 복잡한 읽기는 SQL이며, 도구를 프로젝트 단위가 아니라 경로 단위로 고르는 이 분리가 CQRS의 첫 단추다.

0. 질문 + 출제 의도

질문: "JPA를 사용하는 이유는? SQL Mapper(MyBatis)와의 차이는?"

출제 의도: 도구 선택의 근거를 말할 수 있는지. 팀마다 둘 다 쓰이므로 "왜 이 프로젝트엔 이게 맞는가"를 논할 수 있어야 기술 스택 논의에 참여할 수 있다.

함정 — "JPA는 편하다 / 생산성이 좋다" 이렇게만 답하면 취향 진술이 된다. 면접관이 듣고 싶은 건 양면이다 — 무엇을 얻고 무엇을 지불하는지. 대가를 말하지 못하는 선택은 선택이 아니라 습관이다.
이 페이지가 겨냥하는 약점 세 가지 ① "결합도가 줄어든다"를 뭉뚱그리는 것 → 2절에서 세 층으로 분해하고, 각 층마다 MyBatis에서는 무엇에 묶여 있는지를 짝지어 세운다.
② 장점만 말하고 메커니즘을 모르는 것 → 3절에서 영속성 컨텍스트의 네 기능을 작업대 비유와 도식으로 세우고, 4절에서 같은 기능이 어떻게 사고가 되는지 한 화면에 붙여 놓는다.
③ "둘 중 하나"로 답하는 것 → 5·6절에서 경로 단위 선택과 섞을 때 실제로 터지는 지점(native로 쏜 변경을 1차 캐시가 모른다)까지 간다.
이 문서의 위치 — 3장의 첫 문서 뒤에 오는 문서들이 당연한 전제로 깔고 들어가는 용어(영속성 컨텍스트, 변경 감지, 지연 로딩, N+1)가 여기서 처음 등장하므로 등장하는 자리마다 정의하고 넘어간다. 다만 영속성 컨텍스트의 내부 동작(스냅샷을 언제 뜨는지, flush가 정확히 언제 도는지)은 02-persistence-context-dirty-checking.md의 본론이다. 여기서는 "MyBatis에는 왜 이에 대응하는 장치가 없는가"라는 대비 축에 필요한 만큼만 다룬다.

1. 층부터 세운다 — 두 도구가 하는 일이 애초에 다르다

1-1. 분류부터 다르다 — SQL Mapper와 ORM

MyBatisJPA (구현체: Hibernate)
분류SQL MapperORM(Object-Relational Mapping)
개발자가 쓰는 것SQL객체 조작 코드
SQL을 만드는 주체개발자프레임워크(Dialect가 방언별로 생성)
매핑 대상SQL 결과셋 ↔ 객체 필드테이블 ↔ 엔티티(관계·상속 포함)
상태 추적없음영속성 컨텍스트가 추적

SQL Mapper는 SQL은 내가 쓰고, 그 결과를 객체에 담아주는 것까지만 대신해주는 도구다. 순수 JDBC로 조회를 한 번 하려면 커넥션을 얻고 PreparedStatement를 만들고 파라미터를 바인딩하고 ResultSet을 한 줄씩 돌며 rs.getString("name")을 객체에 옮겨 담고 마지막에 전부 닫아야 한다. 이 반복 코드를 JDBC boilerplate라고 부르는데, SQL Mapper가 없애주는 것이 정확히 이 부분이다. SQL 자체는 그대로 내 손에 남는다.

ORM은 한 단계 더 간다. 객체를 다루면 프레임워크가 그에 맞는 SQL을 만들어 실행해준다. ORM이라는 이름 자체가 "객체(Object)와 관계형(Relational) 데이터를 서로 대응(Mapping)시킨다"는 뜻이다.

임피던스 불일치(impedance mismatch) — ORM이 흡수하는 그 "차이"

객체 세계에는 상속·참조·다형성이 있는데 테이블 세계에는 없고, 반대로 테이블 세계에는 외래 키와 조인이 있는데 객체에는 없다. 두 세계의 모양이 안 맞는다는 뜻으로, 전기 공학의 임피던스 정합 개념에서 빌려온 말이다.

객체: 상속 · 참조 · 다형성↔모양이 안 맞음↔테이블: FK · 조인 · 정규화

SQL Mapper는 이 불일치를 개발자가 SQL로 메운다. ORM은 이 불일치를 프레임워크 안으로 흡수한다. 이 한 줄이 두 도구의 모든 차이의 출발점이다.

1-2. 이름 세 개를 먼저 정리한다 — JPA · Hibernate · Spring Data JPA

이 셋을 뭉뚱그려 쓰면 뒤의 설명이 계속 흔들린다. 층을 나눠 두고 시작하자. 아래 도식은 같은 요청 하나가 두 경로에서 어떻게 처리되는지를 층으로 세운 것이다 — 봐야 할 것은 딱 하나, "SQL이 태어나는 곳이 어디인가"다.

면접에서 층을 섞어 말하면 바로 드러난다 "JPA가 메서드 이름으로 쿼리를 만들어 준다" → 틀렸다. 그건 Spring Data JPA다.
"JPA가 SQL을 생성한다" → 반쯤 틀렸다. 명세는 정의만 하고, 실제로 SQL을 만드는 것은 Hibernate다.
세 이름을 맨 위(Spring Data JPA) · 중간(JPA 명세) · 실행(Hibernate)으로 나눠 부르기만 해도 답변의 해상도가 달라진다.

2. 줄어드는 결합 세 층 — 방 · 부 · 거

"JPA를 쓰면 DB와의 결합도가 줄어든다"는 문장은 그 자체로는 아무것도 설명하지 않는다. 무엇과 무엇 사이의 결합이 줄어드는지를 말하지 않았기 때문이다. 그리고 뭉뚱그려 두면 "그래봐야 QueryDSL로 쿼리 짜면 MyBatis랑 똑같잖아요"라는 반론에 그대로 무너진다.

줄어드는 결합은 성격이 다른 세 층에 나뉘어 있다. 그리고 세 번째 층이 가장 중요한데 면접에서 가장 덜 언급된다.

세 층 3초 암기 — 방 · 부 · 거

방언 종속→SQL 문법이 코드에 박히지 않는다 (이식성)
SQL의 부재→컬럼 추가가 XML 전수 수정으로 번지지 않는다 (변경 비용)
도메인 로직의 거처→엔티티가 상태와 규칙을 함께 가진다 (설계) ★

방·부·거 — 순서가 곧 중요도의 역순이다. 남들이 ①만 말하고 끝낼 때 ③까지 가는 것이 이 질문의 변별점이다.

2-1. 결합 ① 벤더·방언 종속 — SQL 문법이 코드에 박히지 않는다

먼저 전제. 같은 "정렬해서 21번째부터 10건"이라는 요구가 DB 제품마다 문법이 전혀 다르다.

전제 같은 요구, 다른 문법
-- MySQL / PostgreSQL
SELECT * FROM orders ORDER BY id DESC LIMIT 10 OFFSET 20;

-- Oracle 11g 이하 — 같은 요구인데 모양이 아예 다르다
SELECT * FROM (SELECT a.*, ROWNUM rn FROM (SELECT * FROM orders ORDER BY id DESC) a
              WHERE ROWNUM <= 30) WHERE rn > 20;

방언(dialect)은 이렇게 제품마다 갈리는 SQL 문법 차이를 가리키는 말이다. 사람의 언어에서 지역마다 말이 갈리는 것에 빗댄 이름이다. Hibernate는 Dialect라는 클래스로 이 차이를 흡수한다 — DB 제품별 번역기라고 보면 된다. 어떤 페이징 문법을 쓸지, 시퀀스를 어떻게 호출할지, 문자열 결합 함수 이름이 무엇인지를 이 클래스가 알고 있고, Hibernate는 같은 요청을 받아 접속한 DB에 맞는 SQL로 번역해 내보낸다.

MyBatis 문법이 XML에 박힌다
<!-- DB를 바꾸면 이 문자열을 사람이 고친다 -->
<select id="findPage" resultMap="orderMap">
  SELECT * FROM orders
  ORDER BY id DESC
  LIMIT #{size} OFFSET #{offset}   벤더 종속
</select>
JPA 같은 코드가 방언에 따라 다르게 번역된다
// 이 한 줄이 Dialect에 따라
// LIMIT / ROW_NUMBER() / TOP 으로 각각 번역돼 나간다.
orderRepository.findAll(
    PageRequest.of(2, 10, Sort.by(DESC, "id")));
// 페이징 문법을 코드가 알지 못한다는 것이 이 층의 이득이다

키 생성 전략(IDENTITY / SEQUENCE), 페이징, 함수명, 락 문법(FOR UPDATE)이 모두 여기 해당한다.

과대평가 주의 — "DB를 바꿔도 코드가 그대로"는 마케팅 문구에 가깝다

실제 전환에서는 native 쿼리(직접 쓴 SQL), 타입 차이(boolean을 Oracle에서는 NUMBER(1)로 받는 식), 옵티마이저 힌트, 인덱스 전략이 전부 재검토 대상이다.

정직한 표현은 "코드가 그대로다"가 아니라 "바뀌는 면적이 줄어든다"
"코드가 그대로입니다"라고 답하면 전환을 해본 적이 없다는 사실이 드러난다.

2-2. 결합 ② SQL이 애플리케이션에 없다 — 스키마 변경의 파급 면적

운영 중인 orders 테이블에 canceled_at 컬럼 하나가 추가됐다고 하자. 어디를 고쳐야 하는가.

MyBatis 그 테이블을 건드리는 모든 구문을 찾아 수정해야 한다
<resultMap id="orderMap" type="Order">
  <result column="canceled_at" property="canceledAt"/>   추가 ①
</resultMap>

<insert id="insert">
  INSERT INTO orders (id, status, canceled_at)            추가 ②
  VALUES (#{id}, #{status}, #{canceledAt})                추가 ③
</insert>

<update id="update">
  UPDATE orders SET status = #{status}, canceled_at = #{canceledAt} WHERE id = #{id}   추가 ④
</update>

<!-- 그리고 이 테이블을 SELECT 하는 다른 구문들도 전수 확인해야 한다 -->
JPA 엔티티에 필드 하나를 더한다
@Entity
public class Order {
    // 이 한 줄로 INSERT / UPDATE / SELECT 문이 전부 다시 생성된다.
    // 고칠 곳이 "구문 개수만큼"에서 "필드 1개"로 줄어드는 지점이다.
    private LocalDateTime canceledAt;
}
개수보다 중요한 것 — 누락이 조용히 지나간다 MyBatis에서 UPDATE 구문 하나를 빼먹으면 그 경로에서만 값이 저장되지 않는 버그가 되는데, 컴파일은 멀쩡히 통과한다. 테스트가 그 경로를 덮지 않았다면 운영에서 발견된다. 사람이 전수 검사로 막아야 하는 종류의 버그다.

2-3. 결합 ③ 도메인 로직의 거처 — "객체스럽게"의 진짜 값

세 층 중 가장 중요하고, 면접에서 가장 덜 언급되는 층이다.

먼저 용어 하나. MyBatis 실무에서 흔히 말하는 VO(Value Object)는 원래 "값 그 자체로 동일성을 판단하는 불변 객체"를 뜻하는 설계 용어지만, 현장에서는 관례적으로 SQL 결과셋 한 행을 담는 자바 객체를 그렇게 부른다(DTO라고 부르는 팀도 있다). 이름이 무엇이든 구조는 같다 — getter와 setter만 있고, 값을 담는 것 외의 책임이 없다.

결과셋 그릇 = "택배 상자"

상자는 안에 무엇이 들었는지만 안다. "이 물건을 반품해도 되는가"는 상자가 판단하지 못하므로 매번 사람이 규정집을 들고 확인해야 한다. 확인하는 사람이 늘어나면 규정 해석이 갈라진다.

엔티티 = "규정을 아는 직원"

직원은 상태를 들고 있으면서 규칙도 안다. "취소해 주세요"라고만 하면 취소 가능한 상태인지 스스로 확인하고 시각까지 남긴다. 요청자가 몇 명이든 규칙은 한 벌이다.

책임이 없으면 규칙은 어디로 가는가. 서비스로 나간다.

before 규칙이 서비스에 흩어진다 (MyBatis 스타일에서 흔한 귀결)
public class Order {          // getter/setter만 있는 그릇
    private String status;
    private LocalDateTime canceledAt;
    // getters / setters ...
}

@Service
public class OrderService {
    public void cancel(Long id) {
        Order order = orderMapper.findById(id);
        if (!"PAID".equals(order.getStatus())) {          // 취소 규칙 ①: 결제 완료만 취소 가능
            throw new IllegalStateException("결제 완료 상태만 취소 가능");
        }
        order.setStatus("CANCELED");                       // 취소 규칙 ②: 상태를 바꾼다
        order.setCanceledAt(LocalDateTime.now());          // 취소 규칙 ③: 취소 시각을 남긴다
        orderMapper.update(order);                         // 저장은 명시적으로 호출해야 한다
    }
}

@Service
public class AdminOrderService {
    public void forceCancel(Long id) {
        Order order = orderMapper.findById(id);
        order.setStatus("CANCELED");
        // 문제: canceledAt 세팅을 빠뜨렸다. 규칙 ③ 유실
        // 규칙 ①②③이 한 덩어리로 묶여 있지 않으니 경로마다 복붙되고, 복붙된 순간부터 갈라진다.
        orderMapper.update(order);
    }
}

문제는 "setter가 많다"가 아니다. "취소"라는 규칙이 한 군데에 없다는 것이다. 취소 경로가 사용자용 · 관리자용 · 배치용으로 늘어날 때마다 규칙이 복제되고, 복제된 순간부터 서로 갈라진다. 어느 쪽이 진짜 취소 규칙인지 코드만 봐서는 알 수 없게 된다.

after 규칙이 엔티티 안에 있고, 변경은 영속성 컨텍스트가 감지한다
@Entity
public class Order {
    @Enumerated(EnumType.STRING)   // enum을 문자열 컬럼으로 매핑한다. String 필드를 쓸 이유가 없어진다
    private OrderStatus status;
    private LocalDateTime canceledAt;

    public void cancel() {                     // "취소"의 규칙이 이 메서드 하나뿐이다
        if (status != OrderStatus.PAID) {
            throw new IllegalStateException("결제 완료 상태만 취소 가능");
        }
        this.status = OrderStatus.CANCELED;
        this.canceledAt = LocalDateTime.now();
    }
}

@Service
public class OrderService {
    @Transactional
    public void cancel(Long id) {
        orderRepository.findById(id).orElseThrow().cancel();
        // save() 호출이 없다. 이 부분이 다음 절(변경 감지)의 주제다. 3절
    }
}

불변식(invariant) — "객체스럽다"의 실체

불변식이란 "이 객체가 살아 있는 동안 항상 참이어야 하는 조건"이다. 여기서는 "CANCELED 상태이면 canceledAt이 반드시 있다"가 그것이다.

불변식을 객체가 스스로 지킬 수 있게 되는 것 — 이게 "객체스럽다"의 실체이고, 도메인 주도 설계가 ORM 위에서 자연스러운 이유다

status를 String이 아니라 enum으로 둘 수 있는 것도 같은 층의 이득이다 — @Enumerated가 매핑을 흡수하므로 DB 컬럼 타입을 신경 쓰지 않아도 된다.

오해 하나를 막아두자 — MyBatis로 같은 설계를 못 하는 것은 아니다 엔티티에 cancel() 메서드를 두고 그 뒤에 mapper.update(order)를 부르면 된다. 다만 update를 손으로 부르는 순간 "이 객체를 어디서 저장했는지"를 개발자가 계속 추적해야 하고, 그 추적 부담이 결국 로직을 서비스 쪽으로 끌어내린다.
구조적으로 불가능한 것이 아니라, 중력이 반대 방향으로 걸려 있다

3. 엔진 — 영속성 컨텍스트가 세 층을 떠받친다

2-3의 마지막 코드에서 save()를 부르지 않았는데도 UPDATE가 나갔다. 이것을 가능하게 하는 장치가 영속성 컨텍스트(persistence context)다.

정의부터 하면, 트랜잭션이 살아 있는 동안 조회·저장한 엔티티를 담아두고 그 상태를 계속 추적하는 메모리 공간이다. "영속(persistence)"은 데이터를 저장 매체에 남긴다는 뜻이고, "컨텍스트(context)"는 그 작업이 벌어지는 문맥·범위를 뜻한다. 합치면 "저장을 관리하는 작업 범위"쯤 된다. Spring 환경에서는 보통 트랜잭션 하나가 영속성 컨텍스트 하나에 대응한다.

비유하자면 DB와 애플리케이션 사이에 놓인 "작업대" — 물건을 꺼내 올려두고, 위에서 고치고, 작업이 끝나는 시점(커밋)에 바뀐 것만 되돌려 보낸다

3-1. 기능 ① 변경 감지(dirty checking) — "무엇이 바뀌었는지" 계산해 준다

변경 감지는 엔티티를 조회한 시점의 값을 따로 복사해 두었다가(이 복사본을 스냅샷이라 부른다) 커밋 직전에 현재 값과 필드별로 비교해, 달라진 것이 있으면 UPDATE 문을 만들어 내보내는 기능이다. "dirty"는 "원본과 달라진, 손댄"이라는 뜻으로 쓰이는 관용어다.

@Transactional
public void changeName(Long id, String newName) {
    Order order = orderRepository.findById(id).orElseThrow();  // 이 순간 스냅샷이 떠진다
    order.rename(newName);                                     // 인스턴스만 바뀐다. 스냅샷은 그대로다
    // 커밋 직전, 인스턴스와 스냅샷을 비교해 달라진 필드를 찾아 UPDATE를 만든다.
}
MyBatis에서라면 개발자가 mapper.update(order)를 직접 불러야 한다. 부르지 않으면 저장되지 않고, 두 번 부르면 두 번 나간다. 즉 "언제 저장할지"의 결정권이 개발자에게 있다. JPA에서는 그 결정권이 프레임워크에 있다 — 이것이 2-3의 설계를 성립시키는 힘이자, 4-2에서 볼 사고의 원인이다.

3-2. 기능 ② 1차 캐시 — 같은 트랜잭션에서 같은 ID는 같은 객체다

영속성 컨텍스트는 조회한 엔티티를 (엔티티 타입, id)를 열쇠로 하는 맵에 담아둔다. 이것을 1차 캐시라고 부른다. "1차"인 이유는 트랜잭션 범위의 이 캐시와 구분되는 2차 캐시(애플리케이션 전체가 공유하는 캐시)가 따로 있기 때문이다.

JPA 같은 id = 같은 인스턴스
@Transactional
public void sameInstance(Long id) {
    Order a = orderRepository.findById(id).orElseThrow();
    // ↑ SELECT 1회
    Order b = orderRepository.findById(id).orElseThrow();
    // ↑ 쿼리가 나가지 않는다 (1차 캐시 히트)
    // a == b 가 true. 두 변수가 같은 인스턴스다
}
MyBatis 같은 행이라도 객체는 둘
public void twoInstances(Long id) {
    Order a = orderMapper.findById(id);   // SELECT
    Order b = orderMapper.findById(id);   // SELECT 또
    // a == b 는 false. 서로 다른 객체 두 개
    // 버그가 아니라 SQL Mapper의 정상 동작이다.
    // "결과셋을 객체로 담아준다"가 전부이므로
    // 같은 행을 두 번 읽으면 객체도 두 개다.
}

동일성 보장이 왜 중요한가. 한 트랜잭션 안에서 같은 데이터를 두 경로로 조회했을 때, 한쪽에서 바꾼 값이 다른 쪽에도 보이기 때문이다. MyBatis에서는 두 객체가 따로 놀아 "분명히 바꿨는데 다른 코드에서는 옛날 값"이 나올 수 있다. 대신 이 편의가 6절에서 볼 함정(native 쿼리로 바꾼 값을 1차 캐시가 모른다)의 원인이 되기도 한다.

3-3. 기능 ③ 쓰기 지연(write-behind) — SQL을 모았다가 한 번에 내보낸다

쓰기 지연은 INSERT·UPDATE·DELETE를 만들어지는 즉시 DB로 보내지 않고 영속성 컨텍스트 안의 SQL 저장소에 쌓아두었다가, flush 시점에 모아서 한 번에 보내는 동작이다.

여기서 반드시 갈라야 할 두 단어 — flush ≠ commit

flush는 쌓아둔 SQL을 실제로 DB에 내보내는 행위다. 기본적으로 트랜잭션 커밋 직전에 자동으로 일어난다(다른 시점도 있는데 그건 15-flush-timing-and-sql-ordering.md의 주제다).

flush = SQL을 보냈다≠commit = 확정됐다

flush는 커밋이 아니다. SQL을 보냈을 뿐 아직 확정되지 않았고, 롤백하면 사라진다.

@Transactional
public void saveThree() {
    orderRepository.save(new Order(...));   // 이 시점에 INSERT가 나가지 않는다
    orderRepository.save(new Order(...));   // 저장소에 쌓인다
    orderRepository.save(new Order(...));
    // 커밋 직전 flush에서 세 INSERT가 한 번에 전송된다.
    // 모아서 보내므로 JDBC batch(여러 SQL을 한 번의 네트워크 왕복으로)를 쓸 여지가 생긴다.
}
MyBatis에서라면 + 덤으로 얻는 것 mapper.insert()를 부른 즉시 DB로 나간다. 모아 보내려면 개발자가 배치 모드 세션을 직접 열어 관리해야 한다.
그리고 JPA에는 이득이 하나 더 있다 — 쌓아둔 SQL을 보내기 전에 순서를 조정할 수 있다. 부모 INSERT가 자식 INSERT보다 먼저 나가야 FK 제약에 걸리지 않는데, 이런 순서 보장이 쓰기 지연 덕분에 가능하다.

3-4. 기능 ④ 지연 로딩(lazy loading) — 연관 객체를 쓸 때 조회한다

객체 세계에서는 order.getMember().getName()처럼 참조를 타고 들어가는 것이 자연스럽다. 그런데 주문을 하나 읽을 때마다 회원까지 조인해서 읽어오면, 회원 정보를 안 쓰는 화면에서는 낭비다.

지연 로딩은 연관된 객체를 실제로 그 필드에 접근하는 순간에 조회하는 전략이다. 그때까지는 진짜 객체 대신 프록시(proxy)를 넣어둔다. 프록시는 겉모습은 진짜 엔티티인 척하지만 속은 비어 있고, 누군가 값을 물어보는 순간 그때 SELECT를 날려 자기 속을 채우는 대리인 객체다.

Order order = orderRepository.findById(1L).orElseThrow();   // SELECT orders 만 나간다
// 이 시점에 order.member는 프록시다. member 테이블은 아직 읽지 않았다.
String name = order.getMember().getName();                  // 여기서 SELECT member 가 나간다
편의의 대가가 여기서 시작된다 MyBatis에서라면 필요한 조인을 SQL에 직접 쓴다. 조인을 안 썼으면 연관 데이터가 없는 것이고, 그 사실이 SQL에 그대로 보인다.
지연 로딩은 편리하지만 "쿼리가 나가는 시점을 코드만 보고는 알 수 없게" 만든다. 바로 다음 절의 N+1이 여기서 나오고, 트랜잭션이 끝난 뒤에 프록시를 건드려서 터지는 LazyInitializationException(07-lazy-initialization-exception.md)도 여기서 나온다.

4. 대가 — 편의와 사고는 같은 뿌리에서 나온다

이 절이 이 문서에서 면접 변별력이 가장 큰 곳이다. "JPA의 단점은 무엇인가"라는 질문에 제대로 답하려면 장점을 만드는 메커니즘을 알아야 하기 때문이다.

4-1. 대가 ① 의도하지 않은 쿼리가 조용히 나간다 — N+1

N+1 문제란 목록을 1번 조회했을 뿐인데 그 결과 건수(N)만큼 연관 조회가 추가로 따라붙어 총 1 + N번의 쿼리가 나가는 현상이다. 이름 그대로 "1번 + N번"이다.

그래서 JPA를 쓰는 팀에게 이것은 선택이 아니라 의무가 된다

# 개발/스테이징에서 쿼리를 눈으로 확인한다 (운영은 로그량·성능·보안을 고려해 별도 판단)
spring.jpa.properties.hibernate.format_sql: true
logging.level.org.hibernate.SQL: DEBUG

# 눈으로 보는 것보다 확실한 것은 쿼리 수를 테스트로 고정하는 것이다
decorator.datasource.p6spy.enable-logging: true   # 또는 Hibernate Statistics 로 쿼리 수 단정
JPA를 쓰는 사람에게 쿼리 로그 확인은 취향이 아니라 의무다

4-2. 대가 ② 조회만 하려 했는데 UPDATE가 나간다

before 저장할 생각이 없었는데 저장된다
@Transactional
public OrderDto get(Long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    order.setStatus(order.getStatus().normalize());   화면 표시용 의도
    return OrderDto.from(order);
}   // 커밋 시점에 변경 감지가 돌아 UPDATE가 나간다. 저장할 생각이 없었다.
"저장 코드가 없으니 저장되지 않는다"는 직관이 JPA에서는 틀린다
영속 상태 엔티티의 필드를 건드린 것 자체가 저장 지시이기 때문이다
after 읽기 전용임을 선언한다
@Transactional(readOnly = true)
public OrderDto get(Long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    return OrderDto.from(order);
}
사고 예방과 성능이 같은 방향인 드문 경우 readOnly = true를 붙이면 Hibernate가 flush 모드를 MANUAL로 바꿔 자동 flush를 하지 않고, 나아가 스냅샷을 뜨지 않아도 되므로 메모리와 비교 비용까지 절약된다(02-spring/13-transactional-readonly-optimization.md). 보통 "안전 장치는 성능을 깎는다"인데 여기서는 둘이 같은 방향이다.

4-3. 대가 ③ 복잡한 조회는 결국 다른 도구로 내려간다

Spring Data JPA의 "메서드 이름으로 쿼리 생성"은 조건이 적고 고정일 때만 유효하다.

// 조건 2개까지는 우아하다
List<Member> findByStatusAndOrganizationId(Status status, Long orgId);

// 선택적 조건이 6개(이름·이메일·가입일 범위·상태·조직·최근 로그인)라면?
findByNameContainingAndEmailContainingAndCreatedAtBetweenAnd...  조합 폭발

조건이 "선택적"이라는 점이 핵심이다. 사용자가 이름만 넣을 수도, 이름과 상태를 함께 넣을 수도 있으므로 필요한 메서드 개수가 조건 개수의 지수로 늘어난다. 그래서 동적 조회는 JPQL이나 QueryDSL로 간다.

// QueryDSL — where에 넘긴 조건 중 null인 것은 자동으로 무시된다.
// 즉 "입력된 조건만 참여"가 if문 없이 표현된다.
queryFactory.selectFrom(member)
    .where(nameLike(cond.name()), emailLike(cond.email()), joinedBetween(cond.from(), cond.to()))
    .fetch();

private BooleanExpression nameLike(String name) {
    return name == null ? null : member.name.contains(name);   null이면 그 조건은 빠진다
}

여기서 반드시 짚어야 할 축의 구분 — 이걸 섞으면 함정에 걸린다

결합도 축 (1~3층)

QueryDSL이 만드는 것은 JPQL이고 그것을 방언별 SQL로 번역하는 것은 Hibernate다. 결과가 엔티티라면 영속성 컨텍스트도 살아 있다.

안전성 축 (별개의 이득)

컴파일 시점 타입 안전 — 컬럼명 오타와 타입 불일치를 빌드가 잡아내고, 필드명을 바꾸면 IDE 리팩터링이 쿼리까지 따라간다. XML 문자열은 이 중 어느 것도 되지 않는다.

두 축을 섞어 말하면 "그럼 결국 쿼리 짜는 건 똑같잖아요"라는 반론에 답을 못 하게 된다. "타입 안전"만으로 답하면 절반이다.

그리고 다음 영역은 여전히 SQL이 이긴다.

다중 서브쿼리 · 윈도 함수
ROW_NUMBER, LAG, PIVOT, 재귀 CTE

4-4. 대가 ④ 대량 처리와 학습 곡선, 그리고 merge

대량 INSERT가 느리다 — 원인은 IDENTITY 전략에 있다

JPA의 기본 경로는 건별 INSERT다. 특히 IDENTITY 전략(DB의 auto_increment에 키 생성을 맡기는 방식)에서는 키 값을 알아야 영속성 컨텍스트의 1차 캐시에 넣을 수 있는데 그 키를 DB만 알고 있으므로, INSERT를 즉시 보내 키를 받아와야 한다.

IDENTITY = 키를 DB가 만든다→INSERT를 즉시 보내야 키를 안다→쓰기 지연 무력화→JDBC batch도 함께 무력화

대안은 SEQUENCE 전략(미리 키를 받아올 수 있으므로 모아서 보낼 수 있다)에 batch 설정을 얹거나, 아예 JdbcTemplate으로 내려가는 것이다(21-bulk-insert-jdbc-batch.md).

확인 범위 — 버전에 따라 달라질 수 있는 지점 "IDENTITY면 batch가 안 된다"는 오랫동안 참이었으나, Hibernate 6.5 계열에서 드라이버가 배치 실행 후 생성 키 반환을 지원하는 경우에 한해 일부 개선이 있었다. 팀에서 쓰는 Hibernate 버전과 드라이버 조합에서 실제로 batch가 묶이는지는 쿼리 로그나 Statistics로 직접 확인하는 것이 안전하다.

학습 곡선의 "성질"이 나쁘다

몰라도 일단 돌아간다는 것이 문제다. 그래서 이상 동작이 났을 때(안 바꾼 값이 저장됨, 조회 결과가 옛날 값, LazyInitializationException) 원인을 찾지 못한다.

MyBatis는 바닥이 얕다 — 모르는 것이 SQL 문법 하나이고, 로그에 찍힌 SQL이 곧 진실이다.

merge의 함정 — 예외도 나지 않는다

준영속 상태(한때 영속이었지만 지금은 추적되지 않는 상태) 엔티티를 merge하면 전체 필드를 덮어써서, 세팅하지 않은 필드가 null로 저장되는 데이터 유실이 발생한다.

자세한 것은 05-merge-vs-dirty-checking.md. 조용히 지워진다는 점에서 가장 위험한 축에 든다.

6. 섞을 때의 함정과 CQRS의 첫 단추

6-1. native로 쏜 변경은 1차 캐시가 모른다

먼저 안심해도 되는 부분 한 트랜잭션에서 JPA와 JdbcTemplate을 섞어도 같은 커넥션을 공유한다(02-spring/24-transaction-synchronization-connection-binding.md). 그러므로 트랜잭션은 하나로 묶인다.

문제는 다른 곳에 있다. JdbcTemplate이나 native 쿼리로 UPDATE를 쏘면 영속성 컨텍스트는 그 사실을 모른다.

6-2. 이 분리가 CQRS의 첫 단추다

CQRS(Command Query Responsibility Segregation, 명령·조회 책임 분리)는 데이터를 바꾸는 경로(명령)와 읽는 경로(조회)에 서로 다른 모델을 쓰는 설계 패턴이다. 이름의 "책임 분리"가 정확히 그 뜻이다.

7-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

줄어드는 결합 세 층?
방·부·거 — 방언 종속 / SQL의 부재 / 도메인 로직의 거처. 세 번째가 "객체스럽게"의 진짜 값.
영속성 컨텍스트 네 기능?
변·일·쓰·지 — 변경 감지 / 1차 캐시 / 쓰기 지연 / 지연 로딩. MyBatis엔 이 층이 통째로 없다.
JPA의 근본 대가 한 문장?
쿼리가 코드에 보이지 않는다. 그래서 N+1과 의도치 않은 UPDATE가 조용히 나가고, 쿼리 로그 확인이 의무가 된다.
네 기능 ↔ 네 대가?
변경 감지 → 의도 없는 UPDATE / 1차 캐시 → native 변경을 모름 / 쓰기 지연 → 시점 어긋남 / 지연 로딩 → N+1.
세 이름의 층?
Spring Data JPA(Repository) → JPA(표준 명세) → Hibernate(구현·SQL 생성). "메서드 이름 쿼리"는 맨 위 층의 기능.
QueryDSL의 이득은 어느 축?
JPQL이라 방언 종속 없음 + 영속성 컨텍스트 유지 = 결합도 축. 타입 안전은 별개의 안전성 축. 섞어 말하면 반론에 무너진다.
선택 여섯 축?
작·도·쿼·스·팀·성 — 앞 셋은 코드, 뒤 셋은 환경. 레거시 스키마와 팀 역량이 강한 신호.
실무의 결론 한 문장?
둘 중 하나가 아니라 쓰기는 ORM, 복잡한 읽기는 SQL. 도구를 경로 단위로 고르는 것이 CQRS의 첫 단추.
섞을 때 터지는 지점?
JdbcTemplate·native로 쏜 UPDATE를 1차 캐시가 모른다. 트랜잭션은 묶이지만 조회 결과는 옛날 값 → clear().
"DB 바꿔도 코드 그대로"?
과대평가. native·타입 매핑·힌트·인덱스는 재검토 대상. 정직한 표현은 "바뀌는 면적이 줄어든다".

7-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

QueryDSL로 쿼리를 직접 짜면 결국 MyBatis와 같은 거 아닌가요? 함정힌트: "타입 안전"으로만 끝내면 걸린다. 축을 두 개로 갈라 말한다

아니다. 그리고 답을 "타입 안전"으로만 끝내면 안 된다. 세 가지를 나눠 말한다.

① 여전히 SQL을 쓰지 않는다. QueryDSL이 만들어 내는 것은 JPQL이고, 그것을 다시 방언별 SQL로 번역하는 것은 Hibernate다. 2-1의 방언 종속이 그대로 없다.

② 엔티티와 영속성 컨텍스트가 살아 있다. QueryDSL로 조회한 결과가 엔티티라면 그것은 영속 상태이므로, 그대로 필드를 바꾸면 변경 감지가 UPDATE를 만든다. MyBatis의 결과 객체는 그릇일 뿐이라 이 연결이 없다. 2-3과 3-1의 이득이 유지된다는 뜻이다.

③ 거기에 덧붙여 컴파일 시점 타입 안전이 있다.

핵심은 ①②가 결합도 축의 답이고 ③은 안전성 축의 별도 이득이라는 구분
이걸 섞으면 질문자의 함정에 그대로 걸린다
JPA를 쓰면 성능이 나빠지나요? 필수힌트: "느리다 / 안 느리다"의 이분법을 거부하고, 조건을 붙인다

기본 경로에 맡기면 나빠질 수 있다. N+1, 의도치 않은 UPDATE, 필요 없는 컬럼까지 조회하는 것이 대표적이다. 전부 4절에서 본, 편의를 만드는 그 기능들이 만드는 비용이다.

통제하면 MyBatis와 큰 차이가 없다. fetch join과 @EntityGraph로 N+1을 접고, @BatchSize로 남은 지연 로딩을 묶고, DTO 프로젝션으로 필요한 컬럼만 읽고, readOnly로 스냅샷 비용을 없애고, batch 설정으로 INSERT를 모은다.

정확한 문장은 "JPA가 느리다"가 아니라 "통제 없이 쓴 JPA가 느리다"

그리고 통제하려면 3절의 네 기능과 그 대가를 알아야 한다. 이 답변 자체가 "메커니즘을 알고 쓴다"는 신호가 된다.

운영에 나가기 전에 N+1을 어떻게 발견하나요? 필수힌트: 사람이 하는 것과 기계가 하는 것을 갈라 말한다

"코드 리뷰로 본다"만 답하면 약하다. 사람의 주의력에 기대는 장치는 언젠가 뚫린다. 자동으로 걸러지는 장치를 말해야 한다.

1
개발 환경에서 SQL 로깅을 상시 켠다. 개발 중에 쿼리가 101번 나가는 것을 눈으로 보게 만든다. 사람
2
테스트에서 쿼리 수를 단정한다. Hibernate Statistics의 getQueryExecutionCount()나 p6spy로 카운트를 세어 "이 API는 쿼리 3개"를 테스트로 고정한다. 회귀가 나면 빌드가 깨진다 — 이것이 가장 확실한 장치다. 기계
3
PR 리뷰에서 반복문 안의 연관 접근을 지적한다. 사람
4
APM과 slow query 로그로 사후 관측한다. 기계

①③은 사람이 하고 ②④는 기계가 한다는 점을 구분해서 말하면 좋다.

DB를 Oracle에서 MySQL로 바꾼다면 JPA라서 편한가요? 함정힌트: "코드가 그대로입니다"라고 답하면 안 해본 티가 난다

면적은 줄지만 공짜는 아니다. 2-1에서 본 대로 페이징 · 시퀀스 · 함수명 · 락 문법은 Dialect가 흡수한다.

그러나 다음은 전부 재검토 대상이다.

native 쿼리타입 매핑 (boolean ↔ NUMBER(1))시퀀스 vs auto_increment 키 전략옵티마이저 힌트인덱스 전략
"바뀌는 면적이 줄어든다"가 정직한 표현이다
레거시 DB에 JPA를 붙이라고 하면 어떻게 하시겠어요?힌트: "된다 / 안 된다"가 아니라 도입 범위를 나눈다

복합키(@IdClass / @EmbeddedId), 뷰 매핑, 트리거 의존, 컬럼 규칙 부재와 싸워야 한다. 이런 환경에서는 JPA의 이득(2절의 세 층)이 거의 나오지 않는 반면 매핑 비용만 지불하게 된다.

현실적인 답은 부분 도입이다. 조회 비중이 크고 기존 스키마에 얽힌 영역은 MyBatis로 두고, 새로 만드는 도메인만 JPA로 시작한다.

즉 5-2에서 본 경로별 도구 선택을 시간 축으로 적용하는 셈이다. "전면 도입 아니면 포기"라는 이분법을 벗어나는 것이 이 질문의 포인트다.

팀에 JPA 경험자가 없다면요? 필수힌트: 이 질문은 도구가 아니라 "선택 변수"를 묻고 있다

이 질문은 도구 성능이 아니라 팀 역량이 선택 변수임을 인지하는지 보는 질문이다.

JPA는 4-4에서 본 대로 "몰라도 돌아가고 이상하면 못 잡는" 성질이라, 경험자 부재의 위험이 MyBatis보다 크다. MyBatis에서 모르는 것은 SQL 문법 하나지만, JPA에서 모르는 것은 "왜 쿼리가 101번 나가는가"다.

그러므로 답은 "도입하지 말자"가 아니라 "안전망을 먼저 세우고 도입하자"가 된다.

그럼 본인은 새 프로젝트에서 어떻게 정하겠습니까? 시니어 변별힌트: "둘 중 하나"라는 질문의 전제를 먼저 거부한다

단일 도구를 고르지 않는 것이 가장 좋은 답이다. 5-2의 경로별 분리를 제시하고, 그 근거를 셋으로 든다.

결정 근거는 "빠른 개발"이 아니라 스키마 상태 + 조회 복잡도 + 팀 역량 세 축이다.

  • 스키마가 새것이고 도메인 규칙이 많으면 쓰기는 JPA가 확실히 유리하다.
  • 조회 복잡도가 높은 경로는 어차피 SQL로 내려가야 한다.
  • 팀 역량은 안전망(쿼리 수 테스트, 리뷰 기준)으로 보강할 수 있는지로 판단한다.
"둘 중 하나를 고르라"는 질문에 "경로마다 다르게 고른다"고 답하되 그 분리 기준을 말하는 것
이것이 도구를 써본 사람과 골라본 사람의 차이다
JPA와 Spring Data JPA는 같은 건가요? 함정힌트: 층이 세 개다. "메서드 이름 쿼리"는 어느 층의 기능인가

같지 않다. 층이 다르다.

  • JPA — 자바 표준 명세(인터페이스). EntityManager, @Entity, JPQL을 정의한다. 명세일 뿐이므로 그 자체로는 아무것도 실행하지 못한다.
  • Hibernate — 그 명세를 실제로 구현한 라이브러리. SQL을 만들고 실행하는 주체이자 영속성 컨텍스트를 관리하는 주체다.
  • Spring Data JPA — 또 한 층 위. EntityManager를 직접 호출하는 반복 코드를 Repository 인터페이스로 걷어내 준다.

그래서 "메서드 이름만 바꾸면 쿼리가 생성된다"는 것은 JPA의 기능이 아니라 Spring Data JPA의 기능이다. 면접에서 둘을 섞어 말하면 층을 구분하지 못하는 인상을 준다.

save()를 부르지 않았는데 UPDATE가 나가는 이유를 메커니즘으로 설명해보세요. 필수힌트: 등장해야 할 단어가 셋 있다 — 스냅샷, 비교 시점, flush

영속성 컨텍스트가 엔티티를 조회하는 순간 두 개를 만든다 — 인스턴스(1차 캐시에 등록)와 스냅샷(조회 시점 값의 복사본)이다.

이후 order.cancel()로 바뀌는 것은 인스턴스뿐이고 스냅샷은 그대로다. 그리고 커밋 직전 flush 시점에 인스턴스와 스냅샷을 필드별로 대조해 달라진 필드만으로 UPDATE 문을 만들어 내보낸다. 이것이 변경 감지(dirty checking)다.

여기서 한 걸음 더 들어가면 flush와 commit을 구분해야 한다 — flush는 SQL을 보낸 것일 뿐 확정이 아니고, 롤백하면 사라진다.

그래서 "저장 코드가 없으니 저장되지 않는다"는 직관이 JPA에서는 틀린다
영속 상태 엔티티의 필드를 건드린 것 자체가 저장 지시다
같은 트랜잭션에서 같은 행을 두 번 조회하면 두 도구에서 각각 어떻게 되나요? 가산점힌트: 쿼리 횟수 하나, == 하나

JPA: 두 번째 조회는 SELECT가 아예 나가지 않고 1차 캐시의 인스턴스를 그대로 돌려준다. 그래서 a == b가 true다.

MyBatis: SELECT가 두 번 나가고, 서로 다른 객체가 두 개 만들어진다. a == b는 false다. 이것은 버그가 아니라 SQL Mapper의 정상 동작이다 — "결과셋을 객체로 담아준다"가 전부이므로 같은 행을 두 번 읽으면 객체도 두 개다.

동일성 보장이 중요한 이유는 한 트랜잭션 안에서 같은 데이터를 두 경로로 조회했을 때 한쪽에서 바꾼 값이 다른 쪽에도 보이기 때문이다. MyBatis에서는 두 객체가 따로 놀아 "분명히 바꿨는데 다른 코드에서는 옛날 값"이 나올 수 있다. 다만 같은 편의가 6-1의 함정(native 변경을 캐시가 모름)을 만든다는 점까지 붙이면 완성된 답이 된다.

@Transactional(readOnly = true)는 왜 사고 예방과 성능이 동시에 되나요? 가산점힌트: 두 가지가 꺼진다 — 하나는 동작, 하나는 자료구조

둘이 같은 뿌리에서 나오기 때문이다.

① 사고 예방 — Hibernate가 flush 모드를 MANUAL로 바꿔 자동 flush를 하지 않는다. 그래서 조회 중에 필드를 건드려도 UPDATE가 나가지 않는다(4-2의 사고 차단).

② 성능 — 나아가 스냅샷을 뜨지 않아도 되므로 메모리와 비교 비용까지 절약된다. 조회 건수가 많을수록 이 절약이 커진다.

보통은 "안전 장치는 성능을 깎는다"인데 여기서는 둘이 같은 방향이라는 점을 짚으면 좋다. 더 나아가려면 DTO 프로젝션을 얹으면 된다 — 결과가 엔티티가 아니므로 애초에 영속성 컨텍스트에 올라가지 않는다.

JPA와 JdbcTemplate을 한 트랜잭션에서 섞어 써도 되나요? 시니어 변별힌트: 트랜잭션 이야기로만 답하면 절반이다. 진짜 함정은 다른 곳에 있다

트랜잭션은 안심해도 된다. 한 트랜잭션에서 JPA와 JdbcTemplate을 섞어도 같은 커넥션을 공유하므로 하나로 묶인다(02-spring/24-transaction-synchronization-connection-binding.md).

문제는 다른 곳에 있다. JdbcTemplate이나 native 쿼리로 UPDATE를 쏘면 영속성 컨텍스트는 그 사실을 모른다.

t1  Order를 조회한다                → 1차 캐시에 status=PAID 로 올라간다
t2  JdbcTemplate으로 UPDATE 실행    → DB의 status는 CANCELED가 된다
t3  같은 트랜잭션에서 다시 조회      → 1차 캐시가 t1의 인스턴스를 돌려준다
                                      결과: status=PAID  (DB와 다르다)

해법은 영속성 컨텍스트를 비우는 것 — flush 후 clear(), 또는 @Modifying(clearAutomatically = true). JPQL 벌크 연산 뒤에 clear()가 필요한 이유와 정확히 같은 원리다(11-bulk-operation-persistence-context.md). 원인을 "캐시가 있어서"가 아니라 "영속성 컨텍스트를 우회한 변경이라서"로 말하는 것이 변별점이다.

JPA로 대량 INSERT가 느린 이유는? 가산점힌트: 키를 누가 만드는가에서 출발한다

JPA의 기본 경로는 건별 INSERT이고, 특히 IDENTITY 전략에서 쓰기 지연이 무력화되기 때문이다.

IDENTITY는 DB의 auto_increment에 키 생성을 맡기는 방식이다. 그런데 영속성 컨텍스트의 1차 캐시는 (타입, id)를 열쇠로 쓰므로 키 값을 알아야 엔티티를 넣을 수 있다. 그 키를 DB만 알고 있으니 INSERT를 즉시 보내 키를 받아와야 한다. 그래서 모아 두었다 보내기(쓰기 지연)가 성립하지 않고, JDBC batch도 함께 무력화된다.

대안: SEQUENCE 전략(미리 키를 받아올 수 있으므로 모아서 보낼 수 있다)에 batch 설정을 얹거나, 아예 JdbcTemplate batch로 내려간다(21-bulk-insert-jdbc-batch.md).

시니어 변별 여기에 버전 확인 태도를 덧붙이면 좋다 — "IDENTITY면 batch가 안 된다"는 오랫동안 참이었으나 Hibernate 6.5 계열에서 드라이버 지원 조건에 한해 일부 개선이 있었다. 팀의 Hibernate·드라이버 조합에서 실제로 batch가 묶이는지는 쿼리 로그나 Statistics로 직접 확인하겠다고 말하는 것이 안전하고 정확하다.

MyBatis에도 1·2차 캐시가 있는데, 그럼 영속성 컨텍스트와 같은 것 아닌가요? 함정힌트: 캐시의 목적이 "재사용"인지 "추적"인지를 가른다

다르다. 캐시라는 단어가 같을 뿐 하는 일이 다르다.

MyBatis의 캐시는 "같은 SQL을 또 부르면 결과를 재사용한다"는 조회 캐시다. 목적은 중복 조회 절감이다.

영속성 컨텍스트는 조회 결과 재사용(1차 캐시)도 하지만, 그것은 네 기능 중 하나일 뿐이다. 결정적으로 스냅샷을 떠 두었다가 변경을 계산해 UPDATE로 바꿔주는 장치가 있고, MyBatis에는 이에 대응하는 것이 없다.

가르는 한 문장 — MyBatis의 캐시는 "재사용"을 하고, 영속성 컨텍스트는 "추적"을 한다
한 줄 요약
JPA가 줄이는 결합은 세 층 — 방언 종속(SQL을 Dialect가 생성), SQL의 부재(컬럼 추가가 XML 전수 수정으로 번지지 않음), 그리고 가장 중요한 도메인 로직의 거처(MyBatis VO는 결과셋 그릇이라 규칙이 서비스로 흩어지지만, JPA 엔티티는 상태와 불변식을 함께 가질 수 있고 save() 없이도 변경 감지가 UPDATE를 만든다) — 이며 그 엔진이 영속성 컨텍스트(변경 감지·1차 캐시·쓰기 지연·지연 로딩)다. 대가는 쿼리 비가시성이라 N+1과 의도치 않은 UPDATE가 조용히 나가고(그래서 쿼리 로깅과 쿼리 수 테스트가 의무), 동적 조회는 QueryDSL로 가되 그것은 결합도가 아니라 타입 안전 축의 이득이며, 집계·윈도 함수·대량 배치는 SQL로 내려가야 하고, 레거시 스키마·SQL 강한 팀·튜닝 상시 환경에서는 MyBatis가 합리적 선택이다. 그래서 실무의 답은 "둘 중 하나"가 아니라 쓰기는 ORM, 복잡한 읽기는 SQL이고(native로 쏜 변경은 1차 캐시가 모른다는 함정 포함), 이 분리가 CQRS로 가는 첫 단추다.
