JPA Auditing과 벌크 연산의 구멍
"자동으로 채워진다"의 자동은 어느 경로에서만 참인가

면접 질문: "JPA Auditing(생성/수정 시각·주체 자동 기록)은 어떻게 동작하나요? 벌크 연산에서는 왜 기록되지 않나요?"

핵심 관전 포인트 — JPA Auditing은 마법이 아니라 @PrePersist/@PreUpdate라는 엔티티 생명주기 콜백에 얹힌 코드다. AuditingEntityListener는 영속성 컨텍스트가 "이 엔티티를 지금 INSERT/UPDATE 하겠다"고 결정하는 순간에만 호출되므로, 그 결정을 거치지 않는 경로 — 벌크 JPQL(@Modifying), 네이티브 쿼리, JdbcTemplate, DB 콘솔의 수동 SQL — 에서는 값이 전부 빠진다. 그리고 이 누락의 성질이 핵심이다. 예외도, 경고 로그도, 실패 카운트도 없다. 조용히 빠진다. 10만 건의 updated_at이 옛날 값 그대로여도 배치는 "성공"으로 끝난다. 처방은 벌크를 유지한다면 SET 절에 감사 필드를 직접 쓰는 것이고, 건수가 감당 범위면 엔티티를 로드해 변경 감지로 처리하는 것(대가: 왕복 N번 + 영속성 컨텍스트 누적)이다. 여기서 시각만 생각하면 절반만 답한 것이다 — @LastModifiedBy(주체)도 같이 빠지고, 게다가 AuditorAware는 보통 SecurityContext에서 사용자를 꺼내는데 배치 스레드에는 그것이 없어 평소 경로에서도 주체가 안 채워지는 별개의 함정이 따라온다. 마지막으로 감사(監査) 요구가 걸린 데이터라면 애플리케이션 레벨 Auditing은 신뢰 경계가 애플리케이션 안쪽이라는 점을 인정해야 한다 — Envers나 DB 트리거로 내리되, Envers도 벌크 연산에서는 똑같이 빠진다.
  • 1
    동작 경로부터 말한다 — "리스너다"에서 멈추지 않는다 — Auditing은 AuditingEntityListener가 가진 @PrePersist/@PreUpdate 두 개의 생명주기 콜백이고, 그 콜백을 부르는 것은 하이버네이트가 flush 시점에 "이 엔티티는 INSERT/UPDATE 대상"이라고 판정하는 순간이다. 판정이 리스너 호출의 전제조건이다.
  • 2
    그래서 판정을 안 거치는 경로는 전부 빠진다 — 그리고 조용히 빠진다 — 벌크 JPQL · 네이티브 · JdbcTemplate · DB 콘솔은 엔티티 객체를 놓고 판정한 적이 없으므로 콜백이 발생할 계기 자체가 없다. 예외도 경고도 없고 반환값은 정확히 100000이라, 이 사고는 몇 달 뒤 감사 요청에서 발견된다.
  • 3
    처방은 두 갈래뿐이고, 시각만 고치면 절반이다 — SET 절에 m.updatedAt = :now, m.updatedBy = :actor를 직접 쓰거나, 건수가 감당되면 엔티티를 로드해 변경 감지로 되돌린다. 여기에 배치 스레드에는 SecurityContext가 없다는 별개의 구멍과, 애플리케이션 레벨 Auditing의 신뢰 경계(Envers도 벌크에서는 빠진다)까지 얹어야 만점이다.

0. 질문 + 출제 의도

면접 시나리오: BaseEntity에 @EntityListeners(AuditingEntityListener.class) + @CreatedDate/@LastModifiedDate/@LastModifiedBy를 적용해 잘 동작하고 있다. 그런데 휴면 전환을 벌크 UPDATE로 바꾼 뒤 10만 건의 updatedAt이 예전 값 그대로다. 왜이며 어떻게 처리하나?

출제 의도: "생성/수정 이력이 리스너(영속성 컨텍스트 이벤트) 기반이라 벌크 연산·네이티브 쿼리에서는 조용히 빠진다는 것을 아는지 — '자동으로 되는 것'의 동작 경로를 알아야 안 되는 경우도 예측할 수 있다. 감사 요구가 있는 데이터라면 이 구멍이 곧 컴플라이언스 이슈다."

그래서 채점 지점은 "Auditing을 설정할 줄 아느냐"가 아니다. 그건 스타터 문서 한 페이지다. 채점 지점은 셋이다.

① 동작 경로를 말하는가
"리스너다"에서 멈추지 않고 "어느 이벤트에 걸려 있고, 그 이벤트는 누가 발생시키는가"까지.
② 예외를 예측하는가
벌크·네이티브·JdbcTemplate·수동 SQL. 아직 겪지 않은 경로도 같은 논리로 판정할 수 있는가.
③ 감사라는 층위를 아는가
애플리케이션 레벨 Auditing의 신뢰 경계가 어디까지인지, 그 밖을 요구받으면 무엇으로 내려가는지.
이 페이지가 겨냥하는 함정 세 개 ① 처방에서 도구를 바꿔 잡는 것 — "배치 사이즈 옵션으로 처리한다". hibernate.jdbc.batch_size는 값을 채우는 기능이 아니다(4절). 진단이 맞아도 엉뚱한 도구를 집으면 그 자리에서 "적용 범위를 모르는 사람"이 된다.
② 시각만 답하고 주체를 빠뜨리는 것 — updatedAt만 고쳐놓고 updatedBy는 여전히 옛 값인 배치가 실무에 흔하다(5절).
③ "Envers 쓰면 됩니다"로 끝내는 것 — Envers도 같은 이유로 벌크에서 빠진다(6절). 도구 이름을 대는 것과 그 도구가 못 막는 것을 아는 것은 다른 능력이다.

1. 부품 조립도 — 무엇이 무엇을 부르는가

원인을 이야기하기 전에 전체 부품을 한 화면에 올려둔다. 이 문항의 답은 결국 "이 부품들 중 무엇이 언제 호출되는가"로 환원되기 때문이다.

1-1. 최소 동작 코드 — 무엇을 켜야 동작하는가

config ① 기능 활성화 + ③ 주체 공급
@Configuration
@EnableJpaAuditing                       // 이게 없으면 애노테이션이 있어도 아무 일도 일어나지 않는다
public class JpaAuditingConfig {         // AuditorAware 빈이 하나뿐이면 타입으로 자동 주입된다.
                                         // 둘 이상일 때만 auditorAwareRef = "auditorProvider" 로 지목한다.
    @Bean
    public AuditorAware<String> auditorProvider() {
        return () -> {
            Authentication auth = SecurityContextHolder.getContext().getAuthentication();
            if (auth == null || !auth.isAuthenticated()) {
                return Optional.empty();          // 5절의 함정이 여기서 시작된다
            }
            return Optional.of(auth.getName());
        };
    }
}
entity ② 공통 필드 묶음 + ④ 실제 엔티티
@Getter
@MappedSuperclass                                   // 이 클래스용 테이블은 생기지 않는다
@EntityListeners(AuditingEntityListener.class)      // 콜백을 등록하는 것은 정확히 이 한 줄
public abstract class BaseEntity {

    @CreatedDate
    @Column(updatable = false)                      // 생성 시각은 이후 UPDATE 문에서 제외한다
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;

    @CreatedBy
    @Column(updatable = false)
    private String createdBy;

    @LastModifiedBy
    private String updatedBy;
}

@Entity @Getter
public class Member extends BaseEntity {          // 상속만 하면 네 컬럼이 따라온다

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String email;

    @Enumerated(EnumType.STRING)
    private MemberStatus status;                    // ACTIVE / DORMANT / WITHDRAWN

    private LocalDateTime lastLoginAt;

    public void toDormant() {                      // 필드만 바꾼다 → 이 경로가 변경 감지 경로다
        this.status = MemberStatus.DORMANT;
    }
}
부품별 역할을 한 줄씩 고정한다 — "없으면 무슨 일이 생기는가"까지 붙여서 외운다
부품하는 일없으면
@EnableJpaAuditing리스너가 쓸 인프라(AuditingHandler, 시각 공급자, AuditorAware)를 컨텍스트에 등록애노테이션이 조용히 무시된다 — 필드가 계속 null
@EntityListeners(AuditingEntityListener.class)그 엔티티에 생명주기 콜백을 붙인다그 엔티티만 Auditing 미적용
@MappedSuperclass BaseEntity컬럼·애노테이션을 상속으로 배포엔티티마다 네 필드를 복붙
AuditorAware<T>주체를 공급@CreatedBy/@LastModifiedBy가 안 채워짐(5절)

1-2. 인과의 핵심 — 리스너는 "생명주기 콜백"에 얹혀 있을 뿐이다

용어를 그 자리에서 정의한다. 엔티티 생명주기 콜백(lifecycle callback)이란, JPA가 엔티티를 저장·수정·삭제·조회하는 특정 시점마다 "이 메서드를 대신 불러주겠다"고 약속해둔 후크(hook)다. 엔티티가 "새 객체 → 영속 → 준영속 → 삭제"라는 일생을 지나간다는 관점에서 생명주기라는 이름이 붙었고, 그 일생의 특정 지점에 코드를 끼워 넣는 장치라서 콜백이다.

@PrePersist@PostPersist@PreUpdate@PostUpdate@PreRemove@PostRemove@PostLoad ←JPA 표준이 정한 후크 7개

그리고 AuditingEntityListener는 그중 두 개(@PrePersist, @PreUpdate)를 가진 평범한 클래스다. 특별한 프레임워크 마법이 아니라, 우리가 직접 쓸 수도 있는 후크에 스프링 데이터가 미리 짜둔 코드가 얹혀 있는 것뿐이다.

source spring-data-jpa의 AuditingEntityListener — 실제로 이게 전부다
@Configurable
public class AuditingEntityListener {

    private @Nullable ObjectFactory<AuditingHandler> handler;

    @PrePersist                                  // INSERT 문을 만들기 직전에 불린다
    public void touchForCreate(Object target) {
        if (handler != null) {                     // 핸들러가 없으면 여기서 조용히 끝난다
            handler.getObject().markCreated(target);
        }
    }

    @PreUpdate                                   // UPDATE 문을 만들기 직전에 불린다
    public void touchForUpdate(Object target) { /* updatedAt / updatedBy */ }
}

이 문서 전체를 지배하는 한 줄 — 이것만 외우면 나머지는 유도된다

콜백은 스스로 실행되지 않는다. 영속성 컨텍스트가 "이 엔티티를 INSERT/UPDATE 대상"이라고 판정한 결과로 호출된다

전제조건이라는 말을 뒤집으면 이렇게 된다 — 판정이 없으면 콜백도 없다. 리스너가 게으른 것도, 버그가 있는 것도 아니다. 호출될 계기 자체가 발생하지 않는다.

비유 — Auditing은 출입문에 달린 자동 방명록이다

사람이 그 문으로 들어오면 이름과 시각이 자동으로 적힌다. 아주 잘 동작한다. 단, 창문으로 들어온 사람은 적히지 않는다. 방명록은 사람을 감지하는 게 아니라 문의 개폐를 감지하기 때문이다.

그리고 방명록은 경고하지 않는다

벌크 UPDATE · 네이티브 쿼리 · JdbcTemplate · DB 콘솔은 전부 창문이다. 방명록은 "누가 창문으로 들어왔다"고 알리지 않는다 — 그냥 아무것도 안 적힐 뿐이다. 이 성질이 7절(안전망)의 존재 이유다.

2. 급소 — 정상 경로와 벌크 경로를 겹쳐 보기

말로만 두면 "리스너가 알아서 채운다" 수준에서 굳는다. 같은 휴면 전환을 두 방식으로 쓰고, 같은 8단계 위에 겹쳐 놓는다. 어디가 끊기는지가 눈으로 보인다.

A 변경 감지 경로
@Transactional
public void toDormant(Long memberId) {
    Member m = memberRepository.findById(memberId).orElseThrow();
    m.toDormant();       // status 만 바꿨다. updatedAt 은 안 건드렸다.
}                          // 여기서 커밋 → flush
B 벌크 JPQL 경로 — 사고 지점
@Modifying
@Query("update Member m set m.status = 'DORMANT' "
     + "where m.lastLoginAt < :cut")
int toDormantBulk(@Param("cut") LocalDateTime cut);
// 10만 건이 바뀐다. 그리고 감사 컬럼은 옛날 값 그대로다.

처방의 방향은 외울 필요가 없다 — 흐름도에서 유도된다: "쓰거나, 태우거나"

① 쓰거나 — ⑦에 직접 쓴다
벌크를 유지한 채 SET 절에 감사 필드를 손으로 써넣는다. 리스너가 ⑥에서 해주던 일을 사람이 인수인계받는 것. → 4-3
② 태우거나 — ①~④를 다시 태운다
엔티티를 로드해 변경 감지 경로로 되돌린다. 손으로 쓸 것이 없어지는 대신 왕복 N번 + 컨텍스트 누적을 낸다. → 4-5

중간 지대가 하나 더 있다 — 청크로 끊어 태우기(4-6). 세 번째 원리가 아니라 ②를 메모리 한계 안에서 쓰는 방법이다.

부수적으로 따라오는 두 사실 가산점 ① updatedAt은 "setter를 호출한 시각"이 아니라 "flush 시각"이다. ②와 ⑥ 사이에 외부 API 호출이 3초 걸렸다면 updatedAt은 3초 뒤 값이다. 보통은 무의미하지만 밀리초 단위로 이력을 재구성하는 로직이라면 이 사실이 필요하다.
② 변경이 없으면 @PreUpdate도 없다. 같은 값으로 다시 세팅하면 ④의 판정이 "안 바뀌었다"로 나와 UPDATE 자체가 안 나가므로 updatedAt도 그대로다. 반대로 의도치 않은 dirty 판정(BigDecimal의 scale 차이 — 1.0과 1.00은 equals가 false다, 컬렉션 재할당, AttributeConverter의 왕복 비대칭)이 생기면 아무도 수정하지 않은 행의 updatedAt이 갱신된다. 이 조사는 Auditing 설정이 아니라 dirty checking 쪽을 봐야 한다.

3. 경로별 기록 여부 · 그리고 실패가 "조용하다"는 것

같은 휴면 전환을 일곱 가지 방식으로 써본다. 코드는 비슷해 보이지만 2절의 흐름도 위에서는 완전히 다른 경로다.

칸을 O/X가 아니라 "기록됨 / 조용히 누락"으로 쓴 이유가 있다 — X는 "실패했다"로 읽히고 실패에는 보통 신호가 따라온다고 기대하게 되지만, 여기서 벌어지는 일은 실패가 아니라 아무 일도 일어나지 않는 것이다.

4. 처방 두 갈래 — 그리고 여기서 잘못 집는 도구

2절에서 손댈 수 있는 칸이 두 개뿐이라는 것을 확인했다. 이 장은 그 두 처방을 코드로 펼치고 대가를 계산한다. 다만 처방을 꺼내기 전에 가장 흔한 오답 하나를 먼저 걷어낸다.

4-1. 먼저 걷어낼 오해 — hibernate.jdbc.batch_size는 무엇을 하는 옵션인가

"10만 건을 한 번에 바꾸는데 감사 컬럼이 안 채워진다"는 문제를 들으면, 이름에 batch가 들어간 이 옵션이 손에 잡힌다. 벌크(bulk) 연산 문제 → 배치(batch) 옵션이라는 연상이 자연스럽기 때문이다. 실제로 이 오답은 면접에서 자주 나온다. 그런데 이 옵션은 벌크 연산과 아무 관계가 없고, 값을 채우는 기능은 더더욱 아니다.

// org.hibernate.cfg.BatchSettings
/**
 * Specifies the maximum number of {@linkplain java.sql.PreparedStatement statements}
 * to {@linkplain PreparedStatement#addBatch batch} together.
 * A nonzero value enables batching
 *
 * @settingDefault 0
 */
String STATEMENT_BATCH_SIZE = "hibernate.jdbc.batch_size";

핵심 단어는 "statements"(문장들)다. 이 옵션은 여러 개의 SQL 문장을 JDBC 드라이버 레벨에서 묶어 한 번에 전송한다(addBatch()로 쌓았다가 executeBatch()로 전송). 기본값은 0이며 이는 배칭 꺼짐을 뜻한다.

4-2. 진짜 교훈 — 도구는 "해결하는 것"과 "해결 못 하는 것"을 세트로 외운다

이 오적용은 지식 부족이 아니다. batch_size라는 이름을 최근에 정확히 배웠기 때문에 생긴 일이다. 새로 배운 도구는 적용 범위가 함께 고정되지 않으면 인접 문제로 번진다.

네 칸짜리 도구 카드 — "못 하는 것" 칸을 채우는 순간 그 도구는 잘못 집히지 않는다

도구는 항상 네 칸으로 외운다 — 이름 · 해결하는 것 · 해결하지 못하는 것 · 관측 신호
세 번째 칸이 비어 있는 도구는 언젠가 인접 문제에 잘못 집힌다

이 카드 습관이 "도구 이름이 부족하다"는 약점의 진짜 해법이다. 이름만 늘리면 오적용도 같이 늘어난다.

도구 카드 — batch_size가 이 문항에 잘못 집히는 이유는 세 번째 칸을 채워두지 않았기 때문이다
도구해결하는 것해결하지 못하는 것관측 신호

public int runDormantBatch() {

    LocalDateTime cutoff = now.minusYears(1);

2. 주체를 상수 문자열로 명시한다

3. @Modifying의 두 옵션은 이 문항의 처방이 아니다
flushAutomatically와 clearAutomatically는 둘 다 기본값 false이고 1차 캐시 정합성을 다루는 옵션이지 감사 컬럼과 무관하다. 다만 벌크를 쓰는 이상 그 문제도 동시에 존재하므로 함께 검토한다.

public int toDormantByDirtyChecking(LocalDateTime cutoff) {

5-1. 왜 배치 스레드에는 값이 없나 — ThreadLocal이라서다

SecurityContextHolder는 기본적으로 ThreadLocal 기반이다. ThreadLocal은 스레드마다 별개의 값을 갖는 저장소로, 스레드 A가 심어둔 값을 스레드 B가 읽을 수 없다. 스프링 시큐리티는 HTTP 요청을 받는 필터에서 인증 정보를 이 저장소에 심고 응답 후 지우는데, 심는 주체가 요청 처리 스레드라는 것이 핵심이다.

비유 — 사원증은 정문 게이트에서만 발급된다 웹 요청은 정문(시큐리티 필터)을 통과하면서 사원증을 받아 목에 걸고 다닌다. 그래서 어디서 뭘 바꾸든 방명록에 이름이 적힌다. 그런데 스케줄러 · 배치 워커 · @Async · 메시지 컨슈머 · 기동 시 초기화 코드는 정문을 통과하지 않고 건물 안에서 바로 시작된다. 사원증이 없다. 방명록(콜백)은 정상적으로 펼쳐지는데, 적을 이름이 없는 것이다.

5-2. 이때 실제로 채워지는 값 — null이 아니라 "직전 사람 이름"이다 시니어 변별

여기서 흔히 잘못 알려진 부분을 스프링 데이터 소스로 확정한다. AuditorAware가 Optional.empty()를 반환하면 필드에 null이 들어가는 것이 아니라, 필드를 아예 건드리지 않는다.

source spring-data-commons: AuditingHandlerSupport.touchAuditor()
private void touchAuditor(Auditor<?> auditor, AuditableBeanWrapper<?> wrapper, boolean isNew) {

    if (!auditor.isPresent()) {
        return;                    // setCreatedBy / setLastModifiedBy 를 아예 호출하지 않고 빠져나간다
    }
    if (isNew) {
        wrapper.setCreatedBy(auditor.getValue());
    }
    if (!isNew || modifyOnCreation) {
        wrapper.setLastModifiedBy(auditor.getValue());
    }
}

Optional.empty()는 Auditor.none()으로 변환되어 isPresent()가 false가 되고 첫 줄의 조기 리턴에 걸린다. 반면 바로 다음에 호출되는 시각 처리에는 이런 분기가 없어 시각은 정상으로 채워진다. 그래서 결과가 경우에 따라 갈린다.

상황updated_atupdated_by에 남는 값
배치가 새 행을 INSERT지금 시각으로 채워짐필드가 원래 null이었으므로 null로 저장
배치가 기존 행을 UPDATE지금 시각으로 채워짐직전에 들어 있던 값이 그대로 유지되어 다시 저장된다

두 번째 줄이 단순 누락보다 나쁘다

어제 admin이 웹 화면에서 고쳤던 행을 오늘 새벽 배치가 변경 감지 경로로 수정하면, 그 행은 updated_at = 오늘 04:00, updated_by = 'admin'이 된다. 행이 "admin이 오늘 새벽 4시에 이 데이터를 바꿨다"고 진술하게 되는 것이다. admin은 그 시각에 아무것도 하지 않았다.

비어 있는 기록은 "모른다"는 뜻이라도 되지만, 틀린 기록은 조사를 엉뚱한 방향으로 끌고 간다
감사 데이터에서는 이쪽이 훨씬 위험하다

5-3. 처방 — 시스템 주체를 명시적으로 심는다

방향은 하나다. Optional.empty()를 절대 반환하지 않게 만든다. 인증이 없는 경로에는 "인증이 없다"는 사실 자체를 값으로 기록한다.

before 인증이 없으면 손을 놓는다
@Bean
public AuditorAware<String> auditorProvider() {
    return () -> {
        Authentication auth = SecurityContextHolder
                .getContext().getAuthentication();
        if (auth == null || !auth.isAuthenticated()) {
            return Optional.empty();   // 조기 리턴 → 필드 미변경 → 옛 이름 유지
        }
        return Optional.of(auth.getName());
    };
}
after 인증이 없으면 시스템 주체로 폴백한다
@Bean
public AuditorAware<String> auditorProvider() {
    return () -> {
        Authentication auth = SecurityContextHolder
                .getContext().getAuthentication();
        if (auth == null || !auth.isAuthenticated()
                || "anonymousUser".equals(auth.getPrincipal())) {
            return Optional.of(SystemActorHolder.current());
        }                              // empty 를 반환하지 않는 것이 요점
        return Optional.of(auth.getName());
    };
}
good 실행 주체를 명시적으로 심는 홀더 — 배치 진입점에서 세팅한다
public final class SystemActorHolder {
    private static final ThreadLocal<String> ACTOR = new ThreadLocal<>();
    public static void set(String actor) { ACTOR.set(actor); }
    public static void clear()           { ACTOR.remove(); }
    public static String current()       { return ACTOR.get() != null ? ACTOR.get() : "SYSTEM"; }
}

@Scheduled(cron = "0 0 4 * * *")
public void dormantJob() {
    SystemActorHolder.set("BATCH_DORMANT");
    try {
        dormantService.run();
    } finally {
        SystemActorHolder.clear();      // 스레드 풀이 이 스레드를 재사용하므로 정리가 필수다
    }
}
finally의 clear()가 없으면
스레드 풀은 작업이 끝나도 스레드를 죽이지 않고 다음 작업에 재사용한다. ThreadLocal에 남겨둔 값은 그 스레드가 처리하는 완전히 무관한 다음 작업까지 따라간다. 그러면 웹 요청이 "BATCH_DORMANT"가 바꾼 것으로 기록될 수 있다.
empty를 반환하지 않는 것 자체가 설계 결정이다
null은 "기록에 실패했다"와 "시스템이 바꿨다"를 구분하지 못하지만, "SYSTEM"·"BATCH_DORMANT"는 조사 가능한 정보다. 그리고 5-2의 "옛 값이 그대로 남는" 사고도 이 폴백 하나로 사라진다 — 항상 값을 공급하면 조기 리턴에 걸릴 일이 없기 때문이다.
가산점 — @Async에 인증을 넘기고 싶다면 가산점 SecurityContextHolder의 전략을 MODE_INHERITABLETHREADLOCAL로 바꾸거나, 스프링 시큐리티가 제공하는 DelegatingSecurityContextExecutor 계열 래퍼로 실행기를 감싼다. 다만 스레드 풀에서는 컨텍스트가 다음 작업으로 새는 위험이 따라오므로, 배치에는 상속보다 위의 명시적 주입이 안전하다. "얻는 것(편의)과 포기하는 것(누수 위험)"을 같이 말하는 자리다.

6. 신뢰 경계 — 그리고 한 층 내리기(Envers · DB)

신뢰 경계(trust boundary)란 "이 안에서 일어난 일은 기록이 보장되고, 이 밖에서 일어난 일은 보장되지 않는다"고 선을 그을 수 있는 범위를 말한다. 감사 로그를 설계할 때 가장 먼저 정해야 하는 것이 이 선이다. 선을 안 그으면 "우리는 다 기록하고 있다"는 근거 없는 믿음이 생긴다.

사건 1 — 누군가 DB 콘솔에서 직접 UPDATE한다

새벽 장애 대응으로 운영자가 update member set status='ACTIVE' where id = 12345를 실행했다. 데이터는 바뀌고, updated_at도 updated_by도 아무 흔적을 남기지 않는다. 나중에 "이 회원 상태가 왜 바뀌었죠?"를 조사하면 감사 컬럼은 그 전에 애플리케이션이 마지막으로 바꿨던 시각과 사람을 가리킨다. 즉 엉뚱한 사람이 범인으로 지목된다.

사건 2 — 감사 기록을 만드는 코드가 감사 대상과 같은 손에 있다

애플리케이션 코드를 수정·배포할 수 있는 사람은 AuditorAware의 반환값도 바꿀 수 있고, @LastModifiedBy를 떼어낼 수도 있고, 벌크 쿼리로 감사 컬럼을 원하는 값으로 덮어쓸 수도 있다. 감시 카메라의 녹화 버튼이 감시 대상 방 안에 있는 구조다. 그래서 진짜 감사(監査)에서는 "애플리케이션이 스스로 남긴 기록"을 최종 증거로 인정하지 않는 경우가 있다.

6-1. 얻은 것과 포기한 것 — 부족한 것은 두 종류다

얻는 것

  • BaseEntity 한 줄로 전 엔티티 일괄 적용
  • DB 독립 — 벤더가 바뀌어도 그대로
  • 애플리케이션의 인증 정보를 그대로 주체로 사용
  • 테스트에서 시각을 고정할 수 있다

포기하는 것

  • 기록의 경계가 애플리케이션 안쪽 — 벌크·네이티브·JdbcTemplate·타 시스템·운영자 수동 SQL은 못 잡는다
  • 기록의 형태가 덮어쓰기식 — "언제 무엇이 무엇으로 바뀌었는지"의 이력이 없다(마지막 상태만)
  • 실패가 조용하다(3-1)
두 번째를 놓치기 쉽다 — updated_at 컬럼 하나로는 애초에 감사 요건을 만족하지 못한다 @LastModifiedDate는 가장 최근 수정 시각 하나만 갖는 컬럼이다. 두 번 수정되면 첫 번째 수정의 흔적은 두 번째가 덮어써서 사라진다. "3월 12일에 등급이 GOLD에서 SILVER로 바뀌었다"는 변경 내역은 어디에도 없다. 감사 요구는 대부분 이력을 요구한다 — "이 데이터가 언제 어떻게 변해왔는가"를 묻지 "마지막에 언제 바뀌었는가"만 묻지 않는다. 이 구분을 말할 수 있으면 "감사"라는 단어를 실제로 다뤄본 사람으로 읽힌다.

부족한 것을 두 축으로 갈라 두면, 도구 선택이 자동으로 정리된다

축 1 — 기록의 형태
덮어쓰기(마지막 상태) ↔ 전체 이력. 이걸 바꾸는 도구가 Envers다.
축 2 — 기록의 경계
애플리케이션 정상 경로만 ↔ 모든 경로. 이걸 바꾸는 도구는 DB(트리거·ON UPDATE)뿐이다.

6-2. 층위를 2축 지도로 — Envers는 세로로만 움직인다

6-3. Envers도 벌크에서 똑같이 빠진다 함정

Envers는 member_AUD 같은 이력 테이블과 리비전 메타 테이블을 만들고, 변경이 일어날 때마다 그 시점의 스냅샷을 한 행씩 적재한다. 그런데 Envers도 하이버네이트의 엔티티 이벤트(post-insert / post-update / post-delete) 리스너로 동작한다.

접미사가 Pre냐 Post냐만 다를 뿐, 둘 다 ④의 판정이 있어야 발생하는 이벤트다
판정이 없으면 Pre도 Post도 없다
@Modifying
@Query("update Member m set m.status = 'DORMANT' where ...")
int toDormantBulk(...);
// member 테이블은 바뀐다
// member_AUD 에는 리비전이 단 한 건도 안 생긴다. 예외도 경고도 없다.

6-4. DB로 내리면 무엇을 얻고 무엇을 포기하나

경계를 진짜로 넓히려면 애플리케이션 밖으로 나가야 한다. 애플리케이션을 통과하지 않는 변경까지 잡으려면, 기록하는 주체가 모든 변경이 반드시 지나가는 지점 즉 DB에 있어야 하기 때문이다.

-- (가) 컬럼 기본값 / ON UPDATE — MySQL이라면 DDL 한 줄로 시각 축을 모든 경로에 적용
ALTER TABLE member
  MODIFY updated_at TIMESTAMP NOT NULL
         DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP;

이러면 벌크든 네이티브든 JdbcTemplate이든 DB 콘솔이든 UPDATE가 나가는 순간 시각이 찍힌다. 다만 네 가지를 포기한다.

"누가"는 여전히 모른다
DB는 애플리케이션 사용자를 모른다. 아는 것은 DB 접속 계정뿐인데, 커넥션 풀을 쓰는 애플리케이션은 전부 같은 계정으로 붙는다.
벤더 종속이다
PostgreSQL에는 ON UPDATE 절 문법이 없어 BEFORE UPDATE 트리거를 직접 만들어야 한다.
JPA가 채운 값과 경합한다
엔티티에 그냥 매핑된 채로 두면 하이버네이트가 자기 값을 SET 절에 실어 보내 DB 기본값이 무력화된다. @Column(insertable = false, updatable = false) 등으로 소유권을 명시해야 한다. 소유권을 정하지 않은 이중 관리가 가장 나쁘다 — 값이 어디서 왔는지 아무도 모르게 된다.
같은 값으로 덮는 UPDATE에는 반응하지 않는다
MySQL의 ON UPDATE는 행의 다른 컬럼 값이 실제로 달라진 UPDATE에서만 갱신된다.
(나) 트리거 + 이력 테이블 — 모든 경로를 잡는 유일한 방법이지만 대가가 크다 ① 애플리케이션 세션 사용자를 트리거에 전달할 방법을 따로 만들어야 한다(세션 변수 등) — 그 전달 코드를 안 타는 경로에서는 다시 비어버린다. 즉 "누가"를 채우는 순간 경계 문제가 부분적으로 되돌아온다.
② 로직이 DDL에만 있어 코드 리뷰로 발견되지 않는다 — 애플리케이션 저장소를 아무리 뒤져도 안 나온다.
③ 스키마 마이그레이션 · 테스트 환경 구성이 무거워진다.

7. 안전망 — 예외가 안 나는 사고를 막는 유일한 방법

7-1. 실무 규칙 두 갈래 — 여기가 이 문항의 설계 답이다

경계를 완벽히 넓히는 것이 항상 가능하진 않다. 트리거를 못 쓰는 조직도 있고, 쓰더라도 "누가"는 여전히 새어나간다. 그래서 실무는 둘 중 하나(또는 둘 다)를 택한다.

① 감사 대상 엔티티에는 벌크 연산을 금지한다

성능이 아니라 정합성을 우선순위로 못 박는 규칙이다. 그리고 사람의 주의력이 아니라 도구로 고정한다(7-4의 ArchUnit 룰). 감사 대상 엔티티를 @Audited나 전용 마커 애노테이션으로 표시해두면 룰이 대상을 식별할 수 있다.

② 벌크가 불가피하면 이력 적재 경로를 함께 만든다

벌크 UPDATE와 같은 트랜잭션 안에서 이력 테이블에 insert into member_history select ... 형태로 한 문장을 더 넣는다. 그리고 두 문장이 서로를 검증하게 만든다.

good 벌크 + 이력 적재를 한 트랜잭션에 묶고, 건수 일치를 단정한다
@Transactional
public int runDormantBatch(LocalDateTime now) {
    // ① 바꾸기 전 상태를 이력 테이블에 통째로 적재 (한 문장)
    int archived = historyRepository.archiveDormantTargets(cutoff, now, "BATCH_DORMANT");

    // ② 벌크 UPDATE (감사 컬럼 포함)
    int updated  = memberRepository.toDormantBulk(cutoff, now, "BATCH_DORMANT");

    if (archived != updated) {                 // 두 문장의 where 조건이 어긋나면 트랜잭션째 롤백
        throw new IllegalStateException("이력 건수 불일치: " + archived + " vs " + updated);
    }
    return updated;
}

건수 일치 단정이 이 코드의 핵심이다 — 관측 지점이 없으면 만들어 넣는다

조용한 실패→두 문장이 서로를 검증→시끄러운 실패로 승격

3-1에서 본 이 문항의 본질적 위험 — "관측 지점 어디에도 신호가 없다" — 에 대한 직접적인 대응이다. 조건이 어긋나 이력이 누락되는 순간 배치가 즉시 실패한다.

7-2. "테스트로 막는다"의 구체적 형태 — 먼저 함정부터

이 사고는 예외가 나지 않는다. 그러므로 막는 방법은 하나뿐이다 — 단정(assertion)으로 고정하는 것. 다만 "테스트를 쓴다"는 방향만으로는 부족하고, 무엇을 어떻게 단정하느냐에서 갈린다.

bad 같은 트랜잭션에서 검증하면 오염된다
@Test

7-3. 시각을 고정하는 손잡이가 경로마다 다르다 시니어 변별

시각을 고정하면 isAfter 같은 느슨한 단정 대신 정확한 등치 비교가 가능해진다. 그런데 고정하는 방법이 경로에 따라 둘로 갈린다.

시각을 채우는 주체고정 방법
벌크 SET 절(4-3) — 내 코드가 now를 만든다LocalDateTime.now()를 직접 부르지 말고 Clock 빈을 주입받아 테스트에서 Clock.fixed(...)로 못 박는다
리스너(@LastModifiedDate) — 스프링 데이터가 시각을 만든다DateTimeProvider 빈을 만들어 @EnableJpaAuditing(dateTimeProviderRef = "fixedDateTimeProvider")로 지목한다
두 번째가 따로 존재하는 이유 — 리스너 경로의 시각은 내 코드가 만드는 값이 아니라 스프링 데이터 내부의 공급자가 만드는 값이라 Clock 빈을 아무리 갈아끼워도 바뀌지 않는다.
값을 만드는 주체가 다르면 고정하는 손잡이도 다르다

7-4. 회귀를 막는 세 겹 — 테스트 하나는 그 쿼리 하나만 지킨다

다음 사람이 벌크 쿼리를 하나 더 추가하면 다시 뚫린다. 그래서 세 겹으로 간다.

1
스키마로 막기 — 다만 한계를 정확히 알고 쓴다. 감사 컬럼을 NOT NULL로 두면 INSERT 경로의 누락이 즉시 실패가 된다(JdbcTemplate으로 감사 컬럼 없이 INSERT하면 그 자리에서 터진다). 조용한 실패가 시끄러운 실패가 되는 것이다. 다만 UPDATE 누락은 못 잡는다 — 옛날 값이 그대로 남아 있을 뿐 NULL이 아니기 때문이다. 5-2의 "직전 사람 이름이 남는" 경우도 NOT NULL을 통과한다. 4-2의 도구 카드와 같은 성질 — 이 제약이 무엇을 못 하는지 알고 써야 한다.
ALTER TABLE member

  MODIFY created_by VARCHAR(50) NOT NULL;
2

8. 증상 → 원인 역방향 인덱스

원리에서 증상을 유도하는 건 원리를 알면 누구나 한다. 실무에서 필요한 건 증상에서 원인으로 거슬러 올라가는 것이다.

증상원인확인 방법처방
특정 배치가 건드린 행만 updated_at이 옛날 값벌크/네이티브가 리스너 경로 우회 (2·3절)그 배치의 쿼리에 @Modifying이 붙어 있음SET 절에 updatedAt·updatedBy 명시 (4-3)

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

Auditing이 얹혀 있는 콜백 두 개?
@PrePersist · @PreUpdate. 부르는 주체는 하이버네이트가 flush 시점에 내리는 판정이다.
기록 여부 판정 기준 한 문장?
"영속성 컨텍스트가 엔티티 객체를 놓고 INSERT/UPDATE를 판정했는가." 표를 외우지 말고 이 기준을 외운다.
벌크에서 실제로 끊긴 칸?
④ 액션 결정(판정). ⑤ 콜백도 ⑥ 필드 채움도 ④가 없어서 없는 것이다. 끊는 곳은 언제나 맨 앞.
처방 두 갈래?
쓰거나 · 태우거나 — SET 절에 쓰거나, 변경 감지로 다시 태우거나. 중간 지대는 청크.
벌크가 인수인계시키는 목록?
감 · 버 · 캐 · 소 · 이 — 감사 컬럼 / @Version / cascade / soft delete / 이력(Envers) (+2차 캐시). 원리: "JPA를 우회한 변경은 JPA가 모른다."
batch_size가 무관한 두 이유?
① 값 채우는 옵션이 아니다(왕복 횟수를 줄이는 성능 옵션, 기본값 0) ② 이 벌크는 이미 문장 하나라 묶을 대상이 없다.
주체가 비는 두 방식?
경로 결손(벌크 — 콜백 자체가 없음) vs 값 결손(배치 스레드 — 콜백은 도는데 값이 없음). 후자는 벌크를 안 써도 발생한다.
AuditorAware가 empty를 주면?
null이 들어가는 게 아니라 필드를 아예 안 건드린다. 기존 행 UPDATE면 직전 사람 이름이 새 시각과 함께 다시 저장된다 → 빈 기록보다 나쁜 틀린 기록.
Envers가 바꾸는 축은?
기록의 형태(덮어쓰기 → 이력)만. 기록의 경계는 1mm도 안 넓어진다 — 벌크에서 똑같이 빠진다.
안전망 세 겹?
테스트(em.clear() 후 재조회 · 시각과 주체 둘 다 단정) · NOT NULL(INSERT 누락만 잡는다) · ArchUnit(다음에 추가될 쿼리까지 지킨다).
조용한 실패의 관측 신호?
전부 정상이다. 예외 없음 · 경고 없음 · 반환값 100000 · 배치 COMPLETED. 그래서 몇 달 뒤 감사 요청에서 발견된다.
시각을 고정하는 손잡이 두 개?
벌크 SET 절은 Clock 빈, 리스너 경로는 dateTimeProviderRef. 값을 만드는 주체가 다르면 손잡이도 다르다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

리스너는 정확히 언제 호출되나요? save()를 부른 시점인가요? 필수힌트: "저장 시점"이라고 답하면 반쯤 틀린다. 두 개의 파생 사실까지 얹는다

아니다. flush 시점이다. @PrePersist/@PreUpdate는 하이버네이트가 실제로 INSERT/UPDATE 문을 만들기 직전에 호출된다. save()를 부른 시각과 flush 시각 사이에 외부 API 호출이 3초 걸렸다면 createdAt은 3초 뒤 값이다.

그래서 두 가지가 따라온다. ① 변경이 없으면 UPDATE 자체가 안 나가므로 @PreUpdate도 없다 — 같은 값으로 다시 세팅하는 건 감사 이력을 남기지 않는다. ② 반대로 의도치 않은 dirty 판정이 생기면 아무도 수정하지 않은 행의 updatedAt이 갱신된다(BigDecimal scale 차이, 컬렉션 재할당, 컨버터의 왕복 비대칭).

따라서 "이 행이 왜 어제 수정된 걸로 나오죠?"라는 조사는 Auditing 설정이 아니라 dirty checking 쪽을 봐야 한다. 증상의 소관 부서를 정확히 지목하는 것이 이 답변의 값이다.

그럼 벌크 연산은 아예 쓰면 안 되나요? 필수힌트: 금지가 아니라 판단 기준을 제시한다. 기준은 "건수"가 아니다

아니다. 판단 기준은 "이 엔티티에 감사 요구가 걸려 있는가"다.

감사 요구가 없는 데이터
집계 캐시 컬럼, 조회수, 임시 플래그 → 벌크가 정답이다. 10만 건을 굳이 로드할 이유가 없다.
감사 요구가 있는 데이터
회원 상태, 권한, 개인정보, 금액 → 벌크를 쓰되 SET 절에 감사 필드를 명시하거나, 건수가 감당되면 변경 감지로 되돌린다.
감사 요구가 강하고 건수도 큰 경우
벌크 + 이력 테이블 직접 적재를 같은 트랜잭션에 묶고, 건수 일치를 단정해 누락이 즉시 실패가 되게 만든다.
핵심은 벌크의 금지가 아니라 — "벌크를 쓰는 순간 컨텍스트가 해주던 일 목록을 손으로 인수인계받는다"는 인식
감사 컬럼 · @Version · cascade · @SQLDelete · 2차 캐시 무효화 · Envers 리비전이 그 목록이다
감사 요구가 있는 데이터라면 애플리케이션 레벨 Auditing으로 충분한가요? 시니어 변별힌트: 부족한 것을 두 종류로 갈라 말하고, 마지막에 반드시 한 문장을 덧붙인다

충분하지 않다. 두 가지가 부족하다.

① 신뢰 경계가 애플리케이션 안쪽이다. 벌크·네이티브·JdbcTemplate·타 팀 배치·운영자의 수동 SQL은 잡지 못한다. "우리 코드가 정상 경로로 바꾼 것만" 기록되는데, 감사는 보통 "어떤 경로로든 이 데이터가 바뀌면"을 요구한다. 게다가 애플리케이션 코드를 바꿀 수 있는 사람은 감사 기록을 만드는 코드도 바꿀 수 있으므로, 감시 카메라의 녹화 버튼이 감시 대상 방 안에 있는 구조라는 점까지 말하면 신뢰 경계라는 개념을 실제로 이해한 것으로 읽힌다.

② 이력이 아니라 마지막 상태만 남는다. @LastModifiedDate는 최근 수정 시각 하나뿐이라 "3월 12일에 GOLD → SILVER"라는 변경 내역이 없다. 감사 요건은 대부분 내역을 요구하므로 애초에 요건을 만족하지 못한다.

그래서 층을 나눠 답한다. 이력 형태가 필요하면 Envers(@Audited → 리비전 테이블), 경계까지 넓혀야 하면 DB 트리거 + 이력 테이블.

그리고 반드시 덧붙일 것 — Envers도 벌크 연산에서는 똑같이 빠진다
Envers는 기록의 형태를 바꾸지만 기록의 경계는 전혀 바꾸지 않는다 — 이 구분이 이 질문의 변별점이다
@LastModifiedBy가 배치에서만 null입니다. 왜죠? 시니어 변별힌트: 원인을 답한 뒤 질문의 전제를 교정하면 확실히 갈린다

AuditorAware가 SecurityContextHolder에서 사용자를 꺼내는데, 그것은 ThreadLocal 기반이라 배치·스케줄러·@Async·메시지 컨슈머 스레드에는 인증 정보가 없기 때문이다. 벌크 여부와 무관한 별개의 구멍이며, 변경 감지 경로로 정상 동작하는 배치에서도 발생한다.

여기서 질문의 전제를 한 번 교정하면 확실히 갈린다 — 항상 null이 되는 것은 아니다. 스프링 데이터는 AuditorAware가 Optional.empty()를 반환하면 필드에 null을 쓰는 것이 아니라 필드를 아예 건드리지 않는다(touchAuditor()의 조기 리턴). 그래서 신규 INSERT면 null로 남지만, 기존 행 UPDATE면 직전에 들어 있던 사람 이름이 그대로 유지된 채 새 시각과 함께 다시 저장된다. 즉 그 행은 "그 사람이 방금 이걸 바꿨다"고 거짓 진술을 하게 된다. 비어 있는 기록보다 틀린 기록이 나쁘다.

처방 세 가지. ① AuditorAware에 시스템 주체 폴백을 넣어 empty 대신 "SYSTEM"·"BATCH_DORMANT" 같은 조사 가능한 값을 반환한다 — null은 "기록 실패"와 "시스템 변경"을 구분하지 못한다. ② 배치 진입점에서 실행 주체를 ThreadLocal에 명시적으로 심고 finally에서 지운다(스레드 풀 재사용 때문에 정리가 필수). ③ 웹 요청에서 분기한 비동기 작업에 인증을 전달해야 한다면 DelegatingSecurityContext… 계열 래퍼를 쓰되, 스레드 풀에서 컨텍스트가 다음 작업으로 새는 위험을 함께 인지한다.

hibernate.jdbc.batch_size를 올리면 이 문제가 해결되나요? 함정힌트: "아니다"로 끝내지 말고, 이 옵션이 의미를 갖는 자리까지 말한다

아니다. 문제의 종류가 다르다. batch_size는 여러 개의 SQL 문장을 JDBC 레벨에서 묶어 전송해 왕복 횟수를 줄이는 성능 옵션(기본값 0, 즉 꺼짐)이지 값을 채우는 기능이 아니다. 게다가 이 벌크 UPDATE는 이미 한 문장이라 묶을 대상 자체가 없다.

값이 채워지지 않는 원인은 리스너 경로를 안 탄 것이므로, 처방은 SET 절에 직접 쓰거나 변경 감지 경로로 되돌리는 것 둘 중 하나다.

다만 batch_size가 의미를 갖는 지점이 하나 있다 — 감사 컬럼 때문에 벌크를 포기하고 청크 단위 변경 감지로 바꾸면, 그때는 UPDATE 문장이 실제로 여러 개가 되므로 이 옵션이 제 일을 한다. 틀린 도구가 아니라 틀린 자리에 놓였던 도구다.

이 사고를 배포 전에 잡으려면 어떻게 하나요? 가산점힌트: "테스트를 쓴다"로는 부족하다. 무엇을 어떻게 단정하는지 + 겹의 개수

예외가 안 나는 사고이므로 단정으로 고정하는 수밖에 없다. 세 겹으로 간다.

1
테스트로 단정 — @Modifying 쿼리 실행 뒤 em.clear()로 1차 캐시를 비우고 재조회해 updatedAt과 updatedBy를 둘 다 검증한다. 비우지 않으면 벌크가 우회한 옛 객체를 보게 되어 테스트가 아무것도 증명하지 못한다. 시각은 고정한다 — 벌크 경로는 Clock.fixed, 리스너 경로는 dateTimeProviderRef로 손잡이가 다르다.
2
스키마로 승격 — 감사 컬럼을 NOT NULL로 두면 INSERT 누락이 즉시 실패한다. 단 UPDATE 누락은 못 잡는다(옛 값이 남을 뿐 NULL이 아니므로). 도구의 한계를 알고 쓴다.
3
구조 룰로 회귀 차단 — ArchUnit으로 @Modifying이 붙은 메서드가 감사 대상 엔티티를 건드리는지 검사한다. 테스트 하나는 그 쿼리 하나만 지키지만, 룰은 다음에 추가될 쿼리까지 지킨다.

여기에 p6spy로 실제 SQL을 관측하고 Testcontainers로 실제 DB에서 돌리면(트리거나 ON UPDATE를 쓰기로 했다면 벤더 동작이 곧 정답의 일부다) 완성된다.

네이티브 쿼리나 JdbcTemplate도 같은 문제가 있나요? 판단 기준을 하나로 말한다면? 가산점힌트: 기준 한 문장 + 함께 빠지는 것 목록 + 반대 방향의 도구

있다. 그리고 기준은 하나다 — "영속성 컨텍스트가 이 엔티티를 놓고 INSERT/UPDATE를 판정했는가." 판정이 있으면 리스너가 호출되고, 없으면 안 된다. 벌크 JPQL · 네이티브 쿼리 · JdbcTemplate · MyBatis · DB 콘솔은 전부 판정이 없다.

같은 이유로 함께 빠지는 것들: @Version 증가, cascade/orphanRemoval, soft delete의 @SQLDelete, @PreRemove 같은 다른 생명주기 콜백, 2차 캐시 무효화, Envers 리비전. 한 문장으로 묶으면 "JPA를 우회한 변경은 JPA가 모른다." 이렇게 답하면 지식이 조각이 아니라 원리로 들린다.

그리고 여기서 반대 방향의 도구도 하나 알고 있으면 좋다 — DB의 ON UPDATE CURRENT_TIMESTAMP나 트리거는 정확히 이 경계를 넘는 유일한 수단이다. 대신 "누가"는 못 채우고, 벤더에 묶이며, 로직이 DDL에만 있어 코드 리뷰에 안 보인다. 얻는 것과 포기하는 것이 정확히 반대인 도구다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

벌크 SET 절에 :now 대신 current_timestamp를 쓰면 안 되나요? 함정힌트: "동작은 한다." 그런데 무엇을 잃는지 두 개를 대야 한다

동작은 한다. 그런데 두 가지를 잃는다.

① 배치 전체가 같은 시각을 공유하지 못한다. 배치가 여러 쿼리로 쪼개져 있거나(대상 분할, 재시도, 청크) 실행에 몇 분이 걸리면 행마다 시각이 조금씩 달라진다. 나중에 "이 배치가 바꾼 건들"을 시각으로 묶어 조회하려 할 때 구간을 잡아야 하고, 그 구간 안에 다른 변경이 섞여 들어온다. 밖에서 now를 주입하면 그 배치가 만든 행들이 정확히 같은 타임스탬프를 공유하므로 이력이 한 덩어리로 읽힌다.

② 테스트에서 등치 비교로 단정할 수 없다. DB 함수가 만든 값은 테스트가 통제할 수 없으므로 isAfter(before) 같은 느슨한 단정밖에 못 쓴다. 느슨한 단정은 "시각이 갱신되긴 했다"까지만 증명하고 "의도한 그 시각인가"는 증명하지 못한다. Clock을 주입해 고정하면 isEqualTo(now)로 못 박을 수 있다.

같은 논리가 주체에도 적용된다 — 주체를 'BATCH_DORMANT'처럼 상수로 명시하면 updated_by 하나로 그 배치가 바꾼 건을 통째로 골라낼 수 있다. 감사 데이터는 "남기는 것"이 목적이 아니라 "나중에 조회 가능한 형태로 남기는 것"이 목적이다.

@CreatedDate에 @Column(updatable = false)는 왜 붙이나요? 안 붙이면 무슨 일이 생기나요? 가산점힌트: 하이버네이트가 UPDATE 문의 SET 절에 무엇을 싣는지를 떠올린다

붙이면 그 컬럼이 UPDATE 문의 SET 절에서 통째로 빠진다. 하이버네이트는 기본적으로 엔티티의 매핑된 컬럼 전부를 SET 절에 싣기 때문에, 안 붙이면 수정할 때마다 created_at도 함께 다시 쓰인다. 보통은 같은 값을 다시 쓰는 것이라 티가 안 난다.

문제는 "엔티티가 들고 있는 값이 원본과 다를 때"다. 준영속 객체를 병합하거나 일부 필드만 채운 객체로 갱신하는 경로에서 createdAt이 비어 있으면, 그 빈 값이 그대로 SET 절에 실려 나가 생성 시각을 덮는다. 그리고 생성 시각은 한 번 잃으면 복구할 수 없다.

updatable = false는 값을 지키는 장치가 아니라 덮어쓸 수 있는 경로 자체를 없애는 장치다
감사 데이터의 원칙 — 생성 축(createdAt·createdBy)은 불변으로 못 박고, 수정 축만 움직이게 한다
@EntityListeners를 BaseEntity에 붙이는 것과 엔티티마다 직접 붙이는 것의 차이는? 함정힌트: 동작 차이가 아니라 실패 모드의 차이다

동작 자체는 같다. @EntityListeners는 상속되므로 BaseEntity에 한 번 붙이면 Member·Order·Payment 전부에 콜백이 등록되고, 각 엔티티에 직접 붙여도 결과는 동일하다.

차이는 실패 모드다. 직접 붙이는 방식은 새 엔티티를 만든 사람이 빠뜨리는 순간 그 엔티티만 조용히 Auditing이 꺼진다. 그리고 이 실패도 예외가 없다 — 다른 엔티티들은 잘 채워지고 있으니 기능이 켜져 있다고 착각하기 딱 좋다. 증상은 "특정 엔티티만 감사 컬럼이 비어 있다"로 나타난다.

그래서 BaseEntity 상속이 기본값이지만, 그 편의성에 대가가 있다는 것도 같이 알아야 한다 — 한 줄로 전 엔티티에 켜지는 만큼 "어디까지 적용되는지"에 대한 감각이 흐려진다. "우리는 전부 Auditing이 걸려 있다"는 믿음이 신뢰 경계를 착각하게 만드는 출발점이 된다(6절).

감사 컬럼 타입을 LocalDateTime으로 둬도 괜찮나요? 가산점힌트: 이 타입에 없는 정보가 무엇인지 생각한다

LocalDateTime에는 시간대(offset) 정보가 없다. 즉 2026-03-12T04:00이라는 값만 남고 "어느 지역 기준 4시인가"는 값 안에 들어 있지 않다. 그 해석은 애플리케이션 서버와 DB의 타임존 설정에 의존한다.

평소에는 문제가 없다가, 다음 상황에서 해석이 흔들린다. 서버 타임존 설정이 바뀌거나, 인스턴스마다 타임존이 다르거나, 여러 지역에서 쓰거나, 서머타임을 쓰는 지역이 섞이는 경우다. 그리고 감사 데이터는 "나중에 다시 해석되는 데이터"라서, 기록 시점의 맥락 없이도 시점이 확정되어야 한다.

그래서 실무에서는 저장 기준을 하나로 못 박는다 — 시점 자체를 담는 타입(Instant·OffsetDateTime)을 쓰거나, LocalDateTime을 유지하되 애플리케이션·DB의 타임존을 UTC로 고정하고 그 규칙을 문서화한다. 중요한 것은 어느 쪽을 고르든 "이 컬럼의 기준이 무엇인지"가 코드와 문서에 명시되어 있는 것이다. 기준이 없는 타임스탬프는 조사할 때 가장 먼저 신뢰를 잃는다.

감사 이력을 남기려고 @PreUpdate 안에서 이력 테이블에 직접 INSERT해도 되나요? 시니어 변별힌트: 콜백이 실행되는 그 순간에 하이버네이트가 무엇을 하는 중인지 떠올린다

권장되지 않는다. 생명주기 콜백은 하이버네이트가 flush를 진행하며 SQL을 만들고 있는 도중에 호출된다. 그 안에서 EntityManager나 리포지토리를 호출해 새 엔티티를 저장하거나 쿼리를 실행하면, 진행 중인 flush 과정에 개입하는 것이 된다. JPA 명세도 콜백 안에서 EntityManager·쿼리 조작을 하지 않도록 규정하고 있다. 실제 증상은 동작하는 것처럼 보이다가 특정 순서에서만 깨지는 형태로 나타나서 원인 추적이 매우 어렵다.

그러면 이력은 어디서 남기나. ① Envers — 이 용도로 만들어진 도구이고 리비전 테이블 적재를 스스로 처리한다. ② 도메인 이벤트 + 트랜잭션 동기화 — 콜백 안에서는 이벤트만 등록하고, 실제 적재는 커밋 시점(또는 커밋 이후)에 별도로 수행한다. ③ 벌크 경로라면 7-1처럼 이력 적재 SQL을 같은 트랜잭션에 한 문장 더 넣는다.

원칙으로 정리하면 — 콜백은 "지금 만들어지고 있는 그 문장에 값을 채우는 일"까지만 한다. AuditingEntityListener가 하는 일이 정확히 그것이다(필드 세팅뿐, 쿼리 실행 없음). 그 선을 넘는 순간 flush 과정과 싸우게 된다.

한 줄 요약
JPA Auditing은 마법이 아니라 @PrePersist/@PreUpdate 콜백에 얹힌 코드이고, 그 콜백은 "영속성 컨텍스트가 이 엔티티를 INSERT/UPDATE 대상으로 판정한 순간"에만 발생한다 — 그래서 판정을 거치지 않는 벌크 JPQL·네이티브·JdbcTemplate·수동 SQL에서는 예외도 경고도 실패 카운트도 없이 조용히 빠지고, 배치는 "10만 건 성공"으로 정상 종료한다. 처방은 쓰거나(SET 절에 m.updatedAt = :now, m.updatedBy = :actor) 태우거나(변경 감지로 되돌리기) 둘뿐이며, hibernate.jdbc.batch_size는 이 문제와 교집합이 없다(문장이 여러 개일 때 왕복을 줄이는 옵션인데 이 벌크는 이미 한 문장이다 — 다만 청크 단위 변경 감지로 바꾸면 제 일을 한다). 시각만 고치면 절반이다 — @LastModifiedBy도 같은 원인으로 빠지고, 그와 별개로 AuditorAware는 ThreadLocal 기반 SecurityContextHolder에 의존하므로 배치·스케줄러·@Async 스레드에서는 벌크가 아니어도 주체를 공급하지 못하며, 이때 스프링 데이터는 null을 쓰는 게 아니라 필드를 건드리지 않아 직전 사람 이름이 새 시각과 함께 다시 저장된다 — 빈 기록보다 나쁜 틀린 기록이므로 시스템 주체 폴백이 필요하다. 마지막으로 애플리케이션 레벨 Auditing은 신뢰 경계가 애플리케이션 안쪽이고 마지막 상태만 남긴다 — 형태가 부족하면 Envers, 경계를 넘어야 하면 DB 트리거/ON UPDATE(대신 "누가"를 잃고 벤더에 묶인다)로 내리되 Envers도 벌크에서는 똑같이 빠진다는 것을 반드시 함께 말해야 하고, 이 모든 규칙은 em.clear() 이후 재조회해 시각과 주체를 둘 다 단정하는 테스트와 ArchUnit 룰로 고정하기 전까지는 다음 사람이 벌크 쿼리를 하나 더 추가하는 순간 조용히 무너진다.
