엔티티 직접 노출 금지 — "이유를 대라"에는 반드시 세 층으로 답한다

📖 약 39분 🧩 8개 섹션 0/8 섹션 이해
🎯 핵심 관전 포인트

이 질문은 지식 문제가 아니라 전개 문제다. 이유를 하나만 대고 멈추면, 아는 사람이어도 "규율이 몸에 배지 않은 사람"으로 읽힌다. 항상 세 층으로 답한다. 1층 기술적 사고 — 지연 로딩 필드를 Jackson이 건드리는 순간 OSIV가 꺼져 있으면 LazyInitializationException이고, OSIV가 켜져 있으면 예외가 안 나는 대신 직렬화기가 연관을 타고 들어가며 쿼리를 계속 날린다. 조용한 실패가 더 나쁘다. 여기에 양방향 연관의 순환 참조(무한 재귀)와 하이버네이트 프록시 직렬화 실패가 붙는다. 2층 설계·결합도 — API 스펙이 DB 스키마에 묶인다. 컬럼명을 바꾸면 클라이언트가 깨지고, 화면 요구가 바뀌면 테이블을 건드리게 된다. 더 근본적으로 엔티티 구조와 화면 요구는 애초에 다른 축이라, 화면이 여러 애그리거트를 조합해야 하면 엔티티 하나로는 표현 자체가 불가능하다. 3층 보안·운영 — 실무에서 가장 강력한 논거가 여기 있다. 엔티티 노출은 opt-out이라, 누군가 엔티티에 internalMemo·settlementRate를 추가하는 순간 응답 코드를 아무도 건드리지 않았는데 그 필드가 API로 새어 나간다. DTO는 opt-in이라 명시한 것만 나간다 — 사고가 나려면 누군가 의도적으로 코드를 써야 한다. 실수의 방향이 반대다. 그리고 요청 방향은 더 위험하다 — @RequestBody Member member로 받으면 클라이언트가 role: "ADMIN"을 실어 보내 덮어쓴다(mass assignment). @JsonIgnore는 답이 아니다 — 엔티티에 박히는 전역 스위치라 API마다 다른 요구를 표현할 수 없고, 더 근본적으로는 엔티티를 도메인 모델이 아니라 응답 템플릿으로 만든다. 마지막으로 규율은 사람이 아니라 빌드가 지킨다 — ArchUnit으로 컨트롤러의 반환 타입과 @RequestBody 파라미터 양쪽에서 엔티티를 금지한다.

면접 질문

"엔티티를 API 응답으로 직접 노출하면 안 되는 이유는?"

출제 의도rationale은 이렇게 적고 있다 — "엔티티 직접 노출 금지 — API 스펙이 DB 스키마에 종속되는 문제, 지연 로딩 직렬화 폭탄, 순환 참조 — '계층 간 경계'를 지키는 규율이 있는지의 리트머스."

여기서 주목할 단어는 "리트머스" 다. 이 질문은 어려운 지식을 묻는 게 아니다. 정답에 해당하는 항목들(N+1, 순환 참조, 결합도, 보안)은 하나하나 떼어놓고 물으면 대부분 답한다. 그런데도 이 문항이 변별력을 갖는 이유는, 묻지 않아도 여러 층을 한 호흡에 나열하는가가 곧 규율의 유무이기 때문이다. 계층 경계를 지키는 습관이 몸에 밴 사람은 "왜 안 되나"라는 질문에 기술적 사고 → 설계 → 보안을 자동으로 훑는다. 반대로 가장 최근에 겪은 이유 하나만 대고 멈추면, 지식은 있어도 그것이 원칙으로 조직되어 있지 않다는 신호가 된다.

함정 두 개:

  • 가장 좁은 이유 하나로 마감하는 것. 특히 "OSIV를 끄면 직렬화 예외가 난다"는 참이지만 가장 약한 논거다. 상대가 "우리는 OSIV를 켜두는데요?"라고 한마디만 받아치면 논거 전체가 무너진다. 설정 하나로 반박당하는 이유를 첫 번째로 꺼내면 안 된다. (실제로 이 반론은 실무 코드리뷰에서 그대로 나온다.)
  • @JsonIgnore로 해결된다는 반론에 "그건 안 됩니다"라고만 답하는 것. 이 반론은 현업에서 매우 자주 나오고, 부분적으로는 맞다(순환 참조와 지연 로딩은 실제로 막힌다). 그래서 "동작이 안 된다"가 아니라 "동작해도 문제" 라는 층에서 답해야 한다. §5가 통째로 이 반론에 배정된 이유다.

1-1. 왜 하나만 대면 감점인가

면접관이 "이유는?"이라고 물을 때 기대하는 것은 이유 목록이 아니라 이유를 분류하는 축이다. 축이 있는 사람은 하나를 말한 뒤 자연스럽게 "그건 기술적인 문제고, 설계 관점에서는…"으로 넘어간다. 축이 없는 사람은 가장 최근에 겪은 사례 하나를 말하고 멈춘다.

그래서 이 문항은 암기할 목록이 아니라 외울 골격으로 접근한다.

text
1층  기술적 사고   — 직렬화기가 무엇을 하는가 (지연 로딩 / 순환 참조 / 프록시)
2층  설계·결합도   — API 스펙이 DB 스키마에 묶인다 (변경의 이유가 다른 두 축)
3층  보안·운영     — 실수의 방향이 반대다 (opt-out vs opt-in / mass assignment)

세 층은 난이도 순서가 아니라 파급 범위 순서다. 1층은 그 엔드포인트 하나가 느려지거나 터진다. 2층은 시스템 전체의 변경 비용이 올라간다. 3층은 사고가 난다. 그래서 면접에서 3층까지 도달하는 사람이 드물고, 도달하면 그 자체가 변별점이 된다.

1-2. 30초 답변 스크립트

세 층을 실제 말로 옮기면 이 정도다. 이 분량을 첫 답변으로 낸 뒤 꼬리질문을 기다리면 된다.

"이유는 세 층으로 나눠 말씀드리겠습니다.

기술적으로는, JSON 직렬화기가 엔티티의 모든 게터를 호출하기 때문에 지연 로딩 필드를 건드립니다. OSIV가 꺼져 있으면 LazyInitializationException이 나고, 켜져 있으면 예외 대신 연관을 타고 들어가며 쿼리가 폭증합니다. 예외가 안 나는 쪽이 더 위험합니다. 양방향 연관이면 순환 참조로 무한 재귀가 나고, 아직 초기화 안 된 프록시 객체는 직렬화 자체가 실패합니다.

설계 관점에서는, API 스펙이 DB 스키마에 묶입니다. 컬럼 이름 하나 바꾸면 클라이언트가 깨지고, 반대로 화면 요구가 바뀌면 테이블을 건드리게 됩니다. 더 근본적으로는 엔티티 구조와 화면 요구가 애초에 다른 축이라, 화면이 서로 연관관계도 없는 데이터를 조합해야 하면 엔티티 하나로는 표현 자체가 불가능합니다.

그리고 보안·운영 관점이 실무에서는 가장 강력합니다. 엔티티 노출은 opt-out 구조라서, 누군가 엔티티에 정산율이나 내부 메모 필드를 추가하는 순간 응답 코드를 아무도 건드리지 않았는데 그게 API로 새어 나갑니다. DTO는 opt-in이라 명시한 것만 나가고요. 실수의 방향이 반대입니다. 요청 방향은 더 위험해서, @RequestBody로 엔티티를 받으면 클라이언트가 role이나 포인트 값을 실어 보내 덮어쓸 수 있습니다."

2-1. 먼저 전제 하나 — 직렬화기는 모든 게터를 호출한다

Jackson은 객체를 JSON으로 바꿀 때 그 객체의 프로퍼티를 전부 훑는다. 게터가 있으면 호출하고, 반환값이 또 객체면 그 안으로 들어가 같은 일을 반복한다. "필요한 것만 골라 읽는다"는 개념이 없다.

이게 모든 문제의 출발점이다. 코드에는 return order; 한 줄뿐이지만, 실제로 호출되는 게터는 getMember(), getItems(), 그리고 그 안의 getItem()…까지 연관 그래프 전체다. 코드에는 안 보이는 호출이라는 점이 중요하다 — "우리 컨트롤러는 order.getMember()를 부르지 않는데요?"라는 항변이 통하지 않는 이유다.

java
// ❌ 코드에는 게터 호출이 한 줄도 없다. 그런데 실제로는 그래프 전체를 순회한다.
@GetMapping("/orders/{id}")
public Order get(@PathVariable Long id) {
    return orderRepository.findById(id).orElseThrow();
}

2-2. OSIV가 꺼져 있으면 — 예외

Order.member가 LAZY라면 getMember()는 아직 데이터가 안 채워진 프록시를 돌려준다. 프록시가 실제 값을 가져오려면 영속성 컨텍스트(EntityManager)가 살아 있어야 하는데, OSIV가 꺼져 있으면 서비스 트랜잭션이 끝나는 순간 이미 닫혔다. 그래서 직렬화 시점에 LazyInitializationException이 난다(Spring MVC에서는 보통 HttpMessageNotWritableException에 감싸여 올라온다).

여기서 실무적으로 고약한 지점 하나. 직렬화는 응답 본문을 이미 쓰기 시작한 뒤에 일어난다. 상태 코드와 헤더가 이미 나간 뒤에 예외가 터지면 500으로 바꿔 줄 수도 없어서, 클라이언트는 200 OK와 함께 중간에 잘린 JSON을 받는다. 로그에는 예외가 찍히는데 클라이언트 쪽 증상은 "가끔 JSON 파싱이 깨짐"으로 나타나 원인 추적이 오래 걸린다.

💡

확인 범위: 응답이 이미 커밋된 뒤에 예외가 나면 상태 코드를 바꿀 수 없다는 것은 서블릿 스펙 수준의 성질이지만, 실제로 헤더가 언제 flush되는지는 응답 크기·버퍼 설정에 따라 달라진다. 작은 응답은 버퍼 안에서 끝나 정상적으로 500이 나가기도 한다.

자세한 메커니즘은 LazyInitializationException과 OSIV 트레이드오프와 전환에 있다.

2-3. OSIV가 켜져 있으면 — 예외가 안 난다. 그게 더 나쁘다

이 문항의 첫 번째 변별점이 여기다. "우리는 OSIV를 켜두니까 그 예외는 안 나는데요?" 라는 반론에 무너지지 않으려면, 예외가 안 나는 상태가 무엇인지를 정확히 말할 수 있어야 한다.

OSIV가 켜져 있으면 영속성 컨텍스트가 응답 완료까지 열려 있으므로 프록시 초기화가 성공한다. 성공한다는 건 그 자리에서 SELECT가 나간다는 뜻이다. 직렬화기는 멈추지 않으므로 다음 연관, 그 다음 연관으로 계속 들어간다.

java
@Entity
class Order {
    @ManyToOne(fetch = LAZY) private Member member;
    @OneToMany(mappedBy = "order", fetch = LAZY) private List<OrderItem> items;
}

@Entity
class OrderItem {
    @ManyToOne(fetch = LAZY) private Order order;   // 역방향
    @ManyToOne(fetch = LAZY) private Item item;
}

주문 20건을 목록으로 반환한다고 하자. 직렬화기가 그리는 쿼리 곡선은 이렇다.

text
1   회  : 주문 20건 조회
+20 회  : 각 주문의 member 초기화          ← 직렬화기가 getMember() 를 부를 때마다
+20 회  : 각 주문의 items 초기화           ← getItems() 를 부를 때마다
+60 회  : 각 OrderItem 의 item 초기화      ← 주문당 항목 3개 가정
--------------------------------------------------
101 회  : 응답 하나에 SELECT 101 번

전형적인 N+1이고, 심지어 중첩된 N+1이다. 자세한 탐지·대응은 N+1 탐지와 해결에 있다.

여기서 반드시 말해야 할 한 문장.

💡

예외가 나는 쪽보다 예외가 안 나는 쪽이 더 위험하다. 실패가 조용해질 뿐 비용은 오히려 커진다.

예외는 시끄럽다. CI에서 걸리고, 스테이징에서 걸리고, 안 걸려도 500 에러로 즉시 드러난다. 반면 OSIV가 켜진 상태의 쿼리 폭증은 정상 응답 200을 내면서 일어난다. 로컬에서는 데이터가 적어 체감이 안 되고, 운영에서 트래픽이 붙어야 커넥션 풀이 말라붙는다. 그때는 원인이 "특정 엔드포인트의 JSON 직렬화"라는 걸 아무도 떠올리지 못한다 — 코드 어디에도 그 쿼리를 부른 줄이 없기 때문이다.

부작용이 하나 더 있다. 직렬화 시점의 쿼리는 트랜잭션이 커밋된 뒤에 나간다. 즉 응답 본문 안에서 앞부분과 뒷부분이 서로 다른 시점의 데이터를 담을 수 있다. 정합성이 필요한 화면이라면 이것만으로도 결함이다.

2-4. 양방향 연관의 순환 참조 — 무한 재귀

Order.items → OrderItem.order → Order.items → … 직렬화기는 이 고리를 빠져나오지 못한다. 결과는 StackOverflowError(Jackson은 보통 Infinite recursion 메시지가 담긴 JsonMappingException으로 감싼다)다.

json
{"id":1,"items":[{"id":10,"order":{"id":1,"items":[{"id":10,"order":{ ...

이건 성능 문제가 아니라 즉시 터지는 버그라서 대개 개발 단계에서 잡힌다. 그래서 여기서 @JsonIgnore를 붙이는 관행이 생기고 — §5의 반론으로 이어진다.

2-5. 프록시 객체 자체가 직렬화되지 않는다

지연 로딩 필드를 초기화하지 않은 채 직렬화하면, Jackson이 보는 것은 Member가 아니라 하이버네이트가 만든 자식 클래스(프록시) 다. 이 프록시에는 원본에 없던 hibernateLazyInitializer, handler 같은 내부 프로퍼티가 붙어 있고, Jackson은 그걸 직렬화하려다 실패한다.

text
InvalidDefinitionException: No serializer found for class
  org.hibernate.proxy.pojo.bytebuddy.ByteBuddyInterceptor

증상이 지연 로딩 예외와 헷갈리기 쉽지만 원인이 다르다 — "값을 못 가져와서"가 아니라 "객체의 모양이 예상과 달라서" 나는 실패다. 그리고 이걸 막으려고 엔티티에 @JsonIgnoreProperties({"hibernateLazyInitializer", "handler"})를 붙이는 관행이 생기는데, 엔티티에 ORM 구현체 내부 사정과 직렬화 라이브러리 사정이 동시에 새겨진다는 점에서 이미 신호가 나쁘다.

2-6. 1층 정리 — 그리고 1층만 말하면 왜 부족한가

1층의 세 가지는 전부 "직렬화기가 무엇을 하는지" 하나에서 파생된다. 그래서 설명하기 쉽고 인상적이다. 하지만 1층은 전부 우회 가능하다 — 순환 참조는 @JsonIgnore로, 지연 로딩은 fetch join이나 Hibernate5Module로, 프록시는 @JsonIgnoreProperties로 막힌다.

우회 가능한 이유만 대면, 상대가 우회책을 제시하는 순간 논거가 사라진다. 2층과 3층은 우회할 수 없는 이유들이다. 그래서 반드시 올라가야 한다.

3

2층 — 설계·결합도: API 스펙이 DB 스키마에 묶인다

▾

3-1. 종속은 양방향으로 아프다

엔티티를 그대로 반환하면 테이블 구조가 곧 API 계약이 된다. 이 종속은 양쪽으로 비용을 만든다.

DB → API 방향: 컬럼명 user_nm을 user_name으로 바꾸는 리팩터링이 클라이언트를 깨뜨린다. 정규화를 위해 Order.address 문자열을 Address 값 객체로 분리했더니 응답 JSON 모양이 바뀐다. 순수한 내부 리팩터링이 외부 호환성 이슈가 된다 — 그러면 결국 아무도 스키마를 손대지 않게 되고, 나쁜 스키마가 굳는다.

API → DB 방향: 화면이 "주문자 이름 옆에 등급 뱃지"를 요구하면, 응답에 그 필드를 태우기 위해 엔티티에 필드를 붙이거나 연관을 새로 만들게 된다. 표현 계층의 요구가 테이블 설계를 끌고 다닌다.

java
// ❌ 엔티티가 그대로 계약이 된다
@GetMapping("/orders/{id}")
public Order get(@PathVariable Long id) { ... }
// → 컬럼명 변경 = API 파괴 변경(breaking change)
// → 화면 요구 추가 = 엔티티 수정

// ✅ 계약을 따로 세운다
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable Long id) {
    return orderService.getOrder(id);        // 서비스가 DTO 를 반환
}

public record OrderResponse(
        Long orderId,
        String status,
        String ordererName,       // 엔티티 필드명과 달라도 된다
        int totalPrice) { }
// → 컬럼명이 바뀌어도 매핑 한 줄만 고치면 계약은 그대로

DTO는 번역 계층이다. 안쪽 이름과 바깥쪽 이름을 분리해 두면, 양쪽이 각자의 이유로 자유롭게 변할 수 있다.

3-2. 더 근본적인 이유 — 두 구조는 애초에 다른 축이다

여기가 이 문항에서 가장 깊은 논거이고, 면접에서 이걸 스스로 꺼내면 상위권 신호다. (모의면접 5-3에서 후보자가 유도 없이 직접 도출한 논거이기도 하다.)

엔티티는 "데이터를 어떻게 저장하고 정합성을 지킬 것인가" 로 구조가 결정된다. 정규화, 애그리거트 경계, 트랜잭션 단위가 그 축이다.

화면은 "사용자가 한 번에 무엇을 봐야 하는가" 로 구조가 결정된다. 이 축은 저장 구조와 아무 상관이 없다.

두 축은 우연히 겹칠 수는 있어도 같아질 수는 없다. 그래서 다음 결론이 나온다.

💡

화면이 서로 연관관계도 없는 여러 애그리거트의 데이터를 조합해야 한다면, 엔티티 하나로는 그 응답을 표현하는 것 자체가 불가능하다.

이건 "불편하다"가 아니라 "불가능하다" 라는 점이 중요하다. 1층·3-1은 정도의 문제지만 이건 종류의 문제다. 예를 들어 주문 상세 화면이 이런 것들을 한 화면에 요구한다고 하자.

  • 주문 정보 (Order 애그리거트)
  • 배송 추적 상태 (외부 택배사 API 응답 — DB에 아예 없다)
  • 이 상품을 산 다른 사람들의 평균 별점 (Review 집계 — Order와 연관관계 없음)
  • 지금 적용 가능한 쿠폰 (Coupon 애그리거트 + 실시간 정책 계산)

Order에 이걸 다 매달 수는 없다. 매달면 그건 이미 엔티티가 아니라 응답 템플릿이다. 애그리거트 경계를 지키면 지킬수록 화면과의 간극은 오히려 커지므로, DTO는 좋은 설계의 부산물이지 나쁜 설계의 우회로가 아니다.

java
// ✅ 여러 출처를 조합하는 응답 — DTO 가 아니면 표현할 방법이 없다
public record OrderDetailResponse(
        OrderSummary order,             // DB (Order 애그리거트)
        DeliveryStatus delivery,        // 외부 택배사 API
        double averageRating,           // Review 집계 쿼리
        List<CouponOption> coupons) { } // Coupon 애그리거트 + 정책 계산

이 논거의 좋은 점은 반박이 불가능하다는 것이다. @JsonIgnore로도, OSIV로도, Jackson 모듈로도 우회할 수 없다. 존재하지 않는 연관을 직렬화할 방법은 없기 때문이다. 그래서 @JsonIgnore 반론에 대한 가장 강한 응답이 되기도 한다.

3-3. "변경의 이유가 다르면 분리한다"

2층 전체를 한 문장으로 압축하면 이렇다.

💡

엔티티가 바뀌는 이유와 API 응답이 바뀌는 이유는 서로 다르다. 그래서 두 개여야 한다.

엔티티는 저장·정합성 요구가 바뀔 때 바뀌고, 응답은 화면·클라이언트 요구가 바뀔 때 바뀐다. 하나로 합쳐두면 한쪽 이유로 바뀔 때마다 반대쪽이 영향을 받는다. DTO 클래스가 늘어나는 것은 비용이 아니라 그 두 이유를 분리해 산 값이다.

4

3층 — 보안·운영: 실수의 방향이 반대다

▾

이 층이 실무에서 가장 강력하고, 면접에서 가장 적게 언급된다. 앞의 두 층은 "성능이 나빠진다", "유지보수가 힘들어진다"라는 정도의 문제지만, 이 층은 사고다.

4-1. opt-out vs opt-in — 이 문항에서 가장 강력한 한 문장

두 방식의 차이를 딱 한 줄로 못 박자.

💡

엔티티 노출은 opt-out(빼고 싶은 것을 빼는) 구조이고, DTO는 opt-in(넣고 싶은 것만 넣는) 구조다. 실수했을 때 벌어지는 일의 방향이 정반대다.

무슨 뜻인지 시간 순서로 보자. 6개월 전, 누군가 Member를 그대로 반환하는 API를 만들었다. 그때는 문제가 없었다 — 이름, 이메일, 가입일뿐이었으니까.

java
// t0 — 문제 없어 보이는 코드
@Entity
public class Member {
    private Long id;
    private String name;
    private String email;
    private LocalDateTime joinedAt;
}

@GetMapping("/members/{id}")
public Member get(@PathVariable Long id) { ... }   // 지금은 괜찮다

6개월 뒤, 정산 팀 개발자가 정산 기능을 만들며 Member에 필드를 추가한다. 그는 이 엔티티가 어느 API로 나가는지 모른다. 알 이유도 없다 — 그는 정산 로직을 짜고 있을 뿐이다.

java
// t1 — 정산 팀이 필드 3개를 추가했다. 컨트롤러는 아무도 안 건드렸다.
@Entity
public class Member {
    private Long id;
    private String name;
    private String email;
    private LocalDateTime joinedAt;

    private String internalMemo;         // "블랙리스트 의심, 3회 환불 요청"
    private BigDecimal settlementRate;   // 이 회원사의 정산 수수료율
    private String passwordHash;         // 인증 리팩터링 때 함께 들어온 필드
}

이 순간 세 필드는 전부 공개 API 응답에 실려 나간다. 컨트롤러도, 서비스도, 응답 관련 코드도 아무도 수정하지 않았다. 리뷰어는 정산 PR에서 "엔티티에 필드 추가"만 봤고, 그건 지극히 정상적인 변경이다.

정보 유출이 코드 리뷰를 통과하는 게 아니라, 애초에 코드 리뷰의 시야에 들어오지도 않는다. 이것이 opt-out 구조의 본질이다.

DTO였다면 어떻게 되는가.

java
// ✅ opt-in — 명시한 것만 나간다
public record MemberResponse(Long id, String name, String email, LocalDateTime joinedAt) {
    public static MemberResponse from(Member m) {
        return new MemberResponse(m.getId(), m.getName(), m.getEmail(), m.getJoinedAt());
    }
}

정산 팀이 필드를 100개 추가해도 응답은 그대로다. settlementRate가 API로 나가려면 누군가 MemberResponse에 필드를 추가하고 from()에 매핑 한 줄을 써야 한다. 그건 리뷰에서 반드시 눈에 띄는 변경이다.

정리하면 이렇다.

필드가 추가됐을 때사고가 나려면
엔티티 노출 (opt-out)자동으로 노출된다아무것도 안 하면 된다
DTO (opt-in)응답은 그대로누군가 의도적으로 코드를 써야 한다
💡

안전한 설계는 "실수하지 않으면 안전한 설계"가 아니라 "실수해도 안전한 설계"다. DTO는 실수의 기본 방향을 안전한 쪽으로 뒤집는다.

이 논거가 실무에서 가장 자주 인용되는 이유는, 사람의 주의력에 의존하지 않는 유일한 논거이기 때문이다. 1층·2층은 "잘 알고 조심하면" 어느 정도 피할 수 있지만, opt-out 구조의 유출은 조심할 사람이 그 자리에 없다.

4-2. 요청 방향은 더 위험하다 — mass assignment

응답 얘기만 하다 끝내면 절반이다. @RequestBody로 엔티티를 받는 코드가 훨씬 위험하고, 훨씬 흔하다.

java
// ❌ 회원 정보 수정 API — 이름과 이메일만 바꾸라고 만든 것이다
@PatchMapping("/members/{id}")
public void update(@PathVariable Long id, @RequestBody Member member) {
    Member found = memberRepository.findById(id).orElseThrow();
    found.setName(member.getName());
    found.setEmail(member.getEmail());
}

이 코드는 "이름과 이메일만" 반영하므로 안전해 보인다. 그런데 실무에서 훨씬 흔한 형태는 이쪽이다.

java
// ❌❌ 더 흔하고 더 위험한 형태 — 통째로 저장
@PutMapping("/members/{id}")
public void update(@PathVariable Long id, @RequestBody Member member) {
    member.setId(id);
    memberRepository.save(member);       // merge → 전 필드 덮어쓰기
}

클라이언트가 이렇게 보내면 어떻게 되는가.

json
{
  "name": "홍길동",
  "email": "hong@example.com",
  "role": "ADMIN",
  "point": 999999,
  "settlementRate": 0.0
}

Jackson은 요청 JSON의 필드를 대상 객체에 그대로 채운다. role도, point도 전부 세팅된다. 그리고 save()는 그 값을 DB에 반영한다.

💡

서버 코드 어디에도 "역할을 바꿔도 된다"고 허용한 줄이 없는데 권한 상승이 일어난다.

이게 mass assignment(또는 over-posting)다. 이름이 붙어 있다는 건 흔한 취약점이라는 뜻이다.

여기서 흔한 오해 두 개를 짚어야 한다. (가산점 포인트)

  • @Valid는 막지 못한다. 검증은 "값이 올바른가"를 보지 "이 필드를 받아도 되는가"를 보지 않는다. role: "ADMIN"은 완벽하게 유효한 값이다.
  • @InitBinder / WebDataBinder.setDisallowedFields()도 막지 못한다. 그건 폼 바인딩(@ModelAttribute) 경로의 장치이고, @RequestBody는 HttpMessageConverter(Jackson)가 처리하므로 WebDataBinder를 아예 거치지 않는다. "바인딩 화이트리스트를 걸어뒀으니 괜찮다"는 말이 이 경로에서는 성립하지 않는다.

올바른 형태는 받는 그릇 자체를 좁히는 것이다.

java
// ✅ 받을 수 있는 필드를 타입으로 제한한다
public record MemberUpdateRequest(
        @NotBlank String name,
        @Email String email) { }

@PatchMapping("/members/{id}")
public void update(@PathVariable Long id, @RequestBody @Valid MemberUpdateRequest request) {
    memberService.updateProfile(id, request.name(), request.email());
}
// role, point 를 보내도 채울 자리가 없다 — Spring Boot 기본 설정에서는
// 모르는 필드가 조용히 무시된다(FAIL_ON_UNKNOWN_PROPERTIES 비활성).
// 400 으로 거절하고 싶으면 그 설정을 켜면 된다.

응답 쪽 opt-in과 정확히 같은 원리다. 나갈 수 있는 것을 명시하듯, 들어올 수 있는 것도 명시한다. 그리고 권한·잔액처럼 민감한 상태는 애초에 setter가 아니라 도메인 메서드로만 바뀌게 만들면(member.promoteToAdmin(승인자)) 한 겹 더 튼튼해진다.

💡

확인 범위: FAIL_ON_UNKNOWN_PROPERTIES가 Spring Boot에서 기본 비활성인 것은 Jackson 자동 구성의 동작이지만, 프로젝트가 ObjectMapper를 직접 등록했다면 달라진다. 면접에서 단정하기보다 "기본값은 무시하는 쪽이고, 필요하면 켜서 거절할 수 있다" 정도로 말하는 게 안전하다.

4-3. 나머지 운영 비용 — 짧게

세 가지만 덧붙이면 층이 완성된다.

  • 응답 크기. 필요 없는 컬럼까지 전부 실린다. 목록 API에서 행마다 TEXT 컬럼 하나가 딸려 나가면 응답이 수십 배가 된다. 조회 전용 화면이라면 애초에 DTO 프로젝션이 맞다 — fetch join + 페이징 §3-3.
  • 내부 스키마 노출. 필드 이름·id 채번 방식·연관 구조가 그대로 드러난다. 그 자체로 치명적이진 않지만, 공격자에게 시스템 지도를 그려주는 셈이다.
  • 문서·계약 관리. OpenAPI 스키마가 엔티티에서 생성되면 문서가 DB 스키마를 따라 흔들린다. 클라이언트 팀은 어떤 필드가 계약이고 어떤 필드가 우연히 있는 건지 구분할 수 없다.
5

"그냥 @JsonIgnore 붙이면 되지 않나요?" — 정면으로 답한다

▾

이 반론은 코드리뷰에서 실제로 자주 나온다. 그리고 부분적으로 맞다. 순환 참조도 막히고, 지연 로딩 필드도 안 탄다. 그래서 "안 됩니다"라고만 답하면 설득이 안 된다. 동작 층과 설계 층을 나눠서 답해야 한다.

5-1. 동작 층 — 엔티티에 박히는 전역 스위치다

@JsonIgnore는 필드에 붙는다. 즉 그 엔티티를 직렬화하는 모든 곳에 똑같이 적용된다. API마다 요구가 다르면 그 순간 표현할 수 없다.

java
@Entity
public class Order {
    @JsonIgnore                       // ← 이 한 줄이 전역이다
    @ManyToOne(fetch = LAZY)
    private Member member;
}
  • 관리자 API: 주문 조회 시 주문자 실명·연락처가 필수다.
  • 사용자 API: 다른 사람 정보는 절대 노출 금지다.

한 필드에 붙은 한 개의 어노테이션으로 두 요구를 동시에 만족시킬 방법이 없다. 관리자 쪽을 살리려고 떼면 사용자 API에서 정보가 새고, 사용자 쪽을 지키려고 붙이면 관리자 화면이 빈다. 결국 어느 한쪽에서 우회 코드를 쓰게 되고, 그 우회 코드가 결국 DTO다 — 처음부터 DTO를 썼으면 됐을 일을 반 바퀴 돌아 도착하는 셈이다.

5-2. @JsonView로 갈라도 조합이 늘면 무너진다

@JsonView를 쓰면 뷰(마커 인터페이스)별로 필드를 갈라낼 수는 있다.

java
class Views {
    interface Public {}
    interface Admin extends Public {}
}

@Entity
public class Order {
    @JsonView(Views.Public.class) private Long id;
    @JsonView(Views.Admin.class)  private Member member;   // 관리자에게만
}

@GetMapping("/admin/orders/{id}")
@JsonView(Views.Admin.class)          // 컨트롤러에서 뷰를 지정해야 발동한다
public Order adminGet(@PathVariable Long id) { ... }

동작은 한다. 하지만 세 가지가 발목을 잡는다.

  • 조합 폭발. 실무의 요구는 "공개/관리자" 2단이 아니라 엔드포인트 수만큼 다르다. 파트너사 API는 정산율은 보되 내부 메모는 못 보고, 모바일은 목록에서 요약만, 상세에선 전부… 뷰 인터페이스가 조합만큼 늘어나고, 어떤 필드가 어떤 뷰에 속하는지가 엔티티 한 파일에 흩어진다. DTO는 "이 파일 하나 읽으면 이 응답이 전부"인데, @JsonView는 엔티티 전체를 훑으며 머릿속에서 뷰별로 필터링해야 읽힌다.
  • 누락이 조용하다. 새 필드에 @JsonView를 안 붙이면 어느 뷰에서 보이고 어느 뷰에서 안 보이는지가 설정에 달려 있다. Jackson 자체의 기본값 (DEFAULT_VIEW_INCLUSION)은 뷰가 없는 필드를 포함시키는 쪽이고, Spring 계열의 기본 구성은 이를 끄는 쪽으로 알려져 있다. 즉 "필드를 추가했는데 어디로 나가는지가 프레임워크 설정에 좌우된다." 이게 §4-1의 opt-out 문제와 정확히 같은 구조다.
  • 지연 로딩·성능 문제는 그대로다. 뷰에 포함된 연관은 여전히 직렬화 시점에 초기화된다.
💡

확인 범위: MapperFeature.DEFAULT_VIEW_INCLUSION의 Jackson 자체 기본값은 활성(포함)이고, Spring의 Jackson2ObjectMapperBuilder 계열 구성이 이를 비활성으로 바꾸는 것으로 알려져 있다. 다만 Spring Boot 버전과 Jackson 3 계열의 기본값 변화는 확인이 필요하다. 면접에서는 버전별 기본값을 단정하지 말고 "뷰가 지정되지 않은 필드의 처리 방식이 설정에 의존한다는 것 자체가 위험" 이라는 논지로 말하는 게 낫다. 또한 @JsonView는 컨트롤러 메서드에서 뷰를 활성화해야 적용된다 — 활성화를 깜빡하면 필터가 통째로 안 걸린다는 점도 같은 성격의 위험이다.

5-3. 더 근본적인 문제 — 엔티티가 응답 템플릿이 된다

여기가 이 절의 결론이고, 반론을 이기는 지점이다. 동작 여부를 다투는 대신 방향을 지적한다.

💡

문제는 @JsonIgnore가 동작하느냐가 아니라, 그 순간 엔티티에 표현 계층의 관심사가 새겨진다는 것이다.

@JsonIgnore, @JsonView, @JsonProperty("order_no"), @JsonIgnoreProperties({"hibernateLazyInitializer","handler"})가 하나씩 붙을 때마다 엔티티는 "이 데이터가 무엇인가"를 말하는 도메인 모델에서 "이 데이터를 어떻게 보여줄 것인가"를 말하는 응답 템플릿으로 옮겨간다. 어느 순간 그 클래스는 저장 구조와 응답 구조를 동시에 책임지는 클래스가 되고, 그때부터 어떤 변경도 양쪽을 다 고려해야 한다 — §3-3에서 말한 "변경의 이유가 다르면 분리한다"의 정반대다.

의존 방향으로 보면 더 선명하다.

text
❌ 도메인 계층(Entity)  ──의존──▶  Jackson(웹 표현 기술)
   가장 안쪽 계층이 가장 바깥쪽 기술 라이브러리를 알게 된다.

✅ 도메인 계층(Entity)  ◀──의존──  웹 계층(DTO + Jackson)
   바깥이 안을 안다. 안은 바깥을 모른다.

이 방향이 뒤집히면 "이 엔티티를 다른 통로(배치, 메시지 발행, gRPC)로도 쓸 수 있는가" 가 곧바로 흔들린다. HTTP JSON 응답 사정에 맞춰 잘라낸 필드가, 배치에서는 반드시 필요한 필드일 수 있기 때문이다.

5-4. Hibernate5Module 같은 우회책도 성격이 같다

지연 로딩 프록시를 예외 대신 null로 직렬화해 주는 Jackson 모듈이 있다 (하이버네이트 버전에 맞춰 Hibernate5Module / Hibernate6Module). 예외는 사라진다.

그런데 이건 해결이 아니라 은폐이고, 은폐 중에서도 나쁜 쪽이다. 예외는 시끄럽게 터져 즉시 발견되지만 null은 조용히 잘못된 응답을 내보낸다. 클라이언트는 "주문 항목이 없는 주문"을 정상 200 응답으로 받는다. 데이터가 틀린 채 나가는 200이 500보다 훨씬 늦게 발견되고 훨씬 비싸게 수습된다. (OSIV 문서 §6의 같은 질문 참고)

@JsonIgnore, @JsonView, Jackson 모듈은 전부 "엔티티를 직렬화하겠다"는 전제를 편하게 만들어주는 도구다. 세 개 다 전제 자체는 건드리지 않는다. 답은 전제를 없애는 것이다.

6

실무 적용 — 어디서 바꾸고, 무엇으로 고정하는가

▾

6-1. 변환은 트랜잭션 안에서 한다

"DTO를 쓴다"까지만 말하면 절반이다. 어디서 변환하는가가 나머지 절반이다.

java
// ❌ 컨트롤러에서 변환 — 트랜잭션 밖이다
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable Long id) {
    Order order = orderService.findById(id);      // 여기서 트랜잭션 종료
    return OrderResponse.from(order);             // 지연 로딩 필드를 만나면 예외
}

컨트롤러가 DTO를 반환한다는 겉모습은 갖췄지만, 엔티티가 트랜잭션 밖으로 나왔다. OSIV가 켜져 있으면 우연히 동작하고, 끄는 순간 터진다. 즉 OSIV라는 전역 설정에 의존하는 코드다.

java
// ✅ 서비스 트랜잭션 안에서 변환을 끝낸다
@Service
public class OrderService {

    @Transactional(readOnly = true)
    public OrderResponse getOrder(Long id) {
        Order order = orderRepository.findWithItemsById(id);   // 필요한 것만 fetch join
        return OrderResponse.from(order);                      // 트랜잭션 안에서 변환 완료
    }
}

이렇게 하면 트랜잭션 경계 밖으로 나가는 것은 이미 값이 다 채워진 DTO뿐이다. OSIV가 켜져 있든 꺼져 있든 동작이 동일해진다 — 설정에 의존하지 않는 코드가 된다.

이건 OSIV 트레이드오프와 전환 §5-1의 전환 순서 ①②단계와 정확히 같은 작업이다. 그 문서는 "OSIV를 안전하게 끄려면 무엇을 먼저 해야 하나"의 관점에서, 이 문서는 "엔티티를 왜 노출하면 안 되나"의 관점에서 같은 지점에 도달한다. 두 문항은 결국 한 문장으로 수렴한다.

💡

엔티티는 영속성 컨텍스트가 살아 있는 구간 안에서만 존재한다.

엔티티 노출 금지는 그 규칙을 사람의 규율로 지키는 것이고, OSIV 끄기는 같은 규칙을 런타임이 강제하게 만드는 것이다. 면접에서 이 연결을 짚으면 개별 지식이 아니라 원칙을 갖고 있다는 신호가 된다. (가산점 포인트)

6-2. "DTO는 귀찮다"에 답하기

가장 현실적인 반론이다. 정직하게 인정하고 대응을 말하는 편이 낫다 — 비용이 없다고 우기면 오히려 신뢰를 잃는다.

① record로 선언 비용을 줄인다. 생성자·게터·equals·toString이 자동이라 응답 DTO는 사실상 한 줄이다.

java
public record OrderResponse(Long orderId, String status, int totalPrice) {
    public static OrderResponse from(Order order) {
        return new OrderResponse(order.getId(), order.getStatus().name(), order.getTotalPrice());
    }
}

② 조회 전용이면 생성자 프로젝션으로 변환 단계 자체를 없앤다. DB에서 바로 DTO로 받으면 엔티티를 거치지 않으므로 지연 로딩·스냅샷 비용도 함께 사라진다.

java
// JPQL 생성자 프로젝션 — 필요한 컬럼만 SELECT 되고, 결과가 곧바로 DTO 다
@Query("""
    select new com.example.order.dto.OrderSummary(o.id, o.status, m.name)
    from Order o join o.member m
    where o.createdAt >= :from
    """)
List<OrderSummary> findSummaries(@Param("from") LocalDateTime from);

QueryDSL의 Projections.constructor(...)도 같은 일을 타입 안전하게 해 준다.

③ 매핑이 정말 많으면 MapStruct. 컴파일 시점에 매핑 코드를 생성하므로 런타임 리플렉션 비용이 없고, 매핑 누락을 컴파일 에러로 잡을 수 있다 (unmappedTargetPolicy = ERROR). 중요한 건 MapStruct를 써도 opt-in 성질은 유지된다는 점이다 — 나가는 필드 목록은 여전히 DTO 선언이 정한다.

트레이드오프도 같이 말한다.

  • 리플렉션 기반 매퍼(ModelMapper 등)는 신중해야 한다. 이름이 같으면 알아서 복사하는 방식은 편하지만, 매핑 실수와 예상 못 한 필드 복사를 조용히 통과시킨다. §4-1에서 얻은 안전성(명시하지 않으면 안 나간다)을 다시 반납하는 셈이다.
  • DTO를 재사용하려는 유혹을 경계한다. 여러 엔드포인트가 DTO 하나를 공유하기 시작하면 "이 필드는 A 화면용, 저건 B 화면용"이 섞이고, 결국 엔티티를 노출할 때와 똑같은 결합 문제가 DTO 층에서 재현된다. 화면이 다르면 DTO도 다른 게 기본이고, 중복은 감수하는 쪽이 대개 싸다.
  • 요청 DTO와 응답 DTO는 합치지 않는다. 필드 요구가 애초에 다르고(§4-2), 합치는 순간 요청 쪽에 응답 전용 필드가 열려 mass assignment 표면이 다시 생긴다.

6-3. 구조를 룰로 고정한다 — ArchUnit

"엔티티를 반환하지 않기로 합시다"는 대책이 아니다. 사람이 지키는 규칙은 새 팀원이 오거나 급한 릴리스가 하나 지나가면 무너진다. 이 문서 전체의 결론을 지키는 유일한 방법은 빌드가 대신 지키게 하는 것이다.

컨트롤러 반환 타입에 엔티티를 금지하는 룰은 OSIV 문서 §4-3에 코드와 도입 요령 (FreezingArchRule로 기존 위반을 동결하고 신규만 실패시키기)까지 정리되어 있다. 여기서 추가로 다뤄야 할 것은 반대 방향이다.

💡

반환 타입만 막으면 절반이다. @RequestBody 파라미터를 막지 않으면 §4-2의 mass assignment 경로가 그대로 열려 있다.

그리고 실무에서 요청 쪽이 더 자주 놓친다. 리뷰어의 눈이 "응답에 뭐가 나가나"에는 가 있어도 "요청으로 뭐가 들어오나"에는 잘 안 가기 때문이다.

java
@AnalyzeClasses(
        packages = "com.example",
        importOptions = ImportOption.DoNotIncludeTests.class)
class WebLayerRulesTest {

    /**
     * 요청 방향 — 컨트롤러 메서드의 파라미터 타입에 엔티티가 있으면 실패.
     * mass assignment(클라이언트가 role·point 를 실어 보내 덮어쓰기)를 구조적으로 차단한다.
     */
    @ArchTest
    static final ArchRule 컨트롤러는_엔티티를_파라미터로_받으면_안_된다 =
            methods()
                .that().areDeclaredInClassesThat()
                       .areAnnotatedWith(RestController.class)
                .and().arePublic()
                .should(new ArchCondition<JavaMethod>("파라미터 타입에 @Entity 가 없어야 한다") {
                    @Override
                    public void check(JavaMethod method, ConditionEvents events) {
                        method.getParameterTypes().stream()
                              .flatMap(WebLayerRulesTest::flatten)     // 제네릭 안쪽까지 펼친다
                              .filter(type -> type.isAnnotatedWith(Entity.class))
                              .forEach(type -> events.add(SimpleConditionEvent.violated(
                                      method,
                                      method.getFullName() + " 가 엔티티 "
                                          + type.getSimpleName() + " 를 파라미터로 받는다"
                                          + " (@RequestBody 라면 mass assignment 위험)")));
                    }
                });
}

두 가지를 짚어야 한다.

  • flatten이 여기서도 핵심이다. 위반은 Member를 직접 받는 형태보다 List<Member>, Optional<Member>처럼 제네릭 안에 숨은 형태가 많다. 겉 타입만 검사하면 대부분을 놓친다. (반환 타입 룰에서 쓰는 flatten과 동일한 헬퍼를 공유하면 된다 — OSIV 문서 §4-3에 구현이 있다.)
  • @RequestBody가 붙은 파라미터만 걸러도 되지만, 전부 막는 편이 낫다. @ModelAttribute 폼 바인딩도 같은 위험이 있고, @PathVariable에 엔티티가 올 일은 어차피 없다. 규칙은 예외가 적을수록 오래 산다.

가장 강력한 형태는 계층 자체를 끊는 것이다. 반환·파라미터·지역 변수·import를 한꺼번에 막는다.

확인 범위: methods(), ArchCondition, SimpleConditionEvent, FreezingArchRule은 ArchUnit 공개 API이지만 정확한 시그니처는 버전에 따라 다르다 (특히 파라미터 타입·파라미터 어노테이션 접근 API는 버전 편차가 있다). 프로젝트에서 컴파일로 확인해야 한다. 면접에서 중요한 것은 API 이름이 아니라 "반환과 파라미터 양방향을 막아야 하고, 제네릭 안쪽까지 재귀로 펼쳐야 한다" 는 설계 포인트다.

7

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

모양이 같은 것과 성질이 같은 것은 다르다. 지금 필드가 100% 겹치더라도 세 가지가 다르다.

  • 변경의 이유가 다르다. 엔티티는 저장·정합성 요구로 바뀌고 DTO는 화면·클라이언트 요구로 바뀐다. 지금 같아 보이는 것은 아직 두 요구가 갈라지지 않았을 뿐이다. 갈라지는 날, 합쳐뒀으면 한쪽이 다른 쪽을 끌고 다닌다.
  • 실수의 방향이 다르다. 엔티티에 필드가 추가되면 자동으로 노출되지만, DTO는 누군가 명시적으로 써야 노출된다(§4-1). 이건 필드가 겹치는 것과 무관한 성질이다.
  • 표현할 수 있는 범위가 다르다. DTO는 여러 애그리거트와 외부 API 결과를 조합할 수 있지만 엔티티는 못 한다(§3-2).

덧붙이면 좋다 — "완전히 겹치는 상태가 오히려 정상이고, 그때 분리해두는 게 싸다. 갈라진 뒤에 분리하려면 이미 클라이언트가 붙어 있어서 못 한다."

아니다. DTO 변환 코드가 order.getItems()를 순회하면 지연 로딩은 똑같이 일어나고 쿼리도 똑같이 늘어난다. DTO는 N+1을 없애는 장치가 아니다.

바뀌는 것은 문제가 보이는 위치다. 엔티티를 그대로 반환하면 쿼리를 유발하는 지점이 코드에 존재하지 않는다(직렬화기가 부른다). DTO 변환에서는 그 순회가 내가 쓴 코드로 눈앞에 있다. 그래서 fetch join을 붙일 자리도, 리뷰에서 지적할 자리도 명확해진다.

진짜 해결은 조회 방법을 바꾸는 것이다 — ToOne 연관은 fetch join, 컬렉션은 default_batch_fetch_size, 조회 전용이면 생성자 프로젝션으로 애초에 엔티티를 거치지 않기. 선택 기준은 N+1 탐지와 해결과 fetch join + 페이징 §3-5에 있다.

안 된다. 두 가지가 동시에 깨진다.

  • 보안: 응답에 필요한 필드(id, role, point, createdAt)가 요청 쪽에도 열린다. 그 순간 §4-2의 mass assignment 표면이 DTO 층에서 그대로 재현된다. 엔티티를 안 쓰기로 해놓고 같은 구멍을 다시 판 셈이다.
  • 검증: 요청에는 @NotBlank 같은 제약이 필요하지만 응답에는 무의미하다. 합치면 응답 전용 필드에까지 검증 애노테이션이 붙거나, 요청 검증이 느슨해진다.

원칙은 "들어오는 것과 나가는 것은 방향이 다르므로 타입도 다르다" 다. 이름도 MemberDto 같은 중립적인 이름 대신 MemberUpdateRequest / MemberResponse처럼 방향이 드러나게 짓는 편이 실수를 줄인다.

"항상"이라고 답하면 오히려 감점 요인이다. 기준을 말하는 게 답이다. 판단 축은 "이 응답의 계약을 내가 언제든 깰 수 있는가" 하나다.

  • 깰 수 없다면 DTO 필수 — 외부 공개 API, 파트너사 연동, 앱 클라이언트(구버전이 스토어에 남는다), 다른 팀이 소비하는 사내 API. 소비자를 내가 통제할 수 없으면 계약을 분리해야 한다.
  • 깰 수 있으면 완화 여지가 있다 — 나만 쓰는 내부 관리자 화면, 같은 배포 단위에서 함께 나가는 BFF. 그래도 §4-1의 opt-out 위험은 그대로 남는다. 관리자 도구야말로 민감 필드가 많아서, "내부용이니까"가 가장 위험한 문장이 되는 경우가 흔하다.

그래서 현실적인 절충은 이렇게 말하는 게 정확하다 — "응답 DTO는 상황에 따라 완화할 수 있지만, @RequestBody로 엔티티를 받는 것은 예외 없이 금지한다." 유출은 정보 공개지만 mass assignment는 데이터 변조라 피해 규모가 다르고, 내부망이라는 전제가 무너지는 순간(SSRF, 계정 탈취) 그대로 뚫린다.

전면 리팩터링은 답이 아니다. 몇 달짜리 작업은 중간에 우선순위에 밀려 절반만 끝나고, 절반만 끝난 상태가 가장 나쁘다(두 규칙이 공존해 아무도 뭐가 맞는지 모른다).

순서는 위험도 순, 그리고 되돌리기 쉬운 것부터다.

  1. 출혈을 먼저 멈춘다. ArchUnit 룰을 FreezingArchRule로 걸어 기존 위반은 통과시키고 신규 위반만 빌드를 깨게 한다. 하루면 끝나고, 그날부터 문제가 더는 늘지 않는다. 가장 비용 대비 효과가 큰 조치라 반드시 첫 번째여야 한다.
  2. 요청 방향부터 고친다. 응답 유출보다 mass assignment가 피해가 크고, 대상 수는 훨씬 적다(쓰기 API가 읽기 API보다 적다). 위험은 높고 작업량은 적은 구간이라 투자 대비 효과가 가장 좋다.
  3. 민감 엔티티를 골라 응답을 고친다. 전수 조사 대신 축을 정한다 — 개인정보, 금액·정산, 인증 정보를 가진 엔티티가 나가는 엔드포인트부터. "모든 엔티티"가 아니라 "유출되면 사고가 되는 엔티티" 로 범위를 좁혀야 실제로 끝난다.
  4. 나머지는 만질 때 고친다. 해당 파일을 어차피 수정하게 될 때 함께 DTO로 옮긴다. 별도 일정을 잡지 않으므로 협상이 필요 없다.
  5. 동결 목록의 크기를 지표로 삼는다. 스프린트마다 남은 위반 수가 줄어드는지만 본다. "언제 다 끝나나"보다 "단조 감소하고 있나"가 관리 가능한 질문이다.

핵심 한 문장 — "고치는 것보다 늘지 않게 막는 게 먼저다." 이 답의 1번이 나머지 전부보다 가치가 크다.

충분히 일어난다. @JsonIgnore가 붙어 있던 필드는 직렬화 대상이 아니었으므로 지연 로딩도 안 탔다. 그 어노테이션이 우연히 "가져오지 마"라는 성능 가드 역할을 하고 있었던 것이다.

DTO로 바꾸면서 화면에 필요하다는 이유로 그 연관을 매핑에 포함시키면, 이제는 실제로 로딩된다. 없던 쿼리가 생긴 게 아니라 원래 필요했지만 어노테이션에 가려 안 나가던 데이터가 드러난 것이다. 화면이 그 값을 실제로 쓰고 있었다면 이전에는 그 자리가 비어 있었다는 뜻이므로 성능이 나빠진 게 아니라 결함이 드러난 것일 수도 있다.

진단과 처방은 이렇게 나눈다.

  • 정말 필요한 데이터인가? 아니라면 DTO에서 그 필드를 빼면 끝이다(opt-in의 이점이 여기서 나온다 — 뺄 수 있는지 판단할 자리가 코드에 생긴다).
  • 필요하다면 조회 방법을 고친다. fetch join / batch fetch size / 생성자 프로젝션. DTO는 "무엇을 내보낼지"를 정하는 장치이고, "어떻게 가져올지"는 별개 문제다. 이 둘을 섞어서 "DTO를 썼는데 왜 느리냐"고 하면 진단이 어긋난다.
  • 쿼리 수를 테스트로 고정한다. 바꾸기 전후의 쿼리 수를 단정해두면 이런 논쟁이 숫자로 끝난다.
✅ 한 줄 요약

"엔티티를 노출하면 안 되는 이유"에는 하나가 아니라 세 층으로 답한다 — 직렬화기가 연관을 타고 들어가 터지거나(OSIV off) 조용히 쿼리를 폭증시키고(OSIV on), API 스펙이 DB 스키마에 묶여 서로 다른 이유로 변해야 할 두 구조가 한 몸이 되며, 무엇보다 opt-out 구조라서 아무도 응답 코드를 건드리지 않아도 새 필드가 새어 나가고 요청 방향으로는 권한까지 덮어쓰인다. @JsonIgnore는 이 중 어느 것도 해결하지 못한 채 엔티티를 응답 템플릿으로 만들 뿐이고, 규율은 사람이 아니라 ArchUnit이 반환 타입과 @RequestBody 양쪽에서 지킨다.
