엔티티 직접 노출 금지
"이유를 대라"에는 반드시 세 층으로 답한다

면접 질문: "엔티티를 API 응답으로 직접 노출하면 안 되는 이유는?"

핵심 관전 포인트 — 이 질문은 지식 문제가 아니라 전개 문제다. 이유를 하나만 대고 멈추면, 아는 사람이어도 "규율이 몸에 배지 않은 사람"으로 읽힌다. 항상 세 층으로 답한다. 1층 기술적 사고 — 지연 로딩 필드를 Jackson이 건드리는 순간 OSIV가 꺼져 있으면 LazyInitializationException이고, OSIV가 켜져 있으면 예외가 안 나는 대신 직렬화기가 연관을 타고 들어가며 쿼리를 계속 날린다. 조용한 실패가 더 나쁘다. 여기에 양방향 연관의 순환 참조(무한 재귀)와 하이버네이트 프록시 직렬화 실패가 붙는다. 2층 설계·결합도 — API 스펙이 DB 스키마에 묶인다. 컬럼명을 바꾸면 클라이언트가 깨지고, 화면 요구가 바뀌면 테이블을 건드리게 된다. 더 근본적으로 엔티티 구조와 화면 요구는 애초에 다른 축이라, 화면이 여러 애그리거트를 조합해야 하면 엔티티 하나로는 표현 자체가 불가능하다. 3층 보안·운영 — 실무에서 가장 강력한 논거가 여기 있다. 엔티티 노출은 opt-out이라, 누군가 엔티티에 internalMemo·settlementRate를 추가하는 순간 응답 코드를 아무도 건드리지 않았는데 그 필드가 API로 새어 나간다. DTO는 opt-in이라 명시한 것만 나간다 — 사고가 나려면 누군가 의도적으로 코드를 써야 한다. 실수의 방향이 반대다. 그리고 요청 방향은 더 위험하다 — @RequestBody Member member로 받으면 클라이언트가 role: "ADMIN"을 실어 보내 덮어쓴다(mass assignment). @JsonIgnore는 답이 아니다 — 엔티티에 박히는 전역 스위치라 API마다 다른 요구를 표현할 수 없고, 더 근본적으로는 엔티티를 도메인 모델이 아니라 응답 템플릿으로 만든다. 마지막으로 규율은 사람이 아니라 빌드가 지킨다 — ArchUnit으로 컨트롤러의 반환 타입과 @RequestBody 파라미터 양쪽에서 엔티티를 금지한다.
  • 1
    기술적으로는 — 직렬화기가 게터를 전부 호출한다: 지연 로딩 필드를 건드려 OSIV가 꺼져 있으면 LazyInitializationException, 켜져 있으면 예외 대신 쿼리가 폭증한다(예외가 안 나는 쪽이 더 위험). 여기에 양방향 순환 참조(무한 재귀)와 프록시 직렬화 실패가 붙는다.
  • 2
    설계 관점에서는 — API 스펙이 DB 스키마에 묶인다: 컬럼명 하나 바꾸면 클라이언트가 깨지고, 화면 요구가 바뀌면 테이블을 건드린다. 더 근본적으로 저장 구조와 화면 요구는 다른 축이라, 여러 애그리거트를 조합해야 하는 화면은 엔티티 하나로 표현 자체가 불가능하다.
  • 3
    보안·운영이 실무에서는 가장 강력하다 — 실수의 방향이 반대다: 엔티티 노출은 opt-out이라 응답 코드를 아무도 안 건드려도 새 필드가 새어 나가고, DTO는 opt-in이라 사고가 나려면 누군가 의도적으로 코드를 써야 한다. 요청 방향은 mass assignment로 더 위험하다.

0. 질문 + 출제 의도

질문: "엔티티를 API 응답으로 직접 노출하면 안 되는 이유는?"

출제 의도: rationale은 이렇게 적고 있다 — "엔티티 직접 노출 금지 — API 스펙이 DB 스키마에 종속되는 문제, 지연 로딩 직렬화 폭탄, 순환 참조 — '계층 간 경계'를 지키는 규율이 있는지의 리트머스."

여기서 주목할 단어는 "리트머스"다. 이 질문은 어려운 지식을 묻는 게 아니다. 정답에 해당하는 항목들(N+1, 순환 참조, 결합도, 보안)은 하나하나 떼어놓고 물으면 대부분 답한다. 그런데도 이 문항이 변별력을 갖는 이유는, 묻지 않아도 여러 층을 한 호흡에 나열하는가가 곧 규율의 유무이기 때문이다. 반대로 가장 최근에 겪은 이유 하나만 대고 멈추면, 지식은 있어도 그것이 원칙으로 조직되어 있지 않다는 신호가 된다.

함정 두 개 — 이 페이지가 겨냥하는 지점 ① 가장 좁은 이유 하나로 마감하는 것. 특히 "OSIV를 끄면 직렬화 예외가 난다"는 참이지만 가장 약한 논거다. 상대가 "우리는 OSIV를 켜두는데요?" 한마디만 받아치면 논거 전체가 무너진다 → 3절에서 "켜져 있을 때 무슨 일이 벌어지는지"를 로그 단위로 세운다.
② @JsonIgnore로 해결된다는 반론에 "그건 안 됩니다"라고만 답하는 것. 이 반론은 부분적으로 맞다(순환 참조·지연 로딩은 실제로 막힌다). 그래서 "동작이 안 된다"가 아니라 "동작해도 문제"라는 층에서 답해야 한다 → 7절이 통째로 이 반론에 배정돼 있다.
DTO (Data Transfer Object)
계층 사이를 오갈 목적으로만 만든 데이터 전용 객체. 도메인 규칙을 갖지 않는다. 여기서는 API 응답 모양을 정의하는 클래스.
직렬화(serialization)
자바 객체를 JSON 같은 전송 가능한 문자열로 바꾸는 작업. Spring MVC에서는 Jackson이 담당한다.
OSIV (Open Session In View)
영속성 컨텍스트를 HTTP 응답이 완전히 나갈 때까지 열어두는 Spring Boot 기본 설정(spring.jpa.open-in-view=true).

1. 답변의 골격 — 세 층은 난이도가 아니라 "파급 범위" 순서다

면접관이 "이유는?"이라고 물을 때 기대하는 것은 이유 목록이 아니라 이유를 분류하는 축이다. 축이 있는 사람은 하나를 말한 뒤 자연스럽게 "그건 기술적인 문제고, 설계 관점에서는…"으로 넘어간다. 축이 없는 사람은 가장 최근에 겪은 사례 하나를 말하고 멈춘다. 그래서 이 문항은 암기할 목록이 아니라 외울 골격으로 접근한다.

골격 3초 암기 — 터 · 묶 · 샌

1층 기술→터진다 (혹은 조용히 폭증한다)
2층 설계→묶인다 (API가 DB 스키마에)
3층 보안→샌다 (그리고 덮어쓰인다)

세 글자가 파급 범위 순서이자 말하는 순서다. 하나만 떠올려도 나머지 둘이 따라오도록, "터-묶-샌"을 붙여서 외운다.

1-1. 30초 답변 스크립트 — 이대로 말하고 꼬리질문을 기다린다

"이유는 세 층으로 나눠 말씀드리겠습니다.

기술적으로는, JSON 직렬화기가 엔티티의 모든 게터를 호출하기 때문에 지연 로딩 필드를 건드립니다. OSIV가 꺼져 있으면 LazyInitializationException이 나고, 켜져 있으면 예외 대신 연관을 타고 들어가며 쿼리가 폭증합니다. 예외가 안 나는 쪽이 더 위험합니다. 양방향 연관이면 순환 참조로 무한 재귀가 나고, 아직 초기화 안 된 프록시 객체는 직렬화 자체가 실패합니다.

설계 관점에서는, API 스펙이 DB 스키마에 묶입니다. 컬럼 이름 하나 바꾸면 클라이언트가 깨지고, 반대로 화면 요구가 바뀌면 테이블을 건드리게 됩니다. 더 근본적으로는 엔티티 구조와 화면 요구가 애초에 다른 축이라, 화면이 서로 연관관계도 없는 데이터를 조합해야 하면 엔티티 하나로는 표현 자체가 불가능합니다.

그리고 보안·운영 관점이 실무에서는 가장 강력합니다. 엔티티 노출은 opt-out 구조라서, 누군가 엔티티에 정산율이나 내부 메모 필드를 추가하는 순간 응답 코드를 아무도 건드리지 않았는데 그게 API로 새어 나갑니다. DTO는 opt-in이라 명시한 것만 나가고요. 실수의 방향이 반대입니다. 요청 방향은 더 위험해서, @RequestBody로 엔티티를 받으면 클라이언트가 role이나 포인트 값을 실어 보내 덮어쓸 수 있습니다."

2. 1층 — 직렬화기가 실제로 하는 일 전제

1층 전체가 단 하나의 전제에서 파생된다. Jackson은 객체를 JSON으로 바꿀 때 그 객체의 프로퍼티를 전부 훑는다. 게터가 있으면 호출하고, 반환값이 또 객체면 그 안으로 들어가 같은 일을 반복한다. "필요한 것만 골라 읽는다"는 개념이 아예 없다.

Jackson은 고르는 사람이 아니라 버튼을 전부 눌러보는 로봇이다 — 누르면 안 되는 버튼이 있으면 그건 로봇이 아니라 설계의 문제다

이게 모든 문제의 출발점이다. 코드에는 return order; 한 줄뿐이지만, 실제로 호출되는 게터는 getMember(), getItems(), 그리고 그 안의 getItem()…까지 연관 그래프 전체다. 코드에는 안 보이는 호출이라는 점이 중요하다 — "우리 컨트롤러는 order.getMember()를 부르지 않는데요?"라는 항변이 통하지 않는 이유가 여기 있다.

문제 게터 호출이 한 줄도 없다
@GetMapping("/orders/{id}")
public Order get(@PathVariable Long id) {
    return orderRepository.findById(id).orElseThrow();
}
// 이 한 줄이 연관 그래프 전체를 순회시킨다.
// 쿼리를 유발한 코드가 "존재하지 않는다"는 것이 이 문제의 본질.
전제 아래 절들이 쓰는 엔티티
@Entity
class Order {
    @ManyToOne(fetch = LAZY) private Member member;
    @OneToMany(mappedBy = "order", fetch = LAZY)
    private List<OrderItem> items;
}

@Entity
class OrderItem {
    @ManyToOne(fetch = LAZY) private Order order;  // 역방향
    @ManyToOne(fetch = LAZY) private Item item;
}

2-1. 지 — OSIV가 꺼져 있으면 시끄러운 실패가 난다

Order.member가 LAZY라면 getMember()는 아직 데이터가 안 채워진 프록시를 돌려준다. 프록시는 진짜 객체인 척하면서 값을 요구받는 순간 DB에서 채워 오는 대리인 객체다. 프록시가 실제 값을 가져오려면 영속성 컨텍스트(EntityManager)가 살아 있어야 하는데, OSIV가 꺼져 있으면 서비스 트랜잭션이 끝나는 순간 이미 닫혔다. 그래서 직렬화 시점에 LazyInitializationException이 난다(Spring MVC에서는 보통 HttpMessageNotWritableException에 감싸여 올라온다).

로그가 시끄럽다는 점을 기억해두자. SELECT는 한 번뿐이고, 그 뒤에 Closing JPA EntityManager가 찍히고, 곧바로 예외 스택이 올라온다. 원인과 결과가 붙어 있어서 로그만 봐도 진단이 끝난다.

여기서 실무적으로 고약한 지점 하나 — 200 OK와 함께 잘린 JSON 직렬화는 응답 본문을 이미 쓰기 시작한 뒤에 일어난다. 상태 코드와 헤더가 이미 나간 뒤에 예외가 터지면 500으로 바꿔 줄 수도 없어서, 클라이언트는 200 OK와 함께 중간에 잘린 JSON을 받는다. 로그에는 예외가 찍히는데 클라이언트 쪽 증상은 "가끔 JSON 파싱이 깨짐"으로 나타나 원인 추적이 오래 걸린다.
확인 범위 응답이 이미 커밋된 뒤에 예외가 나면 상태 코드를 바꿀 수 없다는 것은 서블릿 스펙 수준의 성질이지만, 실제로 헤더가 언제 flush되는지는 응답 크기·버퍼 설정에 따라 달라진다. 작은 응답은 버퍼 안에서 끝나 정상적으로 500이 나가기도 한다.

2-3. 프 — 프록시 객체 자체가 직렬화되지 않는다

지연 로딩 예외와 헷갈리기 쉽지만 원인이 다르다 "값을 못 가져와서"가 아니라 "객체의 모양이 예상과 달라서" 나는 실패다. 그리고 이걸 막으려고 엔티티에 @JsonIgnoreProperties({"hibernateLazyInitializer", "handler"})를 붙이는 관행이 생기는데, 엔티티에 ORM 구현체 내부 사정과 직렬화 라이브러리 사정이 동시에 새겨진다는 점에서 이미 신호가 나쁘다.

1층만 말하면 왜 부족한가 — 1층은 전부 우회 가능하다 순환 참조는 @JsonIgnore로, 지연 로딩은 fetch join이나 Hibernate5Module로, 프록시는 @JsonIgnoreProperties로 막힌다. 우회 가능한 이유만 대면, 상대가 우회책을 제시하는 순간 논거가 사라진다. 2층과 3층은 우회할 수 없는 이유들이다. 그래서 반드시 올라가야 한다.

4. 2층 — 결합도, 그리고 "두 구조는 애초에 다른 축이다"

4-1. 종속은 양방향으로 아프다

엔티티를 그대로 반환하면 테이블 구조가 곧 API 계약이 된다. 이 종속은 양쪽으로 비용을 만든다.

DB → API 방향

  • 컬럼명 user_nm을 user_name으로 바꾸는 리팩터링이 클라이언트를 깨뜨린다.
  • Order.address 문자열을 Address 값 객체로 분리했더니 응답 JSON 모양이 바뀐다.

  • 화면이 "주문자 이름 옆에 등급 뱃지"를 요구한다.

4-2. 더 근본적인 이유 — 두 구조는 애초에 다른 축이다 상위권 신호

여기가 이 문항에서 가장 깊은 논거이고, 면접에서 이걸 스스로 꺼내면 상위권 신호다. 먼저 용어 하나를 풀고 간다.

애그리거트(Aggregate)는 한 덩어리로 함께 생성·수정·삭제되고 하나의 트랜잭션으로 정합성을 지키는 객체 묶음이다. "여러 객체를 하나로 모아 놓은(aggregate) 단위"라는 뜻이다.

같은 애그리거트
Order와 그에 딸린 OrderItem들 — 한 덩어리로 저장되고 한 덩어리로 취소된다. 대표 객체 Order가 애그리거트 루트.
다른 애그리거트
Review — 주문과 함께 생기지도 사라지지도 않는다. 나누는 기준은 화면이 아니라 "어디까지를 한 트랜잭션으로 지킬 것인가".

엔티티의 구조를 결정하는 축

"데이터를 어떻게 저장하고 정합성을 지킬 것인가"
→ 정규화, 애그리거트 경계, 트랜잭션 단위

화면의 구조를 결정하는 축

"사용자가 한 번에 무엇을 봐야 하는가"
→ 이 축은 저장 구조와 아무 상관이 없다

두 축은 우연히 겹칠 수는 있어도 같아질 수는 없다 — 그래서 다음 결론이 나온다

2층을 한 문장으로 압축하면

엔티티가 바뀌는 이유와 API 응답이 바뀌는 이유는 서로 다르다. 그래서 두 개여야 한다.

엔티티는 저장·정합성 요구가 바뀔 때 바뀌고, 응답은 화면·클라이언트 요구가 바뀔 때 바뀐다. 하나로 합쳐두면 한쪽 이유로 바뀔 때마다 반대쪽이 영향을 받는다. DTO 클래스가 늘어나는 것은 비용이 아니라 그 두 이유를 분리해 산 값이다.

5. 3층 — opt-out과 opt-in, 실수의 방향이 반대다 실무 최강 논거

이 층이 실무에서 가장 강력하고, 면접에서 가장 적게 언급된다. 앞의 두 층은 "성능이 나빠진다", "유지보수가 힘들어진다"라는 정도의 문제지만, 이 층은 사고다.

opt-out — 기본이 포함
빼려면 사람이 명시적으로 빼야 하는 방식("빠져나온다").
= 엔티티를 그대로 반환 — 필드를 추가하면 아무 조치 없이 자동으로 응답에 실린다. 막는 쪽이 사람의 일.
opt-in — 기본이 제외
넣으려면 사람이 명시적으로 넣어야 하는 방식("들어간다").
= DTO 반환 — 엔티티에 필드가 100개 추가돼도 응답은 그대로. 내보내는 쪽이 사람의 일.
비유 — 공항 보안 검색대의 두 방식 opt-out은 반입 금지 목록(블랙리스트) 검색이다. 목록에 적히지 않은 물건은 전부 통과한다. 새로운 위험물이 생겼는데 목록에 추가하는 걸 깜빡하면 그대로 들어간다.
opt-in은 허용 목록(화이트리스트) 검색이다. 목록에 적힌 것만 통과하므로, 목록에 넣는 걸 깜빡하면 필요한 물건이 안 들어올 뿐이다. 둘 다 사람이 목록을 관리하지만, 깜빡했을 때 벌어지는 일이 정반대다.

6. 요청 방향은 더 위험하다 — mass assignment 가장 자주 놓침

응답 얘기만 하다 끝내면 절반이다. @RequestBody로 엔티티를 받는 코드가 훨씬 위험하고, 훨씬 흔하다.

문제 ① 안전해 보이지만 그릇이 열려 있다
// 회원 정보 수정 API. 이름과 이메일만 바꾸라고 만든 것이다.
@PatchMapping("/members/{id}")
public void update(@PathVariable Long id,
                   @RequestBody Member member) {
    Member found = memberRepository.findById(id).orElseThrow();
    found.setName(member.getName());
    found.setEmail(member.getEmail());
}
// "이름과 이메일만" 반영하므로 이 형태는 그나마 낫다.
문제 ② 더 흔하고 더 위험한 형태 — 통째로 저장
@PutMapping("/members/{id}")
public void update(@PathVariable Long id,
                   @RequestBody Member member) {
    member.setId(id);
    memberRepository.save(member);   // merge → 전 필드 덮어쓰기
}
// Jackson 은 요청 JSON 의 필드를 대상 객체에 그대로 채운다.
// role 도, point 도 전부 세팅되고, save() 가 그 값을 DB 에 반영한다.

여기서 흔한 오해 두 개 — 짚으면 가산점

@Valid는 막지 못한다

검증은 "값이 올바른가"를 보지 "이 필드를 받아도 되는가"를 보지 않는다. role: "ADMIN"은 완벽하게 유효한 값이다.

@InitBinder도 막지 못한다

WebDataBinder.setDisallowedFields()는 폼 바인딩(@ModelAttribute) 경로의 장치다. @RequestBody는 HttpMessageConverter(Jackson)가 처리하므로 WebDataBinder를 아예 거치지 않는다.

즉 "바인딩 화이트리스트를 걸어뒀으니 괜찮다"는 말이 이 경로에서는 성립하지 않는다. 올바른 형태는 받는 그릇 자체를 좁히는 것이다.

AFTER 받을 수 있는 필드를 타입으로 제한한다
public record MemberUpdateRequest(
        @NotBlank String name,
        @Email String email) { }

@PatchMapping("/members/{id}")
public void update(@PathVariable Long id,
                   @RequestBody @Valid MemberUpdateRequest request) {
    memberService.updateProfile(id, request.name(), request.email());
}
// role, point 를 보내도 채울 자리가 없다 — Spring Boot 기본 설정에서는
// 모르는 필드가 조용히 무시된다(FAIL_ON_UNKNOWN_PROPERTIES 비활성).
// 400 으로 거절하고 싶으면 그 설정을 켜면 된다.
응답 쪽 opt-in과 정확히 같은 원리다 나갈 수 있는 것을 명시하듯, 들어올 수 있는 것도 명시한다. 그리고 권한·잔액처럼 민감한 상태는 애초에 setter가 아니라 도메인 메서드로만 바뀌게 만들면(member.promoteToAdmin(승인자)) 한 겹 더 튼튼해진다.
확인 범위 FAIL_ON_UNKNOWN_PROPERTIES가 Spring Boot에서 기본 비활성인 것은 Jackson 자동 구성의 동작이지만, 프로젝트가 ObjectMapper를 직접 등록했다면 달라진다. 면접에서 단정하기보다 "기본값은 무시하는 쪽이고, 필요하면 켜서 거절할 수 있다" 정도로 말하는 게 안전하다.

6-1. 나머지 운영 비용 — 짧게 세 가지

응답 크기
필요 없는 컬럼까지 전부 실린다. 목록 API에서 행마다 TEXT 컬럼 하나가 딸려 나가면 응답이 수십 배가 된다. 조회 전용이면 애초에 DTO 프로젝션이 맞다.
내부 스키마 노출
필드 이름·id 채번 방식·연관 구조가 그대로 드러난다. 그 자체로 치명적이진 않지만, 공격자에게 시스템 지도를 그려주는 셈이다.
문서 · 계약 관리
OpenAPI 스키마가 엔티티에서 생성되면 문서가 DB 스키마를 따라 흔들린다. 클라이언트 팀은 어떤 필드가 계약이고 어떤 필드가 우연히 있는 건지 구분할 수 없다.

7. 반론 — "그냥 @JsonIgnore 붙이면 되지 않나요?" 가장 자주 나오는 반박

이 반론은 코드리뷰에서 실제로 자주 나온다. 그리고 부분적으로 맞다. 순환 참조도 막히고, 지연 로딩 필드도 안 탄다. 그래서 "안 됩니다"라고만 답하면 설득이 안 된다.

동작 층과 설계 층을 나눠서 답한다 — "동작이 안 된다"가 아니라 "동작해도 문제"라는 층에서

7-1. 동작 층 — 필드에 붙는 전역 스위치라 API별 요구를 못 담는다

전역 이 한 줄이 모든 엔드포인트에 적용된다
@Entity
public class Order {
    @JsonIgnore                  // 이 한 줄이 전역이다
    @ManyToOne(fetch = LAZY)
    private Member member;
}

동시에 만족시킬 수 없는 두 요구

  • 관리자 API: 주문 조회 시 주문자 실명·연락처가 필수
  • 사용자 API: 다른 사람 정보는 절대 노출 금지

관리자 쪽을 살리려고 떼면 사용자 API에서 정보가 새고, 사용자 쪽을 지키려고 붙이면 관리자 화면이 빈다.

결국 어느 한쪽에서 우회 코드를 쓰게 되고, 그 우회 코드가 결국 DTO다 처음부터 DTO를 썼으면 됐을 일을 반 바퀴 돌아 도착하는 셈이다.

7-2. @JsonView로 갈라도 조합이 늘면 무너진다

참고 뷰(마커 인터페이스)별로 필드를 갈라내는 방식 — 동작은 한다
class Views {
    interface Public {}
    interface Admin extends Public {}
}

@Entity
public class Order {
    @JsonView(Views.Public.class) private Long id;
    @JsonView(Views.Admin.class)  private Member member;   // 관리자에게만
}

@GetMapping("/admin/orders/{id}")
@JsonView(Views.Admin.class)   // 컨트롤러에서 뷰를 지정해야 발동한다 — 깜빡하면 필터가 통째로 안 걸린다
public Order adminGet(@PathVariable Long id) { ... }
① 조합 폭발
실무의 요구는 "공개/관리자" 2단이 아니라 엔드포인트 수만큼 다르다. 파트너사는 정산율은 보되 내부 메모는 못 보고, 모바일은 목록에선 요약만… 뷰 인터페이스가 조합만큼 늘고, 어떤 필드가 어떤 뷰인지가 엔티티 한 파일에 흩어진다.
② 누락이 조용하다
새 필드에 @JsonView를 안 붙이면 어느 뷰에서 보이는지가 설정에 달려 있다. 즉 "필드를 추가했는데 어디로 나가는지가 프레임워크 설정에 좌우된다" — 5절의 opt-out 문제와 정확히 같은 구조.
③ 성능 문제는 그대로
뷰에 포함된 연관은 여전히 직렬화 시점에 초기화된다. 즉 3절의 쿼리 폭증은 하나도 해결되지 않는다.

DTO는 "이 파일 하나 읽으면 이 응답이 전부"인데, @JsonView는 엔티티 전체를 훑으며 머릿속에서 뷰별로 필터링해야 읽힌다. 읽는 비용부터 다르다.

확인 범위 MapperFeature.DEFAULT_VIEW_INCLUSION의 Jackson 자체 기본값은 활성(포함)이고, Spring의 Jackson2ObjectMapperBuilder 계열 구성이 이를 비활성으로 바꾸는 것으로 알려져 있다. 다만 Spring Boot 버전과 Jackson 계열의 기본값 변화는 확인이 필요하다. 면접에서는 버전별 기본값을 단정하지 말고 "뷰가 지정되지 않은 필드의 처리 방식이 설정에 의존한다는 것 자체가 위험"이라는 논지로 말하는 게 낫다.

7-3. 더 근본적인 문제 — 엔티티가 응답 템플릿이 된다 반론을 이기는 지점

문제는 @JsonIgnore가 동작하느냐가 아니라, 그 순간 엔티티에 표현 계층의 관심사가 새겨진다는 것이다

@JsonIgnore, @JsonView, @JsonProperty("order_no"), @JsonIgnoreProperties({"hibernateLazyInitializer","handler"})가 하나씩 붙을 때마다 엔티티는 "이 데이터가 무엇인가"를 말하는 도메인 모델에서 "이 데이터를 어떻게 보여줄 것인가"를 말하는 응답 템플릿으로 옮겨간다. 어느 순간 그 클래스는 저장 구조와 응답 구조를 동시에 책임지는 클래스가 되고, 그때부터 어떤 변경도 양쪽을 다 고려해야 한다 — 4-2절의 "변경의 이유가 다르면 분리한다"의 정반대다.

7-4. Hibernate5Module 같은 우회책도 성격이 같다 — 해결이 아니라 은폐

지연 로딩 프록시를 예외 대신 null로 직렬화해 주는 Jackson 모듈이 있다(하이버네이트 버전에 맞춰 Hibernate5Module / Hibernate6Module). 예외는 사라진다.

그런데 이건 해결이 아니라 은폐이고, 은폐 중에서도 나쁜 쪽이다 예외는 시끄럽게 터져 즉시 발견되지만 null은 조용히 잘못된 응답을 내보낸다. 클라이언트는 "주문 항목이 없는 주문"을 정상 200 응답으로 받는다. 데이터가 틀린 채 나가는 200이 500보다 훨씬 늦게 발견되고 훨씬 비싸게 수습된다.
우회책 3종 대조 — 세 개 다 "엔티티를 직렬화하겠다"는 전제 자체는 건드리지 않는다
수단순환 참조지연 로딩 예외직렬화 시 쿼리API마다 다른 요구새 필드 자동 유출여러 애그리거트 조합엔티티에 남는 것
@JsonIgnore 막힌다 막힌다 (붙인 필드만) 붙인 필드만 — 나머지는 그대로 불가 — 전역 스위치 하나 그대로 유출 — opt-out 유지 불가능 표현 계층 관심사
@JsonView 뷰에서 빼면 막힘 뷰에서 빼면 막힘 뷰에 포함된 연관은 그대로 초기화 가능하지만 조합 폭발 설정 의존 (뷰 미지정 필드) 불가능 뷰 인터페이스가 흩어짐
Hibernate5·6Module 못 막는다 예외 대신 null (은폐) 미초기화 연관은 쿼리 없이 틀린 200 불가 그대로 유출 불가능 Jackson 모듈 의존
DTO 애초에 없음 애초에 없음 (트랜잭션 안 변환) 변환 코드에 드러남 → fetch join 화면마다 따로 안 나간다 — opt-in 가능 아무것도 안 남는다
세 개 다 "엔티티를 직렬화하겠다"는 전제를 편하게 만들어주는 도구일 뿐이다. 답은 전제를 없애는 것이다.

8. 실무 적용 — 변환 위치 · 비용 · 그리고 빌드가 지키게 하기

8-1. 변환은 트랜잭션 안에서 한다 가산점

"DTO를 쓴다"까지만 말하면 절반이다. 어디서 변환하는가가 나머지 절반이다.

BEFORE 컨트롤러에서 변환 — 트랜잭션 밖이다
@GetMapping("/orders/{id}")
public OrderResponse get(@PathVariable Long id) {
    Order order = orderService.findById(id);  // 여기서 트랜잭션 종료
    return OrderResponse.from(order);         // 지연 로딩 필드 만나면 예외
}
AFTER 서비스 트랜잭션 안에서 변환을 끝낸다
@Service
public class OrderService {

    @Transactional(readOnly = true)
    public OrderResponse getOrder(Long id) {
        Order order = orderRepository.findWithItemsById(id); // 필요한 것만 fetch join
        return OrderResponse.from(order);   // 트랜잭션 안에서 변환 완료
    }
}
OSIV 문항과 여기서 만난다 연결하면 원칙이 있는 사람 이건 OSIV 전환 순서의 ①②단계와 정확히 같은 작업이다. 엔티티 노출 금지는 "엔티티는 영속성 컨텍스트 안에서만 존재한다"는 규칙을 사람의 규율로 지키는 것이고, OSIV 끄기는 같은 규칙을 런타임이 강제하게 만드는 것이다.

8-2. "DTO는 귀찮다"에 답하기 — 비용이 없다고 우기면 오히려 신뢰를 잃는다

① record로 선언 비용을 줄인다
생성자·게터·equals·toString이 자동이라 응답 DTO는 사실상 한 줄이다.
② 조회 전용이면 생성자 프로젝션
DB에서 바로 DTO로 받으면 엔티티를 거치지 않으므로 지연 로딩·스냅샷 비용도 함께 사라진다. 변환 단계 자체가 없어진다.
③ 매핑이 정말 많으면 MapStruct
컴파일 시점에 매핑 코드를 생성 → 런타임 리플렉션 비용 없음, 매핑 누락을 컴파일 에러로(unmappedTargetPolicy = ERROR). opt-in 성질은 유지된다.
② JPQL 생성자 프로젝션 — 필요한 컬럼만 SELECT되고 결과가 곧바로 DTO다
@Query("""
    select new com.example.order.dto.OrderSummary(o.id, o.status, m.name)
    from Order o join o.member m
    where o.createdAt >= :from
    """)
List<OrderSummary> findSummaries(@Param("from") LocalDateTime from);
// QueryDSL 의 Projections.constructor(...) 도 같은 일을 타입 안전하게 해 준다.

트레이드오프도 같이 말한다 — 세 가지 함정

리플렉션 매퍼는 신중히
이름이 같으면 알아서 복사하는 방식(ModelMapper 등)은 편하지만 매핑 실수와 예상 못 한 필드 복사를 조용히 통과시킨다. 5절에서 얻은 안전성을 다시 반납하는 셈.
DTO 재사용의 유혹
여러 엔드포인트가 DTO 하나를 공유하면 "이 필드는 A 화면용, 저건 B 화면용"이 섞이고, 엔티티를 노출할 때와 똑같은 결합 문제가 DTO 층에서 재현된다. 화면이 다르면 DTO도 다른 게 기본.
요청 DTO와 응답 DTO는 합치지 않는다
필드 요구가 애초에 다르고, 합치는 순간 요청 쪽에 응답 전용 필드가 열려 mass assignment 표면이 다시 생긴다.

8-3. 구조를 룰로 고정한다 — ArchUnit은 양방향으로 건다 시니어 변별

"엔티티를 반환하지 않기로 합시다"는 대책이 아니다. 사람이 지키는 규칙은 새 팀원이 오거나 급한 릴리스가 하나 지나가면 무너진다. 이 문서 전체의 결론을 지키는 유일한 방법은 빌드가 대신 지키게 하는 것이다.

반환 타입만 막으면 절반이다. @RequestBody 파라미터를 막지 않으면 6절의 mass assignment 경로가 그대로 열려 있다

그리고 실무에서 요청 쪽이 더 자주 놓친다. 리뷰어의 눈이 "응답에 뭐가 나가나"에는 가 있어도 "요청으로 뭐가 들어오나"에는 잘 안 가기 때문이다.

ArchUnit 요청 방향 — 컨트롤러 파라미터 타입에 엔티티가 있으면 빌드 실패
@ArchTest
static final ArchRule 컨트롤러는_엔티티를_파라미터로_받으면_안_된다 =
        methods()
            .that().areDeclaredInClassesThat().areAnnotatedWith(RestController.class)
            .and().arePublic()
            .should(new ArchCondition<JavaMethod>("파라미터 타입에 @Entity 가 없어야 한다") {
                @Override
                public void check(JavaMethod method, ConditionEvents events) {
                    method.getParameterTypes().stream()
                          .flatMap(WebLayerRulesTest::flatten)   // 제네릭 안쪽까지 펼친다
                          .filter(type -> type.isAnnotatedWith(Entity.class))
                          .forEach(type -> events.add(SimpleConditionEvent.violated(
                                  method, method.getFullName() + " 가 엔티티 "
                                      + type.getSimpleName() + " 를 파라미터로 받는다")));
                }
            });

flatten이 여기서도 핵심이다

위반은 Member를 직접 받는 형태보다 List<Member>, Optional<Member>처럼 제네릭 안에 숨은 형태가 많다. 겉 타입만 검사하면 대부분을 놓친다. 반환 타입 룰의 flatten과 같은 헬퍼를 공유하면 된다.

@RequestBody만 걸러도 되지만 전부 막는 편이 낫다

@ModelAttribute 폼 바인딩도 같은 위험이 있고, @PathVariable에 엔티티가 올 일은 어차피 없다. 규칙은 예외가 적을수록 오래 산다.

가장 강력 계층 자체를 끊는다 — 반환·파라미터·지역 변수·import를 한꺼번에
@ArchTest
static final ArchRule 웹_계층은_엔티티에_의존하지_않는다 =
        noClasses().that().resideInAPackage("..api..")
                   .should().dependOnClassesThat().resideInAPackage("..domain.entity..");
// 기존 코드가 대량으로 걸리므로, 신규 모듈부터 적용하고
// 레거시는 FreezingArchRule 로 동결한 뒤 목록을 줄여나가는 방식이 현실적이다.
확인 범위 methods(), ArchCondition, SimpleConditionEvent, FreezingArchRule은 ArchUnit 공개 API이지만 정확한 시그니처는 버전에 따라 다르다(특히 파라미터 타입·파라미터 어노테이션 접근 API는 버전 편차가 있다). 면접에서 중요한 것은 API 이름이 아니라 "반환과 파라미터 양방향을 막아야 하고, 제네릭 안쪽까지 재귀로 펼쳐야 한다"는 설계 포인트다.

8-4. 세 층의 안전망을 함께 놓고 본다

9-1. 면접 전날 이것만 — 질문을 보고 답을 먼저 떠올린 뒤 카드를 읽는다

답변 골격은?
터 · 묶 · 샌 — ① 기술: 터진다(혹은 조용히 폭증) ② 설계: API가 DB 스키마에 묶인다 ③ 보안: 새 필드가 샌다. 난이도가 아니라 파급 범위 순서.
1층의 세 가지는?
지 · 순 · 프 — 지연 로딩(LazyInitializationException) · 순환 참조(StackOverflowError) · 프록시(No serializer found). 원인은 하나 — 직렬화기가 게터를 전부 호출한다.
대표 숫자 101은?
주문 20건 · 항목 3개일 때 1 + 20(member) + 20(items) + 60(item) = 101. 중첩된 N+1이고, 이 쿼리를 부른 코드가 프로젝트에 존재하지 않는다.
OSIV 켜진 쪽이 더 나쁜 이유?
200 OK · DEBUG 로그(운영 미출력) · 통합 테스트 통과. 예외는 시끄러워 즉시 잡히지만, 이쪽은 커넥션 풀 고갈로 전 서비스가 느려진 뒤에 발견된다.
2층에서 반박 불가 논거는?
"엔티티 구조와 화면 요구는 애초에 다른 축" — 외부 API·집계·다른 애그리거트를 조합해야 하면 표현 자체가 불가능하다. 불편이 아니라 불가능.
3층 한 문장은?
안전한 설계는 "실수하지 않으면 안전"이 아니라 "실수해도 안전". opt-out은 아무것도 안 하면 사고, opt-in은 의도적으로 써야 사고.
mass assignment를 못 막는 것 둘?
@Valid(값이 유효한지만 본다 — role:"ADMIN"은 유효한 값) · @InitBinder/setDisallowedFields(@RequestBody는 WebDataBinder를 안 거친다).
@JsonIgnore 반론의 최종 답은?
동작 여부가 아니라 방향 — 도메인이 Jackson을 알게 되고 엔티티가 응답 템플릿이 된다. 그리고 존재하지 않는 연관은 어떤 어노테이션으로도 직렬화할 수 없다.
변환은 어디서?
서비스 트랜잭션 안에서 끝낸다. 경계 밖으로 나가는 것은 값이 다 채워진 DTO뿐. 그래야 OSIV 설정에 의존하지 않는 코드가 된다.
규율은 누가 지키나?
ArchUnit이 양방향으로 — 컨트롤러 반환 타입 + @RequestBody 파라미터. 제네릭 안쪽까지 flatten하고, 레거시는 FreezingArchRule로 동결.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

DTO도 결국 엔티티 필드를 그대로 옮겨 적잖아요. 클래스만 두 개고 내용은 같은데 뭐가 다른가요? 필수힌트: "모양이 같은 것"과 "성질이 같은 것"을 가른다 — 세 가지

모양이 같은 것과 성질이 같은 것은 다르다. 지금 필드가 100% 겹치더라도 세 가지가 다르다.

① 변경의 이유가 다르다. 엔티티는 저장·정합성 요구로 바뀌고 DTO는 화면·클라이언트 요구로 바뀐다. 지금 같아 보이는 것은 아직 두 요구가 갈라지지 않았을 뿐이다. 갈라지는 날, 합쳐뒀으면 한쪽이 다른 쪽을 끌고 다닌다.

② 실수의 방향이 다르다. 엔티티에 필드가 추가되면 자동으로 노출되지만, DTO는 누군가 명시적으로 써야 노출된다. 이건 필드가 겹치는 것과 무관한 성질이다.

③ 표현할 수 있는 범위가 다르다. DTO는 여러 애그리거트와 외부 API 결과를 조합할 수 있지만 엔티티는 못 한다.

덧붙이면 좋다 — "완전히 겹치는 상태가 오히려 정상이고, 그때 분리해두는 게 싸다.
갈라진 뒤에 분리하려면 이미 클라이언트가 붙어 있어서 못 한다."
DTO를 쓰면 N+1이 자동으로 해결되나요? 함정힌트: "아니다"로 시작하고, 그 대신 무엇이 달라지는지를 말한다

아니다. DTO 변환 코드가 order.getItems()를 순회하면 지연 로딩은 똑같이 일어나고 쿼리도 똑같이 늘어난다. DTO는 N+1을 없애는 장치가 아니다.

바뀌는 것은 문제가 보이는 위치다. 엔티티를 그대로 반환하면 쿼리를 유발하는 지점이 코드에 존재하지 않는다(직렬화기가 부른다). DTO 변환에서는 그 순회가 내가 쓴 코드로 눈앞에 있다. 그래서 fetch join을 붙일 자리도, 리뷰에서 지적할 자리도 명확해진다.

진짜 해결은 조회 방법을 바꾸는 것이다 — ToOne 연관은 fetch join, 컬렉션은 default_batch_fetch_size, 조회 전용이면 생성자 프로젝션으로 애초에 엔티티를 거치지 않기. DTO는 "무엇을 내보낼지"를 정하는 장치이고, "어떻게 가져올지"는 별개 문제다.

요청 DTO와 응답 DTO를 하나로 합쳐 쓰면 안 되나요? MemberDto 하나면 될 것 같은데요. 필수힌트: 두 가지가 동시에 깨진다 — 하나는 보안, 하나는 검증

안 된다. 두 가지가 동시에 깨진다.

보안: 응답에 필요한 필드(id, role, point, createdAt)가 요청 쪽에도 열린다. 그 순간 mass assignment 표면이 DTO 층에서 그대로 재현된다. 엔티티를 안 쓰기로 해놓고 같은 구멍을 다시 판 셈이다.

검증: 요청에는 @NotBlank 같은 제약이 필요하지만 응답에는 무의미하다. 합치면 응답 전용 필드에까지 검증 애노테이션이 붙거나, 요청 검증이 느슨해진다.

원칙은 "들어오는 것과 나가는 것은 방향이 다르므로 타입도 다르다". 이름도 MemberDto 같은 중립적 이름 대신 MemberUpdateRequest / MemberResponse처럼 방향이 드러나게 짓는 편이 실수를 줄인다.

내부 관리자 도구나 서버-투-서버 API도 전부 DTO로 감싸야 하나요? 설계 판단힌트: "항상"이라고 답하면 감점이다. 판단 축 하나를 말한다

"항상"이라고 답하면 오히려 감점 요인이다. 기준을 말하는 게 답이다. 판단 축은 하나 — "이 응답의 계약을 내가 언제든 깰 수 있는가."

깰 수 없다 → DTO 필수

외부 공개 API, 파트너사 연동, 앱 클라이언트(구버전이 스토어에 남는다), 다른 팀이 소비하는 사내 API. 소비자를 내가 통제할 수 없으면 계약을 분리해야 한다.

깰 수 있다 → 완화 여지

나만 쓰는 내부 관리자 화면, 같은 배포 단위로 함께 나가는 BFF. 그래도 opt-out 위험은 그대로 남는다 — 관리자 도구야말로 민감 필드가 많아 "내부용이니까"가 가장 위험한 문장이 되는 경우가 흔하다.

현실적인 절충 — "응답 DTO는 상황에 따라 완화할 수 있지만,
@RequestBody로 엔티티를 받는 것은 예외 없이 금지한다."

유출은 정보 공개지만 mass assignment는 데이터 변조라 피해 규모가 다르고, 내부망이라는 전제가 무너지는 순간(SSRF, 계정 탈취) 그대로 뚫린다.

이미 @JsonIgnore가 수백 군데 붙어 있는 레거시입니다. 전부 DTO로 바꾸려면 몇 달인데, 무엇부터 하시겠습니까? 시니어 변별힌트: 전면 리팩터링은 답이 아니다. 첫 번째 항목이 나머지 전부보다 가치가 크다

전면 리팩터링은 답이 아니다. 몇 달짜리 작업은 중간에 우선순위에 밀려 절반만 끝나고, 절반만 끝난 상태가 가장 나쁘다(두 규칙이 공존해 아무도 뭐가 맞는지 모른다). 순서는 위험도 순, 그리고 되돌리기 쉬운 것부터다.

1
출혈을 먼저 멈춘다. ArchUnit 룰을 FreezingArchRule로 걸어 기존 위반은 통과시키고 신규 위반만 빌드를 깨게 한다. 하루면 끝나고, 그날부터 문제가 더는 늘지 않는다. 비용 대비 효과가 가장 커서 반드시 첫 번째여야 한다.
2
요청 방향부터 고친다. 응답 유출보다 mass assignment가 피해가 크고, 대상 수는 훨씬 적다(쓰기 API가 읽기 API보다 적다). 위험은 높고 작업량은 적은 구간.
3
민감 엔티티를 골라 응답을 고친다. 전수 조사 대신 축을 정한다 — 개인정보 · 금액/정산 · 인증 정보. "모든 엔티티"가 아니라 "유출되면 사고가 되는 엔티티"로 범위를 좁혀야 실제로 끝난다.
4
나머지는 만질 때 고친다. 어차피 그 파일을 수정하게 될 때 함께 옮긴다. 별도 일정을 잡지 않으므로 협상이 필요 없다.
5
동결 목록의 크기를 지표로 삼는다. 스프린트마다 남은 위반 수가 줄어드는지만 본다. "언제 다 끝나나"보다 "단조 감소하고 있나"가 관리 가능한 질문이다.
핵심 한 문장 — "고치는 것보다 늘지 않게 막는 게 먼저다."
@JsonIgnore를 떼고 DTO로 바꿨더니 성능이 더 나빠졌습니다. 왜일까요? 시니어 변별힌트: 그 어노테이션이 우연히 무슨 역할을 하고 있었는지 생각한다

충분히 일어난다. @JsonIgnore가 붙어 있던 필드는 직렬화 대상이 아니었으므로 지연 로딩도 안 탔다. 그 어노테이션이 우연히 "가져오지 마"라는 성능 가드 역할을 하고 있었던 것이다.

DTO로 바꾸면서 화면에 필요하다는 이유로 그 연관을 매핑에 포함시키면, 이제는 실제로 로딩된다. 없던 쿼리가 생긴 게 아니라 원래 필요했지만 어노테이션에 가려 안 나가던 데이터가 드러난 것이다. 화면이 그 값을 실제로 쓰고 있었다면 이전에는 그 자리가 비어 있었다는 뜻이므로, 성능이 나빠진 게 아니라 결함이 드러난 것일 수도 있다.

진단과 처방은 이렇게 나눈다.

  • 정말 필요한 데이터인가? 아니라면 DTO에서 그 필드를 빼면 끝이다 — opt-in의 이점이 여기서 나온다(뺄 수 있는지 판단할 자리가 코드에 생긴다).
  • 필요하다면 조회 방법을 고친다. fetch join / batch fetch size / 생성자 프로젝션. DTO는 "무엇을 내보낼지", 조회 전략은 "어떻게 가져올지" — 섞으면 진단이 어긋난다.
  • 쿼리 수를 테스트로 고정한다. 바꾸기 전후의 쿼리 수를 단정해두면 이런 논쟁이 숫자로 끝난다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

record OrderResponse(Order order)처럼 record로 감쌌으면 DTO 맞죠? 함정힌트: 직렬화기가 결국 무엇을 훑게 되는지 따라가 본다

아니다. 겉만 DTO다. Jackson은 OrderResponse를 훑다가 order 프로퍼티를 만나고, 그 안으로 들어가 결국 엔티티의 게터를 전부 호출한다. 즉 2절의 그래프 순회가 그대로 재현되고, 5절의 opt-out도 그대로다 — 엔티티에 필드가 추가되면 order 아래에 자동으로 실려 나간다.

판별 기준 — DTO의 필드 타입에 엔티티가 등장하면, 그것은 DTO가 아니라 "엔티티를 담은 봉투"다

같은 이유로 Page<Order>, List<Order>, ApiResponse<Order>도 전부 같은 문제다. ArchUnit 룰에서 flatten으로 제네릭 안쪽까지 펼치는 이유가 정확히 이것이다 — 겉 타입만 보면 이 위반들을 전부 놓친다.

트랜잭션 안에서 fetch join으로 전부 채워왔다면 엔티티를 반환해도 되지 않나요?힌트: 막히는 층과 안 막히는 층을 가른다. 그리고 새로 생기는 결합이 하나 더 있다

1층은 상당 부분 막힌다. 초기화가 끝난 그래프라면 지연 로딩 예외도, 직렬화 시점의 추가 쿼리도 안 난다(양방향 순환 참조는 여전히 남는다).

그런데 2층과 3층은 하나도 해결되지 않는다. 컬럼명을 바꾸면 여전히 클라이언트가 깨지고, 엔티티에 settlementRate가 추가되면 여전히 아무도 응답 코드를 안 건드렸는데 새어 나간다.

게다가 결합이 하나 더 생긴다. "어디까지 fetch join 했는가"가 곧 API 응답 스펙이 된다. 성능 튜닝을 하려고 fetch join 하나를 빼는 순간 응답 JSON에서 필드가 사라지고 클라이언트가 깨진다. 조회 전략과 API 계약이 한 몸이 되는 것이라, 둘 중 어느 쪽도 자유롭게 못 바꾸게 된다.

정리하면 — "가장 시끄러운 증상만 사라지고, 구조적 문제는 전부 남는다."

@JsonProperty(access = READ_ONLY)를 쓰면 mass assignment는 막히는 것 아닌가요? 가산점힌트: "그 필드에 한해서는 맞다"로 시작하고, 그다음 층으로 올라간다

그 필드에 한해서는 맞다. access = READ_ONLY는 직렬화(내보내기)에만 쓰이고 역직렬화(받기)에서는 무시되게 만드는 설정이라, role에 붙여두면 요청 본문의 role은 채워지지 않는다.

그런데 층이 하나도 안 올라갔다. ① 여전히 opt-out이다 — 새로 추가되는 필드는 기본이 "열림"이고, 누군가 매번 손으로 붙여야 한다. ② 여전히 전역이다 — 어떤 API에서는 받아야 하는 필드를 다른 API에서만 막을 방법이 없다. ③ 여전히 엔티티에 표현 계층 관심사가 새겨진다.

가장 중요한 반박은 이것이다 — 이 방식은 "어떤 필드가 위험한지 아는 사람이 그 자리에 있다"를 전제한다. 그런데 5절에서 본 대로 그 사람은 6개월 뒤의 PR에 없다. 인증 리팩터링을 하는 개발자는 자기가 추가한 passwordHash가 어느 API로 나가는지 모른다. 주의력을 요구하는 대책은 주의할 사람이 없을 때 실패한다.

서비스가 DTO를 반환하면 서비스(도메인)가 웹 계층 타입을 알게 되는 것 아닌가요? 7-3절의 의존 방향과 모순 아닌가요? 시니어 변별힌트: "DTO를 누가 소유하는가"를 나눠서 답한다

좋은 지적이고, 답은 "DTO를 누가 소유하느냐"로 갈린다. 문제가 되는 것은 도메인이 Jackson 같은 웹 기술에 의존하는 것이지, 응용 계층이 자기 출력 타입을 갖는 것이 아니다.

실무적인 정리는 이렇다. 서비스가 반환하는 DTO는 응용(application) 계층 소유로 둔다 — 프레임워크 애노테이션 없이 record로만 선언된 순수한 타입이면 의존 방향이 뒤집히지 않는다. 그리고 웹 전용 표현(페이지 래핑, 공통 응답 봉투, 필드 네이밍 규칙, HATEOAS 링크)이 필요하면 웹 계층에서 한 번 더 감싼다.

트레이드오프도 같이 말하는 게 좋다. 계층마다 타입을 두면 매핑이 두 번이라 비용이 있다. 그래서 판단 기준은 "웹 표현 요구가 실제로 갈라졌는가"다 — 갈라지지 않았다면 응용 계층 DTO를 웹에서 그대로 쓰고, 갈라지는 시점에 웹 DTO를 도입한다.

지켜야 할 선 하나만 기억하면 된다 — 엔티티에는 어떤 직렬화 애노테이션도 붙지 않는다. 이 선만 지키면 DTO를 어느 계층에 두든 방향은 무너지지 않는다.

한 줄 요약
"엔티티를 노출하면 안 되는 이유"에는 하나가 아니라 세 층으로 답한다 — 직렬화기가 연관을 타고 들어가 터지거나(OSIV off) 조용히 쿼리를 폭증시키고(OSIV on), API 스펙이 DB 스키마에 묶여 서로 다른 이유로 변해야 할 두 구조가 한 몸이 되며, 무엇보다 opt-out 구조라서 아무도 응답 코드를 건드리지 않아도 새 필드가 새어 나가고 요청 방향으로는 권한까지 덮어쓰인다. @JsonIgnore는 이 중 어느 것도 해결하지 못한 채 엔티티를 응답 템플릿으로 만들 뿐이고, 규율은 사람이 아니라 ArchUnit이 반환 타입과 @RequestBody 양쪽에서 지킨다.
