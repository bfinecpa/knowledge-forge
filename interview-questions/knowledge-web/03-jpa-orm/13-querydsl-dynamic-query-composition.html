QueryDSL 동적 쿼리
where(null)이 조용히 무시된다는 성질 하나가 절반을 가른다

면접 질문: "QueryDSL을 사용해본 경험이 있나요? 동적 쿼리를 어떻게 구성했나요?"

핵심 관전 포인트 — QueryDSL 동적 쿼리의 모든 관용구는 한 문장에서 나온다 — where()에 null을 넘기면 예외도 아니고 0건도 아니고 그 조건만 사라진다. where(nameEq(x), statusEq(y), null)은 null 자리만 없는 셈 치고 나머지로 쿼리를 만든다. 이걸 알면 조건마다 BooleanExpression을 반환하는 메서드를 만들어 where()에 나열하는 순간 if 여섯 줄이 통째로 사라진다. 하지만 진짜 이점은 if 제거가 아니다. BooleanBuilder는 "쌓는 통"이라 결과가 통 안에 갇히지만, BooleanExpression은 값이라서 nameEq(x).and(statusIn(y))처럼 합성하고, 다른 쿼리에서 재사용하고, 조건 자체를 단위 테스트할 수 있다. 대신 함정이 하나 — 앞쪽이 null이면 .and() 호출에서 NPE가 난다(null.and(...)). 뒤쪽 null은 안전하다(a.and(null)은 a를 그대로 돌려준다). 그래서 합성할 땐 Expressions.allOf(...)처럼 앞뒤 모두 null을 건너뛰는 유틸을 쓴다. 선택 기준은 대체가 아니라 용도 — 단순 AND 나열이면 메서드 분리, OR 중첩처럼 조건 트리를 런타임에 조립해야 하면 BooleanBuilder. 그리고 페이징 — Page 반환은 쿼리 2번이고 조건 없는 count는 전건 스캔인데, PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne)는 첫 페이지에 다 담기거나 마지막 페이지일 때 count 쿼리 자체를 생략한다. 가장 위 층의 답은 더 단순하다 — 조건 없는 전체 검색을 애초에 못 하게 만드는 구조(페이징 강제 시그니처, 페이지 크기 clamp, 필수 조건 검증).
  • 1
    관용구는 한 성질에서 나온다 — where()에 넘긴 null은 예외도 0건도 아니고 "그 조건만 사라짐"이다. 그래서 조건마다 BooleanExpression을 반환하는 메서드를 만들어 where()에 나열하면 if가 한 줄도 남지 않는다.
  • 2
    진짜 이점은 if 제거가 아니라 "조건이 값이 되는 것"이다 — 값이므로 합성(isActive().and(...))되고 재사용되고 DB 없이 단위 테스트된다. 함정은 하나 — a.and(null)은 안전하지만 null.and(a)는 NPE라서 합성은 Expressions.allOf에 맡긴다.
  • 3
    BooleanBuilder는 열등한 대안이 아니라 다른 도구고, 페이징은 구조로 막는다 — 조건 트리를 런타임에 조립해야 하면 빌더가 정직하다. 그리고 검색 API의 진짜 위험은 느린 쿼리가 아니라 조건 없이 들어온 요청이 전건을 긁는 것이라, 페이징 강제 시그니처 · 페이지 크기 clamp · 필수 조건 검증으로 그렇게 호출할 방법 자체를 없앤다.

0. 질문 + 출제 의도

조건 하나가 이름 붙은 값이 되어 합성·재사용·테스트가 열린다.

그런데 이 문항이 진짜 변별력을 갖는 자리는 한 칸 더 안쪽이다. "써봤다"고 답하는 사람은 많은데, 그중 상당수가 BooleanBuilder + if 나열에 머물러 있다. 그 자체가 틀린 코드는 아니지만, where(null)이 무시된다는 성질을 모르면 거기서 멈출 수밖에 없다. 그리고 그 성질을 모른다는 것은 곧 조건을 합성·재사용 가능한 값으로 다루는 사고에 도달하지 못했다는 뜻이다. 도구의 관용구 하나가 코드 구조 전체를 가르는 흔치 않은 사례다.

함정 두 개 ① "동적 쿼리를 어떻게 구성했나"에 개념어로 답하는 것. "조건이 들어왔는지 분기해서 where에 추가했다"는 방향은 맞지만 코드가 아니다. 이 문항은 실제로 써본 사람만 답할 수 있는 코드 수준의 서술을 기대한다 — BooleanBuilder든 BooleanExpression 메서드든 구체적인 이름과 형태를 말해야 한다.
② 페이징을 조회 성능 얘기로만 끝내는 것. 검색 API의 진짜 위험은 느린 쿼리가 아니라 조건 없이 들어온 요청이 전건을 긁는 것이고, 이걸 "조심하겠다"가 아니라 "구조로 막았다"고 말할 수 있는지에서 갈린다(7절).
이 페이지가 겨냥하는 약점 세 가지 ① 관용구를 형태로만 외운 것 → 2절에서 라이브러리 안쪽(addWhere가 null을 버리는 코드)까지 내려가 왜 그런지를 세우고, null의 비대칭(넘기면 안전 / 점 찍으면 NPE)을 못 박는다.
② BooleanBuilder + if에서 멈춘 것 → 4절에서 통과 값의 대비로 합성 · 재사용 · 테스트가 왜 값에서만 열리는지를 코드로 보이고, 5절에서 빌더가 오히려 정직한 자리까지 갈라 준다.
③ 페이징을 "count 최적화 기법"으로만 아는 것 → 6절에서 생략 · 축소 · 되묻기 세 층을 세우고, 7절에서 실수를 불가능하게 만드는 구조로 끌어올린다.
버전 기준 라이브러리 내부 코드를 인용한 부분은 Querydsl 5.1.0(querydsl-core, querydsl-jpa)과 Spring Data Commons 3.5.13 소스를 직접 대조한 것이다. null 처리 동작 자체는 QueryDSL의 오래된 계약이라 버전이 달라도 같지만, 정확한 코드 형태와 패키지 경로는 버전에 따라 다를 수 있다.

1. 전제 — QMember.member는 대체 어디서 오는가

앞으로 나올 코드는 전부 member.name.eq(...) 같은 형태인데, 이 member가 어디서 온 물건인지 모르면 "타입 안전"이라는 말도 공허하게 들린다.

QueryDSL은 쿼리를 문자열이 아니라 자바 코드로 쓰게 해주는 라이브러리다. 그러려면 테이블의 컬럼(정확히는 엔티티의 필드)을 가리킬 자바 객체가 있어야 한다. "member.name"이라는 문자열 대신 member.name이라는 필드 접근으로 쓰기 위해서다. 그 객체를 담는 클래스는 사람이 손으로 만들지 않는다 — 빌드할 때 자동으로 생성된다.

생성 주체는 어노테이션 프로세서(annotation processor)다. 컴파일러(javac)가 컴파일 도중에 호출하는 플러그인으로, 소스에 붙은 어노테이션을 읽고 새 소스 파일을 만들어내는 프로그램이다. QueryDSL이 제공하는 프로세서는 @Entity가 붙은 클래스를 전부 찾아 대응하는 클래스를 하나씩 뽑아낸다. 이름 앞에 Q(Query의 Q)를 붙인 QMember가 그것이고, 이렇게 만들어진 클래스를 통칭 Q타입이라 부른다.

QMember.member의 member는 QueryDSL이 만들어 둔 기본 인스턴스다. QMember 클래스 안에 public static final QMember member = new QMember("member")처럼 선언돼 있고, 괄호 안의 "member"는 SQL로 나갈 때 쓰이는 별칭(alias)이다. 그래서 실무에서는 정적 임포트해 쓰는 것이 관례다.

관례 정적 임포트 한 줄이 이후 모든 코드의 모양을 정한다
import static com.example.domain.QMember.member;   // 이 한 줄 덕분에 member.name 으로 쓸 수 있다

queryFactory.selectFrom(member).where(member.name.eq("김"))...
같은 테이블을 두 번 참조해야 한다면 자기 조인처럼 같은 엔티티가 두 번 등장하는 쿼리에서는 QMember m2 = new QMember("m2")처럼 별칭이 다른 인스턴스를 직접 만든다. 기본 인스턴스 하나로는 별칭이 겹치기 때문이다.
Q타입이 생성되지 않으면 그 아래 모든 코드가 컴파일조차 되지 않는다 그래서 이것이 QueryDSL 도입의 첫 관문이자 가장 흔한 실패 지점이다. 빌드 설정과 깨지는 경로는 8절 함정 ①에서 따로 다룬다.

2. 관용구의 뿌리 — where()에 넘긴 null은 그 조건만 지운다

2-1. 먼저 스스로 답해보기

이 코드는 어떻게 되나?

query.where(user.name.eq(name), null, user.age.gt(20));
①
NullPointerException이 난다
②
조건이 하나도 안 맞아 0건이 나온다
③
null인 자리만 없는 셈 치고 name = ? and age > ?로 나간다
정답과 그 의미 — 답을 정한 뒤에 펼친다 필수힌트: null은 "거짓"도 "참"도 아니다

정답은 ③이다. null은 "거짓"도 "참"도 아니고 "이 조건은 존재하지 않는다"로 해석된다. 그래서 위 쿼리는 정확히 아래와 같다.

query.where(user.name.eq(name), user.age.gt(20));

이 한 줄이 QueryDSL 동적 쿼리의 전부다. 이 성질이 있기 때문에 "조건이 있으면 넣고 없으면 안 넣는다"는 분기를 if로 쓸 필요가 없다. 조건을 만드는 쪽에서 null을 반환하기만 하면, where()가 알아서 걸러낸다.

2-2. 왜 그런가 — 라이브러리 안쪽

이건 "그렇게 동작하더라"가 아니라 명시적으로 그렇게 짜인 코드다. where(...)는 인자를 하나씩 순회하며 쿼리 메타데이터에 넣는데, 그 진입점에서 null을 즉시 걸러낸다.

source 진입점에서 null이 즉시 걸러진다
// QueryMixin — where(Predicate...)는 인자를 하나씩 addWhere로 넘긴다
public final T where(Predicate... o) {
    for (Predicate e : o) {
        metadata.addWhere(convert(e, Role.WHERE));
    }
    return self;
}

// DefaultQueryMetadata — 여기서 null이 조용히 버려진다
public void addWhere(Predicate e) {
    if (e == null) {
        return;          // 예외도 아니고 로그도 아니다. 그냥 빠져나간다.
    }
    ...
}
확인 범위 위 코드는 Querydsl 5.1.0의 querydsl-core 소스(com.querydsl.core.support.QueryMixin, com.querydsl.core.DefaultQueryMetadata)를 직접 확인한 것이다. 이 동작은 QueryDSL의 오래된 계약이라 버전이 달라도 같지만, 정확한 코드 형태는 버전에 따라 다를 수 있다.
개념 설명용 예시라는 단서 하나 query.where(null)처럼 null 리터럴 하나만 넘기면 자바 컴파일러가 where(Predicate)인지 where(Predicate...)인지 판단하지 못해 경고가 뜬다. 실무에서는 항상 where(nameEq(x))처럼 메서드 호출 결과를 넘기므로 이 모호성은 생기지 않는다.

2-3. null의 비대칭 — 관대한 곳이 세 군데, 터지는 곳이 한 군데

여기가 이 문서에서 가장 자주 사고를 내는 지점이다. null을 관대하게 처리하는 곳이 where() 말고도 두 군데 더 있고, 딱 한 자리만 예외를 던진다.

이 한 문장만 붙잡으면 NPE는 안 만난다

넘기는 null은 안전, 찍는 null은 NPE

비유로 굳히면 — 빈손을 건네받는 것은 괜찮다. 없는 사람에게 말을 거는 것이 터진다. where(null)은 내가 빈손을 건네는 것이고 받는 쪽이 알아서 무시한다. null.and(...)은 거기 없는 사람에게 말을 거는 것이라 라이브러리가 개입할 틈이 없다.

표현별 결과 — 세 번째 줄만 사고를 낸다
표현결과왜 그런가
where(a, null, c)a AND caddWhere가 null을 걸러낸다(2-2)
builder.and(null)통에 안 담김BooleanBuilder도 null에 관대하다
a.and(null)a오른쪽 null은 and() 안에서 검사된다
a.or(null)a오른쪽 null은 안전
null.and(b)NullPointerException왼쪽이 null이면 부를 메서드 자체가 없다

2-4. 실무 처방은 두 가지뿐 — null 검사를 사람이 아니라 도구가 하게 만든다

bad 사용자가 이름을 안 넣는 날에만 터진다
return nameEq(name).and(statusEq(status));   // name == null 이면 null.and(...) → NPE
처방 A Expressions.allOf
// 앞이든 뒤든 null을 건너뛴다.
// 전부 null이면 결과도 null → where에서 사라진다.
return Expressions.allOf(
        nameEq(name), statusEq(status));

// 값을 그대로 유지하므로 반환해서
// 다른 곳에 넘길 수 있다 (4절의 이점 유지)
처방 B BooleanBuilder로 받는다
// 빌더의 and()는 null을 그냥 무시한다.
BooleanBuilder builder = new BooleanBuilder();
builder.and(nameEq(name))       // null이면 no-op
       .and(statusEq(status));
return builder;

// 통이라 반복문 안에서 누적할 때 편하다 (5-2)

2-5. or(null)의 의미론 — 방향이 반대다

a.or(null)이 a가 되는 것은 AND일 때와 결과의 방향이 반대다. QueryDSL은 어느 쪽이든 "그 조건은 애초에 없었던 것"으로 취급하기 때문이다.

AND에서 조건 하나가 빠지면

제약이 줄어 결과가 넓어진다. 이름 조건이 사라지면 이름을 안 따지고 다 가져온다.

OR에서 가지 하나가 빠지면

선택지가 줄어 결과가 좁아진다. "이름 또는 이메일"에서 이름 가지가 사라지면 이메일만 본다.

방향 암기 — AND는 넓어지고, OR는 좁아진다

대부분의 동적 검색에서는 이게 원하는 동작이다(사용자가 이름을 안 넣었으면 이름으로 OR 검색할 이유도 없다). 다만 null을 "무조건 참"으로 착각하면 OR에서 결과가 반대로 나온다. 면접에서 이 구분까지 말하면 가산점이다.

3. before / after — if 여섯 개가 통째로 사라진다

조건 6개짜리 회원 검색이다 — 이름 · 이메일 · 상태(enum) · 등급 목록 · 가입일 시작 · 가입일 종료. 사용자는 이 중 아무거나 골라 넣는다.

before BooleanBuilder + if — 가장 흔한 형태

// 나열된 여섯 개 중 null인 것은 알아서 빠진다.
//  · 이름만 넣었으면  → where member.name like ?
//  · 아무것도 안 넣으면 → where 절 자체가 사라진다 (7절에서 이 경우를 막는다)
// 인자를 여러 개 나열하면 AND로 묶인다. OR가 필요하면 anyOf (4-6).
core 조건 하나 = 메서드 하나. 값이 없으면 null을 돌려준다
private BooleanExpression nameContains(String name) {
    return name == null ? null : member.name.contains(name);
}

private BooleanExpression emailEq(String email) {
    return email == null ? null : member.email.eq(email);
}

private BooleanExpression statusEq(MemberStatus status) {   // enum도 똑같다
    return status == null ? null : member.status.eq(status);
}

private BooleanExpression gradeIn(List<Grade> grades) {
    // 빈 리스트를 in()에 넣으면 "in ()" 같은 이상한 SQL이 되거나
    // 벤더에 따라 항상 false가 된다. 빈 것도 null로 눕힌다.함정
    return (grades == null || grades.isEmpty()) ? null : member.grade.in(grades);
}

private BooleanExpression joinedGoe(LocalDate from) {
    return from == null ? null : member.joinedAt.goe(from.atStartOfDay());
}

private BooleanExpression joinedLoe(LocalDate to) {
    return to == null ? null : member.joinedAt.loe(to.atTime(LocalTime.MAX));
}

이 코드에 숨은 실무 함정 두 개

빈 리스트를 in()에 넣지 않는다
null만 검사하고 isEmpty()를 빠뜨리면 in () 같은 이상한 SQL이 되거나 벤더에 따라 항상 false가 되어 결과가 0건이 된다. "비어 있는 것도 null로 눕힌다"가 규칙이다.
날짜 종료 조건의 경계
LocalDate를 LocalDateTime 컬럼에 비교할 때 to.atStartOfDay()로 loe를 걸면 종료일 당일이 통째로 빠진다. 위 코드처럼 atTime(LocalTime.MAX)를 쓰거나 lt(to.plusDays(1).atStartOfDay())로 반열린 구간을 쓴다.
무엇이 사라졌나
before — BooleanBuilder + ifafter — 조건 메서드 나열
분기if 6개없음 (각 메서드 안 삼항 연산자)
조건의 이름없음메서드 이름
재사용복사메서드 호출
단위 테스트어려움 (DB 필요)가능 (4-5)
사라지지 않은 것도 정확히 말해야 한다 null 체크 자체는 없어지지 않았다. if에서 삼항 연산자로 자리를 옮겼을 뿐이다. 그래서 "코드가 짧아진다"만 이유로 들면 약하다. before 코드의 진짜 문제는 길이가 아니라 아래 세 가지이고, 진짜 이유는 4절에 있다.
조건에 이름이 없다
"가입 기간 조건"이라는 개념이 코드 어디에도 이름으로 존재하지 않고 if 두 덩어리로만 흩어져 있다.
다른 쿼리에서 못 쓴다
관리자 검색과 통계 집계가 같은 "활성 회원" 조건을 쓴다면 그 if 블록을 복사해야 한다.
조건만 따로 테스트할 수 없다
builder 내부 상태를 검증하려면 결국 DB를 띄워 쿼리를 돌려야 한다.

4. 심장 — 조건이 "값"이 되면 세 가지가 열린다

이 절이 이 문서에서 가장 중요하다. if를 없애는 건 부수 효과고, 조건이 BooleanExpression이라는 값(value)이 되었다는 사실이 본질이다.

4-1. 통과 값 — 두 타입의 정체를 한 문장씩

BooleanBuilder = 조건을 담아 두는 통

내부에 Predicate 하나를 필드로 들고 있다가, and()를 부를 때마다 그 필드를 새로 합친 결과로 바꿔치기하는 가변(mutable) 객체다. 통을 흔들면 통 안의 내용물이 바뀐다.

비유 — 장바구니. 물건을 계속 던져 넣을 수 있지만 "값"으로 남에게 건네기는 어렵다. 건네준 뒤 내가 하나 더 넣으면 상대의 장바구니도 바뀐다.

BooleanExpression = 조건 하나를 표현하는 불변 값

a.and(b)는 a를 바꾸지 않는다. a와 b를 재료로 새로운 세 번째 값을 만들어 돌려준다. 숫자 3 + 4가 3을 바꾸지 않고 7이라는 새 값을 만드는 것과 같다.

비유 — 영수증에 적힌 금액. 몇 번을 복사해도 같고, 누구에게 보여줘도 안전하며, 다른 금액과 더해 새 금액을 만들 수 있다.

값이라서 열리는 세 가지 — 합 · 재 · 테

합성 — isActive().and(...)→ 재사용 — 목록·집계·다른 화면→ 테스트 — DB 없이 조건만

셋 다 "조건을 값으로 다룰 수 있는가"라는 한 뿌리에서 나온다. 아래 4-3 ~ 4-5가 각각 하나씩이고, 각 항목 끝에 "통이면 왜 안 되는지"를 붙여 둔다.

4-2. 뿌리 한 문장 — 가변 상태를 쌓는 빌더 vs 불변 값

빌더는 "지금까지 뭘 담았는지"라는 상태를 가지므로 함부로 공유하거나 재사용할 수 없고(한 요청에서 쓰던 통을 다른 곳에 넘기면 이후 and() 호출이 원본을 오염시킨다), 반환해도 받는 쪽에서 다시 조작해야 한다. 값은 그런 걱정이 없다 — isActive()는 몇 번을 불러도 같고, 어디에 넘겨도 안전하다.

4-3. 열리는 것 ① 합성 — 조건을 재료로 새 조건을 만든다

// "활성 회원"이라는 도메인 개념 하나가 조건으로 존재하게 된다
private BooleanExpression isActive() {
    return member.status.eq(MemberStatus.ACTIVE)
            .and(member.deletedAt.isNull());
}

// "최근 90일 내 로그인한 활성 회원" — 위에서 만든 값을 그대로 재료로 쓴다
private BooleanExpression isRecentlyActive() {
    return isActive()
            .and(member.lastLoginAt.goe(LocalDateTime.now().minusDays(90)));
}

// 검색 조건끼리 묶어 하나의 값으로 만들 수도 있다
private BooleanExpression nameAndStatus(String name, MemberStatus status) {
    return Expressions.allOf(nameEq(name), statusEq(status));   // null 안전 합성 (4-6)
}

isActive()는 이제 이름이 붙은 도메인 규칙이다. "탈퇴 회원은 deletedAt이 채워진다"는 지식이 코드의 한 군데에만 있고, 나머지는 isActive()를 부르면 된다.

통이면 왜 안 되나 BooleanBuilder를 반환해 봐야 그것은 "조건"이 아니라 "조건이 담긴 통"이라, 다른 통에 AND로 붙이는 순간 괄호 중첩이 지저분해지고 무엇보다 isActive()라는 이름을 가진 값이 코드에 존재하지 않는다.

4-4. 열리는 것 ② 재사용 — 다른 쿼리, 다른 리포지토리에서 그대로

// 목록 조회
queryFactory.selectFrom(member)
        .where(isActive(), gradeIn(cond.getGrades()))
        .fetch();

// 집계 — 같은 조건을 그대로 재사용
queryFactory.select(member.count())
        .from(member)
        .where(isActive())
        .fetchOne();

// 다른 화면 — 활성 회원 중 미인증만
queryFactory.selectFrom(member)
        .where(isActive(), member.emailVerified.isFalse())
        .fetch();
"활성 회원의 정의가 바뀌었다"는 요구가 왔을 때 고칠 자리가 한 곳이라는 것이 재사용의 실질적 가치다

if 블록을 복사해 쓴 코드베이스에서는 이 요구가 "grep해서 다 찾아 고치기"가 된다. 그리고 하나를 빠뜨린다. 조건이 여러 리포지토리에서 쓰인다면 정적 메서드 모음 클래스로 빼는 것이 실무 관행이다.

public final class MemberPredicates {
    private MemberPredicates() {}

    public static BooleanExpression isActive() { ... }
    public static BooleanExpression nameContains(String name) { ... }
}
통이면 왜 안 되나 빌더는 가변이라 여러 쿼리가 같은 인스턴스를 공유하면 서로를 오염시킨다. A 쿼리가 쓰던 통에 B 쿼리가 조건을 하나 더 넣으면 A의 조건도 바뀐다. 그래서 재사용하려면 쓸 때마다 새 통을 만들어야 하고, 그러려면 "통을 만들어 주는 메서드"를 또 두어야 한다 — 결국 값 하나면 될 일에 한 겹이 더 붙는다.

4-5. 열리는 것 ③ 단위 테스트 — 조건 자체를 DB 없이 검증한다

    assertThat(MemberPredicates.nameContains(null)).isNull();
}

@Test
void 빈_등급_목록은_조건이_되지_않는다() {   // in () 사고를 막는 회귀 테스트
    assertThat(MemberPredicates.gradeIn(List.of())).isNull();
}

@Test
void 이름_조건은_like로_변환된다() {
    assertThat(MemberPredicates.nameContains("김").toString())
            .contains("contains");   // 표현식의 문자열 형태를 검사
}

특히 두 번째 테스트가 실무적으로 값지다. "빈 리스트를 in()에 넣으면 안 된다"는 지식이 코드 리뷰어의 기억이 아니라 테스트에 박힌다. 3장 전체를 관통하는 "안전망을 코드로 고정한다"는 주제와 정확히 같은 이야기다(7-5).

확인 범위 표현식의 toString() 형태는 QueryDSL 버전에 따라 문자열이 달라질 수 있다. null 여부 검사(첫 두 테스트)는 안정적이지만, 문자열 매칭 테스트는 깨지기 쉬우니 실제 SQL 검증은 통합 테스트에서 하는 편이 낫다.
통이면 왜 안 되나 검사할 대상이 메서드의 반환값이 아니라 빌더 내부에 쌓인 상태라, "이 조건이 만들어졌는가"를 물어보려면 결국 쿼리를 실행해 결과 행을 봐야 한다. 즉 DB가 필요해지고, 조건 하나를 검증하는 데 통합 테스트 한 벌이 필요해진다.

4-6. 유일한 진짜 함정 — 앞쪽이 null이면 NPE

where()의 관대함에 익숙해지면 합성할 때도 관대할 거라고 착각하는데, 자바 메서드 호출은 그렇지 않다. 그리고 이 NPE는 "사용자가 이름을 안 넣었을 때만" 터진다 — 개발자는 항상 조건을 채워서 테스트하므로 운영에서 처음 만난다.

처방 1 Expressions.allOf / anyOf — 가장 깔끔하다
// 안전: 앞이든 뒤든 null을 건너뛴다. 전부 null이면 결과도 null(= where에서 사라짐).
private BooleanExpression nameAndStatus(String name, MemberStatus status) {
    return Expressions.allOf(nameEq(name), statusEq(status));
}

// OR가 필요할 때 — 통합 검색어를 이름 또는 이메일에서 찾기
private BooleanExpression keywordMatches(String keyword) {
    return Expressions.anyOf(nameContains(keyword), emailContains(keyword));
}
source 왜 안전한지 — allOf의 구현이 근거다
public static BooleanExpression allOf(BooleanExpression... exprs) {
    BooleanExpression rv = null;
    for (BooleanExpression b : exprs) {
        rv = rv == null ? b : rv.and(b);
    }
    return rv;
}
선행 null을 건너뛴다
rv가 아직 null이면 그냥 b를 대입하므로 null.and(...)가 일어나지 않는다.
후행 null도 무해하다
b가 null이면 rv.and(null)이 rv를 그대로 돌려준다(2-3).
null 안전성이 끝까지 전파된다
전부 null이면 null이 반환되고, 그건 where()에서 조용히 사라진다.
확인 범위 — 그리고 반환 타입을 BooleanExpression으로 쓰는 실용적 이유 위 구현은 Querydsl 5.1.0(com.querydsl.core.types.dsl.Expressions)에서 확인했다. 두 메서드는 BooleanExpression...을 받으므로, 조건 메서드의 반환 타입을 Predicate가 아니라 BooleanExpression으로 선언해야 그대로 넘길 수 있다. anyOf도 and 대신 or일 뿐 구조가 같다.
나머지 대응들 — 왜 allOf가 기본값인가
대응동작평가
① Expressions.allOf / anyOf앞뒤 null 모두 건너뜀, 결과도 값기본값. 4절의 세 이점을 유지한다
② BooleanBuilder에 담기빌더의 and()가 null 무시안전하지만 반환 타입이 통이 되어 합성·재사용·테스트를 포기한다. 반복 누적에는 이쪽이 정직(5-2)
③ Optional로 감싸기ofNullable(...).map(e -> e.and(...))동작하지만 조건이 셋만 넘어가도 읽기 힘들다
④ 첫 조건을 항상 참으로 고정Expressions.TRUE, 1=1로 시작필요 없는 조건이 SQL에 남을 수 있다. allOf가 있으니 쓸 이유가 없다

OR 그룹을 쓸 때 반드시 인식해야 할 부작용 하나

// A AND (B OR C) 를 만들려면
.where(
    isActive(),                                          // A
    Expressions.anyOf(nameContains(k), emailContains(k))   // (B OR C)k가 null이면?
)
그 괄호 그룹이 통째로 사라진다 k가 null이면 anyOf는 null을 반환하고, 결과는 where isActive() 하나뿐 — 즉 검색어가 없으면 전체 활성 회원이 나온다. 이게 의도라면 좋지만, 의도가 아니라면 2-2의 "조용한 무시"가 그대로 사고로 이어지는 경로다. OR 그룹이 사라졌을 때 결과가 어떻게 되는지를 반드시 한 번은 따져봐야 한다.

5. 선택 기준 — 대체재가 아니라 용도가 다르다

여기까지 읽으면 BooleanBuilder가 열등해 보이지만, 그렇지 않다. 둘은 잘하는 일이 다르다.

무엇을 보고 고르나 — 판별 축은 "조건 구조가 컴파일 시점에 정해져 있는가" 하나다
상황선택이유
조건 개수가 정해져 있고 전부 AND로 묶인다
— 실무 검색 화면의 대부분		조건 메서드 + where() 나열if가 사라지고 조건마다 이름이 생기며 합성·재사용·테스트가 열린다
조건 개수·연산자가 런타임에 결정된다
— 사용자 정의 필터 규칙을 DB에서 읽어 조립		BooleanBuilder반복문 안에서 누적해야 하고, and/or/andNot을 실행 중에 바꿔 끼울 수 있다
조건이 하나라도 담겼는지 물어봐야 한다BooleanBuilder.hasValue()값에는 이런 질문을 던질 API가 없다 → 7-3 가드에 그대로 쓰인다
필수 조건 + 선택 조건이 섞인다둘 다 (5-3)빌더를 뼈대로, 담기는 조건은 BooleanExpression 메서드로

5-1. 단순 AND 나열이면 메서드 분리

조건들이 전부 AND로만 묶이고 개수가 정해져 있으면 3절의 after가 명백히 낫다. 실무 검색 화면의 대부분이 여기 해당한다.

5-2. 조건 트리를 런타임에 조립해야 하면 BooleanBuilder

// 사용자가 정의한 필터 규칙을 DB에서 읽어와 조립하는 경우
// — 조건의 개수도, 연산자도 실행 시점에야 안다
public Predicate buildFrom(List<FilterRule> rules) {
    BooleanBuilder builder = new BooleanBuilder();
    for (FilterRule rule : rules) {          // 몇 개인지 컴파일 시점에 모른다
        BooleanExpression e = toExpression(rule);
        if (rule.getConjunction() == Conjunction.OR) {
            builder.or(e);
        } else {
            builder.and(e);
        }
    }
    return builder;
}
신호는 하나 — "반복문 안에서 조건을 누적한다"가 보이면 빌더의 자리다

이걸 where() 나열로 쓰려면 배열을 동적으로 만들어야 하는데, 그럴 바에는 BooleanBuilder가 정직하다.

5-3. 실무에서는 섞어 쓴다

가장 흔한 실전 형태는 둘 다다. BooleanBuilder를 뼈대로 쓰되, 담기는 조건은 BooleanExpression 메서드로 만든다 — 2-3에서 확인했듯 BooleanBuilder.and(null)도 무해하기 때문에 이 조합이 자연스럽게 성립한다.

// 필수 조건은 빌더에 먼저 넣고, 선택 조건은 메서드로 얹는다
BooleanBuilder builder = new BooleanBuilder(isActive());   // 필수 — 항상 non-null

builder.and(nameContains(cond.getName()))       // null이면 무시됨
       .and(statusEq(cond.getStatus()))
       .and(Expressions.anyOf(                  // OR 그룹은 anyOf로
               tagEq(cond.getTag()),
               categoryEq(cond.getCategory())));

면접 답변 형태 — 한쪽을 열등하다고 말하면 오히려 감점

"용도가 다르고 실무에서는 섞어 씁니다" → 그 뒤에 판별 축(컴파일 시점에 구조가 정해지는가)을 댄다

근거를 한 겹 더 대면 좋다 — 차이의 뿌리는 통과 값이다(4절). 빌더는 가변 통이라 결과가 갇히고, BooleanExpression은 불변 값이라 합성·재사용·단위 테스트가 열린다.

6. 페이징과 count — 세 층으로 답한다

6-1. 출발점 — Page 반환은 쿼리 2번이다

쿼리가 2번 나간다
Page<T>를 반환하면 데이터(content) 쿼리 + 총건수(count) 쿼리가 따로 나간다.
조건이 없으면 count가 전건을 센다
select count(*) from member — 500만 건이면 500만 건을 센다.
위험한 쪽은 content가 아니라 count다
페이징이 시그니처로 강제돼 있으면(7-1) content 쿼리는 한 페이지 분량만 나간다.

6-2. 1층 — 실행 자체를 생략한다 (PageableExecutionUtils.getPage)

before count를 항상 실행한다
long total = queryFactory
        .select(member.count())
        .from(member)
        .where(...)
        .fetchOne();          // 여기서 즉시 실행

return new PageImpl<>(content, pageable, total);
after 필요할 때만 실행한다
// countQuery는 아직 실행되지 않은 "쿼리 객체"
JPAQuery<Long> countQuery = queryFactory
        .select(member.count())
        .from(member)
        .where(nameContains(...), statusEq(...));
        // join 없음! (6-3)

return PageableExecutionUtils.getPage(
        content, pageable, countQuery::fetchOne);
countQuery::fetchOne이 메서드 참조라는 점이 핵심 — 넘기는 것은 결과가 아니라 "필요하면 실행할 함수"다
source 언제 생략되는가 — 실제 구현의 판정
// Spring Data Commons — org.springframework.data.support.PageableExecutionUtils
public static <T> Page<T> getPage(List<T> content, Pageable pageable, LongSupplier totalSupplier) {

    if (pageable.isUnpaged()) {                      // 페이징 자체가 없으면
        return new PageImpl<>(content, pageable, content.size());        // count 생략
    }

    if (isPartialPage(content, pageable)) {          // 가져온 건수 < 페이지 크기
        if (isFirstPage(pageable)) {                 //   첫 페이지라면
            return new PageImpl<>(content, pageable, content.size());    // count 생략
        } else if (!content.isEmpty()) {             //   마지막 페이지라면
            return new PageImpl<>(content, pageable,
                    pageable.getOffset() + content.size());              // count 생략
        }
    }

    return new PageImpl<>(content, pageable, totalSupplier.getAsLong()); // 여기서만 실행
}

6-3. 2층 — 실행되는 count를 싸게 만든다 (join을 걷어낸다)

이건 위 최적화보다 효과가 크다.

before content 쿼리를 복사해 select만 바꿨다
JPAQuery<Long> countQuery = queryFactory
        .select(member.count())
        .from(member)
        .leftJoin(member.team, team)     // 결과 표시용
        .leftJoin(member.grade, grade)   // 정렬용
        .where(nameContains(...));
after 세는 데 필요한 것만 남긴다
JPAQuery<Long> countQuery = queryFactory
        .select(member.count())
        .from(member)
        .where(nameContains(...));
        // where에 team 조건이 없다면 join도 불필요

판단 기준은 단순하다 — 그 join이 where 조건에 쓰이는가

표시용 leftJoin
팀 이름을 화면에 출력하려고 붙인 것 → count에서 제거
정렬용 join
count에는 정렬 자체가 없다 → 제거
where가 그 테이블을 참조
제거하면 안 된다. 건수가 달라진다

fetch join은 애초에 count 쿼리에 있으면 안 된다. 세는 데 연관 데이터를 가져올 이유가 없고, JPQL 규칙상 문제도 된다(관련 함정은 08-fetch-join-pagination-in-memory.md).

주의 — join(inner join)을 지울 때 가산점 inner join은 매칭되는 행이 없으면 결과에서 빠지므로 그 자체가 필터다. leftJoin은 건수에 영향이 없어 안전하게 제거되지만, join을 무심코 지우면 총건수가 실제보다 커진다. "화면 표시용이니까 지워도 되겠지"가 통하지 않는 경우다. 반대로 1:N leftJoin이 걸려 있으면 행이 뻥튀기되어 count가 부풀려지는 문제도 있는데, 이 역시 count에서 join을 걷어내면 자연히 해결된다.

6-4. 그래서 fetchResults() / fetchCount()를 쓰지 않는다

        .where(...)
        .offset(...).limit(...)

List<Member> content = results.getResults();
문제는 count 쿼리를 "원본 쿼리를 변형해서" 만든다는 데 있다 단순한 쿼리면 잘 되지만, group by가 여러 개이거나 having이 있으면 그 변형이 불가능하다. 그런 경우 QueryDSL의 JPA 구현은 count를 DB에 맡기지 않고 전체를 메모리로 가져와 size()를 세는 방식으로 폴백한다. 즉 총건수를 알려고 전건을 애플리케이션 메모리에 올린다. 500만 건이면 그대로 OOM이다. 경고 로그가 한 줄 남지만 — 08-fetch-join-pagination-in-memory.md의 HHH000104와 성격이 완전히 같다. 조용히 위험해지고, 신호는 로그 한 줄뿐이다.
확인 범위 Querydsl 5.1.0 기준으로 com.querydsl.jpa.impl.AbstractJPAQuery의 fetchResults()와 fetchCount()는 둘 다 @Deprecated이고, javadoc이 "multiple group by elements 또는 having이 있으면 count를 메모리에서 계산하며, 큰 결과 집합에서는 심각한 성능 저하가 있다"고 명시한다. 다만 같은 5.1.0에서 상위 인터페이스 com.querydsl.core.Fetchable에는 @Deprecated가 붙어 있지 않다 — 즉 "JPA 구현에서 deprecated"인 상태다. 표시 범위는 버전에 따라 달라졌으므로, 쓰지 않는 근거는 어노테이션이 아니라 위 폴백 동작 자체로 이해하는 것이 안전하다.

처방은 content 쿼리와 count 쿼리를 손으로 분리하는 것이다(6-2, 6-3). 분리하면 count 쿼리의 join·select를 내가 통제할 수 있다는 부수 이득도 따라온다. 그리고 직접 만든 count에서 fetchOne()은 결과가 없으면 null을 반환하므로 방어적으로 쓴다.

6-5. 3층 — 그 숫자가 정말 필요한가 시니어 변별

여기까지가 "count를 싸게 만드는 법"이라면, 시니어는 한 번 더 묻는다. "이 화면에 총 4,821,933건이라는 숫자가 정말 필요한가?" 대용량 검색에서 정확한 총건수는 가장 비싼 요구사항인데, 정작 사용자가 그 숫자를 쓰는 경우는 거의 없다.

무한 스크롤 / "더 보기" — 가장 근본적
총건수 자체가 필요 없다. Slice<T>를 쓰면 Spring Data가 count 쿼리를 아예 안 날린다.
"1,000건 이상" 표기
count에 상한을 두고 그 이상은 세지 않는다. 구글 검색 결과가 이 방식이다.
근사치
통계 테이블이나 별도 집계 배치의 값을 쓴다. 실시간 정확도를 포기하는 대신 비용이 0에 수렴한다.
정확한 화면은 따로 둔다
정산·감사는 느려도 정확해야 하고 일반 검색은 빨라야 한다 — 두 요구를 같은 엔드포인트에 묶지 않는다.
// 총건수가 필요 없으면 Slice — count 쿼리가 없다
List<Member> content = queryFactory.selectFrom(member)
        .where(...)
        .offset(pageable.getOffset())
        .limit(pageable.getPageSize() + 1)   // 한 건 더 가져와 "다음이 있는지"만 판정
        .fetch();

boolean hasNext = content.size() > pageable.getPageSize();
if (hasNext) {
    content.remove(pageable.getPageSize());
}
return new SliceImpl<>(content, pageable, hasNext);

count 3층 암기 — 생 · 싸 · 되

1층 생략한다 — PageableExecutionUtils→ 2층 싸게 만든다 — join 걷어내기→ 3층 되묻는다 — 그 숫자가 필요한가

1층은 공짜 최적화, 2층은 효과가 크고, 3층이 설계 판단의 자리다. 면접에서 count 최적화를 물었을 때 "그 숫자가 필요한지부터 되묻는" 답변이 가산점을 만든다.

7. 구조적 가드 — 개별 쿼리에서 조심하는 게 아니라, 구조가 실수를 불가능하게 만든다

"조건 없이 검색하면 500만 건이 메모리에 올라오지 않겠느냐"는 지적에 대해, "리포지토리 메서드가 항상 Pageable을 받는 구조라면 조건이 없어도 한 페이지 분량만 나가므로 그 문제는 발생하지 않는다"는 반박이 성립한다. 이건 정확한 지적이고, 더 중요하게는 문제를 개별 케이스가 아니라 구조로 막는 사고방식이다.

"조심하겠습니다"는 대책이 아니다. 대책은 실수할 수 없게 만드는 것이다.

7-3. 가드 3 — 조건 없는 전체 검색을 애초에 못 하게 한다

8. DTO 프로젝션과 함정 3종

8-1. 검색 화면은 "표시가 목적인 조회"다

변경할 것도 아닌 엔티티를 영속성 컨텍스트에 올리면 스냅샷을 뜨고 dirty checking 대상이 되며, 응답으로 그대로 내보내면 엔티티 직접 노출의 모든 문제를 떠안는다(12-entity-exposure-and-dto-boundary.md). QueryDSL은 이 지점을 잘 처리한다.

용어 — 프로젝션(projection) "행 전체가 아니라 필요한 컬럼만 뽑아 원하는 모양으로 담는 것"을 말한다. SQL의 SELECT 절이 하는 일 그대로이고, QueryDSL에서는 그 결과를 엔티티가 아니라 DTO로 받는 방법을 여러 가지로 제공한다. 그 자체로 성능 최적화이기도 하다 — 필요한 컬럼만 SELECT하고, 영속성 컨텍스트에 담기지 않아 스냅샷 비용이 없다.

8-2. 두 방식 — 오류를 언제 발견하느냐가 갈린다

A Projections.constructor — DTO에 자국을 안 남긴다
// DTO는 순수 자바 클래스 — QueryDSL을 전혀 모른다
public record MemberSearchDto(
        Long id, String name, String email, MemberStatus status) {}

List<MemberSearchDto> content = queryFactory
        .select(Projections.constructor(MemberSearchDto.class,
                member.id, member.name, member.email, member.status))
        .from(member)
        .where(nameContains(...), statusEq(...))
        .offset(pageable.getOffset())
        .limit(pageable.getPageSize())
        .fetch();

// 장점: DTO가 깨끗하다. API 응답 DTO를 그대로 쓸 수 있고,
//       다른 모듈로 옮겨도 QueryDSL 의존이 따라가지 않는다.
// 단점: 컴파일러가 검사해 주지 않는다. 인자 개수·타입이
//       생성자와 안 맞아도 컴파일은 통과하고 실행할 때 터진다.
B @QueryProjection — 컴파일 시점에 잡힌다
public record MemberSearchDto(
        Long id, String name, String email, MemberStatus status) {
    @QueryProjection                // DTO에 QueryDSL 어노테이션이 박힌다
    public MemberSearchDto {}
}

// 어노테이션 프로세서가 QMemberSearchDto를 생성해 준다 (1절과 같은 원리)
List<MemberSearchDto> content = queryFactory
        .select(new QMemberSearchDto(
                member.id, member.name, member.email, member.status))
        .from(member)
        ...

// 장점: 타입 안전. 인자를 빠뜨리거나 순서를 바꾸면 컴파일 에러다.
// 단점: DTO가 QueryDSL에 의존한다. import가 들어가고 Q 클래스가
//       하나씩 더 생긴다 — 응답 DTO에 쓰면 API 계층이 영속 기술에 묶인다.

8-3. 그래서 어떻게 고르나

조회 전용 내부 DTO
리포지토리 반환용
@QueryProjection. 어차피 영속 계층 안에 사는 클래스라 의존이 문제되지 않고, 컴파일 검사 이득이 크다.
API 응답 DTO
컨트롤러가 내보내는 것
위 내부 DTO를 서비스에서 변환하거나 Projections.constructor. 응답 클래스에 QueryDSL 자국을 남기지 않는다.
필드가 많고 자주 바뀌는 조회
검색 결과 그리드 등
@QueryProjection의 컴파일 검사 이득이 가장 크게 나타나는 구간이다.

8-4. 함정 ① — Q타입이 안 생긴다 (가장 흔한 첫 관문)

QMember를 import할 수 없다는 컴파일 에러로 시작한다. 1절에서 봤듯 Q타입은 어노테이션 프로세서가 빌드 중에 생성하는 코드라, 프로세서가 안 돌면 존재하지 않는다.

// Spring Boot 3 / Jakarta 기준 — classifier가 핵심이다
dependencies {
    implementation "com.querydsl:querydsl-jpa:5.1.0:jakarta"
    annotationProcessor "com.querydsl:querydsl-apt:5.1.0:jakarta"
    annotationProcessor "jakarta.annotation:jakarta.annotation-api"
    annotationProcessor "jakarta.persistence:jakarta.persistence-api"
}

깨지는 지점 세 가지

jakarta classifier 누락
Spring Boot 3는 jakarta.persistence를 쓰는데 classifier 없는 아티팩트는 javax.persistence 기준이라 @Entity를 못 알아본다. 에러가 안 나고 Q타입이 그냥 안 생기는 형태로 실패해서 원인을 찾기 어렵다.
implementation에 apt를 넣는 것
프로세서는 annotationProcessor 스코프여야 실행된다.
IDE와 Gradle의 생성 경로 불일치
IDE는 되는데 CI에서 깨지거나 반대가 된다. ./gradlew clean build로 확인하는 습관이 필요하고, Q타입 디렉토리는 생성물이므로 .gitignore에 넣는다.
확인 범위 위 좌표(querydsl-jpa:5.1.0:jakarta, querydsl-apt:5.1.0:jakarta)는 로컬 Gradle 캐시에 실제로 존재하는 아티팩트로 확인했다. 이 apt 아티팩트는 META-INF/services/javax.annotation.processing.Processor에 com.querydsl.apt.jpa.JPAAnnotationProcessor를 등록하고 있으므로 프로세서를 별도 옵션으로 지정할 필요가 없다. 다만 Gradle 버전과 프로젝트 구성에 따라 추가 설정이 필요한 경우가 있으니, 정확한 스니펫은 사용 중인 버전 조합에서 검증해야 한다.

8-5. 함정 ② — 문자열 Expressions로 도망가면 타입 안전성이 사라진다

// QueryDSL을 쓰는 이유가 사라지는 코드
.where(Expressions.stringTemplate("function('json_extract', {0}, '$.type')", member.meta)
        .eq("VIP"))

동작은 한다. 하지만 컬럼 이름을 바꿔도 컴파일러가 안 잡아주고, 오타는 런타임 에러이며, DB 방언이 바뀌면 깨진다. QueryDSL을 도입한 이유가 "문자열 조립을 없애는 것"이었는데 그 자리로 돌아간 셈이다 — 1절에서 말한 "컴파일 타임에 오타를 잡는다"는 이점을 스스로 반납하는 코드다.

허용 기준 — 존재 자체가 문제는 아니다 벤더 고유 함수처럼 정말 표현 수단이 없을 때만, 한 곳에 격리해서 쓴다. MemberExpressions.metaTypeEq(String type) 같은 메서드로 감싸면 문자열이 한 군데에만 존재하고 4-5처럼 테스트도 붙일 수 있다. 문자열이 리포지토리 곳곳에 흩어지는 것이 문제다.

8-6. 함정 ③ — 동적 정렬(OrderSpecifier)을 사용자 입력으로 받을 때

최악 사용자 문자열이 그대로 쿼리 조각이 된다
.orderBy(Expressions.stringTemplate(
        request.getSortExpr()).asc())   // SQL 주입 경로

// 나쁨: 주입까지는 아니어도, 엔티티의 모든 필드로 정렬 가능
PathBuilder<Member> path = new PathBuilder<>(Member.class, "member");
.orderBy(new OrderSpecifier(Order.ASC, path.get(request.getSortField())))
good 허용된 키만 미리 만든 OrderSpecifier로 매핑
private static final Map<String, OrderSpecifier<?>> SORTS = Map.of(
        "name",     member.name.asc(),
        "joinedAt", member.joinedAt.desc(),
        "grade",    member.grade.asc());

private OrderSpecifier<?> toOrder(String key) {
    OrderSpecifier<?> order = SORTS.get(key);
    return order != null ? order : member.id.desc();   // 기본 정렬로 폴백
}

PathBuilder 방식이 왜 문제인가. 정렬 결과로 값을 추론할 수 있다. sortField=password나 sortField=ssn으로 정렬한 목록을 여러 번 조회하면 값의 순서 정보가 새어 나가고, 없는 필드를 넣으면 런타임 예외로 내부 구조가 에러 메시지에 노출된다.

원칙은 하나 — 사용자 입력은 "정렬 기준을 고르는 키"일 뿐, 쿼리 조각이 아니다

정렬 실무 팁 — 정렬은 고유해야 한다 가산점

페이징에서 정렬이 고유하지 않으면 페이지 간 중복·누락이 생긴다. joinedAt으로만 정렬했는데 같은 시각 가입자가 여러 명이면, DB가 매 쿼리마다 순서를 다르게 줄 수 있어 2페이지에 1페이지 항목이 다시 나온다.

정렬 마지막에 항상 id를 붙여 전순서를 만든다 — .orderBy(member.joinedAt.desc(), member.id.desc())

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

관용구의 뿌리 한 문장?
where()에 넘긴 null은 예외도 0건도 아니고 "그 조건만 사라짐". 근거는 addWhere의 if (e == null) return;.
null의 비대칭?
넘기는 null은 안전, 찍는 null은 NPE. a.and(null)=a / null.and(a)=NPE.
값이라서 열리는 셋?
합·재·테 — 합성 · 재사용 · 테스트. if 제거는 부수 효과다.
NPE 처방과 그 근거?
Expressions.allOf/anyOf. 구현이 rv == null ? b : rv.and(b)라 앞도 뒤도 건너뛴다.
빌더가 오히려 나은 자리 둘?
① 반복문 안 누적(개수·연산자가 런타임 결정) ② hasValue()로 "조건이 하나라도 있나" 질문.
빈 리스트를 in()에?
안 된다. in ()가 되거나 항상 false. "비어 있는 것도 null로 눕힌다"가 규칙.
count 3층?
생·싸·되 — 생략(PageableExecutionUtils) · 싸게(join 제거) · 되묻기(그 숫자 필요한가).
count가 생략되는 두 경우?
① 첫 페이지인데 덜 왔다 → 전체가 그만큼 ② 중간 페이지인데 덜 왔다 → offset + size.
count에서 지워도 되는 join은?
표시용·정렬용 leftJoin만. inner join은 그 자체가 필터라 지우면 건수가 커지고, fetch join은 애초에 없어야 한다.
fetchResults()를 안 쓰는 이유?
group by가 여럿이거나 having이 있으면 전건을 메모리에 올려 size()로 센다. 신호는 로그 한 줄.
가드 3층?
조·크·시 — 조건 검증(또는 기본 기간 주입) · 크기 clamp · 시그니처 페이징 강제. 위쪽이 가장 많이 막는다.
anyOf OR 그룹이 null이면?
괄호 그룹이 통째로 사라진다 → 검색어 없으면 전체 활성 회원. "조용한 무시"가 사고가 되는 경로.
프로젝션 선택 기준?
내부 조회 DTO는 @QueryProjection(컴파일 검사), 응답 DTO는 Projections.constructor(의존 없음). fields/bean은 조용히 null.
동적 정렬 두 규칙?
① 허용 키 → 미리 만든 OrderSpecifier 화이트리스트 ② 마지막에 id를 붙여 전순서(중복·누락 방지).

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

where()에 null을 넘기면 무시되는데, 그럼 실수로 null이 들어가도 아무도 모르는 것 아닌가요? 함정힌트: 인정부터 하고, 막는 방법 셋을 층으로 댄다

맞다. 그게 이 방식의 유일한 구조적 약점이다. 예외도 로그도 없이 조건 하나가 사라지므로, "왜 검색 결과가 이상하게 많지?"라는 증상으로만 드러난다. 특히 Expressions.anyOf(...)로 만든 OR 그룹이 통째로 사라지면 결과가 크게 넓어진다(4-6).

세 가지로 막는다. 첫째, 조건 메서드에 단위 테스트를 붙인다(4-5) — "값이 있으면 null이 아니다"를 명시적으로 검사한다. 둘째, 절대 null을 반환하면 안 되는 조건은 그렇게 설계한다 — 기본 기간 주입(7-3)처럼 항상 값을 만드는 메서드는 null 분기 자체가 없다. 셋째, 최소 한 개의 조건이 있어야 실행되도록 전체를 검증한다(7-3).

핵심은 "조용한 무시"를 없애는 게 아니라 — 그건 라이브러리 계약이라 못 바꾼다 —
조용히 무시돼도 결과가 위험하지 않게 구조를 짜는 것이다
BooleanBuilder와 BooleanExpression 메서드 중 어느 쪽이 낫습니까? 필수힌트: "낫다"로 답하면 반은 잃는다. 축을 세우고, 근거를 한 겹 더 댄다

대체재가 아니라 용도가 다르다고 답한다. 조건이 컴파일 시점에 정해져 있고 AND로만 묶이면 메서드 분리가 명백히 낫다 — if가 사라지고 조건마다 이름이 생기며 재사용·테스트가 가능해진다. 반면 조건의 개수나 연산자가 런타임에 결정되는 경우(사용자 정의 필터 규칙을 DB에서 읽어 조립) 반복문 안에서 누적해야 하므로 BooleanBuilder가 정직하다.

근거를 한 겹 더 대면 좋다. 차이의 뿌리는 통과 값이다. 빌더는 조건을 쌓는 가변 통이라 결과가 통 안에 갇히고, BooleanExpression은 불변 값이라 합성·재사용·단위 테스트가 열린다(4절).

실무에서는 섞어 쓴다. BooleanBuilder도 and(null)을 무시하므로(2-3), 빌더를 뼈대로 두고 담기는 조건은 BooleanExpression 메서드로 만들면 양쪽 장점을 다 가진다. 그리고 빌더에만 있는 hasValue()는 "조건이 하나라도 있는가"를 물어볼 수 있어 7-3의 가드에 그대로 쓰인다. 한쪽을 열등하다고 말하면 오히려 감점이다.

조건들을 .and()로 이어 붙였더니 가끔 NullPointerException이 납니다. 왜죠? 함정힌트: 왼쪽인가 오른쪽인가

a.and(null)은 안전하지만 null.and(b)는 NPE이기 때문이다(2-3, 4-6). nameEq(name).and(statusEq(status))에서 사용자가 이름을 안 넣으면 nameEq가 null을 반환하고, 그 null에 .and()를 호출하는 순간 터진다.

null을 인자로 넘기는 것은 안전하고, null에 점을 찍는 것이 위험하다

고약한 점은 개발자는 항상 조건을 채워서 테스트하므로 운영에서 처음 만난다는 것이다.

처방은 Expressions.allOf(nameEq(name), statusEq(status)) — allOf는 rv == null ? b : rv.and(b) 형태라 선행 null을 건너뛰고 후행 null도 무해하며, 전부 null이면 null을 반환해 where()에서 자연히 사라진다. OR가 필요하면 anyOf가 같은 성질을 갖는다. 값으로 돌려줄 필요가 없다면 BooleanBuilder에 and()로 담는 것도 같은 효과다.

Page를 반환할 때 count 쿼리를 줄이는 방법은? 시니어 변별힌트: 세 층 — 생·싸·되

1층 — 실행 자체를 생략한다. PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne)는 count를 함수로 받아, 결과만 보고 총건수를 확신할 수 있으면 실행하지 않는다. 첫 페이지인데 페이지 크기보다 적게 왔으면 그게 전체이고, 중간 페이지인데 덜 왔으면 offset + 가져온 수가 전체다(6-2).

2층 — 실행되는 count를 싸게 만든다. content 쿼리를 복사해 select만 바꾸면 표시용·정렬용 join이 그대로 따라간다. where에 쓰이지 않는 leftJoin은 전부 제거한다. 단 inner join은 그 자체가 필터라 지우면 건수가 달라지고, fetch join은 count에 있어선 안 된다(6-3). 그리고 fetchResults()는 쓰지 않는다 — group by가 여럿이거나 having이 있으면 전건을 메모리에 올려 세는 방식으로 폴백한다(6-4).

3층 — 요구사항 자체를 되묻는다. 이 층이 시니어의 자리다. "총 4,821,933건"이라는 숫자가 사용자에게 필요한가? 무한 스크롤이면 Slice로 count를 아예 없앨 수 있고, "1,000건 이상" 표기나 배치 집계 근사치로 대체할 수도 있다. 정확한 총건수가 필요한 화면(정산·감사)과 빨라야 하는 화면(일반 검색)을 같은 엔드포인트에 묶지 않는 것이 근본 처방이다(6-5).

검색 조건을 하나도 안 넣고 조회하면 어떤 쿼리가 나갑니까? 위험하지 않나요? 시니어 변별힌트: 위험의 크기가 구조에 따라 다르다는 점을 먼저 정확히 말한다

where 절이 통째로 사라진 전체 조회가 나간다. 다만 위험의 크기는 구조에 따라 다르다는 점을 함께 말해야 정확하다.

리포지토리 메서드가 항상 Pageable을 받아 offset/limit을 적용하는 구조라면 content 쿼리는 한 페이지 분량만 가져오므로 OOM은 구조적으로 발생하지 않는다. 남는 위험은 둘이다 — Page 반환 시 count 쿼리가 전건을 세는 것과, 깊은 offset이 DB에서 앞부분을 건너뛰며 읽는 비용이다.

그래서 답은 세 겹이다. ① 페이징을 시그니처로 강제해 페이징 없는 경로를 아예 없앤다(편의용 오버로드를 하나라도 열어두면 누군가 반드시 그걸 쓴다). ② 페이지 크기를 코드에서 clamp한다 — Pageable은 클라이언트가 채우는 값이라 size=1000000이 들어올 수 있다. ③ 가장 위에서 조건 없는 검색을 막는다 — 필수 조건 하나를 강제하거나 기본 기간을 자동 주입한다. 특히 기본 기간 주입은 null을 절대 반환하지 않는 조건이 하나 생기는 것이라 "조건이 전부 비는 경우"가 구조적으로 사라지고, 인덱스 진입점까지 덤으로 얻는다(7절).

"조심하겠습니다"가 아니라 "그렇게 호출할 방법이 없습니다"로 답하는 것
그리고 그 가드들은 테스트와 ArchUnit 룰로 고정해야 완성된다
동적 정렬을 클라이언트가 지정하게 하려는데 주의할 점은? 가산점힌트: 보안 하나 + 페이징 정합성 하나

사용자 입력은 정렬 기준을 고르는 키일 뿐, 쿼리 조각이 아니다. Expressions.stringTemplate(사용자입력)은 문자열이 그대로 쿼리에 들어가는 주입 경로이고, PathBuilder.get(사용자입력)도 안전하지 않다 — 엔티티의 아무 필드로나 정렬할 수 있게 되어 정렬 순서로 값을 추론당하거나(password, ssn), 없는 필드는 런타임 예외로 내부 구조를 노출한다. 허용 키 → 미리 만들어 둔 OrderSpecifier 맵으로 화이트리스트하고, 매칭 실패 시 기본 정렬로 폴백한다.

그리고 정렬은 고유해야 한다. 동점이 생길 수 있는 컬럼으로만 정렬하면 페이지 간에 항목이 중복되거나 누락된다. 마지막에 항상 id를 붙여 전순서를 만든다(8-6). Spring Data의 Sort를 QueryDSL 경로로 변환할 때도 같은 검증이 필요하다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

조건 메서드의 반환 타입을 Predicate로 하면 안 되나요? 함정힌트: 그 값을 이후에 무엇에 넘기게 되는지 생각한다

where()에 넘기는 것만 생각하면 Predicate로도 된다. where(Predicate...)가 받는 타입이 그것이기 때문이다. 문제는 그 다음에 하고 싶어지는 일들이다.

① Expressions.allOf / anyOf는 BooleanExpression...을 받는다. 반환 타입이 Predicate면 그대로 넘길 수 없어 캐스팅하거나 다른 유틸을 찾게 된다. ② .and() / .or()로 합성해 다시 값으로 돌려주려면 반환 타입이 BooleanExpression이어야 체이닝이 자연스럽다. ③ .not(), .isTrue() 같은 불리언 전용 연산도 BooleanExpression에 있다.

즉 BooleanExpression을 쓰는 이유는 취향이 아니라 "조건을 값으로 다루기 위한 최소 요구사항"이다 — 4절의 세 이점(합·재·테)이 전부 이 타입 위에서 열린다.

where(a, b, c)로 나열하는 것과 a.and(b).and(c)로 이어 붙이는 것은 결국 같은 SQL 아닌가요?힌트: SQL은 같다. 그런데 "같지 않은 것"이 둘 있다

생성되는 SQL은 같다. where()에 인자를 여러 개 나열하면 AND로 묶이기 때문이다. 그런데 두 가지가 다르다.

① null 안전성이 다르다. 나열은 어느 자리가 null이든 안전하지만, 체이닝은 맨 앞이 null이면 NPE다(2-3). 동적 조건에서는 어느 것이 맨 앞이 될지 실행 전에 모른다는 점이 결정적이다.

② OR를 표현할 수 없다. 나열은 무조건 AND라, A AND (B OR C) 같은 괄호 그룹은 Expressions.anyOf(...)로 하나의 값을 만들어 그 자리에 넣어야 한다.

정리하면 — 단순 AND 나열은 where()에, 그룹을 만들어야 할 때만 합성한다. 그리고 합성은 반드시 allOf/anyOf를 거친다.

검색어를 안 넣었더니 anyOf로 만든 OR 검색이 통째로 사라져 전체가 나왔습니다. 어떻게 잡나요? 함정힌트: AND에서 조건이 빠질 때와 OR에서 가지가 빠질 때는 방향이 반대다

QueryDSL은 AND든 OR든 null을 "그 조건은 애초에 없었던 것"으로 취급한다. 그래서 anyOf(nameContains(k), emailContains(k))는 k가 null이면 null을 반환하고 괄호 그룹 전체가 사라진다.

AND에서 조건이 빠지면

제약이 줄어 결과가 넓어진다

OR에서 가지가 빠지면

선택지가 줄어 결과가 좁아진다

다만 그룹이 통째로 사라지는 것은 "OR가 좁아지는" 경우가 아니라 "AND 한 칸이 비는" 경우라, 결과는 넓어진다 — 이 문항의 증상이 정확히 그것이다.

처방은 두 갈래다. ① 검색어를 필수로 만든다(7-3의 조건 검증) — 통합 검색 화면이라면 검색어 없는 조회는 애초에 의미가 없다. ② 검색어가 없을 때의 기본 동작을 명시적으로 정한다 — 기본 기간을 주입하거나(7-3), 최신순 상위 N건만 보여주는 다른 쿼리 경로로 분기한다. "조용히 사라진 결과"를 그대로 두는 선택지만 없다.

조건 메서드를 MemberPredicates 같은 static 모음으로 뺄 때 주의할 점은? 가산점힌트: Q타입 인스턴스와 별칭(alias)

대부분은 그대로 옮기면 된다. QMember.member는 public static final 기본 인스턴스라 정적 메서드 안에서도 그대로 참조할 수 있고, BooleanExpression은 불변 값이라 여러 스레드가 같은 정적 메서드를 호출해도 안전하다(1절, 4-2).

주의할 것은 별칭(alias)이다. 정적 조건 메서드는 기본 인스턴스 member에 묶여 있으므로, 같은 테이블을 두 번 참조하는 자기 조인 쿼리에서 QMember m2 = new QMember("m2") 쪽 조건으로는 재사용할 수 없다. 그런 조건이 필요하면 QMember를 파라미터로 받는 형태(isActive(QMember m))로 만들어야 한다.

그리고 도메인 규칙을 담은 조건(isActive())과 검색 입력을 받는 조건(nameContains(String))은 성격이 다르므로 섞지 않는 편이 읽기 좋다. 앞의 것은 어디서든 참인 도메인 지식이고, 뒤의 것은 특정 화면의 입력 처리다.

기간 조건에서 종료일을 loe(to.atStartOfDay())로 걸었더니 그날 데이터가 안 나옵니다.힌트: LocalDate와 LocalDateTime의 경계

to.atStartOfDay()는 그 날의 00:00:00이라, loe로 걸면 종료일 당일에 들어온 데이터가 통째로 빠진다. 사용자는 "10월 5일까지"라고 입력했는데 10월 5일 데이터가 안 나오는 전형적인 오프바이원이다.

두 가지 처방이 있다. ① to.atTime(LocalTime.MAX)로 그 날의 끝을 만든다(3절의 joinedLoe). ② lt(to.plusDays(1).atStartOfDay())로 반열린 구간을 쓴다 — 시간 정밀도(초·밀리초·마이크로초)에 의존하지 않아 더 안전한 관행으로 자주 쓰인다.

그리고 이 지식은 테스트에 박아야 한다(4-5) — 조건 메서드가 값이므로 "종료일 당일 23:59 데이터가 포함되는가"를 DB 없이 표현식 단위로, 혹은 얇은 통합 테스트로 고정할 수 있다. 이런 경계 버그는 리뷰어의 기억이 아니라 테스트가 잡아야 하는 종류다.

QueryDSL을 쓰면 N+1이 자동으로 해결되나요? 함정힌트: QueryDSL이 바꾸는 것은 "쿼리를 쓰는 방법"이지 "로딩 전략"이 아니다

아니다. QueryDSL은 JPQL을 자바 코드로 쓰게 해주는 계층일 뿐, 연관을 언제 로딩할지는 전혀 바꾸지 않는다. selectFrom(member).fetch()로 100건을 가져온 뒤 member.getTeam().getName()을 돌면 정확히 같은 N+1이 난다.

해법도 JPQL과 동일하다. join(member.team, team).fetchJoin()으로 함께 읽거나, default_batch_fetch_size로 IN 절 묶음 로딩을 켜거나, 애초에 DTO 프로젝션으로 필요한 컬럼만 평평하게 가져온다(8절). 목록 조회에서는 세 번째가 가장 자주 정답이다 — 연관을 "로딩"할 필요 자체가 없어진다.

다만 페이징이 걸리면 컬렉션 fetch join은 쓰면 안 된다 — 이건 QueryDSL이든 JPQL이든 같은 함정이고 08-fetch-join-pagination-in-memory.md의 주제다. "도구를 바꿨다고 사라지는 문제가 아니다"가 이 질문의 핵심이다.

9-3. 면접에서 이렇게 잇는다 — 30초 흐름

"검색 필터 6개를 사용자가 임의로 조합하는 화면에서 썼습니다.

구성은 이렇습니다. 조건 하나당 BooleanExpression을 반환하는 메서드를 만들고, 값이 없으면 null을 돌려줍니다. 그리고 그 메서드들을 where()에 나열합니다. QueryDSL은 where()에 넘어온 null을 예외도 0건도 아니라 '그 조건은 없는 것'으로 처리하기 때문에 if가 한 줄도 필요 없습니다.

BooleanBuilder 대신 이 방식을 쓴 이유는 if를 없애려는 게 아니라 조건이 '값'이 되기 때문입니다. isActive()처럼 도메인 규칙에 이름을 붙여 목록 조회와 집계에서 같은 조건을 재사용하고, and()로 합성하고, DB 없이 단위 테스트합니다. 단 a.and(null)은 안전하지만 null.and(a)는 NPE라서, 합성할 때는 Expressions.allOf·anyOf로 감쌉니다.

BooleanBuilder가 열등한 건 아니고 용도가 다릅니다. 사용자 정의 필터처럼 조건 개수와 연산자가 런타임에 정해지면 반복문으로 누적해야 해서 빌더가 정직하고, hasValue()로 조건이 하나라도 있는지 물어볼 수 있다는 것도 빌더만의 장점입니다. 실제로는 빌더를 뼈대로 두고 담기는 조건은 BooleanExpression 메서드로 섞어 씁니다.

페이징에서 신경 쓴 건 count입니다. PageableExecutionUtils로 첫 페이지나 마지막 페이지면 count를 아예 생략하고, count 쿼리에서는 표시용·정렬용 leftJoin을 걷어냅니다. fetchResults()는 group by·having에서 전건을 메모리로 올려 세는 폴백이 있어 쓰지 않습니다. 다만 더 중요한 건 조건 없는 전체 검색을 못 하게 만드는 구조였습니다 — 리포지토리 시그니처가 Pageable을 강제하고, 페이지 크기를 상한으로 자르고, 기본 조회 기간을 주입해서 조건이 전부 비는 경우가 아예 없게 했습니다."

한 줄 요약
QueryDSL 동적 쿼리는 where()에 넘긴 null이 예외도 0건도 아닌 "그 조건만 사라짐"으로 처리된다는 성질 하나 위에 서 있다 — 그래서 조건마다 BooleanExpression을 반환하는 메서드를 만들어 where()에 나열하면 if가 전부 없어지고, 더 중요하게는 조건이 값이 되어 and()로 합성되고 다른 쿼리에서 재사용되며 DB 없이 단위 테스트된다(단 null.and(...)은 NPE이므로 Expressions.allOf로 감싼다). BooleanBuilder는 열등한 대안이 아니라 조건 트리를 런타임에 조립할 때 쓰는 다른 도구고, 페이징에서는 count를 PageableExecutionUtils로 생략하고 join을 걷어내되 그전에 "그 총건수가 정말 필요한가"를 되물어야 하며, 궁극적으로는 개별 쿼리에서 조심하는 대신 페이징 강제 시그니처 · 페이지 크기 clamp · 필수 조건 검증으로 조건 없는 전체 검색을 호출할 방법 자체를 없애는 것이 답이다.
