flush 시점과 쓰기 지연 SQL 실행 순서
코드 순서는 실행 순서가 아니다

면접 질문: "영속성 컨텍스트의 flush는 언제 일어나나요? 쓰기 지연 SQL의 실행 순서가 코드 순서와 달라서 생기는 문제(유니크 제약, 데드락)는?"

핵심 관전 포인트 — flush가 일어나는 시점은 세 가지다 — ① 트랜잭션 커밋 직전(자동) ② JPQL·Criteria·네이티브 쿼리를 실행하기 직전(auto-flush, 아직 DB에 안 보낸 변경분 때문에 쿼리 결과가 틀리는 것을 막으려고) ③ em.flush() 명시 호출. 여기서 사람들이 놓치는 비대칭이 하나 있다 — findById는 flush를 유발하지 않는다. auto-flush는 "이 쿼리가 건드리는 테이블 집합(query space)에 미반영 변경이 있는가"를 판정해서 결정하는데, em.find()는 PK 조회라 그 판정 경로 자체를 타지 않는다. 1차 캐시에 있든 없든 마찬가지다. 그리고 flush가 실제로 SQL을 내보낼 때, 순서는 내가 코드에 쓴 순서가 아니라 Hibernate가 ActionQueue에 고정해 둔 타입별 순서다 — DELETE가 항상 맨 마지막이고, 이유는 ① FK 제약 위반을 줄이려는 의도 ② 같은 종류의 SQL을 몰아야 JDBC 배치가 먹히기 때문이다. 그래서 "지우고 넣기"가 실제로는 "넣고 지우기"가 되어 유니크 제약을 위반한다. 최선의 처방은 flush()를 끼워 넣는 것이 아니라 애초에 DELETE+INSERT를 UPDATE로 바꾸는 것이다. 같은 원리의 더 나쁜 얼굴이 데드락인데, 이건 Hibernate가 순서를 지켜주지 않으므로 반드시 PK 정렬로 코드에 고정해야 한다. 마지막으로 이 유형은 배포 전에 기계로 잡을 수 있다 — p6spy로 실제 SQL 순서 관측 + @DataJpaTest의 롤백이 커밋 시점 문제를 숨기므로 @Commit/TestTransaction으로 실제 커밋 + H2 대신 Testcontainers로 실제 DB.
  • 1
    시점은 셋이고, 하나에는 예외가 있다 — 커밋 직전 · JPQL 실행 직전(auto-flush) · em.flush(). auto-flush는 쿼리가 읽는 테이블 집합(query space)에 미반영 변경이 겹치는가로 판정하는데, findById는 쿼리가 아니라 PK 조회라 그 판정 경로 자체를 타지 않는다 — 1차 캐시 히트 여부와 무관하다.
  • 2
    순서는 내 코드가 아니라 ActionQueue가 정한다 — INSERT는 3번 칸, DELETE는 9번 칸으로 항상 맨 마지막이고, 이유는 FK 위반 회피 + JDBC 배치 효율이라는 의도적 설계다. 그래서 "지우고 넣기"가 "넣고 지우기"로 뒤집혀 유니크 위반이 나고, 커밋도 안 했는데 예외가 나는 이유는 DB가 flush 시점에 이미 제약을 검사하고 락을 잡기 때문이다.
  • 3

0. 질문 + 출제 의도

질문: "영속성 컨텍스트의 flush는 언제 일어나나요? 쓰기 지연 SQL의 실행 순서가 코드 순서와 달라서 생기는 문제(유니크 제약, 데드락)는?"

관련 질문: "save(new Member("kim")) 직후 같은 트랜잭션에서 findByName("kim")을 호출하면 결과 크기가 0인가 1인가?" · "그럼 findById(1L)은? 이때도 flush가 일어나나?" · "email에 유니크 제약이 있는 테이블에서 delete(기존 행) 후 save(같은 email 새 행) — 코드는 지우고 넣는데 유니크 위반이 난다. 왜인가? 어떻게 고치겠나? 그리고 이 유형은 테스트에서 잘 안 잡히고 운영에서 터지는데, 배포 전에 발견할 방법이 있나?"

출제 의도: "flush가 커밋·JPQL 실행 직전에 일어나고 쓰기 지연 SQL이 코드 순서와 다르게 나갈 수 있음을 모르면, '코드상 삭제 후 삽입인데 유니크 제약 위반' 같은 미스터리를 못 푼다." 즉 이 질문은 영속성 컨텍스트를 개념으로 외웠는지, 아니면 SQL이 실제로 언제 어떤 순서로 나가는지까지 그림이 있는지를 가르는 리트머스다.

채점은 네 층으로 이루어진다 ① flush 시점을 세 개 다 말하는가 (하나만 말하면 개념만 외운 것)
② findById/findByName의 비대칭을 설명하는가 (= auto-flush의 판정 기준을 아는가)
③ 순서가 뒤집히는 원인을 "Hibernate가 정해둔 규칙"으로 말하는가, 아니면 "왜인지 모르겠지만 그렇더라"에 머무는가
④ 배포 전에 잡는 장치를 설계할 수 있는가
이 페이지가 겨냥하는 함정 세 개 ① "flush는 커밋할 때 일어난다"에서 멈추는 것 — 틀리진 않았지만 트랜잭션 중간의 auto-flush를 설명할 수 없어 "저장했는데 조회에 왜 나오지?"도 "커밋도 안 했는데 왜 유니크 위반이지?"도 못 푼다 → 2·5절.
② "조회하면 flush된다"로 일반화하는 것 — 조회에는 두 종류가 있고 정반대로 동작한다 → 3절.
③ flush()를 끼워 넣는 것을 정답이라고 믿는 것 — 동작은 하지만 증상 대응이다. 애초에 DELETE+INSERT를 하지 않는 설계가 훨씬 낫다 → 7절.
읽는 순서 — 이 페이지는 축이 셋이다 2·3절 = "언제 나가는가"(세 시점과 findById의 비대칭) · 4·5·6절 = "어떤 순서로 나가는가"(ActionQueue의 고정 순서, 유니크 위반, 데드락) · 7·8절 = "그래서 무엇을 하는가"(코드 수정과 기계 장치). 버전에 의존하는 서술은 Hibernate ORM 6.6 / Spring Boot 3.x 기준이며, 내부 동작에는 실제 클래스 이름을 함께 적어 두었다.

1. 못 하나 — flush는 commit이 아니다

모든 오해가 여기서 갈린다. flush는 영속성 컨텍스트에 쌓인 변경분을 SQL로 만들어 DB로 보내는 행위이고, commit은 DB에게 "지금까지 보낸 걸 확정하라"고 말하는 행위다. 둘은 완전히 다른 사건이고, 시점도 다르다.

"flush가 언제 일어나는가"는 학술적 질문이 아니라 "내 트랜잭션이 언제 DB를 건드리는가"라는 운영 질문이다

2. 시점 셋 — 커 · 쿼 · 명

3초 암기 — 커 · 쿼 · 명

커 = 커밋 직전(자동)· 쿼 = 쿼리(JPQL) 실행 직전(auto-flush)· 명 = 명시 호출 em.flush()

"flush는 커밋할 때"라고만 답하면 세 개 중 하나만 말한 것이고, 이 문항의 두 사고(유니크 위반·데드락) 어느 쪽도 설명하지 못한다.

2-1. 시점 ① 커 — 트랜잭션 커밋 직전 (자동)

@Transactional 메서드가 정상 종료되면 Spring이 커밋을 부르고, 커밋 직전에 Hibernate가 flush를 수행한다.

기본 메서드 안에서는 SQL이 한 줄도 안 나간다
@Transactional
public void changeName(Long id, String name) {
    Member m = memberRepository.findById(id).orElseThrow();
    m.setName(name);       // ← 여기서는 SQL이 나가지 않는다
}                          // ← 메서드가 끝나며 커밋 → 그 직전에 flush → 여기서 UPDATE 발생

그래서 디버거로 메서드 중간에 멈춰 DB를 직접 조회해도 옛날 값이 보인다. "코드는 분명 바꿨는데 DB에 없다"는 당황은 대부분 이 시점 문제다.

2-2. 시점 ② 쿼 — JPQL·Criteria·네이티브 쿼리 실행 직전 (auto-flush)

JPQL 같은 쿼리는 DB에 직접 나가서 DB의 데이터를 읽는다. 그런데 내가 방금 저장한 데이터가 아직 메모리에만 있고 DB에는 없다면, 쿼리 결과가 틀린다.

기본 auto-flush가 없다면 결과가 0건이 되어버린다
@Transactional
public void demo() {
    memberRepository.save(new Member("kim"));           // 메모리에만 INSERT 예약
    List<Member> found = memberRepository.findByName("kim");
    //                   ↑ JPQL → 실행 직전에 auto-flush → INSERT가 DB로 나감 → 결과 1건
}
auto-flush의 존재 이유는 한 가지뿐이다 "내 트랜잭션 안에서의 읽기 일관성" — 내가 방금 한 변경은 내가 조회할 때 보여야 한다(read-your-own-writes). 이 판정이 정확히 어떤 기준으로 이루어지는지가 3절의 주제이고, 그 기준을 알아야 findById가 왜 예외인지가 풀린다.

2-3. 시점 ③ 명 — em.flush() 명시 호출

개발자가 직접 부른다. Spring Data JPA의 repository.flush(), saveAndFlush()도 같은 일을 한다. 필요한 경우는 셋뿐이다.

① 실행 순서를 강제할 때
DELETE를 INSERT보다 먼저 내보내야 할 때. flush 경계를 하나 더 만드는 유일한 수단이다 → 7-2절
② DB가 만든 값을 도중에 읽어야 할 때
시퀀스·트리거·DB 기본값처럼 DB에 다녀와야 알 수 있는 값을 트랜잭션 중간에 써야 하는 경우
③ 대량 처리에서 clear()와 짝지을 때
영속성 컨텍스트가 비대해지는 것을 막기 위해 flush() + clear()를 주기적으로 부른다
대가는 분명하다 — 락 보유 시간 flush로 UPDATE/DELETE를 보내는 순간부터 커밋까지 그 행의 쓰기 락을 쥐고 있게 된다. 트랜잭션 앞쪽에서 flush하고 뒤에서 외부 API를 호출하는 코드는 락 보유 시간을 수백 ms 단위로 늘려 경합을 만든다. 그래서 원칙은 "필요할 때만 최소로, 가능하면 커밋 직전으로 미룬다".

2-4. FlushModeType.COMMIT — ②를 끌 수는 있지만 쓰지 않는다

모드동작실무
AUTO (기본)커밋 직전 + 쿼리 실행 직전사실상 항상 이것
COMMIT커밋 직전에만거의 쓰지 않는다
before 위험한 최적화
@Transactional
public void danger() {
    em.setFlushMode(FlushModeType.COMMIT);
    memberRepository.save(new Member("kim"));

    long n = memberRepository.countByName("kim");
    // JPQL인데 flush가 안 일어난다 → n == 0

    if (n == 0) throw new IllegalStateException("저장 실패?");
    // ← 여기서 터진다. 저장은 잘 됐는데.
}
after 기본값(AUTO)을 그대로 둔다
@Transactional
public void safe() {
    memberRepository.save(new Member("kim"));

    long n = memberRepository.countByName("kim");
    // auto-flush → 정확히 1
}

// 성능이 정말 문제라면 flush 모드가 아니라
// "쓰기와 읽기를 같은 트랜잭션에 섞지 않는 설계"로 푼다.
면접에서의 정답은 "끌 수 있지만 그 순간 읽기 일관성을 잃으므로 안 쓴다"까지다
존재를 모르는 것과, 알면서 안 쓰는 것은 다르다

3. 비대칭 — findByName은 flush를 부르고 findById는 안 부른다

여기서부터가 이 문항에서 가장 많이 틀리는 지점이다. "1차 캐시에 있으면 flush를 안 하고, 없으면 DB에 가야 하니까 flush하겠지"라는 추론은 자연스럽지만 틀렸다. 왜 틀렸는지 이해하려면 Hibernate가 무엇을 보고 판정하는지부터 알아야 한다.

3-1. 용어부터 — query space는 그냥 "테이블 이름 목록"이다

query space란 "이 쿼리가 손대는 테이블들의 이름 집합"이다. 직역하면 "쿼리 공간"인데, 하나의 쿼리가 읽거나 쓰는 테이블들을 그 쿼리가 차지하는 영역으로 보고 붙인 이름이다. 어려운 개념이 아니라 그냥 테이블 이름 목록이라고 생각하면 된다.

select m from Member m where m.name = ?      →  query space = { member }
select o from Order o join o.member m        →  query space = { orders, member }

3-2. 왜 하필 "테이블 집합"으로 판정하는가

질문을 뒤집으면 답이 나온다. Hibernate가 flush를 해야 하는 유일한 이유는 "아직 DB에 못 보낸 내 변경분 때문에 이 쿼리의 결과가 틀리는 것"을 막기 위해서다. 그런데 내 변경분이 이 쿼리 결과를 틀리게 만들 수 있으려면, 그 변경분이 이 쿼리가 실제로 읽는 바로 그 테이블에 있어야 한다.

member 테이블에 INSERT가 대기 중인데 orders만 읽는 쿼리를 날린다면, 그 대기 중인 INSERT는 이 쿼리 결과에 영향을 줄 수 없다. 그러니 flush할 이유도 없다. 즉 테이블 집합이 겹치는가는 "미반영 변경이 이 쿼리 결과를 틀리게 만들 수 있는가"를 값싸게 근사하는 방법이다.

가산점 포인트 — 네이티브 쿼리는 이 판정을 못 한다 SQL 문자열을 Hibernate가 파싱해 테이블을 알아내지는 않기 때문에, 네이티브 쿼리는 "어느 테이블을 건드리는지 모른다"고 보고 보수적으로 전체를 flush한다. 실제로 NativeQueryImpl.prepareForExecution()은 동기화 대상 query space가 지정돼 있으면 부분 flush로 끝내고, 지정돼 있지 않으면 session.flush()를 그냥 호출한다. 좁히려면 NativeQuery.addSynchronizedEntityClass(...)(또는 addSynchronizedQuerySpace)로 관련 엔티티를 알려줘야 한다. "네이티브 쿼리 하나 때문에 트랜잭션 중간에 예상 못 한 UPDATE 폭탄이 나갔다"는 사고의 정체가 이것이다.

3-3. em.find()는 그 판정 경로 자체를 타지 않는다

이제 비대칭의 이유를 말할 수 있다. findById(내부적으로 EntityManager.find())는 쿼리가 아니다. 이것은 "PK가 이것인 엔티티 하나를 달라"는 조회(lookup)이고, 애초에 3-2절의 판정 절차에 진입하지 않는다.

findById(1L)
  → 1차 캐시에 (Member, 1) 있나?
       있다  → 그대로 반환 (SQL 없음)
       없다  → select ... from member where id = ? 를 즉시 실행해서 채운다
                ↑ 이 경로 어디에도 "query space 비교 → auto-flush" 단계가 없다

왜 없어도 되는가를 이해하면 외울 필요가 없다. auto-flush의 목적은 "내 변경분이 빠진 결과가 나오는 것"을 막는 것인데, PK 조회에서는 그런 일이 애초에 벌어지지 않는다. 경우를 둘로 나눠 보면 분명하다.

아직 INSERT 안 된 새 엔티티

어차피 영속성 컨텍스트에 있으므로 find()는 1차 캐시에서 찾아 반환한다. DB에 갈 필요가 없다.

수정만 하고 아직 UPDATE 안 된 엔티티

이것도 1차 캐시에 있고, JPA는 "같은 트랜잭션·같은 PK면 항상 같은 인스턴스"(동일성 보장)를 지키므로 DB에서 옛날 값을 읽어와도 캐시에 있는 인스턴스를 그대로 돌려준다. 즉 내가 바꾼 값이 그대로 보인다.

PK 조회는 flush 없이도 읽기 일관성이 이미 보장되므로, Hibernate가 flush할 이유가 없다

"1차 캐시에 없으면 그때는 flush하겠지" — 이것이 틀리는 지점

캐시에 없어서 select ... where id = ?가 실제로 나가더라도, 그 SELECT는 여전히 PK 하나를 집어오는 lookup이지 조건을 평가하는 쿼리가 아니다.

아직 DB에 안 간 내 변경분이 "id로 찾는 행 하나"의 존재 여부를 바꿀 수 있는 경우란, 그 행을 내가 이 트랜잭션에서 방금 만든 경우뿐인데 그건 이미 1차 캐시에 있다. 그래서 판정 경로가 필요 없다. 반면 JPQL은 조건(where name = 'kim')을 DB가 평가하므로, 미반영 변경이 DB에 없으면 애초에 결과 집합에서 빠져버린다 — 그래서 flush가 필수다.

3-4. 나란히 놓고 SQL을 비교한다

같은 상황(엔티티 하나를 수정해 둔 상태)에서 다음 줄만 바꿔 두 코드를 나란히 놓는다.

before 흔한 오해: "조회하면 flush된다"
@Transactional
public void misunderstanding() {
    Member m = memberRepository.findById(1L).orElseThrow();
    m.setName("changed");            // UPDATE 예약 (아직 SQL 없음)

    memberRepository.findById(1L);   // flush 안 남. SQL도 안 남(캐시 히트)
    memberRepository.findById(999L); // flush 안 남. select 999 만 나감
    //   ↑ "캐시에 없으면 flush하겠지"가 틀리는 지점

    // 이 시점까지 DB에는 UPDATE가 단 한 건도 도착하지 않았다.
}
after 실제로 flush를 유발하는 것은 JPQL 쪽
@Transactional
public void reality() {
    Member m = memberRepository.findById(1L).orElseThrow();
    m.setName("changed");            // UPDATE 예약

    memberRepository.findByName("changed");
    // JPQL → query space {member} 겹침 → auto-flush
    // 이 줄에서 UPDATE가 DB로 나가고,
    // 그 순간부터 커밋까지 1번 행의 쓰기 락을 쥔다.
}
면접에서 이 비대칭을 한 문장으로 "findById는 쿼리가 아니라 PK 조회라 auto-flush 판정 경로를 타지 않습니다. 1차 캐시 히트 여부와 무관하고, PK 조회는 동일성 보장 덕분에 flush 없이도 내 변경분이 보이기 때문에 flush할 이유가 없습니다."
실무에서 이 비대칭이 물리는 순간 함정 저장 로직 테스트에서 결과를 findById로 검증하면, flush가 한 번도 일어나지 않은 채로 1차 캐시에 있는 그 객체를 그대로 돌려받으므로 무조건 통과한다. DB에 정말 들어갔는지는 전혀 검증되지 않는다. 이것이 8절에서 다룰 "테스트가 통과하는데 운영에서 터지는" 첫 번째 이유다.

4. 순서 — ActionQueue에 박힌 9칸

flush가 일어나면 Hibernate는 쌓인 작업들을 내가 호출한 순서가 아니라, 작업 종류별로 미리 정해진 순서로 실행한다. 이 대기열이 ActionQueue이고, 순서는 소스의 ActionQueue.OrderedActions 열거형에 박혀 있다. 그 열거형 바로 위에 달린 주석이 "The order of these operations is very important"인데, 말 그대로 열거 순서 자체가 실행 순서다.

정확한 이름까지 — 의심스러우면 ActionQueue.OrderedActions 소스에서 직접 확인할 수 있다
순서액션 (Hibernate 내부 이름)무슨 SQL인가언제 등장하나
1OrphanCollectionRemoveAction고아가 된 컬렉션 통째 삭제컬렉션 매핑 시

3EntityInsertAction엔티티 INSERT거의 항상
4EntityUpdateAction엔티티 UPDATE거의 항상
5QueuedOperationCollectionAction컬렉션에 미뤄 둔 개별 연산컬렉션 매핑 시
6CollectionRemoveAction컬렉션 삭제컬렉션 매핑 시
7CollectionUpdateAction컬렉션 갱신컬렉션 매핑 시
8CollectionRecreateAction컬렉션 재생성컬렉션 매핑 시

면접에서 아홉 개를 다 못 외워도 된다. "INSERT가 항상 DELETE보다 먼저" 하나면 이 문항은 풀린다

4-1. 왜 하필 DELETE가 뒤인가 — 이유 두 가지

이유 ① FK(외래 키) 제약 위반을 줄이려는 의도

부모-자식 관계에서 자식이 부모를 참조할 때 부모를 먼저 지우면 FK 위반이 난다. INSERT를 앞에, DELETE를 뒤에 두면 "필요한 행은 먼저 만들어 두고, 참조가 끊긴 행을 나중에 지우는" 순서가 되어 일반적인 경우에 안전하다.

이유 ② 같은 종류의 SQL을 몰아야 JDBC 배치가 먹힌다

JDBC 배치는 같은 형태의 SQL을 하나로 묶어 한 번에 보내는 최적화다. 종류가 섞여 있으면 묶을 수가 없다. 세탁기를 색깔별로 모아 돌리는 것과 같다 — 손님이 맡긴 순서가 아니라 같은 색끼리 모아야 한 번에 돌아간다.

섞여 있으면 (코드 순서대로 실행한다면):
  insert / delete / insert / delete / insert  →  묶을 수 없다. 네트워크 왕복 5회

종류별로 몰아두면:
  insert · insert · insert  →  한 묶음
  delete · delete           →  한 묶음        →  네트워크 왕복 2회
순서 고정은 버그가 아니라 성능을 위한 의도적 설계다
이걸 알면 "왜 안 고쳐주냐"가 아니라 "이 규칙 위에서 어떻게 코드를 쓸 것인가"로 사고가 바뀐다
가산점 포인트 — IDENTITY 전략에서는 INSERT가 지연되지 않는다 PK를 DB의 auto_increment에 맡기면(GenerationType.IDENTITY), Hibernate는 엔티티를 영속 상태로 만들려면 id가 필요한데 그 id를 DB만 알기 때문에 persist() 시점에 INSERT를 즉시 실행한다. 소스에서는 이 INSERT를 "early insert"라고 부르고, ActionQueue.addInsertAction()이 insert.isEarlyInsert()인 경우 큐에 쌓지 않고 그 자리에서 executeInserts()를 부른다. 그래서 IDENTITY 환경에서는 5절의 문제가 더 확실하게 터진다 — DELETE는 flush까지 대기하는데 INSERT는 이미 나가버렸기 때문이다. 덤으로 IDENTITY는 INSERT 배치도 사실상 불가능하다.

5. 사고 ① — "지우고 넣었는데 유니크 위반"

member 테이블의 email에 유니크 제약이 있다고 하자.

create table member (
    id    bigint auto_increment primary key,
    email varchar(255) not null,
    name  varchar(255),
    constraint uk_member_email unique (email)
);
before 코드는 "지우고 넣기"인데, SQL은 "넣고 나서 지우기"로 나간다
@Transactional
public void replaceMember(String email, String newName) {
    Member old = memberRepository.findByEmail(email).orElseThrow();
    memberRepository.delete(old);                       // ① DELETE 예약 (아직 SQL 없음)
    memberRepository.save(new Member(email, newName));  // ② INSERT 예약 (아직 SQL 없음)
}   // ← 커밋 직전 flush. ActionQueue 규칙에 따라 INSERT가 먼저, DELETE가 나중.
원인을 한 문장으로 — DELETE는 항상 맨 마지막에 실행되므로,
"DELETE로 자리를 비운 뒤 INSERT를 넣는다"는 전제가 애초에 성립하지 않는다
로컬 테스트에서 통과하는 이유도 여기서 설명된다 테스트가 롤백되면 커밋 직전 flush가 아예 실행되지 않아 이 예외를 만날 기회 자체가 없다. 이 함정 하나가 "테스트는 초록불인데 운영에서 터진다"의 절반을 설명한다 → 8-2절

6. 사고 ② — 같은 원리의 더 나쁜 얼굴, 데드락

여기서 축을 하나 옮긴다. 지금까지는 "제약 검사가 언제 되느냐"의 이야기였고, 지금부터는 "락이 언제 잡히느냐"의 이야기다. 둘 다 뿌리는 같다 — flush가 SQL을 DB로 보내는 그 순간에 벌어지는 일이라는 것.

데드락(교착 상태)이란

두 트랜잭션이 서로가 쥔 락을 기다리며 영원히 멈추는 상황이다. DB는 이를 감지하면 한쪽을 희생자로 골라 강제로 롤백시킨다.

유니크 위반보다 훨씬 잡기 어렵다

유니크 위반은 예외 하나로 끝나고 원인도 로그에 찍힌다. 데드락은 재현이 안 되고, 부하가 높을 때만 나고, 로그에는 Deadlock found when trying to get lock이라는 문장만 남는다.

flush로 UPDATE가 나가는 순간, 그 행에 쓰기 락이 걸리고 커밋까지 유지된다(1절). 그래서 한 트랜잭션에서 여러 행을 UPDATE하면 락을 여러 개 순차적으로 쥐게 된다. 두 트랜잭션이 서로 반대 순서로 쥐면 교착이다.

6-1. 그 "순서"는 어디서 오는가

여기가 핵심이다. flush 안의 UPDATE들이 어떤 순서로 나가는지는 내가 엔티티를 다룬 순서(정확히는 영속성 컨텍스트에 올라온 순서)에 좌우된다. 그리고 그 순서는 요청마다 얼마든지 달라진다.

before 요청이 준 순서를 그대로 따른다
@Transactional
public void addPoints(List<Long> memberIds, int amount) {
    for (Long id : memberIds) {        // 클라이언트가 준 순서 그대로
        Member m = memberRepository.findById(id).orElseThrow();
        m.addPoint(amount);
    }
}

// 요청 A: [1, 2, 3]  → 락을 1 → 2 → 3 순으로
// 요청 B: [3, 2, 1]  → 락을 3 → 2 → 1 순으로   ← 서로 반대. 데드락 성립.
after 항상 같은 기준(PK 오름차순)으로 정렬한 뒤 처리
@Transactional
public void addPoints(List<Long> memberIds, int amount) {
    List<Long> ordered = memberIds.stream().distinct().sorted().toList();
    //                                ↑ 중복 제거   ↑ 항상 같은 순서로 고정

    for (Long id : ordered) {
        Member m = memberRepository.findById(id).orElseThrow();
        m.addPoint(amount);
    }
}

// 요청 A: [1,2,3] → 정렬 후 1,2,3
// 요청 B: [3,2,1] → 정렬 후 1,2,3   ← 획득 순서가 같아졌다.

순서가 조용히 흔들리는 다섯 경로 — 전부 "내가 정하지 않은 순서"다

① 요청 파라미터 순서
클라이언트가 준 List를 그대로 순회 — 호출자마다 다르다
② HashSet/HashMap 순회
해시값에 따라 순서가 달라진다. 같은 원소라도 보장 없음
③ ORDER BY 없는 SELECT
반환 순서는 DB가 보장하지 않는다. 실행 계획이 바뀌면 순서도 바뀐다
④ 연관관계를 Set으로 매핑
컬렉션 순회 순서가 정해지지 않는다
⑤ 여러 서비스가 각자 다른 순서로
A 서비스는 회원→주문, B 서비스는 주문→회원 — 테이블 간 순서도 같은 문제다

6-2. 조회 단계에서 순서를 고정하는 것이 더 깔끔하다

before 반환 순서가 보장되지 않는다
List<Member> members =
    memberRepository.findAllByIdIn(ids);
after 쿼리에서 순서를 못 박는다
List<Member> members =
    memberRepository.findAllByIdInOrderByIdAsc(ids);
after 비관적 락을 명시적으로 잡을 때도 같은 원칙
for (Long id : ids.stream().sorted().toList()) {
    accountRepository.findByIdForUpdate(id);   // @Lock(PESSIMISTIC_WRITE)
}

6-3. 이건 Hibernate가 지켜주지 않는다 — 이 문항의 핵심 대비

면접에서 이 대비를 명시적으로 말하면 이해도가 확실히 드러난다

Hibernate가 보장하는 것

"DELETE가 INSERT보다 뒤" — 작업 타입의 순서. 내가 바꿀 수 없고, 알고 피해야 한다.

Hibernate가 보장하지 않는 것

"1번 행 락 → 2번 행 락" — 같은 타입 안에서 어느 행이 먼저인지. 내 코드의 책임이므로 정렬로 직접 고정해야 한다.

가산점 포인트 — 부분적인 도움은 있다: hibernate.order_updates 이 옵션을 켜면 Hibernate가 flush 시점에 UPDATE들을 엔티티 타입과 PK 기준으로 정렬해 실행한다(소스에서는 ExecutableList를 정렬 가능한 형태로 만드는 isOrderUpdatesEnabled() 플래그로 나타난다). 배치 효율을 위한 옵션인데 부수 효과로 데드락 확률도 낮아진다(hibernate.order_inserts도 INSERT에 대해 같은 일을 한다). 다만 기본값이 꺼져 있고, 한계가 분명하다 — ① 한 번의 flush 안에서만 유효하다(중간에 flush가 여러 번 일어나면 소용없다) ② SELECT ... FOR UPDATE나 벌크 JPQL처럼 Hibernate의 UPDATE 액션을 거치지 않는 락 획득 순서는 전혀 덮지 못한다.
옵션은 보험이고, 정렬은 코드로 고정한다

7. 처방 — 코드와 스키마를 고친다

앞의 절들이 "무엇이 왜 일어나는가"였다면 여기서부터는 "그래서 무엇을 하는가"다. 좋은 처방부터 놓는다.

최선 — 7-1
애초에 DELETE + INSERT를 하지 않는다. 있는 행을 UPDATE로 고친다
차선 — 7-2
구조상 불가피하면 flush()로 실행 경계를 하나 더 만든다
스키마 — 7-3
soft delete 환경이면 유니크 제약의 정의 자체를 바꾼다

7-1. 최선 — 애초에 DELETE + INSERT를 하지 않는다

5절의 상황은 사실 UPDATE 한 줄로 끝나는 일이다. 이메일 주인의 이름을 바꾸는 것이라면 행을 지웠다 새로 만들 이유가 없다.

after (최선) 지웠다 넣는 대신, 있는 행을 고친다
@Transactional
public void replaceMember(String email, String newName) {
    Member m = memberRepository.findByEmail(email).orElseThrow();
    m.changeName(newName);   // 변경 감지 → flush 시 UPDATE 한 건
    // 유니크 충돌 자체가 발생할 수 없다. 순서 문제가 사라지는 것이 아니라 "문제 자체"가 사라진다.
}
① 참조가 깨지지 않는다
PK가 유지되므로 이 행을 참조하는 FK·로그·외부 시스템의 참조가 살아 있다
② 더 싸고 락 범위가 좁다
UPDATE 1건으로 끝난다. DELETE+INSERT 2건보다 싸다
③ 이력이 보존된다
created_at 같은 생성 이력이 그대로 남는다

컬렉션 교체에서도 같은 판단이 적용된다. 태그 전체를 갈아끼우는 흔한 코드가 정확히 같은 함정을 밟는다.

before 전체 삭제 + 전체 삽입
@Transactional
public void replaceTags(Long postId, List<String> names) {
    tagRepository.deleteByPostId(postId);
    names.forEach(n -> tagRepository.save(new Tag(postId, n)));
    // (post_id, name) 유니크면 그대로 터진다
    // 안 터지더라도 바뀌지 않은 태그까지 전부 지웠다 다시 넣는다
}
after 차집합만 건드린다
@Transactional
public void replaceTags(Long postId, List<String> names) {
    Set<String> target  = new HashSet<>(names);
    List<Tag>   current = tagRepository.findByPostId(postId);

    current.stream().filter(t -> !target.contains(t.getName()))
           .forEach(tagRepository::delete);            // 빠진 것만 삭제

    Set<String> exists = current.stream().map(Tag::getName).collect(toSet());
    target.stream().filter(n -> !exists.contains(n))
          .forEach(n -> tagRepository.save(new Tag(postId, n)));  // 새 것만 삽입
    // 삭제 대상과 삽입 대상이 겹치지 않으므로 순서가 뒤집혀도 충돌하지 않는다
    // 덤: 실제로 바뀐 것만 SQL이 나가므로 더 싸다
}

7-2. 차선 — 구조상 불가피하면 em.flush()로 경계를 명시

"delete 후 flush를 끼운다"는 처방 자체는 맞다. 다만 최선이 아니라 차선이라는 위치를 알고 쓰는 것이 중요하다.

after (차선) 지우고 넣는 것이 정말 불가피할 때
@Transactional
public void replaceMember(String email, String newName) {
    memberRepository.delete(memberRepository.findByEmail(email).orElseThrow());
    memberRepository.flush();   // ← 여기서 DELETE를 먼저 내보내 자리를 비운다
    //   이 flush를 지우면 유니크 위반이 조용히 부활한다. 반드시 이유를 주석으로 남긴다.
    memberRepository.save(new Member(email, newName));
}
왜 이게 통하는가 — 4절의 규칙으로 설명할 수 있어야 한다 ActionQueue의 순서는 한 번의 flush 안에서만 적용된다. flush()를 중간에 부르면 그 시점의 큐에는 DELETE밖에 없으므로 DELETE가 먼저 나가고, 그 다음에 예약된 INSERT는 다음 flush(커밋 직전)에서 나간다. 즉 개발자가 순서에 개입하는 유일한 수단은 flush 경계를 하나 더 만드는 것이다.

언제 정말 불가피한가

  • 행 전체를 새 스키마로 재구성해야 해서 필드 매핑이 1:1이 아닐 때
  • 상속 매핑에서 타입이 바뀌는 경우 — 엔티티 타입 자체가 달라지면 UPDATE로 표현할 수 없다
  • 이력 테이블처럼 행 교체가 도메인 의미 자체일 때

주의점 둘

  • 반드시 주석으로 이유를 남긴다. 이유 없는 flush()는 다음 사람이 "불필요해 보이는데?" 하며 지우고, 버그가 조용히 부활한다 (→ 8-1절의 순서 단정 테스트가 이걸 막는다)
  • flush로 DELETE를 먼저 보내면 그 행의 락을 커밋까지 쥔다. 이 사이에 외부 API 호출 같은 긴 작업을 넣으면 안 된다

7-3. soft delete 환경이면 — 유니크 제약 자체를 분리한다

물리 삭제 대신 deleted_at 플래그로 지우는 방식(soft delete)을 쓴다면, "지운 행"이 테이블에 그대로 남아 있으므로 순서와 무관하게 유니크 제약이 계속 충돌한다. 이 경우 처방은 코드가 아니라 제약의 정의를 바꾸는 것이다.

before 탈퇴 후에도 이메일 영원히 재사용 불가
constraint uk_member_email unique (email)
after (MySQL) 살아 있는 행끼리만 유니크
-- deleted_at 을 NOT NULL DEFAULT '9999-12-31 00:00:00'
-- 같은 sentinel 로 두는 것이 핵심이다
constraint uk_member_email unique (email, deleted_at)
after (PostgreSQL) 부분 인덱스가 더 깔끔하다
create unique index uk_member_email_alive
    on member (email) where deleted_at is null;
가산점 포인트 — MySQL에서 deleted_at을 NULL로 두면 제약이 사실상 무력화된다 함정 SQL 표준에서 NULL은 서로 같지 않다고 보므로, unique (email, deleted_at)으로 두고 deleted_at을 NULL로 쓰면 (kim@x.com, NULL) 행이 여러 개 들어간다. 그래서 sentinel 값이나 PostgreSQL 부분 인덱스를 쓴다.

8. 안전망 — 기계가 지키게 만든다

"코드 리뷰로 잡는다"는 답은 답이 아니다 이 유형의 버그는 소스 코드만 봐서는 안 보인다 — delete() 다음에 save()가 있는 것은 지극히 자연스러워 보이고, 문제는 실행 시점에 순서가 뒤집힌다는 데 있기 때문이다. 그래서 실행을 관측하는 장치가 필요하다.

안전망 3종 암기 — 보고 · 커밋하고 · 진짜 DB로

보고 = p6spy로 실제 SQL 순서를 본다· 커밋하고 = @Commit으로 롤백이 숨기는 것을 드러낸다· 진짜 DB로 = Testcontainers로 벤더 차이를 없앤다

세 장치는 각각 순서 · 시점 · 벤더라는 서로 다른 축을 덮는다. 하나만 넣는다면 가운데(커밋)다 — 이유는 9절 마지막 꼬리질문에서.

8-1. 보고 — 실제 SQL 순서를 눈으로 본다 (p6spy / datasource-proxy)

show-sql: true나 Hibernate 로거로는 부족하다. 바인딩 값이 ?로 찍혀 어떤 행이 지워지고 어떤 행이 들어갔는지 알 수 없고, 여러 스레드가 섞이면 순서도 흐려진다.

before 이걸로 만족하면 순서 문제를 못 본다
spring:
  jpa:
    show-sql: true         # 바인딩값이 ? 로만 보인다
    properties:
      hibernate:
        format_sql: true
after 완성된 문장을 실행 순서대로 찍는다
// build.gradle
testImplementation 'com.github.gavlyukovskiy:p6spy-spring-boot-starter:<버전>'
-- p6spy 출력 (실제 순서 · 실제 값)
1ms | insert into member (email, name) values ('kim@example.com', 'kim2')
0ms | delete from member where id=1
     ↑ 코드는 delete가 먼저였는데 로그는 insert가 먼저다
습관으로 만들 것 쓰기 로직(특히 삭제·교체·다건 수정)을 건드린 PR에서는 테스트 로그의 SQL 순서를 한 번 눈으로 확인한다. 이것만으로도 5절 유형은 배포 전에 걸러진다.

한 걸음 더 가면 순서를 테스트로 단정할 수 있다. datasource-proxy는 실행된 쿼리를 프로그램으로 수집할 수 있다.

after "DELETE가 INSERT보다 먼저 실행되었는가"를 기계가 검증한다
@Test
void delete가_insert보다_먼저_나가야_한다() {
    QueryExecutionListener listener = /* 실행 SQL을 순서대로 수집 */;

    service.replaceMember("kim@example.com", "kim2");

    List<String> sqls = listener.getExecutedSql();
    int deleteIdx = indexOfFirstStartingWith(sqls, "delete from member");
    int insertIdx = indexOfFirstStartingWith(sqls, "insert into member");
    assertThat(deleteIdx).isLessThan(insertIdx);   // 회귀하면 여기서 빨간불
}
나중에 누가 flush()를 "불필요해 보인다"며 지웠을 때 테스트가 막아준다 — 주석보다 강한 방어다

8-2. 커밋하고 — @DataJpaTest의 롤백이 커밋 시점 문제를 숨긴다

Spring의 테스트는 기본적으로 각 테스트 종료 시 트랜잭션을 롤백한다(@DataJpaTest, @SpringBootTest + @Transactional 모두). 그런데 5절의 예외는 커밋 직전 flush에서 난다.

before 초록불인데 운영에서 터지는 테스트
@DataJpaTest                                  // 종료 시 자동 롤백
class MemberServiceTest {
    @Test
    void 이메일_교체() {
        service.replaceMember("kim@example.com", "kim2");
        // 테스트 메서드가 끝난다 → 커밋이 아니라 롤백
        // → 커밋 직전 flush 가 실행되지 않음 → INSERT/DELETE 가 DB에 도달조차 안 함
        // → 유니크 위반이 발생할 기회가 없다 → 그냥 통과한다
    }
}
after (1) @Commit — 가장 손쉽다
@DataJpaTest
class MemberServiceTest {
    @Test
    @Commit                    // ← 롤백하지 않고 진짜 커밋
    void 이메일_교체() {
        service.replaceMember("kim@example.com", "kim2");
        // 커밋 직전 flush 발생 → insert 가 먼저 나감
        // → DataIntegrityViolationException 으로 실패
        // = 배포 전에 잡혔다
    }
}
after (2) TestTransaction — 커밋 전후를 나눠 검증
@Test
void 이메일_교체() {
    service.replaceMember("kim@example.com", "kim2");

    TestTransaction.flagForCommit();
    TestTransaction.end();        // ← 여기서 실제 커밋

    TestTransaction.start();      // 검증용 새 트랜잭션
    assertThat(memberRepository.findByEmail("kim@example.com"))
        .get().extracting(Member::getName).isEqualTo("kim2");
}
after (3) 가장 정확한 방법 — 테스트에 트랜잭션을 아예 걸지 않는다
@SpringBootTest                               // @Transactional 을 붙이지 않는다
class MemberServiceIntegrationTest {

    @AfterEach
    void cleanUp() { memberRepository.deleteAllInBatch(); }   // 정리는 직접

    @Test
    void 이메일_교체() {
        // 서비스의 @Transactional 이 진짜로 시작되고 진짜로 커밋된다.
        // 운영과 같은 트랜잭션 경계 = 운영과 같은 flush 타이밍.
        service.replaceMember("kim@example.com", "kim2");
    }
}
세 방법의 위치 @Commit이 가장 손쉽고, TestTransaction은 "커밋 전후"를 나눠 검증하고 싶을 때 쓴다. (3)이 가장 정확하다 — 테스트가 트랜잭션을 감싸면 서비스의 @Transactional이 참여(join)해버려서, 커밋 타이밍뿐 아니라 REQUIRES_NEW, 롤백 마킹, 지연 로딩 가능 범위까지 전부 운영과 달라지기 때문이다. 정리 비용을 감수할 가치가 있다.
한 줄로 기억할 것 — "롤백되는 테스트는 커밋 시점에 나는 문제를 구조적으로 통과시킨다"

8-3. 진짜 DB로 — H2가 아니라 Testcontainers

유니크 제약과 데드락의 동작은 DB 벤더마다 다르다. 그래서 "H2에서 통과하고 MySQL에서 터지는" 대표 유형이 바로 이 문항이다.

락 획득 단위와 범위
MySQL InnoDB는 인덱스에 락을 걸고, 유니크 인덱스 검사 과정에서 gap 락을 잡기도 한다. "행이 겹치지 않는데도" 데드락이 나는 상황이 MySQL에만 존재한다
데드락 탐지와 희생자 선택
누가 롤백되는지, 얼마 만에 탐지되는지가 다르다. H2는 아예 타임아웃으로 처리하기도 한다
제약 위반 예외의 형태
에러 코드·메시지가 달라, 예외를 코드로 분기하는 로직은 H2에서만 맞을 수 있다
upsert 문법
ON DUPLICATE KEY UPDATE, ON CONFLICT — 아예 없거나 다르다
after 운영과 같은 엔진을 컨테이너로 띄운다
@SpringBootTest
@Testcontainers
class MemberServiceIntegrationTest {

    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0");
    //     ↑ 운영과 같은 메이저 버전으로 맞춘다

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry r) {
        r.add("spring.datasource.url",      mysql::getJdbcUrl);
        r.add("spring.datasource.username", mysql::getUsername);
        r.add("spring.datasource.password", mysql::getPassword);
    }
}
속도 걱정에 대한 답 컨테이너를 static으로 두면 클래스 간 재사용되고, Testcontainers의 reusable 모드를 켜면 로컬에서 컨테이너가 살아 있어 재기동 비용도 사라진다. 전략은 "단위 테스트는 H2로 빠르게, DB 의존 동작(제약·락·네이티브 쿼리·마이그레이션)은 Testcontainers로" 나누는 것이다.

8-4. 데드락은 재현 테스트로 고정한다

데드락은 "부하가 있어야 난다"고 포기하기 쉽지만, 두 스레드와 CountDownLatch만 있으면 결정론적으로 재현할 수 있다.

after 반대 순서로 갱신하면 나는지, 정렬 후에는 안 나는지를 테스트로 고정
@Test
void 정렬하면_데드락이_나지_않는다() throws Exception {
    CountDownLatch ready = new CountDownLatch(2);
    CountDownLatch go    = new CountDownLatch(1);
    ExecutorService pool = Executors.newFixedThreadPool(2);

    Callable<Void> taskA = () -> { ready.countDown(); go.await();
                                   service.addPoints(List.of(1L, 2L), 10); return null; };
    Callable<Void> taskB = () -> { ready.countDown(); go.await();
                                   service.addPoints(List.of(2L, 1L), 10); return null; };
    //                                              ↑ 반대 순서로 들어온 요청

    Future<Void> fa = pool.submit(taskA);
    Future<Void> fb = pool.submit(taskB);
    ready.await();
    go.countDown();               // 동시에 출발시킨다

    // addPoints 안에서 정렬하지 않으면 → 한쪽이 DeadlockLoserDataAccessException 으로 실패
    // 정렬을 넣으면 → 둘 다 성공
    assertThatCode(() -> { fa.get(); fb.get(); }).doesNotThrowAnyException();
}
이 테스트를 정렬 코드를 넣기 전에 먼저 작성해 빨간불을 확인하는 것이 중요하다
빨간불을 못 봤다면 그 테스트는 아무것도 지키지 못한다

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

flush 시점 셋?
커 · 쿼 · 명 — 커밋 직전(자동) / 쿼리(JPQL·Criteria·네이티브) 실행 직전(auto-flush) / em.flush() 명시 호출.
flush와 commit의 차이?
flush = SQL을 보낸다(우체통), commit = 확정한다(배달 확정). 제약 검사와 락은 flush 시점에 벌어진다 — 그래서 커밋 전에 예외가 난다.
auto-flush의 판정 기준?
query space(쿼리가 읽는 테이블 이름 집합)와 대기 중 작업의 테이블 집합이 겹치는가. DefaultAutoFlushEventListener → areTablesToBeUpdated.
findById는 왜 예외?
쿼리가 아니라 PK 조회(lookup)라 판정 경로 자체를 안 탄다. 1차 캐시 히트 여부와 무관. 동일성 보장 덕분에 flush 없이도 내 변경분이 보인다.
ActionQueue 9칸?
고2 · 인업 · 컬4 · 딜 — 고아 둘 → INSERT(3) · UPDATE(4) → 컬렉션 넷 → DELETE(9) 항상 마지막.
DELETE가 뒤인 이유 둘?
① FK 위반 회피(필요한 행 먼저 만들고 끊긴 행 나중에 삭제) ② JDBC 배치 효율(같은 종류를 몰아야 묶인다). 버그가 아니라 의도.
유니크 위반의 한 문장 설명?
"DELETE로 자리를 비운 뒤 INSERT"라는 전제가 성립하지 않는다. DELETE는 9번 칸, INSERT는 3번 칸이므로 넣고 나서 지우기가 된다.
최선의 처방?
flush() 끼우기는 증상 대응(차선). 최선은 DELETE+INSERT를 UPDATE로 — PK 유지 · 1건으로 감소 · 생성 이력 보존.
Hibernate 보장 / 미보장?
보장 = 타입 순서(INSERT < DELETE). 미보장 = 같은 타입 안의 행 순서 → 락 순서는 내 책임, PK 정렬로 고정.
순서가 흔들리는 경로?
요청 파라미터 · HashSet/HashMap 순회 · ORDER BY 없는 SELECT · Set 매핑 연관관계 · 서비스마다 다른 테이블 순서.
안전망 3종?
보고(p6spy로 실제 순서) · 커밋하고(@Commit으로 롤백이 숨기는 것) · 진짜 DB로(Testcontainers로 벤더 차이).
테스트가 초록불인 이유?
롤백되면 커밋 직전 flush가 아예 실행되지 않는다 — 예외를 만날 기회 자체가 없다. 실력이 아니라 구조의 문제.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

save() 직후 findByName()의 결과는 0인가 1인가? 그럼 findById()는? 필수힌트: 두 답이 다른 이유를 "판정 경로"라는 말로 설명한다

findByName은 1이다. JPQL이므로 실행 직전 auto-flush가 일어나 INSERT가 DB로 나가고, 그 다음 SELECT가 실행되기 때문이다.

findById는 flush를 유발하지 않는다. PK 조회는 쿼리가 아니라 lookup이라 query space 판정 경로를 타지 않는다. 1차 캐시에 있든 없든 마찬가지다 — "캐시에 없으면 DB에 가야 하니 flush하겠지"는 자연스럽지만 틀린 추론이다.

그래도 결과는 올바르다. 새로 저장한 엔티티는 이미 1차 캐시에 있어 그대로 반환되고, 수정된 엔티티는 동일성 보장 덕분에 DB에서 옛 값을 읽어와도 캐시의 인스턴스를 돌려주기 때문이다. PK 조회는 flush 없이도 읽기 일관성이 성립하므로 flush할 이유가 없다.

ActionQueue의 순서를 바꿀 수 있나요? DELETE를 먼저 보내고 싶다면? 필수힌트: "못 바꾼다"로 끝내지 말고, 개입할 수 있는 유일한 지점을 말한다

타입별 순서는 바꿀 수 없다. Hibernate 구현에 박혀 있고(ActionQueue.OrderedActions 열거형의 선언 순서가 곧 실행 순서다), 이유가 FK 위반 회피 + JDBC 배치 효율이라는 설계 의도이기 때문이다.

개발자가 순서에 개입할 수 있는 유일한 수단은 flush()로 실행 경계를 하나 더 만드는 것이다 — DELETE만 쌓아두고 flush하면 그 flush에는 DELETE밖에 없으므로 DELETE가 먼저 나간다.

다만 순서를 강제하려 든다는 것 자체가 설계 신호다. "지웠다 다시 넣는" 모델을 "고친다"로 바꿀 수 있는지를 먼저 검토하는 편이 낫다.

참고로 같은 타입 안의 순서는 hibernate.order_inserts / hibernate.order_updates로 PK 정렬을 켤 수 있는데, 이건 배치 효율을 위한 옵션이고 기본값은 꺼져 있으며 한 번의 flush 안에서만 유효하다. 가산점

커밋도 안 했는데 왜 유니크 제약 위반이 나나요? 함정힌트: 그리고 그 예외를 try/catch로 잡으면 어떻게 되는지까지

flush와 commit이 다르기 때문이다. flush는 SQL을 DB로 보내는 것이고, DB는 SQL을 받는 즉시 제약을 검사하고 락을 잡는다. 커밋은 그 뒤에 "확정하라"고 말할 뿐이다. 그래서 flush 시점에 이미 ConstraintViolationException이 발생하고, Spring이 DataIntegrityViolationException으로 번역해 올려준다.

여기서 이어지는 함정 — 이 예외를 try/catch로 잡아도 트랜잭션은 살아나지 않는다

제약 위반이 나면 Hibernate 세션이 오염 상태로 간주되고 Spring 트랜잭션에 rollback-only 플래그가 찍히므로, catch 후 정상 종료해도 커밋 시점에 UnexpectedRollbackException이 터지며 catch 블록 안에서 한 작업까지 함께 롤백된다. 처방은 후속 작업을 REQUIRES_NEW로 분리하거나 예외를 트랜잭션 경계 밖에서 잡는 것이다. 가산점

데드락 순서를 Hibernate가 정렬해 주지 않나요? 왜 코드로 고정해야 하나요? 시니어 변별힌트: 보장하는 것과 보장하지 않는 것을 먼저 갈라 놓고 시작한다

Hibernate가 보장하는 것과 보장하지 않는 것을 정확히 나눠야 한다.

보장하는 것 — 작업 "타입"의 순서

INSERT는 항상 DELETE보다 먼저다. 내가 바꿀 수 없으니 알고 피해야 할 규칙.

보장하지 않는 것 — 같은 타입 안의 행 순서

기본 설정에서 UPDATE들은 대체로 영속성 컨텍스트에 올라온 순서로 나가고, 그 순서는 요청 파라미터 · Set 순회 · ORDER BY 없는 SELECT에 따라 요청마다 달라진다.

그래서 락 획득 순서는 내 코드의 책임이고, 처방은 처리 대상을 항상 같은 기준(보통 PK 오름차순)으로 정렬한 뒤 순회하는 것이다.

hibernate.order_updates가 부분적으로 돕지만 보험 이상은 아니다 — 기본값이 꺼져 있고, 한 번의 flush 안에서만 유효하며, SELECT ... FOR UPDATE나 벌크 JPQL처럼 Hibernate의 UPDATE 액션을 거치지 않는 락 획득은 전혀 덮지 못한다.

한 걸음 더 가면 트랜잭션 자체를 짧게 자르는 것이 근본 처방이다. 1000건을 한 트랜잭션에서 UPDATE하면 정렬을 해도 락 보유 시간이 길어 경합이 커지므로, 배치로 쪼개거나 아예 벌크 UPDATE 한 문장으로 내리는 편이 낫다.

이 유형을 배포 전에 발견하는 장치를 팀에 하나만 넣는다면 무엇을 넣겠나요? 시니어 변별힌트: 비용 대비 커버 범위로 고르고, 그 다음 순서까지 말한다

@DataJpaTest의 자동 롤백을 걷어내는 것을 고르겠다. 이유는 비용 대비 커버 범위다.

p6spy는 로그를 남길 뿐 사람이 봐야 하고, Testcontainers는 인프라 변경이 필요하다. 반면 "쓰기 로직의 통합 테스트는 실제 커밋까지 간다"는 규칙 하나는 @Commit 한 줄 또는 테스트 클래스에서 @Transactional을 빼는 것으로 끝나는데, 이것만으로 유니크 위반, FK 위반, UnexpectedRollbackException, 커밋 시점 flush 순서 문제, 데드락이 한꺼번에 표면으로 올라온다.

롤백되는 테스트는 커밋 시점 문제를 구조적으로 통과시킨다 — 이 한 가지 성질이 지금까지 통과해 온 초록불의 신뢰도를 통째로 깎아먹고 있기 때문이다.

그 다음 순서는 이렇게 붙이겠다. ② p6spy를 테스트 프로파일 기본으로 켜서 SQL 순서가 항상 로그에 남게 한다 ③ 쓰기 핵심 경로에는 쿼리 수·순서 단정 테스트를 붙여 사람의 눈에서 기계로 옮긴다 ④ 제약·락에 의존하는 시나리오는 Testcontainers로 옮긴다.

원칙은 하나다 — "사람이 잘 보자"는 대책이 아니다.
회귀를 막으려면 빨간불이 되는 테스트가 존재해야 한다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

저장 로직 테스트를 findById로 검증했더니 항상 통과합니다. 무엇이 문제인가요? 함정힌트: 그 검증에서 flush가 몇 번 일어났는지 세어본다

그 테스트는 아무것도 검증하지 못하고 있다. save()는 INSERT를 예약만 하고, 뒤이은 findById()는 PK 조회라 auto-flush를 유발하지 않으며, 찾는 엔티티는 이미 1차 캐시에 있으므로 SQL 없이 그대로 반환된다. 즉 flush가 한 번도 일어나지 않은 채 방금 내가 넣은 그 객체를 되돌려받은 것이고, DB에 정말 들어갔는지는 전혀 검증되지 않는다.

고치는 방법은 셋이다. ① 검증을 JPQL 기반 조회(findByEmail 등)로 바꿔 auto-flush를 유발시킨다 ② 검증 전에 flush() + clear()로 1차 캐시를 비워 DB에서 진짜 읽어오게 만든다 ③ @Commit이나 트랜잭션 없는 통합 테스트로 실제 커밋까지 간다.

②가 특히 유용한 이유는 clear() 없이 flush()만 하면 여전히 1차 캐시가 답을 주기 때문이다. "내가 만든 인스턴스가 아니라 DB가 준 값으로 검증한다"는 것이 이 유형 테스트의 원칙이다.

@Transactional(readOnly = true)에서는 flush가 일어나나요? 가산점힌트: JPA 표준의 기능이 아니라 Spring + Hibernate 조합의 동작이다

Hibernate를 구현체로 쓰는 Spring 환경에서는 flush 모드가 MANUAL로 바뀌어, 변경 감지에 의한 UPDATE가 나가지 않는다. 읽기 전용임을 선언했으니 스냅샷 비교와 flush 자체를 건너뛰어 비용을 아끼는 것이 목적이다.

여기서 실무 함정이 둘 나온다.

① "읽기 전용인데 값을 바꿨더니 저장이 안 된다" — 예외도 안 나고 조용히 무시된다. 쓰기 로직에 readOnly = true가 잘못 붙어 있으면 버그가 소리 없이 생긴다.

② 그렇다고 "읽기 전용이니 안전하다"고 믿으면 안 된다 — 벌크 JPQL(@Modifying)이나 네이티브 DML은 영속성 컨텍스트를 거치지 않고 DB로 직접 나가므로 flush 모드와 무관하다. readOnly가 막아주는 것은 "변경 감지에 의한 flush"이지 "모든 쓰기"가 아니다.

PK 생성 전략(IDENTITY vs SEQUENCE)이 이 문제에 영향을 주나요? 가산점힌트: "언제 id를 알 수 있는가"가 "언제 INSERT를 보내야 하는가"를 정한다

영향을 준다. 그리고 IDENTITY 쪽이 더 나쁘다.

GenerationType.IDENTITY는 PK를 DB의 auto_increment에 맡긴다. 그런데 Hibernate는 엔티티를 영속 상태로 만들려면 id가 있어야 하고, 그 id는 DB만 안다. 그래서 persist() 시점에 INSERT를 즉시 실행해 id를 받아온다(소스에서 early insert라 부르며, ActionQueue.addInsertAction()이 isEarlyInsert()인 경우 큐에 쌓지 않고 바로 executeInserts()를 호출한다).

그래서 IDENTITY에서는 INSERT는 이미 나갔는데 DELETE는 flush까지 대기한다 — 순서 역전이 더 확실하게 일어난다

덤으로 IDENTITY는 INSERT를 배치로 묶는 것도 사실상 불가능하다(건건이 id를 받아와야 하므로). 대량 INSERT 성능이 중요하면 SEQUENCE + allocationSize 쪽이 유리하다.

JPQL 한 줄이 왜 "관계없어 보이는" UPDATE까지 유발할 수 있나요? 가산점힌트: 판정과 실행은 다른 단계다. 그리고 네이티브 쿼리는 판정 자체를 못 한다

먼저 갈라야 할 것이 있다. query space 겹침 판정은 "flush를 할 것인가 말 것인가"를 정하는 단계이지, "겹치는 테이블의 변경만 골라 보낸다"는 보장이 아니다. 그래서 "내 조회는 orders만 건드리니 member 변경은 안 나가겠지"라고 가정한 코드는 위험하다.

네이티브 쿼리에서는 더 분명하다. Hibernate는 SQL 문자열을 파싱해 테이블을 알아내지 않으므로, "어느 테이블을 건드리는지 모른다"고 보고 보수적으로 전체를 flush한다(NativeQueryImpl.prepareForExecution()이 동기화 대상 query space가 없으면 session.flush()를 그냥 호출한다).

그래서 통계용 네이티브 쿼리 한 줄 때문에 트랜잭션 중간에 예상 못 한 UPDATE가 무더기로 나가는 사고가 생긴다. 나쁜 점은 결과가 틀리는 게 아니라 락을 훨씬 일찍 잡게 되어 경합·데드락 확률이 올라간다는 것이다.

좁히는 방법은 NativeQuery.addSynchronizedEntityClass(...)(또는 addSynchronizedQuerySpace)로 관련 엔티티를 명시하는 것이고, 더 나은 방법은 읽기 전용 통계 조회를 쓰기 트랜잭션과 섞지 않는 것이다.

동료가 save() 뒤에 습관처럼 saveAndFlush()를 씁니다. 어떤 리뷰를 남기겠나요?힌트: "불필요하다"로 끝내면 절반이다. 무엇을 대가로 지불하는지 말한다

대부분의 경우 불필요하고, 공짜가 아니다. 이유를 세 층으로 말한다.

① 정확성을 위해 필요한 경우가 거의 없다. 같은 트랜잭션 안에서 JPQL로 조회하면 auto-flush가 알아서 해주고, PK로 조회하면 1차 캐시가 답을 준다. 즉 "저장한 게 안 보일까 봐" 붙이는 saveAndFlush()는 이미 보장된 것을 중복으로 사는 것이다.

② 비용은 락 보유 시간이다. flush로 UPDATE/DELETE가 나가면 그 순간부터 커밋까지 그 행의 쓰기 락을 쥔다. 트랜잭션 앞쪽에서 flush하고 뒤에서 외부 API를 호출하면 락 보유가 수백 ms로 늘어 경합과 데드락 확률이 올라간다.

③ 배치 기회를 깎는다. 건건이 flush하면 같은 종류의 SQL을 모아 한 번에 보내는 JDBC 배치가 성립하지 않는다.

그래서 리뷰 코멘트는 이렇게 남긴다 — "이 flush가 필요한 이유가 순서 강제인지, DB 생성 값 읽기인지, 대량 처리의 clear() 짝인지 알려주세요. 셋 중 하나가 아니면 지우고, 맞다면 그 이유를 주석으로 남겨 주세요." 이유 없는 flush()는 다음 사람이 지워서 버그를 부활시키거나, 반대로 무서워서 못 지우고 계속 남는다.

한 줄 요약
flush는 커밋 직전 · JPQL 실행 직전(auto-flush) · em.flush() 세 시점에 일어나고 findById는 PK 조회라 그 판정 경로를 타지 않으며, flush가 SQL을 내보내는 순서는 내 코드 순서가 아니라 Hibernate가 FK 안전과 JDBC 배치를 위해 고정해 둔 ActionQueue 순서(DELETE가 항상 마지막)다 — 그래서 "지우고 넣기"는 "넣고 지우기"가 되고, 최선의 처방은 flush()를 끼우는 것이 아니라 DELETE+INSERT를 UPDATE로 바꾸는 것이며, 같은 원리로 생기는 데드락은 Hibernate가 지켜주지 않으니 PK 정렬로 코드에 고정하고, 이 모든 것은 p6spy · @Commit · Testcontainers로 배포 전에 기계가 잡게 만든다.
