벌크 연산(@Modifying)과 영속성 컨텍스트
DB는 바뀌었는데 메모리는 옛날 값

면접 질문: "벌크 연산(@Modifying) 후 영속성 컨텍스트는 어떻게 처리해야 하나요?"

핵심 관전 포인트 — 벌크 연산은 영속성 컨텍스트를 거치지 않는다. 1차 캐시를 우회해 DB로 직행한다. 그래서 답의 출발점은 딱 하나다 — 벌크 UPDATE 직후 DB와 1차 캐시는 서로 다른 값을 갖는다. 흔한 오해가 "벌크 연산도 영속성 컨텍스트가 모아서 한번에 처리한다"인데 정반대다. 벌크 연산은 쓰기 지연(write-behind) 대상이 아니라, 오히려 JPQL 실행 직전에 아직 안 나간 변경분을 flush한 다음 즉시 DB로 나간다. 이 불일치가 만드는 사고는 두 방향이다. ① 조회 사고 — 컨텍스트에 남은 엔티티는 옛 값을 계속 돌려준다("DB는 바뀌었는데 API 응답은 그대로"). ② 덮어쓰기 사고 — 그 옛 값 엔티티를 조금이라도 건드리면 커밋 시점 dirty checking이 전 컬럼 UPDATE를 날려 벌크 결과를 조용히 되돌린다. @Modifying의 옵션 두 개는 방향이 정반대다 — flushAutomatically는 실행 전 flush(변경분을 벌크 조건에 반영), clearAutomatically는 실행 후 clear(낡은 캐시를 폐기). 다만 clearAutomatically는 안전장치가 아니다 — 컨텍스트를 통째로 비우므로 같은 트랜잭션에서 수정 중이던 다른 엔티티의 변경분까지 소실되고, 남은 참조는 전부 준영속이 되어 지연 로딩이 터진다. 진짜 처방은 옵션이 아니라 배치다: 영속성 컨텍스트를 우회하는 연산과, 영속성 컨텍스트에 의존하는 연산을 같은 트랜잭션에 섞지 않는다.
  • 1
    벌크 연산은 영속성 컨텍스트를 우회해 즉시 DB로 나간다 — 쓰기 지연 큐에 쌓였다가 커밋 때 나가는 것이 아니라, 실행 직전 flush가 선행되고 그 자리에서 UPDATE가 나간다. 엔티티를 메모리에 올리지 않으므로 1차 캐시는 갱신될 방법이 없다 → 실행 직후 DB와 메모리가 어긋난다.
  • 2
    그 어긋남이 두 방향의 사고를 만든다 — ① 낡은 값 조회(재조회해도 SELECT조차 안 나가고 캐시가 옛 값을 돌려준다) ② 덮어쓰기(그 엔티티의 name만 바꿔도 커밋 시 전 컬럼 UPDATE가 나가 벌크가 만든 값을 되돌린다). 둘 다 예외가 나지 않는다 — 그래서 원인을 모르면 며칠을 헤맨다.
  • 3
    옵션은 방향이 반대이고, 진짜 처방은 배치다 — flushAutomatically는 실행 전 반영, clearAutomatically는 실행 후 폐기. clear는 컨텍스트를 통째로 비워 다른 엔티티의 미flush 변경분까지 소실시키므로 안전장치가 아니다. "먼저 배치로 풉니다 — 벌크를 트랜잭션 맨 끝(또는 맨 앞)이나 별도 트랜잭션에 두고, 그게 불가능할 때만 두 옵션을 짝으로 켭니다."

0. 질문 + 출제 의도

질문: "벌크 연산(@Modifying) 후 영속성 컨텍스트는 어떻게 처리해야 하나요?"

출제 의도: 벌크 UPDATE가 1차 캐시를 우회해 "DB는 바뀌었는데 조회 결과는 옛날 값"인 상황은 증상이 괴상해서 원인을 모르면 며칠을 헤맨다. 겪었거나 원리를 아는 사람만 즉답한다. 즉 채점 지점은 @Modifying 사용법 암기가 아니라 증상을 보고 원인을 역추적할 수 있는가다.

이 사고의 얼굴 — 아무것도 잘못되어 보이지 않는다 코드에는 잘못이 없어 보이고, 예외도 안 나고, 로그도 조용하다. 벌크 UPDATE는 분명히 성공했고 DB를 직접 조회하면 값이 바뀌어 있다. 그런데 애플리케이션이 돌려주는 값만 다르다 — 이 조합에서 "아, 1차 캐시구나"에 도달하지 못하면 며칠이 날아간다.
이 문항이 특히 위험한 이유 세 가지 ① 실패가 조용하다 — 벌크 UPDATE가 dirty checking에 덮어쓰이면 로그상 두 UPDATE는 모두 성공이고, 남는 흔적은 "결과가 사라졌다"는 사실뿐이다.
② 테스트에서 안 잡힌다 — @Transactional을 붙인 테스트는 테스트와 서비스가 같은 영속성 컨텍스트를 공유하므로 검증용 재조회조차 1차 캐시에서 나온다(9절).
③ 재현 조건이 배치 순서다 — 벌크를 트랜잭션 앞쪽에 두면 터지고 맨 뒤에 두면 안 터진다. "어제까지 되던 코드가 리팩터링 후 깨졌다"의 전형이다.

함정 ① "영속성 컨텍스트가 알아서 처리하겠지"

벌크 연산은 컨텍스트를 거치지 않는다. 이 전제가 뒤집혀 있으면 이후 추론이 전부 반대로 간다 — DB와 메모리가 늘 일치한다고 믿게 되므로 이 문항의 문제 자체가 존재하지 않게 된다.

함정 ② "clearAutomatically = true 붙이면 끝"

증상은 사라지지만 더 조용한 사고(다른 엔티티 변경분 소실)로 옮겨간다. 이 옵션을 만병통치약으로 말하면 그 자리가 감점 지점이다(6절).

읽기 전에 용어 셋 — 이 문서는 이 셋의 관계만으로 굴러간다

영속성 컨텍스트
persistence context
JPA가 트랜잭션 동안 엔티티를 담아두고 관리하는 메모리 공간. "영속(persistent) 상태의 객체들이 놓인 문맥"이라 이 이름이 붙었다.
1차 캐시
first-level cache
그 안에서 식별자(PK) → 엔티티 객체로 저장해 두는 맵. findById(1L)을 두 번 불러도 두 번째는 DB로 나가지 않는다. 트랜잭션이 끝나면 통째로 사라진다.
쓰기 지연
write-behind
엔티티를 수정해도 그 자리에서 UPDATE를 보내지 않고 flush 시점(보통 커밋 직전)까지 모아 두었다가 한꺼번에 내보내는 동작.

"1차"인 이유는 애플리케이션 전역에 남는 2차 캐시가 따로 있기 때문이다 — 그리고 2차 캐시도 벌크 연산이 무효화해 주지 않는다(8절).

1. 원리 — 벌크 연산은 영속성 컨텍스트를 우회해 즉시 실행된다

1-1. 벌크 연산이란 — 그리고 왜 우회할 수밖에 없는가

벌크 연산(bulk operation)은 여러 행을 SQL 한 문장으로 한꺼번에 바꾸는 것을 말한다. "덩어리(bulk)로 처리한다"는 뜻이다.

before 한 건씩 — 1만 건이면 UPDATE 1만 번
@Transactional
public void expireAllCoupons() {
    List<Coupon> coupons =
        couponRepository.findByStatus(ACTIVE); 1만 건 적재
    for (Coupon c : coupons) {
        c.setStatus(EXPIRED);  커밋 시 UPDATE 1만 번
    }
}
// 엔티티 1만 개 적재(OOM 위험) + 스냅샷 1만 개
after 벌크 — UPDATE 1 문장
@Modifying
@Query("update Coupon c set c.status = 'EXPIRED' "
     + "where c.status = 'ACTIVE'")
int expireAllCoupons();   반환 = 영향 행 수

// DB 가 자기 안에서 한 번에 처리한다.
// 엔티티를 메모리에 올리지 않는다.
벌크가 빠른 이유(엔티티를 메모리에 올리지 않는다)와 벌크가 사고를 내는 이유(1차 캐시에 넣을 것이 없다)는 같은 문장이다

엔티티를 안 올렸으니 1차 캐시에 넣을 것도 없고, 넣지 않았으니 캐시에 이미 들어 있던 옛 객체를 갱신해 줄 방법도 없다. 이 문항의 모든 문제가 여기서 파생된다.

1-2. @Modifying을 붙이지 않으면 — 조회 실행 경로로 들어가 예외가 난다

Spring Data JPA는 @Query에 적힌 JPQL 문자열을 파싱해서 조회인지 변경인지 판단하지 않는다. 리포지토리 메서드를 만들 때 어떤 실행 방식을 쓸지 미리 정해두는데, 기본값이 조회다. 그래서 @Modifying은 개발자가 직접 붙이는 "이건 조회가 아니라 변경 쿼리다"라는 표시(marker)다.

before 컴파일도 되고 앱도 뜬다. 호출하는 순간 터진다
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    // @Modifying 누락
    @Query("update Product p set p.stock = 0 "
         + "where p.category = :category")
    int zeroStock(@Param("category") String category);
}
after executeUpdate() 경로로 실행된다
public interface ProductRepository
        extends JpaRepository<Product, Long> {

    @Modifying
    @Query("update Product p set p.stock = 0 "
         + "where p.category = :category")
    int zeroStock(@Param("category") String c); 영향 행 수
}

붙이지 않고 호출하면 Spring Data JPA가 조회 실행 경로로 들어가 getResultList()를 호출하고, 하이버네이트가 "SELECT 문이 아닌데 결과 목록을 달라고 한다"며 거부한다. 예외 타입과 메시지는 하이버네이트 버전에 따라 다르다.

# 하이버네이트 5 (Spring Boot 2 계열)
org.hibernate.hql.internal.QueryExecutionRequestException:
    Not supported for DML operations [update Product p set p.stock = 0 ...]

# 하이버네이트 6 (Spring Boot 3 계열)
org.hibernate.query.IllegalSelectQueryException:
    Expecting a selection query, but found 'update Product p set p.stock = 0 ...'

# 둘 다 Spring 의 예외 변환을 거쳐 보통 InvalidDataAccessApiUsageException 으로 감싸진다
면접에서 이렇게 말하는 편이 안전하다 정확한 클래스명을 외우는 것보다 "조회 실행 경로(getResultList())로 들어가서 실패한다"는 메커니즘을 말하는 편이 낫다. 버전마다 이름이 바뀌는 값이라 단정하면 위험하다.

@Modifying이 하는 일은 정확히 셋이다

실행 메서드 교체
getResultList() → executeUpdate()
반환 타입 허용
int(또는 void)를 허용한다. int는 영향받은 행 수다.
두 옵션 제공
flushAutomatically / clearAutomatically로 컨텍스트를 언제 손볼지 지정(5절).

1-3. 트랜잭션도 필수다 — 그리고 영향 행 수를 버리지 마라

변경 쿼리는 쓰기 트랜잭션 안에서만 실행할 수 있다. @Transactional 없이 호출하면 실행 시점에 jakarta.persistence.TransactionRequiredException: Executing an update/delete query가 난다.

JpaRepository의 기본 구현체(SimpleJpaRepository)는 클래스 레벨이 @Transactional(readOnly = true)라서, 직접 선언한 @Modifying 메서드는 그 기본값을 물려받는다. 즉 리포지토리 메서드만 덜렁 호출하면 읽기 전용 트랜잭션 안에서 변경을 시도하는 꼴이 된다.

before 서비스에 트랜잭션이 없다
@Service
public class ProductService {

    public void reset(String category) {
        productRepository.zeroStock(category);
        // TransactionRequiredException
    }
}
after 쓰기 트랜잭션 + 영향 행 수 확인
@Service
public class ProductService {

    @Transactional   readOnly 가 아닌 쓰기 트랜잭션
    public void reset(String category) {
        int affected = productRepository.zeroStock(category);
        log.info("재고 초기화 {}건", affected);
    }
}

영향 행 수를 버리지 마라 가산점

int 반환값은 "내가 의도한 만큼 바뀌었는가"를 검증할 수 있는 유일한 신호다. 0이 돌아왔다는 건 조건에 걸린 행이 하나도 없었다는 뜻이고, 이건 대개 버그다(8절의 "WHERE에 안 걸림" 증상 — 실행 전 flush 누락의 대표 신호). 반환 타입을 void로 두면 이 신호를 통째로 버리는 것이다.

@Modifying 메서드는 항상 int로 받고, 기대 건수와 대조한다

2. 타이밍 — 가장 흔한 오해부터 깨고 간다

많은 사람이 벌크 연산의 동작을 이렇게 상상한다. 그리고 이 그림에서는 DB와 메모리가 늘 일치하므로 이 문항의 문제 자체가 존재하지 않게 된다.

상상하는 동작 — 전부 틀렸다

  • ① 벌크 UPDATE 호출
  • ② 영속성 컨텍스트가 "1만 건을 바꿔야겠군" 하고 기억해둔다
  • ③ 1차 캐시의 엔티티들도 새 값으로 갱신된다
  • ④ 커밋 시점에 모아서 DB로 나간다

특히 ②③이 치명적이다. 오해의 뿌리는 "JPA를 통해 나가는 모든 변경은 영속성 컨텍스트를 거친다"는 일반화인데, 벌크 연산은 정확히 그 규칙의 예외다.

실제 동작

  • ① 벌크 UPDATE 호출
  • ② (flush 선행) 아직 DB에 안 나간 변경분을 먼저 내보낸다
  • ③ UPDATE 문이 즉시 DB로 나간다 — 커밋을 기다리지 않는다
  • ④ 1차 캐시는 아무것도 모른다 — 갱신되지 않는다

③이 이 문항의 핵심이고, ④가 그 대가다.

2-1. ②는 왜 필요한가 — flush-before-query(자동 flush)

앞서 정의한 쓰기 지연 때문에 자바 코드에서 바꾼 값이 아직 DB에 없을 수 있다. 그 상태로 벌크 UPDATE를 날리면 DB는 낡은 값을 기준으로 WHERE를 평가한다. 그래서 하이버네이트는 JPQL을 실행하기 전에 flush를 먼저 수행해 "쿼리가 최신 상태를 보게" 만든다.

단, 이 자동 flush는 무조건 일어나지 않는다. 하이버네이트는 최적화를 한다 — 쿼리가 건드리는 테이블과, 아직 반영되지 않은 변경분의 테이블이 겹칠 때만 flush한다. 이 테이블 집합을 query space("이 쿼리가 발 딛고 선 공간")라 부른다.

겹친다 → flush 된다
Product를 수정해둔 채 Product를 벌크 UPDATE → 같은 테이블이므로 밀린 변경분이 먼저 나간다.
안 겹친다 → flush 안 된다
Event를 수정해둔 채 Ticket을 벌크 UPDATE → 다른 테이블이므로 건너뛴다. 이 세부가 5절·6절에서 결정적으로 중요해진다.
정확도 주의 — 자동 flush는 계약이 아니라 최적화 휴리스틱이다 자동 flush의 정확한 발동 조건은 flush 모드(AUTO / COMMIT / MANUAL)와 하이버네이트 버전·부트스트랩 방식에 따라 달라진다. 기본값인 FlushModeType.AUTO에서 위 규칙이 적용되고, @Transactional(readOnly = true)는 세션을 MANUAL로 두어 자동 flush를 아예 끈다. 그래서 "하이버네이트가 알아서 flush해주니 괜찮다"에 기대는 것은 설정 하나로 무너지는 가정이다.

2-2. 타임라인으로 보면 — 어긋남이 시작되는 지점

stock = 100인 Product를 로드해둔 상태에서 벌크로 stock = 0을 날리는 상황이다.

면접에서 이 두 문장으로 시작하면 된다

"벌크 연산은 영속성 컨텍스트를 우회해 즉시 DB로 나갑니다.
그래서 실행 직후 DB와 1차 캐시가 어긋나고, 그 어긋남을 어떻게 정리하느냐가 이 질문의 답입니다."

3. 사고 ① 덮어쓰기 — name만 바꿨는데 stock이 되돌아간다

-- 영향 행 수: N  → DB 의 stock 은 이제 전부 0

-- ③ 커밋 시점, dirty checking 이 만들어 낸 UPDATE
update product
set    category = ?, name = ?,   -- '[마감] 구상품'

예외도, 경고도, 롤백도 없다 세 문장 모두 성공했다. 애플리케이션 입장에서는 아무 일도 일어나지 않은 정상 트랜잭션이다. 남는 흔적은 "결과가 사라졌다"는 사실뿐이라 원인을 모르면 며칠을 헤맨다.

3-3. 왜 stock까지 되돌아가나 — 두 사실이 겹친다

사무실 비유로 한 번에 — 왜 "이름만 바꿨는데" 재고가 되돌아가나

DB의 행 = 서버에 있는 원본 문서, 1차 캐시의 엔티티 = 내 책상 위 사본, 스냅샷 = 사본을 받아온 순간 찍어둔 사진이다.

  • 총무팀이 서버의 원본만 직접 고쳤다(벌크 UPDATE). 내 책상 사본에는 아무도 알려주지 않았다.
  • 나는 사본의 제목 한 줄만 고쳐서 제출한다(setName).
  • 그런데 제출 규칙이 "수정한 줄만"이 아니라 "문서 전체를 통째로 교체"다(전 컬럼 UPDATE). → 총무팀이 고친 재고 칸까지 내 낡은 사본 값으로 되돌아간다.
면접 답변 문장 — "name만 바꿔도 하이버네이트는 전 컬럼 UPDATE를 날립니다.
stock 자리에는 로드 시점 값인 100이 들어가고, 그게 벌크가 만든 0을 덮습니다. 스냅샷은 DB를 다시 읽어 만들어지지 않기 때문입니다."

4. @DynamicUpdate를 붙이면 해결되나 — 아니다

엔티티에 @DynamicUpdate를 붙이면 하이버네이트가 실제로 변경된 컬럼만 UPDATE에 넣는다. "UPDATE 문을 미리 만들지 않고 매번 동적으로(dynamic) 만든다"는 뜻이다.

설정 엔티티에 붙인다
@Entity
@DynamicUpdate   // 변경된 컬럼만 UPDATE 에 포함
public class Product { ... }
결과 ③ 이 이렇게 바뀐다
update product set name = ? where id = 1;
--            stock 이 빠졌다
--            → 벌크가 만든 0 이 살아남는다

이 특정 덮어쓰기는 확실히 피한다. 그러나 근본 해결이 아니다. 이유가 넷이다.

① 불일치 자체는 그대로다
p.getStock()은 여전히 100을 돌려준다. 그 값으로 계산하거나 응답에 담으면 틀린 값이 그대로 나간다. 덮어쓰기만 막았을 뿐 읽기 오염은 남는다.
② stock을 건드리면 다시 터진다
p.setStock(p.getStock() - 1)처럼 낡은 값을 근거로 계산하면 stock이 변경 컬럼에 포함되어 99가 쓰인다. 벌크 결과는 또 사라진다.
③ 엔티티 전역 설정이다
특정 트랜잭션의 문제를 풀려고 그 엔티티의 모든 UPDATE 방식을 바꾼다. 대가가 문제 범위보다 넓고, SQL 재사용·구문 캐시 이점을 잃는다.
④ 의도가 드러나지 않는다
6개월 뒤 코드를 읽는 사람은 이게 "벌크 덮어쓰기를 막으려고" 붙었다는 걸 알 수 없다. 누군가 성능상의 이유로 떼는 순간 사고가 부활한다.
면접에서의 정답 형태 가산점 @DynamicUpdate는 컬럼 수가 아주 많고 갱신 대상이 소수일 때 쓰는 성능 옵션이지 벌크 연산 대책이 아니다. 언급하는 것 자체는 좋지만, "이건 증상 하나만 가리고 불일치는 그대로 남습니다"까지 붙여야 답이 완성된다.

5. 두 옵션 — 하나는 실행 전, 하나는 실행 후 (방향이 정반대다)

@Modifying에는 영속성 컨텍스트를 손보는 옵션이 두 개 있고, 하나는 쿼리 실행 전, 하나는 실행 후에 동작한다. 둘 다 기본값은 false다.

@Modifying(flushAutomatically = true,   // 실행 "전" : 밀린 변경분을 DB 로 내보낸다
           clearAutomatically = true)   // 실행 "후" : 낡아버린 1차 캐시를 통째로 비운다
@Query("update Product p set p.stock = 0 where p.category = :category")
int zeroStock(@Param("category") String category);
표만 보면 "둘 다 캐시를 손보는 옵션" 정도로 뭉뚱그려 기억하게 된다 — 그래서 아래 도식이 필요하다
옵션시점하는 일데이터가 움직이는 방향막아주는 사고
flushAutomatically = true쿼리 실행 전em.flush() — 밀린 변경분을 DB에 반영메모리 → DB (내보낸다)방금 바꾼 값이 벌크의 WHERE에 안 걸림
clearAutomatically = true쿼리 실행 후em.clear() — 1차 캐시를 통째로 폐기메모리 → 버림 (아무 데도 안 간다)낡은 값 조회 / dirty checking 덮어쓰기

이 한 문장으로 외우면 헷갈리지 않는다

"전에 넣고, 후에 버린다"
flushAutomatically=실행 前=메모리 → DB · 보존
clearAutomatically=실행 後=메모리 → 폐기 · 소실

5-1. flushAutomatically = true — 실행 전 flush(반영)

막으려는 사고: 자바 코드에서 방금 바꾼 값이 아직 DB에 없어서, 벌크 UPDATE의 WHERE 조건에 걸리지 않는 것. 위험한 형태는 벌크의 조건이 "방금 바꾼 값"에 의존할 때다.

before 영향 행 수 0 — 예외 없이 아무 일도 안 일어난다
@Modifying
@Query("update Ticket t set t.status = 'EXPIRED' "
     + "where t.event.id in "
     + "(select e.id from Event e where e.status = 'CLOSED')")
int expireTicketsOfClosedEvents();

@Transactional
public void closeEvent(Long eventId) {
    Event event = eventRepository.findById(eventId).orElseThrow();
    event.setStatus(CLOSED);   메모리에서만 CLOSED

    int n = ticketRepository.expireTicketsOfClosedEvents();
    // DB 안의 event.status 는 아직 OPEN 일 수 있다
    // → 서브쿼리에 이 이벤트가 안 걸린다 → n = 0
    // → 티켓은 하나도 만료되지 않는다. 예외 없이.
}
after 실행 전 flush 를 명시한다
@Modifying(flushAutomatically = true)
@Query("update Ticket t set t.status = 'EXPIRED' "
     + "where t.event.id in "
     + "(select e.id from Event e where e.status = 'CLOSED')")
int expireTicketsOfClosedEvents();

// 실행 직전에 em.flush() 가 확실히 수행된다
//   → DB 의 event.status 도 CLOSED
//   → 서브쿼리에 걸린다 → n = 티켓 수
// 리뷰어에게 "이 벌크는 최신 상태 위에서 돈다"는
// 의도가 코드에 드러난다는 것 자체가 값이다
"하이버네이트가 어차피 자동 flush 해주지 않나요?" 시니어 변별 대개는 해준다. 그러나 조건부다. 2-1절에서 봤듯 자동 flush는 쿼리가 건드리는 테이블과 밀린 변경분의 테이블이 겹칠 때만 일어난다. 위 예는 서브쿼리에 Event가 등장하므로 겹칠 가능성이 높지만, 벌크가 건드리는 테이블에 등장하지 않는 엔티티의 변경분은 flush되지 않는다. 게다가 @Transactional(readOnly = true)가 걸린 경로에서는 flush 모드가 MANUAL이라 자동 flush가 아예 꺼진다.
결론: 자동 flush는 하이버네이트의 최적화 휴리스틱이지 계약이 아니다.

5-2. clearAutomatically = true — 실행 후 clear(폐기)

막으려는 사고: 2절의 조회 오염과 3절의 덮어쓰기. 벌크 실행 직후 1차 캐시를 통째로 비워, 그 뒤의 조회가 DB를 다시 읽게 만든다.

before 재조회해도 SELECT 가 나가지 않는다
@Modifying
@Query("update Product p set p.stock = 0")
int zeroStockAll();

// ...
Product p = productRepository.findById(id).orElseThrow();
productRepository.zeroStockAll();

Product again = productRepository.findById(id).orElseThrow();
// SELECT 조차 나가지 않는다. 캐시의 p 가 그대로 돌아온다
System.out.println(again == p);        // true
System.out.println(again.getStock());  100 — DB 는 0 인데
after 캐시가 비었으므로 DB 를 다시 읽는다
@Modifying(clearAutomatically = true)
@Query("update Product p set p.stock = 0")
int zeroStockAll();

// ...
Product p = productRepository.findById(id).orElseThrow();
productRepository.zeroStockAll();   // 실행 후 컨텍스트가 비워진다

Product again = productRepository.findById(id).orElseThrow();
// SELECT 가 실제로 나간다
System.out.println(again == p);        // false — 다른 인스턴스
System.out.println(again.getStock());  0 — DB 의 진실

옵션 이름을 모르는 상태에서 "EntityManager를 clear하고 다시 조회하면 될 것 같다"고 도출한 처방이 정확히 이것이다. 손으로 쓰면 productRepository.zeroStockAll(); entityManager.clear();가 되고, clearAutomatically = true와 같은 일이다.

그럼 둘 다 켜면 끝인가 — 증상은 대부분 사라진다. 하지만 이걸 "안전장치"라고 부르면 안 된다

6. 사고 ② clearAutomatically가 안전장치가 아닌 이유

6-1. 이유 ① — "벌크 대상만"이 아니라 통째로 비운다

clear()는 "방금 벌크로 건드린 엔티티만" 비우는 기능이 아니다. 영속성 컨텍스트 전체를 비운다. 그 안에는 같은 트랜잭션에서 수정 중이던, 벌크와 아무 상관 없는 엔티티들도 들어 있다. 그것들의 변경분이 아직 flush되지 않았다면 그대로 증발한다. 커밋해도 UPDATE가 나가지 않는다.

비유 — 편지를 부치지 않고 책상을 쓸어버린 것

flush = "밀린 편지를 우체통에 넣는다", clear = "책상 위를 쓸어서 휴지통에 버린다". 순서를 지키면(먼저 부치고, 그다음 쓸기) 아무 문제가 없다. 그런데 부치지 않은 편지가 책상에 남아 있는 상태에서 쓸어버리면 — 그 편지는 어디에도 도착하지 않고, 아무도 그 사실을 알려주지 않는다.

clearAutomatically를 단독으로 쓰는 것이 정확히 이 상황이다
before clearAutomatically를 "안전장치"로 믿고 트랜잭션 한가운데서 벌크
@Modifying(clearAutomatically = true)   flushAutomatically 가 없다
@Query("update Ticket t set t.status = 'EXPIRED' where t.event.id = :eventId")
int expireTickets(@Param("eventId") Long eventId);

@Transactional
public void closeEvent(Long eventId) {
    Event event = eventRepository.findById(eventId).orElseThrow();
    event.setStatus(CLOSED);   ① 아직 flush 안 됨

    int n = ticketRepository.expireTickets(eventId);
    //   └ 벌크는 ticket 테이블만 건드린다 → event 의 변경분과 테이블이 겹치지 않는다
    //     → 하이버네이트의 자동 flush 도 발동하지 않는다
    //   └ 실행 후 clear() → ① 의 변경분이 통째로 폐기된다

    notificationService.notifyClosed(event);  // ② event 는 이제 준영속(detached)
}   // ③ 커밋 — 티켓은 만료됐는데 이벤트는 여전히 OPEN 이다
결과 — 3절의 덮어쓰기보다 더 조용한 사고 티켓 1만 장은 EXPIRED가 됐는데 이벤트만 OPEN으로 남는다. 예외는 없다. event.getStatus()는 메모리에서 여전히 CLOSED를 돌려주므로 디버깅 중에도 정상으로 보인다. DB만 틀려 있다.
여기서 flushAutomatically = true가 없다는 점이 결정적이다. 있었다면 clear 이전에 ①이 DB로 나가 살아남는다.
after 그나마 나은 형태 — 반드시 짝으로
@Modifying(flushAutomatically = true, clearAutomatically = true)
@Query("update Ticket t set t.status = 'EXPIRED' where t.event.id = :eventId")
int expireTickets(@Param("eventId") Long eventId);

6-2. 이유 ② — clear 이후 모든 참조가 준영속이 된다

clear()는 컨텍스트가 관리하던 엔티티를 전부 준영속(detached)으로 만든다. 준영속이란 "한때 영속성 컨텍스트가 관리했지만 지금은 떨어져 나온(detached) 상태"를 말한다. 자바 변수는 그대로 그 객체를 가리키고 있어서 겉보기에는 멀쩡하지만, 그 객체는 더 이상 컨텍스트와 연결돼 있지 않다. 그래서 두 기능이 함께 죽는다.

죽는 기능 ① 지연 로딩

아직 안 채운 연관을 나중에 DB에서 채워 넣는 기능. 컨텍스트가 살아서 붙들고 있어야 동작하므로 LazyInitializationException이 난다.

죽는 기능 ② 변경 감지

값이 바뀌면 커밋 때 UPDATE를 만들어 주는 기능. 준영속 엔티티는 추적 대상이 아니므로 setter를 호출해도 커밋 시 UPDATE가 나가지 않는다.

@Transactional
public void closeEvent(Long eventId) {
    Event event = eventRepository.findById(eventId).orElseThrow();

    ticketRepository.expireTickets(eventId);   // clearAutomatically = true

    for (Sponsor s : event.getSponsors()) {   LazyInitializationException
        ...
    }

    event.setStatus(CLOSED);   변경 감지 정지 — 커밋해도 UPDATE 없음
}

증상이 둘로 갈린다는 점이 고약하다. 초기화된 필드는 잘 읽히고, 초기화 안 된 LAZY 연관에서만 터진다. 그래서 "어떤 요청은 되고 어떤 요청은 예외"라는 형태로 나타난다. 그리고 clear 이후에 다시 영속 상태로 만들려면 재조회하거나 merge해야 하는데, merge는 또 다른 함정을 달고 온다.

6-3. 정리 — 옵션이 하는 일과, 원하지 않았는데 하는 일

clearAutomatically = true가 만들어 내는 다섯 가지 효과 — 원했던 것은 위의 둘뿐이다
효과원했던 것인가내용
벌크 이후의 조회가 DB를 다시 읽게 만든다원했음낡은 값 조회가 사라진다
dirty checking 덮어쓰기를 막는다원했음캐시가 비었으니 덮어쓸 엔티티도 없다
벌크와 무관한 엔티티의 미flush 변경분을 폐기한다원치 않았음커밋해도 UPDATE가 안 나간다 (6-1)
살아 있던 모든 참조를 준영속으로 만든다원치 않았음지연 로딩 실패, 변경 감지 정지 (6-2)
이후 조회가 전부 SELECT를 다시 날린다원치 않았음캐시를 비운 대가, 성능 비용

한 문장으로 — 그리고 이 문장이 다음 절을 부른다

clearAutomatically는 "지금 이 트랜잭션에서 영속성 컨텍스트에 남아 있는 것이 아무것도 없다"가 참일 때만 안전하다.

그런데 그게 참이라면 — 애초에 벌크를 그 자리에 둘 이유가 없다

7. 처방 — 옵션이 아니라 배치

원칙 한 문장 — 이 문항의 진짜 답

영속성 컨텍스트를 우회하는 연산과, 영속성 컨텍스트에 의존하는 연산을
같은 트랜잭션에 섞지 않는다
우회하는 연산 — DB를 본다
벌크 연산(@Modifying JPQL) · 네이티브 쿼리 · JdbcTemplate
의존하는 연산 — 1차 캐시를 본다
엔티티 수정(변경 감지) · 지연 로딩 · 재조회 · cascade

두 종류의 코드는 서로 다른 진실의 원천을 본다. 한 트랜잭션에 섞는 순간 "지금 어느 쪽이 진실인가"를 사람이 머릿속으로 추적해야 하고, 그 추적은 반드시 언젠가 실패한다. 옵션 두 개는 섞인 상태를 사후에 봉합하는 도구일 뿐이다.

7-1. 실행 형태 세 가지

형태 A — 벌크를 트랜잭션의 맨 끝(또는 맨 앞)에 둔다 기본 선택

before 벌크가 한가운데
@Transactional
public void closeEvent(Long eventId) {
    Event event = eventRepository.findById(eventId).orElseThrow();
    ticketRepository.expireTickets(eventId);  벌크
    event.setStatus(CLOSED);   이후에 엔티티를 만진다
    auditService.record(event);
}
after 엔티티 작업을 전부 끝낸 뒤 마지막에 벌크
@Transactional
public void closeEvent(Long eventId) {
    Event event = eventRepository.findById(eventId).orElseThrow();
    event.setStatus(CLOSED);
    auditService.record(event);

    entityManager.flush();   엔티티 변경분을 먼저 확정
    ticketRepository.expireTickets(eventId);  벌크는 맨 끝에서 한 번
}   // 벌크 이후 엔티티를 건드리는 코드가 없다 → clear 도 필요 없다

형태 B — 별도 트랜잭션으로 분리한다 (벌크 대상이 크거나 호출 지점이 여럿일 때)

@Service
public class TicketBulkService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)  자기만의 트랜잭션·컨텍스트
    public int expireTickets(Long eventId) {
        return ticketRepository.expireTickets(eventId);
    }
}

얻는 것

별도 트랜잭션은 자기만의 영속성 컨텍스트를 갖는다. 호출한 쪽 컨텍스트는 손대지 않으므로 6-1의 소실 사고가 원천적으로 불가능하다.

지불하는 것 — 원자성이 깨진다

바깥 트랜잭션이 롤백돼도 안쪽 벌크는 이미 커밋돼 있다. "벌크만 성공하고 나머지는 롤백"이 허용되는 경우에만 쓸 수 있다.

REQUIRES_NEW의 두 함정 ① 자기 자신 호출(self-invocation)에서는 동작하지 않는다. 같은 클래스 안에서 this.expireTickets(...)로 부르면 프록시를 거치지 않아 새 트랜잭션이 열리지 않는다 — 빈을 분리해야 한다.
② 바깥 트랜잭션의 커넥션을 붙든 채로 새 커넥션을 하나 더 쓴다. 호출이 잦으면 커넥션 풀 소모가 두 배가 된다는 점을 염두에 둔다.

형태 C — 트랜잭션 커밋 이후로 미룬다 (부수적인 정리 작업일 때)

@TransactionalEventListener(phase = AFTER_COMMIT)로 벌크를 커밋 이후에 실행하면, 그 시점엔 원래 컨텍스트가 이미 닫혀 있어 오염될 대상 자체가 없다. 단, 이것도 원자성 밖이므로 실패했을 때의 보정 경로를 반드시 설계해야 한다.

7-2. 어떤 걸 고를까

8. 벌크만의 문제가 아니다 — 그리고 증상 → 원인 역방향 인덱스

8-1. "영속성 컨텍스트를 우회한다"는 성질을 공유하는 것들

같은 성질을 가진 것들은 전부 같은 사고를 낸다. 그리고 벌크가 건너뛰는 것은 1차 캐시만이 아니다.

1차 캐시 · 2차 캐시
1차 캐시는 갱신되지 않고, 2차 캐시는 무효화되지도 않는다. 2차 캐시는 트랜잭션이 끝나도 애플리케이션 전역에 남으므로 불일치가 이후 요청들까지 오염시킨다. 가산점
JPA Auditing
@CreatedDate / @LastModifiedDate는 엔티티 리스너 기반이라 벌크에서는 조용히 기록되지 않는다. "벌크로 고친 행만 updated_at이 옛날 그대로" → JPQL에 set p.updatedAt = :now를 직접 써야 한다.
낙관적 락 @Version
벌크 UPDATE는 version 컬럼을 자동으로 올리지 않는다. set p.version = p.version + 1을 명시하지 않으면 다른 트랜잭션이 그 변경을 감지하지 못한다.
cascade · orphanRemoval
이것들도 영속성 컨텍스트의 기능이다. 벌크 DELETE는 자식 행을 알아서 지워주지 않는다. "부모를 벌크로 지웠더니 FK 제약 위반" 또는 "고아 행이 남았다"가 여기서 나온다.
네이티브 쿼리
벌크 연산과 완전히 동일하다. 변경 쿼리면 @Modifying이 여전히 필요하다. 게다가 하이버네이트는 네이티브 SQL 문자열을 해석하지 못해 어떤 테이블을 건드리는지 모르므로 자동 flush 판단이 JPQL과 다르게 동작한다.
JdbcTemplate
같은 트랜잭션·같은 커넥션을 공유하더라도 변경 사실을 컨텍스트는 모른다. 원인을 "캐시가 있어서"가 아니라 "컨텍스트를 우회한 변경이라서"로 말하는 것이 변별점이다.

벌크가 건너뛰는 다섯 — 일 · 감 · 버 · 연 · 이

일차 캐시감사(Auditing)버전(@Version)연쇄(cascade·orphanRemoval)이차 캐시
하나로 묶으면 — "JPA를 우회한 변경은 JPA가 모른다"
벌크 연산이 특별한 게 아니라, 컨텍스트를 거치지 않는 모든 경로가 같은 성질을 갖는다

8-2. 증상 → 원인 역방향 인덱스 — 이 문항의 채점 지점

원인에서 증상을 유도하는 건 원리를 알면 누구나 한다. 실무에서 필요한 건 증상에서 원인으로 거슬러 올라가는 것이다. 아래를 트리거로 외워두면 며칠이 십 분이 된다.

증상원인확인 방법처방
DB를 직접 조회하면 바뀌었는데 API 응답은 옛날 값벌크 후 1차 캐시 미갱신 (2절)같은 트랜잭션에서 재조회 시 SELECT가 안 나감벌크를 맨 끝으로 / 재조회가 필요하면 clearAutomatically
벌크 UPDATE를 분명히 실행했는데 결과가 사라졌다커밋 시 dirty checking의 전 컬럼 UPDATE가 덮어씀 (3절)SQL 로그에 벌크 UPDATE 뒤에 같은 행을 치는 UPDATE가 하나 더벌크 이후 그 엔티티를 건드리지 않기 / 재조회 후 수정
벌크의 WHERE에 방금 바꾼 값이 안 걸린다 (영향 행 수 0)실행 전 flush 누락 (5-1)반환된 int가 0, DB엔 조건 만족 행이 있음flushAutomatically = true 또는 em.flush() 선행
벌크 실행 후 갑자기 LazyInitializationExceptionclearAutomatically가 참조를 준영속화 (6-2)예외가 벌크 호출 이후 줄에서만 발생벌크를 맨 끝으로 / clear 이후 필요한 엔티티는 재조회
벌크와 무관한 엔티티의 수정이 통째로 사라짐clearAutomatically가 미flush 변경분 폐기 (6-1)커밋 로그에 그 엔티티의 UPDATE가 아예 없음flushAutomatically를 짝으로 켜기 / 트랜잭션 분리
벌크 이후 setter를 호출해도 UPDATE가 안 나감clear로 준영속화되어 변경 감지 정지 (6-2)커밋 시 해당 UPDATE 부재재조회 후 수정
벌크로 고친 행만 updated_at이 안 바뀜Auditing은 엔티티 리스너 기반, 벌크는 우회 (8-1)벌크 대상 행만 타임스탬프가 옛날JPQL에 set updatedAt = :now 직접 명시
벌크로 바꿨는데 낙관적 락이 충돌을 못 잡음벌크가 version을 올리지 않음 (8-1)version 컬럼이 그대로JPQL에 set version = version + 1 명시
벌크 DELETE 후 FK 제약 위반 / 고아 행cascade·orphanRemoval은 컨텍스트 기능 (8-1)자식 테이블에 행이 남아 있음자식부터 벌크 삭제 / DB의 ON DELETE 제약 활용
재배포 전까지 옛날 값이 계속 나옴2차 캐시가 무효화되지 않음 (8-1)인스턴스를 재시작하면 정상벌크 후 해당 캐시 영역 명시적 무효화
테스트는 통과하는데 운영에서만 터짐(또는 반대)@Transactional 테스트의 1차 캐시 공유 (9절)테스트에 em.clear()를 넣으면 재현됨검증을 새 트랜잭션·새 컨텍스트에서

세 개의 대표 트리거만 외워도 대부분 잡힌다

"DB는 바뀌었는데 조회는 옛날 값"
→ 벌크가 1차 캐시를 우회했다
"벌크 결과가 조용히 사라졌다"
→ dirty checking이 전 컬럼 UPDATE로 덮었다
"벌크와 상관없는 수정이 사라졌다"
→ clearAutomatically가 미flush 변경분을 버렸다

9. 테스트로 고정하기 — 예외가 안 나는 사고를 막는 유일한 방법

이 문항의 사고는 예외가 나지 않는다. 예외가 안 나는 사고를 막는 방법은 하나뿐이다 — 단정(assertion)으로 고정하는 것. 그런데 평소 쓰던 테스트 골격을 그대로 쓰면 단정 자체가 무력해진다.

before 이 테스트는 사고를 절대 잡지 못한다
@SpringBootTest
@Transactional   테스트 메서드가 트랜잭션을 연다
class ProductServiceTest {

    @Test
    void 벌크_결과가_유지된다() {
        Product p = productRepository.save(new Product("구상품", 100));

        productService.closeOutSale(p.getId());   // 내부에서 벌크 + setName

        Product found = productRepository.findById(p.getId()).orElseThrow();
        assertThat(found.getStock()).isZero();   무엇을 검증한 걸까?
    }
}
① 컨텍스트를 공유한다
테스트가 연 트랜잭션 안에서 서비스가 실행되므로(@Transactional 기본은 REQUIRED), findById는 1차 캐시에서 나온다. DB를 읽지 않는다.
② 커밋이 일어나지 않는다
테스트 트랜잭션은 끝에서 롤백되므로 dirty checking으로 인한 덮어쓰기 UPDATE가 애초에 발생하지 않는다. 잡으려는 사고가 실행조차 되지 않는 것이다.
③ 그래서 무의미하다
이 단정은 통과할 수도, 실패할 수도 있는데 어느 쪽이든 우리가 알고 싶은 것과 무관하다.

9-1. 처방 ① — 쓰는 트랜잭션과 읽는 트랜잭션을 분리한다

after 테스트에 @Transactional을 붙이지 않고, 검증을 별도 트랜잭션에서

class ProductServiceTest {

9-2. 처방 ② — @Transactional을 유지해야 한다면 불일치 자체를 문서화한다

@Test
@Transactional
void 벌크_직후_DB와_1차_캐시는_다르다() {
    Product p = productRepository.save(new Product("구상품", 100));
    entityManager.flush();
    entityManager.clear();   // 저장 직후 캐시를 비워 "새로 조회한 상태"를 만든다

    Product loaded = productRepository.findById(p.getId()).orElseThrow();  // stock = 100
    productRepository.zeroStockAll();   // 벌크

    assertThat(loaded.getStock()).isEqualTo(100);  ① 1차 캐시는 옛 값 그대로

    entityManager.clear();   // ② 캐시를 비우고 다시 읽으면
    Product reloaded = productRepository.findById(p.getId()).orElseThrow();
    assertThat(reloaded.getStock()).isZero();       DB 는 이미 0
}

이 테스트는 "불일치가 실제로 존재한다"는 사실 자체를 문서화한다. 팀에 이 동작을 설명하는 데 문장 열 줄보다 낫다. 다만 주의: 이 방식으로는 3절의 덮어쓰기(커밋 시점에 발생)를 잡을 수 없다. 롤백되는 트랜잭션에서는 커밋 플러시가 일어나지 않기 때문이다.

9-3. 처방 ③ — 값이 아니라 "쿼리 개수"를 단정한다

덮어쓰기의 본질은 "내가 기대하지 않은 UPDATE가 커밋 시점에 하나 더 나갔다"이다. 그러면 값이 아니라 쿼리 개수를 단정하는 편이 원인에 더 가깝다.

@Test
void 벌크_이후_커밋에서_추가_UPDATE가_나가지_않는다() {
    SQLStatementCountValidator.reset();
    productService.closeOutSale(id);                 // 서비스가 커밋까지 수행

    SQLStatementCountValidator.assertSelectCount(1); // 조회 1
    SQLStatementCountValidator.assertUpdateCount(1); 덮어쓰기가 있으면 2 → 실패
}
이 도구 상자는 N+1 회귀 방지와 완전히 동일하다 가산점 SQLStatementCountValidator(datasource-proxy 계열)나 하이버네이트의 Statistics로 같은 단정을 만들 수 있다. 한 번 깔아두면 "조용한 추가 쿼리" 부류의 사고 전체를 같은 방식으로 막을 수 있다.

테스트가 못 잡는 부분은 규칙으로 막는다 — 코드 리뷰 규칙 셋 가산점

1
@Modifying 메서드는 int를 반환한다 — 영향 행 수를 버리지 않기 위해서(1-3).
2
clearAutomatically = true는 flushAutomatically = true와 짝으로만 쓴다 — 단독 사용은 6-1의 소실 사고를 부른다.
3
@Modifying 호출 다음 줄부터는 이전에 로드한 엔티티를 사용하지 않는다 — 지킬 수 없다면 그 벌크는 자리를 잘못 잡은 것이다(7절).

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

벌크 연산의 실행 타이밍은?
쓰기 지연 대상이 아니다. 실행 직전 flush 선행 → 즉시 DB(커밋을 안 기다림) → 1차 캐시는 그대로.
두 방향의 사고는?
① 낡은 값 조회(재조회해도 SELECT조차 안 나감) ② 덮어쓰기(전 컬럼 UPDATE가 벌크 결과를 되돌림).
두 옵션의 방향은?
"전에 넣고, 후에 버린다" — flush는 실행 前 메모리 → DB(보존), clear는 실행 後 메모리 → 폐기(소실).
clearAutomatically의 대가 둘?
① 미flush 변경분 소실(통째로 비우므로) ② 전부 준영속(지연 로딩 실패 + 변경 감지 정지).
왜 name만 바꿨는데 stock이?
스냅샷은 로드 시점 고정 + UPDATE는 전 컬럼이 기본. 그래서 stock 자리에 캐시의 100이 실린다.
진짜 처방 한 문장?
우회하는 연산과 의존하는 연산을 같은 트랜잭션에 섞지 않는다. 벌크는 맨 끝(또는 맨 앞), 아니면 별도 트랜잭션.
벌크가 건너뛰는 다섯?
일·감·버·연·이 — 일차 캐시 / 감사(Auditing) / 버전(@Version) / 연쇄(cascade) / 이차 캐시.
@Modifying이 하는 일 셋?
executeUpdate()로 전환 / int 반환 허용(영향 행 수) / 두 옵션 제공.
@DynamicUpdate는 답인가?
아니다. 그 덮어쓰기 하나만 가린다. 읽기 오염은 그대로이고, 낡은 값으로 stock을 계산하면 다시 터진다.
자동 flush를 믿어도 되나?
조건부다 — 테이블이 겹칠 때만. readOnly = true면 MANUAL이라 아예 꺼진다. 계약이 아니라 휴리스틱.
테스트로 어떻게 고정하나?
쓰기·읽기 트랜잭션 분리(TransactionTemplate) + 쿼리 수 단정(assertUpdateCount(1)).
한 줄로 묶는 문장?
"JPA를 우회한 변경은 JPA가 모른다." 벌크·네이티브·JdbcTemplate 전부 같은 성질.

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

@Modifying을 빼면 정확히 무슨 일이 일어나나요? 필수힌트: 예외 클래스명이 아니라 "어느 실행 경로로 들어가는가"로 답한다

Spring Data JPA는 JPQL 문자열을 해석해 조회/변경을 판단하지 않고 메서드 단위로 실행 방식을 미리 정해두는데, 기본이 조회다. 그래서 @Modifying이 없으면 UPDATE 문을 들고 getResultList()를 호출하고, 하이버네이트가 "SELECT가 아닌데 결과 목록을 요구한다"며 거부한다.

예외 타입은 버전에 따라 다르다 — 하이버네이트 5는 QueryExecutionRequestException: Not supported for DML operations, 하이버네이트 6은 IllegalSelectQueryException: Expecting a selection query, but found ... 계열이고, Spring 계층에서는 대개 InvalidDataAccessApiUsageException으로 변환돼 올라온다.

정확한 클래스명보다 "조회 실행 경로로 들어가 실패한다"는 메커니즘을 말하는 게 안전하다

그리고 @Modifying을 붙여도 쓰기 트랜잭션이 없으면 TransactionRequiredException이 난다 — SimpleJpaRepository가 readOnly = true를 기본으로 갖기 때문이다.

clearAutomatically = true만 붙이면 안 되나요? 시니어 변별힌트: "된다/안 된다"가 아니라 "증상이 어디로 옮겨가는가"로 답한다

증상은 사라지지만 더 조용한 사고로 옮겨간다. clear()는 벌크 대상만 골라 비우는 게 아니라 영속성 컨텍스트 전체를 비운다. 같은 트랜잭션에서 수정 중이던 다른 엔티티의 변경분이 아직 flush되지 않았다면 그대로 증발하고, 커밋해도 UPDATE가 나가지 않는다.

특히 그 엔티티가 벌크와 다른 테이블이면 하이버네이트의 자동 flush도 발동하지 않아 확실히 사라진다. 덤으로 살아 있던 모든 참조가 준영속이 되어 지연 로딩은 LazyInitializationException, 이후의 setter는 변경 감지 정지다.

그래서 flushAutomatically와 반드시 짝으로, 더 근본적으로는 벌크를 맨 끝으로 옮기거나 별도 트랜잭션으로 분리해
애초에 옵션이 필요 없는 구조로 만드는 게 정답이다
flushAutomatically는 왜 필요한가요? 어차피 하이버네이트가 자동으로 flush하지 않나요? 시니어 변별힌트: "해준다"와 "보장한다"는 다르다. 조건을 말할 수 있는가

대개는 해준다. 하지만 조건부이고, 그 조건은 계약이 아니라 최적화 휴리스틱이다.

하이버네이트는 기본 flush 모드(AUTO)에서 쿼리가 건드리는 테이블과 아직 반영되지 않은 변경분의 테이블이 겹칠 때만 flush한다(query space). 겹치지 않으면 건너뛴다. 게다가 @Transactional(readOnly = true)는 세션을 MANUAL로 두어 자동 flush 자체를 끈다. 즉 "하이버네이트가 알아서 해준다"는 설정 하나로 무너지는 가정이다.

flushAutomatically = true는 Spring Data JPA가 실행 직전에 flush를 명시적으로 수행하게 만들어 이 의존을 없애고, 동시에 "이 벌크는 최신 상태 위에서 돈다"는 의도를 코드에 드러낸다.

정확도 주의자동 flush의 세부 발동 조건은 하이버네이트 버전과 부트스트랩 방식(JPA EntityManager vs 네이티브 Session)에 따라 차이가 있다. 면접에서는 "조건부다 / 그래서 명시하는 게 안전하다"까지만 말하는 편이 안전하다.
벌크 UPDATE 결과가 왜 dirty checking에 덮어쓰이나요? name만 바꿨는데요. 필수힌트: 겹쳐야 하는 사실이 둘이다 — 하나는 스냅샷, 하나는 SQL 생성 방식

① 스냅샷은 로드 시점 값으로 고정된다 — 벌크가 DB를 바꿔도 스냅샷은 갱신되지 않는다. 스냅샷은 DB를 다시 읽어 만드는 것이 아니기 때문이다.

② 하이버네이트의 UPDATE는 기본적으로 전 컬럼을 포함한다 — SQL 문자열을 미리 만들어 재사용하고 DB의 실행 계획 캐시를 살리기 위해서다.

그래서 name이 바뀌었다는 이유로 UPDATE가 만들어지면 그 안의 stock 자리에는 1차 캐시의 값(100)이 들어가고, 벌크가 만든 0을 덮는다. 버그가 아니라 정상 동작이며, 하이버네이트는 자기 모르게 DB가 바뀐 사실을 알 방법이 없다.

@DynamicUpdate를 붙이면 이 특정 덮어쓰기는 피하지만 불일치 자체와 읽기 오염은 그대로이고, 낡은 값을 근거로 stock을 계산해 넣는 순간 다시 터진다.

벌크 연산은 왜 쓰기 지연 큐에 쌓였다가 커밋 때 나가지 않나요?힌트: 큐에 담는 것이 "무엇"인지, 그리고 호출자가 무엇을 즉시 돌려받는지 생각한다

이유가 셋이다.

① 쓰기 지연 큐는 "엔티티 단위 변경"을 모으는 곳이다. 영속성 컨텍스트가 추적하는 것은 자기가 관리하는 엔티티의 상태 변화이고, 거기서 INSERT/UPDATE/DELETE를 만들어 낸다. 벌크 JPQL은 어떤 엔티티가 대상인지 실행 전에는 알 수 없다 — 대상 행을 정하는 것은 DB의 WHERE 평가다.

② 호출자가 그 자리에서 결과를 받아야 한다. int 반환값, 즉 영향받은 행 수는 DB가 실행해 봐야 나오는 값이다. 미뤄두면 돌려줄 수가 없다.

③ 미루면 순서가 뒤집힌다. 코드상 벌크 이후에 놓인 엔티티 변경분이 먼저 DB에 도착하는 상황이 생긴다. 그래서 하이버네이트는 반대로 간다 — 실행 직전에 밀린 변경분을 flush해 순서를 맞춘 다음 벌크를 내보낸다.

즉 벌크 연산은 지연의 예외가 아니라 애초에 지연 대상이 될 수 없는 종류의 연산이다
벌크 DELETE도 같은 문제가 있나요? 함정힌트: "같다"에서 멈추지 말고, DELETE 쪽이 더 고약한 지점을 하나 든다

있고, 몇 가지는 더 고약하다.

① 유령 엔티티가 남는다. 삭제된 행의 엔티티가 1차 캐시에 그대로 살아 있어, 같은 트랜잭션에서 재조회하면 이미 없는 행이 멀쩡히 돌아온다(SELECT조차 안 나가므로). 그 값으로 응답을 만들면 지워진 데이터를 반환하게 된다.

② 그 엔티티를 수정해도 반영될 곳이 없다. 커밋 시 UPDATE가 만들어져도 대상 행이 이미 없으므로 그 변경은 어디에도 남지 않는다.

③ cascade·orphanRemoval이 동작하지 않는다. 이것들은 영속성 컨텍스트의 기능이므로 자식 행이 그대로 남고, 그 결과 FK 제약 위반이나 고아 행이 생긴다. 그래서 벌크 DELETE는 자식부터 지우거나 DB의 ON DELETE 제약을 함께 설계해야 한다.

UPDATE의 사고는 "값이 되돌아간다", DELETE의 사고는 "없는 걸 있다고 한다"
clear() 대신 refresh()를 쓰면 되지 않나요? 가산점힌트: 범위가 좁아지는 대신 무엇을 알고 있어야 하고, 무엇을 잃는가

국소 처방으로는 성립한다. em.refresh(entity)는 그 엔티티 하나만 DB에서 다시 읽어 덮어쓰므로, 컨텍스트를 통째로 비우지 않는다 — 6-1의 "다른 엔티티 변경분 소실"을 피할 수 있다는 것이 장점이다.

다만 대가가 셋이다.

  • 대상을 하나하나 알고 있어야 한다. 벌크가 건드린 행이 1만 건이면 현실적이지 않다. 벌크의 본질은 "대상을 개별로 다루지 않는 것"인데 refresh는 개별로 다루는 방식이다.
  • 그 엔티티에 대해 아직 flush되지 않은 내 변경분은 DB 값으로 덮여 사라진다. 범위가 좁을 뿐 "버린다"는 성질은 같다.
  • 대상마다 SELECT가 추가로 나간다.

그래서 "벌크 뒤에 반드시 다시 봐야 하는 엔티티가 한두 개로 명확할 때"의 선택지이고, 여전히 1순위는 배치를 바꾸는 것이다.

그럼 벌크 연산은 아예 쓰지 말아야 하나요?힌트: 질문의 전제를 교정한다 — 문제는 벌크가 아니다

아니다. 대량 갱신에서 벌크 연산은 대체 불가능하다. 1만 건을 한 건씩 처리하면 엔티티 1만 개를 메모리에 올리고(OOM), 스냅샷을 1만 개 만들고, UPDATE를 1만 번 날린다. 벌크는 이걸 SQL 한 문장으로 끝낸다.

문제는 벌크 자체가 아니라 벌크를 영속성 컨텍스트에 의존하는 코드와 같은 트랜잭션에 섞는 것이다.

그래서 규칙은 "쓰지 마라"가 아니라 "섞지 마라"
벌크는 트랜잭션의 맨 끝(또는 맨 앞)이나 별도 트랜잭션에 두고, 그 뒤로는 기존 엔티티 참조를 쓰지 않는다
REQUIRES_NEW로 분리하면 다 해결되는 것 아닌가요? 시니어 변별힌트: 얻는 것 하나, 잃는 것 하나, 그리고 안 먹히는 호출 방식 하나

오염 문제는 확실히 해결된다. 새 트랜잭션은 자기만의 영속성 컨텍스트를 갖기 때문에 호출한 쪽 캐시를 건드리지 않는다.

그러나 원자성이 깨진다. 바깥이 롤백돼도 안쪽 벌크는 이미 커밋돼 있다. 재고 차감·정산처럼 "함께 성공하거나 함께 실패해야 하는" 작업이면 쓸 수 없다. 쓸 수 있는 것은 만료 처리·통계 갱신처럼 따로 커밋돼도 되는 작업이다.

함정 둘: ① 자기 자신 호출에서는 동작하지 않는다 — 같은 클래스의 this.method()는 프록시를 거치지 않아 새 트랜잭션이 열리지 않는다. 빈을 분리해야 한다. ② 바깥 트랜잭션의 커넥션을 붙든 채 새 커넥션을 하나 더 잡으므로 커넥션 풀 소모가 두 배다.

그래서 순서는 형태 A(배치 이동) → 안 되면 형태 B/C(분리) → 그것도 안 되면 옵션 짝으로다.

벌크 이후에 같은 엔티티를 다시 조회했는데 SELECT가 안 나갑니다. 버그인가요?힌트: 이건 JPA가 지키기로 한 약속이다. 이름이 있다

버그가 아니라 보장이다. 1차 캐시는 "같은 트랜잭션 안에서 같은 식별자는 같은 객체"를 보장한다(동일성 보장). 그래서 findById(1L)을 다시 호출해도 DB로 나가지 않고 캐시에 있던 그 인스턴스를 그대로 돌려준다 — again == p가 true다.

이 보장이 있기에 "한 트랜잭션 안에서 같은 데이터를 두 경로로 조회했을 때 한쪽에서 바꾼 값이 다른 쪽에도 보인다"는 편의가 성립한다. 그런데 벌크는 그 캐시를 갱신하지 않으므로, 같은 보장이 그대로 "낡은 값을 계속 돌려주는" 사고가 된다.

편의와 사고가 같은 뿌리에서 나온다 — 그래서 "다시 조회하면 되겠지"가 통하지 않는다
이 사고를 배포 전에 잡으려면 어떻게 하나요? 가산점힌트: 평소 테스트 골격이 왜 무력한지부터 말한다

예외가 안 나는 사고이므로 단정으로 고정해야 한다. 다만 @Transactional을 붙인 테스트는 테스트와 서비스가 같은 영속성 컨텍스트를 공유하고 끝에서 롤백되어 커밋 플러시가 일어나지 않으므로, 잡으려는 사고가 실행조차 되지 않는다.

1
쓰는 트랜잭션과 읽는 트랜잭션을 분리한다(TransactionTemplate) — 검증이 1차 캐시가 아니라 DB를 보게 만든다.
2
값 단정에 더해 assertUpdateCount(1) 같은 쿼리 수 단정으로 "커밋 시점의 유령 UPDATE 0건"을 고정한다.
3
테스트로 못 막는 부분은 리뷰 규칙으로 — @Modifying은 int 반환, clearAutomatically는 flushAutomatically와 짝으로, 벌크 호출 이후에는 이전 엔티티 참조 금지.

같은 도구 상자가 N+1 회귀 방지의 쿼리 수 단정과 정확히 동일하다는 점을 덧붙이면 좋다.

네이티브 쿼리도 같은 문제가 있나요? 가산점힌트: 원인이 "벌크"에 있는지 "우회"에 있는지 짚는다

있다. 원인이 벌크가 아니라 "영속성 컨텍스트를 우회한다"는 성질에 있기 때문이다. 네이티브 변경 쿼리도 @Modifying이 필요하고, 1차 캐시를 갱신하지 않으며, 덮어쓰기도 똑같이 난다.

게다가 하이버네이트는 네이티브 SQL 문자열을 해석하지 못해 어떤 테이블을 건드리는지 모르므로 자동 flush 판단이 JPQL과 다르게 동작한다.

같은 이유로 JPA Auditing이 기록되지 않고(리스너 기반), @Version이 올라가지 않고, cascade·orphanRemoval이 동작하지 않으며, 2차 캐시도 무효화되지 않는다 — 2차 캐시는 트랜잭션이 끝나도 남으므로 불일치가 이후 요청들까지 오염시킨다는 점에서 더 위험하다.

한 문장으로 묶으면 — "JPA를 우회한 변경은 JPA가 모른다"
한 줄 요약
벌크 연산은 영속성 컨텍스트를 우회해 즉시 DB로 나간다 — 쓰기 지연 대상이 아니라 오히려 실행 직전 flush가 선행되고 그 자리에서 UPDATE가 실행되며, 1차 캐시는 갱신되지 않아 DB와 메모리가 어긋난 채로 트랜잭션이 이어진다. 그 불일치는 낡은 값 조회와, 그 엔티티를 조금만 건드려도 전 컬럼 UPDATE가 벌크 결과를 조용히 덮어쓰는 사고로 터진다. @Modifying의 두 옵션은 방향이 반대여서 flushAutomatically는 실행 전 반영, clearAutomatically는 실행 후 폐기이고, clearAutomatically는 컨텍스트를 통째로 비워 다른 엔티티의 미flush 변경분까지 소실시키므로 안전장치가 아니다. 그래서 진짜 처방은 옵션이 아니라 배치 — 영속성 컨텍스트를 우회하는 연산과 그것에 의존하는 연산을 같은 트랜잭션에 섞지 않는다. 그리고 이 사고는 예외를 던지지 않으므로, 트랜잭션을 분리한 테스트와 쿼리 수 단정으로 고정하기 전까지는 언제든 되살아난다.
