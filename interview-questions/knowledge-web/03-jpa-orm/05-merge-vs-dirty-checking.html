merge vs dirty checking
"계산해서 고치기"와 "모르니까 전부 덮기"

면접 질문: "merge와 dirty checking의 차이는?"

핵심 관전 포인트 — 변경 감지(dirty checking)는 무엇이 바뀌었는지 스냅샷과 비교해 계산한다. merge는 무엇이 바뀌었는지 모르니 넘어온 객체의 모든 필드를 덮어쓴다. merge도 결국 변경 감지를 타지만 덮어쓰기가 끝난 상태로 타기 때문에, 채우지 않은 필드의 null까지 "변경"으로 잡혀 UPDATE에 실려 나간다. 그래서 new Member()에 id와 두 필드만 채워 save()하면 예외 없이, 로그도 정상인 채로 나머지 컬럼이 전부 null이 된다. 이 사고의 방아쇠는 Spring Data의 save()가 id 유무로 persist와 merge로 갈린다는 점이다 — id가 있으면 "중복 에러"가 아니라 조용한 UPDATE다. 처방은 하나뿐이다: 조회해서 영속 상태로 만든 뒤 필요한 필드만 바꾼다. merge가 정당한 자리는 값을 덮어쓰는 것이 곧 요구사항인 재부착(reattach) 뿐이고, 그조차 실무에서는 거의 없다.
  • 1
    차이는 "기준선의 유무" 하나로 갈린다 — 변경 감지는 조회 시점의 스냅샷이라는 기준선이 있어 무엇이 바뀌었는지 계산해 그것만 고치고, merge는 넘어온 객체가 언제 어디서 만들어졌는지 알 수 없어 기준선이 없으므로 전 필드를 덮는다.
  • 2
    그래서 안 건드린 필드가 null로 유실된다 — merge도 결국 변경 감지를 타지만 덮어쓰기가 끝난 뒤에 타므로, 변경 감지는 그 null을 정당한 변경으로 인식한다. 변경 감지가 잘못된 게 아니라 입력이 이미 오염된 것이다. 예외도 경고도 나지 않는다.
  • 3
    방아쇠는 save()이고, 처방은 하나다 — Spring Data의 save()는 id 유무로 persist와 merge로 갈리는 분기문이라 id를 채워 넘기면 조용한 UPDATE가 된다. 조회해서 영속 상태로 만든 뒤 필요한 필드만 바꾸고, 그 범위를 도메인 메서드로 고정해 컴파일러가 지키게 한다.

0. 질문 + 출제 의도

질문: "merge와 dirty checking의 차이는?"

출제 의도: merge의 오해(detached 엔티티 전체 덮어쓰기)는 "안 바꾼 필드가 null로 덮이는" 데이터 유실 사고를 만든다. 미묘하지만 사고 유형이 명확한 지식이다.

함정 — 이 질문은 "정답 코드를 쓰는가"를 묻지 않는다 대부분의 개발자는 관례상 "조회해서 setter로 바꾼다"를 이미 쓰고 있다. 묻는 것은 왜 그게 옳은지 아는가다. 이유를 모른 채 관례를 따르는 사람은 DTO를 엔티티로 변환하는 코드를 작성하는 순간, 또는 팀에 들어온 후배의 save() 코드를 리뷰하는 순간에 사고를 통과시킨다.
이 페이지가 겨냥하는 약점 세 가지 ① "merge는 전부 덮는다"를 외우기만 하고 이유를 못 대는 것 → 1·2절에서 스냅샷이라는 기준선을 세우고, 3절에서 기준선이 없으면 왜 덮을 수밖에 없는지를 잇는다.
② merge를 부른 적이 없다고 안심하는 것 → 4절에서 save()의 분기 구조와 isNew()의 판정 기준을 열어 내가 부르지 않아도 불린다는 사실을 못 박는다.
③ 엉뚱한 처방을 내리는 것(@DynamicUpdate를 켜면 되나요) → 2-3절에서 "SQL에 컬럼이 실린다"와 "값이 바뀐다"를 미리 갈라 두고, 5절에서 그 구분으로 오해를 정면으로 푼다.

1. 상태 넷 — 지금 이 객체는 어디에 있는가

merge를 이해하려면 엔티티가 지금 어느 상태에 있는지부터 구분할 수 있어야 한다. 상태는 넷이고, 상태를 바꾸는 것은 특정 메서드 호출이거나 트랜잭션의 끝이다.

1-1. 네 상태의 정의 — 그리고 "객체를 봐도 알 수 없다"

상태뜻특징
비영속 (transient/new)방금 new로 만들었고 영속성 컨텍스트가 모른다id가 없다(보통)
영속 (managed)영속성 컨텍스트가 추적 중이다필드를 바꾸면 flush 때 UPDATE가 나간다
준영속 (detached)한때 영속이었거나 id는 있지만, 지금은 추적 대상이 아니다필드를 바꿔도 아무 일도 일어나지 않는다
삭제 (removed)삭제 예약된 상태flush 시점에 DELETE가 나간다

영속성 컨텍스트란 트랜잭션 동안 엔티티를 담아 추적하는 메모리 공간이다. 여기에 들어 있는 동안만 "내가 이 객체를 바꾸면 DB에 반영된다"가 성립한다. flush는 그 공간에 쌓인 변경을 SQL로 만들어 DB에 내보내는 시점이고, 보통 커밋 직전에 자동으로 일어난다.

이 주제가 헷갈리는 근본 이유 — 상태는 객체 안에 적혀 있지 않다 영속과 준영속의 차이가 "객체 자체"에는 없다. 같은 클래스, 같은 필드값을 가진 객체 두 개가 있을 때 하나는 영속이고 하나는 준영속일 수 있다. 차이는 영속성 컨텍스트가 그 인스턴스를 자기 1차 캐시에 담고 있느냐뿐이다. 객체를 아무리 들여다봐도 자기가 어느 상태인지 알 수 없다 — 그래서 코드만 읽어서는 "이건 반영되겠지"를 눈으로 판단할 수 없고, 인스턴스가 어디서 왔는지를 거슬러 올라가야 한다.

1-2. 준영속은 왜 생기는가 — 이 사고의 진짜 출발점

"준영속이 문제의 온상"이라는 말을 하기 전에, 준영속 상태가 왜 애초에 생기는지를 먼저 봐야 한다. 경로가 셋이다.

① 트랜잭션이 끝나서
가장 흔하다. Spring에서는 트랜잭션 하나가 컨텍스트 하나에 대응하므로 @Transactional 메서드가 끝나면 그 안의 엔티티가 전부 준영속이 된다. 서비스에서 리턴해 컨트롤러가 받은 엔티티는 이미 준영속이라, 거기서 필드를 바꿔도 아무 일도 없다.
② 명시적으로 떼어내서
em.detach(entity)는 그 하나를, em.clear()는 전부를 준영속으로 만든다. 벌크 연산 뒤에 clear()를 부르라고 하는 것이 이 경우다.
③ 컨텍스트를 거친 적이 없어서
이 문서가 다루는 사고의 경로다. 컨트롤러에서 요청 DTO를 받아 new Member()로 만들고 id를 채워 넣으면, 비영속처럼 보이지만 JPA 입장에서는 "id가 있는 낯선 객체"다.
? 이 객체는 무엇인가
Member member = new Member();   // 방금 new 했으니 비영속처럼 보이는데,
member.setId(1L);               // id가 있으니 DB에 이미 존재하는 행을 가리킨다.
member.setName("홍길동");
// JPA는 이 객체를 추적한 적이 없다.
// "1번 회원"을 뜻하지만 컨텍스트와 연결돼 있지 않다 → 준영속에 준하는 취급.
세 경로 모두 결론은 같다 — DB에 반영하려면 어떻게든 영속 상태와 연결해야 하고, 그 연결 작업이 바로 merge다

2. 변경 감지 — "무엇이 바뀌었는지" 계산할 수 있는 이유

2-1. 정상 경로 — save()가 없는 수정 코드

good 영속 상태 엔티티를 고치는 정상 경로
@Transactional
public void changeContact(Long id, String name, String phone) {
    Member member = memberRepository.findById(id).orElseThrow();  // ① SELECT → 영속 상태
    member.setName(name);                                          // ② 필드만 변경
    member.setPhone(phone);
    // ③ save() 호출 없음 — 커밋 시점에 flush가 알아서 UPDATE를 만든다
}
1
findById가 DB에서 읽어오면서 그 시점의 필드값 복사본(스냅샷)을 따로 보관한다.
2
setName/setPhone은 엔티티 인스턴스 자체를 바꾼다. 스냅샷은 그대로 남는다.
3
커밋 직전 flush에서 인스턴스와 스냅샷을 필드별로 비교해 달라진 것을 찾아낸다.
4
달라진 게 있으면 UPDATE를 만든다.

핵심은 3번이다. JPA는 "무엇이 바뀌었는지"를 알고 있다 — 정확히는 계산해서 알아낸다. 스냅샷이라는 기준선이 있기 때문에 가능한 일이다.

2-2. 기준선이 있으면 이렇게 판정된다

2-3. 미리 짚어둘 것 — UPDATE 문에는 원래 "전 컬럼"이 들어간다

여기서 오해가 하나 생기기 쉬우니 미리 정리한다. 기본 설정에서 Hibernate가 만드는 UPDATE 문의 SET 절에는 변경된 컬럼만이 아니라 전 컬럼이 들어간다.

-- name, phone만 바꿨는데도 SET 절에는 전 컬럼이 나열된다
update member set name=?, phone=?, email=?, address=?, grade=?, point=?, ... where id=?

왜 이렇게 하는가. UPDATE 문의 모양을 엔티티마다 하나로 고정해 두면 매번 SQL 문자열을 다시 만들 필요가 없고, DB 쪽의 실행 계획 캐시에도 유리하기 때문이다.

그렇다면 손대지 않은 컬럼은 어떻게 되는가. 스냅샷과 같은 값, 즉 원래 그 컬럼에 있던 값이 그대로 실린다. 그러므로 결과는 바뀌지 않는다. email=?가 SQL에 있어도 그 자리에 들어가는 값은 DB에 원래 있던 a@x.com이다.

이 구분을 꼭 붙잡아 둔다 — 5-2에서 @DynamicUpdate 오해를 푸는 열쇠다

"SQL에 컬럼이 실린다"와 "그 컬럼의 값이 바뀐다"는 완전히 다른 문제다

3. merge — 무엇이 바뀌었는지 모르니 전부 덮는다

3-1. 동작 다섯 단계

given 준영속 객체를 넘겼을 때
Member detached = new Member();
detached.setId(1L);
detached.setName("홍길동");
detached.setPhone("010-1111-2222");

Member managed = em.merge(detached);
1
id로 1차 캐시를 찾는다. 없으면 DB에서 SELECT한다. 즉 merge는 항상 조회가 선행된다.
2
DB에도 행이 없으면 새 엔티티를 만들어 INSERT 경로로 간다(flush 시점에 INSERT). merge는 "수정"만이 아니라 "없으면 삽입"까지 한다는 뜻이다.
3
찾아온 영속 엔티티에 넘어온 객체의 모든 필드를 복사한다. 여기가 전부다.
4
그 영속 엔티티를 반환한다. 넘긴 detached는 끝까지 준영속으로 남는다.
5
flush 시점에 변경 감지가 돌아 UPDATE를 만든다.
3단계에 주목 — merge에게는 "의도"를 담을 자리가 없다 merge는 넘어온 객체의 어느 필드가 "사용자가 의도적으로 바꾼 값"이고 어느 필드가 "그냥 안 채운 값"인지 구분할 수단이 없다. 넘어온 것은 자바 객체 하나이고, 거기에는 "이 필드는 건드리지 마세요"라는 표시를 담을 자리가 없다. 그래서 전부 덮는다.
2절의 변경 감지에는 스냅샷이라는 기준선이 있어서 무엇이 바뀌었는지 계산할 수 있었다. merge에게는 그 기준선이 없다 — 넘어온 객체는 언제 어디서 만들어졌는지 알 수 없는 물건이기 때문이다.

merge 3동작 — 조 · 덮 · 반

조 — 조회한다→덮 — 전 필드를 덮는다→반 — 새 영속 인스턴스를 반환한다

조는 3-6의 "SELECT가 한 번 더"로, 덮은 3-3의 데이터 유실로, 반은 5-1의 "반환값을 버리면 무효"로 각각 이어진다. 세 글자가 이 문서의 사고 세 개를 그대로 가리킨다.

3-2. 두 경로를 한 화면에 — 다른 것은 "비교 직전의 입력"뿐이다

3-3. 사고 재현 — 누락된 필드가 null로 덮인다

회원 엔티티에 필드가 10개 있고, 수정 화면은 이름과 전화번호 2개만 보낸다고 하자. 흔한 요구사항이다.

bad 조용한 데이터 유실 — 예외도 경고도 나지 않는다
@Transactional
public void updateMember(MemberUpdateRequest request) {
    Member member = new Member();                 // ① 비어 있는 객체를 만든다
    member.setId(request.getId());                // ② id를 채운다 → "1번 회원"을 가리키게 된다
    member.setName(request.getName());            // ③ 요청에 온 두 필드만 채운다
    member.setPhone(request.getPhone());
    // ④ 나머지 8개 필드는 자바 기본값 그대로다 — 참조 타입이므로 전부 null이다
    memberRepository.save(member);                // ⑤ id가 있으므로 내부에서 merge가 호출된다
}

④번 주석이 이 사고의 전부다. email, address, grade, point는 "안 건드리겠다"는 의미로 비워둔 것인데, 자바 객체 안에서 그것은 null이라는 값이다. 그리고 merge는 그 null을 "사용자가 이 필드를 비우겠다는 의도"와 구분하지 못한다.

SQL 실제로 실행되는 두 문장
-- ① merge가 먼저 읽는다 (1차 캐시에 없으므로 DB에서)
select m.id, m.name, m.phone, m.email, m.address, m.birth_date,
       m.grade, m.point, m.created_at, m.updated_at
  from member m where m.id = 1;

-- ② 읽어온 영속 엔티티에 넘어온 객체의 "전 필드"를 복사한 뒤 flush
update member
   set name       = '홍길동',           -- 의도한 변경
       phone      = '010-1111-2222',   -- 의도한 변경
       email      = null,       -- 유실: 원래 a@x.com 이었다
       address    = null,       -- 유실
       birth_date = null,       -- 유실
       grade      = null,       -- 유실: 원래 GOLD 였다
       point      = null,       -- 유실: 원래 12000 이었다
       created_at = null,       -- 유실: 가입 이력
       updated_at = null
 where id = 1;

가장 무서운 대목 — 아무것도 터지지 않는다 예외가 나지 않는다. 트랜잭션은 정상 커밋되고, HTTP 응답은 200이고, 애플리케이션 로그에는 아무 이상이 없다. NOT NULL 제약이 걸린 컬럼이 하나라도 있었다면 그나마 예외로 드러났겠지만, nullable한 컬럼들은 조용히 비워진다. 등급과 포인트가 사라지고, 며칠 뒤 고객센터로 문의가 들어온다.
한 칸 더 — 필드가 원시 타입이면 null조차 아니다 point가 Integer가 아니라 int였다면 덮어쓰이는 값은 null이 아니라 0이다. boolean이면 false다. null은 그래도 "비어 있다"는 신호라도 되지만, 0과 false는 정상값처럼 보인다 — 포인트가 0이 된 것은 "다 썼나 보다"로 넘어가기 쉽다. 사고의 발견이 더 늦어지는 쪽이다.

3-4. 처방 — 조회해서 영속 상태로 만든 뒤, 필요한 필드만

before 만들어서 넘긴다

    Member member = new Member();
    member.setId(req.getId());
    member.setName(req.getName());
    member.setPhone(req.getPhone());
    memberRepository.save(member);  merge
}
// 나머지 8개 필드 = null → 전부 덮어쓴다
after 조회해서 고친다
@Transactional
public void updateMember(MemberUpdateRequest req) {
    Member member = memberRepository.findById(req.getId())
        .orElseThrow(() -> new MemberNotFoundException(req.getId()));
    member.changeContact(req.getName(), req.getPhone());
    // save() 호출 불필요 — 변경 감지가 처리한다
}
// 나머지 8개 필드 = DB의 실제 값 → 스냅샷과 같아 "변경 없음"
good 엔티티 — setter를 열지 않고 "바뀔 수 있는 것"을 메서드로 고정한다 가산점
public class Member {
    // public setName / setPhone 을 열지 않는다
    public void changeContact(String name, String phone) {
        this.name = name;
        this.phone = phone;
    }
}

setName/setPhone을 public setter로 열어두면 다음 사람이 또 전체를 만진다. 변경 가능한 범위를 메서드 시그니처로 고정하는 것이 이 사고를 구조적으로 막는 방법이다. 사고 예방을 사람의 주의력이 아니라 컴파일러에게 맡기는 것이기 때문이다.

처방 3단계 — 조 · 필 · 고

조 — 조회해서 영속 상태로 만든다→필 — 필요한 필드만 바꾼다→고 — 그 범위를 도메인 메서드로 고정한다
"조·필"까지는 관례를 따르는 사람도 한다 — "고"까지 말해야 이유를 아는 사람으로 보인다

3-6. 부수 비용 — merge는 조회를 아껴주지 않는다

merge는 항상 SELECT가 선행된다(1차 캐시에 없으면). 3-1의 1단계다. 건별 수정이 많은 배치에서는 이 조회 쿼리가 그대로 배로 붙는다.

반면 변경 감지 경로는 어차피 조회를 하고 그 조회해 온 객체를 그대로 쓰므로 추가 조회가 없다. 즉 "merge가 조회를 아껴준다"는 인상은 사실과 정반대다.

4. 방아쇠 — save()는 id 유무로 갈린다

4-1. save()는 "저장 메서드"가 아니라 분기문이다

이 사고의 출발점은 merge를 직접 호출한 적이 없다는 점이다. 3-3의 코드 어디에도 merge라는 글자가 없다. repository.save()를 썼을 뿐이다.

src Spring Data JPA — SimpleJpaRepository
@Transactional
public <S extends T> S save(S entity) {
    if (entityInformation.isNew(entity)) {
        entityManager.persist(entity);        // 신규 → INSERT
        return entity;
    } else {
        return entityManager.merge(entity);   // 신규가 아니면 → merge
    }
}
save()는 INSERT 전용 메서드가 아니다 — 이름은 "저장한다"지만 실제로는 "신규인가?"를 판정해 두 갈래로 나뉘는 분기문이다

save()의 판정 규칙 — 이 세 줄이 인출 대상이다

Long · String
래퍼 타입 id
id == null → 신규
long · int
원시 타입 id
id == 0 → 신규
@Version
버전 속성이 있을 때
id가 아니라 version == null → 신규

확인 범위: save()와 isNew()의 분기 구조는 Spring Data JPA의 공개된 구현으로 널리 알려진 내용이다. 다만 세부 클래스명과 판정 순서는 버전에 따라 변동이 있을 수 있으므로, 팀에서 쓰는 버전의 SimpleJpaRepository·JpaMetamodelEntityInformation을 직접 열어 확인하는 것을 권한다.

4-2. "id를 채워서 save 하면 중복 에러가 나지 않나요?"

나지 않는다. 그리고 이 오해가 위험한 이유는 오해의 방향 때문이다.

믿는 것

"잘못됐으면 터질 테니, 안 터지면 맞는 것이다." → 그래서 그 코드를 안전하다고 판단한다.

실제

에러가 나지 않고 UPDATE가 조용히 성공한다. id는 "이미 있는 행"을 가리키므로 중복이 아니라 수정이다.

사고는 예외가 날 때 나는 게 아니라 조용히 성공할 때 난다 — 이 사고의 발견에 며칠씩 걸리는 이유가 정확히 이것이다

5. 남은 함정 셋 — 반 · 동 · 캐

세 함정의 공통점 — 셋 다 예외를 내지 않는다

반 — 반환값을 버린다 동 — @DynamicUpdate로 막힌다고 믿는다 캐 — cascade가 컬렉션을 지운다

반은 "수정이 반영되지 않는다", 동은 "옵션을 켰는데 그대로다", 캐는 "자식 데이터가 통째로 사라졌다"로 나타난다. 증상이 다 다르지만 원인은 하나 — merge다.

5-1. 함정 ① 반환값을 버리면 아무 일도 일어나지 않는다

bad 넘긴 객체를 계속 쓴다
Member member = new Member();
member.setId(1L);
memberRepository.save(member);
member.setName("변경");   준영속
// member는 여전히 준영속이다.
// 이 변경은 어디에도 반영되지 않는다.
// 그리고 예외도 나지 않는다.
good 반환값을 받아서 쓴다
Member member = new Member();
member.setId(1L);
Member managed = memberRepository.save(member);
managed.setName("변경");   영속
// 반환된 것이 영속 인스턴스다.
// 이것만 반영된다.

1절의 다이어그램에서 확인한 그대로다. merge는 넘긴 객체를 영속 상태로 만들지 않는다. 새 인스턴스를 만들어 값을 복사하고 그것을 반환한다. 넘긴 객체는 화살표의 출발점에 그대로 남아 있다.

"수정이 반영되지 않는다"는 문의의 상당수가 이것이다 다만 이 함정은 위험도가 다르다. 3-3의 사고는 있던 데이터를 지우지만, 이 함정은 아무 일도 일어나지 않게 만든다. 덜 파괴적인 대신 더 자주 겪는다 — 그리고 역시 예외를 내지 않는다.

5-2. 함정 ② @DynamicUpdate로는 막을 수 없다 흔한 오해

@DynamicUpdate는 변경된 컬럼만 SET 절에 넣도록 만드는 옵션이다. 2-3에서 본 "SET 절에 전 컬럼이 들어간다"는 기본 동작을 바꾸는 것이다. 그러니 이름만 보면 null 덮어쓰기를 막아줄 것처럼 보인다. 막지 못한다.

@DynamicUpdate가 하는 일

"변경된 컬럼"만 SET에 넣는다. 줄여주는 대상은 "안 바뀐 컬럼"이다.

merge 사고에서의 실상

안 바뀐 컬럼이 없다. merge가 전부 덮었으므로 전부 바뀌었다. 줄일 대상이 애초에 존재하지 않는다.

이유는 단순하다. merge가 email을 null로 덮은 시점에 그 필드는 실제로 변경된 것이다(a@x.com → null). 변경 감지는 이것을 정당한 변경으로 판정하고, @DynamicUpdate는 "변경된 컬럼"을 넣으라는 옵션이므로 email = null을 정확히 포함시킨다.

-- @DynamicUpdate 적용 후에도
update member set name=?, phone=?, email=null, address=null, ... where id=?
--                                 ^^^^^^^^^^ 여전히 나간다

2-3에서 미리 갈라 둔 구분이 여기서 쓰인다

"SQL에 컬럼이 실리느냐"와 "값이 바뀌느냐"는 다른 문제이고, @DynamicUpdate는 앞쪽만 건드린다

흔한 오해이므로 면접에서 반대로 짚으면 가산점이다. "옵션을 켜서 막는다"가 아니라 "막을 수 없다, 왜냐하면 문제는 SQL의 모양이 아니라 값이 이미 바뀐 것이기 때문이다"라고 답한다.

5-3. 함정 ③ cascade가 얽히면 자식 컬렉션이 통째로 사라진다

merge는 CascadeType.MERGE(또는 ALL)가 설정된 연관에만 전파된다. 문제는 그 전파가 컬렉션까지 덮는다는 점이다.

확인 범위 cascade·orphanRemoval과 merge의 상호작용은 매핑 설정과 컬렉션의 초기화 상태(빈 컬렉션인지 미초기화 프록시인지)에 따라 결과가 갈린다. 위 시나리오는 "DTO에서 새로 만든 엔티티의 컬렉션은 빈 ArrayList"인 경우를 전제한 것이다. 실제 프로젝트에서는 반드시 쿼리 로그로 DELETE가 나가는지 직접 확인할 것.

6. merge가 정당한 자리와, merge로는 만들 수 없는 것

6-1. 정당한 자리는 하나 — 재부착(reattach)

거의 없다. 정확히는 "넘어온 값으로 전부 덮는 것이 곧 요구사항인 경우"뿐이다.

merge가 맞는 상황 — 받은 것이 전체다

  • 세션이나 캐시에 엔티티를 통째로 보관해 두었다가 꺼내 다시 붙일 때
  • 원격 호출로 엔티티의 전체 상태를 받아온 뒤 영속 상태로 붙일 때

"받은 것이 전체다"라는 전제가 실제로 참이므로, 전부 덮는 동작이 요구사항과 정확히 일치한다.

merge가 틀리는 상황 — 받은 것이 일부다

  • 수정 화면이 일부 필드만 보내는 일반적인 수정 API
  • 요청 DTO를 엔티티로 변환해 넘기는 모든 코드

실무의 거의 전부가 이쪽이다. 그 외에는 전부 조회 후 변경 감지가 맞다.

6-2. "그래도 값을 전부 바꿔야 할 때는 merge가 맞지 않나요?"

그조차 안전하지 않다. 이유는 merge가 두 가지 null을 구분할 수 없다는 데 있다.

클라이언트의 의도요청에 담긴 값merge에게 보이는 것
"이 필드는 안 건드릴게"필드가 아예 없거나 null똑같은 null
구분할 수단이 없다
"이 필드를 비워줘"null
merge로는 PATCH 시맨틱을 구현할 수 없다

PATCH 시맨틱이란 "요청에 온 필드만 부분 수정하고 나머지는 건드리지 않는다"는 HTTP PATCH의 의미론을 말한다. 부분 수정 API를 만들 때 이 구분이 곧 요구사항이 되고, 그래서 실무에서는 DTO로 받아 "온 것만 적용"하는 코드를 직접 쓴다.

good PATCH — "온 것만 적용"을 명시적으로 표현한다
@Transactional
public void patchMember(Long id, MemberPatchRequest request) {
    Member member = memberRepository.findById(id).orElseThrow();
    // null이면 "안 보냈다"로 해석해 건너뛴다.
    // merge가 못 하는 판단을 여기서 사람이 한다.
    if (request.getName() != null)  member.changeName(request.getName());
    if (request.getPhone() != null) member.changePhone(request.getPhone());
    // "비워달라"까지 표현해야 하면 Optional<T>나 JsonNullable 같은 3-상태 타입을 쓴다.
    // 값 있음 / 명시적 null / 필드 없음 — 세 상태를 구분할 수 있는 타입이어야 한다.
}

6-3. 그럼 merge는 왜 명세에 있는가 시니어 변별

merge는 분리된 계층 사이에서 엔티티가 오갔던 시대의 도구다. 원격 호출로 엔티티를 직렬화해 보내고 받아서 다시 붙이는(detach → 전송 → reattach) 구조에서는 "받은 것이 전체 상태"라는 전제가 실제로 참이었고, 그때 merge는 정확히 필요한 연산이었다.

지금은 계층 간에 DTO를 주고받고 엔티티는 트랜잭션 안에 머무르는 구조가 표준이 되어 그 전제가 깨졌다 —
merge는 잘못된 API가 아니라 전제가 달라진 API다

7. 인출 카드 · 꼬리질문 셀프 테스트

7-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

두 방식의 근본 차이 한 문장?
기준선(스냅샷)의 유무. 변경 감지는 계산하고, merge는 모르니 전부 덮는다.
merge 3동작?
조·덮·반 — 조회한다(없으면 INSERT 경로) / 전 필드를 덮는다 / 새 영속 인스턴스를 반환한다.
영속으로 들어가는 문 셋?
① persist ② 조회 ③ merge의 반환값. 넘긴 객체는 준영속 그대로다.
save()의 분기 기준?
isNew() — 래퍼 id면 null, 원시 id면 0, @Version이 있으면 version이 null인지로 판정.
왜 예외가 안 나나?
id가 있는 기존 행에 대한 정상 UPDATE이기 때문. NOT NULL이 없으면 200 OK로 조용히 커밋된다.
merge도 변경 감지를 타나?
탄다. 다만 덮어쓰기가 끝난 뒤에 타므로 null이 정당한 변경으로 잡힌다. 감지가 아니라 입력이 오염된 것.
@DynamicUpdate로 막히나?
안 막힌다. merge가 값을 이미 바꿔 놨으니 email=null은 "변경된 컬럼"에 정확히 포함된다.
함정 셋?
반·동·캐 — 반환값 버리기 / 동적 UPDATE 착각 / 캐스케이드+orphanRemoval 컬렉션 소실.
처방 3단계?
조·필·고 — 조회해서 영속으로 / 필요한 필드만 / 도메인 메서드로 범위 고정.
리뷰 5초 판별식?
save()의 인자가 new로 만든 객체인가, 조회해 온 객체인가. 인자를 따라 올라가면 끝난다.
merge가 정당한 자리?
재부착(reattach) — "받은 것이 전체다"가 참일 때뿐. 실무에서는 거의 없다.
merge는 SELECT를 아껴주나?
반대다. merge는 항상 조회가 선행된다. 변경 감지는 조회한 객체를 그대로 쓴다.

7-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

save()를 호출하지 않았는데 UPDATE가 나갔습니다. 왜죠? 필수힌트: "변경 감지 때문"으로 끝내지 말고, save()가 원래 무엇을 위한 메서드인지까지 잇는다

영속 상태 엔티티의 필드를 바꿨기 때문이다. 영속성 컨텍스트가 조회 시점의 스냅샷과 비교해 변경을 찾아내고, flush 시점(보통 커밋 직전)에 UPDATE를 만든다.

save()는 비영속 객체를 영속화하거나 준영속 객체를 병합할 때 필요한 것이고, 이미 영속 상태인 엔티티에는 불필요하다. 1절의 다이어그램에서 이미 "영속" 박스 안에 있는 객체에게 화살표를 한 번 더 그을 필요가 없는 것과 같다.

뒤집어 보는 것도 좋다 — 조회 전용 트랜잭션에서 의도치 않은 UPDATE가 나가는 문제도 같은 메커니즘이다. 조회해 온 엔티티를 어디선가 건드렸다면 커밋 시점에 UPDATE가 나간다. 그래서 조회 전용 경로에는 @Transactional(readOnly = true)를 붙여 변경 감지 대상에서 빼는 최적화를 쓴다.

그럼 save()는 언제 호출해야 하나요? 필수힌트: 수정 로직의 save()는 둘 중 하나다 — 무의미하거나 위험하거나

신규 저장(비영속 → 영속)에만 필요하다.

수정 로직에서 save()를 부르는 코드는 대개 둘 중 하나다.

① 무의미하다

습관적으로 붙였고 실제로는 아무 효과가 없다. 이미 영속 상태라 merge가 1차 캐시에서 같은 인스턴스를 찾아 그대로 반환한다.

② 위험하다

준영속 객체를 넘기고 있다. 3-3의 사고다. 겉보기 코드는 ①과 똑같이 생겼다는 것이 이 함정의 본질이다.

후자를 걸러내는 리뷰 포인트는 하나 — save()의 인자가 new로 만든 객체인가, 조회해 온 객체인가
인자를 따라 올라가 보면 5초 안에 판별된다
id를 채워서 save() 하면 중복 에러가 나지 않나요? 함정힌트: 답 자체보다 "오해의 방향"이 왜 위험한지를 말하는 게 핵심이다

나지 않는다. id는 "이미 존재하는 행"을 가리키므로 merge가 그 행을 읽어와 UPDATE를 만든다. 중복 삽입이 아니라 수정이다.

그리고 이 오해가 위험한 이유는 오해의 방향 때문이다. "에러가 날 것"이라고 믿는 사람은 그 코드를 안전하다고 판단한다. 잘못됐으면 터질 테니 안 터지면 맞는 것이라고 생각하는 것이다. 실제로는 에러가 나지 않고 UPDATE가 조용히 성공한다.

사고는 예외가 날 때 나는 게 아니라 조용히 성공할 때 난다. 이 문서의 사고가 발견까지 며칠씩 걸리는 이유가 정확히 이것이다. 여기에 "그래서 NOT NULL 제약을 스키마에 제대로 걸어두면 조용한 실패가 시끄러운 실패로 바뀐다"까지 얹으면 답이 한 단계 올라간다.

merge 대신 find + setter를 쓰면 SELECT가 한 번 더 나가서 손해 아닌가요? 함정힌트: 쿼리 수를 세어 본다. 그리고 merge가 "없애버리는 선택지"까지 언급한다

아니다. merge도 내부에서 SELECT를 한다(3-1의 1단계). 쿼리 수는 같고, find + 수정 쪽이 의도가 코드에 드러난다는 이점이 있다.

오히려 merge가 불리한 경우도 있다. getReferenceById로 프록시만 얻어 필드 하나만 바꾸는 최적화가 가능한데(실체를 읽지 않고 UPDATE만 나갈 수 있다), merge는 값을 복사해야 하므로 반드시 실체를 읽어야 한다 — 그 선택지를 없앤다.

정리하면 "merge가 조회를 아껴준다"는 인상은 사실과 반대다. 건별 수정이 많은 배치에서는 merge의 선행 SELECT가 그대로 배로 붙는다.

그래도 값을 전부 바꿔야 할 때는 merge가 맞지 않나요? 함정힌트: merge가 구분하지 못하는 "두 가지 null"을 떠올린다

그조차 안전하지 않다. merge는 "이 필드는 안 건드릴게"의 null과 "이 필드를 비워줘"의 null을 구분할 수 없기 때문이다. 둘 다 똑같은 null로 보인다.

즉 merge로는 PATCH 시맨틱(요청에 온 필드만 부분 수정)을 구현할 수 없다. 부분 수정 API에서는 이 구분이 곧 요구사항이므로, DTO로 받아 "온 것만 적용"하는 코드를 직접 쓴다. "비워달라"까지 표현해야 하면 값 있음 / 명시적 null / 필드 없음 세 상태를 구분할 수 있는 3-상태 타입이 필요하다.

정말로 "받은 것이 전체다"가 참인 경우(세션·캐시에 통째로 보관했다 꺼내는 재부착)라면 merge가 맞다. 그 전제가 참인지를 스스로에게 묻는 것이 판단의 전부다.

merge가 UPDATE가 아니라 INSERT를 낼 수도 있나요? 가산점힌트: 3-1의 2단계. "수정인 줄 알았는데 새 행이 생겼다"는 증상

낼 수 있다. merge는 id로 1차 캐시 → DB 순으로 찾는데, DB에도 그 행이 없으면 새 엔티티를 만들어 INSERT 경로로 간다. 즉 merge는 "수정"만이 아니라 "없으면 삽입"까지 하는 연산이다.

그래서 증상이 두 갈래로 나뉜다. 행이 있으면 조용한 UPDATE(데이터 유실), 행이 없으면 조용한 INSERT(예상 못 한 새 행)다. 둘 다 예외가 나지 않는다는 점이 같다.

여기서 변경 감지 경로와의 차이가 한 번 더 드러난다. 조회 후 수정 경로는 findById(...).orElseThrow()에서 "없는 id"가 즉시 예외로 드러난다. 반면 merge는 없는 id를 조용히 새 행으로 만들어 버린다 — 정상 경로를 쓰면 잘못된 입력이 조기에 실패한다는 부수 이득이 있는 셈이다.

@Version을 붙였더니 id를 채웠는데도 persist가 불렸습니다. 왜죠? 시니어 변별힌트: isNew()가 보는 대상이 바뀐다

isNew()의 판정 기준이 바뀌었기 때문이다. 기본 판정은 id를 보지만(AbstractEntityInformation), @Version 속성이 있고 그 타입이 원시 타입이 아니면 JpaMetamodelEntityInformation이 id가 아니라 버전 필드가 null인지로 신규를 판정한다.

따라서 id를 직접 채웠어도 version이 아직 null이면 "신규"로 판정되어 persist로 간다. 낙관적 락을 쓰는 엔티티에서만 나타나는 현상이라 원인을 짐작하기 어렵다.

여기서 중요한 것은 개별 규칙을 외우는 게 아니다. save()가 어느 갈래로 가는지를 프레임워크의 판정 로직이 결정하고, 그 로직은 매핑에 따라 달라진다는 사실 자체다. 그래서 "save()를 부르면 저장된다"가 아니라 "save()는 분기문이다"로 이해해야 하고, 팀에서 쓰는 버전의 구현을 직접 열어 확인하는 것이 정석이다.

UUID를 id로 쓰는데 save()마다 SELECT가 한 번씩 더 나갑니다. 시니어 변별힌트: 기본 판정이 무엇을 오판하는지 생각한다

기본 isNew() 판정이 "신규가 아니다"로 오판하기 때문이다. UUID처럼 애플리케이션이 id를 미리 만들어 넣는 전략에서는 신규 엔티티인데도 id가 항상 채워져 있다. 그러면 save()가 merge로 가고, merge는 항상 조회가 선행되므로 저장 건마다 불필요한 SELECT가 하나씩 붙는다.

처방은 Persistable<ID> 인터페이스를 구현해 isNew()를 직접 정의하는 것이다. 흔한 구현은 @Transient 플래그를 하나 두고, 새로 만들었을 때는 true, 영속화되거나 DB에서 로드된 뒤에는 false가 되도록 하는 방식이다.

이 답변이 변별력을 갖는 이유는, 같은 isNew() 지식이 한쪽에서는 데이터 유실(오판 ①), 다른 쪽에서는 성능 저하(오판 ②)로 나타난다는 것을 하나의 원인으로 묶어 설명하기 때문이다.

DTO를 엔티티로 자동 매핑하는 매퍼(MapStruct·ModelMapper)를 쓰면 이 사고와 어떤 관계가 있나요? 함정힌트: 매퍼가 문제가 아니다. "만들어진 객체를 어디에 넘기는가"가 문제다

관계가 직접적이다. 부분 필드만 담긴 요청 DTO를 엔티티로 통째로 매핑하면, DTO에 없던 필드가 null인 엔티티 인스턴스가 만들어진다. 그 객체를 save()에 넘기는 순간 3-3의 코드와 완전히 동일해진다 — 다른 점은 setXxx가 코드에 보이지 않아 더 안전해 보인다는 것뿐이다.

매퍼 자체가 문제인 것이 아니다. "DTO → 새 엔티티 생성" 매핑의 결과를 수정 경로에 넘기는 것이 문제다. 안전한 사용법은 두 갈래다.

안전 ①

매퍼는 엔티티 → DTO(응답) 방향에만 쓴다. 이 방향은 영속 상태를 건드리지 않는다.

안전 ②

쓰기에 쓴다면 "새 객체 생성"이 아니라 "조회해 온 영속 엔티티를 갱신"하는 매핑이어야 한다.

다만 null을 무시할지 덮을지는 라이브러리와 설정마다 다르므로, 팀에서 쓰는 매퍼의 null 처리 정책을 직접 확인하고 테스트로 고정해야 한다. "설정에 의존하는 안전"은 설정이 바뀌는 순간 사라진다는 점에서, 결국 도메인 메서드로 변경 범위를 고정하는 처방(3-4)이 더 튼튼하다.

이 사고를 테스트로 잡으려면 어떤 테스트를 써야 하나요? 가산점힌트: 보통의 수정 테스트는 이 사고를 통과시킨다. 무엇을 단언하지 않기 때문일까

보통의 수정 테스트는 이 사고를 그대로 통과시킨다. "이름이 홍길동으로 바뀌었는가"만 단언하기 때문이다. 바뀐 필드만 검증하면 바뀌지 말았어야 할 필드는 아무도 보지 않는다.

그래서 단언을 뒤집어야 한다 — "요청에 담지 않은 필드가 수정 전과 동일한가"를 명시적으로 확인한다. 회원 수정 테스트라면 grade, point, createdAt이 수정 전 값 그대로인지를 단언한다.

두 가지를 더 얹으면 방어가 두꺼워진다.

  • 스키마의 NOT NULL 제약을 실제로 걸어 둔다. 그러면 이 사고가 조용한 유실이 아니라 제약 위반 예외로 드러난다 — 조용한 실패를 시끄러운 실패로 바꾸는 것이다.
  • 쿼리 로그를 확인하는 습관 또는 실행 SQL을 검증하는 테스트를 둔다. merge는 선행 SELECT라는 뚜렷한 흔적을 남기므로, 수정 경로에서 예상보다 SELECT가 하나 더 보이면 merge를 의심할 수 있다.

정리하면 — 이 사고는 "값이 틀렸다"가 아니라 "건드리지 않았어야 할 값이 바뀌었다"이므로, 테스트도 그 형태로 써야 잡힌다.

지금 이 객체가 영속인지 준영속인지 코드에서 확인할 방법이 있나요? 가산점힌트: API가 있긴 하다. 하지만 실무의 진짜 답은 다른 데 있다

API로는 em.contains(entity)가 있다. 현재 영속성 컨텍스트가 그 인스턴스를 관리 중인지를 알려준다. 디버깅이나 학습용으로는 유용하다.

그러나 실무의 답은 이것이 아니다. 프로덕션 코드에 상태 검사를 심어 분기하는 구조는 "내가 이 객체의 출처를 모른다"는 사실을 그대로 드러내는 설계다. 진짜 처방은 인스턴스의 출처를 코드 구조로 확정해 두는 것이다 — 수정 경로에서는 항상 조회로 시작하고, new로 만든 엔티티는 신규 저장 경로에만 넘긴다.

1-1에서 짚은 "객체를 아무리 들여다봐도 자기가 어느 상태인지 알 수 없다"가 여기로 이어진다. 상태가 객체 안에 적혀 있지 않으므로 읽는 사람은 인스턴스가 어디서 왔는지를 거슬러 올라갈 수밖에 없고, 그래서 거슬러 올라갈 거리가 짧은 코드(조회한 자리에서 바로 고치는 코드)가 안전한 코드다.

엔티티에 setter를 열지 말라는 말은 자주 듣는데, 이 사고와 무슨 관계인가요? 시니어 변별힌트: "캡슐화가 좋으니까"라고 답하면 절반이다. 예방의 주체를 누구로 옮기는가

관계가 직접적이다. 이 사고의 본질은 "바뀌어도 되는 필드"와 "바뀌면 안 되는 필드"가 코드에 표현되어 있지 않다는 것이다.

setter가 전부 열려 있으면 merge가 전부 덮는 것을 문법적으로 막을 수 없고, 리뷰에서 사람이 눈으로 찾아야 한다. 반면 member.changeContact(name, phone) 같은 도메인 메서드만 열어두면 "연락처 변경"이라는 연산의 범위가 타입으로 고정되고, 그 밖의 필드를 건드리는 코드는 컴파일되지 않는다.

사고 예방을 사람의 주의력에서 타입 시스템으로 옮기는 것 — 이게 "setter를 닫아라"의 실제 값이다
"캡슐화가 좋으니까"라고 답하는 것과는 설득력이 다르다
그럼 merge는 왜 JPA 명세에 있는 건가요? 시니어 변별힌트: 금기가 아니라 원리로 설명한다. "전제가 달라졌다"

merge는 분리된 계층 사이에서 엔티티가 오갔던 시대의 도구다.

원격 호출로 엔티티를 직렬화해 보내고 받아서 다시 붙이는(detach → 전송 → reattach) 구조에서는 "받은 것이 전체 상태"라는 전제가 실제로 참이었고, 그때 merge는 정확히 필요한 연산이었다. 6-1에서 본 유일한 정당한 자리가 그것이다.

지금은 계층 간에 DTO를 주고받고 엔티티는 트랜잭션 안에 머무르는 구조가 표준이 되어 그 전제가 깨졌다. 즉 merge는 잘못된 API가 아니라 전제가 달라진 API다.

이렇게 답하면 "왜 쓰지 말라는지"를 금기가 아니라 원리로 이해하고 있음을 보일 수 있다. 그리고 전제를 확인하는 습관은 merge에만 쓰이지 않는다 — "이 도구가 참이라고 가정하는 것이 지금도 참인가"는 모든 기술 선택에 적용되는 질문이다.

한 줄 요약
변경 감지는 조회 시점의 스냅샷이라는 기준선이 있어 무엇이 바뀌었는지 계산해 그것만 고치고, merge는 그 기준선이 없어 무엇이 바뀌었는지 모르니 넘어온 객체로 전부 덮는다 — 그래서 new 엔티티에 id만 채워 save()하면(Spring Data의 save()는 id 유무로 persist와 merge로 갈린다) 예외도 경고도 없이 나머지 컬럼이 null이 되고, @DynamicUpdate로도 막히지 않으며, cascade가 걸려 있으면 자식 컬렉션까지 지워진다. 처방은 언제나 "조회해서 영속 상태로 만든 뒤 필요한 필드만 바꾸기"이고, 그 범위를 도메인 메서드로 고정해 컴파일러가 지키게 하는 것이 상위 처방이다.
