API 병목 추적
감이 아닌 측정으로, 모니터링에서 프로파일링까지

면접 질문: "API 응답이 갑자기 느려졌습니다. 병목 지점을 찾는 과정을 처음부터 끝까지 설명해주세요. (모니터링 → 프로파일링)"

핵심 관전 포인트 — 병목 추적은 넓은 곳에서 좁은 곳으로 내려가는 탑다운 수사다. ① 먼저 "무엇이 변했는가"를 확정하고(배포·설정·데이터·트래픽·의존 서비스·인프라 작업·배치), ② 모니터링 지표(p99, 에러율, 자원 사용률)로 어느 계층이 느린지 좁히고, ③ 분산 트레이싱으로 요청 한 건의 시간을 구간별로 분해해 범인 구간을 찾고, ④ 마지막에 그 구간만 프로파일링(스레드 덤프, 플레임 그래프)으로 파고든다. 순서의 핵심은 "코드부터 열어보지 않는 것" — 추측이 아니라 측정이 다음 단계를 결정한다. 그리고 이 수사에서 가장 자주 놓치는 것은 큐 대기 시간이다. 요청이 톰캣 워커 스레드를 기다린 시간과 DB 커넥션을 기다린 시간은 애플리케이션 로그에 잡히지 않으므로, "우리 코드는 10ms인데요"라는 말과 "사용자는 5초 기다렸다"는 사실이 동시에 참일 수 있다. 앞단이 잰 시간과 앱이 잰 시간의 차이가 곧 그 보이지 않는 대기다.
  • 1
    순서가 답이다 — 넓은 곳에서 좁은 곳으로. 변했나 → 지표 → 구간 → 프로파일 네 단계로 내려가고, 매 단계의 다음 행선지는 추측이 아니라 측정이 정한다. 코드 읽기는 이 순서에 없다 — "이 구간이 느리다"가 확정된 뒤에 여는 것이다.
  • 2
    가장 자주 놓치는 구간은 "큐 대기"다 — 톰캣 워커를 기다린 시간과 DB 커넥션을 기다린 시간은 애플리케이션 로그에 구조적으로 잡히지 않는다. 그래서 "우리 코드는 10ms"와 "사용자는 5초 기다렸다"가 동시에 참일 수 있다.
  • 3
    그 보이지 않는 시간은 뺄셈 두 개로 드러난다 — 앞단(nginx)이 잰 시간 − 앱이 잰 시간 = 앱 앞의 큐 대기, 앱이 잰 DB 구간 − DB가 잰 실행 시간 = DB 밖의 대기(커넥션 획득). 이 두 뺄셈이 "DB가 느리다"와 "DB에 도달하지 못하고 있다"를 가른다.

0. 질문 + 출제 의도

질문: "API 응답이 갑자기 느려졌습니다. 병목 지점을 찾는 과정을 처음부터 끝까지 설명해주세요. (모니터링 → 프로파일링)"

출제 의도: 이 질문의 진짜 목적은 방법론이다 — 어디부터 보는지(지표 → 구간 분해 → 프로파일링), 판단의 근거가 추측인지 측정인지. 체계 없이 "코드를 봤어요"로 시작하는 사람은 실전에서 몇 시간을 낭비한다. 장애 상황에서 침착하게 범위를 좁혀가는 수사 능력을 확인하는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① 순서 없이 도구 이름만 나열하는 것("APM 보고 스레드 덤프 뜹니다") → 4절에서 왜 비싼 도구를 나중에 쓰는지를 비용 축으로 못 박고, 5~9절을 단계 순서 그대로 배치한다.
② "우리 코드는 빠른데요"에서 멈추는 것 → 1·2절에서 앱 로그에 구조적으로 안 잡히는 두 구간(워커 대기·커넥션 대기)을 타임라인 위에 그려 놓고, 두 개의 뺄셈으로 꺼내는 법을 규칙으로 만든다.
③ 원인과 증상을 같은 곳에서 찾는 것("전 API가 느리니 서버 문제") → 10·11절에서 쿼리 하나가 21초 만에 서버 전체를 마비시키는 연대책임 메커니즘을 산수로 따라간다.

1. 200ms 한 건을 해부한다 — 수사의 지도부터 그린다

수사를 시작하기 전에 지도가 필요하다. 응답시간 200ms라는 숫자 하나는 실제로는 일곱 개쯤의 구간이 더해진 합계인데, 이 사실을 모르면 "느리다"는 말에서 다음 행동으로 넘어갈 수 없다. 정상적으로 200ms에 응답하는 API 하나를 시간축에 늘어놓으면 이렇게 된다.

1-1. "큐 대기"가 정확히 무슨 뜻인가

서버의 자원은 무한하지 않아서, 톰캣의 워커 스레드도 200개, DB 커넥션 풀도 10개처럼 개수가 정해져 있다. 그 자원이 전부 사용 중일 때 새로 도착한 요청은 거절되지 않고 줄을 선다. 그 줄에서 보낸 시간이 큐 대기 시간이다. CPU를 쓰지도 않고, 네트워크를 타지도 않고, 그냥 자기 차례를 기다린다.

비유 — 대기실은 진료 기록에 없다

진료 자체는 5분인데 대기실에서 40분 기다렸다면 환자의 체감 시간은 45분이다. 그런데 의사의 진료 기록에는 "5분 진료"만 남는다.

개발자의 "우리 코드는 10ms입니다"는 진료 기록이고, 사용자의 "5초 걸렸습니다"는 대기실을 포함한 체감이다 — 둘 다 참이다

2. 계측 도구는 각자 다른 구간만 본다 — 두 개의 뺄셈

87ms가 앱 로그에 안 잡히는 이유는 게으름이 아니라 구조다. 계측 도구마다 스톱워치를 켜는 지점이 다르기 때문이고, 그 사실을 알면 거꾸로 도구 사이의 차이로 안 보이는 구간을 계산해 낼 수 있다.

이 문서에서 딱 하나만 외운다면 — 두 개의 뺄셈

① 앞단이 잰 시간 − 앱이 잰 시간 = 앱 앞의 큐 대기 (톰캣 워커 부족)
② 앱이 잰 DB 구간 − DB가 잰 실행 시간 = DB 밖의 대기 (커넥션 획득·네트워크·드라이버)

뺄셈 ②가 "DB가 느리다"와 "DB에 도달하지 못하고 있다"를 가른다. 10절의 시나리오가 정확히 이 갈림에서 풀린다.

2-1. 톰캣 accept 큐 대기가 안 잡히는 이유

이 구간에서 요청은 아직 워커 스레드에 배정되지 않았다. 스프링의 서블릿 필터, 인터셉터, @RestController 메서드는 모두 워커 스레드가 요청을 집어든 다음에 실행된다. 그러니 필터에서 스톱워치를 켜도 그 스톱워치는 45ms 지점에서 시작한다 — 앞의 45ms는 측정 자체가 불가능하다. 마이크로미터의 http.server.requests 타이머도 서블릿 필터 체인 안에서 재므로 마찬가지다.

2-2. 커넥션 풀 대기는 다르게 숨는다 — "DB 구간"으로 뭉쳐진다

이 시간은 워커 스레드 안에서 흐르므로 필터의 스톱워치에는 포함된다. 문제는 개발자가 남기는 로그의 해상도다.

Before 전체 시간만 로깅한다 — 800ms가 나와도 어디서 썼는지 모른다
public OrderDetail getDetail(long orderId) {
    long start = System.currentTimeMillis();
    OrderDetail result = doGetDetail(orderId);   // 이 안이 통째로 블랙박스
    log.info("getDetail took {}ms", System.currentTimeMillis() - start);
    return result;
}

이 로그는 "800ms 걸렸다"까지만 말한다. 그다음 질문 — DB인가, 외부 API인가, 직렬화인가 — 에 아무 답을 주지 못한다. 그래서 개발자는 급한 마음에 코드를 열고 눈으로 읽기 시작하고, 여기서 몇 시간이 사라진다. 구간을 나눠 재면 그 몇 시간이 5분이 된다.

After 단계별로 시간을 쪼개 기록한다
public OrderDetail getDetail(long orderId) {
    long t0 = System.nanoTime();
    Order  order  = orderRepository.findById(orderId).orElseThrow();  // DB 구간
    long t1 = System.nanoTime();
    Coupon coupon = couponClient.fetch(order.userId());               // 외부 API 구간
    long t2 = System.nanoTime();
    OrderDetail dto = mapper.toDetail(order, coupon);                 // CPU 구간
    long t3 = System.nanoTime();

    log.info("getDetail orderId={} db={}ms api={}ms map={}ms total={}ms",
            orderId, ms(t0, t1), ms(t1, t2), ms(t2, t3), ms(t0, t3));
    return dto;
}

private static long ms(long from, long to) {
    return (to - from) / 1_000_000;
}
왜 currentTimeMillis()가 아니라 nanoTime()인가 currentTimeMillis()는 벽시계(wall clock)라 NTP 시각 보정에 영향을 받는다. 보정이 들어가면 두 시점의 차이가 음수로 나오거나 튀는 경우가 있다. nanoTime()은 단조 증가(monotonic)가 보장되는 경과 시간용 시계이므로 구간 측정에는 이쪽이 맞다. 대신 절대 시각으로는 쓸 수 없다 — 기준점이 임의라서 차이에만 의미가 있다.
After 코드에도 남는 한계 — db= 안에 두 가지가 섞여 있다 findById는 내부적으로 DataSource.getConnection()을 먼저 호출한다. 그래서 db=에는 "커넥션을 얻기까지 기다린 시간"과 "쿼리가 실제로 실행된 시간"이 합쳐져 있다. 이 둘을 가르는 것이 위의 뺄셈 ②다. 
앱이 잰 db 구간                    250ms
PostgreSQL이 잰 그 쿼리 평균         3ms   (pg_stat_statements.mean_exec_time)
                                 ───────
차이                               247ms   <- 쿼리가 아니다. 커넥션을 기다린 시간이다.
DB가 "나는 3ms에 끝냈다"는데 앱이 "250ms 걸렸다"면, 그 차이는 DB 밖에서 생긴 것이다

의심 순서는 커넥션 획득 대기 → 네트워크 → 드라이버 오버헤드다. 이 비교 하나가 수사의 방향을 "DB를 튜닝한다"에서 "커넥션을 왜 못 얻는지 찾는다"로 완전히 돌려놓는다.

3. 큐 대기를 보는 세 가지 방법

① 앞단과 앱의 차이· ② 풀 지표를 직접 본다· ③ 분산 트레이싱 (7절)

3-1. 첫째, 앞단이 잰 시간과 앱이 잰 시간의 차이

가장 범용적이고 언제나 통하는 방법이다. LB나 nginx는 요청이 도착한 순간부터 재고, 앱은 워커 스레드가 요청을 집어든 순간부터 잰다. 그 차이가 곧 앱 앞의 큐 대기다. nginx라면 로그 포맷에 네 값을 나란히 남긴다.

nginx.conf 타이밍 네 값을 액세스 로그에 박아 둔다
# $request_time          : 첫 바이트를 읽기 시작해 응답 마지막 바이트를 다 쓸 때까지.
#                          클라이언트 네트워크까지 포함한다.
# $upstream_connect_time : 업스트림(톰캣)에 TCP 연결을 수립하기까지.
#                          톰캣 accept 큐가 꽉 차면 이 값이 커진다.
# $upstream_header_time  : 업스트림이 응답 헤더 첫 바이트를 줄 때까지.
# $upstream_response_time: 업스트림 응답을 다 받을 때까지.
log_format timing '$remote_addr "$request" $status '
                  'rt=$request_time uct=$upstream_connect_time '
                  'uht=$upstream_header_time urt=$upstream_response_time';

access_log /var/log/nginx/access.log timing;
읽는 법 — 세 값의 조합이 곧 진단이다
관측 패턴해석다음 행동
uct가 평소 0.001초 → 0.04초로 상승톰캣이 새 연결을 받아들이지 못한다 — 워커 스레드 포화tomcat.threads.busy / max 확인 → 왜 워커가 안 돌아오는지(6·9절)
urt는 큰데 uct는 정상연결은 바로 됐다 — 큐 문제가 아니라 톰캣 안에서 시간을 쓰고 있다구간 분해로 진입(7절)
rt − urt가 크다업스트림은 빨리 응답했는데 클라이언트로 내보내는 데 시간이 걸렸다느린 클라이언트·네트워크 — 서버를 뒤질 일이 아니다
uht는 작은데 urt가 크다헤더는 금방 나왔고 본문을 내보내는 데 오래 걸렸다 — 응답이 크거나 스트리밍응답 크기·페이지네이션·압축 확인

3-2. 둘째, 스레드풀과 커넥션풀 지표를 직접 본다

큐 대기 시간을 직접 재는 지표가 이미 존재한다. 없는 것을 만들어야 하는 게 아니라, 대시보드에 안 걸어 뒀을 뿐인 경우가 대부분이다.

tomcat.threads.busy / config.max
요청을 처리 중인 워커 수 / 최대치(server.tomcat.threads.max, 기본 200). 비율이 1.0에 붙어 있으면 그 뒤로는 전부 accept 큐에서 대기한다.
hikaricp.connections.pending
★ 지금 이 순간 커넥션을 못 얻어 멈춰 있는 스레드 수. 0보다 크다는 것 자체가 큐 대기의 직접 증거다.
hikaricp.connections.acquire
★ 커넥션 획득까지 걸린 시간(타이머). 이 값의 p99가 곧 대기 시간의 실측치이고, 사용자 체감과 가장 직결된다.
hikaricp.connections.usage
커넥션을 쥐고 있던 시간(타이머). 이 값이 크면 "쿼리가 느리거나, 트랜잭션 안에서 딴짓을 하고 있다".
hikaricp.connections.active / idle
대여 중 / 반납돼 있는 커넥션 수. idle=0이면서 pending>0이면 풀이 말랐다.
hikaricp.connections.timeout
획득 실패(타임아웃) 누적 횟수. 이 값이 오르기 시작하면 이미 사용자에게 에러가 나가고 있다.

지표 수집 체계가 없는 서버에서도 HikariCP 자신의 로그를 켜면 30초마다 상태를 찍어 준다.

로그 logging.level.com.zaxxer.hikari.pool.HikariPool=DEBUG
HikariPool-1 - Pool stats (total=10, active=10, idle=0, waiting=180)

waiting=180은 180개 스레드가 커넥션 하나를 얻으려고 줄 서 있다는 뜻이다. 이 한 줄이 보이면 수사는 거의 끝난 것이다.

java.sql.SQLTransientConnectionException:
  HikariPool-1 - Connection is not available, request timed out after 30000ms.

DB는 멀쩡한데 우리 풀이 비어 있는 상황이다. 메시지에 HikariPool-1이 박혀 있다는 것 자체가 범인이 풀 쪽이라는 표시다. 진짜 원인은 커넥션을 오래 쥐고 있는 누군가이고, 그 후보는 느린 쿼리 / 트랜잭션 안의 외부 호출 / 반납 누락 셋이다.

"DB가 죽었다"가 아니라 "DB에 도달할 티켓이 없다" — DB 지표를 먼저 보면 멀쩡해서 더 헤맨다

4. 왜 탑다운인가 — 비싼 도구를 나중에 쓴다

지도를 그렸으니 수사 순서를 정할 수 있다. 원칙은 하나다. 넓고 싼 것부터, 좁고 비싼 것을 나중에.

이 표에 아예 없는 것 — "코드를 열어서 읽어본다"

코드는 "이 구간이 느리다"가 확정된 뒤에 여는 것이고, 그 전에 여는 코드 읽기는 수사가 아니라 점(占)이다

면접에서 "일단 코드를 봤습니다"로 시작하면 여기서 감점이 난다. 반대로 "0단계에서 변경 이력부터 봤습니다"로 시작하면 그 자체가 방법론의 증거가 된다.

4단계 암기 — 변 · 지 · 구 · 프

변했나→ 지표→ 구간→ 프로파일

비유하면 지도의 축척을 한 단계씩 줄이는 것이다 — 위성사진(무엇이 변했나) → 항공사진(어느 계층) → 드론(어느 구간) → 현미경(어느 코드 줄). 현미경부터 들이대면 어디를 볼지 모른다.

5. 0단계 — "갑자기"라는 단어부터 수사한다

질문에 담긴 "갑자기"라는 단어가 이미 결정적인 단서다. 서버 코드는 스스로 변하지 않는다. 어제까지 200ms였던 API가 오늘 5초가 됐다면 그 사이에 무언가가 바뀐 것이고, 그 무언가를 찾는 것이 코드를 읽는 것보다 훨씬 빠르다.

변경 후보는 유한하다 — 8종을 "누가 바꿨나"로 3묶음

데이터 증가 — 가장 교활한 후보

배포도 없었고 트래픽도 그대로인데 어느 날 갑자기 느려지는 사고의 대부분이 여기서 나온다. 변한 것이 코드가 아니라 코드가 다루는 데이터의 양이라 저장소 이력에는 아무 흔적이 없다.

SQL 테이블 규모와 통계 갱신 시각을 한 번에 본다
-- last_autoanalyze가 며칠 전이면 옵티마이저가 낡은 통계로 계획을 세우고 있다는 뜻이다.
SELECT relname,
       n_live_tup                                AS live_rows,
       pg_size_pretty(pg_relation_size(relid))   AS heap_size,
       pg_size_pretty(pg_indexes_size(relid))    AS index_size,
       last_autoanalyze,
       last_autovacuum
  FROM pg_stat_user_tables
 ORDER BY pg_total_relation_size(relid) DESC

트래픽 패턴을 볼 때의 요령 — 두 그래프를 같은 시간축에 겹친다 요청량 그래프와 응답시간 그래프를 겹쳐 본다. 두 선이 같이 올라갔으면 용량 문제이고, 요청량은 그대로인데 응답시간만 올라갔으면 건당 처리 비용이 늘어난 것이다. 이 구분 하나로 대응 방향이 정반대로 갈린다 — 전자는 증설, 후자는 원인 제거다.
의존 서비스는 상대의 말이 아니라 우리 지표로 판정한다 상대가 알려주기를 기다리지 않는다. 우리 쪽에서 잰 외부 호출 응답시간 그래프가 우리의 증거다. 상대는 "우리는 정상입니다"라고 말할 수 있지만, 우리 쪽에서 잰 왕복 시간이 3배가 됐다면 그것이 사실이다. (상대 서버 처리 시간 + 네트워크 + 우리 쪽 커넥션 풀 대기가 전부 포함된 값이므로, 상대의 내부 지표와 다른 것이 오히려 자연스럽다.)

5-1. 0단계의 나머지 절반 — 영향 범위 확정

이 판정 하나가 수사 범위를 절반으로 접는다.

전체 API가 느리다 → 공유 자원을 의심

  • 톰캣 스레드풀
  • DB 커넥션 풀
  • GC / 힙
  • DB 자체
  • CPU · 네트워크 · 인프라

후보 목록이 짧다. 그래서 "전체가 느리다"는 나쁜 소식이지만 수사에는 좋은 소식이다.

특정 API만 느리다 → 그 API의 고유 경로를 의심

  • 그 엔드포인트의 쿼리 (실행계획 변화)
  • 그 엔드포인트의 외부 호출
  • 그 로직 (직렬화·반복 연산)
  • 그 캐시 키의 히트율

범위가 하나의 코드 경로로 좁혀지므로 2단계 구간 분해로 바로 내려갈 수 있다.

판정을 확실히 하는 한 가지 요령 DB를 전혀 쓰지 않는 엔드포인트(/health 같은 것)가 느린지 확인한다. 그것마저 느리면 원인은 확실히 공유 자원이다 — 그 코드 경로에는 쿼리도, 외부 호출도 없기 때문이다. 10절의 시나리오에서 이 한 가지 사실이 수사 범위를 통째로 접어 준다.

6. 1단계 — 모니터링: 지표로 계층을 좁힌다

요청이 지나가는 경로를 계층으로 그리고, 각 계층의 지표를 확인한다. 이때 큐가 어디에 있는지를 함께 그려 두는 것이 1~3절에서 얻은 교훈이다.

6-1. 지표는 두 계열로 나눠 본다 — RED와 USE

RED — 요청 관점 (사용자가 겪는 것)

  • Rate — 초당 요청 수
  • Errors — 에러율
  • Duration — 응답시간 (백분위로)

USE — 자원 관점 (자원이 겪는 것)

  • Utilization — 사용률
  • Saturation — 포화 정도 = 대기 큐의 길이
  • Errors — 에러

승부는 S(Saturation)에서 난다

Utilization만 보는 팀은 "CPU 30%인데 왜 느리죠?"에서 멈춘다
Saturation을 보는 팀은 "pending=180"을 보고 그 자리에서 답을 찾는다
계층별로 U와 S를 무엇으로 보는가 — S 열이 이 표의 핵심

6-2. Duration은 평균이 아니라 백분위로 본다

백분위(percentile)란 값을 오름차순으로 늘어놓았을 때 특정 위치의 값이다 — p99는 "100건 중 99번째로 느린 값", 즉 가장 느린 1%의 경계다. 왜 평균이 위험한지 숫자로 보자.

평균이 사람을 속이는 방식

100건의 응답시간: 99건이 50ms, 1건이 5,000ms

평균 = (99 × 50 + 1 × 5,000) ÷ 100 = (4,950 + 5,000) ÷ 100 = 99.5ms
p99  = 5,000ms
평균은 "99.5ms"라고 말하고, 실제로 5초를 기다린 사용자가 존재한다

평균은 소수의 느린 요청을 나머지에 녹여 버린다. 그리고 그 1%는 하루 100만 요청이면 1만 명이다.

p99만 튀고 p50은 그대로

일부 요청만 느리다. 후보: GC pause, 특정 파라미터(데이터 편중), 캐시 미스 경로, 간헐적 풀 대기, 특정 인스턴스 1대.

p50부터 p99까지 전부 함께 밀렸다

공유 자원이 포화됐다. 모든 요청이 같은 줄에서 기다리고 있다는 신호다. 6-1의 계층도에서 공유 상자 두 개를 먼저 본다.

6-3. 결정적 분기 — CPU가 높은가 낮은가

놓치기 쉬운 지표 — 캐시 히트율은 산수로 DB 부하가 된다

히트율이 떨어지면 그 차이만큼이 그대로 DB 부하로 전가된다.

히트율 95% → DB로 가는 조회 = 5%
히트율 80% → DB로 가는 조회 = 20%
                20 ÷ 5 = 4  →  DB 조회량이 4배

히트율이 15%p 떨어졌을 뿐인데 DB가 받는 부하는 4배가 된다. 캐시 서버 하나가 빠지거나 인기 키가 동시에 만료되는 순간 DB가 죽는 사고가 이 산수에서 나온다.

7. 2단계 — 구간 분해: 요청 한 건의 시간을 쪼갠다

계층을 좁혔으면 이제 요청 하나가 어디서 시간을 쓰는지 분해한다. 1절의 그림을 실제 데이터로 만드는 작업이다.

분산 트레이싱(distributed tracing)은 요청 하나에 고유한 추적 ID를 붙여 서비스와 구간마다 시작 시각·종료 시각을 남기고, 그것들을 ID로 다시 이어 붙여 하나의 타임라인으로 보는 기법이다. 이름의 "분산"은 요청이 여러 서비스를 거쳐도 ID가 따라다니므로 서비스 경계를 넘어 하나로 꿰맬 수 있다는 뜻이다.

span (스팬)
구간 하나. 이름, 시작 시각, 종료 시각, 부모 span의 ID를 가진다. "DB 쿼리 실행", "결제사 호출"이 각각 하나의 span이다. 이름이 span인 것은 시간축에서 차지하는 폭(span) 하나를 뜻하기 때문이다.
trace (트레이스)
같은 요청에 속한 span 전체의 묶음. 하나의 trace ID로 묶이고, span들의 부모-자식 관계가 트리를 이룬다. 시간축에 늘어놓으면 계단처럼 겹쳐 보여서 폭포수(waterfall)라고 부른다.

7-1. 추적 ID가 서비스 경계를 넘는 방법 — traceparent 헤더

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  │                                │                │
             │  │                                │                └ 플래그(샘플링 여부)
             │  │                                └ 이 요청을 보낸 쪽의 span ID (16자리 hex)
             │  └ trace ID (32자리 hex) — 요청 전체를 관통하는 하나의 ID
             └ 버전

W3C가 표준화한 헤더이고, 도구로는 Pinpoint, Scouter, Zipkin, Jaeger, Grafana Tempo 등이 있다. Spring Boot 3 계열이면 Micrometer Tracing이 표준 통로다.

로그와 트레이스를 연결해 두는 것도 필수다 로그 패턴에 trace ID를 박아 두면 "이 느린 요청의 로그만" 골라 볼 수 있다. 이게 없으면 트레이스에서 범인 요청을 찾아도 그 요청의 로그를 특정할 수 없다. 
# application.yml
logging:
  pattern:
    level: "%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]"

8-1. DB 쪽 두 수단은 역할이 다르다 — 둘 다 켠다

① 개별 사건 log_min_duration_statement
-- 지정 시간을 넘긴 개별 쿼리를 로그에 남긴다.
-- "어떤 파라미터의 어떤 쿼리가 느렸나"를 잡을 때.
ALTER SYSTEM SET log_min_duration_statement = '200ms';

-- 락 대기도 함께 남긴다. deadlock_timeout(기본 1초)보다
-- 오래 락을 기다린 세션을 로그에 남기므로,
-- 경합이 있었다는 사실 자체가 기록된다.
ALTER SYSTEM SET log_lock_waits = on;

SELECT pg_reload_conf();  -- 재기동 없이 반영
② 총량 pg_stat_statements
-- 쿼리를 정규화해 누적 통계로 쌓는다.
-- "전체 부하에서 어느 쿼리가 시간을 가장 많이 먹었나".
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT calls,
       round(total_exec_time::numeric)   AS total_ms,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       round(max_exec_time::numeric, 2)  AS max_ms,
       rows, shared_blks_hit,
       shared_blks_read,   -- 0이 아니면 디스크를 읽었다
       left(query, 70)                   AS query
  FROM pg_stat_statements
 ORDER BY total_exec_time DESC LIMIT 10;

왜 둘 다 봐야 하는가 — 10초 한 건 vs 50ms 10만 건

10초짜리 쿼리 한 건보다 50ms짜리 쿼리 10만 건이 DB를 더 괴롭힌다 (0.05 × 100,000 = 5,000초)

전자는 로그(log_min_duration_statement)에만 남고, 후자는 total_exec_time 상위에만 나타난다. 한쪽만 보면 반드시 한 종류를 놓친다.

SQL 지금 이 순간 DB에서 무슨 일이 벌어지는가
-- wait_event_type이 'Lock'이면 락 대기, 'IO'면 디스크 읽기 대기다.
SELECT pid,
       now() - query_start   AS duration,
       state,
       wait_event_type,
       wait_event,
       pg_blocking_pids(pid) AS blocked_by,   -- 나를 막고 있는 세션들
       left(query, 60)       AS query
  FROM pg_stat_activity
 WHERE state <> 'idle'
   AND pid <> pg_backend_pid()
 ORDER BY duration DESC;
답의 마무리로 반드시 붙일 한마디 "이번에 없어서 고생한 관측 수단을 도입하는 것까지가 대응의 마무리"라는 태도다. 같은 장애가 다시 오면 또 몇 시간을 쓸 것이고, 그것은 도구가 없어서가 아니라 도입하지 않아서다.

읽는 법은 used / total 비율이다. 위 예시는 3,982,336 ÷ 4,194,304 = 0.95, 즉 힙의 95%가 차 있다. 이 상태에서는 GC가 공간을 조금 확보하고 곧 다시 꽉 차므로 Full GC가 연발한다. 그동안 애플리케이션 스레드는 전부 멈추므로, 전체 API가 주기적으로 함께 느려지는 톱니 패턴이 나타난다.

9-5. CPU 프로파일러와 플레임 그래프

샘플링 프로파일러는 짧은 주기로 스레드 스택을 반복 채취해, 어떤 메서드가 스택에 자주 나타나는지로 CPU 점유를 추정한다. 모든 메서드 호출을 계측하는 방식과 달리 오버헤드가 낮아 운영 환경에서도 잠깐 붙일 수 있다.가산점

# 30초간 CPU 프로파일을 떠서 플레임 그래프 HTML로 만든다
./profiler.sh -d 30 -e cpu -f /tmp/flame.html <pid>

# 대기가 원인일 때는 wall-clock 모드를 쓴다. CPU 모드는 "CPU를 쓰는 시간"만
# 재므로, 기다리기만 하는 스레드는 그래프에 거의 나타나지 않는다.
./profiler.sh -d 30 -e wall -f /tmp/flame-wall.html <pid>

플레임 그래프 읽는 법 — 가로 폭

세로는 호출 스택의 깊이, 가로 폭은 그 메서드가 샘플에 등장한 비율 = 시간 점유율. 넓고 평평한 봉우리가 범인이다. 위에서 아래로 읽는 것이 아니라 넓은 곳을 찾아 그 아래로 파고드는 것이 사용법이다.

-e cpu 와 -e wall 을 잘못 고르면 빈 그래프를 본다

CPU 모드는 "계산하느라 느린" 경우를, wall-clock 모드는 "기다리느라 느린" 경우를 보여준다. 6-3의 분기에서 CPU가 낮았다면 반드시 wall 모드다 — cpu 모드로 뜨면 정작 병목인 대기 스레드가 안 보인다.

10-1. 남은 가설을 산수로 검산한다 — Little's Law

가설은 이제 하나다. "쿼리 하나가 3.1초로 느려져 커넥션 풀을 잠식했고, 그 결과 톰캣 워커 전체가 커넥션 대기로 소진되어 무관한 API까지 느려졌다."

Little's Law — L = λ × W

동시에 시스템 안에 있는 개수 L = 도착률 λ × 체류 시간 W

여기서는 "동시에 대여 중인 커넥션 수 = 초당 커넥션 요청 수 × 커넥션을 쥐고 있는 시간"으로 쓴다. (자세히: 17-littles-law-resource-limits.md)

평시 여유롭다
전체 유입             250 TPS
커넥션 평균 점유 시간   8ms = 0.008초

필요 커넥션 = 250 × 0.008 = 2개
풀 크기 10개  ->  여유. pending은 0이다.
장애 시 그 엔드포인트가 전체의 5%라면
그 엔드포인트 유입   250 × 0.05 = 12.5 TPS
커넥션 점유 시간      3.1초  (쿼리 실행 시간이 곧 점유 시간)

필요 커넥션 = 12.5 × 3.1 = 38.75개
풀 크기 10개  ->  필요량이 풀의 3.875배 (38.75 ÷ 10)
트래픽의 5%밖에 안 되는 엔드포인트 하나가 필요로 하는 커넥션이 풀 전체의 3.9배다 → 나머지 95%(237.5 TPS)는 커넥션을 아예 얻을 수 없다

가설이 검산으로 확인됐으니 마지막 질문 하나가 남는다. 왜 그 쿼리가 4ms에서 3.1초가 됐는가? EXPLAIN을 붙인다.

11-1. 그런데 왜 어제는 4ms였는가 — 절벽의 정체

테이블이 작았을 때 (100만 행, 사용자 1만 명)

한 사용자당 평균 100건. created_at 인덱스를 최신순으로 훑으면 수백 건 안에서 그 사용자의 20건이 모인다.

4ms — 테스트 통과

테이블이 커진 뒤 (1억 행, 사용자 300만 명)

한 사용자당 평균 33건이고, 최근 데이터에 그 사용자의 주문이 없다면 4,288만 건을 훑어야 20건이 모인다.

3.1초 — 사고

왜 테스트에서 절대 안 잡히는가

같은 쿼리, 같은 인덱스, 같은 코드. 바뀐 것은 데이터의 크기뿐이다

ORDER BY ... LIMIT은 "필요한 만큼만 읽고 멈춘다"는 최적화 때문에 작은 테이블에서 유난히 빠르게 보인다. 그래서 이 절벽은 운영 규모의 데이터가 있어야만 드러난다. (테스트가 이런 결함을 못 잡는 구조적 이유: 23-load-test-production-gap-causes.md)

함께 알아둘 변형 — 계획 자체가 바뀌는 경우 위 사례는 인덱스 스캔을 유지한 채 느려진 것이다. 이와 별개로 선택성이 나빠지면 플래너가 인덱스를 포기하고 Seq Scan으로 전환하기도 한다. 다른 사건이지만 원인은 같다 — 데이터가 커져서 원래 계획의 가정이 깨졌다. 그리고 통계가 낡았을 때도(대량 적재 후 ANALYZE가 안 돌았을 때) 플래너가 잘못된 계획을 고르는데, 이것은 pg_stat_user_tables.last_autoanalyze로 확인한다.
조치 조건에 맞는 복합 인덱스를 추가한다
-- WHERE user_id = ? ORDER BY created_at DESC LIMIT 20 에 맞춘 복합 인덱스.
-- 컬럼 순서가 중요하다: 등호 조건(user_id)이 앞, 정렬 기준(created_at)이 뒤.
CREATE INDEX CONCURRENTLY idx_orders_user_created
    ON orders (user_id, created_at DESC);

-- CONCURRENTLY: 인덱스를 만드는 동안 그 테이블에 대한 쓰기를 막지 않는다.
-- 1억 행 테이블에 이걸 빼고 만들면 인덱스 생성 시간 내내 INSERT/UPDATE가
-- 막혀, 병목을 고치려다 더 큰 장애를 만든다.

재발 방지가 조치의 절반이다. 이번 사고에서 배운 것을 지표와 알람으로 바꿔 놓는다.

이번 사고가 남긴 알람 목록 — 목적은 하나, "다음엔 유저보다 먼저 알기"

hikaricp.connections.acquire p99
사용자 영향과 가장 직결된 지표. 이 값이 곧 사용자가 추가로 기다린 시간이다.
pg_stat_statements.mean_exec_time 급증
쿼리별 회귀 감지. "어제 대비 N배"로 걸어 둔다.
log_min_duration_statement
켜 두어 느린 쿼리가 로그로 남게 한다. 사후 분석의 재료.
tomcat.threads.busy / max
1.0에 붙기 전에 알람. accept 큐로 넘어가면 이미 늦다.
테이블 규모 추이 대시보드
데이터 증가는 예측 가능한 사고다 — 절벽에 닿기 전에 알 수 있다.
포스트모템에 반드시 남길 질문 "왜 유저보다 먼저 몰랐는가." 이번 사고의 답은 "커넥션 풀 지표에 알람이 없었다"이고, 그것이 곧 위 목록이 된다. "무엇이 원인이었나"는 이번 사고를 설명하고, "왜 몰랐나"는 다음 사고를 막는다.

12-1. 그리고 병목은 사라지지 않는다 — 다음 지점으로 이동한다 가산점

쿼리가 3.1초  →  커넥션 풀(10개)이 병목  →  톰캣 워커(200개)가 다 묶임

인덱스 추가로 쿼리가 0.06ms가 되면
  →  커넥션 풀은 여유로워진다
  →  그러면 다음 한계는 무엇인가?
     톰캣 워커 200개? DB의 max_connections? 외부 API의 처리량? CPU?
제약 이론(theory of constraints): 병목 하나를 고치면 병목은 사라지지 않고 다음 지점으로 이동한다

비유 — 수도관에서 가장 좁은 마디를 넓히면 물은 더 나오지만, 그 순간 다른 마디가 새로 가장 좁은 곳이 된다. 그래서 "고쳤다"가 아니라 "이제 한계가 어디로 옮겨갔는지 확인한다"가 다음 문장이 되어야 한다.

면접에서 이 한 문장까지 가면 인상이 달라진다 "병목이 다음으로 이동했으니 다음 한계는 어디인지 부하 테스트로 확인하겠습니다"까지 말하면, 문제를 하나 고친 사람이 아니라 시스템의 용량 곡선을 이해하는 사람으로 보인다. (부하 테스트로 포화점을 찾는 방법: 07-load-test-design-tps-scenario-tools.md)

12-2. 그리고 같은 패턴을 한 번에 훑는다

이번에 (user_id) 인덱스가 없어서 터졌다면, 같은 패턴의 ORDER BY ... LIMIT 쿼리가 다른 테이블에 몇 개 더 있을 가능성이 높다. 하나를 고쳤을 때 같은 유형을 한 번에 점검하는 것이 비용 효율이 가장 좋은 시점이다 — 사고 직후는 팀이 그 패턴을 가장 잘 이해하고 있는 유일한 시기이기 때문이다.

13. 인출 카드 · 꼬리질문 셀프 테스트

13-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

수사 4단계 순서?
변 · 지 · 구 · 프 — 무엇이 변했나 → 지표로 계층 → 구간 분해 → 프로파일링. 코드 읽기는 이 순서에 없다.
두 개의 뺄셈?
① 앞단 − 앱 = 앱 앞의 큐 대기(워커 부족) ② 앱의 DB 구간 − DB 실행 시간 = DB 밖의 대기(커넥션 획득).
변경 후보 8종?
우리 3(배포·설정·라이브러리) · 저절로 2(데이터·트래픽) · 남 3(의존 서비스·인프라·배치).
RED / USE?
RED = Rate·Errors·Duration(요청 = 사용자가 겪는 것). USE = Utilization·Saturation·Errors(자원). 승부는 S에서 난다.
CPU 분기 한 줄?
CPU 높다 = 계산하느라 느리다(-e cpu). CPU 낮다 = 기다리느라 느리다(-e wall, 스레드 덤프). 이 한 줄로 범위가 절반.
스레드 덤프에서 볼 두 가지?
상태(RUNNABLE / BLOCKED / WAITING·TIMED_WAITING)와 스택 최상단. 상태는 "기다린다"까지, 최상단이 "무엇을".
왜 덤프를 3회 이상?
한 장으로는 지나가던 스레드와 갇힌 스레드를 구분할 수 없다. 3~5초 간격 3회 이상, 여러 장에 걸쳐 같은 지점이 진짜다.
풀 대기의 직접 증거 2종?
hikaricp.connections.pending(지금 멈춰 있는 스레드 수)과 acquire p99(대기 시간 실측). 로그로는 Pool stats ... waiting=180.
붕괴 산수 3줄?
12.5 × 3.1 = 38.75개 필요 → 10 ÷ 3.1 = 3.2 TPS만 소화 → 200 ÷ (12.5−3.2) ≈ 21.5초에 워커 전멸.
장애 진행 중, 원인 미상이면?
복구 먼저, 그러나 증거 보존과 함께. 덤프·풀 지표·pg_stat_activity를 30초에 뜨고 → 롤백·스케일·TTL 연장·기능 축소·부하 제한.

13-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

평균 응답시간은 정상인데 p99만 튄다면 어디를 보나요? 필수힌트: 후보를 "넷"으로 세고, 각각을 구분하는 관측 방법까지 붙인다

전체가 아니라 일부 요청만 느린 패턴이다. 6-2에서 본 백분위 해석의 왼쪽 갈래이고, 후보는 넷이다.

① 주기성이 있으면 GC pause나 배치다. p99 그래프가 일정 간격으로 톱니처럼 튄다면 무언가 주기적으로 도는 것이다 — Full GC, 캐시 갱신 배치, 백업, 통계 집계. jstat -gcutil로 GC 시각과 튀는 시각을 맞춰 보면 바로 갈린다.

② 특정 파라미터에서만 느리면 데이터 편중이다. 대형 고객사의 데이터가 비대해 그 고객의 요청만 느린 경우(hot data), 인기 상품 하나에 조회가 몰려 그 행의 락 경합이 생기는 경우. 느린 요청의 파라미터를 모아 공통점을 찾는다.

③ 캐시 미스 경로다. 히트는 2ms, 미스는 400ms라면 히트율 99%인 API의 p99는 사실상 미스 경로의 시간이다. 이 경우 p99를 낮추는 방법은 코드 최적화가 아니라 히트율을 올리거나 미스 경로 자체를 빠르게 만드는 것이다.

④ 풀의 간헐적 대기다. 평소에는 커넥션이 남지만 순간적인 유입 스파이크에 몇 건이 대기하는 경우. hikaricp.connections.acquire의 p99가 p50보다 훨씬 크면 이 패턴이다.

접근법은 "느린 요청만 골라 트레이스를 보는 것"이다. 대부분의 APM은 지연 상위 요청을 따로 모아 준다. 그 트레이스들의 공통 패턴 — 시간대 · 파라미터 · 특정 서버 인스턴스 · 특정 구간 — 을 찾으면 위 넷 중 하나로 떨어진다.

놓치기 쉬운 다섯째: 특정 인스턴스만 느린 경우 — 10대 중 1대가 느리면 그 요청이 전체의 10%라 p90~p99에 나타난다

서버별로 지표를 나눠 볼 수 있어야 이걸 잡는다. 전체 집계만 보면 "가끔 느리다"로만 보인다.

스레드 덤프는 왜 한 번이 아니라 여러 번 뜨나요?힌트: 스냅샷 한 장이 구분하지 못하는 두 종류의 스레드가 있다

덤프 한 장은 순간의 스냅샷이라, 그 순간 우연히 그 코드를 지나던 스레드와 병목에 갇힌 스레드를 구분할 수 없다.

100ms 만에 지나가는 정상 코드도, 스레드 200개가 계속 통과하고 있으면 스냅샷 한 장에는 몇 개가 찍힌다. 그것만 보고 "여기가 병목"이라고 판단하면 오진이다.

간격을 두고 여러 장을 떠서 여러 장에 걸쳐 같은 지점에 머무는 스레드를 찾아야 그것이 대기·블로킹의 실체다. 3초 뒤에도 같은 스레드가 같은 줄에 서 있다면 그 스레드는 최소 3초를 그 자리에서 보낸 것이고, 그건 우연이 아니다.

CCTV를 연속 캡처해 계속 같은 자리에 서 있는 사람을 찾는 것과 같다. 원리로 말하면 샘플링 프로파일러가 하는 일을 수동으로 하는 것이다 — 샘플링 프로파일러도 짧은 주기로 스택을 반복 채취해 자주 등장하는 지점을 병목으로 판정한다.

간격 3~5초, 횟수 3회 이상이 실무 기준

간격이 너무 짧으면 세 장이 거의 같은 그림이라 비교 의미가 없고, 너무 길면 그 사이에 상황이 바뀐다.

APM 같은 도구가 전혀 없는 환경이라면 어떻게 하시겠어요? 가산점힌트: "없어서 못 했다"가 아니라 "없으면 만든다"로 답한다. 그리고 마지막 한 문장

구간을 로그로 직접 만든다. 순서대로 답한다.

앞단은 액세스 로그다. nginx라면 $request_time, $upstream_connect_time, $upstream_header_time, $upstream_response_time을 로그 포맷에 넣는다. 이 네 값만 있어도 "클라이언트 구간 / 큐 대기 / 서버 처리"가 갈린다.

앱 내부는 단계별 타이머 로그다. 2-2의 After 코드처럼 DB·외부 호출·직렬화를 나눠 남긴다. 요청 ID를 MDC에 넣어 같은 요청의 로그를 묶는 것이 필수다 — 이게 없으면 동시 요청의 로그가 섞여 읽을 수 없다.

DB는 log_min_duration_statement와 pg_stat_statements다. 둘 다 재기동 없이(전자는 pg_reload_conf(), 후자는 확장 설치만) 켤 수 있다.

OS 레벨은 top/vmstat(CPU·메모리·컨텍스트 스위칭), iostat(디스크), ss -s(소켓 상태 요약), jstat -gcutil(GC).

JVM 내부는 jcmd다. Thread.print, GC.heap_info, GC.class_histogram은 JDK에 기본 포함이라 추가 설치가 없다.

"이번에 없어서 고생한 관측 수단을 도입하는 것까지가 대응의 마무리"

같은 장애가 다시 오면 또 몇 시간을 쓸 것이고, 그것은 도구가 없어서가 아니라 도입하지 않아서다.

느려진 원인을 못 찾고 있는데 장애는 진행 중입니다. 어떻게 하시겠어요? 시니어 변별힌트: 두 가지를 분리한다. 그리고 복구 "전에" 반드시 하는 일이 있다
원인 규명과 서비스 복구를 분리한다. 복구가 우선이다

이것이 핵심이고, 주니어와 갈리는 지점이다. "원인을 알아야 고칠 수 있다"는 생각은 자연스럽지만, 운영에서는 원인을 모른 채로도 실행할 수 있는 완화 조치들이 있다.

  • 최근 배포가 있었다면 원인 확정 전이라도 롤백. 롤백은 5분이고 원인 규명은 두 시간일 수 있다.
  • 스케일 아웃. 인스턴스를 늘리면 인스턴스당 부하가 줄어 시간을 번다. 단, 병목이 DB나 외부 API 같은 공유 자원이면 오히려 그쪽 부하를 늘려 악화시킨다 — 이 단서를 붙이는 것이 중요하다.
  • 캐시 TTL 연장. DB 부하를 줄이는 가장 빠른 카드다.
  • 비핵심 기능 차단(graceful degradation). 추천·통계·부가 알림을 끄고 핵심 경로만 살린다. (15-graceful-degradation-design.md)
  • 부하 제한(load shedding). 받을 수 있는 만큼만 받고 나머지는 빨리 거절한다. 전부 느려지는 것보다 일부를 확실히 처리하는 것이 낫다. (21-load-shedding-priority-and-location.md)

단, 복구 조치 전에 증거를 확보해 둔다. 이것이 답을 완성시키는 부분이다.

재기동하면 스레드 상태, 힙 내용, 풀 상태가 전부 초기화되어 사후 분석이 불가능해진다. 그리고 원인을 모른 채 복구하면 같은 장애가 반복된다.

인스턴스가 여러 대라면 더 좋은 방법이 있다 — 한 대만 트래픽에서 떼어 내고 살려 둔다. LB에서 빼면 사용자 영향은 없어지고, 그 인스턴스는 문제 상태를 그대로 유지한 채 마음껏 프로파일링할 수 있다. 나머지는 재기동해 서비스를 복구한다.

"복구 먼저, 그러나 증거 보존과 함께" — 운영 경험자의 답
병목을 찾아 고쳤습니다. 그다음은요?힌트: 셋으로 나눠 답하고, 마지막에 개념 하나를 얹는다

재발 방지의 체계화다. 셋으로 나눠 답한다.

① 이번에 범인이었던 지표에 알람을 건다. 목적은 하나 — 다음엔 유저보다 먼저 알기 위해. 12절의 목록이 그것이다. 알람 없는 개선은 "이번엔 운이 좋았다"에 가깝다.

② 포스트모템으로 "왜 몰랐는지"를 기록한다. 사고 보고서에서 "무엇이 원인이었나"보다 중요한 질문이 "왜 유저 문의를 통해 알았나"다. 앞의 질문은 이번 사고를 설명하고, 뒤의 질문은 다음 사고를 막는다.

③ 같은 패턴의 잠재 병목이 다른 곳에 없는지 점검한다. (user_id) 인덱스가 없어서 터졌다면 같은 패턴의 ORDER BY ... LIMIT 쿼리가 다른 테이블에도 있을 가능성이 높다. 하나를 고쳤을 때 같은 유형을 한 번에 훑는 것이 비용 효율이 가장 좋은 시점이다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

커넥션 풀을 10개에서 100개로 늘리면 되는 것 아닌가요? 함정힌트: Little's Law로는 40개면 된다. 그런데 늘리면 무엇이 이동하는가

병목이 사라지는 게 아니라 앱에서 DB로 옮겨간다. 이 답의 핵심은 "어디로 옮겨가는가"를 말하는 것이다.

① 산술적으로는 맞다. 10-1의 계산으로 필요량이 38.75개였으니 40개면 그 엔드포인트의 대기는 사라진다. 여기까지만 말하면 답이 절반이다.

② 그러면 3.1초짜리 쿼리 40개가 동시에 DB를 때린다. 지금은 풀이 10개라 앱이 의도치 않게 DB를 보호하고 있던 상태다. 풀을 늘리는 순간 DB의 CPU·디스크 I/O 경합이 커지고, 각 쿼리는 3.1초보다 더 느려진다 — 그러면 필요 커넥션이 또 늘어나는 악순환이 생긴다.

③ DB 쪽에도 상한이 있다. max_connections를 넘으면 연결 자체가 거부되고, 커넥션 하나마다 DB 서버 메모리가 붙는다. 그리고 앱 인스턴스가 10대면 풀 100개는 DB 입장에서 1,000개다.

풀 크기는 "앱 스레드 수"가 아니라 "DB가 동시에 실제로 일할 수 있는 양"에 맞춘다

진짜 답은 점유 시간을 줄이는 것이다. Little's Law L = λ × W에서 우리가 건드릴 수 있는 것은 L(풀 크기)만이 아니라 W(점유 시간)이고, W를 3.1초에서 0.06ms로 줄이면 필요 L이 38.75개에서 사실상 0에 가까워진다. 인덱스 하나가 풀 90개보다 낫다.

덧붙일 한 줄 — 임시 완화로 풀을 조금 늘리는 것 자체는 유효한 카드다. 다만 "근본 조치가 아니라 시간 버는 카드"라고 분류해서 말해야 한다.

hikaricp.connections.pending은 계속 0인데 acquire p99는 200ms입니다. 지표가 잘못된 건가요? 시니어 변별힌트: 둘은 종류가 다른 지표다 — 하나는 게이지, 하나는 타이머

둘 다 맞다. 재는 방식이 다를 뿐이다.

pending은 게이지(gauge) — 수집기가 값을 읽어가는 그 순간의 스냅샷이다. 수집 주기가 15초라면 그 15초 사이에 벌어진 200ms짜리 대기는 그냥 안 보인다. 9-3의 스레드 덤프가 순간 스냅샷인 것과 같은 한계다.

acquire는 타이머(timer) — 모든 획득 시도의 소요 시간을 빠짐없이 기록해 분포로 쌓는다. 그래서 짧고 잦은 대기는 게이지에는 안 잡히고 타이머의 p99에만 나타난다.

게이지는 "지금 몇 명이 줄 서 있나", 타이머는 "줄에서 얼마나 기다렸나" — 후자가 사용자 체감에 직결된다

실무 결론 — 알람은 acquire p99에 걸고, pending은 "지금 상황이 심각한가"를 보는 실시간 보조 지표로 쓴다. pending > 0이 스크레이프에 잡혔다면 이미 상당히 지속적인 대기라는 뜻이다.

이 구분은 백분위 지표 전반에 똑같이 적용된다 — "순간값 지표가 0이니 문제없다"는 판단이 위험한 이유다.

스레드 덤프를 떴더니 RUNNABLE이 대부분인데 CPU는 20%입니다. 모순 아닌가요? 함정힌트: JVM이 구분하지 못하는 것이 하나 있다

모순이 아니다. RUNNABLE은 "CPU를 쓰고 있다"가 아니다.

JVM의 RUNNABLE은 "JVM 입장에서 실행 가능한 상태"일 뿐이고, OS 레벨에서 블로킹된 소켓 읽기는 JVM이 구분하지 못한다. 그래서 외부 API 응답을 기다리며 소켓에서 멈춰 있는 스레드도 RUNNABLE로 찍힌다.

상태만 보면 속는다 — 반드시 스택 최상단을 함께 본다

판정 방법 — 최상단이 SocketRead·read0·epollWait 계열이면 실제로는 기다리는 중이다. 반대로 우리 도메인 코드나 직렬화 라이브러리가 최상단에 있고 여러 장의 덤프에서 그 위치가 계속 바뀐다면 진짜로 CPU를 쓰고 있는 것이다.

더 확실한 방법 — CPU가 낮은데 느리면 플레임 그래프를 -e wall로 뜬다. -e cpu로 뜨면 기다리는 스레드는 샘플에 거의 안 잡혀 그래프가 텅 비어 보인다.

거꾸로, OS의 스레드별 CPU 사용량(top -H)과 덤프의 nid(네이티브 스레드 ID)를 대조하면 "진짜로 CPU를 쓰는 스레드"만 골라낼 수 있다.

DB를 쓰지 않는 /health가 느리다는 사실이 왜 그렇게 강력한 단서인가요? 필수힌트: 이 사실 하나가 "지우는 것"의 목록을 세어 본다

그 요청이 지나가지 않는 모든 경로를 한 번에 배제하기 때문이다.

/health는 쿼리도, 외부 호출도, 캐시 조회도 하지 않는다. 그런데도 느리다면 느려진 원인은 그 셋 중 어느 것도 아니다. 남는 것은 모든 요청이 반드시 통과하는 지점 — 즉 6절 계층도의 왼쪽 공유 상자들뿐이다.

후보가 "전부"에서 "공유 자원 몇 개"로 한 번에 접힌다 — 톰캣 워커 · 커넥션 풀 · GC · CPU · 네트워크 · 인프라

그다음 갈래도 바로 나온다. /health는 커넥션 풀도 쓰지 않으므로, "커넥션 풀이 원인인데 왜 /health까지 느린가?"라는 질문이 자연스럽게 생기고, 그 답이 10절의 21초 메커니즘이다 — 워커 스레드가 전부 커넥션 대기에 묶여서 /health는 워커를 배정받지 못하고 accept 큐에서 기다린다.

실무 팁 — 그래서 의존성을 전혀 타지 않는 초경량 엔드포인트를 하나 두고 지표를 따로 수집해 두면, 장애 때 "공유 자원인가 개별 경로인가"를 즉시 판정하는 리트머스가 된다. 헬스체크를 DB 조회로 만들면 이 판정 능력을 잃는다.

EXPLAIN과 EXPLAIN ANALYZE는 뭐가 다르고, 운영 DB에 ANALYZE를 붙여도 되나요? 가산점힌트: 한쪽은 실제로 실행한다

EXPLAIN은 실행하지 않고 옵티마이저의 계획과 추정치만 보여준다. EXPLAIN ANALYZE는 쿼리를 실제로 실행하고 실측치(actual time, rows, loops)를 함께 보여준다.

병목 추적에서는 실측이 필요하다. 11절의 Rows Removed by Filter: 42,881,903은 실제로 실행해 봐야만 나오는 값이고, 추정 행 수와 실제 행 수의 괴리가 곧 "통계가 낡았다"는 증거가 된다.

BUFFERS를 반드시 같이 붙인다. shared hit(메모리에서 찾음)과 shared read(디스크에서 읽음)의 비율이 "느린 이유가 I/O인가"를 바로 알려준다.

주의: ANALYZE는 실제로 실행한다 — 3초짜리 쿼리는 3초를 실제로 먹고 커넥션도 그동안 점유한다

DML에는 트랜잭션으로 감싼다. UPDATE·DELETE에 EXPLAIN ANALYZE를 붙이면 데이터가 진짜 바뀐다. BEGIN; → EXPLAIN (ANALYZE) ... → ROLLBACK;으로 감싸는 것이 관행이다.

장애 중이라면 느린 쿼리에 ANALYZE를 붙이는 것 자체가 부하를 더한다. 이럴 때는 읽기 복제본이나 스테이징에서 같은 쿼리를 돌려 계획을 보는 편이 안전하다 — 단, 데이터 분포와 통계가 다르면 계획도 다를 수 있다는 단서를 붙여야 한다.

트레이스 샘플링을 1%로 걸어 뒀습니다. 정작 느린 요청을 놓치지 않나요? 시니어 변별힌트: "언제 샘플링 여부를 결정하는가"가 갈림길이다

맞다. 기본 방식으로는 놓친다. 그리고 이 질문의 핵심은 "결정 시점"이다.

앞에서 결정하는 방식(head-based)은 요청이 시작되는 순간 주사위를 굴려 이 트레이스를 남길지 정한다. 그래서 느린 요청이든 빠른 요청이든 똑같이 1%만 남는다 — 하필 그 느린 한 건이 버려질 확률이 99%다. 앞서 본 traceparent의 마지막 플래그가 바로 이 결정을 하위 서비스로 전파하는 자리다(그래야 한 요청의 트레이스가 반쪽만 남는 일이 없다).

뒤에서 결정하는 방식(tail-based)은 트레이스가 끝난 뒤 "느렸는가 / 에러였는가"를 보고 남길지 정한다. 정확히 보고 싶은 것만 남길 수 있지만, 판정할 때까지 모든 span을 어딘가에 모아 두어야 하므로 수집 인프라 비용이 커진다.

"싸지만 눈이 나쁜 앞쪽 결정" vs "정확하지만 비싼 뒤쪽 결정"

실무 절충 셋 — ① 에러와 느린 요청은 무조건 남기는 규칙을 얹는다. ② 중요한 엔드포인트만 샘플링율을 올린다. ③ 지표는 100%로 수집한다 — 트레이스를 샘플링해도 p99·에러율 같은 집계 지표는 전량 기반이어야 "느려졌다"는 사실 자체를 놓치지 않는다.

정리하면 "탐지는 지표로 100%, 원인 추적은 트레이스로 표본"이라는 역할 분담이다. 이걸 말하면 관측 체계를 설계해 본 사람으로 들린다.

p50부터 p99까지 전부 밀렸는데, 이번엔 CPU도 90%입니다. 10절과 뭐가 달라지나요?힌트: 6-3 분기의 반대편으로 간다. 그리고 CPU를 올리는 범인 목록이 따로 있다

"공유 자원 포화"까지는 같고, 그 자원이 커넥션 풀이 아니라 CPU라는 점이 다르다. 6-3 분기의 왼쪽으로 간다.

먼저 갈라야 하는 것은 "누가 CPU를 쓰는가"다. 후보는 둘이다 — 애플리케이션 스레드인가, GC 스레드인가. jstat -gcutil로 FGC 횟수와 FGCT(누적 시간)가 함께 뛰었으면 GC다. 이 경우 CPU가 높은 것은 결과이고 원인은 메모리 압박이라, 힙 사용 추이와 O 영역 회수 여부를 봐야 한다(9-4).

GC가 아니라면 -e cpu 플레임 그래프를 뜬다. 넓고 평평한 봉우리가 범인이고, 실무에서 자주 나오는 것은 과도한 직렬화/역직렬화, 백트래킹이 심한 정규식, 대량 객체 생성을 유발하는 N+1, 로그 과다 출력, 압축·암호화다.

CPU가 높을 때의 확인 순서: GC인가 → 아니면 어느 메서드인가 → 그 메서드를 왜 그렇게 자주 호출하는가

그리고 0단계를 다시 본다. CPU가 갑자기 오른 경우도 "무엇이 변했나"가 유효하다 — 배포로 직렬화 대상이 커졌거나, 로그 레벨이 DEBUG로 바뀌었거나, 응답 페이로드가 커졌거나.

주의할 오답 하나 — "CPU가 높으니 스케일 아웃"은 요청당 CPU 비용이 늘어난 경우에는 돈만 더 쓰고 원인을 덮는다. 5절에서 본 "요청량 그래프와 응답시간 그래프를 겹쳐 보기"로 용량 문제인지 건당 비용 문제인지를 먼저 가른다.

구간 로그를 남기려고 코드마다 타이머를 심는 건 너무 지저분하지 않나요?힌트: "지저분함"의 대안이 무엇인지, 그리고 어디까지 심어야 하는지

맞는 지적이고, 그래서 순서가 있다.

① 먼저 이미 있는 것을 켠다. 대부분의 구간은 손으로 심지 않아도 이미 계측되고 있다 — http.server.requests(요청 전체), hikaricp.connections.acquire(커넥션 대기), HTTP 클라이언트의 요청 타이머, 그리고 액세스 로그. 2-2의 수동 타이머는 이것들로 안 잡히는 구간이 남았을 때의 수단이다.

② 그다음이 트레이싱이다. Micrometer Tracing 같은 통로를 붙이면 DB 호출·HTTP 호출·메시지 소비 같은 주요 경계에 span이 자동으로 생긴다. 손으로 심는 코드는 "우리 도메인 로직 안의 구간"에만 남는다.

③ 그래도 손으로 심어야 한다면 범위를 좁힌다. 모든 메서드가 아니라 "경계"에만 — 외부 시스템 호출 앞뒤, 무거운 계산 앞뒤. 내부 호출 하나하나에 타이머를 다는 것은 오히려 노이즈다.

원칙: "모든 곳을 재는 것"이 아니라 "다음 질문에 답할 수 있을 만큼만 나누는 것"

기준은 명확하다 — 이 로그를 보고 "그다음 어디를 볼지"가 정해지면 충분하고, 안 정해지면 한 칸 더 쪼갠다. 2-2의 Before가 실패한 이유가 정확히 "다음 행선지를 정해주지 못해서"였다.

느려진 게 우리 서버가 아니라 클라이언트나 네트워크일 수도 있지 않나요? 어떻게 가릅니까?힌트: 3-1 표에 이미 답이 있다. 그리고 어디서 재느냐가 핵심이다

nginx의 두 값 차이로 즉시 갈린다.

rt($request_time) − urt($upstream_response_time)가 크다 = 업스트림은 빨리 응답했는데 클라이언트로 내보내는 데 오래 걸렸다

이 경우 원인은 느린 클라이언트(모바일 네트워크), 큰 응답 본문, 클라이언트 쪽 혼잡이고 서버를 뒤질 일이 아니다. 반대로 urt 자체가 크면 서버 안의 문제다.

더 근본적인 구분 — 서버에서 잰 지연시간과 클라이언트에서 잰 지연시간은 애초에 다른 값이다. 서버 지표에는 DNS 조회, TCP 핸드셰이크, TLS 협상, 클라이언트 큐잉, 렌더링이 빠져 있다. 서버 p99가 80ms인데 사용자는 700ms를 겪는 상황은 아주 정상적으로 발생한다.

그래서 실무 결론은 — 서버 지표만으로는 사용자 체감을 알 수 없으므로 클라이언트 쪽 계측(RUM 같은 실사용자 측정)을 별도로 두고, 두 값을 나란히 본다. 둘의 차이가 곧 "우리가 손댈 수 없는 구간"의 크기다. (지연시간 지표 전반: 01-throughput-latency-p99.md)

장애 상황에서 빠르게 가르는 요령 하나 — 같은 리전 내부에서 curl로 직접 호출해 본다. 그게 빠르면 서버는 정상이고 경로 문제다.

한 줄 요약
병목 추적은 "무엇이 변했나" 확정 → 지표(RED/USE)로 계층 좁히기 → 트레이스로 구간 분해 → 프로파일링으로 내부 확인의 탑다운 수사이며, 매 단계에서 다음 행선지를 정하는 것은 추측이 아니라 측정된 데이터다 — 그리고 이 수사에서 가장 자주 놓치는 구간은 애플리케이션 로그에 잡히지 않는 큐 대기(톰캣 워커 대기, 커넥션 풀 대기)이므로, 앞단이 잰 시간과 앱이 잰 시간의 차이, 그리고 앱이 잰 DB 구간과 DB가 잰 실행 시간의 차이를 반드시 확인해야 "느린 쿼리 하나가 공유 자원을 잠식해 전 API가 연대책임을 지는" 구조를 21초 안에 읽어낼 수 있다.
