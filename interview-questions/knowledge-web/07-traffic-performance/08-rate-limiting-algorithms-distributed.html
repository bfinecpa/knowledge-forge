Rate Limiting 알고리즘과 분산 구현
로컬 카운트의 합은 전체 한도가 아니다

면접 질문: "Rate limiting 알고리즘(token bucket, sliding window)을 비교해주세요. 분산 환경에서는 어떻게 구현하나요?"

핵심 관전 포인트 — Rate limiting은 호출자별로 "단위 시간당 허용 요청 수"라는 계약을 강제하는 유입 제어다. 평상시에도 항상 켜져 있고, 한도는 사전에 정해진 값이며, 대상은 호출자별이다 — 이 셋이 load shedding·백프레셔와 갈리는 지점이다. 알고리즘은 "짧은 몰아치기를 허용할 것인가"라는 정책 질문으로 갈린다: token bucket은 장기 평균 속도를 충전률로 제한하면서 통의 크기만큼 순간 버스트를 허용하고, sliding window는 버스트 없이 구간 총량을 일정하게 누른다. Fixed window는 가장 단순하지만 구간이 리셋되는 경계에서 한도의 정확히 2배가 뚫리므로 실무에서 단독으로 쓰지 않는다. 분산 환경의 본체는 세 가지다 — ① 서버별 로컬 카운트의 합은 전체 한도와 같아지지 않는다(나눠 주면 남기면서 거절하고, 넉넉히 주면 서버 대수만큼 뚫린다), ② 카운터를 Redis로 중앙화해도 "읽고 나서 쓰는" 두 단계 사이에 다른 요청이 끼어들어 한도를 넘긴다 — INCR의 반환값으로 판정하거나 Lua 스크립트로 판정과 갱신을 한 덩어리로 묶어야 한다, ③ 요청마다 원격 왕복이 붙고 Redis가 단일 장애점이 되므로 "얼마나 정확해야 하는가"를 먼저 정하고 동기 중앙 카운터와 로컬 근사 중에서 고른다. 그리고 429는 던지는 것으로 끝이 아니다 — Retry-After와 남은 한도를 함께 내려야 거절이 재시도 폭풍으로 되돌아오지 않는다.
  • 1
    Rate limiting은 호출자별 사전 계약을 평상시에도 집행하는 유입 제어다 — 발동은 항상, 기준은 사전에 정해진 한도, 대상은 호출자별. 과부하 때만 발동하는 load shedding(503), 상류를 감속시키는 백프레셔와는 별개 계층이고 서로 보완재다.
  • 2
    알고리즘은 "버스트를 허용할 것인가" 한 질문으로 갈린다 — token bucket은 충전률(장기 평균)과 통 크기(순간 버스트)라는 손잡이 두 개로 분리 제어하고, sliding window는 구간 총량을 눌러 평탄화한다. fixed window는 경계에서 정확히 2배가 뚫려 단독 사용이 부적합하다.
  • 3
    분산의 본체는 세 가지 — 합이 안 맞고(로컬 카운트의 합 ≠ 전체 한도), 틈이 남고(중앙화해도 check-then-act 경쟁 조건 → INCR 반환값·Lua로 원자화), 값을 치른다(원격 왕복 지연 + 단일 장애점 → 정확성 요구를 먼저 정하고 fail open/closed를 명시). 429에는 Retry-After를 실어 거절이 새 부하가 되지 않게 한다.

0. 질문 + 출제 의도

질문: "Rate limiting 알고리즘(token bucket, sliding window)을 비교해주세요. 분산 환경에서는 어떻게 구현하나요?"

출제 의도: 알고리즘 비교보다, 분산 환경에서 "서버별 로컬 카운트의 합이 전체 한도를 넘는" 문제를 인지하는지가 핵심이다. 단일 서버에서 동작하던 지식을 분산으로 확장할 때 무엇이 깨지는지를 보는 사고 실험 — 정합성(정확한 한도)과 성능(요청마다 원격 호출) 사이의 트레이드오프를 설계로 다룰 수 있는지 드러난다.

이 페이지가 겨냥하는 약점 세 가지 ① 알고리즘 이름만 나열하고 끝나는 것("토큰 버킷은 버스트를 허용하고 슬라이딩 윈도는 정확합니다") → 4~6절에서 숫자를 넣어 한 단계씩 계산해 보이고, 7절에서 "버스트가 정당한 사용 패턴인가"라는 한 질문으로 선택을 유도한다.
② "Redis에 카운터를 두면 됩니다"에서 멈추는 것(이 질문의 진짜 승부처를 지나침) → 9절에서 중앙화해도 남는 check-then-act 경쟁 조건을 타임라인으로 못 박고, 원자적 연산이 왜 해결책인지까지 내려간다.
③ 거절 이후를 설계하지 않는 것(429만 던지고 끝) → 2절에서 Retry-After가 없으면 거절 자체가 새 부하가 되는 되먹임을, 10절에서 Redis 장애 시 fail open/closed를 "정하지 않은 상태로 두지 않는다"까지 다룬다.

1. 좌표 잡기 — 유입 제어 장치는 셋이고, 서로 다른 질문에 답한다

이 장에는 이름이 다른데 하는 일이 비슷해 보이는 장치가 셋 있다. Rate limiting, load shedding, 백프레셔다. 셋 다 "들어오는 요청을 그대로 다 받지 않는다"는 점이 같아서 자주 뒤섞이는데, 실은 서로 다른 질문에 답하는 별개의 계층이다. 이 문서를 읽는 동안 계속 대조가 되므로 먼저 갈라 두자.

Rate limiting — 계약을 지킨다
"API 키당 초당 100회"라는 값을 미리 정해 두고, 시스템이 한가하든 붐비든 그 값을 집행한다. 판단 기준은 사전에 정해진 숫자, 대상은 호출자별(API 키·사용자 ID·IP).
Load shedding — 과부하일 때만 버린다
판단 기준이 사전 값이 아니라 실시간 부하 지표(큐 길이, in-flight 요청 수, 응답시간)이고, 대상은 호출자가 아니라 우선순위가 낮은 요청. 평상시에는 아무 요청도 버리지 않는다.
백프레셔 — 거절 대신 늦춘다
하류가 처리할 수 있는 속도를 상류에 되전달해 유입 속도를 하류의 처리 속도에 맞춘다. 거절이 아니라 감속이 기본 동작이라는 점이 앞의 둘과 다르다.

세 장치를 가르는 축 — 한 줄로 꿰기

Rate limiting = 계약· Load shedding = 과부하· 백프레셔 = 감속
"계약은 항상 · 사전 값 · 호출자별 / 과부하는 그때만 · 실시간 지표 · 우선순위별 / 감속은 늘 · 하류 속도 · 상류 자체"

셋을 나란히 못 대면 "429와 503의 차이"에서 막힌다. 429는 "당신이 너무 많이 보냈다"(계약 위반), 503은 "지금 우리가 감당할 수 없다"(서버 과부하) — 원인이 누구에게 있는지가 다르고, 클라이언트의 대응도 달라져야 한다.

2. 무엇을 지키는가, 그리고 429 응답을 어떻게 설계하는가

2-1. 지키는 것은 서버 자원이 아니라 클라이언트 간 공정성

Rate limiting이 보호하는 것을 "서버 자원"이라고만 답하면 절반이다. 서버 자원 보호는 load shedding이 더 직접적으로 하는 일이고, rate limiting이 고유하게 하는 일은 한 호출자의 폭주가 다른 호출자의 몫을 잠식하지 못하게 막는 것이다.

구체적으로 무엇을 막는지 보면 분명해진다. 클라이언트 한 곳의 버그 루프(재시도 로직을 잘못 짜서 초당 수천 건을 쏘는), 악의적 크롤링, 잘못 설정된 배치가 흔한 범인이다. 이때 서버 전체 용량에는 여유가 있어도 그 한 클라이언트가 커넥션 풀이나 특정 테이블의 락을 독점하면 다른 클라이언트는 느려진다. 한도를 호출자별로 걸면 폭주의 영향이 그 호출자 안에 갇힌다.

비유 — 놀이공원의 "1인당 하루 입장 1회" 공원이 한가하든 붐비든 규칙은 항상 적용된다. 한 사람이 하루에 스무 번 들어와 자리를 차지하는 것을 막는 규칙이지, 공원이 꽉 찼을 때 입장을 통제하는 규칙이 아니다. 후자는 load shedding이 하는 일이다.

2-2. 429는 던지는 것으로 끝이 아니다 — 거절이 새 부하가 되는 되먹임

한도를 넘긴 요청에는 HTTP 429 (Too Many Requests) 를 반환한다. 그런데 상태 코드만 던지면 설계가 미완성이다. 클라이언트 입장에서 429는 "지금은 안 된다"까지만 알려 주고 "언제 다시 오면 되는지"를 알려 주지 않기 때문이다. 알 수 없으면 클라이언트가 할 수 있는 유일한 행동은 즉시 다시 시도하는 것이고, 그러면 거절 응답 자체가 새로운 부하가 된다.

429만 던지는 경우 — 되먹임 고리가 닫힌다

  • 클라이언트: "언제 되지?" → 모른다 → 즉시 재시도
  • 서버: 429를 또 만든다 (커넥션·TLS·필터 비용은 이미 지불)
  • 거절량이 늘수록 재시도가 늘고, 재시도가 늘수록 거절이 는다
  • 결과: 리미터가 켜져 있는데도 부하가 오른다

정보를 실어 내리는 경우 — 고리가 끊긴다

  • Retry-After: "이만큼 뒤에 오라" → 무의미한 재시도가 사라진다
  • X-RateLimit-Remaining을 성공 응답에도 실어 준다
  • 클라이언트가 벽에 닿기 전에 스스로 속도를 줄인다
  • 결과: 거절 자체가 줄어든다

429에 함께 실어야 할 것 — 4종

Retry-After
언제 다시 오면 되는지. 초 단위 정수(Retry-After: 5) 또는 HTTP 날짜. 표준 응답 헤더.
X-RateLimit-Limit
얼마가 당신의 한도인지.
X-RateLimit-Remaining
남은 여유. 성공 응답에도 내리는 것이 핵심.
X-RateLimit-Reset
리셋되는 시각.

암기 연상: "언제 · 얼마 · 남은 · 리셋". 뒤의 세 개는 표준으로 확정된 헤더가 아니라 사실상의 관행(대형 API들이 쓰는 형태)이라 이름은 조직마다 조금씩 다르다. 중요한 것은 이름이 아니라 "성공 응답에도 함께 내린다"는 점이다 — 429가 난 뒤에야 알려 주면 클라이언트는 벽에 부딪히고 나서야 벽의 위치를 알게 된다.

필터 429를 던지는 지점 — 상태 코드만 던지지 않고 "언제, 얼마나"를 함께 내린다
@Component
public class RateLimitFilter extends OncePerRequestFilter {

    private final RateLimiter limiter;   // 9~10절에서 만드는 Redis 기반 리미터

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws IOException, ServletException {
        String key = resolveKey(req);        // API 키 > 사용자 ID > IP 순으로 (11절 꼬리질문 참고)
        Decision d = limiter.tryConsume(key);

        // 한도와 남은 여유는 통과했을 때도 내린다. 그래야 클라이언트가
        // 벽에 부딪히기 전에 스스로 속도를 줄일 수 있다.
        res.setHeader("X-RateLimit-Limit", String.valueOf(d.limit()));
        res.setHeader("X-RateLimit-Remaining", String.valueOf(d.remaining()));
        res.setHeader("X-RateLimit-Reset", String.valueOf(d.resetEpochSeconds()));

        if (!d.allowed()) {
            // Retry-After가 없으면 클라이언트가 할 수 있는 일은 즉시 재시도뿐이고,
            // 그러면 거절 응답이 그대로 새 부하가 된다. 이 한 줄이 그 되먹임을 끊는다.
            res.setHeader("Retry-After", String.valueOf(d.retryAfterSeconds()));되먹임 차단
            res.setStatus(429);
            res.setContentType("application/json");
            res.getWriter().write("{\"error\":\"rate_limit_exceeded\"}");
            return;
        }
        chain.doFilter(req, res);
    }
}
이 요구가 알고리즘 선택에도 영향을 준다 Retry-After를 계산할 수 있어야 한다는 요구는 공짜가 아니다. Fixed window라면 "현재 구간이 끝나는 시각까지"로 간단히 나오지만, token bucket이라면 "토큰 1개가 충전될 때까지 남은 시간"을 충전률로 계산해야 한다. 뒤에서 알고리즘을 볼 때 이 값을 뽑을 수 있는지도 같이 보자.

3. 어휘 3종 — 알고리즘 이름이 곧 자료 구조다

알고리즘 네 개의 이름에 낯선 단어가 셋 들어 있다. 이름이 곧 자료 구조를 가리키므로 먼저 정의하면 나머지가 쉽다.

버킷 (bucket, 통)
허용량을 담아 두는 그릇. 안에 들어 있는 것을 토큰이라 부르고, 요청 하나가 토큰 하나를 꺼내 쓴다. 통이 비면 더 못 쓴다. "허용량을 미리 통에 담아 둔다"는 발상 때문에 붙은 이름.
윈도 (window, 창)
"카운트를 세는 시간 구간". 분당 100회면 윈도 길이가 1분. 시계에 맞춰 고정하면 fixed, 지금 시각을 따라 계속 움직이면 sliding. 창을 고정하느냐 미끄러뜨리느냐가 두 계열을 가르는 전부.
로그 (log, 기록부)
요청이 올 때마다 그 시각을 한 줄씩 적어 두는 목록. 애플리케이션 로그 파일과는 무관하고, "언제 요청이 왔는지를 전부 적어 놓은 대장"에 가깝다.

이름 = 설명 — 네 알고리즘을 이름만으로 복원하기

이름이름을 그대로 풀면한 단어 별명
Token bucket토큰 통통
Fixed window counter고정 구간의 카운터칸
Sliding window log미끄러지는 구간 + 요청 기록부대장

암기: 통 · 칸 · 대장 · 비율 — 통에 담고, 칸으로 자르고, 대장에 다 적고, 비율로 추산한다

4. ① Token bucket — 평균은 제한, 순간 몰아치기는 허용

Token bucket에는 통 하나가 있다. 통에는 토큰이 일정 속도로 계속 떨어지고(예: 초당 10개), 요청 하나가 도착하면 토큰 하나를 꺼내 쓴다. 꺼낼 토큰이 없으면 그 요청은 거절된다. 통에는 크기 상한이 있어서(예: 100개) 그 이상은 담기지 않고 넘치는 토큰은 그냥 버려진다.

두 손잡이가 각각 정하는 것

rate (충전률)

4-1. 게으른(lazy) 충전 — 타이머 없이 같은 결과를 만드는 계산

구현상의 장점은 상태가 아주 작다는 것이다. 키당 값 두 개, 즉 (남은 토큰 수, 마지막으로 계산한 시각)만 있으면 된다. 그리고 토큰을 실제로 초당 10번 떨어뜨리는 타이머는 필요 없다. 요청이 올 때 경과 시간만큼 게으르게 계산하면 결과가 같다.

남아 있던 기록: ts = 12:00:00.0, tokens = 30  ·  지금 요청이 도착: now = 12:00:02.5

1
경과 시간 = 12:00:02.5 − 12:00:00.0 = 2.5초
2
그 사이 충전됐어야 할 양 = 2.5초 × 10개/s = 25개
3
tokens = min(capacity, 30 + 25) = min(100, 55) = 55개 — 상한을 넘지 않게 min으로 자른다
4
요청 1건이 토큰 1개를 쓴다 → 54개 남기고 통과
5
(tokens=54, ts=12:00:02.5) 로 갱신
타이머 스레드도, 초당 10번의 쓰기도 필요 없다 — "지난번 이후 흐른 시간"만 알면 결과가 동일하다
Retry-After가 이 구조에서 바로 나온다 토큰이 0개라면 1개가 충전되기까지 1 ÷ rate 초, 즉 초당 10개 충전이면 0.1초다. 소수점 이하는 헤더로 표현할 수 없으니 올림해 1초를 내려 주면 된다.

5. ② Fixed window counter — 가장 단순하지만 경계에서 정확히 2배가 뚫린다

Fixed window counter는 시계를 고정된 구간으로 자르고, 구간마다 카운터 하나만 증가시킨다. "매 분 100회"라면 10:00~10:01 구간의 카운터, 10:01~10:02 구간의 카운터를 따로 세고, 분이 바뀌면 새 카운터가 0에서 시작한다.

구현이 압도적으로 쉽다. Redis 키를 ratelimit:{apiKey}:{yyyyMMddHHmm}처럼 시각을 포함해 만들고 INCR만 하면 끝이며, 구간이 지나면 키가 TTL로 저절로 사라진다. 그런데 실무에서 이것을 단독으로 쓰지 않는 이유가 하나 있고, 그 하나가 결정적이다.

왜 "정확히" 2배인가 — 근거까지 말할 수 있어야 한다

어떤 슬라이딩 구간을 잡아도 그 구간은 고정 구간 두 개에만 걸칠 수 있고, 각 고정 구간이 허용하는 최대는 한도만큼이다. 따라서 최악의 경우가 한도 × 2이고 그 이상은 되지 않는다.

Fixed window의 실질 한도 = 명목 한도 × 2

반대로 말하면 이 방식을 쓸 거라면 애초에 한도를 절반으로 잡아야 계약이 지켜진다. 그러면 평상시에는 필요 이상으로 조이는 셈이 된다 — 이것이 "단독으로 쓰지 않는다"의 진짜 이유다.

비유 — 도서관의 "하루 3권 대출" 자정 직전에 3권을 빌리고 자정이 지나자마자 또 3권을 빌리면, 몇 분 사이에 6권을 손에 쥐게 된다. 규칙은 어긴 적이 없는데 규칙이 의도한 상태는 깨졌다.

6. ③④ Sliding window — 정확한 log와 절충안 counter

6-1. ③ Sliding window log — 정확하지만 비싸다

Sliding window log는 근사 없이 정확하게 계산하는 방식이다. 요청이 올 때마다 그 시각을 기록부에 한 줄 적고, 판정할 때는 "지금부터 과거 1분" 안에 있는 줄의 개수를 센다. 창이 지금 시각을 따라 계속 미끄러지므로 5절의 경계 문제가 원천적으로 없다.

Redis라면 정렬된 집합(sorted set)이 자연스러운 자료 구조다. 점수(score)를 타임스탬프로 두고, 판정 전에 창 밖으로 나간 항목을 ZREMRANGEBYSCORE로 잘라내고 ZCARD로 개수를 센다.

6-2. ④ Sliding window counter — log의 근사, 실무 절충안

Sliding window counter는 log의 정확성과 fixed window의 저렴함 사이를 잇는다. 발상은 이렇다. 기록부를 통째로 들고 있지 않고, 고정 구간 카운터 두 개(이전 구간과 현재 구간)만 들고 있으면서, 슬라이딩 창이 이전 구간과 겹치는 비율만큼만 이전 카운트를 인정한다.

숫자로 한 단계씩

주어진 값: 이전 구간 카운트 80 · 현재 구간 카운트 20 · 한도 100 · 현재 구간 경과 15초

1
현재 구간의 경과 비율 = 15초 ÷ 60초 = 0.25
2
이전 구간과 겹치는 비율 = 1 − 0.25 = 0.75  (= (60 − 15) ÷ 60 = 45 ÷ 60)
3
이전 구간의 기여분 = 80 × 0.75 = 60
4
추정 카운트 = 60 + 20 = 80
5
80 < 100 이므로 통과. 남은 여유 = 100 − 80 = 20건

6-3. 이 근사는 언제, 어느 방향으로 틀리는가 시니어 변별

이 계산에는 숨은 가정이 하나 있다. "이전 구간 안에서 요청이 시간에 걸쳐 고르게 분포했다"는 가정이다. 80건을 0.75로 곱한다는 것은 "80건이 60초에 골고루 흩어져 있었으니 그중 75%가 겹치는 구간에 있을 것"이라고 본다는 뜻이다. 실제 분포가 한쪽에 몰려 있으면 틀린다. 양쪽 방향을 각각 숫자로 확인하자.

방향 1: 과소 추정 — 한도를 넘겨 통과시킨다

상황: 이전 구간 카운트 = 100인데, 그 100건이 전부 10:00:50~10:01:00 (마지막 10초) 에 몰려 있었다.

  • 추정 = 100 × 0.75 + C = 75 + C → 추정이 한도 100에 닿을 때까지 통과하므로 C는 25까지 올라간다
  • 진짜 [10:00:15 ~ 10:01:15) 안의 실제 요청 수는:
    · 이전 구간의 100건은 전부 10:00:50 이후 = 창 안 → 100건
    · 현재 구간 → 25건
    · 합계 → 125건
  • 1분 창에 125건 통과 = 한도 100의 25% 초과

원인: 창 안에 실제로 100건이 있는데 0.75를 곱해 75건으로 과소 계산했다 (25건을 놓쳤다).

방향 2: 과대 추정 — 여유가 있는데 거절한다

상황: 이전 구간 카운트 = 100인데, 그 100건이 전부 10:00:00~10:00:10 (첫 10초) 에 몰려 있었다.

  • 진짜 [10:00:15 ~ 10:01:15) 안의 실제 요청 수:
    · 이전 구간의 100건은 전부 10:00:15 이전 = 창 밖 → 0건
    · 현재 구간 → C건
  • 그런데 추정 = 75 + C → C가 25가 되는 순간 막힌다
  • 실제로는 25건만 쓴 사용자가 한도 100 중 25에서 거절당한다

원인: 창 밖에 있는 100건을 75건이 창 안에 있다고 과대 계산했다.

오차의 상한과 방향

오차 상한 = 이전 구간 카운트 × (1 − 겹치는 비율)  →  위 예에서는 100 × 0.25 = 25건

방향은 이전 구간의 요청이 창 안쪽에 몰려 있었으면 과소 추정(넘겨서 통과), 창 밖쪽에 몰려 있었으면 과대 추정(여유가 있는데 거절)이다. 이 오차를 어떻게 볼 것인가가 판단이다 — 남용 방지 목적이라면 최악에도 25% 초과는 충분히 받아들일 만하다(fixed window의 최악인 100% 초과와 비교하면 훨씬 낫고, 메모리는 카운터 두 개로 끝난다). 반면 과금이나 보안 한도라면 이 근사를 쓰지 않고 log 계열로 간다.

7-1. Leaky bucket — 거절이 아니라 지연 가산점

Leaky bucket(새는 통) 도 함께 언급할 수 있다. Token bucket과 이름이 비슷하지만 통에 담기는 것이 다르다. Token bucket의 통에는 허용량(토큰) 이 담기지만, leaky bucket의 통에는 요청 자체가 담긴다. 그리고 통 아래의 구멍에서 요청이 일정 속도로 새어 나가며 처리된다.

8. 분산 ① 로컬 카운트의 합은 전체 한도와 같아지지 않는다

여기가 이 질문의 본체다 앞 절의 알고리즘은 모두 "카운터(또는 토큰 수)가 한 곳에 있다"는 전제 위에 서 있다. 서버가 여러 대가 되면 그 전제가 무너지고, 무너지는 방식이 세 가지다 — 8절 합이 안 맞고, 9절 틈이 남고, 10절 값을 치른다.

각 서버가 자기 메모리에서 카운트하면 어떤 일이 생기는지 숫자로 따라가 보자. 전체 한도가 초당 1,000건이고 서버가 10대라고 하자. 가장 자연스러운 발상은 "그럼 서버당 100건으로 나눠 주자"다.

여기서 반대 방향으로도 생각해 봐야 한다. "거절이 아까우니 서버당 한도를 넉넉히 주자"는 발상은 더 나쁜 결과를 낸다.

서버당 한도 = 1,000건 (= 전체 한도)으로 넉넉히 준 경우

  • 클라이언트가 초당 1,000건을 보내고 10대에 고르게 분산 → 서버마다 100건 도착 → 전부 통과 → 합계 1,000건. 여기까지는 우연히 맞다.
  • 그런데 초당 10,000건을 보내면 → 서버마다 1,000건 도착 → 각 서버가 모두 "내 한도 이내"라고 판정 → 10,000건 전부 통과 = 전체 한도의 10배
로컬 판정의 최악 통과량 = 서버 대수 × 서버당 한도

"같은 키를 항상 같은 서버로 보내면(sticky·일관 해싱) 되지 않나?" — 반문과 대가

  • ① 서버가 늘거나 줄면 키의 목적지가 바뀌고, 그 순간 새 서버는 카운트를 0에서 시작하므로 한도가 리셋된다
  • ② 트래픽이 큰 키가 특정 서버에 고정되어 부하가 편중된다
  • ③ LB의 분배 정책과 리미터의 정확성이 결합되어, LB 설정을 바꿀 때마다 리미터의 동작이 바뀐다

원리적으로는 맞지만 대가가 셋 붙는다.

이 절의 결론 — 한 문장으로 박아두기

로컬 판정은 나눠 주면 남기면서 거절하고, 넉넉히 주면 서버 대수만큼 뚫린다

사이의 어떤 값을 골라도 두 오차가 동시에 존재하고, 분배 비율이 배포·스케일링·커넥션 재수립에 따라 계속 변하므로 값을 고정할 근거도 없다. 나눠 갖기는 근사조차 어렵다. → 그래서 결론은 카운터를 공유 저장소(대표적으로 Redis)로 중앙화해서 전 서버가 하나의 한도를 보게 하는 것이다.

9. 분산 ② 중앙화해도 남는 경쟁 조건 (check-then-act)

카운터를 Redis에 두었다고 문제가 끝나지 않는다. 코드를 그대로 옮기면 새로운 결함이 생긴다.

Before 읽기와 쓰기가 두 명령으로 분리된 구현 — 경쟁 조건
Long count = redis.get(key);          // ① 현재 카운트 조회
if (count != null && count >= limit) {
    return reject();                  // ② 조회한 값으로 판정
}
redis.incr(key);                      // ③ 증가세 번의 왕복
// ①에서 읽은 값을 근거로 ②에서 판정하고 ③에서 반영한다.
// 세 단계가 별개의 왕복이므로 그 사이에 다른 서버가 끼어들 수 있다.

이 패턴을 check-then-act(확인한 뒤 행동)라고 부른다. 확인한 시점의 값과 행동하는 시점의 값이 다를 수 있다는 것이 결함의 본질이다. 타임라인으로 보면 어디서 어긋나는지 정확히 보인다.

비유 — 같은 좌석표를 동시에 본 두 사람 둘 다 화면에서 "A12 빈자리"를 확인하고, 각자 "내가 앉겠다"고 누른다. 화면을 본 시점과 누른 시점 사이에 상대가 끼어들었다. 좌석은 하나인데 예약은 둘이 됐다.

9-1. 해법의 방향은 하나 — 판정과 갱신을 하나의 명령으로 합친다

가장 간단한 합치기는 판정의 근거를 "읽은 값"에서 "INCR의 반환값"으로 바꾸는 것이다. INCR은 증가시킨 뒤의 값을 돌려주므로, 두 요청이 동시에 호출해도 각자 다른 숫자를 받는다.

Before 읽은 값으로 판정 — 틈이 있다
Long count = redis.get(key);
if (count != null && count >= limit) {
    return reject();
}
redis.incr(key);

// 각자 통과 판정을 내린다.
// → 한도 100에 101건 통과
After 1단계 INCR의 반환값으로 판정 — 틈이 없다
Long count = redis.incr(key);  // 증가+획득 = 1명령
if (count == 1L) {
    redis.expire(key, 60);  // 첫 증가일 때만 TTL

if (count > limit) {

// t5/t6의 두 요청은 각각 100과 101을 받는다.
// 같은 값을 두 번 받는 일이 원리적으로 없으므로
// → 101번째는 반드시 거절된다

원자적 연산이 왜 문제를 해결하는가 — 한 문장

읽기와 쓰기가 하나의 명령으로 합쳐지면 그 사이에 다른 요청이 끼어들 수 있는 틈이 사라진다

8절이 "카운터가 여러 곳에 있다"는 문제였다면, 9절은 "한 곳에 있어도 보는 시점과 쓰는 시점이 다르다"는 문제이고, 해결 수단이 원자적 연산이다.

9-2. 그런데 위 코드에도 아직 구멍이 하나 남아 있다 함정

INCR과 EXPIRE가 두 번의 왕복이라는 점이다.

t1
INCR key → 1 — 키가 새로 생성됐다. Redis의 INCR은 TTL을 설정하지 않는다.
t2
★ 여기서 프로세스가 죽거나 Redis 연결이 끊긴다 — EXPIRE를 못 보냈다
t3
키는 TTL 없이 영구히 남는다 → 이 구간 카운터가 영원히 리셋되지 않는다 → 그 클라이언트는 한도를 넘긴 카운터를 짊어진 채 영구 차단된다
두 명령으로 나뉘는 순간 다시 원자적이지 않아진다

가벼운 해법 — 만드는 명령에 TTL을 실어 보낸다

SET key 0 EX 60 NX

  • 키가 없을 때만(NX) TTL과 함께 0으로 만들고, 이미 있으면 아무것도 하지 않는다
  • 이 명령 자체가 원자적이고 여러 번 실행해도 결과가 같다
  • 그다음 INCR을 부르면 TTL이 없는 키가 생길 수 없다

근본 해법 — 필요한 모든 단계를 Lua 스크립트 하나로

Lua가 왜 원자적인가 — 이유는 단순하다.

  • Redis는 명령을 단일 스레드로 하나씩 처리한다
  • EVAL로 들어온 스크립트를 그 자체로 하나의 명령처럼 취급해 끝까지 실행한 뒤에야 다음 클라이언트의 명령을 처리한다
  • 그래서 스크립트 안의 여러 redis.call 사이에는 어떤 요청도 끼어들 수 없다

Token bucket처럼 읽기·계산·쓰기가 여럿 필요한 알고리즘은 사실상 Lua가 유일한 답이다.

After 2단계 token bucket 전체를 Lua 스크립트 하나로 묶는다
// Redis가 이 스크립트를 하나의 명령처럼 단일 스레드에서 끝까지 실행하므로,
// 안쪽의 HMGET / 계산 / HMSET 사이에 다른 서버의 요청이 끼어들 수 없다.
String script = """
    local tokens_key = KEYS[1]
    local rate = tonumber(ARGV[1])      -- 초당 충전량 (4절의 rate)
    local capacity = tonumber(ARGV[2])  -- 통의 크기 (4절의 capacity = 허용 버스트)
    local now = tonumber(ARGV[3])       -- 호출자가 넘긴 현재 시각(초)

    local data = redis.call('HMGET', tokens_key, 'tokens', 'ts')
    -- 처음 보는 키라면 통이 꽉 찬 상태에서 시작한다.
    -- 그래야 "한동안 안 쓴 클라이언트는 버스트를 쓸 수 있다"는 정책과 일치한다.
    local tokens = tonumber(data[1]) or capacity
    local ts = tonumber(data[2]) or now

    -- 4-1의 게으른 충전. 타이머 없이 경과 시간만으로 같은 결과를 만든다.
    tokens = math.min(capacity, tokens + (now - ts) * rate)

    local allowed = tokens >= 1
    if allowed then tokens = tokens - 1 end

    redis.call('HMSET', tokens_key, 'tokens', tokens, 'ts', now)
    -- 유휴 키를 남겨 두면 키 수가 사용자 수만큼 무한히 누적된다.
    -- 통이 꽉 차는 데 걸리는 시간(capacity/rate)보다 넉넉히 잡으면
    -- 만료로 사라진 키를 "꽉 찬 통"으로 다시 시작해도 정책이 어긋나지 않는다.
    redis.call('EXPIRE', tokens_key, 60)키 무한 누적 방지
    return allowed and 1 or 0
    """;
눈여겨볼 것 — now를 "호출자가 넘긴다" 스크립트 안에서 Redis의 시각을 읽는 대신 애플리케이션의 시각을 넘기는 구현이 흔한데, 그러면 서버 간 시계 오차가 그대로 판정에 섞인다. 반대로 Redis의 시각을 쓰면 오차는 없지만 복제본에 스크립트를 재생할 때 결과가 달라질 수 있다는 별개의 제약이 붙는다. 어느 쪽이든 시각의 출처를 하나로 통일하는 것이 원칙이다.

10. 분산 ③ 중앙화의 비용 — 정확성 vs 성능·가용성

중앙화로 정확성을 얻었지만 대가를 두 개 지불했다.

비용 1 — 모든 요청에 네트워크 왕복 하나
요청 경로에 붙는 지연이므로 p99 응답시간에 그대로 드러난다.
비용 2 — Redis가 단일 장애점(SPOF)
Redis가 흔들리면 정상 트래픽까지 판정을 받지 못한다.

선택지 셋 — 무엇을 사고 무엇을 파는가

① 동기 중앙 카운터
요청마다 Redis에 물어보고 답을 기다린다. 가장 정확. 초과 1건이 곧 비용이나 위험인 한도(과금 API, 로그인 시도 제한 같은 보안 한도)에 쓴다. 대가는 요청 경로의 원격 호출.
② 로컬 카운터 + 주기적 동기화
로컬로 즉시 판정하고, 짧은 주기로 중앙에 자기 소비량을 보고하면서 전체 소비량을 받아 와 로컬 한도를 재조정한다. 주기 동안의 오차를 허용하는 대신 요청 경로에서 원격 호출을 뺀다.
③ 게이트웨이 계층 일괄
각 애플리케이션이 아니라 API 게이트웨이 한 층에서 공통 적용. 정책이 한 곳에 모인다. 다만 게이트웨이가 아는 정보는 경로·헤더·토큰 수준이라 도메인 지식이 필요한 한도("이 사용자의 구독 등급에 따른 한도")는 애플리케이션에 남는다 — 실무에서는 두 층을 겹쳐 쓴다.

10-1. 반드시 함께 정해야 하는 것 — Redis 장애 시의 동작 가산점

fail open은 판정을 못 하면 통과시키는 것이고, fail closed는 판정을 못 하면 거절하는 것이다. 어느 쪽이 맞는지는 이 리미터가 무엇을 지키고 있느냐로 갈린다.

남용 방지 목적의 리미터 → fail open

비교할 손실

  • (한도가 잠깐 안 걸려 초과 통과)
  • vs (전 사용자에게 서비스 거절)

후자가 압도적으로 크다. 리미터가 서비스를 죽이는 원인이 되면 안 된다.

보안 한도 (비밀번호 시도 제한 등) → fail closed

비교할 손실

  • (로그인이 잠깐 안 됨)
  • vs (무제한 비밀번호 대입 허용)

후자가 훨씬 크다. 판정을 못 하면 막는 것이 맞다.

실무에서 가장 흔한 형태 — "정하지 않은 상태"

예외를 잡지 않아 500이 나가거나, 잡아서 통과시키면서 그 결정을 아무도 모르는 상태. 이 선택을 코드에 명시적으로 남기는 것까지가 설계다.

fail open / fail closed는 "고르는" 것이지 "그렇게 되는" 것이 아니다
After 장애 시 동작을 "정하지 않은" 상태로 두지 않는다
try {
    return limiter.tryConsume(key);
} catch (RedisConnectionFailureException e) {
    // 이 리미터가 지키는 것이 남용 방지이므로 fail open을 택한다.
    // 다만 통과시켰다는 사실은 반드시 지표로 남긴다 —
    // "리미터가 사실상 꺼져 있었다"를 나중에 알 수 있어야 하기 때문이다.

    return Decision.allowedByFailOpen();

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

Rate limiting을 가르는 3축?
항상 · 사전 한도 · 호출자별(429). Load shedding은 과부하일 때만 · 실시간 지표 · 우선순위별(503). 백프레셔는 늘 · 하류 속도 · 상류 감속.
알고리즘 4종 별명?
통 · 칸 · 대장 · 비율 — token bucket(통), fixed window(칸), sliding window log(대장=기록부), sliding window counter(비율).
Token bucket 두 손잡이와 공식?
rate = 장기 평균 상한, capacity = 순간 버스트 양. 임의 T초 구간 최대 통과량 = capacity + rate × T.
Fixed window의 최악과 그 이유?
한도의 정확히 2배. 어떤 슬라이딩 구간도 고정 구간 두 개에만 걸치고 각각이 한도만큼 허용하기 때문. → 실질 한도 = 명목 × 2.
Sliding window counter 오차 상한?
이전 카운트 × (1 − 겹치는 비율). 이전 구간의 요청이 창 안쪽에 몰렸으면 과소 추정(넘겨 통과), 창 밖쪽이면 과대 추정(여유 있는데 거절).
분산에서 깨지는 것 3개?
합 · 틈 · 값 — ① 로컬 카운트의 합이 전체 한도와 다르다, ② 중앙화해도 check-then-act 틈이 남는다, ③ 왕복 지연 + SPOF라는 값을 치른다.
로컬 판정의 두 실패 방향?
나눠 주면 남기면서 거절하고(여유 400 + 거절 400), 넉넉히 주면 서버 대수만큼 뚫린다(최악 = 서버 수 × 서버당 한도).
원자화 수단 2개?
INCR의 반환값으로 판정(카운터 계열) · Lua 스크립트로 판정+갱신을 한 덩어리로(token bucket처럼 읽기·계산·쓰기가 여럿일 때).
429에 실을 것 4종?
언제 · 얼마 · 남은 · 리셋 = Retry-After / X-RateLimit-Limit / -Remaining / -Reset. 핵심은 성공 응답에도 남은 여유를 내리는 것.
Redis 장애 시 기준?
남용 방지 → fail open(서비스를 죽이면 안 된다), 보안 한도 → fail closed(판정을 못 하면 막는다). 어느 쪽이든 지표로 남긴다.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

Rate limiting과 load shedding은 뭐가 다른가요? 왜 둘 다 필요합니까? 필수힌트: 세 축으로 가른 다음, "둘 다 필요한 이유"를 숫자로 만든다

1절의 세 축으로 답한다. Rate limiting은 호출자별 사전 계약을 평상시에도 항상 집행하는 것이다(대상: 호출자별, 기준: 사전에 정해진 한도, 발동: 항상). Load shedding은 시스템의 현재 과부하 상태를 실시간 지표로 감지해 우선순위가 낮은 요청부터 버리는 자기 방어다(대상: 우선순위가 낮은 요청, 기준: 실시간 부하 지표, 발동: 과부하일 때만).

왜 둘 다 필요한지가 이 질문의 핵심이다. 모든 클라이언트가 각자의 계약을 완벽히 지켜도 전체 유입 합계가 처리 용량을 넘을 수 있다. 클라이언트 100곳에 각각 초당 100건을 허용했다면 계약상 합계는 초당 10,000건이고, 우리 용량이 5,000건이라면 아무도 계약을 위반하지 않은 상태에서 과부하가 성립한다. Rate limiting은 이 상황을 감지하지도, 막지도 못한다. 그래서 shedding이 별도 계층으로 필요하다.

응답 코드가 다른 것도 여기서 나온다. 429는 "당신이 너무 많이 보냈다"(계약 위반), 503은 "지금 우리가 감당할 수 없다"(서버 과부하)라는 뜻이므로, 원인이 누구에게 있는지가 다르고 클라이언트의 대응도 달라져야 한다.

마무리: "두 층은 대체재가 아니라 보완재이고, 여기에 경계마다의 백프레셔까지 셋을 계층으로 쌓는 것이 완성형입니다."
429를 받은 클라이언트는 어떻게 동작해야 하나요? 필수힌트: "재시도한다"로 끝나면 안 된다. 세 가지를 덧붙일 수 있다

Retry-After 헤더(또는 X-RateLimit-Reset 류)를 존중해 그 시각 이후에 재시도해야 한다. 이 헤더 없이 429만 주면 클라이언트가 즉시 재시도를 반복해 거절 자체가 부하가 되는 역설이 생긴다. 서버는 남은 한도(X-RateLimit-Remaining)를 성공 응답에도 함께 내려 클라이언트가 스스로 속도를 조절하게 돕는 것이 좋은 API 설계다.

한 걸음 더 — 세 가지를 덧붙인다.

① 지터가 필요하다. Retry-After가 있어도 여러 클라이언트가 같은 시각을 받으면 그 시각에 몰려 다시 벽을 친다. 그래서 클라이언트는 헤더 값에 무작위 지터(jitter)를 얹어 흩어져야 한다.

② 재시도 상한이 필요하다. 429는 재시도해도 되는 실패이지만 무한 재시도는 안 된다 — 상한을 두고, 넘으면 사용자에게 실패를 알리거나 큐에 넣어 나중에 처리하는 폴백을 준비해야 한다.

③ 벽에 닿기 전에 줄인다. 매 응답의 X-RateLimit-Remaining을 보고 남은 여유가 줄면 클라이언트가 먼저 감속하는 것이 가장 좋은 동작이다. 429는 이미 늦은 신호다.

알고리즘마다 Retry-After는 어떻게 계산합니까? 필수힌트: "계산할 수 있는가"가 알고리즘 선택의 숨은 조건이었다

알고리즘이 들고 있는 상태에서 그대로 유도된다.

Token bucket — 토큰이 0개면 1개가 충전되기까지 1 ÷ rate 초. 초당 10개 충전이면 0.1초이고, 헤더는 소수점을 표현할 수 없으니 올림해 1초를 내린다. 일반화하면 ⌈(1 − tokens) ÷ rate⌉.

Fixed window — 현재 구간이 끝나는 시각까지. 가장 계산하기 쉽다(키에 시각이 들어 있으므로 뺄셈 한 번).

Sliding window log — 가장 오래된 항목이 창 밖으로 나가는 시각까지. 정렬된 집합의 최솟값 + 윈도 길이 − 현재 시각. 기록부를 들고 있으니 정확한 값이 나온다.

Sliding window counter — 추정 카운트가 한도 밑으로 떨어지는 시각을 겹침 비율의 감소로 역산한다. 근사이므로 이 값도 근사다.

포인트: "Retry-After를 뽑을 수 있는가"는 알고리즘 선택의 조건 중 하나다 — 뽑을 수 없으면 거절 설계가 미완성으로 남는다.
Token bucket의 버스트 허용이 오히려 문제가 되는 경우는? 필수힌트: "평균 속도"와 "순간 동시성"은 다른 축이다

통 크기만큼의 요청이 한 순간에 하류(DB, 외부 API)로 쏟아진다. 하류가 순간 동시성에 약하면(커넥션 풀이 작으면) 평균으로는 한도 이내인데 순간 스파이크로 하류가 흔들린다. 이 경우 통 크기를 줄이거나 sliding window로 총량을 평탄하게 누르는 게 맞다.

핵심 프레임은 "평균 속도"와 "순간 동시성"이 다른 축이라는 것이다. 4절의 계산으로 말하면, 충전률 10개/s는 장기 평균을 눌러 주지만 통 크기 100은 "어느 순간이든 100건이 동시에 들어올 수 있다"를 뜻한다. 하류의 커넥션 풀이 25개라면 나머지 75건은 풀 앞에서 대기하고, 그 대기가 곧 지연이다.

한 문장으로: "리미터의 통 크기는 하류가 동시에 감당할 수 있는 양을 보고 정하는 값입니다."

이 대기가 바로 백프레셔가 다루는 문제이므로, 여기서 백프레셔로 자연스럽게 넘어갈 수 있다. 아니면 leaky bucket을 꺼내 "하류에 도달하는 속도를 평탄화하는 쪽으로 바꾼다"고 답해도 좋다.

사용자별 한도는 어떤 키로 잡나요? 필수힌트: IP 하나로 답하면 과잉 차단 함정에 걸린다. 그리고 "키를 누가 정하는가"가 남는다

인증된 트래픽은 사용자 ID나 API 키, 비인증 트래픽은 IP가 기본이다. 그런데 IP는 NAT이나 모바일 게이트웨이 뒤에서 다수 사용자가 공유될 수 있어 한 사람의 폭주로 같은 IP의 무고한 사용자들이 함께 막히는 과잉 차단 위험이 있다. 반대로 IP를 쓰지 않으면 인증 없이 때리는 트래픽을 전혀 제어할 수 없다.

그래서 실무에서는 계층화한다. "IP당 넉넉한 한도(봇·스캐너 방어) + 사용자당 정밀 한도(공정성)" 처럼 키가 다른 리미터를 겹쳐 쓰고, 요청은 두 리미터를 모두 통과해야 한다. 여기에 "엔드포인트별 한도"를 한 축 더 얹는 것도 흔하다 — 조회 API와 결제 API의 적정 한도가 같을 이유가 없기 때문이다.

키 설계에서 반드시 짚을 한 가지

키를 클라이언트가 정하게 두면 안 된다

클라이언트가 보낸 헤더 값을 그대로 키로 쓰면 값을 바꿔 가며 한도를 무한히 얻을 수 있다. 키는 서버가 검증한 정보(인증 토큰에서 꺼낸 사용자 ID, 신뢰할 수 있는 프록시가 붙인 클라이언트 IP)에서만 만든다.

정확한 한도 보장과 낮은 지연 중 하나를 포기해야 한다면? 시니어 변별힌트: "목적에 따라 다르다"에서 멈추지 말고 숫자를 붙인다

목적에 따라 갈린다는 프레임으로 답한다. 남용 방지나 트래픽 평탄화가 목적이면 근사를 택한다 — 로컬 판정 + 주기 동기화로 오차 몇 퍼센트를 허용하고 요청 경로에서 원격 호출을 뺀다. 반면 요금 부과 한도나 보안 한도처럼 초과 1건이 곧 비용이나 위험이면 동기 중앙 카운터를 쓰고 지연을 받아들인다.

관점: "rate limiter는 원래 방어선이지 회계 장부가 아니다" — 정확성 요구 수준을 먼저 묻고 그다음에 설계를 고르는 순서 자체가 시니어의 답이다.

여기에 숫자를 붙이면 더 좋다.

평균 20ms인 API
요청당 Redis 왕복 1ms → 5% 지연 증가. 충분히 받아들일 만하다.
평균 3ms인 초저지연 API
같은 1ms가 33% 증가. 결론이 완전히 달라진다.

같은 트레이드오프도 기준 응답시간에 따라 결론이 바뀐다는 것까지 말할 수 있으면 계산으로 판단하는 사람으로 보인다.

거절된 요청도 카운터에 넣습니까? 함정힌트: 알고리즘마다 답이 다르고, 한쪽은 "영구 차단"처럼 보이는 증상을 만든다

알고리즘에 따라 갈리고, 이것을 의식하지 않으면 이상한 증상이 나온다.

카운터 계열(INCR 기반) — 판정 근거가 INCR의 반환값이므로 거절된 요청도 카운터를 올린다. 폭주 중인 클라이언트는 그 구간 내내 카운터가 계속 올라가 구간이 끝날 때까지 계속 막힌다. 다만 구간이 지나면 리셋되므로 영구 차단은 아니다. 여기서 놓치기 쉬운 것이 응답 헤더다 — limit − count가 음수가 되므로 0으로 잘라(clamp) 내려야 한다.

Token bucket — 9절의 Lua를 보면 if allowed then tokens = tokens - 1 end이다. 즉 거절될 때는 토큰을 빼지 않는다. 그래서 거절이 상태를 더 나쁘게 만들지 않고, 충전만 되면 즉시 회복된다.

정리: "카운터 계열은 거절도 세므로 구간 끝까지 막히고, token bucket은 거절 시 토큰을 소모하지 않아 자연 회복된다"

정책적으로 "폭주 클라이언트는 더 세게 눌러야 한다"고 판단해 일부러 거절도 세는 설계도 있다. 어느 쪽이든 의도한 선택이어야 하고, 우연히 그렇게 된 상태면 안 된다.

Lua 스크립트 안에서 현재 시각은 어디서 가져와야 합니까? 시니어 변별힌트: 두 선택지 모두 대가가 있다. 원칙은 그 위에 있다

두 선택지가 있고 각각 대가가 다르다.

① 애플리케이션의 시각을 인자로 넘긴다(9절 코드의 ARGV[3]) — 구현이 간단하지만 서버 간 시계 오차가 그대로 판정에 섞인다. 시계가 앞선 서버가 보낸 now로 계산하면 충전이 실제보다 많이 일어난 것처럼 계산되고, 그 값이 저장되면 뒤에 오는 정상 서버의 계산까지 어긋난다.

② Redis의 시각을 스크립트 안에서 읽는다 — 출처가 하나이므로 서버 간 오차는 사라지지만, 복제본에 스크립트를 재생할 때 결과가 달라질 수 있다는 별개의 제약이 붙는다(같은 입력에 같은 출력이 나오지 않는 스크립트가 되기 때문).

어느 쪽이든 원칙은 하나: "시각의 출처를 하나로 통일한다"

① 을 택했다면 서버 간 시계 동기화(NTP)를 운영 전제로 명시하는 것까지가 설계다. "시계가 맞을 것이다"를 암묵적 가정으로 남기지 않는 것이 포인트다.

Redis가 리미터의 병목이 되면 어떻게 하나요? 가산점힌트: 리미터 키의 특성 하나가 확장을 쉽게 만든다

먼저 이 워크로드의 성질을 짚는다. Rate limiting의 판정은 거의 항상 "키 하나"만 건드린다(그 호출자의 카운터 또는 버킷). 여러 키에 걸친 트랜잭션이 없으므로 키 기준으로 수평 분할하기가 쉽다 — 이것이 이 문제의 출발점이다.

① 키 기준 샤딩. 키가 하나뿐이므로 Redis Cluster로 나눠도 스크립트가 여러 슬롯에 걸치는 문제가 생기지 않는다. 리미터 키 자체가 호출자별로 흩어져 있어 분포도 자연스럽다.

② 리미터 전용 인스턴스 분리. 캐시와 같은 Redis를 쓰면 캐시 트래픽이 리미터의 지연을 흔든다. 요청 경로에 있는 판정이므로 분리하는 편이 낫다.

③ 판정 계층을 앞으로 당긴다. 애플리케이션 인스턴스마다 부르는 대신 게이트웨이 층에서 한 번 판정하면 호출 주체 수 자체가 줄어든다.

④ 정확성을 조금 판다. 그래도 감당이 안 되면 로컬 카운터 + 주기 동기화로 내려간다 — 요청마다의 원격 호출이 주기마다의 원격 호출로 바뀌므로 호출량이 수십~수백 배 줄어든다.

순서가 답이다: "나눈다 → 분리한다 → 앞으로 당긴다 → 정확성을 판다" — 정확성을 파는 것은 마지막이다
429를 반환하는 것 자체는 공짜인가요? 리미터는 어느 계층에 둬야 합니까? 가산점힌트: 거절 응답을 만들기까지 이미 쓴 비용이 있다

공짜가 아니다. 429를 만들어 내보내기까지 TCP 커넥션 수립, TLS 핸드셰이크, HTTP 파싱, 필터 체인 진입까지의 비용은 이미 지불된다. 폭주 클라이언트가 초당 수천 건을 쏘면 전부 거절해도 그 비용이 서버에 쌓인다.

그래서 판정은 가능한 한 앞단에서 한다. 게이트웨이나 엣지에서 걸러내면 거절 비용이 애플리케이션까지 오지 않고, 애플리케이션의 커넥션·스레드·풀 자원이 정상 트래픽에만 쓰인다.

다만 앞단이 모든 것을 할 수는 없다. 게이트웨이가 아는 정보는 경로·헤더·토큰 수준이므로, 도메인 지식이 필요한 한도(예: "이 사용자의 구독 등급에 따른 한도")는 애플리케이션 계층에 남는다. 실무에서는 두 층을 겹쳐 쓴다 — 앞단은 거친 그물(IP당 넉넉한 한도), 뒷단은 정밀한 그물(등급별·엔드포인트별).

한 문장: "싸게 거를 수 있는 것은 앞에서, 도메인을 알아야 거를 수 있는 것은 뒤에서."
Fixed window를 꼭 써야 한다면 어떻게 보완합니까?힌트: "한도를 절반으로"는 답의 절반이다

세 가지 방향이 있고, 뒤로 갈수록 좋다.

① 한도를 절반으로 잡는다. 실질 한도가 명목의 2배이므로 계약은 지켜진다. 대신 평상시에 필요 이상으로 조인다 — 정직하지만 손해가 크다.

② 짧은 구간을 겹쳐 건다. "분당 100회" 하나가 아니라 "분당 100회 + 초당 10회" 처럼 서로 다른 길이의 창을 겹쳐서 건다. 경계에서 200회가 몰려도 초 단위 창이 먼저 막으므로 버스트의 폭이 줄어든다. 구현은 카운터 두 개로 여전히 싸다.

③ Sliding window counter로 바꾼다. 상태는 여전히 카운터 두 개인데 경계 문제가 실용적으로 사라진다. 결국 ①·②로 버티는 이유가 거의 없다는 것이 결론이고, 이 결론을 말할 수 있는지가 진짜 포인트다.

면접 답: "보완할 수는 있지만, 같은 메모리로 sliding window counter가 되므로 굳이 보완할 이유가 없습니다."
그래서 지금 우리 서비스에는 무엇을 쓰시겠습니까?힌트: 정답을 찍는 질문이 아니라 판단 순서를 보는 질문이다

네 개를 순서대로 묻고 답을 조립한다.

1
"버스트가 정당한 사용 패턴인가?" → 예(첫 화면에서 API 여러 개 동시 호출)면 token bucket, 총량을 눌러야 하면 sliding window counter.
2
"초과 1건이 비용이나 위험인가?" → 예(과금·보안)면 동기 중앙 카운터 + 정확한 알고리즘(작은 한도라면 sliding window log), 아니오(남용 방지)면 근사를 허용.
3
"기준 응답시간이 얼마인가?" → 20ms대면 Redis 왕복 1ms를 감당할 수 있고, 3ms대면 로컬 판정 + 주기 동기화로 내려간다.
4
"Redis가 죽으면 무엇을 지켜야 하는가?" → 남용 방지면 fail open, 보안이면 fail closed. 어느 쪽이든 지표를 남긴다.
기본값을 하나 대라면: sliding window counter + Redis Lua + fail open + Retry-After 포함 — 그다음 위 네 질문의 답에 따라 조정한다.
한 줄 요약
Rate limiting은 호출자별 사전 계약을 평상시에도 집행하는 유입 제어이고(과부하 때만 발동하는 load shedding, 상류를 감속시키는 백프레셔와는 별개 계층), 알고리즘은 "버스트를 허용할 것인가"로 갈려 token bucket이 충전률과 통 크기라는 두 손잡이로 평균과 순간을 분리 제어하는 반면 sliding window는 구간 총량을 눌러 주며 fixed window는 경계에서 정확히 2배가 뚫린다 — 분산 환경에서는 로컬 카운트의 합이 전체 한도와 같아지지 않으므로(나눠 주면 남기면서 거절하고 넉넉히 주면 서버 대수만큼 뚫린다) 카운터를 중앙화하되, check-then-act 경쟁 조건은 INCR의 반환값이나 Lua 스크립트 같은 원자적 연산으로 막고, 중앙화의 지연·가용성 비용은 "얼마나 정확해야 하는가"에 대한 답과 fail open/closed 결정으로 절충하며, 429에는 Retry-After와 남은 한도를 실어 거절이 재시도 폭풍으로 되돌아오지 않게 하는 것까지가 설계의 완성이다.
