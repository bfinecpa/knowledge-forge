정시 트래픽 스파이크 대비
예측 가능한 스파이크는 계층별로, 시간 축을 갖고 준비한다

면접 질문: "인기 웹툰 신작 공개 시각(예: 밤 11시)에 트래픽이 스파이크됩니다. 어떤 계층에서 어떻게 대비하나요?"

핵심 관전 포인트 — 시각이 정해진 스파이크는 "감지 후 대응"이 아니라 "사전 준비"의 문제다. 반응형 오토스케일링은 원리적으로 늦는다 — 지표 수집 15초 · 어댑터 노출 15초 · 스케일러 평가 15초 · 파드 배치 5초 · 컨테이너 기동 10초 · 앱 부팅 30초 · readiness 20초 · 워밍업 60초가 직렬로 이어져 약 170초가 되는데, 스파이크는 10초 안에 완성된다. 그래서 시각 기반 사전 스케일 아웃이 기본이고, 그 규모는 감이 아니라 예상 피크 λ ÷ 인스턴스당 안전 처리량이라는 나눗셈이다 — 분모를 부하 테스트의 포화 처리량으로 잡으면 안 된다(ρ=0.98이면 응답시간이 51배). 대비는 요청이 흐르는 순서대로 유입(푸시 분할) → CDN(사전 워밍) → 앱(사전 증설 + 워밍업) → 캐시(사전 적재 + 스탬피드 방지) → DB(쓰기 큐 흡수 · 배치 금지 · 커넥션 총량 역산)로 세우고, 예측이 빗나갈 때의 마지막 방어선은 rate limiting과 load shedding이되 준비의 마지막 항목은 그 방어선이 실제로 켜지는지 확인하는 것이다. 이 전부를 T-1일부터 T+30분까지의 시간 축 런북으로 말할 수 있어야 한다.
  • 1
    먼저 선을 긋는다 — 예측 가능한 스파이크는 반응형에 맡기지 않는다. 반응형 스케일 아웃은 아홉 단계가 직렬이라 약 170초가 걸리는데 스파이크는 10초에 완성된다. 그 2분 40초는 그냥 느린 게 아니라 타임아웃 → 재시도 → 유입 증가로 스스로를 증폭시킨다.
  • 2
    그래서 시각 기반 사전 스케일 아웃이고, 규모는 나눗셈으로 낸다. 예상 피크 3,726 RPS ÷ 인스턴스당 안전 처리량 140 RPS(포화 200 × 목표 사용률 0.7) = 27대, 예측 오차 여유 20%를 얹어 33대. 반응형은 끄지 않고 하한(minReplicas)만 올려 초과분을 따라가게 남긴다.
  • 3
    계층 순서대로 준비하고, 시간 축 런북으로 묶는다. 유입 → CDN → 앱 → 캐시 → DB로 안쪽 도달량을 줄이고, 예측 실패용 방어선(degradation → shedding)은 평상시에 켜 봐서 살아 있음을 확인해 둔다. T-1일부터 T+1일까지 담당 · 정상 판단 기준 · 되돌림 기준이 적힌 표가 답의 마지막이다.

0. 질문 + 출제 의도

질문: "인기 웹툰 신작 공개 시각(예: 밤 11시)에 트래픽이 스파이크됩니다. 어떤 계층에서 어떻게 대비하나요?"

출제 의도: 예측 가능한 스파이크는 준비 안 하면 그냥 태만이다. 계층별(CDN, 캐시 사전 워밍, 사전 스케일 아웃) 대비를 시간 축까지 넣어 말하는지 본다 — 이 회사의 매일 밤 실제 상황이므로 도메인 적합성 검증이기도 하다.

이 페이지가 겨냥하는 약점 세 가지 ① "오토스케일링 걸어두면 되죠"로 끝나는 것 → 1·2절에서 리드타임을 아홉 단계로 분해해 170초를 만들고, 스파이크의 10초와 같은 축에 겹쳐 그린다.
② "미리 늘려둡니다"에서 멈추고 "몇 대?"에 답이 없는 것 → 7절에서 분자·분모·여유 세 항을 각각 근거를 대고 채우고, 분모를 포화 처리량으로 쓴 오답과 나란히 비교한다.
③ 계층 나열만 하고 시간표가 없는 것 → 11절에서 담당 · 정상 판단 기준 · 되돌림 기준이 붙은 런북으로 묶는다. 사람이 필요한 이유는 자동화가 실패했는지 판단하고 무엇을 포기할지 결정하는 것이기 때문이다.

1. 반응형은 왜 원리적으로 늦는가 — 170초의 해부

이 질문에서 가장 먼저 그어야 할 선이 있다. 예측 가능한 스파이크와 예측 불가능한 스파이크는 다른 문제다. 밤 11시 공개는 날짜·시각·대상 콘텐츠까지 전부 알고 있다. 그런데도 반응형 오토스케일링에 맡기면 늦는데, "수 분이 걸린다"로 뭉뚱그리면 왜 늦는지도, 어디를 줄일 수 있는지도 알 수 없다. 단계로 분해해서 합산해야 한다.

1-1. 아홉 단계, 각각 무엇을 기다리는가

각 단계의 시간은 우리가 정하는 설정값이거나 환경에 따라 달라지는 값이므로, 자리수와 구조를 먼저 보고 그다음에 "이런 설정이라면 이 값"이라는 예시를 보는 것이 맞다.

단계무엇을 기다리는가시간의 자리수예시 설정에서의 값

② 집계 · 어댑터 노출수집된 값이 스케일러가 읽는 API 형태로 나오기까지10초 자리15초

⑧ readiness 통과probe 주기 × 연속 성공 요구 횟수10초 자리10초 × 2회 = 20초

면접에서는 아홉 개를 다 읊을 필요가 없다. 세 덩어리로 말하고, 물어보면 그 안을 쪼개 보이는 순서가 좋다.

줄이려면 여기를 손댄다 가장 큰 두 덩어리가 앱 부팅(30초)과 워밍업(60초)이므로 기동 시간 단축이 먼저다 — 불필요한 빈 초기화 제거, 이미지 슬림화, 노드에 이미지 사전 캐싱. 반대로 ①②③ 주기를 5초로 줄이면 20~30초를 벌지만, 지표가 출렁여 진동(플래핑)이 늘어난다는 대가가 있다.
최악의 경우 — 170초가 5분이 된다 ⑤에서 노드에 여유가 없으면 새 노드를 부팅해야 하고, 그 노드에는 이미지 캐시도 없다. ⑤와 ⑥이 동시에 100초 자리로 뛰어 합계가 5분을 넘긴다. 그래서 사전 준비 항목에는 파드 증설만이 아니라 "그 파드들이 들어갈 노드 여유를 미리 만들어 두는 것"이 포함된다.

2. 같은 시간축에 겹쳐 보기 — 2분 40초의 실체

이제 스파이크의 상승 속도를 같은 축에 올려 보자. 신작 공개 트래픽은 초 단위로 오른다 — 사용자들이 정각을 기다리고 있었기 때문이다.

비유 — 개봉일 아침의 영화관 관객이 몰린 걸 보고 나서 매표소 직원을 집에서 불러오면 늦는다. 전화하고(①~③), 준비해서 출근하고(⑤~⑦), 시스템에 로그인하고(⑧), 손에 익기까지(⑨)의 시간이 관객이 줄을 서는 속도보다 훨씬 느리다. 개봉 시각 전에 전원 출근시켜 두는 것이 답이다. 그리고 출근했다고 바로 제 속도가 나오는 것도 아니라는 것이 다음 절의 주제다.

3. 워밍업 — readiness가 확인하지 않는 것

1절 ⑨에 60초를 잡아 둔 이유를 설명해야 한다. 새로 뜬 인스턴스는 왜 즉시 제 성능을 내지 못하는가. 원인이 넷인데, 각각 정확히 무엇인지 알아야 대응이 나온다.

워밍업이 필요한 원인 4종 — "제자리에 없는 네 가지 C"

C1. Compiled code — JIT 컴파일
자바는 실행 시 JVM이 바이트코드를 인터프리터로 한 줄씩 해석한다. 어떤 메서드가 반복 호출되면 그때서야 JIT(just-in-time, 실행 시점) 컴파일러가 기계어로 바꾼다. 그 임계 호출 횟수를 넘기기 전까지는 같은 코드가 훨씬 느리게 돈다. 갓 뜬 파드는 그 구간에 있다.
C2. Class — 클래스 로딩
자바 클래스는 시작할 때 전부 읽히는 게 아니라 처음 쓰이는 순간에 로드·검증·초기화된다. 그래서 어떤 요청 경로를 처음 통과하는 요청이 그 경로의 클래스 수백 개 로딩 비용을 혼자 문다.
C3. Connection — 커넥션 풀이 비어 있다
HikariCP의 minimumIdle이 낮거나 0이면 풀은 빈 상태로 시작하고 필요해진 순간 만든다. 커넥션 하나 = TCP 연결 + 인증 핸드셰이크 + 세션 초기화라 수십 ms가 걸리고, 그 비용이 최초 요청의 응답시간에 그대로 붙는다. 외부 API 클라이언트도 같다.
C4. Cache — 로컬 캐시가 비어 있다
인메모리 캐시(Caffeine 등)나 JPA 2차 캐시는 파드 안에 있으므로 새 파드에서는 텅 비어 있다. 기존 파드가 캐시 히트로 처리하던 요청을 새 파드는 전부 DB까지 가서 처리한다.
넷 모두 readiness probe를 통과한다 — probe는 "HTTP 200을 주는가"만 보지, "빠른가"는 보지 않는다
함정 하나 더 — 최소 연결 수(least connection)를 쓰면 더 나빠진다 갓 투입된 파드는 진행 중인 요청이 0건이므로, least connection은 균형이 맞을 때까지 새 요청을 거의 전부 그 파드에만 보낸다. 가장 준비가 안 된 파드에 가장 많은 트래픽이 순간적으로 몰리는 역설이다. LB 쪽 대응은 slow start(신규 서버에 트래픽을 서서히 올리는 기능)이고, 애플리케이션 쪽 대응이 아래 코드다. 둘 중 후자가 더 확실하다 — readiness의 의미를 바꾸면 LB 종류와 무관하게 성립하기 때문이다.

3-1. 코드 — 워밍업이 끝날 때까지 readiness를 올리지 않는다

GOOD readiness 판정에 우리 워밍업 상태를 끼워 넣는다
// 이 지표가 UP이 될 때까지 쿠버네티스는 이 파드를 서비스 엔드포인트에 넣지 않는다.
@Component
public class WarmupHealthIndicator implements HealthIndicator {

    private final AtomicBoolean warmedUp = new AtomicBoolean(false);

    @Override
    public Health health() {
        return warmedUp.get()
                ? Health.up().build()
                // OUT_OF_SERVICE = "살아 있지만 트래픽은 받지 말라". DOWN을 쓰면
                // liveness 그룹에 섞였을 때 파드가 재시작될 수 있다.
                : Health.outOfService().withDetail("phase", "warming-up").build();
    }

    void markWarmedUp() { warmedUp.set(true); }
}

@Component
@RequiredArgsConstructor
public class WarmupRunner implements ApplicationRunner {

    private final WarmupHealthIndicator indicator;
    private final HikariDataSource dataSource;
    private final EpisodeQueryService queryService;

    @Override
    public void run(ApplicationArguments args) throws Exception {
        // ① C3 — 커넥션 풀을 미리 채운다. 최초 요청이 TCP 연결과 인증
        //    핸드셰이크 비용을 대신 물지 않게 하는 것이 목적이다.
        for (int i = 0; i < dataSource.getMinimumIdle(); i++) {
            try (Connection c = dataSource.getConnection()) {
                c.createStatement().execute("SELECT 1");
            }
        }

        // ② C1 + C2 — 주요 조회 경로를 내부에서 반복 호출한다. 목적이 둘이다:
        //    그 경로의 클래스를 모두 로드시키고, 호출 횟수를 JIT 임계 위로 올려
        //    핫 경로가 기계어로 컴파일되게 만든다. 횟수는 부하 테스트에서
        //    "응답시간이 평탄해지는 지점"으로 실측해 정한다.
        for (int i = 0; i < 300; i++) {
            queryService.warmupProbe();
        }

        // ③ C4 — 로컬 캐시를 채운다. 첫 실제 요청부터 캐시 히트를 내게 한다.
        queryService.preloadHotEpisodes();

        // ④ 여기까지 끝난 뒤에야 readiness를 올린다.
        //    이 순서가 이 클래스의 존재 이유다 — 순서를 바꾸면 아무 의미가 없다.
        indicator.markWarmedUp();
    }
}

# 지표를 만들어도 readiness 판정에 넣지 않으면
# 쿠버네티스는 그것을 보지 않는다.
management:
  endpoint:
    health:
      probes:
        enabled: true   # /actuator/health/{liveness,readiness}
      group:
        readiness:
          include: readinessState,warmup
          # warmup = WarmupHealthIndicator 의 지표 id
        liveness:
          include: livenessState
          # 워밍업은 liveness에 넣지 않는다 (오른쪽 참고)
YAML 파드 스펙 — 세 probe의 역할을 분리한다
startupProbe:
  # 부팅이 끝나기를 기다리는 전용 probe. 이게 성공할 때까지
  # liveness/readiness는 아예 시작되지 않는다.
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 5
  failureThreshold: 30   # 5초 × 30 = 최대 150초까지 부팅 허용
readinessProbe:
  # 워밍업 완료 여부가 여기 들어 있다. 실패해도 파드는 죽지 않고
  # 서비스 엔드포인트에서만 빠진다 — 워밍업 중 상태에 정확하다.
  httpGet: { path: /actuator/health/readiness, port: 8080 }
  periodSeconds: 10
  successThreshold: 2    # 2회 연속 성공해야 투입 (1절 ⑧ = 20초)
livenessProbe:
  # 워밍업을 여기 넣으면 안 된다. 느린 날 파드가 재시작되고,
  # 재시작하면 워밍업을 처음부터 → 영원히 뜨지 못한다.
  httpGet: { path: /actuator/health/liveness, port: 8080 }
  periodSeconds: 10

probe 3종의 역할 분리 — 한 줄씩

startup = "부팅 끝났나"→ readiness = "제 성능으로 받을 준비 됐나" (워밍업 여기)→ liveness = "죽었나" (워밍업 넣으면 무한 재시작)

4. 계층별 대비 — 한 장 지도

원칙은 load shedding과 같은 뿌리다. 부하를 가능한 한 바깥 계층에서 흡수해, 안쪽(비싸고 늘리기 어려운 DB)까지 도달하는 양을 구조적으로 줄인다. 그리고 계층마다 "무엇을 한다"만 나열하면 준비 문서가 되지 않는다 — 각 계층에서 얼마나 준비하는지에 산정 근거가 붙어야 다음 공개일에 그 숫자를 갱신할 수 있다.

계층 6종 인출 — "유 · 씨 · 앱 · 캐 · 디 + 방"

유입 — 뾰족함을 깎는다→ CDN — 미리 채운다→ 앱 — 나눗셈으로 미리 늘린다→ 캐시 — 미리 넣고 몰림을 막는다→ DB — 도달량을 줄인다+ 방어선 — 켜지는지 확인해 둔다

방어선을 마지막에 설명하되 그림에서는 게이트웨이에 그리는 이유: 그것은 다섯 계층 다음에 오는 계층이 아니라, 예측이 빗나갔을 때만 열리는 밸브이기 때문이다. 그리고 거절은 게이트웨이에서 해야 값이 있다 — 안쪽에서 버리면 이미 스레드와 커넥션을 쓴 뒤라 방어 효과가 크게 줄어든다.

5. ① 유입 — 스파이크의 뾰족함부터 깎는다

가장 싸고 가장 효과가 큰 대비가 이것이다. 스파이크의 크기는 자연 현상이 아니라 우리가 만든 결과일 수 있다. 수백만 명에게 23:00:00에 동시에 알림이 가면 우리가 우리 손으로 스파이크를 만드는 셈이다.

일제 발송 — 우리가 만든 스파이크

[전제] 알림 대상 300만 명
       알림 수신 후 5분 내 앱 진입률 20%

3,000,000 × 0.2 = 600,000명이 5분 안에 진입
평균 = 600,000 ÷ 300초 = 2,000명/초

실제 분포는 앞으로 몰린다.
첫 30초에 절반이 온다면
300,000 ÷ 30초 = 10,000명/초  ← 순간 피크

10분에 걸쳐 20개 배치로 분할

같은 60만 명이 600초에 걸쳐 진입

한 배치의 진입 = 600,000 ÷ 20 = 30,000명

그 배치의 순간 피크는 20분의 1로 깎인다

서버를 20배로 늘리는 것과
피크를 20분의 1로 깎는 것은
같은 효과인데 비용이 전혀 다르다.
분할 발송 하나로 피크가 한 자리수 줄어든다 — 33대를 더 띄우기 전에 먼저 할 일
클라이언트의 정각 폴링에도 jitter(흔들림)를 심는다 공개 시각을 기다리며 반복 조회하는 클라이언트가 있으면 요청 시점이 정각에 정렬된다. 요청 간격에 무작위 흔들림을 넣어 그 정렬을 깨뜨리는 것이, 재시도에 jitter를 넣어 재시도 폭풍을 막는 것과 완전히 같은 원리다 — "동시에 일어나는 일을 시간 축으로 흩는다." 이 아이디어는 이 문서에서 세 번 반복된다: 푸시 분할, 폴링 jitter, 그리고 8절의 TTL jitter.

6. ② CDN — 런북 항목으로서의 사전 워밍

웹툰 도메인에서 스파이크 트래픽의 대부분은 회차 이미지다. 이미지는 공개 순간부터 변하지 않는 콘텐츠이므로 CDN이 가장 잘 흡수한다. CDN의 동작 원리와 워밍이 오리진 부하를 얼마나 줄이는지의 계산은 별도 문서의 몫이고, 여기서 쓸 것은 런북 항목으로서의 CDN이다 — 언제, 무엇을, 어떻게 확인하는가.

시점무엇을 워밍하는가확인 방법
T-30분공개 회차의 전체 이미지를 지역별 엣지에 사전 요청워밍 스크립트의 완료 건수 = 대상 이미지 수
T-10분목록 · 썸네일 등 진입 경로의 이미지주요 지역 엣지에서 응답 헤더의 캐시 상태가 HIT인지 샘플 확인
T-5분워밍 결과 검증 (새로 워밍하지 않는다)오리진의 요청 수가 워밍 트래픽 이후 평상시로 돌아왔는지
1
워밍 자체가 오리진에 부하를 준다. 우리가 만드는 트래픽이므로 속도를 통제할 수 있다는 것이 유일한 장점이다. 초당 몇 건으로 제한해 천천히 채워야, 워밍 때문에 오리진이 흔들리는 자충수를 피한다.
2
"채웠다고 믿는 것"과 "확인한 것"은 다르다. 워밍 스크립트가 성공으로 끝났어도 우리 사용자가 실제로 붙는 엣지에 들어갔는지는 별개다. 샘플 조회로 캐시 상태를 눈으로 확인하는 항목이 런북에 있어야 한다.
3
공개 전 접근 차단과 캐시 가능성이 충돌한다. 공개 시각 전에는 이미지에 접근할 수 없어야 하는데, 그 차단을 CDN 계층에서 하면 캐시를 채울 수 없다. 그래서 차단은 캐시 가능성을 해치지 않는 방식(서명 URL의 발급 시점을 앱에서 통제하는 등)으로 푼다 — 이미지 자체는 미리 엣지에 있고, 그 URL을 얻는 경로를 정각에 열어 주는 구조다.

7. ③ 애플리케이션 — 증설 규모는 나눗셈이다 승부처

"미리 증설한다"까지는 누구나 말한다. 면접에서 갈리는 지점은 "몇 대로?"에 대한 답이 나눗셈으로 나오는가다.

외울 것은 식 하나 — "분자는 예측, 분모는 안전, 곱은 여유"

목표 대수 = ceil( 예상 피크 처리량 λ ÷ 인스턴스당 안전 처리량 ) × (1 + 예측 오차 여유)
분자 = 예측
지난 공개일들의 실측 피크에 성장 추세와 화제성 보정을 얹는다. 감이 아니라 기록에서 출발한다.
분모 = 안전
부하 테스트의 포화 처리량이 아니다. 거기에 목표 사용률 ρ를 곱한 값이다. 가장 자주 틀리는 곳.
곱 = 여유
분자가 예측값이므로 틀릴 수 있다. 보정 계수 자체에 근거가 부족하므로 20%를 얹는다.

7-1. 분자 — 예상 피크 처리량 λ

지난 3회 공개일의 실측 피크 중 최고값        2,700 RPS
서비스 성장 추세 (전월 대비 이용자 증가)      × 1.15
작품 화제성 보정 (사전 예약 수, 프로모션 규모) × 1.20
───────────────────────────────────────────────────────
예상 피크 λ = 2,700 × 1.15 × 1.20 = 3,726 RPS

7-2. 분모 — 인스턴스당 안전 처리량 (여기가 함정이다)

부하 테스트로 잰 "인스턴스 1대가 목표 p99를 지키며 감당하는 한계 RPS"를 그대로 쓰면 안 된다. 그 값은 사용률 100%에 해당하는 포화 처리량이기 때문이다.

부하 테스트 실측
  파드 1대의 포화 처리량 = 200 RPS   (그 이상에서 p99가 급격히 무너지는 지점)

목표 사용률 ρ = 0.7 을 적용
  인스턴스당 안전 처리량 = 200 × 0.7 = 140 RPS

왜 0.7을 곱하는가. 응답시간은 사용률 ρ에 대해 1/(1−ρ) 배로 자라고, 분모에 (1−ρ)가 있으므로 ρ가 1에 다가갈 때 폭발한다.

같은 표를 손에 들고 보면 사전 증설 규모의 차이가 바로 보인다
사용률 ρ응답시간 배수 1/(1−ρ)기본 응답시간 300ms일 때
0.502.0600ms
0.70 ← 목표3.31,000ms
0.9010.03,000ms
0.9520.06,000ms
0.99100.030,000ms

7-3. 두 산정을 나란히 놓는다

BAD 포화 처리량 200 RPS로 나눈다
필요 대수 = ceil(3,726 ÷ 200) = ceil(18.63) = 19대

그러면 실제 사용률은
  ρ = 3,726 ÷ (19대 × 200 RPS)
    = 3,726 ÷ 3,800 = 0.9805

응답시간 배수 = 1 ÷ (1 − 0.9805)
              = 1 ÷ 0.0195 = 51.3배
300ms × 51.3 = 약 15초

→ 대수 계산은 "딱 맞게" 나왔는데
   서비스는 사실상 죽어 있다.
GOOD 안전 처리량 140 RPS로 나눈다
필요 대수 = ceil(3,726 ÷ 140) = ceil(26.61) = 27대

검산:
  ρ = 3,726 ÷ (27 × 200) = 3,726 ÷ 5,400 = 0.69
  응답시간 배수 = 1 ÷ 0.31 = 3.23배 → 약 970ms
  (목표 ρ 0.7과 일치. 140 = 200 × 0.7 이었으므로 당연)

예측 오차 여유 20%를 얹는다
  목표 대수 = ceil(27 × 1.2) = ceil(32.4) = 33대

최종 검산:
  ρ = 3,726 ÷ (33 × 200) = 0.5645
  배수 = 1 ÷ 0.4355 = 2.30배 → 약 690ms

7-4. 같은 답을 L = λW로도 확인한다

예상 피크 λ = 3,726건/초
요청 1건의 체류 시간 W = 0.3초   (300ms 요청 프로필)

시스템 전체가 동시에 물고 있어야 하는 요청 수
  L = λW = 3,726 × 0.3 = 1,117.8 ≈ 1,118건

인스턴스 1대가 안전하게 물 수 있는 동시 요청 수
  = 안전 처리량 × W = 140 × 0.3 = 42건

필요 대수 = ceil(1,118 ÷ 42) = ceil(26.6) = 27대   ← 위와 같은 답
두 경로를 다 아는 것의 실무적 값 같은 답이 나오는 것은 당연하다 — L = λW의 양변을 W로 나눈 것이 처리량 나눗셈이기 때문이다. 그러나 얻는 것이 다르다: 처리량으로 세면 "몇 대"가 나오고, L로 세면 "그 대수가 물어야 하는 동시 요청 수"가 나온다. 후자는 스레드풀 크기, 커넥션 풀 총량, in-flight 임계값을 정할 때 그대로 쓰이는 숫자다.

7-5. 이 대수를 시각에 맞춰 실제로 만든다

핵심 — 스케일러를 끄는 것이 아니라 하한만 올린다 HPA를 끄고 대수를 고정하면 예측을 넘는 초과분을 따라갈 수단이 사라진다. minReplicas만 올리면 사전 증설 + 반응형 보조가 둘 다 성립한다. 
# T-45분(22:15)에 HPA의 minReplicas를 사전 증설 목표로 올린다.
apiVersion: batch/v1
kind: CronJob
metadata:
  name: episode-api-prescale-up
spec:
  schedule: "15 22 * * *"
  # 서버가 UTC로 돌아도 이 필드가 있으면 KST 기준으로 실행된다.
  # 빼먹으면 9시간 어긋나 아무 준비 없이 공개를 맞는다 — 가장 흔한 사고다.
  timeZone: "Asia/Seoul"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      # 이 작업이 실패하면 그날 준비가 아예 없다. 반드시 재시도하고,
      # 실패 이벤트에 알람을 걸어 사람이 알게 만든다.
      backoffLimit: 3
      template:
        spec:
          serviceAccountName: hpa-patcher   # HPA patch 권한만 가진 계정
          restartPolicy: OnFailure
          containers:
            - name: kubectl
              image: bitnami/kubectl:1.29
              command: ["/bin/sh", "-c"]
              args:
                - |
                  # 7절의 산정 결과. 이 숫자의 근거를 주석으로 남긴다 —
                  # 예상 피크 3,726 RPS ÷ 안전 처리량 140 RPS = 27대,
                  # 예측 오차 여유 20%를 얹어 33대.
                  kubectl patch hpa episode-api --type=merge \
                    -p '{"spec":{"minReplicas":33}}'
---
# T+30분(23:30)에 하한을 평상시 값(6)으로 되돌리는 CronJob을 짝으로 둔다.
# 되돌린다고 즉시 줄어드는 것이 아니다 — 실제 축소 속도는 HPA의
# 안정화 창과 축소 정책이 결정한다(12절).
  schedule: "30 23 * * *"
  timeZone: "Asia/Seoul"
이 모든 것의 전제 하나 — stateless 서버 인스턴스가 요청 사이의 상태(세션, 진행 중인 작업 상태)를 자기 메모리에 들고 있으면, 증설한 파드에 붙은 사용자는 그 상태를 찾지 못한다. 즉 증설 자체가 버그를 만든다. 사전 스케일 아웃을 말하기 전에 "우리 서버가 stateless인가"가 먼저 참이어야 한다.

8. ④ 캐시 — 사전 적재와 스탬피드 방지

공개 정각에 벌어지는 일을 정확히 그려 보자. 신작 회차의 메타데이터·회차 목록은 그 순간까지 캐시에 없다(또는 정각에 무효화된다). 수만 요청이 동시에 캐시 미스를 내고 전부 DB로 직행하는 캐시 스탬피드(cache stampede) — 우르르 몰려드는 소떼처럼, 같은 것을 기다린 다수가 동시에 같은 곳으로 달려드는 현상 — 가 스파이크 장애의 단골 원인이다.

무엇을 얼마나 미리 넣는가 — 사전 적재 대상과 시각

적재 키 수는 수십~수백 개 규모다. DB 쿼리 수백 건이면 끝난다 — 사전 적재는 비용이 거의 없는 준비라는 것이 요점이다.
적재 시각 = T-10분
너무 이르면 그 사이 데이터가 바뀔 수 있고, 너무 늦으면 적재 자체가 스파이크와 겹친다.
TTL
스파이크 창(약 40분)보다 길게 잡아 창 안에서 만료되지 않게 한다. 그리고 같은 배치의 키가 같은 초에 만료되지 않도록 jitter를 준다.
사전 적재는 예측 가능한 스파이크만 쓸 수 있는 특권이다 — 꼬리질문에서 가장 먼저 말할 항목

여기서 짚어야 할 것이 하나 있다. 사전 적재만으로 끝나지 않는다. 적재한 키도 언젠가 만료되고, 적재 목록에 없던 키는 여전히 미스가 난다. 그래서 미스가 났을 때 재계산을 한 요청으로 제한하는 장치가 함께 있어야 한다.

BEFORE 순진한 get-or-load
public Episode getEpisode(long id) {
    Episode cached = cache.get(key(id));
    if (cached == null) {        // 공개 정각: 전원이 여기 도달
        cached = db.findEpisode(id); // 같은 쿼리가 수만 번 동시 실행
        cache.put(key(id), cached);
    }
    return cached;
}

// 문제는 "틀린 코드"가 아니라 "동시성이 없다고 가정한 코드"라는 점이다.
// 평상시에는 미스가 흩어져 있어 이 코드로도 아무 일이 없다.
// 정각에만, 그리고 그때는 크게 터진다.
AFTER ① 사전 적재 + ② single flight + ③ TTL jitter
@Service @RequiredArgsConstructor
public class EpisodeCacheService {

    // 값이 아니라 '진행 중인 작업'을 담는 맵이라는 점이 핵심 —
    // 그래서 뒤늦게 온 요청이 결과를 기다려 공유할 수 있다.
    private final ConcurrentHashMap<String, CompletableFuture<Episode>>
            inFlightLoads = new ConcurrentHashMap<>();

    /** T-10분에 배치로 호출. 미스 자체를 없애는 것이 목적. */
    public void preload(List<Long> episodeIds) {
        for (Long id : episodeIds) {
            Episode e = db.findEpisode(id);
            // 적재 단계에서부터 TTL에 흔들림을 준다. 같은 배치로 넣은
            // 키 수백 개가 같은 초에 만료되면 그것이 2차 스탬피드다.
            cache.set(key(id), e, ttlWithJitter());
        }
    }

    public Episode getEpisode(long id) {
        String k = key(id);
        Episode cached = cache.get(k);
        if (cached != null) return cached;

        // computeIfAbsent는 키 단위로 원자적이다. 동시에 도착한 수천 개
        // 요청 중 최초 1개만 로딩 작업을 만들고 나머지는 같은 Future를 받는다.
        CompletableFuture<Episode> load = inFlightLoads.computeIfAbsent(k, key ->
                CompletableFuture.supplyAsync(() -> {
                    Episode fresh = db.findEpisode(id);
                    cache.set(key, fresh, ttlWithJitter());
                    return fresh;
                }).whenComplete((v, ex) -> inFlightLoads.remove(key)));
        // ↑ 완료 후 반드시 제거한다. 남겨 두면 이 맵이 두 번째 캐시가 되어
        //   낡은 값을 영구 재사용하고, 실패한 Future가 남으면 그 키는
        //   영원히 실패를 반환한다.

        return load.join();
    }

    private Duration ttlWithJitter() {
        // 기준 30분 ± 최대 5분. 대량 키의 동시 만료를 시간 축으로 흩는다.
        long base = Duration.ofMinutes(30).toSeconds();
        long jitter = ThreadLocalRandom.current().nextLong(-300, 301);
        return Duration.ofSeconds(base + jitter);
    }
}
이 single flight의 한계를 반드시 함께 말해야 한다 ConcurrentHashMap은 이 JVM 안에만 있다. 그러므로 인스턴스가 33대면 같은 키에 대해 최대 33건의 쿼리가 DB로 간다. 수만 건보다는 압도적으로 낫지만 1건은 아니다. 완전히 1건으로 줄이려면 Redis 분산 락 같은 인스턴스 간 조율이 필요하고, 그 대가(락 획득 실패 시 무엇을 반환하는가, 락 홀더가 죽으면 어떻게 되는가)를 함께 설계해야 한다. "33건까지 줄였다"를 정확히 말하는 것이 "막았습니다"보다 강한 답이다.

9. ⑤ DB — "도달량을 줄인다"를 구체적으로

앞 계층이 전부 잘 돼도 병목은 결국 상태 있는 계층으로 수렴한다. DB는 늘리기 가장 어렵고 죽었을 때 복구가 가장 오래 걸리는 계층이므로, 여기서 할 일은 증설이 아니라 도달량 자체를 줄이는 것이다. 넷으로 나눠 본다.

9-1. (1) 쓰기를 큐로 흡수해 뒤로 미룬다

스파이크 시 가장 흔한 자충수가 "회차 조회마다 조회수 UPDATE"다. 읽기 요청이 그대로 쓰기 요청이 되므로 캐시가 아무 도움을 주지 못한다.

동기 UPDATE

조회 3,726 RPS 전부가 UPDATE 1건씩
→ DB 쓰기 3,726건/초

10초 단위로 회차별 집계해 UPSERT

공개된 회차가 60개라면 10초에 60건
→ 6건/초   (3,726 ÷ 6 = 약 620분의 1)
SQL 집계한 증분을 한 번에 반영한다 (PostgreSQL UPSERT)
-- 값을 덮어쓰지 않고 '더한다'는 점이 중요하다 — 여러 인스턴스가 각자
-- 자기 버퍼 몫을 올려도 합계가 맞는다.
INSERT INTO episode_stats (episode_id, view_count, updated_at)
VALUES ($1, $2, now())
ON CONFLICT (episode_id) DO UPDATE
   SET view_count = episode_stats.view_count + EXCLUDED.view_count,
       updated_at = now();
트레이드오프를 반드시 붙인다 — 이건 기술 판단이 아니라 비즈니스 판단이다 버퍼에 있던 증분은 인스턴스가 죽으면 사라진다. 조회수는 그 손실이 허용되지만 결제·포인트는 절대 안 된다. 비동기화의 적용 범위는 "정확성이 조금 늦거나 조금 틀려도 되는 데이터"로 한정된다.

9-2. (2) 조회를 캐시와 읽기 복제본으로 돌린다

DB 도달량은 히트율이 아니라 미스율에 비례한다

히트율 95%에서 99%로 올리는 것은 히트율을 4%포인트 올리는 것이 아니라 미스율을 5%에서 1%로, 즉 DB 부하를 5분의 1로 줄이는 것이다. 이 프레임 전환 하나가 캐시 튜닝의 우선순위를 바꾼다.

캐시가 흡수하지 못한 읽기는 읽기 전용 복제본으로 보낸다. 여기서 준비 항목이 하나 생긴다 — 복제 지연을 미리 확인해야 한다. 스파이크 중에 쓰기가 몰리면 복제 지연이 커지고, 지연된 복제본을 읽으면 "방금 본 회차가 목록에 없다" 같은 현상이 생긴다.

SQL T-1일 · T-30분 확인 항목
-- 프라이머리에서: 각 복제본이 얼마나 뒤처져 있는가
SELECT client_addr, state,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_lag_bytes
  FROM pg_stat_replication;

-- 복제본에서: 마지막으로 반영한 트랜잭션이 몇 초 전 것인가
SELECT now() - pg_last_xact_replay_timestamp() AS replay_lag;

9-3. (3) 스파이크 시각에 배치·통계 쿼리를 금지한다 가장 자주 잊는 항목

이것이 가장 싸고 가장 자주 잊는 항목이다. 매시 정각에 도는 통계 집계, 매일 밤 도는 정산 배치, 운영자가 대시보드에서 누르는 무거운 리포트 조회가 하필 그 시각에 DB의 동시 실행 슬롯과 공유 버퍼를 잡아먹는다. 그리고 준비 문서에 "그 시간엔 돌리지 마세요"라고 적어 두는 것으로는 막히지 않는다 — 크론은 이미 등록돼 있고, 사람은 잊는다.

GOOD 스파이크 창을 코드로 정의하고, 배치가 스스로 그 창을 피하게 만든다
@Component @RequiredArgsConstructor
public class SpikeWindowGuard {

    // 설정으로 뺀다. 공개 시각이 바뀌거나 특별 이벤트가 생겨도 배포 없이 조정한다.
    @Value("${spike.window.start:22:50}") private LocalTime start;
    @Value("${spike.window.end:23:30}")   private LocalTime end;

    public boolean isForbiddenNow() {
        // 시간대를 명시한다. 서버가 UTC면 LocalTime.now()는 KST와 9시간
        // 어긋나 금지 창이 엉뚱한 시간에 걸린다.
        LocalTime now = LocalTime.now(ZoneId.of("Asia/Seoul"));
        return !now.isBefore(start) && now.isBefore(end);
    }
}

@Component @RequiredArgsConstructor
public class EpisodeStatsAggregationJob {

    private final SpikeWindowGuard guard;

    @Scheduled(cron = "0 */10 * * * *", zone = "Asia/Seoul")
    public void aggregate() {
        if (guard.isForbiddenNow()) {
            // 건너뛰는 것이 안전한 이유를 로그에 남긴다 — 이 집계는 10분 뒤에
            // 돌아도 결과가 같지만, 지금 도는 것은 DB의 동시 실행 슬롯을 먹는다.
            log.info("스파이크 창이므로 통계 집계를 건너뛴다. 다음 주기에 재시도한다.");
            return;
        }
        // ... 집계 로직
    }
}

두 겹으로 막는 이유 — 한 문장으로

코드 가드는 우리가 아는 배치를 막고, statement_timeout은 우리가 모르는 쿼리까지 막는다

준비의 품질은 "우리가 잊었을 때도 동작하는가"로 결정된다. 이 문장은 이 문서 전체를 관통한다 — 10절의 방어선 리허설도 같은 논리다.

9-4. (4) 앱 증설이 커넥션 총량을 함께 키운다는 함정

이것이 사전 스케일 아웃의 숨은 대가다. 인스턴스마다 자기 커넥션 풀을 가지므로, DB가 실제로 받는 커넥션은 인스턴스 수 × 인스턴스당 풀 크기다. 6대에서 33대로 늘리면 인스턴스당 설정을 건드리지 않아도 총량이 5.5배가 된다.

런북 항목으로 남길 것 — T-1일에 역산해 확인한다 "최대 파드 수 × 인스턴스당 풀 크기"가 DB가 감당하는 커넥션 수 안에 들어오는지 확인한다. 반응형 오토스케일링의 maxReplicas가 45라면 45 × 6 = 270개이므로, 그 값이 감당 가능한지, 아니면 커넥션 풀러를 앞에 둘지를 미리 결정해야 한다. 사전 증설 목표(33대)가 아니라 상한(45대)으로 계산하는 것이 포인트다.

10. ⑥ 마지막 방어선 — "켜지는지 확인"하는 것까지가 준비다

준비량을 넘는 유입이 오면 무엇을 하는가. 답 자체는 짧다. 게이트웨이의 rate limiting과 우선순위 기반 load shedding이 초과분을 빨리 거절해, 수용한 요청의 정상 처리를 지킨다.

이 문서에서 쓸 것은 다른 관점이다 rate limiting과 load shedding은 평상시에 발동하지 않는다. 발동하지 않는다는 것은 그 코드 경로가 실행되지 않는다는 뜻이고, 실행되지 않는 코드는 살아 있는지 알 수 없다는 뜻이다. 그래서 스파이크 때 처음 켜면 바로 그때 설정 오류를 발견한다. — "안 써본 fallback은 동작하지 않는다"와 정확히 같은 논리다.

실제로 발견되는 것들

임계값 단위 실수
초당 대신 분당을 넣어 방어가 아예 안 걸리거나, 반대로 평상시 트래픽을 다 버린다.
분류 규칙의 구멍
우선순위 분류가 새 엔드포인트를 커버하지 않아 결제 API가 비핵심으로 분류돼 있다.
Retry-After 누락
거절 응답에 Retry-After가 빠져 클라이언트가 즉시 재시도하며 부하를 증폭시킨다.
분산 카운터 미연결
카운터가 저장소에 붙지 못해 조용히 전부 통과시킨다 — 실패했다는 사실조차 드러나지 않는다.

방어선 리허설 — T-1일 항목

1
스테이징에서 임계를 실제 트래픽 아래로 낮춰 놓고 부하를 걸어, shedding이 발동하는지 / 무엇이 버려지는지 / 응답 코드와 Retry-After가 의도대로 나오는지를 눈으로 확인한다.
2
운영에서는 아주 좁은 조건으로 상시 발동시켜 경로를 살려 둔다. 예: 특정 테스트 헤더가 붙은 요청, 또는 전체의 0.01%를 강제로 shed 경로에 태워 "shedding 발동 건수" 지표가 0이 아닌 상태를 유지한다. 지표가 0으로 떨어지면 경로가 죽었다는 뜻이므로 알람을 건다.
3
degradation 스위치를 실제로 눌러 본다. 문서에 "추천을 끌 수 있음"이라고 적혀 있는 것과 그것이 동작하는 것은 다른 사실이다.
4
거절이 실제로 게이트웨이에서 일어나는지 확인한다. 안쪽에서 버리면 이미 스레드와 커넥션을 쓴 뒤이므로 방어 효과가 크게 줄어든다.

발동 순서 — 뒤집어 말하면 안 되는 3단 계단

① 스케일링→ ② degradation (비핵심 기능 저하)→ ③ shedding (요청 거절)

degradation이 shedding보다 앞인 이유: 비핵심 기능을 선제적으로 저하시켜 두면 그만큼 자원이 풀려서 버려야 하는 요청의 양 자체가 줄어들기 때문이다. 이 순서를 뒤집어 말하면 "추천 기능은 살려 두고 사용자 요청은 버렸다"가 되므로, 순서를 정확히 말하는 것이 중요하다.

티켓팅급 유입이 예상되면 대기열 시스템 투입까지 검토한다 — 초과분을 거절하는 대신 순번을 주고 기다리게 하는 방식이다.

11. 시간 축 런북 — 누가, 언제, 무엇을 하고 무엇을 확인하는가

계층 나열에 그치지 않고 시간표로 묶어 말하면 "매일 밤 이걸 실제로 굴려 본 사람"의 답이 된다. 그리고 런북이 되기 위해서는 하는 일 외에 두 칸이 더 있어야 한다 — 무엇을 보고 정상이라고 판단하는가, 그리고 무엇이 관측되면 준비를 되돌리거나 방어를 켜는가.

12. 스케일 인 · 되돌림 순서 · 피드백 루프

12-1. 되돌림 판단의 원칙 — 무엇을 포기하는지 사전에 정한다

원칙은 "핵심 여정을 마지막까지 지킨다"이고, 웹툰 도메인에서 핵심 여정은 회차 열람과 결제다.

1
추천 · 랭킹 · 개인화 → 정적 폴백으로 대체
2
통계 · 집계의 실시간성 → 반영 지연을 늘린다 (9-1의 버퍼 주기를 10초 → 60초)
3
비핵심 API · 봇 트래픽 → 우선순위 기반 shedding
4
신규 회차 외 콘텐츠 → 캐시 TTL을 대폭 늘려 DB 도달을 막는다
절대 포기하지 않는 것: 회차 열람 · 결제 · 로그인
이 순서가 사전에 합의돼 있어야 한다는 것이 요점이다 무엇을 먼저 끌지는 기술 판단이 아니라 비즈니스 판단이고, 정각에 온콜 엔지니어가 혼자 내릴 결정이 아니다.

12-2. 스케일 인 — 왜 바로 줄이면 안 되는가

스케일 인도 런북의 일부다. 피크가 지나면 대수를 되돌려야 비용이 절약되는데, 바로 줄이면 위험하다. 이유는 1절의 리드타임에 있다 — 줄인 직후에 부하가 돌아오면 되돌리는 데 다시 약 170초가 걸린다.

급히 줄인 직후 2차 파도가 오면

[33대에서 12대로 급감시킨 직후]

파드당 부하 = 33 ÷ 12 = 2.75배
원래 ρ 0.7 → 0.7 × 2.75 = 1.93
  → 용량의 두 배를 받는 상태

이 상태를 재증설 170초 동안 버텨야 한다.
그 사이 큐가 밀리고, 타임아웃이 나고,
재시도가 유입에 더해진다(2절).

그래서 비대칭 설정을 쓴다

scaleUp   안정화 창 0초
          + 30초마다 최대 2배 또는 4대
          (빠르게 늘린다)

scaleDown 안정화 창 900초(15분)
          + 분당 최대 10%씩
          (천천히 줄인다)

2차 파도는 실제로 온다 — 늦게 알림을 본 사용자, 첫 시도에 실패해 다시 들어오는 사용자, 다른 시간대에 있는 사용자.

축소의 전제 — graceful shutdown이 안 돼 있으면 이 모든 게 무의미하다 파드를 줄이는 것은 프로세스를 죽이는 일이므로, 종료 신호를 받으면 새 요청 수신을 멈추고(서비스 엔드포인트에서 먼저 빠지고) 처리 중인 요청을 마친 뒤 내려가야 한다. 이것이 안 돼 있으면 스케일 인 자체가 에러를 만들고, 그러면 "축소하면 에러가 난다"는 이유로 아무도 축소를 켜지 않게 되어 비용 절감이라는 목적이 사라진다.

12-3. 피드백 루프 — 이 준비가 한 번짜리가 아니게 만드는 것

T+1일의 기록이 다음 회차의 분자다. 7-1의 산정에서 예상 피크는 "지난 3회 실측 피크 × 보정"이었다. 그 실측 피크를 기록하지 않으면 다음 회차에도 감으로 잡게 된다.

① 실측 피크 RPS와 그 시각
정각에서 몇 초 뒤에 최대였는지도 중요하다 — 분할 발송의 효과가 여기 나타난다.
② 예상 대비 오차율
이 값의 추이가 보정 계수를 얼마로 할지의 근거가 된다.
③ 먼저 포화한 계층
다음 회차의 준비 우선순위가 바뀐다.
④ 비어 있던 런북 항목
런북 자체를 다음 회차에 고친다.
매일 밤 도는 일이므로, 오차율이 회차마다 줄어드는지가 이 팀이 학습하고 있는지의 지표가 된다

13. 인출 카드 · 꼬리질문 셀프 테스트

13-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

반응형 리드타임과 그 구성?
45(알아채기) + 65(띄우기) + 60(데우기) = 170초. 스파이크는 10초에 완성된다. 아홉 단계가 직렬이라 한 단계를 줄여도 전체는 별로 안 준다.
사전 증설 대수 공식?
ceil(λ ÷ 안전 처리량) × (1+여유). 3,726 ÷ 140 = 27대 → ×1.2 = 33대. "분자는 예측, 분모는 안전, 곱은 여유."
분모에 무엇을 쓰면 안 되나?
포화 처리량(200 RPS). 그러면 19대가 나오고 ρ=0.98 → 응답시간 51배(약 15초). 대수는 딱 맞는데 서비스는 죽어 있다.
워밍업 4원인?
4C — Compiled code(JIT), Class(로딩), Connection(빈 풀), Cache(빈 로컬 캐시). 넷 다 readiness probe를 통과한다.
계층 6종?
유입 → CDN → 방어선 → 앱 → 캐시 → DB. 바깥에서 흡수해 안쪽 도달량을 줄인다.
DB 도달량 축소 4종?
쓰기 큐 흡수(1/620), 캐시·복제본(미스율 5%→1% = 1/5), 배치 금지 창(2겹), 커넥션 총량 역산(187개).
커넥션 필요량은 무엇으로 정해지나?
λ × W = 3,726 × 0.05초 = 187개. 앱이 6대든 33대든 같은 값이므로, 대수를 늘리면 인스턴스당 풀은 줄여야 한다.
축소가 느린 이유?
안정화 창 900초 = 재증설 170초의 5배 이상. "지난 15분 동안 한 번이라도 33대가 필요했다면 유지한다." 고장이 아니라 설계.
준비의 마지막 항목은?
방어선(rate limiting · shedding)이 실제로 켜지는지 확인하는 것. 평상시 발동하지 않는 코드는 살아 있는지 알 수 없다.
가장 싸고 효과 큰 대비 하나?
푸시 분할 발송. 순간 피크가 20분의 1이 된다 — 서버를 20배 늘리는 것과 같은 효과인데 비용이 전혀 다르다.

13-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

공개 정각에 캐시가 전부 미스 나는 문제는 어떻게 막나요? 필수힌트: 3종 세트로 답하고, 마지막에 "우리 방법의 한계"를 스스로 말한다

캐시 스탬피드 대응 3종 세트로 답한다.

① 사전 적재 — 공개 전에 신작 키를 미리 계산해 넣는다. 예측 가능한 스파이크만 쓸 수 있는 특권이므로 이 질문에서 가장 먼저 말해야 한다. T-10분, 수십~수백 키, DB 쿼리 수백 건이면 끝난다.
② single flight — 미스 시 재계산을 키당 한 요청으로 제한하고 나머지는 그 결과를 공유한다.
③ 만료 분산 — TTL에 흔들림(jitter)을 줘 동시 만료를 피하고, 인기 키는 만료 전 백그라운드 갱신으로 미스 자체를 없앤다.

여기에 한계를 덧붙이면 한 단계 위의 답이 된다

ConcurrentHashMap 기반 single flight는 JVM 안에서만 동작하므로, 인스턴스가 33대면 같은 키에 최대 33건이 DB로 간다. 수만 건보다는 압도적으로 낫지만 1건은 아니다. 1건으로 줄이려면 분산 락이 필요하고, 그 대가(획득 실패 시 무엇을 반환할지, 홀더가 죽으면 어떻게 될지)를 설계해야 한다.

그리고 이미지 계층에서는 CDN이 같은 일을 대신 해준다는 것도 짚는다 — request coalescing이 엣지 안의 동시 미스를 하나로 합치고, origin shield가 엣지들 사이의 중복 미스를 합친다.

사전 스케일 아웃 규모는 어떻게 산정하나요? 필수힌트: 나눗셈으로 답하되, 분모에 0.7을 곱하는 이유가 이 답의 절반이다

나눗셈으로 답한다. 분자는 예상 피크 λ — 지난 공개일들의 실측 피크에 성장 추세와 작품 화제성 보정을 얹는다(2,700 × 1.15 × 1.20 = 3,726 RPS). 분모는 인스턴스당 안전 처리량 — 부하 테스트로 잰 포화 처리량 200 RPS에 목표 사용률 0.7을 곱한 140 RPS다. 나눗셈 결과 ceil(3,726 ÷ 140) = 27대, 예측 오차 여유 20%를 얹어 33대.

여기서 반드시 짚어야 하는 것이 분모에 0.7을 곱하는 이유다. 포화 처리량 200으로 나누면 19대가 나오는데, 그러면 사용률이 3,726 ÷ 3,800 = 0.98이 되고 응답시간 배수가 1/(1−0.98) = 51배가 된다. 대수 계산은 딱 맞게 나왔는데 서비스는 죽어 있는 상태다.

같은 답을 L = λW로 검산할 수 있다는 것까지 말하면 완결된다. λ 3,726 × W 0.3초 = 동시 처리 요청 1,118건, 인스턴스당 안전 동시 요청 140 × 0.3 = 42건, 1,118 ÷ 42 = 27대로 같은 답이다. 처리량으로 세면 "몇 대"가 나오고, L로 세면 "그 대수가 물어야 하는 동시 요청 수"가 나오는데, 후자가 스레드풀 · 커넥션 풀 · in-flight 임계를 정할 때 그대로 쓰이는 숫자다.

마지막으로 "산정이 틀릴 수 있으니 마지막 방어선(shedding)과 반응형 오토스케일링을 뒤에 둔다"까지 붙인다.

스케일 아웃을 충분히 했는데도 DB가 죽으면요? 필수힌트: 먼저 "증설이 병목을 어디로 미는지"를 말하고, 그다음 네 가지를 센다

stateless 계층 증설은 병목을 없애는 게 아니라 상태 있는 계층으로 밀어 넣는 것임을 먼저 짚는다. 파드가 늘면 DB로 향하는 동시 요청과 커넥션 요구만 커진다 — 앱을 6대에서 33대로 늘릴 때 인스턴스당 풀 크기를 그대로 두면 DB에 꽂히는 커넥션 총량이 5.5배가 된다.

답은 DB 도달량 축소이고, 네 가지를 구체적으로 든다.

① 읽기는 캐시 히트율로 흡수 — 도달량은 히트율이 아니라 미스율에 비례하므로 95%→99%는 DB 부하를 5분의 1로 줄이는 것이다. 남는 읽기는 복제본으로 보내되 복제 지연을 미리 확인한다.
② 쓰기는 큐로 흡수해 비동기 집계로 — 조회수 UPDATE를 10초 단위 UPSERT로 바꾸면 3,726건/초 → 6건/초, 약 620분의 1.
③ 스파이크 시각에 배치·통계 쿼리 금지 — 가장 싸고 가장 자주 잊는 항목. 문서가 아니라 코드 가드 + statement_timeout으로 두 겹으로 막는다.
④ 커넥션 총량을 λ로 역산 — 필요량 3,726 × 0.05초 = 187개는 앱 대수와 무관하므로, 인스턴스당 풀은 187 ÷ 33 = 6개로 오히려 줄어야 한다.

그래도 넘치면 DB 앞이 아니라 게이트웨이에서 shedding한다. 안쪽에서 버리면 이미 스레드와 커넥션을 쓴 뒤이므로 방어 효과가 크게 줄어든다.

"예측 기반 준비"와 "예측 실패 대비"는 별개의 계층이라는 인식을 보여야 한다. 네 단계로 답한다.

① 반응형 오토스케일링이 초과분을 따라가게 두되, 따라잡는 데 약 170초가 걸린다는 것을 숫자로 알고 있어야 한다.
② 그 170초를 버티는 것이 degradation이다 — 비핵심 기능을 선제적으로 저하시켜 자원을 풀면 버려야 하는 요청의 양 자체가 줄어든다.
③ 그래도 넘치면 게이트웨이에서 우선순위 기반 load shedding으로 봇 · 비핵심 API부터 거절하고, 회차 열람 · 결제 · 로그인은 끝까지 지킨다.
④ 이번 실측치를 다음 산정에 반영하는 피드백 루프까지 언급한다.

그리고 가장 중요한 것을 마지막에 붙인다

이 방어선들은 평상시에 발동하지 않으므로 살아 있는지 알 수 없는 코드다. 스파이크 때 처음 켜면 그때 설정 오류(임계값 단위 실수, 우선순위 분류에서 빠진 신규 엔드포인트, 누락된 Retry-After)를 발견한다. 그래서 사전 준비의 마지막 항목은 "방어선이 실제로 켜지는지 확인하는 것"이고, 이것은 "안 써본 fallback은 동작하지 않는다"와 같은 논리다. 스테이징에서 임계를 낮춰 발동시켜 보고, 운영에서는 아주 좁은 조건으로 상시 발동시켜 "shedding 발동 건수" 지표가 0이 아닌 상태를 유지한다.

바로 줄이면 위험하고, 그 이유는 재증설 리드타임의 비대칭이다. 33대를 12대로 급히 줄인 직후 2차 파도가 오면 파드당 부하가 2.75배가 되어 사용률 0.7이 1.93이 되고, 그 상태를 재증설이 끝나는 약 170초 동안 버텨야 한다. 그 사이 큐가 밀리고 타임아웃이 나고 재시도가 유입에 더해진다.

2차 파도는 실제로 온다 — 늦게 알림을 본 사용자, 첫 시도에 실패해 다시 들어오는 사용자, 다른 시간대의 사용자.

전제로 graceful shutdown이 돼 있어야 한다는 것까지 붙인다. 축소가 진행 중 요청을 끊으면 스케일 인 자체가 에러를 만들고, 그러면 아무도 축소를 켜지 않게 되어 비용 절감이라는 목적 자체가 사라진다.

계산부터 한다. ①②③을 각각 15초에서 5초로 줄이면 45초 → 15초, 즉 30초를 번다. 170초가 140초가 된다. 여전히 스파이크 10초보다 14배 느리다.

왜 별 효과가 없는지가 요점이다. 남는 ⑦ 앱 부팅 30초 + ⑨ 워밍업 60초 = 90초는 지표 주기와 아무 상관이 없다. 지표 경로(①~④)를 0으로 만들어도 125초가 남는다 — 리드타임의 대부분은 "결정하기까지"가 아니라 "결정한 뒤 실제로 쓸 수 있게 되기까지"에 있다.

(나) 증설을 늦게 시작한다. T-45분이 필요한 이유는 부팅 30초 + 워밍업 60초가 있고 확인할 시간(T-30분 체크)이 필요하기 때문이다. 기동 시간을 줄이면(이미지 슬림화, 노드에 이미지 사전 캐싱, 불필요한 빈 초기화 제거) 증설 시작을 뒤로 당길 수 있다. 노드 여유 확보는 파드를 띄우는 것보다 싸므로, 노드는 미리 잡고 파드는 늦게 띄우는 조합도 가능하다.

(다) 회차별로 차등한다. 산정식의 화제성 보정 계수가 이미 그 자리다. 모든 공개일에 33대를 고정으로 쓰는 것이 아니라 작품마다 분자를 다시 계산하는 것이 원래의 설계다 — 그리고 그 정확도를 올리는 것이 T+1일 기록(피드백 루프)의 목적이다.

그러므로 분할이 줄이는 것은 "알림에 의해 유발된 동시 진입"이고, 그것이 곧 5절 계산의 대상이었다(수신 후 5분 내 진입률 20%).

형평성이 문제가 된다면 설계로 푼다. 배치 순서를 회차마다 로테이션하거나 무작위화하면, 특정 사용자가 항상 마지막 배치에 들어가는 일이 없다. 순서를 기록해 두는 것이 로테이션의 전제다.

그리고 역설적이지만 — 분할하지 않아서 서버가 느려지면 먼저 알림을 받은 사용자도 못 본다. 일제 발송의 "공평함"은 모두가 같이 느려지는 공평함이다.

런북에 배포 동결이 T-1분에 있는데, T-45분에 증설한 뒤 배포가 나가면요? 시니어 변별힌트: 배포는 파드를 교체한다. 교체된 파드는 무엇을 잃는가

날카로운 지적이고, 런북의 T-1분은 "최종 동결 확인" 시점으로 읽어야 한다. 실질 동결은 사전 증설이 시작되는 T-45분 이전으로 앞당기는 것이 안전하다. 이유가 셋이다.

① 워밍업이 리셋된다. 롤링 배포는 파드를 새 이미지의 새 파드로 교체하므로, 교체된 파드는 부팅 30초 + 워밍업 60초를 처음부터 다시 한다. T-30분 체크에서 "파드별 p99가 기존과 같은 수준"을 확인할 수 없게 된다.
② 교체 중에는 용량이 줄어든다. 롤링 배포는 순차로 교체하므로, 그 순간의 Ready 파드 수는 33보다 적다. 스파이크와 겹치면 용량이 줄어든 상태로 피크를 맞는다.
③ 새 이미지는 노드에 캐시돼 있지 않을 수 있다. 1절 ⑥이 10초 자리에서 100초 자리로 뛴다.

동결의 의미: "T-1분에 잠근다"가 아니라 "T-45분 이후의 33대가 피크까지 그대로 살아 있게 한다"

런북 관점의 확인 항목으로 바꾸면 — T-1시간 칸에 "진행 중이거나 예약된 롤아웃이 없는가"가 들어가야 한다. T-1분에 발견하면 이미 늦다.

읽기를 복제본으로 돌렸는데 스파이크 중에 복제 지연이 커지면요?힌트: 무엇을 확인하고, 무엇을 복제본에 보내지 않을 것인가

먼저 "언제 확인하는가"가 답의 절반이다. 복제 지연은 스파이크 중에 처음 보는 값이 아니라 T-1일과 T-0 대시보드에 이미 올라와 있어야 하는 값이다. PostgreSQL이라면 프라이머리에서 pg_stat_replication의 sent_lsn과 replay_lsn 차이를, 복제본에서 now() - pg_last_xact_replay_timestamp()를 본다.

지연이 커졌을 때의 증상은 "느려짐"이 아니라 "이상함"이다. "방금 본 회차가 목록에 없다" 같은 현상이 생긴다 — 사용자에게는 장애보다 버그로 보인다.

대응은 경로별로 나눈다. 자기가 방금 쓴 것을 바로 읽는 경로(결제 직후 상태 확인, 방금 남긴 댓글)는 복제본에 보내지 않는다. 반면 회차 목록·랭킹처럼 몇 초 늦어도 되는 조회는 복제본으로 보낸다. "복제본으로 보낼 수 있는 쿼리"의 목록이 사전에 정해져 있어야 스파이크 중에 판단할 일이 없다.

그리고 지연을 키우는 원인을 줄이는 것이 근본 대응이다. 지연은 프라이머리의 쓰기가 몰릴 때 커지므로, 9-1의 쓰기 큐 흡수(3,726건/초 → 6건/초)가 복제 지연 대책이기도 하다. 그리고 9-3의 배치 금지 창도 같은 효과를 낸다 — 이 문서의 대책들이 서로 독립이 아니라는 것을 보여주는 지점이다.

"오토스케일링 걸어놨습니다"로 답하면 왜 감점인가요?힌트: 틀린 말은 아니다. 그 답에 무엇이 빠져 있나

틀린 말은 아니지만, 이 질문이 묻는 것을 정면으로 비껴간다. 이유가 셋이다.

① 이 질문의 전제가 "시각을 안다"는 것이다. 시각을 아는데도 감지 후 대응에 맡기겠다는 것은, 가진 정보를 안 쓰겠다는 말이 된다. 면접관이 확인하려는 것은 예측 가능성을 자원으로 쓸 줄 아는가다.
② 리드타임을 모른다는 뜻으로 들린다. 오토스케일링이 몇 초 만에 따라잡는지 숫자로 말할 수 없다면, 그 도구를 설정해 본 적은 있어도 겪어 본 적은 없는 사람처럼 들린다.
③ 앱 계층 하나만 말한 답이다. 질문은 "어떤 계층에서"를 명시적으로 묻는다. CDN·캐시·DB·유입은 오토스케일링으로 해결되지 않는다 — 오히려 앱을 늘리면 DB 커넥션 총량이 5.5배가 되는 역효과가 있다.

더 나은 첫 문장: "시각을 아는 스파이크이므로 감지-대응이 아니라 사전 준비의 문제로 봅니다"

그리고 오토스케일링을 버리는 것이 아니다라는 단서를 곧바로 붙인다 — 예측 초과분을 따라가는 보조 수단으로 남긴다는 위치 설정이 균형 잡힌 답이다.

한 줄 요약
시각을 아는 스파이크는 감지-대응이 아니라 사전 준비의 문제다 — 반응형 스케일링의 리드타임은 알아채기 45초 + 띄우기 65초 + 데우기 60초 = 약 170초인데 스파이크는 10초에 완성되므로 원리적으로 늦고, 그래서 사전 스케일 아웃의 규모를 예상 피크 3,726 RPS ÷ 인스턴스당 안전 처리량 140 RPS = 27대 + 여유 20% = 33대로 계산해(포화 처리량 200으로 나누면 사용률 0.98에서 응답시간이 51배가 된다) 시각 기반으로 미리 만들고, 유입 분산(푸시 분할) · CDN 사전 워밍 · 워밍업을 readiness 앞에 두는 설정 · 캐시 사전 적재와 스탬피드 방지 · DB 도달량 축소(쓰기 큐 흡수로 620분의 1, 배치 금지 창, 커넥션 총량 역산)를 계층별로 준비한 뒤, 예측 실패에 대비한 degradation과 shedding을 실제로 켜지는지 확인해 두고, 이 전부를 T-1일부터 T+30분까지 확인 항목과 중단 기준이 적힌 시간 축 런북과 피드백 루프로 묶는 것이 완결된 답이다.
