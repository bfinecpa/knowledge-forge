로드밸런서 — 역할과 알고리즘
"특정 서버만 부하가 몰릴 때"를 푸는 열쇠

면접 질문: "로드밸런서의 역할과 알고리즘(round robin, least connection)을 설명해주세요."

핵심 관전 포인트 — 로드밸런서는 여러 서버에 트래픽을 나눠주는 분배기이자, 헬스체크로 죽은 서버를 자동으로 빼는 장애 격리 장치이며, scale-out의 유일한 진입점이다. 분배 알고리즘은 round robin(순서대로 한 대씩)이 기본이지만, 이는 "모든 요청의 처리 시간이 비슷하다"는 가정 위에서만 공평하다 — 무거운 요청과 가벼운 요청이 번갈아 들어오면 순번은 4:4로 공평한데 서버가 실제로 일한 시간은 10:1로 벌어진다. 이때 필요한 것이 "미완료 요청 수"(LB가 보내놓고 아직 응답을 못 받은 요청 수)가 가장 적은 서버로 보내는 least connection이다. 단 이 지표도 근사치라, keep-alive로 연결이 오래 재사용되거나 long-polling·SSE처럼 오래 열려 있으면서 일은 안 하는 연결이 섞이면 "연결 수"가 작업량을 대변하지 못한다. 그리고 헬스체크는 민감도가 양쪽으로 다 위험하다 — 너무 민감하면 정상 서버가 들락날락하고, 너무 둔감하면 죽은 서버로 계속 보내며, 헬스체크가 DB까지 확인하게 만들면 DB 순단에 전 서버가 동시에 빠져 서비스가 통째로 내려간다. LB를 블랙박스로 두면 "서버 스펙이 같은데 왜 한 대만 힘들지?"를 영원히 못 푼다.
  • 1
    LB는 성능 부가장치가 아니라 scale-out의 구조적 전제다 — 클라이언트에게는 항상 같은 하나의 주소를 주고 뒤에서 실제 서버를 고른다. 역할은 셋: 트래픽 분산 · 헬스체크 기반 장애 격리 · 공통 관심사(TLS 종료·경로 라우팅·rate limit)의 집결지.
  • 2
    알고리즘은 "무엇이 공평인가"의 서로 다른 정의다 — RR은 "받은 개수가 같다"는 공평이라 요청 비용이 균일할 때만 부하 균등이 된다. 무거운·가벼운 요청이 번갈아 오면 순번 4:4인데 일한 시간은 4,000ms : 400ms. least connection은 미완료 요청 수라는 관측값으로 그 가정을 대체해 같은 8건을 2,200 : 2,200으로 만든다.
  • 3
    그 미완료 수도 근사치라 역전된다 — SSE·keep-alive·갓 투입된 서버 앞에서 무너진다. 그래서 답은 "뭐가 더 좋냐"가 아니라 "우리 요청 분포가 어느 가정에 맞냐"이고, 근본 처방은 알고리즘 교체보다 성격이 다른 트래픽을 분리하는 것인 경우가 많다.

0. 질문 + 출제 의도

질문: "로드밸런서의 역할과 알고리즘(round robin, least connection)을 설명해주세요."

출제 의도: least connection이 필요한 상황(요청별 처리 시간 편차)을 아는지 본다. LB를 블랙박스로 두면 "특정 서버만 부하가 몰리는" 현상을 영원히 못 푼다 — 알고리즘의 가정이 깨지는 지점을 아는 사람만이 그 장애를 진단할 수 있다.

이 페이지가 겨냥하는 약점 세 가지 ① "RR은 순서대로, LC는 적은 쪽으로"라는 사전적 설명에서 끝나는 것 → 5·6·7절에서 요청 8건을 손으로 배정해 4,000:400 → 2,200:2,200이 나오는 과정을 직접 따라간다.
② "least connection이 항상 낫다"고 답하는 것 → 8절에서 미완료 수가 작업량을 배신하는 세 가지 상황을 세고, 근사가 역전되는 구간을 보여준다.
③ 헬스체크를 "켜면 좋은 것"으로만 아는 것 → 2절에서 민감도의 양방향 위험과, 헬스체크 한 줄이 DB 3초 순단을 전면 장애로 증폭시키는 경로를 도식으로 박는다.

1. LB의 세 역할 — 분배기 그 이상, scale-out의 입구

서버가 한 대일 때는 로드밸런서라는 말을 들을 일이 없다. api.example.com을 DNS로 조회하면 그 한 대의 IP가 나오고, 요청은 거기로 간다. 서버를 두 대로 늘리는 순간 새 문제가 생긴다 — "어느 IP를 알려줄 것인가." 클라이언트가 서버 목록을 알고 직접 고르게 만들 수는 없다. 서버가 늘거나 줄 때마다 전 세계 클라이언트를 고쳐야 하고, 죽은 서버를 클라이언트가 알아서 피할 방법도 없다.

그래서 "클라이언트에게는 항상 같은 하나의 주소를 주고, 그 주소 뒤에서 실제 서버를 골라 넘겨주는 중간 계층"을 둔다. 이것이 LB다. 즉 LB는 성능을 위한 부가 장치가 아니라 scale-out을 성립시키는 구조적 전제다.

비유 — LB는 은행 창구 안내원이다 손님(요청)을 빈 창구(서버)로 보내고, 자리를 비운 창구(죽은 서버)로는 보내지 않으며, "대출 상담은 2층"(경로 라우팅)도 안내한다. 손님은 창구가 몇 개인지, 어느 창구가 쉬는지 알 필요가 없다 — 안내원만 보면 된다.

역할 ③이 왜 값싼 위치인지 — 세 가지 예로 굳히기

TLS 종료
HTTPS 복호화를 LB에서 한 번만. 서버 N대가 각자 복호화 비용을 내지 않고, 인증서 갱신도 한 곳에서 끝난다.
경로 라우팅
/api/**는 API 그룹, /images/**는 이미지 그룹으로. 무거운 API를 다른 그룹으로 격리하는 처방(10절)의 도구가 된다.
rate limit / load shedding
애플리케이션에서 막으면 이미 스레드·커넥션을 쓴 뒤지만, LB에서 막으면 그 요청은 애플리케이션에 도달조차 하지 않는다.

역할 ①에서 반드시 짚어야 할 것은 "무엇을 단위로 나누는가"다 — 요청 단위인지 TCP 연결 단위인지에 따라 같은 트래픽이 전혀 다르게 분배된다(3절). "LB가 요청을 나눠준다"를 무비판적으로 받아들이면 10절의 장애를 못 푼다.

2. 헬스체크 — 없을 때보다 나쁠 수 있는 장치

헬스체크(health check)는 LB가 각 서버에 주기적으로 "너 살아 있냐"를 확인하고, 응답하지 못하는 서버를 분배 대상에서 자동으로 빼는 장치다. 서버 한 대가 죽어도 사용자는 모르게 지나가는 것, 롤링 배포에서 구 버전을 하나씩 빼고 새 버전을 넣는 것이 전부 이 메커니즘 위에서 돌아간다. 문제는 이 장치가 양방향으로 위험하다는 점이다.

2-2. 가장 위험한 실수 — 헬스체크가 의존성까지 확인할 때

헬스 엔드포인트가 DB에 쿼리를 던져 보고 결과에 따라 200/503을 내려주게 만들면 논리적으로는 그럴듯하다. "DB를 못 쓰면 일을 못 하니 트래픽 받지 말자." 그런데 DB는 모든 서버가 공유하는 자원이다. 판정 근거가 공유 자원이면, 판정 결과도 전 서버에 동시에 나온다.

원칙 — 되돌리기 어려운 판정에는 "나 혼자만의 사정"만 넣는다

LB가 보는 헬스체크는 "이 프로세스가 요청을 받을 수 있는 상태인가"만 판정하고,
의존성 상태는 별도 엔드포인트로 분리해 사람과 모니터링이 본다

판정의 결과가 "트래픽 제외"라는 되돌리기 어려운 행동으로 이어지기 때문이다. 반대로 사람이 보는 대시보드에는 DB·Redis 상태를 다 담아도 된다 — 그 판정은 아무 행동도 자동 유발하지 않으니까.

2-3. Spring Boot Actuator — 분리를 설정으로 구현하기

Before 헬스체크 하나에 전부 넣은 설정 — DB 순단이 전면 장애가 된다
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      show-details: always
# /actuator/health 는 기본적으로 DataSource, Redis 등 등록된 모든
# HealthIndicator를 합산한다. DB가 죽으면 이 엔드포인트가 503을 내려주고,
# 이걸 LB 헬스체크로 쓰면 전 서버가 동시에 분배 대상에서 빠진다.
After liveness / readiness 를 나누고, LB에는 "자기 사정"만 보여준다
management:
  endpoints:
    web:
      exposure:
        include: health
  endpoint:
    health:
      probes:
        enabled: true
      # probes.enabled=true 를 켜면 두 엔드포인트가 따로 열린다.
      #   /actuator/health/liveness  — "프로세스가 살아 있나"   (실패 시 재시작 대상)
      #   /actuator/health/readiness — "지금 트래픽을 받아도 되나" (실패 시 분배 제외)
      group:
        liveness:
          include: livenessState
          # 여기에 DB를 넣으면 DB 장애로 컨테이너가 재시작된다. 최악의 조합이다.
        readiness:
          include: readinessState
          # 기동 완료 여부만 본다. db, redis 를 여기 넣지 않는 것이 이 설정의 요점.
          # 공유 의존성 장애는 "전 서버 동시 제외"로 증폭되기 때문이다.
      show-details: never   # 헬스 엔드포인트는 인증 없이 노출되므로 내부 정보를 감춘다

두 프로브의 차이는 "실패했을 때 시스템이 취하는 행동"으로 외운다

liveness 실패 → 재시작
되돌릴 수 없고 진행 중인 요청까지 죽인다. 그래서 readiness보다 훨씬 둔감하게 잡아야 한다. 일시적 지연으로 재시작을 유발하면 스스로 장애를 만든다.
readiness 실패 → 트래픽 제외
되돌리기 쉽다(다시 통과하면 복귀). 그래서 상대적으로 민감해도 된다. 단 복귀 진동을 막기 위해 successThreshold를 함께 둔다.
liveness에 의존성을 넣으면 DB 장애로 전 컨테이너가 재시작된다 — 이 문서 최악의 조합
Kubernetes 민감도는 결국 이 네 숫자로 드러난다
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  periodSeconds: 5        # 5초마다 확인
  timeoutSeconds: 2       # 2초 안에 응답 없으면 실패로 센다
  failureThreshold: 3     # 연속 3회 실패해야 제외 → 순간 지연 한 번에 흔들리지 않는다
  successThreshold: 2     # 연속 2회 성공해야 복귀 → 복귀 직후 다시 빠지는 진동을 막는다
  # 최악의 방치 시간 = 5초 × 3회 = 15초. 이 곱셈을 해보고 SLO와 견줘 정한다.

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  periodSeconds: 10
  failureThreshold: 6     # 10초 × 6회 = 60초. readiness보다 훨씬 둔감하게 잡는다.
  # 이유: 이쪽 실패의 결과는 "재시작"이라 되돌릴 수 없다.
  #       일시적 지연으로 재시작을 유발하면 스스로 장애를 만든다.

2-4. nginx의 헬스체크는 능동이 아니라 수동이다

이 경계를 모르면 "설정해 본 적 없음"이 드러난다 오픈소스 nginx의 기본 헬스체크는 능동(active)이 아니라 수동(passive)이다. 별도의 확인 요청을 보내는 게 아니라, 실제 사용자 요청이 실패하는 것을 세어 판정한다. 능동적 헬스체크(health_check 디렉티브)와 신규 서버에 트래픽을 서서히 올리는 slow_start는 상용 버전(NGINX Plus)의 기능이다. 오픈소스 nginx만 쓴다면 그 역할을 앞단의 클라우드 LB(ALB 등)나 쿠버네티스 readiness probe가 맡는 구성이 일반적이다.
nginx max_fails / fail_timeout — 두 값이 한 쌍으로 움직인다
upstream api_servers {
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=10s;
    # max_fails=3, fail_timeout=10s 의 뜻은 두 가지가 한 쌍이다.
    #   ① 10초 안에 실패가 3번 누적되면 그 서버를 "장애"로 판정한다.
    #   ② 판정되면 그 뒤 10초 동안 분배 대상에서 제외한다.
    # 즉 fail_timeout 은 "실패를 세는 창"과 "제외 기간"을 겸한다.
    # max_fails=0 은 "절대 제외하지 않는다"는 뜻 — 헬스체크를 끄는 설정이라
    # 죽은 서버로 계속 보내게 된다.
}

헬스체크 3대 실수 — "민 · 둔 · 의"

민 — 너무 민감
GC 300ms에도 제외 → 플래핑 → 남은 서버 과부하 → 연쇄 제외로 0대
둔 — 너무 둔감
주기 × 임계만큼 죽은 서버로 계속 전송. 30초×5회 = 150초 동안 1/N이 허공으로
의 — 의존성 포함
공유 자원(DB)을 판정에 넣으면 전 서버 동시 제외. 3초 순단이 전면 장애로 증폭

셋 중 실무에서 가장 크게 터지는 것은 세 번째다. 앞의 둘은 서버 일부의 문제지만, 세 번째는 정의상 전 서버가 동시에 걸린다.

3. L4 vs L7 — "무엇을 단위로 분배하는가" 필수

이름의 숫자는 OSI 계층 번호다. L4는 전송 계층(TCP/UDP)까지만 보고, L7은 응용 계층(HTTP)까지 해석한다. 이 차이가 곧 분배 단위의 차이로 이어지고, 그것이 10절 장애의 진단 열쇠가 된다.

실전에서는 둘을 겹쳐 쓴다 — 맨 앞에서 L4(또는 DNS·애니캐스트)로 대량 유입을 받고, 그 뒤 L7 게이트웨이가 서비스별로 정교하게 분배한다.

속도해석 없음 → 빠르고 대용량에 강함해석 비용과 지연이 붙음
요청 단위 재시도어렵다 — 연결이 끊긴 뒤 그 위의 요청이 처리됐는지 알 방법이 없다가능 — 요청 경계를 알므로 안전하게 재시도·서킷브레이킹

4. LB 자신은 단일 장애점이 아닌가 — 계층으로 답한다

모든 요청이 반드시 지나간다는 것은, LB가 죽으면 서버가 다 살아 있어도 서비스가 죽는다는 뜻이다. LB는 정의상 단일 장애점(SPOF) 후보다. 그래서 LB도 이중화한다. 전형적인 방식은 가상 IP(VIP) 인수 — 액티브와 스탠바이를 쌍으로 두고, 클라이언트에게 알려준 IP를 물리 장비의 IP가 아니라 둘 사이를 옮겨 다닐 수 있는 가상 IP로 잡는다. 액티브가 죽으면 스탠바이가 그 IP를 인수하므로 클라이언트가 보는 주소는 바뀌지 않는다.

여기서 "그러면 분배기를 누가 분배하나"라는 재귀 질문이 남는데, 답은 계층을 올라가는 것이다.

한 걸음 더 — 이중화의 정확한 의미 이중화는 "죽어도 되게" 만드는 것이지 "죽어도 아무 일 없게" 만드는 것이 아니다. 페일오버 사이의 요청은 실패하고, 액티브 한 대 용량으로 전체를 받고 있었다면 스탠바이가 같은 용량을 상시 확보하고 있지 않으면 페일오버 직후 그쪽이 무너진다.

5. 알고리즘 = "공평"의 서로 다른 정의 — Round Robin

이 절 전체를 지배하는 관점 모든 분배 알고리즘은 "무엇이 공평인가"에 대한 서로 다른 정의이고, 각 정의는 특정 가정 위에서만 실제 부하 균등으로 이어진다. 알고리즘을 고르는 일은 "좋은 것 고르기"가 아니라 "우리 요청 분포가 어느 가정에 맞는지 판정하기"다.

Round Robin(RR)은 서버 목록을 돌면서 한 대씩 차례로 보낸다. 상태를 하나도 추적하지 않으므로 구현이 가장 단순하고, LB의 기본값인 경우가 많다.

RR이 정의하는 공평
"받은 요청 개수가 같다"
그 정의가 성립할 조건
모든 요청의 처리 비용이 비슷해야 한다. 요청 하나가 다 같은 무게라야 개수를 똑같이 나누는 것이 곧 일을 똑같이 나누는 것이 된다.

서버 스펙이 서로 다르면 이 정의를 조금 비틀어 가중 라운드 로빈(weighted round robin)을 쓴다. 좋은 서버에 순번을 더 자주 준다.

nginx weight — 무엇을 보정하고 무엇을 보정하지 못하는가
upstream api_servers {
    server 10.0.1.11:8080 weight=3;   # 3배 좋은 장비라 4번 중 3번을 받는다
    server 10.0.1.12:8080 weight=1;
    # 가중치는 "장비 성능 차이"를 보정할 뿐,
    # "요청 무게 차이"는 보정하지 못한다.
}

가장 흔한 오해

"weighted round robin이면 무거운 요청도 보정되지 않나요?" — 아니다. weight는 서버 쪽 상수다. 어느 서버가 몇 번에 한 번 순번을 받을지를 정할 뿐, 지금 그 서버가 얼마나 바쁜지는 여전히 전혀 보지 않는다. 요청 무게의 편차를 흡수하려면 서버의 현재 상태를 관측하는 알고리즘(7절)이 필요하다.

7. Least Connection — "연결 수"가 정확히 무엇을 세는가

요청이 올 때마다 현재 연결 수가 가장 적은 서버로 보낸다. 이름만 들으면 무엇을 세는지 애매하니 정의를 못 박자.

정의 — 이름에 속지 말 것

least connection이 세는 "연결 수" = LB가 그 서버로 보내놓고 아직 응답을 다 받지 못한 요청 수
= 미완료 요청 수 (in-flight)

서버의 CPU 사용률이나 스레드 상태를 물어보는 것이 아니다. LB가 자기가 보낸 것과 받은 것을 세어 뺀 값일 뿐이다. 그래서 "연결 수"보다 "미완료 요청 수"라고 부르는 편이 오해가 적다.

이 값이 좋은 지표인 이유 — 관측값이 가정을 대신한다 처리 시간을 몰라도 처리 시간의 결과가 자동으로 반영된다. 무거운 요청을 받은 서버는 그것이 끝나지 않는 동안 미완료 수가 계속 1을 유지하므로, LB는 요청 종류를 몰라도 "저 서버는 아직 바쁘다"는 것을 알게 된다. RR이 가정에 기댔다면 LC는 관측에 기댄다.
비유 — 마트 계산대 줄 서기 줄에 선 사람 수(미완료 요청 수)만 보고 짧은 줄에 선다. 카트에 물건이 얼마나 담겼는지(요청의 무게)는 안 보이지만, 앞사람이 오래 걸리면 그 줄이 줄어들지 않으므로 결과적으로 반영된다. — 다만 "카트는 비었는데 안 움직이는 줄"이 섞이는 순간 이 직관이 뒤집힌다. 그것이 8절이다.

7-2. nginx 설정 — 그리고 zone을 빠뜨리면 생기는 일

Before 기본 round robin — 처리 시간 편차가 크면 부하 쏠림
upstream api_servers {
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    server 10.0.1.13:8080;
    # 문제: 무거운 요청을 연달아 받은 서버에 미완료 작업이 누적돼도
    #       순번은 계속 돌아온다 → 그 서버만 응답 지연·스레드풀 고갈
}
After least_conn — 미완료 요청이 적은(한가한) 서버부터 채운다
upstream api_servers {
    least_conn;
    zone api_servers 64k;
    # zone 이 없으면 미완료 수 집계가 워커 프로세스별로 따로 유지된다.
    # nginx 워커가 8개면 각 워커가 자기가 보낸 것만 세어 8개의 부분 시야로
    # 판단하는 셈이 되므로, 공유 메모리 존을 잡아 집계를 하나로 모은다.

    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 max_fails=3 fail_timeout=10s;
    # 효과: 요청별 처리 시간이 달라도 "밀린 일의 양" 기준으로 분배돼
    #       특정 서버 쏠림이 구조적으로 완화된다
}
대가는 상태 추적 — 그리고 "집계 범위 = 판단의 정확도" LB가 서버별 미완료 수를 계속 세고 갱신해야 하므로 RR보다 무겁다. 게다가 집계 범위가 곧 판단의 정확도가 된다 — nginx 워커별로 따로 세면 부분 시야로 판단하게 되고, LB가 여러 대로 분산돼 있으면 각 LB는 자기가 보낸 요청만 알기 때문에 전역적으로는 부정확할 수밖에 없다.

8. 미완료 수가 거짓말할 때 — 3대 함정 시니어 변별

여기가 이 문서에서 가장 중요한 지점이다. least connection의 미완료 요청 수는 어디까지나 작업량의 근사치이고, 그 근사가 무너지는 상황이 실무에 흔하다.

8-1. 함정 ① 오래 열려 있지만 일은 하지 않는 연결

long-polling(응답을 보내지 않고 붙잡고 있다가 이벤트가 생기면 응답하는 방식), SSE(Server-Sent Events, 서버가 한 응답 스트림으로 계속 밀어 보내는 방식), WebSocket이 그렇다. 이 연결들은 몇 분에서 몇 시간 동안 미완료 상태로 남아 있으면서 CPU는 거의 쓰지 않는다.

8-2. 함정 ② HTTP keep-alive로 재사용되는 연결

keep-alive는 요청 하나가 끝나도 TCP 연결을 끊지 않고 다음 요청에 재사용하는 것이다. 왕복 비용을 아끼는 좋은 기능이지만, "연결 개수"와 "처리 중인 요청 개수"의 관계를 끊어 놓는다. 연결은 열려 있는데 그 위에 아무 요청도 안 흐르는 순간이 대부분이고, 반대로 HTTP/2라면 연결 하나에 요청 수십 개가 동시에 흐른다.

L7 LB — 미완료 "요청"을 셀 수 있다

  • HTTP를 해석하므로 요청의 시작과 끝을 안다
  • 연결이 재사용되든 다중화되든 실제 처리 중인 요청 수를 센다
  • 7절에서 계산한 그대로 작동한다

L4 LB — 연결만 볼 수 있다

  • "연결 수가 적은 서버"로 보내는데, 그 연결 하나가 초당 수천 요청을 실어 보내는 중일 수 있다
  • 즉 L4에서 켠 least connection은 이름만 같은 다른 알고리즘이다
  • 세는 대상이 다르면 결론도 다르다

8-3. 함정 ③ 갓 투입된 서버는 미완료 수가 0이다

가장 준비 안 된 서버에 가장 많은 트래픽이 몰리는 역설 배포나 오토스케일링으로 새 서버가 들어오면 미완료 수가 0이므로, least connection은 다른 서버들이 균형에 도달할 때까지 새 요청을 전부 그 서버에만 보낸다. 그런데 새 서버는 JIT 컴파일 전이고, 캐시가 비어 있고, 커넥션 풀도 아직 안 늘어난 상태다. 이것이 신규 서버가 투입 직후 죽는 전형적인 경로이고, 대응은 신규 서버에 트래픽을 서서히 올리는 slow start(NGINX Plus의 slow_start, ALB 대상 그룹의 slow start 설정)다.

3대 함정 — "길 · 재 · 새"

길 — 길게 열린 연결
SSE·WebSocket·long-polling은 미완료인 채로 일은 안 한다. 근사가 역전된다 → 처방은 upstream 분리
재 — 재사용되는 연결
keep-alive·HTTP/2가 연결 수와 요청 수의 관계를 끊는다. L4에서 세면 연결, L7에서 세야 요청

미완료 0 → 혼자 다 받는다. 워밍업 전 폭주 → 처방은 slow start
least connection으로 바꿨는데 쏠림이 남거나 오히려 심해졌다면,

9. 해시 계열 · 응답시간 계열 · sticky session 가산점

9-1. IP hash / consistent hashing — 목표가 다른 알고리즘

같은 클라이언트(또는 같은 키)를 항상 같은 서버로 보내는 방식이다. 부하 균등이 목표가 아니라 목적지의 일관성이 목표라는 점에서 앞의 둘과 성격이 다르다. 서버 로컬 캐시의 적중률을 높이거나(같은 사용자의 요청이 같은 서버로 가면 그 서버 캐시에 이미 데이터가 있다), 세션을 서버 메모리에 둔 레거시를 지탱할 때 쓴다.

① IP 기준 클라이언트 IP를 해시해 서버를 고정한다
upstream api_servers {
    ip_hash;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    # 주의 1: nginx는 IPv4의 앞 3옥텟만 해시 키로 쓴다.
    #   같은 /24 대역의 사용자들이 한 서버로 뭉치므로,
    #   회사·통신사 NAT 뒤의 대규모 사용자가 한 서버에 쏠릴 수 있다.
    # 주의 2: 서버 대수가 바뀌면 나머지 연산의 분모가 바뀌어
    #   대부분의 키가 다른 서버로 재배치된다
    #   → 캐시 전부 미스, 세션 전부 소실.
}
② 임의 키 + consistent 서버 대수 변화의 충격을 줄인다
upstream api_servers {
    hash $arg_userId consistent;
    server 10.0.1.11:8080;
    server 10.0.1.12:8080;
    # consistent 를 붙이면 일관된 해싱(consistent hashing)을 쓴다.
    # 서버 한 대가 빠질 때 그 서버가 맡던 키만 재배치되고
    # 나머지는 그대로 유지된다 — 나머지 연산 방식의
    # "전면 재배치"를 피하는 것이 이 알고리즘의 존재 이유다.
}
least response time 계열 미완료 수 대신 최근 응답 시간까지 반영한다. 미완료 수가 같아도 실제로 더 빨리 응답해 온 서버를 선호하므로, 서버 간 성능 편차나 일시적 저하를 더 잘 반영한다. 대가는 더 많은 상태 추적과, 응답 시간 측정 창을 어떻게 잡느냐에 따른 민감도 문제다.
알고리즘은 "좋은 순서"로 줄 세우는 것이 아니라 "무엇을 공평이라 정의하고, 그 정의가 언제 깨지는가"로 읽는다.
알고리즘공평의 정의성립 조건(가정)깨지는 지점추적 비용
Round Robin받은 개수가 같다모든 요청의 처리 비용이 비슷하다무거운·가벼운 요청이 섞이면 4:4 → 4,000:400없음 (순번 카운터뿐)
Weighted RR개수 × 장비 가중치서버 성능 차이만 있고 요청 무게는 균일하다요청 무게 편차는 전혀 보정하지 못한다없음
Least Connection미완료 요청 수가 같다미완료 수가 실제 작업량에 비례한다SSE·keep-alive·신규 서버에서 역전 (8절)서버별 in-flight 집계 (집계 범위 = 정확도)
Least Response Time미완료 수 + 최근 응답 시간최근 응답 시간이 현재 여력을 대변한다측정 창이 짧으면 과민, 길면 둔감더 많음 (시간 통계까지)
IP hash같은 출발지 → 같은 목적지클라이언트 IP가 사용자 단위로 고르게 분포한다NAT 뒤 대규모 사용자가 한 대로 뭉친다 · 대수 변경 시 전면 재배치없음 (계산만)
Consistent hash같은 키 → 같은 목적지키 분포가 고르다키 편중(핫 키)은 그대로 쏠린다낮음 (링 구조)

9-2. Sticky Session — 분배를 일부러 포기하는 선택

sticky session(세션 고정)은 같은 사용자를 항상 같은 서버로 보내는 설정이다. LB의 본업이 분배인데 그 분배를 일부러 제한하는 것이니, 왜 그런 선택을 하는지부터 알아야 한다. 이유는 하나다 — 서버가 상태를 자기 메모리에 들고 있어서, 다른 서버로 가면 그 상태가 없기 때문이다. 톰캣 기본 설정의 HttpSession이 대표적이다. 로그인 정보가 1번 서버 메모리에 있는데 다음 요청이 2번 서버로 가면 비로그인 취급을 받는다.

응급 처치로는 유효하다

  • 코드를 한 줄도 안 고치고 당장 동작하게 만들 수 있다
  • 세션 외부화 마이그레이션의 과도기 임시 수단으로 위치를 정해 두면 정확하다

대가 넷 — "균 · 소 · 확 · 축"

  • 균 — 무거운 사용자가 한 서버에 고정되면 분배 균형이 깨진다
  • 소 — 그 서버가 죽으면 고정돼 있던 사용자들의 세션이 통째로 소실
  • 확 — 오토스케일링으로 늘려도 기존 사용자는 기존 서버에 묶여 확장 효과가 없다
  • 축 — scale-in이 곧 사용자 강제 로그아웃이라 축소가 어렵다

핵심 프레이밍 — 원인과 증상

sticky session은 원인(서버 로컬 상태)을 그대로 두고 증상만 막는 처방이다

정석은 세션을 서버 밖 공유 저장소(Redis 등)로 빼서 서버를 stateless로 만들고, LB는 자유롭게 분배하게 하는 것이다. 04번 문서(stateless 서버 설계)와 한 몸인 주제.

10. 실무 — "스펙이 같은데 한 대만 죽는" 미스터리

이 질문의 출제 의도가 겨냥하는 실제 장애 패턴이다. 증상은 언제나 같은 모양으로 나타난다 — "서버 3대가 완전히 동일한 스펙·동일한 이미지인데, 유독 한 대만 p99가 튀거나 스레드풀이 마르거나 재시작된다." 이 증상 하나에 원인 후보가 여럿이므로, 관측 순서를 정해 두고 분기로 좁히는 것이 진단의 본체다. 원인을 하나로 단정하고 시작하면 대개 틀린다.

진단 순서의 원칙 — 싼 것부터, 좁은 것부터

① 분배가 이상한가 (LB의 문제)→ ② 분배는 정상인데 내용이 이상한가 (요청 종류의 문제)→ ③ 둘 다 정상인데 서버가 이상한가

뒤로 갈수록 조사 비용이 크다. 그래서 순서 자체가 진단 기술의 일부다.

① 서버별 요청 수
같은 시간 창에서 각 서버가 받은 요청 건수. "LB가 나눠주기는 제대로 했는가"에 대한 답이고 첫 갈림길이다. LB 액세스 로그의 upstream 주소별 집계로 본다.
② 미완료 요청 / 활성 연결 수
요청 수는 균등한데 미완료만 쌓이면, 들어온 개수는 같은데 끝나지 않는 것들이 한쪽에 몰려 있다.
③ 응답시간 분포 (p50 + p99)
p50까지 높다 → 그 서버의 모든 요청이 느리다(서버 자체 의심). p50은 같은데 p99만 → 일부 요청만 무겁다. 평균만 보면 이 구분이 지워진다.
④ 요청 종류 분포
③에서 p99만 튀었다면 여기가 결정적이다. 엔드포인트별로 쪼개 무거운 API가 특정 서버에 몰렸는지 본다.
⑤ 스레드풀·커넥션 풀
활성 수, 대기 큐 길이, 커넥션 풀 대기. 6-2의 계산이 현실에서 어떻게 보이는지가 이 지표다.
⑥ CPU · GC · 디스크 · 이웃
여기까지 와서야 "서버 자체가 이상한가"를 본다. 노이지 네이버, GC 설정 차이, 디스크, 커널/설정 드리프트.

10-3. 사례 1 — RR + 처리 시간 편차

일반 조회(수십 ms)와 대용량 정산 다운로드(수십 초)가 같은 서버 그룹에 섞여 있었다. RR이라 다운로드 요청도 균등하게 순환 분배됐지만, 하필 다운로드가 몰린 서버는 스레드가 장시간 점유돼 그 서버에 온 일반 조회까지 느려졌다.

지표는 진단 트리 그대로 나온다 서버별 요청 수는 균등하다. p50은 세 서버가 비슷한데 서버 3번만 p99가 튄다. 엔드포인트별로 쪼개 보면 그 시간대에 정산 다운로드가 3번 서버에 집중돼 있다. 6절에서 계산한 상황이 실제 지표로 나타난 것이다.

처방은 셋이고, 근본적인 쪽으로 갈수록 뒤에 있다.

①
least connection으로 전환 — 가장 싼 처방. 7절의 계산대로 미완료 작업량 기준으로 분배되므로 쏠림이 구조적으로 완화된다. 다만 8절의 함정에 해당하지 않는지 먼저 확인해야 한다.
②
무거운 API를 별도 서버 그룹으로 분리 — 경로 라우팅으로 정산 다운로드를 전용 그룹에 보낸다. 이쪽이 근본적이다. 성격이 다른 트래픽을 한 풀에 섞은 것 자체가 원인이므로, 알고리즘을 바꾸는 것은 섞인 상태를 더 잘 견디게 만드는 것이고 분리는 섞지 않는 것이다. 무거운 요청이 폭주해도 일반 조회는 멀쩡하다는 격리 효과(벌크헤드)까지 얻는다.
③
무거운 작업을 요청-응답에서 떼어낸다 — 다운로드 요청을 받으면 즉시 접수 응답을 주고, 실제 생성은 비동기 작업으로 넘긴 뒤 완료되면 알린다. 애초에 스레드를 수십 초 점유하는 요청을 없애는 것이므로 가장 근본적이다.
nginx 무거운 API를 전용 upstream으로 격리한다
upstream api_light {
    least_conn;
    zone api_light 64k;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
}

upstream api_heavy {
    least_conn;
    zone api_heavy 64k;
    server 10.0.2.21:8080 max_fails=3 fail_timeout=10s;
    server 10.0.2.22:8080 max_fails=3 fail_timeout=10s;
}

server {
    listen 80;

    location /api/settlements/export {
        proxy_pass http://api_heavy;
        proxy_read_timeout 120s;   # 무거운 쪽만 긴 타임아웃을 허용한다
    }
        # 격리의 효과: 이 API가 폭주해 api_heavy가 마비돼도
        #             일반 조회는 api_light에서 정상 응답한다

    location /api/ {
        proxy_pass http://api_light;
        proxy_read_timeout 5s;     # 일반 API는 짧게 잡아 빨리 실패시킨다
    }
}

10-4. 사례 2 — 연결 단위 분배의 함정

클라이언트가 keep-alive나 gRPC(HTTP/2)처럼 연결 하나를 오래 재사용하면, 분배 판단이 연결을 맺는 순간에만 한 번 일어나고 이후 그 연결 위의 수만 건 요청이 전부 같은 서버로 간다. 3절의 도식이 그대로 현실이 되는 경우다.

이 사례의 지표는 첫 갈림길에서 바로 갈린다 서버별 요청 수 자체가 불균등하다. RR로 설정해 뒀는데도 그렇다 — RR이 나눈 것은 요청이 아니라 연결이기 때문이다. 특히 고약한 변형이 서버 증설 후에도 새 서버가 노는 것이다. 기존 연결은 계속 유지되므로 옮겨가지 않고, 새 연결이 생길 때만 새 서버가 몫을 받는다. 클라이언트가 내부 서비스이고 연결을 영구적으로 유지한다면 새 서버는 영원히 논다.
①
L7에서 요청 단위로 분배한다 — HTTP/2·gRPC를 이해하는 L7 프록시(nginx, Envoy 등)를 두어 하나의 클라이언트 연결에서 온 요청들을 여러 서버로 나눈다. 근본 처방이다.
②
연결에 수명을 준다 — 연결의 최대 요청 수와 최대 지속 시간을 제한해 주기적으로 재수립되게 만든다. 재수립될 때마다 분배가 다시 일어나므로 시간이 지나면 균형이 잡힌다.
③
클라이언트 쪽 커넥션 풀에도 같은 상한을 준다 — gRPC나 HTTP 클라이언트 라이브러리에 연결 최대 수명 설정이 있으면 함께 잡는다. 서버만 닫으면 클라이언트가 즉시 새로 열어 같은 서버로 다시 붙을 수도 있으므로 양쪽을 함께 봐야 한다.
nginx 상한을 두는 것 자체가 분배 정책이 된다
http {
    keepalive_timeout  30s;     # 유휴 연결을 30초 뒤 닫는다
    keepalive_requests 1000;    # 연결 하나로 1,000건을 처리하면 닫는다
    # 이 두 값이 곧 "분배 판단이 다시 일어나는 주기"다.
    # 무한히 재사용되면 분배는 최초 1회로 끝나므로,
    # 상한을 두는 것 자체가 분배 정책이 된다.
}

이 사례가 값진 이유

"LB가 무엇을 단위로 분배하는가(연결 vs 요청)"를 아는지가
이 장애의 진단 가능 여부를 가른다

알고리즘 설정만 들여다보면 영원히 못 찾는다 — 설정은 RR로 정상이기 때문이다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

LB의 세 역할?
① 트래픽 분산 ② 헬스체크 기반 장애 격리 ③ 공통 관심사 집결지(TLS 종료·경로 라우팅·rate limit). ②③이 가능한 이유는 모든 요청이 반드시 이 한 지점을 지나기 때문.
헬스체크 3대 실수?
민 · 둔 · 의 — 너무 민감(플래핑→0대) / 너무 둔감(주기×임계만큼 방치) / 의존성 포함(DB 순단이 전면 장애로 증폭).
최악의 방치 시간 공식?
확인 주기 × 실패 임계 횟수. 30초 × 5회 = 150초. 5초 × 3회 = 15초. 이 곱셈을 SLO와 견줘 정한다.
liveness vs readiness?
실패 시 행동으로 구분한다 — liveness는 재시작(되돌릴 수 없음 → 훨씬 둔감하게), readiness는 트래픽 제외. readiness 그룹에 db를 넣지 않는 것이 요점.
RR의 가정과 붕괴 숫자?
가정은 "모든 요청의 처리 비용이 비슷하다". H/L이 번갈아 오면 순번 4:4 → 일한 시간 4,000ms : 400ms, 스레드 2개면 1,600ms : 100ms.
least connection이 세는 것?
LB가 보내놓고 아직 응답을 못 받은 요청 수(미완료·in-flight). CPU도 스레드도 아니다. 같은 8건이 2,200 : 2,200이 된다.
least_conn 3대 함정?
길 · 재 · 새 — 길게 열린 연결(SSE→역전) / 재사용되는 연결(keep-alive·HTTP2, L4는 연결만 셈) / 새 서버(미완료 0 → 폭주, slow start).
진단의 첫 갈림길?
서버별 요청 수가 균등한가. 불균등이면 분배 자체가 안 되는 것(L4+keep-alive, sticky, ip_hash 편중, 다른 서버가 이미 빠져 있었음). 균등이면 미완료·p50/p99·엔드포인트로 내려간다.
알고리즘 선택의 답변 프레임?
"뭐가 더 좋냐"가 아니라 "우리 요청 분포가 어느 가정에 맞냐". 그리고 알고리즘 교체보다 트래픽 분리가 근본 처방인 경우가 많다.
전 서버가 같이 나빠졌다면?
LB 문제가 아니다. 공유 자원 포화(DB·캐시·외부 API·공용 커넥션 풀)를 본다. 편차 없는 문제를 편차 지표로 쫓는 것이 장애 대응 최대의 낭비.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

헬스체크는 어떻게 설정하나요? 잘못 설정하면 어떤 일이 생기나요? 필수힌트: 두 축으로 나눠 답한다 — 무엇을 확인하나 / 얼마나 민감하게

① 무엇을 확인하나 — 포트가 열렸는지만 보는 얕은 체크(TCP 연결 성공 여부)는 프로세스가 살아만 있으면 통과하므로, 애플리케이션이 실제로 응답 가능한지 보는 HTTP 체크가 낫다. 단, 헬스 엔드포인트가 DB까지 찌르게 만들면 DB 순단에 전 서버가 동시에 불건강 판정돼 전체가 분리되는 참사가 난다. 공유 의존성의 짧은 장애가 전면 장애로 증폭되는 구조다. Spring Boot라면 /actuator/health/liveness와 /actuator/health/readiness를 나누고 readiness 그룹에 db를 넣지 않는 것이 그 분리의 구현이다.

② 얼마나 민감하게 — 너무 민감하면(1회 실패로 제외) 일시 지연에 서버가 들락날락하고(flapping), 심하면 전 서버가 순차적으로 빠진다. 너무 둔감하면 죽은 서버로 트래픽이 계속 간다.

최악의 방치 시간 = 확인 주기 × 실패 임계 횟수 → SLO와 견줘 정하고,
연속 N회 실패 시 제외 · 연속 M회 성공 시 복귀(히스테리시스)로 경계에서 진동하지 않게 한다

한 단계 더 얹으면 좋은 것 — 두 프로브의 실패 처방 차이다. liveness 실패의 결과는 재시작, readiness 실패의 결과는 트래픽 제외. 재시작은 되돌릴 수 없으니 liveness를 더 둔감하게 잡아야 하고, liveness에 의존성을 넣으면 DB 장애로 전 컨테이너가 재시작되는 최악의 조합이 된다.

least connection이 항상 round robin보다 좋은 것 아닌가요? 시니어 변별힌트: 네 가지. 앞의 둘은 "지표의 한계", 뒤의 둘은 "구현의 한계"

아니다. 이유가 넷이다 — "수 · 균 · 집 · 신".

① 수: 연결 수 ≠ 부하다. least connection이 세는 것은 미완료 요청 수일 뿐, 그 요청이 CPU를 태우는지 그냥 대기 중인지는 모른다. SSE 연결 5,000개를 들고 있는 서버(CPU 5%)와 집계 요청 3건을 처리하는 서버(CPU 95%)를 비교하면 LB는 후자가 한가하다고 판단한다 — 근사가 역전되는 구간이다.

② 균: 처리 시간이 균일한 서비스라면 RR과 결과가 같다. 그러면서 상태 추적 비용만 낸다. 요청 무게가 고른 서비스에서 least connection은 이득 없는 복잡도다.

③ 집: LB가 여러 대면 집계가 부정확하다. 각 LB는 자기가 보낸 요청만 세므로 전역 미완료 수를 모른다. nginx 안에서도 공유 메모리 존을 안 잡으면 워커 프로세스별로 따로 세어 부분 시야로 판단한다.

④ 신: 갓 투입된 서버는 미완료 수가 0이라 트래픽이 순간에 몰린다. 가장 준비가 안 된 서버(JIT 미최적화, 캐시 콜드, 커넥션 풀 미확장)에 가장 많은 요청이 가는 역설이므로 slow start와 함께 써야 안전하다.

"무엇이 좋냐"가 아니라 "우리 요청 분포가 어느 가정에 맞냐"로 답하는 게 시니어의 답

여기에 한 가지 더 붙이면 좋다 — 알고리즘 선택보다 트래픽 분리가 근본 처방인 경우가 많다. 성격이 다른 요청을 한 upstream에 섞어 두고 알고리즘으로 해결하려는 것 자체가 설계 문제일 수 있다.

least_conn으로 바꿨는데 쏠림이 더 심해졌습니다. 무엇을 의심합니까? 함정힌트: "세는 대상"이 작업량을 대변하지 못하는 경우를 먼저 본다

세 가지를 순서대로 확인한다.

① 오래 열려 있고 일은 안 하는 연결이 섞였는가 — SSE·WebSocket·long-polling·대용량 업로드가 한 upstream에 섞여 있으면, 미완료 수가 많은 서버가 오히려 한가하다. least_conn은 그 서버를 피해 버리고 실제로 CPU를 태우는 서버로 보낸다 → RR보다 나빠진다. 처방은 튜닝이 아니라 upstream 분리다.

② 방금 서버를 투입했는가 — 미완료 0인 신규 서버가 혼자 다 받는다. 배포·오토스케일 시각과 스파이크 시각을 맞춰 본다. 처방은 slow start(없으면 weight를 낮게 넣고 서서히 올리는 운영 절차).

③ 집계가 쪼개져 있는가 — nginx라면 zone 없이 least_conn만 켠 경우 워커별 부분 시야로 판단한다. LB가 여러 대라면 각자 자기 것만 세므로 전역적으로는 애초에 부정확하다.

그리고 하나 더 — L4에서 켰다면 세는 대상이 미완료 요청이 아니라 연결이다. 이름은 같지만 다른 알고리즘이므로, 애초에 기대한 효과가 나올 수 없다.

L4와 L7 로드밸런서는 어떻게 다르고 무엇을 쓰나요?힌트: 사전적 차이를 말한 뒤, "그 차이가 어떤 장애로 나타나는가"까지 가야 점수가 된다

L4는 TCP/UDP 수준에서 IP·포트만 보고 연결을 통째로 넘긴다 — 해석을 안 하니 빠르고 대용량에 강하다. L7은 HTTP를 해석하므로 경로·헤더 기반 라우팅, 요청 단위 분배, 재시도·서킷브레이커 같은 정교한 제어가 된다. 실전에서는 겹쳐 쓴다 — 맨 앞에 L4(또는 DNS/애니캐스트)로 대량 유입을 받고, 그 뒤 L7 게이트웨이가 서비스별로 분배한다.

변별이 갈리는 지점은 "차이가 실제로 어떤 장애로 나타나는가"다. 분배 단위가 연결이라는 것은 곧 분배 판단이 연결당 한 번뿐이라는 뜻이고, 클라이언트가 keep-alive나 HTTP/2로 연결을 오래 재사용하면 사실상 분배가 사라진다. 서버를 증설해도 기존 연결이 옮겨가지 않아 새 서버가 노는 것도 같은 원인이다.

또 L7만이 요청 단위 재시도를 안전하게 할 수 있다 — L4는 연결이 끊긴 뒤에 그 위의 요청이 처리됐는지 안 됐는지 알 방법이 없다. 그리고 least connection이 세는 대상도 갈린다(L4=연결, L7=미완료 요청).

sticky session은 언제 쓰고, 왜 피하라고 하나요?힌트: "원인"과 "증상"이라는 단어를 쓰면 답이 정리된다

같은 사용자를 항상 같은 서버로 보내는 설정이다. 서버가 상태를 자기 메모리에 들고 있다는 원인은 그대로 두고 증상만 막는 처방이라는 점이 핵심이다.

서버 메모리에 세션을 두는 레거시를 당장 못 고칠 때의 응급 처치로는 유효하다 — 코드 변경이 0이다. 하지만 대가가 넷이다(균·소·확·축): 분배 균형이 깨지고(특정 서버에 무거운 사용자가 고정), 그 서버가 죽으면 고정된 사용자들의 세션이 통째로 날아가며, 오토스케일링으로 늘린 새 서버는 기존 사용자를 받지 못해 확장 효과가 나지 않고, scale-in은 곧 사용자 강제 로그아웃이 된다.

정석은 세션을 외부 저장소(Redis 등)로 빼서 서버를 stateless로 만들고 LB는 자유롭게 분배하게 하는 것 — 04번 문서(stateless 설계)와 한 몸이다.

한 단계 더 파고들면 고정 방식의 차이를 말할 수 있다. LB가 발급한 쿠키로 고정하는 방식은 사용자 단위로 정확하지만 쿠키를 못 쓰는 클라이언트에서 깨지고, IP 해시로 고정하는 방식은 쿠키가 필요 없지만 NAT 뒤 사용자들이 한 서버로 뭉치고 모바일 IP 변경 시 고정이 풀린다.

고정된 서버를 내려야 합니다. 무엇을 해야 합니까? 가산점힌트: 실제로 운영해 본 사람만 말하는 절차가 하나 있다

드레이닝(draining)이 반드시 필요하다 — 신규 고정은 받지 않고, 기존 고정 사용자의 세션이 만료되기를 기다리는 절차다. 바로 내리면 그 서버에 고정된 사용자 전원이 강제 로그아웃된다.

여기서 실무의 아픈 지점은 이 대기 시간이 세션 만료 시간만큼 길어진다는 것이다. 세션 만료가 30분이면 서버 한 대 내리는 데 최대 30분을 기다린다. 이 한마디까지 말하면 실제로 운영해 본 답변으로 들린다 — 그리고 이것이 sticky session을 임시 수단으로만 두어야 하는 또 하나의 이유다.

로드밸런서 자체가 단일 장애점(SPOF)이 되지 않나요?힌트: "분배기를 누가 분배하나"라는 재귀를 어디서 끊는가

된다 — 모든 요청이 반드시 지나가는 지점이니 정의상 SPOF 후보다. 그래서 LB도 이중화한다. 전형적인 방식은 액티브-스탠바이 쌍 + 가상 IP(VIP) 인수다. 클라이언트에게 알려준 IP를 물리 장비가 아니라 둘 사이를 옮겨 다닐 수 있는 가상 IP로 잡아 두면, 액티브가 죽어도 스탠바이가 그 IP를 인수하므로 클라이언트가 보는 주소는 바뀌지 않는다. DNS에 LB 여러 대를 등록하는 방식도 쓴다. 클라우드 관리형 LB(ALB 등)는 이 이중화를 서비스가 대신 해준다.

"분배기를 누가 분배하나" → DNS → L4 → L7 → 앱. 각 계층은 자기 아래를 분배하고
자기 이중화는 위 계층이 맡으며, 맨 위 DNS는 애초에 여러 IP를 돌려줄 수 있으므로 재귀가 끝난다

한 걸음 더 — "이중화했어도 남는 문제". 페일오버에는 시간이 걸리므로 그 사이 요청은 실패하고, 클라이언트나 중간 DNS 캐시가 옛 IP를 붙들고 있으면 복구가 더 늦어진다. 그리고 액티브 한 대의 용량으로 전체 트래픽을 받고 있었다면, 스탠바이도 같은 용량을 상시 확보해 두지 않으면 페일오버 직후에 그쪽이 무너진다. 이중화는 "죽어도 되게" 만드는 것이지 "죽어도 아무 일 없게" 만드는 것이 아니다.

weighted round robin이면 요청 무게 편차도 보정되지 않나요? 함정힌트: weight는 어느 쪽 속성인가

보정되지 않는다. weight는 서버 쪽에 붙는 상수다 — "이 장비는 3배 좋으니 4번 중 3번 순번을 준다"는 뜻이지, 지금 그 서버가 얼마나 밀려 있는지는 여전히 보지 않는다.

6절의 8건 시나리오에 weight를 걸어도 결과는 안 바뀐다 — 두 서버 스펙이 동일했고 문제는 요청의 무게 분포였기 때문이다. 요청 무게 편차를 흡수하려면 서버의 현재 상태를 관측하는 알고리즘(least connection / least response time)이거나, 애초에 무거운 요청을 다른 풀로 분리하는 설계가 필요하다.

헬스체크를 1초 주기·1회 실패로 바짝 조이면 장애 감지가 빨라져서 좋지 않나요? 함정힌트: "빨리 빼는 것"의 대가를 계산해 본다

아니다. 감지 속도를 산 대가로 오판 확률을 산다. 1회 실패로 제외하면 GC로 300ms 멈춘 서버나 순간적으로 지연이 튄 서버가 "죽었다"고 판정된다. 그러면 남은 서버가 그 몫까지 받아 더 느려지고, 그 서버들도 실패하기 시작한다 — 서버가 들락날락하는 플래핑이고, 최악의 경우 전 서버가 순차적으로 빠져 LB 뒤에 아무도 남지 않는다.

제대로 답하는 방법은 두 손잡이를 나누는 것이다. 감지 속도는 주기(period)로 벌고, 오판 방지는 실패 임계(threshold)로 산다. 5초×3회 = 15초처럼 곱셈 결과를 SLO에 맞추면서 임계는 1보다 크게 유지하는 조합을 찾는 것이다.

여기에 복귀 조건(successThreshold)을 함께 둬야 한다. 빼는 기준만 있고 넣는 기준이 같으면 경계에서 상태가 진동한다 — 온도조절기가 설정 온도 하나로 켜고 끄지 않는 이유와 같다(히스테리시스).

새로 투입한 서버가 배포 직후에만 죽습니다. 원인과 대응은? 가산점힌트: 미완료 수가 0이라는 사실이 만드는 역설

least connection + 미완료 수 0의 조합을 먼저 의심한다. 새 서버는 미완료가 0이므로 다른 서버들이 균형에 도달할 때까지 새 요청을 거의 전부 받는다. 그런데 그 서버는 JIT 컴파일 전, 캐시 콜드, 커넥션 풀 미확장 상태다 — 가장 약한 서버에 가장 많은 트래픽이 몰리는 역설이다.

대응은 셋이다. ① slow start로 신규 서버 트래픽을 서서히 올린다(NGINX Plus slow_start, ALB 대상 그룹의 slow start). ② slow start가 없으면 weight를 낮게 넣어 투입한 뒤 단계적으로 올리는 운영 절차로 대체한다. ③ readiness를 "포트 열림"이 아니라 "실제로 받을 준비 완료"로 정의해, 워밍업(캐시 예열·커넥션 풀 예열)이 끝난 뒤에 통과하게 만든다.

이 답변이 좋은 이유는 알고리즘 지식과 배포 운영이 만나는 지점을 짚기 때문이다. "least connection이 좋다"만 아는 사람은 이 장애를 서버 스펙 문제로 오진한다.

롤링 배포 중 5xx가 잠깐 튑니다. LB 관점에서 무엇을 봅니까? 시니어 변별힌트: 2절의 곱셈이 "빼는 데 걸리는 시간"에도 그대로 적용된다

양쪽 끝을 본다 — 넣을 때와 뺄 때.

① 넣을 때 — readiness가 "기동 완료"보다 먼저 통과하면 아직 준비 안 된 서버로 트래픽이 간다. readiness 통과 조건이 실제 준비 상태를 반영하는지 본다.

② 뺄 때 — 여기가 대개 원인이다. LB가 서버를 빼는 데도 "주기 × 실패 임계"만큼 시간이 걸린다. 서버가 종료 신호를 받고 곧바로 닫으면, LB는 아직 그 서버를 정상으로 알고 있는 그 시간 동안 계속 요청을 보낸다 → 그 요청들이 5xx가 된다.

순서를 뒤집는 것이 처방이다 — 종료 신호를 받으면 먼저 readiness를 실패로 바꾸고,
LB가 자기를 뺄 만큼(주기 × 임계) 기다린 뒤 진행 중인 요청을 마치고 종료한다

이 답변의 값은 2절에서 계산한 곱셈이 "제외 지연"에도 그대로 적용된다는 것을 아는 데 있다. 같은 숫자가 장애 방치 시간과 배포 중 5xx 창 두 곳에서 쓰인다.

ip_hash로 캐시 적중률을 올렸는데, 서버 한 대를 추가하니 캐시가 전부 미스가 났습니다.힌트: 나머지 연산의 분모가 바뀌면 무슨 일이 일어나는가

단순 해시는 서버 대수를 나머지 연산의 분모로 쓰기 때문이다. 분모가 3 → 4로 바뀌면 대부분의 키가 다른 서버로 재배치된다 — 캐시는 전부 미스가 되고, 세션을 서버 메모리에 뒀다면 전부 소실된다.

처방은 consistent hashing이다. nginx라면 hash $key consistent. 서버 한 대가 들고 나갈 때 그 서버가 맡던 키만 재배치되고 나머지는 그대로 유지된다. "나머지 연산 방식의 전면 재배치를 피하는 것"이 이 알고리즘의 존재 이유다.

한 가지 더 짚으면 좋은 것 — nginx의 ip_hash는 IPv4의 앞 3옥텟만 해시 키로 쓴다. 같은 /24 대역 사용자들이 한 서버로 뭉치므로, 회사·통신사 NAT 뒤의 대규모 사용자가 한 대에 쏠릴 수 있다. "해시니까 고르게 퍼진다"는 직관이 키 분포 가정에 의존한다는 점을 아는지가 변별점이다.

전 서버가 동시에 느려졌습니다. least_conn으로 바꾸면 도움이 됩니까? 함정힌트: 알고리즘이 고칠 수 있는 문제의 종류를 먼저 정의한다

도움이 되지 않는다. 분배 알고리즘이 고칠 수 있는 것은 서버 간 편차뿐이다. 편차 없이 전부 같이 나빠진 문제는 어느 알고리즘으로 나눠도 총량이 그대로다 — 밀린 일을 누구에게 줄지만 바뀌고 양은 그대로이기 때문이다.

이 경우 후보는 공유 자원 포화다 — DB, 캐시, 외부 API, 공용 커넥션 풀. 여기에 서버 수 자체가 부족한 경우, 앞단(LB·게이트웨이) 자체가 포화된 경우도 포함된다.

진단에서 실질적으로 값진 판단은 이것이다 — "편차가 있는가"를 먼저 확인하고, 없으면 서버별 지표를 그만 보는 것이다. 편차 없는 문제를 편차 지표로 쫓는 시간이 장애 대응에서 가장 많이 낭비되는 시간이다.

L4에서 요청 단위 재시도가 왜 어렵습니까? 가산점힌트: 재시도가 안전하려면 무엇을 알아야 하는가

재시도가 안전하려면 "그 요청이 처리됐는가"를 알아야 한다. L4는 HTTP를 해석하지 않으므로 요청의 경계 자체를 모른다 — 연결이 끊겼을 때 그 연결 위에서 흐르던 요청이 서버에 도달해 처리됐는지, 도달 전에 끊긴 건지 구분할 방법이 없다. 모른 채로 재시도하면 같은 작업을 두 번 실행할 수 있다.

L7은 요청 경계를 알므로 "이 요청은 응답을 못 받았다"를 판정할 수 있고, 그래서 요청 단위 재시도·서킷 브레이킹·타임아웃을 걸 수 있다.

다만 L7이라도 재시도 자체가 안전한 요청인지는 별개다 — 응답을 못 받았다는 것이 서버가 처리하지 않았다는 뜻은 아니기 때문이다. 그래서 재시도는 멱등성과 함께 설계해야 하고, LB의 재시도는 대개 연결 실패·특정 상태코드 등 조건을 좁혀 켠다.

LB를 두지 않고 DNS 라운드로빈만으로 분배하면 안 되나요?힌트: DNS는 "빼는 것"을 얼마나 빨리 할 수 있는가

분배는 어느 정도 된다. 문제는 장애 격리다. DNS는 여러 IP를 돌려주는 것까지는 하지만, 죽은 서버를 즉시 빼는 일을 못 한다 — 클라이언트와 중간 DNS 리졸버가 응답을 캐시하고 있기 때문이다. 레코드를 지워도 캐시가 만료되기 전까지는 죽은 IP로 계속 접속한다.

즉 DNS 계층은 1절의 역할 ②(헬스체크 기반 장애 격리)와 ③(TLS 종료·경로 라우팅·rate limit)을 제공하지 못한다. 그래서 실전 구성은 DNS로 LB들을 가리키고, 실제 분배와 격리는 LB가 하는 형태가 된다(4절의 계층 그림).

같은 이유로, LB를 이중화해도 클라이언트나 중간 DNS 캐시가 옛 IP를 붙들고 있으면 페일오버 복구가 늦어진다. DNS는 계층의 맨 위에서 재귀를 끊는 역할에 적합하고, 초 단위 장애 대응 수단으로는 적합하지 않다.

한 줄 요약
로드밸런서는 트래픽 분산 + 헬스체크 기반 장애 격리 + 공통 방어 로직의 집결지이고, round robin은 "요청 비용이 균일하다"는 가정 위의 순번 공평(무거운·가벼운 요청이 번갈아 오면 순번 4:4에 부하 4,000ms:400ms), least connection은 미완료 요청 수를 관측해 처리 시간 편차를 자동으로 흡수하는 상태 기반 공평(같은 8건이 2,200ms:2,200ms로 균등해진다)이다 — 다만 그 미완료 수도 근사치라 keep-alive·SSE·신규 서버 앞에서 역전되고, 헬스체크는 민감도가 양쪽으로 위험하며 의존성까지 확인하게 만들면 공유 장애를 전면 장애로 증폭시키므로, 알고리즘의 가정이 깨지는 지점을 알아야 "특정 서버만 부하가 몰리는" 장애를 풀 수 있다.
