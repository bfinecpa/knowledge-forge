타임아웃 설정
connection / read / 전체 타임아웃과 타임아웃 예산

면접 질문: "타임아웃은 어디에(connection/read/전체) 어떤 기준으로 설정하나요? 타임아웃 없는 외부 호출의 위험은?"

핵심 관전 포인트 — 타임아웃은 종류별로 지키는 구간이 다르다. connection timeout은 "TCP 연결 수립까지", read timeout은 "응답 데이터 조각 사이의 대기", 전체(요청) timeout은 "호출 시작부터 끝까지". read timeout만 있으면 조금씩 흘러오는 응답에 무한정 끌려갈 수 있어 전체 상한이 따로 필요하다. 값의 기준은 감이 아니라 대상의 p99 응답시간 + 여유분이고, 호출 체인 전체로는 상류의 타임아웃 예산 안에 하류 타임아웃(재시도 포함)의 합이 들어와야 한다 — 어긋나면 상위가 먼저 포기해 하위의 작업이 버려지는 낭비가 되고, 심하면 상위는 실패를 응답한 뒤 하위가 쓰기를 완료해 정합성이 깨진다. 타임아웃 없는 외부 호출은 상대 장애 시 내 스레드를 무기한 인질로 잡아 스레드 풀 고갈 → 연쇄 장애로 번지는 시한폭탄이고, 이때 죽는 것은 그 외부 API를 쓰는 기능만이 아니라 같은 스레드 풀을 쓰는 전혀 무관한 API 전부다. 같은 원리가 HTTP 밖에서도 반복된다 — HikariCP connectionTimeout은 "DB에 연결하는 시간"이 아니라 "풀에서 커넥션을 얻기까지 기다리는 시간"이라는 것이 이름 때문에 거의 모두가 오해하는 지점이다.
  • 1
    셋은 재는 구간이 다른 별개의 나사다 — connection은 연결 수립까지, read는 응답 조각과 조각 사이의 무응답, 전체는 호출 시작~완료 전부. read timeout은 조각이 올 때마다 리셋되므로 총 소요 시간을 보장하지 못한다 — 3초짜리 read timeout에서도 21초가 걸릴 수 있다.
  • 2
    값은 관측치에서, 배분은 위에서 아래로 — 개별 값은 대상 API의 p99 + 여유로 잡고(평균으로 잡으면 정상 요청을 대량으로 자른다), 체인 전체는 사용자 SLO를 예산으로 삼아 계층마다 나눠 준다. 하류의 최악 합(재시도·backoff 포함)이 상류의 남은 예산보다 작아야 한다.
  • 3
    타임아웃이 없으면 무관한 API까지 함께 죽는다 — 워커 스레드 풀은 전 API 공유 자원이라 결제 API 하나가 무응답이면 2초 만에 풀이 마르고 조회·로그인·헬스체크까지 응답하지 못한다. 같은 방어를 HikariCP·JDBC 드라이버·DB 서버 계층마다 반복해야 완성된다.

0. 질문 + 출제 의도

질문: "타임아웃은 어디에(connection/read/전체) 어떤 기준으로 설정하나요? 타임아웃 없는 외부 호출의 위험은?"

출제 의도: 타임아웃 없는 외부 호출은 시한폭탄이고, 너무 긴 타임아웃은 스레드를 인질로 잡는다. 전 구간(connection/read/전체)의 타임아웃 예산을 계산해본 사람인지 — 연쇄 장애 방어의 첫 번째 나사를 조여본 경험을 확인하는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① "타임아웃 하나 걸었으니 안전하다" → 3·4절에서 요청 한 건의 타임라인 위에 셋을 올려, read timeout이 덮지 못하는 구간과 3초 설정에서 21초가 나오는 산수를 눈으로 확인한다.
② 값을 감으로 정하는 것("일단 30초") → 6·7절에서 p99 근거와 3,000 → 2,600 → 2,100 → 1,200/700 → 500으로 내려가는 예산 배분표를 직접 따라 계산한다.
③ HTTP 클라이언트만 챙기는 것 → 10절에서 HikariCP·JDBC·PostgreSQL까지 4계층으로 확장하고, 이름 때문에 거의 모두가 틀리는 connectionTimeout의 정체를 바로잡는다.

1. 타임아웃 없는 호출 — 2초 만에 마르는 스레드 풀

1-1. 전제 — 기다리는 스레드는 자리를 비켜주지 않는다

먼저 깔아둘 사실이 둘이다. 이 둘을 인정하는 순간 나머지는 전부 산수로 풀린다.

하나 — 요청 하나 = 스레드 하나
톰캣 같은 전통적 서블릿 서버에서 HTTP 요청 하나는 워커 스레드 하나가 처음부터 끝까지 맡는다. 처리되는 동안 그 스레드는 다른 요청을 볼 수 없다.
둘 — 기다리는 동안에도 자리를 지킨다
여기가 직관에 반한다. 응답 대기 중인 스레드는 CPU를 쓰지 않는다(소켓에서 데이터가 오기를 기다리며 잠들어 있다). 일을 안 하니 비켜줄 것 같지만, 블로킹 I/O에서는 그 스레드의 호출 스택에 진행 상황이 담겨 있어 다른 요청에 내줄 수 없다.

이 문서 전체의 문제를 한 줄로

유한한 자원(워커 스레드 200개)이  무한한 대기  에 노출되는 구조

외부 호출의 본질은 "내 스레드가 상대의 응답을 기다리는 것"이고, 타임아웃이 없으면 이 기다림에 상한이 없다. Spring Boot의 톰캣 기본 워커 스레드 수는 200개다.

스레드 전부 소진까지 = (200 − 평상시 14) ÷ 100개/초  ≈  약 2초

2. 왜 무관한 API까지 죽는가 — 스레드 풀은 공유 자원이다

이유는 단순하지만 놓치기 쉽다. 톰캣 워커 스레드 풀은 API별로 나뉘어 있지 않다. 하나의 풀에서 모든 요청이 스레드를 꺼내 쓴다.

2-1. 비유와 함정 — "라이브러리 기본값이 있겠지"

비유: 은행 창구 창구 직원(스레드)이 전화 한 통(외부 호출)을 붙들고 무한정 대기하는 상황이다. 직원 수는 유한하므로 전화가 안 끊기면 창구 전체가 마비된다. 대기 중인 직원은 아무 일도 하지 않지만 창구를 비워 주지도 않는다 — 1-1에서 본 그대로다. 타임아웃은 "전화는 최대 3초만 기다리고 끊는다"는 규칙이고, 유한한 자원(스레드)을 무한한 대기로부터 지키는 최소한의 방어선이다.

3. 타임아웃 3종 — 요청 한 건의 타임라인 위에 셋을 올린다

"타임아웃 하나 걸었으니 안전하다"가 왜 착각인지는 한 번의 호출이 여러 구간으로 이뤄져 있고, 타임아웃마다 덮는 구간이 다르다는 사실에서 나온다. 요청 한 건을 시간축에 펼쳐 보자. 이 그림 하나가 3·4·5절의 전부다.

3종 암기 — "연 · 조 · 총"

connection = 연결이 되냐· read = 조각 사이의 침묵· 전체 = 총 소요 상한

전화 통화 비유로 꿰면 잊히지 않는다. ① 신호음이 갈 때까지 기다리는 시간 = connection. ② 통화 중 상대가 말을 멈춘 침묵이 얼마나 길어도 되는가 = read(말이 다시 시작되면 침묵 시계는 0으로 돌아간다). ③ 통화 전체를 몇 분까지 허용하는가 = 전체 타임아웃. "침묵만 재면 통화 시간은 못 잰다"가 4절의 함정이다.

read(socket) timeout응답 데이터 조각 사이의 대기상대가 연결은 받았으나 처리가 느림
전체(요청) timeout호출 시작~응답 완료 전체응답이 조금씩 끊임없이 흘러올 때 · DNS 무응답

3-1. connection timeout — "연결이 되냐"의 문제

짧게 잡아야 하는 이유

  • 정상적인 연결 수립은 네트워크 왕복 몇 번이면 끝난다. 같은 데이터센터 내부라면 수 밀리초, 인터넷을 건너도 수십~수백 밀리초다.
  • 그래서 내부 호출이라면 1초 안팎도 충분히 관대한 값이다.
  • 아직 요청을 보내기 전 단계라 상대에게 아무것도 전달되지 않았다 — 부작용이 없다는 것이 확실한 구간이고, 이 성질이 곧 재시도 안전성으로 이어진다(12절 첫 꼬리질문).

길게 잡으면 생기는 손해

  • 상대 서버가 완전히 죽었을 때, 그 사실을 확인하는 데만 그 시간을 전부 쓴다.
  • connection timeout 10초짜리 클라이언트로 죽은 서버를 호출하면 요청마다 10초씩 스레드가 묶인다.
  • 죽음을 확인하는 비용이 장애 자체보다 커지는 상황이다.

3-2. read timeout — 상대의 처리 속도에 대한 인내심

연결 후 응답을 기다리는 시간인데, 정확히는 "바이트와 바이트 사이의 무응답 허용 시간"이다. 이 정의가 중요하고, 다음 절의 함정이 전부 여기서 나온다. 값의 근거는 대상 API의 응답시간 분포다 — 상대가 보통 얼마나 걸리는지를 모르면 정할 수 없다(6절).

4. read timeout의 함정 — 3초로 잡았는데 21초가 걸린다 가산점

read timeout 3초는 "총 3초 안에 응답 완료"가 아니다. 3절 그림에서 read 시계가 조각이 도착할 때마다 리셋된다는 부분이 이유다. 상대가 타임아웃 직전 간격으로 응답을 조금씩 흘려보내면 read timeout은 한 번도 터지지 않으면서 전체 호출이 수십 초를 넘길 수 있다.

여기에 재시도까지 겹치면

최악 소요 = (connect + read) × 시도 횟수

3초 read timeout에 3회 재시도면 최악은 30초를 훌쩍 넘긴다. "read timeout 3초"라는 설정값만 보고 "3초 안에 끝난다"고 읽는 것이 이 절의 전체 함정이다.

5. 전체 타임아웃 — "무슨 일이 있어도 N초"를 씌우는 방법

"이 호출은 무슨 일이 있어도 N초 안에 끝난다"는 보장이 필요하면 호출 전체를 감싸는 상한을 따로 둬야 한다. 이것만이 3절 그림의 t=0부터 t=끝까지를 덮는다. 블로킹 클라이언트에는 이런 상한이 없는 경우가 많아 바깥에서 씌운다.

방법 1 표준 라이브러리로 — CompletableFuture.orTimeout
CompletableFuture.supplyAsync(() -> paymentClient.pay(order), executor)
        .orTimeout(3, TimeUnit.SECONDS);   // 호출 전체가 3초를 넘으면 실패

// ★ 주의: orTimeout은 "기다리는 쪽"을 3초에 끊어 주지만,
//    executor 안에서 돌고 있는 블로킹 호출 자체는 계속 진행된다.
//    그 스레드를 정말 회수하려면 executor 스레드를 별도 풀로 격리해
//    최악의 경우 그 풀만 마르게 만들어야 한다 (bulkhead).
방법 2 Resilience4j로 선언적으로 — TimeLimiter
TimeLimiterConfig config = TimeLimiterConfig.custom()
        // 7절에서 계산할 결제 API 예산 1,200ms를 그대로 상한으로 쓴다.
        .timeoutDuration(Duration.ofMillis(1_200))
        // 상한을 넘겼을 때 진행 중인 작업에 인터럽트를 걸어 정리를 시도한다.
        // 이것이 없으면 "포기했는데 작업은 계속되는" 8절의 낭비가 남는다.
        .cancelRunningFuture(true)
        .build();
방법 3 반응형 클라이언트 — 세 종류를 한자리에서
HttpClient httpClient = HttpClient.create()
        // ① connection timeout — 3절 그림의 ② 구간
        .option(ChannelOption.CONNECT_TIMEOUT_MILLIS, 1_000)
        // ② read/write timeout — 조각 사이의 무응답 상한 (그림의 ④~⑦)
        .doOnConnected(conn -> conn
                .addHandlerLast(new ReadTimeoutHandler(3, TimeUnit.SECONDS))
                .addHandlerLast(new WriteTimeoutHandler(3, TimeUnit.SECONDS)))
        // ③ 요청을 다 보낸 뒤 응답이 시작되기까지의 상한
        .responseTimeout(Duration.ofSeconds(3));

WebClient client = WebClient.builder()
        .clientConnector(new ReactorClientHttpConnector(httpClient))
        .build();

Mono<PaymentResult> result = client.post().uri("/pay")
        .bodyValue(order)
        .retrieve()
        .bodyToMono(PaymentResult.class)
        // ④ 전체 타임아웃 — 위 셋을 다 통과해도 이 벽은 넘지 못한다.
        //    4절의 "조금씩 흘려보내는" 응답을 막는 유일한 장치다.
        .timeout(Duration.ofMillis(1_200));
DNS 이야기를 한 번 더 짚어 둔다 3절 그림의 ① 구간, 즉 호스트명을 IP로 바꾸는 단계는 connection timeout이 덮지 않는 경우가 많다. DNS 서버가 응답하지 않으면 연결을 시도하기 전에 멈춰 버리고, connection timeout도 read timeout도 터지지 않는다. 이 구간을 덮는 것도 전체 타임아웃뿐이다 — 전체 상한이 왜 별도로 필요한지의 또 하나의 근거다.

6. 값의 근거 — p99와 거짓 실패 사이에서 고르기

6-1. 왜 평균이 아니라 p99인가

p99는 "느린 쪽부터 세어 상위 1%를 뺀 나머지가 그 안에 들어오는 시간"이다. p99가 400ms라면 요청 100건 중 99건은 400ms 안에 끝나고 1건은 그보다 오래 걸린다는 뜻이다.

값을 정하는 규칙

read timeout = 대상 API의 p99(또는 p99.9) + 여유분

타임아웃을 정하려면 먼저 상대의 응답시간을 측정·모니터링하고 있어야 한다. 근거 없는 "그냥 30초"는 스레드를 30초씩 인질 잡는 설정이다. 그리고 타임아웃은 "짧을수록 좋다"가 아니라 "정상 분포는 통과시키고 비정상만 자르는 지점"이다.

6-2. 반대 방향의 실수 — 거짓 실패의 악순환

7. 타임아웃 예산 — 위에서 아래로 나눠 준다

호출이 체인을 이룰 때는 개별 값이 아니라 합이 문제다. 그리고 이 합은 아래에서 위로 더해 올리는 것이 아니라, 위에서 아래로 나눠 주는 것으로 계산해야 한다. 출발점은 기술이 아니라 약속이다 — "사용자에게 최대 몇 초 안에 응답할 것인가"라는 SLO를 정하고, 그 숫자를 예산으로 삼아 안쪽 호출들에 배분한다.

①
게이트웨이 층 — 사용자 예산에서 자기 몫과 여유를 뺀다.
3,000ms − 게이트웨이 자체 처리(라우팅·인증·네트워크) 100ms − 안전 여유 300ms = 주문 서비스에 줄 예산 2,600ms
안전 여유를 왜 남기는가 — 계산에 들어가지 않는 시간이 실제로는 존재한다. GC 일시 정지, 스레드 풀 대기, 커널의 스케줄링 지연, 로그 기록. 이것들을 0으로 가정하면 예산이 딱 맞아떨어지는 설계가 실전에서 아슬아슬하게 넘친다.
②
주문 서비스 층 — 받은 예산에서 다시 자기 몫을 뺀다.
2,600ms − 자기 처리(DB 조회·검증·직렬화) 300ms − 안전 여유 200ms = 하위 호출 총량 2,100ms
③
하위 호출들에 나눈다 — 직렬이면 합, 병렬이면 최댓값.
결제 1,200 + 포인트 700 + 남긴 여유 200 = 2,100ms (예산과 정확히 일치)
④
각 API 예산 안에서 다시 재시도와 구간 타임아웃을 나눈다.
2 × T + backoff 200 ≤ 1,200 → 2T ≤ 1,000 → T ≤ 500ms → connect 100 + read 400
포인트 API는 재시도가 없으므로 예산을 그대로 쓴다 — connect 100 + read 600 = 700ms
⑤
병렬로 바꾸면 예산이 남는다. 결제와 포인트가 서로의 결과를 필요로 하지 않는다면 최악 소요는 합이 아니라 최댓값이다.
직렬: 1,200 + 700 = 1,900ms  /  병렬: max(1,200, 700) = 1,200ms → 900ms가 남는다
남은 900ms의 용도는 셋 중 하나다 — ① 여유로 남긴다(가장 안전) ② 결제 API의 재시도를 1회 더 늘린다 ③ 사용자 SLO를 3초에서 2초로 줄여 약속을 강화한다.

예산 배분 4단계 암기 — "빼고 · 빼고 · 나누고 · 쪼갠다"

SLO에서 게이트웨이 몫·여유를 빼고→ 서비스 자기 처리·여유를 빼고→ 하위 호출들에 나누고(직렬=합, 병렬=max)→ 시도·backoff·구간으로 쪼갠다
타임아웃 예산은 "무엇을 포기하고 무엇을 살지"를 정하는 자원 배분표다

이 산수를 해봤는지가 "타임아웃을 걸어봤다"와 "타임아웃을 설계해봤다"의 차이다.

8. 예산이 지켜지지 않으면 — 버려지는 작업과 유령 성공

거꾸로, 예산을 계산하지 않고 계층마다 각자 값을 정하면 어떻게 되는지 보자. 실제로 흔한 조합이다.

원칙이 깨진 설정 사용자 → [게이트웨이 10초] → [주문 서비스] → 결제 API (read 5초 × 재시도 2회) / 포인트 API (read 4초)
주문 서비스의 최악 소요는 5초 × 2회 + 4초 = 14초다. 그런데 게이트웨이는 10초에 연결을 끊는다 — 하위의 타임아웃 합이 상위보다 길다.

사고 하나 — 버려지는 작업(낭비)

  • t=10s 이후의 작업은 결과를 받을 사람이 이미 없다.
  • 부하가 높을 때 이 낭비가 누적되면 실질 처리 능력이 그만큼 줄어든다.
  • 이미 포기된 요청이 아직 살아 있는 요청의 자원을 빼앗는 구조다.

사고 둘 — 정합성 파괴 (더 심각)

  • 사용자는 실패를 봤는데 DB에는 결제와 주문이 남았다. 이 상태를 흔히 유령 성공이라 부른다.
  • 사용자는 실패했다고 믿으니 다시 주문하고, 멱등성 장치가 없으면 이중 결제가 된다.
  • 반대로 포기하고 떠나면 결제만 되고 아무도 모르는 주문이 남는다.

이 절의 원칙 — 한 문장으로

각 계층의 타임아웃(재시도와 backoff를 포함한 최악 합)은 자기 상위의 남은 예산보다 반드시 작아야 한다

이 순서가 지켜지면 "상위가 먼저 포기하는" 상황 자체가 생기지 않는다. 그리고 돈이 걸린 경로라면 하나를 더 붙여야 한다 — 타임아웃은 성공인지 실패인지 알 수 없는 상태를 만들므로, 쓰기 연산에는 멱등성 키가 함께 있어야 한다. 타임아웃 설계와 멱등성 설계는 짝이다.

9. 데드라인 전파 — 남은 시간을 값으로 넘겨준다 가산점

7절의 배분에는 한계가 하나 있다. 하위 서비스에 걸린 타임아웃은 고정값이라, "자기가 언제 호출되었는지"를 모른다.

상위 남은 예산을 계산해 헤더로 전파
long elapsed   = System.currentTimeMillis() - requestStartMillis;
long remaining = totalBudgetMillis - elapsed;   // 3000 - 2500 = 500

// 이미 예산을 다 썼다면 호출 자체를 하지 않는다.
// 어차피 버려질 작업을 하위에 만들지 않는 것이
// 가장 값싼 방어다.
if (remaining <= MIN_USEFUL_MILLIS) {
    throw new DeadlineExceededException();
}

headers.set("X-Request-Deadline-Millis",
            String.valueOf(remaining));
하위 받은 예산을 자기 타임아웃의 상한으로
long budget = header("X-Request-Deadline-Millis")
        .map(Long::parseLong)
        .orElse(DEFAULT_BUDGET_MILLIS);   // 없으면 폴백

// ★ 이 판단이 핵심이다.
// 남은 시간이 자기 최소 처리 시간보다 짧으면
// 시작해도 완주할 수 없다. 그럴 때는 시작하지 않고
// 즉시 포기하는 것이 옳다 — 결과가 버려질 작업에
// DB 커넥션과 스레드를 쓰지 않는다.
if (budget < minimumProcessingMillis) {
    throw new DeadlineExceededException();
}

long callBudget = Math.min(budget - myProcessingMillis,
                            PAYMENT_BUDGET_MILLIS);
비유 하나 — 릴레이 경주의 배턴에 남은 시간을 적어 넘긴다 고정 타임아웃은 주자마다 "나는 10초 뛰면 된다"고 각자 정해 놓은 것이다. 앞 주자가 늦어도 뒷 주자는 그대로 10초를 쓴다. 데드라인 전파는 배턴에 "팀 전체 기록까지 남은 시간 3초"를 적어 넘기는 방식이다 — 받은 주자는 그 안에서 뛰거나, 3초로는 결승선에 못 간다고 판단되면 아예 출발하지 않는다.

효과가 둘이다. 정확성 — 고정 타임아웃보다 예산을 정확히 지킨다. 효율 — "이미 늦었으니 시작하지 않는다"는 판단은 과부하 상황에서 가장 값싼 부하 감소 수단이다(요청을 선별해 버리는 load shedding의 한 형태). gRPC는 이것을 프로토콜 차원에서 기본 제공하고(호출에 deadline을 걸면 하위 호출로 자동 전파된다), HTTP에서는 위처럼 헤더 규약을 팀에서 정해 쓴다.

10. HTTP 밖의 타임아웃 — 커넥션 풀 · 드라이버 · DB 서버

같은 원리가 계층마다 반복된다. 그런데 DB 쪽에는 이름 때문에 거의 모두가 오해하는 설정이 하나 있어, 이것부터 바로잡아야 한다.

10-1. HikariCP connectionTimeout은 "DB에 연결하는 시간"이 아니다 함정

이름이 거짓말을 한다

HikariCP connectionTimeout = "커넥션 풀에서 커넥션을 얻기까지 기다리는 시간"의 상한

즉 dataSource.getConnection()을 호출했을 때, 이 시간 안에 커넥션을 손에 쥐지 못하면 SQLTransientConnectionException을 던진다. DB 서버로의 TCP 연결 수립 시간은 이 값이 아니라 JDBC 드라이버의 연결 옵션(connectTimeout)이 담당한다.

connectionTimeout
HikariCP · 밀리초
풀에서 커넥션을 얻기까지의 대기
connectTimeout
PostgreSQL JDBC · 초
DB 서버로 TCP 연결이 맺어질 때까지
socketTimeout
PostgreSQL JDBC · 초
소켓 무응답의 상한 (기본 0 = 무한)

이름이 거의 같고(connectionTimeout vs connectTimeout), 단위도 다르고(밀리초 vs 초), 재는 것은 완전히 다르다. 이 셋이 겹쳐 혼동이 생긴다.

Before 풀·드라이버를 기본값으로 방치
spring:
  datasource:
    hikari:
      # connection-timeout 미지정 → 기본 30초
      # 풀이 마르면 요청마다 30초씩 워커 스레드가 묶인다
      maximum-pool-size: 20
    # socketTimeout 미지정 → 기본 0 = 무한
    # DB가 응답 없이 사라지면 영원히 기다린다
After 7절의 예산 안으로 끌어온다
spring:
  datasource:
    hikari:
      # 풀에서 커넥션을 "얻기까지" 기다리는 시간
      connection-timeout: 2000        # 2초
      # 이 값이 곧 "동시 실행 가능한 쿼리 수"의 상한
      maximum-pool-size: 20
      # 커넥션 생존 확인에 쓰는 시간의 상한
      validation-timeout: 1000
      data-source-properties:
        # ↓ PostgreSQL JDBC 드라이버 옵션 (단위: 초)
        connectTimeout: 2   # TCP 연결 수립까지
        socketTimeout: 10   # 최후 방어선. 기본 0 = 무한

10-2. PostgreSQL 서버가 스스로 강제하는 세 가지

클라이언트 쪽 타임아웃은 네트워크가 정상이어야 동작한다. 서버가 스스로 끊어 주는 장치를 함께 둬야 방어가 완성된다. 성격이 다른 세 가지가 있다.

statement_timeout
SQL 문 하나의 실행 시간 상한
넘긴 문은 서버가 취소하고 에러를 반환한다. 단위가 "문"이라는 점이 중요하다 — 트랜잭션 전체가 아니라 문 하나마다 따로 적용되므로, 3초짜리 문이 다섯 개면 트랜잭션은 15초까지 갈 수 있다.
lock_timeout
락 획득 대기의 상한
이쪽은 대기만 잰다 — 락을 얻은 뒤의 실행 시간은 관여하지 않는다. 락 대기는 내 쿼리가 무거워서가 아니라 남이 쥐고 있어서 생기는 지연이므로 실행 시간과 별개로 통제해야 한다.
idle_in_transaction_
session_timeout
트랜잭션 열어둔 유휴 세션 정리
애플리케이션이 트랜잭션 안에서 외부 API를 호출하다 멈추면 이런 세션이 생긴다. 방치하면 ① 그 트랜잭션이 쥔 락이 계속 남아 다른 작업을 막고, ② VACUUM이 진행되지 못해 테이블이 부푼다.
lock_timeout이 따로 필요한 실무 사례 ALTER TABLE처럼 강한 락이 필요한 작업에 lock_timeout을 짧게 걸면, 락을 못 얻을 때 조용히 포기하게 되어 뒤에 줄 선 모든 쿼리를 막는 사고를 예방할 수 있다.
권장 값은 계정에 기본값으로 박아 둔다 — 코드에서 빠뜨려도 서버가 지켜 준다
-- 온라인 API용 계정: 짧게 조인다
ALTER ROLE app_user SET statement_timeout = '3s';
ALTER ROLE app_user SET lock_timeout = '1s';
ALTER ROLE app_user SET idle_in_transaction_session_timeout = '30s';

-- 배치 계정은 긴 쿼리가 정상이므로 따로 준다.
-- 같은 값을 전 계정에 걸면 배치가 죽거나, 배치에 맞추면 온라인이 위험해진다.
ALTER ROLE batch_user SET statement_timeout = '30min';
ALTER ROLE batch_user SET lock_timeout = '10s';

-- 특정 쿼리 하나만 예외를 두고 싶으면 세션·트랜잭션 단위로 덮어쓴다
BEGIN;
SET LOCAL statement_timeout = '60s';   -- 이 트랜잭션 안에서만 유효
SELECT ... ;                            -- 무거운 집계 한 방
COMMIT;

10-3. @Transactional(timeout)과 JDBC queryTimeout의 관계

// 트랜잭션 "시작 시각"을 기준으로 3초의 데드라인이 설정된다.
@Transactional(timeout = 3)
public void createOrder(OrderRequest req) {
    orderRepository.save(req.toEntity());   // 여기서 1.2초 걸렸다면
    pointRepository.deduct(req.userId());   // 이 쿼리에는 남은 1.8초가 걸린다
    couponRepository.use(req.couponId());   // 앞의 둘이 2.9초를 썼다면 0.1초만 남는다
}

Spring은 트랜잭션 시작 시각과 timeout으로 데드라인을 계산해 두고, 그 안에서 실행되는 각 JDBC Statement에 "남은 시간"을 setQueryTimeout()으로 걸어 준다. 그래서 "쿼리 하나당 3초"가 아니라 "트랜잭션 전체 3초"이며, 이미 쓴 만큼을 빼서 다음 쿼리에 주는 방식이다 — 7절에서 예산을 위에서 아래로 나눠 준 것과 정확히 같은 발상이다.

여기에 한계가 하나 있다 setQueryTimeout은 드라이버가 서버에 취소를 "요청"하는 방식이다. PostgreSQL 드라이버는 별도의 연결로 취소 요청을 보내는데, 네트워크가 끊긴 상황에서는 그 요청 자체가 전달되지 않는다. 즉 네트워크 장애에는 클라이언트 쪽 타임아웃이 무력할 수 있다. 그래서 세 겹이 다 필요하다 — 서버가 스스로 강제하는 statement_timeout은 네트워크와 무관하게 동작하고, 소켓 수준의 socketTimeout은 응답이 영원히 오지 않는 경우의 최후 방어선이 된다.

11. 타임아웃 · 재시도 · 서킷 — 순서가 있는 한 세트

세 장치는 대체재가 아니라 순서가 있는 한 세트다.

타임아웃이 있어야
실패가 유한 시간에 판정되고→ 실패 판정이 있어야
재시도·서킷이 성립하며→ 서킷이 없으면 재시도가
이미 죽은 상대를 계속 두드린다

타임아웃이 첫 번째 나사인 이유 — 정확히 짚기

타임아웃이 없으면 응답이 오지 않는 호출은 실패로도 성공으로도 판정되지 않고 영원히 "진행 중"이다.

서킷이 안 열린다
판정되지 않은 호출은 서킷의 슬라이딩 윈도우에 들어가지 못하므로 실패율이 올라가지 않는다. 서킷은 열리지 않은 채 스레드가 다 마른다.
재시도할 기회도 안 온다
첫 시도가 끝나지 않으니 재시도할 기회 자체가 오지 않는다.
도입 순서 = 타임아웃 → 재시도 → 서킷. 타임아웃은 나머지 둘의 전제 조건이다.
서킷의 slowCallDurationThreshold도 타임아웃과 함께 정해야 한다 타임아웃보다 이 값이 크면 느린 호출로 집계될 기회가 없다 — 타임아웃이 먼저 터져 전부 "실패"로 잡히기 때문이다. 두 값은 따로 튜닝할 수 없는 한 쌍이다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

타임아웃 3종과 각각의 구간?
연 · 조 · 총 — connection(연결 수립까지) · read(응답 조각 사이의 무응답) · 전체(호출 총 상한). read는 조각마다 리셋된다.
read timeout 3초면 총 몇 초?
보장 없음. 2.9초 간격 조각 7번이면 2.9×7+0.7 = 21초. 재시도까지 겹치면 (connect+read) × 시도 횟수.
값의 근거는?
대상 API의 p99(또는 p99.9) + 여유. 평균은 안 된다 — 분포가 오른쪽으로 긴 꼬리라 평균보다 느린 정상 요청이 대량으로 잘린다.
예산 배분 숫자 체인?
3,000 → 2,600 → 2,100 → 1,200 / 700 → 500(= connect 100 + read 400). 4단계 = 빼고·빼고·나누고·쪼갠다.
예산이 깨지면 무엇이 나는가?
① 버려지는 작업(포기된 요청이 살아 있는 요청의 자원을 빼앗음) ② 유령 성공(사용자는 실패, DB엔 결제·주문). 원칙: 하류 최악 합 < 상류 남은 예산.
HikariCP connectionTimeout?
"풀에서 커넥션을 얻기까지 기다리는 시간". DB 연결 시간이 아니다. 기본 30초 — 풀이 마르면 요청마다 30초씩 워커 스레드가 묶인다.
무한이 기본값인 것 둘?
PostgreSQL JDBC socketTimeout = 0, RestTemplate/RestClient의 기본 요청 팩토리. "라이브러리 기본값이 있겠지"가 가장 흔한 시한폭탄.
DB 타임아웃 4계층?
앱(@Transactional(timeout)) → 풀(connectionTimeout) → 드라이버(connectTimeout·socketTimeout) → DB 서버(3종).
PostgreSQL 서버 3종?
statement_timeout(문 하나의 실행) · lock_timeout(락 획득 대기만) · idle_in_transaction_session_timeout(락 점유 + VACUUM 차단 방지).
타임아웃 없으면 몇 초에 마르나?
(200 − 14) ÷ 100건/초 ≈ 2초. 그리고 죽는 것은 결제를 쓰는 API가 아니라 같은 풀을 쓰는 전부 — /health까지.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

connection timeout과 read timeout이 터지는 상황은 어떻게 다르고, 대응도 달라지나요? 필수힌트: "요청이 상대에게 넘어갔는가"가 갈림길이다

connection timeout은 요청이 상대에게 도달하기 전의 실패라서 부작용이 없다는 것이 확실하다 — 안전하게 재시도할 수 있다.

read timeout은 요청이 이미 상대에게 도달해 처리됐을 수도 있는 상태의 실패다 — 결제 요청이었다면 "실패로 보였지만 실제로는 승인된" 경우가 가능하므로, 멱등성 보장 없이 재시도하면 중복 결제가 난다.

같은 타임아웃이라도 "요청이 넘어갔는가"에 따라 재시도 안전성이 갈린다

한 걸음 더 나가면 좋은 대답이 된다. 타임아웃은 실패가 아니라 "결과를 모르는 상태"다. 명시적인 실패 응답(500)은 "확실히 안 됐다"는 정보인데, 타임아웃은 됐는지 안 됐는지 알려 주지 않는다. 그래서 read timeout 후의 재시도는 멱등성 키가 있을 때만 안전하고, 없으면 재시도 대신 조회로 결과를 확인하거나 사람이 개입할 대기열에 넣어야 한다.

read timeout이 있는데도 전체 응답이 한없이 길어질 수 있는 이유는? 필수힌트: 숫자를 붙여 답해야 설득력이 생긴다

read timeout은 데이터 조각 사이의 무응답 시간만 제한하기 때문이다. 상대가 타임아웃 직전 간격으로 응답을 조금씩 흘리면 read 시계는 계속 리셋되며 전체 시간은 무한정 늘어난다.

숫자를 붙이면 설득력이 생긴다. read timeout 3초에 2.9초 간격으로 조각이 7번 오면 read timeout은 한 번도 터지지 않는데 총 소요는 21초다(2.9 × 7 + 0.7). 또 재시도가 있으면 (connect + read) × 시도 횟수로 최악 시간이 곱해진다.

그래서 총 소요 시간의 보장이 필요한 곳에는 요청 전체를 감싸는 타임아웃(TimeLimiter, orTimeout, WebClient의 .timeout())을 별도로 둔다.

가산점 한 줄 — DNS 조회 구간을 덮는 것도 이 전체 타임아웃뿐이다. 호스트명 해석이 멈추면 connection timeout도 read timeout도 터지지 않는다.

타임아웃 값을 너무 짧게 잡으면 어떤 문제가 생기나요?힌트: 짧은 타임아웃이 어떻게 "부하를 늘리는지"를 설명해야 한다

정상적으로 처리 중인 요청을 실패로 판정하는 거짓 실패가 늘어난다. 그 실패가 재시도를 유발하면 상대 입장에서는 "아직 처리 중인 요청 + 새로 온 재시도"로 부하가 배가 되고, 부하 증가로 응답이 더 느려져 타임아웃이 더 많이 터지는 악순환에 들어간다.

그래서 타임아웃 단축은 반드시 대상의 p99 관측치를 근거로 해야 하고, 재시도 정책과 함께 검토해야 한다.

평균으로 잡으면 안 되는 이유를 덧붙이면 좋다 — 응답시간 분포는 오른쪽으로 긴 꼬리를 가지므로 평균 위에 정상 요청이 상당수 있고, 평균에 맞춘 타임아웃은 그것들을 통째로 자른다.

HTTP 말고 DB 호출에는 어떤 타임아웃들이 있나요? 가산점힌트: 네 계층으로 나눠 답하고, 첫 계층에서 오해를 먼저 바로잡는다

같은 원리가 계층마다 반복된다. 네 계층으로 나눠 답하면 정리가 깔끔하다.

(1) 커넥션 풀 — HikariCP connectionTimeout. 여기서 오해를 먼저 바로잡는 것이 이 질문의 득점 포인트다. 이 값은 "DB에 연결하는 시간"이 아니라 "풀에서 커넥션을 얻기까지 기다리는 시간"이다. 기본값 30초라 풀이 고갈되면 요청마다 30초씩 워커 스레드가 묶인다 — 1절의 스레드 인질극이 DB 쪽에서 재현되는 경로다.

(2) 드라이버 — connectTimeout, socketTimeout. DB 서버로 TCP 연결이 맺어질 때까지와 소켓 무응답의 상한이다. PostgreSQL 드라이버의 socketTimeout 기본값은 0, 즉 무한이므로 반드시 지정한다. socket timeout이 없으면 쿼리 타임아웃조차 동작하지 않는 경우가 있는데, 취소 신호가 네트워크로 전달돼야 하기 때문이다.

(3) 애플리케이션 — @Transactional(timeout). 트랜잭션 전체의 데드라인을 정하고, 각 JDBC Statement에 남은 시간을 setQueryTimeout으로 전달한다. "쿼리당"이 아니라 "트랜잭션 전체"라는 점, 그리고 드라이버가 취소를 요청하는 방식이라 네트워크 장애에는 무력할 수 있다는 점을 같이 말하면 좋다.

(4) DB 서버 — PostgreSQL의 세 가지. statement_timeout은 문 하나의 실행 시간 상한, lock_timeout은 락 획득 대기의 상한(실행 시간은 안 잰다), idle_in_transaction_session_timeout은 트랜잭션을 열어 둔 채 유휴인 세션을 끊는다. 마지막 것은 그런 세션이 락을 붙잡고 VACUUM까지 막아 테이블을 부풀리기 때문에 필요하다. 서버 쪽 값은 애플리케이션 계정과 배치 계정에 각각 다르게 걸어 두는 것이 실무 관행이다.

마무리: "타임아웃은 HTTP 클라이언트만의 문제가 아니라 모든 블로킹 I/O의 문제이고, 계층 중 하나라도 무한이면 그 계층이 전체 방어의 구멍이 됩니다."
타임아웃 값은 한 번 정하면 끝인가요? 시니어 변별힌트: 타임아웃은 "가설"이다. 그리고 늘리는 결정은 무엇과 짝을 이뤄야 하나

아니다. 타임아웃은 상대의 응답시간 분포에 대한 가설이므로, 상대의 성능이 변하면(데이터 증가, 트래픽 성장, 상대 쪽 배포) 무효가 된다.

운영에서는 ① 대상별 응답시간 p99와 타임아웃 발생률을 대시보드로 추적하고, ② 타임아웃 발생률이 평상시 baseline을 넘으면 알림을 걸고, ③ p99가 타임아웃 값에 근접해오면 "타임아웃을 늘릴지, 상대 성능을 개선할지"를 의사결정한다.

무조건 늘리는 것은 스레드 인질 시간을 늘리는 것이므로, 전체 예산 안에서만 조정한다는 원칙까지 말하면 운영 경험이 드러난다. 한 계층의 타임아웃을 늘리려면 7절의 배분표를 다시 계산해 어디서 그만큼을 빼올지 정해야 한다 — 재시도 횟수를 줄이거나, 직렬 호출을 병렬로 바꾸거나, 사용자 SLO 자체를 재협상하거나다.

"타임아웃을 늘렸다"는 결정이 "무엇을 포기했다"와 짝을 이루지 않으면 예산은 이미 깨진 것이다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

전체 타임아웃을 걸었는데 스레드는 왜 여전히 묶여 있나요? 함정힌트: "포기했다"와 "회수했다"는 다른 말이다

orTimeout이나 .timeout()은 "기다리는 쪽"을 끊어 줄 뿐, 이미 시작된 블로킹 호출을 강제로 회수하지 못한다. 호출을 수행하던 스레드는 소켓에서 응답이 오거나 더 안쪽의 read timeout이 터질 때까지 그대로 잠들어 있다.

그래서 전체 타임아웃만으로는 "사용자 응답 시간은 지켰지만 스레드는 여전히 마르는" 상태가 가능하다. 대응은 둘이다.

① 안쪽에 구간 타임아웃을 반드시 함께 건다. 전체 타임아웃은 바깥의 상한일 뿐이고, 실제로 스레드를 풀어 주는 것은 connection/read 타임아웃이다. 둘은 대체 관계가 아니라 보완 관계다.
② 취소와 격리를 함께 쓴다. Resilience4j의 cancelRunningFuture(true)처럼 진행 중인 작업에 인터럽트를 걸어 정리를 시도하고, 그래도 남는 최악의 경우를 대비해 그 호출용 스레드 풀을 따로 떼어(bulkhead) "마르더라도 그 풀만 마르게" 만든다.

전체 타임아웃 = 사용자와의 약속  /  구간 타임아웃 = 내 스레드의 회수 — 목적이 다르다
WebFlux 같은 논블로킹으로 바꾸면 타임아웃이 없어도 되나요? 시니어 변별힌트: 마르는 자원이 스레드에서 다른 것으로 바뀔 뿐이다

아니다. 마르는 자원이 바뀔 뿐 문제는 남는다.

논블로킹에서는 응답을 기다리는 동안 스레드를 붙잡지 않는 것이 맞다 — 1절의 스레드 인질극은 확실히 완화된다. 그런데 미완료 요청은 그대로 쌓인다. 각 요청은 커넥션 풀의 커넥션 하나, 버퍼와 컨텍스트 객체, 파일 디스크립터를 잡고 있고, 이것들도 유한한 자원이다. 상대가 무응답이면 이 자원들이 대신 마른다.

더 중요한 것은 타임아웃이 스레드 보호 장치이기 이전에 "언제 포기할지의 정책"이라는 점이다. 논블로킹으로 바꿔도 사용자는 여전히 무한정 기다리고, 하류 서비스는 이미 아무도 안 기다리는 요청을 계속 처리하며(8절의 낭비), 서킷은 실패 판정이 없어 열리지 않는다(11절).

"논블로킹은 대기의 비용을 낮출 뿐, 대기의 상한을 정해 주지는 않는다"
예산을 하위에서부터 더해 올려 상위 값을 정하면 안 되나요? 시니어 변별힌트: 그렇게 하면 SLO가 "약속"이 아니라 "결과"가 된다

기술적으로는 합이 맞지만, 설계로서는 방향이 거꾸로다.

상향식(합산)의 문제 — 하위 값들을 더해 상위를 정하면 사용자 응답 시간이 "정해지는 것"이 아니라 "나오는 것"이 된다. 그러면 ① 하위 팀이 자기 타임아웃을 올릴 때마다 사용자와의 약속이 소리 없이 늘어나고, ② 예산이 넘쳤을 때 어디를 줄여야 하는지 판단 근거가 없다(모두가 "내 값은 근거가 있다"고 말한다).

하향식(배분)의 이점 — 먼저 "사용자에게 3초 안에 응답한다"는 약속을 못 박으면, 하위 합이 그것을 넘는 순간 즉시 드러나고(8절의 5×2+4=14초 > 10초처럼), "그래서 무엇을 포기할 것인가"라는 올바른 질문으로 이어진다.

현실에서는 둘을 맞춰 본다 — 하향식으로 배분한 값과 상향식으로 관측한 p99를 비교해, 배분값이 관측치보다 작으면 그 호출이 예산을 못 지킨다는 신호다. 그때 하는 일은 타임아웃을 늘리는 것이 아니라 그 호출을 빠르게 만들거나 구조를 바꾸는 것(병렬화·캐시·비동기 분리)이다.

connection timeout을 아주 짧게 잡으면 무슨 일이 생기나요?힌트: 연결 수립도 "네트워크 왕복"이라는 사실을 잊으면 안 된다

연결 단계에서도 거짓 실패가 난다. 연결 수립은 네트워크 왕복이 필요한 작업이고, HTTPS라면 TLS 핸드셰이크가 왕복을 더 요구한다. 여기에 DNS 조회가 같은 상한 안에 포함되는 구현도 있다.

그래서 상한을 정상 왕복 시간에 딱 붙여 잡으면 순간적인 지연이나 재전송에도 곧바로 실패로 판정된다. 특히 인터넷을 건너는 외부 API는 왕복 자체가 수십~수백 밀리초라 내부 호출 기준을 그대로 쓰면 안 된다.

connection timeout도 같은 논리다 — "관측된 정상 연결 시간 + 여유". 다만 정상값 자체가 작으므로 read보다 훨씬 짧게 잡힌다.

실무 감각 한 줄 — 내부 호출(같은 데이터센터/클러스터)과 외부 호출은 값을 나눠 관리한다. 내부는 1초 안팎도 관대하지만, 외부에 같은 값을 쓰면 멀쩡한 상대를 죽었다고 판정할 수 있다.

타임아웃이 자주 터집니다. "값을 늘려 달라"는 요청이 왔다면 어떻게 답하나요? 시니어 변별힌트: 답은 예/아니오가 아니라 "무엇을 먼저 확인하는가"다

세 가지를 순서대로 확인하고 답한다.

① 무엇이 변했는지 먼저 본다. 타임아웃이 갑자기 터진다면 값이 틀린 게 아니라 상대의 p99가 올라간 것일 가능성이 크다. p99 추이를 보고 데이터 증가·트래픽 성장·상대 배포 중 무엇인지 특정한다. 원인이 상대의 성능 저하라면 값을 늘리는 것은 증상을 가리는 일이다.

② 늘려야 한다면 예산표를 다시 계산한다. 이 호출에 200ms를 더 주려면 그 200ms를 어디서 빼올지가 함께 결정돼야 한다 — 재시도 횟수를 줄이거나, 직렬 호출을 병렬로 바꾸거나, 안전 여유를 줄이거나, 사용자 SLO를 재협상하거나다.

③ 상류에 미치는 영향을 확인한다. 이 값을 늘려 하류 최악 합이 상류 예산을 넘게 되면 8절의 버려지는 작업과 유령 성공이 시작된다. 그러면 상류 예산도 함께 조정하거나, 늘리지 않는 쪽을 택해야 한다.

답의 형태: "늘릴 수는 있는데, 그 시간을 어디서 빼올지와 상류 예산을 함께 정해야 합니다"
헬스체크(/health)가 함께 죽는 것이 왜 특히 위험한가요? 함정힌트: 회복하라고 만든 장치가 무슨 일을 하는지 따라가 본다

회복 장치가 장애를 가속하기 때문이다.

/health는 아무 외부 호출도 하지 않는 API지만, 같은 워커 스레드 풀에서 스레드를 받아야 응답할 수 있다. 풀이 마르면 이것도 응답하지 못한다. 그러면 로드밸런서는 이 인스턴스를 죽은 것으로 판정해 풀에서 제거한다.

결과가 역설적이다 — 남은 인스턴스에 부하가 집중되고, 그 인스턴스들도 같은 이유로 마른다. 원인(결제 API 무응답)은 모든 인스턴스에 공통이므로 인스턴스를 빼는 것으로는 절대 해결되지 않고, 살아 있는 쪽의 소진만 앞당긴다.

인스턴스 한 대의 문제일 때만 유효한 장치가, 공통 원인 장애에서는 가속 페달이 된다

방어의 방향 — 근본은 타임아웃으로 스레드를 반환시키는 것이고, 그 위에 외부 호출용 스레드 풀을 본체와 분리(bulkhead)해 "결제가 마르더라도 조회·헬스체크는 산다"는 구조를 만든다. 헬스체크가 무거운 의존성(외부 API·DB)을 직접 확인하지 않도록 설계하는 것도 같은 맥락이다.

한 줄 요약
타임아웃은 connection(연결 수립)·read(응답 조각 간 대기)·전체(호출 총 상한)가 각각 다른 구간을 지키는 별개의 나사이며 — read timeout 3초여도 2.9초 간격으로 조각이 오면 21초가 걸리므로 전체 상한이 따로 필요하다 — 값은 상대의 p99 관측치 + 여유로 잡고, 체인 전체로는 사용자 SLO를 위에서 아래로 나눠 주는 예산 배분(3,000 − 게이트웨이 몫 − 여유 = 2,600 → 자기 처리·여유를 빼고 하위에 2,100 → 재시도 1회면 시도당 500)으로 계산해 하류의 최악 합이 상류 예산 안에 들어오게 해야 한다. 어긋나면 상위가 먼저 포기해 하위 작업이 버려지고 심하면 유령 성공으로 정합성이 깨지며, 타임아웃 없는 외부 호출은 2초 만에 스레드 풀을 마르게 해 그 API와 무관한 요청까지 전부 죽이는 연쇄 장애의 시한폭탄이고, 같은 방어를 HikariCP(connectionTimeout은 풀 대기 시간이다)·JDBC(socketTimeout 기본 0)·PostgreSQL(statement_timeout/lock_timeout/idle_in_transaction_session_timeout) 계층마다 반복해야 완성된다.
