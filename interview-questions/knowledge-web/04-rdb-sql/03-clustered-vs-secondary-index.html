클러스터드 vs 세컨더리 인덱스
PostgreSQL은 힙 + 전부 세컨더리 — 그래도 PK 설계 2원칙은 살아남는다

면접 질문: "클러스터드 인덱스와 논클러스터드(세컨더리) 인덱스의 차이는? (InnoDB 기준)"

핵심 관전 포인트 — PostgreSQL에는 클러스터드 인덱스가 없다. 테이블은 정렬 없는 힙(heap)이고, PK를 포함한 모든 인덱스가 리프에 행의 물리 주소 TID(블록 번호 + 오프셋, 6바이트)를 담아 힙을 직접 가리키는 세컨더리다. InnoDB의 전제(테이블 = PK B+Tree, 세컨더리 리프 = PK 복제, 2단계 북마크 룩업)는 통째로 뒤집히는데 — PK 설계 2원칙은 살아남는다. ① 작게: 세컨더리에 PK가 복제되는 곱셈은 없지만 FK 컬럼 · FK 인덱스 · 조인 키에는 PK가 그대로 들어간다. ② 단조 증가: 힙은 랜덤 PK에 무관하지만 PK B-tree의 무작위 삽입은 페이지 분할 · 캐시 미스 · full_page_writes WAL 증폭을 그대로 일으킨다. 여기에 PG만의 셋째 비용 — 비-HOT UPDATE는 새 TID를 만들어 모든 인덱스를 갱신한다 — 가 붙는다. 비용은 "메모리 부하" 같은 뭉뚱그린 말 대신 페이지 분할 · shared_buffers 적재율 · 랜덤 I/O · WAL 증폭이라는 이름과 인과 사슬로 말해야 한다. 이름을 붙이는 순간 반박도 검증도 가능한 엔지니어링이 된다.
  • 1
    PostgreSQL에서는 그 구분 자체가 성립하지 않는다 — 테이블은 정렬 없는 힙이고, users_pkey든 idx_users_email이든 리프 엔트리가 (키, TID)로 생김새가 완전히 같다. InnoDB의 어휘로 옮기면 PK 인덱스를 포함해 전부 세컨더리이고, 조회는 인덱스 → TID → 힙 페치의 1단계다(트리 재탐색이 없다).
  • 2
    구조가 뒤집혔는데도 PK 설계 2원칙은 살아남는다 — ① 작게: 세컨더리 복제 곱셈은 없지만 곱셈 계수가 "자식 테이블(FK) 개수 × 자식 행 수"로 자리를 옮겼을 뿐이다. ② 단조 증가: 힙은 무관하지만 삽입 위치를 키 값이 결정하는 PK B-tree가 페이지 분할 · 인덱스 bloat · 캐시 오염 · WAL 증폭을 그대로 앓는다.
  • 3
    여기에 PG만의 셋째 비용이 붙고, 비용은 이름으로 말한다 — UPDATE는 새 튜플 = 새 TID라서 비-HOT이면 인덱스 N개 전부에 새 엔트리를 꽂는다(HOT과 fillfactor로 완화). 그리고 "메모리에 부하가 생긴다"가 아니라 shared_buffers 적재율 · 페이지 분할 · 워킹셋 · 랜덤 I/O · WAL FPI라는 이름의 사슬로 말해야 검증도 반박도 가능해진다.

0. 질문 + 출제 의도

질문: "클러스터드 인덱스와 논클러스터드(세컨더리) 인덱스의 차이는? (InnoDB 기준)"

PostgreSQL 기준 재해석: "PostgreSQL의 힙 구조와 InnoDB의 클러스터드 구조는 어떻게 다르고, 그 차이가 PK 설계와 UPDATE 비용에 어떤 영향을 주는가?"

출제 의도: 저장 구조가 PK 선택을 어떻게 결정하는지를 본다. InnoDB에서는 "세컨더리 인덱스가 PK를 품는 구조"에서, PostgreSQL에서는 "힙 + TID 포인터 + MVCC의 새 튜플" 구조에서 — UUID PK가 왜(그리고 어디까지) 문제인지가 여기서 나온다. 테이블 설계 첫 단추의 근거를 확인하는 질문이다.

함정 — "리프에 뭐가 들었는지"를 암기해서 답하는 것 묻는 것은 암기가 아니라 도출이다. 그 구조로부터 "그래서 PK는 어떻게 설계해야 하는가"를 스스로 끌어낼 수 있는지, 그리고 "PG니까 UUID 써도 된다"는 반쪽 명제를 어디서 잘라 말할 수 있는지를 본다.
이 페이지가 겨냥하는 약점 세 가지 ① InnoDB 지식을 PostgreSQL에 그대로 오적용하는 것 → 1·5절에서 "세컨더리 리프에 PK가 복제된다"는 명제가 PG에서는 성립하지 않음을 도식과 엔트리 해부로 못 박고, 대신 어디로 자리를 옮겼는지를 짚는다.
② "PG는 힙이니까 UUID 괜찮다"로 건너뛰는 것 → 6절에서 힙과 PK B-tree를 두 층으로 갈라, 힙은 무관하지만 B-tree는 분할 · 어긋남 · 워킹셋 · WAL 네 갈래로 앓는다는 것을 보인다.
③ 비용을 "메모리 부하"로 뭉뚱그리는 것 → 4~6절에서 이름 다섯 개를 정의하고 사슬로 잇는다. 이름을 붙이면 EXPLAIN (ANALYZE, BUFFERS)로 검증 가능한 주장이 된다.
읽는 방법 — 이 문서는 "없다"에서 시작한다 출발점이 "PostgreSQL에는 클러스터드 인덱스가 없다"인데, 없다는 말은 있는 쪽을 알아야 정보가 된다. 그래서 1절은 있는 쪽(InnoDB)부터 세우고 나란히 놓는다. 이 문서 전체에서 MySQL 이야기는 회색 "MySQL 대조" 상자에만 담아 섞이지 않게 표시했다 — 면접에서도 같은 습관이 필요하다.

1. 두 세계의 구조 — 클러스터드가 있는 쪽과 없는 쪽

1-1. 먼저 클러스터드 인덱스가 무엇인지부터

클러스터드 인덱스(clustered index)는 인덱스의 리프에 행 자체가 들어 있는 구조, 즉 "테이블이 곧 하나의 인덱스"인 저장 방식이다. 이름의 유래는 "키 값이 가까운 행들이 디스크에서도 한 덩어리로 뭉쳐(cluster) 있다"는 성질이다. MySQL/InnoDB가 이 방식을 쓴다 — 테이블은 PK 순으로 정렬된 B+Tree 하나이고, 리프 페이지를 왼쪽부터 읽으면 그게 곧 PK 순 전체 스캔이다.

여기서 두 가지가 따라 나온다. 첫째, PK로 조회하면 트리 하나만 타면 끝이다 — 리프에 도착한 순간 행 전체가 거기 있으니 더 갈 곳이 없다. 둘째, 세컨더리 인덱스의 리프에는 행이 없다. 행은 클러스터드 쪽에만 있으니 세컨더리는 "그 행을 클러스터드에서 어떻게 찾는지"를 적어 둘 수밖에 없고, 그 값이 PK다. 그래서 세컨더리 조회는 트리를 두 번 탄다 — 이 2단계를 북마크 룩업(bookmark lookup)이라 부른다.

PostgreSQL은 이 구조를 쓰지 않는다. 테이블은 힙(heap) — 정렬 없이 행을 쌓아 두는 파일 — 이고, 인덱스는 전부 별도의 B-tree이며 리프에는 행이 아니라 값과 행의 물리 주소만 들어간다. 두 구조를 나란히 놓으면 이렇다.

PostgreSQL 저장 구조 3줄 각인 — 이 세 줄에서 나머지가 전부 도출된다

① 테이블은 힙이다
정렬 없이 도착 순으로 쌓인다. 삽입 위치는 PK가 아니라 FSM이 정한다.
② 모든 인덱스 리프 = (키, TID)
PK 인덱스도 예외가 아니다. 행을 품은 인덱스도, 다른 키가 복제되는 인덱스도 없다.
③ ctid는 UPDATE로 바뀐다
새 버전은 새 주소에 쓰인다. 이 한 줄이 PG 인덱스 유지 비용의 뿌리다(7절).
①에서 "랜덤 PK가 테이블을 흩뜨리지 않는다"가, ②에서 "세컨더리 복제 곱셈이 없다"가,
③에서 "비-HOT UPDATE는 모든 인덱스를 갱신한다"가 나온다

2. 힙 · 라인 포인터 · ctid — PG의 어휘 세 개

2-1. 페이지 한 장을 열어 보면

PostgreSQL의 테이블 파일은 8KB 페이지(블록)의 나열이다. 행(튜플)은 정렬 없이, 빈 공간이 있는 페이지에 들어간다. 어느 페이지에 빈 공간이 있는지는 Free Space Map(FSM) — 테이블마다 딸려 있는 "페이지별 남은 공간 요약본" — 이 알려주고, 새로 붙는 행은 대개 파일 끝 쪽 페이지에 쌓인다.

이 문서 전체를 관통하는 한 줄 — INSERT 위치를 정하는 것은 PK 값이 아니라 FSM이다
그래서 PK가 아무리 무작위여도 힙은 흔들리지 않는다 (6절의 결론 절반)

2-2. ctid — 행의 물리 주소, 그리고 반드시 붙여야 할 성질 하나

행의 주소는 TID = (블록 번호 4바이트, 라인 포인터 번호 2바이트) = 6바이트다. 시스템 컬럼 ctid로 직접 볼 수 있다.

SQL 물리 주소를 눈으로 확인하기
SELECT ctid, id, email FROM users LIMIT 3;
--   ctid    | id | email
--  (0,1)    |  1 | a@x.com      -- 0번 블록의 1번 라인 포인터
--  (0,2)    |  2 | b@y.com
--  (1042,7) |  7 | c@z.com      -- 1042번 블록의 7번 라인 포인터

ctid는 불변 식별자가 아니다 — 이 한 줄이 7절 전체의 뿌리다

PostgreSQL의 UPDATE는 행을 제자리에서 고치지 않는다. 새 튜플 버전을 힙에 삽입하고(그러므로 새 ctid), 옛 튜플에는 "이 트랜잭션이 지웠음" 표시만 남긴다. 같은 논리적 행인데 UPDATE 한 번에 물리 주소가 바뀐다.

SELECT ctid, id, nickname FROM users WHERE id = 7;
--  (1042,7) |  7 | 오리

UPDATE users SET nickname = '거위' WHERE id = 7;

SELECT ctid, id, nickname FROM users WHERE id = 7;
--  (1042,9) |  7 | 거위     ← 같은 행인데 ctid가 바뀌었다 (새 튜플 버전)

그러면 곤란한 일이 생긴다 — 모든 인덱스가 옛 TID를 가리키고 있기 때문이다. 새 버전을 찾아가게 하려면 원칙적으로 인덱스마다 (키, 새 TID) 엔트리를 하나씩 더 꽂아야 한다. 어떤 컬럼을 고쳤는지와 무관하게, 인덱스 N개 전부에. "인덱스가 많으면 UPDATE가 비싸진다"는 흔한 말의 정확한 메커니즘이 이것이다(자세한 것은 7절).

2-3. 왜 논리 포인터(PK)가 아니라 물리 주소(TID)인가

InnoDB가 세컨더리 리프에 (행 주소가 아니라) PK를 넣는 이유는 "클러스터드 인덱스가 정렬을 유지하느라 행을 물리적으로 옮기기 때문"이다. 페이지가 가득 차 분할되면 행 절반이 새 페이지로 이사한다. 그때 물리 주소를 적어 둔 세컨더리가 있다면 전부 고쳐야 하는데, PK 값을 적어 뒀다면 고칠 것이 없다.

PostgreSQL의 힙은 정렬을 유지하지 않으니 행이 저절로 이동하는 일이 없다. 옮길 일이 없으면 주소를 직접 적어도 깨지지 않는다 — 그래서 TID다.

InnoDB의 책 — 개정판에서 쪽수가 밀린다

그래서 찾아보기에 "4.2절"이라는 논리 포인터를 적는다. 본문이 어디로 옮겨가도 찾아보기는 고칠 필요가 없다. 대신 읽는 사람은 목차에서 4.2절이 몇 쪽인지 다시 찾아야 한다 — 이것이 북마크 룩업이다.

PostgreSQL의 책 — 글을 절대 옮기지 않는다

그래서 "173쪽 7번째 줄"이라는 물리 주소를 적어도 된다. 한 번에 그 자리로 펼친다. 다만 규칙이 하나 더 있다 — "고칠 때 그 자리에 덧쓰지 않고 새 자리에 새로 쓴 뒤 옛 글에 취소선을 긋는다". 그러면 찾아보기에 새 줄이 하나 더 필요해진다.

이 비유의 마지막 조각까지 붙이면 — 취소선 그은 옛 글을 지우는 것이 VACUUM이다. 즉 PostgreSQL의 UPDATE 비용, 인덱스 bloat, VACUUM 부담은 전부 "옮기지 않고 새로 쓴다"는 한 가지 결정에서 파생된다.

2-4. 그럼 PostgreSQL에서 "물리 순서"는 무슨 뜻인가

PostgreSQL은 힙의 순서를 보장하지 않지만 관찰은 한다. ANALYZE가 컬럼마다 pg_stats.correlation을 계산하는데, 이 값은 −1에서 1 사이로 그 컬럼의 값 순서와 힙의 물리 순서가 얼마나 일치하는지를 나타낸다. 플래너는 이 값으로 Index Scan의 힙 접근을 "순차에 가까움(비용 낮음)"에서 "완전 랜덤(random_page_cost)" 사이 어디쯤으로 추정한다. 시간 순으로 쌓이는 bigint IDENTITY나 created_at은 1 근처, 무작위 UUID 컬럼은 0 근처다.

CLUSTER 명령은 "PostgreSQL의 클러스터드 인덱스"가 아니다

CLUSTER orders USING orders_pkey;는 힙을 그 인덱스 순으로 1회 재작성한다. 이름 때문에 오해하기 쉬운데 이것은 "한 번 정렬해 두기"이지 구조를 바꾸는 명령이 아니다. 제약이 셋이다.

그래서 PostgreSQL에서 "정렬된 물리 순서"의 효과는 명령이 아니라 조합으로 얻는다 — ① 삽입 순서가 곧 조회 순서가 되게 키를 설계해 correlation을 높게 유지하고, ② 커버링 인덱스 + Index Only Scan으로 힙 접근 자체를 없애고, ③ 시계열이면 파티셔닝에 BRIN(페이지 범위마다 최솟값·최댓값만 기록하는 초소형 인덱스 — correlation이 높을 때만 쓸모가 있다)을 얹는다.

3. 조회 경로 — 인덱스 → TID → 힙 페치

WHERE email = 'c@z.com'은 ① idx_users_email을 루트에서 리프까지 내려가 (1042,7)을 얻고 ② 1042번 블록의 7번 슬롯을 읽는다. InnoDB의 2단계처럼 "다른 트리를 처음부터 다시 탐색"하는 게 아니라 주소를 보고 한 번에 점프한다. 이 두 번째 단계를 힙 페치(heap fetch)라 부른다.

대칭적인 대가 — PK로 조회해도 힙 페치는 똑같이 붙는다 InnoDB에서 PK 조회는 리프가 곧 행이라 페치가 없지만, PostgreSQL에서는 PK 인덱스도 주소만 갖고 있으므로 힙을 한 번 더 읽어야 한다. "세컨더리가 빨라진 만큼 PK가 한 단계 늘었다"는 것이 이 설계의 교환 조건이다.
EXPLAIN 두 단계가 Buffers에 그대로 보인다
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE email = 'c@z.com';

 Index Scan using idx_users_email on users  (cost=0.43..8.45 rows=1 width=120)
                                             (actual rows=1 loops=1)
   Index Cond: (email = 'c@z.com'::text)
   Buffers: shared hit=4          -- 인덱스 3장(루트→브랜치→리프) + 힙 1장

힙 페치가 항상 따라붙기 때문에 PostgreSQL은 이를 줄이는 장치를 둘 갖고 있다. 세 경로를 한 장에 놓으면 이렇다.

4. 비용에 이름 붙이기 — 등장인물 다섯

여기가 이 문서의 심장이다. 구조가 바뀌었으니 PK 설계 2원칙을 PostgreSQL 구조에서 다시 도출해야 하고, 그 비용을 뭉뚱그리지 않고 이름 → 사슬로 말할 수 있어야 한다.

"메모리에 부하가 생긴다"

확인할 방법이 없다. 반박할 고리도, 검증할 지점도 없다. 그래서 인상 진술로 들린다.

"페이지당 엔트리 수가 줄어 shared_buffers 적재율이 떨어지고, 캐시 미스가 디스크 I/O로 번진다"

고리마다 반박할 수 있고, EXPLAIN (ANALYZE, BUFFERS)로 검증할 수 있다.

이름을 붙이는 순간 엔지니어링이 된다 — 이 절의 방법론은 이 한 줄이다

비용의 이름 다섯 — 적 · 워 · 분 · 랜 · 왈

적재율·워킹셋·분할·랜덤 I/O·WAL(FPI)

캐시에 담기는 행의 수
워 — 워킹셋
실제로 자주 손대는 데이터 크기

앞의 둘(적·워)은 "크기" 계열 — 원칙 ① 작게가 때리는 곳. 뒤의 셋(분·랜·왈)은 "순서" 계열 — 원칙 ② 단조 증가가 때리는 곳. 다섯을 두 무리로 묶어 두면 5·6절의 구조가 그대로 따라온다.

4-1. 다섯 이름의 정의 — "무엇인가" 한 문장, "왜 비용인가" 한 문장

(1) shared_buffers — PostgreSQL이 디스크 페이지를 담아 두는 공유 메모리 캐시

무엇인가: PostgreSQL 프로세스들이 함께 쓰는 고정 크기 메모리 영역으로, 디스크에서 읽어 온 8KB 페이지를 여기에 담아 둔다(기본값 128MB, 운영에서는 대개 RAM의 1/4 안팎으로 키운다). 그 뒤에 OS 페이지 캐시를 한 겹 더 쓰는 이중 캐시 구조라, 플래너에게는 effective_cache_size로 "둘을 합치면 이 정도는 캐시에 있다"고 알려준다.

왜 비용인가: 원하는 페이지가 여기 있으면 EXPLAIN (ANALYZE, BUFFERS)에 shared hit으로 찍히고 메모리 접근으로 끝나지만, 없으면 shared read — 즉 디스크 I/O다. 둘의 지연 차이는 자릿수 단위다.

"적재율"이란 — 이 캐시에 실제 행(엔트리)이 몇 건 담기느냐는 밀도다
shared_buffers는 "몇 GB"로 고정이지 "몇 행"으로 고정이 아니다

(2) 워킹셋(working set) — 실제로 자주 손대는 데이터의 크기

무엇인가: 어떤 부하를 처리하는 동안 실제로 접근하는 페이지들의 집합, 그리고 그 크기. OS 가상 메모리 이론에서 온 개념으로 "이 부하를 감당하려면 메모리에 최소 얼마가 올라와 있어야 하는가"를 뜻한다. 캐시가 공급이라면 워킹셋은 수요다.

왜 비용인가: 둘의 대소가 성능을 가르는데, 경계를 넘는 순간 성능이 선형이 아니라 계단식으로 무너진다. 데이터는 매일 조금씩 늘었을 뿐인데 워킹셋이 캐시를 넘어선 그날 갑자기 붕괴한다 — "어제까지 멀쩡했는데" 장애의 상당수가 이 지점이다.

같은 1,000만 행 orders라도 INSERT 한 건이 손대는 페이지를 세어 보면 이렇게 갈린다.

INSERT 한 건이 손대는 페이지 — 힙 쪽은 같고 PK 인덱스 쪽만 만 배 이상 벌어진다.
PK 타입힙PK B-tree
bigint IDENTITYFSM이 가리키는 끝 페이지 1~2장맨 오른쪽 리프 1장 + 경로 브랜치 2~3장 — 합쳐 약 30KB
uuid v4똑같이 끝 페이지 1~2장 (PK와 무관)삽입 지점이 트리 전역에 흩어져 리프 전체 약 400MB(5만 장)
"모든 리프가 워킹셋"이라는 말의 뜻 "다음 INSERT가 어느 리프로 갈지 예측할 수 없으니 어느 리프든 메모리에 있어야 한다" — 이것이 곧 인덱스 전체가 워킹셋이라는 말이다. 그리고 이 표에는 아직 FK 인덱스(order_items.order_id 등)가 빠져 있다 — 그것들도 uuid면 같은 일이 한 벌씩 더 생긴다.

(3) 페이지 분할(page split) — 가득 찬 B-tree 페이지를 둘로 쪼개는 작업

무엇인가: B-tree 페이지에 새 엔트리를 넣어야 하는데 자리가 없으면, 페이지를 둘로 쪼개 절반을 새 페이지(파일 끝 또는 재활용된 페이지)로 옮기고, 부모 노드에 "여기서 갈린다"는 새 분리 키를 올린다.

왜 비용인가: 세 갈래다. ① 쪼개고 옮기고 부모를 고치는 작업 자체의 비용. ② 쪼갠 결과 반쯤 빈 페이지가 둘 생긴다 — 같은 엔트리 수를 담는 데 페이지가 더 필요해지는 인덱스 bloat이고, 이는 곧 (1)의 적재율 하락이다. ③ 새 페이지는 파일 끝에 붙으므로 논리 순서와 물리 순서가 어긋난다.

여기에 중요한 비대칭이 있다 — 리프 fillfactor 기본값 90 기준
맨 오른쪽 끝에 붙는 삽입 = 90%까지 채우고 오른쪽에 새 페이지를 잇는 "이어 붙이기"
중간에 끼워 넣는 삽입만 진짜 반반 분할 — 이 비대칭이 6절의 원칙 ②를 만든다

(4) 랜덤 I/O — 디스크의 흩어진 위치를 오가는 접근

무엇인가: 인접한 블록을 이어서 읽는 순차 I/O와 달리, 매번 다른 위치로 건너뛰며 읽고 쓰는 접근 패턴.

왜 비용인가: 같은 바이트 수를 읽어도 훨씬 느리다. 플래너가 이 차이를 모델링한 값이 random_page_cost(기본 4.0) 대 seq_page_cost(기본 1.0)이다. B-tree 범위 스캔은 리프의 좌우 링크를 따라가는데, 페이지 분할로 리프의 논리 순서와 파일상 물리 순서가 어긋나 있으면 이 순차 스캔이 랜덤 I/O로 전락한다.

(5) WAL과 full_page_writes — 변경을 먼저 적어 두는 로그, 그리고 페이지 통째 기록

무엇인가: WAL(Write-Ahead Log)은 "데이터 파일을 고치기 전에 무엇을 고칠지 먼저 로그에 적는다"는 내구성 장치다. 여기에 PostgreSQL 고유의 규칙이 하나 붙는다 — 체크포인트 이후 어떤 페이지를 처음 건드릴 때는 변경분이 아니라 8KB 페이지 전체 이미지(FPI, full page image)를 통째로 WAL에 쓴다(full_page_writes, 기본 on).

왜 그런 규칙이 있는가: OS가 8KB 페이지를 디스크에 쓰는 도중 전원이 나가면 페이지가 반만 기록된 채 찢어질 수 있는데(torn page), 그런 페이지에는 "몇 바이트를 이렇게 고쳐라"는 변경분 로그를 적용해 봐야 복구가 안 된다. 그래서 체크포인트 후 첫 변경 때는 성한 페이지 전체를 로그에 박아 둔다.

왜 비용인가: 같은 페이지를 계속 건드리면 FPI는 한 번이지만, 매번 다른 페이지를 건드리면 매번 FPI다. INSERT 한 건마다 8KB가 WAL에 실린다는 뜻이다.

매번 다른 페이지→건당 8KB FPI→WAL 볼륨 증가→체크포인트 I/O 증가→스트리밍 복제 지연→아카이브 비용 증가
MySQL 대조 InnoDB는 같은 찢어진 페이지 문제를 doublewrite buffer로 푼다. 그래서 리두 로그가 페이지 단위로 부풀지는 않는다 — FPI에 의한 WAL 증폭은 InnoDB 설명에는 없던 PostgreSQL 고유의 비용 항목이다.

5. 원칙 ① 작게 — 곱셈 계수는 사라진 게 아니라 자리를 옮겼다

5-1. 먼저 용어 — 엔트리(entry)란

사슬의 첫 고리가 "엔트리"라 이것부터 고정한다. B-tree 노드 하나가 곧 8KB 페이지 한 장이고, 엔트리는 그 페이지 안에 기록된 한 건의 레코드, 즉 "행 하나에 대응하는 한 줄"이다.

엔트리 해부 — B-tree 리프 줄에 PK 값이 없다는 것이 이 절의 출발점이다.
위치엔트리 하나에 들어있는 것
힙 페이지라인 포인터 4B + 튜플 헤더 24B + 행 데이터 (모든 컬럼)
B-tree 리프 (PK든 세컨더리든)라인 포인터 4B + 인덱스 튜플 헤더 8B(TID 6B 포함) + 키 값
B-tree 브랜치분리 키(피벗 — 자식을 가르는 데 필요한 접두 부분만) + 자식 블록 번호

idx_users_email의 리프 페이지 한 장(8KB)은 페이지 헤더 24B + 라인 포인터 배열 + │ 헤더 8B(TID (1042,7)) │ "c@z.com" │ 같은 인덱스 튜플 수백 개 + 특수 영역 16B(좌우 리프 링크·레벨)로 채워진다.

정리하면 엔트리 = 키 값 + TID(헤더에 포함) + 라인 포인터 — 여기 어디에도 PK 값이 없다

users.id가 bigint든 uuid든 idx_users_email 페이지의 엔트리 크기는 1바이트도 달라지지 않는다.

InnoDB의 "PK는 (행 수) × (세컨더리 인덱스 수)만큼 곱해지는 계수"라는 명제는
PostgreSQL에서 성립하지 않는다
MySQL 대조 — 그대로 옮겨 말하면 오적용이 된다 InnoDB 세컨더리 리프 엔트리는 (키, PK)라 PK가 100바이트면 인덱스 5개 × 1,000만 행에 92B × 1,000만 × 5 ≈ 4.6GB가 얹힌다. PostgreSQL 면접에서 이 계산을 그대로 말하면 InnoDB 지식을 PostgreSQL에 오적용한 것이다.

5-2. 그래서 "작게"는 폐기인가 — 아니다, PK가 들어가는 자리가 세 군데 남는다

PK 크기가 실제로 청구되는 자리 셋 — 피 · 에프 · 조

피 — PK 인덱스 자체
리프 엔트리가 (PK 값, TID)라 PK가 크면 그만큼 비대해진다. 여긴 곱셈 없이 1배.
에프 — FK 컬럼과 FK 인덱스
여기가 새 곱셈 계수다. 자식 테이블마다 부모 PK가 힙 컬럼으로 한 벌 + FK 인덱스 엔트리로 한 벌 더 들어간다.
조 — 조인 키·해시 테이블
Nested Loop의 Index Cond 비교, 해시 조인이 work_mem 안에 만드는 해시 테이블 크기.
곱셈 계수가 "세컨더리 인덱스 개수"에서 "자식 테이블(FK) 개수 × 자식 행 수"로
자리를 옮긴 것이지 사라진 게 아니다 — 그리고 자식 행은 보통 부모보다 훨씬 많다
PostgreSQL은 FK 컬럼에 인덱스를 자동 생성하지 않는다 그런데 없으면 부모 행을 DELETE하거나 키를 UPDATE할 때마다 자식 테이블 전체를 훑어야 하므로 사실상 필수다. 즉 "만들지 않으면 성능 사고, 만들면 PK 크기가 곱해지는 자리" — 어느 쪽이든 PK를 작게 유지할 이유가 된다.

5-3. 페이지당 엔트리 수가 주는 건 그냥 나눗셈이다

이유는 단순하다 — 페이지가 8KB로 고정이기 때문이다. 늘어나지 않는 상자에 더 큰 물건을 넣으면 개수가 주는 것과 같다.

페이지당 엔트리 수 ≈ (8,192 − 페이지 헤더 24 − 특수 영역 16) × fillfactor ÷ 엔트리 크기
                   ≈ 8,152 × 0.9 ÷ 엔트리 크기 ≈ 7,300바이트 ÷ 엔트리 크기

보정 하나 — 중복 제거(deduplication) PostgreSQL 13부터 B-tree는 같은 키에 딸린 TID들을 posting list로 묶는 중복 제거를 하므로, FK 인덱스처럼 중복 키가 많은 인덱스는 실제 크기가 위 숫자보다 작아진다. 그래도 키 크기의 차이는 남고 사슬의 방향은 그대로다. (참고로 유일한 무작위 키인 UUID PK 인덱스에는 이 최적화가 도움이 되지 않는다 — 6절.)

5-4. 브랜치 노드는 어떻게 되나 — 유일성은 TID가 만들고, 무게는 가볍다

InnoDB가 브랜치에도 PK를 붙이는 이유는 트리 탐색의 유일성이었다. 중복 값이 허용되는 세컨더리 인덱스에서 특정 엔트리 하나를 집으러 내려가려면 분기 키가 유일해야 하기 때문이다. PostgreSQL은 같은 문제를 TID로 푼다. B-tree 엔트리는 (키, TID) 순으로 정렬되고(PostgreSQL 12부터 힙 TID가 정렬 키의 마지막 컬럼처럼 취급된다), 브랜치의 분리 키(피벗)는 자식을 가르는 데 필요한 접두 부분만 남기고 잘라내므로(suffix truncation) 리프 엔트리보다 오히려 작다.

얼마나 아픈가 — 세 경로의 무게가 전혀 다르다. 여기를 뭉뚱그리면 "트리 높이가 올라간다"를 주장의 중심에 세우는 실수를 하게 된다.

6. 원칙 ② 단조 증가 — 힙은 무관하지만 PK B-tree는 그대로 앓는다

여기가 PostgreSQL에서 가장 자주 틀리는 지점이다 "PostgreSQL은 힙이니까 UUID PK가 테이블을 흩뜨리지 않는다"는 맞다. 그런데 거기서 "그러니 UUID v4 PK는 PostgreSQL에서 문제없다"로 건너뛰면 틀린다.
삽입 위치를 값이 결정하는 구조가 하나 남아 있기 때문이다 — PK B-tree, 그리고 그 값을 받는 FK 인덱스들.

힙 — 여기까지는 "PG는 랜덤 PK에 강하다"가 맞다

새 행은 FSM이 가리키는 빈 공간(대개 파일 끝)에 들어간다. PK가 bigint든 uuid든 힙 쪽 워킹셋은 끝 페이지 몇 장으로 같다.

PK B-tree — 삽입 위치를 키 값이 결정한다

여기서 단조 증가와 랜덤이 두 갈래로 갈린다. 그리고 같은 값을 FK로 받는 자식 테이블의 인덱스들이 같은 병을 한 벌씩 더 앓는다.

랜덤 PK가 PK B-tree에 내는 피해 네 갈래 — 분 · 엇 · 워 · 왈

분할 → bloat+순서 어긋남 → 랜덤 I/O+전 리프 워킹셋 → 캐시 오염+FPI → WAL 증폭

4절의 "순서 계열 셋(분·랜·왈)"에 워킹셋 하나가 더 끌려 들어온 것이 이 넷이다. 그래서 "원칙 ②를 어기면 원칙 ①의 피해까지 같이 온다"고 말할 수 있다 — bloat로 페이지 수가 늘면 그게 곧 적재율 하락이기 때문이다.

접수창구 비유 — 상자는 멀쩡한데 카드철이 문제다 서류 원본은 상자에 도착 순으로 쌓는다(힙: PK와 무관). 문제는 번호별 색인 카드철(PK B-tree)이다. 번호표 순서로 카드를 맨 뒤에 끼우는 것(단조 증가)과, 이미 꽉 찬 카드철 중간을 벌려 끼우려고 카드철을 쪼개는 것(랜덤)의 차이다. 그리고 쪼갠 카드철은 매번 복사기(WAL)에 한 장 통째로 올라간다.
MySQL 대조 — "UUID PK가 나쁘다"의 강도는 엔진마다 다르다 InnoDB에서는 이 모든 일이 테이블 그 자체(클러스터드 리프 = 행 전체, 16KB)에서 일어난다. 피해 규모가 "PK 인덱스 크기"가 아니라 "테이블 크기"라 랜덤 PK가 PostgreSQL보다 훨씬 치명적이다. PostgreSQL은 덜 아프지만 안 아픈 게 아니다.

6-1. before / after — PK 설계로 보는 두 원칙

before 랜덤 PK, 그리고 FK 인덱스 누락

    id  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    -- v4: 16바이트 + 무작위 삽입 순서
    ...
);

CREATE TABLE order_items (
    order_id uuid NOT NULL REFERENCES orders(id),
    -- FK 컬럼에 16바이트 한 벌 더, 게다가 인덱스 없음
    ...
);

-- ① orders_pkey: 매 INSERT가 트리 전역의 아무 리프나 열어
--    분할 → 인덱스 bloat + 전 리프가 워킹셋 →
--    INSERT가 읽기 I/O를 유발 + FPI로 WAL 증폭
--
-- ② FK 인덱스 없음 (PostgreSQL은 자동 생성하지 않는다)
--    → 부모 DELETE마다 order_items 전체 Seq Scan
--
-- ③ 인덱스를 만들어도 그 FK 인덱스 역시 uuid 무작위 삽입
--    → 같은 병을 한 벌 더 앓는다
after 작고 단조 증가하는 PK + 외부 식별자 분리

    id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    -- 8바이트, 항상 맨 오른쪽에 append
    public_id uuid NOT NULL DEFAULT gen_random_uuid() UNIQUE,
    -- 외부 노출용은 세컨더리 유니크로 격리
    ...
);

CREATE TABLE order_items (
    order_id bigint NOT NULL REFERENCES orders(id),
    ...
);
CREATE INDEX idx_order_items_order_id ON order_items (order_id);

-- 외부에는 유추 불가능한 public_id만 노출한다.
-- 무작위 삽입 비용은 public_id 유니크 인덱스 하나만 감당한다.

내부 PK / 외부 식별자 분리 가산점

"PK를 UUID로 할까"라는 논쟁 자체를 우회하는 이 패턴이 실무의 기본형이다. 무작위 삽입 비용은 public_id 유니크 인덱스 한 개가 감당하고, FK와 조인 키는 전부 8바이트 순차 키로 간다.

6-2. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

왼쪽 표현이 입에서 나오려 할 때 가운데 이름을 먼저 떠올리고, 오른쪽 사슬로 바꿔 말한다.
뭉뚱그린 표현이름사슬로 말하면
"메모리에 부하가 생긴다"shared_buffers 적재율큰 PK → 자식 테이블의 FK 컬럼·FK 인덱스 엔트리 비대(자식 수만큼) → 8KB 페이지당 엔트리 감소 → shared_buffers에 담기는 행 수 감소 → 캐시 미스 증가 → 디스크 I/O 증가
"왔다갔다 해서 성능 이슈"페이지 분할 + 랜덤 I/O + WAL 증폭랜덤 PK → PK B-tree 삽입 지점 전역 분산(힙은 무관) → 가득 찬 리프 쪼개기 → 인덱스 bloat + 전 리프가 워킹셋 → 캐시 오염 → INSERT마다 디스크 읽기 + 페이지마다 FPI → WAL·복제 지연 증가
"UPDATE가 느려요"비-HOT 갱신 = 전 인덱스 갱신인덱스 컬럼 변경 또는 페이지 여유 없음 → 새 TID → 인덱스 N개 전부 삽입 → 인덱스 bloat → VACUUM 부담 증가 → Index Only Scan의 Heap Fetches 증가

7. 셋째 비용 — 비-HOT UPDATE는 모든 인덱스를 갱신한다

메커니즘은 2-2절에서 이미 봤다. UPDATE는 새 튜플 = 새 TID이고, 모든 인덱스가 옛 TID를 가리키고 있으므로 원칙적으로 인덱스마다 (키, 새 TID) 엔트리를 하나씩 더 꽂아야 한다. 인덱스가 8개인 테이블에서 updated_at 하나만 고쳤는데 인덱스 쓰기가 8건 발생하는 것이다.

이 대가를 피하는 예외 장치가 HOT(Heap-Only Tuple, "힙 안에서만 사는 튜플")이다. 이름 그대로 "힙 안에서만 존재하고 인덱스에는 흔적을 남기지 않는 튜플"이다.

설계 지침 셋 — 이 절은 InnoDB 기준 문서에는 없던 항목이다

①
인덱스 하나를 추가하는 비용은 "그 인덱스를 유지하는 비용"만이 아니다. 그 컬럼을 UPDATE하는 순간 HOT 조건 ①이 깨져 다른 모든 인덱스까지 갱신된다. 자주 바뀌는 컬럼(updated_at, 카운터, 상태 값)에 인덱스를 거는 결정은 이 비용을 알고 해야 한다.
②
갱신이 잦은 테이블은 테이블 fillfactor를 낮춘다. 힙의 기본값은 100(꽉 채움)인데, 이러면 HOT 조건 ②(같은 페이지의 여유 공간)를 만족할 수가 없다. 70~80으로 낮춰 새 버전이 들어갈 자리를 미리 비워 둔다. 다만 이미 꽉 찬 페이지에는 소급되지 않는다.
③
관찰은 pg_stat_user_tables의 n_tup_upd 대비 n_tup_hot_upd로 한다. UPDATE가 많은데 HOT 비율이 낮은 테이블이 인덱스 bloat와 VACUUM 부담의 진원지다.
그리고 PK 설계와 만나는 지점 — PK 값 자체를 UPDATE하는 설계(자연 키를 PK로 쓰는 경우)는 비-HOT이 확정이고 FK cascade까지 끌고 온다
"PK는 불변이어야 한다"는 원칙이 PostgreSQL에서는 HOT 때문에 한 번 더 무게를 얻는다
MySQL 대조 — 같은 상황에서 비용을 결정하는 요인이 정반대다 InnoDB는 행을 제자리에서 갱신하고 옛 버전은 언두 로그로 보낸다. 세컨더리 인덱스는 바뀐 컬럼의 인덱스만 삭제 표시 + 삽입한다.
"인덱스 8개 테이블에서 컬럼 하나 UPDATE"의 비용을 결정하는 요인 — PostgreSQL은 HOT 여부가, InnoDB는 그 컬럼에 인덱스가 걸렸는지가 결정한다.

8. 실무 사례 — "규모 유추 방지를 위해 PK를 UUID로 하자"는 제안

8-1. 요건은 정당하다, 그리고 "PG니까 괜찮다"는 반론은 반쪽이다

연속 번호 PK를 외부에 노출하면 경쟁사가 "주문 번호가 하루에 얼마나 늘어나는지"로 규모를 유추할 수 있다. 요건 자체는 정당하고, 이걸 "기우"라고 잘라내는 답은 좋지 않다.

그러면 팀에서 "우리는 PostgreSQL이니까 InnoDB의 UUID 문제는 해당 없다"는 반론이 따라붙는다. 반쯤 맞다.

맞는 부분 — 힙에 대해서는

테이블은 정렬 없는 힙이고 삽입 위치는 FSM이 정하므로, 랜덤 PK가 테이블을 물리적으로 흩뜨리지 않는다. InnoDB에서 테이블 그 자체가 조각나는 일은 PostgreSQL에서는 일어나지 않는다.

틀린 부분 — PK B-tree · FK 인덱스 · WAL에 대해서는

삽입 위치를 값이 결정하는 구조가 남아 있다. 6절의 ⑴ 분할·bloat ⑵ 순서 어긋남 → 랜덤 I/O ⑶ 전 리프 워킹셋 → 캐시 오염 ⑷ FPI → WAL 증폭이 그대로 발생한다.

이 문장을 정확히 잘라 말하는 것이 이 사례에서 가져갈 한 마디다
"힙에 대해서는 맞고, PK B-tree · FK 인덱스 · WAL에 대해서는 틀립니다"

8-2. MySQL에서 비싼 이유와 PostgreSQL에서 비싼 이유는 다르다

여기를 뭉뚱그리면 "UUID는 나쁘다"는 미신이 되고, 반대로 뭉뚱그린 반론에 부딪히면 논거를 못 댄다. 두 엔진의 이유를 나눠서 정리한다.

결론(대리 키를 쓰라)은 같은데 이유의 위치가 다르다 — 이 차이를 말할 수 있으면 "두 엔진을 원리로 구분한다"로 들린다.
MySQL / InnoDB에서의 대가PostgreSQL에서의 대가
주된 이유행 자체가 PK 순으로 물리 정렬되므로, 무작위 PK는 테이블(= 클러스터드 B+Tree) 중간을 계속 벌려 페이지 분할을 일으킨다힙은 무관하다. 대신 PK 인덱스 B-tree의 삽입 지역성이 무너진다
피해 규모테이블 크기 전체PK 인덱스 + FK 인덱스 크기
세컨더리 인덱스리프에 PK가 복제돼 인덱스 개수만큼 곱해진다리프가 (키, TID)라 영향 없다

PostgreSQL에서 UUID v4 PK가 지불하는 진짜 대가 셋

① 삽입 지역성 상실
무작위 키는 트리 전역에 흩어져 꽂히므로 가득 찬 리프를 계속 쪼갠다 — 페이지 분할과 캐시 미스가 늘어난다.
② 워킹셋 부풀기 + 적재율 하락
키가 8B→16B면 페이지당 엔트리가 366 → 262로 줄고 bloat까지 겹친다. 게다가 인덱스 전체가 워킹셋이 된다.
③ WAL 기록량 증가
매 INSERT가 새 페이지를 처음 건드리므로 full_page_writes로 건당 8KB FPI. 복제 지연과 아카이브 비용까지 번진다.
MySQL을 인용할 때는 MySQL이라고 명시하고 섞지 않는다
"UUID PK를 쓰면 행이 물리적으로 흩어져 테이블이 조각난다"는 문장은
InnoDB에서는 맞고 PostgreSQL에서는 틀린 말이라, 그냥 말하면 오답이 된다

8-3. 대안 — "유추 불가능"과 "무작위 삽입 순서"를 분리한다

핵심 통찰 — 요건이 요구하는 건 "유추 불가능"이지 "무작위 삽입 순서"가 아니다
UUID v4는 두 성질을 한 몸으로 팔고 있을 뿐이고, 랜덤성은 힙에는 무해해도 B-tree에는 최악의 성질이다

(가) 시간 순 정렬성이 있는 ID로 바꾼다

UUID v7은 타임스탬프가 앞쪽에 오는 UUID다 — v4와 같은 16바이트 uuid 타입에 담기면서 삽입은 맨 오른쪽 리프에 가깝게 꽂힌다(PostgreSQL 18부터 uuidv7() 내장, 그 전에는 애플리케이션에서 생성). Snowflake ID는 64비트에 타임스탬프를 상위 비트로 넣는 방식이라 bigint에 그대로 들어간다.

대가 — 생성 시각이 값에 드러난다. 값을 디코딩하면 언제 만들어진 행인지 알 수 있고, 두 ID의 시각 차이도 계산된다. "총량·증가율 유추 방지"가 요건이면 충분하지만, "생성 시각조차 숨겨야 한다"가 요건이면 부적합하다. 또 UUID v7은 16바이트라 8바이트 bigint보다는 여전히 무겁다.

(나) 별도의 공개용 식별자 컬럼을 둔다 (6-1절의 after)

내부 PK는 bigint IDENTITY로 두고, 외부에는 public_id uuid ... UNIQUE만 노출한다. FK와 조인 키는 전부 8바이트 순차 키로 가므로 자식 테이블 수만큼 곱해지던 비용이 없어진다.

대가 — 무작위 삽입 비용이 사라지는 게 아니라 public_id 유니크 인덱스 하나로 격리되는 것이다. 그 인덱스는 여전히 페이지 분할과 FPI를 겪는다. 추가로 "외부에는 public_id, 내부에는 id"라는 규칙을 API 계층에서 지켜야 하는 운영 부담이 생긴다.

이 사례에서 진짜 평가되는 것 요건을 한 단계 쪼개서 "어느 성질이 진짜 필요한지" 되묻는 것 — 이게 시니어의 답변 태도다. "UUID는 안 됩니다"도, "PG니까 괜찮습니다"도 아니고, "유추 불가능은 지키고 무작위 삽입만 걷어내는 방법이 둘 있고, 각각의 대가는 이렇습니다"가 완결된 답이다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

PG 저장 구조 3줄?
① 테이블은 정렬 없는 힙(삽입 위치는 FSM이 정한다) ② 모든 인덱스 리프 = (키, TID) ③ ctid는 UPDATE로 바뀐다.
조회 경로 비교?
세컨더리: PG는 TID로 한 번에 점프(1단계), InnoDB는 PK 트리 재탐색(2단계 북마크 룩업). PK: PG는 힙 페치가 붙고, InnoDB는 트리 하나로 끝.
비용의 이름 다섯?
적 · 워 · 분 · 랜 · 왈 — 적재율 · 워킹셋 · 페이지 분할 · 랜덤 I/O · WAL(FPI). 앞 둘은 크기 계열, 뒤 셋은 순서 계열.
PK 크기가 청구되는 자리 셋?
피 · 에프 · 조 — PK 인덱스 자체(1배) · FK 컬럼과 FK 인덱스(새 곱셈 계수) · 조인 키와 해시 테이블. 세컨더리 인덱스는 영향 없음.
페이지당 엔트리 수 산식?
≈ 7,300B ÷ 엔트리 크기. 엔트리 = 라인 포인터 4B + 헤더 8B(TID 포함) + 키. 20B / 28B / 112B → 366 / 262 / 65개.
랜덤 PK 피해 네 갈래?
분 · 엇 · 워 · 왈 — 분할→bloat · 논리/물리 순서 어긋남→랜덤 I/O · 전 리프 워킹셋→캐시 오염 · FPI→WAL 증폭. 힙은 무관.
PK 크기가 때리는 경로 순위?
⑶ 리프 페이지 수 ≫ ⑵ 트리 높이 > ⑴ 브랜치 공간. 브랜치는 항상 캐시에 상주하므로 높이는 부차적이다.
HOT 조건 둘?
① 인덱스 걸린 컬럼이 하나도 안 바뀜 ② 같은 힙 페이지에 여유 공간. 처방은 fillfactor 70~80, 관찰은 n_tup_hot_upd.
"PG니까 UUID 괜찮다"를 어디서 자르나?
"힙에 대해서는 맞고, PK B-tree · FK 인덱스 · WAL에 대해서는 틀립니다."
CLUSTER 명령의 정체?
"한 번 정렬해 두기"이지 클러스터드 인덱스가 아니다. ACCESS EXCLUSIVE · 이후 삽입은 다시 무질서 · 유지 메커니즘 없음.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

PostgreSQL은 왜 인덱스 리프에 PK가 아니라 물리 주소(TID)를 넣나요? 행이 옮겨지면 어떻게 하나요? 필수힌트: "옮길 일이 없어서"가 이유의 절반이고, 나머지 절반은 트레이드오프 양쪽을 함께 말하는 것이다

힙은 정렬을 유지하지 않으므로 행이 저절로 이동하는 일이 없다. InnoDB가 논리 포인터(PK)를 택한 이유 — 클러스터드 인덱스가 정렬을 유지하느라 페이지 분할 시 행을 물리적으로 옮기고, 그러면 물리 주소를 적어 둔 세컨더리를 전부 고쳐야 한다 — 가 PostgreSQL에는 없으니, 물리 주소를 적어 트리 재탐색 없이 한 번에 점프하는 쪽을 택했다.

행이 "옮겨지는" 유일한 경우는 UPDATE인데, PostgreSQL은 옮기는 게 아니라 새 버전을 새 TID에 쓰고 옛 버전에 삭제 표시를 한다. 그래서 인덱스마다 새 엔트리를 꽂아야 하고(비-HOT), 그걸 피하는 장치가 HOT이다. VACUUM FULL이나 CLUSTER처럼 힙을 통째로 다시 쓰는 작업은 인덱스도 전부 재구축한다.

완결된 답은 트레이드오프 양쪽을 함께 말하는 것이다
PostgreSQL: 세컨더리 읽기 1단계 + 쓰기 시 전 인덱스 갱신 부담(HOT으로 완화)
InnoDB: 세컨더리 읽기 2단계 + 쓰기 안정

가산점 — PostgreSQL 인덱스 엔트리에는 버전 가시성 정보가 없어 옛 버전의 엔트리도 남는다. 이것이 Index Only Scan이 visibility map을 확인해야 하는 이유이자, VACUUM이 힙뿐 아니라 인덱스도 청소하는 이유다.

100바이트 복합 PK에 세컨더리 인덱스가 5개면, PostgreSQL에서는 정확히 무슨 일이 벌어지나요? 함정힌트: InnoDB의 계산을 그대로 옮기면 오답이다. 비용이 나는 자리를 다시 찾아야 한다

함정 질문이다. InnoDB라면 "5개 인덱스 × 1,000만 행에 92B씩 복제"가 정답이지만, PostgreSQL의 세컨더리 인덱스 5개는 PK 크기에 영향받지 않는다 — 리프 엔트리가 (키, TID)이므로 users.id가 무엇이든 1바이트도 달라지지 않는다.

대신 비용이 나는 자리를 짚는다.

① PK 인덱스 자체
엔트리 112B라 페이지당 65개 — bigint의 1/5.6 밀도.
② 자식 테이블마다
FK 컬럼 100B(힙) + FK 인덱스 엔트리 112B. 자식 행 5,000만이면 힙 +4.6GB, FK 인덱스 약 6GB.
③ 조인과 해시
100바이트 비교 비용, work_mem 해시 테이블이 커져 Batches > 1로 디스크에 쏟아지는 시점이 빨라진다.
④ 갱신
복합 PK 컬럼 중 하나라도 UPDATE되면 비-HOT + FK cascade.

처방은 복합 키를 UNIQUE 제약으로 내리고 bigint GENERATED ALWAYS AS IDENTITY 대리 키를 PK로 세우는 것 — 결론은 InnoDB와 같다. 결론은 같은데 이유의 위치가 다르다는 걸 보여주면 "두 엔진을 원리로 구분한다"로 들린다.

UUID v4를 PK로 쓴 테이블에 INSERT가 몰리면 PostgreSQL에서는 무슨 일이 벌어지나요? 필수힌트: 두 층으로 갈라 답한다. 한 층은 "아무 일도 없다"이다

힙: 아무 일도 없다 — FSM이 가리키는 끝 페이지에 순서대로 쌓인다.

PK B-tree(그리고 그 값을 받는 FK 인덱스들): 여기서 전부 일어난다.

삽입 지점 전역 분산→가득 찬 리프마다 페이지 분할→반쯤 빈 리프 = 인덱스 bloat→모든 리프가 워킹셋→INSERT마다 리프를 디스크에서 읽어옴→건당 8KB FPI → WAL 증폭 → 체크포인트·복제 지연

관찰 수단: pgstattuple 확장의 pgstatindex()가 주는 avg_leaf_density(리프 평균 적재율), pg_stat_wal.wal_fpi, EXPLAIN (ANALYZE, WAL). 대안은 UUID v7 / Snowflake / 내부 PK와 외부 식별자 분리다.

"왜 IDENTITY는 안 그런가"를 물으면 — 삽입 위치를 키 값이 결정하는 B-tree에서
단조 증가는 "맨 오른쪽 한 장"만 만지지만 랜덤은 "아무 장이나" 만지기 때문
PK를 안 만들면 PostgreSQL은 어떻게 하나요? 가산점힌트: InnoDB와 결론은 같은데 이유가 정반대다

아무것도 안 한다. InnoDB는 테이블이 곧 클러스터드 인덱스라 PK가 없으면 NOT NULL UNIQUE 인덱스를 승격하거나 6바이트 숨은 row id라도 만들지만, PostgreSQL의 힙은 PK 없이도 완전히 성립한다 — 숨은 대리 키를 만들지 않는다. ctid가 있긴 하지만 불변 식별자가 아니다(UPDATE로 바뀌고, VACUUM이 슬롯을 재사용한다).

그래서 PK 없는 테이블의 대가는 성능이 아니라 운영 기능 쪽에서 온다.

① 논리 복제
REPLICA IDENTITY가 없어 UPDATE/DELETE가 에러가 난다(cannot update table … does not have a replica identity).
② UPSERT 불가
INSERT … ON CONFLICT의 충돌 대상이 없다.
③ 운영·매핑
중복 행 제거를 ctid로 골라 지우는 수공업으로 해야 하고, ORM 매핑도 안 된다.
결론은 InnoDB와 같되 이유가 반대다
InnoDB: "어차피 만들어지니 의도적으로 설계하라"  /  PostgreSQL: "안 만들면 정말 없으니 반드시 만들어라"
MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 다섯 지점 — 리프 · 곱셈 계수 · 랜덤 PK 피해 범위 · UPDATE 방향 · PK 부재
①
리프에 든 것 — InnoDB는 클러스터드 리프 = 행 전체, 세컨더리 리프 = PK 값. PostgreSQL은 모든 리프가 (키, TID)라 "클러스터드 vs 세컨더리" 구분 자체가 없다.
②
곱셈 계수의 위치 — InnoDB는 세컨더리 인덱스 개수만큼 PK가 복제되고, PostgreSQL은 세컨더리에는 영향 없이 자식 테이블의 FK 컬럼·FK 인덱스로 자리를 옮긴다(그리고 PostgreSQL은 FK 인덱스를 자동 생성하지 않는다).
③
랜덤 PK의 피해 범위 — InnoDB는 테이블 자체가 흩어지지만, PostgreSQL은 힙은 무관하고 PK B-tree + FK 인덱스 + WAL FPI가 앓는다. 덜 아프지만 안 아픈 게 아니다.
④
UPDATE 비용의 방향 — InnoDB는 제자리 갱신 + 바뀐 컬럼의 인덱스만, PostgreSQL은 새 TID + 비-HOT이면 모든 인덱스.
⑤
PK가 없을 때 — InnoDB는 숨은 row id를 강제로 만들고, PostgreSQL은 정말 없다(대가는 논리 복제·UPSERT·ORM).

덤으로 — InnoDB는 세컨더리에 PK가 공짜로 들어 있어 PK 컬럼이 자동으로 커버링되지만, PostgreSQL은 INCLUDE로 명시해야 한다. 이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "저장 구조에서 도출했다"로 들린다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

CLUSTER라는 명령이 있잖아요 — 그게 PostgreSQL의 클러스터드 인덱스 아닌가요? 함정힌트: 이름이 함정이다. "무엇을 하는가"와 "무엇을 유지하는가"를 갈라 말한다

아니다. CLUSTER orders USING orders_pkey;는 힙을 그 인덱스 순으로 1회 재작성하는 명령이지, 저장 구조를 클러스터드로 바꾸는 명령이 아니다. 정확한 표현은 "클러스터드 인덱스"가 아니라 "한 번 정렬해 두기"다.

제약이 셋이다. ① ACCESS EXCLUSIVE 잠금이라 그동안 읽기까지 막힌다(무중단이 필요하면 pg_repack --order-by). ② 이후 삽입되는 행은 다시 무질서해진다. ③ 순서를 유지하는 메커니즘이 아예 없다 — 즉 한 번 찍고 마는 스냅샷이다.

그래서 PostgreSQL에서 "정렬된 물리 순서"의 효과는 명령이 아니라 조합으로 얻는다 — ① 삽입 순서가 곧 조회 순서가 되게 키를 설계해 pg_stats.correlation을 높게 유지하고, ② 커버링 인덱스 + Index Only Scan으로 힙 접근 자체를 없애고, ③ 시계열이면 파티셔닝 + BRIN을 얹는다.

PK 조회에도 힙 페치가 붙는다면, PostgreSQL이 InnoDB보다 PK 단건 조회에서 느린 건가요? 시니어 변별힌트: "느리다/빠르다"가 아니라 "무엇을 내주고 무엇을 샀는가"로 답한다

단계 수만 보면 InnoDB가 하나 적은 게 맞다. InnoDB의 PK 조회는 리프가 곧 행이라 도착하는 순간 끝나지만, PostgreSQL은 PK 인덱스도 주소만 갖고 있으므로 힙을 한 번 더 읽어야 한다. 실제로 EXPLAIN (ANALYZE, BUFFERS)에 인덱스 3장 + 힙 1장 = shared hit=4로 찍힌다.

다만 "그래서 느리다"로 끝내면 절반이다. 대칭적으로 세컨더리 조회에서는 방향이 반대다 — PostgreSQL은 TID를 보고 한 번에 점프하지만 InnoDB는 PK 트리를 루트부터 다시 내려간다(북마크 룩업). 즉 PostgreSQL은 "PK 조회 한 단계"를 내주고 "세컨더리 조회의 트리 재탐색"을 산 것이다.

그리고 이 교환은 읽기에서 끝나지 않는다. 물리 주소를 쓰는 대가로 UPDATE 때 비-HOT이면 모든 인덱스를 갱신해야 하고(HOT으로 완화), InnoDB는 제자리 갱신이라 바뀐 컬럼의 인덱스만 손댄다.

한 문장으로 — PostgreSQL: 세컨더리 읽기 1단계 + 쓰기 시 전 인덱스 갱신 부담
InnoDB: 세컨더리 읽기 2단계 + 쓰기 안정

덧붙일 것 하나 — PostgreSQL에서 힙 페치를 0으로 만드는 경로가 있다. 필요한 컬럼을 INCLUDE로 인덱스에 넣고 Index Only Scan이 성립하면 힙을 아예 안 읽는다(단, visibility map이 "모두 가시"여야 하므로 Heap Fetches를 함께 봐야 한다). InnoDB는 세컨더리에 PK가 공짜로 들어 있어 PK 컬럼이 자동 커버링되지만 PostgreSQL은 명시해야 한다.

"인덱스가 많으면 UPDATE가 비싸진다"는 말의 정확한 메커니즘을 PostgreSQL 기준으로 말해보세요. 필수힌트: 출발점은 "PG의 UPDATE는 제자리 갱신이 아니다"라는 한 줄이다

출발점은 ctid가 불변이 아니라는 한 줄이다. PostgreSQL의 UPDATE는 행을 제자리에서 고치지 않고 새 튜플 버전을 힙에 삽입하고(그러므로 새 TID) 옛 튜플에는 삭제 표시만 남긴다.

그러면 모든 인덱스가 옛 TID를 가리키고 있게 된다. 새 버전을 찾아가게 하려면 원칙적으로 인덱스마다 (키, 새 TID) 엔트리를 하나씩 더 꽂아야 하는데 — 어떤 컬럼을 고쳤는지와 무관하게 인덱스 N개 전부에. 인덱스가 8개인 테이블에서 updated_at 하나만 고쳤는데 인덱스 쓰기가 8건 발생하는 것이다.

예외 장치가 HOT이다. ① 인덱스가 걸린 컬럼이 하나도 안 바뀌었고 ② 같은 힙 페이지에 여유 공간이 있으면, 새 튜플을 같은 페이지에 넣고 페이지 안 체인만 걸어 인덱스 갱신을 전부 생략한다.

비-HOT→새 TID→인덱스 N개 전부 삽입→인덱스 bloat→VACUUM 부담 증가→Index Only Scan의 Heap Fetches 증가

그래서 설계 지침이 셋 나온다 — ① 자주 바뀌는 컬럼에 인덱스를 거는 결정은 "다른 모든 인덱스까지 갱신된다"는 비용을 알고 한다. ② 갱신이 잦은 테이블은 fillfactor를 70~80으로 낮춘다. ③ pg_stat_user_tables의 n_tup_hot_upd / n_tup_upd 비율로 관찰한다. MySQL 대조: InnoDB에서는 이 비용을 "그 컬럼에 인덱스가 걸렸는지"가 결정한다.

갱신이 잦은 테이블에 fillfactor를 70으로 낮추면 무엇을 얻고 무엇을 잃나요? 가산점힌트: 얻는 것 하나, 잃는 것 둘, 그리고 함정 하나

얻는 것 — HOT 조건 ②(같은 페이지의 여유 공간)를 만족시킬 확률이 올라간다. 힙의 기본값은 100(꽉 채움)이라 그대로 두면 여유가 없어 HOT이 성립할 수 없다. 70~80으로 낮추면 새 버전이 들어갈 자리를 미리 비워 두게 되고, 그 결과 비-HOT 갱신이 줄어 인덱스 bloat와 VACUUM 부담이 함께 줄어든다.

잃는 것 — ① 같은 행 수를 담는 데 힙 페이지가 더 필요해진다(빈 공간을 일부러 남기므로). ② 페이지가 늘어난 만큼 순차 스캔이 읽어야 할 페이지도 늘고, shared_buffers에 담기는 행 수도 줄어든다 — 5절의 적재율 사슬을 스스로 한 칸 당기는 셈이다.

함정 — fillfactor를 낮춰도 이미 꽉 찬 페이지에는 소급되지 않는다
새로 쓰이는 페이지부터 적용되므로, 즉시 효과를 보려면 테이블 재작성이 필요하다

그래서 모든 테이블에 기본으로 거는 설정이 아니다. 판단 기준은 "UPDATE가 잦고 인덱스가 많은데 n_tup_hot_upd 비율이 낮은 테이블"이고, 조정 후에는 같은 지표로 효과를 확인한다. 측정 없이 거는 순간 그냥 테이블만 커진다.

UUID v7으로 바꾸면 문제가 완전히 사라지나요? 시니어 변별힌트: 두 가지가 남는다 — 하나는 비용, 하나는 요건 쪽이다

대부분 사라지지만 전부는 아니다. UUID v7은 타임스탬프가 앞쪽에 오는 UUID라 v4와 같은 16바이트 uuid 타입에 담기면서 삽입이 맨 오른쪽 리프에 가깝게 꽂힌다. 즉 6절의 네 갈래(분할·bloat, 순서 어긋남, 전 리프 워킹셋, FPI 증폭)가 대부분 해소된다.

남는 것 ① 크기 — 여전히 16바이트다. 8바이트 bigint에 비하면 FK 컬럼·FK 인덱스·조인 키에 두 배가 실리고, 페이지당 엔트리 수도 366 → 262로 줄어든다. 원칙 ①(작게)은 여전히 위반이라는 뜻이다.

남는 것 ② 요건 쪽 — 생성 시각이 값에 드러난다. 값을 디코딩하면 언제 만들어진 행인지를 알 수 있고, 두 ID의 시각 차이도 계산된다. "총량·증가율 유추 방지"가 요건이면 충분하지만, "생성 시각조차 숨겨야 한다"가 요건이면 부적합하다.

그래서 되물어야 할 질문 — "우리 요건이 막으려는 것은 총량 유추인가, 시점 노출인가?"

시점 노출까지 막아야 한다면 내부 PK(bigint IDENTITY) + 외부 public_id uuid v4 UNIQUE 분리가 답이다 — 이때도 무작위 삽입 비용이 사라지는 게 아니라 유니크 인덱스 하나로 격리된다는 점을 함께 말한다. 참고로 Snowflake ID는 64비트라 bigint에 그대로 들어가 크기 문제까지 해결하지만, 시각이 드러나는 성질은 같다.

"PK가 크면 트리 높이가 올라가서 느려지는 거죠?"라고 물으면 어떻게 답하나요? 함정힌트: 틀린 말은 아니지만, 주장의 중심에 세우면 무게를 모르는 것으로 읽힌다

"오를 수 있지만 그건 주범이 아니다"가 답이다. 세 경로의 무게가 전혀 다르다.

⑴ 브랜치 공간 — 무시 가능
fan-out이 수십~수백이라 브랜치는 전체 페이지의 수 % 이하. 1,000만 행 bigint 인덱스에서 리프 2.7만 장에 브랜치 100장 안팎.
⑵ 트리 높이 — 부차적
계단식이고 값이 싸다. 1,000만 행에서 bigint는 3단, 100B PK는 4단. 게다가 상위 레벨은 페이지가 적어 사실상 항상 캐시에 상주하므로 한 단의 비용은 대개 "디스크 I/O 한 번"이 아니라 "메모리 접근 한 번"이다.
⑶ 리프 페이지 수 — 주범
매끄럽게, 항상, 비례해서 나빠진다. 페이지당 엔트리 감소 → 페이지 수 증가 → shared_buffers 적재율 하락 → 캐시 미스 → 디스크 I/O.
⑶ ≫ ⑵ > ⑴ — ⑶을 주장으로 세우고 ⑵는 "상위 레벨은 캐시에 상주하니 부차적"이라고 덧붙인다
셋을 동급으로 나열하면 무게 차이를 모르는 것으로 읽힌다
pg_stats.correlation은 무엇이고 왜 보나요? 가산점힌트: PG에는 클러스터드가 없어서 "보장" 대신 "관찰"을 한다

ANALYZE가 컬럼마다 계산하는 통계값으로, −1에서 1 사이에서 그 컬럼의 값 순서와 힙의 물리 순서가 얼마나 일치하는지를 나타낸다. 시간 순으로 쌓이는 bigint IDENTITY나 created_at은 1 근처, 무작위 UUID 컬럼은 0 근처다.

왜 보는가 — PostgreSQL은 힙의 순서를 보장하지 않지만 관찰은 하기 때문이다. 플래너는 이 값으로 Index Scan의 힙 접근을 "순차에 가까움(비용 낮음)"에서 "완전 랜덤(random_page_cost)" 사이 어디쯤으로 추정한다. 즉 correlation이 낮으면 같은 인덱스라도 플래너가 더 비싸게 보고, Seq Scan이나 Bitmap Heap Scan 쪽으로 기운다.

설계로 연결하면 — "삽입 순서가 곧 조회 순서가 되게 키를 설계한다"는 지침이 여기서 나온다. 그리고 BRIN(페이지 범위마다 최솟값·최댓값만 기록하는 초소형 인덱스)은 correlation이 높을 때만 쓸모가 있다 — 무작위로 쌓인 컬럼에 BRIN을 얹으면 모든 범위가 모든 값을 포함하게 되어 사실상 전체 스캔이 된다.

한 줄 요약
PostgreSQL에는 클러스터드 인덱스가 없다 — 테이블은 정렬 없는 힙이고, PK를 포함한 모든 인덱스는 리프에 (키, TID)를 담아 힙을 직접 가리키는 세컨더리이며, 조회는 인덱스 → TID → 힙 페치 1단계다. 그런데도 PK 설계 2원칙은 살아남는다 — ① 작게(세컨더리 복제 곱셈은 없지만 자식 테이블의 FK 컬럼·FK 인덱스·조인 키에 PK가 들어가 페이지당 엔트리가 줄고 → shared_buffers 적재율이 떨어지고 → 디스크 I/O가 는다), ② 단조 증가(힙은 무관하지만 PK B-tree의 무작위 삽입이 페이지 분할 → 인덱스 bloat + 캐시 오염 + full_page_writes WAL 증폭을 부른다). 여기에 PG만의 셋째 비용, 비-HOT UPDATE = 새 TID = 모든 인덱스 갱신(HOT과 fillfactor로 완화)이 붙는다. 비용은 뭉뚱그리지 말고 이 이름들의 사슬로 말한다.
