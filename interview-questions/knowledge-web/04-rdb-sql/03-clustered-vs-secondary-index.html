클러스터드 vs 세컨더리 인덱스 — 테이블이 곧 인덱스인 구조가 PK 설계를 결정한다

원본: interview-questions/knowledge/04-rdb-sql/03-clustered-vs-secondary-index.md

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "클러스터드 인덱스와 논클러스터드(세컨더리) 인덱스의 차이는? (InnoDB 기준)"
InnoDB에서 테이블은 별도의 파일에 인덱스가 붙은 게 아니라, PK 순서로 정렬된 B+Tree 그 자체다(리프 = 행 전체). 세컨더리 인덱스의 리프에는 물리 주소가 아니라 PK가 논리 포인터로 들어가고, 그래서 조회는 2단계(북마크 룩업)가 된다. 이 구조에서 PK 설계 2원칙이 저절로 도출된다 — ① 작게: PK는 모든 세컨더리 인덱스 엔트리에 복제되는 곱셈 계수다 ② 단조 증가: 랜덤 PK는 페이지 분할을 일으킨다. 그리고 비용은 "메모리 부하", "왔다갔다 해서 느림" 같은 뭉뚱그린 말 대신 페이지 분할 · 버퍼 풀 적재율 · 랜덤 I/O라는 이름과 인과 사슬로 말해야 한다. 이름을 붙이는 순간 반박도 검증도 가능한 엔지니어링이 된다.
출제 의도 — "리프에 뭐가 들었는지"의 암기가 아니라 테이블 설계 첫 단추의 근거를 본다
세컨더리 인덱스가 PK를 품는 구조에서 PK 선택이 왜 성능 결정인지, UUID PK가 왜 문제인지를 스스로 도출할 수 있는지. 구조 지식(리프 내용물·2차 탐색·논리 포인터의 이유)은 출발점일 뿐이고, 채점은 그 구조에서 "PK는 어떻게 설계해야 하는가"까지 혼자 걸어가는지에 있다.
이번 면접 기록 — 평가 "상에 가까운 중". 구조는 완전 정답, 두 군데에서 멈췄다
잘한 것: 리프 내용물, 2차 탐색, 논리 포인터를 쓰는 이유, Snowflake 대안까지 자력으로 나왔다.
멈춘 곳 ①: PK 설계 2원칙(작게 · 단조 증가)이 스스로 안 나왔다 — 재질문 후 방향만 나옴.
멈춘 곳 ②: 비용을 말할 때마다 "메모리에 부하가 생긴다" "디스크를 왔다갔다 해서 성능 이슈"에서 끝났다 — 랜덤 vs 순차 I/O 비용 모델이 비어 있어 Q1·Q2·Q3 3회 연속 같은 지점.
그래서 이 페이지는 아는 구조는 그림 한 장으로 압축하고, 지면의 대부분을 2원칙의 도출과 이름 붙은 사슬로 말하기에 쓴다.
면접 전날 이것만 — PK 설계 2원칙 · 구조에서 도출되는 순서 그대로
세컨더리 인덱스가 PK를 품는다 + 삽입 위치는 PK 값이 정한다 → 그러므로 PK는 짧고 곧게
1
작게 (짧게) — PK는 전체 인덱스 크기의 "곱셈 계수"다 모든 세컨더리 리프 엔트리에 PK가 한 벌씩 복제된다 → 추가 바이트 = (PK 크기 차) × 행 수 × 세컨더리 개수. 그리고 16KB 페이지는 고정이라 엔트리가 뚱뚱해지면 페이지당 엔트리 수↓ → 페이지 수↑ → 버퍼 풀 적재율↓ → 캐시 미스↑ → 디스크 I/O↑. → §3
2
단조 증가 (곧게) — 삽입 위치는 PK 값이 결정한다 단조 증가 PK는 항상 맨 끝 페이지에 append(손대는 페이지 1~2장, 순차 쓰기). 랜덤 PK는 트리 전역 임의 위치에 끼워 넣어 페이지 분할 → 단편화 + 랜덤 I/O + 모든 리프가 워킹셋 → 버퍼 풀 오염(INSERT가 읽기 I/O를 유발). → §4

암기 장치: "PK는 짧고 곧게" — 짧게 = 작게(바이트), 곧게 = 한 방향으로만 자란다(단조 증가). 둘은 독립된 원칙이라 따로 평가한다(UUID v7은 곧지만 짧지 않다 → §6).

  • 1구조 한 장 — 리프 내용물과 북마크 룩업
  • 2등장인물 넷 — 버퍼 풀 · 워킹셋 · 페이지 분할 · 랜덤 I/O
  • 3원칙 ① 작게 — 곱하고 나눈다
  • 4원칙 ② 단조 증가 — append vs 페이지 분할
  • 5말하기 훈련 — 뭉뚱그린 말 → 이름 붙은 사슬
  • 6UUID v4 vs 대안 — Snowflake · UUID v7 · 분리 패턴
  • 7EXPLAIN에서 북마크 룩업 유무 읽기
  • 8꼬리질문 셀프 테스트
  • 91분 인출 테스트
  • ★한 줄 요약

1. 구조 한 장 — 테이블이 곧 클러스터드 인덱스다 이미 아는 부분 · 압축

InnoDB에는 "테이블 따로, 인덱스 따로"가 없다. 테이블 데이터 자체가 PK 순으로 정렬된 B+Tree이고 리프에 행 전체가 들어있다 — 그래서 테이블당 정확히 하나다. 세컨더리 인덱스는 별도의 B+Tree인데 리프에는 인덱스 컬럼 값 + PK 값만 있어, 나머지 컬럼이 필요하면 그 PK로 클러스터드를 한 번 더 탐색한다.

왼쪽 트리의 리프는 (email, PK)뿐이라 행이 필요하면 오른쪽 트리를 루트부터 한 번 더 탄다 — 이 ②가 북마크 룩업이다.

1-1. 왜 물리 주소가 아니라 PK(논리 포인터)인가 — 읽기 한 단계를 내주고 쓰기 안정성을 샀다

만약 물리 주소를 넣는다면

조회는 2차 탐색 없이 한 번에 간다 — 읽기만 보면 이긴다. 그런데 클러스터드 인덱스는 정렬 유지를 위해 삽입·페이지 분할 때마다 행이 물리적으로 이동한다. 행 하나가 움직일 때마다 그 행을 가리키는 모든 세컨더리 엔트리를 찾아 고쳐야 한다 — 세컨더리가 5개면 행 이동 하나가 쓰기 5건으로 증폭.

PK를 넣으면

행이 어디로 이동하든 PK는 변하지 않는다. 세컨더리 인덱스는 손댈 필요가 없다. 대신 읽기에 트리 탐색 한 번(북마크 룩업)을 더 지불한다. 읽기 한 단계 ↔ 쓰기 증폭 제거의 맞교환이다. 양쪽을 다 말해야 완결된 답.

비유 — 책의 찾아보기
찾아보기에 "173쪽"(물리 주소)이라 적으면 개정판에서 페이지가 밀릴 때마다 찾아보기 전체를 다시 만들어야 한다. "4.2절"(논리 포인터)이라 적으면 페이지가 아무리 밀려도 찾아보기는 그대로다 — 대신 4.2절이 몇 쪽인지 목차를 한 번 더 봐야 한다.
클러스터드 인덱스세컨더리 인덱스
정체테이블 그 자체 (PK 순 정렬 B+Tree)별도의 B+Tree (인덱스 컬럼 순 정렬)
개수테이블당 정확히 1개여러 개
리프 엔트리행 전체 (모든 컬럼)인덱스 컬럼 값 + PK 값
행에 도달하는 법리프가 곧 행리프의 PK로 클러스터드를 다시 탐색 (북마크 룩업)
포인터 종류—논리 포인터 (PK). 물리 주소가 아님
PK 없으면첫 NOT NULL UNIQUE → 없으면 숨은 6B row id로 구성— (→ §8)

2. 등장인물 넷 — 이름을 고정해야 사슬을 말할 수 있다 비어 있던 비용 모델

이 절이 이 문서의 심장이다. "메모리에 부하가 생긴다"와 "페이지당 엔트리 수가 줄어 버퍼 풀 적재율이 떨어지고 캐시 미스가 디스크 I/O로 번진다"는 전혀 다른 평가를 받는다. 사슬을 말하려면 먼저 고리의 이름이 있어야 한다. 넷을 공급 · 수요 · 사고 · 대가로 외운다.

버퍼 풀 공급

디스크 페이지를 담아두는 고정 크기 메모리 캐시. 있으면 메모리 속도, 없으면(캐시 미스) 디스크 I/O. 적재율 = 같은 메모리에 실제 행이 몇 건 담기느냐는 밀도. 버퍼 풀은 "몇 GB"로 고정이지 "몇 행"으로 고정이 아니다.

워킹셋 수요

어떤 부하를 처리하는 동안 실제로 손대는 페이지들의 집합. OS 가상 메모리에서 온 개념 — "이 부하를 감당하려면 메모리에 최소 얼마가 올라와 있어야 하는가". 버퍼 풀이 공급이면 워킹셋은 수요. 둘의 대소가 성능을 가른다.

페이지 분할 사고

가득 찬 페이지의 중간에 끼워 넣어야 할 때, 페이지를 둘로 쪼개 절반을 새 페이지로 옮기는 작업. 대가 = 쪼개는 비용 자체 + 반쯤 빈 페이지 두 개가 남는 단편화 + 부모 노드 길잡이 갱신.

랜덤 I/O 대가

디스크의 흩어진 위치를 오가며 읽고 쓰는 접근. 연속된 페이지를 이어 읽는 순차 I/O보다 훨씬 비싸다. "왔다갔다"의 정식 이름이 이것이다 (→ 01 문서 §3 비용 모델).

2-1. 워킹셋 vs 버퍼 풀 — 경계를 넘는 순간 선형이 아니라 계단식으로 무너진다

수치는 md의 예시 규모. 요지는 절대값이 아니라 선형 저하가 아닌 절벽이라는 모양이다.

PK 설계가 이 수요(워킹셋)를 얼마나 좌우하는지가 §4의 요지다. 같은 1,000만 행(클러스터드 리프 약 130,000장 ≈ 2GB)이라도 INSERT 부하의 워킹셋은 —

PKINSERT의 워킹셋크기
BIGINT AUTO_INCREMENT맨 끝 리프 1~2장 + 경로 브랜치 3장≈ 80KB
UUID v4삽입 지점이 전역에 흩어져 리프 전체≈ 2GB (약 25,000배)

"다음 INSERT가 어느 페이지로 갈지 예측할 수 없으니 어느 페이지든 메모리에 있어야 한다" = "모든 리프가 워킹셋".

2-2. 사슬의 첫 고리 — "엔트리"란 16KB 페이지 안의 한 줄이다

B+Tree의 노드 하나 = 16KB 디스크 페이지 한 장. 엔트리 = 그 페이지 안에 기록된 한 건의 레코드, 즉 "행 하나에 대응하는 한 줄". 무엇이 담기는지는 어느 인덱스의 어느 레벨이냐로 정해진다.

위치엔트리 하나에 들어있는 것
클러스터드 리프행 전체 (모든 컬럼)
세컨더리 리프인덱스 컬럼 값 + PK 값 + 약간의 오버헤드(레코드 헤더·길이 정보)← 지금 문제되는 곳
브랜치(중간) 노드길잡이 키 + 자식 페이지 번호(4B) — 세컨더리라면 길잡이 키에도 PK가 붙는다→ §3-3

"PK가 복제된다"는 말은 이 줄마다 PK 값이 한 벌씩 통째로 들어간다는 뜻이다.

3. 원칙 ① 작게 — PK는 곱하고, 페이지는 나눈다 자력 도출 실패 지점

두 개의 산수만 있으면 이 원칙은 외울 필요가 없다. 곱셈(PK가 모든 세컨더리에 복제된다) 그리고 나눗셈(16KB 고정 페이지를 엔트리 크기로 나눈다). 면접에서는 곱셈을 먼저 말하고 나눗셈으로 사슬을 잇는다.

3-1. 곱셈 — PK는 (행 수 × 세컨더리 개수)만큼 복제되는 계수다

행 1건당 PK 사본 5벌. 1,000만 행이면 사본 5,000만 벌 — PK가 8B에서 100B로 커지면 그 차이가 5,000만 번 곱해진다.

3-2. 나눗셈 — 페이지당 엔트리 수가 주는 건 16KB가 고정이기 때문이다

늘어나지 않는 상자에 더 큰 물건을 넣으면 개수가 준다. 페이지당 엔트리 수 ≈ (16KB − 페이지 오버헤드) ÷ 엔트리 크기 ≈ 15,000B ÷ 엔트리 크기. email(평균 30B)에 인덱스를 걸었고 PK만 다른 두 경우:

인덱스 컬럼(30B)은 그대로인데 PK만 커졌을 뿐인데 페이지당 수용량이 37% 깎였다. 상자(16KB)는 늘어나지 않는다.

여기서 나머지는 자동으로 따라온다. 핵심은 ③ — 버퍼 풀은 "몇 GB"로 고정이지 "몇 행"으로 고정이 아니라서, 엔트리가 뚱뚱해지면 같은 메모리에 담기는 행의 수가 줄고, 어제까지 메모리에서 끝나던 조회가 오늘은 디스크를 때린다.

① 페이지당 엔트리↓→ 312개 → 197개→ ② 필요한 페이지 수↑→ 32,051장 → 50,761장 (1.58배)
→③ 버퍼 풀 적재율↓→ 8GB = 524,288장 · 8B PK면 ≈ 1.6억 엔트리 상주, 36B PK면 ≈ 1.0억 — 메모리는 같은데 캐시되는 행이 37%↓
→④ 캐시 미스↑→디스크 I/O↑

"메모리 부하"라는 말은 이 사슬 전체를 뭉뚱그린 것이다. 면접에서는 고리를 하나씩 짚어 말한다 (→ §5).

3-3. 브랜치 노드에도 PK가 붙는다 — 왜, 그리고 얼마나 아픈가 무게 구분이 변별

왜 붙나 — 트리 탐색의 유일성 때문

InnoDB에서 세컨더리 인덱스의 키는 내부적으로 (인덱스 컬럼, PK 컬럼) 전체이고, 리프뿐 아니라 브랜치에도 동일하게 적용된다. idx_email이 non-unique라 'b@y.com'인 행이 3만 건, 리프 100장에 걸쳐 있다면 — 길잡이가 email뿐이면 특정 행 하나를 집으러 내려갈 방법이 없다. ('b@y.com', PK:887)이면 한 지점을 특정한다. 갱신·purge 때 특정 행 하나를 찾아야 하므로 분기 키가 유일해야 한다.

인덱스 정의에 PK 컬럼이 이미 들어있으면 중복해서 붙이지 않는다 — PK=id일 때 INDEX(user_id, id)가 (user_id, id, id)가 되진 않는다.

얼마나 아픈가 — 세 경로의 무게가 전혀 다르다

여기를 뭉뚱그리면 "트리 높이가 올라간다"를 주장으로 세우는 실수를 한다. 순위는 ⑶ ≫ ⑵ > ⑴.

  • ⑴ 브랜치 공간 — 무시 가능. fan-out이 수백이라 브랜치는 전체 페이지의 0.3% 수준(102장 → 257장).
  • ⑵ 트리 높이 — 부차적. 오를 수 있지만 계단식이고, 상위 레벨은 사실상 항상 버퍼 풀에 상주해 "메모리 접근 1회 추가"로 싸다.
  • ⑶ 리프 페이지 수 = 버퍼 풀 적재율 — 주범. 매끄럽게, 항상, 비례해서 나빠진다. §3-2의 ①~④가 이것.
PK 8B  (브랜치 엔트리 ≈ 30+8+4+5 = 47B → 페이지당 319개)
  리프 32,051장 → 상위 101장 → 루트 1장          = 3단

PK 36B (브랜치 엔트리 ≈ 30+36+4+5 = 75B → 페이지당 200개)
  리프 50,761장 → 상위 254장 → 그 위 2장 → 루트   = 4단   ← 경계를 넘긴 했지만, 늘어난 한 단은 대개 메모리 접근 1회
면접에서의 배치
⑶(리프 수 → 적재율)을 주장으로 세우고, ⑵는 "높이도 오를 수 있지만 상위 레벨은 캐시에 상주하니 부차적"이라고 덧붙인다. 셋을 동급으로 나열하면 무게 차이를 모르는 것으로 읽힌다.

4. 원칙 ② 단조 증가 — 맨 끝 append vs 임의 위치 삽입·페이지 분할 "왔다갔다"의 정체

클러스터드 인덱스는 PK 순 정렬을 유지한다. 그래서 삽입 위치는 PK 값이 결정한다 — 이 한 문장에서 아래 그림 전체가 나온다.

위: 손대는 페이지가 늘 "맨 끝 한 장". 아래: "아무 장이나" — 이 차이가 워킹셋 80KB vs 2GB의 25,000배다.

4-1. 페이지 분할의 결과가 번지는 세 갈래

갈래사슬이름
1분할 비용 + 단편화쪼개기 + 절반 이동 + 부모 갱신 → 반쯤 빈 페이지들이 남음 → 같은 행 수에 페이지 수↑ → 적재율↓단편화
2물리 배치 흐트러짐새 페이지가 디스크에서 멀리 놓임 → 리프 연결 리스트를 따라가는 범위 스캔이 순차 I/O에서 랜덤 I/O로 전락랜덤 I/O
3가장 치명적삽입 지점이 전역에 흩어짐 → 모든 리프가 워킹셋 → 버퍼 풀이 못 담으면 INSERT 한 건마다 대상 페이지를 디스크에서 읽어와야 쓸 수 있다 (쓰기가 읽기 I/O를 유발하는 역설)버퍼 풀 오염
비유 — 접수창구의 서류철
번호표 순서로 서류를 서류철 맨 뒤에 끼우는 것(단조 증가)과, 이미 꽉 찬 서류철 중간을 벌려 끼워 넣으려고 서류철을 쪼개는 것(랜덤)의 차이다. 후자는 쪼갤 때마다 반쯤 빈 서류철이 두 권 생기고, 새 서류철은 선반 어디 빈자리든 꽂히니 다음에 순서대로 훑을 때 선반을 왔다갔다 해야 한다 — 이 "왔다갔다"의 이름이 랜덤 I/O다.

4-2. before / after — PK 설계로 보는 두 원칙

before — 크고 랜덤한 PK
CREATE TABLE orders (
    id   CHAR(36) PRIMARY KEY,   -- UUID v4 문자열
    ...
);
-- 36바이트 + 무작위 순서 → 두 원칙을 동시에 위반
-- ① 모든 세컨더리 엔트리에 36B 복제 (곱셈 계수)
-- ② 매 INSERT가 트리 전역의 아무 페이지나 열어
--    페이지 분할 → 단편화 + 전 리프가 워킹셋
--    → 버퍼 풀 오염 → INSERT가 읽기 I/O 유발
after — 작고 단조 증가 PK + 외부 노출용 식별자 분리
CREATE TABLE orders (
    id        BIGINT AUTO_INCREMENT PRIMARY KEY,
    public_id BINARY(16) NOT NULL UNIQUE,
    ...
);
-- id: 8바이트, 항상 맨 끝 append
-- public_id: 외부 노출용은 세컨더리 유니크로
-- 내부 조인·FK·세컨더리 인덱스는 전부 8B PK 기준으로 가볍게,
-- 외부에는 유추 불가능한 public_id만 노출
가산점 — 내부 PK / 외부 식별자 분리 패턴
"PK를 UUID로 할까"라는 논쟁 자체를 우회한다. 클러스터드 인덱스가 지는 비용은 내부용 작은 PK가 감당하고, 규모 유추 방지는 세컨더리 유니크 인덱스의 몫으로 넘긴다.

5. 말하기 훈련 — 뭉뚱그린 말을 이름 붙은 사슬로 교체한다 3회 연속 멈춘 지점

왼쪽은 이번 면접에서 실제로 나온 말이다. 틀린 말이 아니라 사슬의 첫 고리와 마지막 고리만 있고 중간이 없는 말이다. 오른쪽처럼 고리를 채우면 면접관이 어느 고리든 골라 파고들 수 있고 — 그게 "검증 가능한 엔지니어링"이다.

멈춘 말이름사슬로 말하면
"세컨더리마다 100바이트를 더해가니 메모리에 부하가 생긴다" 버퍼 풀 적재율
PK가 모든 세컨더리 엔트리에 복제→엔트리 비대→ 16KB 페이지당 엔트리↓→페이지 수↑→ 버퍼 풀에 담기는 행 수↓ (적재율↓)→캐시 미스↑→디스크 I/O↑
"디스크를 왔다갔다 하면서 저장하게 되어 성능 이슈" (쓰기) 페이지 분할 + 버퍼 풀 오염
랜덤 PK→삽입 지점 전역 분산→ 가득 찬 페이지 분할→단편화 + 새 페이지 디스크 멀리→ 모든 리프가 워킹셋→버퍼 풀 오염→INSERT마다 디스크 읽기
"왔다갔다 해서 느리다" (읽기 — 북마크 룩업이 많을 때) 랜덤 I/O
세컨더리 순서 ≠ PK 순서→매칭 행 1건당 클러스터드 페이지 요청 1건→ 매칭이 많으면 워킹셋 ≈ 테이블 전체→버퍼 풀 미스→ 디스크 랜덤 I/O × 매칭 행 수→그래서 옵티마이저는 매칭 비율이 크면 풀스캔(순차 I/O)로 전환

셋째 줄은 Q2("인덱스가 있는데 안 탄다")와 같은 비용 모델이다 — 세컨더리 리프는 email 순으로 이웃이지만 그 PK들은 클러스터드에서 서로 먼 페이지에 흩어져 있으므로, 북마크 룩업 n회 = 랜덤 페이지 요청 n회. (→ 02 문서, 01 문서 §3)

5-1. 30초 답변 스크립트 — 이름을 이렇게 박아 넣는다

"InnoDB 기준으로 클러스터드와 세컨더리 인덱스의 차이는?"
"InnoDB는 테이블 자체가 PK 순으로 정렬된 클러스터드 B+Tree라서 리프에 행 전체가 있고, 세컨더리 인덱스는 별도 트리인데 리프에 인덱스 컬럼과 PK만 있습니다. 그래서 세컨더리로 찾은 뒤 PK로 클러스터드를 한 번 더 타는 북마크 룩업이 생깁니다. 물리 주소 대신 PK를 넣는 이유는 페이지 분할로 행이 이동해도 세컨더리를 안 고쳐도 되기 때문이고 — 읽기 한 단계를 내주고 쓰기 안정성을 산 겁니다.
이 구조에서 PK 설계 원칙이 두 개 나옵니다. 첫째 작게 — PK는 모든 세컨더리 엔트리에 복제되는 곱셈 계수라, 커지면 16KB 페이지당 엔트리가 줄고 버퍼 풀 적재율이 떨어져 캐시 미스가 디스크 I/O로 번집니다. 둘째 단조 증가 — 삽입 위치를 PK 값이 정하므로 랜덤 PK는 전역에 흩어져 페이지 분할과 단편화를 만들고, 모든 리프가 워킹셋이 돼 버퍼 풀 오염으로 INSERT가 읽기 I/O를 유발합니다. 그래서 UUID v4 대신 BIGINT AUTO_INCREMENT나, 유추 방지가 필요하면 시간 정렬 ID(Snowflake, UUID v7) 또는 내부 PK / 외부 식별자 분리를 씁니다."
셀프 체크 — 사슬을 말하다 막히면 이 세 개만 되짚는다
고리의 이름(버퍼 풀 적재율 · 페이지 분할 · 워킹셋 · 랜덤 I/O) → 고리의 방향(↓인지 ↑인지) → 마지막 고리는 항상 디스크 I/O. "메모리 부하"로 끝나려 하면 "그 메모리가 왜 모자라게 되는가"를 한 번 더 묻는다.

6. 실무 사례 — "규모 유추 방지를 위해 PK를 UUID로 하자" Snowflake 대안은 자력으로 나옴

연속 번호 PK를 노출하면 경쟁사가 "주문 번호가 하루에 얼마나 늘어나는지"로 규모를 유추한다 — 요건 자체는 정당하다. 문제는 UUID v4가 그 요건에 지불하는 대가가 '랜덤성'이고, §4에서 본 대로 랜덤성은 클러스터드 인덱스에 최악의 성질이라는 것.

7. EXPLAIN에서 북마크 룩업 유무 읽는 법 추가

EXPLAIN에 "북마크 룩업" 컬럼은 없다. 대신 "세컨더리를 탔는가"와 "인덱스만으로 끝났는가" 두 신호를 조합해 읽는다. 규칙은 하나 — key에 세컨더리 인덱스가 있는데 Extra에 Using index가 없으면 룩업이 있다.

신호뜻북마크 룩업
key: idx_x + Extra에 Using index 없음세컨더리로 찾고 클러스터드로 되돌아간다있음 — rows 건마다
Extra: Using index커버링 — 필요한 컬럼이 전부 인덱스 안. 인덱스만 읽고 끝없음
Extra: Using index conditionICP — 인덱스 컬럼 조건을 룩업 전에 스토리지 엔진에서 걸러 룩업 횟수를 줄임있음 (줄어듦)
Extra: Using MRR룩업 전에 모은 PK를 정렬해 클러스터드 접근을 순차에 가깝게 — 랜덤 I/O를 순차화있음 (덜 랜덤)
type: ALL, key: NULL (인덱스가 있는데도)옵티마이저가 "룩업 n회의 랜덤 I/O > 풀스캔의 순차 I/O"로 판단해 인덱스를 버림인덱스 포기 (§5 셋째 줄)
type: index + Using index세컨더리 리프 전체를 훑되 커버링없음
before — 룩업 118,240회
EXPLAIN SELECT id, email, name
FROM users WHERE email LIKE 'a%'\G

         type: range
          key: idx_email          -- (email)
         rows: 118240
        Extra: Using index condition
-- 'Using index'가 아니다
-- name은 idx_email에 없음 → 클러스터드에서 가져와야
-- → 118,240회 북마크 룩업 = 랜덤 페이지 요청 118,240건
-- 매칭 비율이 더 커지면 type: ALL로 뒤집힐 수 있다
after — 커버링으로 룩업 0회
ALTER TABLE users ADD INDEX idx_email_name (email, name);
EXPLAIN SELECT id, email, name
FROM users WHERE email LIKE 'a%'\G

         type: range
          key: idx_email_name     -- (email, name) + PK id는 자동 포함
         rows: 118240
        Extra: Using where; Using index
-- id·email·name 전부 세컨더리 안 → 인덱스만 읽고 끝
-- rows는 같아도 페이지 요청은 리프 연결 리스트 순차 읽기
-- 대신 쓰기마다 이 인덱스도 갱신 — 공짜가 아니다 (→ 09)
MySQL 8의 EXPLAIN FORMAT=TREE에서는 이름에 바로 드러난다
Index lookup on users using idx_email (email='a@x.com') → 룩업 있음. Covering index lookup on users using idx_email_name (email='a@x.com') → Covering이 붙으면 룩업 없음. EXPLAIN ANALYZE로 실제 rows와 시간까지 보면 "룩업 118,240회가 실제로 얼마였는지"가 숫자로 남는다.

여기서 "왜 PK id가 자동 포함되나"에 답할 수 있어야 한다 — §1의 구조(세컨더리 리프 = 인덱스 컬럼 + PK) 그대로다. SELECT id는 어떤 세컨더리 인덱스로도 커버된다.

8. 꼬리질문 셀프 테스트 — 질문만 보고 먼저 답한 뒤 펼친다

세컨더리 리프에 물리 주소를 넣으면 2차 탐색 없이 더 빠를 텐데, 왜 PK를 넣나요?

읽기만 보면 물리 주소가 이긴다. 그러나 클러스터드 인덱스는 정렬 유지를 위해 페이지 분할 때마다 행을 물리적으로 이동시키는데, 물리 주소를 넣었다면 행 하나가 움직일 때마다 그 행을 가리키는 모든 세컨더리 인덱스를 찾아 고쳐야 한다. 세컨더리가 5개면 행 이동 하나가 쓰기 5건으로 증폭된다.

PK는 행이 어디로 가든 불변이므로 세컨더리는 영향이 없다. 읽기 한 단계(북마크 룩업)를 내주고, 쓰기 증폭을 없앤 트레이드오프 — 양쪽을 다 말해야 완결된 답이다. (PostgreSQL이 반대 선택을 한 것과 대비하면 격이 오른다 → 아래 시니어 문항.)

100바이트 복합 PK에 세컨더리 인덱스가 5개면, 정확히 무슨 일이 벌어지나요? "메모리 부하"로 멈췄던 문항

"곱셈 계수"부터. PK는 5개 인덱스의 모든 리프 엔트리에 복제되므로 행마다 100B × 5 = 500B가 인덱스 쪽에 얹히고, 1,000만 행이면 그것만 수 GB다.

이어서 사슬. 엔트리가 비대해져 16KB 페이지당 엔트리 수가 줄고 → 같은 인덱스를 담는 데 페이지가 많아져 → 버퍼 풀 적재율이 떨어지고 → 캐시 미스가 늘어 디스크 I/O가 는다. 트리 높이도 오를 수 있지만 상위 레벨은 캐시 상주라 부차적.

쓰기 쪽도. INSERT 한 번에 트리 6개(클러스터드 1 + 세컨더리 5)를 갱신하는데 엔트리가 크니 페이지가 빨리 차고 분할도 잦다.

처방. 복합 PK를 유니크 제약으로 내리고 작은 대리 키(BIGINT AUTO_INCREMENT)를 PK로 세운다.

UUID v4를 PK로 쓴 테이블에 INSERT가 몰리면 무슨 일이 벌어지나요? AUTO_INCREMENT와 달리 왜 UUID v4만 이런가요? "왔다갔다"로 멈췄던 문항

삽입 지점이 트리 전역에 흩어진다 → 대상 페이지가 가득 차 있으면 페이지 분할(쪼개기 + 절반 이동 + 부모 갱신) → 반쯤 빈 페이지가 쌓이는 단편화 → 인덱스의 모든 리프가 워킹셋이 되어 버퍼 풀이 못 담는 순간부터 INSERT 한 건마다 대상 페이지를 디스크에서 읽어와야 한다 (버퍼 풀 오염 — 쓰기가 읽기 I/O를 유발).

왜 UUID v4만. 삽입 위치를 PK 값이 결정하는 클러스터드 구조에서, 단조 증가는 "맨 끝 한 장"만 만지지만 랜덤은 "아무 장이나" 만지기 때문. 워킹셋 80KB vs 2GB.

대안은 시간 정렬성 있는 ID(Snowflake, UUID v7) 또는 내부 PK / 외부 식별자 분리.

PK를 안 만들면 InnoDB는 어떻게 하나요? 가산점

테이블 = 클러스터드 인덱스라는 명제 때문에 InnoDB는 클러스터드 인덱스 없이는 테이블을 만들 수 없다. PK가 없으면 ① 첫 번째 NOT NULL UNIQUE 인덱스를 클러스터드로 승격하고, ② 그것도 없으면 내부적으로 6바이트짜리 숨은 row id를 만들어 클러스터드를 구성한다.

숨은 row id는 개발자가 조회 조건으로 쓸 수 없으므로 세컨더리 → 클러스터드 재탐색 구조의 이점을 하나도 못 누린다. 결론: 어차피 클러스터드는 만들어지니, 그 축을 의도적으로 설계하라(명시적 PK).

이 구조가 모든 DB의 보편인가요? PostgreSQL도 이런가요? 시니어 변별

아니다 — 클러스터드 테이블은 InnoDB의 설계 선택이지 RDB의 보편이 아니다.

InnoDBPostgreSQLSQL Server
테이블클러스터드 B+Tree (PK 순 정렬)정렬 없는 힙(heap)테이블마다 클러스터드/힙 선택
인덱스가 가리키는 것PK (논리 포인터)행의 물리 위치 (TID)클러스터드면 키, 힙이면 RID
조회인덱스 → 클러스터드 재탐색 (2단계)인덱스 → 힙 한 번 (트리 재탐색 없음)—
행 이동 시세컨더리 무수정인덱스 갱신 필요 → HOT(Heap-Only Tuple)로 완화—

PostgreSQL은 InnoDB가 피해간 그 비용(행 이동 시 인덱스 갱신)을 지불하는 대신 조회 단계가 하나 적다. 이 비교를 할 수 있으면 "InnoDB의 논리 포인터는 쓰기 안정성과 읽기 단계 수를 맞바꾼 트레이드오프"라는 프레임으로 답의 격이 올라간다.

따라서 "UUID PK는 무조건 나쁘다"도 틀린 명제다 — 힙 테이블에서는 랜덤 PK의 페이지 분할 문제가 클러스터드만큼 치명적이지 않다. 저장 엔진의 구조를 먼저 묻고 결론을 내리는 것이 시니어의 순서다.

UUID v7로 바꾸면 PK 설계 2원칙이 다 해결되나요? 추가

아니다 — 한 원칙만 해결된다. UUID v7은 타임스탬프가 선두라 삽입이 순차적이 되어 ② 단조 증가는 만족한다. 그러나 BINARY(16)으로 저장해도 16B로 BIGINT의 2배라 ① 작게는 절반만 해결이다(CHAR(36) 36B에 비하면 크게 나아지긴 한다).

그러니 "v7이면 괜찮다"가 아니라 "곧게는 됐고, 짧게는 여전히 곱셈 계수가 2배"라고 두 원칙을 분리해 말한다. 세컨더리 인덱스가 많은 테이블일수록 그 2배가 §3-1의 곱셈으로 불어난다.

PK 값을 UPDATE하면 내부적으로 무슨 일이 벌어지나요? 추가

두 군데가 동시에 움직인다. ① 클러스터드는 PK 순 정렬이라 행이 새 위치로 이동한다(사실상 삭제 + 삽입). ② 모든 세컨더리 인덱스의 그 행 엔트리에 박힌 PK 사본을 전부 갱신해야 한다 — 세컨더리가 5개면 5군데.

즉 "세컨더리는 PK를 논리 포인터로 쓰니 행 이동에 안전하다"는 §1-1의 장점은 PK가 불변이라는 전제 위에 서 있다. 그래서 PK 설계에는 사실상 세 번째 원칙이 따라온다 — 바뀌지 않는 값. 이메일·주민번호 같은 자연 키를 PK로 삼지 않는 이유 중 하나다.

랜덤 삽입이 세컨더리 인덱스에서도 똑같이 치명적인가요? 클러스터드만 특별히 아픈 이유가 있나요? 시니어 변별

세컨더리 인덱스도 인덱스 컬럼 순으로 정렬이라 랜덤 값(예: email)의 삽입은 흩어진다. 그런데 InnoDB에는 체인지 버퍼(change buffer)가 있다 — non-unique 세컨더리 인덱스의 대상 페이지가 버퍼 풀에 없을 때, 변경을 즉시 적용하지 않고 버퍼에 모아 두었다가 그 페이지가 나중에 읽힐 때 병합한다. 그래서 세컨더리 쪽의 랜덤 삽입은 "INSERT마다 디스크 읽기"로 직결되지 않는다.

클러스터드 삽입은 이 완충이 없다. 행 자체가 들어갈 자리를 지금 확정해야 하므로 대상 페이지를 반드시 읽어와야 한다. 그래서 랜덤 PK의 버퍼 풀 오염은 클러스터드에서 특별히 아프고, 같은 이유로 "PK만큼은 단조 증가"가 우선순위가 높다.

커버링이면 북마크 룩업이 사라지는데, 그럼 세컨더리 인덱스에 컬럼을 다 넣으면 되지 않나요? 추가

그 순간 §3의 사슬이 그대로 돌아온다. 컬럼을 넣을수록 세컨더리 엔트리가 비대해져 → 페이지당 엔트리↓ → 페이지 수↑ → 버퍼 풀 적재율↓. 그리고 인덱스에 포함된 컬럼이 UPDATE될 때마다 그 인덱스도 갱신 — 쓰기 비용이 컬럼 수에 비례해 는다.

커버링은 "이 쿼리가 자주, 그리고 필요한 컬럼이 몇 개 안 될 때"의 국소 최적화다. 원칙은 같다 — 인덱스는 조회를 위해 쓰기와 메모리를 파는 거래. 판단 축은 09 문서.

9. 1분 인출 테스트 — 면접 전날, 답을 가리고 소리 내어

  1. 클러스터드 리프와 세컨더리 리프에 각각 무엇이 들어있나?
    답 확인
    클러스터드: 행 전체. 세컨더리: 인덱스 컬럼 값 + PK 값. 그래서 세컨더리 → 클러스터드 재탐색 = 북마크 룩업.
  2. 세컨더리 리프에 물리 주소 대신 PK를 넣는 이유를 "거래"로 한 문장.
    답 확인
    페이지 분할로 행이 이동해도 PK는 불변이라 세컨더리를 안 고쳐도 된다 — 읽기 한 단계를 내주고 쓰기 증폭을 없앤 거래.
  3. PK 설계 2원칙과 각각의 근거 한 줄.
    답 확인
    ① 작게 — 모든 세컨더리 엔트리에 복제되는 곱셈 계수. ② 단조 증가 — 삽입 위치를 PK 값이 정하므로 랜덤이면 페이지 분할. "짧고 곧게".
  4. 등장인물 넷의 이름과 역할(공급·수요·사고·대가).
    답 확인
    버퍼 풀(공급, 고정 크기 캐시) · 워킹셋(수요, 실제로 손대는 페이지 집합) · 페이지 분할(사고) · 랜덤 I/O(대가).
  5. "메모리 부하" 대신 말할 사슬을 끊지 않고.
    답 확인
    PK 복제 → 엔트리 비대 → 16KB 페이지당 엔트리↓ → 페이지 수↑ → 버퍼 풀 적재율↓ → 캐시 미스↑ → 디스크 I/O↑.
  6. "왔다갔다" 대신 말할 쓰기 쪽 사슬.
    답 확인
    랜덤 PK → 삽입 지점 전역 분산 → 페이지 분할 → 단편화 + 새 페이지 디스크 멀리 → 모든 리프가 워킹셋 → 버퍼 풀 오염 → INSERT마다 디스크 읽기.
  7. PK 8B → 36B일 때 페이지당 엔트리, 페이지 수, 적재율 숫자 세 개.
    답 확인
    312 → 197개(63%) · 32,051 → 50,761장(1.58배) · 8GB 버퍼 풀 상주 엔트리 1.6억 → 1.0억(37%↓).
  8. 브랜치에 PK가 붙는 이유와, 세 경로의 무게 순위.
    답 확인
    non-unique 세컨더리에서 특정 행 하나를 특정하려면 분기 키가 유일해야 해서. 순위: ⑶ 리프 수=적재율 ≫ ⑵ 트리 높이 > ⑴ 브랜치 공간.
  9. INSERT 워킹셋 — AUTO_INCREMENT vs UUID v4, 숫자로.
    답 확인
    ≈ 80KB(맨 끝 리프 1~2장 + 브랜치 3장) vs ≈ 2GB(리프 전체). 약 25,000배.
  10. "규모 유추 방지로 UUID PK" 제안에 되물을 질문과 대안 셋.
    답 확인
    "필요한 건 유추 불가능이지 무작위 삽입 순서가 아니다 — 생성 시각까지 숨겨야 하나?" 대안: Snowflake · UUID v7(시간 정렬, 시각 노출) · 내부 BIGINT PK + 외부 public_id 분리.
  11. EXPLAIN에서 북마크 룩업이 있는지 판별하는 규칙 하나.
    답 확인
    key에 세컨더리 인덱스가 있는데 Extra에 Using index가 없으면 룩업 있음. TREE 포맷은 "Covering index lookup"이 붙는지로.
  12. PK가 없으면 InnoDB는? PostgreSQL은 왜 다른가?
    답 확인
    첫 NOT NULL UNIQUE 승격 → 없으면 6B 숨은 row id. PostgreSQL은 힙 테이블 + TID 직접 포인터라 조회 1단계 대신 행 이동 시 인덱스 갱신 비용(HOT로 완화) — 클러스터드는 InnoDB의 선택.
한 줄 요약
InnoDB에서 테이블은 PK 순으로 정렬된 클러스터드 B+Tree 그 자체이고, 세컨더리 인덱스는 리프에 PK를 논리 포인터로 품어 2단계(북마크 룩업)로 조회한다. 이 구조에서 PK 설계 2원칙이 도출된다 — ① 작게(PK는 모든 세컨더리에 복제되는 곱셈 계수 → 페이지당 엔트리↓ → 버퍼 풀 적재율↓ → 디스크 I/O↑), ② 단조 증가(랜덤 PK는 페이지 분할 → 단편화 + 버퍼 풀 오염). 비용은 뭉뚱그리지 말고 이 이름들의 사슬로 말한다.
