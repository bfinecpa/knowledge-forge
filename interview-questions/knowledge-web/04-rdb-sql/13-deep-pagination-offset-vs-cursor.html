깊은 페이지네이션
OFFSET은 "건너뛰기"가 아니라 "읽고 버리기"다

면접 질문: "LIMIT 100000, 20 같은 깊은 페이지네이션이 느린 이유와 해결책(no-offset, 커서 기반)은?"

핵심 관전 포인트 — LIMIT 20 OFFSET 100000이 느린 이유는 DB가 10만 건을 건너뛰는 게 아니라 100,020건을 전부 만들어 올린 뒤 Limit 노드가 앞의 10만 건을 세며 버리기 때문이다. B-tree에는 "앞에서 N번째"라는 좌표가 없어 세며 걷는 수밖에 없고, PostgreSQL은 테이블이 힙이라 정렬 인덱스가 PK든 아니든 버릴 행에도 인덱스 → TID → 힙 페치를 100,020번 지불한다 — MVCC 가시성 확인 때문에 "버릴 행인지"조차 힙을 봐야 알기 때문이다. 그래서 비용이 페이지 번호에 선형으로 비례한다. 해결책은 네 가지를 한 번에 꺼낸다: ① 커서(키셋) 기반 — "마지막으로 본 행의 정렬 키"를 다음 요청의 WHERE로 넘겨(WHERE (created_at, id) < ($1, $2)) 시작점을 인덱스 탐색 한 번으로 바꿔 offset 자체를 없앤다 ② 지연 조인 — (created_at, id) Index Only Scan으로 id 20개만 먼저 뽑아 힙 페치를 20회로 줄인다 ③ offset 상한을 API 레벨에서 강제한다(안전망) ④ 복잡한 검색은 검색 엔진에 위임한다. 그리고 커서가 포기하는 것 — 임의 페이지 점프 불가, 전체 페이지 수 표시 불가, 정렬 기준을 바꾸면 커서 무효, API 스펙 변경 — 을 한 호흡에 같이 말해야 완결된 답이다.
  • 1
    "느리다"를 메커니즘 이름으로 말한다 — read-and-discard — B-tree에 "N번째" 좌표가 없어서 Limit 노드가 세며 버린다. 스캔 노드는 버려질 행인지 알 길이 없으므로 온전히 만들어 올리고, PostgreSQL은 힙 테이블이라 가시성 확인을 위해 버릴 10만 건에도 힙을 찍는다. 그래서 일의 양 = offset + limit이고 결과 크기와 무관하다.
  • 2
    해결책은 네 개를 세트로, 각각에 대가를 붙여서 — 커서(근본) · 지연 조인(완화, API 무변경) · offset 상한(안전망) · 검색 엔진(구조 변경). 실무 조합은 ③은 항상 + ①이나 ② 중 하나다. 하나만 말하면 "그 방법을 못 쓰는 상황에서는요?"가 바로 따라온다.
  • 3
    커서 전환은 쿼리 하나가 아니라 조직적 결정이다 — page/size가 cursor/size로 바뀌고 페이지 번호 UI와 전체 건수 표시가 사라진다. 그래서 판단 기준은 "커서가 더 빠르다"가 아니라 "이 화면의 접근 패턴이 순차 탐색인가 임의 접근인가"다.

0. 질문 + 출제 의도

질문: "LIMIT 100000, 20 같은 깊은 페이지네이션이 느린 이유와 해결책(no-offset, 커서 기반)은?"

PostgreSQL 기준 재해석: LIMIT offset, count는 MySQL 문법이고 PostgreSQL은 LIMIT count OFFSET offset이다. 문법만 다를 뿐 offset의 비용 구조는 같다.

출제 의도: 관리자 페이지나 크롤러가 유발하는 고전적 부하 패턴. offset의 비용 구조를 알아야 커서 기반으로 재설계할 수 있고, 이는 API 스펙 변경까지 수반하므로 미리 아는 것의 가치가 크다.

채점 지점 셋 ⑴ "느리다"를 메커니즘으로 설명하는가 — 왜 skip이 아니라 read-and-discard인가. 실행 계획의 Limit 노드와 그 아래 스캔 노드의 actual rows 차이로 증명할 수 있는가.
⑵ 해결책을 목록으로 꺼내고 각각의 대가를 붙이는가.
⑶ 커서 전환이 DB 쿼리 하나가 아니라 API 스펙·클라이언트·UI까지 바꾸는 조직적 결정임을 내다보는가.
옆 문항과의 경계 — 같은 증상, 다른 계층 컬렉션 fetch join + 페이징(03-jpa-orm/08)은 Hibernate가 limit을 SQL에서 빼 버리고 힙(JVM 메모리)에서 자르는 JPA 계층 문제다. 이 문항은 LIMIT/OFFSET이 SQL에 정상적으로 붙었는데도 DB가 offset만큼 읽고 버리는 DB 계층 문제다. 둘 다 "페이징이 느리다"로 보고되지만 원인 계층이 다르다.

1. 오해 걷어내기 — OFFSET은 skip이 아니라 read-and-discard다

OFFSET 100000이라고 쓰면 DB가 어딘가로 순간이동한 다음 20건을 준다고 상상하기 쉽다. 이 문항의 전부는 그 상상이 틀렸다는 것이고, 왜 틀렸는지는 인덱스 구조에서 나온다.

1-1. 책에는 쪽번호가 인쇄돼 있지만, B-tree에는 없다

1-2. 세는 주체는 Limit 노드다 — 스캔 노드는 "버릴 행"을 알지 못한다

PostgreSQL 실행기는 계획 트리를 위에서 아래로 "다음 튜플 줘"라고 당기는(pull) 파이프라인이고, OFFSET과 LIMIT은 트리 맨 위의 Limit 노드가 처리한다. 아래 스캔 노드는 조건에 맞는 행을 한 건씩 위로 올리고, Limit 노드가 카운터를 세며 offset에 못 미친 행을 버린다.

2. 사슬 — PostgreSQL은 버릴 행에도 힙을 100,020번 찍는다

PostgreSQL에는 클러스터드 인덱스가 없다. 테이블은 힙(heap)이고 PK를 포함한 모든 인덱스가 리프에 TID(힙 페이지 번호 + 슬롯)를 담아 힙을 가리키는 구조다. 그래서 정렬 기준이 PK든 created_at이든 score든 사슬의 모양은 하나뿐이다.

전제 idx_posts_created_at (created_at) 존재. posts에는 title, body 등 컬럼이 많다
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
①
플래너가 정렬(Sort)을 피하려고 idx_posts_created_at을 역방향으로 읽는 계획(Index Scan Backward)을 고른다 — PostgreSQL은 B-tree를 거꾸로 읽을 수 있어 DESC 전용 인덱스가 따로 필요 없다.
②
리프 끝에서 엔트리 하나를 읽는다 — 리프에는 (created_at, TID)만 있다.
③
TID가 가리키는 힙 페이지를 읽어 가시성을 확인하고, SELECT *라 나머지 컬럼을 그 튜플에서 가져온다(힙 페치) — 이 페이지들이 인덱스 순서와 무관하게 흩어져 있으면 랜덤 I/O.
④
온전한 행을 Limit 노드로 올린다 → Limit: "아직 100,000 미만" → 버린다.
⑤
②~④를 100,000번 반복 — 버릴 행에도 ③의 힙 페치를 전부 지불한다.
⑥
100,001번째부터 20건만 결과에 담아 반환하고 스캔을 멈춘다.

면접에서 그대로 말하는 한 문장

"PostgreSQL은 힙 테이블이라 어떤 인덱스로 정렬하든 리프에는 TID뿐이고,
버릴 10만 건에 대해서도 가시성 확인과 컬럼 조립을 위해 힙을 10만 번 찍고 나서 버립니다."

합계: 인덱스 엔트리 100,020건 + 힙 페치 100,020회 + 그중 shared_buffers(그리고 OS 페이지 캐시)에 없는 페이지만큼의 디스크 읽기. 결과는 20건이다.

2-1. "PK 순이면 덜 나쁘다"의 PostgreSQL 판 — 클러스터링이 아니라 상관관계

PostgreSQL의 PK는 유니크 B-tree일 뿐이라 PK 순에도 힙 페치는 그대로 붙는다. 그래도 PK 순(또는 삽입 순인 created_at 순)이 score 순보다 덜 나쁜 것은 사실인데, 이유가 클러스터링이 아니라 힙의 물리 순서와 인덱스 순서가 얼마나 일치하는가다.

상관관계 높음 — created_at·id 순

연속된 엔트리가 같은 힙 페이지를 가리켜 힙 페치가 사실상 순차 읽기가 된다. 이 일치도를 PostgreSQL은 pg_stats.correlation 통계로 들고 있다(1에 가까울수록 일치). 플래너도 이 값을 인덱스 스캔 비용에 반영한다.

상관관계 낮음 — score 순

엔트리마다 다른 페이지를 찍어 랜덤 I/O 100,020회에 가까워진다.

어느 쪽이든 읽는 양 자체는 여전히 offset에 선형이다 — 랜덤 I/O 항이 줄었을 뿐이다
플래너가 아예 다른 길을 고르기도 한다 — Seq Scan + Sort 시니어 변별 상관관계가 낮고 offset이 크면 "흩어진 힙 페치 10만 번보다 테이블을 통째로 읽고 정렬하는 게 싸다"고 판단해 Seq Scan + Sort로 간다. 이때 Sort는 상위 N건만 유지하는 top-N heapsort인데 N은 20이 아니라 offset + limit = 100,020이라, 그 양이 work_mem을 넘으면 external merge Disk:로 내려간다. 어느 길이든 비용이 offset 또는 테이블 크기에 비례하고, 결과 20건과는 무관하다.

2-2. 갈래 둘 — "정렬 컬럼에 인덱스가 없다" / "커버링이면 괜찮나"

정렬 컬럼에 인덱스가 없을 때

풀스캔 → 조건에 맞는 전체를 정렬(Sort, N = 100,020인 top-N heapsort, work_mem 초과 시 디스크 임시 파일) → 앞 10만 건 버림.

이건 offset이 없어도 이미 비싼 쿼리이고 offset은 그 위에 얹힌 것뿐이다. 1차 처방은 페이지네이션 기법이 아니라 정렬 컬럼 인덱스 — 그다음에야 해결책 4종이 의미 있다.

커버링(Index Only Scan)이어도 남는 비용

① 엔트리 100,020건을 순회하는 비용 — 힙을 안 봐도 세며 걷는 일은 그대로다.
② 가시성 확인 — 힙 대신 visibility map(페이지 단위로 "이 페이지는 전부 가시"를 표시한 비트맵)을 보는데, VACUUM이 못 따라온 테이블이면 그 비트가 꺼져 있어 결국 힙을 찍는다(계획의 Heap Fetches: N).

커버링은 offset 비용의 상수를 줄이지 차수를 바꾸지 못한다 — 지연 조인(§8)의 한계가 여기서 나온다.

2-3. 덤으로 따라오는 비용 — 페이지 번호 UI의 count(*)

"전체 3,204페이지 중 5,001페이지"를 그리려면 매 요청마다 조건에 맞는 전체 건수를 세야 한다. PostgreSQL의 count(*)는 MVCC 때문에 미리 들고 있을 수 없어(누구에게 몇 건인지가 스냅샷마다 다르다) 가시성 확인을 위해 전부 훑는 쿼리이고, 목록 본체보다 비싼 경우가 많다.

offset 페이지네이션은 보통 count와 세트로 와서 비용이 두 벌로 든다

3. 실행 계획으로 증명하기 — EXPLAIN (ANALYZE, BUFFERS) 한 장

이 문항의 "느린 이유"는 실행 계획 한 장으로 닫힌다. 말로 설명하는 사람과 증거를 대는 사람의 차이가 여기서 갈린다.

before 깊은 offset — 수치는 예시
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM posts ORDER BY created_at DESC LIMIT 20 OFFSET 100000;

 Limit  (cost=4183.20..4184.04 rows=20 width=412)
        (actual time=318.6..318.7 rows=20 loops=1)          ← 반환은 20건
   Buffers: shared hit=71204 read=29311                     ← 읽은 페이지는 합쳐 100,515장
   ->  Index Scan Backward using idx_posts_created_at on posts
         (actual time=0.05..311.9 rows=100020 loops=1)      ← 실제로 100,020건 올렸다
 Execution Time: 318.8 ms
actual rows 격차
Limit의 20 대 그 아래 스캔 노드의 100020. 이 격차가 "버릴 행도 전부 만들어서 올렸다"는 직접 증거다.
Buffers
shared hit(캐시에서 찾음) + shared read(디스크에서 읽음) = 100,515장 — 반환 행 20건이 아니라 읽은 행 수 규모로 잡힌다. shared read가 크면 캐시에도 없어 디스크까지 갔다는 뜻.
Limit의 시작 비용 ≠ 0
cost=4183.20..4184.04 — 앞의 숫자가 시작 비용이다. 플래너가 offset만큼 먼저 걷는 비용을 셈에 넣고 있다는 표시.

흔한 오해 둘 — 여기서 잘못 짚으면 "계획을 읽을 줄 모른다"가 드러난다

오해 ①: "rows=20(추정)과 actual rows=20(실제)이 같으니 문제없다."
이 둘의 차이는 플래너 추정이 맞았는지를 보는 지표이지 offset 낭비의 증거가 아니다. 봐야 할 것은 같은 노드의 추정 대 실제가 아니라 위아래 노드의 실제 대 실제다.

오해 ②: "버린 행은 Rows Removed by Filter에 잡히겠지."
PostgreSQL은 offset으로 버린 행을 별도 카운터로 세어 주지 않는다. 그 카운터는 필터·조인 조건·인덱스 재검사에서 탈락한 행에만 붙는다. offset이 버린 일은 actual rows 격차와 Buffers로만 드러난다.

3-1. 말하기 훈련 — 뭉뚱그린 표현을 이름 붙은 사슬로 교체

뭉뚱그린 표현이름사슬로 말하면
"offset이 크면 느리다"read-and-discardB-tree에 N번째 좌표 없음 → Limit 노드가 세며 버림 → 일의 양 = offset + limit → 페이지 번호에 선형
"DB가 많이 읽는다"힙 페치 × offset모든 인덱스 리프엔 TID뿐 → 버릴 행마다 힙 페이지를 읽어 가시성 확인 + 컬럼 조립 → 상관관계 낮으면 랜덤 I/O 100,020회
"메모리에 부담"shared_buffers 미스깊은 페이지 = 오래된 데이터 = 캐시에 없음 → Buffers: shared read 증가 → 디스크 랜덤 I/O로 전락
MySQL 대조 — 구조는 같고 갈리는 지점은 "정렬 인덱스 종류" MySQL은 LIMIT/OFFSET을 InnoDB 위의 SQL 서버 계층이 세고 엔진은 행을 조립해 올린다 — "버릴 행도 온전히 만든다"는 구조는 같다. 다른 점은 정렬 인덱스 종류로 사슬이 갈린다는 것 — PK(클러스터드) 순이면 리프에 행 자체가 있어 북마크 룩업 없이 순차 읽기, 세컨더리 순이면 PK로 클러스터드를 다시 찾는 북마크 룩업 × 100,020. PostgreSQL은 힙 구조라 항상 힙 페치이고 상관관계가 무게를 정한다. 계획 표기는 EXPLAIN의 rows가 10만 단위, 정렬을 못 피하면 Extra: Using filesort다.

5. 커서(키셋) 기반 — "몇 번째부터"를 "이 값 다음부터"로

용어 충돌 주의 — DECLARE ... CURSOR(서버 커서)와 다른 것이다 서버 커서는 트랜잭션 안에서만 살며 커넥션과 트랜잭션을 점유하므로, 요청 사이에 상태를 못 드는 HTTP 페이지네이션에는 맞지 않는다 — 롱 트랜잭션의 해악을 API가 스스로 만드는 꼴이고 PgBouncer 트랜잭션 풀링 뒤에서는 유지되지도 않는다. 여기서 말하는 키셋 커서는 "마지막으로 본 값"이라는 데이터를 클라이언트가 들고 오는 무상태 방식이다.

정의부터 고정한다. 커서(키셋) 페이지네이션이란 "마지막으로 본 행의 정렬 키 값"을 클라이언트가 들고 있다가 다음 요청의 WHERE 조건으로 넘기는 방식이다. "몇 번째부터 주세요"가 아니라 "이 값 다음부터 주세요"로 요청의 언어가 바뀐다.

왜 이게 빨라지는지는 §1의 뒤집기다. B-tree는 "N번째"는 못 찾지만 "값이 X보다 작은 첫 지점"은 로그 시간에 찾는다. 그러니 지난 페이지의 마지막 값을 조건으로 주면 시작점 탐색이 O(offset)에서 트리 높이 한 번(인덱스 탐색 1회)으로 바뀌고, 거기서부터 인덱스를 이어 읽으며 20건만 가져온다. 읽는 양은 페이지가 아무리 깊어도 항상 limit + 1건이다.

before 5,001페이지 — 100,020건 읽고 100,000건 버림
SELECT * FROM posts
ORDER BY id DESC
LIMIT 20 OFFSET 100000;

-- Limit 노드가 앞의 10만 건을
--   세며 버린다 (read-and-discard)
after "마지막으로 본 id 다음부터 20건" — 인덱스 탐색 1회 + 20건
SELECT * FROM posts
WHERE id < $1          -- 지난 페이지 마지막 행의 id
ORDER BY id DESC
LIMIT 20;

-- 시작점 탐색이 범위 조건 하나로
--   바뀐다 → offset이 사라진다

6. 커서의 급소 — tie-breaker와 행 비교

앞의 예시는 정렬 키가 id라 문제가 없었다. PK는 유일하니까. 그런데 실제 목록은 created_at DESC처럼 유일하지 않은 컬럼으로 정렬한다. 같은 초에 글이 세 개 올라올 수 있다.

말로만 하면 안 와닿으니 데이터를 놓고 본다. posts에 다섯 건이 있고 created_at DESC, id DESC 순으로 정렬한다. 페이지 크기 3으로 1페이지를 받으면 105, 104, 103이고 마지막으로 본 행은 (10:00:02, 103)다. 이제 2페이지를 요청한다. 정답은 102, 101이다.

행 비교(row comparison) — (a, b) < (x, y)

값 여러 개를 튜플로 묶어 사전순으로 비교하는 SQL 표준 문법이다. 뜻은 "a가 x보다 작거나, a가 같으면서 b가 y보다 작은 것".

PostgreSQL은 이 형태를 표준 의미 그대로 지원하면서 B-tree 범위 탐색 하나로 실행한다
— 이 문항의 PostgreSQL 가산점 포인트
after 인덱스는 반드시 복합으로, 조건은 행 비교로
-- PostgreSQL의 인덱스 리프에는 TID만 있어서 (created_at) 단독 인덱스 안에서
--   같은 시각의 엔트리는 id 순이 아니다 — 명시하지 않으면 tie-breaker 정렬이 인덱스에 없다.
CREATE INDEX idx_posts_created_at_id ON posts (created_at, id);

SELECT * FROM posts
WHERE (created_at, id) < ($1, $2)          -- (마지막 created_at, 마지막 id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
증거 계획에 ROW(...) < ROW(...)가 Index Cond로 찍히면 성공 — 수치는 예시
 Limit  (actual time=0.06..0.14 rows=20 loops=1)
   Buffers: shared hit=24                          ← 5,001페이지든 1페이지든 이 수준
   ->  Index Scan Backward using idx_posts_created_at_id on posts
         Index Cond: (ROW(created_at, id) < ROW('2026-08-30 12:34:56+09'::timestamptz, '102034'::bigint))
         (actual rows=20 loops=1)                  ← 읽은 것도 20건

이 표기가 뜻하는 것 — 플래너가 행 비교를 "이 지점보다 작은 첫 엔트리로 점프한 뒤 거기서 역방향으로 20개"라는 범위 조건 하나로 번역했다는 뜻이다. Limit 아래 actual rows가 20이고 Buffers가 수십 장에서 멈춘 것이 §3의 before 계획과 대비되는 증거다.

6-1. 맞춰야 하는 네 가지 — 하나라도 어긋나면 인덱스를 놓치거나 행이 샌다

① 부등호 방향 = 정렬 방향
"created_at이 더 이르거나, 같은 시각이면 id가 더 작은 것" — 정렬(둘 다 DESC)과 부등호(<)가 반드시 일치해야 한다. ASC 정렬이면 >로 뒤집는다.
② 인덱스 방향 — 섞지 않는다
PostgreSQL은 B-tree를 역방향으로도 읽으므로 (created_at, id) 하나로 ASC, ASC도 DESC, DESC도 처리된다. 방향이 섞이면(created_at DESC, id ASC) 행 비교 한 줄로 표현이 안 되고 인덱스도 컬럼별 방향을 줘야 한다 — 굳이 섞을 이유가 없으면 통일한다.
③ 정렬 키는 NOT NULL
NULL과의 비교 결과는 참도 거짓도 아닌 UNKNOWN이라 그 행이 커서 조건에서 조용히 빠진다. PostgreSQL 기본은 ASC가 NULLS LAST, DESC가 NULLS FIRST라, nullable 컬럼을 굳이 쓰겠다면 인덱스와 ORDER BY 양쪽의 NULLS 옵션을 맞추고 NULL 구간을 따로 처리해야 한다.
④ 등호 필터가 앞에 있으면 인덱스도 그 순서
WHERE board_id = $1로 걸러지는 목록이면 인덱스는 (board_id, created_at, id), 조건은 board_id = $1 AND (created_at, id) < ($2, $3) — 등호 구간 안에서 행 비교가 범위 하나로 잡힌다.
MySQL 대조 — 같은 문법, 다른 최적화 시니어 변별 MySQL도 (a, b) < (x, y) 문법 자체는 받지만 인덱스 범위로 최적화하지 못해 풀어 쓴 created_at < ? OR (created_at = ? AND id < ?)를 쓴다. 반대로 PostgreSQL에서 이 OR 형태를 그대로 쓰면 플래너가 "결국 created_at <= ? 범위 하나"임을 스스로 추론하지 못해 BitmapOr + Sort로 커서 이전 행을 다 읽거나, 역방향 스캔 + Filter로 이미 본 행을 다 지나가기 쉽다. JPQL처럼 행 비교를 못 쓰는 자리라면 created_at <= $1 상한을 중복으로 덧붙여 범위를 준다(§9-5). 또 하나 — MySQL 세컨더리 인덱스는 리프에 PK를 품어 (created_at) 단독으로도 사실상 (created_at, PK) 순이지만, PostgreSQL은 리프가 TID라 복합 인덱스를 반드시 명시해야 한다.
가산점 — 커서 쿼리마저 Index Only Scan으로 목록 API가 몇 컬럼만 돌려준다면 (created_at, id) INCLUDE (title)로 비키 컬럼을 리프에 얹어 커서 쿼리를 Index Only Scan으로 만들 수 있다 — 20건의 힙 페치마저 사라진다. 대가는 인덱스 크기와 title 갱신 시의 HOT 업데이트 탈락이다.

6-2. 커서는 불투명(opaque) 토큰으로 넘긴다

클라이언트에 created_at과 id를 따로 노출하면 두 가지가 생긴다. ⑴ 클라이언트가 값을 마음대로 조작해 호출하기 시작하고 ⑵ 나중에 정렬 키를 바꾸려 할 때 이미 공개된 파라미터라 바꿀 수 없다.

그래서 두 값을 하나로 직렬화해 Base64 같은 불투명 토큰으로 주고받는다. "이 문자열을 다음 요청에 그대로 돌려주세요"가 계약이 되면, 안에 무엇이 들었는지는 서버만의 사정으로 남는다.

{
  "items": [ ... 20건 ... ],
  "nextCursor": "MjAyNi0wOC0zMFQwMzozNDo1Nlp8MTAyMDM0",
  "hasNext": true
}

7. 커서가 포기하는 것 — 얻는 것과 잃는 것을 한 호흡에

커서는 공짜로 빨라지는 기법이 아니다. 읽기 순서를 순차 탐색으로 제한하는 대가로 상수 비용을 사는 거래다. 그래서 잃는 것이 분명하다.

얻는 것지불하는 것
깊이와 무관한 상수 비용임의 페이지 점프 불가 — "3,204페이지로" 못 간다
스크롤 중 삽입·삭제에도 중복/누락 없음정렬 키 유일성 필요 — tie-breaker와 복합 인덱스 설계
count 쿼리 불필요(Slice)전체 페이지 수 표시 불가 — 페이지 번호 UI 자체가 성립 안 함
—정렬 축마다 커서 설계 — 정렬 기준을 바꾸면 기존 커서가 무효
—API 스펙 변경 — 클라이언트 전부 수정, 구·신 API 병행 기간

인출 장치 — 커서가 내주는 것 점 · 수 · 정 · 약

점 = 임의 페이지 점프· 수 = 전체 페이지 수· 정 = 정렬 유연성· 약 = API 약속(스펙 호환)

"커서로 바꾸면 무엇을 잃습니까?"는 거의 반드시 따라오는 꼬리질문이다. 네 글자를 먼저 던지고 하나씩 풀면 목록 인출이 무너지지 않는다.

점
임의 페이지 점프 불가 — 커서는 "직전 페이지의 끝"만 안다. 5페이지에서 갑자기 100페이지로 가려면 그 사이를 다 읽어야 하므로 사실상 못 간다. 그래서 커서는 무한 스크롤·"더 보기"·타임라인과 짝이고, 페이지 번호 UI를 기획이 고수하면 ②지연 조인 + ③상한으로 가야 한다.
키
정렬 키 유일성 + 불변성 — tie-breaker가 필수이고, 한 가지 조건이 더 붙는다: 정렬 키는 불변이어야 한다. updated_at DESC 정렬에 커서를 쓰면 스크롤 도중 갱신된 행이 목록 위로 튀어 올라 위치가 바뀌고, 중복/누락이 다시 생긴다.
수
전체 페이지 수 표시 불가 — "전체 12,345건 / 618페이지"가 사라진다. 대개 이건 손실이 아니라 count 비용까지 함께 던져 버리는 이득이지만, 화면에서 숫자가 사라지는 일이므로 기획과 합의가 필요한 요구사항 변경이다.
정
정렬 축마다 커서 — 정렬 기준이 바뀌면 커서의 구성 값도, 인덱스도 바뀐다. 사용자가 목록 중간에 정렬을 바꾸면 들고 있던 커서는 그냥 무효라 첫 페이지부터 다시 시작해야 한다. 관리자 그리드처럼 컬럼 헤더를 눌러 정렬을 계속 바꾸는 화면에는 커서가 맞지 않는다 — 그건 ④검색 엔진의 영역이다.
약
API 스펙 변경 — page/size가 cursor/size로 바뀌고 응답 구조도 바뀐다. 모바일 앱처럼 구버전이 오래 남는 클라이언트가 있으면 구 API에는 ③상한을 걸고, 신 API를 병행 운영하다 폐기하는 마이그레이션 계획이 필요하다. 출제 의도가 "미리 아는 것의 가치가 크다"고 한 이유가 바로 이 비용이다 — 처음부터 커서로 설계했으면 안 냈을 값이다.
가산점 — "이전 페이지"는 뒤집어서 만든다 조건과 정렬을 반대로 뒤집어 조회한 뒤 결과 리스트를 다시 뒤집어 돌려준다 — WHERE (created_at, id) > ($1, $2) ORDER BY created_at ASC, id ASC LIMIT 20 후 reverse. 같은 (created_at, id) 인덱스를 정방향 Index Scan으로 읽을 뿐이라 인덱스를 더 만들 필요가 없다. 양방향이 필요하면 prevCursor도 함께 내려준다. 같은 뒤집기가 §9의 "마지막 페이지" 버튼 처방으로 그대로 쓰인다.

8. 나머지 셋 — 지연 조인 · offset 상한 · 검색 엔진

8-1. 지연 조인(deferred join) — offset은 두고 "버릴 행의 힙 페치"만 없앤다

페이지 번호 UI를 당장 못 버리거나 API를 바꿀 수 없을 때의 처방이다. 발상은 이렇다 — 어차피 버릴 100,000건에 대해 힙을 찍어 행 전체를 조립하는 게 낭비이니, 먼저 인덱스만 훑어 id 20개를 고르고, 그 20개에 대해서만 본 테이블을 읽는다.

비유 — 도서관 서가 before는 "300번째 책부터 20권을 달라"는 말에 사서가 서가를 처음부터 돌며 책을 한 권씩 실제로 꺼내 들고 와서 세다가 앞의 300권을 도로 꽂는 것이다. after는 목록 카드(인덱스)만 넘겨 청구기호 20개를 뽑고, 서가에는 딱 20번만 다녀오는 것이다. 세는 일은 그대로지만, 무거운 왕복이 100,020번에서 20번으로 줄었다.
before 힙 페치 100,020회 → 100,000건 버림
SELECT * FROM posts
ORDER BY created_at DESC
LIMIT 20 OFFSET 100000;
after 서브쿼리는 인덱스만으로 끝난다 — 힙 페치는 바깥 조인의 20회뿐
SELECT p.*
FROM posts p
JOIN (
    SELECT id                    -- id만! → Index Only Scan
    FROM posts
    ORDER BY created_at DESC
    LIMIT 20 OFFSET 100000   -- offset은 그대로
) AS page USING (id)
ORDER BY p.created_at DESC;   -- 조인 결과 순서는 보장 안 됨 → 20건 재정렬

장점 — 오늘 밤 배포할 수 있다

API도 UI도 바꾸지 않는다. 그래서 지연 조인은 "커서로 가는 마이그레이션 기간의 다리"로 쓰이는 경우가 많다.

대가 — 여전히 O(offset)이다

인덱스 스캔이 싸다는 것이지 공짜는 아니라서 페이지가 수만 단위로 깊어지면 다시 느려진다. 그리고 PostgreSQL 고유 조건 하나 — Index Only Scan이 힙을 건너뛰는 것은 visibility map이 신선할 때뿐이라 VACUUM이 밀린 테이블이면 Heap Fetches가 튀어 before와 비슷해진다.

MySQL 대조 지연 조인은 MySQL 쪽에서 유명해진 기법이다 — 세컨더리 리프에 PK가 있어 (created_at) 단독 인덱스로도 서브쿼리가 커버링(Using index)이 되고, 북마크 룩업을 바깥 PK 조인의 20회로 줄인다. PostgreSQL은 복합 인덱스를 명시해야 커버링이 성립하고, 성립해도 VM 상태에 좌우된다.

8-2. offset 상한 — 사람의 기억에 의존하지 않는 위치에 둔다

"5,001페이지를 누가 보겠어"는 사실이지만, 사람은 안 봐도 크롤러와 관리자 화면의 '마지막 페이지' 버튼은 본다.

상한은 업계 관행이다 — 구글 검색도 일정 페이지 이상은 결과를 넘겨주지 않고, Elasticsearch는 from + size가 index.max_result_window(기본 10,000)를 넘으면 요청 자체를 거절한다. RDB 위의 API도 같은 선을 그어야 한다.

핵심은 어디에 두느냐다. 컨트롤러마다 if (page > 500) throw를 쓰면 다음 사람이 새 목록 API를 만들 때 빠뜨린다. 사람의 기억에 의존하지 않는 위치 — 모든 목록 요청이 지나가는 한 곳 — 에 둔다.

@Component
public class DeepOffsetGuardInterceptor implements HandlerInterceptor {

    static final long MAX_OFFSET = 10_000;   // 팀 합의값. 넘는 요청은 커서 API로 보낸다
    static final int  MAX_SIZE   = 100;

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        int page = parseOrDefault(req.getParameter("page"), 0);
        int size = parseOrDefault(req.getParameter("size"), 20);
        if (size > MAX_SIZE || (long) page * size > MAX_OFFSET) {
            // → @ControllerAdvice에서 400으로 변환.
            //   메시지에 "cursor 파라미터를 사용하세요"를 담아 대체 경로를 안내한다.
            throw new DeepPaginationException(page, size, MAX_OFFSET, MAX_SIZE);
        }
        return true;
    }

    private static int parseOrDefault(String raw, int def) {
        try { return raw == null ? def : Integer.parseInt(raw); }
        catch (NumberFormatException e) { return def; }   // 파싱 실패는 바인딩 단계가 400으로 처리
    }
}

    }
}

8-3. 검색 엔진/전용 저장소 위임 — RDB의 일이 아닐 때

조건이 다음 세 가지를 동시에 요구하면 RDB 페이지네이션 기법으로는 한계가 있다 — 다중 필터 조합 + 사용자가 고르는 정렬 축 + 깊은 탐색. 관리자 검색 그리드, 상품 검색이 전형이다.

이럴 때는 Elasticsearch 같은 검색 엔진에 색인하고 search_after(키셋의 검색 엔진판)로 넘긴다. 검색 엔진조차 깊은 from + size는 기본적으로 거절한다는 사실이 "offset은 어디서나 비싸다"의 증거다.

대가 — 목록 하나 빠르게 하려고 도입할 도구가 아니다 색인 동기화 지연(RDB 쓰기와 검색 결과 사이의 최종 일관성) · 운영 컴포넌트 추가(클러스터, 매핑 관리, 재색인) · 이중 저장. 검색 요구사항이 이미 그 방향을 가리킬 때 선택한다.

9-2. 요구와의 충돌 — "마지막 페이지" 버튼은 커서로 만들 수 없다

여기가 §7에서 말한 대가가 실제로 부딪히는 지점이다. 커서 페이지네이션은 직전 페이지의 끝만 안다. 그래서 관리자 화면의 세 가지 요구와 정면으로 충돌한다.

관리자 화면의 요구커서로 되는가이유
"전체 12,345건 / 618페이지" 표시불가전체 건수를 세지 않는 것이 커서의 이득이었다(§2-3)
페이지 번호를 눌러 임의 이동불가"N번째"라는 좌표가 커서에는 없다
"마지막 페이지 »"우회 가능정렬을 뒤집으면 "마지막"이 "첫 페이지"가 된다

세 번째가 실무의 실마리다. 기획이 원한 것은 "5,001페이지를 보고 싶다"가 아니라 "가장 오래된 주문 20건을 보고 싶다"였다. 그렇다면 정렬을 뒤집어 첫 페이지처럼 처리하면 된다.

9-4. 배치의 전수 순회 — 같은 함정, 다른 옷

"모든 주문을 순회하며 정산 파일을 만드는" 배치가 PageRequest.of(page++, 1000)으로 돌면, 뒤로 갈수록 한 페이지가 느려진다. 매 페이지가 자기 offset만큼 읽으므로 총 읽은 행 수는 1,000 + 2,000 + 3,000 + ...이 되어 실행 시간이 페이지 수의 제곱에 비례한다.

처방은 동일하게 키셋이다 — 마지막 id를 들고 WHERE id > $1 ORDER BY id LIMIT 1000을 반복한다
가산점 — 리더 선택이 곧 이 문항의 적용이다 Spring Batch의 JpaPagingItemReader는 내부적으로 offset 페이징(setFirstResult)이라 같은 문제를 안고 있고, JdbcPagingItemReader는 sortKeys를 기준으로 "마지막 키 다음부터"를 조회하는 키셋 방식이다. 그리고 배치처럼 한 트랜잭션 안에서 한 번에 끝까지 읽는 경우라면 HTTP와 달리 서버 커서도 정당하다 — pgjdbc는 autocommit = false + fetchSize > 0이면 서버 커서로 나눠 받는다(JdbcCursorItemReader). 대신 §5에서 말한 트랜잭션 점유 비용을 낸다.

@Repository
@RequiredArgsConstructor
public class PostQueryRepository {
    private final JPAQueryFactory queryFactory;

    public Slice<Post> findSlice(Long boardId, PostCursor cursor, int size) {
        List<Post> rows = queryFactory
                .selectFrom(post)
                .where(post.board.id.eq(boardId),
                       afterCursor(cursor))                  // 첫 페이지면 null → 무시
                .orderBy(post.createdAt.desc(), post.id.desc())
                .limit(size + 1L)                             // 다음 페이지 유무 판정용 +1
                .fetch();

        boolean hasNext = rows.size() > size;
        if (hasNext) rows.remove(size);                       // 판정용 1건은 응답에서 제거
        return new SliceImpl<>(rows, PageRequest.of(0, size), hasNext);
    }

    // 정렬 (createdAt DESC, id DESC)과 부등호 방향을 반드시 맞춘다
    private BooleanExpression afterCursor(PostCursor c) {
        if (c == null) return null;
        return post.createdAt.loe(c.createdAt())              // 플래너용 범위 상한 (중복 조건)
                .and(post.createdAt.lt(c.createdAt())
                     .or(post.createdAt.eq(c.createdAt()).and(post.id.lt(c.id()))));
    }
}

// 커서 값 객체 — 클라이언트에는 불투명 토큰으로만 노출
public record PostCursor(Instant createdAt, Long id) {

    public String encode() {
        String raw = createdAt + "|" + id;                    // ISO-8601 UTC 문자열 | id
        return Base64.getUrlEncoder().withoutPadding().encodeToString(raw.getBytes(UTF_8));
    }

    public static PostCursor decode(String token) {
        String[] parts = new String(Base64.getUrlDecoder().decode(token), UTF_8).split("\\|");
        return new PostCursor(Instant.parse(parts[0]), Long.parseLong(parts[1]));
    }

    public static PostCursor from(Post last) {
        return new PostCursor(last.getCreatedAt(), last.getId());
    }
}

// 응답 조립 — 마지막 행에서 다음 커서를 만든다
public PostListResponse list(Long boardId, String cursorToken, int size) {
    PostCursor cursor = cursorToken == null ? null : PostCursor.decode(cursorToken);
    Slice<Post> slice = postQueryRepository.findSlice(boardId, cursor, size);
    String next = slice.hasNext()
            ? PostCursor.from(slice.getContent().get(slice.getNumberOfElements() - 1)).encode()
            : null;
    return new PostListResponse(toDtos(slice.getContent()), next, slice.hasNext());
}

10-1. 꼬리질문 셀프 테스트 — 먼저 스스로 답한 뒤 펼친다

"느리다"를 메커니즘으로 설명해 보세요. 왜 skip이 아니라 read-and-discard입니까? 필수힌트: 세는 주체가 누구인지 + 스캔 노드가 무엇을 모르는지

B-tree에 "앞에서 N번째"라는 좌표가 없기 때문이다. 인덱스는 "값이 X인 곳"은 트리 높이만큼(로그 시간)에 찾지만, 노드가 자기 아래 서브트리의 행 수를 세어 두지 않아 순번으로는 못 간다. 그리고 MVCC 때문에 세어 둘 수도 없다 — "N번째"는 보는 트랜잭션마다 다른 값이라 인덱스에 저장할 수 있는 성질이 아니다.

세는 주체는 계획 트리 맨 위의 Limit 노드다. 실행기는 위에서 아래로 "다음 튜플 줘"라고 당기는 파이프라인이고, 아래 스캔 노드는 그 행이 "결국 버려질 행"인지 알 길이 없으므로 온전히 만들어서 올린다. 그래서 일의 양 = offset + limit이고 결과 크기와 무관하다.

PostgreSQL에서 한 겹 더 — 인덱스 엔트리에는 버전 정보가 없어서 어떤 엔트리가 내 스냅샷에 보이는지는 힙의 튜플 헤더를 봐야만 안다. 즉 "카운터에 넣을지 말지"를 정하는 것 자체가 힙 페치를 요구한다 — 버릴 행조차 공짜로 버릴 수 없다.

정렬이 PK 순이면 LIMIT 20 OFFSET 100000도 괜찮은 거 아닌가요? 함정힌트: "덜 나쁘다"의 이유가 InnoDB와 다르다

"덜 나쁠 수 있다"이지 "괜찮다"가 아니다 — 그리고 PostgreSQL에서는 덜 나쁜 이유가 InnoDB와 다르다.

PostgreSQL의 PK는 클러스터드가 아니라 유니크 B-tree라 PK 순에도 힙 페치가 100,020번 붙는다. 덜 나쁜 것은 id가 삽입 순이라 힙의 물리 순서와의 상관관계(pg_stats.correlation)가 높아 힙 페치가 순차 읽기에 가까워지기 때문일 뿐이다.

Limit 노드가 100,000건을 세며 버리는 read-and-discard는 그대로이고, 깊은 페이지의 오래된 데이터는 shared_buffers에 없을 확률이 높아 디스크 읽기가 된다. 랜덤 I/O 항이 줄었을 뿐 비용은 여전히 offset에 선형이다. 그리고 실제 목록의 정렬은 대부분 PK가 아니다.

커서 기반으로 바꾸면 무엇을 잃습니까? 그럼 offset을 그대로 두는 게 맞는 경우는요? 시니어 변별힌트: 잃는 것을 먼저 목록으로 — 점 · 수 · 정 · 약

잃는 것을 먼저 목록으로 — ⑴ 임의 페이지 점프(페이지 번호 UI 불가) ⑵ total count(전체 건수·전체 페이지 수 표시 불가) ⑶ 정렬 유연성(정렬 축마다 커서와 인덱스를 따로 설계, 정렬 기준을 바꾸면 기존 커서 무효, 정렬 키는 유일하고 불변이어야 함) ⑷ API 호환성(스펙 변경, 구·신 병행 운영, 클라이언트 전부 수정). 얻는 것은 깊이와 무관한 상수 비용과 스크롤 중 중복/누락 없음이다.

그래서 offset을 두는 게 맞는 경우가 분명히 있다 — 사용자가 실제로 앞 몇 페이지만 보는 화면 + 페이지 번호 UI가 요구사항인 경우. 이때는 커서로 갈아엎지 않고 offset 상한 + 지연 조인으로 충분하다.

도구를 고르는 기준은 "커서가 더 빠르다"가 아니라 "이 화면의 접근 패턴이 순차 탐색인가 임의 접근인가"
정렬 키가 created_at 하나면 커서로 왜 안 됩니까? 같은 시각에 여러 건이면 어떻게 되나요? 필수힌트: 누락과 중복, 두 가지 실패를 값으로 보여준다

정렬 키가 유일하지 않으면 "그 다음"이 정의되지 않는다. 같은 초에 글 세 개(104, 103, 102)가 있고 커서가 그중 가운데(103)에서 끊겼다면 — created_at < $1은 남은 102를 건너뛰고(누락), created_at <= $1은 이미 본 104·103을 다시 준다(중복).

처방은 유일 컬럼 id를 tie-breaker로 붙여 (created_at, id)를 전순서로 만들고, 조건을 행 비교 (created_at, id) < ($1, $2)로, 인덱스도 (created_at, id)로 두는 것이다.

가산점 PostgreSQL에서는 이 복합 인덱스가 선택이 아니라 필수다 — 리프에 있는 것은 PK가 아니라 TID라 (created_at) 단독 인덱스 안에서 같은 시각의 엔트리는 id 순이 아니다. 그리고 행 비교가 Index Cond로 잡히려면 컬럼 순서·방향이 인덱스와 일치해야 하므로, 인덱스 정의가 곧 커서 조건의 설계도다.

지연 조인은 여전히 OFFSET 100000인데 왜 빨라지나요? 한계는요? 필수힌트: "세는 일"과 "무거운 왕복"을 갈라 말한다

사슬로 말한다. before는 인덱스 엔트리마다 TID로 힙을 읽어 가시성을 확인하고 행을 조립한 뒤 버린다 × 100,000. after의 서브쿼리는 SELECT id라 필요한 값이 전부 (created_at, id) 리프에 있어 Index Only Scan으로 힙을 건너뛰고 리프만 역순으로 세며 걷고, 살아남은 id 20개만 PK 인덱스로 힙을 읽는다. 흩어진 힙 페치 100,020회가 20회로 줄어든다.

한계는 둘이다. ① 인덱스 스캔 자체가 여전히 O(offset)이라 offset이 수십만·수백만이면 다시 느려진다. ② Index Only Scan의 힙 생략은 visibility map이 신선할 때뿐이라 VACUUM이 밀리면 Heap Fetches가 튀어 이득이 줄어든다.

그래서 지연 조인은 "페이지 번호 UI를 유지하면서 상한 안쪽을 빠르게" 또는 "커서로 가는 동안의 다리"로 쓴다.

무한 스크롤 중에 새 글이 올라오면 offset과 커서는 어떻게 다르게 동작하나요? 가산점힌트: 이건 성능이 아니라 "결과 정합성" 문제다

offset은 "앞에서 N번째"를 매번 다시 센다. 1페이지를 본 뒤 새 글이 하나 들어오면 2페이지 LIMIT 20 OFFSET 20의 창이 한 칸 밀려 1페이지 마지막 글이 2페이지 첫머리에 다시 나온다. 삭제가 일어나면 반대로 한 건이 건너뛰어진다. 커서는 "이 값 다음"을 조회하므로 삽입·삭제와 무관하게 이어진다.

즉 커서 기반은 성능만이 아니라 사용자가 보는 결과의 정합성 문제이기도 하다 — 피드에서 "아까 본 글이 또 나온다"는 CS의 상당수가 offset 페이지네이션이다.

단, 커서도 정렬 키가 갱신되는 컬럼(updated_at)이면 행이 위치를 옮겨 다니므로 같은 문제가 재발한다
— 커서의 정렬 키는 유일할 뿐 아니라 불변이어야 한다는 조건이 여기서 나온다
OFFSET 0인 1페이지도 느립니다. 뭘 봐야 하나요? 함정힌트: 이건 이 문항의 문제가 아니다. 그걸 알아보는 것이 답이다

offset 문제가 아니다. offset이 0인데 느리면 정렬·필터가 인덱스를 못 타고 있는 것이다 — Seq Scan으로 전체를 읽고 Sort로 전부 정렬한 뒤 앞 20건만 가져오는 계획이라, offset이 없어도 이미 비싼 쿼리다. 계획에 Sort가 있는지, work_mem을 넘겨 external merge Disk:로 내려갔는지를 본다.

1차 처방은 페이지네이션 기법이 아니라 정렬 컬럼(그리고 앞선 등호 필터를 포함한 복합) 인덱스다. 인덱스를 태워 Index Scan이 잡힌 다음에야 커서·지연 조인·상한이 의미를 갖는다.

순서를 바꿔 말하면 감점된다 — "느리니까 커서로 바꾸겠습니다"는, 인덱스가 없는 상태에서는 커서 조건조차 Filter로 처리돼 안 빨라진다.

커서로 바꿨는데도 뒤 페이지가 느립니다. 어디부터 의심하나요? 시니어 변별힌트: 계획에서 딱 두 가지만 확인하면 원인이 좁혀진다

확인할 것은 두 가지뿐이다. ① Index Cond에 커서 조건이 들어가 있는가(Filter로 밀려나지 않았는가) ② Limit 아래 actual rows가 size + 1에서 멈추는가. 둘 중 하나라도 아니면 "커서 문법만 썼을 뿐 실제로는 여전히 걷고 있다"는 뜻이다.

거기서 좁혀지는 원인 후보 — ⑴ 인덱스가 (created_at) 단독이라 tie-breaker 정렬이 인덱스에 없다 ⑵ JPQL 때문에 OR 형태로 풀어 썼는데 범위 상한(created_at <= $1)을 안 붙였다 → 플래너가 범위를 못 잡는다 ⑶ 정렬 방향을 섞었다(created_at DESC, id ASC) ⑷ 커서 값의 타입이 컬럼과 달라 캐스트가 붙었다(timestamptz 컬럼에 LocalDateTime) ⑸ 등호 필터가 있는데 인덱스 컬럼 순서가 (board_id, created_at, id)가 아니다.

공통점은 하나다 — 전부 "조건이 범위 탐색으로 번역되지 못하고 스캔 후 필터로 떨어진" 경우다. 커서는 문법이 아니라 인덱스와의 합의다.

계획의 Rows Removed by Filter가 0인데 정말 10만 건을 버린 게 맞나요? 함정힌트: 그 카운터가 세는 것은 다른 종류의 탈락이다

맞다. 그리고 PostgreSQL은 offset이 버린 행을 별도 카운터로 세어 주지 않는다. Rows Removed by Filter는 필터·조인 조건·인덱스 재검사에서 탈락한 행에만 붙는다. offset이 버린 행은 조건에서 탈락한 것이 아니라 "조건을 통과했지만 순번이 앞이라 버려진" 것이라 성격이 다르다.

그래서 증거는 둘로만 잡는다 — Limit의 actual rows(20)와 그 아래 스캔 노드의 actual rows(100020)의 격차, 그리고 Buffers의 shared hit + read가 반환 행이 아니라 읽은 행 규모로 잡히는 것. 여기서 rows=20(추정) 대 actual rows=20(실제)을 근거로 드는 것은 오답이다 — 그 둘의 차이는 플래너 추정의 정확도를 보는 지표다.

커서를 Base64로 감쌌는데, 클라이언트가 디코드해서 조작한 값을 보내면 어떻게 되나요? 시니어 변별힌트: 불투명 토큰의 목적이 무엇이었는지부터 정정한다

Base64는 보안 장치가 아니라 "계약을 불투명하게 만드는 장치"다. 목적은 두 가지였다 — 클라이언트가 내부 정렬 키에 의존하지 못하게 해서 나중에 정렬 키를 바꿀 수 있게 하는 것, 그리고 파라미터를 손대는 습관을 막는 것. 위변조 방지는 애초에 목적이 아니었다.

그래서 서버는 커서 값을 신뢰하지 않는 전제로 짠다. ⑴ 디코드 실패·타입 불일치·범위 이상은 400으로 거절한다(파싱 예외가 500으로 새지 않게). ⑵ 권한·소유권 필터(board_id, 테넌트, 공개 여부)는 커서와 무관하게 항상 WHERE에 붙인다 — 커서는 "어디서부터"만 정할 뿐 "무엇을 볼 수 있는가"를 정하지 않는다. ⑶ 그 결과 조작으로 얻을 수 있는 최대치가 "같은 목록의 다른 지점부터 보기"에 머물면 된다.

그 이상이 필요하면(커서에 필터 조건까지 담아야 하는 경우) 토큰에 서명을 붙여 서버가 검증하거나, 서버가 커서를 저장하고 클라이언트에는 불투명 ID만 준다. 다만 후자는 상태를 서버가 들게 되므로 만료·저장소 비용이 생긴다 — 무상태라는 키셋의 장점을 얼마나 내줄지의 거래다.

MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 다섯 지점 — 문법 · PK · 행 비교 · 복합 인덱스 · 도구

① 문법 — MySQL LIMIT 100000, 20, PostgreSQL LIMIT 20 OFFSET 100000. 비용 구조는 같다.

② PK 순의 특권 — InnoDB는 클러스터드라 PK 순이면 북마크 룩업이 없지만, PostgreSQL은 힙 구조라 PK 순에도 힙 페치가 붙고 대신 correlation이 무게를 정한다.

③ 행 비교 — PostgreSQL은 (created_at, id) < ($1, $2)를 B-tree 범위 하나로 실행하지만(Index Cond: ROW(...)), MySQL은 인덱스 최적화를 못 해 OR로 풀어 쓴다. (PostgreSQL에서 OR 형태를 쓰면 상한을 중복으로 줘야 한다.)

④ 복합 인덱스 — MySQL 세컨더리는 리프에 PK를 품어 (created_at)만으로 사실상 (created_at, PK) 순이지만, PostgreSQL은 리프가 TID라 (created_at, id)를 반드시 명시한다. 지연 조인의 커버링도 같은 이유로 복합 인덱스가 필요하고 VM 상태에 좌우된다.

⑤ 도구 — Using filesort·MAX_EXECUTION_TIME·슬로 쿼리 로그가 PostgreSQL에서는 Sort(top-N heapsort, N = offset + limit)·statement_timeout·auto_explain/pg_stat_statements에 대응한다.

이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "저장 구조에서 도출했다"로 들린다.

한 줄 요약
OFFSET은 건너뛰기가 아니라 읽고 버리기다 — B-tree에 "N번째" 좌표가 없어 Limit 노드가 100,020건을 세며 버리고, PostgreSQL은 힙 테이블이라 정렬 인덱스가 PK든 아니든 버릴 행에도 가시성 확인을 위한 힙 페치를 100,020번 지불해 비용이 페이지 번호에 선형이다(계획에서 Limit 아래 노드의 actual rows와 Buffers가 그 증거이고, offset이 버린 행을 세어 주는 별도 카운터는 없다). 해결책은 네 개를 세트로 — 커서(키셋)로 offset을 없애거나(마지막으로 본 정렬 키를 조건으로 넘기고, 정렬 키가 유일하지 않으면 tie-breaker를 붙여 행 비교 (created_at, id) < ($1, $2)로 쓴다. PostgreSQL은 이것을 인덱스 범위 하나로 실행한다), 지연 조인으로 버릴 행의 힙 페치를 없애거나(Index Only Scan, VM 상태에 좌우), API 레벨 상한으로 깊은 페이지를 거절하거나, 검색 엔진에 위임한다. 커서를 고를 때는 임의 페이지 점프 · 전체 페이지 수 · 정렬 유연성 · API 호환을 내주는 거래임을 같은 호흡에 말하고, 관리자 화면의 "마지막 페이지" 버튼은 정렬을 뒤집어 첫 페이지로 처리한다.
