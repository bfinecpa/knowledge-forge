RDB의 JSON 컬럼 "귀찮아서 JSON"과 "비정형이라 JSON"을 가르는 규율

Q. RDB의 JSON 컬럼은 언제 쓰고 언제 피하나요? 인덱싱과 스키마 진화 관점의 트레이드오프는?
핵심 관전 포인트 — 첫 답변으로 그대로 말한다

JSON 컬럼은 "행마다 모양이 다른 데이터를 DDL 없이 담는 자유"를 사는 대신, RDB가 컬럼에 제공하던 세 가지 — ① 인덱스(값의 정렬된 사본) ② 타입·제약(DB가 지키는 불변식) ③ 제자리 부분 갱신 — 를 반납하는 거래다.

그래서 판별은 취향이 아니라 질문이다. ⑴ 그 안의 값이 WHERE·JOIN·GROUP BY·ORDER BY의 대상인가 ⑵ 스키마가 행마다 진짜 다른가(모든 행이 같은 키를 가지면 컬럼을 JSON에 숨긴 것) ⑶ 쓰기 후 부분 수정이 잦은가 ⑷ DB가 지켜야 할 불변식(참조·UNIQUE·NOT NULL·타입)인가. 하나라도 "예"면 컬럼(또는 별도 테이블). 다 "아니오"인 데이터 — 외부 원문 보존, 희소(sparse) 속성, 통째로 읽고 쓰는 문서 — 가 JSON의 자리다.

쓰기로 했다면 안전망을 함께 든다: 조회 조건이 된 키는 생성 컬럼+인덱스로 승격, CHECK+JSON_SCHEMA_VALID(또는 DTO)로 스키마 검증, 버전 필드로 세대 관리.

1.거래 — JSON 컬럼은 무엇을 반납하고 무엇을 사는가

비유부터. 정식 컬럼은 서류 양식의 인쇄된 칸이다. 칸이 정해져 있으니 접수처는 그 칸 기준으로 색인(인덱스)을 만들 수 있고, 칸의 형식(숫자만, 빈칸 금지, 다른 서류 번호와 대조)을 접수 시점에 검사하며, 칸 하나만 고쳐 쓸 수 있다. JSON 컬럼은 비고란에 붙여 둔 메모지다. 무엇이든 적을 수 있지만 — 접수처는 메모지 안의 내용으로 색인을 만들지 않고, 내용을 검사하지도 않으며, 한 글자를 고치려면 메모지를 새로 써서 다시 붙여야 한다.

도식 1. 컬럼이 공짜로 주던 3가지를 반납하고 4가지 자유를 산다. 왼쪽 3개 각각이 아래 비용 사슬 ①②③이 된다.

첫 변별점

"인덱스가 잘 안 된다", "타입이 없다"는 결과다. 면접은 왜 그런지를 사슬로 묻는다.

아래 세 사슬을 각각 4~5단계로 소리 내어 말할 수 있어야 한다.

사슬 ① 조건 검색 — 값이 정렬된 사본에 없어서 풀스캔 인덱스 반납

인덱스란 인덱스 컬럼의 값과 PK를 함께 담아 그 값 기준으로 정렬해 둔 별도의 사본이다. 탐색이 빠른 이유는 오직 "찾는 값이 이미 정렬된 사본 안에 있어서"다. 그런데 JSON 컬럼의 내부 키는 DB 입장에서 컬럼이 아니다. DB가 아는 것은 "이 행의 attrs 자리에 JSON 문서 하나가 있다"까지고, 그 안의 genre는 스키마에 존재하지 않는다.

  1. ⑴ 정렬 사본에 값이 없다attrs.genre는 컬럼이 아님 (MySQL은 JSON 컬럼 자체에 인덱스도 불허)
  2. ⑵ 탐색 불가B+Tree를 탈 정렬 기준이 없다
  3. ⑶ 전 행 읽기풀스캔
  4. ⑷ 행마다 파싱I/O + CPU 이중 비용
  5. ⑸ 큰 문서 = 많은 페이지오버플로 페이지, 다른 키 수십 개까지 끌어옴
BEFORE — JSON 내부 키로 조건 검색 
SELECT id, title
FROM episodes
WHERE attrs->>'$.genre' = '로맨스';정렬 사본에 없는 값
-- EXPLAIN: type=ALL, key=NULL, rows≈전체 행 수
-- 인덱스가 "안 쓰인" 게 아니라 애초에 후보조차 없다.
-- 300만 에피소드면 300만 번 파싱 + 전 페이지 순차 읽기.

구조적으로는 "컬럼에 함수를 씌운 조건"과 같은 부류다 — JSON_EXTRACT(attrs, '$.genre')는 함수 적용의 극단형이고, 가공 전 원본 값만 정렬해 둔 사본이 가공 후 값을 알 리 없다. 우회(5장)의 원리는 하나 — 값을 정렬 사본 안에 "존재하게" 만든다.

사슬 ② 부분 갱신 — 키 하나 고쳐도 문서 전체를 다시 쓴다 제자리 갱신 반납

일반 컬럼의 UPDATE는 행 안에서 그 컬럼의 바이트 범위만 고친다. view_count가 4바이트 정수면 4바이트를 덮어쓰고 끝. JSON 컬럼은 JSON_SET(attrs, '$.view_count', 101)을 만나면 다음을 전부 한다.

  1. ⑴ 이진 문서 전체 읽기
  2. ⑵ 파싱
  3. ⑶ 값 변경
  4. ⑷ 재직렬화
  5. ⑸ 문서 전체 재기록100KB 문서면 숫자 하나에 100KB

재기록은 혼자 끝나지 않는다 — 변경 페이지만큼 redo 로그가 커지고, undo 로그에 "옛 문서 전체"가 실리며, 행 기반 복제면 binlog 행 이미지도 문서 크기에 비례하고, 행 락 보유 시간도 늘어난다. 일부 DB는 조건이 맞을 때만 제자리 갱신을 최적화하지만 조건이 까다로워 설계 시 기본 가정은 "전체 재기록"이다. PostgreSQL은 MVCC 특성상 UPDATE가 새 행 버전을 만들므로 어차피 통째로 다시 쓰인다.

금지 규칙

JSON 안에 카운터를 넣지 마라.

가장 잦은 쓰기를 가장 비싼 방식으로 하는 최악의 조합. 사슬 ②에는 우회가 없다 — 부분 갱신 대상은 처음부터 컬럼이다.

BEFORE — JSON 안의 조회수 
UPDATE episodes
SET attrs = JSON_SET(attrs, '$.view_count',조회 1건마다 문서 전체 재기록
                     CAST(attrs->>'$.view_count' AS UNSIGNED) + 1)
WHERE id = ?;
-- 읽기→파싱→수정→직렬화→전체 기록. 썸네일 URL 목록·태그·번역 상태 같은
-- 다른 키가 클수록 "조회수 +1"의 비용이 커진다.
AFTER — 카운터는 컬럼 
UPDATE episodes SET view_count = view_count + 1 WHERE id = ?;정수 자리만 제자리 갱신
-- 초고빈도 카운터는 컬럼이어도 핫 로우 문제가 남는다(정규화 문서의 사슬).
-- JSON은 거기에 재기록 비용을 얹을 뿐이다.

사슬 ③ 타입·제약 상실 — 불변식이 DB에서 애플리케이션 관례로 내려간다 타입·제약 반납

price DECIMAL(12,2) NOT NULL, FOREIGN KEY, UNIQUE (sku) — 정식 컬럼의 제약은 DB가 지킨다. 어떤 코드 경로로 들어오든, 운영자가 콘솔에서 직접 넣든 뚫리지 않는다. JSON 컬럼에는 이 검사가 하나도 없다. DB가 보장하는 것은 "문법적으로 올바른 JSON인가"뿐이다.

BEFORE — 세 행 모두 "유효한 JSON"이라 전부 성공한다 
INSERT INTO products (attrs) VALUES ('{"price": 1000}');      -- 숫자
INSERT INTO products (attrs) VALUES ('{"price": "1000"}');    -- 문자열타입 불일치 통과
INSERT INTO products (attrs) VALUES ('{"prcie": 1000}');      -- 오타 키오타 통과

-- 그리고 조회는 조용히 틀린다
SELECT COUNT(*) FROM products WHERE attrs->'$.price' > 500;에러 없이 1건
-- 숫자 1000은 걸리고, 문자열 "1000"은 비교 규칙에 따라 빠지고,
-- 오타 행은 키가 없어 NULL → 아무 에러 없이 1건.
  1. ⑴ DB는 문법만 검사
  2. ⑵ 불변식이 앱 관례로 강등모든 필드에 대해 기본값으로
  3. ⑶ 관례 모르는 경로에 뚫림새 코드 경로 · 콘솔 직접 수정
  4. ⑷ 조용히 틀린 데이터·집계
+ 참조 무결성 부재{"author_id": 42}가 삭제된 작가를 가리켜도 DB는 모른다. FK가 막던 고아(orphan) 참조가 검출 수단 없이 쌓인다.
+ NULL의 세 얼굴SQL NULL(컬럼이 비었다) · JSON null(키는 있고 값이 null) · 키 부재(키 자체가 없다)가 서로 다른 의미로 공존한다. 셋을 구분하지 않으면 집계가 어긋난다.

그럼에도 사는 것 — 정확히 네 가지

대가를 다 말했으니 편익도 정확히 말해야 양면이 조립된다.

① 희소 속성행마다 키 집합이 진짜 다를 때, NULL투성이 컬럼 수십 개나 EAV 없이 담는다.
② DDL 없는 필드 추가수억 건 테이블의 ALTER TABLE 리스크를 피한다 — 청구서는 스키마 진화에서 온다.
③ 외부 원문 무손실 보존스키마의 주인이 우리가 아닌 데이터(PG 응답, 웹훅)를 그대로 둔다.
④ 문서 단위 접근항상 통째로 읽고 통째로 쓰는 1:N 부속 데이터를 조인 없이 한 번에.
인출 규칙

얻는 것이 이 넷 중 하나가 아니면 JSON을 쓸 이유가 없다.

"테이블 하나 더 만들기 귀찮아서"는 이 목록에 없다.

2.판별 체크리스트 — "귀찮아서"와 "비정형이라"를 가르는 네 질문

데이터 하나를 놓고 위에서 아래로 묻는다. 오른쪽으로 한 번이라도 빠지면 컬럼이고, 끝까지 내려온 것만 JSON 후보다.

도식 2. 판별 4질문. 각 질문의 "예"는 1장의 사슬 ①②③ 중 하나로 귀결된다 — 질문이 사슬에서 나왔기 때문이다.

질문"예"라면근거 사슬
⑴ 그 안의 값이 WHERE·JOIN·GROUP BY·ORDER BY에 등장하는가?컬럼사슬 ① — 조건 검색·집계는 정렬 사본이 필요
⑵ 모든 행이 (거의) 같은 키 집합을 갖는가?컬럼스키마가 균일하면 JSON은 컬럼을 문자열 안에 숨긴 것
⑶ 쓰기 후 부분 수정이 잦은가? (카운터·상태·수정 가능한 항목)컬럼사슬 ② — 문서 전체 재기록
⑷ 다른 테이블을 참조하거나 UNIQUE·NOT NULL·타입 보장이 필요한가?컬럼 / 별도 테이블사슬 ③ — DB가 지켜야 할 불변식
⑵의 실무 판정법

테이블의 JSON 문서 1,000개의 키 집합을 뽑아 본다. 거의 전부가 같은 키를 가지면 그 키들은 컬럼이었어야 한다. 키 집합이 진짜 제각각이면 희소 속성이 맞다.

이름 붙이기

⑴~⑷에 "예"인데 테이블 만들기 싫어서 JSON에 넣은 것은 반정규화(대가를 알고 관리하는 의도적 중복)가 아니라 정규화 실패의 새 포장이다. 반정규화가 "중복을 두는 결정"이라면 이것은 "구조를 포기하는 결정"이다.

3.목록으로 인출한다 — JSON이 맞는 경우 5 / 피해야 할 경우 5

면접에서 "경우에 따라 다르다"로 끝내지 말고 목록을 그대로 꺼낸다. 외울 때는 왼쪽은 "사는 것 4"의 실체, 오른쪽은 "질문 4"에 예인 것 + 관계(1:N)로 묶으면 따로 외울 것이 없다.

JSON이 맞는 경우

  1. 외부 시스템 원문 보존 사는 것 ③PG 응답, 웹훅 페이로드, 외부 API 응답. 스키마의 주인이 우리가 아니고, write-once이며, 감사·분쟁 대응용.
  2. 행마다 키가 다른 희소 속성 사는 것 ①상품 카테고리별 규격, 콘텐츠 형식별 메타. 컬럼으로 펼치면 NULL이 대부분인 컬럼 수십 개.
  3. 통째로 읽고 통째로 쓰는 문서 사는 것 ④사용자 설정(preferences), 에디터 레이아웃 상태. 항상 전체 로드·전체 저장, 조건 검색 없음.
  4. 감사·이력 스냅샷 사는 것 ④"그 시점에 이 객체가 어떤 모양이었나"를 통째로. 조회는 PK나 시각 컬럼으로, 문서는 그냥 보여 준다.
  5. 아직 형태가 굳지 않은 실험 속성 사는 것 ②단, "굳는 순간 승격한다"는 출구 규칙이 함께 있을 때만.

JSON을 피해야 할 경우

  1. 조회 조건·정렬·집계 대상 질문 ⑴ · 사슬 ①WHERE·ORDER BY·GROUP BY에 오르는 값.
  2. 다른 테이블과의 관계 질문 ⑷주문의 상품 목록, 글의 태그처럼 반대 방향 조회("이 상품이 포함된 주문")가 필요한 1:N → 별도 테이블.
  3. 모든 행이 같은 키를 갖는 균일 데이터 질문 ⑵그냥 컬럼이다.
  4. 잦은 부분 갱신 질문 ⑶ · 사슬 ②카운터, 상태값, 재고.
  5. DB가 지켜야 할 불변식 질문 ⑷ · 사슬 ③금액, 식별자, 필수값, 유일값.

4.도메인에 대 보기 — 세 사례와 반례 하나

(a) 웹툰 에피소드 메타데이터 — 공통은 컬럼, 형식별 희소 속성만 JSON

BEFORE — "메타데이터는 다 JSON에" 
CREATE TABLE episodes (
    id    BIGINT PRIMARY KEY,
    meta  JSON   -- {"title":..., "no":12, "published_at":..., "is_free":true,조회 조건까지 문서 안에
                 --  "genre":"로맨스", "cut_count":48, "bgm_track":"..."}
);
-- 목록 화면: WHERE meta->>'$.is_free' = 'true' ORDER BY meta->>'$.published_at'
-- → 사슬 ① 그대로. 회차 번호 UNIQUE도, 공개일 NOT NULL도 못 건다.
AFTER — 모든 에피소드가 갖는 것 + 조회 조건은 컬럼 
CREATE TABLE episodes (
    id            BIGINT PRIMARY KEY,
    series_id     BIGINT NOT NULL,          -- FK, "시리즈의 에피소드 목록" 조회⑴⑷
    episode_no    INT    NOT NULL,          -- UNIQUE(series_id, episode_no)⑵⑷
    title         VARCHAR(200) NOT NULL,
    published_at  DATETIME NOT NULL,        -- 정렬·범위 조건⑴

5.안전망 3종 — 쓰기로 했다면 함께 든다

안전망은 사슬에서 나온다. 사슬 ①(인덱스)에는 승격, 사슬 ③(제약)에는 검증, "DDL 없는 추가"의 청구서(세대 공존)에는 버전 필드. 사슬 ②(재기록)에만 안전망이 없다 — 그래서 부분 갱신 대상은 처음부터 컬럼이다.

A. 승격 — 생성 컬럼 + 인덱스← 사슬 ① 인덱스 반납. 조회 조건이 된 키를 정렬 사본에 "존재하게" 만든다.
B. 검증 — CHECK + JSON_SCHEMA_VALID← 사슬 ③ 제약 반납. 불변식을 앱 관례에서 DB 제약으로 되돌린다.
C. 세대 — schema_version← 스키마 진화 청구서. 어느 세대의 문서인지 자기 표시.

안전망 A — 생성 컬럼 승격: 값을 정렬 사본 안에 "존재하게" 만든다

생성 컬럼(generated column)은 "이 컬럼의 값은 이 식으로 계산된다"고 DB에 등록한 컬럼이다. JSON에서 키를 뽑는 식을 등록하면 DB는 그것을 정식 컬럼으로 인식하고, 정식 컬럼이니 인덱스를 걸 수 있으며, 인덱스에는 식의 결과값이 물질화되어 정렬된다.

BEFORE — JSON 키로 직접 조건 
SELECT id, title FROM episodes WHERE format_attrs->>'$.genre' = '로맨스';type=ALL
-- 어떤 인덱스의 정렬 기준에도 genre 값이 없다
AFTER — 생성 컬럼으로 승격 + 인덱스 
ALTER TABLE episodes
    ADD COLUMN genre VARCHAR(30)타입 선언 = 정식 컬럼
        GENERATED ALWAYS AS (format_attrs->>'$.genre') VIRTUAL;DB에 식을 등록
CREATE INDEX idx_episodes_genre ON episodes (genre);인덱스에 값 물질화

SELECT id, title FROM episodes WHERE genre = '로맨스';type=ref, key=idx_episodes_genre

세 가지를 함께 말하면 원리를 이해했다는 신호다.

VIRTUAL vs STOREDVIRTUAL은 행에 값을 저장하지 않고 읽을 때 계산하지만 인덱스에는 값이 물질화된다 — 그래서 탐색이 된다. STORED는 행에도 저장한다(행이 커지는 대신 계산 비용 없음).
식 일치 조건원래 식 format_attrs->>'$.genre'로 조회하면 옵티마이저가 생성 컬럼의 식과 같은 형태로 인식할 때만 치환한다. 안전하게는 생성 컬럼 이름으로 조회. 함수 기반 인덱스는 "숨은 생성 컬럼+인덱스"의 축약 문법이고, PostgreSQL 표현식 인덱스 CREATE INDEX ON episodes ((format_attrs->>'genre'))도 같은 원리.
타입 고정생성 컬럼은 VARCHAR(30)처럼 타입을 선언한다 — JSON 안에 "12"와 12가 섞여 있으면(사슬 ③) 인덱스 값도 섞인다. 우회는 사슬 ①만 풀지 사슬 ③은 풀지 않는다.
가산점 — 배열·문서 안을 역색인

멀티밸류 인덱스(MySQL): tags: ["로맨스","학원","완결"]처럼 배열 원소가 조건이면 생성 컬럼으로 안 된다 — 행 하나에 값이 여러 개라 "정렬 사본의 한 자리"에 못 넣는다. 멀티밸류 인덱스는 배열 원소 하나당 엔트리 하나를 만든다(위 행은 3개 엔트리). CREATE INDEX ... ((CAST(format_attrs->'$.tags' AS CHAR(30) ARRAY)))로 만들고 MEMBER OF, JSON_CONTAINS, JSON_OVERLAPS 조건이 탄다.

GIN(PostgreSQL): jsonb 컬럼의 모든 키/값 쌍을 역색인해 attrs @> '{"genre":"로맨스"}' 같은 포함 검색을 키를 미리 정하지 않고도 탄다. 대신 인덱스가 크고 쓰기 비용이 높으며 범위·정렬 조건에는 약하다 — "모든 키/값"을 색인하는 값이다.

우회의 한계 — 반드시 붙인다

결국 "미리 정한 키"만 빠르다. 생성 컬럼이 다섯 개가 됐다면 우회가 아니라 뒤늦은 컬럼화다.

"미리 정해진, 모든 행이 갖는, 조회 조건인 키"는 2장의 표로 돌아가면 정의상 컬럼이었어야 하는 것. 우회의 정직한 적용 범위는 — 문서의 대부분이 진짜 비정형이고 그중 한두 키만 조회 조건이 됐을 때, 문서를 깨지 않고 그 키만 꺼내 색인하는 도구. 공짜 우회는 없다.

스키마 진화 — "자유"가 아니라 "책임의 이전"

"DDL 없는 필드 추가"의 청구서가 여기서 온다. 컬럼과 JSON의 스키마 변경을 나란히 놓으면 차이가 보인다.

JSON은 스키마 변경 비용을 없앤 게 아니라 "DB의 DDL 한 번"에서 "애플리케이션의 모든 읽기 경로, 무기한"으로 옮긴 것이다.

배포마다 형태가 다른 세대(generation)의 행이 쌓이고, 읽는 코드는 모든 세대를 이해해야 한다. 이 책임을 감당하는 것이 안전망 B·C다.

안전망 B — CHECK + JSON_SCHEMA_VALID: 불변식을 DB 제약으로 되돌린다

BEFORE — 검증도 버전도 없는 JSON 
CREATE TABLE user_preferences (
    user_id BIGINT PRIMARY KEY,
    prefs   JSON NOT NULL무엇이 들어 있는지 아무도 보장 못 함

CREATE TABLE user_preferences (
    user_id        BIGINT PRIMARY KEY,
    schema_version INT  NOT NULL DEFAULT 2,안전망 C
    prefs          JSON NOT NULL,
    CONSTRAINT chk_prefs_schema CHECK (안전망 B
        JSON_SCHEMA_VALID(
            '{
              "type": "object",
              "required": ["theme", "reader"],
              "properties": {
                "theme":  {"type": "string", "enum": ["light", "dark", "system"]},
                "reader": {
                  "type": "object",
                  "required": ["direction"],
                  "properties": {
                    "direction":         {"type": "string", "enum": ["vertical", "horizontal"]},

-- 이제 {"theme": 3}도, {"reader": {}}도, 콘솔에서 직접 넣어도 INSERT가 실패한다.
-- 불변식이 애플리케이션 관례에서 다시 DB 제약으로 올라왔다 (사슬 ③의 부분 회복).

DB 층에 두는 이유는 사슬 ③과 같다 — 콘솔 직접 수정과 새 코드 경로까지 막는 것은 DB 제약뿐이다. DB가 지원하지 않거나 스키마가 너무 자주 바뀌면 최소한 애플리케이션 DTO + Bean Validation으로 쓰기 경로를 단일화한다. 둘 중 하나는 반드시.

안전망 C — schema_version: 세대를 표시하고 업캐스팅한다

public UserPreferences read(long userId) {
    var row = repo.findById(userId);
    return switch (row.schemaVersion()) {세대별 분기
        case 1 -> upcastV1(mapper.readValue(row.prefs(), PrefsV1.class)); // 옛 세대 → 현재 모델업캐스팅
        case 2 -> mapper.readValue(row.prefs(), PrefsV2.class);
        default -> throw new UnsupportedSchemaVersionException(row.schemaVersion());
    };
}

// (읽기 시 점진 마이그레이션). 남은 v1은 야간 배치로 훑어 올린다.
// DTO에는 Bean Validation(@NotNull, @Min)을 붙여 DB 층 검증과 이중으로 건다.
세 안전망을 한 호흡에

① 버전 필드 — 세대 표시 → 읽기 시 업캐스팅 → 쓰기는 최신 세대로 → 잔여분 배치 마이그레이션. "지금 v1이 몇 건 남았나"를 WHERE schema_version = 1로 셀 수 있다는 것 자체가 가치다. ② 스키마 검증 — DB 층 우선 — CHECK+JSON_SCHEMA_VALID(MySQL) 또는 jsonb 검증 제약(PostgreSQL), 안 되면 DTO+Bean Validation. ③ 승격 규율 — 팀 규칙으로 문서화: "JSON 안의 키가 조회 조건·집계·정렬 대상이 되는 순간 컬럼(또는 생성 컬럼+인덱스, 또는 별도 테이블)으로 승격한다." 출구 규칙이 없는 JSON은 "임시"라는 이름으로 영구화된다.

6.셀프 테스트 — 질문만 보고 먼저 답한 뒤 펼친다

JSON 컬럼 안의 값으로 WHERE를 걸면 왜 느린가요? 어떻게 우회하나요?

사슬로 답한다. 인덱스는 컬럼 값을 정렬해 둔 사본인데 JSON 내부 키는 컬럼이 아니라 어떤 사본에도 값이 없다 → 탐색 불가 → 전 행 읽기 → 행마다 JSON 파싱 후 비교(I/O + CPU 이중 비용) → 큰 문서일수록 읽을 페이지도 많다.

우회의 원리는 "값을 사본에 존재하게 만들기" — 생성 컬럼으로 키를 정식 컬럼으로 등록하고 인덱스를 걸면 인덱스에 값이 물질화된다(VIRTUAL이어도 인덱스에는 저장). 배열 원소 조건이면 멀티밸류 인덱스, PostgreSQL이면 jsonb + GIN.

한계를 붙인다 — 우회는 미리 정한 키만 빠르게 하므로, 조회 키가 늘면 그건 컬럼이어야 했던 것이다.

JSON 안의 키 하나만 바꾸는 UPDATE는 싸지 않나요? 어차피 한 행인데요.

아니다 — 문서 전체 재기록이 기본이다. 일반 컬럼은 그 컬럼의 바이트만 고치지만, JSON은 저장된 문서를 읽고 → 파싱 → 수정 → 직렬화 → 전체를 다시 기록한다. 재기록 크기가 문서 크기에 비례하고, 그만큼 redo·undo 로그, 복제 행 이미지, 행 락 보유 시간이 커진다. 일부 DB의 제자리 갱신 최적화는 조건이 까다로워 설계 가정으로 삼지 않는다.

그래서 JSON 안에 카운터·상태 같은 잦은 부분 갱신 대상을 두지 않는다 — 가장 잦은 쓰기를 가장 비싼 방식으로 하는 조합. 반대로 통째로 읽고 통째로 쓰는 문서(사용자 설정)는 어차피 전체 재기록이라 이 비용이 문제가 안 된다 — 그래서 JSON에 맞는 것이다.

1년 뒤 JSON 안의 필드 이름을 바꿔야 합니다. 컬럼이면 RENAME 한 번인데, JSON은 뭐가 다른가요?

컬럼은 DDL 한 번으로 모든 행이 즉시 같은 형태가 되지만, JSON은 DDL이 없는 대신 옛 형태의 행이 영구 공존한다. 이름 변경은 (a) 전 행 UPDATE — 행마다 문서 전체 재기록이라 대용량이면 그 자체가 부하 작업 — 이거나, (b) 읽기 코드가 옛 이름·새 이름을 영원히 둘 다 이해하는 이중 읽기다.

즉 JSON은 스키마 변경 비용을 없앤 게 아니라 DB의 DDL 한 번 → 애플리케이션의 모든 읽기 경로, 무기한으로 옮긴 것. 감당하는 장치는 schema_version 필드(세대 표시 → 읽기 시 업캐스팅 → 쓰기는 최신 세대로 → 잔여분 배치 마이그레이션)와 스키마 검증(CHECK+JSON_SCHEMA_VALID 또는 DTO). 버전 필드가 없으면 "지금 어떤 세대가 몇 건 남았는지"조차 셀 수 없다.

주니어가 "상품 속성은 카테고리마다 달라서 attrs JSON에 다 넣겠다"는 PR을 올렸습니다. 어떤 질문을 던지시겠어요?

체크리스트를 질문으로 바꾼다. ⑴ "이 속성들 중 검색 필터·정렬·집계에 쓰이는 게 있나요?" — 가격·브랜드·색상처럼 필터가 되는 것은 컬럼(또는 생성 컬럼+인덱스). ⑵ "모든 상품이 갖는 키가 있나요?" — 있으면 컬럼. ⑶ "등록 후 자주 바뀌는 값이 있나요?" — 재고·판매 상태는 컬럼. ⑷ "다른 테이블을 참조하거나 유일·필수여야 하는 값이 있나요?" — 브랜드 ID·SKU는 컬럼/FK.

넷을 통과한 진짜 희소 속성(의류의 소재·세탁법, 가전의 소비전력)만 JSON. 그리고 두 가지를 더 요구한다 — 검증(허용 키·타입을 JSON_SCHEMA_VALID 또는 DTO로)과 승격 규칙("필터가 되는 순간 컬럼으로"). 이 질문 세트가 곧 "귀찮아서"와 "비정형이라"를 가르는 리뷰 기준이다.

PG 원문 응답을 JSON으로만 저장했는데, CS팀에서 "승인번호로 검색"을 요구합니다. 어떻게 하시겠어요? 처음부터는 어떻게 설계했어야 하나요? 시니어 변별

지금: 승인번호는 조회 키가 됐으니(⑴ 예) 승격한다. 가장 싼 경로는 생성 컬럼 + 인덱스(approval_no VARCHAR(32) GENERATED ALWAYS AS (pg_response->>'$.approvalNo') VIRTUAL + 인덱스) — 기존 행을 다시 쓰지 않고 인덱스 생성 한 번으로 끝난다. 단 PG사마다 응답 필드명이 다르면 식이 복잡해지므로, 그 경우엔 정식 컬럼을 추가하고 배치로 채운다.

처음부터: 이중 저장이 정답이었다 — 원문 pg_response는 write-once 무손실 보존(스키마의 주인이 PG사, 분쟁 시 증거)으로 JSON이 맞고, 우리가 조회·집계·정합성 검증에 쓰는 값(거래 ID, 승인번호, 금액, 상태)은 저장 시점에 추출해 정식 컬럼으로 둔다.

양면으로 말하면 — 대가는 "같은 값이 두 곳에 있는 중복"이지만, 원문은 갱신 경로가 없어 어긋날 수 없는 스냅샷 성격의 중복이라 동기화 장치가 필요 없다. 편익은 조회 키가 인덱스를 타고, 금액에 DECIMAL NOT NULL, 거래 ID에 UNIQUE를 걸어 불변식을 DB로 되돌린다는 것. "JSON이냐 컬럼이냐"의 이분법이 아니라 "원문 보존과 조회는 다른 요구이고, 다른 컬럼이 맡는다"까지 가면 변별된다.

MySQL에서 JSON 컬럼에 바로 CREATE INDEX를 걸면 어떻게 되나요? 추가

실패한다. JSON 컬럼 자체는 일반 인덱스를 허용하지 않는다 — 인덱스에 담을 "값"이 정의되지 않기 때문이다(문서 전체를 정렬 기준으로 삼을 수 없다). 인덱스가 필요하면 반드시 "어떤 경로의 값인지"를 지정해야 한다 — 생성 컬럼+인덱스, 함수 기반 인덱스, 배열이면 멀티밸류 인덱스. 이 사실 자체가 사슬 ①의 증거다: DB에게 JSON 내부 키는 컬럼이 아니다.

생성 컬럼을 VIRTUAL로 만들었는데 행에 값이 없다면서 왜 인덱스가 타나요? 추가

VIRTUAL은 행(클러스터드 인덱스)에 값을 저장하지 않을 뿐이고, 그 컬럼에 만든 보조 인덱스에는 식의 결과값이 물질화되어 정렬 저장된다. 탐색은 보조 인덱스에서 일어나므로 값이 "존재"한다. 행에도 값을 두려면 STORED — 행이 커지는 대신 SELECT 시 계산 비용이 없다. 따라서 "인덱스 탐색용이면 VIRTUAL로 충분, 인덱스 없이 자주 읽는 값이면 STORED"가 선택 기준이다.

SQL NULL, JSON null, 키 부재 — 셋을 쿼리에서 어떻게 구분하나요? 추가

세 질문을 따로 던져야 한다. 컬럼 자체가 비었는가는 attrs IS NULL. 키가 존재하는가는 경로 존재 검사(MySQL JSON_CONTAINS_PATH(attrs, 'one', '$.k')). 값이 JSON null인가는 타입 검사(JSON_TYPE(attrs->'$.k') = 'NULL'). 추출 연산자 하나로 물으면 "키 부재"와 "SQL NULL"이 같은 결과로 뭉개진다. 코드 쪽도 마찬가지 — DTO에서 "필드 없음"과 "명시적 null"을 구분하려면 Optional이나 존재 플래그가 따로 필요하다. 집계가 어긋나는 대표 원인이라 설계 단계에서 "이 키의 null은 무슨 뜻인가"를 정해 두는 것이 안전망 B(스키마 검증)의 일부다.

PostgreSQL이면 json과 jsonb 중 무엇을 쓰나요? 추가

기본은 jsonb. 이진으로 분해 저장해 읽을 때 파싱을 반복하지 않고, GIN 인덱스와 포함 연산자(@>)를 쓸 수 있다. 대신 키 순서·중복 키·공백 같은 원문 표기는 보존하지 않는다. 그래서 목적으로 가른다 — 조회·포함 검색이 있으면 jsonb, "PG가 그때 보낸 바이트 그대로"가 증거로서 의미 있는 원문 보존이면 json(또는 text)에 원문을 두고 조회 키는 컬럼으로 추출한다. (b) 사례의 이중 저장과 같은 결론이다.

희소 속성이면 EAV(속성 테이블)가 JSON보다 낫지 않나요? 추가

EAV(entity–attribute–value)는 속성 하나당 행 하나를 두는 방식이라 값 컬럼이 범용 문자열이 되어 타입·제약을 역시 잃고(사슬 ③과 같은 문제), 객체 하나를 읽으려면 속성 수만큼 조인·피벗이 필요하다. 희소 속성이 조회 조건이 아니고 통째로 읽힌다면 JSON이 더 단순하고 읽기 비용도 싸다. 반대로 특정 속성이 조회 조건이라면 EAV도 JSON도 아니라 그 속성은 컬럼이다 — 판별 4질문은 저장 형식이 아니라 "그 값이 무엇을 요구받는가"를 묻는 것이기 때문이다.

왜 "귀찮아서 JSON"을 반정규화의 일종이 아니라 "정규화 실패의 새 포장"이라 부르나요? 추가

반정규화는 정규화된 구조를 알고서 대가(중복·동기화)를 계산해 의도적으로 중복을 두는 결정이고, 대가를 관리하는 장치(동기화 경로, 갱신 지점 단일화)가 따라온다. "귀찮아서 JSON"은 ⑴~⑷에 "예"인 데이터 — 즉 컬럼이나 별도 테이블이어야 할 구조 — 를 구조 자체를 만들지 않고 문자열 안에 숨긴 것이라 대가 계산도 관리 장치도 없다. 중복을 두는 결정이 아니라 구조를 포기하는 결정이므로, 반정규화의 어휘를 빌릴 자격이 없다.

판별 연습 — 컬럼인가, JSON인가, 별도 테이블인가

4질문을 머릿속으로 돌린 뒤 펼친다. 근거 질문 번호까지 말할 수 있어야 한다.

상품의 재고 수량
컬럼 — 판매마다 바뀌는 잦은 부분 갱신(⑶), 음수 금지·정합성 검증 대상(⑷). JSON에 두면 "가장 잦은 쓰기를 가장 비싼 방식으로".
결제 웹훅 페이로드 원문
JSON — 스키마 주인이 외부, write-once, 분쟁 증거(사는 것 ③). 단 우리가 조회에 쓰는 키(거래 ID·승인번호·금액·상태)는 저장 시 추출해 컬럼으로 — 이중 저장.
에피소드 공개일 published_at
컬럼 — 목록 정렬·범위 조건(⑴), 모든 행이 갖는 값(⑵), NOT NULL 보장(⑷).
글의 태그 목록 — "이 태그가 달린 글" 조회가 필요
별도 테이블(post_tags) — 반대 방향 조회가 필요한 1:N(피해야 할 ②). 태그 존재 여부를 참조로 보장해야 하면 더욱(⑷). 문서 대부분이 진짜 비정형이고 태그 포함 검색 하나만 필요하다면 멀티밸류 인덱스가 우회지만, 그건 "한두 키만" 조건일 때의 도구다.
에디터 레이아웃 상태 (패널 위치·크기·접힘 여부)
JSON — 항상 통째로 읽고 통째로 저장, 조건 검색 없음, 클라이언트 버전마다 키가 늘어남(사는 것 ④·②). 단 schema_version과 스키마 검증을 함께.
의류 상품의 소재·세탁법, 가전의 소비전력
JSON — 카테고리마다 있거나 없는 진짜 희소 속성(⑵ 아니오), 필터가 아니며(⑴ 아니오), 등록 후 거의 안 바뀌고(⑶ 아니오), 참조·유일 제약 없음(⑷ 아니오). 단 "소재로 필터"가 요구되는 순간 승격 규칙 발동.
사용자 설정 안의 다크 모드 여부 — 어느 날 "다크 모드 사용자 비율" 대시보드 요구가 왔다
처음엔 JSON(통째 문서의 일부)이 맞았다. 집계 대상이 된 순간(⑴ 예) 승격 — 생성 컬럼+인덱스 또는 정식 컬럼 — 하거나, 설정 변경 이벤트를 따로 적재해 거기서 센다. 운영 DB에 JSON 풀스캔 집계를 매일 돌리는 선택지는 없다.
한 줄 요약
JSON 컬럼은 행마다 다른 데이터를 DDL 없이 담는 자유를 사는 대신 인덱스(정렬 사본에 값이 없어 풀스캔+파싱)·타입/제약(불변식이 앱 관례로 강등)·제자리 갱신(키 하나 바꿔도 문서 전체 재기록)을 반납하는 거래이므로, "조회·집계 대상인가 / 모든 행이 같은 키인가 / 부분 갱신이 잦은가 / DB가 지킬 불변식인가"에 하나라도 "예"면 컬럼이고, 넷 다 "아니오"인 외부 원문·희소 속성·통째로 읽고 쓰는 문서만 JSON에 두되 — 조회 조건이 된 키는 생성 컬럼+인덱스로 승격하고, CHECK+JSON_SCHEMA_VALID(또는 DTO)로 검증하며, 버전 필드로 세대를 관리하는 안전망을 함께 든다.
