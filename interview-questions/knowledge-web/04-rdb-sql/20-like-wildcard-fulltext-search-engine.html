LIKE '%keyword%'와 검색 전환 기준
인덱스는 "왼쪽부터 정렬된 사전"이라, 중간 일치는 시작점이 없다

면접 질문: "LIKE '%keyword%' 검색이 인덱스를 못 타는 이유는? 풀텍스트 인덱스와 검색 엔진(Elasticsearch) 전환은 어떤 기준으로 판단하나요?"

핵심 관전 포인트 — B-tree 인덱스는 문자열을 첫 글자부터 정렬해 둔 사전이다. LIKE '나무%'는 "나무"로 시작하는 첫 장을 펼쳐 연속 구간 하나만 읽으면 되지만, LIKE '%나무%'는 첫 글자를 모르니 트리를 내려갈 시작점을 찍을 수 없다 — 사전에서 "…나무"로 끝나는 단어를 찾으려면 첫 장부터 끝 장까지 넘겨야 하는 것과 같다. 그래서 PostgreSQL 계획은 Seq Scan + Filter + Sort이고, 비용은 행 수에 선형이다: 힙 페이지 전부 순차 읽기 + 행마다 패턴 매칭(CPU) + 정렬, 이게 QPS만큼 곱해져 커넥션(= 백엔드 프로세스) 점유 시간이 늘고 풀이 마르면 검색과 무관한 기능까지 번진다. 대응은 네 층위 — ① B-tree 안에서 버티기(접두 일치로 요구 협상 — 단 PG는 collation이 C가 아니면 접두 LIKE조차 인덱스를 안 타므로 text_pattern_ops가 필수 / 역방향·정규화 표현식 인덱스 / 자체 n-gram 토큰 테이블 / 선행 필터로 스캔 폭 축소) ② pg_trgm + GIN — 3글자 조각(트라이그램)의 역색인으로 "포함 검색"을 "조각들의 등호 조회"로 바꿔 LIKE '%kw%' 문법 그대로 인덱스를 태운다(대가: 3글자 미만 검색어에 무력, 색인 크기, 쓰기 비용, 관련도 순위 없음) ③ tsvector + GIN 전문 검색 — 단어 단위 검색·가중치·ts_rank 랭킹(대가: 한국어 형태소 분석기 미내장) ④ 검색 엔진 — 형태소·오타·동의어·관련도·패싯·부하 격리가 필요할 때. ④의 진짜 대가는 인프라가 아니라 색인이 DB 밖에 따로 사는 데서 오는 데이터 동기화와 최종 일관성, 그리고 장애 도메인 추가다. 전환 판단은 감이 아니라 데이터량 · QPS · 일치 유형 · 검색어 길이 · 품질 · 결합 · 범위/신선도 · 격리 8칸으로 하고, "무엇이 넘으면 다음 층위로 간다"를 ADR에 숫자로 박아 둔다.
  • 1
    못 타는 게 아니라 "탐색(seek)"을 못 한다 — B-tree 리프는 첫 글자부터 정렬된 사전이라 '나무%'는 범위 조건(>= '나무' AND < '나묵')으로 바뀌어 시작점을 찍고 연속 구간 하나만 읽지만, '%나무%'는 첫 글자를 몰라 루트에서 내려갈 방향을 정할 수 없다. 문제는 "인덱스가 검색을 못 한다"가 아니라 정렬 기준과 검색 조건이 어긋난다는 것이고, 그 대가는 Seq Scan + Filter + Sort — 행 수에 선형이라 배포 없이 조용히 자란다.
  • 2
    해법은 네 층위이고, 층위를 가르는 축은 "인덱스에 무엇을 키로 넣는가"다 — 값 통째(B-tree: 요구를 접두로 협상 + text_pattern_ops, 역순·정규화 표현식 인덱스, 자체 토큰 테이블, 선행 필터) → 3글자 조각(pg_trgm GIN: 포함 검색이 조각들의 등호 조회가 된다) → 단어(tsvector GIN: 가중치·ts_rank 랭킹) → 엔진이 정하는 모든 것(형태소·오타·동의어·패싯). 잘게 쪼갤수록 잘 찾지만, 쪼갠 규칙을 따로 관리해야 하는 정도가 곧 비용이다.
  • 3
    전환 판단은 감이 아니라 체크리스트이고, ④의 대가는 인프라가 아니라 동기화다 — 층위 ①②③에서는 색인이 같은 트랜잭션 안에서 DB가 갱신해 줬지만, ④에서 처음으로 색인이 DB 밖에 산다. 그 순간 이중 쓰기 금지·Outbox/CDC·지연 합의·폴백·전량 재색인이 전부 우리가 만들어야 하는 절차가 된다. 그래서 요구를 받으면 8칸(데이터량·QPS·일치 유형·검색어 길이·품질·결합·범위/신선도·격리)을 먼저 채우고, 전환 트리거를 ADR에 숫자로 고정한다.

0. 질문 + 출제 의도

질문: "LIKE '%keyword%' 검색이 인덱스를 못 타는 이유는? 풀텍스트 인덱스와 검색 엔진(Elasticsearch) 전환은 어떤 기준으로 판단하나요?"

출제 의도: 중간 일치 검색이 인덱스 구조상 불가능함을 알고, 풀텍스트 인덱스로 버틸 수 있는 규모와 검색 엔진 도입(운영 비용·동기화 문제)의 문턱을 판단하는지 — 즉 "검색 기능 추가해주세요"라는 흔한 요구의 숨은 비용을 산정하는 능력이다. "LIKE는 인덱스 못 탐"이라는 사실 확인이 아니라, 기획자가 툭 던진 한 줄 요구를 받았을 때 네 층위의 비용과 한계를 양쪽 다 놓고 어디서 멈출지 결정하는 판단 과정을 본다.

PostgreSQL에서 "풀텍스트 인덱스"는 하나가 아니라 둘이다 부분 문자열을 찾는 pg_trgm과 단어 단위로 찾는 tsvector. 그래서 이 질문의 답은 "풀텍스트 쓰면 됩니다"가 아니라 "어느 것으로 얼마나 버티는가"까지다.
이 페이지가 겨냥하는 약점 세 가지 ① "LIKE는 인덱스 못 탄다"는 사실 암기에서 멈추는 것 → 1·2절에서 정렬 기준과 검색 조건의 어긋남이라는 원리와 seek / scan 구분(Index Cond 없는 Index Only Scan)까지 내려간다.
② 중간 선택지 없이 "pg_trgm이나 ES 쓰죠"로 점프하는 것 → 5·6절에서 층위를 가르는 축과 B-tree 안에서 버티는 다섯 가지 우회를 번호로 세운다.
③ 도입 대가를 "서버 비용"으로만 세는 것 → 9·10절에서 색인이 DB 밖에 사는 순간 생기는 동기화·최종 일관성·폴백·재색인을 대가의 무게중심으로 놓고, 8칸 체크리스트와 ADR로 판단을 고정한다.

1. 원리 — 왜 "시작점"이 없는가

B-tree의 리프는 인덱스 컬럼 값 기준으로 정렬된 (키, TID) 엔트리의 연결 리스트다. 여기서 TID는 그 값이 든 힙(테이블 본체) 행의 물리 주소다. 문자열 컬럼이면 그 정렬 기준은 첫 글자, 같으면 둘째 글자, 그다음 셋째 글자 — 사전과 정확히 같다. 이 한 문장이 이 문서 전체의 뿌리다.

외울 것은 결론이 아니라 이 문장이다 — "정렬 기준(첫 글자)과 검색 조건(중간 글자)이 어긋나면, 정렬은 아무것도 건너뛰게 해 주지 못한다"

비유 두 개 — 사전, 그리고 출석부

국어사전과 "역순 사전"

"나무로 시작하는 단어"는 ㄴ 항목을 펴고 '나무' 페이지로 바로 간다. 그런데 "…나무로 끝나는 단어"(사과나무·소나무·참나무)는? 사전은 끝 글자로 정렬돼 있지 않으니 첫 장부터 끝 장까지 한 단어씩 확인하는 수밖에 없다.

국어사전에 "역순 사전"(단어를 뒤집어 정렬한 사전)이 따로 존재하는 이유가 정확히 이것이고, 6절의 역방향 표현식 인덱스는 그 역순 사전을 DB에 만드는 것이다.

성씨 순 출석부

출석부는 성씨 순으로 정렬돼 있다. "김씨 학생"은 김씨 페이지만 보면 되지만, "이름 가운데 글자에 '지'가 들어간 학생"은 1번부터 끝번까지 전부 읽어야 한다. 김지훈·박지수·최민지는 명부에서 서로 멀리 떨어져 있다.

정렬이 존재해도 정렬의 기준이 내가 묻는 것과 다르면 아무 소용이 없다는 것 — 이것이 중간 일치 문제의 전부다.

2. 정확히 말하면 "인덱스를 못 쓴다"가 아니라 "인덱스로 탐색(seek)을 못 한다"

면접에서 한 단계 정밀하게 말할 지점이다. 용어를 먼저 갈라 둔다.

탐색 (seek)
정렬을 이용해 시작점으로 곧장 내려간 뒤 필요한 구간만 읽는 것. B-tree의 존재 이유이자 로그 시간의 근거.
훑기 (scan)
처음부터 끝까지 전부 읽으며 하나씩 조건에 맞는지 확인하는 것. 대상이 힙이면 Seq Scan, 인덱스면 "인덱스 풀스캔".

LIKE '%kw%'도 인덱스를 읽을 수는 있다. 조회 컬럼이 인덱스 안에 다 있으면(커버링) 플래너는 힙 대신 인덱스 전체를 순서대로 훑는 쪽을 고를 수 있다 — 인덱스가 힙보다 작으면 훑는 양이 줄기 때문이다. PostgreSQL에는 "인덱스 풀스캔"이라는 별도 노드가 없고, Index Cond 없이 Filter만 붙은 Index Only Scan이 그 모습이다.

SQL (title, id) 인덱스가 있고 SELECT 컬럼이 id, title 뿐일 때
SELECT id, title FROM webtoons WHERE title LIKE '%나무%';
EXPLAIN 인덱스를 "읽었지만" 시작점은 못 찍은 계획
 Index Only Scan using idx_webtoons_title_id on webtoons  (actual rows=312 loops=1)
   Filter: (title ~~ '%나무%'::text)      Index Cond가 없다 = 시작점 없이 인덱스 전체를 순서대로 훑었다
   Rows Removed by Filter: 499688         50만 엔트리를 읽고 거의 다 버림
   Heap Fetches: 0                        visibility map 덕에 힙은 안 갔다
   Buffers: shared hit=2731               인덱스 페이지 전부

판별식 — 계획에서 Index Cond가 있느냐 없느냐

Index Cond 있음→시작점을 찍었다 = seek·Filter만 있음→시작점이 없다 = 훑기

Rows Removed by Filter가 테이블 행 수에 육박하면 확정이다. 커버링으로 얻는 것은 상수배 개선이지 선형을 로그로 바꾸는 개선이 아니다 — 데이터가 10배 되면 여전히 10배 느려진다.

MySQL 대조 같은 상황이 MySQL에서는 type: index, Extra: Using where; Using index로 찍힌다. 표기만 다르고 뜻은 같다 — "인덱스를 읽긴 했으나 시작점은 못 찍었다".

3. 비용 사슬 — 풀스캔은 데이터 증가에 선형이다

"느려진다", "부하가 온다"에서 멈추면 절반이다. 단계마다 이름을 붙여 사슬로 말해야 "왜 지금은 안 느린데 나중에 장애가 되는가"까지 설명할 수 있다.

그리고 그 사이 어느 날 — 배포도 없이 — 임계를 넘는다. 이게 "배포 없었는데 DB CPU가 올랐다" 문항의 전형적 정답 중 하나(데이터 증가 자체가 변경)다.

검색 기능의 진짜 비용은 오늘의 응답 시간이 아니라 기울기로 산정한다

4. 그럼 LIKE 'kw%'는 왜 타는가 — 그리고 PG에서 그마저 안 타는 네 경우

접두 일치는 플래너가 범위 조건으로 바꿔 처리한다: title LIKE '나무%' ≡ title >= '나무' AND title < '나묵' ('나묵'은 '나무'의 마지막 글자를 하나 올린 값 — 플래너가 계산한다). 그런데 이 변환이 성립하려면 인덱스의 정렬 순서에서 "같은 접두사를 가진 문자열이 연속 구간을 이룬다"가 보장돼야 한다. PostgreSQL의 함정이 정확히 여기 있다.

접두 LIKE조차 인덱스를 못 타는 네 경우 — 암기 고리 "콜 · 함 · 선 · 와"

① 콜레이션② 함수 · ILIKE③ 선택도④ 와일드카드 입력

PG에서는 ①이 압도적으로 흔하다. ②③④는 풀스캔 원인 6종에서 그대로 도출되는 것들이라 ①만 새로 외우면 된다.

4-1. ① collation — PG 고유이자 가장 먼저 만나는 함정 함정

collation(콜레이션)은 문자열을 어떤 순서로 정렬할지 정하는 규칙이다. DB 기본 collation이 en_US.UTF-8·ko_KR.UTF-8 같은 로케일 collation이면(대부분의 관리형 PG가 그렇다 — SHOW lc_collate로 확인) 정렬이 바이트 순이 아니라 로케일 규칙(공백·기호·대소문자를 뒤 단계에서 비교하는 등)을 따른다. 그 순서에서는 접두사 연속성이 보장되지 않으므로 플래너는 변환을 아예 하지 않는다 — 일반 B-tree는 접두 LIKE에도 Seq Scan이다.

before 기본 collation 컬럼의 일반 B-tree
CREATE INDEX idx_webtoons_title ON webtoons (title);

EXPLAIN SELECT id, title FROM webtoons
WHERE title LIKE '나무%';

-- 접두 일치인데도 …
 Seq Scan on webtoons
   Filter: (title ~~ '나무%'::text)  변환 자체를 포기

-- 로케일 정렬에서는 "같은 접두사 = 연속 구간"이
--   보장되지 않으므로 범위로 못 바꾼다
after text_pattern_ops — 바이트 순 비교 인덱스
CREATE INDEX idx_webtoons_title_pattern
  ON webtoons (title text_pattern_ops);

-- 쿼리는 한 글자도 바꾸지 않는다
 Index Scan using idx_webtoons_title_pattern
   Index Cond: ((title ~>=~ '나무'::text)
            AND (title ~<~ '나묵'::text))  범위로 변환됨
   Filter: (title ~~ '나무%'::text)   재확인용으로 남는다
대가도 같이 말한다 — text_pattern_ops 인덱스는 만능이 아니다 이 인덱스는 <·>·ORDER BY title 같은 일반 비교에는 쓰이지 않는다(등호는 된다). 둘 다 필요하면 인덱스를 둘 유지해야 하고, 그만큼 쓰기 비용과 저장 공간이 늘어난다. 컬럼이나 DB 자체를 COLLATE "C"로 두는 선택지도 있지만 정렬 결과가 달라지므로 화면 정렬 요구와 충돌하지 않는지 먼저 본다.
MySQL 대조 — "MySQL에선 됐는데요"의 정체 MySQL은 일반 인덱스로 접두 LIKE가 바로 type: range다. MySQL에서 옮겨온 팀이 "인덱스 걸었는데 LIKE가 안 탄다"로 처음 부딪히는 것이 대개 이 collation 함정이다.

4-2. 나머지 셋 — 함수·ILIKE / 선택도 / 와일드카드 입력

② 함수 · ILIKE 컬럼에 함수를 씌우면 원본 값이 정렬된 인덱스와 무관해진다
-- before: lower()로 감싼 컬럼, 그리고 ILIKE
SELECT * FROM webtoons WHERE lower(title) LIKE 'solo%';
SELECT * FROM webtoons WHERE title ILIKE 'solo%';   ILIKE는 text_pattern_ops로도 B-tree 탐색 불가

-- after: PG의 정석은 표현식 인덱스 — 함수를 WHERE가 아니라 "인덱스 쪽"에 미리 적용한다
CREATE INDEX idx_webtoons_title_lower ON webtoons (lower(title) text_pattern_ops);
SELECT * FROM webtoons WHERE lower(title) LIKE lower('Solo') || '%';
③ 선택도 플래너가 "일부러" 안 타는 경우 — 이건 옳은 판단이다
-- '가%'가 전체의 30%면 인덱스로 300만 행의 TID를 얻어 힙을 랜덤 접근하느니
--   순차로 훑는 게 싸다. 그래서 자동완성은 "최소 2글자부터"라는 UX 제약을 둔다.
SELECT * FROM webtoons WHERE title LIKE '가%';
④ 와일드카드 입력 코드는 접두처럼 보이는데 실행은 중간 일치
String kw = request.getKeyword();               // 사용자가 "%나무"를 입력했다
query.setParameter("kw", kw + "%");             → '%나무%' 로 바인딩되어 접두 일치가 깨진다

// 대응: %, _, \ 를 이스케이프하거나 제거하고 바인딩한다 (LIKE 와일드카드 인젝션 방지)
String safe = kw.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_");
// SQL 쪽에서는  ... LIKE :kw || '%' ESCAPE '\'  로 이스케이프 문자를 명시한다
가산점 포인트 — 준비문(prepared statement)과 제네릭 계획 가산점 접두 LIKE의 범위 변환은 패턴 상수를 계획 시점에 알아야 상한('나묵')을 만들 수 있다. pgjdbc가 반복 실행 문장을 서버 준비문으로 바꾸고 서버가 제네릭 계획으로 넘어가면 패턴이 $1이라 변환이 불가능하다. 다행히 플래너가 제네릭(Seq Scan) 비용이 커스텀 계획보다 훨씬 크다고 보고 대개 커스텀을 유지하지만, 잘 타던 접두 검색이 어느 날 Seq Scan으로 급변했다면 이 축을 의심하고 plan_cache_mode = force_custom_plan으로 고정한다.

5. 층위를 가르는 축 — "인덱스에 무엇을 키로 넣는가"

네 층위를 그냥 "약한 것부터 센 것" 순서로 외우면 왜 그 순서인지가 안 남는다. 층위를 가르는 축은 하나다 — 인덱스에 무엇을 키로 넣는가.

네 층위 3초 암기 — 통 · 조각 · 단어 · 엔진

통 (값 전체)→조각 (3글자)→단어 (lexeme)→엔진 (전부 위임)

네 글자만 기억하면 도구 이름(B-tree · pg_trgm · tsvector · ES)과 각 층의 한계가 따라 나온다. 면접에서 "네 층위가 있고요"로 시작하는 것과 "pg_trgm 쓰면 됩니다"로 시작하는 것의 차이가 여기서 갈린다.

6. 층위 ① — B-tree 안에서 버티는 우회 5가지

"pg_trgm이나 ES로 가야죠"로 바로 점프하면 중간 선택지가 없는 사람으로 보인다. 도구를 바꾸기 전에 B-tree 안에서 할 수 있는 다섯 가지를 번호로 꺼내고, 각각 "어떤 요구까지 커버하고 무엇을 못 하는지"를 붙인다.

우회 5종 암기 고리 — 협상 · 역순 · 정규화 · 토큰 · 선행필터

① 협상② 역순③ 정규화④ 토큰⑤ 선행필터

①은 요구를 바꾸는 것, ②③은 인덱스에 넣는 "식"을 바꾸는 것, ④는 역색인을 손으로 만드는 것, ⑤는 스캔할 구간 자체를 좁히는 것이다. 넷째 칸까지 오면 이미 pg_trgm이 대신해 줄 일을 손으로 하고 있다는 신호다.

다섯 우회 — 커버 범위와 대가를 짝으로 말한다
#우회커버하는 요구대가 / 한계
①요구를 접두 일치로 협상
(+ text_pattern_ops)		자동완성, "작품명이 ~로 시작"UX 변경을 기획과 합의해야 함. 그 인덱스는 ORDER BY title엔 못 씀
②역방향 표현식 인덱스 reverse(title)접미 일치(%나무)인덱스 하나 추가, 쿼리가 같은 식을 써야 함(JPQL 불가), 중간 일치는 여전히 불가
③정규화 표현식 인덱스 / 생성 컬럼공백·대소문자·특수문자를 무시한 접두 일치정규화 규칙을 한 곳에 고정해야 함 (DB와 앱 양쪽에 두면 조용히 어긋난다)
④자체 n-gram 토큰 테이블중간 일치 — 2글자 검색어 포함쓰기마다 토큰 재생성, 저장량 수 배 — PG에선 pg_trgm이 대신하므로 2글자가 핵심일 때만
⑤선행 필터로 스캔 폭 축소필터 조건이 함께 오는 중간 일치필터가 좁을 때만 의미. 전역 검색엔 무력

6-1. 우회 ① 요구를 접두 일치로 바꾼다 — 가장 싼 해법은 요구를 바꾸는 것

"작품 검색"이라는 요구의 실제 UX가 검색창에 타이핑하면 후보가 뜨는 자동완성이라면, 그건 접두 일치로 충분한 경우가 많다. 기획자에게 "중간 글자로도 찾아야 하나요?"를 먼저 묻는 것이 백엔드의 일이다. "요구의 숨은 비용을 산정"의 첫 단계가 요구를 되묻기다.

good 자동완성: 접두 일치 + 인기순 — text_pattern_ops 인덱스로 seek 후 상위 N만
SELECT id, title FROM webtoons
WHERE title LIKE '나무%'
ORDER BY view_count DESC
LIMIT 10;

 Limit
   ->  Sort  Sort Key: view_count DESC  Sort Method: top-N heapsort  Memory: 25kB
         ->  Index Scan using idx_webtoons_title_pattern on webtoons  (actual rows=38)
               Index Cond: ((title ~>=~ '나무') AND (title ~<~ '나묵'))
               Filter: (title ~~ '나무%'::text)

-- 구간이 좁으면(38행) Sort 비용도 작다.
-- 구간이 넓은 한 글자 접두('가%')는 최소 2글자부터 검색하도록 UX에서 막는다.

6-2. 우회 ② 역방향 표현식 인덱스 — 역순 사전을 만든다

접미 일치(%나무: "…나무"로 끝나는 작품)가 진짜 요구라면 뒤집은 값에 인덱스를 건다. 뒤집으면 접미가 접두가 되기 때문이다. PostgreSQL은 표현식 인덱스가 있어 컬럼을 추가하지 않고 "식" 자체에 인덱스를 걸 수 있다 — "이 컬럼을 정렬해 두겠다"가 아니라 "이 컬럼에 이 함수를 적용한 결과를 정렬해 두겠다"고 선언하는 것이다.

good 컬럼 추가 없이 "식"에 인덱스 — 테이블 구조도 애플리케이션 코드도 그대로
CREATE INDEX idx_webtoons_title_rev ON webtoons (reverse(title) text_pattern_ops);

-- "…나무"로 끝나는 작품 = 뒤집으면 "무나…"로 시작하는 작품 → 접두 일치
SELECT id, title FROM webtoons
WHERE reverse(title) LIKE reverse('나무') || '%';
-- reverse('나무') || '%' 는 계획 시점에 '무나%' 상수로 접히므로 범위 변환이 된다
한계는 명확하다 접두와 접미는 되지만 중간은 여전히 안 된다. 플래너가 인덱스를 매칭하려면 쿼리가 인덱스 정의와 글자 하나까지 같은 식(reverse(title))을 써야 하므로 JPQL로는 못 쓰고 네이티브 쿼리가 된다. 쓰기마다 식을 한 번 더 계산하고 인덱스도 하나 더 유지한다. 뒤집은 값 자체를 SELECT로 봐야 한다면 생성 컬럼(GENERATED ALWAYS AS (reverse(title)) STORED)에 인덱스를 거는 것도 같은 효과다. 실무 빈도는 낮지만 "구조적 한계를 구조로 우회한다"는 사고를 보여주기엔 좋은 예다.

6-3. 우회 ③ 정규화 표현식 인덱스 — 함수를 WHERE가 아니라 인덱스 쪽에 미리 적용한다

"나 혼자만 레벨업"을 "나혼자만"으로 쳐도 나와야 한다, 영문 대소문자는 무시해야 한다 같은 요구는 검색 시점에 컬럼에 함수를 씌우면 인덱스가 죽는다(4-2 ②). 인덱스는 원본 값을 정렬해 둔 것인데 검색은 가공한 값을 찾으니 정렬이 쓸모없어지기 때문이다. 대신 정규화한 식에 인덱스를 걸고, 조회도 같은 식으로 한다.

기본형 표현식 인덱스 + SQL 안에서 검색어도 같은 식으로
CREATE INDEX idx_webtoons_title_norm ON webtoons
  (lower(replace(title, ' ', '')) text_pattern_ops);

SELECT id, title FROM webtoons
WHERE lower(replace(title, ' ', ''))
      LIKE lower(replace($1, ' ', '')) || '%';

-- 검색어도 SQL 안에서 같은 식으로 정규화
--   → 규칙이 DB 한 곳에만 존재한다
변형 ORM에서 식을 쓰기 불편하거나 화면에도 필요하면 생성 컬럼
ALTER TABLE webtoons
  ADD COLUMN title_norm text
  GENERATED ALWAYS AS (lower(replace(title, ' ', ''))) STORED;

CREATE INDEX idx_webtoons_title_norm
  ON webtoons (title_norm text_pattern_ops);

-- PG 12+ . 값이 실체화되므로 SELECT·ORM 매핑이 쉽다
대가 — 정규화 규칙이 두 곳에 살면 조용히 검색이 안 된다 앱에서 검색어를 전처리하는 순간 규칙이 DB(인덱스 식)와 애플리케이션(검색어 전처리) 두 곳에 존재한다. 한쪽만 바꾸면 에러 없이 결과가 0건이 된다 — 위 예처럼 검색어도 SQL 식으로 정규화해 규칙을 DB 한 곳에 두거나, 통합 테스트에 "정규화 규칙 일치" 검증을 박아 둔다(10-3절).

6-4. 우회 ④ 자체 n-gram 토큰 테이블 — 역색인을 손으로 만든다

중간 일치가 꼭 필요한데 확장을 설치할 수 없는 환경이거나 2글자 검색어가 핵심이라면(7절의 pg_trgm은 3글자 조각이라 2글자 검색어에 무력하다), 제목을 2글자 조각(bigram)으로 쪼개 별도 테이블에 저장하고 검색어도 같은 방식으로 쪼개 등호 조회의 교집합으로 찾는다. 이것이 pg_trgm GIN이 내부에서 하는 일의 축소판이라 원리 이해에도 좋다.

SQL 토큰 테이블 — token 기준 정렬(PK) → 등호 조회는 seek
CREATE TABLE webtoon_title_tokens (
  token      text   NOT NULL,      -- 2글자 조각
  webtoon_id bigint NOT NULL REFERENCES webtoons (id),
  PRIMARY KEY (token, webtoon_id)
);
-- "사과나무 아래"(id=7) 저장 시 → ('사과',7) ('과나',7) ('나무',7) ('무아',7)* ('아래',7)
--   * 공백 처리 규칙은 정규화 식과 마찬가지로 한 곳에 고정한다

-- 검색어 "과나무" → 토큰 '과나', '나무' 를 모두 가진 작품
SELECT webtoon_id
FROM webtoon_title_tokens
WHERE token IN ('과나', '나무')            두 개의 짧은 등호 구간 = seek
GROUP BY webtoon_id
HAVING count(DISTINCT token) = 2;          -- 집계 후 필터 = HAVING

얻는 것

  • 중간 일치가 seek이 된다
  • 어떤 RDB에서도 된다 (확장 불필요)
  • 2글자 검색어도 된다 — pg_trgm이 못 하는 자리

치르는 것 셋

  • ⑴ 제목 한 번 바꾸면 토큰 행을 지우고 다시 넣어야 한다 — 같은 트랜잭션에서 하지 않으면 검색 결과와 실제 제목이 어긋난다(PG라면 트리거로 묶는 것이 정석)
  • ⑵ 저장량이 제목 길이만큼 행이 생겨 수 배
  • ⑶ bigram 교집합은 순서를 보장하지 않는다 — '과나'·'나무'를 다 가진 "나무과나"도 매치되므로 후보 id로 원본을 읽어 LIKE '%과나무%' 2차 검증이 필요하다
그리고 이 지점이 바로 "확장으로 넘어갈 시점"의 신호다 7절에서 보겠지만 pg_trgm은 이 2차 검증까지 Recheck Cond로 자동 수행한다. 이 정도로 손이 가기 시작하면 "확장이 이걸 대신 해 준다"로 넘어갈 때다.

6-5. 우회 ⑤ 선행 필터로 스캔 폭 축소 — LIKE를 액세스 조건이 아니라 필터 조건으로 격하

검색이 항상 다른 좁은 조건과 함께 온다면(장르 페이지 안에서 검색, 특정 작가의 작품 중 검색), 그 조건을 선두로 한 복합 인덱스로 구간을 먼저 좁히고 그 안에서 LIKE는 필터로만 쓴다. 복합 인덱스 컬럼 순서의 "뒤 컬럼은 탐색용이 아니라 제거용" 원칙 그대로다.

good author_id 등호로 seek → 그 작가의 작품 수십 건 안에서만 LIKE 평가
CREATE INDEX idx_webtoons_author_title ON webtoons (author_id, title);

SELECT id, title FROM webtoons
WHERE author_id = 1024 AND title LIKE '%나무%';

 Index Scan using idx_webtoons_author_title on webtoons  (actual rows=3)
   Index Cond: (author_id = 1024)               구간을 좁힌 조건 (액세스)
   Filter: (title ~~ '%나무%'::text)             좁힌 구간 안에서 제거용
   Rows Removed by Filter: 41
한계 — 전역 검색에는 무력하다 genre = 'ROMANCE'처럼 전체의 30%를 남기는 필터는 스캔 폭을 별로 줄이지 못한다. 말할 때 "필터가 충분히 좁을 때만"이라는 조건을 반드시 붙인다.

7. 층위 ② — pg_trgm + GIN: 포함 검색을 "조각들의 등호 조회"로 바꾼다

이 문서의 전환점이다. 여기서 문제의 모양 자체가 바뀐다.

7-1. 먼저 GIN — "값 하나가 키를 여럿 갖는 경우"를 위한 인덱스

B-tree의 전제 — 행 하나 = 키 하나

title이 "사과나무 아래"인 행은 그 문자열 하나를 키로 갖고, 그 키로 정렬된다. 그래서 정렬 기준과 검색 조건이 어긋나면(1절) 손쓸 방법이 없다.

역색인의 전제 — 행 하나가 키를 여럿

키마다 그 키를 가진 행들의 목록을 매단다. 책 뒤 찾아보기에서 "나무 …… 12, 87, 203쪽"을 보고 바로 그 쪽으로 가는 것과 같다. "색인 → 본문"이 아니라 "본문의 조각 → 그 조각이 나오는 위치"라 거꾸로 된 색인이라는 이름이 붙었다.

PostgreSQL에서 이 구조를 구현한 인덱스 종류가 GIN(Generalized Inverted iNdex, 일반화된 역색인)이다. "일반화"가 붙은 이유는 "값을 어떻게 여러 키로 쪼갤 것인가"를 GIN 자신이 정하지 않기 때문이다. 쪼개는 방법은 연산자 클래스가 가르쳐 준다 — 배열이면 원소로, jsonb면 키·값으로, 그리고 문자열이면 pg_trgm이 "3글자씩"을 가르쳐 준다.

값을 미리 조각으로 쪼개 저장해 두면, 검색어가 값의 어느 위치에 있든 조각 하나를 등호로 찾으면 된다
— "중간 일치"라는 문제 자체가 "조각들의 등호 조회"로 바뀌어 사라진다

7-2. 어떻게 쪼개나 — 트라이그램(3글자 조각)

pg_trgm은 문자열을 3글자씩 한 칸씩 밀며 잘라 낸다. 자르기 전에 단어 앞에 공백 2개, 뒤에 공백 1개를 붙이는데, 이 패딩 덕분에 "단어의 시작"과 "단어의 끝"이라는 정보까지 조각에 담긴다.

7-3. 사용법 — 쿼리는 LIKE 그대로, 인덱스만 붙인다

good 확장 + GIN 인덱스 (운영 테이블이면 CONCURRENTLY)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX CONCURRENTLY idx_webtoons_title_trgm  ON webtoons USING gin (title gin_trgm_ops);
CREATE INDEX CONCURRENTLY idx_webtoons_author_trgm ON webtoons USING gin (author_name gin_trgm_ops);

-- 쿼리는 그대로. 애플리케이션 코드 수정 없음
SELECT id, title FROM webtoons WHERE title LIKE '%사과나무%';
EXPLAIN 계획이 이렇게 바뀐다
 Bitmap Heap Scan on webtoons  (actual rows=4 loops=1)
   Recheck Cond: (title ~~ '%사과나무%'::text)   조각 교집합 후보를 원문으로 2차 검증
   Rows Removed by Index Recheck: 1
   Heap Blocks: exact=5
   ->  Bitmap Index Scan on idx_webtoons_title_trgm  (actual rows=5 loops=1)
         Index Cond: (title ~~ '%사과나무%'::text)  패턴에서 뽑은 '사과나','과나무'를 가진 행의 TID 비트맵
보너스 같은 인덱스로 유사도 검색까지 — 오타를 일부 흡수한다
-- % 연산자: 공유하는 트라이그램 비율로 "비슷한" 값을 찾는다 (임계값 pg_trgm.similarity_threshold, 기본 0.3)
SELECT id, title, similarity(title, '사과나무') AS sim
FROM webtoons
WHERE title % '사과나무'
ORDER BY sim DESC LIMIT 20;

-- "가장 비슷한 N개"를 인덱스로 바로 뽑으려면 GiST + <-> (KNN 정렬). GIN은 정렬을 못 돕는다
CREATE INDEX idx_webtoons_title_trgm_gist ON webtoons USING gist (title gist_trgm_ops);
SELECT id, title FROM webtoons ORDER BY title <-> '사과나무' LIMIT 20;

GIN이냐 GiST냐 — 한 줄로 가른다

"포함 여부"만 필요 → GIN (조회가 빠르다) "비슷한 순서로 N개" 필요 → GiST (구축·갱신이 가볍고 <-> 정렬을 인덱스로 처리)

7-4. 한국어와 트라이그램 — 되는 것과 막히는 것

한국어에서 오히려 편한 점

  • 조사 문제가 자연히 사라진다 — "나무를"·"나무가"·"나무에서"에 '나무'가 그대로 들어 있으니 부분 문자열 일치로 다 걸린다
  • 띄어쓰기 없는 제목도 된다 — "나혼자만레벨업"을 '레벨업'으로 찾는다
  • 대소문자는 기본으로 무시한다 (ILIKE도 같은 인덱스)

막히는 곳 — 같은 호흡으로 말한다

  • 3글자 미만 검색어에 무력 — 한국어에서 가장 아픈 한계
  • 의미를 모른다 — '과나' 같은 무의미 조각도 전부 색인 → 색인 크기가 크게 불어난다
  • 관련도 순위가 없다 — 결과는 "포함 여부"뿐, 부스팅을 조합할 수단이 없다
  • 형태소 분석이 없다 — "달리기"와 "달렸다"를 못 묶고, 동의어·초성 검색은 영역 밖
MySQL 대조 — 여기서는 MySQL이 유리하다 InnoDB FULLTEXT의 ngram 파서는 ngram_token_size 기본 2 — 2글자 검색어가 되는 대신 색인이 더 크고 MATCH ... AGAINST 전용 문법을 써야 한다. PG 트라이그램은 3글자라 한국어 2글자 검색어에서 뚜렷이 불리하고, 대신 LIKE 문법 그대로 인덱스가 붙는다.

7-5. pg_trgm의 대가 — 쓰 · 크 · 결 · 조

"pg_trgm 걸면 됩니다"로 끝내면 한쪽 면만 본 것이다. 얻는 것(중간 일치가 조각 조회로)과 치르는 것 네 가지를 한 호흡에 붙인다.

대가 4종 암기 고리 — 쓰기 · 크기 · 결합 · 조인

① 쓰기 (pending list)② 크기③ 결합 — 필터는 OK, 정렬이 문제④ 조인 결과엔 못 건다
1
쓰기 비용 — pending list라는 완충 장치와 톱니 패턴 가산점

행 하나 INSERT/UPDATE에 트라이그램 수만큼 GIN 항목이 생긴다. PG의 GIN은 이를 곧바로 트리에 꽂지 않고 pending list(대기 목록)에 쌓았다가(fastupdate, 기본 on) 한도(gin_pending_list_limit, 기본 4MB)를 넘거나 (auto)VACUUM이 돌 때 본 트리에 병합한다 — 조각이 많으니 매번 트리에 꽂으면 쓰기가 너무 느려지기 때문이다.

그 사이 검색은 pending list까지 훑어야 하므로, 갱신 폭주 뒤 검색이 느려졌다가 VACUUM 후 회복하는 톱니 패턴이 생긴다(gin_clean_pending_list()로 수동 병합 가능). 반영 시점 자체는 일반 인덱스와 같아 같은 트랜잭션에서 방금 넣은 행도 바로 검색된다. 그리고 title 갱신은 인덱스 컬럼 변경이라 HOT에서 탈락 → 그 테이블의 모든 인덱스에 새 엔트리를 꽂는다.

2
크기 — 원본 컬럼보다 인덱스가 커지는 경우가 흔하다

제목 20자면 트라이그램도 20개 남짓 생긴다(글자 수 + 1). 작가명·줄거리까지 넣으면 원본보다 인덱스가 커진다. pg_size_pretty(pg_relation_size('idx_webtoons_title_trgm'))로 실측하고 shared_buffers 경쟁을 감안한다.

3
필터·정렬과의 결합 — 필터는 잘 되고, 정렬이 남는다

필터는 PG가 잘 결합한다: BitmapAnd로 GIN 후보와 B-tree 후보의 교집합을 인덱스 단계에서 만든다. 문제는 정렬이다 — ORDER BY view_count DESC LIMIT 20은 후보 전부를 Sort에 넣어야 하므로 흔한 단어의 후보가 수십만이면 여기서 다시 느려진다.

SELECT id, title FROM webtoons
WHERE title LIKE '%레벨업%' AND genre = 'ROMANCE'
ORDER BY view_count DESC LIMIT 20;

 Limit
   ->  Sort  Sort Key: view_count DESC  Sort Method: top-N heapsort
         ->  Bitmap Heap Scan on webtoons  (actual rows=48213)   '레벨업' 후보 전부가 정렬 입력
               Recheck Cond: ((title ~~ '%레벨업%') AND (genre = 'ROMANCE'))
               ->  BitmapAnd            두 인덱스의 후보 비트맵을 교집합 — 필터는 잘 결합된다
                     ->  Bitmap Index Scan on idx_webtoons_title_trgm
                     ->  Bitmap Index Scan on idx_webtoons_genre

후보가 많을수록 Sort 비용이 커진다 — 이게 9절 "전환 신호 ②"의 정체다.

4
조인 결과에는 못 건다 — 인덱스는 테이블 하나의 것이다

같은 테이블의 여러 컬럼은 컬럼별 인덱스 + OR(BitmapOr)로 되지만, "작품명 + 작가명 + 태그(별도 테이블) + 줄거리"를 한 번에 검색하려면 검색용 반정규화 컬럼(트리거로 유지)이나 materialized view(REFRESH MATERIALIZED VIEW CONCURRENTLY — 신선도 지연)를 만들어 거기에 걸어야 하고, 그 순간 갱신 정합성 문제가 따라온다.

7-6. pg_trgm으로 "버틸 수 있는" 조건 — 어디까지인가

수치는 하드웨어·데이터 형태에 따라 달라 팀이 실측해야 하지만, 정성적 경계는 분명하다.

왼쪽 열에 들어가면 pg_trgm으로 버티고, 오른쪽 열 조건이 하나라도 "필수 요구"로 들어오는 순간이 전환점이다
조건pg_trgm으로 버팀다음 층위 신호
대상단일 테이블, 짧은 필드(제목·이름)긴 본문 · 여러 테이블 · 태그 결합
검색어3글자 이상 포함 여부2글자가 주력 / 형태소·오타·동의어·초성 품질
결합필터는 BitmapAnd로 가능, 정렬 후보가 작음후보가 커져 Sort가 지배, 패싯(장르별 건수) 동시

신선도커밋 즉시 반영이 필요수 초 지연 허용 가능

웹툰 플랫폼의 작품명·작가명 검색은 대체로 왼쪽 열이다 짧은 필드, 단일 테이블, 수만~수십만 건. 그래서 첫 선택은 pg_trgm GIN이고, 다음이 tsvector인지 검색 엔진인지는 8·9절이 가른다.

8. 층위 ③ — tsvector + GIN 전문 검색: 글자 조각에서 "단어"로

같은 GIN 위에 올라가지만 쪼개는 단위가 글자 조각이 아니라 단어다. 이 차이 하나가 나머지 전부를 결정한다.

두 "풀텍스트 인덱스"의 차이 — 자르는 단위가 다르면 잘하는 일과 못하는 일이 통째로 갈린다
pg_trgmtsvector
쪼개는 단위3글자 조각 — 의미와 무관하게 기계적으로 자른다단어(lexeme) — 파서가 공백·구두점으로 자른 뒤 사전이 정규화한다
정규화소문자화 정도어간 추출(running → run) + 불용어 제거(the, is …)
잘 하는 일부분 문자열 · 오타 · 조사 붙은 말 — "어디든 들어 있으면 찾는다"단어 검색과 랭킹 — "이 단어가 이 문서에 얼마나 중요한가"
못 하는 일관련도 순위, 불리언 질의, 동의어단어 중간의 부분 문자열, 형태소 없는 언어(한국어)
색인 크기크다 (조각 수만큼)작다 (단어 수만큼)
어간 추출 (stemming)
"달리는"·"달렸다"·"달린" 같은 변형을 공통의 뿌리 하나로 바꾸는 처리. 그래야 어떤 형태로 검색해도 같은 단어로 걸린다.
불용어 (stop word)
"the", "은", "는"처럼 거의 모든 문서에 나와 변별력이 없는 단어. 색인에서 빼면 크기와 검색 품질이 동시에 좋아진다.
한 문장으로 — pg_trgm은 "이 글자들이 들어 있나"를 묻고, tsvector는 "이 단어를 다루는 문서인가, 그리고 얼마나 그런가"를 묻는다

8-1. 사용법 — 문서를 단어 목록(tsvector)으로, 질의를 tsquery로

good 검색 벡터를 생성 컬럼으로 실체화(PG 12+) — 컬럼별 가중치(A > B > C)
ALTER TABLE webtoons
  ADD COLUMN search_vec tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('simple', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('simple', coalesce(author_name, '')), 'B') ||
    setweight(to_tsvector('simple', coalesce(synopsis, '')), 'C')
  ) STORED;
CREATE INDEX CONCURRENTLY idx_webtoons_search_vec ON webtoons USING gin (search_vec);

-- websearch_to_tsquery 는 "사과나무 -완결" 같은 검색창 문법을 tsquery로 바꿔 준다
SELECT id, title, ts_rank(search_vec, q) AS rank
FROM webtoons, websearch_to_tsquery('simple', '사과나무 -완결') AS q
WHERE search_vec @@ q
ORDER BY rank DESC LIMIT 20;
-- 접두 매치는 to_tsquery('simple', '레벨:*'), 하이라이트는 ts_headline(...)

pg_trgm에 없던 것이 여기서 생긴다

  • 불리언 질의 — -완결 제외, 구문 검색
  • 컬럼 가중치 — 제목 A > 작가 B > 줄거리 C
  • ts_rank 관련도 점수
  • 단어 단위라 인덱스가 트라이그램보다 훨씬 작다

그래도 남는 것 — 정렬 비용

ts_rank는 인덱스가 계산해 주지 않는다. 후보 전부에 점수를 매긴 뒤 Sort이므로, 흔한 단어의 후보가 크면 7-5 대가 ③과 같은 정렬 비용이 그대로 남는다.

검색 엔진이 앞서는 지점이 정확히 여기다.

8-2. 한국어 문제 — simple 파서는 공백으로 자르고, 형태소 분석기는 내장돼 있지 않다 함정

PostgreSQL의 기본 텍스트 검색 파서는 공백·구두점으로 단어를 자른다. simple 설정은 거기에 소문자화만 하고 어간 추출·불용어 제거를 하지 않는다(english 같은 설정은 어간 추출을 한다). 영어처럼 띄어쓰기가 단어 경계인 언어를 전제한 것이라 한국어에서 두 가지가 깨진다.

① 조사·어미가 붙는다
"나무를", "나무가", "나무에서"가 전부 다른 단어로 색인된다. "나무"로 검색하면 하나도 안 걸린다.
② 띄어쓰기 없는 제목
"나혼자만레벨업"은 단어 하나다. "레벨업"으로 못 찾는다('나혼자':* 접두만 된다).

이걸 푸는 것이 형태소 분석기(문장을 의미 단위로 쪼개고 조사·어미를 떼는 도구)인데, PostgreSQL에는 한국어 분석기가 내장돼 있지 않다. 외부 확장을 직접 빌드해 붙이는 길이 있지만 관리형 PG(RDS/Aurora 등)에서는 대개 설치할 수 없다.

그래서 실무 판단은 이렇게 갈린다 — "제목은 trgm, 본문은 tsvector"

A
짧은 필드(제목·이름)의 한국어 검색은 pg_trgm에 머문다 — 부분 문자열 일치가 조사·붙여쓰기 문제를 우회해 주기 때문이다.
B
tsvector가 맞는 자리는 (a) 줄거리·댓글처럼 긴 본문에서 단어 단위로 찾을 때(트라이그램 색인은 너무 커진다), (b) 여러 컬럼에 가중치를 주고 ts_rank로 순위를 매겨야 할 때, (c) -완결 같은 불리언 질의가 필요할 때 — 조사 문제는 검색어 쪽 접두 매치('나무':*)로 일부 흡수한다.
C
둘을 같이 쓰는 것도 정상이다 — 제목은 pg_trgm, 줄거리는 tsvector. "둘 중 뭘 쓰나요"가 아니라 "어느 필드에 무엇을"이 정확한 질문이다.

9-1. 진짜 대가는 인프라가 아니라 데이터 동기화다

신호 다섯을 말했으면 대가 다섯을 같은 호흡에 붙인다. "ES 쓰면 다 해결"은 운영을 안 해 본 사람의 말이다. 그리고 그 다섯 중 무게중심은 ①(클러스터 운영)이 아니라 ②(동기화)인데, 이유가 구조적이다.

층위 ①②③에서는 색인이 같은 트랜잭션 안에서 DB가 알아서 갱신해 줬다 — 행을 넣으면 인덱스도 같이 들어가고, 롤백하면 같이 사라진다
층위 ④에서 처음으로 색인이 DB 밖에 따로 산다. 그 순간 "언제 반영되나 · 빠지면 어떻게 아나 · 다시 만들려면"이 전부 우리가 만들어야 하는 절차가 된다

도입 대가 5종 암기 고리 — 운 · 동 · 장 · 원 · 트

① 운영할 시스템 +1② 동기화·최종 일관성③ 장애 도메인 +1④ 원천이 둘로 보임⑤ 트랜잭션 모델이 다름

무게중심은 ②다. 실제로 전환 후 팀을 오래 괴롭히는 것은 클러스터 비용이 아니라 "등록했는데 검색에 안 나와요" 문의다.

1
운영할 시스템이 하나 는다 — 클러스터(노드·샤드·레플리카 설계), JVM 힙과 GC, 디스크 워터마크, 버전 업그레이드, 모니터링·알람, 그리고 담당자. 매니지드 서비스로 일부를 돈으로 바꿀 수 있지만 매핑 설계·재색인·용량 계획은 남는다.
2
데이터 동기화와 최종 일관성 — 이 항목 하나가 나머지 넷을 합친 것보다 오래 괴롭힌다
  • 이중 쓰기 금지 — 애플리케이션이 PG와 ES에 각각 쓰면 한쪽만 성공하는 순간 영구 불일치. PG 트랜잭션은 ES를 롤백해 주지 않는다.
  • 정석은 "PG 커밋을 사실의 원천으로 두고 그 변경을 흘려보내는 것" — 같은 트랜잭션에 Outbox 행을 넣고 별도 프로세스가 색인하거나, WAL 논리 디코딩을 CDC(Debezium의 pgoutput 플러그인, wal_level = logical)로 읽어 색인한다. 논리 디코딩은 복제 슬롯을 쓰므로 소비자가 멈추면 WAL이 디스크에 쌓인다 — 슬롯 지연 감시가 필수다.
  • 등록 직후 몇 초간 검색에 안 나온다(파이프라인 지연 + ES의 refresh 주기). 기획에 "검색 반영은 최대 N초 지연"을 명시적으로 합의해야 하고, 등록 화면에 "검색 반영 중" 같은 UX가 필요할 수 있다.
  • 삭제·비공개도 지연된다 — 검색엔 나오는데 클릭하면 404. 검색 결과 id로 PG 상태를 한 번 더 확인(후처리 필터)하거나 지연을 UX로 흡수한다.
  • 매핑 변경·분석기 교체 때는 전량 재색인(새 인덱스에 다시 넣고 alias 스왑)이 필요하다. 이 절차가 없으면 분석기 하나 못 바꾼다.
MySQL 대조 같은 CDC를 MySQL은 binlog로 한다. PG는 WAL 하나가 복구·복제·CDC를 겸하므로 wal_level을 logical로 올리는 것과 복제 슬롯 관리가 추가 운영 항목이다.
3
장애 도메인이 추가된다 — ES 클러스터가 red가 되면 검색이 죽는다. "검색은 비핵심이니 비활성화" / "PG pg_trgm 축소 검색 폴백" / "인기 작품 목록으로 대체" 중 무엇으로 degrade할지 미리 정해 두고 회로 차단기로 연결해야 한다. 폴백이 없으면 격리(신호 ⑤)로 얻은 것을 도로 잃는다.
4
사실의 원천이 둘로 보인다 — ES는 파생 데이터다. "언제든 PG에서 전량 재구축할 수 있다"가 성립해야 하고, 그 재구축 스크립트가 주기적으로 돌아가는지가 팀의 성숙도다.
5
트랜잭션과 정합성 모델이 다르다 — ES 검색 결과는 PG 격리 수준의 보호를 받지 않는다. 검색 결과로 뭔가를 결정(결제·권한)하면 안 되고, 검색은 "후보를 찾는" 용도로 제한하고 최종 판단은 PG에서 한다는 경계를 코드에 둔다.

10-3. 안전망을 고정하는 방법 — 문서 · 코드 · 알람

① ADR에 전환 트리거를 숫자로
"현재 pg_trgm GIN. 검색 p99 > 300ms가 1주 지속 / 요구에 형태소·오타 추가 / 검색 대상 테이블 2개 이상 → ES 검토 착수". 숫자는 팀이 정하되 정하지 않은 채로 두지 않는 것이 핵심이다 — 그래야 "언제 갈지"로 매번 감정 싸움을 안 한다.
② 코드 리뷰 규칙 + 자동 검출
"선행 % LIKE는 검색 전용 포트(SearchPort) 밖에서 금지"(포트 안의 것만 pg_trgm 인덱스가 받쳐 준다). 사람 눈만 믿지 말고 통합 테스트에서 DataSource 프록시(p6spy 등)로 실행 SQL을 잡아 포트 밖에서 LIKE '% 패턴이 나오면 테스트를 실패시킨다.
③ 풀스캔 감시 알람
pg_stat_user_tables.seq_scan·seq_tup_read가 webtoons에서 검색 QPS만큼 늘면 검색이 Seq Scan으로 돌고 있다는 뜻이다. pg_stat_statements에서 호출당 shared_blks_hit + read가 큰 쿼리를 상시 대시보드에, auto_explain으로 Filter: (title ~~ '%…%')가 붙은 Seq Scan을 로그로 잡는다. pg_stat_user_indexes.idx_scan으로 trgm 인덱스가 실제로 쓰이는지도 본다. 데이터가 자라 임계를 넘는 날을 "배포 없이도" 잡아낸다.
④ GIN 건강 감시
pg_relation_size로 인덱스 크기 추이, pgstattuple 확장의 pgstatginindex()로 pending list 크기, 해당 테이블의 autovacuum 주기. 갱신 폭주 후 검색이 느려지는 톱니를 원인째로 잡는다.
⑤ 부하 테스트에 "검색 × 데이터 N배"
현재 데이터로만 테스트하면 선형 비용은 절대 안 잡힌다. 1년 뒤 예상 건수를 채운 환경에서 검색 QPS를 건다.
⑥ 규칙 일치 테스트 · 재구축 정기 실행
표현식 인덱스의 식과 앱 전처리, 토큰 테이블과 원본이 어긋나지 않는지 CI에서 검증한다. ES 도입 후에는 전량 재구축 스크립트를 주기 작업으로 돌려 "언제든 PG에서 다시 만들 수 있다"를 말이 아니라 절차로 증명한다.

이 코드가 위험한 진짜 이유 ②

OR로 두 컬럼을 묶어 선행 필터(우회 ⑤)조차 못 붙는다. 나중에 손보려 해도 가장 싼 우회부터 막혀 있다.

검색 QPS가 오르던 어느 이벤트 날, 배포도 없이 커넥션 풀이 마르고 결제 API까지 타임아웃이 났다 — 3절의 사슬 그대로다.

11-2. 단계 2 — pg_trgm GIN + 자동완성은 접두 인덱스로 경로를 쪼갠다

마이그레이션 운영 중이므로 CONCURRENTLY (Flyway/Liquibase에선 트랜잭션 밖에서 실행)
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX CONCURRENTLY idx_webtoons_title_pattern ON webtoons (title text_pattern_ops);   자동완성용
CREATE INDEX CONCURRENTLY idx_webtoons_title_trgm    ON webtoons USING gin (title gin_trgm_ops);
CREATE INDEX CONCURRENTLY idx_webtoons_author_trgm   ON webtoons USING gin (author_name gin_trgm_ops);
after 검색 요구를 둘로 쪼갠다: 자동완성(접두, 2글자 포함) / 결과 검색(중간 일치, 3글자 이상)
public interface WebtoonSearchRepository extends JpaRepository<Webtoon, Long> {

    // 자동완성: 접두 일치 → text_pattern_ops 인덱스 seek.
    //   2글자 미만·와일드카드 문자는 컨트롤러에서 거른다
    @Query("SELECT w FROM Webtoon w WHERE w.title LIKE :prefix% ORDER BY w.viewCount DESC")
    List<Webtoon> autocomplete(@Param("prefix") String prefix, Pageable pageable);

    // 결과 검색: pg_trgm GIN — LIKE 문법 그대로, 두 인덱스는 BitmapOr로 결합.
    //   3글자 미만은 자동완성 경로로 보낸다

        SELECT * FROM webtoons
        WHERE (title ILIKE '%' || :keyword || '%' OR author_name ILIKE '%' || :keyword || '%')
          AND status = 'ONGOING'

        LIMIT :size
        """, nativeQuery = true)

}

11-3. 단계 3 — "태그로도, 줄거리로도, 오타 나도 찾게": 검색 엔진

요구가 ②③④를 한꺼번에 밟았다. 이제 PG 안에서는 답이 없다 — 여러 테이블(태그), 형태소·오타(품질), 패싯(집계). 검색을 포트 뒤로 격리하고 ES 어댑터를 붙인다.

good 검색을 포트로 격리 — 구현(pg_trgm / ES)을 바꿔도 호출부는 모른다. 폴백도 여기서
public interface WebtoonSearchPort {
    SearchResult search(SearchQuery query);   // 키워드 + 필터 + 정렬 + 패싯 요청
}

@Component
class ElasticsearchWebtoonSearchAdapter implements WebtoonSearchPort {
    private final ElasticsearchClient es;
    private final WebtoonSearchPort fallback;   pg_trgm 축소 검색 어댑터
    private final CircuitBreaker breaker;

    @Override
    public SearchResult search(SearchQuery q) {
        // nori + edge_ngram + fuzziness + 장르 패싯은 es.search 안에서.
        //   차단기가 열리면 즉시 폴백으로
        return Try.ofSupplier(breaker.decorateSupplier(() -> es.search(q)))
                  .recover(ex -> fallback.search(q.withoutFacets()))   ES 장애 시 degrade (패싯 없이)
                  .get();
    }
}

12-2. 꼬리질문 — 먼저 스스로 답하고 펼쳐서 확인한다

LIKE '나무%'는 인덱스를 탄다고 했는데, 항상 타나요? 필수힌트: 넷을 짚되 PostgreSQL에서는 첫째가 제일 흔하다

아니다. 넷을 짚는다 — 콜 · 함 · 선 · 와.

① collation이 C가 아니면 일반 B-tree로는 안 탄다. 로케일 정렬에서는 접두사 연속성이 보장되지 않아 플래너가 범위 변환 자체를 포기한다. text_pattern_ops 연산자 클래스로 인덱스를 만들거나 컬럼을 COLLATE "C"로 둔다. 계획에서 Index Cond: ((title ~>=~ '나무') AND (title ~<~ '나묵'))이 보이면 변환이 된 것이다.

② 컬럼에 함수를 씌우거나 ILIKE를 쓰면 못 탄다 — 대소문자 무시는 lower(title) 표현식 인덱스로 함수를 인덱스 쪽에 미리 적용한다.

③ 선택도가 낮으면 플래너가 일부러 안 탄다 — LIKE '가%'가 전체의 30%면 랜덤 힙 접근보다 순차 스캔이 싸다(옳은 판단이다). 그래서 자동완성은 최소 2글자부터 받는다.

④ 사용자 입력에 %·_가 섞이면 코드는 접두처럼 보여도 실행은 중간 일치가 된다 — 와일드카드를 이스케이프하거나 제거한 뒤 바인딩한다.

가산점 — 준비문(prepared statement): 범위 변환은 패턴 상수가 계획 시점에 있어야 하므로 제네릭 계획에서는 못 한다. 잘 타던 접두 검색이 급변했다면 plan_cache_mode를 의심한다.
PostgreSQL로 한국어 검색이 제대로 되나요? pg_trgm과 tsvector 중 무엇을 쓰나요? 필수힌트: "둘 중 뭘"이 아니라 "어느 필드에 무엇을"로 답한다

둘의 일치 단위가 다르다. pg_trgm은 3글자 조각의 부분 문자열 일치라 "나무를"·"나혼자만레벨업"처럼 조사가 붙거나 띄어쓰기가 없어도 찾고, LIKE 문법 그대로 인덱스가 붙는다 — 짧은 필드(제목·이름)의 한국어 검색은 여기서 오래 버틴다.

막히는 지점 넷: 2글자 검색어(패턴에서 뽑을 조각이 없어 전체 recheck로 퇴화 → 접두 경로 분리, bigram 테이블, pg_bigm), 큰 색인, 관련도 순위 없음, 형태소·동의어·초성 불가.

tsvector는 단어 단위라 인덱스가 작고 가중치·ts_rank·불리언 질의가 되지만, 기본 파서가 공백으로 자르고 한국어 형태소 분석기가 내장돼 있지 않아(관리형 PG에선 설치도 어렵다) 조사·붙여쓰기에서 깨진다 — 긴 본문(줄거리·댓글)이나 순위가 필요할 때 쓰고 제목은 pg_trgm과 병행한다.

형태소·오타·동의어·부스팅이 필수 요구로 들어오면 PG 안에는 답이 없고 검색 엔진 신호다.

ES를 도입하면 PG와의 데이터 불일치는 어떻게 다루나요? 시니어 변별힌트: "없앤다"가 아니라 "관리한다"로 전제를 깔고 원칙 넷

먼저 불일치는 없앨 수 없고 관리하는 것이라고 전제한다. 원칙 넷:

① 이중 쓰기 금지 — PG 트랜잭션은 ES를 롤백해 주지 않으니 앱이 두 곳에 직접 쓰면 영구 불일치가 생긴다.

② PG 커밋을 원천으로, 변경을 흘려보낸다 — 같은 트랜잭션의 Outbox 행 또는 WAL 논리 디코딩 CDC(Debezium pgoutput)를 인덱서가 소비. 실패해도 재시도로 따라잡는다(최종 일관성). 논리 디코딩은 복제 슬롯이 WAL을 붙잡으므로 소비자 지연을 감시한다.

③ 지연을 기획과 합의한다 — "등록 후 최대 N초", 등록 화면 UX, 삭제·비공개 작품이 검색에 남는 창은 검색 결과 id로 PG 상태를 재확인하는 후처리로 막는다.

④ 전량 재구축 절차를 정기 실행한다 — 매핑 변경·분석기 교체·유실 복구가 이 절차 하나로 수렴하고, "언제든 PG에서 다시 만들 수 있다"를 주기 작업으로 증명한다.

이 넷 중 ①②가 없으면 언젠가 "검색엔 있는데 DB엔 없는 작품"을 손으로 지우게 된다.

ES 클러스터가 죽으면 검색은 어떻게 하나요? 그럼 격리한 의미가 있나요? 시니어 변별힌트: 격리로 얻은 것이 정확히 무엇인지부터 정정한다

격리로 얻은 건 "검색이 죽어도 결제는 산다"이지 "검색이 안 죽는다"가 아니다. 그래서 검색 경로에 degrade 계층을 미리 설계한다 — 회로 차단기로 ES 호출을 끊고 → (a) PG pg_trgm 축소 검색(패싯·오타 없이 키워드만) (b) 인기 작품 목록으로 대체 (c) 검색 UI 비활성 + 안내 중 서비스 성격에 맞는 것으로 떨어진다.

폴백 (a)를 유지하려면 "GIN 인덱스를 ES 도입 후에도 지우지 않는다"는 결정이 따라오고, 그 쓰기 비용(pending list·HOT 탈락)이 폴백의 가격이다.

이 "장애 도메인 추가 → 폴백 설계 → 폴백 유지 비용"까지가 전환 대가의 한 묶음이고, ES 자체의 가용성은 레플리카 샤드·다중 AZ·매니지드로 올린다.

LIKE '%나무%'인데 계획에 Index Only Scan이 나옵니다. 인덱스를 탄 건가요? 가산점힌트: 판별식은 Index Cond의 유무

인덱스 풀스캔이다 — 탐색(seek)이 아니라 힙 대신 인덱스 사본을 처음부터 끝까지 훑은 것.

판별은 Index Cond의 유무다: 없고 Filter만 있으면 시작점을 못 찍은 것이고, Rows Removed by Filter가 테이블 행 수에 육박한다. 조회 컬럼이 인덱스에 다 들어 있어(커버링) 플래너가 "더 작은 쪽을 훑자"고 고른 결과이고, Heap Fetches가 작으려면 visibility map이 신선해야 한다.

힙 풀스캔보다 읽는 페이지가 적으니 빠르긴 하지만 비용은 여전히 N에 선형이고, 데이터가 10배면 10배 느려진다. 이 구분을 못 하면 "인덱스 탔는데 왜 느리죠"에서 멈춘다.

pg_trgm GIN 인덱스를 걸었는데 여전히 Seq Scan입니다. 무엇부터 봅니까? 함정힌트: 검색어 길이 → 후보 크기 → 식 일치 → 인덱스 자체 상태 순서로 좁힌다

① 검색어가 3글자 미만인가. 가장 흔하다. 양쪽 %에서 뽑히는 조각 수는 글자 수 − 2라 2글자면 0개다. 좁힐 조각이 없으니 인덱스가 아무 도움이 안 되고, 플래너는 당연히 순차 스캔을 고른다. 해결은 인덱스가 아니라 경로 분리(3글자 미만은 접두 자동완성으로).

② 후보가 너무 많은가. 흔한 조각이면 비트맵 후보가 테이블 상당 부분이 되고, 그럴 땐 순차 스캔이 실제로 더 싸다 — 플래너가 옳다. EXPLAIN (ANALYZE, BUFFERS)로 후보 수를 먼저 확인한다.

③ 인덱스의 식과 쿼리의 식이 다른가. 인덱스는 title에 걸었는데 쿼리가 lower(title) LIKE …이면 다른 것이다. 정규화를 쓸 거면 표현식 GIN 인덱스로 같은 식에 걸어야 한다.

④ 연산자 클래스를 빠뜨렸는가. USING gin (title)이 아니라 USING gin (title gin_trgm_ops)여야 트라이그램으로 쪼갠다. "GIN을 걸었다"와 "trgm으로 걸었다"는 다르다.

⑤ 인덱스가 유효한가. CREATE INDEX CONCURRENTLY가 중간에 실패하면 사용 불가 상태의 인덱스가 남는다 — pg_index.indisvalid를 확인하고 DROP 후 재생성한다. 마지막으로 통계(ANALYZE)도 본다.

"검색 결과를 인기순으로 정렬해 주세요"가 왜 어려운 요구인가요? 시니어 변별힌트: 인덱스가 답을 찾아 주는 것과 순서를 정해 주는 것은 다른 일이다

GIN은 항상 비트맵 스캔으로만 읽히기 때문에 결과의 순서를 인덱스가 정해 줄 수 없다. 그래서 ORDER BY view_count DESC LIMIT 20은 매치된 후보 전부를 Sort에 넣은 뒤 상위 20개를 고른다. Sort Method: top-N heapsort는 메모리를 아낄 뿐 입력 크기는 그대로다.

즉 "찾는 비용"은 인덱스가 줄여 줬는데 "줄 세우는 비용"이 남는다. 흔한 단어의 후보가 수만~수십만이면 여기서 다시 느려진다 — 이게 검색 엔진 전환 신호 ②의 실제 얼굴이다.

순서대로 시도할 것: ⑴ 후보를 줄인다(최소 검색어 길이, 연재상태·장르 등 함께 오는 필터를 BitmapAnd로 결합) ⑵ 유사도 순서면 GiST + <-> KNN으로 "가장 비슷한 N개"를 인덱스가 뽑게 한다 ⑶ 여기에 패싯(장르별 건수)까지 얹히면 후보 전체를 매번 집계해야 하므로 층위 ④의 영역이다.

검색어에 사용자가 %나 _를 넣으면 어떻게 되나요? 함정힌트: 성능 사고와 보안 사고가 같은 원인에서 나온다

LIKE 와일드카드 인젝션이다. %는 임의 문자열, _는 임의 한 글자를 뜻하므로 사용자가 패턴 자체를 조작할 수 있다.

성능 쪽: '나무' + '%'로 접두 검색을 하려던 코드에 사용자가 "%나무"를 넣으면 바인딩 값이 '%나무%'가 되어 접두 일치가 깨지고 풀스캔이 된다. 검색어를 "%" 하나로 보내면 전 행 매치다.

보안·정확성 쪽: 의도한 것보다 훨씬 넓은 범위의 데이터가 매치되므로, 검색 결과가 권한 필터와 엮여 있으면 노출 범위가 넓어질 수 있다.

대응: 바인딩 전에 \, %, _를 이스케이프하거나 제거하고, SQL에는 LIKE :kw || '%' ESCAPE '\'처럼 이스케이프 문자를 명시한다. 여기에 최소 검색어 길이와 결과 상한(LIMIT)을 함께 둔다. 프리페어드 스테이트먼트는 SQL 인젝션은 막지만 와일드카드 인젝션은 막지 못한다는 점이 핵심이다.

격리만 필요하면 레플리카로 검색을 보내면 되지 않나요? 가산점힌트: 5개 신호 중 어느 것을 풀고 어느 것을 못 푸는지로 답한다

맞다. 신호 ⑤(격리)만 문제라면 좋은 중간 선택지다. 검색 쿼리를 hot standby 스트리밍 복제 레플리카로 보내면 OLTP 보호는 되고, GIN 인덱스는 물리 복제로 그대로 따라간다(색인을 따로 만들 필요가 없다).

다만 못 푸는 것이 있다. 신호 ①(품질)은 전혀 풀리지 않는다 — 레플리카에서 돌아도 pg_trgm은 여전히 형태소·동의어·부스팅을 모른다. ②(정렬·패싯)와 ③(다중 소스)도 그대로다. 즉 "같은 한계를 다른 서버에서 겪는 것"이다.

추가로 생기는 문제: 긴 검색 쿼리가 복제 충돌로 레플리카에서 취소되거나, 이를 막으려 hot_standby_feedback을 켜면 프라이머리의 정리(VACUUM)가 지연돼 bloat가 생긴다. "검색이 프라이머리를 다시 아프게 하는 경로"가 열리는 셈이라, 이 옵션의 대가로 반드시 같이 말해야 한다.

자동완성에 최소 글자 수 제한을 두는 이유를 세 가지로 말해보세요.힌트: 선택도 · 정렬 · 트라이그램 — 세 이유가 서로 다른 층위에서 온다

① 선택도 — 한 글자 접두('가%')는 전체의 큰 비율을 남기므로 플래너가 인덱스를 버리고 순차 스캔을 고른다(그게 옳다). 구간이 넓으면 인덱스가 있어도 의미가 없다.

② 정렬 비용 — 접두 구간이 넓으면 ORDER BY view_count DESC LIMIT 10의 Sort 입력이 커진다. 인덱스로 구간을 좁혀야 Sort도 같이 싸진다.

③ 트라이그램 규칙 — 결과 검색을 pg_trgm으로 받는다면 3글자 미만은 조각이 안 나와 무력하다. 그래서 실무에서는 "2글자까지는 접두(자동완성) 경로, 3글자부터 중간 일치 경로"로 글자 수에 따라 경로 자체를 나눈다.

이 답이 좋은 이유는 UX 제약처럼 보이는 규칙이 실행 계획·정렬 비용·색인 구조라는 세 근거에서 나왔음을 보여주기 때문이다 — "기획과 협상하는 근거"가 감이 아니라 계획서에 있다.

MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 접두 · 도구 · 반영 시점 · 필터 결합 · 계획 표기

다섯 지점이다.

① 접두 LIKE — MySQL은 일반 인덱스로 바로 type: range지만, PG는 collation이 C가 아니면 안 타서 text_pattern_ops가 필요하다.

② 중간 일치 도구 — MySQL은 FULLTEXT + ngram 파서와 MATCH ... AGAINST 전용 문법(코드 변경)이고, PG는 pg_trgm으로 LIKE '%kw%' 문법 그대로(코드 무변경). 대신 ngram은 기본 2글자, 트라이그램은 3글자라 한국어 2글자 검색어는 MySQL이 유리하다.

③ 반영 시점 — InnoDB FULLTEXT는 커밋 시 토큰화라 같은 트랜잭션에서 안 보이고 삭제는 OPTIMIZE TABLE로 정리하지만, PG GIN은 일반 인덱스처럼 즉시 보이는 대신 pending list와 VACUUM이 따라온다.

④ 필터 결합 — MySQL은 테이블당 인덱스 하나라 FULLTEXT 후보에 나머지는 필터·filesort지만, PG는 BitmapAnd/BitmapOr로 인덱스 여럿을 결합하고 정렬만 남는다.

⑤ 계획 읽기 — MySQL의 type: index / type: fulltext가 PG에서는 "Index Cond 없는 Index Only Scan"과 "Bitmap Index Scan + Recheck Cond"다. 이 다섯을 짚으면 "LIKE는 안 탄다" 암기가 아니라 "저장 구조에서 도출"로 들린다.

한 줄 요약
B-tree 인덱스는 첫 글자부터 정렬된 사전이라 LIKE '%kw%'는 트리를 내려갈 시작점을 찍을 수 없어(seek 불가) Seq Scan + Filter로 전부 훑고, 그 비용은 행 수에 선형이라 QPS와 곱해져 커넥션 풀을 말리며 조용히 자란다. 층위를 가르는 축은 "인덱스에 무엇을 키로 넣는가"다 — ① 값 전체를 그대로 넣는 B-tree 안에서 버티기(요구 협상, PG는 text_pattern_ops 필수 / 역순·정규화 표현식 인덱스 / 자체 토큰 테이블 / 선행 필터) → ② 3글자 조각으로 쪼개 역색인에 넣어 포함 검색을 조각들의 등호 조회로 바꾸는 pg_trgm GIN(대가: 2글자 무력 · 크기 · pending list · 순위 없음) → ③ 단어로 쪼개 어간·불용어를 정리하고 ts_rank 순위까지 주는 tsvector GIN(대가: 한국어 형태소 미내장) → ④ 형태소·오타·패싯·다중 소스·격리가 필수일 때 검색 엔진. ④의 진짜 대가는 클러스터 운영이 아니라 색인이 DB 밖에 따로 살면서 생기는 동기화 지연·유실·재색인 절차이고, 그것이 "검색 기능 추가해주세요"의 숨은 비용이다. 전환은 데이터량 · QPS · 일치 유형 · 검색어 길이 · 품질 · 결합 · 범위/신선도 · 격리 8칸을 채워 판단하고, 그 트리거를 ADR에 숫자로 박아 둔다.
