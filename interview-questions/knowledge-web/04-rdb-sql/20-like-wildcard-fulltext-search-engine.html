LIKE '%kw%'와 검색 전환 기준
인덱스는 "왼쪽부터 정렬된 사전"이라 중간 일치는 시작점이 없다

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "LIKE '%keyword%' 검색이 인덱스를 못 타는 이유는? 풀텍스트 인덱스와 검색 엔진(Elasticsearch) 전환은 어떤 기준으로 판단하나요?"
B+Tree 인덱스는 문자열을 첫 글자부터 정렬해 둔 사전이다. LIKE '나무%'는 '나무'로 시작하는 첫 장을 펼쳐 연속 구간 하나만 읽으면 되지만, LIKE '%나무%'는 첫 글자를 모르니 트리를 내려갈 시작점을 찍을 수 없다 — 사전에서 "…나무"로 끝나는 단어를 찾으려면 첫 장부터 끝 장까지 넘겨야 하는 것과 같다. 그래서 풀스캔이고 비용은 행 수에 선형이다: 전 행 순차 읽기 + 행마다 패턴 매칭(CPU) + filesort, 이것이 QPS만큼 곱해져 커넥션 점유 시간이 늘고 풀이 마르면 검색과 무관한 기능까지 번진다. 전환 판단은 감이 아니라 데이터량 · QPS · 일치 유형 · 정확도 요구 · 필터/정렬 결합 · 신선도 · 격리 체크리스트로 하고, "무엇이 넘으면 다음 층위로 간다"를 ADR에 숫자로 박아 둔다.
1LIKE 안에서 버티기
접두 협상 · 역방향 컬럼 · 정규화 컬럼 · 자체 n-gram · 선행 필터대가: 우회마다 한계가 있고 중간 일치는 여전히 어렵다
2풀텍스트 인덱스
InnoDB FULLTEXT + ngram — 역색인으로 "중간 일치"를 "토큰 등호 조회"로대가: 색인 크기 · 쓰기 비용 · 형태소 부재 · 필터/정렬 결합 약함
3검색 엔진 (Elasticsearch)
형태소 · 오타 · 동의어 · 관련도 · 패싯 · 부하 격리가 필요할 때대가: 운영할 클러스터 · RDB와의 동기화와 최종 일관성 · 장애 도메인 추가
출제 의도 — 무엇을 보는 질문인가
"LIKE는 인덱스 못 탐"이라는 사실 확인이 아니다. 중간 일치가 인덱스 구조상 불가능함을 알고, 풀텍스트로 버틸 수 있는 규모와 검색 엔진 도입의 문턱(운영 비용, 동기화 문제)을 판단하는지 — 즉 "검색 기능 추가해주세요"라는 흔한 한 줄 요구의 숨은 비용을 산정하는 능력을 본다. 기획자가 툭 던진 요구를 받았을 때 세 층위의 비용과 한계를 양쪽 다 놓고 어디서 멈출지 결정하는 과정을 말할 수 있어야 한다.
이 페이지가 겨냥하는 약점 두 가지 — ① 비용을 "느려진다"가 아니라 이름 붙은 메커니즘 사슬로(1·2절), ② 트레이드오프를 편익만이 아니라 대가까지 같은 호흡에(각 층위마다 "얻는 것 / 치르는 것" 쌍 카드, 6절 양면 화법 템플릿). LIKE '%kw%'가 풀스캔 원인 6종 중 하나라는 사실은 index-not-used-full-scan에 있으므로 여기서는 원리의 깊이와 전환 판단에 지면을 쓴다.

1. 원리 — 왜 "시작점"이 없는가

B+Tree의 리프는 인덱스 컬럼 값 기준으로 정렬된 연결 리스트다. 문자열 컬럼이면 정렬 기준은 첫 글자, 같으면 둘째 글자, … — 사전과 정확히 같다. 아래 그림 하나로 seek와 scan의 차이를 눈에 넣는다.

같은 인덱스, 같은 리프. 차이는 딱 하나 — 루트에서 내려갈 시작점을 찍을 수 있느냐. 국어사전에 "역순 사전"이 따로 있는 이유가 이것이고, 3절의 역방향 컬럼은 그 역순 사전을 DB에 만드는 것이다.

1-1. 정밀하게 — "못 탄다"가 아니라 "탐색(seek)을 못 한다"

면접에서 한 단계 정밀하게 말할 지점
본질은 "타냐 못 타냐"가 아니라 seek(시작점 찍고 구간만) 이냐 scan(전부 읽기) 이냐다.

LIKE '%kw%'도 인덱스를 읽을 수는 있다. 조회 컬럼이 인덱스 안에 다 있으면(커버링) 옵티마이저는 테이블 대신 인덱스 전체를 순차로 훑는다 — EXPLAIN에 type: index, Extra: Using where; Using index. 테이블 풀스캔(type: ALL)보다 작은 사본을 읽으니 싸긴 하지만 상수배 개선이지 선형을 로그로 바꾸는 개선이 아니다. 데이터가 10배면 여전히 10배 느리다.

-- title 인덱스가 있고 SELECT 컬럼이 id, title 뿐이면
SELECT id, title FROM webtoons WHERE title LIKE '%나무%';
-- type: index  ← "인덱스 풀스캔". 시작점은 못 찍었고, 더 작은 사본을 처음부터 끝까지 읽은 것.
--               type 이 range/ref 가 아니라 index 면 "읽긴 했으나 seek 는 아니다"로 읽는다.

1-2. LIKE 'kw%'는 왜 타는가 — 그리고 그마저 안 타는 세 경우

접두 일치는 옵티마이저가 범위 조건으로 바꾼다: title LIKE '나무%' ≡ title >= '나무' AND title < ('나무' 접두사의 상한값). 시작점과 끝점이 있으니 seek 후 연속 구간 하나 — type: range. 다만 접두 일치도 아래 셋 중 하나면 못 탄다(모두 풀스캔 원인 6종에서 도출된다).

❌ 접두처럼 보이지만 못 타는 세 경우
-- ① 컬럼에 함수 (원인 ①): 원본 값으로 정렬된 인덱스와 무관해진다
SELECT * FROM webtoons WHERE LOWER(title) LIKE 'solo%';

-- ② 낮은 선택도 (원인 ⑥): '가%'가 전체 30%면 옵티마이저가
--    일부러 풀스캔을 고른다 — 옳은 판단
SELECT * FROM webtoons WHERE title LIKE '가%';

-- ③ 사용자 입력에 % 가 섞임: 코드는 접두, 실행은 중간 일치
String kw = request.getKeyword();      // "%나무"
query.setParameter("kw", kw + "%");    // → '%나무%'
✅ 각각의 처방
-- ① 대소문자 무시 콜레이션(_ci)이면 함수 없이도 무시된다.
--    아니면 정규화 생성 컬럼(3-3절)에 미리 적용
SELECT * FROM webtoons WHERE title LIKE 'solo%';

-- ② 한 글자 접두는 UX에서 막는다 — 자동완성은 최소 2글자부터
if (prefix.length() < 2) return List.of();

-- ③ %, _ 를 이스케이프하거나 제거하고 바인딩
--    (LIKE 와일드카드 인젝션 방지)
String safe = kw.replace("%", "\\%").replace("_", "\\_");
query.setParameter("kw", safe + "%");

2. 비용 사슬 — 풀스캔은 데이터 증가에 선형이고, 조용히 자란다

약점 ① 겨냥 — "느려진다", "부하가 온다"에서 멈추지 않는다
비용은 이름 붙은 사슬로 말한다. 특히 "왜 지금은 안 느린데 나중에 장애가 되는가"를 선형성으로 설명할 수 있어야 한다. 아래 흐름도의 박스 이름을 순서대로 말하는 것이 곧 답변이다.
위 4칸은 쿼리 한 번의 비용, 아래는 그것이 서비스로 번지는 경로. 커넥션 점유 → 풀 고갈의 세부는 connection-count-vs-throughput에 있다.

2-1. "지금은 빠른데요?"의 함정 — 오늘의 응답 시간이 아니라 기울기

작품 5천 건이면 페이지 수십 장, 전부 버퍼 풀 안이라 %kw%도 수 ms다. 문제는 이 비용이 N에 선형이라 조용히 자란다는 것. 4장 뒤쪽 "배포 없었는데 DB CPU가 올랐다" 문항의 전형적 정답 중 하나가 데이터 증가 자체가 변경이다.
말하기 템플릿 — 비용 사슬을 한 호흡에
시작점 못 찍음→전 페이지 순차 I/O→행마다 CPU 매칭→filesort→ 응답 ∝ N→× QPS→커넥션 점유 ∝ N×QPS→풀 고갈→무관 기능 대기→전체 지연

마무리 한 마디: "이 사슬은 배포 없이 데이터가 자라는 것만으로 진행되므로, 검색 기능의 진짜 비용은 오늘의 응답 시간이 아니라 기울기로 산정해야 합니다."

3. 층위 ① — LIKE 안에서 버티는 우회 5가지

"풀텍스트나 ES로 가야죠"로 바로 점프하면 중간 선택지가 없는 사람으로 보인다
도구를 바꾸기 전에 RDB 안에서 할 수 있는 다섯 가지를 번호로 꺼내고, 각각 "어떤 요구까지 커버하고 무엇을 못 하는지"를 붙인다.
암기 카드 — 우회 5종 기억 고리
협① 접두로 협상역② 역방향 컬럼정③ 정규화 컬럼토④ 자체 n-gram 토큰선⑤ 선행 필터

"협·역·정·토·선" — 가장 싼 것(요구를 바꾸기)부터 가장 손이 가는 것(수제 역색인)까지 비용 오름차순이다.

#우회커버하는 요구대가 / 한계
①요구를 접두 일치로 협상자동완성, "작품명이 ~로 시작"UX 변경을 기획과 합의해야 함
②역방향 생성 컬럼접미 일치(%나무)컬럼·인덱스 하나 추가, 중간 일치는 여전히 불가
③정규화 생성 컬럼공백·대소문자·특수문자 무시한 접두 일치앱과 DB의 정규화 규칙을 일치시켜야 함
④자체 n-gram 토큰 테이블중간 일치쓰기 시 토큰 재생성, 저장량 수 배, 직접 만든 역색인 = 풀텍스트의 수제판
⑤선행 필터로 스캔 폭 축소필터 조건이 붙는 중간 일치필터가 좁을 때만 의미, 전역 검색엔 무력

① 요구를 접두 일치로 바꾼다 — 가장 싼 해법은 요구를 바꾸는 것

"작품 검색"의 실제 UX가 타이핑하면 후보가 뜨는 자동완성이라면 접두 일치로 충분한 경우가 많다. 기획자에게 "중간 글자로도 찾아야 하나요?"를 먼저 묻는 것이 백엔드의 일이다 — 숨은 비용 산정의 첫 단계는 요구를 되묻기다.

-- ✅ 자동완성: 접두 일치 + 인기순은 (title) 인덱스로 seek 후 상위 N만
SELECT id, title FROM webtoons
WHERE title LIKE '나무%'
ORDER BY view_count DESC
LIMIT 10;
-- 구간이 좁으면 filesort 비용도 작다. 구간이 넓은 한 글자 접두('가%')는 최소 2글자부터 검색하도록 UX에서 막는다.

② 역방향 생성 컬럼 — 역순 사전을 만든다

접미 일치(%나무: "…나무"로 끝나는 작품)가 진짜 요구라면 뒤집어 저장한 컬럼에 인덱스를 건다. MySQL 생성 컬럼(generated column)을 쓰면 애플리케이션 수정 없이 DB가 값을 유지한다.

-- ✅ 역순 사전
ALTER TABLE webtoons
  ADD COLUMN title_rev VARCHAR(200) AS (REVERSE(title)) STORED,
  ADD INDEX idx_webtoons_title_rev (title_rev);

-- "…나무"로 끝나는 작품 = 뒤집으면 "무나…"로 시작하는 작품 → 접두 일치
SELECT id, title FROM webtoons
WHERE title_rev LIKE CONCAT(REVERSE('나무'), '%');   -- '무나%'
얻는 것

접미 일치가 seek이 된다. 앱 코드 수정 없음.

치르는 것

접두와 접미는 되지만 중간은 여전히 안 된다. STORED라 쓰기마다 한 번 더 계산·저장, 인덱스도 하나 더 유지.

③ 정규화 생성 컬럼 — 함수를 WHERE가 아니라 컬럼 쪽에 미리 적용한다

"나 혼자만 레벨업"을 "나혼자만"으로 쳐도 나와야 한다, 영문 대소문자는 무시해야 한다 — 이런 요구를 검색 시점에 함수를 씌워 풀면 인덱스가 죽는다(1-2절 ❌ ①). 대신 저장 시점에 정규화한 값을 별도 컬럼에 두고 거기에 인덱스를 건다.

-- ✅ 공백 제거 + 소문자화한 검색용 컬럼
ALTER TABLE webtoons
  ADD COLUMN title_norm VARCHAR(200) AS (LOWER(REPLACE(title, ' ', ''))) STORED,
  ADD INDEX idx_webtoons_title_norm (title_norm);

-- 앱에서도 같은 규칙으로 정규화한 뒤 접두 검색
SELECT id, title FROM webtoons WHERE title_norm LIKE '나혼자만%';
얻는 것

공백·대소문자·특수문자를 무시한 접두 일치가 seek이 된다.

치르는 것

정규화 규칙이 DB(생성 컬럼 식)와 앱(검색어 전처리) 두 곳에 존재한다. 한쪽만 바꾸면 조용히 검색이 안 된다 → 규칙을 한 곳에 두거나, "규칙 일치" 통합 테스트를 CI에 박는다(7-3절).

④ 자체 n-gram 토큰 테이블 — 역색인을 손으로 만든다

중간 일치가 꼭 필요한데 풀텍스트 기능을 쓸 수 없는 환경(권한, DB 종류, 파서 제약)이라면, 제목을 2글자 조각(bigram)으로 쪼개 별도 테이블에 저장하고 검색어도 같은 방식으로 쪼개 등호 조회의 교집합으로 찾는다. 4절 풀텍스트가 내부에서 하는 일의 축소판이라 원리 이해에도 좋다.

-- ✅ 토큰 테이블: token 기준 정렬(PK) → 등호 조회는 seek
CREATE TABLE webtoon_title_tokens (
  token      CHAR(2) NOT NULL,      -- 2글자 조각
  webtoon_id BIGINT  NOT NULL,
  PRIMARY KEY (token, webtoon_id)
);
-- "사과나무 아래"(id=7) 저장 시 → ('사과',7) ('과나',7) ('나무',7) ('무아',7)* ('아래',7)
--   * 공백 처리 규칙은 정규화 컬럼과 마찬가지로 한 곳에 고정

-- 검색어 "과나무" → 토큰 '과나', '나무' 를 모두 가진 작품
SELECT webtoon_id
FROM webtoon_title_tokens
WHERE token IN ('과나', '나무')            -- 두 개의 짧은 등호 구간 (seek)
GROUP BY webtoon_id
HAVING COUNT(DISTINCT token) = 2;          -- 집계 후 필터 = HAVING
얻는 것

중간 일치가 seek이 된다. 어떤 RDB에서도 된다.

치르는 것
  • 제목을 바꾸면 토큰 행을 지우고 다시 넣어야 한다 — 같은 트랜잭션이 아니면 검색 결과와 실제 제목이 어긋난다(반정규화 갱신 정합성과 같은 뿌리)
  • 저장량은 제목 길이만큼 행이 생겨 수 배
  • bigram 교집합은 순서를 보장하지 않는다 — "나무과나"도 매치되므로 후보 id로 원본을 읽어 LIKE '%과나무%'로 2차 검증(후보가 좁으니 이 LIKE는 싸다)

이 정도 손이 가기 시작하면 "풀텍스트 인덱스가 이걸 대신 해 준다"로 넘어갈 시점이다.

⑤ 선행 필터로 스캔 폭을 줄인다 — LIKE를 액세스 조건이 아니라 필터 조건으로 격하

검색이 항상 다른 좁은 조건과 함께 온다면(특정 작가의 작품 중 검색), 그 조건을 선두로 한 복합 인덱스로 구간을 먼저 좁히고 그 안에서 LIKE는 필터로만 쓴다. 복합 인덱스의 "뒤 컬럼은 탐색용이 아니라 제거용" 원칙 그대로다.

CREATE INDEX idx_webtoons_author_title ON webtoons (author_id, title);

-- ✅ author_id 등호로 seek → 그 작가의 작품 수십 건 안에서만 LIKE 평가
SELECT id, title FROM webtoons
WHERE author_id = 1024 AND title LIKE '%나무%';
-- type: ref, key: idx_webtoons_author_title, Extra: Using index condition
한계를 반드시 붙여 말한다
전역 검색에는 무력하다. genre = 'ROMANCE'처럼 전체의 30%를 남기는 필터는 스캔 폭을 별로 줄이지 못한다. "필터가 충분히 좁을 때만"이라는 조건이 이 우회의 전부다.

4. 층위 ② — 풀텍스트 인덱스: 중간 일치를 "토큰 등호 조회"로 바꾼다

4-1. 역색인(inverted index) — 책 뒤의 "찾아보기"

B+Tree가 "값 → 행"을 값 순서로 정렬한 사전이라면, 역색인은 "단어 → 그 단어가 나오는 문서 목록"이다. 책 뒤 찾아보기에서 "나무 …… 12, 87, 203쪽"을 보고 바로 가는 것. 문서를 미리 토큰으로 쪼개 저장하므로 검색어가 문서 어느 위치에 있든 토큰 하나를 등호로 찾으면 된다.

왼쪽은 "제목"이 키, 오른쪽은 "토큰"이 키. 키가 바뀌는 순간 문제의 종류가 바뀐다 — 3절 ④의 수제 토큰 테이블이 정확히 오른쪽 구조를 손으로 만든 것이다.

4-2. InnoDB FULLTEXT 사용법

-- ✅ 풀텍스트 인덱스 (한국어라면 ngram 파서 필수 — 4-3절)
ALTER TABLE webtoons
  ADD FULLTEXT INDEX ft_webtoons_title_author (title, author_name) WITH PARSER ngram;

-- 자연어 모드: 토큰 중 하나라도 맞으면 매치, 관련도 점수순
SELECT id, title, author_name,
       MATCH(title, author_name) AGAINST('사과나무' IN NATURAL LANGUAGE MODE) AS score
FROM webtoons
WHERE MATCH(title, author_name) AGAINST('사과나무' IN NATURAL LANGUAGE MODE)
ORDER BY score DESC
LIMIT 20;

-- 불리언 모드: +필수 -제외 *접두 "구문" 연산자. ngram 파서에서는 검색어가 구문 검색으로 바뀐다
SELECT id, title
FROM webtoons
WHERE MATCH(title, author_name) AGAINST('+사과나무 -완결' IN BOOLEAN MODE);
-- EXPLAIN: type: fulltext, key: ft_webtoons_title_author

LIKE '%사과나무%'가 N에 선형이었다면 이건 토큰의 문서 목록 길이에 비례한다 — 전체 N이 아니라 해당 토큰이 든 문서 수다.

4-3. 한국어 문제와 ngram 파서

기본 파서가 깨지는 곳
  • 기본 파서는 공백·구두점으로 단어를 자른다 — 띄어쓰기가 단어 경계인 영어 전제
  • 조사·어미: "나무를", "나무가", "나무에서"가 전부 다른 토큰 → "나무"로 검색하면 하나도 안 걸린다
  • 띄어쓰기 없는 제목: "나혼자만레벨업"은 토큰 하나 → "레벨업"으로 못 찾는다
ngram 파서
  • 의미 단위와 무관하게 글자를 n개씩 겹쳐 자른다 (ngram_token_size 기본 2)
  • "사과나무" → '사과', '과나', '나무'. 검색어도 같은 방식으로 잘라 찾으니 어디서 잘렸든 중간 일치
  • 자기 토큰 크기를 쓰므로 일반 파서의 innodb_ft_min_token_size에 걸리지 않는다
ngram의 한계도 같은 호흡으로 — 네 가지
  1. 의미를 모른다 — '과나' 같은 무의미 토큰도 전부 색인 → 색인 크기가 텍스트 길이에 비례해 크게 불어난다(형태소 분석 대비 수 배)
  2. 자연어 모드는 노이즈가 크다 — "사과나무"가 '사과'·'과나'·'나무' 중 하나라도 든 문서를 매치해 "나무늘보 일기", "사과 농장"이 딸려 온다. "정확히 사과나무가 든 것만"은 불리언 모드(구문 검색)로
  3. 형태소 분석이 없다 — "달리기"와 "달렸다"를 못 묶는다. 동의어("웹툰"↔"만화"), 오타("나무우"), 초성(ㄴㅁ)은 영역 밖
  4. 관련도 계산이 단순하다 — TF-IDF 계열 점수뿐. "인기 작품을 위로" 같은 부스팅을 조합할 수단이 없다(ORDER BY로 덧붙이면 관련도 정렬이 깨진다)

4-4. 풀텍스트의 대가 — 쓰기 · 크기 · 결합 · 조인

약점 ② 겨냥
"풀텍스트 인덱스를 쓰면 됩니다"로 끝내면 한쪽 면만 본 것이다. 얻는 것(중간 일치가 토큰 조회로)과 치르는 것 네 가지를 한 호흡에 붙인다.
암기 카드 — FULLTEXT 대가 4
쓰쓰기 비용크색인 크기결필터·정렬 결합 약함조조인 결과엔 못 건다
1
쓰기 비용 가산점행 하나 INSERT/UPDATE에 토큰 수만큼 역색인 항목. InnoDB는 메모리 캐시에 모았다가 보조 테이블로 내려쓰고 트랜잭션 커밋 시점에 토큰화 — 같은 트랜잭션 안에서 방금 넣은 행을 MATCH로 찾으면 안 보인다. 삭제도 즉시 지우지 않고 "삭제됨" 목록에 표시했다가 나중에 정리(OPTIMIZE TABLE) → 갱신이 잦으면 색인이 점점 비대해진다.
2
크기ngram이면 특히. 제목 20자에 bigram 19개, 작가명·줄거리까지 넣으면 원본보다 색인이 커지는 경우가 흔하다 → 버퍼 풀 경쟁.
3
필터·정렬과의 결합이 약하다한 테이블 조회에서 옵티마이저는 인덱스 하나를 고른다. MATCH … AND genre = ? ORDER BY view_count DESC는 풀텍스트로 후보를 뽑은 뒤 genre는 필터, view_count는 filesort. 후보가 수십만이면 여기서 다시 느려진다 — 이것이 5절 "전환 신호 ②"다.
4
조인 결과에는 못 건다FULLTEXT는 테이블 단위. "작품명 + 작가명 + 태그(별도 테이블) + 줄거리"를 한 번에 검색하려면 검색용 반정규화 컬럼을 만들어야 하고, 그 순간 갱신 정합성 문제가 따라온다.
-- 검색 + 장르 필터 + 인기순: 풀텍스트 인덱스 하나로 후보 → 나머지는 필터·정렬
SELECT id, title FROM webtoons
WHERE MATCH(title) AGAINST('나무' IN BOOLEAN MODE) AND genre = 'ROMANCE'
ORDER BY view_count DESC LIMIT 20;
-- 후보('나무' 포함)가 많을수록 filesort 비용↑

4-5. 풀텍스트로 "버틸 수 있는" 경계

수치는 하드웨어·데이터 형태에 따라 달라 팀이 실측해야 하지만, 정성적 경계는 분명하다. 오른쪽 열 조건이 하나라도 필수 요구로 들어오는 순간이 전환점이다.

조건풀텍스트로 버팀검색 엔진 신호
대상단일 테이블, 짧은 필드(제목·이름)여러 테이블 · 긴 본문 · 태그 결합
일치키워드 포함 여부형태소 · 오타 · 동의어 · 초성 · 자동완성 품질
결합필터 없거나 아주 좁음필터 + 정렬 + 패싯(장르별 건수) 동시
규모실측 p99가 목표 안후보 집합이 커져 filesort가 지배
신선도커밋 즉시 반영이 필요수 초 지연 허용 가능
격리검색 트래픽이 OLTP에 묻힘검색 스파이크가 OLTP를 밀어냄

웹툰 플랫폼의 작품명·작가명 검색은 왼쪽 열에 대체로 들어간다 — 짧은 필드, 단일 테이블, 수만~수십만 건. 그래서 첫 선택은 FULLTEXT ngram이다.

5. 층위 ③ — 검색 엔진(Elasticsearch) 전환: 신호 5 / 대가 5

"규모가 커지면 ES"는 판단 기준이 아니다
아래 다섯 신호 중 어느 것이 요구로 들어왔는지를 번호로 짚고, 곧바로 대가 다섯을 같은 호흡에 붙인다. "ES 쓰면 다 해결"은 운영을 안 해 본 사람의 말이다.
전환을 미는 신호 5 — 기억 고리
품검색 품질결필터·정렬·집계 결합범다중 소스 범위규규모격부하 격리
전환의 대가 5 — 기억 고리
운운영할 시스템동동기화·최종 일관성장장애 도메인 추가원사실의 원천이 둘로정정합성 모델 다름

"운동장 원정" — 남의 운동장(클러스터)으로 원정 가는 비용

신호 (얻는 것)
  1. 검색 품질 요구 — 형태소(한국어 nori: "달렸다"→"달리다"), 동의어, 오타 허용(fuzziness), 초성, 자동완성(edge_ngram), 관련도 튜닝(BM25 + 인기·최신 부스팅). RDB 풀텍스트는 어느 것도 제대로 못 한다. 가장 흔한 전환 사유.
  2. 필터·정렬·집계의 결합 — "나무 검색을 로맨스만, 인기순으로, 장르별 건수와 함께". 역색인 + 컬럼 저장 + 집계가 한 엔진의 본업. RDB는 인덱스 하나 + filesort.
  3. 검색 범위가 여러 소스 — 작품명·작가명·태그·줄거리·에피소드 제목을 한 검색창에서. RDB는 조인 위에 FULLTEXT를 못 건다.
  4. 규모 — 실측 p99가 목표를 넘고 filesort가 지배적일 때. 단, ①~③ 없이 규모만으로 가는 경우는 드물다 — 규모만이면 인덱스·캐시로 더 버틸 수 있다.
  5. 부하 격리 — 검색 스파이크(이벤트·푸시 직후, 크롤러)가 결제와 같은 DB의 버퍼 풀·CPU·커넥션을 잠식. 떼어내면 검색이 죽어도 결제는 산다.
대가 (치르는 것)
  1. 운영할 시스템이 하나 는다 — 노드·샤드·레플리카 설계, JVM 힙과 GC, 디스크 워터마크, 업그레이드, 모니터링·알람, 그리고 담당자. 매니지드로 일부를 돈으로 바꿔도 매핑 설계·재색인·용량 계획은 남는다.
  2. 동기화와 최종 일관성 — 이중 쓰기 금지(RDB 트랜잭션은 ES를 롤백해 주지 않는다). 정석은 RDB 커밋을 원천으로 두고 Outbox/CDC로 흘려보내기. 결과: 등록 직후 몇 초간 검색에 안 나온다 → 기획과 "최대 N초 지연" 합의, 삭제·비공개도 지연되므로 결과 id로 RDB 상태 후처리 재확인. 매핑·파서 변경 시 전량 재색인 절차 필요.
  3. 장애 도메인 추가 — 클러스터 red면 검색이 죽는다. 회로 차단기 + degrade(FULLTEXT 축소 검색 / 인기 목록 / 검색 비활성)를 미리 정한다. 폴백이 없으면 격리로 얻은 것을 도로 잃는다.
  4. 사실의 원천이 둘로 보인다 — ES는 파생 데이터. "언제든 RDB에서 전량 재구축"이 성립해야 하고, 그 스크립트가 주기적으로 도는지가 팀의 성숙도.
  5. 정합성 모델이 다르다 — ES 결과는 RDB 격리 수준의 보호를 받지 않는다. 검색 결과로 결제·권한을 결정하지 않고, "후보 찾기"로 제한한다.

5-1. 구조 한 장 — RDB가 원천, ES는 파생

화살표 방향이 곧 원칙이다 — 데이터는 RDB → ES 한 방향으로만 흐르고(이중 쓰기 없음), 검색 결과는 RDB로 되돌아와 확인받으며, ES가 없어도 내려앉을 곳이 있다.

5-2. 중간 선택지 가산점

매니지드 검색 서비스

운영 대가 ①의 일부를 비용으로 전환. 동기화·폴백 대가는 그대로다.

경량 검색 엔진

Meilisearch, Typesense 등. 단일 노드로 오타·자동완성·패싯이 되고 운영이 가볍다. 규모·집계 요구가 작을 때 ES와 FULLTEXT 사이의 선택지.

읽기 레플리카에 FULLTEXT

격리(신호 ⑤)만 문제라면 검색 쿼리를 레플리카로 보내는 것으로 OLTP 보호는 된다. 품질(신호 ①)은 못 푼다.

6. 세 층위 사다리 — 오를수록 얻는 것과 치르는 것이 함께 는다

사다리 한 칸을 오를 때마다 "왜 오르는가(신호)"와 "무엇을 지불하는가(대가)"를 쌍으로 말한다. 한 칸을 건너뛰면(LIKE → 바로 ES) 그 이유도 설명할 수 있어야 한다.
양면 화법 템플릿 — 편익만 말하는 버릇 고치기

구조: 얻는 것 → 치르는 것 → 그래서 경계. 세 문장을 한 호흡으로.

FULLTEXT ngram은 중간 일치를 토큰 등호 조회로 바꿔 N 선형을 벗어나지만, 쓰기 시 토큰화·색인 크기·형태소 부재·필터/정렬 결합 약함을 치르므로, 단일 테이블·짧은 필드·포함 여부 검색까지가 경계입니다.
검색 엔진은 형태소·오타·패싯·다중 소스·격리를 한 번에 얻지만, 운영할 클러스터, RDB와의 동기화와 최종 일관성, 장애 도메인 추가를 치르므로, 그 다섯 신호 중 하나가 필수 요구가 되기 전에는 가지 않습니다.
선행 필터 우회는 인덱스 추가만으로 LIKE를 필터로 격하시키지만, 필터가 좁을 때만 스캔 폭이 줄고 전역 검색엔 무력하므로, "특정 작가/장르 안에서 검색" 요구에만 씁니다.

7. 판단 절차 — "검색 기능 추가해주세요"의 숨은 비용을 산정하는 팀 체크리스트

약점 ③ 겨냥 — 판단 기준을 "그때그때 감으로"가 아니라 팀 문서와 도구에 고정한다
사람의 기억에 의존하지 않는 형태여야 한다. 아래 8칸은 요구를 받으면 답변 전에 채우는 것이다.

7-2. 결정 트리 3단계

7-3. 안전망을 고정하는 방법 — 문서 · 코드 · 알람

  1. ADR에 전환 트리거를 숫자로 — "현재 FULLTEXT ngram. 검색 p99 > 300ms가 1주 지속 / 요구에 형태소·오타 추가 / 검색 대상 테이블 2개 이상 → ES 검토 착수". 숫자는 팀이 정하되 정하지 않은 채로 두지 않는 것이 핵심 — 그래야 "언제 갈지"를 두고 매번 감정 싸움을 안 한다.
  2. 코드 리뷰 규칙 + 자동 검출 — "선행 % LIKE는 검색 전용 포트(SearchPort) 밖에서 금지". 통합 테스트에서 DataSource 프록시(p6spy 등)로 실행 SQL을 잡아 LIKE '% 패턴이 나오면 테스트를 실패시킨다.
  3. 풀스캔 감시 알람 — 슬로 쿼리 로그 + sys.statements_with_full_table_scans / Select_scan 상태 변수 추이. 데이터가 자라 임계를 넘는 날을 배포 없이도 잡아낸다.
  4. 부하 테스트 시나리오에 "검색 × 데이터 N배" — 현재 데이터로만 테스트하면 선형 비용은 절대 안 잡힌다. 1년 뒤 예상 건수를 채운 환경에서 검색 QPS를 건다.
  5. 정규화 규칙·토큰 규칙 일치 테스트 — 생성 컬럼 식과 앱 전처리, 토큰 테이블과 원본이 어긋나지 않는지 검증하는 테스트를 CI에 둔다.
  6. ES 도입 시 재구축 스크립트를 정기 실행 — "언제든 RDB에서 다시 만들 수 있다"를 말이 아니라 주기 작업으로 증명한다.

8. 실무 사례 — 웹툰 플랫폼 작품명·작가명 검색의 3단계

단계 1: LIKE '%kw%'로 시작, 조용히 자라는 비용

❌ 출시 초기 — 작품 3천 건, 잘 돌아간다
// 문제는 이 코드가 "N에 선형인 비용"을 심는다는 것
@Query("SELECT w FROM Webtoon w WHERE w.title LIKE %:keyword% " +
       "OR w.authorName LIKE %:keyword% " +
       "ORDER BY w.viewCount DESC")
List<Webtoon> search(@Param("keyword") String keyword,
                     Pageable pageable);
// EXPLAIN: type=ALL, rows=3000,
//          Extra=Using where; Using filesort
이 코드가 위험한 진짜 이유 둘
1. 복사된다 — 이 패턴을 본 동료가 댓글·에피소드
   테이블에도 복사한다. 거기는 N이 수천만.

2. OR 로 두 컬럼을 묶어 선행 필터(3절 ⑤)조차
   못 붙는다.

결과: 검색 QPS가 오르던 어느 이벤트 날, 배포도
없이 커넥션 풀이 마르고 결제 API까지 타임아웃
— 2절의 사슬 그대로.

단계 2: FULLTEXT ngram + 자동완성은 접두 인덱스

// ✅ 검색 요구를 둘로 쪼갠다: 자동완성(접두) / 결과 검색(중간 일치)
public interface WebtoonSearchRepository extends JpaRepository<Webtoon, Long> {

    // 자동완성: 접두 일치 → title 인덱스 seek. 2글자 미만은 컨트롤러에서 거른다
    @Query("SELECT w FROM Webtoon w WHERE w.title LIKE :prefix% ORDER BY w.viewCount DESC")
    List<Webtoon> autocomplete(@Param("prefix") String prefix, Pageable pageable);

    // 결과 검색: FULLTEXT ngram, 불리언 모드(구문 검색으로 노이즈 억제)
    @Query(value = """
        SELECT * FROM webtoons
        WHERE MATCH(title, author_name) AGAINST(:keyword IN BOOLEAN MODE)
          AND status = 'ONGOING'
        ORDER BY view_count DESC
        LIMIT :size
        """, nativeQuery = true)
    List<Webtoon> searchFullText(@Param("keyword") String keyword, @Param("size") int size);
}
이 시점에 ADR에 적은 전환 트리거
"① 검색 p99 > 300ms 지속 ② 태그·줄거리 검색 요구 ③ 오타·초성 요구 ④ 장르 패싯 요구". 이 시점의 검색은 단일 테이블·짧은 필드·수만 건이라 4-5절 왼쪽 열 안이다.

단계 3: "태그로도, 줄거리로도, 오타 나도 찾게" — 검색 엔진

요구가 ②③④를 한꺼번에 밟았다. 여러 테이블(태그), 형태소·오타(품질), 패싯(집계) — RDB 안에서는 답이 없다. 검색을 포트 뒤로 격리하고 ES 어댑터를 붙인다.

// ✅ 검색을 포트로 격리 — 구현(FULLTEXT / ES)을 바꿔도 호출부는 모른다. 폴백도 여기서
public interface WebtoonSearchPort {
    SearchResult search(SearchQuery query);   // 키워드 + 필터 + 정렬 + 패싯 요청
}

@Component
class ElasticsearchWebtoonSearchAdapter implements WebtoonSearchPort {
    private final ElasticsearchClient es;
    private final WebtoonSearchPort fallback;   // FULLTEXT 축소 검색 어댑터 — ES 도입 후에도 유지
    private final CircuitBreaker breaker;

    @Override
    public SearchResult search(SearchQuery q) {
        // nori + edge_ngram + fuzziness + 장르 패싯은 es.search 안에서. 차단기가 열리면 즉시 폴백으로
        return Try.ofSupplier(breaker.decorateSupplier(() -> es.search(q)))
                  .recover(ex -> fallback.search(q.withoutFacets()))   // ES 장애 시 degrade (패싯 없이)
                  .get();
    }
}
색인 파이프라인: webtoons/tags/authors 변경 → outbox → 인덱서 → ES 문서(작품명·작가명·태그·줄거리 반정규화)
합의한 지연:    "등록 후 최대 10초 내 검색 반영" (기획 문서에 명시)
후처리:         검색 결과 id로 RDB status 재확인 → 비공개·삭제 작품 제거
재구축:         매주 새벽 전량 재색인 → alias 스왑 (분석기 변경 리허설 겸용)
대가로 실제 치른 것 — 전환 전에 산정해 보고했던 목록
검색 팀 1명 상시, 클러스터 비용, 등록 직후 "검색에 안 나와요" 문의 → UX 안내 추가, 분석기 교체 때 전량 재색인 2시간. 이 목록을 전환 전에 산정했기 때문에 "왜 이렇게 오래 걸리냐"가 아니라 "예상 범위"로 받아들여졌다 — 숨은 비용 산정의 실제 모습이다.

9. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 답에 "얻는 것 / 치르는 것"이 둘 다 들어갔는지, 비용을 사슬로 말했는지 스스로 채점한다.

Q1. LIKE '나무%'는 인덱스를 탄다고 했는데, 항상 타나요?
아니다. 셋을 짚는다.
  1. 컬럼에 함수를 씌우면 못 탄다 — 대소문자 무시용 LOWER(title) LIKE가 전형. 대소문자 무시 콜레이션(_ci)이나 정규화 생성 컬럼으로 함수를 컬럼 쪽에 미리 적용한다.
  2. 선택도가 낮으면 옵티마이저가 일부러 안 탄다 — LIKE '가%'가 전체의 30%면 랜덤 I/O 북마크 룩업보다 순차 풀스캔이 싸다(옳은 판단). 그래서 자동완성은 최소 2글자부터 받는다.
  3. 사용자 입력에 %·_가 섞이면 코드는 접두처럼 보여도 실행은 중간 일치 — 와일드카드를 이스케이프하거나 제거한 뒤 바인딩한다.
셋 모두 풀스캔 원인 6종의 ①·⑥과 입력 검증에서 도출된다.
Q2. InnoDB FULLTEXT로 한국어 검색이 제대로 되나요? 어디까지 되고 어디서 막히나요?
기본 파서는 공백 기준이라 조사·어미가 붙는 한국어("나무를" ≠ "나무")와 띄어쓰기 없는 제목에서 깨진다. ngram 파서로 글자를 2개씩 겹쳐 잘라 색인하면 중간 일치와 조사 문제는 풀린다.
막히는 지점 넷: ① 형태소를 모른다("달렸다"↔"달리다" 불가) ② 의미 없는 토큰까지 색인해 크기가 크게 는다 ③ 자연어 모드는 토큰 하나만 맞아도 매치해 노이즈가 크다(불리언 모드 구문 검색으로 억제) ④ 관련도가 TF-IDF 계열 하나뿐이라 인기·최신 부스팅을 못 섞는다.
작품명·작가명처럼 짧은 필드의 "포함 여부" 검색까지는 충분하고, 오타·동의어·초성·부스팅이 요구로 들어오면 검색 엔진 신호다.
Q3. ES를 도입하면 RDB와의 데이터 불일치는 어떻게 다루나요? 시니어 변별
먼저 불일치는 없앨 수 없고 관리하는 것이라고 전제한다. 원칙 넷:
  1. 이중 쓰기 금지 — RDB 트랜잭션은 ES를 롤백해 주지 않으니 앱이 두 곳에 직접 쓰면 영구 불일치가 생긴다.
  2. RDB 커밋을 원천으로, 변경을 흘려보낸다 — 같은 트랜잭션의 Outbox 행 또는 binlog CDC를 인덱서가 소비. 실패해도 재시도로 따라잡는다(최종 일관성).
  3. 지연을 기획과 합의한다 — "등록 후 최대 N초", 등록 화면 UX. 삭제·비공개 작품이 검색에 남는 창은 검색 결과 id로 RDB 상태를 재확인하는 후처리로 막는다.
  4. 전량 재구축 절차를 정기 실행한다 — 매핑 변경·분석기 교체·유실 복구 모두 이 절차 하나로 수렴. "언제든 RDB에서 다시 만들 수 있다"를 주기 작업으로 증명한다.
①②가 없으면 언젠가 "검색엔 있는데 DB엔 없는 작품"을 손으로 지우게 된다. 12장 "source of truth" 문항과 같은 뿌리다.
Q4. ES 클러스터가 죽으면 검색은 어떻게 하나요? 그럼 격리한 의미가 있나요? 시니어 변별
격리로 얻은 건 "검색이 죽어도 결제는 산다"이지 "검색이 안 죽는다"가 아니다. 그래서 검색 경로에 degrade 계층을 미리 설계한다: 회로 차단기로 ES 호출을 끊고 → (a) RDB FULLTEXT 축소 검색(패싯·오타 없이 키워드만) (b) 인기 작품 목록으로 대체 (c) 검색 UI 비활성 + 안내 중 서비스 성격에 맞는 것으로 떨어진다.
폴백 (a)를 유지하려면 FULLTEXT 인덱스를 ES 도입 후에도 지우지 않는다는 결정이 따라오고, 그 쓰기 비용은 폴백의 가격이다. "장애 도메인 추가 → 폴백 설계 → 폴백 유지 비용"까지가 전환 대가의 한 묶음이고, ES 자체의 가용성은 레플리카 샤드·다중 AZ·매니지드로 올린다.
Q5. LIKE '%나무%'인데 EXPLAIN에 type: index, Using index가 나옵니다. 인덱스를 탄 건가요? 가산점
인덱스 풀스캔이다 — 탐색(seek)이 아니라 테이블 대신 인덱스 사본을 처음부터 끝까지 훑은 것. 조회 컬럼이 인덱스에 다 들어 있어(커버링) 옵티마이저가 "더 작은 쪽을 훑자"고 고른 결과다. 테이블 풀스캔(type: ALL)보다 읽는 페이지가 적으니 빠르긴 하지만 비용은 여전히 N에 선형이고 데이터가 10배면 10배 느려진다. type이 range/ref가 아니라 index면 "인덱스를 읽긴 했으나 시작점은 못 찍었다"로 읽는다. 이 구분을 못 하면 "인덱스 탔는데 왜 느리죠"에서 멈춘다.
Q6. "지금 5ms인데 왜 미리 바꾸자는 거죠?"라는 동료를 어떻게 설득하나요? 약점 ①
응답 시간이 아니라 기울기로 말한다. 비용이 N에 선형이라 5천 건 5ms는 50만 건 500ms, 거기에 QPS가 곱해져 커넥션 점유가 늘고, 풀이 마르면 검색과 무관한 결제까지 대기한다 — 그리고 이 진행에는 배포가 필요 없다. 덧붙여 이 패턴은 복사된다(댓글·에피소드 테이블은 N이 수천만).
그렇다고 "지금 당장 ES"를 주장하는 것도 아니다. 제안은 "언제 바꿀지를 지금 정하자" — ADR에 트리거를 숫자로(p99, 요구 유형, 대상 테이블 수), 부하 테스트에 "데이터 N배" 시나리오, 풀스캔 알람. 즉 감정 싸움을 기준 싸움으로 바꾸는 것이 설득의 형태다.
Q7. 자체 n-gram 토큰 테이블(3절 ④)을 이미 만들었는데, FULLTEXT ngram으로 바꾸면 무엇이 달라지나요?
원리는 같다 — 둘 다 2글자 토큰을 키로 한 역색인이고, 중간 일치를 등호 조회로 바꾼다. 달라지는 것은 누가 유지하느냐다.
얻는 것: 제목 변경 시 같은 트랜잭션에서 토큰 행을 지우고 다시 넣던 코드가 사라진다(DB가 색인을 유지). bigram 교집합의 순서 문제를 앱에서 2차 LIKE로 검증하던 것을 불리언 모드 구문 검색이 대신한다. 관련도 점수가 따라온다.
치르는 것: FULLTEXT 특유의 대가를 받는다 — 커밋 시점 토큰화라 같은 트랜잭션 안에서 방금 넣은 행이 MATCH에 안 보이고, 삭제가 지연 정리라 색인이 비대해지며(OPTIMIZE TABLE), 파서 선택지가 DB가 주는 것으로 제한된다.
그래서 수제판이 남는 이유는 딱 하나 — 풀텍스트 기능을 쓸 수 없는 환경(권한, DB 종류, 파서 제약)일 때다.
Q8. 검색 부하가 결제 DB를 밀어내는 게 걱정입니다. ES 없이 격리할 수 있나요? 약점 ②
신호 ⑤(격리)만 문제라면 읽기 레플리카에 FULLTEXT를 두고 검색 쿼리를 레플리카로 라우팅하는 것으로 OLTP 보호는 된다.
얻는 것: 검색 스파이크가 원본 DB의 버퍼 풀·CPU·커넥션을 잠식하지 않는다. 운영할 새 시스템도 없다.
치르는 것: 레플리카에도 색인 쓰기 비용은 그대로 들어가고, 복제 지연만큼 신선도가 떨어지며, 무엇보다 품질(신호 ①)은 하나도 풀리지 않는다 — 형태소·오타·동의어·패싯은 여전히 안 된다.
그래서 답은 "격리만이면 레플리카, 품질까지면 엔진"이고, 어느 쪽인지는 7-1절 8칸 중 3·4·8번 답이 정한다.
Q9. 이중 쓰기(앱이 RDB와 ES에 둘 다 저장)가 왜 안 되나요? 실패하면 재시도하면 되지 않나요?
RDB 트랜잭션은 ES를 롤백해 주지 않는다는 것이 핵심이다. RDB 커밋 성공 후 ES 쓰기가 실패(네트워크, 프로세스 종료)하면 "재시도해야 한다"는 사실 자체를 기록할 곳이 없다 — 그 기록을 트랜잭션 안에 남기자는 것이 곧 Outbox다. 반대로 ES 먼저 쓰고 RDB가 롤백되면 ES에 유령 문서가 남는다. 동시 갱신이면 두 저장소에 도착하는 순서가 뒤집혀 오래된 값이 이길 수도 있다.
정석은 RDB 커밋을 유일한 사실의 원천으로 두고, 같은 트랜잭션의 Outbox 행이나 binlog CDC를 인덱서가 소비해 ES에 반영하는 것 — 실패해도 재시도로 따라잡는 최종 일관성이고, 그 대가가 "등록 직후 몇 초간 검색에 안 나온다"는 지연 합의다.
한 줄 요약
B+Tree 인덱스는 첫 글자부터 정렬된 사전이라 LIKE '%kw%'는 트리를 내려갈 시작점을 찍을 수 없어(seek 불가) 전부 훑고, 그 비용은 행 수에 선형이라 QPS와 곱해져 커넥션 풀을 말리며 조용히 자란다. 대응은 세 층위 — 요구 협상·역순/정규화 생성 컬럼·자체 토큰 테이블·선행 필터로 LIKE 안에서 버티기 → 역색인으로 중간 일치를 토큰 등호 조회로 바꾸는 FULLTEXT ngram(대가: 쓰기·크기·형태소 부재·결합 약함) → 형태소·오타·패싯·다중 소스·격리가 필수일 때 검색 엔진(대가: 운영 클러스터, 동기화와 최종 일관성, 장애 도메인 추가). 전환은 데이터량·QPS·일치 유형·품질·결합·범위·신선도·격리 8칸을 채워 판단하고, 그 트리거를 ADR에 숫자로 박아 둔다.
