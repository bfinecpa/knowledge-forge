핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "배포도 없었는데 어제부터 DB CPU만 올랐습니다. '변경이 없다'는 전제를 어떻게 검증하고, 원인 후보를 어떻게 좁혀가나요?"
"배포 안 했다"는 코드가 안 바뀌었다는 말이지 시스템이 안 바뀌었다는 말이 아니다. DB는 배포 없이도 매일 변한다 — 데이터 증가·분포 변화, 통계 갱신에 따른 실행 계획 변경, 인접 배치·타 팀 잡, 트래픽 구성 변화·크롤러, 외부사 변경(웹훅 폭주), 인프라 작업(파라미터·페일오버·리플리카 소실), 캐시 만료·무효화, 긴 트랜잭션. 그래서 첫 행동은 원인을 찍는 것이 아니라 ① "변경 없음"이라는 전제를 변경 타임라인(배포·스키마·배치·인프라 이벤트·플래그·외부 공지·트래픽을 한 화면에)으로 검증하고, ② 후보를 언제부터(CPU 곡선의 변곡점 시각과 모양) → 무엇이(변곡점 전후의 top SQL digest 비교 — 새로 나타난 쿼리 / 횟수 급증 / 건당 비용 급증의 세 갈래) → 왜(그 쿼리의 실행 계획을 베이스라인과 대조, 발신자 추적) 순으로 좁힌다. "CPU만"이라는 증상도 단서다 — CPU는 DB가 메모리 안의 행을 많이 읽고 비교·정렬하고 있다는 뜻이고, 디스크 병목이면 iowait, 락 대기면 Threads_running만 오르고 CPU는 낮다. 이 검증이 사람의 기억이 아니라 시스템(변경 어노테이션, digest 스냅샷 잡, 실행 계획 베이스라인)에 고정돼 있어야 다음 장애 때도 같은 속도로 답이 나온다.
출제 의도 — 이 질문은 MySQL 지식 시험이 아니다. 네 가지를 한 번에 본다
⑴ 전제("변경 없음")를 검증하는 습관 · ⑵ 후보 목록을 빠짐없이 인출하는 능력 · ⑶ 각 후보가 왜 하필 CPU로 나타나는지를 자원 단위로 설명하는 능력 · ⑷ 그 절차가 사람 기억이 아니라 시스템에 있는지.

1. 첫 갈림길 — "변경 없음"은 전제가 아니라 검증 대상이다

1-1. "배포 안 했다"가 실제로 뜻하는 것 — 코드는 같은데 무엇이 다른가

"배포 없음"은 우리 팀이 이 서비스의 코드를 어제 이후 올리지 않았다는 사실 하나다. 그 문장이 배제하지 못하는 것이 여섯 방향에 있고, 후보 9종은 전부 이 여섯 방향의 끝에 매달려 있다. 표를 통째로 외우기보다 중심에서 여섯 방향을 돌려 표를 재생하는 편이 면접장에서 안전하다.

중심(코드)은 그대로인데 여섯 방향 중 하나가 달라진 것이 "배포 없는 변화"다. 8(긴 트랜잭션)은 코드가 읽는 행에 붙은 버전 체인이 달라진 것이므로 데이터 방향에 매단다.
암기 장치 — 여섯 방향은 "안 둘, 앞 둘, 발밑 둘"
DB 안에서 스스로 변하는 것
데이터 · 계획행 수·분포가 변하고, 그걸 본 옵티마이저가 길을 바꾼다
DB 앞 — 요청이 오는 쪽
호출자 · 방패누가 부르는지가 변하고, 앞에서 막아 주던 캐시가 약해진다
발밑 — 코드가 서 있는 자리
바닥 · 경로인프라가 바뀌거나, 배포 없이 코드 스위치(플래그)가 켜진다

비유 — 같은 레시피(코드)로 요리하는데 오늘만 늦다면: 재료 양이 늘었거나(데이터), 요리사가 다른 조리 순서를 택했거나(계획), 주문 구성이 달라졌거나(호출자), 화구가 바뀌었거나(바닥), 메뉴 옵션 스위치가 켜졌거나(경로), 미리 만들어 둔 밑반찬이 떨어졌거나(방패)다. 레시피를 아무리 다시 읽어도 답이 안 나온다.

"변경이 없다"는 결론이 아니라 가설이다
검증 방법은 사람에게 "어제 뭐 하셨어요?"라고 묻는 것이 아니라 §4-1의 변경 타임라인을 여는 것이다. 사람의 기억은 자기 팀 배포까지만 미치고, 위 여섯 방향은 대부분 우리 팀 밖에서 일어난다.

1-2. 변경의 정의를 넓힌 후보 목록 — 체크리스트

면접에서 이 표를 순서대로 말할 수 있으면 "목록 인출"은 통과다. 각 줄이 왜 CPU로 이어지는지는 §2에서 사슬로 편다.

1-3. 증상 읽기 — "CPU만"이 이미 후보를 반으로 가른다

"DB가 느리다"가 아니라 "DB CPU가 올랐다"는 정보량이 큰 증상이다. DB 서버의 CPU는 버퍼 풀 안의 페이지에서 행을 찾고, 조건과 비교하고, 정렬하고, 조인 버퍼를 채우고, 해시를 만들고, MVCC 버전 체인을 따라가고, 결과를 직렬화하는 데 쓰인다 — 전부 메모리 안에서 일어나는 계산이다. 반대로 디스크에서 페이지를 기다리는 시간과 락을 기다리는 시간은 CPU를 쓰지 않는다.

암기 규칙
계산은 CPU, 기다림은 CPU가 아니다. 디스크 기다림은 iowait로, 락 기다림은 Threads_running만으로 나타난다.

비유 — 요리사의 손이 바쁘면 CPU. 창고에서 재료가 오길 기다리면 iowait. 옆 요리사가 도마를 쓰고 있어 서서 기다리면 락 — 서 있는 동안 손은 놀고 있다.

여기서 나오는 추론 세 가지
1
"CPU만 올랐다"면 디스크 병목이 아니라 계산 병목이다."데이터가 늘어 버퍼 풀을 넘쳤다 → 디스크 I/O"는 iowait로 나타나지 user CPU로 나타나지 않는다. 대시보드가 user·system·iowait를 합산해 보여준다면 먼저 분해한다(OS top, RDS Enhanced Monitoring의 cpuUtilization.user/wait). wait가 주범이면 데이터 증가·콜드 버퍼 풀 쪽으로, user가 주범이면 실행 계획·쿼리 수·긴 트랜잭션 쪽으로 무게가 옮겨간다.
2
"DB CPU만" — 앱 서버 CPU는 그대로라면 요청 총량이 늘어난 것이 아니다.총량이 늘면 앱 CPU도 같이 오른다. 남는 것은 ⑴ 쿼리당 비용이 올랐거나(계획·데이터·긴 트랜잭션), ⑵ 앱을 거치지 않는 발신자가 있거나(배치·타 팀·수동 세션·리플리카 폴백), ⑶ 앱은 기다리기만 하는 패턴(캐시 미스로 DB 호출 수만 증가)이다.
3
락 대기는 CPU를 올리지 않는다."락 경합 때문에 CPU가 올랐다"는 사슬이 틀린 이유다. 락은 후보 목록에 있지만 그 경로는 "락" 자체가 아니라 "긴 트랜잭션 → undo 누적 → 버전 체인 순회"라는 다른 사슬로 CPU에 닿는다(§2-8).

2. 각 후보가 CPU로 나타나는 메커니즘 사슬

"원인 후보를 안다"와 "그 후보가 왜 CPU로 나타나는지 안다"는 다른 수준이다. 각 후보를 변한 것 → DB 안에서 늘어난 일 → 그 일이 소비하는 자원 세 마디로 끊어 말한다. 세 마디가 끊기지 않고 이어지면 사슬이다.

0배포 아닌 코드 경로 변경 — 플래그·원격 설정·A/B 비율
변한 것누군가 어제 feature flag를 켰거나, 원격 설정에서 페이지 크기·조회 기간·정렬 옵션을 바꿨거나, A/B 비율을 10%→50%로 올렸다. 배포 이력에는 아무것도 없다.
늘어난 일새 경로의 쿼리가 실행되기 시작하거나(digest에 어제부터 FIRST_SEEN인 쿼리), 기존 쿼리의 파라미터가 비싼 값으로 바뀐다(조회 기간 7일→90일).
자원새 쿼리가 인덱스를 못 타면 행 수 폭증 → CPU. 파라미터 변경이면 같은 digest의 건당 rows_examined만 오른다.
확인 플래그 시스템의 변경 이력, config 저장소 커밋 로그 — 이 둘이 변경 타임라인에 안 들어가 있으면 "배포 없음"은 영원히 검증되지 않는다.
1데이터 증가·분포 변화
변한 것행 수가 임계를 넘었거나, 특정 키의 행 수가 튀었거나(한 대형 고객이 어제 주문 10만 건), 값 분포가 바뀌었다(status='PENDING' 비율 1%→30%).
늘어난 일실행 계획은 그대로인데 같은 계획이 읽는 행 수가 는다. WHERE user_id = ?가 ref로 인덱스를 타도 그 user의 행이 100건→10만 건이면 검사 행 수는 1,000배.
자원읽는 행이 버퍼 풀 안이면 CPU(페이지 내 탐색·비교), 넘치면 iowait. 정렬이 sort_buffer_size를 넘으면 디스크 정렬(Sort_merge_passes ↑), 임시 테이블이 한도를 넘으면 Created_tmp_disk_tables ↑ — 임계를 넘는 순간 계단식.
확인 테이블 행 수·크기 추이(§4-3 일별 스냅샷), digest에서 호출 수는 같은데 SUM_ROWS_EXAMINED/COUNT_STAR만 오른 쿼리, 그 쿼리의 파라미터별 대상 행 수. "어제부터 갑자기"가 완만한 증가와 양립하는 이유가 이 임계들이다.
2통계 갱신 → 실행 계획 변경
변한 것옵티마이저가 보는 통계. InnoDB는 테이블 행의 일정 비율(기본 약 10%)이 바뀌면 통계를 자동 재수집하고, 일부 페이지를 샘플링해 만든다. 어제 대량 적재·삭제·일괄 갱신이 있었다면 재수집이 돌았고, 샘플이 편향되면 추정이 뒤집힌다.
늘어난 일추정이 뒤집히면 옵티마이저는 정직하게 다른 길을 고른다 — 인덱스 대신 풀스캔, 드라이빙 테이블 역전, 다른 인덱스. 쿼리 텍스트는 한 글자도 안 바뀌었는데 읽는 행 수가 자릿수로 뛴다.
자원풀스캔은 순차 I/O라 디스크 관점에선 싸지만(index-not-used §4), 테이블이 버퍼 풀에 있으면 행마다 조건을 비교하는 CPU가 그대로 남는다. "CPU만"에 가장 잘 맞는 후보 중 하나.
확인 그 digest의 현재 EXPLAIN을 베이스라인(§4-3)과 대조. rows 추정과 실측이 자릿수로 다르면 통계가 범인 — 응급 처방은 ANALYZE TABLE. 히스토그램·샘플 페이지 수·힌트 고정의 대가는 실행 계획 급변 문서작성 예정와 explain 문서 꼬리질문 1에.
3인접 배치·크론·타 팀 잡
변한 것새 잡이 등록됐거나, 기존 잡의 시간이 옮겨져 피크와 겹치거나, 처리량이 커졌거나(월말·이벤트), 타 팀이 같은 DB에 리포트 쿼리를 붙였다. 우리 배포 이력이 아니라 그 팀의 배포 이력에 있다.
늘어난 일배치는 본성상 대량 스캔·집계·정렬이다. 운영 쿼리 1만 건 분량의 행을 쿼리 한 개가 읽는다.
자원스캔·집계·정렬 자체가 CPU. 그리고 2차 피해 — 대량 스캔이 버퍼 풀의 뜨거운 페이지를 밀어내면 배치가 끝난 뒤에도 운영 쿼리가 디스크를 다시 읽어 iowait가 뒤따른다. "배치는 새벽 3시에 끝났는데 아침까지 느렸다"의 정체다. 가산점
확인 Spring Batch의 BATCH_JOB_EXECUTION의 START_TIME/END_TIME, 크론 로그, SHOW FULL PROCESSLIST의 User/Host — 계정이 서비스별로 분리돼 있으면 발신자가 한눈에 보이고, 하나의 계정이면 여기서 막힌다(§4-4). 리포트를 운영 DB에서 떼어내는 구조는 dashboard-stats 문서.
4트래픽 구성 변화·크롤러·특정 사용자
변한 것총 RPS는 어제와 같은데 구성이 다르다 — 검색·필터 페이지 비중이 올랐거나, 크롤러가 목록 API를 깊은 페이지까지 훑거나, 특정 사용자(대형 고객·어뷰저·사내 스크립트)가 대량 조회를 돌린다.
늘어난 일엔드포인트마다 쿼리 비용이 10~1,000배 다르다. LIMIT 100000, 20은 20건을 주려고 10만 건을 읽는다(deep-pagination). 비싼 엔드포인트 비중 5%→20%면 총 RPS가 같아도 DB 일은 몇 배.
자원읽는 행 수 증가 → CPU. 앱은 20건만 직렬화하므로 앱 CPU는 크게 안 오른다 — "DB CPU만"과 잘 맞는다.
확인 엔드포인트별 RPS와 p95, UA·IP별 요청 수, 페이지 번호 분포, 사용자별 호출 순위. APM이 있으면 "어느 엔드포인트의 DB 시간 합계가 어제 대비 가장 늘었나"가 한 번에 나온다.
5외부사 변경 — 웹훅 폭주·재전송 루프
변한 것결제사·물류사·메신저 등 외부 시스템이 배포했다. 이벤트 형식이 바뀌어 우리 처리가 실패 → 상대가 재전송 → 또 실패의 루프, 혹은 상대 장애 복구로 밀렸던 이벤트가 한꺼번에 밀려온다.
늘어난 일웹훅 하나가 "주문 조회 + 상태 갱신 + 이력 INSERT" 세 쿼리라면 수신 건수에 정비례해 쿼리 수가 는다. 멱등 처리가 되어 있어도 멱등 확인 조회는 실행된다.
자원쿼리 수 증가형 CPU. 외부 API 응답 지연이 트랜잭션 안에 들어 있으면 §2-8의 긴 트랜잭션 사슬이 겹친다.
확인 웹훅 수신 건수·실패율 그래프, 외부사 공지·상태 페이지·변경 알림 메일 — 이 채널이 변경 타임라인에 구독돼 있지 않으면 "외부사는 변경 없다"도 검증되지 않은 가설이다.
6인프라 작업 — 파라미터·페일오버·리플리카 소실·패치
변한 것운영팀이나 관리형 서비스가 우리 모르게 무언가를 했다. ⓐ 파라미터 그룹 변경(버퍼 풀 축소, optimizer_switch, 정렬·임시 테이블 버퍼 축소) ⓑ 페일오버·재시작 ⓒ 리플리카 소실·복제 지연으로 라우팅 이탈 ⓓ 자동 마이너 패치.
늘어난 일ⓑ 새 인스턴스의 버퍼 풀은 비어 있다(콜드 캐시). ⓒ 읽기 트래픽 전부가 프라이머리로 온다 — 앱은 오류 없이 폴백하므로 아무도 모른다(§5). ⓓ 옵티마이저 동작이 미세하게 바뀌어 특정 쿼리의 계획이 달라질 수 있다.
자원리플리카 소실은 쿼리 수 증가형 CPU, 콜드 버퍼 풀은 iowait(워밍 후 회복 — 스탠바이 사양이 달랐다면 회복 안 함), 파라미터 축소는 디스크 정렬·임시 테이블 증가로 CPU+I/O 혼합.
확인 클라우드 이벤트 로그(RDS 이벤트: failover · configuration change · maintenance), 파라미터 그룹 변경 이력, 감사 로그(CloudTrail의 ModifyDBInstance·ModifyDBParameterGroup·RebootDBInstance), 리플리카 상태·지연. SHOW GLOBAL STATUS LIKE 'Uptime'이 하루보다 짧으면 어제 무슨 일이 있었던 것이다.
7캐시 무효화·만료
변한 것Redis가 재시작됐거나(유지보수·OOM), 메모리 상한에 닿아 evict가 돌거나, 캐시 키 버전이 바뀌었거나, 같은 TTL로 적재된 키들이 같은 시각에 일괄 만료되기 시작했다(어제 예열 배치 뒤 24시간마다 동시 만료 — cache stampede).
늘어난 일미스마다 원본 쿼리. 히트율 95%→70%면 DB로 오는 쿼리는 5%→30%, 즉 6배. 앱은 캐시 대신 DB를 기다릴 뿐이라 앱 CPU는 거의 그대로.
자원쿼리 수 증가형 CPU. 원본 쿼리가 비싼 집계였다면(캐시하는 이유가 그것이다) 건당 비용도 크다.
확인 캐시 히트율 그래프의 어제 변곡점, Redis evicted_keys·used_memory·재시작 시각, 앱 로그의 캐시 연결 오류. TTL 지터·확률적 조기 갱신은 5장 캐싱 문서의 영역.
8락·긴 트랜잭션 — 락 대기는 CPU가 아니고, 긴 트랜잭션은 CPU다 자원 매핑 시험
변한 것배치·수동 세션·외부 호출을 품은 트랜잭션 하나가 어제부터 열려 있다. 락 대기는 스레드가 잠든 상태라 Threads_running은 오르고 응답은 느려지지만 CPU는 오르지 않는다 — "락 때문에 CPU"는 끊긴 사슬.
늘어난 일purge가 그 트랜잭션이 볼 수도 있는 undo를 못 지운다 → History list length가 자란다 → 갱신 잦은 행의 버전 체인이 길어진다 → 그 행을 읽는 모든 쿼리가 자기 시점 버전을 찾아 체인을 순회한다.
자원체인 순회는 메모리 안의 포인터 추적이라 순수 CPU. 잠긴 행이 아니라 무관한 조회까지 느려지고, 트랜잭션을 닫는 순간 회복된다.
확인 information_schema.innodb_trx에서 trx_started가 오래된 행(trx_mysql_thread_id로 PROCESSLIST와 조인해 누가 열었나), SHOW ENGINE INNODB STATUS의 History list length 추이(평소 대비 수십·수백 배면 확정), HikariCP 커넥션 장기 점유 로그. 사슬 전체는 mvcc-innodb §3, 짧게 유지하는 방법은 long-transaction 문서.

3-2. 무엇이 — 변곡점 전후의 top SQL digest 비교

이제 DB에 들어간다. 볼 것은 "지금 느린 쿼리"가 아니라 "변곡점 전과 후에 달라진 쿼리"다. performance_schema.events_statements_summary_by_digest는 쿼리를 파라미터를 지운 패턴(digest)별로 호출 수·총 시간·검사 행 수를 누적하는데(explain 문서 §4-1), 누적값이라 그냥 조회하면 어제와 오늘이 섞인다. 그래서 스냅샷(§4-2)의 디프를 본다. 스냅샷이 없다면 차선으로 현재 값을 덤프한 뒤 TRUNCATE하고 10분 뒤 다시 읽어 "현재 구간"만이라도 확보한다.

비유 — digest 테이블은 자동차 주행거리계다. "어제 얼마나 달렸나"를 알려면 어제 저녁의 숫자를 적어 두었어야 한다. 그 메모가 스냅샷이다.

암기: 세 갈래는 "새로 · 많이 · 비싸게". B 갈래는 건당은 빠르므로 slow query log에 안 잡힌다(§6 첫 꼬리질문).
-- 변곡점 전(스냅샷 s1)과 후(스냅샷 s2)의 디프 — 총 소요 시간 증가분 순
SELECT s2.digest_text,
       s2.count_star        - s1.count_star                    AS calls_delta,             -- B 갈래 판별
       (s2.sum_timer_wait   - s1.sum_timer_wait) / 1e12        AS sec_delta,
       (s2.sum_rows_examined - s1.sum_rows_examined)
         / NULLIF(s2.count_star - s1.count_star, 0)            AS rows_examined_per_call,  -- C 갈래 판별
       s2.first_seen                                           -- A 갈래 판별
FROM   ops.digest_snapshot s2
LEFT JOIN ops.digest_snapshot s1
       ON s1.digest = s2.digest AND s1.taken_at = '2026-08-30 14:00:00'
WHERE  s2.taken_at = '2026-08-30 15:00:00'
ORDER  BY sec_delta DESC
LIMIT  10;
읽는 법 — C 갈래는 "특정"과 "전체"를 먼저 가른다
C 갈래인데 모든 쿼리의 건당 시간이 조금씩 올랐으면 개별 쿼리 문제가 아니라 전역 원인(긴 트랜잭션, 버퍼 풀 축소, 콜드 캐시, 인스턴스 사양)이고, 특정 쿼리 하나만 자릿수로 뛰었으면 그 쿼리의 계획 또는 데이터다. B 갈래면 다음 질문은 "누가 부르나" — SHOW FULL PROCESSLIST 또는 sys.session의 user·host·db로 발신자를 세고, 앱이면 APM의 엔드포인트별 호출 수로 내려간다.

함께 떠 두는 것: 상태 카운터 전후 비교(Innodb_rows_read, Handler_read_rnd_next, Created_tmp_disk_tables, Sort_merge_passes, Threads_running), innodb_trx의 오래된 트랜잭션, Uptime. 관리형 서비스라면 Performance Insights의 "wait event별 DB load"가 §1-3의 자원 매핑을 그래프로 대신해 준다. 가산점

3-4. 응급 조치와 그 대가 — 양면으로 말한다

원인을 확정하기 전이라도 CPU가 90%라면 무언가 해야 한다. 조치마다 얻는 것과 잃는 것을 한 호흡에 붙인다.

암기 순서 — 보존 → 국소 → 전역
① 증거 보존 → ② 가역적이고 국소적인 조치 → ③ 전역 조치는 마지막

어떤 조치든 먼저 증거를 보존한다(PROCESSLIST 덤프, digest 스냅샷, innodb_trx, SHOW ENGINE INNODB STATUS) — 조치가 성공하면 증거도 사라진다. 응급 조치는 "시간을 산다"이지 "해결"이 아니다.

조치얻는 것잃는 것
원인 세션 KILL즉시 부하 제거큰 갱신이었다면 롤백이 실행만큼 오래 걸리고 그동안 부하는 계속. 배치라면 재실행 계획 필요
배치·크론 일시 중지즉시 부하 제거그 배치의 SLA(정산·리포트 지연), 밀린 처리량이 재개 시 몰림
ANALYZE TABLE통계 원인이면 계획이 즉시 복귀원인이 통계가 아니면 무효. 샘플이 다시 편향될 수 있어 근본 대책은 아님
인덱스 힌트·옵티마이저 힌트특정 쿼리의 계획을 고정데이터가 바뀌어도 계획이 안 바뀌는 경직. 코드 배포가 필요
캐시 TTL 연장·예열미스형이면 DB 호출 수 즉시 감소데이터 신선도 저하, 예열 자체가 DB 부하
특정 발신자 rate limit·차단크롤러·어뷰저형이면 즉시 효과정상 사용자 오탐, 외부사면 계약 문제
리플리카 추가·읽기 분리프라이머리 CPU를 구조적으로 나눔복제 지연에 따른 stale read, 비용, 라우팅 코드
인스턴스 스케일업근본 원인 무관하게 여유 확보재시작·페일오버를 동반하면 콜드 버퍼 풀로 일시 악화, 비용, 원인을 덮어 재발
"스케일업하면 되죠"가 왜 부족한 답인가
원인을 덮을 뿐 아니라 재시작을 동반하면 몇 시간 동안 더 나빠질 수 있고, 데이터 증가·트래픽 구성처럼 계속 커지는 원인이면 다음 달에 같은 자리로 돌아온다.

4. 안전망 고정 — 검증을 사람의 기억에서 시스템으로

§3의 절차가 훌륭해도 그 입력(변경 타임라인, 전후 스냅샷, 베이스라인)이 미리 쌓여 있지 않으면 장애 당일에는 쓸 수 없다. "다음에는 이렇게 하자"를 사람이 기억하는 대신 잡과 파이프라인이 기억하게 만드는 네 층 — 각 층은 §3의 한 단계에 재료를 댄다.

네 층은 기능 개발이 아니라 "다음 장애의 진단 시간을 반나절에서 5분으로 줄이는 투자"다.

5. 실무 사례 — 리플리카가 조용히 사라진 날

증상: 화요일 아침 알람. 프라이머리 CPU가 월요일 14:17부터 38%→81%로 계단형 상승 후 유지. 앱 서버 CPU·RPS는 평소와 같음. 배포 파이프라인 이력: 마지막 배포는 금요일.

변경 타임라인이 있었기에 ①이 5분에 끝났다. 없었다면 "인프라팀, 어제 뭐 하셨어요?"에서 시작했을 것이다.
  1. 언제부터 — 변곡점 14:17, 계단형 → 이벤트형 후보(0·2·3·6·7)로 압축. 변경 타임라인을 겹치니 14:16에 클라우드 이벤트 세로선 — "read replica: instance restarted (maintenance)". 배포·플래그·배치·마이그레이션 세로선은 없음. 첫 가설: 후보 6.
  2. 무엇이 — digest 스냅샷 14:00 vs 15:00 디프. 상위 8개가 전부 B 갈래 — SELECT … FROM episode WHERE series_id = ?, SELECT … FROM comment WHERE episode_id = ? ORDER BY id DESC LIMIT ? 등 읽기 전용 쿼리의 COUNT_STAR가 프라이머리에서 2.1배, 건당 시간·행 수는 동일. 새 쿼리(A)도, 건당 비용 급증(C)도 없음. PROCESSLIST의 발신 계정은 평소 리플리카에 붙던 webtoon_ro — 프라이머리에 나타나 있음. 리플리카 지표: 14:16 이후 커넥션 0.
  3. 왜 — 리플리카가 유지보수로 재시작 → 복제 재동기화에 시간이 걸리며 지연이 임계를 넘음 → 앱의 라우팅 데이터소스가 "리플리카 비정상"으로 판정하고 조용히 프라이머리로 폴백 → 리플리카는 복구됐지만 앱 쪽 헬스체크가 재편입을 시도하지 않는 구현이라 폴백 상태가 유지됨. 크기 검증: 읽기 쿼리 총 소요 시간 증가분이 CPU 증가분과 비례.
  4. 응급 조치와 대가 — 앱 인스턴스 롤링 재시작으로 라우팅 초기화(수 분의 배포와 같은 위험, 그러나 코드 변경 없음) vs 리플리카 추가(수십 분, 비용). 전자를 택하고 5분 내 CPU 복귀.
  5. 안전망으로 고정한 것 — ⑴ 폴백은 시끄럽게: 프라이머리로 폴백하는 순간 메트릭과 알람. 조용한 폴백은 가용성을 지키는 대신 장애를 숨긴다는 트레이드오프 — 가용성은 유지하되 알람을 붙이는 쪽으로 양면을 취함. ⑵ 리플리카 재편입을 주기 헬스체크로 자동화. ⑶ 클라우드 이벤트가 타임라인에 이미 들어와 있었기에 ①이 5분에 끝났음을 회고에 기록.
❌ before — 조용한 폴백: 가용성은 지키지만 아무도 모른다
@Override
protected Object determineCurrentLookupKey() {
    if (isReadOnlyTx() && replicaHealthy) return "replica";
    return "primary";  // 폴백 사실이 어디에도 남지 않는다
}
✅ after — 폴백은 유지하되 관측 가능하게, 그리고 재편입을 시도한다
@Override
protected Object determineCurrentLookupKey() {
    if (isReadOnlyTx()) {
        if (replicaHealth.isHealthy()) return "replica";
        fallbackCounter.increment();     // 메트릭 → 알람 (지속 1분이면 페이지)
        replicaHealth.scheduleRecheck(); // 복구 시 자동 재편입
    }
    return "primary";
}

같은 절차를 후보 2(통계 갱신)에 적용한 사례는 C 갈래·특정 쿼리로 시작해 EXPLAIN 대조 → ANALYZE TABLE로 끝나는데, 그 사례와 재발 방지(히스토그램·배치 후 통계 재수집 스텝)는 실행 계획 급변 문서작성 예정에서 이어진다.

6. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 답의 깊이가 갈리는 지점, 추가는 이 페이지에서 보탠 문항.

CPU는 올랐는데 slow query log에는 아무것도 안 잡힙니다. 왜 그럴 수 있고, 어디를 보나요?

slow query log는 건당 실행 시간이 long_query_time을 넘는 쿼리만 기록한다. CPU를 올리는 가장 흔한 패턴 — 건당 20ms인 쿼리가 초당 5,000번(캐시 미스, 크롤러, N+1, 리플리카 폴백) — 은 한 건도 임계를 안 넘는다. 그래서 §3-2의 B 갈래는 slow log가 아니라 digest의 COUNT_STAR × 평균 시간으로만 보인다.

보조로 long_query_time을 0에 가깝게 낮추되 min_examined_row_limit으로 "많이 읽은 것만" 남기거나 log_queries_not_using_indexes를 켜면 "빠르지만 많이 읽는" 쿼리를 잡을 수 있지만, 로그량이 급증해 디스크와 I/O를 먹는다는 대가가 있다.

결론 "slow log에 없다"는 "느린 쿼리가 없다"가 아니라 "건당은 빠르다"는 정보이고, 그 자체가 B 갈래를 가리키는 단서다.

CPU 상승, I/O 대기, 락 대기를 지표만으로 어떻게 구분하나요?

§1-3의 카드 네 장을 말로 풀면 된다.

  • user CPU와 Threads_running이 함께 오르면 계산(읽는 행 수·쿼리 수·정렬).
  • user CPU는 낮은데 iowait와 Innodb_buffer_pool_reads(물리 읽기)가 오르면 디스크(버퍼 풀 초과, 콜드 캐시, 대량 스캔의 오염).
  • CPU도 iowait도 낮은데 Threads_running과 Innodb_row_lock_waits가 오르고 PROCESSLIST State가 Waiting for …면 락.
  • 셋 다 낮은데 앱만 느리면 DB 밖(커넥션 풀, 네트워크, 앱 스레드).

이 구분이 되어야 "CPU가 올랐으니 인덱스를 보자"와 "iowait가 올랐으니 버퍼 풀과 배치를 보자"가 갈린다 — 같은 "DB가 느리다"에서 정반대의 첫 행동이 나온다.

원인을 찾기 전에 당장 CPU를 내려야 한다면 무엇을 하고, 그 대가는 무엇인가요? 시니어 변별

순서가 답이다.

  1. 증거 보존 — PROCESSLIST·innodb_trx·digest 스냅샷·SHOW ENGINE INNODB STATUS를 파일로 뜬다. 조치가 성공하면 증거는 사라지고 재발 방지가 불가능해진다.
  2. 가역적이고 국소적인 조치부터 — 발신자가 특정되면 그 배치 중지·그 IP 제한, 오래된 트랜잭션이면 KILL(단, 큰 갱신의 롤백은 실행만큼 오래 걸려 부하가 이어질 수 있음), 계획 문제로 보이면 ANALYZE TABLE.
  3. 전역 조치는 마지막 — 스케일업은 재시작·페일오버를 동반하면 콜드 버퍼 풀로 몇 시간 더 나빠질 수 있고, 원인을 덮어 다음 달 같은 자리로 돌아온다.

각 조치의 대가는 §3-4 표 그대로. 면접관이 듣고 싶은 문장은 "응급 조치는 시간을 사는 것이고, 무엇을 샀는지와 무엇을 지불했는지를 회고에 적는다"이다.

performance_schema는 누적값인데 "어제와 오늘"을 어떻게 비교하나요? 운영 DB에서 켜두는 비용은요? 시니어 변별

누적값은 그 자체로는 구간 비교가 안 되므로 주기 스냅샷의 디프(§4-2)나 관리형 서비스의 Performance Insights, pt-query-digest 일일 리포트처럼 "전후"가 남는 형태가 필요하다. 없을 때의 차선은 현재 값을 덤프한 뒤 TRUNCATE하고 일정 시간 뒤 다시 읽어 현재 구간만 확보하는 것 — 단 이 순간 과거는 영구히 사라지므로 덤프가 먼저다.

비용은 트레이드오프다. statement 단위 계측은 일반적으로 감수할 만한 오버헤드지만, 모든 instrument·consumer를 켜면 부하가 눈에 띄게 늘고, 반대로 아예 끄면 §3-2 전체를 잃는다. "기본 statement digest는 켜 두고, 더 세밀한 계측은 장애 시 잠깐 켠다"가 균형점이다.

"변경 없음"을 사람에게 묻지 않고 확인하려면 팀에 무엇이 갖춰져 있어야 하나요? 시니어 변별

§4를 우선순위로 답한다.

  1. 변경 타임라인 — 배포·스키마·배치·플래그·인프라 이벤트·외부사 공지가 한 저장소에 어노테이션으로 들어오고 대시보드에 세로선으로 겹쳐 보이는 것. 이것이 없으면 §3-1이 성립하지 않는다.
  2. digest 스냅샷 잡 — 전후 비교의 재료.
  3. 실행 계획·테이블 크기 일별 스냅샷 — "관측되지 않는 변경"(통계·데이터 임계)을 관측 가능하게 만드는 것.
  4. 발신자 식별 — 서비스·배치·사람별 DB 계정 분리.

그리고 이 네 가지는 기능 개발이 아니라 다음 장애의 진단 시간을 반나절에서 5분으로 줄이는 투자라는 프레임으로 팀을 설득한다 — 시니어 변별은 도구 목록이 아니라 "이 투자가 언제 회수되는가"를 말할 수 있는지에 있다.

"락 경합 때문에 CPU가 올랐습니다"라고 답하면 왜 감점인가요? 락은 후보에 있는데요. 추가

락 대기는 스레드가 잠들어 있는 상태다. Threads_running은 오르고 응답은 느려지지만 CPU는 쓰지 않는다 — 그래서 "락 → CPU"는 중간 마디가 없는 끊긴 사슬이다.

락이 후보 목록에 있는 이유는 다른 사슬 때문이다: 긴 트랜잭션 → purge가 undo를 못 지움 → History list length ↑ → 행의 버전 체인이 길어짐 → 그 행을 읽는 모든 쿼리가 체인을 순회 → 순수 CPU. 잠긴 행이 아니라 무관한 조회까지 느려지고, 트랜잭션을 닫는 순간 회복된다.

확인 innodb_trx의 오래된 trx_started, SHOW ENGINE INNODB STATUS의 History list length. 면접관은 후보 이름이 아니라 자원까지 이어지는 세 마디를 듣고 있다.

사례에서 왜 "조용한 폴백"을 없애지 않고 알람만 붙였나요? 추가

폴백은 가용성을 지키는 장치다. 리플리카가 죽었을 때 폴백이 없으면 읽기 요청 전체가 실패한다 — 그건 CPU 상승보다 나쁜 장애다. 문제는 폴백 자체가 아니라 폴백이 관측되지 않는 것과 돌아오지 않는 것이었다.

그래서 양면을 취했다: 폴백은 유지하되 ⑴ 폴백하는 순간 카운터를 올려 알람(지속 1분이면 페이지), ⑵ 주기 헬스체크로 리플리카 복구 시 자동 재편입. 트레이드오프를 없애는 게 아니라 숨겨진 쪽에 알람을 붙이는 것이 시니어의 선택이다.

한 줄 요약
"배포 없음"은 코드가 안 바뀌었다는 말일 뿐이라 시스템의 변경(데이터·계획·호출자·바닥·경로·방패)을 변경 타임라인으로 먼저 검증하고, 좁히기는 언제부터(변곡점의 시각과 모양) → 무엇이(전후 digest 비교를 새 쿼리·횟수 급증·건당 비용 급증 세 갈래로) → 왜(계획 베이스라인 대조·발신자 추적)의 순서로 — "CPU만"은 계산 병목이라 디스크(iowait)·락(Threads_running만)과 구분되고, 이 절차의 입력(타임라인·스냅샷·베이스라인)은 장애 전에 시스템이 쌓아 두어야 장애 당일에 쓸 수 있다.
