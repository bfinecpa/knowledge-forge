겉 — 인출 테스트

"EXPLAIN 컬럼을 아는가." 목록을 순서대로 꺼낼 수 있어야 한다. 긴장하면 목록은 두 개에서 끊기므로, 이 페이지는 읽는 순서 그대로 외우게 만든다.

속 — 태도 테스트

"성능 문제를 재현 가능한 절차로 다루는가." 인덱스 하나 추가해 빨라진 경험은 누구나 있다. 면접관이 가르고 싶은 것은 왜 빨라졌는지 숫자로 설명하고, 재발을 막기 위해 무엇을 남겼는가까지 말하는 사람이다.

관련 질문: "잘 돌던 쿼리의 실행 계획이 어느 날 갑자기 바뀌어 느려졌습니다. 원인과 대응은?" / "ORDER BY가 인덱스를 타는 조건은? filesort는 언제 발생하고 왜 문제인가요?" — 둘 다 §6 꼬리질문에서 다룬다. 출제 의도의 원문: "프로세스를 묻는 이유는 이 능력이 쿼리를 넘어 모든 성능 문제에 이식되기 때문이다."

1EXPLAIN은 "견적서"다 — 실행하지 않고, 통계로 추정한다

옵티마이저는 쿼리를 받으면 실제 데이터를 세어보지 않는다. DB가 주기적으로 모아둔 통계(테이블 행 수, 컬럼별 서로 다른 값의 개수, 인덱스 크기)를 보고 "이 인덱스를 타면 대략 몇 행을 읽겠구나"를 추정하고, 후보 계획들의 추정 비용을 비교해 가장 싼 것을 고른다. EXPLAIN은 그 선택 결과를 보여주는 것이다.

공사 견적서 비유
견적서에는 "벽지 30롤, 인건비 2일"처럼 예상 수량이 적혀 있다. 실제로 공사를 해보면 벽지가 45롤 들 수도 있다. EXPLAIN의 rows가 이 "30롤"이고, EXPLAIN ANALYZE의 actual rows가 "45롤"이다. 견적과 청구서가 크게 다르면 견적을 낸 근거(통계)가 틀린 것이다.
첫 전제 — 이걸 놓치면 "EXPLAIN은 멀쩡한데 왜 느리지"에서 멈춘다

여기 적힌 숫자는 전부 추정이고, 추정은 통계가 낡으면 틀린다.

MySQL의 EXPLAIN 출력은 테이블 접근 하나당 한 행이다. 조인이 세 테이블이면 세 행이 나오고, 위에서 아래 순서가 곧 실행 순서(같은 id라면 맨 위가 드라이빙 테이블)다. 서브쿼리·파생 테이블은 id가 달라지고 select_type에 종류가 찍힌다.

2읽는 순서 5단계 — 순서가 곧 진단 순서다

긴장하면 목록은 두 개에서 끊긴다. 그래서 읽는 순서 그대로 외운다. 각 단계가 답하는 질문을 함께 외우면 순서가 저절로 복원된다 — 누가 → 어떻게 → 얼마나 깊이 → 얼마나 많이 → 무슨 추가 작업.

한 행을 볼 때마다 이 순서로 내려간다. 조인이면 위 행(드라이빙)을 먼저 끝까지 읽고 다음 행으로.
암기 카드EXPLAIN 읽는 순서 5
  1. 행 순서 위 → 아래 = 실행 순서. 맨 위가 드라이빙 테이블
  2. type 접근 방식 등급. 경계선은 range | index
  3. key, key_len 어느 인덱스를, 몇 번째 컬럼까지 썼나
  4. rows × filtered 몇 행 읽어서(rows) 몇 %가 살아남나(filtered)
  5. Extra 위험 3 (filesort / temporary / join buffer) · 좋은 3 (Using index / index condition / MRR)
연상: 누가(순서) → 어떻게(type) → 얼마나 깊이(key_len) → 얼마나 많이(rows×filtered) → 무슨 추가 작업(Extra). 질문 다섯 개를 떠올리면 칸 이름이 따라온다.

2-1. type — 접근 방식 등급 사다리

MySQL 문서의 공식 순서(좋음 → 나쁨)는 system > const > eq_ref > ref > fulltext > ref_or_null > index_merge > unique_subquery > index_subquery > range > index > ALL이다. 전부 외울 필요는 없다. 실무에서 매일 보는 일곱 개를 "한 번의 접근에서 읽는 폭"과 함께 사다리로 고정한다.

착시 주의 — "인덱스는 탔는데요"

index는 이름에 "인덱스"가 들어 있어 착시를 일으킨다. 읽는 폭이 테이블보다 좁을 뿐 전수 조사라는 점에서 ALL과 같은 부류다. "인덱스는 탔는데요"라는 말이 type: index를 가리키고 있다면 그건 탄 게 아니다.

2-2. key · key_len — 어느 인덱스를 어디까지 썼나

  • possible_keys: 후보로 검토된 인덱스들. 여기 있다고 쓴 게 아니다.
  • key: 실제로 선택된 인덱스. NULL이면 아무것도 안 썼다.
  • key_len: 선택된 인덱스에서 몇 바이트까지 사용했는가.

key_len이 중요한 이유는 복합 인덱스에서 몇 번째 컬럼까지 조건에 쓰였는지를 알려주는 유일한 칸이기 때문이다. key에 (user_id, status, created_at) 인덱스 이름이 찍혀 있어도, key_len이 첫 컬럼 크기만큼이면 나머지 두 컬럼은 좁히는 데 쓰이지 않았다.

계단 비유
복합 인덱스는 왼쪽 컬럼부터 순서대로 내려가는 계단이다. key는 "어느 계단을 탔나", key_len은 "몇 칸까지 내려갔나". 가운데 칸(status)을 건너뛰면 그 아래 칸(created_at)은 밟을 수 없다 — 이것이 leftmost prefix다.

key_len은 "인덱스를 탔는가"가 아니라 "인덱스를 얼마나 깊이 탔는가"에 답한다. 복합 인덱스를 설계해 놓고 실제로는 선두 컬럼 하나만 쓰이고 있는 경우를 잡아내는 칸이다.

2-3. rows × filtered — 얼마나 읽어서 얼마나 남기나

  • rows: 이 단계에서 읽을 것으로 추정한 행 수 (스토리지 엔진에서 가져올 양).
  • filtered: 읽은 행 중 인덱스로 못 거른 나머지 WHERE 조건을 통과해 살아남을 비율(%)의 추정.

rows × filtered%가 다음 단계로 넘어가는 행 수다. 앞의 예시 rows: 48000, filtered: 10.00은 "인덱스로 4만 8천 행을 가져와서, 그중 10%인 4,800행만 status = 'ACTIVE'를 통과한다"는 뜻이다. 읽은 것의 90%를 버린다 — 여기가 이 쿼리의 비용이 새는 지점이다.

그물 비유
rows는 그물에 걸려 올라온 물고기 수, filtered는 그중 배에 남기는 비율이다. 4만 8천 마리를 끌어올려 4천 8백 마리만 남기고 도로 버린다면, 힘은 "버릴 고기를 끌어올리는 데" 다 쓴 것이다. 그물코(인덱스 컬럼)를 촘촘히 하면 끌어올리는 양(rows) 자체가 준다.

조인이라면 각 행의 rows를 곱한 것이 총 검사량의 어림이다. 드라이빙에서 4만 8천 행이 넘어가고 안쪽이 eq_ref로 행당 1건이면 안쪽 탐색이 4만 8천 번 일어난다 — NL 조인 비용 공식 "바깥 루프 횟수 × 안쪽 탐색 비용" 그대로다.

암기 카드rows × filtered 위험 조합 2
  1. rows ≈ 테이블 전체 행 수 → 사실상 풀스캔
  2. rows 큰데 filtered 낮음 → 인덱스가 조건을 절반만 덮는다. 많이 읽고 대부분 버린다. 인덱스에 컬럼을 추가하면 rows 자체가 줄어든다

2-4. Extra — 위험 신호 3 + 좋은 신호 3

위험 신호 3F · T · J
  1. Using filesort 정렬을 인덱스 순서로 해결 못 해 별도 정렬 작업. LIMIT 20이어도 대상 전부 읽고 정렬한 뒤 20건. (이름과 달리 메모리에서도 하고, sort buffer를 넘치면 디스크 임시 파일)
  2. Using temporary GROUP BY·DISTINCT·UNION에 임시 테이블. 메모리 한도를 넘으면 디스크 임시 테이블
  3. Using join buffer (Block Nested Loop / hash join) 안쪽 테이블의 조인 키에 쓸 인덱스가 없어 버퍼에 담아 뭉텅이로 비교. "조인이 느려요"의 단골
연상: Filesort · Temporary · Join buffer = "정렬 · 임시 · 조인 버퍼" — 셋 다 인덱스가 못 해준 일을 따로 하는 것이다.
좋은 신호 3I · C · M
  1. Using index 필요한 컬럼이 전부 인덱스에 있어 테이블에 안 감(커버링). 최고의 신호 — 북마크 룩업 0회
  2. Using index condition 인덱스 컬럼으로 거를 수 있는 조건을 스토리지 엔진 층에서 먼저 적용(Index Condition Pushdown) — 테이블 접근 전에 버림
  3. Using MRR 세컨더리 인덱스에서 모은 PK를 PK 순으로 정렬한 뒤 테이블을 읽음(Multi-Range Read) — 흩어진 랜덤 I/O를 순차에 가깝게
연상: Index(커버링) · Condition(푸시다운) · MRR(정렬 후 읽기) — 셋 다 테이블 접근(랜덤 I/O)을 줄이는 것이다.

세컨더리 인덱스에서 얻은 PK 목록은 뒤죽박죽 순서라 그대로 테이블을 읽으면 페이지를 여기저기 찌른다(랜덤). MRR은 그 PK들을 버퍼에 모아 정렬한 뒤 읽어서 인접 페이지를 연달아 읽게 만든다(순차에 가깝게). "DB가 랜덤 I/O를 얼마나 싫어하면 이런 기능까지 만들었겠는가"로 기억하면 비용 모델이 같이 굳는다.

2-5. select_type — 한 번만 훑어두면 되는 칸

SIMPLE(서브쿼리·UNION 없음) / PRIMARY(가장 바깥) / SUBQUERY / DERIVED(FROM 절의 서브쿼리 = 파생 테이블) / UNION. 경계할 것은 DEPENDENT SUBQUERY 하나 — 바깥 행의 값에 의존하는 서브쿼리라 바깥 행마다 재실행된다. 바깥이 10만 행이면 서브쿼리가 10만 번 돈다. 처방은 조인으로 풀어 쓰기.

3추정 vs 실측 — EXPLAIN과 EXPLAIN ANALYZE

MySQL 8.0.18부터 지원하는 EXPLAIN ANALYZE는 쿼리를 실제로 실행하고, 계획의 각 단계마다 실측값을 붙여 트리 형태로 보여준다. "견적서 vs 청구서"를 한 화면에서 비교할 수 있다.

--             -> Filter: (o.status = 'ACTIVE')  (cost=16800 rows=4800) (actual time=0.06..289.7 rows=4720 loops=1)
--                 -> Index lookup on o using idx_orders_user (user_id=100)  (cost=16800 rows=48000) (actual time=0.05..271.3 rows=47215 loops=1)
--             -> Single-row index lookup on u using PRIMARY (id=o.user_id)  (cost=0.25 rows=1) (actual time=0.003..0.003 rows=1 loops=4720)
--   빨강: 0.05ms에 시작해 271ms에 끝남 — 시간의 대부분이 여기 (4만 7천 행 북마크 룩업)
--   파랑: 0.003ms × loops 4720 ≈ 14ms — 안쪽 테이블은 반드시 loops를 곱해 읽는다
암기 카드EXPLAIN ANALYZE 읽는 법 3
  1. 괄호 두 개를 나란히 (cost=… rows=48000)이 추정, (actual … rows=47215)가 실측. 두 rows가 자릿수 단위로 어긋나면 통계가 틀린 것 → 튜닝이 아니라 ANALYZE TABLE이 먼저
  2. loops를 곱한다 actual time은 first..last 밀리초이고 loops만큼 반복된 평균. 안쪽 테이블 0.003ms × 4720 ≈ 14ms. 안 곱하면 "조인은 0.003ms밖에 안 걸리는데?"라는 오독
  3. 아래에서 위로 시간이 어디서 튀는지 잎(leaf)부터 올라간다. 위 예시는 Index lookup on o에서 271ms — 4만 7천 행을 인덱스로 찾고 각 행을 테이블에서 다시 읽는(북마크 룩업) 데 대부분. 그중 4,720행만 남음 → 비용의 90%가 "결국 버릴 행을 랜덤 I/O로 읽는 데"
연상: 둘 비교 · 곱하기 · 거슬러 오르기.
가산점 — 같은 식구들
  • EXPLAIN FORMAT=TREE — 실행 안 하고 트리 형태로. 해시 조인 사용 여부가 보임.
  • EXPLAIN FORMAT=JSON — 단계별 추정 비용 수치 포함.
  • EXPLAIN FOR CONNECTION <스레드 id> — 지금 돌고 있는 쿼리의 실행 계획. 장애 상황에서 SHOW PROCESSLIST로 오래 걸리는 스레드를 찾은 뒤 즉시 확인.
  • PostgreSQL EXPLAIN (ANALYZE, BUFFERS) — 버퍼 캐시 적중(shared hit)과 디스크 읽기(read)를 분리해 "느린 이유가 랜덤 디스크 I/O인가, CPU인가"를 숫자로 가른다.

4개선 프로세스 — 측정 → 가설 → 검증 → 고정

❌ 흔한 흐름 — 프로세스가 아니다

느리다는 제보 → 쿼리를 눈으로 봄 → WHERE 컬럼에 인덱스 추가 → 빨라진 것 같음 → 끝

  • 무엇이 얼마나 느렸는지 숫자가 없다
  • 왜 빨라졌는지 모른다
  • 다른 쿼리가 느려졌는지 모른다
  • 3개월 뒤 같은 패턴이 재발해도 아무도 모른다
✅ 사이클 — 고정까지 가야 한 바퀴
  1. 측정: 무엇이, 얼마나, 몇 번, 언제 — 숫자와 재현 조건
  2. 가설: 비용이 새는 지점을 "메커니즘 사슬"로, 예상 효과를 숫자로
  3. 검증: EXPLAIN ANALYZE 전후 실측 + 부작용까지 양면으로
  4. 고정: 재발을 사람이 아니라 설정·테스트·파이프라인이 잡도록
화살표 위의 글은 다음 단계로 넘겨주는 산출물이다. 고정 → 측정 화살표가 굵은 이유: 고정이 있어야 측정이 "사람이 마음먹을 때"가 아니라 항상 돌아간다.
병원 진료 비유
측정은 검사 수치(혈압 160), 가설은 진단(염분 과다 → 혈압 상승 → 두통), 검증은 처방 후 재검사 + 부작용 확인(약의 부작용은?), 고정은 재발 방지를 생활 규칙으로 남기는 것(정기 검진 예약 = slow log 알람, 식단표 = PR 템플릿). "약 먹었더니 나아진 것 같음"에서 끝나면 석 달 뒤 같은 증상으로 돌아온다.
암기 카드사이클 4 — 측 · 가 · 검 · 고
  1. 측정 가장 비싼 쿼리를 숫자로 (avg × calls), 재현 조건까지
  2. 가설 비용이 새는 지점을 랜덤 I/O 사슬로, 예상 효과를 숫자로
  3. 검증 EXPLAIN ANALYZE 전후 실측 + 쓰기 비용·다른 쿼리·DDL 리스크까지 한 호흡에
  4. 고정 slow log 임계치 · 쿼리 수 단정 · EXPLAIN 단정 · PR 템플릿을 설정과 코드로
연상: 측가검고. 각 단계의 산출물은 숫자 → 사슬+숫자 → 실측+대가 → 파일. 마지막이 "파일"이 아니면 아직 안 끝난 것.

4-1. 측정 — "느리다"를 네 개의 숫자로

입력은 사람의 제보가 아니라 로그와 지표여야 한다.

입력원무엇이 보이나이것만 보이는 것
slow query loglong_query_time을 넘긴 쿼리의 실행 시간, Lock_time, Rows_examined, Rows_sentRows_examined가 Rows_sent의 수천 배 → 그것만으로 "많이 읽고 대부분 버린다" 진단
performance_schema.events_statements_summary_by_digest파라미터를 정규화한 쿼리 패턴별 실행 횟수 · 총 시간 · 총 검사 행 수 누적 (sys.statement_analysis, sys.statements_with_full_table_scans가 보기 좋게 감쌈)"가장 느린"이 아니라 "가장 비싼" 쿼리
APM (Pinpoint, Datadog 등)어느 API 엔드포인트에서 어느 쿼리가 몇 번 호출되는지N+1 — 쿼리 하나는 빠른데 요청당 수백 번. slow log에는 안 잡히고 여기서만 보임
 
-- 총 비용 = 평균 시간 × 호출 횟수 순으로 정렬
SELECT DIGEST_TEXT,
       COUNT_STAR                          AS calls,
       SUM_TIMER_WAIT / 1e12               AS total_sec,
       SUM_TIMER_WAIT / COUNT_STAR / 1e9   AS avg_ms,
       SUM_ROWS_EXAMINED / COUNT_STAR      AS avg_rows_examined,
       SUM_ROWS_SENT / COUNT_STAR          AS avg_rows_sent
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
-- 1초짜리 하루 1회(총 1초)보다 50ms짜리 하루 10만 회(총 5,000초)가 병목이다
암기 카드측정 때 같이 적는 재현 조건 3 + 전제 1
  1. 어떤 파라미터에서 느린가 — 같은 쿼리도 user_id에 따라 대상 행 수가 100배 차이
  2. 어느 시간대인가 — 배치와 겹치는가
  3. 실행이 느린가, 락을 기다린 건가 — slow log의 Lock_time, SHOW PROCESSLIST의 State가 Waiting for …면 실행 계획이 아니라 동시성 문제
  4. 운영 규모 데이터에서 — 로컬 100건 테이블은 실행 계획 자체가 다르다. 작은 테이블에서 옵티마이저가 풀스캔을 고르는 건 정상이라 로컬 ALL이 운영에선 ref일 수 있고 그 반대도 있다

4-2. 가설 — 비용이 "어디서 새는지"를 사슬로 말한다

EXPLAIN을 §2 순서대로 읽으면서 "느리다"를 메커니즘 사슬로 번역하는 단계다. "성능 저하", "메모리 부하", "왔다갔다"에서 끝내지 않고 이름 붙은 단계로 끝까지 잇는다.

EXPLAIN에서 본 것뭉뚱그린 말사슬로 말하기
type: ref, rows: 48000, filtered: 10, Extra: Using where; Using filesort, SELECT *"인덱스는 타는데 느려요"인덱스로 PK 4만 8천 개 수집(순차, 쌈) → 각 PK로 클러스터드 인덱스 재탐색 4만 8천 번(랜덤 I/O, 비쌈) → 그중 90%를 status 필터에서 버림 → 남은 4,800건을 sort buffer에서 정렬 → 20건 반환. 비용 = 버릴 행에 쓴 랜덤 I/O + 정렬
안쪽 테이블 key: NULL, Extra: Using join buffer"조인이 느려요"드라이빙 행 수만큼 안쪽을 통순회 → 버퍼에 뭉텅이로 담아 비교하지만 결국 안쪽 전체 × 뭉텅이 수만큼 읽음 → 조인 키 인덱스 하나로 "행당 트리 탐색 1회"로 바뀜
Extra: Using filesort + LIMIT 20"정렬이 느려요"정렬 컬럼이 인덱스 순서와 안 맞음 → 대상 전부를 읽어 sort buffer에 적재 → 넘치면 디스크 임시 파일에 청크 저장 후 병합 → 그제야 앞 20건. 인덱스 순서와 맞추면 리프 앞 20건 읽고 끝
type: ALL, rows: 1000000"풀스캔이라 느려요"순차 I/O라 행당은 싸지만 총량이 100만 → 읽은 페이지가 버퍼 풀을 채우며 다른 쿼리의 캐시를 밀어냄(버퍼 풀 오염) → 이 쿼리만이 아니라 옆 쿼리까지 디스크로 떨어짐
select_type: DEPENDENT SUBQUERY"서브쿼리가 느려요"바깥 행마다 서브쿼리 재실행 → 바깥 10만 행이면 10만 번 → 조인 또는 파생 테이블로 한 번만 실행되게

가설에는 반드시 예상 효과를 숫자로 붙인다. "인덱스 추가하면 빨라질 것 같다"가 아니라 "(user_id, status, created_at) 인덱스를 만들면 rows가 4만 8천에서 20 근처로 줄고 filesort가 사라진다". 이렇게 써 두어야 검증 단계에서 맞았는지 틀렸는지를 판정할 수 있다. 숫자 없는 가설은 검증이 불가능하다.

4-3. 검증 — 실측으로 확인하고, 부작용까지 한 호흡에

가설대로 고친 뒤 같은 파라미터, 운영 규모 데이터에서 EXPLAIN ANALYZE를 전후로 비교한다.

BEFORE 312ms — rows 47215, Sort 노드 있음
-- -> Index lookup on o using idx_orders_user (user_id=100)  (actual time=0.05..271.3 rows=47215 loops=1)
-- -> Sort ... (actual time=312.4..312.4 rows=20 loops=1)
CREATE INDEX idx_orders_user_status_created
  ON orders (user_id, status, created_at);
--   등호(user_id) → 등호(status) → 정렬(created_at) 순: 두 등호로 좁힌 구간이
--   created_at 순으로 이미 정렬돼 있으므로 LIMIT 20이 리프 앞 20건에서 끝난다
AFTER 0.3ms — rows 20, Sort 노드 자체가 사라짐
-- -> Limit: 20 row(s)  (actual time=0.31..0.34 rows=20 loops=1)
--     -> Index lookup on o using idx_orders_user_status_created (user_id=100, status='ACTIVE') (reverse)
--          (actual time=0.05..0.19 rows=20 loops=1)     ← rows 47215 → 20

여기서 멈추면 반쪽이다. 이득만 말하고 대가를 안 붙이는 것을 이 단계에서 교정한다. 인덱스 추가의 대가는 정해져 있다.

한 호흡 템플릿 — [이득] → [대가] → [판단]

이득 "이 인덱스는 이 쿼리의 rows를 4만 8천에서 20으로 줄이고 filesort를 없애며 랜덤 I/O 4만 8천 번을 20번으로 만든다."

대가 "대신 orders에 INSERT/UPDATE가 일어날 때마다 B+Tree 하나를 더 갱신하고, 인덱스 크기만큼 디스크와 버퍼 풀을 더 쓰며, user_id를 선두로 쓰는 다른 쿼리들의 계획이 바뀔 수 있고, 수억 건 테이블이면 인덱스 생성 DDL 자체가 운영 리스크다."

판단 "그래서 기존 (user_id) 단독 인덱스는 새 인덱스의 선두 컬럼에 흡수되므로 삭제해 쓰기 대가를 상쇄하고, DDL은 온라인 방식으로 트래픽이 적은 시간에 건다."

암기 카드검증 체크리스트 4
  1. 대상 쿼리의 실측이 가설대로 개선됐는가 — actual rows, actual time
  2. 같은 테이블을 쓰는 상위 쿼리들의 EXPLAIN이 나빠지지 않았는가 — 새 인덱스는 옵티마이저의 선택지를 늘리고, 선택도 낮은 컬럼이 선두인 인덱스는 오히려 잘못된 길로 유인할 수 있다. digest 상위 목록에서 같은 테이블 쿼리를 골라 다시 EXPLAIN
  3. 쓰기 처리량이 허용 범위인가 — 쓰기 비중이 높은 테이블이면 인덱스 하나가 INSERT p95를 눈에 띄게 올린다
  4. DDL 실행 방식 — ALTER TABLE … ADD INDEX …, ALGORITHM=INPLACE, LOCK=NONE으로 온라인 생성이 가능한지, 불가능하면 pt-online-schema-change / gh-ost 같은 도구가 필요한지
연상: 대상 · 이웃 · 쓰기 · DDL — 내 쿼리, 옆 쿼리, 쓰는 쪽, 만드는 순간.

4-4. 고정 — 사람의 기억이 아니라 설정·테스트·파이프라인에

이 문서에서 가장 힘을 주는 절

"사람의 기억에 의존하지 않는 방법"을 물었는데 TODO 주석으로 답하는 것 — 안전망을 코드로 고정하는 습관의 부재는 반복되는 약점이다. 성능 개선은 한 번 고치는 것보다 재발을 잡는 구조를 남기는 것이 더 가치 있다. 같은 팀의 다른 개발자가 석 달 뒤 같은 패턴의 쿼리를 또 쓸 것이기 때문이다.

층 1

설정

측정이 자동으로 계속되게
  • slow query log 임계치를 my.cnf / 파라미터 그룹(IaC)에
  • "분당 slow log 건수" 알람, 임계치도 IaC 파일에
  • pt-query-digest 일일 리포트를 채널로
층 2

테스트

회귀가 CI에서 터지게
  • 쿼리 수 단정 테스트 (datasource-proxy / p6spy) — N+1 회귀
  • EXPLAIN 단정 테스트 (Testcontainers + 운영 규모 시드) — 인덱스 삭제·컬럼 순서 변경 회귀
층 3

파이프라인 · 템플릿

절차가 사람 기억 밖에 있게
  • 인덱스 DDL은 반드시 마이그레이션 파일로 (Flyway)
  • PR 템플릿에 DB 변경 체크 항목
  • 힌트에는 "왜·근거·재검토일" 주석 + 티켓
  • sys.schema_unused_indexes 월 1회 리포트
암기 카드고정 3층 — 설 · 테 · 파
  1. 설정이 측정한다 — slow log 임계치 + 알람을 코드로
  2. 테스트가 회귀를 잡는다 — 쿼리 수 단정 + EXPLAIN 단정을 CI에
  3. 파이프라인이 절차를 강제한다 — 마이그레이션 파일 + PR 템플릿
연상: 설테파 — "설정이 측정하고, 테스트가 회귀를 잡고, 템플릿이 절차를 강제한다." 그러면 다음 느린 쿼리는 사용자 항의가 아니라 slow log 알람으로 도착한다.

층 1 — 설정: slow query log 임계치와 알람을 코드로

BEFORE "느리면 누가 보겠지"
# long_query_time 기본값(10초)이면 9초짜리 쿼리는 영영 안 잡힌다
AFTER my.cnf 또는 RDS 파라미터 그룹 (Terraform으로 형상 관리)
[mysqld]
slow_query_log                = ON
long_query_time               = 0.5    # API p95 목표에서 역산한 값. 0.5초 넘는 쿼리는 전부 기록
log_queries_not_using_indexes = ON     # 시간과 무관하게 풀스캔 쿼리 기록
                                       # (소음이 크면 log_throttle_queries_not_using_indexes로 제한)
로그는 쌓이기만 하면 아무도 안 본다. pt-query-digest 일일 리포트를 채널로 보내거나, 로그 수집기(CloudWatch, Datadog)에서 "분당 slow log 건수" 알람을 건다. 알람 임계치 자체도 IaC 파일에 들어간다. 이러면 "측정"이 사람이 마음먹을 때가 아니라 항상 돌아간다.

층 2 — 테스트: 쿼리 수 단정과 EXPLAIN 단정을 CI에

5실무 사례 — 한 사이클을 처음부터 끝까지

"주문 목록 API가 느리다"는 제보를 사이클로 처리한 기록. 숫자는 예시다.

  1. ①

    측정

    APM에서 GET /orders p95 2.4초. digest 상위 1위는 SELECT * FROM orders WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20 — 평균 1.8초, 하루 12만 회, avg_rows_examined 4만 7천 / avg_rows_sent 20 → 2,350배를 읽어서 버린다. slow log의 Lock_time은 0에 가까워 락 문제는 아니다. 느린 파라미터는 주문이 많은 헤비 유저들 — user_id별 편차가 크다.

  2. ②

    가설

    EXPLAIN: type: ref, key: idx_orders_user, key_len: 8, rows: 48000, filtered: 10.00, Extra: Using where; Using filesort.

    사슬: user_id 인덱스로 4만 8천 개 PK를 모아 → 4만 8천 번 북마크 룩업(랜덤 I/O) → status 필터로 90% 폐기 → 4,800건 정렬 → 20건. 비용의 대부분이 "버릴 행의 랜덤 I/O"와 "정렬".

    처방 가설: (user_id, status, created_at) 복합 인덱스. 예상 효과(숫자): rows 4만 8천 → 20, filesort 제거, key_len 8 → 90.

  3. ③

    검증

    스테이징(운영 마스킹 덤프)에서 EXPLAIN ANALYZE 전후: 312ms → 0.3ms. 같은 테이블 digest 상위 5개 재확인 — 3개는 새 인덱스로 자연 이동(user_id 선두 동일), 2개는 무관. 기존 idx_orders_user는 새 인덱스에 흡수되므로 삭제 → 인덱스 수 유지, 쓰기 비용 증가분 상쇄. orders 3억 건이라 DDL은 ALGORITHM=INPLACE, LOCK=NONE 확인 후 새벽 배포.

    대가: 인덱스 크기 약 12GB 증가(status·created_at 추가분), 배포 중 복제 지연 모니터링 필요.

  4. ④

    고정

    Flyway 마이그레이션 2건(생성·삭제) / EXPLAIN 단정 테스트 1건 추가 / long_query_time을 1초에서 0.5초로 내리고 알람 연결 / PR 템플릿에 DB 체크 항목 추가.

    다음 주 같은 팀원이 orders에 WHERE user_id = ? AND payment_method = ? 쿼리를 올렸을 때, PR 템플릿이 EXPLAIN을 요구했고 filtered: 5.00이 리뷰에서 잡혔다. 이것이 고정의 효과다.

6꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 트레이드오프를 한 호흡에 말해야 하는 문항, 퀴즈는 숫자 계산 문항.

rows 추정이 실제와 크게 다르면 무엇을 의심하고, 어떻게 확인·수정하나요?

통계 정보가 현실과 어긋난 것을 첫째로 의심한다. 옵티마이저는 통계로 추정하고, 통계는 샘플링으로 만들어지며, 대량 적재·삭제 직후나 데이터 분포가 편중된 컬럼에서 잘 틀린다.

확인: EXPLAIN ANALYZE의 추정 rows와 actual rows 비교 — 자릿수가 다르면 확정이다.

수정 3단계: ⑴ ANALYZE TABLE로 통계 재수집 → ⑵ 그래도 틀리면 샘플링 페이지 수(innodb_stats_persistent_sample_pages)를 늘려 정밀도를 올림 → ⑶ 값 분포가 편중된 컬럼(90%가 ACTIVE인 status 같은)이라면 MySQL 8의 히스토그램(ANALYZE TABLE … UPDATE HISTOGRAM ON status). 기본 통계는 "서로 다른 값 몇 개"만 알지 "어느 값이 몇 %인지"는 모르는데, 히스토그램이 그 분포를 알려준다. 이 세 단계를 다 밟은 뒤에야 힌트를 검토한다. "코드도 쿼리도 안 바꿨는데 느려졌다"의 정체가 대개 이것이다.

EXPLAIN 결과는 좋은데(ref, rows 작음) 운영에서 느립니다. 어디를 보나요?

EXPLAIN은 "쿼리 하나의 계획"이지 "요청 하나의 비용"이 아니다라는 전제에서 출발한다. 순서대로 다섯 군데:

  1. EXPLAIN에 넣은 파라미터가 느린 그 파라미터인가 — user_id = 1(주문 3건)과 user_id = 100(4만 건)은 같은 쿼리, 다른 비용. slow log에서 실제 느렸던 값을 가져와 다시 본다.
  2. 실행이 아니라 대기인가 — Lock_time, SHOW PROCESSLIST의 State. 계획이 완벽해도 앞 트랜잭션의 락을 기다리면 느리다.
  3. 호출 횟수 — 3ms짜리 쿼리가 요청당 500번 돌면 1.5초. N+1은 EXPLAIN에 절대 안 보이고 APM이나 쿼리 수 단정 테스트에만 보인다.
  4. 버퍼 풀 미스 — 계획은 같아도 페이지가 메모리에 있느냐 디스크에 있느냐로 100배 차이. 새벽 첫 호출, 배치 직후(버퍼 풀 오염)가 전형.
  5. 결과셋 크기와 네트워크 — SELECT *로 TEXT 컬럼 수천 건을 끌어오면 DB는 빠른데 전송이 느리다.

EXPLAIN ANALYZE가 이 중 ⑴과 ⑷를 실측으로 갈라준다. 연상: 값 · 대기 · 횟수 · 캐시 · 전송.

인덱스를 추가하면 다른 쿼리가 느려질 수도 있나요? 그걸 어떻게 미리 아나요?시니어 변별

있다. 세 경로다.

  1. 쓰기 경로: 모든 INSERT/UPDATE/DELETE가 B+Tree 하나를 더 갱신하므로 쓰기 p95가 오른다 — 쓰기 비중이 높은 테이블일수록 체감이 크다.
  2. 옵티마이저 오유인: 선택지가 늘면 옵티마이저가 새 인덱스를 잘못 고를 수 있다. 특히 선두 컬럼의 선택도가 낮은 인덱스는 "일단 이걸 타볼까"로 유인해 북마크 룩업 폭탄을 만든다.
  3. 버퍼 풀 경쟁: 인덱스도 메모리에 올라오므로, 큰 인덱스 하나가 다른 테이블의 핫 페이지를 밀어낸다.

미리 아는 방법: 검증 체크리스트 2번 — 같은 테이블을 쓰는 digest 상위 쿼리를 골라 새 인덱스 생성 후 EXPLAIN을 다시 뜬다. 그리고 이 재확인을 사람이 기억하지 않도록 PR 템플릿에 항목으로 박고, 핵심 쿼리는 EXPLAIN 단정 테스트로 고정한다.

한 호흡: "이 인덱스는 조회 쿼리 A의 랜덤 I/O를 없애는 대신 쓰기 비용·메모리·옵티마이저 선택지라는 세 대가를 내고, 그 대가가 허용 범위인지는 digest 재확인과 쓰기 p95로 검증한다."

EXPLAIN ANALYZE를 운영 DB에서 그냥 돌려도 되나요?

조건부다. 실제로 실행하므로 ⑴ 무거운 SELECT는 그 자체가 부하고 버퍼 풀을 오염시킨다, ⑵ UPDATE/DELETE에 붙이면 데이터가 실제로 바뀐다.

원칙은 읽기 복제본이나 운영 규모 스테이징에서 돌리는 것. 운영 프라이머리에서 꼭 해야 한다면 SELECT만, 트래픽 낮은 시간에, 필요하면 LIMIT으로 범위를 줄여서. 변경문은 트랜잭션을 열고 ROLLBACK하거나 SELECT로 바꿔서 본다.

대신 일반 EXPLAIN은 실행하지 않으므로 운영에서 언제든 안전하다 — 첫 진단은 EXPLAIN, 괴리 확인은 EXPLAIN ANALYZE. 이 분업을 말하면 된다.

이 프로세스를 팀에 정착시키려면 무엇부터 코드로 고정하나요? 우선순위와 이유를 말해주세요.시니어 변별

비용 대비 효과 순으로 네 단계다.

  1. slow query log 임계치 + digest 대시보드 — 측정이 없으면 나머지 전부가 시작을 못 한다. 설정 몇 줄이라 비용이 가장 싸고, 이것만으로 "어디가 비싼지"가 매일 보인다.
  2. 쿼리 수 단정 테스트 — 실무에서 가장 흔한 성능 회귀는 인덱스 누락이 아니라 N+1이고, N+1은 slow log에 안 잡힌다. datasource-proxy 하나 붙이고 핵심 조회 메서드에 단정 3~4개면 된다.
  3. 인덱스 DDL의 마이그레이션 강제 + PR 템플릿 — 도구가 아니라 규칙이지만 파일로 박으면 리뷰어 기억에서 독립한다.
  4. EXPLAIN 단정 테스트 — 운영 규모 시드 데이터가 필요해 비용이 가장 크므로 마지막이고, 장애를 겪은 핵심 쿼리부터 하나씩 늘린다.

이 순서를 뒤집어 ⑷부터 하면 시드 데이터 관리에 지쳐 중단되고, ⑴을 빼면 무엇을 테스트할지조차 모른다. "측정 → 가장 흔한 회귀 → 절차의 파일화 → 정밀 회귀 방지" 순이다.

ORDER BY가 인덱스를 타는 조건은? filesort는 언제 발생하고 왜 문제인가요?

인덱스를 타는 조건 — 정렬 컬럼이 인덱스 안에서 "이미 그 순서로 놓여 있어야" 한다.

  1. WHERE의 등호 조건 컬럼들 바로 뒤에 정렬 컬럼이 이어지는 복합 인덱스일 것. 예) (user_id, status, created_at) + WHERE user_id = ? AND status = ? ORDER BY created_at — 두 등호로 좁힌 구간 안은 이미 created_at 순이다.
  2. 범위 조건(>, BETWEEN) 컬럼 뒤의 컬럼으로는 정렬을 못 탄다 — 구간 안에서 그 다음 컬럼의 순서가 보장되지 않기 때문. WHERE user_id = ? AND created_at > ? ORDER BY amount는 filesort.
  3. 정렬 방향이 인덱스 방향과 일치하거나 전부 반대(역방향 스캔 — 앞 예시의 (reverse))일 것. 컬럼마다 ASC/DESC를 섞으려면 MySQL 8의 DESC 인덱스로 그 방향대로 정의해야 한다.
  4. 조인이면 드라이빙 테이블의 컬럼으로만 정렬해야 인덱스 순서를 그대로 쓸 수 있다.

filesort가 발생하는 때: 위 조건 중 하나라도 깨져 인덱스 순서로 결과를 낼 수 없을 때. 왜 문제인가: LIMIT 20이어도 대상 전부를 읽어 sort buffer에 적재하고, 넘치면 디스크 임시 파일에 청크로 저장한 뒤 병합해서야 앞 20건을 낸다. 인덱스 순서와 맞추면 리프 앞 20건 읽고 끝 — 앞 사례에서 Sort 노드가 사라지며 312ms → 0.3ms가 된 이유다.

잘 돌던 쿼리의 실행 계획이 어느 날 갑자기 바뀌어 느려졌습니다. 가능한 원인과 대응은?시니어 변별

코드도 쿼리도 안 바꿨는데 계획이 바뀌었다면 옵티마이저의 입력(통계·데이터 분포·선택지)이 바뀐 것이다.

원인 후보: ⑴ 통계 갱신 또는 노후 — 대량 적재·삭제 뒤 자동 재수집된 통계가 이전과 다른 계획을 고르게 함. ⑵ 데이터 분포 변화 — 특정 값의 비중이 커지며 선택도가 역전돼 옵티마이저가 인덱스 대신 풀스캔(또는 다른 인덱스)을 선택. ⑶ 파라미터 편차 — 헤비 유저처럼 대상 행 수가 100배 큰 값이 새로 생김. ⑷ 누군가 인덱스를 추가·삭제해 선택지가 바뀜(콘솔에서 손으로 만든 인덱스가 전형).

대응 순서: ① 지금 도는 쿼리는 SHOW PROCESSLIST → EXPLAIN FOR CONNECTION으로 현재 계획을 확인 → ② EXPLAIN ANALYZE로 추정 rows vs 실측 비교 → ③ 자릿수가 어긋나면 ANALYZE TABLE → 샘플링 페이지 수 → 히스토그램 순으로 통계를 고침 → ④ 그래도 안 되면 힌트(FORCE INDEX)를 쓰되 "왜·근거·재검토일" 주석과 티켓을 남긴다(만료일 있는 부채). 고정: 인덱스 변경이 원인이었다면 DDL을 마이그레이션 파일로만 하도록 강제하고, 그 쿼리를 EXPLAIN 단정 테스트에 올린다.

type: index면 인덱스를 탄 것 아닌가요? 왜 나쁘다고 하나요?

index는 인덱스 풀스캔 — 리프를 처음부터 끝까지 읽는다. 조건으로 범위를 좁힌 게 아니라 전부 읽되 테이블보다 좁은 자료구조를 읽는 것뿐이라, 경계선(range | index)의 오른쪽, 즉 ALL과 같은 "전부 읽은 것" 부류다. 조건은 못 좁히는데 필요한 컬럼이 인덱스에 다 있을 때(커버링)나 인덱스 순 정렬만 필요할 때 나온다. "인덱스는 탔는데요"가 type: index를 가리키면 그건 탄 게 아니다.

Extra: Using where가 보이면 무조건 문제인가요?

아니다. Using where는 "스토리지 엔진에서 받은 행을 서버 층에서 한 번 더 거른다"는 뜻으로 그 자체는 흔하다. 문제가 되는 건 rows가 크고 filtered가 낮은 것과 함께 있을 때 — 많이 읽어 올려서 서버 층에서 대부분 버린다는 신호다. 이때 처방은 버려지는 조건의 컬럼을 인덱스에 넣어 rows 자체를 줄이는 것(또는 ICP로 Using index condition이 되게 하는 것)이다.

인덱스 (user_id BIGINT NOT NULL, status VARCHAR(20) NOT NULL, created_at)에서 WHERE user_id = ? AND created_at > ?의 key_len은?퀴즈

8. user_id(BIGINT NOT NULL = 8)까지만 쓰였다. 가운데 status 조건이 없어 계단이 끊기므로 created_at은 인덱스 탐색에 못 쓰인다(leftmost prefix). key에는 인덱스 이름이 찍혀 있어 "인덱스 탔다"고 안심하기 쉬운 경우다. 참고로 WHERE user_id = ? AND status = ?면 8 + (20×4+2) = 90.

(actual time=0.003..0.003 rows=1 loops=4720)인 안쪽 테이블 노드의 총 소요 시간은?퀴즈

약 14ms. actual time은 한 번 실행의 first..last이고 loops만큼 반복된 평균이므로 0.003 × 4720 ≈ 14ms. 안쪽 테이블은 반드시 loops를 곱해서 읽는다 — 안 곱하면 "조인은 0.003ms밖에 안 걸리는데?"라는 오독이 나온다.

"가장 느린 쿼리"부터 잡으면 되나요?

아니다. 우선순위 기준은 "가장 비싼 쿼리" = 평균 시간 × 호출 횟수다. 1초짜리 하루 1회(총 1초)보다 50ms짜리 하루 10만 회(총 5,000초)가 병목이다. performance_schema.events_statements_summary_by_digest를 SUM_TIMER_WAIT DESC로 정렬하면 이 순서가 나온다. 같은 이유로 N+1은 개별 쿼리가 빨라 slow log에 안 잡히고 호출 횟수를 보는 APM이나 쿼리 수 단정 테스트에서만 보인다.

7인출 연습 — 카드 뒤집기

이 문서의 "목록"들만 모았다. 제목과 개수만 보고 항목을 전부 말한 뒤 카드를 눌러 확인한다. 순서까지 맞아야 한다.

한 줄 요약

EXPLAIN은 통계로 쓴 견적서, EXPLAIN ANALYZE는 실행해 받은 청구서다 — 견적서는 행 순서 → type(경계선 range|index) → key·key_len(몇 번째 컬럼까지) → rows×filtered(읽어서 남기는 비율) → Extra(filesort·temporary·join buffer 위험, Using index 최고) 순으로 읽고, 두 문서의 rows가 어긋나면 튜닝이 아니라 통계 갱신이 먼저다. 느린 쿼리 개선은 측정(가장 비싼 쿼리를 숫자로) → 가설(비용이 새는 지점을 랜덤 I/O 사슬로, 예상 효과를 숫자로) → 검증(실측 + 쓰기 비용·다른 쿼리·DDL 리스크까지 한 호흡에) → 고정(slow log 임계치·쿼리 수 단정·EXPLAIN 단정·PR 템플릿을 설정과 코드로)의 사이클이며, 고정까지 가야 다음 느린 쿼리가 사용자 항의가 아니라 알람으로 도착한다.
