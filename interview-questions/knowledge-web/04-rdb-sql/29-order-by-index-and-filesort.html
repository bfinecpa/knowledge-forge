ORDER BY와 filesort

정렬은 인덱스 순서를 "빌리거나", 전부 읽어 "다시 줄 세우거나" 둘 중 하나다

리프 순서 = 정렬 순서유일한 공짜 경로 접 · 범 · 방 · 한 · 원 · 드인덱스를 타는 조건 6 읽 · 적 · 스 · 머 · 자 · 재filesort 6고리 비용 ∝ N, not LIMIT결과 20건 · 일은 8만 건
핵심 관전 포인트 — 첫 답변으로 그대로 말하기

ORDER BY가 공짜가 되는 경우는 하나뿐이다 — 옵티마이저가 고른 인덱스의 리프 순서가 곧 정렬 순서일 때. 그 조건은 여섯 개를 세트로 꺼낸다.

  1. 접 — WHERE 등호 컬럼 + ORDER BY 컬럼이 인덱스 선두부터 빈칸 없이 연속
  2. 범 — 범위 조건(IN 포함) 뒤 컬럼으로는 정렬 불가, 범위 컬럼 자체로는 가능
  3. 방 — 방향이 전부 같거나 전부 반대(역방향 스캔), 혼합은 MySQL 8 내림차순 인덱스로만
  4. 한 — WHERE와 ORDER BY가 한 인덱스 안에서
  5. 원 — 컬럼 원형 그대로, 함수·연산·RAND() 없음
  6. 드 — 조인이면 드라이빙 테이블 컬럼만

하나라도 깨지면 filesort — 이름과 달리 메모리에서도 하지만 본질은 "WHERE에 맞는 N건을 전부 읽어 sort buffer에 적재 → 넘치면 임시 파일에 청크로 쓰고 다시 읽어 병합 → 그제야 LIMIT 20"이라 비용이 결과 20건이 아니라 매칭 행 수 N에 비례한다. 인덱스 순서를 타면 구간 끝에서 20건 읽고 멈춘다. 그래서 WHERE만 보고 인덱스를 걸면 반쪽이고 "등·범·정·커"의 정(정렬) 자리까지 채워야 완성이며, 정렬 축이 여럿인 화면은 "축마다 인덱스"가 아니라 N × 빈도 × 정렬 컬럼 변동성으로 인덱스/허용/사전 집계를 갈라 결정하고, 그 결정을 EXPLAIN 단정 테스트와 Sort_merge_passes·Sort_rows 알람으로 고정한다.

질문

"ORDER BY가 인덱스를 타는 조건은? filesort는 언제 발생하고 왜 문제가 되나요?"

관련 문서 (전제로 삼는 것들)

복합 인덱스 컬럼 순서 — "등·범·정·커" 네 자리 · 깊은 페이지네이션 — offset 비용 · 실행 계획 읽기 — EXPLAIN 순서 · 커버링 인덱스 — Using index의 뜻. 이 페이지는 그중 정렬 축 하나만 깊게 판다.

출제 의도 — "목록 조회의 기본형(WHERE+ORDER BY+LIMIT)에서 정렬이 인덱스를 못 타면 매 요청이 정렬 작업이 된다. WHERE 조건만 보고 인덱스를 설계하는 반쪽 습관을 가리는 질문." 즉 "인덱스가 있는가"가 아니라 "인덱스가 정렬까지 책임지는가"를 묻는다. 목록 API는 거의 예외 없이 WHERE … ORDER BY … LIMIT 20 꼴이고, 여기서 정렬이 새면 결과는 20건인데 비용은 조건에 맞는 전체 행 수가 된다 — 데이터가 늘수록 첫 페이지부터 느려지는 가장 흔한 목록 장애의 정체다.

면접관이 보는 세 가지: ⑴ 인덱스가 정렬을 대신하는 조건을 목록으로 꺼내는가 ⑵ filesort 비용을 "느리다"가 아니라 메커니즘으로 말하는가 ⑶ 정렬 컬럼을 인덱스에 넣는 대가와 정렬 축이 여러 개인 화면의 판단까지 가는가.

이 페이지가 겨냥하는 네 지점 (4장 전 구간에서 반복된 패턴)
  • 비용을 이름 붙은 사슬로 — 읽기 → 적재 → 스필 → 머지 → 자르기 → 재조회, 인덱스 경로의 "20건 읽고 중단"과 나란히 (§3)
  • 트레이드오프를 양면으로 — 정렬 컬럼을 인덱스에 넣으면 무엇을 내주는지, 정렬 5개 화면에서 인덱스/허용/사전 집계를 가르는 기준 (§6)
  • 안전망을 코드로 — EXPLAIN 단정 테스트, Sort_merge_passes 알람, 정렬 축 enum (§8)
  • 목록 인출 — 조건 6 · 패턴 7 · Extra 세 조합을 세트로 즉시 (§2, §4, §9 드릴)

1원리 — 정렬을 공짜로 얻는 조건은 "리프 순서 = 정렬 순서" 하나뿐이다

B+Tree 리프는 키 순서로 정렬된 연결 리스트다.
읽고 있는 구간의 순서가 ORDER BY가 원하는 순서와 같으면 — 정렬은 이미 돼 있다. 다르면? 읽은 것을 어딘가에 모아 다시 줄 세우는 수밖에 없다 — 그게 filesort다.

웹툰 목록 쿼리 하나를 끝까지 따라가면 원리가 그림 한 장으로 남는다.

WHERE genre = 'ROMANCE' AND status = 'ACTIVE'
ORDER BY updated_at DESC LIMIT 20;     -- 인덱스 (genre, status, updated_at)

3filesort는 왜 비싼가 — "느리다"가 아니라 사슬로

3-1. filesort의 실체 — 이름은 파일, 본질은 "서버 계층의 별도 정렬 단계"

누가
스토리지 엔진(InnoDB)이 아니라 그 위층 SQL 서버 계층. 엔진은 조건에 맞는 행을 한 건씩 올려 보낼 뿐, 서버가 모아서 정렬한다 — LIMIT/OFFSET을 세는 것과 같은 층
이름의 함정
옛날엔 반드시 파일에 썼기에 붙은 이름. 지금은 메모리 안에서 끝나도 똑같이 Using filesort. "filesort = 디스크 정렬"로 외우면 틀리고, "인덱스 순서를 못 빌려서 별도 정렬 단계를 붙였다"로 외운다
어디에
세션마다 정렬용 메모리 sort_buffer_size를 잡는다. 정렬할 데이터가 이 크기를 넘으면 그때 디스크 임시 파일로 간다
무엇을 — 모드 둘 가산점
rowid 모드(two-pass): <정렬 키, PK>만 정렬하고 상위 N건의 PK로 테이블을 다시 찾는다. addon fields 모드(single-pass): <정렬 키, SELECT 컬럼 전부>를 넣어 재조회는 없지만 버퍼가 더 빨리 넘친다. 8.0은 대체로 후자, 긴 TEXT/BLOB이 끼면 전자로 떨어진다 → SELECT *는 정렬 비용까지 키운다

3-2. 비용 사슬 — filesort 6고리 vs 인덱스 3고리 (암기: 읽·적·스·머·자·재)

여기가 "성능 저하"·"메모리 부하"에서 멈추던 지점이다. 고리마다 이름을 붙여 끝까지 잇고, 인덱스 경로와 나란히 놓는다. 두 경로의 차이는 속도가 아니라 비용이 무엇에 비례하는가다.

비유 — 전교 성적 상위 20명 뽑기. 성적순 명부(인덱스)가 있으면 첫 장에서 20명 읽고 덮는다. 없으면 전교생 답안지 N장을 다 걷어(읽기) 책상(sort buffer)에 펼치고(적재), 책상이 좁으면 바닥에 묶음으로 내려놨다가(스필) 다시 합쳐 줄 세운(머지) 뒤에야 위에서 20장을 자른다(자르기). 번호만 적어 정렬했다면 그 20명의 답안지를 다시 찾아와야(재조회) 한다. 20명을 뽑는 데 든 일은 20이 아니라 N이다.
면접에서 말하는 문장 — 한 호흡
"filesort는 조건에 맞는 8만 건을 전부 읽어 정렬 버퍼에 넣고, 버퍼가 넘치면 디스크 임시 파일에 썼다 다시 읽어 병합한 다음에야 20건을 자릅니다. 비용이 LIMIT이 아니라 매칭 행 수에 비례하죠. 인덱스 순서를 타면 구간 끝에서 20건 읽고 멈춥니다."

3-3. "왜 문제인가" — 세 겹, 그리고 "언제는 문제가 아닌가"

⑴ 비례 대상이 틀렸다
결과는 20건, 일은 N건. 그래서 ⓐ 데이터 10배 → 첫 페이지부터 10배 느림 ⓑ 개발 DB(N=50)에선 절대 안 보이고 운영(N=8만)에서 터짐 ⓒ 파라미터마다 N이 100배 다름(로맨스 8만 vs 스릴러 800) → p50은 멀쩡한데 p99가 널뛰는 목록 API의 정체
⑵ 자원이 공유 자원이다
sort buffer는 세션마다 — 동시 200요청 = 버퍼 200개. 스필 파일은 tmpdir을 모든 세션이 공유 — 한 쿼리의 정렬이 옆 쿼리의 임시 테이블과 I/O를 다투고, 극단에선 무관한 쿼리까지 실패. "이 쿼리가 느리다"가 아니라 옆 쿼리를 느리게 만드는 이유
⑶ 응답이 "다 읽은 뒤" 시작
인덱스 경로는 첫 행을 바로 흘려보내지만 filesort는 마지막 행까지 읽고 정렬을 마쳐야 첫 행이 나간다 → 그동안 커넥션을 물고 있다 → 목록 API 하나가 커넥션 풀을 잠식. FOR UPDATE에 붙은 정렬이면 N건의 락을 정렬 끝까지 쥔다
언제는 문제가 아닌가 — 세 겹은 전부 N이 클 때 성립한다. N이 수백 건이고 메모리 안에서 끝나며 호출 빈도가 낮으면 filesort는 밀리초 아래다. 문제는 filesort라는 단어가 아니라 "정렬 입력 N의 크기 × 빈도"다. Using filesort를 보자마자 인덱스를 추가하는 것도 또 하나의 반쪽 습관이다 — 이 판단이 §6의 매트릭스로 이어진다.

4EXPLAIN에서 읽기 — Extra 세 조합과 Sort 노드

Extra뜻 (한 줄)위험도 · 처방 방향
Using filesort서버 계층 정렬 단계가 붙었다 — 읽은 행을 sort buffer로. 한 단계N에 비례. 인덱스에 "정" 자리 채우기, 또는 N이 작으면 허용(선언)
Using temporary;
Using filesort		정렬 전에 중간 결과를 임시 테이블로 물질화 — 조인 드리븐 컬럼 정렬, GROUP BY와 다른 ORDER BY, DISTINCT·UNION. 두 단계가장 위험. 임시 테이블도 한도를 넘으면 디스크(Created_tmp_disk_tables) — 스필이 두 군데. 인덱스가 아니라 쿼리 구조를 바꿔야 한다
Using index;
Using filesort		커버링이라 테이블 접근 0(읽기는 싸다)인데 인덱스 순서가 정렬과 안 맞아 정렬은 남았다읽기 최적 · 정렬 미해결. 대개 "접두사 빈칸"이나 "컬럼 순서" — 순서를 바꾸면 둘 다 해결되는 신호
Backward index scan인덱스를 뒤에서 앞으로 읽어 DESC를 처리했다좋은 신호. 정렬을 인덱스가 해결했다는 뜻
(없음 / Using where만)정렬이 인덱스 순서로 해결됐다좋음

외우는 말: temporary는 "두 번 쌓는다", index; filesort는 "읽기는 공짜, 정렬은 남았다", Backward는 "잘 됐다".

Using index; Using filesort — 예 하나를 고정한다

-- 인덱스 (status, genre, updated_at). 쿼리는 genre 없이:
EXPLAIN SELECT id, updated_at FROM webtoon
WHERE status = 'ACTIVE' ORDER BY updated_at DESC LIMIT 20;
-- type: ref  key: idx_webtoon_status_genre_updated
-- Extra: Using where; Using index; Using filesort
--   읽기: 필요한 컬럼(status, updated_at, id)이 전부 인덱스에 있어 테이블엔 안 간다 → 싸다
--   정렬: status 구간 안은 genre별로 따로 updated_at 순 → 전체 순서가 아니다 → 모아서 정렬 (패턴 ③ 빈칸)
--   해석: "ACTIVE 전체(수십만)를 리프에서 순차로 읽어(싸다) 전부 정렬한다(비싸다)"
--   처방: 이 쿼리가 뜨겁다면 (status, updated_at) 인덱스, 아니면 허용 — N을 보고 정한다
EXPLAIN ANALYZE 에서는 두 가지만 본다
  1. Sort: 노드의 존재 — 있으면 filesort, 사라지면 인덱스가 정렬을 해결한 것
  2. 그 바로 아래 노드의 rows — 그 값이 정렬 입력 N이다. LIMIT 20인데 8만이면 §3 사슬이 돌고 있다

limit input to 20 row(s) per chunk는 우선순위 큐 최적화가 적용됐다는 표시(§9 첫 꼬리질문). EXPLAIN FORMAT=JSON에서는 ordering_operation.using_filesort 불리언 하나로 떨어져 테스트 단정에 쓰기 좋다(§8-1).

가산점 옵티마이저 트레이스의 filesort_summary (SET optimizer_trace='enabled=on') 에는 정렬한 행 수, 스필된 임시 파일 수, 사용한 sort buffer 크기, sort_mode(<fixed_sort_key, rowid> vs <fixed_sort_key, packed_additional_fields>)가 실측으로 남는다. "이 filesort가 메모리에서 끝났는지, 몇 번 디스크에 갔는지"를 쿼리 하나 단위로 보는 가장 정확한 창.

5"등·범·정·커"에서 "정"의 자리 — WHERE만 보는 반쪽 습관

복합 인덱스 컬럼 순서의 네 자리 중 "정"이 이 문서의 자리다. 습관적으로 WHERE 컬럼만 보고 인덱스를 걸면 "등"까지만 채우고 멈춘 것이다. 화면: 장르 탭 → 연재 중 작품을 최신 업데이트순으로 20개 (홈 트래픽의 대부분).

BEFORE WHERE만 보고 건 인덱스 — "등"까지만 채웠다
CREATE INDEX idx_webtoon_genre_status ON webtoon (genre, status);
-- EXPLAIN
--   type: ref   key: idx_webtoon_genre_status   rows: 80000
--   Extra: Using where; Using filesort   ← 로맨스·연재중 8만 건을 전부 모아 정렬한 뒤 20건
-- EXPLAIN ANALYZE
--   -> Limit: 20 row(s)                             (actual time=96.3..96.3 rows=20)
--       -> Sort: webtoon.updated_at DESC, limit input to 20 row(s) per chunk
--           -> Index lookup on webtoon using idx_webtoon_genre_status
--                (genre='ROMANCE', status='ACTIVE')  (actual time=0.07..81.9 rows=80000)

Sort 노드가 있고, 그 아래 노드의 rows가 8만 — "정렬에 들어간 입력"이 8만 건이라는 뜻. 시간의 거의 전부(81.9ms)가 Sort 아래, 즉 버릴 79,980건을 읽는 데 쓰였다.

AFTER "정"의 자리를 채운다 — 등호 두 개 뒤에 정렬 컬럼
DROP INDEX idx_webtoon_genre_status ON webtoon;   -- 접두사가 같으니 교체 (중복 방지)
CREATE INDEX idx_webtoon_genre_status_updated ON webtoon (genre, status, updated_at);
-- EXPLAIN
--   type: ref   key: idx_webtoon_genre_status_updated
--   Extra: Using where; Backward index scan   ← filesort 없음. DESC라 뒤에서 앞으로 읽는다
-- EXPLAIN ANALYZE
--   -> Limit: 20 row(s)                             (actual time=0.05..0.09 rows=20)
--       -> Index lookup on webtoon using idx_webtoon_genre_status_updated
--            (genre='ROMANCE', status='ACTIVE') (reverse)  (actual time=0.04..0.08 rows=20)

Sort 노드 자체가 사라졌고 rows=20 — 20건 읽고 멈췄다. 96ms → 0.1ms. 대가: 인덱스 폭에 updated_at만큼, 회차 업로드 때 엔트리 이동 1회(작품당 주 1~2회라 무시 가능).

함정 — "정"을 "등"보다 앞에 두면? 정렬만 급해서 (genre, updated_at, status)로 만들면 genre 구간이 updated_at 순이라 정렬은 인덱스가 해결한다. 하지만 status는 등호인데도 정렬 컬럼 뒤에 있어 탐색 조건에서 필터로 강등된다 — 리프를 최신순으로 걸으며 ACTIVE가 아닌 엔트리를 버리면서 20건을 채운다.
조회 값비율20건을 채우려고 걷는 엔트리
status = 'ACTIVE'60%≈ 33건 — 티가 안 난다
status = 'SUSPENDED'1%≈ 2,000건 — 같은 인덱스, 60배
등호 → 정렬 순서 (genre, status, updated_at)어느 값이든20건
비용이 필터 선택도에 따라 널뛰는 구조다. "등·범·정·커"의 순서가 중요한 이유가 정렬 축에서 이렇게 드러난다.

6트레이드오프 — 정렬 컬럼을 인덱스에 넣는 대가, 그리고 "정렬 5개" 판단

6-1. 대가부터 — 정렬 컬럼 하나가 인덱스에 들어가면

얻는 것내주는 것
정렬 단계 제거 — 비용이 N → LIMIT인덱스 폭↑ → 페이지당 엔트리↓ → 버퍼 풀 적재율↓
첫 행 즉시 반환, 커넥션 점유↓쓰기 증폭 — 정렬 컬럼 값이 바뀔 때마다 엔트리가 옛 자리에서 지워지고 새 자리에 꽂힌다(삭제+삽입)
커서 페이지네이션의 전제 확보정렬 축마다 인덱스면 인덱스 수↑ → DML당 갱신 트리 수↑, 옵티마이저 후보 혼선↑

두 번째 줄이 핵심이다. 세컨더리 인덱스는 값 순서로 놓이므로 정렬 컬럼이 자주 바뀔수록 인덱스가 자주 움직인다. 후보 컬럼의 변동성을 나란히 놓으면 판단이 저절로 갈린다.

created_at
불변. 삽입 때 한 번 꽂히고 끝 — 인덱스 대가 0에 가깝다
updated_at
회차가 올라올 때마다(작품당 주 1~2회). 엔트리가 구간 끝으로 이동하지만 빈도가 낮아 감당 가능
rating_avg
평점이 들어올 때마다 소수점이 바뀐다. 인기작이면 분 단위
view_count
조회할 때마다. 인덱스를 걸면 모든 페이지뷰가 인덱스 엔트리 이동 — 초고빈도 카운터 문제가 인덱스까지 번지는 최악의 조합

6-2. 정렬 기준이 5개인 화면 — "축마다 인덱스"가 답이 아닌 이유

장르 탭에 정렬 옵션이 최신순 / 신작순 / 인기순 / 별점순 / 제목순 다섯 개. "(genre, status, X)를 다섯 개 만들자"는 위 대가를 다섯 배로 지불하겠다는 뜻이고, 그중 view_count 인덱스는 서비스를 세운다. 판단 기준은 셋을 곱한다.

N×요청 비중×정렬 컬럼 변동성(+ 커버링 필요 여부)
N = WHERE 후 매칭 행 수. 앞의 둘이 "인덱스로 얻는 것", 셋째가 "인덱스로 내주는 것"의 크기
정렬컬럼요청 비중(예)변동성판단
최신순updated_at70%낮음 (회차 업로드)인덱스 — 기본 정렬, 트래픽 대부분
신작순created_at5%없음N 크면 인덱스 (불변이라 쓰기 대가 ≈ 0) · 작으면 허용
인기순view_count15%매 조회라이브 컬럼 인덱스 금지 → 사전 집계 (랭킹 스냅숏 테이블 / Redis Sorted Set)
별점순rating_avg5%중간집계 컬럼을 일 배치로 갱신하면 인덱스 가능, 아니면 filesort 허용
제목순title5%없음N 수만 · 저빈도면 filesort 허용 (콜레이션 정렬 키가 넓지만 빈도가 낮다)
읽는 법 — 네 줄 규칙: 기본은 인덱스 · 불변은 싸다 · 라이브 카운터는 금지 · 저빈도는 선언
  1. 기본 정렬은 무조건 인덱스 — 요청 비중이 압도적이라 N × 빈도가 가장 크다
  2. 변동성 큰 컬럼은 라이브 값에 인덱스를 걸지 않고 사전 집계 산출물에 건다 — "실시간 카운터"를 "10분 전 스냅숏"으로 바꾸는 건 기획과 합의할 요구사항 변경이지만, 대부분의 랭킹은 그래도 된다
  3. 저빈도 + N 감당 가능 + 불변 컬럼은 filesort를 허용하고 그 사실을 목록에 적는다 — "허용"은 방치가 아니라 선언이다(§8-1의 테스트가 그 목록을 읽는다)
  4. 이 표는 한 번 정하고 끝이 아니라 Sort_rows·p99로 재검토한다(§8-2)
BEFORE 정렬 옵션 수만큼 인덱스
CREATE INDEX idx_w_gs_updated ON webtoon (genre, status, updated_at);
CREATE INDEX idx_w_gs_created ON webtoon (genre, status, created_at);
CREATE INDEX idx_w_gs_views   ON webtoon (genre, status, view_count);  -- 매 조회 = 엔트리 이동
CREATE INDEX idx_w_gs_rating  ON webtoon (genre, status, rating_avg);
CREATE INDEX idx_w_gs_title   ON webtoon (genre, status, title);

DML마다 트리 다섯을 갱신하고 버퍼 풀을 다섯 배 나눠 쓴다. view_count 인덱스는 페이지뷰마다 움직인다.

AFTER 기본 + 불변만 인덱스, 라이브 카운터는 스냅숏, 나머지는 허용(선언)
CREATE INDEX idx_w_gs_updated ON webtoon (genre, status, updated_at);   -- 최신순 (70%)
CREATE INDEX idx_w_gs_created ON webtoon (genre, status, created_at);   -- 신작순 (불변)
-- 인기순: 배치가 10분마다 채우는 랭킹 스냅숏 (읽기 전용이라 인덱스가 움직이지 않는다)
CREATE TABLE webtoon_rank_snapshot (
    genre       VARCHAR(20) NOT NULL,
    rank_no     INT         NOT NULL,
    webtoon_id  BIGINT      NOT NULL,
    PRIMARY KEY (genre, rank_no)   -- WHERE genre = ? ORDER BY rank_no LIMIT 20 → PK 순서 그대로
);
-- 별점순·제목순: filesort 허용. N(장르×ACTIVE) 수만 이하, 요청 비중 합 10% 미만 — §8-1 목록에 등록
가산점 정렬 축이 다섯을 넘고 필터 조합까지 자유로운 화면(관리자 그리드, 통합 검색)이라면 RDB 인덱스로 덮으려는 시도 자체를 멈추고 검색 엔진에 위임한다. "정렬 축 수 × 필터 조합 수"만큼 인덱스를 만들 수는 없다.

7-2. 회귀 — "장르 여러 개 선택" 기능이 IN을 가져왔다

한 달 뒤 기획이 다중 선택을 넣었다. 리포지토리의 genre = ?가 genre IN (?, ?)으로 바뀌었고 리뷰는 통과했다 — 인덱스는 그대로니까.

SELECT id, title, thumbnail_url, updated_at FROM webtoon
WHERE genre IN ('ROMANCE', 'DRAMA') AND status = 'ACTIVE'
ORDER BY updated_at DESC LIMIT 20;
-- EXPLAIN   type: range   key: idx_webtoon_genre_status_updated
--           Extra: Using where; Using filesort     ← 돌아왔다 (패턴 ④ 범위/IN 뒤)
-- 이유: ROMANCE·ACTIVE 칸도 updated_at 순, DRAMA·ACTIVE 칸도 updated_at 순 —
--       하지만 "두 칸을 합친 순서"는 없다. 두 구간의 행(8만 + 5만)을 전부 모아 다시 정렬한다

"인덱스가 있는데 filesort"의 전형이고, §8-1의 단정 테스트가 있었다면 CI에서 빨간불이 켜졌을 회귀다. 처방은 셋 중 하나를 N과 빈도로 고른다.

처방 A 구간마다 인덱스로 20건씩 뽑고, 그 합(장르 수 × 20)만 정렬한다
SELECT * FROM (
    (SELECT id, title, thumbnail_url, updated_at FROM webtoon
      WHERE genre = 'ROMANCE' AND status = 'ACTIVE' ORDER BY updated_at DESC LIMIT 20)
    UNION ALL
    (SELECT id, title, thumbnail_url, updated_at FROM webtoon
      WHERE genre = 'DRAMA'   AND status = 'ACTIVE' ORDER BY updated_at DESC LIMIT 20)
) AS candidates
ORDER BY updated_at DESC LIMIT 20;
-- 안쪽 두 SELECT: 각각 Backward index scan으로 20건 — 정렬 0
-- 바깥 정렬: 입력 40건 — 메모리에서 마이크로초. "filesort가 남았지만 N이 40"이라 문제가 아니다(§3-3)
-- 대가: 선택 장르 수만큼 서브쿼리가 늘어난다 → 선택 개수 상한(예: 5개)을 API에서 강제
처방 B — 허용
선택 장르가 많거나(10개+) 화면 빈도가 낮다면 filesort를 허용하고 목록에 등록. 단, 커서 페이지네이션은 정렬 키 순서를 인덱스가 보장할 때만 안전하므로 이 화면은 offset 상한 + 지연 조인으로
처방 C — 위임
이런 조합 필터가 계속 늘어날 화면이면 검색 엔진(§6 가산점)
교훈 두 줄 — ⑴ ORDER BY의 인덱스 사용은 WHERE의 모양이 조금만 바뀌어도 깨진다(= → IN, 컬럼 하나 추가, 방향 하나 변경) ⑵ 그래서 "지금 안 타는가"보다 "깨졌을 때 누가 알아채는가"가 설계의 일부다.

8-1. EXPLAIN 단정 테스트 — 허용한 filesort는 "목록으로 선언", 목록 밖은 실패

꼬리질문 셀프 테스트

질문만 보고 소리 내어 답해 본 뒤 펼쳐서 확인한다. 배지: 시니어 변별 가산점 추가

"LIMIT 20인데 왜 8만 건을 다 정렬하나요? 상위 20건만 추리면 안 됩니까?"

MySQL은 실제로 그렇게 한다 — 우선순위 큐(힙) 최적화. LIMIT이 있고 상위 N건이 sort buffer에 들어가면 전체를 정렬하는 대신 크기 20짜리 힙을 유지하며 행마다 "현재 20위 안에 드는가"만 비교한다. EXPLAIN ANALYZE의 limit input to 20 row(s) per chunk가 그 표시다. 이것으로 메모리와 디스크 스필(③④)은 사라진다.

그러나 사슬의 ①은 그대로다 — 8만 건을 전부 읽어(북마크 룩업 포함) 힙과 비교해야 20위를 확정할 수 있다. 정렬 비용은 N log 20으로 줄지만 읽기 비용은 여전히 N에 비례하고, 실제 목록 쿼리에서 비싼 쪽은 대개 읽기다. 인덱스 경로는 읽기 자체가 20이다. "LIMIT이 있으니 괜찮다"는 스필만 피한 것이지 사슬을 끊은 게 아니다.

"정렬 옵션이 다섯 개인 화면입니다. 인덱스를 다섯 개 만들겠습니까?" 시니어 변별

아니다 — 기준을 먼저 세운다. N(WHERE 후 매칭 행 수) × 요청 비중 × 정렬 컬럼의 변동성. ⑴ 요청 대부분을 받는 기본 정렬(updated_at)은 인덱스 ⑵ 불변 컬럼(created_at)은 쓰기 대가가 거의 없으니 N이 크면 인덱스 ⑶ 조회마다 바뀌는 컬럼(view_count)은 라이브 값에 절대 인덱스를 걸지 않는다 — 페이지뷰마다 인덱스 엔트리가 이동한다. 배치가 채우는 랭킹 스냅숏 테이블이나 Redis Sorted Set에서 읽고, "10분 지연"을 기획과 합의한다 ⑷ 저빈도·N 감당 가능한 축(title, rating_avg)은 filesort를 허용하고 그 결정을 enum과 테스트에 선언한다.

양면을 붙이면 — 인덱스 다섯은 정렬 비용을 없애는 대신 DML마다 트리 다섯을 갱신하고 버퍼 풀을 다섯 배 나눠 쓰며, 허용은 쓰기 대가가 0인 대신 N이 자라면 p99가 되돌아오므로 Sort_rows로 감시한다. 축이 그 이상 늘고 필터 조합까지 자유로우면 RDB 인덱스가 아니라 검색 엔진의 일이다.

"Using filesort와 Using temporary; Using filesort는 어떻게 다르고, 어느 쪽이 더 위험한가요?"

Using filesort는 읽은 행을 sort buffer로 보내 정렬하는 한 단계다. Using temporary; Using filesort는 정렬 전에 중간 결과를 임시 테이블로 한 번 물질화해야 한다는 뜻 — 조인에서 드리븐 테이블 컬럼으로 정렬할 때(조인이 끝나야 순서를 알 수 있다), GROUP BY 컬럼과 다른 컬럼으로 ORDER BY 할 때, DISTINCT·UNION 뒤 정렬할 때 나온다.

두 단계 비용이고, 임시 테이블도 메모리 한도를 넘으면 디스크로 가서(Created_tmp_disk_tables) 스필이 두 군데서 일어날 수 있으니 후자가 더 위험하다. 처방도 다르다 — 전자는 인덱스에 "정" 자리를 채우는 문제지만, 후자는 쿼리 구조의 문제다: 정렬 컬럼을 드라이빙 테이블 쪽으로 옮기거나(조인 순서 조정), 그룹핑을 서브쿼리로 먼저 끝내고 바깥에서 정렬하거나, 집계 결과를 사전 계산 테이블로 뺀다.

"sort_buffer_size를 키우면 해결되는 것 아닌가요?"

증상 하나(스필)만 가리고 원인(N)은 그대로 둔다. 사슬에서 키운 버퍼가 없애는 것은 ③ 스필과 ④ 머지뿐이고, ① N건 읽기와 ② 적재, ⑤ "정렬 뒤에야 LIMIT"은 그대로다. 게다가 이 버퍼는 세션마다 잡히므로 전역으로 키우면 동시 정렬 수 × 크기의 메모리가 예약된다 — 목록 API가 동시에 200개 돌면 200배다.

원칙은 ⑴ N을 줄이는 것(인덱스의 "정" 자리, 또는 §7-2의 구간별 LIMIT) ⑵ 대량 정렬이 정당한 배치·리포트 세션에만 SET SESSION sort_buffer_size로 올리는 것 ⑶ 전역값은 Sort_merge_passes 증가율을 보고 보수적으로. 한 호흡에 — "버퍼를 키우면 디스크 스필은 줄지만 읽기 비용과 세션 메모리 예약이라는 대가는 그대로라, 정렬 입력 N을 줄이는 게 먼저다."

"정렬 컬럼에 인덱스를 걸었더니 특정 장르에서 오히려 느려졌습니다. 왜죠?" 가산점

WHERE만 보는 반쪽의 거울상 — ORDER BY만 보는 반쪽이다. (genre)와 (updated_at)이 따로 있으면 옵티마이저는 ORDER BY updated_at DESC LIMIT 20을 보고 "(updated_at)을 역방향으로 걸으며 genre = ?를 필터하다가 20건 차면 멈추자"를 고를 수 있다 — filesort는 사라지고, 로맨스처럼 흔한 장르는 수십 건만 걸어도 20건이 차서 빠르다.

그러나 희귀 장르(전체의 0.1%)면 20건을 채우려고 인덱스의 거의 전부를 걷는다. 비용이 필터 선택도에 따라 1,000배 널뛰고, 옵티마이저는 통계로 이걸 정확히 예측하지 못한다. 처방은 WHERE 등호와 ORDER BY를 한 인덱스로 묶는 것((genre, status, updated_at)) — 그러면 어느 장르든 구간 끝에서 20건이다. 임시로는 MySQL 8.0 optimizer_switch의 prefer_ordering_index=off로 이 선택을 억제할 수 있지만 증상 억제일 뿐이다. 교훈 — 정렬 인덱스는 WHERE의 등호 컬럼 뒤에 붙어야 정렬 인덱스이지, 정렬 컬럼 단독 인덱스는 또 다른 반쪽이다.

"filesort는 디스크에 쓰는 정렬 아닌가요? 메모리에서 끝나면 안 찍히죠?" 추가

아니다 — 메모리 안에서 끝나도 똑같이 Using filesort다. 이름은 옛날에 반드시 파일에 쓰던 시절의 흔적이고, 지금 뜻은 "인덱스 순서를 못 빌려서 서버 계층에 별도 정렬 단계를 붙였다"이다. 디스크에 갔는지는 Extra가 아니라 Sort_merge_passes(0이면 메모리에서 끝남)나 옵티마이저 트레이스의 filesort_summary로 본다. 그래서 "filesort = 디스크 정렬"이라고 답하면 첫 문장부터 어긋난다.

"인덱스 (genre, status, updated_at)인데 WHERE genre = ? ORDER BY status, updated_at은 filesort인가요?" 추가

아니다 — 인덱스를 탄다. "접"의 조건은 WHERE 등호 컬럼 + ORDER BY 컬럼이 합쳐서 선두부터 연속이면 된다. genre가 등호로 고정되면 그 구간은 (status, updated_at) 순으로 이미 놓여 있고, ORDER BY가 정확히 그 순서를 요구하니 빈칸이 없다. 반대로 WHERE genre = ? ORDER BY updated_at은 status 자리가 비어 있어 filesort(패턴 ③). 즉 빈칸은 WHERE 등호로 채우든 ORDER BY로 채우든 상관없지만, 비워 두면 안 된다.

"커서 페이지네이션 tie-breaker ORDER BY updated_at DESC, id DESC는 인덱스를 타나요?" 추가

탈 수 있다. InnoDB 세컨더리 인덱스는 리프에 PK를 품으므로 (genre, status, updated_at)은 물리적으로 (genre, status, updated_at, id) 순이고, 같은 방향(둘 다 DESC)이면 "방" 조건도 만족한다. 다만 옵티마이저가 이 암묵 컬럼을 정렬에 이용하는지는 EXPLAIN으로 확인하고, 확실히 하려면 인덱스에 id를 명시한다 — 커서 페이지네이션은 정렬 키 순서를 인덱스가 보장할 때만 안전하기 때문이다.

"ORDER BY updated_at DESC, title ASC처럼 방향이 섞였는데 꼭 인덱스로 처리해야 한다면?" 추가

인덱스는 통째로 앞→뒤 또는 뒤→앞으로만 읽으므로 일반 인덱스로는 불가능하다(패턴 ⑤). MySQL 8.0의 내림차순 인덱스로 컬럼별 방향을 인덱스 정의에 박으면 된다 — CREATE INDEX … (genre, status, updated_at DESC, title ASC). 그러면 이 방향 조합(그리고 그 전체 반전 updated_at ASC, title DESC)은 인덱스 순서 그대로다. 대신 그 외의 방향 조합은 다시 filesort가 되므로, 화면이 요구하는 방향이 고정돼 있을 때만 쓴다.

"SELECT *가 정렬 비용에도 영향을 주나요?" 추가

준다. MySQL 8.0의 filesort는 대체로 addon fields 모드로, <정렬 키 + SELECT에 필요한 컬럼 전부>를 sort buffer에 넣는다. 컬럼이 많을수록 엔트리가 넓어져 버퍼가 빨리 넘치고(③ 스필이 일찍 옴), 긴 TEXT/BLOB이 끼면 rowid 모드로 떨어져 ⑥ 재조회(랜덤 I/O)가 붙는다. 그래서 목록 쿼리에서 SELECT 컬럼을 줄이는 것은 전송량 절감만이 아니라 정렬 최적화이기도 하다. 커버링까지 되면 ①의 북마크 룩업도 사라진다.

"EXPLAIN에 Backward index scan이 뜨면 걱정해야 하나요?" 추가

반대다 — 좋은 신호다. ORDER BY … DESC를 인덱스를 뒤에서 앞으로 읽어 처리했다는 뜻이고, 정렬 단계가 없다는 증거다. 걱정할 것은 그 옆에 Using filesort가 있는 경우다. 오름차순 리프를 거꾸로 걷는 비용은 순방향과 사실상 같다.

한 줄 요약
ORDER BY가 공짜인 경우는 옵티마이저가 고른 인덱스의 리프 순서가 곧 정렬 순서일 때뿐이다 — 조건은 "접·범·방·한·원·드": 등호 컬럼 + 정렬 컬럼이 선두부터 연속, 범위(IN 포함) 뒤 컬럼으로는 정렬 불가, 방향은 전부 같거나 전부 반대, 한 인덱스 안에서, 컬럼 원형 그대로, 조인은 드라이빙 테이블 컬럼만. 하나라도 깨지면 filesort — 매칭 N건을 전부 읽어 sort buffer에 적재하고, 넘치면 임시 파일에 썼다 다시 읽어 병합한 뒤에야 LIMIT을 적용하므로 비용이 결과가 아니라 N에 비례하고, 인덱스 순서를 타면 20건 읽고 멈춘다. 그래서 인덱스는 "등·범·정·커"의 정 자리까지 채워야 완성이고, 정렬 축이 여럿이면 N × 빈도 × 컬럼 변동성으로 인덱스/허용/사전 집계를 가른 뒤 그 결정을 EXPLAIN 단정 테스트 · Sort_merge_passes 알람 · 정렬 축 enum에 박아 둔다.
