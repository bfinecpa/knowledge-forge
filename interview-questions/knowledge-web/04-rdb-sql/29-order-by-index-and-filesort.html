ORDER BY와 Sort 노드
정렬은 인덱스 순서를 "빌리거나", 전부 읽어 "다시 줄 세우거나" 둘 중 하나다

면접 질문: "ORDER BY가 인덱스를 타는 조건은? filesort는 언제 발생하고 왜 문제가 되나요?"

핵심 관전 포인트 — ORDER BY가 공짜가 되는 경우는 하나뿐이다 — 플래너가 고른 인덱스의 리프 순서가 곧 정렬 순서일 때. 그 조건은 여섯 개를 세트로 꺼낸다: ① WHERE 등호 컬럼 + ORDER BY 컬럼이 인덱스 선두부터 빈칸 없이 연속(접) ② 범위 조건(IN 포함) 뒤 컬럼으로는 정렬 불가, 범위 컬럼 자체로는 가능(범) ③ 방향이 전부 같거나 전부 반대(PostgreSQL은 B-tree를 거꾸로도 읽는다 — Index Scan Backward), 혼합은 인덱스 정의에 방향을 명시했을 때만, 그리고 NULLS FIRST/LAST까지 일치해야(방) ④ WHERE와 ORDER BY가 한 인덱스 안에서(한) ⑤ 컬럼 원형 그대로 — 함수·연산·random() 없음, 표현식 인덱스는 예외(원) ⑥ 조인이면 드라이빙(outer, 첫 자식) 테이블 컬럼만(드). 하나라도 깨지면 계획에 Sort 노드가 붙는다 — 본질은 "WHERE에 맞는 N건을 전부 읽어 work_mem 안에서 정렬 → 넘치면 임시 파일에 청크로 쓰고 다시 읽어 병합(Sort Method: external merge Disk) → 그제야 LIMIT 20 적용"이라 비용이 결과 20건이 아니라 매칭 행 수 N에 비례한다. 인덱스 순서를 타면 구간 끝에서 20건 읽고 멈춘다. 그래서 인덱스를 WHERE만 보고 걸면 반쪽이고 "등·범·정·커"의 정(정렬) 자리까지 채워야 완성이며, 정렬 축이 여럿인 화면은 "축마다 인덱스"가 아니라 N × 빈도 × 정렬 컬럼의 변동성(PostgreSQL에서는 그 컬럼의 UPDATE가 HOT에서 탈락해 모든 인덱스를 건드린다)으로 인덱스/허용/사전집계를 갈라 결정하고, 그 결정을 EXPLAIN 단정 테스트와 temp_blks_written·log_temp_files 알람으로 고정한다.
  • 1
    정렬이 공짜가 되는 경우는 하나뿐이다 — "리프 순서 = 정렬 순서" — B-tree 리프는 키 순서로 이어진 한 줄이라, 플래너가 읽고 있는 연속 구간이 흘러나오는 순서가 ORDER BY가 원하는 순서와 같으면 정렬을 하는 게 아니라 이미 정렬된 것을 읽을 뿐이다(비교 0회). 거꾸로 읽으면 그대로 DESC — 계획의 Index Scan Backward가 그 신호다.
  • 2
    그 조건을 여섯 개로 꺼낸다 — "접·범·방·한·원·드" — 등호+정렬 컬럼이 선두부터 연속(접), 범위·IN 뒤로는 불가(범), 방향은 전부 같거나 전부 반대이고 NULLS 위치까지 일치(방), 한 인덱스 안에서(한), 컬럼 원형 그대로(원), 조인이면 드라이빙 테이블 컬럼만(드).
  • 3
    깨지면 Sort 노드가 붙고, 비용이 "결과"가 아니라 "매칭 행 수 N"에 비례한다 — 매칭 8만 건을 전부 읽어 work_mem에 넣고, 넘치면 임시 파일에 썼다 다시 읽어 병합한 뒤에야 Limit이 20건을 자른다. 그래서 결과는 20건인데 일은 8만 건이고, 데이터가 늘면 깊은 페이지가 아니라 첫 페이지부터 느려진다.

0. 질문 + 출제 의도 (그리고 "filesort"라는 이름)

질문: "ORDER BY가 인덱스를 타는 조건은? filesort는 언제 발생하고 왜 문제가 되나요?"

PostgreSQL 기준 재해석: "ORDER BY가 인덱스 순서를 빌려 Sort 노드 없이 처리되는 조건은? 실행 계획에 Sort 노드가 붙는 것은 언제이고, 그것이 왜 문제인가요?"

출제 의도: 목록 조회의 기본형(WHERE + ORDER BY + LIMIT)에서 정렬이 인덱스를 못 타면 매 요청이 정렬 작업이 된다. WHERE 조건만 보고 인덱스를 설계하는 반쪽 습관을 가리는 질문이다. 즉 이 문항은 "인덱스가 있는가"가 아니라 "인덱스가 정렬까지 책임지는가"를 묻는다.

이 페이지가 겨냥하는 네 지점 ① "Sort가 있어서 느리다"에서 멈추는 것 → 7절에서 매칭 N건 읽기 → 적재 → 스필 → 머지 → 그제야 LIMIT까지 고리에 이름을 붙이고, 인덱스 경로의 "20건 읽고 중단"과 나란히 놓는다.
② 트레이드오프를 한쪽만 말하는 것 → 9절에서 정렬 컬럼을 인덱스에 넣는 대가(HOT 탈락 = 모든 인덱스 갱신), 10절에서 정렬 축이 다섯인 화면의 판단 공식을 세운다.
③ 목록 인출이 안 되는 것 → 2·5절에서 "타는 조건 6"과 "Sort가 나는 패턴 7"을 세트로, 8절에서 계획 모양 다섯과 Sort Method 세 값을 즉시 꺼낼 수 있게 만든다.
④ 결정을 말로만 하는 것 → 13절에서 EXPLAIN (FORMAT JSON) 단정 테스트, log_temp_files·temp_blks_written 알람, 정렬 축 enum 화이트리스트로 고정한다.

먼저 용어 하나 — 이 문서 파일명의 filesort는 MySQL 용어다

MySQL — Using filesort
스토리지 엔진(InnoDB) 위층인 SQL 서버 계층이 "인덱스 순서를 못 빌렸으니 내가 직접 줄을 세우겠다"며 도는 별도 정렬 단계의 이름. 실행 계획 Extra 칸에 찍힌다. 이름에 "file"이 들어가지만 메모리에서 끝나도 그렇게 찍히는 이름 함정이 있다.
PostgreSQL — 계획의 Sort 노드
같은 자리에 오는 것은 실행 계획의 Sort 노드다. 메모리에서 했는지 디스크로 갔는지는 이름이 아니라 Sort Method 한 줄(quicksort / top-N heapsort / external merge)이 따로 알려준다 — 이름 함정이 없다.

파일명은 다른 문서들이 이 경로를 참조하고 있어 그대로 두지만, 본문은 전부 PostgreSQL 기준이다. 앞으로 "filesort"라는 단어는 MySQL을 대조할 때만, 반드시 "MySQL"이라는 표시와 함께 나온다.

옆 문서와의 경계 — 이 페이지는 "정렬 축" 하나만 본다 복합 인덱스 컬럼 순서(08-composite-index-column-order.md)가 "등·범·정·커" 네 자리를 세우고 순서 오류의 사슬을 다뤘다면, 이 문서는 그중 "정"의 자리 하나만 깊게 판다. OFFSET이 커서 생기는 비용은 깊은 페이지네이션(13), EXPLAIN을 읽는 순서와 개선 사이클은 실행 계획 읽기(10), Index Only Scan의 의미는 커버링 인덱스(09)에 있다.

1. 전제 — B+Tree의 리프는 "키 순서로 이어진 하나의 줄"이다

이 문서의 결론은 전부 한 가지 사실 위에 서 있는데, 그 사실이 보통 설명 없이 놓인다. 먼저 그것부터 깔고 간다.

PostgreSQL의 기본 인덱스인 B-tree(정확히는 B+Tree 계열)는 값을 정렬해서 보관한다. 트리의 위층(내부 노드)은 "어느 자식으로 내려가야 하는가"만 가리키는 이정표이고, 실제 데이터 항목은 전부 맨 아래층인 리프(leaf) 페이지에만 있다. 그리고 그 리프 페이지들은 왼쪽에서 오른쪽으로 형제 링크(sibling pointer)로 이어져 있다 — 페이지 안에서도 키 순서, 페이지와 페이지 사이도 키 순서다.

비유 — 사전에서 "ㄱ으로 시작하는 단어 20개"

사전에서 가나다순으로 20개를 뽑는 데 드는 일은 페이지를 펴서 읽는 것뿐이다. 아무도 단어를 다시 줄 세우지 않는다. 사전이 이미 그 순서로 인쇄돼 있기 때문이다.

= 인덱스 경로 — 비교 0회, 20개 읽고 덮는다

비유 — 흩어진 사람들을 운동장에 모아 키 순으로 세우기

"키 큰 순으로 20명"이 필요한데 사람들이 줄을 서 있지 않다면, 조건에 맞는 8만 명을 전부 운동장에 모아 키를 비교해 세운 다음에야 앞의 20명을 부를 수 있다.

= Sort 노드 — 필요한 건 20명인데 일은 8만 명분

왜 "공짜"라는 표현을 쓰는가 — 정렬은 원래 비교 작업이다 정렬(sort)은 N개를 서로 비교해 순서를 정하는 작업이고, 최선의 비교 정렬 알고리즘도 대략 N × log₂N번의 비교가 필요하다. N이 8만이면 약 130만 번이다(7절에서 계산한다). 리프를 순서대로 읽으면 이 비교가 0번이다. 그래서 "공짜"다.

1-1. 한 문장 원리 — "리프 순서 = 정렬 순서"

플래너가 읽고 있는 연속 구간이 흘러나오는 순서가 ORDER BY가 원하는 순서와 같으면, 정렬은 이미 돼 있는 셈이라 아무 일도 안 해도 된다

이것이 유일한 공짜 경로다. 반대로 읽는 순서와 원하는 순서가 다르면, DB는 읽은 것을 어딘가에 모아 다시 줄 세우는 수밖에 없다 — 그게 계획의 Sort 노드다.

PostgreSQL 한 겹 더 — "N건을 읽는다"는 "N번 힙을 찌른다"이다 리프에서 읽은 엔트리는 TID(힙 위치)로 힙을 찾아가야 비로소 행이 된다(모든 인덱스가 세컨더리인 힙 테이블). 그래서 인덱스 경로의 "20건 읽고 중단"은 힙 방문도 20회로 끝낸다는 뜻이고, 커버링(Index Only Scan)이면 그 20회마저 사라진다. 반대로 Sort 경로의 "8만 건 읽기"는 힙을 8만 번 찌른다는 뜻이다 — 11절에서 이 숫자가 힙 페이지 6만 장으로 번역된다.

2. ORDER BY가 인덱스를 타는 조건 6 — "접·범·방·한·원·드"

여섯 조건을 여섯 글자로 — 접 · 범 · 방 · 한 · 원 · 드

외우는 문장: "접힌 범위의 방향을, 한 인덱스에서 원형 그대로 드라이빙한다"
접 — 접두사 연속
인덱스 선두부터 빈칸 없이
WHERE 등호(상수) 컬럼들 + ORDER BY 컬럼들이 인덱스 선두부터 연속
범 — 범위 조건 뒤
가장 자주 틀리는 자리
범위(>, BETWEEN, LIKE 'x%', 그리고 IN) 뒤 컬럼으로는 정렬 불가. 범위 컬럼 자체로는 가능
방 — 읽는 방향
NULLS 위치까지
방향이 전부 같거나 전부 반대(Index Scan Backward). 혼합은 인덱스에 방향을 박았을 때만. NULLS FIRST/LAST도 일치
한 — 한 인덱스
둘로 갈리면 못 쓴다
WHERE에 쓴 인덱스와 ORDER BY에 쓸 인덱스가 같은 하나여야 한다
원 — 컬럼 원형
표현식 인덱스는 예외
정렬 컬럼이 원형 그대로 — 함수·연산·형변환·random() 없음
드 — 드라이빙 테이블
조인 방식도 함께 본다
조인이면 ORDER BY 컬럼이 전부 드라이빙(outer, 계획 트리의 첫 자식) 것이고, 조인 방식이 순서를 보존해야

암기 장치는 인출을 돕는 손잡이일 뿐이고, 각 글자가 무엇의 줄임이며 왜 필요한지를 모르면 손잡이만 남는다. 아래에서 조건마다 한 소절씩 이유를 붙인다.

2-1. ① 접 — 앞 컬럼 값이 하나로 고정돼야 그 안에서 뒤 컬럼 순서가 살아 있다

복합 인덱스 (A, B, C)는 "A로 정렬하고, A가 같은 것끼리만 B로, A와 B가 둘 다 같은 것끼리만 C로" 정렬된 하나의 트리다. 그러니 C로 정렬된 구간을 얻으려면 그 앞의 A와 B가 하나의 값으로 못 박혀 있어야 한다. 못 박는 조건이 등호(=)다.

빈칸이 하나라도 있으면 깨진다

-- 인덱스 (genre, status, updated_at)
WHERE genre = 'ROMANCE'
ORDER BY updated_at

genre='ROMANCE' 구간 안에서 updated_at은 status별로 따로 정렬돼 있다 — ACTIVE 칸의 시간축, ENDED 칸의 시간축, HIATUS 칸의 시간축이 각각 따로 논다. 전체를 하나로 보면 순서가 아니다.

그 빈칸을 ORDER BY가 채워 주면 살아난다

-- 같은 인덱스, 같은 WHERE
WHERE genre = 'ROMANCE'
ORDER BY status, updated_at

인덱스 리프 순서 그대로다. 즉 정확한 서술은 "WHERE 등호 컬럼 + ORDER BY 컬럼을 이어 붙인 것이 인덱스 선두부터 연속이면 된다"이고, 둘 중 어느 쪽이 그 자리를 채우는지는 상관없다.

접(接) = "등호 컬럼 + 정렬 컬럼"을 이어 붙인 것이 인덱스 선두부터 빈칸 없이 연속이면 통과

3. ② 범 — 리프에 밑줄을 그으면 눈으로 보인다

여기가 여섯 중 가장 자주 틀리는 자리다. 문장으로 읽으면 "범위 뒤는 안 된다"인데, 왜 안 되는지는 리프를 실제 행 목록으로 펼쳐 놓고 구간에 밑줄을 그으면 눈으로 보인다.

(genre, status, updated_at) 인덱스의 리프를 ROMANCE 구간만 펼친다. 왼쪽 컬럼부터 차례로 정렬되므로 이렇게 늘어선다(status는 문자열이라 ACTIVE < ENDED < HIATUS 순).

②범을 한 줄로

앞 컬럼의 값이 하나로 고정돼야, 그 안에서 뒤 컬럼의 정렬이 살아 있다.
범위 조건은 앞 컬럼을 여러 값에 걸쳐 열어 놓으므로, 그 뒤 컬럼의 정렬은 값마다 따로 논다.
범위 컬럼 자체로 정렬→가능 (패널 D) 범위 컬럼 뒤로 정렬→불가 (패널 B·C)

4. ③방 · ④한 · ⑤원 · ⑥드 — 나머지 네 조건

4-1. ③ 방 — 인덱스는 앞→뒤 아니면 뒤→앞, 두 방향뿐이다

리프는 한 줄로 이어진 목록이다. 그러니 읽는 방법은 처음부터 끝까지(Index Scan)이거나 끝에서 처음까지(Index Scan Backward), 둘뿐이다. ORDER BY updated_at DESC는 두 번째로 처리된다 — 그래서 "전부 ASC"와 "전부 DESC"는 둘 다 공짜다.

문제는 혼합이다. ORDER BY status ASC, updated_at DESC는 "status는 앞에서 뒤로, updated_at은 뒤에서 앞으로" 읽으라는 뜻인데, 한 줄짜리 목록을 그렇게 읽을 방법이 없다. 해법은 인덱스를 만들 때 방향을 박아 넣는 것이다.

X 혼합 방향 — 기본 인덱스로는 못 읽는다
-- 인덱스: (genre, status, updated_at)  ← 전부 기본(ASC)
SELECT id, title FROM webtoon
WHERE  genre = $1
ORDER BY status ASC, updated_at DESC;   -- 혼합

-- 계획
--  Sort
--        Sort Key: status, updated_at DESC
--        ->  Index Scan using idx_w_gs_updated ...
--   한 줄을 "앞에서 뒤로 읽으면서 동시에 뒤에서 앞으로"
--   읽을 방법이 없다 → 모아서 정렬
O 인덱스 정의에 방향을 박는다
CREATE INDEX idx_w_g_status_updated_desc
    ON webtoon (genre, status ASC, updated_at DESC);

-- 리프가 애초에 그 순서로 늘어서므로
-- 앞에서 뒤로 읽기만 하면 된다.
-- 계획
--  Limit
--    ->  Index Scan using idx_w_g_status_updated_desc
--          Index Cond: (genre = $1)
--   Sort 노드 없음

NULL의 위치도 순서의 일부다 — PostgreSQL 고유의 함정

PostgreSQL 기본값
ASC일 때 NULLS LAST(NULL이 맨 뒤). 그 인덱스를 거꾸로 읽으면 자동으로 DESC NULLS FIRST가 된다.
그래서 깨지는 조합
ORDER BY updated_at DESC NULLS LAST — NULL이 있어야 할 자리가 반대라 기본 인덱스로는 순서를 못 빌린다. 계획에 Sort가 붙는다.

해결은 둘이다.

① 인덱스를 (… updated_at DESC NULLS LAST)로 만든다 ② 컬럼을 NOT NULL로 만들어 NULL 위치 문제 자체를 없앤다

후자가 대개 더 좋은 답이다. 정렬 축으로 쓰는 컬럼이 NULL을 가질 수 있다는 것 자체가 대개 모델링의 미완성이다 — "업데이트된 적 없는 작품"이라면 updated_at을 created_at과 같은 값으로 채우면 된다.

4-2. ④ 한 — 인덱스를 둘 합치면 순서가 사라진다

(genre) 인덱스와 (updated_at) 인덱스가 따로 있고 쿼리가 WHERE genre = $1 ORDER BY updated_at DESC라면, 플래너는 둘 중 하나만 고르고 나머지 일을 다른 노드로 떠넘긴다.

"인덱스가 둘 다 쓰였으니 정렬도 되겠지"는 성립하지 않는다 함정 PostgreSQL은 BitmapAnd/BitmapOr로 두 인덱스의 TID 집합을 합칠 수 있는데, 합치는 순간 순서가 사라진다. TID 비트맵은 "어느 힙 페이지의 어느 슬롯이 필요한가"를 물리 위치 순으로 모아 놓은 것이지 인덱스 키 순서가 아니기 때문이다.

4-3. ⑤ 원 — 리프에는 값이 들어 있지 f(값)이 들어 있지 않다

인덱스 리프에 저장된 것은 컬럼 값 그 자체다. ORDER BY lower(title)은 "lower(title) 순서"를 요구하는데 리프는 title 순서로 정렬돼 있다 — Apple과 apple과 Banana가 두 순서에서 다르게 놓일 수 있으므로 리프 순서를 그대로 쓸 수 없다.

lower(title)
대소문자를 지운 순서는 리프에 없다
updated_at + interval '1 day'
연산 결과는 리프에 없다
CAST(id AS text)
형변환하면 10 < 9가 된다 — 아예 다른 순서
array_position(ARRAY[…], status)
사용자 정의 순서는 인덱스에 없다
random()

4-4. ⑥ 드 — 조인 결과의 순서를 만드는 것은 드라이빙 테이블뿐이다

조인은 두 테이블을 합치는 작업이고, 합친 결과가 어떤 순서로 나오는지는 조인 방식이 정한다.

PostgreSQL의 조인 방식 셋을 순서 관점에서만 본 것
조인 방식결과의 순서정렬을 빌릴 수 있나
Nested Loop드라이빙(outer) 테이블의 순서 그대로 — outer 한 행마다 inner를 찾아 붙이므로 outer 순서가 유지된다outer 컬럼으로 정렬하면 가능
Merge Join조인 키 순서 — 양쪽을 조인 키로 정렬해 지퍼처럼 맞물리므로 결과도 조인 키 순ORDER BY가 조인 키와 같으면 덤으로 해결
Hash Join보장 없음 — inner로 해시 테이블을 만들고 outer를 흘려보내는데, 플래너는 이 출력에 순서가 있다고 보지 않는다불가
"outer 컬럼으로 정렬했는데 Sort가 붙었다"면 원인은 앞쪽이 아니라 뒤쪽이다 조건 ⑥의 앞쪽(어느 테이블 컬럼인가)이 아니라 뒤쪽(조인 방식)이 원인일 수 있다 — 플래너가 Hash Join을 골랐기 때문이다. 그리고 inner 테이블 컬럼으로 정렬하는 것은 어느 방식으로도 안 된다 — inner 쪽 행은 조인이 끝나야 어떤 것들이 결과에 남는지 알 수 있으므로 순서를 미리 정할 방법이 없다.

4-5. 여섯 조건 위의 전제 하나 — 플래너가 그 인덱스를 Index Scan으로 골라야 한다

조건을 다 만족하는 인덱스가 있어도 플래너가 그것을 안 고르면 소용없다. 비용 계산상 다른 인덱스 + Sort가 싸다고 판단하면 그쪽으로 간다.

PostgreSQL 고유의 함정 — Bitmap Heap Scan은 인덱스 키 순서를 버린다

매칭 행이 많다→ 플래너가 Bitmap Heap Scan 선택→ 인덱스에서 TID를 전부 모아 힙의 물리 순서로 재배열→ 인덱스 키 순서 소멸 → 위에 Sort

랜덤 I/O를 순차 I/O로 바꾸는 좋은 최적화지만, 재배열하는 순간 정렬을 빌릴 근거가 사라진다. LIMIT이 있으면 플래너가 "앞 20건만 있으면 된다"를 알고 Index Scan을 유지하는 편이지만, LIMIT 없는 대량 목록은 이 경로로 빠지기 쉽다.

6절의 before 계획에 Bitmap Heap Scan이 나오는 것이 정확히 이 경우다 — 어차피 정렬할 것이므로 순서를 잃어도 손해가 없다고 플래너가 판단한 것이다.

4-6. 조건 6을 웹툰 스키마 한 줄씩으로 — O / X 대조표

인덱스는 전부 (genre, status, updated_at)이라고 두고 읽는다. O는 Sort 없음, X는 계획에 Sort가 붙는다는 뜻이다.

-- ① 접: 등호 두 개 + 정렬 컬럼이 선두부터 연속 → 인덱스 순서 그대로
WHERE genre = $1 AND status = $2          ORDER BY updated_at DESC      -- O  Sort 없음
WHERE genre = $1                          ORDER BY updated_at DESC      -- X  가운데 status 빈칸 → Sort
WHERE genre = $1                          ORDER BY status, updated_at   -- O  빈칸을 ORDER BY가 채우면 연속

-- ② 범: 범위 컬럼 "자체"로 정렬은 되고, 범위 "뒤" 컬럼으로는 안 된다
WHERE genre = $1 AND status = $2 AND updated_at >= $3  ORDER BY updated_at DESC   -- O  범위 = 정렬 컬럼
WHERE genre = $1 AND status IN ('ACTIVE','HIATUS')     ORDER BY updated_at DESC   -- X  IN은 구간이 갈라진다
WHERE genre = $1 AND status >= 'A'                     ORDER BY updated_at DESC   -- X  범위 뒤 컬럼

-- ③ 방: 전부 반전은 되고(Index Scan Backward), 혼합은 방향을 준 인덱스가 있어야 한다
WHERE genre = $1 AND status = $2  ORDER BY updated_at DESC               -- O  Index Scan Backward
WHERE genre = $1                  ORDER BY status DESC, updated_at DESC  -- O  둘 다 반전 → 역방향
WHERE genre = $1                  ORDER BY status ASC,  updated_at DESC  -- X  혼합 → Sort
--   → CREATE INDEX ... ON webtoon (genre, status ASC, updated_at DESC) 로 만들면 O
WHERE genre = $1 AND status = $2  ORDER BY updated_at DESC NULLS LAST    -- X
--   기본 인덱스(ASC NULLS LAST)를 거꾸로 읽으면 DESC NULLS FIRST다. NULLS LAST를 원하면
--   인덱스도 (… updated_at DESC NULLS LAST)로, 또는 컬럼을 NOT NULL로 만들어 문제 자체를 없앤다

-- ④ 한: WHERE는 (genre)로, ORDER BY는 (updated_at)로 — 인덱스가 둘로 갈리면 하나만 쓴다
--   인덱스가 (genre) 와 (updated_at) 따로 있을 때:
WHERE genre = $1                  ORDER BY updated_at DESC    -- X  (genre)+Sort, 또는 (updated_at) 역순 걷기+Filter

-- ⑤ 원: 컬럼에 손대면 순서가 깨진다 — 단 같은 식으로 만든 표현식 인덱스가 있으면 산다
ORDER BY lower(title)           -- X  단, (genre, status, lower(title)) 표현식 인덱스가 있으면 O
ORDER BY updated_at + interval '0'   -- X     ORDER BY random()   -- X (항상 전체 정렬)
ORDER BY array_position(ARRAY['ACTIVE','HIATUS','ENDED'], status)   -- X  사용자 정의 순서

-- ⑥ 드: 조인 시 정렬 컬럼이 inner 테이블 것이면 조인 결과를 모아 정렬한다
SELECT w.*, a.name FROM webtoon w JOIN author a ON a.id = w.author_id
WHERE w.genre = $1 ORDER BY w.updated_at DESC   -- O  드라이빙(w) 컬럼 — 단 Nested Loop일 때
WHERE w.genre = $1 ORDER BY a.name              -- X  조인 위에 Sort

tie-breaker id는 인덱스에 명시해야 한다 가산점

tie-breaker란 정렬 키 값이 같은 행들 사이의 순서를 확정하려고 뒤에 덧붙이는 컬럼이다 — updated_at이 같은 두 행의 앞뒤가 요청마다 뒤바뀌면 커서 페이지네이션에서 행이 중복되거나 건너뛰어지므로, 보통 ORDER BY updated_at DESC, id DESC처럼 PK를 붙인다.

PostgreSQL — 공짜가 아니다

리프는 키 뒤에 TID(힙 위치)를 달지 PK를 달지 않는다. 그래서 (genre, status, updated_at)은 물리적으로도 딱 그 세 컬럼 순서고, id는 인덱스에 없는 컬럼이다 — 조건 ①(접)이 깨진다.

다만 Incremental Sort가 그 틈을 메운다 (PG 13+)

입력이 updated_at까지는 이미 정렬돼 있으니(계획에 Presorted Key: updated_at), 같은 updated_at 값을 가진 작은 묶음 안에서만 id로 정렬하고 LIMIT 20이 차면 멈춘다.

그래도 확실히 하려면 인덱스에 id를 명시한다 — (genre, status, updated_at, id).

MySQL 대조 InnoDB 세컨더리 인덱스는 리프에 PK를 품으므로 (genre, status, updated_at)이 물리적으로 (genre, status, updated_at, id) 순이라 tie-breaker가 공짜다. PostgreSQL은 공짜가 아닌 대신 Incremental Sort가 그 틈을 메운다 — MySQL에는 접두 정렬을 재사용하는 이 노드가 없다.

6. "등·범·정·커"에서 "정"의 자리 — WHERE만 보는 반쪽 습관

복합 인덱스 컬럼 순서의 네 자리 — 등호 → 범위 → 정렬 → 커버링 — 중 "정"이 이 문서의 자리다. 습관적으로 WHERE 컬럼만 보고 인덱스를 걸면 "등"까지만 채우고 멈춘 것이다.

화면은 이것이다 — 장르 탭 → 연재 중 작품을 최신 업데이트순으로 20개. 홈 트래픽의 대부분이 이 쿼리다.

SELECT id, title, thumbnail_url, updated_at
FROM   webtoon
WHERE  genre = 'ROMANCE' AND status = 'ACTIVE'
ORDER BY updated_at DESC
LIMIT 20;
before WHERE만 보고 건 인덱스 — "등"까지만 채웠다
CREATE INDEX idx_webtoon_genre_status
    ON webtoon (genre, status);

-- EXPLAIN (ANALYZE, BUFFERS)
 Limit  (actual time=96.3..96.3 rows=20 loops=1)
   ->  Sort  (actual time=96.3..96.3 rows=20 loops=1)
         Sort Key: updated_at DESC
         Sort Method: top-N heapsort  Memory: 27kB
              ↑ LIMIT 덕에 메모리는 작다. 그러나 ↓
         ->  Bitmap Heap Scan on webtoon
               (actual time=0.9..81.9 rows=80000 loops=1)
               Recheck Cond: genre='ROMANCE' AND status='ACTIVE'
               Buffers: shared hit=61234
               ->  Bitmap Index Scan on idx_webtoon_genre_status
                     (actual rows=80000 loops=1)

※ Sort 노드가 있고, 그 아래 노드의 rows가 8만
   = "정렬에 들어간 입력"이 8만 건이라는 뜻.
   매칭이 많으니 플래너는 Bitmap Heap Scan을 골랐다
   (어차피 정렬하므로 순서를 잃어도 손해가 없다 — 4-5)
after "정"의 자리를 채운다 — 등호 두 개 뒤에 정렬 컬럼
-- 접두사가 같으니 교체한다(중복 인덱스 방지)
DROP INDEX idx_webtoon_genre_status;
CREATE INDEX idx_webtoon_genre_status_updated
    ON webtoon (genre, status, updated_at);

-- EXPLAIN (ANALYZE, BUFFERS)
 Limit  (actual time=0.05..0.09 rows=20 loops=1)
   ->  Index Scan Backward using
         idx_webtoon_genre_status_updated on webtoon
         Index Cond: genre='ROMANCE' AND status='ACTIVE'
         (actual time=0.04..0.08 rows=20 loops=1)
         Buffers: shared hit=24
              ↑ 인덱스 몇 페이지 + 힙 20페이지

※ Sort 노드 자체가 사라졌고 rows=20 — 20건 읽고 멈췄다.
   DESC는 Backward로 처리됐다.
   96.3ms → 0.09ms, 블록 61,234 → 24

"정"을 "등"보다 앞에 두면 어떻게 되나 — 값 하나로 60배가 갈린다 함정

정렬만 급해서 (genre, updated_at, status)로 만들면 genre 구간이 updated_at 순이라 정렬은 인덱스가 해결한다. 하지만 status는 등호인데도 정렬 컬럼 뒤에 있어 구간을 좁히는 액세스 조건에서 "인덱스 내 검사"로 강등된다 — 리프를 최신순으로 걸으며 ACTIVE가 아닌 엔트리를 버리면서 20건을 채운다.

status = 'ACTIVE' (60%)
20 ÷ 0.6 = 평균 33건쯤 읽고 끝나 티가 안 난다
status = 'SUSPENDED' (1%)
20 ÷ 0.01 = 평균 2,000건을 걷는다 — 60배 차이가 코드 한 줄 없이 필터 값 하나로

그리고 강등된 status도 계획에는 멀쩡히 Index Cond로 찍히므로 계획 텍스트로는 구분이 안 되고 Buffers로 판별한다. "등·범·정·커"의 순서가 중요한 이유가 정렬 축에서 이렇게 드러난다.

7. Sort는 왜 비싼가 — 6고리 vs 3고리

7-1. Sort 노드의 실체 — 계획에 끼어든 "별도 정렬 단계"

누가
플래너가 "인덱스 순서를 못 빌린다"고 판단하면 계획에 Sort 노드를 끼워 넣고 실행기(executor)가 거기서 정렬한다. 아래 노드는 조건에 맞는 행을 한 건씩 올려 보낼 뿐이고, Sort가 마지막 한 건까지 다 받은 뒤에야 첫 행을 위로 내보낸다. Limit은 그 위에 따로 붙는 노드다 — "정렬이 끝나야 자른다"가 계획 모양에 그대로 보인다.
이름
PostgreSQL에는 이름 함정이 없다 — Sort 노드가 있느냐 없느냐를 본다. 대신 어디서 정렬했는지는 Sort Method가 알려준다(8절). 그래서 "Sort = 디스크 정렬"로 외우면 틀리고, "인덱스 순서를 못 빌려 별도 정렬 단계를 붙였다 — 디스크로 갔는지는 Sort Method를 본다"로 외워야 맞다.
어디에
정렬 노드 하나당 work_mem(기본 4MB)까지 메모리를 쓴다 — 쿼리당이 아니라 노드당이고, 해시와 달리 정렬에는 hash_mem_multiplier 배수가 붙지 않는다. 이 크기를 넘으면 데이터 디렉토리의 임시 파일(base/pgsql_tmp, 또는 temp_tablespaces)로 간다. BUFFERS를 켜면 그 노드에 temp read=N written=N이 찍힌다.
무엇을 정렬하나
Sort는 정렬 키만이 아니라 위 노드가 필요로 하는 컬럼을 튜플째 정렬 입력에 싣는다. 그래서 SELECT *로 summary 같은 넓은 컬럼까지 끌어오는 목록 쿼리는 튜플이 넓어져 같은 N에서도 work_mem을 더 빨리 넘긴다 — SELECT 컬럼을 줄이는 것이 정렬 최적화이기도 하다.

두 가지 변종 — 이름을 알고 있으면 계획을 읽는 눈이 달라진다 가산점

bounded sort (= top-N heapsort)
위에 LIMIT n이 있으면 플래너가 그 n을 Sort에 "상한"으로 넘겨 크기 n짜리 힙만 유지한다. 메모리·스필은 거의 사라지지만 입력 N을 전부 읽고 비교하는 비용은 그대로다.
Incremental Sort (PG 13+)
입력이 정렬 키의 접두사로는 이미 정렬돼 있을 때(Presorted Key: updated_at), 접두사 값이 같은 묶음 안에서만 나머지 키로 정렬한다. 묶음 단위로 결과를 흘려보내므로 메모리가 작고 LIMIT과 만나면 앞 묶음 몇 개만 처리하고 멈춘다. 계획에 Full-sort Groups / Pre-sorted Groups 통계가 함께 찍힌다.

7-2. 비용 사슬 — 고리마다 이름을 붙여 두 경로를 나란히

여기가 "성능 저하"·"메모리 부하"에서 멈추던 지점이다. 고리마다 이름을 붙이고, 각 고리가 어떤 자원을 쓰는지를 함께 놓는다.

7-3. N log N을 실제 숫자로 — 130만 회와 15.3MB

비교 횟수

전체 정렬(quicksort, LIMIT 없음)
  log₂(80,000) = 16.29
  80,000 × 16.29 = 1,303,017 회 비교

LIMIT 20 → top-N heapsort로 바뀌면
  ⑴ 모든 행이 "현재 20위 힙의 꼴찌"와 1회 비교
       → 80,000 회
  ⑵ 통과해 힙을 갱신하는 경우만 힙 재정렬
       갱신 기대 = 20 × ln(80,000/20) = 20 × 8.29 = 166 회
       갱신 1회당 log₂(20) = 4.32 회 → 717 회
  합계 ≈ 80,717 회  (약 16배 감소)

인덱스 경로
  비교 0회. 리프가 이미 그 순서다.
  (트리 하강에서 3~4회 비교할 뿐)

임시 파일 I/O

정렬 입력
  80,000 건 × 200 B = 15.3 MB
  work_mem            =  4 MB

런(run) 개수
  ceil(15.3 / 4) = 4 개

  쓰기 15.3MB  (런 4개를 임시 파일에)
  읽기 15.3MB  (병합하며 다시 읽는다)
  ─────────────────────────
  합계 30.5 MB

계획에 찍히는 모양 (8KB 블록 기준)

  Buffers: temp read=1953 written=1953

면접에서 이 한 호흡으로 말한다

"Sort 노드는 조건에 맞는 8만 건을 전부 읽어 work_mem에 넣고, 4MB를 넘으니 런 네 개로 임시 파일에 썼다 다시 읽어 병합한 다음에야 Limit이 20건을 자릅니다. 비교만 130만 번이고 임시 파일 I/O가 30MB인데, 비용이 LIMIT이 아니라 매칭 행 수에 비례하기 때문입니다. 인덱스 순서를 타면 비교 0번으로 구간 끝에서 20건 읽고 멈춥니다."

7-4. "왜 문제인가" — 세 겹으로, 그리고 "언제는 문제가 아닌가"

1
비례 대상이 틀렸다. 결과는 20건인데 일은 N건이다. 그래서 ⓐ 데이터가 10배 되면 깊은 페이지가 아니라 첫 페이지부터 10배 느려지고 ⓑ 개발 DB(N=50)에서는 절대 안 보이고 운영(N=8만)에서 터지며 ⓒ 같은 쿼리도 파라미터에 따라 N이 100배 다르다(로맨스 8만 vs 스릴러 800) — p50은 멀쩡한데 p99가 널뛰는 목록 API의 흔한 정체.
2
자원이 공유 자원이다. work_mem은 백엔드마다, 정렬 노드마다 잡는다 — 동시 요청 200개가 같은 쿼리를 치면 200 × (계획 안의 Sort 노드 수) 몫이다. 그리고 스필된 임시 파일은 데이터 디렉토리를 모든 백엔드가 공유하므로 한 쿼리의 정렬이 옆 쿼리의 해시 조인 스필과 I/O를 다투고, 극단에서는 디스크가 차서 무관한 쿼리까지 실패한다(temp_file_limit으로 세션당 상한). "이 쿼리가 느리다"에서 끝나지 않고 옆 쿼리를 느리게 만든다.
3
응답이 "다 읽은 뒤"에 시작된다. 인덱스 경로는 첫 행을 바로 흘려보낼 수 있지만, Sort는 마지막 행까지 읽고 정렬을 마쳐야 첫 행이 나간다. 첫 행까지의 시간 = 전체 정렬 시간이고, 그동안 커넥션 — PostgreSQL에서는 OS 프로세스 하나 — 을 물고 있다 → 목록 API 하나가 커넥션 풀을 잠식한다. 그 트랜잭션의 스냅샷도 그만큼 오래 살아 VACUUM이 치울 수 있는 죽은 튜플의 경계를 뒤로 민다. SELECT … FOR UPDATE에 붙은 정렬이라면 N건의 행 락을 정렬이 끝날 때까지 쥐고 있는 셈이다.
언제는 문제가 아닌가 — "Sort가 보이면 인덱스 추가"도 반쪽 습관이다 위 세 겹은 전부 N이 클 때 성립한다. N이 수백 건이고 quicksort Memory: 50kB로 끝나며 호출 빈도가 낮으면 Sort는 밀리초 아래다. 즉 문제는 Sort라는 노드 이름이 아니라 "정렬 입력 N의 크기 × 빈도"이고, 이 판단이 9절·10절의 트레이드오프로 이어진다.
MySQL 대조 같은 자리가 filesort다 — SQL 서버 계층이 세션별 sort_buffer_size 안에서 정렬하고, 메모리에서 끝나도 Using filesort라 찍혀 이름 함정이 있다. 정렬 튜플 구성도 두 모드(<정렬 키, rowid>로 정렬 후 재조회 vs <정렬 키, 필요 컬럼 전부>)로 나뉘고, LIMIT 병용 시 우선순위 큐 최적화가 PostgreSQL의 top-N heapsort에 해당한다. Incremental Sort에 해당하는 노드는 MySQL에 없다.

8. EXPLAIN에서 읽기 — 계획 모양 다섯 · Sort Method 세 값

MySQL이 Extra 컬럼의 문구 조합으로 알려주던 것을 PostgreSQL은 트리의 모양과 Sort 노드에 붙는 두 줄(Sort Key, Sort Method)로 알려준다. 먼저 모양.

계획에서 만나는 다섯 모양 — 어느 것을 봤는지가 곧 처방의 방향이다
계획 모양뜻위험도 · 처방 방향
Sort가 스캔 노드 바로 위별도 정렬 단계가 붙었다. 읽은 행을 work_mem으로 보낸다N에 비례. 인덱스에 "정" 자리 채우기, 또는 N이 작으면 허용
Sort가 Hash Join / HashAggregate / Append(UNION) 위 시니어 변별조인·집계·합집합이 다 끝나야 정렬을 시작할 수 있다 — inner 컬럼 정렬, GROUP BY와 다른 ORDER BY, DISTINCT두 단계 비용. 아래 노드도 Batches > 1로 스필할 수 있어 스필이 두 군데. 쿼리 구조를 바꿔야 한다
Sort 아래가 Index Only Scan커버링이라 힙 접근은 0(Heap Fetches: 0)인데 인덱스 순서가 정렬과 안 맞아 정렬은 남았다읽기 최적·정렬 미해결. 대개 "접두사 빈칸"이나 "컬럼 순서" 문제 — 순서를 바꾸면 둘 다 해결되는 신호
Incremental Sort (Presorted Key: …)접두사까지는 인덱스 순서를 빌렸고 나머지 키만 묶음 안에서 정렬대체로 양호. tie-breaker 컬럼이 인덱스에 없을 때의 정상 모양. LIMIT이 있으면 조기 종료
Index Scan Backward, 그리고 Sort 없음인덱스를 뒤에서 앞으로 읽어 DESC를 처리했다좋은 신호. 정렬을 인덱스가 해결했다는 뜻

8-1. Sort Method 세 값 — 언제 어느 것이 선택되는가

Sort Method는 EXPLAIN ANALYZE(실제로 실행하는 모드)에서만 나온다. 값이 세 개뿐이고, 어느 것이 나오는지는 실행기가 두 가지 질문에 어떻게 답하느냐로 결정된다.

Sort Method언제 선택되나어디를 쓰나무엇을 걱정하나
quicksort  Memory: NkBLIMIT 없이, 정렬 입력 전체가 work_mem에 들어갈 때메모리만Memory: NkB가 work_mem에 가까우면 위험 신호 — 데이터가 조금만 늘면 external merge로 떨어진다
top-N heapsort  Memory: NkB위에 LIMIT n이 있고 플래너가 그 n을 Sort에 상한으로 넘겼을 때힙 n개분 — LIMIT 20이면 수십 kB 고정메모리는 안심. 그러나 아래 노드 rows가 정렬 입력이고, 그만큼 읽었다
external merge  Disk: NkBLIMIT이 없고(또는 n이 커서) 입력이 work_mem을 넘겼을 때work_mem + 디스크 임시 파일Disk: NkB가 곧 런의 총 크기. 정상 상태의 목록 API에 있어선 안 되는 값

8-2. 같은 테이블·같은 정렬 키로 세 값을 만들어 본다

[1] quicksort — LIMIT 없이, 입력이 work_mem 안에 들어간 경우
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, updated_at FROM webtoon WHERE genre = 'THRILLER' AND status = 'ACTIVE'
ORDER BY rating_avg DESC;
--  Sort  (actual time=1.842..1.901 rows=800 loops=1)
--        Sort Key: rating_avg DESC
--        Sort Method: quicksort  Memory: 63kB          ← 메모리에서 끝. 63kB는 work_mem 4MB의 1.5%
--        Buffers: shared hit=214                       ← temp 줄이 아예 없다 = 디스크를 안 썼다
--        ->  Bitmap Heap Scan on webtoon (actual rows=800 loops=1)
--   판별: Memory 표기 + temp 줄 없음. 정렬 입력이 800건이라 문제 자체가 없다.
[2] top-N heapsort — 같은 정렬에 LIMIT 20을 붙였을 뿐인데 방식이 바뀐다
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, updated_at FROM webtoon WHERE genre = 'ROMANCE' AND status = 'ACTIVE'
ORDER BY rating_avg DESC LIMIT 20;
--  Limit  (actual time=96.284..96.291 rows=20 loops=1)
--    ->  Sort  (actual time=96.283..96.288 rows=20 loops=1)
--          Sort Key: rating_avg DESC
--          Sort Method: top-N heapsort  Memory: 27kB   ← LIMIT 20이 Sort에 상한으로 전달됐다
--          Buffers: shared hit=61234                   ← 그런데 힙은 6만 장을 읽었다
--          ->  Bitmap Heap Scan on webtoon (actual rows=80000 loops=1)   ← 정렬 입력 8만 건
--   판별: Sort 노드의 rows=20 인데 아래 노드 rows=80000.
--         이 두 숫자의 차이가 낭비의 전부다. Memory가 27kB로 작다고 안심하면 안 되는 이유.
[3] external merge — LIMIT을 떼고 8만 건을 전부 정렬한다 (CSV 내보내기 같은 경로)
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title, thumbnail_url, updated_at FROM webtoon
WHERE genre = 'ROMANCE' AND status = 'ACTIVE' ORDER BY rating_avg DESC;
--  Sort  (actual time=412.7..455.3 rows=80000 loops=1)
--        Sort Key: rating_avg DESC
--        Sort Method: external merge  Disk: 15296kB    ← 15.3MB. 7-3에서 계산한 그 값이다
--        Buffers: shared hit=61234, temp read=1953 written=1953   ← 8KB × 1953 = 15.3MB
--        ->  Bitmap Heap Scan on webtoon (actual rows=80000 loops=1)
--   판별: Disk 표기 + temp read/written 이 0이 아니다. 같은 순간 서버 로그에도
--         log_temp_files = 0 이면 "temporary file: ... size 15663104" 한 줄이 찍힌다.

세 출력의 판별 포인트 — 세 줄

Memory인가 Disk인가→메모리 / 디스크가 갈린다
top-N이라는 접두어가 붙었는가→LIMIT 최적화 여부가 갈린다
어느 경우든 진짜 비용은 Sort 바로 아래 노드의 actual rows←이 세 번째가 가장 자주 놓친다

특히 [2]는 "LIMIT 20인데 왜 8만 건을 다 정렬하나요"라는 꼬리질문의 답이 그대로 담긴 출력이다. PostgreSQL은 실제로 8만 건을 "정렬"하지는 않는다 — 크기 20짜리 힙만 유지하니 비교는 130만이 아니라 8만 회다. 그러나 그 20위를 확정하려면 8만 건을 전부 읽어 봐야 하고(21번째 행이 1위일 수도 있으니), 그 읽기가 Buffers: shared hit=61234다.

top-N heapsort는 정렬 비용을 깎지 읽기 비용은 못 깎는다

8-3. Index Only Scan 위의 Sort — 읽기는 최적, 정렬은 미해결

-- 인덱스 (status, genre, updated_at) INCLUDE (id). 쿼리는 genre 없이:
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, updated_at FROM webtoon
WHERE status = 'ACTIVE' ORDER BY updated_at DESC LIMIT 20;
--  Limit
--    ->  Sort  (actual rows=20 loops=1)
--          Sort Key: updated_at DESC
--          Sort Method: top-N heapsort  Memory: 26kB
--          ->  Index Only Scan using idx_webtoon_status_genre_updated on webtoon
--                Index Cond: (status = 'ACTIVE')
--                Heap Fetches: 0                        ← 힙에 안 갔다 (읽기는 최적)
--                (actual rows=450000 loops=1)           ← 그런데 정렬 입력이 45만 건
--                Buffers: shared hit=2113
--   읽기: 필요한 컬럼(status, updated_at, id)이 전부 인덱스에 있고 visibility map이 신선해 힙엔 안 갔다 → 싸다
--   정렬: status 구간 안은 genre별로 따로 updated_at 순이라 전체 순서가 아니다(조건 ① 위반) → 모아서 정렬
--   해석: "ACTIVE 전체(45만)를 인덱스 리프에서 순차로 읽어(싸다) 전부 힙에 넣고 비교한다(비싸다)"
--   처방: 이 쿼리가 뜨겁다면 (status, updated_at) 인덱스, 아니면 허용 — N을 보고 정한다

9-1. HOT(Heap-Only Tuple)을 먼저 정의한다

두 번째 줄이 핵심인데, 용어를 풀지 않으면 무게가 전달되지 않는다.

PostgreSQL의 UPDATE는 행을 제자리에서 고치지 않는다. 옛 튜플은 그대로 두고 새 튜플 버전을 삽입한 뒤, 옛 것에 "이 XID 이후로는 무효"라는 표시를 남긴다(MVCC). 그러면 원칙적으로 모든 인덱스가 새 튜플의 위치를 가리키도록 새 엔트리를 꽂아야 한다 — 인덱스가 5개면 UPDATE 한 번에 트리 5개를 건드린다.

여기에 PostgreSQL이 둔 예외가 HOT이다.

9-2. 후보 컬럼의 변동성을 나란히 놓으면 판단이 저절로 갈린다

created_at — 불변
인덱스에 넣어도 삽입 때 한 번 꽂히고 끝. HOT과 무관하다. 쓰기 대가가 사실상 0이다.
updated_at — 회차가 올라올 때
작품당 주 1~2회. 그때마다 HOT 탈락 → 인덱스 전부 갱신이지만 빈도가 낮아 감당 가능.
rating_avg — 평점이 들어올 때
소수점이 바뀐다. 인기작이면 분 단위 — 분 단위로 HOT 탈락.
view_count — 조회할 때마다
인덱스가 없어도 이미 초고빈도 카운터 갱신의 문제(행 락 직렬화, 죽은 튜플 폭증, VACUUM 추격 실패)를 안고 있는데, 여기에 인덱스를 걸면 모든 페이지뷰가 모든 인덱스 갱신이 된다 — 최악의 조합.

감시 지표 하나 — HOT 비율

pg_stat_user_tables의 n_tup_upd(전체 UPDATE 수) 대비 n_tup_hot_upd(그중 HOT으로 끝난 수)

이 비율이 높을수록 건강하고, 인덱스에 변동 컬럼을 넣는 순간 곤두박질친다. 인덱스를 하나 추가한 뒤 이 값을 보면 "내가 지불하기로 한 대가"가 실제로 얼마인지를 숫자로 확인할 수 있다.

10. 정렬 기준이 5개인 화면 — "축마다 인덱스"가 답이 아닌 이유 시니어 변별

장르 탭에 정렬 옵션이 최신순 / 신작순 / 인기순 / 별점순 / 제목순 다섯 개다. 이 화면이 이 문서의 변별 지점이다 — "ORDER BY가 인덱스를 타야 한다"를 배운 직후 가장 자연스러운 답이 "그럼 (genre, status, X)를 다섯 개 만들자"이고, 그것이 오답이기 때문이다.

1
인덱스 5개의 쓰기 비용 — 곱셈으로 온다. 9절의 결론을 그대로 적용한다. 인덱스가 5개면 HOT에서 탈락한 UPDATE 한 번이 트리 5개를 건드린다. 그런데 인덱스를 5개 만든다는 것은 그 안에 rating_avg와 view_count 같은 변동 컬럼을 넣는다는 뜻이고, 그러면 그 컬럼을 바꾸는 모든 UPDATE가 HOT에서 탈락한다. 두 효과가 곱해진다.
2
실제로 쓰이는 정렬은 상위 1~2개다 — 사용 분포를 먼저 본다. 비용을 알고 나야 "그 비용을 지불할 만큼 쓰이는가"를 묻게 된다. 정렬 옵션이 다섯이라고 트래픽이 5분의 1씩 나뉘지 않는다 — 기본값으로 지정된 정렬이 압도적이고(대부분의 사용자는 정렬을 바꾸지 않는다) 나머지는 꼬리에 붙는다. 이 분포는 추측이 아니라 로그로 확인할 수 있는 사실이다 — API 접근 로그의 sort 파라미터 분포, 또는 pg_stat_statements에서 정렬 키별로 갈라진 쿼리의 calls.
3
나머지는 Sort를 허용하되, 결과 집합을 작게 만드는 쪽으로 간다. "인덱스를 안 건다"가 곧 "방치한다"는 아니다. 7-4에서 못 박은 대로 문제는 Sort라는 노드가 아니라 정렬 입력 N이므로, 인덱스로 정렬을 없앨 수 없다면 N을 줄이는 쪽으로 간다.

③-ⓐ 필터 인덱스로 N을 줄인다

(genre, status) 인덱스는 정렬은 못 해줘도 정렬 입력을 전체 120만에서 8만으로 줄여 준다. 필터 축이 하나 더 붙는 화면(예: "완결작만")이라면 그 컬럼까지 넣어 N을 더 깎는다.

정렬을 포기한 축에서 비용을 지배하는 것은 N이므로, 정렬 인덱스보다 필터 인덱스가 먼저다.

③-ⓑ 정렬 대상 자체를 작게 만든다

변동성이 큰 축(view_count)은 라이브 컬럼을 정렬하는 대신 배치가 주기적으로 채우는 랭킹 스냅숏 테이블에서 읽는다.

스냅숏은 이미 순위가 매겨져 있으므로 정렬이 아예 없고, 읽기 전용이라 인덱스가 움직이지 않는다.

11-2. 사슬로 번역 → 처방 → 검증 → 대가

(genre, status) 인덱스로 8만 건의 TID를 모아→ 힙 페이지 6만 장을 읽어 8만 행을 만들고(SELECT *라 넓은 행을 통째로)→ 8만 건을 Sort에 흘려 넣어 크기 20짜리 힙과 비교→ 그제야 LIMIT 20

LIMIT 덕에 스필은 없지만 비용의 전부가 "버릴 79,993건을 읽는 데" 쓰였고, 저녁에 동시 요청이 겹치자 이 6만 장이 shared_buffers를 밀어내 read가 늘면서 p99가 뛰었다 — 캐시 오염까지가 사슬의 끝이다.

"같은 쿼리, 다른 파라미터"가 p50과 p99를 갈라 놓는다 이 쿼리는 로맨스에서만 느리다 — 스릴러(N=800)는 같은 계획으로도 밀리초라 로그에 안 잡힌다. 같은 쿼리를 LIMIT 없이 CSV 내보내기에도 썼다면 거기서는 8-2의 [3]번 출력처럼 Sort Method: external merge Disk와 log_temp_files 한 줄이 함께 찍혔을 것이다.

12. 실무 ② — "장르 여러 개 선택" 기능이 IN을 가져왔다

한 달 뒤 기획이 "장르 다중 선택"을 넣었다. 리포지토리의 genre = $1이 genre IN ($1, $2)로 바뀌었고, 리뷰는 통과했다 — 인덱스는 그대로니까.

-- 배포 후 쿼리
SELECT id, title, thumbnail_url, updated_at
FROM   webtoon
WHERE  genre IN ('ROMANCE', 'DRAMA') AND status = 'ACTIVE'
ORDER BY updated_at DESC
LIMIT 20;
-- EXPLAIN (ANALYZE, BUFFERS)
--  Limit
--    ->  Sort                                                  ← 돌아왔다
--          Sort Key: updated_at DESC
--          Sort Method: top-N heapsort  Memory: 28kB
--          ->  Bitmap Heap Scan on webtoon (actual rows=130000 loops=1)
--                Recheck Cond: ((genre = ANY ('{ROMANCE,DRAMA}'::text[])) AND (status = 'ACTIVE'))
--                ->  Bitmap Index Scan on idx_webtoon_genre_status_updated

12-1. col IN (a, b)가 계획에서 어떤 모양이 되는가

IN이 왜 정렬을 깨뜨리는지는 3절에서 리프 목록으로 봤다. 여기서는 그것이 실행 계획 차원에서 어떤 모양이 되는지를 그린다. 이 그림이 있어야 처방이 왜 그 모양인지가 이해된다.

Merge Append가 서는 조건과, IN에는 자동으로 붙지 않는 이유

서는 조건 둘 — ⑴ 각 가지가 이미 같은 정렬 키·같은 방향(NULLS 위치 포함)으로 정렬된 출력을 내야 하고 ⑵ 플래너가 그 사실을 pathkey로 알고 있어야 한다.

UNION ALL로 가지를 명시했을 때
각 가지가 Index Scan Backward로 정렬된 출력을 내고 바깥 ORDER BY가 그 키와 일치하면 Append 대신 Merge Append가 선다 — 아래 처방 A가 이 경로다.
선언적 파티셔닝 테이블
파티션마다 같은 인덱스가 있고 ORDER BY가 그 인덱스 순서와 맞으면 파티션들의 Append가 Merge Append가 된다 — 파티션 테이블에서 ORDER BY … LIMIT이 빠른 이유.
반대로 col IN (…) 한 줄에는 자동으로 붙지 않는다 — 하나의 Index Scan 노드 안에서 여러 구간을 훑는 형태라 "가지"라는 구조 자체가 계획에 없기 때문이다. 그래서 가지를 사람이 만들어 줘야 한다

12-2. 처방 셋 — N과 빈도로 고른다

처방 A 구간마다 인덱스로 20건씩 뽑고, 그 합(장르 수 × 20)만 병합한다
SELECT * FROM (
    (SELECT id, title, thumbnail_url, updated_at FROM webtoon
      WHERE genre = 'ROMANCE' AND status = 'ACTIVE' ORDER BY updated_at DESC LIMIT 20)
    UNION ALL
    (SELECT id, title, thumbnail_url, updated_at FROM webtoon
      WHERE genre = 'DRAMA'   AND status = 'ACTIVE' ORDER BY updated_at DESC LIMIT 20)
) AS candidates
ORDER BY updated_at DESC
LIMIT 20;
-- 안쪽 두 SELECT: 각각 Index Scan Backward로 20건 — 정렬 0
-- 바깥: 입력 40건이라 Sort가 남아도 마이크로초다. "Sort가 있지만 N이 40"이라 문제가 아니다(7-4)
--   (가산점: 각 가지가 이미 updated_at DESC 순이므로 플래너가 바깥 Sort 대신
--    Merge Append 를 고를 수 있다 — 그러면 정렬 자체가 사라진다)
-- 왜 안쪽에 LIMIT 20이 필요한가: 최종 20건에 드는 행은 어느 가지에서 오든
--   그 가지 안에서는 상위 20위 안이다. 그러니 가지마다 20건만 있으면 정답이 보장된다.
-- 대가: 선택 장르 수만큼 서브쿼리가 늘어난다 → 선택 개수 상한(예: 5개)을 API에서 강제
처방 B — Sort 허용 + 목록 등록
선택 장르가 많거나(10개+) 이 화면 빈도가 낮다면 Sort를 허용하고 13절 목록에 등록한다. 단 커서 페이지네이션은 정렬 키 순서를 인덱스가 보장할 때만 안전하므로, 이 화면은 OFFSET 상한 + INCLUDE 커버링으로 힙 페치를 줄여서 간다.
처방 C — 검색 엔진
이런 조합 필터가 계속 늘어날 화면이면 10절 마지막의 결론과 같다 — RDB 인덱스로 덮으려 하지 않는다.

이 사례의 교훈 두 줄

⑴ORDER BY의 인덱스 사용은 WHERE의 모양이 조금만 바뀌어도 깨진다 — = → IN, 컬럼 하나 추가, 방향·NULLS 하나 변경
⑵그래서 "지금 안 타는가"보다 "깨졌을 때 누가 알아채는가"가 설계의 일부다 — 13절의 단정 테스트가 있었다면 이 회귀는 CI에서 빨간불이 켜졌다

@SpringBootTest
class WebtoonListPlanTest {

    @Autowired JdbcTemplate jdbcTemplate;
    @Autowired ObjectMapper objectMapper;

    @BeforeAll
    static void seed(@Autowired JdbcTemplate jdbc) {
        seedWebtoons(jdbc, 300_000);            // 운영 규모. 작은 테이블에선 플래너가 다른 계획을 고른다
        jdbc.execute("ANALYZE webtoon");        // 통계가 없으면 계획이 실전과 다르다
    }

    @ParameterizedTest
    @EnumSource(WebtoonSort.class)
    void 장르목록_정렬축별_실행계획은_선언과_일치한다(WebtoonSort sort) throws Exception {
        // ANALYZE 없이 계획만 — 실행하지 않으므로 빠르고, Plan Rows(추정)로 정렬 입력을 읽는다
        String plan = jdbcTemplate.queryForObject(
            "EXPLAIN (FORMAT JSON) SELECT id, title, thumbnail_url FROM webtoon "
          + "WHERE genre = 'ROMANCE' AND status = 'ACTIVE' "
          + "ORDER BY " + sort.column + " DESC LIMIT 20", String.class);

        JsonNode root = objectMapper.readTree(plan).at("/0/Plan");
        // 트리를 내려가며 "Sort" 또는 "Incremental Sort" 노드를 찾는다.
        // 정렬이 인덱스로 해결되면 노드 자체가 없다 → "Sort 없음"
        Optional<JsonNode> sortNode = findNode(root,
            n -> n.path("Node Type").asText().endsWith("Sort"));

        if (sort.indexed) {
            assertThat(sortNode)
                .as("%s 정렬은 인덱스로 처리돼야 한다 — 인덱스 삭제/순서 변경/IN 도입을 의심", sort)
                .isEmpty();
        } else {
            // 허용한 Sort는 "정렬 입력 N"에 상한을 건다 — N이 자라면 결정을 재검토하라는 신호
            long sortInputRows = sortNode.orElseThrow().at("/Plans/0/Plan Rows").asLong();
            assertThat(sortInputRows)
                .as("%s 은 Sort 허용이지만 정렬 입력이 %d건 — 10절 판단을 다시 하라", sort, sortInputRows)
                .isLessThan(50_000);
        }
    }

    private static Optional<JsonNode> findNode(JsonNode node, Predicate<JsonNode> pred) {
        if (pred.test(node)) return Optional.of(node);
        for (JsonNode child : node.path("Plans")) {
            Optional<JsonNode> found = findNode(child, pred);
            if (found.isPresent()) return found;
        }
        return Optional.empty();
    }
}

전역 — 대시보드 + 알람

pg_stat_database의 temp_files(임시 파일 개수), temp_bytes(그 크기).

temp_bytes의 증가율은 정상 상태에서 0에 가깝다 — 지속적으로 오르면 어떤 쿼리가 work_mem을 넘겨 디스크 정렬(또는 해시 스필)을 하고 있다는 뜻이다.

정렬 입력 N을 직접 세는 전역 카운터는 없다

그래서 "N이 큰 정렬"은 아래 쿼리 단위 지표의 읽은 블록 대비 반환 행으로 잡는다 — 11절의 계획이 정확히 "블록 6만, 반환 20"이었다는 것을 떠올리면 왜 이 비율이 신호인지가 보인다.

SELECT queryid,
       left(query, 80)                                   AS query_head,
       calls,
       temp_blks_written,                                -- 0이 아니면 디스크 스필이 있었다 (정렬·해시)
       (shared_blks_hit + shared_blks_read) / calls      AS blks_per_call,   -- 호출당 읽은 블록
       rows / calls                                      AS rows_per_call    -- 호출당 반환 행
FROM pg_stat_statements
WHERE temp_blks_written > 0
   OR (shared_blks_hit + shared_blks_read) / GREATEST(calls, 1) > 1000
ORDER BY temp_blks_written DESC, blks_per_call DESC
LIMIT 10;
-- 읽는 법: rows_per_call 이 20인데 blks_per_call 이 6만이면 7절의 사슬 그대로다 —
--   "결과 20건을 위해 블록 6만 장". 정확한 정렬 입력 N은 그 queryid의 auto_explain 로그에서
--   Sort 아래 노드의 actual rows로 확인한다. 10절 표의 재검토 입력이 된다

work_mem을 전역으로 키우는 것은 처방이 아니다 함정

백엔드마다·정렬 노드마다 잡는 메모리라 동시 정렬 수 × 노드 수만큼 곱해지고, 무엇보다 N을 줄이지 않는다. 대량 정렬이 정당한 배치·리포트 트랜잭션에서만 SET LOCAL work_mem = '256MB'로 올린다.

키운 work_mem이 없애는 것은 사슬의 ③ 스필과 ④ 머지뿐이다 — ①②⑤⑥은 그대로 남는다

14-2. 꼬리질문 셀프 테스트 — 먼저 스스로 답한 뒤 펼친다

LIMIT 20인데 왜 8만 건을 다 정렬하나요? 상위 20건만 추리면 안 됩니까? 필수힌트: "실제로 그렇게 한다"로 시작하되, 무엇이 줄고 무엇이 안 주는지를 갈라 말한다

PostgreSQL은 실제로 그렇게 한다 — bounded sort. Sort 위에 Limit이 있으면 플래너가 그 20을 Sort의 상한으로 넘기고, 실행기는 전체를 정렬하는 대신 크기 20짜리 힙을 유지하며 행마다 "현재 20위 안에 드는가"만 비교한다. EXPLAIN ANALYZE의 Sort Method: top-N heapsort Memory: 28kB가 그 표시다.

정렬 비용은 실제로 줄어든다. 전체 정렬이면 80,000 × log₂80,000 ≈ 130만 회 비교인데, top-20 힙이면 80,000 + 166 × log₂20 ≈ 8만 회로 약 16배 줄고 메모리와 디스크 스필도 사라진다.

그러나 사슬의 ①은 그대로다 — 8만 건을 전부 읽어야 20위를 확정할 수 있다

21번째로 읽은 행이 1위일 수도 있으니 건너뛸 방법이 없다. 즉 정렬 비교는 16분의 1이 됐지만 읽기 비용은 여전히 N에 비례하고, 실제 목록 쿼리에서 비싼 쪽은 대개 읽기다 — 11절의 계획이 정확히 이 모양이었다(Memory: 28kB인데 Buffers 6만 장). 인덱스 경로는 읽기 자체가 20이다.

"LIMIT이 있으니 괜찮다"는 스필만 피한 것이지 사슬을 끊은 게 아니다. 덧붙이면 — 진짜로 일찍 멈추는 정렬은 Incremental Sort + LIMIT뿐인데, 그것도 입력이 접두사까지는 인덱스 순서를 빌리고 있을 때만 가능하다.

정렬 옵션이 다섯 개인 화면입니다. 인덱스를 다섯 개 만들겠습니까? 시니어 변별힌트: 기준을 먼저 세우고, 축마다 다른 결정을 내리고, 각 결정의 대가를 붙인다

아니다 — 기준을 먼저 세운다. N(WHERE 후 매칭 행 수) × 요청 비중 × 정렬 컬럼의 변동성.

⑴ 요청 대부분을 받는 기본 정렬(updated_at, 비중 70%)은 인덱스 ⑵ 불변 컬럼(created_at)은 쓰기 대가가 거의 없으니 N이 크면 인덱스 ⑶ 조회마다 바뀌는 컬럼(view_count)은 라이브 값에 절대 인덱스를 걸지 않는다 — PostgreSQL에서는 그 컬럼의 UPDATE가 HOT에서 탈락해 페이지뷰마다 테이블의 모든 인덱스에 새 엔트리를 꽂고 죽은 엔트리를 남긴다. 배치가 채우는 랭킹 스냅숏 테이블(또는 materialized view, Redis Sorted Set)에서 읽고 "10분 지연"을 기획과 합의한다 ⑷ 저빈도·N 감당 가능한 축(title, rating_avg)은 Sort를 허용하고 그 결정을 enum과 테스트에 선언한다.

인덱스 다섯의 대가

정렬 비용을 없애는 대신 DML마다 트리 다섯을 갱신하고 shared_buffers를 다섯 배 나눠 쓴다.

허용의 대가

쓰기 대가가 0인 대신 N이 자라면 p99가 되돌아온다 → pg_stat_statements의 호출당 블록 수와 auto_explain의 정렬 입력으로 감시한다.

축이 그 이상 늘고 필터 조합까지 자유로우면 RDB 인덱스가 아니라 검색 엔진의 일이다.

Sort가 스캔 바로 위에 있는 것과 조인·집계 위에 있는 것은 어떻게 다르고, 어느 쪽이 더 위험한가요? 시니어 변별힌트: "한 단계"와 "두 단계"로 갈라 말하고, 처방이 인덱스냐 쿼리 구조냐로 끝낸다

스캔 위의 Sort는 읽은 행을 work_mem으로 보내 정렬하는 한 단계다. 조인·집계 위의 Sort는 그 아래 작업이 다 끝나야 정렬을 시작할 수 있다는 뜻이다 — 조인에서 inner 테이블 컬럼으로 정렬할 때(Hash Join은 순서를 보장하지 않으니 조인이 끝나야 순서를 안다), GROUP BY 컬럼과 다른 컬럼으로 ORDER BY 할 때(HashAggregate 결과를 만든 뒤 정렬), DISTINCT·UNION 뒤 정렬할 때(Append 위).

두 단계 비용이고, 아래 노드도 Batches > 1로 스필할 수 있어 temp written이 두 노드에서 잡힐 수 있으니 후자가 더 위험하다

처방도 다르다 — 전자는 인덱스에 "정" 자리를 채우는 문제지만, 후자는 쿼리 구조의 문제다: ① 정렬 컬럼을 outer 테이블 쪽으로 옮기고 안쪽 조인 키 인덱스로 Nested Loop을 유도하거나 ② ORDER BY를 조인 키와 맞춰 Merge Join이 정렬을 덤으로 주게 하거나 ③ 그룹핑을 서브쿼리로 먼저 끝내고 바깥에서 정렬하거나 ④ 집계 결과를 사전 계산 테이블·materialized view로 뺀다.

(가산점) GROUP BY 컬럼이 ORDER BY 컬럼과 같고 그 순서의 인덱스가 있으면 PostgreSQL은 HashAggregate 대신 GroupAggregate(정렬된 입력을 그대로 묶는 집계)를 골라 Sort 없이 끝낼 수 있다 — 집계 쿼리에서도 "인덱스 순서를 빌린다"는 같은 원리가 통한다.

work_mem을 키우면 해결되는 것 아닌가요? 함정힌트: 사슬 여섯 고리 중 무엇이 사라지고 무엇이 남는지를 짚는다

증상 하나(스필)만 가리고 원인(N)은 그대로 둔다. 7-2의 사슬에서 키운 work_mem이 없애는 것은 ③ 스필과 ④ 머지뿐이고, ① N건 읽기와 ② 적재, ⑤ "정렬 뒤에야 LIMIT", ⑥ 첫 행까지의 대기는 그대로다. 예제 규모로 말하면 임시 파일 I/O 30MB는 사라져도 힙 페이지 6만 장 읽기는 그대로다.

게다가 work_mem은 백엔드마다, 계획의 정렬·해시 노드마다 잡히므로 전역으로 키우면 동시 세션 수 × 노드 수 × 크기의 메모리가 예약된다 — 목록 API가 동시에 200개 돌고 계획에 정렬이 둘이면 400배이고, 프로세스 모델이라 OOM killer가 서버 전체를 세운다.

원칙은 ⑴ N을 줄이는 것(인덱스의 "정" 자리, 또는 12절의 구간별 LIMIT) ⑵ 대량 정렬이 정당한 배치·리포트 트랜잭션에만 SET LOCAL work_mem ⑶ 전역값은 pg_stat_database.temp_bytes 증가율을 보고 보수적으로.

한 호흡으로 — "work_mem을 키우면 디스크 스필은 줄지만 읽기 비용과 세션당·노드당 메모리 예약이라는 대가는 그대로라, 정렬 입력 N을 줄이는 게 먼저다."

정렬 컬럼에 인덱스를 걸었더니 특정 장르에서 오히려 느려졌습니다. 왜죠? 가산점힌트: 이번엔 "WHERE만 보는 반쪽"이 아니라 "ORDER BY만 보는 반쪽"이다

WHERE만 보는 반쪽의 거울상 — ORDER BY만 보는 반쪽이고, PostgreSQL 플래너의 고전적 함정이다.

(genre)와 (updated_at)이 따로 있으면 플래너는 ORDER BY updated_at DESC LIMIT 20을 보고 "(updated_at)을 Index Scan Backward로 걸으며 Filter: genre = $1을 적용하다가 20건 차면 멈추자"를 고를 수 있다 — Sort는 사라지고, 로맨스처럼 흔한 장르(6.7%)는 평균 20 ÷ 0.067 ≈ 300건만 걸어도 20건이 차서 빠르다.

그러나 희귀 장르(전체의 0.1%)면 20건을 채우려고 평균 20 ÷ 0.001 = 20,000건을 걷는다

그 장르의 최신 작품이 오래전 것이면 인덱스 거의 전부를 걷는다 — 계획의 Rows Removed by Filter가 그 계산서다.

플래너가 이렇게 판단하는 이유는 "필터 값이 정렬 순서 위에 균등하게 흩어져 있다"고 가정하기 때문이고, 컬럼 간 순서 상관은 통계에 없어 ANALYZE나 CREATE STATISTICS로도 못 고친다. 처방은 WHERE 등호와 ORDER BY를 한 인덱스로 묶는 것((genre, status, updated_at)) — 그러면 어느 장르든 구간 끝에서 정확히 20건이다. 응급으로 ORDER BY updated_at + interval '0'처럼 표현식으로 만들어 그 인덱스를 못 쓰게 하는 트릭이 있지만, 그건 증상 억제이고 인덱스 설계가 답이다.

교훈은 하나 — 정렬 인덱스는 WHERE의 등호 컬럼 뒤에 붙어야 정렬 인덱스이지, 정렬 컬럼 단독 인덱스는 또 다른 반쪽이다.

MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 다섯 지점 — 이름·단위 / 방향 / tie-breaker / 쓰기 대가 / 단독 인덱스 함정

① 이름과 단위 — MySQL은 메모리에서 끝나도 Using filesort라 찍혀 이름 함정이 있고 정렬 버퍼가 세션당 sort_buffer_size인데, PostgreSQL은 Sort 노드의 유무로 보고 어디서 했는지는 Sort Method가 말하며 메모리는 정렬 노드당 work_mem이다. 지표도 Sort_merge_passes·Sort_rows 대신 temp_blks_written·log_temp_files·auto_explain이다.

② 방향 — MySQL은 8.0에서야 내림차순 인덱스가 생겨 혼합 방향이 가능해졌지만, PostgreSQL은 오래전부터 컬럼별 ASC/DESC/NULLS FIRST/LAST를 지정할 수 있고 어느 인덱스든 Index Scan Backward로 거꾸로 읽는다. 대신 NULLS 방향 불일치라는 PostgreSQL 고유 함정이 있다.

③ tie-breaker — InnoDB 세컨더리 리프는 PK를 품어 ORDER BY updated_at, id가 공짜지만, PostgreSQL 리프는 TID라 id를 인덱스에 명시해야 하고 그 틈은 Incremental Sort가 메운다(MySQL에는 없는 노드).

④ 정렬 컬럼을 인덱스에 넣는 쓰기 대가 — InnoDB는 그 인덱스에서 삭제+삽입으로 끝나지만, PostgreSQL은 HOT 탈락으로 모든 인덱스에 새 엔트리가 꽂힌다.

⑤ 정렬 컬럼 단독 인덱스의 함정 — 양쪽 다 있지만 MySQL은 prefer_ordering_index 스위치로 임시 억제가 가능하고 PostgreSQL에는 그런 스위치가 없어 인덱스 설계로만 푼다. 이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "차이를 저장 구조에서 이해했다"로 들린다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

조건 6을 전부 만족하는 인덱스가 있는데도 계획에 Sort가 붙었습니다. 무엇을 의심합니까? 함정힌트: 조건 6 위에 있는 "전제" 하나를 떠올린다

조건을 다 만족해도 플래너가 그 인덱스를 Index Scan으로 고르지 않으면 소용없다는 전제(4-5)를 먼저 꺼낸다. 의심할 것은 넷이다.

① Bitmap Heap Scan으로 갔다. 매칭 행이 많으면 플래너는 인덱스에서 TID를 전부 모아 힙의 물리 순서로 재배열해 순차로 읽는 쪽이 싸다고 본다. 재배열하는 순간 인덱스 키 순서를 버리므로 위에 Sort가 붙는다. 계획에 Bitmap Index Scan + Recheck Cond가 보이면 이것이다.

② 통계가 낡았다. ANALYZE가 오래 안 돌아 선택도 추정이 틀리면 "이 조건은 행이 많이 나온다"고 잘못 판단해 ①로 간다. EXPLAIN ANALYZE에서 추정 rows와 actual rows의 괴리를 먼저 본다.

③ 비용 파라미터가 인덱스 경로에 불리하다. random_page_cost가 기본 4.0인데 실제 저장소가 SSD면 랜덤 읽기가 실제보다 비싸게 계산돼 인덱스 경로가 밀린다.

④ 데이터 타입·collation이 다르다. 정렬 컬럼이나 조건 값의 타입이 인덱스와 달라 암묵적 형변환이 끼면 그것은 사실상 조건 ⑤(원) 위반이다 — 계획에 ::text 같은 캐스팅이 보이는지 확인한다.

인덱스가 (genre, status, updated_at)인데 ORDER BY updated_at DESC, id DESC로 바꿨더니 Sort가 생겼습니다. 심각한가요?힌트: 노드 이름을 정확히 보면 심각도가 갈린다

계획에 붙은 것이 Sort인지 Incremental Sort인지부터 본다. 심각도가 완전히 다르다.

Incremental Sort + Presorted Key: updated_at

정상 모양이다. 입력이 updated_at까지는 이미 인덱스 순서이므로, 같은 updated_at 값을 가진 작은 묶음 안에서만 id로 정렬하고 LIMIT 20이 차면 멈춘다. 묶음이 작으니 메모리도 작다.

그냥 Sort

접두 정렬을 재사용하지 못했다는 뜻이라 입력 N 전체가 정렬 입력이다. 아래 노드의 actual rows를 확인한다.

왜 애초에 id가 문제가 되는가 — PostgreSQL 인덱스 리프는 키 뒤에 TID(힙 위치)를 달지 PK를 달지 않기 때문이다. 그래서 id는 그 인덱스에 없는 컬럼이고 조건 ①(접)이 깨진다. MySQL(InnoDB)은 리프가 PK를 품으므로 같은 상황이 생기지 않는다.

확실히 하려면 인덱스에 id를 명시한다 — (genre, status, updated_at, id). 그리고 tie-breaker를 붙이는 것 자체는 옳다 — 값이 같은 행들의 앞뒤가 요청마다 뒤바뀌면 커서 페이지네이션에서 행이 중복되거나 건너뛰어진다.

커서 페이지네이션과 "정렬 인덱스"는 어떤 관계인가요? 시니어 변별힌트: 커서는 정렬이 인덱스로 보장돼야 성립하는 기법이다

커서 페이지네이션은 "정렬 순서가 인덱스로 보장된다"를 전제로 성립하는 기법이다. 다음 페이지를 OFFSET 대신 "마지막으로 본 값보다 뒤"라는 조건으로 표현하는데, 그 조건이 인덱스 구간 탐색이 되려면 정렬 축이 그 인덱스의 리프 순서와 같아야 하기 때문이다.

-- 인덱스 (genre, status, updated_at, id) 가 있을 때
SELECT id, title, updated_at FROM webtoon
WHERE genre = $1 AND status = $2
  AND (updated_at, id) < ($3, $4)     -- 마지막으로 본 행의 (updated_at, id)
ORDER BY updated_at DESC, id DESC
LIMIT 20;

세 가지가 동시에 맞아야 한다. ① 커서 조건의 컬럼 순서·방향이 ORDER BY와 같을 것 ② 그 순서가 인덱스 리프 순서와 같을 것(조건 ①접·③방) ③ tie-breaker 컬럼이 인덱스에 있을 것.

그래서 "Sort 허용"으로 결정한 정렬 축에는 커서 페이지네이션을 붙이면 안 된다

정렬이 Sort 노드로 처리되는 축은 동일 값의 앞뒤 순서가 실행마다 달라질 수 있어 커서가 행을 중복시키거나 건너뛴다. 12절 처방 B에서 "Sort 허용 화면은 OFFSET 상한으로 간다"고 적은 이유가 이것이다 — 정렬 축의 결정(10절)과 페이지네이션 방식의 결정은 한 세트다.

ORDER BY random() LIMIT 10은 왜 항상 느린가요? 어떻게 바꿉니까? 함정힌트: 조건 ⑤(원) 위반 중에서도 가장 지독한 경우다

조건 ⑤(원) 위반 중에서도 원리적으로 인덱스로 구제할 수 없는 유일한 경우다. lower(title)은 표현식 인덱스로 살릴 수 있지만, random()은 행마다·실행마다 값이 달라지므로 어떤 인덱스도 그 순서를 미리 가질 수 없다.

그래서 실행기는 대상 행 전부에 난수를 하나씩 매기고 전부 정렬해야 한다 — LIMIT 10이 top-N heapsort로 비교 횟수는 줄여 주지만, "전부 읽고 전부 난수를 매긴다"는 부분은 그대로다. 테이블이 커질수록 선형으로 느려진다.

방향은 "정렬로 풀지 말고 키 공간에서 뽑는다"이다.

  • 키 범위에서 난수로 찍어 근처 행을 집는다 — id가 대략 연속이라면 WHERE id >= (난수) ORDER BY id LIMIT 1을 필요한 만큼 반복. 삭제로 생긴 구멍 때문에 완전 균등은 아니라는 점을 알고 쓴다.
  • TABLESAMPLE — 테이블 일부 페이지만 샘플링해 후보를 좁힌 뒤 그 안에서 고른다. 페이지 단위라 같은 페이지의 행들이 함께 뽑히는 편향이 있다.
  • 후보를 먼저 좁힌다 — "이번 주 신작 200건" 같은 작은 집합으로 줄인 뒤 그 안에서 랜덤. N이 200이면 Sort가 있어도 문제가 아니다(7-4).
  • 애플리케이션·캐시에서 고른다 — 후보 ID 목록을 캐시에 두고 애플리케이션이 뽑는다.

판단 기준은 늘 같다 — "정렬 입력 N이 얼마인가." N이 수백이면 ORDER BY random()도 그냥 쓰면 되고, N이 수십만이면 위 방법들로 N 자체를 줄인다.

Sort 아래 노드의 actual rows가 정렬 입력이라고 했는데, loops가 1보다 크면 어떻게 읽습니까? 가산점힌트: EXPLAIN의 actual rows는 "합계"가 아니다

EXPLAIN ANALYZE의 actual rows는 합계가 아니라 loops당 평균값이다. 그래서 Nested Loop 안쪽처럼 여러 번 실행되는 노드에서는 실제 총량이 rows × loops가 된다.

정렬 축에서 이것이 중요한 이유는 Sort가 조인 안쪽에 들어가면 정렬이 loops 횟수만큼 반복된다는 뜻이기 때문이다. rows=500 loops=2000인 Sort는 "500건짜리 가벼운 정렬"이 아니라 "500건 정렬을 2,000번"이다 — 100만 건 정렬과 같은 무게이고, work_mem도 매번 잡았다 푼다.

그래서 계획을 읽을 때는 항상 rows와 loops를 같이 읽고, 곱한 값으로 판단한다. 처방은 대개 안쪽 정렬을 없애는 인덱스를 주거나, 조인 순서를 바꿔 반복 횟수 자체를 줄이는 것이다.

인덱스가 정렬을 해결했는지 계획을 보지 않고 판단할 수 있나요? 필수힌트: 못 한다. 그리고 "못 한다"는 사실 자체가 답의 일부다

안정적으로는 못 한다. 그리고 그 사실이 이 문서의 안전망(13절)이 존재하는 이유다.

이유는 셋이다. ① 조건 6은 쿼리·인덱스·플래너의 선택 세 가지가 모두 맞아야 성립하는데, 세 번째는 데이터 분포와 통계에 따라 배포 없이도 바뀐다(4-5의 Bitmap Heap Scan 전환). ② 같은 코드가 파라미터에 따라 다른 계획을 탄다 — 로맨스에서는 Sort, 스릴러에서는 Index Scan일 수 있다. ③ WHERE의 모양이 조금만 바뀌어도(12절의 = → IN) 인덱스는 그대로인데 조건이 깨진다 — 그래서 코드 리뷰로는 안 잡힌다.

그래서 판단은 계획으로 하고, 그 판단을 테스트와 알람에 박아 둔다

구체적으로는 ⑴ CI에서 EXPLAIN (FORMAT JSON) 단정(인덱스로 선언한 축에 Sort 노드가 있으면 실패, 허용한 축은 정렬 입력 N에 상한) ⑵ 운영에서 auto_explain + log_temp_files로 실제 계획과 스필을 남기고 ⑶ pg_stat_statements의 호출당 블록 수 대비 반환 행으로 주간 리뷰. "지금 타는가"가 아니라 "깨졌을 때 누가 알아채는가"를 설계하는 것이 답이다.

목록 API에서 SELECT *를 쓰는 것이 정렬 비용과 관계가 있나요? 가산점힌트: Sort 노드가 정렬 입력에 무엇을 싣는지 떠올린다

있다. 그것도 두 겹으로.

① 정렬 튜플이 넓어진다. Sort는 정렬 키만이 아니라 위 노드가 필요로 하는 컬럼을 튜플째 정렬 입력에 싣는다. SELECT *로 summary 같은 넓은 컬럼까지 끌어오면 같은 N에서도 work_mem을 더 빨리 넘겨 quicksort에서 external merge로 떨어진다. 7-3의 계산에서 튜플 폭 200B를 600B로 바꾸면 임시 파일이 15.3MB → 46MB가 된다.

② 커버링(Index Only Scan)의 가능성이 사라진다. 필요한 컬럼이 전부 인덱스에 있으면 힙 방문이 0이 되는데, SELECT *는 그 조건을 원천적으로 불가능하게 만든다. 11절에서 "행이 넓어 페이지당 13행"이었던 것도 SELECT *의 결과다.

목록 API에서 SELECT 컬럼을 줄이는 것은 네트워크 절약이 아니라 정렬·읽기 최적화다 — 목록 화면에 필요한 것은 대개 id · title · thumbnail_url · updated_at 넷뿐이다
"이 목록은 정렬이 인덱스를 안 타지만 괜찮습니다"라고 말하려면 무엇을 근거로 대야 합니까?힌트: "느리지 않아서"는 근거가 아니다. 숫자 셋을 댄다

"지금 안 느리다"는 근거가 아니다. N이 자라면 되돌아오기 때문이다. 근거로 대야 할 숫자는 셋이다.

① 정렬 입력 N
Sort 바로 아래 노드의 actual rows. 지금 값과, 데이터 증가 추세를 감안한 1년 뒤 값을 함께 댄다.
② 호출 빈도
pg_stat_statements의 calls 또는 API 접근 로그의 비중. N이 커도 하루 몇 번이면 다른 결정이 나온다.
③ Sort Method
quicksort Memory: NkB여야 하고, 그 NkB가 work_mem에 가까우면 이미 위험하다. external merge가 보이면 "괜찮다"가 성립하지 않는다.

그리고 그 판단에는 유효기간이 있다. 그래서 "허용"은 말이 아니라 선언이어야 한다 — 13절처럼 enum에 indexed = false로 적고, 테스트가 정렬 입력 N의 상한을 감시하게 만든다. 전제가 무너지면 CI가 알려주는 구조가 되어야 "괜찮다"고 말할 자격이 생긴다.

면접에서는 여기에 한 줄 더 붙이면 좋다 — "허용한 정렬 축에는 커서 페이지네이션을 붙이지 않는다"(위 꼬리질문). 결정의 파급까지 관리한다는 신호다.

한 줄 요약
ORDER BY가 공짜인 경우는 플래너가 고른 인덱스의 리프 순서가 곧 정렬 순서일 때뿐이다 — B-tree 리프가 키 순서로 이어져 있으니 순서대로 훑으면 비교 0회로 정렬이 따라오고, 거꾸로 훑으면 Index Scan Backward로 DESC가 된다. 조건은 "접·범·방·한·원·드": 등호 컬럼 + 정렬 컬럼이 선두부터 연속(접), 범위(IN 포함) 뒤 컬럼으로는 정렬 불가(범), 방향은 전부 같거나 전부 반대이고 NULLS 위치까지 일치(방), 한 인덱스 안에서(한), 컬럼 원형 그대로(원, 표현식 인덱스는 예외), 조인은 드라이빙 테이블 컬럼만(드). 하나라도 깨지면 계획에 Sort 노드 — 매칭 N건을 전부 읽어 work_mem에 적재하고, 넘치면 임시 파일에 썼다 다시 읽어 병합(external merge Disk)한 뒤에야 Limit이 자르므로 비용이 결과가 아니라 N에 비례한다(N=8만이면 비교 130만 회·임시 파일 I/O 30MB, top-N heapsort면 비교는 8만 회로 줄지만 힙 페이지 6만 장 읽기는 그대로). 인덱스 순서를 타면 20건 읽고 멈춘다. 그래서 인덱스는 "등·범·정·커"의 정 자리까지 채워야 완성이고, 정렬 축이 여럿이면 N × 요청 비중 × 컬럼 변동성(HOT 탈락 = 모든 인덱스 갱신)으로 인덱스/허용/사전 집계를 가른 뒤 그 결정을 EXPLAIN (FORMAT JSON) 단정 테스트 · temp_bytes/log_temp_files 알람 · 정렬 축 enum에 박아 둔다.
