통계 조회의 분리 — "기능은 다른데 자원은 공유"를 OLTP/OLAP 분리 사다리로 푼다

질문: "대시보드용 통계 조회가 운영 트래픽과 같은 DB를 때리고 있습니다. 어떻게 분리하나요? (집계 테이블, 사전 계산 배치, replica)"

핵심 관전 포인트 — 면접 첫 답변으로 그대로 말한다

대시보드 집계와 운영 트랜잭션은 "기능은 다른데 자원은 공유"하는 관계다.
  1. 잠식은 자원 다섯 개의 사슬이다 — 무거운 집계 쿼리 하나가 ① 버퍼 풀의 핫 페이지를 밀어내고(운영 쿼리가 메모리 대신 디스크로) ② CPU 코어·디스크 I/O 큐를 수 분간 점유하고 ③ 긴 Read View로 purge를 멈춰 undo를 쌓고 ④ 커넥션을 오래 쥐고 메타데이터 락으로 DDL과 그 뒤 쿼리까지 세운다 — ⑤ replica에서 돌려도 적용 스레드와 경쟁해 복제 지연을 만든다.
  2. 분리는 사다리로 오른다 — ⓪ 실시간 요구를 되묻고("하루 지연 허용 가능?") ① 쿼리를 다이어트하고 ② 통계 전용 replica로 라우팅하고 ③ 집계 테이블 + 사전 계산 배치로 "조회 시점의 계산"을 "배치 시점의 계산"으로 옮기고 ④ 임의 분석이 필요해지면 CDC로 OLAP 저장소에 뺀다.
  3. 각 단은 대가가 따른다 — replica는 복제 지연과 (replica 위에서도 여전히 무거운) 자원 경쟁, 집계 테이블은 실시간성 상실과 배치 실패·원본 정정 시 보정 부담, OLAP은 이중 저장과 파이프라인 운영.
어느 단을 고르든 통계 쿼리가 운영 DB로 새지 않도록 별도 DataSource · 읽기 전용 계정 · max_execution_time · 리소스 그룹 · ArchUnit으로 코드와 권한에 고정한다. 이 문항의 함정은 "replica로 보내면 끝" — replica는 격리이지 해결이 아니다(집계는 거기서도 10분 걸린다).

1왜 같은 DB에 두면 안 되는가 — 자원 다섯 개의 잠식 사슬

1-1. 두 워크로드는 DB에게 정반대의 일을 시킨다

항목OLTP (운영 트랜잭션)OLAP (대시보드 집계)
한 번에 만지는 행수 건 ~ 수십 건수십만 ~ 수억 건
접근 방식인덱스로 콕 찍는 랜덤 접근범위 스캔·풀스캔 + GROUP BY·정렬
쿼리 1건 실행 시간밀리초초 ~ 분
동시 실행 수초당 수백 ~ 수천초당 몇 건
최적 저장 구조행 저장(row store) + B+Tree열 저장(column store)

OLTP(Online Transaction Processing)는 "주문 한 건 넣고, 주문 한 건 읽는" 일이고, OLAP(Online Analytical Processing)는 "지난 3년 주문을 셀러별·월별로 접어 매출 추이를 만드는" 일이다. 같은 orders 테이블을 보지만 DB에게 시키는 일의 성격이 반대다. RDB의 버퍼 풀 크기·인덱스 구조·커넥션 풀·격리 수준은 전부 OLTP에 맞춰져 있고, 그 위에서 OLAP 쿼리를 돌리면 OLAP만 느린 게 아니라 OLTP가 같이 느려진다.

편의점 계산대에 창고 전수조사를 시키는 것

계산대 직원(OLTP)에게 손님 줄이 선 채로 창고 재고 전수조사(OLAP)를 시키면 — 전수조사가 느린 것은 둘째 문제고, 그동안 계산대 줄이 안 빠지는 것이 첫째 문제다. 이 문항의 "분리"는 전수조사를 빠르게 하는 일이 아니라 계산대에서 떼어 놓는 일이다.

1-2. "부하가 커진다"를 자원 다섯 개로 쪼개기 — 한 화면 사슬 지도

4장 내내 비용을 말할 때 "성능 저하", "메모리 부하"에서 멈췄다. 아래 다섯 줄을 자원 이름 → 원인 → 운영 쿼리에 나타나는 결과의 화살표로 말할 수 있어야 한다. 사슬끼리는 서로 먹인다(⇢ 표시).

다섯 사슬을 한 문장으로 — 인출용

"집계 쿼리 하나가 버퍼 풀에선 핫 페이지 축출과 히트율 하락, CPU·디스크에선 코어 독점과 I/O 큐 적체, MVCC에선 purge 정지와 undo 누적, 커넥션 풀에선 슬롯 장기 점유, 메타데이터 락에선 DDL 뒤 대기열을 만들어 무관한 운영 쿼리 하나하나를 느리게 하고, replica로 옮겨도 적용 스레드와 경쟁해 복제 지연을 만든다."

순서 연상: 쿼리가 DB 안에서 지나가는 길 그대로 — 메모리(버퍼 풀)를 채우고 → 코어·디스크를 붙잡고 → 버전(undo)을 붙들고 → 문(커넥션·MDL)을 막고 → 복제본까지 따라간다. "채우고·붙잡고·붙들고·막고·따라간다".

A버퍼 풀 오염 (buffer pool pollution)

버퍼 풀은 디스크 페이지를 메모리에 올려두는 캐시다. 운영 쿼리가 빠른 이유는 자주 쓰는 페이지(최근 주문·인기 상품·활성 유저)가 이미 메모리에 있어서다. 집계가 3년치 주문 페이지 수백만 개를 읽어 올리면 크기가 정해진 버퍼 풀에서 누군가는 쫓겨나야 한다. 쫓겨난 것이 운영 핫 페이지면 다음 운영 쿼리는 디스크로 간다 — 그것도 인덱스 탐색 특유의 랜덤 I/O로.

대량 페이지 적재→LRU에서 핫 페이지 축출→히트율 하락→운영 쿼리 디스크 랜덤 읽기 ↑→응답시간 ↑ · 디스크 큐 적체 ⇢ B

시그니처: Innodb_buffer_pool_reads(디스크까지 간 읽기)가 Innodb_buffer_pool_read_requests(논리 읽기) 대비 급증.

"풀스캔 한 번 = 버퍼 풀 전멸"은 과장이다 — 방어가 있고, 그 방어가 뚫리는 조건까지 말한다

InnoDB는 새로 읽힌 페이지를 LRU 맨 앞이 아니라 중간 지점(old 영역, 기본 37%)에 넣고, 첫 접근 후 innodb_old_blocks_time(기본 1초) 안에 다시 접근돼도 young 영역으로 승격하지 않는다. 풀스캔은 페이지를 한 번 훑고 지나가므로 young 영역의 핫 페이지를 직접 밀어내지 못한다(PostgreSQL도 대형 순차 스캔에 작은 링 버퍼를 따로 쓴다). 그러나 방어는 뚫린다:

  1. old 영역 자체는 통째로 갈리므로 거기 있던 "최근 적재됐지만 아직 승격 전인" 운영 페이지는 사라진다
  2. 집계가 조인·정렬·재스캔으로 같은 페이지를 1초 뒤에 또 만지면 young으로 승격돼 방어가 풀린다
  3. 대시보드 위젯 6개가 같은 테이블을 6번 훑으면 ②가 사실상 보장된다

"방어가 있지만 이런 경우 뚫린다"까지 말하면 버퍼 풀을 실제로 들여다본 사람으로 보인다.

BCPU 코어 독점과 디스크 I/O 큐 적체
  • CPU — MySQL에서 쿼리 하나는 스레드 하나가 실행한다. 수백만 행 GROUP BY는 해시 집계·정렬(filesort)이고 실행 내내 코어 하나를 100%로 쓴다. 8코어 서버에서 집계 하나는 운영 처리 능력의 1/8을 수 분간 가져가고, 위젯 6개면 6/8이다. 남은 코어에 운영 스레드가 몰리면 컨텍스트 스위칭 비용까지 얹힌다.
  • 디스크 큐 — 집계가 읽는 과거 데이터는 캐시에 없으므로 대량의 순차 읽기 스트림이 들어온다. 디스크가 동시에 처리하는 요청 수에는 상한이 있어, 운영의 작은 랜덤 읽기가 그 스트림 뒤에 줄을 선다 — iostat의 await가 오른다.
  • 임시 공간 — 정렬 버퍼·메모리 임시 테이블 한도를 넘으면 디스크로 넘친다(Sort_merge_passes, Created_tmp_disk_tables 증가). 읽기 부하였던 집계가 쓰기 I/O까지 만들기 시작하는 지점이다.
코어 독점 + 순차 읽기 + 디스크 스필→운영 쿼리 CPU 대기·I/O 큐 대기→쿼리당 실행 시간 ↑→커넥션 점유 시간 ↑ → 풀 pending ⇢ D
C긴 Read View → purge 정지 → undo 누적

MVCC에서 SELECT는 락을 안 잡는 대신 자기가 시작한 시점의 스냅샷(Read View)을 들고 있다. 10분짜리 집계는 10분 동안 Read View를 쥔다 — REPEATABLE READ면 트랜잭션 첫 조회부터, READ COMMITTED여도 그 문장이 끝날 때까지다. 그 사이 운영 트랜잭션이 만든 옛 버전(undo)은 "저 Read View가 볼 수도 있는 버전"이라 purge가 지우지 못한다.

긴 Read View 보유→purge 정지→History list length ↑→핫 로우 버전 체인 길어짐→무관한 운영 조회가 행마다 체인 순회 (undo 페이지 적재 ⇢ A)→집계 종료 후 밀린 purge가 한꺼번에 → I/O 스파이크

집계는 orders만 보지만 청구서는 users·products를 읽는 조회들이 받는다 — Read View는 테이블 단위가 아니기 때문이다. 긴 트랜잭션의 대표 주범이 바로 대시보드 집계다(MVCC 문서 §3).

D커넥션 장기 점유와 메타데이터 락(MDL)
  • 커넥션 — 대시보드가 운영 커넥션 풀(예: 최대 20)을 같이 쓰면, 위젯 6개 × 동시 사용자 2명 = 커넥션 12개가 수 분간 사라진다. 운영 요청은 남은 8개를 두고 줄을 서고 connection-timeout이 지나면 500이 난다. DB가 멀쩡해도 앱이 먼저 죽는 경로다.
  • 메타데이터 락 — SELECT는 행 락을 안 잡지만 테이블 구조가 도중에 바뀌지 않도록 공유 MDL은 잡는다 — 문장이 끝날 때까지(명시적 트랜잭션이면 커밋까지). 이때 누군가 ALTER TABLE orders ADD COLUMN을 실행하면(온라인 DDL도 시작과 끝에 잠깐 배타 MDL이 필요하다) ALTER는 집계가 끝날 때까지 기다리고, 그 ALTER 뒤로 들어오는 orders 쿼리 전부가 ALTER 뒤에 줄을 선다. SHOW PROCESSLIST에 Waiting for table metadata lock이 수십 개.
통계 쿼리 하나+컬럼 추가 하나=주문 테이블 정지
Ereplica로 보내도 남는 것 — 복제 지연 유발

"그럼 replica에서 돌리면 되죠"는 2단의 정답이지만 공짜가 아니다. replica는 primary의 변경 로그(binlog)를 적용 스레드(applier)가 재실행하는데,

  • 집계가 replica의 CPU·디스크 큐를 점유하면 적용 스레드도 같은 줄에 선다 → 적용 처리량 ↓ → lag ↑
  • primary의 DDL이 복제돼 오면 replica에서도 MDL이 필요하다 → 집계 SELECT 뒤에서 대기 → 적용 스레드가 통째로 멈춘다 → lag가 집계 실행 시간만큼 한 번에 튄다
  • replica에서도 긴 Read View는 purge를 멈춘다 (사슬 C의 replica 판)

그 lag는 이 replica를 함께 쓰는 운영 읽기 라우팅의 문제가 된다 — "등록했는데 목록에 없어요".

가산점 PostgreSQL은 스탠바이의 긴 쿼리가 WAL 적용과 충돌하면 max_standby_streaming_delay만큼 미루다 쿼리를 강제 취소한다("canceling statement due to conflict with recovery"). 취소를 피하려고 hot_standby_feedback을 켜면 이번엔 primary가 옛 버전을 못 지워 primary에 bloat가 쌓인다 — 비용이 자리만 옮긴다.

2분리 단계 사다리 — 0단부터 4단까지 (암기 목록)

이 질문의 정답은 하나의 기술이 아니라 순서가 있는 목록이다. 오르는 방향은 "운영 DB에서 집계 작업을 얼마나 멀리 떼어 놓는가" — 2단은 같은 데이터의 복제본 위에서 여전히 집계를 실행하고, 3단은 집계 자체를 미리 해두고, 4단은 집계에 맞는 다른 저장소로 옮긴다. 높이 오를수록 격리는 완전해지고 대신 지연·복잡도·비용이 는다.

  2. ① 쿼리·인덱스 다이어트 — 분리가 아니라 전제 조건. 기간 제한·커버링 인덱스·불필요 조인 제거
  3. ② 통계 전용 replica — 자원 격리(부분). 운영 read replica와도 분리. 대가: 복제 지연·여전히 무거움
  4. ③ 집계 테이블 + 사전 계산 배치 — 시간 이동: "조회 시점 계산"을 "배치 시점 계산"으로. 대가: 실시간성·보정
  5. ④ CDC → OLAP 저장소 — 시스템 분리: 열 저장소로 임의 분석. 대가: 이중 저장·파이프라인 운영

동사 다섯 개로: 묻고 → 빼고 → 옮기고 → 미리 하고 → 내보낸다. (되묻기 / 다이어트 / replica로 옮김 / 사전 계산 / OLAP로 내보냄)

2-0. 0단 — 요구를 되묻는다: 기획과의 협상 대화

기술 해법을 고르기 전에 "실시간"이 정말 요구인지를 확인한다. 대부분의 대시보드는 실시간이 아니라 "새로고침하면 바뀌는 것"을 원할 뿐이고, 그 둘은 비용이 수십 배 다르다.

백엔드이 대시보드의 "오늘 매출"은 몇 분 전 숫자면 될까요? 지금은 새로고침할 때마다 주문 테이블 전체를 다시 집계해서, 이게 돌 때 주문 API가 같이 느려집니다.
① 비용을 알려준다
기획실시간이면 좋죠. 근데 꼭 그래야 하냐고 물으시는 거면… 어디에 쓰느냐에 따라 다를 것 같아요.
백엔드용도를 여쭤볼게요. 이 매출 그래프를 보고 누가 어떤 결정을 하나요?
② "실시간"을 용도로 분해한다
기획마케팅팀이 오전에 어제까지의 추이를 보고 프로모션을 조정해요. 오늘 숫자는 참고용이고요.
백엔드그러면 "어제까지"는 하루 한 번 새벽에 계산해 두고, "오늘"만 5분 간격이면 될까요? 화면에 "○○:○○ 기준"을 붙여서 몇 분 전 숫자인지 보이게 하고요.
기획그건 괜찮아요. 다만 월말 정산 화면은 취소·환불이 정확히 반영돼야 해요.
백엔드그 화면은 '정확'이 '실시간'보다 중요하니까 — 마감 시점에 확정 계산을 돌리고, 마감 전에는 "잠정치"라고 표시하는 걸로 하죠. 이렇게 하면 운영 DB에는 부하가 거의 안 가고, 정산 숫자도 더 믿을 수 있게 됩니다.
③ 항목별로 다른 SLA를 받아낸다

백엔드가 한 일은 세 가지다 — ① 비용을 알려줬고(운영 API가 느려진다) ② "실시간"을 용도로 분해했고(의사결정 주기가 하루라면 하루 지연은 손실이 아니다) ③ 항목별로 다른 SLA를 받아냈다. 결과물은 이런 표다.

대시보드 항목허용 지연정확도처리 방식
어제까지 일별 매출 추이하루확정치새벽 배치 → 집계 테이블 (3단)
오늘 매출5분잠정치5분 배치 또는 replica 위 소량 조회 + 5분 TTL 캐시
월말 정산마감 시점확정치 (환불 반영)마감 배치 + 재계산 창

"요구사항의 비용을 알려주는 것까지가 백엔드의 일"

되묻지 않고 4단으로 직행하면 과잉 설계이고, 되묻지 않고 1단에서 버티면 운영 장애다.

되묻는 것은 기술 선택지를 여는 과정이다 — "5분"을 받아냈기 때문에 5분 TTL 캐시라는 처방이 가능해진다(§4-5).

2-1 ~ 2-4. 각 단의 "얻는 것 / 내주는 것 / 여기서 멈추는 조건"

1쿼리·인덱스 다이어트— 분리 전에 반드시. "무거운 쿼리를 옮기는 것"과 "가볍게 하는 것"은 다른 일이다
얻는 것기간 제한(WHERE paid_at >= :from — 최근 90일만) · 커버링 인덱스((seller_id, paid_at, amount) — 테이블 페이지를 안 건드려 사슬 A·B가 크게 준다) · 불필요 조인 제거(위젯이 order_items를 안 보여주는데 조인된 경우, EXPLAIN으로 rows 확인)
내주는 것 / 한계운영 DB 위에서 여전히 실행된다. 기간을 제한해도 테이블이 크는 만큼 매일 느려지는 성질은 남는다. 인덱스는 쓰기 비용을 얹는다.
멈춰도 되는 조건: "충분"의 기준은 대시보드 응답시간이 아니라 운영 지표(버퍼 풀 히트율·p99·pending)다. 대시보드는 2초 만에 나오는데 그 2초 동안 운영 p99가 튄다면 다음 단.
2통계 전용 replica— 자원 격리. 구현(readOnly 라우팅·lazy 프록시·lag 계측)은 라우팅 문서, 여기서는 판단 둘만
얻는 것primary가 사슬 A~D에서 벗어난다. 코드 변경 최소. 데이터는 항상 "거의 최신".
내주는 것복제 지연(사슬 E). replica 위에서도 집계는 똑같이 10분 — 사용자 수·실행 횟수에 못 버틴다. 인프라 비용.

판단 ① 운영 read replica와 통계 replica를 분리한다. 같은 replica에 두면 사슬 A·B·C가 replica 위에서 재현돼 운영 조회(목록·상세)가 느려지고 lag가 커져 read-your-writes 문제가 잦아진다. 허용 lag가 다른 워크로드는 다른 복제본에 둔다 — 통계 replica는 lag 1분이어도 상관없지만 운영 replica는 그러면 안 된다.

primary ──복제──▶ replica-1, replica-2   ← 운영 읽기 라우팅 (lag 임계 낮음, 풀 제외 정책 있음)
        └─복제──▶ replica-stats          ← 대시보드·배치·분석가 (lag 임계 느슨, 타임아웃 길게 허용)

판단 ② replica는 "격리"이지 "해결"이 아니다. 대시보드 사용자가 5명이고 하루 몇 번 보는 내부 도구라면 충분하다. 셀러 10만 명이 각자 자기 매출을 본다면 replica가 몇 대여도 못 버틴다 — 그때는 3단.

멈춰도 되는 조건: 실행 횟수가 적고 실행 시간을 감수할 수 있을 때. 초 단위 지연 OK · 쿼리 고정 · 내부 사용자 소수.
3집계 테이블 + 사전 계산 배치— 이 문항의 중심. 계산을 조회 시점에서 배치 시점으로 옮긴다

조회 때마다 3년치 주문을 접는 대신 새벽에 한 번 접어서 "날짜 × 셀러"당 한 행짜리 작은 테이블에 넣어 두고, 대시보드는 그 테이블에서 몇 행만 읽는다. 조회 비용이 O(주문 수)에서 O(날짜 수)로 떨어지고 운영 DB는 집계 실행에서 완전히 벗어난다. 반정규화 문서의 "연산 컬럼"(posts.comment_count)이 행 하나에 붙는 반정규화였다면, 집계 테이블은 테이블 단위의 반정규화다 — 그래서 대가도 같은 종류다: 원본과 사본이 어긋날 수 있고, 어긋남을 관리하는 장치를 함께 설계해야 한다.

얻는 것조회 수 밀리초. 운영 DB는 집계에서 완전 해방. 사용자 수에 무관. 배치 끝난 시점의 일관된 스냅샷(위젯끼리 숫자가 어긋나지 않는다).
내주는 것실시간성 상실. 배치 실패·지연·중복 실행 시 틀린 숫자. 원본 정정(환불·취소)의 재반영. 질문이 바뀌면 테이블·배치도 바뀐다.
맞는 경우: 질문이 고정돼 있다(위젯은 정해진 차원으로 정해진 숫자를 본다) · 지연 분~하루 허용 · 사용자·조회 횟수 많음. 안 맞는 경우: 매번 다른 차원으로 자르는 임의 질의(ad-hoc) — 차원 조합마다 테이블을 만들다 수십 개가 되고 배치가 새벽을 다 잡아먹는다. 그 신호가 오면 4단.
4CDC → OLAP 저장소— 시스템 분리. binlog를 읽어 행 변경 이벤트를 흘리는 CDC(Debezium)로 Kafka를 거쳐 열 저장소(ClickHouse·BigQuery·Redshift·Snowflake)에 적재

열 저장소가 집계에 유리한 이유는 구조에 있다. 행 저장소는 SUM(amount) 하나를 구하려 해도 행 전체(수십 컬럼)가 든 페이지를 읽지만, 열 저장소는 amount 컬럼 블록만 읽는다 — 읽는 바이트가 수십 분의 1이고 같은 타입이 연속돼 압축률도 높다. OLAP 전용 DB가 따로 존재하는 이유가 이 한 줄이다.

얻는 것임의 질의·차원 자유. 열 저장 압축·속도. 분석 워크로드가 운영에서 완전 분리 — 분석가가 어떤 차원으로 잘라도 운영 DB는 전혀 모른다.
내주는 것데이터가 두 벌(저장 비용 + 어느 쪽이 정답인지의 규칙). 파이프라인이 운영 대상(커넥터 죽음·오프셋·재처리). 운영 스키마 변경이 파이프라인을 깨뜨림(스키마 진화 동기화). 개인정보 복제 범위 확대(마스킹). 초~분의 최종 일관성.
맞는 경우: 임의 질의 필요 · 차원이 자주 바뀜 · 분석가·BI 도구가 SQL로 직접 탐색 · 집계 테이블이 10개를 넘어가며 배치 창이 모자람.

2-5. 어느 단에서 멈추나 — 판단 기준 한 표

상황멈출 단
지연 허용 안 됨 + 쿼리를 인덱스로 가볍게 만들 수 있음1단
초 단위 지연 OK, 쿼리 고정, 내부 사용자 소수, 실행 횟수 적음2단
분~하루 지연 OK, 질문 고정(위젯), 사용자·조회 횟수 많음3단 (+2단 위에서 배치 실행)
임의 질의, 차원 다수, 분석가 존재, 집계 테이블 폭증4단

실무에서 가장 흔한 착지는 2단 + 3단의 조합이다 — 배치는 통계 replica에서 읽어 계산하고, 결과만 작은 테이블에 쓰고, 대시보드는 그 작은 테이블을 읽는다.

3트레이드오프 양면 — 세 해법을 한 호흡에

질문은 괄호 안에 해법 셋을 적어줬다. 면접관이 보는 것은 "셋 중 뭘 쓰겠느냐"가 아니라 "각각 무엇을 얻고 무엇을 내주는지를 같은 문장 안에서 말하는가"다. 얻는 것 → 내주는 것 → 내준 것을 관리하는 장치, 세 박자를 한 호흡으로.

표를 양면 문장으로 조립하면 — 면접에서 그대로 말하는 형태

"replica로 보내면 primary는 버퍼 풀·CPU·undo 잠식에서 벗어나고 코드도 거의 안 바뀌지만, 대신 복제 지연을 감수해야 하고 집계 자체는 replica에서 여전히 10분이 걸려서 사용자가 많아지면 못 버팁니다. 그래서 통계 전용 replica를 따로 두고 lag를 지표로 봅니다.

집계 테이블로 내리면 조회가 수 밀리초로 떨어지고 운영 DB는 집계에서 완전히 해방되지만, 대신 실시간성을 잃고 배치가 실패하거나 두 번 돌거나 원본이 나중에 정정되면 숫자가 틀립니다. 그래서 배치를 구간 재계산 + UPSERT로 멱등하게 만들고 재계산 창과 성공 시각을 화면에 노출합니다.

CDC로 OLAP 저장소에 빼면 어떤 차원으로 잘라도 운영이 모르지만, 대신 데이터가 두 벌이 되고 파이프라인이 새 운영 대상이 되며 스키마 변경 때마다 동기화를 챙겨야 합니다. 그래서 질문이 고정된 대시보드에는 과합니다."

공식: "~하면 [얻는 것]이지만, 대신 [내주는 것]입니다. 그래서 [관리 장치]를 둡니다." — 세 해법 모두 이 틀 하나.

"실시간을 잃는다"는 항상 손실이 아니다

집계 테이블은 배치가 끝난 시점의 일관된 스냅샷이라 "위젯 A는 10:00 기준, 위젯 B는 10:03 기준"처럼 위젯 간 숫자가 안 맞는 일이 없다. 실시간 집계는 매 위젯이 다른 순간을 보므로 "합계가 안 맞아요" 문의가 온다. 정산·리포트처럼 "모두가 같은 숫자를 봐야 하는" 화면은 오히려 사전 계산이 정확성 면에서 낫다. — 내주는 것 안에 숨은 얻는 것까지 말하면 양면을 진짜로 아는 사람이다.

4집계 테이블·배치 설계 — before / after

4-1. before — 대시보드가 운영 리포지토리를 그대로 쓴다

// ❌ before — 운영 JPA 리포지토리에 집계 쿼리를 얹었다
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("""
        select new com.shop.dashboard.DailySales(function('date', o.paidAt), sum(o.amount))
        from Order o
        where o.sellerId = :sellerId and o.paidAt between :from and :to
        group by function('date', o.paidAt)
        """)
    List<DailySales> aggregateDailySales(Long sellerId, LocalDateTime from, LocalDateTime to);   // 운영 리포지토리 안에 집계가 산다
}

@RestController
class DashboardController {
    private final OrderRepository orderRepository;   // ❌ 운영 DataSource · 운영 커넥션 풀(20) · 운영 계정 app

    @GetMapping("/seller/dashboard/sales")
    List<DailySales> sales(@AuthSeller Long sellerId, LocalDate from, LocalDate to) {
        return orderRepository.aggregateDailySales(sellerId, from.atStartOfDay(), to.plusDays(1).atStartOfDay());
        // ❌ @Transactional 없음 → readOnly 라우팅을 탈 정보 자체가 없어 primary로 간다
        // ❌ 타임아웃 없음 → from=2021-01-01을 넣으면 수 분짜리 쿼리가 운영 풀 커넥션을 수 분 점유
        // ❌ 운영 계정 → 실수로 잠금 조회를 붙여도, 다른 테이블을 조인해도 막을 것이 없다
        // ❌ 셀러 10만 명이 각자 새로고침 → 사슬 A~D가 동시에 10만 번
    }
}

4-2. after ① — 집계 테이블 스키마: 단위(grain)를 먼저 정한다

집계 테이블 설계의 첫 결정은 한 행이 무엇을 뜻하는가(grain)다. "날짜 × 셀러"로 정하면 대시보드가 보여줄 수 있는 것은 그 단위와 그 단위를 더한 것뿐이다(셀러별 일·주·월 매출은 되고, 상품별은 안 된다). 차원을 하나 추가할 때마다 행 수가 곱으로 늘므로 위젯이 실제로 자르는 차원만 넣는다.

영수증 더미 vs 일계표

월말 결산 때마다 영수증 더미(orders)를 처음부터 다시 더하지 않고, 하루 한 번 "날짜별 매출 한 줄"짜리 일계표(daily_seller_sales)를 적어 두는 것. 일계표의 한 줄이 무엇인지(grain)를 먼저 정해야 한다 — "날짜 × 셀러" 한 줄이면 월 합계는 줄을 더해서 나오지만 "상품별"은 애초에 적지 않았으니 안 나온다.

-- ✅ after ① — 날짜 × 셀러 단위 집계 테이블
CREATE TABLE daily_seller_sales (
    stat_date     DATE          NOT NULL,
    seller_id     BIGINT        NOT NULL,                  -- grain = (날짜, 셀러) 한 행
    order_count   INT           NOT NULL,
    gross_amount  DECIMAL(15,2) NOT NULL,   -- 결제 금액 합
    refund_amount DECIMAL(15,2) NOT NULL,   -- 환불 금액 합 (원본 정정을 흡수하는 컬럼)
    net_amount    DECIMAL(15,2) NOT NULL,   -- gross - refund
    computed_at   DATETIME      NOT NULL,   -- 이 행을 마지막으로 계산한 시각 → 화면의 "기준 시각"
    PRIMARY KEY (stat_date, seller_id)      -- 조회 패턴: 셀러 하나의 기간 범위 → (seller_id, stat_date)도 검토
);

-- 배치 실행 상태: 대시보드가 "어디까지 계산됐는지"를 이 표에서 읽는다
CREATE TABLE stats_batch_run (
    id               BIGINT AUTO_INCREMENT PRIMARY KEY,
    job_name         VARCHAR(64)  NOT NULL,
    range_from       DATE         NOT NULL,
    range_to         DATE         NOT NULL,   -- exclusive
    status           VARCHAR(16)  NOT NULL,   -- RUNNING / SUCCESS / FAILED  → 알람은 이 컬럼을 본다
    started_at       DATETIME     NOT NULL,
    finished_at      DATETIME     NULL,
    error_message    TEXT         NULL,
    INDEX idx_job_status (job_name, status, finished_at)
);

어디에 두는가도 결정이다. 쓰기가 하루 수만 행으로 작으므로 운영 DB(primary)에 둬도 되고, 그러면 통계 replica로 복제돼 대시보드가 거기서 읽는다. 완전한 격리를 원하면 별도 stats DB에 둔다. 어느 쪽이든 무거운 계산(원본 읽기)은 통계 replica에서 하고, 가벼운 결과 쓰기만 primary로 간다 — 읽는 곳과 쓰는 곳이 다르다는 점이 §5-1에서 DataSource가 둘로 나뉘는 이유다.

4-3. after ② — 증분 배치: 재계산 창 + 구간 절대값 재계산 + UPSERT

배치 설계에서 가장 중요한 결정은 "어제 값에 더할 것인가, 어제 구간을 통째로 다시 계산할 것인가"다.

증분 덧셈 — 멱등하지 않다net_amount = net_amount + 오늘 새 주문 합
빠르다. 그러나 배치가 두 번 돌면 두 배가 되고, 어제 주문이 오늘 환불되면 어제 행을 어떻게 고칠지 별도 로직이 필요하다.
구간 절대값 재계산 — 멱등하다net_amount = 그 날짜 구간 전체를 다시 SUM
같은 구간을 몇 번 돌려도 같은 값. 환불도 원본에 반영돼 있으면 다시 계산할 때 저절로 반영. 대신 구간이 넓을수록 배치가 무겁다.

그래서 정석은 "최근 N일(재계산 창)은 매번 통째로 다시 계산하고, 그 이전은 건드리지 않는다"다. N은 "원본이 정정될 수 있는 기간"(환불 가능 기간, 지연 도착 데이터의 최대 지연)에서 나온다.

멱등성은 재시도 정책이 아니라 계산 방식에서 나온다.

"잔액에 +210" 메모는 두 번 적으면 틀리지만 "D-1 합계 = 210" 메모는 두 번 적어도 안 틀린다. UPSERT는 그 메모를 같은 자리에 덮어쓰는 장치다. ShedLock은 "동시에" 도는 것을 막고, 멱등성은 "따로따로 두 번" 도는 것을 무해하게 만든다 — 둘은 다른 구멍을 막는다.

// ✅ after ② — 통계 replica에서 읽고(무거움), primary에 결과만 쓴다(가벼움)
@Component
public class DailySalesAggregationJob {

    private static final int RECOMPUTE_WINDOW_DAYS = 3;   // 환불 가능 기간·지연 도착 상한에서 도출

    private final NamedParameterJdbcTemplate statsJdbc;   // → replica-stats (§5-1)  : 무거운 읽기
    private final NamedParameterJdbcTemplate mainJdbc;    // → primary               : 가벼운 쓰기
    private final StatsBatchRunRepository runRepository;

    @Scheduled(cron = "0 10 0 * * *", zone = "Asia/Seoul")
    @SchedulerLock(name = "dailySalesAggregation", lockAtMostFor = "PT2H")   // 인스턴스 2대면 배치도 2번 "동시에" 도는 문제 차단
    public void run() {
        LocalDate to   = LocalDate.now(ZoneId.of("Asia/Seoul"));            // exclusive: 오늘은 아직 안 닫힘
        LocalDate from = to.minusDays(RECOMPUTE_WINDOW_DAYS);               // 재계산 창 시작
        long runId = runRepository.start("dailySalesAggregation", from, to);
        try {
            // 1) 무거운 읽기: 재계산 창 구간을 통째로 다시 집계 (replica-stats, 타임아웃 넉넉히)
            List<DailySellerSalesRow> rows = statsJdbc.query("""
                SELECT /*+ RESOURCE_GROUP(stats_rg) */
                       DATE(o.paid_at)                         AS stat_date,
                       o.seller_id,
                       COUNT(*)                                AS order_count,
                       SUM(o.amount)                           AS gross_amount,
                       SUM(COALESCE(r.amount, 0))              AS refund_amount
                FROM orders o
                LEFT JOIN refunds r ON r.order_id = o.id
                WHERE o.paid_at >= :from AND o.paid_at < :to                -- 구간 절대값: 더하지 않고 다시 센다
                  AND o.status IN ('PAID', 'REFUNDED')
                GROUP BY DATE(o.paid_at), o.seller_id
                """, Map.of("from", from.atStartOfDay(), "to", to.atStartOfDay()), ROW_MAPPER);

            // 2) 가벼운 쓰기: 같은 키면 덮어쓴다 → 두 번 돌아도 같은 결과 (멱등)
            mainJdbc.batchUpdate("""
                INSERT INTO daily_seller_sales
                    (stat_date, seller_id, order_count, gross_amount, refund_amount, net_amount, computed_at)
                VALUES (:statDate, :sellerId, :orderCount, :gross, :refund, :gross - :refund, NOW())
                AS new
                ON DUPLICATE KEY UPDATE
                    order_count = new.order_count, gross_amount = new.gross_amount,
                    refund_amount = new.refund_amount, net_amount = new.net_amount,
                    computed_at = new.computed_at
                """, SqlParameterSourceUtils.createBatch(rows));
            // PostgreSQL이면 ON CONFLICT (stat_date, seller_id) DO UPDATE SET ... = EXCLUDED.... 형태

            // 3) 창 안에서 주문이 0건이 된 (날짜, 셀러)는 UPSERT로는 안 지워진다 — 창 구간을 먼저 DELETE 하거나
            //    0건 행을 명시적으로 만들어 넣는다. (전부 환불돼도 order_count는 남으므로 보통은 문제 없음)

            runRepository.success(runId);
        } catch (Exception e) {
            runRepository.fail(runId, e);   // 알람은 이 상태를 보고 울린다 (§4-4)
            throw e;
        }
    }
}

주석 3)이 놓치기 쉬운 구멍이다 — UPSERT는 "있는 키를 갱신"하지 "사라진 키를 삭제"하지는 않는다. 재계산 창 안의 키가 원본에서 완전히 없어질 수 있는 도메인(주문 삭제가 물리 삭제인 경우)이라면 창 구간 DELETE 후 INSERT가 더 안전하다. 그 경우 DELETE와 INSERT를 한 트랜잭션으로 묶어 대시보드가 빈 구간을 보지 않게 한다. 데이터가 커서 한 번에 못 읽으면 reader(replica)–processor–writer(primary) 청크 구조, 즉 Spring Batch의 기본 모양(11장)이 정확히 이 형태다.

4-4. 실패 세 가지와 보정 — "어긋남을 전제로 설계한다"

집계 테이블은 원본의 사본이다. 사본은 어긋난다. 세 장치의 관계는 "어긋남을 막는다"가 아니라 "어긋남이 남아 있는 시간을 줄인다"다.

실패 ①배치가 안 돌았다 / 실패했다대시보드에 어제 숫자가 없거나 그제 숫자가 어제로 보인다.
장치stats_batch_run의 마지막 SUCCESS가 기준 시각 이후에 없으면 알람. 화면에 computed_at을 "○월 ○일 00:10 기준"으로 노출해 낡은 숫자를 숨기지 않는다. 복구는 그냥 다시 돌리는 것 — 멱등하니까. runbook + 관리자 수동 트리거.
실패 ②배치가 두 번 돌았다재시도, 인스턴스 2대, 수동 실행과 스케줄 겹침.
장치구간 절대값 재계산 + UPSERT는 몇 번 돌아도 같은 값. 덧셈 누적이었다면 여기서 두 배가 됐다. ShedLock은 "동시에", 멱등성은 "따로따로 두 번" — 다른 구멍.
실패 ③원본이 나중에 바뀌었다어제 주문이 오늘 환불, 결제 확정 지연으로 어제 주문이 오늘 도착(late-arriving), 운영자의 DB 직접 정정.
장치 세 겹1) 재계산 창 — 최근 N일은 매일 다시 계산되니 자동 반영 · 2) 창 밖은 정정 이벤트(refund.created)가 (stat_date, seller_id)를 재계산 큐에 · 3) 월 1회 전체 대사 — 이벤트를 안 거치는 경로를 잡는 마지막 그물.

4-5. 하이브리드 — 과거는 집계 테이블, 오늘은 소량 실시간

"오늘 매출은 5분 지연"이라는 0단의 합의를 구현하는 가장 단순한 형태는 과거 구간과 오늘 구간을 다른 곳에서 읽어 합치는 것이다.

-- 어제까지: 집계 테이블 (행 수 = 날짜 수)
SELECT stat_date, net_amount
FROM daily_seller_sales
WHERE seller_id = :sellerId AND stat_date >= :from AND stat_date < CURRENT_DATE

UNION ALL

-- 오늘: 원본에서 오늘치만 (replica-stats, (seller_id, paid_at) 인덱스로 오늘 범위만 탐색 → 수십~수백 행)
SELECT CURRENT_DATE, SUM(o.amount) - SUM(COALESCE(r.amount, 0))
FROM orders o LEFT JOIN refunds r ON r.order_id = o.id
WHERE o.seller_id = :sellerId AND o.paid_at >= CURRENT_DATE AND o.status IN ('PAID', 'REFUNDED');

오늘 구간은 셀러 하나의 하루치라 인덱스 범위 탐색으로 작게 끝난다(1단 다이어트의 조건을 만족한다). 그래도 셀러 10만 명이 초 단위로 새로고침하면 부담이므로 오늘 구간 결과를 5분 TTL 캐시에 얹는다 — 0단에서 "5분"을 받아냈기 때문에 가능한 처방이다.

5안전망 5층 — 통계 쿼리가 운영 DB로 새지 못하게 고정한다

"통계 쿼리는 replica로 보내기로 했다"는 결정은 새 위젯을 만드는 다음 개발자가 모른다. 결정은 코드·권한·설정·빌드가 지키게 한다. 아래 다섯 층은 하나가 뚫려도 다음 층이 잡도록 겹친다.

층 1
문
DataSource 분리통계 코드는 물리적으로 다른 문(별도 빈·별도 풀·별도 계정)으로만 나간다. 잡는 것: "실수로 운영 리포지토리를 주입"
↓ 뚫리는 경우: 누군가 통계 코드에 운영 DataSource를 꽂거나 jdbc-url을 바꿈
층 2
권한
읽기 전용 계정 + 접속 수 상한 + 리소스 그룹 + 네트워크코드가 뚫려도 DB가 거부한다. 잡는 것: UPDATE·FOR UPDATE 혼입, 풀 크기 40으로 올린 설정, primary 주소 입력
↓ 뚫리는 경우: 권한은 맞는데 쿼리가 너무 오래 돈다
층 3
시간
타임아웃 3겹 (DB 세션 / JDBC / 풀)한 건이 수 분 점유하지 못하게. 잡는 것: from=2021-01-01 같은 입력, 고아 쿼리, 동시 폭주
↓ 뚫리는 경우: 설정은 다 맞는데 새 코드가 규칙을 모름
층 4
규칙
ArchUnit — 대시보드 패키지는 운영 리포지토리에 의존 불가빌드가 깨진다. 잡는 것: 다음 개발자의 새 위젯, 코드 리뷰가 놓친 의존
↓ 뚫리는 경우: 빌드는 통과했는데 운영에서 새고 있음
층 5
눈
관측 — primary에 stats 계정 쿼리가 1건이라도 보이면 알람"통계 쿼리는 운영 DB로 가지 않는다"는 결정 자체를 지표로 감시. 틀려도 에러가 안 나는 결정은 지표로만 지킬 수 있다

다섯 층 인출 — 문 · 권한 · 시간 · 규칙 · 눈

DataSource(문) → 읽기 전용 계정(권한) → 타임아웃 3겹(시간) → ArchUnit(규칙) → 알람(눈)

앞 셋은 런타임이 막고, 넷째는 빌드가 막고, 다섯째는 지표가 알린다. "조심한다"는 어느 층에도 없다.

5-1. 층 1 — DataSource 분리: @Qualifier로 물리적으로 다른 문을 낸다

public enum DataSourceKey { MASTER, REPLICA, STATS }

@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME)
public @interface StatsQuery {}

@Aspect @Component
public class StatsRouteAspect {
    @Around("@annotation(StatsQuery)")
    public Object route(ProceedingJoinPoint pjp) throws Throwable {
        RouteContext.force(DataSourceKey.STATS);        // determineCurrentLookupKey()가 ①번으로 먼저 본다
        try { return pjp.proceed(); }
        finally { RouteContext.clear(); }                // 안 지우면 다음 요청이 같은 스레드에서 STATS로 샌다
    }
}

LazyConnectionDataSourceProxy 필수, ThreadLocal 정리, @Async 스레드 유실 함정은 라우팅 문서와 같다. 단점은 명확하다 — 같은 EntityManagerFactory·같은 JdbcTemplate을 공유하므로 타임아웃·풀 크기·계정을 통계만 따로 주기가 어렵고, 애노테이션을 빠뜨린 새 위젯은 조용히 primary로 간다. 통계처럼 경계가 뚜렷한 모듈은 별도 DataSource가 맞고, 라우팅은 같은 엔티티를 읽는 OLTP 조회 분산에 맞다.

5-3. 층 2 — 권한: 읽기 전용 계정 + 접속 수 상한 + 리소스 그룹 + 네트워크

코드가 뚫려도 DB가 거부하게 한다. 조용히 잘못 동작하는 것보다 시끄럽게 실패하는 것이 낫다.

-- MySQL — 통계 워커 대역에서만, SELECT만, 동시 접속 상한
CREATE USER 'stats_ro'@'10.0.20.%' IDENTIFIED BY '...';
GRANT SELECT ON shop.* TO 'stats_ro'@'10.0.20.%';
ALTER USER 'stats_ro'@'10.0.20.%' WITH MAX_USER_CONNECTIONS 8;   -- 인스턴스 수 × stats 풀 크기 이하

-- MySQL 8.0 리소스 그룹 — 통계 스레드를 특정 코어·낮은 우선순위에 가둔다 (리눅스, 우선순위 적용에는 CAP_SYS_NICE 필요)
CREATE RESOURCE GROUP stats_rg TYPE = USER VCPU = 6-7 THREAD_PRIORITY = 15;
GRANT RESOURCE_GROUP_USER ON *.* TO 'stats_ro'@'10.0.20.%';
-- 쿼리에서: SELECT /*+ RESOURCE_GROUP(stats_rg) MAX_EXECUTION_TIME(30000) */ ...

-- PostgreSQL — 역할 단위로 타임아웃·읽기 전용·접속 수를 박아둔다
CREATE ROLE stats_ro LOGIN PASSWORD '...' CONNECTION LIMIT 8;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO stats_ro;
ALTER ROLE stats_ro SET statement_timeout = '30s';
ALTER ROLE stats_ro SET default_transaction_read_only = on;
  • GRANT SELECT만 — 통계 코드에 실수로 UPDATE가 섞이면 권한 오류로 즉시 실패. SELECT ... FOR UPDATE도 UPDATE 권한이 없으면 거부된다.
  • 접속 수 상한 — 앱의 풀 크기를 누가 40으로 올려도 DB가 8에서 막는다. 설정은 바뀌지만 권한은 리뷰를 거친다.
  • 리소스 그룹 — 사슬 B(코어 독점)를 DB 안에서 직접 억제한다. 통계 스레드가 8코어 중 2개에만 묶이면 나머지 6개는 운영 몫. primary에서 돌아가는 무거운 배치(정산 확정 등)에 특히 유효.
  • 네트워크 층 — 계정은 primary에서 만들면 replica로 복제되므로 "계정이 replica에만 있다"는 성립하지 않는다. primary의 3306 포트를 여는 보안 그룹에 통계 워커·분석 도구 대역을 넣지 않는 것이 실제 차단이다. datasource.stats.jdbc-url에 primary 주소를 넣어도 연결이 안 된다.

5-4. 층 3 — 타임아웃 3겹: 왜 하나로는 부족한가

층설정잡는 것
DB 세션MySQL max_execution_time(ms, SELECT 전용) / PG statement_timeout앱이 죽어도 DB가 스스로 쿼리를 죽인다. 앱 재시작·네트워크 단절 뒤 고아 쿼리가 계속 도는 것을 막는다 — 마지막 보루

세 층이 필요한 이유는 잡는 대상이 다르기 때문이다. JDBC 타임아웃만 있으면 앱이 OOM으로 죽는 순간 KILL QUERY를 보낼 주체가 사라져 DB에서 집계가 끝까지 돈다. DB 타임아웃만 있으면 30초 동안 톰캣 스레드가 묶여 있다. 풀 상한이 없으면 30초짜리 쿼리 100개가 동시에 들어와 replica가 넘어간다.

배치 잡은 예외 — "통계"라는 이름 하나로 묶지 않는다

새벽 배치의 집계는 30초를 넘는 것이 정상이므로 배치용 JdbcTemplate은 setQueryTimeout(1800)처럼 따로 잡고, 대시보드 API용과 빈을 분리한다. 대화형(짧게)과 배치(길게)를 나눈다. 이걸 안 나누면 §7의 "배치가 새벽에 실패했다"의 원인이 30초 타임아웃 자신이 된다.

6실제 사례 — 월말 정산 대시보드가 주문 API를 세웠다

  1. 증상월말 오전 10시, 주문 생성 API p99 200ms → 3s. DB CPU 45% → 95%. 배포 없음. 앱 로그에 HikariPool-1 - Connection is not available, request timed out after 3000ms 산발.
  2. 진단SHOW PROCESSLIST — 계정 app으로 14분째 Sending data 상태인 쿼리 4개, 전부 SELECT ... FROM orders o JOIN order_items oi ... GROUP BY o.seller_id, DATE(o.paid_at). 정산팀이 월말이라 정산 대시보드를 여러 탭에서 열어둔 것. Innodb_buffer_pool_reads 급증(사슬 A), History list length 수백만(사슬 C), HikariCP active 20/20 with pending(사슬 D).
  3. 즉시해당 쿼리 KILL QUERY. 정산 대시보드 메뉴를 feature flag로 잠시 내림. 5분 안에 p99 회복.
  4. 단기(그 주)층 1~3 — statsDataSource(통계 replica, stats_ro, 풀 4, 30초 타임아웃) 분리. 운영 영향은 0이 됐지만 대시보드는 여전히 replica에서 14분 — 2단은 격리이지 해결이 아님을 팀이 체감.
  5. 중기(그 달)0단 협상 — 정산팀과 "마감 전 잠정치(하루 1회 갱신) / 마감 후 확정치(마감 배치)" 합의. 3단 — daily_seller_sales + 새벽 배치 + 3일 재계산 창 + 환불 이벤트 재계산 큐. 대시보드 응답 50ms. 층 4·5 — ArchUnit 룰과 primary의 stats_ro 쿼리 수 알람 추가.
  6. 배운 것"배포 안 했는데요"의 변경은 코드가 아니라 달력(월말)이었다. 시스템은 데이터 증가·사용 패턴·인접 배치로 매일 바뀐다 — 다음 문항("변경 없음"의 검증)으로 이어지는 교훈.

7꼬리질문 셀프 테스트 — 먼저 소리 내어 답하고 펼친다

"replica로 보냈는데 운영 API가 여전히 느려집니다. 왜죠?"

원인 후보를 두 갈래로 나눠 확인한다.

① 정말 replica로 갔는가 — 라우팅 기반이라면 LazyConnectionDataSourceProxy 누락이나 @Transactional(readOnly = true) 누락으로 primary로 새고 있을 가능성이 1순위. 확인은 "라우팅 키별 쿼리 수 비율" 지표 또는 primary의 PROCESSLIST에서 집계 쿼리를 직접 찾는 것. 별도 DataSource 방식이면 jdbc-url과 계정을 확인 — 층 5-①의 알람이 있으면 이미 울렸을 것이다.

② replica로 갔는데도 운영이 느리다면 — 그 replica를 운영 읽기가 같이 쓰고 있는지 본다. 그렇다면 사슬 A·B·C가 replica 위에서 운영 조회를 느리게 하고, 사슬 E로 lag가 커져 라우팅이 그 replica를 풀에서 빼면 남은 replica나 primary가 그 부하를 다 받는다. 처방은 통계 전용 replica 분리. PostgreSQL이라면 반대로 통계 쿼리가 취소되는 증상(recovery conflict)이 먼저 올 수도 있다 — hot_standby_feedback은 primary bloat로 비용이 옮겨오므로, 전용 스탠바이에서 max_standby_streaming_delay를 넉넉히 주는 쪽이 맞다.

"집계 배치가 새벽에 실패했습니다. 대시보드는 어떻게 되고, 어떻게 복구하나요?"

대시보드는 어제 배치 결과(그제까지의 숫자)를 그대로 보여주되, computed_at 기준 시각이 화면에 있어 사용자가 "어제 것이 아직 안 들어왔다"를 알 수 있어야 한다. 낡은 숫자를 최신인 척 보여주는 것이 진짜 사고다.

복구는 재실행이다 — 구간 절대값 재계산 + UPSERT라서 실패 지점이 어디였든 처음부터 다시 돌리면 된다. 도중에 절반만 UPSERT됐어도 다음 실행이 덮어쓴다. 필요한 것은 ① stats_batch_run의 FAILED를 보고 우는 알람 ② 관리자용 수동 트리거 ③ 실패 원인이 30초 타임아웃이면 배치용 JdbcTemplate의 타임아웃이 대화형용과 분리돼 있는지 확인 ④ 재계산 창이 3일이므로 하루 실패는 다음 날 배치가 자동으로 메운다 — 창은 정정 반영만이 아니라 실패 흡수 장치이기도 하다. 덧셈 누적 방식이었다면 "어디까지 더해졌는지"를 알아내야 해서 복구가 수작업이 된다.

"환불·주문 취소처럼 과거 데이터가 바뀌면 집계 테이블은 어떻게 맞추나요?"

세 겹으로 답한다. ① 최근 N일은 재계산 창이 매일 다시 계산하므로 자동 반영 — N은 환불 가능 기간에서 도출. ② 창 밖의 정정은 정정 이벤트(refund.created)가 해당 (stat_date, seller_id)를 재계산 큐에 넣고 다음 배치가 그 키만 추가 계산. ③ 이벤트를 안 거치는 경로(운영자 DB 직접 수정)를 위해 월 1회 원본과 집계의 합계를 대사해 차이 나는 달을 재계산.

스키마 차원의 답을 덧붙이면 좋다 — refund_amount를 별도 컬럼으로 둔 이유가 이것이다. 환불이 gross_amount를 깎는 게 아니라 refund_amount에 쌓이므로 "환불 전 매출"과 "순매출"을 둘 다 보여줄 수 있고, 정산팀의 "환불이 제대로 반영됐나요?" 문의에 숫자로 답할 수 있다. 집계 테이블의 컬럼은 정정이 어떻게 들어오는지를 알고 설계한다.

"실시간 통계가 정말 필요하다고 하면요?" 시니어 변별

먼저 "실시간"을 항목별로 쪼갠다 — 대시보드 전체가 실시간이어야 하는 경우는 거의 없다. 0단의 표처럼 "오늘 매출 5분 / 어제까지 하루 / 접속자 수 초 단위"로 분해하면 진짜 실시간이 필요한 항목은 한두 개로 준다.

그 한두 개에 대한 처방은 RDB 밖이다. ① 이벤트 시점에 미리 더해두는 카운터(Redis INCRBY, 주문 확정 이벤트마다 sales:today:{sellerId}에 가산 — 조회는 O(1)) ② 스트림 집계(Kafka Streams·Flink로 주문 이벤트를 윈도우 집계해 결과를 Redis나 집계 테이블에 씀). 둘 다 "조회 시점에 계산하지 않는다"는 원칙은 3단과 같고, 계산 시점이 "배치"에서 "이벤트 도착 순간"으로 당겨진 것뿐이다.

대가를 같은 호흡에 — 카운터는 이벤트 유실·중복 시 어긋나고 원본과 대사가 필요하다. 스트림 집계는 인프라(Kafka·상태 저장소)와 운영 역량이 필요하고, 지연 도착·정정 이벤트를 윈도우가 닫힌 뒤 어떻게 반영할지가 어렵다. 그래서 "정말 필요한가"를 한 번 더 되묻는 것이 시니어의 답이다 — "실시간 대신 5분 지연이면 비용이 1/10인데, 5분이 의사결정을 바꾸나요?"

"이게 CQRS인가요? 뭐가 다른가요?" 가산점

핵심 아이디어는 같다 — 쓰기 모델(정규화된 orders)과 읽기 모델(대시보드에 맞게 접힌 daily_seller_sales)을 분리하고, 읽기 모델을 쓰기 모델에서 파생시킨다. rationale이 "12장 CQRS의 실용 판"이라 부른 이유다.

다른 점은 파생 방법과 범위다. 교과서 CQRS는 커맨드 측이 이벤트를 발행하고 프로젝터가 이벤트를 소비해 읽기 모델을 갱신하며, 이벤트 소싱과 함께 오는 경우가 많다. 여기서는 배치(3단)나 CDC(4단)가 그 프로젝터 역할을 하고, 쓰기 모델은 평범한 RDB 테이블 그대로다. 아키텍처를 바꾸지 않고 CQRS의 이득(읽기 모델 최적화, 워크로드 격리)만 취하는 것이 실용 판이라는 뜻이다. 이 답을 하면 "패턴 이름을 아는 사람"이 아니라 "패턴이 해결하는 문제를 아는 사람"으로 보인다.

"READ COMMITTED로 낮추면 Read View가 문장마다 새로 생기니 undo 문제는 없지 않나요?" 추가

아니다. READ COMMITTED는 문장마다 Read View를 새로 만들 뿐, 그 문장이 끝날 때까지는 유지한다. 집계는 문장 하나가 10분이므로 그 10분 동안 purge가 멈추는 것은 같다. 격리 수준은 "여러 문장에 걸친 트랜잭션"의 Read View 수명을 줄여줄 뿐, 문장 하나가 긴 것은 해결하지 못한다. 그래서 처방은 격리 수준이 아니라 문장을 짧게 만들거나(1단), 다른 곳에서 돌리거나(2단), 아예 조회 시점에 계산하지 않는 것(3단)이다.

"ShedLock을 걸었으면 멱등성은 필요 없지 않나요?" 추가

둘은 다른 구멍을 막는다. ShedLock은 인스턴스 2대가 동시에 같은 잡을 도는 것을 막는다. 멱등성은 따로따로 두 번 도는 것 — 실패 후 재시도, 관리자의 수동 트리거와 스케줄의 겹침, 지난달 데이터의 재계산 요청 — 을 무해하게 만든다. ShedLock만 있으면 재시도가 두 배를 만들고, 멱등성만 있으면 동시 실행이 replica를 두 배로 두드린다. 동시성 제어와 멱등성은 항상 짝이다.

"UPSERT로 못 잡는 경우는요?" 추가

UPSERT는 "있는 키를 갱신"하지 "사라진 키를 삭제"하지 않는다. 재계산 창 안에서 어떤 (stat_date, seller_id)의 주문이 원본에서 완전히 없어지면(물리 삭제) 집계 테이블에는 옛 행이 그대로 남는다. 도메인이 그럴 수 있다면 창 구간 DELETE 후 INSERT가 안전하고, DELETE와 INSERT를 한 트랜잭션으로 묶어 대시보드가 빈 구간을 보지 않게 한다. 전부 환불돼도 order_count는 남으므로 보통의 주문 도메인에서는 문제가 안 되지만, "왜 안 되는지"까지 말할 수 있어야 한다.

"타임아웃을 DB 세션에만 걸면 안 되나요?" 추가

DB 세션 타임아웃(max_execution_time 30초)만 있으면 30초 동안 톰캣 스레드가 묶여 있다. 그 30초짜리 요청이 100개 들어오면 톰캣 스레드 풀이 말라 운영 요청까지 죽는다. 그래서 JDBC 층(setQueryTimeout)이 앱 스레드를 풀어주고, 풀 층(maximum-pool-size: 4 + connection-timeout: 3000)이 동시 실행 수를 4로 묶어 5번째부터는 3초 만에 빨리 실패시킨다. 반대로 JDBC 층만 있으면 앱이 OOM으로 죽는 순간 KILL QUERY를 보낼 주체가 사라져 DB에서 집계가 끝까지 돈다. DB 층은 마지막 보루, JDBC 층은 앱 보호, 풀 층은 동시성 제어 — 잡는 대상이 달라 셋 다 필요하다.

"replica 대신 집계 결과를 Redis에 캐싱하면 안 되나요?" 추가

캐시는 "같은 질문의 반복"을 줄이지, 첫 계산(미스)의 비용은 그대로 운영 DB에서 발생시킨다. 셀러 10만 명이 각자 다른 키(자기 매출)를 보면 미스가 곧 집계 쿼리이고, TTL이 만료되는 순간마다 사슬 A~D가 다시 돈다. 여러 요청이 동시에 미스를 맞으면 같은 집계가 동시에 여러 번 실행되는 스탬피드까지 얹힌다. 그래서 캐시는 계산 자체를 옮기는 3단 위에 얹는 보조(§4-5 오늘 구간 5분 TTL)이지, 분리의 대체가 아니다. "조회 시점에 계산하지 않는다"는 원칙을 캐시가 충족시키려면 미리 계산해 넣어두는 쪽(사전 계산)이어야 하고, 그것이 곧 집계 테이블·카운터다.

"1단 다이어트로 충분한지는 무엇으로 판단하나요?" 추가

대시보드 응답시간이 아니라 운영 지표다 — 버퍼 풀 히트율(Innodb_buffer_pool_reads 대비 read_requests), 운영 API p99, HikariCP pending, History list length. 대시보드가 2초 만에 나와도 그 2초 동안 운영 p99가 튄다면 충분하지 않다. "분리"의 목적은 대시보드를 빠르게 하는 것이 아니라 계산대 줄을 빠지게 하는 것이기 때문이다(§1-1 비유).

"InnoDB에는 풀스캔 방어(midpoint insertion)가 있다던데, 그럼 버퍼 풀 오염은 걱정 안 해도 되나요?" 가산점

방어는 있다 — 새 페이지는 LRU 중간(old 영역, 기본 37%)에 들어가고 innodb_old_blocks_time(기본 1초) 안의 재접근은 승격시키지 않아, 한 번 훑고 지나가는 풀스캔은 young 영역의 핫 페이지를 직접 밀어내지 못한다. 그러나 세 경우에 뚫린다: ① old 영역 자체는 통째로 갈려 거기 있던 승격 전 운영 페이지가 사라진다 ② 집계가 조인·정렬·재스캔으로 같은 페이지를 1초 뒤 다시 만지면 young으로 승격돼 방어가 풀린다 ③ 위젯 6개가 같은 테이블을 6번 훑으면 ②가 사실상 보장된다. "방어가 있지만 대시보드 패턴이 정확히 그 방어를 뚫는 패턴"이라고 답한다.

81분 인출 테스트 — 면접 전날, 답을 가리고

공유 자원 5개와 각각의 사슬 한 줄.

분리 사다리 5단을 "무엇을 무엇으로"와 함께.

⓪ 실시간 요구 되묻기(하루 지연 허용?) → ① 쿼리 다이어트(전제 조건) → ② 통계 전용 replica(자원 격리, 운영 replica와 분리) → ③ 집계 테이블 + 배치(조회 시점 계산 → 배치 시점 계산) → ④ CDC → OLAP(시스템 분리). 실무 착지 ②+③. 묻고·빼고·옮기고·미리 하고·내보낸다. → 2절

협상에서 백엔드가 한 일 3가지와 SLA 표 4행.

① 비용 알려주기 ② "실시간"을 용도로 분해 ③ 항목별 SLA. 표: 어제까지 추이 하루·확정치·새벽 배치 / 오늘 매출 5분·잠정치·5분 배치 또는 소량 조회+캐시 / 월말 정산 마감 시점·확정치·마감 배치+재계산 창 / 접속자 수 초·근사치·Redis 카운터. → 2-0

세 해법의 "얻는 것 / 내주는 것 / 관리 장치" 한 호흡.

replica: primary 격리·코드 최소 / 복제 지연·여전히 무거움 / 전용 replica·lag 알람·"N분 전 기준". 집계 테이블: O(날짜 수)·완전 해방 / 실시간성·배치 실패·정정 / 멱등 UPSERT·재계산 창·성공 시각 노출. CDC→OLAP: 임의 질의·열 저장 / 이중 저장·파이프라인·스키마 진화 / 레지스트리·대사·마스킹. → 3절

멱등 배치의 원리 한 문장 + 실패 3종과 장치.

"최근 N일 창을 구간 절대값으로 다시 SUM해 같은 키에 UPSERT — 멱등성은 재시도 정책이 아니라 계산 방식에서 나온다." 실패 ① 안 돌았다 → 상태 테이블 알람 + computed_at 노출 + 재실행 · ② 두 번 돌았다 → 멱등(ShedLock은 동시 실행만) · ③ 원본 정정 → 재계산 창 / 정정 이벤트 큐 / 월 1회 대사. → 4-3

"replica로 보내면 되죠"에 한 마디로.

"격리이지 해결이 아닙니다." — 집계는 replica에서도 10분이고, 적용 스레드와 경쟁해 복제 지연을 만들며, 운영 read replica와 같이 쓰면 운영 조회까지 느려진다. 사용자·횟수가 늘면 3단.

한 줄 요약

집계 쿼리는 운영 트랜잭션과 버퍼 풀·CPU·I/O 큐·undo·커넥션·MDL을 나눠 쓰며 그 하나하나를 잠식하므로, "하루 지연 허용 가능?"을 먼저 되물어 요구를 낮춘 뒤 통계 전용 replica → 멱등한 집계 테이블·배치 → CDC·OLAP의 사다리를 필요한 높이까지만 오르되, 어느 단이든 통계 쿼리가 운영 DB로 새지 못하게 DataSource·계정·타임아웃·ArchUnit·지표로 고정한다.
