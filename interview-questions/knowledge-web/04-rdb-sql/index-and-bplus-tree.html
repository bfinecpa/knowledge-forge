인덱스와 B+Tree — 구조 3요소가 각각 어떤 능력을 사주는가

📖 약 16분 🧩 6개 섹션 0/6 섹션 이해
🎯 핵심 관전 포인트

B+Tree는 세 가지 구조적 선택으로 이루어져 있고, 각 선택이 사주는 능력이 1:1로 대응한다. ① 한 노드(=디스크 페이지)에 키를 수백 개 담는 다분기 구조 → 트리 높이가 3~4로 낮아짐 → 디스크 접근 몇 번으로 끝난다. ② 실제 데이터는 리프에만 두고 중간 노드는 길잡이 키만 갖는다 → 중간 노드가 가벼워져 한 페이지에 더 많은 키가 들어가고 트리가 더 낮아진다. ③ 리프끼리 양방향 연결 리스트 → 한 번 진입하면 옆으로 훑을 수 있어 범위 조회와 ORDER BY가 공짜로 따라온다. 여기서 흔한 오해가 +의 방향인데, 중간 노드에도 데이터를 두는 쪽이 B-Tree, 리프에만 두는 쪽이 B+Tree다. 그리고 인덱스를 "걸까 말까"는 쓰기 빈도 / 선택도 / 기존 인덱스와의 중복(선두 컬럼 규칙) / EXPLAIN 검증, 이 네 축을 한 호흡에 펼칠 수 있어야 한다.

면접 질문

"인덱스는 어떻게 동작하나요? B+Tree 구조를 설명해주세요."

관련 질문: "인덱스를 걸었는데도 풀스캔이 발생하는 경우는 어떤 경우인가요?" "클러스터드 인덱스와 논클러스터드(세컨더리) 인덱스의 차이는? (InnoDB 기준)"

출제 의도"인덱스 걸면 빨라진다"는 누구나 안다. 구조를 알아야 "왜 이 쿼리는 인덱스를 못 타는지", "인덱스 하나가 쓰기를 얼마나 느리게 하는지"를 추론할 수 있다. 인덱스 설계는 백엔드가 매주 하는 일이라 이 추론 능력이 곧 생산성이다. 즉 이 질문은 암기 확인이 아니라, 구조 → 성능 특성 → 설계 판단으로 이어지는 사슬을 스스로 이어붙일 수 있는지를 본다.
1

그림 한 장 — 3층 B+Tree

▾

말로 외우면 방향이 뒤집힌다. 이 그림 한 장으로 고정하는 게 낫다.

text
[레벨 1] 루트 노드 — 길잡이 키만, 데이터 없음
                        ┌─────────────────────┐
                        │   30    │    60     │
                        └──┬──────┴─────┬─────┴──┬──┘
             k < 30 ───────┘   30 ≤ k < 60      └─────── 60 ≤ k
                    │                │                      │
[레벨 2] 브랜치 노드 — 여기도 길잡이 키만, 데이터 없음
                    ▼                ▼                      ▼
            ┌────────────┐    ┌────────────┐        ┌────────────┐
            │  10 │  20  │    │  40 │  50  │        │  70 │  80  │
            └─┬───┴──┬───┴─┬  └─┬───┴──┬───┴─┬      └─┬───┴──┬───┴─┬
              ▼      ▼     ▼    ▼      ▼     ▼        ▼      ▼     ▼

[레벨 3] 리프 노드 — ★ 실제 데이터(또는 데이터로 가는 주소)는 여기에만 ★
  ┌───────────┐   ┌───────────┐   ┌───────────┐   ┌───────────┐
  │ 1,5,9 →행 │◄─►│10,14 →행  │◄─►│20,25 →행  │◄─►│30,33 →행  │◄─► ...
  └───────────┘   └───────────┘   └───────────┘   └───────────┘
        └────────── 양방향 연결 리스트(정렬 순서대로) ──────────┘

읽는 법: WHERE id = 25는 루트에서 "25는 30보다 작다" → 왼쪽 브랜치 → "25는 20 이상" → 해당 리프, 이렇게 레벨 수만큼만 페이지를 읽고 끝난다. WHERE id BETWEEN 25 AND 33이면 25가 있는 리프까지 내려간 뒤, 위로 다시 올라가지 않고 리프 연결 고리를 따라 오른쪽으로 계속 훑는다.

1-1. 구조 3요소 ↔ 능력 1:1 매칭

면접에서는 이 세 줄을 각각 "그래서 뭘 얻는데?"까지 붙여서 말해야 한다.

구조적 선택왜 그렇게 만들었나그 결과 얻는 능력
① 다분기(한 노드에 키 수백 개)노드 하나 = 디스크 페이지 하나. 페이지를 어차피 통째로 읽으니 꽉 채우는 게 이득트리 높이가 3~4단으로 낮아짐 → 디스크 접근 횟수 최소화
② 데이터는 리프에만중간 노드에서 데이터(행)를 빼면 노드가 가벼워짐한 페이지에 길잡이 키를 더 많이 담음 → fan-out 증가 → 트리가 더 낮아짐, 그리고 모든 조회의 비용이 균일
③ 리프 양방향 연결리프만 순회하면 전체 데이터를 정렬 순서로 다 볼 수 있게범위 조회(BETWEEN, >, <), ORDER BY, GROUP BY, 페이징이 정렬 비용 없이 처리됨

"왜 이진 트리가 아닌가"를 한 문장으로: 메모리 위 자료구조는 비교 횟수가 비용이지만, 디스크 위 자료구조는 페이지 읽기 횟수가 비용이다. 1억 건을 이진 트리에 담으면 높이가 약 27단이라 최악의 경우 27번 디스크를 때리지만, 한 노드에 키 수백 개가 들어가는 B+Tree라면 3~4단이면 끝난다. 이진 트리는 "한 번 읽어온 페이지의 4096바이트 중 키 하나만 쓰고 버리는" 낭비 구조다.

2

+의 방향 — B-Tree vs B+Tree (가장 흔한 오해)

▾

여기서 방향을 반대로 기억하는 경우가 아주 많다. "중간 노드에도 데이터를 둘 수 있게 바꾼 게 B+Tree"는 정확히 반대다.

  • B-Tree: 중간(내부) 노드에도 실제 데이터(값/레코드 포인터)를 함께 저장한다. 운이 좋으면 루트 근처에서 바로 값을 찾아 조회가 일찍 끝날 수 있다.
  • B+Tree: 중간 노드는 길잡이 키(separator key)만 갖는다. 값이 없다. 모든 조회는 반드시 리프까지 내려간다. 대신 중간 노드가 가벼워져 fan-out이 커지고, 리프끼리 연결해 범위 스캔을 얻는다.
비교 축B-TreeB+Tree
실제 데이터 위치내부 노드 + 리프 (어디든)리프에만
내부 노드의 무게무거움(데이터 포함) → fan-out 작음가벼움(키만) → fan-out 큼
조회 비용의 균일성들쭉날쭉(운 좋으면 루트에서 끝)항상 리프까지 = 균일
범위 스캔트리를 오르내리며 순회 → 비쌈리프 연결 따라 순차 스캔 → 쌈
리프 연결 리스트없음있음(대개 양방향)
💡

왜 DB는 B+Tree를 택했나 — 조회 한 건이 "운 좋게 빨리 끝나는 것"보다 모든 조회가 예측 가능하게 3~4번의 I/O로 끝나는 것이 서비스에서는 훨씬 가치 있다. 게다가 실무 쿼리의 상당수가 범위·정렬·페이징인데, 그건 리프 연결 리스트가 있어야 싸진다. 트리를 낮추는 것과 범위 스캔을 싸게 하는 것, 두 마리 토끼를 "데이터를 리프로 몰아넣기"라는 하나의 선택으로 잡은 게 +다.

(가산점 포인트) 리프 연결 리스트 덕에 유리해지는 것 / 전혀 도움 안 되는 것을 짝으로 말하면 좋다.

  • 유리: WHERE created_at BETWEEN ..., ORDER BY id LIMIT 20, WHERE name LIKE 'kim%' (선행 문자가 고정 → 시작점을 찾을 수 있다)
  • 무용: WHERE name LIKE '%kim%' — 시작점을 특정할 수 없어 트리를 내려갈 방법이 없다. 이건 인덱스의 한계이지 튜닝 문제가 아니고, 필요하면 전문 검색 인덱스(Full-Text)나 검색 엔진으로 풀어야 한다.
3

"인덱스 하나만 걸어주세요" — 걸기 전에 따지는 4축

▾

팀원이 "이 조회 느리니 컬럼 A에 인덱스 걸어주세요"라고 하면, 아래 네 축을 한 호흡에 펼치는 게 실무 답변이다. ("일단 걸자"와 "안 됩니다" 사이에 있는 게 이 체크리스트다.)

축 1. 쓰기 빈도 — 인덱스는 조회를 위해 쓰기를 파는 거래다

인덱스는 별도의 B+Tree를 하나 더 만드는 것이다. 그 컬럼이 포함된 INSERT/UPDATE/DELETE마다 인덱스 트리도 함께 갱신된다. 인덱스가 5개면 INSERT 한 번에 트리 6개(클러스터드 1 + 세컨더리 5)를 손본다.

걸지 마라 예시: 초당 수천 건이 꽂히는 이벤트 로그 테이블에, 하루 한 번 운영자가 보는 조회를 위해 인덱스를 추가하는 것. 그 조회는 배치로 돌리거나 분석용 저장소로 넘기는 게 맞다.

쓰기 부하 말고도 대가는 더 있다 — 저장 공간(인덱스도 디스크를 먹는다), 버퍼 풀 오염(쓸모없는 인덱스 페이지가 메모리 캐시를 차지해 정작 필요한 페이지를 밀어낸다), 옵티마이저 혼선(후보 인덱스가 많아지면 실행 계획이 엉뚱하게 잡힐 확률이 올라간다), 생성 시점 리스크(대형 테이블에 인덱스를 추가하는 DDL은 온라인 DDL이라도 I/O 부하와 복제 지연을 만든다).

축 2. 선택도(카디널리티) — 값 종류가 적으면 인덱스는 무의미하다

선택도 = 그 컬럼이 조건에 걸렸을 때 전체 행 중 몇 %로 좁혀지는가. 카디널리티 = 그 컬럼에 서로 다른 값이 몇 개나 있는가. 카디널리티가 낮으면 선택도도 낮다.

왜 낮은 선택도에서 인덱스가 무의미한가 — 세컨더리 인덱스로 행을 찾으면 인덱스에서 PK를 얻고 다시 실제 행을 읽으러 가는 랜덤 I/O가 행마다 발생한다. 100만 건 중 80만 건이 대상이면, 랜덤 I/O 80만 번보다 테이블을 순차로 쭉 읽는 풀스캔이 더 빠르다. 그래서 옵티마이저는 인덱스가 있어도 안 쓴다.

걸지 마라 예시: is_deleted(true/false), gender, status가 대부분 'ACTIVE'인 컬럼에 단독 인덱스. 값 종류가 2~3개면 어떤 값으로 조회해도 전체의 30~90%가 걸린다.

예외 — 값이 극단적으로 편중돼 있고, 희귀한 쪽만 조회한다면 유효하다. 전체의 0.01%뿐인 status = 'FAILED'만 골라 쓰는 알림 배치라면 인덱스가 극적으로 먹힌다. 이럴 땐 단독 인덱스보다 다른 컬럼과 묶어 복합으로 걸거나, 지원되는 DB라면 부분 인덱스(조건부 인덱스)를 쓴다.

sql
-- ❌ 낭비: 값이 3종류뿐인 컬럼에 단독 인덱스.
--    조회할 때마다 전체의 절반이 걸려서 옵티마이저가 무시한다.
CREATE INDEX idx_orders_status ON orders (status);

-- ✅ 개선: 실제 쿼리가 "특정 상태를 최근 순으로" 라면 복합으로.
--    status로 좁힌 뒤 created_at이 이미 정렬돼 있어 ORDER BY도 공짜.
CREATE INDEX idx_orders_status_created ON orders (status, created_at);

축 3. 기존 인덱스와의 중복 — 선두 컬럼(leftmost prefix) 규칙

복합 인덱스 (A, B)는 "A로 먼저 정렬하고, A가 같으면 B로 정렬"한 하나의 트리다. 그래서 이 트리는 A만으로 검색할 때도 그대로 쓸 수 있다. 전화번호부가 "성 → 이름" 순으로 정렬돼 있으면 성만으로도 찾을 수 있는 것과 같다. 반대로 이름만 알고는 못 찾는다 — 이름이 책 전체에 흩어져 있기 때문이다.

(A, B, C) 인덱스가 있을 때:

쿼리 조건인덱스 사용이유
WHERE A = ?✅ 사용선두 컬럼부터 붙었다
WHERE A = ? AND B = ?✅ 사용앞에서부터 연속
WHERE A = ? AND B = ? AND C = ?✅ 완전 활용—
WHERE B = ?❌ 못 씀선두 컬럼 A가 없다
WHERE B = ? AND C = ?❌ 못 씀마찬가지
WHERE A = ? AND C = ?△ A까지만중간의 B가 빠져 C는 필터로만 쓰임
WHERE A > ? AND B = ?△ A까지만범위 조건 뒤 컬럼은 정렬이 깨져 못 씀

여기서 나오는 실무 결론: (A, B) 인덱스가 이미 있다면 A 단독 인덱스는 대개 불필요하다. (A, B) 트리가 A 단독 검색을 이미 커버하기 때문이다. (엄밀히는 A 단독 인덱스가 폭이 좁아 페이지 수가 적다는 미세 이점은 있지만, 쓰기 비용과 공간을 한 벌 더 내는 값어치는 거의 없다.)

sql
-- ❌ 중복: 아래 두 인덱스는 사실상 겹친다.
CREATE INDEX idx_a   ON orders (user_id);              -- (A)
CREATE INDEX idx_a_b ON orders (user_id, created_at);  -- (A, B)
--   → idx_a는 idx_a_b의 왼쪽 접두사와 동일. 유지비만 두 배.

-- ✅ 정리: 접두사에 흡수되는 인덱스는 지운다.
DROP INDEX idx_a ON orders;

-- ⚠️ 단, 방향이 반대면 흡수되지 않는다.
--   (user_id, created_at)가 있어도 created_at 단독 조회는 못 탄다.
--   그 쿼리가 진짜 필요하면 별도 인덱스가 맞다.
CREATE INDEX idx_created ON orders (created_at);

새 인덱스 요청을 받으면 먼저 SHOW INDEX FROM orders;(또는 information_schema.STATISTICS)로 기존 인덱스 목록을 보고, 요청 컬럼이 어떤 인덱스의 선두에 이미 들어있는지 확인한다. 이 습관 하나로 테이블당 인덱스 개수가 눈에 띄게 줄어든다.

축 4. EXPLAIN으로 "실제로 타는지" 검증 — 걸었다고 쓰는 게 아니다

인덱스를 만들었다고 옵티마이저가 쓴다는 보장은 없다. 추가 전/후로 실행 계획을 떠서 type, key, rows, Extra 네 칸을 비교한다.

✕ BEFORE인덱스 없음
EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY created_at DESC LIMIT 20;
-- type: ALL          (풀 테이블 스캔)
-- key : NULL         (아무 인덱스도 안 씀)
-- rows: 1,000,000    (다 읽겠다는 뜻)
-- Extra: Using where; Using filesort   ← 정렬을 따로 하고 있다

CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);
✓ AFTER
EXPLAIN SELECT * FROM orders WHERE user_id = 100 ORDER BY created_at DESC LIMIT 20;
-- type: ref                          (인덱스로 좁혀 접근)
-- key : idx_orders_user_created      ← 의도한 인덱스를 탄다
-- rows: 42                           (읽을 행이 줄었다)
-- Extra: Using where                 ← filesort 사라짐: 인덱스 순서가 곧 정렬 순서

Extra에서 Using filesort가 사라진 것이 ③번 구조(리프가 정렬 순서로 연결돼 있음)의 직접적인 효과다. 그리고 인덱스를 걸었는데도 key: NULL이 나오는 흔한 원인은 다음과 같다 — 이 목록이 머리에 있으면 슬로 쿼리를 5분 만에 고친다.

  • 인덱스 컬럼에 함수·연산 적용: WHERE DATE(created_at) = '2026-01-01' → WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'로 바꾼다
  • 타입 불일치로 인한 암묵적 형변환: VARCHAR 컬럼에 숫자 리터럴 비교
  • 선행 와일드카드: LIKE '%kw%'
  • 낮은 선택도: 축 2 — 옵티마이저가 풀스캔이 낫다고 판단
  • 선두 컬럼 누락: 축 3
  • OR로 묶인 조건에서 한쪽 컬럼에 인덱스가 없는 경우
4

리프에는 정확히 무엇이 들어있나 (InnoDB 기준)

▾

"데이터는 리프에만 있다"고 할 때 그 데이터가 정확히 뭐냐는 인덱스 종류에 따라 다르고, 이게 다음 문항(클러스터드 vs 세컨더리)의 입구다.

  • 클러스터드 인덱스(= PK 인덱스): 리프에 행 전체(모든 컬럼) 가 들어있다. 즉 InnoDB에서 테이블 데이터 자체가 PK 순서로 정렬된 B+Tree다.
  • 세컨더리 인덱스(그 외 모든 인덱스): 리프에 인덱스 컬럼 값 + PK 값만 들어있다. 나머지 컬럼이 필요하면 그 PK로 클러스터드 인덱스를 한 번 더 타야 하는데, 이걸 북마크 룩업(back to table) 이라고 부른다.

(가산점 포인트) 이 구조에서 두 가지가 따라 나온다. ⑴ 세컨더리 인덱스가 PK를 품고 있으므로 PK가 크면 모든 세컨더리 인덱스가 함께 비대해진다 (랜덤 UUID를 PK로 쓰면 안 되는 이유 중 하나). ⑵ 쿼리가 필요로 하는 컬럼이 전부 인덱스 안에 있으면 북마크 룩업 없이 인덱스만 읽고 끝나는데, 이게 커버링 인덱스다.

5

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

디스크는 바이트 단위가 아니라 페이지(InnoDB 기본 16KB) 단위로 읽는다. 어차피 16KB를 통째로 읽어올 거면 그 안에 키를 최대한 많이 담는 게 이득이다. 한 노드에 키가 많다 = 자식이 많다(fan-out이 크다) = 같은 데이터 건수를 더 낮은 높이로 담을 수 있다 = 루트에서 리프까지 읽는 페이지 수, 즉 디스크 접근 횟수가 준다. 게다가 상위 레벨(루트·브랜치)은 개수가 적어 버퍼 풀에 상주하기 쉬우므로, 실제 물리 I/O는 리프 한두 번으로 줄어드는 경우가 많다.

해시 인덱스는 등호 비교(=)만 가능하다. 해시 함수는 순서를 파괴하므로 >, BETWEEN, ORDER BY, LIKE 'kim%', 그리고 복합 인덱스의 선두 컬럼 부분 활용이 전부 불가능하다. 실무 쿼리에서 범위·정렬이 차지하는 비중을 생각하면 "모든 걸 웬만큼 잘하는" B+Tree가 기본이 되는 게 자연스럽다. 해시는 캐시성 정확 일치 조회처럼 용도가 확실할 때 보조로 쓴다.

선두 컬럼 규칙 때문에 그 쿼리는 기존 인덱스를 못 탄다. 선택지는 셋이다. ⑴ 쿼리를 고친다 — 대부분의 화면 조회는 사실 특정 사용자 범위 안의 조회라서 user_id 조건을 붙일 수 있는 경우가 많다. 이게 가능하면 이게 최선. ⑵ (created_at) 또는 (created_at, user_id) 인덱스를 새로 만든다 — 전역 최근순 조회가 실제 요구사항이라면 이쪽이 맞다. 인덱스 하나 값을 지불하는 것. ⑶ 컬럼 순서를 바꾼 인덱스로 교체한다 — 단, 기존 인덱스를 쓰던 쿼리들이 무엇인지 먼저 확인해야 한다. 순서 변경은 다른 쿼리를 조용히 망가뜨릴 수 있다.

개수 자체보다 "각 인덱스가 어떤 쿼리를 위해 존재하는지 설명할 수 있는가" 가 기준이다. 설명 못 하는 인덱스는 지운다. 위험은 네 갈래다 — 쓰기 증폭(모든 DML이 인덱스 수만큼 트리를 갱신), 공간과 버퍼 풀 잠식, 옵티마이저의 선택 실패 확률 증가, 그리고 가장 무서운 것은 "이미 있는 인덱스를 몰라서 비슷한 걸 또 만드는" 누적이다. 실무에서는 정기적으로 사용되지 않는 인덱스(MySQL은 sys.schema_unused_indexes, PostgreSQL은 pg_stat_user_indexes.idx_scan = 0)를 뽑아 정리하는 절차를 두는 게 낫다. 그리고 인덱스 추가·삭제는 되돌리기 쉬운 결정처럼 보이지만, 대형 테이블에서는 DDL 자체가 부하이자 복제 지연 요인이라 배포 시점까지 함께 설계해야 한다.

있다. ⑴ 낮은 선택도 인덱스를 옵티마이저가 잘못 골라 랜덤 I/O를 대량으로 발생시키던 케이스, ⑵ 쓰기가 지배적인 테이블에서 거의 안 쓰이는 인덱스를 제거해 INSERT 처리량이 오르는 케이스, ⑶ 중복 인덱스를 정리해 버퍼 풀 적중률이 올라가는 케이스. "성능 개선 = 인덱스 추가"라는 반사신경 대신, 측정 → 가설 → 검증(EXPLAIN + 실제 응답 시간) 사이클로 접근한다는 태도를 보여주는 게 이 질문의 핵심이다.

✅ 한 줄 요약

B+Tree는 "다분기로 트리를 낮추고, 데이터를 리프로 몰아 더 낮추고, 그 리프들을 이어 붙여 범위 스캔까지 얻은" 구조이며(+는 데이터를 리프로 몰았다는 뜻이지 그 반대가 아니다), 인덱스를 걸지 말지는 쓰기 빈도 · 선택도 · 기존 인덱스와의 중복(선두 컬럼 규칙) · EXPLAIN 검증 네 축으로 판단한다.
