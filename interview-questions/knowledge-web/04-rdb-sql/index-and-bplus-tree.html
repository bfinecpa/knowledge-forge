인덱스와 B+Tree — 구조 3요소가 각각 어떤 능력을 사주는가

질문: "인덱스는 어떻게 동작하나요? B+Tree 구조를 설명해주세요."

핵심 관전 포인트 — 면접 첫 답변으로 그대로 말한다

B+Tree는 세 가지 구조적 선택으로 이루어져 있고, 각 선택이 사주는 능력이 1:1로 대응한다.
  1. 다분기 — 한 노드(=디스크 페이지 하나)에 키를 수백 개 담는다 → 트리 높이가 3~4로 낮아짐 → 디스크 접근 몇 번으로 끝난다.
  2. 데이터는 리프에만 — 중간 노드는 길잡이 키만 갖는다 → 중간 노드가 가벼워져 한 페이지에 키가 더 들어가고 → 트리가 더 낮아진다.
  3. 리프끼리 양방향 연결 리스트 — 한 번 진입하면 옆으로 훑을 수 있다 → 범위 조회와 ORDER BY가 공짜로 따라온다.
흔한 오해는 +의 방향이다. 중간 노드에도 데이터를 두는 쪽이 B-Tree, 리프에만 두는 쪽이 B+Tree다. 그리고 인덱스를 "걸까 말까"는 쓰기 빈도 / 선택도 / 기존 인덱스와의 중복(선두 컬럼 규칙) / EXPLAIN 검증 네 축을 한 호흡에 펼칠 수 있어야 한다.

1그림 한 장 — 3층 B+Tree

말로 외우면 방향이 뒤집힌다. 이 그림 한 장으로 고정한다. 파란 경로가 WHERE id = 25, 초록 화살표가 WHERE id BETWEEN 25 AND 33이다.

1-1. 구조 3요소 ↔ 능력 1:1 매칭

면접에서는 이 세 줄을 각각 "그래서 뭘 얻는데?"까지 붙여서 말해야 한다.

구조적 선택왜 그렇게 만들었나그 결과 얻는 능력
① 다분기
한 노드에 키 수백 개		노드 하나 = 디스크 페이지 하나. 페이지를 어차피 통째로 읽으니 꽉 채우는 게 이득높이 3~4단 → 디스크 접근 횟수 최소화
② 데이터는 리프에만중간 노드에서 데이터(행)를 빼면 노드가 가벼워짐한 페이지에 길잡이 키를 더 담음 → fan-out ↑ → 트리 더 낮아짐, 모든 조회 비용 균일
③ 리프 양방향 연결리프만 순회하면 전체 데이터를 정렬 순서로 다 볼 수 있게범위 조회(BETWEEN, >, <), ORDER BY, GROUP BY, 페이징이 정렬 비용 없이

3요소를 한 문장으로 — "낮추고 · 더 낮추고 · 이어 붙여"

1다분기로 낮추고 2데이터를 리프로 몰아 더 낮추고 3리프를 이어 붙여 범위 스캔까지

①②는 "페이지 읽기 횟수"를 줄이는 선택, ③은 "정렬·범위를 공짜로 만드는" 선택. 각 chip 뒤에 능력 한 마디를 붙이면 그대로 답변이 된다.

"왜 이진 트리가 아닌가" — 숫자 세 개

  • 메모리 위 자료구조는 비교 횟수가 비용, 디스크 위 자료구조는 페이지 읽기 횟수가 비용
  • 1억 건: 이진 트리 높이 약 27단(최악 27번 디스크 접근) vs 노드당 키 수백 개인 B+Tree 3~4단
  • 이진 트리는 읽어온 페이지(수 KB) 중 키 하나만 쓰고 버리는 낭비 구조. B+Tree는 페이지를 꽉 채운다

2+의 방향 — B-Tree vs B+Tree 정반대로 답한 지점

여기서 방향을 반대로 기억하는 경우가 아주 많다. "중간 노드에도 데이터를 둘 수 있게 바꾼 게 B+Tree"는 정확히 반대다. 아래 두 그림에서 ● (실제 데이터)가 어느 층에 있는지만 보면 된다.

❌ 오답 (실제 면접 답변)"리프에만 있던 데이터를 중간 노드에도 둘 수 있게 바꾼 것이 B+Tree고, 그래서 트리가 작아진다."

결론(트리가 낮아짐)만 맞고 원인이 뒤집혔다. 데이터를 중간 노드에 넣으면 노드가 무거워져 fan-out이 오히려 줄어든다.

✅ 정답"중간 노드에도 있던 데이터를 리프로만 몰아넣은 것이 B+Tree다. 중간 노드가 가벼워져 fan-out이 커지고 트리가 낮아지며, 리프끼리 연결해 범위 스캔을 얻는다."

"어디에 데이터가 있나?"를 물으면 리프에만. 이 한 마디가 나오면 방향은 틀릴 수 없다.

+의 방향을 고정하는 연상 두 가지

+ = "리프 쪽에 더해진 것" — 데이터도 리프로, 연결선도 리프에
  • "플러스 = 한 층 더 내려간다." B+Tree는 어떤 조회든 리프까지 한 층 더(+) 가야 한다. 도중에 멈출 수 있으면 그냥 B-Tree.
  • "플러스 = 리프 사이에 그은 연결선(─)." 리프끼리 잇는 그 선이 B에 붙은 +다. 연결선이 리프에 있으니 데이터도 리프에 있다고 같이 기억한다.
비교 축B-TreeB+Tree
실제 데이터 위치내부 노드 + 리프 (어디든)리프에만
내부 노드의 무게무거움(데이터 포함) → fan-out 작음가벼움(키만) → fan-out 큼
조회 비용의 균일성들쭉날쭉(운 좋으면 루트에서 끝)항상 리프까지 = 균일
범위 스캔트리를 오르내리며 순회 → 비쌈리프 연결 따라 순차 스캔 → 쌈
리프 연결 리스트없음있음(대개 양방향)

왜 DB는 B+Tree를 택했나 — 조회 한 건이 "운 좋게 빨리 끝나는 것"보다 모든 조회가 예측 가능하게 3~4번의 I/O로 끝나는 것이 서비스에서는 훨씬 가치 있다. 게다가 실무 쿼리의 상당수가 범위·정렬·페이징인데, 그건 리프 연결 리스트가 있어야 싸진다. 트리를 낮추는 것과 범위 스캔을 싸게 하는 것, 두 마리 토끼를 "데이터를 리프로 몰아넣기"라는 하나의 선택으로 잡은 게 +다.

리프 연결 리스트가 먹히는 쿼리 / 안 먹히는 쿼리 가산점

유리 — 시작점을 찾을 수 있다
  • WHERE created_at BETWEEN … AND …
  • ORDER BY id LIMIT 20
  • WHERE name LIKE 'kim%' — 선행 문자가 고정
무용 — 시작점을 특정할 수 없다
  • WHERE name LIKE '%kim%' — 트리를 내려갈 방법이 없다

이건 인덱스의 한계이지 튜닝 문제가 아니다. 필요하면 전문 검색 인덱스(Full-Text)나 검색 엔진으로 푼다.

3랜덤 I/O vs 순차 I/O — 인덱스 판단의 밑바닥 비용 모델 통째로 비어 있던 지점

"인덱스가 있는데 왜 안 타지?", "선택도가 낮으면 왜 무의미하지?", "커버링 인덱스가 왜 빠르지?", "깊은 페이지네이션이 왜 느리지?" — 이 질문들의 답은 전부 하나의 비용 모델에서 나온다. 세컨더리 인덱스로 행을 찾는 일은 행마다 랜덤 I/O 한 번이고, 테이블을 처음부터 읽는 일은 순차 I/O라는 것.

비용 모델 한 줄 + 거기서 파생되는 사슬

세컨더리 인덱스 조회 = 행마다 랜덤 I/O 1회. 대상이 넓으면 순차 풀스캔이 이긴다.
선택도 낮음→대상 행 넓음→랜덤 I/O 폭증→풀스캔이 더 쌈→옵티마이저가 인덱스를 버림
  • 같은 모델의 다른 얼굴들: 커버링 인덱스가 빠른 이유(북마크 룩업의 랜덤 I/O 자체를 없앰) · PK가 크면 안 되는 이유(페이지당 엔트리 ↓ → 버퍼 풀 적재율 ↓ → 디스크 I/O ↑) · UUID v4 PK가 INSERT를 느리게 하는 이유(아무 페이지나 열어 쓰는 랜덤 쓰기 + 페이지 분할) · 커밋이 로그 파일 끝에 순차로 append만 하는 이유
  • 말할 때 금지어: "메모리 부하", "왔다갔다해서 느림". 대신 "페이지 단위 랜덤 I/O가 대상 행 수만큼", "버퍼 풀 적재율", "페이지 분할"처럼 이름으로 말한다.

4"인덱스 하나만 걸어주세요" — 걸기 전에 따지는 4축

팀원이 "이 조회 느리니 컬럼 A에 인덱스 걸어주세요"라고 하면, 아래 네 축을 한 호흡에 펼치는 게 실무 답변이다. "일단 걸자"와 "안 됩니다" 사이에 있는 게 이 체크리스트다.

4축을 네 개의 질문으로 — "자주 바뀌나? 잘 좁혀지나? 이미 있나? 진짜 타나?"

1쓰기 빈도 — 자주 바뀌나? 2선택도 — 잘 좁혀지나? 3중복(선두 컬럼) — 이미 있나? 4EXPLAIN — 진짜 타나?

머리글자 "쓰·선·중·검"(쓰기·선택도·중복·검증). 면접에서 ①④는 스스로 나왔고 ②③이 빠졌다 — 빨간 두 개를 먼저 말하는 연습을 한다.

축 1쓰기 빈도 — 인덱스는 조회를 위해 쓰기를 파는 거래다

인덱스는 별도의 B+Tree를 하나 더 만드는 것이다. 그 컬럼이 포함된 INSERT/UPDATE/DELETE마다 인덱스 트리도 함께 갱신된다. 인덱스가 5개면 INSERT 한 번에 트리 6개(클러스터드 1 + 세컨더리 5)를 손본다.

걸지 마라 예시 — 초당 수천 건이 꽂히는 이벤트 로그 테이블에, 하루 한 번 운영자가 보는 조회를 위해 인덱스를 추가하는 것. 그 조회는 배치로 돌리거나 분석용 저장소로 넘긴다.

인덱스 하나의 대가 5종 — "쓰기" 하나로 답하면 반쪽이다

  1. 쓰기 증폭 — 모든 DML이 인덱스 수만큼 트리를 갱신
  2. 저장 공간 — 인덱스도 디스크를 먹는다
  3. 버퍼 풀 오염 — 쓸모없는 인덱스 페이지가 캐시를 차지해 필요한 페이지를 밀어낸다
  4. 옵티마이저 혼선 — 후보가 많아지면 실행 계획이 엉뚱하게 잡힐 확률 ↑
  5. 생성 시점 리스크 — 대형 테이블의 인덱스 DDL은 온라인 DDL이라도 I/O 부하와 복제 지연을 만든다

축 2선택도(카디널리티) — 값 종류가 적으면 인덱스는 무의미하다 2회 연속 누락

두 용어를 분리해서 외운다

  • 카디널리티 = 그 컬럼에 서로 다른 값이 몇 개인가 — 컬럼의 성질. gender 2개, status 3개, user_id 100만 개
  • 선택도 = 그 컬럼이 조건에 걸렸을 때 전체 행 중 몇 %로 좁혀지는가 — 조건의 성질. 잘 좁혀질수록 선택도가 높다
  • 카디널리티가 낮으면 선택도도 낮다(안 좁혀진다). 값 종류 2~3개 → 어떤 값으로 조회해도 전체의 30~90%가 걸린다.

왜 낮은 선택도에서 인덱스가 무의미한가 — 3절의 비용 모델 그대로다. 세컨더리 인덱스로 행을 찾으면 인덱스에서 PK를 얻고 다시 실제 행을 읽으러 가는 랜덤 I/O가 행마다 발생한다. 100만 건 중 80만 건이 대상이면, 랜덤 I/O 80만 번보다 테이블을 순차로 쭉 읽는 풀스캔이 더 빠르다. 그래서 옵티마이저는 인덱스가 있어도 안 쓴다.

걸지 마라 예시 — is_deleted(true/false), gender, 대부분 'ACTIVE'인 status에 단독 인덱스.
예외 — 값이 극단적으로 편중돼 있고 희귀한 쪽만 조회한다면 유효하다. 전체의 0.01%뿐인 status = 'FAILED'만 골라 쓰는 알림 배치라면 인덱스가 극적으로 먹힌다. 이럴 땐 단독보다 다른 컬럼과 묶어 복합으로 걸거나, 지원되는 DB라면 부분 인덱스(조건부 인덱스)를 쓴다.
-- ❌ 낭비: 값이 3종류뿐인 컬럼에 단독 인덱스CREATE INDEX idx_orders_status ON orders (status);--    어떤 값으로 조회해도 전체의 절반쯤 걸린다 → 옵티마이저가 무시한다
-- ✅ 개선: 실제 쿼리가 "특정 상태를 최근 순으로"라면 복합으로CREATE INDEX idx_orders_status_created ON orders (status, created_at);--    status로 좁힌 뒤 created_at이 이미 정렬돼 있어 ORDER BY도 공짜

축 3기존 인덱스와의 중복 — 선두 컬럼(leftmost prefix) 규칙 부분 도달

복합 인덱스 (A, B)는 "A로 먼저 정렬하고, A가 같으면 B로 정렬"한 하나의 트리다. 그래서 이 트리는 A만으로 검색할 때도 그대로 쓸 수 있다. 전화번호부가 "성 → 이름" 순으로 정렬돼 있으면 성만으로도 찾을 수 있는 것과 같다. 반대로 이름만 알고는 못 찾는다 — 이름이 책 전체에 흩어져 있기 때문이다.

(A, B, C) 인덱스가 있을 때:

쿼리 조건인덱스 사용이유
WHERE A = ?✅ 사용선두 컬럼부터 붙었다
WHERE A = ? AND B = ?✅ 사용앞에서부터 연속
WHERE A = ? AND B = ? AND C = ?✅ 완전 활용—
WHERE B = ?❌ 못 씀선두 컬럼 A가 없다
WHERE B = ? AND C = ?❌ 못 씀마찬가지
WHERE A = ? AND C = ?△ A까지만중간의 B가 빠져 C는 필터로만 쓰임
WHERE A > ? AND B = ?△ A까지만범위 조건 뒤 컬럼은 정렬이 깨져 못 씀

선두 컬럼 규칙 두 마디

"왼쪽부터 끊기지 않게. 범위를 만나면 거기서 끝."

그리고 실무 결론: (A, B) 인덱스가 이미 있다면 A 단독 인덱스는 대개 불필요하다. (A, B) 트리가 A 단독 검색을 이미 커버한다. (엄밀히는 A 단독이 폭이 좁아 페이지 수가 적다는 미세 이점은 있지만, 쓰기 비용과 공간을 한 벌 더 낼 값어치는 거의 없다.)

-- ❌ 중복: 아래 두 인덱스는 사실상 겹친다CREATE INDEX idx_a   ON orders (user_id);              -- (A)CREATE INDEX idx_a_b ON orders (user_id, created_at);  -- (A, B)--    idx_a는 idx_a_b의 왼쪽 접두사와 동일. 유지비만 두 배
-- ✅ 정리: 접두사에 흡수되는 인덱스는 지운다DROP INDEX idx_a ON orders;
-- ⚠️ 단, 방향이 반대면 흡수되지 않는다--    (user_id, created_at)가 있어도 created_at 단독 조회는 못 탄다CREATE INDEX idx_created ON orders (created_at);       -- 그 쿼리가 진짜 필요할 때만

새 인덱스 요청을 받으면 먼저 SHOW INDEX FROM orders;(또는 information_schema.STATISTICS)로 기존 인덱스 목록을 보고, 요청 컬럼이 어떤 인덱스의 선두에 이미 들어있는지 확인한다. 이 습관 하나로 테이블당 인덱스 개수가 눈에 띄게 줄어든다.

축 4EXPLAIN으로 "실제로 타는지" 검증 — 걸었다고 쓰는 게 아니다

인덱스를 만들었다고 옵티마이저가 쓴다는 보장은 없다. 추가 전/후로 실행 계획을 떠서 type, key, rows, Extra 네 칸을 비교한다. 자세한 before/after는 5절.

5EXPLAIN before / after — 그리고 key: NULL의 원인 6종

같은 쿼리 SELECT * FROM orders WHERE user_id = 100 ORDER BY created_at DESC LIMIT 20;를 인덱스 전/후로 비교한다. 빨간 줄이 문제, 초록 줄이 달라진 곳이다.

before — 인덱스 없음 
EXPLAIN SELECT * FROM orders
  WHERE user_id = 100
  ORDER BY created_at DESC LIMIT 20;

type : ALL         ← 풀 테이블 스캔key  : NULL        ← 아무 인덱스도 안 씀rows : 1,000,000   ← 다 읽겠다는 뜻Extra: Using where;       Using filesort  ← 정렬을 따로
after — (user_id, created_at) 
CREATE INDEX idx_orders_user_created
  ON orders (user_id, created_at);
EXPLAIN … (같은 쿼리)

type : ref         ← 인덱스로 좁혀 접근key  : idx_orders_user_createdrows : 42          ← 읽을 행이 줄었다Extra: Using where ← filesort 사라짐
인덱스 순서가 곧 정렬 순서 = 구조 ③의 효과

인덱스를 걸었는데 key: NULL — 원인 6종 (슬로 쿼리를 5분 만에 고치는 목록)

외우지 말고 "인덱스는 원본 값의 정렬"이라는 한 문장에서 각 항목이 왜 깨지는지 도출한다.

  1. 인덱스 컬럼에 함수·연산 — WHERE DATE(created_at) = '2026-01-01' → 원본 값이 아니다
    → WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02'로 바꾼다
  2. 타입 불일치(암묵적 형변환) — VARCHAR 컬럼에 숫자 리터럴 비교 → 컬럼 쪽이 변환되어 1번과 같아진다
  3. 선행 와일드카드 — LIKE '%kw%' → 정렬의 시작점이 없다
  4. 낮은 선택도 — 3절 비용 모델. 옵티마이저가 풀스캔이 낫다고 계산
  5. 선두 컬럼 누락 — 축 3. 정렬의 시작점이 없다
  6. OR로 묶인 조건에서 한쪽 컬럼에 인덱스가 없는 경우 (부정 조건 !=, NOT IN도 전 구간이 대상이라 못 타기 쉽다)

변별점: 1·2·3·5·6은 "구조상 못 타는" 경우, 4는 "탈 수 있는데 안 타는" 경우. 이 두 부류를 구분해 말하는 것 자체가 점수다.

6리프에는 정확히 무엇이 들어있나 (InnoDB)

"데이터는 리프에만 있다"고 할 때 그 데이터가 정확히 뭐냐는 인덱스 종류에 따라 다르고, 이게 다음 문항(클러스터드 vs 세컨더리)의 입구다.

  • 클러스터드 인덱스(= PK 인덱스): 리프에 행 전체(모든 컬럼)가 들어있다. InnoDB에서 테이블 데이터 자체가 PK 순서로 정렬된 B+Tree다.
  • 세컨더리 인덱스(그 외 모든 인덱스): 리프에 인덱스 컬럼 값 + PK 값만 들어있다. 나머지 컬럼이 필요하면 그 PK로 클러스터드 인덱스를 한 번 더 타야 하는데, 이걸 북마크 룩업(back to table)이라고 부른다.

이 구조에서 따라 나오는 두 가지 가산점

  1. 세컨더리 인덱스가 PK를 품고 있으므로 PK가 크면 모든 세컨더리 인덱스가 함께 비대해진다 — 랜덤 UUID를 PK로 쓰면 안 되는 이유 중 하나.
  2. 쿼리가 필요로 하는 컬럼이 전부 인덱스 안에 있으면 북마크 룩업 없이 인덱스만 읽고 끝난다 — 이게 커버링 인덱스.

7꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 회색 배지는 md에 없어서 추가한 질문이다.

한 노드에 자식이 여러 개 달리는 구조가 이진 트리에 비해 뭘 벌어주나요?

디스크는 바이트 단위가 아니라 페이지(InnoDB 기본 16KB) 단위로 읽는다. 어차피 16KB를 통째로 읽어올 거면 그 안에 키를 최대한 많이 담는 게 이득이다. 한 노드에 키가 많다 = 자식이 많다(fan-out이 크다) = 같은 데이터 건수를 더 낮은 높이로 담을 수 있다 = 루트에서 리프까지 읽는 페이지 수, 즉 디스크 접근 횟수가 준다.

게다가 상위 레벨(루트·브랜치)은 개수가 적어 버퍼 풀에 상주하기 쉬우므로, 실제 물리 I/O는 리프 한두 번으로 줄어드는 경우가 많다.

해시 인덱스가 O(1)인데 왜 B+Tree를 기본으로 쓰나요?

해시 인덱스는 등호 비교(=)만 가능하다. 해시 함수는 순서를 파괴하므로 >, BETWEEN, ORDER BY, LIKE 'kim%', 그리고 복합 인덱스의 선두 컬럼 부분 활용이 전부 불가능하다. 실무 쿼리에서 범위·정렬이 차지하는 비중을 생각하면 "모든 걸 웬만큼 잘하는" B+Tree가 기본이 되는 게 자연스럽다. 해시는 캐시성 정확 일치 조회처럼 용도가 확실할 때 보조로 쓴다.

(user_id, created_at) 인덱스가 있는데 created_at만으로 조회하는 쿼리가 느립니다. 어떻게 하죠?

선두 컬럼 규칙 때문에 그 쿼리는 기존 인덱스를 못 탄다. 선택지는 셋이다.

  1. 쿼리를 고친다 — 대부분의 화면 조회는 사실 특정 사용자 범위 안의 조회라서 user_id 조건을 붙일 수 있는 경우가 많다. 가능하면 이게 최선.
  2. (created_at) 또는 (created_at, user_id) 인덱스를 새로 만든다 — 전역 최근순 조회가 실제 요구사항이라면 이쪽이 맞다. 인덱스 하나 값을 지불하는 것.
  3. 컬럼 순서를 바꾼 인덱스로 교체한다 — 단, 기존 인덱스를 쓰던 쿼리들이 무엇인지 먼저 확인해야 한다. 순서 변경은 다른 쿼리를 조용히 망가뜨릴 수 있다.
인덱스가 많으면 왜 위험한가요? 테이블당 몇 개까지가 적당한가요? 시니어 변별

개수 자체보다 "각 인덱스가 어떤 쿼리를 위해 존재하는지 설명할 수 있는가"가 기준이다. 설명 못 하는 인덱스는 지운다. 위험은 네 갈래 — 쓰기 증폭(모든 DML이 인덱스 수만큼 트리를 갱신), 공간과 버퍼 풀 잠식, 옵티마이저의 선택 실패 확률 증가, 그리고 가장 무서운 것은 "이미 있는 인덱스를 몰라서 비슷한 걸 또 만드는" 누적이다.

실무에서는 정기적으로 사용되지 않는 인덱스(MySQL은 sys.schema_unused_indexes, PostgreSQL은 pg_stat_user_indexes.idx_scan = 0)를 뽑아 정리하는 절차를 두는 게 낫다. 그리고 인덱스 추가·삭제는 되돌리기 쉬운 결정처럼 보이지만, 대형 테이블에서는 DDL 자체가 부하이자 복제 지연 요인이라 배포 시점까지 함께 설계해야 한다.

인덱스를 지우면 성능이 좋아지는 경우도 있나요? 가산점

있다. ⑴ 낮은 선택도 인덱스를 옵티마이저가 잘못 골라 랜덤 I/O를 대량으로 발생시키던 케이스, ⑵ 쓰기가 지배적인 테이블에서 거의 안 쓰이는 인덱스를 제거해 INSERT 처리량이 오르는 케이스, ⑶ 중복 인덱스를 정리해 버퍼 풀 적중률이 올라가는 케이스.

"성능 개선 = 인덱스 추가"라는 반사신경 대신, 측정 → 가설 → 검증(EXPLAIN + 실제 응답 시간) 사이클로 접근한다는 태도를 보여주는 게 이 질문의 핵심이다.

선택도와 카디널리티는 같은 말인가요? 추가 약점 겨냥

다르다. 카디널리티는 컬럼에 서로 다른 값이 몇 개 있느냐는 컬럼의 성질이고, 선택도는 어떤 조건이 전체 행을 몇 %로 좁히느냐는 조건의 성질이다. 카디널리티가 낮으면 어떤 값으로 걸어도 넓게 걸리므로 선택도도 낮아진다. 다만 카디널리티가 낮아도 값이 극단적으로 편중돼 있으면 희귀한 값에 대한 조건은 선택도가 높을 수 있다(0.01%뿐인 FAILED). 그래서 판단은 "이 컬럼에 값이 몇 종류냐"가 아니라 "실제 쿼리가 거는 값이 전체의 몇 %를 남기느냐"로 한다.

(A, B) 인덱스에서 WHERE A > 10 AND B = 5는 왜 B를 못 쓰나요? 추가

B는 "A가 같은 구간 안에서만" 정렬돼 있다. A > 10은 A 값이 여러 개인 넓은 구간이라, 그 안에서 B=5는 A 값마다 한 번씩 흩어져 나타난다 → B로 좁힐 시작점이 없다. 그래서 A 범위로 시작점만 잡고 B는 읽으면서 거르는 필터로만 쓰인다.

설계 팁: 등호로 거는 컬럼을 앞에, 범위로 거는 컬럼을 뒤에 둔다. 이 쿼리라면 (B, A)가 낫다 — B=5로 좁힌 구간 안에서 A가 정렬돼 있으니 A>10은 옆으로 훑기만 하면 된다.

옵티마이저는 선택도를 어떻게 알죠? 틀릴 수도 있나요? 추가

테이블·인덱스 통계(추정 카디널리티 등)를 보고 계산한다. 통계는 페이지 일부를 표본으로 추정하므로 정확하지 않고, 데이터가 크게 바뀐 뒤 갱신이 안 됐으면 낡아서 엉뚱한 계획이 나온다 — 그래서 ANALYZE TABLE로 통계를 갱신하는 것이 튜닝의 기본 동작 중 하나다. 또 값이 극단적으로 편중된 컬럼은 "평균 선택도" 기준 통계로는 희귀 값의 이점을 못 잡을 수 있어, DB에 따라 히스토그램 통계나 옵티마이저 힌트로 보정한다. 핵심은 옵티마이저의 판단은 추정이고, 그 추정의 입력이 통계라는 것.

SSD면 랜덤 I/O 문제가 사라지지 않나요? 추가

격차는 크게 줄지만 0이 되지 않는다. ⑴ 랜덤 접근은 요청 횟수 자체가 대상 행 수만큼 늘어난다(IOPS 소모). ⑵ 행 하나 때문에 16KB 페이지를 통째로 읽는 낭비는 매체와 무관하다. ⑶ 순차 읽기는 미리 읽기(read-ahead)와 버퍼 풀 적중의 이득을 받지만 랜덤 읽기는 못 받는다. ⑷ 옵티마이저의 비용 모델도 랜덤 페이지 접근을 순차보다 비싸게 친다. 그래서 SSD에서도 "대상이 넓으면 풀스캔"이라는 결론은 유지된다 — 손익분기점이 다소 이동할 뿐이다.

보지 않고 말한 뒤 펼친다. 막히는 카드가 오늘 다시 볼 절이다.

B+Tree 구조 3요소와 각각이 사주는 능력은?

① 다분기 → 트리 낮음 → 디스크 접근 최소. ② 데이터는 리프에만 → 중간 노드 가벼움 → fan-out ↑ → 더 낮음 + 비용 균일. ③ 리프 양방향 연결 → 범위·정렬·페이징 공짜. "낮추고 · 더 낮추고 · 이어 붙여". → 1절

+의 방향을 한 문장으로?

중간 노드에도 데이터를 두는 쪽이 B-Tree, 리프에만 두는 쪽이 B+Tree. +는 "리프 쪽에 더해진 것"(데이터도, 연결선도). → 2절

세컨더리 인덱스 조회는 왜 "행마다 랜덤 I/O"인가? 언제 풀스캔이 이기나?

세컨더리 리프에는 (인덱스 값, PK)만 있어 나머지 컬럼은 PK로 클러스터드를 다시 타야 하고(북마크 룩업), 그 행들은 디스크 위 흩어진 페이지에 있으므로 행마다 페이지 하나를 랜덤으로 읽는다. 대상이 넓어지면(경험칙 대략 20~30% 이상) 페이지 수로 고정된 순차 풀스캔이 이기고, 옵티마이저는 인덱스를 버린다. → 3절

인덱스 걸기 전 4축은? 그 중 내가 늘 빠뜨리는 둘은?

쓰기 빈도 / 선택도 / 기존 인덱스와의 중복(선두 컬럼 규칙) / EXPLAIN 검증 — "자주 바뀌나? 잘 좁혀지나? 이미 있나? 진짜 타나?" 빠뜨리는 둘은 선택도와 중복. → 4절

(A, B, C) 인덱스에서 WHERE B = ?는? WHERE A > ? AND B = ?는?

전자는 못 탄다(선두 컬럼 A 없음). 후자는 A까지만 — 범위 조건 뒤 컬럼은 정렬이 깨진다. "왼쪽부터 끊기지 않게, 범위를 만나면 거기서 끝." → 4절 축 3

key: NULL 원인 6종을 나열하고, "못 타는" 것과 "안 타는" 것으로 나눠보라.

함수·연산 / 타입 불일치 / 선행 와일드카드 / 낮은 선택도 / 선두 컬럼 누락 / OR(한쪽 인덱스 없음). 낮은 선택도만 "탈 수 있는데 안 타는" 경우, 나머지는 "구조상 못 타는" 경우. → 5절

한 줄 요약

B+Tree는 "다분기로 트리를 낮추고, 데이터를 리프로 몰아 더 낮추고, 그 리프들을 이어 붙여 범위 스캔까지 얻은" 구조이며(+는 데이터를 리프로 몰았다는 뜻이지 그 반대가 아니다), 인덱스를 걸지 말지는 쓰기 빈도 · 선택도 · 기존 인덱스와의 중복(선두 컬럼 규칙) · EXPLAIN 검증 네 축으로 판단한다.
