운영 DB의 FK 제약 논쟁 — "안 건다"가 관행이 된 이유와, 포기한 방어선을 무엇으로 메우는가

질문: "운영 DB에서 FK 제약을 걸지 않는 팀이 많은 이유는 무엇이고, 본인의 견해는? FK 없이 정합성은 어떻게 지키나요?"

핵심 관전 포인트 — 면접 첫 답변으로 그대로 말한다

FK는 "가리키는 곳이 반드시 있다"를 어떤 경로로 들어와도 DB가 강제하는 최후 방어선이다. 그 대가로 DB는 자식 INSERT마다 부모 행에 공유(S) 락을 잡아 커밋까지 쥐고, 부모 DELETE마다 자식 테이블을 검사한다.
  1. 빼는 이유는 이 검사가 만드는 사슬이다 — 핫 부모 행의 S 락 ↔ X 락 경합과 데드락, 대량 적재·아카이빙의 순서 제약, gh-ost가 FK 테이블을 못 다루고 ADD FOREIGN KEY는 COPY, 샤딩·서비스 분리에선 FK가 성립 불가, CASCADE의 보이지 않는 폭발. 솔직히는 대규모 회사의 관행이 전파된 몫도 크다.
  2. 잃는 것도 정면으로 말한다 — 어떤 경로(콘솔·배치·신규 코드)로 와도 뚫리지 않는 유일한 검사, 고아 행 0건 보장, 스키마 자체가 문서인 상태, MySQL이 FK와 함께 자동으로 만들던 인덱스.
  3. 내 견해 — 기본값은 건다. 빼는 것은 조건(쓰기 부하·핫 부모·마이그레이션 빈도·분산 계획·삭제 정책·데이터 민감도·팀 규율)이 확인된 예외이고, 빼는 순간 앱 레벨 존재 검증 + 소프트 삭제 + FK 컬럼 인덱스 린트 + 고아 탐지 배치·알람 + 소프트 참조 규약·문서화 (+ 테스트 환경에서만 FK)가 한 세트로 따라온다.
대체 체계를 운영할 준비 없이 FK만 빼는 것은 결정이 아니라 방치다. 그리고 "나중에 걸면 된다"는 사실상 거짓 — 고아가 한 행이라도 있으면 ADD FOREIGN KEY는 실패하고, 통과시키려 검사를 끄면 거짓 안심만 남는다. FK는 처음에 걸든가, 처음부터 대체 체계로 가든가다.

이 문항은 "FK 찬성/반대"를 묻는 것이 아니다. 교과서 규범("참조 무결성은 DB가 지킨다")과 실무 관행("운영 DB엔 FK 안 건다")이 충돌하는 지점에서 "우리 서비스의 조건"으로 결론을 내는 사고를 본다.

1FK가 하는 일 — 무엇을 지키고, 그 대가로 DB가 매번 무엇을 하는가

1-1. 참조 무결성 = "가리키는 곳이 반드시 있다"

외래 키(FK, foreign key) 제약은 한 문장이다 — 자식 행의 참조 컬럼 값은 부모 테이블에 반드시 존재하는 키여야 한다. comments.post_id = 42라면 posts.id = 42가 있어야 하고, 그 행을 지우려면 먼저 댓글을 처리해야 한다. 이 성질이 참조 무결성(referential integrity), 이것이 깨진 자식 행 — 부모 없는 자식 — 이 고아 행(orphan row)이다.

건물 출입구의 경비원으로 외우기

FK는 건물 출입구의 경비원이다. 어떤 문으로 들어오든(앱 코드, 배치, 운영자의 콘솔 DELETE, 마이그레이션 스크립트) 신분증(부모 존재)을 확인한다. 경비원을 없애면 출입은 빨라지고 이삿짐(대량 적재)도 편해지지만, 그때부터 "누가 들어왔는지"는 각 부서(코드 경로)가 알아서 확인해야 한다. 그리고 부서 하나가 확인을 잊으면 — 아무도 모른 채 들어온다.

1-2. 검사가 일어나는 네 순간 — 그리고 각 순간에 DB가 잡는 것

FK를 "느리다"고 뭉뚱그리지 않으려면, 언제 검사가 일어나고 그때 무엇을 잡는지부터 고정한다. InnoDB 기준.

② 자식의 FK 컬럼 UPDATE새 부모 값을 ①처럼 찾는다새 부모 행에 S 락

"검사"는 한순간, "락"은 트랜잭션 수명만큼 산다

  • InnoDB는 FK 검사를 즉시 한다 — 커밋 시점으로 미루지 않는다. (PostgreSQL은 DEFERRABLE INITIALLY DEFERRED로 커밋까지 미룰 수 있다 — 상호 참조 행을 한 트랜잭션에서 넣을 때 쓴다.)
  • 검사 때 잡은 S 락은 트랜잭션이 끝날 때까지 유지된다. 2-1의 사슬은 여기서 출발한다.
  • READ COMMITTED로 낮춰도 FK 검사의 갭 락은 남는다. "격리 수준 낮췄으니 갭 락 없다"가 이 지점에서 깨진다.

FK 비용의 실체 — "찾기"가 아니라 "찾은 뒤 쥐고 있는 락" + 운영상의 제약

부모 PK 한 번 찾기는 싸다. 비싼 것은 커밋까지 쥐는 S 락과, 그 락이 만드는 순서·도구·지형의 제약이다.

이 구분을 못 하면 "FK는 느려서 뺐다"는 말이 근거 없는 관행 반복으로 들린다.

2-1. ① 락 전파 — 자식 INSERT → 부모 행 S 락 → 핫 부모의 X 락과 경합 → 데드락

가장 중요한 사슬이고, 정규화 문서의 posts.comment_count 예제와 정확히 맞물린다. 네 고리를 이름 붙여 순서대로 말한다.

  1. S 락자식 INSERT가 부모 행에 S 락 — INSERT INTO comments (post_id=42)는 FK 검사로 posts.id=42 행에 공유 락을 잡고 커밋까지 쥔다.
  2. X 락 경합부모가 핫하면 X 락과 경합 — 같은 트랜잭션에서, 혹은 다른 트랜잭션이 UPDATE posts SET comment_count = comment_count + 1 WHERE id = 42를 치면 배타(X) 락이 필요하다. X는 S와 비호환이므로 다른 트랜잭션이 쥔 S 락이 풀릴 때까지 대기한다.
  3. 교차대기의 교차 = 데드락 — 두 트랜잭션이 각각 "INSERT 자식 → UPDATE 부모" 순서면 서로의 S 락을 기다리며 교착한다.
  4. 전파데드락이 아니어도 대기 전파 — 인기 글에 초당 수백 댓글이 붙으면 부모 행 하나의 락 큐에 모든 댓글 트랜잭션이 걸린다 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 무관한 API까지 전파. 정규화 문서 §3의 사슬이 FK가 있으면 한 단계 더 일찍, S 락 단계에서 시작된다.
-- ❌ before: FK 있음 + "자식 INSERT → 부모 UPDATE" 순서 (가장 흔한 코드 순서)
-- T1                                        -- T2
BEGIN;                                       BEGIN;
INSERT INTO comments (post_id, body)         INSERT INTO comments (post_id, body)
VALUES (42, 'a');                            VALUES (42, 'b');
-- FK 검사 → posts.id=42 에 S 락 (T1)        -- FK 검사 → posts.id=42 에 S 락 (T2)
--                                           -- S ↔ S 는 호환 → 둘 다 통과
UPDATE posts SET comment_count = comment_count + 1
WHERE id = 42;
-- X 락 필요 → T2 의 S 락 때문에 대기          UPDATE posts SET comment_count = comment_count + 1
                                             WHERE id = 42;
                                             -- X 락 필요 → T1 의 S 락 때문에 대기
-- ⇒ 데드락. InnoDB 가 한쪽을 롤백한다.
-- ERROR 1213 (40001): Deadlock found when trying to get lock
-- ✅ after-1: FK 유지 + 순서 반전 — 부모 X 락을 먼저 잡는다
BEGIN;
UPDATE posts SET comment_count = comment_count + 1 WHERE id = 42;  -- X 락 선점
INSERT INTO comments (post_id, body) VALUES (42, 'a');             -- 자기 X 위의 FK 검사는 통과
COMMIT;
-- 데드락은 사라진다. 대신 X 락을 트랜잭션 처음부터 쥐므로 락 보유 시간이 길어진다
-- → 정규화 문서가 권한 "UPDATE 를 커밋 직전에"와 정면충돌한다.
-- FK 가 있는 한 "락 짧게"와 "데드락 회피" 중 하나를 고르게 된다.
 
-- ✅ after-2: FK 제거 — S 락 자체가 안 생기므로 순서 제약이 사라진다
--   (대신 3장에서 잃는 것을 4장의 체계로 메워야 한다)

이 문서에서 가장 자주 써먹을 무기 — 한 문장을 이렇게 바꾼다

✗ "FK는 락 때문에 뺐다"

✓ "자식 INSERT의 S 락이 핫 부모 UPDATE의 X 락과 교차해 데드락이 나고, 회피하려면 X를 먼저 잡아 락 보유 시간을 늘려야 하는 딜레마가 생깁니다."

"딜레마"까지 말해야 사슬이 닫힌다 — 회피책(순서 반전)이 다른 비용(락 보유 시간)을 만든다는 것이 양면의 핵심이다.

2-2. ② 부모 DELETE의 자식 검사 — 인덱스가 없으면 자식 테이블 풀스캔

부모 행을 지우면 DB는 "이 부모를 가리키는 자식이 있나"를 자식 테이블에서 찾아야 한다. 자식의 FK 컬럼에 인덱스가 있으면 탐색 한 번, 없으면 자식 테이블 전체 스캔이다. 자식이 수억 건이면 부모 한 행 삭제가 수십 초짜리 풀스캔이 되고, 그동안 훑은 레코드에 S 락이 걸린다.

②는 "FK를 빼는 이유"라기보다 "FK 컬럼 인덱스를 빠뜨리면 생기는 문제"다

이 구분을 아는 것이 변별점이다. FK를 빼도 인덱스를 빠뜨리면 같은 풀스캔이 WHERE member_id = ?에서 난다(3-4).

2-3. ③ 대량 적재·마이그레이션·아카이빙의 순서 제약

FK가 있으면 데이터 이동에 순서가 생긴다.

  • 적재: 부모 → 자식 순서로만 넣을 수 있다. 수억 건을 병렬로 붓는 파이프라인에서 이 순서는 병렬성을 죽인다. 그래서 흔히 SET foreign_key_checks = 0으로 끄고 붓는데 — 이것이 아래 함정으로 이어진다.
  • 아카이빙: 오래된 부모 행을 아카이브 테이블로 옮기려면 자식을 먼저 옮기거나 지워야 한다. 자식이 여러 테이블에 흩어져 있으면 아카이빙 잡이 FK 그래프 전체를 알아야 한다.
  • 테이블 교체·복구: 백업에서 테이블 하나만 되살리거나 스왑 방식으로 교체할 때, FK가 다른 테이블을 물고 있으면 순서·잠금 창이 생긴다.

foreign_key_checks = 0으로 붓고 다시 1로 켜도, 이미 들어간 데이터는 검사하지 않는다

"적재 중엔 어차피 FK를 끈다"는 현실이 "그럼 평소에도 없는 것과 무엇이 다른가"라는 질문으로 이어진다. 그리고 이 상태에서 위반 행은 FK가 있는데도 그대로 남는다 — 6절의 "거짓 안심"과 같은 뿌리.

2-4. ④ online DDL 도구의 제약 — gh-ost는 FK 테이블을 아예 못 다룬다

도구FK가 있으면
gh-ost대상 테이블이 FK의 부모든 자식이든 지원하지 않는다 (하드 리밋). FK가 있는 스키마에서는 선택지에서 빠진다.
pt-online-schema-change--alter-foreign-keys-method로 rebuild_constraints(자식 테이블들에 ALTER — 자식이 크면 또 하나의 대공사) 또는 drop_swap(테이블이 잠깐 존재하지 않는 창)을 골라야 한다.
네이티브 online DDLADD FOREIGN KEY는 foreign_key_checks=1이면 COPY 알고리즘(쓰기 차단, 디스크 2배). INPLACE로 하려면 검사를 끄고 걸어야 하는데, 그러면 기존 데이터의 위반을 검사하지 않는다.

"수억 건 테이블을 자주 바꾸는 팀"에게 FK는 도구 선택지를 절반 이하로 줄이는 제약이다.

대규모 팀이 FK를 빼는 가장 실질적인 이유 중 하나이고, "성능"보다 훨씬 설득력 있는 근거다. 면접에서 ①과 함께 반드시 말한다.

2-5. ⑤ 샤딩·파티셔닝·서비스 분리 — FK가 성립 불가한 지형

FK는 같은 DB 인스턴스 안의 두 테이블 사이에서만 성립한다.

샤딩comments가 user_id로, posts가 post_id로 샤딩되면 부모와 자식이 다른 서버에 있다. 검사할 대상이 물리적으로 다른 곳이니 FK 자체가 정의될 수 없다 — 크로스 샤드 조인이 사라지는 것과 같은 뿌리.
파티셔닝MySQL의 파티션 테이블은 FK를 지원하지 않는다. 파티셔닝을 도입하는 순간 그 테이블의 FK는 걷어내야 한다.
서비스 분리(MSA)주문 서비스의 orders.member_id가 회원 서비스의 members.id를 가리키지만 DB가 다르다. 참조는 DB가 아니라 계약(API·이벤트)으로만 지켜진다 — 4-5의 소프트 참조가 유일한 선택지.

"언젠가 샤딩·분리할 것"이라면 FK에 기대 짠 코드(삭제 순서를 FK에 맡기기, cascade)는 그때 전부 다시 짜야 한다. 그래서 처음부터 FK 없는 규율로 가는 팀이 생긴다.

2-6. ⑥ CASCADE의 예측 불가 폭발

ON DELETE CASCADE는 부모 한 행 DELETE가 자식 → 손자 → 증손자로 번진다.

  1. 범위가 코드에 안 보인다. DELETE FROM posts WHERE id = 42 한 줄이 댓글·첨부·알림·통계 행 수만 건을 지우는데, 리뷰어는 그 한 줄만 본다. JPA cascade는 코드에 파급이 보이고, DB cascade는 안 보인다.
  2. MySQL에서 캐스케이드된 삭제는 트리거를 발동시키지 않는다. 감사 로그 트리거가 있어도 연쇄 삭제분은 기록되지 않는다.
  3. 중첩 깊이 제한이 있어 깊은 그래프에서는 에러로 실패한다.
  4. 락과 시간이 예측 불가. 부모 한 행 삭제가 자식 수십만 건의 X 락으로 확장되고 그 트랜잭션은 그만큼 길어진다 — 장기 트랜잭션의 해악이 한 문장에서 시작된다.

FK를 쓰더라도 CASCADE는 안 쓰고 RESTRICT만 쓴다

그러면 "어차피 RESTRICT만 쓸 거면 앱에서 막는 것과 무엇이 다른가"가 FK 제거의 또 다른 논거가 된다 — 답은 3-1: 앱은 앱을 거치는 경로만 막는다.

2-7. ⑦ 솔직한 이유 — 관행의 전파

위 여섯이 다 해당되는 팀은 사실 많지 않다. 그런데 "운영 DB엔 FK 안 건다"는 규칙은 훨씬 넓게 퍼져 있다. 대규모 서비스 회사의 DBA 컨벤션이 "정답"으로 전파되었기 때문이다 — 그 회사들은 ①~⑥을 실제로 겪었지만, 컨벤션만 가져온 팀은 겪지 않은 문제를 피하려고 방어선을 버린다.

"성능 때문에 뺐다"는 대개 사후 정당화이고, 실제 결정 요인은 운영 유연성(③④)과 분산 계획(⑤)입니다. 우리 팀이 그 조건에 해당하는지가 판단 기준입니다.

이걸 인정하고 말하는 것이 오히려 신뢰를 준다. 그리고 자연스럽게 5절의 "조건"으로 넘어가는 다리가 된다.

3-1. ① 최후 방어선 — 불변식이 DB 제약에서 앱 관례로 내려온다

"FK나 UNIQUE 제약은 DB가 지키므로 어떤 코드 경로로 들어와도 뚫리지 않는다. 반면 앱의 약속은 약속을 모르는 경로가 하나만 생겨도 뚫린다."

FK를 빼는 것은 참조 무결성을 정확히 그 "앱의 약속" 등급으로 강등시키는 일이다. 뚫는 경로는 늘 같은 세 종류다.

뚫는 경로예FK 있으면FK 없으면

앱을 거치지 않는 경로장애 대응 중 콘솔에서 DELETE FROM posts WHERE .... 데이터 보정 스크립트. ETL 역적재.에러로 즉시 드러남조용히 성공

"에러로 즉시 드러남" vs "조용히 성공" — 이 차이가 최후 방어선의 뜻이다.

3-2. ② 고아 행 — 조용히 쌓이고, 증상은 엉뚱한 곳에서 터진다

고아 행의 무서움은 생길 때가 아니라 발견될 때다.

  1. 부모를 조인해 화면을 그리는 코드가 null을 만나 NPE — 그런데 원인 행은 석 달 전 배치가 만들었다.
  2. INNER JOIN 통계에서 고아 행이 빠져 매출 집계가 조용히 작다. 아무도 모른다.
  3. 개인정보 삭제 요청으로 회원을 지웠는데 그 회원의 주소가 담긴 자식 행이 남아 있다 — 버그가 아니라 컴플라이언스 사고다.
  4. 고아를 뒤늦게 발견해 지우려는데 "정말 고아인지, 부모가 다른 경로로 옮겨진 건지" 판별할 근거가 없다.

보장 등급이 바뀐다 — "생성 시 0건" → "발견 지연 N시간"

FK는 이 모든 것을 생성 시점에 0건으로 유지한다. 대체 체계(4-4)는 "발견 시점"을 몇 시간 단위로 당기는 것이지 0건을 보장하지 못한다 — 이 차이를 알고 받아들이는 것이 결정이다.

3-3. ③ 스키마의 문서 역할

FK가 있는 스키마는 그 자체로 ERD다. DB 도구가 관계를 그려주고, 신규 입사자가 SHOW CREATE TABLE만으로 "이 테이블은 누구를 가리키나"를 안다. FK가 없으면 member_id가 members.id인지 legacy_members.member_no인지 컬럼 이름과 부족의 기억으로만 남는다. 테이블이 200개를 넘으면 이 지식은 반드시 유실되고, 4-5의 문서화 규약이 그 자리를 메워야 한다.

3-4. ④ 자동 인덱스의 소멸 — MySQL에서 가장 흔한 함정

MySQL은 FK를 걸면 자식 FK 컬럼에 인덱스를 자동으로 만든다. FK를 안 거는 팀은 이 인덱스를 손으로 만들어야 한다는 사실을 자주 잊는다.

-- FK 없이 만든 자식 테이블. member_id 에 인덱스가 없다.
CREATE TABLE orders (
    id         BIGINT PRIMARY KEY,
    member_id  BIGINT NOT NULL,   -- 논리적 FK. 그런데 인덱스는? 없다.
    amount     DECIMAL(19, 2)
);
 
-- 가장 흔한 조회가 풀스캔이 된다
SELECT * FROM orders WHERE member_id = ?;            -- type: ALL
-- 회원 삭제 전 "주문 있나" 검사도 풀스캔
SELECT 1 FROM orders WHERE member_id = ? LIMIT 1;    -- type: ALL

"FK를 뺐더니 느려졌다"의 상당수는 FK가 아니라 함께 사라진 인덱스 때문이다.

4-3에서 이걸 사람 기억이 아니라 린트로 막는다.

// ❌ before: FK 도 없고 검증도 없다 — 존재하지 않는 postId 가 그대로 저장된다
@Transactional
public Long addComment(Long postId, String body) {
    Comment comment = new Comment(postId, body);
    return commentRepository.save(comment).getId();   // 고아 행 생성 경로
}
// ✅ after: 부모 존재(그리고 삭제되지 않음)를 같은 트랜잭션에서 확인한다
@Transactional
public Long addComment(Long postId, String body) {
    Post post = postRepository.findActiveById(postId)        // deleted = false 조건 포함
        .orElseThrow(() -> new PostNotFoundException(postId));
    Comment comment = new Comment(post.getId(), body);
    return commentRepository.save(comment).getId();
}

@Transactional
public void deletePost(Long postId) {
    if (commentRepository.existsByPostId(postId)) {
        throw new PostHasCommentsException(postId);
    }
    postRepository.deleteById(postId);   // 물리 삭제. 이 사이에 addComment 가 끼면 고아
}
// ✅ after: 물리 삭제 대신 soft delete — 자식이 가리키는 행이 사라지지 않는다
@Transactional
public void deletePost(Long postId) {
    Post post = postRepository.findActiveById(postId)
        .orElseThrow(() -> new PostNotFoundException(postId));
    post.markDeleted(clock.now());       // UPDATE posts SET deleted_at = ? WHERE id = ?
    // 자식 정책은 명시적으로: 댓글도 함께 soft delete 할지, 남길지 — 도메인 규칙으로
    commentRepository.softDeleteAllByPostId(postId);
}

4-2. ② 삭제는 소프트 삭제/아카이브로 — 고아가 생기는 조건을 없앤다

고아 행은 "부모가 사라질 때" 생긴다. 부모가 사라지지 않으면 — deleted_at만 찍히면 — 참조 무결성은 FK 없이도 물리적으로 깨질 수 없다.

FK를 빼는 팀이 거의 예외 없이 soft delete를 함께 택하는 이유다.

대신 두 가지를 짊어진다.

대가 1 · 논리적 고아"삭제된 부모를 가리키는 살아 있는 자식"이라는 새 종류의 고아가 생기고, 이건 FK가 있어도 못 막는다. "부모가 soft delete될 때 자식은 어떻게 할 것인가"를 도메인 규칙으로 정해야 한다 (위 softDeleteAllByPostId).
대가 2 · 아카이브 이동데이터가 계속 쌓이므로 언젠가 아카이브 테이블로 이동해야 하고, 그 이동이 2-3의 순서 제약을 다시 만난다. 다만 FK가 없으므로 자식·부모를 독립적으로 옮길 수 있고, "옮긴 뒤 고아가 없는지"를 4-4의 배치가 검증한다.

4-3. ③ FK 컬럼 인덱스 강제 — 사람 기억이 아니라 린트로

3-4의 함정은 "인덱스 잊지 말자"로 막히지 않는다. CI에서 스키마를 훑어 *_id 컬럼에 인덱스가 없으면 빌드를 깨뜨린다. 마이그레이션이 적용된 테스트 DB(Testcontainers)에서 아래 쿼리가 한 행이라도 돌려주면 실패.

-- MySQL: 이름이 *_id 로 끝나는데 어떤 인덱스의 선두 컬럼도 아닌 컬럼
SELECT c.table_name, c.column_name
FROM information_schema.columns c
LEFT JOIN information_schema.statistics s
       ON s.table_schema = c.table_schema
      AND s.table_name   = c.table_name
      AND s.column_name  = c.column_name
      AND s.seq_in_index = 1                 -- 선두 컬럼일 때만 인정 (복합 인덱스의 2번째 컬럼은 못 탄다)
WHERE c.table_schema = DATABASE()
  AND c.column_name LIKE '%\_id'             -- 소프트 참조 규약(4-5)의 이름 규칙이 여기서 힘을 발휘한다
  AND c.column_name <> 'id'
  AND s.index_name IS NULL;                  -- 한 행이라도 나오면 = 인덱스 없는 논리적 FK
// 테스트로 고정 — 새 테이블·새 컬럼이 들어와도 사람이 기억할 필요가 없다
@Test
void everyLogicalFkColumnIsIndexed() {
    List<String> missing = jdbcTemplate.queryForList(MISSING_FK_INDEX_SQL, String.class);
    assertThat(missing)
        .as("논리적 FK 컬럼에 인덱스가 없다 — 마이그레이션에 CREATE INDEX 를 추가하라")
        .isEmpty();
}

예외(일부러 인덱스를 안 두는 컬럼)는 허용 목록 테이블로 관리한다. "허용 목록에 넣으려면 PR에 이유를 적어야 한다"가 곧 리뷰 게이트가 된다.

4-4. ④ 고아 행 탐지 배치 + 알람 — 발견 지연을 시간 단위로 묶는다

FK가 "생성 시점 0건"을 보장했다면, 배치는 "N시간 안에 발견하고 사람을 부른다"를 보장한다. 정규화 문서의 "보정 배치"와 같은 성격 — 어긋남을 전제로 한 안전망이다.

-- 고아 탐지의 기본형: 부모가 없는 자식
SELECT c.id, c.post_id, c.created_at
FROM comments c
LEFT JOIN posts p ON p.id = c.post_id
WHERE p.id IS NULL
  AND c.created_at < NOW() - INTERVAL 10 MINUTE   -- ① 유예 창: 진행 중 트랜잭션·복제 지연 제외
  AND c.id BETWEEN ? AND ?                        -- ② PK 범위로 청크 — 대형 테이블 풀스캔 금지
LIMIT 1000;
 
-- soft delete 를 쓰는 팀은 "논리적 고아"도 함께 본다
SELECT c.id, c.post_id
FROM comments c
JOIN posts p ON p.id = c.post_id
WHERE p.deleted_at IS NOT NULL
  AND c.deleted_at IS NULL                        -- 부모는 삭제됐는데 자식은 살아 있다
  AND c.id BETWEEN ? AND ?;
@Scheduled(cron = "0 15 * * * *")                  // 매시 15분
public void detectOrphanComments() {
    long count = orphanScanner.scanInChunks("comments", "post_id", "posts", "id");
    orphanGauge.set("comments.post_id", count);    // 시계열 지표 — "어느 배포 이후 늘었다"가 보인다
    if (count > 0) {
        alert.page("orphan rows detected: comments.post_id -> posts.id = " + count);
    }
}

운영 규칙 4가지까지 세트다

  • 주기: 핵심 관계(주문–회원, 결제–주문)는 시간 단위, 나머지는 일 단위. 배치 자체가 부하가 되면 안 되므로 복제본에서, 청크로, 야간에.
  • 결과 처리: 0건이 아니면 알람(Slack·페이저) → 자동 삭제가 아니라 격리 테이블로 이동 + 원인 경로 추적. 자동 삭제는 "부모가 다른 경로로 옮겨진 정상 데이터"를 지울 수 있다.
  • 지표화: 고아 건수를 시계열로 남기면 "어느 배포 이후 늘었다"가 보인다 — 3-1의 "새 코드 경로"를 잡는 유일한 방법이다.
  • 커버리지 목록: 어떤 관계를 검사하는지 목록으로 관리하고, 새 *_id 컬럼이 생기면 4-3의 린트가 "탐지 목록에도 추가했나"를 함께 묻게 한다.

4-5. ⑤ 소프트 참조 규약 + 스키마 문서화 — 잃어버린 "문서로서의 스키마"를 되찾기

소프트 참조(soft reference) 규약: 물리 FK 대신 팀이 지키는 이름·타입 규칙이다.

  1. 참조 컬럼은 <부모단수>_id, 타입은 부모 PK와 동일(BIGINT ↔ BIGINT). 타입이 다르면 조인에서 암묵적 형변환으로 인덱스를 못 탄다.
  2. 컬럼 COMMENT에 대상을 명시한다 — 도구가 읽고 사람이 읽는다.
  3. 서비스 경계를 넘는 참조(주문 → 회원 서비스)는 코드에서도 @ManyToOne Member가 아니라 Long memberId로 둔다. "여기는 DB가 지켜주지 않는 참조"임이 타입에서 드러난다.
CREATE TABLE orders (
    id         BIGINT PRIMARY KEY,
    member_id  BIGINT NOT NULL COMMENT 'FK(logical) -> members.id, 회원 서비스 소유',
    KEY idx_orders_member_id (member_id)         -- 4-3: 손으로 만든다
) COMMENT = '주문. FK 미사용 — 고아 탐지 배치 orphan-check.orders 참조';

ERD 도구: 물리 FK가 없어도 이름 규약을 근거로 관계를 추론해 그려주는 도구(SchemaSpy의 implied relationship, dbdocs 류의 선언형 스키마)를 CI에 붙여 문서를 자동 생성한다. 손으로 그린 ERD는 반드시 낡는다.

4-6. ⑥ 테스트·스테이징에서만 FK 켜기 — 선택지와 그 대가 가산점

운영에는 FK가 없지만 테스트 DB에는 FK를 건다. 그러면 4-1의 검증을 빠뜨린 새 코드 경로가 통합 테스트에서 FK 위반 예외로 즉시 드러난다.

-- src/test/resources/db/testonly/R__fk_constraints.sql  (테스트 프로파일에서만 적용)
ALTER TABLE comments ADD CONSTRAINT fk_comments_post
    FOREIGN KEY (post_id) REFERENCES posts(id);
ALTER TABLE orders ADD CONSTRAINT fk_orders_member
    FOREIGN KEY (member_id) REFERENCES members(id);
# application-test.yml — Flyway 위치에 테스트 전용 디렉토리를 추가
spring:
  flyway:
    locations: classpath:db/migration, classpath:db/testonly

대가 셋을 같이 말해야 한다

  1. 테스트와 운영의 락 동작이 달라진다 — 2-1의 데드락은 테스트에서만 나고 운영에선 안 나거나 그 반대다.
  2. 테스트 픽스처 정리(TRUNCATE) 순서가 FK에 묶여 귀찮아진다.
  3. 스테이징에 FK를 두면 운영 데이터를 복제해 넣을 때 기존 고아 때문에 적재가 실패한다 — 그 실패가 오히려 고아를 발견하는 계기가 되기도 한다.

"FK를 빼도 개발 단계의 방어선은 유지하고 싶다"는 팀에 잘 맞는다.

4-7. ⑦ JPA — 객체 매핑과 물리 제약은 별개다

JPA의 @ManyToOne은 객체 참조를 어떻게 로딩할지에 대한 선언이고, DB의 FK 제약과는 독립이다. 그런데 Hibernate가 DDL을 생성하면(ddl-auto) @JoinColumn마다 FK 제약을 기본으로 만든다. 여기서 두 가지 사고가 난다.

// ❌ before: 팀 규칙은 "운영 DB 에 FK 없음"인데, 매핑은 FK 를 만든다
@Entity
public class Comment {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "post_id")            // ddl-auto=create/update 면 FK 제약이 생성된다
    private Post post;
}
// 사고 ①: 로컬·테스트는 ddl-auto 로 FK 있는 스키마, 운영은 Flyway 로 FK 없는 스키마
//         → "테스트에선 예외, 운영에선 조용히 고아"가 반대로도 일어난다
// 사고 ②: 어느 날 누가 운영에 ddl-auto=update 를 켰다 → 수억 건 테이블에
//         ADD FOREIGN KEY = COPY 알고리즘 → 쓰기 차단 (online DDL 문서 §2)
// ✅ after: 매핑은 유지하되 "물리 FK 를 만들지 마라"를 명시한다
@Entity
public class Comment {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(
        name = "post_id",
        foreignKey = @ForeignKey(ConstraintMode.NO_CONSTRAINT)   // DDL 생성 시 FK 제약 생략
    )
    private Post post;
}
 
// 서비스 경계를 넘거나 애초에 객체 그래프가 필요 없는 참조는 ID 만 든다 (4-5 소프트 참조)
@Entity
public class Order {
    @Column(name = "member_id", nullable = false)
    private Long memberId;                   // 타입 자체가 "DB 가 지켜주지 않는 참조"라고 말한다
}
# 운영: 스키마는 마이그레이션 도구가 소유한다. Hibernate 는 DDL 을 만들지 않는다.
spring:
  jpa:
    hibernate:
      ddl-auto: none
      # validate 도 가능하지만, validate 는 테이블·컬럼·타입만 보고 FK 유무는 검사하지 않는다
      # — "FK 없는 운영 스키마"를 잡아주지 않는다

NO_CONSTRAINT여도 @ManyToOne 지연 로딩·조인은 그대로 동작한다 — 단, 고아를 만나면

부모가 없는 자식을 로딩하면 프록시 초기화 시점에 EntityNotFoundException이 난다 — 고아 행이 있는 운영 DB에서 JPA가 먼저 비명을 지르는 지점이고, 4-4 배치가 있으면 그 전에 잡힌다.

5본인의 견해 — "우리 서비스의 조건"으로 결론 내기

5-1. 판단 기준 6축

"FK 건다/안 건다"는 팀의 신념이 아니라 아래 여섯 축의 답으로 정해진다.

축질문FK 유지 쪽FK 제거 쪽
① 쓰기 부하·핫 부모자식 INSERT가 집중되는 부모 행이 있는가(인기 글, 이벤트 상품)없다있다 → 2-1 사슬
② 스키마 변경 빈도·크기수억 건 테이블을 분기마다 바꾸는가아니다그렇다 → gh-ost 필요
③ 분산 계획샤딩·파티셔닝·서비스 분리가 로드맵에 있는가없다있다 → 어차피 불가
④ 삭제 정책부모를 물리 삭제하는가그렇다 → FK가 막아줘야soft delete → 고아 조건 자체가 없음
⑤ 데이터 민감도돈·법적 근거·개인정보인가그렇다 → 방어선 필요로그·집계·파생 데이터
⑥ 팀 규율·도구4장의 체계를 운영할 배치 인프라·CI 린트·리뷰 문화가 있는가없다 → 빼면 방치있다

⑥이 결정적이다. ①~⑤가 전부 "제거"를 가리켜도 ⑥이 없으면 빼지 않는다.

대체 체계 없이 FK만 빼는 것은 트레이드오프가 아니라 손실만 받아들인 것이기 때문이다.

5-2. 결론은 세 갈래다 — 그리고 기본값은 "건다"

내 견해 — 한 문장

"기본값은 FK를 건다. 빼는 것은 위 조건이 확인된 예외이며, 빼는 순간 4장의 일곱 가지가 세트로 따라온다."

A · 걸어라단일 DB, 중간 이하 쓰기 부하, 작은 팀, 물리 삭제가 있는 도메인. 이 조건에서 FK의 비용(부모 PK 탐색 한 번 + 드문 S 락)은 4장 체계의 운영 비용보다 훨씬 싸다. "대규모 회사가 안 건다더라"는 이 팀에 해당하지 않는 근거다. 단 CASCADE는 쓰지 않고 RESTRICT로 두어 파급을 코드에 드러낸다.
B · 선택적으로 걸어라대부분의 중규모 서비스가 여기다. 원장성 관계(결제 → 주문, 정산 → 결제, 권한 → 회원)에는 FK를 유지하고, 고빈도·로그성 자식(알림, 조회 이력, 이벤트 로그)과 핫 부모를 가진 관계(댓글 → 인기 글)에는 빼고 4장 체계를 붙인다. 서비스 경계를 넘는 참조는 무조건 소프트 참조다. "테이블마다 판단한다"가 가장 성숙한 답이다.
C · 빼라샤딩·파티셔닝이 이미 있거나 확정, gh-ost 없이는 운영이 안 되는 테이블 크기, 적재 파이프라인이 병렬로 붓는 구조, 그리고 4장을 이미 운영하고 있는 팀. 이 팀은 FK를 빼는 것이 아니라 FK가 하던 일을 다른 자리(앱·배치·CI)에서 하고 있는 것이다.

5-3. 면접에서 말하는 순서 — 세 말풍선, 이 순서 그대로

이유 — 핵심 셋 + 솔직한 하나 "FK를 빼는 팀이 많은 이유는 일곱 가지로 정리할 수 있는데, 핵심은 세 가지입니다. 첫째 락 — 자식 INSERT가 부모 행에 S 락을 커밋까지 쥐기 때문에, 핫 부모의 UPDATE X 락과 교차해 데드락이 나고 회피하려면 X를 먼저 잡아 락 보유 시간을 늘려야 하는 딜레마가 생깁니다. 둘째 운영 — 대량 적재·아카이빙에 순서가 강제되고, gh-ost는 FK 테이블을 아예 못 다루며, ADD FOREIGN KEY는 COPY입니다. 셋째 지형 — 샤딩·파티셔닝·서비스 분리에선 FK가 정의 자체가 안 됩니다. 솔직히는 대규모 회사의 관행이 전파된 몫도 큽니다."
잃는 것 — 정면으로 "대신 잃는 것도 분명합니다. 어떤 경로로 와도 뚫리지 않는 최후 방어선, 고아 행이 0건이라는 보장, 스키마가 곧 문서인 상태, 그리고 MySQL이 자동으로 만들던 FK 컬럼 인덱스입니다."
견해 — 기본값 · 조건 · 세트 "제 견해는 기본값은 건다, 입니다. 빼는 것은 쓰기 부하·핫 부모·마이그레이션 빈도·분산 계획·데이터 민감도·팀 규율을 확인한 예외이고, 빼는 순간 앱 레벨 존재 검증, 소프트 삭제, FK 컬럼 인덱스 CI 린트, 고아 탐지 배치와 알람, 소프트 참조 규약과 문서화, 그리고 테스트 환경에서만 FK를 켜는 것까지 세트로 갑니다. 현실적으론 테이블마다 판단해서 원장성 관계엔 걸고, 고빈도·로그성 관계와 서비스 경계를 넘는 참조엔 빼는 구성이 가장 많습니다."

6"나중에 다시 걸면 되지 않나요?" — 사실상 비가역이다

FK를 나중에 다시 걸 수 있나 — 걸 수는 있지만, 두 가지가 앞을 막는다

⑴ 기존 고아FK 추가는 기존 데이터를 검사하므로 고아가 한 행이라도 있으면 실패한다. 먼저 4-4의 탐지 쿼리로 고아를 찾아 격리·정리해야 하고, 이것이 몇 주짜리 데이터 정비 프로젝트가 되곤 한다. foreign_key_checks = 0으로 검사를 끄고 걸면 통과는 하지만 위반 데이터가 그대로 남은 채 FK만 생긴다 — 방어선이 아니라 거짓 안심이다.
⑵ DDL 비용MySQL에서 ADD FOREIGN KEY는 검사를 켠 상태면 COPY 알고리즘이라 쓰기 차단·디스크 2배이고, gh-ost는 못 쓴다. PostgreSQL이라면 ADD CONSTRAINT ... NOT VALID로 새 쓰기부터 검사를 시작하고 VALIDATE CONSTRAINT를 나중에 돌려 긴 락을 피할 수 있다 — MySQL엔 이 경로가 없다.

"FK는 나중에 걸면 된다"는 사실상 거짓에 가깝다. FK는 처음에 걸든가, 처음부터 대체 체계로 가든가 — 둘 중 하나다.

이것이 비가역에 가까운 결정임을 아는 것이 시니어의 답이다. 그래서 5절의 결정은 "일단 빼고 보자"가 아니라 조건을 확인한 뒤에 내린다.

7꼬리질문 셀프 테스트 — 먼저 소리 내어 답하고, 펼쳐서 확인

"FK가 락을 잡는다고 했는데, 정확히 어떤 락이 어디에 걸리고 왜 데드락이 나나요?"

자식 INSERT는 FK 검사를 위해 부모 행에 공유(S) 레코드 락을 잡고 커밋까지 유지한다. 두 트랜잭션이 같은 부모(인기 글)에 댓글을 넣으면 둘 다 S를 쥔다(S끼리는 호환). 이어서 각자 UPDATE posts SET comment_count = comment_count + 1로 배타(X) 락을 요구하면 상대의 S 때문에 서로 대기 — 데드락이다. 회피하려면 UPDATE(X)를 INSERT보다 먼저 두어 X를 선점해야 하는데, 그러면 X를 트랜잭션 처음부터 쥐어 락 보유 시간이 늘어난다. 덧붙여 READ COMMITTED로 낮춰도 FK 검사의 갭 락은 남는다는 것까지 말하면 InnoDB 락을 이해한 사람으로 들린다. → 2-1

"앱에서 부모 존재를 확인하고 INSERT하면 FK와 같은 것 아닌가요?"

같지 않다 — 두 가지가 빠진다. ⑴ 레이스 조건: 확인과 INSERT 사이에 다른 트랜잭션이 부모를 물리 삭제하면 고아가 생긴다. FK의 S 락이 정확히 이 틈을 막던 장치다. 손으로 같은 수준을 만들려면 SELECT ... FOR SHARE인데, 그러면 FK의 락 경합이 그대로 돌아오므로 얻는 게 없다. 현실적 답은 부모를 물리 삭제하지 않는 것(soft delete)으로 틈 자체를 없애고, 남는 구멍은 고아 탐지 배치가 "N시간 내 발견"으로 커버하는 것 — 즉 보장 등급이 "생성 시 0건"에서 "발견 지연 N시간"으로 내려왔음을 인지하고 말한다. ⑵ 경로 커버리지: 앱 검증은 앱을 거치는 경로만 지킨다. 콘솔 DELETE, 보정 스크립트, 검증을 빠뜨린 새 API는 못 막는다. 그래서 검증 진입점을 도메인 서비스 한 곳으로 모으고, 테스트 환경에선 FK를 켜서 새 경로의 누락을 조기에 잡는 선택지를 붙인다. → 4-1

"FK를 안 걸었을 때 팀이 가장 흔히 놓치는 게 뭔가요?"

인덱스다. MySQL은 FK를 걸면 자식 FK 컬럼에 인덱스를 자동으로 만드는데, FK를 안 걸면 그 인덱스도 없다. WHERE member_id = ?와 "삭제 전 자식 존재 확인"이 풀스캔이 되고, "FK 뺐더니 느려졌다"의 상당수가 이것이다. 처방은 "잊지 말자"가 아니라 CI 린트 — 테스트 DB의 information_schema를 훑어 *_id 컬럼 중 어떤 인덱스의 선두도 아닌 컬럼이 있으면 빌드를 깨뜨린다. 두 번째로 자주 놓치는 것은 고아 탐지 배치의 커버리지 목록 — 새 참조 컬럼이 생겼는데 탐지 목록에 안 들어가 있는 관계다. → 3-4 · → 4-3

"MSA로 분리된 서비스 간 참조는 어떻게 정합성을 지키나요?"

DB가 다르므로 FK는 선택지에 없고, 참조는 계약으로만 지켜진다. ⑴ 코드에서는 @ManyToOne Member가 아니라 Long memberId로 든다 — "DB가 지켜주지 않는 참조"임이 타입에 드러난다. ⑵ 생성 시 상대 서비스에 존재를 묻거나(동기 API — 결합·지연 대가), 상대 서비스가 발행한 이벤트로 만든 로컬 사본(회원 요약 테이블)을 참조한다(최종적 일관성 대가). ⑶ 상대가 삭제되면 이벤트로 통보받아 로컬 자식을 처리한다 — 이벤트 유실을 전제로 주기적 대사(reconciliation) 배치가 두 서비스의 ID 집합을 맞춰 본다. 즉 단일 DB의 "고아 탐지 배치"가 서비스 간에서는 "대사 배치"가 되고, 이것은 "결제됐는데 주문이 없다" 사고의 Outbox·대사와 같은 도구 상자다. → 2-5 · → 4-5

"그럼 나중에 FK를 다시 걸 수 있나요? 이미 고아가 있으면요?" 시니어 변별

걸 수는 있지만 두 가지가 앞을 막는다. ⑴ 기존 고아: FK 추가는 기존 데이터를 검사하므로 고아가 한 행이라도 있으면 실패한다. 먼저 탐지 쿼리로 고아를 찾아 격리·정리해야 하고, 이것이 몇 주짜리 데이터 정비 프로젝트가 되곤 한다. foreign_key_checks = 0으로 검사를 끄고 걸면 통과는 하지만 위반 데이터가 그대로 남은 채 FK만 생긴다 — 방어선이 아니라 거짓 안심이다. ⑵ DDL 비용: MySQL에서 ADD FOREIGN KEY는 검사를 켠 상태면 COPY 알고리즘이라 쓰기 차단·디스크 2배이고, gh-ost는 못 쓴다. PostgreSQL이라면 ADD CONSTRAINT ... NOT VALID로 새 쓰기부터 검사를 시작하고 VALIDATE CONSTRAINT를 나중에 돌려 긴 락을 피할 수 있다. 결론 — "FK는 나중에 걸면 된다"는 사실상 거짓에 가깝고, FK는 처음에 걸든가 처음부터 대체 체계로 가든가 둘 중 하나다. 비가역에 가까운 결정임을 아는 것이 시니어의 답이다. → 6절

"결제·정산처럼 돈이 걸린 테이블도 FK를 빼나요?" 시니어 변별

여기서 "우리 팀은 FK 안 겁니다"로 일괄 답하면 탈락이다. 판단 축 ⑤(데이터 민감도)가 다른 축을 누른다 — 원장성 관계(결제 → 주문, 정산 → 결제)는 고아 한 건이 곧 돈의 불일치이고, "N시간 내 발견"이 아니라 "생성 시 0건"이 필요하다. 이 관계는 쓰기가 폭주하는 핫 부모도 아니고(주문 하나에 결제 몇 건), 샤딩하더라도 주문과 결제는 같은 샤드 키로 같은 샤드에 두는 것이 정석이므로 FK 제거의 이유 ①⑤가 해당되지 않는다. 따라서 원장성 관계에는 FK를 유지하고, 그 위에 고아 탐지가 아니라 금액 대사 배치를 얹는다. 같은 시스템 안에서도 알림·이력 테이블은 FK를 빼는 — "테이블마다 판단"이 이 질문의 정답 형태다. → 5-2

"PostgreSQL이라면 이 논쟁이 어떻게 달라지나요?" 추가

네 지점이 다르다. ⑴ 자식 FK 컬럼 인덱스를 자동으로 만들지 않는다 — 이유 ②(부모 DELETE 시 자식 스캔)가 InnoDB보다 더 자주, 더 크게 터진다. 4-3의 린트는 PostgreSQL에서 더 절실하다. ⑵ DEFERRABLE INITIALLY DEFERRED로 FK 검사를 커밋 시점까지 미룰 수 있어 상호 참조 행을 한 트랜잭션에서 넣기 쉽다. ⑶ ADD CONSTRAINT ... NOT VALID + 나중에 VALIDATE CONSTRAINT가 있어 "나중에 걸기"의 DDL 비용 쪽은 완화된다 — 다만 기존 고아를 정리해야 VALIDATE가 통과하는 것은 같다. ⑷ FK 검사가 부모 행에 잡는 락이 InnoDB의 S 락이 아니라 FOR KEY SHARE이고, 키가 아닌 컬럼(comment_count)만 바꾸는 UPDATE는 FOR NO KEY UPDATE라 둘이 호환된다 — 그래서 2-1의 데드락 사슬은 PostgreSQL에서는 훨씬 덜하다. 정리하면 PostgreSQL에서는 "락" 논거는 약해지고 "인덱스 누락"과 "운영·지형" 논거가 남는다. → 2-2

"SET foreign_key_checks = 0으로 적재하고 다시 1로 켜면, 그때 검사되나요?" 추가

아니오. 다시 켜도 이미 들어간 행은 검사하지 않는다 — 위반 행이 FK가 있는데도 그대로 남는다. 그래서 대량 적재 뒤에는 4-4의 탐지 쿼리를 한 번 돌리는 것이 세트다. 같은 이유로 foreign_key_checks = 0 상태에서 ADD FOREIGN KEY를 하면 기존 고아를 품은 채 FK만 생긴다(6절의 "거짓 안심"). "적재 중엔 어차피 FK를 끈다"가 "그럼 평소에도 없는 것과 무엇이 다른가"로 이어지는 것이 이유 ③의 뿌리다. → 2-3

"FK를 쓰더라도 ON DELETE CASCADE 대신 RESTRICT를 권하는 이유는?" 추가

CASCADE는 ⑴ 파급 범위가 코드에 안 보인다 — DELETE 한 줄이 자식·손자 수만 건을 지우는데 리뷰어는 그 한 줄만 본다. ⑵ MySQL에서 캐스케이드된 삭제는 트리거를 발동시키지 않아 감사 로그에 빠진다. ⑶ 중첩 깊이 제한에 걸려 실패할 수 있다. ⑷ 부모 한 행 삭제가 자식 수십만 건의 X 락과 장기 트랜잭션으로 변한다. RESTRICT는 "자식이 있으면 실패"만 하므로 파급이 앱 코드에 명시적으로 드러난다 — 삭제 순서를 코드가 책임지게 만드는 것이 목적이다. → 2-6

"고아 탐지 배치가 고아를 찾았을 때 자동으로 지우면 안 되는 이유는? 유예 창은 왜 두나요?" 추가

자동 삭제는 "부모가 다른 경로로 옮겨진 정상 데이터"(계정 병합, 이관 중인 행)를 지울 수 있고, 지운 뒤에는 원인 경로를 추적할 근거가 사라진다. 그래서 격리 테이블로 이동 + 알람 + 원인 경로 추적이다. 유예 창(created_at < NOW() - INTERVAL 10 MINUTE)은 진행 중인 트랜잭션과 복제 지연을 제외하기 위한 것 — 복제본에서 배치를 돌리면 방금 커밋된 부모가 아직 안 보일 수 있고, 그 순간의 자식은 고아가 아니라 "아직 도착 전"이다. 지표화까지 하면 "어느 배포 이후 늘었다"가 보여 새 코드 경로를 잡을 수 있다. → 4-4

"gh-ost는 왜 FK가 있는 테이블을 못 다루나요?" 추가

gh-ost는 고스트 테이블에 데이터를 복사한 뒤 원본과 이름을 바꿔치기(swap)하는 방식이다. 대상 테이블이 FK의 부모면 자식들이 물고 있는 참조를 새 테이블로 옮겨 붙일 수 없고, 자식이면 새 테이블에 FK를 다시 정의하고 검증하는 비용과 순서 문제가 생긴다. 그래서 gh-ost는 부모든 자식이든 지원 자체를 하지 않는다(하드 리밋). pt-osc는 트리거 기반이라 --alter-foreign-keys-method로 자식 FK를 재작성(rebuild_constraints)하거나 잠깐 테이블이 없는 창을 감수(drop_swap)하는 선택지를 준다. 즉 FK가 있는 스키마는 "무중단 스키마 변경" 도구 선택지가 절반 이하로 준다. → 2-4

"@ManyToOne + NO_CONSTRAINT 상태에서 고아 자식을 조회하면 무슨 일이 나나요?" 추가

매핑과 지연 로딩은 그대로 동작하지만, 부모가 없는 자식의 프록시를 초기화하는 순간 EntityNotFoundException이 난다 — 화면 렌더링 중에 터지고, 원인 행은 몇 달 전 배치가 만든 것일 수 있다. Hibernate 전용 @NotFound(action = IGNORE)로 null 처리할 수는 있지만, 이는 고아를 숨기는 것이고 즉시 로딩을 강제하는 부작용이 있다. 정답은 숨기기가 아니라 4-4 배치가 먼저 잡게 하는 것. 그리고 서비스 경계를 넘는 참조는 애초에 Long memberId로 들어 프록시 자체를 만들지 않는다. → 4-7

"앱 검증을 컨트롤러가 아니라 도메인 서비스 한 곳에 두라는 이유는?" 추가

자식 생성 진입점이 여러 개(REST 컨트롤러, 배치, 관리자 API, 이벤트 컨슈머)면 검증도 여러 벌이 되고, 나중에 추가된 진입점 하나가 검증을 빠뜨리는 "경로 비대칭"(3-1)이 그대로 재현된다. 진입점을 도메인 서비스 한 곳으로 모으면 검증이 한 벌이고, 새 경로도 그 서비스를 거치지 않을 방법이 없다. 그래도 남는 구멍(콘솔·스크립트)은 4-6의 테스트 FK와 4-4의 배치가 맡는다 — "한 곳에 모으기"는 코드로 고정한 안전망이고, "각자 조심하기"는 안전망이 아니다. → 4-1

FK를 안 거는 이유 7가지, 순서대로.

① 락 전파(자식 INSERT S ↔ 핫 부모 X → 데드락) ② 부모 DELETE의 자식 검사(인덱스 없으면 풀스캔) ③ 적재·마이그레이션·아카이빙 순서 제약 ④ online DDL 도구 제약(gh-ost 불가, ADD FK는 COPY) ⑤ 샤딩·파티셔닝·MSA에서 성립 불가 ⑥ CASCADE 폭발 ⑦ 관행의 전파. 묶으면 락·운영·지형·폭발 + 솔직. → 카드

빼면 잃는 것 4가지.

① 최후 방어선(어떤 경로로 와도 뚫리지 않는 유일한 검사) ② 고아 0건 보장 ③ 스키마 = 문서 ④ (MySQL) 자동 인덱스. 지켜주던 것 둘 + 공짜로 주던 것 둘.

대체 체계 7가지 — 세트.

① 앱 레벨 존재 검증(+레이스 보정) ② soft delete/아카이브 ③ FK 컬럼 인덱스 CI 린트 ④ 고아 탐지 배치 + 알람 + 지표 ⑤ 소프트 참조 규약 + 문서화 ⑥ 테스트/스테이징에서만 FK ⑦ JPA NO_CONSTRAINT + ddl-auto: none.

2-1 사슬을 한 문장으로.

"자식 INSERT의 S 락이 핫 부모 UPDATE의 X 락과 교차해 데드락이 나고, 회피하려면 X를 먼저 잡아 락 보유 시간을 늘려야 하는 딜레마가 생긴다."

판단 기준 6축 — 그리고 결정적인 축은?

① 쓰기 부하·핫 부모 ② 스키마 변경 빈도·크기 ③ 분산 계획 ④ 삭제 정책 ⑤ 데이터 민감도 ⑥ 팀 규율·도구. ⑥이 결정적 — ①~⑤가 전부 제거를 가리켜도 ⑥이 없으면 빼지 않는다.

세 갈래 결론과 기본값.

A 걸어라(기본값, CASCADE 금지·RESTRICT) / B 선택적으로(원장성 관계 유지, 고빈도·로그성·핫 부모 관계 제거 + 세트, 서비스 경계는 소프트 참조 — 가장 성숙한 답) / C 빼라(샤딩·gh-ost 필수·병렬 적재 + 4장 이미 운영). 기본값은 A.

"나중에 걸면 된다"가 거짓인 두 이유.

⑴ 기존 고아가 한 행이라도 있으면 ADD FK 실패 — 검사 끄고 걸면 거짓 안심. ⑵ MySQL ADD FK = COPY(쓰기 차단·디스크 2배), gh-ost 불가. PostgreSQL은 NOT VALID + VALIDATE로 완화.

앱 검증의 레이스 조건 — 보정 3가지와 각 대가.

① 부모 물리 삭제 안 함(soft delete) → 틈 소멸, 대신 논리적 고아 규칙 ② FOR SHARE → FK 수준 정합성, 대신 2-1 락 경합 복귀(얻는 게 없음) ③ 배치가 잡게 → 단순, 대신 보장 등급 0건 → N시간 내 발견.

"FK 뺐더니 느려졌다"의 진짜 원인은 대개?

FK와 함께 사라진 자식 FK 컬럼의 자동 인덱스. WHERE member_id = ?가 풀스캔. 처방은 CI 린트(information_schema에서 *_id 중 선두 인덱스 없는 컬럼 → 빌드 실패).

MySQL vs PostgreSQL — FK 컬럼 인덱스는?

MySQL(InnoDB)은 FK 생성 시 자식 컬럼 인덱스를 자동 생성, PostgreSQL은 안 만든다. 그래서 MySQL은 "FK 빼면 인덱스도 사라짐"이 함정이고, PostgreSQL은 "FK 있어도 인덱스 없어서 부모 삭제가 자식 풀스캔"이 함정.

고아 탐지 배치의 보장 등급과 운영 규칙 4가지.

등급: "생성 시 0건" → "N시간 내 발견". 규칙: 주기(핵심 관계 시간 단위, 복제본·청크·야간) / 결과 처리(자동 삭제 금지 → 격리 + 알람 + 원인 추적) / 지표화(어느 배포 이후 늘었나) / 커버리지 목록(새 *_id는 탐지 목록에도).

가장 위험한 한 문장 — 면접에서 절대 하면 안 되는 답은?

"우리 팀은 FK 안 겁니다"로 일괄 답하는 것. 특히 결제·정산 질문에서. 정답 형태는 언제나 "테이블(관계)마다 판단" + 원장성 관계엔 유지 + 금액 대사.

한 줄 요약

FK는 "가리키는 곳이 반드시 있다"를 어떤 경로로 와도 강제하는 최후 방어선이고, 그 대가는 자식 INSERT마다 부모 행에 커밋까지 쥐는 S 락(핫 부모의 X 락과 교차해 데드락) · 적재·아카이빙의 순서 제약 · gh-ost 불가와 ADD FOREIGN KEY의 COPY · 샤딩·분리에서의 성립 불가 · CASCADE의 보이지 않는 폭발이다. 빼면 최후 방어선·고아 0건 보장·문서로서의 스키마·자동 인덱스를 잃으므로, 기본값은 걸고 빼는 것은 조건(쓰기 부하·마이그레이션 빈도·분산 계획·삭제 정책·데이터 민감도·팀 규율)이 확인된 예외로 다루며, 빼는 순간 앱 레벨 존재 검증 + 소프트 삭제 + FK 컬럼 인덱스 린트 + 고아 탐지 배치와 알람 + 소프트 참조 규약·문서화 + 테스트 환경 FK + JPA NO_CONSTRAINT가 한 세트로 따라와야 한다 — 대체 체계 없이 FK만 빼는 것은 결정이 아니라 방치다.
