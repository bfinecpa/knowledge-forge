4. RDB / SQL / 데이터 모델링

클러스터드 vs 세컨더리 인덱스 — 테이블이 곧 인덱스인 구조가 PK 설계를 결정한다

📖 약 14분 🧩 5개 섹션 0/5 섹션 이해
🎯 핵심 관전 포인트

InnoDB에서 테이블은 별도의 파일에 인덱스가 붙은 게 아니라, PK 순서로 정렬된 B+Tree 그 자체다(리프 = 행 전체). 세컨더리 인덱스의 리프에는 물리 주소가 아니라 PK가 논리 포인터로 들어가고, 그래서 조회는 2단계(북마크 룩업)가 된다. 이 구조에서 PK 설계 2원칙이 저절로 도출된다 — ① 작게: PK는 모든 세컨더리 인덱스 엔트리에 복제되는 곱셈 계수다 ② 단조 증가: 랜덤 PK는 페이지 분할을 일으킨다. 그리고 비용은 "메모리 부하", "왔다갔다 해서 느림" 같은 뭉뚱그린 말 대신 페이지 분할 · 버퍼 풀 적재율 · 랜덤 I/O라는 이름과 인과 사슬로 말해야 한다. 이름을 붙이는 순간 반박도 검증도 가능한 엔지니어링이 된다.

질문 + 의도

▾
면접 질문

"클러스터드 인덱스와 논클러스터드(세컨더리) 인덱스의 차이는? (InnoDB 기준)"

출제 의도InnoDB에서 PK 선택이 왜 성능 결정인지(세컨더리 인덱스가 PK를 품는 구조), UUID PK가 왜 문제인지가 여기서 나온다. 테이블 설계 첫 단추의 근거를 확인한다. 즉 "리프에 뭐가 들었는지"의 암기가 아니라, 그 구조로부터 "PK는 어떻게 설계해야 하는가"라는 실무 판단을 스스로 도출할 수 있는지를 본다.
1

구조 — 테이블이 곧 클러스터드 인덱스다

▾

InnoDB에는 "테이블 따로, 인덱스 따로"가 없다. 테이블 데이터 자체가 PK 순서로 정렬된 B+Tree이고, 그 리프 노드에 행 전체(모든 컬럼)가 들어있다. 이것이 클러스터드 인덱스다. 그래서 테이블당 정확히 하나이고, "클러스터드 인덱스를 추가로 하나 더"라는 말은 성립하지 않는다.

세컨더리 인덱스(PK 외의 모든 인덱스)는 별도의 B+Tree인데, 리프에는 인덱스 컬럼 값 + PK 값만 들어있다. 행의 나머지 컬럼이 필요하면 그 PK로 클러스터드 인덱스를 한 번 더 탐색해야 한다 — 이 2단계 조회를 북마크 룩업(back to table) 이라 부른다.

text
클러스터드 인덱스 (= 테이블 그 자체, PK 순 정렬)
        [루트/브랜치 — PK 길잡이 키만]
                      │
  리프: │ PK=3 │ 행 전체(name, email, ...) │◄─►│ PK=7 │ 행 전체 │◄─► ...

세컨더리 인덱스 (예: email 인덱스)
        [루트/브랜치 — email 길잡이 키만]
                      │
  리프: │ 'a@x.com' │ PK=7 │◄─►│ 'b@y.com' │ PK=3 │◄─► ...
                       │
        ① email로 여기까지 탐색 → ② 얻은 PK로 위의 클러스터드
           인덱스를 처음부터 다시 탐색 (= 북마크 룩업)

왜 물리 주소가 아니라 PK(논리 포인터)인가

세컨더리 리프에 행의 디스크 물리 주소를 직접 넣으면 2차 탐색 없이 한 번에 갈 수 있어 조회는 더 빠르다. 그런데 클러스터드 인덱스는 정렬을 유지해야 하므로 삽입·페이지 분할 때마다 행이 물리적으로 이동한다. 물리 주소를 넣었다면 행 하나가 움직일 때마다 그 행을 가리키는 모든 세컨더리 인덱스 엔트리를 찾아 고쳐야 한다. PK는 행이 어디로 이동하든 변하지 않으므로, PK를 넣으면 세컨더리 인덱스는 손댈 필요가 없다.

책의 찾아보기에 비유하면 — 찾아보기에 "173쪽"(물리 주소)이라고 적으면 개정판에서 페이지가 밀릴 때마다 찾아보기 전체를 다시 만들어야 하지만, "4.2절"(논리 포인터)이라고 적으면 페이지가 아무리 밀려도 찾아보기는 그대로다. 읽기 한 단계를 내주고 쓰기의 안정성을 산 거래다.

(쿼리가 필요로 하는 컬럼이 전부 세컨더리 인덱스 안에 있으면 2단계 없이 인덱스만 읽고 끝난다 — 커버링 인덱스, 중급 문항에서 별도로 다룬다.)

2

비용에 이름 붙이기 — 페이지 분할 · 버퍼 풀 적재율 · 랜덤 I/O

▾

이 절이 이 문서의 심장이다. "세컨더리 인덱스가 PK를 품는다"는 구조 지식에서 PK 설계 2원칙이 저절로 나와야 하고, 그 비용을 뭉뚱그리지 않고 이름 → 사슬로 말할 수 있어야 한다. 면접에서 "메모리에 부하가 생긴다"와 "페이지당 엔트리 수가 줄어 버퍼 풀 적재율이 떨어지고 캐시 미스가 디스크 I/O로 번진다"는 전혀 다른 평가를 받는다.

먼저 등장인물 셋의 이름을 고정한다.

  • 버퍼 풀(buffer pool): 디스크 페이지를 담아두는 고정 크기 메모리 캐시. 필요한 페이지가 여기 있으면 메모리 속도, 없으면(캐시 미스) 디스크 I/O다. "적재율"은 같은 메모리에 실제 행이 몇 건 담기느냐는 밀도를 말한다 — 엔트리가 비대해지면 페이지 수가 늘고, 같은 버퍼 풀에 담기는 행 수가 줄어든다.
  • 페이지 분할(page split): 가득 찬 페이지의 중간에 끼워 넣어야 할 때, 페이지를 둘로 쪼개 절반을 새 페이지로 옮기는 작업. 쪼개는 비용 자체 + 반쯤 빈 페이지 두 개가 남는 단편화가 대가다.
  • 랜덤 I/O: 디스크의 흩어진 위치를 오가며 읽고 쓰는 접근. 연속된 페이지를 이어 읽는 순차 I/O보다 훨씬 비싸다(Q2의 비용 모델).

2-1. 원칙 ① 작게 — PK는 전체 인덱스 크기의 "곱셈 계수"다

세컨더리 인덱스의 모든 리프 엔트리에는 PK가 복제된다. 그러니 PK 크기는 어느 한 곳의 비용이 아니라 (행 수) × (세컨더리 인덱스 개수)만큼 곱해지는 계수다.

숫자로 보면: 1,000만 행 테이블에 세컨더리 인덱스가 5개일 때, PK가 8바이트(BIGINT)에서 100바이트(복합 PK)로 커지면 — (100 − 8)바이트 × 1,000만 행 × 5개 ≈ 4.6GB가 세컨더리 인덱스들에만 추가로 얹힌다. 클러스터드 인덱스의 브랜치 노드도 PK로 길잡이를 만드니 같이 비대해진다.

그리고 이 크기가 성능으로 번지는 사슬:

💡

PK가 크다 → 세컨더리 인덱스 엔트리가 비대해진다 → 16KB 페이지 하나에 들어가는 엔트리 수가 줄어든다 → 같은 데이터를 담는 데 페이지가 더 많이 필요하다(트리 높이도 올라갈 수 있다) → 고정 크기인 버퍼 풀에 담기는 "행의 수"(적재율)가 떨어진다 → 같은 쿼리를 쳐도 캐시 미스가 늘어난다 → 캐시 미스는 곧 디스크 I/O다.

"메모리 부하"라는 말은 이 사슬 전체를 뭉뚱그린 것이다. 면접에서는 사슬의 고리를 하나씩 짚어 말한다.

2-2. 원칙 ② 단조 증가 — 랜덤 PK는 페이지 분할을 부른다

클러스터드 인덱스는 PK 순서로 정렬을 유지한다. 그래서 삽입 위치는 PK 값이 결정한다.

  • 단조 증가 PK(AUTO_INCREMENT 등): 새 행은 항상 인덱스의 맨 끝. 마지막 페이지에 이어 붙이고(append), 그 페이지가 가득 차면 뒤에 새 페이지를 하나 붙일 뿐이다. 손대는 페이지가 늘 "맨 끝 한 장"이라 버퍼 풀에 항상 올라와 있고, 디스크에도 순차로 쌓인다.
  • 랜덤 PK(UUID v4 등): 새 행의 삽입 지점이 트리 전역에 흩어진다. 대상 페이지가 가득 차 있으면 페이지 분할 — 쪼개고, 절반을 옮기고, 부모 노드에 새 길잡이 키를 올린다. 그 결과가 세 갈래로 번진다:
💡

⑴ 분할 비용 자체 + 반쯤 빈 페이지들(단편화) → 같은 행 수에 페이지 수↑ → 적재율↓. ⑵ 새로 만든 페이지는 디스크에서 물리적으로 멀리 놓일 수 있다 → 리프 연결 리스트를 따라가는 범위 스캔이 순차 I/O에서 랜덤 I/O로 전락한다. ⑶ 가장 치명적: 삽입 지점이 전역에 흩어지므로 인덱스의 모든 리프 페이지가 워킹셋이 된다. 버퍼 풀이 인덱스 전체를 못 담으면, INSERT 한 건마다 대상 페이지를 디스크에서 읽어와야 쓸 수 있다 — 쓰기 작업이 읽기 I/O를 유발하는 역설. 이걸 버퍼 풀 오염이라 부른다.

접수창구 비유 — 번호표 순서로 서류를 서류철 맨 뒤에 끼우는 것(단조 증가)과, 이미 꽉 찬 서류철 중간을 벌려 끼워 넣으려고 서류철을 쪼개는 것(랜덤)의 차이다.

2-3. before / after — PK 설계로 보는 두 원칙

sql
-- ❌ before: 크고 랜덤한 PK
CREATE TABLE orders (
    id   CHAR(36) PRIMARY KEY,        -- UUID v4 문자열: 36바이트 + 무작위 순서
    ...
);
-- ① 모든 세컨더리 인덱스 엔트리에 36바이트가 복제 (곱셈 계수)
-- ② 매 INSERT가 트리 전역의 아무 페이지나 열어 페이지 분할 유발
--    → 단편화 + 전 리프가 워킹셋 → 버퍼 풀 오염 → INSERT가 읽기 I/O를 유발

-- ✅ after: 작고 단조 증가하는 PK + 외부 노출용 식별자 분리
CREATE TABLE orders (
    id        BIGINT AUTO_INCREMENT PRIMARY KEY,  -- 8바이트, 항상 맨 끝 append
    public_id BINARY(16) NOT NULL UNIQUE,         -- 외부 노출용은 세컨더리 유니크로
    ...
);
-- 내부 조인·FK·세컨더리 인덱스는 전부 8바이트 PK 기준으로 가볍게,
-- 외부에는 유추 불가능한 public_id만 노출.

(가산점 포인트) "PK를 UUID로 할까"라는 논쟁 자체를 우회하는 이 내부 PK / 외부 식별자 분리 패턴을 아는 것. 클러스터드 인덱스가 지는 비용은 내부용 작은 PK가 감당하고, 규모 유추 방지는 세컨더리 유니크 인덱스의 몫으로 넘긴다.

2-4. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

뭉뚱그린 표현이름사슬로 말하면
"메모리에 부하가 생긴다"버퍼 풀 적재율PK 복제 → 엔트리 비대 → 페이지당 엔트리↓ → 버퍼 풀에 담기는 행 수↓ → 캐시 미스↑ → 디스크 I/O↑
"왔다갔다 해서 성능 이슈"페이지 분할 + 랜덤 I/O랜덤 PK → 삽입 지점 전역 분산 → 가득 찬 페이지 쪼개기 → 단편화 + 전 리프가 워킹셋 → 버퍼 풀 오염 → INSERT마다 디스크 읽기
3

실무 사례 — "규모 유추 방지를 위해 PK를 UUID로 하자"는 제안

▾

연속 번호 PK를 외부에 노출하면 경쟁사가 "주문 번호가 하루에 얼마나 늘어나는지"로 규모를 유추할 수 있다 — 요건 자체는 정당하다. 문제는 UUID v4가 그 요건에 지불하는 대가가 '랜덤성'이라는 점이고, 2-2절에서 본 대로 랜덤성은 클러스터드 인덱스에 최악의 성질이다.

핵심 통찰: 요건이 요구하는 건 "유추 불가능"이지 "무작위 삽입 순서"가 아니다. 두 성질을 분리하는 대안이 있다.

  • 시간 순 정렬성이 있는 ID: Snowflake(64비트, 타임스탬프가 상위 비트라 단조 증가에 가깝고 BIGINT에 들어간다), UUID v7(타임스탬프 선두의 UUID — v4의 호환성을 유지하면서 삽입은 순차적). 둘 다 값 자체는 유추 불가능하면서 클러스터드 인덱스에는 append에 가깝게 꽂힌다.
  • 또는 2-3절의 내부 BIGINT PK + 외부 노출용 식별자 분리.

단, 시간 정렬 ID는 생성 시각이 값에 드러난다는 점은 알고 선택해야 한다. "총량·증가율 유추 방지"가 요건이면 충분하고, "생성 시각조차 숨겨야 한다"는 요건이면 분리 패턴 쪽이 맞다. 요건을 한 단계 쪼개서 어느 성질이 진짜 필요한지 되묻는 것 — 이게 시니어의 답변 태도다.

읽기 성능만 보면 물리 주소가 이긴다. 그러나 클러스터드 인덱스는 정렬 유지를 위해 페이지 분할 때마다 행을 물리적으로 이동시키는데, 물리 주소를 넣었다면 행 하나가 움직일 때마다 그 행을 가리키는 모든 세컨더리 인덱스를 찾아 고쳐야 한다. 세컨더리 인덱스가 5개면 행 이동 하나가 쓰기 5건으로 증폭된다. PK는 행이 어디로 가든 불변이므로 세컨더리 인덱스는 영향이 없다. 읽기 한 단계(북마크 룩업)를 내주고, 쓰기 증폭을 없앤 트레이드오프라고 양쪽을 다 말해야 완결된 답이다.

"곱셈 계수"부터 말한다 — PK는 5개 인덱스의 모든 리프 엔트리에 복제되므로, 행마다 100바이트 × 5 = 500바이트가 인덱스 쪽에 얹히고 1,000만 행이면 그것만 수 GB다. 이어서 사슬: 엔트리가 비대해져 16KB 페이지당 엔트리 수가 줄고, 같은 인덱스를 담는 데 페이지가 많아져 버퍼 풀 적재율이 떨어지고, 캐시 미스가 늘어 디스크 I/O가 는다. 쓰기 쪽도 마찬가지 — INSERT 한 번에 트리 6개(클러스터드 1 + 세컨더리 5)를 갱신하는데 엔트리가 크니 페이지가 빨리 차고 분할도 잦아진다. 처방은 복합 PK를 유니크 제약으로 내리고 작은 대리 키(BIGINT AUTO_INCREMENT) 를 PK로 세우는 것.

삽입 지점이 트리 전역에 흩어진다 → 대상 페이지가 가득 차 있으면 페이지 분할(쪼개기 + 절반 이동 + 부모 갱신) → 반쯤 빈 페이지가 쌓이는 단편화 → 그리고 인덱스의 모든 리프가 워킹셋이 되어 버퍼 풀이 못 담는 순간부터 INSERT 한 건마다 대상 페이지를 디스크에서 읽어와야 한다 (쓰기가 읽기 I/O를 유발). 대안은 시간 정렬성 있는 ID(Snowflake, UUID v7) 또는 내부 PK / 외부 식별자 분리. AUTO_INCREMENT와 달리 왜 UUID v4만 이런가를 물으면 — 삽입 위치를 PK 값이 결정하는 클러스터드 구조에서, 단조 증가는 "맨 끝 한 장"만 만지지만 랜덤은 "아무 장이나" 만지기 때문.

테이블 = 클러스터드 인덱스라는 명제 때문에 InnoDB는 클러스터드 인덱스 없이는 테이블을 만들 수 없다. PK가 없으면 ① 첫 번째 NOT NULL UNIQUE 인덱스를 클러스터드 인덱스로 승격하고, ② 그것도 없으면 내부적으로 6바이트짜리 숨은 row id를 만들어 클러스터드 인덱스를 구성한다. 숨은 row id는 개발자가 조회 조건으로 쓸 수 없으므로 세컨더리 인덱스 → 클러스터드 재탐색 구조의 이점을 하나도 못 누린다. 결론: 어차피 클러스터드 인덱스는 만들어지니, 그 축을 의도적으로 설계하라(명시적 PK).

아니다 — 클러스터드 테이블은 InnoDB의 설계 선택이지 RDB의 보편이 아니다. PostgreSQL의 테이블은 정렬 없는 힙(heap) 이고, 모든 인덱스가 행의 물리 위치(TID)를 직접 가리킨다. 그래서 조회는 인덱스 → 힙 한 번에 가지만(북마크 룩업의 2차 "트리 탐색"이 없다), 행이 이동하면 인덱스를 갱신해야 하는 InnoDB가 피해간 그 비용을 지불하며, HOT(Heap-Only Tuple) 같은 최적화로 완화한다. SQL Server는 클러스터드/힙을 테이블마다 선택할 수 있다. 이 비교를 할 수 있으면 "InnoDB의 논리 포인터는 쓰기 안정성과 읽기 단계 수를 맞바꾼 트레이드오프"라는 프레임으로 답의 격이 올라간다. 따라서 "UUID PK는 무조건 나쁘다"도 틀린 명제가 된다 — 힙 테이블에서는 랜덤 PK의 페이지 분할 문제가 클러스터드만큼 치명적이지 않다. 저장 엔진의 구조를 먼저 묻고 결론을 내리는 것이 시니어의 순서다.

✅ 한 줄 요약

InnoDB에서 테이블은 PK 순으로 정렬된 클러스터드 B+Tree 그 자체이고, 세컨더리 인덱스는 리프에 PK를 논리 포인터로 품어 2단계(북마크 룩업)로 조회한다. 이 구조에서 PK 설계 2원칙이 도출된다 — ① 작게(PK는 모든 세컨더리 인덱스에 복제되는 곱셈 계수 → 페이지당 엔트리↓ → 버퍼 풀 적재율↓ → 디스크 I/O↑), ② 단조 증가(랜덤 PK는 페이지 분할 → 단편화 + 버퍼 풀 오염). 비용은 뭉뚱그리지 말고 이 이름들의 사슬로 말한다.
