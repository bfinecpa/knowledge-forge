커버링 인덱스와 Index Only Scan
힙 페치를 0으로 만드는 대신 폭·쓰기·취약성을 치르고, 그 0은 visibility map이 지킨다

면접 질문: "커버링 인덱스란? 어떤 상황에서 효과가 큰가요?"

핵심 관전 포인트 — PostgreSQL의 인덱스 조회는 언제나 2단계다. ① 인덱스를 훑어 "조건에 맞는 행들의 힙 주소(TID)" 목록을 얻고 ② 그 TID를 들고 테이블 본체(힙)의 페이지를 행마다 한 장씩 읽는다. 이 ②를 힙 페치라 부르고, 커버링 인덱스란 쿼리가 필요로 하는 모든 컬럼(SELECT 목록 · WHERE · ORDER BY · 조인 키)이 인덱스 안에 들어 있어서 ②가 통째로 사라진 상태다 — 계획에는 Index Only Scan으로 찍힌다. 빠른 이유는 "테이블에 안 가서"가 아니라, 힙 페치가 행 1건마다 힙에 흩어진 8KB 페이지를 한 장씩 찌르는 랜덤 I/O인데 커버링은 그것을 좁은 리프 페이지 몇 장을 이어 읽는 것으로 바꾸기 때문이다. 단 PostgreSQL에는 조건이 하나 더 있다 — 인덱스는 그 행이 지금 내게 보이는 버전인지를 모르므로, visibility map에 "전부 가시"로 표시된 페이지만 힙 방문을 생략한다. Heap Fetches: N이 크면 커버링인데 안 빠른 상태이고, 그 N을 0으로 되돌리는 것은 VACUUM이다. 효과가 큰 조건은 "대상 행이 많고 · 필요한 컬럼이 좁고 · 자주 불리는" 쿼리(목록·랭킹·count(*)·페이징)이고, 대가는 인덱스 폭 증가(캐시 적재율 저하) · 실은 컬럼이 UPDATE될 때 HOT 탈락으로 모든 인덱스에 번지는 쓰기 증폭 · SELECT에 컬럼 하나만 추가해도 조용히 깨지는 취약성이다.
  • 1
    정의는 "인덱스만 읽고 끝"이 아니라 "2단계 중 2단계가 사라진 상태"다 — PostgreSQL의 인덱스 조회는 ① 인덱스를 훑어 TID 목록을 얻고 ② 그 TID로 힙 페이지를 행마다 읽는 2단계인데, 쿼리가 쓰는 모든 컬럼(SELECT · WHERE/ON · ORDER BY/GROUP BY)이 인덱스 안에 있으면 ②가 통째로 없어지고 계획에 Index Only Scan으로 찍힌다.
  • 2
    빠른 이유는 "테이블에 안 가서"가 아니라 랜덤 I/O N회가 사라져서다 — 힙은 정렬이 없어 인덱스에서 이웃한 행이 힙에서는 먼 페이지에 있다. N행이면 흩어진 8KB 페이지 N장을 따로 요청하는 랜덤 I/O N회인데, 커버링은 그것을 좁은 리프 N/수백 장을 이어 읽는 것으로 바꾼다. 이 비율이 "몇 배"의 정체다.
  • 3
    PostgreSQL에는 조건이 하나 더 붙고, 대가가 셋 있다 — 인덱스 리프에는 xmin/xmax가 없어 가시성을 모르므로, visibility map이 "전부 가시"로 표시한 페이지에서만 힙을 건너뛴다(Heap Fetches). 그리고 폭(캐시 적재율↓)·쓰기(HOT 탈락 → 모든 인덱스 갱신)·취약성(SELECT 컬럼 추가로 조용히 무효)을 치른다.

0. 질문 + 출제 의도

질문: "커버링 인덱스란? 어떤 상황에서 효과가 큰가요?"

출제 의도: 랭킹·목록 조회 같은 고빈도 쿼리를 힙 접근 없이 처리하는 핵심 기법. 아는 사람은 같은 하드웨어에서 몇 배의 처리량을 뽑는다. 즉 "인덱스만 읽고 끝난다"는 정의의 암기가 아니라, 왜 몇 배인지를 I/O 비용 모델(랜덤 vs 순차, 페이지 수)로 설명할 수 있는지, 그리고 그 몇 배를 위해 무엇을 지불하는지(폭·쓰기·취약성)를 함께 말해 "언제 쓰고 언제 쓰지 않는지"를 스스로 판단하는지를 본다. PostgreSQL에서는 한 겹 더 — "커버링을 만들었는데 왜 안 빠르죠?"에 visibility map과 VACUUM으로 답할 수 있는가.

이 페이지가 겨냥하는 약점 네 가지 ① "테이블에 안 가서 빠르다"에서 멈추는 것 → 2절에서 ⑴~⑹의 비용 사슬로 분해해 어느 고리가 끊기는지를 이름 붙여 말하게 한다.
② 편익만 말하고 대가를 못 말하는 것 → 6절의 폭 · 쓰기 · 취약 · 상한 네 대가와 한 호흡 템플릿으로 편익·대가를 한 문장에 넣는다.
③ PostgreSQL 고유 조건을 모르는 것 → 4절 전체가 visibility map · Heap Fetches · VACUUM이다. "계획 이름은 Index Only Scan인데 안 빠르다"가 이 문항의 실무 급소다.
④ "만들었으니 됐다"로 끝내는 것 → 7절에서 조용히 깨지는 취약성을 프로젝션 · EXPLAIN 단정 테스트 · 마이그레이션 주석 · 호출당 블록 수 알림 네 겹으로 막는다.
이 문서가 서 있는 토대 (이미 세운 세 문서) 이 문서는 한 줄 위에 서 있다 — "PostgreSQL의 인덱스 조회는 2단계이고, 2단계(힙 페치)는 랜덤 I/O다." 01-index-and-bplus-tree.md §4(리프에 무엇이 드는가) · 03-clustered-vs-secondary-index.md §1(인덱스 → TID → 힙 페치) · 02-index-not-used-full-scan.md §4(랜덤 vs 순차 손익분기)가 그 한 줄을 세운다. 아직 안 읽었어도 1절이 그 한 줄을 이 페이지 안에서 다시 세우므로 여기서부터 읽으면 된다.

1. 전제 — 인덱스 조회는 2단계이고, 커버링은 2단계를 없앤다

제목이 던지는 질문("어느 단계를 없애는가")에 답하려면 없앨 그 단계를 먼저 알아야 한다. 용어 셋을 여기서 정의하고 시작한다.

힙(heap) — 테이블 본체
"쌓아 둔 더미"라는 이름 그대로, 행이 정렬 없이 8KB 페이지에 들어온 순서대로 쌓인다. 정렬이 없다는 것이 이 문서 내내 비용의 원인이 된다.
TID — 힙 안 행 하나의 주소
(블록 번호 4바이트, 페이지 안 슬롯 번호 2바이트) = 6바이트. 시스템 컬럼 ctid로 눈에 보인다 — SELECT ctid, id FROM orders LIMIT 3; → (0,1), (1042,7).
힙 페치 — 없애려는 그 단계
인덱스에서 얻은 TID를 들고 그 블록의 힙 페이지를 실제로 읽어 오는 일. 이 문서의 모든 이야기가 이 한 동작을 0회로 만드는 일과 그 대가에 관한 것이다.

이제 "인덱스로 조회한다"가 실제로 무엇을 하는지 그림으로 본다. 쿼리는 SELECT id, created_at, amount FROM orders WHERE user_id = 7이고, 인덱스는 (user_id, created_at) 둘뿐이다.

1-1. 정의 — 세 군데의 컬럼이 전부 인덱스 안에 있어야 한다

쿼리가 쓰는 컬럼이 리프 엔트리 안에서 전부 해결되면 DB는 TID를 들고 힙으로 내려갈 이유가 없다. 이 상태의 인덱스를 그 쿼리에 대한 커버링 인덱스라 부른다. "덮는다(cover)"는 이름은 인덱스가 그 쿼리의 요구를 남김없이 덮는다는 뜻이다.

체크할 곳은 세 군데 — 셀 · 웨 · 오

셀 — SELECT 목록
화면에 그리는 컬럼. PK도 예외가 아니다(1-2).
웨 — WHERE / ON
필터 조건, 조인이면 조인 키까지.
오 — ORDER BY / GROUP BY
정렬·집계 기준. 이건 키 컬럼이어야 한다(5절).
세 군데 중 하나라도 인덱스 밖에 있으면 커버링이 아니다 — 그 하나 때문에 힙 페치 N회가 전부 부활한다

그리고 결정적인 성질 하나. 커버링은 인덱스의 종류가 아니라 인덱스와 쿼리의 관계다. 같은 인덱스가 어떤 쿼리에는 커버링이고 다른 쿼리에는 아니다. CREATE COVERING INDEX 같은 문법은 없다 — "커버링 인덱스"는 DDL의 이름이 아니라 상태의 이름이다. 이 한 줄이 뒤에 나올 취약성(6-4)의 뿌리이므로 지금 새겨 둔다.

1-2. PostgreSQL의 첫 함정 — PK도 공짜가 아니다

MySQL에서 넘어온 사람이 가장 먼저 밟는 지뢰

PostgreSQL 인덱스 리프에 있는 것은 PK 값이 아니라 TID다. 그래서 (user_id) 인덱스로 SELECT id FROM orders WHERE user_id = $1을 실행하면 — id 하나 가져오려고 힙에 간다. "PK는 당연히 커버되겠지"가 통하지 않는다.

PostgreSQL — 리프에 TID만

리프 엔트리 = (user_id, TID)

PK를 커버하려면 인덱스 정의에 명시해야 한다 → 그때 쓰는 문법이 INCLUDE(PostgreSQL 11+): 탐색·정렬에는 쓰지 않고 리프에만 싣는 컬럼 선언(5-1).

MySQL InnoDB — 리프에 PK가 들어 있다

리프 엔트리 = (인덱스 컬럼들, PK)

PK 컬럼은 정의에 안 써도 공짜로 커버된다. 뒤에 나올 지연 조인이 MySQL에서 "그냥 되는" 이유도 이것이다.

2. 비용 사슬 — "왔다갔다"를 I/O 단위로 분해한다

이 절이 이 문서의 심장이다. "테이블까지 안 가서 빠르다", "왔다갔다 안 해서 빠르다"는 결론만 말한 것이지 비용을 말한 게 아니다. 면접에서는 어느 고리가 끊겼는지를 이름을 붙여 말해야 한다.

2-1. 랜덤 I/O가 순차보다 왜 비싼가 — 세 축으로 고정한다

이 세 축이 비어 있으면 위 사슬의 ⑷~⑹이 전부 "그냥 느리다"로 뭉개진다.

① 요청 단위
랜덤은 8KB 페이지 1장마다 I/O 요청 1건이다. 순차는 이어진 페이지를 읽으므로 OS의 미리 읽기(readahead)가 다음 페이지들을 알아서 올려둔다. 흩어진 힙 페이지 접근에는 미리 읽기가 작동하지 않는다.
② 매체
HDD는 요청마다 헤드 이동 + 회전 대기가 붙어 차이가 수십 배다. SSD는 그 기계적 대기가 없지만 요청 1건당 고정 오버헤드(커널·드라이버·컨트롤러 경로)와 미리 읽기 불가는 그대로다 — 차이가 줄어들 뿐 사라지지 않는다.
③ 캐시
순차는 좁은 범위만 만지므로 캐시 히트율이 높고, 랜덤은 워킹셋이 넓어 미스율이 높다. 즉 랜덤 I/O는 디스크 비용이자 캐시 비용이다 — 남의 페이지까지 밀어낸다.
"SSD니까 랜덤도 괜찮다"는 절반만 맞다 기계적 대기가 사라진 것은 사실이지만 ②의 고정 오버헤드와 ①의 미리 읽기 불가는 남는다. PostgreSQL 운영에서도 SSD면 random_page_cost를 기본 4.0에서 낮추지만 seq_page_cost와 같은 1.0으로 만들지는 않는다 — 플래너의 기본 설정 자체가 "줄어들 뿐 사라지지 않는다"를 반영하고 있다.

2-2. 숫자 감각 — 세 사례로 자릿수를 잡는다

자릿수 감각용이지 정확한 상수가 아니다. 오른쪽 칸은 visibility map이 신선하다는 전제 위에 성립한다.
쿼리커버링이 아닐 때커버링일 때 (VM 신선)
내 주문 목록 LIMIT 20리프 1장 + 힙 랜덤 페치 20회리프 1장
랭킹 TOP 100리프 1~2장 + 힙 랜덤 페치 100회리프 1~2장
count(*) WHERE status = 'ACTIVE'
(90만 행 / 테이블 100만 행)		힙 페치 90만 회가 되니 플래너가 포기하고 테이블 100만 행 Seq Scan좁은 인덱스 리프 수천 장
Index Only Scan

세 번째 줄이 이 표의 핵심 — 커버링은 손익분기 자체를 옮긴다

대상 행이 많아 인덱스가 버려지던 쿼리(02-index-not-used-full-scan.md §4의 랜덤 vs 순차 손익분기)도, 커버링이면 인덱스 전체 스캔이 테이블 Seq Scan보다 싸다. 이유는 단순하다 — 인덱스가 테이블보다 훨씬 좁기 때문이다. 힙을 안 읽어도 되니 "인덱스 전부 + 힙 전부"가 아니라 "인덱스 전부"만 읽으면 되고, 그 인덱스는 테이블의 몇 분의 일이다.

커버링은 "힙 페치를 없앤다"에서 끝나지 않는다 — "인덱스를 쓸까 말까"의 경계선을 통째로 옮긴다
괄호 안의 전제를 절대 빼지 말 것 세 번째 줄의 "VM 신선"이 깨지면 그 칸은 도로 "힙 페치 90만 회"로 돌아간다. 그리고 플래너는 pg_class.relallvisible로 그 비율을 미리 알고 계획을 고르므로, VM이 낡으면 아예 Seq Scan을 고른다 — "어제는 인덱스로 세더니 오늘은 풀스캔"이 대량 갱신 뒤에 나타나는 이유다(4절).

2-3. 말하기 훈련 — 뭉뚱그린 표현을 이름 붙은 사슬로 교체

뭉뚱그린 표현붙여야 할 이름사슬로 말하면
"테이블까지 안 가서 빠르다"힙 페치 제거
(Index Only Scan)		필요한 컬럼이 인덱스 안에 있다 → TID로 힙 방문 0회 → 행마다 흩어진 페이지를 찌르던 랜덤 I/O N회가 → 좁은 리프 N/수백 장 읽기로. 단 visibility map이 "전부 가시"인 페이지에 한해.
"왔다갔다 해서 느리다"랜덤 I/O + 워킹셋 확대인덱스 정렬 순서 ≠ 힙 순서(무정렬) → 이웃 엔트리의 행이 먼 페이지 → 요청 1건당 페이지 1장 → 미리 읽기 무용 → 워킹셋 = 테이블 전체 → 캐시 미스 → 디스크 랜덤 읽기.
비유로 한 번 더 — 도서관의 색인 카드와 서가 색인 카드(인덱스)에는 "제목 · 청구기호"만 적혀 있고 카드는 제목 순으로 가지런히 꽂혀 있다. "제목이 ㄱ으로 시작하는 책의 청구기호를 다 알려줘"는 카드만 넘기면 끝난다(= 커버링). 그런데 "그 책들의 출판사도 알려줘"는 카드에 없으니 서가로 가야 한다. 문제는 서가가 들어온 순서대로 꽂혀 있다는 것 — 제목 순으로 나란한 스무 권이 서가에서는 1층·4층·지하·3층에 흩어져 있어 스무 번을 뛰어다녀야 한다. 이 뜀박질이 힙 페치이고, 랜덤 I/O다.

3. 효과 공식과 "효과 큰 상황 5종"

"어떤 상황에서 효과가 큰가요?"는 질문의 후반부다. 목록을 외우기 전에 공식 하나를 세우면 목록이 저절로 도출된다 — 그리고 효과가 없는 상황도 같은 공식에서 나온다.

암기 목록 ① — 효과 큰 상황 5종: 많이 · 좁게 · 자주 · 세기 · 정렬

1
많이 — 대상 행이 많다. 범위 조회, 낮은 선택도 조건. 힙 페치 횟수 N 자체가 크다. 극단에서는 인덱스 전체 스캔이 Seq Scan을 이긴다(2-2).
2
좁게 — 필요한 컬럼이 좁다. 목록 카드·랭킹 행처럼 2~4개의 짧은 컬럼만 쓴다. jsonb·text가 많은 넓은 테이블에서 좁은 컬럼만 뽑을수록 상대 이득이 커진다.
3
자주 — 호출 빈도가 높다. 메인 목록 API, 랭킹 보드, 홈 화면. 출제 의도의 "같은 하드웨어에서 몇 배"는 여기서 실현된다.
4
세기 — 값이 아니라 개수·합만 필요하다. count(*) / EXISTS / sum(amount) 같은 집계, 또는 조인에서 조인 키와 필터 컬럼만 필요한 안쪽(inner) 테이블. 06-join-types-and-execution.md의 "안쪽이 Index Only Scan이면 Nested Loop가 다시 유리해진다"가 이 항목이다.
5
정렬 — 정렬·페이징을 인덱스에서 끝낸다. ORDER BY … LIMIT, 키셋 페이지네이션. 정렬 컬럼까지 인덱스 키에 있어야 커버링과 Sort 노드 제거가 동시에 성립한다.

3-1. before / after — 목록 조회 한 건으로

화면은 "내 주문 목록"이고, 카드에 id·created_at·amount 세 컬럼만 그린다. 테이블은 orders (id, user_id, status, created_at, amount, memo, …).

before 탐색용 인덱스 + SELECT * — "Only"가 없다
-- 탐색·정렬만 노린 인덱스
CREATE INDEX idx_orders_user_created
    ON orders (user_id, created_at);

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders                    모든 컬럼
WHERE user_id = 7
ORDER BY created_at DESC LIMIT 20;

--  Limit  (actual rows=20 loops=1)
--    ->  Index Scan Backward using …      ← "Only"가 없다
--          Index Cond: (user_id = 7)
--          Buffers: shared hit=23        ← 인덱스 3 + 힙 20

-- 정렬은 인덱스가 해결했다(Sort 노드 없음).
-- 그러나 행마다 TID로 힙 페이지를 한 장씩 찔렀다.
after 화면이 쓰는 컬럼을 INCLUDE로 리프에 싣는다
-- 접두사가 같은 기존 인덱스는 추가가 아니라 "교체"(중복 방지).
-- 운영 중이면 CONCURRENTLY. id(PK)도 공짜가 아니라 명시한다.
CREATE INDEX CONCURRENTLY idx_orders_user_created_cover
    ON orders (user_id, created_at) INCLUDE (id, amount);
DROP INDEX CONCURRENTLY idx_orders_user_created;

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, amount FROM orders  세 컬럼만
WHERE user_id = 7
ORDER BY created_at DESC LIMIT 20;

--  Limit  (actual rows=20 loops=1)
--    ->  Index Only Scan Backward using …
--          Index Cond: (user_id = 7)
--          Heap Fetches: 0    ← 힙 방문 0회
--          Buffers: shared hit=3   ← 인덱스 페이지만
버퍼가 23 → 3. 줄어든 그 20이 정확히 1절 그림의 2단계다

설계할 때 헷갈리지 않는 한 줄 — 앞쪽은 "찾기 위한" 컬럼, 뒤쪽은 "나르기 위한" 컬럼

amount는 조건에도 정렬에도 안 쓰인다. 그래도 커버링에 기여한다 — 뒤쪽·INCLUDE 컬럼은 탐색에 기여하지 않아도 리프에 실려 있기만 하면 된다. 이걸 "실어 나르는(payload) 컬럼"이라고 생각하면 설계가 단순해진다.

앞쪽 키 컬럼 = 찾기 위한 것·등호 → 범위/정렬 순 (08-composite-index-column-order.md의 "등·범·정·커")
INCLUDE = 나르기 위한 것·탐색·정렬에는 절대 못 쓰지만, 힙 페치를 없애는 데는 똑같이 기여한다

복합 인덱스 순서 규칙의 마지막 글자 "커"가 바로 이 문서다 — 등호 · 범위 · 정렬 다음에 커버링용 컬럼.

4. PostgreSQL만의 두 번째 조건 — visibility map이 없으면 힙을 다시 읽는다

여기가 이 문서에서 가장 실무적인 대목이고, 이 문항에서 PostgreSQL과 다른 DB의 답이 갈리는 지점이다. 다른 DB에는 없는 조건이 PostgreSQL에만 하나 더 붙는다.

4-1. 왜 조건이 하나 더 필요한가 — 인덱스는 "값"은 알아도 "가시성"은 모른다

전제 — PostgreSQL은 MVCC를 힙 안에서 구현한다

  • UPDATE는 제자리 수정이 아니다. 옛 튜플에 "죽었다"고 표시하고 새 버전을 삽입한다.
  • "이 버전이 지금 이 트랜잭션에 보이는가"를 판정할 정보(xmin/xmax)는 힙 튜플의 헤더에만 있다.

귀결 — 인덱스만 읽고 답하면 틀린 답이 나갈 수 있다

  • 리프에는 (컬럼 값들, TID)뿐 — xmin/xmax가 없다.
  • 심지어 이미 죽은 옛 버전을 가리키는 엔트리도 VACUUM이 치우기 전까지 그대로 남는다.
  • 즉 이미 삭제된 행을 결과에 섞어 내보낼 수 있다.

그렇다고 행마다 힙에 물으면 커버링이 무의미해진다. 그래서 PostgreSQL은 페이지 단위 요약본을 하나 둔다.

4-2. 직접 재현 — 계획 이름은 그대로인데 속도만 커버링 이전으로 돌아간다

A VACUUM 직후 — VM 비트가 서 있다
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, amount FROM orders
WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20;

--  Limit  (actual rows=20 loops=1)
--    ->  Index Only Scan Backward using idx_..._cover
--          Index Cond: (user_id = 7)
--          Heap Fetches: 0        ← 힙 방문 0회
--          Buffers: shared hit=3  ← 인덱스 3장이 전부
B 인덱스와 아무 상관 없는 컬럼을 갱신한 뒤
UPDATE orders SET memo = 'gift' WHERE user_id = 7;
-- memo는 어떤 인덱스에도 없으니 HOT 업데이트다(인덱스는 안 건드린다).
-- 그래도 힙 페이지의 내용이 바뀐 것은 사실이므로 → VM 비트가 꺼진다.

-- 같은 쿼리 · 같은 인덱스 · 같은 계획 이름
--  Limit  (actual rows=20 loops=1)
--    ->  Index Only Scan Backward …  ← 이름은 그대로다!
--          Index Cond: (user_id = 7)
--          Heap Fetches: 20       ← 힙을 20장 읽었다
--          Buffers: shared hit=23 ← 커버링 만들기 전과 똑같다

VACUUM orders;  -- 죽은 튜플 회수 + VM 갱신
-- 다시 실행 → Heap Fetches: 0, Buffers: 3 으로 복귀

세 줄 결론 — 이 세 줄이 4절의 전부다

① Index Only Scan이라는 계획 이름은 "컬럼이 전부 인덱스에 있다"까지만 보장한다.
② 힙을 실제로 건너뛰었는지는 Heap Fetches만이 말해 준다.
③ 그 값을 0으로 되돌리는 것은 인덱스 설계가 아니라 VACUUM이다.
EXPLAIN은 반드시 (ANALYZE, BUFFERS)로 돌린다 ANALYZE 없이는 Heap Fetches가 아예 출력되지 않는다 — 실행해 봐야 아는 값이기 때문이다. 그리고 BUFFERS 없이는 그 20이 실제 페이지 비용으로 얼마인지가 안 보인다. 이 문항에서 EXPLAIN만 말하면 절반이고, EXPLAIN (ANALYZE, BUFFERS)라고 말하면 실제로 진단해 본 사람으로 들린다.

4-3. Heap Fetches가 큰 원인 3종 — 대응이 각각 다르다

암기 목록 ② — 밀 · 롱 · 인 (autovacuum 밀림 · 롱 트랜잭션 · INSERT만)

밀
autovacuum이 밀렸다 — 대량 갱신 직후에 흔하다. pg_stat_user_tables의 n_dead_tup이 크고 last_autovacuum이 오래됐으면 이 경우다.
대응: 수동 VACUUM 후, 그 테이블만 autovacuum_vacuum_scale_factor를 낮춘다.
롱
롱 트랜잭션 — 오래 열린 트랜잭션이 pg_stat_activity.backend_xmin을 잡고 있으면 VACUUM이 돌아도 그보다 나중의 죽은 튜플을 못 치우고 VM도 못 세운다.
대응: VACUUM 튜닝으로는 안 풀린다. 트랜잭션을 끊어야 풀린다(16-long-transaction-harm-and-shortening.md). 시니어 변별
인
INSERT만 쌓이는 테이블 — 죽은 튜플이 없어 옛 버전 PostgreSQL에서는 autovacuum이 아예 안 돌았다. PostgreSQL 13부터는 INSERT 양으로도 기동한다(autovacuum_vacuum_insert_threshold).

왜 원인을 갈라야 하나 — 셋 다 증상이 Heap Fetches 폭증으로 똑같은데 대응이 완전히 다르기 때문이다. "롱"을 "밀"로 오진하면 VACUUM을 아무리 돌려도 낫지 않는다.

빠른 확진 한 줄 — pg_class의 relallvisible / relpages VM 비트가 선 페이지의 비율이다. 이 비율이 낮으면 플래너도 Index Only Scan의 이득을 낮게 잡아 아예 다른 계획을 고르기 시작하므로, "어느 날부터 커버링 인덱스를 안 탄다"의 원인이기도 하다(31-execution-plan-sudden-change.md). 즉 이 한 숫자가 두 가지 증상을 동시에 설명한다 — "계획은 맞는데 안 빠름"과 "계획 자체가 바뀜".

5. 계획 읽기 3종과 INCLUDE vs 키 컬럼

PostgreSQL에서는 스캔 노드 이름 + Heap Fetches + Index Cond/Filter를 함께 읽는다. 셋 중 하나만 보면 반드시 오진한다.

암기 목록 ③ — 계획 3종

계획뜻힙 방문
Index Only Scan + Heap Fetches: 0커버링 완성 — 인덱스만 읽고 끝0회
Index Only Scan + Heap Fetches: N컬럼은 다 인덱스에 있으나 가시성 확인을 위해 힙에 감 — 값이 아니라 "보이는가"를 물으러N회
VM이 낡은 페이지의 행 수만큼
Index Scan + Index Cond (+Filter)컬럼을 힙에서 가져와야 함. Index Cond는 인덱스 단계에서 걸러 힙 방문을 줄이고, Filter는 힙에 갔다 와서 버린다통과한 행 전부

두 번째 줄이 PostgreSQL 고유의 함정이고(4절), 세 번째 줄은 커버링을 못 만들었을 때의 차선과 최악의 구분이다.

5-1. 같은 컬럼을 넣는 두 가지 방법 — 트리 어디까지 실리는가

커버링을 만들려고 컬럼을 인덱스에 넣는 방법은 둘이다. 키 컬럼으로 붙이거나, INCLUDE로 붙이거나. 차이는 "트리의 어디까지 실리는가" 하나에서 전부 갈라져 나온다.

5-2. DDL 두 벌로 대비한다 가산점

가 키 컬럼으로 붙인다
CREATE INDEX idx_a
    ON orders (user_id, created_at, id, amount);

-- 1) id, amount가 정렬 기준에 참여한다
--    → 내부(비리프) 페이지에도 실려 트리가 뚱뚱해지고
--      비교 비용도 늘어난다
-- 2) 유니크 인덱스였다면 유일성 판정에까지 참여한다
--    → 제약의 의미 자체가 바뀐다
-- 3) 비교 연산자(연산자 클래스)가 정의된 타입만 넣을 수 있다
-- 4) 그 대신 (user_id, created_at, id)까지가 접두사이므로
--    키셋 페이지네이션의 타이브레이커로 id를 쓸 수 있다
나 INCLUDE로 붙인다 (PostgreSQL 11+)
CREATE INDEX idx_b
    ON orders (user_id, created_at) INCLUDE (id, amount);

-- 1) id, amount는 리프에만 실린다
--    → 내부 페이지는 2컬럼 그대로, 트리의 폭·높이 유지
-- 2) 정렬·유일성 판정에 참여하지 않는다
--    → 유니크 인덱스에도 그대로 덧붙일 수 있다
-- 3) 비교 연산자가 없는 타입도 실을 수 있다
-- 4) 그 대신 탐색·정렬에는 절대 못 쓴다
--    (Index Cond에 등장하지 않는다)

선택 기준은 한 줄 — "찾거나 · 정렬하거나 · 비교하면 키, 싣기만 하면 INCLUDE"

WHERE에 쓴다
→ 키 컬럼
ORDER BY에 쓴다
→ 키 컬럼
키셋 비교에 쓴다
→ 키 컬럼

키셋 페이지네이션의 타이브레이커로 id를 쓸 계획이면 (user_id, created_at, id) INCLUDE (amount)처럼 id만 키로 올린다. — "전부 키" 또는 "전부 INCLUDE"가 아니라 컬럼마다 용도로 가른다.

함정 둘 — "나르기용이니 공짜겠지"와 "아무 인덱스나 되겠지"

INCLUDE 컬럼도 HOT 판정에서는 인덱스 컬럼이다

INCLUDE 컬럼이 바뀌는 UPDATE는 HOT에서 탈락한다(6-3). "나르기용이니 갱신 비용은 없겠지"는 틀렸다. 정렬·탐색에서 빠졌을 뿐, 쓰기 대가는 키 컬럼과 똑같이 낸다.

Index Only Scan은 B-tree 이야기다

Index Only Scan은 인덱스가 원래 값을 돌려줄 수 있어야 성립한다. B-tree는 되지만 GIN·BRIN은 불가하다 — 둘 다 원본 값이 아니라 요약본을 들고 있기 때문이다. 커버링 설계는 사실상 B-tree 설계다.

6. 대가 4종 — 폭 · 쓰기 · 취약 · 상한

편익만 말하면 반쪽 답이다. 커버링 인덱스는 읽기의 랜덤 I/O를 인덱스 폭 + 쓰기 비용 + 유지보수 취약성으로 바꾸는 거래이고, 면접관은 후자를 말하는지 반드시 본다.

대가한 줄 이유
폭나르기용 컬럼을 실으면 리프 엔트리가 커지고, 그만큼 8KB 페이지에 들어가는 엔트리 수가 줄어 같은 행 수를 읽는 데 페이지가 더 필요해진다. 커버링으로 번 이득을 스스로 조금 갉아먹고, 캐시에서 남의 페이지까지 밀어낸다.
쓰기실은 컬럼이 UPDATE되면 그 UPDATE가 HOT에서 탈락하고, PostgreSQL은 새 튜플이 새 TID를 받으므로 그 테이블의 모든 인덱스에 새 엔트리를 꽂는다. 인덱스 하나 몫이 아니라 전부 몫이다.
취약커버링은 인덱스의 성질이 아니라 인덱스와 쿼리의 관계라서(1-1), 인덱스를 안 건드려도 쿼리 쪽이 바뀌면 깨진다. SELECT 목록에 컬럼 하나만 늘어도 끝이고, 에러도 경고도 없다.
상한B-tree 엔트리는 페이지의 약 1/3을 넘을 수 없다. 큰 text/jsonb는 애초에 실을 수 없고, 실으려 하면 INSERT 시점에 에러가 난다.

6-2. 폭 — 넓어진 인덱스는 커버링의 이득 일부를 스스로 갉아먹는다

나르기용 컬럼 추가→ 리프 엔트리↑→ 8KB 페이지당 엔트리 수↓→ 같은 범위에 리프 페이지 수↑→ 캐시 적재율↓→ 다른 인덱스·힙 페이지를 밀어낸다

03-clustered-vs-secondary-index.md의 "엔트리 폭 → 페이지당 엔트리 수 → 캐시 적재율" 사슬과 같은 것이다. 그래서 원칙은 필요한 컬럼만, 짧은 타입만이다. text 제목이나 numeric 여러 개를 "혹시 쓸지 모르니" 싣는 순간 2절의 "N/수백 장"이 "N/수십 장"으로 줄어들고 이득이 반감된다.

INCLUDE가 내부 노드는 지켜 주지만 리프의 폭은 그대로 늘어난다 — 폭은 문법으로 피할 수 없는 대가

6-3. 쓰기 — 실은 컬럼이 UPDATE되는 순간 그 테이블의 모든 인덱스가 움직인다

인덱스에 없던 컬럼은 UPDATE해도 인덱스가 움직이지 않았다. 커버링을 위해 그 컬럼을 실은 순간부터는 다르다 — 그리고 PostgreSQL에서는 그 대가가 그 인덱스 하나에 머물지 않는다.

먼저 용어 — HOT(Heap-Only Tuple) 업데이트 바뀐 컬럼이 어떤 인덱스에도 안 들어 있고 새 버전을 같은 힙 페이지에 놓을 자리가 있을 때, 인덱스를 하나도 안 건드리고 힙 페이지 안에서만 끝내는 UPDATE다. "힙에만 사는 튜플"이라는 이름 그대로, 인덱스는 이 새 버전의 존재를 모른 채 옛 엔트리로 계속 도달한다.
비유 — 같은 방 안에서 가구 위치만 바꾸면(HOT) 주소록을 안 고쳐도 된다.
다른 집으로 이사하면(HOT 탈락) 주소가 바뀌니 모든 주소록을 다 고쳐야 한다.
실은 컬럼이 UPDATE된다→ PostgreSQL UPDATE = 새 튜플 버전 삽입→ 어떤 인덱스에라도 들어 있으면 HOT 탈락
(INCLUDE 컬럼 포함)
새 튜플 = 새 TID→ 그 테이블의 모든 인덱스에 새 엔트리→ 옛 엔트리는 죽은 버전을 가리킨 채 남음 (인덱스 bloat)→ 그 힙 페이지의 VM 비트가 꺼진다
즉 자주 바뀌는 컬럼을 싣는 것은 쓰기 증폭과 읽기 커버링 약화를 동시에 사는 일이다

08-composite-index-column-order.md의 "상태 5번 × 인덱스 5개 = 인덱스 쓰기 25번"이 여기서 그대로 재현된다. 다른 점은 하나 — 거기서는 "인덱스를 늘리면"이었고, 여기서는 "인덱스에 컬럼 하나를 더 실으면"이다.

before "화면에 다 보이니까" 자주 바뀌는 컬럼까지 실었다
CREATE INDEX idx_orders_user_cover
    ON orders (user_id, created_at)
    INCLUDE (id, amount, status, updated_at);

-- status    → 주문 상태 전이마다 바뀐다
-- updated_at → 모든 UPDATE마다 바뀐다

-- 그때마다:
--   HOT 탈락 → 이 테이블의 모든 인덱스에 새 엔트리
--            → 인덱스 bloat
--            → 그 페이지의 VM 비트 해제 → Heap Fetches↑
-- = 읽기에서 번 랜덤 I/O를 쓰기로 도로 지불한다
after 생성 후 거의 안 바뀌는 컬럼만 싣는다
CREATE INDEX idx_orders_user_cover
    ON orders (user_id, created_at) INCLUDE (id, amount);

-- 자주 바뀌는 컬럼(status, updated_at)은
--   ⑴ 화면 요구를 재협상하거나
--      (목록엔 상태를 안 보여주고 상세에서 본다)
--   ⑵ 별도 조회로 뺀다

-- 판단 기준 한 줄:
--   "이 컬럼은 행이 만들어진 뒤 몇 번 바뀌는가?"
-- 실측: pg_stat_user_tables 의 n_tup_upd 대비 n_tup_hot_upd
--   인덱스 추가 뒤 HOT 비율이 떨어졌다면 그 컬럼이 범인이다
MySQL 대조 — 같은 대가를 훨씬 싸게 낸다 InnoDB는 바뀐 컬럼이 들어 있는 그 세컨더리 인덱스만 옛 엔트리 삭제 표시 + 새 엔트리 삽입으로 갱신한다(행은 제자리 갱신 + 언두 로그). 같은 대가가 MySQL에서는 인덱스 하나 몫, PostgreSQL에서는 테이블의 인덱스 전부 몫이다.

6-4. 취약 — SELECT에 컬럼 하나 추가하면 에러 없이 조용히 깨진다

가장 실무적인 대가다. 커버링은 인덱스와 쿼리의 관계라서, 쿼리 쪽이 바뀌면 인덱스는 그대로여도 관계가 깨진다.

진짜 무서운 것은 이 쿼리가 아니다 목록 20건이면 힙 페치 20회라 사람이 체감하지도 못한다. 문제는 같은 인덱스를 커버링으로 믿고 있던 다른 쿼리들이다 — 랭킹 TOP 1,000이면 힙 페치 1,000회, 집계 쿼리면 수만 회가 부활한다. p99 지연 그래프만 조용히 올라가고, 원인이 6개월 전 DTO에 필드 하나 추가한 커밋이라는 사실은 아무도 연결하지 못한다.
그리고 JPA는 이 취약성을 구조적으로 안고 있다 — 엔티티를 조회하면 모든 컬럼을 SELECT하므로 엔티티 조회는 절대 커버링이 되지 않는다

6-5. 상한과 중복 — 넣을 수 없는 것, 흉내 낼 수 없는 것, 교체해야 하는 것

엔트리 크기 상한
B-tree 엔트리는 페이지의 약 1/3(8KB 페이지에서 약 2,700바이트)을 넘을 수 없다 — 트리가 성립하려면 내부 페이지 하나에 최소 몇 개의 키가 들어가야 하기 때문이다. 긴 text를 키나 INCLUDE에 넣으면 그 행을 INSERT하는 순간 "index row size … exceeds … maximum" 에러가 난다. 큰 text/jsonb가 필요한 화면은 커버링 대상이 아니다.
접두사 인덱스가 없다
MySQL의 title(30) 같은 문법이 PostgreSQL에는 없다. 흉내는 표현식 인덱스 (left(title, 30))인데, title 전체를 들고 있지 않으므로 title을 SELECT하는 쿼리를 커버할 수 없다.
중복 인덱스 — 추가가 아니라 교체
(user_id, created_at)가 있는데 … INCLUDE (id, amount)를 추가하면 접두사가 같은 중복이다. 교체 전에 기존 인덱스를 쓰던 다른 쿼리를 pg_stat_user_indexes.idx_scan으로 확인하고, CREATE INDEX CONCURRENTLY → DROP INDEX CONCURRENTLY로 잠금 없이 바꾼다.
CONCURRENTLY의 제약(트랜잭션 블록 불가, 실패 시 INVALID 잔존)은 14-online-ddl-zero-downtime-schema-change.md.

6-6. 한 호흡 템플릿 — 편익과 대가를 한 문장에

이 문장이 입에서 그대로 나오면 "편익만 서술"이라는 약점은 이 문항에서 재발하지 않는다

"커버링 인덱스는 읽기에서 힙 페치 N회, 즉 랜덤 I/O N회를 0으로 만들어 몇 배의 처리량을 얻는 대신 — PostgreSQL에선 그 0이 visibility map이 신선할 때만 성립하고 — 폭(엔트리 비대 → 캐시 적재율↓)·쓰기(실은 컬럼 UPDATE마다 HOT 탈락으로 모든 인덱스 갱신)·취약성(SELECT에 컬럼 하나 추가로 조용히 무효)을 치릅니다. 그래서 '많이 읽고, 좁게 쓰고, 자주 불리는' 쿼리에, 거의 안 바뀌는 컬럼만 INCLUDE로 실어 제한적으로 씁니다."

7. 안전망 4종 — 깨짐을 사람이 아니라 기계가 잡게 한다

7-1. ⑴ 코드 — DTO 프로젝션으로 SELECT 목록을 타입에 고정한다

before 엔티티 조회 — 어떤 인덱스로도 커버 불가
List<Order> findByUserIdOrderByCreatedAtDesc(
        Long userId, Pageable pageable);

// → SELECT o.id, o.user_id, o.status, o.created_at,
//           o.amount, o.memo, …
//    FROM orders o …

// 모든 컬럼을 SELECT하므로 커버링이 원천적으로 불가능하다.
// 그리고 컬럼이 늘어나도 이 코드는 한 글자도 안 바뀐다
// = diff에 드러나지 않는다.
after 닫힌 인터페이스 프로젝션 — 여기 선언한 getter만 SELECT
public interface OrderCard {
    Long getId();
    OffsetDateTime getCreatedAt();  // timestamptz 매핑
    BigDecimal getAmount();
}
List<OrderCard> findByUserIdOrderByCreatedAtDesc(
        Long userId, Pageable pageable);

// → SELECT o.id, o.created_at, o.amount FROM orders o
//    WHERE o.user_id = ? ORDER BY o.created_at DESC LIMIT ?
// idx_orders_user_created_cover
//   (user_id, created_at) INCLUDE (id, amount) 에 정확히 덮인다
핵심은 프로젝션 타입이 곧 SELECT 목록의 계약이라는 것 — 컬럼을 추가하려면 이 타입을 고쳐야 하고, 그 diff가 리뷰에 드러난다

@Query("select new …OrderCard(o.id, o.createdAt, o.amount) …")의 클래스 기반 DTO나 QueryDSL Projections.constructor도 같은 효과다. 중요한 것은 문법이 아니라 "SELECT 목록이 타입 선언에 묶여 있다"는 성질이다.

7-2. ⑵ CI — 실행 계획을 단정하는 통합 테스트

프로젝션을 고쳐도 사람이 "이거 커버링 깨지는데?"를 떠올려야 한다면 아직 기억 의존이다. 실행 계획 자체를 테스트가 단정하게 한다.

test Testcontainers PostgreSQL 위에서 실행
@Test
void 주문목록_조회는_Index_Only_Scan을_탄다() throws Exception {
    // 행이 수백 건뿐이면 플래너가 Seq Scan을 고르는 게 정상이라 거짓 실패한다 → 실전 규모 시드
    seedOrders(200_000);
    // 통계(플래너 판단용) + visibility map(Heap Fetches 0의 전제)을 한 번에 갱신한다
    jdbcTemplate.execute("VACUUM ANALYZE orders");

    // JPA가 실제로 내보내는 SQL(p6spy 로그에서 확보)을 그대로 EXPLAIN 한다
    String plan = jdbcTemplate.queryForObject(
        "EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) "
      + "SELECT o.id, o.created_at, o.amount FROM orders o "
      + "WHERE o.user_id = 7 ORDER BY o.created_at DESC LIMIT 20", String.class);
    JsonNode scan = objectMapper.readTree(plan).at("/0/Plan/Plans/0");   // Limit 아래 첫 자식

    assertThat(scan.at("/Node Type").asText()).isEqualTo("Index Only Scan");   // 깨지면 "Index Scan"
    assertThat(scan.at("/Index Name").asText()).isEqualTo("idx_orders_user_created_cover");
    assertThat(scan.at("/Heap Fetches").asInt()).isZero();   // VACUUM 직후이므로 0이어야 정상
}

이 테스트에서 사람들이 밟는 지뢰 셋

1
단정 대상을 잘못 고른다. 단정은 Node Type·Index Name처럼 구조적으로 결정되는 값에 한정한다 — 비용·추정 행 수는 통계에 따라 흔들리고, Heap Fetches는 직전에 VACUUM을 돌렸을 때만 단정할 수 있다.
2
EXPLAIN 대상 SQL이 진짜가 아니다. 반드시 JPA가 실제로 내보낸 문장이어야 한다(p6spy·datasource-proxy 로그로 확보). 손으로 옮겨 적은 SQL은 테스트만 통과하고 운영은 안 지킨다.
3
VACUUM은 트랜잭션 블록 안에서 실행할 수 없다. 테스트 메서드에 @Transactional을 걸면 실패한다. 그리고 무거우니 커버링이 곧 SLA인 쿼리 몇 개에만 건다.

7-3. ⑶ 설정 — 마이그레이션 파일에 존재 이유를 박는다

인덱스 정의는 Flyway/Liquibase 마이그레이션이라는 코드로 관리되므로, "이 인덱스가 누구를 위해 존재하는지"를 그 파일 안에 남길 수 있다.

config V37__orders_user_created_cover.sql
-- [COVERING] OrderCard 프로젝션(id, created_at, amount) 전용 커버링 인덱스.
--   키 2컬럼 = 탐색·정렬용, INCLUDE = 나르기용(id는 PK지만 PG 리프엔 TID뿐이라 명시).
--   OrderCard에 컬럼을 추가하면 커버링이 깨진다 → OrderCoveringIndexTest가 실패한다.
--   자주 바뀌는 컬럼(status, updated_at)은 HOT 탈락을 피하려고 의도적으로 제외(6-3).
--   CONCURRENTLY는 트랜잭션 밖에서만 가능 → 이 파일은 비트랜잭션 마이그레이션으로 표시.
CREATE INDEX CONCURRENTLY idx_orders_user_created_cover
    ON orders (user_id, created_at) INCLUDE (id, amount);
이름 규약도 설정의 일부다 — _cover 접미사 _cover를 붙여 두면 리뷰어가 이름만 보고 "나르기용 컬럼이 실린 인덱스"임을 알고, \d orders나 pg_indexes 조회에서도 "왜 amount가 INCLUDE에 있지? 지워도 되나?"라는 오판을 막는다. 주석은 파일 안에만 있지만, 이름은 DB 안에서도 보인다.

7-4. ⑷ 운영 — 호출당 블록 수 알림, 마지막 그물

앞의 세 겹을 다 뚫고 배포된 뒤에도 에러는 나지 않는다. 그래서 관측이 마지막 그물이다.

pg_stat_statements
해당 쿼리(queryid)의 호출당 읽은 블록 수 (shared_blks_hit + shared_blks_read) / calls가 기준선 대비 튀면 알림이 오게 둔다 — 커버링이 깨지면 반환 행 수는 그대로여도 힙 블록이 행 수만큼 추가되어 자릿수가 바뀐다.
auto_explain
log_min_duration · log_analyze · log_buffers를 켜 두면 느려진 쿼리의 계획이 로그에 남아 Index Only Scan → Index Scan 전환이나 Heap Fetches 폭증을 확진할 수 있다.
이 지표는 혼자서는 원인을 못 가른다 시니어 변별 호출당 블록 수는 ⑴ 커버링이 깨졌을 때와 ⑵ VM이 낡았을 때 똑같이 오른다. 그래서 n_dead_tup·last_autovacuum을 같이 봐서 둘을 가른다. 그리고 두 원인을 최종적으로 구분해 주는 것은 auto_explain이 남긴 계획이다 — 노드 이름이 Index Scan으로 바뀌었으면 ⑴, Index Only Scan 그대로인데 Heap Fetches만 커졌으면 ⑵.
반대 방향도 본다 — 안 쓰이는 커버링 인덱스는 순수한 손실이다 pg_stat_user_indexes에서 _cover 인덱스의 idx_scan이 0에 머물면 쿼리 쪽이 바뀌어 더는 안 쓰이는 것이니 정리 대상이다. 읽기 이득은 0인데 폭·쓰기 대가는 계속 내고 있는 상태다.

8. MySQL로 물으면 답이 갈리는 다섯 지점

같은 질문을 MySQL 기준으로 받으면 다섯 군데에서 답이 달라진다. 이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "저장 구조에서 도출했다"로 들린다.

지점PostgreSQLMySQL (InnoDB)
① PK 커버링리프에 TID뿐 → PK도 INCLUDE로 명시해야 커버된다세컨더리 리프에 PK가 들어 있어 자동 커버 — 지연 조인이 "공짜"인 이유
② 두 번째 조건Index Only Scan은 VM이 신선한 페이지만 힙을 건너뛴다 → Heap FetchesUsing index는 그 자체로 룩업 0회. 언두 로그 기반 MVCC라 세컨더리 리프에서 가시성을 판정할 수 있어 이 조건이 아예 없다
③ 문법INCLUDE로 리프에만 싣는다 (SQL Server에도 같은 문법이 있다)INCLUDE가 없다. 나르기용도 키 컬럼으로 붙여야 하므로 내부 노드가 넓어지고 키 길이 상한·비교 비용을 함께 짊어진다
④ 조건 평가 이름표Index Cond의 비접두 키 검사로 기본 내장 — 별도 이름이 없다Using index condition(ICP)이라는 이름표가 따로 있다. Using where는 룩업 후 필터 = PostgreSQL의 Filter
⑤ 자주 바뀌는 컬럼HOT 탈락 → 모든 인덱스에 새 엔트리 + VM 해제그 인덱스만 삭제 표시 + 삽입 (행은 제자리 갱신 + 언두 로그)
참고 · 엔트리 상한페이지의 약 1/3(8KB에서 약 2,700바이트). 접두사 인덱스 없음DYNAMIC 행 포맷 기준 3072바이트. TEXT/BLOB은 접두사 인덱스로만 가능하고 접두사 인덱스는 커버 불가
참고 · 계획 이름Index Only Scan / Index Scan / 인덱스 전체 스캔은 Index Cond 없는 Index Only ScanExtra 칸에 Using index / Using index condition / Using where. 인덱스 전체 스캔은 type: index
②가 이 문항에서 두 DB의 답이 가장 크게 갈리는 지점이다 — MySQL에는 Heap Fetches에 해당하는 것이 아예 없다
둘째 줄이 왜 그렇게 갈리는가 — MVCC를 어디에 구현했는가의 차이 PostgreSQL은 버전을 힙 안에 쌓고(그래서 가시성 정보가 힙에만 있다), InnoDB는 행을 제자리에서 갱신하고 옛 버전을 언두 로그에 둔다. 그 결과 InnoDB는 세컨더리 인덱스에서도 가시성을 판정할 수 있고, PostgreSQL은 못 한다. 커버링 인덱스라는 같은 개념이 두 DB에서 다르게 동작하는 이유가 전부 이 한 줄에서 나온다 — 11-mvcc-postgresql.md와 이어진다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 면접 직전에 이것만 훑는다

목록이 인출되지 않으면 사슬도 트레이드오프도 꺼낼 수 없다. 보기 전에 먼저 답해본다.

커버링의 정의 한 문장?
쿼리가 쓰는 모든 컬럼이 인덱스 안에 있어 인덱스 조회 2단계 중 ②(힙 페치)가 사라진 상태. 인덱스의 종류가 아니라 인덱스와 쿼리의 관계.
체크할 세 군데?
셀·웨·오 — SELECT 목록 / WHERE·ON / ORDER BY·GROUP BY. PK도 예외가 아니다(리프엔 TID뿐).
효과 큰 상황 5종?
많이 · 좁게 · 자주 · 세기 · 정렬. 다섯 모두 "VM이 신선한 테이블"을 전제로 한다.
대가 4종?
폭 · 쓰기 · 취약 · 상한. 폭=캐시 적재율↓ / 쓰기=HOT 탈락으로 모든 인덱스 갱신 + VM 해제 / 취약=SELECT 컬럼 추가로 조용히 무효 / 상한=엔트리 페이지 1/3.
안전망 4종?
프 · 테 · 주 · 알 — DTO 프로젝션 / EXPLAIN 단정 테스트(Node Type·Index Name) / 마이그레이션 주석 + _cover 규약 / 호출당 블록 수 알림 + auto_explain.
Heap Fetches가 큰 원인 3종?
밀 · 롱 · 인 — autovacuum 밀림 / 롱 트랜잭션(backend_xmin) / INSERT만 쌓이는 테이블. 대응이 각각 다르다.
계획 3종?
Index Only Scan+HF:0(완성) / Index Only Scan+HF:N(가시성 확인 → VACUUM) / Index Scan+Index Cond·Filter(힙 방문).
비용 사슬 한 줄?
컬럼이 인덱스 밖 → TID로 힙 페이지 행마다 → 인덱스 순서 ≠ 힙 순서 → 페이지 1장당 요청 1건 = 랜덤 I/O → 워킹셋=테이블 전체 → 캐시 미스 → 디스크 랜덤 읽기. 커버링은 첫 고리를 끊는다.
키 컬럼 vs INCLUDE?
찾거나·정렬하거나·키셋 비교에 쓰면 키, 싣기만 하면 INCLUDE. 차이의 근원은 내부(비리프) 페이지에도 실리는가 하나.
INCLUDE는 공짜인가?
아니다. HOT 판정에서는 인덱스 컬럼으로 친다 → 갱신 대가는 키 컬럼과 동일. 그리고 리프의 폭은 그대로 늘어난다.
MySQL과 갈리는 급소 하나?
Heap Fetches에 해당하는 것이 MySQL엔 없다. 언두 로그 기반 MVCC라 세컨더리 리프에서 가시성 판정이 되기 때문. PK 자동 커버도 여기서 갈린다.
한 문장 템플릿?
"힙 페치 N회 = 랜덤 I/O N회를 0으로 만드는 대신 — 그 0은 VM이 신선할 때만 — 폭·쓰기·취약성을 치릅니다. 그래서 많이·좁게·자주 읽히는 쿼리에 거의 안 바뀌는 컬럼만 실어 제한적으로 씁니다."

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

커버링 인덱스가 왜 빠른지, "테이블에 안 가서" 말고 I/O 단위로 설명해보세요. 필수힌트: 2단계를 나누고, 2단계의 성질에 "랜덤"이라는 이름을 붙인다

PostgreSQL의 인덱스 조회는 2단계다. 1단계는 리프를 형제 링크로 훑는 읽기라 싸고, 2단계는 리프에서 얻은 TID로 힙 페이지를 행마다 한 장씩 읽는 것이다.

인덱스는 자기 컬럼 순으로 정렬돼 있지만 힙은 정렬이 없어 인덱스에서 이웃한 행이 힙에서는 먼 페이지에 있고, 그래서 2단계는 페이지 1장당 요청 1건인 랜덤 I/O다 — 미리 읽기가 안 걸리고, 워킹셋이 테이블 전체로 퍼져 캐시 미스도 늘어난다.

커버링은 필요한 컬럼이 전부 인덱스에 있어 2단계 자체가 없다. 대상 N행에 대해 "랜덤 페이지 N장"이 "좁은 리프 N/수백 장"으로 바뀌는 것이 몇 배의 정체다.

두 마디를 붙이면 비용 모델을 이해했다는 신호가 된다

① SSD에서도 요청당 고정 오버헤드 때문에 차이는 줄어들 뿐 사라지지 않는다. ② PostgreSQL에서는 이 0이 visibility map이 "전부 가시"인 페이지에 한해 성립한다(Heap Fetches).

Index Only Scan이 떴는데도 안 빠릅니다. 뭘 보나요? 함정힌트: 인덱스 정의를 다시 들여다보면 영원히 못 찾는다

EXPLAIN (ANALYZE, BUFFERS)의 Heap Fetches부터 본다. 계획 이름은 "컬럼이 다 인덱스에 있다"까지만 보장하고, 힙을 건너뛸지는 실행 시점에 페이지마다 visibility map을 보고 정한다.

Heap Fetches가 actual rows에 가깝고 Buffers가 커버링 이전과 비슷하면, 커버링은 성립했지만 VM이 낡아 사실상 Index Scan으로 동작한 것이다.

원인은 순서대로 밀 · 롱 · 인:

밀
autovacuum이 밀림 — 대량 갱신 직후. n_dead_tup↑ · last_autovacuum 오래됨 → 수동 VACUUM 후 그 테이블만 autovacuum_vacuum_scale_factor를 낮춘다.
롱
롱 트랜잭션이 pg_stat_activity.backend_xmin을 잡고 있어 VACUUM이 돌아도 죽은 튜플을 못 치우고 VM을 못 세움 → 트랜잭션을 끊어야 해결된다. VACUUM 튜닝으로는 안 풀린다.
인
INSERT만 쌓이는 테이블이라 죽은 튜플이 없어 autovacuum이 안 돎 — PostgreSQL 13부터는 INSERT 양으로도 기동한다.

빠른 확진은 pg_class의 relallvisible / relpages(VM 비트가 선 페이지 비율). 이 비율이 낮으면 플래너도 Index Only Scan의 이득을 낮게 잡아 다른 계획을 고르기 시작하니, "어느 날부터 커버링 인덱스를 안 탄다"의 원인이기도 하다.

커버링 인덱스는 항상 이득인가요? 만들지 말아야 할 때는 언제죠? 시니어 변별힌트: 3절의 공식을 그대로 뒤집어 답한다

아니다. 이득은 절감 힙 페치 횟수 × 랜덤 I/O 비용 × 호출 빈도 × VM 신선도 − 인덱스 폭 비용이므로, 앞이 작거나 뒤가 크면 손해다. 만들지 말아야 할 때는 다섯이다.

1
실을 컬럼이 자주 UPDATE될 때 — HOT 탈락으로 테이블의 모든 인덱스에 새 엔트리 + bloat + VM 해제. 읽기 이득까지 같이 깎인다.
2
컬럼이 넓거나 많을 때 — 엔트리 비대 → 캐시 적재율↓로 다른 인덱스까지 밀어내고, 큰 text/jsonb는 엔트리 크기 상한에 걸려 애초에 불가.
3
호출이 드물거나 대상이 1~2건일 때 — 절감분이 없다. 대가만 남는다.
4
갱신 폭풍 테이블이라 VM이 늘 낡아 있을 때 — Index Only Scan이 떠도 Heap Fetches가 행 수만큼 나온다. autovacuum 튜닝이나 갱신 패턴 분리(자주 바뀌는 컬럼을 별도 테이블로)가 선행돼야 한다.
5
쿼리 모양이 자주 바뀌는 화면일 때 — 컬럼 추가로 조용히 깨지는 취약성을 감당할 안전망(프로젝션 고정 + EXPLAIN 테스트)이 없다면 만들지 않는 게 낫다.
답은 "많이·좁게·자주 읽히고, 거의 안 바뀌는 컬럼만 싣고, VM이 유지되는 테이블에서, 깨짐을 테스트가 잡아주는 조건에서만 만든다"
그리고 그 근거를 EXPLAIN (ANALYZE, BUFFERS) 전후 비교와 실제 지연 측정으로 남기는 것까지가 세트다
JPA 엔티티 조회는 SELECT *인데, 그러면 커버링 인덱스를 못 쓰나요? 필수힌트: 방법이 둘이고, 둘째 방법에는 PostgreSQL 고유의 조건이 붙는다

엔티티 조회로는 못 쓴다 — 모든 컬럼을 SELECT하므로 어떤 인덱스로도 덮이지 않는다. 방법은 둘이다.

⑴ DTO 프로젝션(인터페이스 프로젝션, select new, QueryDSL Projections)으로 SELECT 목록을 필요한 컬럼만으로 고정한다.

⑵ 행 전체가 정말 필요하면 지연 조인(deferred join) — 커버링 인덱스로 PK만 먼저 뽑고, 살아남은 PK로만 행을 가져온다. 단 PostgreSQL에서는 PK가 인덱스에 자동으로 들어 있지 않으므로 서브쿼리가 Index Only Scan이 되려면 id를 키나 INCLUDE에 실어 둬야 한다.

-- 인덱스: (user_id, created_at) INCLUDE (id)   ← id를 싣지 않으면 서브쿼리부터 힙에 간다
SELECT o.*
FROM orders o
JOIN (SELECT id FROM orders                     -- Index Only Scan: 인덱스만으로 id를 뽑는다
      WHERE user_id = $1
      ORDER BY created_at DESC
      LIMIT 20 OFFSET 100000) t ON o.id = t.id;  -- 버리는 10만 건에는 힙 페치가 없고,
                                                 -- 살아남은 20건만 orders_pkey로 힙 페치

JPA에서는 "PK 목록 조회 → findAllById" 2단계로 같은 효과를 낸다.

다만 OFFSET이 버리는 10만 엔트리를 "읽기는 읽는다"는 한계는 그대로라, 깊은 페이지에서는 키셋 페이지네이션 — WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 20을 (user_id, created_at, id) 인덱스로 — 이 정석이다. PostgreSQL은 이 행 비교를 B-tree 범위 탐색으로 실행한다.

커버링 인덱스를 추가했더니 오히려 다른 쿼리가 느려졌습니다. 왜 그럴까요? 함정힌트: 대가 4종 중 셋이 전부 "다른 쿼리"에게 청구된다. 그리고 DDL을 어떻게 냈는지도 본다

커버링의 이득은 그 쿼리 하나가 받고, 대가는 테이블 전체가 나눠 낸다. 경로가 셋이다.

폭
넓어진 인덱스가 캐시를 더 차지한다. 리프 엔트리가 커져 같은 데이터를 담는 데 페이지가 더 필요하고, 그만큼 shared_buffers·OS 캐시에서 다른 인덱스와 힙 페이지를 밀어낸다. 내 쿼리는 빨라졌는데 남의 쿼리의 캐시 히트율이 떨어진 것. 확인: pg_relation_size로 인덱스 크기 증가분.
쓰기
실은 컬럼이 UPDATE되면 HOT에서 탈락한다. 그러면 그 테이블의 모든 인덱스에 새 엔트리가 꽂혀 모든 쓰기 쿼리가 느려지고, bloat이 쌓이며, VM 비트까지 꺼져 다른 커버링 쿼리의 Heap Fetches도 올라간다. 확인: pg_stat_user_tables의 n_tup_hot_upd / n_tup_upd 비율이 인덱스 추가 뒤 떨어졌는가.
중복
기존 인덱스를 "교체"하지 않고 "추가"했다면 접두사가 같은 인덱스가 두 개 남는다. 모든 INSERT/UPDATE가 두 번씩 인덱스를 쓴다. 확인: pg_stat_user_indexes.idx_scan이 0에 가까운 쪽이 있으면 그게 유령이다 → DROP INDEX CONCURRENTLY.
그래서 커버링 인덱스는 "추가했다"가 아니라 "교체했고, 실은 컬럼은 거의 안 바뀌는 것뿐이며, 쓰기 지표를 전후로 비교했다"까지가 한 세트다
SELECT count(*) FROM orders가 PK가 아니라 엉뚱한 작은 인덱스를 타던데, 왜 그런가요? 가산점힌트: "필요한 컬럼이 0개"라는 극한을 정의에 대입해 본다

count(*)는 어떤 컬럼 값도 필요 없어 사실상 모든 B-tree 인덱스가 그 쿼리에 대해 커버링이다. 그러면 남는 기준은 "어느 트리가 가장 좁아서 페이지 수가 적은가"뿐이고, 플래너는 조건 없는 count(*)를 가장 작은 인덱스의 Index Only Scan(대량이면 Parallel Index Only Scan)으로 처리한다 — PK 인덱스가 가장 좁다는 보장은 없다(단일 boolean 인덱스가 더 작다).

이 현상을 설명할 수 있으면 "커버링 = 필요한 컬럼이 인덱스 안"이라는 정의를 극한(필요한 컬럼이 0개)까지 밀어 이해했다는 뜻이다.

단 PostgreSQL에는 조건이 하나 더 붙는다 플래너는 pg_class.relallvisible로 힙 페치 비율을 추정하므로, VM이 낡은 테이블에서는 같은 count(*)가 Seq Scan으로 간다 — 인덱스 전체 + 힙 전체를 읽느니 힙만 읽는 게 싸기 때문이다. "어제는 인덱스로 세더니 오늘은 풀스캔"이 대량 갱신 뒤에 나타나고 VACUUM 후 돌아오는 이유가 이것이다. MVCC 때문에 카운트를 미리 들고 있을 수 없다는 근본 한계와 대안은 17-total-count-cost-and-alternatives.md에서 잇는다.
Index Only Scan인데 Index Cond가 없습니다. 좋은 건가요, 나쁜 건가요? 가산점힌트: "좋다/나쁘다"로 답하지 말고 쿼리 종류에 따라 갈라 답한다

둘 다일 수 있다. Index Cond가 없다는 것은 B-tree 탐색으로 범위를 좁히지 못하고 인덱스를 처음부터 끝까지 훑었다는 뜻 — 즉 인덱스 전체 스캔이다.

정상이자 최적인 경우

조건 없는 count(*)·전체 집계처럼 애초에 좁힐 조건이 없는 쿼리. 이때는 인덱스가 테이블보다 좁다는 이유만으로 Seq Scan을 이기므로 이게 최선이다.

신호인 경우

좁혀야 할 조회인데 이렇다면 조건이 인덱스 앞쪽 키에 안 걸린 것이다 — 접두사 규칙 위반, 컬럼에 함수 적용, 타입 불일치 등(02-index-not-used-full-scan.md). 커버링이라 계획 이름은 그럴듯한데 스캔 범위는 전체인, 가장 착각하기 쉬운 상태다.

판단은 이름이 아니라 숫자로 한다 — actual rows가 반환 행 수에 비해 터무니없이 크거나 Buffers가 인덱스 전체 크기에 가깝다면 후자다. "Only가 붙었으니 됐다"고 넘어가면 놓친다.

id를 INCLUDE에 넣을까요, 키 컬럼 맨 뒤에 붙일까요? 필수힌트: "커버링만 되면 같다"가 아니다. 이 화면에 다음에 무엇이 올지를 묻는 질문이다

커버링 효과만 놓고 보면 둘은 같다 — 어느 쪽이든 리프에 실리므로 힙 페치는 사라진다. 갈리는 곳은 커버링 바깥이다.

기준키 컬럼 (user_id, created_at, id)INCLUDE (id)
커버링된다된다
키셋 타이브레이커쓸 수 있다 — (created_at, id) < ($1, $2)가 범위 탐색이 된다못 쓴다 — Index Cond에 등장하지 않는다
내부(비리프) 페이지넓어진다 — 트리가 뚱뚱해지고 비교 비용↑그대로
유니크 인덱스에 덧붙이기유일성 판정에 참여해 제약의 의미가 바뀐다참여하지 않아 그대로 덧붙일 수 있다
타입 제약비교 연산자가 정의된 타입만비교 연산자가 없는 타입도 가능
HOT 판정양쪽 다 "인덱스 컬럼"으로 친다 — 갱신 대가는 동일하다
그래서 답은 "이 목록에 키셋 페이지네이션을 붙일 계획이 있는가"로 갈린다
있으면 (user_id, created_at, id) INCLUDE (amount)처럼 id만 키로 올리고, 없으면 INCLUDE (id, amount)로 내부 페이지를 지킨다
MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 다섯 지점이고, 전부 "저장 구조의 차이"에서 도출된다

다섯 지점이다. 그리고 다섯 모두 "리프에 무엇이 들어 있는가"와 "MVCC를 어디에 구현했는가"에서 도출된다.

1
PK 공짜 커버링 — InnoDB 세컨더리 리프에는 PK가 들어 있어 PK 컬럼은 자동 커버되지만, PostgreSQL 리프에는 TID뿐이라 PK도 INCLUDE로 명시해야 한다. 지연 조인이 MySQL에서 "공짜"인 이유가 이것이다.
2
커버링 판정의 두 번째 조건 — MySQL Using index는 그 자체로 룩업 0회지만, PostgreSQL Index Only Scan은 VM이 신선한 페이지만 힙을 건너뛴다. MySQL은 언두 로그 기반 MVCC라 세컨더리 리프에서 가시성을 판정할 수 있어 이 조건이 없다. 가장 크게 갈리는 지점
3
문법 — MySQL은 나르기용 컬럼도 키에 붙여야 하지만 PostgreSQL은 INCLUDE로 리프에만 싣는다.
4
ICP — MySQL은 Using index condition이라는 이름표가 따로 있고, PostgreSQL은 같은 동작이 Index Cond의 비접두 키 검사로 기본 내장돼 이름이 없다.
5
자주 바뀌는 컬럼의 대가 — InnoDB는 그 인덱스만 삭제+삽입, PostgreSQL은 HOT 탈락으로 모든 인덱스에 새 엔트리 + VM 해제.

이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "저장 구조에서 도출했다"로 들린다.

한 줄 요약
PostgreSQL의 인덱스 조회는 ① 인덱스를 훑어 TID 목록을 얻고 ② 그 TID로 힙 페이지를 행마다 읽는 2단계인데, 커버링 인덱스는 쿼리가 쓰는 모든 컬럼이 인덱스 안에 있어 ②(힙 페치 — 행마다 힙에 흩어진 페이지를 찌르는 랜덤 I/O)가 0회가 된 상태(Index Only Scan)이고, 그 랜덤 N장이 좁은 리프 N/수백 장으로 바뀌는 것이 "몇 배"의 정체다. 단 PostgreSQL에서는 인덱스가 가시성을 모르므로 그 0은 visibility map이 "전부 가시"로 표시한 페이지에서만 성립한다 — Heap Fetches가 크면 인덱스 설계가 아니라 VACUUM 문제다. 효과는 "많이·좁게·자주·세기·정렬" 쿼리에서 크고, 대가는 폭·쓰기(실은 컬럼 UPDATE마다 HOT 탈락 → 모든 인덱스 갱신)·취약·상한이며, PK도 공짜가 아니니 INCLUDE로 명시한다. 깨짐은 프로젝션 · EXPLAIN 단정 테스트 · 마이그레이션 주석 · pg_stat_statements 호출당 블록 수 알림이 잡게 한다.
