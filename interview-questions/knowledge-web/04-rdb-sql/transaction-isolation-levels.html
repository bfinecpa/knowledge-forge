트랜잭션 격리 수준 4가지와 이상 현상
"같은 걸 두 번 읽었는데 값이 다른" 문제의 지도 — dirty · non-repeatable · phantom

면접 질문: "트랜잭션 격리 수준 4가지와 각각에서 발생 가능한 문제(dirty read, non-repeatable read, phantom read)를 설명해주세요."

핵심 관전 포인트 — 격리 수준은 "동시에 도는 다른 트랜잭션의 변경이 나에게 얼마나 보이는가"를 4단계로 정한 표준(SQL 표준)이고, 각 단계는 허용하는 이상 현상(dirty read / non-repeatable read / phantom read)으로 정의된다. 세 이상 현상의 구분 — 커밋 안 된 걸 읽음 / 같은 행의 값이 바뀜(UPDATE) / 행 개수가 바뀜(INSERT·DELETE) — 이 1차 변별 포인트고, "MySQL InnoDB는 REPEATABLE READ가 기본인데 MVCC + 갭 락으로 phantom도 상당 부분 막는다"는 교과서와 실제 DB의 차이, 그리고 "동시성 제어를 격리 수준 올리기로 풀면 안 되는 이유"까지 가면 시니어 답변이다.
  • 1
    정의 — ACID의 I(격리)를 "완벽히 지키면 동시성이 죽으니 얼마나 양보할지"를 4단계로 정한 표준. 각 단계는 어떤 이상 현상까지 허용하는가로 정의된다.
  • 2
    세 현상 — dirty read: 커밋 안 된 값을 읽음 · non-repeatable read: 같은 행을 다시 읽으니 값이 다름(UPDATE) · phantom read: 같은 조건으로 다시 읽으니 행 개수가 다름(INSERT/DELETE).
  • 3
    실제 DB — MySQL만 기본이 RR이고 나머지는 RC. InnoDB RR은 MVCC 스냅샷(읽기)+갭 락(쓰기)으로 phantom까지 대부분 막는다. 쓰기 충돌 같은 국소 문제는 격리 수준이 아니라 락·원자적 UPDATE로 푼다.

0. 질문 + 출제 의도

질문: "트랜잭션 격리 수준 4가지와 각각에서 발생 가능한 문제(dirty read, non-repeatable read, phantom read)를 설명해주세요."

출제 의도: 격리 수준은 "정합성 버그가 재현 안 되는 이유"의 단골 원인이다. non-repeatable read를 모르면 "같은 트랜잭션에서 두 번 읽었는데 값이 달라요"라는 버그 리포트 앞에서 코드만 백날 들여다본다 — 동시성 버그를 코드가 아닌 격리 수준 관점에서 진단할 수 있는지 확인하는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① ACID 정의 인출 실패(격리성↔원자성 혼동) → 1절의 ACID 인출 카드에서 A와 I를 "혼자의 끝 / 남과의 사이"라는 축으로 갈라 둔다.
② 개념 목록 인출이 약함 → 매트릭스(4×3), 이름=막는 현상 규칙, "4·3·1·3" 숫자 카드로 목록을 눈에 박는다.
③ 비용을 메커니즘 사슬로 서술하지 못함 → 4절에서 격리 수준을 올릴 때의 비용을 3개의 사슬로 이름 붙여 나열한다.

1. 격리 수준은 무엇을 정하는 규칙인가 — ACID의 I에서 "얼마나 양보할지"

1-1. 먼저 ACID에서 I의 자리를 정확히 잡는다 약점 겨냥

격리 수준은 ACID 중 I(Isolation, 격리성)의 구현 강도를 고르는 다이얼이다. 그런데 I를 A와 헷갈리면 이 다이얼이 무엇을 돌리는지부터 흔들린다. 네 글자를 "어떤 질문에 답하는 성질인가"로 외운다.

A
Atomicity · 원자성
끝났을 때 전부냐 전무냐?
한 트랜잭션 혼자의 시간축(시작→끝). 도구: undo 로그로 롤백
C

전후로 규칙(제약)이 지켜지나?

두 성질이 헷갈리는 진짜 이유는 InnoDB에서 undo 로그가 A(롤백용 이전 값)와 I(MVCC가 보여줄 과거 버전)를 겸직하기 때문이다. 장치는 하나지만 답하는 질문은 다르다 — 자세한 구조는 MVCC와 InnoDB 구현.

1-2. 완벽한 격리에서 얼마나 양보할 것인가 — 4단계

I를 완벽하게 지키려면 모든 트랜잭션을 순차 실행한 것과 같게 만들어야 하는데, 그러면 동시성이 죽는다. 그래서 SQL 표준은 "완벽한 격리에서 얼마나 양보할 것인가"를 4단계로 정의하고, 각 단계를 "이 단계에서는 이런 이상 현상까지는 일어날 수 있다"로 규정했다. 즉 격리 수준의 정의는 기능 목록이 아니라 허용 현상 목록이다.

2. 세 가지 이상 현상 — 두 트랜잭션의 시간 순서로 이해하기

세 현상 모두 "트랜잭션 A가 읽는 중에 트랜잭션 B가 끼어드는" 시나리오다. 차이는 B가 무엇을 했고, A에게 무엇이 다르게 보이는가뿐이다. 세 타임라인을 같은 틀(위: 읽는 A, 아래: 끼어드는 B)로 놓고 다른 부분만 본다.

2-1. Dirty Read — 커밋 안 된 데이터를 읽음

2-2. Non-Repeatable Read — 같은 행을 두 번 읽었는데 값이 다름 (UPDATE)

2-3. Phantom Read — 같은 조건으로 두 번 조회했는데 행 개수가 다름 (INSERT/DELETE)

2-4. Non-repeatable vs Phantom — 왜 따로 구분하나 1차 변별

Non-Repeatable ReadPhantom Read
무엇이 달라지나이미 읽었던 기존 행의 값같은 조건에 걸리는 행의 개수
B가 한 일UPDATEINSERT / DELETE
행 락으로 막히나?막힌다 — 읽은 행에 락못 막는다 — 아직 없는 행엔 락을 걸 수 없음
막는 도구행 단위 스냅샷 또는 행 락범위(갭) 락 또는 순차 실행에 준하는 제어(SERIALIZABLE)
막히기 시작하는 수준REPEATABLE READSERIALIZABLE (표준) / InnoDB는 RR에서 대부분
한 문장으로따로 구분하는 이유는 막는 방법이 다르기 때문이다. 기존 행의 변경은 그 행에 락을 걸면 막히지만, "아직 존재하지 않는 행의 INSERT"는 행 락으로는 막을 수 없다. 조건에 해당하는 범위(갭) 자체를 잠그거나(갭 락), 순차 실행에 준하는 제어가 필요하다. 그래서 표준은 RR까지도 phantom을 허용한다.

3. 교과서 vs 실제 DB — 기본값과 InnoDB의 특수성 시니어 변별

3-1. 실무 기본값 — "우리 DB의 기본 격리 수준이 뭔지 아는가"

DB기본 격리 수준비고

확인 명령: MySQL SELECT @@transaction_isolation; · PostgreSQL SHOW transaction_isolation; — "실제로 확인해 봤다"는 한 마디가 실무 감각을 전달한다.

3-2. InnoDB의 REPEATABLE READ는 교과서보다 강하다 — 팬텀을 두 경로에서 따로 막는 이중 구조

교과서 매트릭스대로면 RR에서 phantom read가 발생해야 하지만, InnoDB는 읽기 경로는 MVCC 스냅샷으로, 쓰기(잠금 읽기) 경로는 갭 락으로 각각 막는다. 두 경로가 서로 다른 원리로 동작한다는 점이 핵심이다.

정확한 답변 문장 — 3단 구조"InnoDB REPEATABLE READ는 표준 정의상 phantom이 허용되지만, 구현상 일관된 읽기는 MVCC 스냅샷으로, 잠금 읽기는 갭 락으로 대부분 방지한다. 단 스냅샷 읽기와 잠금 읽기를 한 트랜잭션에서 섞으면 예외가 생긴다." — "표준의 정의"와 "특정 DB의 구현"을 분리해서 말하는 것 자체가 가산점.

혼용 예외를 코드로 보기

-- Tx A (InnoDB, REPEATABLE READ)
BEGIN;
SELECT COUNT(*) FROM emp WHERE salary > 500;              -- 3건. 여기서 Read View 생성
--                ← Tx B: INSERT INTO emp(salary) VALUES (600); COMMIT;
SELECT COUNT(*) FROM emp WHERE salary > 500;              -- 여전히 3건 (스냅샷 재사용) ✔
SELECT * FROM emp WHERE salary > 500 FOR UPDATE;         -- 4건! 잠금 읽기 = 최신 읽기팬텀처럼 보임
UPDATE emp SET flag = 1 WHERE salary > 500;              -- 4건 갱신 → 내가 만진 행은 이후 내 스냅샷에도 보임
SELECT COUNT(*) FROM emp WHERE salary > 500;              -- 이제 4건

스냅샷은 읽기에만 적용되고 UPDATE는 최신 행에 적용된다. 남의 커밋 행을 내가 UPDATE하면 그 행의 버전이 "내 트랜잭션이 만든 것"이 되어 이후 내 스냅샷에 나타난다.

3-3. RC vs RR의 진짜 차이 — Read View를 "언제" 만드느냐 하나

InnoDB에서 RC와 RR은 둘 다 MVCC로 읽는다. 차이는 Read View(스냅샷)를 만드는 시점 하나뿐이다: RC는 문장마다, RR은 트랜잭션의 첫 읽기 때 한 번. 이 한 줄이 non-repeatable read가 RC에서 생기고 RR에서 안 생기는 이유 전부다.

3-4. SERIALIZABLE의 실체 — DB마다 "어떻게" 직렬화하는지가 다르다

InnoDB
일반 SELECT까지 전부 공유 락을 잡는 잠금 읽기로 바뀐다. MVCC 스냅샷 읽기를 버리고 "락만으로 격리하는 세계"로 돌아간다 → 읽기가 쓰기를 막고, 쓰기가 읽기를 막는다.
PostgreSQL
SSI(Serializable Snapshot Isolation) — 락 대신 충돌을 감지해 한쪽 트랜잭션을 강제 실패(직렬화 오류)시킨다 → 애플리케이션에 재시도 코드가 필수.
공통 결론읽기끼리도 서로를 기다리거나 죽이므로 처리량이 급감하고 데드락/재시도가 급증한다. 일반 서비스 트래픽에서 전역으로 켜는 수준이 아니라, 정합성이 절대적인 특수 구간에 한정해서 쓰는 도구다.

4. 격리 수준을 올릴 때의 대가 · 내릴 때의 대가 — 양면 표

격리 수준은 공짜로 올라가지 않는다. 한 칸 올릴 때 무엇을 얻고 무엇을 치르는지, 반대로 한 칸 내릴 때 무엇을 얻고 무엇을 허용하는지를 전환 단위로 놓으면 "왜 그 수준이면 충분한가"를 말할 수 있다.

전환올릴 때 얻는 것올릴 때 치르는 것내릴 때 얻는 것내릴 때 허용하는 것

4-2. 비용을 "결과"가 아니라 "사슬"로 말하기 약점 겨냥

"느려진다", "데드락이 난다"는 결과다. 면접관이 듣고 싶은 것은 어떤 장치가 어떤 순서로 그 결과를 만드는가다. 세 사슬을 이름 붙여 외운다.

잠금 읽기(UPDATE/DELETE/FOR UPDATE)→ 조건 범위에 넥스트 키 락→ 그 범위로 오는 INSERT 대기→ 두 트랜잭션이 서로의 갭을 기다림→ 데드락 감지 · 한쪽 롤백→ 재시도 · 처리량↓
사슬 B — RR의 스냅샷 비용 (읽기 경로)
첫 SELECT에 Read View 생성→ 트랜잭션이 길면 그 시점 이전 undo를 purge 못 함→ history list 증가→ 버전 체인 길어짐→ 무관한 조회까지 행마다 체인 순회→ 전체 조회 지연
사슬 C — SERIALIZABLE 비용 (InnoDB)
일반 SELECT→ 공유 락 잠금 읽기로 전환→ 읽기가 쓰기를 막음→ 쓰기 대기 · 커넥션 점유 시간↑→ 풀 고갈 · 락 대기 그래프 복잡→ 처리량 급감 · 데드락 폭증

사슬 B는 격리 수준 자체보다 트랜잭션 길이가 배수로 작용한다 — 그래서 RR을 쓰는 곳일수록 "트랜잭션은 짧게"가 더 중요하다(긴 트랜잭션의 해악).

4-3. "우리 서비스는 RC/RR 중 무엇, 왜" — 판단 기준 카드

판단은 "바꿨다"가 아니라 "왜 그 수준이면 충분/부족했는가"

RR을 유지하는 근거 (MySQL 기본)
  • 한 트랜잭션 안에서 여러 SELECT의 일관성이 로직·리포트 정확성에 필요하다(정산 검증, 스냅샷성 집계).
  • 트랜잭션이 짧아 스냅샷 유지(사슬 B) 비용이 미미하다.
  • 팀이 갭 락을 이해하고 인덱스로 잠금 범위를 좁힌다 — 데드락 로그가 통제 범위 안.
  • 바꿀 명확한 이유가 없다 — 기본값 유지 자체가 팀 전체가 아는 단일 기준이라는 가치.
RC로 내리는 근거
  • 갭 락 데드락이 반복된다 — INSERT가 몰리는 테이블에 범위 조건 UPDATE/DELETE가 섞이는 구간.
  • 긴 조회 트랜잭션(배치·리포트)에서 history list length가 올라가 남들까지 느려진다.
  • 매 문장 최신 커밋이 필요하다(작업 큐 폴링, 상태 전이 확인).
  • 그 로직이 같은 행을 두 번 읽어 판단하지 않는다 — 또는 필요한 곳은 FOR UPDATE로 이미 잠근다.
  • MySQL 전제 조건: binlog가 ROW 형식이어야 한다(요즘 기본값).
어느 쪽이든 — 쓰기 충돌은 격리 수준이 아니라 국소 락 · 원자적 UPDATE로 푼다
답변 템플릿(예시) — "우리는 MySQL이라 기본 RR을 유지한다. 트랜잭션을 짧게 유지해 스냅샷 비용이 작고, 재고·정산 같은 갱신 충돌은 FOR UPDATE·원자적 UPDATE로 국소 처리하기 때문이다. 다만 INSERT가 몰리는 로그성 테이블에 범위 UPDATE를 하는 배치에서 갭 락 데드락이 반복돼, 그 배치의 @Transactional만 RC로 낮췄다 — 그 로직은 같은 행을 두 번 읽어 판단하지 않으므로 non-repeatable read가 문제되지 않는다는 것을 확인하고 내렸다."

구조: 기본값 → 유지 근거 → 예외 구간 → 예외를 허용해도 되는 이유(허용 현상이 그 로직에 무해함). 이 네 칸이 채워지면 "격리 수준을 판단해 본 사람"으로 들린다.

5. 격리 수준으로 풀 문제 vs 락으로 풀 문제

격리 수준은 읽기 일관성의 기본기(광역 설정) · 쓰기 충돌은 락(국소 도구)으로

격리 수준은 "트랜잭션 전체가 세상을 얼마나 일관되게 보는가"라는 광역 설정이고, 재고 차감은 "이 행 하나의 갱신 충돌"이라는 국소 문제다. 국소 문제를 광역 설정으로 풀면 무관한 트랜잭션까지 전부 비용을 치른다 — 이 구분을 말할 수 있으면 시니어 답변이 된다.

BEFORE"SERIALIZABLE로 올리면 되지 않나?"
-- 재고 차감 동시성 문제를 격리 수준으로 해결 시도
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;광역
BEGIN;
SELECT stock FROM item WHERE id = 1;   -- 공유 락
-- 앱에서 stock - 1 계산
UPDATE item SET stock = 9 WHERE id = 1; -- 배타 락 승격
COMMIT;
-- 두 트랜잭션이 동시에 하면: 둘 다 S락 → 둘 다 X락 대기
-- → 데드락. 게다가 무관한 조회 전부 락을 잡기 시작
AFTER문제가 되는 그 지점만 잠근다
-- 방법 A: 비관적 락 (그 행만 잠그고 읽기)
SELECT stock FROM item WHERE id = 1 FOR UPDATE;
UPDATE item SET stock = stock - 1 WHERE id = 1;

-- 방법 B: 원자적 UPDATE (읽기-계산-쓰기를 한 문장으로)
UPDATE item SET stock = stock - 1
 WHERE id = 1 AND stock >= 1;affected rows=0 → 재고 부족

-- 방법 C: 낙관적 락 (버전 컬럼, 충돌 시 재시도)
UPDATE item SET stock = 9, version = version + 1
 WHERE id = 1 AND version = 5;
원자적 UPDATE
가장 싸다. 읽기-계산-쓰기를 DB 한 문장으로 합쳐 경합 자체를 없앤다. 차감 전후 검증 로직이 없을 때.
SELECT … FOR UPDATE
차감 전후로 검증·부가 로직이 필요할 때. 그 행만 잠근다 — 범위는 FOR UPDATE 락 범위.
낙관적 락
충돌이 드물 때. 락 대기 없이 버전 불일치를 실패로 받아 재시도.

6. Spring @Transactional(isolation = …)과 MySQL 세션 설정

"스프링 @Transactional의 격리 수준 기본값은?"

Isolation.DEFAULT — 스프링이 정하는 게 아니라 DB의 기본 격리 수준을 그대로 따른다는 뜻이다. 같은 코드가 MySQL에서는 REPEATABLE READ로, PostgreSQL에서는 READ COMMITTED로 돈다. "READ_COMMITTED"라고 박아 답하면 틀린다 — DB 기본값 위임이 정답.

항목내용
선택지Isolation.DEFAULT / READ_UNCOMMITTED / READ_COMMITTED / REPEATABLE_READ / SERIALIZABLE
동작 방식트랜잭션 시작 시 커넥션에 Connection.setTransactionIsolation(...) 호출 → 그 트랜잭션 동안만 적용 → 끝나면 원복(커넥션 풀 공유 때문)
적용 단위트랜잭션을 새로 시작하는 쪽이 정한다. REQUIRED로 기존 트랜잭션에 합류하는 경우 지정은 무시된다(validateExistingTransaction을 켜면 예외)
전역 vs 국소DB 전역 설정 변경은 전체 서비스에 영향을 주는 별개의 결정. 예외 구간은 트랜잭션 단위 지정이 정석

7. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 힌트는 답의 뼈대 첫 단어다.

"같은 트랜잭션에서 같은 행을 두 번 읽었는데 값이 달라요"라는 버그 리포트 — 무슨 현상이고 어떻게 확인하나?힌트: 현상 이름 → 격리 수준 확인 → "정말 같은 트랜잭션인가"

전형적인 non-repeatable read이고, 격리 수준이 READ COMMITTED 이하일 때 가능한 현상이다(REPEATABLE READ부터는 스냅샷으로 막힘).

  1. 그 DB/커넥션의 실제 격리 수준 확인 — MySQL SELECT @@transaction_isolation, PostgreSQL SHOW transaction_isolation.
  2. 코드에서 @Transactional(isolation = ...) 지정 여부와, 애초에 두 읽기가 정말 같은 트랜잭션 안인지 확인 — 트랜잭션이 없거나(프록시 자기 호출 등으로) 끊겨서 각 SELECT가 별도 트랜잭션(auto-commit)으로 돈 것일 수 있다.
  3. 해결: 그 로직만 REPEATABLE READ로 올리거나, 값을 다시 읽지 말고 첫 읽기 결과를 변수로 들고 가거나, 갱신 충돌이 본질이면 FOR UPDATE로 잠그고 읽는다 — 요구사항에 맞는 것을 고른다.
MySQL REPEATABLE READ에서 phantom read가 정말 발생하나? 시니어힌트: 표준 정의 / InnoDB 구현 / 혼용 예외 — 3단

일반 SELECT(일관된 읽기)만 쓰는 한 발생하지 않는다 — 첫 읽기 시점의 MVCC 스냅샷을 트랜잭션 내내 재사용하므로 다른 트랜잭션의 INSERT가 보이지 않고, 잠금 읽기(UPDATE/DELETE/FOR UPDATE)는 갭 락이 범위 INSERT를 차단한다.

단 예외: 같은 트랜잭션에서 스냅샷 읽기와 잠금 읽기를 섞으면 — SELECT로 3건을 확인한 뒤 SELECT ... FOR UPDATE를 하면 후자는 최신 데이터를 읽으므로 그 사이 커밋된 4번째 행이 나타난다 — phantom처럼 보이는 결과가 나온다. 또 스냅샷은 읽기에만 적용되고 UPDATE는 최신 행에 적용되므로, 남의 커밋 행을 내가 UPDATE하면 그 행이 이후 내 스냅샷에 나타난다.

"표준 정의상 허용 / InnoDB 구현상 대부분 방지 / 잠금 읽기 혼용 시 예외"의 3단 구조로 답하면 정확하다.

재고 차감 동시성 문제를 SERIALIZABLE로 풀면 안 되나?힌트: 광역 vs 국소

기술적으로는 막을 수 있지만 정석이 아니다. SERIALIZABLE은 읽기까지 락을 잡거나(InnoDB) 충돌 트랜잭션을 강제 실패시키는(PostgreSQL SSI) 방식이라, 재고와 무관한 조회 트래픽까지 전부 대기/재시도 비용을 치르고 데드락이 폭증한다.

재고 차감은 "특정 행의 갱신 충돌"이라는 국소 문제이므로 국소 도구로 푼다 — 원자적 UPDATE(SET stock = stock - 1 WHERE ... AND stock >= 1, affected rows로 성공 판정)가 가장 싸고, 차감 전후로 검증/부가 로직이 필요하면 SELECT ... FOR UPDATE(비관적 락), 충돌이 드물면 버전 컬럼 기반 낙관적 락 + 재시도. "격리 수준은 광역 설정, 쓰기 충돌은 국소 락"이 답의 뼈대다.

격리 수준을 실무에서 바꾸거나 확인해본 경험이 있나?힌트: 확인 → 판단 근거 → 데드락 로그

경험 스토리의 뼈대: ① 운영 DB의 기본값을 실제로 확인해본 경험(SELECT @@transaction_isolation) — "MySQL이라 REPEATABLE READ가 기본이었다"만 말해도 실무 감각 전달. ② 배치/통계성 긴 조회에서 스냅샷 유지 비용(undo 로그 누적, purge 지연) 때문에 READ COMMITTED로 낮추는 판단, 또는 반대로 정합성이 중요한 정산 로직에서 FOR UPDATE를 선택한 판단처럼 "바꿨다"보다 "왜 그 수준이면 충분했다/부족했다를 판단했다"를 말하는 게 좋다. ③ 갭 락으로 인한 데드락 로그(SHOW ENGINE INNODB STATUS)를 추적해본 경험이 있다면 REPEATABLE READ의 비용을 체감으로 안다는 강한 신호가 된다. (4-3절의 판단 카드 구조를 그대로 쓴다.)

스프링 @Transactional의 격리 수준 기본값은? 함정힌트: 특정 수준이 아니다

Isolation.DEFAULT — 특정 수준이 아니라 DB 기본값을 따른다는 의미다. 그래서 같은 애플리케이션 코드도 MySQL(REPEATABLE READ)과 PostgreSQL(READ COMMITTED) 위에서 다른 격리 수준으로 돈다. 명시 지정 시 트랜잭션 시작 시점에 커넥션에 설정했다가 종료 시 원복하며, 이미 열린 트랜잭션에 합류하는 경우에는 적용되지 않는다.

추가 꼬리질문 — 약점을 콕 찍어 묻는 것들

격리성(I)과 원자성(A)의 차이를 한 문장씩으로? 약점 겨냥힌트: 혼자의 끝 / 남과의 사이

원자성(A)은 "한 트랜잭션이 끝났을 때 전부 반영되거나 전부 취소되거나" — 나 혼자의 시간축 문제이고 도구는 undo 로그로 롤백. 격리성(I)은 "동시에 도는 다른 트랜잭션이 내 중간 상태를 보느냐" — 남과의 사이의 동시성 문제이고 도구는 락·MVCC·격리 수준.

헷갈리는 이유는 InnoDB에서 undo 로그가 둘을 겸직하기 때문(롤백용 이전 값 = 남에게 보여줄 과거 버전). 장치는 하나여도 답하는 질문이 다르다. 격리 수준 4단계는 I만의 다이얼이다 — A는 어느 격리 수준에서도 항상 보장된다.

READ COMMITTED에서 non-repeatable read가 생기는 이유를 Read View로 설명하면?힌트: 셔터를 언제 누르나

RC는 SELECT 문장마다 새 Read View를 만든다. 첫 SELECT의 Read View 이후 다른 트랜잭션이 커밋하면, 두 번째 SELECT의 새 Read View에는 그 커밋이 "이미 끝난 트랜잭션"으로 들어가므로 최신 값이 보인다. RR은 첫 SELECT의 Read View를 끝까지 재사용하므로 그 커밋이 "내 스냅샷 이후의 일"로 계속 취급되어 옛 버전을 본다. 둘 다 MVCC이고 차이는 생성 시점 하나다.

격리 수준 이름만 보고 어떤 현상을 막는지 알 수 있나?힌트: 이름이 곧 막는 현상

있다. READ COMMITTED = "커밋된 것만 읽는다" → dirty read 차단. REPEATABLE READ = "같은 행을 반복해 읽어도 같다" → non-repeatable read 차단. SERIALIZABLE = "직렬 실행과 같다" → 남은 phantom까지 전부 차단. READ UNCOMMITTED는 "커밋 안 된 것도 읽는다" → 아무것도 안 막는다. 매트릭스를 잊어도 이름에서 복원할 수 있다.

MySQL에서 RC로 낮추면 갭 락이 사라지나? 그럼 무엇이 좋아지고 무엇을 조심하나? 가산점힌트: 대부분 안 쓴다 / 데드락↓ / binlog

RC에서는 일반적인 검색·갱신에 갭 락을 대부분 쓰지 않고 레코드 락만 잡는다(외래 키·유니크 키 검사 같은 일부 경우 제외). 그래서 범위 조건 UPDATE/DELETE와 INSERT가 섞이는 구간의 삽입 대기와 데드락이 크게 줄고, 스냅샷도 문장 단위라 긴 트랜잭션의 undo 부담이 준다.

조심할 것: ① non-repeatable read·phantom이 허용되므로 "같은 값을 두 번 읽어 판단"하는 로직이 없는지 점검, 필요한 곳은 FOR UPDATE. ② MySQL은 RC에서 binlog가 ROW 형식이어야 한다(요즘 기본값이지만 오래된 설정은 확인). ③ 전역으로 내릴지, 해당 트랜잭션만 @Transactional(isolation=READ_COMMITTED)로 내릴지는 별개 결정.

Lost update(갱신 유실)는 어느 격리 수준에서 막히나? 시니어힌트: 표준 매트릭스에 없다 / 스냅샷은 읽기만

두 트랜잭션이 같은 행을 읽고 → 계산하고 → 쓰는 패턴에서 나중 쓰기가 먼저 쓰기를 덮는 현상이다. SQL 표준 매트릭스의 세 현상에는 들어 있지 않다.

InnoDB RR은 막지 못한다 — 일반 SELECT는 스냅샷(옛 값)을 읽고 UPDATE는 최신 행에 그대로 덮어쓰기 때문이다(잠금 읽기가 아닌 한 충돌을 감지하지 않는다). PostgreSQL RR은 먼저 커밋한 갱신과 충돌하면 직렬화 오류로 실패시킨다. SERIALIZABLE은 양쪽 다 막는다. 그러나 정석은 격리 수준이 아니라 원자적 UPDATE(stock = stock - 1) · FOR UPDATE · 낙관적 락이다 — 5절의 국소 도구 3종이 바로 lost update 대책이다.

PostgreSQL에서 READ UNCOMMITTED로 설정하면 어떻게 되나?힌트: 지원하지 않는다

설정은 받아들이지만 READ COMMITTED로 동작한다. PostgreSQL은 MVCC 구조상 커밋 안 된 버전을 남에게 보여줄 이유가 없어 RU 자체를 제공하지 않는다. Oracle도 RU·RR을 제공하지 않고 RC / SERIALIZABLE만 있다 — "4단계는 표준이고 DB마다 실제 제공 단계는 다르다"는 사실을 아는지 보는 확인 질문.

REPEATABLE READ의 스냅샷은 BEGIN 시점에 만들어지나?힌트: 아니다. 첫 SELECT

아니다. InnoDB는 첫 일관된 읽기(일반 SELECT)를 실행하는 순간 Read View를 만든다. BEGIN 후 한참 있다가 첫 SELECT를 하면 스냅샷은 그 SELECT 시점이다. 즉시 만들고 싶으면 START TRANSACTION WITH CONSISTENT SNAPSHOT. 이 디테일은 "긴 트랜잭션이 언제부터 purge를 막기 시작하는가"에도 그대로 적용된다 — 첫 SELECT부터다.

관련 문서

트랜잭션 ACID선행 — 격리 수준은 I의 다이얼. A/I 혼동을 여기서 끊는다 MVCC와 InnoDB 구현후속 — Read View 4요소·undo 체인·RC/RR 생성 시점의 내부 갭 락 · 넥스트 키 락 · 데드락후속 — RR이 "쓰기에서" phantom을 막는 장치와 그 비용 SELECT … FOR UPDATE 락 범위국소 도구 — 쓰기 충돌을 격리 수준 대신 락으로 긴 트랜잭션의 해악사슬 B — 스냅샷 유지 비용은 트랜잭션 길이에 비례
한 줄 요약
격리 수준 4단계는 dirty read(커밋 안 된 값) / non-repeatable read(같은 행의 값 변경, UPDATE) / phantom read(행 개수 변경, INSERT·DELETE)를 어디까지 허용하느냐의 매트릭스인데, 실제 DB는 표준과 다르게 동작하고(MySQL 기본 REPEATABLE READ는 MVCC+갭 락으로 phantom까지 대부분 방지, PostgreSQL/Oracle 기본은 READ COMMITTED), 스프링 @Transactional의 기본값은 이 DB 기본값을 그대로 따르며(ISOLATION_DEFAULT), 쓰기 충돌 같은 국소 동시성 문제는 격리 수준 올리기가 아니라 락/원자적 UPDATE로 푸는 것이 정석이다.
