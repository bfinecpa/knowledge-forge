백업이 "있다"와 복구가 "된다"의 거리 — PITR의 메커니즘 사슬과 복구 훈련으로 마지막 방어선을 검증한다

질문: "백업이 "있다"와 복구가 "된다"의 차이는? PITR(특정 시점 복구)과 복구 훈련은 어떻게 하나요?"

핵심 관전 포인트 — 면접 첫 답변으로 그대로 말한다

백업은 "파일이 존재한다"가 아니라 "정해진 시간(RTO) 안에, 정해진 손실(RPO) 이내로, 앱이 붙어 동작하는 DB가 실제로 다시 만들어진다"가 증명됐을 때만 백업이다. 복구를 한 번도 연습 안 한 백업은 없는 것과 같다.
  1. "있다"와 "된다" 사이에는 검증 단계가 있다 — 파일 손상, binlog 유실로 생긴 갭, 위치 기록 불일치, 절차 부재, RTO 초과, 계정·스키마·암호화 키 누락은 전부 "복구하는 날" 처음 발견된다.
  2. PITR은 버튼이 아니라 사슬이다 — 전체 백업(물리 or 논리) 복원 → 그 백업이 찍힌 binlog 위치(포지션/GTID)부터 순서대로 재생 → 원하는 시각(삭제 사고라면 사고 문장의 위치) 직전에서 정지. 전제는 binlog 활성화(ROW)·보존 기간 ≥ 백업 주기·오프호스트 전송·sync_binlog=1·백업과 binlog 위치의 기록 일치·일관 스냅샷.
  3. 삭제 사고는 운영 DB를 통째로 되돌리지 않는다 — 별도 인스턴스에 사고 직전 시점을 재구성한 뒤 지워진 행만 운영에 병합한다 (사고 후 들어온 정상 주문을 지키기 위해).
  4. 이 전부를 사람 기억이 아니라 파이프라인·런북에 고정한다 — 주 1회 자동 복구 훈련(임시 인스턴스 복원 → 체크섬·행 수 검증 → 소요 시간 기록 → RTO 대비 알람).
이 문항의 함정 둘. "복제본이 있으니 백업은 됐다" — 잘못된 DROP TABLE은 밀리초 뒤 복제본에서도 실행된다(복제는 실수도 복제한다). "binlog 켜두면 PITR 된다" — 전제조건 사슬 6고리 중 1개만 말한 것이다.

1"있다"와 "된다" 사이의 거리를 이름 붙여 잰다

두 문장은 서로 다른 것을 주장한다. 이 차이를 먼저 입력/출력의 언어로 고정하면, 뒤의 모든 내용(사슬·트레이드오프·훈련)이 "출력을 확인하는 방법"으로 정렬된다.

1-1. 두 문장은 다른 것을 주장한다

"있다"입력이 있었다는 주장
어딘가에 파일이 존재하고, 백업 잡이 어젯밤 "성공" 로그를 남겼다. 파일을 열어본 적은 없다.
"된다"출력을 확인했다는 주장
그 파일에서 정해진 시간 안에(RTO), 정해진 손실 이내로(RPO), 앱이 붙어서 동작하는 DB가 다시 만들어졌다.

두 주장 사이에는 "복원해서 열어봤는가"라는 검증 단계가 있다. 이 단계를 생략한 팀은 사고 당일 처음으로 그 단계를 밟는다.

소화기로 외우기

소화기가 벽에 걸려 있다(있다)와, 불이 났을 때 핀을 뽑으면 실제로 분말이 나온다(된다)는 다른 명제다. 후자는 점검 스티커(정기 훈련)로만 보증된다. 스티커가 오래됐으면 소화기를 믿지 말라는 신호다 — 4-2절 런북 맨 위에 "마지막 훈련 일자"를 적는 이유.

1-2. RPO / RTO — "된다"의 두 기준

"된다"는 감이 아니라 두 숫자로 판정한다. 정의를 한 줄로, 그 값을 무엇이 결정하는지 목록으로 고정한다.

RPO · RTO — 정의와 결정 요소

RPO Recovery Point Objective
"사고가 나면 최대 얼마 분량의 데이터 손실을 감수하는가"

단위: 시간 분량 (예: 5분, 24시간). P = Point = 어느 시점까지 돌아가나 → 잃는 양.

  1. 전체 백업 주기 — 로그 재생이 없으면 RPO = 백업 주기
  2. binlog 보존·전송 주기 — PITR이 되면 "마지막으로 안전한 곳에 도착한 binlog까지"로 줄어든다. 원본 디스크에만 있으면 디스크 소실 시 다시 백업 주기로 튄다
  3. 커밋 시 로그 동기화 — sync_binlog=1·innodb_flush_log_at_trx_commit=1이 아니면 크래시 직전 트랜잭션이 binlog에 없을 수 있다
  4. 비즈니스 요구 — 결제 원장은 0에 가깝게, 조회 로그는 하루도 가능. 테이블 군마다 다르게
RTO Recovery Time Objective
"사고 후 서비스가 다시 살아나기까지 최대 얼마를 허용하는가"

단위: 시간. T = Time = 돌아가는 데 걸리는 시간.

  1. 백업 형식 — 물리(파일 복사)는 크기에 비례해 빠르고, 논리(SQL 재실행)는 인덱스 재구축 때문에 훨씬 느리다
  2. 데이터 크기 + 마지막 전체 백업 이후 경과 시간 — 재생할 binlog 양이 곧 시간
  3. 절차의 자동화 정도 — 문서 찾기·타이핑·담당자 도착 시간이 전부 RTO
  4. 복원할 자리 — 인스턴스·디스크·네트워크 권한을 여는 시간
  5. 전환 시간 — DNS/엔드포인트 변경, 앱 재기동, 트래픽이 붙기까지

누가 줄이나: RPO는 binlog 상시 전송이, RTO는 물리 백업 + 자동화가 산다. 그리고 둘 다 훈련으로만 실측된다 — "RTO 1시간"이라고 적은 문서와 "지난주 훈련 47분" 기록은 다른 것이다. RPO↓·RTO↓는 공짜가 아니다(3-4절).

1-3. 백업이 있는데 복구가 실패하는 원인 10종

이 목록이 "있다"와 "된다"의 거리 그 자체다. 공통점 하나 — 전부 복구하는 날 처음 발견된다. 면접에서는 두 부류로 묶어 말한다.

실패 원인 10종 — 물건 5 / 절차·체계 5

"물건"의 문제 (파일·로그·키) 복원 테스트가 잡는다
  • 1파일 자체가 손상·불완전 — 덤프 중 디스크 풀, 압축 깨짐, 전송 중 잘림. 로그는 "성공"인데 열리지 않는다
  • 2binlog 유실로 갭 — 보존 기간 < 백업 주기라 앞부분이 지워짐, 또는 데이터와 같은 디스크라 함께 소실. 고리 하나 없으면 그 뒤는 전부 재생 불가
  • 3백업과 binlog 위치가 안 맞음 — 백업 순간의 파일명·포지션(GTID)을 기록 안 함. 너무 앞이면 중복 적용, 뒤면 유실
  • 4백업이 일관되지 않음 — 덤프 중 DDL, 스냅샷 없이 테이블별로 떠서 테이블 간 시점이 다름. 복원은 되는데 데이터가 서로 안 맞는다
  • 8암호화 키·자격증명 없음 — KMS 키 권한이 사고 난 계정에 묶임, 키 로테이션으로 옛 백업 못 품
"절차·체계"의 문제 훈련·런북·모니터링이 잡는다
  • 5절차가 사람 머릿속에만 — 런북 부재·낡음, 그 사람은 휴가 중. 새벽 3시에 처음 읽는 문서엔 항상 빠진 단계가 있다
  • 6복구 시간이 RTO 초과 — 수 TB 논리 복원이 이틀. 기술적으로 "된다"지만 비즈니스적으로 "안 된다"
  • 7복구 대상 누락 — 데이터만 있고 스키마 이력·계정·권한·파라미터·트리거·프로시저·이벤트가 없다. 앱이 붙자마자 권한 에러
  • 9복원할 자리 없음 — 저장소가 원본과 같은 리전·계정이라 함께 죽음, 또는 복원 인스턴스 디스크 부족
  • 10백업이 몰래 멈춰 있었음 — 크론이 몇 달 전부터 실패, 실패 알림 없음, 크기 0 파일이 매일 생성

가산점 물건은 복원 테스트가, 절차는 훈련과 런북이, 체계는 모니터링이 잡는다 — 4절이 그 셋을 한 파이프라인으로 묶는다. 마무리 문장은 항상 "이 전부가 복구하는 날 처음 발견되므로, 정기 복구 훈련만이 사전에 잡는다".

2메커니즘 — PITR은 "전체 백업 + 로그 순서 재생 + 직전 정지"라는 사슬이다

PITR(Point-In-Time Recovery) = 어떤 시점 T0의 전체 백업을 복원한 뒤, T0 이후의 모든 변경 기록(MySQL은 binlog, PostgreSQL은 WAL 아카이브)을 순서대로 다시 적용하다가, 원하는 시각(또는 특정 문장의 위치) 직전에서 멈추는 것. "버튼"이 아니라 세 단계다.

사진 + CCTV로 외우기

전체 백업은 자정에 찍은 사진이고, binlog는 그 뒤로 계속 돌아가는 CCTV 녹화다. 사고 직전 상태를 되살리려면 ① 사진을 벽에 건다(복원) ② 사진이 찍힌 시각부터 녹화를 빠른 재생한다(roll-forward) ③ 사고 장면 직전 프레임에서 일시정지한다(stop-position). 녹화가 중간에 지워졌거나(보존 기간), 사진에 "몇 시 몇 분에 찍음"이 안 적혀 있거나(위치 기록), 녹화기가 사진과 같은 건물에서 같이 탔으면(오프호스트) 재생은 거기서 끝난다.

2-1. 세 단계 — 시간축으로 본다

redo log ≠ binlog — 원리는 같고 역할이 다르다

재생의 원리는 ACID 문서 §2-2의 redo와 같다 — 커밋된 변경을 로그로 다시 적용한다. 다만 redo log는 InnoDB가 크래시 복구용으로 짧게 순환시키는 물리 로그고, binlog는 MySQL 서버가 "무슨 변경이 있었는지"를 논리/행 단위로 남기는 보존용 로그다. 그래서 MySQL에서 PITR은 binlog의 몫이다. (PostgreSQL은 WAL 하나가 크래시 복구와 PITR을 겸한다 — 아카이브된 WAL을 restore_command로 가져와 recovery_target_time까지 재생. 개념은 동일.)

2-2. 전제조건 사슬 6고리 — 하나라도 끊기면 그 지점부터 복구 불가

PITR은 옵션 하나가 아니라 전제조건들이 직렬로 연결된 사슬이다. 면접에서 "binlog 켜두면 된다"로 끝내지 말고 사슬로 말한다.

6고리 — 각 고리가 왜 필요한가 (사슬로 말하기)

  1. binlog 켜짐 + ROW 포맷 (log_bin, binlog_format=ROW) — 문장 기반은 NOW()나 정렬 없는 LIMIT처럼 재실행 결과가 달라지는 문장이 있어, ROW여야 재생 결과가 결정적이다.
  2. 보존 기간 ≥ 백업 주기 + 여유 (binlog_expire_logs_seconds, 구버전 expire_logs_days) — 마지막 전체 백업 시점의 binlog가 아직 남아 있어야 한다. 백업이 한 번 실패해도 끊기지 않을 여유(주기의 2~3배)를 둔다.
  3. binlog가 원본 서버 밖에 있다 — 서버 디스크에만 있는 binlog는 디스크와 함께 죽는다. 복제본에도 binlog를 기록하게 하거나, 오브젝트 스토리지로 주기적으로 밀어 올리거나, mysqlbinlog의 원격 실시간 수신 모드로 별도 호스트에 계속 받아둔다.
  4. 커밋마다 binlog가 디스크에 내려간다 (sync_binlog=1, 짝으로 innodb_flush_log_at_trx_commit=1) — 아니면 크래시 직전 커밋 몇 개가 데이터에는 있고 binlog에는 없어, 재생 결과가 원본과 어긋난다. 대가는 커밋마다 fsync 한 번 더 — "성능을 위해" 끄는 순간 RPO는 "마지막 fsync까지"로 후퇴한다.
  5. 백업이 찍힌 binlog 위치가 기록돼 있다 — 논리 백업은 덤프 머리에 파일명·포지션을 주석으로 남기는 --source-data=2(구 --master-data=2), 물리 백업은 xtrabackup_binlog_info 파일. GTID를 쓰면 "어느 트랜잭션까지 포함됐는가"가 서버 간에 이식 가능한 식별자로 남는다.
  6. 백업 자체가 일관된 스냅샷이다 — 논리 백업은 --single-transaction으로 하나의 MVCC 스냅샷에서 뜬다(MVCC 문서의 REPEATABLE READ 일관 읽기 = "덤프 시작 순간의 세상"). 도중에 DDL이 끼면 깨지므로 배포 창과 백업 창을 분리한다. 물리 백업은 복사 중 바뀐 페이지를 redo로 맞추는 준비(prepare) 단계가 이 역할.

before/after로 대비하면 — "백업은 매일 하고 있다"는 크론 한 줄이 사슬을 몇 개나 끊고 있는지 보인다.

# - --single-transaction 없음     → 테이블마다 시점이 다른 덤프    (고리 ⑥ ✗)
# - /backup 이 원본과 같은 디스크 → 디스크 장애 시 같이 소실      (고리 ③ ✗)
# - 실패해도 아무도 모름                                           (1-3절 ⑩)
# ✅ after: 사슬을 전부 잇는다 (요지 — 세부 옵션은 팀 표준에 맞춘다)
set -euo pipefail
DAY=$(date +%F)
mysqldump -u backup \
  --single-transaction \            # 하나의 MVCC 스냅샷고리 ⑥
  --source-data=2 \                 # 덤프 머리에 binlog 파일명·포지션 주석고리 ⑤

  shop | gzip > /backup/shop-$DAY.sql.gz

# binlog도 주기적으로 오프사이트로 (또는 원격 실시간 수신 호스트 운영)
# 마지막 성공 시각·파일 크기를 메트릭으로 발행 → 24h 이상 갱신 없으면 알람1-3절 ⑩

# 0) 사고 직후 가장 먼저: 현재 binlog를 보존한다 (만료로 지워지기 전에 사본 확보)

#    (물리 백업이면 xtrabackup_binlog_info 의 파일명·포지션)

# 2) 로그 재생 — 시작 위치부터 목표 시각 직전까지, 파일들을 "한 번의 호출"로② 재생

            --stop-datetime="2026-08-31 14:07:00" \
            /safe/binlogs/binlog.000410 /safe/binlogs/binlog.000411 /safe/binlogs/binlog.000412 \
  | mysql -h recovery-host
#    --start-position 은 첫 파일에, --stop-* 는 마지막 파일에 적용된다.
#    파일을 하나씩 따로 재생하지 않는 이유: 파일 경계에 걸친 세션 상태(임시 테이블 등)가 끊긴다.

# 3) 검증 후 전환 (또는 필요한 행만 병합 — 2-4절)③ 정지 후

--stop-datetime은 초 단위다

그 1초 안에 정상 커밋과 사고 커밋이 섞여 있으면 정상 커밋도 함께 잘리거나 사고가 함께 들어간다. 그래서 삭제 사고에서는 시각이 아니라 위치(--stop-position)로 멈춘다. 시각은 "대략 언제"를 좁히는 용도(2-4절 ②), 위치는 실제 정지선.

2-4. "삭제 사고 직전 시점" 시나리오 — 운영을 되돌리지 않고 행만 되살린다

가장 자주 그려보게 되는 시나리오. 14:05경 배치가 WHERE 없는 DELETE FROM orders를 날렸고, 14:20에 알림으로 발견했다. 왜 운영 DB를 통째로 14:05로 되돌리면 안 되는가 — 14:05~14:20 사이에 들어온 정상 주문·결제가 있다. 통째로 되돌리면 그 15분이 사라진다(RPO가 사고→발견 시간만큼 커진다).

# 1) 사고 시각 특정 — 앱 로그·알림·배치 실행 기록으로 "대략 14:04~14:06"

# 2) binlog에서 사고 문장의 위치 찾기 (ROW 포맷은 -v 로 의사 SQL을 풀어서 본다)
mysqlbinlog --base64-output=DECODE-ROWS -v \
  --start-datetime="2026-08-31 14:03:00" --stop-datetime="2026-08-31 14:08:00" \
  /safe/binlogs/binlog.000412 \
  | grep -n -B12 -m1 "### DELETE FROM \`shop\`.\`orders\`"
#   출력 위쪽으로 거슬러 올라가 사고 트랜잭션의 BEGIN 앞에 있는 "# at 8834211" 이 시작 위치
#   (수천 행이 지워졌다면 Delete_rows 이벤트가 길게 이어진다 — 트랜잭션 첫머리의 "# at" 을 잡는다)

# 3) 별도 인스턴스에 전체 백업 복원 (2-3절 1단계)

# 4) 백업 위치부터 사고 트랜잭션 "직전"까지 재생
mysqlbinlog --start-position=1573 --stop-position=8834211 \
  /safe/binlogs/binlog.000410 /safe/binlogs/binlog.000411 /safe/binlogs/binlog.000412 \
  | mysql -h recovery-host
#   → recovery-host 의 orders 는 "지워지기 직전" 상태

# 5) 운영에 없는 행만 골라 병합 (사고 후 운영에 새로 생긴 행과 PK 충돌하지 않게)
mysqldump -h recovery-host --no-create-info --insert-ignore shop orders > /tmp/orders_restore.sql
mysql -h prod-host shop < /tmp/orders_restore.sql
#   INSERT IGNORE: 운영에 이미 있는 PK(사고 후 새로 생긴 주문)는 건너뛴다.
#   자식 테이블(order_item 등)도 같은 방식으로 — FK 순서 주의.
#   병합 전후로 행 수·금액 합계를 운영 팀과 대조한다.

30초 답변 골격 — "DELETE를 30분 뒤에 발견했습니다"

"운영을 30분 전으로 되돌리면 그 30분의 정상 주문까지 지워지므로 안 됩니다. 절차는 ⓪ 즉시 binlog 보존(FLUSH BINARY LOGS + 사본) → ① 앱 로그로 시각을 좁히고 mysqlbinlog -v로 사고 트랜잭션의 # at 위치를 찾고 → ② 별도 인스턴스에 전체 백업 복원 → ③ 백업 위치부터 그 위치 직전(--stop-position)까지 재생 → ④ 지워진 행만 INSERT IGNORE로 병합(자식 테이블은 FK 순서) → ⑤ 행 수·합계 대조. 통째로 되돌릴지 행만 병합할지는 비즈니스 결정이라 런북에 결정권자를 적어둡니다."

3트레이드오프 — 백업 방식은 "무엇을 지키려고 무엇을 지불하는가"로 고른다

네 선택지의 "얻는 것"만 나열하면 도구 이름을 아는 사람이고, "지불하는 것"까지 짝지어 말하면 써 본 사람이다. 표는 요약이고 판단은 아래 본문이다.

3-1. 선택지 4종 — 얻는 것 / 지불하는 것

방식대표 형태얻는 것지불하는 것

3-2. 물리 vs 논리 — "빠르다"의 대가는 "묶인다"이다

물리 백업은 InnoDB 데이터 파일을 그대로 복사하면서, 복사하는 동안 바뀐 부분을 redo 로그로 추적해 두었다가 준비 단계에서 맞춘다(크래시 복구와 같은 원리). 수백 GB~수 TB에서 유일하게 현실적인 RTO를 준다. 대가는 같은 메이저 버전·같은 엔진에서만 열린다는 것 — 업그레이드를 건너뛴 옛 백업을 새 서버에 얹는 시나리오가 막힌다. 그래서 물리 백업을 쓰는 팀도 주기적 논리 백업 한 벌을 별도로 남긴다(이식성 보험).

논리 백업은 SQL 문(또는 행 데이터)이라 어디서든 열리고, 특정 테이블만 골라 복원할 수 있고, 에디터로 열어 사고 문장을 찾을 수도 있다. 대가는 시간이다 — 복원은 INSERT를 다시 실행하는 것이고 세컨더리 인덱스는 그 위에서 다시 만들어진다(B+Tree가 통째로 재구성). 또 --single-transaction 덤프는 그 자체가 긴 읽기 트랜잭션이라 undo 누적·퍼지 지연 비용을 운영 서버에 지운다 — 그래서 논리 백업은 대개 복제본에서 뜬다. mydumper처럼 병렬로 뜨고 넣는 도구가 시간을 줄여주지만 "인덱스를 다시 만든다"는 본질은 같다.

"둘 다, 역할을 나눠서"

크기가 RTO를 결정한다 → 수백 GB 이상이면 물리 백업이 기준점, 여기에 주기적 논리 백업 한 벌(이식성 보험 + 테이블 단위 복원)을 복제본에서 뜬다. 어느 쪽이든 RPO는 binlog 상시 전송이 책임진다.

선택의 최종 기준은 "복원 훈련이 실측한 RTO가 목표 안에 들어오는가" — 훈련 없는 선택은 추정일 뿐이다.

3-3. 스냅샷 — "즉시"의 대가는 "일관성과 장애 도메인"이다

볼륨 스냅샷은 찍는 데 몇 초고 복원도 볼륨을 갈아 끼우는 수준이라 RTO가 매우 짧다. 그러나 ⑴ DB를 멈추지 않고 찍은 스냅샷은 크래시 일관성이다 — "전원을 뽑은 순간의 디스크"와 같아서, 그 위에서 기동한 InnoDB는 redo/undo로 크래시 복구를 수행한다(그래서 대개 복원은 된다). 다만 데이터 파일과 binlog가 서로 다른 볼륨에 있으면 두 스냅샷의 시점이 어긋나 PITR 시작점이 흔들린다. 잠깐 쓰기를 멈추거나(FLUSH TABLES WITH READ LOCK 같은 정지 창), 관리형 서비스의 일관 스냅샷을 쓴다. ⑵ 스냅샷이 원본과 같은 리전·같은 계정에 있으면 리전 장애·계정 탈취·실수로 인한 계정 정리에서 원본과 함께 사라진다 — 다른 리전/계정으로 복사하는 단계까지 있어야 "백업"이다.

3-4. 빈도 — RPO를 사면 부하와 비용을 낸다

전체 백업 빈도를 올리면 로그 재생분이 줄어 RTO도 줄고, PITR이 없는 환경이라면 RPO도 줄어든다. 대가는 ⑴ 백업 중 I/O·CPU 부하(운영 서버에서 뜨면 지연으로 직결), ⑵ 저장 비용(세대 수 × 크기), ⑶ 논리 백업이면 긴 트랜잭션의 빈도 증가.

흔한 절충 공식

주 1회 전체 + 매일 증분(물리 백업의 증분 모드) + binlog 상시 전송

RPO는 binlog가 책임지고, 전체 백업은 RTO를 위한 기준점 갱신 역할만 한다. 두 지표를 각각 누가 사는지 분리해서 말하면 "빈도를 올리면 좋다"보다 한 단계 위의 답이다.

3-5. 복제본은 백업이 아니다 — "가용성"과 "복구"는 다른 축

복제는 실수도 복제한다

잘못 날린 DROP TABLE은 복제 지연만큼의 밀리초 뒤 복제본에서도 실행된다.

복제본은 하드웨어 장애(원본 서버가 죽음)에 대한 답이지 논리 사고에 대한 답이 아니다. 복제본이 지키는 것은 "서비스가 계속 응답한다"(가용성), 백업이 지키는 것은 "과거의 올바른 상태로 돌아갈 수 있다"(복구 가능성). 축이 다르므로 어느 하나가 다른 하나를 대체하지 않는다.

1층복제본가용성 — 원본 하드웨어가 죽어도 응답.
침묵: 논리 사고(밀리초 뒤 같이 실행), 랜섬웨어, 리전 장애
2층 (선택)지연 복제본지연 창 안의 논리 사고에 즉시 대응 — 2-4절의 "별도 인스턴스"를 미리 데워두는 셈.
침묵: 창을 넘긴 발견, 디스크 소실, 리전 장애. 비용: 인스턴스 1대, 승격 시 지연분 따라잡으며 사고 직전에서 멈추는 제어
3층오프사이트 백업 + binlog복구 가능성 — 보존 기간 내 어느 시점으로든. 최후의 복구선.
비용: 저장·전송, 재구성 시간(RTO), 그리고 훈련 없이는 "있다"일 뿐

3-6. 관리형 DB(RDS 등)의 PITR — 버튼 뒤의 사슬은 같다

클라우드 관리형 DB의 "특정 시점으로 복원"은 내부적으로 자동 스냅샷 + 짧은 주기로 올려둔 트랜잭션 로그를 재생하는, 2장과 같은 사슬이다. 알아둘 성질 세 가지 — ⑴ 복원 결과는 기존 인스턴스를 덮어쓰지 않고 새 인스턴스로 만들어진다(2-4절의 "별도 인스턴스에 복원 → 병합" 패턴이 기본 동작인 셈). ⑵ 복원 가능한 최신 시점은 "지금"이 아니라 마지막으로 로그가 올라간 시각이고, 보존 기간을 넘긴 과거로는 못 간다. ⑶ 파라미터 그룹·보안 그룹·계정 권한·엔드포인트는 자동으로 붙지 않으므로 1-3절 ⑦의 "복구 대상 누락"은 관리형에서도 그대로 발생한다. 버튼이 있어도 훈련은 필요하다 — 복원에 얼마나 걸리는지, 앱을 새 엔드포인트로 돌리는 절차가 무엇인지는 눌러봐야 안다.

4안전망 고정 — 복구 훈련을 사람의 의지가 아니라 파이프라인·런북에 박는다

"분기마다 복구 테스트를 하자"는 다짐은 두 번째 분기에 사라진다. 고정하려면 자동으로 돌고, 실패하면 알람이 오고, 결과가 기록으로 남는 형태여야 한다. 1-3절의 세 부류(물건·절차·체계)를 하나의 파이프라인이 다 잡는다.

주 1회 스케줄→오프사이트에서 백업+binlog 가져옴→임시 인스턴스 복원→기준 시각까지 재생→검증 5종 (열린다 ≠ 맞다)→소요 시간 메트릭→RTO 80% 초과 알람→정리 + 훈련 대장 기록

4-1. 자동 복구 훈련 파이프라인 — 셸 의사코드

#!/usr/bin/env bash
# restore-drill.sh — 주 1회 스케줄러(cron / CI 스케줄 잡)에서 실행
set -euo pipefail                             # 어느 assert든 실패하면 즉시 종료 → 스케줄러가 실패 알람
START=$(date +%s)
RTO_SEC=3600                                  # 팀이 합의한 RTO (예: 1시간)
DRILL_HOST=drill-db-$(date +%Y%m%d)
AS_OF=$(date -d '1 hour ago' '+%F %T')        # 재생 기준 시각 (훈련 시작 1시간 전)

# 1) 최신 전체 백업 + 그 이후 binlog 를 "오프사이트 저장소에서" 가져온다
#    (원본 서버의 로컬 사본을 쓰면 고리 ③을 검증하지 못한다)
aws s3 cp s3://db-backup-other-region/shop/latest/ /drill/backup/  --recursive고리 ③
aws s3 cp s3://db-backup-other-region/shop/binlog/ /drill/binlogs/ --recursive
gzip -t /drill/backup/*.gz                    # 파일 무결성원인 ①

# 2) 임시 인스턴스 기동 (컨테이너 / 임시 VM / 관리형 PITR 복원 — 환경에 맞게)
provision_temp_instance "$DRILL_HOST"

# 3) 기준점 복원 + binlog 를 기준 시각까지 재생 (2-3절 그대로 — 실제 복구와 같은 함수)
restore_full_backup "$DRILL_HOST" /drill/backupPITR ①
replay_binlog_until "$DRILL_HOST" /drill/binlogs "$AS_OF"PITR ②③ · 갭 검증

# 4) 검증 — "열린다"가 아니라 "맞다"를 확인한다
#    4-a 스키마 객체 수: 테이블·뷰·프로시저·트리거 개수가 운영과 같은가원인 ⑦
assert_equal "$(count_objects prod-replica shop)" "$(count_objects "$DRILL_HOST" shop)"
#    4-b 핵심 테이블 행 수: append-only 테이블은 기준 시각 이전 행 수를 양쪽에서 세어 비교
for t in orders payments users; do
  Q="SELECT COUNT(*) FROM shop.$t WHERE created_at < '$AS_OF'"
  assert_within_tolerance "$(mysql -h prod-replica  -N -e "$Q")" \
                          "$(mysql -h "$DRILL_HOST" -N -e "$Q")" 0.001
done
#    4-c 체크섬: 변경이 드문 기준 테이블(코드 테이블 등)은 CHECKSUM TABLE 로 일치 확인
assert_equal "$(mysql -h prod-replica  -N -e 'CHECKSUM TABLE shop.currency')" \
             "$(mysql -h "$DRILL_HOST" -N -e 'CHECKSUM TABLE shop.currency')"
#    4-d 도메인 불변식: "원장 합계 = 결제 합계" 같은 비즈니스 규칙이 복원본에서 성립하는가
assert_equal "$(mysql -h "$DRILL_HOST" -N -e 'SELECT SUM(amount) FROM shop.ledger')" \
             "$(mysql -h "$DRILL_HOST" -N -e 'SELECT SUM(paid)   FROM shop.payments')"
#    4-e 앱 스모크: 읽기 전용 앱 인스턴스를 붙여 헬스체크·대표 API 1~2개 호출
smoke_test_app_against "$DRILL_HOST"

# 5) 소요 시간 기록 → 메트릭 → RTO 대비 알람
ELAPSED=$(( $(date +%s) - START ))
push_metric backup.restore_drill.seconds "$ELAPSED"      # 추세 그래프 = "데이터가 커져 RTO가 밀리는 것"을 잡는다
push_metric backup.restore_drill.success 1
if (( ELAPSED > RTO_SEC * 80 / 100 )); then원인 ⑥ 사전 탐지
  alert "복구 훈련 소요 ${ELAPSED}s — RTO(${RTO_SEC}s)의 80% 초과. 데이터 증가에 RTO가 밀리고 있다."
fi

# 6) 정리 + 기록 (성공/실패·소요 시간·검증 결과를 훈련 대장에 append)
teardown_temp_instance "$DRILL_HOST"
append_drill_log "$DRILL_HOST" "$ELAPSED" ok체크리스트 ⑩

실패하면(어느 assert든) set -e로 즉시 종료되고 스케줄러가 실패 알람을 낸다 — 그 알람이 곧 "백업은 있는데 복구는 안 된다"를 사고 전에 발견한 것이다. 스케줄은 주 1회를 기본으로, 큰 스키마 변경·버전 업그레이드·백업 방식 변경 직후에는 수동으로 한 번 더 돌린다.

백업 파이프라인 자체의 모니터링 4메트릭 — 원인 ⑩은 이 중 하나만 있어도 잡힌다

1마지막 백업 성공 후 경과 시간 2백업 크기의 전일 대비 변화 (급감 = 적신호) 3오프사이트 전송 성공 여부 4binlog 전송 지연 (원본 최신 위치 vs 저장소 도착 위치)

훈련의 최종 형태 — "훈련 스크립트가 곧 복구 스크립트"

훈련에서 쓰는 함수(restore_full_backup, replay_binlog_until)와 실제 사고에서 쓰는 함수가 같은 코드면, 매주 실행되는 훈련이 곧 실제 복구 절차의 회귀 테스트가 된다. 런북의 명령도 같은 함수를 부르게 만들면 런북과 실제가 어긋나지 않는다. 이 원칙은 대량 삭제/아카이빙 문서의 "아카이브한 데이터를 삭제 전에 복원해서 검증한다"와 같은 뿌리다 — 지워도 되는지의 증명은 '아카이브 파일이 있다'가 아니라 '아카이브에서 돌아온다'다.

4-2. 런북 — 새벽 3시에 처음 읽는 사람이 따라 할 수 있게

  1. 어디에 무엇이 있는가 — 백업 저장소 경로, binlog 저장소 경로, 암호화 키 위치와 그 키에 접근 가능한 역할, 복원용 인스턴스를 만들 권한.
  2. 시나리오별 분기 — ⑴ 원본 서버 소실(전체 복원 후 전환) ⑵ 논리 사고(별도 인스턴스 PITR 후 행 병합, 2-4절) ⑶ 특정 테이블만 손상. 시나리오마다 "정지점을 어떻게 정하는가"가 다르다.
  3. 복사-붙여넣기 가능한 명령 — 2-3·2-4절 수준으로, 변수만 바꾸면 되게. 훈련 스크립트와 같은 함수를 쓰게 만든다.
  4. 검증 단계 — 4-1의 4-a~4-e를 사람이 수행하는 버전.
  5. 전환 절차 — 엔드포인트/DNS 변경, 앱 재기동 순서, 캐시 무효화, 복제 토폴로지 재구성.
  6. 의사결정자와 연락 체계 — "통째로 되돌릴 것인가, 행만 병합할 것인가"는 기술 결정이 아니라 비즈니스 결정(사고 후 정상 데이터를 얼마나 잃을 것인가)이므로, 누가 결정하는지 적어둔다.
  7. 마지막 훈련 일자와 실측 소요 시간 — 문서 맨 위에. 이 줄이 오래됐으면 문서를 믿지 말라는 신호다(소화기 점검 스티커).

4-3. 복구 훈련 체크리스트 10항목

훈련 1회가 "통과"하려면 전부 예여야 한다

  1. 백업 파일을 오프사이트 저장소에서 가져와 열었는가 (로컬 사본 말고). 고리 ③ · 원인 ①⑨
  2. 백업 메타데이터의 binlog 위치부터 빠짐없이 로그를 이어 붙일 수 있었는가 (갭 없음). 고리 ②⑤ · 원인 ②③
  3. 임의의 과거 시각(또는 특정 위치)까지 재생을 멈출 수 있었는가. PITR ③
  4. 스키마 객체 수·핵심 테이블 행 수·기준 테이블 체크섬·도메인 불변식이 운영과 일치했는가. 원인 ④
  5. 계정·권한·파라미터·트리거·프로시저·이벤트가 복원본에 존재하는가. 원인 ⑦
  6. 앱 인스턴스를 복원본에 붙여 대표 요청이 성공했는가.
  7. 처음부터 끝까지의 소요 시간이 RTO 이내였는가 — 그리고 지난 훈련 대비 추세는. 원인 ⑥
  8. 절차를 런북만 보고 수행했는가 (머릿속 지식 없이). 막힌 지점은 런북에 반영했는가. 원인 ⑤
  9. 암호화 키·자격증명에 사고 시나리오의 계정으로 접근 가능했는가. 원인 ⑧
  10. 결과(성공/실패·소요·발견 사항)를 기록으로 남겼는가. 원인 ⑩

외우는 순서: 가져와(①) → 잇고(②) → 멈추고(③) → 맞는지(④⑤⑥) → 시간(⑦) → 런북만으로(⑧) → 키(⑨) → 기록(⑩). 실패 원인 10종과 1:1로 대응된다 — 체크리스트는 원인 목록을 "예/아니오"로 뒤집은 것이다.

5꼬리질문 셀프 테스트

질문만 먼저 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 보라색 배지는 시니어 변별 포인트, 회색 배지는 md에 없는 추가 꼬리질문.

"PITR을 하려면 뭐가 준비돼 있어야 하나요? binlog만 켜두면 되나요?"

아니다 — 사슬이다. ⑴ binlog 활성화 + ROW 포맷, ⑵ 보존 기간이 전체 백업 주기보다 길 것(백업이 한 번 실패해도 끊기지 않을 여유 포함), ⑶ binlog가 원본 서버 밖(복제본·오브젝트 스토리지·원격 수신 호스트)에도 존재할 것, ⑷ sync_binlog=1로 커밋마다 디스크에 내려갈 것(아니면 크래시 직전 커밋이 binlog에 없어 재생 결과가 어긋난다), ⑸ 전체 백업이 찍힌 binlog 파일명·포지션(또는 GTID)이 백업과 함께 기록될 것, ⑹ 전체 백업 자체가 일관된 스냅샷일 것. 어느 고리가 끊기든 그 지점 이후로는 돌아갈 수 없다. "binlog 켜두면 된다"는 ⑴만 말한 것이다. → 2-2

"백업 파일은 매일 잘 생기고 있는데, 복구가 안 될 수 있는 경우를 구체적으로 말해보세요."

두 부류로 답한다. 물건의 문제: 파일 손상·불완전(한 번도 열어보지 않음), binlog 유실로 갭, 백업과 binlog 위치 기록 불일치, 비일관 덤프, 암호화 키 접근 불가. 절차·체계의 문제: 런북 부재, 복구 시간이 RTO 초과(수 TB 논리 복원), 계정·권한·파라미터·트리거 누락, 백업 저장소가 원본과 같은 장애 도메인, 백업 잡이 몰래 실패 중인데 알림 없음. 마무리는 "이 전부가 복구하는 날 처음 발견된다는 공통점이 있어서, 정기 복구 훈련만이 사전에 잡는다"로. → 1-3

"실수로 DELETE를 날려서 30분 뒤에 발견했습니다. 운영 DB를 30분 전으로 되돌리면 되나요?"

안 된다 — 그 30분 동안 들어온 정상 주문·결제까지 지워진다(RPO가 사고→발견 시간만큼 커진다). 절차는 ⑴ 즉시 현재 binlog를 보존(FLUSH BINARY LOGS 후 사본), ⑵ 앱 로그·배치 기록으로 사고 시각을 좁히고 mysqlbinlog -v로 binlog에서 해당 DELETE 이벤트가 속한 트랜잭션의 시작 위치(# at N)를 찾고, ⑶ 별도 인스턴스에 전체 백업을 복원한 뒤 백업 위치부터 그 위치 직전(--stop-position)까지 재생 — 시각(--stop-datetime)은 초 단위라 같은 초의 정상 커밋이 섞일 수 있어 위치가 정확하다, ⑷ 복원본에서 지워진 행만 뽑아 운영에 INSERT IGNORE(사고 후 새로 생긴 PK와 충돌 방지)로 병합, 자식 테이블도 FK 순서대로, ⑸ 병합 전후 행 수·금액 합계 대조. "통째로 되돌릴지, 행만 병합할지"는 비즈니스 결정이라 런북에 결정권자를 적어둔다. → 2-4

"복제본이 있으니 백업은 없어도 되지 않나요?" 시니어 변별

축이 다르다. 복제본은 가용성(원본 하드웨어가 죽어도 서비스가 계속 응답)의 장치고, 백업은 복구 가능성(과거의 올바른 상태로 돌아감)의 장치다. 잘못된 DROP TABLE은 밀리초 뒤 복제본에서도 실행되므로 복제본은 논리 사고를 막지 못한다. 지연 복제본을 두면 지연 창 안의 논리 사고에는 즉시 대응할 수 있지만 — 대가로 인스턴스 1대, 지연 창을 넘겨 발견하면 무용, 승격 시 지연분을 따라잡으며 사고 직전에서 멈추는 제어가 필요, 그리고 디스크 소실·리전 장애·복제본까지 번지는 랜섬웨어에는 여전히 무력하다. 결론은 "복제본(가용성) + 지연 복제본(빠른 논리 사고 대응, 선택) + 오프사이트 백업과 binlog(최후의 복구선)"의 층이고, 어느 하나가 다른 하나를 대체하지 않는다. 각 층이 어떤 장애에 답하고 어떤 장애에 침묵하는지를 짝지어 말하는 것이 변별점이다. → 3-5

"물리 백업과 논리 백업 중 무엇을 쓰시겠어요?" 시니어 변별

"둘 다, 역할을 나눠서"가 답이고 이유가 핵심이다. 크기가 RTO를 결정하므로 수백 GB 이상이면 물리 백업(XtraBackup류)이 기준점 — 파일 복사라 빠르고, 복원도 준비 단계 후 바로 기동한다. 대가는 버전·엔진 종속이라, 업그레이드 경계를 넘거나 다른 시스템으로 옮기는 시나리오를 위해 주기적 논리 백업 한 벌을 따로 남긴다(이식성 보험 + 테이블 단위 선택 복원). 논리 백업은 복제본에서 뜬다 — --single-transaction 덤프가 긴 읽기 트랜잭션이라 운영 서버의 undo·퍼지에 부담을 주기 때문. 어느 쪽이든 RPO는 백업이 아니라 binlog 상시 전송이 책임진다. 마지막으로 "어느 쪽을 골랐든 복원 훈련이 실측한 RTO가 목표 안에 들어오는가"가 선택의 최종 기준이다 — 훈련 없는 선택은 추정일 뿐이다. → 3-2

"--stop-datetime이 있는데 왜 굳이 --stop-position을 찾나요?" 추가

--stop-datetime은 초 단위다. 사고 커밋과 같은 1초 안에 정상 커밋이 섞여 있으면, 그 초 전체를 자르면 정상 커밋이 함께 잘리고, 그 초를 포함하면 사고가 함께 들어간다. 위치(# at N)는 트랜잭션 단위 경계라 정확히 사고 트랜잭션 직전에서 멈춘다. 그래서 시각은 "대략 언제인지 좁히는 검색 범위"(mysqlbinlog -v --start/stop-datetime)로 쓰고, 실제 정지선은 위치로 잡는다. → 2-3

"redo log가 있는데 왜 PITR은 binlog로 하나요? 둘 다 '로그 재생' 아닌가요?" 추가

원리는 같다 — 커밋된 변경을 로그로 다시 적용한다. 역할이 다르다. redo log는 InnoDB가 크래시 복구용으로 고정 크기 안에서 짧게 순환시키는 물리(페이지 단위) 로그라 오래 보존되지 않고, 서버 밖으로 나가지도 않는다. binlog는 MySQL 서버 층에서 "무슨 변경이 있었는지"를 논리/행 단위로 보존하는 로그라 복제와 PITR의 재료가 된다. 그래서 크래시 직후 마지막 몇 초는 redo가, 자정부터 14:05까지는 binlog가 책임진다. PostgreSQL은 WAL 하나가 두 역할을 겸하고, 아카이브된 WAL을 restore_command로 가져와 recovery_target_time까지 재생한다. → 2-1

"sync_binlog=1을 끄면 성능이 좋아진다던데, 왜 안 되나요?" 추가

대가를 정확히 말해야 한다. 끄면 커밋마다 fsync 한 번이 줄어 쓰기 처리량은 오르지만, 크래시 순간 데이터 파일(redo로 보호됨)에는 있는데 binlog에는 없는 커밋이 생긴다. 그러면 ⑴ 그 binlog로 재생한 PITR 결과가 원본과 어긋나고, ⑵ 복제본도 그 커밋을 못 받는다. 즉 RPO가 "마지막 커밋"에서 "마지막 fsync"로 후퇴한다. ACID 문서의 "로그도 fsync까지 내려가야 D가 성립한다"가 binlog에도 그대로 적용된다. 결제 원장처럼 RPO≈0이 요구되는 도메인에서는 끌 수 없고, 끈다면 "우리 RPO는 그만큼이다"를 문서에 적고 합의해야 한다. → 2-2 고리 ④

"binlog 파일 3개를 하나씩 순서대로 mysqlbinlog | mysql 하면 안 되나요?" 추가

파일 경계에 걸친 세션 상태가 끊긴다 — 예컨대 임시 테이블을 만든 세션이 다음 파일에서 그 임시 테이블을 쓰는데, 별도 호출이면 새 mysql 세션이라 임시 테이블이 없다. 그래서 파일들을 한 번의 mysqlbinlog 호출에 순서대로 넘긴다. 이때 --start-position은 첫 파일에, --stop-*는 마지막 파일에 적용된다. → 2-3

"지연 복제본을 1시간으로 걸어뒀는데 사고를 2시간 뒤에 발견했습니다. 어떻게 하나요?" 추가

지연 창을 넘겼으므로 지연 복제본에도 이미 사고가 적용됐다 — 이 층은 무용이다. 그래서 3층(오프사이트 백업 + binlog)으로 내려간다: 2-4절 절차 그대로, 별도 인스턴스에 전체 백업 복원 → 사고 트랜잭션 직전까지 재생 → 행만 병합. 이 질문의 요지는 "지연 복제본은 백업을 대체하지 못하고, 발견이 빠를 때의 지름길일 뿐"임을 아는지다. 덧붙이면: 지연 창 안에 발견했더라도 복제본을 그대로 승격하면 안 되고, 지연분을 사고 직전까지만 따라잡도록(START REPLICA UNTIL 계열) 제어한 뒤 행을 꺼내야 한다. → 3-5

"논리 백업은 왜 운영 서버가 아니라 복제본에서 뜨나요?" 추가

--single-transaction 덤프는 덤프가 끝날 때까지 하나의 MVCC 스냅샷을 유지하는 긴 읽기 트랜잭션이다. 그동안 운영에서 갱신된 행의 옛 버전(undo)을 퍼지하지 못해 undo가 누적되고, 긴 버전 체인을 따라가느라 읽기가 느려진다(긴 트랜잭션 문서). 수 시간짜리 덤프를 운영 서버에서 뜨면 그 비용을 운영 트래픽이 진다. 복제본에서 뜨면 운영은 무관하다 — 단, 복제본이 지연되고 있으면 덤프의 binlog 위치도 그만큼 과거이므로, 위치 기록(고리 ⑤)은 복제본 기준으로 정확히 남겨야 한다. → 3-2

"RDS는 PITR 버튼이 있는데도 복구 훈련이 필요한가요?" 추가

필요하다. 버튼이 대신해 주는 것은 2장의 사슬(스냅샷 + 로그 재생)뿐이다. 눌러봐야만 아는 것 — ⑴ 우리 크기에서 복원에 실제로 몇 분 걸리는지(RTO), ⑵ 복원은 새 인스턴스로 만들어지므로 앱을 새 엔드포인트로 돌리는 절차와 그 시간, ⑶ 파라미터 그룹·보안 그룹·계정 권한이 자동으로 붙지 않아 생기는 "복구 대상 누락"(원인 ⑦), ⑷ 복원 가능한 최신 시점이 "지금"이 아니라 마지막 로그 업로드 시각이라는 점(RPO), ⑸ 보존 기간을 넘긴 과거로는 못 간다는 점. 관리형이라 사슬을 안 봐도 되는 게 아니라, 사슬 중 어디까지를 공급자가 맡고 어디부터가 우리 몫인지가 바뀌는 것이다. → 3-6

"복구 훈련에서 '열린다'와 '맞다'는 어떻게 다르게 검증하나요?" 추가

"열린다"는 복원본에 접속되고 테이블이 보인다는 것 — 원인 ①·⑤만 잡는다. "맞다"는 5종 검증이다: 4-a 스키마 객체 수(테이블·뷰·프로시저·트리거)가 운영과 같은가(원인 ⑦), 4-b append-only 핵심 테이블의 기준 시각 이전 행 수가 양쪽에서 같은가(갭·비일관 탐지), 4-c 변경이 드문 기준 테이블의 CHECKSUM TABLE 일치, 4-d 도메인 불변식("원장 합계 = 결제 합계")이 복원본에서 성립하는가, 4-e 읽기 전용 앱을 붙여 대표 API 호출 성공. 여기에 소요 시간을 RTO와 비교하는 것까지가 한 세트다. → 4-1

61분 인출 테스트

면접 직전 — 아래 항목을 펼치기 전에 답이 3초 안에 나오는지 확인한다.

"있다" vs "된다"를 한 문장으로.

"있다"는 입력이 있었다(파일 존재, 성공 로그), "된다"는 출력을 확인했다(RTO 안에, RPO 이내로, 앱이 붙는 DB). 사이에 "복원해서 열어봤는가"가 있다. → 1-1

RPO·RTO 정의와 각각 누가 줄이나.

RPO = 최대 감수하는 데이터 손실 분량(Point, 어디까지 돌아가나) → binlog 상시 전송이 줄인다. RTO = 서비스 복귀까지 최대 허용 시간(Time) → 물리 백업 + 자동화가 줄인다. 둘 다 훈련으로만 실측. → 1-2

PITR 3단계.

① 전체 백업 복원(DB = T0) → ② 기록된 binlog 위치부터 순서대로·빠짐없이 재생 → ③ 목표 시각(삭제 사고면 사고 문장의 위치) 직전에서 정지. → 2-1

전제조건 6고리 — 순서대로.

binlog 넷: ① 켜짐(ROW) ② 남음(보존 ≥ 주기) ③ 밖(오프호스트) ④ 내림(sync_binlog=1) / 백업 둘: ⑤ 적힘(binlog 위치 기록) ⑥ 일관(--single-transaction / prepare). 하나 끊기면 그 지점 이후 복구 불가. → 2-2

실패 원인 10종 — 두 부류로.

물건(①파일 손상 ②binlog 갭 ③위치 불일치 ④비일관 덤프 ⑧키 없음) → 복원 테스트가 잡음. 절차·체계(⑤런북 부재 ⑥RTO 초과 ⑦대상 누락 ⑨자리 없음 ⑩몰래 멈춤) → 훈련·런북·모니터링이 잡음. 공통점: 복구하는 날 처음 발견. → 1-3

삭제 사고 대응 — 왜 운영을 되돌리지 않나, 절차 5단계.

사고→발견 사이의 정상 주문이 지워지므로(RPO 증가). ⓪ binlog 보존 → ① # at 위치 특정 → ② 별도 인스턴스에 전체 백업 복원 → ③ --stop-position 직전까지 재생 → ④ INSERT IGNORE로 행만 병합(FK 순서) → ⑤ 행 수·합계 대조. → 2-4

4종 백업 방식 — 각각 지불하는 것 한 마디.

물리: 버전·엔진 종속. 논리: 느림(인덱스 재구축) + 긴 트랜잭션. 스냅샷: 크래시 일관성 + 같은 장애 도메인. 지연 복제본: 창 넘기면 무용 + 백업 대체 불가. → 3-1

"복제본 ≠ 백업"을 한 문장으로.

복제본은 가용성, 백업은 복구 가능성 — 잘못된 DROP은 밀리초 뒤 복제본에서도 실행된다. → 3-5

흔한 빈도 절충 공식.

주 1회 전체 + 매일 증분 + binlog 상시 전송 — RPO는 binlog가, 전체 백업은 RTO 기준점 갱신만. → 3-4

훈련 파이프라인 6단계와 검증 5종.

오프사이트에서 가져옴 → 임시 인스턴스 → 복원+재생 → 검증(객체 수 · 행 수 · 체크섬 · 불변식 · 앱 스모크) → 소요 시간 메트릭 + RTO 80% 알람 → 정리·기록. 훈련 함수 = 복구 함수. → 4-1

런북 맨 위에 적는 한 줄은?

마지막 훈련 일자와 실측 소요 시간 — 오래됐으면 문서를 믿지 말라는 신호(소화기 점검 스티커). → 4-2

체크리스트 10항목 — 순서 연상.

가져와(오프사이트) → 잇고(갭 없음) → 멈추고(임의 시점) → 맞는지(객체·행·체크섬·불변식 / 계정·권한·트리거 / 앱 요청) → 시간(RTO 이내·추세) → 런북만으로 → 키(사고 계정으로) → 기록. → 4-3

한 줄 요약

백업이 "있다"는 파일의 존재고, 복구가 "된다"는 RTO 안에 RPO 이내로 앱이 붙는 DB가 다시 만들어진다는 검증된 사실이다 — 그 사이를 가르는 것은 파일 손상·binlog 갭·위치 불일치·절차 부재·RTO 초과·계정·키 누락이고, 전부 복구하는 날 처음 드러난다. PITR은 전체 백업 복원 → 기록된 binlog 위치부터 순서대로 재생 → 목표 시각(삭제 사고라면 사고 문장의 위치) 직전 정지라는 사슬이며, 보존 기간·오프사이트·sync_binlog=1·위치 기록이 그 고리다. 삭제 사고는 운영을 되돌리지 않고 별도 인스턴스에서 직전 시점을 만들어 행만 병합하고, 이 전부를 주 1회 자동 복구 훈련(복원 → 체크섬·행 수·불변식 검증 → 소요 시간 기록 → RTO 대비 알람)과 런북으로 고정한 팀만이 "복구가 된다"고 말할 자격이 있다.
