트랜잭션 ACID — 글자마다 "한 줄 정의 + 메커니즘 하나"로 고정한다

📖 약 15분 🧩 5개 섹션 0/5 섹션 이해
🎯 핵심 관전 포인트

ACID는 암기 항목이 아니라 글자마다 "한 줄 정의 + 그것을 구현하는 메커니즘 하나"를 묶어서 말하는 문제다. A(원자성) = 전부 반영 or 전부 취소, 중간 상태 없음 — undo log / C(일관성) = 트랜잭션 전후로 시스템의 불변식·제약이 유지 — DB 제약 + 애플리케이션의 공동 책임 / I(격리성) = 동시 트랜잭션이 서로의 중간 상태를 보지 않음 — 락 + MVCC / D(지속성) = 커밋 응답 후엔 전원이 나가도 보존 — redo log(WAL). 특히 두 가지를 틀리지 말 것: ① "끼어들 수 없다"는 격리성의 언어다 — 원자성은 동시성이 아니라 실패에 대한 보장. ② 로그 쓰기도 똑같은 디스크 I/O다 — 다만 파일 끝 순차 append라서 싸고, 흩어진 페이지의 랜덤 쓰기는 나중에 모아서 한다. 이게 WAL이 존재하는 이유다.

질문 + 의도

▾
면접 질문

"트랜잭션의 ACID를 설명해주세요."

출제 의도개념 암기가 아니라, 이후 꼬리 질문("그럼 커밋 순간 서버가 죽으면 D는 어떻게 보장되나요")의 발판. 각 글자를 실제 메커니즘(redo log, undo, 락/MVCC)과 연결하는지로 깊이를 잰다. 즉 "네 단어를 외웠는가"가 아니라, 각 글자가 무엇으로부터 무엇을 지키는지(실패로부터? 동시성으로 부터? 장애로부터?)와 DB가 그걸 무슨 장치로 구현하는지를 짝지어 말할 수 있는지를 본다. 여기서 짝이 맞으면 격리 수준·MVCC(중급), redo/undo 내부(중급)로 자연스럽게 이어진다.
1

개념 — 네 글자를 "한 줄 정의 + 메커니즘 하나"로 고정

▾

트랜잭션은 여러 개의 작업을 하나의 논리적 단위로 묶은 것이다. 계좌이체가 표준 예시인 이유 — "A 차감"과 "B 입금"이라는 두 UPDATE는 따로 보면 각각 멀쩡하지만, 둘 중 하나만 실행된 세상은 존재해선 안 되기 때문이다. ACID는 이 "하나의 단위"라는 약속을 네 방향에서 지키는 성질들이다.

글자한 줄 정의무엇으로부터 지키나메커니즘
A 원자성(Atomicity)전부 반영 or 전부 취소 — 중간 상태 없음실패(에러·크래시)undo log
C 일관성(Consistency)트랜잭션 전후로 불변식·제약이 항상 유지규칙 위반DB 제약 + 애플리케이션 (공동 책임)
I 격리성(Isolation)동시 트랜잭션이 서로의 중간 상태를 보지 않음동시성락 + MVCC
D 지속성(Durability)커밋 응답 후엔 전원이 나가도 보존장애(전원 차단·크래시)redo log (WAL)

비유로 고정하면 —

  • A: 계약서에 양쪽이 서명하거나, 아무도 안 하거나. "한쪽만 서명된 계약서"라는 물건은 세상에 존재하지 않는다.
  • C: 복식부기 장부. 어떤 거래를 적든 차변과 대변의 총합은 맞아야 한다. 거래(트랜잭션)가 장부의 규칙을 깨면 그 거래 자체가 무효다.
  • I: 각자 회의실에서 작업하고, 문서가 완성되기 전에는 서로의 초안을 들여다보지 않는다.
  • D: 연필이 아니라 잉크로 쓴 서명. 정전이 나도 종이에 남는다.

1-1. A와 I를 절대 섞지 말 것 — "끼어들 수 없다"는 격리성의 언어다

가장 흔한 혼동이자 이 문서가 첫 번째로 교정하는 지점. 원자성을 "트랜잭션 실행 도중 누군가 끼어들 수 없다"로 설명하면 틀린다 — "끼어든다"는 동시성의 언어이고, 동시성을 다루는 글자는 I(격리성)다.

두 글자는 지키는 대상 자체가 다르다:

  • 원자성이 상대하는 적은 "실패"다. 다른 트랜잭션이 하나도 없는, 나 혼자 쓰는 DB에서도 원자성은 필요하다 — UPDATE 두 개 중 첫 번째만 실행되고 서버가 죽으면? 에러가 나서 두 번째를 실행 못 하면? 이때 "절반만 반영된 세상"을 없애는 것이 원자성이다.
  • 격리성이 상대하는 적은 "동시성"이다. 크래시가 절대 없는 완벽한 서버라도, 두 트랜잭션이 같은 계좌를 동시에 만지면 서로의 중간 상태(차감은 됐는데 입금은 아직인 순간)를 볼 위험이 생긴다. 이걸 차단하는 것이 격리성이다.

한 문장 테스트로 구분한다 — "혼자 쓰는 DB에서도 문제가 되면 A, 둘 이상이 써야 문제가 되면 I."

1-2. C는 층위가 다르다 — "같은 쿼리 같은 결과"가 아니다

두 번째 교정 지점. 일관성은 "같은 쿼리를 날리면 같은 결과가 나온다"가 아니다(그건 굳이 분류하면 격리 수준의 반복 읽기 이야기에 가깝다).

일관성의 정의는 이것이다 — 트랜잭션이 시작되기 전에 성립하던 시스템의 규칙(불변식·제약)이, 트랜잭션이 끝난 후에도 여전히 성립한다.

계좌이체로 말하면 규칙은 두 가지다:

  1. 총합 불변: 이체는 돈을 옮기는 것이지 만들거나 없애는 게 아니다. A+B의 총합은 이체 전후로 같아야 한다.
  2. 잔액 ≥ 0: 어떤 순간에도 계좌 잔액은 음수가 될 수 없다(마이너스 통장이 아니라면).

일관성이 깨진 상태란: 10만원을 이체했는데 A에서는 빠졌고 B에는 안 들어와서 두 계좌 총합에서 10만원이 증발한 상태, 또는 잔액 5만원인 계좌에서 10만원이 빠져나가 잔액이 -5만원이 된 상태다. 각 행만 보면 멀쩡한 숫자지만, 시스템 전체의 규칙이 무너져 있다.

이 글자만 유일하게 DB 혼자 다 지켜줄 수 없다는 점이 특징인데, 3절에서 자세히 다룬다.

2

동작 — 계좌이체 한 건으로 네 글자를 관통한다

▾

2-1. before / after — 트랜잭션이 없으면 무슨 일이 벌어지나

sql
-- ❌ before: 트랜잭션 없이 UPDATE 두 방
UPDATE account SET balance = balance - 100000 WHERE id = 'A';
-- ← 여기서 서버 다운 / 애플리케이션 예외 / 네트워크 단절이 나면?
UPDATE account SET balance = balance + 100000 WHERE id = 'B';

-- 결과: A에서 10만원이 빠졌는데 B에는 안 들어옴.
-- "절반만 실행된 세상"이 그대로 남는다 = 원자성 없음
-- → 총합에서 10만원 증발 = 일관성 파괴로 번짐
sql
-- ✅ after: 하나의 트랜잭션으로 묶는다
START TRANSACTION;

UPDATE account SET balance = balance - 100000 WHERE id = 'A';
UPDATE account SET balance = balance + 100000 WHERE id = 'B';

COMMIT;
-- 중간 어디서 실패하든 DB가 undo log로 전부 되돌린다(롤백).
-- 바깥 세상에는 "둘 다 반영" 아니면 "아무 일도 없었음" 두 상태만 존재.

이 한 건의 이체 위에 네 글자가 각각 언제 작동하는지를 붙이면 정의가 저절로 복원된다:

  • A가 작동하는 순간: 첫 UPDATE 후, 둘째 UPDATE 전에 서버가 죽었다. 재시작한 DB는 커밋되지 않은 이 트랜잭션을 발견하고 undo log를 따라 차감 전 상태로 되돌린다. A 잔액은 원래대로.
  • D가 작동하는 순간: COMMIT 성공 응답을 클라이언트가 받은 직후 전원이 나갔다. 재시작해도 이체 결과는 남아 있어야 한다 — redo log 덕분에 남는다(2-3절).
  • I가 작동하는 순간: 이체가 진행되는 도중 다른 트랜잭션이 A와 B의 잔액을 조회했다. "차감만 되고 입금은 안 된" 중간 상태를 보여주면 안 된다 — 락 또는 MVCC(과거 스냅샷 읽기)로 차단한다.
  • C가 확인되는 순간: 커밋 전후로 총합 불변·잔액 ≥ 0이라는 규칙이 유지됐는가. A·I·D라는 도구 + 제약 + 애플리케이션 로직이 합작한 결과로서 지켜진다.

2-2. undo와 redo — "되돌리기 장부"와 "다시하기 장부"

이름이 비슷해서 섞이기 쉬운데, 담당 글자가 다르다:

  • undo log — A의 도구. 변경하기 전 값을 기록해 둔다("A 잔액은 원래 50만원이었다"). 롤백하거나 크래시 후 미커밋 트랜잭션을 정리할 때 이 장부를 거꾸로 따라가며 원상복구한다.
  • redo log — D의 도구. 변경한 후 값을 기록해 둔다("A 잔액을 40만원으로 바꿨다"). 크래시 후 재시작할 때, 테이블 파일에 아직 반영 못 한 커밋된 변경을 이 장부를 따라가며 다시 적용한다.

크래시 복구는 이 둘의 합작이다 — redo로 로그에 있는 변경을 다시 적용한 다음, undo로 커밋 안 된 트랜잭션만 골라 되돌린다. 그래서 "커밋된 것은 살아남고(D), 커밋 안 된 것은 흔적 없이 사라진다(A)"가 동시에 성립한다.

2-3. WAL이 존재하는 이유 — 로그 쓰기도 디스크 I/O다, 다만 싸다

이 문서가 세 번째로 교정하는 지점. "테이블 파일을 고치는 건 I/O라서 느리고, 로그는 그냥 갖고 있으면 되니까 빠르다"는 설명은 틀렸다. 로그 쓰기도 똑같이 디스크에 쓰는 I/O다. 메모리에만 갖고 있으면 전원이 나가는 순간 같이 증발하므로 D를 보장할 수 없다 — 커밋 시점에 로그는 반드시 디스크까지 내려가야 한다(fsync).

그럼 왜 굳이 로그에 먼저 쓰나? 같은 디스크 쓰기라도 접근 패턴이 다르기 때문이다. (이 랜덤 vs 순차 비용 모델은 Q2의 인덱스 손익분기, Q3의 페이지 분할과 정확히 같은 축이다.)

  • 테이블(데이터 페이지)에 직접 반영 = 이번 트랜잭션이 건드린 행들이 들어 있는 페이지들은 디스크 여기저기에 흩어져 있다. 커밋마다 이걸 다 쓰려면 흩어진 위치를 오가는 랜덤 쓰기 — 비싸다.
  • 로그에 기록 = 로그는 하나의 파일이고, 쓰기는 항상 파일 끝에 이어붙이기(순차 append) 다. 헤드가 이동할 필요 없이 한 방향으로만 쓴다 — 같은 디스크 I/O지만 훨씬 싸다.

그래서 전략이 WAL(Write-Ahead Logging, 로그 선행 기입) 이다:

💡

커밋 순간에는 싼 순차 쓰기(로그 append + fsync)만 하고 응답한다. 변경된 데이터 페이지는 메모리(버퍼 풀)에 더티 상태로 두었다가, 나중에 비싼 랜덤 쓰기를 모아서(체크포인트) 천천히 반영한다. 그 사이에 죽어도 redo log가 디스크에 있으니 D는 깨지지 않는다.

한 줄로 — "로그도 디스크 쓰기다. 다만 순차 append라 싸고, 비싼 랜덤 쓰기는 뒤로 미뤄 모아서 한다." 이 문장이 나오면 WAL의 존재 이유를 이해한 것이고, 안 나오면 외운 것이다.

3

실무 사례 — 일관성은 누가 지키나: DB와 애플리케이션의 공동 책임

▾

C가 네 글자 중 유일하게 "DB가 알아서" 다 못 해주는 글자다. 규칙에는 두 부류가 있기 때문이다.

① DB가 선언적으로 강제할 수 있는 규칙 — 스키마에 박아둘 수 있다:

sql
-- ❌ before: "잔액은 음수가 될 수 없다"를 애플리케이션 코드만 믿는다
CREATE TABLE account (
    id      VARCHAR(20) PRIMARY KEY,
    balance BIGINT NOT NULL
);
-- 코드에서 if (balance >= amount) 검사를 하더라도 —
-- 검사와 차감 사이에 다른 요청이 끼어들면(동시성) 음수 잔액이 뚫린다.
-- 검사를 빼먹은 신규 API 하나만 있어도 뚫린다.

-- ✅ after: 최후의 방어선을 DB 제약으로 선언
CREATE TABLE account (
    id      VARCHAR(20) PRIMARY KEY,
    balance BIGINT NOT NULL,
    CONSTRAINT chk_balance_non_negative CHECK (balance >= 0)
);
-- 어떤 경로로 UPDATE가 들어와도, 잔액을 음수로 만드는 트랜잭션은
-- DB가 에러를 내고 거부 → 롤백(A가 C를 지키는 도구로 동원된다).

NOT NULL, UNIQUE, FK, CHECK가 이 부류다. 어떤 코드 경로로 들어와도 우회 불가능하다는 것이 애플리케이션 검증에 없는 강점이다.

② DB에 선언할 수 없는 비즈니스 규칙 — "이체 총합은 불변이어야 한다", "VIP 등급은 연 구매액 천만원 이상만 가능하다" 같은 규칙은 CHECK 한 줄로 표현이 안 된다. 이건 애플리케이션이 트랜잭션 안에서 지켜야 하고, DB는 그 코드가 절반만 실행되지 않게(A), 동시 실행에 찢기지 않게(I) 도구를 제공할 뿐이다.

그래서 정확한 문장은 이렇다 — "DB는 자신이 아는 제약을 강제하고 A·I·D라는 도구를 제공한다. 그 도구 위에서 비즈니스 불변식까지 지켜 '일관된 상태 → 일관된 상태'로 옮기는 최종 책임은 애플리케이션과 DB의 공동 책임이다." (가산점 포인트) 일관성을 이렇게 "공동 책임"으로 설명하면, ACID를 DB 기능 목록이 아니라 시스템 설계의 언어로 쓰고 있다는 신호가 된다.

(가산점 포인트) 네 글자가 이후 어떤 질문의 발판인지 지도를 갖고 있으면 꼬리질문이 두렵지 않다 — I → 격리 수준 4단계와 MVCC(중급), D → redo log/체크포인트, A → undo log와 롤백 비용, 그리고 긴 트랜잭션이 왜 위험한가(undo 누적, 중급)로 이어진다.

4

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

남아 있어야 한다 — 그게 D(지속성)의 정의다. "커밋 성공"이라는 응답은 "이제 무슨 일이 있어도 이 결과는 보존된다"는 약속이기 때문이다. 보장 수단은 redo log(WAL): 커밋 시점에 변경 내역을 로그 파일에 순차 append하고 fsync로 디스크까지 내려보낸 뒤에야 성공을 응답한다. 테이블 파일(데이터 페이지)에는 아직 반영 전이어도 상관없다 — 재시작한 DB가 redo log를 읽어 커밋된 변경을 다시 적용(redo) 하기 때문이다. 요점은 "메모리 어딘가에 갖고 있다"가 아니라 "응답 전에 디스크의 로그에 내려갔다"는 것.

맞다, 로그 쓰기도 똑같은 디스크 I/O다 — 이걸 인정하는 데서 답이 시작된다. 차이는 접근 패턴이다. 트랜잭션이 건드린 행들은 디스크 여기저기 흩어진 페이지에 있어서 직접 반영은 랜덤 쓰기이고, 로그는 하나의 파일 끝에 순차 append라 같은 양을 써도 훨씬 싸다. 그래서 커밋 순간엔 싼 순차 쓰기만 하고, 비싼 랜덤 쓰기는 버퍼 풀에 모아뒀다가 체크포인트 때 배치로 처리한다. "로그는 I/O가 아니라서 빠르다"라고 답하면 즉시 감점 — 로그가 디스크에 안 내려가면 D 자체가 성립하지 않는다.

구체적으로 두 가지 — ① 이체 후 두 계좌 총합에서 이체액만큼 증발한 상태(차감만 반영), ② 잔액이 음수가 된 상태(제약 뚫림). "같은 쿼리 같은 결과"는 일관성의 정의가 아니다. 그리고 DB 혼자는 못 지킨다 — NOT NULL·UNIQUE·FK·CHECK처럼 선언 가능한 제약은 DB가 강제하지만, "총합 불변" 같은 비즈니스 불변식은 선언할 방법이 없어 애플리케이션이 트랜잭션(A·I라는 도구) 안에서 지켜야 한다. "DB 제약 + 애플리케이션의 공동 책임"이라는 문장까지 나와야 완결된 답이다.

undo = A, redo = D. undo는 변경 전 값을 적어두는 "되돌리기 장부"로 롤백·미커밋 정리에 쓰이고, redo는 변경 후 값을 적어두는 "다시하기 장부"로 크래시 후 커밋된 변경 재적용에 쓰인다. 둘 다 필요한 이유: 크래시 순간 디스크의 데이터 파일에는 "커밋됐는데 아직 반영 안 된 변경"(redo로 다시 적용해야) 과 "커밋 안 됐는데 이미 반영된 변경"(체크포인트가 더티 페이지를 미리 내렸을 수 있다 — undo로 되돌려야) 이 동시에 존재할 수 있기 때문이다. 복구는 redo 먼저 전부 재적용 → 미커밋분만 undo로 롤백 순서다.

각 글자의 메커니즘이 전부 "트랜잭션이 살아 있는 동안" 자원을 붙들고 있기 때문이다. ① A의 undo가 누적된다 — 롤백에 대비해 변경 전 값을 계속 쌓아야 하고, 트랜잭션이 길수록 undo 영역이 비대해지며 만약 롤백하면 그 긴 장부를 거꾸로 다 타야 해서 롤백 자체가 오래 걸린다. ② I의 락·스냅샷이 오래 유지된다 — 잡은 락은 커밋까지 안 풀리니 경합이 번지고, MVCC에서는 이 트랜잭션이 봐야 할 과거 버전들을 다른 트랜잭션들이 지우지 못해 오래된 버전이 쌓인다. ③ 여기에 커넥션까지 오래 점유하면 락 경합 → 대기 → 트랜잭션 장기화 → 커넥션 풀 고갈 사슬로 번진다. 그래서 실무 수칙이 "트랜잭션은 짧게, 외부 API 호출은 트랜잭션 밖으로"다. ACID의 네 글자를 보장 목록이 아니라 비용의 원천으로도 읽을 수 있는지가 시니어 변별점이다.

✅ 한 줄 요약

ACID는 글자마다 "한 줄 정의 + 메커니즘"으로 말한다 — A: 전부 반영 or 전부 취소, 실패에 대한 보장(undo log) / C: 트랜잭션 전후 불변식 유지 — 총합 불변·잔액 ≥ 0, DB 제약과 애플리케이션의 공동 책임 / I: 동시 트랜잭션이 중간 상태를 못 본다, 동시성에 대한 보장(락+MVCC) / D: 커밋 응답 후엔 전원이 나가도 보존(redo log/WAL). "끼어들 수 없다"는 격리성의 언어이고, 로그도 똑같은 디스크 I/O지만 순차 append라 싸기에 커밋 순간엔 로그만 쓰고 비싼 랜덤 쓰기는 모아서 나중에 한다.
