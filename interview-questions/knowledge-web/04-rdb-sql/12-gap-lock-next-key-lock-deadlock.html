갭 락과 넥스트 키 락 — "INSERT만 하는데 데드락"의 정체

락은 "행"이 아니라 인덱스 레코드와 그 사이에 걸린다 — 이 문장 하나에서 데드락 타임라인을 스스로 그려내기

Q. 갭 락(gap lock), 넥스트 키 락이란? 어떤 상황에서 데드락을 유발하나요? 관련: 대량 UPSERT(INSERT … ON DUPLICATE KEY UPDATE)의 주의점은? · SELECT … FOR UPDATE는 어떤 락을 잡고, WHERE가 인덱스를 못 타면 무슨 일이 벌어지나?

핵심 관전 포인트 — 첫 답변으로 그대로 말한다

InnoDB의 행 락은 "행"이 아니라 인덱스 레코드에 걸리고, 레코드 사이의 빈 구간(갭)에도 걸린다. 갭 락은 그 구간으로의 INSERT를 막는 것이 유일한 목적이라 갭 락끼리는 충돌하지 않지만, INSERT가 잡는 인서트 인텐션 락은 남의 갭 락에 막힌다.

그래서 두 트랜잭션이 같은 갭을 각자 잠그는 데 둘 다 성공한 뒤 각자 그 갭에 INSERT하면 서로의 갭 락에 막혀 순환 대기 — 이것이 "INSERT만 하는데 데드락"의 정체다. 갭 락은 REPEATABLE READ의 잠금 읽기(FOR UPDATE/UPDATE/DELETE)에서 생기고, READ COMMITTED에서는 유니크 중복 검사·외래 키 검사 때만 남는다.

진단은 SHOW ENGINE INNODB STATUS의 LATEST DETECTED DEADLOCK에서 두 트랜잭션의 HOLDS/WAITING 락 모드를 교차 대조하는 것이고, 처방은 락 순서나 격리 수준이 아니라 "없는 행을 잠그지 않는 설계"(앵커 행 락 · 유니크 제약+INSERT · 단일 UPSERT)에 트랜잭션 밖의 제한된 재시도와 재현 테스트를 안전망으로 얹는 것이다.

30초 답변 스크립트 — "갭 락은 갭에 거는 락입니다"에서 끝내지 말고, 이 네 문장을 순서대로
  1. 정의 — "InnoDB 락은 행이 아니라 인덱스 레코드와 그 사이 갭에 걸립니다. 레코드 락, 갭 락, 둘을 합친 넥스트 키 락, 그리고 INSERT 직전에 잡는 인서트 인텐션 락, 네 가지입니다."
  2. 규칙 한 칸 — "갭 락은 INSERT 차단이 유일한 목적이라 갭 락끼리는 호환되지만, 인서트 인텐션 락은 남의 갭 락에 막힙니다."
  3. 타임라인 — "그래서 RR에서 없는 행을 FOR UPDATE로 잠근 두 트랜잭션이 같은 갭을 둘 다 잠그는 데 성공한 뒤 각자 INSERT하면, 서로의 갭 락에 막혀 순환 대기가 됩니다. 이게 'INSERT만 하는데 데드락'입니다."
  4. 진단·처방 — "진단은 INNODB STATUS의 HOLDS/WAITING 락 모드 교차 대조, 처방은 락 순서나 격리 수준이 아니라 없는 행을 잠그지 않는 설계 — 앵커 행 락, 유니크 제약+INSERT, 단일 UPSERT — 에 트랜잭션 밖 재시도와 재현 테스트를 얹는 겁니다."
1. 락은 어디에 걸리나 2. 락 4종 + 호환표 3. 어떤 문장이 갭 락을 만드나 4. 데드락 타임라인 5. 로그 읽기 6단계 6. 처방과 양면 7. 재현 테스트 8. 꼬리질문 셀프 테스트 한 줄 요약

1락은 어디에 걸리나 — 인덱스 수직선 위에 그리기

"InnoDB의 행 락"은 정확히는 인덱스 레코드 락이다. 테이블의 행이 아니라 인덱스(클러스터드 인덱스 = 테이블 자체, 그리고 세컨더리 인덱스) 위에 정렬된 레코드와, 레코드 사이에 걸린다. 이 문장을 받아들이면 나머지가 전부 따라온다.

예: uk_user_coupon (user_id, coupon_id) 유니크 인덱스에 coupon_id = 7인 레코드가 user_id 5, 10, 20, 30으로 4건. 인덱스 위에는 레코드 4개와 갭 5개가 있다.

비유 — 주차장의 빈 칸과 콘

빈 주차 칸(갭)에 "여기 세우지 마" 콘을 놓는 것이 갭 락이다. 같은 칸에 두 사람이 콘을 놓는 건 같은 주장을 두 번 하는 것이라 서로 막지 않는다(갭 락끼리 호환). 그런데 그 칸에 실제로 차를 대려면(인서트 인텐션) 남이 놓은 콘이 막는다. 둘 다 콘을 놓고 둘 다 차를 못 댄다 — 이게 데드락이다.

이 비유에서 "앵커 행 락" 처방은 콘 대신 주차장 입구 차단봉(항상 존재하는 자원 하나)을 잡는 것이다. 한 명만 통과하고 나머지는 입구에서 기다린다 — 데드락이 아니라 직렬화.

3어떤 문장이 갭 락을 만드나 — RR vs RC

갭 락은 잠금 읽기(locking read)에서만 생긴다. 일반 SELECT는 MVCC 스냅샷을 읽으므로 어떤 락도 잡지 않는다. 잠금 읽기란 SELECT … FOR UPDATE / FOR SHARE, 그리고 UPDATE / DELETE가 대상 행을 찾는 과정이다. (INSERT의 유니크 중복 검사는 별도 경로로 락을 잡는다 — §4 패턴 B.)

RC로 낮추면 얻는 것

검색·스캔의 갭 락·넥스트 키 락 전부 소멸 → 쓰기 동시성 상승. UPDATE/DELETE가 스캔 중 조건에 안 맞는 행의 락을 즉시 해제(RR은 트랜잭션 끝까지 유지).

RC로 낮추면 내주는 것

phantom read 허용 — 같은 트랜잭션에서 잠금 읽기를 두 번 하면 사이에 커밋된 행이 나타난다. 바이너리 로그를 쓰면 ROW 포맷이어야 한다(STATEMENT 복제는 RC에서 정합성이 깨질 수 있어 InnoDB가 거부). 그리고 유니크 중복·외래 키 검사의 갭 락은 못 끈다.

암기"RC는 검색의 갭 락을 끈다 — 단 유니크·FK 검사의 갭 락은 못 끈다." 그래서 "RC로 낮추면 갭 락 데드락이 다 사라진다"는 반만 맞다.

갭 락의 비용 — "락 경합"에서 멈추지 말고 사슬로 끝까지

데드락이 나지 않아도 갭 락은 비용을 만든다. 각 화살표 하나가 면접의 "왜요?"에 대한 답이다. 마지막 두 마디(커넥션 풀 → 전 서비스)까지 통째로 입에 붙여 둔다.

잠금 읽기가 범위·비유니크·인덱스 미사용 조건→ 넥스트 키 락이 레코드뿐 아니라 갭까지 덮음→ 그 값과 무관한(범위에 우연히 드는) INSERT까지 대기→ 대기하는 쓰기 트랜잭션 수명이 잠금 트랜잭션 수명만큼 늘어남→ 그동안 커넥션을 쥔 채 놓지 못함→ 풀 활성 커넥션 ↑ → 풀 고갈→ 무관한 API까지 getConnection 대기→ 전 서비스 응답 시간 상승

4"INSERT만 하는데 데드락" — 한 스텝씩 타임라인으로

애플리케이션 로그에는 INSERT 문장에서 Deadlock found when trying to get lock이 찍힌다. 코드를 보면 INSERT 한 줄. 그래서 "INSERT는 새 행을 만드는 건데 무슨 락 충돌이야?"가 첫 반응이 된다. 경로는 둘이고, 공통점은 INSERT 이전에 갭(또는 레코드) 락이 이미 잡혀 있었다는 것이다.

패턴 A — "없으면 넣기"를 FOR UPDATE로 짠 경우 갭 락 + 인서트 인텐션

쿠폰 발급: "이 사용자가 이미 받았는지 잠그고 확인한 뒤, 없으면 INSERT". uk_user_coupon(user_id, coupon_id), coupon_id = 7에 user_id 5, 10, 20, 30이 발급된 상태. 사용자 15번과 17번이 거의 동시에 요청한다 — 둘 다 (10,20) 갭에 들어가는 값이다.

❌ 없는 행을 FOR UPDATE로 잠그는 코드 — RR에서 갭 락을 만든다
@Transactional
public void issue(long userId, long couponId) {
    var existing = repo.findForUpdate(userId, couponId);  // SELECT … FOR UPDATE → 행 없음 → 갭 락갭 락 획득
    if (existing.isPresent()) throw new AlreadyIssued();
    repo.save(new CouponIssue(userId, couponId));          // INSERT → 인서트 인텐션 락남의 갭 락에 막힘
}
직관을 배신하는 것 ①

값이 겹치지 않는데 난다. 15와 17은 서로 다른 행이다. 충돌하는 건 행이 아니라 두 값이 함께 들어 있는 갭 (10,20)이다.

직관을 배신하는 것 ②

t2에서 B의 잠금이 성공한다. 레코드 락이었다면 B는 t2에서 A를 기다렸다가 이어서 진행해 데드락이 아니라 직렬화가 됐을 것이다. 갭 락은 호환이라 둘 다 "잠갔다고 믿는" 상태가 되고, 그 믿음이 INSERT에서 깨진다.

이 타임라인이 성립하는 조건 4개

하나라도 빠지면 안 난다 — 처방은 이 중 하나를 없애는 것
조건 1격리 수준 RR (갭 락이 켜져 있음)
조건 2잠금 읽기(FOR UPDATE/UPDATE/DELETE)가 존재하지 않는 값이나 범위를 조건으로 함 → 갭 락
조건 3같은 트랜잭션이 이어서 그 갭에 INSERT
조건 4이 트랜잭션이 동시에 둘 이상
같은 얼굴의 변형UPDATE … WHERE key = ? 후 affected rows가 0이면 INSERT하는 "UPSERT 흉내" 코드도 정확히 같은 타임라인이다 — UPDATE가 행을 못 찾으면 갭 락만 남기고 끝나기 때문이다.

패턴 B — 정말로 INSERT 문장만 있는 경우 유니크 중복 검사의 공유 락

이번엔 트랜잭션 안에 INSERT 말고 아무것도 없다. 그런데도 난다. 열쇠는 유니크 인덱스의 중복 검사가 락을 잡는다는 사실이다. 다른 트랜잭션이 아직 커밋하지 않은 같은 키의 행이 있으면, 그 행의 운명(커밋/롤백)이 정해질 때까지 중복 여부를 확정할 수 없다. 그래서 InnoDB는 그 레코드에 공유(S) 락을 요청하고 기다린다. 이 S 락이 갭을 포함한 넥스트 키 성격이라는 점, 그리고 S 락은 여러 트랜잭션이 동시에 얻을 수 있다는 점이 데드락을 만든다.

운영에서 이 패턴이 나오는 얼굴 ① 재시도 폭풍

첫 시도가 다른 이유로 롤백되는 사이, 같은 키로 재시도 요청이 여럿 몰려 S 락 대기 줄을 만든 경우.

얼굴 ② "지우고 다시 넣기" 배치

DELETE … WHERE key = ? 후 같은 키를 INSERT하는 재적재 배치가 동시에 둘 돌 때. 첫 배치의 DELETE가 X 락을 쥔 동안 두 번째 배치의 INSERT들이 S 락 대기 줄에 서고, 첫 배치가 COMMIT하는 순간 t4 상황이 된다.

3장의 데드락(락 순서 역전)과 무엇이 다른가 — 모델을 하나 더 갖는다

"데드락 = 반대 순서로 락을 잡는 것"이라는 모델 하나만 있으면 갭 락 데드락은 영원히 안 보인다. 두 트랜잭션이 같은 자원(같은 갭)을 같은 순서로 잠갔는데도 나기 때문이다. 순서를 맞춰도 못 막는다.

  2. 두 트랜잭션의 정체 — MySQL thread id, 접속 IP·계정, ACTIVE n sec(얼마나 오래된 트랜잭션인지), undo log entries(수정한 행 수). 계정·IP로 어느 서비스/배치인지 특정한다.
  3. 마지막 문장 — 각 트랜잭션이 대기 중이던 문장이다. 초보가 가장 헷갈리는 지점: 로그에는 그 트랜잭션이 앞에서 실행한 문장들이 나오지 않는다. INSERT만 보이지만 INSERT가 갭 락을 잡은 게 아니다. "앞에 뭔가 있었다"는 사실은 다음 단계의 HOLDS에서 읽는다.
  4. HOLDS THE LOCK(S) 해독 — 인덱스 이름(uk_user_coupon)과 락 모드. locks gap before rec가 있으면 이 트랜잭션은 INSERT 이전에 갭 락을 잡는 문장(FOR UPDATE / UPDATE / DELETE)을 실행했다는 뜻이다. 이제 코드에서 그 트랜잭션 경계 안의 잠금 읽기를 찾으러 간다.
  5. WAITING 해독 + 교차 대조 — (1)이 기다리는 락과 (2)가 쥔 락이 같은 인덱스·같은 페이지·같은 갭인지, 반대 방향도 성립하는지 확인한다. 성립하면 순환 확정.
  6. 희생자와 예외 매핑 — WE ROLL BACK TRANSACTION (2)가 1213을 받은 쪽이다. 애플리케이션 에러 로그의 시각·스레드와 맞춰 본다.

6처방 — "없는 행을 잠그지 마라" + 얻는 것 / 내주는 것

패턴 A의 근본 원인은 존재하지 않는 행을 잠그려 한 것이다. 없는 행을 잠그면 InnoDB는 갭을 잠글 수밖에 없고, 갭 락은 호환이라 상호 배제가 안 된다. 처방은 세 갈래 — 앵커 · 유니크 · UPSERT — 고 각각 대가가 있다.

❌ Before — 없는 행을 잠근다
@Transactional
public void issue(long userId, long couponId) {
    var existing = repo.findForUpdate(userId, couponId);
    // 행 없음 → (10,20) 갭 락 → 둘 다 성공
    if (existing.isPresent()) throw new AlreadyIssued();
    repo.save(new CouponIssue(userId, couponId));
    // 인서트 인텐션 → 서로의 갭 락에 막힘
}
✅ After ① — 존재하는 앵커 행에 레코드 락
@Transactional
public void issue(long userId, long couponId) {
    userRepo.lockById(userId);앵커
    // SELECT id FROM users WHERE id = ? FOR UPDATE
    // 유니크+등호+존재 → 레코드 락만 → 갭 없음
    if (repo.existsByUserIdAndCouponId(userId, couponId))
        throw new AlreadyIssued();
    repo.save(new CouponIssue(userId, couponId));
    // 두 번째 Tx는 t2에서 "대기" → 직렬화, 데드락 아님
}
처방 ① 앵커 행 락사용자별 발급을 직렬화하고 싶다면 없는 coupon_issue 행이 아니라 항상 존재하는 users 행을 잠근다. 두 번째 트랜잭션은 잠그는 단계에서 대기 → 직렬화.
처방 ② 유니크 제약 + INSERT 시도사전 확인 없이 INSERT하고 DataIntegrityViolationException을 "이미 발급됨"으로 번역. 갭 락을 잡는 문장 자체가 없다. rollback-only·REQUIRES_NEW 처리는 3장 복합 유니크 제약 문서 §3.
처방 ③ 단일 UPSERT 문장INSERT … ON DUPLICATE KEY UPDATE는 중복이 나면 S가 아니라 X 락을 잡아 패턴 B의 "S 둘 → X 승격 경쟁" 구조 자체가 안 생긴다. 대신 갱신에도 AUTO_INCREMENT를 소모하는 등 별도 주의점.
패턴 B의 처방"지우고 다시 넣기" 배치는 DELETE + INSERT를 UPDATE로 바꾸거나, 재적재 배치가 같은 키 범위에 동시에 둘 돌지 않도록 키 범위로 분할한다.
상시 규칙 1잠금 읽기의 WHERE는 반드시 인덱스를 타게 — 못 타면 전 테이블 넥스트 키 락. EXPLAIN으로 확인
상시 규칙 2트랜잭션을 짧게 — 갭 락은 트랜잭션 끝까지 유지. 외부 호출·파일 처리를 안에 두면 갭 락 점유 시간이 그만큼 늘어난다
상시 규칙 3여러 행을 잠글 때 PK 순서 고정은 여전히 필요 — 갭 락 데드락과 별개로 순서 역전 데드락이 겹칠 수 있다

이 로직에서만 갭 락을 끈다 — DB 전역 설정을 바꾸지 않는다

public void issue(long userId, long couponId) { ... }

패턴 A는 사라진다. 그러나 (a) 패턴 B는 그대로 남고, (b) 그 트랜잭션 안에서 "범위를 잠갔으니 phantom이 없다"고 가정한 로직이 있었다면 깨지며, (c) 격리 수준 지정은 트랜잭션을 새로 여는 쪽에서만 유효하다(기존 트랜잭션에 합류하면 무시).

트레이드오프 양면 조립 — 처방을 하나 고르면 오른쪽 열까지 한 호흡에

처방얻는 것내주는 것
① 앵커 행 락갭 락 소멸, 사용자 단위 직렬화로 의도가 명확부모 행이 핫스팟(그 사용자의 모든 발급이 직렬화), 앵커가 반드시 존재해야 함
② 유니크 제약 + INSERT 시도락 문장 자체가 없음, 모든 진입 경로를 DB가 방어예외 기반 흐름, rollback-only 처리 필요, 친절한 메시지는 별도 UX 처리
③ 단일 UPSERT 문장라운드트립 1회, S 락 승격 경쟁 없음AUTO_INCREMENT 소모, 영속성 컨텍스트 우회, 벤더 종속 구문
④ RC로 낮추기검색·스캔 갭 락 전부 소멸, 쓰기 동시성 상승phantom 허용, 중복 검사 갭 락은 남음, ROW 바이너리 로그 필요, 합류 트랜잭션엔 미적용
⑤ 재시도일시적 데드락을 사용자 실패로 노출하지 않음처리량 저하, 멱등성 요구, 구조적 원인을 숨김
갭 락 자체의 양면얻는 것: RR에서 잠금 읽기가 phantom 없이 "범위 전체를 소유"한다는 보장(범위 재고 예약, 순번 채번에 필요). 내주는 것: §3의 사슬 — 무관한 INSERT 대기, 데드락 가능성, 트랜잭션 장기화. 판단 기준은 "갭 락은 나쁘다"가 아니라 "이 보장이 필요 없는 곳에서 비용만 내고 있지 않은가".

재시도 정책 — 트랜잭션 밖에서, 상한과 지터를 두고

데드락 희생자는 InnoDB가 트랜잭션 전체를 롤백했으므로 "처음부터 다시"가 안전하다 — 단, 다시 시작하는 위치가 트랜잭션 경계 밖이어야 한다.

❌ 트랜잭션 안에서 재시도 — 이미 롤백된 트랜잭션 위에서 돌고 있다
@Transactional
public void issue(long userId, long couponId) {
    for (int i = 0; i < 3; i++) {
        try { doIssue(userId, couponId); return; }
        catch (PessimisticLockingFailureException e) { /* 재시도 */ }커밋 시점에 UnexpectedRollbackException
    }
}
✅ 재시도는 바깥 빈에서, 트랜잭션은 안쪽 빈에서 — 경계를 구조로 분리 (@EnableRetry 필요)
@Service
public class CouponIssueFacade {
    private final CouponIssueService service;   // 이 안의 issue()가 @Transactional
 
    @Retryable(
        retryFor = PessimisticLockingFailureException.class,  // 데드락(1213) + 락 대기 타임아웃(1205)
        maxAttempts = 3,상한 // 무한 재시도는 장애를 증폭한다
        backoff = @Backoff(delay = 50, multiplier = 2, random = true))지터 // 같은 박자로 재충돌하지 않게
    public void issue(long userId, long couponId) {
        service.issue(userId, couponId);   // 매 시도마다 새 트랜잭션이 열린다
    }
 
    @Recover
    public void giveUp(PessimisticLockingFailureException e, long userId, long couponId) {
        throw new TemporarilyUnavailable("잠시 후 다시 시도해 주세요", e);   // 사용자에겐 재시도 가능 오류로
    }
}
재시도 규칙 1 · 상한데드락이 구조적이면(§4 코드 그대로면) 재시도는 매번 같은 자리에서 다시 죽는다. 상한 없는 재시도는 커넥션과 CPU만 태운다
재시도 규칙 2 · 지터두 요청이 같은 간격으로 재시도하면 같은 박자로 다시 충돌한다 — random backoff
재시도 규칙 3 · 멱등성롤백되지 않는 부수효과(외부 API·메일·트랜잭션 밖 이벤트)가 있었다면 재시도가 그것을 두 번 실행한다. 붙이기 전에 먼저 확인
재시도는 진통제lock_deadlocks 카운터가 우상향이면 재시도가 덮고 있는 구조적 원인이 있다는 뜻 → 처방 ①~③으로 돌아간다.

7재현 테스트 — CountDownLatch로 타임라인을 강제한다

데드락은 "동시에 돌리면 가끔" 나는 게 아니라 t1 → t2 → t3 → t4 순서가 만들어지면 반드시 난다. 그러니 테스트는 스레드를 동시에 출발시키는 게 아니라 그 순서를 래치로 강제해야 한다.

규칙 1 · 진짜 MySQLTestcontainers여야 한다 — H2에는 갭 락이 없어 이 테스트가 통과해 버린다(거짓 초록)
규칙 2 · 테스트에 @Transactional 금지테스트 스레드의 트랜잭션은 워커 스레드에 전파되지 않고, 시드 데이터가 롤백에 묶여 다른 커넥션에서 안 보인다. 각 스레드가 TransactionTemplate으로 자기 트랜잭션을 연다
규칙 3 · 래치로 순서 강제aLockedGap → B가 잠금 → bLockedGap → A가 INSERT → B가 INSERT. 타임라인의 t1~t4를 코드로 못 박는다
GapLockDeadlockTest — 타임라인 t1~t4를 래치로 고정

            jdbc.queryForList("SELECT id FROM coupon_issue WHERE user_id = 17 AND coupon_id = 7 FOR UPDATE");t2 갭 락 — 안 막힌다
            bLockedGap.countDown();                     // t2: 갭 락끼리 호환 → 여기서 막히지 않는다
            jdbc.update("INSERT INTO coupon_issue (user_id, coupon_id) VALUES (17, 7)");t4 순환 완성
        }));
 
        var failures = new ArrayList<Throwable>();
        for (var f : List.of(a, b)) {
            try { f.get(10, TimeUnit.SECONDS); } catch (ExecutionException e) { failures.add(e.getCause()); }
        }
        pool.shutdownNow();
 
        // 정확히 한 트랜잭션만 데드락 희생자가 되고, 나머지 하나는 성공한다
        assertThat(failures).hasSize(1);
        assertThat(failures.get(0)).isInstanceOf(PessimisticLockingFailureException.class);공통 부모로 단언
        assertThat(jdbc.queryForObject(
                "SELECT COUNT(*) FROM coupon_issue WHERE user_id IN (15, 17)", Integer.class))
            .isEqualTo(1);
    }
 
    private static void await(CountDownLatch latch) {
        try {
            if (!latch.await(5, TimeUnit.SECONDS)) throw new IllegalStateException("latch timeout");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException(e);
        }
    }
}
쓰임 ① 먼저 빨간 불을 본다

"우리 코드가 정말 갭 락 데드락을 내는가"를 추측이 아니라 사실로 만든다.

쓰임 ② 회귀 방지 장치로 남긴다

처방 적용 후엔 같은 시나리오에서 데드락 예외 0건, 두 행 모두 삽입을 단언하는 테스트로 바꾼다(앵커 행 락으로 바꾸면 B가 t2에서 대기하므로 래치 대신 "동시 출발" 패턴). 나중에 누군가 "확인 후 INSERT가 더 읽기 쉽다"며 FOR UPDATE로 되돌리면 이 테스트가 막는다.

예외 타입단언하기 전에 실제로 어떤 타입이 올라오는지 이 테스트로 먼저 확인한다. JdbcTemplate 경로에서는 MySQL 1213이 DeadlockLoserDataAccessException으로, JPA 경로에서는 Hibernate 예외 변환을 한 번 더 거쳐 CannotAcquireLockException으로 올라올 수 있다. 둘의 공통 부모 PessimisticLockingFailureException으로 잡는 것이 안전하다.

8꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 한 가지 모델만 가진 사람과 갈리는 지점.

갭 락끼리 충돌하지 않는다면서 왜 데드락이 나죠?

갭 락의 유일한 목적이 "이 구간에 INSERT 금지"라서, 두 트랜잭션이 같은 갭을 잠그는 건 같은 주장을 두 번 하는 것이라 충돌할 이유가 없다. 충돌은 INSERT가 잡는 인서트 인텐션 락이 남의 갭 락을 만날 때만 일어난다.

그래서 순서가 "둘 다 잠그기 성공(호환) → 둘 다 넣기 시도 → 각자 상대의 갭 락에 막힘(순환)"이 된다. 레코드 락이었다면 두 번째 트랜잭션이 잠그는 단계에서 이미 대기해 직렬화됐을 것이다 — 갭 락이 호환이라는 성질이 "잠갔다고 믿는 두 트랜잭션"을 만들고, 그 믿음이 INSERT에서 깨진다.

패턴 A에서 두 트랜잭션이 넣는 값이 15와 17로 다른데도 나나요? 그럼 15와 25였다면요?

난다. 충돌 단위는 행이 아니라 갭이다. 15와 17은 둘 다 (10,20) 갭에 속하므로 같은 갭 락을 잡고, 각자의 INSERT가 상대의 갭 락에 막힌다.

15와 25였다면 안 난다. 유니크 인덱스 + 등호 + 행 없음은 그 값이 들어갈 자리의 갭만 잠그므로 A는 (10,20), B는 (20,30)을 잠근다. 서로 다른 갭이라 각자의 인서트 인텐션은 자기 갭 락만 만난다 → 둘 다 성공. "같은 값"이 아니라 "같은 갭에 떨어지는 값"이 조건이라는 걸 말하면 갭이라는 단위를 진짜로 이해했다는 뜻이다.

시니어 변별 READ COMMITTED로 낮추면 해결되나요?

패턴에 따라 다르다. 검색·스캔의 갭 락은 RC에서 꺼지므로 패턴 A(없는 행 FOR UPDATE + INSERT)는 사라진다. 그러나 유니크 중복 검사와 외래 키 검사의 갭 락은 RC에서도 남으므로 패턴 B(INSERT만의 S 락 데드락)는 그대로 난다.

그리고 대가가 있다 — phantom을 허용하므로 "범위를 잠갔다"는 가정 위의 로직이 깨지고, 바이너리 로그는 ROW 포맷이어야 하며, 트랜잭션 단위 지정은 새 트랜잭션을 여는 쪽에서만 유효하다. 그래서 순서는 "먼저 로그로 패턴 분류 → 패턴 A이고 그 트랜잭션에 phantom 방지 의존이 없다면 트랜잭션 단위 RC는 유효한 카드 → 그래도 1순위는 없는 행을 잠그지 않는 설계"다.

데드락 로그에 INSERT 한 줄만 찍혀 있으면 원인을 어떻게 찾나요?

로그의 SQL은 대기 중이던 마지막 문장일 뿐, 그 트랜잭션이 앞에서 실행한 문장은 나오지 않는다. 대신 HOLDS THE LOCK(S)의 락 모드가 앞 문장의 흔적이다: locks gap before rec가 있으면 INSERT 이전에 갭 락을 잡는 잠금 읽기(FOR UPDATE / UPDATE / DELETE)가 있었다는 뜻이고, lock mode S면 유니크 중복 검사 경로다.

여기서 인덱스 이름을 얻어, 코드의 해당 트랜잭션 경계 안에서 그 인덱스를 조건으로 쓰는 잠금 문장을 찾는다. 확신이 안 서면 §7처럼 재현하면서 performance_schema.data_locks로 t2 상태를 직접 본다. 마지막 1건만 남으므로 innodb_print_all_deadlocks를 켜 두는 것이 운영 습관이다.

SELECT … FOR UPDATE의 WHERE가 인덱스를 못 타면 어떻게 되나요?

InnoDB는 클러스터드 인덱스를 처음부터 끝까지 스캔하며 지나가는 모든 레코드와 모든 갭에 넥스트 키 락을 잡는다. 사실상 테이블 락이다. RR에서는 조건에 안 맞는 행의 락도 트랜잭션 끝까지 풀리지 않는다(RC는 안 맞는 행의 락을 즉시 해제하지만 스캔 자체는 한다).

결과는 §3 사슬의 최악 버전 — 그 테이블로의 모든 INSERT·UPDATE가 이 트랜잭션이 끝날 때까지 대기 → 커넥션 풀 고갈. 잠금 읽기는 배포 전 EXPLAIN으로 인덱스 사용을 확인하는 것이 규칙이어야 한다.

시니어 변별 락 순서를 통일하면 되지 않나요?

3장에서 다룬 순서 역전 데드락(A: 재고 → 포인트, B: 포인트 → 재고)에는 맞는 처방이다. 그러나 갭 락 데드락은 두 트랜잭션이 같은 자원(같은 갭)을 같은 순서로 잠갔는데도 난다 — 갭 락이 호환이라 첫 단계에서 상호 배제가 성립하지 않기 때문이다.

순서로는 못 막고, 잠금 대상을 갭이 아닌 존재하는 레코드로 바꾸거나(앵커 행), 잠금 문장 자체를 없애야(유니크 제약 + INSERT / 단일 UPSERT) 한다. 이 차이를 말할 수 있으면 "데드락 = 락 순서 문제"라는 한 가지 모델만 가진 사람과 구분된다.

일반 SELECT도 갭 락을 잡나요?

아니다. 일반 SELECT는 MVCC 스냅샷을 읽으므로 어떤 락도 잡지 않는다. 갭 락이 생기는 건 잠금 읽기 — SELECT … FOR UPDATE / FOR SHARE, 그리고 UPDATE·DELETE가 대상 행을 찾는 과정 — 와, 별도 경로인 INSERT의 유니크 중복 검사·외래 키 검사뿐이다.

따라서 "SELECT 후 INSERT" 코드에서 SELECT가 일반 읽기라면 패턴 A는 생기지 않는다 — 대신 두 트랜잭션이 모두 "없음"을 보고 둘 다 INSERT해 중복 삽입(유니크 제약이 있으면 한쪽이 Duplicate entry)이 된다. 잠그느냐 안 잠그느냐의 선택이 "데드락 vs 중복" 중 어느 문제를 안을지를 결정한다.

복합 유니크 인덱스 uk(user_id, coupon_id)에 WHERE user_id = 10 FOR UPDATE는 레코드 락만 잡나요?

아니다. 유니크 인덱스의 일부 컬럼만 조건으로 쓰면 유니크 조회로 취급되지 않는다 — user_id = 10인 행이 여럿일 수 있기 때문이다. 그래서 일치하는 레코드마다 넥스트 키 락을 잡고, 마지막 일치 레코드 다음 갭까지 잠근다(같은 user_id를 하나 더 넣는 INSERT를 막아야 하므로).

"유니크·등호·존재" 세 조건이 모두 성립해야 레코드 락만 남는다. 앵커 행 락 처방이 users.id(단일 컬럼 PK)를 잠그는 이유도 이것이다.

supremum이 뭔가요? WHERE user_id > 30 FOR UPDATE는 무엇을 잠그나요?

인덱스 페이지의 끝을 나타내는 의사(pseudo) 레코드다. 마지막 실제 레코드 뒤에도 "갭"이 있어야 "30보다 큰 값을 넣지 마"를 표현할 수 있는데, 그 갭의 오른쪽 끝 역할을 supremum이 한다. 그래서 (30, +∞) 갭은 로그에 "supremum 앞의 갭"으로 나온다.

user_id > 30 FOR UPDATE는 일치하는 레코드가 없어도 (30, +∞) 갭 락을 잡는다 → 30보다 큰 어떤 값의 INSERT도 막힌다. user_id > 10이면 (10,20], (20,30], (30,+∞)를 전부 잠근다 — 있는 것도 없는 것도. 이것이 RR이 phantom을 막는 방식이다.

가산점 INSERT … ON DUPLICATE KEY UPDATE는 왜 패턴 B를 피하나요?

패턴 B의 구조는 "중복 검사에서 S 락을 둘이 동시에 얻음 → 각자 삽입하려고 X로 올리려다 서로의 S에 막힘"이다. ON DUPLICATE KEY UPDATE는 중복이 나면 그 행을 갱신해야 하므로 처음부터 S가 아니라 배타(X) 락을 잡는다. X는 둘이 동시에 못 얻으니 두 번째는 첫 번째를 기다렸다가 이어서 진행 — 승격 경쟁 자체가 생기지 않는다.

대신 내주는 것이 있다: 갱신으로 끝나도 AUTO_INCREMENT를 소모하고, JPA 영속성 컨텍스트를 우회하며, 벤더 종속 구문이다. 이 양면까지 말해야 처방 ③을 "골랐다"고 할 수 있다.

데드락(1213)과 락 대기 타임아웃(1205)은 뭐가 다른가요?

데드락은 대기 그래프에 사이클이 생긴 것이고, InnoDB가 즉시 감지해 한쪽 트랜잭션을 통째로 롤백한다(ERROR 1213). 락 대기 타임아웃은 사이클 없이 그냥 오래 기다린 것이다 — 상대가 락을 쥔 채 긴 트랜잭션을 돌리고 있을 때 innodb_lock_wait_timeout(기본 50초)을 넘기면 ERROR 1205가 난다.

둘의 차이가 처방을 가른다. 1213은 순환 구조가 있으니 이 문서의 처방(없는 행 잠그지 않기)으로 가고, 1205는 순환이 아니라 긴 트랜잭션 문제이니 락 점유 시간을 줄이는 쪽(트랜잭션 단축, 외부 호출 분리)으로 간다. 재시도 대상으로는 둘 다 PessimisticLockingFailureException으로 묶인다.

재현 테스트를 왜 H2로 하면 안 되나요? 테스트에 @Transactional을 붙이면 왜 안 되나요?

H2에는 갭 락이 없다. 그러니 §7 테스트가 H2에서는 두 INSERT 모두 성공해 통과해 버린다 — 데드락을 내는 코드에 초록 불이 켜지는 최악의 테스트다. 락 동작을 검증하는 테스트는 반드시 실제 MySQL(Testcontainers)이어야 한다.

@Transactional을 테스트 메서드에 붙이면 두 가지가 깨진다. ① 테스트 스레드의 트랜잭션은 워커 스레드로 전파되지 않으므로 두 워커가 어차피 자기 트랜잭션을 열어야 하고, ② 시드 데이터가 테스트 트랜잭션 안에 갇혀 다른 커넥션에서 보이지 않아 (10,20) 갭 자체가 만들어지지 않는다. 그래서 각 스레드가 TransactionTemplate으로 자기 트랜잭션을 열고, 뒷정리는 @BeforeEach에서 직접 한다.

재시도를 트랜잭션 안에서 catch해서 하면 왜 안 되나요?

데드락 희생자가 되는 순간 InnoDB는 그 트랜잭션 전체를 이미 롤백했고, 스프링 쪽에서도 트랜잭션이 rollback-only로 표시된다. 같은 트랜잭션 안에서 catch하고 다시 시도하면 이미 죽은 트랜잭션 위에서 작업하는 셈이라, 재시도가 성공한 것처럼 보여도 커밋 시점에 UnexpectedRollbackException을 만난다.

그래서 재시도 위치는 트랜잭션 경계 밖이어야 한다 — 바깥 빈(@Retryable)이 재시도하고 안쪽 빈(@Transactional)이 매 시도마다 새 트랜잭션을 연다. 같은 클래스 안의 자기 호출로는 프록시를 타지 않으니 빈을 분리하는 것이 구조적으로 맞다.

InnoDB의 락은 인덱스 레코드와 그 사이의 갭에 걸리고, 갭 락은 INSERT 차단이 유일한 목적이라 갭 락끼리는 호환되지만 INSERT의 인서트 인텐션 락은 남의 갭 락에 막힌다 — 그래서 RR에서 없는 행(또는 범위)을 FOR UPDATE/UPDATE로 잠근 두 트랜잭션이 각자 그 갭에 INSERT하면 "둘 다 잠그기 성공, 둘 다 넣기 실패"의 순환이 생기고(유니크 중복 검사의 공유 락 경로는 RC에서도 남는다), 진단은 LATEST DETECTED DEADLOCK의 HOLDS/WAITING 락 모드 서명(gap before rec + insert intention)을 교차 대조하는 것이며, 처방은 격리 수준 조정이나 락 순서가 아니라 "없는 행을 잠그지 않는 설계(앵커 행 락 · 유니크 제약+INSERT · 단일 UPSERT)"에 트랜잭션 밖의 상한·지터 있는 재시도와 Testcontainers 위의 래치 재현 테스트를 안전망으로 얹는 것이다.
