질문: ""결제는 성공했는데 주문 데이터가 없다"는 정합성 문제가 발생했습니다. 원인 후보와 재발 방지 설계를 설명해주세요."

핵심 관전 포인트 — 면접 첫 답변으로 그대로 말한다

이 증상의 뿌리는 하나다 — 돈의 원장(PG)과 주문의 원장(우리 DB)은 서로 다른 시스템이고, PG 승인은 우리 트랜잭션의 롤백으로 되돌아오지 않는다.
  1. 원인 후보는 "PG에 진실이 생긴 뒤 우리 DB에 진실이 안 남는 경로" 여섯 — (a) @Transactional 안에서 승인 후 예외로 롤백 (b) 승인 웹훅이 주문보다 먼저 와 매칭 실패 후 폐기 (c) 승인 직후 타임아웃·크래시로 INSERT 미실행 (d) 멱등 레코드가 "결과" 대신 "봤다"만 저장해 재시도 무시 (e) 배포·failover 순간 커밋 전 단절 (f) @Async·이벤트 후처리에서 주문 유실.
  2. 좁히는 첫 질문 둘 — "고객이 성공 화면을 봤는가" / "우리 DB에 흔적이 하나라도 있는가".
  3. 재발 방지는 다섯 겹 — ① 순서 설계(PENDING 선생성 → 트랜잭션 밖 승인 → 조건부 확정) ② 멱등(요청·PG·DB 유니크 세 층) ③ Outbox/Inbox(웹훅은 "받았다"만 먼저 확정) ④ 양방향 대사 배치 ⑤ 알람. ①~③은 사고 확률을 줄이고 ④⑤는 그래도 난 사고를 대사 주기 안에 반드시 잡히는 유계 불일치로 바꾼다.
각 겹은 값을 치른다 — 미완료 주문 정리 배치 / 키 저장소·스코프 계약 / 테이블·릴레이 운영 / PG 조회 비용과 의존 / 오탐. 값을 말하지 않은 방어선은 설계가 아니라 희망이다. 그리고 이 전부를 사람의 주의가 아니라 ArchUnit(트랜잭션 안 PG 호출 금지) · 부분 실패 테스트 · 대사 배치 코드 · "0이 정상"인 카운터로 고정한다.

1무대 고정 — 두 개의 원장, 그리고 롤백이 못 건드리는 것

증상을 정확히 진술한다. "결제는 성공했는데 주문이 없다"는 PG의 원장에는 승인 레코드가 있는데 우리 DB의 orders에는 대응하는 확정 주문이 없다는 뜻이다. 돈은 빠져나갔고 물건은 안 나간다. 고객은 카드사 승인 문자와 함께 "주문 내역 없음"을 본다. CS가 가장 먼저 알고 개발팀은 그 다음에 안다 — 이것 자체가 방어선 ⑤(알람)가 필요한 이유다.

이 사고를 낳는 전형적 코드를 하나로 고정한다. 문서 끝까지 이 무대를 쓴다.

@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional                                                 // 경계 안의 참여자는 우리 DB 커넥션 하나뿐
    public OrderResponse placeOrder(PlaceOrderRequest req) {
        stockService.decrease(req.items());                        // ① 재고 차감 (UPDATE → 행 락)
        PgApproval approval = pgClient.approve(req.paymentKey(), req.amount());  // ② PG 승인 (외부 HTTP)되돌릴 수 없는 사건
        Order order = orderRepository.save(Order.create(req, approval));         // ③ 주문 INSERT (아직 커밋 전)
        couponService.use(req.couponId());                         // ④ 쿠폰 사용 — 여기서 예외가 나면?
        return OrderResponse.of(order);
    }
}

겉보기엔 "전부 한 트랜잭션이니 안전"하다. 여기서 두 가지를 못 박아야 이후의 모든 원인 후보가 보인다.

식당의 카드 단말기와 주방 주문표로 외우기

홀 직원이 손님 카드를 단말기에 긁는다(PG 승인 — 카드사 원장에 기록). 그다음 주방에 넣을 주문표를 쓰다가 실수를 깨닫고 주문표 뭉치를 통째로 찢어 버린다(ROLLBACK). 카드사에는 결제가 남고 주방에는 주문이 없다 — 손님은 결제 문자만 받고 음식은 못 받는다. 찢은 주문표는 되돌아오지만 단말기 승인은 찢는다고 없어지지 않는다. 고치는 법도 식당과 같다: 주문표를 먼저 써 두고("PENDING") → 카드를 긁고 → 주문표에 "결제완료" 도장을 찍는다(조건부 확정). 그리고 마감 때 단말기 전표 뭉치와 주문표 뭉치를 맞춰 본다(대사).

증상 3갈래 — "주문 데이터가 없다"를 들으면 첫 SQL로 어느 갈래인지부터 확인한다

iorders에 행이 아예 없다 — INSERT 미실행 또는 롤백 iiPENDING(중간 상태)으로 남아 있다 — 승인까진 갔는데 확정 안 됨 iiiFAILED로 잘못 마킹돼 있다 — 불명을 실패로 오판

(ii)(iii)는 이미 방어선 ①(PENDING 선생성) 구조일 때 나오는 갈래다. (i)는 §1 원본 구조 — 흔적이 0이라 영향 범위조차 우리 DB로 못 센다.

2사고 대응 사이클 여섯 단계 — 답변의 골격

출제 의도는 "Outbox를 아는가"가 아니라 사고 대응의 전체 사이클을 수행할 수 있는가다. 면접에서는 이 여섯 칸을 먼저 말하고 각 칸을 채우는 것이 가장 안전한 답변 구조다. 원인을 모르는 상태에서도 ②③은 진행할 수 있다 — 원인 규명이 끝날 때까지 고객 피해를 방치하는 것이 가장 나쁜 대응이다.

  1. 탐지 — 어떻게 알았나(CS 문의인가, 대사 배치 알람인가). CS로 알았다면 그 자체가 관측 공백이다.
  2. 영향 범위 산정 — 언제부터, 몇 건, 얼마. SQL로 숫자를 만든다. 우리 DB에 흔적이 없으면 PG 거래내역이 기준이 된다.
  3. 임시 조치 — 출혈 차단(원인이 진행 중이면 결제 진입 차단·기능 플래그)과 고객 복구(주문 수동 생성 vs 취소·환불)를 분리해 결정한다. 증거(로그, PG 콘솔 이력)를 먼저 보존한다.
  4. 근본 원인 — 원인 후보 여섯을 세우고 단서로 좁힌다.
  5. 재발 방지 — 방어선 다섯 겹 중 뚫린 겹과 없던 겹을 식별해 설계한다. 각 겹의 대가를 명시한다.
  6. 회고 — 타임라인, 탐지까지 걸린 시간, 왜 방어선이 없었나, 액션 아이템에 담당·기한, 재발 시 잡아낼 지표.

3원인 후보 여섯 가지 — 각각을 t1→t6 타임라인으로

§1의 코드와 그 주변(웹훅 핸들러, 멱등 필터, 비동기 리스너, 인프라)에서 "PG에 진실이 생긴 뒤 우리 DB에 진실이 안 남는" 경로를 전부 적는다. 각 후보는 사건의 순서로 말한다. 이 순서를 말할 수 있어야 "그 원인이 왜 이 증상을 만드는지"를 설명한 것이다.

원인 후보 6종 — 순서대로 인출한다 (연상: 경·웹·부·멱·페·비)

  1. (a) 경계 오류 — @Transactional 안에서 승인, 그 뒤 예외로 롤백. 롤백은 우리 쪽만 되돌린다.
  2. (b) 웹훅 유실·순서 역전 — 승인 웹훅이 주문보다 먼저 와서 매칭 실패 → 200 → 폐기.
  3. (c) 부분 실패 — 승인은 됐는데 응답 수신 후(또는 직전) 타임아웃·크래시. 불명을 실패로 취급.
  4. (d) 멱등키 충돌 — 멱등 레코드가 "결과" 대신 "봤다"만 저장해 재시도가 409로 무시됨.
  5. (e) 페일오버·배포 단절 — 커밋 직전에 커넥션이 끊겼다 (커밋 전/응답 전/비동기 복제 유실).
  6. (f) 비동기 후처리 유실 — @Async·이벤트 리스너에서 주문을 만들다 조용히 죽었다. 유일하게 고객이 성공 화면을 본다.

성격이 전부 다르다 — 코드 경계 / 외부 통지 / 불명 / 멱등 설계 / 인프라 / 비동기. 그래서 방어선도 한 방이 아니라 계층이어야 한다(6절).

우리 앱·DBPG되돌릴 수 없는 사건(PG 커밋)우리 쪽 실패 지점

a트랜잭션 경계 오류 — 승인이 트랜잭션 안에 있고, 승인 뒤 예외로 롤백

단서: "승인 성공" 로그 직후 수백 ms 뒤 예외 스택. orders에 행은 없지만 AUTO_INCREMENT 값은 롤백돼도 되돌아오지 않으므로 ID에 구멍이 남는다 — 사고 시각 부근의 ID 갭이 "INSERT까지는 갔다가 롤백됐다"는 DB 쪽 증거. 변형: t5가 checked 예외였다면 기본 규칙상 커밋되어 주문이 남고, "주문은 있는데 쿠폰 처리는 안 된" 반대 증상이 된다 — 롤백 규칙을 모르면 사고 유형을 못 맞춘다.

b웹훅 유실·순서 역전 — 승인 웹훅이 주문보다 먼저 와서 매칭 실패 후 폐기

PG 연동은 보통 두 채널이 병행한다 — 우리가 부르는 승인 API(동기)와 PG가 우리를 부르는 웹훅(비동기). 웹훅은 "승인이 일어났다"는 통지이고, PG는 웹훅을 매우 빠르게, 순서 보장 없이 보낸다.

단서: 웹훅 수신 로그에 "order not found" + 200 응답. PG 관리자 콘솔의 웹훅 전송 이력이 "성공". 고객은 결제창 뒤 화면을 못 봤거나 에러를 봤다.

c부분 실패 — 승인은 됐는데 응답 수신 후(또는 직전) 앱이 죽거나 타임아웃

단서: SocketTimeoutException/ResourceAccessException 로그와 PG 콘솔의 승인 시각이 거의 일치. 또는 로그 절단 + 컨테이너 재시작 이벤트(OOMKilled, 배포 롤아웃 시각).

d멱등키 충돌 — 멱등 레코드가 "결과" 대신 "봤다"만 저장해 재시도가 무시됨

멱등키는 중복 결제를 막는 필수 장치인데, 잘못 설계하면 이 사고의 원인이 된다. 전형적 구현은 요청 진입 시 멱등 테이블에 키를 남기고 같은 키가 또 오면 튕겨내는 필터다.

단서: 멱등 저장소에서 해당 키의 상태가 IN_PROGRESS/FAILED. 서버 로그에 409 또는 "duplicate key" 반복. 클라이언트 로그에 재시도 흔적.

e배포·failover 순간 커넥션 단절 — 커밋 직전에 DB가 바뀌었다

단서: 사고 건들의 시각이 배포 이벤트·failover 이벤트와 정확히 겹침. CommunicationsException, Connection is closed, The last packet successfully received 류 로그가 같은 시각에 묶여 있음.

f비동기 후처리에서 주문 생성 — @Async·이벤트 리스너가 조용히 죽었다

"승인은 빨리 응답하고 주문 생성은 뒤에서" 하려고 주문 생성을 이벤트로 뺀 구조다. 결합도는 낮아졌지만 주문이라는 진실을 메모리 위 이벤트에 맡긴 것이다.

단서: 응답 로그는 200인데 주문 없음. AsyncUncaughtExceptionHandler 로그, 실행기 거부 카운트, 재시작 시각과의 상관.

4좁히기 — 두 질문으로 절반을 자른다

여섯 후보를 한 번에 조사하지 않는다. 면접에서 "여섯 가지 다 조사하겠습니다"는 답이 아니다. 어떤 단서로 어떤 후보를 먼저 자르는지가 사고 대응 경험의 증거다.

5영향 범위 산정과 임시 조치 — 원인을 몰라도 지금 할 수 있는 것

5-1. 영향 범위 — 숫자를 만드는 SQL

"몇 건, 얼마, 언제부터"가 없으면 임시 조치의 크기도, 회고의 심각도도 정할 수 없다. 여기서 방어선 ① 구조의 유무가 갈린다. 우리 쪽에 결제 기록(payment)이 남는 구조라면 우리 DB만으로 양방향 불일치를 셀 수 있다.

-- 방향 1: 결제는 승인인데 주문이 없거나 확정이 아닌 건 (돈은 받았는데 물건이 안 나감)
SELECT p.payment_key, p.order_no, p.amount, p.approved_at, o.status AS order_status
FROM payment p
LEFT JOIN orders o ON o.order_no = p.order_no
WHERE p.status = 'APPROVED'
  AND p.approved_at BETWEEN :from AND :to     -- 하한 = 배포 시각 / PG 장애 공지 / 첫 CS 접수 중 가장 이른 것
  AND (o.id IS NULL OR o.status <> 'CONFIRMED');

-- 방향 2: 주문은 확정인데 승인 결제가 없는 건 (돈은 안 받았는데 물건이 나감)
SELECT o.order_no, o.total_amount, o.confirmed_at
FROM orders o
LEFT JOIN payment p ON p.order_no = o.order_no AND p.status = 'APPROVED'
WHERE o.status = 'CONFIRMED'
  AND o.confirmed_at BETWEEN :from AND :to
  AND p.id IS NULL;

-- 방향 3 (가산점): 둘 다 있는데 금액이 다른 건 — 부분 취소·쿠폰 재계산 버그가 여기서 드러난다
SELECT o.order_no, o.total_amount, p.amount

WHERE o.status = 'CONFIRMED' AND p.status = 'APPROVED'

§1의 원본 구조처럼 우리 쪽에 아무 흔적도 남지 않으면 — 우리 DB로는 영향 범위를 셀 수 없다

이때 기준은 PG 원장이다. PG 거래내역 API나 정산 파일을 받아 임시 테이블(pg_tx_snapshot)에 적재하고 우리 주문과 anti-join으로 대조한다. "우리 DB에 기록이 없어서 PG 파일을 받아 대조해야 했다"는 경험 자체가 방어선 ①(PENDING 선생성)의 가장 강한 근거다 — 시도의 흔적이 우리 쪽에 남아야 영향 범위를 우리 손으로 잴 수 있다.

주의: 이 쿼리들은 사고 중 운영 DB에 날린다. payment(status, approved_at), orders(status, confirmed_at), orders(order_no) 인덱스가 없으면 풀스캔이고, 사고 중의 긴 조회는 2차 사고다. 대사 배치가 상시 도는 구조라면 이 인덱스는 이미 있어야 한다.

5-2. 임시 조치 — 출혈 차단과 고객 복구를 분리한다

출혈 차단원인이 진행 중인가부터. 웹훅 장애·failover·PG 장애가 계속되면 결제 진입을 기능 플래그로 잠그거나 결제 수단 전환. 산발적 코드 결함 (a)(c)(d)면 차단보다 빠른 핫픽스 + 대사 빈도 상향. 차단은 매출 손실 — "지금 분당 몇 건 새는가"(5-1 쿼리를 1분 창으로)와 저울질.
고객 복구방향 1의 각 건마다 주문을 살릴 것인가, 결제를 취소할 것인가. 기준은 재고·배송 가능 여부와 고객 의사 — 재고가 있고 고객이 원하면 PG 승인 정보로 CONFIRMED 주문 복구, 아니면 PG 취소 API로 환불·안내. 방향 2(확정인데 결제 없음)는 배송 후면 추심 문제라 방향 2가 먼저 막아야 하는 출혈일 때가 많다.
증거 보존재시작·재배포 전에 앱 로그, SHOW ENGINE INNODB STATUS, PG 콘솔의 웹훅·승인 이력, 배포·failover 타임라인을 캡처. 재시작은 원인 (e)(f)의 증거를 지운다.

6재발 방지 — 방어선 다섯 겹과 각각의 대가

한 방으로 막는 설계는 없다. 여섯 원인은 성격이 다르므로 방어선도 계층이어야 한다. ①~③은 사고가 나는 확률을 줄이고, ④⑤는 그래도 난 사고가 방치되는 시간을 대사 주기로 제한한다. 방어선마다 "얻는 것"과 "치르는 값"을 같은 호흡에 적는다.

방어선 5겹 — 순서대로 인출한다 (연상: 순·멱·아·대·알)

①순서 설계 — PENDING 선생성 → 밖에서 승인 → 조건부 확정 ②멱등 3층 — 요청 / PG / DB 유니크 ③Outbox / Inbox — "받았다"만 먼저 확정 ④양방향 대사 배치 — PG 원장 ↔ 주문 원장 ⑤알람 — PENDING 나이 · 불일치 건수

파란 셋 = 예방(확률↓) · 초록 둘 = 탐지(유계). 치르는 값도 순서대로: 정리 배치 / 키 저장소 / 테이블·릴레이 운영 / PG 조회 비용·의존 / 오탐.

6-1. 방어선 ① — 순서 설계: PENDING 선생성 → 트랜잭션 밖 승인 → 조건부 확정

원칙은 두 줄이다. 되돌릴 수 없는 외부 사건(PG 승인) 전에 우리 쪽 원장에 "시도"를 먼저 남기고, 외부 사건은 트랜잭션 밖에서 일으키며, 그 결과를 조건부 UPDATE로 확정한다. 그러면 어느 지점에서 죽어도 우리 DB에는 "PENDING 주문"이라는 흔적이 남고, 그 흔적을 보고 나중에 PG에 진실을 물을 수 있다.

BEFORE
BEGIN→재고→PG 승인→INSERT 주문→쿠폰→COMMIT

승인 뒤 어디서 죽어도 흔적 0. 롤백은 승인을 못 되돌린다.

AFTER
[A] INSERT PENDING → COMMIT→[PG] 승인 (밖)→[B] UPDATE PENDING→CONFIRMED + payment + outbox → COMMIT

어디서 죽어도 PENDING이 남는다. 죽은 지점은 PENDING의 나이와 PG 조회로 판별한다.

6-2. 방어선 ② — 멱등 세 층: 요청 / PG / DB 유니크

(d)를 막으려면 멱등을 "필터 하나"가 아니라 세 층으로 두고, 각 층이 "봤다"가 아니라 "결과"를 기억하게 한다.

요청 층 (클라이언트 → 우리)멱등키를 order_no로 받고 orders.idempotency_key UNIQUE로 저장. 같은 키가 오면 거절하지 말고 그 키의 주문 상태를 보고 이어간다. 멱등 레코드를 [A]와 같은 트랜잭션에 넣는 것이 (d)의 근본 처방. IN_PROGRESS에는 만료 시간.
PG 층 (우리 → PG)승인 요청에 order_no를 멱등 기준으로 실어 보낸다. 같은 주문번호·같은 금액의 재요청에 PG는 이전 승인 결과를 돌려주거나 중복 승인을 거절 → (c)의 "불명" 뒤 재시도가 이중 결제가 되지 않는다.
DB 층 (최후 방어선)payment.payment_key UNIQUE, orders.order_no UNIQUE, 조건부 UPDATE. 위 두 층이 다 뚫려도 DB가 두 번째 INSERT를 거절. 애플리케이션 멱등은 버그가 날 수 있지만 유니크 제약은 안 난다 — 4장 관점에서 가장 중요한 층.

@Scheduled(fixedDelay = 1_000)
public void processInbox() {
    for (WebhookInbox in : inboxRepository.findDue(100)) {              // next_attempt_at <= now
        Optional<Order> order = orderRepository.findByOrderNo(in.orderNo());
        if (order.isEmpty()) {                                          // 순서 역전 — 주문이 아직 없다
            in.scheduleRetry(backoff(in.attempts()));                   // 1s → 5s → 30s → 5m … 상한 초과 시 수동 큐 + 알람폐기 대신 재시도
            continue;
        }
        orderTx.confirmByWebhook(order.get().getId(), in);              // 조건부 UPDATE — 이미 확정이면 no-op
        in.markProcessed();
    }
}

Outbox(발신 측)는 [B] 확정 뒤 후속 처리(재고 확정, 알림, 정산 이벤트)의 유실을 막는다. (f)에 대한 처방이 여기서 나온다 — 주문 생성은 비동기로 빼지 않는다. 비동기로 빼도 되는 것은 "주문이 확정됐다는 사실이 DB에 있고, 그 사실에서 파생되는 것"뿐이며, 그것도 메모리 이벤트가 아니라 Outbox를 거친다.

  • 후속 처리가 프로세스 사망에도 살아남는다
  • 두 테이블 자체가 5-1 영향 범위 산정에 쓸 흔적이 된다
치르는 값
  • 테이블 두 개와 처리기·릴레이라는 운영 대상 — 적체 모니터링, 청소 배치, 재시도 상한과 수동 큐 정책
  • 처리가 비동기가 되므로 지연, at-least-once라 소비자 멱등 필수(②와 맞물림)
  • 작은 서비스에선 운영 비용이 막는 사고보다 클 수 있다 — 그땐 ①②④로 시작하고 웹훅은 "PG 조회 트리거"로만 쓰는 축소판도 답

6-4. 방어선 ④ — 양방향 대사 배치: 두 원장을 주기적으로 맞춘다

①②③이 전부 있어도 뚫린다 — 정리 배치의 버그, PG 쪽 장애, 우리가 생각 못 한 일곱 번째 경로. 그래서 PG 원장과 주문 원장을 주기적으로 대조하는 배치가 마지막 그물이다. 세 방향으로 돈다 — (1) 우리 쪽 오래된 PENDING → PG에 상태 조회 (2) PG 승인 목록 → 우리 쪽 확정 주문 존재 확인 (3) 우리 쪽 CONFIRMED → 승인 결제 존재 확인. 코드는 7-1에.

얻는 것
  • 어떤 경로로 새든 대사 주기 안에 반드시 발견
  • 불일치 지속 시간에 상한이 생기고, 그 상한은 배치 주기라는 우리가 정하는 숫자
  • CS보다 먼저 안다
치르는 값
  • PG 조회 API 비용과 rate limit — PENDING 1만 건인 날 1만 번 조회하면 PG가 차단할 수 있다. 배치 크기·간격 조절
  • PG 의존 — PG가 장애면 대사도 못 돈다. "대사 중단" 알람 + 복구 후 밀린 구간 재실행
  • 주기 vs 탐지 지연 — 1분마다면 빨리 잡지만 부하, 하루 한 번이면 싸지만 하루치 CS. 방향 (1)은 분 단위, (2)는 정산 파일 기준 일 단위가 보통
  • 오보정의 위험 — 자동 보정이 틀리면 대사가 사고의 원인. 자동/수동 경계를 코드로(7-1)

6-5. 방어선 ⑤ — 알람: CS보다 먼저 아는 장치

관측 없이는 ④가 돌아도 아무도 안 본다. 원칙 — "결제 승인 수 vs 주문 확정 수"의 차이를 분 단위로 보고, PENDING의 나이 분포와 대사 불일치 건수를 알람 대상으로 둔다. 임계치는 "0건이어야 정상"인 지표(불일치 건수)와 "분포가 정상이어야 하는" 지표(PENDING 나이 p99)를 구분한다.

얻는 것
  • 탐지 주체가 CS에서 시스템으로 바뀐다 — 회고의 "탐지까지 걸린 시간"이 분 단위로
  • 배포·failover 마커와 겹쳐 보면 (e)의 상관이 한눈에
치르는 값
  • 오탐 — PG 결제창 체류 시간이 긴 상품군에서는 PENDING 나이 알람이 계속 울린다
  • 임계치를 결제창 유효 시간과 맞추고 상품군별로 분리하는 조정 비용

6-6. 원인 ↔ 방어선 대응표 — 왜 다섯 겹인가

원인1차로 막는 방어선그래도 뚫리면코드로 고정 (7절)
(a) 경계 오류① 순서 설계④ 대사ArchUnit — 트랜잭션 안 PG 호출 금지
(b) 웹훅 역전·유실③ Inbox + 지연 재시도④ 대사 (PG 조회)테스트 — "웹훅이 먼저 와도 버려지지 않는다"
(c) 불명·크래시① PENDING 흔적 + graceful shutdown④ 대사테스트 — "확정 실패해도 PENDING이 남고 대사가 복구"
(d) 멱등 충돌② 결과 저장·상태별 재개④ 대사테스트 — "같은 키 두 번이면 PENDING에서 이어간다"
(e) failover① PENDING 흔적 + 반동기 복제④ 대사대시보드에 배포·failover 마커
(f) 비동기 유실주문 생성은 동기 [A]로, 후속만 ③ Outbox④ 대사ArchUnit — @Async에서 OrderTxService 접근 금지

"무엇부터 하겠습니까?" — 답은 ①이 아니라 ④⑤

표에서 ④는 모든 행의 마지막 칸이다. ①②③은 각각 특정 원인을 막지만 ④⑤는 원인을 모르는 사고까지 잡는다. 지금 당장 사고가 나 있는 상황에서는 "다시 안 나게"보다 "나면 바로 알게"가 먼저다. 이것이 사고 대응 사이클에서 재발 방지의 우선순위다.

7안전망을 코드로 고정 — "조심하자"가 아니라 "못 어기게"

7-1. 대사 배치 — 양방향 탐지 + 자동 보정 vs 수동 큐 기준

자동 보정 허용 조건이 코드로 박힌 줄사람에게 넘기는 줄

@Component
@RequiredArgsConstructor
public class PaymentOrderReconciler {

    private static final Duration GRACE = Duration.ofMinutes(5);      // 정상 흐름([A]→[PG]→[B])이 끝나기에 충분한 시간
    private static final int BATCH = 200;                              // PG rate limit 과 DB 부하를 함께 고려한 크기
    private static final int CIRCUIT_BREAK = 500;                      // 이 이상이면 대사가 아니라 장애 — 멈추고 사람을 부른다조건⑤ 임계치

    // 방향 (1) — 우리 쪽 오래된 PENDING → PG 에 진실을 묻는다 (분 단위)
    @Scheduled(fixedDelay = 60_000)
    public void reconcilePendingOrders() {
        Instant threshold = clock.instant().minus(GRACE);
        long total = orderRepository.countPendingOlderThan(threshold);
        if (total > CIRCUIT_BREAK) { alert.critical("PENDING 폭증 — 대사 중단", total); return; }조건⑤

        for (Order o : orderRepository.findPendingOlderThan(threshold, BATCH)) {   // 인덱스: orders(status, created_at)
            PgInquiry pg = pgClient.inquireByOrderNo(o.getOrderNo());
            switch (pg.status()) {
                case APPROVED -> {조건① PG가 명확히 답함
                    if (pg.amount().compareTo(o.getAmount()) != 0) {                 // 금액 불일치 — 자동 보정 금지조건② 위반 → 사람
                        manualQueue.push(o.getOrderNo(), pg, "AMOUNT_MISMATCH"); break;
                    }
                    orderTx.confirm(o.getId(), pg.toApproval());                      // 조건부 UPDATE — 멱등조건③ 멱등 · 조건④ 고객이 원한 방향
                    metrics.counter("reconcile.auto_confirmed").increment();          // 0 이 아니면 어딘가 새고 있다는 뜻
                }
                case CANCELED, FAILED, NOT_FOUND -> orderTx.markFailed(o.getId(), "RECONCILED_" + pg.status());조건①
                case IN_PROGRESS -> { /* 결제창 체류 중 — 다음 주기 */ }조건① — 불명은 안 건드림
            }
        }
    }

    // 방향 (2) — PG 원장 기준: 승인됐는데 우리 쪽에 확정 주문이 없는 건 (정산 API/파일, 일 단위)
    @Scheduled(cron = "0 30 4 * * *")
    public void reconcileAgainstPgLedger() {
        for (PgTransaction tx : pgClient.listApproved(yesterday())) {
            if (!orderRepository.existsConfirmedByPaymentKey(tx.paymentKey())) {
                manualQueue.push(tx.orderNo(), tx, "APPROVED_WITHOUT_ORDER");         // 우리 쪽 흔적 없음 → 자동 보정 불가사람
                alert.critical("결제 승인인데 주문 없음", tx);
            }
        }
    }

    // 방향 (3) — 주문은 확정인데 승인 결제가 없는 건 (돈 안 받고 물건 나가는 방향)
    @Scheduled(fixedDelay = 300_000)
    public void reconcileConfirmedWithoutPayment() {
        for (Order o : orderRepository.findConfirmedWithoutApprovedPayment(clock.instant().minus(GRACE), BATCH)) {
            PgInquiry pg = pgClient.inquireByOrderNo(o.getOrderNo());
            if (pg.status() == APPROVED) {
                paymentTx.recordMissing(o.getId(), pg);                              // 결제 기록만 빠진 것 → 자동 보정
            } else {
                manualQueue.push(o.getOrderNo(), pg, "CONFIRMED_WITHOUT_PAYMENT");   // 확정 취소는 배송·재고가 얽힘 → 사람조건④ — 취소 방향은 수동
                alert.critical("주문 확정인데 승인 결제 없음", o.getOrderNo());
            }
        }
    }
}

자동 보정을 허용하는 다섯 조건 — 코드에 박아 둔다

  1. PG가 진실을 명확히 답했다(APPROVED/CANCELED). IN_PROGRESS나 조회 실패는 건드리지 않는다.
  2. 주문번호·금액·통화가 정확히 일치한다.
  3. 보정 동작이 멱등하다 — 조건부 UPDATE, 유니크 제약.
  4. 보정 방향이 고객이 원한 결과 쪽이다 — PENDING→CONFIRMED는 자동, CONFIRMED→취소는 수동.
  5. 건수가 임계치 이하다. 갑자기 수백 건이면 대사가 아니라 장애 — 멈추고 알람. 자동 보정이 장애를 조용히 덮어 원인 규명을 늦추는 것을 막는다.

한 줄로: "진실이 명확하고, 멱등하고, 고객이 원한 방향이고, 건수가 정상 범위일 때만 자동 — 나머지는 사람." 수동 큐로 보내는 것: 금액 불일치 / 우리 쪽 흔적 없음(방향 2) / 확정 취소 방향(방향 3의 미승인) / 부분 취소·환불 진행 중 / 임계치 초과. 수동 큐는 "담당자가 보는 화면"이 있어야 큐다 — 로그 한 줄은 큐가 아니다.

reconcile.auto_confirmed는 0이 정상이다

자동 보정이 매일 몇 건씩 잡힌다면 대사가 잘 돌고 있다는 뜻이 아니라 ①②③ 어딘가가 새고 있다는 뜻이다. 그 건들의 원인을 4절로 좁혀 앞 방어선을 고친다. 대사는 그물이지 처방이 아니다.

7-2. ArchUnit — 트랜잭션 안에서 PG를 부르지 못하게

(a)는 코드 리뷰어의 눈에 의존하면 반드시 재발한다. 빌드 단계에서 막는다.

@AnalyzeClasses(packages = "com.example")
class PaymentBoundaryRulesTest {

    @ArchTest
    static final ArchRule 트랜잭션_안에서_PG를_호출하지_않는다 =
        noMethods().that().areAnnotatedWith(Transactional.class)
            .or().areDeclaredInClassesThat().areAnnotatedWith(Transactional.class)
            .should().accessClassesThat().resideInAnyPackage("..infrastructure.pg..", "..client.pg..")
            .because("PG 승인은 롤백되지 않는다 — 트랜잭션 안에서 부르면 롤백 시 '결제됐는데 주문 없음'이 된다");

    @ArchTest
    static final ArchRule 주문_생성은_비동기_리스너에서_하지_않는다 =
        noMethods().that().areAnnotatedWith(Async.class)
            .should().accessClassesThat().haveSimpleNameEndingWith("OrderTxService")
            .because("주문이라는 진실을 메모리 위 이벤트에 맡기지 않는다 — 후속 처리만 Outbox 를 거쳐 비동기로");
}

한계를 같이 말한다 — PgClient가 인터페이스이고 구현체만 HTTP를 쓰면 "접근"으로 안 잡히므로 패키지 규약(..infrastructure.pg..)을 룰에 명시해야 하고, TransactionTemplate 블록 안의 호출은 애노테이션 기반 룰로는 못 잡는다. 룰은 "가장 흔한 위반을 막고, 우회하려면 룰을 고쳐야 하니 논의가 강제된다"는 가치로 쓰고 나머지는 7-3의 테스트가 받친다.

7-3. 부분 실패를 테스트로 고정

"PG 승인 뒤 우리 쪽이 죽어도 흔적이 남고 대사가 복구한다"는 성질은 테스트가 지켜야 한다. 그렇지 않으면 다음 리팩터링에서 [A]와 [PG]가 다시 한 트랜잭션으로 합쳐진다. 테스트 이름이 곧 사고 시나리오여야 다음 사람이 왜 이 구조인지 안다.

@SpringBootTest
class PaymentPartialFailureTest {

    @Test
    void PG_승인_후_확정_단계가_실패해도_PENDING이_남고_대사가_복구한다() {(c)(e) 고정
        // given — PG 는 승인하고, 확정 트랜잭션은 첫 호출에 DB 장애를 흉내 낸다
        pgStub.willApprove(cmd.orderNo(), cmd.amount());
        orderTxFailure.failNextConfirmWith(new CannotCreateTransactionException("failover"));

        // when
        assertThatThrownBy(() -> facade.place(cmd)).isInstanceOf(CannotCreateTransactionException.class);

        // then — 흔적이 남아 있다 (before 구조였다면 여기서 행이 없다)
        Order o = orderRepository.findByOrderNo(cmd.orderNo()).orElseThrow();
        assertThat(o.getStatus()).isEqualTo(OrderStatus.PENDING);

        // and — 대사 배치가 PG 에 묻고 확정한다
        clock.advance(Duration.ofMinutes(6));
        reconciler.reconcilePendingOrders();
        assertThat(orderRepository.findByOrderNo(cmd.orderNo()).orElseThrow().getStatus()).isEqualTo(OrderStatus.CONFIRMED);
        assertThat(paymentRepository.findByPaymentKey(pgStub.lastPaymentKey())).isPresent();
    }

    @Test
    void 승인_웹훅이_주문보다_먼저_와도_버려지지_않고_나중에_매칭된다() {(b) 고정
        webhookEndpoint.receive(PgWebhook.done("ORD-1", "pk-1"));       // 주문이 아직 없다
        inboxProcessor.processInbox();                                    // 매칭 실패 → 재시도 예약, 폐기 아님
        assertThat(inboxRepository.findByEventId("evt-1").get().getStatus()).isEqualTo(PENDING_RETRY);

        orderTx.createPending(cmdFor("ORD-1"));                           // 이제 주문이 생겼다
        clock.advance(Duration.ofSeconds(5));
        inboxProcessor.processInbox();
        assertThat(orderRepository.findByOrderNo("ORD-1").get().getStatus()).isEqualTo(OrderStatus.CONFIRMED);
    }
}

두 번째 테스트가 (b)를, 첫 번째가 (c)(e)를 고정한다. (a)는 7-2가, (d)는 "같은 멱등키로 두 번 호출하면 두 번째가 PENDING에서 이어간다"는 테스트로 고정한다.

7-4. 관측 지표와 알람 — 숫자로 본다

-- 오래된 PENDING 건수 — 0 이 아니어도 되지만 늘어나면 안 된다 (결제창 유효 시간을 임계치로)
SELECT COUNT(*) FROM orders
WHERE status = 'PENDING' AND created_at < NOW() - INTERVAL 10 MINUTE;

-- 분 단위 승인 vs 확정 차이 — PG 승인 콜백/웹훅 수와 CONFIRMED 전이 수를 같은 창에서 비교
SELECT DATE_FORMAT(confirmed_at, '%Y-%m-%d %H:%i') AS minute, COUNT(*) AS confirmed
FROM orders WHERE confirmed_at >= NOW() - INTERVAL 30 MINUTE
GROUP BY minute;

알람 대상 네 가지 + 인프라 처방 한 줄

  1. 대사 불일치 건수(방향 2·3) > 0
  2. reconcile.auto_confirmed 증가율 — 0이 정상
  3. PENDING 나이 p99 > 결제창 유효 시간
  4. Inbox 미처리 적체 · 재시도 상한 도달 건수

배포·failover 이벤트를 같은 대시보드에 마커로 올려 (e)의 상관을 한눈에. 인프라 — server.shutdown=graceful과 종료 유예 시간을 두어 SIGTERM 시 진행 중인 [B]가 끝날 시간을 준다 (c)(ii).

7-5. 회고 — 무엇을 남기나

  1. 타임라인 — 첫 발생 → 탐지 → 임시 조치 → 원인 확정 → 복구, 각 시각
  2. 탐지까지 걸린 시간 — CS로 알았다면 그 시간이 곧 ⑤의 부재 비용
  3. 영향 — 건수·금액·고객 수 (5-1 쿼리 결과)
  4. 원인 사슬 — 3절의 t1→t6 타임라인 형식 그대로
  5. 왜 방어선이 없었나 / 있었는데 왜 뚫렸나 — 6-6 표에 대입
  6. 액션 아이템 — 담당·기한. "조심하자"류는 액션이 아님. 7-1~7-4 중 무엇을 넣는지
  7. 재발 시 잡아낼 지표 — 7-4 중 무엇이 울릴 것인가. 이 항목이 없는 회고는 "다음에도 CS로 알겠다"는 선언이다.

8꼬리질문 — 먼저 스스로 답하고 펼친다

"그냥 XA/2PC로 PG까지 한 트랜잭션에 묶으면 되지 않나요?"

세 가지로 답한다. ① PG는 XA 리소스가 아니다 — 외부 HTTP API에 prepare/commit 프로토콜을 걸 수 없다. ② 설령 된다 해도 "불명"은 남는다 — 2PC의 커밋 응답이 유실되면 코디네이터도 참여자 상태를 모르고, 그 복구가 곧 대사다. ③ 비용 — 2PC는 prepare 상태에서 락을 쥔 채 남의 응답을 기다리므로 3-1의 "PG가 느린 날" 문제가 더 커진다.

그래서 외부 시스템과의 정합성은 원자성으로 푸는 것이 아니라 "시도의 흔적 + 멱등 + 대사"로 최종적 일관성을 만드는 것이 정석이다. 이 답이 있어야 "왜 Outbox·대사 같은 번거로운 걸 하느냐"에 대한 근거가 선다.

"PENDING 주문을 먼저 만들면 재고는 언제 차감하나요? PENDING이 쌓이면요?"

두 선택지와 각각의 대가로 답한다. PENDING에서 선점하면 결제 중 품절이 없어 UX가 좋지만 이탈 고객이 재고를 묶으므로 선점 TTL과 해제 배치가 필요하고, 그 배치가 늦으면 "재고 있는데 품절 표시"가 된다. 확정([B])에서 차감하면 PENDING 부담은 없지만 승인 뒤 품절이 날 수 있어 PG 취소(보상) 경로와 고객 안내가 필요하다. 한정 수량·타임세일은 선점, 일반 상품은 확정 차감이 보통.

어느 쪽이든 PENDING 정리 배치는 PG 조회 후 만료해야 한다 — 확인 없이 만료하면 배치가 이 사고를 만든다. "PENDING이 쌓이면"에 대한 답은 "쌓이는 것 자체는 정상이고, 나이 분포를 알람으로 본다"(7-4)이다.

"웹훅이 주문보다 먼저 왔습니다. 그냥 버리고 승인 API 응답으로만 처리하면 안 되나요?"

승인 API 응답 경로가 (c)(e)로 죽을 수 있기 때문에 웹훅은 두 번째 기회이고, 두 번째 기회를 버리는 것은 방어선 하나를 스스로 없애는 일이다. 그래서 Inbox에 "받았다"만 먼저 남기고 지연 재시도로 매칭한다.

단 반대 방향의 함정도 말한다 — 웹훅은 통지이지 진실이 아니다. 서명 검증 없이 웹훅 본문만 믿고 확정하면 위조 요청으로 주문이 확정될 수 있으므로, 보수적인 설계는 웹훅을 "PG에 조회하라는 트리거"로만 쓰고 확정의 근거는 항상 PG 조회 결과로 삼는다. 그러면 웹훅 순서·중복·위조가 전부 무해해진다.

"대사 배치가 불일치를 찾았으면 자동으로 다 보정하면 되지, 왜 수동 큐를 두나요?" 시니어 변별

자동 보정은 틀렸을 때 되돌리기 어려운 방향과 원인을 덮어버리는 효과라는 두 위험이 있다. 첫째, PENDING→CONFIRMED는 고객이 원한 결과라 자동이 안전하지만, CONFIRMED→취소는 배송·재고·쿠폰 복원이 얽혀 자동 취소가 새 사고를 만든다. 금액 불일치는 "어느 쪽이 맞는지"를 기계가 판단할 수 없다. 둘째, 자동 보정이 매일 조용히 수십 건을 고치고 있으면 앞 방어선이 새고 있다는 신호가 사라진다 — 그래서 auto_confirmed 카운터를 "0이 정상"으로 알람에 걸고, 임계치를 넘으면 보정을 멈춘다(7-1의 다섯 조건).

요약하면 "진실이 명확하고, 멱등하고, 고객이 원한 방향이고, 건수가 정상 범위일 때만 자동 — 나머지는 사람"이 기준이고, 이 기준을 코드에 박아야 담당자가 바뀌어도 유지된다.

"PG 승인을 트랜잭션 밖으로 뺐더니 이번엔 '주문은 확정인데 결제 기록이 없다'가 생겼습니다." 가산점

쪼갠 뒤에 생기는 반대 방향 불일치를 알고 있는지 묻는 질문이다. [B] 안에서 confirmIfPending UPDATE와 payment INSERT가 같은 트랜잭션이면 둘 중 하나만 남을 수는 없다 — 그러므로 이 증상은 [B]가 둘로 쪼개져 있거나(확정은 응답 경로에서, 결제 기록은 웹훅 경로에서), 웹훅 경로가 확정만 하고 결제 기록을 안 남기거나, 예전 데이터 마이그레이션 잔재다.

처방은 확정과 결제 기록을 한 트랜잭션에 두는 것(이 둘은 순수 DB 작업이라 쪼갤 이유가 없다 — "블로킹 I/O가 없고 함께 되돌려야 하면 쪼개지 않는다")과, 그래도 새는 것을 잡는 대사 방향 (3)이다. "양방향 대사가 그래서 필요하다"로 연결하면 6-4를 이해한 것이다.

"AUTO_INCREMENT ID 갭이 왜 (a)의 증거가 되나요?" 추가

InnoDB의 AUTO_INCREMENT 카운터는 INSERT 시점에 값을 배정하고, 그 트랜잭션이 롤백돼도 카운터는 되돌아오지 않는다. 그래서 "INSERT까지는 실행됐다가 롤백됐다"는 사건은 행 없이 ID 구멍으로만 남는다. 사고 시각 부근의 갭이 승인 로그 직후 예외 스택과 같은 시각이면 (a)의 DB 쪽 증거다.

단, 갭은 다른 이유(정상적인 다른 롤백, 벌크 INSERT의 값 예약, 유니크 충돌 실패)로도 생기므로 단독 증거가 아니라 시각·로그와 함께 보는 보조 단서다. (c)(ii)의 크래시나 (e)(α)처럼 INSERT 자체가 안 갔으면 갭이 없다 — 갭의 유무가 "INSERT 전에 죽었나, INSERT 뒤에 롤백됐나"를 가른다.

"t5의 예외가 checked 예외였다면 증상이 어떻게 달라지나요?" 추가

스프링 @Transactional의 기본 규칙은 unchecked(RuntimeException·Error)에만 롤백이다. t5가 checked 예외면 프록시는 롤백 마크 없이 커밋한다 — 주문(t4)이 남고 쿠폰 처리만 안 된 "주문은 있는데 쿠폰이 안 쓰인" 반대 증상이 된다. 같은 코드, 같은 위치의 예외인데 종류에 따라 사고 유형이 갈린다는 사실 자체가 "롤백 규칙을 모르면 사고 유형을 못 맞춘다"는 뜻이다.

덧붙이면, 그 경우에도 트랜잭션 안에 PG 호출이 있다는 구조적 문제는 그대로다 — 다음번 unchecked 예외에서 (a)가 난다. 예외 종류로 운이 갈리는 구조를 두지 말고 승인을 밖으로 빼는 것이 답이다.

"웹훅 핸들러가 5xx를 돌려주면 PG가 재시도하니 Inbox 없이도 괜찮지 않나요?" 추가

재시도 정책(횟수·간격·중단 조건)을 PG가 쥐고 있다는 것이 문제다. 재시도 창 안에 우리 배포가 겹치거나, 새 버전에서 경로·인증 방식이 바뀌어 4xx를 돌려주면 PG는 재시도를 멈추고 그 웹훅은 영영 오지 않는다. 또 (b)의 t3처럼 "주문이 없다"를 200으로 돌려주는 코드는 재시도조차 유발하지 않는다.

Inbox는 재시도의 주도권을 우리 쪽으로 가져오는 장치다 — 수신은 무조건 200으로 확정하고, 매칭 실패는 우리 스케줄(1s → 5s → 30s → 5m …)로 재시도하며, 상한 초과는 수동 큐 + 알람으로 넘긴다. "수신 실패"와 "처리 실패"를 분리하는 것이 핵심이다.

"graceful shutdown은 여섯 후보 중 무엇을 막나요? 못 막는 건요?" 추가

server.shutdown=graceful + 종료 유예 시간은 배포 SIGTERM 시 진행 중인 요청이 끝날 시간을 준다 — (c)(ii)의 "배포로 인한 강제 종료"와 (e)의 "배포로 커넥션 종료"를 완화한다. 진행 중인 [B]가 끝난 뒤에 프로세스가 내려가므로 PENDING이 확정될 시간을 번다.

못 막는 것: OOMKilled·노드 축출·전원 장애처럼 유예 없이 죽는 경우, 그리고 DB 쪽 failover(e)(β)(γ). 그래서 graceful shutdown은 ①(PENDING 흔적)과 ④(대사)를 대체하는 것이 아니라 그 앞에 얹는 완화책이다 — "인프라 처방 한 줄"로 언급하되 이것만으로 충분하다고 말하지 않는다.

"왜 DB 유니크 제약이 멱등 세 층 중 '4장 관점에서 가장 중요한 층'인가요?" 추가

요청 층과 PG 층은 애플리케이션 코드다 — 키 스코프를 잘못 잡거나, 캐시가 날아가거나, 배포 중 두 버전이 섞이면 뚫린다. 반면 payment.payment_key UNIQUE·orders.order_no UNIQUE·WHERE status='PENDING' 조건부 UPDATE는 DB 엔진이 강제하므로 위 두 층이 어떻게 실패하든 두 번째 INSERT와 두 번째 확정을 거절한다.

"애플리케이션 멱등은 버그가 날 수 있지만 유니크 제약은 안 난다" — 그래서 DB 층은 "있으면 좋은 것"이 아니라 앞 두 층의 버그를 이중 결제·이중 확정이 아니라 예외 한 번으로 바꿔 주는 최후 방어선이다. 예외가 나면 그 키의 현재 상태를 읽어 이어가면 된다.

"작은 서비스라 Outbox/Inbox까지 운영할 여력이 없습니다. 어디까지 줄여도 되나요?" 추가

③은 테이블 두 개 + 처리기·릴레이 + 적체 모니터링 + 청소 배치라는 운영 대상을 늘리므로, 작은 서비스에선 막는 사고보다 비용이 클 수 있다. 축소판은 ①②④로 시작하는 것 — PENDING 선생성과 조건부 확정(①), 유니크 제약 중심의 멱등(②), 방향 (1)의 PENDING 대사(④)만 있어도 (a)(c)(d)(e)는 "대사 주기 안에 잡히는 불일치"가 된다.

웹훅은 처리하지 말고 "이 주문번호를 PG에 조회해 보라"는 트리거로만 쓴다 — 확정의 근거는 항상 PG 조회 결과이므로 순서 역전·중복·위조가 무해해지고 Inbox 테이블 없이도 (b)의 절반이 사라진다. 대신 포기한 것도 말한다 — 후속 처리(알림·정산 이벤트)의 유실 방지는 없으므로 그 부분은 대사 방향 (3)류의 배치로 보완해야 한다.

양방향 대사 배치 코드(3방향 + 5조건 + 수동 큐) / ArchUnit(트랜잭션 안 PG 호출 금지, @Async에서 주문 생성 금지) / 부분 실패 테스트(확정 실패해도 PENDING 잔존 + 대사 복구, 웹훅 선착 매칭) / 알람 4종(불일치 건수, auto_confirmed, PENDING 나이 p99, Inbox 적체).

한 줄 요약 — 면접장을 나올 때 이 문장이 남아야 한다

"결제됐는데 주문이 없다"는 PG 원장과 우리 원장이 다른 시스템이고 롤백은 우리 쪽만 되돌린다는 사실에서 나오는 사고이며, 원인은 (a) 트랜잭션 안 승인 후 롤백 (b) 웹훅 순서 역전·폐기 (c) 불명을 실패로 취급 (d) 멱등 레코드가 결과 대신 "봤다"만 기억 (e) failover·배포 중 커밋 전 단절 (f) 비동기 후처리 유실 여섯 경로로 열거해 "고객이 성공 화면을 봤는가 / 우리 DB에 흔적이 있는가"로 좁히고, 재발 방지는 ① PENDING 선생성 → 밖에서 승인 → 조건부 확정 ② 요청·PG·DB 유니크 세 층 멱등 ③ Inbox/Outbox ④ 양방향 대사 배치 ⑤ 알람 다섯 겹으로 — 각각 정리 배치·키 저장소·릴레이 운영·PG 조회 비용과 의존·오탐이라는 값을 치르며 — 쌓되, 이 모든 것을 ArchUnit·부분 실패 테스트·대사 코드·"0이 정상"인 카운터로 못 어기게 고정해야 사고 대응 사이클이 사람의 기억이 아니라 시스템의 성질이 된다.
