커버링 인덱스
북마크 룩업을 0으로 만드는 대신 인덱스 폭·쓰기·취약성을 치른다

핵심 관전 포인트 — 첫 답변으로 그대로

커버링 인덱스는 쿼리가 필요로 하는 모든 컬럼(SELECT 목록 · WHERE · ORDER BY · 조인 키)이 세컨더리 인덱스 안에 들어 있어서, 리프에서 PK를 꺼내 클러스터드 인덱스를 다시 타는 2단계(북마크 룩업)가 통째로 사라진 상태다. 빠른 이유는 "테이블에 안 가서"가 아니라 — 북마크 룩업은 행 1건마다 PK 순으로 흩어진 페이지를 한 장씩 찌르는 랜덤 I/O인데, 커버링은 그것을 좁은 리프 페이지 몇 장을 연결 리스트 따라 이어 읽는 순차 I/O로 바꾸기 때문이다. 효과가 큰 조건은 "많이 · 좁게 · 자주" 불리는 쿼리(목록·랭킹·COUNT·페이징)이고, 대가는 인덱스 폭 증가(버퍼 풀 적재율↓) · 포함 컬럼 UPDATE마다의 쓰기 증폭 · SELECT에 컬럼 하나만 추가해도 조용히 깨지는 취약성이다. EXPLAIN에서 Extra: Using index가 커버링이고, Using index condition은 룩업 횟수만 줄이는 ICP라 다른 것이다.

질문 — "커버링 인덱스란? 어떤 상황에서 효과가 큰가요?"
출제 의도 — 랭킹·목록 조회 같은 고빈도 쿼리를 디스크 접근 없이 처리하는 핵심 기법. 아는 사람은 같은 하드웨어에서 몇 배의 처리량을 뽑는다. "인덱스만 읽고 끝난다"는 정의의 암기가 아니라 왜 몇 배인지를 I/O 비용 모델(랜덤 vs 순차)로 설명하는지, 그 몇 배를 위해 무엇을 지불하는지(폭·쓰기·취약성)를 함께 말해 "언제 쓰고 언제 쓰지 않는지"를 스스로 판단하는지를 본다.

전제 한 줄 — "세컨더리 조회는 2단계이고, 2단계는 랜덤 I/O다." 이 한 줄이 흔들리면 이 문서도 같이 흔들린다. (B+Tree §4 · 클러스터드 vs 세컨더리 §1 · 인덱스가 있는데 풀스캔 §4의 공통 축)

0. 용어 먼저, 그리고 비유 하나본문에서 반복되는 낱말을 미리 풀어 둔다

클러스터드 인덱스
InnoDB에서 테이블 그 자체. PK 순으로 정렬돼 있고 리프에 행 전체가 들어 있다.
세컨더리 인덱스
PK 외의 인덱스. 리프 엔트리 = (인덱스 컬럼들, PK). 행 전체는 없다.
북마크 룩업
세컨더리 리프에서 얻은 PK로 클러스터드 인덱스를 다시 탐색해 행을 가져오는 2단계. 행마다 1회.
버퍼 풀 / 워킹셋
버퍼 풀 = InnoDB가 페이지를 올려두는 메모리 캐시. 워킹셋 = 어떤 작업이 실제로 만지는 페이지의 집합. 워킹셋이 넓을수록 캐시 미스가 는다.
미리 읽기 (read-ahead)
연속 접근을 감지하면 다음 묶음(익스텐트)을 미리 올려두는 기능. 순차 접근에서만 작동한다.
ICP
Index Condition Pushdown. 인덱스 컬럼으로 된 조건을 룩업 전에 인덱스 엔트리에서 평가해 탈락 행의 룩업을 건너뛴다. 커버링이 아니다.

비유 — 이름순 명부와 주소순 도시

테이블(클러스터드)
집들이 주소 순(PK 순)으로 늘어선 도시
세컨더리 인덱스
이름순 명부. 각 줄에 (이름, 주소)만 적혀 있다
북마크 룩업
"김씨들의 전화번호를 알려줘" → 명부에서 김씨는 연달아 있지만(리프 순차), 주소는 도시 전역에 흩어져 집집마다 찾아간다(랜덤 I/O N회)
커버링
명부 각 줄에 전화번호까지 적어 둔다 → 명부만 훑고 끝, 집에 안 간다
대가
명부가 두꺼워지고(폭), 번호가 바뀔 때마다 명부도 고쳐야 하고(쓰기), "이메일도 알려줘"라고 하는 순간 도로 집집마다 다닌다(취약)

1. 개념 — "인덱스만 읽고 끝난다"가 정확히 어느 단계를 없애는가

정의 — 세 군데의 컬럼이 전부 인덱스 안에 있어야 한다

세컨더리 리프 엔트리는 (인덱스 컬럼들, PK)다. 쿼리가 쓰는 컬럼이 이 엔트리 안에서 전부 해결되면 DB는 PK를 들고 클러스터드로 내려갈 이유가 없다. 이 상태의 인덱스를 그 쿼리에 대한 커버링 인덱스라 부른다.

"커버링"은 인덱스의 종류가 아니라 인덱스와 쿼리의 관계다. 같은 인덱스가 어떤 쿼리에는 커버링이고 다른 쿼리에는 아니다. — 이 한 줄이 §3의 "취약성"의 뿌리다.

①
SELECT 목록
의 컬럼
②
WHERE
조인이면 ON 조건까지
③
ORDER BY / GROUP BY
의 컬럼

InnoDB의 공짜 한 줄 — PK 컬럼은 모든 세컨더리 리프에 이미 들어 있으므로 인덱스 정의에 안 써도 커버된다. (user_id) 인덱스 하나로 SELECT id FROM orders WHERE user_id = ?는 이미 커버링이다. 가산점 이 성질이 §6 "지연 조인"의 근거다.

1-2. 비용 사슬 — "왔다갔다"를 I/O 단위로 분해한다이 절이 문서의 심장. 결론이 아니라 어느 고리가 끊겼는지를 이름 붙여 말한다

"테이블까지 안 가서 빠르다", "왔다갔다 안 해서 빠르다"는 결론이지 비용이 아니다. 아래 두 그림의 차이를 말로 옮길 수 있어야 한다.

커버링이 아닐 때의 사슬 6고리 — 커버링은 ⑴을 끊는다

  1. 필요한 컬럼이 인덱스 밖에 있다 ✂ 커버링이 끊는 고리
  2. 리프에서 얻은 PK로 클러스터드 B+Tree를 행마다 한 번씩 재탐색 (루트·브랜치는 캐시돼 있어도 리프는 행마다 다른 페이지)
  3. 세컨더리는 (user_id, created_at) 순, 클러스터드는 PK 순 → 인덱스에서 이웃한 두 엔트리의 행이 테이블에서는 서로 먼 페이지
  4. 룩업 1건 = 흩어진 페이지 1장을 따로 요청 = 랜덤 I/O 1회
  5. 대상이 N행이면 랜덤 I/O N회, 그 N장은 테이블 전역에 퍼져 워킹셋 = 테이블 전체
  6. 버퍼 풀에 없는 비율만큼 디스크 랜덤 읽기 → 처리량이 초당 랜덤 I/O 수에 묶인다

⑴이 끊기면 ⑵의 재탐색이 없고 ⑶~⑹이 통째로 사라진다. 남는 것은 세컨더리 리프를 연결 리스트 따라 옆으로 읽는 것뿐 — 리프는 정렬 순서로 이어져 있고(순차), 엔트리가 좁아 페이지 1장에 수백 건이 들어간다.

랜덤 I/O가 순차 I/O보다 비싼 이유 — 세 축 (이 축이 비면 ⑷~⑹이 전부 "그냥 느리다"로 뭉개진다)

① 요청 단위랜덤은 16KB 페이지 1장마다 I/O 요청 1건. 순차는 이어진 페이지를 큰 묶음으로 한 번에 요청하고, InnoDB는 연속 접근을 감지하면 다음 익스텐트를 미리 읽기로 올려둔다. 랜덤에는 미리 읽기가 안 걸린다.
② 매체HDD는 요청마다 헤드 이동 + 회전 대기 → 수십 배. SSD는 기계적 대기는 없지만 요청 1건당 고정 오버헤드(커널·드라이버·컨트롤러 경로)와 미리 읽기 불가는 그대로 → 차이가 줄어들 뿐 사라지지 않는다.
③ 캐시순차는 좁은 범위만 만져 버퍼 풀 히트율이 높고, 랜덤은 워킹셋이 넓어 미스율이 높다. 즉 랜덤 I/O는 디스크 비용이자 캐시 비용이다.

"SSD니까 랜덤도 괜찮다"는 절반만 맞다. 이 한 마디를 붙이면 비용 모델을 이해했다는 신호가 된다.

숫자 감각 — 자릿수용이지 정확한 상수가 아니다

쿼리커버링이 아닐 때커버링일 때
내 주문 목록 LIMIT 20리프 1장 + 랜덤 룩업 20회리프 1장
랭킹 TOP 100리프 1~2장 + 랜덤 룩업 100회리프 1~2장
COUNT(*) WHERE status='ACTIVE' (90만 행)룩업 90만 회 → 옵티마이저가 포기하고 테이블 100만 행 풀스캔좁은 인덱스 리프 수천 장 순차

세 번째 줄이 중요하다. 대상이 많아 인덱스가 버려지던 쿼리(풀스캔 문서의 손익분기)도, 커버링이면 인덱스 풀스캔(type: index)이 테이블 풀스캔보다 싸다 — 인덱스가 테이블보다 훨씬 좁기 때문이다. 커버링은 "룩업을 없앤다"에서 끝나지 않고 손익분기 자체를 옮긴다.

말하기 훈련 — 뭉뚱그린 표현을 이름 붙은 사슬로 교체

뭉뚱그린 표현이름사슬로 말하면
"테이블까지 안 가서 빠르다"북마크 룩업 제거필요한 컬럼이 인덱스 안 → PK 재탐색 0회 → 행마다 흩어진 페이지를 찌르던 랜덤 I/O N회가 → 좁은 리프 N/수백 장의 순차 읽기로
"왔다갔다 해서 느리다"랜덤 I/O + 워킹셋 확대세컨더리 정렬 ≠ PK 정렬 → 이웃 엔트리의 행이 먼 페이지 → 요청 1건당 페이지 1장 → 미리 읽기 무용 → 워킹셋 = 테이블 전체 → 버퍼 풀 미스 → 디스크 랜덤 읽기

2. 효과 — 어떤 상황에서 큰가공식 하나에서 5종이 전부 나온다

효과 ≈ (절감되는 룩업 횟수) × (룩업 1회의 랜덤 I/O 비용) × (호출 빈도) − (인덱스 폭 증가로 늘어난 비용)

앞의 세 항이 크고 마지막 항이 작을수록 효과가 크다. 효과가 큰 상황 5종은 이 공식의 항을 하나씩 키우는 조건들이다.

많이 · 좁게 · 자주 · 세기 · 정렬
① 많이
대상 행이 많다
범위 조회, 낮은 선택도. 룩업 횟수 N 자체가 크다. 극단에서는 인덱스 풀스캔이 테이블 풀스캔을 이긴다.항: 절감 룩업 횟수↑
② 좁게
필요한 컬럼이 좁다
목록 카드·랭킹 행처럼 2~4개의 짧은 컬럼만 쓴다.항: 폭 비용↓
③ 자주
호출 빈도가 높다
메인 목록 API, 랭킹 보드, 홈 화면. "같은 하드웨어에서 몇 배"는 여기서 실현된다.항: 호출 빈도↑
④ 세기
세기만 한다
COUNT/EXISTS/SUM(amount) 집계, 또는 조인에서 조인 키 + 필터 컬럼만 필요한 드리븐 테이블. 행의 나머지가 애초에 필요 없다.행의 나머지 불필요
⑤ 정렬
정렬·페이징을 인덱스에서 끝낸다
ORDER BY … LIMIT, 깊은 페이지네이션의 지연 조인. 정렬 컬럼까지 인덱스에 있어야 커버링과 filesort 제거가 동시에 성립.커버링 + 정렬 제거 동시

반대로 효과가 작거나 없는 상황 (같은 공식에서 나온다) — ⑴ PK 단건 조회: 클러스터드 리프가 이미 행이라 룩업이 없다 · ⑵ SELECT *나 TEXT/BLOB 포함: 커버 자체가 불가 · ⑶ 대상 행이 1~2건: 절감 룩업이 1~2회 · ⑷ 쓰기가 지배적인 테이블: 마지막 항이 앞을 잡아먹는다.

2-2. before / after — 목록 조회 한 건으로

orders (id BIGINT PK, user_id, status, created_at, amount, memo TEXT, …) · 화면 "내 주문 목록" 카드에는 id, created_at, amount 세 컬럼만 표시.

❌ before — 탐색용 인덱스 + SELECT *
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);

EXPLAIN SELECT * FROM orders 모든 컬럼 → 어떤 인덱스로도 못 덮음
WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20;
-- type: ref   key: idx_orders_user_created   rows: 20
-- Extra: Backward index scan  "Using index"가 없다
--   정렬은 인덱스가 해결했지만 20행 각각 PK로 클러스터드 재탐색 = 랜덤 룩업 20회
✅ after — 화면이 쓰는 amount를 인덱스 끝에 "실어" 커버링으로
-- id(PK)는 세컨더리 리프에 이미 있으니 적지 않는다.
-- 접두사가 같은 기존 인덱스는 추가가 아니라 교체(중복 인덱스 방지).
DROP INDEX idx_orders_user_created ON orders;
CREATE INDEX idx_orders_user_created_cover ON orders (user_id, created_at, amount); 나르기용 컬럼

EXPLAIN SELECT id, created_at, amount FROM orders SELECT 목록 = 인덱스 안
WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20;
-- type: ref   key: idx_orders_user_created_cover   rows: 20
-- Extra: Using index (DESC라 Backward index scan도 함께)  룩업 0회, 리프 1~2장

규칙 — 앞은 찾기용, 뒤는 나르기용

user_id등호 — 찾기 created_at범위·정렬 — 찾기 | amountpayload — 나르기 + id (PK)InnoDB가 자동 포함

amount는 조건에도 정렬에도 안 쓰인다. 인덱스 뒤쪽 컬럼은 탐색에는 기여하지 않아도 리프에 실려 있기만 하면 커버링에 기여한다. 앞쪽은 찾기 위한 컬럼(등호 → 범위/정렬 순), 뒤쪽은 나르기 위한(payload) 컬럼 — 이렇게 나눠 생각하면 설계할 때 헷갈리지 않는다.

2-3. EXPLAIN Extra 3종 — Using index ≠ Using index condition둘을 섞어 말하면 "커버링을 이해했다"는 주장이 바로 무너진다

안 간다 · 덜 간다 · 다 간다
Extra뜻북마크 룩업테이블에…
Using index커버링 — 인덱스만 읽고 끝, 테이블 접근 없음0회안 간다 (없앤다)
Using index conditionICP — 인덱스 컬럼으로 된 조건을 스토리지 엔진이 룩업 전에 인덱스 엔트리에서 평가해, 탈락한 행의 룩업을 건너뜀줄어듦 (통과한 행만)덜 간다 (줄인다)
Using where룩업으로 행을 가져온 뒤 서버 층에서 조건 평가전부다 간다 (그대로)

ICP가 왜 존재하는지를 예로 잡는다.

CREATE INDEX idx_users_last_first ON users (last_name, first_name);

SELECT * FROM users WHERE last_name = 'Kim' AND first_name LIKE '%수%';
-- last_name = 'Kim'      → 인덱스 탐색에 쓰인다(ref)
-- first_name LIKE '%수%' → 선행 와일드카드라 탐색에는 못 쓴다. 하지만 값은 인덱스 리프에 있다.

-- ICP 없음: 'Kim' 전부를 룩업해 행을 가져온 뒤 first_name을 검사   → Extra: Using where
-- ICP 있음: 리프의 first_name 값으로 먼저 거르고, 통과한 행만 룩업  → Extra: Using index condition
--   룩업 횟수: (Kim 전체) → (Kim 중 '수' 포함). 크게 줄지만 0은 아니다.
-- SELECT id, first_name 이었다면: 전부 인덱스 안                   → Extra: Using index (커버링)

한 문장 구분 — Using index는 테이블 접근이 없다, Using index condition은 테이블 접근 횟수를 인덱스에서 미리 걸러 줄인다. 커버링이 성립하면 룩업이 없으니 ICP가 등장할 자리도 없다 — Using index만 뜬다. ICP는 "커버링을 못 만들었을 때 룩업을 덜 하게 해주는 차선"으로 위치를 잡아두면 둘이 섞이지 않는다.

type 칸도 같이 읽는다. Using index가 떠도 type: index면 인덱스를 처음부터 끝까지 읽는 인덱스 풀스캔이다. 테이블 풀스캔보다는 싸지만 "좁힌 뒤 커버링"(ref/range + Using index)과는 다르므로, 좋은 신호인지는 rows와 함께 판단한다.

다른 DB는 — PostgreSQL의 Index Only Scan과 INCLUDE 가산점

  • PostgreSQL은 힙 테이블이고 MVCC 가시성 정보가 힙 튜플에 있다. 인덱스만 읽어서는 "이 행이 내 트랜잭션에 보이는가"를 알 수 없어, visibility map에 "이 페이지의 튜플은 전부 가시"로 표시된 페이지만 힙 방문을 생략한다. VACUUM이 밀리면 Index Only Scan 계획이 잡혀도 EXPLAIN ANALYZE의 Heap Fetches가 치솟아 사실상 커버링 효과가 사라진다 — "커버링 인덱스를 만들었는데 안 빨라요"의 PostgreSQL판 원인.
  • PostgreSQL과 SQL Server에는 INCLUDE (col)이 있다 — 탐색 키가 아닌 컬럼을 리프에만 실어 커버링을 만든다. 키 길이와 정렬 순서에 영향을 주지 않는다. MySQL에는 없다. 그래서 MySQL은 나르기용 컬럼도 키에 직접 붙여야 하고, 그만큼 키 길이 상한(§3)과 정렬·비교 비용을 함께 짊어진다.

3. 대가 — 트레이드오프를 한 호흡에편익만 말하면 반쪽 답. 커버링은 읽기의 랜덤 I/O를 인덱스 폭 + 쓰기 비용 + 유지보수 취약성으로 바꾸는 거래다

폭 · 쓰기 · 취약 · 상한
폭
넓어진 인덱스는 이득 일부를 스스로 갉아먹는다
나르기 컬럼↑ → 리프 엔트리 커짐 → 16KB 페이지당 엔트리↓ → 리프 페이지↑(트리 높이↑ 가능) → 버퍼 풀 적재율↓ → 다른 인덱스·테이블 페이지를 밀어냄.원칙: 필요한 컬럼만, 짧은 타입만
쓰기
실은 컬럼이 UPDATE되는 순간 그 인덱스도 갱신 대상
InnoDB는 세컨더리 엔트리를 제자리 수정하지 않고 옛 엔트리 삭제 표시 + 새 엔트리 삽입 → 인덱스 페이지 쓰기 + undo/redo↑ → UPDATE 경로 전체가 느려지고 락 점유 시간↑.기준: "행 생성 후 몇 번 바뀌는가?"
취약
SELECT에 컬럼 하나 추가하면 에러 없이 조용히 깨진다
커버링은 인덱스와 쿼리의 관계라서 쿼리 쪽이 바뀌면 인덱스는 그대로여도 관계가 깨진다. JPA 엔티티 조회는 모든 컬럼을 SELECT → 절대 커버링 불가.가장 실무적인 대가
상한
키 길이 제한 · 접두사 인덱스 · 중복 인덱스
InnoDB 키 길이 상한(DYNAMIC 행 포맷 3072바이트), TEXT/BLOB 불가, 접두사 인덱스 title(30)는 그 컬럼을 커버 못 함. 왼쪽 접두사 같은 인덱스는 추가가 아니라 교체.대형 테이블 DDL = 부하 + 복제 지연

폭 — 숫자로

VARCHAR(255) 제목이나 DECIMAL(20,4) 여러 개를 "혹시 쓸지 모르니" 싣는 순간, §1-2의 "N/수백 장"이 "N/수십 장"으로 줄어들고 이득이 반감된다. 클러스터드 문서의 "PK는 곱셈 계수"와 같은 사슬이다.

쓰기 — before / after

❌ before — "화면에 다 보이니까" 자주 바뀌는 컬럼까지 실었다
CREATE INDEX idx_orders_user_cover ON orders (user_id, created_at, amount, status, updated_at); status · updated_at
-- status는 주문 상태 전이마다, updated_at은 모든 UPDATE마다 바뀐다
-- → 주문 한 건의 상태가 바뀔 때마다 이 인덱스 엔트리가 삭제+삽입된다
-- → 읽기에서 번 랜덤 I/O를 쓰기의 인덱스 갱신으로 도로 지불
✅ after — 생성 후 거의 안 바뀌는 컬럼만 싣는다
-- 자주 바뀌는 컬럼은 화면 요구를 재협상하거나(목록엔 상태를 안 보여주고 상세에서 본다) 별도 조회로 뺀다
CREATE INDEX idx_orders_user_cover ON orders (user_id, created_at, amount); 거의 불변 컬럼만

판단 기준 한 줄 — "이 컬럼은 행이 만들어진 뒤 몇 번 바뀌는가?" 거의 안 바뀌면 싣고, 자주 바뀌면 싣지 않는다. 그 경계가 이 인덱스의 손익분기다.

취약 — 조용히 깨지는 순서

  • 기획이 카드에 status 뱃지 추가
  • →
  • DTO에 필드 하나 추가
  • →
  • SELECT 목록에 status
  • →
  • Using index 사라짐, 20행 룩업 부활
  • →
  • 목록 20건은 티도 안 남
  • →
  • 같은 인덱스를 믿던 랭킹·집계 쿼리는 절벽
  • →
  • 에러도 경고도 없음. p99 그래프만 조용히 오른다

JPA는 이 취약성을 구조적으로 안고 있다 — 엔티티를 조회하면 모든 컬럼을 SELECT하므로 엔티티 조회는 절대 커버링이 되지 않는다. 커버링을 쓰려면 DTO 프로젝션이 필수이고, 그래서 안전망(§4)이 필요하다.

상한과 중복

  • 키 길이 상한: InnoDB 인덱스 키에는 길이 상한이 있다(DYNAMIC 행 포맷 기준 3072바이트). TEXT/BLOB은 실을 수 없고, 긴 VARCHAR 여러 개를 실으면 상한에 걸린다. 접두사 인덱스(title(30))는 값의 일부만 가지므로 그 컬럼을 SELECT하는 쿼리는 커버할 수 없다.
  • 중복 인덱스: (user_id, created_at)가 있는데 (user_id, created_at, amount)를 추가하면 왼쪽 접두사가 같은 중복이다. 교체가 맞지만, 교체 전에 기존 인덱스를 쓰던 다른 쿼리를 확인해야 한다. 대형 테이블에서는 DDL 자체가 부하이자 복제 지연 요인이라는 점도 같이 말한다.
"커버링 인덱스는 읽기에서 북마크 룩업 N회, 즉 랜덤 I/O N회를 0으로 만들어 몇 배의 처리량을 얻는 대신, 폭(엔트리 비대 → 버퍼 풀 적재율↓)·쓰기(실은 컬럼 UPDATE마다 인덱스 갱신)·취약성(SELECT에 컬럼 하나 추가로 조용히 무효)을 치릅니다. 그래서 '많이 읽고, 좁게 쓰고, 자주 불리는' 쿼리에, 거의 안 바뀌는 컬럼만 실어 제한적으로 씁니다."

이 문장이 입에서 그대로 나오면 "편익만 서술"하는 약점은 이 문항에서 재발하지 않는다.

4. 안전망 — 깨짐을 사람이 아니라 코드·테스트·설정이 잡게컬럼을 추가하는 사람은 6개월 뒤의 다른 사람이고, 이 인덱스의 존재를 모른다

프로젝션 · 단정 테스트 · 마이그레이션 주석 · rows_examined 알림
코드
DTO 프로젝션
프로젝션 타입이 곧 SELECT 목록의 계약. 컬럼을 추가하려면 타입을 고쳐야 하고 그 diff가 리뷰에 드러난다.
테스트
EXPLAIN 단정
실행 계획의 key·using_index를 통합 테스트가 단정. 커버링이 깨지면 빨간불.
설정
마이그레이션 주석 + _cover
인덱스가 누구를 위해 존재하는지 파일 안에 남기고, 이름으로 "나르기용 컬럼이 실린 인덱스"임을 알린다.
운영
rows_examined 알림
마지막 그물. 비율·p99가 기준선 대비 튀면 알림. schema_unused_indexes에 _cover가 올라오면 정리 대상.

4-1. 코드 — 엔티티 SELECT * → DTO 프로젝션

❌ before — 엔티티 조회: 모든 컬럼을 SELECT하므로 어떤 인덱스로도 커버 불가
List<Order> findByUserIdOrderByCreatedAtDesc(Long userId, Pageable pageable); 엔티티 = 모든 컬럼
// → SELECT o.id, o.user_id, o.status, o.created_at, o.amount, o.memo, … FROM orders o …
✅ after — 닫힌 인터페이스 프로젝션: 여기 선언한 getter만 SELECT 된다
public interface OrderCard { SELECT 목록의 계약
    Long getId();
    LocalDateTime getCreatedAt();
    BigDecimal getAmount();
}
List<OrderCard> findByUserIdOrderByCreatedAtDesc(Long userId, Pageable pageable);
// → SELECT o.id, o.created_at, o.amount FROM orders o WHERE o.user_id = ? ORDER BY o.created_at DESC LIMIT ?
//   idx_orders_user_created_cover(user_id, created_at, amount)에 정확히 덮인다

@Query("select new …OrderCard(o.id, o.createdAt, o.amount) …")의 클래스 기반 DTO나 QueryDSL Projections.constructor도 같은 효과다. 핵심은 프로젝션 타입이 곧 SELECT 목록의 계약이라는 것 — 인덱스 정의와 1:1로 대응하는 코드상의 지점이 생긴다.

4-2. 테스트 — 실행 계획을 단정하는 통합 테스트

@Test  // Testcontainers MySQL 위에서 실행. 데이터는 수백 건 정도 적재해 둔다.
void 주문목록_조회는_커버링_인덱스를_탄다() {
    // JPA가 실제로 내보내는 SQL(p6spy 로그에서 확보)을 그대로 EXPLAIN 한다
    String plan = jdbcTemplate.queryForObject(
        "EXPLAIN FORMAT=JSON SELECT o.id, o.created_at, o.amount FROM orders o " +
        "WHERE o.user_id = 7 ORDER BY o.created_at DESC LIMIT 20", String.class);

    assertThat(plan).contains("\"key\": \"idx_orders_user_created_cover\"");
    assertThat(plan).contains("\"using_index\": true"); 커버링이 깨지면 여기서 빨간불
}

주의 두 가지. ⑴ 단정은 key·using_index처럼 구조적으로 결정되는 값에 한정 — rows나 비용 수치는 통계에 따라 흔들려 테스트가 불안정해진다. ⑵ EXPLAIN 대상 SQL은 손으로 쓴 것이 아니라 JPA가 실제로 내보낸 문장이어야 한다(p6spy·datasource-proxy 로그). 손으로 쓴 SQL이 통과해도 실제 쿼리가 다르면 거짓 안심이다.

4-3. 설정 — 마이그레이션 파일에 인덱스의 존재 이유를 박는다

-- V37__orders_user_created_cover.sql
-- [COVERING] OrderCard 프로젝션(id, created_at, amount) 전용 커버링 인덱스.
--   앞 2컬럼 = 탐색·정렬용, amount = 나르기용.
--   OrderCard에 컬럼을 추가하면 커버링이 깨진다 → OrderCoveringIndexTest가 실패한다.
--   자주 바뀌는 컬럼(status, updated_at)은 의도적으로 제외(§3-2).
CREATE INDEX idx_orders_user_created_cover ON orders (user_id, created_at, amount); _cover 접미사 규약

_cover 접미사를 붙여 두면 리뷰어가 이름만 보고 "나르기용 컬럼이 실린 인덱스"임을 알고, SHOW INDEX 결과에서 "왜 amount가 여기 있지? 지워도 되나?"라는 오판을 막는다.

4-4. 운영 — rows_examined 비율 알림, 마지막 그물

앞의 세 겹을 다 뚫고 배포된 뒤에도 에러는 나지 않는다. slow query log나 performance_schema의 쿼리 다이제스트 통계에서 해당 쿼리의 rows_examined / rows_sent 비율이나 p99 지연이 기준선 대비 튀면 알림이 오게 둔다. 커버링이 깨지면 읽는 행 수는 그대로여도 페이지 접근 수가 뛰므로 지연 그래프에 먼저 나타난다. 반대 방향도 — sys.schema_unused_indexes에 _cover 인덱스가 올라오면 쿼리 쪽이 바뀌어 더는 안 쓰이는 것이니 정리 대상이다.

5. 암기 카드 — 네 개의 목록을 한 장에면접 직전에 이 카드만 훑는다. 목록이 인출되지 않으면 사슬도 트레이드오프도 꺼낼 수 없다

효과 큰 상황 5종① 대상 행이 많다 ② 필요한 컬럼이 좁다 ③ 자주 불린다 ④ 세기만 한다(COUNT/EXISTS/집계/조인 키) ⑤ 정렬·페이징을 인덱스에서 끝낸다
→ "많이 · 좁게 · 자주 · 세기 · 정렬"
Extra 3종Using index(커버링, 룩업 0) / Using index condition(ICP, 룩업 감소) / Using where(룩업 후 필터)
→ "안 간다 · 덜 간다 · 다 간다" — 그리고 type: index는 인덱스 풀스캔
대가 4종폭(버퍼 풀 적재율↓) · 쓰기(실은 컬럼 UPDATE마다 삭제+삽입) · 취약(SELECT 컬럼 추가로 조용히 무효) · 상한(키 길이, 접두사 인덱스 불가, 중복 인덱스 교체)
안전망 4종DTO 프로젝션 · EXPLAIN 단정 테스트 · 마이그레이션 주석 + _cover 규약 · rows_examined 알림
설계 규칙앞은 찾기용(등호 → 범위/정렬) · 뒤는 나르기용(payload) · PK는 공짜 · 실을 컬럼은 "생성 후 몇 번 바뀌는가?"로 거른다
비용 사슬 한 줄컬럼이 인덱스 밖 → PK로 클러스터드 재탐색(행마다) → 세컨더리 순서 ≠ PK 순서 → 페이지 1장당 요청 1건 = 랜덤 I/O → 워킹셋 = 테이블 전체 → 버퍼 풀 미스 → 디스크 랜덤 읽기. 커버링은 첫 고리를 끊는다.

6. 꼬리질문 셀프 테스트질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다

"커버링 인덱스가 왜 빠른지, '테이블에 안 가서' 말고 I/O 단위로 설명해보세요."

세컨더리 인덱스 조회는 2단계다. 1단계는 리프를 연결 리스트로 훑는 순차 읽기라 싸고, 2단계는 리프에서 얻은 PK로 클러스터드 인덱스를 행마다 재탐색하는 것이다. 세컨더리는 자기 컬럼 순, 클러스터드는 PK 순으로 정렬돼 있어 인덱스에서 이웃한 행이 테이블에서는 먼 페이지에 있고, 그래서 2단계는 페이지 1장당 요청 1건인 랜덤 I/O다 — 미리 읽기가 안 걸리고, 워킹셋이 테이블 전체로 퍼져 버퍼 풀 미스도 늘어난다.

커버링은 필요한 컬럼이 전부 인덱스에 있어 2단계 자체가 없다. 대상 N행에 대해 "랜덤 페이지 N장"이 "좁은 리프 N/수백 장 순차"로 바뀌는 것이 몇 배의 정체다. SSD에서도 요청당 고정 오버헤드와 미리 읽기 부재 때문에 차이는 줄어들 뿐 사라지지 않는다는 한 마디를 붙인다.

"Using index와 Using index condition은 뭐가 다른가요?"

Using index는 커버링 — 쿼리가 쓰는 컬럼이 전부 인덱스에 있어 테이블 접근이 0회다. Using index condition은 ICP — 인덱스 컬럼으로 된 조건 중 탐색에는 못 쓰는 것(범위 뒤 컬럼, 선행 와일드카드 LIKE 등)을 스토리지 엔진이 룩업 전에 인덱스 엔트리에서 평가해, 탈락한 행의 룩업을 건너뛴다. 즉 전자는 테이블 접근을 없애고, 후자는 테이블 접근 횟수를 줄인다.

커버링이 성립하면 룩업이 없으니 ICP가 나올 자리가 없고 Using index만 뜬다. 예시: (last_name, first_name) 인덱스에 last_name = 'Kim' AND first_name LIKE '%수%' — SELECT *면 ICP, SELECT id, first_name이면 커버링이라는 대비까지 말한다.

"JPA 엔티티 조회는 SELECT *인데, 그러면 커버링 인덱스를 못 쓰나요?"

엔티티 조회로는 못 쓴다 — 모든 컬럼을 SELECT하므로 어떤 인덱스로도 덮이지 않는다. 방법은 둘이다. ⑴ DTO 프로젝션(인터페이스 프로젝션, select new, QueryDSL Projections)으로 SELECT 목록을 필요한 컬럼만으로 고정한다. ⑵ 행 전체가 정말 필요하면 지연 조인(deferred join) — 커버링 인덱스로 PK만 먼저 뽑고, 살아남은 PK로만 행을 가져온다.

SELECT o.*
FROM orders o
JOIN (SELECT id FROM orders                      -- id(PK)는 세컨더리 리프에 있으므로
      WHERE user_id = 7                          -- (user_id, created_at)만으로 커버링
      ORDER BY created_at DESC
      LIMIT 20 OFFSET 100000) t ON o.id = t.id;  -- 버리는 10만 건에는 룩업이 없고,
                                                 -- 살아남은 20건만 PK로 룩업

깊은 페이지네이션에서 OFFSET이 버리는 행에 대해서도 룩업을 다 하던 비용을 없애는 표준 기법이고, JPA에서는 "PK 목록 조회 → findAllById" 2단계로 같은 효과를 낸다. 가산점 이 기법이 성립하는 근거가 바로 "InnoDB 세컨더리 리프에는 PK가 공짜로 들어 있다"는 §1이다.

"커버링 인덱스는 항상 이득인가요? 만들지 말아야 할 때는 언제죠?" 시니어 변별

아니다. 이득은 절감 룩업 횟수 × 랜덤 I/O 비용 × 호출 빈도 − 인덱스 폭 비용이므로, 앞이 작거나 뒤가 크면 손해다. 만들지 말아야 할 때는 —

  • ⑴ 실을 컬럼이 자주 UPDATE될 때: 실은 순간부터 그 UPDATE마다 세컨더리 엔트리 삭제+삽입이 붙어, 읽기에서 번 것을 쓰기에서 도로 낸다.
  • ⑵ 컬럼이 넓거나 많을 때: 엔트리 비대 → 페이지당 엔트리↓ → 버퍼 풀 적재율↓로 다른 인덱스까지 밀어내고, TEXT/BLOB이나 키 길이 상한에 걸리면 애초에 불가.
  • ⑶ 호출이 드물거나 대상이 1~2건일 때: 절감분이 없다.
  • ⑷ 쿼리 모양이 자주 바뀌는 화면일 때: 컬럼 추가로 조용히 깨지는 취약성을 감당할 안전망(프로젝션 고정 + EXPLAIN 테스트)이 없다면 만들지 않는 게 낫다.

답은 "많이·좁게·자주 읽히고, 거의 안 바뀌는 컬럼만 싣고, 깨짐을 테스트가 잡아주는 조건에서만 만든다"이고, 그 판단 근거를 EXPLAIN 전후 비교와 실제 지연 측정으로 남기는 것까지가 세트다.

"SELECT COUNT(*) FROM orders가 PK가 아니라 엉뚱한 세컨더리 인덱스를 타던데, 왜 그런가요?" 가산점

COUNT(*)는 어떤 컬럼 값도 필요 없어 모든 인덱스가 그 쿼리에 대해 커버링이다. 그러면 남는 기준은 "어느 트리가 가장 좁아서 페이지 수가 적은가"뿐이고, InnoDB는 조건 없는 COUNT(*)를 가장 작은 세컨더리 인덱스를 훑어 처리한다 — 클러스터드 인덱스는 리프가 행 전체라 가장 넓기 때문이다. "커버링 = 필요한 컬럼이 인덱스 안"이라는 정의를 극한(필요한 컬럼이 0개)까지 밀어 이해했다는 뜻이다.

덧붙여 PostgreSQL이라면 같은 Index Only Scan이라도 visibility map이 갱신돼 있어야 힙 방문을 생략하므로, VACUUM 상태에 따라 같은 계획이 빠르기도 느리기도 하다는 점까지 말하면 저장 엔진별 차이를 안다는 신호가 된다.

"나르기용 컬럼 amount를 인덱스 맨 앞에 두면 어떻게 되나요? (amount, user_id, created_at)" 추가

커버링 자체는 성립한다 — 쿼리가 쓰는 세 컬럼이 전부 인덱스 안에 있으니 Using index는 뜬다. 하지만 WHERE user_id = 7이 인덱스 선두 컬럼이 아니라 탐색(ref)에 쓸 수 없고, 정렬 컬럼 created_at도 선두가 아니라 filesort가 붙는다. 결과는 type: index + Using index — 인덱스 전체를 처음부터 끝까지 읽는 인덱스 풀스캔이다. 테이블 풀스캔보다는 싸지만 "좁힌 뒤 커버링"과는 전혀 다르다.

그래서 규칙은 앞은 찾기용(등호 → 범위/정렬), 뒤는 나르기용. Using index만 보고 안심하지 말고 type과 rows를 같이 읽어야 하는 이유이기도 하다.

"인덱스가 (user_id) 하나뿐인데 SELECT id FROM orders WHERE user_id = ?에 Using index가 뜨는 건 왜죠?" 추가

InnoDB 세컨더리 인덱스의 리프 엔트리는 (인덱스 컬럼들, PK)라서, PK 컬럼은 인덱스 정의에 안 써도 모든 세컨더리 리프에 이미 들어 있다. 쿼리가 필요로 하는 것이 user_id(WHERE)와 id(SELECT)뿐이면 둘 다 리프 엔트리 안에 있으므로 클러스터드로 내려갈 이유가 없다 — 커버링이다.

이 "PK 공짜 포함" 성질이 지연 조인(deferred join)의 근거다: 커버링으로 PK 목록만 먼저 뽑고, 살아남은 PK로만 행을 가져온다.

"요즘은 다 SSD인데, 그래도 랜덤 I/O를 신경 써야 하나요?" 추가

차이가 줄어들 뿐 사라지지 않는다. SSD는 HDD의 헤드 이동·회전 대기는 없애지만, 랜덤 I/O가 비싼 세 축 중 두 축은 그대로다 — ⑴ 요청 단위: 랜덤은 여전히 16KB 페이지 1장당 요청 1건이고, 요청마다 커널·드라이버·컨트롤러 경로의 고정 오버헤드가 붙는다. 순차처럼 큰 묶음으로 요청하거나 미리 읽기(read-ahead)를 태울 수 없다. ⑵ 캐시: 랜덤 룩업은 워킹셋을 테이블 전체로 넓혀 버퍼 풀 미스율을 높인다 — 이건 매체와 무관한 메모리 비용이다.

그래서 "SSD니까 랜덤도 괜찮다"는 절반만 맞고, 커버링의 효과는 SSD에서도 유효하다. 다만 HDD 시절의 "수십 배"가 아니라 그보다 줄어든 배수라는 것까지 말하면 정확하다.

"PostgreSQL에서 커버링 인덱스를 만들었는데 Index Only Scan이 안 빨라요. 왜죠?" 가산점추가

PostgreSQL은 힙 테이블이고 MVCC 가시성 정보가 힙 튜플에 있다. 인덱스만 읽어서는 "이 행이 내 트랜잭션에 보이는가"를 알 수 없어, visibility map에 "이 페이지의 튜플은 전부 가시"로 표시된 페이지만 힙 방문을 생략한다. VACUUM이 밀려 visibility map이 갱신되지 않았으면 계획은 Index Only Scan이어도 EXPLAIN ANALYZE의 Heap Fetches가 치솟아 사실상 커버링 효과가 사라진다.

확인은 Heap Fetches 수치, 대응은 VACUUM 상태 점검이다. InnoDB는 세컨더리 리프에서 곧장 답을 내지만 PostgreSQL은 가시성 확인이라는 조건이 하나 더 붙는다 — 저장 엔진별 차이로 묶어 말한다.

한 줄 요약
커버링 인덱스는 쿼리가 쓰는 모든 컬럼이 세컨더리 인덱스 안에 있어 북마크 룩업 — 행마다 PK 순으로 흩어진 페이지를 찌르는 랜덤 I/O — 이 0회가 된 상태이고, 그 랜덤 N장이 좁은 리프 N/수백 장의 순차 읽기로 바뀌는 것이 "몇 배"의 정체다. 효과는 "많이·좁게·자주·세기·정렬" 쿼리에서 크고, 대가는 폭(버퍼 풀 적재율↓)·쓰기(실은 컬럼 UPDATE마다 갱신)·취약(컬럼 추가로 조용히 깨짐)·상한이며, 그 깨짐은 사람의 기억이 아니라 프로젝션 · EXPLAIN 단정 테스트 · 마이그레이션 주석 · rows_examined 알림이 잡게 한다. Using index는 커버링, Using index condition은 룩업을 줄일 뿐인 ICP다.
