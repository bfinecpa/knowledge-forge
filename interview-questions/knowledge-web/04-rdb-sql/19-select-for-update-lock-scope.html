SELECT ... FOR UPDATE의 락 범위
락은 "찾은 행"이 아니라 "스캔한 인덱스 레코드"에 걸린다

면접 질문: "SELECT ... FOR UPDATE는 어떤 락을 잡나요? WHERE 조건이 인덱스를 못 타면 무슨 일이 벌어지나요?"

핵심 관전 포인트 — InnoDB에서 SELECT ... FOR UPDATE는 ① 테이블에 IX(의도 배타) 락, ② 탐색 중 만난 모든 인덱스 레코드에 배타(X) 레코드 락, ③ REPEATABLE READ면 그 레코드 앞의 갭까지 묶은 넥스트 키 락(유니크 인덱스 등호 단건만 예외로 레코드 락만), ④ 세컨더리 인덱스로 찾았으면 대응하는 클러스터드(PK) 레코드까지 잠근다. 원리는 하나다 — InnoDB는 WHERE 조건을 기억하지 않고 어떤 인덱스 범위를 스캔했는지만 알기 때문에, 락은 "조건에 맞아 찾은 행"이 아니라 "찾는 과정에서 스캔한 레코드"에 걸린다. 그래서 WHERE가 인덱스를 못 타면 사슬이 시작된다: 클러스터드 풀스캔(type=ALL) → 전 행 X 락 + RR이면 전 갭 락 → 사실상 테이블 배타 락 → 이 테이블에 쓰는 모든 트랜잭션이 innodb_lock_wait_timeout까지 대기 → 대기마다 커넥션을 쥔 채 멈춤 → 커넥션 풀 고갈 → 무관한 API까지 커넥션 획득 실패 → 전면 장애. 한 건 잠그려다 서비스를 세운다. 그래서 FOR UPDATE는 PK/유니크 등호로만 걸고, 리뷰에서 EXPLAIN 증빙을 요구하며, 락 대기 상한을 3층(DB·JPA·커넥션 풀)으로 걸고, performance_schema.data_locks로 잠긴 레코드 수를 눈으로 확인한다.

rationale의 문장 — "조건이 인덱스를 못 타면 스캔한 행 전부에 락이 걸려 '한 건 잠그려다 테이블을 세우는' 사고가 난다. 락을 '무엇을 잠그는가'가 아니라 '어떻게 찾은 행을 잠그는가'로 이해하는지를 확인한다." 채점 지점은 네 개다.

②실행 계획 결합
락의 폭이 어떤 인덱스를 어떻게 스캔했나에 의해 정해진다는 것을 아는가
③사슬 서술
"느려진다"가 아니라 풀스캔 → 전 행 락 → 쓰기 전원 대기 → 커넥션 고갈이라는 이름 붙은 사슬로 말하는가
④안전망
리뷰·설정·모니터링으로 미리 막는 장치를 갖고 있는가
이 문서가 다루는 축 — 락의 "폭" 비관적 vs 낙관적 락의 선택 기준, "대기 중 붙잡히는 건 스레드가 아니라 커넥션"이라는 대가는 03장의 낙관적 락 vs 비관적 락·동시성 갱신 4가지 비교에서 다뤘다. 여기서는 DB 안에서 락이 몇 개의 레코드에, 어떤 모양으로 걸리는가에 집중한다. 갭 락·넥스트 키 락의 상세와 그것이 만드는 데드락은 갭 락과 데드락 문서의 몫이다.

1. 무엇을 잠그는가 — 락 목록을 통째로 인출한다네 칸을 "줌 인 순서"로 외운다: 테이블 → 레코드 → 레코드 앞 갭 → 옆 트리

잡히는 락 네 칸 — 줌 인 순서로 인출

①IX
테이블 수준 · 의도 배타
"이 테이블 어딘가의 행에 X를 걸 예정"이라는 예고. IX끼리는 호환 → 다른 트랜잭션의 행 락과 충돌 없음. LOCK TABLES ... WRITE 같은 테이블 전체 락과만 충돌. (+ 서버의 MDL이 트랜잭션 끝까지 DDL을 막는다)
②레코드 X
인덱스 레코드 수준 · REC_NOT_GAP
스캔 중 만난 인덱스 레코드마다 배타 락. 다른 트랜잭션의 UPDATE / DELETE / FOR UPDATE / FOR SHARE는 대기. 일반 SELECT는 MVCC 스냅샷이라 안 막힌다.
③넥스트 키
레코드 + 그 "앞" 갭 · RR일 때
REPEATABLE READ면 레코드 락에 앞 갭의 갭 락을 묶는다 → 범위 안 INSERT 차단(phantom 방지). 예외: 유니크 인덱스 + 등호 + 단건은 같은 값이 또 들어올 수 없으니 레코드 락만.
④클러스터드 연쇄
옆 트리 · 세컨더리로 찾았을 때
세컨더리 인덱스 레코드를 잠갔으면 그 PK 값으로 클러스터드 레코드를 찾아가 거기에도 X. 세컨더리 3건 매치 → 클러스터드 3건도 잠긴다.
테이블(IX) → 레코드(X) → 레코드 앞 갭(넥스트 키) → 옆 트리(클러스터드) — 카메라를 줌 인하다 옆 트리로 건너뛴다

1-1. 가장 안전한 형태 — PK 등호 조회는 ②만 남고 ③④가 빈다

-- orders(PK id), REPEATABLE READ(MySQL 기본)
SELECT * FROM orders WHERE id = 42 FOR UPDATE;
①IX
테이블에 의도 배타 락
②X,REC_NOT_GAP
클러스터드 레코드 id=42 하나
③갭 없음
유니크(PK) + 등호 + 단건 → 갭을 잠글 이유가 없다
④연쇄 없음
처음부터 클러스터드를 탐색했으므로

FOR UPDATE를 안전하게 쓰는 기본형이 왜 "PK 등호"인지가 이 네 칸에서 드러난다 — ②만 남고 ③④가 비기 때문이다. 폭 = 1, 갭 = 0.

1-2. 일반형 — 세컨더리(비유니크) 인덱스로 찾으면 네 칸이 다 찬다

-- idx_customer(customer_id): 비유니크 세컨더리 인덱스, REPEATABLE READ
SELECT * FROM orders WHERE customer_id = 7 FOR UPDATE;
①IX
동일
②+③넥스트 키 × 매치 수
idx_customer에서 customer_id=7인 레코드 각각에 레코드 X + 앞 갭, 그리고 마지막 매치 다음 레코드 앞 갭에 갭 락 하나 더. 비유니크라 "7이 또 있을 수 있다"고 보고 범위를 잠근다 → customer_id=7 신규 INSERT 차단
④클러스터드 × 매치 수
매치된 레코드의 PK로 클러스터드 레코드에도 X. 세컨더리 3건 → 클러스터드 3건

1-3. 왜 세컨더리로 찾아도 PK(클러스터드) 레코드까지 잠기나 — 두 트리 연쇄

InnoDB의 락은 "행"에 붙는 게 아니라 인덱스 레코드에 붙는다. 그런데 행의 실체(모든 컬럼)는 클러스터드 인덱스의 리프에만 있고, 세컨더리 리프에는 (인덱스 컬럼 값, PK)만 있다. 세컨더리 레코드만 잠그면 무슨 일이 나는지를 그림으로 본다.

도서관 비유 색인 카드(세컨더리)에만 "대출 중" 스티커를 붙이면, 서가 번호(PK)를 이미 알고 직접 서가로 가는 사람은 못 막는다. 책 자체(클러스터드 레코드)에 붙여야 어떤 경로로 오든 막힌다.
가산점 — 커버링 인덱스여도 적용된다 조회 컬럼이 전부 세컨더리 안에 있어 북마크 룩업이 필요 없는 쿼리라도, FOR UPDATE면 InnoDB는 클러스터드 레코드를 찾아가 잠근다. FOR UPDATE는 "곧 갱신하겠다"는 선언이고 갱신은 클러스터드 레코드에서 일어나기 때문이다. (FOR SHARE는 배타가 아니라 커버링일 때 클러스터드까지 안 갈 수 있다 — "X 락을 걸어야 할 때"라는 단서가 붙는 이유.) 반대 방향도 성립한다: 인덱스 컬럼 값을 바꾸는 UPDATE는 클러스터드뿐 아니라 영향받는 세컨더리 인덱스 레코드도 잠근다.

1-4. 격리 수준이 ③의 모양을 바꾼다 — RR vs RC

같은 FOR UPDATE, 격리 수준에 따라 ③(갭)이 있느냐 없느냐가 갈린다

REPEATABLE READ (MySQL 기본)READ COMMITTED
스캔한 레코드넥스트 키 락 (레코드 + 앞 갭)레코드 락만
조건에 안 맞는 레코드락 유지 (커밋까지)WHERE 평가 후 해제
범위 안 INSERT갭 락으로 차단허용
유니크 인덱스 등호 단건레코드 락만 (예외)레코드 락만

RC에서는 갭 락이 사라지고(외래 키 검사·중복 키 검사 제외), 서버가 WHERE를 평가해 조건에 안 맞는 행의 락을 풀어준다. "RC로 낮추면 락 사고가 줄어든다"는 절반만 맞다 — "안 잠그는 것"이 아니라 "잡았다가 푸는 것"이고, 그 차이가 §2에서 중요해진다.

1-5. 락은 SELECT가 끝나도 안 풀린다 — 커밋까지 (폭 × 기간)

2. 인덱스를 못 타면 — 메커니즘 사슬로 말하기"느려진다"가 아니다. 단계마다 이름과 관측 증거를 붙인다

2-1. 원리 한 문장: InnoDB는 WHERE를 기억하지 않는다

MySQL의 실행 구조를 한 줄로 — 스토리지 엔진(InnoDB)이 인덱스 순서로 레코드를 하나씩 읽어 올리고, SQL 계층이 그 레코드가 WHERE에 맞는지 판정한다. 잠금 읽기에서는 InnoDB가 레코드를 읽어 올리는 그 시점에 락을 건다. 조건에 맞는지는 아직 아무도 모른다. 그리고 InnoDB는 정확한 WHERE 조건을 기억하지 못하고 "어떤 인덱스 범위를 스캔했는가"만 안다. 그래서 락은 그 범위 안의 모든 레코드에 남는다.

검문소 비유 InnoDB는 지나가는 차를 전부 세워 두는 검문 요원이고, WHERE를 판정하는 SQL 계층은 뒤에서 서류를 보는 조사관이다. 요원은 누가 수배자인지 모르니 자기 차선을 지난 차를 전부 세워 둔다(락). 조사관이 "이 차는 아니다"라고 해도 RR에서는 세워 둔 채다. 인덱스는 "이 차선 한 대만 검문하라"는 지시서다 — 지시서가 없으면 전 차선 검문이 된다.

반환 행 ≠ 잠긴 레코드

"한 건만 조회하는 쿼리인데요"는 반환 행 이야기고, 락은 스캔 이야기다. 락은 스캔 시점에, WHERE는 그 뒤에. 이 문장이 이 질문의 전부다.

2-2. 사슬 8단계 — 각 단계에 이름과 관측 증거를 붙인다

비용을 "락이 많이 걸려서 느려진다"로 뭉뚱그리지 않는다. 사슬은 3막이다 — DB 안(①②③) → 경계: 대기(④) → 앱으로 전파(⑤⑥⑦) → 회복(⑧). "DB에서 시작해 커넥션을 타고 앱으로 번진다"로 외운다.

면접에서 한 호흡으로 말할 버전

인덱스 부재→ 풀스캔→ 스캔한 전 레코드에 X (RR이면 갭까지)→ 사실상 테이블 락→ 쓰기 트랜잭션 전원 대기→ 대기마다 커넥션 점유→ 풀 고갈→ 무관한 API로 전파

잠그려던 건 한 행이었다.

2-3. 같은 쿼리, 두 실행 계획, 두 락 개수 — EXPLAIN과 data_locks를 나란히

BEFORE coupon.code에 인덱스가 없다
EXPLAIN SELECT * FROM coupon WHERE code = 'SUMMER-2026' FOR UPDATE;
-- type=ALL | key=NULL | rows=1,203,441        전부 읽겠다는 뜻

-- 이 트랜잭션이 잡은 락 (다른 세션에서)
SELECT index_name, lock_type, lock_mode, lock_status, lock_data
  FROM performance_schema.data_locks
 WHERE engine_transaction_id = <trx_id>;
-- NULL    | TABLE  | IX | GRANTED | NULL
-- PRIMARY | RECORD | X  | GRANTED | 1              X 만 있으면 "넥스트 키 락"
-- PRIMARY | RECORD | X  | GRANTED | 2
-- ...      (행 수만큼 계속)
-- PRIMARY | RECORD | X  | GRANTED | supremum pseudo-record   테이블 끝 갭
AFTER 유니크 인덱스를 걸었다
ALTER TABLE coupon ADD UNIQUE INDEX ux_coupon_code (code);

EXPLAIN SELECT * FROM coupon WHERE code = 'SUMMER-2026' FOR UPDATE;
-- type=const | key=ux_coupon_code | rows=1     딱 하나

SELECT index_name, lock_type, lock_mode, lock_status, lock_data FROM performance_schema.data_locks ...;
-- NULL           | TABLE  | IX            | GRANTED | NULL
-- ux_coupon_code | RECORD | X,REC_NOT_GAP | GRANTED | 'SUMMER-2026', 42   세컨더리 레코드 (갭 없음)
-- PRIMARY        | RECORD | X,REC_NOT_GAP | GRANTED | 42                  ④ 클러스터드 레코드까지

lock_mode 읽는 법 — 이 표를 읽으면 "몇 개를 어떤 모양으로"를 추측이 아니라 관측으로 말한다

X
넥스트 키 락 — 레코드 + 앞 갭
X,REC_NOT_GAP
레코드만
X,GAP
갭만
X,INSERT_INTENTION
INSERT 대기 중

lock_data의 supremum pseudo-record는 테이블 끝의 열린 갭. lock_status는 GRANTED / WAITING.

2-4. 실무 변형 — 인덱스가 "있는데도" 테이블이 잠기는 네 가지

풀스캔 원인 6종이 그대로 FOR UPDATE에 붙는다. 읽기 쿼리에서 "느린 쿼리"로 끝나던 것이 잠금 읽기에서는 "테이블 락"으로 격상된다.

-- (a) 타입 불일치 — code 는 VARCHAR 인데 숫자 리터럴/파라미터를 넘겼다
SELECT * FROM coupon WHERE code = 20260801 FOR UPDATE;
--  → 컬럼 쪽이 숫자로 형변환 → 인덱스 무효 → 풀스캔 → 전체 락
--  JPA 에서 파라미터 타입이 엔티티 필드 타입과 다를 때 조용히 발생한다

-- (b) 컬럼에 함수
SELECT * FROM reservation WHERE DATE(starts_at) = CURDATE() FOR UPDATE;

-- (c) 낮은 선택도 — 옵티마이저가 인덱스를 버린다
SELECT * FROM job WHERE status = 'PENDING' FOR UPDATE;
--  → 인덱스를 타도 PENDING 전부 + 갭, 안 타면 테이블 전부

-- (d) LIMIT 은 반환 행을 제한하지 잠기는 레코드를 제한하지 않는다
SELECT * FROM job WHERE status = 'PENDING' ORDER BY created_at LIMIT 10 FOR UPDATE;
--  → ORDER BY 를 인덱스로 못 풀면 filesort: 조건에 맞는 행을 "전부" 읽어 정렬한 뒤 10건을 자른다
--  → 읽은 전부가 잠긴다. (status, created_at) 인덱스가 있어야 10건에서 스캔이 멈춘다
(d)가 특히 뼈아프다 — 배치 워커의 LIMIT n FOR UPDATE "10건만 가져오니 락도 10개겠지"는 반환 행과 스캔 행을 혼동한 것이다. 큐 테이블 전체를 잠그는 사고의 정체가 이것이다. LIMIT은 스캔이 멈추는 지점을 정하지 않는다 — 인덱스가 정한다.

2-5. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

뭉뚱그린 표현이름사슬로 말하면
"락이 많이 걸려서 느려진다"스캔 = 잠금인덱스 부재 → 풀스캔 → 스캔한 전 레코드에 X 락(+갭) → 사실상 테이블 락
"DB가 멈춘다"커넥션 풀 고갈쓰기 트랜잭션 전원 대기 → 대기마다 커넥션 점유 → 풀 소진 → 무관 API 전파
"한 건만 잠그는 쿼리인데요"반환 행 ≠ 잠긴 레코드락은 스캔 시점에, WHERE는 그 뒤에 서버가 평가 → 조건도 LIMIT도 락 수를 안 줄인다
"인덱스 있으니 괜찮다"실행 계획이 폭을 정한다함수·타입 불일치·낮은 선택도로 인덱스를 못 타면 읽기 쿼리의 "느림"이 잠금 읽기의 "테이블 락"으로 격상

3. 트레이드오프 — 비관적 락의 대가와 선택 기준폭 · 기간 · 자원, 그리고 NOWAIT / SKIP LOCKED

3-1. FOR UPDATE가 지불하는 것 — 세 축, 누가 정하나

폭 — 몇 개의 레코드를
정하는 것: 실행 계획
쿼리를 쓴 사람의 의도가 아니라 옵티마이저가 고른 접근 경로가 정한다. 이 문서의 주제.
기간 — 얼마나 오래
정하는 것: 트랜잭션 경계
커밋까지. 락 구간 안의 왕복·계산·외부 호출이 그대로 남의 대기 시간.
자원 — 기다리며 무엇을 붙잡나
상한: 커넥션 풀 크기
대기자는 스레드가 아니라 커넥션을 붙잡는다.

비관적 락을 "간단하고 확실하다"고 고를 때 치르는 값은 이 셋의 곱이다. 폭이 1이면 기간과 자원만 관리하면 되지만, 폭이 테이블 전체가 되는 순간 나머지 둘이 아무리 잘 관리돼도 사고다. 그래서 선택의 첫 관문은 "충돌이 잦은가"가 아니라 "잠글 행을 PK/유니크 등호로 특정할 수 있는가"다.

예

아니오
먼저 인덱스를 만들거나 "조회 → PK로 잠금" 2단계로 바꾼다(§4-1 B). 그래도 안 되면 비관적 락은 후보에서 뺀다. 주의: 원자적 UPDATE도 잠금 읽기라 같은 폭 문제를 갖는다.

3-3. NOWAIT vs SKIP LOCKED — 용도·대가 대칭 표

-- NOWAIT: 이미 잠겨 있으면 대기하지 않고 즉시 에러 (MySQL 8.0+, PostgreSQL)
SELECT * FROM seat WHERE id = 1042 FOR UPDATE NOWAIT;
-- ERROR 3572: Statement aborted because lock(s) could not be acquired immediately and NOWAIT is set.

-- SKIP LOCKED: 다른 트랜잭션이 잠근 행은 건너뛰고, 안 잠긴 10건만 잠가서 가져온다
SELECT id, payload FROM job
 WHERE status = 'PENDING'
 ORDER BY id
 LIMIT 10
   FOR UPDATE SKIP LOCKED;
FOR UPDATE (기본)FOR UPDATE NOWAITFOR UPDATE SKIP LOCKED
잠긴 행을 만나면대기 (타임아웃까지)즉시 실패건너뜀
한 마디"기다린다""기다리느니 실패""잠긴 건 남의 것, 다음 것"
용도단건 정합성 갱신, 락 안에서 복잡한 로직사용자 대면 선점(좌석·쿠폰·예약 버튼) — "기다리는 것"이 "실패 응답"보다 나쁠 때. 사용자는 다시 누르면 된다워커 N개가 같은 테이블에서 서로 다른 행을 나눠 가져갈 때 — 작업 큐, 아웃박스 릴레이, 배치 분산. 표준 해법
얻는 것재시도 없음대기열이 아예 안 생긴다 → 대기자 쪽 커넥션 보호에 가장 강력 (사슬 ④⑤⑥을 대기자 입장에서 절단)워커들이 같은 행에서 줄 서지 않는다. 없으면 N개 워커 전원이 맨 앞 10건에서 직렬화되고, 뒤 워커는 이미 처리된 행을 잡아 "할 일 없음"
대가커넥션 점유 대기열, 폭 사고 위험① 실패 처리를 앱이 반드시(에러 매핑·메시지·재시도 정책) ② 자동 재시도하면 재시도 폭풍으로 모양만 바뀜 ③ 가해자의 폭은 못 고침 — 피해자를 빨리 죽일 뿐① 결과 비결정 — "몇 건 남았나"·"존재하나" 같은 정합성 판단에 쓰면 안 됨 ② 순서·공정성은 최선 노력 ③ 가져온 행은 커밋까지 잠김 → PROCESSING으로 바꾸고 바로 커밋, 처리는 밖에서
폭 문제그대로그대로그대로 — (status, id) 인덱스 없이 filesort면 "안 잠긴 PENDING 전부"를 읽고 잠근 뒤 10건을 자른다
JPA@Lock(PESSIMISTIC_WRITE)힌트 jakarta.persistence.lock.timeout = 0 → MySQL 8 방언에서 NOWAIT. 실패 시 LockTimeoutException(Spring: CannotAcquireLockException 계열)네이티브 쿼리에 직접 쓰는 것이 가장 확실. 힌트 -2(LockOptions.SKIP_LOCKED)도 번역되지만 생성 SQL 확인이 전제
둘 다 "대기 정책"이지 "폭 처방"이 아니다 풀스캔 FOR UPDATE가 테이블을 잡고 있으면 NOWAIT 쿼리는 전부 즉시 실패할 뿐이고, SKIP LOCKED는 건너뛸 행이 없다. 방언마다 지원이 달라 생성 SQL을 로그로 확인하고 쓴다.
BEFORE 워커 5개가 전부 같은 10건에서 줄을 선다 — 인덱스도 없어 큐 테이블 전체가 잠긴다
@Lock(LockModeType.PESSIMISTIC_WRITE)
List<Job> findTop10ByStatusOrderByCreatedAt(JobStatus status);   파생 쿼리 — SQL이 안 보인다 · filesort · 대기 직렬화
AFTER 잠긴 건 건너뛰고, 인덱스로 10건에서 스캔을 멈추고, 상태만 바꾸고 바로 커밋
@Query(value = """
        SELECT * FROM job
         WHERE status = 'PENDING'
         ORDER BY id
         LIMIT :n
           FOR UPDATE SKIP LOCKED
        """, nativeQuery = true)
List<Job> claimPending(@Param("n") int n);       인덱스 (status, id) 필수

@Transactional

3-5. 한 장으로 정리 — 다섯 도구

도구잠긴 행을 만나면어울리는 상황지불하는 것
FOR UPDATE대기 (타임아웃까지)단건 정합성 갱신, 락 안에서 복잡한 로직커넥션 점유 대기열, 폭 사고 위험
FOR UPDATE NOWAIT즉시 실패사용자 대면 선점실패 처리·재시도 설계, 가해자는 못 고침
FOR UPDATE SKIP LOCKED건너뜀워커 간 작업 분배결과 비결정성, 정합성 판단 불가
원자적 UPDATE대기읽기-계산-쓰기가 한 문장으로 압축될 때폭 규칙은 동일, 영속성 컨텍스트 우회 (03)
낙관적 락(읽을 때 안 잠금)충돌이 드물 때재시도 코드, 실패 노출 (03)

선택의 순서 — 폭 → 기간 → 대기 정책

① 폭을 먼저 1로 (PK/유니크 등호)→ ② 기간을 줄이고 (락 안 왕복·외부 호출 제거)→ ③ 마지막에 대기 정책 (대기 / NOWAIT / SKIP LOCKED)

"1로 만들고, 줄이고, 고른다."

4. JPA before / after와 안전망사람의 기억에 맡기지 않는다 — 코드 구조·리뷰 템플릿·설정·테스트로 고정

4-1. before / after

BEFORE 파생 쿼리 + 비관적 락 — 세 가지 문제
public interface CouponRepository extends JpaRepository<Coupon, Long> {

    // 나가는 SQL: select ... from coupon c where c.code=? for update
    @Lock(LockModeType.PESSIMISTIC_WRITE)   문제 3: 락 대기 상한 없음 → 기본 50초 동안 커넥션을 쥔다
    Optional<Coupon> findByCode(String code);   문제 1: code에 인덱스 없음 → 풀스캔 → 테이블 + 모든 갭 잠금
}   문제 2: 파생 쿼리라 SQL이 코드에 안 보인다 → 리뷰어가 "findByCode니까 한 건이겠지" 하고 지나간다

@Transactional
public void redeem(String code, Long userId) {
    Coupon coupon = couponRepository.findByCode(code).orElseThrow();   여기서 테이블이 선다
    coupon.redeem(userId);
}
AFTER (A) 유니크 인덱스 + 명시적 쿼리 + 대기 상한
@Entity
@Table(name = "coupon",
       indexes = @Index(name = "ux_coupon_code", columnList = "code", unique = true))
public class Coupon { ... }
// 운영 DB의 인덱스는 @Index가 아니라 마이그레이션(Flyway 등)으로 만든다. @Index는 의도를 코드에 남기는 문서 역할

public interface CouponRepository extends JpaRepository<Coupon, Long> {

    // 유니크 인덱스 등호 → EXPLAIN type=const → 레코드 락 1(세컨더리) + 클러스터드 1, 갭 없음
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))   대기 상한 (방언별 번역 확인 — §4-3)
    @Query("select c from Coupon c where c.code = :code")   SQL이 코드에 보인다 → 리뷰 가능한 락
    Optional<Coupon> findByCodeForUpdate(@Param("code") String code);
}
AFTER (B) "락은 항상 PK로만 건다" 규칙으로 폭 사고를 원천 차단
@Transactional
public void redeem(String code, Long userId) {
    // 1) 락 없는 일반 조회로 PK만 얻는다 — 인덱스가 없어도 느릴 뿐, 남을 세우지 않는다(MVCC)
    Long couponId = couponRepository.findIdByCode(code).orElseThrow();

    // 2) PK로 잠근다 — select ... where id=? for update. 실행 계획이 const로 "고정"된다
    Coupon coupon = em.find(Coupon.class, couponId, LockModeType.PESSIMISTIC_WRITE);   폭 = 1 이 코드 구조에 고정

    // 3) 잠근 뒤 조건을 다시 검증한다 — 1)과 2) 사이에 다른 트랜잭션이 바꿨을 수 있다
    if (coupon.isRedeemed()) throw new AlreadyRedeemedException(code);   재검증 습관
    coupon.redeem(userId);
}
(B)의 가치 누가 나중에 인덱스를 지우거나 조건을 바꿔도 락의 폭이 1로 유지된다. 폭이 코드 구조에 고정되므로 리뷰어의 기억에 의존하지 않는다. 대가는 왕복 1회 추가와 3)의 재검증 습관이다.

4-2. 코드 리뷰 체크리스트 — FOR UPDATE / @Lock(PESSIMISTIC_WRITE)가 보이면

  • 1. WHERE 컬럼에 PK 또는 유니크 인덱스가 있는가? 비유니크 인덱스면 넥스트 키 락이 잡는 범위(매치 행 + 갭)를 계산해 봤는가?
  • 2. PR에 EXPLAIN 결과가 첨부돼 있는가? 핵심 type = const / eq_ref / ref / range, key ≠ NULL, rows가 의도한 자릿수. 파생 쿼리·@Lock이면 먼저 생성 SQL을 확보한다(p6spy / show_sql) — "SQL이 안 보이는 락"은 리뷰가 불가능한 락이다
  • 3. 파라미터 타입 = 컬럼 타입인가? (암묵적 형변환) 컬럼에 함수·연산이 없는가?
  • 4. 락 보유 구간(FOR UPDATE ~ 커밋)에 외부 호출·긴 계산·불필요한 왕복이 없는가? (기간)
  • 5. 락 대기 상한과 실패 시 동작이 정해져 있는가? (대기 n초 / NOWAIT / SKIP LOCKED, 예외 매핑)
  • 6. 락 범위 회귀 테스트가 있는가? (§4-5)

2번이 핵심이다. FOR UPDATE가 붙은 쿼리는 EXPLAIN 없이 머지하지 않는다를 팀 규칙으로 두면 사고의 절대다수(인덱스 없음·형변환·선택도)가 리뷰 단계에서 걸린다. 이 규칙은 기억이 아니라 PR 템플릿의 체크박스로 고정한다.

4-3. 락 대기 타임아웃 — 세 층으로 상한을 건다

기본값으로 두면 §2 사슬의 ④⑤⑥이 50초 + 30초 동안 진행된다. 상한을 세 층에 걸고, 안쪽 층이 바깥 층보다 짧게 맞춘다.

4-5. 테스트로 고정 — 락 범위 회귀 테스트

"이 FOR UPDATE는 한 행만 잠근다"를 테스트로 박아 두면, 누가 인덱스를 지우거나 조건을 바꿔 폭이 넓어지는 순간 CI가 잡는다. 두 커넥션을 직접 쓴다 — @Transactional 테스트 안에서는 두 트랜잭션이 재현되지 않는다. 그리고 H2가 아니라 Testcontainers로 운영과 같은 MySQL을 띄운다. 락 모양은 엔진마다 다르다.

@Test
void forUpdate_on_code_locks_only_that_row() throws Exception {
    try (Connection holder = dataSource.getConnection();
         Connection other  = dataSource.getConnection()) {

        holder.setAutoCommit(false);
        try (var ps = holder.prepareStatement(
                "select id from coupon where code = ? for update")) {
            ps.setString(1, "SUMMER-2026");
            ps.executeQuery();                              락을 쥔 채 커밋하지 않는다
        }

        other.setAutoCommit(false);
        other.createStatement().execute("set session innodb_lock_wait_timeout = 1");

        // 다른 행의 갱신은 막히면 안 된다 — 막히면 폭이 1이 아니라는 뜻
        assertDoesNotThrow(() -> other.createStatement()
                .executeUpdate("update coupon set redeemed = redeemed where code = 'WINTER-2026'"));

        // 새 행의 INSERT 도 막히면 안 된다 — 막히면 갭/supremum 까지 잠겼다는 뜻
        assertDoesNotThrow(() -> other.createStatement()
                .executeUpdate("insert into coupon(code, redeemed) values ('TEST-NEW', false)"));

        other.rollback();
        holder.rollback();
    }
}
빨간 불로 지켜지는 규칙 인덱스가 사라지면 첫 번째 assertDoesNotThrow에서 Lock wait timeout exceeded로 실패한다. "PK/유니크로만 잠근다"는 규칙이 사람의 리뷰가 아니라 CI의 빨간 불로 지켜진다.

5. 꼬리질문 셀프 테스트질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다

"READ COMMITTED로 낮추면 이 문제가 해결되나요?"힌트: "안 잠그는 것"과 "잡았다가 푸는 것"의 차이

완화되지만 해결은 아니다. RC에서는 ① 갭 락이 사라져 INSERT는 막히지 않고 ② 서버가 WHERE를 평가한 뒤 조건에 안 맞는 행의 락을 풀어주므로 유지되는 락은 매치된 행으로 줄어든다. 그러나 ③ 풀스캔 자체의 비용(수백만 행 읽기)은 그대로고 ④ 스캔 중 각 행을 잠갔다가 푸는 것이므로, 다른 트랜잭션이 잡고 있는 행을 만나면 그 자리에서 대기한다(UPDATE는 세미 컨시스턴트 읽기로 이 대기를 피하지만 SELECT ... FOR UPDATE는 아니다) ⑤ 격리 수준은 세션·전역 설정이라 이 쿼리 하나를 위해 바꾸면 다른 모든 쿼리의 phantom 동작과 바이너리 로그 형식(ROW 필수)까지 바뀐다.

처방은 인덱스이고, RC는 기껏해야 응급 완화책이다. "격리 수준은 광역 설정, 폭 문제는 국소 수정".

"세컨더리 인덱스로 찾았는데 왜 PK 레코드까지 잠기나요? 커버링 인덱스면 안 잠기나요?"힌트: 모든 경로의 종착지

락은 행이 아니라 인덱스 레코드에 붙고, 행의 실체는 클러스터드 리프에만 있다. 세컨더리 레코드만 잠그면 PK로 직접 오는 UPDATE ... WHERE id = ?가 그 행을 그냥 고친다 — 락이 뚫린다. 모든 접근 경로가 마지막에 통과하는 지점이 클러스터드 레코드이므로 그것을 잠가야 "이 행은 잠겼다"가 경로와 무관하게 성립한다.

커버링 인덱스여도 FOR UPDATE면 클러스터드까지 잠근다 — 북마크 룩업이 필요 없는 건 "읽기" 이야기고, FOR UPDATE는 갱신 의도의 선언이며 갱신은 클러스터드 레코드에서 일어나기 때문이다. (FOR SHARE는 배타가 아니라 커버링일 때 클러스터드까지 안 갈 수 있다 — "X 락을 걸어야 할 때"라는 단서가 정확한 표현이다.)

"락이 걸려 있는 동안 다른 트랜잭션의 일반 SELECT는 왜 안 막히나요? 그럼 그 값을 믿어도 되나요?"힌트: 용도가 갈린다 — 표시 vs 결정

일반 SELECT는 잠금 읽기가 아니라 MVCC 스냅샷 읽기라 락 큐에 서지 않는다. 그래서 풀스캔 FOR UPDATE 장애의 증상이 "조회는 되는데 저장이 안 된다"로 나타난다.

그 값을 믿어도 되는 용도와 안 되는 용도가 갈린다 — 화면 표시, 통계, 목록에는 충분하다. 그러나 "읽은 값을 근거로 쓰기를 결정"하는 로직(재고 확인 후 차감, 쿠폰 상태 확인 후 사용)에는 안 된다. 읽는 순간 이미 남이 잠그고 바꾸는 중일 수 있고, 내 스냅샷은 그걸 모른다. 결정에 쓰이는 읽기는 잠금 읽기(FOR UPDATE)이거나 읽기-결정-쓰기를 한 문장으로 압축한 원자적 UPDATE여야 한다. 03 문서의 "check-then-act 틈"이 DB 레벨에서 같은 얼굴로 나타난 것.

"PostgreSQL에서도 같은 사고가 나나요?" 시니어 변별힌트: 엔진의 구현을 먼저 묻고 결론을 낸다

같은 모양으로는 안 난다. PostgreSQL의 FOR UPDATE는 실행 계획에서 스캔 위에 LockRows 노드가 올라가고, WHERE를 통과한 행만 잠근다(잠근 뒤 그 사이 바뀌었으면 조건을 재평가한다). 갭 락도 없다. 따라서 "인덱스 없는 FOR UPDATE 한 건 → 테이블 전체 락"이라는 InnoDB식 사고는 나지 않는다.

대신 다른 비용이 있다 — PostgreSQL의 행 락은 메모리 락 테이블이 아니라 튜플 헤더(xmax)에 기록되므로, 많은 행을 잠그면 그만큼 페이지가 더러워지고 WAL이 쓰인다. 그리고 풀스캔 비용, 커밋까지의 락 보유 기간, 대기자가 커넥션을 붙잡는 구조는 완전히 동일하다. 결론: "함정의 모양은 엔진마다 다르지만, 규율(PK/유니크로 잠근다 · 짧게 쥔다 · 대기 상한을 건다)은 엔진과 무관하다."

"SELECT FOR UPDATE 대신 UPDATE ... WHERE code = ?로 바로 치면 이 문제가 없어지나요?" 시니어 변별힌트: 폭은 문장의 종류가 정하지 않는다

없어지지 않는다. UPDATE와 DELETE도 잠금 읽기다 — 스캔한 인덱스 레코드에 X 락(RR이면 넥스트 키)을 거는 규칙이 똑같이 적용된다. UPDATE coupon SET ... WHERE code = ?에 인덱스가 없으면 역시 클러스터드 풀스캔 + 전 행 락이다.

원자적 UPDATE가 FOR UPDATE보다 나은 것은 폭이 아니라 기간(왕복 1회로 락 구간이 끝난다)이고, RC에서 조건 불일치 행의 락을 풀어주는 완화도 양쪽에 같이 적용된다. 폭은 문장의 종류가 아니라 접근 경로(실행 계획)가 정한다 — 이 한 문장이 채점 포인트다. 그러니 UPDATE ... WHERE status = 'PENDING' 같은 배치 갱신도 인덱스와 청크 분할 없이 날리면 같은 사고다.

"운영 중 '락 대기' 알림이 왔습니다. 어디부터 보나요?" 가산점힌트: 가해자 → 폭 → 실행 계획 → 즉시 조치 → 근본 조치 → 재발 방지
① sys.innodb_lock_waits→ ② INNODB_TRX.trx_rows_locked→ ③ EXPLAIN→ ④ KILL 가해→ ⑤ 인덱스 / 구조 배포→ ⑥ 체크리스트 + 테스트

① sys.innodb_lock_waits로 가해자(blocking_trx_id, blocking_query)와 대기 시간(wait_age)을 본다 — 대기자 수십 건에 가해자가 한 건이면 폭 사고 의심. ② information_schema.INNODB_TRX에서 그 트랜잭션의 trx_rows_locked — 테이블 행 수에 가까우면 확정. ③ 그 쿼리를 EXPLAIN — type=ALL이면 원인은 인덱스. ④ 즉시 조치는 가해 트랜잭션 KILL(대기열이 풀린다) + 커넥션 풀 회복 확인. ⑤ 근본 조치는 인덱스 추가 또는 "조회 → PK 잠금" 구조 변경 배포. ⑥ 재발 방지는 §4-2 체크리스트와 §4-5 테스트 추가.

"느려요"에서 시작해 EXPLAIN까지 가는 이 단계를 이름으로 말할 수 있으면 장애를 겪어 본 사람으로 읽힌다.

"LIMIT 1 FOR UPDATE면 락도 1개인가요?" 함정추가힌트: 스캔이 어디서 멈추는지는 누가 정하나

아니다. LIMIT은 반환 행을 제한하지 스캔을 제한하지 않는다. 락은 스캔 시점에 걸리므로 "스캔이 1건에서 멈추느냐"가 관건인데, 그것은 LIMIT이 아니라 인덱스가 WHERE와 ORDER BY를 함께 풀어주느냐가 정한다. 인덱스 순서대로 읽어 첫 매치에서 멈출 수 있으면 락은 1개 근처지만, ORDER BY를 인덱스로 못 풀어 filesort가 되면 조건에 맞는 행을 전부 읽어(=전부 잠가) 정렬한 뒤 1건을 자른다.

그래서 배치 워커의 LIMIT n FOR UPDATE에는 (status, id)처럼 조건 + 정렬을 한 번에 커버하는 인덱스가 전제이고, SKIP LOCKED를 붙여도 이 전제는 사라지지 않는다.

"AUTO_INCREMENT로 테이블 끝에 INSERT하는 건 기존 행과 무관한데 왜 막히나요?" 추가힌트: 마지막 레코드 다음의 갭

RR에서 풀스캔은 마지막 실제 레코드를 지나 supremum(테이블 끝 가상 레코드)까지 읽고, 그 앞 갭 — 즉 "마지막 행 이후의 모든 값" — 에 갭 락을 남긴다. AUTO_INCREMENT로 새 행을 붙이는 INSERT는 정확히 이 갭에 들어가야 하므로 X,INSERT_INTENTION 락을 요청한 채 대기한다. data_locks에 lock_data = supremum pseudo-record인 X 락이 보이면 이 상태다.

이것이 "조회는 되는데 저장도 안 되고 신규 생성도 안 된다"는 증상의 두 번째 절반이다. 앞 절반(UPDATE/DELETE 대기)은 레코드 락, 뒤 절반(INSERT 대기)은 갭·supremum 락.

"락 대기 타임아웃이 나면 트랜잭션이 자동으로 롤백되나요?" 가산점추가힌트: 문장 실패와 트랜잭션 실패는 다르다

기본 설정에서는 그 문장만 실패하고 트랜잭션은 살아 있다. 즉 그 트랜잭션이 이전 문장에서 잡아 둔 락은 그대로 쥔 채다. 애플리케이션이 예외를 받고 롤백(또는 재시도)을 결정해야 하며, Spring의 @Transactional은 런타임 예외가 전파되면 롤백하지만 예외를 삼키면 락을 쥔 트랜잭션이 남는다. (innodb_rollback_on_timeout=ON이면 문장이 아니라 트랜잭션 전체를 롤백한다.)

이것이 §4-3에서 "초과 시 그 문장만 실패한다"고 단서를 단 이유이고, 데드락(ERROR 1213, InnoDB가 즉시 감지해 한쪽 트랜잭션을 롤백)과 락 대기 타임아웃(ERROR 1205, 한 방향 대기가 상한을 넘김)이 다르게 처리되는 지점이다. 폭 사고는 데드락이 아니라 가해 1 : 대기 N의 타임아웃 폭주다.

"FOR SHARE(공유 락)면 안전한가요?" 추가힌트: 폭 규칙은 락 모드와 무관

폭 규칙은 같다. FOR SHARE도 잠금 읽기라 스캔한 인덱스 레코드에 S 락(RR이면 넥스트 키)을 건다. 인덱스를 못 타면 전 행에 S 락이다. S끼리는 호환이라 읽기끼리는 안 막히지만, X가 필요한 UPDATE/DELETE/FOR UPDATE는 전부 대기한다 → "쓰기 전원 대기 → 커넥션 점유 → 풀 고갈" 사슬은 그대로 시작된다.

차이는 두 가지뿐이다: 읽기끼리 안 막히는 것, 그리고 커버링 인덱스일 때 클러스터드까지 안 갈 수 있는 것. "락 모드가 약하니 폭도 좁겠지"는 축을 혼동한 것이다 — 모드는 누구와 충돌하나, 폭은 몇 개를 잠그나.

한 줄 요약
SELECT ... FOR UPDATE는 InnoDB에서 테이블 IX 락 + 스캔한 모든 인덱스 레코드에 X 락(RR이면 갭까지 넥스트 키, 유니크 등호 단건만 예외) + 세컨더리로 찾았으면 클러스터드 레코드까지 잠그며, 락은 "찾은 행"이 아니라 "스캔한 레코드"에 걸린다. 그래서 WHERE가 인덱스를 못 타면 풀스캔 → 전 행 락 → 사실상 테이블 락 → 쓰기 전원 대기 → 커넥션 점유 → 풀 고갈 → 무관 API 전파로 한 건 잠그려다 서비스를 세운다. 처방은 폭을 1로 만드는 것(PK/유니크 등호, 또는 조회 후 PK 잠금)이고, 그것을 EXPLAIN 증빙 · 락 대기 상한 3층 · data_locks 관측 · 락 범위 회귀 테스트로 사람의 기억 밖에 고정한다.
