SELECT ... FOR UPDATE의 락 범위와 모드
"스캔한 행"이 아니라 "WHERE를 통과해 반환된 행"만 잠근다

면접 질문: "SELECT ... FOR UPDATE는 어떤 락을 잡나요? WHERE 조건이 인덱스를 못 타면 무슨 일이 벌어지나요?"

핵심 관전 포인트 — PostgreSQL에서 SELECT ... FOR UPDATE가 잡는 것은 네 칸의 목록으로 말할 수 있다. ① 테이블에 ROW SHARE 락(DDL 계열과만 충돌), ② WHERE를 통과해 반환된 행에만 행 락 — 실행 계획에서 스캔 노드 위에 LockRows 노드가 서고, 락은 별도 락 테이블이 아니라 튜플 헤더 xmax에 기록된다, ③ 갭 락·넥스트 키 락은 없다, ④ 인덱스 엔트리는 잠그지 않는다(힙 튜플 하나가 정본). 그래서 WHERE가 인덱스를 못 타면 MySQL과 정반대 방향의 일이 벌어진다 — 스캔한 행이 전부 잠기는 게 아니라 Seq Scan으로 느려질 뿐, 조건 미충족 행은 하나도 안 잠긴다. 대신 위험은 다른 데 있다: 잠근 채 스캔이 끝날 때까지 락 보유 기간이 늘어 같은 행을 노리는 트랜잭션이 그 구간에 직렬화되고(커넥션 고갈은 이 경로로 온다), 스캔 순서가 세션마다 달라져 락 획득 순서가 어긋나면 데드락 확률이 오르며, READ COMMITTED의 재평가(EvalPlanQual)로 후보 행마다 대기가 생기고, 조인이면 모든 테이블의 행이 잠기며, FOR UPDATE는 네 모드 중 최강이라 FK 검사의 KEY SHARE와 충돌해 자식 INSERT를 막고(잔액 갱신 같은 비키 갱신은 FOR NO KEY UPDATE), 존재하지 않는 행은 못 잠근다. 처방은 폭(등호 조건) → 기간(인덱스, 락 안 왕복 제거) → 강도(NO KEY UPDATE) → 대기 정책(lock_timeout / NOWAIT / SKIP LOCKED) 순이고, 리뷰에서 EXPLAIN (ANALYZE, BUFFERS)의 LockRows 행 수와 Buffers를 증빙으로 요구한다.
  • 1
    잠기는 자리를 네 칸 목록으로 말한다 — 테이블에 ROW SHARE(DDL과만 충돌), WHERE를 통과해 반환된 힙 튜플의 xmax에 행 락, 갭 락 없음, 인덱스 엔트리 락 없음. 한 문장으로 압축하면 "반환 행 = 잠긴 행"이고, 그 근거는 실행 계획에서 LockRows가 Filter 뒤에 선다는 사실이다.
  • 2
    그래서 인덱스를 못 타도 폭은 늘지 않는다 — 대신 기간이 는다 — Seq Scan이어도 잠기는 건 매치된 1행뿐이고 무관한 행·새 INSERT는 자유다. 늘어나는 것은 그 한 건을 잡은 채 스캔이 끝날 때까지의 시간이라 같은 행 경쟁이 그 구간에 직렬화되고 커넥션을 붙잡는다. 폭 사고가 아니라 기간 사고이며, 폭은 조건이 정하고 기간은 실행 계획이 정한다.
  • 3
    PG에는 축이 하나 더 있다 — 강도 — 행 락은 4종이고 FOR UPDATE는 그중 최강이라 FK 검사의 FOR KEY SHARE와 충돌해 자식 테이블 INSERT까지 막는다. 키를 안 바꾸면 FOR NO KEY UPDATE가 업무 락의 기본형이다. 처방 순서는 폭 → 기간 → 강도 → 대기 정책이고 증빙은 EXPLAIN의 LockRows·Buffers다.

0. 질문 + 출제 의도

질문: "SELECT ... FOR UPDATE는 어떤 락을 잡나요? WHERE 조건이 인덱스를 못 타면 무슨 일이 벌어지나요?"

출제 의도: 락을 "무엇을 잠그는가"가 아니라 "어떻게 찾은 행을 잠그는가"로 이해하는지 — 실행 계획과 락이 결합되는 한 단계 깊은 이해를 확인하는 질문이다. 출제자가 기대하는 모범 답안은 InnoDB 전제다: "조건이 인덱스를 못 타면 스캔한 행 전부에 락이 걸려 한 건 잠그려다 테이블을 세우는 사고가 난다."

그런데 PostgreSQL로 답하면 결론이 뒤집힌다 PG는 스캔한 행이 아니라 반환된 행만 잠그므로 "테이블을 세우는" 사고는 그 모양으로는 나지 않는다. 여기서 갈리는 것이 이 문서의 전부다 — 같은 처방(인덱스), 다른 이유. 면접관이 MySQL을 전제로 물었다면 "PG는 반대 방향이고, MySQL이라면 이렇다"를 함께 말하는 것이 가장 높은 답이다.
PG 사용자의 채점 지점 네 개 ① 잡히는 락의 종류와 기록 위치(ROW SHARE + 튜플 xmax, 행 락 4종 모드)를 목록으로 꺼낼 수 있는가 (1·2·3절)
② LockRows가 Filter 뒤에 선다는 실행 구조에서 "반환 행 = 잠긴 행"을 도출하는가 (4절)
③ "그럼 인덱스 없어도 괜찮다"로 끝내지 않고 기간 · 재평가 · 조인 · FK KEY SHARE · 부재 행이라는 PG 고유 위험 다섯을 이름 붙여 말하는가 (5·6절)
④ 그것을 리뷰 · 설정 · 관측 · 테스트로 미리 막는 안전망을 갖고 있는가 (8·9절)
이 문서가 다루는 범위 비관적 락 vs 낙관적 락의 선택 기준과 "대기 중 붙잡히는 건 스레드가 아니라 커넥션"이라는 대가는 03장(낙관적 락 vs 비관적 락 · 동시성 갱신 4가지 비교)이, 갭 락 없는 PG의 팬텀·데드락 유형은 12 문서가, 락 점유 시간 자체는 16 문서가 본론이다. 여기서는 DB 안에서 락이 몇 개의 행에(폭), 어떤 모양과 강도로(모드) 걸리는가에 집중한다.

1. 무엇을 잠그는가 — 네 칸 목록을 통째로 인출한다

1-1. 전제 — 이 문장이 존재하는 이유

두 요청이 같은 행을 읽고 → 계산하고 → 쓰는 순서로 처리하면 한쪽의 갱신이 통째로 사라질 수 있다. 쿠폰 잔여 수량이 1인데 A와 B가 동시에 "1이네" 하고 읽어 둘 다 0으로 쓰면, 쿠폰은 두 번 쓰였는데 수량은 한 번만 줄어든다. 이렇게 나중 쓰기가 앞 쓰기를 덮어써서 갱신이 없어지는 현상을 lost update(갱신 유실)라 부른다.

낙관적 락 — 쓸 때 확인한다

일단 읽고 계산한 뒤 쓸 때 "내가 읽은 그 버전이 아직 그대로인가"를 확인하고, 아니면 실패시켜 재시도하게 한다. 읽는 동안 아무것도 잠그지 않는다.

비관적 락 — 읽을 때 표시한다

읽는 순간 그 행에 미리 표시를 남겨 다른 트랜잭션이 손대지 못하게 한다. SELECT ... FOR UPDATE가 이쪽이고, 이렇게 읽으면서 동시에 락을 남기는 SELECT를 잠금 읽기(locking read)라 부른다.

회의실 비유 — 팻말은 어느 문에, 몇 개나 걸리는가 일반 SELECT는 복도에서 회의실 안을 들여다보는 것이다. 누가 있든 없든 내가 본 순간의 모습을 기억할 뿐 아무 흔적도 남기지 않는다(MVCC 스냅샷 읽기). FOR UPDATE는 들여다본 뒤 문에 "사용 예정" 팻말을 거는 것이다. 팻말을 본 사람은 내가 뗄 때까지 기다리고, 팻말은 회의가 끝날 때 = 트랜잭션이 커밋될 때 떼어진다. 이 문서의 질문은 결국 하나다 — 팻말이 정확히 어느 문에, 몇 개나 걸리는가.

1-2. 기본형 — PK 등호 조회가 잡는 것

기준 쿼리 orders(PK id), READ COMMITTED(PostgreSQL 기본)
SELECT * FROM orders WHERE id = 42 FOR UPDATE;

2. 락은 어디에 기록되나 — 락 테이블이 아니라 튜플 헤더 xmax

PostgreSQL의 행 락은 공유 메모리의 락 구조체가 아니라 잠근 튜플 자체의 헤더에 남는다. 락을 잡으면 그 튜플의 xmax에 내 트랜잭션 ID를 쓰고, infomask에 "이건 삭제가 아니라 락"이라는 비트와 모드 비트를 세운다.

xmax
원래는 "이 튜플 버전을 지운(또는 새 버전으로 밀어낸) 트랜잭션 ID"를 담는 헤더 필드다 — 이름 그대로 이 버전이 보이는 트랜잭션 범위의 최댓값을 뜻한다(MVCC). 락은 이 필드를 재활용해 "지운 게 아니라 잠갔을 뿐"이라는 비트와 함께 쓴다.
infomask
그 튜플의 상태를 나타내는 비트 묶음. "락이다 / 삭제다"와 "어떤 모드다"가 여기 들어간다. 공유 계열이거나 여러 트랜잭션이 함께 잠근 경우엔 xmax 자리에 MultiXactId(여럿을 가리키는 하나의 번호)를 넣고 구성원 목록은 별도 multixact 영역에 둔다.

가장 흔한 오답 — "락이 몇 개 걸렸는지 pg_locks로 세어 보겠습니다"

셀 수 없다. pg_locks에 있는 것은 테이블 락과 "대기 중인 요청"뿐이고, 잡혀 있는 행 락 자체는 튜플 헤더에 있어서 목록이 존재하지 않는다. 잠긴 행을 보려면 pgrowlocks 확장을 쓴다.

대기의 모양도 알아 두면 장애 화면이 읽힌다 — 잠긴 튜플을 만난 트랜잭션은 xmax의 트랜잭션이 끝나기를 기다리므로 pg_stat_activity에 wait_event_type = Lock, wait_event = transactionid로 보이고, 같은 행에 대기자가 둘 이상이면 순서 보장을 위해 임시 tuple 락을 쓰므로 첫 대기자만 transactionid, 나머지는 tuple로 보인다. 이 분포가 "한 행에 줄이 섰다"의 증거다.

2-1. 왜 인덱스 엔트리는 안 잠그나 — 힙 튜플 하나가 정본

PostgreSQL의 테이블은 힙이고, 모든 인덱스는 리프에 (키, TID)만 들고 힙을 가리키는 세컨더리다. 행의 실체는 힙 튜플 하나뿐이고, 어떤 경로로 오든 — PK 인덱스든, 다른 인덱스든, Seq Scan이든 — 그 행을 갱신하려면 마지막에 반드시 그 힙 튜플에 손을 대야 한다. 거기서 xmax를 본다. 그래서 잠글 곳은 한 군데면 충분하다.

가산점 — 커버링 인덱스여도 힙 방문이 살아난다 가산점 조회 컬럼이 전부 인덱스 안에 있어 평소엔 Index Only Scan으로 힙을 안 가는 쿼리라도, FOR UPDATE가 붙으면 LockRows가 잠그기 위해 힙 튜플을 가져와야 하므로 힙 방문이 되살아난다 — 락은 힙에만 있기 때문이다. 대가도 같은 자리에서 나온다: 인덱스에 락도 버전도 없으므로 "이 키 값의 행이 아직 없다"는 상태를 잠글 방법이 없다 — 갭 락 부재의 근원이다(6절 ⑤).

2-2. 락은 SELECT가 끝나도 안 풀린다 — 커밋까지

락 보유 기간 = 그 SELECT 이후 트랜잭션이 끝날 때까지의 시간 전부

행 락은 트랜잭션이 커밋/롤백될 때 한꺼번에 풀린다. FOR UPDATE 문장이 결과를 돌려준 순간이 아니다. 그 안에 자바 계산, 왕복 몇 번, 외부 API 호출이 들어가면 그만큼 남들이 기다린다. PG에서는 한 겹이 더 있다 — 락을 쥔 채 열려 있는 트랜잭션은 backend_xmin으로 VACUUM을 붙잡아 무관한 테이블의 bloat까지 만든다(16 문서). 이 문서의 폭 × 강도와 저 문서의 기간을 곱한 것이 락 비용의 총량이다.

3. 강도 — 행 락은 4종이다 (PG에만 있는 축)

MySQL의 행 락이 S(공유)/X(배타) 둘이라면 PostgreSQL은 네 단계다. 이걸 모르면 PG에서 가장 흔한 질문 — "한 건만 잠갔는데 왜 다른 테이블 INSERT가 멈추죠" — 를 설명할 수 없다. 네 이름은 무작위가 아니라 두 개의 축을 조합한 것이라, 축을 먼저 보면 넷이 따로 놀지 않는다.

인출 카드 — 누가 어떤 모드를 자동으로 잡는가

사람이 SELECT ... FOR ...로 명시하는 것보다 DB가 알아서 잡는 쪽이 사고의 원인이 되는 경우가 많다.

FOR UPDATE

FOR NO KEY UPDATE

3-2. 그래서 "한 건 잠갔는데 다른 테이블이 멈춘다"가 일어난다

before 세션 A가 FOR UPDATE로 잠근 경우
-- 세션 A: 잔액 갱신 전에 계좌를 잠근다
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;

-- 세션 B: 이 계좌의 거래내역을 남긴다
--   transactions.account_id → accounts.id 로 FK
INSERT INTO transactions (account_id, amount)
VALUES (1, 500);
-- FK 검사가 accounts id=1 에 FOR KEY SHARE 요청
-- → A의 FOR UPDATE와 충돌 → 대기
-- pg_stat_activity:
--   wait_event_type = Lock, wait_event = transactionid
after 강도만 한 칸 낮추면 끝난다
-- 세션 A: 바꾸는 건 balance뿐 — 키가 아니다
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR NO KEY UPDATE;

-- 세션 B
INSERT INTO transactions (account_id, amount)
VALUES (1, 500);
-- KEY SHARE는 NO KEY UPDATE와 충돌하지 않는다 → 즉시 통과

-- 다른 트랜잭션의 잔액 갱신은 여전히 막힌다
-- (NO KEY UPDATE끼리는 충돌) → 원래 목적은 그대로 달성

여기서 나오는 역설 — FOR UPDATE가 UPDATE보다 세다

평범한 UPDATE accounts SET balance = balance - 500 WHERE id = 1은 비키 갱신이라 FOR NO KEY UPDATE만 잡고 자식 INSERT를 막지 않는다. 그런데 "안전하게 하겠다"고 SELECT ... FOR UPDATE를 앞에 붙이는 순간 UPDATE 단독보다 더 센 락을 잡아 자식 INSERT를 막는다.

UPDATE 단독 = NO KEY UPDATE＜SELECT FOR UPDATE + UPDATE = FOR UPDATE

이 구분이 만드는 데드락(자식 INSERT 후 부모 FOR UPDATE가 교차)은 12 문서, FK가 부모에 거는 비용은 34 문서에 있다.

모드 선택 규칙 — 질문은 딱 하나다

"이 트랜잭션이 그 행의 키(PK·유니크)를 바꾸거나 행을 지우는가?"
아니오 → FOR NO KEY UPDATE
잔액·상태·수량·플래그 갱신. PostgreSQL 업무 락의 기본형. 자식 테이블 INSERT를 막지 않는다
예 → FOR UPDATE
이 행을 삭제하거나 키를 바꿀 때만. 최강 모드이므로 "혹시 몰라서"로 고르지 않는다

JPA 표준(LockModeType.PESSIMISTIC_WRITE)에는 NO KEY UPDATE가 없다 — 그래서 이 모드를 쓰려면 네이티브 쿼리가 된다(9절).

4. 폭 — 원리 한 문장: LockRows는 Filter 뒤에 선다

PostgreSQL의 실행 구조를 한 줄로 요약하면 — 스캔 노드가 힙(또는 인덱스)을 읽으며 WHERE(Filter / Index Cond)를 그 자리에서 판정하고, 통과한 행만 위 노드로 올려보낸다. 잠금 읽기는 그 위에 LockRows라는 별도 노드가 서서 올라온 행만 잠근다. 조건에 안 맞아 스캔 노드에서 버려진 행은 LockRows에 도달하지 않으므로 잠길 기회 자체가 없다.

5. 인덱스 부재의 대가 — 폭 사고가 아니라 기간 사고

여기서 딱 한 번 넘어진다 — "PG는 폭이 안 늘어난다"를 "PG는 괜찮다"로 옮겨 적는 것

PG에서 인덱스 부재가 만드는 사고는 두 갈래로 실제로 존재하고, 둘 다 인과가 분명하다. ⑴ 지연 → 직렬화 구간 확대, ⑵ 스캔 순서 가변 → 락 획득 순서 어긋남 → 데드락. 면접관이 "그럼 뭐가 문제인데요?"라고 물었을 때 이 둘을 못 꺼내면 절반만 답한 것이다.

5-2. 그래도 위험한 다섯 가지 — "잠그지 않는다"가 "안전하다"는 아니다

인출 카드 — PG 고유 위험 다섯 (이름을 붙여 꺼낸다)

① 기간② 재평가③ 조인④ FK KEY SHARE⑤ 부재 행
암기 — 기 · 재 · 조 · 키 · 부  ("기재조키부" 다섯 글자)
①
기간 — 스캔 시간만큼 락을 쥐고, 같은 행 경쟁이 그 구간에 직렬화된다. 풀스캔은 (a) 문장을 수백 ms~수 초로 늘려 트랜잭션·커넥션 점유를 키우고, (b) 잠글 행을 스캔 중간에 찾았다면 그 시점부터 잠근 채 나머지를 읽는다. 같은 쿠폰 코드를 노리는 요청 N개가 오면 각자 풀스캔 → 첫 번째가 잠그고 나머지는 대기 → 커밋 → 두 번째가 잠그고 남은 페이지를 마저 읽고 로직을 돌린 뒤 커밋 → … 직렬화 구간이 "0.1ms"가 아니라 "수백 ms + 로직"이 된다. 대기자마다 커넥션을 쥐므로 풀 고갈로 간다.
②
READ COMMITTED의 재평가(EvalPlanQual) — 후보 행마다 대기, 반환은 최신 버전. FOR UPDATE는 문장 시작 시점 스냅샷으로 후보를 찾는다. 후보 행이 다른 진행 중 트랜잭션에 의해 갱신·삭제·잠금 중이면 그 트랜잭션이 끝날 때까지 대기하고, 커밋됐으면 최신 버전을 다시 가져와 WHERE를 재평가한다 — 여전히 맞으면 그 최신 버전을 잠그고 반환, 아니면 건너뛴다. 이름 그대로 "Evaluate Plan Qualification = 계획의 조건식을 최신 버전으로 다시 평가"이고, 스냅샷 시점 값으로 잠그면 이미 남이 바꿔 놓은 값을 근거로 쓰기를 하게 되므로 RC는 이 길을 택했다.
재평가가 만드는 함의 넷
  • (a) 반환 값이 스냅샷 시점 값이 아니라 최신 커밋 값일 수 있다 — 같은 트랜잭션의 앞선 일반 SELECT와 값이 다를 수 있다(RC의 성질).
  • (b) 풀스캔 중 만나는 후보 행마다 대기가 생길 수 있고, 조건이 넓을수록(status = 'PENDING') 대기 지점이 많다. 반대로 스냅샷에서는 조건에 안 맞았지만 동시 트랜잭션이 맞게 바꾼 행은 보지도 않고 지나간다.
  • (c) ORDER BY + FOR UPDATE: 정렬은 스냅샷 값으로 먼저 끝나고 락은 그 뒤에 잡히므로, 대기 중 정렬 컬럼이 바뀌면 반환 순서가 실제 값 기준으로는 어긋날 수 있다(공식 문서의 경고). 순서가 정합성에 중요하면 SELECT * FROM (SELECT ... FOR UPDATE) s ORDER BY ...로 잠근 뒤 정렬한다 — 단 서브쿼리가 반환하는 행을 전부 잠그므로 LIMIT과 함께 쓰면 폭이 커진다.
  • (d) LIMIT: 락은 LIMIT을 채우면 멈춘다(좋다). 다만 재평가에서 탈락한 행은 건너뛰고 다음 후보를 끌어오므로 "스냅샷 기준 상위 n"과 "실제로 잠긴 n"이 다를 수 있고, OFFSET으로 건너뛴 행은 잠긴다.
③
조인 — OF로 한정하지 않으면 모든 테이블의 행이 잠긴다.
before orders만 잠그려 했는데
SELECT o.*, u.tier
  FROM orders o JOIN users u ON u.id = o.user_id
 WHERE o.id = 42 FOR UPDATE;
-- users 행까지 FOR UPDATE
-- → 그 사용자의 모든 요청이 이 트랜잭션 뒤에 선다
after 잠글 테이블을 지정
SELECT o.*, u.tier
  FROM orders o JOIN users u ON u.id = o.user_id
 WHERE o.id = 42 FOR UPDATE OF o;
-- JPA fetch join + @Lock 이면 방언·버전에 따라
-- FOR UPDATE가 전체에 붙을 수 있다 → 생성 SQL에
-- OF 별칭이 붙는지 반드시 확인

외부 조인의 NULL 쪽은 잠글 수 없어 에러이고, GROUP BY·DISTINCT·집계·UNION과는 함께 쓸 수 없다 — 반환 행이 특정 테이블의 행 하나에 대응하지 않으므로 잠글 대상을 특정할 수 없기 때문이다.

④
강도 — FOR UPDATE는 FK 검사의 KEY SHARE와 충돌한다. 3절 그대로다. 부모 행(계좌·쿠폰·상품)을 FOR UPDATE로 쥐고 있는 동안, 그 부모를 참조하는 자식 테이블(거래내역·사용이력·주문항목)의 INSERT가 전부 대기한다. "한 건만 잠갔는데 다른 테이블이 멈춘다"의 정체. 키를 안 바꾸면 FOR NO KEY UPDATE.
⑤
존재하지 않는 행은 못 잠근다. SELECT ... WHERE code = 'NEW' FOR UPDATE가 0행이면 잠긴 것도 0개다. 두 트랜잭션이 동시에 "없네" → 둘 다 INSERT → 유니크 제약이 없으면 중복이다. 갭 락이 없는 대가이며, check-then-insert는 UNIQUE + INSERT ... ON CONFLICT, pg_advisory_xact_lock(hashtext(code)), 또는 SERIALIZABLE로 막는다(12 문서).

5-3. 곁가지 — 스캔 순서가 흔들리면 데드락까지 온다

데드락은 "서로 상대가 쥔 것을 기다리는 순환"이고, 순환이 생기려면 락 획득 순서가 세션마다 달라야 한다. 그 순서를 정하는 것이 실행 계획이다.

인덱스를 탈 때 — 순서가 고정된다

Index Scan은 항상 인덱스 키 순서로 행을 올린다. 세션 A도 B도 id 10 → id 20 순서라 순환이 생길 수 없다.

Seq Scan일 때 — 시작 지점이 다를 수 있다

PostgreSQL은 synchronize_seqscans = on(기본)이라 이미 돌고 있는 순차 스캔이 있으면 새 스캔은 그 지점에 합류해 읽다가 테이블 끝에서 앞으로 되돌아온다(wrap around). 캐시 적중률을 높이는 최적화인데, 부작용으로 ORDER BY 없는 쿼리의 행 순서가 세션마다 달라진다.

A: 블록 0부터 → id 10 잠금 → id 20 대기
B: 블록 500부터 → id 20 잠금 → id 10 대기
= 순환 → ERROR 40P01 deadlock detected(deadlock_timeout 기본 1초 뒤 검출, 한쪽 강제 롤백)

처방 둘은 방향이 같다

  • 인덱스를 걸어 실행 계획을 Index Scan으로 고정한다 — 기간이 줄고 획득 순서도 함께 고정된다. 한 번에 둘을 산다.
  • 여러 행을 잠가야 한다면 잠금 순서를 쿼리로 명시한다. ORDER BY id를 붙이면 계획이 LockRows → Sort → Seq Scan이 되어 정렬된 순서로 잠그므로 세션 간 획득 순서가 같아진다(LockRows가 Sort 위에 서기 때문에 가능한 처방이다). 다만 Sort 입력은 여전히 전체 스캔이므로 기간 문제는 인덱스로 따로 풀어야 한다.

데드락의 유형·검출·재현은 12 문서가 본론이다. 여기서 기억할 것은 "인덱스는 폭이 아니라 기간과 순서를 산다" 한 줄.

5-4. 사슬 — PG에서 끊기는 곳과 이어지는 곳

비용을 "느려진다"로 뭉뚱그리지 않는다 — 단계마다 이름과 관측 증거를 붙인다
#단계관측 증거MySQL / InnoDB라면
①인덱스 부재 (또는 함수·타입·부분 인덱스 조건 불일치로 못 탐)EXPLAIN → LockRows 아래 Seq Scan, Rows Removed by Filter ≈ 전체 행, Buffers ≈ 테이블 페이지 수같다
②전 페이지 읽기 — 그러나 잠기는 건 WHERE 통과 행뿐
여기가 갈라지는 지점이다		pgrowlocks('coupon')의 행 수 = 1. 무관한 행 UPDATE·새 INSERT는 그대로 통과스캔한 전 레코드에 X 락(RR이면 갭까지) → 사실상 테이블 배타 락
③기간 사고 — 잠글 행을 찾은 시점부터 스캔 끝 + 커밋까지 락 보유. 문장 자체가 수백 ms~수 초pg_stat_activity에서 그 pid가 active로 오래, backend_xmin이 잡혀 VACUUM 지연폭이 이미 터졌으므로 기간은 부차적
④같은 행을 노리는 트랜잭션들이 그 긴 구간에서 직렬화 — 각자 또 풀스캔을 돌린 뒤 그 행에서 대기wait_event = transactionid 1명 + tuple 여러 명, pg_blocking_pids가 같은 pid를 가리킴. CPU·IO는 풀스캔 N개로 포화 → 무관한 쿼리까지 느려짐(락이 아니라 자원으로 전파)
곁가지: 여러 행을 잠그면 시작 지점 차이로 40P01 데드락까지		이 테이블에 쓰는 트랜잭션 전원 대기(innodb_lock_wait_timeout 기본 50초). 무관한 행도 새 INSERT도 막힌다
⑤대기자는 커넥션을 쥔 채 멈춘다 (lock_timeout 기본 0 = 무한 대기)HikariCP active ≈ maximumPoolSize, idle = 0, pending 증가같다 (단 대기 상한 50초가 기본으로 있다)
⑥커넥션 풀 고갈 → 이 테이블과 무관한 API(로그인·조회)까지 커넥션을 못 얻는다connectionTimeout(기본 30초) 후 SQLTransientConnectionException: Connection is not available. 무관한 엔드포인트의 p99가 동시에 튄다같다
⑦전면 장애 + 호송 효과(convoy) — 원인 트랜잭션이 커밋해도 다음 대기자가 또 같은 쿼리(또 남은 페이지 읽기) → 대기열이 줄지 않는다범인 pid를 죽여도 잠시 뒤 같은 모양이 재현같다
⑧회복: pg_terminate_backend(범인 pid) → CREATE INDEX CONCURRENTLY / 쿼리 수정 배포재발 방지는 9절 (리뷰 · 타임아웃 · 관측 · 테스트)같다

면접에서 한 호흡으로 말할 버전

인덱스 부재→Seq Scan(전 페이지 읽기)→그래도 잠기는 건 WHERE 통과 행뿐→락 보유 기간이 스캔 시간만큼→같은 행 경쟁이 직렬화→대기마다 커넥션 점유→풀 고갈→무관 API 전파
폭 사고가 아니라 기간 사고다. 처방은 같은 인덱스지만, 이유가 "잠기는 행을 줄이려고"가 아니라 "잠그는 데 걸리는 시간을 줄이려고"다

6. PG에서 "폭 사고"는 인덱스가 아니라 조건이 넓을 때 난다

풀스캔 원인 6종(02 문서)이 FOR UPDATE에 붙으면 기간 사고가 되고, 조건 자체가 넓으면 폭 사고가 된다. 둘을 구분해서 본다.

(a) 타입 불일치 — PG는 대개 조용히 풀스캔하지 않고 에러를 낸다
SELECT * FROM coupon WHERE code = 20260801 FOR UPDATE;
-- ERROR:  operator does not exist: text = integer        ← 리뷰 전에 드러난다
-- 단 bigint 컬럼 = numeric 파라미터 같은 조합은 컬럼 쪽이 캐스트돼 인덱스를 잃는다 → 기간 사고
(b) before 컬럼에 함수 → 인덱스 무효 → 기간 사고
SELECT * FROM reservation
 WHERE date(starts_at) = current_date FOR UPDATE;
-- Seq Scan → 잠기는 건 매치 행뿐이지만 문장이 길다
(b) after 범위 조건으로 바꾸거나 표현식 인덱스
SELECT * FROM reservation
 WHERE starts_at >= current_date
   AND starts_at < current_date + 1 FOR UPDATE;

CREATE INDEX idx_reservation_starts_date
    ON reservation ((date(starts_at)));
(c) 조건이 넓다 — PG의 진짜 "폭 사고"
SELECT * FROM job WHERE status = 'PENDING' FOR UPDATE;
-- → 인덱스를 타든 안 타든 PENDING 행 전부를 잠근다 (갭은 없다). 폭 = 매치 행 수.
--    PENDING이 10만 건이면 10만 튜플의 xmax를 쓴다 → 페이지 더티 + WAL,
--    그리고 그 10만 행을 만지는 트랜잭션 전원 대기. "한 건"이 아니었던 것뿐이다
(d) ORDER BY ... LIMIT — PG는 LIMIT을 채우면 락을 멈춘다
SELECT * FROM job WHERE status = 'PENDING' ORDER BY created_at LIMIT 10 FOR UPDATE;
--  계획이 Limit → LockRows → Sort → Seq Scan 순이라 정렬 뒤 상위 10건만 잠근다 (폭 = 10)
--  덤: 정렬된 순서로 잠그므로 세션 간 락 획득 순서가 같아져 데드락 순환이 생기지 않는다
--  단 ① Sort가 남으면 PENDING 전부를 읽고 정렬하는 비용은 그대로 → 기간 사고
CREATE INDEX job_pending_created_idx ON job (created_at) WHERE status = 'PENDING';
--     ② OFFSET으로 건너뛴 행은 잠긴다 — 페이지네이션과 FOR UPDATE를 섞지 않는다
--     ③ RC 재평가로 순서·구성이 어긋날 수 있다 (5-2 ②)

(c)가 PG 사용자가 진짜 조심할 곳

MySQL 경험자가 "인덱스 있으니 괜찮다"고 넘기는 자리에서, PG는 "인덱스는 기간을 줄일 뿐 폭은 조건이 정한다"로 되묻는다.

(d)는 반대로 PG가 이기는 자리

MySQL에서 배치 워커의 LIMIT n FOR UPDATE가 큐 테이블 전체를 잠그던 사고가 PG에서는 나지 않는다 — LockRows가 Limit 아래에 있기 때문. InnoDB는 ORDER BY를 인덱스로 못 풀면 filesort — 조건에 맞는 행을 전부 읽어 잠근 뒤 정렬하고 10건을 자른다. LIMIT이 잠기는 레코드 수를 줄여주지 않는다.

이 절의 규칙 한 줄

폭은 조건이 정하고, 기간은 실행 계획이 정한다. 문장의 종류(SELECT FOR UPDATE냐 UPDATE냐)는 폭을 바꾸지 못한다

7. 네 축과 선택 플로우 — 무엇이 무엇을 정하는가

폭 — 몇 개의 행을
WHERE 조건(과 OF, OFFSET, 조인 범위)이 정한다. 실행 계획은 폭을 바꾸지 못한다. 조건이 좁으면 1, 넓으면 매치 행 전부
기간 — 얼마나 오래
트랜잭션 경계 + 스캔 시간이 정한다. 실행 계획이 정하는 건 이쪽이다. 락 구간 안의 왕복·계산·외부 호출은 그대로 남의 대기 시간
강도 — 어떤 모드로
PG 고유 축. FOR UPDATE는 4종 중 최강이라 FK의 KEY SHARE까지 막는다. 대부분의 업무 락은 FOR NO KEY UPDATE로 충분
자원 — 기다리며 무엇을 붙잡나
커넥션 풀 크기가 상한을 정한다. 대기자가 붙잡는 것은 스레드가 아니라 커넥션이다(03장)
비관적 락을 "간단하고 확실하다"고 고를 때 치르는 값은 이 넷의 곱이다

폭이 1이고 강도가 맞으면 기간과 자원만 관리하면 되지만, 조건이 넓어 폭이 수만이 되거나 FOR UPDATE가 자식 테이블까지 세우는 순간 나머지가 아무리 잘 관리돼도 사고다. 그래서 선택의 첫 관문은 "충돌이 잦은가"가 아니라 "잠글 행을 좁게·빨리·필요한 강도로 특정할 수 있는가"다.

처방 순서 — 이 네 글자로 외운다

폭 — 등호 조건→기간 — 인덱스 + 락 안 왕복 제거→강도 — 키 안 바꾸면 NO KEY UPDATE→대기 — lock_timeout / NOWAIT / SKIP LOCKED
폭 · 기 · 강 · 대
세 방식과의 비교를 폭 · 강도 관점으로만 짧게
방식폭강도이기는 지점 / 지불하는 것
원자적 UPDATE
UPDATE ... WHERE id=$1 AND qty>=$2		동일 — 매치 행만자동으로 맞는다 — 비키 갱신이면 FOR NO KEY UPDATE이기는 것은 기간(왕복 1회). 인덱스가 없으면 역시 스캔 시간만큼 기간이 는다
낙관적 락읽기가 일반 SELECT라 아무것도 안 잠근다—인덱스가 없어도 느릴 뿐 남을 세우지 않는다. 대신 충돌 시 재시도 비용
비관적 락 (FOR UPDATE)조건이 정한다4종 중 최강 (기본값으로 고르면)폭·기간·자원·강도 넷 다 진다. 대신 재시도가 없고 복잡한 로직을 락 안에서 안전하게 수행

8. 대기 정책 — 잠긴 행을 만났을 때 무엇을 할 것인가

기본값이 무한 대기다 — 이 사실이 5-4 사슬의 ⑤⑥을 가능하게 만든다

락을 요청했는데 이미 남이 쥐고 있으면 PostgreSQL의 기본 동작은 끝없이 기다리는 것이다(lock_timeout = 0). MySQL의 innodb_lock_wait_timeout이 기본 50초인 것과 대비된다 — PG는 아무도 안 끊어 준다.

8-1. lock_timeout — 모든 락 대기의 기본 상한

-- 롤 단위로 걸어 두는 것이 가장 확실하다 (PgBouncer transaction pooling 환경에서도 안전)
ALTER ROLE app_user SET lock_timeout = '3s';

-- 특정 트랜잭션에서만 다르게 하려면 SET LOCAL (그 트랜잭션이 끝나면 되돌아간다)
BEGIN;
SET LOCAL lock_timeout = '500ms';
SELECT * FROM seat WHERE id = 1042 FOR NO KEY UPDATE;
얻는 것
대기자가 커넥션을 붙잡는 시간에 상한이 생긴다. 사슬 ⑤⑥을 시간으로 끊는 유일한 장치다
대가 ① 트랜잭션 abort
초과 시 ERROR 55P03 canceling statement due to lock timeout이고, PG에서는 문장 하나가 실패하면 트랜잭션 전체가 abort 상태가 되므로 반드시 ROLLBACK해야 한다(MySQL처럼 "그 문장만 실패하고 계속"이 안 된다)
대가 ② 누적 상한이 아니다
락 획득 시도마다 따로 적용된다. 한 트랜잭션에서 락을 다섯 번 잡으면 최악의 경우 3초 × 5. 트랜잭션 전체 상한은 @Transactional(timeout = n)이나 statement_timeout으로 따로 건다
JPA 주의 jakarta.persistence.lock.timeout에 양수를 주는 힌트는 PostgreSQL에서 SQL로 번역되지 않는다(PG에는 FOR UPDATE WAIT n 구문이 없다). 그래서 실질적인 대기 상한은 언제나 이 lock_timeout 설정이다.

8-2. NOWAIT — "기다리느니 실패"

SQL 즉시 실패
SELECT * FROM seat WHERE id = 1042 FOR UPDATE NOWAIT;
-- 이미 잠겨 있으면 대기하지 않고 즉시 에러
-- ERROR:  could not obtain lock on row in relation "seat"
--         (SQLSTATE 55P03)
얻는 것
대기열이 아예 생기지 않는다 → 대기자 쪽 커넥션 보호에 가장 강력. 사슬 ④⑤⑥을 대기자 입장에서 끊는다
대가
① 실패를 애플리케이션이 반드시 처리(트랜잭션 abort) ② 클라이언트가 자동 재시도하면 재시도 폭풍으로 모양만 바뀐다 ③ 잠근 쪽의 기간 사고는 못 고친다 — 피해자를 빨리 죽이는 것이지 가해자를 고치는 게 아니다
JPA 좌석 선점 — 이미 잡혀 있으면 409로 즉시 응답
public interface SeatRepository
        extends JpaRepository<Seat, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(          // 0 = NOWAIT
            name = "jakarta.persistence.lock.timeout",
            value = "0"))
    @Query("select s from Seat s where s.id = :id")
    Optional<Seat> findByIdNoWait(@Param("id") Long id);
}

@Transactional
public void hold(Long seatId, Long userId) {
    try {
        Seat seat = seatRepository
                .findByIdNoWait(seatId).orElseThrow();
        seat.holdBy(userId);
    } catch (CannotAcquireLockException e) {  // 55P03 → 여기로
        throw new SeatAlreadyBeingHeldException(seatId);
        // 컨트롤러에서 409 + "다시 시도" 안내
    }
}
// 생성 SQL을 로그로 확인하고 쓴다 — 버전·방언마다 지원이 다르다

8-3. SKIP LOCKED — "잠긴 건 남의 것, 다음 것" (실무 값어치가 가장 큰 도구)

앞의 둘이 "대기 시간을 어떻게 할까"에 답한다면, SKIP LOCKED는 질문 자체를 바꾼다 — "굳이 그 행이어야 하나?" 아니라면 잠긴 행은 건너뛰고 다음 것을 집으면 된다. 이 한 줄이 열어 주는 것이 작업 큐 패턴이다. 워커 여러 개가 같은 테이블을 보면서도 서로 다른 행을 집어 가므로 테이블 하나가 그대로 큐가 된다 — 별도 메시지 브로커 없이 "DB에 쌓고 워커가 꺼내 처리"를 안전하게 구현하는 PostgreSQL의 표준 해법이다.

패턴 워커 N개가 동시에 도는 작업 큐 — 이 한 문장이 전부다
SELECT id, payload
  FROM job
 WHERE status = 'PENDING'
 ORDER BY id                        -- 대체로 오래된 것부터. 순서는 최선 노력이다
 LIMIT 10
   FOR NO KEY UPDATE SKIP LOCKED;   -- 잠긴 행은 건너뛰고, 안 잠긴 10건만 잠가서 가져온다
                                    -- status만 바꾸므로 NO KEY UPDATE
                                    --   → job_log(job_id FK) INSERT를 막지 않는다

-- PG 고유의 짝: 부분 인덱스 — PENDING 행만 담아 작고, id 순으로 바로 읽어 10건에서 멈춘다
CREATE INDEX job_pending_id_idx ON job (id) WHERE status = 'PENDING';
-- 계획: Limit → LockRows → Index Scan using job_pending_id_idx   (Sort 없음, Seq Scan 없음)
before 워커 5개가 전부 같은 10건에서 줄을 선다
// 인덱스도 없어 매번 Seq Scan + Sort,
// FOR UPDATE라 job_log INSERT까지 막고, 처리까지 락 안에서 한다
@Lock(LockModeType.PESSIMISTIC_WRITE)
List<Job> findTop10ByStatusOrderByCreatedAt(JobStatus status);

@Transactional
public void runOnce() {
    List<Job> jobs =
        repo.findTop10ByStatusOrderByCreatedAt(PENDING);
    jobs.forEach(j -> jobProcessor.process(j));  // 락 안에서 처리
}   // 커밋까지 10건을 쥔 채 처리 시간 전부 = 기간 사고
after 잠긴 건 건너뛰고, 상태만 바꾸고 바로 커밋
@Query(value = """
        SELECT * FROM job
         WHERE status = 'PENDING'
         ORDER BY id
         LIMIT :n
           FOR NO KEY UPDATE SKIP LOCKED
        """, nativeQuery = true)
List<Job> claimPending(@Param("n") int n);

@Transactional               // 트랜잭션 ①: 선점만 (수 ms)
public List<Long> claim(int n) {
    List<Job> jobs = jobRepository.claimPending(n);
    jobs.forEach(j -> j.markProcessing(workerId));  // 비키 갱신
    return jobs.stream().map(Job::getId).toList();
}

public void runOnce() {
    for (Long jobId : jobService.claim(10)) {
        jobProcessor.process(jobId);   // 트랜잭션 밖 — 락 없이 처리
    }
}

SKIP LOCKED가 지불하는 것 다섯

  • ① 결과가 비결정적이다 — 같은 쿼리를 두 번 쳐도 다른 행이 온다. "몇 건 남았나", "이 행이 존재하나" 같은 정합성 판단에 쓰면 안 된다. 오직 "내 몫 가져오기" 전용.
  • ② 순서·공정성은 최선 노력 — 잠긴 행을 건너뛰므로 ORDER BY는 "대체로 그 순서"일 뿐이다.
  • ③ 가져온 행은 커밋까지 잠긴다 → 위 코드처럼 바로 커밋해야 한다. 처리를 락 안에서 하면 기간 문제가 그대로 온다.
  • ④ 스캔 비용을 없애 주지 않는다 — 부분 인덱스가 있어야 10건에서 스캔이 멈춘다.
  • ⑤ 고아 행 청소가 짝으로 필요하다 — 워커가 죽어 롤백되면 그 행은 다시 PENDING으로 돌아오지만(좋은 성질), markProcessing 커밋 후에 죽으면 PROCESSING에 남아 고아가 된다 → 오래된 PROCESSING을 회수하는 청소 배치.

JPA: Hibernate는 jakarta.persistence.lock.timeout = -2(LockOptions.SKIP_LOCKED)를 PostgreSQL 방언에서 SKIP LOCKED로 번역하지만, NO KEY UPDATE는 JPA 표준에 없으므로 어차피 네이티브다. 생성 SQL 확인이 전제.

8-4. 한 장으로 정리

도구잠긴 행을 만나면어울리는 상황지불하는 것

9. 코드·리뷰·설정·관측으로 고정하기 — 사람의 기억에 맡기지 않는다

경계 — 애플리케이션 쪽 락은 03장, 여기는 DB 쪽 JPA의 LockModeType이 무엇을 뜻하는지, 낙관적 락의 @Version을 어떻게 붙이는지, 재시도를 어디에 두는지 같은 애플리케이션 쪽 설계는 03장이 본론이다. 여기서 다루는 것은 그 위임의 결과로 DB에 나가는 SQL이 무엇을 얼마나 잠그는가이므로, 아래 before/after의 관심사도 "어떤 어노테이션을 쓸까"가 아니라 "생성된 SQL의 폭·기간·강도가 의도와 같은가" 하나다.

@Transactional
public void redeem(String code, Long userId) {
    // 1) 락 없는 스냅샷 읽기로 PK만 얻는다 — 인덱스가 없어도
    //    느릴 뿐, 남을 세우지 않는다(MVCC)
    Long couponId = couponRepository
            .findIdByCode(code).orElseThrow();
    //    엔티티가 아니라 id 프로젝션이어야 한다 — 먼저 로드해 두면
    //    2)의 em.find는 이미 관리 중인 엔티티에 락 문장만 보내고
    //    상태를 새로 읽지 않아 3)의 재검증이 헛돈다

    // 2) PK로 잠근다 — Index Scan으로 계획이 "고정"된다
    Coupon coupon = em.find(Coupon.class, couponId,
                            LockModeType.PESSIMISTIC_WRITE);

    // 3) 잠근 뒤 조건을 다시 검증한다 — RC라 1)의 스냅샷과
    //    2)의 최신 버전이 다를 수 있다
    if (coupon.isRedeemed())
        throw new AlreadyRedeemedException(code);
    coupon.redeem(userId);
}

(C)의 가치는 누가 나중에 인덱스를 지우거나 조건을 바꿔도 락 문장의 실행 계획이 PK 조회로 유지된다는 데 있다. PG에서 폭은 원래 1이었으므로 (C)가 지키는 것은 폭이 아니라 기간이고, 여러 행을 잠그는 로직이라면 PK 순서로 잠그게 되므로 5-3의 데드락도 함께 막는다. 대가는 왕복 1회 추가와 3)의 재검증 습관, 그리고 여전히 FOR UPDATE라는 강도(자식 INSERT가 있으면 (A)로).

after (B) — 표준 JPA만 써야 할 때 명시적 JPQL + @Lock. 나가는 SQL은 FOR UPDATE(최강)이므로 이 테이블을 FK로 참조하는 자식 INSERT가 동시에 없을 때만 고른다. 힌트 값의 의미도 알고 쓴다 — 0 → FOR UPDATE NOWAIT, -2 → FOR UPDATE SKIP LOCKED, 양수 → PostgreSQL에서는 SQL로 번역되지 않는다(WAIT n 구문이 없다). 일반적인 "n초만 기다린다"는 lock_timeout 설정으로 건다.

9-4. 잠긴 행과 대기열 확인법 — 네 개의 창

-- ① 누가 기다리고 누가 막고 있나 — 장애 중 가장 먼저 여는 창
SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start  AS xact_age,
       now() - query_start AS query_age,
       pg_blocking_pids(pid) AS blocked_by,
       left(query, 80) AS query
  FROM pg_stat_activity
 WHERE cardinality(pg_blocking_pids(pid)) > 0 OR wait_event_type = 'Lock'
 ORDER BY xact_start;
-- wait_event = transactionid : 잠긴 행의 xmax 트랜잭션이 끝나길 대기 (행 락 대기의 실제 모습)
-- wait_event = tuple         : 같은 행 대기열의 2번째 이후 (첫 대기자만 transactionid)
-- wait_event = relation      : 테이블 락 대기 — DDL이 끼어든 경우 (14 문서)
-- blocked_by에 같은 pid가 수십 번 나오면 그 pid가 범인.
--   그 pid의 state가 'idle in transaction'이면 쿼리가 아니라 트랜잭션 경계가 원인

-- ② 락 요청 목록 — 행 락 자체는 여기 없다(튜플 헤더에 있으므로)
SELECT locktype, relation::regclass, mode, granted, pid, transactionid
  FROM pg_locks WHERE NOT granted;
--  transactionid | (null) | ShareLock | f | 91234 | 421874  ← 행 락 대기의 pg_locks 표현

SELECT locked_row, locker, multi, modes, pids FROM pgrowlocks('coupon');

9-5. 테스트로 고정 — 폭 · 강도 · 계획 회귀 테스트

"이 락은 좁고, 약하고, 빠르다"를 테스트로 박아 두면, 누가 인덱스를 지우거나 FOR UPDATE로 되돌리는 순간 CI가 잡는다. 두 커넥션을 직접 쓴다 — @Transactional 테스트 안에서는 두 트랜잭션이 재현되지 않는다. 그리고 H2가 아니라 Testcontainers로 운영과 같은 PostgreSQL을 띄운다. 락 모양은 엔진마다 다르다.

@Test
void redeem_lock_is_narrow_weak_and_indexed() throws Exception {
    try (Connection holder = dataSource.getConnection();
         Connection other  = dataSource.getConnection()) {

        holder.setAutoCommit(false);
        try (var ps = holder.prepareStatement(          // 리포지토리와 같은 문장 (상수로 공유)
                "SELECT * FROM coupon WHERE code = ? FOR NO KEY UPDATE")) {
            ps.setString(1, "SUMMER-2026");
            ps.executeQuery();                              // 락을 쥔 채 커밋하지 않는다
        }

        other.setAutoCommit(false);
        other.createStatement().execute("SET lock_timeout = '1s'");  // 막히면 1초 뒤 55P03 → 실패

        // ① 폭: 다른 쿠폰 행은 막히면 안 된다 — 조건이 넓어졌거나 테이블 락으로 바뀌었는지 감시
        assertDoesNotThrow(() -> other.createStatement()
                .executeUpdate("UPDATE coupon SET redeemed = redeemed WHERE code = 'WINTER-2026'"));

        // ② 강도: 자식 INSERT가 막히면 안 된다 — 누가 FOR UPDATE로 되돌리면 여기서 실패한다
        assertDoesNotThrow(() -> other.createStatement()
                .executeUpdate("INSERT INTO coupon_redemption (coupon_id, user_id) "
                             + "SELECT id, 999 FROM coupon WHERE code = 'SUMMER-2026'"));

        // ③ 기간: 락 문장이 인덱스를 타는지 (EXPLAIN은 잠그지 않는다)
        try (var rs = holder.createStatement().executeQuery(
                "EXPLAIN (FORMAT JSON) SELECT * FROM coupon WHERE code = 'SUMMER-2026' FOR NO KEY UPDATE")) {
            rs.next();
            assertThat(rs.getString(1)).contains("\"Index Scan\"").doesNotContain("\"Seq Scan\"");
        }

        other.rollback();
        holder.rollback();
    }
}
주의 — ③은 데이터 양과 통계에 좌우된다 행이 몇 개뿐인 테스트 DB에서는 플래너가 유니크 인덱스가 있어도 Seq Scan을 고르는 게 정상이라 거짓 실패한다. 실전 규모 시드 + ANALYZE가 필요하고, 그래서 이 단정은 락 사고가 곧 장애인 쿼리 몇 개에만 건다. ①②는 데이터 양과 무관하게 항상 유효하다.

10-1. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체한다

뭉뚱그린 표현붙일 이름사슬로 말하면
"인덱스 없으면 테이블이 잠긴다"Filter 뒤의 LockRowsPG는 WHERE 통과 행만 잠근다 — 폭은 실행 계획이 아니라 조건이 정한다. 테이블 락은 안 생긴다
"그럼 인덱스 없어도 괜찮네"폭 대신 기간, 그리고 순서Seq Scan 시간만큼 락 보유·트랜잭션·커넥션 점유가 늘고, 같은 행 경쟁이 그 구간에서 직렬화된다. 여러 행을 잠그면 스캔 시작 지점 차이로 데드락까지
"한 건만 잠그는데 왜 다른 테이블 INSERT가 멈추죠"FK KEY SHARE 충돌FOR UPDATE는 KEY SHARE와 충돌 → 자식 INSERT 대기. 키를 안 바꾸면 FOR NO KEY UPDATE
"없는 행을 FOR UPDATE로 잠갔다"갭 락 부재0행 반환 = 0개 잠금. check-then-insert는 UNIQUE/ON CONFLICT/advisory lock
"락이 몇 개 걸렸는지 pg_locks로 세자"xmax에 기록행 락은 pg_locks에 없다. 보이는 건 대기자(transactionid/tuple). 잠긴 행은 pgrowlocks

10-3. 꼬리질문 셀프 테스트 먼저 스스로 답해 보고 펼친다

PostgreSQL은 기본이 READ COMMITTED인데, REPEATABLE READ로 올리면 FOR UPDATE 동작이 달라지나요? 필수힌트: 폭·모드·갭은 그대로. 달라지는 건 "동시 갱신을 만났을 때"뿐이다

잠기는 폭·모드·갭 없음은 그대로고, 동시 갱신을 만났을 때의 처리만 달라진다.

READ COMMITTED (기본)

후보 행이 동시 트랜잭션에 의해 갱신 중이면 기다렸다가 최신 버전을 재평가해 잠그고 진행한다(EvalPlanQual) — 문장이 "성공"으로 끝난다.

REPEATABLE READ

트랜잭션 스냅샷이 고정돼 있어, 잠그려는 행이 내 스냅샷 이후 갱신·삭제됐으면 재평가 대신 ERROR 40001 could not serialize access due to concurrent update로 트랜잭션 전체가 실패한다 → 애플리케이션 재시도가 필수.

즉 격리 수준을 올린다고 락 사고가 줄지 않는다 — "기다렸다 최신 값으로 진행"이 "실패로 알려줌"으로 바뀔 뿐이다. 그래서 MySQL식 "RC로 낮추면 갭 락이 줄어 완화된다"는 처방은 PG에 없다 — 애초에 RC가 기본이고 락 폭은 격리 수준과 무관하다.

인덱스로 찾았는데 인덱스 엔트리는 안 잠근다면, PK로 직접 오는 UPDATE는 어떻게 막히나요? 필수힌트: 모든 경로가 어디서 끝나는지

모든 경로가 힙 튜플에서 끝나기 때문이다. 인덱스는 리프에 TID만 들고 있는 경로일 뿐 정본이 아니고, 갱신은 힙에서 일어난다(새 버전 삽입 + 옛 버전 xmax). 그러니 어떤 인덱스로 오든 힙 튜플을 집는 순간 xmax에 남의 락이 보인다.

커버링 인덱스로 평소엔 힙을 안 가는 쿼리도 FOR UPDATE면 LockRows가 힙 튜플을 가져와 잠근다.

대가는 같은 자리에서 나온다 — 인덱스에 락도 버전도 없으니 "이 키의 행이 아직 없다"는 상태를 잠글 수 없다(갭 락 부재). 유일한 예외가 유니크 인덱스 삽입 시 동일 키 대기다(12 문서).

락이 걸려 있는 동안 다른 트랜잭션의 일반 SELECT는 왜 안 막히나요? 그 값을 믿어도 되나요? 함정힌트: 앞부분은 쉽고, 뒷부분이 진짜 질문이다

일반 SELECT는 잠금 읽기가 아니라 MVCC 스냅샷 읽기라 락 큐에 서지 않는다 — xmax에 "락 전용" 비트가 서 있으면 가시성 판정에 영향이 없다. 그래서 풀스캔 FOR UPDATE 장애의 증상이 "조회는 되는데 저장이 안 된다"로 나타난다.

믿어도 되는 용도

화면 표시, 통계, 목록. 읽고 끝나는 읽기.

믿으면 안 되는 용도

"읽은 값을 근거로 쓰기를 결정"하는 로직(재고 확인 후 차감, 쿠폰 상태 확인 후 사용). 읽는 순간 이미 남이 잠그고 바꾸는 중일 수 있고, RC라 같은 트랜잭션 안의 다음 문장은 다른 스냅샷을 본다.

결정에 쓰이는 읽기는 FOR NO KEY UPDATE / FOR UPDATE이거나, 읽기-결정-쓰기를 한 문장으로 압축한 원자적 UPDATE여야 한다.

잔액 갱신 로직에 FOR UPDATE를 썼더니 거래내역 INSERT가 멈춥니다. 왜죠? 시니어 변별힌트: 자식이 부모에게 무엇을 요구하는지부터

FK 검사가 부모 행에 FOR KEY SHARE를 요구하는데, FOR UPDATE가 4종 중 유일하게 그것과 충돌하기 때문이다. 계좌를 FOR UPDATE로 쥔 동안 그 계좌를 참조하는 transactions INSERT는 전부 transactionid 대기에 걸린다.

판단 기준은 하나 — "이 트랜잭션이 부모의 키를 바꾸거나 행을 지우는가?"

잔액은 키가 아니므로 FOR NO KEY UPDATE가 정확한 도구이고, 그러면 자식 INSERT는 통과한다.

한 발 더 — 자식 INSERT(부모에 KEY SHARE) 뒤에 부모 FOR UPDATE를 잡는 트랜잭션 둘이 교차하면 40P01 deadlock detected다. NO KEY UPDATE면 충돌 자체가 없어 데드락도 사라진다(12 문서). JPA 표준에는 이 모드가 없어 네이티브 쿼리로 쓴다.

"InnoDB에는 이 구분이 없다 — 부모 X 락은 항상 자식 INSERT의 S 락 요청을 막는다"까지 말하면 PG를 원리로 쓴다는 인상을 준다.

SELECT FOR UPDATE 대신 UPDATE ... WHERE code = $1로 바로 치면 이 문제가 없어지나요? 시니어 변별힌트: 폭·기간·강도 셋으로 나눠서 답한다

폭은 원래 문제가 아니었고, 기간과 강도에서 이긴다.

  • 폭 — UPDATE도 매치 행만 잠근다. 규칙은 같다. 인덱스가 없으면 UPDATE도 Seq Scan이라 기간 사고는 그대로다.
  • 기간 — 이긴다. 왕복 1회로 락 구간이 끝난다.
  • 강도 — 이긴다. 비키 갱신 UPDATE는 FOR NO KEY UPDATE만 잡아 자식 INSERT를 막지 않는다.
"SELECT FOR UPDATE + UPDATE" 조합이 UPDATE 단독보다 더 센 락을 잡는 역설이 여기 있다

대신 UPDATE는 새 튜플 버전을 만들고(비-HOT이면 모든 인덱스 갱신, bloat), FOR UPDATE는 xmax 표시만 한다.

그리고 UPDATE ... WHERE status = 'PENDING' 같은 배치 갱신은 매치 행 전부를 잠그고 스캔 시간만큼 쥐므로, 인덱스와 청크 분할 없이 날리면 같은 사고다. 폭은 문장의 종류가 아니라 조건이, 기간은 실행 계획이 정한다.

운영 중 "락 대기" 알림이 왔습니다. 어디부터 보나요? 가산점힌트: 다섯 단계를 순서로 외워 둔다 — 관측 → 진단 → 응급 → 근본 → 재발 방지
1
관측 — pg_stat_activity + pg_blocking_pids()로 범인 pid, 그 state, xact_age를 본다. 대기자 수십에 범인 하나면 같은 행 경쟁, 범인이 idle in transaction이면 쿼리가 아니라 트랜잭션 경계 문제.
2
진단 — 범인의 query를 EXPLAIN. LockRows 아래가 Seq Scan이면 기간(인덱스), 조건이 넓으면 폭, 대기자가 다른 테이블의 INSERT면 강도(FOR UPDATE vs FK). wait_event가 relation이면 DDL이 끼어든 것(14 문서).
3
응급 — pg_terminate_backend(범인)으로 대기열을 푼다. idle in transaction엔 pg_cancel_backend가 안 통한다.
4
근본 — CREATE INDEX CONCURRENTLY / NO KEY UPDATE로 강도 조정 / 조건 축소 배포.
5
재발 방지 — 롤 단위 lock_timeout, idle_in_transaction_session_timeout, log_lock_waits, 리뷰 체크리스트(9-2)와 회귀 테스트(9-5).

이 다섯을 이름으로 말할 수 있으면 장애를 겪어 본 사람으로 읽힌다.

MySQL로 물어보면 답이 달라지는 부분은? 시니어 변별힌트: 다섯 지점 — 위치와 폭 / 갭 / 모드 / 저장과 관측 / 기본 격리와 타임아웃 뒤 상태

① 락의 위치와 폭 — InnoDB는 스캔한 인덱스 레코드에(RR이면 앞 갭까지), PG는 WHERE 통과 후 힙 튜플에만. 그래서 인덱스 부재 시 MySQL은 사실상 테이블 락(폭 사고), PG는 느린 스캔 + 매치 행만(기간 사고) — 질문의 답 방향이 정반대다.

② 갭 락·넥스트 키 락 부재 — PG는 "없는 행"·범위를 못 잠근다(check-then-insert는 UNIQUE/ON CONFLICT/advisory/SERIALIZABLE). 반대로 MySQL RR에서 LIMIT n FOR UPDATE가 filesort로 큐 전체를 잠그던 사고는 PG에서 Limit 아래 LockRows가 n건에서 멈춰 나지 않는다.

③ 락 모드 — InnoDB는 S/X(+갭·insert intention), PG는 4단계에 FK가 KEY SHARE를 잡아 FOR UPDATE vs FOR NO KEY UPDATE의 선택이 PG에만 있다. InnoDB는 부모 UPDATE든 FOR UPDATE든 X 락이라 자식 INSERT를 막는 걸 피할 수단이 없다.

④ 락 저장과 관측 — InnoDB는 메모리 락 구조체(trx_rows_locked, data_locks로 셀 수 있고 행 수만큼 메모리), PG는 튜플 헤더 xmax(개수 제한·에스컬레이션 없음, 대신 락도 페이지 더티 + WAL, pg_locks엔 안 보여 pgrowlocks). 세컨더리 → 클러스터드 연쇄 잠금도 PG엔 없다.

⑤ 기본 격리와 타임아웃 뒤 상태 — MySQL은 RR 기본(+갭), innodb_lock_wait_timeout 50초 뒤 그 문장만 실패하고 트랜잭션은 계속. PG는 RC 기본(EvalPlanQual 재평가), lock_timeout 기본 무한, 초과 시 55P03과 함께 트랜잭션이 abort 상태라 반드시 ROLLBACK. 이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "차이를 저장 구조에서 도출했다"로 들린다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

커버링 인덱스를 만들어 뒀는데, FOR UPDATE를 붙여도 Index Only Scan이 유지되나요? 가산점힌트: 락이 어디에 기록되는지를 떠올린다

유지되지 않는다 — 힙 방문이 되살아난다. 조회 컬럼이 전부 인덱스 안에 있어도 LockRows는 잠그기 위해 힙 튜플을 가져와야 한다. 락은 xmax, 즉 힙 튜플의 헤더에만 있기 때문이다.

그래서 "커버링 인덱스로 힙을 안 가서 빠르다"는 이점은 잠금 읽기에서는 사라진다. 다만 인덱스로 행을 특정하는 이점(= 기간)은 그대로 남는다 — 힙 방문이 페이지 1장 추가일 뿐, Seq Scan 14,741장과는 비교가 안 된다.

같은 사실의 뒷면이 갭 락 부재다. 인덱스에 락도 버전도 없으니 "이 키의 행이 아직 없다"는 상태를 잠글 방법이 없다 — PG가 팬텀을 갭 락이 아닌 다른 수단(UNIQUE, advisory lock, SERIALIZABLE)으로 막는 이유가 여기서 나온다.

큐 테이블에 ORDER BY created_at LIMIT 10 FOR UPDATE를 쓰면 정말 10건만 잠기나요? 가산점힌트: 계획 트리에서 Limit·LockRows·Sort의 순서를 그려 본다

PostgreSQL에서는 10건만 잠긴다. 계획이 Limit → LockRows → Sort → Seq Scan 순이라 정렬이 먼저 끝나고 상위 10건만 LockRows에 도달하기 때문이다. 덤으로 정렬된 순서로 잠그므로 세션 간 락 획득 순서가 같아져 데드락 순환이 생기지 않는다.

그러나 셋을 함께 말해야 답이 완성된다.

  • 기간은 안 줄었다 — Sort가 남으면 PENDING 전부를 읽고 정렬한 뒤 10건을 자른다. 폭은 10, 기간은 풀스캔. 부분 인덱스(ON job (created_at) WHERE status = 'PENDING')로 Sort를 없애야 진짜 10건에서 멈춘다.
  • OFFSET은 예외다 — 건너뛴 행도 잠긴다. 페이지네이션과 FOR UPDATE를 섞지 않는다.
  • RC 재평가로 구성이 어긋날 수 있다 — 대기 후 최신 버전을 재평가하므로 "스냅샷 기준 상위 10"과 "실제로 잠긴 10"이 다를 수 있다.

MySQL은 다르다 — ORDER BY를 인덱스로 못 풀면 filesort라 조건에 맞는 행을 전부 읽어 잠근 뒤 정렬하고 10건을 자른다. LIMIT이 잠기는 레코드 수를 줄여주지 않는다. "PG에서 큐 테이블이 편한 이유" 중 하나가 이것이다.

SKIP LOCKED로 "지금 남은 작업이 몇 건인지" 세도 되나요? 함정힌트: 이 도구가 무엇을 포기하고 성능을 얻었는지

안 된다. SKIP LOCKED의 결과는 비결정적이다. 같은 쿼리를 두 번 쳐도 다른 행이 온다 — 그 순간 누가 무엇을 잠그고 있느냐에 따라 결과가 달라지기 때문이다.

"몇 건 남았나", "이 행이 존재하나" 같은 정합성 판단에 쓰면 안 된다. 오직 "내 몫 가져오기" 전용

같은 이유로 ORDER BY도 "대체로 그 순서"일 뿐이다(잠긴 행을 건너뛰므로). 엄격한 FIFO가 요구되는 큐라면 이 도구는 맞지 않는다.

건수를 세려면 락 없는 평범한 집계(SELECT count(*) FROM job WHERE status='PENDING')를 쓴다 — MVCC 스냅샷 읽기라 아무도 막지 않고 아무에게도 막히지 않는다.

100만 행을 FOR UPDATE로 잠그면 락 메모리가 터지거나 테이블 락으로 승격되나요? 가산점힌트: PG에서 "승격"은 안 일어난다. 그런데 공짜도 아니다

승격되지 않고, 락 메모리도 0이다. 락이 튜플 헤더의 xmax에 기록되므로 락 개수 제한도 락 에스컬레이션도 존재하지 않는다. "행 락이 너무 많아 테이블 락으로 승격"은 PG에는 없는 개념이다.

그러나 공짜는 아니다. 값은 다른 곳에서 받아 간다.

  • 락도 쓰기다 — 100만 개의 xmax를 쓰면 그만큼 페이지가 더러워지고 WAL이 나간다. (단 새 튜플 버전은 만들지 않으므로 UPDATE와 달리 bloat는 생기지 않는다.)
  • 그 100만 행을 만지려는 트랜잭션은 전원 대기한다 — 테이블 락이 아닐 뿐 체감은 그것에 가깝다.
  • 기간도 함께 길어진다 — 100만 행을 찾아 표시하는 시간 전부가 락 보유 구간이다.

그래서 "에스컬레이션이 없으니 마음껏 잠가도 된다"가 아니라 "폭은 조건으로 관리해야 한다"가 결론이다. InnoDB는 반대로 행 수만큼 락 구조체 메모리를 쓰므로, 같은 상황에서 메모리라는 다른 벽을 먼저 만난다.

lock_timeout = '3s'를 걸어 뒀는데 어떤 트랜잭션이 12초를 붙잡고 있었습니다. 설정이 안 먹은 건가요? 함정힌트: 이 설정이 무엇의 상한인지 정확히 말해 본다

설정은 정상 동작한 것이다. lock_timeout은 트랜잭션 전체가 아니라 "락 획득 시도 하나"의 상한이기 때문이다. 한 트랜잭션에서 락을 네 번 잡으면 최악의 경우 3초 × 4 = 12초가 나온다 — 누적 상한이 아니다.

그래서 상한은 세 층에 건다 — ① lock_timeout(대기자) ＜ ② statement_timeout·@Transactional(timeout)·idle_in_transaction_session_timeout(보유자) ＜ ③ HikariCP connectionTimeout(마지막 방어선)

그리고 ①이 ③보다 길면 안 된다 — 락을 기다리는 요청이 아직 안 끝났는데 그 뒤에서 커넥션을 기다리던 요청이 먼저 실패하면, 피해가 가해보다 먼저 터져 원인 추적이 어려워진다.

참고로 실패 시 상태도 MySQL과 다르다 — PG는 55P03과 함께 트랜잭션 전체가 abort 상태가 되므로 반드시 ROLLBACK해야 하고, "그 문장만 실패하고 계속"은 불가능하다.

SELECT ... FOR UPDATE가 0행을 반환했습니다. 그럼 무엇이 잠긴 건가요? 함정힌트: "반환 행 = 잠긴 행"에 0을 대입해 본다

아무것도 잠기지 않았다. "반환 행 = 잠긴 행"이므로 0행 = 0개 잠금이다. PostgreSQL에는 갭 락이 없으므로 "없는 행"을 미리 찜해 둘 방법이 없다.

그래서 check-then-insert 패턴이 그대로 깨진다 — 두 트랜잭션이 동시에 "없네"를 확인하고 둘 다 INSERT하면 중복이다. FOR UPDATE는 이 경쟁에 대해 아무 보호도 제공하지 않는다.

MySQL(RR) 사용자가 가장 자주 헛디디는 자리다 — 거기서는 넥스트 키 락이 범위를 통째로 잠가 이 경쟁을 막아 주지만, PG에는 그 장치가 없다.

EXPLAIN (ANALYZE, BUFFERS)를 BEGIN … ROLLBACK으로 감싸라는 이유는?힌트: ANALYZE가 붙은 순간 무엇이 달라지는가

EXPLAIN만 붙이면 계획을 세우기만 하고 실행하지 않지만, ANALYZE가 붙으면 쿼리가 실제로 실행된다. FOR UPDATE가 붙어 있으면 실제로 락을 잡는다 — 운영 DB에서 무심코 치면 내가 장애의 원인이 된다.

그래서 BEGIN; … ROLLBACK;으로 감싸 락을 즉시 되돌린다. (회귀 테스트에서 EXPLAIN (FORMAT JSON)만 쓰는 이유도 같다 — ANALYZE가 없으면 잠그지 않는다.)

BUFFERS를 함께 요구하는 이유는 기간의 증빙이기 때문이다. LockRows의 actual rows가 폭을 증명하고, Buffers: shared hit이 "이 락을 잡기까지 페이지를 몇 장 읽었나" = 기간을 증명한다. PR에는 이 두 줄이면 충분하다.

한 줄 요약
PostgreSQL의 SELECT ... FOR UPDATE는 테이블에 ROW SHARE, 그리고 WHERE를 통과해 반환된 힙 튜플에만 행 락(튜플 헤더 xmax에 기록, 갭 락·인덱스 엔트리 락 없음)을 건다 — 반환 행 = 잠긴 행. 그래서 인덱스를 못 타도 테이블이 잠기지는 않지만, 잠근 채 스캔이 끝날 때까지의 기간이 늘어 같은 행 경쟁이 그 구간에 직렬화되고(커넥션 고갈은 이 경로로 온다), 스캔 시작 지점이 세션마다 달라 락 획득 순서가 어긋나면 데드락까지 나며, READ COMMITTED의 재평가로 후보 행마다 대기가 생기고, 조건이 넓으면 매치 행 전부가, 조인이면 모든 테이블이 잠기며, FOR UPDATE는 FK의 KEY SHARE와 충돌해 자식 INSERT까지 막고, 없는 행은 못 잠근다. 처방은 폭(등호 조건) → 기간(인덱스, 락 안 왕복 제거) → 강도(키 안 바꾸면 FOR NO KEY UPDATE) → 대기 정책(무한 대기를 막는 lock_timeout, 기다리지 않는 NOWAIT, 남의 것은 건너뛰고 작업 큐를 만드는 SKIP LOCKED) 순이고, 그것을 EXPLAIN의 LockRows·Buffers 증빙, 롤 단위 lock_timeout, pg_stat_activity + pg_blocking_pids·log_lock_waits 관측, 폭·강도·계획 회귀 테스트로 사람의 기억 밖에 고정한다.
