DB failover 중 애플리케이션 동작 — 인프라는 40초 만에 복구됐는데 앱은 왜 30분 동안 장애인가

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "DB 장애로 failover가 일어나는 동안 애플리케이션은 어떻게 동작해야 하나요?"
failover는 DB 쪽에서 끝나는 이벤트가 아니라 애플리케이션까지 이어지는 사슬이다. 다운 감지(헬스체크 간격 × 실패 임계) → 리플리카 승격(복제 지연분은 유실 가능 = RPO) → 엔드포인트 DNS 전환(TTL) → 앱 JVM의 DNS 캐시 만료, 여기까지가 "인프라 복구"다. 진짜 문제는 그 뒤에 있다 — 앱의 커넥션 풀은 여전히 죽은 프라이머리를 향한 소켓을 쥐고 있다. RST를 받은 커넥션은 다음 사용에서 에러가 나 풀이 알아서 갈아끼우지만, 조용히 죽은 반개방(half-open) 소켓은 socketTimeout이 없으면 read()에서 무한 대기하고, 구 프라이머리가 리플리카로 살아나면 쓰기마다 read-only 에러가 나는데 HikariCP는 그걸 끊을 사유로 보지 않는다. 커넥션이 하나씩 좀비가 되면 풀이 마르고 → 풀을 기다리는 톰캣 스레드가 마르고 → 헬스체크까지 죽는다. 이것이 "인프라는 복구됐는데 앱은 계속 장애"의 정체다. 대비는 설정과 코드로 고정한다: JDBC socketTimeout/connectTimeout, HikariCP connectionTimeout·validationTimeout·maxLifetime·keepaliveTime, JVM networkaddress.cache.ttl, read-only 에러를 evict 사유로 등록(SQLExceptionOverride), 멱등키가 있을 때만 쓰기 재시도, 서킷 브레이커로 빠른 실패, readiness에만 DB 체크, 정기 failover 훈련. 그리고 모든 안전망에는 대가가 있다 — 짧은 타임아웃은 긴 정상 쿼리를 죽이고(오탐·플래핑), 자동 재시도는 커밋 여부가 불명한 쓰기를 중복시키며, 읽기 전용 저하 모드는 쓰기 기능과 코드 복잡도를 맞바꾸고, 동기 복제(RPO 0)는 쓰기 지연과 가용성 결합을 치른다.
출제 의도 — "인프라가 복구를 해줘도 애플리케이션이 커넥션을 못 갈아타면 장애는 계속된다. '내 코드 밖에서 벌어지는 일'까지 책임 범위로 보는 시야를 확인한다."
두 문장이 각각 채점 지점이다. ⑴ "커넥션을 못 갈아타면" — DB 팀은 "failover 완료, 40초"라고 보고하는데 앱은 30분째 5xx. 이 간극이 어디서, 왜 생기는지를 TCP 소켓·DNS 캐시·커넥션 풀·스레드 풀의 사슬로 설명할 수 있는가. ⑵ "내 코드 밖까지 책임 범위로" — 헬스체크 간격, DNS TTL, 커널의 TCP 동작, 드라이버 기본값은 전부 내가 짠 코드가 아닌데 그 기본값이 내 서비스의 복구 시간을 결정한다. "인프라 문제라 우리 소관이 아니다"가 성립하지 않음을 알고, 설정과 코드로 안전망을 고정해 뒀는가.
약점 ①메커니즘 사슬

1. 큰 그림 — failover는 "DB 이벤트"가 아니라 앱까지 이어지는 사슬이다

이 절의 그림 하나를 통째로 머리에 넣는다. 면접에서 "failover 중 앱은 어떻게 되나요"를 받으면 위 레인을 왼쪽에서 오른쪽으로, 그 다음 아래 레인을 왼쪽에서 오른쪽으로 읽는 것이 답변이다. 비유 하나 — DNS는 전화번호부다. 지점이 이사하면 번호부는 갱신되지만, 이미 통화 중인 전화는 번호부를 다시 들춰보지 않는다. 풀 안의 커넥션이 그 "통화 중인 전화"다.

위 레인은 DB 팀의 RTO, 아래 레인은 앱의 RTO. 경계선(≈40초) 오른쪽은 인프라 입장에서 "정상"이지만, 앱 풀 안의 (b)(c)가 그 시간을 30분으로 늘린다.
암기 — 인프라 4단계 "감·승·전·캐" + 각 단계에서 시간이 어디에 쓰이고 무엇을 잃는가
①
감지 — 왜 즉시가 아닌가.감시자는 통보를 받는 게 아니라 주기적으로 찔러보고 판단한다. 1회 실패로 판정하면 긴 GC 멈춤·순간 네트워크 지연·I/O 스파이크가 전부 failover를 유발하므로 "N초 간격 × M번 연속 실패"를 기다린다. 이 대기가 RTO의 첫 조각이고, 짧게 잡을수록 오탐이 는다(§4-1).
②
승격 — 무엇을 잃는가.비동기 복제는 커밋을 클라이언트에 응답한 뒤 로그를 리플리카로 보낸다. 다운 직전 몇 초의 커밋은 클라이언트가 "성공"을 받았지만 리플리카에는 없다 → 승격되면 새 프라이머리의 역사에서 사라진다 = RPO ≠ 0. "최신 리플리카 고르기·따라잡을 때까지 대기"는 RTO를 늘려 RPO를 줄이는 선택. 구 프라이머리는 역사가 갈라지므로 리플리카로 재구성해 붙인다 — 이것이 (c) read-only 좀비를 만든다.
③
전환 — 왜 DNS이고 왜 지연되나.관리형 DB는 "클러스터 엔드포인트" DNS 이름의 CNAME이 가리키는 IP를 바꾼다. DNS는 push가 아니라 캐시 만료(pull) 모델이라 TTL이 끝날 때까지 리졸버는 구 IP를 준다 → 그래서 엔드포인트 TTL은 수 초로 짧다. VIP 이동이나 프록시(RDS Proxy·ProxySQL·PgBouncer·HAProxy)는 이 단계를 앱에서 숨기지만 새 병목·새 장애점이 된다(§4-5).
④
JVM 캐시 — DNS가 두 번 걸리는 이유.자바는 호스트명→IP 결과를 프로세스 안에 따로 캐시한다(InetAddress 캐시). 리졸버 TTL이 5초로 만료돼도 JVM이 자기 캐시를 안 비우면 새 커넥션은 계속 구 IP로 간다. 그리고 DNS는 새 커넥션을 맺을 때만 관여한다 — 이미 맺어진 소켓은 다시 DNS를 묻지 않는다. "TTL이 5초인데 왜 30분?"의 답은 DNS가 아니라 §1-2에 있다.

1-2. 앱 쪽에서 이어지는 사슬 — 풀 안 커넥션 세 부류

인프라가 복구된 시점에 앱의 풀 안에는 세 부류의 커넥션이 섞여 있다. 각 부류가 기본 설정에서 어떻게 되는지가 이 문항의 핵심이다. 외우는 말: "죽음을 알린 소켓 / 죽음을 안 알린 소켓 / 안 죽고 틀린 커넥션".

(a)는 좋은 죽음, (b)는 나쁜 죽음, (c)는 가장 교활하다. HikariCP의 isValid()는 "응답하나"만 묻고, evict 판정은 "SQLState가 08로 시작하나"만 본다 — (c)는 둘 다 통과한다.
부류어떻게 생기나다음 사용 시HikariCP 판정결과
(a) RST를 받은 것구 인스턴스가 소켓을 닫아줌(정상 종료·재시작)즉시 Communications link failure, SQLState 08S01evict → 새 커넥션 생성 → (DNS 갱신됐다면) 새 프라이머리로✅ 자가 치유
(b) 반개방상대가 소리 없이 사라짐(전원 차단·네트워크 단절)read()에서 응답 대기. socketTimeout 없으면 영원히반환이 안 되니 판정할 기회도 없음. 스레드 1개 소멸❌ 조용한 누수
(c) 살아 있는데 read-only구 프라이머리가 리플리카로 살아났고 그쪽에 붙어 있음 (또는 JVM 캐시 때문에 구 IP로 새로 붙음)SELECT는 멀쩡. INSERT/UPDATE만 MySQL 1290 / PG 25006SQLState ≠ 08 → evict 안 함 → 풀로 반환 → 다음 요청이 또 잡음❌ 좀비 (maxLifetime까지)
세 부류가 만드는 뒷사슬은 하나로 합쳐진다 — 이 줄을 한 호흡으로 (b) 스레드가 하나씩 갇힘 + (c) 쓰기가 계속 실패 → 풀 active = max, pending 누적 → 새 요청은 connectionTimeout(기본 30초) 동안 풀 앞에서 대기 — 톰캣 스레드를 쥔 채 → 톰캣 스레드 풀 고갈 → DB 무관 API·헬스체크까지 응답 불능 → LB 제외 / (liveness에 DB 체크면) 파드 재시작 → 재시작된 파드들이 동시에 풀을 채우며 새 프라이머리로 몰림 (connection storm) → 새 프라이머리 max_connections·CPU 압박 → 복구가 더 늦어짐
rationale의 문장을 메커니즘으로 번역하면
"DB가 죽어서 앱이 죽었다"가 아니다. DB는 40초 만에 살아났고, 앱은 자기가 쥔 소켓과 자기 설정의 기본값 때문에 계속 죽어 있었다.

1-3. 왜 반개방 소켓은 조용히 스레드를 먹나 — TCP 메커니즘

TCP는 "연결이 살아 있다"를 상대의 명시적 통보(FIN/RST)로만 안다. 통보 없이 사라지면 내 쪽 소켓은 아무 일 없다는 듯 ESTABLISHED로 남는다 — 이것이 반개방(half-open)이다. 비유: 상대가 전화를 끊지 않고 그냥 전원이 꺼졌다. 내 수화기는 "통화 중"이고, "여보세요?"에 답이 없는데 끊기지도 않는다. 여기서 앱 스레드가 빠져나올 경로는 셋뿐인데, 기본값에서는 셋 다 사실상 닫혀 있다.

출구 1재전송 포기

보낸 데이터에 ACK가 안 오면 커널이 재전송을 반복하다 포기하고 에러를 올린다. 리눅스 기본(tcp_retries2)으로 십수 분 단위.

  • 함정: "아직 ACK 못 받은 데이터가 있을 때만" 작동. 쿼리를 보내고 ACK까지 받은 뒤 서버가 죽었다면 재전송할 게 없어 이 경로는 아예 없다.
출구 2TCP keepalive

유휴 소켓에 주기적으로 탐침. 리눅스 기본은 2시간(tcp_keepalive_time=7200) 유휴 후 시작.

  • 함정: 드라이버 옵션으로 켜도 커널 값을 안 줄이면 2시간이다.
출구 3애플리케이션 타임아웃 = socketTimeout

드라이버가 read()에 SO_TIMEOUT을 걸어 그 시간 안에 응답이 없으면 예외. 이것만이 앱이 직접 쥔 시계다.

  • 함정: MySQL Connector/J와 pgjdbc 모두 기본값 0 = 무한.
@Transactional(timeout = n)·setQueryTimeout은 대체재가 아니다

쿼리 타임아웃은 대개 별도 스레드가 서버에 취소 요청을 보내는 방식이다. 서버가 죽었으면 취소 요청도 갈 곳이 없다. 반개방 소켓에서 스레드를 꺼내주는 건 socketTimeout뿐이다.

스레드 덤프에서 (b)를 알아보는 법

소켓 읽기 프레임(구형 JDK SocketInputStream.socketRead0, 신형 NioSocketImpl.park 계열)에서 멈춰 있고 상태는 RUNNABLE로 보여 "일하고 있는 것처럼" 읽힌다. 그 위에 드라이버의 결과 읽기(readPacket, receiveResponse)와 HikariProxyPreparedStatement.executeQuery가 있으면 확정.

1-4. 왜 DNS가 두 겹인가

JVM 캐시의 기본값은 환경에 따라 다르다 — 보안 관리자가 설치돼 있으면 영구, 없으면 구현별 기본(OpenJDK 계열은 30초). 컨테이너 베이스 이미지나 런타임 옵션에 따라 예상과 다를 수 있으므로 명시적으로 짧게 고정한다(§3-3).

2. failover 중 앱이 겪는 증상 8종 — 번호 암기 카드

번호와 한 줄 원인을 세트로 외운다. 면접에서 "어떤 증상이 나타나나요"는 이 목록을 순서대로 읊는 자리다. 그룹으로 묶으면 — 죽는 동안 1·2·3·4 (에러 → 멈춤 → 풀 → 스레드), 복구된 뒤 5·6·7 (쓰기만 실패 → 커밋 불명 → 유실), 그리고 8 재연결 폭풍.

1
Communications link failure / Connection reset / Broken pipe
죽는 동안 · §1-2 (a)
닫힌 소켓을 쓴 순간 난다. 일시적이고 스스로 낫는다. 이것만 보이면 운이 좋은 failover.
2
응답 없이 멈춤 (hang)
죽는 동안 · §1-2 (b)
에러도 로그도 없다. 스레드 덤프에 소켓 읽기에서 멈춘 스레드가 쌓인다. socketTimeout이 없다는 증거.
3
Connection is not available, request timed out after 30000ms
죽는 동안 · 풀 고갈
2번의 결과다. 이 스레드들은 피해자, 용의자는 2번 스레드들.
4

3-1. JDBC 타임아웃 — 드라이버 기본값은 "무한"이다

❌ before — 타임아웃이 하나도 없다
# MySQL Connector/J 기본: connectTimeout=0, socketTimeout=0
# → 둘 다 무한 대기
spring:
  datasource:
    url: jdbc:mysql://shop-cluster.cluster-xxxx.ap-northeast-2.rds.amazonaws.com:3306/shop
✅ after — 연결 수립과 응답 대기에 각각 상한 (MySQL: 밀리초)
spring:
  datasource:
    url: jdbc:mysql://shop-cluster.cluster-xxxx.ap-northeast-2.rds.amazonaws.com:3306/shop?connectTimeout=3000&socketTimeout=10000
    # connectTimeout=3000 — TCP 연결 수립 3초.
    #   죽은 IP로 SYN 보내고 무한정 기다리지 않는다
    # socketTimeout=10000 — 쿼리 하나의 응답 대기 10초.
    #   반개방 소켓에서 스레드를 꺼내주는 유일한 시계 (§1-3)
⚠ PostgreSQL(pgjdbc)은 단위가 "초"다 — MySQL 값을 그대로 옮기면 10000초(약 2.8시간)
spring:
  datasource:
    url: jdbc:postgresql://shop.internal:5432/shop?connectTimeout=3&socketTimeout=10&tcpKeepAlive=true
  • socketTimeout은 이 DataSource로 나가는 가장 긴 정상 쿼리보다 길어야 한다. 10초로 잡았는데 월말 정산 쿼리가 40초라면 매달 말 배치가 죽는다 → 배치·통계용 DataSource는 분리해 다른 타임아웃(§4-1).
  • URL 대신 spring.datasource.hikari.data-source-properties.socketTimeout: 10000으로 넘겨도 같다. 어느 쪽이든 코드 리뷰에서 보이는 곳에 둔다.

3-2. HikariCP — 기본값 넷을 바꾼다

❌ before — 풀 크기만 정하고 나머지는 기본값. 각 기본값이 failover에서 무슨 뜻인지:
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      # connection-timeout: 30000
      #   → 풀이 비면 30초 대기. 그동안 톰캣 스레드를 쥔다 (증상 3→4 전이)
      # validation-timeout: 5000
      #   → 대여 전 isValid() 검사에 최대 5초
      # max-lifetime: 1800000
      #   → 30분. 잘못 붙은 커넥션(§1-2 c)의 최대 수명 = "앱 장애 30분"의 30분
      # keepalive-time: 0
      #   → 꺼짐. 유휴 커넥션이 반개방이 돼도 다음 대여 때까지 모른다
✅ after
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      connection-timeout: 3000
        # 풀 대기 3초. 못 받으면 빨리 실패 → 톰캣 스레드를 돌려준다
      validation-timeout: 1000
        # 대여 직전 isValid() 상한. connection-timeout보다 반드시 짧게
      max-lifetime: 300000
        # 5분. 잘못 붙은 커넥션은 5분 안에 자연 교체. DB의 wait_timeout보다는 짧게
      keepalive-time: 60000
        # 1분마다 유휴 커넥션에 ping → 반개방을 사용 전에 발견해 조용히 교체
      exception-override-class-name: com.example.infra.db.ReadOnlyPrimaryEvictor   # §3-5
      # initialization-fail-timeout: -1
      #   (선택) 기동 시 DB에 못 붙어도 앱은 뜬다 → failover 중 재시작돼도 CrashLoop 안 감.
      #   대신 readiness가 트래픽을 막아줘야 한다 (§3-8)
암기 — 네 시계의 역할 분담을 한 문장으로: 순찰 → 관문 → 상한 → 최종 교체
유휴 중 순찰
keepaliveTime1분마다 유휴 커넥션에 ping. 반개방을 대여 전에 발견
유휴 → 대여 관문
validationTimeout대여 직전 isValid()의 상한. connectionTimeout보다 짧게
사용 중 상한
socketTimeout (JDBC)한 번의 read()가 기다릴 최대 시간. 유일하게 반개방을 끊는 시계
최종 교체 주기
maxLifetime모든 것이 실패했을 때의 보루. §3-5가 없으면 이 값이 곧 장애 시간

HikariCP는 커넥션이 일정 시간(짧은 우회 창) 이상 놀다가 대여될 때만 isValid()로 검사한다. 즉 검사는 사용 중에 죽은 커넥션을 못 잡고(그건 socketTimeout의 몫), 살아 있지만 read-only인 커넥션도 못 잡는다(isValid()는 "응답하나"만 본다). 그래서 §3-5가 따로 필요하다. maxLifetime 5분은 "장애 시 자연 치유 상한"과 "평시 재연결 비용" 사이의 타협값이지 정답이 아니다(§4-6).

3-3. JVM DNS 캐시 — 시스템 속성이 아니라 보안 속성이다

❌ before — 아무 것도 안 함 / 또는 -D로 넘겨서 조용히 무시됨
# 기본값이 환경마다 다르고(30초 또는 영구), 아무도 확인한 적 없다

# 흔한 실수 — 시스템 속성으로 넘긴다:
java -Dnetworkaddress.cache.ttl=5 -jar shop.jar
# → 보안 속성이라 이 플래그는 조용히 무시된다. 에러도 없다.
✅ after — 어떤 네트워크 호출보다 먼저, 진입점에서 고정
public static void main(String[] args) {
    java.security.Security.setProperty("networkaddress.cache.ttl", "5");           // 성공 캐시 5초
    java.security.Security.setProperty("networkaddress.cache.negative.ttl", "3");  // 실패(NXDOMAIN 등) 캐시 3초
    SpringApplication.run(ShopApplication.class, args);
}

// 대안 ② $JAVA_HOME/conf/security/java.security 를 이미지 빌드 시 덮어쓰기
// 대안 ③ 구형 호환 시스템 속성 -Dsun.net.inetaddr.ttl=5
// 셋 중 하나를 Dockerfile이나 진입점에 박아 배포 파이프라인이 보장하게 한다

이걸 해도 §1-2의 기존 커넥션 문제는 남는다. DNS TTL은 "새 커넥션이 어디로 가나"만 정한다.

3-4. 드라이버가 failover를 아는가 — DNS를 기다리지 않는 길

DNS 전환을 기다리는 대신 드라이버가 후보 호스트를 직접 확인하게 하면 ③④ 단계를 건너뛸 수 있다.

PostgreSQL — 후보를 나열하고 "쓰기 가능한 쪽"에만 붙으라고 지시
jdbc:postgresql://db-a.internal:5432,db-b.internal:5432/shop
    ?targetServerType=primary        # 접속 후 읽기 전용 여부를 확인해 프라이머리만 선택
    &hostRecheckSeconds=5            # 호스트 상태 캐시 5초 → failover 후 5초면 새 프라이머리
    &connectTimeout=3&socketTimeout=10
MySQL Connector/J — multi-host failover URL
jdbc:mysql://db-a.internal:3306,db-b.internal:3306/shop
    ?failOverReadOnly=true           # 기본값 true: 두 번째 호스트로 넘어간 커넥션은 읽기 전용
    &connectTimeout=3000&socketTimeout=10000

# autoReconnect=true 는 MySQL 문서가 권장하지 않는다 —
# 트랜잭션 상태를 모른 채 재접속해 §2-6의 불명 상태를 조용히 삼킨다
failOverReadOnly의 기본이 true인 이유 — 편의와 위험의 맞교환

이 기능은 원래 "프라이머리가 죽으면 리플리카에서 읽기라도 계속하라"는 용도다. 두 번째 호스트가 실제로 승격된 프라이머리라면 false로 바꿔야 쓰기가 되지만, 그러면 네트워크 분단으로 프라이머리가 살아 있는데 리플리카로 넘어간 경우 리플리카에 쓰기를 시도하게 된다(리플리카가 read_only면 1290으로 막히긴 한다). "자동으로 다른 호스트에 쓴다"는 편의는 "엉뚱한 곳에 쓸 위험"과 맞바꾼다.

✅ AWS Advanced JDBC Wrapper — 클러스터 토폴로지를 SQL로 직접 조회해 DNS 갱신을 기다리지 않는다 가산점
jdbc:aws-wrapper:postgresql://shop-cluster.cluster-xxxx.ap-northeast-2.rds.amazonaws.com:5432/shop?wrapperPlugins=failover

# 래퍼는 재시도를 대신 해주지 않는다. 예외로 "판단하라"고 알려줄 뿐:
#   SQLState 08S02 — 연결이 바뀌었다. 세션 상태를 다시 세팅하고 트랜잭션을 재실행하라
#   SQLState 08007 — 트랜잭션 도중이었다. 커밋됐는지 알 수 없다
# 그 판단이 §3-6이다. "커밋됐는지 모르는 상태"는 어떤 드라이버도 없애줄 수 없다 — 프로토콜 수준의 한계

3-5. read-only 프라이머리 감지 → 풀에서 쫓아낸다

❌ before — HikariCP 기본 판정만 믿는다
// HikariCP 기본 판정:
//   예외의 SQLState가 "08"로 시작(통신 실패) → evict
//   그 외 → 유지
// MySQL 1290 (SQLState HY000) → "그 외"
// PG 25006 → "그 외"
// → 커넥션은 멀쩡히 풀로 돌아가
//   다음 요청을 또 실패시킨다
//   maxLifetime(30분)까지
✅ after — "살아 있지만 쓰기가 안 되는" 커넥션을 evict 사유로 등록
package com.example.infra.db;

import com.zaxxer.hikari.SQLExceptionOverride;
import java.sql.SQLException;

public class ReadOnlyPrimaryEvictor implements SQLExceptionOverride {

    // (주의) 이 인터페이스의 중첩 enum 이름이 Override라 @Override 애노테이션과 겹친다.
    //        애노테이션을 생략하거나 @java.lang.Override로 쓴다.
    public Override adjudicate(SQLException e) {
        int code = e.getErrorCode();
        String state = e.getSQLState() == null ? "" : e.getSQLState();

        if (code == 1290 || code == 1836) {          // MySQL: --read-only 옵션 / read-only 모드
            return Override.MUST_EVICT;
        }
        if ("25006".equals(state)) {                 // PostgreSQL: read_only_sql_transaction
            return Override.MUST_EVICT;
        }
        return Override.CONTINUE_EVICT;              // 나머지는 HikariCP 기본 판정("08" 접두)에 맡긴다
    }
}
// 등록: spring.datasource.hikari.exception-override-class-name (§3-2)
// 비교적 최근 HikariCP에 들어온 인터페이스 — 사용 중인 버전에 있는지 확인
대안 — read-only 에러를 감지한 지점에서 풀 전체(또는 그 하나)를 소프트 리셋
// 유휴 커넥션은 즉시 폐기, 사용 중인 것은 반환되는 순간 폐기. 새 커넥션은 (DNS가 갱신됐다면) 새 프라이머리로.
hikariDataSource.getHikariPoolMXBean().softEvictConnections();

// 또는 문제의 커넥션 하나만
hikariDataSource.evictConnection(connection);
정밀도 vs 부작용

SQLExceptionOverride는 그 커넥션만 버리고, softEvictConnections()는 20개를 한 번에 버려 재연결 파도를 만든다. 대신 후자는 "구 프라이머리에 붙은 커넥션이 몇 개인지 모른다"는 불확실성을 한 방에 없앤다. failover 직후 한 번이라면 후자가 오히려 깔끔한 경우가 많다.

이 항목이 결정적인 이유

§3-1~3-4는 전부 "죽은 커넥션"을 다루고, 이것만이 "살아 있지만 틀린 커넥션"을 다룬다. 앞의 넷을 완벽히 해도 이게 없으면 §5의 30분은 그대로 온다(maxLifetime을 5분으로 줄였다면 5분).

3-6. 재시도 — "무조건"에서 "멱등 조건부"로

재시도는 안전망이면서 동시에 사고 원인이다. 어떤 조건에서 재시도하는지를 코드로 말한다. 먼저 왜 위험한지부터 — 타임아웃 하나에는 세 가지 결과가 숨어 있고 클라이언트는 셋을 구분할 수 없다.

암기 — 타임아웃의 삼거리
결과 ①
서버에 안 닿았음재시도 → 정상 삽입. 안 하면 유실
결과 ②
닿아서 커밋됐고 복제도 됨재시도 → 중복. 안 하면 정상
결과 ③
커밋됐지만 승격에서 유실재시도 → 정상 삽입. 안 하면 유실. 앱 로그엔 "성공"

이 삼거리를 없애는 유일한 방법이 멱등키다. 멱등키가 UNIQUE로 박혀 있으면 ②에서 재시도는 제약 위반으로 튕기고 그 충돌을 "이미 됐음"으로 읽으면 된다 — 세 경우 모두 안전. 멱등키가 없다면 재시도가 아니라 대조가 맞다.

❌ before — "DB 에러면 3번" 한 줄. 무엇을 재시도하는지 모른다

@Transactional
public Order placeOrder(PlaceOrderCommand cmd) {
    return orderRepository.save(Order.from(cmd));

// 2차: 새 프라이머리에 (복제됐다면) 이미 주문이 있음 → 같은 주문이 한 건 더 들어간다
// 그리고 20개 파드 × 3회 재시도가 동시에 새 프라이머리를 두드린다 (retry storm)
✅ after ① — 쓰기에 멱등키를 심는다. 이것이 없으면 뒤의 어떤 재시도 정책도 안전하지 않다

}
✅ after ② — 예외를 분류해 "재시도 / 대조 / 실패"를 가른다
public enum RetryDecision { RETRY, RECONCILE, FAIL }

public final class DbRetryPolicy {

    /** @param idempotent 이 작업을 두 번 실행해도 결과가 같은가 (읽기, 또는 멱등키가 있는 쓰기) */
    public static RetryDecision classify(Throwable t, boolean idempotent) {
        SQLException sql = unwrapSqlException(t);
        if (sql == null) return RetryDecision.FAIL;

        String state = sql.getSQLState() == null ? "" : sql.getSQLState();

        // 커밋 여부 불명 (표준 08007, AWS 래퍼의 TransactionStateUnknownSQLException 등)
        if ("08007".equals(state)) {
            return idempotent ? RetryDecision.RETRY : RetryDecision.RECONCILE;
        }
        // 연결 계열 실패(08xxx) / 소켓 타임아웃 — "요청이 서버에 닿았는지"부터 모른다
        if (state.startsWith("08") || sql instanceof java.sql.SQLTimeoutException) {
            return idempotent ? RetryDecision.RETRY : RetryDecision.RECONCILE;
        }
        // read-only 프라이머리 — 커넥션은 §3-5가 버린다. 요청은 다른 커넥션으로 재시도해도 된다
        // (실행 자체가 거부됐으므로 부분 적용 없음)
        if (sql.getErrorCode() == 1290 || sql.getErrorCode() == 1836 || "25006".equals(state)) {
            return RetryDecision.RETRY;
        }
        // 제약 위반·문법 오류·데드락 외 나머지 — 다시 해도 같은 결과
        return RetryDecision.FAIL;
    }
}
✅ after ③ — 정책을 적용하는 쪽. 멱등키 충돌은 "이미 됐다"로 해석한다
public Order placeOrderResilient(PlaceOrderCommand cmd) {
    int attempt = 0;
    while (true) {
        attempt++;
        try {
            return placeOrder(cmd);
        } catch (DataIntegrityViolationException dup) {
            // 멱등키 UNIQUE 충돌 = 앞선 시도가 실제로는 커밋돼 있었다 → 그 결과를 돌려준다 (중복 생성이 아니다)
            return orderRepository.findByIdempotencyKey(cmd.idempotencyKey()).orElseThrow();
        } catch (DataAccessException e) {
            RetryDecision d = DbRetryPolicy.classify(e, /* idempotent */ true);   // 멱등키가 있으므로 true
            if (d == RetryDecision.RETRY && attempt < 3) {
                backoffWithJitter(attempt);      // 지수 백오프 + 지터: 20개 파드가 같은 순간에 다시 몰리지 않게
                continue;
            }
            if (d == RetryDecision.RECONCILE) {
                reconciliationQueue.enqueue(cmd);  // 사람/보정 배치가 "실제로 커밋됐나"를 대조. 재시도로 뭉개지 않는다
            }
            throw e;
        }
    }
}
세 조각의 의존 관계

①이 없으면 ②의 idempotent=true가 거짓말이 되고, ②가 없으면 ③은 before와 같다. 면접에서 "재시도 하겠다"고 말했으면 반드시 "무엇이 멱등을 보장하는가"가 따라와야 한다. 멱등키를 UNIQUE 제약으로 고정하는 패턴은 UNIQUE 동시 INSERT작성 예정의 "DB가 마지막 심판"과 같은 뿌리다.

왜 필요한가를 사슬로 — 서킷이 없으면 failover 중 모든 요청이 connectionTimeout(3초) 또는 socketTimeout(10초)을 꽉 채운 뒤 실패한다. 초당 200요청이면 10초 동안 2,000개 스레드가 필요하다. 톰캣은 200개다. 서킷이 OPEN이면 요청은 즉시 실패하고 스레드는 즉시 돌아오고 헬스체크와 DB 무관 기능은 계속 응답한다. 새 프라이머리 쪽에서 봐도 좋다 — 재연결 폭풍 대신 HALF_OPEN의 탐침 5개만 온다.

3-8 ~ 3-11. 헬스체크 배치 · 저하 모드 · 관측 · 훈련

8헬스체크 배치 — liveness에 DB를 넣지 않는다

failover 중 DB 체크가 liveness에 있으면 §2-8이 확정된다: 프로세스는 멀쩡한데 DB가 아프다고 재시작 → 뜨자마자 또 실패 → CrashLoop → 재시작할 때마다 새 프라이머리로 커넥션 폭풍. readiness에만 넣어 "트래픽만 빼고 프로세스는 살아서 재연결을 시도"하게 한다. 판단 기준은 liveness/readiness 문서작성 예정 §3·§5.

9저하 모드 — "전부 아니면 전무"를 피한다
  • 쓰기 차단, 읽기 유지 — 기능 플래그 writes.enabled=false를 서킷 OPEN 이벤트나 운영자가 켠다. 쓰기 엔드포인트는 503과 안내 문구, 조회는 리플리카·캐시로 계속. 상품 목록은 보이고 주문 버튼만 잠기는 상태.
  • 지연 가능한 쓰기는 큐로 — 조회수·로그·알림은 큐/아웃박스에 쌓았다가 복구 후 흘려보낸다. 주문·결제처럼 즉시 확정이 필요한 쓰기는 안 된다 — "완료"를 말할 수 없으므로.
  • 캐시 응답에 시각 표시 — "3분 전 기준"과 함께 마지막 성공 응답.

무엇을 어느 모드로 내릴지는 장애 중에 정할 수 없다. 평시에 도메인별로 정해두고(§3-11에서 검증), 대가는 §4-3.

10관측 — 30분 뒤가 아니라 30초 뒤에 알게
  • 풀 메트릭 — hikaricp.connections.pending·.acquire·.timeout·.active. failover 중 active=max, pending↑, timeout↑이 기본 파형이고, DB가 복구됐다는데 active가 안 내려오면 §1-2 (b).
  • 에러 분류 카운터 — SQLState 앞 두 자리(08=연결, 25=트랜잭션 상태, 40=직렬화/데드락)와 벤더 코드(1290/1836)로 나눠 센다. 1290이 failover 완료 알림 뒤에도 0이 안 되면 §1-2 (c) — 이 카운터 하나가 §5의 30분을 30초로.
  • 톰캣 스레드 사용률 — tomcat.threads.busy가 max에 붙으면 §2-4 진입. 풀 메트릭보다 이게 먼저 알람이면 순서가 잘못된 것.
  • 합성 쓰기 체크 — 1분마다 하트비트 테이블에 UPDATE 한 건. 읽기가 아니라 쓰기여야 (c)를 잡는다. 이 값이 "앱 기준 failover 완료 시각".

4. 트레이드오프 — 모든 안전망에는 대가가 있다

고난이도에서는 "이렇게 하면 됩니다"가 아니라 "이렇게 하면 이걸 얻고 저걸 잃습니다"가 답이다. 각 항목을 얻는 것 → 잃는 것 → 그래서 어디에 선을 긋나 세 박자로 말한다. 편익만 말하면 감점, 대가까지 말하면 통과, 선 긋는 법까지 말하면 시니어다.

1짧은 타임아웃 · 예민한 헬스체크
얻는 것
빠른 감지, 짧은 RTO. 반개방 스레드가 3초 만에 풀려난다.
잃는 것
오탐 — 월말 정산 쿼리도 3초에 죽는다. 헬스체크 1초 간격 1회 실패면 2초짜리 GC 멈춤이 failover를 유발하고, failover 자체가 수십 초의 쓰기 불가를 만들므로 오탐 한 번 = 진짜 장애 한 번. 예민할수록 "죽었다→살았다→죽었다" 플래핑도 는다.
선 긋기
타임아웃은 워크로드별로 분리 — 온라인 DataSource socketTimeout=10s, 배치·통계는 별도 DataSource에 600s. 같은 풀에 섞으면 한쪽을 반드시 희생. 헬스체크 임계는 "감수할 수 있는 최대 정상 멈춤(GC·I/O 스파이크)보다 조금 길게", 값은 실측(GC 로그·p99)에서.
2자동 재시도
얻는 것
순단 흡수, 사용자 무인지.
잃는 것
커밋 불명 쓰기의 중복 — 타임아웃의 삼거리(§3-6)를 클라이언트는 구분 못 한다. 재시도하면 ②에서 중복, 안 하면 ①③에서 유실. 재시도 폭풍 — 20개 파드 × 200 TPS × 3회가 같은 순간 새 프라이머리를 두드리면 겨우 승격된 DB가 다시 넘어진다.
선 긋기
읽기는 자유롭게, 쓰기는 멱등키가 있을 때만, 불명(08007·타임아웃)은 멱등 아니면 대조 큐로. 지수 백오프 + 지터 + 서킷 브레이커 없는 재시도는 장애 증폭기. 재시도 총량에 예산을 두고 서킷 OPEN이면 재시도도 안 한다.
3읽기 전용 저하 모드
얻는 것
전면 장애를 "주문만 안 되는 상태"로 축소.
잃는 것
① 쓰기 기능 상실 자체 — 그 시간의 주문은 없다. 비즈니스가 "차라리 느리더라도 받아라"를 원할 수 있고, 그건 기술이 정할 일이 아니다. ② 코드 복잡도 — 모든 쓰기 경로가 모드를 확인해야 하고, "읽기처럼 보이지만 쓰는" 경로(로그인 시 마지막 접속 시각 갱신, 조회수 증가)가 모드를 뚫고 나가 에러를 만든다. ③ 전환 판단의 오탐 — 서킷이 순간 스파이크에 열리면 멀쩡한 DB를 두고 쓰기를 막는다.
선 긋기
저하 모드는 만든 날이 아니라 훈련한 날(§3-11)에 완성된다. 들어가는 조건은 failover 감지만큼 보수적으로, 나오는 조건은 자동보다 사람 확인이 안전한 경우가 많다.
4동기 / 반동기 복제 (RPO 0)
얻는 것
§1-1 ②의 유실 제거 — RPO 0에 근접.
잃는 것
모든 쓰기 지연에 네트워크 왕복이 더해짐, 그리고 더 중요하게 가용성 결합 — 리플리카가 느리거나 죽으면 마스터의 쓰기가 멈춘다. 리플리카를 둔 이유가 가용성이었는데 결합이 가용성을 깎는다. MySQL 반동기는 대기 상한 초과 시 비동기로 자동 강등 → "반동기를 켰으니 RPO 0"이 아니라 "평시 RPO≈0, 리플리카가 아플 땐 비동기". 반동기가 보장하는 건 "받았다"이지 "적용했다"가 아니라 읽기 일관성 문제는 그대로.
선 긋기
RPO 0이 진짜 요구라면 비용을 쓰기 지연으로 낼지, 공유 스토리지 구조로 낼지, 애플리케이션 대조(§3-6 RECONCILE)로 낼지 — 셋 중 하나는 반드시 낸다. "RPO 0이 정말 요구사항인가"를 비즈니스에 되묻는 것까지가 답.
5프록시 (RDS Proxy · ProxySQL · PgBouncer)
얻는 것
앱은 프록시와만 커넥션을 맺고 failover는 프록시가 흡수 — 앱 쪽 커넥션은 안 끊기고 진행 중 쿼리만 실패. §1-2 (b)(c)가 대부분 사라지고, 멀티플렉싱으로 파드 수 × 풀 크기가 DB에 그대로 닿는 문제(§2-8)도 완화.
잃는 것
홉 하나의 지연, 프록시 자체가 새 병목이자 장애점(프록시의 failover는 누가 하나), 세션 고정(pinning) — 세션 변수·임시 테이블·프리페어드 스테이트먼트를 쓰면 특정 백엔드 커넥션에 고정돼 멀티플렉싱 효과가 사라진다.
선 긋기
프록시를 뒀다고 §3-1·§3-6이 필요 없어지지 않는다 — 앱→프록시 소켓도 반개방이 될 수 있고, 프록시 뒤에서 실패한 쓰기의 커밋 여부는 여전히 불명. "프록시는 사슬의 DB 쪽 절반을 짧게 만들고, 앱 쪽 절반(타임아웃·멱등·서킷)은 그대로 우리 몫."
6짧은 maxLifetime · keepaliveTime
얻는 것
좀비의 최대 수명을 30분 → 5분으로. 반개방을 대여 전에 조기 회수.
잃는 것
커넥션 하나당 5분마다 재연결 비용(TCP + 인증 + TLS 핸드셰이크). 풀 20 × 파드 20 = 400개가 5분 주기로 다시 맺어진다. HikariCP가 만료 시각에 작은 편차를 줘 동시 만료는 피하지만 DB 접속 로그와 CPU에 주기적 파도. keepaliveTime 1분은 유휴에만 ping이라 비용이 작지만 0은 아니다.
선 긋기
"장애 시 허용 가능한 자연 치유 상한"에서 긋는다 — §3-5가 제대로 있으면 maxLifetime은 최종 보루일 뿐이므로 더 길어도 되고, §3-5가 없다면 maxLifetime이 곧 장애 시간이므로 짧아야 한다.

5. 실무 사례 — "failover는 40초 만에 끝났는데 쓰기가 30분 동안 간헐 실패"

상황

새벽에 관리형 DB의 writer 인스턴스가 장애로 failover. 인프라 알림은 "40초 만에 완료". 그런데 그 뒤 30분 동안 주문 API의 약 30%가 --read-only option 에러로 실패하고 나머지 70%는 정상. 조회 API는 100% 정상. 인프라 팀: "클러스터 정상, 새 writer 쓰기 가능 확인." 앱 팀: "코드 안 바꿨는데요."

메커니즘 사슬 — 이 순서로 말한다 failover 개시 → 구 writer 재기동 → 기존 커넥션 전부 RST (a) → HikariCP evict → 풀 재생성 → DNS는 이미 새 writer IP지만 JVM InetAddress 캐시(30초)엔 구 IP → 그 30초 안에 만든 20개 중 ~6개가 구 IP로 접속 → 구 인스턴스는 리플리카로 재구성, read_only=ON. 접속 성공, isValid() 통과 (c) → 6개로 나간 INSERT/UPDATE만 1290, SELECT는 성공 → "30% 간헐, 쓰기만" → SQLState HY000 → evict 안 함 → 풀로 반환 → 다음 요청이 또 잡음 → maxLifetime 30분 도달 → 6개 차례로 폐기·재생성 → DNS 갱신돼 새 writer → 자연 회복

회고에서 나온 문장

"인프라가 40초 만에 복구했다는 말은 맞았다. 앱이 30분 동안 복구하지 않았다는 말도 맞았다. 두 팀 다 자기 경계 안만 봤고, 사슬의 가운데 — 소켓·DNS 캐시·풀의 evict 판정 — 는 누구의 경계도 아니었다." 이 "누구의 경계도 아닌 구간"을 자기 책임으로 끌어오는 것이 rationale의 "내 코드 밖에서 벌어지는 일까지 책임 범위로 보는 시야"다.

6. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 답의 깊이가 갈리는 지점, 가산점은 알면 점수가 붙는 지점, 추가는 이 페이지에서 보탠 문항.

"failover가 끝났다는 알림을 받았는데 앱은 아직 에러입니다. 무엇부터 봅니까?"

증상의 모양으로 §1-2의 세 부류 중 어느 것인지 먼저 가른다.

  • 읽기·쓰기 모두 실패 + 풀 active가 max에 붙어 안 내려옴 + DB는 한가 → (b) 반개방. 스레드 덤프에서 소켓 읽기에 멈춘 스레드 확인. 즉효는 softEvictConnections() 또는 재시작, 근본은 socketTimeout.
  • 쓰기만, 그것도 일부만 실패 + 에러가 1290/25006 → (c) read-only 좀비. SHOW VARIABLES LIKE 'read_only'를 앱이 붙은 그 IP에서 확인. 즉효는 softEvictConnections(), 근본은 SQLExceptionOverride + DNS TTL.
  • Communications link failure가 계속 → DNS가 아직 구 IP를 주고 있거나(JVM 캐시 영구 설정 의심: dig는 새 IP인데 앱은 구 IP로 SYN), 새 프라이머리가 max_connections에 막혀 접속 거부 중(재연결 폭풍).

"재시작해보겠습니다"는 마지막 답이다. 재시작은 (b)(c)를 지우지만 원인도 같이 지워서 다음 failover에 그대로 재발한다. 재시작 전에 스레드 덤프와 SHOW PROCESSLIST를 남기는 것이 시니어의 순서다.

"socketTimeout을 몇 초로 잡을 건가요? 배치 쿼리는 그보다 긴데요."

하나의 값으로 답하지 않는다. DataSource를 워크로드별로 나눈다. 온라인 트랜잭션용은 "p99 쿼리 시간 × 여유 배수"(예: p99 300ms → 5~10초), 배치·통계용은 별도 DataSource(별도 HikariCP 풀)에 그 배치의 최장 실행 시간보다 긴 값. 같은 풀에 섞으면 §4-1의 오탐과 §1-3의 무한 대기 중 하나를 반드시 고른다. 덤으로 배치 풀 분리는 배치가 온라인 풀을 고갈시키는 것도 막는다.

그리고 socketTimeout은 "쿼리 하나의 응답"이 아니라 "소켓에서 한 번의 read()"의 상한임을 안다 — 결과가 스트리밍으로 계속 오는 대량 조회는 각 패킷 사이 간격이 10초를 안 넘으면 전체가 10분이어도 안 끊긴다.

"타임아웃으로 실패한 결제 INSERT를 재시도해도 되나요?" 시니어 변별

"멱등키가 있으면 예, 없으면 재시도가 아니라 대조." 이유를 삼거리로 — 타임아웃 하나에는 (1) 서버에 안 닿았음 (2) 커밋됐고 복제됐음 (3) 커밋됐지만 승격에서 유실됨이 숨어 있고 클라이언트는 구분 못 한다.

  • 멱등키가 UNIQUE로 박혀 있으면 (2)에서 재시도는 제약 위반으로 튕기고 그 충돌을 "이미 됐음"으로 읽으면 되며, (1)(3)에서는 정상 삽입 — 세 경우 모두 안전.
  • 멱등키가 없으면 (2)에서 이중 결제. 그때는 재시도 대신 결제 ID로 SELECT해 실제 상태를 대조하고, 대조도 안 되면(새 프라이머리에 없음 = (1) 또는 (3)) 사용자에게 "확인 중"을 보여주고 보정 큐로.

한 발 더 — (3)은 앱 로그에 "성공"으로 남아 있다. 로그와 DB를 대조하는 배치가 없으면 사용자가 신고할 때까지 모른다. "결제됐는데 주문이 없다"가 이 지점에서 이 문항과 만난다.

"RDS Proxy 같은 프록시를 두면 이 문제가 다 해결되나요?" 가산점

절반은. 프록시는 §1-2 (b)(c) — 앱이 죽은/틀린 백엔드 소켓을 쥐는 문제 — 를 앱 대신 처리하고, 재연결 폭풍(§2-8)도 흡수한다. 그래서 failover 중 앱이 보는 것은 "진행 중 쿼리 몇 개의 실패"로 줄어든다.

해결 안 되는 것: ① 커밋 여부 불명(§4-2) — 프록시 뒤에서 죽은 트랜잭션의 결과는 프록시도 모른다. 멱등키는 그대로 필요. ② 앱→프록시 소켓의 반개방 — socketTimeout은 그대로 필요. ③ 프록시 자체의 가용성과 세션 고정(§4-5).

정리 "프록시는 사슬의 DB 쪽 절반을 짧게 만들고, 앱 쪽 절반(타임아웃·멱등·서킷)은 그대로 우리 몫."

"복제를 동기로 바꾸면 데이터 유실은 없어지나요?" 가산점

"유실 확률을 줄이는 대신 쓰기 지연과 가용성 결합을 산다. 그리고 반동기는 타임아웃 시 비동기로 강등되므로 무조건 0도 아니다." §4-4를 그대로 말하되 마지막에 선택지를 셋으로 정리한다 — 쓰기 지연으로 내거나(동기 복제), 스토리지 구조로 내거나(공유 스토리지), 애플리케이션 대조로 내거나(멱등키 + 보정).

"RPO 0이 정말 요구사항인가"를 비즈니스에 되묻는 것까지가 답이다 — 대부분의 도메인은 "수 초의 유실을 사후 대조로 복구"가 "모든 쓰기가 느려짐"보다 싸다.

"failover 훈련은 어떻게 하나요?"

강제 failover 명령 한 줄과, 그 전후로 재는 숫자 셋. (1) 인프라 완료 시각 vs 앱 완료 시각(합성 쓰기 기준)의 차이 = 앱 RTO, (2) 그 사이 5xx 건수와 최대 지속 시간, (3) 재시작된 파드 수(0이 목표)와 1290/25006 카운터가 0으로 돌아온 시각.

스테이징에서 시작해 트래픽 낮은 시간대의 운영으로 넓히고, 드라이버·풀·JVM 설정을 바꿀 때마다 다시 잰다. 훈련이 잡아내는 전형적 결함: -D로 넘겨서 무시된 DNS TTL, 배치 풀에 온라인용 타임아웃, liveness에 남아 있던 DB 체크, 저하 모드를 뚫고 나가는 "읽기처럼 보이는 쓰기".

"HikariCP가 대여 전에 isValid()로 검사한다면서요. 그런데 왜 죽은/틀린 커넥션이 풀에 남나요?" 추가

검사가 보는 것과 시점이 둘 다 좁기 때문이다.

  • 시점 — HikariCP는 커넥션이 일정 시간 이상 놀다가 대여될 때만 검사한다. 사용 중에 죽은 커넥션(쿼리 보내고 응답 기다리는 중에 서버가 사라짐)은 검사 대상이 될 기회가 없다 → 그건 socketTimeout의 몫.
  • 내용 — isValid()는 "응답하나"만 본다. 구 프라이머리가 리플리카로 살아 있으면 응답은 잘 한다 → (c) read-only 좀비는 검사를 통과한다. 쓰기가 되는지는 SQLExceptionOverride(§3-5)나 합성 쓰기 체크(§3-10)로만 안다.

그래서 §3-2의 네 시계는 역할이 다르다 — keepaliveTime은 유휴 중 순찰, validationTimeout은 대여 관문, socketTimeout은 사용 중 상한, maxLifetime은 최종 교체. 어느 하나가 나머지를 대신하지 않는다.

"@Transactional(timeout = 5)를 걸어뒀는데 왜 반개방 소켓에서 스레드가 안 빠져나오나요?" 추가

쿼리 타임아웃은 "서버에게 취소를 부탁하는" 구조이기 때문이다. @Transactional(timeout)과 Statement.setQueryTimeout은 대개 별도 스레드가 서버에 취소 요청(KILL QUERY 류)을 보내는 방식으로 구현된다. 서버가 죽었거나 네트워크가 끊겼으면 그 취소 요청도 갈 곳이 없고, 원래 스레드는 여전히 read()에 있다.

반개방 소켓에서 스레드를 꺼내는 건 내 쪽 커널에 건 시계 — 드라이버의 socketTimeout(SO_TIMEOUT)뿐이다. 둘은 대체 관계가 아니라 보완 관계다: 쿼리 타임아웃은 "살아 있는 서버의 느린 쿼리"를, socketTimeout은 "사라진 서버"를 다룬다.

"PostgreSQL로 옮기면서 URL에 socketTimeout=10000을 그대로 넣었습니다. 문제가 있나요?" 추가

단위가 다르다. MySQL Connector/J는 밀리초, pgjdbc는 초다. socketTimeout=10000은 PG에서 10,000초 ≈ 2.8시간 — 사실상 무한과 같다. PG는 connectTimeout=3&socketTimeout=10&tcpKeepAlive=true처럼 초 단위로 쓴다(§3-1).

면접 포인트는 "값을 안다"가 아니라 "단위까지 말한다"다. 이런 실수는 코드 리뷰로는 안 잡히고 §3-11 훈련에서만 잡힌다 — 그래서 훈련이 체크리스트 11번이다.

"-Dnetworkaddress.cache.ttl=5를 JVM 옵션에 넣었는데 failover 때 여전히 구 IP로 붙었습니다. 왜죠?" 추가

networkaddress.cache.ttl은 시스템 속성이 아니라 보안 속성이라 -D로 넘기면 조용히 무시된다. 에러도 경고도 없다. 코드에서 java.security.Security.setProperty(...)로 넣거나, $JAVA_HOME/conf/security/java.security를 이미지 빌드 시 덮어쓰거나, 구형 호환 시스템 속성 -Dsun.net.inetaddr.ttl=5를 쓴다(§3-3).

그리고 이걸 고쳐도 이미 풀에 있는 커넥션은 그대로다 — DNS TTL은 "새 커넥션이 어디로 가나"만 정한다. "DNS를 고쳤는데 왜 아직?"의 답은 §1-2 (b)(c)에 있다.

"read-only 에러가 나면 softEvictConnections()로 풀을 통째로 비우면 되지 않나요? 왜 SQLExceptionOverride까지 만드나요?" 추가

정밀도와 부작용의 맞교환이다. SQLExceptionOverride는 그 커넥션 하나만 버린다 — 재연결 파도 없이 좀비만 골라낸다. softEvictConnections()는 20개를 한 번에 버려 재연결 파도(TCP + 인증 + TLS × 20 × 파드 수)를 만들지만, "구 프라이머리에 붙은 커넥션이 몇 개인지 모른다"는 불확실성을 한 방에 없앤다.

선 긋기: 평시 안전망은 SQLExceptionOverride(자동·정밀), failover 직후 운영자의 즉효 조치는 softEvictConnections()(한 번이라면 파도를 감수할 만하다). 그리고 후자는 DNS가 이미 갱신돼 있어야 의미가 있다 — 아니면 새 커넥션이 다시 구 IP로 간다(§1-4).

"저하 모드에서 '읽기처럼 보이지만 쓰는 경로'가 뭔가요? 왜 문제가 되나요?" 추가

GET 요청 뒤에 숨은 UPDATE다. 로그인 시 "마지막 접속 시각" 갱신, 상품 상세 조회 시 조회수 +1, 알림 목록 조회 시 "읽음" 처리, 세션 터치 — 사용자와 코드 모두 "조회"라고 생각하지만 DB에는 쓰기가 나간다.

저하 모드가 "쓰기 엔드포인트만 503"으로 설계돼 있으면 이 경로들은 모드를 뚫고 나가 read-only 프라이머리에 쓰기를 시도하고 조회 화면 자체가 500으로 죽는다 — "읽기는 살린다"던 저하 모드가 읽기를 죽인다. 대책은 이런 쓰기를 미리 찾아 (1) 큐/아웃박스로 지연시키거나 (2) 모드에서 예외 처리하거나 (3) 실패해도 조회를 살리는 try-catch로 감싸는 것. 이걸 장애 중에 찾을 수는 없으므로 §3-11 훈련에서 미리 터뜨린다.

"그냥 파드를 재시작하면 (b)(c) 다 사라지는 거 아닌가요?" 추가

사라진다. 원인과 증거도 같이. 재시작은 풀을 새로 만드니 (b)(c)는 지워지지만, 다음 failover에 그대로 재발한다. 그리고 세 가지 부작용이 있다.

  1. 증거 소멸 — 스레드 덤프(소켓 읽기에 멈춘 스레드), SHOW PROCESSLIST, 어느 IP에 붙어 있었는지가 사라진다. 재시작 전에 남긴다.
  2. CrashLoop 위험 — HikariCP는 기동 시 첫 커넥션을 못 만들면 앱 기동을 실패시킨다(initializationFailTimeout 기본 양수). failover가 끝나기 전에 재시작하면 뜨지도 못한다(§2-8).
  3. connection storm — 파드 20개가 동시에 풀 20개씩을 새 프라이머리에 맺으면 겨우 승격된 DB의 max_connections·CPU를 압박해 복구를 더 늦춘다.

그래서 순서는 증거 보존 → 국소 조치(softEvictConnections()) → 그래도 안 되면 순차 재시작이고, 근본은 §3의 설정을 코드에 박아 다음엔 재시작이 필요 없게 만드는 것이다.

한 줄 요약
failover는 다운 감지 → 승격(복제 지연분 유실 = RPO) → DNS 전환(TTL) → JVM DNS 캐시까지가 인프라의 일이고, 그 뒤 앱의 풀에 남은 반개방 소켓(socketTimeout 없으면 무한 대기 → 풀 고갈 → 스레드 고갈)과 살아 있지만 read-only인 좀비 커넥션(isValid() 통과, HikariCP는 evict 안 함, maxLifetime 30분까지 생존)이 "인프라는 복구됐는데 앱은 계속 장애"를 만든다 — 대비는 JDBC socketTimeout · HikariCP connectionTimeout/maxLifetime/keepaliveTime · JVM networkaddress.cache.ttl · SQLExceptionOverride로 read-only evict · 멱등키 조건부 재시도 · 서킷 브레이커 · readiness 전용 DB 체크 · 정기 failover 훈련으로 코드에 고정하되, 짧은 타임아웃은 오탐을, 자동 재시도는 커밋 불명 쓰기의 중복을, 저하 모드는 쓰기 기능과 복잡도를, 동기 복제는 지연과 가용성 결합을 대가로 치른다는 양면까지 한 호흡에 말하는 것이 이 문항의 답이다.
