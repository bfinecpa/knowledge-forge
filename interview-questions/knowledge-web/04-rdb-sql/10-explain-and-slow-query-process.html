실행 계획 읽기와 느린 쿼리 개선 프로세스
견적서(cost·rows)를 읽고, 청구서(actual·Buffers)로 검증하고, 사이클을 팀 자산으로 고정한다

면접 질문: "실행 계획(EXPLAIN)을 어떻게 읽나요? 느린 쿼리를 발견했을 때의 개선 프로세스를 설명해주세요."

핵심 관전 포인트 — EXPLAIN은 플래너가 통계를 보고 쓴 "견적서"(추정)이고, EXPLAIN (ANALYZE, BUFFERS)는 실제로 실행해 받은 "청구서"(실측)다. PostgreSQL의 계획은 표가 아니라 트리이고, 실행은 들여쓰기가 깊은 안쪽에서 시작해 바깥으로 올라오며, 노드마다 견적(cost= rows= width=)과 청구서(actual time= rows= loops=)가 나란히 찍힌다. 읽는 순서는 ① 모양(안쪽·아래부터 실행, 조인 노드의 첫 자식이 outer) → ② 노드 이름(Seq Scan은 전부 읽은 것, Index·Bitmap 계열은 좁힌 것 — 단 Index Cond 없는 Index Scan은 전수 조사) → ③ 추정 rows vs 실제 rows(자릿수가 다르면 튜닝이 아니라 통계가 먼저 — 1순위 진단) → ④ Buffers(느린 이유가 I/O인지 CPU인지를 가른다) → ⑤ 경고등(Rows Removed by Filter·external merge·Batches > 1·Heap Fetches·안쪽 loops)이다. 느린 쿼리 개선은 "인덱스 추가해봄 → 빨라짐"이 아니라 측정(pg_stat_statements로 가장 비싼 쿼리를 숫자로) → 가설(비용이 새는 지점을 힙 랜덤 I/O 사슬로) → 검증(같은 파라미터의 실측 + 부작용까지 양면으로) → 고정(auto_explain·쿼리 수 단정 테스트·pg_stat_statements 기준선을 설정과 코드로)의 사이클이며, 마지막 "고정"까지 가야 한 사이클이 끝난 것이다.
  • 1
    두 도구는 견적서와 청구서다 — EXPLAIN은 통계로 추정한 계획이라 실행하지 않고, EXPLAIN (ANALYZE, BUFFERS)는 실제로 실행해 actual과 Buffers를 붙여 준다. 첫 진단은 견적서로, 추정과 현실의 괴리 확인과 개선 전후 비교는 청구서로 한다.
  • 2
    트리는 다섯 단계 순서로 읽는다 — 모 · 이 · 행 · 버 · 경 — 모양(안쪽부터 실행, 첫 자식이 outer) → 노드 이름(전부 읽었나 좁혔나) → 행 수(추정 vs 실측, 자릿수가 다르면 튜닝이 아니라 통계 교정이 먼저) → 버퍼(I/O 병목인지 CPU 병목인지) → 경고등(Rows Removed by Filter·스필·loops).

0. 질문 + 출제 의도

질문: "실행 계획(EXPLAIN)을 어떻게 읽나요? 느린 쿼리를 발견했을 때의 개선 프로세스를 설명해주세요."

관련 질문: "잘 돌던 쿼리의 실행 계획이 어느 날 갑자기 바뀌어 느려졌습니다. 가능한 원인과 대응은?" / "ORDER BY가 인덱스를 타는 조건은? 계획에 Sort 노드가 남는 건 언제이고, Sort Method: external merge는 왜 문제인가요?"

출제 의도: 느린 쿼리 개선을 "인덱스 추가해봄 → 빨라짐"이 아니라 측정 → 가설 → 검증의 사이클로 수행하는지. 프로세스를 묻는 이유는 이 능력이 쿼리를 넘어 모든 성능 문제에 이식되기 때문이다.

이 문항은 두 겹이다 겉은 "PostgreSQL 계획 트리의 노드와 숫자를 읽을 줄 아는가"(인출 테스트)이고, 속은 "성능 문제를 재현 가능한 절차로 다루는가"(태도 테스트)다. 인덱스 하나 추가해서 빨라진 경험은 누구나 있다. 면접관이 가르고 싶은 것은 그 경험을 왜 빨라졌는지 Buffers 숫자로 설명하고, 다음에 같은 문제가 재발하지 않도록 무엇을 남겼는가까지 말하는 사람이다.
이 페이지가 겨냥하는 약점 세 가지 ① 계획을 "본다"고 하지만 눈이 어디로 갈지 모르는 것 → 2·3절에서 실행 순서(안쪽 → 바깥)와 다섯 단계 읽기 순서를 카드로 고정한다.
② Index Scan이 찍혔으니 됐다고 안심하는 것 → 3·4절에서 판별은 노드 이름이 아니라 Rows Removed by Filter와 Buffers임을 못 박고, 5절에서 오추정 하나가 조인 방식을 통째로 틀리게 만드는 계획 두 벌을 실측으로 본다.
③ 개선을 "고쳤다"에서 끝내는 것 → 6~10절에서 측정·가설·검증·고정을 하나의 사이클로 밟고, 특히 고정(설정·테스트·파이프라인 3층)에 가장 큰 지면을 쓴다.

1. 견적서와 청구서 — 두 도구의 분업

1-1. 플래너는 데이터를 세지 않는다 — 통계로 추정한다

플래너(planner)는 PostgreSQL에서 "이 SQL을 어떤 순서로, 어떤 방법으로 실행할지"를 정하는 부품이다. 이름 그대로 계획을 세우는 자리이고, 실행은 그다음 단계인 익스큐터(executor)가 한다.

플래너가 계획을 세울 때 실제 데이터를 세어보지는 않는다. 100만 행짜리 테이블에서 "status = 'ACTIVE'인 행이 몇 개냐"를 매번 세면 그 자체가 쿼리 한 번 값이기 때문이다. 대신 미리 모아 둔 통계를 본다. 그 통계를 모으는 명령이 ANALYZE이고, 테이블에서 표본을 뽑아 분포를 요약해 시스템 카탈로그 pg_statistic에 저장한다(사람이 읽는 뷰가 pg_stats). autovacuum이 백그라운드에서 주기적으로 이 일을 대신 돌려 준다.

1-2. 통계에 무엇이 들어 있나 — 추정의 재료

플래너가 "몇 행이 나올까"를 계산할 때 쓰는 재료들. 이 재료가 낡으면 5절의 사고가 난다.

1-3. 옵션 고정 — 이 문서가 계속 쓰는 조합은 하나다

실무에서 사실상 기본 조합은 EXPLAIN (ANALYZE, BUFFERS) 하나다. 나머지는 상황별 추가 옵션.

ANALYZE라는 이름은 두 가지로 쓰인다 — 이름만 같고 하는 일이 다르다

단독 명령 ANALYZE orders;

통계를 수집하는 명령. 표본을 다시 뽑아 pg_statistic을 갱신한다. 계획을 보여주지 않는다.

옵션 EXPLAIN (ANALYZE) SELECT …

쿼리를 실제로 실행해 실측을 붙이라는 옵션. 통계를 갱신하지 않는다.

5절의 처방이 "ANALYZE orders;를 돌린다"인데 "EXPLAIN ANALYZE를 한 번 더 떠본다"로 잘못 알아듣는 사고가 여기서 나온다. 실행 몇 번 더 해봐야 통계는 그대로다.

1-4. ANALYZE는 진짜로 실행한다 — 변경문에 붙이면 데이터가 바뀐다

"실제로 실행한다"는 말은 비유가 아니다. 데이터를 바꾸는 문에 붙이면 데이터가 진짜로 바뀐다.

bad 되돌릴 방법이 없는 한 줄
-- EXPLAIN: 실행하지 않는다. 운영 DB에서도 안전하다.
EXPLAIN UPDATE orders SET status = 'CANCELED' WHERE user_id = 100;
-- 계획만 출력된다. orders의 데이터는 하나도 바뀌지 않았다.

-- EXPLAIN (ANALYZE): 실측을 붙이려고 "실제로 실행"한다 = UPDATE가 진짜 일어난다.
EXPLAIN (ANALYZE) UPDATE orders SET status = 'CANCELED' WHERE user_id = 100;
-- 계획도 나오고, 주문 4,720건의 status도 진짜로 바뀐다. 되돌릴 방법이 없다.
good 변경문은 반드시 트랜잭션으로 감싸고 롤백한다
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE orders SET status = 'CANCELED' WHERE user_id = 100;
ROLLBACK;   -- 계획과 실측은 이미 손에 들어왔고, 데이터 변경만 취소된다

BEGIN … ROLLBACK이 되돌리지 않는 네 가지 — 락 · 시 · 트 · 왈

락
행 락은 ROLLBACK 시점까지 유지된다. UPDATE가 건드린 4,720행은 그동안 다른 트랜잭션의 갱신을 막는다 — 운영 프라이머리에서 대량 UPDATE를 이렇게 재보면 그 자체가 장애가 될 수 있다.
시퀀스
nextval()은 롤백해도 되돌아가지 않는다(동시성을 위해 의도된 동작). INSERT를 재보면 ID에 구멍이 생긴다.
트리거
트리거가 실제로 발화한다. DB 안에서만 일한다면 함께 롤백되지만, 외부로 나가는 부수효과(다른 시스템 호출 등)는 되돌아오지 않는다.
WAL
WAL이 실제로 쌓인다. 롤백해도 이미 기록된 WAL은 남으므로 복제 지연과 디스크를 건드린다.
그래서 원칙은 읽기 레플리카나 운영 규모 스테이징에서 돌리는 것

2. 계획은 표가 아니라 트리다 — 실행 순서와 노드 한 줄 해부

처음 EXPLAIN 출력을 보면 화살표와 들여쓰기가 뒤엉킨 덩어리로 보인다. 여기에는 규칙이 셋뿐이다.

① 한 줄이 노드 하나다
노드는 "스캔 하나, 조인 하나, 정렬 하나" 같은 작업 단위이고, 노드마다 자기 이름(Seq Scan, Sort, Nested Loop…)이 있다.
② 들여쓰기가 깊을수록 자식이다
->로 시작하며 한 단계 더 들어간 줄들이 바로 위 노드의 자식이다. 자식이 만든 행을 부모가 받아 처리한다.
③ 실행은 가장 안쪽에서 시작해 바깥으로
맨 위 줄이 마지막에 끝나는 노드다. 그리고 조인 노드의 첫 번째 자식이 outer(드라이빙, 바깥 루프), 두 번째가 inner다.

세 번째가 핵심이다. 출력은 위에서 아래로 인쇄되지만 실행 순서는 아래에서 위로 간다. 그래서 "무엇이 먼저 일어났나"를 알려면 눈을 맨 아래·맨 안쪽에 두고 올라와야 한다.

2-1. 노드 한 줄 해부 — cost · rows · width, 그리고 그 옆의 실측

노드 줄의 괄호 안 숫자를 하나씩 뜯는다. ANALYZE를 켜면 괄호가 두 개가 되고, 두 번째가 실측이다.

읽기 한 노드에 붙는 모든 숫자
 Index Scan using idx_orders_user on orders o
        (cost=0.56..61893.40 rows=4800 width=32)          <- 견적서 (EXPLAIN이 늘 주는 것)
        (actual time=0.071..283.917 rows=4720 loops=1)    <- 청구서 (ANALYZE를 켰을 때만)
   Index Cond: (user_id = 100)                            <- 인덱스 안에서 걸러진 조건
   Filter: (status = 'ACTIVE'::text)                      <- 힙에서 행을 가져온 "뒤에" 검사한 조건
   Rows Removed by Filter: 42495                          <- 힙 I/O를 이미 낸 뒤에 버린 행 수 (ANALYZE일 때만)
   Buffers: shared hit=5412 read=41856                    <- 읽은 페이지 수 (BUFFERS일 때만)
cost=시작..전체
앞이 시작 비용(첫 행을 내보내기 전까지), 뒤가 전체 비용(끝까지). 둘을 나눠 놓은 이유는 LIMIT 때문이다 — Sort는 입력을 전부 읽어야 첫 행이 나오므로 시작 비용이 크고, Index Scan은 거의 0이다. "앞 20건만 필요한" 쿼리에서는 시작 비용이 작은 계획이 이긴다.
rows=
이 노드가 내보낼 것으로 추정한 행 수. 헷갈리기 쉬운 지점 — 이 수는 노드의 조건(Index Cond·Filter)을 모두 적용한 뒤의 수다. "인덱스에서 몇 개를 꺼냈나"가 아니라 "부모에게 몇 개를 올려보내나"다.
width=
그 행 하나의 평균 바이트. SELECT *로 큰 text·jsonb 컬럼을 끌고 다니면 여기가 커진다. rows × width가 대략의 메모리 요구량이라 Sort 노드 아래에서 특히 의미가 있다.
actual time=첫행..마지막행
밀리초 단위 실측. 앞이 첫 행이 나온 시각, 뒤가 마지막 행이 나온 시각이며, 둘 다 이 노드가 시작된 뒤로 경과한 시간이다.
actual rows= / loops=
실제로 내보낸 행 수 / 이 노드가 몇 번 반복 실행됐나. 여기에 큰 함정이 있다 — 아래 함정 카드.
Rows Removed by Filter
Filter에 걸려 버려진 행은 이미 힙 랜덤 I/O 비용을 지불한 뒤에 버려진 행이다. 그 수가 이것이고, "많이 읽고 대부분 버린다"의 계산서다.

actual time과 actual rows는 loops당 평균값이다 — 총량을 보려면 × loops

오독

  (actual time=0.003..0.003
   rows=1 loops=4720)

"조인은 0.003ms밖에 안 걸리네?"

제대로

한 번에 0.003ms, 이걸 4,720번.
0.003 × 4720 ≈ 14ms
읽은 페이지도 이미 누적돼 있다:

(한 번에 4페이지 × 4,720번)

병렬 계획도 같은 규칙이다 — Parallel Seq Scan의 loops는 리더 + 워커 수이고 rows는 프로세스당 평균이다. 5절의 41초짜리 쿼리에서 39초가 이 곱셈에 숨어 있다.

cost=64273은 64초라는 뜻이 아니다 — 단위는 밀리초가 아니라 상대값

seq_page_cost = 1.0(순차로 읽은 페이지 한 장)을 1로 잡은 상대값이다. 그래서 cost=64273은 "대략 순차 페이지 6만 4천 장어치 일"이라는 뜻이다.

같이 보는 파라미터가 random_page_cost(기본 4.0)로 "랜덤하게 흩어진 페이지 한 장은 순차 네 장 값"이라는 선언이다 — 회전 디스크 시절의 값이라 SSD면 1.1 근처로 낮춰야 플래너가 인덱스를 제값에 평가한다.

2-2. Index Cond vs Filter — 낭비의 층이 다르다

Index Cond — 인덱스 안에서 걸린 조건

인덱스 컬럼에 대한 조건. 구간을 좁히는 조건(액세스 조건)과, 구간은 못 좁히고 인덱스 안에서 걸러내기만 하는 조건이 여기 함께 찍힌다.

낭비의 층 — 인덱스 안에서 훑고 버린 양. 흔적은 Buffers의 과다.

Filter — 힙에서 읽은 "뒤에" 걸린 조건

인덱스에 없는 컬럼의 조건. 힙에서 행을 읽은 뒤에 검사한다 — 버릴 행에 힙 랜덤 I/O를 이미 지불한 상태.

낭비의 층 — 힙까지 읽고 버린 양. 흔적은 Rows Removed by Filter.

PostgreSQL 고유의 함정 — "몇 번째 컬럼까지 썼나"를 알려주는 칸이 없다 함정 복합 인덱스 (user_id, status, created_at)에서 가운데 status 조건이 빠지면 created_at은 구간을 못 좁히고 인덱스 안에서 하나씩 걸러지는데, 계획 텍스트는 완전히 좁힌 경우와 똑같이 보인다. MySQL의 key_len에 해당하는 칸이 PostgreSQL에는 없다.
함정 Index Cond에 찍혀 있지만 구간은 못 좁혔다
CREATE INDEX idx_orders_user_status_created ON orders (user_id, status, created_at);

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 100 AND created_at > '2026-08-01';
--  Index Scan using idx_orders_user_status_created on orders
--    Index Cond: ((user_id = 100) AND (created_at > '2026-08-01 00:00:00+09'::timestamptz))
--    (actual rows=2104 loops=1)
--    Buffers: shared hit=2318        <- user 100의 엔트리 전부(4만 7천)를 훑은 흔적
-- created_at이 Index Cond에 찍혀 있지만 구간을 좁히진 못했다(leftmost prefix).
-- "인덱스 탔다"고 안심하면 안 되는 경우 — 판별은 계획 텍스트가 아니라 Buffers다.
-- (user_id, created_at) 인덱스였다면 같은 결과에 Buffers: shared hit=61 수준.
"인덱스를 얼마나 깊이 탔는가"는 PostgreSQL에서 계획 텍스트로 판별되지 않는다
① 인덱스 정의의 컬럼 순서와 조건의 등호/범위를 대조하고 ② BUFFERS의 읽은 페이지 수로 판별한다

트리 맨 아래에는 Planning Time과 Execution Time(ANALYZE일 때만)이 따로 찍힌다. 짧은 쿼리가 수백 번 도는데 Planning Time이 실행보다 크면 준비문(prepared statement)으로 계획을 재사용할 후보다. 큰 쿼리에는 JIT: 블록이 붙을 수 있다 — 추정 비용이 jit_above_cost를 넘으면 표현식을 기계어로 컴파일하는데, 추정이 틀려 짧은 쿼리에 붙으면 컴파일 시간이 실행보다 길어지는 역효과가 난다(그때는 jit = off).

3. 읽는 순서 5단계 — 모 · 이 · 행 · 버 · 경

긴장하면 목록은 두 개에서 끊긴다. 그래서 이 절은 읽는 순서 그대로 외우는 카드로 만든다. 순서가 곧 진단 순서다.

다섯 단계 인출 카드 — 텍스트로 통째 외운다

① 모양      : 안쪽(깊은 들여쓰기)·아래부터 실행. 조인 노드의 첫 자식 = outer(드라이빙)
② 노드 이름  : 스캔 방식(Seq / Index / Index Only / Bitmap) — "전부 읽었나, 좁혔나"
③ rows      : 추정 rows  vs  actual rows — 자릿수가 다르면 통계 문제. 1순위 진단
④ Buffers   : shared hit / read — 어느 노드가 페이지를 얼마나 읽었나 (자식 포함 누적)
⑤ 경고등     : Rows Removed by Filter / Sort Method: external / Batches > 1
              / Heap Fetches / 안쪽 노드의 loops

3-1. 스캔 노드 사전 — 트리의 가장 안쪽, 테이블에서 행을 처음 꺼내는 노드

노드하는 일같이 보는 것
Seq Scan힙을 처음부터 끝까지 순차로 읽는다Filter + Rows Removed by Filter가 크면 "많이 읽고 대부분 버림"
Index ScanB-tree에서 시작점을 찾아 인덱스 순서로 읽고, 엔트리마다 TID로 힙을 찾아간다(랜덤 I/O)Index Cond(인덱스에서 거른 조건)·Filter(힙에서 거른 조건). Index Cond가 없으면 인덱스 전체 순회 — 정렬 순서만 빌린 전수 조사
Index Only Scan인덱스만 읽고 힙에 안 간다(커버링). 단 visibility map이 "전부 가시"라고 보증하는 페이지만 생략Heap Fetches: N — 크면 커버링이 무력화된 상태(VACUUM 부족, 갱신 잦은 테이블)
Bitmap Index Scan → Bitmap Heap Scan인덱스에서 TID를 모아 블록 번호순으로 정렬한 비트맵을 만든 뒤 힙을 순차에 가깝게 읽는다. 여러 인덱스를 BitmapOr/BitmapAnd로 합칠 수 있다Recheck Cond, Heap Blocks: exact= lossy= — lossy가 있으면 work_mem 부족으로 비트맵이 페이지 단위로 뭉개져 힙에서 재검사(Rows Removed by Index Recheck)
Parallel Seq Scan + Gather워커 여럿이 힙을 나눠 읽고 리더가 모은다Workers Planned/Launched. 대량 스캔의 정상 선택일 수 있다 — "인덱스가 없어서"라고 단정하지 않는다

여기서 TID(tuple identifier)는 "행 하나의 물리적 주소"다. (블록 번호, 블록 안 몇 번째 슬롯) 쌍이고, 인덱스 엔트리에는 키 값과 이 TID만 들어 있다. 그래서 인덱스만으로 답이 안 나오면 TID를 들고 힙 페이지를 찾아가야 하는데, TID들이 힙 여기저기에 흩어져 있으므로 이 접근이 랜덤 I/O가 된다.

경계선은 노드 이름이 아니다 — 읽은 행 대비 남긴 행(Rows Removed by Filter)과 읽은 페이지 수(Buffers)다
Index Scan인데 Rows Removed by Filter가 actual rows의 열 배면, 이름만 인덱스지 비용은 풀스캔에 가깝다.
"인덱스는 탔는데요"라는 말은 이 두 숫자를 보기 전까지 아무것도 보장하지 않는다.
Bitmap Heap Scan은 "랜덤 vs 순차 I/O"라는 비용 모델이 스캔 방식으로 구현된 사례다 가산점 인덱스에서 얻은 TID 목록은 힙 위치가 뒤죽박죽이라 그대로 읽으면 페이지를 여기저기 찌른다(랜덤). 비트맵은 그 TID를 블록 번호순으로 정렬한 뒤 읽어 인접 페이지를 연달아 읽게 만들고(순차에 가깝게), 그래서 플래너는 "좁혀지긴 하는데 수천~수만 행"인 중간 선택도에서 Index Scan 대신 이걸 고른다. "DB가 랜덤 I/O를 얼마나 싫어하면 스캔 방식 하나를 따로 만들었겠는가"로 기억하면 비용 모델이 같이 굳는다. 그리고 이것도 인덱스를 쓴 계획이다 — 이름에 Index Scan이 없다고 풀스캔으로 오해하지 않는다.

ORDER BY가 인덱스를 타는 조건 — 계획에서 Sort 노드가 사라지는 경우

관련 질문 "ORDER BY가 인덱스를 타는 조건은?"의 PostgreSQL 답이다. B-tree 리프는 이미 정렬되어 저장돼 있으므로, 정렬 요구가 그 리프 순서와 일치하면 정렬 작업 자체가 필요 없다.

Sort가 사라지는 조건
① ORDER BY 컬럼이 인덱스의 컬럼 순서와 일치하고 ② 앞 컬럼들이 등호로 고정돼 있으며 ③ 정렬 방향이 일관될 것. 역순이면 Index Scan Backward로 처리된다. → LIMIT이 붙으면 리프 앞 N건만 읽고 종료.
Sort가 남는 경우
정렬 컬럼 앞에 범위 조건이 끼거나, 인덱스에 없는 컬럼으로 정렬하거나, 여러 컬럼의 방향이 엇갈릴 때. 이때는 대상 전부를 읽어 정렬해야 한다.
Sort Method: external merge Disk:가 최악인 이유
work_mem을 넘겨 디스크 임시 파일에 청크를 쓰고 다시 병합한다 — 읽기·쓰기·다시 읽기가 추가되고, LIMIT 20이 붙어 있어도 정렬은 입력 전체를 봐야 하므로 조기 종료가 안 된다.
MySQL 대조 — 표를 순서대로 읽는 기술 vs 트리를 안쪽부터 읽는 기술 경험 대조 MySQL의 EXPLAIN은 트리가 아니라 테이블 접근 하나당 한 행인 표다: 위에서 아래가 실행 순서(맨 위가 드라이빙), type(접근 등급 — const > eq_ref > ref > range > index > ALL, 경계선은 range와 index 사이), key/key_len(어느 인덱스를 몇 바이트까지 썼나 — 복합 인덱스의 깊이를 알려주는 유일한 칸), rows × filtered, Extra(위험 3: Using filesort·Using temporary·Using join buffer / 좋은 3: Using index·Using index condition·Using MRR).
PostgreSQL 대응 — type: ALL = Seq Scan, type: index = Index Cond 없는 Index Scan, key_len은 대응물이 없고(Buffers로 판별), filtered = Rows Removed by Filter, Using filesort = Sort 노드, Using temporary = HashAggregate/Materialize, Using index = Index Only Scan, Using index condition(ICP) = Index Cond의 인덱스 내 검사(PostgreSQL은 기본 동작이라 이름이 없다), Using MRR = Bitmap Heap Scan, DEPENDENT SUBQUERY = SubPlan(loops 큰 것).

4-2. 둘째 — hit과 read의 구성비가 병목의 성격을 알려준다

read가 곧 디스크 접근은 아니다 — 이중 캐시 구조 PostgreSQL은 shared_buffers와 OS 페이지 캐시의 이중 캐시 구조라, read로 잡힌 페이지가 실은 OS 캐시에서 왔을 수도 있다. 그래서 I/O 병목을 단정하려면 track_io_timing = on을 켜 I/O Timings: shared read=…가 붙게 해야 한다 — "그 read 중 진짜 디스크에서 온 것이 몇 밀리초였나"까지 갈린다.

노드의 Buffers는 자식 수치를 포함한 누적값이다 — 더하면 이중 계산

맨 위 Limit의 Buffers: shared hit=24292 read=41856은 트리 전체의 합이고, 그 아래 자식들의 수치가 이미 그 안에 들어 있다. 그래서 노드별 Buffers를 전부 더하면 실제보다 훨씬 큰 수가 나온다.

읽는 법은 뺄셈이 아니라 "어느 노드에서 갑자기 커지는가"를 아래에서 위로 올라가며 보는 것이다. 급증한 지점 바로 그 노드가 페이지를 실제로 읽은 범인이다.

한 줄로 정리하면 — 시간은 "얼마나 걸렸나"이고 Buffers는 "얼마나 일했나"다
환경이 달라져도 변하지 않는 쪽은 후자이므로, 가설을 세우고 검증하는 기준선은 Buffers로 잡는다

6. 사이클 개관 + ① 측정 — "느리다"를 숫자와 재현 조건으로

"인덱스 추가해봄 → 빨라짐"이 왜 프로세스가 아닌지부터 분명히 한다.

6-1. 입력은 사람의 제보가 아니라 로그와 지표여야 한다 — 네 개의 창구

log_min_duration_statement
이 값(ms)을 넘긴 문장을 서버 로그에 남긴다. 기본값 -1은 "아무것도 안 남김"이다. 파라미터가 실제 값으로 찍히므로 "느렸던 그 파라미터"를 여기서 가져온다.
auto_explain
같은 임계를 넘긴 문장의 실제 실행 계획을 로그에 남기는 확장. log_analyze·log_buffers를 켜면 청구서까지 남는다 — "그때 그 계획"을 사후에 알 수 있는 유일한 길이다.
pg_stat_statements
파라미터를 정규화한 쿼리 패턴별로 호출 횟수, 총·평균 실행 시간, 반환 행 수, 읽은 페이지 수를 누적하는 확장. "어느 쿼리가 비싼가"의 대시보드.
APM (Pinpoint, Datadog 등)
어느 API에서 어느 쿼리가 몇 번 호출되는지를 본다. N+1은 쿼리 하나는 빠른데 요청당 수백 번 호출되는 문제라 느린 쿼리 로그에는 안 잡히고 여기서만 보인다.
측정 우선순위는 "가장 느린 쿼리"가 아니라 "가장 비싼 쿼리"
-- 총 비용 = 평균 시간 × 호출 횟수 순으로 정렬
SELECT queryid,
       left(query, 80)                                   AS query,
       calls,
       round((total_exec_time / 1000)::numeric, 1)       AS total_sec,
       round(mean_exec_time::numeric, 2)                 AS mean_ms,
       rows / calls                                      AS avg_rows,
       (shared_blks_hit + shared_blks_read) / calls      AS blks_per_call
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
-- 1초짜리 하루 1회(총 1초)보다 50ms짜리 하루 10만 회(총 5,000초)가 병목이다.
-- blks_per_call(호출당 읽은 페이지)이 avg_rows(호출당 반환 행)의 수천 배면
-- 그것만으로 "많이 읽고 대부분 버린다"는 진단이 선다.
1초짜리 하루 1회(총 1초) < 50ms짜리 하루 10만 회(총 5,000초)
눈에 띄는 것은 앞이지만 서비스를 잡아먹는 것은 뒤다

6-2. 재현 조건 — 이게 없으면 "내 로컬에선 빠른데요"로 끝난다

어떤 파라미터에서 느린가
같은 쿼리도 user_id에 따라 대상 행 수가 100배 차이 난다. pg_stat_statements의 query는 파라미터가 $1로 지워져 있으니 실제 값은 log_min_duration_statement 로그에서 가져온다.
어느 시간대인가
배치 · autovacuum · 리포트와 겹치는가. 겹친다면 쿼리가 아니라 동시에 도는 무언가가 원인일 수 있다.
실행이 느린 건가, 기다린 건가
계획이 완벽해도 앞 트랜잭션의 락을 기다리면 느리다. wait_event_type이 Lock이면 실행 계획 문제가 아니라 동시성 문제이므로 EXPLAIN을 아무리 봐도 답이 안 나온다.
배제 "느린 게 아니라 기다린 것"부터 걷어낸다
SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start        AS xact_age,
       pg_blocking_pids(pid)     AS blocked_by,
       left(query, 60)           AS query
FROM pg_stat_activity
WHERE state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY xact_start;
-- wait_event_type = 'Lock' + blocked_by가 차 있으면 락 문제(범인은 그 pid).
-- 'IO'면 디스크, NULL이면 CPU에서 실행 중 → 계획 문제 쪽.

재현 조건의 PostgreSQL 고유 함정 — "psql에선 빠른데 앱에선 느리다"의 정체는 제네릭 계획 시니어 변별

psql에서 본 것 — 커스텀 계획

리터럴 값으로 뜬 EXPLAIN은 그 값의 통계로 세운 계획이다. user_id = 100이 4만 건이라는 사실을 알고 세운 계획.

앱에서 도는 것 — 제네릭 계획일 수 있다

pgjdbc가 같은 문장을 5회 실행한 뒤 서버 준비문으로 바꾸고, 서버는 커스텀 계획 5회 뒤 제네릭 계획(파라미터 값을 모른 채 평균 선택도로 세운 계획)이 더 싸다고 판단하면 그쪽으로 전환한다.

편중 데이터에서 특히 갈린다. 확인은 PREPARE 후 EXPLAIN EXECUTE를 6회 이상 반복하거나 auto_explain 로그를 보는 것이고, 통제는 plan_cache_mode = force_custom_plan이다.

그리고 측정은 운영 규모 데이터에서, ANALYZE를 돌린 뒤 해야 한다 함정 로컬 100건짜리 테이블에서는 어떤 쿼리든 빠르고, 심지어 실행 계획 자체가 다르다. 플래너는 작은 테이블에서 인덱스 대신 Seq Scan을 고르는 게 정상이라(페이지 몇 장이면 다 읽히는데 인덱스를 거칠 이유가 없다), 로컬 EXPLAIN에 Seq Scan이 떠도 운영에선 Index Scan일 수 있고 그 반대도 있다.

7. ② 가설 — 비용이 "어디서 새는지"를 사슬로 말한다

계획을 3절의 순서대로 읽으면서, "느리다"를 메커니즘 사슬로 번역하는 단계다. "성능 저하", "메모리 부하", "왔다갔다" 같은 뭉뚱그린 말에서 끝내지 않고 이름 붙은 단계로 끝까지 잇는다.

7-1. 뭉뚱그린 말 → 사슬로 말하기 — 계획에서 본 것별 번역표

8-1. PostgreSQL만의 한 겹 — HOT 업데이트에서 탈락하면 모든 인덱스를 건드린다

PostgreSQL의 UPDATE는 행을 제자리에서 고치는 게 아니라 새 버전을 만드는 방식인데, 바뀐 컬럼이 어떤 인덱스에도 들어 있지 않으면 인덱스를 하나도 건드리지 않고 힙 안에서만 처리한다(Heap-Only Tuple, 줄여서 HOT).

한 호흡 템플릿 — 이득 / 대가 / 판단을 한 번에 말한다 시니어 변별 "이 인덱스는 [이득] 이 쿼리의 힙 랜덤 I/O 4만 7천 번을 20번으로 만들고 Sort를 없앤다(Buffers 66,148에서 103으로). [대가] 대신 orders에 INSERT가 일어날 때마다 B-tree 하나를 더 갱신하고, status가 인덱스에 들어갔으므로 status를 바꾸는 UPDATE가 HOT 업데이트에서 탈락해 이 인덱스만이 아니라 테이블의 모든 인덱스에 새 엔트리를 꽂게 되며, 인덱스 크기만큼 디스크와 shared_buffers를 더 쓰고, user_id를 선두로 쓰는 다른 쿼리들의 계획이 바뀔 수 있고, 수억 건 테이블이면 인덱스 생성 자체가 테이블 2회 스캔짜리 운영 작업이다. [판단] 그래서 기존 (user_id) 단독 인덱스는 새 인덱스의 선두 컬럼에 흡수되므로 삭제해 쓰기 대가를 상쇄하고, 생성은 CREATE INDEX CONCURRENTLY로 트래픽이 적은 시간에 하며, 배포 후 n_tup_hot_upd 비율이 얼마나 떨어지는지 확인한다."

8-2. 검증 체크리스트 — 네 줄

1
대상 쿼리의 실측이 가설대로 개선됐는가 — actual rows, actual time, 그리고 Buffers. 4절에서 봤듯 시간은 캐시 상태에 따라 흔들리지만 읽은 페이지 수는 같은 계획이면 같으므로, 전후 비교의 기준 숫자는 Buffers다.
2
같은 테이블을 쓰는 상위 쿼리들의 계획이 나빠지지 않았는가 — 새 인덱스가 생기면 플래너의 선택지가 늘고, 선택도 낮은 컬럼이 선두인 인덱스는 플래너를 오히려 잘못된 길로 유인할 수 있다. pg_stat_statements 상위 목록에서 같은 테이블 쿼리를 골라 다시 EXPLAIN한다.
3
쓰기 처리량이 허용 범위인가 — 쓰기 비중이 높은 테이블이면 인덱스 하나가 INSERT p95를 눈에 띄게 올리고, 인덱스에 들어간 컬럼을 갱신하는 UPDATE는 HOT 탈락으로 모든 인덱스를 건드린다. pg_stat_user_tables의 n_tup_upd 대비 n_tup_hot_upd 비율을 전후로 본다.
4
DDL 실행 방식 — CREATE INDEX CONCURRENTLY로 쓰기를 막지 않고 만들되, 실패하면 INVALID 인덱스가 남으므로(pg_index.indisvalid) 확인 후 DROP하고 재시도한다. 일반 CREATE INDEX는 테이블에 쓰기 잠금을 건다.

인덱스 DDL은 반드시 마이그레이션 파일로

단 CREATE INDEX CONCURRENTLY는 트랜잭션 블록 안에서 실행할 수 없으므로 마이그레이션 도구가 그 스크립트를 트랜잭션으로 감싸지 않게 설정한다(Flyway executeInTransaction=false, Liquibase runInTransaction="false").
플래너를 강제했다면 만료일을 붙인다
PostgreSQL에는 힌트 문법이 없어서 강제 수단은 확장 pg_hint_plan이나 세션의 enable_* 스위치뿐인데, 어느 쪽이든 지금의 데이터 분포를 코드에 박제하는 것이라 만료일이 있는 부채다. 주석에 "왜, 어떤 측정 근거로, 언제 재검토"를 남기고 티켓을 건다.
SET LOCAL enable_seqscan = off는 가설 검증 도구지 운영 설정이 아니다.
PR 템플릿 리뷰어의 기억이 아니라 파일이 묻게 한다
## DB 변경 체크 (해당 없으면 N/A)
- [ ] 새로 추가/변경한 쿼리의 EXPLAIN (ANALYZE, BUFFERS) 결과를 첨부했다
      (운영 규모 데이터·ANALYZE 후 기준)
- [ ] 인덱스 추가/삭제는 마이그레이션 파일로 했고, CONCURRENTLY + 트랜잭션 밖 실행을 확인했다
- [ ] 같은 테이블을 쓰는 기존 상위 쿼리(pg_stat_statements)의 계획 변화를 확인했다
가산점 만든 인덱스가 실제로 쓰이는지 주기적으로 확인 — 죽은 인덱스는 쓰기 비용만 낸다
SELECT s.indexrelname, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0 AND NOT i.indisunique      -- 유니크는 제약 역할이라 제외
ORDER BY pg_relation_size(s.indexrelid) DESC;
-- 통계 리셋(pg_stat_reset) 이후 기준. 레플리카에서만 쓰이는 인덱스는
-- 프라이머리 카운트가 0일 수 있으니 양쪽에서 확인.

팀에 정착시킬 때의 우선순위 — 비용 대비 효과 순으로 넷 시니어 변별

① 설정 (pg_stat_statements · log_min_duration_statement · auto_explain)→ ② 쿼리 수 단정 테스트→ ③ DDL 마이그레이션 강제 + PR 템플릿→ ④ EXPLAIN 단정 테스트

①이 첫째인 이유 — 측정이 없으면 나머지 전부가 시작을 못 한다. 설정 몇 줄이라 가장 싸고, 이것만으로 "어디가 비싼지"와 "그때 계획이 무엇이었는지"가 매일 보인다. 특히 auto_explain은 미리 켜 두지 않으면 지나간 사고의 계획을 되살릴 방법이 없다는 점에서 다른 것들과 급이 다르다.

②가 둘째인 이유 — 가장 흔한 성능 회귀는 인덱스 누락이 아니라 N+1이고, N+1은 쿼리 하나하나가 빨라서 느린 쿼리 로그에 안 잡힌다. datasource-proxy 하나 붙이고 핵심 조회 메서드에 단정 3~4개면 된다.

④가 마지막인 이유 — 운영 규모 시드와 ANALYZE가 필요해 비용이 가장 크다. 장애를 겪은 핵심 쿼리부터 하나씩 늘린다.

뒤집어 ④부터 하면 시드 관리에 지쳐 중단되고, ①을 빼면 무엇을 테스트할지조차 모른다
순서는 "측정 → 가장 흔한 회귀 → 절차의 파일화 → 정밀 회귀 방지"

10. 한 사이클을 처음부터 끝까지 — 주문 목록 API

"주문 목록 API가 느리다"는 제보를 사이클로 처리한 기록이다. 숫자는 예시이지만, 말하는 순서와 붙이는 근거의 형태가 그대로 면접 답변의 뼈대가 된다.

측
측정. APM에서 GET /orders p95가 2.4초였다. pg_stat_statements 총 시간 1위는 SELECT … FROM orders o JOIN products p … WHERE o.user_id = $1 AND o.status = $2 ORDER BY o.created_at DESC LIMIT 20 — mean_exec_time 1.8초, 하루 12만 회, blks_per_call 약 6만 6천, avg_rows 20. 페이지 3,300장을 읽어 행 하나를 돌려주는 셈이다(66,000 ÷ 20).
pg_stat_activity의 wait_event_type은 비어 있고 log_lock_waits 로그도 없어 락 문제는 아니다. 느린 파라미터는 log_min_duration_statement 로그에서 확인했다 — 주문이 많은 헤비 유저들로 user_id별 편차가 크다.
가
가설. 그 파라미터로 EXPLAIN (ANALYZE, BUFFERS)를 떴다: Index Scan using idx_orders_user, Filter: (status = 'ACTIVE'), Rows Removed by Filter: 42495, 이 노드 Buffers: shared hit=5412 read=41856, 위에 Sort (top-N heapsort).
추정 4,800 대 실측 4,720으로 통계는 멀쩡하니 통계 교정 건은 아니다. 사슬로 번역하면 — user_id 인덱스로 TID 4만 7천 개를 모아 → 4만 7천 번 힙 랜덤 접근 → status 필터로 90% 폐기 → 4,720건 정렬 → 20건 반환. 비용의 대부분이 "버릴 행의 힙 랜덤 I/O"와 "정렬"이다.
처방 가설은 (user_id, status, created_at) 복합 인덱스, 예상 효과는 숫자로 — Rows Removed by Filter 0, Sort 노드 제거(Index Scan Backward + Limit), Buffers 6만 6천에서 수십으로.
검
검증. 스테이징(운영 마스킹 덤프 + ANALYZE)에서 전후를 실측했다: 291ms → 0.2ms, Buffers 66,148 → 103.
pg_stat_statements 상위 5개를 재확인 — 3개는 새 인덱스로 자연 이동(user_id 선두가 같다), 2개는 무관했다. 기존 idx_orders_user는 새 인덱스에 흡수되므로 삭제해 인덱스 개수를 유지하고 쓰기 비용 증가분을 상쇄했다. orders가 3억 건이라 CREATE INDEX CONCURRENTLY로 새벽에 생성했다(테이블 2회 스캔 동안 I/O와 레플리카 지연을 모니터링).
대가는 인덱스 크기 약 12GB 증가와 status를 바꾸는 UPDATE의 HOT 탈락 — 배포 후 n_tup_hot_upd / n_tup_upd가 71%에서 58%로 내려간 것을 확인하고 허용 범위로 기록했다.
고
고정. Flyway 마이그레이션 2건(생성·삭제, 트랜잭션 밖 실행) / EXPLAIN 단정 테스트 1건 추가 / log_min_duration_statement를 1000에서 500으로 내리고 auto_explain 활성화 + 알람 연결 / 개선된 쿼리의 queryid·mean_ms·blks_per_call을 기준선으로 PR에 기록 / PR 템플릿에 DB 체크 항목 추가.
그리고 그다음 주 — 이것이 "고정"의 효과다 같은 팀원이 orders에 WHERE user_id = $1 AND payment_method = $2 쿼리를 올렸을 때, PR 템플릿이 EXPLAIN을 요구했고 Rows Removed by Filter: 44100이 리뷰에서 잡혔다. 아무도 이 사이클을 기억하고 있지 않았지만, 파일이 기억하고 있었다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

두 도구 한 문장 정의?
EXPLAIN = 통계로 쓴 견적서(추정, 실행 안 함), EXPLAIN (ANALYZE, BUFFERS) = 실제로 실행해 받은 청구서(실측). 첫 진단은 견적서, 괴리 확인과 전후 비교는 청구서.
읽는 순서 5단계?
모 · 이 · 행 · 버 · 경 — 모양(안쪽부터, 첫 자식=outer) → 노드 이름 → 행 수(추정 vs 실측) → Buffers → 경고등.
1순위 진단은?
추정 rows vs actual rows. 자릿수가 다르면 튜닝이 아니라 통계 교정이 먼저. 오추정 하나가 조인 방식 선택을 통째로 틀리게 만든다.
실행 순서 규칙?
안쪽(들여쓰기 깊은 쪽)·아래부터 위로. 조인 노드의 첫 자식이 outer, 두 번째가 inner. loops가 붙는 쪽이 항상 inner.
loops의 함정?
actual time과 actual rows는 loops당 평균값. 총량은 × loops. 0.003ms × 4720을 못 하면 "조인은 0.003ms인데?"라는 오독이 나온다.
왜 시간 대신 Buffers?
시간은 캐시 상태로 13배 흔들리지만(3,842ms vs 289ms), 계획이 같으면 읽는 페이지 수는 같다(둘 다 48,122장). 기준선은 Buffers.
Buffers로 무엇을 가르나?
read 큼 + I/O Timings 큼 = I/O 병목(읽는 페이지를 줄여라) / hit 압도적인데 느림 = CPU 병목(반복 횟수를 줄여라) / temp 큼 = work_mem 스필.
사이클 4단계?
측 · 가 · 검 · 고 — 측정(숫자와 재현 조건) → 가설(사슬 + 예상 효과 숫자) → 검증(실측 + 대가) → 고정. 고정까지 가야 한 사이클.
고정 3층?
설정(측정이 상시 돌게) / 테스트(회귀가 CI에서 터지게) / 파이프라인·템플릿(절차가 사람 기억 밖에). 우선순위는 설정 → 쿼리 수 단정 → DDL·PR → EXPLAIN 단정.
경고등 5종?
필 · 머 · 배 · 힙 · 룹 — Rows Removed by Filter / external merge / Batches > 1 / Heap Fetches / 안쪽 loops.
오추정 원인 3종과 처방?
낡음 → ANALYZE 테이블 / 표본 부족 → SET STATISTICS 1000 / 컬럼 간 상관 → CREATE STATISTICS. (플래너는 조건을 독립으로 가정해 곱한다.)
ROLLBACK이 안 되돌리는 것?
락 · 시퀀스 · 트리거 · WAL — 행 락은 ROLLBACK까지 유지, nextval()은 소모, 트리거는 발화, WAL은 이미 쌓인다.
"인덱스 탔다"의 판별 기준?
노드 이름이 아니다. Rows Removed by Filter(힙까지 읽고 버린 양)와 Buffers(인덱스 안에서 훑고 버린 양). PostgreSQL엔 key_len에 해당하는 칸이 없다.
Sort 노드를 없애는 조건?
정렬 컬럼이 인덱스 순서와 일치 + 앞 컬럼이 등호로 고정 + 방향 일관. 그러면 Index Scan Backward + Limit으로 앞 N건만 읽고 종료.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

rows 추정이 실제와 크게 다르면 무엇을 의심하고, 어떻게 확인·수정하나요? 필수힌트: 의심 → 확인 → 수정 넷을 "순서대로". 마지막에 힌트 확장은 맨 끝에 둔다

통계 정보가 현실과 어긋난 것을 첫째로 의심한다. 플래너는 통계로 추정하고, 통계는 ANALYZE의 표본으로 만들어지며, 대량 적재·삭제 직후나 컬럼 간 상관관계가 강한 조건에서 잘 틀린다. 확인은 EXPLAIN ANALYZE의 추정 rows와 actual rows 비교 — 자릿수가 다르면 확정이다.

수정은 순서대로 넷이다.

⑴ ANALYZE 테이블
즉시 재수집. autovacuum의 analyze 임계(기본은 행의 10% 변경)가 큰 테이블에서 너무 둔하면 테이블 단위로 낮춘다.
⑵ SET STATISTICS
표본을 키운다 — ALTER TABLE … ALTER COLUMN status SET STATISTICS 1000(기본 default_statistics_target 100). PostgreSQL은 MCV와 히스토그램을 기본으로 들고 있어 "90%가 ACTIVE인 status" 같은 편중은 대체로 잡아내지만, 표본이 모자라면 희귀 값이 MCV에서 빠진다.
⑶ CREATE STATISTICS
컬럼 간 상관이면 CREATE STATISTICS … (dependencies, ndistinct, mcv) ON city, zipcode FROM addresses. 플래너는 조건들을 독립으로 가정해 선택도를 곱하므로, "서울 AND 06236"처럼 한쪽이 다른 쪽을 결정하는 조건은 심하게 과소추정된다.
⑷ plan_cache_mode
추정이 아니라 파라미터를 모르는 것일 수도 있다 — 제네릭 계획이면 plan_cache_mode = force_custom_plan.

이 넷을 다 밟은 뒤에야 pg_hint_plan을 검토한다. 그리고 "코드도 쿼리도 안 바꿨는데 느려졌다"의 정체가 대개 이 중 하나라는 말까지 붙이면 답변이 닫힌다.

EXPLAIN 결과는 좋은데(Index Scan, rows 작음) 운영에서 느립니다. 어디를 보나요? 필수힌트: 전제 한 문장으로 시작한다 — "EXPLAIN은 쿼리 하나의 계획이지 요청 하나의 비용이 아니다"

"EXPLAIN은 '쿼리 하나의 계획'이지 '요청 하나의 비용'이 아니다"라는 전제에서 출발한다. 순서대로 여섯을 본다.

⑴ EXPLAIN에 넣은 파라미터가 "느린 그 파라미터"인가. user_id = 1(주문 3건)과 user_id = 100(4만 건)은 같은 쿼리, 다른 비용이다. log_min_duration_statement 로그에서 실제 느렸던 값을 가져와 다시 보고, 앱은 준비문의 제네릭 계획을 타고 있을 수 있다는 PostgreSQL 고유 함정도 배제한다.

⑵ 실행이 아니라 대기인가. pg_stat_activity.wait_event_type = 'Lock', pg_blocking_pids(). 계획이 완벽해도 앞 트랜잭션의 락을 기다리면 느리다.

⑶ 호출 횟수. 3ms짜리 쿼리가 요청당 500번 돌면 1.5초다 — N+1은 EXPLAIN에 절대 안 보이고 APM·calls·쿼리 수 단정 테스트에만 보인다.

⑷ 캐시 미스. 계획은 같아도 Buffers가 shared hit이냐 read냐로 열 배 넘게 차이 난다(3,842ms 대 289ms). 새벽 첫 호출, 배치 직후(캐시 오염)가 전형이고, I/O Timings로 진짜 디스크였는지 가른다.

⑸ 같은 계획인데 읽는 페이지가 늘었다. 죽은 튜플이 쌓여(bloat) 같은 행을 얻는 데 페이지를 더 읽거나, VACUUM이 밀려 Index Only Scan의 Heap Fetches가 늘어난 경우 — n_dead_tup, last_autovacuum, 그리고 VACUUM을 막는 롱 트랜잭션을 본다.

⑹ 결과셋 크기와 네트워크. SELECT *로 큰 text·jsonb(TOAST) 컬럼 수천 건을 끌어오면 DB는 빠른데 전송이 느리다. — EXPLAIN (ANALYZE, BUFFERS)가 이 중 ⑴·⑷·⑸를 실측으로 갈라준다.

인덱스를 추가하면 다른 쿼리가 느려질 수도 있나요? 그걸 어떻게 미리 아나요? 시니어 변별힌트: "있다"로 시작하고 경로 넷을 든 뒤, 마지막에 "미리 아는 방법"을 붙인다

있다. 네 경로다.

⑴ 쓰기 경로. 모든 INSERT가 B-tree 하나를 더 갱신하고, PostgreSQL에서는 한 겹 더 — 인덱스에 들어간 컬럼을 바꾸는 UPDATE는 HOT 업데이트에서 탈락해 그 인덱스만이 아니라 테이블의 모든 인덱스에 새 엔트리를 꽂는다. 자주 바뀌는 컬럼(status, updated_at)을 인덱스에 넣는 순간 쓰기 증폭이 테이블 전체로 번진다.

⑵ 플래너 오유인. 선택지가 늘면 플래너가 새 인덱스를 잘못 고를 수 있다 — 특히 선두 컬럼의 선택도가 낮은 인덱스는 "일단 이걸 타볼까"로 유인해 힙 랜덤 접근 폭탄을 만든다.

⑶ shared_buffers 경쟁. 큰 인덱스 하나가 다른 테이블의 핫 페이지를 밀어낸다. ⑷ VACUUM 비용. 인덱스도 VACUUM 대상이라 autovacuum 한 사이클이 길어진다.

미리 아는 방법 — 같은 테이블을 쓰는 pg_stat_statements 상위 쿼리를 새 인덱스 생성 후 다시 EXPLAIN하고, n_tup_hot_upd 비율을 전후로 본다

진짜로 만들기 전에 "만들면 플래너가 쓸까"만 보고 싶다면 가상 인덱스 확장(HypoPG)이 있다. 이 재확인은 PR 템플릿에 항목으로 박고 핵심 쿼리는 EXPLAIN 단정 테스트로 고정한다.

한 호흡으로 — "이 인덱스는 조회 쿼리 A의 힙 랜덤 I/O를 없애는 대신 쓰기 비용(HOT 탈락 포함)·메모리·플래너 선택지라는 대가를 내고, 그 대가가 허용 범위인지는 상위 쿼리 재확인과 HOT 비율·쓰기 p95로 검증한다."

EXPLAIN ANALYZE를 운영 DB에서 그냥 돌려도 되나요? 필수힌트: "조건부"로 시작하고, ROLLBACK의 한계까지 말해야 완결된다

조건부다. 실제로 실행하므로 ⑴ 무거운 SELECT는 그 자체가 부하고 shared_buffers를 오염시킨다, ⑵ UPDATE/DELETE에 붙이면 데이터가 실제로 바뀐다.

그래서 원칙은 읽기 레플리카나 운영 규모 스테이징에서 돌리는 것이고, 운영 프라이머리에서 꼭 해야 한다면 SELECT만, 트래픽 낮은 시간에, statement_timeout을 걸고 한다. 변경문은 BEGIN; EXPLAIN (ANALYZE) UPDATE …; ROLLBACK;으로 감싼다.

다만 롤백이 전부를 되돌리지는 않는다는 것까지 말해야 완결된다 — 롤백 자체는 O(1)이지만 그동안 잡은 행 락은 ROLLBACK 시점까지 유지되고, 시퀀스 값은 소모되며, 트리거는 실제로 발화하고, WAL은 이미 쌓인다. 노드별 시간 계측이 수치를 부풀리면 TIMING off로 rows·Buffers만 본다.

대신 일반 EXPLAIN은 실행하지 않으므로 운영에서 언제든 안전하다 — 첫 진단은 EXPLAIN, 괴리 확인은 EXPLAIN ANALYZE, 이 분업을 말하면 된다.

비용 대비 효과 순으로 네 단계다.

⑴ pg_stat_statements + log_min_duration_statement + auto_explain — 측정이 없으면 나머지 전부가 시작을 못 한다. 설정 몇 줄이라 가장 싸고, 이것만으로 "어디가 비싼지"와 "그때 계획이 무엇이었는지"가 매일 보인다. 특히 auto_explain은 미리 켜 두지 않으면 지나간 사고의 계획을 되살릴 방법이 없다는 점에서 다른 것들과 급이 다르다.

⑵ 쿼리 수 단정 테스트 — 가장 흔한 성능 회귀는 인덱스 누락이 아니라 N+1이고, N+1은 쿼리 하나하나가 빨라서 느린 쿼리 로그에 안 잡힌다. datasource-proxy 하나 붙이고 핵심 조회 메서드에 단정 3~4개면 된다.

⑶ 인덱스 DDL의 마이그레이션 강제(CONCURRENTLY, 트랜잭션 밖) + PR 템플릿 — 규칙이지만 파일로 박으면 리뷰어 기억에서 독립한다.

⑷ EXPLAIN 단정 테스트 — 운영 규모 시드와 ANALYZE가 필요해 비용이 가장 크므로 마지막이고, 장애를 겪은 핵심 쿼리부터 하나씩 늘린다.

뒤집어 ⑷부터 하면 시드 관리에 지쳐 중단되고, ⑴을 빼면 무엇을 테스트할지조차 모른다. 순서는 "측정 → 가장 흔한 회귀 → 절차의 파일화 → 정밀 회귀 방지"다.

MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 다섯 지점 — 출력 형태 · 인덱스 깊이 · 측정 도구 · 통계 교정 · 랜덤 I/O 완화

① 출력의 형태. MySQL은 테이블당 한 행인 표(type·key·rows·Extra)라 "칸을 순서대로 읽는" 기술이고, PostgreSQL은 노드 트리라 "안쪽부터 올라오며 추정과 실측을 나란히 읽는" 기술이다. 실측 쪽인 EXPLAIN ANALYZE도 MySQL은 8.0.18에서야 추가됐고 BUFFERS에 해당하는 노드별 페이지 수는 없다.

② 복합 인덱스를 얼마나 깊이 탔나. MySQL은 key_len과 Extra: Using index condition으로 텍스트에 드러나지만, PostgreSQL은 강등된 조건도 Index Cond에 찍혀 Buffers로 판별해야 한다.

③ 측정 도구. MySQL의 slow query log(long_query_time, Rows_examined)와 performance_schema의 digest 테이블·sys 뷰 대신 PostgreSQL에서는 log_min_duration_statement·pg_stat_statements·auto_explain을 쓴다. 실행 중 쿼리의 계획을 보는 MySQL의 EXPLAIN FOR CONNECTION은 PostgreSQL에 대응물이 없어 auto_explain을 미리 켜 둔다.

④ 통계 교정과 강제 수단. MySQL은 ANALYZE TABLE에 히스토그램을 따로 만들어야 하고 FORCE INDEX·옵티마이저 힌트가 문법으로 있지만, PostgreSQL은 MCV·히스토그램이 기본이고 상관관계는 CREATE STATISTICS로 잡으며, 힌트 문법이 없어 통계 교정이 곧 튜닝이다(강제는 확장 pg_hint_plan). 대신 준비문의 제네릭 계획 전환이라는 PostgreSQL 고유 함정이 있다.

⑤ 랜덤 I/O의 정체와 완화. MySQL의 InnoDB는 세컨더리 인덱스에서 PK를 얻어 클러스터드 인덱스를 재탐색하고 Using MRR이 그 PK를 정렬해 완화하지만, PostgreSQL은 힙 테이블이라 모든 인덱스가 TID로 힙을 찌르고 Bitmap Heap Scan이 TID를 블록순으로 정렬해 완화한다 — 그래서 PostgreSQL에는 커버링의 Index Only Scan과 visibility map, 그리고 HOT 탈락이라는 쓰기 대가가 따라온다. 이 다섯을 짚어 말하면 "한쪽만 써봤다"가 아니라 "차이를 원리로 이해했다"로 들린다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

잘 돌던 쿼리의 실행 계획이 어느 날 갑자기 바뀌어 느려졌습니다. 가능한 원인과 대응은? 필수힌트: "계획을 바꾸는 입력이 무엇인가"를 먼저 정리하면 원인 목록이 저절로 나온다

먼저 전제를 세운다 — 플래너의 출력(계획)은 세 가지 입력의 함수다: ① 통계 ② 데이터의 양과 분포 ③ 설정과 사용 가능한 인덱스. 쿼리도 코드도 안 바뀌었는데 계획이 바뀌었다면 이 셋 중 하나가 바뀐 것이다.

⑴ 통계가 갱신됐다 / 낡았다. autovacuum이 ANALYZE를 돌리는 순간 계획이 갈아탈 수 있고, 반대로 대량 적재 뒤 통계가 안 따라와 5절의 500배 오추정이 날 수도 있다. 방향이 어느 쪽이든 확인은 추정 rows vs actual rows다.

⑵ 데이터가 임계를 넘었다. 같은 쿼리도 선택도가 변하면 계획이 정당하게 바뀐다 — 어제까지는 인덱스가 유리한 비율이었는데 오늘 데이터가 늘어 Seq Scan이 더 싸진 경우다. 이건 버그가 아니라 플래너가 제 일을 한 것이고, 그렇다면 손봐야 할 것은 쿼리가 아니라 접근 패턴이나 인덱스 설계다.

⑶ 제네릭 계획으로 전환됐다. 앱이 같은 문장을 반복 실행하다 준비문 + 제네릭 계획으로 갈아탄 경우. "배포도 안 했는데 어느 순간부터"의 전형적인 정체다. 통제는 plan_cache_mode = force_custom_plan.

⑷ 인덱스·설정이 바뀌었다. 누군가 인덱스를 추가/삭제했거나(플래너의 선택지가 늘어 오유인), work_mem·random_page_cost·effective_cache_size 같은 파라미터가 바뀌었거나, 인덱스가 INVALID 상태로 남아 못 쓰이고 있을 수도 있다(pg_index.indisvalid).

대응의 첫 걸음은 "그때 계획이 무엇이었는지"를 아는 것인데, PostgreSQL에는 사후 조회 수단이 없다
그래서 auto_explain을 미리 켜 두는 것이 이 질문의 진짜 답이다

대응 순서는 ① auto_explain·pg_stat_statements로 전후 계획과 blks_per_call 변화를 확인 → ② 오추정이면 통계 교정(ANALYZE → SET STATISTICS → CREATE STATISTICS) → ③ 제네릭 계획이면 plan_cache_mode → ④ 그래도 안 되면 인덱스 설계나 쿼리 형태를 바꾼다. enable_* 스위치나 pg_hint_plan은 맨 마지막이고, 만료일을 붙인다.

ORDER BY가 인덱스를 타는 조건은? 계획에 Sort 노드가 남는 건 언제이고, Sort Method: external merge는 왜 문제인가요? 필수힌트: "B-tree 리프는 이미 정렬돼 있다"에서 시작한다

출발점은 하나다 — B-tree의 리프는 이미 정렬된 순서로 저장돼 있다. 그래서 정렬 요구가 그 리프 순서와 일치하면 정렬이라는 작업 자체가 필요 없어지고, 계획에서 Sort 노드가 통째로 사라진다.

타는 조건 셋 — ① ORDER BY 컬럼이 인덱스의 컬럼 순서와 일치하고, ② 정렬 컬럼 앞의 컬럼들이 등호로 고정돼 있고(그래야 그 구간 안이 정렬 상태다), ③ 정렬 방향이 일관될 것. 역순 전체는 Index Scan Backward로 처리된다.

Sort가 남는 경우 — 정렬 컬럼 앞에 범위 조건이 끼거나(구간이 여러 개가 되어 전체 순서가 깨진다), 인덱스에 없는 컬럼으로 정렬하거나, 여러 컬럼의 정렬 방향이 엇갈릴 때다.

external merge가 왜 문제인가 — work_mem을 넘겨 디스크 임시 파일에 청크를 쓰고 다시 읽어 병합하기 때문이다. Buffers의 temp read/written에 그 양이 찍힌다. 게다가 LIMIT 20이 붙어 있어도 소용이 없다 — 정렬은 입력 전체를 봐야 첫 행이 나오므로 조기 종료가 불가능하다. top-N heapsort도 마찬가지로 메모리는 N건 몫만 쓰지만 입력은 전부 읽는다.

처방의 순서는 ① 인덱스 순서를 정렬에 맞춰 Sort를 없애는 것이 먼저이고(Buffers가 수만에서 수십으로 떨어진다), ② 그게 불가능할 때만 세션 work_mem을 올려 디스크 정렬을 메모리 정렬로 되돌린다. ②만 하면 "덜 느린 전수 정렬"이 될 뿐이고 데이터가 늘면 다시 넘친다. — MySQL에서 같은 신호가 Extra: Using filesort다.

actual time=0.003..0.003이면 눈 깜짝할 새인데, 왜 이 노드가 병목이라는 거죠? 함정힌트: 그 줄에 같이 찍힌 다른 숫자 하나를 놓쳤다

loops를 놓쳤기 때문이다. actual time과 actual rows는 이 노드가 한 번 실행될 때의 평균값이고, 총량은 × loops다.

5절의 계획에서 Index Scan using users_pkey … (actual time=0.078..0.078 rows=1 loops=500000)이 정확히 이 경우다. 한 번에 0.078ms라 아무 문제 없어 보이지만, 0.078 × 500,000 = 39,000ms — 41초짜리 쿼리의 39초가 여기 있다.

같은 줄의 Buffers가 결정적인 방증이다. 그 노드 혼자 shared hit=1450122 — 같은 users 페이지들을 50만 번 되짚느라 145만 페이지 읽기를 기록했다. 캐시에 다 있어서 디스크는 안 갔지만(hit), 페이지를 찾고 락을 잡고 튜플을 꺼내는 CPU 비용은 그대로 나갔다 — 4절에서 말한 "hit이 압도적인데 느린 CPU 병목"의 교과서적 모습이다.

병렬 계획에서도 같은 규칙이 적용된다 — Parallel Seq Scan의 loops는 리더 + 워커 수이고 rows는 프로세스당 평균이라, 전체 처리 행 수를 알려면 역시 곱해야 한다.

cost=64273이면 64초쯤 걸린다는 뜻인가요? 함정힌트: 단위가 무엇을 1로 잡은 값인지 떠올린다

아니다. cost의 단위는 시간이 아니다. seq_page_cost = 1.0, 즉 "순차로 읽은 페이지 한 장"을 1로 잡은 상대값이다. 그래서 cost=64273은 "대략 순차 페이지 6만 4천 장어치의 일"이라는 뜻이지 64초가 아니다.

이 값은 계획 후보들끼리 비교하라고 있는 것이지 절대 시간을 예측하라고 있는 것이 아니다. 그래서 실제 시간을 알고 싶으면 ANALYZE를 켜서 actual time과 Execution Time을 봐야 한다.

같이 알아야 할 파라미터가 random_page_cost(기본 4.0)다 — "랜덤하게 흩어진 페이지 한 장은 순차 네 장 값"이라는 선언이고, 회전 디스크 시절의 값이다. SSD에서는 랜덤과 순차의 실제 격차가 훨씬 작으므로 이 값을 그대로 두면 플래너가 인덱스 스캔을 실제보다 비싸게 평가해 불필요하게 Seq Scan을 고른다. SSD면 1.1 근처로 낮추는 것이 일반적이다.

그리고 cost의 앞뒤 두 숫자(시작..전체)를 구분하는 것이 LIMIT 쿼리에서 결정적이다 — Sort는 입력을 전부 읽어야 첫 행이 나오므로 시작 비용이 크고, Index Scan은 거의 0이다. 그래서 앞 20건만 필요한 쿼리에서는 전체 비용이 커도 시작 비용이 작은 계획이 이긴다.

계획에 Seq Scan이 떴습니다. 무조건 나쁜 건가요? 함정힌트: "정상 선택인 경우"를 세 가지 들 수 있어야 한다

아니다. Seq Scan이 정당한 선택인 경우가 셋 있다.

⑴ 테이블이 작을 때. 페이지 몇 장이면 다 읽히는데 인덱스를 거쳐 힙을 랜덤 접근할 이유가 없다. 로컬 100건짜리 테이블에서 Seq Scan이 뜨는 것은 정상이고, 그래서 로컬 EXPLAIN으로 운영 계획을 판단하면 안 된다.

⑵ 대상 행의 비율이 클 때. 테이블의 상당 비율을 읽어야 한다면 순차 I/O로 통째로 읽는 편이 랜덤 접근보다 싸다. 5절의 after 계획이 정확히 이 경우다 — 500만 행 중 50만 행을 읽어야 하니 플래너가 Seq Scan + Hash Join을 골랐고, 그게 옳았다.

⑶ Parallel Seq Scan + Gather. 워커 여럿이 힙을 나눠 읽는 대량 스캔의 정상 선택일 수 있다.

판별은 노드 이름이 아니라 "읽은 양 대비 남긴 양"이다
Rows Removed by Filter가 actual rows에 비해 압도적으로 크면 그때가 진짜 문제다

뒤집으면 더 중요한 이야기가 된다 — Index Scan이 찍혔다고 안심할 수도 없다. Index Cond 없는 Index Scan은 정렬 순서만 빌린 전수 조사이고, Rows Removed by Filter가 큰 Index Scan은 이름만 인덱스지 비용은 풀스캔에 가깝다. 노드 이름은 "무엇을 시도했나"이지 "얼마나 일했나"가 아니다.

노드별 Buffers를 다 더했더니 맨 위 Limit의 값보다 훨씬 큽니다. 왜 그렇죠? 가산점힌트: 그 값이 "그 노드만의 값"이 아니다

노드의 Buffers는 자식 수치를 포함한 누적값이기 때문이다. 맨 위 Limit의 Buffers가 트리 전체의 합이고, 그 아래 자식들의 수치가 이미 그 안에 들어 있다. 그래서 전부 더하면 같은 페이지를 여러 번 세게 된다.

제대로 읽는 법은 뺄셈이 아니라 "어느 노드에서 갑자기 커지는가"를 아래에서 위로 훑는 것이다. 2절의 계획을 보면 Index Scan on orders가 hit=5412 read=41856이고 부모인 Nested Loop이 hit=24292 read=41856이다 — read는 그대로인데 hit이 크게 늘었다. 차이가 생긴 그 지점이 페이지를 실제로 읽은 범인이고, 여기서는 inner의 products_pkey 반복 탐색(hit=18880)이 그 정체다.

같은 사고를 actual time에서도 한다 — 부모의 actual time에는 자식이 걸린 시간이 포함돼 있으므로, "이 노드가 자기 몫으로 쓴 시간"은 부모 시간에서 자식 시간을 빼야 나온다. 계획 시각화 도구(explain.depesz.com 등)가 색으로 보여주는 것이 정확히 이 "자기 몫"이다.

계획에 Index Scan이 찍혔고 조건도 전부 Index Cond에 들어가 있는데, Buffers가 수천 장입니다. 무슨 일인가요? 함정힌트: Index Cond에 찍혔다는 것과 "구간을 좁혔다"는 것은 다른 말이다

복합 인덱스의 leftmost prefix가 끊긴 경우다. (user_id, status, created_at) 인덱스에서 가운데 status 조건이 빠지면, created_at은 구간을 좁히지 못하고 인덱스 안에서 하나씩 걸러지기만 한다. 그런데 PostgreSQL의 계획 텍스트는 이 경우에도 완전히 좁힌 경우와 똑같이 Index Cond에 두 조건을 다 적어 준다.

MySQL이라면 key_len으로 "몇 바이트까지 썼나"가 드러나지만, PostgreSQL에는 그 칸이 없다. 그래서 판별은 두 가지로 한다 — ① 인덱스 정의의 컬럼 순서와 조건의 등호/범위를 직접 대조하고, ② BUFFERS의 읽은 페이지 수를 본다.

actual rows=2104인데 Buffers: shared hit=2318이면 결과 2천 건을 위해 페이지 2천 장을 읽은 것이고, 이는 user_id = 100의 엔트리 전부(4만 7천)를 훑은 흔적이다. (user_id, created_at) 인덱스였다면 같은 결과에 Buffers: shared hit=61 수준이 나온다.

낭비의 층이 두 가지라는 점을 구분해 말하면 답이 정확해진다 — Rows Removed by Filter는 "인덱스에 없는 컬럼 때문에 힙까지 읽고 버린 양"이고, Buffers의 과다는 "인덱스 안에서 훑고 버린 양"이다. 앞의 것은 힙 랜덤 I/O를 지불했고, 뒤의 것은 인덱스 리프를 헛돌았다.

"성능을 개선했습니다"를 보고할 때, 무슨 숫자를 근거로 대야 하나요? 시니어 변별힌트: "몇 초 → 몇 초"는 반박당하기 쉬운 숫자다. 그 이유부터

"2.4초에서 0.3초가 됐습니다"만 말하면 약하다. 시간은 캐시 상태·서버 부하·동시 트래픽에 따라 흔들리는 숫자여서, 다음 주에 다시 재면 다른 값이 나오고 "원래 그날 서버가 한가했던 거 아니냐"는 반박을 막을 수 없다. 4절의 예시가 그대로 그 증거다 — 같은 계획, 같은 쿼리가 캐시 상태만으로 3,842ms와 289ms 사이를 오갔다.

흔들리지 않는 숫자는 세 가지다.

Buffers
"읽는 페이지가 66,148장에서 103장으로". 계획이 같으면 캐시 상태와 무관하게 같은 값이 나온다 — "얼마나 일했나"의 숫자.
blks_per_call
pg_stat_statements에서 호출당 읽은 페이지. 운영에서 누적으로 확인되는 값이라 "스테이징에서만 그렇겠지"를 막는다.
사라진 노드·줄
"Sort 노드가 없어졌고 Rows Removed by Filter 줄이 사라졌다" — 메커니즘이 바뀌었다는 증거라 숫자보다 강하다.

그리고 이득 옆에 대가를 같이 적어야 보고가 완결된다 — 인덱스 크기 증가분, n_tup_hot_upd / n_tup_upd 비율 변화(HOT 탈락), 쓰기 p95, 흡수되어 삭제한 기존 인덱스. 대가를 적지 않은 보고는 "재봤더니 빨라졌다"와 구분되지 않는다.

마지막으로 기준선을 남긴다 — queryid, calls, mean_ms, blks_per_call, 그리고 stats_reset(언제부터의 누적인가). 이 다섯 줄이 석 달 뒤 "느려진 것 같은데요"에 답할 유일한 근거가 된다.

한 줄 요약
EXPLAIN은 통계로 쓴 견적서, EXPLAIN (ANALYZE, BUFFERS)는 실제로 실행해 받은 청구서다 — PostgreSQL의 계획 트리는 안쪽(들여쓰기가 깊은 쪽)부터 실행돼 바깥으로 올라오며, 모양(첫 자식이 outer) → 노드 이름(Seq Scan과 Index Cond 없는 Index Scan은 전수, 나머지는 좁힌 것) → 추정 rows vs 실제 rows(자릿수가 다르면 튜닝이 아니라 통계 교정이 먼저 — 오추정 하나가 상위 노드의 조인 방식 선택을 통째로 틀리게 만든다) → Buffers(shared hit/read로 I/O 병목인지 CPU 병목인지를 가르고, 캐시 상태에 흔들리는 시간 대신 전후 비교의 기준선이 된다) → 경고등(Rows Removed by Filter·external merge·Batches > 1·Heap Fetches·안쪽 loops) 순으로 읽는다. ANALYZE는 진짜로 실행하므로 변경문에 쓰면 데이터가 실제로 바뀐다 — BEGIN … ROLLBACK으로 감싸되 행 락·시퀀스·트리거·WAL은 되돌아오지 않는다는 것까지 안다. 느린 쿼리 개선은 측정(pg_stat_statements로 가장 비싼 쿼리를 숫자로, 락 대기와 제네릭 계획을 배제하고) → 가설(비용이 새는 지점을 힙 랜덤 I/O 사슬로, 예상 효과를 숫자로) → 검증(같은 파라미터의 실측 + 쓰기 비용·HOT 탈락·다른 쿼리·DDL 리스크까지 한 호흡에) → 고정(auto_explain·쿼리 수 단정·EXPLAIN 단정·pg_stat_statements 기준선·PR 템플릿을 설정과 코드로)의 사이클이며, 고정까지 가야 다음 느린 쿼리가 사용자 항의가 아니라 알람으로 도착한다.
