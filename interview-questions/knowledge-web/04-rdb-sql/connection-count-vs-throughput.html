DB 커넥션 수와 처리량
커넥션은 "처리 능력"이 아니라 "줄 서는 자리"다

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "DB 커넥션 수와 처리량(throughput)의 관계 — 커넥션을 늘리면 항상 빨라지나요?"
커넥션을 늘리면 처리량은 어느 지점까지만 오르고, 그 뒤로는 평평해지다가 오히려 떨어진다. DB가 실제로 동시에 일할 수 있는 양은 커넥션 수가 아니라 DB 서버의 CPU 코어 수와 디스크 병렬성이 정하기 때문이다. 그 한계를 넘긴 커넥션은 일을 더 시키는 게 아니라 경합을 더 만든다 — ① CPU 컨텍스트 스위칭 ② 디스크 I/O 큐 적체와 순차 I/O의 랜덤화 ③ 락 경합 ④ 버퍼 풀·내부 뮤텍스 경합, 이 네 사슬이 쿼리 하나하나를 느리게 만들어 총처리량을 깎는다. 그래서 "느리니까 커넥션을 늘리자"는 처방은 병목 위치(앱 스레드 풀 → 커넥션 풀 → DB CPU → 디스크 I/O → 락 대기)를 확인한 뒤에만 유효하고, 풀 크기는 경험식으로 출발해 부하 테스트와 active / pending / acquire-time 메트릭으로 고정한다.
출제 의도 — 무엇을 보는 질문인가
"느리니까 커넥션을 늘리자"는 직관이 왜 역효과인지(경합 증가)를 아는지 확인한다. 더 깊게는 병목의 위치를 확인하지 않은 처방이 얼마나 위험한지에 대한 감각을 검사한다 — 커넥션 풀 크기는 설정 한 줄이라 누구나 만질 수 있는데, 그 한 줄이 DB 전체를 무너뜨릴 수 있다는 걸 아는 사람과 모르는 사람의 운영 태도가 다르다.
이 페이지의 1차 목표: 비용을 "성능 저하"·"부하 증가" 같은 뭉뚱그린 말이 아니라 이름 붙은 메커니즘 사슬로 말하기, 특히 랜덤 vs 순차 I/O 비용 모델을 채우기. 풀 크기 산정(Little's law)과 고갈 진단은 2장 문서 (02-spring/thread-pool-connection-pool-sizing, 02-spring/hikaricp-connection-pool-exhaustion)에 있으므로 여기서는 DB 서버 내부에서 무슨 일이 벌어지는가에 집중한다.

1. 큰 그림 — 처리량 곡선은 오르다가 꺾인다

커넥션 수(= DB에 동시에 들어와 있는 요청 수)를 가로축, 초당 처리 건수를 세로축으로 그리면 거의 모든 DB에서 같은 모양이 나온다. 이 그림 하나가 이 질문의 전부다.

그림 1. 커넥션 수 대비 처리량 곡선 — 선형 증가 → 포화 → 붕괴
① 선형커넥션 < 코어

CPU가 놀고 있다. 커넥션을 늘리는 만큼 처리량이 는다. "늘리면 빨라진다"는 직관은 이 구간의 경험이다.

② 포화CPU·디스크 100%

커넥션을 더 넣어도 처리량은 그대로. 새로 들어온 요청은 DB 안에서 대기할 뿐이다.

③ 붕괴대기가 비용을 만듦

대기 중인 요청이 CPU·디스크·락·버퍼를 건드려 쿼리 1건이 느려지고, 총처리량이 오히려 떨어진다.

암기 문장 — 커넥션의 정체
커넥션은 "DB가 동시에 처리할 수 있는 능력"이 아니라
"DB 앞에 동시에 서 있을 수 있는 자리 수"다.

능력의 상한은 DB 서버의 CPU 코어 수와 디스크 병렬성이 정한다. 자리를 늘린다고 창구가 늘지 않는다.

비유 — 창구 8개에 번호표 500장
은행 창구(코어)는 8개인데 번호표(커넥션)를 500장 뿌린 상황이다. 번호표를 더 뿌린다고 창구가 늘지 않는다. 오히려 대기 손님이 로비를 가득 채워 직원 이동을 방해하고(컨텍스트 스위칭), 서류 보관함 앞에서 서로 부딪히고(버퍼 풀 경합), 같은 계좌를 처리하려고 서로 기다린다(락 경합). 창구 직원이 서류를 가지러 창고에 갈 때도 손님 500명의 서류가 창고 곳곳에 흩어져 있어 한 번에 못 가져온다(순차 I/O의 랜덤화).

왜 이 곡선이 생기나 — DB는 커넥션마다 실행 단위를 하나씩 붙인다

MySQL커넥션 1개 = 서버 스레드 1개

쿼리가 오면 그 스레드가 실행한다. 스레드라 비교적 가볍지만, 500개면 스레드 500개가 살아 있다.

PostgreSQL커넥션 1개 = 백엔드 프로세스 1개 (fork)

스레드보다 훨씬 무겁다 — 프로세스마다 독립 메모리, 캐시된 카탈로그를 따로 가진다. 그래서 PG 앞에는 PgBouncer 같은 풀러가 사실상 표준이다.

즉 커넥션 500개 = DB 서버 안에 실행 단위 500개가 살아 있다는 뜻이다. 이 중 실제로 CPU 위에서 도는 건 코어 수만큼뿐이고, 나머지는 어딘가에서 대기 중이다. 어디서 어떻게 대기하느냐가 2절의 네 사슬이다.

2. 역효과의 메커니즘 사슬 — "경합 증가"를 네 개의 이름으로 쪼개기

겨냥하는 공백
비용을 말할 때마다 "성능 저하", "메모리 부하", "부하 증가"에서 멈췄다. 면접관이 "커넥션을 늘리면 왜 역효과인가요?"라고 물을 때 "경합이 늘어서요"는 답의 제목일 뿐이다. 아래 네 사슬을 각각 이름 → 원인 → 결과의 화살표로 말할 수 있어야 한다.
그림 2. 커넥션 증가가 총처리량을 깎는 네 갈래 — 답할 때는 이 순서(A→B→C→D)로 이름을 먼저 부른다
암기 장치 — 4사슬을 "C·D·L·M"으로
CPU 스위칭 · Disk 큐+랜덤화 · Lock 경합 · Memory 버퍼 풀

요청이 DB 안에서 지나가는 자원 순서 그대로다: CPU에 올라가 → 디스크를 읽고 → 다른 트랜잭션과 락을 다투고 → 그 사이 메모리(버퍼 풀)를 나눠 쓴다. 순서를 외우면 하나도 빠뜨리지 않는다.

A사슬 A — CPU 컨텍스트 스위칭

그림 3. 사슬 A — 실행 가능 스레드가 코어 수를 넘으면 CPU가 "일" 대신 "교대"에 쓰인다
함정 — "I/O 대기 중인 스레드는 CPU를 안 쓰니까 괜찮지 않나?"
커넥션이 많으면 깨어나는 스레드도 그만큼 많다. I/O가 끝날 때마다 깨어나 run queue에 줄을 서고, 그 줄이 코어 수보다 길면 다시 시분할 비용이 든다. 잠든 동안은 공짜지만 깨어나는 순간마다 값을 치른다.

B사슬 B — 디스크 I/O 큐, 그리고 순차 I/O의 랜덤화 최우선 공백

겨냥하는 공백 — 랜덤 vs 순차 I/O 비용 모델
기본 구간에서 5회 연속 비어 있던 축이다. 북마크 룩업(Q2)·페이지 분할(Q3)·redo log(Q5)가 전부 이 축 위에 있었고, 여기서는 "왜 디스크가 병목일 때 동시성을 올리는 게 무의미하거나 해로운가"로 같은 축이 다시 등장한다. 먼저 비용 모델부터 고정한다.
그림 4. 랜덤 vs 순차 I/O 비용 모델 — 같은 블록 수라도 seek 횟수가 시간을 결정한다
암기 문장 — I/O 비용 모델
디스크 비용은 "몇 바이트를 읽었나"가 아니라 "헤드를 몇 번 옮겼나(seek 수)"로 센다.
순차 = seek 1회 + 전송, 랜덤 = 블록마다 seek.

이 한 줄이 북마크 룩업·페이지 분할·redo log(순차 쓰기)·그리고 지금 이 질문(동시성이 순차를 랜덤으로 만든다)을 전부 관통한다.

이제 커넥션을 늘렸을 때 디스크에서 벌어지는 일은 두 가지다.

(1)큐만 길어진다 — IOPS는 고정

디스크가 초당 처리할 수 있는 I/O 수(IOPS)는 장치가 정한 상수다. 이미 iostat %util이 100%라면 요청자를 늘려도 초당 처리되는 I/O는 1도 안 는다. 요청은 디스크 큐에 쌓이고 await(요청당 대기+처리 시간)만 길어진다. → 각 쿼리 느려짐 → 커넥션을 더 오래 물음 → 앱 풀도 마름.

(2)순차가 랜덤으로 뒤섞인다 — IOPS가 떨어진다

더 중요한 포인트. 쿼리 하나만 보면 인덱스 리프 따라가기·테이블 스캔은 순차적이다. 그런데 이런 쿼리 50개가 동시에 돌면 디스크가 받는 요청 스트림은 50개 쿼리의 요청이 번갈아 섞인 것이 된다. 아래 그림.

그림 5. 순차 I/O의 랜덤화 — 동시성이 올라갈수록 디스크 총처리량이 순차 수준에서 랜덤 수준으로 내려간다
그래서 — 디스크 병목에선 커넥션을 줄이는 것이 총 디스크 처리량을 올린다
동시 스트림 수가 줄면 각 스캔이 순차성을 회복해 seek가 사라진다. 6절 사례("줄였더니 빨라졌다")의 물리적 근거 중 하나다. OS와 디스크 컨트롤러가 요청을 재정렬(elevator)해 완화해 주긴 하지만, 요청자 수가 많을수록 재정렬로 살릴 수 있는 순차성 자체가 줄어든다.
SSD · 클라우드 블록 스토리지에서는?
seek 비용이 없으니 (2)는 약해지고 (1)이 주로 남는다. 다만 클라우드 볼륨은 IOPS 자체가 상품 스펙으로 상한이 걸려 있어 (1)이 더 일찍, 더 딱딱하게 온다. "SSD니까 괜찮다"가 아니라 "SSD니까 큐 적체가 먼저 온다"로 답한다.

C사슬 C — 락 경합

그림 6. 사슬 C — 락 대기는 "자원을 쥔 채 기다리는" 대기라서 스스로를 증폭한다
핫 로우재고 1건 · 카운터 1행

처리량은 결국 그 행을 잠그고 푸는 속도로 직렬화된다. 커넥션 500개든 5개든 그 행은 한 번에 하나씩만 갱신되므로, 500개는 처리량을 못 올리고 대기열과 데드락 검사 비용만 만든다.

2장 연결DB 내부 현상, 장애는 앱 전체

락 대기로 트랜잭션이 길어지면 → 커넥션 점유 시간 ↑ → 앱 풀 고갈 → 톰캣 스레드 고갈. 락 경합은 DB 안에서 생기지만 터지는 곳은 앱이다.

D사슬 D — 버퍼 풀·내부 자원 경합

그림 7. 사슬 D — 커넥션이 버퍼 풀을 두 방향(배분·워킹셋)에서 압박해 결국 디스크 사슬을 다시 키운다
가산점 — MySQL은 왜 innodb_thread_concurrency를 갖고 있나 가산점
내부 뮤텍스·래치 경합을 DB 스스로 억제하기 위해서다. 커넥션이 아무리 많아도 InnoDB 안에서 동시에 실행되는 스레드 수에 상한을 두는 옵션 — "DB조차 동시 실행 단위를 코어 근처로 묶고 싶어 한다"는 증거로 인용하면 좋다.
네 사슬을 한 문장으로 — 이 문장을 말한 뒤 어느 사슬을 파고들어도 한 단계 더 내려갈 수 있으면 통과
"커넥션을 늘리면 DB 안의 동시 실행 단위가 늘고, 그것이 CPU에선 컨텍스트 스위칭, 디스크에선 큐 적체와 순차 I/O의 랜덤화, 트랜잭션 사이에선 락 경합, 메모리에선 버퍼 풀 몫 감소와 히트율 하락을 일으켜 쿼리 하나하나가 느려지고 총처리량이 떨어진다."

3. 트레이드오프 양면 — 늘리는 것이 맞는 경우와 틀린 경우

겨냥하는 공백 — 트레이드오프를 한 호흡에 양면으로
"늘리면 안 된다"로 끝내면 반쪽이다. 늘리는 것이 정답인 조건과 오답인 조건을 같은 문장 안에서 대비시킨다.
상황 (DB 쪽 지표)커넥션 늘리기의 효과판단
DB CPU 여유(예: 40%), 디스크 여유, 락 대기 없음, 앱 pending 발생처리량 선형 증가 (곡선 ①)늘리는 게 맞다
DB CPU 포화, 앱 pending 발생처리량 그대로, DB 응답시간 ↑ (곡선 ②)늘려도 소용없음 — 점유 시간 단축·쿼리 튜닝
디스크 %util 100%, await 상승IOPS 정체 + 순차 I/O 랜덤화로 처리량 ↓ (곡선 ③)줄이는 게 맞다 — 인덱스·버퍼 풀·I/O 줄이기
락 대기 지표 상승충돌 확률 ↑, 트랜잭션 장기화줄이거나, 락 범위·트랜잭션 길이 축소
DB 여유 있는데 앱 pending도 없음아무 효과 없음병목이 다른 곳 (앱 CPU, 외부 API)
양면 문장 — 그대로 말하기
"커넥션을 늘리면 DB가 놀고 있을 때는 놀던 코어를 채워 처리량이 오르지만, DB가 이미 포화일 때는 대기 줄을 DB 내부로 옮겨 컨텍스트 스위칭·I/O 랜덤화·락 경합만 키워 처리량이 떨어진다. 그래서 늘리기 전에 DB 쪽 지표로 어느 구간에 있는지부터 확인한다."

"늘려도 되는가"는 앱 메트릭이 아니라 DB 메트릭이 결정한다.

그림 8. 같은 대기라도 DB 안에서는 자원을 쥔 채 기다리고(비쌈), 앱 풀에서는 스레드가 park만 한다(쌈)
단, 안전장치가 함께 필요하다
앱 쪽 대기가 톰캣 스레드를 오래 묶어 스레드 풀 고갈로 번지지 않도록 connection-timeout을 짧게(예: 3초) 두고 빨리 실패시킨다. "싼 대기"도 무한정 쌓이면 앱 스레드 풀이라는 다음 자원을 마르게 한다 (고갈 문서 5절).

4. 병목 위치 확인 순서 — 처방 전 진단 체크리스트

겨냥하는 공백 — 목록 인출
장애 중에 "어디가 병목인지 어떻게 확인하나요?"를 받으면 아래 다섯 단계를 순서대로, 각 단계의 확인 지표와 함께 꺼낼 수 있어야 한다. 순서에 의미가 있다 — 요청이 흐르는 방향(앱 → DB → 디스크)을 따라가며, 앞 단계가 병목이 아님을 확인한 뒤 다음으로 내려간다.
그림 9. 진단 순서 = 요청이 흐르는 방향. 앞 단계가 아님을 확인한 뒤 다음으로 내려간다
암기 카드 — 병목 위치 확인 5단계 (단계 · 지표 · 시그니처 · 처방)
1
앱 스레드 풀 — tomcat.threads.busy vs max, 앱 CPU 병목 시그니처: busy가 max에 붙고 DB는 한가 → 스레드 수 재산정, 앱 CPU 병목 확인
2
커넥션 풀 — hikaricp.connections.active/pending, acquire 시간 active = max, pending > 0, acquire ↑ → 여기서 멈추지 말 것. pending은 "커넥션이 안 돌아온다"이지 "개수가 모자란다"가 아니다. [3]~[5]로 내려간다
3
DB CPU — DB 호스트 CPU, Threads_running, vmstat cs/r CPU 90%↑, Threads_running ≫ 코어, cs 폭증 → 커넥션 줄이기 + 쿼리 CPU 비용(정렬·조인·함수) 튜닝
4
디스크 I/O — iostat %util/await/r/s, 버퍼 풀 히트율 %util 100%, await ↑, 히트율 ↓ → 커넥션 줄이기 + 인덱스·커버링·버퍼 풀 확대(읽는 페이지 수 줄이기)
5
락 대기 — Innodb_row_lock_waits, sys.innodb_lock_waits, PG wait_event_type=Lock 락 대기 수·시간 ↑, PROCESSLIST에 대기 다수 → 트랜잭션 짧게, 락 범위 축소, 핫 로우 분산

연상: "스-커-씨-디-락" — 스레드 풀 → 커넥션 풀 → CPU → Disk → 락. 앱 2단계, DB 3단계.

각 단계를 읽는 법 — 갈림길 3개

[1]→[2]DB 쪽인가 아닌가

앱 스레드가 놀고 있는데 커넥션 pending이 있다 → 문제는 DB 쪽. 스레드는 꽉 찼는데 커넥션은 여유 → DB와 무관한 병목(외부 API, 앱 CPU).

[3] vs [4]CPU 바운드 vs I/O 바운드

DB CPU 높고 디스크 한가 → CPU 바운드(정렬·조인·함수 무거운 쿼리) → 연산량을 줄인다. CPU 낮은데 iowait·%util 높음 → I/O 바운드(버퍼 풀 미스, 풀스캔) → 읽는 페이지 수를 줄인다.

[5]자원은 노는데 느리다

CPU도 디스크도 한가한데 느리면 락 대기를 의심한다. 트랜잭션들이 서로를 기다리는 상태 — 이때 커넥션을 늘리면 대기자만 는다.

-- [3] MySQL: 실제로 실행 중인 스레드 수 (커넥션 수와 다르다)
SHOW GLOBAL STATUS LIKE 'Threads_running';    -- 코어 수의 몇 배면 CPU 경합 의심
SHOW GLOBAL STATUS LIKE 'Threads_connected';  -- 이건 그냥 붙어 있는 수

-- [4] MySQL: 버퍼 풀 히트율 — reads(디스크) / read_requests(논리)
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';

-- [5] MySQL: 지금 누가 누구를 기다리는가
SELECT * FROM sys.innodb_lock_waits;

-- [3]~[5] PostgreSQL: 세션별로 무엇을 기다리는지 한 번에
SELECT wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE state = 'active'
GROUP BY 1, 2 ORDER BY 3 DESC;
-- wait_event_type: NULL=CPU 실행 중 · 'IO'=디스크 · 'Lock'=락 · 'LWLock'=내부 래치
이 체크리스트의 존재 이유
"커넥션을 늘릴까 줄일까"가 아니다. 어느 자원이 포화인지 알기 전에는 어떤 처방도 도박이라는 것 — 출제 의도가 말하는 "병목 위치를 확인하지 않은 처방의 위험"이 정확히 이것이다.

5. 풀 크기를 고정하는 방법 — 경험식으로 출발, 측정으로 확정, 알람으로 유지

겨냥하는 공백 — 안전망 고정
풀 크기를 "감으로 50" 또는 "공식대로 17"로 정하고 끝내는 게 아니라, 부하 테스트로 곡선의 꺾이는 지점을 찾고 메트릭 알람으로 이탈을 감지하는 체계까지 말한다. 세 단계: 경험식 → 부하 테스트 → 알람.

5-1. 경험식 — HikariCP 위키(About Pool Sizing)의 출발점

암기 카드 — 경험식과 각 항의 뜻
connections = (DB 서버 코어 수 × 2) + 유효 스핀들 수
코어
동시에 CPU 위에서 돌 수 있는 쿼리의 상한사슬 A. 이 수를 넘으면 컨텍스트 스위칭이 시작된다
×2
I/O 대기 동안 다른 스레드가 CPU를 쓰게 하는 겹치기(overlap) 여유I/O 대기 비율이 높을수록 계수는 더 커도 되고, 데이터가 전부 메모리에 있으면 1에 가까워도 된다
스핀들
독립적으로 I/O를 동시에 처리할 수 있는 디스크 수 = 디스크 병렬성사슬 B. 스핀들 수만큼은 동시에 I/O를 걸어도 서로 큐를 만들지 않는다
한계 1경험식이지 정리가 아니다

SSD·NVMe·클라우드 볼륨에는 "스핀들"이라는 물리 단위가 없다. 큐 깊이·IOPS 상한을 대신 넣어야 하는데 정확한 환산은 없다. → 자릿수를 잡는 용도로만 쓰고 최종 숫자는 측정으로.

한계 2DB 전체 기준 숫자다

앱 인스턴스 N대면 DB에는 N × 풀 크기가 꽂힌다. 공식 값은 인스턴스 수로 나눠야 한다. 오토스케일링으로 10대 → 30대가 되면 DB 커넥션도 3배 — 최대 인스턴스 수로 계산하지 않으면 피크에 붕괴 구간으로 밀려난다.

5-2. 부하 테스트 — 곡선의 꺾이는 지점을 직접 그린다

  1. 실제와 비슷한 쿼리 믹스·데이터 크기로 부하 도구(k6, Gatling 등) 준비
  2. 풀 크기를 단계적으로 바꿔가며(예: 5 → 10 → 20 → 40 → 80) 같은 부하를 건다
  3. 각 단계에서 기록: TPS, p50/p99 응답시간, DB CPU, iostat %util, 락 대기 수
  4. TPS가 더 이상 오르지 않는 지점(포화)과 p99가 급격히 나빠지는 지점(붕괴)을 찾는다
  5. 포화 지점보다 약간 아래를 채택 — 여유는 커넥션 수가 아니라 응답시간에 둔다
너무 크면시한폭탄

"일단 크게 잡아두면 안전하겠지"가 가장 위험하다. 큰 풀은 평소엔 조용하다가 트래픽 피크에 DB를 붕괴 구간으로 밀어 넣는다.

너무 작으면풀보다 점유 시간 먼저

앱 pending이 상시 발생한다. 이때도 풀을 키우기 전에 커넥션 점유 시간(트랜잭션 안의 외부 호출, 느린 쿼리)부터 줄인다 — 같은 TPS를 더 작은 풀로 감당하는 게 언제나 DB에 이롭다.

5-3. 메트릭과 알람 — 결정을 코드로 고정한다

BEFORE — "느리다"는 보고에 감으로 늘린 설정
spring:
  datasource:
    hikari:
      maximum-pool-size: 200   # 근거 없음. 10대면 DB에 2,000개
      connection-timeout: 30000 # 30초 대기 → 톰캣 스레드까지 묶임
      # 메트릭 없음 → pending/acquire를 볼 수 없다
AFTER — 측정으로 정한 크기 + 빨리 실패 + 관측 가능
spring:
  datasource:
    hikari:
      maximum-pool-size: 12    # 부하 테스트 포화 지점 (8코어, 10대 → DB 120)
      minimum-idle: 12         # 고정 크기 — 피크에 생성 비용 없음
      connection-timeout: 3000 # 3초 안에 못 받으면 실패 — 대기 전이 차단
      leak-detection-threshold: 30000
management:
  metrics:
    enable:
      hikaricp: true           # active/idle/pending/acquire/usage/timeout
암기 카드 — HikariCP 알람 지표 4 + DB 지표 (임계값은 부하 테스트에서 본 정상 범위 기준)
P
hikaricp.connections.pending — 커넥션을 기다리는 스레드 수 0보다 큰 상태가 지속되면 "커넥션이 안 돌아온다". 4절 체크리스트의 시작 신호이지, "늘려라"는 신호가 아니다
A
hikaricp.connections.acquire (p99) — 커넥션을 받기까지 기다린 시간 응답시간 악화의 선행 지표
U
hikaricp.connections.usage (p99) — 커넥션을 물고 있는 시간 이게 늘면 풀 크기가 아니라 점유 시간이 문제다 (트랜잭션 안의 외부 호출·느린 쿼리)
T
hikaricp.connections.timeout — 획득 실패 건수 0이 아니면 이미 사용자 영향
DB
Threads_running > 코어 배수 지속 시간 · 락 대기 시간 · 버퍼 풀 히트율 하락 앱 pending과 DB 지표를 같은 대시보드에 나란히 — "pending이 뜨는데 DB CPU는 포화인가 여유인가"를 한눈에 읽어야 4절 처방 방향을 즉시 고른다

연상: P·A·U·T — Pending(기다리는 수) → Acquire(기다린 시간) → Usage(물고 있는 시간) → Timeout(포기한 수). 요청이 커넥션을 만나는 순서 그대로.

풀 크기 결정 근거(테스트 날짜·부하 조건·채택 이유)는 설정 파일 주석이나 운영 위키에 남긴다. 반년 뒤 다른 사람이 "느리니까 늘리자"를 반복하지 않게 하는 것까지가 안전망이다.

6. 실제 사례 — 풀을 줄였더니 빨라졌다

HikariCP 위키가 인용하는 Oracle 성능팀의 시연이 대표 사례다. 수천 개 수준(약 2,000개)이던 커넥션 풀을 100개 미만으로 줄이자 쿼리 응답시간이 수십 배 빨라지고 처리량이 올랐다. 하드웨어도 쿼리도 그대로였다. 이 결과를 "신기한 일"이 아니라 구조적으로 설명할 수 있어야 한다. 아래는 같은 구조의 전형적 시나리오다(예시 수치).

그림 10. 같은 하드웨어·같은 쿼리에서 풀 크기만 300 → 1,000 → 80으로 바꿨을 때
늘렸는데 왜 나빠졌나1~2절로 읽기
  • A 대기자 3배 → 컨텍스트 스위칭 폭증 → CPU 100% 중 쿼리 실행 몫 ↓
  • D 세션 메모리가 버퍼 풀 잠식 + 동시 쿼리 워킹셋 > 버퍼 풀 → 히트율 ↓
  • B 디스크 읽기 ↑, 그 읽기들이 서로 뒤섞여 랜덤화
  • C 락 걸리는 UPDATE의 대기열 3배
  • 타임아웃 로그가 줄어든 건 앱 대기가 DB 안으로 옮겨갔기 때문 — 더 비싼 곳에서 대기
줄였는데 왜 좋아졌나거꾸로 읽기
  • A 동시 실행 단위가 코어 근처 → 스위칭 사라짐 → 같은 CPU 75%가 이전 100%보다 많이 처리
  • D 워킹셋이 버퍼 풀 안에 들어옴 → 히트율 회복
  • B 줄어든 디스크 읽기가 덜 섞여 순차성을 되찾음
  • C 동시 트랜잭션 ↓ → 충돌 확률 ↓ → 트랜잭션 짧아짐
  • 쿼리 1건이 빨라져 커넥션이 빨리 돌아옴 → 80개로 1,000개보다 많은 요청 처리. 대기는 앱 풀에서 park만
사례의 교훈 — 한 문장
"대기 줄은 어디에든 생긴다. 그 줄을 DB 안(비싼 대기)에 세울 것인가, DB 앞의 앱 풀(싼 대기)에 세울 것인가가 풀 크기 결정의 본질이다."

작은 풀은 DB를 최적 동시성으로 돌리기 위한 의도적인 관문(throttle)이다. 남은 pending을 더 줄이고 싶다면 풀을 키우는 게 아니라 점유 시간을 줄인다 — 트랜잭션 안의 외부 호출 제거, 느린 쿼리 튜닝, 읽기 트래픽의 레플리카 분리. Little's law(동시수 = TPS × 점유 시간)가 그대로 말해 준다.

7. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별 가산점 추가 = md에 없어 이 페이지에서 추가한 질문.

"그럼 커넥션을 늘리는 게 정답인 경우는 언제인가요?"
DB가 놀고 있을 때. 구체적으로 DB CPU 여유, 디스크 %util 여유, 락 대기 없음 — 이 세 가지가 동시에 만족되는데 앱 쪽 hikaricp.connections.pending이 발생하면, 커넥션이 DB의 처리 능력보다 적어서 코어가 비는 상태다(곡선 ① 구간). 이때는 늘리면 처리량이 선형으로 오른다. 반대로 셋 중 하나라도 포화면 늘리는 것은 대기 줄을 DB 내부로 옮기는 것일 뿐이다. "늘려도 되는가"는 앱 메트릭이 아니라 DB 메트릭이 결정한다는 것이 답의 핵심.
"디스크가 병목인 상황에서 커넥션을 늘리면 정확히 무슨 일이 일어나나요?"
두 가지. 첫째, 디스크의 IOPS는 장치가 정한 상수라 요청자를 늘려도 초당 처리되는 I/O는 안 늘고 큐(await)만 길어진다. 둘째, 더 나쁜 쪽 — 각 쿼리가 혼자서는 순차적으로 읽더라도 여러 쿼리의 요청이 디스크에 번갈아 도착하면 디스크 입장에서는 랜덤 접근이 된다. HDD라면 매 요청마다 seek가 발생해 총처리량이 순차 수준에서 랜덤 수준으로 떨어진다 — 자릿수가 다른 하락이다. 그래서 디스크 병목에서 동시성 증가는 무의미를 넘어 유해하고, 오히려 커넥션을 줄여 각 스캔의 순차성을 되찾는 것이 총 디스크 처리량을 올린다. SSD·클라우드 볼륨은 seek가 없어 두 번째 효과는 약하지만, IOPS 상한이 상품 스펙으로 딱딱하게 걸려 있어 첫 번째 효과는 더 일찍 온다.
"풀을 줄였더니 앱에서 커넥션 획득 대기가 늘었습니다. 잘못 조정한 건가요?" 시니어 변별
대기가 어디로 옮겨갔는지를 먼저 본다. 줄이기 전에는 요청이 DB 내부에서 CPU·락·버퍼 풀을 쥔 채 기다렸고(비싼 대기), 줄인 뒤에는 앱 풀에서 스레드가 park된 채 기다린다(싼 대기 — DB 자원 소모 0). 판단 기준은 대기 발생 여부가 아니라 최종 처리량과 p99 응답시간이다. 둘이 좋아졌다면 조정은 옳다 — 대기가 눈에 보이는 위치로 옮겨왔을 뿐이다. 남은 대기를 줄이고 싶다면 풀을 도로 키우는 게 아니라 점유 시간을 줄인다 (트랜잭션 밖으로 외부 호출 빼기, 느린 쿼리 튜닝, 읽기 레플리카 분리). 단, 앱 쪽 대기가 톰캣 스레드를 오래 묶어 스레드 풀 고갈로 번지지 않도록 connection-timeout을 짧게 두고 빨리 실패시키는 안전장치를 같이 건다. "대기 총량"이 아니라 "대기의 위치와 비용"으로 답하면 시니어 답변.
"HikariCP 공식(코어 × 2 + 스핀들)을 그대로 쓰면 되지 않나요?"
경험식이라 자릿수를 잡는 용도로만. 항의 의미는 분명하다 — 코어 수는 CPU 병렬성 상한, ×2는 I/O 대기 동안 다른 스레드가 CPU를 쓰는 겹치기 여유, 스핀들 수는 디스크 병렬성. 하지만 SSD·NVMe·클라우드 볼륨에는 스핀들이라는 물리 단위가 없고, I/O 대기 비율이 워크로드마다 달라 ×2가 맞는지도 알 수 없다. 그래서 공식으로 출발점(예: 8코어 → 20 전후)을 잡고, 부하 테스트에서 풀 크기를 단계적으로 바꿔가며 TPS 포화 지점과 p99 붕괴 지점을 직접 그려 채택한다. 인스턴스 N대의 합이 DB 기준 숫자라는 것, 오토스케일링 최대 대수까지 곱해 봐야 한다는 것도 공식이 말해 주지 않는 부분.
"MySQL과 PostgreSQL에서 커넥션의 비용이 다른가요? 앱이 오토스케일링되면요?" 가산점
다르다. MySQL은 커넥션당 스레드, PostgreSQL은 커넥션당 프로세스(fork)라 PG 쪽이 메모리·생성 비용이 훨씬 크고, 그래서 PG 생태계에서는 PgBouncer 같은 외부 커넥션 풀러를 DB 앞에 두는 것이 사실상 표준이다. 오토스케일링은 이 문제를 증폭한다 — 앱이 10대에서 40대로 늘면 풀 크기를 안 바꿔도 DB 커넥션은 4배가 되어 붕괴 구간으로 밀려나고, 스케일 아웃이 오히려 DB 장애를 만든다. 대책은 두 방향: ① 앱 풀 크기를 최대 인스턴스 수 기준으로 나눠 잡기 ② DB 앞에 프록시/풀러(PgBouncer, ProxySQL, RDS Proxy 류)를 두어 앱 커넥션 수와 무관하게 DB 커넥션 총량을 고정하기. 후자는 "DB 동시성의 상한을 DB 바로 앞에서 한 곳으로 통제"하는 구조라 인스턴스 수가 유동적인 환경에서 특히 유효하다.
"pending이 0보다 크면 커넥션이 부족하다는 뜻 아닌가요?" 추가
아니다 — pending은 "커넥션이 안 돌아오고 있다"는 뜻이지 "개수가 모자란다"는 뜻이 아니다. 안 돌아오는 이유는 [3] DB CPU 포화, [4] 디스크 포화, [5] 락 대기, 또는 앱 코드가 트랜잭션 안에서 외부 API를 호출해 커넥션을 오래 물고 있는 것(점유 시간) 중 하나다. 이 중 어느 것도 커넥션을 늘려서 해결되지 않고, [3]~[5]라면 늘릴수록 나빠진다. 그래서 pending은 4절 체크리스트를 시작하라는 신호이고, usage(점유 시간 p99)와 DB 지표를 같이 봐야 "개수 문제인지, 점유 시간 문제인지, DB 포화 문제인지"를 가를 수 있다. 개수 문제라고 결론 나는 경우는 오직 DB 세 지표가 모두 여유인데 pending이 뜰 때뿐이다.
"CPU가 100%인데 처리량이 안 오릅니다. CPU가 병목이면 커넥션을 줄여도 CPU는 100% 아닌가요?" 추가
같은 100%라도 "무엇에 쓰인 100%"인지가 다르다. 커넥션이 코어 수를 크게 넘으면 CPU 시간의 상당 부분이 컨텍스트 스위칭(레지스터·스택 저장/복원, 캐시 재적재)과 내부 뮤텍스 스핀 대기에 소모된다 — 이건 "쿼리 실행"이 아니라 "쿼리 사이를 오가는" CPU다. 커넥션을 코어 근처로 줄이면 스위칭이 사라져 같은 CPU 시간이 온전히 쿼리에 쓰이고, 6절 사례처럼 CPU가 75%로 내려가면서도 TPS는 오른다. 확인 지표는 vmstat의 cs(초당 스위칭)와 r(run queue 길이) — 커넥션을 줄였을 때 cs가 급감하고 TPS가 오르면 CPU 병목의 정체가 "쿼리 연산량"이 아니라 "스위칭 오버헤드"였다는 뜻이다. 둘 다 아니라면 그때 쿼리 자체의 연산량(정렬·조인·함수)을 줄인다.
"순차 I/O가 랜덤화되는 문제를 커넥션을 줄이는 것 말고 완화할 방법은 없나요?" 추가
"디스크에 도착하는 요청의 순차성"을 지키는 방향이면 무엇이든 된다. ① 읽기 자체를 줄인다 — 커버링 인덱스로 북마크 룩업을 없애고, 버퍼 풀을 키워 워킹셋을 메모리에 담으면 디스크에 가는 스트림 수가 준다(사슬 D → B 차단). ② 큰 스캔을 격리한다 — 배치·리포트성 풀스캔은 읽기 레플리카나 한가한 시간대로 보내 OLTP 트랜잭션의 짧은 I/O와 섞이지 않게 한다. ③ DB 내부 동시 실행 상한(innodb_thread_concurrency 류)이나 DB 앞의 풀러(PgBouncer, ProxySQL)로 앱 커넥션 수와 무관하게 DB 동시성을 묶는다. ④ SSD·클라우드 볼륨으로 seek 비용 자체를 없애면 랜덤화 효과(2)는 약해지지만, IOPS 상한에 의한 큐 적체(1)는 남으므로 ①②는 여전히 유효하다. 공통 원리: 동시에 디스크를 두드리는 스트림 수를 줄이거나, 두드리기 전에 메모리에서 끝낸다.
한 줄 요약
커넥션은 DB의 처리 능력이 아니라 DB 앞의 자리 수라서, 코어와 디스크가 정한 상한을 넘긴 커넥션은 일을 더 시키는 게 아니라 컨텍스트 스위칭 · I/O 큐 적체와 순차 I/O의 랜덤화 · 락 경합 · 버퍼 풀 경합을 더 만들어 처리량을 깎는다 — 그래서 늘리기 전에 앱 스레드 풀 → 커넥션 풀 → DB CPU → 디스크 I/O → 락 대기 순으로 병목 위치를 확인하고, 풀 크기는 경험식으로 출발해 부하 테스트로 포화 지점을 찾은 뒤 active / pending / acquire 메트릭 알람으로 고정하며, 대기 줄은 DB 안(비싼 대기)이 아니라 앱 풀(싼 대기)에 세운다.
