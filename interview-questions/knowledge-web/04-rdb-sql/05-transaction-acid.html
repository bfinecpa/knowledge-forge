트랜잭션 ACID — 글자마다 "한 줄 정의 + 메커니즘 하나"로 고정한다

원본: interview-questions/knowledge/04-rdb-sql/05-transaction-acid.md

30초 암기 카드 — 글자 ↔ 한 줄 정의 ↔ 무엇으로부터 ↔ 메커니즘 ↔ 깨졌을 때 증상
질문: "트랜잭션의 ACID를 설명해주세요." — 이 표의 한 행을 한 문장으로 말하는 것이 답이다. 네 행을 순서대로 말하면 첫 답변이 끝난다.
글자한 줄 정의적(무엇으로부터)메커니즘깨지면 (계좌이체 A→B 10만원)
A원자성Atomicity 전부 반영 or 전부 취소 — 중간 상태 없음 실패 에러·크래시 undo log (변경 전 값) A에서 빠졌는데 B엔 안 들어옴 — "절반만 실행된 세상"이 남는다
C일관성Consistency 트랜잭션 전후로 불변식·제약이 유지 규칙 위반 DB 제약(CHECK·FK·UNIQUE·NOT NULL) + 앱 불변식 두 계좌 총합에서 10만원 증발 / 잔액 −5만원
I격리성Isolation 동시 트랜잭션이 서로의 중간 상태를 못 봄 동시성 다른 세션 락 + MVCC (스냅샷 읽기) 옆 세션이 "차감만 된 순간"의 잔액을 읽어 간다
D지속성Durability 커밋 응답 후엔 전원이 나가도 보존 장애 전원 차단 redo log = WAL + fsync (변경 후 값) "이체 완료" 화면을 봤는데 재시작하니 없던 일
첫 답변으로 그대로 말하기
ACID는 암기 항목이 아니라 글자마다 "한 줄 정의 + 그것을 구현하는 메커니즘 하나"를 묶어서 말하는 문제다. A(원자성) = 전부 반영 or 전부 취소, 중간 상태 없음 — undo log / C(일관성) = 트랜잭션 전후로 시스템의 불변식·제약이 유지 — DB 제약 + 애플리케이션의 공동 책임 / I(격리성) = 동시 트랜잭션이 서로의 중간 상태를 보지 않음 — 락 + MVCC / D(지속성) = 커밋 응답 후엔 전원이 나가도 보존 — redo log(WAL). 특히 두 가지를 틀리지 말 것: ① "끼어들 수 없다"는 격리성의 언어다 — 원자성은 동시성이 아니라 실패에 대한 보장. ② 로그 쓰기도 똑같은 디스크 I/O다 — 다만 파일 끝 순차 append라서 싸고, 흩어진 페이지의 랜덤 쓰기는 나중에 모아서 한다. 이게 WAL이 존재하는 이유다.
출제 의도 — "네 단어를 외웠는가"가 아니라 "짝을 맞추는가"를 본다
각 글자가 무엇으로부터 무엇을 지키는지(실패로부터? 동시성으로부터? 장애로부터?)와 DB가 그걸 무슨 장치로 구현하는지를 짝지어 말할 수 있는지. 짝이 맞으면 "커밋 순간 서버가 죽으면 D는?"(redo), "격리는 무엇으로?"(락·MVCC → 격리 수준) 같은 꼬리질문의 발판이 된다.

1. 네 글자 인출 장치 — 약어가 안 떠오르면 여기서 복원한다

ACID가 안 떠오르는 건 지식이 없어서가 아니라 꺼내는 손잡이가 없어서다. 손잡이를 세 개 만든다 — 한국어 네 음절, 각 글자에 던지는 질문 하나, 비유 하나. 하나만 잡혀도 나머지가 딸려 나온다.

1-1. 손잡이 ① — "원·일·격·지" 네 음절과 각 글자에 던지는 질문

원
원자성 · Atomicity
atom = 더 쪼갤 수 없다
중간에 죽으면?
→ 절반만 남지 않는다
일
일관성 · Consistency
consistent = 규칙과 일치
규칙이 깨지면?
→ 그 트랜잭션은 무효
격
격리성 · Isolation
isolate = 떼어 놓다
옆에서 들여다보면?
→ 중간 상태는 안 보인다
지
지속성 · Durability
durable = 오래 간다
커밋 뒤에 죽으면?
→ 그래도 남는다
네 글자를 "적"으로 외운다 — 실패 · 규칙 · 동시 · 장애
A는 실패로부터, C는 규칙 위반으로부터, I는 동시성으로부터, D는 장애로부터 지킨다.

각 글자는 "무엇으로부터 지키는가"가 다르기 때문에 서로 대체할 수 없다. 이 네 단어(실패·규칙·동시·장애)가 §2·§3·§5·§6의 제목이기도 하다. A와 D는 둘 다 "죽으면?"이지만 커밋 전에 죽으면 A(되돌린다), 커밋 뒤에 죽으면 D(남긴다)로 갈린다.

1-2. 손잡이 ② — 비유 네 개 (md의 비유를 카드로)

A계약서 서명

양쪽이 서명하거나, 아무도 안 하거나. "한쪽만 서명된 계약서"라는 물건은 존재하지 않는다.

C복식부기 장부

어떤 거래를 적든 차변·대변 총합은 맞아야 한다. 장부의 규칙을 깨는 거래는 그 자체가 무효.

I각자 회의실

각자 방에서 작업하고, 문서가 완성되기 전엔 서로의 초안을 들여다보지 않는다.

D잉크 서명

연필이 아니라 잉크. 정전이 나도 종이에 남는다. (메모리에만 있으면 연필이다)

1-3. 손잡이 ③ — 네 글자의 층위: 셋은 도구, 하나는 목표

표를 네 줄로 나란히 외우면 C가 자꾸 흔들린다. C만 층이 다르기 때문이다 — A·I·D는 DB가 가진 메커니즘이고, C는 그 메커니즘들(과 제약, 애플리케이션 코드)이 떠받치는 목표다. 이 그림 하나가 §3의 뼈대다.

A·I·D는 메커니즘, C는 그것들이 떠받치는 목표. 그래서 C만 "DB 혼자 다 지켜줄 수 없다"는 말이 붙는다.

2. A vs I — "A는 끝의 문제, I는 동시의 문제"

가장 흔한 혼동. 원자성을 "트랜잭션 실행 도중 누군가 끼어들 수 없다"로 설명하면 틀린다 — "끼어든다"는 동시성의 언어이고, 동시성을 다루는 글자는 I다. 두 글자는 상대하는 적 자체가 다르다.

A원자성 — 끝의 문제

질문: 이 트랜잭션은 어떻게 끝나는가? 전부 반영으로 끝나거나, 아무 일도 없던 것으로 끝나거나. 셋째 결말은 없다.

  • 적은 실패 — 에러, 예외, 서버 크래시, 네트워크 단절
  • 나 혼자 쓰는 DB에서도 필요하다. UPDATE 두 개 중 첫 번째만 되고 죽으면?
  • 도구: undo log — 변경 전 값으로 되돌린다
vs
I격리성 — 동시의 문제

질문: 실행되는 동안 옆에서 보면 무엇이 보이는가? 중간 상태(차감됐는데 입금은 아직)는 남에게 보이면 안 된다.

  • 적은 동시성 — 같은 행을 만지는 다른 세션
  • 크래시가 절대 없는 완벽한 서버에서도 필요하다. 둘이 동시에 같은 계좌를 만지면?
  • 도구: 락(막는다) + MVCC(과거 스냅샷을 보여준다)
한 문장 테스트 — 어느 글자인지 3초 안에 가르는 법
"혼자 쓰는 DB에서도 문제가 되면 A, 둘 이상이 써야 문제가 되면 I."

면접에서 "끼어들다·동시에·다른 사용자가" 같은 단어가 입에서 나오려 하면 그건 I를 설명하고 있는 것이다. A를 설명할 때는 "죽으면·실패하면·예외가 나면"만 써라.

위 그림에는 트랜잭션이 하나뿐인데도 A가 필요하고, 아래 그림에는 실패가 없는데도 I가 필요하다. 두 성질이 독립이라는 증거.

3. C 일관성 — "DB가 지키는 제약" + "앱이 지키는 불변식", 두 층으로 답한다

일관성이 막막한 이유는 정의를 "같은 쿼리 같은 결과"나 "컬럼 타입이 안 바뀐다"로 잘못 잡았기 때문이다. 둘 다 아니다. 정의는 이것 하나 —

C의 정의 — 이 문장 그대로
트랜잭션이 시작되기 전에 성립하던 시스템의 규칙(불변식·제약)이, 트랜잭션이 끝난 후에도 여전히 성립한다.

"규칙"이 무엇인지 즉시 두 개를 댈 수 있어야 한다. 계좌이체라면 ① 총합 불변(이체는 돈을 옮기는 것이지 만들거나 없애는 게 아니다) ② 잔액 ≥ 0(마이너스 통장이 아니라면).

3-1. 시나리오로 잡기 — "일관성이 깨진 상태"란 구체적으로 이 두 장면이다

장면 ①총합에서 10만원이 증발했다
AB총합
이체 전50만30만80만
차감만 반영40만30만70만

각 행만 보면 멀쩡한 숫자다. 그런데 시스템 전체의 규칙(총합 불변)이 무너져 있다. 이 규칙은 어느 한 행 안에 없다 — 두 행을 합쳐 봐야 보인다.

장면 ②잔액이 −5만원이 됐다
A 잔액규칙
이체 전5만≥ 0 ✅
10만 출금 후−5만≥ 0 ❌

BIGINT 컬럼에 -50000은 타입으로는 100% 유효한 값이다. 아무도 스키마를 안 건드렸다. 그런데 "잔액 ≥ 0"이라는 업무 규칙이 깨졌다 = 일관성 파괴.

3-2. 오해 ① — 일관성은 컬럼 타입·스키마 얘기가 아니다

"규칙이 유지된다"를 "컬럼 타입이 바뀌지 않는다"로 읽으면 층위가 완전히 달라진다. 타입은 "어떤 값이 담길 수 있는가", 일관성은 "지금 담긴 값들이 업무 규칙에 맞는가"의 문제다.

무엇에 대한 것누가 바꾸나트랜잭션과의 관계
컬럼 타입스키마(구조)ALTER TABLE (DDL)트랜잭션이 건드리는 대상이 아니다
일관성(C)데이터 값(상태)INSERT/UPDATE/DELETE (DML)트랜잭션 전후로 규칙이 유지돼야 한다
 
balance BIGINT      ← 타입 선언은 그대로. 아무도 스키마를 안 건드렸다.

A: -50000           ← BIGINT로서 100% 유효한 값. 타입 위반이 아니다.
                    ← 그런데 "잔액 ≥ 0" 규칙 위반 = 일관성 파괴

3-3. 오해 ② — 일관성은 "언제나"가 아니라 "경계에서" 성립한다

규칙은 트랜잭션 도중에는 반드시 깨진다. 두 UPDATE를 물리적으로 동시에 실행할 수 없으니 총합이 안 맞는 순간은 반드시 존재한다. 일관성이 요구하는 건 "항상 성립"이 아니라 시작 전과 커밋 후, 두 경계에서만 성립이다.

깨져 있는 구간을 감당하는 건 I(가린다)와 A(되돌린다). "A·I·D는 메커니즘, C는 목표"의 실체가 이 그림이다.

3-4. 두 층 — 누가 지키나: 같은 "일관성" 안에 성격이 다른 규칙 둘이 섞여 있다

C가 네 글자 중 유일하게 "DB가 알아서" 다 못 해주는 이유는 규칙에 두 부류가 있기 때문이다. 계좌이체의 규칙 두 개가 정확히 이 선을 따라 갈린다.

① DB가 강제하는 층"잔액 ≥ 0"

스키마에 선언해 둘 수 있는 규칙. NOT NULL · UNIQUE · FK · CHECK. 강점은 어떤 코드 경로로 들어와도 우회 불가 — 검사를 빼먹은 신규 API가 하나 있어도 뚫리지 않는다. 위반하면 DB가 에러를 내고 거부 → 롤백(A가 C를 지키는 도구로 동원된다).

② 앱이 지키는 층"총합 불변"

CHECK 한 줄로 표현이 안 되는 규칙. "이체 총합 불변", "VIP 등급은 연 구매액 천만원 이상만". 애플리케이션 코드가 규칙의 구현체가 되고, DB는 그 코드가 절반만 실행되지 않게(A), 동시 실행에 찢기지 않게(I) 도구를 제공할 뿐이다. DB는 이 규칙의 존재조차 모른다.

before — "잔액 ≥ 0"을 애플리케이션 코드만 믿는다
CREATE TABLE account (
    id      VARCHAR(20) PRIMARY KEY,
    balance BIGINT NOT NULL
);
-- 코드에서 if (balance >= amount) 검사를 하더라도 —
-- 검사와 차감 사이에 다른 요청이 끼어들면(동시성) 음수 잔액이 뚫린다.
-- 검사를 빼먹은 신규 API 하나만 있어도 뚫린다.
after — 최후의 방어선을 DB 제약으로 선언
CREATE TABLE account (
    id      VARCHAR(20) PRIMARY KEY,
    balance BIGINT NOT NULL,
    CONSTRAINT chk_balance_non_negative CHECK (balance >= 0)
);
-- 어떤 경로로 UPDATE가 들어와도, 잔액을 음수로 만드는
-- 트랜잭션은 DB가 에러를 내고 거부 → 롤백.

3-5. CHECK의 한계 — 왜 "총합 불변"은 DB에 선언할 수 없나

CHECK는 자기 행 안에서 판정 가능한 것만 검사한다. 여러 행에 걸친 규칙은 표현 자체가 안 된다.

가능 — 이 행의 balance만 보면 참/거짓이 결정된다
CHECK (balance >= 0)
-- 한 행 안에서 닫힌 규칙 → 선언 가능
불가능 — 판정하려면 테이블 전체를 봐야 한다
ALTER TABLE account ADD CONSTRAINT chk_total
    CHECK ((SELECT SUM(balance) FROM account) = 10000000);
-- 서브쿼리를 쓸 수 없다. 여러 행에 걸친 규칙은 표현 자체가 안 된다.
그럼 표준에는 없나? — CREATE ASSERTION이 있지만 거의 구현되지 않았다

SQL 표준에는 테이블 전체·여러 테이블에 걸친 제약을 위한 CREATE ASSERTION이 정의돼 있다. 그러나 모든 쓰기 때마다 테이블 전체를 재검증해야 해서 비용이 감당이 안 되므로 실제 DB가 거의 구현하지 않았다. 그래서 총합 불변 같은 규칙은 애플리케이션 코드가 규칙의 구현체가 된다.

// 총합 불변은 여기서 지켜진다. DB는 이 규칙의 존재조차 모른다.
@Transactional
public void transfer(String from, String to, long amount) {
    accountRepo.withdraw(from, amount);   // 같은 amount를
    accountRepo.deposit(to, amount);      // 양쪽에 쓴다 ← 이게 규칙의 구현체
}
가산점 문장 — 일관성을 "공동 책임"으로 말한다
"DB는 자신이 아는 제약을 강제하고 A·I·D라는 도구를 제공한다. 그 도구 위에서 비즈니스 불변식까지 지켜 '일관된 상태 → 일관된 상태'로 옮기는 최종 책임은 애플리케이션과 DB의 공동 책임이다."

이 문장이 나오면 ACID를 DB 기능 목록이 아니라 시스템 설계의 언어로 쓰고 있다는 신호가 된다.

4. 계좌이체 한 건 위에 네 글자를 올린다 — 정의가 저절로 복원되는 방법

트랜잭션은 여러 개의 작업을 하나의 논리적 단위로 묶은 것이다. 계좌이체가 표준 예시인 이유 — "A 차감"과 "B 입금"이라는 두 UPDATE는 따로 보면 각각 멀쩡하지만, 둘 중 하나만 실행된 세상은 존재해선 안 되기 때문이다.

before — 트랜잭션 없이 UPDATE 두 방
UPDATE account SET balance = balance - 100000 WHERE id = 'A';
-- ← 여기서 서버 다운 / 예외 / 네트워크 단절이 나면?
UPDATE account SET balance = balance + 100000 WHERE id = 'B';

-- 결과: A에서 10만원이 빠졌는데 B에는 안 들어옴.
-- "절반만 실행된 세상"이 그대로 남는다 = 원자성 없음
-- → 총합에서 10만원 증발 = 일관성 파괴로 번짐
after — 하나의 트랜잭션으로 묶는다
START TRANSACTION;

UPDATE account SET balance = balance - 100000 WHERE id = 'A';
UPDATE account SET balance = balance + 100000 WHERE id = 'B';

COMMIT;
-- 중간 어디서 실패하든 DB가 undo log로 전부 되돌린다(롤백).
-- 바깥 세상에는 "둘 다 반영" 아니면 "아무 일도 없었음" 두 상태만 존재.

이 한 건의 이체 위에 네 글자가 각각 언제 작동하는지를 붙이면 정의가 저절로 복원된다. 면접장에서 정의가 막히면 이 그림을 머릿속에서 재생한다.

A는 커밋 전의 ✕, D는 커밋 후의 ✕, I는 실행 중의 다른 세션, C는 양쪽 경계에서의 규칙 확인.
A커밋 전 ✕

첫 UPDATE 후, 둘째 UPDATE 전에 죽었다. 재시작한 DB는 미커밋 트랜잭션을 발견하고 undo log를 따라 차감 전으로 되돌린다.

D커밋 후 ✕

COMMIT 성공 응답을 받은 직후 전원이 나갔다. 재시작해도 결과는 남아 있어야 한다 — redo log 덕분에 남는다(§5·§6).

I실행 중 옆 세션

이체 도중 다른 트랜잭션이 잔액을 조회했다. "차감만 되고 입금은 안 된" 상태를 보여주면 안 된다 — 락 또는 MVCC로 차단.

C양쪽 경계

커밋 전후로 총합 불변·잔액 ≥ 0이 유지됐는가. A·I·D라는 도구 + 제약 + 앱 로직이 합작한 결과로서 지켜진다.

5. undo vs redo — "되돌리기 장부"와 "다시하기 장부", 그리고 크래시 순간

이름이 비슷해서 섞이기 쉬운데, 담당 글자가 다르고 적어두는 값이 다르다.

담당 글자무엇을 적나예시언제 쓰나어떻게 타나
undo logA 원자성변경 전 값"A 잔액은 원래 50만이었다"롤백 / 크래시 후 미커밋 정리거꾸로 따라가며 원상복구
redo log (WAL)D 지속성변경 후 값"A 잔액을 40만으로 바꿨다"크래시 후 커밋된 변경 재적용앞으로 따라가며 다시 적용
암기 고정 — 전/후, 뒤로/앞으로
undo = 변경 전 값 · 뒤로 탄다 · A / redo = 변경 후 값 · 앞으로 탄다 · D

MVCC의 과거 스냅샷도 undo log의 "변경 전 값"을 재활용한다 — undo 하나가 A(롤백)와 I(스냅샷 읽기) 둘을 먹여 살린다. 상세는 MVCC 문서.

5-1. 크래시 순간 타임라인 — 디스크에는 "커밋됐는데 미반영"과 "미커밋인데 반영됨"이 동시에 존재한다

왜 둘 다 필요한가를 보려면 크래시 순간 디스크 상태를 정확히 그려야 한다. 아래는 커밋된 T1과 미커밋 T2가 겹친 채 전원이 나간 장면이다.

복구는 항상 redo 전부 재생 → 미커밋분만 undo 순서. 그래서 "커밋된 것은 살아남고(D), 커밋 안 된 것은 흔적 없이 사라진다(A)"가 동시에 성립한다.
  1. redo 재생 — 디스크의 redo log를 처음(마지막 체크포인트)부터 끝까지 앞으로 따라가며, 데이터 파일에 아직 반영 안 된 변경을 전부 다시 적용한다. 커밋 여부를 따지지 않고 일단 다 적용한다.
  2. undo 롤백 — 로그에 commit 기록이 없는 트랜잭션(T2)만 골라 undo log를 거꾸로 타며 변경 전 값으로 되돌린다.
  3. 결과: 데이터 파일 = "커밋된 트랜잭션은 전부 반영, 미커밋은 전부 취소". A와 D가 한 번의 복구에서 함께 성립.

6. WAL이 존재하는 이유 — 로그 쓰기도 디스크 I/O다, 다만 순차라 싸다

즉시 감점 문장 — "테이블 파일을 고치는 건 I/O라 느리고, 로그는 그냥 갖고 있으면 되니까 빠르다"

로그 쓰기도 똑같이 디스크에 쓰는 I/O다. 메모리에만 갖고 있으면 전원이 나가는 순간 같이 증발하므로 D를 보장할 수 없다 — 커밋 시점에 로그는 반드시 디스크까지 내려가야 한다(fsync). "로그는 I/O가 아니다"라고 하면 D 자체가 성립하지 않는다.

그럼 왜 굳이 로그에 먼저 쓰나? 같은 디스크 쓰기라도 접근 패턴이 다르기 때문이다. 이 랜덤 vs 순차 비용 모델은 Q2의 인덱스 손익분기, Q3의 페이지 분할과 정확히 같은 축이다.

왼쪽도 오른쪽도 디스크 쓰기다. 차이는 탐색(seek) 횟수뿐 — 그 차이가 커밋 지연을 가른다.

6-1. WAL(Write-Ahead Logging) 전략 — 커밋 순간엔 싼 것만 하고, 비싼 것은 모아서 나중에

"Write-Ahead" = 데이터 파일보다 로그를 먼저 쓴다. 커밋 응답의 조건은 로그의 fsync이지 데이터 파일 반영이 아니다.
이 문장이 나오면 이해한 것, 안 나오면 외운 것
"로그도 디스크 쓰기다. 다만 순차 append라 싸고, 비싼 랜덤 쓰기는 뒤로 미뤄 모아서 한다."

면접관이 "로그도 어차피 디스크 쓰기잖아요?"라고 되물으면, "맞다"로 시작하는 것이 정답의 첫 단어다. 부정하는 순간 D의 근거가 사라진다.

8. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 답의 깊이가 갈리는 지점, 추가는 이 페이지에서 보탠 문항.

커밋 완료 응답 직후 전원이 나갔습니다. 데이터는 남아 있어야 하나요? 테이블 파일엔 아직 안 쓰였을 수도 있는데 무슨 수로 보장하죠?

남아 있어야 한다 — 그게 D(지속성)의 정의다. "커밋 성공"이라는 응답은 "이제 무슨 일이 있어도 이 결과는 보존된다"는 약속이기 때문이다.

보장 수단은 redo log(WAL): 커밋 시점에 변경 내역을 로그 파일에 순차 append하고 fsync로 디스크까지 내려보낸 뒤에야 성공을 응답한다. 테이블 파일(데이터 페이지)에는 아직 반영 전이어도 상관없다 — 재시작한 DB가 redo log를 읽어 커밋된 변경을 다시 적용(redo)하기 때문이다(§5 그림의 ①).

요점 "메모리 어딘가에 갖고 있다"가 아니라 "응답 전에 디스크의 로그에 내려갔다"는 것.

로그 쓰기도 어차피 디스크 쓰기잖아요. 그런데 왜 테이블 파일을 바로 고치는 것보다 빠르다는 거죠?

"맞다"로 시작한다 — 로그 쓰기도 똑같은 디스크 I/O다. 이걸 인정하는 데서 답이 시작된다.

차이는 접근 패턴이다. 트랜잭션이 건드린 행들은 디스크 여기저기 흩어진 페이지에 있어서 직접 반영은 랜덤 쓰기(탐색 여러 번)이고, 로그는 하나의 파일 끝에 순차 append(탐색 0번)라 같은 양을 써도 훨씬 싸다. 그래서 커밋 순간엔 싼 순차 쓰기만 하고, 비싼 랜덤 쓰기는 버퍼 풀에 모아뒀다가 체크포인트 때 배치로 처리한다(§6).

감점 문장 "로그는 I/O가 아니라서 빠르다" — 로그가 디스크에 안 내려가면 D 자체가 성립하지 않는다.

일관성이 깨진 상태란 계좌이체에서 구체적으로 어떤 상태인가요? DB가 혼자 다 지켜줄 수 있나요?

구체적으로 두 가지 — ① 이체 후 두 계좌 총합에서 이체액만큼 증발한 상태(차감만 반영), ② 잔액이 음수가 된 상태(제약 뚫림). "같은 쿼리 같은 결과"는 일관성의 정의가 아니다(§3-1).

DB 혼자는 못 지킨다 — NOT NULL·UNIQUE·FK·CHECK처럼 선언 가능한 제약은 DB가 강제하지만, "총합 불변" 같은 비즈니스 불변식은 CHECK가 자기 행 안만 볼 수 있어 선언할 방법이 없고, 애플리케이션이 트랜잭션(A·I라는 도구) 안에서 지켜야 한다(§3-4·3-5).

완결 문장 "DB 제약 + 애플리케이션의 공동 책임"까지 나와야 끝난 답이다.

undo log와 redo log는 각각 어느 글자 담당인가요? 왜 둘 다 필요하죠?

undo = A, redo = D. undo는 변경 전 값을 적어두는 "되돌리기 장부"로 롤백·미커밋 정리에 쓰이고, redo는 변경 후 값을 적어두는 "다시하기 장부"로 크래시 후 커밋된 변경 재적용에 쓰인다.

둘 다 필요한 이유: 크래시 순간 디스크의 데이터 파일에는 "커밋됐는데 아직 반영 안 된 변경"(redo로 다시 적용해야)과 "커밋 안 됐는데 이미 반영된 변경"(체크포인트가 더티 페이지를 미리 내렸을 수 있다 — undo로 되돌려야)이 동시에 존재할 수 있기 때문이다(§5-1 그림).

순서 redo 먼저 전부 재적용 → 미커밋분만 undo로 롤백.

각 글자의 메커니즘이 전부 "트랜잭션이 살아 있는 동안" 자원을 붙들고 있기 때문이다.

  1. A의 undo가 누적된다 — 롤백에 대비해 변경 전 값을 계속 쌓아야 하고, 길수록 undo 영역이 비대해지며 만약 롤백하면 그 긴 장부를 거꾸로 다 타야 해서 롤백 자체가 오래 걸린다.
  2. I의 락·스냅샷이 오래 유지된다 — 잡은 락은 커밋까지 안 풀리니 경합이 번지고, MVCC에서는 이 트랜잭션이 봐야 할 과거 버전들을 다른 트랜잭션들이 지우지 못해 오래된 버전이 쌓인다.
  3. 여기에 커넥션까지 오래 점유하면 락 경합 → 대기 → 트랜잭션 장기화 → 커넥션 풀 고갈 사슬로 번진다.

그래서 실무 수칙이 "트랜잭션은 짧게, 외부 API 호출은 트랜잭션 밖으로"다. ACID의 네 글자를 보장 목록이 아니라 비용의 원천으로도 읽을 수 있는지가 변별점. 상세는 긴 트랜잭션 문서.

원자성을 "실행 도중 다른 트랜잭션이 끼어들 수 없다"고 설명하면 왜 틀린 건가요? 추가

"끼어든다"는 동시성의 언어이고 동시성을 다루는 글자는 I다. 원자성이 상대하는 적은 실패다 — 다른 트랜잭션이 하나도 없는, 나 혼자 쓰는 DB에서도 UPDATE 두 개 중 첫 번째만 되고 죽으면 "절반만 반영된 세상"이 남고, 그걸 없애는 것이 원자성이다.

반대로 크래시가 절대 없는 서버에서도 두 세션이 같은 계좌를 만지면 중간 상태가 새어 나갈 수 있고, 그걸 막는 것이 격리성이다. 한 문장 테스트: "혼자 쓰는 DB에서도 문제가 되면 A, 둘 이상이 써야 문제가 되면 I."(§2)

ACID 네 글자 중 성능을 위해 "일부러 완화"하는 글자가 있나요? 있다면 어느 것이고 무엇을 잃나요? 추가 시니어 변별

I와 D는 완화 다이얼이 있고, A와 C는 없다.

  • I — 격리 수준: SERIALIZABLE을 항상 쓰면 동시성이 죽으므로, 대부분의 DB가 기본값을 낮춰(예: InnoDB는 REPEATABLE READ) 팬텀 등 일부 이상 현상을 허용하는 대신 처리량을 얻는다. 잃는 것 = 특정 동시성 이상 현상. 상세는 격리 수준 문서.
  • D — fsync 정책: 커밋마다 fsync하지 않고 OS 캐시에 넘긴 뒤 주기적으로 내리는 설정(InnoDB의 innodb_flush_log_at_trx_commit을 1이 아닌 값으로)으로 커밋 지연을 줄일 수 있다. 잃는 것 = 정전 시 마지막 약 1초분 커밋 유실 가능. "커밋 응답 = 보존 약속"이 더 이상 참이 아니게 된다.
  • A와 C는 완화 대상이 아니다 — "절반만 반영돼도 된다"거나 "규칙이 좀 깨져도 된다"는 다이얼은 존재하지 않는다. 그건 성능 튜닝이 아니라 버그다.

이 구분을 말할 수 있으면 ACID를 "보장 목록"이 아니라 트레이드오프 축으로 이해하고 있다는 신호다.

UPDATE 한 문장짜리 작업(예: 여러 행 일괄 갱신)에도 원자성이 필요한가요? 트랜잭션을 안 열었는데요. 추가

필요하고, 실제로 보장된다. 단일 SQL 문장 자체가 하나의 트랜잭션(autocommit)이다. UPDATE ... WHERE status='PENDING'이 1만 행 중 6천 행을 고치다가 제약 위반·데드락·크래시로 실패하면, DB는 undo log로 그 6천 행을 전부 되돌린다 — 절반만 갱신된 상태로 남지 않는다.

즉 START TRANSACTION은 "원자성을 켜는 스위치"가 아니라 "원자성의 단위를 여러 문장으로 넓히는 선언"이다. 이 구분이 되면 "트랜잭션 = 원자성"이 아니라 "트랜잭션 = 원자성의 경계"라고 정확히 말하게 된다.

롤백이 커밋보다 오래 걸릴 수 있다는데, ACID 메커니즘으로 설명하면요? 추가

커밋의 비용은 redo log 끝에 커밋 레코드를 순차 append하고 fsync하는 것 — 트랜잭션이 아무리 커도 커밋 순간에 하는 일은 거의 상수다(변경 페이지는 이미 버퍼 풀에 있고 나중에 내린다).

롤백의 비용은 undo log를 거꾸로 끝까지 타며 변경 전 값을 하나하나 되돌리는 것 — 변경량에 비례한다. 100만 행을 고친 트랜잭션을 롤백하면 100만 개의 undo 레코드를 역순으로 적용해야 한다. 그래서 "대량 UPDATE를 돌리다 취소했더니 취소가 더 오래 걸린다"는 현상이 나오고, 긴 트랜잭션의 위험(§8 다섯째 문항)이 여기서도 드러난다.

격리성은 "무엇으로" 구현한다고 했는데, 락과 MVCC는 각각 언제 쓰이나요? 추가

한 줄 구분 — 읽기는 MVCC, 쓰기는 락.

  • MVCC(스냅샷 읽기): 일반 SELECT는 남을 막지 않고, 트랜잭션 시작(또는 문장 시작) 시점의 과거 버전을 undo log에서 재구성해 보여준다. §2 그림에서 T2가 "80만 시절 스냅샷"을 보는 것이 이것. 읽기와 쓰기가 서로를 기다리지 않는다.
  • 락: UPDATE/DELETE/SELECT ... FOR UPDATE는 대상 행에 배타 락을 잡아 다른 쓰기를 커밋까지 기다리게 한다. "같은 쿠폰을 둘이 동시에 0으로 만드는" 문제는 스냅샷으로는 못 막고 락으로 막는다.

여기서 격리 수준(무엇을 허용할지)과 갭 락·넥스트키 락(범위를 어떻게 잠글지)으로 이어진다 — MVCC, 갭 락, SELECT FOR UPDATE.

한 줄 요약
ACID는 글자마다 "한 줄 정의 + 메커니즘"으로 말한다 — A: 전부 반영 or 전부 취소, 실패에 대한 보장(undo log) / C: 트랜잭션 전후 불변식 유지 — 총합 불변·잔액 ≥ 0, DB 제약과 애플리케이션의 공동 책임 / I: 동시 트랜잭션이 중간 상태를 못 본다, 동시성에 대한 보장(락+MVCC) / D: 커밋 응답 후엔 전원이 나가도 보존(redo log/WAL). "끼어들 수 없다"는 격리성의 언어이고, 로그도 똑같은 디스크 I/O지만 순차 append라 싸기에 커밋 순간엔 로그만 쓰고 비싼 랜덤 쓰기는 모아서 나중에 한다.
