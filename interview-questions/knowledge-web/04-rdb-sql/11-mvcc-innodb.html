MVCC와 InnoDB 구현
"읽기는 왜 락을 안 잡는가"를 숨은 컬럼 · undo 체인 · Read View로 답한다

면접 질문: "MVCC란 무엇인가요? InnoDB에서 어떻게 구현되어 있나요?"

핵심 관전 포인트 — MVCC(다중 버전 동시성 제어)는 "읽는 쪽이 락을 잡는 대신, 자기 시점에 맞는 과거 버전을 본다"는 격리(I)의 구현 방식이다. 그래서 읽기는 쓰기를 막지 않고 쓰기는 읽기를 막지 않지만, 쓰기끼리는 여전히 락이다. InnoDB는 세 부품으로 구현한다 — ① 행마다 숨은 컬럼 DB_TRX_ID·DB_ROLL_PTR, ② 이전 값을 연결 리스트로 쌓는 undo 로그 = 버전 체인, ③ "어떤 트랜잭션까지 보이는가"를 찍어 두는 Read View. Read View를 문장마다 만들면 RC, 트랜잭션의 첫 읽기 때 한 번만 만들면 RR — 격리 수준 차이는 생성 시점 하나다. 비용은 트랜잭션 길이에 비례한다: 오래된 Read View 하나가 살아 있으면 purge가 그 뒤의 undo를 못 지우고 → 버전 체인이 길어져 → 무관한 트랜잭션의 조회까지 행마다 체인을 순회하느라 느려진다.
  • 1
    정의 — 읽는 쪽이 락 대신 자기 시점의 과거 버전을 보는 격리(I) 구현. 읽기↔쓰기는 서로 안 막고, 쓰기끼리는 락.
  • 2
    InnoDB 세 부품 — 숨은 컬럼(DB_TRX_ID·DB_ROLL_PTR) · undo 버전 체인 · Read View. RC는 문장마다, RR은 트랜잭션당 한 번 Read View를 만든다.
  • 3
    비용 — 긴 트랜잭션 → purge 정지 → history list 증가 → 체인 길어짐 → 무관한 조회까지 행마다 체인 순회. 그래서 트랜잭션은 짧게.

0. 질문 + 출제 의도

질문: "MVCC란 무엇인가요? InnoDB에서 어떻게 구현되어 있나요?"

출제 의도: "읽기는 왜 락을 안 잡는가"를 이해해야 격리 수준·락 경합·undo 폭증(긴 트랜잭션의 해악) 같은 운영 이슈가 전부 연결된다. RDB 내부 이해의 허리다. 정의 암기가 아니라 — 격리 수준 4단계가 내부적으로 무엇이 다른지, ACID의 I가 무슨 장치로 구현되는지, "트랜잭션은 짧게"의 근거가 무엇인지를 하나의 메커니즘으로 꿰어 말할 수 있는지를 본다.

이 페이지가 겨냥하는 약점 두 가지 ① ACID에서 격리성(I)과 원자성(A)을 혼동하는 문제 → 1-3절의 인출 카드로 A/I를 축으로 구분하고, undo가 둘을 겸직한다는 사실로 연결한다.
② 비용을 "조회가 느려진다"라는 결과로만 말하고 메커니즘 사슬로 서술하지 못하는 문제 → 3절에서 사슬 7단계를 이름 붙여 타임라인으로 그린다.

1. 개념 — MVCC는 "락 대신 과거 버전을 보여주는" 격리 구현 방식

1-1. 락만으로 격리하면 무엇이 문제인가

격리성(I)의 요구는 "동시 트랜잭션이 서로의 중간 상태를 보지 않는다"다. 가장 단순한 구현은 읽을 때도 락을 잡는 것 — 내가 읽는 행은 남이 못 고치고(공유 락), 남이 고치는 중인 행은 내가 못 읽는다(배타 락에 막힘). 정확하지만 비용이 치명적이다.

읽기가 쓰기를 막는다
통계 쿼리 하나가 10만 행을 읽는 동안 그 10만 행에 대한 UPDATE가 전부 대기.
쓰기가 읽기를 막는다
주문 한 건을 갱신 중이면 그 주문을 보려는 조회가 전부 대기.

웹 서비스 트래픽은 읽기가 압도적이다. 읽기마다 락이면 동시성이 죽는다.

1-2. MVCC의 아이디어 — 행을 덮어쓰지 말고 버전을 남긴다

UPDATE가 행을 덮어쓰더라도 이전 값을 어딘가에 남겨 두면, 읽는 쪽은 락을 기다릴 필요 없이 "자기 시점에 맞는 버전"을 골라 읽으면 된다.

비유 — 팻말 vs 판본 서랍 문서를 한 부만 두고 "편집 중이니 읽지 마세요" 팻말을 거는 것이 락. 편집할 때마다 이전 판을 서랍에 보관하고, 읽는 사람에게 "당신이 들어온 시각 기준 최신 판"을 건네는 것이 MVCC. 편집자와 독자가 서로를 기다리지 않는다. — 서랍이 undo 로그, "들어온 시각"이 Read View다.

MVCC의 성질 — 한 문장, 마지막 절까지

읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는다.
단, 쓰기끼리는 여전히 락이다.

같은 행을 두 트랜잭션이 동시에 UPDATE하는 충돌은 버전을 아무리 쌓아도 해결되지 않는다 — 누가 먼저 쓸지 정하는 건 락의 일이다. MVCC는 격리성의 읽기 절반, 락은 쓰기 절반.

1-3. ACID와 연결 — I의 두 축, 그리고 undo의 겸직

먼저 ACID 네 글자를 메커니즘과 함께 인출할 수 있어야 한다. 특히 A와 I는 "묻는 축"이 다르다.

ACID 인출 카드 — 정의 + 담당 장치

A · 원자성
Atomicity
전부 반영되거나 전부 취소된다. 중간에 멈춘 상태를 남기지 않는다.
장치: undo 로그(변경 전 값으로 되돌림)
C · 일관성
Consistency
트랜잭션 전후로 제약(PK·FK·CHECK, 업무 규칙)이 깨지지 않는다.
장치: 제약 조건 + 애플리케이션 로직
I · 격리성
Isolation
동시에 도는 트랜잭션이 서로의 중간 상태를 보지 않는다.
장치: 락(쓰기-쓰기) + MVCC(읽기-쓰기)
D · 지속성
Durability
커밋된 결과는 장애 후에도 남는다.
장치: redo 로그(커밋 전에 변경 내용을 먼저 디스크에 기록)
A와 I를 헷갈리지 않는 축 하나 A는 "끝"의 문제 — 트랜잭션이 끝났을 때 전부냐 전무냐 (시간축, 나 혼자여도 성립).
I는 "동시"의 문제 — 동시에 도는 남이 내 중간 상태를 보느냐 (동시성축, 남이 있어야 성립).
→ "원자성 덕분에 다른 트랜잭션이 중간값을 못 본다"는 틀린 문장이다. 중간값을 못 보게 하는 건 격리성(락 + MVCC)이다.

ACID 문서에서 I의 메커니즘을 "락 + MVCC"로 적었다. 이제 그 뜻이 정확해진다 — I = 락(쓰기-쓰기 충돌 직렬화) + MVCC(읽기-쓰기 비차단). 그리고 MVCC가 "이전 버전"을 보관하는 장소가 바로 undo 로그다.

2. InnoDB 구현 — 세 부품: 숨은 컬럼 · undo 버전 체인 · Read View

① 숨은 컬럼 — "누가, 이전은 어디"+ ② undo 버전 체인 — 재료+ ③ Read View — 고르는 기준

2-1. 숨은 컬럼 3개

InnoDB는 사용자가 정의한 컬럼 외에 모든 클러스터드 인덱스 레코드(= 실제 행)에 시스템 컬럼을 붙인다.

숨은 컬럼 3개 — "누가 · 이전은 · 대용키" (6 · 7 · 6 바이트)

DB_TRX_ID
6바이트 · 누가
이 행을 마지막으로 INSERT/UPDATE/DELETE-mark한 트랜잭션 ID. "이 버전을 누가 만들었나"
DB_ROLL_PTR
7바이트 · 이전은
이 행의 직전 버전이 기록된 undo 레코드를 가리키는 포인터(롤백 포인터). "이 버전 이전엔 뭐였나"
DB_ROW_ID
6바이트 · 대용키
PK도 NOT NULL UNIQUE도 없는 테이블에서만 붙는 자동 증가 행 ID(클러스터드 인덱스 키 대용). MVCC와는 무관.
왜 숫자 비교만으로 시간 순서가 되는가 트랜잭션 ID는 쓰기 트랜잭션이 시작될 때 단조 증가로 발급된다. 그래서 ID의 크기 비교 = 시작 시각 비교이고, Read View 판정이 숫자 비교만으로 가능하다. (단, 시작 순서 ≠ 커밋 순서 — 이 틈이 Read View의 "활성 목록"이 필요한 이유다. 2-3절)

2-2. undo 로그 = 버전 체인

UPDATE item SET stock = 7 WHERE id = 1이 실행될 때 InnoDB가 하는 일을 순서대로 놓으면 버전 체인이 저절로 그려진다.

저장 구조 — 한 문장

행 하나에 버전은 여러 개 있되, 테이블(클러스터드 인덱스)에는 항상 최신 하나만 있고
나머지는 undo에 사슬로 매달려 있다.

undo 로그의 두 종류 가산점

종류담는 것누가 필요로 하나언제 지우나
insert undoINSERT를 되돌리는 정보롤백(A)만. INSERT 전엔 행이 없었으니 남이 "과거 버전"으로 볼 일이 없다커밋 즉시 폐기
update undoUPDATE/DELETE의 이전 값롤백(A) + 다른 트랜잭션의 일관된 읽기(I)커밋해도 못 지움 — "이 버전을 봐야 하는 Read View가 하나도 없다"가 확인될 때 purge가 정리
DELETE도 지우지 않는다 — delete-mark InnoDB의 DELETE는 행을 물리적으로 지우지 않고 delete-mark(삭제 표시) 비트만 켠다. 아직 그 행을 봐야 할 Read View가 있을 수 있기 때문이다. 실제 제거는 역시 purge의 몫이다. → 3절 사슬 ⑥ "유령 인덱스 엔트리"의 원인.

2-3. Read View — "내 눈에 보이는 트랜잭션의 경계"

버전 체인이 "재료"라면, Read View는 "어느 버전을 고를지 정하는 기준"이다. 일관된 읽기(consistent read)를 시작하는 순간 InnoDB는 그 시점에 어떤 트랜잭션이 아직 안 끝났는지를 스냅샷으로 찍어 둔다. 구성 요소는 넷이다.

Read View 4요소 — "목록 · 하한 · 상한 · 나"

m_ids
활성 트랜잭션 ID 목록
생성 시점에 시작됐지만 아직 커밋/롤백 안 된 쓰기 트랜잭션들
m_up_limit_id
하한선 (low water mark)
활성 목록 중 최솟값. 이보다 작은 ID는 전부 이미 끝난 트랜잭션 → 무조건 보임
m_low_limit_id
상한선 (high water mark)
생성 시점에 다음에 발급될 ID(= 현재 최대 + 1). 이 이상은 내 스냅샷 이후 시작 → 무조건 안 보임
m_creator_trx_id
자기 트랜잭션 ID
내가 만든 변경은 커밋 전이라도 나에게는 보여야 하므로 따로 기억
이름 함정 — 소스의 이름이 직관과 반대 up_limit이 하한, low_limit이 상한이다. 면접에서는 소스 이름 대신 "하한선 = 활성 중 최소 ID, 상한선 = 다음 발급 ID"라는 뜻으로 말하면 충분하다.

판정 규칙 4단계 — 순서대로 적용

판정 4단계 — 외우는 순서 "나 · 아래 · 위 · 목록"

① 나(내 ID) → 보임→ ② 하한 아래 → 보임→ ③ 상한 위 → 안 보임→ ④ 사이 → 목록에 있으면 안 보임, 없으면 보임

2-4. 한 행을 읽는 절차 — 판정 → 체인 순회 (단계별 도식)

일반 SELECT가 행 하나를 만났을 때의 절차를 구체적인 숫자로 따라가 본다. 2-2절의 체인(stock 7 → 8 → 9 → 10, TRX 120 → 115 → 101 → 90)을 그대로 쓴다.

시나리오 A — 내 Read View
활성 목록 m_ids = {115, 120} 하한선 = 115 상한선 = 121 내 ID: 아직 아무것도 안 바꿈 (①은 해당 없음)

= "내가 스냅샷을 찍은 순간 115와 120은 아직 진행 중이었고, 121부터는 아직 시작도 안 했다"

1
클러스터드 인덱스의 현재 행을 본다. DB_TRX_ID = 120 → 115 ≤ 120 < 121, 사이 구간 → 목록에 있음 → 안 보임 → DB_ROLL_PTR을 따라간다.
2
undo 레코드에서 직전 버전을 재구성한다. TRX_ID = 115 → 사이 구간 → 목록에 있음 → 안 보임 → 다시 ROLL_PTR을 따라 더 과거로.
3
TRX_ID = 101 → 101 < 하한선 115 → 규칙 ② → 보임 → stock = 9를 결과로 반환. 순회 종료. (더 과거인 TRX 90 버전은 볼 필요가 없다.)
체인 끝까지 갔는데도 보이는 버전이 없다면? 내 스냅샷 시점엔 이 행이 존재하지 않았던 것 (그 뒤에 INSERT됨) → 결과에서 제외한다.

시나리오 B — 규칙 ④의 "없으면 보임"이 왜 필요한가

같은 체인. 이번엔 TRX 120이 115보다 늦게 시작했지만 먼저 커밋한 뒤에 내가 스냅샷을 찍었다.
m_ids = {115}하한 = 115상한 = 121

"하한 ≤ ID"라고 무조건 숨기면 이미 커밋된 120의 값을 못 보게 되어 스냅샷이 실제 세상보다 낡아진다. 그래서 사이 구간은 목록을 직접 확인한다 — 시작 순서(ID)와 커밋 순서가 다르기 때문이다.

이 절차에서 반드시 짚을 두 가지

락은 어디에도 없다
남이 지금 그 행을 UPDATE 중이어도(배타 락을 잡고 있어도) 나는 undo에서 이전 버전을 꺼내 읽으면 된다. 이것이 "읽기가 락을 안 잡는" 정확한 이유다.
비용의 씨앗
2단계의 반복 횟수 = 버전 체인의 길이. 체인이 짧으면 공짜에 가깝고, 길면 행 하나 읽는 데 undo 페이지를 여러 번 뒤진다. → 3절 사슬의 출발점.

2-5. 격리 수준별 Read View 생성 시점 — 차이는 "언제 찍느냐" 하나

숨은 컬럼도 undo 체인도 똑같다. RC와 RR의 내부 차이는 코드 몇 줄 — "Read View를 문장마다 새로 만드느냐, 트랜잭션당 한 번 만드느냐"다.

격리 수준별 일반 SELECT의 동작 — Read View는 "언제"

격리 수준Read View결과
READ UNCOMMITTED안 만듦. 클러스터드 인덱스의 현재 행을 그대로 읽음미커밋 값도 보임 (dirty read)
READ COMMITTED문장(statement)마다 새로매 SELECT가 그 순간 커밋된 최신을 봄 → non-repeatable read 발생
REPEATABLE READ트랜잭션의 첫 일관된 읽기 때 한 번, 끝까지 재사용같은 스냅샷 → non-repeatable read·phantom 방지
SERIALIZABLE안 씀. 일반 SELECT도 공유 락을 잡는 잠금 읽기로 바뀜MVCC 스냅샷을 쓰지 않음
RC = 문장마다  ·  RR = 트랜잭션당 한 번 (첫 SELECT 때)

주의할 디테일 두 가지 가산점

RR의 Read View는 BEGIN 시점이 아니다
첫 일관된 읽기(SELECT)를 실행하는 순간 만들어진다. BEGIN 후 한참 있다가 첫 SELECT를 하면 스냅샷은 그 SELECT 시점. 즉시 만들려면 START TRANSACTION WITH CONSISTENT SNAPSHOT.
스냅샷 읽기 vs 현재 읽기
Read View를 쓰는 건 일반 SELECT뿐. SELECT ... FOR UPDATE / FOR SHARE, UPDATE, DELETE는 격리 수준과 무관하게 항상 최신 커밋 버전을 읽고 락을 잡는다 (locking read, 흔히 current read).

실무 함정 — 두 읽기가 다른 세상을 본다

RR에서 내 SELECT는 과거 스냅샷을 보는데 내 UPDATE는 최신 행에 적용된다. "SELECT로 재고 10개 확인 → UPDATE SET stock = 9"는 그 사이 남이 재고를 3으로 줄였어도 9로 덮어쓴다(갱신 유실). → 꼬리질문 4에서 고치는 법.

MVCC의 스냅샷은 보고용, 결정용 읽기는 잠금 읽기여야 한다.

3. 비용 — "긴 트랜잭션 → undo 누적 → purge 지연 → 조회 저하" 사슬

이 절이 이 페이지가 가장 겨냥하는 지점이다. "긴 트랜잭션은 안 좋다"가 아니라 어떤 부품이 어떤 순서로 막혀서 누구의 무엇이 느려지는지를 이름 붙여 말해야 한다.

3-1. purge는 무엇을 하는가

치우는 것 ①
더 이상 어떤 Read View도 필요로 하지 않는 update undo 레코드 폐기
치우는 것 ②
delete-mark만 켜져 있던 행과 그 인덱스 엔트리를 물리적으로 제거

purge의 진도를 정하는 단 하나

"더 이상 필요 없다"의 기준 = 현재 살아 있는 가장 오래된 Read View가 그 버전을 볼 가능성이 없는가.
→ 가장 오래된 Read View 하나가 purge의 진도를 결정한다.

커밋됐지만 아직 purge되지 않은 undo의 목록이 history list, 그 길이가 SHOW ENGINE INNODB STATUS의 History list length — MVCC 건강의 대표 지표다.

3-2. 사슬 — 이름 붙여서 순서대로

사슬 7단계 — 이름으로 부르기 "보유 · 정지 · 증가 · 길어짐 · 순회 · 유령 · 폭주"

① Read View 보유→ ② purge 정지→ ③ history list 증가→ ④ 체인 길이 증가→ ⑤ 체인 순회 비용 (무관 트랜잭션 전파)→ ⑥ 유령 인덱스 엔트리→ ⑦ 종료 시 purge 폭주
MVCC의 청구서는 "무엇을 했는가"가 아니라 "얼마나 오래 열려 있었는가"에 비례하고,
그 청구서를 받는 건 그 트랜잭션이 아니라 남들이다.

3-3. 세컨더리 인덱스와 MVCC — 커버링 인덱스가 조용히 무력화되는 순간 가산점

DB_TRX_ID는 클러스터드 인덱스 레코드에만 있다. 세컨더리 인덱스 엔트리에는 없다. 그럼 세컨더리 인덱스만 읽고 끝내는 커버링 인덱스 조회는 버전 판정을 어떻게 하나?

인덱스 페이지의 PAGE_MAX_TRX_ID< 내 하한선?
예 — 페이지 전체가 내 스냅샷 이전
이 페이지의 엔트리는 전부 봐도 되는 것 → 인덱스만으로 끝 (커버링 유지)
아니오 — 최근 누가 건드렸다 / delete-mark
판정 불가 → 클러스터드 인덱스로 내려가 DB_TRX_ID 확인 → 북마크 룩업(랜덤 I/O) 부활

커버링 인덱스로 설계했는데 갱신이 잦은 구간에서 느려진다면 숨은 원인 하나가 MVCC다. "커버링 인덱스인데 왜 느리지"의 답 후보.

3-4. 실무에서 사슬 ①을 만드는 전형적인 코드

가장 흔한 범인은 트랜잭션 안의 외부 호출이다. 락 점유·커넥션 풀 고갈 관점의 피해는 ACID 문서에서 다뤘고, 여기서는 MVCC 관점의 피해를 붙인다 — 이 코드가 도는 동안 DB 전체의 purge가 멈춘다.

BEFORE 트랜잭션 안에서 외부 PG 호출
@Transactional
public void settle(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();RR: 여기서 Read View 생성 → purge가 이 시점에 묶임

    PgResult result = pgClient.capture(order);외부 HTTP. 평소 300ms, 장애 시 30초 × 재시도
    // 그동안 이 트랜잭션은 "살아 있는 가장 오래된 Read View"가 되어
    // DB의 모든 테이블에 대한 undo 정리를 막는다. 커넥션도 점유.

    order.markPaid(result);
}   // 커밋 → 그제야 Read View 해제 → 밀린 purge 폭주
AFTER 읽기 트랜잭션 / 외부 호출 / 쓰기 트랜잭션을 분리
public void settle(Long orderId) {
    OrderSnapshot snapshot = orderTxService.loadForSettlement(orderId);짧은 @Transactional(readOnly=true) — 수 ms 안에 RV 생성·해제

    PgResult result = pgClient.capture(snapshot);트랜잭션 밖. 30초 걸려도 DB는 아무것도 안 붙듦

    orderTxService.markPaid(orderId, result);별도의 짧은 @Transactional — 이미 처리됐는지 검증 후 갱신
}
// orderTxService는 별도 빈이어야 @Transactional 프록시가 적용된다 (자기 호출 함정)
두 번째 범인 — 사람이 연 콘솔 트랜잭션 SET autocommit = 0 상태의 DB 클라이언트에서 SELECT 한 번 날리고 창을 켜 둔 채 퇴근하면, 그 세션이 밤새 "가장 오래된 Read View"가 된다. 코드 리뷰로는 절대 못 잡는 유형이라 4-2절의 DB 쪽 안전망이 필요하다.

4. 트레이드오프 양면 조립 + 안전망 고정

4-1. MVCC의 양면 — 한 호흡으로

"MVCC는 읽기 성능이 좋다"까지만 말하면 절반이다. 얻는 것과 내는 것을 같은 문장에 넣는다.

축얻는 것내는 것
읽기락 없이 일관된 스냅샷 — 읽기와 쓰기가 서로 안 막힘행마다 버전 판정 + 체인 순회 (CPU · undo 페이지 I/O)
쓰기읽기에 막히지 않음모든 UPDATE/DELETE가 undo를 추가로 기록(쓰기 증폭); 쓰기끼리는 여전히 락
저장 공간—undo 누적, delete-mark 유령 엔트리, purge 백그라운드 부하
정합성긴 리포트도 일관된 결과를 봄스냅샷은 "과거"다 — 판단(check-then-act)에 쓰면 갱신 유실 위험

조립한 문장 — 그대로 말하기

"MVCC는 읽기 락을 없애 읽기-쓰기 비차단을 얻는 대신, 그 대가를 undo 공간 · 버전 체인 순회 · purge 부하로 치른다. 그리고 그 청구서는 트랜잭션 길이에 비례해 커지고, 범인이 아닌 트랜잭션들에게 배달된다."

이 문장이 그대로 "그래서 트랜잭션은 짧게"의 근거가 된다.

한 겹 더 시니어 변별 이 트레이드오프는 읽기 위주 OLTP 워크로드에 최적화된 선택이다. 쓰기 비중이 압도적이거나 같은 행을 초고빈도로 갱신하는 워크로드(카운터, 재고)에서는 버전 체인이 빨리 길어지고 쓰기끼리 락 직렬화가 병목이라 MVCC의 강점이 거의 안 보인다 — 그런 구간은 원자적 UPDATE · 버퍼링 · 배치 반영으로 설계를 바꾸는 것이 답이지 격리 수준을 만지는 게 아니다.

4-2. 안전망 — 기억이 아니라 시스템이 잡게 한다

"트랜잭션을 짧게 유지하자"는 규칙을 사람의 기억에 맡기면 반드시 뚫린다. DB 쪽과 애플리케이션 쪽에 각각 고정한다.

DB 쪽 — 지금 누가 purge를 막고 있는지 즉시 찾는 쿼리

-- ① 열려 있는 트랜잭션, 오래된 순. trx_query가 NULL인데 age가 크면
--    "쿼리는 안 돌고 트랜잭션만 열어 둔" 전형적 범인 (외부 호출 대기, 콘솔 방치)
SELECT trx_id, trx_state, trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec,
       trx_mysql_thread_id, trx_rows_locked, trx_query
  FROM information_schema.INNODB_TRX
 ORDER BY trx_started
 LIMIT 10;

-- ② purge 대기 중인 undo 양 (History list length)
SELECT COUNT FROM information_schema.INNODB_METRICS
 WHERE NAME = 'trx_rseg_history_len';
-- 또는 SHOW ENGINE INNODB STATUS\G 의 TRANSACTIONS 절 "History list length"
지표 알림
②를 모니터링 지표로 수집해 임계치 알림. 평소 대비 급증 = "어딘가에 긴 트랜잭션이 생겼다". 조회가 느려지기 전에 잡는 유일한 선행 지표.
범인 특정 → KILL
알림이 오면 ①로 스레드를 특정하고 KILL <thread_id>. "N분 이상 열린 idle 트랜잭션 자동 종료"를 도구(pt-kill류)로 고정. 사람이 새벽에 깨서 죽이는 구조는 안전망이 아니다.
사후 정리
innodb_undo_log_truncate로 팽창한 undo 테이블스페이스를 자동 축소. 단 이건 사후 정리이지 사슬 ①을 막는 게 아니다.

5. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 답에 부품 이름(숨은 컬럼 · undo 체인 · Read View · purge · history list)이 들어갔는지 스스로 채점한다.

MVCC가 있는데 왜 락이 여전히 필요한가요?힌트: MVCC가 없애는 대기는 딱 한 종류

MVCC가 없애는 건 읽기-쓰기 사이의 대기뿐이다. 두 트랜잭션이 같은 행을 동시에 UPDATE하는 쓰기-쓰기 충돌은 버전을 아무리 쌓아도 "누구 것이 최종인가"를 정할 수 없어 배타 락으로 직렬화한다.

또 UPDATE·DELETE·SELECT ... FOR UPDATE 같은 잠금 읽기는 스냅샷이 아니라 최신 버전을 읽고 락을 잡는다 — 스냅샷을 근거로 갱신하면 갱신 유실이 나기 때문이다. 마지막으로 RR에서 "아직 없는 행"의 INSERT를 막는 건 MVCC가 못 하는 일이라 갭 락이 맡는다(다음 문항).

읽기 절반은 MVCC, 쓰기 절반과 범위 보호는 락.
READ COMMITTED와 REPEATABLE READ의 차이를 InnoDB 내부 동작으로 설명해 보세요.힌트: 부품은 같다. 다른 건 딱 하나

숨은 컬럼도 undo 체인도 똑같다. 차이는 Read View를 언제 만드느냐 하나다. RC는 문장마다 새 Read View를 만들어 매 SELECT가 그 순간 커밋된 최신을 보고, RR은 트랜잭션의 첫 일관된 읽기 때 한 번 만들어 끝까지 재사용한다. 그래서 RC에서는 두 SELECT 사이에 남이 커밋하면 값이 바뀌고(non-repeatable read), RR에서는 같은 스냅샷을 보니 안 바뀐다.

덧붙이면 RR의 Read View는 BEGIN이 아니라 첫 SELECT 시점에 만들어지고, 잠금 읽기는 두 수준 모두 스냅샷을 쓰지 않는다.

운영 관점 한 줄 — RC는 Read View 수명이 문장 단위라 긴 트랜잭션이 purge를 막는 정도가 훨씬 약하다. 배치·통계성 긴 조회를 RC로 내리는 판단의 근거가 이것이다.

긴 트랜잭션 하나가 왜 그것과 무관한 다른 조회까지 느리게 만드나요? 어떻게 확인하죠?힌트: 사슬 7단계를 이름으로. "무관한"의 답은 ②와 ⑤

메커니즘 사슬로 답한다. ① 긴 트랜잭션이 Read View를 보유한다 → ② purge는 "가장 오래된 Read View가 볼 수도 있는 버전"을 지울 수 없어 그 이후의 update undo를 전부 보존한다 — Read View는 테이블 단위가 아니라 DB 전체에 걸린다, 그래서 무관한 테이블도 영향권이다 → ③ History list length 증가 → ④ 자주 갱신되는 행의 버전 체인이 길어진다 → ⑤ 그 행을 읽는 모든 트랜잭션이 행마다 체인을 순회하며 undo 페이지 I/O와 CPU를 쓴다 → ⑥ delete-mark 행이 인덱스에 유령으로 남아 범위 스캔이 더 읽는다.

확인은 INNODB_METRICS의 trx_rseg_history_len(또는 SHOW ENGINE INNODB STATUS의 History list length) 급증으로 감지하고, information_schema.INNODB_TRX를 trx_started 순으로 정렬해 쿼리는 없는데 오래 열린 트랜잭션을 특정한다. 재발 방지는 지표 알림 + 장기 idle 트랜잭션 자동 종료 + 코드 쪽 ArchUnit·timeout.

REPEATABLE READ에서 SELECT로 재고 10개를 확인하고 UPDATE로 9를 썼는데 재고가 꼬였습니다. 왜 그렇고, 어떻게 고치나요? 시니어 변별힌트: 두 읽기가 다른 세상을 본다

스냅샷 읽기와 현재 읽기가 다른 세상을 보기 때문이다. 일반 SELECT는 Read View 기준 과거 스냅샷(10)을 보여 주지만, UPDATE는 격리 수준과 무관하게 최신 커밋 행에 적용된다. 그 사이 다른 트랜잭션들이 재고를 3까지 줄여 커밋했어도 내 SELECT는 여전히 10이라 하고, 내 SET stock = 9는 최신 행을 9로 덮어쓴다 — 갱신 유실이다. 격리 수준을 올려서 풀 문제가 아니다(SERIALIZABLE은 전역 비용).

고치는 법 — "판단의 근거가 되는 읽기는 현재 읽기로"

  1. 가장 싼 건 읽기 자체를 없애는 원자적 UPDATE — UPDATE item SET stock = stock - 1 WHERE id = ? AND stock >= 1, affected rows 0이면 재고 부족.
  2. 차감 전후로 검증 로직이 필요하면 SELECT ... FOR UPDATE로 최신을 읽으면서 잠근다.
  3. 충돌이 드물면 버전 컬럼 기반 낙관적 락 + 재시도.
MVCC의 스냅샷은 보고용이고, 결정용 읽기는 잠금 읽기여야 한다.
PostgreSQL의 MVCC와 InnoDB의 MVCC는 어떻게 다른가요? 가산점힌트: 과거 버전을 어디에 두느냐

과거 버전을 어디에 두느냐가 다르다. InnoDB는 테이블(클러스터드 인덱스)에 최신 버전 하나만 두고 과거 버전을 undo 로그에 사슬로 매단다. PostgreSQL은 UPDATE를 "새 튜플 INSERT + 옛 튜플에 만료 표시"로 처리해 과거 버전이 테이블 힙 안에 그대로 남는다(각 튜플이 xmin/xmax로 생성·만료 트랜잭션을 기록).

공통점긴 트랜잭션이 정리 작업을 막아 남들을 느리게 한다 — 어느 DB든 "트랜잭션은 짧게"의 근거는 같다

이 비교를 할 수 있으면 MVCC를 특정 DB의 기능이 아니라 설계 선택으로 이해하고 있다는 신호가 된다.

추가 꼬리질문 — 부품 하나씩 콕 찍어 묻는 것들

undo 로그는 ACID의 어느 글자를 담당하나요? 약점 겨냥힌트: 한 글자가 아니다

두 글자를 겸직한다. A(원자성) — 변경 전 값을 적어 뒀다가 롤백 때 역순으로 되돌리는 도구. I(격리성) — 그 "변경 전 값"이 곧 다른 트랜잭션에게 보여줄 "과거 버전"이므로 MVCC의 버전 저장소. 같은 장부 하나가 롤백용이자 과거 버전 제공용이다.

그래서 undo가 누적되면 A의 비용(롤백이 오래 걸림)과 I의 비용(조회가 느려짐)이 동시에 청구된다. 참고로 D(지속성)는 redo 로그의 몫이고, A/I를 헷갈리지 않는 축은 — A는 "끝났을 때 전부냐 전무냐", I는 "동시에 도는 남이 내 중간을 보느냐".

REPEATABLE READ의 Read View는 BEGIN 시점에 만들어지나요?힌트: 아니다. 그럼 언제?

아니다. 첫 일관된 읽기(일반 SELECT)를 실행하는 순간 만들어진다. BEGIN 후 한참 있다가 첫 SELECT를 하면 스냅샷은 그 SELECT 시점이다. 즉시 만들고 싶으면 START TRANSACTION WITH CONSISTENT SNAPSHOT을 쓴다. 이 디테일은 "긴 트랜잭션이 언제부터 purge를 막기 시작하는가"에도 그대로 적용된다 — 첫 SELECT부터다.

DELETE를 커밋하면 행이 바로 사라지나요?힌트: 비트 하나

아니다. InnoDB의 DELETE는 행을 물리적으로 지우지 않고 delete-mark 비트만 켠다. 아직 그 행을 봐야 할 Read View가 있을 수 있기 때문이다. 실제 제거(행 + 인덱스 엔트리)는 purge가 "그 버전을 볼 Read View가 하나도 없다"를 확인한 뒤 수행한다. 그래서 긴 트랜잭션이 있으면 지운 행이 인덱스에 유령 엔트리로 남아, 대량 삭제 후에도 범위 스캔·COUNT가 느린 역설이 생긴다.

insert undo는 왜 커밋 즉시 지워도 되나요? update undo와 뭐가 다르죠?힌트: INSERT 전엔 무엇이 있었나

insert undo는 롤백(A)에만 필요하다. INSERT 전에는 행이 없었으므로, 다른 트랜잭션이 "과거 버전"으로 볼 것이 없다 — 그 행이 안 보여야 할 Read View에는 그냥 안 보이면 된다(체인 끝까지 가도 보이는 버전 없음 → 제외). 그래서 커밋하는 순간 폐기한다.

반면 update undo는 이전 값을 담고 있어 롤백(A)뿐 아니라 다른 트랜잭션의 일관된 읽기(I)에도 쓰인다. 커밋했다고 바로 못 지우고, 그 버전을 봐야 할 Read View가 사라질 때까지 history list에 남아 purge를 기다린다.

History list length 알림이 왔습니다. 첫 조치 순서는?힌트: 찾고 → 끊고 → 못 만들게
  1. information_schema.INNODB_TRX를 trx_started 오름차순으로 조회 — trx_query가 NULL인데 age가 큰 트랜잭션이 범인 후보(외부 호출 대기 또는 콘솔 방치).
  2. trx_mysql_thread_id로 KILL <thread_id>. 끝나면 밀린 purge가 돌면서 History list length가 내려가고 잠시 I/O가 튈 수 있음을 알고 본다.
  3. 재발 방지 — 장기 idle 트랜잭션 자동 종료(pt-kill류), 코드 쪽 @Transactional(timeout)·ArchUnit·HikariCP leak detection. 팽창한 undo는 innodb_undo_log_truncate로 사후 축소.
커버링 인덱스로 설계했는데 갱신이 잦은 구간에서 느립니다. MVCC와 무슨 관계죠? 가산점힌트: 세컨더리 인덱스엔 DB_TRX_ID가 없다

DB_TRX_ID는 클러스터드 인덱스 레코드에만 있다. 세컨더리 인덱스만 읽는 커버링 조회는 페이지 단위의 PAGE_MAX_TRX_ID(그 페이지를 마지막으로 수정한 트랜잭션 ID)로 판정한다. 이 값이 내 Read View의 하한선보다 작으면 페이지 전체가 보이는 것이라 인덱스만으로 끝낸다. 그런데 최근 누군가 그 페이지를 건드렸거나 엔트리가 delete-mark 상태면 판정이 불가능해 클러스터드 인덱스로 내려가 DB_TRX_ID를 확인한다 — 커버링이 깨지고 북마크 룩업(랜덤 I/O)이 되살아난다.

SERIALIZABLE에서도 MVCC 스냅샷을 쓰나요?힌트: 일반 SELECT의 정체가 바뀐다

InnoDB의 SERIALIZABLE은 일반 SELECT도 공유 락을 잡는 잠금 읽기로 바꾼다. 즉 Read View 기반 스냅샷 읽기를 쓰지 않고, 읽는 행마다 락을 잡아 락만으로 격리하는 1-1절의 세계로 돌아간다. 그래서 읽기가 쓰기를 막고 쓰기가 읽기를 막는 비용이 전역으로 되살아난다 — "격리 수준을 올려서 갱신 유실을 막자"가 답이 아닌 이유.

스냅샷 읽기가 phantom을 막는다면서 왜 RR에 갭 락이 필요한가요?힌트: 잠금 읽기는 스냅샷을 안 쓴다

일반 SELECT(스냅샷 읽기)는 같은 Read View를 재사용하므로 남이 INSERT해 커밋한 행이 안 보인다 — 여기까진 MVCC가 phantom을 가린다. 그러나 SELECT ... FOR UPDATE·UPDATE·DELETE 같은 잠금 읽기는 최신 버전을 읽으므로 새로 INSERT된 행이 보인다. 이걸 막으려면 "아직 없는 행"이 들어올 범위(갭) 자체를 잠가 INSERT를 차단해야 하고, 그게 갭 락·넥스트 키 락이다. MVCC는 과거 버전을 보여줄 수는 있어도 미래의 INSERT를 막을 수는 없다.

한 줄 요약
MVCC는 "읽는 쪽이 락 대신 자기 시점의 과거 버전을 보는" 격리(I) 구현으로, InnoDB는 행의 숨은 컬럼 DB_TRX_ID·DB_ROLL_PTR, undo 로그로 이어진 버전 체인, 그리고 "어떤 트랜잭션까지 보이는가"를 찍은 Read View(활성 목록·하한선·상한선·자기 ID)로 구현한다 — Read View를 문장마다 만들면 RC, 트랜잭션당 한 번이면 RR이고, 잠금 읽기는 스냅샷이 아닌 최신을 읽는다. 읽기-쓰기 비차단을 얻는 대가는 undo 공간·체인 순회·purge 부하이며, 이 청구서는 트랜잭션 길이에 비례해 커져 "긴 트랜잭션 → purge 정지 → history list 증가 → 체인 길어짐 → 무관한 조회까지 행마다 체인 순회"라는 사슬로 남들에게 배달된다. 그래서 History list length를 지표로 걸고, 외부 호출을 트랜잭션 밖으로 빼는 규칙을 ArchUnit·timeout·leak detection으로 고정한다.
