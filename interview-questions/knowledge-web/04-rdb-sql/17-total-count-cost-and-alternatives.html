목록 API의 total count 비용
"전체 몇 건 중 몇 페이지"는 목록 본체보다 비싼 요구다

면접 질문: "목록 API의 전체 건수(total count) 조회가 대용량에서 비싼 이유와 대안은? (근사치, 카운트 캐싱, 무한 스크롤 전환)"

핵심 관전 포인트 — 목록 쿼리는 LIMIT 20에서 멈추지만 count(*)는 조건에 맞는 행을 전부 만나야 끝난다 — 비용이 페이지 크기가 아니라 조건에 맞는 전체 행 수 N에 비례한다. PostgreSQL이 행 수를 메타데이터로 못 드는 이유는 MVCC다: 옛 버전 튜플이 힙 페이지 안에 그대로 남고 스냅샷마다 보이는 행이 달라 "정답인 숫자"가 하나가 아니므로, 튜플마다 xmin/xmax로 가시성을 판정하며 셀 수밖에 없다. 그래서 어떤 인덱스도 개수를 미리 알고 있지 않고, 조건 없는 count(*)조차 전체를 훑는다. 조건 컬럼이 인덱스에 다 없으면 그 N건마다 힙 페치(랜덤 I/O)가 붙고, 다 있어도 Index Only Scan이 힙을 건너뛰려면 visibility map이 신선해야(Heap Fetches: 0) 한다. 대안은 다섯 갈래 — ① 커버링·부분 인덱스 ② 근사치 ③ 카운트 캐싱·카운터 테이블 ④ Slice ⑤ 무한 스크롤·커서·검색 엔진 — 각각 정확도·정합성·UX 중 하나를 내주는 거래다. Spring Data의 Page는 count 쿼리를 자동으로 붙이므로 기본은 Slice, Page는 근거 필수라는 규약을 코드(ArchUnit)와 계측(count 분리 측정)으로 고정한다. 그 가격표를 기획에 보여주는 것까지가 백엔드의 일이다.
  • 1
    비용의 "차원"이 다르다 — 목록은 LIMIT에서 멈춰 페이지 크기(상수)에 비례하고, count는 멈출 수 없어 조건에 맞는 전체 행 수 N에 비례한다. 같은 화면의 두 쿼리가 20건 대 300만 건이고, 게다가 페이지를 넘길 때마다 매번 다시 실행된다.
  • 2
    메타데이터로 못 드는 이유는 MVCC다 — 옛 버전이 힙에 남고 스냅샷마다 보이는 행이 달라 단일 정답이 없으므로 튜플마다 세는 수밖에 없다. 인덱스 엔트리에는 버전 정보가 없어 어떤 인덱스도 개수를 미리 알지 못하고, reltuples는 추정치다. 훑을 때 힙 페치냐 Index Only Scan이냐가 수십 배를 가른다.
  • 3
    커버링은 배수만 줄이고, 차원을 바꾸려면 무언가를 내줘야 한다 — 근사치(정확도) · 카운트 캐싱(정합성) · Slice·무한 스크롤(UX). 그래서 첫 질문은 기술이 아니라 "총 건수가 어디에 쓰이나요?"이고, 합의 결과는 ArchUnit 규칙과 분리 측정으로 코드에 고정한다.

0. 질문 + 출제 의도

질문: "목록 API의 전체 건수(total count) 조회가 대용량에서 비싼 이유와 대안은? (근사치, 카운트 캐싱, 무한 스크롤 전환)"

출제 의도: COUNT는 조건에 맞는 전체를 세야 해서 목록 조회 본체보다 비싼 경우가 많다. "전체 몇 건 중 몇 페이지" UI가 기술적으로 얼마나 비싼 요구인지 알고 근사치·카운트 캐싱·무한 스크롤 같은 대안을 기획과 협상해봤는지 — 요구사항의 비용을 알려주는 것까지가 백엔드의 일임을 아는지 본다.

함정 — "COUNT는 전체를 다 훑어서 느립니다" 맞는 말이지만 현상 진술이다. 이 문장으로 끝내면 "왜 다 훑어야만 하나요? 인덱스가 있는데도요?" 한 마디에 무너진다. 필요한 것은 멈출 수 없는 이유 + 메타데이터로 못 드는 이유 + 훑을 때 무엇을 읽는지의 세 고리다.
이 페이지가 겨냥하는 약점 세 가지 ① 비용을 뭉뚱그리는 것 → 1·2·3절에서 "이름 → 사슬"로 바꿔 말하는 훈련. 비용 차원의 차이 → MVCC 스냅샷 → Index Only Scan vs 힙 페치.
② 내 코드가 count를 날리는 줄 모르는 것 → 4절에서 SQL 로그로 눈으로 확인한다. Page 한 줄이 SQL 두 개다.
③ 대안을 한쪽 면만 말하는 것 → 6·7절에서 다섯 대안을 목록으로 인출하고 각각의 대가를 한 호흡에 붙이고, 8절에서 그 선택을 기억이 아니라 코드·계측으로 고정한다.
역할 구분 — 깊은 페이지네이션 문서와 무엇이 다른가 같은 섹션의 13-deep-pagination-offset-vs-cursor.md는 LIMIT 20 OFFSET 100000의 offset 비용(건너뛰기 위해 읽는 행)을 다룬다. 이 문서는 count 비용(세기 위해 읽는 행)이다. 목록 API가 느릴 때 이 둘은 원인도 처방도 다르므로 따로 측정하고 따로 고친다(8-1절). 커서(키셋) 페이징 자체의 구현·tie-breaker는 13번 문서에 있고, 여기서는 "커서가 count 비용까지 함께 없앤다"는 접점만 다룬다.

1. 비용의 차원 — 목록은 20건에서 멈추고, count는 멈출 수 없다

먼저 비유 하나 — 도서관에서 "빌리기"와 "세기" 서가에서 책 20권을 빌리는 일은 조건에 맞는 책 20권을 찾는 순간 끝난다. 서가에 그 조건의 책이 300만 권 더 있어도 상관없다. 그런데 "이 조건의 책이 총 몇 권인지"를 답하려면 서가 끝까지 걸어가며 하나하나 세는 것 말고 방법이 없다. 같은 서가에서 벌어지는 두 작업인데 걸리는 시간의 차원이 다르다 — 이것이 목록 쿼리와 count 쿼리의 관계다.
SQL 같은 화면의 두 쿼리 — 비용의 차원이 다르다
-- 목록 본체: 인덱스 (seller_id, status, created_at)를 타고
-- 조건에 맞는 첫 20건을 읽는 순간 끝난다.        비용 ∝ 페이지 크기(20)
SELECT id, amount, created_at
  FROM orders
 WHERE seller_id = 42 AND status = 'PAID'
 ORDER BY created_at DESC
 LIMIT 20;                                 -- ← 여기서 멈춘다

-- 총 건수: 조건에 맞는 행이 300만 건이면 300만 건을 전부 "만나야" 끝난다.
--                                                비용 ∝ 조건에 맞는 전체 행 수(N)
SELECT count(*)                              -- ← 멈출 조건이 없다
  FROM orders
 WHERE seller_id = 42 AND status = 'PAID';
첫 문장은 "count는 느리다"가 아니라 "count는 비용의 차원이 다르다 — 페이지 크기가 아니라 N에 비례한다"

2. "그냥 행 수를 저장해 두면 되잖아요?" — 못 하는 이유는 MVCC다

가장 자연스러운 반문부터 받아내야 한다. "테이블에 행 수를 하나 적어 두고 INSERT/DELETE 때 ±1 하면 되지 않나?" 그럴 수 없는 이유가 MVCC(Multi-Version Concurrency Control, 다중 버전 동시성 제어)다. 읽기가 쓰기를 막지 않도록(락 없이) 행의 여러 버전을 동시에 보관하는 방식인데, PostgreSQL의 구현은 이렇다.

① 옛 버전은 지워지지 않고 힙에 남는다
UPDATE/DELETE는 행을 제자리에서 고치거나 지우지 않는다. 모든 튜플(행의 한 버전)은 헤더에 xmin(이 버전을 만든 트랜잭션 ID)과 xmax(이 버전을 지우거나 갱신한 트랜잭션 ID, 없으면 0)를 달고 있다. DELETE는 xmax만 찍고, UPDATE는 새 튜플을 하나 더 넣고 옛 튜플에 xmax를 찍는다. 옛 버전은 별도 공간이 아니라 힙 페이지 안에 그대로 남는다.
② 보이는 버전은 스냅샷이 정한다
각 트랜잭션(기본 격리인 READ COMMITTED에서는 각 문장)은 시작 시점에 스냅샷("어느 트랜잭션들이 진행 중인가"를 찍어 둔 것)을 하나 뜬다. 튜플을 만날 때마다 xmin/xmax를 스냅샷과, 그리고 그 트랜잭션이 커밋됐는지 기록한 pg_xact(CLOG)와 대조해 "내게 보이는 버전인가"를 판정한다.

PostgreSQL 고유의 덤 — count는 죽은 튜플까지 만난다

옛 버전이 힙 안에 남으므로, count는 살아 있는 행뿐 아니라 VACUUM이 아직 안 치운 죽은 튜플까지 만나서 "안 보임"을 판정해야 한다. 갱신·삭제가 몰리는 시간대에 VACUUM이 못 따라오거나, 긴 트랜잭션이 backend_xmin을 붙들고 있어 VACUUM이 치우지 못하면 count가 읽는 페이지 수가 살아 있는 행 수보다 커진다.

긴 트랜잭션의 해악이 count에까지 번지는 지점 — 8-4절 사례의 절반이 이것이다
가산점 — "대량 INSERT 직후의 첫 count가 두 번째보다 유독 느려요" 커밋 직후 처음 읽히는 튜플은 pg_xact를 조회한 결과를 튜플 헤더의 힌트 비트에 적어 두느라 페이지를 더럽히기까지 한다. 그래서 첫 count가 눈에 띄게 느리고 두 번째부터 빨라지는 현상이 나온다. 튜플 헤더·스냅샷·VACUUM의 상세는 11-mvcc-postgresql.md.

2-1. 반례를 하나 알면 원리가 선명해진다 — MyISAM은 왜 즉답하는가

"그럼 카운트를 싸게 주는 DB는 없나?" 있다. 그리고 그것이 규칙의 예외임을 보면 원리가 선명해진다.

MyISAM — 동시성을 팔아 상수 시간 카운트를 샀다

MySQL의 MyISAM 스토리지 엔진은 조건 없는 count(*)를 테이블 메타데이터에서 즉답한다. 가능한 이유는 테이블 단위 락을 쓰기 때문이다 — 쓰기가 진행 중이면 아무도 못 읽으므로 "한 시점에 유효한 행 수"가 언제나 하나뿐이고, 그러니 그 숫자를 저장해 둘 수 있다.

PostgreSQL·InnoDB — 카운트 비용을 내고 동시성을 샀다

읽기가 쓰기를 안 막는 동시성을 사고, 그 대가로 세는 비용을 낸다. 위 도식처럼 스냅샷마다 정답이 달라지는 세계에서는 미리 세어 둔 숫자가 누구의 정답도 아니다.

"count는 느립니다"가 아니라 "읽기가 쓰기를 안 막는 동시성과 맞바꾼 비용입니다" — 트레이드오프 문장으로 닫는다
MySQL 대조 — 세야 하는 건 같지만, 옛 버전이 어디 있느냐가 다르다 MySQL의 InnoDB도 같은 이유(MVCC)로 세야 하지만 옛 버전을 힙이 아니라 언두 로그에 둔다. 그래서 안 보이는 버전을 만나면 DB_ROLL_PTR을 따라 언두 체인을 거슬러 올라가는 비용이 붙는다 — PostgreSQL은 옛 버전이 죽은 튜플로 힙에 남아 VACUUM 부담이 되는 것과 대칭이다. MySQL 8.0은 조건 없는 count(*)를 가장 작은 세컨더리 인덱스로 훑도록 고정했고, 조건 없는 추정치는 information_schema.TABLES.TABLE_ROWS다.

면접에서 이 표의 오른쪽 칸이 나와야 답이 된다. 왼쪽 칸으로 끝나면 현상 진술이다.

3. 훑을 때 무엇을 읽나 — Index Only Scan vs 힙 페치 카운트

"다 훑는다"가 확정이어도, 무엇을 훑느냐에 따라 I/O가 몇십 배 차이 난다. 전제를 한 줄로 복습하면 — PostgreSQL 테이블은 힙(정렬되지 않은 페이지 더미)이고 모든 인덱스 리프는 (키, TID)만 들고 있어, 인덱스에 없는 컬럼을 확인하려면 TID를 따라 힙 페이지를 열어야 한다(= 힙 페치). 판매자 42의 주문이 500만 건이고 그중 PAID가 300만 건이라고 하자.

before 인덱스가 (seller_id)뿐 — status를 보려고 힙을 연다
CREATE INDEX idx_orders_seller ON orders (seller_id);

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders
 WHERE seller_id = 42 AND status = 'PAID';

--  Aggregate  (actual rows=1 loops=1)
--    ->  Bitmap Heap Scan on orders  (actual rows=3000000)
--          Recheck Cond: (seller_id = 42)
--          Filter: (status = 'PAID')
--          Rows Removed by Filter: 2000000
--          Buffers: shared hit=61000 read=352000
--          ->  Bitmap Index Scan on idx_orders_seller
--                (actual rows=5000000)
--                Index Cond: (seller_id = 42)
읽는 법 인덱스에서 판매자 42의 TID 500만 개를 모아 정렬한 뒤 힙 페이지를 순서대로 방문해 status를 읽고 PAID인지 가른다. 버린 200만 행에도 힙 I/O를 먼저 냈다. 행이 500B면 8KB 페이지에 16행 안팎이고 판매자 42의 행이 힙 전체에 흩어져 있으므로 여는 페이지는 41만 장 — shared_buffers·OS 캐시에 다 못 올라가고 없는 페이지는 디스크에서 읽는다(shared read=352000).
after 조건 컬럼이 전부 인덱스 안 — 인덱스만 읽고 센다
CREATE INDEX idx_orders_seller_status_created
    ON orders (seller_id, status, created_at);

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*) FROM orders
 WHERE seller_id = 42 AND status = 'PAID';

--  Aggregate  (actual rows=1 loops=1)
--    ->  Index Only Scan using
--        idx_orders_seller_status_created on orders
--          (actual rows=3000000)
--          Index Cond: ((seller_id = 42)
--                   AND (status = 'PAID'))
--          Heap Fetches: 0
--          Buffers: shared hit=15400
읽는 법 (seller_id=42, status='PAID') 구간의 리프 엔트리를 오른쪽 링크를 따라 순차로 읽으며 센다. 엔트리가 40B 안팎이면 페이지당 200개 가까이 들어가 300만 건 ≈ 1.5만 페이지 순차 읽기. 힙 페치 0회, 읽은 버퍼가 41만 → 1.5만으로 떨어졌다.

커버링 카운트의 완성 조건은 두 개다

① 계획이 Index Only Scan
조건 컬럼이 전부 인덱스 안에 있어야 한다. 하나라도 빠지면 Filter + 힙 페치로 떨어진다.
② Heap Fetches가 0에 가까움
visibility map이 신선해야 한다 = VACUUM이 따라오고 있어야 한다. 갱신이 잦은 테이블에서 VACUUM이 밀리면 커버링이 무력화된다.

"Index Only Scan이 찍혔는데 왜 안 빨라요?"의 답이 ②다 — 계획 이름만 보지 말고 Heap Fetches 줄을 읽는 습관이 이 문서의 실무 감각이다.

가산점 부분 인덱스 — 조건이 고정된 화면이라면 PostgreSQL에 더 좋은 도구가 있다
-- PAID 행만 담는 인덱스: 인덱스 자체가 조건을 대신하고, 크기도 PAID 비율만큼만
CREATE INDEX idx_orders_seller_paid ON orders (seller_id) WHERE status = 'PAID';

-- count(*) ... WHERE seller_id = 42 AND status = 'PAID'
--   → Index Only Scan using idx_orders_seller_paid, Index Cond: (seller_id = 42)
-- 제약: 쿼리의 WHERE가 인덱스의 WHERE를 "포함"해야 플래너가 쓴다.
--       status가 파라미터로 바뀌는 화면에는 못 쓰고, 그때는 위의 복합 인덱스가 답이다.

3-1. 사슬로 한 호흡에 말하기

조건에 맞는 행이 N건→ count는 N건을 전부 만나야 한다 (LIMIT처럼 못 멈춘다)→ 튜플마다 MVCC 가시성 판정 (죽은 튜플도 만나서 "안 보임" 판정)
조건 컬럼이 인덱스에 다 없으면→ 튜플마다 힙 페치 = 랜덤 I/O N회→ 응답 시간 ∝ N × 힙 I/O 비용
커버링이면→ 인덱스 리프만 순차 읽기 · 페이지당 밀도가 높아 페이지 수가 수십 분의 일→ 단 Heap Fetches: 0이어야 힙을 건너뛴다

마지막 문장이 중요하다 — Bitmap Heap Scan이 TID를 정렬해 랜덤 I/O를 순차화해 주지만 크고 성긴 힙 페이지 수십만 장을 여는 것은 그대로이고, 병렬 집계(Finalize Aggregate → Gather → Partial Aggregate → Parallel Seq Scan)도 워커 수만큼 배수를 나눌 뿐이다. 커버링 인덱스는 count를 "덜 비싸게" 만들지 "싸게" 만들지 않는다. 차원을 바꾸려면 6절의 나머지 대안이 필요하다.

4. 내 코드는 어디서 count를 날리고 있나

대용량에서 count가 비싸다는 걸 알아도, 내 코드가 count를 날리고 있다는 사실 자체를 모르는 경우가 많다. Spring Data JPA의 Page<T>가 그 주범이다. 실제로 나가는 SQL을 눈으로 봐 두는 것이 이 절의 목적이다.

4-1. 몰래 나가는 경로 ① — Page는 count 쿼리를 자동으로 붙인다

bad 이 한 줄이 SQL 두 개다
Page<Order> page = orderRepository.findBySellerIdAndStatus(sellerId, PAID, pageable);
SQL 로그 show-sql 또는 p6spy를 켜면 이렇게 찍힌다
-- 요청: GET /orders?seller=42&status=PAID&page=3&size=20   (Page<Order> 반환)

Hibernate: select o1_0.id, o1_0.amount, o1_0.created_at, o1_0.seller_id, o1_0.status
           from orders o1_0
           where o1_0.seller_id=? and o1_0.status=?
           order by o1_0.created_at desc
           offset ? rows fetch first ? rows only   -- [42, PAID, 60, 20]  목록 본체   12ms

Hibernate: select count(o1_0.id)                     -- 코드 어디에도 안 쓴 쿼리
           from orders o1_0
           where o1_0.seller_id=? and o1_0.status=? -- [42, PAID]          자동 파생 count  780ms

왜 개발 DB에서는 안 보이고 운영에서만 터지나 — Page가 count를 건너뛰는 두 경우

PageableExecutionUtils.getPage는 총 건수를 산수로 알아낼 수 있으면 count 쿼리를 아예 실행하지 않는다.

① 첫 페이지인데 덜 찼다
offset 0 · 가져온 건수 < 페이지 크기
총 건수 = 가져온 건수. count 생략.
② 마지막 페이지다
offset > 0 · 덜 찼고 비어 있지도 않다
총 건수 = offset + 가져온 건수. count 생략. 결과가 아예 비어 있으면 몇 건인지 알 수 없어 count가 나간다.
바꿔 말하면 — 페이지가 꽉 차는 "대용량일 때만" count가 나간다
개발 DB의 데이터 몇십 건으로 테스트하면 count가 안 보이고, 운영에 올라가면 매 요청 count가 붙는 이유

4-2. 몰래 나가는 경로 ② — 파생 count가 틀리거나 무거울 때는 countQuery

@Query를 쓰면 Spring Data는 JPQL의 select … from 부분을 select count(…)로 바꿔 count 쿼리를 파생한다. 이 파생이 문제를 일으키는 세 경우가 있다.

before 목록용 JPQL을 그대로 count에 재사용
@Query("""
    select o from Order o
      join fetch o.seller s
      left join fetch o.coupon c
     where s.id = :sellerId and o.status = :status
    """)
Page<Order> findPage(Long sellerId, OrderStatus status, Pageable pageable);

// ① fetch join이 든 JPQL을 count로 바꾸면 Hibernate가 예외를 던진다
//    ("query specified join fetching, but the owner … was not
//      present in the select list")
//    — 그것도 count가 "실제로 실행될 때만"(4-1절) 터지므로
//      개발 DB에서는 끝까지 안 보인다
// ② 예외가 안 나더라도, 세는 데 필요 없는 coupon 조인까지
//    count 쿼리에 끌려 들어가 조인 비용을 두 번 낸다
// ③ 네이티브 쿼리(nativeQuery = true)는 파생 자체가 불안정하다
after 세는 데 필요한 최소 조건만 남긴 countQuery를 따로
@Query(value = """
    select o from Order o
      join fetch o.seller s
      left join fetch o.coupon c
     where s.id = :sellerId and o.status = :status
    """,
    countQuery = """
    select count(o) from Order o
     where o.seller.id = :sellerId and o.status = :status
    """)
Page<Order> findPage(Long sellerId, OrderStatus status, Pageable pageable);

// count는 조인 없이 orders 한 테이블 +
// (seller_id, status, …) 인덱스의 Index Only Scan으로 끝난다
countQuery를 분리하는 이유는 두 가지다 ① 실패를 막기 위해(fetch join) ② count가 3절의 Index Only Scan 경로를 타도록 만들기 위해. 목록 쿼리는 표시할 컬럼이 많아 커버링이 안 되지만, count는 조건 컬럼만 있으면 되니 훨씬 가벼운 실행 계획을 줄 수 있다 — 같은 화면의 두 쿼리에 서로 다른 계획을 태우는 것이 요령이다.
가산점 — Querydsl의 fetchResults()가 deprecated된 이유도 같다 목록 + count를 한 번에 만들어 주던 fetchResults()는 같은 문제(조인이 count에 끌려 들어감)로 폐기됐다. 정석은 목록은 fetch(), count는 조인을 뺀 별도 select(order.count())로 만들고 PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne)처럼 LongSupplier로 넘기는 것이다. count 쿼리가 "지연 실행"되어야 4-1절의 건너뛰기 최적화까지 그대로 누릴 수 있다는 점이 핵심이다.

4-3. 몰래 나가는 경로 ③ — 총 건수가 필요 없다면 Slice

before 화면은 "더 보기" 버튼뿐인데 Page를 쓴다
Page<Order> findBySellerIdAndStatus(
        Long sellerId, OrderStatus status, Pageable pageable);

// 매 요청 count 쿼리가 붙는다 (아무도 쓰지 않는 숫자를 위해)
after 반환 타입 한 줄만 바꾼다
Slice<Order> findBySellerIdAndStatus(
        Long sellerId, OrderStatus status, Pageable pageable);

// count 쿼리가 사라진다. 추가 비용은 행 1건(size + 1)

그런데 여기서 응답 모델도 따라 바뀐다. 이것이 백엔드 혼자 결정할 수 없는 이유이기도 하다 — 6-4절과 7절에서 다시 다룬다.

before 총 페이지 수를 실어 클라이언트가 페이지 번호를 그린다
record PageResponse<T>(
    List<T> content, int page,
    int totalPages, long totalElements) {}
after 다음 페이지 유무만 실어 "더 보기"를 그린다
record SliceResponse<T>(
    List<T> content, int page,
    boolean hasNext) {}
더 가벼운 선택지와, 더 나아간 선택지 더 가벼운 쪽 — List<Order> findBy…(Pageable)도 가능하다. count도 hasNext도 없이 딱 페이지 크기만큼만. "다음" 버튼조차 없는 위젯(최근 주문 5건 같은)에 맞다.
더 나아간 쪽 가산점 — 최근 Spring Data에는 Window<T>/ScrollPosition 기반 Scroll API가 있어 offset이 아닌 키셋(커서) 방식으로 다음 묶음을 가져올 수 있다. count 비용(이 문서)과 offset 비용(13번 문서)을 한 번에 없애는 방향이다.

5. "목록과 count를 쿼리 한 번에"라는 함정 — count(*) OVER ()

왕복 한 번을 아끼려고 윈도우 함수로 총 건수를 각 행에 실어 보내는 패턴이 PostgreSQL에서 자주 보인다. 겉으로는 쿼리 하나로 깔끔해 보이는데, 정확히 반대 결과가 나온다.

anti-pattern 목록 쿼리에 총 건수를 얹는다
SELECT id, amount, created_at, count(*) OVER () AS total
  FROM orders
 WHERE seller_id = 42 AND status = 'PAID'
 ORDER BY created_at DESC
 LIMIT 20;

-- 윈도우 함수는 LIMIT "전에", 조건에 맞는 전체 결과 집합 위에서 계산된다.
-- → 20건짜리 목록 쿼리가 N건을 전부 만난다. 목록까지 count 비용을 물게 된 것.
-- EXPLAIN (ANALYZE)를 보면 Limit 아래 WindowAgg의 입력 스캔이
--   actual rows=3000000 으로 찍힌다 — 목록 본체의 "20건에서 멈춤"이 사라졌다.
MySQL 대조 — 같은 유혹의 MySQL 판 SQL_CALC_FOUND_ROWS + FOUND_ROWS()가 정확히 같은 아이디어였다. LIMIT을 무시하고 결과 집합 전체를 끝까지 평가하게 만들어 같은 이유로 느렸고, MySQL 8.0에서 deprecated 됐다. "DB가 한 번에 해 주면 싸겠지"라는 직관이 두 DB에서 똑같이 틀린 것이 이 함정의 요점이다.

6. 대안 5가지 — 무엇을 내주고 무엇을 얻는가

3절의 결론은 "count 비용은 N에 비례하고, 커버링은 배수만 줄인다"였다. 차원을 바꾸려면 정확도 · 정합성 · UX 중 하나를 내줘야 한다. 다섯 대안을 목록으로 고정하고, 각각 얻는 것과 내주는 것을 한 호흡에 말한다. 한쪽만 말하면 답이 아니다.

대안 5종 인출 장치 — 커 · 근 · 캐  /  슬 · 무

① 커버링·부분 인덱스 ② 근사치 ③ 캐싱·카운터 테이블 | ④ 슬라이스(Slice) ⑤ 무한 스크롤·커서·검색 엔진
앞의 셋(커·근·캐)은 백엔드가 혼자 결정할 수 있다 — 코드와 인프라만 바뀐다
뒤의 둘(슬·무)은 화면이 바뀐다 — 기획·프론트 합의가 선행돼야 한다
이 구분선이 곧 "협상이 필요한 지점"이고, 7절의 프레임이 여기서 나온다

6-1. 커버링·부분 인덱스로 세기 — 정확도 유지, 배수만 절감

얻는 것

  • 정확한 값. 힙 페치 제거, 페이지 밀도 상승으로 같은 N에 I/O 수십 분의 일(3절).
  • 조건이 고정이면 부분 인덱스로 인덱스 자체를 더 작게.

내주는 것

  • 인덱스 하나만큼의 쓰기 비용·저장 공간 — PostgreSQL에서는 한 겹 더 무겁다. 인덱스에 넣은 컬럼(status)을 바꾸는 UPDATE는 HOT 업데이트에서 탈락해 그 테이블의 모든 인덱스에 새 엔트리를 꽂는다.
  • 효과가 VACUUM 상태에 좌우된다 — Heap Fetches가 크면 배수 절감도 못 누린다.
  • N에 비례하는 구조는 그대로 — 조건에 맞는 행이 수천만이면 여전히 초 단위다.

맞는 상황: 조건에 맞는 N이 수십만 이하이고 정확한 값이 꼭 필요한 화면. 다른 대안을 쓰더라도 첫 번째로 깔아 두는 기초 공사.

6-2. 근사치 — 정확도를 내주고 상수 시간을 산다

PostgreSQL에서 쓸 수 있는 근사치 재료는 셋이다. 각각 무엇을 언제 계산한 숫자인지가 달라서, 언제 크게 틀리는지도 다르다.

근사치 재료 3종 — 렐 · 플 · 상

(a) reltuples
마지막 VACUUM/ANALYZE 시점
조건이 없는 "이 테이블 전체 몇 건" 전용
(b) Plan Rows
EXPLAIN — 실행하지 않고 계획만
조건이 있는 화면에 쓸 수 있는 유일한 상수 시간 재료
(c) 상한 카운트
LIMIT 1001로 세기
상한 이하에서는 정확하고, 비용은 상한으로 고정

(a) pg_class.reltuples — 마지막 VACUUM/ANALYZE 시점의 추정 행 수

SQL 비용 = 시스템 카탈로그 한 행 읽기 = 사실상 0
SELECT reltuples::bigint AS approx_rows
  FROM pg_class
 WHERE oid = 'orders'::regclass;

-- reltuples 는 마지막 ANALYZE 또는 VACUUM 이 "표본으로" 계산해 적어 둔 값이다.
-- PostgreSQL 14+ 에서 -1 이면 "한 번도 분석된 적 없음" — 그대로 쓰면 안 된다.
-- 같은 성격의 숫자로 pg_stat_user_tables.n_live_tup 도 있다(통계 수집기가 갱신).
크게 틀리는 때 — 하필 "숫자를 확인하고 싶은 바로 그 순간" ⑴ 대량 적재 직후 ANALYZE 전 — 방금 넣은 1,000만 건이 아직 반영되지 않았다 ⑵ 대량 삭제 직후 VACUUM·ANALYZE 전 — 지운 행이 그대로 포함된 옛 숫자가 남아 있다 ⑶ 갱신이 잦아 autovacuum 주기 사이 편차가 큰 테이블. 즉 "쓰기가 몰린 직후"에 가장 많이 틀린다.

(b) 플래너 추정치 — 실행하지 않고 "몇 건쯤일지"만 묻는다

SQL 비용 ≈ 계획 수립 시간(수 ms) — 조건이 있어도 상수 시간
EXPLAIN (FORMAT JSON) SELECT 1 FROM orders WHERE seller_id = 42 AND status = 'PAID';
-- → [0]."Plan"."Plan Rows" 가 추정치.

-- 앱에서 쓰기 좋게 함수로 감싼 형태 (PostgreSQL wiki의 count_estimate 패턴)
CREATE FUNCTION count_estimate(q text) RETURNS bigint
LANGUAGE plpgsql AS $$
DECLARE plan json;
BEGIN
    EXECUTE 'EXPLAIN (FORMAT JSON) ' || q INTO plan;
    RETURN (plan->0->'Plan'->>'Plan Rows')::bigint;
END $$;
-- (q에 사용자 입력을 직접 이어 붙이면 SQL 인젝션 — 서버가 만든 문장만 넘긴다)
크게 틀리는 때 — Plan Rows는 표본 통계로 계산한 숫자다 Plan Rows는 ANALYZE가 수집한 표본 통계(MCV 목록 = 자주 나오는 값들, 히스토그램 = 값의 분포)로 계산된다. ⑴ 통계가 낡았을 때(위 (a)와 같은 이유) ⑵ 조건 컬럼끼리 상관관계가 있을 때 — 플래너는 기본적으로 조건들이 서로 독립이라고 가정하고 선택도를 곱하므로, "서울에 사는 사람"과 "지역번호 02"처럼 사실상 같은 조건 둘을 곱하면 자릿수 단위로 과소 추정한다(교정: CREATE STATISTICS … (dependencies)) ⑶ MCV 목록에 없는 희귀 값이나 LIKE '%키워드%'처럼 플래너가 기본 선택도로 때려 맞히는 조건.
요약 — 조건이 단순하고 통계가 신선하면 수 % 오차, 그 반대면 자릿수 오차

(c) 상한 카운트 — 상한까지만 정확히 세고, 넘으면 "1,000+"

good 근사치이면서도 상한 이하에서는 정확하다
SELECT count(*) FROM (
    SELECT 1 FROM orders
     WHERE seller_id = 42 AND status = 'PAID'
     LIMIT 1001          -- ← 여기서 멈춘다. 다시 "멈출 수 있는 쿼리"가 됐다
) t;
-- 1,000건 이하면 정확한 값, 1,001이면 "1,000건 이상". 비용은 최대 1,001건으로 고정.

얻는 것

  • (a)(b)는 N과 무관한 상수 시간.
  • (c)는 상한으로 고정된 시간에, 상한 이하에서는 정확한 값까지.

내주는 것

  • (a)(b)는 정확도 — "약 12,000건"이라는 표기와 허용 오차를 기획과 합의해야 쓸 수 있다.
  • (c)는 상한 너머의 정보 — "51페이지 이후"를 숫자로 못 보여준다.
맞는 상황 — 숫자가 "감(感)"의 용도인 화면 Google이 "약 1,230,000개"라고 쓰고, Elasticsearch조차 기본 설정으로 총 건수를 1만 건까지만 정확히 세고 그 이상은 "1만 건 이상"으로 돌려주는(track_total_hits) 이유가 이것이다 — 검색 엔진도 정확한 총 건수를 비싸게 본다. "좋아요 500+" 표기도 같은 장치의 UI 버전이다.
가산점 count(DISTINCT user_id)처럼 고유값 개수의 근사가 필요하면 hll 확장(HyperLogLog)이 있다 — 상수 크기의 스케치로 오차 몇 % 안에 세고, 일자별 스케치를 합쳐 기간 집계도 만든다. 행 수 count와는 다른 문제라는 걸 구분해 말하면 된다.

6-3. 카운트 캐싱 · 카운터 테이블 — 정합성을 내주고 읽기를 산다

(a) 결과 캐싱 — 조건 조합을 키로 짧게 캐시
String key = "orders:count:" + sellerId + ":" + status;  // 필터 조합이 곧 키
Long total = cache.get(key,
        () -> orderRepository.countBySellerIdAndStatus(sellerId, status),
        Duration.ofMinutes(5));

// 대가: TTL 동안 값이 낡는다. 그리고 필터 조합(상태 × 기간 × 검색어)이
//       곱셈으로 늘어 "인기 조합만" 캐시할 수 있다.
(b) 카운터 테이블 — 쓰기 시점에 미리 세어 둔다
UPDATE seller_order_stats SET paid_count = paid_count + 1
 WHERE seller_id = 42;

-- 조회는 PK 한 건 읽기 — 상수 시간.
-- 하지만 이 UPDATE가 주문 INSERT와 같은 트랜잭션에 있으면
-- 판매자 42의 모든 주문이 이 한 행의 락(xmax)을 두고 줄을 선다 — 핫 로우.

얻는 것

  • 읽기가 상수 시간, N과 무관.

내주는 것 — 정합성과 무효화

  • (b)는 비용이 읽기 경로에서 쓰기 경로로 옮겨 간 것이지 사라진 게 아니다.
  • 같은 트랜잭션에서 갱신하면 핫 로우 락 경합 + 죽은 튜플 폭증.
  • 비동기(이벤트)로 빼면 최종적 일관성과 유실·중복 처리가 따라온다.
  • 어느 쪽이든 보정 배치(주기적으로 실제 count(*)로 재계산)가 필요하다.
  • 필터 조합마다 카운터를 따로 둘 수 없다 — 카운터 테이블은 미리 정해진 축(판매자별 상태별 같은)에만 맞는다.

맞는 상황: 정확한 숫자가 업무 지표로 쓰여 근사치가 안 되지만, 몇 분의 지연은 허용되는 대시보드. 축이 고정된 집계.

이 대안은 count 맥락 밖에서 더 큰 주제다 "집계 값을 미리 계산해 들고 있는다"는 설계 일반의 대가는 04-normalization-vs-denormalization.md가, 한 행에 초당 수백 번 UPDATE가 몰릴 때의 핫 로우 완화(슬롯 분할, 배치 병합, INSERT … ON CONFLICT DO UPDATE)는 23-high-frequency-counter-hot-row.md가 전담한다. 여기서는 "읽기 비용을 쓰기 비용과 정합성으로 바꾼 거래"라는 것만 고정하고 넘어간다.

6-4. 다음 페이지 존재 여부만 확인 — Slice

얻는 것

  • count 쿼리 자체가 사라진다. 추가 비용은 행 1건(4-3절).
  • 코드 변경은 반환 타입 한 줄.

내주는 것 — "전체 N건 중 k페이지" UI

  • 총 페이지 수 · 마지막 페이지로 점프 · 페이지 번호 나열이 모두 불가능해진다.
  • 백엔드 혼자 결정할 수 없다 — 화면이 바뀌므로 기획·프론트 합의가 선행돼야 한다.

맞는 상황: 최신순으로 흘러가는 피드, "더 보기" 버튼, 모바일 목록. 대부분의 사용자향 목록이 사실 여기 속한다 — 사용자가 57페이지로 점프하는 일은 거의 없다.

6-5. 무한 스크롤 · 커서 · 검색 엔진 — UX와 아키텍처를 바꾼다

얻는 것

  • 무한 스크롤 + 커서 기반이면 count 비용과 offset 비용을 둘 다 없앤다. PostgreSQL은 키셋 조건 WHERE (created_at, id) < ($1, $2) 같은 행 비교를 B-tree 범위 탐색으로 그대로 실행하므로 커서 구현이 깔끔하다(13번 문서).
  • 복합 조건 검색·집계가 잦으면 검색 엔진이 역색인으로 필터·건수를 RDB보다 싸게 준다.

내주는 것

  • 무한 스크롤은 UX 자체의 변경(뒤로 가기 · 특정 위치 공유 · 총량 감각 상실)이라 기획 협상의 크기가 가장 크다.
  • 커서는 정렬 키가 유일해야 하고 API 스펙이 바뀐다(13번 문서).
  • 검색 엔진은 운영 비용 + RDB↔엔진 동기화(지연·유실)라는 새 시스템을 하나 들이는 일이고, 그마저도 총 건수는 기본이 근사치(6-2절).

맞는 상황: 트래픽이 크고 목록이 제품의 중심인 사용자향 서비스. 검색 조건이 다차원이라 RDB 인덱스로 감당이 안 되는 경우.

다섯 대안 한 장 요약 — 면접에서는 "얻는 것"과 "내주는 것"을 반드시 붙여서 말한다

8. 실무 — 분리 측정으로 특정하고, 코드로 고정하고, 사례로 회수한다

"count가 비싸다"를 알아도 6개월 뒤 새 목록 API를 만드는 동료(또는 나)는 습관대로 Page를 쓴다. 지식을 습관에 맡기지 않고 코드가 막고 계측이 드러내게 한다.

8-1. count 쿼리를 목록 응답에서 분리 측정한다

"목록 API가 800ms"라는 숫자는 진단이 아니다. 목록 쿼리와 count 쿼리가 각각 몇 ms인지 따로 봐야 offset 문제인지 count 문제인지 갈린다 — 13번 문서와 이 문서가 갈리는 지점이 바로 여기다.

1
SQL 단위 로깅 — p6spy 또는 datasource-proxy를 붙이면 요청 하나에서 나간 SQL이 한 줄씩 실행 시간과 함께 찍힌다. 4-1절의 로그처럼 LIMIT 붙은 목록 쿼리 12ms, count 쿼리 780ms — 이렇게 보이는 순간 진단이 끝난다.
2
APM의 SQL 스팬 — Pinpoint·Datadog 류는 요청 트레이스 안에 SQL 하나하나를 스팬으로 그려 준다. count 스팬이 목록 스팬보다 긴 화면이 곧 증거다.
3
서버 쪽 로그와 누적 통계 — log_min_duration_statement를 낮추면 count 쿼리만 잡힌다(목록 쿼리는 LIMIT 덕에 안 걸린다). "느린 목록 API"에서 로그에 count만 남는 것 자체가 신호다. auto_explain을 켜면 그 count의 실제 계획(Heap Fetches, Buffers)까지 남는다. 누적으로는 pg_stat_statements — 상수가 정규화되므로 목록과 count가 별개의 행(queryid)으로 잡히고, calls·mean_exec_time·shared_blks_read를 나란히 읽는다.
4
EXPLAIN은 count 쿼리에 따로 — 목록 쿼리 계획은 Limit 아래 actual rows=20이라 문제를 숨긴다. count 쿼리를 따로 EXPLAIN (ANALYZE, BUFFERS) 해서 Index Only Scan인지, Heap Fetches가 0에 가까운지, actual rows(= N)와 Buffers가 얼마인지를 본다.
good 코드 안에서 count만 따로 재기 — Micrometer Timer로 supplier를 감싼다
LongSupplier timedCount = () -> countTimer.record(() -> countQuery.fetchOne());
return PageableExecutionUtils.getPage(content, pageable, timedCount);

// 대시보드에 "목록 p95"와 "count p95"가 따로 그려진다.
// 그리고 supplier로 넘겼으므로 4-1절의 "건너뛰기"도 그대로 살아 있다.

8-2. Page vs Slice를 코드 규약으로 — 기본은 Slice, Page는 근거를 남겨야

규약은 문서에 쓰면 잊히고 리뷰 체크리스트에 두면 놓친다. 테스트가 실패하게 만든다.

good 표식 + ArchUnit — 근거 없는 Page는 빌드를 깬다
// 총 건수가 정말 필요한 메서드에만 붙이는 표식 — "왜 필요한지"를 값으로 강제
@Retention(RUNTIME) @Target(METHOD)
public @interface ExactTotalRequired {
    String reason();     // 예: "정산 화면 — 건수 불일치 시 감사 이슈"
}

// ArchUnit: 표식 없이 Page를 반환하는 리포지토리 메서드는 빌드가 깨진다
@ArchTest
static final ArchRule page_requires_justification =
    methods()
        .that().areDeclaredInClassesThat().resideInAPackage("..repository..")
        .and().areNotAnnotatedWith(ExactTotalRequired.class)
        .should().notHaveRawReturnType(Page.class)
        .because("Page는 매 요청 count 쿼리를 추가한다. 총 건수가 꼭 필요하면 "
               + "@ExactTotalRequired(reason=...)로 근거를 남기고, 아니면 Slice를 써라");
기본값을 민다
새 목록 API의 기본값이 Slice가 된다 — 아무 생각 없이 Page를 쓰는 경로가 막힌다.
협상을 앞당긴다
Page를 쓰려면 이유를 코드에 적어야 하므로 7절의 기획 협상이 먼저 일어난다.
6개월 뒤를 구한다
"이 화면 왜 Page지?"의 답이 코드 옆에 있다.
같은 결의 안전망 — 나가는 쿼리 수를 단정한다 목록 API 통합 테스트에서 datasource-proxy의 쿼리 카운터로 assertThat(count).isEqualTo(1). Slice로 바꾼 API가 SQL 1개만 실행하는지를 못 박아 두면, 누군가 Page로 되돌렸을 때 2가 되어 테스트가 깨진다.

8-3. count를 별도 경로로 — 목록의 응답 시간을 count가 볼모 잡지 못하게

Page를 유지해야 하는 화면이라도 목록과 count를 같은 응답에 묶지 않는 선택이 있다.

API 두 엔드포인트로 쪼갠다
GET /orders?seller=42&status=PAID&page=0    → 목록만, 즉시 응답 (Slice)
GET /orders/count?seller=42&status=PAID     → 총 건수, 별도 타임아웃 + 실패 시 "1,000+" 폴백

8-4. 사례 — "관리자 주문 목록이 새벽엔 빠르고 낮엔 느려요"

관리자 주문 목록 API(Page<Order>, 상태 필터, 20건씩)가 낮 시간대에만 p95 2초를 넘겼다. 처음 의심은 "낮에 트래픽이 많아서" — 틀리진 않지만 진단이 아니다.

"시간대에 따라 갈린다"는 현상 자체가 단서다

코드는 그대로인데 결과가 다르다면 변한 것은 코드가 아니라 DB의 상태다. 그리고 시간대에 따라 변하는 DB 상태는 세 가지뿐이다.

⑴ 캐시가 얼마나 따뜻한가 ⑵ 동시에 무엇이 돌고 있는가 ⑶ 통계·VACUUM이 언제 갱신됐는가

이 셋을 1~3절의 메커니즘에 대응시키는 것이 진단이다.

먼저 8-1절대로 분리 측정을 했다. p6spy 로그를 요청 단위로 보니 목록 쿼리는 낮에도 15ms, count 쿼리가 1.8초였다. 범인이 count로 특정된 다음, 위 세 가지를 순서대로 확인했다.

시간대에 따라 변한 것어느 메커니즘인가새벽낮
⑴ 캐시 적재 상태힙 페치가 shared hit이냐 shared read냐(3절) — 같은 계획도 디스크에서 읽으면 수십 배야간 배치가 훑어 둬 대부분 hit데이터가 커져 밀려나고 read 비중 상승
⑵ 동시 부하같은 I/O·CPU를 다른 쿼리들과 나눠 씀 + 리포트 쿼리가 backend_xmin을 붙들어 VACUUM 정지(2절)거의 없음운영자 다수 + 리포트 배치 동시 실행
⑶ VACUUM·통계죽은 튜플이 쌓이고 visibility map이 낡으면 count가 만나는 튜플·페이지가 늘고 Index Only Scan이 힙 페치로 퇴화(2·3절)autovacuum이 따라잡아 n_dead_tup 바닥주문 INSERT/UPDATE가 몰려 n_dead_tup 계속 상승

증거는 이렇게 모였다. ⑴ 인덱스가 (created_at)뿐이라 상태 필터 count가 힙 페치 N회(Bitmap Heap Scan + Filter)로 돌고 있었고(3절 Before 계획), 그래서 캐시 적재 상태에 그대로 노출돼 있었다. ⑵ pg_stat_user_tables에서 n_dead_tup이 낮 동안 계속 오르고 last_autovacuum이 새벽 시각이었으며, 낮의 리포트 쿼리가 pg_stat_activity.backend_xmin을 오래 붙들고 있었다 — VACUUM이 "돌긴 도는데 못 치우는" 상태다. 새벽엔 autovacuum이 따라잡아 ⑶이 사라지고 캐시도 따뜻해서 "빨라 보였던" 것이다.

1
배수 절감 — (status, created_at) 인덱스로 count를 Index Only Scan으로 바꾸고, Heap Fetches가 0 근처에 머물도록 이 테이블만 autovacuum_vacuum_scale_factor를 낮췄다. (대안 ①)
2
요구 확인 — 그래도 N에 비례하는 건 그대로라, 기획과 "이 화면에서 총 페이지 수를 실제로 쓰는가"를 확인했다. 운영자는 최신순으로 몇 페이지 넘기며 처리할 뿐 마지막 페이지로 점프하지 않았다. (7절 프레임)
3
차원 변경 — Slice로 전환하고 상단 건수는 상한 카운트 "1,000+"로 바꿔 count 비용을 없앴다. (대안 ④ + ②)
4
재발 방지 — 8-2절의 ArchUnit 규칙을 넣어 다음 관리자 화면이 같은 길을 밟지 않게 했다.

이 사례에서 면접관이 듣고 싶은 것은 세 가지다

① 분리 측정
"목록이 느리다"에서 멈추지 않고 count를 범인으로 특정했는가
② 배수 vs 차원
인덱스·VACUUM(배수 절감)과 Slice(차원 변경)를 구분해서 순서대로 적용했는가
③ 합의와 고정
화면 변경을 기획과 확인하고 결과를 규약으로 고정했는가

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

왜 비싼가, 한 문장?
목록은 LIMIT에서 멈추고 count는 못 멈춘다 — 비용이 페이지 크기가 아니라 조건에 맞는 전체 행 수 N에 비례. 게다가 페이지마다 재실행.
왜 메타데이터로 못 드나?
MVCC — 옛 버전이 힙에 남고 스냅샷마다 보이는 행이 달라 단일 정답이 없다. 죽은 튜플까지 만나서 "안 보임"을 판정해야 한다.
인덱스가 있으면 개수를 알지 않나?
모른다. 리프 엔트리는 (키, TID)뿐이고 xmin/xmax가 없다 → 엔트리 100만 ≠ 보이는 행 100만.
커버링 완성 조건 두 개?
① 조건 컬럼이 전부 인덱스에 → Index Only Scan ② visibility map 신선 → Heap Fetches: 0. ②가 안 되면 계획 이름만 좋다.
대안 5종?
커 · 근 · 캐 / 슬 · 무 — 커버링·근사치·캐싱(백엔드 혼자) / Slice·무한스크롤(화면이 바뀐다).
차원을 바꾸는 값은?
정확도 · 정합성 · UX 중 하나. 커버링은 배수만 줄인다 — "공짜로 빨라지는 대안"을 말하면 답이 무너진다.
근사치 재료 3종?
렐 · 플 · 상 — reltuples(조건 없음) / Plan Rows(조건 있음) / 상한 카운트(상한 이하는 정확).
개발 DB에서 안 보이는 이유?
Page는 첫 페이지가 덜 찼거나 마지막 페이지면 count를 건너뛴다 → 페이지가 꽉 차는 대용량에서만 count가 나간다.
"쿼리 한 번에" 함정?
count(*) OVER ()는 LIMIT 전에 전체 집합 위에서 계산 → 목록까지 N건을 읽는다. MySQL 판이 SQL_CALC_FOUND_ROWS(폐기).
첫 질문은?
"총 건수가 어디에 쓰이나요?" — 페이지 번호 / 검색 건수 / 업무 지표 / 정산에 따라 대안이 갈린다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

SELECT count(*) FROM orders처럼 조건도 없는데, PostgreSQL은 왜 그 숫자를 메타데이터로 즉답하지 못하나요? 필수힌트: 이유 + 인덱스도 못 하는 이유 + 반례 하나로 닫는다

MVCC라서 스냅샷마다 보이는 행이 다르다. 커밋 전 INSERT는 그 트랜잭션에게만 보이고, xmax가 찍힌 삭제 행은 먼저 시작한 트랜잭션에게 아직 보여야 한다. 단일 정답이 없으니 튜플마다 xmin/xmax를 스냅샷·pg_xact와 대조해 세는 수밖에 없고, 옛 버전이 힙에 남는 구조라 VACUUM이 안 치운 죽은 튜플까지 만나야 한다.

인덱스가 대신해 주지도 못한다 — 인덱스 엔트리에는 버전 정보가 없어서 엔트리 개수가 곧 보이는 행 수가 아니기 때문이다. 들고 있는 숫자는 pg_class.reltuples와 n_live_tup 같은 추정치뿐이다. 실제 count(*)는 플래너가 병렬 Seq Scan과 가장 작은 인덱스의 Index Only Scan(visibility map 비율 relallvisible을 보고) 중 싼 쪽을 골라 끝까지 훑는다.

반례로 닫으면 이해가 선명해진다 — MySQL의 MyISAM은 테이블 단위 락이라 유효한 행 수가 한 시점에 하나뿐이어서 메타데이터로 즉답한다

"읽기가 쓰기를 안 막는 동시성을 산 대가로 세는 비용을 낸다"는 트레이드오프 문장으로 마무리하면, "느리다"가 아니라 "무엇과 바꾼 것이다"가 된다.

count(*), count(1), count(id)는 성능이 다른가요? 함정힌트: 성능 이전에 "의미가 다른 함수"가 하나 섞여 있다

count(*)와 count(1)은 PostgreSQL에서 사실상 동일하게 처리된다 — "count(1)이 더 빠르다"는 속설은 근거가 없다. 오히려 count(*)는 컬럼을 하나도 안 읽으므로 어느 인덱스로든(가장 작은 것으로) Index Only Scan이 가능하다.

count(col)은 의미 자체가 다르다 — col이 NULL이 아닌 행만 센다. 그래서 col을 실제로 읽어야 하고, col이 플래너가 고른 인덱스에 없으면 힙 페치 경로로 떨어진다.

결론 — 행 수를 세려면 count(*), 특정 컬럼의 비-NULL 개수를 세려는 의도가 있을 때만 count(col)

"성능이 다르다/같다"로 답하지 말고 "의미가 다른 함수다"로 답하는 것이 정확하다. count(id)는 id가 PK(NOT NULL)라 결과는 같지만, 그렇다고 같은 함수인 것은 아니다.

목록 API가 느립니다. offset이 깊어서인지 count 때문인지 어떻게 구분하나요? 필수힌트: "800ms"는 진단이 아니다. 무엇을 나눠 봐야 하는가

둘은 원인도 처방도 다르므로 반드시 분리 측정한다. 요청 하나가 발생시킨 SQL을 한 줄씩 실행 시간과 함께 봐야 한다(p6spy·datasource-proxy·APM SQL 스팬).

count 문제의 모양

LIMIT 붙은 목록 쿼리는 빠른데(12ms) count 쿼리만 느리다(780ms). log_min_duration_statement를 낮췄을 때 목록은 안 걸리고 count만 로그에 남는 것도 신호. → 이 문서의 대안.

offset 문제의 모양

목록 쿼리 자체가 페이지가 깊어질수록 느려진다. 1페이지는 12ms인데 5,000페이지는 900ms. EXPLAIN의 Limit 노드 아래에 버려지는 행이 잔뜩 찍힌다. → 13번 문서(커서·지연 조인).

결정적 구분법 하나 — 1페이지를 요청해 본다. 1페이지에서도 느리면 offset이 아니라 count다(offset 0에는 건너뛸 행이 없으므로). 반대로 1페이지는 빠르고 뒷페이지만 느려지면 offset 쪽이다.

둘 다인 경우도 흔하다. 그때는 커서(키셋) 페이징 + Slice가 두 비용을 한 번에 없앤다 — 다만 API 스펙과 화면이 모두 바뀌므로 협상 단위가 가장 크다.

Index Only Scan이 찍혔는데도 count가 여전히 느립니다. 다음에 무엇을 보나요? 함정힌트: 계획 "이름"이 아니라 그 아래 두 줄을 읽는다

계획 이름은 절반의 정보일 뿐이다. 순서대로 본다.

1
Heap Fetches — 0이 아니면 visibility map이 낡은 것이고, 커버링이 무력화된 상태다. pg_stat_user_tables의 n_dead_tup·last_autovacuum을 보고, 이 테이블만 autovacuum_vacuum_scale_factor를 낮춘다. 긴 트랜잭션이 backend_xmin을 붙들고 있으면 VACUUM이 돌아도 못 치우므로 pg_stat_activity도 같이 본다.
2
actual rows(= N) 자체 — N이 수천만이면 커버링으로도 초 단위가 정상이다. 이건 튜닝의 실패가 아니라 대안을 바꿔야 한다는 신호다(6절).
3
Buffers의 shared read 비중 — 같은 계획도 디스크에서 읽으면 수십 배다. 시간대에 따라 결과가 갈린다면 대개 여기다(8-4절 ⑴).
4
인덱스 자체의 비대화 — 필요 없는 컬럼까지 넣어 엔트리가 크면 페이지당 밀도가 떨어져 읽을 페이지가 늘어난다. 조건이 고정이면 부분 인덱스가 더 작다.

그리고 마지막 확인 — 병렬 집계(Gather → Partial Aggregate)가 붙었는지. 붙어도 워커 수만큼 배수를 나눌 뿐이므로, 여기까지 왔는데 여전히 느리면 배수의 문제가 아니라 차원의 문제다.

Slice는 count 없이 hasNext를 어떻게 아나요? 대가는 무엇인가요? 필수힌트: 원리는 한 문장. 대가는 화면 쪽에 있다

한 건을 더 달라고 해서 그게 오면 다음이 있는 것. size=20이면 SQL은 LIMIT 21로 나가고, 21번째 행이 오면 hasNext = true, 응답에는 20건만 담는다. 추가 비용은 행 1건이다.

대가는 세 가지 — ① 총 건수·총 페이지 수를 모른다 ② 마지막 페이지로 점프가 불가능하다 ③ 응답 모델이 바뀌므로 프론트가 함께 바뀐다(totalPages → hasNext). ③ 때문에 백엔드 혼자 결정할 수 없다.

한 걸음 더 — Slice는 offset 비용은 그대로 남긴다. 여전히 OFFSET으로 페이지를 넘기므로 깊은 페이지는 느리다. count와 offset을 둘 다 없애려면 커서(키셋)여야 하고, Spring Data에서는 Window<T>/ScrollPosition이 그 방향이다.

왕복 한 번을 아끼려고 count(*) OVER ()로 합치면 낫지 않나요? 함정힌트: 윈도우 함수가 언제 계산되는지를 말한다

대개 더 느리다. 윈도우 함수는 LIMIT 전에, 조건에 맞는 전체 결과 집합 위에서 계산되기 때문이다. 그 결과 20건짜리 목록 쿼리가 N건을 전부 만나게 된다 — 목록 본체의 "20건에서 멈춤"이 사라지는 것이 대가의 실체다. EXPLAIN (ANALYZE)를 보면 Limit 아래 WindowAgg의 입력 스캔이 actual rows=3000000으로 찍힌다.

게다가 4-1절의 "count 건너뛰기" 최적화도 못 누린다 — 쿼리가 하나로 합쳐졌으니 건너뛸 count가 없다. 왕복 1회(수 ms)를 아끼려고 수백만 행의 I/O를 더 내는 거래다.

같은 유혹의 MySQL 판이 SQL_CALC_FOUND_ROWS + FOUND_ROWS() — 같은 이유로 느렸고 8.0에서 deprecated

정말 왕복이 문제라면 방향은 반대다 — 8-3절처럼 목록과 count를 오히려 더 갈라서 목록을 먼저 응답하고 건수는 나중에 채운다. "합치기"가 아니라 "떼어내기"가 답이다.

카운터 테이블로 가면 어떤 새 문제가 생기고, 어떻게 다루나요? 시니어 변별힌트: "캐싱하면 됩니다"로 끝내면 주니어 답. 새로 생기는 것이 셋이다

읽기 비용을 쓰기 경로로 "옮긴 것"이지 없앤 게 아니다. 세 가지가 새로 생긴다.

⑴ 핫 로우 — 같은 트랜잭션에서 paid_count + 1을 하면 그 판매자의 모든 주문이 한 행의 락을 두고 직렬화된다. PostgreSQL에서는 여기에 UPDATE마다 새 튜플 버전이 생겨 죽은 튜플이 쌓이고 VACUUM이 못 따라오는 문제가 겹친다. 완화는 카운터를 여러 슬롯으로 쪼개 합산하거나, 이벤트로 빼서 비동기 갱신하거나, 메모리에서 모았다가 INSERT … ON CONFLICT DO UPDATE SET cnt = t.cnt + EXCLUDED.cnt로 배치 병합.

⑵ 비동기로 빼면 정합성 — 최종적 일관성, 이벤트 유실·중복에 대한 멱등 처리, 그리고 실패 시 롤백되지 않는 카운터.

⑶ 축의 고정 — 카운터는 미리 정한 축(판매자별 상태별)에만 답하고, 새 필터 조합이 오면 답이 없다. 필터가 상태 × 기간 × 검색어로 곱해지는 화면에는 애초에 맞지 않는다.

어느 방식이든 보정 배치(주기적으로 실제 count(*)로 재계산해 덮어쓰기)를 안전망으로 깔고, "얼마나 어긋나도 되는가"를 기획과 숫자로 합의한다

이 셋을 묻지 않고 "캐싱하면 됩니다"로 끝내는 답이 주니어 답이다. 한 문장으로 압축하면 — "읽기 비용을 쓰기 비용과 정합성으로 바꾼 거래이고, 되돌릴 보정 장치가 필수다."

Slice로 바꾸자고 하니 기획이 "페이지 번호는 꼭 있어야 한다"고 합니다. 어떻게 하나요? 시니어 변별힌트: "안 됩니다"도 "네 하겠습니다"도 답이 아니다. 사이에 두 단계가 있다
1
가격표를 보여준다 — 이 화면의 count가 요청당 N건 스캔이고 p95의 몇 %를 차지하는지(8-1절의 분리 측정 결과). 숫자 없이 하는 요청은 취향 논쟁이 된다.
2
요구를 한 단계 쪼갠다 — "페이지 번호"가 필요한 건지, "마지막 페이지로 점프"가 필요한 건지, "총량의 감"이 필요한 건지. 대개 답은 앞의 둘이 아니다.
3
절충안을 같이 고른다 — 상한 카운트로 "1 2 3 … 10 다음"까지만 번호를 그리고 그 뒤는 "다음"으로 잇는다. 비용은 상한으로 고정되고 UI는 거의 그대로다.
4
정말 필요하다면 유지하되 격리한다 — 마지막 페이지 점프가 업무에 필요하다면(감사·정산) Page를 유지하되 커버링·부분 인덱스 + count 별도 엔드포인트 + 캐시로 목록 응답에서 떼어낸다(8-3절).

핵심은 "안 됩니다"도 "네 하겠습니다"도 아니고, 비용을 숫자로 보여주고 요구를 한 단계 쪼개 같이 고르는 것이다. 그리고 합의 결과를 @ExactTotalRequired(reason=…)처럼 코드에 남긴다 — 6개월 뒤 같은 논의를 반복하지 않기 위해서다.

근사치를 화면에 쓰기로 했는데, 사용자가 "숫자가 틀렸다"고 하면 어떻게 하나요? 시니어 변별힌트: 기술 답이 아니라 "표기와 합의"의 문제다. 그리고 언제 크게 틀리는지를 알고 있어야 한다

이 문제는 근사치를 쓰기로 결정하는 순간 예약된 것이므로, 미리 세 가지를 준비해 두는 것이 답이다.

① 표기로 약속한다 — "12,347건"이 아니라 "약 12,000건", 혹은 "1,000+". 사용자가 정확한 숫자라고 오해할 여지를 UI에서 먼저 없앤다. Google의 "약 1,230,000개"가 그 표기법이다.

② 허용 오차를 기획과 미리 합의한다 — "몇 % 오차까지 괜찮은가"를 숫자로 정해 둔다. 정해 두지 않으면 사고가 났을 때 "근사치를 쓴 것" 자체가 잘못이 된다.

③ 크게 틀리는 구간을 알고 방어한다 — reltuples는 대량 적재·삭제 직후 ANALYZE 전에, Plan Rows는 조건 컬럼끼리 상관관계가 있을 때(선택도를 곱해 자릿수로 과소 추정 — 교정은 CREATE STATISTICS … (dependencies)) 크게 틀린다. "쓰기가 몰린 직후에 가장 많이 틀린다"는 것이 위험한 이유는, 하필 그때가 사람들이 숫자를 확인하고 싶어 하는 순간이기 때문이다.

정확도가 정말 필요한 자리라면 근사치를 고집하지 말고 상한 카운트로 바꾼다 — 상한 이하에서는 정확하므로 "틀린 숫자"가 나오지 않는다

마지막 원칙 하나 — 정산·감사처럼 돈이 걸린 자리에는 근사치를 쓰지 않는다. 그 자리는 목록 API가 아니라 별도 집계 경로로 뺀다.

부분 인덱스(WHERE status = 'PAID')는 언제 못 쓰나요? 가산점힌트: 플래너가 그 인덱스를 쓸 수 있는 조건이 하나 있다

쿼리의 WHERE가 인덱스의 WHERE를 "포함"해야 플래너가 쓴다. 즉 조건이 고정된 화면에만 맞는다. status가 파라미터로 바뀌는 화면(PAID도 보고 CANCELED도 보는 관리자 필터)에서는 PAID 요청에만 쓰이고 나머지는 다른 계획으로 떨어지므로, 그때는 (seller_id, status, created_at) 복합 인덱스가 답이다.

부분 인덱스가 빛나는 자리는 ① 조건이 상수로 고정되어 있고 ② 그 조건이 전체의 소수 비율일 때다. "미처리 주문", "삭제되지 않은 행", "에러 상태" 같은 작고 뜨거운 부분집합이 전형이다 — 인덱스 크기가 그 비율만큼만이라 읽을 페이지도, 쓰기 부담도 함께 줄어든다.

주의 하나 — 부분 인덱스도 Index Only Scan의 완성 조건(Heap Fetches: 0)은 똑같이 적용된다. 인덱스가 작아졌다고 VACUUM 의존성이 사라지는 것은 아니다.

count 쿼리가 목록 응답 시간의 몇 %인지 어떻게 확인하나요? 필수힌트: 도구 이름만 대지 말고 "무엇이 보이면 진단이 끝나는지"까지

요청 하나가 발생시킨 SQL을 한 줄씩 실행 시간과 함께 보는 도구가 필요하다 — p6spy · datasource-proxy 로그, 또는 APM의 SQL 스팬. 거기서 LIMIT 붙은 목록 쿼리와 count 쿼리의 시간을 나란히 읽는다. 목록 12ms / count 780ms가 보이는 순간 진단이 끝난다.

지속적으로 보려면 count supplier를 Micrometer Timer로 감싸 "목록 p95"와 "count p95"를 따로 그린다. 서버 쪽에서는 pg_stat_statements에 두 쿼리가 별개 행으로 잡히니 mean_exec_time을 나란히 보고, log_min_duration_statement에 count만 남고 목록은 안 남는 것도 좋은 신호다.

그리고 EXPLAIN은 count 쿼리에 따로 건다 — 목록 쿼리의 EXPLAIN은 Limit 때문에 actual rows=20만 보여 문제를 숨긴다. count 쿼리를 EXPLAIN (ANALYZE, BUFFERS)로 따로 봐서 Index Only Scan 여부, Heap Fetches, actual rows(= N), Buffers를 확인한다.

MySQL로 물어보면 답이 달라지는 부분은 어디인가요? 경험 대조힌트: 네 지점 — 옛 버전의 위치 / 커버링 완성 조건 / 조건 없는 count / 도구

① 옛 버전의 위치 — InnoDB는 언두 로그(안 보이는 버전을 만나면 DB_ROLL_PTR로 언두 체인 추적), PostgreSQL은 힙 안의 죽은 튜플(VACUUM 전까지 count가 읽음). 그래서 "낮에 count가 느려진다"의 진단 지표가 다르다 — MySQL은 history list length, PostgreSQL은 n_dead_tup과 visibility map.

② 커버링 카운트의 완성 조건 — MySQL은 Extra: Using index가 뜨면 끝이지만, PostgreSQL은 Index Only Scan이어도 Heap Fetches가 붙을 수 있어 VACUUM 상태까지 봐야 한다. 이 차이가 실무에서 가장 자주 사람을 넘어뜨린다.

③ 조건 없는 count와 추정치 — MySQL 8.0은 가장 작은 세컨더리 인덱스로 고정 선택, PostgreSQL은 relallvisible을 보고 병렬 Seq Scan과 Index Only Scan 중 비용으로 고른다. 추정치는 information_schema.TABLES.TABLE_ROWS vs pg_class.reltuples/n_live_tup.

④ "한 번에" 함정과 PostgreSQL만의 도구 — MySQL의 SQL_CALC_FOUND_ROWS(폐기)가 PostgreSQL에서는 count(*) OVER ()로 나타난다. 반대로 count 대상을 인덱스 정의에 박아 두는 부분 인덱스는 PostgreSQL에만 있다. 그리고 MyISAM처럼 메타데이터 카운트를 주는 스토리지 엔진은 PostgreSQL에 없다.

한 줄 요약
목록은 LIMIT에서 멈추지만 count는 조건에 맞는 행을 전부 만나야 하고(PostgreSQL은 MVCC 때문에 옛 버전이 힙에 남고 스냅샷마다 보이는 행이 달라 행 수를 메타데이터로 들 수 없으며, 인덱스 엔트리에는 버전 정보가 없어 어떤 인덱스도 개수를 미리 알지 못한다 — reltuples는 추정치), 조건 컬럼이 인덱스에 없으면 그 N건마다 힙 페치가 붙고, 있어도 visibility map이 신선해야(Heap Fetches: 0) Index Only Scan이 힙을 건너뛴다 — 비용이 페이지 크기가 아니라 N에 비례하는 요구다. 커버링·부분 인덱스는 배수만 줄이고, 차원을 바꾸려면 근사치(정확도) · 카운트 캐싱(정합성) · Slice/무한 스크롤(UX) 중 하나를 내줘야 한다. Page가 count를 자동으로 붙인다는 사실을 SQL 로그로 확인하고, 기본은 Slice·Page는 근거 필수라는 규약을 ArchUnit과 분리 측정으로 고정하며, 그 가격표를 기획에 보여주는 것까지가 백엔드의 일이다.
