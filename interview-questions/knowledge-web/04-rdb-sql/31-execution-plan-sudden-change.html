실행 계획의 갑작스러운 변경 — 옵티마이저는 "통계를 입력받는 함수"다, 입력이 바뀌면 출력이 바뀐다

원본: interview-questions/knowledge/04-rdb-sql/31-execution-plan-sudden-change.md

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "잘 돌던 쿼리의 실행 계획이 어느 날 갑자기 바뀌어 느려졌습니다. 가능한 원인과 대응은?"
옵티마이저는 쿼리를 "계산"하는 계산기가 아니라, 통계·샘플·파라미터 값·비용 상수를 입력으로 받아 후보 계획들의 비용을 비교하는 함수다. 코드도 쿼리도 안 바꿨는데 계획이 바뀌었다면 셋 중 하나다 — ① 입력이 바뀜(통계 자동 재계산, 샘플링 오차, 데이터 분포 변화, 들어오는 파라미터 값), ② 후보가 바뀜(인덱스 추가·삭제), ③ 함수가 바뀜(DB 업그레이드, 파라미터 변경). 대응은 사다리다 — 진단(느려진 시각 특정 → 그 시각 전후 digest의 "건당 examined 행" 비교 → EXPLAIN 현재 vs 베이스라인 diff → 통계 last_update 확인 → 데이터 분포 확인) → 즉시 완화(ANALYZE TABLE, 기한 붙인 힌트, INVISIBLE) → 근본 대응(복합 인덱스로 후보를 하나로, 히스토그램, 샘플 페이지 상향) → 고정(EXPLAIN 베이스라인 잡, digest 스냅샷 알람, 배치 마지막 단계 ANALYZE). 힌트는 "옵티마이저가 오늘 맞았다"를 영구 고정하는 것이라, 데이터가 바뀌어도 계획이 못 따라오고 코드에 물리 정보가 결합되는 대가를 낸다 — 이슈와 만료일을 붙인 지혈대로만 쓴다.
출제 의도 — 두 층을 잰다
아래층 = 모델. "같은 SQL을 넣으면 같은 계획이 나온다"는 계산기 모델을 버리고, "통계라는 입력으로 비용을 계산하는 함수라서 입력이 바뀌면 출력이 바뀐다"는 모델을 갖고 있는가. 이 모델이 있어야 원인 후보가 목록으로 인출되고 진단 순서가 논리적으로 나온다.
위층 = 판단. 계획을 고정하는 힌트가 "문제 해결"이 아니라 "옵티마이저의 판단 기능을 끄는 것"임을 알고, 그 대가와 기한을 붙여 쓰는가. rationale 표현 그대로 — "힌트로 고정하는 것의 트레이드오프까지 가면 상급이다."

이 페이지가 겨냥하는 네 가지 약점: ① 인과를 메커니즘 사슬로 서술하기(§1·§2) · ② 대응책의 대가를 한 호흡에 양면으로(§4) · ③ 안전망을 기억이 아니라 코드·잡으로 고정(§5) · ④ "원인 8종"과 "대응 사다리"를 목록으로 인출(§3·§4). 같은 장의 배포 없이 DB CPU만 올랐다가 "변경 없음"을 의심하며 원인 전체를 넓게 훑는다면, 이 문서는 그중 가장 흔한 한 갈래인 "실행 계획이 바뀌었다"를 깊게 판다.

  • 1모델 — 계획 = f(후보, 입력)
  • 2사슬 — 새벽 배치가 계획을 뒤집는 7단
  • 3원인 8종 — 세 칸에서 꺼내기
  • 4대응 사다리 — 진단 → 완화 → 근본
  • 4-2힌트는 지혈대 — 대가 4종
  • 5안전망 5층 — 기억 밖으로
  • 6꼬리질문 셀프 테스트
  • ★한 줄 요약

1. 모델 — 옵티마이저는 함수다: 계획 = f(후보 집합, 입력)

먼저 머릿속 모델을 교체한다. 계산기는 2 + 3을 넣으면 언제나 5다. 옵티마이저는 그렇지 않다 — 같은 SQL이 들어와도 그 순간의 입력으로 후보들의 비용을 다시 계산하고, 가장 싸게 계산된 것을 고른다.

색이 곧 "바뀐 칸"이다 — 파랑 = 입력, 초록 = 후보 집합, 주황 = 함수(계수 포함). §3의 원인 8종은 전부 이 세 색 중 하나에 들어간다.
암기 카드 — "바뀌었다면 셋 중 하나": 입 · 후 · 함
코드도 쿼리도 안 바꿨는데 계획이 바뀌었다 → 입력이 바뀌었거나, 후보가 바뀌었거나, 함수가 바뀌었다.

원인 목록을 통째로 외우지 말고, 이 세 칸에서 꺼낸다. 면접장에서 하나가 생각 안 나도 칸이 남아 있으면 복구된다.

입력이 바뀜
  • ①통계 자동 재계산
  • ②샘플링 오차
  • ③데이터 분포 변화
  • ④들어오는 파라미터 값
  • ⑧버퍼 풀 상태 가산점
후보가 바뀜
  • ⑤인덱스 추가 · 삭제

남이 만든 유사 인덱스가 "경쟁 후보"로 들어오거나, 특정 값에서만 쓰이던 인덱스가 사라진다.

함수가 바뀜
  • ⑥DB 업그레이드 · 패치
  • ⑦파라미터 변경 (계수)

같은 통계·같은 SQL을 넣어도 계산식이 달라져 다른 답이 나온다.

내비게이션 비유 — "내비가 미쳤다"가 아니라 "무슨 정보를 보고 그렇게 판단했나"

같은 집에서 같은 회사로 가는데 어느 날 내비가 다른 길을 안내한다. 지도(쿼리)는 그대로다. 바뀐 것은 교통정보(통계)다. 교통정보가 갱신되면 안내가 바뀌는 건 정상이고 대개 더 나은 길이다. 문제는 교통정보가 낡았거나(통계가 현실과 어긋남), 표본이 적어 엉뚱하게 잡혔거나(샘플링 오차), 평균 차량 기준이라 내 차에는 안 맞을 때(파라미터 값)다. 진단의 시작은 언제나 "내비가 무슨 정보를 보고 그렇게 판단했나"를 묻는 것이다.

1-1. 입력 4종 — 각각 무엇이고, 계획의 어디에 쓰이나

"입력이 바뀌었다"를 말하려면 입력이 계획의 어느 칸에 들어가는지 알아야 한다. 특히 ①과 ②는 다른 입력이다 — 이 구분이 §2 사고의 열쇠다.

입력 ①영속 통계 — 디스크에 저장된 "추정치"

mysql.innodb_table_stats(행 수 n_rows, 마지막 갱신 last_update)와 mysql.innodb_index_stats(인덱스 접두사별 서로 다른 값 수 n_diff_pfx01…). SHOW INDEX의 Cardinality가 바로 이 값이다.

옵티마이저는 여기서 키 하나당 평균 행 수를 만든다: rows_per_key = n_rows / n_diff.

  • 풀스캔 비용 — n_rows와 클러스터드 인덱스 페이지 수
  • 조인의 ref 예상 행 수 — 값이 행마다 달라 실측 불가, rows_per_key를 그대로 씀. 조인 순서 결정의 핵심
  • ORDER BY … LIMIT 휴리스틱 — "정렬 인덱스를 훑으며 WHERE로 거르면 몇 행 만에 LIMIT이 차나"에 WHERE 키의 rows_per_key. §2의 사고가 정확히 여기서 난다
  • 긴 IN 리스트 — 항목이 eq_range_index_dive_limit(기본 200)을 넘으면 dive 대신 통계
입력 ②최적화 시점 샘플 (index dive) — "지금" 세어본 값

WHERE user_id = 42처럼 상수 조건이 인덱스 컬럼에 걸리면 통계를 믿지 않고 그 인덱스의 해당 범위에 실제로 들어가 대략 몇 행인지 세어본다. 그래서 단일 테이블의 단순 등호·범위 조건은 통계가 낡아도 비교적 정확하다.

대신 dive는 지금 데이터·지금 값에 즉시 반응한다. status = 'FAILED'가 어제 1%에서 오늘 40%가 되면 통계 갱신과 무관하게 계획이 바뀐다 — 원인 ③④가 "통계 갱신 시각과 안 맞는데도 계획이 바뀌는" 이유.

입력 ③쿼리에 들어온 값 — 매 실행 다시 최적화

MySQL은 한 번 세운 계획을 캐시해 재사용하지 않고, 실행할 때마다 실제 파라미터 값으로 다시 최적화한다. 따라서 같은 SQL이 값에 따라 다른 계획을 갖는 것은 정상이다.

"갑자기 느려졌다"가 실은 "느린 값이 들어오기 시작했다"인 경우 — 주문 8건 사용자와 40만 건 대형 가맹점은 같은 SQL, 다른 최적 계획.

입력 ④비용 상수 · 스위치 — 함수의 계수

페이지를 디스크/메모리에서 읽는 비용, 행 하나 평가 비용은 mysql.server_cost·mysql.engine_cost에, 어떤 최적화 기법을 쓸지는 optimizer_switch에. DB 업그레이드는 이 계수와 스위치 기본값을 바꾸고 새 기법을 후보에 추가한다 — 입력이 그대로여도 출력이 달라지는 이유.

가산점 MySQL 8의 비용 모델은 "이 인덱스가 버퍼 풀에 얼마나 올라와 있나" 추정치도 참고한다. 재시작·failover 직후(버퍼 풀 비어 있음)와 예열 뒤의 비용 계산이 달라 "재시작하고 나서 계획이 달라졌다"가 나온다.

-- 입력 ①이 실제로 저장된 곳 — 진단 4단계(§4-1)에서 그대로 쓴다
SELECT table_name, n_rows, clustered_index_size, sum_of_other_index_sizes, last_update
FROM mysql.innodb_table_stats
WHERE database_name = 'shop' AND table_name = 'orders';

SELECT index_name, stat_name, stat_value, sample_size, last_update
FROM mysql.innodb_index_stats
WHERE database_name = 'shop' AND table_name = 'orders' AND index_name = 'idx_user';
-- n_diff_pfx01 = user_id의 서로 다른 값 수(추정)
-- n_diff_pfx02 = (user_id, id)의 서로 다른 값 수 — 세컨더리 인덱스는 PK를 품으므로 접두사가 하나 더 있다
첫 번째 결론 — 첫 답변의 첫 문장
"실행 계획이 바뀌었다"는 결과이지 원인이 아니다.

진단은 "어느 입력이, 언제, 왜 바뀌었나"를 찾는 일이고, 대응은 세 갈래의 선택이다 — 그 입력을 바로잡을 것인가(통계·히스토그램), 후보를 줄여 흔들릴 여지를 없앨 것인가(인덱스 설계), 함수를 우회할 것인가(힌트). 이 문장을 첫머리에 말하면 면접관이 확인하려는 "정적인 계산기가 아니라 상태에 따라 판단이 바뀌는 시스템"이라는 이해가 바로 드러난다.

2. 사슬 — 새벽 배치 한 번이 계획을 뒤집는 과정, 숫자로

가장 큰 약점은 "통계가 바뀌어서 느려졌다"에서 멈추는 것이다. 그 사이의 일곱 칸을 채운다. 숫자는 메커니즘을 보이기 위한 예시값이다.

상황

orders 1,000만 건. 인덱스는 PRIMARY(id)와 idx_user(user_id). 사용자 100만 명, 1인당 평균 주문 10건. 주문 목록 API의 쿼리:

SELECT * FROM orders WHERE user_id = ? ORDER BY id DESC LIMIT 20;

옵티마이저 앞에 놓인 후보는 둘이다.

계획 Aidx_user → filesort

idx_user로 이 사용자의 행을 전부 찾는다(ref) → id로 정렬 → 20건.

비용 ∝ 이 사용자의 행 수 (랜덤 룩업 N번 + N건 정렬)

계획 BPRIMARY 역순 스캔 → LIMIT

PRIMARY를 뒤에서부터 훑으며(id DESC 순서 그대로) user_id로 거른다 → 20건 모이면 중단.

비용 ∝ 20 × (전체 행 수 / 이 사용자의 "예상" 행 수) — 여기서 "예상 행 수"의 입력이 idx_user 통계의 rows_per_key다(§1-1).

평소(베이스라인). n_diff(user_id) 추정 100만 → rows_per_key = 1,000만 / 100만 = 10. 계획 A는 랜덤 룩업 10번, 계획 B는 20 × (1,000만 / 10) = 2,000만 행 = 테이블 전체. A가 압도적으로 싸다. p95 20ms.

7단 사슬. 1·2는 정상 동작, 3·4에서 입력이 망가지고, 5·6에서 함수가 (정확하게) 틀린 답을 내고, 7에서 사용자가 맞는다.
평소 — 베이스라인 EXPLAIN
id  select_type  table  type  key       key_len  rows  filtered  Extra
1   SIMPLE       o      ref   idx_user  8        10    100.00    Using filesort
사고 당일 — 전환된 EXPLAIN
id  select_type  table  type   key      key_len  rows   filtered  Extra
1   SIMPLE       o      index  PRIMARY  8        16000  0.01      Using where; Backward index scan

diff는 세 칸이다 — key(idx_user → PRIMARY), type(ref → index), rows(10 → 16000). 베이스라인 잡(§5-1)이 엄격 비교하는 칸이 정확히 이 셋이다.

2-1. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

❌ 칸이 비어 있는 답
"통계가 갱신돼서 옵티마이저가 다른 인덱스를
 타게 됐고, 그래서 느려졌습니다."

→ 왜 갱신됐는지, 갱신되면 무엇이 바뀌는지,
  그게 왜 다른 인덱스로 이어지는지,
  왜 그게 느린지가 전부 비어 있다.
✅ 일곱 칸을 채운 답
"대량 적재로 변경 행 비율이 임계(10%)를 넘어
  백그라운드 통계 재계산이 돌았고
→ 20페이지 샘플이 편중돼 user_id 카디널리티
  추정이 100만에서 수백으로 떨어졌고
→ 옵티마이저는 '키당 행 수'가 1만 배로 늘었다고
  믿게 됐고
→ 그러면 'PK를 역순으로 조금만 훑어도 LIMIT이
  채워진다'는 계획의 비용이 'idx_user 룩업 + 정렬'
  보다 싸게 계산돼 계획이 전환됐고
→ 실제로는 주문이 몇 건뿐인 사용자에게 PK 전체
  스캔이 돼 examined/sent 비율이 100만 배로
  뛰었습니다."

2-2. 이 사례가 가르치는 세 가지

첫째재계산은 정상, 문제는 샘플링 오차

문제는 "재계산"이 아니라 "재계산할 때마다 샘플이 다른 답을 낸다"는 것이다. 그래서 대응은 "자동 재계산을 끄자"가 아니라 "샘플을 늘리거나 후보를 줄이자"로 간다(§4-3).

둘째옵티마이저는 "평균 사용자"를 가정한다

rows_per_key는 평균이다. 평균 15,000건은 대형 가맹점에게는 맞고 일반 사용자에게는 틀리다. 편중(스큐)된 컬럼에서는 "옵티마이저가 옳은 값"과 "틀린 값"이 동시에 존재한다.

셋째후보가 둘이었기 때문에 뒤집혔다

(user_id, id) 복합 인덱스가 있었다면 "이 사용자의 행을 id 순서로 바로 읽는" 후보 하나가 WHERE·ORDER BY를 동시에 만족해 정렬도 없고, 계획 B가 이길 수 있는 통계값이 존재하지 않는다. 흔들릴 여지를 없애는 것이 근본 대응이다.

EXPLAIN은 "고른 것"만 보여준다. "무엇과 비교해서 골랐는지"는 옵티마이저 트레이스에 있다.

4. 대응 사다리 — 진단 → 즉시 완화 → 근본 대응

왜 순서가 있는가

진단 없이 완화하면 무엇을 되돌려야 할지 모르고, 완화 없이 근본 대응만 하면 장애 시간이 길어지고, 근본 대응 없이 완화만 하면 다음 재계산에 또 뒤집힌다.

4-1. 진단 5단계 — 순서 고정

암기 카드 — 진단 5단계: 시 · 건 · 디 · 통 · 분 (시각 → 건당 examined → diff → 통계 → 분포)
  1. 느려진 시각을 특정한다APM에서 p95가 꺾인 분 단위 시각, slow log에 그 쿼리가 처음 등장한 시각, digest의 FIRST_SEEN·LAST_SEEN. 그 위에 배포·배치·유지보수 창·파라미터 변경·인덱스 DDL 타임라인을 겹친다."갑자기"는 대개 이 겹치기에서 이미 반쯤 풀린다.
  2. 그 시각 전후 digest의 건당 examined를 비교해 "계획이 바뀐 게 맞는지"부터 확정한다계획 변경의 지문 = 건당 examined 행은 뛰는데 건당 sent 행은 그대로. 같은 결과를 내려고 훨씬 많이 읽고 있다는 뜻.자릿수 단위로 뛰었으면 계획 변경(또는 ③ 분포 급변), 안 뛰었으면 §3-8 — 이 문서 밖.
  3. EXPLAIN 현재 vs 베이스라인을 diff한다key·type·used_key_parts·rows. 베이스라인이 없으면 PR에 붙였던 EXPLAIN이나 스테이징(통계가 다르므로 참고용). 넣는 값은 slow log에 찍힌 실제 느린 값 — digest의 QUERY_SAMPLE_TEXT가 샘플을 준다.두 계획의 비용을 나란히 보려면 §2-3 트레이스.
  4. 통계 갱신 시각과 값을 확인한다innodb_table_stats.last_update가 1단계 시각 직전이면 ①. 이어서 innodb_index_stats.n_diff를 레플리카의 실제 COUNT(DISTINCT)와 대조 → 자릿수가 다르면 ②.
  5. 데이터 분포와 "후보·함수" 변경을 확인한다값별 건수(GROUP BY status), 파라미터 값별 건수(그 가맹점의 주문 수), 히스토그램 유무(COLUMN_STATISTICS), 인덱스 목록 diff(⑤), 버전(⑥), 파라미터 diff(⑦).5단계까지 오면 원인은 8종 중 하나로 특정된다.
-- 2단계: digest에서 "건당 examined / 건당 sent"를 본다
SELECT LEFT(DIGEST_TEXT, 80)                          AS q,
       COUNT_STAR                                     AS calls,
       ROUND(SUM_TIMER_WAIT / 1e12 / COUNT_STAR, 4)   AS avg_sec,       -- TIMER는 피코초
       ROUND(SUM_ROWS_EXAMINED / COUNT_STAR)          AS examined_per_call,   -- 이게 뛰고
       ROUND(SUM_ROWS_SENT / COUNT_STAR)              AS sent_per_call,       -- 이게 그대로면 계획 변경
       SUM_NO_GOOD_INDEX_USED, SUM_SORT_ROWS, SUM_CREATED_TMP_DISK_TABLES,
       FIRST_SEEN, LAST_SEEN
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'shop' AND DIGEST_TEXT LIKE '%FROM `orders`%'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
-- 서버 기동 이후 누적이라 "어제 대비"는 스냅샷(§5-2)이 있어야 한다. 없으면 slow log의 Rows_examined/Rows_sent를 시각별로.

지혈대 비유. 응급 처치에서 지혈대는 팔다리를 살리려고 감는 게 아니라 사람을 살리려고 감는다 — 그래서 감은 시각을 반드시 적어 둔다. 힌트도 같다: 감을 수 있지만, 이슈 번호·이유·만료일을 적고, 그 만료를 사람이 아니라 §5-5의 린트가 기억하게 한다. "장애 중이라면 힌트 먼저, 정리는 나중"도 맞는 답이다 — 단 "나중"을 기계가 기억하게 하는 장치까지 말해야 상급이다.

카드 3INVISIBLE— 원인 ⑤(새 인덱스가 경쟁)
ALTER TABLE orders ALTER INDEX idx_created_status INVISIBLE;
-- 메타데이터만 변경, 즉시, 가역. 정말 그 인덱스 탓인지 내 세션에서만 다시 켜서 확인:
SET SESSION optimizer_switch = 'use_invisible_indexes=on';
얻는 것DROP 없이 후보에서만 빼므로 잘못 판단했으면 한 줄로 되돌린다.
내는 것인덱스 유지(쓰기·저장) 비용은 그대로 — 결정이 나면 DROP까지 간다.

거꾸로 "인덱스를 지우기 전 일주일은 INVISIBLE로 둔다"는 안전 규칙으로도 쓴다(⑤의 반대편 예방).

카드 4원복— 원인 ⑥⑦

파라미터 그룹을 이전 값으로 되돌리거나, 업그레이드로 바뀐 optimizer_switch 항목을 이전 기본값으로 명시한다.

얻는 것원인이 확실하면 가장 정확한 완화.
내는 것업그레이드 롤백은 대개 불가능하므로 스위치 원복은 "전역"이 되고, 그 스위치 덕을 보던 다른 쿼리가 느려진다.

→ 전역 대신 카드 2의 SET_VAR로 문장 단위로 좁히는 게 먼저다.

4-3. 근본 대응 — 흔들릴 여지를 없앤다

1순위 — 복합 인덱스로 후보를 하나로 만든다
계획 B가 이길 수 있는 통계값이 존재하지 않게 만들면, 통계가 어떻게 흔들려도 계획이 안 흔들린다.

§2의 쿼리에 (user_id, id)를 두면 "이 사용자의 행을 id 순서로 읽는다"는 후보 하나가 WHERE·ORDER BY·LIMIT을 전부 만족하고 정렬이 사라진다. 순서 원칙(등호 → 범위 → 정렬 → 커버링)은 복합 인덱스 컬럼 순서, 읽기를 인덱스 안에서 끝내는 확장은 커버링 인덱스.

얻는 것통계와 무관하게 안정. 정렬 제거.
내는 것인덱스 하나만큼의 쓰기·메모리, 대형 테이블 DDL 절차(무중단 DDL), 기존 idx_user가 접두사 중복이 되므로 INVISIBLE → DROP 정리.
2히스토그램 — 원인 ③이 비인덱스 컬럼·조인 순서에 걸릴 때
ANALYZE TABLE orders
  UPDATE HISTOGRAM ON status WITH 16 BUCKETS;

기본 통계는 "서로 다른 값이 몇 개"만 알고 "어느 값이 몇 %"는 모른다. 히스토그램이 그 분포를 알려줘 filtered와 조인 순서를 바로잡는다.

내는 것: 자동 갱신되지 않는다(기본은 수동) — 갱신을 잡으로 고정해야 한다. 인덱스 컬럼의 상수 조건은 dive가 더 정확해 쓰이지 않는다 — 만능이 아니다.

3샘플 페이지 상향 — 원인 ②가 반복될 때
ALTER TABLE orders STATS_SAMPLE_PAGES = 256;
ANALYZE TABLE orders;   -- 새 설정으로 재수집

추정의 흔들림 폭이 준다. 내는 것: 재계산이 그만큼 페이지를 더 읽는다.

대안 STATS_AUTO_RECALC = 0 + 예약 ANALYZE — 얻는 것은 "재계산 시각을 내가 정한다", 내는 것은 "그 사이 낡아도 아무도 안 고쳐준다". 매일 TRUNCATE 후 재적재하는 테이블에 어울리고 일반 테이블엔 과하다.

LAYER 1EXPLAIN 베이스라인 잡운영 레플리카 · 운영 통계 · 매일 diff

실행 계획 읽기의 "EXPLAIN 단정 테스트"는 CI에서 시드 데이터로 돌아 코드 변경이 만드는 회귀를 잡는다. 이 문서의 원인은 데이터·통계가 만드는 회귀라 그것으로는 안 잡힌다. 그래서 한 층이 더 필요하다 — 운영 레플리카에서, 운영 통계로, 매일 뜨는 베이스라인.

#!/usr/bin/env bash
# explain-baseline.sh — 핵심 쿼리의 실행 계획을 운영 레플리카에서 뜨고 git에 커밋된 베이스라인과 비교
set -euo pipefail
BASE=db/explain-baseline                       # 커밋된 JSON (쿼리당 1개)
WORK=$(mktemp -d)
changed=0
for q in db/critical-queries/*.sql; do         # 파일 1개 = 쿼리 1개. 파라미터는 "대표값"과 "최악값" 두 벌
  name=$(basename "$q" .sql)
  mysql -h "$REPLICA_HOST" -N -e "EXPLAIN FORMAT=JSON $(cat "$q")" \
    | jq -S '[.. | objects | select(has("table")) | .table
              | {table: .table_name, type: .access_type, key: .key, parts: .used_key_parts}]' \
    > "$WORK/$name.json"
  if ! diff -q "$BASE/$name.json" "$WORK/$name.json" > /dev/null; then
    echo "PLAN CHANGED: $name"; diff "$BASE/$name.json" "$WORK/$name.json" || true
    changed=1
  fi
done
exit $changed        # 0이 아니면 알람 채널로. 승인된 변경이면 베이스라인 JSON을 PR로 갱신

key·type·used_key_parts는 엄격 비교, rows_examined_per_scan과 query_cost는 따로 기록해 "3배 이상 변동"을 경고로(통계 재계산만으로도 조금씩 움직이므로 엄격 비교하면 소음). 이 잡의 일은 "느려지기 전에" 계획 전환을 알리는 것 — 새벽 2시 재계산 뒤 6시 잡이 diff를 내면 출근 전에 안다. MySQL에는 Oracle SQL Plan Baseline·SQL Server Query Store 같은 계획 고정 기능이 없으므로, "우리가 기록한 베이스라인"이 그 역할을 대신한다.

LAYER 2digest 스냅샷 + 비율 알람"건당 examined"의 급변을 기계가 본다
CREATE TABLE ops.digest_snapshot (
  snapshot_at        DATETIME     NOT NULL,
  digest             VARCHAR(64)  NOT NULL,
  digest_text        LONGTEXT,
  count_star         BIGINT, sum_timer_wait BIGINT,
  sum_rows_examined  BIGINT, sum_rows_sent  BIGINT,
  PRIMARY KEY (snapshot_at, digest)
);

-- 매시 (이벤트 스케줄러 또는 외부 크론)
INSERT INTO ops.digest_snapshot
SELECT NOW(), DIGEST, DIGEST_TEXT, COUNT_STAR, SUM_TIMER_WAIT, SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST IS NOT NULL;

-- 최근 1시간 구간의 "건당 examined"가 7일 중앙값의 5배를 넘는 digest → 알람
SELECT cur.digest, LEFT(cur.digest_text, 80) AS q,
       (cur.sum_rows_examined - prev.sum_rows_examined)
         / NULLIF(cur.count_star - prev.count_star, 0)      AS examined_per_call_now
FROM ops.digest_snapshot cur
JOIN ops.digest_snapshot prev
  ON prev.digest = cur.digest AND prev.snapshot_at = cur.snapshot_at - INTERVAL 1 HOUR
WHERE cur.snapshot_at = (SELECT MAX(snapshot_at) FROM ops.digest_snapshot)
  AND cur.count_star > prev.count_star;
-- (7일 중앙값과의 비교는 같은 테이블에서 윈도우 집계로 붙인다)

mysqld_exporter의 perf_schema 수집기 + Prometheus로 같은 것을 만들면 알람 규칙이 YAML 파일이 된다. 어느 쪽이든 "이 digest의 건당 examined 행이 갑자기 100배"라는 알람은 계획 변경의 가장 이른 신호이고, 사람이 slow log를 열어보기 전에 온다.

LAYER 3신규 digest 등장 알람slow log에 "어제 없던 것"

§2의 사고는 "배치가 끝나고 백그라운드가 알아서" 재계산한 데서 났다. 대량 적재 배치가 스스로 통계를 갱신하고 끝나면 재계산 시각이 배치 시각으로 고정되고, 샘플 오차가 있더라도 배치 직후 베이스라인 잡(Layer 1)이 그것을 본다.

LAYER 5힌트 레지스트리 린트지혈대의 만료를 기계가 본다

# ci/lint-plan-pins.sh
status=0
while IFS=: read -r file line _; do
  ctx=$(sed -n "$((line > 3 ? line - 3 : 1)),$((line + 3))p" "$file")
  expiry=$(grep -oE "PLAN-PIN:.*만료 ([0-9]{4}-[0-9]{2}-[0-9]{2})" <<< "$ctx" \
           | grep -oE "[0-9]{4}-[0-9]{2}-[0-9]{2}$" || true)
  if [ -z "$expiry" ]; then
    echo "$file:$line 힌트에 PLAN-PIN(이슈·만료일)이 없다"; status=1
  elif [[ "$expiry" < "$(date +%F)" ]]; then
    echo "$file:$line PLAN-PIN 만료($expiry) — 근본 대응 배포 후 제거하거나 재검토해 기한을 연장"; status=1
  fi
done < <(grep -rnE "FORCE INDEX|USE INDEX|IGNORE INDEX|/\*\+ *(INDEX|NO_INDEX|JOIN_ORDER|SET_VAR)" src/ || true)
exit $status

6. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 답의 깊이가 갈리는 지점, 추가는 이 페이지에서 보탠 문항.

"힌트로 고정하면 끝 아닌가요? 왜 최후 수단이라고 하죠?" 시니어 변별

힌트는 문제를 푸는 게 아니라 옵티마이저의 판단 기능을 끄는 것이다. 오늘 틀렸다고 내년에도 틀리리라는 보장이 없는데, 힌트는 "오늘의 정답"을 영구 고정한다.

대가 네 가지를 한 호흡에 — ⑴ 분포가 바뀌어도 계획이 못 따라간다, ⑵ 인덱스 이름이라는 물리 정보가 코드에 결합돼 인덱스 변경이 애플리케이션 변경이 되고 FORCE INDEX는 인덱스가 사라지면 그 자리에서 에러다, ⑶ 업그레이드로 옵티마이저가 좋아져도 그 쿼리만 과거에 묶인다, ⑷ 증상을 덮어 통계·인덱스 설계의 진짜 원인이 다른 쿼리에서 재발한다.

순서 통계 갱신(입력 교정) → 인덱스 설계로 후보 단일화(흔들릴 여지 제거) → 그래도 안 되면 힌트. 쓴다면 이슈 번호·이유·만료일을 붙이고 린트가 만료를 잡게 한다. "장애 중이라면 힌트 먼저, 정리는 나중"도 맞다 — 단 "나중"을 기계가 기억하게 하는 장치까지 말해야 상급이다.

"옵티마이저가 '틀린' 게 아니라 '맞게' 바꾼 경우는 어떻게 구분하나요?"

EXPLAIN ANALYZE로 추정과 실측의 거리를 잰다. 새 계획의 추정 rows와 actual rows가 가까우면 옵티마이저는 지금 데이터를 정확히 보고 있고, 계획 전환은 옳다 — status='FAILED'가 1%에서 40%가 된 뒤의 풀스캔은 정답이다.

이때 느린 것은 계획 탓이 아니라 "실패 주문 전부를 읽는 쿼리"가 된 요구 탓이므로 대응은 힌트가 아니라 쿼리·요구의 변경(기간 조건 강제, 아카이빙, 상태별 파티션이나 별도 집계)이다.

반대로 추정과 실측이 자릿수 단위로 어긋나면 입력(통계·샘플)이 틀린 것이고, 그때는 ANALYZE TABLE → 샘플 페이지 → 히스토그램 순서. "옵티마이저가 이상하다"는 말은 이 측정을 하기 전에는 할 수 없다.

"통계 자동 재계산을 꺼버리면 안정적이지 않나요?"

안정은 얻지만 낡음의 책임을 전부 떠안는다. STATS_AUTO_RECALC = 0이면 계획은 내가 ANALYZE할 때만 바뀐다 — 재계산 시각을 통제하고 샘플 오차로 며칠에 한 번 흔들리는 일도 없다.

대가는 데이터가 10배로 자라도 통계는 그대로라는 것이고, 그러면 "낡은 통계로 인한 오판"이 이번엔 영구화된다. 그래서 끌 때는 반드시 예약 ANALYZE 잡과 짝이어야 하고, 어울리는 곳은 매일 TRUNCATE 후 재적재하는 테이블처럼 행 수가 요동쳐 자동 재계산이 오히려 해로운 곳이다.

일반 테이블에는 끄는 것보다 샘플 페이지를 올려 재계산의 품질을 높이는 쪽이 맞다 — "재계산이 문제"가 아니라 "재계산의 표본이 문제"이기 때문이다.

"같은 쿼리인데 특정 파라미터에서만 느립니다. 계획이 '바뀐' 건가요?"

MySQL은 실행마다 실제 값으로 다시 최적화하므로 값마다 계획이 다른 것은 바뀐 게 아니라 원래 그렇다. 주문 8건 사용자와 40만 건 대형 가맹점은 같은 SQL이지만 최적 계획이 다르고, 옵티마이저는 각각에 맞게 고른다.

문제는 통계의 "평균"이 어느 한쪽에는 틀리다는 점과, 그 값에서만 나쁜 계획(정렬 인덱스 선호 규칙 등)이 튀어나오는 점이다. 대응은 ⑴ WHERE·ORDER BY를 동시에 만족하는 복합 인덱스로 값과 무관하게 후보를 하나로 만들고, ⑵ 그래도 대형 값이 무거우면 그 경로를 분리(커서 기반, 기간 강제)한다.

가산점 PostgreSQL은 반대 방향의 함정 — 프리페어드 문 5회 실행 뒤 값과 무관한 generic plan으로 고정할 수 있어 "여섯 번째부터 느려진다"가 나오고 plan_cache_mode로 제어한다. 어느 DB든 스큐의 문제는 인덱스 설계로 푸는 것이 정석이다.

"DB 업그레이드 전에 실행 계획 변경을 어떻게 미리 잡나요?" 시니어 변별

"업그레이드는 함수가 바뀌는 것"이므로 같은 입력으로 새 함수를 미리 돌려본다.

  1. digest 상위 N개(시간 합 기준)와 핵심 쿼리 목록을 뽑는다.
  2. 운영 스냅샷으로 만든 스테이징을 새 버전으로 올린 뒤 ANALYZE로 통계를 맞춘다.
  3. 두 버전의 EXPLAIN FORMAT=JSON을 §5 Layer 1의 스크립트로 diff해 key·type이 바뀐 쿼리를 추린다.
  4. 바뀐 것은 EXPLAIN ANALYZE로 실측해 좋아진 것과 나빠진 것을 나눈다.

나빠진 쿼리는 업그레이드 전에 인덱스를 손보거나, 임시로 SET_VAR 힌트나 이전 optimizer_switch 값을 브리지로 두고 업그레이드 뒤 하나씩 푼다. 관리형 DB라면 마이너 자동 업그레이드를 끄고 유지보수 창을 내가 정하는 것이 전제.

한 호흡으로 "업그레이드의 이득(새 최적화·보안 패치)을 받되, 상위 digest의 계획 diff로 손해 볼 쿼리를 미리 특정하고, 그 쿼리에만 국소 브리지를 걸어 리스크를 문장 단위로 좁힌다."

"index dive가 있는데 왜 §2의 사고가 났나요? user_id = ? 는 상수 조건 아닌가요?" 추가

dive가 고쳐 주는 것은 "계획 A의 예상 행 수"이지, "계획 B가 몇 행 만에 LIMIT을 채울까"의 추정이 아니다.

계획 A(ref)의 행 수는 dive로 실측되므로 비교적 정확하다. 그런데 계획 B는 "PK를 역순으로 훑을 때 이 사용자의 행이 얼마나 촘촘히 나오나"를 계산해야 하고, 이 ORDER BY … LIMIT 휴리스틱은 WHERE 키의 rows_per_key(영속 통계)를 쓴다(§1-1). 즉 두 후보의 비용이 서로 다른 입력으로 계산되고, 그중 통계 쪽이 무너지면 B가 이긴다.

이것이 "단순 등호 조건은 dive 덕에 안전하다"가 ORDER BY LIMIT이 붙는 순간 깨지는 이유이고, 복합 인덱스 (user_id, id)로 후보를 하나로 만드는 것이 근본 대응인 이유다 — 비교 자체가 사라진다.

"장애 중에 ANALYZE TABLE을 바로 돌려도 되나요? 몇 초면 끝나잖아요." 추가

ANALYZE 자체는 몇 초지만, 끝나면서 테이블 정의 캐시를 flush한다. 그 테이블을 오래 잡고 있는 쿼리·트랜잭션(리포트 쿼리, 열어 둔 트랜잭션)이 있으면 flush가 그것이 끝날 때까지 기다리고, 뒤이어 들어오는 모든 쿼리가 그 뒤에 줄을 선다 — "ANALYZE 돌렸더니 DB가 멈췄다"의 정체다. ANALYZE는 이미 끝나 있어 원인으로 지목되기도 어렵다.

절차 ⑴ SHOW PROCESSLIST로 그 테이블의 장기 실행 쿼리를 확인하고, ⑵ 세션의 lock_wait_timeout을 짧게 잡아 못 얻으면 ANALYZE 쪽이 포기하게 하고, ⑶ 레플리카 동시 flush가 싫으면 NO_WRITE_TO_BINLOG. 그리고 같은 테이블에서 두 번째 ANALYZE라면 카드가 아니라 샘플 페이지 상향(§4-3)으로 가야 한다는 신호다.

"EXPLAIN 비교를 스테이징에서 하면 안 되나요? 운영 레플리카까지 필요한가요?" 추가

계획 = f(후보, 입력)인데, 스테이징은 입력(통계)이 다르다. 같은 스키마·같은 SQL이라도 행 수·카디널리티·분포가 다르면 옵티마이저는 다른 답을 낸다 — 스테이징에서 ref idx_user가 나왔다고 운영도 그렇다는 보장이 없다.

그래서 층이 둘이다: CI의 시드 데이터 EXPLAIN 테스트는 코드 변경이 만드는 회귀를, 운영 레플리카의 일일 베이스라인(§5 Layer 1)은 데이터·통계 변경이 만드는 회귀를 잡는다. 스테이징 EXPLAIN은 장애 당일 "평소 계획"의 참고용으로는 쓸 수 있지만, 베이스라인의 자리를 대신하지는 못한다.

"복합 인덱스 (user_id, id)를 만들면 기존 idx_user(user_id)는 어떻게 하나요?" 추가

접두사 중복이므로 정리 대상이다 — 단, 바로 DROP하지 않는다. 세컨더리 인덱스는 PK를 품으므로 idx_user(user_id)는 사실상 (user_id, id)와 같은 순서를 갖지만, 명시적 복합 인덱스가 생기면 옵티마이저 입장에서는 두 후보가 남는다 — §2-2 "후보가 둘이면 뒤집힐 수 있다"가 그대로 적용된다.

절차 ⑴ sys.schema_redundant_indexes로 중복 확인 → ⑵ ALTER INDEX idx_user INVISIBLE로 후보에서 빼고 일주일 관찰(카드 3의 예방 규칙) → ⑶ 베이스라인 잡의 diff와 digest examined에 이상이 없으면 DROP. 되돌릴 수 있는 단계를 하나 끼우는 것이 안전망을 코드로 두는 습관의 일부다.

한 줄 요약
옵티마이저는 통계·샘플·파라미터 값·비용 상수를 입력받아 후보 계획의 비용을 비교하는 함수라서, 코드도 쿼리도 안 바꿨는데 계획이 바뀌었다면 입력이 바뀌었거나(통계 자동 재계산·샘플링 오차·분포 변화·들어오는 값), 후보가 바뀌었거나(인덱스 추가·삭제), 함수가 바뀐 것(업그레이드·파라미터)이다. 진단은 느려진 시각 → digest의 건당 examined 행 비교 → EXPLAIN 베이스라인 diff → 통계 last_update → 분포 확인의 순서로, 완화는 ANALYZE TABLE·만료일 붙인 힌트·INVISIBLE로, 근본 대응은 복합 인덱스로 후보를 하나로 만들어 흔들릴 여지를 없애는 것이며, 배포 없이 일어나는 변경이므로 EXPLAIN 베이스라인 잡·digest 스냅샷 알람·배치 끝 ANALYZE를 기계에 맡겨야 다음번엔 사용자보다 먼저 안다.
배포 없이 DB CPU만 올랐다"변경 없음"을 의심하며 원인 전체를 넓게 훑는 진단 — 이 문서는 그중 "계획이 바뀌었다" 갈래를 깊게 판다 실행 계획 읽기와 느린 쿼리 개선 프로세스EXPLAIN 칸 읽는 법, 측정→가설→검증→고정 사이클 인덱스를 걸었는데도 풀스캔옵티마이저가 인덱스를 일부러 버리는 비용 모델(랜덤 vs 순차 I/O), 역전의 손익분기 복합 인덱스 컬럼 순서등호 → 범위 → 정렬 → 커버링 — 후보를 하나로 만드는 설계
