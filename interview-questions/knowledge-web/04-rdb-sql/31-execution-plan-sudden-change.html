실행 계획의 갑작스러운 변경
플래너는 "통계를 입력받는 함수"다 — 입력이 바뀌면 출력이 바뀐다

면접 질문: "잘 돌던 쿼리의 실행 계획이 어느 날 갑자기 바뀌어 느려졌습니다. 가능한 원인과 대응은?"

핵심 관전 포인트 — PostgreSQL 플래너는 쿼리를 "계산"하는 계산기가 아니라, 통계·확장 통계·파라미터 값·비용 상수를 입력으로 받아 후보 계획들의 비용을 비교하는 함수다. 코드도 쿼리도 안 바꿨는데 계획이 바뀌었다면 셋 중 하나다 — ① 입력이 바뀜(autoanalyze, 통계 노후, n_distinct 오추정, MCV 목록 교체, 파라미터 값을 안 보기로 한 제네릭 계획 전환), ② 후보가 바뀜(인덱스 추가·삭제·INVALID), ③ 함수가 바뀜(GUC 변경, 메이저 업그레이드 — pg_upgrade는 통계를 안 옮긴다). PostgreSQL에는 index dive도, 힌트 문법도, INVISIBLE 인덱스도 없다. 그래서 통계가 유일한 진실이고 대응 순서가 강제로 고정된다 — ANALYZE → statistics target 상향 → CREATE STATISTICS → 비용 파라미터 국소 교정 → 부분·복합 인덱스로 후보 단일화 → 최후에 pg_hint_plan. 진단도 사다리다: 느려진 시각 특정 → pg_stat_statements의 "건당 읽은 블록" 비교 → auto_explain 로그의 계획 diff → last_autoanalyze·pg_stats 확인 → 분포 확인. 확장을 깔아야 계획을 고정할 수 있다는 사실 자체가 "그건 최후 수단"이라는 설계 메시지다.
  • 1
    먼저 모델을 바꿔 말한다 — 플래너는 계산기가 아니라 함수다. 계획 = f(후보 집합, 입력)이므로 코드도 쿼리도 안 바꿨는데 출력이 바뀌었다면 경우의 수는 셋뿐이다 — 입력이 바뀌었거나, 후보 집합이 바뀌었거나, 함수 자체가 바뀌었거나. "원인 후보 10종"은 외우는 목록이 아니라 이 세 칸에서 꺼내는 것이다.
  • 2
    PostgreSQL에서 가장 자주 터지는 두 갈래는 "계단"과 "방향"이다 — 등호 조건의 추정은 MCV에 있으면 정확한 빈도, 없으면 나머지 균등 분배, 값을 아예 모르면 1/n_distinct로 갈리는데, 값 하나가 MCV 목록에서 밀려나는 순간 추정이 계단처럼 점프한다. 그리고 제네릭 계획은 자기 추정이 커스텀 평균보다 싸 보일 때만 채택되므로, 사고의 피해자는 늘 "평균보다 훨씬 흔한 값만 조회하는 화면"이다.
  • 3
    대응은 "입력을 바로잡는다"에서 출발하고, 고정은 기한부다 — PostgreSQL에는 index dive도 힌트 문법도 INVISIBLE도 없어 순서가 강제된다(ANALYZE → statistics target → CREATE STATISTICS → 비용 파라미터 → 복합·부분 인덱스로 후보 단일화 → 최후에 pg_hint_plan). 계획 고정은 문제 해결이 아니라 플래너의 판단 기능을 끄는 것이라 이슈 번호·이유·만료일을 붙이고, 배포 없이 일어나는 변경이므로 EXPLAIN 베이스라인 잡이 사용자보다 먼저 알게 한다.

0. 질문 + 출제 의도

질문: "잘 돌던 쿼리의 실행 계획이 어느 날 갑자기 바뀌어 느려졌습니다. 가능한 원인과 대응은?"

출제 의도: "코드도 쿼리도 안 바꿨는데 느려졌다"의 단골 원인(통계 정보 갱신, 데이터 분포 변화). DB를 정적인 계산기가 아니라 상태에 따라 판단이 바뀌는 시스템으로 이해하는지 — 힌트로 고정하는 것의 트레이드오프까지 가면 상급이다.

아래층 — 모델

"같은 SQL을 넣으면 같은 계획이 나온다"는 계산기 모델을 버렸는가. "플래너는 통계라는 입력으로 비용을 계산하는 함수라서 입력이 바뀌면 출력이 바뀐다"는 모델이 있어야 원인 후보가 목록으로 인출되고 진단 순서가 논리적으로 나온다.

위층 — 판단

계획을 고정하는 수단이 "문제 해결"이 아니라 "플래너의 판단 기능을 끄는 것"임을 알고 대가와 기한을 붙여 쓰는가. PostgreSQL에서는 이 위층이 특히 선명하다 — "고정한다"는 선택지 자체가 확장 설치라는 문턱 뒤에 있어, 대응이 자연히 "입력을 바로잡는다"에서 출발한다.

이 페이지가 겨냥하는 약점 네 가지 ① 인과를 뭉뚱그리는 것 → 6·7절에서 "통계가 바뀌어서 느려졌다"의 빈칸을 숫자로 채운다(추정 384 vs 실측 80,000).
② 대응책의 대가를 못 말하는 것 → 10절에서 완화 카드마다 얻는 것 · 내주는 것 · 기한 · 만료를 강제하는 장치를 한 호흡에 붙인다.
③ 안전망을 사람의 기억에 맡기는 것 → 11절에서 잡 · 설정 · CI 린트로 고정한다.
④ 목록이 인출되지 않는 것 → 8절의 원인 10종을 1절의 세 칸에, 10절의 대응을 사다리에 걸어 외운다.
이 문서의 자리 — 22번과의 분업, 10번·02번과의 경계 같은 장의 "배포도 없었는데 DB CPU만 올랐다"(22-db-cpu-spike-without-deployment.md)는 "변경 없음"이라는 전제를 의심하며 원인 전체를 넓게 훑고, 이 문서는 그중 가장 흔한 한 갈래인 "실행 계획이 바뀌었다"를 깊게 판다. EXPLAIN 출력의 노드를 읽는 법(cost·rows·actual time·loops·Buffers)은 이미 아는 상태를 전제하고(10-explain-and-slow-query-process.md), "왜 플래너가 인덱스를 일부러 버리는가"의 비용 모델은 02-index-not-used-full-scan.md에 맡긴다. 이 문서가 얹는 것은 딱 하나 — "어제까지 옳던 판단이 오늘 왜 바뀌는가."

1. 모델 — 계산기를 버리고 함수를 세운다

먼저 머릿속 모델을 교체한다. 계산기는 2 + 3을 넣으면 언제나 5다. 같은 입력에 같은 출력이 나오는 것이 계산기의 정의다. 플래너는 계산기가 아니다. 같은 SQL을 넣어도 오늘과 어제의 출력이 다를 수 있고, 그건 고장이 아니라 설계다.

"실행 계획이 왜 바뀌었나요"는 자동으로 세 개의 질문으로 쪼개진다

질문무엇을 확인하나8절의 원인 번호
입력이 바뀌었나?last_autoanalyze 시각, pg_stats의 값, 파라미터를 보고 있나① ② ③ ④ ⑤ ⑥ ⑨ ⑩
후보 집합이 바뀌었나?인덱스 목록 diff, pg_index.indisvalid⑦
함수 자체가 바뀌었나?pg_settings diff, version()⑧

원인 10종은 전부 이 세 칸 중 하나에 들어간다. 목록을 외우는 게 아니라 이 세 칸에서 꺼내는 것이고, 그래서 면접장에서 긴장해도 인출된다.

비유 — 내비게이션 같은 집에서 같은 회사로 가는데 어느 날 내비가 다른 길을 안내한다. 지도(쿼리)는 그대로다. 바뀐 것은 교통정보(통계)다. 교통정보가 갱신되면 안내가 바뀌는 건 정상이고 대개 더 나은 길이다. 문제는 교통정보가 낡았거나(통계가 현실과 어긋남), 표본이 적어 엉뚱하게 잡혔거나(샘플링 오차), "목적지를 안 물어보고 평균적인 통근자 기준으로" 짜였을 때(제네릭 계획)다. "내비가 미쳤다"가 아니라 "내비가 무슨 정보를 보고 그렇게 판단했나"를 묻는 것이 진단의 시작이다.
"실행 계획이 바뀌었다"는 결과이지 원인이 아니다 — 진단은 "어느 입력이, 언제, 왜 바뀌었나"를 찾는 일이다

2. 입력 ①② — 통계에는 실제로 무엇이 들어 있나

2-1. 통계란 무엇인가 — 여론조사와 같은 구조

플래너는 "이 조건에 몇 행이나 맞을까"를 알아야 비용을 계산할 수 있는데, 매번 테이블을 세어 보면 그 자체가 쿼리 한 번 값이다. 그래서 테이블 전체를 세지 않고도 그 답을 추정할 수 있도록, 미리 표본으로 떠 둔 요약이 통계다. 여론조사가 국민 전체에게 안 묻고 1,000명 표본으로 지지율을 추정하는 것과 정확히 같은 구조다 — 그러므로 표본 오차가 있는 것이 정상이고, 이 사실이 8절 원인 ③의 뿌리다.

이 요약을 만드는 명령이 ANALYZE다. 테이블에서 무작위 표본을 뽑아 분포를 요약해 시스템 카탈로그 pg_statistic에 저장하고, 사람이 읽는 뷰가 pg_stats다. 크기 정보는 pg_class에 있고, autovacuum이 백그라운드에서 이 일을 대신 돌려 준다(autoanalyze).

확인 통계를 눈으로 보는 세 개의 쿼리
-- 크기 + "전부 가시"로 표시된 페이지 수(Index Only Scan 비용의 입력)
SELECT relname, reltuples::bigint, relpages, relallvisible
FROM pg_class WHERE relname = 'orders';

-- 언제 통계를 떴나 + 그 뒤로 몇 행이 바뀌었나 (autoanalyze 임계 추적의 핵심)
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables WHERE relname = 'orders';

-- 컬럼 단위 분포 — 세로로 펼쳐 보는 것이 읽기 쉽다(psql 에서 \x on)
SELECT attname, null_frac, n_distinct, correlation,
       most_common_vals, most_common_freqs, histogram_bounds
FROM pg_stats WHERE tablename = 'orders' AND attname = 'status';

2-3. 입력 ② 확장 통계 — "컬럼들이 서로 독립"이라는 기본 가정

기본 통계는 컬럼 하나씩만 안다. 그래서 조건이 여럿이면 플래너는 선택도를 곱한다. 확률에서 독립사건의 동시 확률을 곱하는 것과 같은 계산이고, 그 "독립"이라는 전제가 여기 숨어 있다.

good 곱셈 가정을 깨는 도구 — 만든 뒤 ANALYZE를 해야 비로소 채워진다
CREATE STATISTICS stat_orders_city_zip (dependencies, ndistinct, mcv)
  ON city, zipcode FROM orders;
ANALYZE orders;   -- 이 줄을 빼면 확장 통계는 "만들어졌지만 비어 있다"
함정 — 확장 통계는 자동으로 생기지 않는다 기본 통계는 autoanalyze가 알아서 갱신해 주지만, 확장 통계는 사람이 "어느 컬럼 조합이 상관관계가 있는지" 판단해 직접 만들어야 한다. 그리고 테이블 하나 안의 컬럼들에만 적용된다 — 조인 양쪽의 상관은 못 잡는다.

3. 선택도 세 갈래 — "계단"이 생기는 자리

여기가 이 문서에서 가장 중요한 절이다. 등호 조건 하나의 선택도를 정하는 규칙이 세 갈래로 갈리고, 갈래가 바뀌는 순간 추정이 연속적으로 조금 변하는 게 아니라 계단처럼 점프한다. 6절의 사고가 정확히 이 계단이다.

3초 인출 — 등호 선택도 세 갈래 "안 · 밖 · 모름"

MCV 안→그 값의 빈도 그대로 (정확)
MCV 밖→나머지 확률 ÷ 나머지 값 개수 (균등 분배 가정)
값을 모름→1 / n_distinct (평균 하나 걸린다 가정)

"안 · 밖 · 모름" 세 글자만 붙잡으면 6절(안 → 밖)과 7절(모름) 두 사고가 같은 그림의 두 자리로 정리된다.

3-1. PostgreSQL에는 index dive가 없다 — 이 문서 전체의 전제

index dive란 무엇인가. MySQL은 WHERE user_id = 42처럼 상수 조건이 걸리면 통계를 믿지 않고, 계획을 세우는 그 시점에 그 인덱스의 해당 범위에 실제로 들어가 대략 몇 행인지 세어 본다. 인덱스 안으로 "잠수한다(dive)"는 이름이 여기서 나왔다. PostgreSQL은 그러지 않는다. 상수 조건이든 파라미터든 선택도는 오직 pg_stats의 MCV·히스토그램·n_distinct에서 계산되고, 실측하러 인덱스에 들어가는 단계가 아예 없다.

MySQL — 통계 + 실측

WHERE user_id = 42 → 통계로 1차 추정 → 그 인덱스의 42 구간에 실제로 들어가 행 수를 센다 → 훨씬 정확한 수를 얻는다.

PostgreSQL — 통계뿐

WHERE user_id = 42 → pg_stats만 본다. 끝. 통계가 낡았거나 표본이 편중됐으면 그대로 틀린다.

PostgreSQL에 없는 것 셋 — 이 셋이 없다는 사실이 대응 순서를 강제한다

index dive
계획 시점에 인덱스에 들어가 실제 행 수를 세는 장치. 없다 → 통계가 유일한 진실이라 낡으면 가장 단순한 등호 조건도 틀린다.
힌트 문법
SQL 안에서 계획을 강제하는 문법. 없다 → pg_hint_plan 확장을 깔아야 한다. 그 문턱 자체가 "최후 수단"이라는 설계 메시지.
INVISIBLE 인덱스
메타데이터만 바꿔 인덱스를 후보에서 빼는 기능. 없다 → 인덱스 삭제가 비가역적 결정이 된다.

여기서 PostgreSQL 운영의 결론 세 개가 곧바로 나온다.

  1. 통계가 낡으면 가장 단순한 등호 조건도 틀린다. 대량 적재 직후가 특히 위험하다 — MySQL이었다면 dive가 새 데이터를 즉시 보지만, PostgreSQL은 ANALYZE가 돌기 전까지 옛 세계를 믿는다.
  2. 그래서 ANALYZE가 1순위 대응이다. 어떤 원인이든 통계 갱신을 먼저 해서 "입력이 낡은 건 아니다"를 배제하고 시작한다.
  3. 분포가 급변해도 통계가 안 돌면 계획은 안 바뀐다. 분포 변화가 계획을 바꾸려면 반드시 그 사이에 ANALYZE가 있었다 — 진단에서 last_autoanalyze 시각이 결정적 단서가 되는 이유다.

4. 입력 ③ — 커스텀 계획과 제네릭 계획 (PostgreSQL 고유의 사고)

결론("여섯 번째 실행부터 느려진다")을 먼저 말하면 마법처럼 들리므로, 다섯 단계를 순서대로 밟는다.

1
준비문(prepared statement)이 무엇인가 — SQL 문장을 서버에 한 번 등록해 두고, 그 뒤로는 값만 바꿔 실행하는 것이다. 값이 들어갈 자리는 $1, $2 같은 자리표시자로 남겨 둔다. JDBC의 PreparedStatement가 바로 이것이고, 자바 진영에서는 "SQL 인젝션을 막으려고" 쓰는 것으로 배우지만 서버 쪽 이유는 다르다 — 파싱과 계획 수립을 아끼려고 쓴다.
2
매번 계획을 짜는 것은 비싸다 — 그래서 재사용하고 싶다. EXPLAIN 출력 맨 아래에 찍히는 Planning Time이 그 비용이다. 조인이 여럿인 쿼리는 계획 수립에 수 ms가 들 수 있는데, 실행이 0.5ms인 짧은 쿼리를 초당 수천 번 돌리면 계획 수립이 실행보다 비싸진다.
3
그런데 값에 따라 최적 계획이 달라진다 — 딜레마. user_id = 42(주문 8건)와 user_id = 7001(대형 가맹점, 주문 150만 건)은 같은 SQL이지만 최적 계획이 다르다. 계획을 재사용하려면 값을 안 볼 수밖에 없고, 값을 안 보면 최적이 아닐 수 있다.
4
PostgreSQL의 타협 — 처음 다섯 번은 실제 값으로 계획을 세워 비용을 누적하고, 여섯 번째 계획 수립에서 "커스텀 다섯 번의 평균 비용"과 "값을 모르는 채로 만든 제네릭 계획의 추정 비용"을 비교한다. 아래 도식이 그 판정이다.
5
그래서 "여섯 번째 실행부터 느려진다". 주의할 점 하나 — 회차를 세는 주체가 둘이다. pgjdbc는 같은 PreparedStatement를 5회 실행해야 비로소 서버 준비문으로 전환한다(prepareThreshold 기본 5). 그전까지는 이름 없는 문장이라 서버가 매번 값을 보고 새로 계획한다. 그러니 애플리케이션 관점에서는 "열 번쯤 실행한 뒤"에 바뀌고, 서버 관점에서는 정확히 "여섯 번째 계획 수립"에서 바뀐다. psql에서 PREPARE/EXECUTE로 직접 재현하면 딱 여섯 번째다.

4-1. 증상의 지문 — 톱니 모양으로 온다

4-2. 확인과 통제 — 세 가지 수단

확인 제네릭 계획을 눈으로 보고, 손으로 재현하고, 끄는 법
-- ⑴ 파라미터를 채우지 않고 제네릭 계획을 그대로 본다 (PG 16+)
EXPLAIN (GENERIC_PLAN)
SELECT * FROM orders WHERE user_id = $1 ORDER BY id DESC LIMIT 20;

-- ⑵ 손으로 재현한다 — 여섯 번째 EXECUTE 에서 계획이 바뀌는 것을 눈으로 본다
PREPARE p(bigint) AS SELECT * FROM orders WHERE user_id = $1 ORDER BY id DESC LIMIT 20;
EXPLAIN EXECUTE p(7001);   -- 1~5회는 커스텀 계획, 6회째부터 제네릭인지 확인

-- ⑶ 통제: 이 세션/롤/DB 에서는 항상 값을 보고 계획하게 한다 (= 제네릭 전환을 끈다)
SET plan_cache_mode = force_custom_plan;                       -- 지금 세션만(검증용)
ALTER ROLE app_user SET plan_cache_mode = force_custom_plan;   -- 이 앱 롤만. 새 커넥션부터
ALTER DATABASE shop SET plan_cache_mode = force_custom_plan;   -- 더 넓게
-- 반대로 force_generic_plan 은 "항상 제네릭" — 계획 수립 비용을 아껴야 하는 특수한 경우에만
MySQL 대조 — 같은 뿌리, 다른 얼굴 MySQL은 실행할 때마다 실제 값으로 다시 최적화하므로 이 제네릭 계획 함정이 없다. 대신 "같은 SQL이 값에 따라 다른 계획을 갖는 것이 정상"이라는 다른 얼굴로 온다 — 주문 8건인 사용자와 150만 건인 대형 가맹점은 같은 SQL, 다른 최적 계획이다. 즉 스큐(편중)라는 뿌리는 같고 증상만 다르다: MySQL은 "특정 값에서만 느리다", PostgreSQL은 "여섯 번째 실행부터 모든 값에서 느리다".

5. 입력 ④ · 후보 집합 — 함수의 계수와, 방법의 목록

5-1. 비용 상수와 스위치 (GUC)

플래너의 산술에 들어가는 계수들은 GUC(Grand Unified Configuration, PostgreSQL의 설정 파라미터)다.

seq_page_cost 1.0 / random_page_cost 4.0
랜덤 대 순차의 비율이 인덱스 스캔과 Seq Scan의 손익분기를 정한다. 회전 디스크 시절의 4.0을 SSD에서 그대로 두면 플래너가 인덱스를 과소평가한다(1.1 근처로 낮추는 것이 통례).
effective_cache_size
"이 정도는 캐시에 있겠지"의 짐작값. 크게 잡을수록 반복 인덱스 접근을 싸게 본다. cpu_tuple_cost 계열은 행·연산자당 CPU 비용이다.
work_mem (+ hash_mem_multiplier)
해시·정렬이 메모리에 들어가는지. 이 값이 바뀌면 Hash Join ↔ Merge Join, quicksort ↔ external merge가 갈린다.
enable_seqscan 류 스위치
운영 설정이 아니라 가설 검증 도구다. 그 노드의 비용에 큰 상수를 더하는 것이지 금지가 아니다.
jit + 비용 임계
짧고 자주 도는 쿼리에 JIT가 붙으면 컴파일 시간이 실행 시간을 압도할 수 있다.
max_parallel_workers_per_gather
테이블이 임계 크기를 넘으면 Parallel Seq Scan을 후보에 추가한다 — 입력이 아니라 후보를 늘리는 설정이다.

(가산점) PostgreSQL 플래너는 "지금 캐시에 뭐가 올라와 있는지"를 보지 않는다

effective_cache_size는 정적인 짐작값일 뿐이다. 그래서 "재시작 직후 계획이 달라졌다"는 PostgreSQL에서는 성립하지 않는다 — 재시작 후 느린 것은 같은 계획이 캐시 미스로 디스크를 읽는 것이고, BUFFERS의 shared read가 그것을 증명한다.

MySQL 대조: MySQL 8의 비용 모델은 "이 인덱스가 버퍼 풀에 얼마나 올라와 있나" 추정치를 참고하므로 재시작·failover 직후와 예열 뒤의 계획 자체가 다를 수 있다. PostgreSQL에는 그 입력이 없어 위의 구분이 더 깔끔하게 떨어진다.

5-2. 후보 집합 — 무엇이 "후보"인가

후보 집합은 "이 SQL을 실행할 수 있는 물리적 방법들의 목록"이다. 인덱스를 하나 만들면 후보가 늘고, 지우면 준다. 테이블이 임계 크기를 넘으면 병렬 계획이 후보에 추가되고, CREATE INDEX CONCURRENTLY가 실패해 INVALID 상태로 남은 인덱스는 디스크에 존재하고 쓰기 비용도 내지만 후보에는 안 들어간다.

후보가 하나뿐이면 통계가 어떻게 흔들려도 계획은 안 흔들린다
— 입력을 정확하게 만드는 것보다 후보를 줄이는 쪽이 근본적인 이유(10절 근본 대응 1번)

6. 사고 ① — 새벽 배치 한 번이 계획을 뒤집는 여섯 칸

상황 고정. orders 1,200만 건. 인덱스는 orders_pkey(id)와 idx_orders_user(user_id) 둘. 사용자 구성은 편중돼 있다 — 가맹점(입점 판매자) 계정 5,000개가 900만 건을 갖고 있고(평균 1,800건, 최대 150만 건), 일반 사용자 100만 명이 300만 건을 갖는다(평균 3건). 주문 목록 API의 쿼리는 이것 하나다.

SELECT * FROM orders WHERE user_id = $1 ORDER BY id DESC LIMIT 20;

계획 A — idx_orders_user

이 사용자의 행을 전부 모아 → 힙에서 읽고 → id로 정렬 → 앞 20건.

비용 ∝ (예상 행 수) × (힙 랜덤 접근) + 정렬
→ 예상 행 수가 적을수록 싸다

계획 B — orders_pkey 역방향

id DESC 순서 그대로 뒤에서부터 훑으며 user_id로 거른다 → 20건 모이면 Limit이 중단시킨다. 정렬 노드가 아예 없다.

비용 ∝ (전체 스캔 비용) × 20 / (예상 행 수)
→ 예상 행 수가 많을수록 싸다

두 계획의 방향이 정반대다 — 그래서 "예상 행 수" 하나가 뒤집히면 계획도 뒤집힌다

6-1. 평소(베이스라인) — 플래너가 정확히 알고 있던 시절

피해자는 가맹점 X다. 주문 8만 건을 가진 중견 가맹점이고, 전체 1,200만 건의 0.667%를 차지해 most_common_vals 목록의 끝자락(100번째)에 실려 있다. 그래서 지금까지 플래너는 X의 행 수를 정확히 알고 있었다 — 3절 규칙 ⑴이 적용돼 빈도 0.006667을 그대로 써서 예상 행 수 80,000행, 실제도 80,000행.

7-2. 두 사례가 가르치는 네 가지

첫째 — ANALYZE 자체는 정상 동작이다
문제는 "재계산"이 아니라 "재계산 결과가 특정 값에게만 나빠질 수 있다"는 것이다. 그래서 대응이 "autoanalyze를 끄자"가 아니라 "목록을 넓히거나 후보를 줄이자"로 간다.
둘째 — 플래너는 "평균적인 값"을 가정한다
MCV에 못 든 값들은 전부 똑같이 생겼다고 보고, 제네릭 계획은 아예 "평균 하나로 모든 값을 처리하겠다"고 결정한다. 그래서 증상이 "쿼리가 느리다"가 아니라 "이 값에서만 느리다"로 온다.
셋째 — 후보가 둘이었기 때문에 뒤집힐 수 있었다
(user_id, id) 복합 인덱스가 있었다면 후보 하나가 WHERE·ORDER BY·LIMIT을 동시에 만족해 계획 B가 이길 수 있는 통계값이 아예 존재하지 않는다. 흔들릴 여지를 없애는 것이 근본 대응이다.
넷째 — PostgreSQL에는 실측 안전장치가 없다
대신 통계를 정밀하게 만드는 손잡이(statistics target, 확장 통계, n_distinct 고정)가 열려 있다 — 그 손잡이를 쓰는 것이 PostgreSQL 운영자의 일이다.

7-3. 두 후보의 비용을 나란히 보는 법 가산점

EXPLAIN은 "고른 것"만 보여준다. "무엇과 비교해서 골랐는지"를 PostgreSQL에서 보는 정석은 후보를 하나씩 막아 각 계획의 총비용을 뽑아 비교하는 것이다.

EXPLAIN SELECT * FROM orders WHERE user_id = 70100 ORDER BY id DESC LIMIT 20;
--  Limit  (cost=1565.22..1565.27 rows=20 ...)   ← 지금 고른 계획 A 의 비용 1,565

BEGIN;                                 -- SET LOCAL 이라 이 트랜잭션에서만 적용되고 ROLLBACK 이면 원복
SET LOCAL enable_indexscan = off;      -- idx_orders_user 를 쓰는 A 를 막아 B 를 보게 한다
SET LOCAL enable_indexonlyscan = off;
EXPLAIN SELECT * FROM orders WHERE user_id = 70100 ORDER BY id DESC LIMIT 20;
--  Limit -> Bitmap Heap Scan ... 또는 Seq Scan ...  (cost=... .. 37211.43)   ← B 계열의 비용
ROLLBACK;
이 측정이 주는 것 — "뒤집힐 뻔했다"를 미리 안다 "A가 1,565, B가 37,211이면 24배 차이"처럼 두 후보의 비용 간격을 알면, 그 쿼리가 다음 ANALYZE에서 또 뒤집힐 후보인지 판단할 수 있다. 간격이 두 배 남짓이면 통계가 조금만 흔들려도 뒤집힌다. 반대로 실제 실행 시간은 A가 압도적으로 느린데 비용은 A가 싸다면 "비용 모델의 입력이 틀렸다"는 확진이다 — 사고 ①이 정확히 그 상태다.

주의: enable_*를 끄는 것은 그 노드의 비용에 큰 상수를 더하는 것이지 금지가 아니고, 가설 검증 도구이지 운영 설정이 아니다.

MySQL 대조 MySQL은 optimizer_trace가 후보별 cost·chosen을 JSON으로 한 번에 준다. PostgreSQL에는 내장 트레이스가 없어 위처럼 후보를 하나씩 막아 재는 방식이 표준이다. 대신 PostgreSQL은 노드별 실제 읽은 블록까지 주므로 "왜 골랐나"는 약하고 "고른 게 실제로 어땠나"는 강하다.

8-1. ①② autoanalyze가 돌았거나, 반대로 안 돌았거나

변경 행 수(n_mod_since_analyze)가 autovacuum_analyze_threshold(기본 50) + autovacuum_analyze_scale_factor(기본 0.1) × 추정 행 수를 넘으면 autovacuum 워커가 다음 순회에서 ANALYZE를 돌린다. 배치가 끝난 시각과 일치하지도 않고 기본 설정으로는 로그에도 안 남아서 "배포도 배치도 끝난 지 한참인데 갑자기"라는 인상을 준다(①).

반대편도 같은 임계에서 나온다 — 임계가 비율이라 1억 건 테이블은 1,000만 행이 바뀌어야 돈다(0.1 × 1억). 그 사이 적재된 새 데이터는 통계에 아예 존재하지 않고, 플래너는 created_at >= '어제'를 히스토그램 밖 값으로 보고 "거의 안 걸린다"고 추정한다 → 과도한 Nested Loop·인덱스 스캔(②). PostgreSQL에는 index dive가 없으므로 이 오차를 실행 시점에 바로잡을 장치가 없다.

SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze,
       (SELECT reltuples::bigint FROM pg_class c WHERE c.oid = relid) AS reltuples
FROM pg_stat_user_tables WHERE relname = 'orders';
-- last_autoanalyze 가 느려진 시각 직전 → ①
-- n_mod_since_analyze 가 크고 last_analyze 가 오래됨 → ②
가산점 포인트 — 사후에 "그 시각에 정말 돌았나"를 확인할 유일한 기록 log_autovacuum_min_duration을 켜 두면 autovacuum·autoanalyze 실행이 서버 로그에 남는다. 기본값으로는 아무 기록이 없어 사후 확인이 불가능하므로, 운영 기본값으로 켜 두는 게 낫다.

8-2. ③ n_distinct 오추정 — "돌았다"가 아니라 "다르게 나왔다"가 문제

표본 3만 행은 1,200만 건 테이블의 0.25%다. PostgreSQL은 이 표본에서 본 서로 다른 값의 개수를 전체로 외삽하는데, 고카디널리티 컬럼에서는 구조적으로 낮게 잡힌다 — 2절 예시에서 실제 100만 명 이상인 user_id가 16,685로 나온 것이 그 얼굴이다. 값이 뭉쳐서 저장되는 컬럼일수록 어느 행을 맞히느냐에 따라 추정이 더 크게 흔들린다. 증상은 "아무것도 안 했는데 며칠에 한 번씩 계획이 왔다 갔다 한다"이다.

SELECT attname, n_distinct, null_frac, correlation
FROM pg_stats WHERE tablename = 'orders' AND attname = 'user_id';
--  n_distinct 가 양수면 그 값 자체, 음수면 행 수 대비 비율(-0.1 = 행 수의 10%)
SELECT COUNT(DISTINCT user_id) FROM orders;   -- 레플리카에서. 자릿수가 다르면 ③ 확정
③의 특징 — 한 값의 문제가 아니라 컬럼 전체의 문제다 n_distinct는 3절 규칙 ⑵·⑶의 분모다. 분모가 흔들리면 MCV에 없는 모든 값의 추정이 함께 흔들린다. PostgreSQL의 손잡이 둘: ALTER COLUMN user_id SET STATISTICS 1000(이 컬럼만 표본·MCV 목록 크기를 키운다), 그리고 값 개수가 안정적이라면 SET (n_distinct = -0.1)로 추정치를 아예 고정(대가는 10절에서).

8-3. ④ 제네릭 계획 전환 — 진단 진입점이 유일하게 다르다

4·7절의 사슬 그대로이고, 이 원인만 진단 진입점이 다르다 — 통계는 멀쩡하고 last_autoanalyze도 조용한데 계획만 바뀐다. 입력 중에서 "쿼리에 들어온 값"만 바뀐(정확히는 "안 보게 된") 경우이기 때문이다. 판별은 4-1절의 지문 세 개, 확진은 EXPLAIN (GENERIC_PLAN)(PG 16+)이나 PREPARE + 여섯 번의 EXPLAIN EXECUTE.

가산점 포인트 track_planning = on을 켜면 pg_stat_statements에 plans가 수집된다(PG 13+) — calls는 느는데 plans가 거의 안 늘면 계획을 재사용 중이라는 간접 신호다.

8-4. ⑤ 데이터 분포 변화 — 플래너가 "옳게" 바꾼 경우일 수 있다

status = 'FAILED'가 1%일 때는 인덱스가 정답이고 40%일 때는 Seq Scan이 정답이다. 외부 결제사 장애로 실패 주문이 쏟아지고 그 뒤 ANALYZE가 돌면 most_common_freqs가 갱신되고 플래너는 Seq Scan으로 바꾼다. 이때 계획 전환은 오판이 아니라 정확한 판단이고, 느려진 것은 "실패 주문 전부를 읽어야 하는 쿼리"가 된 요구 자체 때문이다. 구분법은 추정 rows와 actual rows의 거리 — 가까우면 플래너가 옳고, 대응은 쿼리·요구의 변경(기간 조건, 아카이빙, 부분 인덱스, 파티셔닝)이다.

PostgreSQL 특유의 미묘함 — MCV 목록은 크기가 유한하다

목록 칸 수는 statistics target(기본 100)이 정하고, 새 값이 들어오면 누군가는 밀려난다. 어떤 값이 MCV에 들어오거나 밀려 빠지는 순간, 그 값의 선택도 계산이 규칙 ⑴에서 규칙 ⑵로 불연속하게 바뀐다. "어제까지 잘 되던 특정 값만 갑자기"의 정체가 이것인 경우가 많고, 6절의 사고가 정확히 이것이다. 처방은 statistics target 상향(= MCV 목록 확대)이다.

8-5. ⑥ 컬럼 상관관계 — 확장 통계를 안 만들었으면 항상 틀리고 있다

2-3절 그대로 — 조건이 둘 이상 AND로 걸리는 쿼리에서 추정 rows가 실제보다 자릿수로 작으면 이 칸을 의심한다. CREATE STATISTICS는 만든 뒤 ANALYZE를 해야 채워지고, 테이블 하나 안의 컬럼들에만 적용된다(조인 양쪽의 상관은 못 잡는다).

8-6. ⑦ 인덱스 추가·삭제·INVALID — 후보 집합이 바뀜

옆 팀이 리포트 쿼리를 위해 idx_orders_created_status를 추가했더니 내 쿼리의 플래너가 그쪽을 고르기 시작하는 경우. 인덱스는 추가만으로 다른 쿼리의 계획을 바꿀 수 있다. 반대로 "안 쓰는 것 같아서" 지운 인덱스가 특정 값에서만 쓰이던 것이라 그 값이 들어올 때 무너지기도 한다.

SELECT i.indexrelid::regclass AS index_name, pg_get_indexdef(i.indexrelid) AS def,
       i.indisvalid, s.idx_scan
FROM pg_index i JOIN pg_stat_user_indexes s ON s.indexrelid = i.indexrelid
WHERE i.indrelid = 'orders'::regclass ORDER BY s.idx_scan;
-- indisvalid = false → CIC 실패 잔존(DROP 후 재시도) / idx_scan = 0 → 미사용 후보
PostgreSQL 고유의 함정 — INVALID 인덱스 CREATE INDEX CONCURRENTLY가 실패하면 INVALID 상태의 인덱스가 남는다 — 쓰기 비용은 다 내면서 플래너의 후보에는 안 들어간다. "인덱스가 분명히 있는데 안 탄다"의 단골이다. 인덱스 bloat도 이 칸이다 — 인덱스가 부풀면 relpages가 커져 인덱스 스캔 비용이 올라가고 어느 지점에서 Seq Scan에 진다(처방은 REINDEX CONCURRENTLY).

8-7. ⑧ GUC 변경과 메이저 업그레이드 — 함수가 바뀜

work_mem, random_page_cost, effective_cache_size, jit, 병렬 설정, default_statistics_target. 누군가 "다른 문제를 고치려고" 만진 파라미터의 영향이 내 쿼리에 왔다. pg_settings의 정기 스냅샷 diff로 잡는다 — WHERE source NOT IN ('default','override')가 "기본값에서 벗어난 것들"을 준다.

⑴ 플래너 자체가 바뀐다

새 노드(Memoize, Incremental Sort 등)가 후보에 추가되고 비용 계산이 개선된다. 대개는 좋아지지만 개별 쿼리는 나빠질 수 있다.

⑵ 더 흔하고 더 치명적인 쪽 — 통계가 사라진다

pg_upgrade는 옵티마이저 통계를 새 클러스터로 옮기지 않는다. 업그레이드 직후의 DB는 통계가 텅 빈 상태라 플래너가 기본 추정치로 계획을 세운다 — 모든 쿼리의 계획이 동시에 이상해지고, 사람들은 "새 버전이 나쁘다"고 오진한다.

good 그래서 업그레이드 절차의 마지막 줄은 반드시 통계 재수집이다
vacuumdb --all --analyze-in-stages   # 낮은 정밀도로 전체를 빠르게 훑고 점점 정밀하게 반복
# (--analyze 로 한 번에 돌리면 정확하지만 그동안 통계가 계속 비어 있다)

8-8. ⑨⑩ 아무 사건 없이 넘어가는 두 임계

⑨ 테이블 크기
테이블이 커지면 어느 지점에서 인덱스 스캔의 힙 랜덤 접근 비용이 Seq Scan을 넘어서고, 또 어느 크기를 넘으면 Parallel Seq Scan이 후보에 추가된다. 이 전환은 배치도 배포도 없이 데이터가 자란 것만으로 일어난다 — pg_class.relpages 추이를 베이스라인에 남겨 두면 "그날 임계를 넘었다"가 보인다.
⑩ visibility map 노후 가산점
Index Only Scan의 비용 추정에는 relallvisible / relpages 비율이 들어간다. 롱 트랜잭션이 VACUUM을 막거나 autovacuum이 밀리면 "전부 가시" 페이지 비율이 떨어지고 → 예상 힙 접근이 늘어 비용이 올라가고 → 다른 계획으로 전환된다. 전환되지 않더라도 Heap Fetches가 폭증해 같은 계획이 느려진다.

8-9. 계획은 안 바뀌었는데 그렇게 보이는 것들 — 이 문서 밖

같은 계획, 다른 실행 비용 락 대기(wait_event_type = 'Lock'), 캐시 냉각(같은 계획인데 shared read 급증), bloat로 같은 계획이 더 많은 블록을 읽는 것, work_mem 초과 스필(external merge Disk, Batches > 1), N+1 호출 수 증가.

진단 2단계(9절)에서 계획 텍스트가 동일하다면 계획 변경이 아니므로 이 문서를 덮고 22-db-cpu-spike-without-deployment.md로 돌아간다.

9. 진단 5단계 — 순서 고정

9-1. 2단계의 핵심 쿼리 — "건당 읽은 블록"과 "건당 반환 행"을 나란히

-- pg_stat_statements 는 누적이므로 "구간"을 보려면 스냅샷 diff 가 필요하다(11절)
SELECT left(query, 80) AS q, calls,
       round(mean_exec_time::numeric, 2) AS mean_ms,
       round((shared_blks_hit + shared_blks_read)::numeric / NULLIF(calls, 0), 1) AS blocks_per_call,
       round(rows::numeric / NULLIF(calls, 0), 1) AS rows_per_call,
       temp_blks_written                              -- 정렬·해시가 디스크로 흘렀나(사고 ①의 지문 ⑵)
FROM pg_stat_statements WHERE query LIKE '%FROM orders%'
ORDER BY total_exec_time DESC LIMIT 10;
blocks_per_call이 자릿수로 뛰었는데 rows_per_call은 그대로면 계획 변경(또는 원인 ⑤의 분포 급변)
blocks_per_call도 그대로인데 느려졌으면 8-9절이다 — 이 문서를 덮는다
MySQL 대조 — "얼마나 헛일했나"를 재는 칸이 다르다 MySQL은 digest 테이블의 SUM_ROWS_EXAMINED로 "훑은 행 수"를 직접 볼 수 있다. PostgreSQL의 pg_stat_statements에는 그 칸이 없고 rows는 반환 행 수다. 그래서 PostgreSQL에서 "얼마나 헛일했나"의 대용치는 읽은 블록 수이고, 정확한 훑은 행 수는 개별 쿼리를 EXPLAIN (ANALYZE)로 재현해 Rows Removed by Filter에서 읽는다.

9-2. 3단계 — 과거의 계획이 남아 있어야 diff가 가능하다

10. 대응 — 사다리 · 완화 카드 5장 · 근본 대응

순서가 있는 이유: 진단 없이 완화하면 무엇을 되돌려야 할지 모르고, 완화 없이 근본 대응만 하면 장애 시간이 길어지고, 근본 대응 없이 완화만 하면 다음 ANALYZE에 또 뒤집힌다. PostgreSQL에서는 이 순서가 강제된다 — 힌트 문법이 없어 "일단 고정하고 나중에 본다"는 지름길이 막혀 있기 때문이다.

10-1. 즉시 완화 — 카드 5장, 각각 대가와 함께

장애 중이라면 근본 대응(DDL·배포)을 기다릴 수 없다. 카드는 원인에 맞춰 뽑고 대가를 같이 말한다. 다섯 장을 같은 네 칸으로 세워 둔다.

카드무엇을 얻나무엇을 내주나언제까지만 쓰나어떻게 만료를 강제하나
1. ANALYZE배포 없이 통계를 지금 데이터에 맞춘다. 원인 ①②③⑤⑧의 첫 수표본 I/O, 계획 캐시 무효화로 잠깐 계획 수립이 몰림, 원인 ③이면 다음 autoanalyze에 또 흔들림만료 개념이 없다 — 유일하게 영구히 둬도 되는 카드불필요. 대신 같은 테이블에 두 번째 ANALYZE를 하고 있다면 카드 3으로 올라가라는 신호
2. plan_cache_mode = force_custom_plan값을 다시 보게 만들어 원인 ④를 즉시 원복매 실행 계획 수립 비용, 범위가 쿼리 단위가 아니라 롤/DB 단위근본 대응(경로 분리·커버링 인덱스)이 배포될 때까지ALTER ROLE은 코드가 아니라 DB에 남으므로 마이그레이션 파일로만 적용하고 베이스라인이 pg_settings 스냅샷으로 감시
3. statistics target 상향 + 재수집표본과 MCV 목록이 커져 추정 흔들림이 줄고 원인 ③⑤가 완화ANALYZE I/O 증가, MCV 목록을 훑는 만큼 계획 수립 시간 증가영구 설정이 정상 — 문제 컬럼에 남겨 둔다마이그레이션 파일에 이유 주석과 함께 남긴다
4. 비용 파라미터 국소 교정함수의 계수를 하드웨어 현실에 맞춘다. 원인 ⑧그 롤/DB의 모든 쿼리 계획에 영향SSD 교정처럼 "현실을 반영한" 것이면 영구, 특정 쿼리를 살리려는 것이면 임시바꾼 뒤 베이스라인 잡을 돌려 diff를 확인하는 것이 절차. 임시면 PLAN-PIN 주석 + CI 린트
5. pg_hint_plan즉시 · 확실 · 그 쿼리만확장 의존, 데이터 변화 추종 불가, 물리 정보가 코드에 결합, 업그레이드 혜택 제외, 원인 은폐반드시 기한부 — 근본 대응 배포까지힌트 옆에 PLAN-PIN: 주석으로 이슈 번호·이유·만료일. CI 린트가 만료를 검사해 빌드를 깬다

카드 1. ANALYZE — 가장 싼 첫 수

ANALYZE orders;                       -- 테이블 전체
ANALYZE orders (user_id, status);     -- 컬럼을 지정하면 그 컬럼만 떠서 더 빠르다

얻는 것: 코드 변경·배포 없이 통계를 지금 데이터에 맞춘다. PostgreSQL의 ANALYZE는 SHARE UPDATE EXCLUSIVE 잠금이라 읽기·쓰기를 막지 않는다 — 같은 테이블의 VACUUM/ANALYZE, CREATE INDEX CONCURRENTLY, 일부 ALTER TABLE과만 충돌한다. 내는 것 셋 — ⑴ 표본 I/O, ⑵ 계획 캐시 무효화로 잠깐 계획 수립 비용이 몰린다, ⑶ 원인이 ③이라면 이번엔 좋은 표본이 잡혀도 다음 autoanalyze에 또 흔들린다.

MySQL 대조 — 같은 이름, 다른 위험 MySQL의 ANALYZE TABLE은 테이블 정의 캐시를 비우므로 그 테이블을 오래 잡고 있는 쿼리가 있으면 뒤이어 들어오는 쿼리들이 줄을 서는 flush 대기가 생기고, 기본적으로 binlog에 기록돼 레플리카에서도 같이 돈다. PostgreSQL에는 이 두 위험이 없다 — 잠금이 약하고, 물리 복제에서는 통계 자체가 WAL로 복제되므로 레플리카에서 따로 돌릴 필요도 없다(standby는 읽기 전용이라 돌릴 수도 없다).

카드 2. force_custom_plan — PostgreSQL 고유의 원복 카드

얻는 것: 값을 다시 보게 만들어 즉시 원상 복구된다. 코드 배포도 DDL도 없다. 내는 것 셋 — ⑴ 매 실행 계획 수립 비용(준비문의 존재 이유였던 계획 재사용을 포기하는 것이라, 짧고 초당 수천 번 도는 쿼리에서는 계획 수립 CPU가 무시 못 할 비용), ⑵ 범위가 쿼리 단위가 아니다, ⑶ 원인을 덮는다 — 진짜 문제는 "이 화면이 유난히 흔한 값만 조회한다"는 것이고, 그건 경로 분리나 인덱스 설계로 푸는 편이 낫다. 애플리케이션 쪽 대안도 같이 안다 — pgjdbc의 prepareThreshold로 서버 준비문 전환 시점을 늦추거나 아예 쓰지 않게 할 수 있다(prepareThreshold=0). 대가는 같은 방향이다.

카드 3. statistics target 상향 + 재수집 — 원인 ③⑤를 동시에 완화하는 유일한 카드

ALTER TABLE orders ALTER COLUMN user_id SET STATISTICS 1000;  -- 메타데이터 변경이라 즉시 끝난다
ANALYZE orders (user_id);                                     -- 새 설정으로 바로 재수집

얻는 것: 표본이 300 × 1000 = 30만 행으로 늘고 MCV 목록도 100칸에서 1,000칸으로 늘어난다. 사고 ①처럼 "MCV에서 밀려나 규칙 ⑵로 떨어진" 값이 다시 목록 안으로 들어올 여지가 생기고, n_distinct 추정의 흔들림 폭도 줄어든다. 내는 것: ANALYZE가 그만큼 더 읽고, 계획 수립 시간이 늘어난다(플래너가 MCV 목록을 훑는 비용이 목록 길이에 비례한다). 전역 default_statistics_target을 올리는 것보다 문제 컬럼만 올리는 쪽이 거의 항상 옳다.

힌트가 내는 것 다섯 가지 — 한 호흡에 말한다

  1. 확장 의존: 설치·유지가 필요하고 관리형 서비스에 따라 지원 여부가 갈린다.
  2. 데이터가 바뀌어도 계획이 못 따라간다: 오늘 옳은 인덱스가 내년에는 틀린 인덱스가 되는데 힌트는 그 판단 기능을 꺼버린 것이다.
  3. 코드에 물리 정보가 결합된다: 인덱스 이름 변경·삭제가 애플리케이션 변경이 된다.
  4. 업그레이드의 혜택에서 그 쿼리만 제외된다.
  5. 원인을 덮는다: 통계·인덱스 설계의 진짜 문제는 남아 다른 쿼리에서 재발한다.
한 가지 더 — PostgreSQL에는 인덱스를 "후보에서만 빼는" 스위치가 없다 원인 ⑦의 가설 검증은 BEGIN; DROP INDEX ...; EXPLAIN ...; ROLLBACK;으로 한다 — PostgreSQL은 DDL이 트랜잭션에 포함되므로 "지웠다 되돌리는" 검증이 가능하다가산점. 단 DROP INDEX는 ACCESS EXCLUSIVE 잠금이라 트래픽이 있는 운영에서 이 몇 초가 대기열을 만들어 사고가 된다 — SET LOCAL lock_timeout = '2s'를 같이 걸고 가능하면 스냅샷 복제본에서 한다.

MySQL 대조: MySQL 8은 ALTER INDEX ... INVISIBLE로 메타데이터만 바꿔 즉시·가역적으로 인덱스를 후보에서 뺄 수 있어 "지우기 전 일주일은 INVISIBLE로 둔다"는 안전 규칙이 성립한다. PostgreSQL에는 이 기능이 없어 인덱스 삭제가 비가역적 결정이 되고, 그래서 idx_scan을 오래 관찰해 근거를 쌓는 일이 더 중요해진다.

10-2. 근본 대응 — 흔들릴 여지를 없앤다

1. 복합 인덱스로 후보를 하나로 만든다 — 최우선

6절의 쿼리에 (user_id, id)를 두면 "이 사용자의 행을 id 순서로 읽는다"는 후보 하나가 WHERE·ORDER BY·LIMIT을 전부 만족하고 정렬 노드가 사라진다. 계획 B가 이길 수 있는 통계값이 존재하지 않으므로 통계가 어떻게 흔들려도 계획이 안 흔들린다.

CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id, id);
-- PostgreSQL 은 B-tree 를 역방향으로도 읽으므로 (user_id, id DESC) 로 만들 필요가 없다
-- → Index Scan Backward using idx_orders_user_id 로 찍히고 Sort 노드가 사라진다

내는 것: 인덱스 하나만큼의 쓰기·공간 비용(PostgreSQL에서는 인덱스 컬럼이 바뀌는 UPDATE가 HOT에서 탈락해 모든 인덱스에 새 엔트리를 꽂는다는 추가 대가), 대형 테이블 DDL의 절차 비용, 기존 idx_orders_user가 접두사로 중복되므로 관찰 후 정리.

2. 부분 인덱스 — PostgreSQL의 무기. 단 제네릭 계획과는 궁합이 나쁘다

-- 관리자 화면이 보는 것은 전체의 1%뿐이다. 그 1%만 담는 인덱스를 만든다
CREATE INDEX CONCURRENTLY idx_orders_failed_created
  ON orders (created_at DESC) WHERE status = 'FAILED';
여기서 흔한 오답 하나 — 부분 인덱스는 원인 ④의 해결책이 아니다 부분 인덱스는 "쿼리의 WHERE가 인덱스의 WHERE를 포함한다"는 것을 플래너가 증명할 수 있어야만 쓴다. 그래서 status = $1처럼 파라미터로 오면 $1 = 'FAILED'임을 증명할 수 없어 이 인덱스를 못 쓴다.

쓰려면 그 화면만 리터럴을 박은 전용 쿼리로 분리해야 하고, 분리하는 순간 그 쿼리는 준비문 파라미터가 아니게 되므로 원인 ④도 함께 사라진다. 즉 처방은 "부분 인덱스"가 아니라 "경로 분리 + 부분 인덱스" 한 묶음이다.

11. 안전망 다섯 층 — 배포가 없으니 파이프라인이 못 잡는다

이 주제의 회귀는 배포 없이 일어난다 — 그래서 배포 파이프라인이 못 잡는다. 잡는 것은 정기 잡과 알람뿐이다.

CI에서 시드 데이터로 도는 "EXPLAIN 단정 테스트"는 코드 변경이 만드는 회귀를 잡는데, 이 문서의 원인은 데이터·통계가 만드는 회귀라 그것으로는 안 잡힌다. 한 층이 더 필요하다 — 운영 레플리카에서, 운영 통계로, 매일 뜨는 베이스라인.

11-1. 안전망 ① — EXPLAIN 베이스라인 잡: 운영 통계로, 정기적으로, diff

# explain-baseline.sh — 핵심 쿼리 계획을 운영 레플리카에서 뜨고 커밋된 베이스라인과 비교
BASE=db/explain-baseline; WORK=$(mktemp -d); changed=0
for q in db/critical-queries/*.sql; do    # 파일 1개 = 쿼리 1개. 파라미터는 대표값·최악값 두 벌
  name=$(basename "$q" .sql)
  psql -X -A -t -h "$REPLICA_HOST" -d shop -c "EXPLAIN (FORMAT JSON, SETTINGS) $(cat "$q")" \
    | jq -S '[.. | objects | select(has("Node Type"))
              | {node: ."Node Type", rel: ."Relation Name",
                 idx: ."Index Name", cond: ."Index Cond"}]' > "$WORK/$name.json"
  diff "$BASE/$name.json" "$WORK/$name.json" || { echo "PLAN CHANGED: $name"; changed=1; }
done
exit $changed        # 0이 아니면 알람 채널로. 승인된 변경이면 베이스라인 JSON 을 PR 로 갱신
엄격 비교할 것
노드 종류 · 인덱스 이름 · Index Cond. 이 셋이 바뀌면 계획이 바뀐 것이다.
따로 기록할 것
Total Cost와 Plan Rows는 "3배 이상 변동"만 경고로. ANALYZE만으로도 조금씩 움직이므로 엄격 비교하면 소음이 된다.
SETTINGS 를 켜는 이유
기본값에서 벗어난 GUC가 계획과 함께 기록되므로 원인 ⑧의 증거가 베이스라인 안에 남는다.
사고 ①을 잡으려면 — 파라미터를 "대표값"만 넣으면 안 된다 대표값(일반 사용자)은 계획이 안 바뀌었고, 밀려난 가맹점 X에서만 바뀌었기 때문이다. 그래서 쿼리 파일마다 대표값과 최악값(가장 행이 많은 값) 두 벌을 넣는다. 원인 ④까지 잡으려면 파라미터 쿼리는 EXPLAIN (GENERIC_PLAN) 판도 같이 떠서 비교한다.
이 잡이 대신하는 것 PostgreSQL에는 Oracle의 SQL Plan Baseline이나 SQL Server Query Store 같은 "계획 고정·회귀 감지" 기능이 없다. 그래서 "우리가 기록한 베이스라인"이 그 역할을 대신한다. 이 잡이 하는 일은 "느려지기 전에" 계획 전환을 알리는 것이다 — 새벽 2시 autoanalyze 뒤 6시 잡이 diff를 내면 출근 전에 안다.

11-2. 안전망 ② — pg_stat_statements 스냅샷과 비율 알람

-- ops.pgss_snapshot(snapshot_at, queryid, query, calls, total_exec_time, rows,
--                   shared_blks_hit, shared_blks_read)  PK(snapshot_at, queryid)
-- 매시 적재 (pg_cron 또는 외부 크론)
INSERT INTO ops.pgss_snapshot
SELECT now(), queryid, left(query, 500), calls, total_exec_time, rows,
       shared_blks_hit, shared_blks_read
FROM pg_stat_statements WHERE queryid IS NOT NULL;

-- 직전 구간 대비 "건당 읽은 블록"과 "건당 반환 행"을 나란히 — 앞만 뛰면 계획 변경
SELECT c.queryid, left(c.query, 80) AS q,
       (c.shared_blks_hit + c.shared_blks_read - p.shared_blks_hit - p.shared_blks_read)
         / NULLIF(c.calls - p.calls, 0)                 AS blocks_per_call_now,
       (c.rows - p.rows) / NULLIF(c.calls - p.calls, 0) AS rows_per_call_now
FROM ops.pgss_snapshot c
JOIN ops.pgss_snapshot p
  ON p.queryid = c.queryid AND p.snapshot_at = c.snapshot_at - interval '1 hour'
WHERE c.snapshot_at = (SELECT max(snapshot_at) FROM ops.pgss_snapshot)
  AND c.calls > p.calls
ORDER BY 3 DESC;
-- (7일 중앙값 대비 5배 같은 임계는 같은 테이블에서 윈도우 집계로 붙인다)
"건당 읽은 블록이 갑자기 100배인데 반환 행은 그대로"라는 알람이 계획 변경의 가장 이른 신호다

주의 — pg_stat_statements는 누적이고 pg_stat_statements.max를 넘으면 오래된 항목이 밀려나므로, 스냅샷 테이블이 사실상의 시계열 원본이 된다. postgres_exporter + Prometheus로 만들면 알람 규칙이 YAML 파일이 된다.

11-3. 안전망 ③ — auto_explain 상시 + "신규 느린 쿼리 등장" 알람

계획이 뒤집힌 쿼리는 어제까지 느린 쿼리 로그에 없다가 오늘 처음 나타난다. log_min_duration_statement 임계와 "분당 건수" 알람에 더해, auto_explain을 상시로 켜 두는 것이 이 문서의 핵심 장치다 — 사고가 났을 때 "그때의 계획"이 로그에 남아 있어야 9절의 3단계가 성립한다. pgBadger 같은 도구로 일일 리포트를 만들고 어제 리포트에 없던 정규화 쿼리를 따로 표시한다. 총량 알람은 묻히지만 "신규 등장"은 안 묻힌다.

# ci/lint-plan-pins.sh — 계획 고정 자리에 PLAN-PIN(이슈·만료일)이 없거나 만료됐으면 빌드를 깬다
status=0
while IFS=: read -r file line _; do
  ctx=$(sed -n "$((line > 3 ? line - 3 : 1)),$((line + 3))p" "$file")

  if [ -z "$expiry" ]; then echo "$file:$line PLAN-PIN(이슈·만료일)이 없다"; status=1

done < <(grep -rnE "/\*\+ *(IndexScan|SeqScan|NestLoop|HashJoin|MergeJoin|Rows|Set)|SET (LOCAL )?(enable_[a-z]+|plan_cache_mode|random_page_cost|jit) *=" src/ db/ || true)

12-2. 꼬리질문 — 먼저 스스로 답한 뒤 펼친다

계획을 고정해 버리면 끝 아닌가요? 왜 최후 수단이라고 하죠? 시니어 변별힌트: "PostgreSQL에는 힌트 문법이 없다"가 답의 절반이다

PostgreSQL에는 애초에 힌트 문법이 없다 — 그 사실 자체가 답의 절반이다. 계획을 강제하려면 pg_hint_plan 확장을 설치해야 하고, 그건 "여기까지 왔다면 먼저 통계를 의심하라"는 설계 메시지다.

원리로 말하면 힌트는 문제를 푸는 게 아니라 플래너의 판단 기능을 끄는 것이다. 플래너가 오늘 틀렸다고 내년에도 틀리리라는 보장이 없는데, 힌트는 "오늘의 정답"을 영구 고정한다. 대가를 한 호흡에 — ⑴ 확장 설치·유지라는 운영 부담, ⑵ 분포가 바뀌어도 계획이 못 따라간다, ⑶ 인덱스 이름이라는 물리 정보가 코드에 결합된다, ⑷ 업그레이드로 플래너가 좋아져도 그 쿼리만 과거에 묶인다, ⑸ 증상을 덮어 진짜 원인이 다른 쿼리에서 재발한다.

그래서 순서는 ANALYZE → statistics target·CREATE STATISTICS → 비용 파라미터 국소 교정 → 복합·부분 인덱스로 후보 단일화 → 그래도 안 되면 pg_hint_plan이고, 쓴다면 이슈 번호·이유·만료일을 붙이고 린트가 만료를 잡게 한다.

한 단계 더 나은 답: 계획을 통째로 고정하는 대신 /*+ Rows(...) */처럼 추정치만 고쳐 주는 힌트 — 플래너의 판단은 살려 두고 틀린 입력만 바로잡는 것이라 대가가 작다. "장애 중이라면 먼저 고정하고 나중에 정리하겠다"도 맞는 답이다 — 단, "나중"을 기계가 기억하게 하는 장치까지 말해야 상급이다.

플래너가 '틀린' 게 아니라 '맞게' 바꾼 경우는 어떻게 구분하나요? 필수힌트: 재는 자가 하나 있다 — 추정과 실측의 거리

EXPLAIN (ANALYZE, BUFFERS)로 추정과 실측의 거리를 잰다. 새 계획의 추정 rows와 actual rows가 가까우면 플래너는 지금 데이터를 정확히 보고 있고 계획 전환은 옳다 — status = 'FAILED'가 1%에서 40%가 된 뒤의 Seq Scan은 정답이다.

이때 느린 것은 계획 탓이 아니라 "실패 주문 전부를 읽는 쿼리"가 된 요구 탓이므로, 대응은 쿼리·요구의 변경(기간 조건 강제, 아카이빙, 부분 인덱스, 파티셔닝)이다. 반대로 추정과 실측이 자릿수로 어긋나면 입력이 틀린 것이고, 그때는 ANALYZE → statistics target → CREATE STATISTICS 순서다.

PostgreSQL에서 함께 봐야 할 칸이 둘 더 있다 — Rows Removed by Filter(헛일의 크기)와 Buffers(실제 I/O). "플래너가 이상하다"는 말은 이 측정 전에는 할 수 없다.

같은 쿼리인데 앱에서만 느리고 psql에선 빠릅니다. 재시작하면 잠깐 낫고요. 필수힌트: 준비문 · 여섯 번째 · 채택 "방향"

PostgreSQL 준비문의 제네릭 계획 전환이다 — PostgreSQL 면접에서 이 답을 아는지가 갈림길이다.

사슬로 말한다: pgjdbc가 같은 문장 5회 뒤 서버 준비문으로 전환하고, 서버는 커스텀 계획 다섯 번의 평균 비용과 제네릭 계획 비용을 비교해 제네릭이 더 싸 보이면 그쪽으로 고정한다. 제네릭 계획은 $1을 모르므로 1 / n_distinct(평균 선택도)를 쓰는데, 이 화면이 실제로 조회하는 값이 평균보다 훨씬 흔한 값이면 플래너는 "몇 행 안 걸린다"고 믿고 인덱스 스캔·Nested Loop를 고른다 → 싸 보이므로 채택된다 → 실행하면 몇십만 행을 그 계획으로 처리한다.

psql에서 리터럴로 실행하면 커스텀 계획이라 빠르고, 앱을 재시작하면 준비문 캐시가 비어 잠깐 회복됐다가 여섯 번째 계획 수립부터 다시 느려진다. 확진은 EXPLAIN (GENERIC_PLAN)(PG 16+) 또는 PREPARE 후 여섯 번의 EXPLAIN EXECUTE.

즉시 완화는 force_custom_plan을 롤 단위로(대가: 매 실행 계획 수립 비용) 또는 pgjdbc prepareThreshold=0. 근본 대응은 그 화면의 경로를 분리하는 것(리터럴 쿼리, 별도 집계 테이블, 키셋 커서)과 커버링·복합 인덱스로 후보를 하나로 만들어 커스텀이든 제네릭이든 같은 계획이 나오게 하는 것이다.

흔한 오답 하나를 피해야 한다 — 부분 인덱스는 이 문제의 해결책이 아니다. status = $1처럼 파라미터로 오면 플래너가 $1 = 'FAILED'임을 증명할 수 없어 후보에 넣지 못하기 때문이다. 부분 인덱스를 쓰려면 먼저 리터럴로 경로를 분리해야 하고, 분리하는 순간 제네릭 계획 문제도 같이 사라진다. 가산점 track_planning을 켜면 calls는 느는데 plans가 안 느는 것으로 계획 재사용을 간접 확인할 수 있다.

autovacuum의 ANALYZE를 꺼버리면 안정적이지 않나요?힌트: 안정은 얻는다. 그런데 무엇을 함께 끄게 되는가?

안정은 얻지만 낡음의 책임을 전부 떠안는다. autovacuum_enabled = false로 두면 계획은 내가 ANALYZE할 때만 바뀌지만 대가가 셋이다.

⑴ 데이터가 10배로 자라도 통계는 그대로라 "낡은 통계로 인한 오판"이 영구화된다. ⑵ PostgreSQL에서는 특히 위험한데, autovacuum을 끄면 ANALYZE만이 아니라 VACUUM까지 멈춘다 — bloat가 늘고 visibility map이 낡아 Index Only Scan이 퇴화하며, 최악의 경우 XID wraparound 위험까지 간다. ⑶ 예약 ANALYZE 잡이 실패하면 아무도 모른다.

그래서 PostgreSQL의 올바른 선택은 "끈다"가 아니라 임계를 테이블 단위로 조정(autovacuum_analyze_scale_factor = 0.02)이다. "재계산이 문제"가 아니라 "재계산의 표본과 시점이 문제"이므로, 표본은 statistics target으로 키우고(MCV 목록도 함께 넓어진다) 시점은 임계와 배치 끝 ANALYZE로 당긴다.

메이저 업그레이드 전후로 실행 계획 변경을 어떻게 미리 잡나요? 시니어 변별힌트: 두 가지를 분리해서 말한다. 그리고 더 흔한 쪽은 플래너가 아니다

두 가지를 분리해서 말해야 한다 — "플래너가 바뀌는 것"과 "통계가 사라지는 것". 후자가 훨씬 흔하고 치명적이다: pg_upgrade는 옵티마이저 통계를 새 클러스터로 옮기지 않는다. 업그레이드 직후의 DB는 통계가 빈 상태라 모든 쿼리의 계획이 동시에 이상해지고, 사람들은 "새 버전이 나쁘다"고 오진한다. 그래서 절차의 마지막 줄은 반드시 vacuumdb --all --analyze-in-stages다.

전자(플래너 변경)의 절차는 ⑴ pg_stat_statements 상위 N개와 핵심 쿼리 목록을 뽑고, ⑵ 운영 스냅샷 스테이징을 새 버전으로 올린 뒤 ANALYZE로 통계를 맞추고(빼면 비교가 무의미하다), ⑶ 두 버전의 계획을 베이스라인 스크립트로 diff하고, ⑷ 바뀐 것은 실측해 좋아진 것과 나빠진 것을 나눈다. 나빠진 쿼리는 미리 인덱스를 손보거나 롤 단위 GUC를 브리지로 둔다.

한 호흡으로 — "업그레이드의 이득을 받되, 통계 재수집을 절차에 못 박고, 계획 diff로 손해 볼 쿼리를 미리 특정해 리스크를 좁힌다."

① index dive상수 조건이면 인덱스 범위에 실제로 들어가 행 수를 센다 → 통계가 낡아도 단순 조건은 비교적 정확오직 pg_stats만 본다 → "대량 적재 직후 ANALYZE"가 선택이 아니라 절차이고 진단 첫 수도 ANALYZE로 고정
② 제네릭 계획매 실행 재최적화라 이 함정이 없다. 대신 "특정 값에서만 느리다"로 온다준비문 다섯 번 뒤 값을 안 보는 계획으로 고정될 수 있어 "여섯 번째부터 느려진다" — 뿌리는 같은 스큐
③ 고정 수단FORCE INDEX·옵티마이저 힌트·SET_VAR가 문법에 있고 INVISIBLE로 인덱스를 즉시·가역적으로 뺀다힌트가 확장이고 INVISIBLE이 없어 인덱스 삭제가 비가역. 대신 GUC를 전역/DB/롤/세션/트랜잭션 계층으로 좁혀 덮는다
④ 후보 비교optimizer_trace가 후보별 비용을 JSON으로 준다enable_*를 하나씩 꺼서 재는 수동 방식. 대신 노드별 실제 블록을 준다
⑤ 통계 단위인덱스별 카디널리티를 20페이지 표본으로, 히스토그램은 수동 갱신컬럼별 MCV·히스토그램·correlation을 기본 통계로 갖고 autoanalyze가 갱신, 컬럼 간 상관은 CREATE STATISTICS로 따로

이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "차이를 원리로 이해했다"로 들린다.

EXPLAIN은 고른 계획만 보여줍니다. "무엇과 비교해서 골랐는지"는 PostgreSQL에서 어떻게 보나요? 가산점힌트: 후보를 하나씩 막아 잰다. 그리고 왜 그 값을 재는지가 더 중요하다

후보를 하나씩 막아 각 계획의 총비용을 뽑아 비교한다. BEGIN; SET LOCAL enable_indexscan = off; EXPLAIN ...; ROLLBACK; — SET LOCAL이라 그 트랜잭션에서만 적용되고 ROLLBACK이면 원복된다.

왜 재는지가 더 중요하다. "A가 1,565, B가 37,211이면 24배 차이"처럼 두 후보의 비용 간격을 알면 그 쿼리가 다음 ANALYZE에서 또 뒤집힐 후보인지 판단할 수 있다 — 간격이 두 배 남짓이면 통계가 조금만 흔들려도 뒤집힌다. 베이스라인에 이 비용도 남겨 두면 "왜 뒤집혔나"가 아니라 "뒤집힐 뻔했다"를 미리 안다.

두 가지 주의. ⑴ enable_*는 그 노드의 비용에 큰 상수를 더하는 것이지 금지가 아니다. ⑵ 가설 검증 도구이지 운영 설정이 아니다 — ALTER ROLE ... SET enable_seqscan = off 같은 것은 완화 카드에 들어오면 안 된다. 그리고 실행 시간은 A가 압도적으로 느린데 비용은 A가 싸다면 그것이 "비용 모델의 입력이 틀렸다"는 확진이다.

그러면 default_statistics_target을 전역으로 1000까지 올려두면 되는 것 아닌가요? 함정힌트: 무엇이 목록 길이에 비례해서 늘어나는지 생각한다

거의 항상 "문제 컬럼만" 올리는 쪽이 옳다. 이유는 대가가 두 방향으로 붙기 때문이다.

⑴ ANALYZE가 읽는 표본이 커진다 — target 100이면 표본이 3만 행, 1000이면 30만 행이다. 전 테이블·전 컬럼에 걸면 autoanalyze의 I/O 자체가 부하가 된다. ⑵ 더 중요한 쪽 — 계획 수립 시간이 늘어난다. 플래너가 선택도를 계산할 때 MCV 목록을 훑는 비용이 목록 길이에 비례하므로, 모든 쿼리가 조금씩 느려진다. 짧고 초당 수천 번 도는 쿼리가 많은 서비스에서는 이 비용이 눈에 띈다.

그래서 처방은 "편중이 심하고 파라미터로 자주 들어오는 컬럼"만 골라 ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 1000을 걸고 이유 주석과 함께 마이그레이션 파일에 남기는 것이다. 판단 기준은 명확하다 — 같은 테이블에서 ANALYZE를 두 번째 하고 있다면, 또는 MCV 이탈이 원인으로 확인됐다면 그 컬럼이 대상이다.

"인덱스가 분명히 있는데 안 탑니다." 계획 급변 맥락에서 후보 집합을 어떻게 확인하나요? 함정힌트: 후보에 "안 들어가는" 인덱스가 존재할 수 있다

인덱스가 디스크에 있다고 후보에 들어가는 것은 아니다. 확인 순서는 셋이다.

⑴ pg_index.indisvalid를 먼저 본다. CREATE INDEX CONCURRENTLY가 실패하면 INVALID 상태의 인덱스가 남는데, 쓰기 비용은 다 내면서 플래너의 후보에는 안 들어간다. 처방은 DROP 후 재시도. ⑵ 정의가 내 조건과 맞는지 — 부분 인덱스라면 플래너가 "쿼리의 WHERE가 인덱스의 WHERE를 포함한다"를 증명할 수 있어야 하고, 파라미터로 오면 증명이 안 된다. ⑶ idx_scan과 bloat — 인덱스가 부풀면 relpages가 커져 스캔 비용이 올라가고 어느 지점에서 Seq Scan에 진다(처방 REINDEX CONCURRENTLY).

"이 인덱스가 없으면 어떤 계획이 되나"를 안전하게 재는 법도 함께 안다 — PostgreSQL은 DDL이 트랜잭션에 포함되므로 BEGIN; DROP INDEX ...; EXPLAIN ...; ROLLBACK;이 가능하다. 다만 DROP INDEX는 ACCESS EXCLUSIVE 잠금이라 트래픽이 있는 운영에서는 이 몇 초가 대기열을 만들어 그 자체가 사고가 된다 — SET LOCAL lock_timeout = '2s'를 같이 걸고 가능하면 스냅샷 복제본에서 한다. MySQL의 INVISIBLE처럼 가역적인 수단이 없다는 것이 이 조심스러움의 이유다.

n_distinct를 고정하는 건 언제 쓰고, 왜 "가장 위험한 손잡이"인가요? 시니어 변별힌트: 이 값이 무엇의 분모였는지 떠올린다

ALTER TABLE ... ALTER COLUMN ... SET (n_distinct = -0.1)은 "이 컬럼의 서로 다른 값 개수는 행 수의 10%다"라고 플래너에게 통보하는 것이다(음수는 행 수 대비 비율, 양수는 그 값 자체).

쓰는 자리: 원인 ③처럼 표본 오차 때문에 n_distinct 추정이 며칠에 한 번씩 흔들려 계획이 오락가락하는데, 실제 값 개수는 안정적임을 우리가 아는 경우다. 고정하면 흔들림이 원천 차단된다.

왜 가장 위험한가: 이 값은 선택도 규칙 ⑵·⑶의 분모다. 즉 MCV에 없는 모든 값의 추정과, 제네릭 계획의 모든 추정이 이 하나에 매달려 있다. 그리고 데이터 성격이 바뀌어도 플래너는 영구히 그 값을 믿는다 — 서비스가 커져 실제 카디널리티가 달라져도 아무 경고 없이 옛 숫자로 계산한다. 게다가 코드가 아니라 DB에 남는 고정이라 grep으로 안 잡힌다.

그래서 규약은 셋이다 — ⑴ 이유와 재검토 시점을 마이그레이션 파일에 남긴다, ⑵ 베이스라인 잡이 reloptions 스냅샷을 함께 떠서 "코드에 없는 고정"을 diff로 드러내게 한다, ⑶ 우선순위상 이것보다 statistics target 상향을 먼저 시도한다(추정을 더 정확하게 만드는 쪽이 추정을 얼리는 쪽보다 낫다).

계획이 안 바뀌었는데 계획 변경처럼 보이는 경우는 어떤 것들이 있나요? 필수힌트: "같은 계획, 다른 실행 비용" 다섯 가지

다섯 가지다 — ⑴ 락 대기(wait_event_type = 'Lock'), ⑵ 캐시 냉각(같은 계획인데 shared read만 급증 — 재시작·failover 직후), ⑶ bloat(같은 계획이 더 많은 블록을 읽는다), ⑷ work_mem 초과 스필(external merge Disk, Batches > 1), ⑸ N+1 호출 수 증가(쿼리당은 그대로인데 호출이 늘었다).

가르는 방법은 9절의 2단계 하나다 — blocks_per_call이 뛰었는가. 뛰었으면 계획 변경(또는 분포 급변)이고, 블록도 그대로인데 느려졌으면 이 다섯 중 하나다. 더 확실하게는 auto_explain 로그의 계획 텍스트가 동일한지 본다.

PostgreSQL에서 특히 자주 나오는 오답이 ⑵다. "재시작했더니 계획이 달라졌다"는 PostgreSQL에서는 성립하지 않는다 — 플래너는 지금 캐시에 뭐가 올라와 있는지 보지 않기 때문이다(effective_cache_size는 정적인 짐작값이다). 재시작 후 느린 것은 같은 계획이 캐시 미스로 디스크를 읽는 것이고 BUFFERS의 shared read가 그것을 증명한다. MySQL 8은 버퍼 풀 적재율 추정치를 비용 모델에 넣으므로 여기서 답이 갈린다.

조인이 있는 쿼리에서 같은 원인이 어떤 얼굴로 나타나나요? 가산점힌트: 안쪽 노드의 loops를 본다

과소 추정은 조인에서 Nested Loop 폭주로 나타난다. 플래너는 "바깥 노드가 몇 행 안 나온다"고 믿고 Nested Loop를 고르는데(바깥 행마다 안쪽을 한 번씩 도는 방식이라 바깥이 적을 때만 싸다), 실제로 바깥이 150만 행이면 안쪽 인덱스 조회를 150만 번 하게 된다.

지문은 안쪽 노드의 loops다 — loops=1500000처럼 찍힌다. 그리고 EXPLAIN ANALYZE의 안쪽 노드 시간은 1회 평균으로 표시되므로 actual time × loops로 곱해서 봐야 진짜 비용이 보인다.

뿌리는 같다 — 사고 ①(MCV 이탈)이든 사고 ②(제네릭 계획)든 원인 ⑥(컬럼 상관관계 미반영)이든 "추정 행 수가 실제보다 훨씬 작다"는 하나의 입력 오류가 단일 테이블에서는 인덱스 스캔 + 디스크 정렬로, 조인에서는 Nested Loop 폭주로 얼굴만 바꿔 나타난다. 그래서 대응도 같다 — 먼저 추정을 고치고(ANALYZE·target·확장 통계), 안 되면 후보를 줄인다.

"어제 밤에 계획이 바뀐 것 같은데 auto_explain을 안 켜뒀습니다." 지금 무엇을 할 수 있나요?함정힌트: 과거 계획은 못 살린다. 그렇다면 무엇으로 대신 증명하는가?

먼저 인정할 것 — 과거의 계획 텍스트는 복원할 수 없다. PostgreSQL에는 Query Store 같은 계획 이력 저장소가 없기 때문이다. 그러니 "계획 diff" 대신 "간접 증거 + 재현"으로 간다.

⑴ 간접 증거: pg_stat_statements 스냅샷이 있으면 blocks_per_call이 뛰었고 rows_per_call은 그대로임을 보이고, temp_blks_written이 함께 뛰었다면 정렬이 디스크로 흘렀다는 근거가 된다. 스냅샷조차 없으면 지금 시점부터라도 스냅샷을 시작한다(이것이 이 사고의 가장 흔한 후속 조치다).

⑵ 통계에서 역산: last_autoanalyze가 느려진 시각 직전인지, 문제의 값이 지금 MCV에 있는지, n_distinct가 실제와 자릿수로 다른지. 사고 ①이라면 "지금 MCV에 없다"가 결정적이다.

⑶ 재현: 실제로 느린 값을 로그에서 찾아 EXPLAIN (ANALYZE, BUFFERS)를 뜨고, 추정과 실측의 거리를 본다. 원인 ④가 의심되면 EXPLAIN (GENERIC_PLAN)과 PREPARE 여섯 번을 함께 돌린다. 후보 비교는 BEGIN; SET LOCAL enable_*; ... ROLLBACK;으로 한다.

그리고 이 답의 마지막 문장이 중요하다 — "이번 건은 간접 증거로 결론을 냈고, 같은 상황이 다시 오면 즉시 알 수 있도록 auto_explain 상시화와 pg_stat_statements 스냅샷, EXPLAIN 베이스라인 잡을 함께 넣었습니다." 진단 실패를 안전망 추가로 닫는 것이 이 문항에서 기대하는 태도다.

한 줄 요약
PostgreSQL 플래너는 통계·확장 통계·파라미터 값·비용 상수를 입력받아 후보 계획의 비용을 비교하는 함수라서, 코드도 쿼리도 안 바꿨는데 계획이 바뀌었다면 입력이 바뀌었거나(autoanalyze·통계 노후·n_distinct 오추정·MCV 목록 교체·제네릭 계획 전환), 후보가 바뀌었거나(인덱스 추가·삭제·INVALID), 함수가 바뀐 것(GUC·메이저 업그레이드 — pg_upgrade는 통계를 안 옮긴다)이다. 등호 조건의 추정은 세 갈래로 갈리는데 — 값이 MCV에 있으면 정확한 빈도, 없으면 "나머지 균등 분배", 값을 아예 모르면 1/n_distinct — 값 하나가 MCV 목록에서 밀려나는 순간 추정이 계단처럼 점프하는 것이 "어제까지 잘 되던 특정 값만 갑자기"의 정체이고, 제네릭 계획은 자기 추정이 커스텀 평균보다 싸 보일 때만 채택되므로 사고의 피해자는 늘 "평균보다 훨씬 흔한 값만 조회하는 화면"이다. PostgreSQL에는 index dive도, 힌트 문법도, INVISIBLE 인덱스도 없으므로 통계가 유일한 진실이고 대응 순서가 강제로 고정된다 — ANALYZE → statistics target → CREATE STATISTICS → 비용 파라미터 국소 교정 → 부분·복합 인덱스로 후보 단일화 → 최후에 pg_hint_plan(원인이 제네릭 계획이면 그 앞에 force_custom_plan). 진단은 느려진 시각 → 건당 읽은 블록 비교 → auto_explain 로그의 계획 diff → last_autoanalyze·pg_stats·문제의 값이 MCV에 있는지 확인 순서이며, 배포 없이 일어나는 변경이므로 EXPLAIN 베이스라인 잡(대표값과 최악값 두 벌로)·pg_stat_statements 스냅샷 알람·배치 끝 ANALYZE·업그레이드 런북의 vacuumdb --analyze-in-stages를 기계에 맡겨야 사용자보다 먼저 안다.
