대용량 유니크 채번 설계
"주문번호"와 "PK"는 다른 물건이고, PostgreSQL의 시퀀스는 AUTO_INCREMENT가 아니다

면접 질문: "유니크 채번(주문번호 등)을 대용량 트래픽에서 어떻게 설계하나요? (Auto Increment 한계, Snowflake, 채번 테이블, UUID v7 비교)"

핵심 관전 포인트 — 채번 질문의 정답은 방식 이름이 아니라 요구사항을 쪼개는 순서다. 먼저 내부 PK(조인·인덱스의 축)와 외부 주문번호(고객·CS·정산이 부르는 업무 식별자)를 분리한다 — 두 식별자에 걸리는 요구가 다르기 때문이다. 내부 PK는 ① 작고(8바이트) ② 단조 증가해야 하는데, PostgreSQL에서 이 두 원칙의 근거는 클러스터드 인덱스가 아니다. 테이블은 힙이라 랜덤 PK에 무관하고, 아픈 곳은 PK B-tree의 삽입 위치 · 자식 테이블의 FK 인덱스 · full_page_writes로 부푸는 WAL이다. 후보는 bigint GENERATED ALWAYS AS IDENTITY(시퀀스) 또는 Snowflake. PG의 시퀀스는 AUTO_INCREMENT와 결정적으로 다르다 — 테이블과 독립된 객체이고 트랜잭션 밖에서 동작해 nextval()을 INSERT 전에 미리 부를 수 있다. 그래서 "Auto Increment 한계" 넷 중 하나(INSERT 전 ID 미확보)는 PG에서 애초에 성립하지 않고 JPA 쓰기 지연 배치도 살아난다. 대신 비트랜잭션성의 대가로 빈 번호가 정상이고, CACHE가 세션별 블록을 선점해 발급 순서와 값의 대소가 어긋나며, 다중 노드 충돌은 그대로 남는다. UUID는 네이티브 uuid 16바이트 — v4는 힙이 아니라 PK B-tree를 앓고, v7은 그 사슬을 끊지만 16바이트라는 계수는 남는다. 외부 주문번호는 채번 테이블(+블록 할당, UPDATE ... RETURNING, 별도 짧은 트랜잭션)로 업무 의미를 담되 유니크 제약을 최후 방어선으로 둔다. 그리고 각 방식이 내는 대가 — 시퀀스의 단일 노드 의존과 연속 번호 노출, 채번 테이블의 핫 로우 직렬화·죽은 튜플·재기동 시 구멍, Snowflake의 시계 역행·워커 ID 배포, UUID v7의 크기와 생성 시각 노출 — 를 얻는 것과 같은 호흡에 붙여야 고난이도 답이 된다.
  • 1
    방식 이름보다 먼저 요구를 쪼갠다 — "유니크"는 최소 조건일 뿐이고 실제 설계는 유일성 · 정렬성 · 분산 생성 · 노출 안전성 · 크기 · 업무 의미 여섯 성질 중 무엇을 어디까지 요구하느냐로 갈린다. 이 여섯은 서로를 배반하므로(정렬성↔노출 안전성, 크기↔업무 의미) 한 컬럼으로는 불가능하다 → 내부 PK와 외부 주문번호를 분리하는 것이 결론이다.
  • 2
    내부 PK는 8바이트 단조 증가 — 단, PG에서 그 근거는 클러스터드 인덱스가 아니다 — 테이블은 힙이라 PK가 무엇이든 새 행은 끝 페이지로 간다. 대신 삽입 위치를 값이 결정하는 구조가 남아 있다 — PK B-tree와 자식 FK 인덱스. 무작위 키는 여기서 캐시 미스 → 페이지 분할 → 적재율 저하 → 랜덤 I/O → full_page_writes로 INSERT 한 건에 8KB FPI의 사슬을 돈다.
  • 3
    단일 DB면 시퀀스가 여전히 첫 정답이고, 분산이 실제 요구면 Snowflake 또는 UUID v7이다 — PG 시퀀스는 테이블 밖 독립 객체라 nextval()을 INSERT 전에 부를 수 있어 AUTO_INCREMENT의 한계 하나가 사라진다(JPA 배치 유지). 대가는 빈 번호 · CACHE의 순서 교차 · 단일 노드 의존. 외부 주문번호는 채번 테이블 + 블록 할당 + 유니크 제약으로 따로 만든다.

0. 질문 + 출제 의도

질문: "유니크 채번(주문번호 등)을 대용량 트래픽에서 어떻게 설계하나요? (Auto Increment 한계, Snowflake, 채번 테이블, UUID v7 비교)"

PostgreSQL 기준 재해석: "PG의 시퀀스(GENERATED ALWAYS AS IDENTITY)는 어디까지 되고 어디서 막히는가 — 비트랜잭션성·CACHE·다중 노드 충돌을 포함해 — 그리고 Snowflake·채번 테이블·uuid(v4/v7)와 어떻게 조합하는가?"

출제 의도: rationale의 표현 그대로 — "Auto Increment의 한계(샤딩, 노출 위험)에서 출발해 Snowflake/UUID v7의 트레이드오프(정렬성, 인덱스 지역성)까지 — 작은 주제 하나에 분산 시스템 지식이 압축돼 있어 깊이 측정에 효율적이다."

채점 지점 ⑴ 메커니즘
각 방식이 "왜" 빠르고 "왜" 막히는지를 저장 구조(힙 + B-tree + WAL)와 분산 시스템(시계·조율) 두 층으로 설명하는가.
채점 지점 ⑵ 같은 축의 비교
4방식을 같은 축으로 비교하고 각각에 대가를 붙이는가. 얻는 것만 말하면 절반이다.
채점 지점 ⑶ 착지
"주문번호"라는 단어에 숨은 두 요구(내부 식별 vs 외부 노출)를 분리해 설계로 착지시키는가.
이 페이지가 겨냥하는 네 지점 ① 비용을 이름 붙은 사슬로 — "UUID는 인덱스에 안 좋다"에서 멈추지 않는다. 2·3·8절에서 고리 하나씩 이어 붙인다.
② 트레이드오프를 양면으로 — 5~8절 각 절 말미에 대차대조표(얻는 것 / 내는 것)를 한 쌍으로 붙인다.
③ 안전망을 코드로 고정 — "조심하면 된다"가 아니라 시계 역행 감지 · 워커 ID 임대 · 유니크 제약 + 새 트랜잭션 재시도 · 동시성 테스트 · 소진 감시로(10절).
④ 목록 인출 — 여섯 성질 · 비교표 6축 · 선택 기준 6가지 · 빈 번호 4경로 · v4 사슬 6고리를 세트로 꺼낸다(11절 인출 카드).
옆 문항과의 경계 클러스터드 vs 세컨더리 인덱스(03)는 PG의 힙 구조에서 PK 설계 2원칙(작게·단조 증가)을 도출하고 "곱셈 계수가 FK 인덱스로 자리를 옮겼다"는 계산을 다뤘다 — 이 문서는 그 원칙을 전제로 "어떤 채번 방식이 그 원칙을 만족하며 분산까지 확장되는가"를 다룬다. 대량 INSERT와 JDBC batch(03-jpa-orm/21)는 IDENTITY 전략이 쓰기 지연을 무력화하는 메커니즘과 allocationSize를 다뤘다 — 이 문서는 그 무력화를 PG에서는 시퀀스 전략으로 피할 수 있다는 점을 5절에서 짚는다.

1. 요구를 쪼갠다 — 여섯 성질, 그리고 두 식별자

"주문번호를 어떻게 채번하나요"에 방식 이름부터 대면 감점이다. "유니크"는 최소 조건일 뿐이고, 실제 설계는 아래 여섯 성질 중 무엇을 어디까지 요구하느냐로 갈린다. 지금은 성질만 세운다 — 각 성질이 왜 비용이 되는지는 2절부터, 어느 방식이 그 성질을 만족하는지는 5~8절에서 다룬다.

암기 대상 ① — 채번 요구의 여섯 성질 (2 · 2 · 2로 묶어서 외운다)

공통 요구 — 유일 · 분산
두 식별자 모두가 원한다
① 유일성 — 전역에서 절대 겹치지 않는가. 겹치면 어디서 걸러지는가.
③ 분산 생성 가능성 — DB 한 대에 묻지 않고 만들 수 있는가. 그리고 INSERT 전에 ID를 알 수 있는가 — PG에서는 이 둘이 갈라진다(5절).
내부 PK가 원함 — 정렬 · 크기
기계가 원하는 성질
② 정렬성(시간 순) — 나중에 만든 ID가 더 큰가. 즉 "값의 대소"와 "만들어진 순서"가 같은 방향인가.
⑤ 크기 — 8바이트인가 16바이트인가 36바이트 문자열인가.
외부 번호가 원함 — 노출 · 의미
사람과 업무가 원하는 성질
④ 노출 안전성 — 외부에 보여도 다음 번호·총량·증가율·생성 시각이 새지 않는가.
⑥ 업무 의미(가독성) — 날짜·채널 코드·체크 디짓을 담아 사람이 읽고 불러줄 수 있어야 하는가.

여섯 개를 순서 없이 외우면 면접장에서 두세 개가 빠진다. "공통 둘 → 안쪽 둘 → 바깥 둘"이라는 자리 순서로 외우면 하나만 떠올려도 나머지가 따라오고, 그대로 "그래서 분리한다"는 결론까지 이어진다.

이 여섯을 놓고 보면 한 컬럼으로 전부 만족시키는 방식은 없다는 게 바로 보인다. 성질끼리 서로를 배반하기 때문이다.

면접 첫 문장은 이것이다 — "채번은 방식 선택 문제가 아니라 식별자 분리 문제입니다. 먼저 내부 PK와 외부 주문번호를 나눕니다."

2. 비용의 단위 — 페이지 · 워킹셋 · WAL의 FPI

성질을 세웠으니 이제 비용의 단위를 정해야 한다. "UUID는 느리다"가 아니라 "UUID는 무엇을 몇 번 더 하게 만드는가"로 말하려면, 그 "무엇"의 이름이 먼저 있어야 한다. 이 문서 전체를 관통하는 비용 모델이라 여기서 한 번 못 박는다. 앞의 셋은 DB 공통이고, 마지막 하나는 PostgreSQL 고유 항목이다.

페이지(page) — 비용을 세는 최소 단위
DB가 디스크와 메모리 사이에서 데이터를 주고받는 최소 단위 덩어리. PostgreSQL은 8KB(8,192바이트)다. 8바이트짜리 bigint 하나만 필요해도 그 값이 든 8KB 페이지를 통째로 읽어 온다. 그래서 이 문서에서 "비싸다"는 말은 항상 페이지를 몇 장 만졌는가로 환산된다.
순차 I/O vs 랜덤 I/O — 같은 장수라도 값이 다르다
순차는 이웃한 페이지를 이어서 읽고 쓰는 접근이라 페이지당 비용이 작고, 랜덤은 흩어진 위치를 하나씩 찾아가므로 페이지마다 위치 이동 비용을 따로 낸다. PG 플래너의 비용 모델에 숫자로 박혀 있다 — random_page_cost 4.0 대 seq_page_cost 1.0. 랜덤 한 장을 순차 네 장만큼 비싸게 친다.
shared_buffers — 공급
PG가 디스크 페이지를 담아두는 고정 크기 메모리 캐시(기본 128MB, 운영에서는 대개 물리 메모리의 25% 안팎). 뒤에 OS 페이지 캐시가 한 겹 더 있는 이중 캐시다. 찾는 페이지가 여기 있으면 EXPLAIN (ANALYZE, BUFFERS)에 shared hit, 없으면 shared read(= 디스크 I/O)로 찍힌다.
워킹셋(working set) — 수요
어떤 부하를 처리하는 동안 실제로 손대는 페이지들의 집합. "테이블 전체 크기"가 아니라 "지금 이 작업이 반복해서 만지는 페이지들"이라는 점이 핵심이다. 100GB 테이블이라도 INSERT만 하는 부하의 워킹셋은 맨 끝 페이지 몇 장일 수 있다.
이 둘의 관계가 이 문서에서 가장 중요한 비선형성을 만든다 워킹셋이 shared_buffers 안에 들어가면 필요한 페이지가 거의 항상 메모리에 있어(shared hit) 응답 시간이 데이터 증가에 거의 둔감하다. 워킹셋이 캐시를 넘치는 순간, 만지는 페이지마다 캐시에 없을 확률이 높아지고(shared read = 디스크 랜덤 I/O), 새 페이지를 넣으려면 기존 페이지를 밀어내므로 서로가 서로를 쫓아낸다(캐시 오염). 성능은 선형이 아니라 계단식으로 무너진다 — 그래서 "조금 느려졌다"가 아니라 "어느 날 갑자기 못 쓰게 됐다"로 나타난다.

채번 방식이 워킹셋을 결정한다는 것이 이 문서의 첫 번째 축이다. 단조 증가 키는 항상 같은 자리(맨 끝)를 만지므로 워킹셋이 몇 페이지로 고정되고, 무작위 키는 매번 다른 자리를 만지므로 워킹셋이 인덱스 전체로 부푼다. 그리고 여기에 PG 고유 항목이 하나 더 붙는다.

2-1. WAL과 full_page_writes — PG 고유의 비용 축

WAL(Write-Ahead Log) 은 데이터 파일을 고치기 전에 "무엇을 어떻게 고칠 것인지"를 먼저 적어두는 로그다. 크래시가 나도 이 로그만 있으면 데이터 파일을 정합한 상태로 되돌릴 수 있다. 여기까지는 어느 DB나 비슷하다.

PG 고유 항목은 full_page_writes 다. 체크포인트(디스크에 변경분을 반영하는 정기 작업) 이후 어떤 페이지를 처음 건드릴 때는 변경분이 아니라 8KB 페이지 전체 이미지(FPI, Full Page Image) 가 WAL에 실린다. 쓰기 도중 전원이 끊겨 페이지가 반쯤만 쓰인 상태(torn page)가 돼도 통째 이미지로 덮어써 고칠 수 있게 하기 위해서다.

비유 — 서류 한 장을 고칠 때마다 "그 장 전체를 복사기에 올리는" 규칙 체크포인트 이후 어떤 서류를 처음 고칠 때는 그 장을 통째로 복사해 백업 상자에 넣어야 한다. 두 번째부터는 "3번째 줄을 이렇게 바꿈"이라는 메모 한 줄이면 된다. 그래서 같은 장을 계속 고치는 사람은 복사기를 한 번만 쓰고, 매번 다른 장을 고치는 사람은 고칠 때마다 복사기 앞에 선다. 고치는 양은 같은데 복사 비용이 수십 배 차이 난다 — 이것이 채번 방식이 WAL에 청구되는 방식이다.

3. PG에서 "정렬성"은 힙이 아니라 인덱스의 문제다

여기가 이 주제에서 가장 자주 오해되는 지점이라 한 절을 따로 쓴다.

MySQL/InnoDB를 기준으로 배운 사람은 "PK가 무작위면 테이블이 흩어진다"고 기억한다. InnoDB의 테이블은 PK로 정렬된 B-tree 그 자체(클러스터드 인덱스)라서 맞는 말이다. 그런데 PostgreSQL의 테이블은 힙(heap) 이다.

힙은 "정렬 규칙 없이 빈자리에 던져 넣는 저장 구조"다. PG는 새 행을 넣을 때 FSM(Free Space Map, 페이지별 여유 공간 지도)에게 "지금 여유 있는 페이지 아무거나"를 물어 그곳에 쓴다. 대개 파일 끝의 페이지다. 행의 PK 값이 1이든 999999든 f47ac10b-...든, 들어가는 자리는 똑같다.

이제 이 문서의 질문은 이렇게 바뀐다 — "이 채번 방식이 만드는 INSERT의 워킹셋은 몇 페이지이고, 그 INSERT는 WAL에 페이지 이미지를 몇 번 싣는가."

4. 크기 계수는 사라진 게 아니라 자리를 옮겼다

1절의 성질 ⑤(크기)도 엔진에 따라 청구서가 오는 자리가 다르다. 이것도 정면으로 계산해 두는 편이 낫다.

MySQL/InnoDB — PK 크기는 곱셈 계수였다

InnoDB의 세컨더리 인덱스는 리프에 "인덱스 키 + PK 값"을 담는다. 행의 물리 주소가 아니라 PK를 담는 이유는, 클러스터드 인덱스에서 행이 이사를 다녀도 PK는 안 변하기 때문이다. 그래서 세컨더리 인덱스가 5개면 PK 값이 5벌 복제된다.

PostgreSQL — 그 곱셈이 없다

PG의 인덱스 리프에는 PK가 아니라 TID(Tuple ID, 6바이트 — 힙의 몇 번째 페이지 몇 번째 슬롯인지)가 들어간다. 인덱스가 몇 개든 PK 크기는 그 인덱스들에 영향을 주지 않는다.

그런데 계수가 사라진 게 아니라 자리를 옮겼다. 부모의 PK 값을 그대로 들고 있어야 하는 곳이 하나 더 있기 때문이다 — 자식 테이블의 FK 컬럼, 그리고 그 컬럼에 건 인덱스. orders.id가 16바이트가 되면 order_items.order_id도 16바이트가 되고, payments.order_id도, shipments.order_id도 그렇게 된다.

"PG 13의 중복 제거(deduplication)가 해결해 주지 않나요?" 함정 PG 13부터 B-tree는 중복 키를 posting list 하나로 묶는 중복 제거를 하지만, 유니크한 무작위 키에는 도움이 안 된다 — 중복이 없으니 묶을 것도 없다. 이 최적화는 "같은 값이 여러 번 나오는 인덱스"(예: 상태 컬럼)를 위한 것이다.

5. 방식 ① 시퀀스 / IDENTITY — DB 한 대의 카운터, 단 테이블 밖에 있는 객체

메커니즘. PG의 자동 증가는 컬럼의 속성이 아니라 독립된 시퀀스 객체다. 표준 문법인 GENERATED ALWAYS AS IDENTITY를 쓰면 컬럼에 딸린 시퀀스가 자동으로 만들어지고 소유권까지 묶인다.

good 신규 설계의 기본형 (PG 10+ 표준 문법)
CREATE TABLE orders (
    id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at timestamptz NOT NULL DEFAULT now()
);

-- 구식: serial / bigserial — "bigint + 시퀀스 + DEFAULT nextval()"의 축약.
--   소유권·권한·DDL에서 잔손질이 필요해 신규 설계에서는 IDENTITY를 쓴다.

-- 앱이 값을 미리 받아 명시적으로 넣어야 한다면(아래 '반전') 독립 시퀀스로 둔다
CREATE SEQUENCE orders_id_seq AS bigint;
ALTER TABLE orders ALTER COLUMN id SET DEFAULT nextval('orders_id_seq');

함정 ① — ALWAYS와 BY DEFAULT를 잘못 고르면 이관 스크립트가 통째로 막힌다

GENERATED ALWAYS는 앱이 id를 직접 넣는 INSERT를 거부한다(OVERRIDING SYSTEM VALUE를 붙여야 통과). 데이터 이관이나 JPA 시퀀스 전략처럼 앱이 값을 들고 들어오는 구조라면 GENERATED BY DEFAULT AS IDENTITY이거나 독립 시퀀스여야 한다.

판별식 — "이 컬럼에 앱이 값을 넣을 일이 한 번이라도 있는가?" → 있으면 BY DEFAULT 또는 독립 시퀀스

5-1. 왜 순차 I/O가 되는가 — 사슬로

새 PK가 항상 최댓값→ 삽입 위치 = 맨 오른쪽 리프 한 장→ 방금 만졌으니 캐시 히트 100%→ 페이지가 차면 반반 분할이 아니라 오른쪽에 이어 붙이기
같은 리프를 수백 번 → FPI는 체크포인트당 1회→ 힙은 애초에 PK와 무관(FSM이 끝 페이지)→ shared_buffers가 테이블보다 훨씬 작아도 INSERT 처리량 유지

접수창구 비유 — 서류를 늘 서류철 맨 뒤에 끼우니 서류철을 열어볼 필요도, 중간을 벌릴 필요도, 통째로 복사기에 올릴 필요도 없다. (fillfactor는 B-tree 기본 90이고, 중간 삽입만 반반 분할이다 — 끝 삽입은 최적화되어 있다.)

5-2. 반전 — PG에서는 "INSERT 전에 ID를 알 수 없다"가 성립하지 않는다

여기가 이 문항을 MySQL 기준으로 외운 사람과 갈리는 지점이다. 시퀀스는 테이블 밖의 독립 객체이므로 INSERT와 무관하게 nextval()을 먼저 부를 수 있다.

good PG에서 배치를 살리는 JPA 매핑
// 시퀀스에서 50개씩 받아 메모리에서 나눠 쓴다
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE,
                generator = "orders_seq")
@SequenceGenerator(name = "orders_seq",
                   sequenceName = "orders_id_seq",
                   allocationSize = 50)
private Long id;
good 짝이 되는 DDL — 반드시 같은 PR에서 함께 바꾼다
-- INCREMENT BY 가 allocationSize 와 같아야 한다
CREATE SEQUENCE orders_id_seq AS bigint
    INCREMENT BY 50;

-- 불일치하면? 하이버네이트는 "받은 값이 50개 블록의 끝"
-- 이라고 가정하고 값을 나눠 주므로
-- 인스턴스 두 대가 같은 번호를 발급한다.

함정 ② — allocationSize = 50인데 DDL이 INCREMENT BY 1 가산점

하이버네이트는 nextval()이 돌려준 값을 "내가 쓸 블록의 경계"로 해석해 그 값으로부터 allocationSize만큼을 메모리에서 나눠 준다. DB가 실제로는 1씩만 밀고 있으면 두 인스턴스의 블록이 겹치고, 같은 번호가 두 번 발급된다. 하이버네이트 6에는 이 불일치를 기동 시 알려주는 설정(hibernate.id.sequence.increment_size_mismatch_strategy)이 있지만 기본 동작은 버전마다 다르므로, DDL과 allocationSize를 같은 PR에서 함께 바꾸는 규칙으로 고정하는 편이 안전하다.

증상이 "PK 중복"으로 나타나는데 원인은 스키마와 코드의 숫자 불일치다 — 로그만 봐서는 절대 안 잡힌다

5-3. 비트랜잭션성 — 빈 번호는 버그가 아니라 성질이다

nextval()은 트랜잭션 밖에서 동작한다. 롤백해도 소모된 값은 돌아오지 않고, 두 세션이 동시에 불러도 서로 기다리지 않는다(그래서 빠르다).

BEGIN;
SELECT nextval('orders_id_seq');   -- 101
ROLLBACK;
SELECT nextval('orders_id_seq');   -- 102  ← 101은 영원히 비어 있다
왜 이렇게 만들었는가 — 이유까지 말하면 답이 한 단계 올라간다 nextval()이 트랜잭션을 따랐다면, 값을 받은 세션이 커밋할 때까지 다음 세션은 기다려야 한다 — 시퀀스 자체가 6절의 핫 로우가 되는 것이다. PG는 그 직렬화를 피하려고 연속성을 포기하는 쪽을 골랐다. 즉 빈 번호는 성능을 산 대가다. 비유하면 은행 번호표 기계 — 번호표를 뽑고 그냥 나가버려도 기계는 그 번호를 되돌려주지 않는다. 되돌려주려면 모든 손님이 창구를 나설 때까지 기계가 멈춰 서 있어야 하기 때문이다.

암기 대상 ③ — 빈 번호가 생기는 네 경로 "롤 · 업 · 캐 · 크"

롤 — 롤백 · 에러
소모된 값은 돌아오지 않는다
업 — UPSERT
ON CONFLICT DO NOTHING이면 행이 안 들어가도 DEFAULT의 nextval()은 먼저 평가되어 소모 (대량 UPSERT의 단골)
캐 — CACHE 폐기
세션이 선점한 블록의 잔여분이 세션 종료로 폐기
크 — 크래시
PG는 시퀀스 값을 일정 개수 단위로 미리 WAL에 기록하므로 재시작 시 번호가 앞으로 건너뛴다
결론 — 시퀀스로는 gapless(빈 번호 없음)를 보장할 수 없다. 유실 판단은 번호 연속성이 아니라 별도 대사(reconciliation)로 한다

⑴ 샤딩

-- 노드 2:  CREATE SEQUENCE orders_id_seq INCREMENT BY 2 START WITH 2;

복제·이관에서 시퀀스가 사라지는 사고 가산점 스트리밍(물리) 복제는 바이트 단위 복제라 시퀀스 상태까지 그대로 따라오지만, 논리 복제는 시퀀스를 복제하지 않는다. 논리 복제로 새 클러스터에 이관하고 전환할 때 setval()로 시퀀스를 앞당겨 놓지 않으면, 새 프라이머리가 1번부터 다시 발급해 PK 중복 폭탄이 터진다. 전환 체크리스트에 "모든 시퀀스 setval 확인"을 넣는 것이 정석이다.

5-6. 노출 위험과 타입 고갈

노출 위험. 값이 연속이라 외부에 보이면 ⑴ 하루 주문량·증가율이 그대로 새고 ⑵ /orders/10231 다음은 10232라고 누구나 추측할 수 있어 권한 검사가 한 곳이라도 빠지면 남의 주문이 열린다(IDOR — Insecure Direct Object Reference, "식별자를 바꿔 넣으면 남의 자원이 열리는" 취약점). 이건 시퀀스의 결함이 아니라 내부 PK를 외부에 그대로 노출한 설계의 결함이다 — 그래서 분리가 결론이다.

MySQL 대조 — 같은 자리에 다른 어휘가 있다 MySQL의 AUTO_INCREMENT는 테이블의 속성이라 값을 미리 받을 수 없고(그래서 "INSERT 전 ID 미확보"가 진짜 한계다), 카운터가 메모리에 있어 MySQL 8.0 이전에는 재기동 시 MAX(id)+1로 재계산돼 지웠던 끝 번호가 재사용되는 함정이 있었다(8.0부터 영속). 동시 삽입 시에는 innodb_autoinc_lock_mode 설정에 따라 짧은 뮤텍스 또는 테이블 수준 AUTO-INC 락을 잡는다. PG는 시퀀스가 별도 객체라 이 락 모드 논의 자체가 없고, 대신 비트랜잭션성·CACHE·setval이라는 다른 어휘를 쓴다.

  • 논리 복제·이관 시 setval 누락 사고, int로 고르면 고갈
언제 정답인가 — DB가 한 대(+레플리카)이고 ID를 외부에 직접 노출하지 않는다면 여전히 첫 번째 정답
"요즘은 다 Snowflake 쓰지 않나요"에 흔들리지 않는 것이 시니어다 — 인프라를 늘리지 않고 되는 일을 늘려서 하지 않는다.

6. 방식 ② 채번 테이블(+블록 할당) — 핫 로우를 어떻게 식히는가

메커니즘. id_sequences(seq_name, next_val) 같은 테이블에 이름별 카운터 행을 두고, 채번할 때마다 그 행을 UPDATE ... SET next_val = next_val + 1로 밀어 값을 받는다. 날짜별로 행을 따로 두면 20260901-000123처럼 매일 1번부터 다시 시작하는 업무 번호를 만들 수 있다.

먼저 경계를 긋는다 — PG에서 이 방식의 존재 이유는 "분산"이 아니다 MySQL에서는 채번 테이블이 "여러 앱 인스턴스가 INSERT 전에 ID를 받는" 유일한 길이었지만, PG에서는 시퀀스가 이미 그 일을 한다(5절). 그래서 PG에서 채번 테이블이 남는 자리는 딱 하나 — 시퀀스가 못 하는 포맷 요구다. 날짜별 리셋, 채널별 접두어, 체크 디짓처럼 "값 자체에 업무 의미를 담아야 하는" 외부 식별자. 이 경계를 먼저 말하고 들어가야 "옛날 패턴을 습관으로 쓴다"로 들리지 않는다.

6-1. 왜 병목이 되는가 — 핫 로우 사슬

이 사슬을 "성능 저하"나 "락 경합" 한 단어로 뭉뚱그리지 않는다. 고리를 하나씩 이어 붙인다.

모든 요청이 같은 한 행을 UPDATE→ 튜플 헤더 xmax에 배타 락 표시→ 문장이 끝나도 안 풀리고 커밋까지 유지→ 주문 처리 전체 길이만큼 다음 주문이 줄을 선다
처리량 상한 = 1 / 트랜잭션 한 건의 길이→ 대기자가 커넥션(= OS 프로세스)을 쥔 채 대기→ 커넥션 풀 고갈 → 채번과 무관한 API까지 지연→ 락 대기 + 데드락

6-2. PG에는 고리가 하나 더 붙는다 — 죽은 튜플과 HOT

PG의 UPDATE는 제자리 갱신이 아니라 새 튜플 버전을 만들고 옛 버전을 죽은 튜플로 남기는 것이다. 초당 수천 번 갱신되는 채번 행은 그 페이지에 죽은 튜플을 계속 쌓고, autovacuum이 추격에 실패하면 페이지가 부풀어 한 행 읽는 데 여러 페이지를 훑게 된다.

다행히 채번 테이블은 HOT(Heap-Only Tuple) 업데이트 조건을 만족한다. HOT은 "바뀐 컬럼이 어떤 인덱스에도 들어 있지 않고, 새 버전이 같은 페이지 안에 들어갈 자리가 있으면, 인덱스를 하나도 건드리지 않고 힙 안에서만 새 버전을 만드는" 최적화다. 채번 테이블에서 바뀌는 next_val은 어떤 인덱스에도 없으므로(인덱스는 seq_name PK뿐) 조건 절반은 이미 충족이고, 남은 조건은 "같은 페이지에 자리가 있는가"뿐이다.

good 그래서 처방이 하나 더 생긴다 — fillfactor를 낮춰 새 버전 자리를 미리 비워 둔다
CREATE TABLE id_sequences (
    seq_name text   PRIMARY KEY,
    next_val bigint NOT NULL
) WITH (fillfactor = 70);      -- 같은 페이지 안에 새 버전 자리를 남긴다 → HOT 유지

-- 확인: HOT 비율이 떨어지면 인덱스까지 갱신되고 있다는 뜻
SELECT relname, n_tup_upd, n_tup_hot_upd, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables WHERE relname = 'id_sequences';

암기 대상 ⑤ — 채번 테이블 처방 세 가지는 세트로 꺼낸다

① 짧은 트랜잭션
REQUIRES_NEW로 분리하고 UPDATE ... RETURNING 한 문장으로 값을 받는다 — SELECT ... FOR UPDATE를 쓰면 조회와 갱신 사이의 경쟁 구간이 생기는데, RETURNING은 그 구간 자체를 없앤다 가산점
② 블록 할당 (hi/lo)
한 번에 N개(예: 500)를 선점하고 나머지는 인스턴스 메모리에서 배분 → 방문 횟수 1/N. JPA @TableGenerator + allocationSize가 이 방식이고 PG 시퀀스의 CACHE도 원리가 같다
③ fillfactor 70
HOT 업데이트를 유지해 죽은 튜플·인덱스 갱신·autovacuum 부담을 줄인다. n_tup_hot_upd 비율로 검증

①과 ②는 다른 것을 줄인다 — ①은 락을 쥐는 시간을, ②는 락을 잡는 횟수를 줄인다. 그래서 둘 다 해야 한다. ③은 PG에서만 붙는 고리다.

bad 주문 트랜잭션 안에서 채번 행을 잡는다
@Transactional
public Order place(PlaceOrderCommand cmd) {
    long seq = jdbc.queryForObject(
        "SELECT next_val FROM id_sequences "
      + "WHERE seq_name = 'order' FOR UPDATE", Long.class);
    jdbc.update("UPDATE id_sequences SET next_val = ? "
              + "WHERE seq_name = 'order'", seq + 1);

    // ↓ 재고 차감·결제 승인(외부 HTTP)·주문 저장이 끝나
    //   커밋될 때까지 다른 모든 주문이 id_sequences 행
    //   앞에서 대기한다 → 커넥션 풀 고갈로 번진다
    inventory.reserve(cmd);
    payment.approve(cmd);
    return orderRepository.save(Order.of(cmd, seq));
}
good 블록 할당 + 별도 짧은 트랜잭션 (한 문장·한 왕복)
@Component
public class SequenceBlockAllocator {

    // 행이 없으면 만들고, 있으면 블록만큼 밀어서,
    // 시작값을 한 문장으로 돌려받는다
    private static final String ALLOCATE = """
        INSERT INTO id_sequences (seq_name, next_val)
        VALUES (?, ?)
        ON CONFLICT (seq_name)
        DO UPDATE SET next_val =
             id_sequences.next_val + EXCLUDED.next_val
        RETURNING next_val - ? AS block_start
        """;

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public long allocate(String name, int blockSize) {
        return jdbc.queryForObject(ALLOCATE, Long.class,
                   name, blockSize, blockSize);
        // 최초 삽입이면 블록 [0, blockSize)
        // 충돌이면   블록 [기존, 기존 + blockSize)
    }
}

ON CONFLICT가 "행이 없으면 만들고 있으면 민다"를 한 문장·한 왕복으로 끝내는 것이 PG판의 핵심이다. MySQL 예제에서 INSERT IGNORE → 재귀 호출로 풀던 자리가 통째로 사라졌다.

6-3. 블록 할당이 새로 지불하는 대가 — 반드시 같은 호흡에

재기동하면 구멍이 난다
500개를 선점하고 120개 쓴 뒤 재배포되면 380개는 버려진다. 인스턴스가 10대면 배포 한 번에 최대 수천 개가 빈다(10대 × 최대 499개 ≈ 5,000개). "주문번호는 연속이 아니다"를 정책으로 명문화해야 한다 — 회계·CS·정산이 "번호가 비었는데 주문이 유실된 것 아니냐"고 묻는 순간이 반드시 온다.
인스턴스 간 순서가 섞인다
A가 [0,500), B가 [500,1000)을 들고 있으면 시간상 나중인 A의 3번이 B의 501번보다 작다. "번호 순 = 시간 순"이 아니다 — 시간 순 정렬은 created_at으로 한다. (시퀀스 CACHE가 내는 대가와 정확히 같은 성질이다.)
가용성 결합점이 된다
그 행이 잠기거나 그 DB가 죽으면 채번이 멈춘다. 블록이 클수록 방문이 드물어 버티는 시간이 길어진다 — 블록 크기는 "재기동 시 버릴 수 있는 양"과 "DB 장애 시 버틸 시간"의 거래다.
연속성이 진짜 규제 요건이라면 이 방식을 쓸 수 없다 시니어 변별 일부 국가의 세금 계산서 일련번호처럼 gapless가 법적 요건이라면 블록 할당도, 시퀀스도 쓸 수 없다. 건별 채번 + 짧은 트랜잭션으로 돌아가 처리량을 포기해야 한다. gapless와 처리량은 맞바꾸는 관계라고 말하고, 이 선택을 ADR 한 장으로 남긴다고 덧붙이면 요구를 비용으로 번역할 줄 아는 것으로 들린다.
MySQL 대조 — RETURNING이 없는 자리에 세션 변수 트릭이 있다 MySQL에는 RETURNING이 없어(최근 MariaDB 계열 제외) UPDATE id_sequences SET next_val = LAST_INSERT_ID(next_val + ?) 뒤에 SELECT LAST_INSERT_ID()를 붙이는 관용구로 같은 일을 한다. 세션 변수를 경유하는 트릭이라 커넥션 풀·프록시에서 세션이 바뀌면 깨질 수 있는데, PG의 RETURNING은 문장 자체가 값을 돌려주므로 그 위험이 없다.

얻는 것

  • 업무 의미 자유 — 날짜별 리셋 · 채널 접두어 · 체크 디짓
  • INSERT 전 ID 확보
  • DB 외 인프라 0, 포맷을 원하는 대로

내는 것

  • 핫 로우(분리 트랜잭션 + 블록 + fillfactor로 완화)
  • 죽은 튜플 · autovacuum 부담
  • 재기동 시 구멍, 인스턴스 간 순서 교차, 채번 테이블 가용성 의존
  • 연속 노출 시 추측 위험은 그대로. 그리고 PG에서는 "분산 생성"이 더 이상 이 방식만의 장점이 아니다

7. 방식 ③ Snowflake — 시계와 워커 ID로 조율 없이 만든다

메커니즘. 64비트 정수 하나를 세 조각으로 나눈다(트위터가 공개한 설계라 이 이름으로 불린다). 각 서버가 자기 시계 + 자기 워커 ID + 같은 ms 안의 카운터로 로컬에서 만들므로 DB 왕복도, 서버 간 합의도 없다.

7-1. 왜 PG의 PK로도 좋은가

시간이 상위 비트→ 새 ID는 거의 항상 PK B-tree 오른쪽 끝 근처→ 섞임은 맨 끝 페이지 몇 장 안에서만→ 워킹셋·FPI 수가 시퀀스와 거의 같다

크기도 8바이트라 4절에서 계산한 자식 테이블 FK 컬럼·FK 인덱스의 계수가 IDENTITY와 동일하다. 즉 분산 생성을 얻으면서 순차 I/O와 WAL 효율을 거의 포기하지 않는다. 이것이 Snowflake가 대용량에서 표준 답이 된 이유다.

비유 — 본사에 전화하지 않는 지점 발급 번호 모든 지점이 본사(=DB)에 전화해 번호를 받아 오는 방식이 시퀀스라면, Snowflake는 각 지점이 "오늘 시각 + 우리 지점 번호 + 오늘 우리 지점의 몇 번째"로 스스로 번호를 만드는 방식이다. 전화가 필요 없으니 본사가 죽어도 번호는 나오고, 지점을 늘려도 본사 회선이 병목이 되지 않는다. 대신 두 가지를 지점이 직접 책임져야 한다 — 지점 시계가 정확할 것, 그리고 두 지점이 같은 지점 번호를 갖지 않을 것. 그 둘이 아래의 두 의존이다.

7-2. 어디서 위험한가 — 두 가지 의존

⑴ 시계 의존

유일성이 "같은 워커에서 시간은 뒤로 가지 않는다"에 걸려 있다. NTP(Network Time Protocol, 서버 시계를 표준 시각에 맞추는 프로토콜)가 시계를 뒤로 맞추거나, VM 마이그레이션·절전 복귀로 시계가 튀면 이미 발급한 ms로 되돌아가 같은 ID를 다시 만들 수 있다.

대응 — 발급기가 마지막 발급 시각을 기억하고 역행을 감지한다. 작은 역행(수 ms)은 기다리고, 큰 역행은 발급을 거부한다(10절 코드). 운영 쪽 짝은 NTP를 step이 아니라 slew로 설정하는 것.

⑵ 워커 ID 배포

두 서버가 같은 워커 ID를 들면 같은 ms에 같은 ID가 나온다. 오토스케일링·컨테이너 환경에서 "설정 파일에 1, 2, 3 적어두기"는 배포 한 번에 무너진다.

대응 — 워커 ID는 중앙에서 유일하게 임대한다. DB 테이블에 기동 시 INSERT해 받은 값(10절), K8s StatefulSet의 순번, ZooKeeper 순차 노드, Redis 임대 + 하트비트 등. 어느 것이든 "프로세스가 죽으면 회수, 살아 있으면 갱신"이 있어야 재사용 충돌이 없다.

7-3. 그 밖의 대가

생성 시각이 값에 드러난다
상위 41비트를 풀면 ms 단위 생성 시각이 나오고, 시퀀스 비트로 "그 ms에 몇 건"도 어느 정도 읽힌다. 총량 추측은 연속 번호보다 훨씬 어렵지만 "언제 만들었는지도 숨겨라"는 요건이면 부적합.
전역 순서는 ms 단위 근사다
워커 간 시계가 몇 ms 어긋나면 나중에 만든 ID가 더 작을 수 있다. "ID 순 = 정확한 시간 순"으로 커서 페이지네이션을 짜면 경계에서 건너뛰기가 생긴다.
에포크를 한 번 정하면 바꿀 수 없다
41비트는 에포크로부터 약 69년. 에포크를 바꾸면 기존 ID보다 작은 값이 새로 나와 정렬성이 깨진다.
업무 의미는 없다
사람이 읽거나 불러줄 수 없다. 주문번호로 고객에게 안내할 수 없다 → 외부 식별자는 따로 필요하다.

함정 ③ — JSON 직렬화에서 끝자리가 조용히 반올림된다 가산점

JavaScript 안전 정수 한계
2^53 − 1 = 9,007,199,254,740,991 → 16자리
오늘 발급한 Snowflake ID
2025년 에포크 기준 (경과 ms) << 22 ≈ 2.2 × 10^17 → 18자리

브라우저가 파싱하면서 끝자리가 조용히 반올림된다 — 에러가 아니라 값이 살짝 달라지는 형태라 더 위험하다. 조회는 되는데 "가끔" 없는 주문이 되는 식으로 나타난다. API 응답에서는 문자열로 내보내야 한다.

얻는 것

  • 8바이트, 거의 단조 증가(순차 I/O·FPI 효율 유지)
  • 조율 없는 분산 생성, INSERT 전 ID 확보, DB 왕복 0
  • 초당 워커당 약 410만 개

내는 것

  • 시계 역행 감지 의무, 워커 ID 임대 인프라
  • 생성 시각 노출, ms 단위 근사 순서
  • 에포크 고정(69년 · 1,024대 상한), 문자열 직렬화 필요
  • 업무 의미 없음

8. 방식 ④ UUID — v4가 아픈 곳은 힙이 아니라 PK B-tree다

8-1. 먼저 저장 타입 — 이건 논쟁거리가 아니라 전제다

PG에는 uuid 타입이 있다 — 16바이트 고정, 비교는 바이트 비교다. 문자열로 저장하면 varchar(36)은 36바이트에 더해 비교가 collation(문자 정렬 규칙)을 타서 정수 비교보다 훨씬 비싸다.

bad 36바이트 + collation 비교
id varchar(36) PRIMARY KEY
-- 인덱스도 힙도 2배 이상으로 부푼다
-- v7을 써도 "크기" 문제는 v4와 똑같아진다
good 16바이트 네이티브
id uuid PRIMARY KEY DEFAULT gen_random_uuid()
-- gen_random_uuid()는 v4 (PG 13+ 내장)
-- 드라이버가 java.util.UUID로 그대로 매핑한다

8-2. v4가 왜 문제인가 — 이 문서에서 가장 중요한 사슬

UUID v4는 128비트 중 대부분이 난수다. PG에서 이 값을 PK로 쓰면 힙은 멀쩡한데 PK B-tree가 앓는다. 3절의 "힙은 자리를 고를 수 있고 B-tree는 못 고른다"가 여기서 청구서로 돌아온다.

암기 대상 ⑥ — v4 사슬 여섯 고리 "무 · 캐 · 분 · 적 · 랜 · 왈"

무작위 삽입 위치→ 캐시 미스 (쓰기가 랜덤 읽기를 부른다)→ 페이지 반반 분할
적재율 저하 (인덱스 bloat)→ 논리/물리 순서 어긋나 범위 스캔 랜덤화→ WAL FPI 증폭 (왈)

"인덱스가 깨진다", "정렬이 안 돼서 느리다"로 줄이면 기본 문항에서 했던 뭉뚱그리기의 반복이다. 고리를 다 말해야 한다. 관찰은 EXPLAIN (ANALYZE, WAL)의 WAL: fpi=와 pg_stat_wal(PG 14+)의 wal_fpi로 한다.

고리를 문장으로 이어 붙이면 이렇게 된다. 힙은 무관하다 — 새 행은 FSM이 가리키는 빈 공간(대개 파일 끝)에 들어가고, PK가 bigint든 uuid든 힙 쪽 워킹셋은 같다. 문제는 삽입 위치를 값이 결정하는 구조가 하나 남아 있다는 것 — PK B-tree, 그리고 그 값을 받는 자식 테이블의 FK 인덱스들.

가득 찬 페이지를 만났을 때 — 여기가 v4와 순차 키가 갈리는 결정적 지점
끝 삽입이면 오른쪽에 새 페이지를 이어 붙인다(적재율 거의 100%). 중간 삽입이면 반반 페이지 분할이다 — 쪼개고, 새 페이지를 파일 끝에 붙이고, 부모에 분리 키를 추가한다. 반쯤 빈 페이지가 전역에 쌓여 적재율이 평균 약 70%까지 떨어지고(분할 직후 50%, 채워지며 회복), 같은 엔트리 수에 페이지가 더 필요해지는 악순환이 된다.
그리고 논리 순서와 물리 순서가 어긋난다
새 페이지가 파일 끝에 붙으므로 키 순서(논리)와 파일 배치(물리)가 어긋나고, 범위 스캔이 순차에서 랜덤으로 전락한다. 2절의 random_page_cost 4.0 : seq_page_cost 1.0이 여기서 청구된다.

캐시 히트 확률이 어떻게 무너지는지 — 숫자로 (shared_buffers 8GB 가정, 4절의 262개/페이지로 계산)

같은 UUID PK라도 행 수가 늘면 어느 순간 계단을 밟는다 — 그 시점이 언제인지가 설계의 관전 포인트다
행 수 / PK 타입PK 인덱스 크기8GB 캐시 대비INSERT에 무슨 일이
uuid 1억 행약 3.13GB전부 들어간다히트율 사실상 100% — 이 구간에서는 문제가 안 보인다
uuid 5억 행약 15.6GB8 / 15.6 ≈ 51%INSERT 두 건 중 한 건이 디스크 랜덤 읽기를 유발
bigint 5억 행약 11.2GB8 / 11.2 ≈ 72%100%는 아니지만 계단에 도달하는 시점 자체가 훨씬 뒤
그래서 UUID v4의 사고는 "처음부터 느림"이 아니라 "어느 날 갑자기 못 쓰게 됨"으로 온다 — 인덱스가 캐시를 넘는 날

8-3. v7은 무엇을 고쳤는가

RFC 9562의 UUID v7은 앞 48비트를 Unix ms 타임스탬프로, 나머지를 버전·변형 비트와 난수로 채운다. 상위 비트가 시간이므로 삽입 위치가 오른쪽 끝 근처로 모이고, 위의 사슬이 한꺼번에 끊긴다.

-- PG 18부터는 서버 내장 함수가 있다
id uuid PRIMARY KEY DEFAULT uuidv7()

-- 그 이전 버전이면 애플리케이션에서 생성하거나 확장을 쓴다.
-- (DB 기본값으로 두면 'INSERT 전 ID 확보'라는 장점을 스스로 버리게 되므로,
--  분산 채번이 목적이라면 애초에 앱에서 만들어 넣는 편이 일관된다.)
무엇이 남는가 ① 16바이트
bigint의 두 배. 4절의 표대로 자식 FK 컬럼·FK 인덱스와 PK 인덱스 자체에서 적재율로 청구된다(페이지당 366 → 262).
② 문자열로 저장하면 최악
varchar(36)은 v4와 다를 바 없는 크기 문제를 그대로 되살린다 — uuid 타입이 전제다.
③ 생성 시각이 드러난다
Snowflake와 같다. 가독성·업무 의미도 0이라 주문번호로 고객에게 불러줄 수 없다.
④ JDK 표준은 v4다
UUID.randomUUID()는 v4다. v7은 별도 라이브러리나 직접 구현이 필요하다. 하이버네이트 6.x 계열은 @UuidGenerator로 시간 정렬 스타일을 지원하지만, 사용 중인 버전에서 지원 여부를 반드시 확인하고 쓴다.

얻는 것 (v7)

  • 조율·시계 역행·워커 ID 걱정이 없는 완전 무의존 분산 생성
  • 거의 단조 증가 → 순차 I/O·WAL 효율 회복
  • 표준(RFC 9562), 클라이언트 생성 가능, 총량 추측 불가
  • PG 네이티브 타입·드라이버 매핑(java.util.UUID 그대로)

내는 것 (v7)

  • 16바이트 계수 — PK 인덱스 + 자식 FK 컬럼·인덱스의 적재율 저하
  • 생성 시각 노출, 가독성 0
  • 저장 타입을 잘못 고르면(문자열) v4와 다를 바 없는 크기
  • JDK 표준 미지원
MySQL 대조 — "UUID PK가 나쁘다"의 강도는 엔진마다 다르다 MySQL의 InnoDB에서는 이 모든 일이 테이블 그 자체(클러스터드 인덱스의 리프 = 행 전체)에서 벌어지므로 랜덤 PK의 피해 규모가 "PK 인덱스 크기"가 아니라 "테이블 크기"다 — 훨씬 치명적이다. 게다가 MySQL에는 UUID 전용 타입이 없어 BINARY(16) + UUID_TO_BIN()/BIN_TO_UUID()로 손수 변환해야 하고, UUID_TO_BIN(uuid, 1)의 스왑 플래그는 시간 필드가 뒤에 있는 v1을 앞으로 돌리는 용도라 v7에 걸면 오히려 정렬성이 깨진다. PG는 uuid 타입과 드라이버 매핑이 그 수공업을 없앤다. 정리하면 — PG는 덜 아프지만 안 아픈 게 아니다.

9. 4방식 비교표 · 선택 기준 6가지

9-1. 먼저, 단조 증가에도 대가는 있다 가산점

트레이드오프를 양면으로 말하려면 "정렬성이 무조건 좋다"에서도 한 걸음 물러설 줄 알아야 한다. 모든 INSERT가 맨 오른쪽 리프 한 장에 몰리면 그 페이지의 버퍼 잠금을 두고 백엔드들이 경합한다 — pg_stat_activity에서 wait_event_type = 'LWLock'으로 관측되는 종류의 대기다. LWLock(Lightweight Lock)은 트랜잭션 락이 아니라 메모리 구조 하나를 아주 짧게 보호하는 내부 잠금이라 대개 마이크로초 단위로 끝나지만, 같은 페이지에 초당 수만 건이 몰리면 그 짧은 대기가 쌓여 병목이 된다.

그런데 완화책은 "랜덤 키로 돌아가기"가 아니다 — 이 판단이 시니어 변별점이다

맞는 완화책

해시 파티셔닝으로 끝 페이지를 여러 개로 나누거나, 샤딩한다. 끝 페이지가 N개가 되면 경합도 1/N이 된다.

틀린 완화책

랜덤 키로 돌아가는 것. 랜덤 키는 락 경합 대신 디스크 I/O와 WAL 볼륨을 지불하는데, 그쪽이 수천 배 비싸다.

마이크로초짜리 LWLock 경합을 피하려고 80배의 WAL(41MB/s vs 0.5MB/s)을 사는 것은 거래가 아니다

9-3. 선택 기준 6가지 — 이 순서로 되묻는다

1
생성 지점이 하나인가 여럿인가. DB 한 대(+레플리카)면 bigint IDENTITY로 충분하다 — 앱 인스턴스가 몇 대든 시퀀스 하나를 같이 쓴다. 샤딩·다중 리전·클라이언트 생성이 요구되면 Snowflake / UUID v7로 간다. PG에서 채번 테이블은 "분산"의 답이 아니라 "포맷"의 답이다.
2
INSERT 전에 ID가 필요한가. 이벤트를 먼저 발행하거나, 멱등 키로 쓰거나, JPA 쓰기 지연 배치를 살려야 하는 경우 — MySQL이면 여기서 AUTO_INCREMENT가 탈락하지만 PG는 시퀀스 전략으로 그대로 통과한다.
3
외부에 노출되는가, 노출되면 무엇이 새는가. 총량·증가율이 문제면 연속 번호가 탈락, 생성 시각까지 숨겨야 하면 시간 정렬 ID도 탈락 → 내부 PK와 별개의 무작위 외부 식별자가 필요하다.
4
업무 의미(날짜·채널·체크 디짓) 요구가 있는가. 있으면 어차피 PK와 분리해야 하고, 외부 식별자 쪽은 채번 테이블 + 포맷 조립이 답이다.
5
저장 구조를 정확히 반영했는가. "PG는 힙이라 UUID를 써도 된다"는 반쪽 명제다. 힙은 무관하지만 PK B-tree의 무작위 삽입 · 자식 FK 인덱스의 크기 계수 · full_page_writes로 부푸는 WAL은 그대로다. 허용 범위가 InnoDB보다 넓어진 것이지 비용이 사라진 것이 아니다.
6
팀이 감당할 의존성은 어디까지인가. Snowflake는 워커 ID 임대와 시계 규율이라는 상시 운영 의무를 사고, 채번 테이블은 DB 가용성에 묶이며, UUID v7은 의존성 대신 16바이트를 낸다. "인프라를 늘리지 않고 되는 일을 늘려서 하지 않는다"가 기본값이다.

10-1. 스키마와 JPA 매핑 — before / after

bad UUID v4 문자열 하나가 PK이자 주문번호
@Entity
@Table(name = "orders")
public class Order {
    @Id
    @Column(length = 36)
    private String id = UUID.randomUUID().toString();

    // ① 36바이트 키 + collation 비교
    //    — uuid 타입(16B, 바이트 비교)을 두고 최악을 골랐다
    // ② 삽입 위치 무작위 → PK B-tree 캐시 미스 → 페이지 분할
    //    → 적재율↓ → INSERT마다 랜덤 읽기
    //    → full_page_writes로 WAL에 8KB 이미지 한 장씩
    // ③ 자식 테이블 FK 컬럼·FK 인덱스가 전부 이 크기를 받는다
    //    (페이지당 엔트리 −28%)
    // ④ 이 값을 그대로 고객·CS에 노출 → 불러줄 수도,
    //    날짜를 읽을 수도 없다
    // ⑤ id가 이미 채워진 채 save() → Spring Data는
    //    "새 엔티티 아님"으로 보고 merge → SELECT가 한 번 더
}
good 내부 PK(bigint, 시간 순) + 외부 주문번호(업무 포맷, 유니크)
@Entity
@Table(name = "orders",
   uniqueConstraints = @UniqueConstraint(
       name = "uk_orders_order_no", columnNames = "order_no"))
public class Order {

    // 분산이 요구사항이면 Snowflake, 단일 DB면 시퀀스 전략.
    // PG에서는 어느 쪽이든 INSERT 전에 값이 손에 들어와
    // JDBC 배치가 살아 있다.
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE,
                    generator = "orders_seq")
    @SequenceGenerator(name = "orders_seq",
        sequenceName = "orders_id_seq", allocationSize = 50)
    private Long id;              // 8B, 조인·FK·인덱스의 축

    @Column(name = "order_no", nullable = false,
            updatable = false, length = 20)
    private String orderNo;      // 20260901-A-004821-7

    @Column(name = "created_at", nullable = false,
            updatable = false)
    private Instant createdAt;   // 시간 순 정렬·커서는 이 컬럼으로
}
good 짝이 되는 DDL — FK 인덱스는 직접 만든다
CREATE SEQUENCE orders_id_seq AS bigint INCREMENT BY 50;

CREATE TABLE orders (
    id          bigint      PRIMARY KEY DEFAULT nextval('orders_id_seq'),
    order_no    varchar(20) NOT NULL,
    customer_id bigint      NOT NULL,
    status      varchar(20) NOT NULL,
    created_at  timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uk_orders_order_no UNIQUE (order_no)   -- 최후 방어선
);
CREATE INDEX ix_orders_customer_created ON orders (customer_id, created_at DESC);

-- 자식 테이블: FK 컬럼에 인덱스를 "직접" 만든다.
-- PG는 FK 인덱스를 자동 생성하지 않으므로, 없으면 부모 DELETE/키 UPDATE마다
-- 자식 전체 스캔이다. PK를 작게 유지해야 하는 진짜 이유도 여기에 있다.
CREATE TABLE order_items (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id bigint NOT NULL REFERENCES orders(id)
);
CREATE INDEX ix_order_items_order_id ON order_items (order_id);

10-2. 안전망 ① Snowflake 발급기 — 시계 역행 감지와 시퀀스 고갈 대기

public final class Snowflake {
    private static final long EPOCH = 1_735_689_600_000L;  // 2025-01-01T00:00:00Z — 한 번 정하면 못 바꾼다
    private static final long WORKER_BITS = 10, SEQ_BITS = 12;
    private static final long MAX_WORKER = (1L << WORKER_BITS) - 1;   // 1023
    private static final long SEQ_MASK   = (1L << SEQ_BITS) - 1;      // 4095
    private static final long TOLERABLE_BACKWARD_MS = 5;    // 이 이하 역행은 기다리고, 초과는 거부

    private final long workerId;
    private long lastTs = -1L;
    private long seq = 0L;

    public Snowflake(long workerId) {
        // 범위를 벗어난 워커 ID는 비트가 겹쳐 다른 워커의 ID를 침범한다 — 기동 실패가 정답
        if (workerId < 0 || workerId > MAX_WORKER) throw new IllegalArgumentException("workerId out of range");
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long now = System.currentTimeMillis();

        if (now < lastTs) {                                   // ── 시계 역행 감지 ──
            long backward = lastTs - now;
            if (backward > TOLERABLE_BACKWARD_MS) {
                // 큰 역행: 같은 ms를 다시 쓰면 중복이므로 발급을 거부한다. 알람 대상.
                throw new ClockMovedBackwardsException(backward);
            }
            now = spinUntil(lastTs);                          // 작은 역행: 마지막 발급 시각까지 기다린다
        }

        if (now == lastTs) {
            seq = (seq + 1) & SEQ_MASK;                       // 같은 ms 안이면 카운터를 올린다
            if (seq == 0) now = spinUntil(lastTs + 1);        // 4096개를 다 썼다 → 다음 ms까지 대기
        } else {
            seq = 0L;                                         // ms가 바뀌었으니 카운터 리셋
        }
        lastTs = now;

        // 상위부터 자리를 맞춰 OR로 합친다: [타임스탬프][워커][시퀀스]
        return ((now - EPOCH) << (WORKER_BITS + SEQ_BITS)) | (workerId << SEQ_BITS) | seq;
    }

    private static long spinUntil(long targetTs) {
        long now;
        do { now = System.currentTimeMillis(); } while (now < targetTs);
        return now;
    }
}
ClockMovedBackwardsException은 삼키지 않는다 주문 API는 실패로 응답하고 알람이 울려야 한다. "조용히 새 ID를 만들어 내는" 발급기는 중복 ID를 만들어 내는 발급기다. 운영 쪽 짝은 NTP를 step이 아니라 slew로 맞추도록 설정하는 것이다 — step은 시계를 한 번에 목표 시각으로 점프시키고, slew는 클럭 속도를 미세하게 늦춰 천천히 수렴시킨다. 후자는 시계가 뒤로 "가지" 않는다.

@Component
public class OrderNoGenerator {
    private static final int BLOCK = 500;
    private final SequenceBlockAllocator allocator;   // §6-2의 REQUIRES_NEW 할당기
    private final Clock clock;

    private LocalDate blockDate;                      // 현재 블록의 날짜
    private long next, limit;                         // 현재 블록 [next, limit)

    public synchronized String next(Channel channel) {
        LocalDate today = LocalDate.now(clock);
        if (!today.equals(blockDate) || next >= limit) {          // 날짜가 바뀌었거나 블록 소진
            long start = allocator.allocate("order:" + today, BLOCK);
            blockDate = today; next = start; limit = start + BLOCK;
        }
        long serial = next++;
        String body = today.format(DateTimeFormatter.BASIC_ISO_DATE) + "-" + channel.code() + "-"
                    + String.format("%06d", serial);
        return body + "-" + luhnCheckDigit(body);                 // 체크 디짓: CS 오타 입력을 걸러 준다
    }
}
체크 디짓(check digit)이 무엇인가 — 한 줄로 앞자리들로 정해진 규칙에 따라 계산한 검산용 마지막 한 자리다. 사람이 번호를 한 자리 잘못 부르거나 두 자리를 바꿔 부르면 계산이 안 맞아 DB에 물어보기 전에 걸러진다. 신용카드 번호에 쓰는 Luhn 알고리즘이 대표적이다.

함정 ④ — PG에서 재시도를 같은 트랜잭션 안에서 하면 전부 25P02로 죽는다 가산점

MySQL이라면 문장 하나가 실패해도 같은 트랜잭션을 이어 쓸 수 있지만, PG는 트랜잭션 안에서 에러가 나는 순간 그 트랜잭션 전체가 실패 상태로 들어가 이후 모든 문장이 ERROR 25P02 current transaction is aborted, commands ignored until end of transaction block으로 거부된다. 같은 트랜잭션 안에서 재시도하려면 SAVEPOINT(스프링의 Propagation.NESTED)로 감싸야 하고, 그게 아니라면 재시도 루프는 트랜잭션 밖에 있어야 한다.

그런데 삽입 위치를 값이 결정하는 구조가 하나 남아 있다 — PK B-tree, 그리고 그 값을 받는 자식 FK 인덱스들. 힙은 append-only에 가까워 자리를 고를 수 있지만 B-tree는 키 순서가 자리를 강제하기 때문이다.

인덱스 bloat · 적재율 저하→ 논리/물리 순서 어긋나 범위 스캔 랜덤화→ PG 고유: full_page_writes FPI 증폭→ WAL 볼륨 · 체크포인트 I/O · 복제 지연

숫자를 하나 붙이면 강하다 — 초당 5,000 INSERT에서 무작위 키는 FPI만으로 5,000 × 8KB = 41MB/s(시간당 약 147GB), 단조 증가 키는 인덱스 레코드 수십~수백 바이트로 1MB/s 미만이다.

v7은 시간을 상위 비트에 두어 삽입 위치를 오른쪽 끝으로 모으므로 이 사슬 전체가 끊긴다. 남는 것은 크기다 — uuid 16바이트는 자식 테이블 FK 컬럼·FK 인덱스에서 페이지당 엔트리 366 → 262(약 28% 감소)로 청구된다. "완전히 해결"이 아니라 "두 문제 중 치명적인 하나를 해결"이 정확한 답이고, varchar(36)으로 저장하면 v7이어도 크기 문제는 v4와 같다.

시퀀스 번호가 군데군데 비어 있습니다. 데이터가 유실된 건가요? 가산점힌트: "정상이다" + 왜 그렇게 설계했는지까지 말한다

아니다 — 정상이다. nextval()은 트랜잭션 밖에서 동작하도록 설계돼 있다.

왜 그렇게 만들었는지까지 말하면 좋다 — 트랜잭션을 따랐다면 값을 받은 세션이 커밋할 때까지 다음 세션이 기다려야 하고, 그러면 시퀀스 자체가 핫 로우가 된다. PG는 직렬화를 피하려고 연속성을 포기했다. 그래서 롤백해도 소모된 값은 돌아오지 않는다.

구멍이 생기는 경로는 넷 — ⑴ 롤백·에러 ⑵ INSERT ... ON CONFLICT DO NOTHING처럼 행이 안 들어가도 컬럼 DEFAULT의 nextval()은 먼저 평가되어 소모 ⑶ CACHE로 선점한 값이 세션 종료로 폐기 ⑷ 크래시 후 재시작 시 미리 WAL에 기록해 둔 지점까지 건너뜀.

번호 연속성으로 유실을 판단하면 안 된다 — 유실 판단은 별도 대사(reconciliation)로 한다

연속성이 진짜 요건(세금 계산서 일련번호 등)이라면 시퀀스로는 불가능하고 채번 테이블을 트랜잭션 안에서 UPDATE해야 하는데, 그건 핫 로우 직렬화를 그대로 받아들인다는 뜻이다 — gapless와 처리량은 맞바꾸는 관계라고 말하면 요구를 비용으로 번역할 줄 아는 것으로 들린다.

채번 테이블이 왜 트래픽에서 병목이 되나요? PostgreSQL이라 더한 점이 있나요? 필수힌트: 락 사슬 → PG 고유의 죽은 튜플 한 겹 → 처방 둘 + fillfactor

핫 로우 사슬 — 모든 요청이 같은 행을 UPDATE → 튜플 헤더 xmax에 기록되는 배타 락 → 락은 트랜잭션 커밋까지 유지 → 채번을 주문 트랜잭션 안에서 하면 주문 처리 전체 길이만큼 다음 요청이 대기(pg_stat_activity의 wait_event = 'transactionid') → 처리량 상한 = 1/트랜잭션 길이 → 대기자가 커넥션(= OS 프로세스)을 쥔 채 서므로 풀 고갈로 다른 API까지 번진다.

PG에서 한 겹 더 있는 것은 UPDATE가 제자리 갱신이 아니라 새 튜플 버전을 만든다는 점이다 — 죽은 튜플이 그 페이지에 쌓이고 autovacuum이 추격해야 한다. 다행히 next_val은 어떤 인덱스에도 없으므로 HOT 업데이트가 가능하니 fillfactor를 낮춰(예: 70) 같은 페이지에 새 버전 자리를 비워 두고, n_tup_hot_upd 비율로 확인한다.

처방은 그 위에 둘 — ① REQUIRES_NEW로 채번 트랜잭션을 UPDATE ... RETURNING 한 문장으로 짧게 분리하고, ② 블록 할당으로 방문 횟수를 1/N로 줄인다. 블록 할당 후 남는 것은 ⑴ 재기동 시 구멍 ⑵ 인스턴스 간 순서 교차 ⑶ 채번 테이블 가용성 의존이다.

덧붙일 한마디 — PG에서는 이 블록 할당을 시퀀스의 CACHE가 이미 제공하므로, 채번 테이블을 직접 쓰는 이유는 "분산"이 아니라 "날짜별 리셋 같은 업무 포맷"이어야 한다.

주문번호에 날짜와 채널 코드를 넣어 달라는 요구가 왔습니다. PK를 바꾸시겠어요? 시니어 변별힌트: 요구를 한 단계 쪼갠다. 그리고 되물을 것 세 가지

바꾸지 않는다. 이 요구는 "외부 식별자에 업무 의미를 담아 달라"는 요구이지 "내부 식별자를 바꿔 달라"는 요구가 아니다.

PK는 조인·FK·인덱스의 축이라 작고 단조 증가하는 정수여야 하고, 날짜·채널이 들어간 문자열은 그 두 원칙을 다 어긴다 — 크기는 자식 테이블 FK 컬럼·FK 인덱스로 번지고, 채널별로 삽입 위치가 갈라져 PK B-tree 끝 페이지 append가 깨진다. 그래서 PK는 그대로 두고 order_no 컬럼을 유니크 제약과 함께 추가한다.

이어서 되물어야 할 것 세 가지 — ① "일련번호가 연속이면 하루 주문량이 노출되는데 괜찮은가" ② "채널 코드가 바뀌면 기존 번호는 어떻게 하는가"(번호는 불변, 채널 매핑은 별도 테이블) ③ "체크 디짓을 넣어 CS 오입력을 막을까".

요구를 한 단계 쪼개 어느 성질이 진짜 필요한지 되묻고, PK와 업무 식별자를 겸용하던 것이 애초의 문제였다고 짚는 것이 시니어의 답이다.

우리 서비스는 DB 한 대로 충분한데, 그래도 Snowflake를 미리 도입해야 할까요? 시니어 변별힌트: 의존성 비용 → 지금 해 둘 것 하나 → 넘어가는 신호 셋

아니다 — 의존성 비용을 먼저 말한다. Snowflake는 워커 ID 임대 인프라(레지스트리·하트비트·회수)와 시계 규율(NTP slew, 역행 감지·알람)이라는 상시 운영 의무를 산다. DB 한 대인 지금은 bigint IDENTITY가 순차 I/O, 8바이트, 의존성 0을 공짜로 준다.

게다가 PG에서는 "INSERT 전에 ID를 못 받는다"는 이유로 넘어갈 필요도 없다 — nextval()을 미리 부르면 되고, JPA도 시퀀스 전략 + allocationSize로 배치가 살아 있다.

다만 미리 해 둘 것은 하나 — 내부 PK를 외부에 노출하지 않도록 order_no를 지금부터 분리해 두는 것

그러면 나중에 샤딩이나 다중 리전이 실제 요구가 됐을 때 바뀌는 것은 @GeneratedValue 전략 한 줄과 마이그레이션이고, 외부 계약(주문번호 포맷)은 그대로다.

넘어가는 신호도 정해 둔다 — ⑴ 샤딩/다중 마스터 결정 ⑵ 클라이언트·오프라인 생성 요구 ⑶ 단일 노드 쓰기 처리량 한계 관측.

가산점 한 줄 — 넘어갈 때는 기존 시퀀스 값과 Snowflake 값이 같은 bigint 컬럼에서 겹치지 않는지 확인한다. 계산은 간단하다 — 에포크로부터 30일만 지나도 Snowflake 값은 (30 × 86,400,000 ms) << 22 ≈ 1.1 × 10^16이라 시퀀스가 1부터 세는 값(수억~수십억 대)과 자릿수부터 다르다. 즉 에포크를 충분히 과거로 잡지만 않으면 겹칠 일이 없다. 그리고 시퀀스를 계속 쓸 경로가 남는다면 setval로 앞당겨 두는 마이그레이션 체크까지 말하면 끝이다.

Snowflake에서 서버 시계가 뒤로 가면 무슨 일이 생기고, 어떻게 막나요? 필수힌트: 가정이 무엇이었는지 → 코드에서 하는 일 → 운영에서 하는 일 → v7과의 연결

유일성이 "같은 워커에서 시간은 단조"라는 가정에 걸려 있으므로, 시계가 이미 발급한 ms로 되돌아가면 같은 (시각, 워커, 시퀀스) 조합이 다시 나올 수 있다.

코드에서: 발급기는 마지막 발급 시각을 들고 있다가 역행을 감지해야 한다 — 수 ms 이내면 그 시각까지 기다리고, 그 이상이면 예외로 발급을 거부하고 알람을 울린다. 예외를 삼키고 계속 발급하는 것이 최악이다.

운영에서: NTP를 step(한 번에 되돌림)이 아니라 slew(클럭 속도를 늦춰 천천히 보정)로 설정하고, VM 마이그레이션·절전 복귀 뒤 시계 점프를 모니터링한다.

가산점 — UUID v7은 같은 상황에서 난수 74비트가 완충하므로 역행 감지 코드가 필요 없다. Snowflake의 시계 의존을 16바이트로 산 것이라고 연결하면 트레이드오프 서술이 완성된다.

Snowflake ID로 정렬하면 정확한 시간 순이 되나요? 커서 페이지네이션 키로 써도 되나요? 가산점힌트: 워커 안 / 워커 간을 갈라 말하고, 역할을 나눈다

워커 안에서는 단조, 워커 간에는 ms 단위 근사다. 두 서버의 시계가 몇 ms 어긋나면 나중에 만든 ID가 더 작을 수 있고, 같은 ms 안의 순서는 워커 ID 순이지 실제 발생 순이 아니다.

따라서 "최근 주문순" 목록의 정렬 키로는 created_at(+ 타이브레이커로 id)을 쓰고, ID는 유일성과 인덱스 지역성을 위한 것이라고 역할을 나눈다.

UUID v7도 같은 성질이고, PG 시퀀스도 CACHE를 1보다 크게 잡으면 세션별 블록 선점 때문에 같은 현상이 생긴다 — "시간 정렬 ID"라는 말은 "인덱스 삽입 위치가 모인다"는 뜻이지 "정확한 발생 순서를 보장한다"는 뜻이 아니다. 키셋 페이지네이션은 (created_at, id) 행 비교로 짜는 것이 안전하다.

UUID v7과 Snowflake 중 하나만 고른다면? 판단 기준을 말해보세요. 시니어 변별힌트: 비교표의 두 열을 나란히 읽고, 마지막에 "무엇을 살 여유가 있는가"로 닫는다

비교표의 두 열을 나란히 읽는 것이 정확한 답변 형식이다 — 정렬성 같음(둘 다 ms 단위 근사 단조), 분산성 같음(둘 다 로컬 생성·조율 0), 크기 8 vs 16, 의존성은 Snowflake가 무겁고 UUID v7이 가볍다.

Snowflake를 고르는 조건

8바이트가 가치 있을 만큼 자식 테이블·FK 인덱스가 크고, 워커 ID 레지스트리와 NTP 규율을 상시 운영할 여력이 있는 팀. 즉 운영 비용을 내고 크기를 사는 선택.

UUID v7을 고르는 조건

그 상시 운영 의무를 지고 싶지 않은 팀. 16바이트를 내고 단순함을 사는 선택이며, 클라이언트·오프라인 생성이 필요하면 더욱 유리하다.

정리 한 문장 — "의존성을 살 여유가 있으면 Snowflake, 없으면 UUID v7이 크기를 내고 단순함을 산다."

그리고 반드시 앞에 붙일 것 — "그 전에, 정말 분산 생성이 요구사항인가"를 되묻는다. DB 한 대라면 두 후보 모두 bigint IDENTITY에 진다.

PG에서 GENERATED ALWAYS AS IDENTITY로 만들었더니 데이터 이관 스크립트가 전부 막힙니다. 왜죠? 함정힌트: ALWAYS의 의미 하나 + 대안 두 가지 + 이관 후 반드시 할 일 하나

GENERATED ALWAYS는 앱이 id를 직접 넣는 INSERT를 거부하기 때문이다. 통과시키려면 문장마다 OVERRIDING SYSTEM VALUE를 붙여야 한다.

대안은 둘 — ① GENERATED BY DEFAULT AS IDENTITY(앱이 값을 넣으면 그 값을 쓰고, 안 넣으면 시퀀스가 채운다) ② 독립 시퀀스 + DEFAULT nextval(). JPA 시퀀스 전략처럼 앱이 값을 들고 들어오는 구조라면 둘 중 하나여야 한다.

이관 후 반드시 — setval()로 시퀀스를 옮긴 데이터의 최댓값 뒤로 앞당긴다

이걸 빼먹으면 시퀀스는 1부터 세는데 테이블에는 이미 큰 값이 있어 다음 INSERT부터 PK 중복이 난다. 판별식은 하나 — "이 컬럼에 앱이 값을 넣을 일이 한 번이라도 있는가?"

allocationSize를 50으로 올렸더니 가끔 PK 중복이 납니다. 어디를 보시겠어요? 함정힌트: 로그가 아니라 DDL을 본다

DDL의 INCREMENT BY를 본다. 하이버네이트는 nextval()이 돌려준 값을 "내가 쓸 블록의 경계"로 해석해 그 값으로부터 allocationSize만큼을 메모리에서 나눠 준다. DB가 실제로는 1씩만 밀고 있으면(INCREMENT BY 1) 두 인스턴스의 블록이 겹치고, 같은 번호가 두 번 발급된다.

하이버네이트 6에는 이 불일치를 기동 시 알려주는 설정(hibernate.id.sequence.increment_size_mismatch_strategy)이 있지만 기본 동작은 버전마다 다르므로 이것에 의존하지 않는다.

팀 규칙으로 고정한다 — DDL의 INCREMENT BY와 allocationSize는 같은 PR에서 함께 바꾼다

증상이 "PK 중복"으로 나타나는데 원인은 "스키마와 코드의 숫자 불일치"라는 점이 이 함정의 악질적인 부분이다 — 애플리케이션 로그만 봐서는 절대 안 잡히고, 인스턴스가 한 대인 개발 환경에서는 재현조차 되지 않는다.

Snowflake ID를 JSON으로 내려줬더니 프런트에서 "없는 주문"이 됩니다. 함정힌트: 에러가 아니라 값이 조용히 달라지는 종류의 사고

JavaScript Number의 안전 정수 범위를 넘었기 때문이다. 한계는 2^53 − 1 = 9,007,199,254,740,991로 16자리인데, 2025년 에포크로 오늘 발급한 Snowflake ID는 (경과 ms) << 22라 약 2.2 × 10^17, 즉 18자리다.

브라우저가 파싱하면서 끝자리가 조용히 반올림된다 — 예외가 나지 않고 값만 살짝 달라지므로 "조회는 되는데 가끔 없는 주문"이라는 형태로 나타난다. 서버 로그에는 존재하지 않는 ID로 조회한 정상 요청만 남는다.

처방 — API 응답에서 64비트 ID는 문자열로 내보낸다 (직렬화 설정 또는 DTO 타입으로 고정)

같은 함정이 붙는 다른 자리 — 로그 수집기·BI 도구·스프레드시트로 ID를 옮길 때도 숫자로 해석되면 같은 반올림이 일어난다. 애초에 외부로는 order_no만 내보내는 설계가 이 문제까지 같이 막는다.

논리 복제로 새 클러스터에 이관하고 전환했더니 PK 중복이 터졌습니다. 가산점힌트: 물리 복제와 논리 복제가 옮기는 것이 다르다

논리 복제는 시퀀스를 복제하지 않기 때문이다. 스트리밍(물리) 복제는 바이트 단위 복제라 시퀀스 상태까지 그대로 따라오지만, 논리 복제는 테이블 행의 변경만 옮긴다.

그래서 전환 시점에 새 프라이머리의 시퀀스는 초기 상태(1부터)이고, 테이블에는 이미 큰 id들이 들어 있다. 첫 INSERT부터 23505 duplicate key가 쏟아진다.

전환 체크리스트에 못 박는다 — "모든 시퀀스 setval 확인"

이 사고의 성질이 나쁜 이유는 전환 리허설에서 테이블 행 수만 비교하면 통과한다는 데 있다. 검증 항목에 "시퀀스 last_value vs 테이블 MAX(id)"를 넣어야 잡힌다.

단조 증가 PK는 끝 페이지 한 장에 경합이 몰린다던데, 그럼 랜덤 키가 낫지 않나요? 시니어 변별힌트: 경합의 종류를 구분하고, 두 비용의 자릿수를 비교한다

경합이 있는 것은 사실이다 — 모든 INSERT가 맨 오른쪽 리프 한 장에 몰리면 그 페이지의 버퍼 잠금을 두고 백엔드들이 경합하고, pg_stat_activity에 wait_event_type = 'LWLock'으로 관측된다.

그런데 그 대기의 단위가 다르다. LWLock은 트랜잭션 락이 아니라 메모리 구조 하나를 아주 짧게 보호하는 내부 잠금이라 대개 마이크로초 단위로 끝난다. 반면 랜덤 키가 사는 것은 디스크 랜덤 I/O와 WAL 볼륨이다.

마이크로초짜리 LWLock 경합을 피하려고 80배의 WAL(41MB/s vs 0.5MB/s)을 사는 것은 거래가 아니다

맞는 완화책은 방향이 다르다 — 해시 파티셔닝으로 끝 페이지를 여러 개로 나누거나 샤딩한다. 끝 페이지가 N개가 되면 경합도 1/N이 되고, 각 파티션 안에서는 여전히 끝 삽입이라 순차 I/O와 FPI 효율을 유지한다. "랜덤으로 되돌아가기"는 문제를 더 비싼 문제로 바꾸는 것이다.

세금계산서 일련번호처럼 "빈 번호가 절대 없어야 한다"가 요건이면 어떻게 하나요? 시니어 변별힌트: 무엇을 포기해야 하는지를 먼저 계산해서 보여준다

먼저 "그것은 처리량을 사는 대신 포기하는 것"이라고 번역한다. gapless를 만족시키려면 번호를 준 트랜잭션이 커밋될 때까지 다음 번호를 줄 수 없다 — 즉 채번을 트랜잭션 안에 넣어 직렬화를 받아들이는 것이 유일한 길이다.

그래서 탈락하는 것들 — 시퀀스(비트랜잭션이라 롤백·UPSERT·CACHE·크래시로 구멍), 블록 할당(재기동 시 구멍), Snowflake·UUID(애초에 연속이 아님). 남는 것은 채번 테이블을 업무 트랜잭션 안에서 UPDATE하는 방식뿐이다.

그러면 처리량 상한이 계산된다 — 1 / (그 트랜잭션 한 건의 길이). 그래서 이 경로에서는 트랜잭션 안에 외부 HTTP 호출을 절대 넣지 않고, 트랜잭션을 DB 작업만으로 최소화하는 것이 핵심 설계가 된다.

범위를 좁히는 것이 실무의 답이다 — gapless가 필요한 것은 "세금 문서 번호"이지 "모든 주문"이 아니다

내부 PK는 그대로 시퀀스로 두고, gapless가 필요한 문서 번호만 별도 채번으로 분리한다. 그리고 이 선택(무엇을 포기했는지)을 ADR 한 장으로 남긴다.

워커 ID를 등록 테이블 대신 K8s StatefulSet의 파드 순번으로 쓰면 안 되나요?힌트: "된다, 단 조건이 있다" — 그 조건이 무엇을 보장해야 하는지로 답한다

된다. StatefulSet의 순번은 "중앙에서 유일하게 배정된 번호"라는 요건을 이미 만족하는 한 가지 구현이다. 요건 자체는 저장소가 무엇이냐가 아니라 "같은 순간에 두 프로세스가 같은 워커 ID를 들지 않는다" 하나다.

조건 세 가지를 확인하고 쓴다. ① Deployment가 아니라 StatefulSet이어야 한다 — Deployment의 파드 이름에는 안정적인 순번이 없다. ② 순번이 0~1,023 범위 안이어야 한다(10비트). ③ 같은 순번의 파드가 동시에 둘 존재하는 상황이 없어야 한다 — 블루/그린으로 두 세트를 동시에 띄우거나, 여러 클러스터·리전에 같은 StatefulSet을 배포하면 순번이 겹친다.

③이 흔들리는 순간 같은 ms에 같은 ID가 나온다 — 그리고 그 사고는 "가끔 PK 중복"으로만 보인다

등록 테이블 임대가 더 안전한 이유는 어떤 배포 형태에서도 "유일성"을 DB의 PK 제약이 보증하기 때문이다. 반대로 운영을 단순하게 유지하고 싶다면 조건 ③을 배포 파이프라인의 규칙으로 고정한 뒤 순번을 쓰는 것도 합리적인 선택이다 — 어느 쪽이든 "죽으면 회수, 살아 있으면 갱신"이 성립하는지를 말할 수 있어야 한다.

기존 서비스의 PK가 이미 varchar(36) UUID v4입니다. 지금 무엇부터 하시겠어요? 시니어 변별힌트: "전부 바꾼다"가 아니라 순서 — 관측 → 경계 분리 → 타입 → PK

PK 교체는 마지막이다. PK를 바꾸는 것은 자식 테이블 FK 전부 + 모든 인덱스 + 애플리케이션 코드 + 외부에 노출된 값까지 함께 움직이는 일이라, 먼저 싼 것부터 한다.

1
관측으로 현재 위치를 확인한다. PK 인덱스 크기 vs shared_buffers, EXPLAIN (ANALYZE, BUFFERS, WAL)의 shared read와 fpi=, pg_stat_wal의 wal_fpi. 이미 계단을 밟았는지, 아직 여유가 있는지가 이후 결정의 근거다.
2
외부 식별자를 먼저 분리한다. order_no를 유니크 제약과 함께 추가하고 외부 계약을 그쪽으로 옮긴다. 이 단계는 PK를 건드리지 않으면서 나중에 PK를 바꿀 자유를 만든다 — 가장 싸고 가장 효과가 큰 한 걸음.
3
타입만이라도 varchar(36) → uuid로 옮긴다. 36바이트 + collation 비교가 16바이트 + 바이트 비교가 된다. 값의 의미는 그대로라 애플리케이션 변경이 작다.
4
그다음에야 PK 후보를 고른다. 분산이 실제 요구가 아니면 bigint 시퀀스, 요구면 Snowflake / UUID v7. 새 컬럼을 추가해 이중 쓰기 → 백필 → 참조 전환 → 구 컬럼 제거의 온라인 절차로 옮기고, 각 단계가 되돌릴 수 있는지를 확인한다.

이 순서 자체가 답변의 내용이다 — "UUID v4는 나쁘니 bigint로 바꾸겠습니다"는 비용을 세어보지 않은 답으로 들린다.

한 줄 요약
채번 설계의 답은 방식 이름이 아니라 분리다 — 내부 PK는 작고(8바이트) 단조 증가해야 하는데, PostgreSQL에서 그 근거는 클러스터드 인덱스가 아니라 PK B-tree의 삽입 위치 · 자식 FK 인덱스의 적재율 · full_page_writes로 부푸는 WAL이다(힙은 자리를 고를 수 있고 B-tree는 키가 자리를 강제하기 때문). 단일 DB면 bigint GENERATED ALWAYS AS IDENTITY가 첫 정답이고, PG의 시퀀스는 테이블과 독립된 객체라 nextval()을 INSERT 전에 미리 부를 수 있어 AUTO_INCREMENT의 한계 하나가 애초에 없다 — 대신 비트랜잭션성 때문에 빈 번호는 정상이고 CACHE는 세션 간 순서를 교차시키며 다중 노드 충돌은 남는다. 분산이 실제 요구면 Snowflake(41비트 약 69년 + 10비트 1,024대 + 12비트 ms당 4,096개, 시계 역행 감지와 워커 ID 임대를 코드로) 또는 UUID v7이고, v4는 힙이 아니라 PK B-tree에서 무작위 삽입 → 캐시 미스 → 페이지 분할 → 적재율 저하 → 랜덤 I/O → WAL FPI 증폭의 사슬로 실격, v7은 그 사슬을 끊되 16바이트를 낸다(페이지당 엔트리 366 → 262). 외부 주문번호는 채번 테이블(+블록 할당, UPDATE ... RETURNING, 별도 짧은 트랜잭션, fillfactor로 HOT 유지, 구멍 허용 정책 명문화)로 업무 의미를 담고, 유니크 제약을 최후 방어선으로 두되 재시도는 반드시 새 트랜잭션에서 한다. 4방식은 정렬성 · 분산성 · 크기 · 노출 · 의존성 · 업무 의미 여섯 축으로 비교하고, 각 방식의 얻는 것과 내는 것을 같은 호흡에 붙인다.
