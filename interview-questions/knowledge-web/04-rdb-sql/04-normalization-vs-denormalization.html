정규화 vs 반정규화 — "조회 성능을 위해"에서 멈추면 반쪽짜리 정의다

원본: interview-questions/knowledge/04-rdb-sql/04-normalization-vs-denormalization.md

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "정규화와 반정규화란? 반정규화를 선택하는 기준은?"
정규화는 "하나의 사실은 한 곳에만" — 중복을 없애 수정 이상(update anomaly)을 개발자 주의력이 아니라 테이블 구조 자체로 차단하는 설계다. 반정규화는 조회 패턴에 맞춰 의도적으로 중복·연산 값을 허용하고, 그 대가(갱신 정합성)를 관리 장치와 함께 지불하는 결정이다 — "대가 관리"까지 말해야 정의가 완성된다. 선택 기준은 4축: ① 읽기:쓰기 비율 ② 실측된 조인·집계 병목 ③ 인덱스·커버링 인덱스·캐시 선행 검토 ④ 대가 지불 준비(같은 트랜잭션 + 원자적 UPDATE + 보정 배치). 그리고 핫 로우의 비용은 "성능 저하"라는 뭉뚱그린 말 대신 락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파라는 이름 붙은 사슬로 말한다.
출제 의도 — 정규형 번호 암기가 아니라 "양면을 조립"하는가를 본다
교과서 정규화만 아는 사람과 "조회 패턴에 맞춰 의도적으로 중복을 허용하고 그 대가(갱신 정합성)를 관리"해본 사람을 구분한다. 대용량 조회 시스템은 반정규화 없이 성립하지 않는다. 편익(조회 성능)과 대가(갱신 정합성)를 한 호흡에 말하고, 언제 어떤 관리 장치와 함께 중복을 들여오는지의 실무 판단을 본다.
이번 면접에서 된 것
  • 반정규화의 두 형태(중복 컬럼·연산 컬럼) 구분
  • 같은 트랜잭션으로 묶을 때의 결합 비용 인지
  • 원자적 UPDATE(cnt = cnt + 1) 자력 제시
  • 보정 배치(안전망) 자력 제시 — 첫 개선 신호
재발한 약점 — 이 페이지가 겨냥하는 곳
  • 본질문에서 편익만 서술 — 트레이드오프 양면 조립 실패 (→ §2 저울, 문장 틀)
  • 핫 로우 비용을 "성능 저하"로 뭉뚱그림, 힌트 후에도 "락 경합" 이름 하나에서 멈춤 — 사슬 미완주 (→ §5 사슬 흐름도, 5박자)
  • 1정규화 — 하나의 사실은 한 곳에만 · 1NF~3NF
  • 2반정규화 — 두 형태 · 저울 · 한 호흡 문장 틀
  • 3선택 기준 4축 체크리스트 · 수단의 사다리
  • 4정합성 안전망 3층 · before/after
  • 5핫 로우 사슬 — "성능 저하" 대신 이름으로
  • 6웹툰 도메인 적용 훈련 · 스냅샷 함정
  • 7꼬리질문 셀프 테스트
  • ★한 줄 요약

1. 정규화 — 규칙 목록이 아니라 원칙 하나: "하나의 사실은 한 곳에만"

1-1. 수정 이상을 구조로 차단한다

정규화의 본질은 1NF, 2NF… 번호가 아니라 원칙 하나다 — 하나의 사실(fact)은 데이터베이스에 정확히 한 곳에만 존재해야 한다. 같은 사실이 여러 곳에 흩어져 있으면 수정할 때 전부 찾아 고쳐야 하고, 하나라도 놓치면 "같은 질문에 DB가 두 가지 답을 하는" 상태가 된다. 이것이 수정 이상(update anomaly)이고, 정규화는 이것을 코드 리뷰나 개발자 주의력이 아니라 테이블 구조 자체로 막는다 — 어긋날 "다른 곳"이 애초에 없으니까.

❌ before — "부서 이름"이라는 사실이 직원 수만큼 복제
CREATE TABLE employees (
    id        BIGINT PRIMARY KEY,
    name      VARCHAR(50),
    dept_name VARCHAR(50)   -- '개발1팀'이 300행에 흩어져 있다
);

-- 부서 이름이 바뀌면?
UPDATE employees SET dept_name = '플랫폼팀'
 WHERE dept_name = '개발1팀';
-- 조건을 잘못 쓰거나 일부만 갱신되면
-- → 한 부서에 두 이름 (update anomaly)
✅ after — 부서 이름은 departments 한 행에만
CREATE TABLE departments (
    id   BIGINT PRIMARY KEY,
    name VARCHAR(50)         -- '개발1팀'은 여기 한 행에만
);
CREATE TABLE employees (
    id      BIGINT PRIMARY KEY,
    name    VARCHAR(50),
    dept_id BIGINT           -- 사실을 복제하지 않고 참조(FK)만
);

-- 부서 이름 변경 = 한 행 UPDATE
UPDATE departments SET name = '플랫폼팀' WHERE id = 7;
-- 어긋날 "다른 곳"이 구조적으로 없다
비유 — 규정집 복사본 vs 사내 위키 링크

회사 규정을 각 팀이 복사해 갖는 것(정규화 전)과, 원본은 사내 위키 한 페이지에만 두고 각 팀은 링크만 갖는 것(정규화)의 차이다. 복사본 체제에서는 개정 때마다 전 팀을 돌며 바꿔야 하고, 한 팀이라도 옛 버전을 들고 있으면 사고가 난다. 링크 체제에서는 "옛 버전을 든 팀"이 존재할 수 없다.

1-2. 정규형 1NF~3NF 요약 — 외울 건 "원자 · 키 전체 · 키에만" 세 마디

면접에서 정규형 번호를 묻는 일은 드물지만, 물었을 때 한 문장씩 못 하면 정규화의 원칙을 "말만" 아는 것으로 보인다. 영어권 암기구 "the key, the whole key, and nothing but the key"를 그대로 쓰면 된다 — 2NF = 키 전체에, 3NF = 오직 키에만.

정규형한 마디규칙웹툰 도메인 위반 예 → 분해위반 시 생기는 일
1NF원자 모든 컬럼 값이 더 쪼갤 수 없는 원자값. 반복 그룹·다중값 컬럼 없음 series.genres = '로맨스,판타지' → series_genres(series_id, genre) 행으로 분리 장르로 검색·집계 불가, 장르 이름 하나 바꾸려면 문자열 수술
2NF키 전체에 1NF + 부분 함수 종속 제거 — 복합 키의 일부에만 종속하는 컬럼이 없어야 PK (series_id, episode_no)인 episodes에 series_title — 제목은 series_id에만 종속 → series로 작품 제목이 회차 수만큼 복제 → 제목 변경 시 회차 전부 갱신
3NF오직 키에만 2NF + 이행적 종속 제거 — 키가 아닌 컬럼이 다른 비키 컬럼에 종속하면 안 됨 episodes(author_id, author_name) — 작가명은 author_id에 종속 → authors로 작가 필명 변경 시 회차 전부 갱신, 회차 없는 작가는 저장할 곳이 없음
BCNF(참고) 모든 결정자가 후보키. 3NF의 드문 빈틈을 막는 강화판 실무 스키마는 대개 3NF/BCNF를 기준으로 삼고, 그 이상(4NF·5NF)은 실제 이상 현상이 확인될 때만 꺼낸다
암기 카드 — 정규형 세 마디
1NF 원자값 · 2NF 키 전체에 종속 · 3NF 오직 키에만 종속

셋 다 결국 같은 원칙의 단계별 적용이다 — "이 컬럼의 사실은 정말 이 행(키)의 것인가? 아니면 다른 곳의 사실을 베껴 온 것인가?"

2. 반정규화 — "의도적"과 "대가 관리"가 빠지면 정의가 아니다

2-1. 두 형태 — 베껴 두기(중복 컬럼)와 세어 두기(연산 컬럼)

반정규화가 들여오는 중복은 크게 두 형태다. 원리는 같다 — 정규화가 금지한 "같은 사실의 복제"를 조회 패턴을 위해 일부러 되돌리는 것.

중복 컬럼 베껴 두기

다른 테이블의 값을 조인 없이 읽으려고 복사해 둔다. 원본이 바뀌면 사본을 따라 바꿔야 한다.

comments.author_name (원본 users.name)
episodes.series_title (원본 series.title)
  • 대가: 원본 변경 시 사본 N행 동기 갱신
  • 원본 변경이 드물수록 안전
연산(집계) 컬럼 세어 두기

매번 COUNT/SUM/MAX 하는 대신 결과를 컬럼에 유지한다. 원본 행이 늘거나 줄 때마다 갱신해야 한다.

posts.comment_count (원본 comments 행 수)
series.episode_count · series.like_count
  • 대가: 모든 쓰기 경로가 +1/−1 의무를 짐
  • 인기 행에 쓰기가 수렴하면 핫 로우(§5)

2-2. 저울 — 얻는 것은 조회할 때, 내는 것은 갱신할 때

반정규화의 편익과 대가는 서로 다른 순간에 발생한다. 편익은 읽을 때 받고, 청구서는 쓸 때 온다. 그래서 읽기만 보고 있으면 공짜처럼 보인다 — 저울의 오른쪽 접시를 같이 올려놓아야 "결정"이 된다.

왼쪽 접시만 말하면 저울이 아니라 접시 하나다. 오른쪽 접시와 받침점까지 말해야 "트레이드오프를 조립한 답"이 된다.
한 호흡 문장 틀 — "조회가 빨라진다"에서 마침표를 찍지 않는다
얻는 것조회 패턴을 위해 [사본: comment_count]을 [위치: posts]에 의도적으로 두어 [조인/집계]를 없앤다
— 대 신 —
내는 것원본↔사본이 어긋날 수 있는 갱신 정합성 대가가 생기고, 모든 쓰기 경로가 갱신 의무를 지며, 인기 행이면 핫 로우 사슬(락 경합 → 직렬화 → 장기화 → 풀 고갈 → 전파)을 각오해야 한다
— 그 래 서 —
관리원자적 UPDATE + 같은 트랜잭션(또는 이벤트) + 보정 배치·드리프트 알람으로 대가를 지불하고, 도입 전에 실측·인덱스·캐시를 먼저 검토한다

"대신"이 이 답의 심장이다. 면접관은 "대신" 뒤가 나오는지를 듣고 있다.

2-3. 정의의 자격 요건 두 단어 — "의도적" + "대가 관리"

같은 "중복"이라도 오른쪽에서 왼쪽으로 알고서 되돌린 것만 반정규화다. 처음부터 왼쪽에 있었던 중복은 결정이 아니라 사고다.
"의도적" 자격 요건 1

정규화된 설계를 알고서 되돌리는 결정. 어떤 사실을 어디에 복제했는지가 문서와 코드에 드러나야 한다. 모르고 생긴 중복은 정규화 실패이지 반정규화가 아니다.

"대가 관리" 자격 요건 2

중복을 두는 순간 "원본과 사본이 어긋날 수 있다"는 부채가 생긴다. 이 부채를 갚는 장치(§4의 3층)가 함께 설계되지 않은 중복은 결정이 아니라 방치다.

3. 선택 기준 4축 — 체크리스트로 외우고, 수단은 싼 것부터

3-1. 4축 체크리스트 — "읽기 · 실측 · 선행 · 대가"

☐
① 읽기:쓰기 비율 — 이 데이터, 읽기가 압도적인가? 사본은 읽을 때 이득이고 쓸 때 비용이다. 쓰기가 잦으면 대가만 키운다. (인기작 like_count처럼 쓰기도 폭주하면 동기 반정규화는 부적합)
☐
② 실측 병목 — 조인·집계 비용이 측정으로 확인됐는가? "느릴 것 같아서"는 근거가 아니다. 실행 계획(EXPLAIN)·슬로 쿼리·digest로 확인한 뒤에만 다음 축으로.
☐
③ 선행 검토 — 인덱스·커버링 인덱스·캐시로 먼저 해결되지 않는가? 반정규화는 스키마를 바꾸는, 비가역에 가까운 수단. 더 싸고 되돌리기 쉬운 수단부터 (3-2 사다리).
☐
④ 대가 지불 준비 — 갱신 정합성 관리 장치를 설계했는가? 원자적 UPDATE + 같은 트랜잭션(또는 이벤트) + 보정 배치·드리프트 알람 (+ 핫 로우 대비). 이게 없는 제안은 "대출로 뭘 살지"만 정하고 상환 계획이 없는 것.
암기 카드 — 4축 네 글자
읽기(비율) · 실측(병목) · 선행(인덱스/캐시) · 대가(관리 장치)

면접에서 "기준은요?"가 오면 이 네 글자를 순서대로 편다. ④를 빠뜨리면 트레이드오프 한 면만 본 답이 된다.

3-2. 수단의 사다리 — 가장 비싼 수단을 가장 마지막에

③의 순서가 중요한 이유는 가역성이다. 인덱스는 DROP INDEX로 되돌리고 캐시는 DB 스키마를 건드리지 않지만, 반정규화 컬럼은 모든 쓰기 경로가 그 컬럼을 함께 갱신해야 하는 영구적 의무를 만든다 — 한 번 들여오면 빼기가 훨씬 어렵다.

커버링 인덱스는 09 커버링 인덱스, 실측 절차는 10 EXPLAIN·슬로 쿼리 참고.

4. 정합성 안전망 3층 — 한 문장 안 · 한 경로 안 · 시간 축

"대가를 관리한다"를 구체적으로 말하는 절이다. 층마다 막는 것과 못 막는 것이 다르고, 위층에서 새는 것을 아래층이 받는다. 층의 이름을 범위로 외우면 순서가 안 헷갈린다 — 원자적 UPDATE는 한 문장 안, 트랜잭션은 한 경로 안, 보정 배치는 시간 축.

위층이 촘촘할수록 아래층이 받는 양이 줄지만, 층②가 완벽할 수 없는 이유(불변식이 앱 관례에 산다)가 구조적이라 층③은 생략 불가다.

4-1. before / after — posts.comment_count

게시글 목록 20건을 보여줄 때마다 댓글 수를 세는 상황. ②실측으로 병목 확인, ③인덱스·캐시로 부족 판단이 끝났다는 전제다.

❌ before — 정규화 그대로: 목록 한 페이지에 집계 조인
SELECT p.id, p.title,
       COUNT(c.id) AS comment_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id, p.title
ORDER BY p.created_at DESC
LIMIT 20;
-- 목록 20건을 위해 그 글들에 달린 댓글 수만큼
-- 행을 만나 집계한다. 트래픽 큰 목록 화면이면
-- 실측 병목으로 잡힐 수 있다.
✅ after — 연산 컬럼 도입 (편익 쪽)
ALTER TABLE posts
  ADD COLUMN comment_count INT NOT NULL DEFAULT 0;

SELECT p.id, p.title,
       p.comment_count      -- 조인·집계 없음
FROM posts p
ORDER BY p.created_at DESC
LIMIT 20;
-- 여기서 답을 끝내면 반쪽.
-- 아래 "대가 쪽" 코드가 함께 나와야 한다 ↓
❌ 새는 갱신 코드 2종 (층①·② 없음)
-- (1) 읽고 → 앱에서 +1 → 쓰기 : lost update
SELECT comment_count FROM posts WHERE id = ?;  -- 둘 다 10을 읽고
-- (앱) count = 10 + 1
UPDATE posts SET comment_count = 11 WHERE id = ?;  -- 둘 다 11을 쓴다
-- 댓글은 2개 늘었는데 카운트는 +1

-- (2) INSERT와 UPDATE가 따로 커밋 : 한쪽만 반영
INSERT INTO comments (post_id, author_id, body) VALUES (?, ?, ?);
COMMIT;
UPDATE posts SET comment_count = comment_count + 1 WHERE id = ?;
-- 여기서 실패하면 댓글만 남는다
✅ 층① 원자적 UPDATE + 층② 같은 트랜잭션
BEGIN;
INSERT INTO comments (post_id, author_id, body) VALUES (?, ?, ?);
UPDATE posts
   SET comment_count = comment_count + 1   -- 현재 값 위에서 +1 (행 락)
 WHERE id = ?;
COMMIT;  -- 하나라도 실패하면 함께 롤백

-- 대가: 댓글 쓰기가 posts 갱신 비용·실패까지 짊어진다.
-- UPDATE를 트랜잭션의 마지막 문장에 두면
-- 행 락 보유 시간이 그만큼 짧아진다 (§5 개입 ⑶)
✅ 층③ 보정 배치 + 드리프트 알람 — 어긋남을 전제로
-- 1) 드리프트 탐지: 원본 기준 재계산과 사본을 비교 (실전은 전체가 아니라 최근 변경분·표본 위주)
SELECT p.id, p.comment_count, COUNT(c.id) AS actual
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
WHERE p.id IN (/* 최근 N일 내 변경된 글 */)
GROUP BY p.id, p.comment_count
HAVING p.comment_count <> COUNT(c.id);   -- 어긋난 행. 건수가 임계를 넘으면 알람 → 새는 경로 추적

-- 2) 되돌리기: 사본을 원본 기준으로 덮어쓴다
UPDATE posts p
   SET p.comment_count = (SELECT COUNT(*) FROM comments c WHERE c.post_id = p.id)
 WHERE p.id IN (/* 위에서 어긋난 것으로 판정된 id */);
-- 드리프트는 막는 게 아니라 "주기적으로 0으로 되돌리는" 대상. 알람은 층②의 구멍(새 경로)을 찾는 신호.
암기 카드 — 안전망 3층은 "범위"로 외운다
① 한 문장 안 — 원자적 UPDATE  ·  ② 한 경로 안 — 같은 트랜잭션(또는 이벤트)  ·  ③ 시간 축 — 보정 배치 + 드리프트 알람

셋을 한 호흡에 말하면 "대가를 관리해본 사람"의 답. 그리고 ②가 왜 완벽할 수 없는지(불변식이 DB 제약이 아니라 앱 관례에 산다)까지 붙이면 ③이 왜 필수인지가 설명된다.

왜 다 묶어도 1년 뒤 어긋나나 — 불변식이 DB 제약이 아니라 애플리케이션 관례에 산다

FK나 UNIQUE는 DB가 지키므로 어떤 코드 경로로 들어와도 뚫리지 않는다. 반면 "comment_count = comments의 행 수"는 "댓글을 건드리는 모든 코드가 카운트도 함께 갱신하기로 한 약속"일 뿐이라, 약속을 모르는 경로가 하나만 생겨도 뚫린다 — 신입이 만든 관리자용 일괄 삭제 API(컴파일도 테스트도 통과), 운영 이슈로 콘솔에서 직접 실행한 DELETE, 나중에 추가된 "블라인드 처리" 경로(카운트를 어떻게 할지 정의조차 없음). DB가 지키는 제약과 앱이 지키는 관례의 차이는 34 FK 제약 논쟁과 같은 축이다.

5. 핫 로우 — "성능 저하"가 아니라 이름 붙은 사슬로 말하기

이 절이 이 페이지의 심장이다. 초당 수백 개 댓글이 달리는 인기 글에서 §4-1의 구조가 무슨 일을 겪는지 물었을 때, "성능이 저하되고 다른 요청도 문제가 생긴다"는 답과 아래 사슬을 이름으로 짚는 답은 전혀 다른 평가를 받는다. 사슬의 힘은 처방이 사슬의 고리에서 나온다는 데 있다 — "성능 저하"에서는 아무 처방도 안 나온다.

면접장 금지어
"성능이 저하된다" · "다른 요청도 문제가 생긴다" · "락 경합이 생긴다"(여기서 멈추기)

"락 경합"은 사슬의 첫 고리 이름일 뿐이다. 그 다음 칸 — 락은 한 번에 하나만 통과시키므로 동시 요청이 한 줄로 서서 직렬화된다 — 를 말해야 "왜 서버 증설로 안 풀리는지"와 "왜 커넥션이 마르는지"가 이어진다.

5-1. 사슬 흐름도 — "락 경합" 다음 칸이 제일 크다

고리를 짚으면 고리별 개입 지점이 보인다 — 경합 자체를 줄이거나(⑴), 락 보유 시간을 줄이거나(⑶), 풀을 보호하거나(⑷). "성능 저하"에서는 셋 중 아무것도 안 나온다.
암기 장치 — 5박자로 외우는 사슬 (마트 계산대 비유의 압축)
⑴락 경합줄 선다
⑵사실상 직렬화한 명씩만
⑶트랜잭션 장기화오래 걸린다
⑷커넥션 풀 고갈자리가 찬다
⑸전 서비스 전파남까지 막힌다

계산대가 백 개인 마트(서버·커넥션)에서 특정 상품 하나의 재고 장부(핫 로우)를 계산 때마다 고쳐야 하는데 그 장부에 펜이 하나뿐인 상황. 계산원들이 펜을 기다리며 계산대를 점유하고(⑶⑷), 그 상품과 무관한 손님까지 빈 계산대가 없어 줄을 선다(⑸).

5-2. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

뭉뚱그린 표현이름사슬로 말하면
"성능이 저하된다"락 경합 + 사실상 직렬화같은 행 락에 수백 트랜잭션이 줄 서서 동시성이 1로 붕괴 — 서버 증설로 해결 불가
"다른 요청도 문제가 생긴다"커넥션 풀 고갈 + 전파락 대기 트랜잭션이 커넥션을 쥔 채 장기화 → 풀 소진 → 무관한 요청까지 타임아웃
"락 경합이 생긴다" (여기서 끝)첫 고리만 말한 상태"그래서 락은 한 번에 하나만 통과시키니 한 줄로 서고 → 그동안 커넥션을 쥐고 있으니 → …"로 끝까지 완주

5-3. 처방 스케치 — 경합을 행에서 떼어내기 (각각의 대가와 함께)

핫 로우의 근본 원인은 "쓰기 지점이 행 하나로 수렴"이므로 처방은 수렴을 푸는 방향이다. 처방에도 대가가 붙는다 — 여기서도 한 호흡에.

비동기 집계 개입 ⑴

댓글 트랜잭션에서 카운트 UPDATE를 빼고 이벤트를 쌓아 모아서(배치로 묶어) 반영. 수백 번의 +1이 한 번의 +347이 된다.

  • 대가: 정합성이 "즉시"에서 "잠시 후"로 (최종적 일관성). 이벤트 유실·중복 처리(멱등성) 설계 필요
카운터 분산 (sharded counter) 개입 ⑴

카운터를 N개 행으로 쪼개 무작위로 하나에 +1, 읽을 때 SUM. 락 경합이 1/N로.

  • 대가: 읽기 때 N행 SUM 비용, 스키마·코드 복잡도
외부 카운터 개입 ⑴

Redis 같은 인메모리 카운터에 증가시키고 주기적으로 DB에 반영. DB 행에는 경합이 안 생긴다.

  • 대가: 두 저장소 관리, 유실 시 DB 원본 기준 재계산 필요 (층③이 더 중요해짐)
UPDATE 위치 조정 개입 ⑶

트랜잭션 안에서 핫 로우 UPDATE를 커밋 직전 마지막 문장에 두어 락 보유 시간을 최소화.

  • 대가: 거의 없음 — 대신 완화일 뿐, 수렴 자체는 남는다

핫 로우 카운터의 처방 상세는 23 고빈도 카운터·핫 로우, 락 대기가 커넥션을 쥐는 메커니즘은 16 긴 트랜잭션·15 커넥션 수 vs 처리량과 이어진다.

6. 웹툰 도메인 적용 훈련 — 같은 틀을 내 도메인에 돌려본다

작품(series) 테이블에 흔히 두는 후보 컬럼들을 4축과 안전망 3층으로 판정해 본다. 핵심은 같은 "연산 컬럼"이라도 쓰기 빈도에 따라 판정이 갈린다는 것 — episode_count와 like_count가 정확히 그 대비다.

후보 컬럼형태읽기 : 쓰기어긋나면핫 로우 위험관리 장치판정
series.episode_count
원본: episodes 행 수		 연산 (세어 두기) 목록·상세마다 읽음 : 회차 발행 시에만 씀 (작품당 주 1회 수준) "총 52화"가 51로 보임 — 경미하지만 눈에 띈다 낮음 — 작품당 쓰기가 드묾 발행/삭제/비공개 전환 트랜잭션 안에서 원자적 ±1 + 야간 보정 적합
series.like_count
원본: episode_likes 행 수		 연산 (세어 두기) 목록·랭킹마다 읽음 : 인기작은 쓰기도 폭주 근사치면 충분 — 사용자는 정확한 수를 검증하지 않음 높음 — 인기작 한 행에 쓰기 수렴 동기 UPDATE 대신 이벤트 적재 → 워커가 모아서 반영, 또는 Redis 카운터 + 주기 반영 + 보정 비동기로만
series.last_episode_at
원본: MAX(episodes.published_at)		 연산 (세어 두기) "최신 업데이트순" 정렬마다 읽음 : 발행 시에만 씀 정렬 순서가 틀림 — 노출에 직접 영향 낮음 발행 트랜잭션 안에서 갱신 + 인덱스로 정렬 지원 + 보정 적합
episodes.series_title
원본: series.title		 중복 (베껴 두기) 회차 화면마다 읽음 : 제목 변경은 드묾 회차마다 다른 제목 — 검색·목록 혼란 낮음 제목 변경 시 회차 수만큼 동기 일괄 UPDATE + 보정 조건부
PK 조인은 대개 싸다 — ②실측 병목일 때만
coin_purchases.episode_price
결제 당시 회차 가격		 스냅샷 — 어긋나야 정상 — 가격 인상 후에도 "그때 얼마 냈는지"가 사실 — 동기화 금지 (환불·정산 근거) 반정규화 아님
❌ 인기작 like_count를 좋아요마다 동기 UPDATE → 핫 로우
BEGIN;
INSERT INTO episode_likes (episode_id, user_id) VALUES (?, ?);
UPDATE series SET like_count = like_count + 1 WHERE id = ?;
-- 인기작 한 행에 수백 TPS가 수렴
-- → 락 경합 → 직렬화 → 장기화 → 풀 고갈 → 전파
COMMIT;
✅ 좋아요 트랜잭션에서 카운트 갱신을 떼어낸다
BEGIN;
INSERT INTO episode_likes (episode_id, user_id) VALUES (?, ?);
INSERT INTO like_events (series_id, delta) VALUES (?, +1);
-- 이벤트는 append — 같은 행 경합이 없다
COMMIT;

-- 워커가 N초마다 모아서 한 번에 반영
UPDATE series SET like_count = like_count + 347 WHERE id = ?;
-- 대가: "즉시" → "잠시 후". 좋아요 수는 근사치 허용이므로 지불 가능.
-- 코인 잔액이었다면 이 대가는 지불 불가 → 동기 트랜잭션 유지
판단 질문 하나 — "이 숫자가 틀리면 누가 손해를 보나?"
아무도 안 본다(좋아요 수) → 비동기·근사치 허용  ·  돈·권리가 걸린다(코인 잔액·구매 여부) → 동기 트랜잭션 + 정확

정합성 요구 수준을 먼저 정해야 어떤 관리 장치가 "충분"한지가 정해진다. 모든 사본에 같은 수준을 요구하면 핫 로우를 자초하거나, 반대로 돈에 근사치를 쓰는 사고가 난다.

6-1. 스냅샷 함정 — 동기화하면 안 되는 중복이 있다 시니어 변별

"주문 테이블에 상품명·가격을 복사해 두는 것도 반정규화인가요? 상품명이 바뀌면 동기화 배치를 돌려야 하나요?"는 함정 질문이다. 중복을 보면 먼저 물어야 한다 — 이 사본이 가리키는 사실이 현재의 사실인가, 과거 시점의 사실인가.

현재의 사실의 사본 — 반정규화

posts.comment_count, series.like_count, episodes.series_title

  • 원본과 어긋나면 오류
  • 동기화 장치(3층)가 필요
  • 원본 변경 → 사본도 따라간다
vs
과거 시점의 사실 — 스냅샷

orders.product_name, orders.price, coin_purchases.episode_price

  • 원본과 어긋나는 것이 정합성
  • 동기화하면 영수증·정산·환불 근거 파괴
  • 원본 변경 → 사본은 그대로

"중복은 다 동기화"로 접근하면 반정규화와 스냅샷을 같은 것으로 취급하는 것이고, 구분해서 말하면 중복의 의미론까지 설계해본 사람으로 변별된다.

7. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 답의 깊이가 갈리는 지점, 약점 겨냥은 이번 면접에서 흔들린 지점, 추가는 이 페이지에서 보탠 문항.

posts.comment_count 반정규화 — 무엇을 대가로 지불했고 어떻게 관리하나요?

대가: 갱신 정합성. 댓글이라는 원본과 카운트라는 사본이 어긋날 수 있는 부채가 생기고, 모든 댓글 쓰기 경로가 카운트 갱신 의무를 영구히 짊어진다.

관리 장치 3층을 한 호흡에 —

  1. 원자적 UPDATE(SET comment_count = comment_count + 1)로 읽고-더하고-쓰는 lost update 차단 (한 문장 안)
  2. 같은 트랜잭션으로 묶어 한쪽만 반영된 채 커밋되는 경로 차단 — 대신 댓글 쓰기가 posts 갱신 실패 시 함께 롤백되는 결합 비용 (한 경로 안)
  3. 주기적 보정 배치 + 드리프트 알람으로 그래도 새는 드리프트를 되돌리는 안전망 (시간 축)

셋을 이어 말하면 "대가를 관리해본 사람"의 답이 된다.

초당 수백 개 댓글이 달리는 인기 글이 되면 이 구조에서 무슨 일이 벌어지나요? 약점 겨냥

사슬을 이름으로 완주한다 — 모든 트랜잭션이 같은 posts 행을 UPDATE하는 핫 로우가 되고,

  1. 락 경합 — 배타적 행 락은 커밋까지 유지되므로 수백 트랜잭션이 락 하나에 줄 선다
  2. 사실상 직렬화 — 락은 한 번에 하나만 통과시키므로 동시성이 1로 붕괴, 서버 증설 무효
  3. 트랜잭션 장기화 — 락 대기만큼 수명이 늘고, 자기 락도 그만큼 오래 쥐어 대기가 대기를 키운다
  4. 커넥션 풀 고갈 — 대기 중에도 커넥션을 쥐고 있으므로 유한한 풀이 바닥난다
  5. 전 서비스 전파 — 풀은 서비스 공용이라 무관한 요청(로그인·결제)까지 타임아웃

이어서 처방을 고리에 연결한다 — 쓰기 수렴을 푸는 비동기 집계·카운터 분산·외부 카운터(⑴), 락 보유 시간을 줄이는 UPDATE 위치 조정(⑶), 풀 보호(⑷). "성능 저하"라고 답하는 순간, 그리고 "락 경합"에서 멈추는 순간 이 질문의 목적(비용을 사슬로 말하는가)에서 탈락한다.

같은 트랜잭션 + 원자적 UPDATE로 다 묶어도 1년 뒤 어긋날 수 있다 — 왜, 그리고 장기적으로 어떻게 유지하나요?

불변식이 DB 제약이 아니라 애플리케이션 관례에 살기 때문. FK처럼 DB가 지키는 규칙은 어떤 경로로 와도 뚫리지 않지만, "댓글을 건드리면 카운트도 갱신한다"는 코드의 약속일 뿐이라 — 약속을 모르는 새 코드 경로(일괄 삭제 API), 애플리케이션을 거치지 않는 DB 직접 수정, 정의가 누락된 신규 상태(블라인드 처리)가 뚫는다.

장기 유지는 드리프트를 전제로 한 주기적 보정 배치(원본 기준 재계산)가 답이며, 이것은 버그 대응이 아니라 설계에 처음부터 포함되는 안전망이다. 어긋난 건수에 알람을 걸어 두면 보정이 "새는 경로를 찾는 신호"로도 쓰인다.

반정규화를 하기 전에 먼저 검토해야 할 것은 무엇인가요?

순서가 답이다.

  1. 실측 — 실행 계획과 슬로 쿼리로 조인·집계가 진짜 병목인지 확인. "느릴 것 같아서"는 근거가 아니다.
  2. 더 싼 수단 먼저 — 인덱스 추가, 커버링 인덱스(조인·집계 대상 컬럼을 인덱스에 포함해 테이블 접근 제거), 캐시 계층(자주 읽는 목록이면 캐시 적중이 집계 자체를 없앤다). 인덱스는 되돌리기 쉽고 캐시는 스키마를 안 건드리는 반면, 반정규화 컬럼은 모든 쓰기 경로에 영구적 갱신 의무를 새기는 가장 비싼 수단이므로 마지막에.
  3. 그래도 필요하면 대가 지불 준비(관리 장치 3층)와 함께 도입한다.
주문 테이블에 상품명·가격을 복사해 두는 것도 반정규화인가요? 상품명이 바뀌면 동기화 배치를 돌려야 하나요? 시니어 변별가산점

함정 질문이다 — 동기화하면 안 되는 중복이 존재한다. orders.product_name, orders.price는 "지금의 상품 정보"의 사본이 아니라 "주문 시점에 무엇을 얼마에 샀는가"라는 역사적 사실의 스냅샷이다. 상품명이 바뀌거나 가격이 인상됐다고 과거 주문을 동기화하면 영수증·정산·환불 근거가 파괴된다 — 여기서는 원본과 어긋나는 것이 정합성이다.

즉 중복을 보면 먼저 묻는다: 이 사본이 가리키는 사실이 현재의 사실(comment_count — 어긋나면 오류, 동기화 장치 필요)인가, 과거 시점의 사실(주문 스냅샷 — 동기화가 오히려 오류)인가. 이 구분을 말하면 중복의 의미론까지 설계해본 사람으로 변별된다.

1NF · 2NF · 3NF를 한 문장씩, 웹툰 도메인 예와 함께 말해보세요. 추가
  • 1NF — 원자값. 모든 컬럼 값이 더 쪼갤 수 없어야 한다. series.genres = '로맨스,판타지'는 위반 → series_genres(series_id, genre) 행으로.
  • 2NF — 키 전체에 종속. 복합 키의 일부에만 종속하는 컬럼이 없어야 한다. PK (series_id, episode_no)인 회차 테이블의 series_title은 series_id에만 종속 → series로.
  • 3NF — 오직 키에만 종속. 비키 컬럼이 다른 비키 컬럼에 종속(이행 종속)하면 안 된다. episodes(author_id, author_name)의 작가명은 author_id에 종속 → authors로.

셋 다 "이 사실은 정말 이 행의 것인가"라는 같은 질문의 단계별 적용이고, 실무 스키마는 대개 3NF/BCNF를 기준점으로 삼는다.

정규화는 어디까지 하나요? 왜 보통 3NF 근처에서 멈추나요? 추가

정규화를 한 단계 올릴 때마다 테이블이 쪼개져 조회 시 조인 수가 늘어난다. 3NF까지는 흔한 이상 현상(부분 종속·이행 종속)을 막는 실익이 조인 비용을 압도하지만, 그 이상(BCNF의 특수 사례, 4NF의 다치 종속, 5NF의 조인 종속)은 실제로 그 이상 현상이 스키마에 있을 때만 의미가 있다.

답의 틀: "3NF를 기본선으로 두고, 그 이상은 특정 이상 현상이 확인될 때 적용하며, 반대로 3NF에서 조회 병목이 실측되면 §3의 4축을 거쳐 의도적으로 되돌린다." — 정규화와 반정규화가 하나의 저울 위에 있음을 보여주는 답이다.

좋아요 카운트 갱신을 같은 트랜잭션에서 빼고 이벤트로 옮기면 무엇이 달라지나요? 새로 생기는 대가는요? 추가시니어 변별

달라지는 것: ① 핫 로우 수렴이 풀린다 — 좋아요 트랜잭션은 append만 하고, 워커가 수백 개의 +1을 한 번의 +N으로 반영한다. ② 좋아요 쓰기가 series 갱신 비용과 실패에서 분리된다(결합 비용 해소). ③ 정합성이 "즉시"에서 "잠시 후"(최종적 일관성)로 바뀐다.

새로 생기는 대가:

  • 이벤트 유실·중복 — 워커가 죽거나 재시도하면 빠지거나 두 번 더해질 수 있다. 이벤트를 원본 트랜잭션과 같이 커밋(테이블에 적재)하고, 반영을 멱등하게(처리 위치 기록) 설계해야 한다.
  • 지연 노출 — 사용자가 누른 직후 숫자가 안 바뀌어 보일 수 있다. 화면에서 낙관적으로 +1 표시하는 식의 UX 보완이 붙는다.
  • 층③의 중요도 상승 — 경로가 늘어난 만큼 원본 기준 보정이 더 자주 필요하다.

이 대가를 지불할 수 있는 이유는 좋아요 수가 근사치 허용 데이터이기 때문이다. 코인 잔액이라면 같은 처방을 쓸 수 없다 — "이 숫자가 틀리면 누가 손해를 보나"가 처방을 결정한다.

집계(요약) 테이블이나 읽기 리플리카도 반정규화인가요? 추가

집계 테이블(예: 일별 작품 조회수 요약)은 연산 컬럼을 테이블 단위로 확장한 것이라 반정규화의 연장선이다 — 얻는 것은 OLTP 테이블에서 무거운 집계를 떼어내는 것, 내는 것은 "갱신 주기만큼의 지연"과 재계산 장치. 관리 장치의 형태가 "갱신 주기·재계산 배치"로 바뀔 뿐 틀은 같다 (21 대시보드 통계·OLTP/OLAP 분리).

읽기 리플리카는 데이터 전체의 중복이지만 정합성을 DB의 복제 메커니즘이 책임지므로, 애플리케이션이 관례로 지켜야 하는 반정규화와는 범주가 다르다. 다만 "복제 지연만큼 어긋난 값을 읽을 수 있다"는 대가는 같은 언어로 말할 수 있다 — 여기서도 편익과 대가를 한 호흡에.

"중복이 있다"와 "반정규화했다"는 어떻게 다른가요? 코드 리뷰에서 어떻게 구분하나요? 추가

자격 요건 두 가지로 판정한다. ① 의도적인가 — 어떤 사실을 어디에 복제했고 왜(어떤 조회 패턴·실측 병목) 그랬는지가 문서·마이그레이션·코드 주석에 남아 있는가. ② 대가 관리가 있는가 — 갱신 경로가 원자적 UPDATE·같은 트랜잭션(또는 이벤트)으로 묶여 있고, 보정 배치·알람이 존재하는가.

둘 중 하나라도 없으면 반정규화가 아니라 정규화 실패 또는 방치다. 리뷰에서 물을 질문은 "이 컬럼의 원본은 무엇이고, 원본이 바뀔 때 이 컬럼은 어느 코드가 따라 바꾸며, 어긋나면 누가 언제 알아차리나?" 세 개다.

한 줄 요약
정규화는 "하나의 사실은 한 곳에만"으로 수정 이상을 구조적으로 차단하고, 반정규화는 조회 패턴을 위해 의도적으로 중복·연산 값을 두되 그 대가(갱신 정합성)를 관리 장치(원자적 UPDATE + 같은 트랜잭션 + 보정 배치)와 함께 지불하는 결정이다. 선택 기준은 읽기:쓰기 비율 · 실측 병목 · 인덱스/캐시 선행 검토 · 대가 지불 준비의 4축이고, 핫 로우의 비용은 락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파라는 이름 붙은 사슬로 말한다.
