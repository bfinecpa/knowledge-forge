정규화 vs 반정규화
"조회 성능을 위해"에서 멈추면 반쪽짜리 정의다

면접 질문: "정규화와 반정규화란? 반정규화를 선택하는 기준은?"

핵심 관전 포인트 — 정규화는 "하나의 사실은 한 곳에만" — 중복을 없애 수정 이상(update anomaly)을 구조적으로 차단하는 설계다. 반정규화는 조회 패턴에 맞춰 의도적으로 중복·연산 값을 허용하고, 그 대가(갱신 정합성)를 관리하는 결정이다 — "대가 관리"까지 말해야 정의가 완성된다. 선택 기준은 4축: ① 읽기:쓰기 비율 ② 실측된 조인·집계 병목 ③ 인덱스·Index Only Scan·캐시 선행 검토 ④ 대가 지불 준비. PostgreSQL은 generated column·트리거·materialized view로 관리 장치 일부를 DB 안으로 끌어올 수 있지만, 다른 테이블을 세는 집계 컬럼은 어느 도구로도 FK 같은 선언적 제약이 되지 못한다 — 보정 배치가 끝까지 남는 이유다. 그리고 핫 로우의 비용은 "성능 저하"라는 뭉뚱그린 말 대신 락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파라는 이름 붙은 사슬로 말한다 — PostgreSQL에서는 UPDATE마다 쌓이는 죽은 튜플(bloat)이 그 위에 한 겹 더 얹힌다.
  • 1
    정규화는 규칙 목록이 아니라 한 문장이다 — "하나의 사실은 한 곳에만". 같은 사실이 여러 행에 복제돼 있으면 일부만 고쳐 DB가 같은 질문에 두 가지 답을 하는 상태(수정 이상)가 되고, 정규화는 이것을 개발자의 주의력이 아니라 테이블 구조 자체로 차단한다 — 고칠 곳이 하나뿐이면 어긋날 방법이 없다.
  • 2
    반정규화의 정의는 "의도적" + "대가 관리" 두 단어로 완성된다 — 조회 패턴을 위해 알고서 중복·연산 값을 들여오고, 그 대가인 갱신 정합성을 관리 장치와 함께 지불하는 결정이다. "조회가 빨라진다"에서 끊기면 트레이드오프의 한 면만 본 것이고, 관리 장치 3단(같은 트랜잭션 · 원자적 UPDATE · 보정 배치)까지 이어져야 양면이 조립된 답이다.
  • 3
    선택은 4축으로, 비용은 사슬로 말한다 — 읽기:쓰기 비율 · 실측 병목 · 더 싼 수단(인덱스·캐시) 선행 검토 · 대가 지불 준비. 그리고 인기 글의 핫 로우 비용은 락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파로, PostgreSQL이면 죽은 튜플·HOT 깨짐·VACUUM 추격 실패를 한 겹 더 얹는다.

0. 질문 + 출제 의도

질문: "정규화와 반정규화란? 반정규화를 선택하는 기준은?"

출제 의도: 교과서 정규화만 아는 사람과 "조회 패턴에 맞춰 의도적으로 중복을 허용하고 그 대가(갱신 정합성)를 관리"해본 사람을 구분한다. 대용량 조회 시스템은 반정규화 없이 성립하지 않는다. 즉 정규형 번호의 암기가 아니라 — 편익(조회 성능)과 대가(갱신 정합성)를 양면으로 조립해서, 언제 어떤 관리 장치와 함께 중복을 들여오는지의 실무 판단을 본다.

함정 — "정규화는 중복 제거, 반정규화는 조회 성능을 위해 중복 허용" 틀린 말은 아닌데 딱 절반이다. 반정규화의 정의에는 "그 대가를 관리한다"가 반드시 붙어야 하고, 대가를 말하지 못하면 중복을 들여온 것이 결정이 아니라 방치가 된다. 면접의 변별점은 정확히 이 지점이다.
이 페이지가 겨냥하는 약점 세 가지 ① "수정 이상"을 정의 없이 말하는 것 → 1절에서 실제 데이터 표로 세 가지 이상(수정·삽입·삭제)을 눈으로 보이고, 뿌리가 하나임을 도식으로 못 박는다.
② 편익만 말하고 대가를 못 대는 것 → 4·6절에서 정의의 나머지 반쪽과 관리 장치 3단이 각각 다른 실패 원인에 대응한다는 구조를 세운다.
③ 비용을 "성능 저하"로 뭉뚱그리는 것 → 8절에서 락 경합부터 전 서비스 전파까지의 사슬과 PostgreSQL의 죽은 튜플 축을 이름으로 붙여 세운다.
이 문서에서 쓰는 예제 두 개 ① employees / departments — 정규화 쪽 설명 전부(수정·삽입·삭제 이상, 1NF~3NF)가 이 하나의 테이블에서 나온다. ② posts / comments — 반정규화 쪽 설명 전부(comment_count, 관리 장치 3단, 핫 로우)가 여기서 나온다. 예제를 갈아타지 않으므로 앞 절의 그림을 그대로 이어서 보면 된다.

1. 먼저 "이상(anomaly)"부터 — 데이터로 본다

정규화를 설명할 때 가장 먼저 나오는 말이 수정 이상(update anomaly)인데, 이 말이 정의 없이 지나가면 그 뒤가 전부 뜬다. 그러니 데이터부터 본다.

수정 이상 = 같은 사실이 여러 행에 중복 저장돼 있을 때, 그중 일부만 고쳐서 데이터가 서로 모순되는 상태
"이상(anomaly)"은 "정상적인 연산(UPDATE 한 번)을 했는데 데이터가 비정상이 되는 현상"이라는 뜻이다

1-1. 수정 이상을 실제로 만들어 본다 — UPDATE 한 번으로

사고 조건을 잘못 걸었거나 배치가 중간에 끊겨 한 행만 반영됐다
UPDATE employees SET dept_phone = '02-100-0009' WHERE id = 1;   -- 한 행만 갱신됐다

 id | name   | dept_name | dept_phone
----+--------+-----------+-------------
  1 | 김하늘 | 개발1팀   | 02-100-0009   ← 새 번호
  2 | 이바다 | 개발1팀   | 02-100-0001   ← 옛 번호
  3 | 박구름 | 개발1팀   | 02-100-0001   ← 옛 번호

"개발1팀 대표번호가 뭐죠?"  →  DB가 두 가지 답을 내놓는다. 어느 쪽이 맞는지 DB는 모른다.
이 사고가 특히 고약한 이유 — 아무도 즉시 알아채지 못한다 문법 오류도, 제약 위반도 아니다. DB는 아무 불평 없이 이 모순을 받아들이고 계속 서비스한다. 그래서 이런 데이터는 몇 달 뒤 "리포트가 이상하다"는 신고로 발견되고, 그때는 어느 값이 진실인지 되짚을 방법이 없다. 로그도, 에러 알림도, 모니터링 지표도 아무것도 울리지 않았기 때문이다.

1-2. 삽입 이상 — 부서를 등록하려고 유령 직원을 만든다

 id | name   | dept_name  | dept_phone
----+--------+------------+-------------
  9 | (NULL) | 플랫폼팀   | 02-100-0003   ← 부서를 등록하려고 만든 가짜 직원 행

이제 "직원 수를 세시오"라는 모든 쿼리가 이 유령을 어떻게 걸러낼지 신경 써야 한다.
스키마의 결함이 애플리케이션 곳곳의 WHERE 조건으로 번지는 순간이다.

이상 3종 3초 인출 — 수 · 삽 · 삭, 그리고 "뿌리는 하나"

수정 이상·삽입 이상·삭제 이상→한 행에 두 사실이 묶여 있다
수정
일부만 고쳐 모순 — 같은 질문에 두 가지 답
삽입
딸린 것이 없으면 등록 불가 — 유령 행을 만들게 된다
삭제
마지막 행을 지우면 다른 사실까지 증발

면접 답변 형태: "세 가지가 따로 있는 게 아니라, 독립적인 두 사실이 한 행에 묶여서 생기는 같은 문제의 세 얼굴입니다."

2. 정규화 = "하나의 사실은 한 곳에만"

정규화의 본질은 규칙 목록(1NF, 2NF, ...)이 아니라 하나의 원칙이다.

하나의 사실(fact)은 데이터베이스에서 정확히 한 곳에만 존재해야 한다

같은 사실이 여러 곳에 흩어져 있으면 수정할 때 전부 찾아 고쳐야 하고, 하나라도 놓치면 1절에서 본 "같은 질문에 DB가 두 가지 답을 하는" 상태가 된다. 정규화는 이것을 코드 리뷰나 개발자의 주의력이 아니라 테이블 구조 자체로 차단한다.

before "부서 이름"이라는 하나의 사실이 직원 수만큼 복제됨
CREATE TABLE employees (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name       text NOT NULL,
    dept_name  text,           -- '개발1팀'이 소속 직원 300행에 흩어져 있다
    dept_phone text            -- 대표번호도 마찬가지로 300벌
);
-- 부서 이름이 바뀌면? UPDATE employees SET dept_name = ... WHERE dept_name = ...
-- 조건을 잘못 쓰거나 일부 행만 갱신되면 → 한 부서에 두 이름 (수정 이상)
-- 직원이 없는 부서는 등록 자체가 불가 (삽입 이상)
-- 마지막 직원을 지우면 부서까지 사라짐 (삭제 이상)
after 부서라는 사실은 departments에 딱 한 곳
CREATE TABLE departments (
    id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name  text NOT NULL,        -- '개발1팀'은 여기 한 행에만 존재
    phone text
);
CREATE TABLE employees (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name    text NOT NULL,
    dept_id bigint NOT NULL REFERENCES departments (id)  -- 복제 대신 참조(FK)
);
CREATE INDEX ON employees (dept_id);  -- PG는 FK 컬럼 인덱스를 자동으로 만들지 않는다놓치기 쉬움
-- 부서 이름 변경 = departments 한 행 UPDATE. 어긋날 "다른 곳"이 구조적으로 없다.
-- 직원 없는 부서도 등록 가능. 마지막 직원을 지워도 부서는 남는다.
비유 — 복사본 체제 vs 원본 한 페이지 + 링크 회사 규정을 각 팀이 복사해 갖는 것(정규화 전)과, 원본은 사내 위키 한 페이지에만 두고 각 팀은 링크만 갖는 것(정규화)의 차이다. 복사본 체제에서는 개정 때마다 전 팀을 돌며 바꿔야 하고, 한 팀이라도 옛 버전을 들고 있으면 사고가 난다. 링크 체제에서는 원본 한 곳만 고치면 전원이 즉시 새 버전을 본다.

3. 정규형은 암기 목록이 아니라 "이 단계가 무엇을 막는가"의 체크리스트다

정규형을 1NF·2NF·3NF라는 번호로 외우면 면접에서 아무 쓸모가 없다. 각 단계는 "위반하면 어떤 이상이 생기는가"로 읽어야 판단에 쓰인다. 세 단계를 그 관점으로 정리한다.

정규형 3초 인출 — 칸 · 일부 · 이행

1NF
칸
한 칸에 값 하나 — 쉼표 이어붙이기·반복 컬럼 금지
2NF
일부
복합 PK의 일부에만 딸린 컬럼 금지 (부분 종속)
3NF
이행
비-PK를 거쳐 가는 종속 금지 (이행적 종속)

셋 다 "고칠 곳을 하나로"라는 같은 목적의 서로 다른 검사다. 실무의 기본선은 3NF까지이고, 그 위(BCNF·4NF)는 후보 키가 여러 개 겹치는 특수한 모양에서 등장한다.

PostgreSQL에서 1NF의 선을 넘기가 유난히 쉬운 이유 PostgreSQL은 배열과 jsonb를 지원해서 한 칸에 값을 여러 개 담는 일이 문법적으로 자연스럽다. 넘는 순간 그 안의 값은 타입 제약·FK·통계·일반 인덱스의 대상에서 벗어난다는 것을 알고서 넘어야 한다. "쓰면 안 된다"가 아니라 "무엇을 포기하는지 알고 쓴다"가 기준이다.

4. 반정규화 — 두 형태, 그리고 정의의 나머지 반쪽

4-1. 반정규화가 들여오는 중복은 두 형태다

4-2. 정의를 완성하는 나머지 반쪽 — "의도적" + "대가 관리"

여기가 이 주제의 첫 번째 핵심이다. 반정규화를 "조회 성능을 위해 중복을 두는 것"까지만 말하면 편익만 말한 반쪽 정의다. 완성된 정의는 이렇다.

완성된 정의 — 이 문장을 통째로 외운다

반정규화 = 조회 패턴에 맞춰 의도적으로 중복·연산 값을 허용하고,
그 대가(갱신 정합성)를 관리 장치와 함께 지불하는 결정
"의도적"
설계를 몰라서 생긴 중복은 반정규화가 아니라 그냥 정규화 실패다. 반정규화는 정규화된 설계를 알고서 되돌리는 결정이고, 어떤 사실을 어디에 복제했는지가 문서와 코드에 드러나야 한다.
"대가 관리"
중복을 두는 순간 "원본과 사본이 어긋날 수 있다"는 부채가 생긴다. 이 부채를 갚는 장치(같은 트랜잭션 · 원자적 UPDATE · 보정 배치)가 함께 설계되지 않은 중복은 결정이 아니라 방치다.
면접의 변별점은 정확히 여기다 — 편익과 대가를 한 호흡에 말하는가 "조회가 빨라진다"에서 끊기면 트레이드오프의 한 면만 본 것이고, "대신 갱신 정합성이라는 대가가 생기며 이를 이렇게 관리한다"까지 이어져야 양면이 조립된 답이다. ④가 빠진 반정규화 제안은 "대출로 뭘 살지"만 정하고 상환 계획이 없는 것과 같다.

5-1. before — 정규화 그대로의 집계 조인

게시글 목록 20건을 보여줄 때마다 댓글 수를 세는 상황이다.

before 목록 한 페이지에 집계 조인이 붙는다
SELECT p.id, p.title, count(c.id) AS comment_count
FROM posts p
LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id          -- PK로 묶으면 p.title은 함수 종속으로 인정돼 GROUP BY에 안 써도 된다
ORDER BY p.created_at DESC
LIMIT 20;
-- 목록 20건을 위해 그 글들에 달린 댓글 수만큼 행을 만나 집계한다.
-- 계획을 보면 Limit 아래의 집계 노드는 posts 전체를, 조인 노드는 comments
-- 전체를 훑는다(actual rows가 20이 아니다).
-- 트래픽이 큰 목록 화면이라면 이 비용이 실측 병목으로 잡힐 수 있다.
여기서 곧바로 반정규화로 뛰지 않는다 ②실측으로 병목을 확인하고 ③인덱스·캐시로는 부족하다는 판단이 끝났을 때 비로소 posts.comment_count 연산 컬럼을 도입한다. ③에서 실제로 먼저 시도해 볼 것들: comments(post_id) 인덱스(이것만 있어도 count(*)는 Index Only Scan으로 셀 수 있다 — VACUUM이 visibility map을 신선하게 유지한다는 전제에서), 쿼리 형태 변경(목록 20건을 먼저 자르고 그 20건만 상관 서브쿼리로 세면 집계 범위가 전체에서 20건으로 준다), 캐시 계층(자주 읽는 목록이면 캐시 적중이 집계 자체를 없앤다).

6. after — posts.comment_count와 3단 관리 장치

3단은 "겹겹이 쌓은 같은 방어"가 아니다. 서로 다른 세 가지 실패 원인에 각각 대응하는 세 장치이고, 하나가 다른 하나를 대신하지 못하기 때문에 셋 다 필요하다.

6-1. 컬럼 추가부터 — PostgreSQL에서 조심할 한 줄

ALTER TABLE posts ADD COLUMN comment_count integer NOT NULL DEFAULT 0;
-- 상수 DEFAULT의 컬럼 추가는 테이블을 다시 쓰지 않고 카탈로그만 바꾼다(PG 11+).
-- 다만 ACCESS EXCLUSIVE 잠금은 잡으므로 SET lock_timeout = '2s' 와 함께 실행한다.
--   → 잠금을 기다리는 동안 그 뒤에 도착한 SELECT까지 대기열에 서기 때문이다.

6-2. 장치 ① 같은 트랜잭션 — 원본과 사본의 운명을 묶는다

BEGIN;
INSERT INTO comments (post_id, author_id, body) VALUES ($1, $2, $3);
UPDATE posts SET comment_count = comment_count + 1 WHERE id = $1;
COMMIT;
-- 카운트 갱신이 실패하면 댓글 INSERT도 함께 롤백 — 어긋난 채 커밋되는
-- 경로를 트랜잭션이 막는다. (대가: 댓글 쓰기가 posts 갱신 비용까지 짊어짐)

6-3. 장치 ② 원자적 UPDATE — 값을 읽어와 더하지 않는다

6-4. 장치 ③ 주기적 보정 배치 — 어긋남을 전제로 한 안전망

UPDATE posts p
SET    comment_count = c.cnt
FROM  (SELECT p2.id, count(c2.id) AS cnt
       FROM posts p2 LEFT JOIN comments c2 ON c2.post_id = p2.id
       GROUP BY p2.id) c
WHERE  c.id = p.id
  AND  p.comment_count IS DISTINCT FROM c.cnt;   -- 이미 맞는 행은 건드리지 않는다
-- PG의 UPDATE는 값이 같아도 새 튜플 버전을 쓴다(죽은 튜플 + WAL + 인덱스
-- 갱신 가능성). 위 가드가 없으면 보정 배치가 posts 전체를 매번 다시 쓰는 셈이다.
-- (실전에서는 전체가 아니라 최근 변경분·표본 검증 위주로 돈다)

관리 장치 3단 3초 인출 — 트 · 원 · 보

트 = 같은 트랜잭션→원 = 원자적 UPDATE→보 = 보정 배치
트 — 예방
단일 요청의 원자성
한쪽만 반영된 채 커밋되는 경로 차단
원 — 예방
동시 요청의 격리
읽고-더하고-쓰기의 lost update 차단
보 — 복구
코드 밖에서 오는 변경
드리프트를 원본 기준으로 되돌림

외우는 짝: "트=한 요청 / 원=동시 요청 / 보=코드 밖". 이 짝만 붙이면 "왜 셋 다 필요한가"가 자동으로 설명된다.

7. 다 묶어도 왜 어긋나나 — 그리고 PostgreSQL이 주는 도구들

장치 ①②를 다 갖춰도 1년 뒤 comment_count는 실제와 어긋날 수 있다. 이유는 하나로 요약된다.

불변식 "comment_count = comments의 행 수"가
DB 제약이 아니라 애플리케이션의 관례로만 존재하기 때문

7-1. 실제로 뚫리는 세 경로

새 코드 경로
신입이 만든 관리자용 댓글 일괄 삭제 API가 카운트 갱신을 빼먹는다. 컴파일도 테스트도 통과한다.
DB 직접 수정
운영 이슈로 콘솔에서 DELETE FROM comments ...를 직접 실행 — 애플리케이션의 약속은 애초에 거치지 않는다.
경로 비대칭
작성 경로는 +1을 하는데, 나중에 추가된 "블라인드 처리" 경로는 카운트를 어떻게 할지 정의조차 안 돼 있다.

7-2. PostgreSQL 도구 4종 — 관례를 DB 안으로 얼마나 옮길 수 있나

PostgreSQL에는 이 관례를 DB 쪽으로 옮겨 주는 도구가 몇 개 있는데, 각각 옮겨 주는 범위가 다르다. 무엇을 DB가 대신 져 주고 무엇이 여전히 내 몫인지가 선택 기준이다.

도구DB가 대신 져 주는 것여전히 내 몫
generated column
GENERATED ALWAYS AS (...) STORED (PG 12+)		같은 행 안의 연산 값 계산·저장 — 어긋날 경로 자체가 없다다른 테이블을 참조하는 식은 불가 → comment_count에는 못 쓴다
트리거
AFTER INSERT OR DELETE ON comments		콘솔 DELETE·새 코드 경로까지 모든 쓰기가 카운트 갱신을 거친다절차적 코드라 우회 가능(트리거 비활성화, session_replication_role = replica), 핫 로우 비용은 그대로
materialized view
REFRESH MATERIALIZED VIEW CONCURRENTLY		집계 결과를 통째로 스냅샷 — 쓰기 경로를 안 건드린다신선도가 REFRESH 주기에 묶임, CONCURRENTLY는 유니크 인덱스 필수, 매번 전체 재계산
jsonb·배열에 자식 데이터 내장1:N 조인을 없앤다부분 갱신 없음 — 원소 하나 바꿔도 값 전체를 새 튜플로 재기록
same-row 같은 행 안의 연산 값이면 generated column — 드리프트가 구조적으로 불가능
ALTER TABLE order_items
    ADD COLUMN amount numeric GENERATED ALWAYS AS (qty * unit_price) STORED;
cross-table 다른 테이블을 세는 값이면 트리거로 "관례"를 DB 안으로 — 단, 선언적 제약은 아니다
CREATE FUNCTION bump_comment_count() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        UPDATE posts SET comment_count = comment_count + 1 WHERE id = NEW.post_id;
    ELSIF TG_OP = 'DELETE' THEN
        UPDATE posts SET comment_count = comment_count - 1 WHERE id = OLD.post_id;
    END IF;
    RETURN NULL;   -- AFTER 트리거의 반환값은 무시된다 (댓글의 post_id 변경 처리는 생략)
END $$;
CREATE TRIGGER trg_comment_count
AFTER INSERT OR DELETE ON comments
FOR EACH ROW EXECUTE FUNCTION bump_comment_count();
트리거를 고를 때 함께 드는 대가 세 가지 ① 갱신 로직이 애플리케이션 코드 밖으로 나가므로 git grep comment_count로는 안 잡히고, 트랜잭션이 왜 느린지 추적할 때 계획에도 잘 안 드러난다.
② 대량 적재 성능 때문에 트리거를 꺼 두는 순간 그 구간은 그대로 뚫린다.
③ 행 단위 트리거라 댓글 1만 건을 한 문장으로 INSERT해도 UPDATE가 1만 번 발생한다 — 8절의 핫 로우 사슬을 오히려 키운다.

도구 선택 규칙 — 한 줄로 정리된다

사본의 원본이 같은 행 안
generated column
어긋날 경로 자체가 없다
원본이 다른 테이블
트리거 또는 앱 트랜잭션 + 보정 배치
"잠시 후"로 느슨해도 됨
materialized view
쓰기 경로를 안 건드린다
어느 도구를 써도 — 다른 테이블을 세는 집계 컬럼은 FK·UNIQUE 같은 선언적 제약이 되지 못한다
그래서 장치 ③(보정 배치)은 도구 선택과 무관하게 끝까지 남는다

8. 핫 로우 — "성능 저하"가 아니라 이름 붙은 사슬로 말하기

초당 수백 개 댓글이 달리는 인기 글에서 6절의 구조가 무슨 일을 겪는지 물었을 때, "성능이 저하되고 다른 요청도 문제가 생긴다"는 답과 아래 사슬을 이름으로 짚는 답은 전혀 다른 평가를 받는다.

모든 댓글 트랜잭션이 UPDATE posts ... WHERE id = 인기글 — 같은 행 하나를 갱신한다. 이런 행을 핫 로우(hot row)라 부른다. 그 다음은 필연의 연쇄인데, 갈래가 둘이다.

비유 — 계산대는 백 개인데 그 장부의 펜은 하나 계산대가 백 개인 마트(서버·커넥션)에서 특정 상품 하나의 재고 장부(핫 로우)를 계산 때마다 반드시 고쳐야 하는데, 그 장부에 펜이 하나뿐인 상황이다. 계산대가 아무리 많아도 모든 계산원이 펜 하나를 기다리며 계산대를 점유하고, 그 상품과 무관한 손님까지 빈 계산대가 없어 줄을 선다.

사슬 5고리 3초 인출 — 경 · 직 · 장 · 고 · 전

경 = 락 경합→직 = 사실상 직렬화→장 = 트랜잭션 장기화→고 = 커넥션 풀 고갈→전 = 전 서비스 전파

PostgreSQL이면 한 축을 더 얹는다 — 새 튜플 버전 → 죽은 튜플 축적 → 페이지 여유 소진 → HOT 깨짐 → 인덱스 갱신 → autovacuum 추격 실패 → bloat.

가장 중요한 한 마디: "⑵에서 동시성이 사실상 1로 붕괴하므로 서버 증설로는 해결되지 않는다" — 병목이 CPU가 아니라 행 하나이기 때문이다.

8-1. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

뭉뚱그린 표현이름사슬로 말하면
"성능이 저하된다"락 경합 + 사실상 직렬화같은 행 락에 수백 트랜잭션이 줄 서서 동시성이 1로 붕괴 — 서버 증설로 해결 불가
"다른 요청도 문제가 생긴다"커넥션 풀 고갈 + 전파락 대기 트랜잭션이 커넥션을 쥔 채 장기화 → 풀 소진 → 무관한 요청까지 타임아웃
"DB가 좀 무거워졌다"죽은 튜플 + VACUUM 추격 실패UPDATE마다 새 튜플 버전 → 페이지 여유 소진 → HOT 깨짐 → 인덱스 갱신 → bloat → 조회까지 느려짐

8-2. 처방 스케치 — 경합을 행에서 떼어내기

핫 로우의 근본 원인은 "쓰기 지점이 행 하나로 수렴"이므로, 처방은 수렴을 푸는 방향이다.

비동기 집계
댓글 트랜잭션에서 카운트 UPDATE를 빼고, 이벤트를 모아서 배치로 반영한다. N건을 + N 한 번으로 반영하면 락 횟수도 새 튜플 버전도 1/N. 대가: 정합성이 "즉시"에서 "잠시 후"로 느슨해진다
카운터 분산 (sharded counter)
카운터를 N개 행으로 쪼개 무작위로 하나에 +1 하고, 읽을 때 SUM 한다. 락 경합이 1/N. 대가: 읽기가 N행 집계가 되고 그 컬럼으로 정렬·인덱스를 못 쓴다
외부 카운터
Redis 같은 인메모리 카운터에 증가시키고 주기적으로 DB에 반영. DB 쓰기가 극적으로 줄지만 대가: 반영 주기만큼의 유실 창 + 이중 소스 관리
락 보유 시간 줄이기
트랜잭션 안에서 UPDATE를 커밋 직전(마지막 문장)에 두면 락을 쥐는 구간이 짧아진다 — ⑶ 고리에 대한 직접 개입
PostgreSQL 물리 설계 위생
posts의 fillfactor를 낮춰 HOT 업데이트 여지를 넓힌다. 새 버전이 같은 페이지에서 소화되면 인덱스 갱신과 bloat 확산이 준다. 그리고 카운터 컬럼에는 인덱스를 걸지 않는다.
결정의 순서 — 이게 먼저다
이 카운터가 "정확해야 하는 숫자"인지 "대략 맞으면 되는 숫자"인지가 먼저다. 조회수는 뒤쪽이라 비동기·외부 카운터가 성립하지만, 결제 잔액이나 재고는 앞쪽이라 같은 처방을 쓰면 안 된다.

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

정규화 한 문장 정의?

수 · 삽 · 삭 — 뿌리는 하나: 독립적인 두 사실이 한 행에 묶여 한쪽 연산이 다른 쪽을 건드린다.
정규형 1·2·3?
칸 · 일부 · 이행 — 한 칸에 값 하나 / 복합 PK의 일부에 딸리지 않기 / 비-PK를 거쳐 가는 종속 금지.
선택 기준 4축?
비율 · 실측 · 더 싼 수단 · 대가 준비. ③의 이유: 인덱스는 되돌리기 쉽고 캐시는 스키마를 안 건드리지만, 반정규화는 모든 쓰기 경로에 영구적 의무를 새긴다.
관리 장치 3단과 담당?
트 · 원 · 보 — 트=한 요청의 원자성 / 원=동시 요청의 격리 / 보=코드 밖에서 오는 변경. 앞의 둘은 예방, 셋째는 복구.
다 묶었는데 왜 어긋나나?
불변식이 DB 제약이 아니라 애플리케이션 관례에 살기 때문. FK는 어떤 경로로 와도 안 뚫리지만, 약속은 모르는 경로 하나면 뚫린다.
핫 로우 사슬?
경 · 직 · 장 · 고 · 전 — 락 경합 → 사실상 직렬화(증설 무효) → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파. PG는 죽은 튜플·HOT 깨짐·bloat 한 겹 더.
PG 도구 선택 규칙?
원본이 같은 행 안 → generated column / 다른 테이블 → 트리거 또는 앱 트랜잭션 + 보정 배치 / "잠시 후" 허용 → materialized view. 어느 쪽이든 보정 배치는 남는다.
동기화하면 안 되는 중복은?
orders.product_name·price는 과거 시점의 스냅샷이다. 여기서는 원본과 어긋나는 것이 정합성 — 동기화가 오히려 오류다.

9-2. 핵심 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

posts.comment_count 반정규화 — 무엇을 대가로 지불했고 어떻게 관리하나요? 필수힌트: 대가를 한 단어로 먼저 못 박고, 장치 3단을 "각각 무엇을 막는지"와 짝지어 말한다

대가는 갱신 정합성이다. 댓글이라는 원본과 카운트라는 사본이 어긋날 수 있는 부채가 생기고, 모든 댓글 쓰기 경로가 카운트 갱신 의무를 영구히 짊어진다.

관리 장치 3단 — ① 같은 트랜잭션으로 묶어 한쪽만 반영된 채 커밋되는 경로를 차단한다(대신 댓글 쓰기가 posts 갱신 실패 시 함께 롤백되는 결합 비용을 진다). ② 원자적 UPDATE(SET comment_count = comment_count + 1)로 읽고-더하고-쓰는 lost update를 차단한다. ③ 주기적 보정 배치로 그래도 새는 드리프트를 되돌린다.

여기까지 오면 완성된다 — "셋이 각각 다른 실패 원인에 대응합니다: 단일 요청의 원자성 / 동시 요청의 격리 / 코드 밖에서 오는 변경"

왜 이 한 문장이 결정적인가. 3단을 나열만 하면 "들어본 사람"이고, 각 장치가 못 막는 것까지 말하면 "대가를 관리해본 사람"이 된다 — 장치 ①은 동시 요청의 덮어쓰기를 못 막고, 장치 ②는 아예 UPDATE를 실행하지 않는 경로를 못 막으며, 장치 ③은 실시간 정확성을 못 준다.

초당 수백 개 댓글이 달리는 인기 글이 되면 이 구조에서 무슨 일이 벌어지나요? 필수힌트: "성능 저하"라고 말하는 순간 이 질문의 목적에서 탈락한다. 사슬을 이름으로 완주한다

모든 트랜잭션이 같은 posts 행을 UPDATE하는 핫 로우가 되고, 그 다음은 필연의 연쇄다.

락 경합→사실상 직렬화→트랜잭션 장기화→커넥션 풀 고갈→전 서비스 전파

UPDATE는 그 행의 배타 락을 커밋까지 쥐고, 락은 한 번에 하나만 통과시키므로 수백 개 "동시" 요청이 한 줄로 선다 — 서버를 늘려도 소용없다. 병목이 CPU가 아니라 행 하나이기 때문이다. 줄 뒤쪽 트랜잭션은 대기 시간만큼 수명이 늘고, 기다리는 동안에도 DB 커넥션을 쥐고 있으므로 풀이 바닥난다. 풀은 서비스 공용이라 로그인·결제 같은 무관한 요청까지 타임아웃된다.

PostgreSQL이면 두 번째 축을 덧붙인다 — UPDATE마다 새 튜플 버전이 쌓여 페이지 여유가 마르고, HOT이 깨지면 다른 인덱스까지 갱신되며, autovacuum이 못 따라잡아 bloat이 남아 조회까지 느려진다.

이어서 처방을 고리에 연결하면 답이 닫힌다 — 쓰기 수렴을 푸는 비동기 집계·카운터 분산·외부 카운터, 락 보유 시간을 줄이는 UPDATE 위치 조정(커밋 직전으로), 물리 설계의 fillfactor 조정. 그리고 그 전에 "이 숫자가 정확해야 하는가, 대략 맞으면 되는가"를 먼저 가른다.

같은 트랜잭션 + 원자적 UPDATE로 다 묶어도 1년 뒤 어긋날 수 있다 — 왜, 그리고 장기적으로 어떻게 유지하나요? 시니어 변별힌트: 한 문장으로 원인을 못 박고, FK와의 대비를 든다

불변식이 DB 제약이 아니라 애플리케이션 관례에 살기 때문이다. FK나 UNIQUE는 DB가 지키므로 어떤 코드 경로로 들어와도 뚫리지 않지만, "댓글을 건드리면 카운트도 갱신한다"는 코드의 약속일 뿐이라 약속을 모르는 경로가 하나만 생겨도 뚫린다.

실제로 뚫는 셋 — ① 새 코드 경로(관리자용 일괄 삭제 API가 카운트 갱신을 빼먹는다. 컴파일도 테스트도 통과한다) ② DB 직접 수정(운영 이슈로 콘솔에서 DELETE FROM comments) ③ 경로 비대칭(나중에 추가된 "블라인드 처리"는 카운트를 어떻게 할지 정의조차 안 돼 있다).

장기 유지의 답은 드리프트를 전제로 한 주기적 보정 배치(원본 기준 재계산)이며, 이것은 버그 대응이 아니라 설계에 처음부터 포함되는 안전망이다. 드리프트는 막는 게 아니라 "주기적으로 0으로 되돌리는" 대상이라는 관점이 핵심이다.

트리거를 얹으면? "직접 수정"과 "새 코드 경로"는 막히지만, 대량 적재 때 트리거를 꺼 두는 구간이 다시 구멍이 되므로 보정 배치는 여전히 남는다.

반정규화를 하기 전에 먼저 검토해야 할 것은 무엇인가요? 필수힌트: 항목 나열이 아니라 "순서"가 답이다

순서가 답이다.

① 실측 — EXPLAIN (ANALYZE, BUFFERS)와 pg_stat_statements로 조인·집계가 진짜 병목인지 확인한다. "느릴 것 같아서"는 근거가 아니다.

② 더 싼 수단 먼저 — 인덱스 추가(comments(post_id) 인덱스만 있어도 count(*)는 Index Only Scan으로 셀 수 있다 — VACUUM이 visibility map을 신선하게 유지한다는 전제에서), 쿼리 형태 변경(목록 20건을 먼저 자르고 그 20건만 상관 서브쿼리로 세면 집계 범위가 전체에서 20건으로 준다), 애플리케이션·캐시 계층(자주 읽는 목록이면 캐시 적중이 집계 자체를 없앤다).

인덱스는 되돌리기 쉽고 캐시는 스키마를 안 건드리는 반면,
반정규화 컬럼은 모든 쓰기 경로에 영구적 갱신 의무를 새기는 가장 비싼 수단이다

③ 그래도 필요하면 대가 지불 준비(관리 장치 3단)와 함께 도입한다. ④가 빠진 반정규화 제안은 "대출로 뭘 살지"만 정하고 상환 계획이 없는 것과 같다.

주문 테이블에 상품명·가격을 복사해 두는 것도 반정규화인가요? 상품명이 바뀌면 동기화 배치를 돌려야 하나요? 함정시니어 변별힌트: "네, 동기화해야죠"라고 답하는 순간 걸린다. 동기화하면 안 되는 중복이 있다

함정 질문이다 — 동기화하면 안 되는 중복이 존재한다.

현재의 사실을 가리키는 사본

posts.comment_count — 원본(comments)이 지금 무엇인가를 복제한 것. 어긋나면 오류이고, 그래서 동기화 장치(3단)가 필요하다.

과거 시점의 사실을 박제한 스냅샷

orders.product_name·orders.price — "주문 시점에 무엇을 얼마에 샀는가"라는 역사적 사실. 원본과 어긋나는 것이 곧 정합성이다.

상품명이 바뀌거나 가격이 인상됐다고 과거 주문의 값을 동기화하면 영수증·정산·환불 근거가 파괴된다. 즉 여기서는 "안 고치는 것"이 올바른 동작이다.

중복을 보면 먼저 물어야 한다 — "이 사본이 가리키는 사실이 현재의 사실인가, 과거 시점의 사실인가?"

이 구분 없이 "중복은 다 동기화"로 접근하면 반정규화와 스냅샷을 같은 것으로 취급하는 것이고, 구분해서 말하면 중복의 의미론까지 설계해본 사람으로 변별된다. 덧붙이면 — 스냅샷 컬럼에는 "이 값은 갱신하지 않는다"는 의도를 스키마 주석이나 문서에 남겨야 다음 사람이 "동기화가 안 돼 있네요"라며 배치를 만들지 않는다.

MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 네 지점 — 저장 비용 · 같은 값 UPDATE · 문법 · 도구

① 카운터 UPDATE의 저장 비용 — InnoDB는 행을 제자리에서 고치고 옛 값을 언두 로그로 빼내지만, PostgreSQL은 새 튜플 버전을 삽입하고 옛 버전을 죽은 튜플로 남긴다. 락 직렬화 사슬은 둘 다 같지만, PostgreSQL은 그 위에 bloat과 VACUUM 추격이 한 겹 더 있다.

② 같은 값으로의 UPDATE — MySQL은 값이 안 바뀌면 행을 건드리지 않지만, PostgreSQL은 값이 같아도 새 버전을 쓴다. 그래서 보정 배치의 IS DISTINCT FROM 가드가 PostgreSQL에서는 선택이 아니라 필수다.

③ 문법 — 보정 배치는 PostgreSQL이 UPDATE ... FROM, MySQL이 UPDATE ... JOIN이고, MySQL의 SET p.col = ...처럼 SET에 테이블 한정자를 붙이면 PostgreSQL은 에러다.

④ 도구 — materialized view는 PostgreSQL에만 있고(MySQL은 집계 테이블 + 배치를 직접 짠다), JSON 부분 갱신은 반대로 MySQL 8.0에만 있다(PostgreSQL jsonb는 값 전체 재기록). 컬럼 추가는 PostgreSQL 11+가 상수 DEFAULT를 카탈로그만 바꾸고 MySQL 8.0은 ALGORITHM=INSTANT로 같은 효과를 내는데, PostgreSQL은 ACCESS EXCLUSIVE 대기열이 뒤의 SELECT까지 세우므로 lock_timeout이 붙어야 한다.

9-3. 추가 꼬리질문 — 한 칸씩 더 파고드는 것들

정규화하면 조인이 늘어나니까 무조건 느려지는 것 아닌가요? 함정힌트: "무조건"이 틀린 지점을 짚고, 마지막에 4축의 ②로 되돌린다

"조인이 는다"는 맞지만 "무조건 느려진다"는 틀리다. 정규화는 동시에 세 가지를 벌어준다.

① 행이 좁아진다 — 부서 이름·전화번호가 직원 행에서 빠지면 한 페이지에 더 많은 행이 들어가고, 같은 스캔·같은 캐시 메모리로 더 많은 행을 다룰 수 있다. ② 쓰기가 싸진다 — 부서명 변경이 300행 UPDATE에서 1행 UPDATE로 준다(PostgreSQL이면 죽은 튜플도 300개에서 1개로 준다). ③ 조인 비용은 인덱스로 상당 부분 흡수된다 — 다만 PostgreSQL은 FK 컬럼 인덱스를 자동으로 만들어 주지 않으므로 CREATE INDEX ON employees (dept_id)를 직접 걸어야 한다. 이걸 빼먹고 "정규화하니 느리다"고 결론 내리는 경우가 실제로 많다.

그리고 결정적으로 — 느려지는지 아닌지는 "추정"이 아니라 4축의 ②(실측)로 답할 문제다

답변 형태: "조인이 실측된 병목으로 확인되고, 인덱스·쿼리 형태·캐시로도 해결되지 않을 때 비로소 반정규화를 검토합니다. 그전에 반정규화부터 꺼내면 얻지도 않은 이득을 위해 갱신 정합성이라는 영구 비용을 먼저 지불하는 셈입니다."

generated column으로 comment_count를 만들면 되지 않나요? 그러면 관리 장치가 통째로 필요 없잖아요. 함정힌트: generated column의 식이 참조할 수 있는 범위가 어디까지인지

안 된다. generated column의 식은 같은 행 안의 값만 참조할 수 있어서, 다른 테이블(comments)을 세는 식은 쓸 수 없다. 그래서 comment_count에는 애초에 적용 대상이 아니다.

반대로 적용 대상이면 최선의 선택이다. order_items.amount = qty * unit_price처럼 원본이 같은 행 안에 있으면 GENERATED ALWAYS AS (qty * unit_price) STORED로 두는 순간 어긋날 경로 자체가 사라진다 — 애플리케이션이 값을 직접 넣을 수 없고, DB가 항상 계산하기 때문이다.

기준 한 줄 — "사본이 가리키는 원본이 같은 행 안에 있는가, 다른 테이블에 있는가"

같은 행 안이면 generated column, 다른 테이블이면 트리거 또는 앱 트랜잭션 + 보정 배치, "잠시 후"로 느슨해도 되면 materialized view. 그리고 다른 테이블을 세는 집계 컬럼은 어느 도구로도 FK 같은 선언적 제약이 되지 못하므로 보정 배치는 남는다.

트리거로 모든 경로를 막으면 보정 배치는 빼도 되지 않나요? 시니어 변별힌트: 트리거가 막아주는 것을 먼저 인정한 뒤, 그것이 "선언적 제약"이 아니라는 데서 시작한다

트리거가 실제로 막아주는 것부터 인정하고 시작하는 게 좋은 답이다. 트리거를 걸면 콘솔에서의 직접 DELETE도, 카운트 갱신을 빼먹은 새 코드 경로도 트리거를 거치게 되므로 7절의 구멍 셋 중 둘이 막힌다.

그래도 보정 배치가 남는 이유는 셋이다. ① 트리거는 선언적 제약이 아니라 절차적 코드라 비활성화하거나 session_replication_role = replica로 우회할 수 있다. ② 그리고 그 우회는 이론이 아니라 실제로 일어난다 — 대량 적재 성능 때문에 트리거를 꺼 두는 구간이 생기고, 그 구간은 그대로 뚫린다. ③ 행 단위 트리거라 댓글 1만 건을 한 문장으로 INSERT해도 UPDATE가 1만 번 발생해 8절의 핫 로우 사슬을 오히려 키운다.

운영 관점의 대가도 함께 말하면 좋다 — 갱신 로직이 애플리케이션 코드 밖으로 나가므로 git grep comment_count로는 안 잡히고, 트랜잭션이 왜 느린지 추적할 때 계획에도 잘 안 드러난다. "숨은 쓰기"가 되는 셈이다.

보정 배치는 그냥 매일 전체 테이블에 돌리면 안전하지 않나요? 가산점힌트: PostgreSQL에서는 "값이 같은 UPDATE"가 공짜가 아니다

PostgreSQL에서는 특히 위험하다. UPDATE는 값이 같아도 새 튜플 버전을 쓰기 때문이다 — 죽은 튜플 + WAL 기록 + 인덱스 갱신 가능성이 따라온다. 가드 없는 전체 보정은 매일 밤 posts 테이블 전체를 다시 쓰는 것과 같고, 정합성을 지키려던 배치가 bloat 생산기가 된다.

그래서 AND p.comment_count IS DISTINCT FROM c.cnt 가드가 PostgreSQL에서는 선택이 아니라 필수다(같은 이유로 MySQL에서는 엔진이 알아서 건드리지 않으므로 이 가드의 중요도가 다르다). IS DISTINCT FROM을 쓰는 이유는 NULL이 섞여도 안전하게 "다르다"를 판정하기 위해서다.

실전 운영의 형태는 "전체 재계산"이 아니라 최근 변경분 위주 + 주기적 표본 검증이다. 그리고 보정 배치 자체가 부하가 되지 않도록 범위를 좁혀 도는 것이 원칙이다 — 드리프트를 되돌리려다 8절의 사슬을 스스로 만드는 것이 가장 흔한 자충수다.

comment_count가 음수가 될 수도 있나요? CHECK (comment_count >= 0)을 걸면 되지 않나요? 가산점힌트: 걸 수는 있다. 다만 그것이 "무엇을 보장하고 무엇을 보장하지 않는지"가 답이다

음수가 될 수 있다. 삭제 경로는 규약대로 -1을 하는데 그 댓글의 +1이 애초에 반영되지 않았던 경우(장치를 거치지 않은 INSERT 경로가 있었던 경우) 카운트가 0 아래로 내려간다.

CHECK 제약은 걸 수 있고 쓸모도 있다. 다만 무엇을 보장하는지 정확히 알아야 한다.

보장하는 것

"0 이상"이라는 값의 범위. 그리고 위반 시 예외로 드러나므로 드리프트가 조용한 오류에서 시끄러운 오류로 바뀐다.

보장하지 못하는 것

"comments의 행 수와 같다"는 불변식. 사본이 3인데 원본이 5여도 CHECK는 그냥 통과한다 — 진짜 문제는 통과시킨다.

대가도 함께 말한다 — 제약에 걸리는 순간 그 댓글 삭제 요청 자체가 실패한다. 즉 CHECK는 "드리프트를 조기에 탐지하는 장치"로 쓰고, 정합성 자체는 여전히 보정 배치로 되돌린다. 이 답변이 좋은 이유는 "제약을 걸면 되지 않나요"를 그냥 부정하지 않고, 선언적 제약이 왜 이 불변식을 대신할 수 없는지(7절)를 재확인하기 때문이다.

카운터를 Redis로 빼면 핫 로우 문제가 다 해결되는 것 아닌가요? 함정힌트: 해결되는 것을 먼저 인정하고, 새로 생기는 문제 셋과 "판단 순서"로 답을 닫는다

DB 쓰기가 극적으로 줄어드는 것은 사실이다. 8절 사슬의 출발점인 "같은 행에 UPDATE가 몰린다"가 사라지므로 락 경합도 죽은 튜플도 함께 사라진다. 여기까지는 맞다.

대신 새로 생기는 것이 셋이다. ① 반영 주기만큼의 유실 창 — 반영 전에 잃으면 그만큼의 증가가 사라진다. ② 이중 소스 관리 — "지금 진실은 Redis인가 DB인가"가 항상 따라다니고, 장애 복구 시 어느 쪽으로 맞출지 정해 둬야 한다. ③ DB 쪽 활용의 제약 — 그 숫자로 DB에서 정렬·필터·조인을 하려면 결국 DB에 반영돼 있어야 한다.

그래서 순서가 먼저다 — "이 카운터는 정확해야 하는 숫자인가, 대략 맞으면 되는 숫자인가?"

조회수·좋아요 수는 뒤쪽이라 비동기 집계·외부 카운터가 성립하지만, 결제 잔액이나 재고는 앞쪽이라 같은 처방을 쓰면 안 된다. 같은 "카운터"라는 이름으로 묶어 같은 처방을 적용하는 것이 사고의 지름길이고, 이 구분을 먼저 말하는 사람이 변별된다.

한 줄 요약
정규화는 "하나의 사실은 한 곳에만"으로 수정 이상(중복된 사실 중 일부만 고쳐 DB가 두 가지 답을 하게 되는 상태)을 구조적으로 차단하고, 반정규화는 조회 패턴을 위해 의도적으로 중복·연산 값을 두되 그 대가(갱신 정합성)를 관리 장치와 함께 지불하는 결정이다. 관리 장치 3단은 서로 다른 실패 원인에 각각 대응한다 — 같은 트랜잭션(단일 요청의 원자성) + 원자적 UPDATE(동시 요청의 격리) + 보정 배치(코드 밖에서 오는 변경). 선택 기준은 읽기:쓰기 비율 · 실측 병목 · 인덱스/캐시 선행 검토 · 대가 지불 준비의 4축이고, PostgreSQL의 generated column·트리거·materialized view는 관리 장치 일부를 DB 안으로 옮겨 주되 보정 배치를 없애 주지는 않는다. 핫 로우의 비용은 락 경합 → 사실상 직렬화 → 트랜잭션 장기화 → 커넥션 풀 고갈 → 전 서비스 전파라는 이름 붙은 사슬로 말하고, PG에서는 UPDATE마다 쌓이는 죽은 튜플(bloat)이 그 위에 얹힌다.
