인덱스와 B+Tree
구조 3요소가 각각 어떤 능력을 사주고, PostgreSQL 리프에는 정확히 무엇이 있는가

면접 질문: "인덱스는 어떻게 동작하나요? B+Tree 구조를 설명해주세요."

핵심 관전 포인트 — B+Tree는 세 가지 구조적 선택으로 이루어져 있고, 각 선택이 사주는 능력이 1:1로 대응한다. ① 한 노드(=8KB 디스크 페이지)에 키를 수백 개 담는 다분기 구조 → 트리 높이가 3~4로 낮아짐 → 페이지 몇 장 읽고 끝난다. ② 실제 데이터는 리프에만 두고 내부 노드는 길잡이 키만 갖는다 → 내부 노드가 가벼워져 fan-out이 커지고 트리가 더 낮아진다. ③ 리프끼리 양방향 연결 → 한 번 진입하면 옆으로 훑을 수 있어 범위 조회와 ORDER BY(역방향 포함)가 공짜로 따라온다. 흔한 오해가 +의 방향인데, 내부 노드에도 데이터를 두는 쪽이 B-Tree, 리프에만 두는 쪽이 B+Tree다 — PostgreSQL이 "B-tree"라고 부르는 기본 인덱스도 구조는 B+Tree다. 그리고 PostgreSQL에서 그 리프에 든 "데이터"는 행이 아니라 행의 물리 주소(TID)다 — 테이블은 힙이고 모든 인덱스가 힙을 가리키므로 인덱스 조회에는 힙 페치가 따라붙는다. 인덱스를 "걸까 말까"는 쓰기 빈도(HOT 탈락 포함) / 선택도(부분 인덱스라는 PostgreSQL의 무기) / 기존 인덱스와의 중복(선두 컬럼 규칙) / EXPLAIN (ANALYZE, BUFFERS) 검증, 이 네 축을 한 호흡에 펼칠 수 있어야 한다.
  • 1
    구조는 세 가지 선택뿐이고, 각각이 사주는 능력이 정해져 있다 — 다분기(8KB 페이지 하나에 키 수백 개) → 트리 높이 3~4단, 데이터는 리프에만 → 내부 노드가 가벼워져 fan-out이 커지고 모든 조회 비용이 균일, 리프 양방향 연결 → 범위 조회·ORDER BY·페이징이 정렬 비용 없이 따라온다.
  • 2
    +는 "데이터를 리프로 몰았다"는 뜻이고, PostgreSQL의 리프에 든 것은 행이 아니라 TID다 — 내부 노드에도 데이터를 두는 쪽이 B-Tree, 리프에만 두는 쪽이 B+Tree(방향을 반대로 외우는 사람이 많다). PostgreSQL은 테이블이 힙이고 모든 인덱스가 (키, TID)만 갖는 전부 세컨더리 구조라, 인덱스 조회에는 힙 페치가 따라붙는다.
  • 3
    그래서 인덱스 설계는 "걸면 빨라진다"가 아니라 네 축의 저울질이다 — 쓰기 빈도(비-HOT UPDATE는 바뀐 컬럼과 무관하게 모든 인덱스를 건드린다) · 선택도(낮으면 Seq Scan이 이긴다, 희귀값이면 부분 인덱스) · 기존 인덱스와의 중복(선두 컬럼 규칙) · EXPLAIN (ANALYZE, BUFFERS)로 실제로 타는지 검증.

0. 질문 + 출제 의도

질문: "인덱스는 어떻게 동작하나요? B+Tree 구조를 설명해주세요."

관련 질문: "인덱스를 걸었는데도 풀스캔이 발생하는 경우는?" · "클러스터드 인덱스와 논클러스터드(세컨더리) 인덱스의 차이는? (InnoDB 기준)"

PostgreSQL 기준 재해석: "PostgreSQL에는 클러스터드 인덱스가 없다 — 힙 테이블 + 모든 인덱스가 TID를 가리키는 구조에서 '리프에 든 데이터'는 무엇이고, 그 차이가 조회·쓰기 비용에 어떻게 번지는가."

출제 의도: "인덱스 걸면 빨라진다"는 누구나 안다. 구조를 알아야 "왜 이 쿼리는 인덱스를 못 타는지", "인덱스 하나가 쓰기를 얼마나 느리게 하는지"를 추론할 수 있다 — PostgreSQL이라면 "UPDATE 한 번이 인덱스를 몇 개나 건드리는지"(HOT)까지. 즉 암기 확인이 아니라 구조 → 성능 특성 → 설계 판단으로 이어지는 사슬을 스스로 이어붙일 수 있는지를 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "인덱스는 책의 색인"에서 멈추는 것 → 1·2·3절에서 한 페이지에 몇 개가 들어가는지부터 직접 세어 3~4층·7만 배라는 숫자를 손에 쥔다.
② +의 방향을 반대로 아는 것 → 4절에서 "내부 노드에 데이터를 두는 쪽이 B-Tree"를 못 박고, 리프로 몬 선택이 사주는 능력 두 가지를 각각 그림으로 본다.
③ 조회 이야기만 하고 쓰기·판단으로 못 넘어가는 것 → 6~8절에서 TID · 힙 페치 · HOT으로 쓰기 비용을 세고, 9~10절에서 4축 판단과 안 타는 원인 목록을 인출 가능한 형태로 만든다.

이 문서는 4장(RDB / SQL)의 첫 문서다. 뒤에 나오는 문항들 — 인덱스가 안 먹는 이유, 클러스터드 vs 세컨더리, 커버링 인덱스, 깊은 페이지네이션 — 이 전부 여기서 세운 어휘(페이지 · fan-out · 힙 · TID · 힙 페치) 위에서 돌아간다.

1. 전제 — 디스크는 바이트가 아니라 "페이지" 단위로 읽는다

먼저 용어 하나. 페이지(page) 는 DB가 디스크와 메모리 사이에서 데이터를 주고받는 최소 단위 덩어리다. PostgreSQL은 8KB(8,192바이트) 이고, 이 크기는 컴파일 시점에 정해져 운영 중에 바꿀 수 없다. id = 25인 행 하나가 필요해도 DB는 그 행이 든 8KB 페이지를 통째로 읽어 온다. 1바이트만 달라고 할 방법이 없다.

비유 — 페이지는 "택배 상자"다 볼펜 한 자루를 주문해도 상자 하나가 통째로 배송된다. 배송비는 볼펜 개수가 아니라 상자 개수로 매겨진다. 그렇다면 이득을 보는 방법은 하나다 — 상자 하나에 물건을 최대한 많이 채워 담는 것. 디스크 자료구조의 설계 목표가 정확히 이것이고, 그 결과물이 B+Tree다.

이 사실 하나가 "빠른 자료구조"의 정의를 바꾼다.

 메모리 위 자료구조디스크 위 자료구조
비용의 단위비교 횟수 (CPU 연산)페이지 읽기 횟수 (I/O)
그래서 좋은 모양노드가 작아도 됨. 이진 트리로 충분노드 하나 = 페이지 하나를 꽉 채우는 게 이득
대표 구조이진 탐색 트리, 해시 테이블B+Tree

이진 트리는 노드 하나에 키를 하나만 담는다. 그런데 그 노드를 읽으려면 어차피 8KB 페이지를 통째로 읽어야 하므로, 8,192바이트를 읽어 와서 키 하나만 쓰고 나머지를 버리는 셈이 된다. 1억 건을 이진 트리에 담으면 높이가 약 27단이라 최악의 경우 디스크를 27번 때린다.

디스크 자료구조의 설계 목표는 하나 — 한 페이지에 키를 최대한 많이 담아 트리 높이를 낮춘다

한 노드에서 갈라지는 자식 수를 fan-out(팬아웃, "부챗살처럼 퍼지는 정도")이라 부른다. B+Tree는 이 fan-out을 수백까지 키운 다분기 트리다. 앞으로 이 문서에서 fan-out이 커진다 = 트리가 낮아진다 = 디스크를 덜 때린다는 사슬이 계속 반복된다.

2. 지도 한 장 — 3층 B+Tree

말로 외우면 방향이 뒤집힌다. 이 그림 한 장으로 고정하는 게 낫다. PostgreSQL 용어로는 루트 / 내부(internal) / 리프 페이지이고, 노드 하나가 디스크 페이지 하나(8KB)다.

구조 3요소 3초 암기 — 다 · 리 · 옆

다 = 다분기 (한 페이지에 키 수백 개)→트리 높이 3~4단
리 = 데이터는 리프에만→fan-out ↑ → 더 낮아짐 + 비용 균일
옆 = 리프끼리 양방향 연결→범위 · ORDER BY · 페이징이 공짜

면접에서는 이 세 줄을 각각 "그래서 뭘 얻는데?"까지 붙여서 말해야 한다. 왼쪽만 말하면 구조 암기, 오른쪽까지 말해야 이해다.

3. 숫자 — 한 페이지에 몇 개가 들어가고, 3층이면 몇 행에 닿나

"3층이면 수백만 행"은 그림만 봐서는 와닿지 않는다. 직접 세어 보면 감이 잡힌다. PostgreSQL의 8KB 페이지 안을 뜯어 보자.

넉넉히 잡아 한 페이지에 약 400개, 보수적으로 300개다. 그러면 층수별로 담을 수 있는 엔트리 수가 이렇게 된다.

그래서 결정적인 귀결은 이것이다 — 조회 한 번에 읽는 페이지가 3~4장이다. 층수만큼 내려가고(3장), 리프에서 얻은 TID로 힙 페이지를 한 장 더 읽는다(1장, 6절). 풀스캔과 나란히 놓아 보자.

한 겹 더 — 실제 물리 I/O는 3~4장도 아니다 상위 레벨(루트·내부 페이지)은 개수 자체가 적어서(위 계산에서 루트 1장 + 내부 약 90장) 거의 항상 메모리 캐시(shared_buffers)에 상주한다. 그래서 실제 디스크 I/O는 리프 한 장 + 힙 한 장, 사실상 두 장으로 줄어드는 경우가 많다. "트리가 낮다"는 것은 곧 "상위 층 전체를 메모리에 올려둘 수 있다"는 뜻이기도 하다.

4. +의 방향과, 리프로 몬 대가로 사는 것 둘

가장 흔한 오해 — "내부 노드에도 데이터를 둘 수 있게 바꾼 게 B+Tree"는 정확히 반대다

B-Tree

내부 노드에도 실제 데이터(값/레코드 포인터)를 함께 저장한다. 운이 좋으면 루트 근처에서 바로 값을 찾아 조회가 일찍 끝날 수 있다.

B+Tree

내부 노드는 길잡이 키(separator key)만 갖는다. 값이 없다. 모든 조회는 반드시 리프까지 내려간다. 대신 내부 노드가 가벼워지고, 리프끼리 연결할 수 있게 된다.

"데이터를 리프로 몰아넣었다"는 한 번의 선택이 서로 다른 능력 두 가지를 사 준다. 이 둘을 각각 그림으로 보고 넘어가면 표를 외울 필요가 없어진다.

4-1. 사는 것 ① — 내부 노드가 가벼워져 트리가 더 낮아진다

비유 — 도서관의 층별 안내판 B+Tree의 내부 노드는 안내판이다. "3층: 역사 / 4층: 과학"처럼 길만 알려주므로 얇고, 그래서 한 장에 항목을 많이 적을 수 있다. B-Tree의 내부 노드는 안내판 옆에 책을 몇 권씩 꽂아 둔 것이다. 운 좋으면 안내판 앞에서 바로 원하는 책을 집을 수 있지만, 책이 자리를 먹어 안내 항목이 확 줄어든다 — 그러면 층이 더 많이 필요해진다.

4-2. 사는 것 ② — 범위 조회가 인덱스의 진짜 값어치

두 번째가 실무에서는 더 크다. 데이터가 리프에만 있으면 리프들만 정렬 순서대로 이어 붙여도 전체 데이터를 빠짐없이 순회할 수 있다. 그래서 B+Tree는 리프끼리 연결 리스트로 묶는다. B-Tree는 데이터가 트리 곳곳에 흩어져 있어 이 연결이 불가능하다 — 순서대로 읽으려면 중위 순회(in-order traversal)로 트리를 오르내려야 한다.

정렬된 순서로 들어오면 그룹 경계가 자연히 보여 별도 정렬·해시가 필요 없다
이 전부가 정렬 비용 없이 처리된다 — 인덱스 순서가 곧 정렬 순서이기 때문이다

가산점 — 리프 연결이 있어도 도움이 안 되는 경우를 짝으로 말할 수 있으면 구조를 이해했다는 신호다

되는 것 — LIKE 'kim%'

선행 문자가 고정이라 리프에서 시작점을 찍을 수 있다.

단, PostgreSQL 함정 — 컬럼 collation이 C가 아니면 B-tree 정렬이 바이트 접두 순서와 달라 접두 LIKE가 인덱스를 안 탄다. → text_pattern_ops 연산자 클래스로 인덱스를 만들거나 COLLATE "C".

안 되는 것 — LIKE '%kim%'

시작점을 특정할 수 없어 트리를 내려갈 방법이 아예 없다.

B-tree의 구조적 한계이지 튜닝 문제가 아니다. 필요하면 pg_trgm GIN 인덱스나 전문 검색(tsvector)·검색 엔진으로 풀어야 한다.

판별식 — "리프에서 시작점을 찍을 수 있는가?" 찍을 수 있으면 인덱스가 산다

5. 구조 3요소 총정리 · PostgreSQL "B-tree"의 정체

면접에서는 이 세 줄을 각각 "그래서 뭘 얻는데?"까지 붙여서 말해야 한다. 왼쪽 열만 말하면 구조 암기, 오른쪽 열까지 가야 이해다.

구조적 선택왜 그렇게 만들었나그 결과 얻는 능력
① 다분기
한 노드에 키 수백 개		노드 하나 = 8KB 페이지 하나. 페이지를 어차피 통째로 읽으니 꽉 채우는 게 이득트리 높이가 3~4단으로 낮아짐 → 디스크 접근 횟수 최소화 (3절의 7만 배)
② 데이터는 리프에만
= +의 정체		내부 노드에서 데이터를 빼면 노드가 가벼워짐한 페이지에 길잡이 키를 더 많이 담음 → fan-out 증가 → 트리가 더 낮아짐(4-1의 3층 대 5층). 그리고 모든 조회의 비용이 균일
③ 리프 양방향 연결리프만 순회하면 전체 데이터를 정렬 순서로 다 볼 수 있게범위 조회(BETWEEN, >, <) · ORDER BY(양방향) · GROUP BY · 페이징이 정렬 비용 없이 처리됨(4-2)
"왜 DB는 B+Tree를 택했나"에 대한 완성형 답변 조회 한 건이 "운 좋게 빨리 끝나는 것"보다 모든 조회가 예측 가능하게 3~4번의 I/O로 끝나는 것이 서비스에서는 훨씬 가치 있다. 게다가 실무 쿼리의 상당수가 범위·정렬·페이징인데, 그건 리프 연결 리스트가 있어야 싸진다. 트리를 낮추는 것과 범위 스캔을 싸게 하는 것, 두 마리 토끼를 "데이터를 리프로 몰아넣기"라는 하나의 선택으로 잡은 게 +다.

5-1. PostgreSQL의 "B-tree"는 이름과 달리 B+Tree다 가산점

매뉴얼과 USING btree는 "B-tree"라 부르지만, TID는 리프에만 있고 내부 페이지는 길잡이 키만 가지며 리프는 양방향 연결 — 위 표의 B+Tree 열 그대로다. 구현 특징 넷만 더 알아두자.

Lehman-Yao 트리 — 읽기가 쓰기를 거의 안 막는 이유
모든 페이지가 오른쪽 형제 링크와 high key(이 페이지 키의 상한)를 갖는다. 남이 분할하는 도중에 내려와도 "찾는 키 > high key면 오른쪽으로 한 칸"으로 락 없이 회복한다. 왼쪽 링크도 있어 역방향 스캔이 된다.
8KB 페이지, 리프 fillfactor 기본 90
리프를 90%만 채워 이후 삽입이 바로 분할로 이어지지 않게 한다(3절에서 400이 아니라 300으로 낮춰 잡은 이유). 차면 둘로 나누고 부모에 길잡이 키를 올린다(루트가 갈라지면 높이 +1). 단조 증가 키가 붙는 맨 오른쪽 페이지만은 반으로 안 가르고 오른쪽에 계속 채운다 — bigint IDENTITY PK 인덱스가 촘촘하고 UUID v4 PK 인덱스가 헐렁한 이유.
중복 키 dedup (PostgreSQL 13)
같은 키의 TID들을 "키 하나 + TID 목록"으로 접어 status처럼 중복 많은 컬럼의 인덱스를 줄인다.
bottom-up deletion (PostgreSQL 14)
리프가 분할 직전일 때 죽은 힙 튜플을 가리키는 엔트리를 먼저 치워 반복 UPDATE로 인덱스가 부푸는 속도를 늦춘다(8절).

6. PostgreSQL의 리프 — 힙 · TID · 힙 페치

"데이터는 리프에만 있다"고 할 때 그 데이터가 정확히 뭐냐가 DB마다 다르고, 이게 다음 문항(클러스터드 vs 세컨더리)의 입구다. PostgreSQL의 답은 단순하다.

용어 — 여기서 "힙(heap)"은 자료구조 수업의 힙이 아니다 우선순위 큐가 아니라 "아무렇게나 쌓아 둔 더미"라는 일상어 쪽 뜻이다. PostgreSQL의 테이블 파일은 정확히 그렇게 생겼다 — 행이 정렬 없이 8KB 페이지에 들어오는 대로 쌓인다. PK 순서로 정렬된 테이블 같은 것은 없다.

테이블(힙)

각 행의 위치는 TID(tuple identifier) = (블록 번호, 페이지 안의 라인 포인터 번호), 6바이트다. SELECT ctid, * FROM orders로 직접 볼 수 있다 — (0,1), (0,2)처럼 찍히는 그 값이 인덱스 리프에 적혀 있는 주소다.

모든 인덱스(PK 포함)

리프 엔트리 = 인덱스 컬럼 값 + TID. PK 인덱스도 그저 "유니크 B-tree + NOT NULL"일 뿐 특별한 지위가 없다. 나머지 컬럼이 필요하면 TID로 힙 페이지를 읽으러 가는데, 이게 힙 페치(heap fetch) 다.

이 장 전체의 기준 어휘 — PostgreSQL에는 클러스터드 인덱스가 없고, 모든 인덱스가 세컨더리다

"클러스터드 인덱스"란 인덱스의 리프가 곧 테이블 자체여서 인덱스를 타면 행이 바로 손에 들어오는 구조를 말한다(MySQL InnoDB가 PK로 그렇게 만든다). PostgreSQL은 그 구조가 없다. 인덱스는 언제나 "값 → 주소"까지만 알려주는 별도의 파일이고, 행을 손에 넣으려면 그 주소를 들고 힙을 한 번 더 다녀와야 한다.

비유 — 인덱스는 "물건 이름 → 선반 번호" 쪽지 묶음, 힙은 물건이 아무렇게나 쌓인 창고
쪽지에서 이름은 정렬돼 있지만, 그 쪽지가 가리키는 선반 번호는 창고 여기저기로 흩어져 있다

6-1. 이 구조에서 갈라지는 세 가지 스캔

"리프에 TID뿐"이라는 사실 하나에서 PostgreSQL 실행 계획에 찍히는 스캔 셋이 갈라진다.

Index Scan
TID를 하나 얻을 때마다 힙 페이지를 읽는다. 대상 행이 적을 때 최선. 행이 늘수록 힙 랜덤 I/O가 비례해서 는다.
Bitmap Index Scan → Bitmap Heap Scan
TID를 전부 모아 물리 순서로 정렬한 뒤 힙을 한 번 훑는다. 랜덤 접근을 순차로 바꾸는 PostgreSQL 고유의 완화책이라 "인덱스는 타는데 행이 수만 건" 구간에서 플래너가 고른다.
Index Only Scan
필요한 컬럼이 전부 인덱스에 있으면 힙 페치를 생략한다. 7절에서 따로 본다.

Bitmap Heap Scan에 붙는 Recheck Cond는 비트맵이 work_mem을 넘겨 페이지 단위(lossy)로 뭉개졌을 때 힙에서 조건을 다시 검사한다는 뜻이다.

6-2. B-tree가 전부가 아니다 — 인덱스 종류와 PostgreSQL의 두 가지 무기

CREATE INDEX의 기본은 B-tree지만 PostgreSQL은 접근 방식(access method)이 여러 개다. "각각 어떤 질문에 답하는 구조인가"만 말할 수 있으면 된다.

종류잘 답하는 질문한 줄
B-tree (기본)=, <, >, BETWEEN, ORDER BY, 접두 LIKE범용. 유니크 제약도 이걸로
Hash=만키 값 대신 해시만 저장해 긴 키에 작다. 순서 없음
GIN"이 값 안에 X가 들어 있나" — 배열, jsonb, tsvector, pg_trgm역색인. 한 행이 키 여러 개를 낸다. 갱신은 느린 편
GiST범위·기하·근접(k-NN), EXCLUDE 제약"겹치나/가까운가"를 균형 트리로
SP-GiST공간 분할 구조(쿼드트리·기수 트리)특수 용도
BRIN물리 순서와 상관이 높은 컬럼(로그의 created_at)블록 범위별 min/max만 → 초소형, 정밀도 낮음
종류와 무관하게 어떤 인덱스에나 붙는 두 옵션 — 이게 PostgreSQL 인덱스 설계의 핵심 무기다 부분 인덱스(WHERE …, 9-2절)는 크기와 쓰기 비용을 "조건에 맞는 행만큼"으로 줄이고, 표현식 인덱스(((lower(email))), 10절)는 "컬럼에 함수를 씌우면 인덱스가 죽는다"는 규칙의 정식 예외를 만든다.
MySQL 대조 — 같은 질문에 InnoDB는 이렇게 답한다 MySQL의 InnoDB는 클러스터드 인덱스(= PK B+Tree)의 리프에 행 전체가 들어 있어 테이블 자체가 PK 순 트리이고, 세컨더리 인덱스의 리프에는 PK 값이 복제돼 있다(그래서 PK가 크면 모든 세컨더리가 함께 커지고, PK 컬럼은 공짜로 커버링된다). 세컨더리 → PK → 클러스터드로 두 번 타는 것이 북마크 룩업이고, 이것이 PostgreSQL의 힙 페치에 대응한다. PostgreSQL에는 이 위계가 없다 — 힙 + 전부 세컨더리 + TID. 부분 인덱스·BRIN·GIN도 MySQL에는 대응물이 없거나 다르다(FULLTEXT·SPATIAL).

7. Index Only Scan과 visibility map

앞의 두 스캔은 반드시 힙을 다녀온다. 그래서 인덱스가 아무리 잘 걸려 있어도 "인덱스 페이지 몇 장 + 힙 페이지 N장"이 비용의 바닥이 된다. Index Only Scan은 그 바닥을 없애는 유일한 경로라 특별하다 — 커버링 인덱스의 PostgreSQL 판이다.

성립 조건은 하나 — 쿼리가 필요로 하는 컬럼이 전부 인덱스 안에 있을 것
힙에 간다인덱스에 없는 컬럼이 하나라도 필요하면
-- amount 는 인덱스에 없다
SELECT user_id, created_at, amount
  FROM orders
 WHERE user_id = 100;

--  Index Scan using idx_orders_user_created
--    → TID마다 힙 페이지 한 장씩
힙에 안 간다필요한 컬럼이 전부 인덱스 안에 있으면
-- 인덱스: (user_id, created_at)
SELECT user_id, created_at
  FROM orders
 WHERE user_id = 100;

--  Index Only Scan using idx_orders_user_created
--    Heap Fetches: 0        ← 이 숫자가 증거

7-1. PostgreSQL 고유의 단서 — 인덱스 엔트리에는 MVCC 정보가 없다

힙 튜플에는 "이 버전을 만든 트랜잭션(xmin)/지운 트랜잭션(xmax)"이 헤더에 적혀 있어 "내 스냅샷에서 이 행이 보이는가"를 판단할 수 있다. 그런데 인덱스 엔트리에는 그 정보가 없다. 그러니 인덱스만 읽고 답하면 이미 삭제된 행을 살아 있다고 답할 위험이 있다.

이 문제를 푸는 장치가 visibility map(가시성 맵)이다. 테이블마다 딸린 아주 작은 비트맵 파일로, 힙 페이지 한 장당 비트 하나를 두고 "이 페이지의 모든 튜플이 모든 트랜잭션에게 보인다(= 죽은 튜플이 하나도 없다)"를 표시한다. 이 비트를 켜는 것은 VACUUM이다.

Index Only Scan이라고 찍혔다고 끝이 아니다 — Heap Fetches를 같이 봐야 한다

Heap Fetches: 0
힙을 정말 안 갔다. 커버링이 의도대로 먹히는 중.
Heap Fetches ≈ 결과 행 수
커버링 인덱스를 만들어 놓고 효과를 못 보고 있는 것. 원인은 대개 VACUUM이 밀린 것이고, VACUUM이 밀리는 대표 원인은 롱 트랜잭션이다.
가산점 — 이 구조에서 따라 나오는 두 가지 ⑴ 리프에 PK가 아니라 6바이트 TID가 들어가므로 "PK가 크다고 다른 인덱스까지 같이 비대해지지는 않는다" — 랜덤 UUID PK의 비용은 힙이 아니라 PK B-tree 자체의 무작위 삽입(5-1의 분할 정책)과 그 값을 담는 FK 컬럼·조인 키 인덱스에서 난다.
⑵ 커버링은 INCLUDE (컬럼)(PostgreSQL 11+)으로 탐색 키가 아닌 컬럼을 리프에만 실어 만들 수 있다 — 내부 노드는 가벼운 채로 두므로 fan-out(4-1)을 안 깎는다. "커버링하려고 컬럼을 자꾸 붙이면 트리가 뚱뚱해진다"는 문제의 정식 해법이다.

8. 쓰기 비용 — HOT · 비-HOT · bloat

여기서 조회 이야기가 쓰기 이야기로 넘어간다. PostgreSQL의 UPDATE는 행을 제자리에서 고치지 않고 새 버전 튜플을 만든다. 그 새 튜플이 다른 TID를 갖게 되면 인덱스 리프에 적힌 옛 주소가 무효가 되므로, 모든 인덱스에 새 엔트리를 꽂아야 한다.

여기서 HOT(Heap-Only Tuple) 이라는 최적화가 나온다. 이름 그대로 "힙에만 사는 튜플"이라는 뜻으로, 인덱스에 엔트리를 만들지 않는 새 버전을 말한다. 성립 조건이 둘이다.

1
바뀐 컬럼이 어떤 인덱스에도 들어 있지 않을 것 — 인덱스의 키 값이 안 바뀌었으니 인덱스를 고칠 이유가 없다.
2
새 튜플이 같은 페이지 안에 들어갈 자리가 있을 것 — 옛 튜플이 새 튜플을 가리키는 포인터 체인을 페이지 안에 만들어, 인덱스가 여전히 옛 TID를 가리켜도 따라갈 수 있게 한다.

8-1. 그 결과 — 인덱스 bloat

VACUUM 전까지 인덱스는 "살아 있는 행 수보다 큰" 상태이고, 갱신이 잦은 테이블에서 이것이 누적된 것이 인덱스 bloat(부풀기)다 — 같은 행 수인데 페이지가 배로 늘어 트리가 높아지고 캐시를 더 먹는다. 방어는 세 겹이다.

① 테이블 fillfactor를 낮춘다
예: 80. 페이지에 여유를 남겨 HOT 조건 ②가 자주 성립하게 한다.
② autovacuum이 따라오게 한다
죽은 튜플과 그걸 가리키는 인덱스 엔트리를 치운다. 밀리면 bloat도 Index Only Scan도 같이 망가진다.
③ 이미 부푼 인덱스는 다시 짠다
REINDEX CONCURRENTLY (PostgreSQL 12+)

관찰 지표 — 이 한 줄이면 "인덱스가 UPDATE를 얼마나 무겁게 하는지"가 보인다

-- n_tup_hot_upd / n_tup_upd 비율이 낮으면 비-HOT이 지배적이라는 뜻
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
  FROM pg_stat_user_tables
 ORDER BY n_tup_upd DESC;

9. "인덱스 하나만 걸어주세요"에 답하는 4축

팀원이 "이 조회 느리니 컬럼 A에 인덱스 걸어주세요"라고 하면, 아래 네 축을 한 호흡에 펼치는 게 실무 답변이다. "일단 걸자"와 "안 됩니다" 사이에 있는 게 이 체크리스트다.

4축 3초 암기 — 쓰 · 선 · 중 · 검

선

중

9-1. 축 1. 쓰기 빈도 — 인덱스는 조회를 위해 쓰기를 파는 거래다

인덱스는 별도의 B+Tree(별도 파일)를 하나 더 만드는 것이다. PostgreSQL에서 DML마다 벌어지는 일을 정확히 세면 이렇다.

INSERT
힙에 튜플 1개 + 모든 인덱스에 엔트리 1개씩. 인덱스가 5개면 힙 1 + 트리 5.
UPDATE
8절 그대로. HOT이면 인덱스를 하나도 안 건드리고, HOT이 깨지면 바뀐 컬럼과 무관하게 모든 인덱스에 새 엔트리. "자주 바뀌는 컬럼에 인덱스"는 테이블의 모든 인덱스에 쓰기를 얹는 결정이다.
DELETE
힙 튜플에 지운 표시(xmax)만 남긴다. 인덱스 엔트리는 그대로 있다가 VACUUM이 치운다 — 비용이 사라지는 게 아니라 뒤로 밀린다.
걸지 마라 예시 초당 수천 건이 꽂히는 이벤트 로그 테이블에, 하루 한 번 운영자가 보는 조회를 위해 인덱스를 추가하는 것. 그 조회는 배치로 돌리거나 분석용 저장소로 넘기는 게 맞다(시계열이라면 초소형 BRIN이 답일 수도 — 6-2절).

쓰기 부하 말고도 대가는 더 있다.

저장 공간
B+Tree 파일이 하나 더 생긴다. 백업 시간·저장소·WAL 전송량·복원 시 인덱스 재생성 시간이 전부 같이 는다.
캐시 오염
쓸모없는 인덱스 페이지가 shared_buffers에서 필요한 페이지를 밀어낸다(11절 꼬리질문에서 자세히).
플래너 혼선
후보가 많아지면 계획이 엉뚱하게 잡힐 확률이 올라간다.
생성 시점 리스크
기본 CREATE INDEX는 끝날 때까지 그 테이블의 쓰기를 막는다. 운영 중에는 CREATE INDEX CONCURRENTLY가 필수인데, 테이블을 두 번 스캔해 오래 걸리고 트랜잭션 블록 안에서 못 쓰며 실패하면 INVALID 인덱스가 남는다. 어느 쪽이든 WAL이 늘어 레플리카가 지연된다.
MySQL 대조 MySQL의 InnoDB는 UPDATE가 행을 제자리에서 고치므로 바뀐 컬럼이 든 인덱스만 갱신하고, 세컨더리 인덱스 페이지가 버퍼 풀에 없으면 변경을 체인지 버퍼에 모아 뒀다가 나중에 반영한다. PostgreSQL에는 둘 다 없다.

9-2. 축 2. 선택도(카디널리티) — 값 종류가 적으면 인덱스는 무의미하다

선택도(selectivity)

그 컬럼이 조건에 걸렸을 때 전체 행 중 몇 %로 좁혀지는가

카디널리티(cardinality)

그 컬럼에 서로 다른 값이 몇 개나 있는가

카디널리티가 낮으면(값 종류가 몇 개 없으면) 어떤 값으로 조회해도 결과가 전체의 상당 비율이 되므로 선택도도 낮아진다.

왜 낮은 선택도에서 인덱스가 무의미한가 — 6절에서 본 대로 PostgreSQL 인덱스로 행을 찾으면 인덱스에서 TID를 얻고 다시 힙 페이지를 읽으러 가는 랜덤 I/O가 행마다 발생한다. 100만 건 중 80만 건이 대상이면, 랜덤 I/O 80만 번보다 테이블을 순차로 쭉 읽는 Seq Scan이 더 빠르다.

플래너의 손익분기 계산식 — random_page_cost(기본 4.0) 대 seq_page_cost(1.0)
"랜덤 페이지 한 장은 순차 페이지 네 장 값"이라는 뜻이다. 그래서 인덱스가 있어도 안 쓴다 — 대개 옳은 판단이다.

그리고 중간 구간에서는 TID를 물리 순서로 정렬해 힙을 순차에 가깝게 읽는 Bitmap Heap Scan(6-1)을 고른다.

걸지 마라 예시 is_deleted(true/false), gender, 대부분이 'ACTIVE'인 status 컬럼에 단독 인덱스. 값 종류가 2~3개면 어떤 값으로 조회해도 전체의 30~90%가 걸린다.
예외 — 값이 극단적으로 편중돼 있고, 희귀한 쪽만 조회한다면 유효하다 전체의 0.01%뿐인 status = 'FAILED'만 골라 쓰는 알림 배치라면 인덱스가 극적으로 먹힌다. 이럴 때 PostgreSQL에는 단독·복합 말고 세 번째 선택지가 있다 — 부분 인덱스(partial index). 이름 그대로 테이블의 일부 행만 담는 인덱스다.
before값이 3종류뿐인 컬럼에 단독 인덱스 — 플래너가 무시한다
-- 조회할 때마다 전체의 절반이 걸려서 Seq Scan이 이긴다
CREATE INDEX idx_orders_status ON orders (status);
after실제 쿼리 모양에 맞춘 두 가지 정답
-- ① 실제 쿼리가 "특정 상태를 최근 순으로" 라면 복합으로.
--    status로 좁힌 뒤 created_at이 이미 정렬돼 있어 ORDER BY도 공짜(4-2의 능력 ③).
CREATE INDEX idx_orders_status_created ON orders (status, created_at);

-- ② PostgreSQL의 정석: 희귀한 값만 조회한다면 부분 인덱스.
--    FAILED 행만 담으므로 크기가 전체의 0.01%이고,
--    PAID/DONE 사이의 상태 변경은 이 인덱스를 건드리지 않는다(비-HOT 여지가 줄어든다).
CREATE INDEX idx_orders_failed_created ON orders (created_at)
WHERE status = 'FAILED';

-- 단, 쿼리의 WHERE가 인덱스의 WHERE를 포함해야 플래너가 쓴다.
--    WHERE status = $1 처럼 값이 파라미터면 포함 여부를 몰라 후보에서 빠진다.

9-3. 축 3. 기존 인덱스와의 중복 — 선두 컬럼(leftmost prefix) 규칙

복합 인덱스 (A, B)는 "A로 먼저 정렬하고, A가 같으면 B로 정렬"한 하나의 트리다

그래서 이 트리는 A만으로 검색할 때도 그대로 쓸 수 있다. 전화번호부가 "성 → 이름" 순으로 정렬돼 있으면 성만으로도 찾을 수 있는 것과 같다. 반대로 이름만 알고는 못 찾는다 — 이름이 책 전체에 흩어져 있기 때문이다.

(A, B, C) 인덱스가 있을 때
쿼리 조건인덱스 사용이유
WHERE A = ?O선두 컬럼부터 붙었다
WHERE A = ? AND B = ?O앞에서부터 연속
WHERE A = ? AND B = ? AND C = ?O (완전 활용)—
WHERE B = ?X선두 컬럼 A가 없다
WHERE B = ? AND C = ?X마찬가지
WHERE A = ? AND C = ?부분 (A까지만)중간의 B가 빠져 C는 구간을 못 좁히고 인덱스 안에서 걸러내는 데만 쓰인다
WHERE A > ? AND B = ?부분 (A까지만)범위 조건 뒤 컬럼은 정렬이 깨져 못 씀

PostgreSQL 각주: 선두 컬럼 조건이 없어도 인덱스 전체를 훑을 수는 있지만 구간을 못 좁혀 플래너가 대개 Seq Scan을 고른다 — "못 탄다"가 아니라 "타 봐야 손해". 선두 고유값이 한 자릿수일 때의 skip scan은 PostgreSQL 18부터. "부분" 행의 강등된 조건도 계획에는 Index Cond로 찍혀 텍스트로는 구분이 안 된다.

중복아래 두 인덱스는 사실상 겹친다
CREATE INDEX idx_a   ON orders (user_id);              -- (A)
CREATE INDEX idx_a_b ON orders (user_id, created_at);  -- (A, B)
--   → idx_a는 idx_a_b의 "왼쪽 접두사"와 동일. 유지비만 두 배.
정리접두사에 흡수되는 인덱스는 지운다 — 단, 방향이 반대면 흡수되지 않는다
DROP INDEX idx_a;   -- 운영 중이면 DROP INDEX CONCURRENTLY

-- 주의: (user_id, created_at)가 있어도 created_at 단독 조회는 못 탄다.
--       그 쿼리가 진짜 필요하면 별도 인덱스가 맞다.
CREATE INDEX idx_created ON orders (created_at);

습관 하나로 테이블당 인덱스 개수가 눈에 띄게 줄어든다

새 인덱스 요청을 받으면 먼저 psql의 \d orders(또는 pg_indexes 뷰의 indexdef)로 기존 인덱스 목록을 보고, 요청 컬럼이 어떤 인덱스의 선두에 이미 들어있는지 확인한다.

반대로 빠뜨리기 쉬운 인덱스도 있다 — PostgreSQL은 FK 컬럼에 인덱스를 자동으로 만들지 않는다
없으면 부모 행 DELETE마다 자식 테이블 전체를 훑는다

10-1. 걸었는데도 계획이 Seq Scan 그대로라면 — 원인 목록

이 목록이 머리에 있으면 슬로 쿼리를 5분 만에 고친다. 일곱 가지를 낱개로 외우기보다 세 덩어리로 묶는 편이 인출이 쉽다.

원인 7종을 세 덩어리로 — 손 · 시 · 안

① 컬럼에 손을 댔다→함수·연산 · 타입 캐스트
② 시작점을 못 찍는다→선행 와일드카드 · 선두 컬럼 누락
③ 플래너가 안 쓴다→낮은 선택도 · OR 한쪽 무인덱스 · 부분 인덱스 조건 불일치

①②는 "못 타는 것(can't)", ③은 "안 타는 것(won't)"이다. 고치는 손이 다르다 — ①②는 쿼리를, ③은 인덱스 설계나 통계를 건드린다.

덩어리 ① — 컬럼에 손을 댔다

못 탐함수·연산·캐스트가 컬럼 쪽에 붙었다
-- 인덱스에는 컬럼의 "원본 값"이 정렬돼 있는데
-- 가공된 값이라 트리에서 내려갈 시작점을 못 잡는다
WHERE date(created_at) = '2026-01-01'
WHERE price * 1.1 > 10000
WHERE id::text = '100'
WHERE id = 100.0  -- bigint 컬럼 vs numeric 리터럴
--   → id::numeric 으로 승격돼 인덱스 상실
고침계산은 반대편 상수 쪽에서 끝낸다
WHERE created_at >= '2026-01-01'
  AND created_at <  '2026-01-02'
WHERE price > 10000 / 1.1
WHERE id = 100   -- JDBC라면 setLong

-- 정식 출구: 표현식 인덱스
--   조건 둘 — 쿼리의 식이 인덱스의 식과 "똑같아야" 하고,
--            함수가 IMMUTABLE 이어야 한다
CREATE INDEX ON users ((lower(email)));
-- → WHERE lower(email) = $1 이 탄다
타입 불일치는 대개 "에러로 드러난다" — 조용히 죽는 경우만 조심하면 된다 WHERE phone = 01012345678(컬럼은 varchar)은 operator does not exist: character varying = integer로 실행 자체가 안 된다. 조용히 인덱스를 잃는 쪽은 컬럼 쪽에 캐스트가 붙는 경우다.
그리고 timestamptz의 date()는 세션 타임존에 따라 달라져 IMMUTABLE이 아니므로 표현식 인덱스로 못 만든다 — 날짜 조건은 범위로 고치는 게 정답이다. 표현식 인덱스는 인덱스 한 벌 값이라, 쿼리를 고칠 수 있으면 그게 먼저다.

덩어리 ② — 시작점을 못 찍는다

WHERE name LIKE '%kim%'
시작 문자가 안 정해져 트리를 내려갈 방법이 없다. 튜닝 문제가 아니라 B-tree의 구조적 한계(4-2). → LIKE 'kim%'로 요건을 좁히거나(collation 함정 주의 — text_pattern_ops), 정말 부분 일치가 필요하면 pg_trgm GIN·전문 검색·검색 엔진으로 넘긴다
(A, B) 인덱스에 WHERE B = ?
선두 컬럼 누락(9-3). B는 리프 전체에 흩어져 있어 연속 구간을 찍을 수 없다

덩어리 ③ — 플래너가 안 쓴다

낮은 선택도
축 2. 쿼리가 아니라 인덱스 설계 쪽 문제. 플래너가 "Seq Scan이 더 싸다"고 판단해 의도적으로 안 쓴다. 통계가 낡아 잘못 판단한 것이라면 ANALYZE orders가 먼저다
OR로 묶인 조건에서 한쪽에 인덱스가 없음
인덱스 없는 쪽 때문에 어차피 전체를 훑어야 해서 양쪽 다 Seq Scan. → 양쪽 모두에 인덱스를 건다 — PostgreSQL은 두 인덱스 결과를 BitmapOr로 합쳐 힙을 한 번에 읽으므로 UNION ALL로 쪼개는 우회가 필요 없는 경우가 많다
부분 인덱스의 조건 불일치
축 2. 인덱스의 WHERE를 쿼리가 포함하지 않으면 후보에서 빠진다

덩어리 ①②를 관통하는 규칙 한 줄

WHERE 절에서 인덱스 컬럼은 맨몸으로 두고, 계산은 반대편 상수 쪽에서 끝낸다
컬럼에 손을 대는 순간(함수 · 연산 · 캐스트) 인덱스는 죽는다
덤 — 날짜 범위를 BETWEEN으로 쓰지 않는 이유 BETWEEN '2026-01-01' AND '2026-01-31'은 timestamptz 컬럼에서 끝값이 2026-01-31 00:00:00으로 해석돼 1월 31일 하루가 통째로 누락된다. 그래서 >= 시작 AND < 다음_시작(끝을 여는 반열린 구간)이 표준형이다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

구조 3요소와 각각의 효과?
다 · 리 · 옆 — 다분기(높이 3~4단) / 데이터는 리프에만(fan-out↑ + 비용 균일) / 옆으로 양방향 연결(범위·ORDER BY·페이징 공짜).
+는 어느 쪽인가?
데이터를 리프로 "몰았다"는 뜻. 내부 노드에도 데이터를 두는 쪽이 B-Tree. 방향을 반대로 외우는 사람이 아주 많다.
페이지 산수 한 줄?
8,192 − 24 − 16 = 8,152B, 엔트리 20B → 407개(보수 300) → 3층 = 2,700만 행, 조회 한 건 3~4장.
인덱스 vs Seq Scan 배수?
1,000만 행 · 200B 기준 4장 대 285,715장 ≈ 71,000배. 그리고 데이터가 커질수록 더 벌어진다.
PostgreSQL 리프에 든 것?
행이 아니라 TID(6B) = (블록 번호, 라인 포인터 번호). 클러스터드 인덱스가 없고 전부 세컨더리 → 힙 페치가 항상 따라붙는다.
스캔 세 가지?
Index Scan(TID마다 힙) / Bitmap Heap Scan(TID를 물리 순서로 모아 한 번에) / Index Only Scan(힙 생략, 단 VM 비트).
Index Only Scan의 진짜 확인법?
노드 이름이 아니라 Heap Fetches 숫자. 결과 행 수에 육박하면 VACUUM이 밀린 것(대개 롱 트랜잭션).
비-HOT UPDATE의 한 줄?
바뀐 컬럼과 무관하게 모든 인덱스에 새 엔트리. 인덱스를 하나 더 걸면 HOT 성립 확률 자체가 떨어져 다른 인덱스의 쓰기까지 는다.
걸까 말까 4축?
쓰 · 선 · 중 · 검 — 쓰기 빈도(HOT) / 선택도(부분 인덱스) / 기존 인덱스와 중복(선두 컬럼) / EXPLAIN (ANALYZE, BUFFERS) 검증.
안 타는 원인 3덩어리?
손 · 시 · 안 — 컬럼에 손댐(함수·캐스트) / 시작점 못 찍음(선행 %, 선두 컬럼) / 플래너가 안 씀(선택도·OR·부분 인덱스 조건).
규칙 한 줄?
인덱스 컬럼은 맨몸으로, 계산은 반대편 상수에서. 날짜는 BETWEEN 말고 반열린 구간.
MySQL과 갈리는 첫 지점?
InnoDB는 PK 리프에 행 전체 · 세컨더리 리프에 PK 값. PostgreSQL은 힙 + 전부 세컨더리 + TID.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

한 노드에 자식이 여러 개 달리는 구조가 이진 트리에 비해 뭘 벌어주나요? 필수힌트: "높이가 낮아진다"로 끝내지 말고 숫자로 말한다

디스크는 바이트 단위가 아니라 페이지(PostgreSQL은 8KB) 단위로 읽는다. 어차피 8KB를 통째로 읽어올 거면 그 안에 키를 최대한 많이 담는 게 이득이다. 한 노드에 키가 많다 = 자식이 많다(fan-out이 크다) = 같은 데이터 건수를 더 낮은 높이로 담을 수 있다 = 루트에서 리프까지 읽는 페이지 수, 즉 디스크 접근 횟수가 준다.

숫자로 말하면 설득력이 붙는다. bigint 키의 인덱스 엔트리는 20바이트이고 페이지의 유효 공간이 8,152바이트이므로 한 페이지에 약 400개, 여유를 보고 300개로 잡으면 3층이 2,700만 행, 4층이 81억 행이다. 같은 2,700만 행을 이진 트리에 담으면 25단이다.

여기에 한 겹 더 얹으면 좋다 — 상위 레벨(루트·내부 페이지)은 개수가 적어 shared_buffers에 상주하기 쉬우므로, 실제 물리 I/O는 리프 한두 장 + 힙 페치로 줄어드는 경우가 많다. "트리가 낮다"는 것은 곧 "상위 층 전체를 메모리에 올려둘 수 있다"는 뜻이기도 하다.

해시 인덱스가 O(1)인데 왜 B+Tree를 기본으로 쓰나요? 필수힌트: 해시 함수가 무엇을 파괴하는지 한 단어로

해시 인덱스는 등호 비교(=)만 가능하다. 해시 함수는 순서를 파괴하므로 >, BETWEEN, ORDER BY, LIKE 'kim%', 그리고 복합 인덱스의 선두 컬럼 부분 활용이 전부 불가능하다. 실무 쿼리에서 범위·정렬이 차지하는 비중(4-2)을 생각하면 "모든 걸 웬만큼 잘하는" B+Tree가 기본이 되는 게 자연스럽다.

PostgreSQL의 Hash 인덱스(USING hash)는 PostgreSQL 10부터 WAL에 기록돼 크래시 안전해졌고, 키 값 대신 해시 코드만 저장하므로 긴 문자열 키의 등호 조회에서는 B-tree보다 작아 보조로 쓸 만하다 — 유니크 제약은 못 건다.

(user_id, created_at) 인덱스가 있는데 created_at만으로 조회하는 쿼리가 느립니다. 어떻게 하죠? 필수힌트: 선택지 셋을 "비용 순"으로 늘어놓는다

선두 컬럼 규칙(9-3) 때문에 그 쿼리는 기존 인덱스를 못 탄다. created_at 값이 리프 전체에 흩어져 있어 연속 구간을 찍을 수 없기 때문이다. 선택지는 셋이다.

⑴ 쿼리를 고친다. 대부분의 화면 조회는 사실 특정 사용자 범위 안의 조회라서 user_id 조건을 붙일 수 있는 경우가 많다. 가능하면 이게 최선 — 인덱스를 한 벌도 더 안 산다.

⑵ (created_at) 또는 (created_at, user_id) 인덱스를 새로 만든다. 전역 최근순 조회가 실제 요구사항이라면 이쪽이 맞다. 인덱스 하나 값을 지불하는 것. 최근순 DESC라고 DESC 인덱스를 따로 만들 필요는 없다 — PostgreSQL은 같은 인덱스를 Index Scan Backward로 읽는다.

⑶ 컬럼 순서를 바꾼 인덱스로 교체한다. 단, 기존 인덱스를 쓰던 쿼리들이 무엇인지 먼저 확인해야 한다. 순서 변경은 다른 쿼리를 조용히 망가뜨릴 수 있다.

인덱스가 많으면 왜 위험한가요? 테이블당 몇 개까지가 적당한가요? 시니어 변별힌트: 개수로 답하면 진다. 기준을 바꿔서 답한다

개수 자체보다 "각 인덱스가 어떤 쿼리를 위해 존재하는지 설명할 수 있는가"가 기준이다. 설명 못 하는 인덱스는 지운다. 위험은 네 갈래다.

쓰기 증폭
INSERT는 인덱스 수만큼, UPDATE는 인덱스 컬럼을 하나라도 건드리면 HOT에서 탈락해 모든 인덱스를 갱신 — 인덱스가 늘수록 HOT 성립 확률 자체가 떨어진다.
공간과 캐시 잠식
디스크 비용 + shared_buffers 자리 다툼(다음 질문에서 자세히).
플래너의 선택 실패 확률 증가
후보가 많아질수록 엉뚱한 계획이 나올 여지가 는다.
가장 무서운 것 — 누적
"이미 있는 인덱스를 몰라서 비슷한 걸 또 만드는" 일이 팀 규모로 반복된다.

실무에서는 미사용 인덱스(pg_stat_user_indexes의 idx_scan = 0, 통계 리셋 시점 주의)를 정기적으로 정리하고, pg_stat_user_tables의 n_tup_upd 대비 n_tup_hot_upd 비율로 인덱스가 UPDATE를 얼마나 무겁게 하는지를 본다.

그리고 인덱스 추가·삭제는 되돌리기 쉬워 보이지만, 대형 테이블에서는 CREATE INDEX CONCURRENTLY조차 테이블 2회 스캔 + WAL 폭증 + 레플리카 지연이라 배포 시점까지 함께 설계해야 한다.

인덱스가 "공간과 캐시를 잠식"한다는 게 정확히 무슨 뜻인가요? 시니어 변별힌트: 공간(디스크)과 캐시(메모리)를 갈라 말한 뒤, 둘이 만나는 지점까지 잇는다

바로 앞 답변에서 던진 표현이라 되받아치기 좋은 꼬리질문이다. 공간은 디스크 비용, 캐시(shared_buffers)는 메모리 비용으로 성격이 완전히 다르고, 둘을 구분해 말한 뒤 "그래서 둘이 어떻게 만나 문제가 되는가"까지 잇는 게 답변의 완성형이다.

⑴ 공간 — 인덱스가 디스크를 얼마나 먹는가

인덱스는 논리적인 메타데이터가 아니라 B+Tree 파일을 하나 더 만드는 것이다. 리프 엔트리가 키 + TID를 품은 8바이트 헤더 + 4바이트 라인 포인터이므로(3절), 크기는 대략 이렇게 잡힌다.

인덱스 1개 크기 ≈ (키 크기 + 12바이트 고정 오버헤드) × 행 수 ÷ fillfactor(0.9)
orders 1,000만 행, 행 평균 200바이트 (3절과 같은 테이블)
대상계산대략적인 크기
힙(행 200B + 튜플 헤더 24B + 라인 포인터 4B)285,715 페이지 × 8KB약 2.3GB
(user_id, created_at) 인덱스 1개 (키 16B + 12B)28B × 1,000만 ÷ 0.9약 300MB
인덱스 5개—약 1.5GB 안팎

인덱스를 5개 달면 테이블 용량의 절반 이상이 더 붙고, 행이 좁은 테이블이면 인덱스 총합이 힙을 넘어선다. 대가는 디스크 값만이 아니다 — 백업 시간과 저장소, WAL 전송량(레플리카), 복원 시 인덱스 재생성 시간이 전부 같이 늘어난다.

-- 어떤 테이블이 인덱스로 뚱뚱해졌는지 한눈에 본다
SELECT c.relname,
       pg_size_pretty(pg_table_size(c.oid))   AS table_size,   -- 힙(+TOAST)
       pg_size_pretty(pg_indexes_size(c.oid)) AS index_size    -- 인덱스 총합
  FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
 WHERE c.relkind = 'r' AND n.nspname = 'public'
 ORDER BY pg_indexes_size(c.oid) DESC;
--   → index_size가 table_size를 넘어서는 테이블이 1순위 정리 대상이다.

⑵ 캐시 — shared_buffers와 OS 페이지 캐시, 두 겹

shared_buffers는 PostgreSQL이 디스크에서 읽어온 8KB 페이지를 메모리에 올려두고 재사용하는 공유 캐시다(기본값 128MB — 운영에서는 RAM의 1/4 안팎). PostgreSQL 고유의 사정 하나 — 파일 I/O를 OS에 맡기므로 shared_buffers에 없는 페이지는 OS 페이지 캐시가 한 번 더 받아 준다. 플래너는 이 둘을 합친 크기를 effective_cache_size로 짐작해 인덱스 스캔 비용을 매긴다.

디스크까지 가는 비율 1% → 0.99 × 0.1µs + 0.01 × 100µs ≈ 1.1µs
디스크까지 가는 비율 5% → 0.95 × 0.1µs + 0.05 × 100µs ≈ 5.1µs   ← 약 4.6배 느려짐
4%p 차이가 응답 시간 4.6배 — "메모리에 다 안 올라가면 갑자기 느려진다"는 현상의 정체

함정 하나: PostgreSQL 통계의 read는 "커널에 요청했다"는 뜻이지 디스크까지 갔다는 보장이 아니다(OS 캐시 적중일 수 있다).

⑶ 잠식 — 디스크 비용이 결국 메모리 자리를 놓고 경쟁한다

shared_buffers는 유한하고, 오래 안 쓴 페이지부터 밀어내는 방식(clock-sweep — 페이지마다 usage_count를 두고 시곗바늘이 지나갈 때마다 깎아 0이 되면 교체)으로 관리된다. 여기서 두 갈래로 잠식이 일어난다.

① 쓰기가 인덱스 페이지를 계속 끌어올린다

INSERT 한 번에 인덱스 5개를 갱신하려면 그 5개 트리의 해당 리프 페이지를 전부 shared_buffers로 읽어올려야 한다(PostgreSQL은 인덱스 변경을 미뤄 두는 장치가 없다). 아무도 조회에 안 쓰는 인덱스라도 쓰기 때문에 메모리를 점유하고, 매번 접근되니 usage_count가 높아 잘 밀려나지도 않는다.

② 안 쓰는 인덱스가 핫 데이터를 밀어낸다

before — 필요한 인덱스만 2개 (shared_buffers 8GB)
[ 최근 주문 4GB │ 인덱스 2GB │ 여유 2GB ]
→ 핫 데이터가 전부 상주. 적중률 99.5%

after — 안 쓰는 인덱스 3개 + 야간 배치가 그걸 훑고 감
[ 최근 주문 2GB │  인덱스 5GB  │ …      ]
→ 낮 시간 일반 조회가 디스크를 때린다. 적중률 93%

핵심은 "인덱스가 디스크를 먹는다"로 끝나는 게 아니라, 그 디스크 페이지들이 결국 메모리 자리를 놓고 실데이터와 경쟁한다는 점이다. 디스크는 돈으로 사면 되지만 캐시는 RAM이라 늘리는 값이 훨씬 비싸다.

-- shared_buffers 적중률: hit / (hit + read).  read는 "커널에 요청" (디스크 확정 아님)
SELECT round(100.0 * sum(heap_blks_hit)
             / nullif(sum(heap_blks_hit) + sum(heap_blks_read), 0), 2) AS heap_hit_pct,
       round(100.0 * sum(idx_blks_hit)
             / nullif(sum(idx_blks_hit) + sum(idx_blks_read), 0), 2)   AS idx_hit_pct
  FROM pg_statio_user_tables;
--   99% 아래로 내려가면 조사 대상. 인덱스별은 pg_statio_user_indexes.

-- 지금 shared_buffers에 무엇이 들어있나 — 릴레이션(테이블·인덱스)별 점유량
CREATE EXTENSION IF NOT EXISTS pg_buffercache;
SELECT c.relname, count(*) AS buffers, pg_size_pretty(count(*) * 8192) AS size
  FROM pg_buffercache b
  JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
 WHERE c.relname LIKE '%orders%'
 GROUP BY c.relname ORDER BY buffers DESC;
pg_stat_user_indexes.idx_scan = 0인 인덱스가 위 결과의 상위에 있다면, 그게 정확히 "잠식"의 현장 증거다
"안 쓰는데 메모리는 먹고 있다"를 숫자로 보여줄 수 있으면 인덱스 삭제를 설득하기가 훨씬 쉬워진다
가산점 — PostgreSQL도 이 문제를 알고 있다. 다만 반만 막는다 일회성 대량 읽기가 캐시를 씻어내는 것을 막으려고, shared_buffers의 1/4보다 큰 테이블을 Seq Scan할 때는 작은 링 버퍼(256KB)만 돌려쓰고 나머지 캐시를 건드리지 않는다(VACUUM·대량 COPY도 각자의 링 버퍼를 쓴다). 다만 이건 일회성 풀스캔에 대한 방어다. 안 쓰는 인덱스가 매 INSERT마다 정상 경로로 접근되면 usage_count가 계속 올라가 이 장치로는 막히지 않는다 — 결국 안 쓰는 인덱스는 지우는 것이 유일한 해법이라는 결론으로 돌아온다.

MySQL 대조: InnoDB 버퍼 풀은 단일 캐시(16KB 페이지, 보통 O_DIRECT로 OS 캐시 우회)이고, 같은 문제를 LRU를 old/young 두 구역으로 나눠(새 페이지는 뒤쪽 3/8 지점에 넣고 innodb_old_blocks_time 안에 다시 접근된 것만 승격) 푼다. 장치는 다르지만 "반복 접근되는 안 쓰는 인덱스는 못 막는다"는 결론은 같다.
인덱스를 지우면 성능이 좋아지는 경우도 있나요? 가산점힌트: 네 가지. 그리고 마지막에 "태도"로 마무리한다

있다. 네 갈래다.

⑴ 낮은 선택도 인덱스를 플래너가 잘못 골라 힙 랜덤 I/O를 대량으로 내던 케이스 — 통계가 낡았을 때 흔하다. 지우기 전에 ANALYZE부터.
⑵ 쓰기가 지배적인 테이블에서 거의 안 쓰이는 인덱스를 제거해 INSERT 처리량이 오르는 케이스.
⑶ 자주 바뀌는 컬럼을 품은 인덱스를 지워 UPDATE가 HOT으로 돌아서는 케이스 — 모든 인덱스의 쓰기가 같이 사라지고 bloat도 멎는다(n_tup_hot_upd 비율로 확인). 가장 극적인 개선이 여기서 나온다.
⑷ 중복 인덱스를 정리해 shared_buffers 적중률이 오르는 케이스.

"성능 개선 = 인덱스 추가"라는 반사신경 대신, 측정 → 가설 → 검증(EXPLAIN (ANALYZE, BUFFERS) + 실제 응답 시간) 사이클로 접근한다는 태도를 보여주는 게 이 질문의 핵심이다.

MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 다섯 지점 — 리프·UPDATE·완충·설계도구·캐시

① 리프에 든 것 — InnoDB는 클러스터드(PK) 리프에 행 전체, 세컨더리 리프에 PK 값. PostgreSQL은 테이블이 힙이고 모든 인덱스 리프에 TID(6바이트). 그래서 "PK가 크면 모든 세컨더리가 커진다"는 PostgreSQL에서 성립하지 않고, 대신 힙 페치가 항상 따라붙는다.

② UPDATE 비용 — InnoDB는 제자리 갱신이라 바뀐 컬럼이 든 인덱스만 갱신하지만, PostgreSQL은 새 버전 튜플을 만드므로 HOT이 안 되면 모든 인덱스에 새 엔트리를 꽂는다.

③ 인덱스 쓰기 완충 — InnoDB의 체인지 버퍼 같은 지연 장치가 PostgreSQL에는 없어 인덱스 변경이 즉시 해당 페이지에 닿는다.

④ PostgreSQL만의 설계 도구 — 부분 인덱스(WHERE), 표현식 인덱스, INCLUDE, BRIN·GIN. MySQL은 함수 인덱스가 8.0.13부터이고 부분 인덱스는 없다.

⑤ 캐시와 페이지 — 16KB 페이지 + 단일 버퍼 풀 vs 8KB 페이지 + shared_buffers와 OS 캐시의 이중 구조.

이 다섯을 짚으면 "한쪽만 써봤다"가 아니라 "저장 구조의 차이를 원리로 이해했다"로 들린다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

그래서 +는 정확히 무엇을 뜻하나요? B-Tree와 뭐가 다른가요? 함정힌트: 방향을 반대로 답하면 그 뒤 설명이 전부 무너진다

+는 "데이터를 리프로 몰았다"는 뜻이다. 내부 노드에도 데이터를 두는 쪽이 B-Tree이고, 리프에만 두는 쪽이 B+Tree다. "내부 노드에도 데이터를 둘 수 있게 개선한 게 B+Tree"는 정확히 반대다.

그리고 이 한 번의 선택이 능력 두 가지를 사 준다는 것까지 붙여야 답이 완성된다. ⑴ 내부 노드가 가벼워져 fan-out이 커지고 트리가 더 낮아진다(같은 2,700만 행에 3층 대 5층). ⑵ 리프만 정렬 순서로 이어 붙이면 전체를 순회할 수 있게 되므로 리프 연결 리스트가 가능해진다 → 범위·정렬·페이징이 싸진다.

PostgreSQL 각주도 함께 던지면 좋다 — 매뉴얼과 USING btree는 "B-tree"라 부르지만 TID는 리프에만 있고, 내부 페이지는 길잡이 키만 가지며, 리프는 양방향 연결이다. 이름만 B-tree이고 구조는 B+Tree다.

범위 조회가 리프를 옆으로 훑는 거라면, 그냥 정렬된 배열이나 연결 리스트로 인덱스를 만들면 안 되나요? 가산점힌트: 조회만 보면 맞는 말이다. 쓰기를 보면 무너진다

조회만 놓고 보면 정렬된 배열이 오히려 낫다. 이진 탐색으로 시작점을 찾고 옆으로 훑으면 되니 B+Tree의 리프 스캔과 같다. 무너지는 지점은 쓰기다.

중간에 한 건을 삽입하면 뒤의 모든 원소를 밀어야 한다. 1,000만 행이면 디스크 페이지 수십만 장을 다시 쓰는 일이다.

연결 리스트

삽입은 싸지만 시작점을 찾는 데 O(n)이다. "어디로 내려갈지 알려주는 상위 구조가 없다"는 게 치명적이다.

B+Tree는 이 둘을 합친 물건이다 — 리프끼리의 연결 리스트(옆으로 훑기)를 유지하면서, 위에 다분기 트리를 얹어 시작점을 3~4번 만에 찍게 해 준다. 그리고 삽입은 페이지 하나가 찼을 때만 둘로 나누고 부모에 길잡이 키를 올리는 국소적인 작업이라, 전체를 다시 쓰지 않으면서도 균형이 유지된다.

정리하면 — B+Tree는 "정렬 순서 유지 · 빠른 진입 · 싼 삽입" 셋을 동시에 만족시키려고 나온 타협안이다. 셋 중 하나만 필요하면 더 단순한 구조가 이긴다(예: 등호만 필요하면 해시, 물리 순서와 상관이 높으면 BRIN).

PostgreSQL 리프에 든 게 행이 아니라 TID라는 사실이, 실제로 무엇을 바꾸나요? 필수힌트: 조회 쪽 하나, 쓰기 쪽 하나, 설계 쪽 하나

조회 — 인덱스는 "값 → 주소"까지만 알려주므로 힙 페치가 항상 따라붙는다. 그래서 대상 행이 많아지면 랜덤 I/O가 행 수에 비례해 늘고, 어느 지점부터는 Seq Scan이 이긴다(random_page_cost 4.0 대 seq_page_cost 1.0). 그 사이 구간을 메우는 것이 Bitmap Heap Scan이고, 힙 페치를 없애는 유일한 경로가 Index Only Scan이다.

쓰기 — 행이 다른 TID로 옮겨가면(비-HOT UPDATE) 그 행을 가리키던 모든 인덱스가 갱신된다. InnoDB처럼 "바뀐 컬럼의 인덱스만" 고치는 게 아니다.

설계 — PK가 커도 다른 인덱스가 같이 커지지 않는다(리프에 PK가 아니라 6바이트 TID가 들어가므로). InnoDB에서는 세컨더리 리프에 PK 값이 복제되므로 PK 크기가 전 인덱스에 번지지만, PostgreSQL에서는 그 경로가 없다. 대신 랜덤 UUID PK의 비용은 PK B-tree 자체의 무작위 삽입(페이지 분할)에서 난다.

계획에 Index Only Scan이라고 찍혔는데도 느립니다. 무엇을 봐야 하나요? 함정힌트: 노드 이름은 "시도했다"는 뜻이지 "성공했다"는 뜻이 아니다

Heap Fetches 숫자를 봐야 한다. Index Only Scan은 "힙에 안 갈 수도 있는 경로를 골랐다"는 뜻이지 "힙에 안 갔다"는 뜻이 아니다.

이유는 인덱스 엔트리에 MVCC 정보(xmin/xmax)가 없다는 데 있다. 그래서 PostgreSQL은 visibility map에서 해당 힙 블록의 비트를 확인하고, 비트가 0이면 결국 힙 페이지를 읽어 가시성을 확인한다. 그때마다 Heap Fetches가 1씩 오른다.

비트를 켜는 것은 VACUUM이므로, Heap Fetches가 결과 행 수에 육박한다면 원인은 대개 VACUUM이 밀린 것이고, VACUUM이 밀리는 대표 원인은 롱 트랜잭션이다(오래 열려 있는 트랜잭션이 "아직 이 버전을 볼 수도 있다"고 주장하는 동안에는 죽은 튜플을 못 치운다). 즉 이 문제는 인덱스 문제가 아니라 트랜잭션 관리 문제로 귀결된다.

Bitmap Heap Scan은 언제 고르고, Recheck Cond는 왜 붙나요? 가산점힌트: 랜덤을 순차로 바꾸는 장치. 그리고 메모리가 모자랄 때의 타협

"인덱스는 타는데 대상 행이 수만 건"인 중간 구간에서 고른다. Index Scan은 TID 하나마다 힙 페이지를 랜덤으로 읽으므로 행이 늘수록 급격히 비싸지는데, Bitmap 계열은 TID를 전부 모아 블록 번호 순으로 정렬한 뒤 힙을 한 번 훑는다. 랜덤 접근을 순차에 가깝게 바꾸는 것이 핵심이고, 같은 페이지에 여러 행이 걸려도 페이지를 한 번만 읽는다는 이득도 있다.

BitmapOr로 여러 인덱스의 결과를 합칠 수 있는 것도 이 구조 덕분이다 — WHERE a = 1 OR b = 2에서 두 인덱스를 각각 타고 비트맵을 합쳐 힙을 한 번에 읽는다.

Recheck Cond는 비트맵이 work_mem을 넘겨 "행 단위"에서 "페이지 단위(lossy)"로 뭉개졌을 때 붙는다. 페이지 단위가 되면 "이 페이지 어딘가에 대상이 있다"까지만 알므로, 힙 페이지를 읽은 뒤 조건을 한 번 더 검사해 진짜 대상 행을 골라야 한다. work_mem이 모자라다는 신호로 읽을 수 있다.

(A, B) 인덱스에서 A가 범위 조건이면 왜 B가 쓸모없어지나요? 필수힌트: 리프 정렬 순서를 머리에 그린다

(A, B)는 "A로 먼저 정렬하고, A가 같을 때만 B로 정렬"된 하나의 트리이기 때문이다. B의 정렬은 "같은 A 그룹 안에서만" 유효하다.

A = 5 AND B = 3이면 A=5 그룹 안에서 B가 정렬돼 있으므로 B=3의 위치를 바로 찍을 수 있다. 그런데 A > 5 AND B = 3이면 대상이 A=6, 7, 8… 여러 그룹에 걸치고, 각 그룹마다 B=3이 따로따로 들어 있다. 즉 B 기준으로 보면 다시 흩어진 상태라 연속된 한 구간을 찍을 수 없다.

그래서 B는 구간을 좁히는 데(access) 못 쓰이고, 인덱스를 훑으며 걸러내는 데(filter)만 쓰인다. 계획에는 둘 다 Index Cond로 찍혀 텍스트로는 구분이 안 되므로, EXPLAIN (ANALYZE, BUFFERS)에서 실제로 읽은 행 수와 Buffers로 판단해야 한다.

여기서 복합 인덱스 컬럼 순서 규칙이 나온다 — 등호 조건 컬럼을 앞에, 범위 조건 컬럼을 뒤에. WHERE status = 'PAID' AND created_at > ?이면 (status, created_at)이 맞고, 순서를 뒤집으면 status가 죽는다.

UUID v4를 PK로 쓰면 인덱스에 무슨 일이 생기나요? 가산점힌트: 페이지 분할 정책 하나만 떠올리면 전부 설명된다

핵심은 PostgreSQL의 B-tree가 "맨 오른쪽 페이지"만 특별 취급한다는 사실이다. 단조 증가 키가 계속 붙는 경우 맨 오른쪽 페이지는 반으로 가르지 않고 오른쪽에 계속 채운다. 그래서 bigint IDENTITY PK 인덱스는 페이지가 촘촘하게(거의 꽉) 찬다.

UUID v4는 값이 무작위라 삽입이 트리 곳곳의 페이지로 흩어진다. 그 페이지들은 일반 규칙대로 반으로 갈라지므로 평균 밀도가 낮아지고, 결과적으로 같은 행 수에 페이지 수가 더 많아진다 — 인덱스가 커지고, 캐시를 더 먹고, 층수가 늘어날 여지도 생긴다.

두 번째 비용은 쓰기 지역성이다. 단조 증가 키는 매번 같은 맨 오른쪽 페이지를 만지므로 그 페이지가 항상 캐시에 있지만, 랜덤 키는 삽입마다 다른 리프 페이지를 만져 캐시 미스와 디스크 쓰기가 흩어진다.

단, PostgreSQL에서 "PK가 커서 모든 세컨더리 인덱스가 커진다"는 InnoDB식 비용은 없다(리프에 PK가 아니라 6바이트 TID가 들어가므로). 비용이 나는 자리는 PK B-tree 자체와, 그 UUID 값을 담는 FK 컬럼·조인 키 인덱스다. 시간 순서를 담은 UUID(v7 계열)나 bigint 대리 키를 쓰면 단조 증가 쪽 이점을 되찾을 수 있다.

"이 인덱스는 3층입니다"를 실제로 확인할 수 있나요? 가산점힌트: contrib 확장 하나

pageinspect 확장으로 볼 수 있다. bt_metap('인덱스이름')이 돌려주는 level이 루트 페이지의 레벨이고, 리프 레벨이 0이므로 트리 높이 = level + 1이다.

CREATE EXTENSION IF NOT EXISTS pageinspect;
SELECT level, root, fastroot FROM bt_metap('idx_orders_user_created');
-- level = 2 이면 루트·내부·리프 3층

다만 면접에서 더 중요한 건 도구 이름이 아니라 "그래서 무엇을 확인하려는가"다. 층수보다 실무에서 훨씬 자주 보는 것은 EXPLAIN (ANALYZE, BUFFERS)의 Buffers이고 — "조회 한 건에 페이지 몇 장을 만졌나"가 곧 층수 + 힙 페치의 실측값이다. 인덱스 크기는 pg_relation_size(), bloat 여부는 pgstattuple의 pgstatindex()로 본다.

한 줄 요약
B+Tree는 "다분기로 트리를 낮추고(8KB 페이지에 20바이트 엔트리를 400개 담아 fan-out 수백 — 3층이면 2,700만 행, 조회 한 건에 페이지 3~4장), 데이터를 리프로 몰아 내부 노드를 가볍게 만들어 더 낮추고, 그 리프들을 양방향으로 이어 붙여 범위 스캔과 역방향 정렬까지 얻은" 구조이며 (+는 데이터를 리프로 몰았다는 뜻이지 그 반대가 아니고, PostgreSQL이 "B-tree"라 부르는 것도 이 구조다). PostgreSQL에서 그 리프에 든 데이터는 행이 아니라 힙을 가리키는 TID라서 모든 인덱스 조회에 힙 페치가 따라붙고(그걸 없애는 유일한 경로가 visibility map에 기댄 Index Only Scan이다), 비-HOT UPDATE는 모든 인덱스를 건드린다. 인덱스를 걸지 말지는 쓰기 빈도(HOT) · 선택도(부분 인덱스) · 기존 인덱스와의 중복(선두 컬럼 규칙) · EXPLAIN (ANALYZE, BUFFERS) 검증, 네 축으로 판단한다.
