무중단 스키마 변경(online DDL) — "컬럼 하나 추가"가 서비스를 세우는 사슬과 그 사슬을 끊는 방법

질문: "대용량 테이블에 컬럼 추가/인덱스 추가를 무중단으로 하려면? (online DDL, pt-osc 등)"

핵심 관전 포인트 — 면접 첫 답변으로 그대로 말한다

대용량 테이블의 ALTER가 위험한 이유는 두 갈래다.
  1. 알고리즘과 무관한 사슬 — 모든 ALTER는 테이블의 배타 메타데이터 락(MDL)을 잡아야 한다. 열려 있는 긴 트랜잭션 하나가 그것을 막으면: ALTER 대기 → 그 테이블의 뒤따르는 모든 쿼리가 줄을 섬 → 앱 커넥션 풀 고갈 → 무관한 API까지 전면 장애.
  2. 알고리즘이 COPY/재구성일 때의 사슬 — 수 시간 동안 쓰기 차단 · 디스크 2배 · 복제 지연.
그래서 답은: 알고리즘 3종(INSTANT / INPLACE / COPY) 중 무엇이 걸리는지 먼저 판별 → 컬럼 추가는 INSTANT, 인덱스 추가는 INPLACE로 단언하되 lock_wait_timeout을 짧게 → 재구성이 불가피하면 pt-osc / gh-ost로 청크 복사 → 이 절차를 사람 기억이 아니라 마이그레이션 도구 · CI 린트 · 체크리스트에 고정.
도구 셋은 각각 복제 지연(네이티브) / 트리거 부하(pt-osc) / FK 미지원(gh-ost)이라는 대가를 지불하며, 어느 것도 MDL 문제 자체를 없애주지는 않는다. 그리고 INSTANT여도 MDL은 잡는다 — "MySQL 8이니까 안전하다"가 이 문항의 함정이다.

1왜 ALTER 한 줄이 전면 장애가 되는가 — 세 개의 사슬

"ALTER는 위험하다"를 아는 것과 어떤 단계를 거쳐 장애가 되는지를 말할 수 있는 것은 다른 평가를 받는다. 뭉뚱그린 "락 걸려서 느려진다"를 세 개의 사슬로 쪼갠다. 면접에서는 사슬 A를 먼저, 그 다음 B·C를 말한다.

1-1. 사슬 A — 메타데이터 락(MDL) 큐 · 알고리즘과 무관, 가장 흔한 사고

등장인물의 이름부터 고정한다. 이름이 비슷한 락 두 개를 섞으면 사슬 전체가 무너진다.

메타데이터 락(MDL) ≠ 행 락 — 완전히 다른 락이다

메타데이터 락 (MDL)행 락 (InnoDB row lock)
무엇을 보호테이블 정의(구조)행(데이터)
누가 잡나SELECT/INSERT/UPDATE = 공유, ALTER/DROP = 배타UPDATE/DELETE/FOR UPDATE
언제 풀리나문장 끝이 아니라 트랜잭션 끝트랜잭션 끝
대기 상한lock_wait_timeout 기본 31,536,000초 = 1년innodb_lock_wait_timeout 기본 50초
막혔을 때 표시Waiting for table metadata lockLock wait timeout exceeded(행)

함정: 트랜잭션 안에서 SELECT 한 번 하고 커밋을 안 한 세션은 그 테이블의 공유 MDL을 계속 쥐고 있다. 그리고 innodb_lock_wait_timeout을 5초로 줄여 놨어도 MDL 대기는 여전히 1년이다 — 다른 변수다.

엘리베이터 점검으로 외우기

점검 기사(ALTER)는 엘리베이터가 완전히 비어야(배타 MDL) 점검을 시작할 수 있다. 그런데 안에 오래 타고 있는 사람(긴 트랜잭션, 공유 MDL)이 내리질 않는다. 기사는 문 앞에서 기다린다. 문제는 건물 규칙 — "점검 기사가 대기 중이면 새로 타려는 사람은 태우지 않는다"(기사가 영원히 굶지 않게). 그래서 뒤이어 온 사람들(뒤따르는 SELECT/INSERT)이 전부 로비에 쌓이고(커넥션 풀 고갈), 로비가 막히니 그 엘리베이터와 상관없는 층에 가려던 사람까지 건물에 못 들어온다(무관한 API 장애). 점검이 1분짜리(INSTANT)여도, 안에 있는 사람이 안 내리면 로비는 똑같이 마비된다.

사슬을 문장으로 고정하면 이렇다. 각 칸에 역할 이름이 붙어 있는 것에 주목 — 인과를 서술하지 못하는 이유는 대개 칸이 없어서다.

  1. 보유자어떤 세션이 orders를 건드리는 긴 트랜잭션을 열어 두고 있다 — 대시보드 집계, 배치, 워크벤치에서 BEGIN 후 잊은 세션, 외부 API 호출을 트랜잭션 안에 넣은 앱 코드. 이 세션은 공유 MDL을 쥐고 있다.
  2. 대기자운영자가 ALTER TABLE orders ADD COLUMN …을 실행한다. ALTER는 배타 MDL을 요청하고 ①때문에 대기한다(SHOW PROCESSLIST에 Waiting for table metadata lock). 상한이 1년이므로 스스로 포기하지 않는다.
  3. 줄MDL은 큐다. 배타 요청이 대기 중이면, DDL이 영원히 굶는 것을 막기 위해 그 뒤에 들어오는 공유 요청도 배타 요청을 추월하지 못하고 줄을 선다. 이 순간부터 orders를 읽는 SELECT 한 줄까지 전부 멈춘다.
  4. 병목 자원앱 요청 스레드가 DB 응답을 기다리며 커넥션을 쥔 채 멈춘다. HikariCP 풀(기본 10개)은 순식간에 바닥난다. 풀은 앱 전체가 공유하므로 orders와 무관한 API(로그인, 상품 조회)까지 connection-timeout(기본 30초) 후 실패한다.
  5. 증폭톰캣 워커 스레드도 대기 요청으로 가득 차고, 헬스체크 타임아웃 → LB 제외 또는 재시작 → 재시작해도 DB 쪽 큐는 그대로라 다시 막힘. 테이블 하나의 락 대기가 서비스 전면 장애로 증폭됐다.

30초 스크립트 — 사슬 A를 입으로

"ALTER는 배타 메타데이터 락을 잡아야 하는데, 누군가 그 테이블에 긴 트랜잭션을 열어 두면 공유 MDL이 안 풀려서 ALTER가 대기합니다. 문제는 MDL이 큐라서, 대기 중인 배타 요청 뒤로 들어오는 SELECT까지 전부 줄을 선다는 겁니다. 앱 스레드는 커넥션을 쥔 채 멈추니 풀이 30초 안에 바닥나고, 그 테이블과 무관한 API까지 커넥션을 못 얻어 실패합니다. 이건 INSTANT여도 똑같습니다 — 그래서 lock_wait_timeout을 5초로 두고 실패하면 재시도합니다."

틀: 보유자 → 대기자 → 줄 → 병목 자원 → 증폭 범위. 다른 장애 사슬(커넥션 고갈, 스레드 고갈, 캐시 스탬피드)도 같은 다섯 칸으로 말할 수 있다.

사슬 A의 숫자 4개

  • lock_wait_timeout 기본 31,536,000초(1년) — MDL 대기 상한. 사실상 무한.
  • innodb_lock_wait_timeout 기본 50초 — 행 락 상한. MDL과 무관.
  • HikariCP 풀 기본 10개 — 앱 전체가 공유.
  • HikariCP connection-timeout 기본 30초 — 풀이 비었을 때 요청이 실패하기까지.

1-2. 사슬 B — 테이블 재구성의 자원 비용 (COPY / INPLACE-재구성)

알고리즘이 COPY거나 INPLACE 중에서도 재구성(rebuild)이 필요한 작업이면, MDL을 무사히 얻은 뒤에도 두 번째 사슬이 기다린다.

  1. 새 테이블 파일을 만들고 전 행을 읽어 다시 쓴다 → 테이블 크기만큼 디스크가 일시적으로 2배 필요(모자라면 중간 실패, 실패 정리도 오래 걸림).
  2. 수 시간 동안 CPU와 디스크 I/O를 점유 → 같은 인스턴스의 다른 쿼리도 느려진다(버퍼 풀을 복사 작업이 밀어내는 것 포함).
  3. COPY면 그 시간 내내 쓰기 차단(읽기만 허용) → 주문·결제 API 통째로 실패. INPLACE-재구성이면 쓰기는 허용되지만 그 사이 변경분을 온라인 로그(innodb_online_alter_log_max_size, 기본 128MB)에 쌓았다가 끝에 반영 → 쓰기가 많아 로그가 넘치면 수 시간 작업이 마지막에 실패.
  4. 마지막에 원본 ↔ 새 테이블 교체 시 다시 배타 MDL → 사슬 A가 여기서 한 번 더 발생할 수 있다.

1-3. 사슬 C — 복제 지연 (프라이머리에서 "온라인"이어도)

프라이머리에서 아무 문제 없이 끝난 ALTER가 읽기 복제본을 무너뜨리는 경로다. 이걸 아는지가 "네이티브 online DDL만으로 충분한가"에 답하는 열쇠고, pt-osc·gh-ost가 존재하는 가장 큰 이유다.

1-4. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

뭉뚱그린 표현이름사슬로 말하면
"ALTER 하면 락 걸려서 느려진다"MDL 큐긴 트랜잭션이 공유 MDL 점유 → ALTER가 배타 MDL 대기(상한 1년) → 뒤따르는 모든 쿼리가 큐 → 커넥션 풀 고갈 → 무관한 API까지 전면 장애
"테이블이 커서 오래 걸린다"재구성(rebuild) 비용전 행 재작성 → 디스크 2배 + CPU/I/O 점유 → (COPY) 쓰기 차단 / (INPLACE) 온라인 로그 초과 시 말미 실패 → 교체 시 MDL 재획득
"복제본이 밀린다"DDL 재실행 장벽ALTER 문장이 binlog로 전파 → 복제본이 같은 시간만큼 재실행 → 그동안 뒤 트랜잭션 전부 대기 → 지연 = ALTER 소요 시간

2MySQL 8 ALTER 알고리즘 3종 — 갈리는 원리 하나, 그 위에 목록

목록을 인출하려면 먼저 갈리는 원리 하나를 잡아야 한다. 판별 기준은 "이 작업이 클러스터드 인덱스 안의 행(row) 레이아웃을 건드리는가"다.

압축 암기구 — 질문의 두 작업이 이 안에 다 있다

"추가는 INSTANT, 인덱스는 INPLACE, 타입은 COPY."

I컬럼 추가 → INSTANT P인덱스 추가 → INPLACE(재구성 없음) C컬럼 타입 변경 → COPY

질문의 두 작업 — 컬럼 추가 = INSTANT, 인덱스 추가 = INPLACE — 는 둘 다 네이티브로 DML을 막지 않는다. 그런데도 이 문항이 중급인 이유는 사슬 A(MDL)와 사슬 C(복제 지연)가 알고리즘과 무관하게 남기 때문이다.

2-1. 알고리즘을 "요청"하지 말고 "단언"하라

MySQL은 ALGORITHM을 명시하지 않으면 가능한 가장 가벼운 것을 골라 주지만, 안 되면 조용히 무거운 쪽으로 내려간다. 컬럼 추가가 어떤 이유로 INSTANT가 불가능하면 INPLACE-재구성으로, 그것도 안 되면 COPY로 — 운영자는 실행이 끝날 때까지 모른다.

-- ❌ before: 알고리즘을 MySQL 재량에 맡김
ALTER TABLE orders ADD COLUMN coupon_code VARCHAR(32) NULL;
-- INSTANT일 거라 "믿고" 실행. 조건이 안 맞으면 재구성으로 조용히 강등
-- → 수 시간 디스크 2배 + 복제 지연. 끝날 때까지 아무도 모름.
 
-- ✅ after: 알고리즘과 락 수준을 단언 — 안 되면 즉시 에러로 멈춘다
ALTER TABLE orders
    ADD COLUMN coupon_code VARCHAR(32) NULL,
    ALGORITHM = INSTANT, LOCK = NONE;
-- 지원 안 되면: ERROR 1846 ALGORITHM=INSTANT is not supported. Reason: ...
-- → 사람이 "그럼 gh-ost로 가자"를 결정할 기회가 생긴다.
 
ALTER TABLE orders
    ADD INDEX idx_orders_user_created (user_id, created_at),
    ALGORITHM = INPLACE, LOCK = NONE;

LOCK 절은 NONE(DML 허용) / SHARED(읽기만) / EXCLUSIVE이고, LOCK=NONE을 단언하면 "쓰기를 막아야만 가능한 작업"일 때 역시 에러로 멈춘다. "실패하면 에러로 멈추게 한다"는 것 자체가 안전망이다 — 4장에서 이걸 CI 린트로 고정한다.

INSTANT 컬럼 추가가 거부되는 대표 조건 (한두 개만 말해도 충분)

  • ROW_FORMAT=COMPRESSED 테이블
  • FULLTEXT 인덱스가 있는 테이블
  • 한 ALTER 문에 INSTANT 불가 작업을 섞은 경우 — ALTER 한 문장은 가장 무거운 작업의 알고리즘으로 통일된다. ADD COLUMN과 MODIFY … BIGINT를 한 줄에 쓰면 컬럼 추가까지 COPY가 된다.
  • 가산점 INSTANT 컬럼 추가는 행에 "버전"을 매겨 기존 행을 안 건드리는 방식이라 테이블당 누적 횟수 상한(8.0.29 기준 64회)이 있고, 넘기면 재구성이 필요하다. "INSTANT는 공짜"가 아니라 "재구성을 미루는 빚".

규칙: 작업은 알고리즘별로 문장을 쪼갠다

INSTANT 작업과 재구성 작업을 한 ALTER에 섞지 않는다. 섞는 순간 가벼운 쪽이 무거운 쪽에 끌려 내려간다.

3도구 3종의 트레이드오프 — 네이티브 / pt-osc / gh-ost

세 선택지 각각을 "무엇을 얻고, 무엇을 지불하는가"를 한 호흡에 말하는 연습이다. 편익만 말하고 멈추면 "도구 이름을 아는 사람", 대가까지 말하면 "써 본 사람"으로 갈린다. 먼저 두 도구가 어떻게 다르게 움직이는지부터 그림으로.

3-1. 얻는 것 / 지불하는 것 — 양면 조립표

N네이티브 → 복제 지연 Ppt-osc → 트리거 부하 (+FK 처리 비용) Ggh-ost → FK 불가

셋의 공통 대가: 디스크 2배(재구성 시)와 MDL. 이 둘은 도구가 해결해 주지 않는다.

pt-osc / gh-ost 명령 예시 펼치기 (옵션 이름이 곧 "지불하는 것"의 제어 장치)
# pt-osc — 감속 임계치와 FK 처리 방식을 옵션으로 명시
pt-online-schema-change \
  --alter "ADD INDEX idx_orders_user_created (user_id, created_at)" \
  D=shop,t=orders \
  --chunk-size=1000 --max-lag=1 --check-interval=1 \
  --max-load "Threads_running=25" --critical-load "Threads_running=50" \
  --alter-foreign-keys-method=rebuild_constraints \
  --execute          # 없으면 dry-run
# gh-ost — 복제본에서 binlog를 읽고, 플래그 파일로 실행 중 제어
gh-ost \
  --host=replica-host --assume-master-host=primary-host \
  --database=shop --table=orders \
  --alter="MODIFY amount BIGINT NOT NULL" \
  --chunk-size=1000 \
  --max-lag-millis=1500 \
  --max-load="Threads_running=25" --critical-load="Threads_running=100" \
  --throttle-flag-file=/tmp/gh-ost.throttle \
  --postpone-cut-over-flag-file=/tmp/gh-ost.postpone \
  --execute
# throttle 파일을 touch 하면 즉시 일시정지, 지우면 재개.
# postpone 파일이 있는 동안은 복사가 끝나도 교체를 미룬다 → 사람이 확인 후 교체.

선택 순서 — "가벼운 것부터 배제"

① INSTANT 되면 → 네이티브→ ② INPLACE + 복제 지연 감당 가능 → 네이티브→ ③ 재구성이거나 지연 못 견딤 → 도구→ ④ FK 있으면 pt-osc / 없으면 쓰기 부하 민감할수록 gh-ost

셋의 공통 한계 — MDL은 남는다

pt-osc의 트리거 생성·RENAME, gh-ost의 cut-over, 네이티브의 시작·종료는 모두 배타 MDL을 잡는다. 그래서 두 도구는 그 순간의 락 대기 상한을 짧게 두고 실패하면 재시도하도록 내장돼 있다(pt-osc --set-vars lock_wait_timeout=… + --tries, gh-ost --cut-over-lock-timeout-seconds + 재시도). 직접 ALTER를 칠 때도 이 동작을 흉내 내야 한다 — 그게 4장의 1층이다.

4절차를 팀 규칙으로 고정하기 — 안전망 3층

1~3장의 지식은 "그날 그 사람이 기억하고 있었는가"에 의존하면 무용지물이다. 출제 의도의 후반부("스키마 변경 절차를 갖춘 팀에서 일해봤는지")는 정확히 이걸 묻는다. 규칙은 사람의 주의력이 아니라 실행 경로에 심는다 — 세션 설정, 저장소의 CI, 배포 파이프라인. 각 층이 어느 사슬의 어느 고리를 끊는지를 같이 외운다.

1층 · 실행 세션lock_wait_timeout 짧게 + 재시도ALTER가 MDL을 몇 초 안에 못 얻으면 스스로 실패. 실행 전 INNODB_TRX 확인.
끊는 고리: 사슬 A-② "1년 대기"
2층 · 저장소 / CIALGORITHM/LOCK 명시 린트마이그레이션 SQL에 ALTER가 있는데 ALGORITHM=이 없으면 빌드 실패. 문장 분리 규칙.
끊는 고리: 사슬 B "조용한 강등"
3층 · 배포 파이프라인게이트 마이그레이션 + 기동 분리대형 테이블 재구성은 런북(gh-ost)으로 먼저, Flyway에는 적용 여부 검증만. 잊으면 배포 실패.
끊는 고리: "사람이 잊음"

4-1. 1층 — lock_wait_timeout을 짧게 두고, 실패하면 재시도

사슬 A의 ②("1년 대기")를 끊는 가장 값싼 안전망이다. 실패는 아무에게도 피해를 주지 않는다 — 대기가 피해를 준다.

-- ❌ before: 기본값(1년) 그대로 실행 → 긴 트랜잭션 하나에 서비스 전체가 인질
ALTER TABLE orders ADD COLUMN coupon_code VARCHAR(32) NULL, ALGORITHM=INSTANT, LOCK=NONE;
 
-- ✅ after: 이 세션에서만 MDL 대기 상한을 5초로 → 못 얻으면 에러, 큐도 즉시 해소
SET SESSION lock_wait_timeout = 5;
ALTER TABLE orders ADD COLUMN coupon_code VARCHAR(32) NULL, ALGORITHM=INSTANT, LOCK=NONE;
-- ERROR 1205 Lock wait timeout exceeded 가 나면 → 원흉 트랜잭션을 찾거나 잠시 후 재시도
# 재시도 루프 — 운영 런북 스크립트에 고정 (사람이 F5를 누르지 않게)
for i in $(seq 1 30); do
  mysql shop -e "SET SESSION lock_wait_timeout=3;
                 ALTER TABLE orders ADD COLUMN coupon_code VARCHAR(32) NULL,
                 ALGORITHM=INSTANT, LOCK=NONE;" && break
  sleep 5
done

실행 전에 긴 트랜잭션을 확인하고, 실행 중 막히면 누가 막는지 보는 쿼리도 런북에 같이 둔다.

-- 실행 전: 60초 넘게 열려 있는 트랜잭션 (사슬 A의 ① 후보)
SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
  FROM information_schema.INNODB_TRX
 WHERE trx_started < NOW() - INTERVAL 60 SECOND;
 
-- 실행 중 막혔을 때: 누가 어떤 MDL을 쥐고 있고 누가 기다리는지
SELECT * FROM sys.schema_table_lock_waits;
SELECT object_name, lock_type, lock_status, owner_thread_id
  FROM performance_schema.metadata_locks
 WHERE object_schema = 'shop' AND object_name = 'orders';

4-2. 2층 — ALGORITHM/LOCK 명시를 강제 (리뷰 + 린트)

2-1절의 "단언"을 개인 습관이 아니라 CI가 검사하게 한다. 정규식 한 줄짜리 스크립트로 충분하고, 스키마 린터를 쓸 수 있으면 더 좋다.

beforePR 템플릿의 체크박스
"ALGORITHM 명시했는지 리뷰어가 확인" — 리뷰어가 바쁘면, 새로 온 사람이면, 금요일 저녁이면 통과한다. 체크박스는 사람이 여전히 무시할 수 있다.
afterCI 스크립트가 빌드를 깨뜨림
마이그레이션 디렉토리의 ALTER TABLE 중 ALGORITHM=이 없는 파일이 하나라도 있으면 exit 1. 사람의 상태와 무관하게 매번 같은 검사.
# ci/lint-migrations.sh — ALTER에 ALGORITHM 절이 없으면 실패
if grep -rliE '^\s*ALTER\s+TABLE' src/main/resources/db/migration \
   | xargs grep -LiE 'ALGORITHM\s*=' | grep -q .; then
  echo "ALTER TABLE without ALGORITHM= found. Declare INSTANT/INPLACE explicitly." >&2
  exit 1
fi

가산점 skeema 같은 선언형 스키마 도구는 린트 규칙에 더해, 일정 크기 이상 테이블의 ALTER를 자동으로 pt-osc/gh-ost로 감싸는 옵션(alter-wrapper, alter-wrapper-min-size)이 있다. "큰 테이블이면 도구를 쓰자"는 규칙을 도구가 대신 기억하게 만드는 사례다.

4-3. 3층 — 마이그레이션 도구(Flyway/Liquibase)와의 결합: 기동 분리 + 게이트

Spring 팀은 대개 Flyway/Liquibase로 스키마를 버전 관리하고, 기본 설정은 앱 기동 시 마이그레이션 실행이다. 여기에 대형 테이블 DDL이 섞이면 전용 함정이 생긴다.

앱 기동→Flyway가 3시간짜리 ALTER 시작→readiness 실패→롤링 배포 정지 / 오케스트레이터가 타임아웃으로 컨테이너 kill→MySQL DDL은 스크립트 롤백 불가 → 어디까지 적용됐는지 불명→Flyway 히스토리 실패 표시 → 다음 기동도 실패 → flyway repair + 수동 복구

8.0의 "원자적 DDL"은 "문장 하나가 반쯤 적용되지 않는다"는 뜻이지 "스크립트를 되돌린다"는 뜻이 아니다.

⑴ 마이그레이션을 앱 기동에서 떼어 파이프라인 단계로. 앱은 "스키마가 기대와 다르면 기동 실패"만 담당한다.

# ❌ before: application.yml — 앱이 뜨면서 마이그레이션까지 실행 (기본값)
spring.flyway.enabled: true
spring.jpa.hibernate.ddl-auto: update
 
# ✅ after: 앱은 검증만, 마이그레이션은 CI/CD의 별도 잡
spring.flyway.enabled: false
spring.jpa.hibernate.ddl-auto: validate      # 선언과 실물이 다르면 기동 실패
 
# 파이프라인(배포 직전 잡)에서 실행하는 Flyway에는 1층의 타임아웃을 심는다
flyway -url=jdbc:mysql://... -initSql="SET SESSION lock_wait_timeout=5" migrate
# 또는 각 SQL 파일 첫 줄에:  SET SESSION lock_wait_timeout = 5;

⑵ 대형 테이블 목록을 저장소에 두고, 그 테이블의 재구성 DDL은 Flyway SQL로 금지. 대신 gh-ost/pt-osc 런북으로 배포와 분리해 먼저 실행한다. Flyway 쪽에는 SQL 대신 "이미 적용됐는지 검증만 하는 게이트 마이그레이션"을 둔다 — 사람이 gh-ost를 잊었으면 배포가 실패하게.

// ❌ before: V43__orders_amount_bigint.sql
//    ALTER TABLE orders MODIFY amount BIGINT NOT NULL;
//    → COPY 알고리즘, 앱 기동 중 수 시간 쓰기 차단, 실패 시 반쯤 적용
 
// ✅ after: V43__gate_orders_amount_bigint.java — 실물을 확인만 한다
public class V43__gate_orders_amount_bigint extends BaseJavaMigration {
    @Override
    public void migrate(Context ctx) throws Exception {
        try (var st = ctx.getConnection().createStatement();
             var rs = st.executeQuery("""
                 SELECT DATA_TYPE FROM information_schema.COLUMNS
                  WHERE TABLE_SCHEMA = DATABASE()
                    AND TABLE_NAME = 'orders' AND COLUMN_NAME = 'amount'""")) {
            rs.next();
            if (!"bigint".equalsIgnoreCase(rs.getString(1))) {
                // gh-ost 런북(docs/runbook/orders-amount-bigint.md)을 먼저 실행해야 한다
                throw new IllegalStateException(
                    "orders.amount is not BIGINT yet — run gh-ost migration before deploying V43");
            }
        }
    }
}

Liquibase라면 같은 의도를 선언으로 쓴다 — 전제조건이 충족돼 있으면 통과, 아니면 HALT.

<changeSet id="43-orders-amount-bigint-gate" author="team">
  <preConditions onFail="HALT">
    <sqlCheck expectedResult="bigint">
      SELECT DATA_TYPE FROM information_schema.COLUMNS
       WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME='orders' AND COLUMN_NAME='amount'
    </sqlCheck>
  </preConditions>
  <comment>out-of-band gh-ost 적용 여부 검증 — 미적용 시 배포 중단</comment>
</changeSet>

⑶ 작은 DDL은 Flyway SQL로 두되 알고리즘 단언 + 문장 분리. INSTANT 컬럼 추가처럼 안전한 것까지 런북으로 보내면 절차가 무거워져 지켜지지 않는다.

두 문장으로 외우는 4장의 철학

  • "실패는 피해를 주지 않는다 — 대기가 피해를 준다." 타임아웃·린트·게이트는 전부 "빨리 실패하게 만드는 장치"다.
  • "규칙은 지킬 수 있을 만큼만 무겁게." 코드·설정으로 고정할 수 있는 것은 체크리스트에 두지 않는다 — 체크박스는 사람이 무시할 수 있다.

4-4. Expand / Contract — 앱 배포 무중단과 맞물리는 지점

스키마를 무중단으로 바꿔도, 롤링 배포 중에는 구버전과 신버전 앱이 같은 DB를 동시에 본다. 컬럼을 지우거나 이름을 바꾸는 순간 구버전 앱이 죽고, ddl-auto=validate를 켜 뒀다면 구버전 인스턴스가 재기동조차 못 한다. 그래서 파괴적 변경은 한 릴리스에서 금지하고 두 단계로 나눈다.

Expand: 새 컬럼 추가만(INSTANT)→ 신버전 앱 배포: 양쪽에 쓰고 새 쪽을 읽음→ 백필: 청크 UPDATE, 저트래픽 시간대→ 구버전 앱이 한 대도 없음을 확인→ Contract: 다음 릴리스에서 옛 컬럼 삭제

순서를 한 줄로: 호환되는 스키마 먼저 → 앱 배포(프로세스 교체의 무중단은 02장 graceful shutdown) → 정리 DDL은 다음 릴리스. 컬럼 이름 변경도 "새 컬럼 추가 → 양쪽 쓰기 → 읽기 전환 → 옛 컬럼 삭제" 네 단계로 푼다. SELECT *와 위치 기반 매핑을 금지하는 코딩 규칙도 이 축의 일부다(컬럼 추가만으로 깨지지 않게).

4-5. PR 템플릿 체크리스트 — 사람이 판단해야 하는 것만 남긴다

위 규칙들이 기계가 잡는 부분이고, 나머지는 리뷰어가 같은 질문을 매번 같은 순서로 던지게 템플릿에 박는다.

5사고 사례 — "INSTANT니까 괜찮다"며 점심시간에 친 ALTER

상황: orders(수억 건)에 coupon_code 컬럼을 추가하는 PR이 승인됐다. 리뷰어는 "MySQL 8이고 INSTANT라 1ms면 끝난다"고 했고, 담당자는 점심시간에 운영 DB에 ALTER TABLE orders ADD COLUMN coupon_code VARCHAR(32) NULL;을 실행했다. 12분 뒤 전 API가 타임아웃으로 죽었다.

1-1절의 타임라인이 그대로 재현된 것이다. 정산팀 대시보드가 매 시 정각에 리포팅 트랜잭션을 열어 orders를 15분간 읽고 있었다(①). ALTER는 배타 MDL을 못 얻고 대기, 상한은 1년(②). 그 뒤로 orders를 읽는 모든 API 요청이 큐(③), HikariCP 풀 10개가 30초 안에 바닥나 로그인·상품 조회까지 실패(④), 헬스체크 실패로 인스턴스 재시작 반복(⑤). 담당자는 SHOW PROCESSLIST에서 Waiting for table metadata lock을 보고 ALTER 세션을 KILL했고, 큐는 즉시 풀렸다. ALTER 자체는 나중에 리포팅 트랜잭션이 끝난 직후 재실행해 정확히 수 ms에 끝났다.

6꼬리질문 셀프 테스트 — 먼저 소리 내어 답하고 펼친다

"MySQL 8이면 컬럼 추가는 INSTANT라 그냥 쳐도 되는 것 아닌가요?"

두 가지로 나눠 답한다. 첫째, INSTANT여도 배타 MDL은 잡는다. 긴 트랜잭션이 공유 MDL을 쥐고 있으면 1ms짜리 ALTER가 그 뒤에서 대기하고, 그 뒤로 들어오는 모든 쿼리가 큐에 서며, 커넥션 풀이 고갈돼 무관한 API까지 죽는다 — 알고리즘이 아니라 락 큐의 문제다. 그래서 INSTANT여도 lock_wait_timeout을 짧게 두고 재시도하는 절차를 밟는다. 둘째, INSTANT가 된다는 보장을 확인해야 한다. ALGORITHM=INSTANT, LOCK=NONE을 단언해서 조건이 안 맞으면(COMPRESSED, FULLTEXT, 다른 재구성 작업과 혼합, 누적 횟수 초과) 조용히 재구성으로 강등되지 않고 에러로 멈추게 한다. "그냥 쳐도 된다"는 이 두 확인을 생략한 말이다.

"인덱스 추가는 INPLACE라 DML도 허용되는데, 그런데도 도구를 쓰는 이유가 뭔가요?"

프라이머리에서는 온라인이어도 복제본에서는 아니기 때문이다. ALTER 문장이 binlog로 전파되면 복제본은 같은 ALTER를 처음부터 재실행하고, DDL은 병렬 적용의 장벽이라 그 시간 동안 뒤의 트랜잭션이 전부 대기한다 → 복제 지연이 ALTER 소요 시간만큼 벌어진다. 읽기를 복제본으로 보내는 구조라면 그건 곧 "방금 쓴 데이터가 안 보이는" 장애다. 여기에 ⑵ 실행 중 속도 조절·중단이 불가능하다는 것, ⑶ 온라인 로그 초과로 말미에 실패할 수 있다는 것이 붙는다. pt-osc/gh-ost는 큰 ALTER를 청크 DML로 바꿔 복제본이 따라오게 하고 지연이 임계치를 넘으면 감속한다. 반대로 복제본이 없거나 지연을 감내할 수 있는 환경이면 네이티브 INPLACE가 가장 단순하고 옳다 — 도구는 공짜가 아니다.

"pt-osc와 gh-ost 중 무엇을 고르나요? 각각 무엇을 포기하나요?" 시니어 변별

첫 분기는 FK다 — 대상 테이블이 FK의 부모든 자식이든 gh-ost는 불가하므로 pt-osc밖에 없고, 그때는 rebuild_constraints(자식 재구성 비용)와 drop_swap(테이블 부재 창) 중 하나를 감수한다. FK가 없다면 두 번째 분기는 쓰기 부하 민감도다 — pt-osc는 트리거가 원본의 모든 쓰기에 동기적으로 끼어들어 쓰기 지연과 락 범위를 늘리므로, 쓰기가 몰리는 테이블일수록 gh-ost가 낫다. gh-ost가 지불하는 것은 ROW binlog 전제, 기존 트리거 불가, binlog 순차 적용 탓에 쓰기 폭주 시 총 시간이 더 길 수 있다는 점이다. 대신 실행 중 일시정지·교체 연기·복제본 리허설이라는 운영 통제력을 얻는다. 어느 쪽이든 디스크 2배와 cut-over 순간의 MDL은 공통이므로 도구로 해결되지 않는다고 덧붙이면 완결된다. 결정을 "우리 팀은 항상 X"가 아니라 이 두 분기로 말하는 것이 핵심이다.

"Flyway를 쓰는데, 대형 테이블 DDL은 실제로 어떻게 흘러가나요?"

세 겹으로 답한다. ⑴ 마이그레이션 실행을 앱 기동에서 떼어 파이프라인 단계로 옮긴다 — 기동 중 긴 DDL은 readiness 실패·롤링 배포 정지·타임아웃 재시작을 부르고, MySQL DDL은 스크립트 단위 롤백이 안 되어 반쯤 적용된 상태를 남기기 때문이다. 앱은 ddl-auto=validate로 검증만 한다. ⑵ 대형 테이블의 재구성 DDL은 Flyway SQL로 쓰지 않고 gh-ost/pt-osc 런북으로 배포 전에 별도 실행하며, Flyway에는 information_schema로 적용 여부를 확인만 하는 게이트 마이그레이션(Java 마이그레이션 또는 Liquibase preConditions)을 둬서 잊으면 배포가 실패하게 한다. ⑶ 나머지 작은 DDL은 Flyway SQL로 두되 ALGORITHM/LOCK 단언, 알고리즘별 문장 분리, initSql로 lock_wait_timeout을 심는다. "사람이 gh-ost를 잊으면 어떻게 되나요"에 "배포가 실패합니다"라고 답할 수 있어야 절차가 있는 팀이다.

"PostgreSQL이면 같은 문제인가요?" 가산점

락 큐의 원리는 같다 — ALTER는 ACCESS EXCLUSIVE 락을 잡고, 긴 트랜잭션 뒤에서 대기하면 뒤따르는 쿼리가 모두 막히므로 lock_timeout을 짧게 두고 재시도하는 절차는 그대로 필요하다. 다른 점은 도구 지형이다. PostgreSQL은 DDL이 트랜잭션 안에서 롤백되므로 마이그레이션 실패 복구가 쉽고, ADD COLUMN … DEFAULT는 상수 기본값이면 카탈로그에만 기록해 즉시 끝나며(11+), 인덱스는 CREATE INDEX CONCURRENTLY로 쓰기를 막지 않고 만든다 — 단 이건 트랜잭션 안에서 못 쓰고 실패하면 INVALID 인덱스가 남아 지워야 한다. 제약 추가는 NOT VALID로 걸고 나중에 VALIDATE CONSTRAINT로 나눠 긴 락을 피한다. 즉 "MySQL의 pt-osc/gh-ost 자리"를 PostgreSQL에서는 DB 내장 기능 + lock_timeout 재시도가 상당 부분 대신한다. 엔진마다 답이 다르다는 걸 알고 "우리 DB는 무엇인가"부터 확인하는 것이 시니어의 순서다.

"innodb_lock_wait_timeout을 5초로 줄여 뒀는데 왜 ALTER는 몇 분씩 기다리나요?" 추가

그 변수는 행 락의 대기 상한이다. ALTER가 기다리는 것은 메타데이터 락이고, 그 상한은 별개 변수 lock_wait_timeout(기본 1년)이다. 이름이 비슷해서 "타임아웃은 이미 짧게 해 뒀다"고 착각하기 쉽다. SHOW PROCESSLIST의 상태가 Waiting for table metadata lock이면 MDL이고, 행 락이면 Lock wait timeout exceeded가 50초(기본) 뒤에 난다. 둘을 구분해서 말하면 사슬 A를 실제로 겪어 본 사람으로 보인다.

"ALTER가 멈춰 있을 때 무엇을 KILL 하나요? 왜 ALTER를 죽이면 큐가 즉시 풀리나요?" 추가

사슬의 ①(원흉 트랜잭션) 또는 ②(ALTER 세션) 중 하나를 끊는다. ALTER를 죽이면 대기 중인 배타 요청이 큐에서 사라지므로, 그 뒤에 줄 서 있던 공유 요청들이 더는 막힐 이유가 없어 즉시 진행된다 — 뒤따르는 쿼리들이 멈춘 이유는 "배타 요청을 추월하지 못한다"는 규칙 때문이지 자원이 부족해서가 아니었다. ALTER는 아직 시작도 못 했으니 죽여도 데이터 손상이 없고, 나중에 다시 실행하면 된다. 원흉 트랜잭션을 죽이는 것도 가능하지만 그것이 무엇인지(결제 배치일 수도) 모른 채 죽이는 것은 위험하므로, 즉각 복구는 ALTER 쪽을 죽이는 편이 안전하다. 누가 쥐고 있는지는 sys.schema_table_lock_waits로 본다.

"공유 MDL은 왜 문장이 끝날 때가 아니라 트랜잭션이 끝날 때 풀리나요?" 추가

트랜잭션 도중에 테이블 정의가 바뀌면 같은 트랜잭션의 앞 문장과 뒤 문장이 다른 테이블 구조를 보게 되어 트랜잭션의 일관성이 깨지고, 바이너리 로그에 기록되는 순서(트랜잭션 커밋 ↔ DDL)도 실제 실행과 어긋나 복제본이 다른 결과를 낼 수 있다. 그래서 MySQL은 트랜잭션이 끝날 때까지 공유 MDL을 유지해 DDL이 끼어들지 못하게 한다. 이 설계 때문에 "SELECT 한 번 하고 커밋 안 한 세션"이 ALTER를 막는 것이고, 그래서 긴 트랜잭션 자체가 스키마 변경의 적이다(Q9 긴 트랜잭션의 해악과 연결).

"한 ALTER 문에 ADD COLUMN과 MODIFY … BIGINT를 같이 쓰면 어떻게 되나요?" 추가

ALTER 한 문장은 가장 무거운 작업의 알고리즘으로 통일된다. 컬럼 추가 혼자면 INSTANT지만, 타입 변경(COPY)과 섞이는 순간 문장 전체가 COPY가 되어 컬럼 추가까지 전 행 복사 + 쓰기 차단을 치른다. 그래서 규칙은 "알고리즘별로 문장을 쪼개라"이고, ALGORITHM=INSTANT를 단언해 두면 이 혼합이 ERROR 1846으로 잡혀서 실수를 실행 전에 발견한다.

"INPLACE-재구성 중에 온라인 로그가 넘치면 어떻게 되나요? 그럼 뭘 조정하나요?" 추가

재구성 동안 들어온 DML은 innodb_online_alter_log_max_size(기본 128MB)의 온라인 로그에 쌓였다가 끝에 반영되는데, 쓰기가 많아 로그가 한도를 넘으면 수 시간 걸린 작업이 마지막에 실패하고 그때까지의 시간·I/O는 날아간다. 대응은 ⑴ 한도를 키우거나 ⑵ 저트래픽 시간대로 옮기거나 ⑶ 애초에 이런 규모의 재구성은 네이티브 대신 pt-osc/gh-ost로 청크 처리하는 것이다. "네이티브 online DDL의 대가" 목록에 이 항목이 들어가 있어야 한다.

"게이트 마이그레이션이 실패하면 배포는 어떻게 되나요? 그게 좋은 건가요?" 추가

파이프라인의 flyway migrate 단계가 예외로 끝나므로 배포가 중단되고, 앱은 새 버전으로 교체되지 않는다. 이것이 의도된 동작이다 — 대안은 "gh-ost를 안 한 채로 새 앱이 떠서 BIGINT를 기대하는 코드가 INT 컬럼에 오버플로를 내는 것" 또는 "Flyway가 직접 COPY ALTER를 시작해 사슬 B를 여는 것"이다. 사람은 gh-ost 런북을 실행한 뒤 파이프라인을 재시도하면 되고, 게이트는 이미 적용된 상태를 보고 통과한다. "실패는 피해를 주지 않는다 — 대기(와 반쯤 적용)가 피해를 준다"의 배포판이다.

"gh-ost 실행 중에 트래픽이 갑자기 튀면 무엇을 하나요?" 추가

--throttle-flag-file로 지정한 파일을 touch하면 gh-ost가 즉시 일시정지하고, 지우면 재개한다. 복사가 끝나갈 때 교체(cut-over)를 사람이 확인한 뒤 하고 싶으면 --postpone-cut-over-flag-file을 미리 두어 파일이 있는 동안 교체를 미룬다. 이것이 pt-osc(감속만 가능, 일시정지 없음)와 갈리는 "운영 통제력"이고, 네이티브 ALTER(죽이기만 가능)와는 더 크게 갈린다.

71분 인출 테스트 — 면접 전날 이것만

사슬 A 5단계를 역할 이름을 붙여 순서대로 말해보라.

보유자 긴 트랜잭션이 공유 MDL 점유 → 대기자 ALTER가 배타 MDL 대기(상한 1년) → 줄 뒤따르는 모든 쿼리가 큐(추월 불가) → 병목 자원 커넥션 풀 고갈(10개, 30초) → 증폭 무관한 API까지 전면 장애, 재시작해도 큐는 그대로. → 1-1

INSTANT여도 사슬 A가 발생하는 이유를 한 문장으로.

INSTANT는 "실행이 수 ms"라는 뜻이지 "MDL을 안 잡는다"는 뜻이 아니다 — 1ms짜리 ALTER가 긴 트랜잭션 뒤에서 10분을 대기하면 그 10분 동안 서비스는 죽어 있다.

알고리즘 3종 ↔ 대표 작업 압축 문장은? 갈리는 원리 하나는?

"추가는 INSTANT, 인덱스는 INPLACE, 타입은 COPY." 원리: 이 작업이 클러스터드 인덱스 안의 행 레이아웃을 건드리는가 — 딕셔너리만이면 INSTANT, 별도 구조만 지으면 INPLACE, 전 행을 다시 쓰면 재구성(INPLACE-재구성 / COPY). → 2절

도구 셋이 지불하는 대가를 한 단어씩. 셋의 공통 한계 둘은?

네이티브 복제 지연 / pt-osc 트리거 부하(+FK 처리 비용) / gh-ost FK 불가. 공통: 디스크 2배와 MDL. → 3-1

선택 순서 4단계는?

① INSTANT 되면 네이티브 → ② INPLACE + 복제 지연 감당되면 네이티브 → ③ 재구성이거나 지연 못 견디면 도구 → ④ FK 있으면 pt-osc, 없으면 쓰기 부하 민감할수록 gh-ost. → 3-2

안전망 3층과 각 층이 끊는 고리는?

1층 실행 세션: lock_wait_timeout=5 + 재시도 + 실행 전 INNODB_TRX → 사슬 A-② "1년 대기". 2층 CI: ALGORITHM= 없는 ALTER는 빌드 실패 → 사슬 B "조용한 강등". 3층 배포: 마이그레이션 기동 분리(flyway.enabled=false, ddl-auto=validate) + 게이트 마이그레이션 → "사람이 잊음". → 4절

"사람이 gh-ost를 잊으면 어떻게 되나요?"에 한 마디로.

"배포가 실패합니다." — 게이트 마이그레이션이 information_schema로 실물을 확인하고 아니면 예외를 던진다.

숫자 6개 — 값과 의미.

lock_wait_timeout 1년(MDL 대기 상한) / innodb_lock_wait_timeout 50초(행 락, 다른 변수) / HikariCP 풀 10 / connection-timeout 30초 / 온라인 로그 innodb_online_alter_log_max_size 128MB(넘치면 말미 실패) / INSTANT 컬럼 추가 누적 상한 64회(8.0.29 기준, "재구성을 미루는 빚").

Expand/Contract를 한 줄로.

호환되는 스키마 먼저(추가만, INSTANT) → 앱 배포(양쪽 쓰기, 새 쪽 읽기) → 구버전이 한 대도 없음을 확인한 뒤 다음 릴리스에서 정리 DDL. 파괴적 변경은 한 릴리스에서 금지. → 4-4

한 줄 요약

대용량 테이블의 ALTER는 알고리즘과 무관한 메타데이터 락 큐(긴 트랜잭션 → ALTER 대기 → 뒤따르는 모든 쿼리 대기 → 커넥션 풀 고갈 → 전면 장애)와, 재구성 알고리즘의 자원 비용(쓰기 차단·디스크 2배·복제 지연)이라는 두 사슬로 서비스를 세운다. 그래서 MySQL 8 알고리즘 3종을 판별해 컬럼 추가는 INSTANT, 인덱스 추가는 INPLACE로 단언하고, 재구성이 불가피하면 복제 지연(네이티브) / 트리거 부하·FK 처리(pt-osc) / FK 미지원(gh-ost)이라는 대가를 비교해 고르며, lock_wait_timeout 단축 · 알고리즘 단언 린트 · 마이그레이션의 배포 분리와 게이트 · Expand/Contract를 사람의 기억이 아니라 팀의 실행 경로에 고정한다.
