복합 인덱스 컬럼 순서
"카디널리티 높은 컬럼 먼저"는 1순위 규칙이 아니라 3순위 기준이다

면접 질문: "복합 인덱스의 컬럼 순서는 어떤 기준으로 정하나요? 카디널리티와의 관계는?"

핵심 관전 포인트 — 복합 인덱스 (A, B, C)는 "A로 정렬하고, A가 같은 것끼리만 B로, B까지 같은 것끼리만 C로" 정렬된 하나의 트리다. 그래서 컬럼 순서는 "플래너가 리프에서 얼마나 좁은 연속 구간 하나를 찍을 수 있는가"를 결정한다. 순서 결정 원칙은 셋 — ① 등호(=) 조건 컬럼을 앞에, 범위 조건(>, <, BETWEEN, LIKE 'x%')은 맨 뒤에 (범위 뒤 컬럼은 정렬이 깨져 탐색 조건으로 못 쓴다) ② 등호 컬럼끼리는 "더 많은 쿼리가 접두사로 재사용하는 컬럼"을 앞에, 그 다음에야 카디널리티 높은 쪽을 앞에 ③ 범위·정렬 컬럼 뒤에는 커버링용 컬럼. 카디널리티는 ②의 타이브레이커일 뿐이고, "이 인덱스를 탈지 말지"는 개별 컬럼이 아니라 컬럼 조합의 선택도(랜덤 vs 순차 I/O 손익분기)가 정한다. 순서가 틀리면 뒤 컬럼 조건이 구간을 못 좁혀 인덱스 스캔 폭이 자릿수로 커지는데 — PostgreSQL 계획에는 강등된 조건도 멀쩡히 Index Cond로 찍혀서 겉으로는 구분이 안 된다. 판별 도구는 계획 텍스트가 아니라 EXPLAIN (ANALYZE, BUFFERS)의 읽은 페이지 수다.
  • 1
    복합 인덱스는 "사전 안의 사전"이라, 규칙은 한 줄에서 다 나온다 — (A, B, C)는 A로 정렬하고 A가 같은 구간 안에서만 B로, A·B가 둘 다 같은 구간 안에서만 C로 정렬된 트리다. 그래서 "앞 컬럼 값이 하나로 고정돼야 그 안에서 뒤 컬럼의 정렬이 살아 있다" — 컬럼 순서 설계란 결국 가장 좁은 연속 구간 하나를 만드는 일이다.
  • 2
    그 한 줄에서 순서 원칙 셋이 유도된다 — 등호 먼저(값을 하나로 못 박아 뒤 컬럼 정렬을 살린다), 범위는 맨 뒤에 하나(값을 여러 개로 열어 놓아 그 뒤는 정렬이 깨진다), 그 뒤에 정렬·커버링. 등호 컬럼끼리는 접두사 재사용(= 이 인덱스를 몇 개의 쿼리가 탈 수 있나)이 먼저고, 카디널리티는 우열이 안 갈릴 때 쓰는 3순위 타이브레이커다.
  • 3
    순서가 틀리면 조건이 "강등"되는데, PostgreSQL 계획 텍스트로는 안 보인다 — 뒤 컬럼 조건이 액세스 조건 → 인덱스 내 검사로 강등되면 스캔 폭이 자릿수로 커지지만, 계획에는 둘 다 똑같이 Index Cond로 찍힌다. 그래서 판별은 EXPLAIN (ANALYZE, BUFFERS)의 읽은 블록 수로 하고, 규칙은 인덱스 이름·계획 단정 테스트·카탈로그 조회·auto_explain에 박아 둔다.

0. 질문 + 출제 의도

질문: "복합 인덱스의 컬럼 순서는 어떤 기준으로 정하나요? 카디널리티와의 관계는?"

관련 질문: "커버링 인덱스란? 어떤 상황에서 효과가 큰가요?" · "ORDER BY가 인덱스를 타는 조건은? 정렬(Sort)은 언제 발생하고 왜 문제가 되나요?"

출제 의도: 인덱스를 "거는" 것과 "설계하는" 것의 차이가 여기서 갈린다. 등호 먼저·범위 뒤 같은 원칙을 쿼리 패턴에서 도출할 수 있어야, 테이블당 인덱스 수를 늘리지 않으면서 여러 쿼리를 커버하는 설계가 가능하다. 즉 "카디널리티 높은 컬럼을 앞에"라는 격언을 외웠는지가 아니라, 쿼리 조건을 등호/범위/정렬로 분류해 순서를 스스로 조립하고, 그 순서가 I/O 비용으로 어떻게 번지는지를 말할 수 있는지를 본다.

Q1 B+Tree — 구조를 아는가→ Q2 풀스캔 6종 — 구조로 현상을 설명하는가→ Q8 이 문서 — 구조로 설계하는가
이 페이지가 겨냥하는 약점 세 가지 ① 격언만 외우고 근거를 못 대는 것 → 1~3절에서 리프를 행 목록으로 펼쳐, 순서 규칙을 "앞 컬럼이 고정돼야 뒤 컬럼 정렬이 산다" 한 줄에서 직접 유도한다.
② 카디널리티를 1순위로 쓰는 것 → 7·8절에서 등호끼리는 순서를 바꿔도 최종 구간이 같다는 반례로, 카디널리티를 3순위 타이브레이커 자리로 내린다.
③ "순서 틀리면 느려진다"를 숫자로 못 말하는 것 → 6절에서 인덱스 페이지 1,200 대 12와 총 버퍼 4,203 대 3,015를 갈라, "100배"가 어디에 붙는 100배인지를 정확히 말하게 만든다.

1. 리프를 펼쳐 본다 — 복합 인덱스는 "사전 안의 사전"이다

1-1. 전제 — 인덱스가 빠른 이유는 오직 "정렬돼 있다" 하나다

먼저 한 문장을 고정하고 간다. 인덱스란 인덱스 컬럼의 값과 그 행의 힙 주소(TID)를 함께 담아, 그 값 기준으로 정렬해 둔 별도의 사본이다. TID는 "몇 번 블록의 몇 번째 슬롯"이라는 6바이트 주소이고, 시스템 컬럼 ctid로 눈으로 볼 수 있다.

여기서 중요한 것은 "정렬돼 있다"가 빠름의 유일한 근거라는 점이다. 정렬돼 있으니 B-tree를 타고 내려가 찾는 값의 시작점을 한 번에 찍을 수 있고, 리프 페이지들이 형제 링크로 이어져 있으니 끝점까지 옆으로 이어 읽으면 끝난다. 정렬 순서를 벗어난 조건은 시작점을 못 찍는다. 이 문서의 모든 결론이 이 한 줄에서 나온다.

스캔 폭이 곧 비용이다 → 컬럼 순서 설계란 "가장 좁은 연속 구간 하나를 어떻게 만들 것인가"를 정하는 일

1-2. 비유 둘 — 전화번호부, 그리고 도서관 서가

전화번호부 — 순서 원칙 전부가 여기서 나온다

(A, B, C)는 성으로 정렬하고, 성이 같은 사람들 안에서만 이름으로 정렬하고, 성과 이름이 같은 사람들 안에서만 중간 이름으로 정렬한다.

책 전체가 이름순은 아니다 — 그래서 "이름이 철수인 사람"을 찾으려면 책을 처음부터 끝까지 넘겨야 한다.

도서관 서가 — 범위 조건이 왜 뒤 컬럼을 죽이는가

책을 출판연도로 먼저 꽂고, 같은 연도 칸 안에서만 저자 이름순으로 꽂았다고 하자. "2020년 책"을 찾는 것은 한 칸이니 그 안에서 저자를 이진 탐색할 수 있다.

그런데 "2020년 이후"(범위)로 열면 칸이 여러 개가 되고, 저자 이름은 칸마다 다시 ㄱ부터 시작한다. 열린 칸 전부를 훑으며 저자를 하나씩 확인하는 수밖에 없다.

1-3. 실제 리프를 행 목록으로 — orders (user_id, status, created_at)

비유는 여기까지 하고, 리프가 실제로 어떻게 늘어서는지를 행 목록으로 본다. 이 목록 하나만 머릿속에 있으면 이 문서의 모든 규칙을 그 자리에서 유도할 수 있다.

이 문서에서 계속 쓸 용어 셋 — 조건이 하는 일에 따라 이름이 다르다

액세스 조건 (access predicate)
인덱스 트리를 내려가 시작점·끝점을 찍는 데 쓰인 조건. 스캔 폭을 실제로 줄인다.
인덱스 내 검사 (in-index filter)
구간은 못 좁히지만 훑는 인덱스 엔트리 단계에서 하나씩 검사해 걸러낸다. 힙 방문은 막아 주지만 스캔 폭은 못 줄인다.
필터 조건 (Filter:)
인덱스에 아예 없는 컬럼의 조건. 힙에서 행을 가져온 뒤 검사해 버린다 — 버릴 행에 랜덤 I/O를 이미 지불했다. Rows Removed by Filter가 그 계산서.

여기서 미리 못 박는 함정 — PostgreSQL 계획은 앞의 둘을 구분해서 보여주지 않는다

인덱스 컬럼에 대한 조건이면 시작점을 찍었든 못 찍었든 전부 Index Cond:에 나란히 찍힌다. 그래서 "계획에 Index Cond로 잘 나오는데요?"는 순서가 맞다는 증거가 아니다. (MySQL이 ICP라고 따로 이름 붙인 동작이 PostgreSQL에는 기본 내장이라 이름표가 없다.)

판별은 계획 텍스트가 아니라 EXPLAIN (ANALYZE, BUFFERS)의 읽은 페이지 수로 한다

2. 밑줄 긋기 — 되는 조건과 안 되는 조건

1절의 목록 위에 조건을 하나씩 대 보면 규칙이 눈으로 보인다. 외울 것은 없고, 밑줄이 하나로 이어지는지만 보면 된다.

2-1. 중간이 비어도 똑같이 걸린다 — 가운데 컬럼 건너뛰기

같은 규칙이 "선두는 있는데 가운데가 없는" 경우에도 그대로 걸린다. WHERE user_id = 7 AND created_at >= '08-03'처럼 가운데 status를 건너뛰면 어떻게 되는지 보자.

user 7 구간(1~7행)에서 created_at 칸만 세로로 읽으면

08-01, 08-04, 08-02, 08-05, 08-01, 08-03, 08-06
        ↑ 내려갔다        ↑ 또 내려갔다
오름차순이 아니다.

status라는 칸막이가 시간축을 세 토막(DONE 칸·FAILED 칸·PAID 칸)으로 잘라 각각 따로 정렬했기 때문이다.

그래서 플래너가 할 수 있는 일

  • user_id = 7로 구간(1~7행)은 찍는다 — 선두 조건은 살아 있으므로
  • created_at으로는 그 안의 시작점을 못 찍는다
  • → user 7 구간 7개를 전부 훑으며 하나씩 검사해 조건에 맞는 것만 남긴다

"인덱스를 타긴 탔지만, 뒤 조건은 구간을 못 좁혔다" — 이 상태가 뒤에서 말할 강등이다.

3. 범위 뒤는 왜 죽는가 — 같은 데이터, 순서만 뒤집어서

여기가 "등호 먼저, 범위 뒤"의 진짜 이유다. 새 규칙을 외울 필요는 없다 — 2절의 한 줄을 그대로 적용하면 나온다. 범위 조건은 앞 컬럼 값을 하나로 고정하지 못하고 여러 값에 걸쳐 열어 놓기 때문에, 그 안에서 뒤 컬럼의 정렬이 살아 있지 않다.

범위 컬럼이 "하나뿐"인 이유 — 외우지 말고 유도한다

등호 = 값을 하나로 못 박는다→그 안에서 뒤 컬럼 정렬이 산다→등호는 몇 개든 앞에 이어 붙일 수 있다
범위 = 값을 여러 개로 열어 놓는다→그 뒤는 정렬이 따로 논다→범위는 구간을 좁히는 마지막 컬럼 = 하나뿐

4. 접두사 — 인덱스 1개는 사실상 "인덱스 N개"다

접두사(prefix) = 인덱스 컬럼 목록의 왼쪽부터 끊기지 않고 이어지는 조각. 2절에서 본 대로 왼쪽이 빠지거나 중간이 끊기면 시작점을 못 찍기 때문에, 의미가 있는 형태는 이것뿐이다.

접두사 재사용 vs 카디널리티 — 관계 한 줄

접두사 재사용 = 커버 범위
"이 인덱스를 몇 개의 쿼리가 탈 수 있나"를 정한다. → 2순위
카디널리티 = 효율
"그 접두사로 탔을 때 얼마나 좁혀지나"를 정한다. → 3순위 타이브레이커
커버 범위가 먼저고, 둘 다 탈 수 있어 우열이 안 갈릴 때 효율로 타이브레이크한다
PostgreSQL 각주 — "못 탄다"가 아니라 "타 봐야 손해" PG의 복합 B-tree는 선두 컬럼 조건이 없어도 "인덱스 전체를 훑는 식으로" 쓸 수는 있다. 하지만 구간을 못 좁히므로 플래너가 대개 Seq Scan을 고른다 — 결론은 같다. 또 PostgreSQL 18부터는 선두 컬럼 고유값이 아주 적을 때 값마다 뒤 컬럼 구간을 따로 탐색하는 skip scan이 생겼는데(MySQL은 8.0부터), 예외의 조건이 좁아 설계 원칙을 대체하지 않는다(8절).

5. 순서 결정 — "등 · 범 · 정 · 커"와 설계 절차

조건을 바구니로 나눈 뒤 순서대로 배치한다. 암기용 네 글자는 등호 → 범위 → 정렬 → 커버링인데, 외우기 전에 각 글자가 왜 그 자리인지를 2·3절의 규칙에서 직접 뽑아 본다.

순서 4자리 — 등 · 범 · 정 · 커

등호 = IS NULL IN→ 범위 > BETWEEN LIKE 'x%' — 하나만→ 정렬 ORDER BY — 범위와 같은 자리→ 커버링 INCLUDE

앞의 둘은 구간을 좁히는 자리, 뒤의 둘은 구간을 좁힌 뒤 일을 덜어주는 자리다. 이 이분법으로 기억하면 순서가 헷갈리지 않는다.

각 자리의 근거 — "앞 컬럼 값이 하나로 고정돼야 뒤 컬럼 정렬이 살아 있다"에서 전부 유도된다
자리무엇이 오나그 자리인 이유 (규칙에서 유도)
등호=, IS NULL, IN 조건 컬럼등호는 앞 컬럼 값을 하나로 못 박는다. 못 박힌 안쪽에서는 뒤 컬럼 정렬이 살아 있으므로 뒤 컬럼도 시작점을 찍을 수 있다 → 몇 개든 앞에 이어 붙일 수 있다
범위>, BETWEEN, LIKE 'x%' 조건 컬럼 — 하나만범위는 앞 컬럼 값을 여러 개로 열어 놓는다. 열린 순간 뒤 컬럼 정렬은 값마다 따로 놀아 시작점을 못 찍는다(3절) → 범위 컬럼은 구간을 좁히는 마지막 컬럼이고, 그런 컬럼은 정의상 하나뿐
정렬ORDER BY 컬럼인덱스 정렬 순서가 곧 ORDER BY 순서면 Sort 노드가 사라진다. 그러려면 등호 컬럼 바로 뒤여야 하는데 — 그 자리는 범위와 겹친다
커버링SELECT 목록에만 등장하는 컬럼탐색에 아무 기여도 못 한다(구간도 못 좁히고 정렬도 못 만든다). 순수하게 값을 실어 나르는 용도이므로 맨 뒤 — PostgreSQL은 이 자리를 INCLUDE 절로 따로 선언하게 해 준다

5-1. 범위 vs 정렬 — 자리를 누구에게 줄 것인가

경쟁이 없는 경우 — 범위 컬럼 = 정렬 컬럼

created_at >= ? ORDER BY created_at DESC가 그 경우다. 한 컬럼이 구간도 좁히고 정렬도 만든다.

실무에서 가장 흔하고 가장 좋은 모양 — 목록 API 대부분이 여기 해당한다.

다르면 하나를 골라야 한다 — 대가를 알고 고른다

  • 정렬을 앞에 → Sort는 사라지지만 범위가 구간을 못 좁힌다
  • 범위를 앞에 → 구간은 좁아지지만 Sort가 남는다
  • LIMIT이 작으면(목록 20건) 정렬 쪽이 대개 이긴다 — 구간 앞에서 20개만 읽고 멈추기 때문
  • LIMIT 없이 대량을 뽑는 배치라면 반대

결정 근거는 취향이 아니라 실측이다.

5-2. 무엇이 "범위"로 취급되는가 즉답 필요

원칙 ①을 적용하려면 이 분류가 즉시 나와야 한다. 조건을 보고 "이건 등호 바구니, 이건 범위 바구니"를 못 가르면 순서를 조립할 수 없다.

조건 4분류 — 바구니에 던져 넣기

등호처럼 동작
=, IS NULL, 그리고 IN (…)
단 IN은 값 개수만큼 구간이 여러 개로 갈라진다. 뒤 컬럼을 탐색에 쓸 수는 있지만, 뒤 컬럼 기준 ORDER BY는 갈라진 구간을 병합해야 해서 대개 Sort가 남는다.
범위
>, >=, <, <=, BETWEEN, LIKE 'kim%'(선행 문자 고정)
→ 인덱스에서 딱 하나만 액세스 조건으로 쓸 수 있다
사실상 전 구간 (범위 중 최악)
!=, NOT IN, IS NOT NULL, NOT LIKE
→ 구간이 거의 전체라 좁히는 효과가 없다
아예 못 씀
LIKE '%kim%', 컬럼에 함수·연산, 타입 불일치
→ 인덱스에 저장된 원본 값의 형태와 달라져 시작점 자체를 못 찍는다

IN의 각주: PostgreSQL 17에서 IN 배열 처리가 한 번의 스캔으로 개선돼 정렬이 살아남는 경우가 생겼지만, 기본기는 "갈라지면 정렬이 필요하다"로 두는 게 안전하다.

5-3. 설계 절차 — 면접에서 이 순서로 소리 내어 조립한다

순서 원칙을 아는 것과 즉석에서 조립하는 것은 다르다. 면접에서 "이런 쿼리들이 있는데 인덱스를 설계해보세요"가 나오면 아래 다섯 칸을 소리 내어 통과하면 된다.

PostgreSQL은 훑은 행이 아니라 실제로 수정하는(또는 FOR UPDATE로 반환되는) 행에만 락을 건다 — 스캔 폭이 락 범위로 직결되진 않는다. 대신 PostgreSQL에서 스캔 폭 실수는 트랜잭션 장기화로 번진다: 락 보유 시간이 길어지고, 오래 열린 트랜잭션은 VACUUM이 죽은 튜플을 치우지 못하게 막아(블로트) 무관한 테이블 성능까지 끌어내린다. "인덱스 순서 실수"가 성능 문제를 넘어 운영 사고가 되는 경로다.

7. 등호끼리의 순서 — 접두사 재사용이 먼저다

등호 컬럼이 둘 이상일 때는 어떻게 정하나. 여기서 카디널리티 격언이 처음으로 무력해진다.

7-1. 접두사 재사용으로 정한다 — 뜨거운 쿼리 셋을 놓고

이 테이블을 치는 뜨거운 쿼리 셋 (5-3 절차의 ①단계)

  • (a) 내 주문 중 상태별 목록 — WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20
  • (b) 내 주문 전체 최근순 — WHERE user_id = ? ORDER BY created_at DESC LIMIT 20
  • (c) 실패 주문 알림 배치 — WHERE status = 'FAILED' AND created_at >= ?
before"status도 등호니까 아무 데나"
CREATE INDEX idx_orders_status_user_created
    ON orders (status, user_id, created_at);

-- (a) 완전 커버
--     등호 둘 다 액세스 조건, created_at으로 정렬까지

-- (b) 불가  ← 치명적
--     선두 status 조건이 없다 → 구간을 못 찍어
--     플래너가 버린다 (Seq Scan행)

-- (c) 절반
--     status까지만 구간, created_at은 인덱스 내 검사로 강등
--     (스캔 폭 = FAILED 전체)
after접두사 재사용 기준 — (a)(b)가 공유하는 user_id를 선두로
CREATE INDEX idx_orders_user_status_created
    ON orders (user_id, status, created_at);

-- (a) 완전 커버 (before와 동일한 구간)

-- (b) 가능  ← 접두사 (user_id)로 탄다
--     정렬 문제는 11절 세 번째 꼬리질문 참고

-- (c) 불가 — 이건 어차피 선두가 status여야 하므로
--     별도 인덱스 (status, created_at)

CREATE INDEX idx_orders_status_created
    ON orders (status, created_at);
-- status 단독은 카디널리티 3이라 무의미해 보이지만,
-- FAILED가 전체의 1%면 "희귀 값만 조회하는" 쿼리엔 유효하다 (8절)
같은 세 컬럼, 순서만 다른 두 인덱스가 커버하는 쿼리 — 차이는 (b)에서 갈린다
인덱스(a) user + status + 정렬(b) user만 + 정렬(c) status + 기간
(status, user_id, created_at)완전 커버불가 — 선두 조건 없음절반 (범위가 강등)
(user_id, status, created_at)완전 커버가능 — 접두사로 탄다불가 → 별도 인덱스
카디널리티가 실제로 개입하는 순간 — "앞 컬럼만 쓰는 쿼리가 있을 때" (user_id, status, …)의 접두사 user_id만 쓰면 사용자 한 명 분(수십 건)으로 좁혀지지만, (status, user_id, …)의 접두사 status만 쓰면 전체의 90%가 걸려 플래너가 인덱스를 버린다.
즉 카디널리티 높은 컬럼을 앞에 두는 이유는 "그 컬럼만으로도 인덱스가 쓸모 있게" 하기 위해서이지, 등호 둘을 다 쓰는 쿼리를 위해서가 아니다.

7-2. 뒤에 붙는 컬럼은 탐색용이 아니라 "제거용"이다

범위 컬럼 뒤에 붙는 컬럼은 구간을 좁히지 못한다(3절). 그래도 붙이는 이유는 둘이다 — 정렬을 없애거나, 힙 방문을 없애거나.

⑴ 정렬 제거 — Sort 노드를 지운다

등호 컬럼들 바로 뒤에 ORDER BY 컬럼을 두면 인덱스 순서가 곧 정렬 순서라 Sort가 사라진다. 특히 LIMIT 20이 붙으면 구간의 앞 20개만 읽고 멈춘다.

Sort가 남으면 조건에 맞는 행을 전부 읽은 뒤에야 정렬한다 — LIMIT이 있으면 Sort Method: top-N heapsort로 정렬 메모리는 20건 몫만 쓰지만 매칭 행 전수를 읽는 비용은 그대로이고, LIMIT 없이 대량이면 external merge Disk:(디스크 정렬)까지 간다.

⑵ 커버링 — 힙 방문 자체를 없앤다

SELECT가 필요로 하는 컬럼까지 인덱스가 들고 있으면 리프에서 TID를 꺼내 힙 페이지를 찌르는 단계 자체가 사라진다 — 계획에 Index Only Scan으로 찍힌다.

다만 실제로 힙을 건너뛰는지는 visibility map(VACUUM 상태)에 달려 있다 — 다음 문항 커버링 인덱스의 주제다.

8. 카디널리티의 진짜 자리 — 오해 둘, 개입 지점 둘

카디널리티 (cardinality)
그 컬럼에 서로 다른 값이 몇 종류 있는가. 컬럼 자체의 성질이고 쿼리와 무관하다. user_id 100만 종(높음), status 3종(낮음), is_deleted 2종(최악). PostgreSQL은 pg_stats.n_distinct.
선택도 (selectivity)
이 조건이 전체 행을 몇 %로 좁히는가. 조건의 성질이라 같은 컬럼이라도 값에 따라 다르다. 카디널리티가 낮으면 대개 선택도도 낮지만, 편중 분포에서는 갈라진다.

8-1. 오해 ① "카디널리티 높은 컬럼을 무조건 앞에" 함정

틀린 이유가 둘인데, 둘 다 앞에서 이미 실증했다.

⑴ 그 컬럼이 범위 조건이면 뒤로 가야 한다

6절의 before가 정확히 이 실수다 — created_at은 카디널리티 최상위(초 단위면 사실상 행 수만큼)지만 범위 조건이라, 앞에 두는 순간 status가 인덱스 내 검사로 강등되고 인덱스 스캔 폭이 100배가 됐다.

⑵ 등호끼리라면 최종 구간이 동일하다

7절에서 본 대로, 같은 쿼리 안에서 등호 둘의 순서를 바꿔도 도착지도 읽은 엔트리 수도 같다. 카디널리티는 결정에 참여할 자리가 없다.

여기서 얻는 교정된 문장 — 이 한 줄이 이 문서의 핵심이다

중요한 것은 컬럼 자체의 분포가 아니라, 그 컬럼이 이 쿼리에서 등가 조건으로 쓰이는가다
카디널리티 3인 status
등호로 쓰이면 선두 후보다
카디널리티 1,000만인 created_at
범위로 쓰이면 맨 뒤다

정확한 순위는 등호/범위 구분(1순위) → 접두사 재사용(2순위) → 카디널리티(3순위).

8-2. 오해 ② "카디널리티 낮은 컬럼은 복합 인덱스 안에서도 쓸모없다" 함정

단독 인덱스로는 무의미한 status(값 3종)가 복합 안에서는 구간을 쪼개는 칸막이가 된다. 1절 목록에서 status가 user 7의 7건을 DONE 2건 · FAILED 2건 · PAID 3건으로 나눠 놓은 것이 바로 그 일이다.

수치로 — "인덱스를 탈지 말지"는 조합의 선택도가 정한다 조합의 선택도는 (컬럼들이 서로 독립이라면) 각 컬럼 선택도의 곱이다. 이 장의 분포로 계산하면 user_id = 7이 1/1,000,000, status = 'FAILED'가 1/100이므로 조합은 1/100,000,000이다. "이 인덱스를 탈지 말지"(랜덤 vs 순차 I/O 손익분기)를 정하는 것은 이 조합의 선택도이지, 개별 컬럼의 카디널리티가 아니다.
독립 가정이 깨지는 경우 — 예를 들어 city와 zipcode처럼 한쪽이 다른 쪽을 거의 결정하는 컬럼 쌍 — 에는 플래너가 곱을 과소추정한다. PostgreSQL은 CREATE STATISTICS … (dependencies, ndistinct)로 다중 컬럼 통계를 따로 만들어 교정할 수 있다.

8-3. 개입 지점 ① 편중 분포 — 카디널리티 숫자만 보면 속는다

status의 카디널리티가 3이라는 숫자는 "각 값이 33%씩"이라는 인상을 준다. 그런데 실제 분포가 PAID 90% / DONE 9% / FAILED 1%라면 status = 'FAILED'의 선택도는 1%로 충분히 좋다. 사람이 카디널리티만 보고 "status는 인덱스 무의미"라고 판단하면 7-1의 (c) 배치 쿼리를 풀스캔으로 방치하게 된다.

before카디널리티 숫자로 판단한다
SELECT n_distinct FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';

   3   → "무의미하네" (오판)
after분포로 판단한다 — 이 조회가 습관이 돼야 한다
SELECT most_common_vals, most_common_freqs FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';

   {PAID,DONE,FAILED} / {0.90,0.09,0.01}
   → FAILED 조회는 1%, 인덱스 유효
   (pg_stats는 ANALYZE 표본 기반 — 낡았다 싶으면 ANALYZE orders 먼저)
속는 쪽은 플래너가 아니라 사람이다 플래너는 MCV(최빈값 목록)·히스토그램으로 추정하므로 편중을 대체로 잡아낸다 — 표본이 모자라 못 잡으면 ALTER TABLE … ALTER COLUMN … SET STATISTICS(또는 default_statistics_target)로 표본을 키운다. 속는 쪽은 카디널리티 숫자 하나로 설계 판단을 내리는 사람이다.

8-4. 개입 지점 ② 접두사만 쓰는 쿼리의 효율

등호 컬럼 A, B가 있고 "A만 쓰는 쿼리"와 "B만 쓰는 쿼리"가 둘 다 있어 접두사 재사용으로 우열이 안 갈릴 때, 카디널리티 높은 쪽을 앞에 둔다 — 접두사만으로도 구간이 좁아져 인덱스가 실제로 쓰이도록. 카디널리티가 낮은 쪽을 앞에 두면 그 접두사 쿼리는 플래너가 인덱스를 버린다.

가산점 — skip scan (PostgreSQL 18 / MySQL 8.0) 가산점 선두 컬럼이 조건에 없어도, 선두 고유값이 아주 적을 때 값마다 뒤 컬럼 구간을 따로 탐색해 주는 최적화다. 2절의 "조각이 100만 개"가 "조각이 3개"라면 조각마다 시작점을 찍어도 견딜 만하다는 발상이다. 그 이전 버전에서는 재귀 CTE로 흉내 내는 수공업(loose scan 패턴)뿐이었다.
"카디널리티 낮은 컬럼을 앞에 두면 접두사 규칙을 우회할 수 있다"는 뜻이지만, 고유값 수만큼 탐색을 반복하므로 선두 카디널리티가 한 자릿수일 때만 의미 있는 예외다. 설계 원칙을 대체하지 않는다.
카디널리티 관계 — 한 장 요약 (암기 대상)
질문답
카디널리티가 컬럼 순서를 정하나?3순위. 등호/범위 → 접두사 재사용 → 그다음
카디널리티가 "인덱스를 탈지"를 정하나?개별 컬럼이 아니라 조합의 선택도가 정한다 (랜덤 vs 순차 I/O 손익분기)
낮은 카디널리티 컬럼은 버리나?단독은 무의미, 복합 안에서는 칸막이. 편중 분포면 단독도 유효

9. 순서 고민 자체를 우회하는 두 갈래 — BitmapAnd · 부분 인덱스

여기까지는 "복합 인덱스 하나를 어떤 순서로 만들 것인가"였다. PostgreSQL에는 그 질문을 다른 질문으로 바꿔 버리는 두 갈래가 있다. 면접에서 이 둘을 꺼내면 "격언 암기"가 아니라 "도구 상자를 안다"로 들린다.

9-2. 갈래 ⑵ 부분 인덱스로 컬럼을 하나 없애 버린다

부분 인덱스(partial index) = WHERE 절을 붙여 조건에 맞는 행만 담는 인덱스다. 등호 조건이 사실상 고정돼 있다면, 그 컬럼을 인덱스에 넣고 순서를 고민할 게 아니라 인덱스 정의 안으로 옮겨 컬럼 자체를 없애는 것이 정석이다.

beforestatus를 컬럼으로 들고 순서를 고민한다
CREATE INDEX idx_orders_status_created
    ON orders (status, created_at);

-- 인덱스 엔트리 1,000만 개 (전 행)
-- status가 매 엔트리에 반복 저장된다
afterstatus = 'FAILED'가 이 쿼리의 고정 전제라면 정의로 올린다
CREATE INDEX idx_orders_failed_created
    ON orders (created_at) WHERE status = 'FAILED';

-- 인덱스 엔트리 10만 개 (전체의 1%)
-- 컬럼이 created_at 하나뿐이라 순서 고민이 사라진다
--   ① 인덱스가 1/100 크기 → 리프 페이지 수도 1/100
--   ② FAILED가 아닌 행을 INSERT할 때는 이 인덱스를 안 건드린다
--   ③ created_at이 유일한 컬럼 → ORDER BY가 그대로 인덱스 순서
확인조건이 계획에서 아예 사라진다
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, user_id, amount FROM orders
WHERE status = 'FAILED' AND created_at >= now() - interval '1 hour';

--  Index Scan using idx_orders_failed_created on orders
--    Index Cond: (created_at >= …)
--    ← status 조건은 Index Cond에도 Filter에도 없다.
--      인덱스 자체가 FAILED만 담고 있으므로 플래너가
--      "이 쿼리의 WHERE는 인덱스의 WHERE를 포함한다"고 증명하고 조건을 지워 버린 것.

부분 인덱스 주의 둘 — 이걸 모르고 쓰면 "만들었는데 안 탄다"가 된다

① 리터럴이어야 증명된다
플래너는 쿼리의 WHERE가 인덱스의 WHERE를 논리적으로 포함한다는 것을 증명할 수 있을 때만 이 인덱스를 쓴다. status = 'FAILED'처럼 상수 비교면 증명되지만, status = $1처럼 파라미터로 넘기면 계획 생성 시점에 값을 모르므로 증명에 실패해 인덱스를 못 탄다.
② "고정 조건"이 정말 고정인가
상태 값이 하나 늘어나면 인덱스를 새로 만들어야 한다. 요건이 흔들릴 여지가 있으면 부분 인덱스는 부채가 된다.

10. 대가와 안전망 — 결정마다 붙는 청구서

순서를 정하는 각 결정에는 대가가 붙어 있다. 편익만 말하면 반쪽이다.

결정 → 얻는 것 / 내주는 것 — 한 호흡에 양면으로 말한다
결정얻는 것내주는 것
정렬·커버링용 컬럼을 뒤에 더 붙인다Sort 제거, 힙 방문 제거엔트리 폭↑ → 페이지당 엔트리↓ → 버퍼 적재율↓; 그 컬럼이 자주 바뀌면 HOT 탈락으로 쓰기 증폭(10-1)
기존 인덱스의 순서를 바꾼다대상 쿼리 최적그 인덱스의 접두사에 기대던 다른 쿼리가 조용히 풀스캔으로 전락 — 에러가 아니라 지연으로 나타나서 늦게 발견된다
넓은 인덱스 하나로 여러 쿼리 커버인덱스 수↓ → DML당 갱신 트리 수↓, 버퍼 경쟁↓각 쿼리는 차선(어떤 쿼리는 Sort 감수), 순서 변경 시 영향 범위↑
쿼리별 좁은 인덱스 여럿각 쿼리 최적DML마다 트리 N개 갱신, 공간, 후보가 많아져 플래너 선택 실패 확률↑
범위 조건이 둘일 때 하나만 인덱스 범위로더 좁히는 범위로 스캔 폭 최소화다른 범위는 인덱스 내 검사 → 그만큼 초과 스캔
부분 인덱스로 컬럼을 없앤다인덱스 크기·쓰기 비용 급감, 순서 고민 소멸조건이 바뀌면 인덱스를 다시 만들어야 하고, 조건을 파라미터로 넘기면 아예 안 쓰인다

10-1. 자주 바뀌는 컬럼을 인덱스에 넣는 대가 — PostgreSQL에서 한 겹 더 무겁다

표의 첫 줄에 나온 "쓰기 증폭"을 사슬로 풀어 둔다. PostgreSQL의 UPDATE는 행을 제자리에서 고치지 않는다. 옛 튜플에 "죽었다"는 표시를 하고 새 버전 튜플을 삽입한다(MVCC). 새 튜플은 새 TID를 받으므로, 원칙적으로는 그 테이블의 모든 인덱스에 새 TID를 가리키는 엔트리를 하나씩 꽂아야 한다.

그런데 예외가 하나 있다. 바뀐 컬럼이 어떤 인덱스에도 안 들어 있고 새 버전을 같은 힙 페이지 안에 놓을 자리가 있으면, 인덱스를 하나도 안 건드리고 힙 페이지 안에서만 처리한다. 이것이 HOT(Heap-Only Tuple) 업데이트 — "힙에만 사는 튜플"이라는 이름 그대로, 인덱스가 이 버전의 존재를 모른다.

10-2. 안전망 네 겹 — 규칙을 사람의 기억에 맡기지 않는다

"등호 먼저, 범위 뒤"를 리뷰어가 기억해 주기를 바라는 것이 가장 약한 안전망이다. 고정할 곳은 넷이다.

1

CREATE INDEX idx_orders_status_created_at

2

    seedOrders(200_000);
    jdbcTemplate.execute("ANALYZE orders");

    // when: FORMAT JSON으로 받아야 계획을 문자열 파싱 없이 필드로 꺼낼 수 있다
    String plan = jdbcTemplate.queryForObject(
        "EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) "
      + "SELECT id, user_id, amount FROM orders "
      + "WHERE status = 'FAILED' AND created_at >= ?",
        String.class, LocalDateTime.now().minusHours(1));
    JsonNode p = objectMapper.readTree(plan).at("/0/Plan");

    // then ①: 의도한 인덱스를 탄다 — 인덱스 이름은 통계가 흔들려도 안 바뀌는 구조적 값이다
    assertThat(p.at("/Index Name").asText()).isEqualTo("idx_orders_status_created_at");

    // then ②: 읽은 블록이 "좁은 구간" 수준 — (created_at, status)로 뒤집히면 수천으로 튄다
    //   비용·추정 행 수는 통계에 따라 흔들리므로 단정 대상이 아니다
    int blocks = p.at("/Shared Hit Blocks").asInt() + p.at("/Shared Read Blocks").asInt();
    assertThat(blocks).isLessThan(200);   // 임계값은 실측 후 여유 있게
}
이 테스트에도 대가가 있다실행 계획은 데이터 양과 통계에 따라 바뀐다. 그래서 실전 규모의 시드 + ANALYZE가 필요하고, 그만큼 테스트가 무거워진다. 모든 쿼리에 걸지 말고 테이블 규모가 크고 순서 실수가 곧 장애인 쿼리 몇 개에만 건다.
3
중복·미사용 인덱스를 사람이 기억하지 않는다 — (A, B)를 만들면서 기존 (A)를 지우는 걸 잊는 일은 반드시 생긴다. (A)는 (A, B)의 접두사이므로 하는 일이 완전히 포함되는데(4절), 쓰기 비용은 따로 붙는다. 
-- 미사용: 통계 수집 이후 한 번도 안 쓰인 인덱스 (pg_stat_reset 시점 주의)
SELECT indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE relname = 'orders' AND idx_scan = 0;

-- 접두사에 흡수되는(중복) 인덱스: a의 컬럼 목록이 b의 접두사인 쌍
SELECT a.indexrelid::regclass AS redundant, b.indexrelid::regclass AS covering
FROM pg_index a
JOIN pg_index b ON a.indrelid = b.indrelid AND a.indexrelid <> b.indexrelid
WHERE a.indrelid = 'orders'::regclass
  AND b.indkey::text LIKE a.indkey::text || ' %';
-- (단순 비교 버전 — 부분 인덱스(WHERE 절)·연산자 클래스가 다르면 중복이 아니니 따로 확인)
4
느린 쿼리를 계획째로 자동 수집한다 — log_min_duration_statement를 낮게 잡으면 느린 쿼리가 로그에 남고, auto_explain 확장을 켜면(auto_explain.log_min_duration, log_buffers = on) 그 쿼리의 실제 실행 계획 + Buffers까지 같이 남는다 — 순서 실수로 스캔 폭이 늘어난 쿼리는 "읽은 블록 대비 반환 행이 적은" 형태로 잡힌다. 상시 감시는 pg_stat_statements로 shared_blks_read·mean_exec_time 상위 쿼리를 본다. 운영에서 "느려요"가 오기 전에 설정이 먼저 알려주는 구조다.

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

복합 인덱스를 한 문장으로?
사전 안의 사전. A로 정렬하고 A가 같은 것끼리만 B로, 둘 다 같은 것끼리만 C로. → 앞 컬럼 값이 고정돼야 뒤 컬럼 정렬이 산다
순서 4자리는?
등 · 범 · 정 · 커 — 등호(여러 개) → 범위(하나, 맨 뒤) → 정렬(범위와 같은 자리 경쟁) → 커버링(INCLUDE)
순위 3단은?
등범 → 재사용 → 카디. ① 등호/범위 구분 ② 접두사 재사용(커버 범위) ③ 카디널리티(타이브레이커)
범위가 "하나뿐"인 이유?
범위는 앞 컬럼 값을 여러 개로 열어 놓는다 → 열린 순간 뒤 컬럼 정렬이 값마다 따로 논다 → 시작점을 못 찍는다
등호끼리 순서는 무엇이 정하나?
이 쿼리가 아니라 다른 쿼리들. 같은 쿼리 안에선 순서를 바꿔도 최종 구간이 같다 → 접두사만 쓰는 쿼리가 결정한다
"100배"는 어디에 붙나?
인덱스 페이지 1,200 vs 12 = 100배. 총 버퍼는 4,203 vs 3,015 = 1.4배(힙 3,000회가 양쪽에 똑같이 붙으므로)
강등을 어떻게 판별하나?
계획 텍스트로는 안 보인다 — 강등된 키도 Index Cond. → EXPLAIN (ANALYZE, BUFFERS)의 읽은 블록 수
카디널리티가 개입하는 두 지점?
① 편중 분포(status 3종이어도 FAILED 1%면 유효) ② 접두사만 쓰는 쿼리의 효율(그 컬럼만으로도 좁아지게)
"인덱스를 탈지"는 무엇이 정하나?
개별 컬럼 카디널리티가 아니라 조합의 선택도(독립이면 곱). 예: 1/100만 × 1/100 = 1/1억
순서 고민을 우회하는 둘?
조합이 유동적이면 단일 인덱스 + BitmapAnd, 조건이 고정이면 부분 인덱스(컬럼 자체가 사라진다)
조건 4분류는?
등호처럼(=·IS NULL·IN) / 범위(>·BETWEEN·LIKE 'x%') / 사실상 전 구간(!=·NOT IN·IS NOT NULL) / 못 씀(LIKE '%x%'·함수·타입 불일치)
순서를 바꿀 때의 진짜 위험?
그 인덱스의 접두사에 기대던 다른 쿼리가 조용히 풀스캔으로 전락한다 — 에러가 아니라 지연이라 늦게 발견된다

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

카디널리티 높은 컬럼을 앞에 두라고 배웠는데, 틀린 건가요? 필수힌트: "맞다/틀리다"로 답하지 말고 순위를 매겨 답한다

반쯤 맞다 — 3순위 기준으로는 맞고, 1순위로 쓰면 틀린다.

1순위는 등호/범위 구분이다. 범위 조건 컬럼은 카디널리티가 최상위여도 뒤로 가야 한다 — created_at을 앞에 둔 순간 status가 구간을 못 좁히는 인덱스 내 검사로 강등돼 인덱스 스캔 폭이 100배가 된 예가 6절이다.

2순위는 접두사 재사용이다. 등호 컬럼끼리는 같은 쿼리에서 순서를 바꿔도 최종 구간이 같으므로, "이 인덱스의 앞부분만 쓰는 다른 쿼리"가 무엇인지가 순서를 정한다.

카디널리티는 그래도 우열이 안 갈릴 때, 접두사만으로도 구간이 좁아지도록 높은 쪽을 앞에 두는 타이브레이커다.

한 문장으로 고쳐 말하면 — 중요한 것은 컬럼의 분포가 아니라, 그 컬럼이 이 쿼리에서 등가 조건으로 쓰이는가다
범위 조건이 두 개(created_at 기간 + amount >= ?)면 어떻게 하나요? 필수힌트: 하나를 고르는 기준 + 나머지를 어디에 둘지 + 한 단계 위의 답

인덱스는 범위를 하나만 액세스 조건으로 쓴다 — 첫 범위 뒤는 정렬이 깨지므로 두 번째 범위는 구간을 못 좁힌다. 그래서 둘 중 더 좁히는 범위(또는 ORDER BY에 쓰이는 범위)를 인덱스의 범위 컬럼으로 두고, 나머지는 그 뒤에 붙인다 — 뒤에 붙이면 적어도 인덱스 안에서 걸러져 힙 방문 전에 버려진다(계획엔 똑같이 Index Cond로 찍힌다).

한 단계 위의 답은 요건을 되물어 고정 조건인지 확인하는 것이다. "금액 1만 원 이상"이 사실상 고정된 기준이면 PostgreSQL에서는 부분 인덱스가 정석이다.

CREATE INDEX … ON orders (status, created_at) WHERE amount >= 10000;
-- 인덱스 자체가 그 조건의 행만 담으므로 두 번째 범위가 사라지고 인덱스도 작아진다

다만 조건이 정말 고정인지, 쿼리의 WHERE가 인덱스 WHERE를 포함하는지(포함해야 플래너가 쓴다)를 확인하고 간다. 조합이 유동적이라 부분 인덱스를 못 쓰는 관리자 검색 화면이라면 단일 컬럼 인덱스 여럿 + BitmapAnd가 차선이다.

(user_id, status, created_at)가 있는데 WHERE user_id = ? ORDER BY created_at DESC LIMIT 20이 정렬을 합니다. 왜죠? 어떻게 하죠? 함정힌트: 가운데가 비었다. 선택지는 넷이고 각각 대가가 있다

가운데 status가 조건에 없어서다. 2-1절이 그대로 이 상황이다 — user 100의 구간 안에서 created_at은 status별로 따로 정렬돼 있지(DONE 칸의 시간순, PAID 칸의 시간순…) 전체가 시간순이 아니다.

선택지는 넷이고 각각 대가가 있다.

⑴ 그냥 수용한다
사용자당 행이 수십 건이면 Sort(top-N heapsort) 비용이 미미할 수 있다 — 실측하고 수용
⑵ (user_id, created_at)을 따로
이 쿼리는 최적. 대가는 인덱스 하나 몫의 쓰기·공간
⑶ status IN (모든 값)을 넣는다
대개 안 통한다. 구간이 값 수만큼 갈라져 병합 정렬이 필요하므로 Sort는 대개 안 사라진다
⑷ (user_id, created_at, status)로 순서 변경
이 쿼리는 해결되지만 user_id + status + 정렬 쿼리에서 status가 구간을 못 좁히게 된다

결정은 취향이 아니라 어느 쿼리가 더 뜨거운지를 pg_stat_statements로 측정해 내린다.

인덱스 하나를 넓게(4~5컬럼) 만들어 여러 쿼리를 커버하는 것과 쿼리별로 좁은 인덱스를 여러 개 두는 것, 기준은? 시니어 변별힌트: 양면을 먼저 펴고, 기준 셋 + PostgreSQL의 제3의 선택지

양면을 먼저 편다. 넓은 하나는 DML당 갱신하는 트리 수와 버퍼 경쟁을 줄이지만, 각 쿼리는 차선이 되고 순서를 바꿀 때 영향 범위가 커진다. 좁은 여럿은 각 쿼리가 최적이지만 쓰기 증폭·공간·플래너 선택 혼선을 낸다.

기준은 셋이다.

  • ① 읽기:쓰기 비율 — 쓰기가 무거운 테이블일수록 넓은 하나로 합친다
  • ② 접두사 공유 여부 — 쿼리들이 같은 등호 컬럼으로 시작하지 않으면 넓혀도 못 커버하므로 애초에 선택지가 아니다
  • ③ 포함 컬럼의 변경 빈도 — 자주 바뀌는 컬럼이 인덱스에 들어가면 그 컬럼을 바꾸는 UPDATE가 HOT에서 탈락해 "모든 인덱스"가 쓰기 부담을 진다(10-1)

PostgreSQL이라면 제3의 선택지도 같이 편다 — 조건 조합이 예측 불가능한 화면이라면 단일 컬럼 인덱스 여럿을 두고 BitmapAnd에 맡기는 것이 인덱스 수와 커버 범위를 동시에 잡는다(대신 ORDER BY … LIMIT과 커버링은 포기).

결정보다 중요한 건 "각 인덱스가 어떤 쿼리를 위해 존재하는지"를 표로 남기는 것 — 이게 없으면 다음 사람이 순서를 바꾸다 다른 쿼리를 깨뜨린다
순서를 잘 잡았는데 어느 날부터 플래너가 그 인덱스를 안 탑니다 가산점힌트: 순서는 안 바뀌었어도 "무엇"이 바뀌었을까. 후보 셋

순서는 안 바뀌었어도 조합의 선택도는 바뀐다. 후보 셋을 순서대로 본다.

2
통계가 낡음 — 대량 적재·삭제 후 추정 행 수가 어긋나면 ANALYZE로 갱신한다. autovacuum의 analyze 임계가 큰 테이블에서 둔한 것도 흔한 원인 — autovacuum_analyze_scale_factor를 테이블 단위로 낮춘다.
3
새로 추가된 인덱스가 후보로 경쟁 — 누군가 비슷한 인덱스를 만들어 플래너가 그쪽을 고르기 시작한 경우. 10-2의 중복 인덱스 쿼리로 확인한다.

(A, B) 인덱스가 있는데 (A) 인덱스도 따로 필요할까요? 필수힌트: 원칙은 하나, 예외는 둘

원칙적으로 필요 없다. (A)는 (A, B)의 접두사이므로 조회 관점에서 하는 일이 완전히 포함된다(4절). 그런데 쓰기 비용은 따로 붙는다 — INSERT/비-HOT UPDATE마다 트리를 하나 더 갱신한다. 즉 얻는 것 없이 비용만 내는 인덱스이므로 지우는 것이 기본이다.

예외는 둘이다.

  • ① 목적이 조회가 아니라 제약일 때 — UNIQUE (A)는 A의 유일성을 강제하지만 UNIQUE (A, B)는 쌍의 유일성만 강제한다. 하는 일이 다르므로 접두사 논리가 적용되지 않는다.
  • ② 폭 차이가 유의미할 때 — (A)가 훨씬 좁으면 페이지당 엔트리가 많아 같은 건수를 더 적은 리프 페이지로 읽는다. A만 쓰는 쿼리가 초고빈도이고 그 차이가 측정될 때만 — 반드시 실측으로 판단한다.

확인은 사람 기억이 아니라 카탈로그로 한다 — pg_stat_user_indexes의 idx_scan = 0(미사용)과 접두사 흡수 쌍 조회(10-2)를 배치나 대시보드에 걸어 둔다.

IN (…)은 등호처럼 쓴다면서, 왜 뒤 컬럼 ORDER BY에서 Sort가 남나요? 함정힌트: 등호는 칸을 "하나" 고르고, IN은 칸을 "여러 개" 고른다

등호는 칸을 하나 고르지만 IN은 칸을 여러 개 고르기 때문이다. status IN ('PAID','DONE')이면 PAID 칸과 DONE 칸 두 개를 각각 탐색한다. 탐색 자체는 된다 — 각 칸 안에서 뒤 컬럼 정렬이 살아 있으므로 뒤 컬럼도 액세스 조건으로 쓸 수 있다.

문제는 정렬이다. 각 칸은 칸 안에서만 created_at 순이고, 두 칸을 이어 붙이면 시간순이 아니다. 전체를 시간순으로 내놓으려면 갈라진 구간들을 병합해야 하는데, 플래너가 그 병합을 못 하면 Sort가 남는다.

실무 대응은 셋이다. ⑴ LIMIT이 작고 매칭 행이 적으면 Sort(top-N heapsort)를 그냥 수용한다. ⑵ 값별로 쿼리를 갈라 각각 인덱스 순서로 LIMIT만큼 읽고 합친다 — Sort는 피하지만 쿼리 수가 늘고 최종 병합을 직접 맡아야 한다. ⑶ IN이 사실상 고정 집합이면 부분 인덱스로 조건을 인덱스 정의로 올린다(9-2).

각주: PostgreSQL 17에서 IN 배열 처리가 한 번의 스캔으로 개선돼 정렬이 살아남는 경우가 생겼다. 다만 기본기는 "갈라지면 정렬이 필요하다"로 두는 게 안전하다.

INCLUDE로 붙인 컬럼과 키 컬럼으로 붙인 컬럼, 무엇이 다르고 언제 갈라 쓰나요? 시니어 변별힌트: 다른 점 셋, 그리고 "똑같은 점" 하나가 진짜 변별 포인트

INCLUDE 컬럼은 리프에만 실리고 탐색에는 안 쓰인다. 그래서 다른 점이 셋이다 — ① 내부 노드에는 키 컬럼만 들어가므로 트리가 덜 뚱뚱해지고, ② 비교 연산자가 없는 타입도 실을 수 있으며, ③ 유니크 인덱스에도 덧붙일 수 있다(유일성은 키 컬럼으로만 판정하므로).

갈라 쓰는 기준은 하나다 — 그 컬럼이 탐색에 참여하는가. 조건이나 ORDER BY에 쓰이면 키 컬럼이어야 하고(INCLUDE 컬럼으로는 구간을 좁힐 수도 정렬을 만들 수도 없다), SELECT 목록에만 등장하면 INCLUDE다.

진짜 변별 포인트 — "똑같은 점"INCLUDE 컬럼도 HOT을 깬다. 그 컬럼을 바꾸는 UPDATE는 HOT에서 탈락하고, 새 TID를 꽂기 위해 그 테이블의 모든 인덱스가 갱신된다(10-1). "탐색에 안 쓰이니 갱신 비용도 없겠지"는 틀렸다. 그래서 자주 바뀌는 컬럼은 INCLUDE로도 넣지 않는다가 실무 규칙이다.
정렬 방향이 섞인 ORDER BY a ASC, b DESC도 인덱스로 처리되나요? 가산점힌트: 역방향 읽기가 만들어 주는 조합이 무엇인지 생각한다

된다 — 단, 인덱스를 그 방향으로 만들어야 한다. PostgreSQL은 인덱스를 역방향으로도 읽을 수 있다(Index Scan Backward). 그런데 역방향 읽기는 모든 컬럼의 방향을 한꺼번에 뒤집는다 — (a, b) 인덱스로 만들 수 있는 순서는 a ASC, b ASC와 그 역인 a DESC, b DESC 둘뿐이다.

그래서 혼합 정렬은 컬럼별 방향을 준 인덱스로 해결한다.

-- ORDER BY a ASC, b DESC 를 Sort 없이 처리하려면
CREATE INDEX … ON t (a ASC, b DESC);
-- 이 인덱스는 역방향으로 읽으면 ORDER BY a DESC, b ASC 도 커버한다

설계 관점의 함의: 방향을 준 인덱스는 그 조합과 그 역, 두 가지만 커버한다. 목록 API의 정렬 옵션이 여러 개라면 "어떤 정렬을 인덱스로 사줄 것인지"를 정하고 나머지는 Sort를 수용하는 것이 인덱스 수를 지키는 방법이다.

실전 드릴 — 이 세 쿼리를 주고 "인덱스를 설계해보세요"라고 하면, 어떤 순서로 소리 내어 말하겠습니까? 시니어 변별힌트: 5-3의 다섯 칸을 그대로 통과한다. 결론만 말하면 절반이다

주어진 쿼리 — (a) WHERE user_id = ? AND status = ? ORDER BY created_at DESC LIMIT 20 / (b) WHERE user_id = ? ORDER BY created_at DESC LIMIT 20 / (c) WHERE status = 'FAILED' AND created_at >= ?

1
"먼저 이 인덱스가 태울 쿼리 집합을 확인하겠습니다" — 세 쿼리의 호출 빈도와 총 시간을 pg_stat_statements로 본다고 말한다. 한 쿼리만 보고 순서를 정하지 않는다는 신호다.
2
"조건을 등호·범위·정렬·SELECT 전용으로 가르겠습니다" — (a) 등호 user_id·status, 정렬 created_at / (b) 등호 user_id, 정렬 created_at / (c) 등호 status, 범위 created_at.
3
"등호 컬럼끼리는 접두사 재사용으로 정합니다" — (a)와 (b)가 user_id를 공유하므로 user_id가 선두. 여기서 카디널리티를 꺼내지 않는 것이 포인트다 — (a) 안에서는 순서를 바꿔도 구간이 같기 때문.
4
"남은 한 자리는 정렬에 줍니다" — (a)(b) 모두 ORDER BY created_at DESC LIMIT 20이고 LIMIT이 작으므로 정렬을 인덱스로 사서 앞에서 20개만 읽고 멈추게 한다.
5
"(c)는 선두가 달라 같은 인덱스로 못 태웁니다" — status가 선두여야 하므로 별도 인덱스. 그리고 status = 'FAILED'가 고정 전제라면 부분 인덱스를 제안한다.
CREATE INDEX idx_orders_user_status_created ON orders (user_id, status, created_at);
--   (a) 완전 커버 / (b) 접두사 (user_id)로 커버 — 단 status가 비어 정렬 이슈는 별도 확인

CREATE INDEX idx_orders_failed_created ON orders (created_at) WHERE status = 'FAILED';
--   (c) 전용. 컬럼이 하나뿐이라 순서 고민이 사라지고 인덱스도 1/100 크기

마무리 한 마디까지 해야 완결이다 — "(b)가 정렬을 하는지 EXPLAIN (ANALYZE, BUFFERS)로 확인하고, 읽은 블록 수를 기준으로 (user_id, created_at)을 추가할지 판단하겠습니다." 결론을 단정하지 않고 검증 방법까지 붙이는 것이 설계자의 답이다.

한 줄 요약
복합 인덱스는 "앞 컬럼 값이 하나로 고정돼야 뒤 컬럼 정렬이 살아 있는" 사전 안의 사전이므로, 순서는 등호 → 범위(하나, 맨 뒤) → 정렬 → 커버링 순으로 배치하고, 등호 컬럼끼리는 접두사 재사용(커버 범위) → 카디널리티(접두사 효율) 순으로 정한다. 카디널리티는 순서의 3순위 기준일 뿐이며 — 중요한 것은 컬럼의 분포가 아니라 그 컬럼이 이 쿼리에서 등가 조건으로 쓰이는가다 — "인덱스를 탈지"는 개별 컬럼이 아닌 조합의 선택도가 정한다. 순서가 틀리면 뒤 컬럼이 구간을 못 좁혀 인덱스 스캔 폭이 자릿수로 커지는데, PostgreSQL 계획에는 강등된 조건도 Index Cond로 찍혀 겉으로 안 보인다 — EXPLAIN (ANALYZE, BUFFERS)의 읽은 블록 수로 판별한다. 조합이 유동적이면 단일 인덱스 + BitmapAnd로, 조건이 고정이면 부분 인덱스로 순서 고민 자체를 우회할 수 있고, 규칙은 인덱스 이름 · 블록 수 단정 테스트 · 카탈로그 조회 · auto_explain에 박아 둔다.
