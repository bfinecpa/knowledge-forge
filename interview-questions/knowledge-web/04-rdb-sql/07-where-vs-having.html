WHERE vs HAVING
같은 "5000"인데 답이 7000과 5000으로 갈리는 이유를 말로 재현한다

면접 질문: "WHERE절과 HAVING절의 차이는?"

핵심 관전 포인트 — 논리적 실행 순서로 고정한다: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. WHERE는 집계에 들어갈 재료(행)를 거르고, HAVING은 집계가 끝난 결과(그룹)를 거른다. 그래서 같은 테이블에 같은 "5000" 조건을 걸어도 자리에 따라 답이 7000 vs 5000으로 갈린다 — WHERE로 옮기면 평균의 분모(재료)가 바뀌고, HAVING으로 옮기면 재료는 그대로인 채 완성된 평균이 문턱을 넘는지만 본다. 이 차이를 데이터 없이 말로 재현하는 것이 이 문서의 훈련 목표이고, 성능 축까지 얹으면 완성이다 — 같은 조건이면 WHERE(집계 전에 행을 줄이고 인덱스를 탄다). PostgreSQL 계획에는 이 자리가 그대로 찍힌다: WHERE는 스캔 노드의 Index Cond/Filter, HAVING은 집계 노드의 Filter. 플래너가 집계 없는 HAVING 조건을 알아서 WHERE로 내려 주긴 하지만, 그것에 기대는 것과 의도를 자리로 표현하는 것은 다르다.
  • 1
    정의는 한 줄, 근거는 순서다 — WHERE는 개별 행에 대한 조건, HAVING은 그룹(집계 결과)에 대한 조건. 그렇게 될 수밖에 없는 이유는 논리적 실행 순서에서 WHERE(②)와 HAVING(④) 사이에 GROUP BY(③)가 끼어 있기 때문이다 — WHERE가 볼 수 있는 것은 아직 "행"뿐이고, HAVING이 보는 것은 이미 만들어진 "그룹"이다.
  • 2
    그래서 자리를 바꾸면 "의미가 달라지는" 게 아니라 "다른 틀린 숫자가 나온다" — 개발팀에 A=3000, B=7000이 있을 때 WHERE salary >= 5000이면 평균 7000(A가 재료에서 빠져 분모가 바뀐다), HAVING avg(salary) >= 5000이면 평균 5000(재료는 그대로, 완성된 평균만 검사). 게다가 WHERE로 재료가 전부 잘린 부서는 결과에서 통째로 증발한다.
  • 3
    집계 함수가 없는 조건이면 WHERE에 둔다 — WHERE는 해시·정렬에 흘려보낼 입력 행 자체를 줄이고 인덱스를 탈 수 있지만, HAVING은 버릴 그룹까지 다 만든 뒤에 거른다. 계획에서 스캔 노드의 Index Cond냐 집계 노드의 Filter+Rows Removed by Filter냐로 확인되고, 플래너가 내려 주더라도 그것은 비용 차이를 지울 뿐 의도 표현을 대신하지 않는다.

0. 질문 + 출제 의도

질문: "WHERE절과 HAVING절의 차이는?"

출제 의도: 집계 전/후 필터의 구분이 안 되면 통계 쿼리에서 틀린 숫자를 만들고, 틀린 숫자는 틀린 비즈니스 판단으로 이어진다. 문법 암기("HAVING은 GROUP BY 뒤에 쓴다")가 아니라 조건의 자리가 결과 숫자를 바꾼다는 사실을 구체 데이터로 추적할 수 있는지 — 그리고 그것을 데이터 없이도 말로 설명할 수 있는지를 본다. PostgreSQL은 이 순서를 표준대로 엄격히 지키는 쪽이라(WHERE·HAVING에서 SELECT 별칭 불가, GROUP BY에 없는 컬럼은 에러) 순서를 몸으로 아는지가 에러 메시지에서 바로 드러난다.

이 페이지가 겨냥하는 약점 세 가지 ① "HAVING은 GROUP BY 뒤"라는 문법만 외운 상태 → 1·2절에서 실행 순서 도식을 세우고, 자주 만나는 에러 세 개를 그 순서에서 유도한다.
② 바꿔 쓰면 "의미가 달라진다" 정도로 뭉개는 것 → 3·4절에서 7000 vs 5000을 행 단위로 추적하고, 5절에서 데이터 없이 말로 재현하는 문장 틀을 고정한다.
③ 성능 축이 비어 있는 것 → 7·8절에서 GROUP BY 비용이 어디서 나는지, 그리고 실행 계획의 어느 노드에 조건이 붙는지로 "같은 조건이면 WHERE"를 증명한다.

1. 논리적 실행 순서 — 도식 하나로 고정하면 두 절은 헷갈릴 수 없다

정의는 한 줄이면 된다. WHERE는 개별 행에 대한 조건, HAVING은 그룹(집계 결과)에 대한 조건. 문제는 이 한 줄을 외워도 실전에서 헷갈린다는 것이다. 헷갈리지 않게 만드는 유일한 방법은 왜 그럴 수밖에 없는지를 아는 것이고, 그 답이 SQL의 논리적 실행 순서에 들어 있다.

먼저 용어 — "논리적 실행 순서"는 "DB가 실제로 이 순서로 돈다"가 아니다 "이 순서대로 처리한 것과 같은 결과가 나와야 한다"는 SQL 표준의 약속이다. 실제 실행은 플래너가 더 싼 순서로 바꿔도 되지만(8-3절), 결과는 반드시 이 순서를 따른 것과 같아야 한다. 그래서 "결과가 왜 이렇게 나오는가"는 항상 이 순서로 설명된다.

그리고 우리가 SQL을 쓰는 순서(SELECT → FROM → WHERE → …)와 이 순서는 다르다. 이 불일치가 이 문서의 모든 혼란의 출발점이다.

1-1. 비유 두 개로 고정한다

요리 — 재료 손질 vs 완성품 검수

WHERE는 재료 손질이다. 상한 재료를 조리 전에 버린다. HAVING은 완성된 요리 검수다. 맛없는 요리를 상에서 내린다.

같은 "버린다"여도 — 재료를 버리면 요리의 맛 자체(평균값)가 바뀌고, 완성품을 버리면 상에 오르는 접시 수(그룹 수)만 바뀐다.

학교 — 학생을 거르나, 반을 거르나

"60점 미만 학생을 빼고 반 평균을 내라"는 WHERE(학생=행을 거른다 → 반 평균이 올라간다). "반 평균이 60점 이상인 반만 보여라"는 HAVING(반=그룹을 거른다 → 반 평균은 그대로다).

전원이 60점 미만인 반은 앞쪽에서는 명단이 비어 반 자체가 사라지고, 뒤쪽에서는 평균이 계산된 뒤 탈락한다.

실행 순서 3초 암기 — 두문자 "프·웨·그·해·셀·오" / 동사 사슬 "읽·거·묶·거·고·줄"

프 FROM→웨 WHERE→그 GROUP BY→해 HAVING→셀 SELECT→오 ORDER BY
읽고→거르고(행)→묶고→거르고(그룹)→고르고→줄 세운다

동사 사슬 쪽이 실전에서 강하다 — "거르고"가 두 번 나오고 그 사이에 "묶고"가 끼어 있다는 것 하나만 기억하면, "두 번의 거르기는 판정 단위가 다르다(행 vs 그룹)"는 결론까지 저절로 따라온다.

2. 순서에서 곧바로 유도되는 에러 세 개

이 세 개를 "외운 규칙"이 아니라 "순서에서 나오는 필연"으로 설명할 수 있으면, 이 문항은 사실상 끝난 것이다.

2-1. WHERE에는 집계 함수를 쓸 수 없다 — ②가 ③보다 앞이기 때문

error 아직 태어나지 않은 것에 대해 질문했다
SELECT dept, avg(salary) FROM employee
WHERE avg(salary) >= 5000        -- ② 시점: 묶을 그룹 자체가 없다
GROUP BY dept;                -- ③ 그룹은 여기서 처음 생긴다

ERROR:  aggregate functions are not allowed in WHERE

avg(salary)는 "여러 행을 묶은 그룹"이 있어야 계산되는 값이다. 그런데 WHERE(②)가 실행되는 시점에는 GROUP BY(③)가 아직 오지 않았으므로 묶을 그룹 자체가 존재하지 않는다. 문법을 몰라서 나는 에러가 아니라 아직 태어나지 않은 것에 대해 질문했기 때문에 나는 에러다.

그리고 이것이 곧 HAVING의 존재 이유다 — 집계 결과를 거를 절이 따로 필요해서 ④가 있는 것이다

2-2. WHERE에도 HAVING에도 SELECT의 별칭을 쓸 수 없다 — ②·④가 ⑤보다 앞이기 때문

error HAVING에서 별칭 참조
SELECT dept, avg(salary) AS avg_sal
FROM employee
GROUP BY dept
HAVING avg_sal >= 5000;      -- ④ < ⑤

ERROR:  column "avg_sal" does not exist

-- AS avg_sal 이라는 이름은 SELECT(⑤)에서
-- 만들어진다. HAVING(④)은 그 이름을
-- 아직 들어본 적이 없다.
fix 집계식을 다시 쓰거나, 한 겹 감싼다
-- 처방 ① 집계식을 그대로 다시 쓴다
HAVING avg(salary) >= 5000

-- 처방 ② 별칭이 "이미 태어난" 바깥에서
--         일반 컬럼처럼 참조한다
WITH g AS (
  SELECT dept, avg(salary) AS avg_sal
  FROM employee GROUP BY dept
)
SELECT * FROM g
WHERE avg_sal >= 5000;   -- 바깥에선 그냥 컬럼

2-3. 그런데 ORDER BY에서는 별칭이 통한다 — ⑥이 ⑤보다 뒤이기 때문

ok 같은 별칭인데 여기서는 통과한다
SELECT dept, avg(salary) AS avg_sal FROM employee
GROUP BY dept
ORDER BY avg_sal DESC;          -- ⑥ > ⑤ 이므로 이름이 이미 있다

같은 별칭인데 HAVING에서는 에러고 ORDER BY에서는 통한다. 이 비대칭이 "SQL은 원래 그런 것"이 아니라 순서에서 나오는 필연이라는 것을 설명하는 순간, 면접관이 확인하려던 것은 확인된 것이다.

절별로 "무엇을 쓸 수 있는가" — 전부 실행 순서에서 유도된다 (PostgreSQL 기준)
절순서집계 함수SELECT 별칭이유 (순서로 유도)
FROM①✗✗행이 만들어지기 전/직후. 그룹도 별칭도 없다
WHERE②✗ aggregate functions are not allowed in WHERE✗ column … does not exist③보다 앞이라 그룹이 없고, ⑤보다 앞이라 별칭도 없다
GROUP BY③✗△여기서 그룹이 태어난다. 별칭은 PostgreSQL 확장으로 허용되나 입력 컬럼명과 겹치면 입력 컬럼 우선
HAVING④✓ 그러라고 있는 절✗그룹이 이미 있으므로 집계 가능. 그러나 ⑤보다 앞이라 별칭은 불가
SELECT⑤✓여기서 생성AS로 이름이 태어나는 자리
ORDER BY⑥✓✓ 표준⑤보다 뒤라 이름을 이미 알고 있다

여기서 3년차가 가장 자주 걸리는 지점 — "MySQL에서는 됐는데요?"

MySQL은 확장으로 HAVING에서 SELECT 별칭을 허용한다(WHERE는 MySQL도 불가). 그래서 MySQL에서 잘 돌던 HAVING avg_sal >= 5000이 PostgreSQL로 옮기면 column "avg_sal" does not exist로 죽는다 — 이식할 때 가장 먼저 마주치는 차이다.

암기 문장 — "별칭은 SELECT에서 태어난다. 그러니 SELECT보다 뒤인 ORDER BY만 그 이름을 안다."

3. 같은 "5000", 갈리는 답 — 7000 vs 5000

개발팀에 직원이 둘 있다. A = 3000, B = 7000 (평균 5000). 요구사항 두 개를 각각 SQL로 옮긴다.

요구 ① "연봉 5000 이상인 직원만 대상으로, 부서별 평균 연봉"
-- 집계에 들어갈 "재료"를 먼저 거른다 → WHERE
SELECT dept, avg(salary)
FROM employee
WHERE salary >= 5000     -- A(3000) 탈락
GROUP BY dept;

-- 재료 = {7000}  →  개발팀 평균 = 7000
요구 ② "부서별 평균 연봉이 5000 이상인 부서"
-- 집계를 끝낸 뒤 그 "결과"를 거른다 → HAVING
SELECT dept, avg(salary)
FROM employee
GROUP BY dept
HAVING avg(salary) >= 5000;   -- 5000 ≥ 5000 통과

-- 재료 = {3000, 7000}  →  개발팀 평균 = 5000

이 문서에서 인출해야 할 첫 번째 문장

WHERE로 옮기면 평균의 분모(재료)가 바뀐다 · HAVING으로 옮기면 분모는 그대로, 검사 시점만 바뀐다

"의미가 서로 바뀐다"까지만 말하면 절반이다. "각각 다른 틀린 숫자가 나온다"까지 말해야 완성이다.

4. 단계별 추적 — 행이 줄고, 묶이고, 그룹이 증발한다

두 팀짜리 예시로는 "그룹이 통째로 사라지는" 장면이 안 보인다. 부서 셋짜리 데이터로 1절의 여섯 단계를 실제로 밟아 본다. 돌릴 쿼리는 WHERE와 HAVING을 둘 다 쓴다.

data 원본 테이블 employee — 5행
 name | dept   | salary
------+--------+--------
 A    | 개발팀 |   3000
 B    | 개발팀 |   7000
 C    | 영업팀 |   4000
 D    | 영업팀 |   4500
 E    | 인사팀 |   6000
query 두 필터를 한 쿼리에
SELECT dept, avg(salary)
FROM employee
WHERE salary >= 5000            -- ② 행 필터
GROUP BY dept                   -- ③ 묶기
HAVING avg(salary) >= 6500;     -- ④ 그룹 필터

4-1. 같은 과정을 표로 — 판정이 어디서 어떻게 일어나는가

② WHERE 통과 행 — 행 하나씩 salary >= 5000 판정. 부서는 아직 관심 밖이다.
namedeptsalary판정남는가
A개발팀30003000 >= 5000 → 거짓탈락
B개발팀70007000 >= 5000 → 참통과
C영업팀4000거짓탈락
D영업팀4500거짓탈락
E인사팀6000참통과

5행 → 2행. 여기서 이미 영업팀은 재료가 한 행도 남지 않았다.

③ GROUP BY 결과 — 이 시점에 처음으로 avg(salary)라는 값이 존재하게 된다.
dept묶인 salarycountavg(salary)
개발팀{7000}17000
인사팀{6000}16000

2행 → 2그룹. 원본에 있던 영업팀은 목록에 없다.

④ HAVING 통과 그룹 — 이제 그룹 하나씩 avg(salary) >= 6500 판정.
deptavg(salary)판정남는가
개발팀70007000 >= 6500 → 참통과
인사팀60006000 >= 6500 → 거짓탈락

2그룹 → 1그룹 → ⑤ SELECT 출력 1행(개발팀 · 7000).

5. 언어화 템플릿 — 데이터 없이 "말로" 재현하기

숫자 추적은 되는데 말로 설명하려면 뭉개진다면, 문장 틀을 하나 고정해 두는 것이 답이다. 면접에서 나오는 질문은 대개 "바꿔 쓰면 어떻게 되는지 데이터 없이 말해보세요" 형태이기 때문이다.

세 칸짜리 문장 틀 — 이 칸만 채우면 어떤 변형 질문에도 문장이 무너지지 않는다

① 조건이 집계 전/후로 이동한다→ ② 재료(분모)가 바뀐다 / 재료는 그대로고 문턱 검사만 한다→ ③ 숫자가 X → Y로 바뀐다

핵심 어휘는 두 개다 — WHERE 이동은 "분모가 바뀐다", HAVING 이동은 "분모는 그대로, 검사 시점만 바뀐다".

요구 ①(WHERE로 써야 할 것)을 HAVING으로 잘못 쓰면

  • ① 조건이 집계 후로 밀린다
  • ② 걸러냈어야 할 A(3000)도 재료에 들어가 평균의 분모가 바뀐다
  • ③ 숫자가 7000 → 5000으로 내려간다

"저연봉을 뺀 평균"이라는 요구 자체가 증발한다 — 질문에 답하지 않은 숫자가 보고서에 실린다.

요구 ②(HAVING으로 써야 할 것)를 WHERE로 잘못 쓰면

  • ① 조건이 집계 전으로 당겨진다
  • ② 평균을 검사하는 게 아니라 재료를 미리 잘라낸다
  • ③ 숫자가 5000 → 7000으로 올라간다

게다가 전원이 5000 미만인 부서는 재료가 전부 사라져 결과에서 부서 자체가 증발한다(4절의 영업팀). "행이 안 나온다"가 아니라 "그룹이 안 생긴다"가 정확한 표현이다.

그대로 말하는 완성 답변 (약 20초) "WHERE는 집계에 들어갈 재료를 거르고, HAVING은 집계가 끝난 결과를 거릅니다. 그래서 ①번 조건을 HAVING으로 옮기면 걸러야 할 저연봉 행이 평균의 분모에 들어가 답이 7000에서 5000으로 내려가고, ②번 조건을 WHERE로 당기면 평균 검사 대신 재료를 미리 잘라 5000에서 7000으로 올라갑니다. 극단적으로는 재료가 전부 잘린 부서가 결과에서 통째로 사라집니다. 즉 의미가 서로 바뀌는 게 아니라 각각 다른 틀린 숫자가 나옵니다."

6. 세 번째 자리 — 집계 함수 안의 FILTER (WHERE …)

요구 ①과 ②를 한 화면에 같이 내야 한다면? 조건을 WHERE에 걸면 ②의 분모가 깨지고, HAVING에 걸면 ①의 분모가 안 좁혀진다. 조건을 둘 자리가 하나 더 있다 — 집계 함수 안이다.

good 분모가 다른 집계를 한 줄에 나란히
SELECT dept,
       avg(salary)                                AS avg_all,   -- 분모: 부서 전원
       avg(salary) FILTER (WHERE salary >= 5000)  AS avg_high,  -- 분모: 5000 이상만
       count(*)    FILTER (WHERE salary >= 5000)  AS n_high
FROM employee
GROUP BY dept
HAVING avg(salary) >= 5000;    -- 그룹 필터는 여전히 HAVING
4절의 5행 데이터로 실행한 결과 — 영업팀(avg 4250)은 HAVING에서 탈락
deptavg_allavg_highn_high
개발팀500070001
인사팀600060001
같은 일을 CASE로도 쓸 수 있지만 avg(CASE WHEN salary >= 5000 THEN salary END)도 같은 값을 낸다(CASE가 NULL을 돌려주면 avg가 그 행을 무시하기 때문). 다만 FILTER 쪽이 "이 집계의 분모를 바꾼다"는 의도가 문장에 그대로 드러난다.
CASE로 옮길 때의 함정 — count count(*)는 행을 세므로 count(*) FILTER (WHERE …)를 count(CASE WHEN … THEN 1 END)로 바꿔야 한다. count(*)를 그대로 두고 CASE만 씌우면 조건과 무관하게 전 행이 세어진다.
덤으로 알아둘 값 — 조건에 걸리는 행이 하나도 없으면? avg(...) FILTER (...)는 NULL을 돌려주고 count(...) FILTER (...)는 0을 돌려준다. 화면에 "0"으로 보여야 하는 자리라면 coalesce()가 필요하다 — "평균이 없다"와 "평균이 0이다"는 다른 사실이기 때문이다.

7. 성능 — "언제 거르느냐"의 문제

집계 함수가 안 들어간 조건은 WHERE와 HAVING 어디에 둬도 결과가 같을 수 있다. 그러나 논리적 비용은 다르다.

before 전 부서를 다 그룹핑한 뒤에 버린다
SELECT dept, avg(salary)
FROM employee
GROUP BY dept
HAVING dept = '개발팀';

-- 실행 순서대로라면 영업팀·인사팀·…
-- 모든 부서의 평균을 전부 계산하고,
-- 다 만든 결과에서 개발팀 한 줄만 남기고
-- 나머지를 버린다.
after 집계에 들어갈 행을 먼저 줄인다
SELECT dept, avg(salary)
FROM employee
WHERE dept = '개발팀'    -- dept 인덱스를 탈 수 있다
GROUP BY dept;

-- 개발팀 행만 읽어서
-- 그 행들만 그룹핑한다.

7-1. 왜 비싼가 — "그룹을 만드는 비용"이 어디서 나는지부터 본다

"HAVING이 더 비싸다"를 결론으로 외우면 응용이 안 된다. GROUP BY가 실제로 무슨 일을 하는지를 알면 비용의 출처가 보인다. DB가 그룹을 만드는 방법은 둘 중 하나다.

HashAggregate — 해시 방식
그룹 키를 키로 하는 해시 테이블을 만들고, 입력 행을 하나씩 흘려보내며 해당 그룹의 누적값(합계·건수)을 갱신한다. 자바로 치면 Map<String, Accumulator>에 computeIfAbsent로 담으며 도는 것.
GroupAggregate — 정렬 방식
입력을 그룹 키로 정렬한 뒤 같은 키가 이어지는 구간마다 집계를 마감한다. 인덱스 순서로 읽어 이미 정렬돼 있으면 정렬 비용이 공짜가 된다.

비용의 두 축 — 이것만 잡으면 어떤 변형에도 답이 나온다

축 ① 집계에 흘려보낸 입력 행 수 축 ② 만들어진 그룹 수

해시 방식이면 행 수가 해싱·누적 CPU를, 그룹 수가 해시 테이블의 메모리(work_mem, 넘치면 디스크 스필)를 결정한다. 정렬 방식이면 행 수가 정렬 비용 자체를 결정한다. WHERE는 축 ①을 직접 줄이고, HAVING은 축 ①을 하나도 못 줄인다.

같은 조건 dept = '개발팀'을 두 자리에 뒀을 때 — 두 번째 칸이 핵심이다
조건의 자리스캔이 읽는 행집계에 흘려보내는 행만드는 그룹버리는 그룹인덱스
HAVING dept = '개발팀'전 직원전 직원전 부서개발팀 외 전부못 탄다 (집계 후 값)
WHERE dept = '개발팀'개발팀만개발팀만1개없음탈 수 있다

핵심은 세 번째 칸이다. WHERE는 집계 앞에 있으므로 해시·정렬에 들어가는 입력 자체를 줄이고, HAVING은 집계 뒤에 있으므로 입력을 하나도 못 줄인 채 "다 만든 뒤에 버리는" 일만 한다. 버려질 그룹을 만드는 데 든 행 읽기·해싱·누적 비용은 이미 치른 뒤다.

마지막 칸도 순서에서 나온다 — HAVING이 다루는 값에는 인덱스가 있을 수 없다 인덱스는 테이블에 저장된 값의 정렬된 사본인데, avg(salary)는 저장된 값이 아니라 쿼리를 실행하는 중에 비로소 만들어지는 값이다. 반면 WHERE의 조건은 저장된 컬럼 값에 대한 것이라 인덱스를 탈 수 있다. "집계 결과에는 인덱스를 만들 수 없다"는 한 줄이 이 칸의 전부다.

8. 계획에서 확인 — 조건이 어느 노드의 Filter에 붙었나

PostgreSQL은 이 자리를 실행 계획에 그대로 보여 준다. WHERE 조건은 스캔 노드에 Index Cond 또는 Filter로, HAVING 조건은 집계 노드(HashAggregate/GroupAggregate)에 Filter로 찍힌다.

HAVING 집계 노드에 Filter가 붙는다
EXPLAIN (ANALYZE, BUFFERS)
SELECT dept, avg(salary) FROM employee
GROUP BY dept HAVING avg(salary) >= 5000;

 HashAggregate  (actual rows=3 loops=1)
   Group Key: dept
   Filter: (avg(salary) >= '5000'::numeric)
   Rows Removed by Filter: 5
   ->  Seq Scan on employee  (actual rows=1000 loops=1)
         Buffers: shared hit=12

↑ 전 행 1000개가 재료로 들어가 부서 8개를 만든 뒤
  5개를 버렸다. 페이지는 12개를 읽었다.
WHERE 스캔 노드에 Index Cond가 붙는다
EXPLAIN (ANALYZE, BUFFERS)
SELECT dept, avg(salary) FROM employee
WHERE dept = '개발팀' GROUP BY dept;

 GroupAggregate  (actual rows=1 loops=1)
   Group Key: dept
   ->  Index Scan using idx_employee_dept on employee
         (actual rows=120 loops=1)
         Index Cond: (dept = '개발팀'::text)
         Buffers: shared hit=4

↑ 인덱스로 120행만 뽑아 그룹 1개를 만들었다.
  페이지는 4개만 읽었다.

8-1. (가산점) 플래너는 집계 없는 HAVING 조건을 WHERE로 내려보낸다 가산점

그런데 7절의 before 쿼리(HAVING dept = '개발팀')를 실제로 EXPLAIN 해 보면 after와 똑같은 계획이 나온다. PostgreSQL 플래너가 HAVING 절의 조건 중 집계 함수도, volatile 함수(random() 같은)도 들어 있지 않은 것을 WHERE로 옮겨서 계획을 세우기 때문이다.

그렇다면 WHERE에 쓸 이유가 없어지는가? 아니다 — 이유가 두 겹이다 시니어 변별 ① 플래너가 내려 줄 수 있는 조건은 한정돼 있고, 그 판단은 내가 아니라 플래너가 한다 — 조건에 집계가 섞이는 순간 아무도 못 내린다.
② 기대는 것과 의도를 코드로 표현하는 것은 다르다 — "행 조건은 WHERE, 그룹 조건은 HAVING"으로 자리를 지키면 성능 이전에 쿼리를 읽는 사람에게 의도가 전달된다. 최적화가 지워 주는 것은 비용 차이지 의미 차이가 아니다.

판단 기준은 결국 하나다

조건식 안에 집계 함수(또는 집계 결과)가 있는가? — 있으면 HAVING밖에 못 쓰고, 없으면 WHERE에 두는 것이 원칙

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

논리적 실행 순서 6단계?
프·웨·그·해·셀·오 = FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. 동사로는 읽·거·묶·거·고·줄.
두 절 한 줄 정의?
WHERE = 개별 행 조건(집계에 들어갈 재료를 거른다) · HAVING = 그룹 조건(집계가 끝난 결과를 거른다).
WHERE에 집계 함수를 못 쓰는 이유?
②가 ③보다 앞이라 묶을 그룹 자체가 없다. 문법 문제가 아니라 아직 태어나지 않은 것에 질문한 것. aggregate functions are not allowed in WHERE.
HAVING에 별칭을 못 쓰는 이유? ORDER BY는?
④ < ⑤라 이름이 아직 없다(column "avg_sal" does not exist). ⑥ > ⑤인 ORDER BY는 통한다. PG는 GROUP BY도 확장으로 허용(입력 컬럼 우선).
7000 vs 5000의 원인 한 문장?
WHERE는 분모(재료)를 바꾸고, HAVING은 분모 그대로 문턱만 검사한다.
조건을 WHERE로 옮길 때의 부작용?
재료가 전부 잘린 그룹은 결과에서 통째로 증발한다(영업팀). "행이 안 나온다"가 아니라 "그룹이 안 생긴다".
판정 단위 비교?
WHERE는 행 5개를 5번, HAVING은 그룹 2개를 2번 판정한다. 도중에 단위가 바뀐다는 것이 핵심.
세 번째 필터 자리?
avg(x) FILTER (WHERE …) — 집계 함수 하나의 재료만 거른다. 같은 그룹 안에서 분모가 다른 집계를 나란히.
GROUP BY 비용의 두 축?
흘려보낸 입력 행 수(해싱·누적·정렬 CPU)와 만든 그룹 수(해시 테이블 메모리 work_mem, 넘치면 스필). WHERE는 축 ①을 직접 줄인다.
성능 규칙 한 줄?
집계 함수가 없는 조건은 WHERE에. 집계 앞에서 입력 행을 줄이고 인덱스를 탈 수 있다.
계획에서 자리 확인?
WHERE = 스캔 노드의 Index Cond/Filter · HAVING = 집계 노드의 Filter + Rows Removed by Filter(= 만들었다 버린 그룹 수).
플래너의 내려보내기?
집계·volatile 함수가 없는 HAVING 조각은 WHERE로 내려간다. 그래도 WHERE에 쓰는 이유 — 내려 줄 수 있는 조건이 한정적이고, 최적화는 비용 차이를 지울 뿐 의미 차이는 못 지운다.
GROUP BY 없이 HAVING만?
가능 — 테이블 전체가 하나의 암묵적 그룹. 통과하면 1행, 아니면 빈 결과. 실무에서 보면 GROUP BY 누락 실수인지 먼저 의심한다.
MySQL 대조 4지점?
별칭(MySQL은 HAVING 허용) · ONLY_FULL_GROUP_BY(꺼져 있으면 조용히 아무 값) · FILTER 없음(SUM(CASE WHEN …)) · 계획에 HAVING 위치가 안 보임.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

①과 ②의 조건을 서로 바꿔 쓰면 결과가 어떻게 되는지, 데이터 없이 말로만 설명해보세요. 필수힌트: 세 칸짜리 문장 틀 — 이동 → 분모 → 숫자

"조건이 집계 전/후로 이동한다 → 분모가 바뀌거나 / 분모는 그대로고 검사 시점만 바뀐다 → 숫자가 달라진다"로 답한다.

①을 HAVING으로 밀면 걸러냈어야 할 저연봉 행이 평균의 분모에 들어가 숫자가 내려간다(7000 → 5000). ②를 WHERE로 당기면 평균 검사 대신 재료를 미리 잘라 숫자가 올라가고(5000 → 7000), 전원이 기준 미달인 부서는 결과에서 통째로 증발한다.

"의미가 서로 바뀐다"가 아니라 "각각 다른 틀린 숫자가 나온다"까지 말해야 완성이다
WHERE 절에 avg(salary) >= 5000을 쓰면 왜 에러인가요? 필수힌트: "문법상 안 된다"가 아니라 "무엇이 아직 없는가"로 답한다

WHERE가 실행되는 시점에는 그룹이 아직 없기 때문이다. WHERE는 행을 하나씩 보며 남길지 버릴지 정하는 단계인데, avg(salary)는 "여러 행을 묶은 그룹"이 있어야 계산되는 값이다. 논리적 실행 순서에서 WHERE(②)는 GROUP BY(③)보다 앞이므로, 아직 존재하지 않는 것에 대한 질문이라 문법 이전에 논리적으로 성립하지 않는다 — 그래서 표준이 금지하고, PostgreSQL은 ERROR: aggregate functions are not allowed in WHERE로 거절한다.

거꾸로 이 사실이 HAVING의 존재 이유다 — 집계 결과를 거를 절이 따로 필요해서 HAVING이 있는 것이다. 여기까지 이어 붙이면 "외운 답"이 아니라 "유도한 답"이 된다.

집계 함수가 없는 조건은 WHERE와 HAVING 어디 둬도 결과가 같은데, 그래도 WHERE에 둬야 하는 이유는? 시니어 변별힌트: 비용 한 겹, 의미 한 겹. 그리고 "플래너가 내려 준다"까지 스스로 꺼낸다

먼저 결과가 같아지는 조건부터 짚는다 — 주로 GROUP BY 컬럼 자체에 대한 조건일 때다(그룹핑 전에 행을 버리나 그룹핑 후에 그 그룹을 버리나 남는 그룹이 같다).

① 비용: WHERE는 집계 앞에 있어 해시·정렬에 흘려보내는 입력 행 자체를 줄이고 인덱스를 탈 수 있지만, HAVING은 버릴 그룹까지 전부 만든 뒤에 거른다(계획의 Rows Removed by Filter가 그 증거다).

② 의미: 행 조건은 WHERE, 그룹 조건은 HAVING이라는 자리 약속이 지켜져야 읽는 사람이 쿼리의 의도를 오해하지 않는다.

여기에 플래너 이야기를 스스로 꺼내면 한 단계 올라간다 — PostgreSQL 플래너는 집계 없는 HAVING 조건을 WHERE로 내려 주므로 이 예에서는 실제 계획이 같아진다(조건이 HashAggregate의 Filter가 아니라 스캔 노드의 Index Cond에 붙은 것으로 확인). 그러나 그것은 "내려 줄 수 있는 조건"에 한정된 플래너의 판단이지 내가 보장한 것이 아니다.

HAVING에서 SELECT의 별칭(alias)이나 집계식을 쓸 수 있나요? 함정힌트: 둘을 갈라 답하고, 별칭이 통하는 자리를 정확히 열거한다

집계식(avg(salary) >= 5000)은 당연히 가능하다 — 그러라고 있는 절이다.

별칭은 PostgreSQL에서는 불가다. 논리 순서상 SELECT(⑤)가 HAVING(④)보다 뒤라서 표준 SQL이 허용하지 않고, PostgreSQL은 표준대로 ERROR: column "avg_sal" does not exist로 거절한다. WHERE도 마찬가지 — SELECT보다 한참 앞이라 별칭이 아직 태어나지도 않았다.

PostgreSQL에서 SELECT 별칭이 통하는 자리는 ORDER BY(표준)와 GROUP BY(PostgreSQL 확장 — 입력 컬럼명과 겹치면 입력 컬럼이 우선)뿐이다. 별칭으로 거르고 싶으면 집계식을 다시 쓰거나, 서브쿼리·CTE로 한 번 감싸서 그 바깥 WHERE에서 일반 컬럼으로 참조한다.

MySQL 대조: MySQL은 확장으로 HAVING에서 별칭을 허용한다(WHERE는 MySQL도 불가). MySQL에서 돌던 HAVING avg_sal >= 5000이 PostgreSQL로 옮기면 에러가 나는 것이 이식 때 가장 먼저 마주치는 차이다.

WHERE와 HAVING을 한 쿼리에 같이 써도 되나요? 그러면 판정이 몇 번 일어나나요? 필수힌트: 4절의 5행 예시를 숫자로 그대로 재생한다

같이 쓴다. 오히려 그게 정상적인 형태다 — 행 조건과 그룹 조건은 서로 다른 질문이기 때문이다. 실행은 WHERE(②)가 먼저, HAVING(④)이 나중이고 그 사이에 GROUP BY(③)가 있다.

판정 횟수로 말하면 차이가 선명해진다. 5행/3부서 데이터에 WHERE salary >= 5000 + HAVING avg(salary) >= 6500을 걸면 — WHERE는 행 5개를 5번 판정해 2행을 남기고, GROUP BY가 2그룹을 만들고, HAVING은 그룹 2개를 2번 판정해 1그룹을 남긴다.

여기서 한 걸음 더 — WHERE가 앞에서 행을 줄이면 HAVING이 판정할 그룹 수도 함께 줄어든다. 즉 두 절은 경쟁 관계가 아니라 WHERE가 앞에서 일을 덜어 주는 관계다. "WHERE로 가능한 것은 WHERE에서 끝낸다"가 여기서도 그대로 성립한다.

WHERE salary > (SELECT avg(salary) FROM employee)는 WHERE 안에 avg()가 있는데 왜 에러가 아닌가요? 함정힌트: 그 avg()가 "누구의" 집계인지를 따진다

그 avg()는 바깥 쿼리의 집계가 아니라 서브쿼리라는 별개 쿼리의 집계이기 때문이다. 서브쿼리는 자기 안에서 FROM → … → SELECT를 다 마치고 하나의 스칼라 값이 된다. 바깥 WHERE 입장에서 그 자리는 그냥 상수 하나이므로 "그룹이 없는데 집계를 요구한다"는 문제가 애초에 생기지 않는다.

금지되는 것은 "이 쿼리 레벨의 집계"를 WHERE에서 요구하는 것이다. WHERE avg(salary) >= 5000은 바깥 쿼리 자신의 그룹을 요구하므로 ③보다 앞이라 성립할 수 없다.

실무 감각까지 얹으면 — 이 패턴은 "전체 평균보다 많이 받는 직원"처럼 기준값을 먼저 계산해 상수로 쓰는 전형적인 형태다. 다만 서브쿼리가 바깥 행마다 다시 평가되는 상관 서브쿼리가 되면 비용이 완전히 달라지므로, 계획에서 InitPlan(한 번만 계산)인지 SubPlan(행마다 계산)인지를 확인하는 습관이 필요하다.

중복 이메일을 찾을 때 GROUP BY email HAVING count(*) > 1을 쓰잖아요 — WHERE로는 왜 못 하나요? 필수힌트: count(*)가 "무엇에 대한 값"인지 한 문장으로

count(*)는 행 하나에 대한 값이 아니라 그룹에 대한 값이기 때문이다. "이 이메일이 몇 번 나왔는가"는 같은 이메일 행을 다 모아 봐야 알 수 있고, 그 모으기가 GROUP BY(③)다. WHERE(②) 시점에는 지금 보고 있는 행 하나밖에 없으므로 "몇 번 나왔는가"를 물을 대상 자체가 없다.

그래서 이 관용구는 두 절의 차이를 보여주는 가장 짧은 예시이기도 하다 — "중복이다"라는 판정은 행이 아니라 그룹의 성질"이라는 문장 하나로 정리된다.

한 걸음 더 — HAVING count(*) > 1과 HAVING count(email) > 1은 다를 수 있다. count(*)는 행을 세지만 count(email)은 email이 NULL인 행을 빼고 센다. 그리고 GROUP BY는 NULL끼리 한 그룹으로 묶으므로, NULL 그룹에서 두 표현의 값이 갈린다.

HAVING에 집계도 아니고 GROUP BY에도 없는 컬럼(예: HAVING name = 'A')을 쓰면 어떻게 되나요? 함정힌트: 에러 메시지가 곧 이유다

에러다 — PostgreSQL은 ERROR: column "employee.name" must appear in the GROUP BY clause or be used in an aggregate function으로 거절한다.

이유도 순서에서 나온다. HAVING(④) 시점에 남아 있는 것은 그룹이고, 한 그룹 안에는 name이 여러 개 들어 있을 수 있다. "그 그룹의 name"이라는 값은 유일하게 정해지지 않는다 — 그래서 그룹 키에 넣어 하나로 만들거나(GROUP BY), 여러 값을 하나로 접는 집계 함수를 씌우거나(max(name), string_agg(name, ',')) 둘 중 하나를 요구한다. SELECT 절에서 나는 에러와 정확히 같은 규칙이다.

MySQL 대조가 여기서 위험해진다 — ONLY_FULL_GROUP_BY가 꺼져 있으면 MySQL은 그룹 안의 아무 값이나 조용히 돌려준다. 에러 없이 틀린 숫자가 그대로 나가는 경로이므로, PostgreSQL의 엄격함은 불편이 아니라 안전장치로 읽는 것이 맞다.

WHERE 조건이 어차피 인덱스를 못 타는 상황이면(둘 다 풀스캔) HAVING과 성능이 같아지는 것 아닌가요? 시니어 변별힌트: 이득이 사라지는 게 아니라 "이득이 나는 층"이 바뀐다

아니다. 이득의 층이 바뀔 뿐 이득은 남는다. 인덱스를 못 타면 스캔 단계에서 읽는 페이지 수는 같아진다(둘 다 전 행을 읽는다). 그러나 집계 노드에 흘려보내는 행 수는 여전히 WHERE 쪽이 적다.

7절의 두 축으로 옮기면 정확히 말할 수 있다 — 축 ①(입력 행 수)이 줄어 해싱·누적 CPU나 정렬 비용이 줄고, 축 ②(그룹 수)가 줄어 해시 테이블이 작아진다. 특히 그룹 수가 많아 work_mem을 넘겨 디스크로 스필하던 쿼리라면, WHERE로 입력을 줄이는 것만으로 스필이 사라져 체감 차이가 크게 난다.

정리하면 — 인덱스는 WHERE가 가져다주는 이득의 전부가 아니라 하나다. "인덱스를 못 타니 의미 없다"는 말은 I/O 층만 보고 CPU·메모리 층을 안 본 것이다.

GROUP BY 없이 HAVING만 쓸 수 있나요? 가산점힌트: 된다. 그때 "그룹"은 무엇인가?

가능하다(PostgreSQL도 허용) — 이때는 테이블 전체가 하나의 암묵적 그룹이 된다.

SELECT avg(salary) FROM employee HAVING avg(salary) >= 5000은 전체 평균이 5000 이상이면 한 행, 아니면 빈 결과를 돌려준다.

"전사 평균이 기준을 넘을 때만 리포트 행을 만든다" 같은 조건부 집계에 쓸 수 있지만 드문 형태라, 실무에서 마주치면 의도된 것인지(GROUP BY 누락 실수가 아닌지) 먼저 의심하는 게 맞다.

FILTER (WHERE …)는 WHERE와 뭐가 다른가요? 그냥 WHERE를 쓰면 안 되나요? 가산점힌트: "거르는 범위"가 쿼리 전체인지 집계 하나인지

거르는 범위가 다르다. WHERE는 쿼리 전체의 재료를 거르므로 그 뒤의 모든 집계가 같은 분모를 갖게 된다. FILTER는 그 집계 함수 하나의 재료만 거르므로, 같은 그룹 안에서 분모가 다른 집계를 나란히 놓을 수 있다.

그래서 "부서 전원 평균"과 "5000 이상만의 평균"을 한 줄에 같이 내야 하는 요구는 WHERE로는 표현할 수 없다 — WHERE를 걸면 전원 평균이 깨지고, 안 걸면 고연봉 평균이 안 좁혀진다.

주의 두 가지 — ① 조건에 맞는 행이 하나도 없으면 avg … FILTER는 NULL(count는 0)이다. ② MySQL에는 FILTER가 없어 SUM(CASE WHEN … THEN … END)/COUNT(IF(…))로 쓴다. 같은 일을 PostgreSQL에서 CASE로 쓸 수도 있지만, FILTER 쪽이 "이 집계의 분모를 바꾼다"는 의도가 문장에 드러난다.

HAVING에 그룹 컬럼 조건과 집계 조건이 AND로 섞여 있으면 플래너는 어떻게 하나요? 가산점힌트: 조건 전체를 통째로 판단하지 않는다

조건을 AND 조각 단위로 나눠 각각 판단한다. 집계 함수도 volatile 함수도 없는 조각은 WHERE로 내려보내고, 집계가 섞인 조각은 집계 노드에 남긴다. 즉 HAVING dept = '개발팀' AND avg(salary) >= 5000이면 앞 조각은 스캔 노드로, 뒤 조각은 집계 노드의 Filter로 간다.

확인 방법은 하나 — EXPLAIN에서 조건이 어느 노드에 붙어 있는지를 본다. 스캔 노드의 Index Cond/Filter에 있으면 내려간 것이고, HashAggregate/GroupAggregate의 Filter에 남아 있으면 안 내려간 것이다.

그래도 손으로 옮겨 쓰는 이유는 8-1절과 같다 — 플래너가 내려 준다는 사실에 기대는 것과 "행 조건은 WHERE"라고 자리로 의도를 표현하는 것은 다르다.

MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 네 지점 — 별칭 · 그룹 밖 컬럼 · 집계 안 조건 · 계획

① HAVING의 SELECT 별칭 — MySQL은 HAVING avg_sal >= 5000을 허용하지만 PostgreSQL은 column "avg_sal" does not exist 에러다. PostgreSQL에서 별칭이 통하는 자리는 ORDER BY와 GROUP BY뿐이다.

② GROUP BY에 없는 컬럼을 SELECT — PostgreSQL은 항상 에러(must appear in the GROUP BY clause or be used in an aggregate function; 예외는 PK로 그룹핑했을 때의 함수 종속 인정)지만, MySQL은 ONLY_FULL_GROUP_BY가 꺼져 있으면 그룹 안의 아무 값이나 조용히 돌려준다 — "틀린 숫자"가 에러 없이 나가는 경로다.

③ 집계 안 조건 — PostgreSQL은 FILTER (WHERE …), MySQL은 없어서 SUM(CASE WHEN …)/COUNT(IF(…))로 쓴다.

④ 계획에서 위치 확인 — PostgreSQL은 HAVING이 집계 노드의 Filter로, WHERE가 스캔 노드의 Filter/Index Cond로 찍혀 눈에 보인다. MySQL의 표 형식 EXPLAIN에는 Using temporary 정도만 남아 HAVING의 위치가 안 보이고, 트리 형식은 EXPLAIN ANALYZE에서야 읽을 수 있다.

한 줄 요약
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY의 실행 순서 위에서, WHERE는 집계에 들어갈 재료(행)를 거르고 HAVING은 집계가 끝난 결과(그룹)를 거른다 — WHERE가 GROUP BY보다 앞이라 집계 함수를 못 쓰고, 둘 다 SELECT보다 앞이라 별칭을 못 쓴다. 같은 조건이라도 자리가 바뀌면 분모가 바뀌어 다른 숫자가 나오고(7000 vs 5000), 재료가 다 잘린 부서는 결과에서 통째로 증발하며, 틀린 숫자는 틀린 비즈니스 판단이 된다. 집계 함수 안의 FILTER (WHERE …)는 그룹 안에서 분모만 따로 바꾸는 세 번째 자리다. 집계 함수가 없는 조건은 WHERE에 — 집계 전에 해시·정렬로 흘려보낼 행 자체를 줄이고 인덱스를 탈 수 있으며, HAVING은 버릴 그룹까지 다 만든 뒤에야 거르기 때문이다. PostgreSQL 계획에서는 WHERE가 스캔 노드의 Index Cond/Filter로, HAVING이 집계 노드의 Filter(+ Rows Removed by Filter)로 찍혀 자리가 눈에 보이고, 플래너가 집계 없는 HAVING 조건을 WHERE로 내려 주더라도 그것은 비용 차이를 지울 뿐 의도 표현을 대신하지 않는다.
