WHERE vs HAVING — 같은 "5000"인데 숫자가 갈리는 이유를 말로 재현한다

원본: interview-questions/knowledge/04-rdb-sql/07-where-vs-having.md

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "WHERE절과 HAVING절의 차이는?"
논리적 실행 순서로 고정한다 — FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY. WHERE는 집계에 들어갈 재료를 거르고, HAVING은 집계가 끝난 결과를 거른다. 그래서 같은 테이블에 같은 "5000" 조건을 걸어도 위치에 따라 답이 7000 vs 5000으로 갈린다 — WHERE로 옮기면 평균의 분모(재료)가 바뀌고, HAVING으로 옮기면 재료는 그대로인 채 완성된 평균이 문턱을 넘는지만 본다. 이 차이를 데이터 없이 말로 재현하는 것이 이 문서의 훈련 목표이고, 성능 축(같은 조건이면 WHERE — 집계 전에 행을 줄이고 인덱스를 탄다)까지 얹으면 완성이다.
출제 의도 — 문법 암기가 아니라 "조건의 위치가 숫자를 바꾼다"를 추적하고, 그것을 말로 설명할 수 있는가
집계 전/후 필터의 구분이 안 되면 통계 쿼리에서 틀린 숫자를 만들고, 틀린 숫자는 틀린 비즈니스 판단으로 이어진다. "HAVING은 GROUP BY 뒤에 쓴다"가 아니라, 구체 데이터로 숫자를 추적할 수 있는지 — 그리고 데이터 없이도 그 추적을 말로 재현할 수 있는지를 본다.

면접 기록: 개념·절 배치·미니 데이터 계산(7000 / 5000, 경계값 포함) 모두 자력 — 평가 상. 유일한 흠은 "바꿔 쓰면 어떻게 되나"를 데이터 없이 말할 때 요청 2는 요청 1처럼 나온다로 뭉개진 것. 지식이 아니라 언어화 습관의 문제라, 이 페이지의 무게는 §3 "30초 스크립트"와 §4 "성능 축"에 실려 있다.

  • 1실행 순서 파이프라인 — 두 절의 자리
  • 2숫자 추적 — A=3000, B=7000이 두 길을 지난다
  • 3말로 재현하는 30초 스크립트
  • 4성능 축 — 같은 조건이면 WHERE
  • 5함정 카드 3종 + 실행 순서 암기 드릴
  • 6꼬리질문 셀프 테스트
  • ★한 줄 요약

1. 실행 순서 위에 올려놓으면 두 절은 헷갈릴 수 없다

정의는 한 줄이면 된다 — WHERE는 개별 행에 대한 조건, HAVING은 그룹(집계 결과)에 대한 조건. 이게 왜 그럴 수밖에 없는지는 두 절을 SQL의 논리적 실행 순서 위에 올려놓으면 저절로 나온다. GROUP BY가 행을 묶어 집계를 만드는 순간이 경계다 — 그 왼쪽에는 그룹이 없고, 오른쪽에는 개별 행이 없다.

순서를 외우는 것이 목적이 아니다 — 두 절의 자리가 정해지면 "무엇을 걸 수 있고 무엇을 못 거는지"가 전부 따라 나온다(§5 규칙 4개).
WHERE 집계 전 · 행 필터
  • 시점 — FROM 직후, 그룹이 만들어지기 전
  • 대상 — 테이블에서 막 읽어온 개별 행 하나하나
  • 집계 함수 — ✕ 평균을 낼 그룹이 아직 없다
  • 효과 — 집계에 들어갈 재료 자체가 바뀐다 → 평균의 분모가 바뀐다
  • 인덱스 — 행 단위 조건이라 탈 수 있다
HAVING 집계 후 · 그룹 필터
  • 시점 — GROUP BY로 집계가 끝난 뒤
  • 대상 — "부서별 평균" 같은 집계 결과 행(그룹)
  • 집계 함수 — ○ 그러라고 있는 절이다
  • 효과 — 재료는 그대로, 완성된 그룹 중 어느 것을 남길지만 정한다
  • 인덱스 — 집계 결과는 실행 중 만들어지는 값이라 인덱스가 있을 수 없다
비유로 고정 — 요리 과정의 두 번의 "버린다"
재료를 버리면 요리의 맛(평균)이 바뀌고, 완성품을 버리면 상에 오르는 접시 수(그룹 수)만 바뀐다.
조리 전
재료 손질 WHERE

상한 재료를 조리 전에 골라낸다. 냄비에 들어가는 재료가 달라지니 요리의 맛 자체가 바뀐다.

= 평균의 분모가 바뀐다. 3000을 빼면 개발팀 평균이 5000에서 7000이 된다.

조리 후
완성 요리 검수 HAVING

다 만든 요리를 맛보고 기준 미달인 접시를 상에서 내린다. 요리 자체는 이미 완성돼 있어 접시 수만 바뀐다.

= 분모는 그대로, 완성된 평균 5000이 문턱을 넘는지만 본다. 남은 접시의 맛은 그대로 5000.

2. 숫자 추적 — A=3000, B=7000이 두 길을 지난다

개발팀에 직원이 둘 있다: A = 3000, B = 7000(평균 5000). 같은 테이블에 같은 "5000"을 거는데, 요구가 다르면 조건의 자리가 다르고, 자리가 다르면 분모가 다르다. 아래 도식에서 각 단계의 값이 어떻게 바뀌는지를 손가락으로 따라가 본다 — §3의 스크립트는 이 그림을 말로 읽은 것일 뿐이다.

요구 ① — "5000 이상인 직원만 대상으로" → 재료를 거른다 → WHERE
SELECT dept, AVG(salary)
FROM   employee
WHERE  salary >= 5000     -- A(3000) 탈락, B(7000)만 재료로
GROUP  BY dept;
-- 개발팀 평균 = 7000 (분모 1)
요구 ② — "평균이 5000 이상인 부서" → 결과를 거른다 → HAVING
SELECT dept, AVG(salary)
FROM   employee
GROUP  BY dept
HAVING AVG(salary) >= 5000;  -- 평균 5000 ≥ 5000 → 통과
-- 개발팀 평균 = 5000 (분모 2)

이것이 "집계 전/후 구분 실패 → 틀린 숫자 → 틀린 비즈니스 판단"의 실체다. 경영진이 "개발팀 평균 연봉"이라고 받아든 숫자가 7000이냐 5000이냐에 따라 연봉 정책 판단이 갈린다. 그러면 바꿔 쓰면 어떻게 되는가 — 각각 다른 틀린 숫자가 나온다.

①을 HAVING으로 잘못 쓰면 — 7000이 나와야 하는데 5000
SELECT dept, AVG(salary)
FROM   employee
GROUP  BY dept
HAVING AVG(salary) >= 5000;  -- 조건이 집계 "후"로 밀렸다
-- A(3000)도 재료에 들어가 분모가 2 → 평균 5000
-- "저연봉을 뺀 평균"이라는 요구 자체가 증발
②를 WHERE로 잘못 쓰면 — 5000이 나와야 하는데 7000
SELECT dept, AVG(salary)
FROM   employee
WHERE  salary >= 5000     -- 조건이 집계 "전"으로 당겨졌다
GROUP  BY dept;
-- 평균을 검사하는 게 아니라 재료를 미리 잘라냄
-- A(3000) 빠진 채 평균 7000 → "팀 전체 평균이 기준을
-- 넘는가"와는 다른 숫자를 보고하게 된다
재료가 전부 사라지면 그룹이 "0"이나 "NULL"이 되는 게 아니라 — 아예 안 생긴다
②를 WHERE로 당겼을 때 전원이 5000 미만인 부서는 WHERE에서 모든 행이 탈락한다. 그러면 GROUP BY가 묶을 재료가 없어 그 부서의 그룹 자체가 만들어지지 않고, 결과에서 부서가 통째로 증발한다. "평균 NULL인 행이 하나 나오겠지"라고 기대하면 리포트에서 부서가 사라진 이유를 못 찾는다.

2-1. 데이터를 하나만 더 — 숫자만 다른 게 아니라 "부서가 사라지거나 나타난다" 추가

개발팀은 어느 쪽으로 틀려도 개발팀 행은 남고 숫자만 달라졌다. 부서 안에 기준 위·아래가 섞여 있으면 더 극적이다 — 인사팀: P = 2000, Q = 6000(평균 4000)을 같은 두 요구에 넣어 본다.

인사팀 (2000, 6000)정답 쿼리의 결과조건 자리를 바꾼 오답의 결과틀린 방식
요구 ①
5000 이상 직원만으로 부서별 평균		 인사팀 6000
WHERE → Q(6000)만 재료, 분모 1		 인사팀 없음
HAVING → 평균 4000 < 5000 → 그룹 탈락		 있어야 할 부서가 사라진다
요구 ②
평균이 5000 이상인 부서		 인사팀 없음
HAVING → 평균 4000 < 5000 → 탈락		 인사팀 6000
WHERE → P 탈락, Q만 남아 평균 6000		 없어야 할 부서가 나타난다

그래서 "의미가 서로 바뀐다"는 답은 절반이다 — 실제로는 행이 생기고 없어지며 각각 다른 틀린 숫자가 나온다. 이 표의 네 칸을 머릿속으로 다시 채울 수 있으면 §3의 스크립트는 저절로 나온다.

3. 말로 재현하는 30초 스크립트

면접 기록의 유일한 흠은 여기였다 — 숫자 추적은 정확했는데, 데이터 없이 "바꿔 쓰면 어떻게 되나"를 말하려니 요청 2는 요청 1처럼 나온다로 뭉개졌다. 고치는 방법은 지식 추가가 아니라 문장 틀을 하나 고정하는 것이다. 아래 스크립트를 소리 내어 두 번 읽으면 끝난다.

30초 스크립트 — 데이터 없이, 이 순서대로
  1. 0–5초
    실행 순서는 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY입니다. WHERE는 집계 전에 행을 거르고, HAVING은 집계 후에 그룹을 거릅니다.
  2. 5–15초
    개발팀에 3000·7000 두 명이 있다고 하면 — WHERE salary >= 5000이면 3000이 재료에서 빠져 평균은 7000이 되고, HAVING AVG(salary) >= 5000이면 두 명이 다 재료로 들어가 평균 5000이 나오고, 그 5000이 문턱을 넘는지만 봅니다.
  3. 15–22초
    같은 5000인데 위치에 따라 분모가 1이냐 2냐로 갈려 7000 vs 5000이 됩니다. 조건을 서로 바꿔 쓰면 각각 다른 틀린 숫자가 나옵니다 — ①을 HAVING으로 밀면 분모에 저연봉이 들어가 숫자가 내려가고, ②를 WHERE로 당기면 평균 검사 대신 재료를 잘라 숫자가 올라갑니다.
  4. 22–30초
    그래서 집계 함수가 없는 조건은 WHERE에 둡니다 — 집계 전에 행을 줄여 인덱스를 타고, HAVING은 버릴 그룹까지 다 만든 뒤에야 거르기 때문입니다.

3-1. 언어화 템플릿 — 세 칸만 채우면 문장이 무너지지 않는다

칸 1 · 이동조건이 집계 [전 / 후]로 이동한다
칸 2 · 메커니즘[분모(재료)가 바뀐다 / 분모는 그대로, 문턱 검사만 한다]
칸 3 · 숫자숫자가 [X → Y]로 바뀐다

채운 예 두 개 — 이 두 문장을 통째로 외운다:

①을 HAVING으로조건이 집계 후로 밀린다
→A(3000)도 재료에 들어가서 분모가 바뀐다
→7000 → 5000. "저연봉을 뺀 평균"이라는 요구가 증발
②를 WHERE로조건이 집계 전으로 당겨진다
→평균을 검사하는 게 아니라 재료를 미리 잘라낸다
→5000 → 7000. 전원 미달 부서는 결과에서 증발
WHERE 쪽으로 옮기면
"분모가 바뀐다"
재료(행)가 달라지므로 평균 자체가 다른 값이 된다. 재료가 다 사라지면 그룹도 사라진다.
HAVING 쪽으로 옮기면
"분모는 그대로, 검사 시점만 바뀐다"
재료는 전부 들어간 채 완성된 평균이 문턱을 넘는지만 본다. 남는 그룹의 값은 변하지 않는다.
❌ 면접에서 나온 답 — 뭉개진 문장
요청 2는 요청 1처럼 나온다.

"의미가 서로 바뀐다"를 말하려던 것이지만, 숫자가 달라진다는 핵심이 문장에 없다. 면접관은 "그래서 몇이 나오는데요?"를 다시 묻게 된다.

✅ 완성된 답 — 템플릿 세 칸을 채운 문장
②를 WHERE로 쓰면 조건이 집계 전으로 당겨져서, 평균을 검사하는 대신 3000을 재료에서 잘라내 분모가 2에서 1로 바뀌고, 5000이 아니라 7000이 나옵니다. 반대로 ①을 HAVING으로 밀면 3000이 분모에 들어가 7000이 아니라 5000이 나오고요 — 서로 바뀌는 게 아니라 각각 다른 틀린 숫자가 나옵니다.

4. 성능 축 — 같은 조건이면 WHERE: 성능은 "언제 거르느냐"의 문제

집계 함수가 안 들어간 조건은 WHERE와 HAVING 어디에 둬도 결과가 같을 수 있다. 그러나 비용은 다르다 — HAVING은 그룹핑·집계가 전부 끝난 뒤에야 실행되므로, 거기에만 조건을 두면 버릴 그룹을 만드는 비용을 이미 치른 뒤다.

before — 결과는 맞지만, 전 부서를 다 그룹핑한 뒤에 버린다
SELECT dept, AVG(salary)
FROM   employee
GROUP  BY dept
HAVING dept = '개발팀';   -- 집계가 끝난 뒤에야 거른다
-- 영업팀·인사팀·… 모든 부서의 평균을 일단 전부 계산하고,
-- 다 만든 결과에서 개발팀 한 줄만 남기고 나머지를 버린다.
after — 집계에 들어갈 행을 먼저 줄인다
SELECT dept, AVG(salary)
FROM   employee
WHERE  dept = '개발팀'    -- dept 인덱스를 탈 수 있다
GROUP  BY dept;
-- 개발팀 행만 읽어서 그 행들만 그룹핑한다.
-- 다른 부서는 읽지도, 묶지도, 버리지도 않는다.

4-1. 실행 계획으로 보면 — 개념적 EXPLAIN 대비

항목before — HAVING dept = '개발팀'after — WHERE dept = '개발팀'
접근 방식 (type)ALL / index — 전 행을 훑는다ref — idx_dept로 개발팀 행만 찾아간다
사용 인덱스 (key)NULL — 조건이 그룹핑 뒤에 걸리므로 인덱스가 끼어들 자리가 없다idx_dept
읽는 행 (rows)테이블 전체 행 수개발팀 행 수
그룹핑 대상모든 부서 — 그룹핑용 임시 테이블(Using temporary)이 생기기 쉽다개발팀 하나 — 인덱스 순서로 읽으면 임시 테이블 없이 끝날 수 있다
버리는 시점집계가 다 끝난 뒤 (N−1개 그룹 폐기)집계 전 (다른 부서는 읽지도 않는다)

위 표는 "옵티마이저가 HAVING 조건을 그대로 두었을 때"의 개념적 대비다. 실제 값은 DB·버전·데이터 분포에 따라 다르므로, 면접에서는 숫자가 아니라 "인덱스를 타느냐 / 그룹핑 대상이 얼마나 되느냐 / 버리는 시점이 언제냐" 세 축으로 말한다.

판단 기준은 하나
조건식 안에 집계 함수(또는 집계 결과)가 있는가?
있다 → HAVING 선택지가 없다

AVG(salary) >= 5000, COUNT(*) >= 2 — WHERE 시점엔 계산할 그룹이 없어 HAVING밖에 못 쓴다.

없다 → WHERE 원칙

dept = '개발팀', salary >= 5000 — 집계 전에 행을 줄이고 인덱스를 탄다. HAVING에 두면 결과는 같아도 비용과 의도가 흐려진다.

가산점 — "옵티마이저가 내려주기도 한다"까지 말하되, 거기에 기대지는 않는다 가산점
집계와 무관한 HAVING 조건을 옵티마이저가 WHERE 쪽으로 내려 최적화해 주기도 한다. 그러나 최적화에 기대는 것과 의도를 코드로 표현하는 것은 다르다 — "행 조건은 WHERE, 그룹 조건은 HAVING"이라는 자리 약속을 지키면 성능 이전에 쿼리를 읽는 사람에게 의도가 전달된다. 이 한 문장이 실행 계획을 의식하는 사람의 언어다.

5. 함정 카드 3종 + 실행 순서 암기 드릴

세 함정 모두 새로 외울 것이 아니다 — §1의 파이프라인에서 자리만 확인하면 답이 나온다. 그래서 순서 하나를 확실히 외우는 것이 가장 싸다.

함정 1 — WHERE에 집계 함수 에러
SELECT dept, AVG(salary)
FROM   employee
WHERE  AVG(salary) >= 5000
GROUP  BY dept;
-- MySQL: Invalid use of group function

왜: WHERE 시점에는 그룹이 없다. 아직 존재하지 않는 것에 대한 질문이라 문법 이전에 논리적으로 성립하지 않는다.

고치기: 조건을 HAVING으로 옮긴다. 거꾸로 이 사실이 HAVING의 존재 이유다.

함정 2 — HAVING에 비집계 조건 두 갈래

(a) GROUP BY 컬럼 조건 — HAVING dept = '개발팀'. 결과는 같지만 §4의 비용·의도 문제 → WHERE로.

(b) 그룹 컬럼도 집계도 아닌 컬럼 — GROUP BY dept HAVING salary > 5000. "그룹의 salary"가 무엇인지 정해지지 않아 표준에선 성립하지 않고, MySQL 기본 설정(ONLY_FULL_GROUP_BY)도 거부한다. 허용되는 설정에서는 그룹 안 임의 행의 값으로 검사돼 결과가 비결정적이 된다.

"행 조건인가, 그룹 조건인가"를 먼저 묻고 자리를 정한다.

함정 3 — 별칭(alias) 참조 표준 vs MySQL
SELECT dept,
       AVG(salary) AS avg_sal
FROM   employee
GROUP  BY dept
HAVING avg_sal >= 5000;  -- MySQL ○ / 표준 ✕

왜 갈리나: 별칭은 SELECT에서 태어나는데 HAVING은 SELECT보다 앞이다. 표준은 그래서 금지, MySQL은 확장으로 허용.

이식성이 필요하면 HAVING에도 AVG(salary) >= 5000처럼 집계식을 다시 쓴다.

절SELECT 별칭 사용 — 표준 SQLMySQL이유 (실행 순서)

5-2. 암기 드릴 — 답을 소리 내어 말한 뒤 펼친다

드릴 1 · 빈칸 채우기 — FROM → ___ → GROUP BY → ___ → SELECT → ___. 그리고 "집계 경계"는 어디 사이인가?

WHERE → GROUP BY → HAVING → SELECT → ORDER BY. 6박자로는 "가져와 · 행 거르고 · 묶고 · 묶음 거르고 · 고르고 · 줄 세워".

집계 경계는 GROUP BY와 HAVING 사이다 — GROUP BY가 행을 묶어 집계값을 만드는 순간, 그 왼쪽(FROM·WHERE)에는 그룹이 없고 오른쪽(HAVING·SELECT·ORDER BY)에는 개별 행이 없다.

드릴 2 · 자리 배치 — 다음 네 조건은 각각 어느 절에 두는가? salary >= 5000 / AVG(salary) >= 5000 / dept = '개발팀' / COUNT(*) >= 2
  • salary >= 5000 → WHERE. 행 조건. HAVING에 두면 "그룹의 salary"가 정해지지 않아 성립하지 않는다(함정 2-b).
  • AVG(salary) >= 5000 → HAVING. 집계 함수 — 선택지가 없다.
  • dept = '개발팀' → WHERE. HAVING에 둬도 결과는 같지만 인덱스를 못 타고 버릴 그룹까지 만든다(§4).
  • COUNT(*) >= 2 → HAVING. 집계 함수.

판단 기준은 하나 — 조건식 안에 집계 함수가 있는가? 있으면 HAVING, 없으면 WHERE.

드릴 3 · 별칭 — SELECT dept, AVG(salary) AS avg_sal …에서 avg_sal을 WHERE / HAVING / ORDER BY 각각에서 쓸 수 있는가? 표준과 MySQL로 나눠 답하라.

WHERE — 표준 ✕, MySQL ✕. SELECT보다 한참 앞이라 별칭이 아직 태어나지 않았다.
HAVING — 표준 ✕, MySQL ○(확장). 논리 순서상 SELECT보다 앞이라 표준은 금지하지만 MySQL은 허용한다.
ORDER BY — 표준 ○, MySQL ○. SELECT 뒤라 별칭이 이미 존재한다.

이식성이 필요하면 HAVING에는 AVG(salary) >= 5000처럼 집계식을 그대로 다시 쓴다.

6. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 답의 깊이가 갈리는 지점, 추가는 이 페이지에서 보탠 문항.

①과 ②의 조건을 서로 바꿔 쓰면 결과가 어떻게 되는지, 데이터 없이 말로만 설명해 보세요. 면접에서 뭉개진 지점

§3-1 템플릿 그대로 — "조건이 집계 전/후로 이동한다 → 분모가 바뀌거나 / 분모는 그대로 검사 시점만 바뀐다 → 숫자가 달라진다."

  • ①을 HAVING으로 밀면: 걸러냈어야 할 저연봉 행이 평균의 분모에 들어가 숫자가 내려간다(7000 → 5000). "저연봉을 뺀 평균"이라는 요구 자체가 증발한다.
  • ②를 WHERE로 당기면: 평균 검사 대신 재료를 미리 잘라 숫자가 올라가며(5000 → 7000), 전원이 기준 미달인 부서는 결과에서 통째로 증발한다.

완성 조건 "의미가 서로 바뀐다"가 아니라 "각각 다른 틀린 숫자가 나온다"까지 말해야 한다. 면접에서 나온 "요청 2는 요청 1처럼 나온다"는 방향은 맞았지만 숫자가 문장에 없어서 절반이다.

WHERE 절에 AVG(salary) >= 5000을 쓰면 왜 에러인가요?

WHERE가 실행되는 시점에는 그룹이 아직 없기 때문이다. WHERE는 행을 하나씩 보며 남길지 버릴지 정하는 단계인데, AVG(salary)는 "여러 행을 묶은 그룹"이 있어야 계산되는 값이다. 아직 존재하지 않는 것에 대한 질문이라 문법 이전에 논리적으로 성립하지 않고, 그래서 표준이 금지한다(MySQL 메시지: Invalid use of group function).

거꾸로 이 사실이 HAVING의 존재 이유다 — 집계 결과를 거를 절이 따로 필요해서 HAVING이 있는 것이다.

집계 함수가 없는 조건은 WHERE와 HAVING 어디 둬도 결과가 같은데, 그래도 WHERE에 둬야 하는 이유는? 시니어 변별

결과가 같은 경우는 주로 GROUP BY 컬럼 자체에 대한 조건일 때다 — 그룹핑 전에 행을 버리나 그룹핑 후에 그 그룹을 버리나 남는 그룹이 같다. 그래도 WHERE에 둬야 하는 이유는 두 겹이다.

  1. 비용 — WHERE는 집계 전에 행을 줄여 그룹핑 대상 자체를 작게 만들고 인덱스를 탈 수 있다. HAVING은 버릴 그룹까지 전부 만든 뒤에 거른다(집계 결과는 실행 중 만들어지는 값이라 인덱스가 있을 수 없다).
  2. 의미 — "행 조건은 WHERE, 그룹 조건은 HAVING"이라는 자리 약속이 지켜져야 읽는 사람이 쿼리의 의도를 오해하지 않는다.

여기에 "옵티마이저가 이런 HAVING 조건을 WHERE로 내려주기도 하지만, 최적화 의존과 의도 표현은 별개"까지 얹으면 실행 계획을 의식하는 사람의 언어가 된다.

HAVING에서 SELECT의 별칭(alias)이나 집계식을 쓸 수 있나요?

집계식(AVG(salary) >= 5000)은 당연히 가능 — 그러라고 있는 절이다. 별칭은 갈린다: 논리 순서상 SELECT가 HAVING보다 뒤라서 표준 SQL은 HAVING에서 SELECT 별칭을 허용하지 않지만, MySQL은 확장으로 허용한다(SELECT AVG(salary) AS avg_sal … HAVING avg_sal >= 5000).

같은 논리로 WHERE에서는 MySQL조차 별칭을 못 쓴다 — WHERE는 SELECT보다 한참 앞 단계라 별칭이 아직 태어나지도 않았기 때문이다. 이식성이 필요하면 HAVING에도 별칭 대신 집계식을 그대로 다시 쓰는 것이 안전하다.

GROUP BY 없이 HAVING만 쓸 수 있나요?

가능하다 — 이때는 테이블 전체가 하나의 암묵적 그룹이 된다. SELECT AVG(salary) FROM employee HAVING AVG(salary) >= 5000은 전체 평균이 5000 이상이면 한 행, 아니면 빈 결과를 돌려준다.

"전사 평균이 기준을 넘을 때만 리포트 행을 만든다" 같은 조건부 집계에 쓸 수 있지만 드문 형태라, 실무에서 마주치면 의도된 것인지(GROUP BY 누락 실수가 아닌지) 먼저 의심하는 게 맞다.

"연봉 5000 이상인 직원이 2명 이상인 부서"를 뽑으려면? WHERE와 HAVING 중 하나를 고르는 문제인가요? 추가

둘 중 하나가 아니라 둘 다 쓴다 — 조건이 두 층이기 때문이다. "5000 이상인 직원"은 행 조건이라 WHERE, "2명 이상"은 그 행들을 묶은 뒤의 그룹 조건이라 HAVING.

SELECT dept, COUNT(*)
FROM   employee
WHERE  salary >= 5000        -- 재료: 5000 이상인 행만
GROUP  BY dept
HAVING COUNT(*) >= 2;        -- 완성품: 그 재료가 2명 이상인 부서만

WHERE와 HAVING은 경쟁 관계가 아니라 파이프라인의 다른 지점이다. 요구 문장을 "행에 대한 말"과 "묶음에 대한 말"로 쪼개면 자리가 저절로 정해진다.

WHERE에서 걸러진 행을 HAVING 단계에서 다시 볼 수 있나요? 추가

없다. 파이프라인은 한 방향이다 — WHERE에서 버려진 행은 GROUP BY의 재료에 들어가지 못하므로 집계값에도, 따라서 HAVING이 보는 그룹에도 흔적이 남지 않는다.

이것이 "WHERE 이동은 분모가 바뀐다"는 말의 정체다. ①에서 A(3000)가 WHERE에서 탈락하면 개발팀 평균은 처음부터 B 한 명의 평균으로 계산되지, "두 명 평균을 낸 뒤 A를 뺀 값"이 아니다. 양쪽 정보가 다 필요하면(예: 전체 평균과 5000 이상자 평균을 나란히) 조건을 WHERE에 두는 대신 AVG(CASE WHEN salary >= 5000 THEN salary END)처럼 집계식 안으로 조건을 넣는다 — 재료는 다 통과시키고 계산할 때만 골라 쓰는 방식이다.

요구 ②를 WHERE로 잘못 쓰면 숫자만 달라지나요, 아니면 결과 행의 구성도 달라지나요? 추가

행의 구성도 달라진다 — 두 방향으로. §2-1의 인사팀(2000, 6000)이 그 예다.

  • 없어야 할 부서가 나타난다: 인사팀 평균은 4000이라 정답(HAVING)에서는 빠져야 하는데, WHERE로 당기면 2000이 잘려 나가 인사팀 6000이라는 행이 등장한다.
  • 부서가 증발한다: 전원이 5000 미만인 부서는 재료가 전부 사라져 그룹 자체가 만들어지지 않는다 — 평균 NULL 행이 아니라 행 없음이다.

그래서 "숫자가 다르다"만으로는 부족하고, 리포트에서 부서 목록 자체가 달라진다까지 말할 수 있어야 비즈니스 영향을 설명한 것이 된다.

집계 함수가 없는 HAVING 조건은 항상 WHERE와 같은 결과를 내나요? 시니어 변별 추가

GROUP BY 컬럼(또는 그 컬럼에 함수 종속인 컬럼)에 대한 조건일 때만 같다 — 그룹 안의 모든 행이 같은 값을 가지므로 "그룹을 버린다"와 "그 행들을 미리 버린다"가 일치한다.

그룹 컬럼이 아닌 컬럼(GROUP BY dept HAVING salary > 5000)은 그룹 안에서 값이 제각각이라 "그룹의 salary"가 정의되지 않는다. 표준에서는 성립하지 않고 MySQL 기본 설정(ONLY_FULL_GROUP_BY)도 거부한다. 이를 허용하는 설정에서는 그룹 안 임의 행의 값으로 검사하므로, 같은 쿼리가 실행마다 다른 결과를 낼 수 있다 — WHERE에 두었을 때(행 단위로 명확히 거른다)와 결과가 다르고, 게다가 비결정적이다.

정리: "결과가 같다"는 말은 GROUP BY 컬럼 조건에 한해서이고, 그 경우에도 §4의 비용·의도 때문에 WHERE가 원칙이다.

한 줄 요약
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY의 실행 순서 위에서, WHERE는 집계에 들어갈 재료(행)를 거르고 HAVING은 집계가 끝난 결과(그룹)를 거른다 — 같은 조건이라도 위치가 바뀌면 분모가 바뀌어 다른 숫자가 나오고(7000 vs 5000), 틀린 숫자는 틀린 비즈니스 판단이 된다. 집계 함수가 없는 조건은 WHERE에 — 집계 전에 행을 줄이고 인덱스를 탈 수 있으며, HAVING은 버릴 그룹까지 다 만든 뒤에야 거르기 때문이다.
