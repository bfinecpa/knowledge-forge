핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "수억 건 테이블에서 특정 기간 데이터를 삭제/아카이빙해야 합니다. 어떻게 접근하겠습니까? (파티셔닝 포함)"
수억 건 테이블에 DELETE ... WHERE created_at < ? 한 방은 "느린 쿼리"가 아니라 자원 다섯 개에서 동시에 출발하는 장애다 — ① 거대 트랜잭션의 undo 폭증(+ 중간에 KILL하면 롤백이 원 작업만큼, 혹은 더 오래) ② 커밋까지 쥐는 행 락·갭 락 → 대기 → 커넥션 풀 고갈 ③ 커밋 순간의 거대 binlog 덩어리 → 복제본이 단일 트랜잭션으로 재생 → 읽기 복제본 stale ④ 세컨더리 인덱스마다 흩어진 엔트리 삭제 = 랜덤 I/O로 버퍼 풀 오염 ⑤ 다 지워도 .ibd는 안 줄어드는 공간 미반환. 그래서 답은 접근법 3종을 조건에 따라 고르는 것이다 — 청크 삭제(지금 당장 가능하지만 총 시간·총 I/O가 크고 공간은 안 돌아옴) / 파티션 DROP(즉시·저비용이지만 사전 파티셔닝 필요, 파티션 키가 PK·모든 유니크 키에 포함돼야 하는 제약, 조회에 프루닝 조건 필요, FK 불가) / 남길 것만 복사 후 RENAME(공간 완전 회수·인덱스 재구축이지만 복사 중 쓰기 델타·디스크 2배). 어느 쪽이든 삭제 전 아카이브 검증(건수·체크섬) → 드라이런 → 복제 지연 임계 시 스스로 멈추는 청크 루프 → 파티션 자동 생성·드랍 스케줄러 → 보존 정책을 테이블 설계 시점에 고정을 사람의 기억이 아니라 코드로 박는다.

1. 왜 DELETE ... WHERE created_at < ? 한 방이 장애가 되는가 — 자원별 다섯 사슬

-- "3개월 지난 조회 로그 지워주세요" 티켓을 받고 새벽에 실행한 한 줄
DELETE FROM episode_view_log
 WHERE created_at < DATE_SUB(NOW(), INTERVAL 3 MONTH);   -- 대상 약 2억 건, 트랜잭션 1개

"오래 걸린다"가 답이 아니다. 이 한 문장은 하나의 트랜잭션으로 2억 행을 지우며, 그동안 아래 다섯 자원을 동시에 점유·소모한다. 한 자원의 사슬이 끝난 뒤 다음이 시작되는 게 아니라, 실행 버튼을 누른 순간 다섯 사슬이 한꺼번에 출발한다 — 그래서 방사형으로 그린다. 면접에서는 A → B → C 순으로 말하고, D · E는 "그리고 다 끝나도"로 붙인다.

그림 1. 한 방 DELETE의 방사형 장애 — 다섯 사슬은 순서대로가 아니라 동시에 출발한다. 색은 이 페이지 전체에서 같은 사슬을 가리킨다.

1-1 ~ 1-5. 사슬별 화살표 — 자원 → 누적 → 피해자 → 왜 죽는가

한 칸씩 화살표를 따라 말하는 연습을 한다. 마지막 빨간 칸이 면접관이 듣고 싶은 "장애"다.

A
undo — 트랜잭션 크기에 비례해 자라고, 중단하면 더 오래 걸린다
자원행 삭제 = 즉시 제거가 아니라 delete-mark + undo 레코드. 물리 제거는 purge가 나중에.
누적2억 undo → 테이블스페이스 수 GB~수십 GB. 커밋 전엔 하나도 못 버린다 — 자기 롤백 재료라서.
피해자가장 오래된 활성 TX가 되어 purge 정지 → history list 급증 → 무관한 조회도 버전 체인 순회로 느려짐.
장애40분 뒤 KILL → undo 역순 적용 = 원 작업 이상의 롤백, 취소 불가, 재시작해도 이어짐 → 1시간+ 뒤 0건 삭제.

정상 커밋돼도 끝이 아니다 — 커밋 직후 purge가 2억 delete-mark를 물리 삭제하느라 I/O 스파이크가 한동안 이어진다.

B
락 — 커밋까지 쥔다 → 대기 큐 → 커넥션 고갈
자원DELETE는 스캔한 행에 X 락. created_at 인덱스 없으면 풀스캔 = 전 행. RR이면 조건 불일치 행 락도 끝까지.
누적REPEATABLE READ 넥스트키 락 → 인덱스 범위의 "사이"까지 잠금 → 그 구간 INSERT 대기. 풀스캔이면 범위 = 테이블 전체.
피해자락은 문장이 아니라 트랜잭션 끝에 풀린다. 대기 세션은 커넥션을 쥔 채 innodb_lock_wait_timeout(50초)까지 대기.
장애HikariCP 풀이 대기자로 채워짐 → 이 테이블과 무관한 API까지 connection-timeout.
C
binlog · 복제 — 커밋 순간 한 덩어리 → 복제본 stale
자원ROW 포맷 = 삭제 행마다 이벤트. binlog는 TX 단위로 커밋 시점에 한 번에 기록 → 그 전엔 binlog 캐시(넘치면 임시 파일).
누적커밋 자체가 수십 초. max_binlog_cache_size 초과 시 몇 시간 일하고 커밋 직전 에러 → 롤백 가산점
피해자복제본은 TX 단위 재생 → 워커 1개가 처음부터 다시 삭제, 이후 커밋된 TX 전부 뒤에 줄 → 프라이머리 소요만큼 지연.
장애Seconds_Behind_Source 수십 분 → 리플리카 조회 stale("읽었는데 안 읽음") → 지연 헬스체크가 리플리카 제외 → 부하 마스터 집중. 커밋된 뒤엔 복제본에서 멈출 방법 없음.
D
인덱스 유지 비용 — 세컨더리 인덱스마다 랜덤 I/O 반복 공백: 랜덤 vs 순차
자원행 1건 삭제 = 클러스터드 1건 + 세컨더리 N개 각 1건 delete-mark. 인덱스 2개면 B+Tree 세 개를 건드린다.
누적클러스터드는 id가 시간순 → 3개월 행이 물리적으로 붙어 있어 페이지 단위 순차. 세컨더리는 member_id 순 → 같은 행이 인덱스 전체에 흩어짐.
피해자2억 × N = 수억 번 랜덤 페이지 접근. change buffer가 일부 버퍼링해도 결국 읽어 머지 → 버퍼 풀이 삭제 대상 페이지로 채워짐.
장애운영 조회가 쓰던 페이지가 축출 → 캐시 미스 → 삭제와 무관한 쿼리 p99 상승. 커밋 후 purge가 같은 페이지를 다시 방문 → 랜덤 I/O 한 번 더.
그림 2. 같은 "3개월치 삭제"가 클러스터드 인덱스에서는 인접 페이지 몇 장(순차), 세컨더리 인덱스에서는 인덱스 전체 페이지(랜덤)다. 빨간 줄 하나가 delete-mark 대상 엔트리.
I/O 비용 모델 — 외울 규칙
세컨더리 인덱스는 자기 키 순서로 정렬돼 있으므로, "기간"이라는 조건에 대해서는 항상 랜덤이다.

순차 = 인접 페이지를 이어서 읽는다(디스크 헤드/프리페치가 유리). 랜덤 = 페이지마다 따로 찾아 읽는다. 클러스터드 인덱스만 시간(=PK) 순이고, 세컨더리 인덱스 N개는 각자 다른 키로 정렬돼 있어 시간 조건이 N개의 흩어진 랜덤 접근으로 번역된다. 이 비용은 청크로 나눠도 총액이 같다(2-1) — 나눠 내는 것이지 깎이는 게 아니다.

E
다 지워도 디스크는 안 줄어든다 — 공간 미반환 · 조각화
자원purge까지 끝나도 빈 페이지는 그 테이블스페이스 안의 free 목록으로만 돌아간다. 이후 INSERT가 재사용.
누적.ibd 파일은 줄지 않는다 → "디스크 80% 알람"이 목적이었다면 목적 달성 실패.
피해자부분적으로 빈 페이지 → 범위 스캔 시 페이지당 유효 행 ↓ → 같은 결과에 더 많은 페이지 I/O → "지웠는데 더 느려졌다".
장애회수 = OPTIMIZE TABLE(= ALTER TABLE ... FORCE, 테이블 재구성) → online-ddl의 디스크 2배·복제 지연·MDL 사슬 재발.

information_schema.TABLES의 DATA_FREE로 "지웠지만 회수 안 된 공간"을 숫자로 볼 수 있다.

1-6. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

뭉뚱그린 표현사슬 이름사슬로 말하면
"오래 걸린다"A · undo 폭증 · 롤백 배증2억 undo 레코드 → 테이블스페이스 팽창 + purge 정지 → 중단하면 역순 롤백이 원 작업 이상 → 결과 0건
"락 걸려서 느려진다"B · 락 보유 큐스캔 행 X 락(풀스캔이면 전 행) + 넥스트키 락 → 커밋까지 유지 → 대기자가 커넥션 점유 → 풀 고갈 → 무관 API 장애
"복제본이 밀린다"C · binlog 한 덩어리커밋 시 수 GB 이벤트 일괄 기록 → 복제본이 단일 트랜잭션으로 재생 → 이후 트랜잭션 전부 대기 → 읽기 stale
"인덱스 때문에 느리다"D · 세컨더리 랜덤 I/O행 1건 = 인덱스 N개 delete-mark → 세컨더리는 시간순이 아니라 흩어짐 → 랜덤 페이지 I/O → 버퍼 풀 오염 → 남의 쿼리 캐시 미스
"지웠는데 용량이 그대로다"E · 공간 미반환빈 페이지는 free 목록으로만 → .ibd 불변 → 회수는 재구성(=DDL) → MDL·디스크 2배 재발

2. 접근법 3종 비교 — 목록 먼저, 대가를 양면으로

다섯 사슬은 전부 "트랜잭션 하나가 크다"에서 출발한다. 세 접근법은 그 전제를 각각 다르게 깬다 — 청크는 트랜잭션을 작게 여러 개로, 파티션 DROP은 DML을 파일 삭제로, 복사 후 RENAME은 삭제를 "남길 것 재작성"으로 바꾼다. 표는 인출용이고, 점수는 각 칸의 "왜"에서 난다.

암기 순서: 조건 → 시간 → A~C → D → E → 되돌리기 → 대가 → 언제. 앞 여섯 축은 "1장의 사슬을 각 접근법이 어떻게 처리하는가"이고, 뒤 두 축이 결론이다.

① 청크 삭제 — PK 범위로 잘라 짧은 트랜잭션 수천 개로
아이디어 하나: 트랜잭션을 작게 쪼개면 사슬 A·B·C가 각각 짧게 끊긴다. undo는 청크만큼 쌓였다 커밋과 함께 정리, 락은 수백 ms, binlog는 청크 단위로 흘러 복제본이 실시간으로 따라온다. 단, "어떻게 자르느냐"가 성패를 가른다.
나쁜 청크 — LIMIT 반복
-- 매번 인덱스 앞쪽부터 다시 스캔.
-- 방금 지운 행은 purge 전까지 delete-mark로 남아
-- 다음 청크가 "유령 엔트리"를 건너뛰며 시작 → 갈수록 느려짐.
-- ORDER BY 없는 LIMIT는 비결정적 → statement binlog unsafe.
DELETE FROM episode_view_log
 WHERE created_at < '2026-06-01'
 LIMIT 5000;
좋은 청크 — 경계 고정 + PK 범위 seek
-- 상한을 1회 계산해 "움직이는 목표"를 없앤다
SELECT MAX(id) FROM episode_view_log
 WHERE created_at < '2026-06-01';
-- 루프 본문: (last_id, last_id + 5000] 구간만
DELETE FROM episode_view_log
 WHERE id > ? AND id <= ?
   AND created_at < '2026-06-01';  -- 안전벨트: PK가 시간순 아닌 행 오삭제 방지

전제: PK가 시간에 따라 단조 증가(AUTO_INCREMENT, Snowflake/TSID, UUID v7). 그러면 "기간" = "PK 연속 구간" = 클러스터드 인덱스의 인접 페이지 몇 장. UUID v4처럼 무작위면 (created_at, id) 인덱스로 키셋 탐색해야 하고 매 청크마다 세컨더리 → 클러스터드 룩업 비용이 붙는다(deep pagination의 "배치 전수 순회"와 같은 함정).

얻는 것
  • 사전 준비 없음 — 파티션 없는 기존 테이블에 지금 당장.
  • 트랜잭션마다 짧으니 사슬 A·B·C가 청크 길이로 제한.
  • 멈출 수 있다. 복제 지연이 오르면 쉬고, 피크엔 안 돌고, 킬 스위치로 즉시 정지. 한 방 DELETE에는 없는 성질.
지불하는 것 (반드시 같이 말할 것)
  • 총 시간이 길다. 2억 건 ÷ 5,000 + 100ms 휴식 = 4만 번, 며칠. "약하게, 오래" 부하.
  • 총 I/O는 오히려 최대. 사슬 D는 청크로 나눠도 한 건도 안 줄어든다 — 나눠 낼 뿐 총액 동일.
  • 공간은 안 돌아온다(사슬 E). 디스크 회수가 목적이면 절반의 답.
  • 중간 상태 노출. "3개월 전 로그가 절반만 남은" 상태가 조회됨 → 집계 배치가 어긋남 → 공지 또는 집계를 아카이브로.
  • 운영이 필요. 청크 크기·sleep·임계값을 측정·조정하는 코드와 사람(3장). "돌려놓고 퇴근" 불가.
  • 같은 범위를 갱신하는 TX와 데드락 → 청크 단위 재시도. 대량 삭제 후 인덱스 통계 변동 → 다른 쿼리 실행 계획 흔들림(ANALYZE TABLE).
② 파티션 DROP — 삭제를 DML이 아니라 "파일 제거"로 바꾼다
행을 하나씩 지우는 게 아니라 파티션의 데이터 파일을 버린다. undo도, 행 단위 binlog도, 인덱스 랜덤 I/O도 없다.
CREATE TABLE episode_view_log (
  id         BIGINT      NOT NULL,
  member_id  BIGINT      NOT NULL,
  episode_id BIGINT      NOT NULL,
  created_at DATETIME(6) NOT NULL,
  PRIMARY KEY (id, created_at),            -- ★ 파티션 키가 PK에 들어가야 한다 (대가 2)
  KEY idx_member  (member_id,  created_at),
  KEY idx_episode (episode_id, created_at)
) PARTITION BY RANGE COLUMNS (created_at) (
  PARTITION p202606 VALUES LESS THAN ('2026-07-01'),
  PARTITION p202607 VALUES LESS THAN ('2026-08-01'),
  PARTITION p202608 VALUES LESS THAN ('2026-09-01'),
  PARTITION p202609 VALUES LESS THAN ('2026-10-01')
  -- 선택: PARTITION p_future VALUES LESS THAN (MAXVALUE)   ← catch-all, 대가는 5번
);

-- 3개월 보존: 지난 달 파티션 하나를 통째로
ALTER TABLE episode_view_log DROP PARTITION p202605;   -- 건수 무관 즉시, 파일 삭제
얻는 것
  • 수억 건이든 즉시. 사슬 A~D 소멸.
  • 공간 즉시 반환(사슬 E 소멸) — 파티션이 곧 별도 파일.
  • 복제본에도 ALTER ... DROP PARTITION 한 줄만 → 복제 지연 없음.
지불하는 것 — 아래 8가지 시니어 변별
  • 한 줄로: "삭제가 설계의 일부일 때" 최강, "삭제가 나중에 생각난 요구일 때" 가장 비싸다.
  • 그래서 파티션 DROP은 "이번 삭제"의 답이 아니라 "다음 삭제"를 위한 투자다.
암기 — 파티션 DROP의 대가 8가지
1
사전에 파티셔닝돼 있어야 한다이미 수억 건 쌓인 테이블에 파티션 걸기 = 전체 재구성(COPY) → online-ddl 사슬 A·B. 도입 경로: pt-osc/gh-ost로 옮기거나, 새 파티션 테이블로 신규 쓰기를 돌리고 구 테이블은 청크 삭제로 자연 소멸.
2
파티션 키가 PK와 모든 유니크 키에 포함돼야 한다 (MySQL 규칙)PRIMARY KEY (id) → (id, created_at). 잃는 것 넷: (a) id 단독 유일성의 DB 보장 → 채번기 책임 (b) 모든 세컨더리 리프가 복합 PK를 품어 인덱스 커짐 (c) UNIQUE(member_id, episode_id)에 created_at을 끼우면 업무 규칙이 사라짐 → 유니크 제약 필요한 테이블은 부적합 (d) JPA @Id가 복합키(@IdClass/@EmbeddedId).
3
조회에 파티션 키 조건이 없으면 모든 파티션을 뒤진다로컬 인덱스만 있고 글로벌 인덱스가 없다. WHERE id = ?만으로는 파티션 수만큼 seek. 프루닝(조건으로 파티션을 미리 걸러냄) 조건이 필수 → 조회 API 계약이 바뀐다("기간은 필수"). EXPLAIN의 partitions 컬럼으로 확인.
4
FK를 못 쓴다InnoDB 파티션 테이블은 FK를 정의할 수도, 다른 테이블에서 참조될 수도 없다.
5
파티션은 유한하다다음 달 파티션이 없으면 그달 첫 INSERT 실패(Table has no partition for value). MAXVALUE catch-all은 실패는 막지만 나중에 REORGANIZE PARTITION(= 그 파티션 재구성). 어느 쪽이든 자동 생성 스케줄러 + "미래 파티션 N개 이상" 알람 필수(4-4).
6
DROP PARTITION도 DDL이다배타 MDL 필요 → 그 테이블을 읽는 긴 TX가 있으면 online-ddl 사슬 A(MDL 큐 → 전면 장애) 재현. lock_wait_timeout을 짧게 두고 재시도.
7
삭제 단위가 파티션으로 굳는다"5월 데이터 중 탈퇴 회원 것만"은 여전히 DML. 파티션 단위(일/주/월)는 보존 정책의 세밀함과 파티션 수 상한(테이블당 8,192개) 사이에서 정한다.
8
운영 지식이 비용이다백업·복구·통계 수집이 파티션 단위 운영 지식을 요구한다 — 팀에 경험이 없으면 그 자체가 비용.

연상: "사전 · PK · 프루닝 · FK · 유한 · DDL · 단위 · 운영" — 앞 넷(1~4)은 스키마가 내는 값, 뒤 넷(5~8)은 운영이 내는 값.

③ 남길 것만 새 테이블로 복사한 뒤 RENAME — 삭제 대신 "재작성"
지울 90%를 건드리지 않고 남길 10%만 옮긴다. 이 기회에 파티셔닝을 함께 도입할 수 있다.
-- 1) 같은 구조의 빈 테이블
CREATE TABLE episode_view_log_new LIKE episode_view_log;
ALTER TABLE episode_view_log_new AUTO_INCREMENT = <원본 현재값보다 큰 값>;  -- 카운터는 따라오지 않는다

-- 2) 남길 행만 복사 — 이것도 한 방이 아니라 PK 범위 청크로
--    (INSERT ... SELECT 한 방 = 거대 TX + RR에서 원본 행에 공유 넥스트키 락 → 원본 쓰기 차단)
INSERT INTO episode_view_log_new
SELECT * FROM episode_view_log
 WHERE id > ? AND id <= ? AND created_at >= '2026-06-01';

-- 3) 복사 시작 이후 들어온 쓰기(델타)를 따라잡은 뒤 원자적 교체
RENAME TABLE episode_view_log     TO episode_view_log_old,
             episode_view_log_new TO episode_view_log;

-- 4) 며칠 관찰 후
DROP TABLE episode_view_log_old;   -- 공간 즉시 반환
얻는 것
  • 삭제 I/O를 아예 지불하지 않는다. 새 테이블의 세컨더리 인덱스는 흩어진 delete-mark가 아니라 정렬된 빌드 = 순차 I/O.
  • 공간 완전 회수 + 조각화 0. OPTIMIZE TABLE 효과를 삭제와 동시에.
  • RENAME TABLE은 원자적 → 앱은 끊김 없이 새 테이블. old를 며칠 두면 되돌리기도 RENAME 한 번.
지불하는 것
  • 복사 시작 이후의 쓰기 델타 — 가장 큰 대가. 해법은 둘뿐: 쓰기를 멈추는 점검 창, 또는 트리거/binlog로 델타 추적(pt-osc/gh-ost가 하는 일이지만 그 도구들은 전체 행을 복사하지 "남길 행만"이 표준 옵션은 아님 → 직접 짜거나 점검 창).
  • 디스크 일시 2배(원본 + 새 테이블 + old 보관 기간).
  • 원본을 참조하는 FK가 있으면 RENAME 후 자식 FK가 old를 따라감 → 자식 FK 재정의(DDL). 트리거·뷰·권한도 다시.
  • 남길 비율이 크면(예: 절반) 복사 비용 > 삭제 비용 → 손해.
  • RENAME도 MDL을 잡는다 — 짧지만 긴 TX가 있으면 대기.

2-4. 선택 기준 — 결정 순서로 말하기

  1. 이미 파티셔닝돼 있는가? → 파티션 DROP. 다른 선택지는 볼 필요가 없다.
  2. 지울 비율이 압도적(대략 80~90% 이상)이고, 점검 창이나 델타 처리 수단이 있는가? → 복사 후 RENAME. 이 기회에 파티셔닝을 함께 도입한다.
  3. 그 외 → 청크 삭제로 지금의 문제를 풀고, 동시에 파티셔닝 도입 계획을 세운다. 청크는 "이번"의 답, 파티션은 "다음"의 답.
pt-archiver를 먼저 검토한다 가산점

Percona Toolkit의 pt-archiver는 PK 기준 청크로 다른 테이블/파일에 옮기고 지우며 --check-slave-lag, --sleep, --txn-size, --bulk-delete로 3장의 필수 요소를 검증된 형태로 제공한다. "도구가 있다는 것을 알고, 그래도 직접 짤 때는 같은 요소를 빠뜨리지 않는다"가 시니어의 태도다.

3. 청크 삭제 루프 — 필수 요소 9가지와 게이트 6종

"청크로 나눕니다"는 출발선이다. 아래 열 가지(0~9) 중 하나라도 빠진 청크 삭제는 한 방 DELETE를 여러 번으로 늘려 놓은 것에 불과하다. 안전한 삭제 코드는 자기가 지금 몇 건을 지우고 있고 DB가 그걸 감당하는지를 매 순간 안다.

3-0. 필수 요소 9가지 (인출용 목록)

암기 카드 — 0번 + 9가지
0
삭제 전 아카이브 검증건수 + 체크섬 통과 범위(verified_until_id) 이하만 지운다(4-1). 루프 앞에 붙는 전제.
1
경계 고정시작 전 MAX(id)로 상한 1회 계산. 매 청크 NOW()면 대상이 계속 늘어 끝나지 않는다.
2
PK 범위 커서id > last AND id <= last + N. LIMIT가 아니다(2-1).
3
청크 크기트랜잭션 하나가 수백 ms 안에. 1,000~10,000에서 시작해 측정 후 결정. 정답 숫자는 없고 측정만 있다.
4
청크 간 sleep + 적응형 스로틀느려지면 크기 절반·휴식 증가. 버퍼 풀·purge·복제본이 따라올 시간.
5
복제 지연 게이트임계 초과면 대기, 일정 시간 넘게 초과면 스스로 중단. 사람이 알람 보고 멈추는 게 아니다.
6
DB 부하 게이트Threads_running, 락 대기, 커넥션 풀 사용률.
7
진행 위치 영속화 + 멱등마지막 id를 삭제와 같은 트랜잭션에 기록. 언제 죽어도 그 지점부터 재개, 같은 범위 두 번 지워도 무해.
8
킬 스위치 + 실행 시간 창플래그 하나로 즉시 정지, 피크 시간엔 자동으로 안 돈다.
9
관측청크당 소요·삭제 건수·현재 지연을 메트릭·로그로. 이상치(청크 시간 급증, 삭제 0건 연속)에 알람.

연상: "경계 · 커서 · 크기 · 숨 · 지연 · 부하 · 위치 · 스위치 · 눈" — 앞 넷은 "어떻게 자르나", 5·6·8은 "언제 멈추나"(게이트), 7·9는 "죽어도 되고 보인다".

3-1. 루프 흐름도 — 게이트 6종이 어디서 루프를 세우는가

그림 3. 청크 루프 한 바퀴. 게이트 G1~G3·G5·G6은 트랜잭션 전에, G4는 후에 있다 — 트랜잭션 안에는 DELETE와 진행 위치 저장 둘뿐이다.
게이트신호동작대체하는 사고
G1복제 지연하트비트 지연 > 임계(예: 5초)대기 → 일정 시간 초과 시 오늘 중단"25분 뒤 복제 지연 알람" → 사람이 40분에 KILL
G2DB 부하Threads_running > 임계백오프운영 쿼리 p99 상승
G3커넥션 풀HikariCP active/total > 70%백오프 (내 루프가 풀을 굶기고 있다는 신호)무관 API의 connection-timeout
G4청크 시간목표의 2배 초과청크 크기 절반트랜잭션이 커져 사슬 A·B 재발
G5시간 창피크 시간 진입진행 위치 저장 후 종료낮 트래픽과 삭제 부하 겹침
G6킬 스위치설정값/파일/캐시 키즉시 종료"프로세스 어떻게 세우죠?" → KILL → 롤백

대량 삭제 사고의 전형은 "알람이 울렸고, 사람이 보고, 판단하고, KILL했다"인데 그 사이 40분이 지나 있고 KILL은 롤백을 부른다. 게이트는 그 40분을 0으로 만든다.

3-2. before / after — @Scheduled 한 방 vs TransactionTemplate + PK 범위 청크 + 지연 감시

before — 한 방, 그리고 더 나쁜 파생 삭제 메서드

    private final EpisodeViewLogRepository repository;

    @Scheduled(cron = "0 0 4 * * *")
    @Transactional                                   // ← 2억 행이 한 트랜잭션
    public void purgeOld() {
        LocalDateTime cutoff = LocalDateTime.now().minusMonths(3);

        // 함정 1: Spring Data JPA 파생 삭제 메서드(deleteBy...)는 벌크 DELETE가 아니다.

@Component
@RequiredArgsConstructor
public class ViewLogChunkPurger {

    private final JdbcTemplate jdbc;                 // 프라이머리 DataSource
    private final TransactionTemplate tx;            // 청크 하나 = 트랜잭션 하나
    private final ReplicationLagProbe lagProbe;      // 리플리카 지연 측정 (3-4)
    private final PurgeProgressRepository progress;  // 진행 위치 영속화 (별도 테이블)
    private final ArchiveVerifier archiveVerifier;   // 삭제 허가 범위 (4-1)
    private final PurgeProperties props;             // chunkSize, sleep, lagThreshold, window, killSwitch...
    private final MeterRegistry meters;

    // ★ 이 메서드에 @Transactional을 붙이지 않는다.                          함정: 붙이면 다시 한 방
    //   붙이는 순간 안의 TransactionTemplate(기본 REQUIRED)이 그 트랜잭션에 참여해
    //   루프 전체가 다시 "한 방"이 된다. 실제로 자주 나는 실수다.
    @Scheduled(cron = "0 0 2 * * *")                 8 off-peak 시작
    public void run() {
        LocalDateTime cutoff = LocalDate.now().minusMonths(props.retentionMonths()).atStartOfDay();

        Long maxId = jdbc.queryForObject(                                             1 경계 고정 — 상한 PK 1회
            "SELECT MAX(id) FROM episode_view_log WHERE created_at < ?", Long.class, cutoff);
        if (maxId == null) return;

        long verifiedUntil = archiveVerifier.verifiedUntilId("episode_view_log");    0 아카이브 검증 범위까지만
        maxId = Math.min(maxId, verifiedUntil);

        long lastId = progress.lastDeletedId("episode_view_log").orElse(0L);         7 재개
        int chunk = props.chunkSize();

        while (lastId < maxId) {
            if (props.killSwitchOn() || !props.window().contains(LocalTime.now())) {     G6 · G5
                log.warn("[purge] paused at id={}", lastId);
                return;                                // 진행 위치는 이미 저장돼 있다
            }
            if (!lagProbe.waitUntilBelow(props.lagThresholdSec(), props.lagWaitMax())) { G1
                log.error("[purge] replica lag stayed above {}s — aborting today", props.lagThresholdSec());
                meters.counter("purge.aborted", "reason", "replica_lag").increment();
                return;
            }
            if (dbBusy()) { sleepQuietly(props.backoff()); continue; }                  G2 · G3

            final long from = lastId;
            final long to   = Math.min(lastId + chunk, maxId);

            long started = System.nanoTime();
            int deleted = tx.execute(status -> {                                        2 PK 범위 청크 = 짧은 TX 1개
                int n = jdbc.update(
                    "DELETE FROM episode_view_log WHERE id > ? AND id <= ? AND created_at < ?",
                    from, to, cutoff);
                progress.save("episode_view_log", to);                                7 같은 트랜잭션
                return n;
            });
            long elapsedMs = (System.nanoTime() - started) / 1_000_000;

            meters.timer("purge.chunk.duration").record(Duration.ofMillis(elapsedMs));  9
            meters.counter("purge.rows.deleted").increment(deleted);
            log.info("[purge] ({}, {}] deleted={} in {}ms chunk={} lag={}s",
                     from, to, deleted, elapsedMs, chunk, lagProbe.current());

            chunk  = adapt(chunk, elapsedMs);                                          G4 3·4
            lastId = to;
            sleepQuietly(props.sleepBetweenChunks());   // 트랜잭션 밖에서 잔다              4
        }
        progress.clear("episode_view_log");
        log.info("[purge] completed up to id={}", maxId);
    }

    private int adapt(int chunk, long elapsedMs) {
        long target = props.targetChunkMs();            // 예: 200ms
        if (elapsedMs > target * 2) return Math.max(chunk / 2, props.minChunk());
        if (elapsedMs < target / 2) return Math.min(chunk * 2, props.maxChunk());
        return chunk;
    }

    private boolean dbBusy() {
        Integer running = jdbc.queryForObject(
            "SELECT VARIABLE_VALUE FROM performance_schema.global_status WHERE VARIABLE_NAME = 'Threads_running'",
            Integer.class);
        return running != null && running > props.maxThreadsRunning();
    }

    private static void sleepQuietly(Duration d) {
        try { Thread.sleep(d.toMillis()); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

@Component @StepScope @RequiredArgsConstructor
public class ViewLogPurgeTasklet implements Tasklet {
    private final JdbcTemplate jdbc;
    private final ReplicationLagProbe lagProbe;
    private final PurgeProperties props;
    @Value("#{jobParameters['cutoff']}") private LocalDateTime cutoff;   // 같은 파라미터면 재실행이 아니라 "재시작"

    @Override
    public RepeatStatus execute(StepContribution contribution, ChunkContext ctx) {
        ExecutionContext ec = ctx.getStepContext().getStepExecution().getExecutionContext();

        if (!ec.containsKey("maxId")) {                            1 첫 호출 때 한 번
            Long maxId = jdbc.queryForObject(
                "SELECT MAX(id) FROM episode_view_log WHERE created_at < ?", Long.class, cutoff);
            if (maxId == null) return RepeatStatus.FINISHED;
            ec.putLong("maxId", maxId);
        }
        long maxId  = ec.getLong("maxId");
        long lastId = ec.getLong("lastId", 0L);                    7 재시작 시 여기서부터
        if (lastId >= maxId) return RepeatStatus.FINISHED;

        if (lagProbe.current() > props.lagThresholdSec()) {        G1 TX 안 → 기다리지 않고 즉시 실패
            throw new PurgeThrottledException("replica lag " + lagProbe.current() + "s");
        }  // 스텝 FAILED → 다음 스케줄에 같은 JobParameter로 restart → lastId부터

        long to = Math.min(lastId + props.chunkSize(), maxId);
        int n = jdbc.update(                                        2
            "DELETE FROM episode_view_log WHERE id > ? AND id <= ? AND created_at < ?",
            lastId, to, cutoff);
        contribution.incrementWriteCount(n);                        9
        ec.putLong("lastId", to);                                   7 커밋과 함께 JobRepository에 저장
        return RepeatStatus.CONTINUABLE;                            // 새 트랜잭션으로 다시 호출된다
    }
}

@RequiredArgsConstructor
class SleepAfterChunk implements ChunkListener {
    private final Duration sleep;
    @Override public void afterChunk(ChunkContext context) {
        try { Thread.sleep(sleep.toMillis()); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

하트비트 테이블권장

프라이머리가 1초마다 현재 시각을 한 행에 쓰고, 리플리카에서 그 행을 읽어 지금과의 차이를 지연으로. 복제 경로 전체를 실제로 통과한 값이라 정확.

@Component
@RequiredArgsConstructor
public class ReplicationLagProbe {
    private final List<JdbcTemplate> replicas;   // 리플리카별 DataSource

    /** 모든 리플리카 중 최대 지연(초). 하트비트 방식. */
    public double current() {
        return replicas.stream()
            .mapToDouble(r -> r.queryForObject(
                "SELECT TIMESTAMPDIFF(MICROSECOND, ts, UTC_TIMESTAMP(6)) / 1e6 " +
                "  FROM replication_heartbeat WHERE id = 1", Double.class))
            .max().orElse(0.0);
    }

    /** 임계 아래로 내려올 때까지 최대 maxWait 동안 기다린다. 못 내려오면 false. */
    public boolean waitUntilBelow(double thresholdSec, Duration maxWait) {
        long deadline = System.nanoTime() + maxWait.toNanos();
        while (current() > thresholdSec) {
            if (System.nanoTime() > deadline) return false;
            try { Thread.sleep(5_000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); return false; }
        }
        return true;
    }
}

4. 안전망 — 사람이 아니라 코드·스키마가 지킨다

순서는 아카이브 → 검증 → (유예) → 드라이런 승인 → 게이트 있는 삭제 → 재발 방지(스케줄러·보존 정책)다. 각 단계가 "담당자가 기억한다"가 아니라 "코드가 다음 단계를 허가한다"로 연결돼야 한다.

4-1. 삭제 전 아카이브 검증 — 건수 + 체크섬 3중, 그리고 유예 기간 시니어 변별

그림 4. 아카이브 검증 절차 — 세 값 중 하나만 보면 각각 놓치는 것이 있고, 통과한 상한이 verified_until_id가 되어 삭제 루프의 천장이 된다.

4-4. 파티션 자동 생성 · 드랍 스케줄러 — 대가 5·6번을 코드가 처리한다

ensureFuturePartitions미래 파티션 항상 N개

없으면 다음 달 첫 INSERT가 실패한다. information_schema.PARTITIONS로 존재 확인 후 ADD PARTITION. SET SESSION lock_wait_timeout = 5로 MDL 대기 상한 — 못 잡으면 실패하고 다음 스케줄에 재시도.

dropExpiredPartitions만료 파티션 드랍 — 단, 검증된 것만

retention_policy의 보존 기간이 지난 파티션 중 archiveVerifier.isVerified(table, partition)가 참인 것만 DROP. 미검증이면 드랍하지 않고 알람 → 사람이 본다.

@Component
@RequiredArgsConstructor
public class PartitionMaintenanceScheduler {
    private final JdbcTemplate jdbc;
    private final RetentionPolicyRepository policies;   // 4-5: 테이블별 보존 기간·선행 생성 개수
    private final ArchiveVerifier archiveVerifier;
    private final AlertClient alert;

    @Scheduled(cron = "0 30 3 * * *")
    public void maintain() {
        for (RetentionPolicy p : policies.findAllPartitioned()) {
            ensureFuturePartitions(p);
            dropExpiredPartitions(p);
        }
    }

    /** 미래 파티션이 항상 aheadMonths개 존재하게 한다 — 이게 없으면 다음 달 첫 INSERT가 실패한다. */
    private void ensureFuturePartitions(RetentionPolicy p) {
        YearMonth now = YearMonth.now(ZoneOffset.UTC);
        for (int i = 1; i <= p.aheadMonths(); i++) {
            YearMonth ym = now.plusMonths(i);
            if (!partitionExists(p.table(), name(ym))) {
                jdbc.execute("SET SESSION lock_wait_timeout = 5");           // MDL 대기 상한
                jdbc.execute(("ALTER TABLE %s ADD PARTITION (PARTITION %s VALUES LESS THAN ('%s'))")
                    .formatted(p.table(), name(ym), ym.plusMonths(1).atDay(1)));
            }
        }
    }

    /** 보존 기간이 지난 파티션을 드랍한다 — 단, 아카이브 검증이 끝난 것만. */
    private void dropExpiredPartitions(RetentionPolicy p) {
        YearMonth oldestToKeep = YearMonth.now(ZoneOffset.UTC).minusMonths(p.retentionMonths());
        for (String partition : partitionsOlderThan(p.table(), oldestToKeep)) {
            if (p.archiveRequired() && !archiveVerifier.isVerified(p.table(), partition)) {
                alert.warn("[partition] %s.%s 보존 만료됐으나 아카이브 미검증 — 드랍 보류".formatted(p.table(), partition));
                continue;                                                    // 드랍하지 않는다. 사람이 본다.
            }
            jdbc.execute("SET SESSION lock_wait_timeout = 5");
            jdbc.execute("ALTER TABLE %s DROP PARTITION %s".formatted(p.table(), partition));
        }
    }

    private boolean partitionExists(String table, String partition) {
        Integer n = jdbc.queryForObject(
            "SELECT COUNT(*) FROM information_schema.PARTITIONS " +
            " WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = ? AND PARTITION_NAME = ?",
            Integer.class, table, partition);
        return n != null && n > 0;
    }
    // partitionsOlderThan(...)도 information_schema.PARTITIONS 의 PARTITION_DESCRIPTION 으로 계산
    private static String name(YearMonth ym) { return "p" + ym.getYear() + "%02d".formatted(ym.getMonthValue()); }
}
안전망을 지키는 안전망

스케줄러와 독립된 감시를 하나 더 — "미래 파티션이 2개 미만이면 경보". 스케줄러 자체가 배포 실수로 죽어 있을 때를 위한 것. MySQL Event Scheduler로 DB 안에서 같은 일을 할 수도 있다 — 앱 코드에 두면 배포·테스트·관측 경로가 다른 코드와 같아지고, DB에 두면 앱과 무관하게 돈다. 팀이 DB 쪽 스크립트를 얼마나 잘 관리하느냐로 고른다.

4-5. 보존 정책을 설계 시점에 — "이 행은 언제 죽는가"에 답이 없는 테이블은 만들지 않는다

가장 싼 대량 삭제는 처음부터 삭제가 쉬운 구조로 만든 테이블의 삭제다. 이벤트성 테이블(*_log, *_history, *_event)의 DDL PR은 다음 넷에 답해야 통과한다.

DDL PR이 답해야 할 네 질문
1
보존 기간"무기한"은 답이 아니다. 무기한이면 왜 RDB인지 답해야 한다.
2
삭제 방식파티션 DROP인지 청크 삭제인지. 파티션이면 PK에 created_at이 들어가고 FK가 없어야 하므로 지금 정해야 한다.
3
아카이브 여부와 목적지지우기 전에 어디로 보내는지, 안 보낸다면 그 합의가 어디 기록돼 있는지.
4
PK 단조 증가 또는 created_at 인덱스청크 삭제가 PK range로 가능한 구조인지.

이 답을 사람의 리뷰 기억이 아니라 기계가 읽는 자리에 둔다 — 테이블 COMMENT와 retention_policy 메타 테이블. 4-4의 스케줄러가 이 테이블을 읽으므로 "새 로그 테이블 추가 = 정책 행 하나 INSERT"가 된다.

  • 접근법 선택 근거: 파티션 유무 / 지울 비율 / 점검 창 가능 여부 (2-4)
  • 드라이런 계획서 첨부: 범위·건수 자릿수·EXPLAIN(type=range, key=PRIMARY)·예상 소요 (4-2)
  • 아카이브 검증(건수·XOR·SUM) 통과 + verified_until_id 기록 + 샘플 복원 테스트 (4-1)
  • 청크 루프에 게이트 6종(복제 지연·Threads_running·풀 사용률·청크 시간·시간 창·킬 스위치) (3-1)

  • 실행 중 관측 대시보드: 청크 시간·삭제 건수·복제 지연·풀 사용률

삭제는 테이블을 만들 때 이미 결정된 비용이고, 그 결정을 미룬 값을 2년 뒤 새벽 3시에 한꺼번에 치른 것이다.

6. 꼬리질문 셀프 테스트 — 먼저 소리 내어 답하고 펼친다

질문만 보고 30초 안에 답을 조립한 뒤 펼쳐서 빠진 조각을 확인한다. 배지가 붙은 문항은 시니어 변별·가산점 지점.

"청크 크기와 sleep은 어떻게 정하나요? 1,000이면 안전한가요?"

숫자가 아니라 측정 기준으로 답한다. 목표는 "청크 트랜잭션 하나가 수백 ms 안에 끝나고, 그동안 복제 지연·락 대기·Threads_running이 평소 수준을 벗어나지 않는 것".

  • 1,000에서 시작해 청크 시간과 복제 지연을 보며 두 배씩 올리고, 목표 시간의 2배를 넘으면 절반으로 — 적응형(3-2 adapt).
  • 행 크기·세컨더리 인덱스 수·디스크 종류에 따라 같은 1,000이 50ms일 수도 2초일 수도 있어 고정 숫자는 답이 될 수 없다.
  • sleep은 버퍼 풀·purge·복제본이 따라올 시간 — 대체로 청크 시간과 비슷한 길이에서 시작.
"DELETE ... LIMIT 1000을 반복하면 안 되나요? 훨씬 간단한데요."

세 가지 이유로 PK 범위가 낫다.

  1. LIMIT는 매번 인덱스 앞쪽부터 다시 스캔 — 방금 지운 행은 purge 전까지 delete-mark로 남아 다음 청크가 유령 엔트리를 건너뛰며 시작 → 갈수록 느려짐. PK 범위는 고정 구간 seek라 속도 일정.
  2. ORDER BY 없는 LIMIT는 비결정적 → statement binlog에서 unsafe 경고, 프라이머리·복제본이 다른 행을 지울 수 있음.
  3. 잠그는 범위가 예측되지 않는다 — PK 범위는 "이 구간"이라 말할 수 있지만 LIMIT는 옵티마이저가 고른 경로에 따라 다르다.

LIMIT가 허용되는 경우는 PK가 시간순이 아니어서 범위가 성립하지 않을 때뿐이고, 그때도 (created_at, id) 키셋으로 하한을 밀며 간다.

"파티셔닝하면 무엇을 잃나요? PK를 왜 바꿔야 하죠?" 시니어 변별

MySQL은 파티션 키 컬럼이 모든 유니크 키(PK 포함)에 들어 있어야 한다. 유니크 검사가 파티션 단위 로컬 인덱스로 이뤄지기 때문 — 글로벌 인덱스가 없으니 id만으로 유일성을 검사하려면 모든 파티션을 다 봐야 하고, MySQL은 그 비용 대신 제약을 택했다.

그래서 PRIMARY KEY (id) → (id, created_at). 잃는 것 넷:

  1. id 단독 유일성의 DB 보장 (채번기 책임)
  2. 세컨더리 인덱스 크기 (리프가 복합 PK를 품음)
  3. 업무 유니크 제약의 표현력 (UNIQUE(member_id, episode_id)에 created_at을 끼우는 순간 의미 소멸)
  4. JPA @Id의 단순함

여기에 FK 불가 · 프루닝 조건 없는 조회의 파티션 수 배수 seek · 파티션 고갈 시 INSERT 실패까지. 판단 기준은 "삭제가 잦은가"가 아니라 "이 테이블에 유니크 제약·FK·기간 없는 점 조회가 있는가" — 셋 다 없는 순수 시계열에서만 파티셔닝은 공짜에 가깝다.

"아카이브가 제대로 됐다는 걸 어떻게 보장하나요? 삭제한 뒤 아카이브가 깨져 있었다면요?" 시니어 변별

"보장"은 삭제 전에만 가능하므로 절차를 앞에 둔다.

  1. 범위 고정 후 원본·아카이브에서 COUNT + BIT_XOR(CRC32) + SUM(CRC32) 세 값 비교 (하나만으로는 건수 불일치·중복 적재를 각각 놓친다).
  2. 통과한 상한을 archive_verification에 기록, 삭제 루프는 그 값 이하만 — 검증과 삭제가 코드로 연결돼 순서를 어길 수 없다.
  3. 검증과 삭제 사이 유예 기간 + 샘플 복원 테스트 자동 실행 — 아카이브에서 읽어 원본과 대조하는 것이 "복구되는 백업"의 유일한 증거.

그래도 삭제 후 깨진 것을 발견했다면 남은 카드는 PITR로 삭제 직전 시점을 별도 인스턴스에 복원해 그 범위만 다시 추출하는 것 → 그래서 대량 삭제 일정은 백업 보존 기간 안에서 잡고 삭제 전 스냅샷을 하나 더 뜬다. 듣고 싶은 문장: "삭제는 되돌릴 수 없으니 되돌릴 수 있는 지점을 삭제 전에 만들어 둔다."

"다 지웠는데 디스크가 안 줄었습니다. 왜죠? 어떻게 회수하나요?" 가산점

InnoDB의 DELETE는 페이지를 비울 뿐 .ibd를 OS에 돌려주지 않는다. 빈 페이지는 그 테이블의 free 목록에 들어가 이후 INSERT가 재사용 — "앞으로 3개월치가 다시 쌓일 자리"로는 쓸모 있지만 디스크 알람은 그대로.

회수 방법은 셋뿐이고 전부 "테이블을 새로 쓰는 것": ① OPTIMIZE TABLE(= ALTER TABLE ... FORCE, 재구성 → 디스크 2배·MDL·복제 지연) ② 복사 후 RENAME(2-3) ③ 파티션 DROP(2-2, 파일 자체가 사라지므로 즉시). 그래서 "디스크 회수"가 목적이라면 청크 삭제는 절반의 답이고 처음부터 그 목적을 말하고 접근법을 골라야 한다. information_schema.TABLES.DATA_FREE로 미회수 공간을 숫자로 본다.

"PostgreSQL이면 같은 문제인가요?" 가산점

큰 그림은 같고 부품 이름이 다르다.

  • undo 대신 행의 옛 버전을 테이블 안에 남기는(dead tuple) MVCC → 대량 DELETE 후 VACUUM이 치우기 전까지 테이블·인덱스 bloat. VACUUM도 공간을 OS에 돌려주지 않는다(VACUUM FULL은 재작성 + 배타 락 = OPTIMIZE TABLE 위치, 무중단은 pg_repack).
  • 긴 트랜잭션이 VACUUM을 막아 bloat가 커지는 사슬 = InnoDB의 purge 정지.
  • 선언적 파티셔닝으로 DROP TABLE/DETACH PARTITION(CONCURRENTLY) 가능. PK·유니크에 파티션 키가 포함돼야 하는 제약은 PostgreSQL도 같다.
  • 차이: 파티션 테이블의 FK 지원 범위가 넓고, 복제가 WAL 스트리밍이라 "거대 TX 하나가 복제본을 막는" 양상이 binlog와 다르다.

질문의 목적은 MySQL 암기가 아니라 원리(과거 버전 보관 → 정리 지연 → 공간·성능 비용)를 다른 엔진에 옮겨 말할 수 있는가다.

"청크로 나누면 총 I/O가 줄어드나요?" 추가

아니다. 사슬 D(세컨더리 인덱스 랜덤 I/O)는 총액이 같다 — 나눠 낼 뿐이다. 삭제할 행 2억 × 세컨더리 인덱스 N개의 delete-mark는 청크 크기와 무관하게 정확히 그만큼 발생하고, purge의 재방문도 마찬가지다.

청크가 줄이는 것은 동시성 비용(사슬 A·B·C — 한 시점에 쥐는 undo·락·binlog 크기)이지 총 작업량이 아니다. sleep은 버퍼 풀이 숨 쉴 시간을 주는 것이지 비용을 없애지 않는다. 그래서 "총 I/O 최대"가 청크 삭제의 대가 칸에 들어가고, I/O 자체를 안 내려면 파티션 DROP이나 복사 후 RENAME(정렬 빌드)으로 가야 한다.

"run()에 @Transactional을 붙이면 정확히 무슨 일이 생기나요?" 추가

TransactionTemplate의 기본 전파가 REQUIRED라, 이미 열린 바깥 트랜잭션에 참여한다. tx.execute가 끝나도 커밋되지 않고 run()이 반환될 때 한 번에 커밋 → 청크 4만 개의 DELETE와 진행 위치 저장이 전부 한 트랜잭션. 코드는 청크처럼 보이는데 DB에는 1장의 한 방 그대로(사슬 A~E 전부).

덤으로 sleep도 트랜잭션 안이 되어 락·undo를 쥔 채 잔다. 리뷰 1순위인 이유. 정말 바깥 트랜잭션이 필요하다면 PROPAGATION_REQUIRES_NEW로 명시해야 하지만, 애초에 루프 메서드에 트랜잭션이 필요할 이유가 없다.

"진행 위치를 DELETE와 다른 트랜잭션(또는 파일)에 저장하면 어떤 경우가 생기나요?" 추가

두 순서 중 하나가 깨진다.

  • DELETE 커밋 → 위치 저장 전에 죽음: 재시작 시 같은 범위를 다시 지운다. PK 범위 삭제는 멱등이라 0건 삭제로 무해 — 이 방향은 괜찮다.
  • 위치 먼저 저장 → DELETE 전에 죽음: 재시작 시 그 범위를 건너뛴다. 지워지지 않은 구간이 영구히 남고 아무도 모른다 — 이 방향이 위험하다.

같은 트랜잭션에 넣으면 두 번째 경우가 원천 봉쇄된다. Spring Batch의 ExecutionContext가 커밋과 함께 저장되는 것도 같은 원리다.

"복사 후 RENAME에서 AUTO_INCREMENT를 왜 따로 맞추나요?" 추가

CREATE TABLE ... LIKE는 구조만 복사하고 카운터는 따라오지 않는다. 새 테이블은 1부터(또는 복사된 최대 PK + 1부터) 채번하려 하는데, RENAME 직후 들어오는 INSERT가 원본이 이미 발급한 id와 겹치면 PK 충돌 — 특히 델타를 나중에 따라잡을 때 충돌이 난다.

그래서 ALTER TABLE ..._new AUTO_INCREMENT = <원본 현재값보다 큰 값>을 명시한다. 채번기가 DB 밖(Snowflake/TSID)이면 이 문제는 없지만, 대신 파티션 대가 2번의 "id 유일성은 채번기 책임"이 이미 성립해 있다는 뜻이다.
