04 · RDB / SQL · 기본 ⭐ · 인덱스 ②

인덱스를 걸었는데도 풀스캔

원인 6종을 외우지 말고 "한 문장"에서 찢어내기 — 그리고 옵티마이저가 인덱스를 일부러 버리는 이유

Q. 인덱스를 걸었는데도 풀스캔이 발생하는 경우는 어떤 경우인가요?

핵심 관전 포인트 — 첫 답변으로 그대로 말한다

원인 목록을 외우는 게 아니라 "인덱스는 원본 값을 정렬해 둔 별도의 사본"이라는 한 문장에서 전부 도출한다. 이 문장에는 ① 저장된 것은 가공되지 않은 원본 값이고 ② 정렬은 왼쪽부터이며 ③ 이득을 보려면 연속된 한 구간으로, 그것도 충분히 작게 좁혀져야 한다는 세 전제가 들어 있다.

답변은 반드시 두 부류로 갈라서 말한다 — A 구조상 못 타는 경우 ① 컬럼에 함수·연산 ② 타입 불일치로 인한 암묵적 형변환 ③ 선행 와일드카드 LIKE '%kw%' ④ 복합 인덱스 선두 컬럼 미사용 ⑤ OR·부정 조건 — 와 B 탈 수 있는데 옵티마이저가 일부러 안 타는 경우 ⑥ 낮은 선택도.

후자의 근거가 랜덤 I/O vs 순차 I/O 비용 모델이다 — 세컨더리 인덱스 조회는 "인덱스에서 PK 얻기 → PK로 실제 행 다시 읽기" 2단계이고, 두 번째가 디스크 여기저기를 때리는 랜덤 I/O라서 대상 행이 전체의 일정 비율(흔히 20~30% 어림)을 넘으면 순차로 쭉 읽는 풀스캔이 더 싸다. 진단은 EXPLAIN의 type · key · rows · Extra 네 칸으로 한다.

30초 답변 스크립트 — "인덱스를 타지 않는 경우입니다"라는 동어반복 대신, 이 네 문장을 순서대로
  1. 전제 한 문장 — "인덱스는 원본 값을 왼쪽부터 정렬해 둔 별도 사본이라, 그 전제가 깨질 때 못 탑니다."
  2. 부류 A 다섯 — "구조상 못 타는 경우가 다섯입니다. 컬럼에 함수·연산, 타입 불일치로 인한 암묵적 형변환, 선행 와일드카드, 복합 인덱스 선두 컬럼 미사용, OR·부정 조건."
  3. 부류 B 하나 + 이유 — "탈 수 있는데 옵티마이저가 일부러 안 타는 경우가 낮은 선택도입니다. 세컨더리 인덱스는 PK를 얻고 행을 다시 읽는 2단계라 랜덤 I/O가 생기고, 대상이 전체의 20~30%쯤을 넘으면 순차 풀스캔이 더 쌉니다."
  4. 진단 — "EXPLAIN의 type·key·rows·Extra로 확인합니다."
1. 암기 카드 6종 2. 한 문장에서 도출 3. 부류 A 상세 4. 부류 B — 비용 모델 5. EXPLAIN 진단 6. 꼬리질문 셀프 테스트 한 줄 요약

1암기 카드 — 풀스캔 원인 6종

이 문항은 이해도 확인이 아니라 인출(retrieval) 테스트다. "이 목록이 머리에 있는 사람은 슬로 쿼리를 5분 만에 고치고, 없는 사람은 '인덱스 있는데 왜 느리지'에서 멈춘다." 여섯 장을 번호·부류와 함께 통째로 고정한다.

부류 A

구조상 못 탄다 (①~⑤)

인덱스로 시작점을 찍을 방법이 없다 → 쿼리·스키마를 고쳐야 풀린다
1
컬럼에 함수·연산
깨지는 전제 ① 원본 값 — 가공된 값은 인덱스에 없다
✗ WHERE DATE(created_at) = '2026-08-11'
✓ WHERE created_at >= '…08-11' AND created_at < '…08-12'
"컬럼은 맨몸으로, 연산은 상수 쪽으로"
2
타입 불일치 → 암묵적 형변환
깨지는 전제 ① 원본 값 — DB가 컬럼 쪽에 몰래 CAST를 씌운다
✗ WHERE phone = 01012345678
✓ WHERE phone = '01012345678'
"함수가 안 보여도 함수다 — 컬럼 쪽이 변환된다"
3
선행 와일드카드
깨지는 전제 ② 왼쪽부터 정렬 — 첫 글자를 모르면 시작점이 없다
✗ WHERE title LIKE '%결제%'
✓ WHERE title LIKE '결제%' / Full-Text
"사전에서 '가운데에 결제가 든 단어' 찾기"
4
복합 인덱스 선두 컬럼 미사용
깨지는 전제 ② 왼쪽부터 정렬 — leftmost prefix 위반
INDEX (user_id, created_at)
✗ WHERE created_at > ?
✓ WHERE user_id = ? AND created_at > ?
"선두가 빠지면 인덱스가 없는 것과 같다"
5
OR / 부정 조건
깨지는 전제 ③ 연속된 한 구간 — 구간이 갈라지거나 전 구간이 대상
✗ email = ? OR phone = ? / status != 'DONE'
✓ UNION ALL 분해 / IN ('READY','RUNNING',…)
"OR는 위험 신호 — EXPLAIN으로 확인 후 분해"
부류 B

탈 수 있는데 옵티마이저가 일부러 안 탄다 (⑥)

써봤자 손해라서 버린다 → 쿼리를 고쳐도 안 풀리고 인덱스 설계·데이터 분포를 바꿔야 한다
6
낮은 선택도 (카디널리티 ↓)
깨지는 전제 ③ 작은 구간 — 대상이 전체의 상당 비율이면 북마크 룩업(랜덤 I/O)이 순차 풀스캔보다 비싸다
✗ WHERE status = 'ACTIVE' -- 전체의 90%
✓ 복합 인덱스 / 부분 인덱스 / 커버링 인덱스
"옵티마이저가 옳다 — FORCE INDEX는 오처방"
이 구분 자체가 변별점

A는 "못 탄다", B는 "안 탄다". 부류를 나눠 말하지 못하면 B에 FORCE INDEX를 박아 넣는 오처방으로 간다 — 옵티마이저가 옳았던 상황에서 강제로 인덱스를 태우면 오히려 느려진다.

뉘앙스 한 줄: ⑤의 부정 조건은 A의 얼굴을 하고 있지만 속은 B(타봐야 이득이 없음)다.

암기 장치 — 2·2·2 리듬

여섯 개를 낱개로 외우면 긴장하면 둘째에서 끊긴다. 전제 셋 × 원인 둘로 묶어 "가공 둘, 왼쪽 둘, 구간 둘"이라고 리듬을 탄다. 첫 글자만 이으면 함·타 / 와·선 / 오·선.

함 · 타
가공 둘 — 원본 값이 아니다
① 함수·연산 / ② 타입 불일치
와 · 선
왼쪽 둘 — 시작점이 없다
③ 와일드카드 / ④ 선두 컬럼
오 · 선
구간 둘 — 갈라지거나 너무 크다
⑤ OR·부정 / ⑥ 선택도

인출 훈련 — 빈칸을 먼저 채우고 클릭해서 확인

면접 전날 이 여섯 칸을 보지 않고 소리 내어 말할 수 있어야 한다. 부류(A/B)까지 함께.

1
전제 ①이 깨짐 — 눈에 보이는 가공컬럼에 함수·연산 A
2
전제 ①이 깨짐 — 눈에 안 보이는 가공타입 불일치 → 암묵적 형변환 A
3
전제 ②가 깨짐 — 문자열의 왼쪽선행 와일드카드 LIKE '%kw%' A
4
전제 ②가 깨짐 — 복합 인덱스의 왼쪽복합 인덱스 선두 컬럼 미사용 A
5
전제 ③이 깨짐 — 구간이 갈라짐OR / 부정 조건(!=, NOT IN) A
6
전제 ③이 깨짐 — 구간이 너무 큼낮은 선택도 — 옵티마이저가 일부러 버림 B

2모든 항목은 한 문장에서 나온다

후보자가 꼬리질문에서 LOWER(email) = 'a@b.com'이 못 타는 이유를 "인덱스에 lower 처리된 값이 저장돼 있지 않기 때문"이라고 답한 것 — 이 추론 방식이 맞다. 그것이 전제 ①이고, 전제 ②·③만 얹으면 여섯 개가 순서대로 나온다.

전제내용깨지면 나오는 원인
① 원본 값 그대로인덱스에 저장된 건 컬럼의 가공되지 않은 값. 대문자로 바꾼 값도, 날짜만 잘라낸 값도, 숫자로 바꾼 값도 거기 없다① 함수·연산 / ② 암묵적 형변환
② 정렬은 왼쪽부터문자열은 첫 글자부터, 복합 인덱스는 첫 컬럼부터 정렬. 사전이 첫 글자 순인 것과 같다③ 선행 와일드카드 / ④ 선두 컬럼 미사용
③ 작고 연속된 한 구간정렬돼 있으니 시작점 하나, 끝점 하나를 찍고 그 사이만 훑는 게 인덱스의 이득. 구간이 여러 개로 갈라지거나 전체의 상당 부분이면 이득이 사라진다⑤ OR·부정 조건 / ⑥ 낮은 선택도

3부류 A — 구조상 못 타는 다섯 가지

3-1. 컬럼에 함수·연산을 씌웠다 ①

인덱스에는 created_at의 원본 타임스탬프가 정렬돼 있지, DATE(created_at)의 결과인 날짜가 정렬돼 있지 않다. "모든 행에 함수를 적용해봐야 그 값을 알 수 있다" = 모든 행을 읽어야 한다 = 풀스캔.

BEFORE — 못 탄다
-- created_at에 DATE()가 씌워져
-- 인덱스의 원본 값과 형태가 다르다
SELECT * FROM orders
WHERE DATE(created_at) = '2026-08-11';컬럼 가공
AFTER — 탄다
-- 컬럼은 맨몸, 조건을 "구간"으로
-- 08-11 00:00 지점을 찍고 08-12 직전까지 훑는다
SELECT * FROM orders
WHERE created_at >= '2026-08-11 00:00:00'시작점
  AND created_at <  '2026-08-12 00:00:00';끝점

산술 연산도 똑같다. 핵심 규칙은 "컬럼을 부등호 한쪽에 맨몸으로 남겨라".

연산은 상수 쪽으로 옮긴다
SELECT * FROM products WHERE price * 1.1 > 11000;컬럼이 곱셈에 참여
SELECT * FROM products WHERE price > 10000;값은 동일, 컬럼은 맨몸

-- 이건 괜찮다: 연산이 "상수 쪽"에서만 일어난다.
-- NOW() - INTERVAL 1 DAY 는 쿼리 시작 시 하나의 값으로 확정된다
SELECT * FROM orders WHERE created_at >= NOW() - INTERVAL 1 DAY;OK
가산점 도저히 함수를 뗄 수 없는 요구사항이라면 함수 기반 인덱스 / 생성 컬럼(generated column) + 인덱스가 정공법이다. "가공된 값이 인덱스에 없다"가 원인이니 가공된 값 자체를 인덱스로 만들어 두면 된다.
대소문자 무시 검색이 진짜 요구사항일 때
ALTER TABLE users ADD COLUMN email_lower VARCHAR(255) AS (LOWER(email)) STORED;
CREATE INDEX idx_users_email_lower ON users (email_lower);
-- 이제 WHERE email_lower = 'a@b.com' 이 인덱스를 탄다.
-- (대안: 대소문자 구분 없는 콜레이션 지정 — 애초에 함수가 필요 없어진다)

3-2. 타입이 안 맞아 암묵적 형변환 — 컬럼 쪽이 변환된다 ②

겉보기엔 함수가 하나도 없다. 그런데 DB가 몰래 컬럼에 형변환 함수를 씌운다. 이 항목이 무서운 이유는 쿼리만 봐서는 아무 문제가 없어 보인다는 점이다.

BEFORE — 못 탄다 (phone은 VARCHAR, 인덱스 있음)
-- 따옴표를 빠뜨려 숫자 리터럴과 비교
SELECT * FROM users WHERE phone = 01012345678;숫자 리터럴
-- DB 내부에서는 사실상 이렇게 해석된다:
--   WHERE CAST(phone AS SIGNED) = 1012345678= 3-1과 동일
-- 덤으로 선행 0이 날아가 결과까지 틀릴 수 있다
AFTER — 탄다
-- 컬럼 타입에 맞춰 문자열 리터럴로
SELECT * FROM users WHERE phone = '01012345678';타입 일치

-- 방향이 반대면 문제없다 (user_id BIGINT):
-- 리터럴 '100' 쪽이 숫자로 변환되고 컬럼은 맨몸
SELECT * FROM orders WHERE user_id = '100';OK
왜 하필 컬럼 쪽인가 문자열과 숫자를 비교하면 표준 규칙은 양쪽을 숫자로 맞춰 비교하는 것이다. 반대로 하면(리터럴을 문자열로) 결과 집합이 달라진다 — '01012345678', '1012345678', ' 1012345678'은 문자열로는 전부 다르지만 숫자로는 전부 같다. DB는 정확성을 위해 숫자 비교를 택하고, 그 대가로 "컬럼 전체를 숫자로 바꾸는" 비용을 치른다. 그 순간 인덱스는 무용지물이 된다.
가산점 실무에서 가장 아프게 터지는 곳은 JOIN이다. a.user_id가 BIGINT인데 b.user_id가 VARCHAR이면 조인 조건마다 형변환이 일어나 한쪽 테이블의 인덱스를 통째로 못 쓰고 조인이 풀스캔으로 퇴화한다. 문자셋·콜레이션이 다른 문자열 컬럼끼리의 조인도 같은 증상. 그래서 "같은 의미의 컬럼은 모든 테이블에서 같은 타입·같은 콜레이션"이 스키마 설계의 기본 규율이다.

3-3. 선행 와일드카드 LIKE '%kw%' ③

인덱스는 첫 글자부터 정렬돼 있으므로, 첫 글자를 모르면 트리를 내려갈 시작점을 찍을 수 없다. 사전에서 "가운데에 '결제'가 들어간 단어"를 찾으라면 처음부터 끝까지 넘기는 수밖에 없는 것과 같다.

BEFORE — 못 탄다
-- 시작점을 특정할 수 없다
SELECT * FROM posts WHERE title LIKE '%결제%';첫 글자 미상
AFTER — 탄다
-- '결제'로 시작하는 지점을 찍고 그 구간만
SELECT * FROM posts WHERE title LIKE '결제%';전방 일치

이건 튜닝으로 해결되는 문제가 아니라 B+Tree의 구조적 한계다. 요구사항이 진짜 "포함 검색"이라면 도구를 바꾼다 — 전문 검색 인덱스(Full-Text)나 검색 엔진(Elasticsearch 등).

가산점 접미사 검색만 필요하다면 값을 뒤집어 저장한 컬럼에 인덱스를 거는 트릭이 있다 — REVERSE(title)을 생성 컬럼으로 두고 LIKE '제결%'. "왼쪽을 모른다"가 문제니 왼쪽을 아는 형태로 데이터를 바꿔 둔다.

3-4. 복합 인덱스의 선두 컬럼을 안 썼다 (leftmost prefix 위반) ④

(user_id, created_at) 인덱스는 "user_id로 먼저 정렬하고, 같으면 created_at으로 정렬한" 하나의 트리다. 전화번호부가 "성 → 이름" 순이면 성만으로도 찾을 수 있지만 이름만으로는 못 찾는다 — 같은 이름이 책 전체에 흩어져 있기 때문이다.

CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);
SELECT * FROM orders WHERE created_at >= '2026-08-01';선두 user_id 없음
SELECT * FROM orders WHERE user_id = 100 AND created_at >= '2026-08-01';선두부터

-- 대안: 전역 최근순 조회가 진짜 요구사항이라면 인덱스를 새로 만든다
CREATE INDEX idx_orders_created ON orders (created_at);재설계

-- 변형 주의: 선두 컬럼에 "범위" 조건이 오면 그 뒤 컬럼은 정렬이 깨져 못 쓴다
-- (user_id가 여러 값에 걸치면 각 값마다 created_at 정렬이 따로 놀기 때문)
SELECT * FROM orders WHERE user_id > 100 AND created_at = '2026-08-11';user_id까지만 인덱스

여기서는 "선두 컬럼이 빠지면 인덱스가 아예 없는 것과 같다"만 확실히 붙잡는다. 조합별 사용 여부 표는 인덱스와 B+Tree §3 축 3, 컬럼 순서 규칙은 중급 "복합 인덱스 컬럼 순서" 문항에서.

3-5. OR로 묶인 조건, 그리고 부정 조건 ⑤

OR: 서로 다른 컬럼을 OR로 묶으면 인덱스 하나로는 시작점·끝점을 하나씩 찍을 수 없다. 두 개의 서로 다른 탐색이 필요한데 인덱스는 한 번에 하나의 트리만 탄다. 게다가 한쪽 컬럼에 인덱스가 없으면 어차피 전체를 봐야 하므로 나머지 한쪽의 인덱스도 무의미해진다.

BEFORE — 서로 다른 컬럼의 OR
-- 하나의 연속 구간으로 표현 불가
SELECT * FROM users
WHERE email = 'a@b.com' OR phone = '01012345678';구간 갈라짐
AFTER — 각자 자기 인덱스를 타는 두 쿼리로
SELECT * FROM users WHERE email = 'a@b.com'
UNION ALL
SELECT * FROM users WHERE phone = '01012345678'
  AND email <> 'a@b.com';중복 방지
-- 중복 제거를 DB에 맡기려면 UNION. 단 정렬 비용이 붙는다
같은 컬럼의 OR는 다르다 — IN으로 바꾸면 "여러 개의 짧은 구간 탐색"
SELECT * FROM orders WHERE status = 'READY' OR status = 'RUNNING';대개 처리되지만
SELECT * FROM orders WHERE status IN ('READY', 'RUNNING');의도 명확

부정 조건(!=, <>, NOT IN, NOT LIKE): "이 값이 아닌 것"은 정렬된 축 위에서 한 점을 빼고 나머지 전부다. 구간이 좌우로 갈라지고 그 합이 사실상 전체라 인덱스로 좁히는 의미가 없다.

BEFORE — "아닌 것"
-- DONE이 아닌 것 = 사실상 전 구간
SELECT * FROM jobs WHERE status != 'DONE';전 구간
AFTER — "인 것들의 열거"로 뒤집기
-- 짧은 구간 몇 개로 분해된다
SELECT * FROM jobs WHERE status IN ('READY','RUNNING','FAILED');열거
뉘앙스 엄밀히 말하면 부정 조건은 "못 탄다"기보다 "타봐야 이득이 없다"에 가깝고, 그래서 실제로는 ⑥번(부류 B)의 논리로 귀결된다. 면접에서 이 뉘앙스까지 붙이면 목록을 외운 게 아니라 이해했다는 신호다.
가산점 MySQL에는 OR를 만났을 때 여러 인덱스를 각각 타고 결과를 합치는 index merge(union) 최적화가 있다. 즉 OR가 항상 풀스캔은 아니다. 다만 합치는 비용 때문에 옵티마이저가 자주 포기하므로, "OR는 위험 신호이니 EXPLAIN으로 확인하고 필요하면 분해한다"가 실무 태도다.

4부류 B — 랜덤 I/O vs 순차 I/O, 옵티마이저가 일부러 버리는 이유

여기가 이 문항의 진짜 깊이다. 조건식은 완벽하고 인덱스도 멀쩡한데 EXPLAIN에 key: NULL이 뜬다. 왜 원하는 행만 골라 읽는 게, 전체를 다 읽는 것보다 비쌀 수 있는가? 답은 세 단계다 — (1) 세컨더리 인덱스 조회는 2단계다 → (2) 2단계는 랜덤 I/O다 → (3) 그래서 손익분기가 생긴다.

4-1. 세컨더리 인덱스 조회는 2단계다 — 북마크 룩업

InnoDB 기준으로, PK가 아닌 컬럼에 건 인덱스(세컨더리 인덱스)의 리프에는 행 전체가 아니라 (인덱스 컬럼 값, PK)만 들어 있다. 그래서 조회가 두 단계로 나뉜다.

도서관 비유 1단계는 색인 카드를 훑어 청구기호를 적는 것. 2단계는 그 청구기호를 들고 서가 사이를 뛰어다니며 책을 한 권씩 뽑는 것. 찾을 책이 10권이면 색인이 압도적으로 이득이다. 그런데 장서의 30%를 뽑아야 한다면? 서가 사이를 30만 번 왕복하느니 1번 서가부터 순서대로 쓸어 담는 게 훨씬 빠르다. 이게 풀스캔이다.

4-2. 풀스캔은 왜 "생각보다" 싼가 — 랜덤 I/O vs 순차 I/O

풀스캔이 싼 이유는 단순히 "인덱스를 안 뒤져서"가 아니다. 읽는 방식 자체가 다르다.

세컨더리 인덱스 + 북마크 룩업풀 테이블 스캔
읽는 총량대상 행만테이블 전체
I/O 패턴랜덤 흩어진 페이지순차 이어진 페이지
미리 읽기거의 못 씀적극 활용
행 1건당 비용비쌈 (트리 탐색 + 랜덤 페이지)쌈 (연 페이지의 행 전부 사용)
비용이 비례하는 것대상 행 수테이블 크기 (일정)
유리한 구간대상이 소수일 때대상이 다수일 때

4-3. 그래서 손익분기가 생긴다

대상 행이 전체의 일정 비율을 넘는 순간 "적게 읽지만 비싸게 읽기"가 "많이 읽지만 싸게 읽기"에 진다. 옵티마이저는 이 두 비용을 통계로 추정해 싼 쪽을 고른다 — 그러니 낮은 선택도에서 인덱스를 버리는 건 고장이 아니라 계산의 결과다.

4-4. 선택도 vs 카디널리티 — 두 번 연속 빠뜨린 축

카디널리티 cardinality — 컬럼의 속성

그 컬럼에 서로 다른 값이 몇 개나 있는가.

status = 3개 (낮다) · email = 행 수만큼 (높다)

선택도 selectivity — 조건의 속성

그 조건이 전체 행을 몇 %로 좁히는가.

status='ACTIVE' → 90% (낮다) · status='FAILED' → 1% (높다)

인과 한 줄 값 종류가 몇 개 안 되면(카디널리티 ↓) 어떤 값으로 조회해도 결과가 전체의 상당 비율이 된다(선택도 ↓) → 북마크 룩업이 대량 발생 → 옵티마이저가 풀스캔을 고른다. 그래서 status, is_deleted, 성별 같은 컬럼의 단독 인덱스는 대개 무의미하다. 인덱스를 새로 걸지 판단할 때 이 축이 자동으로 나와야 한다.
같은 인덱스, 값만 다른데 계획이 갈린다 — orders 100만 건, ACTIVE 90만 / DONE 9만 / FAILED 1만
CREATE INDEX idx_orders_status ON orders (status);

EXPLAIN SELECT * FROM orders WHERE status = 'ACTIVE';
-- type: ALL, key: NULL인덱스가 있는데도 안 쓴다
--   90만 행 북마크 룩업 90만 번  vs  100만 행 순차 스캔 1회 → 후자가 압도적으로 싸다. 옵티마이저가 옳다.

EXPLAIN SELECT * FROM orders WHERE status = 'FAILED';
-- type: ref, key: idx_orders_status같은 인덱스인데 이번엔 탄다
--   대상 1만 행(1%). 북마크 룩업 1만 번이 훨씬 싸다.

후보자가 답한 "풀스캔이 비용이 싼 경우"라는 방향은 옳았다. 거기에 왜 싼지의 근거 — 북마크 룩업의 랜덤 I/O — 를 붙이면 완성이다.

4-5. 처방 세 가지 — 쿼리가 아니라 인덱스 설계를 바꾼다

① 복합 인덱스status로 좁힌 뒤 정렬까지 인덱스가 처리하게 한다.
(status, created_at)
"최근 것 20개"만 보는 화면이라면 대상이 90만이어도 리프 앞쪽 20개만 읽고 끝.
② 부분 인덱스희귀한 값만 인덱싱해 크기와 쓰기 비용을 동시에 줄인다 (PostgreSQL 등).
… ON orders (created_at) WHERE status = 'FAILED'
③ 커버링 인덱스필요한 컬럼을 전부 인덱스에 담아 2단계 자체를 없앤다.
(status, created_at, amount)
북마크 룩업 0회 → Extra: Using index. 랜덤 I/O가 사라지므로 손익분기 논리 자체가 무력화된다.

4-6. 이 절이 떠받치는 다음 주제들

랜덤 I/O vs 순차 I/O, 그리고 북마크 룩업은 뒤에 나오는 여러 문항의 공통 토대다. 여기서 잡아두면 나머지가 파생으로 풀린다.

클러스터드 vs 세컨더리세컨더리 리프에 PK가 들어 있다는 사실이 북마크 룩업의 출발점이자 "PK가 크면 모든 세컨더리 인덱스가 비대해진다"의 근거.
커버링 인덱스북마크 룩업(2단계)을 아예 제거. 랜덤 I/O가 왜 비싼지를 알아야 커버링이 왜 몇 배의 처리량을 뽑는지 설명된다.
깊은 페이지네이션LIMIT 20 OFFSET 100000이 느린 이유 = 버릴 10만 건에 대해서도 북마크 룩업을 다 수행. 커서 기반 재설계의 근거.
SELECT … FOR UPDATE가 인덱스를 못 탈 때스캔한 모든 행에 락 → 테이블 전체가 잠기는 사고. "인덱스를 못 탄다"는 성능을 넘어 동시성 사고가 된다.

5진단 절차 — EXPLAIN에서 무엇을 보는가

"인덱스 있는데 왜 느리지"에서 멈추지 않으려면 볼 칸이 정해져 있어야 한다. MySQL 기준 네 칸.

칸무엇을 보나나쁜 신호좋은 신호
type접근 방식ALL(테이블 풀스캔), index(인덱스 풀스캔 — 이것도 전부 읽는 것)const / eq_ref / ref / range 쪽으로 갈수록 좋다
key실제로 사용한 인덱스NULL = 아무 인덱스도 안 씀의도한 인덱스 이름
rows읽을 것으로 예상한 행 수전체 행 수에 가깝다 / 실제 결과 건수와 자릿수가 다르다결과 건수와 비슷한 규모
Extra부가 동작Using filesort(별도 정렬), Using temporary(임시 테이블)Using index = 커버링, 북마크 룩업 0회 — 최고의 신호
원인 ⑥이 의심되면 — 실제로 몇 %인지 세어보는 것이 가장 확실하다
-- 이 조건이 전체의 몇 %를 고르는지 직접 확인
SELECT COUNT(*) FILTER (WHERE status = 'ACTIVE') * 100.0 / COUNT(*) AS pct FROM orders;
-- MySQL 이라면:
SELECT SUM(status = 'ACTIVE') * 100.0 / COUNT(*) FROM orders;
-- 이 값이 20~30%를 넘는다면 옵티마이저가 인덱스를 버린 판단이 옳을 가능성이 높다

5-1. rows는 예상값이다 — 통계가 낡으면 오판한다

옵티마이저는 실제 데이터를 세어보고 판단하는 게 아니라 DB가 주기적으로 수집해 둔 통계 정보(값의 분포, 카디널리티)를 보고 추정한다. 대량 적재·대량 삭제 직후에는 이 통계가 현실과 크게 어긋나 "멀쩡한 쿼리가 어느 날 갑자기 느려지는" 현상이 생긴다.

실행 계획이 이상하면 통계부터 갱신하고 다시 EXPLAIN
ANALYZE TABLE orders;   -- MySQL
ANALYZE orders;         -- PostgreSQL
가산점 MySQL 8.0 이상과 PostgreSQL은 EXPLAIN ANALYZE로 쿼리를 실제로 실행해 예상값이 아닌 실측 행 수와 소요 시간을 보여준다. 예상 rows와 실측이 크게 벌어지면 그게 곧 "통계가 틀렸다"는 증거다. 다만 실제로 실행되므로 운영 DB의 무거운 쿼리에는 주의.

6꼬리질문 셀프 테스트

질문만 보고 먼저 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 답의 구조(순서·예외·조건)까지 맞아야 한다.

타입 불일치에서 왜 하필 컬럼 쪽이 변환되나요? 리터럴을 컬럼 타입으로 바꾸면 인덱스를 살릴 수 있잖아요?

결과 집합이 달라지기 때문에 그렇게 할 수 없다. 문자열과 숫자의 비교는 숫자 기준으로 맞추는 것이 표준 규칙인데, 문자열 → 숫자 변환은 여러 값이 하나로 뭉개지는 비가역 변환이다. '01012345678', '1012345678', ' 1012345678'은 문자열로는 다르지만 숫자로는 모두 같다. DB가 편의를 위해 리터럴 쪽을 문자열로 바꾼다면 원래 매칭되어야 할 행이 조용히 누락된다.

DB는 성능보다 정확성을 우선해 숫자 비교를 택하고, 그 대가로 컬럼 전체에 변환 함수를 씌운다. 그래서 원인 ①과 완전히 같은 상황이 된다. 반대로 숫자 컬럼에 문자열 리터럴을 비교하면 리터럴 쪽만 변환되므로 인덱스를 그대로 탄다 — 방향에 따라 결과가 다르다는 게 포인트.

시니어 변별 OR를 UNION ALL로 바꾸면 항상 빨라지나요?

아니다. 세 가지를 먼저 확인한다.

  1. 의미가 바뀔 수 있다 — 두 조건을 모두 만족하는 행은 UNION ALL에서 두 번 나온다. UNION으로 바꾸면 중복은 제거되지만 정렬·해시 비용이 붙는다.
  2. 양쪽 다 인덱스를 탈 수 있어야 이득이다 — 한쪽 컬럼에 인덱스가 없으면 분해해봐야 그 갈래가 풀스캔이라 총비용이 오히려 늘 수 있다.
  3. 같은 컬럼의 OR라면 분해가 아니라 IN이 정답 — 옵티마이저가 여러 구간 탐색으로 잘 처리한다.

게다가 MySQL의 index merge가 이미 잘 처리하고 있는 경우도 있으므로, 재작성 전후를 EXPLAIN으로 비교해 근거를 만든 다음에 바꾼다. "OR 보면 무조건 UNION"은 튜닝이 아니라 미신이다.

!=나 NOT IN은 정말 무조건 인덱스를 못 타나요?

"못 탄다"보다 "타봐야 이득이 없는 게 보통이다"가 정확한 표현이다. 부정 조건은 정렬 축 위에서 한 점을 뺀 나머지 전부를 가리키므로 결과가 대개 전체의 대부분이 되고, 그러면 4절의 논리대로 풀스캔이 이긴다.

예외는 두 가지. ⑴ 값이 극단적으로 편중돼 "아닌 것"이 오히려 소수인 경우 — 99%가 'ACTIVE'인 컬럼의 status != 'ACTIVE'는 1%만 고르므로 인덱스가 유효할 수 있다. ⑵ 커버링 인덱스인 경우 — 북마크 룩업이 없으니 인덱스 전체를 훑어도(type: index) 폭이 좁은 인덱스를 읽는 편이 넓은 테이블 전체를 읽는 것보다 싸다.

즉 부정 조건 항목은 ⑤번(구조) 얼굴을 하고 있지만 속은 ⑥번(비용)이다.

시니어 변별 인덱스는 제대로 탔는데(key에 인덱스가 잡혔는데)도 느립니다. 어디를 봐야 하나요?

key가 채워졌다고 끝이 아니다. 확인 순서:

  1. type이 index인지 — 인덱스를 처음부터 끝까지 읽는 인덱스 풀스캔. 이름만 인덱스지 전수 조사다.
  2. rows가 큰가 — 인덱스로 좁히긴 했는데 그 뒤 북마크 룩업이 대량 발생하는 전형. SELECT *를 필요한 컬럼만으로 줄이고 커버링 인덱스를 검토한다. 이 하나로 몇 배가 빨라지는 일이 흔하다.
  3. Extra에 Using filesort / Using temporary — 정렬·그룹핑을 인덱스가 처리하지 못해 별도 작업이 붙었다. 정렬 컬럼을 인덱스 뒤쪽에 넣어 해결.
  4. OFFSET이 큰가 — 깊은 페이지네이션이면 버릴 행에 대해서도 룩업을 전부 수행하므로, 커서 기반(마지막으로 본 키 이후를 조회)으로 재설계.
  5. 락 대기인가 — 실행 계획은 멀쩡한데 느리다면 성능이 아니라 동시성 문제일 수 있다.
시니어 변별 옵티마이저가 틀렸다고 확신할 때 FORCE INDEX를 써도 되나요?

마지막 수단이고, 그 앞에 밟아야 할 단계가 있다.

  1. ANALYZE TABLE로 통계 정보를 갱신한다 — "옵티마이저가 이상해요" 사례의 상당수가 낡은 통계 탓이고, 이건 힌트 없이 해결된다.
  2. EXPLAIN ANALYZE로 예상 rows와 실측을 비교해 정말로 오판인지 근거를 만든다.
  3. 오판이 맞다면 인덱스 설계 자체를 고치는 쪽을 먼저 — 복합 인덱스로 선택도를 올리거나 커버링으로 만들면 옵티마이저가 알아서 고른다.

그래도 안 되면 힌트를 쓰되, 힌트는 코드에 박히는 부채다. 지금은 옳아도 데이터 분포가 바뀌거나 DB를 업그레이드하면 그 힌트가 틀린 선택을 고정시키고, 옵티마이저는 개선되었는데 우리 쿼리만 과거에 묶인다. 쓴다면 주석으로 "왜 강제했는지, 언제 재검토할지"를 남기는 것까지가 세트다.

가산점 그럼 풀스캔은 언제나 나쁜 건가요?

아니다. 테이블이 작으면(페이지 몇 개 수준) 풀스캔이 정답이다 — 인덱스를 타면 트리 탐색 오버헤드만 추가된다. 배치·집계처럼 어차피 대부분의 행을 읽어야 하는 작업도 풀스캔이 맞다.

판단 기준은 "풀스캔이냐 아니냐"가 아니라 "읽는 행 수가 결과 건수에 비해 합리적인가"다. 100건을 반환하려고 100만 행을 읽었다면 문제고, 90만 건을 반환하려고 100만 행을 읽었다면 정상이다. 이 관점을 가지면 EXPLAIN의 rows를 "무조건 작아야 하는 숫자"가 아니라 결과 건수와의 비율로 읽게 된다.

선택도와 카디널리티는 뭐가 다른가요? 왜 status 컬럼 단독 인덱스는 무의미하다고 하나요?

카디널리티는 컬럼의 속성(서로 다른 값이 몇 개인가), 선택도는 조건의 속성(그 조건이 전체를 몇 %로 좁히는가)이다. 둘은 인과로 이어진다 — 값 종류가 몇 개 안 되면 어떤 값으로 조회해도 결과가 전체의 상당 비율이 된다.

status가 3종이면 평균적으로 한 값이 전체의 1/3이고, 실제 분포는 대개 더 편중돼 있다(ACTIVE 90%). 대상이 이 정도면 북마크 룩업 비용이 순차 풀스캔을 넘어 옵티마이저가 인덱스를 버린다. 인덱스는 만들어져서 쓰기 비용만 먹고 읽기에는 안 쓰이는 최악의 상태가 된다.

단, "무의미"는 단독일 때다. 희귀 값(FAILED 1%)만 조회한다면 유효하고, (status, created_at)처럼 복합 인덱스의 선두로 두면 "status로 좁힌 뒤 정렬"을 인덱스가 처리해 의미가 생긴다. 인덱스를 새로 걸지 판단할 때 쓰기 빈도 / 선택도 / 기존 인덱스와의 중복 / EXPLAIN 검증 네 축 중 선택도가 자동으로 나와야 한다.

(user_id, created_at) 인덱스에 WHERE created_at > ? AND user_id = ?처럼 WHERE 절의 컬럼 순서를 바꿔 쓰면 선두 컬럼 규칙 위반인가요?

아니다. 선두 컬럼 규칙은 "WHERE 절에 선두 컬럼 조건이 존재하는가"의 문제이지, 조건을 적은 순서의 문제가 아니다. 옵티마이저는 조건들을 인덱스 컬럼 순서에 맞춰 알아서 재배열한다. 위 쿼리는 user_id = ?가 있으니 인덱스를 정상적으로 탄다.

위반이 되는 것은 user_id 조건 자체가 없을 때(원인 ④), 그리고 주의할 변형은 선두 컬럼에 범위 조건이 와서 뒤 컬럼의 정렬이 깨지는 경우다. "적은 순서"와 "인덱스 컬럼 순서"를 혼동하는 것은 흔한 오개념이라 면접에서 일부러 던지는 질문이다.

옵티마이저는 대상 행이 전체의 몇 %인지 어떻게 아나요? 쿼리를 실행해보지도 않았는데.

실행하지 않는다. DB가 주기적으로 수집해 둔 통계 정보 — 테이블 행 수, 컬럼의 카디널리티, 값의 분포 — 를 보고 추정한다. EXPLAIN의 rows가 "예상값"인 이유가 이것이다.

따라서 대량 적재·삭제 직후처럼 통계가 현실과 어긋나면 옵티마이저는 틀린 지도로 길을 고른다 — 어제까지 인덱스를 타던 쿼리가 오늘 풀스캔이 되거나 그 반대가 된다. 처방은 ANALYZE TABLE로 통계를 갱신하는 것이고, EXPLAIN ANALYZE로 예상 rows와 실측을 비교하면 통계가 틀렸는지 근거를 잡을 수 있다. 이 질문은 FORCE INDEX 꼬리질문의 1단계와 같은 뿌리다.

SELECT *가 이 주제와 무슨 상관이 있나요?

SELECT *는 북마크 룩업을 강제한다. 인덱스 리프에는 (인덱스 컬럼, PK)만 있으므로, 인덱스에 없는 컬럼을 하나라도 요구하면 반드시 2단계(클러스터드 인덱스 재탐색)를 거쳐야 한다. 모든 컬럼을 요구하는 SELECT *는 커버링 인덱스가 성립할 여지를 원천 봉쇄한다.

두 가지 결과가 따라온다. ⑴ 인덱스를 탔더라도 대상 행마다 랜덤 I/O가 붙어 rows가 크면 느리다. ⑵ 옵티마이저 입장에서는 "이 쿼리는 무조건 2단계"이므로 손익분기 논리가 그대로 적용돼 낮은 선택도에서 인덱스를 버린다. 필요한 컬럼만 적으면 커버링 인덱스로 2단계를 없앨 수 있고, 그러면 선택도가 낮아도 인덱스 경로가 이길 수 있다. "SELECT * 줄이기"가 스타일 문제가 아니라 I/O 패턴을 바꾸는 튜닝인 이유다.

type: index(인덱스 풀스캔)와 type: ALL(테이블 풀스캔)의 차이는? 전자는 인덱스니까 괜찮은 건가요?

둘 다 "처음부터 끝까지 다 읽는다"는 점은 같다. 차이는 읽는 대상이 폭이 좁은 인덱스냐 폭이 넓은 테이블이냐다. 인덱스는 몇 개 컬럼만 담고 있어 같은 행 수라도 페이지 수가 훨씬 적으므로, 커버링이 성립하는 경우(필요한 컬럼이 전부 인덱스 안에 있는 경우)에는 인덱스 풀스캔이 테이블 풀스캔보다 싸다. 옵티마이저가 type: index + Extra: Using index를 고르는 상황이 이것이다.

반대로 커버링이 안 되는 type: index는 최악에 가깝다 — 인덱스 전체를 훑고 나서 행마다 북마크 룩업까지 하기 때문이다. 그래서 type: index를 보면 반드시 Extra에 Using index가 있는지 같이 본다.

SSD를 쓰면 랜덤 I/O가 싸지니까 손익분기 논리는 사라지지 않나요?

줄어들지만 사라지지 않는다. SSD에서는 헤드 이동이 없어 랜덤 읽기와 순차 읽기의 격차가 HDD보다 훨씬 작아지지만, 여전히 차이가 난다. 게다가 손익분기를 만드는 요인은 스토리지 종류만이 아니다.

⑴ 북마크 룩업은 행 1건당 B+Tree 탐색 1회라는 CPU·페이지 접근 비용이 있고 이건 디스크와 무관하다. ⑵ 순차 스캔은 미리 읽기로 요청 횟수 자체를 줄이고, 연 페이지의 행을 전부 쓴다. ⑶ 랜덤 룩업은 한 행 쓰자고 페이지 하나를 여는 일을 반복한다. 그래서 손익분기의 위치는 스토리지·버퍼 풀 상태에 따라 움직여도 존재 자체는 남는다 — 면접에서 "정확한 %"가 아니라 "존재와 이유"를 말하라는 것이 이 때문이다.

한 줄 요약

"인덱스는 원본 값을 왼쪽부터 정렬해 둔 사본"이라는 한 문장에서 여섯 가지 원인이 전부 도출된다 — 원본을 가공하면(함수·암묵적 형변환) 못 찾고, 왼쪽을 비우면(선행 와일드카드·선두 컬럼 미사용) 시작점을 못 찍고, 구간이 갈라지거나(OR·부정 조건) 너무 크면(낮은 선택도) 이득이 없다. 앞의 다섯은 구조상 못 타는 것이고 마지막 하나는 북마크 룩업의 랜덤 I/O 때문에 옵티마이저가 일부러 안 타는 것이며, 이 둘을 갈라 말하는 것이 곧 변별점이다.
