4. RDB / SQL / 데이터 모델링

인덱스를 걸었는데도 풀스캔 — 원인 6종을 한 문장에서 도출하기

📖 약 23분 🧩 7개 섹션 0/7 섹션 이해
🎯 핵심 관전 포인트

원인 목록을 외우는 게 아니라 "인덱스는 원본 값을 정렬해 둔 별도의 사본"이라는 한 문장에서 전부 도출한다. 이 문장에는 ① 저장된 것은 가공되지 않은 원본 값이고 ② 정렬은 왼쪽부터이며 ③ 이득을 보려면 연속된 한 구간으로, 그것도 충분히 작게 좁혀져야 한다는 세 전제가 들어 있다. 그리고 답변은 반드시 두 부류로 갈라서 말한다 — 구조상 못 타는 경우(① 컬럼에 함수·연산 ② 타입 불일치로 인한 암묵적 형변환 ③ 선행 와일드카드 LIKE '%kw%' ④ 복합 인덱스 선두 컬럼 미사용 ⑤ OR·부정 조건)와, 탈 수 있는데 옵티마이저가 일부러 안 타는 경우(⑥ 낮은 선택도). 후자의 근거가 랜덤 I/O vs 순차 I/O 비용 모델이다 — 세컨더리 인덱스 조회는 "인덱스에서 PK 얻기 → PK로 실제 행 다시 읽기" 2단계이고, 두 번째가 디스크 여기저기를 때리는 랜덤 I/O라서 대상 행이 전체의 일정 비율(흔히 20~30% 어림)을 넘으면 순차로 쭉 읽는 풀스캔이 더 싸다. 진단은 EXPLAIN의 type · key · rows · Extra 네 칸으로 한다.

면접 질문

"인덱스를 걸었는데도 풀스캔이 발생하는 경우는 어떤 경우인가요?"

관련 질문: "인덱스는 어떻게 동작하나요? B+Tree 구조를 설명해주세요." "LIKE '%keyword%' 검색이 인덱스를 못 타는 이유는?"

출제 의도rationale의 표현 그대로 — "함수 적용, 타입 불일치, 낮은 선택도 등 원인이 다양한데, 이 목록이 머리에 있는 사람은 슬로 쿼리를 5분 만에 고치고 없는 사람은 '인덱스 있는데 왜 느리지'에서 멈춘다." 즉 이 문항은 이해도 확인이 아니라 인출(retrieval) 테스트다. 장애 상황에서 목록이 즉시 튀어나오는지, 그리고 그 목록을 암기가 아니라 구조에서 도출하는지를 본다. 앞 문항(인덱스와 B+Tree)이 "구조를 아는가"라면, 이 문항은 "그 구조로 현상을 설명할 수 있는가"이다.
1

모든 항목은 한 문장에서 나온다

▾

암기 목록은 긴장하면 두 개쯤에서 끊긴다. 대신 문장 하나를 붙잡고 거기서 찢어내는 방식으로 가면 여섯 개가 순서대로 나온다.

💡

인덱스란, 인덱스 컬럼의 값과 PK를 함께 담아 그 값 기준으로 정렬해 둔 별도의 사본이다.

이 한 문장에 숨은 전제가 셋이다.

전제내용깨지면 나오는 원인
① 원본 값 그대로인덱스에 저장된 건 컬럼의 가공되지 않은 값이다. 대문자로 바꾼 값도, 날짜만 잘라낸 값도, 숫자로 바꾼 값도 거기 없다①번(함수·연산), ②번(암묵적 형변환)
② 정렬은 왼쪽부터문자열은 첫 글자부터, 복합 인덱스는 첫 컬럼부터 정렬된다. 사전이 첫 글자 순으로 정렬된 것과 같다③번(선행 와일드카드), ④번(선두 컬럼 미사용)
③ 이득은 "작고 연속된 한 구간"에서만정렬돼 있으니 시작점 하나, 끝점 하나를 찍고 그 사이만 훑는 게 인덱스의 이득이다. 구간이 여러 개로 갈라지거나, 구간이 전체의 상당 부분이면 이득이 사라진다⑤번(OR·부정 조건), ⑥번(낮은 선택도)

후보자가 꼬리질문에서 정확히 짚었던 것도 바로 전제 ①이다 — LOWER(email) = 'a@b.com'이 인덱스를 못 타는 이유를 "인덱스에 lower 처리된 값이 저장돼 있지 않기 때문"이라고 답한 것. 이 추론 방식이 맞다. 여기에 전제 ②·③만 얹으면 여섯 개가 다 나온다.

체크리스트 — 이 표 하나로 인출한다

▾

면접장에서든 장애 대응 중이든, 이 표를 머릿속에 펼치는 것이 목표다. 부류를 나눠 말하는 것 자체가 변별점이므로 표의 마지막 칸이 가장 중요하다.

#원인깨지는 전제못 타는 예 → 고친 예부류
①컬럼에 함수·연산 적용① 원본 값WHERE DATE(created_at) = '2026-08-11'<br>→ WHERE created_at >= '2026-08-11' AND created_at < '2026-08-12'A. 구조상 못 탐
②타입 불일치로 인한 암묵적 형변환① 원본 값WHERE phone = 01012345678<br>→ WHERE phone = '01012345678'A. 구조상 못 탐
③선행 와일드카드② 왼쪽부터 정렬WHERE title LIKE '%결제%'<br>→ WHERE title LIKE '결제%' / 전문 검색 인덱스A. 구조상 못 탐
④복합 인덱스 선두 컬럼 미사용② 왼쪽부터 정렬(user_id, created_at) 인덱스에 WHERE created_at > ?<br>→ 선두 조건 추가 or 인덱스 재설계A. 구조상 못 탐
⑤OR / 부정 조건(!=, NOT IN)③ 작고 연속된 구간WHERE email = ? OR phone = ?<br>→ UNION ALL로 분해A. 구조상 못 탐(구간이 갈라짐)
⑥낮은 선택도(카디널리티)③ 작고 연속된 구간WHERE status = 'ACTIVE' (전체의 90%)<br>→ 복합 인덱스 / 부분 인덱스 / 쿼리 재설계B. 탈 수 있는데 안 탐

부류 A는 옵티마이저가 아무리 쓰고 싶어도 인덱스로 시작점을 찍을 방법이 없는 경우다. 쿼리(또는 스키마)를 고쳐야 풀린다. 부류 B는 인덱스를 쓸 수는 있는데 써봤자 손해라서 옵티마이저가 계산 끝에 일부러 버린 경우다. 쿼리를 고쳐도 안 풀리고, 데이터 분포나 인덱스 설계 자체를 바꿔야 한다.

💡

이 구분을 못 하면 부류 B에 FORCE INDEX를 박아 넣는 잘못된 처방으로 간다. 옵티마이저가 옳았던 상황에서 강제로 인덱스를 태우면 오히려 느려진다.

3

부류 A — 구조상 못 타는 다섯 가지

▾

3-1. 컬럼에 함수·연산을 씌웠다

가장 흔하고, 가장 알아채기 쉬운 형태다. 인덱스에는 created_at의 원본 타임스탬프가 정렬돼 있지, DATE(created_at)의 결과인 날짜가 정렬돼 있지 않다. "모든 행에 함수를 적용해봐야 그 값을 알 수 있다" = 모든 행을 읽어야 한다 = 풀스캔.

sql
-- ❌ 못 탄다: created_at에 DATE() 함수가 씌워져 인덱스의 원본 값과 형태가 다르다
SELECT * FROM orders WHERE DATE(created_at) = '2026-08-11';

-- ✅ 탄다: 컬럼은 맨몸으로 두고, 조건을 "구간"으로 바꾼다
--    인덱스 리프에서 08-11 00:00:00 지점을 찍고 08-12 00:00:00 직전까지 훑는다
SELECT * FROM orders
WHERE created_at >= '2026-08-11 00:00:00'
  AND created_at <  '2026-08-12 00:00:00';

산술 연산도 똑같다. 핵심 규칙은 "컬럼을 부등호 한쪽에 맨몸으로 남겨라" 이다.

sql
-- ❌ 못 탄다: 컬럼이 곱셈에 참여했다
SELECT * FROM products WHERE price * 1.1 > 11000;

-- ✅ 탄다: 연산을 상수 쪽으로 옮겼다 (값은 동일)
SELECT * FROM products WHERE price > 10000;

-- ✅ 이건 괜찮다: 연산이 컬럼이 아니라 "상수 쪽"에서만 일어난다
--    NOW() - INTERVAL 1 DAY는 쿼리 시작 시 하나의 값으로 확정된다
SELECT * FROM orders WHERE created_at >= NOW() - INTERVAL 1 DAY;

(가산점 포인트) 도저히 함수를 뗄 수 없는 요구사항이라면 함수 기반 인덱스(functional index) / 생성 컬럼(generated column) + 인덱스 라는 정공법이 있다. "가공된 값이 인덱스에 없다"가 원인이니, 가공된 값 자체를 인덱스로 만들어 두면 된다.

sql
-- 대소문자 무시 검색이 진짜 요구사항일 때
ALTER TABLE users ADD COLUMN email_lower VARCHAR(255)
  AS (LOWER(email)) STORED;
CREATE INDEX idx_users_email_lower ON users (email_lower);
-- 이제 WHERE email_lower = 'a@b.com' 이 인덱스를 탄다.
-- (대안: 콜레이션을 대소문자 구분 없는 것으로 지정 — 애초에 함수가 필요 없어진다)

3-2. 타입이 안 맞아 암묵적 형변환이 일어났다 — 컬럼 쪽이 변환된다

겉보기엔 함수가 하나도 없다. 그런데 DB가 몰래 컬럼에 형변환 함수를 씌운다. 이 항목이 무서운 이유는 쿼리만 봐서는 아무 문제가 없어 보인다는 점이다.

sql
-- phone은 VARCHAR(20), 인덱스 있음
-- ❌ 못 탄다: 따옴표를 빠뜨려 숫자 리터럴과 비교했다
SELECT * FROM users WHERE phone = 01012345678;
--   DB 내부에서는 사실상 이렇게 해석된다:
--   WHERE CAST(phone AS SIGNED) = 1012345678   ← 컬럼에 함수가 씌워진 꼴 = 3-1과 동일
--   덤으로 '01012345678'의 선행 0이 날아가 결과까지 틀릴 수 있다

-- ✅ 탄다: 컬럼 타입에 맞춰 문자열 리터럴로 비교
SELECT * FROM users WHERE phone = '01012345678';

왜 하필 컬럼 쪽이 변환되는가가 이 항목의 핵심이고, 면접에서 파고드는 지점이다. 문자열과 숫자를 비교하면 표준적인 규칙은 양쪽을 숫자로 맞춰 비교하는 것이다. 반대로 하면(리터럴을 문자열로) 결과 집합이 달라지기 때문이다 — '01012345678', '1012345678', ' 1012345678'은 문자열로는 전부 다르지만 숫자로는 전부 같다. DB는 정확성을 위해 숫자 비교를 택하고, 그 대가로 "컬럼 전체를 숫자로 바꾸는" 비용을 치른다. 그 순간 인덱스는 무용지물이 된다.

방향이 반대면 문제가 없다는 것도 함께 알아두면 좋다.

sql
-- user_id가 BIGINT일 때
-- ✅ 이건 탄다: 리터럴 '100' 쪽이 숫자 100으로 변환되고, 컬럼은 맨몸 그대로다
SELECT * FROM orders WHERE user_id = '100';

(가산점 포인트) 실무에서 이게 가장 아프게 터지는 곳은 JOIN이다. a.user_id가 BIGINT인데 b.user_id가 VARCHAR이면, 조인 조건마다 형변환이 일어나 한쪽 테이블의 인덱스를 통째로 못 쓰고 조인이 풀스캔으로 퇴화한다. 문자셋·콜레이션이 다른 문자열 컬럼끼리의 조인도 같은 증상을 낸다. 그래서 "같은 의미의 컬럼은 모든 테이블에서 같은 타입·같은 콜레이션" 이 스키마 설계의 기본 규율이다.

3-3. 선행 와일드카드 LIKE '%kw%'

전제 ②가 깨지는 경우다. 인덱스는 첫 글자부터 정렬돼 있으므로, 첫 글자를 모르면 트리를 내려갈 시작점을 찍을 수 없다. 사전에서 "가운데에 '결제'가 들어간 단어"를 찾으라면 처음부터 끝까지 넘기는 수밖에 없는 것과 똑같다.

sql
-- ❌ 못 탄다: 시작점을 특정할 수 없다
SELECT * FROM posts WHERE title LIKE '%결제%';

-- ✅ 탄다: '결제'로 시작하는 지점을 찍고 그 구간만 훑으면 된다
SELECT * FROM posts WHERE title LIKE '결제%';

이건 튜닝으로 해결되는 문제가 아니라 B+Tree의 구조적 한계다. 요구사항이 진짜 "포함 검색"이라면 해법은 도구를 바꾸는 쪽이다 — 전문 검색 인덱스(Full-Text) 나 검색 엔진(Elasticsearch 등). 접미사 검색만 필요하다면 값을 뒤집어 저장한 컬럼에 인덱스를 거는 트릭도 있다 (REVERSE(title)을 생성 컬럼으로 두고 LIKE '제결%').

3-4. 복합 인덱스의 선두 컬럼을 안 썼다 (leftmost prefix 위반)

(user_id, created_at) 인덱스는 "user_id로 먼저 정렬하고, 같으면 created_at으로 정렬한" 하나의 트리다. 전화번호부가 "성 → 이름" 순으로 정렬돼 있으면 성만으로도 찾을 수 있지만, 이름만으로는 못 찾는다 — 같은 이름이 책 전체에 흩어져 있기 때문이다.

sql
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at);

-- ❌ 못 탄다: 선두 컬럼 user_id 조건이 없다
SELECT * FROM orders WHERE created_at >= '2026-08-01';

-- ✅ 탄다: 선두 컬럼부터 붙었다
SELECT * FROM orders WHERE user_id = 100 AND created_at >= '2026-08-01';

-- ✅ 대안: 전역 최근순 조회가 진짜 요구사항이라면 인덱스를 새로 만든다
CREATE INDEX idx_orders_created ON orders (created_at);

주의할 변형이 하나 더 있다. 선두 컬럼에 범위 조건이 오면 그 뒤 컬럼은 정렬이 깨져 못 쓴다.

sql
-- △ user_id 범위까지만 인덱스로 좁히고, created_at은 걸러내는 용도로만 쓰인다
--   (user_id가 여러 값에 걸치면 각 값마다 created_at 정렬이 따로 놀기 때문)
SELECT * FROM orders WHERE user_id > 100 AND created_at = '2026-08-11';

컬럼 순서 규칙은 중급의 "복합 인덱스 컬럼 순서" 문항에서 더 파고들지만, 여기서는 "선두 컬럼이 빠지면 인덱스가 아예 없는 것과 같다" 만 확실히 붙잡으면 된다. 자세한 조합별 사용 여부 표는 인덱스와 B+Tree §3 축 3에 정리돼 있다.

3-5. OR 로 묶인 조건, 그리고 부정 조건

전제 ③의 "연속된 한 구간"이 깨지는 경우다.

OR: 서로 다른 컬럼을 OR로 묶으면, 인덱스 하나로는 시작점·끝점을 하나씩 찍을 수 없다. 두 개의 서로 다른 탐색이 필요한데 인덱스는 한 번에 하나의 트리만 탄다. 게다가 한쪽 컬럼에 인덱스가 없으면 어차피 전체를 다 봐야 하므로 나머지 한쪽의 인덱스도 무의미해진다.

sql
-- ❌ 두 조건이 서로 다른 컬럼 → 하나의 연속 구간으로 표현 불가
SELECT * FROM users WHERE email = 'a@b.com' OR phone = '01012345678';

-- ✅ 각각 자기 인덱스를 타는 두 쿼리로 분해한다
SELECT * FROM users WHERE email = 'a@b.com'
UNION ALL
SELECT * FROM users WHERE phone = '01012345678'
  AND email <> 'a@b.com';   -- ← 두 조건을 모두 만족하는 행의 중복 방지
--   (중복 제거를 DB에 맡기려면 UNION ALL 대신 UNION. 단 정렬 비용이 붙는다)

같은 컬럼에 대한 OR는 상황이 다르다. 이건 IN으로 바꾸면 옵티마이저가 여러 개의 짧은 구간 탐색으로 처리할 수 있어 그대로 인덱스를 탄다.

sql
-- △ 이대로도 대개 처리되지만
SELECT * FROM orders WHERE status = 'READY' OR status = 'RUNNING';
-- ✅ 의도가 명확하고 옵티마이저도 다루기 쉽다
SELECT * FROM orders WHERE status IN ('READY', 'RUNNING');

부정 조건(!=, <>, NOT IN, NOT LIKE): "이 값이 아닌 것"은 정렬된 축 위에서 한 점을 빼고 나머지 전부를 뜻한다. 구간이 좌우로 갈라지고, 그 합이 사실상 전체다. 그래서 인덱스로 좁히는 의미가 없다.

sql
-- ❌ status가 DONE이 아닌 것 = 사실상 전 구간
SELECT * FROM jobs WHERE status != 'DONE';

-- ✅ "아닌 것"을 "인 것들의 열거"로 뒤집는다 → 짧은 구간 몇 개로 분해된다
SELECT * FROM jobs WHERE status IN ('READY', 'RUNNING', 'FAILED');
💡

엄밀히 말하면 부정 조건은 "못 탄다"기보다 "타봐야 이득이 없다"에 가깝고, 그래서 실제로는 ⑥번(부류 B)의 논리로 귀결된다. 면접에서 이 뉘앙스까지 붙이면 목록을 외운 게 아니라 이해했다는 신호가 된다.

(가산점 포인트) MySQL에는 OR를 만났을 때 여러 인덱스를 각각 타고 그 결과를 합치는 index merge(union) 최적화가 있다. 즉 OR가 항상 풀스캔인 것은 아니다. 다만 두 인덱스 결과를 합치는 비용 때문에 옵티마이저가 자주 포기하므로, "OR는 위험 신호이니 EXPLAIN으로 확인하고 필요하면 분해한다" 가 실무 태도다.

4

부류 B — 랜덤 I/O vs 순차 I/O, 옵티마이저가 일부러 버리는 이유

▾

여기가 이 문항의 진짜 깊이다. 조건식은 완벽하고 인덱스도 멀쩡한데 EXPLAIN에 key: NULL이 뜬다. 왜 원하는 행만 골라 읽는 게, 전체를 다 읽는 것보다 비쌀 수 있는가?

4-1. 세컨더리 인덱스 조회는 2단계다 — 북마크 룩업

InnoDB 기준으로, PK가 아닌 컬럼에 건 인덱스(세컨더리 인덱스)의 리프에는 행 전체가 아니라 (인덱스 컬럼 값, PK) 만 들어 있다. 그래서 조회가 두 단계로 나뉜다.

text
[1단계] 세컨더리 인덱스 B+Tree 탐색
  status = 'ACTIVE' 인 리프 구간을 찾아 옆으로 훑으며 PK를 수집한다.
  → 리프가 연결 리스트로 이어져 있으므로 이 단계는 대체로 순차적이고 싸다.
  결과: [PK=8231, PK=4, PK=99120, PK=577, PK=31, ...]   ← 값이 뒤죽박죽

[2단계] 수집한 PK 하나하나로 클러스터드 인덱스(= 테이블 본체)를 다시 탐색
  PK=8231 → 트리 타고 내려가 행 읽기
  PK=4    → 트리 타고 내려가 행 읽기
  PK=99120→ 트리 타고 내려가 행 읽기
  ...
  → 이게 "북마크 룩업(bookmark lookup) / back to table".
    PK 값이 흩어져 있으니 읽는 디스크 페이지도 흩어진다 = 랜덤 I/O

핵심은 2단계가 "행 하나당 트리 탐색 한 번"이라는 것이다. 대상이 30만 행이면 트리 탐색을 30만 번 한다. 게다가 그 30만 번이 디스크(또는 버퍼 풀)의 서로 멀리 떨어진 페이지를 찌른다.

💡

도서관 비유 1단계는 색인 카드를 훑어 청구기호를 적는 것. 2단계는 그 청구기호를 들고 서가 사이를 뛰어다니며 책을 한 권씩 뽑는 것. 찾을 책이 10권이면 색인이 압도적으로 이득이다. 그런데 장서의 30%를 뽑아야 한다면? 서가 사이를 30만 번 왕복하느니 1번 서가부터 순서대로 쓸어 담는 게 훨씬 빠르다. 이게 풀스캔이다.

4-2. 풀스캔은 왜 "생각보다" 싼가

풀스캔이 싼 이유는 단순히 "인덱스를 안 뒤져서"가 아니다.

  • 순차 I/O: 페이지를 물리적으로 이어진 순서대로 읽는다. 디스크(특히 회전 디스크)에서 순차 읽기와 랜덤 읽기의 비용 차이는 크고, SSD에서도 여전히 차이가 난다.
  • 미리 읽기(read-ahead): DB는 "앞으로 이 근처를 계속 읽겠구나"를 감지해 여러 페이지를 한꺼번에 미리 가져온다. 랜덤 접근에는 이 최적화가 안 걸린다.
  • 행 하나당 오버헤드가 없다: 페이지를 열면 그 안의 행을 전부 쓴다. 반면 북마크 룩업은 한 행 쓰자고 페이지 하나를 여는 일이 반복될 수 있다.

정리하면 이렇다.

세컨더리 인덱스 + 북마크 룩업풀 테이블 스캔
읽는 총량대상 행만테이블 전체
I/O 패턴랜덤 (흩어진 페이지)순차 (이어진 페이지)
미리 읽기거의 못 씀적극 활용
행 1건당 비용비쌈(트리 탐색 + 랜덤 페이지)쌈
유리한 구간대상이 소수일 때대상이 다수일 때

그래서 손익분기가 생긴다. 대상 행이 전체의 일정 비율을 넘는 순간 "적게 읽지만 비싸게 읽기"가 "많이 읽지만 싸게 읽기"에 진다. 흔히 인용되는 어림값이 전체의 20~30% 안팎인데, 이건 DB 종류·버전·스토리지·행 크기· 버퍼 풀 상태에 따라 달라지는 경험적 기준이지 고정 상수가 아니다. 면접에서는 정확한 수치보다 "손익분기가 존재한다는 사실과 그 이유" 가 훨씬 중요하다.

4-3. 그래서 status, is_deleted 같은 컬럼은 인덱스가 무시된다

선택도(selectivity) 는 그 조건이 전체 행을 몇 %로 좁히는가이고, 카디널리티(cardinality) 는 그 컬럼에 서로 다른 값이 몇 개나 있는가다. 값 종류가 몇 개 안 되면(카디널리티가 낮으면) 어떤 값으로 조회해도 결과가 전체의 상당 비율이 된다(선택도가 낮다).

sql
-- orders 100만 건, status는 'ACTIVE' 90만 / 'DONE' 9만 / 'FAILED' 1만
CREATE INDEX idx_orders_status ON orders (status);

EXPLAIN SELECT * FROM orders WHERE status = 'ACTIVE';
-- type: ALL, key: NULL   ← 인덱스가 있는데도 안 쓴다
--   이유: 90만 행에 대해 북마크 룩업 90만 번 vs 100만 행 순차 스캔 1회.
--         후자가 압도적으로 싸다. 옵티마이저의 판단이 옳다.

EXPLAIN SELECT * FROM orders WHERE status = 'FAILED';
-- type: ref, key: idx_orders_status   ← 같은 인덱스인데 이번엔 탄다
--   이유: 대상이 1만 행(1%). 북마크 룩업 1만 번이 훨씬 싸다.

같은 컬럼, 같은 인덱스인데 값에 따라 계획이 달라진다는 이 사실이 "옵티마이저는 비용을 계산한다"의 가장 좋은 실증이다. 후보자가 답한 "풀스캔이 비용이 싼 경우"라는 방향은 옳았고, 여기에 왜 싼지의 근거가 바로 위의 랜덤/순차 비용 모델이다.

처방은 세 가지다.

sql
-- ① 복합 인덱스: status로 좁힌 뒤 정렬까지 인덱스가 처리하게 한다
CREATE INDEX idx_orders_status_created ON orders (status, created_at);
--   "최근 것 20개"만 보는 화면이라면 대상이 90만이어도 리프 앞쪽 20개만 읽고 끝난다.

-- ② 부분 인덱스(조건부 인덱스, PostgreSQL 등에서 지원)
--   희귀한 값만 인덱싱해 인덱스 크기와 쓰기 비용을 동시에 줄인다
CREATE INDEX idx_orders_failed ON orders (created_at) WHERE status = 'FAILED';

-- ③ 커버링 인덱스: 필요한 컬럼을 전부 인덱스에 담아 2단계 자체를 없앤다
CREATE INDEX idx_orders_status_cover ON orders (status, created_at, amount);
SELECT status, created_at, amount FROM orders WHERE status = 'ACTIVE';
--   → 인덱스만 읽고 끝. 북마크 룩업 0회. EXPLAIN Extra에 "Using index"

4-4. 이 절이 떠받치는 다음 주제들

랜덤 I/O vs 순차 I/O, 그리고 북마크 룩업은 뒤에 나오는 여러 문항의 공통 토대다. 여기서 확실히 잡아두면 나머지가 파생으로 풀린다.

  • 클러스터드 vs 세컨더리 인덱스 — 세컨더리 리프에 PK가 들어 있다는 사실이 북마크 룩업의 출발점이자, "PK가 크면 모든 세컨더리 인덱스가 비대해진다"의 근거.
  • 커버링 인덱스 — 북마크 룩업(2단계)을 아예 제거하는 기법. 위 ③번. 랜덤 I/O가 왜 비싼지를 알아야 커버링이 왜 몇 배의 처리량을 뽑는지 설명된다.
  • 깊은 페이지네이션 — LIMIT 20 OFFSET 100000이 느린 이유가 정확히 "버릴 10만 건에 대해서도 북마크 룩업을 다 수행한다"이다. 커서 기반으로 재설계하는 근거가 여기서 나온다.
  • SELECT ... FOR UPDATE가 인덱스를 못 탈 때 — 인덱스를 못 타면 스캔한 모든 행에 락이 걸려 테이블 전체가 잠기는 사고로 이어진다. 즉 "인덱스를 못 탄다"는 성능 문제를 넘어 동시성 사고가 된다.

구조 쪽 배경은 인덱스와 B+Tree §4에 정리돼 있다.

5

진단 절차 — EXPLAIN에서 무엇을 보는가

▾

"인덱스 있는데 왜 느리지"에서 멈추지 않으려면 볼 칸이 정해져 있어야 한다. MySQL 기준 네 칸이다.

sql
EXPLAIN SELECT * FROM orders
WHERE DATE(created_at) = '2026-08-11' AND status = 'ACTIVE';
칸무엇을 보나나쁜 신호
type접근 방식ALL(테이블 풀스캔), index(인덱스 풀스캔 — 이것도 전부 읽는 것)
key실제로 사용한 인덱스NULL = 아무 인덱스도 안 씀
rows읽을 것으로 예상한 행 수전체 행 수에 가깝다 / 실제 결과 건수와 자릿수가 다르다
Extra부가 동작Using filesort(별도 정렬), Using temporary(임시 테이블)

좋은 신호도 함께 외워두면 대비가 된다 — type이 const/eq_ref/ref/range 쪽으로 갈수록 좋고, Extra의 Using index는 커버링 인덱스가 걸려 북마크 룩업이 사라졌다는 뜻이라 최고의 신호다.

5-1. 판단 흐름

text
1) key 가 NULL 인가?
   ├─ 예 → 인덱스를 아예 안 썼다.
   │        ├─ WHERE 절에 함수·연산이 있나?            → 원인 ①
   │        ├─ 컬럼 타입과 리터럴 타입이 다른가?        → 원인 ②
   │        ├─ LIKE '%...' 형태인가?                   → 원인 ③
   │        ├─ 복합 인덱스인데 선두 컬럼 조건이 없나?    → 원인 ④
   │        ├─ OR / != / NOT IN 이 있나?               → 원인 ⑤
   │        └─ 위 어느 것도 아니다                     → 원인 ⑥ (선택도)
   │             SELECT COUNT(*) 로 대상 비율을 재서 확인한다
   └─ 아니오 → 인덱스는 탔다. 그런데도 느리다면
            ├─ rows 가 큰가?              → 북마크 룩업 과다 (커버링 인덱스 검토)
            ├─ Extra 에 filesort 가 있나? → 정렬이 인덱스 순서와 안 맞는다
            └─ 의도한 인덱스가 아닌가?     → 통계 정보 노후 (ANALYZE TABLE)

원인 ⑥이 의심되면 실제로 몇 %인지 세어보는 것이 가장 확실한 확인법이다.

sql
-- 이 조건이 전체의 몇 %를 고르는지 직접 확인한다
SELECT COUNT(*) FILTER (WHERE status = 'ACTIVE') * 100.0 / COUNT(*) AS pct
FROM orders;
-- MySQL이라면: SELECT SUM(status='ACTIVE') * 100.0 / COUNT(*) FROM orders;
-- 이 값이 20~30%를 넘는다면 옵티마이저가 인덱스를 버린 판단이 옳을 가능성이 높다.

5-2. rows는 예상값이다 — 통계 정보가 낡으면 오판한다

옵티마이저는 실제 데이터를 세어보고 판단하는 게 아니라, DB가 주기적으로 수집해 둔 통계 정보(각 값의 분포, 카디널리티) 를 보고 추정한다. 대량 적재나 대량 삭제 직후에는 이 통계가 현실과 크게 어긋나서 "멀쩡한 쿼리가 어느 날 갑자기 느려지는" 현상이 생긴다.

sql
-- 실행 계획이 이상하면 통계부터 갱신하고 다시 EXPLAIN
ANALYZE TABLE orders;   -- MySQL
-- PostgreSQL: ANALYZE orders;

(가산점 포인트) MySQL 8.0 이상과 PostgreSQL은 EXPLAIN ANALYZE 로 쿼리를 실제로 실행해 예상값이 아닌 실측 행 수와 소요 시간을 보여준다. 예상 rows와 실측이 크게 벌어지면 그게 곧 "통계가 틀렸다"는 증거다. 다만 실제로 실행되므로 운영 DB의 무거운 쿼리에는 주의해야 한다.

결과 집합이 달라지기 때문에 그렇게 할 수 없다. 문자열과 숫자의 비교는 숫자 기준으로 맞추는 것이 표준 규칙인데, 문자열 → 숫자 변환은 여러 값이 하나로 뭉개지는 비가역 변환이다. '01012345678', '1012345678', ' 1012345678'은 문자열로는 다르지만 숫자로는 모두 같은 값이 된다. 만약 DB가 편의를 위해 리터럴 쪽을 문자열로 바꾼다면, 원래 매칭되어야 할 행이 조용히 누락된다. DB는 성능보다 정확성을 우선해 숫자 비교를 택하고, 그 대가로 컬럼 전체에 변환 함수를 씌운다. 그래서 원인 ①과 완전히 같은 상황이 된다. 반대로 숫자 컬럼에 문자열 리터럴을 비교하면 리터럴 쪽만 변환되므로 인덱스를 그대로 탄다 — 방향에 따라 결과가 다르다는 게 포인트다.

아니다. 세 가지를 먼저 확인해야 한다. ⑴ 의미가 바뀔 수 있다 — 두 조건을 모두 만족하는 행은 UNION ALL에서 두 번 나온다. UNION으로 바꾸면 중복은 제거되지만 정렬·해시 비용이 붙는다. ⑵ 양쪽 다 인덱스를 탈 수 있어야 이득이다 — 한쪽 컬럼에 인덱스가 없으면 분해해봐야 그 갈래가 풀스캔이라 총비용이 오히려 늘 수 있다. ⑶ 같은 컬럼의 OR라면 분해가 아니라 IN이 정답이다. 이건 옵티마이저가 여러 구간 탐색으로 잘 처리한다. 게다가 MySQL의 index merge가 이미 잘 처리하고 있는 경우도 있으므로, 재작성 전후를 EXPLAIN으로 비교해 근거를 만든 다음에 바꾼다. "OR 보면 무조건 UNION"은 튜닝이 아니라 미신이다.

"못 탄다"보다 "타봐야 이득이 없는 게 보통이다"가 정확한 표현이다. 부정 조건은 정렬 축 위에서 한 점을 뺀 나머지 전부를 가리키므로 결과가 대개 전체의 대부분이 되고, 그러면 4절의 논리대로 풀스캔이 이긴다. 예외는 두 가지다. ⑴ 값이 극단적으로 편중돼 있어 "아닌 것"이 오히려 소수인 경우 — 예컨대 99%가 'ACTIVE'인 컬럼의 status != 'ACTIVE'는 1%만 고르므로 인덱스가 유효할 수 있다. ⑵ 커버링 인덱스인 경우 — 북마크 룩업이 없으니 인덱스 전체를 훑어도(type: index) 폭이 좁은 인덱스를 읽는 편이 넓은 테이블 전체를 읽는 것보다 싸다. 즉 부정 조건 항목은 사실 ⑤번(구조) 얼굴을 하고 있지만 속은 ⑥번(비용)이다.

key가 채워졌다고 끝이 아니다. 확인 순서는 이렇다. ⑴ type이 index인지 본다 — 이건 "인덱스를 처음부터 끝까지 읽는" 인덱스 풀스캔이라 이름만 인덱스지 전수 조사다. ⑵ rows가 큰가 — 인덱스로 좁히긴 했는데 그 뒤 북마크 룩업이 대량 발생 하는 전형적 케이스다. SELECT *를 필요한 컬럼만으로 줄이고 커버링 인덱스를 검토한다. 이 하나로 몇 배가 빨라지는 일이 흔하다. ⑶ Extra에 Using filesort / Using temporary — 정렬이나 그룹핑을 인덱스가 처리하지 못해 별도 작업이 붙었다. 정렬 컬럼을 인덱스 뒤쪽에 넣어 해결한다. ⑷ OFFSET이 큰가 — 깊은 페이지네이션이면 버릴 행에 대해서도 룩업을 전부 수행하므로, 커서 기반(마지막으로 본 키 이후를 조회)으로 재설계한다. ⑸ 락 대기인가 — 실행 계획은 멀쩡한데 느리다면 성능이 아니라 동시성 문제일 수 있다.

마지막 수단이고, 그 앞에 밟아야 할 단계가 있다. 순서는 ⑴ ANALYZE TABLE로 통계 정보를 갱신한다 — 실무에서 "옵티마이저가 이상해요" 사례의 상당수가 낡은 통계 탓이고, 이건 힌트 없이 해결된다. ⑵ EXPLAIN ANALYZE로 예상 rows와 실측을 비교해 정말로 오판인지 근거를 만든다. ⑶ 오판이 맞다면 인덱스 설계 자체를 고치는 쪽을 먼저 본다 — 복합 인덱스로 선택도를 올리거나 커버링으로 만들면 옵티마이저가 알아서 고른다. 그래도 안 되면 힌트를 쓰되, 힌트는 코드에 박히는 부채임을 인지해야 한다. 지금은 옳아도 데이터 분포가 바뀌거나 DB를 업그레이드하면 그 힌트가 틀린 선택을 고정시키고, 옵티마이저는 개선되었는데 우리 쿼리만 과거에 묶인다. 쓴다면 주석으로 "왜 강제했는지, 언제 재검토할지"를 남기는 것까지가 세트다.

아니다. 테이블이 작으면(페이지 몇 개 수준) 풀스캔이 정답이다. 인덱스를 타면 트리 탐색 오버헤드만 추가된다. 배치·집계처럼 어차피 대부분의 행을 읽어야 하는 작업도 풀스캔이 맞다. 판단 기준은 "풀스캔이냐 아니냐"가 아니라 "읽는 행 수가 결과 건수에 비해 합리적인가" 이다. 100건을 반환하려고 100만 행을 읽었다면 문제고, 90만 건을 반환하려고 100만 행을 읽었다면 정상이다. 이 관점을 가지면 EXPLAIN의 rows를 "무조건 작아야 하는 숫자"가 아니라 결과 건수와의 비율로 읽게 된다.

✅ 한 줄 요약

"인덱스는 원본 값을 왼쪽부터 정렬해 둔 사본"이라는 한 문장에서 여섯 가지 원인이 전부 도출된다 — 원본을 가공하면(함수·암묵적 형변환) 못 찾고, 왼쪽을 비우면(선행 와일드카드·선두 컬럼 미사용) 시작점을 못 찍고, 구간이 갈라지거나 (OR·부정 조건) 너무 크면(낮은 선택도) 이득이 없다. 앞의 다섯은 구조상 못 타는 것이고 마지막 하나는 북마크 룩업의 랜덤 I/O 때문에 옵티마이저가 일부러 안 타는 것이며, 이 둘을 갈라 말하는 것이 곧 변별점이다.
