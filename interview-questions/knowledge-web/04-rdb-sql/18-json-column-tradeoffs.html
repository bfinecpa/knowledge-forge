RDB의 JSON 컬럼 트레이드오프
"귀찮아서 jsonb"와 "비정형이라 jsonb"를 가르는 규율

면접 질문: "RDB의 JSON 컬럼은 언제 쓰고 언제 피하나요? 인덱싱과 스키마 진화 관점의 트레이드오프는?"

핵심 관전 포인트 — JSON 컬럼(PostgreSQL에서는 jsonb)은 "행마다 모양이 다른 데이터를 DDL 없이 담는 자유"를 사는 대신, RDB가 컬럼에 공짜로 얹어 주던 네 가지 — ① 인덱스(값의 정렬된 사본) ② 타입·제약(DB가 지키는 불변식) ③ 좁은 갱신(바뀐 만큼만 쓰기) ④ 통계(플래너가 행 수를 맞출 근거) — 를 반납하는 거래다. PostgreSQL은 ①을 표현식 인덱스·GIN으로 상당 부분 되찾게 해 주지만 "미리 정한 키"만 빠르고, ③은 MVCC 위에서 오히려 더 비싸다 — 키 하나를 바꿔도 문서 전체가 새 튜플 버전으로 다시 쓰이고 (TOAST 청크까지) WAL·죽은 튜플로 번진다. ④는 우회가 가장 늦게 오는 손실이다 — 플래너는 문서 안 키의 분포를 모르므로 추정 행 수가 상수가 되고, 그 쿼리가 조인의 한 축이면 조인 방식과 순서까지 통째로 어긋난다. 그래서 판별은 취향이 아니라 네 질문이다: ⑴ 그 안의 값이 WHERE·JOIN·GROUP BY·ORDER BY의 대상인가 ⑵ 스키마가 행마다 진짜 다른가 ⑶ 쓰기 후 부분 수정이 잦은가 ⑷ DB가 지켜야 할 불변식인가. 하나라도 "예"면 컬럼(또는 별도 테이블), 넷 다 "아니오"인 데이터 — 외부 원문 보존, 희소(sparse) 속성, 통째로 읽고 쓰는 문서 — 가 jsonb의 자리다. 쓰기로 했다면 안전망을 함께 든다: 조회 조건이 된 키는 표현식 인덱스로 승격, CHECK + jsonb 연산자로 스키마 검증, 버전 필드로 세대 관리. 그리고 스키마 진화의 정체를 정직하게 말한다 — jsonb는 마이그레이션을 없앤 것이 아니라 DB의 DDL 한 번을 애플리케이션 읽기 코드의 영구 분기로 옮긴 것이다.
  • 1
    먼저 "거래"로 규정한다 — jsonb는 DDL 없이 행마다 다른 모양을 담는 자유를 사고, RDB가 컬럼에 공짜로 얹어 주던 인덱스 · 통계 · 좁은 갱신 · 타입/제약(그리고 이름)을 반납한다. "유연하다"만 말하고 반납 목록을 못 대면 이 질문은 절반도 답이 안 된다.
  • 2
    반납의 이유를 저장 구조로 말한다 — 문서 안의 키는 스키마에 없는 데이터라 어떤 정렬 사본에도 통계에도 들어 있지 않고(→ Seq Scan + 추정이 상수 0.5%), MVCC 위에서는 키 하나를 바꿔도 문서 전체가 새 튜플로 다시 쓰인다(→ TOAST 청크 · WAL · 죽은 튜플 · 비-HOT).
  • 3
    판별은 네 질문이고, 쓰기로 했다면 안전망을 함께 든다 — 조회 대상인가 / 모든 행이 같은 키인가 / 부분 갱신이 잦은가 / DB가 지킬 불변식인가 중 하나라도 "예"면 컬럼. jsonb로 간다면 표현식 인덱스 · CHECK 검증 · schema_version을 세트로 붙인다. 스키마 진화 비용은 사라진 게 아니라 앱 읽기 코드로 옮겨간 것이다.

0. 질문 + 출제 의도

질문: "RDB의 JSON 컬럼은 언제 쓰고 언제 피하나요? 인덱싱과 스키마 진화 관점의 트레이드오프는?"

출제 의도: 스키마 유연성의 편의와 그 대가(인덱싱 제약, 타입 안전 상실, 조회 최적화 어려움)를 아는지. "정규화가 귀찮아서 JSON"과 "진짜 비정형 속성이라 JSON"을 구분하는 설계 규율의 표본이다. 즉 jsonb 연산자 문법이 아니라 — 편익과 대가를 양면으로 조립하고, 그 대가가 "왜" 생기는지를 저장 구조(힙 튜플 · TOAST · MVCC)의 메커니즘으로 말하며, 쓰기로 했을 때 어떤 안전망을 함께 설계하는지를 본다.

PostgreSQL은 도구가 유난히 풍부해서 "되니까 쓴다"의 유혹이 크다 — 도구가 있다는 것과 써야 한다는 것은 다르다
이 페이지가 겨냥하는 약점 세 가지 ① 편익만 말하고 대가를 못 대는 것 → 2절에서 반납 다섯(인·통·갱·제·명)을 "없으면 나는 사고"까지 붙여 목록으로 세운다.
② 대가를 "인덱스가 안 된다"는 결과로만 말하는 것 → 2절의 다섯 소절이 전부 저장 구조에서 사슬로 도출한다 — 정렬 사본, 상수 선택도, 힙 튜플·TOAST·WAL·HOT.
③ 우회를 말하고 한계를 못 붙이는 것 → 5절에서 표현식 인덱스가 통계까지 되사온다는 가산점과, 우회는 읽기만 되사올 뿐이라는 한계를 같은 호흡으로 말한다.

읽는 순서: 2절(무엇을 반납하는가)을 먼저 손에 쥐어야 3절의 네 질문이 암기가 아니라 도출이 된다. 5·6·7절은 "그래도 jsonb를 골랐을 때" 무엇을 되살 수 있고(표현식 인덱스·GIN), 무엇은 되살 수 없으며(스키마 진화), 그래서 무엇을 함께 들어야 하는지(안전망)를 다룬다.

1. 전제 — json과 jsonb는 이름만 닮은 다른 타입이다

이 문서의 모든 서술은 "어느 타입 이야기인가"에 따라 참·거짓이 갈린다. 그래서 여기부터 갈라 둔다. PostgreSQL에는 JSON을 담는 타입이 둘이고, 둘은 저장 방식이 근본적으로 다르다.

json — 입력 텍스트를 그대로 저장

INSERT 때 하는 일은 "문법적으로 올바른 JSON인가" 한 번 검사뿐. 받은 문자열을 한 바이트도 손대지 않고 넣는다. 공백도, 키 순서도, 중복 키도 남는다. 대신 값을 꺼낼 때마다 처음부터 다시 파싱한다.

저장이 싸고 읽기가 비싸다

jsonb — 파싱해서 이진 구조로 저장

이름의 b가 binary다. INSERT 때 파싱·정규화 비용을 한 번 치르고, 저장된 형태 자체가 이미 "키 → 값"의 탐색 가능한 구조라 꺼낼 때 다시 파싱하지 않는다.

저장이 비싸고 읽기가 싸다 — 그리고 이 이진 구조가 @>·GIN·인덱스의 전제다

같은 "JSON"이라는 이름 아래 성질이 갈리는 지점 — 인덱스 행이 실무 선택을 결정한다

정규화가 실제로 무엇을 바꾸는지는 한 번 넣었다 꺼내 보면 바로 보인다.

확인 같은 입력을 두 타입에 넣고 그대로 꺼내 본다
SELECT '{"b": 1,  "a": 2, "a": 3}'::json  AS as_json,
       '{"b": 1,  "a": 2, "a": 3}'::jsonb AS as_jsonb;

--   as_json                     |  as_jsonb
--  ---------------------------- + -------------------
--   {"b": 1,  "a": 2, "a": 3}   |  {"a": 3, "b": 1}
--
-- json  : 공백 두 칸도, 중복된 "a"도, b가 먼저 온 순서도 그대로다.
-- jsonb : 공백이 사라지고, 키가 정렬되고, 중복 "a"는 마지막 값 3만 남았다.
--         "받은 그대로"가 요구였다면 이 시점에 이미 요구를 어긴 것이다.

함정 — "jsonb가 상위 호환이니까 무조건 jsonb"가 아니다

실무의 기본 선택은 jsonb가 맞다. 조회·인덱싱·연산자가 전부 jsonb 쪽에만 있으므로 "JSON 컬럼을 쓴다"는 말은 거의 항상 jsonb를 뜻한다. 그러나 json이 맞는 자리가 딱 하나 있다.

입력 바이트를 그대로 보존하는 것 자체가 요구사항일 때 — 그때는 json(또는 text)이다

결제 PG사(결제 게이트웨이) 응답 원문처럼 분쟁 시 "그때 상대가 정확히 뭐라고 응답했는가"를 증거로 내야 하는 데이터가 여기 해당한다(4절 (b)). jsonb에 넣으면 키 순서가 바뀌고 공백이 사라져 "바이트 단위로 같다"를 주장할 수 없다. 어차피 조회 조건으로 쓰지 않을 컬럼이니 json의 "읽을 때마다 파싱" 비용도 문제가 되지 않는다.

아래 본문에서 그냥 "JSON 컬럼"이라고 쓰면 jsonb를 뜻한다. json을 말할 때는 그때마다 명시한다.

2. 반납 목록 — 컬럼이 공짜로 주던 다섯

비유부터. 정식 컬럼은 서류 양식의 인쇄된 칸이다. 칸이 정해져 있으니 접수처는 그 칸 기준으로 색인(인덱스)을 만들 수 있고, 칸의 형식(숫자만, 빈칸 금지, 다른 서류의 번호와 대조)을 접수 시점에 검사하며, 칸 하나만 고쳐 쓸 수 있고, 칸마다 "이 값이 대략 몇 건"이라는 장부(통계)를 갖는다. 그리고 칸에는 이름이 인쇄되어 있어서 없는 칸에 적으려 하면 적을 자리가 없다.

정식 컬럼 = 인쇄된 칸

  • 칸 기준으로 색인을 만든다
  • 접수 시점에 형식을 검사한다
  • 칸 하나만 고쳐 쓴다
  • 칸마다 몇 건인지 장부가 있다
  • 칸 이름이 인쇄되어 있다

JSON 컬럼 = 비고란에 붙인 메모지

  • 메모지 안으로는 색인을 안 만든다
  • 내용을 검사하지 않는다
  • 한 글자 고치려면 메모지를 새로 써서 다시 붙인다
  • 안에 무엇이 몇 건인지 세지 않는다
  • 인쇄된 칸 이름이 없어 이름을 잘못 써도 아무도 모른다

반납 5종 3초 인출 — 인 · 통 · 갱 · 제 · 명

인 — 인덱스
정렬 사본에 값이 없다
통 — 통계
추정이 상수가 된다
갱 — 좁은 갱신
문서 전체가 재기록된다
제 — 타입·제약
불변식이 앱 관례로 강등
명 — 이름
오타 키를 아무도 안 잡는다

이 다섯을 손에 쥐면 3절의 네 질문이 저절로 도출된다 — 질문 ⑴은 인·통, ⑵는 스키마 균일성, ⑶은 갱, ⑷는 제·명이다. 외우는 게 아니라 접는 것이다.

2-1. 반납 ① 인덱스 — 값이 정렬된 사본에 없어서 Seq Scan

인덱스란 인덱스 컬럼의 값과 그 행의 위치(TID)를 함께 담아, 그 값 기준으로 정렬해 둔 별도의 사본이다. 탐색이 빠른 이유는 오직 "찾는 값이 이미 정렬된 사본 안에 있어서"다. 정렬돼 있으니 이진 탐색으로 시작점을 찍고, 필요한 만큼만 옆으로 이어 읽으면 끝난다.

여기서 결정적인 사실 하나 JSON 컬럼의 내부 키는 플래너 입장에서 컬럼이 아니다. DB가 카탈로그(pg_attribute)에서 아는 것은 "이 테이블에 attrs라는 이름의 jsonb 컬럼이 하나 있다"까지이고, 그 문서 안의 genre라는 키는 스키마에 존재하지 않는다. 데이터일 뿐 구조가 아니다.

2-2. 반납 ② 통계 — 플래너가 행 수를 모르면 조인 방식이 통째로 어긋난다

이 고리는 다섯 중 가장 늦게 눈에 띄고 가장 크게 터진다. 그래서 따로 뗀다.

먼저 전제. PostgreSQL의 플래너는 규칙표를 보고 실행 방법을 고르는 것이 아니라 비용을 추정해서 가장 싼 계획을 고른다. 그 추정의 재료가 통계다. ANALYZE가 테이블을 표본 추출해 컬럼마다 값이 몇 종류인가(n_distinct), 가장 흔한 값과 그 빈도(most_common_vals/most_common_freqs), 값이 어떻게 퍼져 있나(히스토그램)를 적어 둔다. WHERE genre = '스릴러'가 몇 건을 남길지를 플래너가 아는 것은 이 통계 덕이다.

jsonb 컬럼에도 통계는 있다 — 단, "문서 전체를 하나의 값으로 본" 통계다 pg_stats에서 attrs 행을 조회하면 문서 전체의 n_distinct와 most common values가 나온다. 그런데 문서 전체가 통째로 똑같은 행이 몇 개나 되겠는가 — 사실상 전부 유일하다. 우리가 알고 싶은 것은 "attrs->>'genre'가 '스릴러'인 행이 몇 건인가"인데, 그 분포는 어디에도 수집돼 있지 않다.
Nested Loop
바깥 한 건마다 안쪽을 한 번씩. 바깥이 적을 때 압도적으로 싸고, 많으면 그 횟수만큼 곱해진다.
Hash Join
한쪽을 통째로 읽어 해시 테이블을 만들고 다른 쪽을 흘려보낸다. 양쪽이 클 때 유리, work_mem 초과 시 디스크.
Merge Join
양쪽을 정렬해 지퍼처럼 맞춘다. 이미 정렬돼 있거나 결과가 아주 클 때 후보.

세 방식의 선택이 전적으로 "양쪽이 몇 건인가"에 달려 있다 — 그래서 행 수 추정이 틀리면 고른 방식 자체가 틀린다.

확인 jsonb 컬럼의 통계에 무엇이 들어 있는지 직접 본다
SELECT attname, n_distinct, null_frac, avg_width
  FROM pg_stats
 WHERE tablename = 'episodes' AND attname = 'format_attrs';
-- attname      | n_distinct | null_frac | avg_width
-- format_attrs |         -1 |         0 |       412
--
-- n_distinct = -1 은 "행마다 전부 다른 값"이라는 뜻이다. 문서 전체를 하나의 값으로
-- 봤으니 당연하다. 여기 어디에도 "genre 키의 값 분포"는 없다 — 그래서 상수 추정이다.
이 손실만은 되살 수 있다 가산점 5절의 표현식 인덱스를 만들면 ANALYZE가 그 식의 결과에 대한 통계까지 수집한다 — 반납 ②가 부수 효과로 풀린다. 통계만 따로 원하면 인덱스 없이 CREATE STATISTICS로도 만들 수 있다. 이 점이 PostgreSQL에서 표현식 인덱스가 단순한 "검색 가속" 이상인 이유다.

2-3. 반납 ③ 좁은 갱신 — 키 하나 고쳐도 문서 전체가 새 튜플로 다시 쓰인다

전제부터. PostgreSQL에서는 어떤 컬럼이든 UPDATE가 제자리 덮어쓰기가 아니다. 옛 튜플(행의 한 버전)의 헤더에 "이 XID가 지웠다"는 뜻으로 xmax를 찍고, 바뀐 값이 담긴 새 튜플 버전을 힙에 삽입한다(MVCC). 옛 버전은 그 자리에 남아 있다가 VACUUM이 회수할 때 사라진다.

그러면 정당한 반문이 하나 나온다 "컬럼이든 jsonb든 어차피 새 튜플인데 뭐가 다른가?" — 좋은 질문이고, 답은 쓰는 양과 인덱스 두 가지다.
같은 "새 튜플"이라도 규모가 다르다 — 이 표가 위 반문에 대한 답 전체다
정식 컬럼 갱신 view_count = view_count + 1jsonb 내부 키 갱신 jsonb_set(attrs,'{view_count}',…)
새 튜플에 담기는 양행 폭만큼 (수십~수백 바이트)문서 전체 (10KB면 10KB, 100KB면 100KB)
안 바뀐 큰 값TOAST에 나가 있으면 포인터만 복사, 청크는 손 안 댐문서 전체가 새로 만들어지므로 새 TOAST 청크 세트를 다시 쓴다
인덱스인덱스된 컬럼이 아니면 HOT 업데이트 → 인덱스 갱신 0회attrs에 GIN·표현식 인덱스가 있으면 HOT이 깨져 테이블의 모든 인덱스에 새 엔트리
WAL새 튜플 크기만큼새 튜플 + TOAST 청크 전부. 그대로 레플리카까지 흘러간다
죽은 튜플행 폭만큼문서 크기만큼. VACUUM이 치울 때까지 공간을 차지한다
여기 나온 HOT을 한 문장으로 정의하고 간다 HOT(Heap-Only Tuple) 업데이트란 "바뀐 컬럼이 어떤 인덱스에도 들어 있지 않고, 새 버전을 같은 페이지에 놓을 자리가 있을 때" PostgreSQL이 인덱스를 하나도 건드리지 않고 새 버전을 놓는 최적화다. 인덱스는 여전히 옛 튜플의 주소를 가리키고, 힙 페이지 안의 포인터 사슬이 최신 버전으로 안내한다. → 인덱스가 5개인 테이블에서 HOT이 되느냐 마느냐는 UPDATE 한 번의 쓰기가 1회냐 6회냐를 가른다.

이 사슬에서 곧바로 도출되는 금지 사항 — JSON 안에 카운터를 넣지 마라

가장 잦은 쓰기를 가장 비싼 방식으로 하는 최악의 조합이다
before JSON 안의 조회수
UPDATE episodes
   SET format_attrs = jsonb_set(format_attrs, '{view_count}',
           to_jsonb((format_attrs->>'view_count')::bigint + 1))
 WHERE id = $1;

-- 읽기 → 새 문서 생성 → 새 튜플(+ 새 TOAST 청크)
-- → WAL(레플리카까지) → 죽은 튜플.
--
-- 문서에 썸네일 URL 목록, 태그, 번역 상태 같은
-- 다른 키가 클수록 "조회수 +1"의 비용이 커진다.
-- 즉 비용이 바꾸는 값의 크기가 아니라
-- "옆에 뭐가 같이 들어 있는가"에 비례한다.
after 카운터는 컬럼
UPDATE episodes
   SET view_count = view_count + 1
 WHERE id = $1;

-- 좁은 새 튜플 · TOAST 무관 · HOT 가능.
--
-- (물론 초고빈도 카운터는 컬럼이어도
--  "핫 로우" 문제가 남는다 — 그건 별도 사슬이고,
--  JSON은 거기에 "문서 전체 재기록"을
--  한 겹 더 얹을 뿐이다.)
관찰 이 비용은 추측이 아니라 재 볼 수 있다
-- ① HOT 비율과 죽은 튜플 — 사슬이 돌고 있는지
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct,
       n_live_tup, n_dead_tup
  FROM pg_stat_user_tables WHERE relname = 'episodes';
-- hot_pct가 낮고 n_dead_tup이 빠르게 쌓이면 이 사슬이다.

-- ② 문서 크기 — 한 번의 갱신이 얼마를 다시 쓰는지
SELECT pg_size_pretty(avg(pg_column_size(format_attrs))::bigint) AS avg_doc
  FROM episodes TABLESAMPLE SYSTEM (1);

-- ③ TOAST 몫 — 문서가 별도 테이블로 얼마나 밀려나 있는지
SELECT pg_size_pretty(pg_table_size('episodes'))     AS total,
       pg_size_pretty(pg_relation_size('episodes'))  AS heap_only,
       pg_size_pretty(pg_table_size('episodes')
                      - pg_relation_size('episodes')) AS toast_and_fsm;

2-4. 반납 ④ 타입·제약 — 불변식이 DB에서 애플리케이션 관례로 내려간다

price numeric(12,2) NOT NULL, FOREIGN KEY (product_id), UNIQUE (sku) — 정식 컬럼의 제약은 DB가 지킨다. 여기서 "DB가 지킨다"는 말의 무게를 정확히 새겨야 한다. 어떤 코드 경로로 들어오든, 어떤 배치가 넣든, 운영자가 psql에서 직접 넣든 뚫리지 않는다는 뜻이다.

애플리케이션 검증은 "그 코드를 통과한 데이터"만 지키지만, DB 제약은 "그 테이블에 들어오는 모든 데이터"를 지킨다

jsonb 컬럼에는 이 검사가 하나도 없다. DB가 보장하는 것은 "문법적으로 올바른 JSON인가"뿐이다.

bad 세 행 모두 "유효한 JSON"이라 INSERT가 전부 성공한다
INSERT INTO products (attrs) VALUES ('{"price": 1000}');      -- 숫자
INSERT INTO products (attrs) VALUES ('{"price": "1000"}');    -- 문자열
INSERT INTO products (attrs) VALUES ('{"prcie": 1000}');      -- 오타 키

-- 그리고 조회는 조용히 틀리거나, 시끄럽게 죽는다
SELECT count(*) FROM products WHERE (attrs->>'price')::numeric > 500;
-- 숫자 1000    → 텍스트 '1000' → 캐스트 성공 → 포함
-- 문자열 "1000" → 텍스트 '1000' → 캐스트 성공 → 포함 (타입이 달라도 조용히 섞인다)
-- 오타 행       → 키 없음 → NULL → 제외 → 아무 에러 없이 2건이 답으로 나온다
--
-- 그리고 누군가 '{"price": "1,000"}' 을 넣는 순간, 이 쿼리는 그 한 행 때문에
-- ERROR: invalid input syntax for type numeric 로 통째로 실패한다.
-- 어제까지 잘 돌던 대시보드가 오늘 죽는데, 배포는 없었다.

-- 섞여 있다는 사실은 이렇게 사후에야 드러난다
SELECT jsonb_typeof(attrs->'price') AS t, count(*) FROM products GROUP BY 1;
--  t      | count
--  number |  81234
--  string |    417   <- 언제부터 들어왔는지 아무도 모른다
--  (null) |      3   <- 키 자체가 없는 행
차이가 "정도"가 아니라 "범위"다 반정규화 컬럼은 불변식 "하나"를 애플리케이션 관례로 내려보내지만, jsonb 컬럼은 그 안의 모든 필드에 대해 그것을 기본값으로 만든다. 불변식이 DB 제약이 아니라 관례에 살면, 그 관례를 모르는 새 코드 경로·DB 직접 수정에 뚫린다.
참조 무결성 부재 — 고아가 조용히 쌓인다
{"author_id": 42}가 삭제된 작가를 가리켜도 DB는 모른다. FK가 있었다면 작가 삭제 시점에 ERROR: … violates foreign key constraint로 막혔을 일이 아무 일도 일어나지 않는다. 발견은 보통 "작가 이름이 안 나온다"는 CS 문의로 오고, 되짚어 세려면 jsonb_array_elements로 전 행을 전개해 대조하는 배치를 따로 만들어야 한다.
NULL의 세 얼굴 — 상태가 둘에서 셋이 된다
SQL NULL(컬럼 자체가 비었다) · JSON null(키는 있고 값이 null) · 키 부재(키 자체가 없다)가 서로 다른 의미로 공존한다. 컬럼이었다면 "값이 있다 / NULL이다" 둘뿐이었다.
함정 같은 "값이 없다"를 세 연산자가 다르게 본다
WITH t(doc) AS (VALUES ('{"k": null}'::jsonb), ('{}'::jsonb), ('{"k": 1}'::jsonb))
SELECT doc,
       doc->>'k'          AS arrow_text,   -- text  : JSON null과 키 부재를 둘 다 SQL NULL로 뭉갠다
       doc->'k'           AS arrow_jsonb,  -- jsonb : JSON null은 'null', 키 부재는 SQL NULL — 구분된다
       doc ? 'k'          AS has_key       -- bool  : 값과 무관하게 키 존재만 본다
  FROM t;
--  doc          | arrow_text | arrow_jsonb | has_key
--  {"k": null}  | (NULL)     | null        | t
--  {}           | (NULL)     | (NULL)      | f
--  {"k": 1}     | 1          | 1           | t
-- "값을 명시적으로 비운 것"과 "아직 그 필드가 없던 옛 세대 문서"를 구분해야 하는데,
-- ->> 만 쓰면 둘이 똑같이 NULL로 보인다. 집계와 마이그레이션이 여기서 어긋난다.

2-5. 반납 ⑤ 이름 — 컬럼명 오타를 아무도 잡아주지 않는다

앞의 넷보다 사소해 보이지만 실무에서 가장 자주 물리는 것이 이것이다. 컬럼은 이름이 스키마에 등록돼 있다. INSERT INTO products (prcie) VALUES (1000)은 ERROR: column "prcie" of relation "products" does not exist로 즉시 죽는다. 오타가 프로덕션에 도달할 수 없다.

jsonb에서는 오타가 새 키를 만드는 정상 동작이다. 문법적으로 올바른 JSON이니 아무 문제가 없다. 그래서 다음 세 가지가 조용히 벌어진다.

1
쓰기는 성공한다. 그 행에는 prcie 키가 생겼고 price 키는 없다.
2
읽기는 예외 없이 그 행을 뺀다. attrs->>'price'가 NULL이라 WHERE (attrs->>'price')::numeric > 500에서 조용히 제외된다. 에러가 없으니 아무도 모른다.
3
발견은 집계가 어긋난 뒤에 온다. "500원 넘는 상품이 어제보다 왜 줄었지?"에서 시작해 jsonb_object_keys로 키 목록을 세어 봐야 나온다.
탐지 오타 키를 사후에 찾아내는 쿼리 — 정기적으로 돌려야 한다는 사실 자체가 대가다
SELECT k, count(*) AS rows
  FROM products, LATERAL jsonb_object_keys(attrs) AS k
 GROUP BY k
 ORDER BY rows;
--  k       | rows
--  prcie   |    3   <- 소수 등장 키가 오타 후보다
--  color   |  812
--  price   | 81651
이 손실은 CHECK로 "부분적으로만" 되살 수 있다 "이 키들은 반드시 있어야 한다"(?&)는 강제할 수 있지만, "이 키들 말고는 있으면 안 된다"까지 강제하려면 허용 키 목록을 CHECK 안에 적어야 하고, 그러면 사실상 컬럼 정의를 CHECK로 재현하는 셈이 된다. 그 지점에 도달했다면 답은 이미 나온 것이다 — 컬럼으로 만들어라.

3. 사는 것 넷 + 판별 네 질문

대가를 다 말했으니 편익도 정확히 말해야 양면이 조립된다. 반납만 나열하면 "그럼 절대 쓰지 말라는 거냐"가 되고, 그건 답이 아니다.

JSON 컬럼이 사는 것 — 정확히 넷 (원 · 희 · 문 · 디)

원 — 외부 원문의 무손실 보존
스키마의 주인이 우리가 아닌 데이터(결제 PG 응답, 웹훅 페이로드)를 그대로 둔다. "바이트 그대로"가 요구면 json(또는 text) — jsonb는 키 순서·공백·중복 키를 정규화한다(1절).
희 — 희소(sparse) 속성
행마다 키 집합이 진짜 다를 때, NULL투성이 컬럼 수십 개나 EAV(속성을 행으로 늘어놓는 별도 테이블) 없이 담는다. EAV는 조회마다 여러 행을 피벗해야 해 쿼리가 급격히 복잡해지는데, jsonb는 그 복잡도를 한 컬럼으로 접는다.
문 — 문서 단위 접근
항상 통째로 읽고 통째로 쓰는 부속 데이터를 조인 없이 한 번에 가져온다. 이 경우엔 반납 ③이 대가가 아니다 — 어차피 전체를 다시 쓸 참이었기 때문이다.
디 — DDL 없는 필드 추가
수억 건 테이블에 ALTER TABLE … ADD COLUMN을 내는 리스크를 피한다. 단, 이 자유의 청구서는 6절에서 온다 — 공짜로 사라진 것이 아니라 청구지가 바뀐 것이다.
얻는 것이 이 넷 중 하나가 아니면 JSON을 쓸 이유가 없다 — "테이블 하나 더 만들기 귀찮아서"는 이 목록에 없다

3-1. 네 질문 — 반납 목록을 3분짜리 리뷰 도구로 접는다

2절의 반납 목록을 실무에서 3분 안에 쓸 수 있는 형태로 접으면 네 개의 예/아니오 질문이 된다. 각 질문은 2절의 사슬 하나와 정확히 짝을 이룬다 — 그래서 답을 외울 필요가 없고, 사슬을 기억하면 질문이 도출된다.

JSON이 맞는 경우 5

  • 외부 시스템 원문 보존 — 결제 PG 응답, 웹훅 페이로드, 외부 API 응답. 스키마의 주인이 우리가 아니고, write-once이며, 감사·분쟁 대응용
  • 행마다 키가 다른 희소 속성 — 상품 카테고리별 규격, 콘텐츠 형식별 메타데이터. 컬럼으로 펼치면 NULL이 대부분인 컬럼 수십 개
  • 통째로 읽고 통째로 쓰는 문서 — 사용자 설정, 에디터 레이아웃 상태. 항상 전체 로드·전체 저장, 조건 검색 없음
  • 감사·이력 스냅샷 — "그 시점에 이 객체가 어떤 모양이었나". 조회는 PK나 시각 컬럼으로 하고 문서는 그냥 보여 준다
  • 아직 형태가 굳지 않은 실험 속성 — 단, "굳는 순간 승격한다"는 출구 규칙(7-3)이 함께 있을 때만

JSON을 피해야 할 경우 5

  • 조회 조건·정렬·집계 대상 — 반납 ①. 특히 조인의 축이 되는 값은 통계 부재(반납 ②)로 계획까지 망친다
  • 다른 테이블과의 관계 — 주문의 상품 목록, 글의 태그처럼 반대 방향 조회("이 상품이 포함된 주문")가 필요한 1:N. 별도 테이블이다
  • 모든 행이 같은 키를 갖는 균일 데이터 — 그냥 컬럼이다
  • 잦은 부분 갱신, 특히 큰 문서의 — 카운터·상태값·재고. 반납 ③. 문서가 클수록(TOAST) 한 번의 갱신이 비싸진다
  • DB가 지켜야 할 불변식이 있는 값 — 금액, 식별자, 필수값, 유일값. 반납 ④

핵심은 "원문 보존"과 "조회"를 같은 컬럼에 시키지 않는 것 — 두 요구는 성격이 다르다

원문은 PG사가 스키마의 주인이고, 필드가 언제 늘어날지 모르며, 분쟁 시 "그때 PG사가 정확히 뭐라고 응답했나"의 증거다. 그래서 JSON이 맞고 — "정확히"가 요구이므로 정규화하는 jsonb가 아니라 원문 텍스트를 보존하는 json이다(1절). 조회하지 않을 컬럼이니 json의 "읽을 때마다 파싱" 비용도 문제가 되지 않는다.

반면 우리가 조회·집계·정합성 검증에 쓰는 값(거래 ID, 승인번호, 금액, 상태)은 우리 도메인의 컬럼이다. 저장 시 한 번 추출해 두 곳에 쓴다. 이것은 중복이지만, 원문은 write-once라 어긋날 갱신 경로가 없어 동기화 장치가 필요 없는 스냅샷 성격의 중복이다.

그러나 두 값은 문서 밖으로 빼낸다 "마케팅 수신 동의자에게 발송"은 WHERE 조건이고 법적 기록이라(⑴·⑷ 예) 컬럼이다. 그리고 "다크 모드 사용자 비율"을 대시보드에 띄우자는 요구가 오면? 집계 대상이 됐으니(⑴ 예) 승격하거나, 설정 변경 이벤트를 따로 적재해 거기서 센다 — jsonb Seq Scan 집계를 운영 DB에 매일 돌리는 선택지는 없다.

5. 우회 — 표현식 인덱스 · GIN, 그리고 반드시 붙여야 할 한계

반납 ①의 원인이 "값이 정렬 사본에 없다"였으니, 우회는 그 값을 사본에 넣는 것이다

5-1. 표현식 인덱스 — 식의 결과를 인덱스 리프에 "물질화"한다

일반 인덱스가 "이 컬럼의 값으로 정렬한 사본을 만들어라"라면, 표현식 인덱스는 "이 식을 모든 행에 대해 계산한 결과값으로 정렬한 사본을 만들어라"다. 인덱스 리프에는 식의 결과가 물질화(계산해서 실제로 저장)되어 정렬된다. 테이블 행은 한 바이트도 바뀌지 않는다 — 사본만 새로 생긴다.

① 식 일치 조건 — 이 우회의 가장 흔한 함정

플래너는 쿼리의 식이 인덱스 정의의 식과 같은 형태일 때만 인덱스를 매칭한다. "같은 형태"의 판정은 사람의 눈이 아니라 파싱된 식 트리 기준이라, 연산자·캐스트·결과 타입이 하나라도 다르면 매칭되지 않는다. 그리고 매칭에 실패해도 에러가 나지 않는다 — 그냥 조용히 Seq Scan으로 돌아간다.

함정 전부 에러 없이 Seq Scan으로 돌아가는 조건들
-- 인덱스는 numeric으로 캐스트한 식으로 만들었다
CREATE INDEX idx_products_price ON products (((attrs->>'price')::numeric));

-- 타는 조건: 인덱스 정의와 식이 정확히 같다
SELECT * FROM products WHERE (attrs->>'price')::numeric > 500;   -- Index Scan

-- 안 타는 조건들
SELECT * FROM products WHERE attrs->>'price' > '500';            -- text 비교. 식이 다르다
                                                                 -- 게다가 '90' > '500'이 참이라 결과도 틀린다
SELECT * FROM products WHERE (attrs->'price')::numeric > 500;    -- -> vs ->> : 다른 연산자
SELECT * FROM products WHERE (attrs->>'price')::float8 > 500;    -- 캐스트 타입이 다르다
SELECT * FROM products WHERE (attrs#>>'{price}')::numeric > 500; -- 결과는 같지만 식이 다르다

그래서 실무 규율은 하나 — "이 식을 한 곳에만 적는다"

리포지토리의 상수 문자열로 고정하거나, 아예 뷰(또는 아래의 생성 컬럼)를 만들어 애플리케이션이 식을 직접 쓰지 못하게 한다. 사람이 매번 손으로 적으면 언젠가 누군가 #>>를 쓰고, 그날 그 API만 조용히 1.8초가 된다.

② 통계까지 따라온다 가산점

표현식 인덱스가 있으면 ANALYZE가 그 식의 결과에 대한 통계를 함께 수집한다. 반납 ②(상수 선택도)가 이 순간 풀린다 — 위 계획에서 추정이 15,000에서 9,030으로 바뀐 이유다. 이것이 표현식 인덱스가 단순한 검색 가속이 아닌 이유이고, 조인의 축이 되는 jsonb 키에는 검색 속도보다 이쪽이 더 중요할 때도 있다.

가산점 인덱스 없이 통계만 원한다면
-- 인덱스 유지 비용을 안 내고 "계획만" 고치고 싶을 때
CREATE STATISTICS stx_episodes_genre ON ((format_attrs->>'genre')) FROM episodes;
ANALYZE episodes;

-- 수집됐는지는 pg_stats에서 확인한다
-- (표현식 인덱스의 통계는 "인덱스 이름"으로 잡힌다는 점에 주의)
SELECT most_common_vals, most_common_freqs
  FROM pg_stats WHERE tablename = 'idx_episodes_genre';

③ 타입 고정 — 그리고 인덱스가 데이터 품질 검사기가 된다

불편이 아니라 공짜 데이터 검증이다 ((attrs->>'price')::numeric) 인덱스는 생성 시 모든 행에 대해 식을 계산한다. 그래서 한 행이라도 "1,000"이 들어 있으면 CREATE INDEX 자체가 ERROR: invalid input syntax for type numeric로 실패한다. 반납 ④가 인덱스 생성 시점에 터져 주는 것이고, 프로덕션 조회가 터지기 전에 알게 된다. 동시에 이 장면은 우회의 한계도 보여 준다 — 우회는 반납 ①·②만 되사고 ③·④·⑤는 그대로 남는다.

두 가지 변형

부분 인덱스와의 결합

… ON episodes ((format_attrs->>'genre')) WHERE format_attrs ? 'genre' — 그 키가 없는 행을 인덱스에서 아예 뺀다. 희소 속성일수록 효과가 크다(키가 10%의 행에만 있으면 인덱스도 10% 크기). 단, 쿼리에도 같은 WHERE 조건이 들어 있어야 플래너가 "이 부분 인덱스로 답을 다 낼 수 있다"고 판단한다.

생성 컬럼(STORED) + 일반 인덱스

ADD COLUMN genre text GENERATED ALWAYS AS (format_attrs->>'genre') STORED — 식의 결과를 아예 정식 컬럼으로 만든다. 식 일치 함정이 사라지고 일반 인덱스·통계·NOT NULL·CHECK가 다 붙는다. 대신 값이 행에도 저장되어 테이블이 커지고, 기존 테이블에 추가하면 테이블 재작성(ACCESS EXCLUSIVE 잠금)이다.

큰 테이블에는 표현식 인덱스가 먼저이고, 생성 컬럼은 "이 키는 이제 사실상 컬럼이다"라고 선언할 때의 도구다

5-2. GIN — 키를 미리 정하지 않고 문서 안을 역색인한다 가산점

표현식 인덱스로 안 되는 경우가 있다. tags: ["로맨스","학원","완결"]처럼 배열 원소가 조건이 되는 경우다. 행 하나에 값이 여러 개라서 "정렬된 사본의 한 자리"에 넣을 수가 없다 — 어느 태그를 그 자리에 넣을 것인가?

이때의 도구가 GIN(Generalized Inverted Index)이다. 이름의 inverted(역)가 핵심이다. B-tree가 "행 → 그 행의 값"을 정렬해 두는 것이라면, GIN은 "값(키/원소) → 그 값을 가진 행들의 목록"을 담는다. 책 뒤의 찾아보기와 같은 구조다 — 단어 하나에 그 단어가 나오는 페이지 번호들이 줄줄이 달려 있다. 그래서 한 행에 값이 여러 개여도 문제가 없다.

확인 GIN 계획은 항상 Bitmap으로 나온다 — 그리고 추정은 여전히 상수다
CREATE INDEX CONCURRENTLY idx_episodes_attrs_gin
    ON episodes USING gin (format_attrs);        -- 연산자 클래스 기본값은 jsonb_ops

SELECT id FROM episodes WHERE format_attrs @> '{"tags": ["완결"]}';
--                                       ^ @> 는 "왼쪽 문서가 오른쪽 문서를 포함하는가"

                               (actual time=18.204..210.331 rows=51238 loops=1)

         Index Cond: (format_attrs @> '{"tags": ["완결"]}'::jsonb)

-- 페이지 순서대로 훑기 때문이다. Recheck Cond가 붙는 것도 정상이다 —
-- 비트맵이 페이지 단위로 흐려지면(lossy) 그 페이지의 행을 다시 검사해야 한다.
-- rows=3000은 또 상수 선택도다 — GIN은 통계를 만들어 주지 않는다(반납 ②는 안 풀린다).

범 — 범위 조건

대가도 같은 호흡으로 말한다 — GIN은 검색만의 결정이 아니라 "쓰기 비용의 결정"이다 ① 인덱스가 크다 — jsonb_ops는 모든 키와 값을 엔트리로 만든다. 키가 20개인 문서면 행 하나가 수십 개의 엔트리를 만드는 셈이고, 인덱스가 테이블 크기에 근접하거나 넘어서는 경우도 드물지 않다.
② 쓰기 비용이 높다 — INSERT/UPDATE 한 번이 키 수만큼 엔트리를 만든다. 기본 설정(fastupdate = on)에서는 이 엔트리를 pending list에 모아 뒀다 나중에 병합하는데, 병합 전까지는 읽기가 트리와 pending list를 둘 다 훑어야 해서 조회가 느려지고, 병합이 일어나는 순간 그 쿼리가 병합 비용을 뒤집어쓴다.
③ HOT이 깨진다 — attrs에 GIN이 있는 순간 그 컬럼을 바꾸는 모든 UPDATE가 비-HOT이 된다(반납 ③이 악화된다).
good 범위를 좁혀 크기를 줄인다 — 문서 전체가 아니라 실제로 검색하는 서브 문서에만

    ON episodes USING gin ((format_attrs->'tags') jsonb_path_ops);

-- 인덱스가 실제로 얼마나 큰지는 재 보면 된다. 세 방식을 나란히 재서 고른다.
SELECT relname, pg_size_pretty(pg_relation_size(oid)) AS size
  FROM pg_class
 WHERE relname IN ('episodes',
                   'idx_episodes_genre',       -- 표현식 B-tree: 키 하나만 뽑아 정렬 → 가장 작다
                   'idx_episodes_tags_gin',    -- 범위를 좁힌 path_ops GIN
                   'idx_episodes_attrs_gin')   -- 문서 전체 jsonb_ops GIN → 가장 크다
 ORDER BY pg_relation_size(oid) DESC;
-- 크기 순서는 데이터에 따라 달라지므로 외우지 말고 이 쿼리로 직접 재라.
-- 다만 "표현식 B-tree < path_ops GIN < 문서 전체 jsonb_ops GIN"이라는 순서 자체는
-- 엔트리 개수 정의에서 나오는 것이라 거의 항상 성립한다.

5-3. 우회의 한계 — 결국 "미리 정한 키"만 빠르다

우회를 말한 다음에는 반드시 한계를 붙인다. 여기서 답변의 깊이가 갈린다.

표현식 인덱스도 생성 컬럼도 어떤 키를 색인할지 미리 정해야 한다. 그런데 "미리 정해진, 모든 행이 갖는, 조회 조건인 키"는 — 3-1의 흐름도로 돌아가면 — ⑴과 ⑵에 모두 "예"인 키다. 즉 정의상 컬럼이었어야 하는 것이다. 그래서 우회의 정직한 적용 범위는 아주 좁다.

우회가 정직하게 맞는 자리는 여기 하나뿐이다 문서의 대부분이 진짜 비정형이고, 그중 한두 키만 뒤늦게 조회 조건이 됐을 때 — 문서를 깨지 않고 그 키만 꺼내 색인하는 도구.

범위를 넘어섰다는 신호 — 표현식 인덱스가 다섯 개가 됐다면

그것은 우회가 아니라 "컬럼이어야 했던 것을 뒤늦게, 그리고 더 비싼 방식으로 컬럼으로 만들고 있는 것"이다. 인덱스 다섯 개의 유지 비용을 내면서 타입 검사도 제약도 없는 상태를 유지하고 있는 셈이니 양쪽 다 손해다. 그 시점엔 JSON에서 빼내 정식 컬럼으로 승격하는 게 맞다.

되사온 것 / 못 사는 것 매트릭스 — 이 표를 말할 수 있으면 "우회를 안다"가 "우회의 한계를 안다"로 올라간다

6. 스키마 진화 — 마이그레이션이 없어진 게 아니라 코드로 옮겨간 것

3절 편익 디(DDL 없는 필드 추가)의 청구서가 여기서 온다. jsonb를 고르는 가장 흔한 명분이 "나중에 스키마가 바뀔 것 같아서"인데, 이 명분을 정확히 해부해야 한다.

같은 변경을 두 방식으로 했을 때 — 마지막 행이 이 절의 결론이다
정식 컬럼 (PostgreSQL)JSON 필드
필드 추가ADD COLUMN … DEFAULT 1회 — 상수 기본값이면 카탈로그만 고쳐 즉시 끝. 모든 행이 그 순간 같은 형태가 된다새로 쓰는 문서부터 키가 생긴다. 옛 행은 키가 없는 채로 영구 공존

before 세대가 데이터에 섞여 있으니 코드가 전부 처리한다
// 세대 v0 (2024): {"darkMode": true}              — boolean
// 세대 v1 (2025): {"theme": "dark"}               — 3값 enum
// 세대 v2 (2026): {"display": {"theme": "dark"}}  — 한 단계 내림

String theme(JsonNode prefs) {
    if (prefs.path("display").has("theme"))       // v2
        return prefs.get("display").get("theme").asText();
    if (prefs.has("theme"))                        // v1
        return prefs.get("theme").asText();
    if (prefs.has("darkMode"))                     // v0 — 새 어휘로 번역
        return prefs.get("darkMode").asBoolean() ? "dark" : "light";
    return "system";  // 한 번도 저장하지 않은 사용자
}
// 이 분기는 "언제 지울 수 있는지"를 알 수 없어 사실상 영구화된다.
after 세대를 읽어서 분기한다 (7-1의 안전망)
public UserPreferences read(long userId) {
    var row = repo.findById(userId).orElseThrow();
    // "어느 필드가 있나"를 추측하는 대신
    // "이 행은 몇 세대인가"를 읽는다 → 세대가 늘어도 사슬이 깊어지지 않는다.
    return switch (row.schemaVersion()) {
        case 0 -> upcastV0(mapper.readValue(row.prefs(), PrefsV0.class));
        case 1 -> upcastV1(mapper.readValue(row.prefs(), PrefsV1.class));
        case 2 -> mapper.readValue(row.prefs(), PrefsV2.class);
        // 모르는 세대를 만나면 조용히 기본값을 주지 않고 터뜨린다.
        // 롤백된 배포가 "미래 세대" 문서를 읽는 상황을 무시하면
        // 설정이 조용히 초기화된다.
        default -> throw new UnsupportedSchemaVersionException(row.schemaVersion());
    };
}

7-1. 안전망 ① 버전 필드 — 세대를 세고, 점진적으로 옮긴다

schema_version은 각 문서가 어느 세대인지 스스로 표시하게 하는 정수 컬럼이다. jsonb 안이 아니라 정식 컬럼으로 두는 것이 중요하다 — 이 값으로 세고 필터해야 하므로 질문 ⑴에 "예"이기 때문이다.

good ① 세대를 셀 수 있다 — "그 분기를 지워도 되나?"에 숫자로 답한다
SELECT schema_version, count(*) FROM user_preferences GROUP BY 1 ORDER BY 1;
--  schema_version | count
--               0 |    412      <- 아직 남아 있다. v0 분기는 못 지운다
--               1 |  38102
--               2 | 2914883
-- 412가 0이 되는 날 v0 분기를 지우는 PR을 올린다. 추측이 아니라 조회 결과로 결정한다.
good ② 쓰기는 언제나 최신 세대로만 — "읽기 시 점진 마이그레이션"
// 사용자가 설정을 한 번 저장할 때마다 그 행이 v2로 올라간다.
public void save(long userId, UserPreferences prefs) {
    repo.upsert(userId, CURRENT_SCHEMA_VERSION, mapper.writeValueAsString(prefs));
}
// 활동이 없는 계정은 영원히 v0로 남으므로, 남은 잔여분은 야간 배치로 훑어 올린다. ↓
배치 ③ 잔여분 — PK 범위로 잘라 짧은 트랜잭션 여러 번으로
UPDATE user_preferences
   SET prefs = jsonb_build_object('display',
                   jsonb_build_object('theme',
                       CASE WHEN (prefs->>'darkMode')::boolean THEN 'dark' ELSE 'light' END))
             || (prefs - 'darkMode'),
       schema_version = 2
 WHERE schema_version = 0
   AND user_id IN (SELECT user_id FROM user_preferences
                    WHERE schema_version = 0 ORDER BY user_id LIMIT 1000);
-- 한 문장으로 412만 건을 돌리면 그 자체가 긴 트랜잭션이 되어 VACUUM을 막는다.
-- 행마다 문서 전체 재기록이므로(반납 ③) 대용량이면 이 배치 자체가
-- WAL·bloat·VACUUM 부하 작업이다. 트래픽이 낮은 시간에, 간격을 두고 돌린다.

7-2. 안전망 ② DB 층 스키마 검증 — CHECK + jsonb 연산자

검증은 DB 층에 두는 것이 우선이다. 이유는 반납 ④와 정확히 같다. 애플리케이션 DTO 검증은 그 코드를 통과한 쓰기만 지키지만, psql 직접 수정과 아직 만들어지지 않은 새 코드 경로까지 막는 것은 DB 제약뿐이다.

PostgreSQL에는 JSON Schema 문서를 통째로 검사하는 함수가 내장돼 있지 않다(pg_jsonschema 같은 확장은 있다). 대신 CHECK 안에 jsonb_typeof · ?& · ->> + IN을 조합하면 필수 키, enum, 타입, 범위를 DB가 지키게 만들 수 있다.

before 검증도 버전도 없다

    user_id bigint PRIMARY KEY,
    prefs   jsonb  NOT NULL
);

-- {"theme": 3} 도, {"reader": {}} 도, 오타 키도
-- 전부 INSERT 성공. 몇 년 자란 뒤에는
-- 이 컬럼의 실제 모양을 아는 사람이 사라진다.
after 버전 필드 + DB 층 스키마 검증
CREATE TABLE user_preferences (
    user_id        bigint PRIMARY KEY,
    schema_version int    NOT NULL DEFAULT 2,
    prefs          jsonb  NOT NULL,
    CONSTRAINT chk_prefs_shape CHECK (
        jsonb_typeof(prefs) = 'object'              -- 배열·스칼라부터 막는다
        AND prefs ?& array['theme', 'reader']      -- 필수 키
        AND prefs->>'theme' IN ('light','dark','system')  -- enum
        AND jsonb_typeof(prefs->'reader') = 'object'  -- 중첩 타입
        AND prefs->'reader'->>'direction' IN ('vertical','horizontal')
        AND (
            NOT (prefs->'reader' ? 'auto_scroll_speed')  -- 선택 키: 없어도 되고
            OR (jsonb_typeof(prefs->'reader'->'auto_scroll_speed') = 'number'
                AND (prefs->'reader'->>'auto_scroll_speed')::numeric
                    BETWEEN 1 AND 5)                     -- 있으면 숫자 + 범위
        )
    )
);
-- 이제 psql에서 직접 넣어도 INSERT가 실패한다.
-- 불변식이 앱 관례에서 DB 제약으로 올라왔다(반납 ④의 부분 회복).
-- "부분"인 이유: 여기 안 적은 키는 여전히 아무거나 들어온다(반납 ⑤는 안 풀린다).
이미 데이터가 있는 큰 테이블에 붙일 때는 두 단계로 나눈다 한 번에 붙이면 전 행 검증 동안 테이블을 잠근다.

7-3. 안전망 ③ 승격 규율 — 출구 규칙이 없는 JSON은 "임시"라는 이름으로 영구화된다

팀 규칙으로 문서화한다 — "JSON 안의 키가 조회 조건·집계·정렬 대상이 되는 순간 컬럼(또는 표현식 인덱스, 또는 별도 테이블)으로 승격한다"

이것이 안전망인 이유는, jsonb의 실패가 대개 한 번의 잘못된 결정이 아니라 수정하지 않은 채 흘려보낸 시간에서 오기 때문이다. 처음 넣을 때는 정말로 비정형이었는데, 6개월 뒤 기획이 "이걸로 필터링하고 싶다"고 하고, 그때 "일단 되니까" 두면 그대로 굳는다.

점검 시점 ① — PR 리뷰
jsonb 키가 WHERE에 등장하는 PR은 리뷰에서 승격 여부를 묻는다.
점검 시점 ② — 분기별 키 분포 재측정
3-1의 표본 쿼리로 키 분포를 다시 재서 "거의 모든 행에 있는 키"를 찾아낸다. 그 키가 발견되면 이미 컬럼이었어야 하는 것이다.

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

한 문장 정의?
jsonb는 기능이 아니라 거래 — DDL 없이 행마다 다른 모양을 담는 자유를 사고, 컬럼이 공짜로 주던 것들을 반납한다.
반납 다섯은?
인 · 통 · 갱 · 제 · 명 — 인덱스 · 통계 · 좁은 갱신 · 타입/제약 · 이름.
사는 것 넷은?
원 · 희 · 문 · 디 — 원문 보존 · 희소 속성 · 문서 단위 접근 · DDL 없는 추가. 이 넷이 아니면 쓸 이유가 없다.
판별 네 질문은?
조 · 균 · 갱 · 제 — 조회 대상인가 / 모든 행이 같은 키인가 / 부분 갱신이 잦은가 / DB가 지킬 불변식인가. 하나라도 "예" → 컬럼.
왜 느린가, 한 줄로?
내부 키는 컬럼이 아니라 어떤 정렬 사본에도 값이 없다 → 탐색 불가 → Seq Scan + 행마다 키 탐색·변환(I/O+CPU 이중).
"추정이 상수"의 숫자는?
등호 조건에 정보가 없으면 선택도 0.005 → 300만 × 0.005 = rows 15,000. 실제가 0.3%든 30%든 같다.
우회가 되사는 것은?
표현식 인덱스 = ① + ②(통계까지!), GIN = ①의 일부(포함 검색만). ③·④·⑤는 어느 쪽도 못 산다.
GIN이 못 하는 것은?
범 · 정 · 접 · 통 — 범위 · 정렬 · 접두사 · 통계. 역색인에는 순서가 없기 때문이다.
안전망 셋은?
버 · 검 · 승 — schema_version · CHECK+DTO 검증 · 승격 규율.
스키마 진화의 정체는?
마이그레이션이 없어진 게 아니라 DB의 DDL 한 번 → 앱 읽기 코드의 영구 분기로 옮겨간 것.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

jsonb 안의 값으로 WHERE를 걸면 왜 느린가요? 어떻게 우회하나요? 필수힌트: "인덱스가 안 걸려서"로 끝내지 말고 사슬로 답한 뒤, 우회에는 반드시 한계를 붙인다

사슬로 답한다. B-tree는 컬럼 값을 정렬해 둔 사본인데 jsonb 내부 키는 컬럼이 아니라 어떤 사본에도 값이 없다 → 탐색 시작점을 찍을 수 없어 Seq Scan → 행마다 jsonb를 열어 키를 찾고 텍스트로 꺼내 비교(I/O + CPU 이중 비용, 계획에는 Filter와 Rows Removed by Filter) → 큰 문서면 TOAST 청크를 모아 압축을 풀어 문서 전체를 복원까지 → 게다가 내부 키 통계가 없어 추정 rows가 상수(등호 조건이면 0.5%)라 조인 계획까지 틀어진다.

우회의 원리는 하나다 — 값을 사본에 존재하게 만들기. 표현식 인덱스 ((attrs->>'genre'))를 걸면 인덱스 리프에 식의 결과가 물질화되고, ANALYZE가 그 식의 통계까지 만들어 줘서 추정도 같이 고쳐진다(CONCURRENTLY면 테이블 재작성도 쓰기 차단도 없다). 배열 원소나 임의 키 포함 검색이면 GIN(jsonb_ops/jsonb_path_ops, @>)인데, 이쪽은 통계를 안 만들어 주고 범위·정렬에도 못 쓴다.

그리고 반드시 한계를 붙인다 — 우회는 미리 정한 키만 빠르게 하므로, 조회 키가 늘어 표현식 인덱스가 다섯 개가 됐다면 그건 컬럼이어야 했던 것이다.

jsonb 안의 키 하나만 바꾸는 UPDATE는 싸지 않나요? PostgreSQL은 어차피 새 튜플이잖아요. 함정힌트: 반문 자체는 옳다. 갈리는 지점은 "무엇이" 다른가 두 가지

좋은 반문이고, 답은 "새 튜플인 건 같지만 쓰는 양과 인덱스가 다르다"이다.

컬럼 하나를 바꾼 새 튜플은 행 폭만큼이고, 안 바뀐 TOAST 값은 포인터만 복사되며, 인덱스된 컬럼이 아니면 HOT이라 인덱스를 하나도 안 건드린다. jsonb 내부 키 하나를 바꾸면 jsonb_set이 새 문서 전체를 만들고 → 새 튜플 + 새 TOAST 청크 전부 → 그 전부가 WAL(레플리카로도) → 옛 문서 전체가 죽은 튜플로 VACUUM 대기다. 재기록량이 바꾼 값의 크기가 아니라 문서 전체 크기에 비례한다. 여기에 GIN이나 표현식 인덱스가 걸려 있으면 비-HOT이라 테이블의 모든 인덱스에 새 엔트리까지 붙는다.

그래서 jsonb 안에 카운터·상태 같은 잦은 부분 갱신 대상을 두지 않는다 — 가장 잦은 쓰기를 가장 비싼 방식으로 하는 조합이다. 반대로 통째로 읽고 통째로 쓰는 작은 문서(사용자 설정)는 어차피 전체 재기록이라 이 비용이 문제가 안 된다 — 그래서 그쪽이 jsonb에 맞는 것이다.

관찰까지 말하면 완성이다 — pg_stat_user_tables의 n_tup_hot_upd / n_tup_upd 비율과 n_dead_tup, 그리고 pg_column_size()로 잰 평균 문서 크기.

1년 뒤 jsonb 안의 필드 이름을 바꿔야 합니다. 컬럼이면 RENAME 한 번인데, JSON은 뭐가 다른가요? 필수힌트: 선택지가 둘뿐이고, 둘 다 대가가 있다. 그리고 "지울 수 있는 시점"을 어떻게 아는가까지

컬럼은 카탈로그 한 번으로 모든 행이 즉시 같은 형태가 되지만, JSON은 DDL이 없는 대신 옛 형태의 행이 영구 공존한다. 선택지는 둘뿐이다.

(a) 전 행 UPDATE — SET doc = (doc - 'old') || jsonb_build_object('new', doc->'old') WHERE doc ? 'old'를 PK 범위로 잘라 배치 실행한다. 행마다 문서 전체 재기록이라 대용량이면 그 배치 자체가 WAL·bloat·VACUUM 부하 작업이다. (b) 영원한 이중 읽기 — 읽기 코드가 옛 이름과 새 이름을 둘 다 이해한다. 그리고 그 분기는 옛 형태 행이 0건이 됐다는 것을 확인하기 전까지 지울 수 없는데, schema_version이 없으면 확인할 방법이 없어서 사실상 영구화된다.

즉 JSON은 스키마 변경 비용을 없앤 게 아니라 DB의 DDL 한 번 → 애플리케이션의 모든 읽기 경로, 무기한으로 옮긴 것이다. 게다가 읽는 곳이 웹·앱·배치·어드민 네 군데면 네 곳 모두에 분기가 있어야 하고, 한 곳을 빠뜨리면 그 경로에서만 조용히 값이 안 나온다 — 컬럼이었다면 존재할 수 없는 버그다.

감당하는 장치는 schema_version 필드(세대 표시 → 읽기 시 업캐스팅 → 쓰기는 항상 최신 세대 → 잔여분 배치 마이그레이션 → 0건이 되면 분기 삭제)와 스키마 검증(CHECK + jsonb 연산자, 기존 테이블엔 NOT VALID → VALIDATE)이다.

주니어가 "상품 속성은 카테고리마다 달라서 attrs jsonb에 다 넣겠다"는 PR을 올렸습니다. 어떤 질문을 던지시겠어요? 필수힌트: 체크리스트를 그대로 질문 문장으로 바꾼다. 그리고 통과해도 두 가지를 더 요구한다

체크리스트를 질문으로 바꾼다.

⑴ 조 — "이 속성들 중 검색 필터·정렬·집계에 쓰이는 게 있나요?" 가격·브랜드·색상처럼 필터가 되는 것은 컬럼(또는 표현식 인덱스).
⑵ 균 — "모든 상품이 갖는 키가 있나요?" 있으면 그건 컬럼이다. 논쟁하지 말고 jsonb_object_keys 표본 쿼리로 세어 보자고 한다.
⑶ 갱 — "등록 후 자주 바뀌는 값이 있나요?" 재고·판매 상태는 컬럼.
⑷ 제 — "다른 테이블을 참조하거나 유일·필수여야 하는 값이 있나요?" 브랜드 ID·SKU는 컬럼/FK.

넷을 통과한 진짜 희소 속성(의류의 소재·세탁법, 가전의 소비전력)만 jsonb다. 그리고 두 가지를 더 요구한다 — 검증(어떤 키·타입이 허용되는지 CHECK 또는 DTO)과 승격 규칙("필터가 되는 순간 컬럼으로").

"GIN 걸면 검색은 되는데요"가 오면 — 검색 하나는 되지만 FK·부분 갱신·통계·정렬·오타 검출은 그대로라고 짚는다. 이 질문 세트가 곧 "귀찮아서"와 "비정형이라"를 가르는 리뷰 기준이다.

결제 PG 원문 응답을 jsonb로만 저장했는데, CS팀에서 "승인번호로 검색"을 요구합니다. 어떻게 하시겠어요? 그리고 처음부터 어떻게 설계했어야 하나요? 시니어 변별힌트: "지금"과 "처음부터"를 나눠 답하고, 마지막에 중복의 성격까지 규정한다

지금: 승인번호는 조회 키가 됐으니(⑴ 예) 승격한다. 가장 싼 경로는 표현식 인덱스 — CREATE INDEX CONCURRENTLY … ON payment_approvals ((gateway_response->>'approvalNo')). 기존 행을 다시 쓰지 않고, 테이블 재작성도 없으며, CONCURRENTLY라 쓰기도 막지 않는다(단 트랜잭션 밖에서 실행해야 하고, 실패하면 INVALID 인덱스가 남으므로 지우고 재시도한다). 단 PG사마다 응답 필드명이 다르면 COALESCE(resp->>'approvalNo', resp->>'approval_no') 식이 되어 식 일치가 깨지기 쉬우므로, 그 경우엔 nullable 정식 컬럼을 추가하고(상수 기본값 없는 nullable 추가는 카탈로그 변경만이라 싸다) 배치로 채운 뒤 일반 인덱스를 건다.

처음부터: 이중 저장이 정답이었다. 원문 gateway_response는 write-once 무손실 보존(스키마의 주인이 PG사이고, 분쟁 시 증거)이라 JSON이 맞고, "받은 그대로"가 요구이므로 정규화하는 jsonb가 아니라 json(또는 text)으로. jsonb에 넣으면 키 순서와 공백이 바뀌어 "바이트 단위로 같다"를 주장할 수 없다는 것까지 말하면 타입 구분을 이해한 것이다. 우리가 조회·집계·정합성 검증에 쓰는 값(거래 ID, 승인번호, 금액, 상태)은 저장 시점에 추출해 정식 컬럼으로 둔다.

트레이드오프를 양면으로 — 대가는 "같은 값이 두 곳에 있는 중복"이지만, 원문은 갱신 경로가 없어 어긋날 수 없는 스냅샷 성격의 중복이라 동기화 장치가 필요 없다. 편익은 조회 키가 인덱스를 타고, 금액에 numeric NOT NULL, 거래 ID에 UNIQUE를 걸어 불변식을 DB로 되돌린다는 것이다. "JSON이냐 컬럼이냐"의 이분법이 아니라 "원문 보존과 조회는 다른 요구이고, 다른 컬럼(그리고 다른 타입)이 맡는다"까지 가면 이 질문에서 변별된다.

그냥 전부 jsonb 쓰면 안 되나요? jsonb가 json의 상위 호환 아닌가요? 함정힌트: 상위 호환이 아닌 지점이 정확히 하나 있다

기능만 보면 jsonb가 넓은 게 맞다 — 연산자(@>, ?, jsonpath), GIN, 동등 비교가 전부 jsonb 쪽에만 있다. 그래서 실무의 기본 선택도 jsonb다.

그러나 "상위 호환"이 아닌 지점이 하나 있다 — 입력을 그대로 보존하지 않는다. jsonb는 저장 시 공백을 지우고, 키를 정렬하고(길이순 → 사전순), 중복 키는 마지막 값만 남긴다. '{"b": 1, "a": 2, "a": 3}'을 넣으면 {"a": 3, "b": 1}이 나온다. 이건 손실이 아니라 "정규화"지만, 요구가 "받은 그대로"였다면 그 순간 요구를 어긴 것이다.

그래서 json이 맞는 자리는 딱 하나 — 입력 바이트 보존 자체가 요구사항일 때(결제 PG 응답 원문, 웹훅 페이로드의 서명 검증 대상 같은 증거성 데이터). 그런 컬럼은 어차피 조회 조건으로 쓰지 않으므로 json의 "읽을 때마다 파싱" 비용도 문제가 되지 않는다. "둘 중 뭐가 낫냐"가 아니라 "무엇을 요구로 삼았느냐"의 문제다.

표현식 인덱스를 만들었는데 계획을 보니 여전히 Seq Scan입니다. 무엇을 의심하시겠어요? 함정힌트: 세 가지를 순서대로 본다. 그리고 "왜 에러가 안 났는지"도 설명해야 한다

① 식 일치를 가장 먼저 의심한다. 플래너는 파싱된 식 트리 기준으로 인덱스 정의와 쿼리의 식이 같을 때만 매칭한다. -> vs ->>, #>>'{price}' vs ->>'price', ::numeric vs ::float8 — 결과가 같아도 식이 다르면 안 탄다. 그리고 매칭에 실패해도 에러가 나지 않는다는 게 이 함정의 핵심이다. 조용히 Seq Scan으로 돌아가므로 모니터링에는 "그 API만 느려졌다"로만 보인다.

② ANALYZE를 돌렸는지. 표현식 인덱스를 만들어도 ANALYZE 전에는 그 식의 통계가 없다. 통계가 없으면 상수 추정이 남아 있어 플래너가 인덱스를 쓰는 계획을 비싸다고 판단할 수 있다.

③ 부분 인덱스인데 쿼리에 같은 WHERE가 없는지. … WHERE format_attrs ? 'genre'로 만든 부분 인덱스는 쿼리에도 그 조건이 있어야 플래너가 "이 인덱스로 답을 다 낼 수 있다"고 판단한다.

재발 방지까지 말하면 좋다 — 식을 리포지토리의 상수 문자열이나 뷰(또는 STORED 생성 컬럼) 한 곳에만 두어 사람이 매번 손으로 적지 않게 한다.

GIN을 걸었는데도 조회가 느리고, 계획의 추정 행 수도 이상합니다. 무엇을 의심하시겠어요? 가산점힌트: 네 가지 — 그중 하나는 "원래 GIN이 못 하는 일"이다

① 애초에 GIN이 못 하는 조건인지 본다. 범위(>, BETWEEN) · 정렬(ORDER BY) · 접두사 검색은 역색인에 순서가 없어서 구조적으로 불가능하다. 이건 튜닝 문제가 아니라 도구 선택 문제이고, 답은 표현식 B-tree다.

② 추정 행 수는 GIN으로 안 고쳐진다. GIN은 통계를 만들어 주지 않는다 — 반납 ②는 그대로다. 그래서 계획에 rows=3000 같은 상수 추정이 남고, 그 노드가 조인의 한 축이면 조인 방식이 뒤집힌다. 통계가 필요하면 표현식 인덱스나 CREATE STATISTICS를 따로 얹는다.

③ pending list(fastupdate = on). 기본 설정에서 GIN은 새 엔트리를 임시 목록에 모아 뒀다 나중에 병합한다. 병합 전까지는 읽기가 트리와 pending list를 둘 다 훑어야 해서 조회가 느려지고, 병합이 일어나는 순간 그 쿼리가 병합 비용을 뒤집어쓴다 — "가끔 한 번씩만 튀는" 지연의 원인이 된다.

④ 후보가 너무 넓게 잡히는 경우. jsonb_ops는 모든 키와 모든 값을 엔트리로 만들어서 흔한 키 때문에 후보가 넓어진다. 포함 검색만 한다면 jsonb_path_ops로 바꾸거나 색인 범위를 서브 문서로 좁힌다(gin ((attrs->'tags') jsonb_path_ops)). 그리고 계획에 Recheck Cond가 보이는 것 자체는 정상이다 — 비트맵이 페이지 단위로 흐려지면(lossy) 그 페이지의 행을 다시 검사하기 때문이다.

표현식 인덱스와 STORED 생성 컬럼 중 무엇을 고르시겠어요? 가산점힌트: 기준은 "테이블 크기"와 "이 키를 앞으로 무엇으로 취급할 것인가"

큰 테이블에는 표현식 인덱스가 먼저다. 테이블 행을 한 바이트도 건드리지 않고 사본만 새로 만들며, CONCURRENTLY면 쓰기도 막지 않는다. 그리고 ANALYZE가 그 식의 통계까지 걷어 준다.

생성 컬럼(STORED)은 "이 키는 이제 사실상 컬럼이다"라고 선언할 때의 도구다. 정식 컬럼 이름으로 조회하니 식 일치 함정이 사라지고, 일반 인덱스·통계·NOT NULL·CHECK가 전부 붙는다. 대신 값이 행에도 저장되어 테이블이 커지고, 기존 테이블에 추가하면 테이블 재작성(ACCESS EXCLUSIVE 잠금)이다 — 수억 건 테이블에서는 이게 결정적이다.

MySQL 대조를 얹으면 더 좋다 — MySQL은 JSON 식에 인덱스를 직접 못 걸어 VIRTUAL 생성 컬럼 + 인덱스가 정석이고, VIRTUAL은 행에 값을 저장하지 않고 인덱스에만 물질화되며 추가가 메타데이터 변경만이라 싸다. PostgreSQL의 생성 컬럼은 STORED만 있어 추가 비용의 성격이 정반대라는 점이 대조 포인트다.

jsonb 안의 author_id에는 FK를 못 건다고 했는데, 그러면 참조 정합성은 어떻게 지키나요?힌트: "무엇이 없어졌는지"를 먼저 정확히 말한다 — 없어진 건 "검사"가 아니라 "삭제 시점의 차단"이다

먼저 무엇이 없어졌는지를 정확히 말한다. FK가 있었다면 작가를 삭제하는 시점에 ERROR: … violates foreign key constraint로 차단됐을 일이, jsonb에서는 아무 일도 일어나지 않는다. 즉 없어진 것은 사후 검사가 아니라 사전 차단이고, 그래서 고아(orphan) 참조가 검출 수단 없이 쌓인다. 발견은 보통 "작가 이름이 안 나온다"는 CS 문의로 온다.

1순위 답은 "지키는 방법"이 아니라 "거기 두지 않는 것"이다. 다른 테이블을 참조하는 값은 판별 질문 ⑷에 "예"이므로 정식 컬럼 + FK(또는 별도 테이블)로 간다. 특히 1:N 관계를 JSON 배열로 넣은 경우(주문의 상품 목록)는 비정형이 아니라 그냥 정규화 대상이다.

불가피하게 남긴다면 — jsonb_array_elements로 전 행을 전개해 참조 대상과 대조하는 정기 배치를 만들고, 그 배치가 존재해야 한다는 사실 자체를 대가로 계상한다. 그리고 삭제 쪽 코드 경로에 애플리케이션 검증을 붙이더라도, 그 경로를 지나지 않는 psql 직접 삭제·다른 배치에는 뚫린다는 점을 함께 말해야 한다.

"일단 jsonb로 넣고 필요해지면 컬럼으로 빼면 되지 않나요?" — 이 말의 어디가 맞고 어디가 틀린가요? 시니어 변별힌트: 절반은 맞다. 틀린 절반은 "빼는 비용"과 "빼기로 결정할 사람"이다

맞는 절반: 정말로 형태가 안 굳은 실험 속성이라면 그 판단은 합리적이고, 승격 경로도 실재한다 — 표현식 인덱스는 테이블 재작성 없이(CONCURRENTLY) 붙고, nullable 컬럼 추가도 카탈로그 변경만이라 싸다.

틀린 절반 ①: 빼는 비용이 넣을 때보다 훨씬 크다. 컬럼으로 승격하려면 컬럼 추가 → 전 행 백필(행마다 문서 전체 재기록, 반납 ③) → 이중 쓰기 → 읽기 전환 → 옛 키 정리를 배포 여러 번에 걸쳐 해야 하고, 그동안 두 곳에 같은 값이 있는 기간이 생긴다. "나중에 빼면 된다"의 "나중에"는 DDL 한 번이 아니라 마이그레이션 프로젝트다.

틀린 절반 ②: 빼기로 결정할 사람이 없다. jsonb의 실패는 한 번의 잘못된 결정이 아니라 수정하지 않은 채 흘려보낸 시간에서 온다. 6개월 뒤 "이걸로 필터링하고 싶다"가 왔을 때 "일단 되니까" 두면 그대로 굳고, 출구 규칙이 없는 JSON은 "임시"라는 이름으로 영구화된다.

그래서 답은 "쓰지 마라"가 아니라 "출구를 명시하고 쓰라"이다 — 승격 규율을 팀 규칙으로 문서화하고, 점검 시점(jsonb 키가 WHERE에 등장하는 PR 리뷰 / 분기별 키 분포 재측정)을 정해 둔다. 그리고 schema_version이 있어야 승격 후 옛 세대를 언제 지울 수 있는지를 숫자로 판단할 수 있다.

MySQL로 물어보면 답이 달라지는 부분은? 경험 대조힌트: 판별 규율은 같다. 다른 것은 도구와 비용 구조 다섯 지점

판별 규율(네 질문 · 안전망)은 같고, 도구와 비용 구조 다섯 지점이 다르다.

① 타입과 문법 — MySQL은 JSON 타입 하나(내부적으로 바이너리)이고 경로를 ->>'$.genre'처럼 JSON path 문자열로 쓴다. PostgreSQL은 json/jsonb 둘이고 ->>·#>>·@>·? 연산자에 jsonpath가 따로 있다. "원문 바이트 보존"에 PostgreSQL은 json이라는 선택지가 있지만 MySQL은 text로 내려가야 한다.

② 인덱스 도구 — MySQL은 JSON 컬럼에도 JSON 식에도 인덱스를 직접 못 걸어 VIRTUAL 생성 컬럼 + 인덱스가 정석이고(메타데이터 변경만이라 추가가 싸다), 배열은 멀티밸류 인덱스다. PostgreSQL은 표현식 인덱스(+ 표현식 통계)와 키를 미리 정하지 않는 GIN이 있다 — 대신 STORED 생성 컬럼 추가는 테이블 재작성이다.

③ 부분 갱신 — MySQL 8.0은 JSON_SET/JSON_REPLACE/JSON_REMOVE가 크기가 늘지 않는 등 조건을 만족하면 제자리 부분 갱신을 하고 binlog에도 부분 갱신 로그를 남길 수 있다(조건이 까다로워 설계 가정으로 삼을 수는 없다). PostgreSQL은 MVCC라 예외 없이 문서 전체가 새 튜플이고 TOAST 청크까지 다시 쓴다 — 반납 ③이 더 무겁다.

④ 스키마 검증 — MySQL은 JSON_SCHEMA_VALID로 JSON Schema를 CHECK에 바로 넣을 수 있지만, PostgreSQL은 내장 함수가 없어 CHECK + jsonb 연산자 조합이거나 확장(pg_jsonschema)이다.

⑤ 통계 — 둘 다 내부 키의 통계가 없어 추정이 상수인 것은 같지만, PostgreSQL은 표현식 인덱스(또는 CREATE STATISTICS)가 그 식의 통계를 만들어 준다는 출구가 있다.

한 줄 요약
jsonb 컬럼은 행마다 다른 데이터를 DDL 없이 담는 자유를 사는 대신 인덱스(정렬 사본에 값이 없어 Seq Scan + 행마다 키 탐색)·통계(내부 키 분포를 모르니 추정이 상수가 되어 조인 방식까지 뒤집힌다)·좁은 갱신(키 하나 바꿔도 문서 전체가 새 튜플 + TOAST + WAL + 죽은 튜플)·타입/제약(불변식이 DB에서 앱 관례로 강등되고 오타 키도 조용히 저장된다)을 반납하는 거래이므로, "조회·집계 대상인가 / 모든 행이 같은 키인가 / 부분 갱신이 잦은가 / DB가 지킬 불변식인가"에 하나라도 예면 컬럼이고, 넷 다 아니오인 외부 원문(바이트 보존이 요구면 정규화하지 않는 json)·희소 속성·통째로 읽고 쓰는 문서만 jsonb에 둔다. 쓰기로 했다면 조회 조건이 된 키는 표현식 인덱스(CONCURRENTLY, 통계까지 따라온다)나 GIN(포함 검색만, 범위·정렬·통계는 못 산다)으로 승격하고, CHECK + jsonb 연산자(또는 DTO)로 검증하며, schema_version으로 세대를 세어 분기를 지울 시점을 판단하는 안전망을 함께 든다. 마지막 관문은 스키마 진화의 정체를 정직하게 말하는 것이다 — jsonb는 마이그레이션을 없앤 것이 아니라 DB의 DDL 한 번을 애플리케이션 읽기 코드의 영구 분기로 옮긴 것이고, PostgreSQL은 도구가 풍부해서 "되니까 쓴다"의 유혹이 큰데 되는 것과 써야 하는 것은 다르다.
