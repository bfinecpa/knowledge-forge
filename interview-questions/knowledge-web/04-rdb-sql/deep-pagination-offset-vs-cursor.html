깊은 페이지네이션 — OFFSET은 "건너뛰기"가 아니라 "읽고 버리기"다

Q. "LIMIT 100000, 20 같은 깊은 페이지네이션이 느린 이유와 해결책(no-offset, 커서 기반)은?"
핵심 관전 포인트 — 첫 답변으로 그대로 말한다
① 왜 느린가 (메커니즘 사슬) LIMIT 100000, 20이 느린 이유는 DB가 10만 건을 건너뛰는 게 아니라 100,020건을 전부 읽어 조립한 뒤 앞의 10만 건을 버리기 때문이다. B+Tree에는 "앞에서 N번째"라는 좌표가 없어 세며 걷는 것 말고는 방법이 없고, 정렬 기준이 세컨더리 인덱스면 버릴 행에 대해서도 PK로 클러스터드 인덱스를 다시 찾는 북마크 룩업(랜덤 I/O)을 100,020번 지불한다 — 비용이 페이지 번호에 선형으로 비례한다.
② 해결책 — 네 가지를 한 번에 커서(키셋) — WHERE (created_at, id) < (마지막 값)으로 시작점을 인덱스 탐색으로 바꿔 offset 자체를 없앤다 · 지연 조인 — 커버링 인덱스로 PK 20개만 먼저 뽑아 북마크 룩업을 20회로 줄인다 · offset 상한을 API 레벨에서 강제한다(안전망) · 복잡한 검색은 검색 엔진에 위임한다.
③ 커서의 대가 — 같은 호흡에 임의 페이지 점프 불가, 정렬 키 유일성 필요, total count 미제공, API 스펙 변경을 붙여야 완결된 답이다.

1. 왜 느린가 — offset은 skip이 아니라 read-and-discard다

📜
비유 — 페이지 번호 없는 두루마리. "앞에서 10만 번째 줄"로 가려면 처음부터 한 줄씩 펼치며 세는 수밖에 없다. 게다가 각 줄의 본문(각주)이 다른 서고에 있으면(세컨더리 인덱스), 버릴 줄에 대해서도 매번 서고를 다녀와야 한다(북마크 룩업). 커서는 책갈피다 — "이 문장 다음부터"라고 하면 바로 그 자리를 편다.

1-1. B+Tree에는 "앞에서 N번째"라는 좌표가 없다 — 그리고 세는 주체는 서버 계층이다

인덱스는 "값이 X인 곳"으로는 트리 높이만큼(로그 시간)이면 가지만, "앞에서 N번째"로 가는 길은 없다. 노드가 자기 아래 서브트리에 행이 몇 건 있는지 세어 두지 않고, MVCC 때문에 트랜잭션마다 보이는 행 집합이 달라 "N번째"라는 값은 저장해 둘 수도 없다. 그러니 10만 번째로 가려면 처음부터 세며 걷는 수밖에 없다.

세는 주체도 중요하다. LIMIT/OFFSET은 스토리지 엔진(InnoDB)이 아니라 그 위층의 SQL 서버 계층이 처리한다. 엔진은 조건에 맞는 행을 한 건씩 위로 올리고, 서버 계층이 카운터를 세며 offset에 못 미친 행은 버린다. 엔진은 그 행이 "결국 버려질 행"인지 알 길이 없으므로 행을 온전히 조립해서 올린다. 이 한 문장이 아래 모든 비용의 출발점이다.

그림 1 — read-and-discard의 단계. 세컨더리 인덱스로 정렬하면 리프에 PK밖에 없어 행마다 클러스터드 인덱스를 루트부터 다시 찾고(②), 조립된 행을 서버 계층이 세며 버린다(③). 일의 양은 offset + limit에 비례하고 결과 크기(20)와 무관하다.

1-2. 대비 — offset은 "세며 걷기", 커서는 "탐색으로 점프"

그림 2 — 같은 시작점, 다른 도착 방법. B+Tree는 "N번째"는 못 찾지만 "값이 X보다 작은 첫 지점"은 로그 시간에 찾는다. 커서는 그 성질을 쓴다 — 시작점 탐색이 O(offset)에서 트리 높이 한 번으로 바뀌고, 그 뒤 limit+1건만 순차로 읽는다.

1-3. 정렬 키에 따라 사슬이 달라진다 — A / B / C

사슬 A

2. 해결책 4가지 — 목록으로 먼저, 각각의 대가와 함께

🧩
항상 네 개를 세트로 꺼낸다. 하나만 말하면 "그 방법을 못 쓰는 상황에서는요?"가 바로 따라온다. 연상: 커·지·상·검  커서 · 지연 조인 · 상한 · 검색 엔진
① 근본 해결
커서(키셋, no-offset)
"몇 번째부터"를 "이 값 다음부터"로 — offset 자체를 없앤다
대가: 임의 점프 불가 · 정렬 키 유일·불변 · total count 없음 · API 스펙 변경
② 완화책
지연 조인(deferred join)
offset은 두고 버릴 행의 북마크 룩업만 없앤다 — 커버링 인덱스로 PK 20개 먼저
대가: 여전히 O(offset). 장점은 API·UI 무변경
③ 안전망
offset 상한
깊은 페이지 요청을 API 레벨에서 거절 — 인터셉터 한 장
대가: 깊은 페이지가 진짜 필요한 호출자에게 대체 경로(커서 API)를 안내해야 함
④ 구조 변경
검색 엔진 위임
다중 필터 + 자유 정렬 + 깊은 탐색이 동시에 필요하면 RDB의 일이 아니다 — search_after
대가: 색인 동기화 지연 · 운영 컴포넌트 추가 · 이중 저장
실무 조합 규칙 — "③은 항상 + ①이나 ② 중 하나" ③ 없이 ①만 하면 구 API가 남아 있는 동안 계속 두들겨 맞는다. 상한 없이 커서 API만 추가하면 아무도 옮겨오지 않는다.

2-1. 커서(키셋) 기반 — "몇 번째부터"를 "이 값 다음부터"로

원리는 하나다. B+Tree는 "N번째"는 못 찾지만 "값이 X보다 작은 첫 지점"은 로그 시간에 찾는다. 그러니 "지난 페이지의 마지막 값"을 클라이언트가 들고 왔다가 WHERE로 넘기면, 시작점 탐색이 O(offset)에서 트리 높이 한 번으로 바뀐다. 읽는 양은 페이지가 아무리 깊어도 항상 limit + 1건이다.

BEFORE 5,001페이지 — 100,020건 읽고 100,000건 버림
SELECT * FROM posts
ORDER BY id DESC
LIMIT 100000, 20;                -- offset 100,000: 서버 계층이 세며 버린다
AFTER "마지막으로 본 id 다음부터 20건" — 인덱스 탐색 1회 + 20건 순차
SELECT * FROM posts
WHERE id < :last_seen_id          -- 지난 페이지 마지막 행의 id = 커서
ORDER BY id DESC
LIMIT 20;                         -- offset 없음. 읽는 양 = 항상 limit(+1)

복합 정렬 키 — created_at 하나로는 왜 안 되는가

실제 목록은 created_at DESC처럼 유일하지 않은 컬럼으로 정렬한다. 같은 초에 글이 세 개 올라올 수 있다. 정렬 키가 행을 유일하게 식별하지 못하면 "그 다음"이 정의되지 않는다. 아래는 같은 12:34:56에 글 #31·#32·#33이 있고, 1페이지가 #33에서 끊긴 상황이다.

2페이지 커서 조건#33 (이미 봄)#32#31#30 (12:34:55)판정
created_at < :c제외건너뜀건너뜀포함누락
created_at <= :c다시 나옴포함포함포함중복
(created_at, id) < (:c, 33)제외포함포함포함정확

처방은 유일한 컬럼을 tie-breaker로 붙여 정렬 순서를 전순서(total order)로 만드는 것 — (created_at, id). 커서도 두 값을 함께 들고, 조건은 튜플 비교다.

-- 정렬 키 (created_at DESC, id DESC) · 인덱스 (created_at, id)
-- InnoDB 세컨더리 인덱스는 리프에 PK를 품어 (created_at)만 있어도 사실상 이 순서지만,
-- 명시하는 편이 실행 계획 예측이 쉽다.

-- 형태 1: 풀어 쓴 조건 — 어느 DB/버전에서든 인덱스 범위 스캔으로 잘 잡힌다
SELECT * FROM posts
WHERE  created_at <  :last_created_at
   OR (created_at =  :last_created_at AND id < :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 형태 2: 행 생성자(row constructor) 비교 — 같은 의미를 한 줄로
SELECT * FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
-- PostgreSQL 은 이 형태를 인덱스로 잘 태운다. MySQL 은 문법은 지원하지만 인덱스 범위
-- 최적화 여부가 버전·조건에 따라 달라 EXPLAIN 으로 확인하고, 불확실하면 형태 1.

규칙 — 정렬 방향과 부등호 방향은 반드시 일치. 읽는 법: "created_at이 더 이르거나, 같은 시각이면 id가 더 작은 것". 둘 다 DESC면 둘 다 <. ASC 정렬이면 >로 뒤집는다. 방향이 섞이면(created_at DESC, id ASC) 그 컬럼만 뒤집어 … AND id > :last_id.

커서는 불투명(opaque) 문자열로 넘긴다

클라이언트에 created_at과 id를 따로 노출하면 클라이언트가 값을 조작해 호출하기 시작하고, 나중에 정렬 키를 바꿀 수 없게 된다. 두 값을 하나로 직렬화해 Base64 같은 불투명 토큰으로 주고받는다 — "이 문자열을 다음 요청에 그대로 돌려주세요"가 계약이 된다.

{
  "items": [ ... 20건 ... ],
  "nextCursor": "MjAyNi0wOC0zMFQxMjozNDo1NnwxMDIwMzQ",   // created_at|id 를 Base64 로
  "hasNext": true
}

커서의 대가 — 얻는 것과 잃는 것을 한 호흡에

얻는 것깊이와 무관한 상수 비용 · 스크롤 중 삽입·삭제에도 중복/누락 없음(§5) · COUNT 쿼리 불필요(Slice)
지불 ①
임의 페이지 점프 불가
커서는 "직전 페이지의 끝"만 안다. "3,204페이지로" 못 간다. 그래서 커서는 무한 스크롤·더 보기·타임라인과 짝. 페이지 번호 UI를 기획이 고수하면 ②+③.
지불 ②
total count 미제공
"전체 12,345건" 표시가 사라진다. 대개 COUNT 비용까지 던져 버리는 이득이지만, 기획과 합의가 필요한 요구사항 변경.
지불 ③
정렬 유연성 상실
정렬 키는 유일(tie-breaker)하고 불변이어야 한다 — updated_at 정렬에 커서를 쓰면 갱신된 행이 위로 튀어 중복/누락 재발. 정렬 축마다 커서·인덱스를 따로 설계 → 컬럼 헤더 클릭 정렬과 상성이 나쁘다(그건 ④의 영역).
지불 ④
API 스펙 변경
page/size → cursor/size, 응답 구조도 바뀜. 구버전이 오래 남는 모바일 앱이 있으면 구 API엔 ③ 상한, 신 API 병행 운영 후 폐기하는 마이그레이션 계획이 필요. rationale의 "미리 아는 것의 가치" = 처음부터 커서로 설계했으면 안 냈을 값.

연상: 점·카·정·A  — 점프 불가 · 카운트 없음 · 정렬 유연성 · API 변경

가산점 — "이전 페이지"는 어떻게?
조건과 정렬을 반대로 뒤집어 조회한 뒤 결과 리스트를 다시 뒤집어 돌려준다: WHERE (created_at, id) > 커서 ORDER BY created_at ASC, id ASC LIMIT 20 → reverse. 양방향이 필요하면 prevCursor도 함께 내려준다.

2-2. 지연 조인(deferred join) — offset은 두고 "버릴 행의 룩업"만 없앤다

페이지 번호 UI를 당장 못 버리거나 API를 바꿀 수 없을 때의 처방. 발상: 어차피 버릴 100,000건에 대해 행 전체를 조립하는 게 낭비이니, 먼저 인덱스만 훑어 PK 20개를 고르고, 그 20개에 대해서만 본 테이블을 읽는다.

BEFORE 세컨더리 인덱스 → 북마크 룩업 100,020회 → 100,000건 버림
SELECT *  FROM posts               -- 행 전체가 필요 → 엔트리마다 PK 룩업
ORDER BY created_at DESC
LIMIT 100000, 20;
AFTER 서브쿼리는 (created_at, id) 인덱스만으로 끝난다(커버링) — 룩업은 바깥 조인의 20회뿐
SELECT p.*
FROM posts p
JOIN (
    SELECT id                     -- id, created_at 모두 인덱스 안 → 북마크 룩업 없음
    FROM posts
    ORDER BY created_at DESC
    LIMIT 100000, 20             -- offset 은 그대로. 인덱스 리프만 순차로 세며 걷는다
) AS page ON page.id = p.id       -- 살아남은 PK 20개만 본 테이블 읽기
ORDER BY p.created_at DESC;        -- 조인 결과 순서는 보장되지 않으므로 바깥에서 다시 정렬
서브쿼리 SELECT id … ORDER BY created_at→ 필요 컬럼(id, created_at)이 전부 인덱스 안 = 커버링→ 북마크 룩업 없이 리프만 순차로 세며 버림→ 엔트리는 행보다 작아 페이지 수 적음→ 랜덤 I/O 100,020회 → 20회
대가 — 여전히 O(offset)인덱스 스캔이 싸다는 것이지 공짜는 아니라서, 페이지가 수만 단위로 깊어지면 다시 느려진다. 장점은 API도 UI도 바꾸지 않고 오늘 밤 배포할 수 있다는 것 — 그래서 "커서로 가는 마이그레이션 기간의 다리"로 쓴다.

2-3. offset 상한 — API 레벨에서 강제하는 안전망

"5,001페이지를 누가 보겠어"는 사실이지만, 사람은 안 봐도 크롤러와 관리자 화면의 '마지막 페이지' 버튼은 본다. 상한은 업계 관행이다 — 구글 검색도 일정 페이지 이상은 넘겨주지 않고, Elasticsearch는 from + size가 index.max_result_window(기본 10,000)를 넘으면 요청 자체를 거절한다.

핵심은 어디에 두느냐다. 컨트롤러마다 if (page > 500) throw를 쓰면 다음 사람이 새 목록 API를 만들 때 빠뜨린다. 사람의 기억에 의존하지 않는 위치 — 모든 목록 요청이 지나가는 한 곳 — 에 둔다.

BEFORE 컨트롤러마다 기억해서 넣어야 하는 검사 — 새 API가 생기면 빠진다

AFTER 인터셉터 한 장 — page/size를 받는 모든 목록 API 앞에서 자동으로 거절
@Component
public class DeepOffsetGuardInterceptor implements HandlerInterceptor {

    static final long MAX_OFFSET = 10_000;   // 팀 합의값. 넘는 요청은 커서 API 로 보낸다
    static final int  MAX_SIZE   = 100;

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        int page = parseOrDefault(req.getParameter("page"), 0);
        int size = parseOrDefault(req.getParameter("size"), 20);
        if (size > MAX_SIZE || (long) page * size > MAX_OFFSET) {
            // → @ControllerAdvice 에서 400 으로 변환.
            //   메시지에 "cursor 파라미터를 사용하세요" 를 담아 대체 경로를 안내한다.
            throw new DeepPaginationException(page, size, MAX_OFFSET, MAX_SIZE);
        }
        return true;
    }

    private static int parseOrDefault(String raw, int def) {
        try { return raw == null ? def : Integer.parseInt(raw); }
        catch (NumberFormatException e) { return def; }   // 파싱 실패는 바인딩 단계가 400 으로 처리
    }
}

@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new DeepOffsetGuardInterceptor())
                .addPathPatterns("/api/**");          // 목록 API 가 있는 경로 전체
    }
}

public final class BoundedPageRequest {
    private static final long MAX_OFFSET = 10_000;

    public static Pageable of(int page, int size, Sort sort) {
        Pageable p = PageRequest.of(page, size, sort);
        if (p.getOffset() > MAX_OFFSET) {
            throw new DeepPaginationException(
                "offset %d > %d. 전수 순회는 커서 기반 리더를 사용하세요"
                    .formatted(p.getOffset(), MAX_OFFSET));
        }
        return p;
    }
}

3. 실무 사례 — 관리자 페이지의 "마지막 페이지" 버튼과 크롤러

3-1. 증상에서 원인까지

월요일 오전, 주문 목록 API의 p99가 튀고 DB CPU가 치솟는다. 슬로 쿼리 로그에는 같은 쿼리가 offset만 바꿔가며 반복된다.

SELECT * FROM orders WHERE status = 'DONE' ORDER BY created_at DESC LIMIT 99980, 20;
SELECT * FROM orders WHERE status = 'DONE' ORDER BY created_at DESC LIMIT 100000, 20;
SELECT * FROM orders WHERE status = 'DONE' ORDER BY created_at DESC LIMIT 100020, 20;
증상: p99 급등 · DB CPU→ 슬로 로그: offset만 다른 같은 쿼리→ 호출자 추적: "마지막 페이지 »" 버튼 or 크롤러/배치 전수 순회→ EXPLAIN: rows 10만 단위, 북마크 룩업 or Using filesort

둘 다 사람이 목록을 읽는 속도가 아니라 기계 속도로 깊은 페이지를 연타한다. §1-3 사슬 B 그대로다.

3-3. 배치의 전수 순회 — 같은 함정, 다른 옷

"모든 주문을 순회하며 정산 파일을 만드는" 배치가 PageRequest.of(page++, 1000)으로 돌면, 뒤로 갈수록 한 페이지가 느려져 실행 시간이 페이지 수의 제곱에 비례해 늘어난다(매 페이지가 offset만큼 읽으므로 1 + 2 + … + P). 처방은 동일하게 키셋 — 마지막 id를 들고 WHERE id > :lastId ORDER BY id LIMIT 1000을 반복한다.

가산점 — Spring Batch 리더 선택이 곧 이 문항의 적용JpaPagingItemReader는 내부적으로 offset 페이징(setFirstResult)이라 같은 문제를 안고 있고, JdbcPagingItemReader는 sortKeys를 기준으로 "마지막 키 다음부터"를 조회하는 키셋 방식이다.

@Repository
@RequiredArgsConstructor
public class PostQueryRepository {
    private final JPAQueryFactory queryFactory;

    public Slice<Post> findSlice(Long boardId, PostCursor cursor, int size) {
        List<Post> rows = queryFactory
                .selectFrom(post)
                .where(post.board.id.eq(boardId),
                       afterCursor(cursor))                  // 첫 페이지면 null → 무시
                .orderBy(post.createdAt.desc(), post.id.desc())
                .limit(size + 1L)                             // 다음 페이지 유무 판정용 +1
                .fetch();

        boolean hasNext = rows.size() > size;
        if (hasNext) rows.remove(size);
        return new SliceImpl<>(rows, PageRequest.of(0, size), hasNext);
    }

    // 정렬 (createdAt DESC, id DESC) 와 부등호 방향을 반드시 맞춘다
    private BooleanExpression afterCursor(PostCursor c) {
        if (c == null) return null;
        return post.createdAt.lt(c.createdAt())
                .or(post.createdAt.eq(c.createdAt()).and(post.id.lt(c.id())));
    }
}

// 커서 값 객체 — 클라이언트에는 불투명 토큰으로만 노출
public record PostCursor(LocalDateTime createdAt, Long id) {

    public String encode() {
        String raw = createdAt + "|" + id;
        return Base64.getUrlEncoder().withoutPadding().encodeToString(raw.getBytes(UTF_8));
    }

    public static PostCursor decode(String token) {
        String[] parts = new String(Base64.getUrlDecoder().decode(token), UTF_8).split("\\|");
        return new PostCursor(LocalDateTime.parse(parts[0]), Long.parseLong(parts[1]));
    }

    public static PostCursor from(Post last) {
        return new PostCursor(last.getCreatedAt(), last.getId());
    }
}

// 응답 조립 — 마지막 행에서 다음 커서를 만든다
public PostListResponse list(Long boardId, String cursorToken, int size) {
    PostCursor cursor = cursorToken == null ? null : PostCursor.decode(cursorToken);
    Slice<Post> slice = postQueryRepository.findSlice(boardId, cursor, size);
    String next = slice.hasNext()
            ? PostCursor.from(slice.getContent().get(slice.getNumberOfElements() - 1)).encode()
            : null;
    return new PostListResponse(toDtos(slice.getContent()), next, slice.hasNext());
}

동적 정렬(컬럼 헤더 클릭)을 지원하려는 순간 afterCursor가 정렬 축마다 분기해야 하고 커서 구성 값도 바뀐다 — §2-1 "정렬 축마다 커서 설계"의 대가가 코드에서 이렇게 드러난다.

가산점 — Spring Data JPA 3.1의 키셋 스크롤 API (Window / ScrollPosition.keyset())
public interface PostRepository extends JpaRepository<Post, Long> {
    Window<Post> findFirst20ByBoardIdOrderByCreatedAtDescIdDesc(Long boardId, ScrollPosition position);
}

Window<Post> first = repo.findFirst20ByBoardIdOrderByCreatedAtDescIdDesc(boardId, ScrollPosition.keyset());
Window<Post> next  = repo.findFirst20ByBoardIdOrderByCreatedAtDescIdDesc(
                             boardId, first.positionAt(first.size() - 1));
// 정렬 컬럼(createdAt, id)의 값을 위치로 삼아 (createdAt, id) < (?, ?) 조건을 자동 생성한다

정렬에 유일 컬럼(id)이 들어 있어야 한다는 전제는 동일하다 — 프레임워크가 튜플 조건을 대신 써 줄 뿐, 정렬 키 유일성이라는 대가는 사라지지 않는다.

5. 속도만이 아니다 — 스크롤 중 새 글이 오면 offset은 결과가 밀린다

사용자가 1페이지를 보는 동안 새 글이 하나 올라오면 무슨 일이 생기나. 아래는 size=3으로 축약한 타임라인이다(실제 LIMIT 20, 20과 구조는 같다).

그림 3 — 같은 t3, 다른 결과. offset은 "앞에서 N번째"를 매번 다시 세므로 새 글 하나가 창을 밀어 중복을, 삭제는 창을 당겨 누락을 만든다. 커서는 "이 값 다음"을 조회하므로 삽입·삭제와 무관하게 이어진다. 커서 기반은 성능 최적화이면서 동시에 정합성 개선이라고 덧붙이면 답의 격이 올라간다.
단, 커서도 정렬 키가 갱신되는 컬럼이면 같은 문제가 재발한다updated_at DESC 정렬에 커서를 쓰면 스크롤 도중 갱신된 행이 위로 튀어 올라 위치가 바뀌고, 중복/누락이 다시 생긴다. 커서의 정렬 키는 불변이어야 한다는 조건(§2-1 지불 ③)이 여기서 나온다.

6. 셀프 테스트 — 꼬리질문

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 양면을 다 말해야 통과, 추가는 md에 없던 파생 질문.

"정렬이 PK 순이면 LIMIT 100000, 20도 괜찮은 거 아닌가요?"

"덜 나쁘다"이지 "괜찮다"가 아니다. 사슬로 — PK 순이면 클러스터드 리프에 행 전체가 있어 북마크 룩업(랜덤 I/O)은 없다. 그러나 서버 계층이 100,000건을 세며 버리는 read-and-discard는 그대로이고, 100,020건은 리프 페이지 수백~수천 장이며, 깊은 페이지의 오래된 데이터는 버퍼 풀에 없을 확률이 높아 디스크 순차 읽기가 된다. 랜덤 I/O 항이 사라졌을 뿐 비용은 여전히 offset에 선형이다. 그리고 실제 목록의 정렬은 대부분 PK가 아니다.

"커서 기반으로 바꾸면 무엇을 잃습니까? 그럼 offset을 그대로 두는 게 맞는 경우는요?" 시니어 변별

잃는 것을 먼저 목록으로 — ⑴ 임의 페이지 점프(페이지 번호 UI 불가) ⑵ total count(전체 건수 표시 불가) ⑶ 정렬 유연성(정렬 축마다 커서·인덱스 따로, 정렬 키는 유일·불변) ⑷ API 호환성(스펙 변경, 구·신 병행, 클라이언트 전부 수정). 얻는 것은 깊이와 무관한 상수 비용과 스크롤 중 중복/누락 없음.

offset을 두는 게 맞는 경우 — 사용자가 실제로 앞 몇 페이지만 보는 화면 + 페이지 번호 UI가 요구사항인 경우. 이때는 커서로 갈아엎지 않고 offset 상한 + 지연 조인으로 충분하다. 고르는 기준은 "커서가 더 빠르다"가 아니라 "이 화면의 접근 패턴이 순차 탐색인가 임의 접근인가"다. 순차(피드·타임라인·무한 스크롤)면 커서, 임의(관리자 그리드·검색 결과 페이지 번호)면 offset + 상한 + 지연 조인, 임의인데 깊이까지 필요하면 검색 엔진.

"정렬 키가 created_at 하나면 커서로 왜 안 됩니까? 같은 시각에 여러 건이면 어떻게 되나요?"

정렬 키가 유일하지 않으면 "그 다음"이 정의되지 않는다. 같은 초에 글 세 개가 있고 커서가 그중 첫 번째에서 끊겼다면 — created_at < :last는 나머지 두 개를 건너뛰고(누락), created_at <= :last는 이미 본 첫 번째를 다시 준다(중복). 처방은 유일 컬럼 id를 tie-breaker로 붙여 (created_at, id)를 전순서로 만들고, 조건을 created_at < :c OR (created_at = :c AND id < :i)로, 인덱스도 (created_at, id)로 두는 것.

가산점 InnoDB 세컨더리 인덱스는 리프에 PK를 품으므로 (created_at) 인덱스만 있어도 물리적으로는 이미 (created_at, id) 순이다 — 그래도 복합 인덱스를 명시하는 편이 실행 계획이 예측 가능하고 다른 DB로 옮겨도 동작이 같다.

"지연 조인은 여전히 offset 100000인데 왜 빨라지나요? 한계는요?"

사슬로 — before는 세컨더리 인덱스 엔트리마다 PK로 클러스터드 인덱스를 재탐색해 행 전체를 조립(북마크 룩업, 랜덤 I/O)한 뒤 버린다 × 100,000. after의 서브쿼리는 SELECT id라 필요한 값이 전부 인덱스 리프에 있어(커버링) 북마크 룩업 없이 인덱스 리프만 순차로 세며 걷고, 살아남은 PK 20개에 대해서만 본 테이블을 읽는다. 랜덤 I/O 100,020회 → 20회.

한계는 인덱스 스캔 자체가 여전히 O(offset)이라는 것 — 엔트리가 행보다 작아 페이지 수가 적을 뿐이라 offset이 수십만·수백만으로 가면 다시 느려진다. 그래서 "페이지 번호 UI를 유지하면서 상한 안쪽을 빠르게" 또는 "커서로 가는 동안의 다리"로 쓴다.

"무한 스크롤 중에 새 글이 올라오면 offset과 커서는 어떻게 다르게 동작하나요?" 가산점

offset은 "앞에서 N번째"를 매번 다시 세므로, 1페이지를 본 뒤 새 글이 하나 들어오면 2페이지 LIMIT 20, 20의 창이 한 칸 밀려 1페이지 마지막 글이 2페이지 첫머리에 다시 나온다. 삭제가 일어나면 반대로 한 건이 건너뛰어진다. 커서는 "이 값 다음"을 조회하므로 삽입·삭제와 무관하게 이어진다. 즉 커서는 성능만이 아니라 사용자가 보는 결과의 정합성 문제이기도 하다. 단, 커서도 정렬 키가 갱신되는 컬럼(updated_at)이면 행이 위치를 옮겨 같은 문제가 재발한다 — 커서의 정렬 키는 불변이어야 한다.

"Page를 Slice로 바꾸면 깊은 페이지 문제가 해결되나요?" 추가

아니다. Slice는 COUNT 쿼리만 없앤다. PageRequest.of(5000, 20)을 그대로 넘기면 여전히 limit 21 offset 100000이 나간다(다음 페이지 유무를 알려고 size+1건을 읽을 뿐). no-offset은 반환 타입이 아니라 WHERE (created_at, id) < 커서 조건에서 온다 — Slice는 그 결과를 담는 그릇이고, page는 항상 0이다.

"느린 이유를 EXPLAIN으로 어떻게 증명하나요? 커서로 바꾸면 무엇이 달라지나요?" 추가

offset 쿼리는 rows가 offset + limit 규모로 잡힌다(20이 아니라 10만 단위). 세컨더리 인덱스를 탔으면 인덱스 스캔 뒤 북마크 룩업이, 못 탔으면 Extra에 Using filesort가 붙는다. 커서 조건을 붙이면 WHERE가 인덱스 범위 조건이 되어 type=range에 rows가 limit 규모로 떨어진다 — "시작점 탐색이 O(offset)에서 트리 높이로 바뀌었다"를 숫자로 보여주는 것.

"배치의 전수 순회가 페이지 수의 제곱에 비례하는 이유는? 처방은?" 추가

매 페이지가 자기 offset만큼 읽고 버리므로 P페이지까지의 총 읽기량은 1 + 2 + … + P에 비례, 즉 P²/2. 처방은 키셋 루프 — 마지막 id를 들고 WHERE id > :lastId ORDER BY id LIMIT 1000을 반복하면 매 페이지가 상수 비용이라 총량이 P에 선형. Spring Batch에서는 JpaPagingItemReader(offset, setFirstResult) 대신 JdbcPagingItemReader(sortKeys 기준 키셋)를 고르는 것이 이 처방의 적용이다.

"offset 상한은 왜 컨트롤러가 아니라 인터셉터에 두나요? HTTP를 안 거치는 호출은요?" 추가

컨트롤러마다 두면 다음 사람이 새 목록 API를 만들 때 빠뜨린다 — 사람의 기억에 의존하지 않는 위치, 즉 모든 목록 요청이 지나가는 한 곳(인터셉터, /api/**)에 둔다. HTTP를 거치지 않는 배치·이벤트 핸들러는 PageRequest.of(5000, 20)을 직접 만들 수 있으므로 서비스 계층에 BoundedPageRequest 팩토리로 같은 선을 하나 더 긋는다. 그 뒤로 DB 타임아웃(2차)과 슬로 쿼리 알람(3차)이 받친다. 그리고 거절 응답에는 반드시 커서 API라는 대체 경로를 안내한다.

"커서 값을 왜 Base64 불투명 토큰으로 주나요? created_at과 id를 그냥 파라미터로 받으면 안 되나요?" 추가

값을 따로 노출하면 클라이언트가 그 값을 조작해 호출하거나 의미에 의존하기 시작하고, 나중에 정렬 키 구성을 바꿀 수 없게 된다. 두 값을 하나로 직렬화해 불투명 토큰으로 주면 계약이 "이 문자열을 다음 요청에 그대로 돌려달라"로 단순해지고, 서버는 커서의 내부 구성을 자유롭게 바꿀 수 있다. Base64는 암호화가 아니라 직렬화·URL 안전성을 위한 것이다.

한 줄 요약 OFFSET은 건너뛰기가 아니라 읽고 버리기다 — B+Tree에 "N번째" 좌표가 없어 서버 계층이 100,020건을 세며 버리고, 세컨더리 인덱스 정렬이면 버릴 행에도 북마크 룩업(랜덤 I/O)을 100,020번 지불해 비용이 페이지 번호에 선형이다. 해결책은 네 개를 세트로 — 커서(키셋)로 offset을 없애거나, 지연 조인으로 버릴 행의 룩업을 없애거나, API 레벨 상한으로 깊은 페이지를 거절하거나, 검색 엔진에 위임한다. 커서를 고를 때는 임의 페이지 점프 · total count · 정렬 유연성 · API 호환을 내주는 거래임을 같은 호흡에 말한다.
