축 ① 종류

문법 나열이 아니라 "잘못 고르면 어떤 버그가 나는가"를 아는지. LEFT를 써야 할 곳에 INNER를 쓰면 데이터가 조용히 누락된다 — 리뷰에서 잡아야 하는 부류.

축 ② 실행 방식

"조인이 왜 느린가"를 실행 계획에서 읽는 밑천이 있는지. 이름을 몰라도 "자바로 짠다면 이렇게…"로 원리에서 출발하면 절반, 이름까지 붙이면 완성.

이번 면접에서 벌어진 일 — 그리고 이 페이지가 고치려는 것

  1. 1

    종류 — 정답 (기본 수준)

    "INNER는 양쪽 다 있는 것만, LEFT는 한쪽 전부 기준." 다만 "매칭 실패 쪽은 NULL로 채워진다"가 빠졌다 — 이게 3절 버그의 토대라 반드시 붙인다.
  2. 2

    실행 방식 — "다 모른다"로 절반 포기

    그런데 "자바로 조인한다면?"으로 바꾸자 이중 루프(NL)와 Map(Hash)을 자력 도출했고, "메모리를 대가로 빨라진다"까지 즉답. 즉 모르는 게 아니라 이미 아는 것의 DB 이름을 몰랐던 것이다.
  3. 3

    빌드 사이드 — "메모리 한계 내에서 큰 쪽" 오답

    정답은 항상 작은 쪽. 프로브 비용은 방향과 무관하게 같고, 다른 건 해시 테이블의 메모리 점유(+스필 위험)뿐 — "비용이 어디서 나는가"를 끝까지 추적하면 답이 하나로 수렴한다. 2-2절에서 다시 고정한다.
이 페이지의 목표 3
  1. 실행 방식 3종에 자바 코드 이름표를 붙여 다시는 "다 모른다"가 안 나오게 한다 (2절, 4절 스크립트).
  2. "해시는 항상 작은 쪽을 build"를 논증째로 외운다 (2-2절 강조 카드).
  3. LEFT/INNER 오용의 "조용한 행 누락"을 before/after로 눈에 익혀 리뷰에서 잡게 한다 (3절).

1JOIN 종류 — 질문은 하나, "매칭 실패한 행을 어떻게 할 것인가"

다섯 종류를 따로 외울 필요가 없다. 조인 조건에 매칭되지 않은 행을 버리나, NULL로 채워 남기나 — 이 한 질문의 답이 종류를 가른다.

CROSS JOIN은 조건 자체가 없어 벤 다이어그램이 아니다 — 왼쪽 × 오른쪽 모든 조합(카테시안 곱). 세 번째 그림은 3절의 예외 패턴(안티조인) 예고.
종류매칭 실패한 행은결과
INNER JOIN양쪽 모두 버린다양쪽에 다 있는 행만
LEFT JOIN왼쪽은 남기고, 오른쪽 컬럼을 NULL로 채운다왼쪽 전부 + 매칭된 오른쪽
RIGHT JOIN오른쪽은 남기고, 왼쪽 컬럼을 NULL로 채운다LEFT의 거울상

비유로 고정 — 참석자 명단 × 식사 신청 명단

참석자 명단(왼쪽)과 식사 신청 명단(오른쪽)을 합칠 때, INNER는 "식사 신청한 참석자만" 남기는 것이고 LEFT는 "참석자 전원을 남기되, 신청 안 한 사람은 메뉴 칸을 빈칸(NULL)으로" 두는 것이다. "참석자 전원 명단 뽑아줘"에 INNER를 쓰면 식사 신청 안 한 사람이 명단에서 사라진다 — 그런데 아무도 에러를 못 본다.

암기 카드LEFT JOIN을 "안다"고 말하려면 두 문장
  1. 왼쪽은 전부 나온다 — 여기서 멈추면 절반.
  2. 매칭 안 된 행의 오른쪽 컬럼은 NULL로 채워져 나온다 — 이 문장이 3절 버그(WHERE에서 NULL이 걸러지는 함정)와 안티조인 패턴의 토대다.
연상: LEFT = "왼쪽은 살리고, 빈자리는 NULL". INNER = "빈자리 있는 행은 통째로 버림".

교과서의 "Sort-merge 조인"이 PostgreSQL 계획에서는 Merge Join으로 찍힌다. 정렬이 필요하면 그 아래에 별도 Sort 노드가 붙고, 인덱스 순서로 읽어 이미 정렬돼 있으면 Sort 없이 Index Scan이 바로 붙는다 — 즉 "정렬이 공짜인가"를 계획 모양으로 눈으로 확인할 수 있다.

2-1. Nested Loop — 이중 루프, 단 안쪽은 인덱스로 찾아간다

// ❌ 소박한 NL — 안쪽을 매번 통순회: 10만 × 1만 = 10억 번 비교
for (Order order : orders) {              // 바깥 = 드라이빙 테이블 (10만 번)
    for (User user : users) {             // 안쪽 = 전체 순회 (매번 1만 번)
        if (order.getUserId().equals(user.getId())) {
            // 매칭
        }
    }
}
// ✅ DB의 실제 NL — 안쪽 루프가 "인덱스 탐색 한 번"으로 대체된다

비용 = 바깥 루프 횟수 × 안쪽 탐색 비용. 바깥 횟수는 드라이빙 테이블 행 수가, 안쪽 비용은 조인 키 인덱스 유무가 정한다 — 튜닝의 두 손잡이가 그대로 보인다.
암기 카드NL 튜닝의 기본 문법 2 — 계획의 두 항을 그대로 확인한다
"드라이빙(바깥) 테이블은 작게, 안쪽 테이블의 조인 키에는 인덱스."
  1. 드라이빙 작게 — 바깥 루프 횟수 = 드라이빙 행 수(계획의 안쪽 loops=N). WHERE 조건으로 먼저 크게 줄어드는 쪽이 바깥이어야 한다. 플래너가 조인 순서를 정하는 기준.
  2. 안쪽 인덱스 — 없으면 PostgreSQL은 대개 NL을 포기하고 Hash Join으로 갈아탄다. 그래서 PG에서 "인덱스 없는 조인"은 10억 번 루프 참사보다 예상 못 한 대량 해시 조인 + 디스크 스필로 나타난다.
가산점(PG 특유) 2: ① 힙 페치가 따라붙는다 — PG는 힙 기반이라 모든 인덱스가 "인덱스 → TID → 힙"이다. 반복 횟수가 커지면 랜덤 I/O가 비싸져 플래너가 순차 읽기 기반 Hash Join을 고르고, 커버링 인덱스로 Index Only Scan이 되면 힙 접근이 사라져 NL이 다시 유리해진다. ② Memoize 노드(PG 14+) — 바깥 행에 같은 조인 키가 반복되면 안쪽 탐색 결과를 캐시한다(자바로 치면 computeIfAbsent). 계획에 Memoize (Hits: 1832 Misses: 210 …)로 찍히고 Hits가 크면 중복 키만큼 공짜로 빨라진 상태다.

SELECT o.id, o.amount, u.name FROM orders o
JOIN users u ON u.id = o.user_id WHERE o.created_at >= '2026-08-01';

Nested Loop  (cost=0.71..1042.19 rows=210) (actual rows=203 loops=1)
  ->  Index Scan using idx_orders_created_at on orders o     ← outer(드라이빙)
        Index Cond: (created_at >= '2026-08-01')
        (actual rows=203 loops=1)
  ->  Index Scan using users_pkey on users u                 ← inner
        Index Cond: (id = o.user_id)                        ← 인덱스 탐색 성립
        (actual rows=1 loops=203)                           ← 바깥 행 수만큼 반복
  1. 조인 노드의 첫 번째(위) 자식이 outer = 드라이빙, 두 번째가 inner다.
  2. inner의 loops=203 = 바깥 행 수만큼 반복 — NL 비용의 첫 번째 항이 여기 그대로 찍힌다.
  3. inner에 Index Cond로 조인 키가 걸려 있으면 인덱스 탐색이 성립한 것 — 여기가 Seq Scan이면 위 ❌ 코드가 실제로 벌어지고 있다는 신호다.
⚠️ 함정: inner의 actual rows는 loops당 평균이다. 실제 총 행 수 = rows × loops(위 예시 1 × 203 = 203). 이걸 모르면 "안쪽이 1행밖에 안 읽었는데 왜 느리지?"에서 멈춘다.

2-2. Hash Join — 작은 쪽으로 build, 큰 쪽으로 probe

// 1단계 build — "작은 쪽"(users 1만)으로 해시 테이블을 만든다
Map<Long, User> built = new HashMap<>();
for (User user : users) {                 // ← 작은 쪽! 메모리에 올라가는 쪽
    built.put(user.getId(), user);
}

// 2단계 probe — "큰 쪽"(orders 10만)을 한 번 순회하며 탐색
for (Order order : orders) {              // ← 큰 쪽. 순회만 하고 메모리에 안 올림
    User user = built.get(order.getUserId());   // O(1) 탐색
    if (user != null) {
        // 매칭
    }
}
양쪽을 각 한 번씩만 훑고 끝난다. 인덱스가 필요 없어 인덱스 없는 대량 조인(배치·통계·임시 테이블)에서 강하고, 대가는 메모리(해시 테이블만큼), 제약은 등호 조인 전용(해시는 "같은 값 찾기"만 할 수 있지 > 같은 범위 비교는 못 한다).
오답 대비 — 면접에서 틀린 지점빌드 사이드는 어느 쪽?
항상 작은 쪽을 해시로 — 메모리에 올릴 쪽이 작아야 하니까.

틀린 답 "메모리 한계를 확인하고, 한계 내에서 가능한 큰 쪽을 해시로." → 큰 쪽을 build해서 얻는 이득은 0이다. 논증 세 단계:

  1. 프로브 비용은 방향과 무관 — 어느 쪽을 build하든 "한쪽 전부 put + 다른 쪽 전부 get". 10만을 넣고 1만으로 찾으나, 1만을 넣고 10만으로 찾으나 순회 총량은 11만으로 같다.
  2. 다른 것은 해시 테이블 크기뿐 — 10만 건짜리 Map과 1만 건짜리 Map. 결과는 같은데 메모리 점유만 10배. 큰 쪽 build는 얻는 것 없이 메모리만 더 쓴다.
  3. 스필 위험 — 해시 테이블이 작업 메모리 한도(work_mem × hash_mem_multiplier)를 넘치면 DB는 양쪽을 파티션으로 쪼개 디스크 임시 파일에 쓰고 파티션끼리 조인(디스크 스필)해야 해서 급격히 느려진다. 작은 쪽 build는 스필 위험 자체를 줄인다.
한 문장: "메모리 한계 내에서 큰 쪽"이 아니라 "이득이 전무하니 무조건 작은 쪽". 자바에서도 같은 이유로 작은 리스트를 Map으로 만드는 게 정석이다. 이 오답의 뿌리는 "비용이 어디서 나는가"를 끝까지 추적하지 않는 습관 — 순회 총량을 실제로 더해 보면 답이 하나로 수렴한다.
용어"디스크 스필(spill)"이란 — 메모리에서 하려던 작업이 넘쳐 디스크로 흐르는 것
  1. 빌드 사이드로 해시 테이블을 메모리에 만들려 한다 — 한도는 work_mem × hash_mem_multiplier.
  2. 안 들어가면 포기하지 않고 양쪽을 조인 키 해시값으로 N개 파티션(batch)으로 쪼개 임시 파일에 쓴다.
  3. 그 뒤 "batch 1의 빌드 쪽 + batch 1의 프로브 쪽"만 메모리에 올려 조인 → batch 2 → … 각 batch는 작아서 들어가므로 결과는 정확히 같다.
  4. 대가는 디스크 쓰기 + 읽기가 한 번씩 추가된다는 것 — 메모리에서 끝났으면 없었을 I/O라 수 배~수십 배 느려진다.
자바로 치면: HashMap이 힙에 안 들어가서 키 해시값으로 100개 파일로 나눠 쓰고, 파일 단위로 나눠 조인하는 것. 정렬도 같은 일이 벌어지고 이름만 다르다(Sort Method: external merge = 외부 병합 정렬). 계획에서 보는 법: Batches: 1이면 스필 없음, Batches: 8이면 8조각으로 쪼개 디스크를 썼다는 뜻. BUFFERS를 켜면 temp read/written으로도 보인다.
용어work_mem이란 — 임시 작업 하나가 디스크로 내려가기 전까지 쓸 수 있는 메모리 상한

PostgreSQL 설정값(기본 4MB). 여기서 "작업"은 실행 계획의 노드다 — Sort, 해시 조인의 Hash, HashAggregate, Materialize. 이 한도를 넘으면 위의 스필이 일어난다.

  1. 쿼리당이 아니라 노드당 — 한 쿼리에 정렬 3개 + 해시 조인 2개면 최대 5 × work_mem, 병렬 워커 수만큼 또 곱해진다. 전역으로 크게 올리면 max_connections × 노드 수 × work_mem이 되어 OOM 위험 — 전역은 보수적으로(4~16MB), 무거운 배치·리포트만 세션에서 올린다.
  2. shared_buffers와 다르다 — shared_buffers는 테이블·인덱스 페이지를 담는 공유 캐시, work_mem은 세션이 혼자 쓰는 작업 공간. (VACUUM·인덱스 생성용은 또 별도로 maintenance_work_mem.)
  3. 해시에는 배수가 붙는다 — hash_mem_multiplier(PG 15부터 기본 2.0)가 곱해져 해시 테이블의 실효 한도는 work_mem × 2. 정렬에는 이 배수가 붙지 않는다.
설정 방법: SET work_mem = '64MB'(현재 세션) / SET LOCAL(현재 트랜잭션만 — 진단할 때 안전) / postgresql.conf(전역) / ALTER ROLE … SET(배치 계정만 크게).
PostgreSQL 계획으로 보는 Hash Join — Hash 노드가 붙은 쪽이 빌드 사이드
Hash Join  (cost=… rows=99873) (actual rows=99873 loops=1)
  Hash Cond: (o.user_id = u.id)
  ->  Seq Scan on orders o    (actual rows=100000 loops=1)   ← probe (큰 쪽)
  ->  Hash  (actual rows=10000 loops=1)                      ← build (작은 쪽)
        Buckets: 16384  Batches: 1  Memory Usage: 1088kB     ← 1이면 메모리 안에서 끝
        ->  Seq Scan on users u  (actual rows=10000 loops=1)

반드시 볼 줄은 Batches — Batches: 1이면 해시 테이블이 메모리 안에서 끝났다는 뜻이고, Batches: 8처럼 1보다 크면 디스크로 스필했다는 뜻이다(양쪽을 파티션으로 쪼개 임시 파일에 쓰고 파티션끼리 조인 → 급격히 느려진다). 처방은 ① 빌드 사이드를 더 작게(선행 필터, 필요한 컬럼만), ② 해시용 작업 메모리를 늘리기.

  • PG의 작업 메모리는 work_mem이며 쿼리당이 아니라 노드당이다 — 해시·정렬 노드가 여러 개면 그만큼 곱해져 쓰인다.
  • 해시 계열은 여기에 hash_mem_multiplier가 곱해진다(PG 13 도입, PG 15부터 기본 2.0 → 실효 한도 = work_mem × 2).
  • 확인법: SET LOCAL work_mem = '64MB' 후 재실행 → Batches가 1로 떨어지는지 본다. 전역으로 크게 올리면 동시 세션 수 × 노드 수만큼 먹으니 조심.
  • 병렬 계획에서는 Parallel Hash / Parallel Hash Join(PG 11+)으로 찍힌다 — 워커들이 공유 해시 테이블 하나를 함께 만든다.

PG는 이 원칙을 outer join에서도 관철한다 — a LEFT JOIN b인데 a가 작으면 a를 해시로 만들고 b로 probe하는 Hash Right Join으로 뒤집어 실행한다(의미는 그대로, 빌드 사이드만 바꾼 것). 계획에서 Right를 보고 "내가 RIGHT JOIN을 안 썼는데?" 하고 당황하지 않으면 된다.

2-3. Merge Join (교과서의 Sort-merge) — 양쪽 정렬 후 지퍼처럼 병합

// 1단계: 양쪽을 조인 키로 정렬 — 비용의 대부분이 여기
orders.sort(comparing(Order::getUserId));
users.sort(comparing(User::getId));

// 2단계: 두 포인터로 지퍼 병합 — 각자 앞으로만 전진, 양쪽 각 한 번
int i = 0, j = 0;
while (i < orders.size() && j < users.size()) {
    long orderKey = orders.get(i).getUserId();
    long userKey  = users.get(j).getId();
    if (orderKey == userKey)      { /* 매칭 */ i++; }
    else if (orderKey < userKey)  i++;      // 작은 쪽 포인터만 전진
    else                          j++;
}
병합 단계는 양쪽을 한 번씩만 훑는다(합병 정렬의 merge와 같은 그림). 비용의 대부분은 정렬이므로 입력이 이미 조인 키 순으로 정렬돼 있으면(조인 키 인덱스 순으로 읽는 경우 등) 정렬이 공짜가 되어 강해진다. 해시와 달리 범위 조건 조인도 소화한다.
PostgreSQL 계획으로 보는 Merge Join — Sort 노드의 유무가 곧 비용
✅ 정렬이 공짜 — 인덱스 순서로 읽는다
Merge Join
  Merge Cond: (o.user_id = u.id)
  ->  Index Scan using idx_orders_user_id on orders o
  ->  Index Scan using users_pkey on users u
❌ 정렬 비용을 낸다 — 게다가 디스크로
Merge Join
  Merge Cond: (o.user_id = u.id)
  ->  Sort   Sort Key: o.user_id
        Sort Method: external merge  Disk: 21544kB
        ->  Seq Scan on orders o
  ->  Index Scan using users_pkey on users u

Sort Method: quicksort Memory: 1234kB면 메모리에서 끝난 정렬이고, external merge Disk: …면 work_mem을 넘겨 디스크로 내려간 정렬이다 — Hash Join의 Batches > 1과 같은 종류의 경고등이다. 해시와 달리 범위 조건 조인(부등호, FULL OUTER)도 소화하고, ORDER BY가 조인 키와 같으면 결과 정렬까지 덤으로 얻는다.

2-5. PostgreSQL EXPLAIN에서 "느린 조인"을 잡는 3단계

같은 쿼리 — SELECT … FROM orders o JOIN users u ON u.id = o.user_id WHERE o.created_at >= ? — 를 두 상태로 본다. 방식 이름을 탓하기 전에 추정과 실제의 간격을 먼저 본다.

✅ 건강한 NL — 추정과 실제가 붙어 있다
Nested Loop  (rows=210) (actual rows=203 loops=1)
  ->  Index Scan using idx_orders_created_at on orders o
        (rows=210) (actual rows=203 loops=1)
  ->  Index Scan using users_pkey on users u
        Index Cond: (id = o.user_id)
        (actual rows=1 loops=203)

드라이빙 o가 조건으로 203건까지 줄었고, 안쪽 u는 PK 인덱스로 행당 1건 탐색. 비용 ≈ 203 × 1. 추정 210 vs 실제 203 — 통계가 맞다.

❌ 추정이 틀려 NL이 폭주 — 진짜 원인은 통계
Nested Loop  (rows=210) (actual rows=1982340 loops=1)
  ->  Seq Scan on orders o
        (rows=210) (actual rows=980000 loops=1)
  ->  Index Scan using users_pkey on users u
        (actual rows=2 loops=980000)  ← 98만 번 반복

추정 210, 실제 98만 — 자릿수가 다르면 방식 선택 자체가 그 오류의 결과다. 처방은 enable_nestloop=off가 아니라 ANALYZE·확장 통계. 추정이 맞으면 플래너가 스스로 Hash Join으로 갈아탄다.

암기 카드"조인이 느리다" — 계획에서 볼 3가지, 이 순서로
  1. 어떤 방식인가 — Nested Loop / Hash Join / Merge Join. 이름은 확인만 하고 탓하지 않는다.
  2. 추정 vs 실제 — rows= vs actual rows=. 자릿수가 다르면 원인은 통계(→ ANALYZE, 상관 컬럼이면 CREATE STATISTICS).
  3. 메모리 경고등 — Hash의 Batches > 1, Sort의 Sort Method: external merge Disk: → 스필. work_mem 또는 빌드 사이드 크기를 손댄다.
방식별 한 줄 더: NL이면 inner의 loops와 Index Cond 유무 / Hash면 Hash 노드가 작은 쪽인지 / Merge면 Sort가 붙었는지. EXPLAIN (ANALYZE, BUFFERS)로 shared read가 큰 노드를 찾으면 실제 I/O 지점까지 잡힌다.

3실무 사례 — "조용한 행 누락": 에러 없이 데이터가 사라지는 두 함정

둘 다 컴파일 에러도, 런타임 예외도 없다. 쿼리는 멀쩡히 돌고 결과만 슬그머니 줄어든다. 그래서 테스트보다 리뷰에서 잡아야 하는 부류다.

3-1. LEFT 자리에 INNER — 쿠폰 안 쓴 주문이 목록에서 사라진다

요구사항: "주문 목록을 보여주되, 쿠폰을 썼다면 쿠폰 코드도 같이."

BEFORE INNER JOIN — 쿼리는 멀쩡히 돌지만
SELECT o.id, o.amount, c.coupon_code
FROM orders o
JOIN coupon_use c ON c.order_id = o.id;      -- JOIN = INNER JOIN

-- 쿠폰을 안 쓴 주문은 coupon_use에 행이 없다
-- → 매칭 실패 → INNER는 그 행을 버린다
-- → "쿠폰 미사용 주문"이 주문 목록에서 통째로 사라진다.
-- 에러도 경고도 없다. 사용자 항의("내 주문 어디 갔죠")로 발견된다.
1절 미니 데이터 기준 — 주문 2번(쿠폰 미사용)이 결과에서 행 자체로 사라진다.
AFTER LEFT JOIN — 주문은 전부, 쿠폰 없으면 NULL
SELECT o.id, o.amount, c.coupon_code
FROM orders o
LEFT JOIN coupon_use c ON c.order_id = o.id;

-- 쿠폰 미사용 주문도 나온다. coupon_code 칸만 NULL.
주문 2번이 coupon_code = NULL로 살아남는다. 애플리케이션은 NULL이면 "쿠폰 없음"으로 표시하면 된다.
리뷰 체크 습관조인문을 볼 때마다 던지는 질문 1
"이 조인의 오른쪽은, 왼쪽 모든 행에 반드시 존재하는가?"
  • 존재가 보장되지 않는(선택적인) 관계 — 쿠폰, 리뷰, 프로필 사진, 배송 추적 — 에 INNER가 보이면 행 누락을 의심한다.
  • 반대로 반드시 존재하는 관계(주문 → 주문자)면 INNER가 맞고, 습관적 LEFT는 의도를 흐린다.
PG 한 줄: 습관적 LEFT가 항상 공짜는 아니다 — PG 플래너는 "오른쪽 컬럼을 아무도 안 쓰고, 조인 키가 유니크해서 행이 늘지 않는" LEFT JOIN은 아예 제거하지만(join removal — 계획에서 그 테이블이 사라진다), 조건이 안 맞으면 그대로 비용이다.

3-2. 가산점 LEFT JOIN 뒤 WHERE에 오른쪽 조건 — LEFT가 조용히 INNER로 변한다

한 단계 더 교묘한 함정. LEFT JOIN을 제대로 썼는데도 INNER처럼 동작한다.

BEFORE LEFT JOIN인데 결과는 INNER JOIN과 동일
SELECT o.id, o.amount, c.coupon_code
FROM orders o
LEFT JOIN coupon_use c ON c.order_id = o.id
WHERE c.used_at >= '2026-08-01';           -- 오른쪽 테이블 조건이 WHERE에

-- 쿠폰 미사용 주문은 c.used_at이 NULL로 채워지는데,
-- NULL >= '2026-08-01' 은 참이 아니다 (NULL 비교 = UNKNOWN)
-- → WHERE에서 걸러짐 → 미사용 주문 전멸 = 사실상 INNER JOIN.
LEFT가 살려둔 행은 오른쪽 컬럼이 전부 NULL이다. WHERE의 c.컬럼 = 값, c.컬럼 >= 값 비교에서 NULL은 참이 될 수 없어 그 행들이 모두 죽는다.
AFTER 오른쪽 테이블 조건은 ON으로 올린다
SELECT o.id, o.amount, c.coupon_code
FROM orders o
LEFT JOIN coupon_use c ON c.order_id = o.id
                      AND c.used_at >= '2026-08-01';   -- 매칭 조건의 일부로

-- 의미: "8월 이후 사용된 쿠폰만 조인 대상으로 삼되, 주문은 전부 남긴다."
-- 조건에 안 맞으면 매칭 실패로 처리 → NULL 채움 → 주문은 살아남는다.
8월 이전에 쓴 쿠폰의 주문도 주문 자체는 남고 쿠폰 칸만 NULL이 된다 — 요구사항("주문은 전부")이 지켜진다.
PostgreSQL이면 EXPLAIN으로 30초에 확진한다

플래너는 "오른쪽에 strict 조건이 붙었으니 이 outer join은 inner join과 같다"고 판단해 조인을 실제로 축약한다(outer join reduction). 그래서 계획에 Hash Left Join이 아니라 그냥 Hash Join이 찍힌다.

-- ❌ before의 계획: 내가 쓴 건 LEFT인데 Left가 사라졌다
Hash Join                        ← Left가 없다 = INNER로 축약됨
  Hash Cond: (c.order_id = o.id)

-- ✅ after의 계획
Hash Left Join                   ← LEFT가 살아 있다
  Hash Cond: (c.order_id = o.id)

리뷰·디버깅 체크로 굳히면 — "LEFT JOIN을 썼는데 계획에 Left가 없다 → 조건 배치가 잘못됐다." 반대로 의도적인 예외도 계획에 드러난다: WHERE c.order_id IS NULL(안티조인)은 축약이 아니라 Hash Anti Join으로 찍히고, 같은 의도를 NOT EXISTS로 써도 동일한 계획이 나온다 — 우연히 되는 트릭이 아니라 플래너가 알아보는 정식 패턴이라는 뜻이다.

암기 카드ON vs WHERE — 한 문장 + 원칙 2 + 예외 1
ON은 "무엇을 매칭할지"(실패해도 LEFT면 NULL로 살린다), WHERE는 "완성된 결과에서 무엇을 남길지"(NULL은 여기서 죽는다).
  1. LEFT JOIN에서 오른쪽 테이블 필터는 ON에.
  2. 왼쪽 테이블 필터는 WHERE에 (왼쪽 행은 NULL 채움과 무관하니 안전).
예외: WHERE c.order_id IS NULL만은 NULL 채움을 역이용해 "쿠폰 안 쓴 주문만" 찾는 정석 패턴(안티조인). 1절 벤 다이어그램의 세 번째 그림이 이것이다.
안티조인 — 예외 패턴을 코드로
-- "쿠폰을 한 번도 안 쓴 주문만" — NULL 채움을 의도적으로 이용
SELECT o.id, o.amount
FROM orders o
LEFT JOIN coupon_use c ON c.order_id = o.id
WHERE c.order_id IS NULL;                -- 매칭 실패 행만 골라낸다
암기 카드조용한 행 누락 함정 2
  1. LEFT 자리에 INNER — 선택적 관계(쿠폰·리뷰·프로필 사진)에 INNER → 매칭 실패 행이 통째로 사라진다.
  2. LEFT 뒤 WHERE에 오른쪽 조건 — NULL 비교는 참이 아니라서 LEFT가 조용히 INNER로 변한다. 처방: 조건을 ON으로.

5꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 오답 재검은 이번 면접에서 틀린 지점, 시니어 변별은 트레이드오프를 한 호흡에 말해야 하는 문항, 추가는 md에 없던 확장 문항.

DB는 해시 테이블을 어느 쪽으로 만드나요? 메모리가 허용하면 큰 쪽으로 만드는 게 이득 아닌가요?오답 재검

항상 작은 쪽이다. 큰 쪽을 build해서 얻는 이득은 없다. 어느 방향이든 한쪽 전체를 넣고 다른 쪽 전체를 순회하므로 프로브 비용(순회 총량)은 동일하다 — 10만을 넣고 1만으로 찾으나 그 반대나 합계는 11만으로 같다. 달라지는 것은 해시 테이블의 크기뿐이고, 큰 쪽을 build하면 같은 결과에 메모리만 몇 배로 쓴다.

게다가 해시 테이블이 작업 메모리를 넘치면 디스크 스필로 급격히 느려지므로, 작은 쪽 build는 스필 위험을 줄이는 선택이기도 하다. "메모리 한계 내에서 큰 쪽"이 아니라 "이득이 전무하니 무조건 작은 쪽" — 비용이 어디서 나는지 끝까지 추적하면 답이 하나로 수렴한다.

PostgreSQL에서 조인 쿼리가 느립니다. 실행 계획에서 먼저 볼 세 가지는?
  1. 어떤 방식을 골랐나 — Nested Loop / Hash Join / Merge Join. 방식 자체를 탓하기 전에 확인만 한다.
  2. 추정과 실제가 얼마나 벌어졌나 — rows=210 vs actual rows=200000처럼 자릿수가 다르면 잘못된 선택의 원인은 통계다(→ ANALYZE, 상관 컬럼이면 CREATE STATISTICS).
  3. 메모리 경고등 — Hash Join의 Batches > 1, Sort Method: external merge Disk:. 스필이면 work_mem이나 빌드 사이드 크기를 손댄다.

방식별로 덧붙이면 — NL이면 inner의 loops와 Index Cond 유무(안쪽이 Seq Scan이면 인덱스부터), Hash면 Hash 노드가 작은 쪽인지, Merge면 Sort가 붙었는지(붙었으면 인덱스로 없앨 수 있는지). EXPLAIN (ANALYZE, BUFFERS)로 shared read가 큰 노드를 찾으면 실제 I/O 지점까지 잡힌다.

MySQL이면 답이 달라진다 — 기본이 NL이므로 "바깥 루프 횟수 × 안쪽 탐색 비용"의 두 항(드라이빙이 작은 쪽인가 · 안쪽 조인 키 인덱스가 있는가)을 type·key로 확인하는 것이 실체다.

LEFT JOIN을 걸었는데 결과가 INNER JOIN과 똑같습니다. 코드는 안 바꿨다는데 뭘 의심하나요?

WHERE 절에 오른쪽 테이블 조건이 있는지부터 본다. LEFT JOIN이 살려둔 매칭 실패 행은 오른쪽 컬럼이 전부 NULL인데, WHERE의 c.컬럼 = 값이나 c.컬럼 >= 값 비교에서 NULL은 참이 될 수 없어 전부 걸러진다 — LEFT가 조용히 INNER로 변하는 전형적 패턴이다.

처방은 오른쪽 테이블 조건을 ON으로 올리는 것. PostgreSQL이면 EXPLAIN으로 30초에 확진한다 — 계획에 Hash Left Join이 아니라 Hash Join이 찍혀 있으면 플래너가 이미 inner join으로 축약했다는 증거다. 단 c.컬럼 IS NULL만은 예외로, 매칭 실패 행만 골라내는 의도적 안티조인 패턴이고 계획에도 Anti Join으로 찍힌다.

세 방식은 각각 언제 이기고, 플래너는 무엇을 보고 고르나요?시니어 변별

플래너의 입력은 네 가지 — 양쪽의 (조건 적용 후) 예상 행 수, 조인 키 인덱스·정렬 여부, 조인 조건이 등호인가, work_mem.

  1. 드라이빙이 작고 안쪽 조인 키에 인덱스가 있으면 Nested Loop: 소량 조회가 대부분인 OLTP의 기본값이고, 필요한 행만 인덱스로 집어가므로 첫 행이 빨리 나온다.
  2. 양쪽 다 크고 인덱스가 없는 등호 조인이면 Hash Join: 인덱스 없이 양쪽 한 번씩 순회로 끝내는 대신 메모리를 낸다. 등호가 아니면 탈락.
  3. 양쪽이 이미 조인 키로 정렬돼 있거나(인덱스 순 읽기) 어차피 정렬이 필요하면 Merge Join: 정렬 비용이 공짜가 되는 판. 범위 조건·FULL OUTER도 여기.

핵심은 이 판단이 전부 "예상 행 수"에 얹혀 있다는 것 — 통계가 낡거나 컬럼 간 상관을 못 잡으면(WHERE city='서울' AND zipcode='06236' 같은 경우) 추정이 무너지고 방식 선택도 같이 틀어진다. 그래서 "조인 방식이 이상하다"의 1차 처방은 방식 강제가 아니라 ANALYZE · 확장 통계(CREATE STATISTICS) · default_statistics_target 상향이다. enable_nestloop = off 같은 스위치는 가설 검증용이라고 선을 그어 말하면 시니어의 언어가 된다.

PostgreSQL은 FULL OUTER JOIN을 지원하는데, 제약이나 주의점이 있나요?

지원한다 — 단 조인 조건이 merge/hash 가능해야 한다. FULL OUTER는 양쪽의 미매칭을 다 추적해야 해서 Nested Loop로는 구현할 수 없고 Merge Full Join 또는 Hash Full Join으로만 실행된다. 그래서 등호나 merge 가능한 조건이 아니면 실행 자체가 거부된다 — FULL JOIN is only supported with merge-joinable or hash-joinable join conditions 에러가 그것이다.

덧붙일 두 가지: ① MySQL에는 FULL OUTER가 없어 LEFT ∪ RIGHT를 UNION(UNION ALL이 아니라 — 매칭 행 중복 제거가 필요하므로)으로 흉내 내야 하므로, MySQL 경험자와 대화할 때 이 차이를 알고 있으면 좋다. ② 실무에서 FULL OUTER가 필요한 상황 자체가 드물고(대개 두 집합의 대사/검증 작업), 자주 필요하다면 모델링을 의심해 볼 신호다.

해시 조인은 왜 등호(=) 조인만 가능한가요?추가

해시 함수는 "같은 값 → 같은 버킷"만 보장하고, 값의 순서 정보는 버린다. h(41)과 h(42)는 아무 관계 없는 위치에 떨어지므로 "42보다 작은 것" 같은 범위 질문에 해시 테이블은 답할 수 없다 — 결국 전부 뒤져야 하고 그러면 해시를 쓸 이유가 없다.

범위 조건 조인(a.x BETWEEN b.lo AND b.hi, a.ts > b.ts 등)은 순서를 아는 구조 — 정렬(Merge Join)이나 B+Tree 인덱스의 range 탐색(NL) — 이 맡는다. 자바로 치면 HashMap은 get(key)만 있고 TreeMap에만 headMap/tailMap이 있는 것과 같은 이유다.

안쪽 테이블 조인 키에 인덱스가 없으면 PostgreSQL은 어떻게 하나요? 계획에 뭐가 보이나요?추가

대개 NL을 아예 포기하고 Hash Join을 고른다. 바깥 행마다 안쪽을 풀스캔하는 비용을 플래너가 계산해 보면 "양쪽 한 번씩 순회 + 해시 테이블"이 훨씬 싸기 때문이다. 그래서 계획에 Nested Loop 대신 Hash Join이 찍히고, 문제는 느린 루프가 아니라 예상 못 한 대량 해시 + 디스크 스필(Batches > 1)로 나타난다.

그래도 Nested Loop 아래에 Seq Scan(또는 Materialize → Seq Scan)이 보이는 경우가 있는데, 이는 바깥이 아주 작다고 추정된 경우다 — 추정이 맞으면 문제없지만 틀리면(2-5절의 ❌ 계획) 폭주한다. 처방은 안쪽 조인 키 인덱스, 그리고 ANALYZE.

MySQL 대조: MySQL은 이 자리에서 조인 버퍼에 바깥 행을 모아 안쪽을 한 번 훑으며 한꺼번에 비교한다 — 구버전의 Block Nested Loop, 8.0 최근 버전은 같은 자리에 해시 조인. EXPLAIN 신호는 type = ALL + Extra Using join buffer (hash join).

드라이빙 테이블은 옵티마이저가 정하는데, 개발자가 개입할 수 있는 지점은?추가

순서대로 세 층.

  1. 조건과 인덱스로 "작은 쪽"을 실제로 작게 만든다 — 드라이빙 후보의 WHERE 조건 컬럼에 인덱스가 있어야 옵티마이저가 "이쪽이 먼저 줄어든다"를 알고 바깥에 둔다. 가장 정석.
  2. 통계를 맞춘다 — 예상 행 수가 틀리면 큰 쪽을 드라이빙으로 고르는 사고가 난다. PG는 ANALYZE(+ 상관 컬럼이면 CREATE STATISTICS, 부족하면 default_statistics_target 상향)로 재수집.
  3. 최후에 개입 — PG에는 MySQL의 STRAIGHT_JOIN 같은 조인 순서 힌트가 기본 제공되지 않는다. 남는 수단은 join_collapse_limit = 1로 FROM 순서를 강제하거나, enable_nestloop 등을 세션에서 끄거나, 확장(pg_hint_plan)을 쓰는 것 — 셋 다 데이터 분포가 바뀌면 발목을 잡으므로 "만료일 있는 부채"로 취급한다. 정상 경로는 ①②다.
INNER JOIN은 테이블 순서를 바꿔도 결과가 같은데, LEFT JOIN도 그런가요?추가

아니다. INNER는 교환 가능(A ⋈ B = B ⋈ A)해서 옵티마이저가 드라이빙을 자유롭게 고르지만, LEFT JOIN은 "왼쪽을 기준으로 살린다"는 방향이 의미의 일부라 A LEFT JOIN B와 B LEFT JOIN A는 다른 결과다(전자는 A 전부, 후자는 B 전부).

이 때문에 옵티마이저도 LEFT JOIN에서는 조인 순서 선택에 제약을 받는다 — 보통 왼쪽 테이블이 드라이빙이 된다. "LEFT JOIN을 많이 쓰면 조인 순서 최적화 여지가 줄어든다"는 말의 근거이고, 반드시 필요한 곳에만 LEFT를 쓰라는 3-1절 리뷰 습관의 성능 쪽 이유이기도 하다.

조인했더니 결과 행이 오히려 늘어나고 합계가 부풀었습니다. 무슨 일인가요?추가

"조용한 누락"의 반대인 "조용한 팽창"이다. 두 원인:

  1. 1:N 관계를 조인한 뒤 집계 — 주문 1건에 주문상품 3건이면 조인 결과는 3행. 여기에 SUM(o.amount)를 걸면 주문 금액이 3배로 잡힌다. 처방은 N쪽을 먼저 서브쿼리로 집계한 뒤 1쪽과 조인하거나, COUNT(DISTINCT o.id)처럼 중복을 의식한 집계.
  2. 조인 조건 누락·불충분 — ON을 빠뜨리거나 복합 키의 일부만 걸면 의도치 않은 CROSS JOIN에 가까워져 M×N으로 폭발한다.

둘 다 에러가 없다는 점에서 3절 함정과 같은 부류 — 리뷰 질문은 "이 조인은 왼쪽 한 행당 오른쪽 몇 행이 붙는가?"다.

MySQL로 물어보면 답이 달라지는 부분은 어디인가요?추가

세 지점이다.

  1. 기본 방식 — MySQL은 전통적으로 NL 계열이 기본이고 해시 조인이 8.0.18에서 뒤늦게 추가됐으며 Merge Join은 아예 없다. 그래서 MySQL 조인 튜닝은 곧 NL 튜닝("드라이빙 작게 + 안쪽 인덱스")에 수렴하는데, PostgreSQL은 셋을 비용으로 고르므로 "플래너가 옳게 고르도록 통계·메모리·인덱스를 갖추는 일"이 된다.
  2. 인덱스 안쪽 비용 — InnoDB는 클러스터드 인덱스라 PK 조인의 안쪽 접근이 곧 데이터 접근이지만, PG는 힙 기반이라 인덱스 탐색 뒤에 힙 페치가 붙는다(커버링 인덱스로 Index Only Scan을 노리는 이유).
  3. FULL OUTER JOIN — PG는 지원, MySQL은 LEFT ∪ RIGHT UNION으로 우회.

이 세 개를 짚어 말하면 "한쪽만 써봤다"가 아니라 "차이를 원리로 이해했다"로 들린다.

한 줄 요약

조인 실행 방식은 이미 아는 코드의 DB 이름이다 — 이중 루프 = Nested Loop(안쪽은 인덱스 탐색, 안쪽 loops와 Index Cond를 본다), Map 빌드+탐색 = Hash Join(빌드는 항상 작은 쪽 — Hash 노드가 붙은 쪽이고 Batches > 1이면 디스크 스필, 등호 전용), 정렬 후 병합 = Merge Join(Sort 노드가 없으면 정렬이 공짜). PostgreSQL은 셋을 모두 비용으로 고르므로 튜닝은 방식 강제가 아니라 통계 · 인덱스 · work_mem을 갖춰 플래너의 선택을 옳게 만드는 일이다. 종류의 핵심은 LEFT JOIN의 매칭 실패 쪽 NULL 채움이며, LEFT 자리에 INNER를 쓰거나 LEFT 뒤 WHERE에 오른쪽 조건을 두면 에러 없이 행이 조용히 사라진다 — PG에서는 계획에 Left가 사라진 것으로 확진할 수 있다.
