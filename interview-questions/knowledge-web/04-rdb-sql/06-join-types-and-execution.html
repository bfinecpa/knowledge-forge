JOIN 종류와 실행 방식
이미 아는 자바 코드에 PostgreSQL 이름표를 붙인다

면접 질문: "JOIN의 종류(INNER, LEFT, ...)와 실행 방식(Nested Loop, Hash, Merge)을 설명해주세요."

핵심 관전 포인트 — 조인 실행 방식 3종은 새로 배울 게 아니라 이미 아는 코드의 DB 이름이다. 이중 for 루프 = Nested Loop(단 DB는 안쪽 루프를 통순회하지 않고 조인 키 인덱스로 탐색) / 한쪽을 Map에 넣고 다른 쪽을 순회 = Hash Join(빌드는 항상 작은 쪽 — 프로브 비용은 방향과 무관하게 동일하고, 차이는 해시 테이블의 메모리 점유뿐) / 양쪽 정렬 후 두 포인터 병합 = Merge Join. PostgreSQL은 이 셋을 모두 갖추고 비용으로 고른다(MySQL의 "NL이 기본"인 세계와 결정적으로 다르다). 그래서 튜닝의 축이 "방식을 강제한다"가 아니라 추정 행 수를 맞추고(통계) · 안쪽 조인 키에 인덱스를 주고 · work_mem을 확인한다로 바뀐다. 종류 쪽의 핵심은 LEFT JOIN의 매칭 실패 쪽이 NULL로 채워진다는 것 — LEFT 자리에 INNER를 쓰면 에러가 아니라 행이 조용히 사라지는 버그가 되고, 다행히 PostgreSQL에서는 그 사고가 EXPLAIN에 흔적을 남긴다(7-2절).

0. 질문 + 출제 의도

질문: "JOIN의 종류(INNER, LEFT, ...)와 실행 방식(Nested Loop, Hash, Merge)을 설명해주세요."

출제 의도: LEFT JOIN을 써야 할 곳에 INNER를 써서 데이터가 조용히 누락되는 버그는 리뷰에서 잡아야 한다. 실행 방식은 "조인이 왜 느린가"를 실행 계획에서 읽는 기초다. 즉 두 축을 본다 — ① 종류: 문법 나열이 아니라 "잘못 고르면 어떤 버그가 나는가"를 아는지, ② 실행 방식: EXPLAIN (ANALYZE, BUFFERS)에서 조인 비용을 추론할 밑천이 있는지.

이 질문에서 유리한 출발점 방식 이름을 모르더라도 "자바로 짠다면 이렇게…"라고 원리에서 출발하면 절반은 온 것이고, 이름까지 붙이면 완성이다. PostgreSQL은 실행 계획에 방식 이름이 노드 이름으로 그대로 찍히므로(Nested Loop, Hash Join, Merge Join) 이 셋을 아는 것이 곧 계획을 읽는 능력이 된다.
이 페이지가 겨냥하는 약점 세 가지 ① 문법만 나열하고 버그로 못 잇는 것 → 1·7절에서 "NULL로 채운다"를 축으로 잡고, INNER 오용과 LEFT의 INNER 강등을 미니 데이터로 분해한다.
② 방식 이름은 외웠는데 계획을 못 읽는 것 → 3~5절에서 실제 EXPLAIN 출력에 형광펜을 긋는다 — loops, Index Cond, Hash 노드 위치, Batches, Sort Method.
③ "NL은 소량에 유리"처럼 결론만 외운 것 → 6절에서 손익분기를 숫자로 계산해 경험칙이 부등식에서 도출되는 과정을 밟는다.

1. 종류 — "매칭 실패한 행을 버리나, NULL로 채워 남기나"

조인 종류를 가르는 질문은 하나뿐이다 — 조인 조건에 매칭되지 않은 행을 어떻게 할 것인가. 다섯 종류는 이 질문에 대한 다섯 가지 답이다.

다섯 종류를 가르는 질문은 하나 — "매칭 실패한 행을 버릴 것인가, NULL로 채워 남길 것인가"
다섯 종류 — 기준은 "매칭 실패한 행의 운명" 하나
종류매칭 실패한 행은결과
INNER JOIN양쪽 모두 버린다양쪽에 다 있는 행만
LEFT JOIN왼쪽은 남기고, 오른쪽 컬럼을 NULL로 채운다왼쪽 전부 + 매칭된 오른쪽
RIGHT JOIN오른쪽은 남기고, 왼쪽 컬럼을 NULL로 채운다LEFT의 거울상
FULL OUTER JOIN양쪽 다 남기고 반대편을 NULL로 채운다양쪽 전부 (PostgreSQL은 기본 지원 — MySQL은 미지원이라 LEFT ∪ RIGHT UNION으로 흉내)
CROSS JOIN조건 없음 — 모든 조합왼쪽 × 오른쪽 (카테시안 곱)

1-1. 비유로 고정 — 참석자 명단과 식사 신청 명단

INNER — "식사 신청한 참석자만"

참석자 명단(왼쪽)과 식사 신청 명단(오른쪽)을 합칠 때, 양쪽에 다 이름이 있는 사람만 남긴다.

"참석자 전원 명단 뽑아줘"라는 요구에 이걸 쓰면 — 식사 신청 안 한 사람이 명단에서 사라진다. 그런데 아무도 에러를 못 본다.

LEFT — "참석자 전원, 메뉴 칸은 빈칸으로"

참석자 전원을 남기되, 식사 신청을 안 한 사람은 메뉴 칸을 빈칸(NULL)으로 둔다.

요구가 "전원 명단 + 있으면 메뉴도"라면 이쪽이 정답이다. 빈칸이 생긴다는 것까지가 이 조인의 정의다.

1-2. 시험대는 두 가지 — "NULL 채움"과 "조용한 행 누락"

① "NULL로 채운다"까지 말해야 LEFT JOIN을 아는 것이다. "왼쪽은 다 나온다"에서 멈추면 절반이다 — 매칭 안 된 행의 오른쪽 컬럼들이 NULL로 채워져 나온다는 사실이 7절의 버그(WHERE에서 NULL이 걸러지는 함정)와 IS NULL 안티조인 패턴의 토대다.

왜 그것이 토대인지는 SQL의 NULL 규칙 하나로 이어진다.

NULL 규칙 — 이 한 줄이 7-2절 사고의 원인 전체다

NULL은 "값이 없음"이지 "0"이나 "빈 문자열"이 아니고,
그래서 어떤 비교 연산자에 넣어도 참이 되지 않는다

NULL >= '2026-08-01'의 결과는 거짓(FALSE)조차 아닌 UNKNOWN이고, WHERE 절은 UNKNOWN인 행을 남기지 않는다.

그래서 LEFT JOIN이 애써 살려 둔 행이 그 뒤 WHERE 한 줄에 전멸하는 사고가 벌어진다(7-2절). "LEFT가 채운 NULL은 WHERE에서 죽는다" — 이 한 문장을 외워 두면 그 절은 이미 절반 이해한 것이다.

② LEFT와 INNER를 잘못 고르면 에러가 아니라 "조용한 행 누락"이다. 컴파일 에러도, 런타임 예외도 없다. 쿼리는 멀쩡히 돌고 결과만 슬그머니 줄어든다. 그래서 이 실수는 테스트보다 리뷰에서 잡아야 하는 부류다 — 7절에서 before/after로 본다.

2. 실행 방식 3종 — 자바 코드 ↔ PostgreSQL 노드 이름 1:1 매핑

List<Order> orders(10만 건) × List<User> users(1만 건)를 order.userId = user.id로 조인한다고 하자. 세 방식 모두 이미 짜 본 코드다 — PostgreSQL이 실행 계획에 찍는 이름만 붙이면 된다.

2-1. 대응표 — 의사코드와 노드 이름을 나란히 놓고 외운다

이 표 하나가 이 문서의 절반이다. 왼쪽 칸(자바)은 이미 아는 것이고, 가운데 칸(노드 이름)이 EXPLAIN 출력에 그대로 찍히는 문자열이며, 오른쪽 칸이 비용의 모양이다.

3방식 3초 인출 — 루 · 맵 · 지퍼

루프→이중 for + 안쪽 인덱스 탐색=Nested Loop
맵→작은 쪽을 HashMap에 넣고 큰 쪽으로 get=Hash Join
지퍼→양쪽 sort 후 두 포인터 병합=Merge Join

한 문장씩으로 압축하면 — NL은 "바깥 한 행마다 안쪽을 찍어 본다", Hash는 "한쪽을 통째로 색인해 두고 다른 쪽을 한 번 훑는다", Merge는 "둘 다 줄 세워 놓고 지퍼처럼 맞춘다". 이 세 문장에서 각각의 강점과 약점이 그대로 따라 나온다 — 다음 세 절이 그 도출 과정이다.

3. Nested Loop — 이중 루프, 단 안쪽은 인덱스로 찾아간다

먼저 오해 하나를 걷어내야 한다. DB의 NL은 소박한 이중 루프가 아니다.

before 소박한 이중 루프 — 안쪽을 매번 통순회
// 10만 × 1만 = 10억 번 비교
for (Order order : orders) {          // 바깥 = outer(드라이빙)
    for (User user : users) {         // 안쪽 = 전체 순회
        if (order.getUserId().equals(user.getId())) {
            // 매칭
        }
    }
}
after DB의 실제 NL — 안쪽 루프가 "인덱스 탐색 한 번"으로
for (Order order : orders) {
    // users.id 인덱스(B+Tree)를 타고 바로 찾아간다 — 통순회 없음
    User user = userIndex.seek(order.getUserId());
    if (user != null) {
        // 매칭
    }
}

안쪽 테이블을 조인 키 인덱스로 탐색하므로, 바깥 행 하나당 안쪽 비용이 "전체 순회"가 아니라 "트리 탐색 한 번"이다. PostgreSQL 계획에서 이 그림은 이렇게 보인다.

가장 자주 걸리는 함정 — inner의 actual rows는 loops당 평균이다

위 계획의 inner는 rows=1 loops=203이다. 이때 안쪽이 읽은 실제 총 행 수는 1이 아니라 rows × loops = 203이다.

이걸 모르면 "안쪽이 1행밖에 안 읽었는데 왜 느리지?"에서 멈춘다. loops가 20만이면 rows=1이라도 20만 번의 인덱스 탐색 + 힙 접근이 벌어진 것이다. NL 계획을 볼 때는 rows보다 loops를 먼저 본다.

3-1. 여기서 튜닝의 기본 문법이 그대로 도출된다

드라이빙(outer) 테이블은 작게, 안쪽(inner) 테이블의 조인 키에는 인덱스

왜 바깥이 작아야 하나

바깥 루프 횟수 = 드라이빙 테이블 행 수이므로, 조건으로 먼저 줄어드는 쪽이 바깥이어야 한다. 플래너가 조인 순서를 정하는 기준이 바로 이것이다.

안쪽 조인 키에 인덱스가 없으면?

PostgreSQL은 대개 NL을 포기하고 Hash Join으로 갈아탄다. 그래서 "인덱스 없는 조인"이 PostgreSQL에서는 O(N×M) 참사보다는 예상 못 한 대량 해시 조인 + 디스크 스필로 나타난다. (MySQL이 예전에 이 자리에서 조인 버퍼로 버티던 것과 다르다.)

3-2. PostgreSQL 특유의 두 가지 가산점

① 힙 페치가 따라붙는다
PostgreSQL은 힙 기반(비클러스터드) 테이블이라 모든 인덱스가 "인덱스 → TID → 힙" 구조다. 그래서 NL 안쪽 비용은 "인덱스 탐색 + 힙 랜덤 접근"이고, 반복 횟수가 커지면 랜덤 I/O가 비싸져 플래너가 순차 읽기 기반의 Hash Join을 고른다. 커버링 인덱스로 Index Only Scan이 되면 이 힙 접근이 사라져 NL이 다시 유리해진다.
② Memoize 노드 (PG 14+)
바깥 행에 같은 조인 키가 반복되면 안쪽 탐색 결과를 캐시한다 — 자바로 치면 computeIfAbsent를 씌운 것. 계획에 Memoize (Hits: 1832 Misses: 210 Evictions: 0)처럼 찍히고, Hits가 크면 NL이 "중복 키만큼 공짜로" 빨라진 상태다. (그 전 버전에서 같은 자리에 쓰이던 Materialize는 안쪽 결과 전체를 메모리에 받아 두고 반복 스캔하는 노드다.)

4. Hash Join — 작은 쪽으로 build, 큰 쪽으로 probe

java 이미 짜 본 코드 — 2단계로 끝난다
// 1단계 build: "작은 쪽"(users 1만)으로 해시 테이블을 만든다
Map<Long, User> built = new HashMap<>();
for (User user : users) {
    built.put(user.getId(), user);
}

// 2단계 probe: "큰 쪽"(orders 10만)을 한 번 순회하며 탐색
for (Order order : orders) {
    User user = built.get(order.getUserId());   // O(1) 탐색
    if (user != null) {
        // 매칭
    }
}

4-2. 용어 ② work_mem — 함정 셋을 같이 외운다

정의 "쿼리 실행 중 임시 작업 하나가 디스크로 내려가기 전까지 쓸 수 있는 메모리 상한"인 PostgreSQL 설정값(기본 4MB). 여기서 "작업"은 계획의 노드다 — Sort, 해시 조인의 Hash, HashAggregate, Materialize.
함정 ⓐ 쿼리당이 아니라 노드당
정렬 3개 + 해시 조인 2개면 최대 5 × work_mem이고, 병렬 워커 수만큼 또 곱해진다. 전역으로 크게 올리면 max_connections × 노드 수만큼 부풀어 OOM 위험 — 전역은 보수적으로 두고 무거운 배치·리포트만 세션에서 올린다.
함정 ⓑ shared_buffers와 다르다
shared_buffers는 테이블·인덱스 페이지를 담는 공유 캐시, work_mem은 세션이 혼자 쓰는 작업 공간이다. (VACUUM·인덱스 생성용은 또 별도로 maintenance_work_mem.)
함정 ⓒ 해시에는 배수가 붙는다
hash_mem_multiplier(PG 13 도입, PG 15부터 기본 2.0)가 곱해져 해시 테이블의 실효 한도 = work_mem × 2이고, 정렬에는 이 배수가 붙지 않는다.
정석 확인법 세션 단위로 SET LOCAL work_mem = '64MB' 후 재실행해 Batches가 1로 떨어지는지 본다. 병렬 계획에서는 Parallel Hash / Parallel Hash Join(PG 11+)으로 찍히는데, 이때는 워커들이 공유 해시 테이블 하나를 함께 만든다.

4-3. "빌드 사이드는 항상 작은 쪽" — 큰 쪽이 이득이라는 건 오개념이다 필수

흔한 오해는 "메모리가 허용하면 큰 쪽을 해시로 만드는 게 이득 아닌가"다. 답은 "이득이 전무하다"이고, 논증은 세 단계다.

1
프로브 비용은 방향과 무관하게 같다. 어느 쪽을 build하든 결국 "한쪽 전체를 넣고, 다른 쪽 전체를 순회하며 get" — 양쪽 다 정확히 한 번씩 훑는 총량은 동일하다. 10만을 넣고 1만으로 찾으나, 1만을 넣고 10만으로 찾으나 순회 총량은 11만으로 같다.
2
다른 것은 해시 테이블의 크기뿐이다. 10만 건짜리 Map과 1만 건짜리 Map — 결과는 같은데 메모리 점유만 10배 차이 난다. 큰 쪽을 build하면 얻는 것 없이 메모리만 더 쓴다.
3
그리고 해시 테이블이 작업 메모리를 넘치면 스필이 일어나 급격히 느려진다 — 작은 쪽을 build할수록 스필 위험 자체가 줄어든다.

규칙 — "항상 작은 쪽을 해시로"

"메모리 한계 내에서 가능한 큰 쪽"이 아니라, 애초에 이득이 전무하니 무조건 작은 쪽

자바에서도 같은 이유로 작은 리스트를 Map으로 만드는 게 정석이다. 그리고 PostgreSQL 계획에서는 Hash 노드가 붙은 쪽이 빌드 사이드이므로 플래너가 정말 작은 쪽을 골랐는지 눈으로 확인할 수 있다.

계획에 Hash Right Join이 찍혀 당황하지 않기 PostgreSQL은 이 원칙을 outer join에서도 관철한다. a LEFT JOIN b인데 a가 작으면, PostgreSQL은 a를 해시로 만들고 b로 probe하는 Hash Right Join으로 뒤집어 실행한다(의미는 그대로, 빌드 사이드만 바꾼 것). 내가 RIGHT JOIN을 쓴 적이 없어도 나올 수 있는 노드 이름이다.

5. Merge Join — 양쪽 정렬 후 지퍼처럼 병합

java 합병 정렬의 merge 단계와 같은 그림
// 1단계: 양쪽을 조인 키로 정렬
orders.sort(comparing(Order::getUserId));
users.sort(comparing(User::getId));

// 2단계: 두 포인터로 지퍼 병합 — 각자 앞으로만 전진
int i = 0, j = 0;
while (i < orders.size() && j < users.size()) {
    long orderKey = orders.get(i).getUserId();
    long userKey  = users.get(j).getId();
    if (orderKey == userKey)      { /* 매칭 */ i++; }
    else if (orderKey < userKey)  i++;
    else                          j++;
}

병합 단계는 양쪽을 한 번씩만 훑는다. 비용의 대부분은 정렬이므로, 입력이 이미 조인 키 순서로 정렬돼 있으면 정렬이 공짜가 되어 강해진다. PostgreSQL 계획으로 보면 차이가 그대로 드러난다.

6. 언제 무엇이 선택되나 — 결론이 아니라 비용으로 따진다

"NL은 소량 조회에 유리하다" 같은 결론만 외우면 판단이 안 선다. 세 방식의 비용을 같은 축에 올려놓으면 선택 기준이 계산에서 나온다. 기호부터 정한다.

6-1. 숫자를 넣어 보면 감이 잡힌다

Merge Join의 자리는 조금 다르다. Hash와 마찬가지로 양쪽을 한 번씩만 훑지만 정렬 비용을 추가로 내야 하므로, 정렬 항이 0이 되는 상황에서만 Hash를 이긴다 — 양쪽 다 조인 키 인덱스 순서로 읽을 수 있거나, ORDER BY가 조인 키와 같아 어차피 정렬해야 하는 경우다. 그리고 해시가 아예 못 하는 일(부등호 조인, FULL OUTER JOIN)에서는 비교 대상 없이 Merge가 유일한 선택지가 된다.

6-2. 판별표 — 다섯 줄로 정리

"어떤 방식이 나올 상황인가"를 역으로 읽는 표 — 계획이 예상과 다르면 이 표의 전제부터 의심한다
상황선택그 이유

7. 실무 사례 — "조용한 행 누락": 에러 없이 데이터가 사라지는 두 함정

7-1. LEFT 자리에 INNER — 쿠폰 안 쓴 주문이 목록에서 사라진다

요구사항: "주문 목록을 보여주되, 쿠폰을 썼다면 쿠폰 코드도 같이."

before INNER JOIN — 쿼리는 멀쩡히 돌지만
SELECT o.id, o.amount, c.coupon_code
FROM orders o
JOIN coupon_use c ON c.order_id = o.id;   -- JOIN = INNER JOIN

-- 쿠폰을 안 쓴 주문은 coupon_use에 행이 없다
-- → 매칭 실패 → INNER는 그 행을 버린다
-- → "쿠폰 미사용 주문"이 목록에서 통째로 사라진다.
-- 에러도 경고도 없다.
-- 사용자 항의("내 주문 어디 갔죠")로 발견된다.
after LEFT JOIN — 주문은 전부, 쿠폰 없으면 NULL
SELECT o.id, o.amount, c.coupon_code
FROM orders o
LEFT JOIN coupon_use c ON c.order_id = o.id;

-- 쿠폰 미사용 주문도 나온다.
-- coupon_code 칸만 NULL.

리뷰 체크 습관 — 조인을 볼 때마다 이 한 문장을 던진다

"이 조인의 오른쪽은 왼쪽 모든 행에 반드시 존재하는가?"

존재가 보장되지 않는(선택적) 관계 + INNER

쿠폰 · 리뷰 · 프로필 사진 · 배송 추적 — 여기에 INNER가 보이면 행 누락을 의심한다.

반드시 존재하는 관계 + INNER

주문 → 주문자처럼 없을 수 없는 관계면 INNER가 맞고, 습관적 LEFT는 오히려 의도를 흐린다.

PostgreSQL 한 줄 덧붙임 — 습관적 LEFT가 무해하다고만 볼 수도 없다 PostgreSQL 플래너는 "오른쪽 컬럼을 아무도 안 쓰고, 조인 키가 유니크해서 행이 늘지 않는" LEFT JOIN은 아예 제거해 버린다(join removal — 계획에서 그 테이블이 사라진다). 즉 조건이 맞으면 공짜지만, 조건이 안 맞으면 그대로 비용이다.

7-2. LEFT JOIN 뒤 WHERE에 오른쪽 조건 — LEFT가 조용히 INNER로 강등된다 함정가산점

한 단계 더 교묘한 함정. LEFT JOIN을 제대로 썼는데도 INNER처럼 동작하는 경우다.

before LEFT JOIN인데 결과는 INNER JOIN과 동일
SELECT o.id, o.amount, c.coupon_code
FROM orders o
LEFT JOIN coupon_use c ON c.order_id = o.id

7-3. PostgreSQL에서는 이 사고가 EXPLAIN에 흔적을 남긴다 실무 팁

플래너는 "오른쪽에 strict 조건이 붙었으니 이 outer join은 inner join과 같다"고 판단해 조인을 실제로 축약한다(outer join reduction). 그래서 계획에 Hash Left Join이 아니라 그냥 Hash Join이 찍힌다.

"LEFT JOIN을 썼는데 계획에 Left가 없다 → 조건 배치가 잘못됐다"

반대로 의도적인 예외도 계획에 드러난다 — WHERE c.order_id IS NULL(쿠폰 안 쓴 주문만 찾는 안티조인 패턴)은 축약이 아니라 Hash Anti Join으로 찍히고, 같은 의도를 NOT EXISTS로 쓰면 동일한 Hash Anti Join 계획이 나온다. 즉 "IS NULL 안티조인"은 우연히 되는 트릭이 아니라 플래너가 알아보는 정식 패턴이다.

9-1. 면접 전날 30초 인출 — 답을 가리고 스스로 말해 본다

해시 빌드 사이드는?
항상 작은 쪽. 프로브 총량은 방향과 무관하게 같고 차이는 메모리 점유뿐 — 큰 쪽 build는 얻는 것 없이 스필 위험만 키운다. 계획에선 Hash 노드가 붙은 쪽.
손익분기 한 줄은?
N × c vs S — 바깥 행 수 × 안쪽 1건 탐색 대 안쪽 통째 스캔. 안쪽 1000만 행이면 분기점은 수만 행 근처.
계획의 경고등 셋은?

loops(= 바깥 행 수)와 Index Cond 유무. actual rows는 loops당 평균이라 총량은 rows × loops다.
LEFT가 INNER로 강등되는 이유는?
LEFT가 채운 NULL을 WHERE가 비교하면 결과가 UNKNOWN이라 그 행은 반드시 탈락한다. "살린 행을 다음 줄에서 죽이는" 구조.
ON과 WHERE의 분업은?
ON = 무엇을 매칭할지(실패해도 NULL로 살린다), WHERE = 완성된 결과에서 무엇을 남길지(NULL은 여기서 죽는다). 오른쪽 필터는 ON, 왼쪽 필터는 WHERE.
work_mem 함정 셋은?
ⓐ 쿼리당이 아니라 노드당(병렬 워커만큼 또 곱) ⓑ shared_buffers와 다르다 ⓒ 해시에는 hash_mem_multiplier가 곱해져 실효 한도 = work_mem × 2(PG 15 기본).
PostgreSQL 튜닝의 축은?
방식 강제가 아니라 플래너의 선택을 옳게 만들기 — ① ANALYZE(통계) ② 안쪽 조인 키 인덱스 ③ work_mem. enable_* 스위치는 가설 검증용.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

DB는 해시 테이블을 어느 쪽으로 만드나요? 메모리가 허용하면 큰 쪽으로 만드는 게 이득 아닌가요? 필수힌트: "작은 쪽"으로 끝내지 말고, 큰 쪽의 이득이 왜 0인지를 논증으로 보인다

항상 작은 쪽이다. 큰 쪽을 build해서 얻는 이득은 없다.

① 프로브 비용은 방향과 무관하게 같다. 어느 방향이든 한쪽 전체를 넣고 다른 쪽 전체를 순회하므로 순회 총량은 동일하다 — 10만을 넣고 1만으로 찾으나 그 반대나 합계는 11만으로 같다.

② 달라지는 것은 해시 테이블의 크기뿐이다. 결과는 같은데 메모리만 몇 배 쓴다.

③ 게다가 스필 위험이 커진다. 해시 테이블이 작업 메모리(work_mem × hash_mem_multiplier)를 넘치면 디스크 스필로 급격히 느려지므로, 작은 쪽 build는 스필 위험을 줄이는 선택이기도 하다.

마무리는 "계획에서 확인할 수 있다"로 닫는다. PostgreSQL 계획에서는 Hash 노드가 붙은 쪽이 빌드 사이드이므로 플래너가 정말 작은 쪽을 골랐는지 눈으로 확인할 수 있고, 거기서 Batches가 1인지까지 보면 스필 여부까지 한 번에 읽힌다.

PostgreSQL에서 조인 쿼리가 느립니다. 실행 계획에서 먼저 볼 세 가지는? 필수힌트: 방 · 추 · 메. 그리고 방식별 추가 확인 지점을 하나씩 덧붙인다

① 어떤 방식을 골랐나 — Nested Loop / Hash Join / Merge Join. 단 방식 자체를 탓하기 전에 다음을 본다.

② 추정과 실제가 얼마나 벌어졌나 — rows=210 vs actual rows=200000처럼 자릿수가 다르면 잘못된 선택의 원인은 통계다(→ ANALYZE, 상관 컬럼이면 CREATE STATISTICS).

③ 메모리 경고등 — Hash Join의 Batches > 1, Sort Method: external merge Disk:. 스필이면 work_mem이나 빌드 사이드 크기를 손댄다.

방식별로 덧붙이면 답이 완성된다.

  • NL이면 — inner의 loops와 Index Cond 유무(안쪽이 Seq Scan이면 인덱스부터)
  • Hash면 — Hash 노드가 작은 쪽에 붙었는지
  • Merge면 — Sort가 붙었는지, 붙었으면 인덱스로 없앨 수 있는지

BUFFERS까지 켜서 shared read가 큰 노드를 찾으면 실제 I/O가 어디서 나는지도 잡힌다.

LEFT JOIN을 걸었는데 결과가 INNER JOIN과 똑같습니다. 코드는 안 바꿨다는데 뭘 의심하나요? 함정힌트: 원인 한 줄 → 처방 한 줄 → PostgreSQL이면 30초 확진법 → 예외 하나

WHERE 절에 오른쪽 테이블 조건이 있는지부터 본다. LEFT JOIN이 살려둔 매칭 실패 행은 오른쪽 컬럼이 전부 NULL인데, WHERE의 c.컬럼 = 값이나 c.컬럼 >= 값 비교에서 NULL은 참이 될 수 없어 전부 걸러진다 — LEFT가 조용히 INNER로 변하는 전형적 패턴이다.

처방은 오른쪽 테이블 조건을 ON으로 올리는 것이다. 그러면 그 조건이 "매칭 여부의 판정 기준"이 되어, 조건 미달인 행도 미매칭으로 처리되어 NULL로 채워져 살아남는다.

PostgreSQL이면 EXPLAIN으로 30초에 확진한다 — 계획에 Hash Left Join이 아니라 Hash Join이 찍혀 있으면 플래너가 이미 inner join으로 축약했다는 증거다(outer join reduction).

단 예외가 하나 있다. c.컬럼 IS NULL만은 매칭 실패 행만 골라내는 의도적 안티조인 패턴이고, 계획에도 Anti Join으로 찍힌다. "WHERE에 오른쪽 조건이 있으면 무조건 버그"가 아니라 "IS NULL만 예외"라고 말하면 정확도가 올라간다.

세 방식은 각각 언제 이기고, 플래너는 무엇을 보고 고르나요? 시니어 변별힌트: 입력 넷 → 비용식 → 손익분기 한 줄 → "전부 추정에 얹혀 있다"로 착지

플래너의 입력은 넷이다 — ① 양쪽의 (조건 적용 후) 예상 행 수, ② 조인 키 인덱스·정렬 순서 유무, ③ 조인 조건이 등호인가, ④ work_mem.

비용으로 말하면 NL은 바깥 행 수 N × 안쪽 1건 탐색 c, Hash와 Merge는 안쪽 통째 스캔 S(+ Merge는 정렬)이므로 손익분기는 N × c vs S 한 줄로 압축된다. 안쪽이 1000만 행쯤이면 손익분기 N이 수만 건 근처라 —

  • 바깥이 수백~수천이면 NL (첫 행이 빨리 나오므로 OLTP 소량 조회의 기본값)
  • 양쪽 다 크고 등호면 Hash (인덱스 없이 양쪽 한 번씩, 대신 메모리)
  • 이미 정렬돼 있거나 정렬이 어차피 필요하거나 범위·FULL 조인이면 Merge

핵심은 이 판단이 전부 "예상 행 수"에 얹혀 있다는 것이다. 통계가 낡거나 컬럼 간 상관을 못 잡으면(WHERE city='서울' AND zipcode='06236' 같은 경우) 추정이 무너지고 방식 선택도 같이 틀어진다.

그래서 "조인 방식이 이상하다"의 1차 처방은 방식 강제가 아니라 ANALYZE / 확장 통계(CREATE STATISTICS) / default_statistics_target 상향이다. enable_nestloop = off 같은 스위치는 가설 검증용이라고 선을 그어 말하면 시니어의 언어가 된다.

PostgreSQL은 FULL OUTER JOIN을 지원하는데, 제약이나 주의점이 있나요? 가산점힌트: "지원한다"로 끝내지 말고 실행 방식의 제약에서 에러 메시지까지 잇는다

지원한다 — 단 조인 조건이 merge/hash 가능해야 한다. FULL OUTER는 양쪽의 미매칭을 다 추적해야 해서 Nested Loop로는 구현할 수 없고 Merge Full Join 또는 Hash Full Join으로만 실행된다.

그래서 등호나 merge 가능한 조건이 아니면 실행 자체가 거부된다 — "FULL JOIN is only supported with merge-joinable or hash-joinable join conditions" 에러가 그것이다. 이 에러 문구를 기억하고 있으면 "실제로 써 봤다"로 들린다.

덧붙일 두 가지 — ① MySQL에는 FULL OUTER가 없어 LEFT ∪ RIGHT를 UNION(중복 제거가 필요하므로 UNION ALL이 아니다)으로 흉내 내야 한다. ② 실무에서 FULL OUTER가 필요한 상황 자체가 드물고(대개 두 집합의 대사·검증 작업), 자주 필요하다면 모델링을 의심해 볼 신호다.

MySQL로 물어보면 답이 달라지는 부분은 어디인가요? 경험 대조힌트: 세 지점 — 기본 방식 · 인덱스 안쪽 비용 · FULL OUTER

① 기본 방식. MySQL은 전통적으로 NL 계열이 기본이고 해시 조인이 8.0.18에서 뒤늦게 추가됐으며 Merge Join은 아예 없다. 그래서 MySQL 조인 튜닝은 곧 NL 튜닝("드라이빙 작게 + 안쪽 인덱스")에 수렴하는데, PostgreSQL은 세 방식을 비용으로 고르므로 "플래너가 옳게 고르도록 통계·메모리·인덱스를 갖추는 일"이 된다.

② 인덱스 안쪽 비용. InnoDB는 클러스터드 인덱스라 PK 조인의 안쪽 접근이 곧 데이터 접근이지만, PostgreSQL은 힙 기반이라 인덱스 탐색 뒤에 힙 페치가 붙는다 — 커버링 인덱스로 Index Only Scan을 노리는 이유가 이것이다.

③ FULL OUTER JOIN. PostgreSQL은 지원, MySQL은 UNION으로 우회. 이 세 개를 짚어 말하면 "한쪽만 써봤다"가 아니라 "차이를 원리로 이해했다"로 들린다.

추가 꼬리질문 — 계획을 실제로 읽을 때 걸리는 것들

inner 노드의 actual rows=1인데 쿼리가 몇 초씩 걸립니다. 어디를 잘못 본 건가요? 함정힌트: 그 숫자가 무엇의 평균인지

inner의 actual rows는 총합이 아니라 loops당 평균이다. 실제 총 행 수는 rows × loops다.

rows=1 loops=203이면 총 203행이라 가볍지만, rows=1 loops=200000이면 20만 번의 인덱스 탐색 + 힙 접근이 벌어진 것이다 — "1행씩 20만 번"은 결코 가볍지 않다. 시간 값(actual time)도 마찬가지로 loops당 평균이므로, 그 노드가 실제로 쓴 시간은 대략 actual time × loops로 읽어야 한다.

그래서 NL 계획을 볼 때는 rows보다 loops를 먼저 본다. 그리고 loops가 예상보다 훨씬 크다면 원인은 대개 바깥의 추정 행 수가 틀린 것이므로, 다음 확인 지점은 outer 노드의 rows vs actual rows다.

계획에 Hash Right Join이 찍혔습니다. 저는 RIGHT JOIN을 쓴 적이 없는데요? 가산점힌트: 4-3절의 원칙이 outer join에서 어떻게 관철되는지

플래너가 빌드 사이드를 뒤집은 것이고, 의미는 그대로다. a LEFT JOIN b인데 a가 작으면 PostgreSQL은 a로 해시 테이블을 만들고 b로 probe하는 편이 싸다고 판단한다. 그런데 해시 조인에서 "어느 쪽을 보존하느냐"는 빌드/프로브 배치에 따라 표기가 달라지므로, 빌드 사이드를 바꾼 결과가 Hash Right Join이라는 이름으로 나타난다.

결과 집합은 내가 쓴 LEFT JOIN과 완전히 동일하다. 바뀐 것은 실행 전략(누구를 메모리에 올리는가)뿐이다.

여기서 읽어야 할 정보는 오히려 이것이다 — 플래너가 "a가 작다"고 판단했다는 사실. 만약 실제로 a가 크다면 추정이 틀렸다는 신호이므로 rows vs actual rows를 확인한다. 노드 이름의 Right에 놀라지 않고 "빌드 사이드가 어디인가"로 번역해 읽는 것이 이 계획을 보는 법이다.

Batches: 8이 찍혔습니다. work_mem을 전역으로 넉넉히 올리면 되지 않나요? 시니어 변별힌트: 올리기 전에 할 일이 있고, 올린다면 어디서 올려야 하는지가 답이다

전역 상향은 마지막 수단이다. work_mem은 쿼리당이 아니라 노드당이라, 정렬 3개 + 해시 조인 2개짜리 쿼리는 최대 5 × work_mem을 쓰고 병렬 워커 수만큼 또 곱해진다. 여기에 동시 세션 수까지 곱하면 서버 메모리를 넘겨 OOM이 난다. "한 쿼리를 살리려다 서버를 죽이는" 전형적 경로다.

순서는 이렇다.

  • ① 빌드 사이드를 먼저 줄인다 — 선행 필터를 조인 전에 걸고, SELECT * 대신 필요한 컬럼만 가져온다(해시 테이블의 폭이 줄어든다). 같은 work_mem으로도 배치가 1로 떨어질 수 있다.
  • ② 추정이 맞는지 본다 — 실제 행 수보다 크게 과소 추정했다면 플래너가 메모리에 들어갈 줄 알고 해시를 고른 것이므로, 통계를 고치면 더 나은 계획 자체가 나올 수 있다.
  • ③ 그래도 필요하면 세션에서 올린다 — SET LOCAL work_mem = '64MB'로 그 배치·리포트 트랜잭션에만 적용하고 재실행해 Batches가 1로 떨어지는지 확인한다.

덧붙이면 가산점 — 해시에는 hash_mem_multiplier(PG 15부터 기본 2.0)가 곱해져 실효 한도는 work_mem × 2이고, 정렬에는 이 배수가 붙지 않는다. 그래서 "정렬은 여전히 디스크로 내려가는데 해시는 괜찮다"는 상황이 생길 수 있다.

Nested Loop인데 inner가 Seq Scan입니다. 무조건 나쁜 계획인가요? 함정힌트: 경고 신호인 건 맞다. 다만 확인 순서가 있고, 괜찮은 경우도 있다

경고 신호인 것은 맞다 — 이 자리가 Seq Scan이면 "소박한 이중 루프"가 실제로 벌어지고 있을 가능성이 있고, 그때 비용은 N × (안쪽 통째 스캔)으로 폭발한다.

다만 확인 순서가 있다. 두 숫자를 같이 본다.

괜찮은 경우 — 안쪽이 아주 작다

코드 테이블처럼 안쪽이 몇 행뿐이면 한 번 훑는 비용 자체가 거의 0이라, 인덱스보다 그냥 훑는 게 싸다. 이때는 안쪽 결과를 재사용하도록 Materialize가 함께 붙는 경우가 많다.

위험한 경우 — loops가 크고 안쪽도 크다

안쪽 조인 키에 인덱스가 없고 loops가 수만 이상이면 이 계획은 그냥 O(N×M)이다. 처방은 안쪽 조인 키 인덱스, 그리고 바깥 추정이 맞는지 확인.

판별식 한 줄 — "loops × 안쪽 스캔 비용"이 감당 가능한가. 그리고 이 계획이 의외로 드문 이유도 알아 두면 좋다 — PostgreSQL은 안쪽에 인덱스가 없고 양쪽이 크면 대개 스스로 Hash Join으로 갈아탄다. 그러니 이 모양이 보였다면 플래너가 "안쪽이 작다"고 믿고 있다는 뜻이고, 그 믿음이 맞는지부터 확인하는 것이 순서다.

Memoize라는 노드가 붙어 있습니다. 이건 뭐고 무엇을 보면 되나요? 가산점힌트: 자바의 computeIfAbsent

NL의 안쪽 탐색 결과를 캐시하는 노드다(PG 14+). 바깥 행에 같은 조인 키가 반복되면 안쪽을 다시 찾지 않고 캐시에서 꺼낸다 — 자바로 치면 안쪽 탐색에 computeIfAbsent를 씌운 것이다.

볼 것은 한 줄이다 — Memoize (Hits: 1832 Misses: 210 Evictions: 0). Hits가 크면 중복 키만큼 안쪽 탐색이 공짜로 생략된 것이고, Evictions가 크면 캐시가 부족해 넣었다 버리기를 반복한 것이라 이득이 줄어든다.

실무적 의미 — 바깥에 중복 조인 키가 많은 경우(예: 주문 10만 건이 사용자 1만 명에 몰려 있는 경우) NL의 손익분기가 오른쪽으로 밀린다. 즉 6절의 N × c에서 실효 c가 히트율만큼 낮아지는 셈이다. (그 전 버전에서 같은 자리에 쓰이던 Materialize는 캐시가 아니라 안쪽 결과 전체를 메모리에 받아 두고 반복 스캔하는 노드라 성격이 다르다.)

"쿠폰을 한 번도 안 쓴 주문"을 찾을 때 IS NULL · NOT EXISTS · NOT IN 중 무엇을 쓰나요? 시니어 변별힌트: 앞의 둘은 같은 계획으로 수렴하고, 하나는 결과가 통째로 사라질 수 있다

앞의 둘은 사실상 같고, NOT IN만 성격이 다르다.

  • LEFT JOIN ... WHERE c.order_id IS NULL — 7절에서 본 의도적 안티조인. 계획에 Anti Join으로 찍힌다.
  • NOT EXISTS (SELECT 1 FROM coupon_use c WHERE c.order_id = o.id) — 같은 Anti Join 계획이 나온다. 의도가 문장에 그대로 드러나 읽기 쉬워 이쪽을 선호하는 경우가 많다.
  • NOT IN (SELECT order_id FROM coupon_use) — 위험하다. 서브쿼리 결과에 NULL이 하나라도 섞이면 비교가 전부 UNKNOWN이 되어 결과가 한 행도 나오지 않는다. 게다가 그 NULL 가능성 때문에 안티조인으로 축약되지 못하는 경우가 많아 성능도 불리하다.

실무 결론 — 기본은 NOT EXISTS, 조인 결과의 다른 컬럼도 함께 써야 한다면 LEFT JOIN + IS NULL, NOT IN은 서브쿼리 컬럼에 NOT NULL이 보장될 때만.

여기가 1-2절의 NULL 규칙과 만나는 지점이라는 걸 짚어 주면 좋다 — LEFT의 INNER 강등도, NOT IN의 전멸도 원인은 하나다. "NULL은 어떤 비교에서도 참이 되지 않는다."

테이블 12개를 조인하는데 계획이 이상하고 플래닝 시간도 깁니다. 무엇을 의심하나요? 가산점힌트: 조인 순서 탐색에는 한도가 있다

join_collapse_limit(기본 8)과 geqo(유전 알고리즘, 기본 임계값 12)를 의심한다.

조인 테이블 수가 join_collapse_limit을 넘으면 PostgreSQL은 모든 조인 순서를 탐색하기를 포기하고 FROM에 쓴 순서를 그대로 쓰거나 부분적으로만 재배열한다. 그 위(기본 12개)부터는 geqo로 근사하는데, 근사이므로 실행할 때마다 계획이 조금씩 달라질 수도 있다.

증상으로 말하면 — "쿼리를 조금만 바꿔도 계획이 크게 요동친다", "FROM 순서를 바꾸니 빨라졌다"가 이 영역의 전형적 신호다. 반대로 조인 순서 탐색은 조합 폭발이므로, 한도를 올리면 플래닝 시간 자체가 실행 시간을 넘길 수도 있다.

실무적 처방은 대개 설정이 아니라 쿼리 구조다 — 필요 없는 조인을 걷어내고(특히 화면에서 안 쓰는 LEFT JOIN), 단계를 나누거나, 사전 집계를 두는 것. "12개를 한 번에 조인해야 하는가"를 먼저 묻는 것이 시니어의 순서다.

실수로 CROSS JOIN이 되는 경우가 있나요? 계획에서 어떻게 알아채나요? 함정힌트: 조건을 "빠뜨린" 경우와 "다른 짝에만 건" 경우 둘 다 있다

있다. 그리고 대개 에러가 아니라 "결과가 이상하게 많다"로 나타난다.

  • ON 조건 누락 — 옛 스타일의 콤마 조인(FROM a, b)에서 WHERE에 조인 조건을 빠뜨린 경우가 대표적이다.
  • 조건을 엉뚱한 짝에만 건 경우 — 세 테이블을 조인하면서 a-b는 이었는데 c는 아무 데도 안 이은 경우. c만큼 결과가 배로 부푼다.
  • 다:다 관계를 눈치 못 챈 경우 — 엄밀히 CROSS는 아니지만 증상은 비슷하다. 양쪽 모두 조인 키가 중복이면 결과 행 수가 곱해진다(그래서 SUM() 값이 갑자기 몇 배로 뛴다).

계획에서의 신호 — 조인 조건이 없는 Nested Loop(Join Filter도 Index Cond도 안 보인다)와, 조인 노드의 rows가 자식들의 곱에 가까운 것이다. rows=100000짜리와 rows=10000짜리를 조인했는데 결과가 rows=1000000000이면 볼 것도 없다.

예방은 습관이다 — 콤마 조인 대신 명시적 JOIN ... ON을 쓰면 조인 조건이 문법 위치로 강제되어 빠뜨리기 어려워지고, 정말 카테시안 곱이 필요할 때만 CROSS JOIN이라고 적어 의도를 드러낸다.

한 줄 요약
조인 실행 방식은 이미 아는 코드의 DB 이름이다 — 이중 루프 = Nested Loop(안쪽은 인덱스 탐색, inner의 loops와 Index Cond를 본다), Map 빌드+탐색 = Hash Join(빌드는 항상 작은 쪽 — Hash 노드가 붙은 쪽이고 Batches > 1이면 스필, 등호 전용), 정렬 후 병합 = Merge Join(Sort 노드가 없으면 정렬이 공짜). 선택 기준은 결론이 아니라 비용이다 — 바깥 행 수 N × 안쪽 1건 탐색 c 대 안쪽 통째 스캔 S의 대소가 NL과 Hash를 가르고, 정렬 항이 0이 될 때 Merge가 낀다. PostgreSQL은 셋을 모두 비용으로 고르므로 튜닝은 방식 강제가 아니라 통계·인덱스·work_mem을 갖춰 플래너의 선택을 옳게 만드는 일이다. 종류의 핵심은 LEFT JOIN의 매칭 실패 쪽 NULL 채움이며, LEFT 자리에 INNER를 쓰거나 LEFT 뒤 WHERE에 오른쪽 조건을 두면 에러 없이 행이 조용히 사라진다 — PostgreSQL에서는 계획에 Left가 사라진 것으로 확진할 수 있다.
