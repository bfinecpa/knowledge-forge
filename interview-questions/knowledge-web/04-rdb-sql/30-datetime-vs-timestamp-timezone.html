timestamp vs timestamptz
"벽시계를 적는 타입"과 "순간을 적는 타입", 그리고 시간 원칙이 스키마에 착지하는 지점

면접 질문: "DATETIME과 TIMESTAMP의 차이(타임존 동작, 범위)는? 글로벌 서비스라면 무엇을 선택하겠습니까?"
PostgreSQL 기준 재해석: "timestamp(without time zone)와 timestamptz(with time zone)의 차이는? 글로벌 서비스라면 무엇을 선택하겠습니까?"

핵심 관전 포인트 — PostgreSQL의 두 타입은 "무엇을 저장하느냐"가 다르다. timestamptz(with time zone)는 이름과 달리 타임존을 저장하지 않는다 — 들어온 값을 세션 TimeZone으로 해석해 UTC 순간 하나로 정규화해 적고, 읽을 때 읽는 세션의 TimeZone으로 되돌려 보여줄 뿐이다. 즉 저장된 것은 "언제"이지 "어디의 몇 시"가 아니다. 반대로 timestamp(without time zone)는 아무 변환 없이 받은 벽시계 값을 그대로 적으므로, "어느 도시의 09:00인지"는 값 어디에도 없고 그 규약은 애플리케이션이 지켜야 한다. 그리고 PostgreSQL에서는 두 타입이 똑같이 8바이트·마이크로초 해상도·4713 BC~294276 AD 범위라, MySQL에서 선택을 갈랐던 2038년 한계와 1바이트 저울질이 통째로 사라진다 — 선택 축이 "타임존 정보를 DB가 정규화해 주느냐, 앱이 규율로 지키느냐" 하나만 남는다. 그래서 결론이 단순해진다: 과거·현재의 사건은 무조건 timestamptz, timestamp는 "벽시계 자체가 의미인" 미래 일정에 IANA 존 ID 컬럼과 짝으로만 쓴다. 대신 PostgreSQL 고유의 함정 셋을 알아야 한다 — ① 같은 값이 세션 TimeZone에 따라 다른 문자열로 보이므로 콘솔에서 본 숫자로 사고를 판정하면 안 되고, 판정은 AT TIME ZONE 'UTC'로 기준을 못 박고 해야 한다 ② now()는 "지금"이 아니라 트랜잭션이 시작된 시각이라 한 배치에서 넣은 1만 건이 전부 같은 created_at을 갖고, 그 값으로 삽입 순서를 가리거나 증분 동기화를 돌리면 행이 조용히 새어 나간다 ③ pgjdbc가 접속할 때 JVM 기본 타임존을 세션 TimeZone으로 밀어 넣으므로, 서버 timezone을 UTC로 맞춰도 앱 세션은 JVM 존을 따라간다. 안전망은 선택과 한 세트다 — -Duser.timezone=UTC, hibernate.jdbc.time_zone=UTC, ALTER DATABASE … SET timezone='UTC', Instant 타입 규약을 ArchUnit으로, 그리고 값뿐 아니라 컬럼 타입이 정말 timestamptz인지까지 단정하는 회귀 테스트.
  • 1
    두 타입은 "저장하는 것" 자체가 다르다 — timestamptz는 이름과 달리 타임존을 저장하지 않고, 입력을 세션 TimeZone으로 해석해 UTC 순간 하나(8바이트 정수 하나)로 정규화해 적는다. timestamp는 변환 없이 벽시계를 그대로 적어 "어느 존의 09:00이었는지"를 버린다. 그래서 timestamptz는 순간을, timestamp는 벽시계를 저장한다.
  • 2
    PostgreSQL에서는 선택 축이 하나만 남는다 — 두 타입이 같은 8바이트·같은 마이크로초·같은 범위라 MySQL을 갈랐던 2038년 한계와 크기 저울질이 아예 성립하지 않는다. 남는 축은 "정규화를 DB가 강제하느냐, 앱이 규약으로 지키느냐" 하나이고, 그래서 답이 단정적이다 — 과거·현재의 사건은 timestamptz + 자바 Instant, timestamp는 벽시계가 곧 의도인 미래 일정에 IANA 존 ID와 짝으로만 남긴다.
  • 3
    대신 PostgreSQL 고유의 함정 셋을 붙여 말한다 — ① 출력이 읽는 세션의 존을 따라 달라져 날짜까지 하루 밀려 보이므로 판정은 AT TIME ZONE 'UTC'로 못 박는다 ② now()는 트랜잭션 시작 시각이라 한 배치의 1만 건이 같은 값이 되고 커서 페이지네이션·증분 동기화가 행을 흘린다 ③ pgjdbc가 세션 TimeZone을 JVM 존으로 설정하므로 -Duser.timezone=UTC 한 줄이 곧 세션 설정이다. 이 셋을 설정 · 타입 규약(ArchUnit) · 회귀 테스트 세 층으로 못 박는다.

0. 질문 + 출제 의도

질문: "DATETIME과 TIMESTAMP의 차이(타임존 동작, 범위)는? 글로벌 서비스라면 무엇을 선택하겠습니까?"

출제 의도: 타임존 처리·범위(2038년 문제)·기본값 동작의 차이는 22장의 시간 원칙이 스키마 레벨에 착지하는 지점이다. 컬럼 타입 선택 하나가 글로벌 확장의 발목을 잡는 사례를 아는지 본다.

채점 지점은 "스펙 암기"가 아니라 셋이다 ⑴ 값이 저장되고 읽히는 변환 경로를 사슬로 말할 수 있는가 — 그래야 "어디가 어긋나면 몇 시간 밀리는지"를 겪지 않고도 예측한다.
⑵ 두 타입의 얻는 것과 내는 것을 양면으로 조립해 "우리 서비스의 조건"으로 결론을 내는가.
⑶ 선택을 설정·타입 규약·테스트로 고정하는가 — "UTC로 저장하기로 했다"는 결정은 코드로 못 박기 전까지 언젠가 깨질 관례일 뿐이다.
PostgreSQL로 물으면 ⑵의 무게가 달라진다 MySQL에서는 범위(2038)와 크기가 결론을 갈랐지만, PostgreSQL은 두 타입이 같은 8바이트·같은 범위라 그 축이 사라진다. 그래서 답이 더 단정적이어야 하고, 대신 "왜 그런데도 timestamp가 남아 있는가"(미래 일정)와 PostgreSQL 특유의 함정 셋(세션 TimeZone · now() · pgjdbc)을 말할 수 있어야 변별된다.

1. 비유부터 — 항해일지와 벽시계 사진

timestamptz = 항해일지

선원은 현지 시각으로 적지만 일지에는 세계 표준시(UTC)로 환산해 기록하고, 읽는 사람은 자기 항구의 시각으로 되돌려 본다. 어느 항구에서 읽어도 "같은 순간"을 가리킨다.

중요한 건 일지에 "어느 항구에서 적었는지"는 안 남는다는 점이다 — 환산 결과인 UTC만 남는다.

timestamp = 벽시계를 찍은 사진

숫자는 정확히 남지만, 사진 어디에도 "어느 도시의 벽시계"인지는 없다.

사진을 찍은 사람이 "서울이었다"고 기억하는 동안만 의미가 유지되고, 그 사람이 떠나면(코드가 바뀌면, 서버가 옮겨가면) 숫자는 남고 기준은 사라진다.

면접에서 "timestamptz는 타임존 변환이 있고 timestamp는 없다"라고 결과만 말하는 것과, 어느 단계에서 어느 시계로 변환되는지를 순서대로 말하는 것이 이 질문의 첫 변별점이다. 그래서 아래 그림 한 장을 먼저 세운다 — 이 페이지의 나머지는 전부 이 그림의 각주다.

이 두 문장을 통째로 외운다 — 나머지는 전부 여기서 파생된다

timestamptz = "순간을 저장하고, 존은 입출력에서만 쓴다"
timestamp = "벽시계를 저장하고, 존은 아예 모른다"

그래서 timestamptz 컬럼을 보고 "몇 시로 저장돼 있나요?"는 잘못된 질문이다 — 답이 보는 사람의 세션에 달려 있기 때문이다. 올바른 질문은 "어느 순간인가요?"이고, 그 답은 AT TIME ZONE 'UTC'로 못 박아야 한다.

2. 사슬 ① timestamptz — 이름이 거짓말한다 최다 오답

이 문항에서 가장 흔한 오답이 "timestamptz는 타임존까지 같이 저장한다"이다. 그런데 "타임존을 저장하지 않는다"를 먼저 던지면 대부분 "그럼 대체 뭘 저장하는데?"에서 막힌다. 순서를 뒤집어서, 먼저 무엇이 있고 그다음 무엇이 없는지로 가는 편이 이해가 빠르다.

Q1
그럼 무엇을 저장하는가 — UTC 순간 하나, 8바이트 정수 하나. timestamptz 컬럼 한 칸에 들어 있는 것은 "2000-01-01 00:00:00 UTC로부터 몇 마이크로초 지났는가"라는 부호 있는 64비트 정수 딱 하나다. 다른 칸은 없다. 존 이름을 담을 자리도, 오프셋을 담을 자리도 물리적으로 존재하지 않는다.
Q2
그럼 출력에 붙는 +09는 어디서 오는가 — 읽는 세션의 TimeZone 설정에서. 저장된 정수를 사람이 읽을 문자열로 바꿀 때, PostgreSQL은 그 순간 이 세션의 TimeZone 파라미터를 보고 환산해 표기를 붙인다. 그러니까 +09는 데이터가 들고 온 정보가 아니라, 지금 이 세션이 쓴 번역기의 상표다.
∴
여기까지 세우고 나면 "이름이 거짓말한다"가 충격이 아니라 당연한 귀결이 된다. with time zone이라는 이름은 "타임존을 저장한다"가 아니라 "타임존을 의식한다"는 뜻으로 읽어야 한다 — 입력을 해석할 때 한 번, 출력을 만들 때 한 번, 존을 쓴다. 그 사이에 남는 것은 존이 사라진 UTC 정수뿐이다.

2-1. 실험 한 번이면 끝난다

실험 같은 리터럴, 세션만 바꿔서 두 번 읽기
-- 오해: "with time zone 이니까 '+09' 가 값에 남겠지"
SET timezone = 'UTC';
SELECT '2026-08-31 09:00:00+09'::timestamptz;
--   2026-08-31 00:00:00+00
--   ↑ 입력의 +09 는 "해석"에만 쓰이고 사라졌다.
--     출력의 +00 은 "저장된 존"이 아니라 "지금 이 세션의 존"이다.

-- 증명: 값은 그대로인데 보이는 문자열만 세션을 따라 바뀐다
SET timezone = 'Asia/Seoul';
SELECT '2026-08-31 09:00:00+09'::timestamptz;
--   2026-08-31 09:00:00+09     ← 같은 순간, 다른 표기

2-2. 같은 한 칸을 세 세션으로 읽으면 — 날짜까지 바뀐다

저장된 정수는 전 행이 동일하다는 것이 이 표의 전부다.

저장된 것은 왼쪽 한 칸뿐. 오른쪽 두 열은 "번역기"가 만든 결과일 뿐이다.
저장된 8바이트 정수
(2000-01-01 00:00:00 UTC 기준 마이크로초)		읽는 세션의 TimeZone보이는 문자열
841449600000000UTC2026-08-31 00:00:00+00
841449600000000Asia/Seoul (UTC+9, 서머타임 없음)2026-08-31 09:00:00+09
841449600000000America/Los_Angeles (8월은 서머타임 중 = UTC-7)2026-08-30 17:00:00-07 ← 하루가 넘어갔다
검산 — 이 숫자는 외우는 게 아니라 세우는 것이다 2026-08-31 00:00:00Z는 PostgreSQL 기준점(2000-01-01 00:00:00 UTC)에서 9,739일 = 841,449,600초 뒤이고, 마이크로초로 접으면 841,449,600,000,000이다. 여기에 서울은 +9시간이라 같은 날 09:00, 로스앤젤레스는 8월이면 서머타임이 적용돼 -7시간이라 하루가 넘어가 전날 17:00이 된다.

2-3. 두 타입을 한 테이블에 나란히 두고 보기

면접에서 이 실험을 말로 재현할 수 있으면 "스펙을 외운 사람"과 갈린다.

준비 세션만 다르게 해서 똑같은 문자열을 두 번 넣는다
CREATE TABLE tz_demo (
    id    int,
    wall  timestamp,      -- 벽시계 값 그대로
    inst  timestamptz     -- UTC 순간으로 정규화
);

-- ⑴ 서울 세션에서 한 건
SET timezone = 'Asia/Seoul';
INSERT INTO tz_demo VALUES (1, '2026-08-31 09:00:00', '2026-08-31 09:00:00');

-- ⑵ UTC 세션에서 한 건 — 문자열은 ⑴과 글자 하나 다르지 않다
SET timezone = 'UTC';
INSERT INTO tz_demo VALUES (2, '2026-08-31 09:00:00', '2026-08-31 09:00:00');
before 세션 UTC로 읽는다
SET timezone = 'UTC';
SELECT id, wall, inst FROM tz_demo;

 id |        wall         |          inst
----+---------------------+------------------------
  1 | 2026-08-31 09:00:00 | 2026-08-31 00:00:00+00
  2 | 2026-08-31 09:00:00 | 2026-08-31 09:00:00+00

↑ wall 은 두 행이 같다(변환이 없으니 당연).
  inst 는 9시간 다르다.

  "같은 INSERT 문자열인데 저장된 순간이 다르다"
  가 사슬 ⑵(세션 존으로 해석)의 증거다.
after 세션만 바꿔 다시 읽는다 — 데이터는 한 글자도 안 건드렸다
SET timezone = 'Asia/Seoul';
SELECT id, wall, inst FROM tz_demo;

 id |        wall         |          inst
----+---------------------+------------------------
  1 | 2026-08-31 09:00:00 | 2026-08-31 09:00:00+09
  2 | 2026-08-31 09:00:00 | 2026-08-31 18:00:00+09

↑ wall 은 세션을 바꿔도 요지부동
  — "타임존 무관"의 정확한 의미.

  inst 만 표기가 바뀐다
  — 값이 바뀐 게 아니라 번역기가 바뀐 것.

timestamptz 사슬 4단계 — 이 순서로 말한다

⑴ 리터럴에는 존이 없다→ ⑵ 세션 TimeZone으로 해석→ ⑶ UTC 순간 하나로 저장→ ⑷ 읽는 세션 존으로 표기
  • 얻는 것: 세션 존이 무엇이든 저장은 UTC 순간 하나 — 규율이 DB에 있다.
  • 내는 것: 세션 존이 어긋나면 오프셋 없는 리터럴의 해석이 밀린다. (드라이버가 OffsetDateTime으로 보내면 이 위험이 사라진다 — 7절의 결정타)
  • 출력이 세션을 따라가므로 "콘솔에서 본 숫자"로 사고를 판정하면 안 된다.
  • 비교·정렬·인덱스는 저장된 UTC 정수 기준이라 세션 존과 무관하게 일관된다. SET timezone을 바꿔도 인덱스 순서나 WHERE 결과는 안 바뀐다.

3. 사슬 ② timestamp — 변환 없음, 그래서 타임존 정보가 사라진다

⑴ 리터럴 도착→ ⑵ 해석도 변환도 없음 (+09도 무시)→ ⑶ 읽을 때도 그대로→ ⑷ "어느 존의 09:00"인지는 값 어디에도 없다

그 정보는 값을 넣은 코드의 머릿속(LocalDateTime.now()를 부른 JVM의 기본 존)에만 있었고, 저장되는 순간 소실됐다. 따라서 timestamp를 쓰는 순간 "이 컬럼의 값은 UTC 벽시계다"라는 규약은 DB가 아니라 애플리케이션이 지켜야 한다. DB는 KST 벽시계가 들어와도 막지 않는다. 이것이 timestamp가 내는 가장 큰 비용이고, 9절의 안전망이 전부 이 비용을 갚기 위한 것이다.

함정 — "timestamp는 타임존과 무관하니 설정은 아무래도 된다"는 반쪽 이해다

timestamp 컬럼에 DEFAULT now()를 걸면 세션 존의 벽시계가 들어간다. now()가 돌려주는 값은 timestamptz(순간)인데, 이걸 timestamp 컬럼에 넣으려면 벽시계로 낮춰야 하고, 그 낮추는 기준이 세션 존이기 때문이다.

앱은 UTC를 넣고 DB 기본값은 KST를 넣는 "한 컬럼 두 기준"이 조용히 생긴다
→ timestamp를 골라도 세션 존은 UTC로 맞춰야 한다
타입이 섞이면 비교에서 승격이 일어난다 가산점 timestamp 컬럼을 timestamptz(예: now())와 비교하면, 벽시계와 순간은 애초에 비교할 수 없는 서로 다른 것이므로 PostgreSQL이 좌변을 세션 TimeZone으로 해석해 timestamptz로 승격한 뒤 비교한다. 즉 한쪽만 timestamp인 순간, 그 비교 결과는 세션 존에 따라 달라진다. 7절의 사고 ①이 정확히 이 지점에서 터진다 — "배치를 앱이 돌리느냐 cron이 psql로 돌리느냐"에 따라 결과가 달라지는 그 사고다.

5. AT TIME ZONE — 값을 바꾸는 게 아니라 타입을 뒤집는 연산자

이걸 "타임존 변환 함수"로만 알면 반쪽이다. 핵심은 입력 타입에 따라 출력 타입이 반대로 뒤집힌다는 것이다. 이름이 하나뿐이라 방향을 헷갈리기 쉬우니, 양방향을 나란히 놓고 각각 언제 쓰는지까지 붙여서 외운다.

방향식읽는 법결과 타입언제 쓰나
내림 (순간 → 벽시계)timestamptz AT TIME ZONE 'Asia/Seoul'"이 순간은 서울에서 몇 시인가"timestamp (벽시계)리포트·화면 표시, 존별 하루 경계로 집계, 검증 SQL에서 AT TIME ZONE 'UTC'로 기준 고정
올림 (벽시계 → 순간)timestamp AT TIME ZONE 'Asia/Seoul'"이 벽시계를 서울 시각으로 읽으면 어느 순간인가"timestamptz (순간)미래 일정의 원본(로컬 벽시계 + 존 ID)에서 UTC 파생 컬럼 계산, 옛 timestamp 컬럼의 마이그레이션
예시 두 방향을 실제 값으로
SET timezone = 'UTC';

-- ⑴ 내림: 순간 → 벽시계 (표시·리포트용). 존을 명시했으므로 세션과 무관하다
SELECT paid_at AT TIME ZONE 'Asia/Seoul' AS seoul_wall FROM payment;
--   2026-08-31 09:00:00      ← 타임존 표기(+09)가 사라진 것에 주목: timestamp 다
--   쓰임새: "서울 기준으로 언제 결제됐나"를 사람에게 보여 줄 때.
--          세션이 UTC든 LA든 이 값은 안 흔들린다.

-- ⑵ 올림: 벽시계 → 순간 (미래 일정의 원본에서 UTC를 계산할 때)
SELECT publish_local_at AT TIME ZONE publish_zone_id AS publish_at_utc
FROM episode_schedule;
--   2026-09-01 14:00:00+00   ← 이제 timestamptz 다
--   검산: 서울(UTC+9) 벽시계 2026-09-01 23:00 → 9시간을 빼면 같은 날 14:00 UTC.
--   쓰임새: "밤 11시 공개"라는 규칙에서 스캐너가 쓸 실제 순간을 뽑을 때.

6. now()는 "지금"이 아니다 — 트랜잭션 시작 시각 PG 고유

PostgreSQL에서 가장 자주 사람을 무는 함정이고, MySQL 경험만으로는 예측할 수 없는 동작이다.

함수언제의 시각인가트랜잭션 안에서 여러 번 부르면
now() = CURRENT_TIMESTAMP = transaction_timestamp()트랜잭션이 시작된 시각전부 같은 값
statement_timestamp()현재 문장이 시작된 시각문장마다 다른 값
clock_timestamp()실제로 함수가 호출된 순간부를 때마다 다른 값

3형제 암기 — 트 · 문 · 클

트랜잭션 = now()· 문장 = statement_timestamp()· 클럭 = clock_timestamp()

왜 이렇게 만들었는가부터 짚으면 외우기 쉽다. 한 트랜잭션은 "한 시점의 세계"라는 것이 트랜잭션의 정의에 가깝기 때문이다. 같은 트랜잭션 안에서 now()를 부를 때마다 값이 달라지면 "이 트랜잭션이 만든 행들의 시각"이 제각각이 되어 원자성이라는 착시가 깨진다. PostgreSQL은 일관성을 택했고, 그 대가로 아래 사고가 생긴다.

before 트랜잭션이 길면 now()는 과거를 가리킨다
BEGIN;
--  … 외부 API 호출·대량 계산으로 10분 경과 …
INSERT INTO payment (paid_at) VALUES (now());
COMMIT;

--   저장된 paid_at 은 실제 결제 시각보다 10분 이르다.
--   "created_at 이 실제 삽입 시각보다 과거"라는 제보의 정체.
after 실제 순간이 필요하면 clock_timestamp()
INSERT INTO payment (paid_at) VALUES (clock_timestamp());

--   "함수가 호출된 그 순간"이 박힌다.
--   감사 시각·수정 시각처럼 "실제 순간"이 의도인
--   컬럼은 이쪽이 맞다.

--   ※ 다만 커밋 순서와의 어긋남은 여전히 남는다
--     (아래 사고 B 참고) — 그래서 근본 처방은 CDC.

6-1. 그래서 무슨 사고가 나는가 — 배치 1만 건이 전부 같은 시각을 갖는다

정산 배치가 한 트랜잭션에서 1만 건을 INSERT하고 created_at이 DEFAULT now()라면, 그 1만 행의 created_at은 글자 하나 다르지 않은 같은 값이 된다. "1만 건이 같은 밀리초에 들어갔을 리 없다"는 직관이 여기서 배신당한다. 그리고 이 뭉친 값이 두 군데에서 정확히 터진다.

처방은 세 갈래 — 마지막이 근본 처방이다

① lookback
폴링 경계에 여유를 둔다 — 마지막 처리 시각에서 최대 트랜잭션 길이만큼 되돌려 겹쳐 읽고, 중복은 멱등 처리로 흡수한다.
② clock_timestamp()
updated_at을 실제 호출 순간으로 찍는다. 다만 커밋 순서와의 어긋남은 트랜잭션 길이만큼 그대로 남는다.
③ 논리 디코딩 CDC
타임스탬프가 아니라 커밋 순서 자체를 따르게 한다. 근본 처방은 이것이다.
MySQL 대조 — "PostgreSQL로 옮기고 나서 증분 배치가 이상해졌다"의 정체 MySQL의 NOW()는 문장이 시작된 시각이라 같은 트랜잭션 안이라도 문장마다 값이 다르다(실제 호출 시각이 필요하면 SYSDATE()). 즉 위 사고는 MySQL에서는 잘 안 나고 PostgreSQL에서만 나는 부류다. 다만 "MySQL이면 안전하다"는 아니다 — 한 문장으로 1만 건을 INSERT하면 MySQL에서도 그 1만 건은 같은 값이고, 커밋 순서와 타임스탬프 순서가 어긋나는 것도 그대로다. PostgreSQL은 그 창을 트랜잭션 길이만큼 크게 벌릴 뿐이다.

6-2. 자동 갱신 — ON UPDATE CURRENT_TIMESTAMP가 없다

DEFAULT now()(또는 DEFAULT clock_timestamp())는 그대로 쓸 수 있다. 없는 것은 UPDATE 시 자동 갱신이다.

MySQL이 주던 것

updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP 한 줄로 DB 레벨 자동 갱신. 벌크 UPDATE·네이티브 쿼리·콘솔 수동 SQL처럼 JPA Auditing이 빠지는 경로에서도 살아 있다.

덤으로 explicit_defaults_for_timestamp=OFF인 옛 설정에서는 첫 TIMESTAMP 컬럼에 이 동작이 묵시로 붙고 NULL 대입이 현재 시각이 되는 마법까지 있었다.

PostgreSQL에서는 트리거로 직접 만든다

자동 갱신도, 묵시 마법도 없다. 문법이 한 줄 더 들 뿐, 조건을 붙일 수 있어 오히려 세밀하다.

트리거가 DB 레벨이라는 점이 요점 — @Modifying 벌크 UPDATE, 네이티브 쿼리, psql 수동 SQL에서도 동작해 JPA Auditing의 구멍을 메운다.

good BEFORE UPDATE 트리거로 updated_at 자동 갱신
CREATE OR REPLACE FUNCTION touch_updated_at() RETURNS trigger AS $$
BEGIN
    -- now() 를 쓰면 트랜잭션 시작 시각이 박힌다. "수정된 순간"이 의도라면 clock.
    NEW.updated_at := clock_timestamp();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_payment_touch
    BEFORE UPDATE ON payment
    FOR EACH ROW
    -- 값이 실제로 바뀔 때만 — 같은 값으로 덮어쓰는 UPDATE 에는 안 붙는다.
    -- IS DISTINCT FROM 을 쓰는 이유: NULL <> NULL 은 NULL(=거짓 취급)이라
    -- 평범한 <> 로는 "NULL 이 값으로 바뀐" 변경을 놓친다.
    WHEN (OLD.* IS DISTINCT FROM NEW.*)
    EXECUTE FUNCTION touch_updated_at();

7. 네 개의 시계와 사고 사슬 두 개 — "앱에서는 맞는데 psql에서 보면 9시간 다르다"

Instant(또는 LocalDateTime) 하나가 컬럼에 적힐 때까지 네 개의 시계를 지난다. 각 시계가 어디에 있고 무엇을 결정하는지부터 세운다.

7-1. 값 하나를 끝까지 따라가 본다 — 경로 A vs 경로 B

말로만 읽으면 어느 단계에서 값이 바뀌는지 안 잡힌다. 서울 시각으로 09:00에 결제가 일어났고, 앱은 컨테이너에서 돌고 있다고 하자.

경로 A Instant + timestamptz — 권장 조합
① JVM (user.timezone=UTC)
     Instant.now()  →  2026-08-31T00:00:00Z
       "순간" 자체. 존이 없는 값이다.
        (서울 09:00 = UTC 00:00. 한국은 서머타임이
         없어 항상 +9)
       │
       ▼

     Instant 를 OffsetDateTime(…+00) 으로 넘긴다

     — 오프셋이 이미 값 안에 있으므로
       │
       ▼

     리터럴에 오프셋이 붙어 있으므로

7-2. 사고 사슬 두 개

사고 ①: LocalDateTime + timestamp 컬럼 + 배치의 now(). 국내 서비스. 결제 시각은 paidAt = LocalDateTime.now()로 채우고 timestamp 컬럼에 저장한다. 30분 넘게 미완료인 결제를 정리하는 배치는 SQL로 WHERE status = 'PENDING' AND created_at < now() - interval '30 minutes'.

⑴ LocalDateTime.now() = 시계 ①(KST)의 벽시계 09:00→ ⑵ timestamp에 변환 없이 기록, 존 정보 소실→ ⑶ 배치의 now()는 timestamptz(진짜 순간)
⑷ timestamp < timestamptz 비교 → 좌변이 읽는 세션 존으로 승격→ ⑸ 배치의 정확성이 "누가 실행하느냐"에 달린다
⑸의 실제 모습 앱(세션 KST)이 돌리면 우연히 맞고, cron이 psql(세션 UTC)로 돌리면 KST 벽시계 09:00이 UTC 09:00으로 해석돼 기준선보다 9시간 미래가 되어 아무것도 정리하지 않는다. ⑹ 로컬 개발에서는 앱도 psql도 다 KST라 완벽히 동작했으므로 테스트도 통과했다.

그리고 두 번째 파도가 온다. 앱을 컨테이너로 옮기면서 시계 ①이 UTC가 되면, 그날 배포 시점부터의 행은 UTC 벽시계, 그 이전 행은 KST 벽시계가 한 컬럼에 섞인다. 어느 행이 어느 기준인지는 배포 시각으로 추정하는 수밖에 없고, 그 경계 근처의 데이터는 영영 애매하다. timestamp가 존 정보를 버린 대가는 "값을 복구할 근거가 없다"로 청구된다.

사고 ②: Instant인데 컬럼이 timestamp — 왕복에서 상쇄돼 앱에선 안 보인다. 엔티티는 제대로 Instant를 쓴다. 그런데 스키마가 Hibernate 자동 생성이거나, 마이그레이션 스크립트에 timestamp로 적혀 있다. hibernate.jdbc.time_zone은 안 줬다.

⑴ Instant를 timestamp에 넣으려면 벽시계로 낮춰야 한다 — 기준은 시계 ②(= JVM 존 KST)
⑵ 진짜 순간 00:00Z가 '09:00'이라는 KST 벽시계로 저장→ ⑶ 읽을 때도 같은 기준으로 되돌리므로 앱이 받는 값은 정확히 00:00Z
⑷ 틀린 값은 이 경로를 거치지 않는 모든 곳에서만 보인다 psql · now()와 비교하는 SQL 배치 · 파이썬 정산 스크립트 · BI 도구 · 레플리카에서 뽑는 리포트. ⑸ 발견은 몇 달 뒤 "정산 금액이 하루치씩 어긋난다"는 제보로 온다.
두 사고의 공통 구조 — 어긋난 시계 한 쌍이 왕복에서 서로 상쇄되면 앱은 정상으로 보이고,
제3의 독자(psql·배치·타 언어)가 나타날 때 드러난다
그리고 둘 다 컬럼 타입이 timestamptz였으면 애초에 일어나지 않았다 — 9절의 회귀 테스트가 값뿐 아니라 컬럼 타입까지 단정하는 이유다.

7-3. 트레이드오프 양면 — 면접관은 반대편 비용을 빠뜨리지 않는지를 본다

timestamptz가 얻는 것

  • UTC 정규화를 DB가 강제한다 — 자바든 파이썬이든 psql이든 넣는 순간 순간(instant)이 된다. 규율이 스키마에 있다.
  • 드라이버가 오프셋을 명시해 보내므로 시계가 어긋나도 저장이 안 밀린다 — 운영 실수에 대한 내성.
  • 타입 자체가 "순간"이라 컬럼의 의미가 DDL에 드러난다.
  • 비교·정렬·인덱스가 세션 존과 무관하게 일관된다.
  • 읽는 쪽이 자기 존으로 보게 하는 표시 변환이 공짜다.

timestamptz가 내는 것

  • 출력이 세션 존에 따라 달라져 디버깅이 헷갈린다 — psql과 BI의 숫자가 다를 수 있고 날짜까지 달라진다. "몇 시로 저장돼 있나"라는 질문 자체가 성립하지 않는다.
  • ::date·date_trunc 계열 연산이 세션 존에 의존해 그대로 쓰면 인덱스를 못 타고 조용히 풀스캔이 된다(8-2).
  • 이름이 오해를 부른다 — "존이 저장되니 미래 일정도 그냥 넣으면 되겠지"라는 잘못된 안도감.
  • DST가 있는 존을 세션에 쓰면 벽시계 → 순간 변환이 1:1이 아닌 시간대가 생긴다(전환일의 중복 1시간, 존재하지 않는 1시간).

timestamp가 얻는 것

  • 세션 존 무관 — psql에서 보이는 값이 곧 저장된 값이라 예측 가능하고, 누가 어디서 읽어도 같은 숫자다.
  • "벽시계가 의도"인 값을 왜곡 없이 담는다 — 미래 일정의 원본, DST가 개입하면 안 되는 값.
  • 존 변환이 없어 연산이 단순하다.

timestamp가 내는 것

  • 타임존 정보가 없다 — "이 컬럼은 UTC"라는 규약이 코드·설정·리뷰 규칙에 있어야 하고, 깨져서 KST 벽시계가 들어와도 DB는 못 잡는다.
  • 그 결과 사고가 나면 복구 근거가 값에 없다.
  • now()·timestamptz와 비교하는 순간 세션 존이 결과를 바꾼다.
  • DEFAULT now()가 세션 존 벽시계를 넣으므로 결국 세션 존도 UTC로 맞춰야 한다 — "타임존 무관"이 "설정 무관"은 아니다.

둘 다 내야 하는 것 — 그리고 결론을 정하는 비대칭

시계 정합. 어느 타입을 골라도 이 비용이 0이 되지는 않는다. 차이는 정합이 깨졌을 때 무엇이 틀리는가다.

timestamptz가 틀릴 때
보이는 표기만 틀린다 — 값은 무사하다. 설정을 고치면 그대로 정상으로 돌아온다.
timestamp가 틀릴 때
저장된 값의 기준이 틀린다 — 복구 불가. 어느 행이 어느 기준인지 값이 모른다.
이 비대칭이 PostgreSQL에서 결론을 정한다

8. 결론 — "글로벌 서비스라면"에 대한 답은 컬럼의 성격별로 나뉜다

시각 컬럼을 한 종류로 보지 않는 것이 출발점이다. 과거·현재의 사건과 미래의 일정은 저장해야 할 것이 다르다.

8-1. (a) 과거·현재의 사건에 timestamptz인 근거 셋

⑴ 규율이 DB에
DB가 정규화를 강제하므로 앱 규율이 깨져도 순간이 안 틀린다 — psql로 손댄 데이터도, 파이썬 배치가 넣은 데이터도 같은 기준이 된다.
⑵ 낼 대가가 없다
범위·크기가 timestamp와 같아 반대편에 낼 대가가 없다 — MySQL에서 DATETIME을 고르게 만들던 2038·1바이트 근거가 PostgreSQL에는 존재하지 않는다.
⑶ 실수에 대한 내성
시계가 어긋나도 저장이 안 밀린다. 운영에서 실수는 반드시 일어나므로, 실수했을 때 "표기만 틀리는" 쪽을 고르는 것이 설계다.
MySQL이었다면 결론이 뒤집힌다 — 이 문장을 붙이면 "근거에서 다시 도출한" 것으로 들린다 MySQL에서는 TIMESTAMP의 2038 한계와 묵시 DEFAULT 이력 때문에 DATETIME(6) + 네 시계 UTC 고정 + 앱 규율을 고르는 것이 합리적이었다. PostgreSQL은 timestamptz에서 그 두 대가가 사라지므로 같은 논리가 정반대 결론에 착지한다.

8-2. (b) 미래 일정을 분해 저장하는 이유

사용자가 의도한 것은 "그 도시의 벽시계로 23:00"이지 특정 UTC 순간이 아니다. 지금 UTC로 환산해 저장하면 DST 전환이나 그 나라의 DST 폐지(tzdata 변경)로 환산 결과가 바뀌는 순간 의도와 어긋난다.

원본: 로컬 벽시계 timestamp+ IANA 존 ID text⇒ 파생 캐시: timestamptz (정렬·스캔용, 언제든 AT TIME ZONE으로 재계산)
왜 오프셋(+09:00)이 아니라 존 ID(Asia/Seoul)인가 오프셋은 "지금의 결과"일 뿐 규칙을 못 담는다. 존 ID는 규칙 자체(그 나라가 언제 DST를 켜고 끄는지)를 가리키므로, tzdata가 갱신되면 같은 존 ID가 새 규칙으로 다시 계산된다. timestamptz가 존을 저장한다고 오해하면 이 설계를 건너뛰게 되고, tzdata가 바뀌는 날 예약 시각 전체가 조용히 틀어진다.

8-3. (d) 구간 — EXCLUDE 제약 가산점

EXCLUDE는 "이 조건들을 동시에 만족하는 두 행이 존재하면 거부한다"는 제약으로, 유니크 제약을 등호가 아닌 임의 연산자로 일반화한 것이다.

good 겹침 검사를 앱이 아니라 제약이 한다
CREATE EXTENSION IF NOT EXISTS btree_gist;   -- 스칼라 = 비교를 GiST 에서 쓰려면 필요

CREATE TABLE reservation (
    id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    room_id bigint      NOT NULL,
    period  tstzrange   NOT NULL,
    -- 같은 방(room_id =)에서 기간이 겹치면(&&) 아예 INSERT 가 거부된다.
    -- 앱의 "조회 후 없으면 INSERT" 경쟁을 제약으로 대체한다.
    EXCLUDE USING gist (room_id WITH =, period WITH &&)
);

8-4. 따라오는 실무 함정 — timestamptz에 ::date를 씌우면 두 번 진다

timestamptz를 고르면 따라오는 함정이 하나 있다. "오늘 매출"류의 일 단위 집계다. "두 번 진다"의 두 번이 각각 무엇인지부터 나눠서 못 박는다.

1
첫 번째 패배 — 컬럼에 함수/캐스트를 씌우면 인덱스를 못 탄다. 인덱스는 paid_at 값 자체로 정렬돼 있는데, 조건이 요구하는 것은 paid_at::date라는 가공된 값이다. 인덱스에는 그 가공된 값이 없으므로 옵티마이저는 모든 행을 읽어 하나씩 캐스트해 볼 수밖에 없다 → Seq Scan. 여기까지는 PostgreSQL만의 이야기가 아니라 인덱스의 일반 원리다.
2
두 번째 패배 — 이 식은 그대로는 표현식 인덱스로 만들 수도 없다. 보통 첫 번째 패배는 "가공된 값 자체를 인덱스로 만들어" 우회한다. 그런데 timestamptz → date 캐스트는 세션 TimeZone에 따라 결과가 달라지는 STABLE 함수다. 인덱스는 "언제 어디서 계산해도 같은 값"을 전제로 디스크에 값을 굳혀 두는 구조이므로, PostgreSQL은 IMMUTABLE 함수만 인덱스 식으로 받는다 → functions in index expression must be marked IMMUTABLE로 거부된다. MySQL에서 DATE(col) 함수 인덱스로 넘기던 습관이 여기서 통하지 않는다.
+
덤으로 세 번째 — '2026-08-31'이 어느 존의 하루인지가 세션 설정에 숨는다. 같은 쿼리가 psql(세션 UTC)과 앱(세션 KST)에서 다른 답을 낸다. 쿼리 텍스트만 봐서는 그 사실을 알 수 없다는 것이 가장 나쁘다.
before 컬럼에 캐스트를 씌운다
SELECT sum(amount) FROM payment
WHERE paid_at::date = DATE '2026-08-31';

 Seq Scan on payment  (actual rows=1204 loops=1)
   Filter: ((paid_at)::date = '2026-08-31'::date)
   Rows Removed by Filter: 4,318,796
   Buffers: shared read=61,204

↑ 431만 행을 읽어 1,204행을 건졌다.
  필요한 것의 3,600배를 읽은 셈.

  게다가 이 식은 표현식 인덱스로도 못 만든다
  (STABLE 이라 IMMUTABLE 요구를 못 맞춘다).
after 경계를 앱이 "비즈니스 존"으로 계산해 UTC 순간으로 바인딩
SELECT sum(amount) FROM payment
WHERE paid_at >= $1 AND paid_at < $2;  -- OffsetDateTime(UTC)

 Index Scan using idx_payment_paid_at on payment
   Index Cond: ((paid_at >= $1) AND (paid_at < $2))
   (actual rows=1204 loops=1)
   Buffers: shared hit=38

↑ 61,204 버퍼 → 38 버퍼.
  컬럼이 맨몸이라 인덱스 범위 탐색이 되고,
  경계 계산이 앱 코드에 드러나
  "무슨 존의 하루인가"가 리뷰에서 보인다.

  ※ >= 와 < 로 반열린 구간을 쓰는 이유:
    BETWEEN 은 양끝을 포함하므로 자정 정각에
    찍힌 행이 이틀에 중복으로 잡힌다.
good 경계 계산은 자바 쪽에서 — 존이 코드에 명시되는 것이 요점
ZoneId biz = ZoneId.of("Asia/Seoul");                  // 비즈니스 존을 명시
LocalDate day = LocalDate.of(2026, 8, 31);
Instant from = day.atStartOfDay(biz).toInstant();      // 2026-08-30T15:00:00Z
Instant to   = day.plusDays(1).atStartOfDay(biz).toInstant();  // 2026-08-31T15:00:00Z
// 서울은 UTC+9 이므로 "서울의 8/31 하루"는 UTC 로 8/30 15:00 ~ 8/31 15:00 이다.
// DST 가 있는 존이라면 atStartOfDay 가 23시간/25시간짜리 하루를 알아서 처리한다 —
// 이것이 "앱이 계산해서 넘긴다"의 진짜 이득이다. SQL 로는 이 처리를 흉내 내기 어렵다.
가산점 — 그래도 SQL 안에서 존별 하루를 다뤄야 한다면 존을 상수로 박아 date_trunc('day', paid_at AT TIME ZONE 'Asia/Seoul')처럼 쓴다. 그리고 이 식은 표현식 인덱스로 만들 수 있다. 이유는 함수 변동성 표시가 갈리기 때문이다 — AT TIME ZONE에 존을 리터럴로 준 형태는 IMMUTABLE로 표시돼 있고(세션 설정을 안 보므로), 그것이 돌려주는 timestamp에 대한 date_trunc도 IMMUTABLE이다. 반면 존 없이 timestamptz에 바로 거는 date_trunc('day', paid_at)이나 paid_at::date는 세션 의존이라 STABLE이고 거부된다.
"존을 명시하면 인덱스가 되고, 세션에 맡기면 안 된다"
다만 이 우회에는 대가가 둘 있다. ⑴ 존이 인덱스에 박힌다 — 서울용·LA용 인덱스를 따로 만들어야 하고, 글로벌 서비스에서는 이게 곧 인덱스 개수 폭발이다. ⑵ IMMUTABLE 표시는 "tzdata가 안 바뀐다"는 가정 위의 실용적 약속이라, 그 존의 규칙이 실제로 바뀌면 인덱스에 굳어 있는 값이 현실과 어긋나 REINDEX가 필요하다. 그래서 정석은 여전히 위 after의 UTC 경계 범위 조건이다 — 인덱스 하나로 모든 존을 커버하고, tzdata 변경에도 영향을 안 받는다.

interval 산술의 DST 함정도 같은 계열이다 가산점

+ interval '1 day'
세션 존의 달력 기준 하루를 더한다 → DST 전환일에는 23시간 또는 25시간. "매일 같은 시각"이 의도면 이쪽.
+ interval '24 hours'
정확히 24시간. "정확히 하루 뒤 순간"이 의도면 이쪽.

둘이 다르다는 것을 아는지가 변별점이고, UTC 세션에서는 DST가 없어 둘이 같아지므로 차이가 숨는다 — 한국만 서비스할 때 이 버그가 안 드러나는 이유도 같다(한국에는 현재 서머타임이 없다).

9. 안전망 — 선택을 설정 · 타입 규약 · 테스트로 고정한다

"timestamptz + Instant로 간다"는 결정은 세 층에 못 박아야 유지된다. 설정(시계), 타입 규약(어떤 자바 타입을 어디에 쓰는가), 테스트(어긋나면 빌드가 깨진다).

① 설정 — 시계를 못 박는다
-Duser.timezone=UTC · hibernate.jdbc.time_zone=UTC · ALTER DATABASE … SET timezone='UTC'
② 규약 — 사람에 의존하지 않는다
ArchUnit으로 LocalDateTime 필드와 LocalDateTime.now() 호출을 빌드에서 막는다
③ 테스트 — 새면 깨진다
여러 JVM 존으로 도는 매트릭스 + AT TIME ZONE 'UTC' 단정 + 컬럼 타입 단정

9-1. before / after — JPA 엔티티

Hibernate 버전 주의 시니어 변별 Instant·OffsetDateTime을 어떤 SQL 타입으로 내보낼지(그리고 hibernate.timezone.default_storage가 어떻게 작동할지)는 Hibernate 메이저 버전 사이에 달라져 왔다. DDL을 Hibernate 자동 생성에 맡기지 말고 마이그레이션 스크립트(Flyway/Liquibase)를 진실로 삼은 뒤, 9-3의 "컬럼 타입 단정" 테스트로 실제 타입을 못 박는다. 이것이 버전 지식에 의존하지 않는 유일한 방법이다.

COMMENT ON COLUMN episode_schedule.publish_at_utc IS

왜 publish_at_utc를 generated column으로 만들지 않나 시니어 변별 생성 컬럼은 "원본이 바뀔 때만" 다시 계산된다. 그런데 이 값이 틀어지는 원인은 원본 변경이 아니라 tzdata(존 규칙) 변경이다. "규칙이 바뀌면 배치가 다시 계산한다"가 설계 의도이므로, 재계산 주체를 앱·배치로 두고 컬럼은 평범한 캐시로 남긴다.

9-3. 타입 규약을 ArchUnit으로 — "규칙을 아는 사람"에 의존하지 않기

자바 타입 규약은 세 줄이다

Instant
순간
저장·전송·비교의 기본. 컬럼은 timestamptz.
LocalDateTime
로컬 벽시계
"존을 모르는 것이 의도"인 자리에만(미래 일정의 사용자 입력). 컬럼은 timestamp + 존 ID.
ZonedDateTime
계산용
로컬 벽시계 + 존 ID로 순간을 구할 때 잠깐 쓰고, 저장은 분해해서.

이 규약을 리뷰 코멘트로만 두면 세 번째 신규 입사자 때 깨진다. 빌드에 넣는다.

good 사고 사슬의 첫 고리를 빌드 단계에서 끊는다
@AnalyzeClasses(packages = "com.example")
class TimeTypeRulesTest {

    // 규약 1: 엔티티 필드에 LocalDateTime 금지 — 예외는 @LocalWallClock 으로 의도를 밝힌 필드뿐
    //         (LocalDateTime 필드는 곧 timestamp 컬럼이 되고, 그것이 7-2 두 사고의 공통 뿌리다)
    @ArchTest
    static final ArchRule entities_store_instants =
        noFields().that().areDeclaredInClassesThat().areAnnotatedWith(Entity.class)
            .and().areNotAnnotatedWith(LocalWallClock.class)
            .should().haveRawType(LocalDateTime.class)
            .because("엔티티의 시각은 Instant(→ timestamptz)로 저장한다. 미래 로컬 일정만 @LocalWallClock 으로 표시");

    // 규약 2: JVM 기본 존에 몰래 의존하는 API 호출 금지 — '지금'은 주입받은 Clock 에서 꺼낸다
    @ArchTest
    static final ArchRule no_default_zone_dependency =
        noClasses().should().callMethod(LocalDateTime.class, "now")
            .orShould().callMethod(ZoneId.class, "systemDefault")
            .orShould().callConstructor(Date.class)
            .because("서버가 어디에 있든 같은 값이어야 한다. Clock.instant() / ZoneId.of(사용자 존)을 쓴다");
}

9-4. 회귀 테스트 — "컬럼 타입"과 "UTC로 못 박은 값"을 단정한다

설정은 누군가 URL을 정리하다가, 베이스 이미지를 바꾸다가, 마이그레이션을 손으로 고치다가 하나씩 사라진다. 사라지면 빌드가 깨져야 한다. PostgreSQL판 요령은 셋이다.

⑴ 일부러 어긋나게
DB 컨테이너와 테스트 JVM을 일부러 UTC가 아닌 존으로 띄운다 — 설정이 OS 존을 이기는지 본다.
⑵ 기준을 못 박고
값을 단정할 때 AT TIME ZONE 'UTC'로 기준을 고정한다 — 세션 존에 따라 표기가 달라지는 2절을 통과하기 위해.
⑶ 타입까지 단정
값뿐 아니라 information_schema로 컬럼 타입까지 단정한다 — 사고 ②는 타입이 잘못된 순간 시작된다.
good 회귀 테스트
@SpringBootTest @Testcontainers
@Tag("timezone")                     // 아래 빌드 매트릭스가 이 태그를 여러 JVM 존에서 돌린다
class TimeZoneRegressionTest {

    // ⑴ DB OS 존을 일부러 UTC가 아닌 곳으로 — 설정이 OS 존을 이기는지 확인
    @Container
    static final PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16")
            .withEnv("TZ", "America/Los_Angeles");

    @Test
    void 컬럼_타입이_timestamptz다() {
        // 사고 ②의 뿌리 차단 — 마이그레이션이나 자동 DDL이 timestamp 로 만들었으면 여기서 깨진다
        String type = jdbc.queryForObject(
                "SELECT data_type FROM information_schema.columns "
              + "WHERE table_name = 'payment' AND column_name = 'paid_at'", String.class);
        assertThat(type).isEqualTo("timestamp with time zone");
    }

    @Test
    void 앱_세션의_TimeZone은_JVM_존을_따라간다() {
        // pgjdbc 가 접속 시 세션 TimeZone 을 JVM 존으로 설정한다는 사실 자체를 문서화하는 테스트.
        // -Duser.timezone=UTC 가 빠지면 여기서 깨져 "왜 psql 과 다르게 보이나"를 미리 알려준다.
        assertThat(jdbc.queryForObject("SHOW TimeZone", String.class))
                .isEqualTo(java.util.TimeZone.getDefault().getID());
    }

    @Test
    void 어떤_JVM_존에서_돌려도_같은_순간이_저장된다() {
        Instant paidAt = Instant.parse("2026-08-31T00:00:00Z");
        Long id = repo.save(Payment.paid(paidAt)).getId();

        // ⑵ 세션 존 표기에 흔들리지 않도록 UTC 로 못 박아 문자열로 꺼낸다
        String raw = jdbc.queryForObject(
                "SELECT to_char(paid_at AT TIME ZONE 'UTC', 'YYYY-MM-DD HH24:MI:SS') "
              + "FROM payment WHERE id = ?", String.class, id);
        assertThat(raw).isEqualTo("2026-08-31 00:00:00");   // KST 09:00 이 적혔다면 여기서 깨진다

        // 앱 경로로 읽어도 같은 순간
        assertThat(repo.findById(id).orElseThrow().getPaidAt()).isEqualTo(paidAt);
    }

    @Test
    void DB_DEFAULT_경로와_앱_경로의_기준이_같다() {
        // 3절의 "한 컬럼 두 기준" 방지 — DEFAULT now() 로 채워진 created_at 과
        // 앱이 넣은 paid_at 의 기준이 같은가
        Long id = jdbc.queryForObject(
                "INSERT INTO payment (paid_at, amount) VALUES (now(), 1000) RETURNING id", Long.class);
        Double diffSec = jdbc.queryForObject(
                "SELECT abs(extract(epoch FROM (paid_at - created_at))) FROM payment WHERE id = ?",
                Double.class, id);
        assertThat(diffSec).isLessThan(5.0);   // 9시간(= 32,400초) 차이면 기준이 어긋난 것
    }
}

9-5. 시간 원칙 7개 — 각 원칙이 PG 스키마에 착지하는 지점

22장의 원칙이 4장에서 컬럼 하나하나로 착지한다. 목록으로 인출한다.
원칙PG 스키마에 착지하는 지점
① 저장은 UTC 순간
과거·현재의 사건은 UTC 하나로		timestamptz. PostgreSQL에서는 이게 곧 UTC 정규화이므로 "앱이 UTC로 바꿔 넣는다"는 규약이 필요 없다. DEFAULT now()도 안전하다.
② 표시는 사용자 타임존, 변환은 가장 바깥에서AT TIME ZONE을 표시용 SELECT 목록에서만 쓰고 WHERE에는 쓰지 않는다. 일 단위 경계는 앱이 비즈니스 존으로 계산해 UTC 파라미터로 바인딩(paid_at >= $1 AND paid_at < $2).
③ 미래 일정은 로컬 벽시계 + IANA 존 IDtimestamp + text 두 컬럼 + 파생 timestamptz 캐시. 오프셋(+09:00) 저장 금지. timestamptz가 존을 저장한다는 오해가 이 원칙을 건너뛰게 만든다.
④ tzdata(타임존 규칙) 변경에 대비
DST 폐지·도입은 실제로 일어난다		파생 UTC 컬럼을 "진실"로 삼지 않는다 — 규칙이 바뀌면 ③의 원본에서 AT TIME ZONE으로 재계산하는 배치가 있어야 한다. tzdata 갱신 절차(JVM·OS·PG 서버)를 운영 항목으로. 존을 박아 만든 표현식 인덱스가 있다면 REINDEX 대상.
⑤ 시계를 하나로 못 박고 테스트로 지킨다9-2 설정(-Duser.timezone=UTC → pgjdbc 세션까지 따라온다, ALTER DATABASE … SET timezone) + 9-4 회귀 테스트 + 빌드 매트릭스.
⑥ "지금"은 주입받은 Clock에서9-3 ArchUnit. 그리고 SQL 쪽에서는 now()가 트랜잭션 시작 시각임을 기억한다 — 배치의 기준 시각을 now()에 맡기지 않고 앱이 Instant로 계산해 파라미터로 넘기면 사고 ①의 존 불일치도, 트랜잭션 길이만큼 기준선이 밀리는 문제도 함께 사라지고 테스트에서 고정된다.
⑦ 타입 규약을 이름으로자바 타입과 PG 타입이 한 쌍씩 맞물린다 — Instant↔timestamptz / LocalDateTime↔timestamp+존 ID / ZonedDateTime↔(저장 안 함) / LocalDate↔date.

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

두 타입 한 문장 정의?
timestamptz = 순간을 저장하고 존은 입출력에서만 쓴다. timestamp = 벽시계를 저장하고 존은 아예 모른다.
timestamptz는 존을 저장하나?
아니다. 들어 있는 것은 UTC 순간 하나 = 8바이트 정수 하나. 출력의 +09는 "저장된 존"이 아니라 "지금 이 세션의 존".
PG에서 선택 축은 몇 개?
하나. 두 타입이 같은 8바이트·마이크로초·4713 BC~294276 AD라 2038·크기 논쟁이 아예 없다 → "정규화를 DB가 하느냐 앱이 하느냐"만 남는다.
컬럼 성격 5분류?
사·일·날·구·시 — 사건 timestamptz+Instant / 일정 timestamp+존 ID / 날짜 date / 구간 tstzrange+EXCLUDE / 시각 time.
PG 함정 셋?
보 · 뭉 · 붙 — 보이는 값이 세션 따라 흔들린다(날짜까지) / 값이 뭉친다(now()=트랜잭션 시작) / 세션이 JVM에 붙는다(pgjdbc).
now() 3형제?
트·문·클 — 트랜잭션 시작 now() / 문장 시작 statement_timestamp() / 클럭 clock_timestamp().
AT TIME ZONE 방향?
항상 반대편으로 넘긴다. 순간 주면 벽시계, 벽시계 주면 순간. 결과에 +09가 붙으면 순간, 안 붙으면 벽시계.
타입이 섞이면?
timestamp를 timestamptz와 비교하면 좌변이 세션 존으로 승격된다 → 비교 결과가 "누가 실행하느냐"에 달린다.
일 단위 집계가 풀스캔?
paid_at::date는 인덱스를 못 타고, STABLE이라 표현식 인덱스로도 못 만든다. 정석은 앱이 계산한 UTC 반열린 구간 >= $1 AND < $2.
안전망 4줄?
-Duser.timezone=UTC · hibernate.jdbc.time_zone=UTC · ALTER DATABASE … SET timezone='UTC' · ArchUnit + 컬럼 타입까지 단정하는 회귀 테스트.
정합이 깨지면 뭐가 틀리나?
timestamptz는 표기만 틀린다(값 무사·복구 가능). timestamp는 값의 기준이 틀린다(복구 불가). 이 비대칭이 결론을 정한다.
테스트를 왜 LA에서도 돌리나?
서울은 DST 없이 +9만, LA는 DST가 있고 부호가 반대. 세 번째가 있어야 "계절마다 다르게 깨지는"·"날짜가 하루 밀리는" 버그가 잡힌다.

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

timestamptz는 타임존까지 저장하는 건가요? 이름이 그런데요. 함정힌트: "저장하지 않는다"로 시작하지 말고 "그럼 무엇을 저장하는가"부터 세운다

아니다 — 저장하는 것은 UTC 순간 하나뿐이고, 존은 입출력에서만 쓰인다. 사슬로 답한다. 입력에 오프셋이 있으면 그걸로, 없으면 세션 TimeZone으로 해석해 UTC로 환산한 8바이트 정수를 저장한다. 출력할 때 붙는 +09 같은 표기는 "저장된 존"이 아니라 "지금 이 세션의 존"이다.

증명은 한 줄이면 된다 — SET timezone을 바꿔가며 같은 행을 두 번 읽으면 표기만 바뀐다. 세션을 America/Los_Angeles로 두면 날짜까지 하루 앞으로 밀려 보인다는 것까지 덧붙이면 확실하다.

그래서 timestamptz 컬럼에 "몇 시로 저장돼 있나요?"는 성립하지 않는 질문이고, 판정은 AT TIME ZONE 'UTC'로 못 박아야 한다.

실무적 파장이 큰 오해다 — "존이 저장되니 예약 시각도 그냥 넣으면 되겠지"라고 믿으면 미래 일정에 존 ID 컬럼을 두지 않게 되고, tzdata가 바뀌는 날 예약 시각 전체가 조용히 틀어진다.

그럼 timestamp(without time zone)는 안 쓰나요? 어떤 자리에 남기나요? 필수힌트: "안 쓴다"로 끝내면 반쪽. 남는 자리 셋 + 양면 서술

과거·현재의 사건에는 안 쓴다. 남는 자리는 "벽시계 자체가 의미인 값"뿐이다.

⑴ 미래 일정의 원본
"매일 밤 11시 공개"는 순간이 아니라 규칙이라 timestamp(로컬 벽시계) + IANA 존 ID로 분해 저장한다.
⑵ DST가 개입하면 안 되는 값
예: 계약서에 적힌 "2026-09-01 09:00"이라는 문자열 자체가 법적 사실인 경우.
⑶ 외부 원문 보관
외부 시스템이 존 없이 준 값을 원문 그대로 보관할 때(변환은 나중에 근거와 함께).

양면을 붙인다 — timestamp가 얻는 것은 "세션 존과 무관하게 보이는 값 = 저장된 값"이라는 예측 가능성이고, 내는 것은 타임존 정보 소실과 복구 근거 없음, 그리고 now()·timestamptz와 비교하는 순간 세션 존이 결과를 바꾼다는 것이다.

PostgreSQL에서는 두 타입의 크기·범위가 같으므로 "성능·용량 때문에 timestamp"라는 근거는 아예 없다 — 오직 의미로만 고른다.

created_at이 실제 시각보다 이르고, 한 배치에서 넣은 1만 건이 전부 같은 시각입니다. 함정힌트: 원인 한 줄 + 파장 셋 + 처방 셋. 마지막에 MySQL 대조

now()가 "지금"이 아니라 트랜잭션 시작 시각이기 때문이다. now() = CURRENT_TIMESTAMP = transaction_timestamp()이고, 문장 시작 시각은 statement_timestamp(), 실제 호출 순간은 clock_timestamp()다. 트랜잭션이 10분 열려 있었으면 DEFAULT now()로 채워진 값은 10분 과거를 가리키고, 한 트랜잭션의 대량 INSERT는 전부 같은 값이 된다.

파장 셋 — ⑴ created_at으로는 삽입 순서를 가릴 수 없다. 커서 페이지네이션이 WHERE created_at < :마지막값으로 다음 장을 뜨면, 같은 값을 가진 1만 건이 < 조건을 못 만족해 통째로 건너뛰어진다 — 키셋 페이지네이션의 타이브레이커가 id처럼 유일한 컬럼이어야 하는 실제 이유가 이것이다. ⑵ WHERE updated_at > :마지막값 폴링 방식의 증분 동기화가 행을 조용히 건너뛴다 — 트랜잭션 시작 시각으로 찍힌 행이 나중에 커밋되면서 이미 지나간 구간에 끼어들기 때문. ⑶ 배치의 기준선도 now()로 잡으면 트랜잭션 길이만큼 밀린다.

처방 셋 — 의도에 맞는 함수를 고르는 것(감사·수정 시각은 clock_timestamp()), 폴링 경계에 여유(lookback)를 두고 중복은 멱등 처리로 흡수하는 것, 그리고 근본 처방으로 논리 디코딩 기반 CDC로 타임스탬프 대신 커밋 순서를 따르게 하는 것이다.

가산점 MySQL의 NOW()는 문장 시작 시각이라 이 사고가 잘 안 난다 — "MySQL에서 PostgreSQL로 옮기고 나서 증분 배치가 이상해졌다"의 정체가 이것이다. 다만 한 문장으로 1만 건을 넣으면 MySQL에서도 같은 값이고 커밋 순서와의 어긋남도 그대로다 — PG는 그 창을 트랜잭션 길이만큼 벌릴 뿐이다.

"매일 밤 11시 신작 공개"를 그냥 timestamptz에 넣으면 안 되나요? 저장은 UTC가 원칙이라면서요. 함정힌트: 원칙의 적용 범위를 먼저 나눈다 — "사건"과 "일정"은 저장할 것이 다르다

"저장은 UTC 순간"은 과거·현재의 사건에 대한 원칙이고, 미래 일정은 저장할 것이 다르다. 사용자가 정한 것은 "서울 벽시계로 23:00"이라는 규칙이지 특정 UTC 순간이 아니다.

지금 14:00Z로 환산해 저장하면(서울 23:00 − 9시간 = 같은 날 14:00 UTC) — ⑴ DST가 있는 존이면 전환일 이후 환산 결과가 1시간 바뀌어 "22:00 공개"가 된다 ⑵ 그 나라가 DST를 폐지하거나 도입하면(tzdata 변경) 이미 저장된 모든 미래 행이 틀린다 ⑶ 되돌릴 근거(원래 벽시계와 존)가 값에 없다 — timestamptz가 존을 저장해 줄 거라는 오해가 여기서 정확히 대가를 청구한다.

그래서 timestamp(로컬 벽시계) + IANA 존 ID(text)를 원본으로 저장하고, UTC는 스캔·정렬용 파생 캐시로 두되 존 규칙이 바뀌면 publish_local_at AT TIME ZONE publish_zone_id로 재계산한다.

오프셋(+09:00)이 아니라 존 ID(Asia/Seoul)여야 하는 이유도 같다 — 오프셋은 "지금의 결과"이고 존 ID는 "규칙"이다.

스캐너(배치)는 파생 UTC 컬럼으로 "지금 공개할 것"을 찾되, 실제 공개 직전에 원본으로 한 번 더 검증하면 규칙 변경 사이의 창도 막는다. DST 전환일에 존재하지 않는 시각(02:30이 없는 날)의 처리는 22장 문서의 몫이다.

이미 timestamp에 KST 벽시계로 3년치가 쌓여 있는 서비스가 글로벌 진출합니다. 어떻게 전환하시겠어요? 시니어 변별힌트: 여섯 단계 — 진단 / "한 줄로 안 되나" / 새 컬럼+이중 쓰기 / 백필 / 읽기 전환·검증·정리 / 미래 일정 분리

"컬럼의 의미를 바꾸는 마이그레이션"이라 단순한 타입 변경보다 어렵다 — 값의 모양은 같고 기준만 바뀌기 때문에, 전환 중에 "이 행은 어느 기준인가"를 잃으면 복구가 안 된다. 순서로 답한다.

1
진단 먼저 — 정말 전부 KST인가? 사고 ①처럼 이미 UTC와 KST가 섞여 있을 수 있다. 배포 이력, created_at이 미래인 행, now() 기준 배치의 오작동 로그로 경계를 찾는다. 섞여 있으면 구간별 오프셋을 먼저 확정한다.
2
"한 줄로 되지 않나"에 대한 답부터 — 문법적으로는 된다: ALTER TABLE payment ALTER COLUMN paid_at TYPE timestamptz USING paid_at AT TIME ZONE 'Asia/Seoul'; 하지만 이건 ACCESS EXCLUSIVE 잠금 + 테이블 전체 재작성이고, PostgreSQL에서 그 잠금은 진행 중인 롱 쿼리 뒤에 줄 서면서 그 뒤에 오는 모든 SELECT까지 줄 세운다 — 수억 건이면 서비스 중단이다. (세션 TimeZone이 UTC일 때 이 변환의 재작성을 피하는 최적화가 최근 버전에 있으므로, 스테이징에서 실제 잠금·소요를 재 보고 들어가는 것이 맞다.) 작은 테이블이면 SET lock_timeout = '2s' + 재시도로 끝내고, 큰 테이블이면 3으로 간다.
3
새 컬럼 + 이중 쓰기 — ADD COLUMN paid_at_tz timestamptz;는 NULL 허용이라 카탈로그만 건드리고 즉시 끝난다(PG 11+는 상수 DEFAULT가 붙어도 재작성 없음). 앱이 두 컬럼을 다 채우거나, BEFORE INSERT OR UPDATE 트리거로 NEW.paid_at_tz := NEW.paid_at AT TIME ZONE 'Asia/Seoul'을 자동화한다.
4
백필 — PostgreSQL 고유의 비용을 계산에 넣는다. UPDATE … WHERE id BETWEEN $1 AND $2를 PK 범위로 쪼개 돌린다. PostgreSQL의 UPDATE는 제자리 수정이 아니라 새 튜플 버전을 만들므로, 전수 백필은 테이블을 사실상 두 배로 부풀리고 WAL·레플리카 지연·autovacuum 추격 실패를 부른다. 그래서 배치 크기를 작게, 사이사이 VACUUM (ANALYZE), 새 컬럼의 인덱스는 백필이 끝난 뒤 CREATE INDEX CONCURRENTLY로. (한국이 DST가 없어 전 구간 균일하게 +9시간인 것이 이 마이그레이션의 행운이고, DST가 있는 존이었다면 행마다 규칙이 다르게 적용된다 — 그래서 오프셋이 아니라 존 ID로 변환해야 한다.)
5
읽기 전환 → 검증 → 정리 — 읽기를 새 컬럼으로 옮기고, 두 컬럼의 관계가 전 구간에서 성립하는지 전수 점검(WHERE paid_at_tz <> paid_at AT TIME ZONE 'Asia/Seoul'가 0건)한 뒤 구 컬럼을 DROP한다. DROP COLUMN은 카탈로그만 바꾸므로 즉시지만 공간은 바로 안 돌아온다 — 회수는 VACUUM(재사용) 또는 pg_repack(축소)의 몫이다.
6
이 기회에 미래 일정 컬럼을 분리 — 예약 공개 시각처럼 "벽시계가 의도"인 컬럼은 UTC로 환산하는 것이 아니라 존 ID 컬럼을 추가해 분해 구조로 바꾼다.

전환의 트레이드오프를 양면으로 — 이중 쓰기 기간에는 코드가 두 컬럼을 알아야 하고 저장 공간이 늘지만, 제자리에서 한 번에 바꾸는 방식은 실행 도중 앱이 어느 기준으로 읽어야 하는지 정의할 수 없어 무중단이 불가능하다. 마지막으로 — 이 전환이 필요해진 이유가 곧 "처음부터 timestamptz + Instant를 썼어야 하는 이유"라고 닫는다.

AT TIME ZONE은 어느 방향으로 변환하나요? 결과 타입은 뭔가요? 필수힌트: "변환 함수"라고 답하면 반쪽. 타입이 어떻게 되는지를 말한다

값을 바꾸는 게 아니라 타입을 뒤집는 연산자다. 입력 타입에 따라 출력 타입이 반대로 뒤집힌다.

  • 내림: timestamptz AT TIME ZONE '존' → timestamp. "이 순간은 그 존에서 몇 시인가". 리포트·화면 표시, 검증 SQL에서 AT TIME ZONE 'UTC'로 기준 고정.
  • 올림: timestamp AT TIME ZONE '존' → timestamptz. "이 벽시계를 그 존으로 읽으면 어느 순간인가". 미래 일정 원본에서 UTC 파생 컬럼 계산, 옛 컬럼 마이그레이션.

요령은 "항상 반대편으로 넘긴다". 확인 방법도 눈으로 된다 — 결과에 +09 같은 표기가 붙으면 순간, 안 붙으면 벽시계.

두 번 쓰면 "존 A의 벽시계를 존 B의 벽시계로"도 된다: (wall AT TIME ZONE 'Asia/Seoul') AT TIME ZONE 'America/Los_Angeles' — 앞쪽이 올리고, 뒤쪽이 내린다.

paid_at에 인덱스가 있는데 "오늘 매출" 쿼리가 풀스캔입니다. 함수 인덱스를 만들려니 그것도 거부되고요. 가산점힌트: "두 번 진다"의 두 번이 각각 무엇인지 나눠 말한다

첫 번째 패배 — WHERE paid_at::date = …처럼 컬럼에 캐스트를 씌우면 인덱스를 못 탄다. 인덱스에는 가공된 값이 없으므로 옵티마이저는 모든 행을 읽어 하나씩 캐스트할 수밖에 없다. 여기까지는 인덱스의 일반 원리다.

두 번째 패배 — 보통 이럴 때 쓰는 우회(표현식 인덱스)가 여기서는 막힌다. timestamptz → date 캐스트는 세션 TimeZone에 따라 결과가 달라지는 STABLE 함수인데, 인덱스는 "언제 어디서 계산해도 같은 값"을 전제로 값을 굳혀 두므로 PostgreSQL은 IMMUTABLE 함수만 받는다 → functions in index expression must be marked IMMUTABLE. MySQL의 DATE(col) 함수 인덱스 습관이 통하지 않는 지점.

덤으로 세 번째 — '2026-08-31'이 어느 존의 하루인지가 세션 설정에 숨는다. 같은 쿼리가 psql과 앱에서 다른 답을 내는데 쿼리 텍스트만 봐서는 알 수 없다.

정석 처방은 앱이 비즈니스 존으로 하루의 시작·끝을 계산해 UTC 순간으로 바인딩하는 것: WHERE paid_at >= $1 AND paid_at < $2. 컬럼이 맨몸이라 인덱스 범위 탐색이 되고, 존이 앱 코드에 드러나 리뷰에서 보인다. >=/< 반열린 구간을 쓰는 이유는 BETWEEN이 양끝을 포함해 자정 정각 행이 이틀에 중복으로 잡히기 때문이다.

SQL 안에서 꼭 해야 한다면 존을 리터럴로 박아 date_trunc('day', paid_at AT TIME ZONE 'Asia/Seoul') — 이건 IMMUTABLE이라 표현식 인덱스가 된다. 대가는 ⑴ 존마다 인덱스가 하나씩(글로벌이면 인덱스 폭발) ⑵ tzdata가 바뀌면 굳어 있는 값이 현실과 어긋나 REINDEX 필요. 그래서 정석은 여전히 UTC 경계 범위 조건이다.

저장했다가 바로 조회했는데 assertEquals(saved, found)가 깨집니다. 함정힌트: 자릿수를 세어 본다

해상도가 다르기 때문이다. PostgreSQL의 기본 해상도는 마이크로초(소수점 6자리)인데 자바 Instant는 나노초(9자리)를 갖고 있어, 저장·조회를 왕복하면 뒤 3자리가 잘려 나간다.

처방은 둘 — 앱에서 truncatedTo(ChronoUnit.MICROS)로 미리 맞추거나, 비교를 "허용 오차 안"으로 단정한다.

추가로, timestamptz(0)·timestamptz(3)처럼 자릿수를 줄여 선언하면 그만큼 더 크게 어긋난다. 특별한 이유가 없으면 기본(마이크로초)을 쓴다.

timestamptz + interval '1 day'와 + interval '24 hours'는 같은 건가요? 가산점힌트: 한국에서만 서비스하면 이 차이가 안 드러난다

다르다. + interval '1 day'는 세션 존의 달력 기준 하루를 더하므로 DST 전환일에는 23시간 또는 25시간이 되고, + interval '24 hours'는 정확히 24시간이다.

"매일 같은 시각"이 의도면 전자, "정확히 하루 뒤 순간"이 의도면 후자다. 둘이 다르다는 것을 아는지가 변별점이다.

이 버그가 숨는 이유도 함께 말하면 좋다 — UTC 세션에서는 DST가 없어 둘이 같아지고, 한국에는 현재 서머타임이 없어 국내 서비스에서는 드러나지 않는다. 글로벌로 나가는 순간 터진다.

updated_at 자동 갱신은 어떻게 하나요? JPA Auditing이 있으면 되지 않나요? 필수힌트: Auditing이 빠지는 경로 셋을 떠올린다

PostgreSQL에는 MySQL의 ON UPDATE CURRENT_TIMESTAMP가 없다. DEFAULT now()는 되지만 UPDATE 시 자동 갱신은 없다. BEFORE UPDATE 트리거로 직접 만든다.

JPA Auditing만으로 부족한 이유는 Auditing이 빠지는 경로가 있기 때문이다 — @Modifying 벌크 UPDATE, 네이티브 쿼리, psql 수동 SQL. 트리거는 DB 레벨이라 이 경로들에서도 살아 있어 Auditing의 구멍을 메운다.

두 가지 디테일을 붙이면 좋다 — ⑴ 트리거 안에서 now()를 쓰면 트랜잭션 시작 시각이 박히므로 "수정된 순간"이 의도라면 clock_timestamp()다. ⑵ WHEN (OLD.* IS DISTINCT FROM NEW.*)로 값이 실제로 바뀔 때만 걸면 같은 값으로 덮어쓰는 UPDATE에는 안 붙는다. IS DISTINCT FROM을 쓰는 이유는 NULL <> NULL이 NULL(거짓 취급)이라 평범한 <>로는 "NULL이 값으로 바뀐" 변경을 놓치기 때문이다.

즉 PostgreSQL은 한 줄을 더 쓰게 하는 대신 조건을 붙일 수 있어 오히려 세밀하다.

"만료 없음", "무기한 정지"를 어떻게 표현하나요? 가산점힌트: 마법 날짜 말고 타입이 주는 값이 있다

PostgreSQL에는 특수값 'infinity' / '-infinity'가 있다. 9999-12-31 같은 마법 날짜로 표현하던 관례를 타입 차원에서 대체한다.

얻는 것 둘 — ⑴ 비교 연산이 그대로 성립한다(expires_at > now()가 'infinity' 행에 대해 언제나 참) ⑵ 의미가 값에 드러난다 — "9999면 무기한"이라는 규약을 사람이 기억할 필요가 없다.

MySQL 대조를 붙이면 더 좋다 — MySQL에서는 TIMESTAMP가 2038까지밖에 못 담아 "영구 이용권을 담아야 하니 DATETIME"처럼 범위가 타입 선택을 뒤집는 일이 실제로 벌어졌다. PostgreSQL은 범위가 294276 AD까지인 데다 'infinity'까지 있어 그 논쟁이 없다.

예약 겹침을 "조회해서 없으면 INSERT"로 막고 있습니다. 동시 요청에 뚫리는데요. 가산점힌트: 유니크 제약을 등호가 아닌 연산자로 일반화한 것이 있다

PostgreSQL에는 전용 도구가 있다 — 범위 타입 tstzrange와 EXCLUDE 제약이다. EXCLUDE는 "이 조건들을 동시에 만족하는 두 행이 존재하면 거부한다"는 제약으로, 유니크 제약을 등호가 아닌 임의 연산자로 일반화한 것이다.

EXCLUDE USING gist (room_id WITH =, period WITH &&) — 같은 방에서 기간이 겹치면(&&) 아예 INSERT가 거부된다. (스칼라 = 비교를 GiST에서 쓰려면 btree_gist 확장이 필요하다.)

요점은 "앱의 조회 후 INSERT 경쟁을 DB 제약으로 대체한다"는 것이다 — 애플리케이션 검사는 두 트랜잭션이 동시에 "없음"을 보는 창을 못 막지만, 제약은 막는다. MySQL에 대응물이 없는 PostgreSQL 고유 카드라 면접에서 잘 먹힌다.

timetz(time with time zone)는 왜 안 쓰나요? 가산점힌트: 날짜가 없으면 무엇을 알 수 없는가

날짜가 없으면 DST 규칙을 적용할 수 없기 때문이다. 같은 존이라도 그 오프셋이 여름 것인지 겨울 것인지는 날짜를 알아야 정해지는데, timetz에는 날짜가 없다. 그래서 붙어 있는 오프셋이 의미를 갖지 못한다.

PostgreSQL 문서 자체가 유용성에 의문을 표시하는 타입이다. "시각만 있고 날짜가 없는 값"(예: 매장 영업 시작 시각)은 time을 쓰고, 존이 필요하면 존 ID를 별도 컬럼으로 둔다 — 미래 일정 설계와 같은 원리다.

한 줄 요약
PostgreSQL의 timestamptz는 이름과 달리 타임존을 저장하지 않고 입력을 세션 TimeZone으로 해석해 UTC 순간 하나(8바이트 정수 하나)로 정규화해 적는 타입이고, timestamp는 변환 없이 벽시계를 그대로 적어 "어느 존의 값인지"를 버리는 타입인데 — 둘 다 8바이트·마이크로초·4713 BC~294276 AD라 MySQL을 갈랐던 2038·크기 논쟁이 통째로 사라지므로, 글로벌 서비스라면 과거·현재의 모든 사건은 timestamptz + 자바 Instant(드라이버가 오프셋을 명시해 보내므로 시계가 어긋나도 저장이 안 밀린다)로 가고, timestamp는 "벽시계 자체가 의도"인 미래 일정에 IANA 존 ID 컬럼과 짝으로만 남겨 UTC는 재계산 가능한 파생 캐시로 둔다. 남는 것은 PostgreSQL 고유의 함정 셋 — 출력이 세션 존을 따라 달라져 날짜까지 하루 밀려 보이므로 판정은 AT TIME ZONE 'UTC'로 못 박고, now()는 트랜잭션 시작 시각이라 한 배치의 1만 건이 같은 값을 갖고 커서 페이지네이션과 증분 동기화가 조용히 행을 흘리므로 clock_timestamp()나 CDC를 쓰며, pgjdbc가 세션 TimeZone을 JVM 존으로 설정하므로 -Duser.timezone=UTC 한 줄이 곧 세션 설정이다 — 그리고 이 셋은 -Duser.timezone=UTC · hibernate.jdbc.time_zone=UTC · ALTER DATABASE … SET timezone='UTC' · ArchUnit 타입 규약 · 컬럼 타입까지 단정하는 회귀 테스트로 못 박는다.
