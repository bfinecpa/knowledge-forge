04 · RDB / SQL — 스키마 설계 · 시간

DATETIME vs TIMESTAMP — "벽시계를 적는 타입"과 "순간을 적는 타입", 그리고 시간 원칙이 스키마에 착지하는 지점

원본: interview-questions/knowledge/04-rdb-sql/30-datetime-vs-timestamp-timezone.md

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "DATETIME과 TIMESTAMP의 차이(타임존 동작, 범위)는? 글로벌 서비스라면 무엇을 선택하겠습니까?"
두 타입은 "무엇을 저장하느냐"가 다르다. TIMESTAMP는 저장할 때 세션 타임존 → UTC로 변환해 1970년 기준 초(epoch)로 적고, 읽을 때 UTC → 세션 타임존으로 되돌리는 "순간(instant)" 타입이다 — 4바이트와 자동 UTC 정규화를 얻는 대신 2038-01-19까지의 범위와 세션 타임존 의존을 낸다. DATETIME은 아무 변환 없이 받은 벽시계 값을 그대로 적는 타입이다 — 넓은 범위(1000~9999년)와 "보이는 값 = 저장된 값"의 예측 가능성을 얻는 대신 타임존 정보가 사라지므로 "이 컬럼은 UTC다"라는 규율을 애플리케이션이 지켜야 한다. 값이 몇 시간 밀리는 사고는 언제나 네 개의 시계 — JVM 기본 타임존, Hibernate가 JDBC에 값을 넘기는 기준 존, JDBC 드라이버의 커넥션 타임존, DB 세션 time_zone — 중 하나가 어긋날 때 생긴다. 글로벌 서비스라면 과거·현재의 사건(created_at, paid_at)은 DATETIME(6) + 네 시계 UTC 고정 + 회귀 테스트로 가고, 미래 일정(예약 공개 시각)은 로컬 벽시계 + IANA 존 ID를 분해 저장한 뒤 UTC는 재계산 가능한 파생 컬럼으로만 둔다. TIMESTAMP는 2038 이전 값만 들어오는 이벤트·로그 컬럼이거나, 여러 언어의 클라이언트가 DB에 직접 써서 앱 규율을 믿을 수 없을 때 고른다. 어느 쪽이든 선택과 안전망은 한 세트다 — -Duser.timezone=UTC, connectionTimeZone=UTC, hibernate.jdbc.time_zone=UTC, DB default-time-zone='+00:00', Instant 타입 규약을 ArchUnit으로, 타임존을 바꿔 도는 테스트.
출제 의도 — 스펙 암기 시험이 아니다. 채점 지점은 셋이다
⑴ 값이 저장되고 읽히는 변환 경로를 사슬로 말하는가 — 그래야 "어디가 어긋나면 몇 시간 밀리는지"를 겪지 않고도 예측한다 · ⑵ 두 타입의 얻는 것과 내는 것을 양면으로 조립해 "우리 서비스의 조건"으로 결론을 내는가 — 정답이 하나가 아닌 문항이라 결론보다 근거의 구조를 본다 · ⑶ 선택을 설정·타입 규약·테스트로 고정하는가 — "UTC로 저장하기로 했다"는 결정은 코드로 못 박기 전까지 언젠가 깨질 관례일 뿐이다.

문서의 위치: 22장(글로벌/시간)의 원칙을 4장의 스키마 결정으로 내려 보내는 다리다. Instant/LocalDateTime/ZonedDateTime의 상세와 DST 전환일 처리는 22장 문서작성 예정가 맡고, 여기서는 MySQL 타입의 변환 메커니즘, JDBC·Hibernate 층의 시계, 그 위에 놓는 안전망에 집중한다. 생성·수정 시각을 채우는 JPA Auditing 경로는 JPA Auditing과 벌크 연산의 구멍작성 예정에 있다 — 그 문서의 LocalDateTime createdAt을 왜 Instant로 바꿔야 하는지에서 이 문서가 출발한다.

1. 개념 — 두 타입은 무엇을 저장하는가

1-1. 비유 — 항해일지와 벽시계 사진

TIMESTAMP항해일지

선원은 현지 시각으로 적지만 일지에는 세계 표준시(UTC)로 환산해 기록하고, 읽는 사람은 자기 항구의 시각으로 되돌려 본다. 어느 항구에서 읽어도 "같은 순간"을 가리키지만, 환산에 쓴 시계(세션 타임존)가 틀리면 기록 자체가 틀린다.

DATETIME벽시계를 찍은 사진

숫자는 정확히 남지만 사진 어디에도 "어느 도시의 벽시계"인지는 없다. 찍은 사람이 "서울이었다"고 기억하는 동안만 의미가 유지되고, 그 사람이 떠나면(코드가 바뀌면, 서버가 옮겨가면) 숫자는 남고 기준은 사라진다.

첫 변별점 — 결과가 아니라 순서로 말한다
"TIMESTAMP는 타임존 변환이 있고 DATETIME은 없다"는 결과다. 면접관이 듣고 싶은 것은 어느 단계에서 어느 시계로 변환되는지를 순서대로 말하는 사슬이다. 아래 도식이 그 사슬이다.

1-2. 두 파이프라인 — 같은 INSERT ... VALUES ('2026-08-31 09:00:00')가 두 타입에서 겪는 일

위: TIMESTAMP는 ⑵에서 세션 존으로 해석하고 ⑶에서 UTC 순간으로 바꿔 적고 ⑷에서 읽는 세션 존으로 되돌린다 — 변환이 두 번. 아래: DATETIME은 ⑵⑶⑷ 어디에도 변환이 없어 예측 가능하지만, 그 대가로 존 정보가 값에서 사라진다.

1-3. 사슬에서 따라 나오는 것 — TIMESTAMP 네 가지, DATETIME 한 가지

TIMESTAMP 얻는 것

세션 존만 정합하면 어떤 언어의 어떤 클라이언트가 넣어도 UTC 순간으로 정규화된다. 규율이 DB에 있다. 비교·정렬·인덱스도 저장된 순간 기준이라 세션 존과 무관하게 일관된다.

TIMESTAMP 내는 것

세션 존이 어긋나면 저장 자체가 밀린다. 그리고 저장할 때와 같은 (틀린) 존으로 읽으면 되돌아오기 때문에 앱에서는 정상으로 보인다 — §2-2 사고 ②가 이것이다. DST 존이면 로컬 → UTC가 1:1이 아닌 시간대(중복 1시간·존재하지 않는 1시간)가 생긴다. 세션 존을 UTC로 두면 이 문제 자체가 없다.

암기 규칙 — DATETIME의 "타임존 무관"은 "설정 무관"이 아니다
DATETIME을 골라도 DB 세션 존은 UTC로 맞춘다. DEFAULT CURRENT_TIMESTAMP·NOW()·ON UPDATE가 전부 세션 존의 벽시계를 넣기 때문이다.

"DATETIME은 타임존과 무관하니 DB 설정은 아무래도 된다"는 반쪽 이해다. §3의 안전망은 전부 DATETIME이 버린 존 정보를 앱·설정·테스트가 대신 지키는 비용이다.

1-4. 사슬 ③ 범위 — 2038년 문제와 1970년 문제

TIMESTAMP는 내부적으로 1970-01-01 00:00:00 UTC부터의 초를 4바이트에 저장한다. 사슬로 — ⑴ 4바이트 초 카운터 → ⑵ 부호 있는 32비트의 최댓값 2³¹−1초 = 2038-01-19 03:14:07 UTC → ⑶ 그 이후 값은 저장 불가(strict SQL 모드면 에러, 아니면 경고와 함께 0 값 0000-00-00 00:00:00으로 대체) → ⑷ 1970년 이전도 마찬가지로 불가. 00:00:00은 "0 값"으로 예약돼 있어 하한은 00:00:01이다.

"12년 뒤 얘기"가 아니다 — 미래 시각을 담는 컬럼은 지금 이미 2038년을 넘는 값을 받는다. 1970년 이전이 필요한 컬럼(생년월일·역사 데이터)은 처음부터 못 쓴다. 타입 변경 비용은 무중단 DDL 문서의 주제다.
암기 장치 — 2038의 경계 시각
2038-01-19 03:14:07 UTC — "파이(3.14) 뒤에 07". 2³¹−1초, 부호 있는 32비트의 끝.

크기는 범위가 좁은 쪽이 1바이트 작다 — TIMESTAMP 4바이트, DATETIME 5바이트, 둘 다 소수 초 자릿수 (3)/(6)에 따라 0~3바이트가 붙는다. 1바이트 차이는 수억 행의 이벤트 테이블에서만 의미 있는 숫자다. 이 문제는 SQL 함수 층이 아니라 컬럼 타입의 4바이트 저장 포맷에서 오므로 함수의 64비트 지원과 별개다.

1-5. DEFAULT / ON UPDATE — 그리고 레거시의 묵시 동작

현재 MySQL에서는 두 타입 모두 DEFAULT CURRENT_TIMESTAMP와 ON UPDATE CURRENT_TIMESTAMP를 쓸 수 있다. 알아둘 것 세 가지.

ON UPDATE는 DB 레벨

벌크 UPDATE·네이티브 쿼리·콘솔 수동 SQL에서도 동작한다 — JPA Auditing이 빠지는 바로 그 경로에서 살아 있다.

  • 단 다른 컬럼 값이 실제로 바뀔 때만 갱신. 같은 값으로 덮어쓰는 UPDATE에서는 안 움직인다.
  • 채워지는 값은 세션 존의 벽시계다.
레거시 묵시 동작

explicit_defaults_for_timestamp=OFF인 옛 설정에서는 테이블의 첫 번째 TIMESTAMP 컬럼에 자동으로 DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP가 붙고, NOT NULL이 묵시 적용되며, NULL 대입 시 현재 시각이 들어갔다.

  • "updated_at에 NULL을 넣었는데 지금 시각이 됐다"의 정체.
  • MySQL 8.0 기본값은 ON(마법 꺼짐)이지만 옛 설정·옛 DDL 덤프에는 살아 있을 수 있다 — TIMESTAMP를 고르면 이 이력까지 안고 간다.
소수 초 반올림가산점

자릿수를 안 적으면 (0)이고 초 아래는 기본적으로 반올림된다(TIME_TRUNCATE_FRACTIONAL 모드면 절삭).

  • 자바 Instant는 나노초를 가져 DATETIME(0)에 넣으면 저장 후 읽은 값이 달라져 assertEquals(saved, found)가 깨지고, .9995초가 다음 초로 올라가 초 경계를 넘기도 한다.
  • 정석: (6)으로 선언하거나 앱에서 truncatedTo(ChronoUnit.MICROS).

2. 네 개의 시계 — 값이 밀리는 사고의 사슬과 선택의 양면

2-1. 값이 DB에 닿기까지 지나는 네 개의 시계 — 요청 경로 어디에 있는가

Instant(또는 LocalDateTime) 하나가 DATETIME/TIMESTAMP 컬럼에 적힐 때까지, 서로 독립적으로 설정되는 시계 네 개를 지난다. 하나만 어긋나도 값이 밀리고, 어긋난 자리에 따라 밀리는 방향과 증상이 다르다.

①②는 앱 프로세스 안, ③은 커넥션 선 위, ④는 DB 서버 — 각각 다른 사람(개발자·프레임워크 설정·URL 파라미터·DBA/클라우드)이 정한다. 빨간 칩은 각 시계가 실제로 어긋나는 흔한 계기.
암기 카드 — 네 개의 시계 "앱 둘 · 선 하나 · DB 하나"와 각각을 UTC로 못 박는 설정 4종
1JVM 기본 존개발 PC와 컨테이너가 다르기 가장 쉬운 시계-Duser.timezone=UTC
2Hibernate → JDBC기본은 ①을 따라간다hibernate.jdbc.time_zone=UTC
3드라이버 커넥션 존기본 SERVER — ④를 읽어 온다connectionTimeZone=UTC
4DB 세션 time_zone기본 SYSTEM — DB OS 존default-time-zone='+00:00'

비유 — 환전 창구 네 곳을 지나는 돈. 창구마다 자기 환율표(존)가 있어 하나라도 다르면 도착 금액이 달라진다. 모든 창구가 같은 통화(UTC)를 쓰면 환전 자체가 없다. 이해는 사고를 진단할 때 필요하고, 설계는 이해에 의존하지 않게 만든다.

2-2. 사고 사슬 두 개 — "앱에서는 맞는데 DB에서 보면 9시간 다르다"

두 사고 모두 다섯 고리다. 면접에서는 고리를 하나씩 끊어 말하고, 어느 시계가 어긋났는지를 고리마다 짚는다.

고리 1(①의 벽시계)과 고리 3(④의 벽시계)이 다른 존인데, 고리 2에서 DATETIME이 존 정보를 버려 고리 4의 비교가 "숫자 대 숫자"가 된다. 첫 고리 LocalDateTime.now()를 빌드에서 끊는 것이 §3-2다.
사고 ①은 값의 "기준"이 틀리고 콘솔에서 바로 보인다. 사고 ②는 저장된 "순간"이 틀리고 앱에선 숨는다 — 두 타입이 정합이 깨졌을 때 무엇이 틀리는가의 차이가 그대로 사고의 모양이다.

2-3. 트레이드오프 양면 — 각 타입이 얻는 것과 내는 것

한 호흡에 양면으로 말한다. 면접관은 어느 쪽을 고르는지보다 반대편 비용을 빠뜨리지 않는지를 본다. 편익만 말하고 멈추면 이 문항은 반타작이다.

TIMESTAMP가 얻는 것
  1. UTC 정규화를 DB가 강제 — 세션 존만 정합하면 자바든 파이썬이든 콘솔이든 넣는 순간 UTC 순간이 된다. 규율이 스키마에 있다.
  2. 4바이트.
  3. 타입 자체가 "순간"이라 컬럼의 의미가 DDL에 드러난다.
  4. 비교·정렬이 세션 존과 무관하게 순간 기준으로 일관된다.
TIMESTAMP가 내는 것
  1. 1970~2038 — 미래 시각·과거 생년월일 컬럼에 못 쓰고, 나중에 바꾸면 대용량 테이블 재작성.
  2. 세션 존 의존 — 같은 행이 보는 사람마다 다른 숫자라 디버깅이 헷갈리고, 세션 존이 틀리면 저장 자체가 밀리며(사고 ②), DST 존이면 변환이 1:1이 아니다.
  3. 옛 설정의 묵시 DEFAULT/NULL 동작이라는 이력.
  4. "DB가 알아서 UTC로 해주니 앱은 신경 안 써도 된다"는 거짓 안도감 — 세션 존 정합은 여전히 앱 쪽(드라이버 설정)의 책임.
DATETIME이 얻는 것
  1. 1000~9999, 범위 걱정 없음.
  2. 세션 존 무관 — 콘솔에서 보이는 값이 곧 저장된 값이라 예측 가능하고, 누가 어디서 읽어도 같은 숫자.
  3. 묵시 동작 없음.
DATETIME이 내는 것
  1. 타임존 정보가 없다 — "이 컬럼은 UTC"라는 규약이 코드·설정·리뷰 규칙에 있어야 하고, 깨져서 KST 벽시계가 들어와도 DB는 못 잡는다(사고 ①).
  2. 그 결과 사고가 나면 복구 근거가 값에 없다.
  3. 1바이트 더.
  4. DEFAULT CURRENT_TIMESTAMP가 세션 존 벽시계를 넣으므로 결국 DB 세션 존도 UTC로 맞춰야 한다 — "타임존 무관"이 "설정 무관"은 아니다.
둘 다 내야 하는 것 — 어느 타입도 면제해 주지 않는 비용
네 개의 시계 정합. 차이는 정합이 깨졌을 때 무엇이 틀리는가뿐이다 — TIMESTAMP는 저장된 순간이 틀리고(대칭 오류로 숨음), DATETIME은 저장된 값의 기준이 틀린다(콘솔에서 바로 보임).

2-4. 선택 조건 — "글로벌 서비스라면"에 대한 내 결론

시각 컬럼을 한 종류로 보지 않는 것이 출발점이다. 과거·현재의 사건과 미래의 일정은 저장해야 할 것이 다르다.

세 갈래의 첫 질문은 "이 컬럼이 담는 것이 날짜인가, 벌어진 순간인가, 의도된 벽시계인가"다. 타입 이름부터 고르면 이 질문을 건너뛰게 된다.
(a) 사건 컬럼에 DATETIME(6) + UTC 고정을 고르는 근거 셋
1
2038 한계가 없어 같은 규약을 만료일 같은 미래 순간 컬럼에도 그대로 쓴다.테이블마다 타입이 갈리면 규약이 둘이 된다.
2
세션 존에 따라 값이 다르게 보이는 함정이 없어 "저장된 값 = UTC 벽시계"라는 단일 규칙만 지키면 된다.그 규칙은 어차피 TIMESTAMP를 써도 지켜야 하는 세션 존 정합과 같은 일이다.
3
대칭 오류로 숨지 않고 콘솔에서 바로 보이므로 회귀 테스트로 잡기 쉽다.단, 이 선택은 §3의 안전망 없이는 TIMESTAMP보다 위험하다 — 규율이 앱에 있으니까.
암기 규칙 — 세 줄 선택
사건은 Instant → DATETIME(6) UTC · 일정은 벽시계 + 존 ID · 날짜는 DATE

TIMESTAMP는 "2038 이전 + 다국어 직접 쓰기 or 수억 행"의 로그성 테이블에 한정. PostgreSQL이면 timestamptz. 가산점

3-1. before / after — JPA 엔티티

❌ before — 값이 "지금 이 서버가 있는 곳"의 벽시계에 묶인다
@Entity
public class Payment {
    @Id @GeneratedValue
    private Long id;

    @CreatedDate
    private LocalDateTime createdAt;
    // ① 타임존 없는 벽시계 — "어디 기준 09:00"인지 값이 모른다

    private LocalDateTime paidAt;
    // ② paidAt = LocalDateTime.now();
    //    → JVM 기본 존의 벽시계. 개발 PC(KST)와 컨테이너(UTC)에서
    //      서로 다른 값이 저장되고, DATETIME은 그 차이를 기록하지 않는다
}
✅ after — 사건은 Instant(순간), 미래 일정은 로컬 벽시계 + 존 ID로 분해
@Entity
public class Payment {
    @Id @GeneratedValue
    private Long id;

    @CreatedDate
    private Instant createdAt;   // ① 순간 — 어느 서버에서 만들어도 같은 값

    private Instant paidAt;      // ② paidAt = clock.instant();
                                 //    ← Clock 주입, 테스트에서 고정 가능
}

@Entity
public class EpisodeSchedule {
    @Id @GeneratedValue
    private Long id;

    @LocalWallClock              // 프로젝트 마커 — "의도적으로 로컬 벽시계"
    private LocalDateTime publishLocalAt; // 2026-09-01T23:00 사용자가 고른 벽시계
    private String        publishZoneId;  // "Asia/Seoul" — 규칙을 담는 IANA 존 ID
    private Instant       publishAtUtc;   // 정렬·스캔용 파생 캐시 — 규칙 바뀌면 재계산
}

@CreatedDate가 Instant 필드를 채우는 것은 Spring Data가 지원한다. "지금"을 Clock에서 꺼내려면 DateTimeProvider 빈을 등록해 @EnableJpaAuditing(dateTimeProviderRef = "...")로 연결한다 — 그러면 Auditing 시각도 테스트에서 고정된다. @LocalWallClock은 §3-2 ArchUnit 규약의 예외 근거가 되는 프로젝트 마커 애노테이션이다.

✅ after — DDL. "UTC"를 컬럼 코멘트로 남겨 규약을 스키마에도 적어 둔다
CREATE TABLE payment (
    id         BIGINT PRIMARY KEY AUTO_INCREMENT,
    -- DEFAULT 는 앱 밖 경로(콘솔·타 언어 배치)용 — 세션 존이 UTC 여야 앱이 넣는 값과 기준이 같다(§1-3)
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) COMMENT 'UTC',
    paid_at    DATETIME(6) NULL                                 COMMENT 'UTC'
);

CREATE TABLE episode_schedule (
    id               BIGINT PRIMARY KEY AUTO_INCREMENT,
    publish_local_at DATETIME    NOT NULL COMMENT 'publish_zone_id 기준 로컬 벽시계',
    publish_zone_id  VARCHAR(64) NOT NULL COMMENT 'IANA 존 ID',
    publish_at_utc   DATETIME(6) NOT NULL COMMENT '파생 캐시(UTC). 재계산 가능',
    INDEX idx_publish_at_utc (publish_at_utc)
);

설정 4종 — 네 개의 시계를 전부 UTC로 못 박는다

before — 시계 네 개를 전부 "기본값"에 맡긴 상태
spring.datasource.url=jdbc:mysql://db:3306/app 한 줄. ① JVM: OS 존 · ② Hibernate: ①과 같음 · ③ 드라이버: SERVER(=④를 따라감) · ④ DB: SYSTEM(DB OS 존) → 앱 서버 OS와 DB 서버 OS의 TZ가 우연히 같을 때만 맞는다.
1JVM 기본 존 — 실행 옵션으로

애플리케이션 코드에서 TimeZone.setDefault()로 바꾸는 것은 이미 초기화된 것들(로깅, 커넥션 풀)에 늦게 적용될 수 있어 실행 옵션으로 준다.

# Dockerfile
ENV TZ=UTC
ENV JAVA_TOOL_OPTIONS="-Duser.timezone=UTC"
2Hibernate → JDBC 기준 존

JVM 기본 존이 무엇이든 UTC 벽시계로 바인딩한다. Jackson은 표시 층 — 응답이 ISO-8601 + 오프셋(Z)로 나가게.

# application.yml
spring:
  jpa:
    properties:
      hibernate.jdbc.time_zone: UTC
  jackson:
    time-zone: UTC   # (표시 층)
3드라이버 커넥션 존 (+ 세션까지)

forceConnectionTimeZoneToSession=true는 접속 시 세션 time_zone도 같은 값으로 SET 해 ④까지 맞춘다(서버 설정을 만질 수 없을 때). 단 이름 있는 존(UTC)을 세션에 SET 하려면 MySQL에 tz 테이블이 로드돼 있어야 한다.

# application.yml
spring:
  datasource:
    url: jdbc:mysql://db:3306/app?connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true
4DB 서버 기본 세션 존

드라이버 옵션이 세션을 덮더라도, 콘솔·배치·타 언어 클라이언트·DEFAULT CURRENT_TIMESTAMP를 위해 서버 기본값도 맞춘다. '+00:00' 오프셋 표기는 tz 테이블 없이도 동작한다.

# my.cnf
[mysqld]
default-time-zone = '+00:00'

3-2. 타입 규약을 ArchUnit으로 — "규칙을 아는 사람"에 의존하지 않기

암기 — 자바 시간 타입 규약 세 줄
순간은 Instant(저장·전송·비교의 기본) · 로컬 벽시계는 LocalDateTime("존을 모르는 것이 의도"인 자리에만) · ZonedDateTime은 계산용(벽시계 + 존 ID로 순간을 구할 때 잠깐, 저장은 분해해서)

이 규약을 리뷰 코멘트로만 두면 세 번째 신규 입사자 때 깨진다. 빌드에 넣는다.

✅ ArchUnit — 엔티티 필드 타입 규약 + JVM 기본 존 의존 호출 금지
@AnalyzeClasses(packages = "com.example")
class TimeTypeRulesTest {

    // 규약 1: 엔티티 필드에 LocalDateTime 금지 — 예외는 @LocalWallClock 으로 의도를 밝힌 필드뿐
    @ArchTest
    static final ArchRule entities_store_instants =
        noFields().that().areDeclaredInClassesThat().areAnnotatedWith(Entity.class)
            .and().areNotAnnotatedWith(LocalWallClock.class)
            .should().haveRawType(LocalDateTime.class)
            .because("엔티티의 시각은 Instant(UTC 순간)로 저장한다. 미래 로컬 일정만 @LocalWallClock 으로 표시");

    // 규약 2: JVM 기본 존에 몰래 의존하는 API 호출 금지 — '지금'은 주입받은 Clock 에서 꺼낸다
    @ArchTest
    static final ArchRule no_default_zone_dependency =
        noClasses().should().callMethod(LocalDateTime.class, "now")
            .orShould().callMethod(ZoneId.class, "systemDefault")
            .orShould().callConstructor(Date.class)
            .because("서버가 어디에 있든 같은 값이어야 한다. Clock.instant() / ZoneId.of(사용자 존)을 쓴다");
}
안전망의 요령 — 사고 사슬의 첫 고리를 빌드 단계에서 끊는다
규약 2가 잡는 것이 사고 ①의 첫 고리(LocalDateTime.now())다. 네 번째 고리(배치 오작동)에서 잡으면 이미 데이터가 섞인 뒤다. KST 벽시계는 대개 LocalDateTime.now()에서 태어난다.

3-3. 타임존을 바꿔 돌리는 회귀 테스트 — "DB에 실제로 적힌 문자열"을 단정한다

설정 네 개는 누군가 URL을 정리하다가, 베이스 이미지를 바꾸다가, DB를 이전하다가 하나씩 사라진다. 사라지면 빌드가 깨져야 한다.

요령 ⑴DB 컨테이너와 테스트 JVM을 일부러 UTC가 아닌 존으로 띄운다

설정이 OS 존을 이기는지 증명한다. UTC 머신에서만 통과하는 테스트는 아무것도 증명하지 못한다.

요령 ⑵드라이버 변환을 거치지 않도록 값을 문자열로 꺼내 단정한다

사고 ②처럼 대칭 오류가 숨는 것을 막는다. repo.findById()로 읽어 비교하면 왕복 상쇄로 거짓 통과한다.

✅ Testcontainers — 비-UTC DB + 문자열 단정 + DEFAULT 경로 정합 검사
@SpringBootTest
@Testcontainers
@Tag("timezone")                     // 아래 빌드 매트릭스가 이 태그를 여러 JVM 존에서 돌린다
class TimeZoneRegressionTest {

    // ⑴ DB OS 존을 일부러 UTC가 아닌 곳으로 — 설정(④)이 SYSTEM 을 이기는지 확인
    @Container
    static final MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0")
            .withEnv("TZ", "America/Los_Angeles");

    @Autowired PaymentRepository repo;
    @Autowired JdbcTemplate jdbc;

    @Test
    void 세션_존은_UTC_로_고정돼_있다() {
        // ③④ 정합 — 드라이버 force 옵션 또는 서버 default-time-zone 이 살아 있는가
        assertThat(jdbc.queryForObject("SELECT @@session.time_zone", String.class))
                .isIn("UTC", "+00:00");
    }

    @Test
    void 어떤_JVM_존에서_돌려도_DB에는_UTC_벽시계가_적힌다() {
        Instant paidAt = Instant.parse("2026-08-31T00:00:00Z");
        Long id = repo.save(Payment.paid(paidAt)).getId();

        // ⑵ 드라이버의 역변환을 거치지 않는 "실제로 적힌 값" — 문자열로 꺼낸다
        String raw = jdbc.queryForObject(
                "SELECT DATE_FORMAT(paid_at, '%Y-%m-%d %H:%i:%s') FROM payment WHERE id = ?",
                String.class, id);
        assertThat(raw).isEqualTo("2026-08-31 00:00:00");   // KST 09:00 이 적혔다면 여기서 깨진다

        // 앱 경로로 읽어도 같은 순간
        assertThat(repo.findById(id).orElseThrow().getPaidAt()).isEqualTo(paidAt);
    }

    @Test
    void DB_기본값_CURRENT_TIMESTAMP_도_UTC_로_들어간다() {
        // §1-3의 "한 컬럼 두 기준" 방지 — DEFAULT 로 채워진 created_at 과 UTC 로 넣은 paid_at 의 기준이 같은가
        long id = 999_999L;
        jdbc.update("INSERT INTO payment (id, paid_at) VALUES (?, UTC_TIMESTAMP(6))", id);
        Integer diffSec = jdbc.queryForObject(
                "SELECT ABS(TIMESTAMPDIFF(SECOND, created_at, paid_at)) FROM payment WHERE id = ?",
                Integer.class, id);
        assertThat(diffSec).isLessThan(5);                  // 9시간(32400초) 차이면 세션 존이 틀린 것
    }
}
함정 — "어떤 JVM 존에서 돌려도"를 TimeZone.setDefault()로 흉내 내지 않는다
드라이버와 커넥션 풀은 접속 시점의 기본 존을 잡아 두므로 런타임에 바꾼 값이 반영되지 않아 거짓 통과가 난다. 대신 빌드 매트릭스로 JVM 자체를 다른 존으로 띄운다.
✅ build.gradle — 같은 테스트를 세 존에서. 하나라도 깨지면 설정 ①②③④ 중 무엇이 새는지 바로 안다
["UTC", "Asia/Seoul", "America/Los_Angeles"].each { zone ->
    tasks.register("testIn${zone.replace('/', '_')}", Test) {
        systemProperty "user.timezone", zone
        useJUnitPlatform { includeTags "timezone" }
    }
}
테스트 1③④ 정합

@@session.time_zone이 UTC인가 — 드라이버 force 옵션 또는 서버 default-time-zone이 살아 있는지.

테스트 2①②③ 정합

JVM 존이 무엇이든 DB에 적힌 문자열이 UTC 벽시계인가 — 드라이버를 거치지 않은 값으로.

테스트 3DB 기본값 경로 정합

DEFAULT CURRENT_TIMESTAMP와 앱 경로의 기준이 같은가 — 세션 존이 KST로 새면 32400으로 깨진다.

운영 안전망 하나 더 — 정합성 점검 쿼리. SELECT COUNT(*) FROM payment WHERE created_at > UTC_TIMESTAMP() 가 0이 아니면 알림. 미래에 생성된 행은 존이 밀린 증거다 — 사고 ①이 이 쿼리 하나로 첫날 잡혔을 것이다.

3-4. 글로벌 서비스 시간 원칙 7가지 — 각 원칙이 스키마에 착지하는 지점

22장의 원칙은 4장에서 컬럼 하나하나로 착지한다. 목록으로 인출한다 — 저장 둘 · 변환 둘 · 고정 셋.

암기 카드 — 원칙 → 착지
1
저장은 UTC 순간.과거·현재의 사건은 UTC 하나로 적는다.DATETIME(6) + 네 시계 UTC 고정(또는 TIMESTAMP) · 컬럼 코멘트 'UTC' · DEFAULT CURRENT_TIMESTAMP도 UTC 세션에서만
2
표시는 사용자 타임존, 변환은 가장 바깥에서.사용자 존은 프로필/요청에서 받고, 변환은 응답 직렬화 층에서.DB에서 CONVERT_TZ(created_at, ...)로 표시용 변환을 하지 않는다. 특히 WHERE CONVERT_TZ(paid_at, ...) >= ...처럼 컬럼에 함수를 씌우면 인덱스를 못 탄다(인덱스가 있는데 풀스캔) — "오늘 매출" 같은 일 단위 경계는 앱이 비즈니스 존으로 시작·끝 순간을 계산해 UTC 상수로 바인딩(paid_at >= :startUtc AND paid_at < :endUtc)

4. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 답의 깊이가 갈리는 지점, 추가는 이 페이지에서 보탠 문항.

"TIMESTAMP를 쓰면 DB가 UTC로 저장해 주니 앱은 타임존을 신경 안 써도 되지 않나요?"

아니다 — 책임의 위치가 바뀔 뿐 없어지지 않는다. 사슬로 답한다.

  1. TIMESTAMP의 UTC 변환은 세션 time_zone을 기준으로 하고, 세션 존은 DB 서버 OS(SYSTEM)나 드라이버 설정(connectionTimeZone + forceConnectionTimeZoneToSession)이 정한다.
  2. 그 세션 존이 실제와 다르면 저장되는 순간 자체가 밀리고(사고 ②), 같은 드라이버로 읽으면 대칭으로 되돌아와 앱에선 안 보인다.
  3. 게다가 앱 안에서 LocalDateTime.now()로 만든 값은 드라이버가 변환 없이 벽시계로 보내므로, 서버가 그것을 세션 존으로 해석하는 순간 JVM 존과 세션 존이 다르면 또 밀린다.

즉 TIMESTAMP가 면제해 주는 것은 "여러 클라이언트가 각자 UTC로 변환하는 수고"이지 "네 시계의 정합"이 아니다. 그리고 그 대가로 2038·세션 의존·묵시 DEFAULT를 낸다 — 양면을 붙여서 답한다.

"DATETIME에 UTC를 저장하기로 했는데, 누군가 KST 벽시계를 넣으면 DB는 모릅니다. 어떻게 막나요?"

세 층으로 답한다.

  1. 첫 고리를 빌드에서 끊는다 — 엔티티 필드 LocalDateTime 금지 + LocalDateTime.now()/ZoneId.systemDefault()/new Date() 호출 금지를 ArchUnit으로(§3-2). KST 벽시계는 대개 LocalDateTime.now()에서 태어난다.
  2. 값이 밀릴 수 있는 시계 네 개를 설정으로 못 박는다 — JVM -Duser.timezone=UTC, hibernate.jdbc.time_zone=UTC, connectionTimeZone=UTC, DB default-time-zone='+00:00'(§3-1). 넷이 같으면 변환이 항등이라 실수해도 안 밀린다.
  3. 회귀 테스트로 지킨다 — DB 컨테이너를 UTC 아닌 존으로 띄우고 JVM도 여러 존으로 돌리며, 드라이버를 거치지 않은 문자열로 저장값을 단정(§3-3).

여기에 운영 안전망 하나 — 정합성 점검 쿼리: created_at이 UTC_TIMESTAMP()보다 미래인 행이 있으면 알림. 미래에 생성된 행은 존이 밀린 증거다(사고 ①이 이 쿼리 하나로 첫날 잡혔을 것이다).

"2038년 문제는 12년 뒤 얘기인데 지금 왜 신경 쓰나요?"

미래 시각 컬럼은 오늘 이미 2038년을 넘는 값을 받기 때문이다 — 영구 이용권 expires_at = 9999-12-31, 30년 만기 계약, "무기한"을 먼 미래로 표현하는 관례. strict 모드면 INSERT가 에러로 죽고, 아니면 0 값이 들어가 "만료일 0000-00-00"이라는 데이터가 생긴다. 반대편 경계도 있다 — 1970년 이전 생년월일은 TIMESTAMP에 애초에 못 들어간다.

그리고 "나중에 바꾸면 되지"의 비용이 크다 — 타입 변경은 테이블 재작성이라 수억 건이면 무중단 DDL 도구를 동원하는 작업이고, 그 사이 TIMESTAMP로 쌓인 값은 세션 존에 따라 다르게 읽히므로 변환 시점의 세션 존까지 맞춰야 한다. 즉 2038은 "먼 미래의 만기"가 아니라 "미래 시각을 담는 모든 컬럼에 대해 지금 타입을 고르는 기준"이다.

가산점 이 문제는 MySQL 함수 층이 아니라 컬럼 타입의 4바이트 저장 포맷에서 오는 것이라 SQL 함수의 64비트 지원과 별개다.

"'매일 밤 11시 신작 공개'를 그냥 UTC로 환산해 저장하면 안 되나요? 저장은 UTC가 원칙이라면서요."

"저장은 UTC"는 과거·현재의 사건에 대한 원칙이고, 미래 일정은 저장할 것이 다르다. 사용자가 정한 것은 "서울 벽시계로 23:00"이라는 규칙이지 특정 UTC 순간이 아니다. 지금 14:00Z로 환산해 저장하면 —

  1. DST가 있는 존이면 전환일 이후 환산 결과가 1시간 바뀌어 "22:00 공개"가 된다.
  2. 그 나라가 DST를 폐지하거나 도입하면(tzdata 변경) 이미 저장된 모든 미래 행이 틀린다.
  3. 되돌릴 근거(원래 벽시계와 존)가 값에 없다.

그래서 로컬 벽시계 + IANA 존 ID를 원본으로 저장하고, UTC는 스캔·정렬용 파생 캐시로 두되 존 규칙이 바뀌면 원본에서 재계산한다. 오프셋(+09:00)이 아니라 존 ID(Asia/Seoul)여야 하는 이유도 같다 — 오프셋은 "지금의 결과"이고 존 ID는 "규칙"이다. 스캐너(배치)는 파생 UTC 컬럼으로 "지금 공개할 것"을 찾되, 실제 공개 직전에 원본으로 한 번 더 검증하면 규칙 변경 사이의 창도 막는다. DST 전환일에 존재하지 않는 시각(02:30이 없는 날)의 처리는 22장 문서의 몫이다.

"이미 DATETIME에 KST 벽시계로 3년치가 쌓여 있는 서비스가 글로벌 진출합니다. 어떻게 전환하시겠어요?" 시니어 변별

"컬럼의 의미를 바꾸는 마이그레이션"이라 타입 변경보다 어렵다 — 값의 모양은 같고 기준만 바뀌기 때문에, 전환 중에 "이 행은 어느 기준인가"를 잃으면 복구가 안 된다. 순서로 답한다.

  1. 진단 먼저 — 정말 전부 KST인가? 사고 ①처럼 이미 UTC와 KST가 섞여 있을 수 있다. 배포 이력·created_at이 미래인 행·NOW() 기준 배치의 오작동 로그로 경계를 찾는다. 섞여 있으면 구간별 오프셋을 먼저 확정한다.
  2. 쓰기 경로부터 UTC로 고정 — §3-1의 네 시계 설정과 ArchUnit을 먼저 넣되, 기존 컬럼은 건드리지 않고 새 컬럼(paid_at_utc DATETIME(6))에 이중 쓰기한다. 이 시점부터 새 행은 두 컬럼이 다 채워진다.
  3. 백필 — 기존 행을 paid_at_utc = CONVERT_TZ(paid_at, 'Asia/Seoul', '+00:00')로 채운다(이름 있는 존을 쓰려면 tz 테이블 로드 필요, 또는 KST는 DST가 없으므로 paid_at - INTERVAL 9 HOUR로 충분하다 — 한국이 DST가 없는 것이 이 마이그레이션의 행운이고, DST가 있는 존이었다면 행마다 규칙을 적용해야 한다). 수억 건이면 PK 범위로 쪼개 배치로 돌린다(무중단 DDL의 백필 절차와 같다).
  4. 읽기 전환 → 검증 → 정리 — 읽기를 새 컬럼으로 옮기고, 두 컬럼의 차이가 정확히 9시간인지 전수 점검 쿼리로 확인한 뒤, 구 컬럼을 삭제하고 새 컬럼을 원래 이름으로 돌리거나 그대로 둔다. 컬럼 코멘트에 'UTC'를 남긴다.
  5. 이 기회에 미래 일정 컬럼을 분리 — 예약 공개 시각처럼 "벽시계가 의도"인 컬럼은 UTC로 환산하는 것이 아니라 존 ID 컬럼을 추가해 §2-4(b) 구조로 바꾼다.

전환의 트레이드오프를 양면으로 — 이중 쓰기 기간에는 코드가 두 컬럼을 알아야 하고 저장 공간이 늘지만, 한 번의 UPDATE로 제자리 변환하는 것은 실행 도중 앱이 어느 기준으로 읽어야 하는지 정의할 수 없어 서비스 중단 없이는 불가능하다. 마지막으로 — 이 전환이 필요해진 이유가 곧 "처음에 네 시계를 UTC로 못 박고 Instant를 썼어야 하는 이유"라고 닫는다.

"'The server time zone value KST is unrecognized' 오류가 나서 URL에 serverTimezone=UTC를 붙여 없앴습니다. 뭐가 문제죠?" 추가

그 오류는 드라이버(시계 ③)가 서버 세션 존(시계 ④)을 알아내지 못했다는 뜻이다. 서버가 SYSTEM을 보고하는데 OS 존 이름이 KST처럼 JVM이 모르는 약어일 때 난다. 여기에 serverTimezone=UTC를 넣는 것은 "서버가 UTC라고 믿어라"이지 서버를 UTC로 만드는 것이 아니다.

결과가 사고 ②다 — 드라이버는 Instant를 KST → UTC로 변환해 보내고, 실제로 KST인 서버가 그것을 KST로 다시 해석해 9시간 이른 순간을 저장한다. 읽을 때 대칭으로 되돌아와 앱에선 정상, 콘솔·배치·타 언어에서만 틀린다.

올바른 처치는 셋 중 하나 — ⑴ DB 서버 OS 존을 IANA 이름(Asia/Seoul)으로 바꾸거나 default-time-zone을 명시, ⑵ connectionTimeZone을 실제 세션 존과 일치시키기, ⑶ 가장 좋은 것은 connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true로 세션까지 UTC로 맞춰 ③=④를 강제하는 것. 그리고 §3-3의 문자열 단정 테스트가 있었다면 이 URL 변경이 빌드에서 깨졌을 것이다.

"DATETIME은 타임존과 무관한데, 왜 DB 세션 존까지 UTC로 맞춰야 하나요?" 추가

DATETIME 컬럼에 앱이 넣는 값은 세션 존과 무관하다. 그러나 DB가 스스로 만드는 값은 전부 세션 존의 벽시계다 —

  • DEFAULT CURRENT_TIMESTAMP / ON UPDATE CURRENT_TIMESTAMP로 채워지는 값 → 앱은 UTC, DB 기본값은 KST인 "한 컬럼 두 기준".
  • 배치·콘솔의 NOW() → 사고 ①처럼 UTC 컬럼과 KST 기준선을 비교하게 된다.
  • 타 언어 클라이언트가 NOW()로 넣는 값.

그래서 "타임존 무관"은 "설정 무관"이 아니다. §3-3의 세 번째 테스트(DEFAULT 경로와 앱 경로의 차이가 5초 미만)가 정확히 이것을 지킨다. 세션 존이 KST로 새면 32400으로 깨진다.

"Instant를 저장했다가 읽었더니 값이 달라져 테스트가 깨집니다. 왜죠?" 추가

두 가지를 의심한다.

  1. 소수 초 자릿수 — 컬럼이 DATETIME(= (0))이면 초 아래가 반올림된다(TIME_TRUNCATE_FRACTIONAL이면 절삭). Instant는 나노초를 가지므로 .9995초가 다음 초로 올라가 초 경계를 넘기도 한다. 처방: DATETIME(6)으로 선언하거나 앱에서 truncatedTo(ChronoUnit.MICROS)로 맞춘다.
  2. 시계 정합 — 값이 정확히 시간 단위(9시간, 8시간 …)로 다르면 네 시계 중 하나가 어긋난 것이다. 다만 대칭 오류(사고 ②)는 왕복에서 상쇄돼 이 테스트로는 안 잡히므로, 문자열 단정(§3-3)이 따로 필요하다.

소수 초 처방은 가산점 포인트다 — "왜 (6)인가"에 "Instant의 정밀도와 반올림 경계"로 답할 수 있으면 된다.

"'오늘 매출'을 뽑을 때 WHERE CONVERT_TZ(paid_at, '+00:00', '+09:00') >= '2026-08-31'로 쓰면 왜 안 되나요?" 추가

두 가지 원칙을 동시에 어긴다.

  1. 컬럼에 함수를 씌우면 인덱스를 못 탄다 — paid_at 인덱스가 있어도 행마다 변환해 비교하므로 풀스캔이다(인덱스가 있는데 풀스캔).
  2. 변환은 가장 바깥에서(원칙 2) — DB 안에서 표시용 변환을 하는 순간 "어느 존 기준인가"가 SQL 곳곳에 흩어진다.

처방: 앱이 비즈니스 존(Asia/Seoul)으로 "오늘"의 시작·끝 순간을 계산해 UTC 상수로 바인딩한다 — paid_at >= :startUtc AND paid_at < :endUtc. 컬럼은 그대로라 인덱스 범위 스캔이 되고, 기준 시각은 Clock에서 나오므로 테스트에서 고정된다(원칙 6).

"테스트에서 TimeZone.setDefault()로 존을 바꿔가며 검증하면 되지 않나요? 왜 빌드 매트릭스까지?" 추가

드라이버와 커넥션 풀은 접속 시점의 JVM 기본 존을 잡아 둔다. 테스트 메서드 안에서 setDefault()를 바꿔도 이미 열린 커넥션의 변환 기준은 그대로라 "바꿨는데도 통과"라는 거짓 통과가 난다. 반대로 어떤 컴포넌트는 호출 시점의 기본 존을 읽어 테스트 순서에 따라 결과가 달라지는 플레이키 테스트가 된다.

그래서 JVM 자체를 다른 존으로 띄운다 — Gradle에서 systemProperty "user.timezone", zone을 준 Test 태스크를 존별로 등록하고 @Tag("timezone")만 돌린다. 같은 이유로 운영에서도 ① 시계는 코드의 setDefault()가 아니라 실행 옵션(JAVA_TOOL_OPTIONS=-Duser.timezone=UTC)으로 준다.

"PostgreSQL이었다면 뭘 고르나요? timestamptz는 타임존을 저장하는 타입인가요?" 추가

이름과 달리 존을 저장하지 않는다. timestamptz(timestamp with time zone)는 UTC 순간을 8바이트로 저장하고 세션 TimeZone으로 입출력 변환하는 타입이다 — MySQL TIMESTAMP의 역할에 2038 한계가 없는 셈이라 사건 컬럼의 답이 된다. timestamp(without time zone)는 MySQL DATETIME에 해당한다.

다만 "존을 저장하지 않는다"는 점은 같으므로 미래 일정은 여전히 로컬 벽시계 + IANA 존 ID를 분해 저장해야 하고, 세션 TimeZone에 의존하는 만큼 네 시계 정합도 그대로 필요하다. 타입이 바뀌어도 원칙 7가지는 바뀌지 않는다. 가산점

"배치의 기준 시각을 SQL의 NOW()로 쓰면 왜 안 되나요? 편한데요." 추가

NOW()/CURRENT_TIMESTAMP는 시계 ④(DB 세션 존)의 벽시계다. 앱이 넣은 컬럼 값은 시계 ①②③을 거쳐 온 값이므로, 둘을 한 WHERE에서 비교하는 순간 서로 다른 시계가 만든 값끼리 비교하게 된다 — 사고 ①의 4번째 고리가 정확히 이것이다.

처방(원칙 6): 기준 시각은 앱이 주입받은 Clock에서 Instant로 계산해 파라미터로 넘긴다(created_at < :cutoffUtc). 이러면 ⑴ 컬럼과 기준선이 같은 경로를 지나 같은 기준이 되고, ⑵ 테스트에서 "지금"을 고정할 수 있으며, ⑶ 배치 로그에 기준 시각이 남는다. UTC가 꼭 필요한 SQL 상수는 UTC_TIMESTAMP()를 쓴다 — 정합성 점검 쿼리처럼 "앱 경로와 독립적으로" 확인하고 싶을 때다.

한 줄 요약
TIMESTAMP는 세션 타임존 → UTC로 변환해 4바이트 epoch 초로 적고 읽을 때 되돌리는 "순간" 타입이라 자동 UTC 정규화를 얻는 대신 2038년 범위와 세션 존 의존을 내고, DATETIME은 변환 없이 벽시계를 그대로 적는 타입이라 넓은 범위와 예측 가능성을 얻는 대신 타임존 정보가 사라져 "이 컬럼은 UTC"라는 규율을 앱이 지켜야 하므로 — 글로벌 서비스라면 사건 시각은 DATETIME(6) + 네 개의 시계(JVM·Hibernate·JDBC·DB 세션) UTC 고정 + Instant 타입 규약(ArchUnit) + 타임존을 바꿔 도는 회귀 테스트를 한 세트로 고르고, 미래 일정은 로컬 벽시계 + IANA 존 ID를 원본으로 분해 저장해 UTC는 재계산 가능한 파생 컬럼으로만 두며, TIMESTAMP는 2038 이전 값만 오고 다국어 클라이언트가 직접 쓰는 로그성 테이블에 한정한다.
