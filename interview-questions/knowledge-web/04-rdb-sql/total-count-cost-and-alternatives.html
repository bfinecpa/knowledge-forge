목록 API의 total count 비용
"전체 몇 건 중 몇 페이지"는 목록 본체보다 비싼 요구다

핵심 관전 포인트 — 첫 답변으로 그대로 말하기
질문: "목록 API의 전체 건수(total count) 조회가 대용량에서 비싼 이유와 대안은? (근사치, 카운트 캐싱, 무한 스크롤 전환)"
목록 쿼리는 LIMIT 20에서 멈추지만 COUNT(*)는 조건에 맞는 행을 전부 만나야 끝난다 — 비용이 페이지 크기가 아니라 조건에 맞는 전체 행 수 N에 비례한다. InnoDB가 행 수를 메타데이터로 못 드는 이유는 MVCC다: 트랜잭션마다 보이는 행이 달라 "정답인 숫자"가 하나가 아니므로, 행마다 가시성을 판정하며 셀 수밖에 없다. 조건 컬럼이 인덱스에 다 없으면 그 N건마다 북마크 룩업(랜덤 I/O)까지 붙는다. 대안은 다섯 갈래 — ① 커버링 인덱스로 세기 ② 근사치 ③ 카운트 캐싱·카운터 테이블 ④ 다음 페이지 존재 여부만(Slice) ⑤ 무한 스크롤·커서·검색 엔진 — 각각 정확도 · 정합성 · UX 중 하나를 내주는 거래다. Spring Data의 Page는 count 쿼리를 자동으로 붙이므로 기본은 Slice, Page는 근거 필수라는 규약을 코드(ArchUnit)와 계측(count 분리 측정)으로 고정한다. 그 가격표를 기획에 보여주는 것까지가 백엔드의 일이다.
출제 의도 — 무엇을 보는 질문인가
"COUNT는 느리다"는 현상 지식이 아니라 세 가지를 한 번에 본다. ⑴ 왜 느린지를 저장 엔진의 메커니즘(멈출 수 없음 + MVCC + 무엇을 읽나)으로 설명하는가 ⑵ 대안마다 무엇을 내주는지를 얻는 것과 함께 양면으로 말하는가 ⑶ 그 선택을 기억이 아니라 팀의 규약(코드·계측)으로 고정할 수 있는가. 그리고 이 요구의 비용을 기획과 협상해 봤는가.
역할 구분 — 같은 "느린 목록 API"의 두 가지 다른 비용
offset 비용건너뛰기 위해 읽는 행. LIMIT 100000, 20 — 깊은 페이지네이션 문서의 몫 count 비용세기 위해 읽는 행. SELECT COUNT(*) WHERE … — 이 문서의 몫
둘은 따로 측정하고 따로 고친다(4-1절). 섞어 말하는 순간 진단이 흐려진다.

1. 왜 비싼가 — "세는 것"의 비용을 메커니즘 사슬로

이 절이 문서의 심장이다. "COUNT는 전체를 다 훑어서 느리다"는 맞지만 뭉뚱그린 말이다. 면접에서는 왜 다 훑어야만 하는지(멈출 수 없는 이유 + 메타데이터로 못 드는 이유)와 훑을 때 무엇을 읽는지(인덱스 페이지 vs 행 페이지)를 고리별로 짚는다.

암기 카드 — COUNT 비용 사슬 4고리 (이 순서로 말한다)
1
멈출 수 없다목록은 LIMIT에서 멈춰 페이지 크기(상수)에 비례, COUNT는 조건에 맞는 행 N건을 전부 만나야 끝난다
2
미리 세어 둘 수 없다 — MVCC트랜잭션마다 보이는 행이 다르다 → 단일 정답 없음 → 행마다 DB_TRX_ID를 리드 뷰와 비교해야 한다
3
무엇을 읽느냐가 배수를 정한다조건 컬럼이 인덱스에 다 있으면 리프 순차 읽기(커버링), 없으면 N회 북마크 룩업 = 랜덤 I/O
4
그래도 N에 비례한다커버링은 배수만 줄이지 차원을 바꾸지 못한다 — 차원을 바꾸려면 3절의 대안이 필요하다

연상: "멈추지 못하고, 미리 못 세고, 무엇을 읽느냐가 배수, 그래도 N"

1-1. 목록 쿼리는 20건에서 멈추고, COUNT는 멈출 수 없다

비유: 줄 서 있는 사람들에게 앞 20명만 번호표를 나눠 주는 일은 줄이 100명이든 300만 명이든 똑같이 20걸음이면 끝난다. 그런데 "줄에 총 몇 명이냐"에 답하려면 줄 끝까지 걸어가야 한다. 같은 줄을 상대하는 두 일인데 비용의 차원이 다르다.

그림 1. 같은 인덱스 구간을 상대하는 두 쿼리의 스캔 범위 — 목록은 STOP 지점이 있고, COUNT는 END까지 간다
-- 목록 본체: 인덱스 (seller_id, status, created_at)를 타고
-- 조건에 맞는 첫 20건을 읽는 순간 끝난다. 비용 ∝ 페이지 크기(20)
SELECT id, amount, created_at
  FROM orders
 WHERE seller_id = 42 AND status = 'PAID'
 ORDER BY created_at DESC
 LIMIT 20;                       -- ← 여기서 멈춘다

-- 총 건수: 조건에 맞는 행이 300만 건이면 300만 건을 전부 "만나야" 끝난다.
-- 비용 ∝ 조건에 맞는 전체 행 수(N)
SELECT COUNT(*)                  -- ← 멈출 조건이 없다
  FROM orders
 WHERE seller_id = 42 AND status = 'PAID';
함정 — "목록 API가 느리다"의 범인은 목록이 아닌 경우가 아주 흔하다
느린 것은 옆에 붙은 count다. 그래서 목록 쿼리와 count 쿼리의 시간을 따로 재지 않으면(5-1절) 엉뚱한 곳(목록 쿼리 튜닝)에 시간을 쓴다.

1-2. InnoDB는 왜 행 수를 메타데이터로 못 들고 있나 — MVCC

"테이블에 행 수를 저장해 두고 INSERT/DELETE 때 ±1 하면 되지 않나?" MyISAM은 실제로 그렇게 한다 — 테이블 단위 락이라 한 시점에 행 수가 하나뿐이므로 SELECT COUNT(*) FROM t가 메타데이터 조회 한 번으로 끝난다.

InnoDB가 그럴 수 없는 이유가 MVCC(다중 버전 동시성 제어)다. 읽기가 락을 잡지 않도록 행의 여러 버전을 동시에 보관하고, 각 트랜잭션은 자기 리드 뷰(시작 시점에 어떤 트랜잭션들이 진행 중이었는지 찍어 둔 스냅샷) 기준으로 "자기에게 보이는 버전"만 읽는다.

비유: 영화관 좌석 예매. 결제 진행 중인 좌석은 예매자 본인에게는 이미 자기 자리지만 다른 사람에게는 아직 빈자리다. "지금 남은 좌석 수는?"에 대한 답이 누가 묻느냐에 따라 다르다. 그래서 벽에 "남은 좌석: 37"이라고 못 써 붙인다 — 물어본 사람마다 좌석을 하나하나 확인해 줄 수밖에 없다.

그림 2. 리드 뷰가 다르면 같은 물리 행 집합에서 보이는 행이 다르다 — 그래서 COUNT는 "판정하며 세기"다
비용이 더 커지는 조건

동시 갱신이 많거나 긴 트랜잭션이 undo를 쌓아 두면, 행마다 하는 가시성 판정이 undo 체인을 타고 거슬러 올라가야 해서 더 비싸진다. 긴 트랜잭션의 해악이 count에까지 번지는 지점이다(6절 사례의 "낮에만 느림").

다른 엔진도 같은 이유

MySQL 8.0은 조건 없는 COUNT(*)를 가장 작은 세컨더리 인덱스로 훑도록 최적화했지만 여전히 "끝까지 훑기"다. PostgreSQL도 count를 메타데이터로 들지 않고 pg_class.reltuples는 통계 추정치일 뿐이다.

1-3. 훑을 때 무엇을 읽나 — 커버링 카운트 vs 북마크 룩업 카운트

"다 훑는다"가 확정이어도 무엇을 훑느냐에 따라 I/O가 몇십 배 차이 난다. 비유: 학급 인원 중 "급식 신청자"를 세는 두 방법 — 신청 여부가 적힌 얇은 명단 한 장을 위에서 아래로 훑기(커버링) vs 명단에 이름만 있어서 학생 한 명씩 교실로 찾아가 물어보기(북마크 룩업). 세는 인원(N)은 같아도 걸음 수가 다르다. 판매자 42의 주문이 500만 건, 그중 PAID가 300만 건이라고 하자.

❌ before — 인덱스가 (seller_id)뿐
CREATE INDEX idx_orders_seller ON orders (seller_id);

SELECT COUNT(*) FROM orders
 WHERE seller_id = 42 AND status = 'PAID';
-- EXPLAIN: key = idx_orders_seller
--          Extra = Using where
-- 세컨더리 인덱스에서 판매자 42의 PK 500만 개를 얻고,
-- PK마다 클러스터드 인덱스를 다시 탐색(북마크 룩업)해
-- status를 읽어 PAID인지 가른다.
-- → 랜덤 I/O 500만 회. 행 하나 500B면 16KB 페이지에
--   30여 행뿐 → 버퍼 풀에 다 못 올라가 디스크 읽기
✅ after — 조건 컬럼이 전부 인덱스 안
CREATE INDEX idx_orders_seller_status_created
    ON orders (seller_id, status, created_at);

SELECT COUNT(*) FROM orders
 WHERE seller_id = 42 AND status = 'PAID';
-- EXPLAIN: key = idx_orders_seller_status_created
--          Extra = Using index   ← 커버링
-- (seller_id=42, status='PAID') 구간의 리프 엔트리를
-- 연결 리스트 따라 순차로 읽으며 센다.
-- 엔트리 30B 안팎 → 페이지당 500개 안팎
-- → 300만 건 ≈ 6천 페이지 순차 I/O. 북마크 룩업 0회
북마크 룩업 카운트 (before)커버링 카운트 (after)
읽는 페이지행 페이지 — 크고 성기다 (페이지당 30여 행)인덱스 리프 — 작고 촘촘하다 (페이지당 500여 엔트리)
I/O 패턴랜덤 I/O N회 (PK마다 클러스터드 인덱스 재탐색)순차 I/O — 리프 연결 리스트 따라 읽기
버퍼 풀 적중률낮음 — 행 페이지가 다 올라가지 못함높음 — 페이지 수가 수십 분의 일
EXPLAIN ExtraUsing whereUsing index
N에 대한 비례∝ N × 랜덤 I/O 비용∝ N × (훨씬 작은) 순차 I/O 비용 — 여전히 N에 비례
가장 자주 놓치는 문장
커버링 인덱스는 count를 "덜 비싸게" 만들지 "싸게" 만들지 않는다 — 배수를 줄일 뿐 차원을 바꾸지는 못한다.

차원(∝ N)을 바꾸려면 정확도·정합성·UX 중 하나를 내주는 3절의 대안이 필요하다. "인덱스 걸면 됩니다"로 끝내면 반쪽 답이다.

1-4. 말하기 훈련 — 뭉뚱그린 표현을 사슬로 교체

뭉뚱그린 표현이름사슬로 말하면
"count는 전체를 다 봐서 느리다"비용 차원의 차이목록은 LIMIT에서 멈춰 페이지 크기에 비례, count는 멈출 수 없어 조건에 맞는 전체 행 수 N에 비례 → 페이지마다 재실행
"InnoDB는 행 수를 저장 안 한다"MVCC 리드 뷰트랜잭션마다 보이는 행이 다르다 → 단일 정답 없음 → 행마다 DB_TRX_ID를 리드 뷰와 비교(필요하면 undo 체인)하며 세야 한다
"인덱스 타면 좀 빠르다"커버링 vs 북마크 룩업조건 컬럼이 인덱스에 다 있으면 리프 순차 읽기(작고 촘촘한 페이지), 없으면 N회 랜덤 I/O(크고 성긴 행 페이지). 단, 둘 다 N에 비례
사슬 한 호흡 버전 (면접에서 이어서 말하기)
조건에 맞는 행 N건→ COUNT는 N건 전부 만나야 함 (멈출 수 없음)→ 행마다 MVCC 가시성 판정→ 조건 컬럼이 인덱스에 없으면 행마다 북마크 룩업 = 랜덤 I/O N회→ 응답 시간 ∝ N × 랜덤 I/O→ 커버링이면 리프 순차 읽기로 배수만 절감→ 그래도 ∝ N

2. Spring Data JPA — count는 어디서 몰래 나가나

대용량에서 count가 비싸다는 걸 알아도, 내 코드가 count를 날리고 있다는 사실 자체를 모르는 경우가 많다. Page가 그 주범이다.

2-1. Page는 count 쿼리를 자동으로 붙인다

// 이 한 줄이 SQL 두 개다
Page<Order> page = orderRepository.findBySellerIdAndStatus(sellerId, PAID, pageable);
// ① SELECT ... FROM orders WHERE seller_id=? AND status=? ORDER BY ... LIMIT 20 OFFSET 0
// ② SELECT COUNT(o.id) FROM orders o WHERE seller_id=? AND status=?   ← 자동 파생

Page는 getTotalElements()·getTotalPages()를 채워야 하므로 Spring Data가 count 쿼리를 파생해 한 번 더 실행한다. 다만 무조건은 아니다 — PageableExecutionUtils.getPage가 count를 건너뛰는 두 경우가 있다.

count 생략 ①첫 페이지 + 페이지 크기보다 적게 옴

총 건수 = 가져온 건수. 셀 필요가 없다.

count 생략 ②첫 페이지 아님 + 페이지 크기보다 적게 옴 (마지막 페이지)

총 건수 = offset + 가져온 건수. 역시 셀 필요가 없다.

함정 — 페이지가 꽉 차는 "대용량일 때만" count가 나간다
개발 DB의 데이터 몇십 건으로 테스트하면 페이지가 안 차서 count가 안 보이고, 운영에 올라가면 매 요청 count가 붙는다. "로컬에선 빨랐는데요"의 정체다. 그리고 2-2절의 fetch join 예외도 count가 실제로 실행될 때만 터진다.

2-2. 파생 count가 틀리거나 무거울 때 — countQuery 분리

@Query를 쓰면 Spring Data는 JPQL의 select … from 부분을 select count(…)로 바꿔 count 쿼리를 파생한다. 이 파생이 문제를 일으키는 경우가 셋이다: ① fetch join이 든 JPQL은 count로 바꿀 때 Hibernate가 예외 ② 예외가 안 나도 세는 데 필요 없는 조인이 count에 끌려 들어감 ③ 네이티브 쿼리는 파생 자체가 불안정.

❌ before — 목록용 JPQL을 그대로 count에 재사용
@Query("""
    select o from Order o
      join fetch o.seller s
      left join fetch o.coupon c
     where s.id = :sellerId and o.status = :status
    """)
Page<Order> findPage(Long sellerId, OrderStatus status, Pageable pageable);
// ① fetch join이 든 JPQL을 count로 바꾸면 Hibernate가 예외를 던진다
//    ("query specified join fetching, but the owner ... was not present in the select list")
//    — count가 실제로 실행될 때만(2-1절) 터지므로 개발 DB에서는 안 보인다
// ② 예외가 안 나더라도 세는 데 필요 없는 coupon 조인까지 count에 끌려 들어가 조인 비용을 두 번 낸다
// ③ 네이티브 쿼리(nativeQuery = true)는 파생 자체가 불안정하다
✅ after — 세는 데 필요한 최소 조건만 남긴 countQuery를 따로 준다
@Query(value = """
    select o from Order o
      join fetch o.seller s
      left join fetch o.coupon c
     where s.id = :sellerId and o.status = :status
    """,
    countQuery = """
    select count(o) from Order o
     where o.seller.id = :sellerId and o.status = :status
    """)
Page<Order> findPage(Long sellerId, OrderStatus status, Pageable pageable);
// count는 조인 없이 orders 한 테이블 + 커버링 인덱스 (seller_id, status, ...)로 끝난다

countQuery를 분리하는 이유는 두 가지다 — 실패를 막기 위해(fetch join), 그리고 count가 1-3절의 커버링 경로를 타도록 만들기 위해. 목록 쿼리는 표시할 컬럼이 많아 커버링이 안 되지만, count는 조건 컬럼만 있으면 되니 훨씬 가벼운 실행 계획을 줄 수 있다.

가산점 — Querydsl의 fetchResults()가 deprecated 된 이유가산점
같은 이유다. 목록은 fetch(), count는 조인을 뺀 별도 select(order.count()) 쿼리로 만들고, PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne)처럼 LongSupplier로 넘겨 2-1절의 "건너뛰기" 최적화까지 누리는 것이 정석이다. count 쿼리가 지연 실행되어야 건너뛸 수 있다는 점이 핵심이다 — 값을 미리 구해서 넘기면 건너뛰기가 무의미해진다.

2-3. 총 건수가 필요 없다면 — Slice로 전환

비유: 책을 넘기다 "다음 장이 있나?"만 알고 싶으면 한 장만 더 넘겨 보면 된다. 남은 페이지 수를 세지 않는다.

❌ before — 화면은 "더 보기" 버튼뿐인데 Page를 써서 매 요청 count가 붙는다
Page<Order> findBySellerIdAndStatus(Long sellerId, OrderStatus status, Pageable pageable);
// SQL ① ... LIMIT 20 OFFSET 0
// SQL ② SELECT COUNT(...) ...     ← 매 요청, N건 스캔
✅ after — 반환 타입 한 줄만 Slice로. count 쿼리가 사라진다
Slice<Order> findBySellerIdAndStatus(Long sellerId, OrderStatus status, Pageable pageable);
// 실행되는 SQL: ... LIMIT 21 OFFSET 0   ← 페이지 크기 + 1건을 요청
// 21번째 행이 있으면 hasNext = true, 응답에는 20건만 담는다.
// 총 건수·총 페이지 수는 모른다. "다음 페이지가 있는가"만 안다. 추가 비용: 행 1건
❌ before — 응답 모델: 총 페이지 수로 페이지 번호를 그린다
record PageResponse<T>(
    List<T> content,
    int page,
    int totalPages,
    long totalElements
) {}
✅ after — 응답 모델: 다음 페이지 유무만 싣는다
record SliceResponse<T>(
    List<T> content,
    int page,
    boolean hasNext
) {}
// "더 보기" / 무한 스크롤 UI가 필요로 하는 전부
한 단계 더 가벼운 것List<Order> findBy…(Pageable)

count도 hasNext도 없이 딱 페이지 크기만큼만. "다음" 버튼조차 없는 위젯(최근 주문 5건 같은)에 맞다.

가산점Scroll API — Window<T> / ScrollPosition

최근 Spring Data의 키셋(커서) 기반 스크롤. count 비용(이 문서)과 offset 비용(깊은 페이지네이션 문서)을 한 번에 없애는 방향이다.

SQL_CALC_FOUND_ROWS라는 함정가산점
"목록과 count를 쿼리 한 번에" 하려던 MySQL의 옛 기능. LIMIT을 무시하고 결과 집합 전체를 끝까지 평가하게 만들어 목록 쿼리까지 count 비용을 물게 한다. 쿼리 두 개로 나누는 것보다 느린 경우가 많아 MySQL 8.0에서 deprecated 됐다. 왕복 횟수를 줄이려다 I/O를 늘리는 전형 — 그림 1의 STOP 마커를 스스로 지워 버리는 셈이다.

3. 대안 5가지 — 무엇을 내주고 무엇을 얻는가

1절의 결론은 "count 비용은 N에 비례하고, 커버링은 배수만 줄인다"였다. 차원을 바꾸려면 정확도 · 정합성 · UX 중 하나를 내줘야 한다. 다섯 대안을 목록으로 고정하고, 각각 얻는 것과 내주는 것을 한 호흡에 말한다. 한쪽만 말하면 답이 아니다.

암기 카드 — 대안 5종과 각각의 대가
커 · 근 · 캐 · 슬 · 무 — "커버링, 근사치, 캐싱, 슬라이스, 무한 스크롤"
#대안내주는 것 (대가)바꾸는 것
①커버링 인덱스로 세기없음 — 쓰기 비용·공간만배수만 (∝ N 그대로)
②근사치 (추정치 · 상한 카운트)정확도차원 (상수 시간 / 상한 고정)
③카운트 캐싱 · 카운터 테이블정합성 (+ 무효화·핫 로우)차원 (읽기 상수 시간)
④Slice — 다음 페이지 유무만UX ("N건 중 k페이지" 화면)차원 (count 자체 소멸)
⑤무한 스크롤 · 커서 · 검색 엔진UX 전체 + 아키텍처(운영·동기화)차원 (count·offset 둘 다)

외우는 틀: ①은 기초 공사(모든 길에 먼저 깔림), ②③④⑤는 각각 정확도 · 정합성 · UX · UX+아키텍처를 내준다.

①커버링 인덱스로 세기대가: 없음 — 배수만 절감
얻는 것
  • 정확한 값 유지
  • 북마크 룩업 제거, 페이지 밀도 상승 → 같은 N에 I/O 수십 분의 일 (1-3절)
내주는 것
  • 인덱스 하나만큼의 쓰기 비용·저장 공간
  • ∝ N 구조는 그대로 — 조건에 맞는 행이 수천만이면 여전히 초 단위
맞는 상황
  • 조건에 맞는 N이 수십만 이하이고 정확한 값이 꼭 필요한 화면
  • 다른 대안을 쓰더라도 첫 번째로 깔아 두는 기초 공사
②근사치 — 옵티마이저 추정치 · 상한 카운트대가: 정확도
얻는 것
  • (a) 추정치: N과 무관한 상수 시간, 비용 ≈ 0
  • (b) 상한 카운트: 상한으로 고정된 시간, 상한 이하에서는 정확한 값
내주는 것
  • (a) 정확도 — "약 12,000건" 표기와 허용 오차를 기획과 합의해야 쓸 수 있다
  • (b) 상한 너머의 정보 — "51페이지 이후"를 숫자로 못 보여준다
맞는 상황
  • 검색 결과 건수처럼 숫자가 감(感)의 용도인 화면
  • Google의 "약 1,230,000개", Elasticsearch의 track_total_hits 기본(1만 건까지만 정확) — 검색 엔진도 정확한 총 건수를 비싸게 본다
-- (a) 옵티마이저 추정치: 실행하지 않고 "몇 건쯤일지"만 묻는다. 비용 ≈ 0
EXPLAIN SELECT 1 FROM orders WHERE seller_id = 42 AND status = 'PAID';
-- → rows 컬럼이 추정치. 통계·인덱스 다이브 기반이라 수십 % 어긋날 수 있다.
-- 조건 없는 전체 건수는 information_schema.TABLES.TABLE_ROWS (역시 추정치)

-- (b) 상한 카운트: 상한까지만 정확히 세고, 넘으면 "1,000+"로 표시
SELECT COUNT(*) FROM (
    SELECT 1 FROM orders
     WHERE seller_id = 42 AND status = 'PAID'
     LIMIT 1001                       -- ← COUNT에 STOP 지점을 만들어 준다
) t;
-- 1,000건 이하면 정확한 값, 1,001이면 "1,000건 이상". 비용은 최대 1,001건으로 고정
③카운트 캐싱 · 카운터 테이블대가: 정합성 · 무효화
얻는 것
  • 읽기가 상수 시간, N과 무관
  • (a) 결과 캐싱: 필터 조합을 키로 짧게 캐시
  • (b) 카운터 테이블: 쓰기 시점에 미리 세어 둠 → 조회는 PK 한 건 읽기
내주는 것
  • (a) TTL 동안 값이 낡음. 필터 조합(상태 × 기간 × 검색어)이 곱셈으로 늘어 인기 조합만 캐시 가능
  • (b) 비용이 쓰기 경로로 이동: 같은 트랜잭션이면 핫 로우 락 경합, 비동기면 최종적 일관성·유실·중복 처리
  • 어느 쪽이든 보정 배치 필요. 카운터는 미리 정한 축에만 답한다
맞는 상황
  • 정확한 숫자가 업무 지표로 쓰여 근사치는 안 되지만, 몇 분의 지연은 허용되는 대시보드
  • 축이 고정된 집계 (판매자별 상태별 등)
// (a) 결과 캐싱: 조건 조합을 키로 count 결과를 짧게 캐시
String key = "orders:count:" + sellerId + ":" + status;      // 필터 조합이 곧 키
Long total = cache.get(key,
        () -> orderRepository.countBySellerIdAndStatus(sellerId, status),
        Duration.ofMinutes(5));                              // ← 이 5분이 "내주는 정합성"
-- (b) 카운터 테이블: 쓰기 시점에 미리 세어 둔다
UPDATE seller_order_stats SET paid_count = paid_count + 1 WHERE seller_id = 42;
-- 조회는 PK 한 건 읽기. 하지만 이 UPDATE가 주문 INSERT와 같은 트랜잭션에 있으면
-- 판매자 42의 모든 주문이 이 한 행의 락을 두고 줄을 선다 — 핫 로우

비유: 입구에 카운터 직원을 세워 들어올 때마다 "딸깍" — 인원 조회는 공짜지만, 입구가 하나라 붐비면 줄이 생기고(핫 로우), 딸깍을 빠뜨리면 숫자가 틀어져 가끔 실제로 세어 맞춰야 한다(보정 배치).

④다음 페이지 존재 여부만 — Slice대가: UX ("N건 중 k페이지")
얻는 것
  • count 쿼리 자체가 사라진다. 비용은 행 1건 (2-3절)
  • 코드 변경은 반환 타입 한 줄
내주는 것
  • "전체 N건 중 k페이지" UI — 총 페이지 수·마지막 페이지 점프·페이지 번호 나열이 불가능
  • 백엔드 혼자 결정 불가 — 화면이 바뀐다. 기획·프론트 합의가 선행
맞는 상황
  • 최신순으로 흘러가는 피드, "더 보기" 버튼, 모바일 목록
  • 대부분의 사용자향 목록 — 사용자가 57페이지로 점프하는 일은 거의 없다
⑤무한 스크롤 · 커서 · 검색 엔진대가: UX 전체 + 아키텍처
얻는 것
  • 무한 스크롤 + 커서면 count 비용과 offset 비용을 둘 다 없앤다
  • 복합 조건 검색·집계가 잦으면 검색 엔진(Elasticsearch)이 역색인으로 필터·건수를 RDB보다 싸게 준다
내주는 것
  • 무한 스크롤은 UX 자체의 변경(뒤로 가기·위치 공유·총량 감각 상실) → 기획 협상 크기가 가장 큼
  • 커서는 정렬 키가 유일해야 하고 API 스펙이 바뀜
  • 검색 엔진은 운영 비용 + RDB↔엔진 동기화(지연·유실)라는 새 시스템. 그마저도 총 건수는 기본이 근사치
맞는 상황
  • 트래픽이 크고 목록이 제품의 중심인 사용자향 서비스
  • 검색 조건이 다차원이라 RDB 인덱스로 감당이 안 되는 경우

4. 기획 협상 프레임 — "총 건수가 무엇에 쓰이나요?"

다섯 대안 중 무엇을 고를지는 기술이 아니라 요구의 정체가 결정한다. 그래서 첫 질문은 늘 "총 건수가 어디에 쓰이나요?"다. "요구사항의 비용을 알려주는 것까지가 백엔드의 일"이라는 말은 아래 흐름도를 들고 기획에 가는 것이다.

그림 3. 의사결정 흐름 — 용도를 묻고, 되묻고, 대안을 고르고, 합의를 코드에 남긴다
총 건수의 용도정확도 요구맞는 대안
페이지 번호 UI (1 2 3 … 57)낮음 — 사실 "다음"만 필요④ Slice / ⑤ 무한 스크롤. 관리자 화면이면 ② 상한 카운트로 번호 10개까지만
검색 결과 건수 표시낮음 — 감의 용도② 근사치 ("약 N건", "1,000+")
업무 지표 (오늘 결제 건수)높음, 지연 허용③ 카운터 테이블 + 보정 배치. 실시간성부터 되묻기
정산 · 감사높음, 지연 불가① 커버링 인덱스 + 조건 축소. 목록 API가 아니라 별도 집계 경로로
협상의 자세 — 두 가지 실패
"안 됩니다"도 "네 하겠습니다"도 아니다. 비용을 숫자로 보여주고, 요구를 한 단계 쪼개, 같이 고른다.

"전체 몇 건 중 몇 페이지"는 화면 요소 하나지만 DB에는 매 요청 N건 스캔이라는 가격표가 붙어 있다. 그 가격표를 보여주는 것까지가 백엔드의 일이다.

5. 안전망 — 기억이 아니라 코드와 계측으로 고정

"count가 비싸다"를 알아도 6개월 뒤 새 목록 API를 만드는 동료(또는 나)는 습관대로 Page를 쓴다. 지식을 습관에 맡기지 않고 코드가 막고 계측이 드러내게 한다.

5-1. count 쿼리를 목록 응답에서 분리 측정한다

"목록 API가 800ms"라는 숫자는 진단이 아니다. 목록 쿼리와 count 쿼리가 각각 몇 ms인지 따로 봐야 offset 문제인지 count 문제인지 갈린다.

도구 1SQL 단위 로깅 — p6spy · datasource-proxy

요청 하나에서 나간 SQL이 한 줄씩 실행 시간과 함께 찍힌다. LIMIT 붙은 목록 12ms, COUNT 780ms — 보이는 순간 진단이 끝난다. 3장 N+1 문서와 같은 도구.

도구 2APM의 SQL 스팬 — Pinpoint · Datadog

요청 트레이스 안에 SQL 하나하나를 스팬으로 그려 준다. count 스팬이 목록 스팬보다 긴 화면이 곧 증거다.

도구 3슬로 쿼리 로그

long_query_time을 낮추면 count 쿼리만 잡힌다 — 목록은 LIMIT 덕에 안 걸린다. "느린 목록 API"에서 슬로 로그에 count만 남는 것 자체가 신호다.

주의EXPLAIN은 count 쿼리에 따로

목록 쿼리의 EXPLAIN은 LIMIT 때문에 rows가 작게 나와 문제를 숨긴다. count 쿼리를 따로 EXPLAIN 해서 Extra: Using index 여부와 rows를 본다.

// 코드 안에서 count만 따로 재고 싶을 때 — Micrometer Timer로 supplier를 감싼다
LongSupplier timedCount = () -> countTimer.record(() -> countQuery.fetchOne());
return PageableExecutionUtils.getPage(content, pageable, timedCount);
// 대시보드에 "목록 p95"와 "count p95"가 따로 그려진다 — 지연 실행이라 2-1절의 건너뛰기도 그대로

5-2. Page vs Slice를 코드 규약으로 — 기본은 Slice, Page는 근거를 남겨야

규약은 문서에 쓰면 잊히고 리뷰 체크리스트에 두면 놓친다. 테스트가 실패하게 만든다.

// 총 건수가 정말 필요한 메서드에만 붙이는 표식 — "왜 필요한지"를 값으로 강제
@Retention(RUNTIME) @Target(METHOD)
public @interface ExactTotalRequired {
    String reason();     // 예: "정산 화면 — 건수 불일치 시 감사 이슈"
}

// ArchUnit: 표식 없이 Page를 반환하는 리포지토리 메서드는 빌드가 깨진다
@ArchTest
static final ArchRule page_requires_justification =
    methods()
        .that().areDeclaredInClassesThat().resideInAPackage("..repository..")
        .and().areNotAnnotatedWith(ExactTotalRequired.class)
        .should().notHaveRawReturnType(Page.class)
        .because("Page는 매 요청 count 쿼리를 추가한다. 총 건수가 꼭 필요하면 "
               + "@ExactTotalRequired(reason=...)로 근거를 남기고, 아니면 Slice를 써라");

새 목록 API의 기본값을 Slice로 밀어붙인다.

5-3. count를 별도 경로로 — 목록의 응답 시간을 count가 볼모 잡지 못하게

Page를 유지해야 하는 화면이라도 목록과 count를 같은 응답에 묶지 않는 선택이 있다.

GET /orders?seller=42&status=PAID&page=0      → 목록만, 즉시 응답 (Slice)
GET /orders/count?seller=42&status=PAID       → 총 건수, 별도 타임아웃 + 실패 시 "1,000+" 폴백

프론트는 목록을 먼저 그리고 건수는 도착하면 채운다. count 엔드포인트에 짧은 타임아웃과 ② 상한 카운트 폴백, ③ 캐시를 얹으면 count가 느려져도 목록은 느려지지 않는다. 장애 격리의 축소판이다.

6. 실무 사례 — "관리자 주문 목록이 새벽엔 빠르고 낮엔 느려요"

관리자 주문 목록 API(Page<Order>, 상태 필터, 20건씩)가 낮 시간대에만 p95 2초를 넘겼다. 처음 의심은 "낮에 트래픽이 많아서" — 틀리진 않지만 진단이 아니다.

  1. 분리 측정으로 범인 특정 — p6spy 로그를 요청 단위로 보니 목록 쿼리는 낮에도 15ms, count 쿼리가 1.8초.
  2. 원인 1 (1-3절 before) — 인덱스가 (created_at)뿐이라 상태 필터 count가 북마크 룩업 N회로 돌고 있었다.
  3. 원인 2 (1-2절) — 낮에는 주문 INSERT/UPDATE가 몰려 count가 만나는 행마다 undo 체인을 타는 가시성 판정이 늘었다. 새벽엔 이게 사라지고 버퍼 풀도 따뜻해서 "빨라 보였던" 것.
  4. 처방 1 — 배수 절감 (①) — (status, created_at) 커버링 인덱스로 count를 Using index로. 그래도 ∝ N은 그대로.
  5. 처방 2 — 차원 변경 (④ + ②) — 기획과 "이 화면에서 총 페이지 수를 실제로 쓰는가"를 확인. 운영자는 최신순으로 몇 페이지 넘길 뿐 마지막 페이지로 점프하지 않았다 → Slice로 전환, 상단 건수는 상한 카운트 "1,000+".
  6. 처방 3 — 규약 고정 (5-2절) — ArchUnit 규칙을 넣어 다음 관리자 화면이 같은 길을 밟지 않게 했다.
이 사례에서 면접관이 듣고 싶은 세 가지
1
분리 측정으로 count를 특정했는가"트래픽이 많아서"가 아니라 "count 쿼리가 1.8초"
2

7. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 시니어 변별은 얻는 것·내주는 것을 양면으로 말해야 통과다.

"MyISAM은 COUNT(*)가 즉시 나오는데 InnoDB는 왜 안 되나요?"

핵심: MyISAM은 테이블 단위 락이라 한 시점에 "행 수"가 하나뿐이고, 그 값을 메타데이터에 들고 있다가 바로 돌려준다. InnoDB는 MVCC라서 트랜잭션마다 보이는 행이 다르다 — 커밋 전 INSERT는 그 트랜잭션에게만 보이고, 삭제 표시된 행은 먼저 시작한 트랜잭션에게 아직 보여야 한다. 단일 정답이 없으니 행마다 DB_TRX_ID를 리드 뷰와 비교해 세는 수밖에 없다(그림 2).

덧붙이면 — MySQL 8.0은 조건 없는 COUNT(*)를 가장 작은 세컨더리 인덱스로 훑도록 최적화했지만 여전히 스캔이고, PostgreSQL도 같은 이유로 reltuples 추정치만 가진다. "읽기가 락을 안 잡는 대가로 count를 세는 비용을 낸다"는 트레이드오프 문장으로 닫는다.

"COUNT(*), COUNT(1), COUNT(id)는 성능이 다른가요?"

핵심: COUNT(*)와 COUNT(1)은 InnoDB에서 동일하게 처리된다 — "COUNT(1)이 더 빠르다"는 속설은 근거가 없다. COUNT(col)은 의미가 다르다: col이 NULL이 아닌 행만 센다. 그래서 col을 실제로 읽어야 하고, col이 옵티마이저가 고른 인덱스에 없으면 커버링 경로를 잃을 수 있다.

결론: 행 수를 세려면 COUNT(*), 특정 컬럼의 비-NULL 개수를 세려는 의도가 있을 때만 COUNT(col). 성능 이전에 의미가 다른 함수라고 말하는 게 정확하다.

"카운터 테이블로 가면 어떤 새 문제가 생기고, 어떻게 다루나요?"시니어 변별

핵심: 읽기 비용을 쓰기 경로로 옮긴 것이지 없앤 게 아니다. 세 가지가 새로 생긴다.

⑴ 핫 로우: 같은 트랜잭션에서 paid_count + 1을 하면 그 판매자의 모든 주문이 한 행의 락을 두고 직렬화된다 — 반정규화의 대가와 같은 뿌리. 완화는 카운터를 여러 슬롯으로 쪼개 합산하거나, 이벤트로 빼서 비동기 갱신. ⑵ 비동기로 빼면 정합성: 최종적 일관성, 이벤트 유실·중복에 대한 멱등 처리, 실패 시 롤백되지 않는 카운터. ⑶ 축의 고정: 카운터는 미리 정한 축(판매자별 상태별)에만 답하고, 새 필터 조합이 오면 답이 없다.

그래서 어느 방식이든 보정 배치(주기적으로 실제 COUNT(*)로 재계산해 덮어쓰기)를 안전망으로 깔고, "얼마나 어긋나도 되는가"를 기획과 숫자로 합의한다. 이 셋을 묻지 않고 "캐싱하면 됩니다"로 끝내는 답이 주니어 답이다.

"Slice로 바꾸자고 하니 기획이 '페이지 번호는 꼭 있어야 한다'고 합니다. 어떻게 하나요?"시니어 변별

핵심: 먼저 가격표를 보여준다 — 이 화면의 count가 요청당 N건 스캔이고 p95의 몇 %를 차지하는지(5-1절의 분리 측정 결과). 그다음 요구를 쪼갠다: "페이지 번호"가 필요한 건지, "마지막 페이지로 점프"가 필요한 건지, "총량의 감"이 필요한 건지. 대개 답은 앞의 둘이 아니다.

그러면 상한 카운트로 "1 2 3 … 10 다음"까지만 번호를 그리고 그 뒤는 "다음"으로 잇는 절충이 있다 — 비용은 상한으로 고정되고 UI는 거의 그대로다. 정말 마지막 페이지 점프가 업무에 필요하다면(감사·정산) Page를 유지하되 커버링 인덱스 + count 별도 엔드포인트 + 캐시로 목록 응답에서 떼어낸다(그림 3의 빨간 경로).

핵심은 "안 됩니다"도 "네 하겠습니다"도 아니고, 비용을 숫자로 보여주고 요구를 한 단계 쪼개 같이 고르는 것. 합의 결과는 @ExactTotalRequired(reason=…)처럼 코드에 남긴다.

"count 쿼리가 목록 응답의 몇 %인지 어떻게 확인하나요?"

핵심: 요청 하나가 발생시킨 SQL을 한 줄씩 실행 시간과 함께 보는 도구 — p6spy·datasource-proxy 로그, 또는 APM의 SQL 스팬. 거기서 LIMIT 붙은 목록 쿼리와 COUNT 쿼리의 시간을 나란히 읽는다.

지속적으로 보려면 count supplier를 Micrometer Timer로 감싸 "목록 p95"와 "count p95"를 따로 그린다. 슬로 쿼리 로그에 count만 남고 목록은 안 남는 것도 좋은 신호다. 그리고 EXPLAIN은 count 쿼리에 따로 걸어 Extra: Using index 여부와 rows를 본다 — 목록 쿼리의 EXPLAIN은 LIMIT 때문에 문제를 숨긴다.

"Slice는 count 없이 hasNext를 어떻게 아나요?"추가

핵심: 한 건을 더 달라고 해서 그게 오면 다음이 있는 것. 페이지 크기 20이면 LIMIT 21로 요청하고, 21번째 행이 있으면 hasNext = true, 응답에는 20건만 담는다. 추가 비용은 행 1건 — N과 무관하다. 총 건수·총 페이지 수는 모른다는 것이 내주는 것이다.

"Page를 쓰는데 어떤 요청은 count 쿼리가 안 나가요. 왜죠?"추가

핵심: PageableExecutionUtils.getPage가 결과만 보고 총 건수를 알 수 있는 두 경우에 count를 건너뛴다 — ⑴ 첫 페이지인데 가져온 건수가 페이지 크기보다 적다(총 건수 = 가져온 건수) ⑵ 첫 페이지가 아닌데 페이지 크기보다 적다(마지막 페이지, 총 건수 = offset + 가져온 건수).

바꿔 말하면 페이지가 꽉 차는 대용량일 때만 count가 나간다. 개발 DB에서 안 보이던 count(그리고 fetch join 예외)가 운영에서 터지는 이유다. 이 최적화를 살리려면 count를 LongSupplier로 넘겨 지연 실행되게 해야 한다.

"커버링 인덱스를 깔았는데도 count가 여전히 느립니다. 다음 단계는?"추가시니어 변별

핵심: 예상된 일이다 — 커버링은 배수를 줄일 뿐 ∝ N이라는 차원은 그대로다(1-3절). 조건에 맞는 행이 수천만이면 리프를 순차로 읽어도 초 단위다.

다음 단계는 기술이 아니라 질문이다: "이 총 건수가 무엇에 쓰이나요?"(그림 3). 용도에 따라 ② 근사치(정확도 내줌) · ③ 캐싱(정합성 내줌) · ④ Slice / ⑤ 무한 스크롤(UX 내줌) 중 하나로 차원을 바꾼다. 그리고 그동안 목록이 count에 볼모 잡히지 않도록 count를 별도 엔드포인트로 떼어내는 것(5-3절)을 병행할 수 있다.

"검색 엔진(Elasticsearch)으로 옮기면 총 건수 문제가 해결되나요?"추가

핵심: 필터·집계는 역색인으로 RDB보다 싸게 주지만, 정확한 총 건수는 검색 엔진도 비싸게 본다. Elasticsearch는 기본 설정(track_total_hits)으로 1만 건까지만 정확히 세고 그 이상은 "1만 건 이상"으로 돌려준다 — ② 상한 카운트와 같은 발상이다.

그리고 검색 엔진 도입은 운영 비용과 RDB↔엔진 동기화(지연·유실)라는 새 시스템을 하나 들이는 일이다. "해결"이 아니라 "내주는 것이 바뀌는 것"이라고 말해야 정확하다.

"SQL_CALC_FOUND_ROWS로 목록과 count를 한 번에 하면 안 되나요?"추가

핵심: 왕복은 한 번 줄지만 LIMIT을 무시하고 결과 집합 전체를 끝까지 평가하게 만든다 — 목록 쿼리까지 count 비용을 물게 된다. 그림 1에서 목록 쿼리의 STOP 마커를 스스로 지우는 셈이라, 쿼리 두 개로 나누는 것보다 느린 경우가 많다. MySQL 8.0에서 deprecated 됐다. 왕복 횟수를 줄이려다 I/O를 늘리는 전형이라고 정리한다.

"낮에만 count가 느려지는 건 왜인가요? 데이터 양은 같은데요."추가시니어 변별

핵심: count는 만나는 행마다 MVCC 가시성 판정을 한다. 낮에 INSERT/UPDATE가 몰리면 ⑴ 판정에서 DB_ROLL_PTR을 따라 undo 체인을 거슬러 가야 하는 행이 늘고 ⑵ 긴 트랜잭션이 undo를 쌓아 두면 그 체인이 길어진다. 거기에 ⑶ 버퍼 풀 경합으로 행 페이지 적중률이 떨어지면 북마크 룩업 비용까지 커진다.

즉 N이 같아도 행 하나를 만나는 단가가 낮에 오른다. 새벽엔 동시 갱신이 없고 버퍼 풀이 따뜻해 "빨라 보이는" 것이다(6절 사례). "트래픽이 많아서"가 아니라 이 사슬로 답해야 한다.

8. 한 줄 요약

면접 전날 이것만
목록은 LIMIT에서 멈추지만 COUNT는 조건에 맞는 행을 전부 만나야 하고 (InnoDB는 MVCC 때문에 트랜잭션마다 보이는 행이 달라 행 수를 메타데이터로 들 수 없다), 조건 컬럼이 인덱스에 없으면 그 N건마다 랜덤 I/O가 붙는다 — 비용이 페이지 크기가 아니라 N에 비례하는 요구다. 커버링 인덱스는 배수만 줄이고, 차원을 바꾸려면 근사치(정확도) · 카운트 캐싱(정합성) · Slice/무한 스크롤(UX) 중 하나를 내줘야 한다. Page가 count를 자동으로 붙인다는 사실을 알고, 기본은 Slice · Page는 근거 필수라는 규약을 ArchUnit과 분리 측정으로 고정하며, 그 가격표를 기획에 보여주는 것까지가 백엔드의 일이다.
