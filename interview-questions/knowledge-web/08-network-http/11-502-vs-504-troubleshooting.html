502 vs 504 — 장애 첫 1분의 방향을 정해주는 코드
"백엔드가 죽었다"와 "백엔드가 느리다"를 가르는 한 글자

면접 질문: "502와 504의 차이 — 각각 발생했을 때 어디를 먼저 봐야 하나요?"

핵심 관전 포인트 — 502와 504는 앱이 만든 코드가 아니라, 요청을 대신 전달하던 프록시(Nginx, 로드밸런서)가 "뒤쪽 백엔드와의 대화가 실패했다"며 스스로 만들어 붙인 코드다. 갈림길은 "백엔드가 응답을 시도할 수 있었는가"다 — 502 Bad Gateway는 연결이 거부됐거나 도중에 끊겼거나 HTTP로 해석할 수 없는 응답이 온 것이라 "백엔드가 죽었거나 깨졌다"는 가설로 배포 이력·프로세스 생존·프록시 에러 로그부터 보고, 504 Gateway Timeout은 프록시가 정한 대기 상한 안에 응답이 오지 않은 것이라 "백엔드가 살아 있는데 느리다"는 가설로 응답시간 지표와 그 뒤의 대기(DB, 외부 호출, 스레드 풀)부터 본다. 여기에 두 가지를 더 알아야 초동에서 헤매지 않는다 — 코드를 만든 주체가 프록시라서 앱 로그가 깨끗할 수 있다는 것, 그리고 504 뒤에는 프록시는 포기했는데 백엔드는 끝까지 처리해 커밋해버리는 "유령 성공"과 사용자 재시도로 인한 중복 처리 위험이 따라온다는 것이다.
  • 1
    제조처가 다르다 — 500은 앱이 자기 예외를 잡아 만들지만 502·504는 프록시가 "뒤쪽과의 대화 결과"로 판정해 만든다. 그래서 앱 로그가 깨끗한 것은 모순이 아니라 힌트이고, 1차 증거는 앱 로그가 아니라 프록시의 error log·access log다.
  • 2
    갈림길은 "응답을 시도라도 할 수 있었나" — 502는 대화 자체가 성립하지 않은 것(연결 거부 / 도중 끊김 / HTTP가 아닌 응답)이라 배포 이력 → 프로세스 생존 → error log 문구 순으로 보고, 504는 대기 상한이 만료된 것이라 응답시간 지표 → 무엇을 기다리는지(스레드 덤프)를 본다. 두 갈래를 확정해 주는 것이 로그의 while connecting / while reading response header다.
  • 3
    504는 조사와 별개로 데이터 사고가 따라온다 — 프록시의 타임아웃은 프록시의 기다림만 끊지 백엔드의 처리를 멈추지 않으므로, 화면은 실패인데 DB에는 커밋이 남는 유령 성공이 생기고 재시도가 중복 처리로 번진다. 그래서 답은 타임아웃 정렬 + 쓰기 API 멱등성 키가 한 쌍이다.

0. 질문 + 출제 의도

질문: "502와 504의 차이 — 각각 발생했을 때 어디를 먼저 봐야 하나요?"

출제 의도: 상태 코드 하나가 "백엔드가 죽었다"와 "백엔드가 느리다"를 갈라준다. 장애 첫 1분에 보는 방향을 정해주는 지식 — 초동 대응 속도의 차이를 만드는지 확인하는 질문이다.

이 페이지가 겨냥하는 약점 네 가지 ① "둘 다 서버 에러"로 뭉뚱그리는 것 → 1·3절에서 제조처와 대화가 깨진 단계로 축을 갈라 놓는다.
② "앱 로그를 봤는데 아무것도 없어요"에서 멈추는 것 → 1·4절에서 1차 증거는 프록시 로그이고, 그 문구가 원인을 직접 말해준다는 것을 사전으로 만든다.
③ 504를 보고 무조건 DB부터 파는 것 → 8절에서 터진 타임아웃이 셋 중 무엇인지부터 확정한다 — while connecting이면 느린 게 아니라 못 닿은 것이다.
④ 504를 "느림 문제"로만 닫는 것 → 10절에서 유령 성공·중복 처리라는 데이터 사고로 이어지는 경로를 타임라인으로 본다.

1. 제조처가 다르다 — 앱 로그가 깨끗한 이유

5xx는 전부 "서버 쪽 잘못"이라는 점에서 한 묶음이지만, 누가 그 코드를 만들어 냈는가를 기준으로 보면 두 부류로 갈린다. 이 한 줄이 이 문서 전체의 출발점이다.

500 — 애플리케이션이 만든다
컨트롤러 어딘가에서 예외가 터졌고 프레임워크가 그것을 잡아 "내가 처리하다 실패했다"고 응답한 것. 그래서 500은 반드시 앱 로그에 스택 트레이스라는 물증을 남긴다.
502 · 504 — 중개자가 만든다
Nginx, ALB 같은 로드밸런서, CDN, API 게이트웨이가 "내가 뒤쪽 서버와 대화를 시도했는데 그 대화가 실패했다"고 판정해 자기가 직접 만들어 반환한 코드. 앱은 이 일을 모를 수도 있다.

초동의 가장 큰 함정 — "에러가 났다는데 앱 로그가 깨끗해요"

502라면 요청이 앱에 도달조차 못 했을 수 있고, 504라면 앱은 아직 처리 중이었거나 뒤늦게 성공으로 끝냈을 수 있다. 즉 로그가 깨끗한 것은 모순이 아니라 "에러의 제조처가 앱이 아니라 프록시"라는 힌트다.

그래서 502/504의 1차 증거는 앱 로그가 아니라 프록시의 error log와 access log다. 이 방향 전환을 첫 30초에 하느냐 마느냐가 초동 속도를 가른다.

503과는 무엇이 다른가 — 기준은 "거절에 의도가 있었는가" 503은 의도적인 거절이다. 과부하 차단, 점검 모드, 헬스체크 실패로 인한 풀 제외처럼 서버가 스스로 "지금은 못 받는다"고 결정한 것이라 Retry-After로 "언제 다시 오라"고 안내할 수 있다. 반면 502/504에는 의도가 없다 — 프록시가 뒷단과 통신을 시도한 결과로 판정된 사고 보고이므로 안내할 재시도 시점도 없다.
503 "지금은 안 받겠습니다, 30초 뒤에" = 결정한 주체가 있다 502 "대화가 깨졌습니다" = 사고의 보고 504 "제한 시간 안에 답이 없어 제가 끊었습니다" = 사고의 보고
단, 일반론만으로는 부족하다 — 같은 상황에 제품마다 다른 코드를 매긴다 가산점 "살아 있는 백엔드가 하나도 없다"는 똑같은 상황에서 Nginx는 no live upstreams 로그와 함께 502를 내지만, AWS ALB는 등록된 정상 대상이 없을 때 503을 낸다. 코드만 보고 제품 동작을 단정하지 말고, "우리 인프라의 LB/게이트웨이가 어떤 상황에 몇 번을 내는지"를 평시에 문서로 확인해두는 것이 실전 대응력이다.

2. upstream — 로그 문장을 읽는 열쇠

프록시 로그를 읽으려면 upstream이라는 단어를 먼저 넘어야 한다. 이 말이 정의 없이 던져지는 바람에 로그를 봐도 무슨 말인지 모르는 경우가 많다.

업스트림은 프록시 관점에서 "요청을 넘겨받는 뒤쪽 서버", 즉 Nginx가 대신 요청을 보내주는 대상(보통 Tomcat, 애플리케이션 서버)을 가리킨다. Nginx 설정의 upstream app { server 10.0.0.11:8080; } 블록의 대상이 그것이다. 이름이 헷갈리는 이유는 "상류"가 직관과 반대로 느껴지기 때문인데, 이름은 요청이 아니라 "응답 데이터가 흘러오는 방향"을 기준으로 붙어 있다.

비유 — 프록시는 전화 교환원이다 고객(클라이언트)이 대표번호로 전화를 걸고 교환원(프록시)이 담당 부서(백엔드)로 연결해 준다. 502는 "연결해 드렸는데 상대가 안 받거나, 받자마자 끊거나, 알아들을 수 없는 소리만 냅니다" — 대화 자체가 성립하지 않았다. 504는 "연결은 됐는데 제가 정한 시간 안에 답이 안 와서 제가 끊었습니다" — 상대는 살아 있고 아마 지금도 뭔가 찾고 있다.
두 경우 모두 고객에게 상황을 알린 것은 담당 부서가 아니라 교환원이다 — 담당 부서는 잠시 뒤 "찾았습니다!"라고 말하겠지만 그때는 아무도 듣고 있지 않다 (10절 유령 성공)

3. 실패 지점 지도 — 어디서 깨지면 502인가

502와 504를 "죽음 vs 느림"으로만 외우면 실전에서 한 발짝을 못 나간다. 실제로 필요한 것은 프록시와 백엔드의 대화를 네 단계로 쪼개고, 지금 깨진 곳이 어느 단계인지 찍는 것이다. 단계가 정해지면 봐야 할 대상이 자동으로 정해진다.

4. 502 로그 문구 사전 · 읽는 규칙 둘

502는 원인이 여럿이라 "이것저것 다 봐야 한다"로 흐르기 쉽다. 그런데 Nginx는 왜 502를 냈는지를 error log에 문장으로 남긴다. 이 문구와 원인을 짝지어 두면 조사 범위가 한 번에 좁혀진다 — 실무에서 가장 값이 나가는 지식이 이 매핑이다.

Nginx error log 문구 사전. 표를 통째로 외우기보다 아래 규칙 두 개로 처음 보는 문구도 해석하는 편이 낫다.
error log 문구실제로 일어난 일첫 확인 대상
connect() failed (111: Connection refused)
while connecting to upstream		그 IP:포트에 리슨 중인 프로세스가 없다 — 커널이 즉시 RST로 거절했다백엔드 프로세스 생존, 배포/재시작 이력, proxy_pass 주소·포트 오타
connect() failed (113: No route to host)
upstream timed out ... while connecting		SYN이 아예 도달하지 못했다 — 라우팅 단절, 보안 그룹·방화벽 차단, 또는 백엔드의 accept 큐 포화보안 그룹·네트워크 ACL, 서브넷/라우팅, 백엔드의 accept 백로그
upstream prematurely closed connection
while reading response header from upstream		요청은 보냈는데 응답 헤더가 오기 전에 상대가 연결을 닫았다keep-alive 유휴 경쟁(6절), 처리 중 프로세스 크래시·OOM kill
recv() failed (104: Connection reset by peer)
while reading response header from upstream		상대가 RST로 강제 종료했다프로세스 강제 종료, 백엔드 앞단 방화벽이 유휴 연결을 RST로 끊는 구성
no live upstreams while connecting to upstreamupstream 그룹의 서버가 전부 "실패 누적"으로 일시 제외된 상태다max_fails/fail_timeout 설정과, 전체 백엔드가 동시에 나간 원인
upstream sent too big header
while reading response header from upstream		응답 헤더가 proxy_buffer_size 한 조각을 넘었다응답에 실리는 쿠키·토큰 크기, proxy_buffer_size 값 (13번 문서 3절)
upstream sent no valid HTTP/1.0 header
upstream sent invalid header		돌아온 바이트가 HTTP 응답 형식이 아니다포트 착오(HTTP가 아닌 서비스에 붙음), 앱이 응답 앞에 이물질을 출력하는 버그

처음 보는 로그도 해석하게 만드는 규칙 두 개

규칙 1 — while connecting이면 연결 단계(네트워크·프로세스 생존), while reading response header면 응답 단계(백엔드 내부 사정)

규칙 2 — 괄호 안 숫자는 리눅스 errno다. 이 네 개만 알면 처음 보는 로그도 읽힌다.

ECONNREFUSED
거부 — 리슨하는 프로세스가 없다
104
ECONNRESET
강제 종료 — 상대가 RST를 보냈다
110

시간 초과 — 응답이 없다
113
EHOSTUNREACH
경로 없음 — 닿을 길이 없다
no live upstreams는 "지금의 문제"가 아니라 "과거의 흔적"이다 Nginx는 upstream 그룹의 서버가 fail_timeout 시간 안에 max_fails 회 실패하면 그 시간 동안 후보에서 뺀다. 그룹의 모든 서버가 이렇게 빠지면 보낼 곳이 없어져 이 로그와 함께 502가 된다. 그러므로 이 문구를 보면 "조금 전에 전체 백엔드가 동시에 실패했다"로 읽고 직전 로그로 거슬러 올라가야 한다 — 진짜 원인은 이 줄이 아니라 그 앞줄에 있다.

5. 최다 용의자 — 배포 시간대의 두 틈

502의 원인 중 압도적으로 빈도가 높은 것은 롤링 배포 중에 생기는 짧은 502 스파이크다. 그래서 조사의 1단계가 "그 시각에 배포가 있었나"인 것이다. 문제의 뿌리는 한 문장이다 — "인스턴스를 내리는 일"과 "로드밸런서 대상 목록에서 빼는 일"은 서로 다른 주체가 하는 별개의 작업이라서, 순서가 어긋나면 틈이 생긴다.

문제 기본값 그대로 — 두 틈이 모두 열려 있다
# application.yml
server:
  shutdown: immediate      # SIGTERM 즉시 종료
  # 처리 중이던 요청의 연결이 그대로 끊긴다
  # -> 프록시에는 prematurely closed -> 사용자에게 502

# Deployment (발췌)
spec:
  containers:
    - name: app
      # readinessProbe 없음
      # 포트가 열리자마자 엔드포인트에 등록된다
      # -> 워밍업 중에 요청을 받아 502/504
      # lifecycle.preStop 없음
      # -> "제외"보다 "종료"가 먼저 시작될 수 있다
개선 틈을 각각 메운다 — 진행 중 요청 보전
# application.yml
server:
  shutdown: graceful
  # 새 요청 수용은 멈추되, 처리 중인 요청은
  # 끝까지 처리하고 종료한다

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
    # 진행 중 요청을 기다려 줄 최대 시간.
    # 넘기면 남은 요청을 버리므로 최장 요청보다 길게

management:
  endpoint:
    health:
      probes:
        enabled: true
        # liveness(살아 있나)와 readiness(받을 준비가
        # 됐나)를 분리해 노출한다
개선 Kubernetes Deployment — 순서를 강제하고, 준비된 뒤에만 받는다
# 종료 쪽 틈 (2) — 순서 강제
lifecycle:
  preStop:
    exec:
      # 컨테이너 종료 신호와 "엔드포인트에서 제외" 전파는 병렬로 일어난다.
      # 여기서 잠깐 버텨, LB/Service가 나를 목록에서 빼는 것을 먼저 끝내게 만든다.
      # 이 대기가 없으면 graceful shutdown도 "이미 죽은 나에게 오는 요청"은 못 막는다.
      command: ["sh", "-c", "sleep 15"]

# 투입 쪽 틈 — "프로세스 기동"이 아니라 "요청 처리 가능"을 확인한 뒤에만 트래픽을 받는다.
readinessProbe:
  httpGet:
    path: /actuator/health/readiness   # readiness 통과 전에는 Service 엔드포인트에 등록되지 않는다
    port: 8080
  periodSeconds: 2

여기까지 말하면 평범

여기까지 말하면 변별

6. 간헐적 502 — 3종 세트

배포도 없었고 프로세스도 멀쩡한데 하루에 몇 번씩 무작위로 502가 나는 경우가 있다. 이때는 아래 세 가지 증상이 한 세트로 나타나며, 이 세트를 보고 즉시 가설을 꺼낼 수 있으면 실전 경험이 드러난다.

① 간헐적이다
부하와 무관하게 하루에 몇 번. 재현이 안 된다.
② 백엔드 지표가 멀쩡하다
CPU, 스레드, 응답시간 모두 정상.
③ 로그가 정해져 있다
upstream prematurely closed connection
정체는 연결 재사용의 경쟁 조건 — 백엔드가 유휴 연결을 닫는 순간과 프록시가 그 연결에 새 요청을 싣는 순간이 겹친 것

여기서 반드시 짚어야 할 것은 "왜 프록시가 미리 알 수 없는가"다. 상대가 보낸 FIN은 "내 송신 방향이 끝났다"는 통보일 뿐이라 Nginx의 송신 방향은 여전히 열려 있고, 그래서 요청을 쓰는 write()는 성공해 버린다(3절 지도의 2단계). 실패는 응답을 읽으려는 순간에야 드러난다 — 즉 "보내기 전에 살아 있는지 확인"이라는 접근으로는 원천적으로 막을 수 없다.

그래서 대응은 "확인"이 아니라 "순서 정하기"다 재사용하는 쪽(Nginx)의 유휴 상한을 닫는 쪽(Tomcat)의 유휴 상한보다 짧게 잡아, 닫는 결정을 우리가 통제하게 만든다. half-close 경쟁의 단계별 타임라인은 10-keepalive-connection-pool-time-wait.md 3-3절에, Nginx↔Tomcat 설정 정렬은 13-nginx-tomcat-timeout-buffer-mismatch.md 2절에 있으므로 여기서는 502 진단의 관점(3종 세트)만 기억한다.

7. 502 조사 동선 4단계

지금까지의 내용을 실제로 움직이는 순서로 압축하면 이렇다. 순서가 중요한 이유는 앞쪽 단계가 압도적으로 빈도가 높기 때문이다 — 1단계에서 걸리면 조사가 5분 만에 끝난다.

1
시각을 먼저 본다. 502가 시작된 시각에 배포·재시작·오토스케일링 이벤트가 있었는지. 여기서 걸리면 5절이 곧 답이다.
2
백엔드 프로세스의 생존을 본다. 크래시, OOM kill(컨테이너 메모리 제한 초과 포함), 헬스체크 탈락으로 대상 풀에서 전부 빠졌는지. 컨테이너면 재시작 횟수(RESTARTS)와 종료 코드(OOM kill이면 137)가 단서다.
3
프록시 error log의 문구를 읽는다. 4절 사전으로 원인을 특정한다. 여기까지 오면 대부분 답이 나온다.
4
문구가 prematurely closed인데 1~3단계가 전부 정상이면 → keep-alive 경쟁을 의심한다(6절 3종 세트).
실전 초동 5분에 실제로 두드리는 명령들
# ① 시각 — 502가 시작된 시각 주변에 무슨 일이 있었나
kubectl get events --sort-by=.lastTimestamp | tail -30
kubectl get pods -o wide                     # RESTARTS 열이 올라갔는지

# ② 프로세스 생존 — 죽었다면 왜 죽었나
kubectl describe pod <pod> | grep -A5 "Last State"
#   Reason: OOMKilled / Exit Code: 137  -> 컨테이너 메모리 제한 초과
ss -lntp | grep :8080                        # 백엔드가 실제로 리슨 중인가 (111 거부의 직접 확인)

# ③ 프록시 error log — 502/504의 1차 증거. 문구가 곧 원인이다
tail -200 /var/log/nginx/error.log | grep -E 'upstream|connect\(\)'

# ④ 502가 "몇 시 몇 분에 몰렸는지" — 스파이크인지 상시인지가 갈린다
#    (combined 포맷 기준 4번째 필드가 시각. 배포 시각과 겹치면 5절 확정)
grep '" 502 ' /var/log/nginx/access.log | awk '{print $4}' | cut -c2-18 | uniq -c

8. 504 — 어느 타임아웃이 터졌는가

504는 프록시가 정한 대기 상한이 만료된 것이다. 그런데 프록시에는 대기 상한이 하나가 아니라 여럿이고, 어느 것이 터졌는지에 따라 조사 방향이 완전히 달라진다. 이 구분을 안 하면 "백엔드가 느린가 보다"라고 단정했다가 하루를 버린다.

설정 세 상한이 각각 어디를 재는지 주석으로 붙여 둔다
location /api/ {
    proxy_pass http://app;

    # (1) 백엔드와 TCP 연결을 맺는 데까지의 상한.
    #     이게 터지면 "백엔드가 느린 것"이 아니라 "연결이 안 되는 것"이다.
    #     로컬 네트워크의 연결 수립은 밀리초 단위이므로 몇 초면 충분하다.
    proxy_connect_timeout 3s;

    # (2) 백엔드에 요청 본문을 쓰는 도중의 상한.
    #     주의: 전체 전송 시간이 아니라 "연속된 두 번의 쓰기 사이" 간격이다.
    proxy_send_timeout 10s;

    # (3) 백엔드의 응답을 읽는 도중의 상한. 504의 최다 발원지.
    #     주의: 전체 응답 시간이 아니라 "연속된 두 번의 읽기 사이" 간격이다.
    proxy_read_timeout 10s;
}

같은 504라도 로그 한 단어로 조사 방향이 갈린다

while connecting
닿지 못했다. 네트워크·보안그룹·accept 큐 → 앱 코드를 봐도 아무것도 안 나온다
while reading response header
백엔드가 처리 중이다. 우리가 흔히 말하는 "느린 백엔드" → 9절로
while reading upstream
본문을 받다가 멈췄다. 헤더가 이미 나갔으면 잘린 200이 된다

9. 504 조사 — "무엇을 기다리는가"

로그가 while reading response header이고 백엔드가 정말 느린 것이 맞다면, 그다음은 "백엔드가 왜 느린가"다. 여기서 중요한 사고 전환이 하나 있다.

애플리케이션이 느린 이유는 대부분 자기가 계산을 많이 해서가 아니라, 그 뒤의 무언가를 기다리기 때문이다 — 그러므로 조사는 "무엇을 기다리는가"를 찾는 일이 된다
1
응답시간 지표의 "모양"을 본다. p99가 언제부터 튀었는지, 그리고 전체 API가 느린지 특정 API만 느린지. 이 갈래 하나로 조사 범위가 절반이 된다.

전체 API가 느리다 → 공용 자원

  • DB — 락 대기, 특정 무거운 쿼리가 전체를 잡아먹음
  • 커넥션 풀 / 스레드 풀 — 획득 대기가 모든 요청에 붙는다
  • GC 정지 — 정지 시간만큼 전 요청이 함께 밀린다
  • 인스턴스 한 대만 느린 것은 아닌지도 함께 확인

특정 API만 느리다 → 그 API가 부르는 것

  • 특정 쿼리 — 데이터 증가로 실행계획이 바뀌었는지
  • 특정 외부 API — 상대의 지연이 그대로 내 지연이 된다
  • 파라미터 의존 — 조회 기간이 긴 요청만 느린지
  • 그 API만 타임아웃이 없는 호출을 하고 있지 않은지
2
스레드 덤프로 "지금 무엇을 기다리는지"를 직접 본다. 이것이 가장 결정적인 증거다. 한 장만 뜨지 말고 3~5초 간격으로 3회 떠서, 같은 프레임에 계속 머물러 있는 스레드를 찾는다 — 그것이 병목이다.

문제 타임아웃 없는 외부 호출 — 504 공장
// 기본 설정 그대로 두면 연결·읽기 타임아웃이
// 사실상 무제한인 클라이언트가 많다.
RestTemplate rt = new RestTemplate();

public PgResult approve(Payment p) {
    // PG가 죽지 않고 "느려지기만" 하면
    // 이 스레드는 영원히 여기 서 있는다.
    return rt.postForObject(PG_URL, p, PgResult.class);
}

// 결과 연쇄:
//  1. 서블릿 스레드가 반환되지 않는다
//  2. 스레드 풀 고갈 -> 이 API와 무관한 요청까지 느려진다
//  3. 프록시의 proxy_read_timeout이 먼저 만료 -> 504
//  4. 그런데 백엔드는 계속 처리 중 -> 유령 성공(10절)
개선 두 타임아웃을 명시하고, 바깥 상한보다 짧게
// 빌더 메서드 이름은 프레임워크 버전에 따라 다르지만,
// 요점은 두 타임아웃을 반드시 명시한다는 것.
RestTemplate rt = builder
    .setConnectTimeout(Duration.ofSeconds(2))  // 연결
    .setReadTimeout(Duration.ofSeconds(3))     // 응답
    .build();

// 값을 정하는 원칙 (13번 문서 2절):
//   내 호출 타임아웃(3s) < 내 처리의 최악 소요
//   < 프록시의 proxy_read_timeout(10s)
// = 안쪽이 먼저 포기해야 내가 상황을 통제한다.

// 안쪽이 먼저 포기하면 얻는 것:
//  - 스레드가 제때 반환되어 고갈이 전파되지 않는다
//  - 504 대신 내가 만든 에러가 나가므로 앱 로그에 남는다
//  - 유령 성공의 창이 좁아진다
"백엔드가 느렸다"인가, "프록시가 못 기다렸다"인가 — 한 컬럼으로 갈린다 액세스 로그의 $upstream_response_time(또는 $upstream_header_time)이 proxy_read_timeout 값에 정확히 붙어 있으면(예: 상한 10s에 10.001) 그것은 "백엔드가 10초 걸렸다"가 아니라 "프록시가 10초에서 끊었다"는 뜻이다. 즉 계층 간 타임아웃 부정합이 확정되고, 유령 성공 점검(10절)이 즉시 열려야 한다. 반대로 그 값이 상한보다 확실히 작은데 504가 났다면 터진 타임아웃이 read가 아니라 connect일 가능성을 먼저 본다.

10. 유령 성공과 중복 처리 시니어 변별

504에는 상태 코드 진단과는 별개로, 데이터 정합성 사고로 번지는 함정이 하나 붙어 있다. 이것을 아느냐가 이 주제에서 주니어와 시니어를 가른다. 전제는 한 문장이다.

프록시의 타임아웃은 프록시의 "기다림"을 중단시킬 뿐, 백엔드의 "처리"를 중단시키지 않는다

둘은 서로 다른 프로세스이고, 프록시가 포기했다는 사실이 백엔드에 전달되는 표준적인 경로는 없다. 그래서 아래 일이 벌어진다.

진짜 위험은 프록시가 아니라 사용자와 재시도 로직에 있다

사용자는 실패 화면을 봤으므로 다시 누른다. 클라이언트 SDK나 앞단 게이트웨이에 재시도가 걸려 있다면 사람이 누르기도 전에 자동으로 다시 보낸다.

"응답을 못 받았다"는 상태는 "실패했다"와 다르다 — 성공했는데 결과를 못 받았을 수도 있는데, 재시도하는 쪽은 이 둘을 구분할 방법이 없다

대응 ① 계층 간 타임아웃 정렬

  • 프록시의 대기 상한이 백엔드 작업의 최악 소요보다 길어야 유령 성공 자체가 안 생긴다
  • 반대로 안쪽(앱의 외부 호출)이 먼저 포기하게 만들면, 504 대신 내가 만든 에러가 나가므로 앱 로그에 물증이 남는다
  • 구체적 정렬 원칙과 숫자 예시: 13-nginx-tomcat-timeout-buffer-mismatch.md 2절

대응 ② 쓰기 API를 멱등하게

  • 타임아웃은 아무리 정렬해도 완전히 없앨 수 없다 → 근본 방어는 같은 요청이 두 번 와도 결과가 한 번과 같게 만드는 것
  • 클라이언트가 요청마다 고유한 멱등성 키를 만들어 보내고, 서버는 그 키에 유니크 제약을 걸어 두 번째를 걸러낸다
  • 구현 상세(테이블 설계, 처리 중 상태에 무엇을 반환할지, 응답 본문 캐싱, 키의 유효 범위): 04-http-method-idempotency-and-safety.md 3절
개선 멱등성 키의 뼈대 — "두 번째 요청은 처리하지 않고 첫 결과를 돌려준다"

표를 "외운 것"이 아니라 "이해한 것"으로 들리게 하는 한 문장

같은 502라도 로그 문구에 따라 재시도 안전성이 달라진다
connection refused
요청이 도달조차 못 했다 → 부작용이 있을 수 없으므로 재시도 안전
prematurely closed
백엔드가 요청을 받아 처리하다 끊긴 것일 수도 있다 → 안전하지 않다

Nginx의 proxy_next_upstream이 기본적으로 비멱등 메서드(POST 등)를 이미 보낸 뒤에는 다음 서버로 넘기지 않는 것도 같은 이유다 — 넘기려면 non_idempotent를 명시해야 하고, 그것은 중복 처리를 감수하겠다는 선언이다.

12. 프록시가 여러 층이면 — 제조 층 특정 시니어 변별

실제 시스템은 CDN → LB → Nginx → 앱처럼 프록시가 여러 층이다. 이때 가장 먼저 할 일은 원인 찾기가 아니라 층 특정이다.

에러 코드는 "그것을 만든 층의 아래쪽"에 문제가 있다는 뜻이므로, 제조 층을 특정하는 순간 조사 범위가 절반씩 줄어든다
준비 ① 요청 ID를 만들거나 이어받아 뒤로 전달한다
map $http_x_request_id $req_id {
    # 앞단(CDN/LB)이 이미 ID를 붙였으면 그것을 그대로 쓴다.
    default   $http_x_request_id;
    # 비어 있으면 Nginx가 만든 요청 고유 ID를 쓴다.
    ""        $request_id;
}

server {
    location /api/ {
        proxy_pass http://app;
        # 뒤쪽(Tomcat)에도 같은 ID를 넘겨 앱 로그와 이어 붙일 수 있게 한다.
        proxy_set_header X-Request-ID $req_id;
        # 응답에도 실어 보내면 사용자 문의 시 스크린샷의 ID로 바로 검색된다.
        add_header X-Request-ID $req_id always;
    }
}
준비 ② 액세스 로그에 "내가 받은 것"과 "내가 내보낸 것"을 나란히 남긴다
log_format upstreamlog
    '$remote_addr "$request" '
    # 내가 클라이언트에게 내보낸 상태 코드
    'status=$status '
    # 업스트림이 나에게 준 상태 코드. 비어 있으면(-) 응답을 아예 못 받은 것이다.
    #   status=504 인데 upstream_status=-   -> "내가 만든 504"가 확정
    #   status=502 인데 upstream_status=502 -> "뒤쪽이 준 502를 전달만 한 것"
    'upstream_status=$upstream_status '
    # 연결 수립까지 걸린 시간. proxy_connect_timeout에 붙어 있으면 연결 단계 문제.
    'ucon=$upstream_connect_time '
    # 응답 헤더의 첫 바이트까지 걸린 시간. 백엔드 처리 시간의 실질적 지표.
    'uhdr=$upstream_header_time '
    # 업스트림 응답 전체 소요. proxy_read_timeout 값에 딱 붙어 있으면
    # "백엔드가 느렸다"가 아니라 "내가 못 기다렸다"는 뜻이다.
    'ures=$upstream_response_time '
    # 실제로 어느 백엔드에 보냈는지. next_upstream 재시도가 있었으면 여러 개가 찍힌다.
    'uaddr=$upstream_addr '
    'req_id=$req_id';

access_log /var/log/nginx/access.log upstreamlog;
액세스 로그 두 컬럼의 조합을 읽는 법 — "내가 범인인가 전달자인가"가 이 한 컬럼으로 갈린다.
$status$upstream_status해석과 다음 행동
502-이 프록시가 만든 502 — 뒤쪽과 대화가 성립하지 않았다. error log 문구로 4절 사전을 편다.
504-이 프록시가 만든 504 — uhdr/ures가 상한에 붙었는지 보고, 붙었으면 유령 성공 점검을 연다.
502502뒤쪽 층이 만든 502를 전달만 했다 — 한 층 더 뒤로 가서 같은 판정을 반복한다.
504504마찬가지로 전달 — 이 층의 타임아웃 값을 만지는 것은 헛수고다.
200502, 200첫 백엔드가 실패했고 proxy_next_upstream 재시도로 두 번째에서 성공했다. 사용자는 정상이지만 한 대가 이미 죽어 있다는 신호이므로 그 인스턴스를 본다.

13. 인출 카드 · 꼬리질문 셀프 테스트

13-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

둘을 가르는 한 문장?
"백엔드가 응답을 시도할 수 있었는가" — 502는 대화 자체가 성립 안 함, 504는 대기 상한 만료. 둘 다 제조처는 프록시.
로그 읽는 규칙 둘?
① while connecting=연결 단계 / while reading response header=응답 단계. ② 괄호 숫자는 errno — 111 거부, 104 리셋, 110 타임아웃, 113 경로 없음.
배포 시간대 502의 두 틈?
내려가는 쪽(종료가 먼저, 제외가 나중 — 헬스체크 주기×임계만큼)과 올라오는 쪽("떴다"≠"준비됐다"). 답은 graceful + preStop + readiness.
간헐적 502의 3종 세트?
간헐 + 백엔드 지표 정상 + prematurely closed → keep-alive 유휴 경쟁. 대응은 재사용하는 쪽의 유휴 상한을 더 짧게.
504에서 가장 먼저 배제할 것?
while connecting인지. 맞으면 느린 게 아니라 못 닿은 것(보안그룹·라우팅·accept 큐) — 여기서 DB를 파면 하루를 버린다.
유령 성공 한 문장?
프록시의 타임아웃은 기다림만 끊지 처리는 못 끊는다. COMMIT이 응답 쓰기보다 먼저라서 화면은 실패·DB는 성공. 답은 타임아웃 정렬 + 멱등성 키.
층 특정 두 도구?
요청 ID 전파(찍힌 층과 안 찍힌 층의 경계가 제조 층) + $upstream_status가 -면 내가 제조, 값이 있으면 전달.
본문 수신 중 타임아웃이면?
헤더가 이미 나갔으므로 502·504를 낼 수 없다 → 사용자는 "200 OK인데 잘린 본문"을 받는다.
재시도 안전성 순서?
503 안전(Retry-After) > 502는 문구에 따라(refused=안전, prematurely closed=위험) > 504는 불확실(멱등성 없이는 금지).

13-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

502가 배포 시간대에만 몇 초씩 발생합니다. 원인과 해결은? 필수힌트: "graceful shutdown을 켠다"에서 멈추면 절반이다. 틈이 두 개라는 것과 순서라는 단어가 채점 포인트

롤링 재시작에서 두 개의 틈이 생기기 때문이다.

첫째, 내려가는 쪽의 틈 — 인스턴스가 리슨 소켓을 닫았는데 로드밸런서의 대상 목록에는 아직 남아 있어, 헬스체크가 실패를 감지할 때까지(주기 × 실패 임계 횟수만큼) 죽은 인스턴스로 요청이 계속 간다. 그 요청들은 커널이 즉시 거절해 connect() failed (111) → 502가 된다.

둘째, 올라오는 쪽의 틈 — 프로세스가 떴다는 이유로 트래픽을 넣었는데 컨텍스트 초기화나 커넥션 풀 워밍업이 안 끝나 실패한다.

해결은 두 틈을 각각 메우는 것이다. 내려가는 쪽은 graceful shutdown(새 요청 수용은 멈추고 처리 중 요청은 끝까지)과 연결 드레이닝(LB 대상에서 먼저 빼고 나서 종료 시작), 올라오는 쪽은 readiness 프로브("프로세스 기동"이 아니라 "요청 처리 가능"을 확인한 뒤에만 투입)다.

한 걸음 더 — 종료 신호 전달과 "대상 목록에서 제외" 전파는 서로 다른 주체가 병렬로 하는 일이라, graceful shutdown만 켜도 순서는 보장되지 않는다

그래서 쿠버네티스라면 preStop 훅에 짧은 대기를 넣어 "제외가 먼저 끝나고 나서 종료가 시작되게" 순서를 강제한다. 무중단 배포는 설정 한 줄이 아니라 순서 설계라는 것이 이 질문의 채점 포인트다.

504가 났는데 백엔드 로그에는 그 요청이 성공으로 남아 있습니다. 어떻게 해석하나요? 함정힌트: 모순이 아니다. "순서" 하나로 전부 설명되고, 대응은 세 갈래인데 그중 하나를 빼먹기 쉽다

모순이 아니라 정상적인 귀결이다. 프록시의 타임아웃은 프록시의 기다림을 끊을 뿐 백엔드의 처리를 중단시키지 않는다. 프록시가 504를 내보낸 뒤에도 백엔드 스레드는 계속 일했고, 커밋까지 마친 뒤 응답을 쓰려다 이미 닫힌 소켓을 만난 것이다(ClientAbortException). 커밋이 응답 전송보다 먼저 일어난다는 순서가 이 현상의 전부다.

증거로 삼을 것은 프록시 타임아웃 값과 백엔드 처리 시간의 대소 관계다. $upstream_response_time이 proxy_read_timeout에 정확히 붙어 있으면 "백엔드가 느렸다"가 아니라 "프록시가 못 기다렸다"는 뜻이므로 계층 간 타임아웃 부정합이 확정된다.

대응은 세 갈래다. (1) 타임아웃 정렬 — 바깥 상한 안에 안쪽 작업의 최악 소요가 들어오게 한다. (2) 쓰기 API의 멱등성 키 도입 — 사용자가 재시도해도 중복 처리가 안 되게 한다. (3) 그 요청이 왜 그렇게 오래 걸렸는지를 별도 과제로 추적한다.

세 가지를 다 말하되 (2)를 빼먹지 않는 것이 중요하다 — (1)만 하면 다음 타임아웃 때 또 같은 사고가 난다
503과는 어떻게 구분하나요?힌트: 일반론(의도) + 제품별 실제 동작, 두 층으로 답해야 완성된다

기준은 "거절에 의도가 있었는가"다. 503은 서버가 스스로 "지금은 처리할 수 없지만 나중엔 될 수 있다"고 판단해 내리는 코드다 — 과부하 차단, 점검 모드, 헬스체크 실패로 인한 풀 제외가 여기 해당한다. 의도가 있으므로 Retry-After로 재시도 시점을 안내할 수 있다.

반면 502/504는 프록시가 뒷단과 통신을 시도한 결과로 판정된 것이라 의도가 없고, 안내할 재시도 시점도 없다.

다만 여기서 멈추면 절반이다. 실무에서는 같은 상황에 제품마다 다른 코드를 매기는 지점이 있다 — "살아 있는 백엔드가 하나도 없다"는 상황에서 Nginx는 no live upstreams와 함께 502를 내지만, ALB는 정상 대상이 없을 때 503을 낸다.

그러므로 일반론 위에 "우리 인프라의 LB/게이트웨이가 어떤 상황에 몇 번을 내는지를 미리 확인해두는 것"이 실전 대응력이라고 덧붙이면 답이 완성된다. 가산점

간헐적 502가 upstream prematurely closed connection 로그와 함께 납니다. 백엔드는 멀쩡해 보이는데요?힌트: 원인만 말하면 절반. "왜 프록시가 미리 알 수 없는가"까지 가야 한다

keep-alive 유휴 타임아웃 경쟁의 전형이다. 백엔드(Tomcat)가 유휴 연결을 닫는 순간과 프록시(Nginx)가 그 연결을 재사용하는 순간이 겹치면, 요청이 막 끊긴 연결에 실려 나가 502가 된다.

반드시 짚어야 할 것은 "왜 미리 알 수 없는가"다. 상대가 보낸 FIN은 "상대의 송신 방향이 끝났다"는 통보일 뿐이고 내 송신 방향은 여전히 열려 있으므로(half-close), 요청을 쓰는 write는 성공해 버린다. 오류는 응답을 읽으려는 순간에야 드러난다 — 즉 "보내기 전에 살아 있는지 확인"이라는 접근으로는 원천적으로 막을 수 없다.

그러므로 대응은 "이 상황 자체가 안 생기게 순서를 정하는 것" — 재사용하는 쪽(Nginx)의 유휴 상한을 닫는 쪽(Tomcat)보다 짧게 잡아 닫는 결정을 우리가 통제한다

"간헐적 + 백엔드 지표 정상 + premature close 로그"라는 3종 세트에서 이 가설을 즉시 꺼낼 수 있으면 실전 경험이 드러난다 — 원인을 모르면 몇 주씩 헤매는 종류의 장애이기 때문이다. (타임라인은 10번 문서 3-3절, 설정 정렬은 13번 문서 2절)

CDN → LB → Nginx → 앱처럼 프록시가 여러 층이면, 어느 층이 만든 502/504인지 어떻게 찾나요? 시니어 변별힌트: 방법 세 가지를 말하되, "셋 다 평시에 준비해 둬야 한다"가 진짜 채점 포인트

에러 코드는 "그것을 만든 층의 아래쪽"에 문제가 있다는 뜻이므로, 제조 층을 특정하는 순간 조사 범위가 절반씩 줄어든다. CDN이 만든 504라면 문제는 LB 이하이고, Nginx가 만든 504라면 문제는 앱 이하다. 그래서 제일 먼저 할 일은 원인 찾기가 아니라 층 특정이다.

첫째, 요청 ID를 전 층에 전파한다. 최전방에서 요청마다 고유 ID를 만들어 헤더로 붙이고 각 층이 그것을 로그에 남기며 뒤로 전달하면, 한 번의 검색으로 "이 요청이 어느 층까지 도달했는가"가 나온다. 3층 로그에 있는데 4층 로그에 없으면 3층이 반려한 것이다. 이때 층마다 새 ID를 만들면 연결이 끊겨 추적이 불가능해진다는 것이 함정이다.

둘째, 액세스 로그에 $status와 $upstream_status를 나란히 남긴다. $upstream_status가 비어 있으면(-) 응답을 아예 못 받았다는 뜻이므로 그 코드는 이 층이 만든 것이고, 값이 있으면 뒤쪽이 만든 코드를 전달만 한 것이다. 이 한 컬럼으로 "내가 범인인가 전달자인가"가 갈린다. $upstream_addr와 시간 지표가 여러 개 찍혀 있으면 proxy_next_upstream 재시도가 있었다는 뜻이다.

셋째, 응답 자체의 지문을 읽는다. Server: nginx와 <center>nginx</center> 푸터, Server: awselb/2.0, X-Cache: Error from cloudfront처럼 제품마다 기본 에러 페이지와 헤더가 다르므로 스크린샷이나 curl -i만으로도 층을 좁힐 수 있다. 본문이 우리 앱의 에러 JSON이면 그건 프록시가 만든 게 아니라 앱이 반환한 것이다.

진짜 채점 포인트 — 셋 다 평시에 준비해 둬야 장애 당일에 쓸 수 있다. 준비가 없으면 "어느 층이 만들었는지" 알아내는 데만 30분을 쓴다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

상태 코드는 200인데 JSON이 중간에 잘려서 옵니다. 502·504가 아닌데 무슨 일인가요? 함정힌트: 3절 지도의 4단계. "상태 코드가 언제 전송되는가"를 떠올린다

응답 헤더를 이미 클라이언트에게 내보낸 뒤에 문제가 생기면 프록시는 502·504를 낼 수 없다. 상태 줄과 헤더는 본문보다 먼저 나가버렸기 때문에, 그 시점 이후의 실패는 "연결이 그냥 끊긴 200 응답"으로 나타난다.

두 가지 원인이 대표적이다. ① 본문을 받는 도중 proxy_read_timeout이 만료됐다 — error log가 while reading response header가 아니라 while reading upstream으로 찍히는 것이 결정적 단서다. ② 백엔드가 본문을 생성하다 예외로 죽었다 — 스트리밍/청크 응답에서는 상태 코드를 이미 200으로 내보낸 뒤라 에러 코드로 바꿀 수 없다.

진단은 세 가지를 맞춰 본다 — 액세스 로그에서 같은 요청이 200인데 전송 바이트가 유난히 작은지, Content-Length와 실제 수신 바이트가 어긋나는지, error log에 while reading upstream이 있는지.

대응은 대용량·스트리밍 응답 경로에 별도의 타임아웃 여유를 주고(전체 시간이 아니라 청크 사이 간격이 기준임을 이용한다), 가능하면 응답을 다 만든 뒤에 헤더를 보내도록 하여 실패를 상태 코드로 표현할 수 있는 시점에 몰아넣는 것이다.

proxy_read_timeout을 60초로 늘렸더니 504는 줄었습니다. 이걸로 끝인가요?힌트: 지연시간 하나만 보면 반드시 속는다. 자원 점유가 어떻게 변하는지 계산해 본다

504 숫자는 줄지만, 그 대가로 다른 것이 나빠진다. 타임아웃은 "느림을 고치는 장치"가 아니라 "손해를 어디서 끊을지 정하는 정책"이다.

첫째, 자원 점유가 그대로 늘어난다. 요청 하나가 시스템에 머무는 시간이 10초에서 60초가 되면 같은 트래픽에서 동시에 붙잡히는 요청 수가 6배가 된다(L = λ × W). 톰캣 스레드·DB 커넥션·Nginx 워커 연결이 그만큼 오래 묶이므로, 느린 API 하나가 무관한 API까지 끌고 내려간다.

둘째, 사용자는 60초를 기다린다. 그 사이 새로고침·재시도가 겹치면 부하가 오히려 늘어난다.

셋째, 반대로 좋아지는 것도 있다 — 프록시가 끝까지 기다릴 확률이 높아지므로 유령 성공은 줄어든다. 즉 이 값은 "자원 점유"와 "유령 성공" 사이의 거래이고, 그래서 답은 늘리기/줄이기가 아니라 정렬이다.

바깥 상한 안에 안쪽 작업의 최악 소요가 들어오게 정렬하고, 안쪽(외부 호출·쿼리)에도 반드시 상한을 건다 — 안쪽이 먼저 포기해야 내가 상황을 통제한다

그리고 "왜 60초가 필요한 요청이 존재하는가"를 별도 과제로 남긴다. 그런 작업은 대개 동기 요청-응답이 아니라 비동기 처리(작업 접수 → 202 → 폴링/알림)로 옮겨야 할 후보다.

502가 났을 때 앞단에서 자동 재시도를 걸어도 되나요? 시니어 변별힌트: "멱등하면 된다"에서 한 발 더 — 여러 층이 각자 재시도하면 무슨 일이 생기나

"502니까 재시도"는 위험하다. 같은 502라도 로그 문구에 따라 안전성이 다르다. connection refused는 요청이 도달조차 못 했으므로 부작용이 있을 수 없어 안전하지만, prematurely closed는 백엔드가 요청을 받아 처리하다 끊긴 것일 수도 있어 안전하지 않다.

그래서 판단 기준은 코드가 아니라 "요청의 성질"이다. 멱등한 GET·PUT·DELETE는 재시도해도 되고, POST는 멱등성 키가 있을 때만 재시도한다. Nginx의 proxy_next_upstream이 기본적으로 비멱등 요청을 이미 보낸 뒤에는 다음 서버로 넘기지 않는 것도 같은 이유이며, 넘기려면 non_idempotent를 명시해야 한다 — 그것은 중복 처리를 감수하겠다는 선언이다.

한 발 더 들어가면 재시도 증폭이다. CDN·LB·Nginx·클라이언트 SDK가 각자 3번씩 재시도하면 최악의 경우 곱셈으로 커진다 — 이미 힘들어하는 백엔드에 몇 배의 부하를 더 얹어 장애를 키우는 전형적인 경로다.

재시도에는 항상 세 가지를 함께 — 지수 백오프 + 지터, 재시도 총량 상한(예산), 층을 하나로 정해 그 층에서만
502가 났고 원인이 OOM kill이라는데, 앱 로그에는 왜 아무 흔적도 없나요?힌트: JVM이 던지는 OOM과 커널이 죽이는 OOM은 다른 사건이다

두 가지 "OOM"을 구분해야 한다.

JVM 힙 부족
OutOfMemoryError가 던져지므로 앱 로그에 스택 트레이스가 남는다. 이 경우 보통 500이 나간다.
컨테이너 메모리 제한 초과
커널의 OOM killer가 프로세스에 SIGKILL을 보낸다. 잡을 수도, 로그를 남길 수도 없다 — 종료 훅조차 안 돈다.

그래서 앱 로그가 깨끗한 것이 정상이다. 처리 중이던 연결은 그대로 끊기고, 프록시에는 upstream prematurely closed connection 또는 recv() failed (104)가 찍혀 502가 된다. 새 요청은 리슨 소켓이 사라졌으므로 connect() failed (111)이 된다.

확인 방법은 앱이 아니라 플랫폼 쪽이다 — 컨테이너의 재시작 횟수, 이전 종료의 Reason: OOMKilled, 종료 코드 137(= 128 + SIGKILL 9), 그리고 호스트의 커널 로그(dmesg)다.

대응은 힙만 보지 않는 것이다. 컨테이너 제한은 힙 + 메타스페이스 + 스레드 스택 + 네이티브 버퍼를 모두 담아야 하므로, 힙을 컨테이너 제한과 같게 잡으면 반드시 죽는다. 컨테이너 인식 옵션으로 제한 대비 비율로 힙을 잡고 나머지를 남겨 둔다.

한 줄 요약
502와 504는 둘 다 프록시가 만드는 코드지만 세우는 가설이 다르다 — 502는 "백엔드가 대화 자체를 못 했다"이므로 배포 이력·프로세스 생존·프록시 error log 문구(connection refused인지 prematurely closed인지)부터 보고, 504는 "백엔드가 살아 있는데 느리다"이므로 응답시간 지표와 그 뒤의 대기(DB·외부 호출·스레드 풀)부터 본다. 여기에 코드를 만든 주체가 프록시라서 앱 로그가 깨끗할 수 있다는 것, 504 뒤에는 백엔드가 뒤늦게 커밋하는 유령 성공과 재시도로 인한 중복 처리 위험이 따라와 멱등성 키가 필요하다는 것, 그리고 프록시가 여러 층이면 요청 ID 전파와 $upstream_status 로깅으로 제조 층부터 특정해야 한다는 것까지가 초동 대응의 완성이다.
