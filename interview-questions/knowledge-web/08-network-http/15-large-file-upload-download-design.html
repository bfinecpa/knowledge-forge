대용량 파일 업로드/다운로드 설계
데이터가 흐르는 경로 자체를 설계하기

면접 질문: "대용량 파일(이미지) 업로드/다운로드 시 서버 설계 고려사항은? (스트리밍, presigned URL)"

핵심 관전 포인트 — 대용량 파일 처리의 원칙은 두 단계다. 1단계는 "메모리 사용량이 파일 크기에 비례하지 않게 하라" — MultipartFile.getBytes()처럼 통째로 읽는 코드는 파일 크기 × 동시 요청 수만큼 힙을 먹다가 OOM으로 죽으므로, 요청 스트림에서 저장소로 조각 단위로 흘려보내야 한다. 2단계는 "파일이 애플리케이션 서버를 아예 거치지 않게 하라" — presigned URL(스토리지가 특정 객체에 대해 특정 동작을 특정 시각까지만 허용한다고 자기 키로 서명해 발급한 URL. 서명 자체가 권한의 증거이므로 별도 인증 없이 스토리지가 검증할 수 있다)로 클라이언트가 오브젝트 스토리지에 직접 올리고, 다운로드는 CDN + signed URL로 엣지가 대신 내려준다. 앱 서버는 파일 바이트를 한 번도 만지지 않고 권한 검증·URL 발급·메타데이터 확정이라는 제어만 맡으므로, 파일 트래픽이 10배가 되어도 서버 용량 계획이 흔들리지 않는다. 대신 새 책임이 생긴다 — 앱이 업로드 완료를 모르므로 스토리지 이벤트나 완료 콜백으로 확인해야 하고, 크기·타입을 앱이 직접 막을 수 없어 서명에 조건을 넣어야 하며, 바이러스 검사와 후처리를 업로드 이벤트 기반 비동기 파이프라인으로 옮겨야 하고, "URL만 발급되고 안 올라간 경우"와 "올라갔는데 DB 레코드가 없는 경우"라는 양방향 고아를 PENDING → CONFIRMED 상태 전이와 정리 배치로 수습해야 한다. 여기에 계층별 크기·타임아웃 정합(Nginx client_max_body_size가 가장 흔한 범인), 다운로드의 Range 요청(Range: bytes=0-1023 → 206 Partial Content)이 만드는 이어받기·구간 탐색, 파일이 커질수록 필수가 되는 분할 업로드와 재개까지가 실무 고려사항의 전체 그림이다.
  • 1
    1단계 — 메모리 사용량이 파일 크기에 비례하면 잘못된 설계다. getBytes()는 힙 사용량을 파일 크기 × 동시 요청 수로 만들고(200MB × 50건 ≈ 9.8GB), 터지는 것은 업로드와 아무 상관없는 남의 스레드다. 입력 스트림을 저장소로 흘리면 힙은 버퍼 크기로 고정된다.
  • 2
    2단계 — 그래도 서버를 통과하는 한 자원은 계속 든다. 그래서 경로에서 서버를 빼낸다. presigned URL로 클라이언트가 스토리지에 직접 올리고 CDN이 직접 내려준다. 앱 서버가 처리하는 것은 수 KB짜리 JSON 두 번이 되고, 용량 계획의 지배 변수가 "파일 전송량"에서 "비즈니스 요청 수"로 바뀐다.
  • 3
    단, presigned는 공짜가 아니라 거래다 — 전송 부담을 덜어내는 대신 제어와 정합성 관리라는 새 책임을 산다. 완료 확인·URL 유출 방어·조건 강제·검증 파이프라인·양방향 고아 정리 다섯이고, 여기에 계층별 한도 정합과 Range·분할 업로드를 얹으면 그림이 완성된다.

0. 질문 + 출제 의도

질문: "대용량 파일(이미지) 업로드/다운로드 시 서버 설계 고려사항은? (스트리밍, presigned URL)"

출제 의도: 파일을 서버 메모리에 통째로 올리는 코드는 파일이 크면 OOM이다. 스트리밍과 presigned URL(서버를 우회시키는 설계)을 아는지 — 요청 처리 코드 한 줄이 아니라 데이터가 흐르는 경로 자체를 설계하는 능력을 확인하는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① "파일 업로드 API를 만들어 봤다"에서 멈추는 것 → 1~3절에서 힙·디스크·스레드가 각각 어떻게 소모되는지를 숫자로 계산한다. "OOM 날 수 있어요"가 아니라 "200MB × 50건 = 9.8GB, 힙 4GB면 20건째"까지 말할 수 있어야 한다.
② "presigned URL 쓰면 됩니다"에서 멈추는 것 — 절반의 답이다 → 9절에서 서버가 경로에서 빠지는 순간 사라지는 다섯 가지 일과 그것을 어떻게 다시 만드는지를 다룬다. 여기가 시니어 변별 구간이다.
③ 코드만 보고 인프라를 안 보는 것 → 8절에서 "큰 파일만 실패하는데 앱 로그엔 아무것도 없다"는 유령 현상의 정체(client_max_body_size 기본 1MB)와, 상태 코드로 원인을 가르는 진단 분기를 정리한다.

1. 파일이 지나는 길 — 경로 위의 모든 지점이 병목·장애 후보가 된다

평범한 API 응답은 수 KB다. 어디를 거치든 아무도 신경 쓰지 않는다. 파일이 수십 MB~수 GB가 되는 순간, 그동안 보이지 않던 모든 제한이 한꺼번에 드러난다. 그래서 이 질문의 답은 "코드를 어떻게 짤까"가 아니라 "파일을 어느 경로로 흘릴까"에서 시작한다.

1절에서 가져갈 문장

경로 위 계층의 가장 작은 값이 실질 한도이고, 앞 계층에서 잘린 요청은 뒤 계층의 로그에 없다

2. 1단계 원칙 — 메모리 사용량이 파일 크기에 비례하면 잘못된 설계다

2-1. 왜 통째로 읽으면 죽는가 — 단건이 아니라 동시성에서 터진다

getBytes()는 이름 그대로 파일 전체를 byte[] 하나로 만들어 준다. 편하지만, byte[]는 힙에 통째로 잡히는 연속된 메모리다. 문제는 단건이 아니라 동시성에서 터진다.

before 파일 전체를 byte[]로 힙에 적재한다
@PostMapping("/api/files")
public FileResponse upload(@RequestParam MultipartFile file) throws IOException {
    byte[] bytes = file.getBytes();   파일 전체가 힙에
    return storage.save(bytes);       저장 끝날 때까지 붙들고 있다
}

// 힙 사용량 = 파일 크기 x 동시 요청 수
// 파일이 커지면 선형으로 증가한다 — 상한이 없다
after 입력 스트림에서 저장소로 조각 단위로 흘려보낸다
@PostMapping("/api/files")
public FileResponse upload(@RequestParam MultipartFile file) throws IOException {
    try (InputStream in = file.getInputStream()) {   닫힘 보장
        // 저장소 클라이언트가 내부적으로 수 KB~수 MB 버퍼로
        // read → write를 반복한다. 어느 순간에도 힙에 올라와
        // 있는 것은 그 버퍼 하나뿐이다.
        // 파일이 200MB든 2GB든 이 메서드가 쓰는 힙은 동일하다.
        return storage.save(in, file.getSize(), file.getContentType());
    }   // try-with-resources: 예외가 나도 스트림이 닫힌다 (핸들 누수 방지)
}

OOM까지 가는 길을 한 단계씩 — 이 계산을 말할 수 있어야 한다

1
요청 하나가 잡는 힙 — 200MB 파일 → byte[] 200MB
2
동시 요청 수를 곱한다 — 동시 업로드 50건 → 200MB × 50 = 10,000MB ≈ 9.8GB
3
힙 크기와 비교한다 — JVM 힙이 4GB라면 4GB를 넘는 20건째쯤에서 OutOfMemoryError
4
실제로는 더 빨리 죽는다 — ① byte[] 말고도 애플리케이션이 쓸 힙이 필요하다 ② GC가 큰 배열을 옮기지 못해(대개 Old 영역 직행) Full GC가 잦아진다 ③ 200MB 배열 하나를 할당할 연속된 공간이 없으면 힙에 여유가 있어도 실패한다

외울 문장은 하나다

메모리 사용량이 파일 크기에 비례하면 잘못된 설계,
버퍼 크기로 고정되면 올바른 설계

비유하자면 저수지를 통째로 집 안에 들이는 것과 호스를 저수지에 연결해 흘려보내는 것의 차이다. 호스가 하는 일은 저수지 크기와 무관하게 항상 같다.

2-2. 다운로드도 대칭이다

파일을 byte[]로 읽어 응답 바디에 담지 말고, 저장소의 스트림을 응답 스트림에 이어 붙인다.

before 파일 전체를 읽어 응답 바디에 담는다
@GetMapping("/api/files/{id}")
public ResponseEntity<byte[]> downloadBad(@PathVariable Long id) throws IOException {
    byte[] bytes = storage.readAll(id);   힙에 통째로
    return ResponseEntity.ok(bytes);
}

// 업로드와 정확히 같은 이유로 위험하다.
// 게다가 전송이 끝날 때까지 이 배열이 살아 있으므로,
// 느린 클라이언트일수록 힙을 오래 붙든다.
after 저장소 스트림을 응답 스트림으로 흘린다
@GetMapping("/api/files/{id}")
public ResponseEntity<StreamingResponseBody> download(@PathVariable Long id) {
    FileMeta meta = fileService.getForDownload(id);  권한·존재 검증은 여기서 끝낸다

    StreamingResponseBody body = out -> {
        try (InputStream in = storage.open(meta.storageKey())) {
            in.transferTo(out);    // 내부 버퍼로 read → write 반복
        }
    };

    return ResponseEntity.ok()
            // 크기를 알면 반드시 명시한다. 이것이 없으면 청크 전송으로 나가고,
            // 클라이언트는 전체 크기를 몰라 진행률을 계산할 수 없다.
            .contentLength(meta.size())
            .contentType(MediaType.parseMediaType(meta.contentType()))
            .body(body);
}
StreamingResponseBody가 해결하는 것과 해결하지 못하는 것 이것을 반환하면 Spring이 응답을 비동기로 처리한다 — 컨트롤러 메서드는 즉시 반환되고, 실제 전송은 별도의 태스크 실행자 스레드에서 일어난다. 요청 스레드를 전송 시간 내내 붙들지 않는다는 점이 ResponseEntity<byte[]>와의 차이다. 다만 완전히 공짜는 아니다 — 전송 자체는 여전히 블로킹이므로 태스크 실행자의 스레드 하나가 전송 내내 점유된다. 문제를 다른 풀로 옮겼을 뿐 없앤 것은 아니고, 이것이 4절에서 2단계로 넘어가는 이유 중 하나가 된다.
이 코드에서 getForDownload가 람다 바깥에 있는 이유 함정 스트림을 흘리기 시작한 뒤에는 에러 응답으로 바꿀 수 없다. 이미 200 OK와 바디 일부가 나간 상태이므로 404나 500으로 정정할 방법이 없고, 클라이언트는 "성공했는데 파일이 잘린" 상태를 받는다. 그래서 존재·권한 검증은 반드시 전송 시작 전에 전부 끝낸다.

3. 그런데 Spring은 업로드 파일을 어디에 두는가

여기서 반드시 짚어야 할 사실이 있다. file.getInputStream()으로 스트리밍한다고 해서 "요청이 도착하는 대로 저장소로 흘러가는" 것이 아니다.

한 문장으로 MultipartFile이 컨트롤러 메서드의 파라미터로 들어와 있다는 것은, 그 시점에 이미 요청 본문 전체가 수신되어 어딘가에 저장을 마쳤다는 뜻이다. Spring Boot의 기본 구성에서 그 "어딘가"는 서블릿 컨테이너(Tomcat)가 관리하는 임시 저장소다.
설정 어디에 저장되는지는 설정 하나가 결정한다
spring:
  servlet:
    multipart:
      # 이 크기 이하의 파트는 메모리에 두고, 초과분은 디스크 임시 파일로 내린다.
      file-size-threshold: 0B     기본값 0B — 즉 기본 동작은 "전부 디스크"
      # 임시 파일을 둘 디렉토리. 비워두면 서블릿 컨테이너의 기본 임시 디렉토리를 쓴다.
      location: ""
      max-file-size: 1MB          # 파일 하나의 상한. 기본 1MB.
      max-request-size: 10MB      # 요청 전체(여러 파일 + 폼 필드)의 상한. 기본 10MB.

3-1. 이 사실이 실무에서 만드는 결과 셋

① getBytes()의 죄가 더 선명해진다
파일은 이미 디스크에 안전하게 있는데, getBytes()는 그것을 굳이 힙으로 한 번 더 복사한다. 아무 이득 없이 OOM 위험만 사는 셈이다. getInputStream()은 그 임시 파일을 스트림으로 읽을 뿐이다.
② 임시 디렉토리가 찬다
대응은 임시 디렉토리를 충분한 용량의 별도 볼륨으로 지정(spring.servlet.multipart.location)하고 그 볼륨 사용률을 모니터링에 올리는 것. 동시 업로드 수에 상한(세마포어, 게이트웨이 동시성 제한)을 두는 것도 유효한 방어다.
③ 진짜 "받는 즉시 흘리기"는 별개의 선택이다
spring.servlet.multipart.enabled=false로 두고 HttpServletRequest.getInputStream()을 직접 파싱하거나, WebFlux에서 FilePart / Flux<DataBuffer>로 받는 방식. 복잡도가 확 올라가는 선택이라 대개 여기까지 가지 않고 presigned URL로 넘어간다.
한 가지 더 — Nginx 쪽에도 같은 임시 파일이 쌓인다 Nginx도 기본적으로 요청 본문을 먼저 버퍼링한다(proxy_request_buffering on). 느린 클라이언트로부터 Tomcat을 보호하는 좋은 기본값이지만, 그 말은 Nginx 쪽에도 같은 크기의 임시 파일이 쌓인다는 뜻이다(client_body_temp_path). 대용량 업로드가 많다면 Nginx의 디스크도 함께 봐야 한다.

4. 스트리밍해도 남는 비용 — 2단계로 가는 이유

1단계를 다 적용해도 근본적으로 남는 것이 있다. 전송이 서버를 통과하는 동안 서버의 자원을 계속 쓴다는 것이다.

5. 2단계 원칙 — 서버를 경유시키지 말라 (presigned URL)

정의 — 면접에서 이 한 문장을 먼저 말한다

presigned URL은 오브젝트 스토리지가 "특정 객체에 대해, 특정 동작을, 특정 시각까지만 허용한다"고
자기 비밀 키로 서명해서 발급한 URL이다

"미리(pre) 서명된(signed)"이라는 이름 그대로, 실제 요청이 오기 전에 미리 허가증을 만들어 둔 것이다.

service ① URL 발급 — 서명을 발급하는 순간이 곧 "허가했다"는 뜻이다
@Service
@RequiredArgsConstructor
class FileService {

    private final S3Presigner presigner;   // 서명 발급 전용 클라이언트
    private final S3Client s3;             // HEAD 등 제어 API용
    private final FileRepository files;
    private final String bucket;

    private static final Duration UPLOAD_URL_TTL = Duration.ofMinutes(5);
    private static final long MAX_UPLOAD_BYTES = 100L * 1024 * 1024;   // 100MB

    @Transactional
    public UploadUrlResponse issueUploadUrl(Long userId, UploadUrlRequest req) {
        // ② 권한 검사 — 이 판단이 곧 서명의 근거가 된다.
        //    서명을 발급하는 순간 "허가했다"는 뜻이므로 여기가 유일한 검문소다.
        permissionChecker.checkCanUpload(userId, req.purpose());

        // 앱이 강제할 수 있는 것은 여기서 미리 막는다.
        // 다만 클라이언트가 신고한 size는 신뢰할 수 없다 — 확정 검증은 ⑧에서 한다.
        if (req.size() > MAX_UPLOAD_BYTES) throw new BadRequestException("파일이 너무 큽니다");
        if (!ALLOWED_TYPES.contains(req.contentType())) throw new BadRequestException("허용되지 않는 형식입니다");

        // ③ 저장 키는 서버가 만든다. 클라이언트가 준 파일명을 그대로 키로 쓰면
        //    경로 조작(../), 다른 사용자 파일 덮어쓰기, 키 충돌이 전부 가능해진다.
        //    원본 파일명은 표시용으로 DB에만 저장한다.
        String key = "uploads/%s/%s".formatted(
                LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy/MM")), UUID.randomUUID());

        // ④ 먼저 PENDING으로 레코드를 만든다.
        //    "업로드는 됐는데 DB에 아무 흔적이 없는" 고아를 원천적으로 줄이기 위해,
        //    서명을 발급하기 전에 의도를 기록해 둔다 (9절 ⑤).
        FileRecord record = files.save(FileRecord.pending(userId, key, req));

        // ⑤ 서명 발급.
        PutObjectRequest objectRequest = PutObjectRequest.builder()
                .bucket(bucket)
                .key(key)
                // Content-Type을 지정하면 이 값이 서명에 포함되므로,
                // 클라이언트는 정확히 이 타입으로만 PUT할 수 있다.
                // 다른 값을 보내면 서명 불일치로 스토리지가 거부한다.
                .contentType(req.contentType())
                .build();

        PutObjectPresignRequest presignRequest = PutObjectPresignRequest.builder()
                // 만료를 짧게 잡는 것이 URL 유출에 대한 1차 방어다 (9절 ②).
                .signatureDuration(UPLOAD_URL_TTL)
                .putObjectRequest(objectRequest)
                .build();

        String uploadUrl = presigner.presignPutObject(presignRequest).url().toString();
        return new UploadUrlResponse(record.getId(), uploadUrl, UPLOAD_URL_TTL.toSeconds());
    }
SDK 버전 주의 SDK 버전에 따라 클래스·메서드 이름이 다르다. 위 코드는 AWS SDK for Java v2의 S3Presigner 형태를 기준으로 한 것이므로, 실제 적용 시에는 사용하는 SDK 문서로 시그니처를 확인한다. 개념(무엇을 서명에 넣고 만료를 어떻게 주는가)은 SDK가 달라도 같다.
service ⑦⑧⑨⑩ 완료 확인 — 클라이언트의 신고를 믿지 않는다
    @Transactional
    public FileResponse confirmUpload(Long userId, Long fileId) {
        FileRecord record = files.findByIdAndOwner(fileId, userId)
                .orElseThrow(() -> new NotFoundException("파일을 찾을 수 없습니다"));

        // 클라이언트의 완료 통보는 네트워크 재시도로 두 번 올 수 있으므로
        // 이 메서드는 멱등해야 한다 — 두 번째 호출이 에러가 되면 안 된다.
        if (record.getStatus() == Status.CONFIRMED) return FileResponse.from(record);

        // ⑧ ★ 클라이언트의 신고를 믿지 않고 스토리지에 직접 확인한다.
        //    "완료됐다"는 말만 믿으면, 실제로는 안 올라간 파일에 대해
        //    CONFIRMED 레코드가 생겨 나중에 404를 뿜는 유령 파일이 된다.
        HeadObjectResponse head;
        try {
            head = s3.headObject(b -> b.bucket(bucket).key(record.getStorageKey()));
        } catch (NoSuchKeyException e) {
            throw new BadRequestException("업로드가 완료되지 않았습니다");
        }

        // 크기도 여기서 확정한다. 발급 시 클라이언트가 신고한 size는 참고값일 뿐이고,
        // 실제로 얼마가 올라왔는지는 스토리지만 안다.
        if (head.contentLength() > MAX_UPLOAD_BYTES) {
            s3.deleteObject(b -> b.bucket(bucket).key(record.getStorageKey()));
            record.markRejected("크기 초과");
            throw new BadRequestException("파일이 너무 큽니다");
        }

        record.confirm(head.contentLength(), head.eTag());   // ⑨ 상태 전이
        postProcessQueue.enqueue(record.getId());            ⑩ 후처리는 큐로 (10절)
        return FileResponse.from(record);
    }

    public String issueDownloadUrl(Long userId, Long fileId) {
        FileRecord record = files.findById(fileId)

        permissionChecker.checkCanDownload(userId, record);   권한 판단은 우리 몫

                .key(record.getStorageKey())

    }

7-1. 이 설계가 답의 중심인 이유 — 지배 변수가 바뀐다

서버 경유

  • 파일 트래픽 10배 → 대역폭 10배, 커넥션 10배, 전송 스레드 10배
  • → 서버 증설이 필요하고, 늘려도 대역폭이라는 물리적 한계에 같은 비율로 부딪힌다
  • 용량 계획의 지배 변수 = 파일 전송량

  • 파일 트래픽 10배 → 앱 서버가 처리하는 것은 URL 발급 요청 10배(수 KB짜리 JSON)
  • 파일 바이트는 스토리지/엣지가 전부 받아낸다 — 애초에 이 일을 하려고 만들어진 시스템이라 사실상 무제한으로 확장된다
  • 용량 계획의 지배 변수 = 비즈니스 요청 수

9. presigned URL의 대가 — 무엇을 새로 책임지게 되는가 시니어 변별

"presigned URL을 쓰면 됩니다"에서 멈추면 절반의 답이다. 서버가 경로에서 빠지는 순간 서버가 하던 일들이 사라지는데, 그 일들이 필요 없어진 것이 아니라 다른 방식으로 다시 만들어야 하는 것이기 때문이다. 다섯 가지다.

다섯 가지를 순서대로 꺼내는 암기 장치 — 완·유·조·검·고

완 — 완료를 모른다→ 유 — URL이 유출된다→ 조 — 조건(크기·타입) 강제가 어렵다→ 검 — 검사 지점이 사라진다→ 고 — 고아 파일이 양방향으로 생긴다
전체를 감싸는 한 문장 — "전송 부담을 덜어내는 대신 제어와 정합성 관리라는 새 책임을 사는 거래"

9-1. ① 앱이 업로드 완료를 모른다

서버 경유 업로드에서는 요청이 끝나는 순간이 곧 업로드 완료 시점이었다. presigned 방식에서는 파일이 스토리지로 직접 가므로 앱은 그 일이 일어났는지조차 모른다. 확인 수단이 둘 있다.

완료 콜백 — 클라이언트가 알려주는 방식 (6절 ⑦)

  • 빠르다 — 사용자가 즉시 결과를 본다
  • 누락된다 — 업로드 직후 브라우저를 닫거나, 네트워크가 끊기거나, 앱이 죽으면 통보가 안 온다
  • 신뢰할 수 없다 — 반드시 스토리지에 HEAD로 실물을 확인해야 한다(6절 ⑧)

스토리지 이벤트 통지 — 스토리지가 알려주는 방식

  • 누락되지 않는다 — 객체가 생성되면 스토리지가 이벤트를 발행한다(S3라면 큐나 함수로 보낼 수 있다)
  • 약간 늦게 온다 (초 단위 지연)
  • 클라이언트를 신뢰하지 않아도 되고 클라이언트가 죽어도 동작한다 — 결정적 장점
실무에서는 둘 다 건다 콜백으로 사용자 응답을 빠르게 주고, 이벤트를 최종 진실로 삼는다. 둘 다 같은 처리를 호출하므로 그 처리는 반드시 멱등해야 한다 — 상태 전이를 UPDATE ... WHERE status = 'PENDING' 같은 조건부 갱신으로 만들고, 큐 메시지 키를 fileId로 두어 중복을 흡수한다.

9-2. ② 클라이언트가 URL을 남에게 넘길 수 있다

발급된 URL은 그것을 가진 누구나 쓸 수 있다. 서명 안에 "누가 쓸 수 있는지"는 들어 있지 않기 때문이다. 사용자가 URL을 복사해 다른 사람에게 주거나, 브라우저 히스토리·로그·에러 리포트를 통해 새어 나가면 그 사람도 같은 동작을 할 수 있다.

방어 1 — 만료를 짧게
업로드 URL은 몇 분이면 충분하다. 다운로드 URL도 "이 링크로 지금 받는다"는 용도라면 10분 안쪽. 유출되더라도 창이 좁으면 피해가 제한된다. S3 계열의 서명 방식에서는 최대 만료가 7일로 제한되기도 하므로, "영구 링크"를 이 방식으로 만들 수는 없다.
방어 2 — 동작과 대상을 좁혀서 서명
PUT용 서명은 GET에 쓸 수 없고, 특정 키에 대한 서명은 다른 키에 쓸 수 없다. "업로드용 URL로 다른 파일을 덮어쓸 수 있나?"의 답이 "없다"가 되도록 키를 서버가 정하고 서명에 고정한다.
방어 3 — 조건을 서명에 포함
Content-Type을 서명에 넣으면 클라이언트는 정확히 그 타입으로만 올릴 수 있다(6절 코드). 다른 값을 보내면 서명이 안 맞아 스토리지가 거부한다.

9-3. ③ 파일 크기·타입을 앱이 강제하기 어렵다

크기가 특히 까다롭다 단순한 presigned PUT에서는 클라이언트가 신고한 크기와 실제 올리는 크기가 다를 수 있다. 앱이 "100MB까지"라고 판단해 URL을 줬는데 클라이언트가 5GB를 올려도, 스토리지 입장에서는 서명이 유효한 정상 요청이다.

대응 A — 스토리지가 강제하게 한다

  • S3 계열에는 브라우저 폼 업로드용 POST 방식이 따로 있고, 여기에는 크기 범위 조건(content-length-range)을 정책에 넣어 서명할 수 있다. 스토리지가 업로드 시점에 크기를 직접 강제하므로 이것이 가장 확실하다.
  • PUT 방식이라면 Content-Length를 서명 대상 헤더에 포함시켜 정확한 크기를 강제하는 방법이 있지만, 업로드 전에 정확한 바이트 수를 알아야 쓸 수 있다.

대응 B — 업로드 완료 시점의 사후 검증 (반드시)

  • 6절의 confirmUpload처럼 HEAD로 실제 크기를 확인하고, 초과했으면 객체를 지우고 레코드를 거부 상태로 만든다.
  • 스토리지에 잠깐 올라갔다가 지워지는 낭비는 있지만, 앱이 최종 판단을 쥔다는 점에서 반드시 있어야 하는 방어선이다.
타입도 같은 구조다 — 헤더를 고정해도 "내용"은 보장 못 한다 Content-Type 헤더는 클라이언트가 보내는 값이라 서명으로 고정해도 "내용이 실제로 그 타입인지"는 보장하지 못한다. image/jpeg라고 선언하고 실행 파일을 올릴 수 있다. 그래서 내용 기반 검증은 결국 업로드 후 후처리에서 해야 한다(다음 항목).

9-4. ④ 바이러스 검사와 후처리를 어디서 하는가

서버 경유였다면 저장 직전에 파일 시그니처를 확인하고 스캔할 수 있었다. presigned 방식에서는 앱이 바이트를 한 번도 못 보므로 그 지점이 사라진다. 해법은 검증의 시점을 옮기는 것이다 — 업로드 전에서 업로드 후로. 그리고 검증이 끝나기 전에는 그 파일이 노출되지 않게 상태로 막는다.

9-5. ⑤ 고아 파일 — 양방향 정합성 문제 시니어 변별

이것이 presigned 설계에서 가장 놓치기 쉬운 부분이다. DB(메타데이터)와 스토리지(실물)는 서로 다른 시스템이라 하나의 트랜잭션으로 묶을 수 없다. 그래서 어긋남이 양방향으로 생긴다.

대응 ② 양방향 정리 루프 — 방향 A는 배치로 잡는다
-- 방향 A: 오래된 PENDING을 찾아 정리한다.
-- URL 만료(5분)보다 충분히 긴 시간(예: 24시간)을 기다린 뒤 처리한다 —
-- 느린 회선의 사용자가 아직 올리고 있는 중일 수 있기 때문이다.
SELECT id, storage_key
  FROM file_record
 WHERE status = 'PENDING'
   AND created_at < now() - interval '24 hours'   만료보다 넉넉히
 ORDER BY created_at
 LIMIT 500;
-- 각 건에 대해 스토리지에 실물이 있는지 확인한다.
--   있으면  → CONFIRMED로 되살린다 (완료 통보만 유실된 경우다)
--   없으면  → 레코드 삭제 (진짜 미완료다)
방향 B는 스토리지 쪽 기능을 함께 쓴다 — 수명주기 규칙(lifecycle rule) 오브젝트 스토리지가 제공하는 "이 조건의 객체를 N일 뒤 자동으로 삭제한다"는 정책이다. 격리 영역(quarantine/ 프리픽스)에 만료 규칙을 걸어두면, 검증을 통과해 서비스 영역으로 옮겨진 객체는 살아남고 어떤 이유로든 옮겨지지 못한 객체는 자동으로 사라진다. 서비스 영역의 진짜 고아는 주기적인 대사 배치로 잡는다 — 스토리지의 객체 목록과 DB의 키 목록을 대조해 참조 없는 객체를 찾는다.

10. 업로드 검증과 비동기 후처리

10-1. 신뢰 경계 밖에서 온 파일 — 클라이언트가 보낸 모든 값은 위조 가능하다

검증 항목 다섯 — 이 순서로 말하면 빠짐이 없다

확장자·Content-Type은 증거가 아니다
둘 다 클라이언트가 정한 문자열일 뿐이다. .jpg로 끝나고 image/jpeg라고 선언한 실행 파일을 만드는 데는 1초도 걸리지 않는다.
실제 형식은 매직 바이트로
대부분의 파일 형식은 맨 앞 몇 바이트에 고유한 값(파일 시그니처)을 갖는다 — 그것을 읽어 선언된 타입과 일치하는지 확인한다.
크기 상한은 두 곳에서
발급 시점의 조건 서명(가능하면)과 완료 시점의 실물 확인(반드시). 9절 ③의 대응 A·B가 그대로 대응된다.
이미지는 재인코딩
검증이면서 동시에 정화(sanitize)다. 픽셀만 꺼내 다시 인코딩하면 메타데이터에 숨은 페이로드가 사라진다.
저장 키는 서버가 만든다
클라이언트가 준 파일명을 그대로 키로 쓰면 경로 조작(../../etc/…), 다른 사용자 파일 덮어쓰기, 키 충돌이 전부 가능하다. 원본 파일명은 표시용으로 DB에만 두고, 다운로드 시 Content-Disposition으로 되살린다(12절).

10-2. 후처리는 비동기로 — 업로드 응답과 분리한다

썸네일 생성, 포맷 변환(WebP), 바이러스 스캔, 동영상 인코딩 같은 후처리를 업로드 요청 안에서 동기로 처리하면 안 된다.

Before — 동기 후처리 (총 17초)

완료 통보→스캔 5초→썸네일 3종 8초→WebP 4초→응답
  • 사용자는 17초 동안 로딩 화면을 본다
  • 그 사이 브라우저·프록시·LB의 타임아웃에 걸릴 수 있다
  • 타임아웃 후 사용자가 재시도하면 후처리가 처음부터 다시 돈다
  • 후처리 중 하나만 실패해도 업로드 전체가 실패로 보인다
  • CPU를 많이 쓰는 작업이 API 서버에서 돌아 다른 요청의 응답 시간을 밀어낸다

After — 비동기 후처리 (수십 ms 응답)

완료 통보→CONFIRMED 전이→큐 적재→즉시 응답
↳워커가 꺼내서 처리→끝나면 READY 전이
  • 사용자는 즉시 "업로드 완료, 처리 중" 응답을 받는다
  • 처리 상태를 폴링하거나 SSE로 진행률을 받는다(14-websocket-sse-polling-selection.md)
  • 후처리 실패는 재시도 대상이지 업로드 실패가 아니다
  • CPU 무거운 작업이 API 서버와 분리되어 독립적으로 스케일된다
상태 필드가 이 설계의 뼈대다 CONFIRMED(실물은 있으나 처리 전)와 READY(처리 완료, 노출 가능)를 구분해 두면, 클라이언트는 그 상태를 보고 "처리 중" 표시를 하거나 원본을 임시로 보여줄 수 있다.
워커는 멱등해야 한다 큐는 대개 최소 1회 전달(at-least-once)을 보장하므로 같은 메시지를 두 번 받을 수 있다. 그때 썸네일을 두 번 만드는 것은 괜찮지만(결과가 같다) 카운터를 두 번 올리거나 알림을 두 번 보내는 것은 곤란하다. 9절 ①에서 콜백과 이벤트를 둘 다 거는 것과 같은 이유로, 이 멱등성은 선택이 아니라 전제다.

11. 분할 업로드와 재개 가산점

11-1. 왜 큰 파일을 조각으로 나누는가 — 이유 셋

① 끊겼을 때 처음부터 다시 하지 않기 위해 (가장 큰 이유)
아래 계산 참조. 잃는 것을 "지금까지 보낸 전부"에서 "조각 하나"로 줄인다.
② 병렬 전송으로 대역폭을 제대로 쓰기 위해
TCP 연결 하나의 처리량은 혼잡 윈도우와 왕복 시간에 묶여 있어(10-keepalive-connection-pool-time-wait.md) 회선 대역폭이 남아도 한 연결로는 다 못 채우는 경우가 많다. 조각 여러 개를 여러 연결로 동시에 보내면 그 상한을 넘어설 수 있다.
③ 단일 요청의 크기 상한을 넘기기 위해
S3 계열은 단일 PUT 상한이 5GB다. 그보다 큰 객체는 분할 업로드가 유일한 방법이다.

단일 PUT으로 5GB를 올리는 경우

전송률 20Mbps → 5GB × 8 ÷ 20Mbps = 40,000Mbit ÷ 20 = 2,000초 ≈ 33분

  • 32분째에 와이파이가 끊기면?
  • 32분 동안 보낸 4.8GB가 전부 무의미해진다. 처음부터 다시.
  • 모바일 환경에서 33분 동안 한 번도 안 끊길 확률이 얼마나 될까.

8MB 조각 640개로 나눈 경우

5GB ÷ 8MB = 640 조각

  • 32분째에 끊기면?
  • 이미 성공한 조각들은 스토리지에 남아 있다.
  • 재개할 때 "어느 조각이 이미 올라갔는지" 조회해서 안 올라간 것만 다시 보낸다.
  • 잃는 것은 전송 중이던 조각 하나(최대 8MB)뿐이다.

11-2. 조각 크기를 어떻게 정하는가 — 제약이 하한을 계산해 준다

S3 계열의 제약 두 개 암기

5MB
조각 최소 크기 (마지막 조각은 예외)
10,000
최대 조각 수
이 둘에서 하한이 계산으로 나온다 — 최소 조각 크기 = 전체 크기 ÷ 10,000
계산 100GB 파일의 조각 크기 정하기 — 검산까지
[제약] 조각 수가 10,000개를 넘으면 안 된다
       → 최소 조각 크기 = 전체 크기 ÷ 10,000

  파일 100GB의 경우:
    100GB = 102,400MB
    102,400MB ÷ 10,000 = 10.24MB   이 값보다 커야 한다

  검산:
    조각  8MB → 102,400 ÷ 8  = 12,800개 > 10,000  ✗ 한도 초과
    조각 16MB → 102,400 ÷ 16 =  6,400개 ≤ 10,000  ✓

조각을 작게 잡으면

  • ✓ 실패 시 다시 보낼 양이 적다
  • ✓ 병렬도를 높이기 쉽다
  • ✗ 요청 수가 많아진다 (왕복 비용 + API 호출 요금)
  • ✗ 조각 수 한도에 걸릴 수 있다

조각을 크게 잡으면

  • ✓ 요청 수가 적다
  • ✗ 실패 시 다시 보낼 양이 크다
  • ✗ 조각 하나를 메모리에 들고 있어야 하는 클라이언트라면 메모리 부담
실무 감각 — 수 MB~수십 MB 범위에서 고르고, "전체 크기 ÷ 10,000"보다 큰지 반드시 확인.
네트워크가 불안정한 환경일수록 작게, 안정적일수록 크게.

11-3. 미완성 업로드 정리 — 보이지 않는 요금이 나간다

분할 업로드는 새로운 종류의 고아를 만든다 함정 시작해놓고 완료 요청을 보내지 않으면 이미 올린 조각들이 스토리지에 남는다. 그런데 이 조각들은 객체 목록 조회에 나타나지 않는다 — 아직 객체가 아니라 "조립 대기 중인 부품"이기 때문이다. 그래서 보이지 않는 채로 스토리지 요금만 계속 나가는 상태가 된다. 대응은 "N일 이상 완료되지 않은 분할 업로드를 자동으로 폐기하라"는 수명주기 규칙이다(S3의 AbortIncompleteMultipartUpload). 대용량 업로드를 쓰는 버킷이라면 사실상 필수다.

12. 다운로드의 Range 요청과 응답 헤더

12-1. Range 요청 — 이어받기와 구간 탐색의 근거

Range 요청은 "파일 전체가 아니라 이 바이트 구간만 주세요"라고 요청하는 HTTP 기능이다.

요청 앞 1KB만 달라
GET /files/movie.mp4 HTTP/1.1
Host: cdn.example.com
Range: bytes=0-1023
응답 200이 아니라 206이라는 점이 중요하다
HTTP/1.1 206 Partial Content
Content-Range: bytes 0-1023/5242880
Content-Length: 1024
Accept-Ranges: bytes
Content-Type: video/mp4

Range 관련 코드·헤더 여섯 암기

Range: bytes=0-1023
요청 — "이 구간만"
206 Partial Content
응답 — "일부만 줬다" (200이 아니다)
Content-Range
bytes 시작-끝/전체 — 슬래시 뒤가 전체 크기
Accept-Ranges: bytes
서버의 지원 선언. 미지원이면 none
If-Range: <ETag>
이어받기 안전장치 — 바뀌었으면 200으로 전체
416
요청 범위가 파일 크기를 벗어남
이것이 서버 직접 서빙을 버릴 또 하나의 이유다 Range 요청을 직접 구현하려면 헤더 파싱, 여러 구간 요청 처리, If-Range 조건 판정, 경계 검사, 206/416 분기를 전부 만들어야 한다. 오브젝트 스토리지와 CDN은 이것을 기본으로 지원한다 — presigned GET URL로 넘기면 우리가 만들 것이 없다.

12-2. Content-Disposition — 파일명과 표시 방식

응답 헤더 Content-Disposition은 브라우저에게 "이 응답을 화면에 표시할지, 파일로 저장할지"와 "저장한다면 어떤 이름으로 할지"를 알려준다.

헤더 세 가지 형태
Content-Disposition: inline                              ← 브라우저에서 바로 표시 (이미지, PDF)
Content-Disposition: attachment                          ← 다운로드 (파일명은 브라우저가 추측)
Content-Disposition: attachment; filename="report.pdf"   ← 다운로드 + 파일명 지정
한글 파일명에서 함정이 나온다 함정 HTTP 헤더는 전통적으로 ASCII 범위를 전제하므로, filename="분기보고서.pdf"처럼 비ASCII 문자를 그냥 넣으면 브라우저마다 다르게 해석해 깨진 이름으로 저장되거나 무시된다.
표준 해법 filename* — 별표가 붙은 파라미터
Content-Disposition: attachment; filename="download.pdf"; filename*=UTF-8''%ED%95%9C%EA%B8%80.pdf
                                 └─────────┬─────────┘  └────────────┬────────────────────┘
                                 ASCII 폴백용              UTF-8 바이트를 퍼센트 인코딩

// 읽는 법: UTF-8'' 부분이 "인코딩은 UTF-8이고, 언어 지정은 생략"이라는 뜻이다.
//          (작은따옴표 두 개 사이가 언어 자리다)
//          %ED%95%9C%EA%B8%80.pdf 는 "한글.pdf" 다.
// 둘을 함께 주는 것이 정석 — filename*을 이해하는 브라우저는 그쪽을 쓰고,
//                          이해하지 못하는 오래된 클라이언트는 filename 으로 폴백한다.
before 한글 파일명이 깨지거나 무시된다
response.setHeader("Content-Disposition",
        "attachment; filename=\"" + originalName + "\"");

// 비ASCII 문자를 그대로 헤더에 넣었다.
// 브라우저마다 해석이 달라 결과를 예측할 수 없다.
after Spring이 규칙에 맞게 조립해 준다
ContentDisposition disposition = ContentDisposition.attachment()
        // 두 번째 인자로 문자셋을 주면 filename*= 형태를 함께 만들어 준다.
        .filename(originalName, StandardCharsets.UTF_8)
        .build();

return ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, disposition.toString())
        .contentLength(meta.size())
        .body(body);
presigned URL 방식이라면 이 헤더를 서명 시점에 지정한다 7절의 responseContentDisposition이 그것이다 — 스토리지가 응답에 이 헤더를 붙이게 만들어서, 저장 키는 UUID여도 사용자에게는 원본 파일명으로 저장되게 하는 방법이다.
압축은 다시 걸지 않는다 JPEG, PNG, MP4, ZIP처럼 이미 압축된 포맷에 gzip을 다시 거는 것은 낭비다. 압축률이 거의 0인데 CPU만 쓰고, 경우에 따라 크기가 오히려 늘어난다. 압축이 이득인 것은 텍스트 계열(JSON, HTML, CSS, JS)이다. 판단 기준은 21-response-compression-tradeoffs.md와 같다.

13. 인출 카드 · 꼬리질문 셀프 테스트

13-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

두 단계 원칙을 한 문장씩?
① 메모리 사용량이 파일 크기에 비례하지 않게(스트리밍) ② 파일이 앱 서버를 아예 거치지 않게(presigned URL / CDN signed URL).
getBytes()가 위험한 계산?
200MB × 50건 = 10,000MB ≈ 9.8GB. 힙 4GB면 20건째쯤 OOM. 그리고 터지는 것은 힙을 요청한 스레드 — 업로드와 무관한 결제 스레드가 죽는다.
Spring은 업로드 파일을 어디에 두나?
컨트롤러 실행 전에 이미 전부 수신해 Tomcat 임시 저장소에 둔다. file-size-threshold 기본 0B → 기본 동작은 "전부 디스크". 그래서 getBytes()는 디스크에 있는 걸 힙으로 한 번 더 복사하는 짓이다.
presigned URL 정의 한 문장?
스토리지가 "특정 객체 · 특정 동작 · 특정 시각까지만 허용"한다고 자기 비밀 키로 서명해 발급한 URL.
왜 인증을 대신할 수 있나?
질문을 바꿨다 — "누구인가"가 아니라 "이 요청이 허가된 것인가"만 묻는다. 서명 = "비밀 키를 가진 누군가가 명시적으로 허가했다"는 증거이고, 그 키는 우리 앱 서버만 갖고 있다.
presigned의 대가 다섯?
완·유·조·검·고 — 완료를 모른다 / URL이 유출된다 / 조건(크기·타입) 강제가 어렵다 / 검사 지점이 사라진다 / 고아가 양방향.
계층별 기본값 네 개?
Nginx client_max_body_size 1MB · client_body_timeout 60s · Spring max-file-size 1MB · max-request-size 10MB. 그리고 가장 작은 값이 실질 한도.
상태 전이 세 단계?
PENDING(의도만) → CONFIRMED(실물 확인) → READY(검증 완료, 이것만 노출). URL 발급 시점에 PENDING을 먼저 만든다는 것이 요점.
수명주기 규칙 세 개?
① 미완성 분할 업로드 폐기(7일) ② 격리 프리픽스 만료(1일) ③ 임시 프리픽스 만료(N일).
분할 업로드 제약과 하한 계산?
조각 최소 5MB, 최대 10,000개 → 최소 조각 크기 = 전체 ÷ 10,000. 100GB면 10.24MB 이상 → 16MB로 6,400개.
Range 관련 코드 셋?
206 Partial Content(성공) · 416(범위 벗어남) · Accept-Ranges: bytes(지원 선언). 안전장치는 If-Range.
"10MB부터 실패"에서 먼저 볼 것?
상태 코드로 가른다 — 413이면 크기(Spring max-request-size 기본 10MB가 유력), 408/504면 타임아웃, 500이면 앱 예외. 앱 로그가 비어 있으면 앱 설정은 볼 필요 없다.

13-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

presigned URL 방식의 단점이나 주의점은 없나요? 시니어 변별힌트: "전송 부담을 덜어내는 대신 제어와 정합성 관리라는 새 책임을 사는 거래"라는 프레임으로 시작한다
프레임 한 문장 — "전송 부담을 덜어내는 대신 제어와 정합성 관리라는 새 책임을 사는 거래"

① 앱이 업로드 완료를 모른다. 파일이 스토리지로 직접 가므로 앱은 그 일이 일어났는지조차 모른다. 클라이언트의 완료 콜백은 브라우저가 닫히거나 네트워크가 끊기면 오지 않고, 온다 해도 그 말을 그대로 믿을 수 없다. 그래서 스토리지에 HEAD로 실물을 직접 확인하거나, 스토리지 이벤트 통지를 받는다. 실무에서는 둘 다 걸고 — 콜백으로 사용자 응답을 빠르게 주고 이벤트를 최종 진실로 삼는다 — 그 처리를 멱등하게 만든다.

② 클라이언트가 URL을 남에게 넘길 수 있다. 서명 안에 "누가 쓸 수 있는지"는 들어 있지 않으므로 URL을 가진 누구나 쓸 수 있다. 방어는 짧은 만료(업로드는 몇 분), 동작과 키를 서명에 고정(업로드용 URL로 다른 파일을 덮어쓸 수 없게), Content-Type 같은 조건을 서명에 포함이다.

③ 크기·타입을 앱이 강제하기 어렵다. 단순 PUT 서명에서는 클라이언트가 신고한 크기와 실제 올리는 크기가 다를 수 있다. 대응은 두 방향 — 스토리지가 강제하게 하는 것(크기 범위 조건을 정책에 넣어 서명하는 POST 방식, 또는 Content-Length를 서명 대상 헤더에 포함)과 완료 시점의 사후 검증(HEAD로 실제 크기 확인, 초과면 객체 삭제 + 거부 상태). 타입은 헤더를 고정해도 내용까지 보장하지 못하므로 결국 후처리에서 매직 바이트로 판별해야 한다.

④ 바이러스 검사와 후처리 지점이 사라진다. 앱이 바이트를 못 보므로 저장 직전 검사가 불가능하다. 해법은 검증 시점을 업로드 후로 옮기고, 그 사이 노출되지 않게 막는 것 — 격리 영역(별도 프리픽스나 버킷)에 올리고, 업로드 이벤트로 검증 워커를 깨우고, 통과한 것만 서비스 영역으로 옮긴다. 상태 필드만으로 막지 않고 저장 위치를 물리적으로 나누는 것이 요점이다.

⑤ 고아 파일 — 양방향 정합성. DB와 스토리지는 다른 시스템이라 한 트랜잭션으로 묶을 수 없어 어긋남이 양방향으로 생긴다. "URL만 발급되고 안 올라간 경우"는 PENDING 레코드만 남고, "올라갔는데 완료 통보가 안 온 경우"는 참조 없는 객체가 남는다. 대응은 PENDING → CONFIRMED → READY 상태 전이(URL 발급 시점에 PENDING을 먼저 만든다)와 양방향 정리 루프다 — 오래된 PENDING을 찾아 스토리지에 실물이 있으면 되살리고 없으면 지우는 배치, 그리고 격리·임시 프리픽스에 건 수명주기 규칙. 분할 업로드를 쓴다면 미완성 업로드 자동 폐기 규칙도 필수다(조각들은 객체 목록에 안 보이는데 요금은 나간다).

이 다섯을 인지하고 도입하는지가 변별 포인트다. "presigned URL을 쓰면 됩니다"에서 멈추면 절반의 답이다.

그래도 서버 경유 업로드를 유지해야 하는 경우가 있을까요? 필수힌트: "기본값은 우회, 예외 조건이 있을 때만 경유"로 정리하되, 그 예외를 구체적으로 셋 말한다
기본값은 우회, 예외 조건이 있을 때만 경유

① 저장 전 동기 검증·변환이 필수인 경우. 업로드 즉시 파싱해서 결과를 응답에 담아야 하는 경우(정산 파일을 올리면 그 자리에서 항목 수와 합계를 보여줘야 하는 화면), 또는 검증 실패 시 즉시 반려해야 하는 문서 심사가 여기 해당한다. presigned 방식에서는 검증이 업로드 후 비동기가 되므로 "올렸는데 나중에 반려됐습니다"라는 UX가 되는데, 그것이 허용되지 않는 요구가 있다.

② 스토리지를 외부에 직접 노출할 수 없는 보안 요건. 폐쇄망, 또는 "모든 데이터 접근은 애플리케이션의 감사 로그를 거쳐야 한다"는 규정이 있는 환경이다. presigned URL은 스토리지 엔드포인트를 클라이언트에게 노출하는 것이므로 이 요건과 충돌한다.

③ 파일이 작고 빈도가 낮아 우회 설계의 복잡도가 이득을 넘는 경우. 프로필 이미지 수백 KB 수준이면 스트리밍 경유로 충분하다. presigned 방식은 API가 둘로 늘고(발급 + 완료), 상태 전이가 생기고, 정리 배치가 필요하다 — 작은 파일에 이 복잡도를 지불할 이유가 없다.

다만 반드시 덧붙일 것이 있다. 규모가 커지면 경유 방식이 서버 용량 계획을 지배하게 된다. 프로필 이미지도 사용자가 100만 명이 되고 이미지 조회가 초당 수천 건이 되면 이야기가 달라진다. "지금 규모에서는 경유가 맞지만, 어느 지점에서 우회로 전환할지"를 미리 정해두는 것이 설계 감각이다.

업로드가 10MB까지는 되는데 그 이상은 실패합니다. 어디를 보나요? 필수힌트: "크기 의존적 실패는 코드 버그보다 계층별 제한의 신호"로 시작하고, 상태 코드로 분기한다

크기 의존적 실패는 코드 버그보다 계층별 제한의 신호다. 코드는 파일 크기를 보고 분기하지 않지만, 인프라 설정은 정확히 크기로 자른다. 그래서 먼저 사용자가 받은 상태 코드를 확인한다 — 여기서 방향이 갈린다.

413이면 크기 제한이다. 바깥에서 안쪽으로 순서대로 본다 — CDN/LB의 본문 크기 한도 → Nginx client_max_body_size(기본 1MB라 가장 흔한 범인) → Spring max-file-size와 max-request-size(기본 1MB / 10MB). 10MB에서 걸린다면 max-request-size 기본값 10MB가 유력한 용의자다.

504나 커넥션 끊김이면 타임아웃이다. 전송 시간이 어느 계층의 상한을 넘은 것이다. Nginx client_body_timeout, LB의 유휴 타임아웃이 후보다. 이 경우 "느린 회선의 사용자만" 재현된다는 특징이 있다 — 같은 파일도 빠른 회선에서는 상한 안에 들어오기 때문이다. 제보자의 네트워크 환경을 물어보면 빠르게 좁혀진다.

500이면 앱 예외일 가능성이 있다. OOM(2절), 임시 디스크 부족(3절)이 후보다.

결정적 단서 — 앱 로그에 아무것도 없으면 요청이 앱에 도달하기 전에 반려된 것

그러면 앱 설정은 볼 필요가 없고 Nginx의 error log부터 봐야 한다 — client intended to send too large body 같은 문구가 바로 답을 준다(13-nginx-tomcat-timeout-buffer-mismatch.md 4절). 근본적으로는 파일 크기 요구사항이 바뀔 때 전 계층 한도를 함께 바꾸는 체크리스트가 있어야 재발을 막고, presigned URL 방식이라면 이 계층 스택을 아예 안 지나므로 문제 자체가 없어진다는 점까지 말하면 좋다.

다운로드 트래픽이 몰리면 어떻게 확장하나요? 필수힌트: "서버 증설이 아니라 경로 재설계"가 답이다. 왜 증설이 답이 아닌지부터 짚는다
서버 증설이 아니라 경로 재설계가 답이다

먼저 왜 서버 증설이 답이 아닌지 짚는다. 서버 직접 서빙은 같은 바이트를 두 번 나른다 — 스토리지 → 서버, 서버 → 클라이언트. 그래서 서버의 대역폭이 실질적으로 절반이 되고, 클라우드라면 전송 요금도 두 번 낸다. 여기에 전송 시간 내내 커넥션과 스레드가 묶인다(4절). 이 구조에서는 서버를 늘려도 대역폭이라는 물리적 한계에 같은 비율로 부딪힌다.

① 오브젝트 스토리지 + CDN으로 옮기고 서버는 signed URL 발급만 한다. 앱 서버가 처리하는 것은 수 KB짜리 JSON 요청이 되고, 파일 바이트는 CDN 엣지가 나른다.

② 이미지처럼 재사용률이 높은 불변 콘텐츠는 CDN 히트율이 대부분의 트래픽을 흡수한다. 여기서 중요한 것이 버전드 URL + 긴 캐시다 — 파일 내용이 바뀌면 URL도 바뀌게 만들면(경로에 해시나 버전을 넣는다) 같은 URL은 영원히 같은 내용이므로 캐시 만료를 아주 길게 잡아도 안전하다. 캐시 무효화라는 어려운 문제를 "무효화할 일이 없게" 설계로 없앤 것이다.

③ 비공개·유료 파일은 signed URL의 만료로 접근을 통제한다. CDN 위에서도 권한 판단은 여전히 우리 서버가 한다 — 서버가 권한을 확인하고 짧은 만료의 signed URL을 발급하며, 전송은 엣지가 한다.

④ Range 요청도 스토리지/CDN이 기본 지원하므로 이어받기와 구간 탐색이 자동으로 따라온다(12절).

정리하면 "다운로드 확장"의 답은 서버 증설이 아니라 경로 재설계이고, 그 원리는 "권한 판단은 서버가, 전송은 엣지가"다.

스트리밍 다운로드 구현에서 흔한 실수는? 함정힌트: 다섯 개다. 첫 번째가 가장 중요하고, 그것이 코드 구조를 정한다

① 응답이 시작된 뒤에는 에러 처리가 불가능하다. 스트림을 열어 흘리기 시작한 뒤 중간에 예외가 나면, 이미 200 OK와 바디 일부가 클라이언트에 나간 상태다. 이제 와서 404나 500으로 바꿀 방법이 없다. 클라이언트는 "성공했는데 파일이 잘린" 상태를 받는다. 대응은 전송을 시작하기 전에 존재·권한 검증을 전부 끝내는 것이다 — 2절 After 코드에서 getForDownload 호출이 바디 람다 바깥에 있는 이유가 정확히 이것이다.

② try-with-resources 누락으로 인한 핸들 누수. 전송 중 클라이언트가 끊으면 쓰기에서 예외가 나는데, 그때 저장소 스트림을 닫지 않으면 파일 핸들이나 HTTP 커넥션이 새어 나간다. 정상 종료 경로가 아니라 예외 경로에서 새기 때문에 평소에는 안 보이다가 부하 상황에서 드러난다.

③ 느린 클라이언트가 전송 내내 스레드를 점유한다. 블로킹 I/O에서는 전송 속도가 클라이언트 속도에 묶이므로 26분짜리 전송이 스레드를 26분 동안 잡는다(4절). StreamingResponseBody를 쓰면 요청 스레드는 놓아주지만 태스크 실행자의 스레드로 옮겨갈 뿐 사라지지 않는다. Nginx의 응답 버퍼링이 어느 정도 완충해 주지만(빠른 로컬 전송으로 WAS를 해방시키고 Nginx가 느린 클라이언트를 상대한다), 대용량 응답은 Nginx 버퍼를 넘겨 디스크 임시 파일로 스풀되므로 이번엔 Nginx의 디스크 I/O가 병목이 된다. 전송량이 많다면 결국 CDN/스토리지 직접 서빙으로 옮기는 것이 답이다.

④ Content-Length를 안 주면 진행률과 재개가 어려워진다. 크기를 모른 채 흘리면 청크 전송으로 나가고, 클라이언트는 전체 크기를 모르므로 진행률 퍼센트를 계산할 수 없다. 크기를 아는 경우에는 반드시 명시한다.

⑤ Range 요청을 무시한다. Range 헤더가 왔는데 그냥 200으로 전체를 내려주면 이어받기와 미디어 탐색이 동작하지 않는다. 직접 구현할 계획이 없다면 Accept-Ranges: none을 명시해 클라이언트가 헛되이 시도하지 않게 하고, 필요하다면 스토리지/CDN 직접 서빙으로 옮기는 것이 정직한 선택이다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

업로드 URL 만료가 5분인데, 전송에 10분이 걸리는 파일은 어떻게 하나요?힌트: "만료를 늘린다"는 답은 절반이다. 왜 늘리는 것만으로는 부족한지까지 말한다

먼저 만료의 의미를 정확히 해둔다. 만료는 URL이 유효한 창이지 전송에 허용된 시간이 아니다. 다만 "전송 도중에 만료 시각이 지나면 어떻게 되는가"는 제공자·구현에 따라 다를 수 있으므로, 대용량 업로드를 만료 경계에 아슬아슬하게 걸치도록 설계하지 않는 것이 원칙이다.

답은 세 갈래로 낸다.

① 만료를 파일 크기와 예상 회선 속도로 산정한다. "무조건 5분"이 아니라 신고된 size를 근거로 발급 시점에 계산한다. 다만 만료를 늘릴수록 유출 시 피해 창이 넓어지므로(9절 ②) 무한정 늘릴 수는 없다 — 여기가 트레이드오프다.

② 근본 해법은 분할 업로드다. 조각마다 짧은 만료의 URL을 쓰면 "긴 만료" 없이도 긴 전송을 감당할 수 있고, 만료된 조각은 URL만 다시 발급받아 그 조각만 재시도하면 된다. 만료 문제와 재개 문제가 같은 해법으로 풀리는 것이 분할 업로드의 숨은 이점이다.

③ 재발급 엔드포인트를 둔다. 클라이언트가 만료 임박을 감지하면 같은 fileId로 URL만 다시 받아가게 한다. 이때도 권한 검사는 다시 돈다 — 서명 발급이 곧 허가이므로, 재발급도 새로운 허가로 다뤄야 한다.

완료 콜백과 스토리지 이벤트를 둘 다 걸면, 같은 후처리가 두 번 돌지 않나요? 시니어 변별힌트: "그렇다. 그래서 멱등하게 만든다"에서 멈추지 말고 구체적으로 어디를 어떻게 잠그는지 말한다

그렇다. 두 번 온다는 것을 전제로 설계한다. 콜백과 이벤트는 둘 다 늦거나 둘 다 오거나 하나만 오는 세 경우가 전부 발생하고, 큐 자체도 대개 최소 1회 전달이라 재전달이 있다.

① 상태 전이를 조건부 갱신으로 만든다. UPDATE file_record SET status='CONFIRMED' WHERE id=? AND status='PENDING' 처럼 현재 상태를 WHERE에 넣으면, 두 번째 호출은 갱신 행 수 0으로 조용히 끝난다. "이미 CONFIRMED면 그대로 돌려준다"는 6절 코드의 첫 분기가 이것의 애플리케이션 레벨 표현이다.

② 큐 적재는 상태 전이에 성공한 쪽만 한다. 갱신 행 수가 1인 경로에서만 enqueue하면 후처리 작업 자체가 한 번만 생긴다.

③ 그래도 워커는 멱등해야 한다. 큐의 재전달은 애플리케이션이 막을 수 없기 때문이다. 기준은 "두 번 해도 결과가 같은가"다 — 썸네일을 두 번 만드는 것은 괜찮지만(덮어쓰면 같은 결과) 카운터 증가·알림 발송·과금은 곤란하다. 이런 작업은 처리 이력 테이블에 (fileId, step) 유니크 키를 두어 두 번째 시도를 튕겨낸다.

정리하면 "중복을 막는다"가 아니라 "중복이 와도 결과가 같게 만든다"가 답이다. 6장(메시징)의 at-least-once + 멱등 소비자 조합과 정확히 같은 이야기다.

URL 발급 시점에 PENDING 레코드를 먼저 만들면, 사용자가 취소만 해도 DB에 쓰레기가 쌓이는 것 아닌가요? 함정힌트: 맞다. 그런데 무엇과 무엇을 저울에 올린 결과인지를 말해야 답이 된다

맞다. 그리고 그것은 의도된 거래다. 두 가지 나쁜 상태 중 덜 나쁜 쪽을 고른 것이다.

PENDING을 먼저 만들면 (선택한 쪽)

  • 취소·이탈한 만큼 PENDING 레코드가 쌓인다
  • 그러나 이것은 발견 가능한 쓰레기다 — status='PENDING' AND created_at < … 한 줄로 전부 찾아낼 수 있다
  • 배치가 스토리지에 실물이 있는지 물어보고 되살리거나 지운다

서명 발급 후에 만들면 (피한 쪽)

  • 업로드는 성공했는데 DB에 흔적이 전혀 없는 객체가 생긴다
  • 이것은 발견 불가능한 유실이다 — 어느 객체가 고아인지 알려면 스토리지 전체 목록과 DB 전체를 대사해야 한다
  • 그동안 보이지 않게 요금이 나간다
발견 가능한 쓰레기가 발견 불가능한 유실보다 훨씬 낫다

비용도 실제로는 크지 않다. PENDING 레코드 한 건은 수백 바이트고, 정리 배치가 24시간 뒤에 걷어간다(URL 만료 5분보다 넉넉히 기다리는 이유는 느린 회선의 사용자가 아직 올리고 있는 중일 수 있기 때문이다). 반대로 고아 객체는 원본 파일 크기 그대로가 계속 쌓인다.

다운로드 URL을 매번 새로 서명해서 발급하면, URL이 계속 달라져 CDN 캐시 히트율이 떨어지지 않나요? 시니어 변별힌트: 캐시 키가 무엇으로 만들어지는지를 떠올린다

기본 동작대로면 떨어진다. 서명 파라미터가 쿼리스트링에 들어가는데, 캐시 키에 쿼리스트링이 포함되면 서명이 바뀔 때마다 다른 객체로 취급되어 매번 원본까지 다녀오게 된다.

대응은 콘텐츠의 성격에 따라 갈린다.

① 공개 콘텐츠는 애초에 서명하지 않는다. 웹툰 이미지처럼 누구나 볼 수 있는 것이라면 버전드 URL(경로에 해시·버전) + 긴 캐시가 정답이다. 권한이 필요 없으면 서명도 필요 없다는 당연한 결론을 놓치기 쉽다.

② 서명이 필요하면 캐시 키에서 서명 파라미터를 제외하도록 구성한다. CDN에는 캐시 키에 포함할 쿼리 파라미터를 지정하는 설정이 있으므로, 서명 관련 파라미터를 캐시 키에서 빼면 같은 객체는 하나의 캐시 엔트리를 공유한다. 서명 검증은 엣지가 여전히 수행하되, 캐시 조회 키만 분리하는 것이다.

③ 또는 CDN 자체의 접근 제어 기능을 쓴다. URL 서명 대신 서명된 쿠키를 쓰면 URL은 그대로 두고 접근만 통제할 수 있어, 같은 사용자가 여러 파일을 연달아 받는 경우(웹툰 한 화의 이미지 수십 장)에 특히 유리하다.

판단 기준 한 줄 — "이 파일이 여러 사람에게 반복 전달되는가". 그렇다면 캐시 공유가 최우선이고 서명은 캐시 키 밖으로 빼야 한다. 한 사람만 한 번 받는 파일(정산 보고서 다운로드)이라면 애초에 캐시 히트율을 걱정할 일이 없다.

서버 경유를 유지해야 한다면, getBytes() 대신 transferTo()는 어떤가요? 가산점힌트: 힙은 안 쓴다. 그런데 다른 전제가 하나 붙는다

힙 관점에서는 좋은 선택이다. MultipartFile.transferTo(File)는 이미 디스크에 있는 임시 파일을 목적지로 옮기는 것이라 파일 내용을 힙에 올리지 않는다. 같은 파일 시스템 안이라면 이름만 바꾸는(rename) 수준으로 끝날 수도 있어 복사보다도 싸다.

그러나 전제가 하나 붙는다 — 목적지가 "서버 로컬 디스크"라는 것. 여기서 두 가지가 따라온다.

① 인스턴스가 여러 대면 로컬 디스크는 답이 아니다. A 서버에 저장한 파일을 B 서버가 서빙할 수 없으므로, 공유 스토리지(NFS·오브젝트 스토리지)로 다시 옮기는 단계가 필요해진다. 그러면 결국 스트림으로 스토리지에 올리는 코드가 있어야 한다.

② 컨테이너 환경에서 로컬 디스크는 휘발성이다. 파드가 재시작되면 사라진다. "업로드는 성공했는데 파일이 없다"는 사고가 배포 때마다 재현된다.

정리하면 — 단일 서버 + 로컬 저장이 요구사항이면 transferTo()가 가장 깔끔하고, 오브젝트 스토리지로 보낼 것이라면 getInputStream() + 스트리밍이 맞다. 어느 쪽이든 getBytes()는 선택지가 아니다.

서버 경유 업로드에서 클라이언트가 신고한 크기를 믿을 수 없다면, 스트리밍 중에 크기 상한을 어떻게 거나요?힌트: 다 받은 뒤에 재는 것은 이미 늦었다

Content-Length 헤더는 참고값이다. 클라이언트가 거짓을 보낼 수도 있고, 청크 전송이면 아예 없을 수도 있다. 다 받은 뒤에 크기를 재는 것은 "이미 그만큼의 디스크·대역폭을 쓴 뒤"라 방어가 아니다.

① 프레임워크 레벨 상한을 먼저 건다. spring.servlet.multipart.max-file-size와 max-request-size는 파싱 중에 걸리므로, 초과 시 끝까지 다 받지 않고 중단된다. 그 앞의 client_max_body_size는 Tomcat에 오기도 전에 자른다 — 바깥일수록 싸게 막는다는 원칙 그대로다.

② 직접 스트리밍한다면 읽은 바이트를 세면서 흘린다. 카운팅 스트림으로 감싸 누적 바이트가 상한을 넘는 순간 예외를 던지고 연결을 끊는다. 이미 저장소에 부분 전송을 시작했다면 그 부분 객체를 지우는 정리까지 같이 해야 한다.

③ presigned 방식이라면 같은 문제가 다른 이름으로 나타난다 — 9절 ③이다. 스토리지가 강제하게 하거나(크기 범위 조건을 정책에 넣어 서명), HEAD로 사후 검증하고 초과분을 삭제한다. 어느 설계든 "클라이언트가 말한 크기"를 최종 근거로 삼지 않는다는 점이 공통이다.

presigned 방식으로 바꾸면 감사 로그와 접근 통계는 어떻게 남기나요?힌트: 앱이 못 보게 된 것을 누가 대신 보는지 생각한다

앱 서버 로그만 보던 시절의 지표가 사라진다는 점을 먼저 인정해야 한다. 실제 다운로드는 스토리지/엣지에서 일어나므로, 앱 로그에는 "URL을 발급했다"까지만 남는다.

① 발급 로그는 여전히 앱이 남긴다. 누가 · 어떤 파일에 대해 · 어떤 동작의 URL을 · 언제 · 몇 분짜리로 받아 갔는지는 권한 판단이 일어난 지점이라 감사 관점에서 가장 중요한 기록이다. "허가한 순간"이 곧 감사 대상이라는 관점으로 보면, 오히려 기록의 초점이 선명해진다.

② 실제 전송 기록은 스토리지·CDN의 액세스 로그를 쓴다. 오브젝트 스토리지와 CDN은 객체 단위 액세스 로그를 남길 수 있고, 이것을 수집하면 실제 다운로드 건수·바이트·엣지 히트율을 볼 수 있다. 발급 로그와 액세스 로그를 객체 키로 조인하면 "발급했지만 실제로 받아 가지 않은 비율"까지 나온다.

③ "모든 접근이 애플리케이션 감사 로그를 거쳐야 한다"는 규정이 있다면 — 그것은 presigned를 쓰지 말아야 할 조건이다(앞의 꼬리질문 ②). 기술적으로 우회하려 하지 말고 요건과 설계가 충돌한다는 사실을 그대로 말하는 것이 옳은 답이다.

한 줄 요약
대용량 파일 설계의 요체는 "경로"다 — 서버를 지나야 한다면 메모리 사용이 파일 크기에 비례하지 않게 스트리밍하고(그리고 Spring은 임계값 초과분을 디스크 임시 파일로 이미 내려두었다는 사실까지 알고 그 볼륨을 관리하고), 가능하다면 presigned URL로 파일 바이트가 애플리케이션 서버를 아예 우회하게 만들어 서버는 권한 검증·URL 발급·메타데이터 확정이라는 제어만 맡는다 — 그 대가로 완료 확인(스토리지 이벤트 또는 HEAD 검증), URL 유출 방어(짧은 만료 + 조건 서명), 검증·후처리의 비동기 파이프라인화, PENDING → CONFIRMED → READY 상태 전이와 양방향 고아 정리라는 새 책임을 지며, 여기에 계층별 크기·타임아웃 정합, Range 요청 기반 이어받기·구간 탐색, 분할 업로드와 미완성 업로드 정리까지 갖추면 전송량이 늘어도 서버 용량 계획이 흔들리지 않는 구조가 된다.
