프록시 뒤 실제 클라이언트 IP
X-Forwarded-For는 프록시의 전유물이 아니라 "폼 입력과 똑같은" 사용자 입력이다

면접 질문: "프록시/LB 뒤에서 실제 클라이언트 IP는 어떻게 얻나요? X-Forwarded-For를 그대로 믿으면 안 되는 이유는?"

핵심 관전 포인트 — 프록시 뒤에서는 소켓의 상대 주소(getRemoteAddr())가 프록시 IP이므로 실제 클라이언트 IP는 프록시가 붙여주는 X-Forwarded-For로 전달받는다. 문제는 이것이 프록시만 붙일 수 있는 특별한 헤더가 아니라 클라이언트가 처음부터 아무 값이나 넣어 보낼 수 있는 평범한 HTTP 헤더라는 점이다. 프록시는 들어온 값을 검증하지 않고 자기가 관측한 주소를 뒤에 덧붙일 뿐이므로, 체인의 왼쪽 값들은 전부 공격자가 심어둔 것일 수 있다. 그래서 흔히 보이는 split(",")[0]은 rate limit·IP 차단·관리자 allowlist·감사 로그를 헤더 한 줄로 통째로 우회시킨다. 올바른 해석은 방향이 반대다 — 오른쪽일수록 우리 인프라에 가까운 프록시가 소켓에서 직접 관측해 적은 값이라 위조가 불가능하므로, 오른쪽 끝에서 시작해 "내가 신뢰하는 프록시 목록"에 있는 IP인 동안 계속 걷어내고, 처음 만나는 신뢰 목록 밖의 값을 클라이언트 IP로 삼는다(Nginx real_ip_recursive, Tomcat RemoteIpValve가 이 알고리즘의 구현체다). 이 신뢰 모델 전체는 앱에 프록시를 우회해 직접 도달할 경로가 없다는 인프라 전제 위에서만 성립하므로, 보안 그룹으로 앱 포트를 LB에서만 열어두는 것까지가 설계의 일부다. 마지막으로 IP를 정확히 얻는 것과 IP를 얼마나 믿고 결정에 쓸 것인가는 별개의 문제다 — NAT 뒤에서는 수천 명이 한 IP를 공유하고 IPv6에서는 한 사용자가 방대한 주소를 쓰므로, IP는 단독 키가 아니라 계정·기기 지문과 조합하는 보조 신호다.
  • 1
    믿을 수 있는 값은 소켓 주소 하나뿐인데, 그 값이 프록시를 가리킨다 — TCP 3-way handshake 때문에 출발지 IP를 위조하면 연결 자체가 성립하지 않으므로, "HTTP 요청이 도착했다"는 사실 자체가 소켓 주소가 진짜라는 증거다. 문제는 프록시 뒤에서 그 값이 언제나 마지막 홉이라는 것이고, 그래서 X-Forwarded-For라는 헤더 관례가 필요해졌다.
  • 2
    XFF는 신뢰 경계 밖에서 온 값이다 — 헤더는 누구나 만들어 보낼 수 있고 프록시는 검사 없이 append만 한다. 그래서 공격자가 심은 값이 체인 왼쪽에 그대로 살아남고, split(",")[0]은 공격자가 정한 값을 읽는다. 뚫리는 것은 넷 — 제·차·허·로(rate 제한 · IP 차단 · 관리자 허용목록 · 감사 로그).
  • 3
    그래서 해석은 오른쪽에서 왼쪽으로 걸어 나간다 — 정·잇·걷·멈: 신뢰 프록시 목록을 정의하고, 위조 불가능한 소켓 주소를 체인 맨 오른쪽에 잇고, 신뢰 목록에 있는 동안 걷어내고, 처음 만나는 바깥 값에서 멈춘다. 직접 짜지 말고 Nginx realip / Tomcat RemoteIpValve로 한 곳에 일원화하고, 네트워크 차단으로 우회로를 없애는 것까지가 이 설계다.

0. 질문 + 출제 의도

질문: "프록시/LB 뒤에서 실제 클라이언트 IP는 어떻게 얻나요? X-Forwarded-For를 그대로 믿으면 안 되는 이유는?"

출제 의도: 스푸핑 가능한 헤더를 그대로 믿으면 rate limit·차단·감사 로그가 전부 우회된다. "신뢰 경계 밖에서 온 값"이라는 보안 감각을 폼 입력뿐 아니라 네트워크 헤더에도 적용하는지를 본다 — IP 기반 기능을 하나라도 만들어본 백엔드라면 반드시 부딪히는 문제다.

이 페이지가 겨냥하는 약점 네 가지 ① "프록시가 붙이는 헤더니까 프록시만 붙일 수 있겠지" → 3절에서 공격자가 심은 값이 우리 인프라를 통과하며 그대로 살아남는 경로를 한 장으로 추적한다.
② "왼쪽이 원래 클라이언트 아닌가요?" → 2·5절에서 왜 방향이 반대인지를 "누가 소켓에서 직접 관측했는가"로 논증하고, 왼쪽부터 걷는 구현이 어떻게 조작당하는지 반례를 든다.
③ 신뢰 경계를 "몇 홉"으로 대충 잡는 것 → 6절에서 신뢰 목록 방식과 신뢰 홉 수 방식을 갈라, 홉 수 고정이 경로가 둘인 순간 위조값을 고르는 구체적 시나리오를 계산한다.
④ "정확한 IP를 얻었으니 차단하면 끝" → 11절에서 IP를 얻는 문제와 IP를 결정에 쓰는 문제를 분리하고, NAT 공유·IPv6 프리픽스라는 식별자 자체의 한계를 다룬다.

1. 기준점 — 소켓 주소만 위조 불가다

이 주제의 모든 판단은 한 문장 위에 서 있다. 소켓 주소는 믿을 수 있고, 헤더는 못 믿는다. 그런데 이 문장을 외우기만 하면 뒤의 논리가 흔들린다 — 왜 소켓 주소는 못 믿을 이유가 없는지부터 짚어야 "그럼 헤더는 왜 다른가"를 스스로 설명할 수 있다.

한 줄 비유 — 자기 신고서 vs CCTV 건물 로비에서 방문자의 출처를 아는 방법은 둘이다. 방문자가 방명록에 적어 낸 "어디서 왔는지"(자기 신고)와, 경비가 CCTV로 직접 본 "어느 문으로 들어왔는지"(직접 관측)다. XFF는 방명록이고 소켓 주소는 CCTV다. 방명록에는 아무 말이나 적을 수 있지만, CCTV 화면은 방문자가 고칠 수 없다. 이 문서의 알고리즘은 결국 "방명록에서 우리 경비가 CCTV로 확인해 적은 줄까지만 인정하고, 그 앞줄은 버린다"는 이야기다.

1-1. 출발지 IP를 위조하면 연결 자체가 성립하지 않는다

서버가 클라이언트 IP를 아는 가장 원초적인 방법은 TCP 소켓의 상대 주소다(서블릿의 request.getRemoteAddr()). 커널이 연결을 관리하며 들고 있는 값이고, 사실상 위조가 불가능하다. 이유는 TCP의 3-way handshake에 있다.

1-2. 그런데 프록시가 끼면 그 값이 프록시를 가리킨다

클라이언트 1.2.3.4→ LB 10.0.0.5→ Nginx 10.0.0.7→ Tomcat 10.0.0.9

Tomcat과 TCP 연결을 맺은 상대는 클라이언트가 아니라 Nginx다. 그러니 getRemoteAddr()는 언제나 마지막 홉의 IP(10.0.0.7)를 돌려준다. 모든 사용자의 "클라이언트 IP"가 내부 프록시 주소 하나로 찍히는 것이다. 접근 로그가 전부 같은 값이라 사고 조사가 불가능해지고, IP 기반 rate limit은 모든 트래픽이 키 하나에 몰려 임계값을 넘으며, 그 키를 차단하는 순간 전면 장애가 된다.

17번 문서와의 관계 "LB에서 TLS를 종료하면 앱이 IP·스킴·인증서를 잃는다"는 이야기는 17-tls-termination-lb-vs-app에서 다뤘다. 이 문서는 그중 IP 하나를 골라 "그래서 헤더를 어떻게 파싱하고, 어디까지를 신뢰 경계로 그을 것이며, 얻은 IP를 어떤 결정에 쓸 것인가"로 파고든다.

2. XFF 문법 — 각 프록시가 "자기가 본 것"을 덧붙인다

X-Forwarded-For(줄여서 XFF)는 표준 규격이 아니라 관례에서 출발한 헤더다. 이름 앞의 X-가 그 흔적이다(비표준 확장 헤더에 붙이던 접두어). 그래서 동작 규칙도 "각 프록시가 이렇게 하기로 한다"는 합의에 가깝고, 규칙은 하나뿐이다.

각 프록시는 "나에게 이 요청을 보낸 상대의 소켓 주소"를 기존 값 뒤에 쉼표로 덧붙인다(append)

한 문장으로 외우는 방향 규칙

오른쪽은 관측, 왼쪽은 전언(傳言) — 그러니 오른쪽 끝에서 출발한다

그리고 XFF만으로는 체인이 미완성이라는 점도 함께 외운다. 마지막 홉은 자기가 본 것을 적어 보냈지 자기 자신을 적지 않았다. 그래서 소켓 주소를 맨 오른쪽에 이어 붙여야 경로가 완성된다(5절 2단계).

Nginx헤더를 뒤 계층으로 넘기는 설정 — append와 set의 차이
location /api/ {
    proxy_pass http://tomcat_upstream;

    # $proxy_add_x_forwarded_for = (들어온 XFF 값) + ", " + (내가 관측한 소켓 주소)
    # 즉 append 다. 들어온 값의 진위는 검사하지 않는다 — 이것이 3절의 출발점이다.
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    # $remote_addr = 내가 소켓에서 관측한 상대 주소 하나만 (set = 덮어쓰기)
    proxy_set_header X-Real-IP       $remote_addr;
}

2-1. 비슷한 헤더 셋 — 이름이 달라도 성질은 같다

같은 목적의 헤더 세 가지. 고를 때의 기준은 "체인이 필요한가"와 "우리 인프라가 실제로 무엇을 붙이는가"이지, 표준 여부가 아니다.
헤더형태동작장점주의점
X-Forwarded-For 쉼표로 이어진 체인 각 프록시가 append 경로 전체가 남아 몇 단을 거쳤는지 검증 가능 — 신뢰 목록 방식의 전제 왼쪽이 위조 가능. 파싱 규칙을 정확히 알아야 쓸 수 있다
X-Real-IP 단일 값 보통 $remote_addr로 덮어쓰기(set) 파싱이 단순하다 경로를 알 수 없다. 덮어쓰기가 곧 안전은 아니다 — 중간 프록시가 클라이언트가 보낸 값을 그대로 통과시키면 위조값이 흘러 들어온다
Forwarded for=·by=·proto=·host=를 한 항목에 묶은 체인 RFC 7239로 표준화 여러 정보를 한 헤더에. IPv6도 for="[2001:db8::1]:4711"처럼 정확히 표현 XFF가 자리 잡은 뒤에 나와 보급률이 낮다. 스프링 ForwardedHeaderFilter는 둘 다 해석하며 둘 다 있으면 Forwarded를 우선
셋을 관통하는 한 문장 이름이 무엇이든 성질은 같다. 셋 다 HTTP 헤더이고, HTTP 헤더는 누구나 만들어 보낼 수 있다. "표준 헤더라서 더 안전하다"거나 "덮어쓰기 방식이라 안전하다"는 것은 없다 — 안전성은 헤더의 이름이나 문법이 아니라 "우리 장비가 소켓에서 관측해 적었는가"에서만 나온다.

3. 헤더는 사용자 입력이다 — 주입값이 살아남는 경로

XFF를 처음 배울 때 만드는 잘못된 그림은 이것이다. "프록시가 붙여주는 헤더니까 프록시만 붙일 수 있겠지." 아니다. HTTP 헤더는 요청을 만드는 쪽이 아무 이름과 값으로나 붙일 수 있고, X-Forwarded-For도 예외가 아니다.

공격도구도 필요 없다 — 옵션 하나다
# 공격자가 처음부터 XFF를 넣어 보낸다.
curl -H "X-Forwarded-For: 10.0.0.1" https://api.example.com/admin/users

그러면 우리 인프라를 지나면서 무슨 일이 벌어지는가. 프록시는 들어온 값의 진위를 검사하지 않는다. 2절에서 본 대로 $proxy_add_x_forwarded_for는 들어온 값 뒤에 자기가 본 주소를 덧붙일 뿐이다.

코드베이스에서 이 한 줄을 찾으면 그것이 취약점이다

String clientIp = request.getHeader("X-Forwarded-For").split(",")[0].trim();
// 가장 왼쪽 값 = 공격자가 마음대로 정할 수 있는 값
XFF는 폼 입력과 똑같은 "신뢰 경계 밖에서 온 값"이다

폼 입력을 검증 없이 SQL에 넣지 않듯, XFF를 검증 없이 보안 로직에 넣으면 안 된다. 차이가 있다면 SQL 인젝션은 값이 이상하게 생겨서 눈에 띄지만, IP 위조는 값이 완벽하게 정상으로 생겼다는 것이다. 정규식으로 "IP 형식인가"를 검사해 봐야 소용없다.

4. 무엇이 뚫리는가 — 제·차·허·로

"위조 가능하다"는 말만으로는 위험이 잘 와닿지 않는다. IP를 쓰는 대표 기능 네 가지에서 각각 어떻게 무너지는지 보면, 면접에서 "그래서 무슨 일이 나는데요?"에 구체적으로 답할 수 있다.

XFF 왼쪽 값을 쓰면 뚫리는 것 4종 — 제 · 차 · 허 · 로

제 — rate 제한
요청마다 헤더만 바꾸면 매번 새 키. 제한이 존재하지 않는 것과 같다.
차 — IP 차단
차단 목록에 없는 값을 적으면 통과. 목록이 무의미해진다.
허 — 관리자 허용목록
사내 대역을 위조해 인터넷 어디서나 관리자 페이지 진입. 최악.
로 — 감사 로그
공격 요청이 엉뚱한 IP로 기록. 사고 조사가 원천 불가능.

4-1. ① rate limiting 우회 — "무제한 시도"가 정상처럼 보인다

로그인 API에 "IP당 분당 5회"를 걸었다고 하자. 목적은 크리덴셜 스터핑(어디선가 유출된 아이디·비밀번호 목록을 대입해 보는 공격) 방어다.

의도한 동작

  • 공격자 IP 5.6.7.8 → 5회 시도 후 429 Too Many Requests
  • 키가 하나로 고정되므로 카운터가 쌓인다

XFF 왼쪽 값을 키로 썼을 때

  • 요청 1 — XFF: 1.1.1.1 → 키 1.1.1.1 카운트 1
  • 요청 2 — XFF: 1.1.1.2 → 키 1.1.1.2 카운트 1
  • 요청 3 — XFF: 1.1.1.3 → 키 1.1.1.3 카운트 1
  • 초당 수백 번 대입해도 걸리지 않는다
더 나쁜 것 — 이 상태가 "정상"으로 보인다 대시보드에는 "IP별 요청 수가 고르게 분포"로 찍히고, rate limiter는 매일 정상 동작 중이라고 보고한다. 뚫렸다는 사실을 알아챌 신호 자체가 없다. 그래서 이 취약점은 지표로 발견되지 않고 코드를 읽어야만 발견된다.

4-2. ② IP 차단 우회 — 차단 목록이 무의미해진다

부정행위가 확인된 IP를 차단 목록에 넣어 뒀다고 하자. 공격자는 XFF에 아무 IP나 적어 넣으면 그만이다 — 차단 목록에 없는 값을 적으면 통과한다. 차단은 "공격자가 스스로 자기 신분증을 제출한다"는 전제 위에서만 동작하는데, 그 신분증을 공격자가 직접 쓰고 있는 것이다.

4-3. ③ 관리자 allowlist 우회 — 네트워크 경계가 헤더 한 줄로 무너진다

가장 위험한 시나리오다. 관리자 페이지에 "사내 IP 대역(10.0.0.0/8)에서만 접근 허용"을 걸어 둔 경우를 보자.

공격한 줄이면 된다
curl -H "X-Forwarded-For: 10.0.0.42" \
     https://api.example.com/admin
앱의 판정형식이 멀쩡하니 통과한다
XFF[0] == "10.0.0.42" → 사내 IP다 → 통과
// 인터넷 어디서나 관리자 페이지에 들어올 수 있다
피해가 커지는 조건 IP allowlist를 "그래도 한 겹의 방어"로 믿고 다른 인증을 느슨하게 뒀다면(관리자 계정 비밀번호가 약하다, 2차 인증이 없다) 피해가 곱해진다. IP 제한은 인증·인가 위에 얹는 추가 계층이지 그 자리를 대신하는 것이 아니다 — 9절에서 다시 짚는다.

4-4. ④ 감사 로그 오염 — 그 시점의 진실을 영구히 잃는다

앞의 셋과 성격이 다른 피해다. 즉시 드러나지 않고 사고가 난 뒤에야 발견된다. 침해 사고가 나서 로그를 뒤지는 상황을 상상해 보자. 공격자가 모든 요청에 X-Forwarded-For: 8.8.8.8을 넣어 보냈다면, 접근 로그에는 공격 요청이 전부 8.8.8.8에서 온 것으로 남아 있다.

추적 불가
진짜 출발지가 어디에도 기록되지 않았다. 나중에 복원할 방법이 없다.
오지목
추적이 안 되는 정도가 아니라 엉뚱한 IP를 범인으로 지목하게 된다.
2차 피해
그 IP가 실재하는 다른 조직의 것이라면 잘못된 신고와 차단으로 피해가 번진다.
로그는 사후에 고칠 수 없다 — 로그에 남길 IP를 잘못 고르는 것은 그 시점의 진실을 영구히 잃는 결정이다
그래서 로그에는 세 가지를 함께 남긴다 가산점 ①해석된 클라이언트 IP(결정에 쓴 값), ②소켓 주소(위조 불가능한 값 — Nginx라면 $realip_remote_addr), ③XFF 원본 문자열(도착한 그대로). 셋을 함께 남기면 나중에 "그때 판단이 옳았는가"를 재검토할 수 있고, 신뢰 목록 설정이 잘못됐을 때 과거 로그로 소급 재계산할 수도 있다. 하나만 남기면 그 하나가 틀렸을 때 되돌릴 방법이 없다.

5. rightmost 알고리즘 — 정 · 잇 · 걷 · 멈

원리는 두 문장이다. 소켓 주소는 위조 불가다. 그리고 XFF의 각 항목은 "그것을 붙인 프록시가 자기 소켓에서 관측한 주소"다. 따라서 내가 아는 프록시들이 붙인 항목까지는 신뢰할 수 있고, 그 앞부터는 신뢰할 수 없다. 구현은 네 단계다.

정
신뢰하는 프록시 목록을 정의한다. 내 LB의 IP 대역, 내 Nginx의 대역, 계약된 CDN의 엣지 대역이 들어간다. 설정으로 관리하고 코드에 흩어놓지 않는다 — 이 목록이 곧 신뢰 경계이므로, 어디에 적혀 있는지 아무도 모르는 순간 경계가 사라진 것과 같다.
잇
XFF 값 뒤에 소켓 주소를 이어 붙여 완전한 체인을 만든다. XFF에는 마지막 홉이 관측한 주소가 없다 — 마지막 홉은 자기가 본 것을 적어 보냈지 자기 자신을 적지 않았다. 이 한 단계를 빠뜨리면 바로 앞 프록시가 클라이언트로 판정된다.
걷
오른쪽 끝에서 왼쪽으로 걸으며, 신뢰 목록에 있는 IP인 동안 계속 걷어낸다. 우리 장비가 적은 값들을 하나씩 벗겨내는 과정이다.
멈
처음 만나는 "신뢰 목록에 없는 값"이 실제 클라이언트 IP다. 그보다 왼쪽은 전부 버린다 — 누가 적었는지 보증할 수 없기 때문이다.

면접에서 이 한 문장으로 답한다

위조 불가능한 소켓 주소에서 출발해, 신뢰 프록시를 오른쪽부터 걷어내고, 처음 만나는 바깥 값을 클라이언트로 삼는다

그리고 "왜 오른쪽부터인가"를 덧붙이는 것이 답변의 완성이다 — 오른쪽 항목일수록 우리 인프라에 가까운 장비가 자기 소켓에서 직접 관측해 적은 값이기 때문이다.

6. 신뢰 경계를 어떻게 그을까 — 신뢰 목록 vs 신뢰 홉 수 시니어 변별

5절의 알고리즘에는 "신뢰 목록"이라는 입력이 필요하다. 그런데 현실에서는 이 목록을 채우기 어려운 경우가 있다 — 관리형 플랫폼이라 앞단 프록시의 IP를 알 수 없거나, CDN 대역이 수시로 바뀌거나, 오토스케일링으로 프록시 IP가 계속 변한다. 그래서 대안으로 등장하는 것이 "신뢰 홉 수" 방식이다. "체인 오른쪽에서 N개를 걷어내고 그 다음 값을 쓴다"로, 목록 없이 숫자 하나로 경계를 긋는다.

신뢰 목록 (trusted proxies) — 원칙

  • 기준은 "이 값을 누가 적었나" — 값 자체를 대조한다
  • 프록시 단수가 요청마다 달라도 스스로 맞춰진다
  • 목록을 최신으로 유지하는 운영 부담이 생긴다(특히 CDN)
  • 구현체: Nginx set_real_ip_from, Tomcat internalProxies/trustedProxies

신뢰 홉 수 (trust hop count) — 차선

  • 기준은 "오른쪽에서 몇 번째" — 위치만 센다
  • 목록 관리가 필요 없다. 앞단 IP를 몰라도 쓸 수 있다
  • 실제 홉 수가 설정보다 적어지는 순간 위조값을 고른다
  • 일부 프레임워크가 숫자 설정을 제공한다(예: Express의 trust proxy에 숫자를 주는 형태)

신뢰 경계를 정할 때 던져야 할 질문 셋

① 앱에 도달하는 경로가 몇 개인가?
둘 이상이면 홉 수 고정은 탈락이다. 헬스체크·내부 호출·CDN 미경유 경로를 빠짐없이 센다.
② 목록에 넣을 대역을 자동으로 갱신할 수 있나?
CDN 엣지 대역은 바뀐다. 사업자의 IP 목록을 주기적으로 받아 반영하는 자동화가 없으면 언젠가 조용히 어긋난다.
③ 최전선에서 XFF를 재시작할 수 있나?
최전선 프록시에서 proxy_set_header X-Forwarded-For $remote_addr;로 덮어쓰면 체인이 항상 우리 관측값에서 시작해 해석이 극적으로 단순해진다(10절 전제 필요).

7. 코드 — before/after와 파싱 함정

아래 코드는 원리를 이해하기 위한 것이고, 실무에서는 8절의 표준 구현을 쓰는 것이 정답이다. 그래도 한 번은 손으로 그려봐야 "프레임워크가 대신 해주는 일이 정확히 무엇인지"를 말할 수 있다.

Before가장 왼쪽 값 — 4절의 모든 우회에 뚫린다
public String clientIpBefore(HttpServletRequest request) {
    String xff = request.getHeader("X-Forwarded-For");
    if (xff != null && !xff.isBlank()) {
        return xff.split(",")[0].trim();  // 공격자가 정한 값
    }
    return request.getRemoteAddr();
}

// 문제 1. 방향이 반대다 — 왼쪽은 "전언"이다.
// 문제 2. getHeader 는 같은 이름 헤더 중 첫 번째만 읽는다.
// 문제 3. 신뢰 목록이라는 개념 자체가 없다.
After소켓 주소에서 출발해 신뢰 프록시를 걷어낸다
public String clientIpAfter(HttpServletRequest request) {
    // [정] 신뢰 프록시 대역 — 설정에서 주입, 한 곳에서만 관리
    List<IpAddressMatcher> trusted = this.trustedProxyMatchers;

    // [잇] 체인 조립. getHeaders 로 같은 이름 헤더를 전부 모은다.
    List<String> chain = new ArrayList<>();
    Enumeration<String> headers = request.getHeaders("X-Forwarded-For");
    while (headers.hasMoreElements()) {
        for (String v : headers.nextElement().split(",")) {
            if (!v.isBlank()) chain.add(v.trim());
        }
    }
    chain.add(request.getRemoteAddr());  // 위조 불가값을 맨 오른쪽에

    // [걷][멈] 오른쪽 끝에서 왼쪽으로
    for (int i = chain.size() - 1; i >= 0; i--) {
        String candidate = chain.get(i);
        boolean isTrustedProxy = trusted.stream()
                .anyMatch(m -> m.matches(candidate));
        if (!isTrustedProxy) return candidate;  // 처음 만난 바깥 값
    }

    // 전부 신뢰 프록시였다 = 내부에서 발생한 요청(헬스체크 등)
    return request.getRemoteAddr();  // 안전한 실패
}

직접 파싱한다면 반드시 밟는 함정 넷

① getHeader vs getHeaders
HTTP는 같은 이름의 헤더가 여러 번 등장하는 것을 허용하고, getHeader(String)은 그중 첫 번째만 돌려준다. 공격자가 자기 X-Forwarded-For를 하나 보내고 프록시가 별도 헤더로 값을 추가하는 구성이라면, getHeader는 공격자의 헤더를 읽는다.
② 예외 상황에서 왼쪽 값으로 되돌아가기
"체인이 이상하면 그냥 왼쪽 값이라도 쓰자"는 fallback을 넣는 순간, 공격자는 그 예외 상황을 만들어 내는 방법을 찾아 우회한다. 불확실하면 소켓 주소로 떨어지는 것이 안전한 실패다.
③ IP가 아닌 값 · 포트가 붙은 값
체인에는 unknown 같은 문자열, 1.2.3.4:56789처럼 포트가 붙은 값, IPv6의 [2001:db8::1]:443이 섞여 올 수 있다. 파싱에 실패한 항목을 "신뢰 밖 값"으로 오인해 클라이언트로 확정하면 그 자체가 위조 통로가 된다 — 파싱 실패는 곧 안전한 실패로 처리한다.
④ 항목 수 폭탄
공격자가 XFF에 항목 수천 개를 넣어 보내면 요청마다 그 길이만큼 순회한다. 최전선에서 헤더 크기 제한을 두고(초과 시 거절), 파서에도 항목 수 상한을 둔다. 이것 역시 "헤더는 사용자 입력"이라는 원칙의 연장이다.

8. 실무에서는 직접 짜지 않는다 — 계층별 표준 구현

각 계층에 검증된 구현이 있고, 앞 계층에서 해석할수록 뒤 계층 전체가 혜택을 본다. 공통점은 하나다 — 해석 결과로 getRemoteAddr()(또는 $remote_addr) 자체를 교체해, 뒤쪽 코드가 헤더를 볼 일이 없게 만든다.

8-1. Nginx — realip 모듈

Nginx신뢰 프록시가 붙인 XFF를 해석해 $remote_addr를 교체한다
# 신뢰하는 앞 계층 대역. 여러 줄로 여러 대역을 지정할 수 있다.
set_real_ip_from 10.0.0.0/8;

# 어느 헤더를 해석할 것인가. X-Real-IP 나 proxy_protocol 도 지정 가능하다.
real_ip_header   X-Forwarded-For;

# 핵심 스위치. on 이면 5절의 rightmost 알고리즘대로 동작한다 —
# 오른쪽부터 신뢰 대역을 재귀적으로 걷어내고 처음 만나는 바깥 값을 취한다.
real_ip_recursive on;
# off(기본)면 헤더의 마지막 항목 하나만 보고 끝낸다.

real_ip_recursive의 기본값은 off다

LB → Nginx처럼 프록시가 두 단 이상인 구성에서 이것을 켜지 않으면 클라이언트 IP가 LB의 IP로 잡힌다. "설정을 다 했는데 로그에 여전히 내부 IP가 찍힌다"의 흔한 원인이다. 증상이 "에러"가 아니라 "그럴듯한 내부 IP"라서 한동안 눈치채지 못한다.

교체 후에도 원래 소켓 주소가 필요하면 $realip_remote_addr로 읽을 수 있다. 로그에 둘 다 남겨두면 사고 조사 때 유용하다(4-4의 로그 3종).

8-2. Spring Boot(내장 Tomcat) — RemoteIpValve

Before앱 코드 곳곳에서 헤더를 직접 뜯는다
# 설정 없음.

# 대신 앱 코드에 이런 유틸이 하나 있고
# request.getHeader("X-Forwarded-For").split(",")[0]

# 복붙된 변형이 서너 개 더 있다.
# → 그중 하나라도 위조값을 쓰면 4절의 우회가 성립한다.
# → 어느 것이 "진짜 클라이언트 IP"인지 아무도 모른다.
After신뢰 프록시를 선언하고 getRemoteAddr()로 일원화
server:
  forward-headers-strategy: native      # 컨테이너(Tomcat) 구현
  tomcat:
    remoteip:
      remote-ip-header: X-Forwarded-For
      protocol-header: X-Forwarded-Proto   # 스킴 복원도 함께
      # 신뢰(내부) 프록시 패턴. 매칭되는 항목은 체인에서 걷어낸다.
      # 기본값도 사설 대역(10/8, 172.16-31/12, 192.168/16)과
      # 루프백을 이미 포함한다.
      internal-proxies: "10\\.\\d{1,3}\\.\\d{1,3}\\.\\d{1,3}"

RemoteIpValve에는 신뢰 대상을 나누는 두 설정이 있고 역할이 다르다. 면접에서 이 구분을 말할 수 있으면 "설정을 복붙한 사람"과 갈린다.

internalProxies — 내 인프라의 프록시

  • 체인에서 조용히 걷어내고 기록도 남기지 않는다
  • 내 LB·Nginx·인그레스가 여기 해당

trustedProxies — 신뢰하되 기록은 남길 프록시

  • 걷어내되 별도 헤더(X-Forwarded-By)에 옮겨 적는다
  • CDN처럼 외부 사업자의 프록시가 여기 해당 — "어느 엣지를 거쳐 왔는가"를 로그로 남길 수 있다
동작 순서는 5절의 알고리즘 그대로다 오른쪽 끝에서 시작 → internalProxies에 매칭되는 동안 조용히 걷어내고 → trustedProxies에 매칭되면 기록하며 계속 걷어내고 → 둘 다 아닌 값을 만나면 그것을 클라이언트 IP로 확정하고 멈춘다.

8-3. native vs framework — 이 표가 이 절의 결론이다

스프링의 forward-headers-strategy 두 값. 클라이언트 IP를 보안 판단에 쓸 거라면 선택지는 사실상 하나다.
축framework — ForwardedHeaderFilternative — Tomcat RemoteIpValve
구현 위치서블릿 필터 (컨테이너 무관)서블릿 컨테이너 내부
신뢰 프록시 지정없다 — 헤더를 무조건 신뢰한다internalProxies / trustedProxies로 지정
실행 시점필터 체인 안 (등록 순서에 의존)모든 필터보다 앞
안전 전제최전선에서 XFF를 반드시 정리해야 함신뢰 목록 밖 요청의 헤더는 스스로 무시
해석 대상Forwarded + X-Forwarded-* (둘 다 있으면 Forwarded 우선)설정한 헤더 이름
이럴 때 쓴다스킴·호스트 복원이 주 목적이고, 앞단 정리 정책이 확실할 때IP를 차단·allowlist·rate limit에 쓸 때의 기본값
framework에는 신뢰 프록시 개념이 아예 없다 즉 도착한 헤더를 검증 없이 그대로 반영한다. 이 전략은 "요청이 반드시 우리 프록시를 거쳐서만 들어온다"는 인프라 보장(10절)과, 최전선에서 클라이언트가 보낸 XFF를 덮어쓰는 정책이 함께 있어야만 안전하다.
참고로 ForwardedHeaderFilter에는 removeOnly 옵션도 있다. 헤더를 해석하지 않고 제거만 하는 모드로, 앞 계층에서 이미 해석이 끝났고 앱은 헤더를 아예 못 보게 하고 싶을 때 쓴다 — 9절의 "앱에서 헤더를 읽지 않는다"를 구조로 강제하는 수단이다.

9. 해석 지점을 한 곳으로 — 그리고 필터 순서

계층별 구현을 다 알아도 어디서 해석할지 정하지 않으면 소용없다. 여러 곳에서 제각기 해석하면 계층마다 다른 답을 내놓고, 어느 것이 맞는지 아무도 모르게 된다.

운영 원칙 세 줄

해석은 신뢰 체인의 입구 한 곳(최전선 프록시 또는 WAS)에서만 한다
  • 그 이후로는 getRemoteAddr()만 쓴다.
  • 애플리케이션 코드에서 getHeader("X-Forwarded-For") 호출을 금지한다.
  • 금지는 정책이 아니라 구조로 건다 — 정적 분석 규칙·리뷰 체크리스트, 또는 removeOnly로 헤더 자체를 없앤다.

이유는 현실적이다. split(",")[0]으로 뜯는 유틸이 하나 굴러다니기 시작하면 복붙된 변형이 몇 개 더 생기고 그중 하나는 반드시 잘못 쓰인다. 그리고 잘못 쓰인 하나만 있어도 4절의 우회는 성립한다.

9-1. Spring Security로 IP 접근 제어를 걸 때 — 순서가 곧 안전이다

Spring Security의 IP 매칭은 결국 request.getRemoteAddr()를 본다. 그러므로 그 값을 교체해 주는 장치가 Security 필터 체인보다 먼저 동작해야 한다.

@Bean
SecurityFilterChain adminChain(HttpSecurity http) throws Exception {
    http.securityMatcher("/admin/**")
        .authorizeHttpRequests(auth -> auth
            // 이 판정의 근거는 getRemoteAddr() 이다.
            // 그 값이 아직 프록시 IP라면 → 모든 요청이 통과하거나 모두 막힌다.
            // 그 값이 위조된 헤더로 채워졌다면 → 4-3의 allowlist 우회가 성립한다.
            .anyRequest().access(new WebExpressionAuthorizationManager(
                    "hasIpAddress('10.0.0.0/8')")));
    return http.build();
}

native(RemoteIpValve) — 순서 문제가 없다

  • 컨테이너 레벨이라 모든 서블릿 필터보다 먼저 동작한다.
  • Security가 보는 getRemoteAddr()는 이미 해석된 값이다.

framework(ForwardedHeaderFilter) — 순서를 직접 챙겨야 한다

  • 필터이므로 Security 필터 체인보다 앞선 순서로 등록돼야 한다.
  • 순서가 뒤집히면 판정은 예전 값(프록시 IP)으로 이뤄지고, 그 사실이 에러로 드러나지 않는다.
그리고 한 가지 더 — IP allowlist는 관리자 인증을 대신하지 못한다 10절의 전제가 깨지거나 사내망 안에서 사고가 나면 그대로 뚫린다. IP 제한은 인증·인가 위에 얹는 추가 계층으로 쓰는 것이지, 그 자리를 대신하는 것이 아니다. "IP로 막고 있으니까 관리자 2차 인증은 나중에"가 가장 위험한 문장이다.

10. 인프라 전제 — 우회로가 없어야 신뢰가 성립한다 가산점

지금까지의 논리는 전부 하나의 문장 위에 서 있다. "요청은 반드시 내 신뢰 프록시를 거쳐서 온다." 이 전제가 깨지면 무엇이 견디고 무엇이 무너지는지를 구분해 말하는 것이 이 절의 핵심이다.

헤더 신뢰의 전제 조건 — 네트워크 수준의 차단 체크리스트

앱에 공인 IP를 주지 않는다
프라이빗 서브넷에 둔다. 도달 경로가 물리적으로 하나가 되게 만드는 것이 목표다.
앱 포트를 LB에서만 연다
IP 대역이 아니라 LB의 보안 그룹 자체를 출발지로 지정할 수 있다면 그 편이 더 견고하다 — 대역은 바뀌어도 그룹 참조는 유지된다.
쿠버네티스는 NetworkPolicy
인그레스 파드에서 오는 트래픽만 허용한다. 기본값이 "전부 허용"임을 잊지 않는다.
최전선에서 XFF를 재시작
proxy_set_header X-Forwarded-For $remote_addr; — append가 아니라 덮어쓰기. 체인이 항상 우리 관측값에서 시작하므로 해석이 극적으로 단순해진다. 다만 이 정책도 "최전선을 우회할 수 없다"는 전제 위에서만 유효하다.

11. IP를 결정 키로 쓸 때의 한계 — 공 · 넓 · 많 시니어 변별

IP를 정확히 얻는 것과, 그 IP를 얼마나 믿고 결정에 쓸 것인가는 별개의 설계 문제다

이 구분에서 시작하는 것이 이 절의 답이다. 10절까지를 완벽히 구현해도, IP라는 식별자 자체에 한계가 있다. 한계는 셋 — 공(공유) · 넓(넓은 IPv6) · 많(많은 IP 확보)이다.

한계 ③ 많 — 공격자 쪽에서는 IP를 대량으로 확보할 수 있다

봇넷, 상용 프록시 풀, 모바일 프록시 서비스를 쓰면 수만 개의 IP를 돌려가며 쓸 수 있다. IP 단위 제한은 공격 비용을 조금 올릴 뿐 막지는 못한다. 여기서 나오는 결론이 아래 한 줄이다.

IP는 단독 키가 아니라 보조 신호 — 계정·기기 지문과 조합한다
① 계정 단위 제한을 1차로
로그인 시도라면 대상 계정 기준으로 세는 것이 IP 기준보다 훨씬 정확하다 — 공격자가 IP를 바꿔도 표적 계정은 그대로이기 때문이다.
② 기기 지문·세션 식별자를 함께
단독으로는 약하지만 여러 신호가 겹칠 때 판단의 근거가 된다.
③ IP는 가중치 신호로
차단의 단독 근거가 아니라 위험 점수를 올리는 요소로 쓰고, 점수가 높으면 차단 대신 추가 인증(CAPTCHA·2차 인증)으로 마찰을 올린다 — 무고한 사용자는 통과하고 자동화 공격은 비용이 커지는 방향이다.
④ 차단은 짧게, 좁게
불가피하면 기간을 짧게 범위를 좁게 건다. NAT 뒤 사용자를 오래 막지 않기 위해서다.
마무리는 관측 가능성으로 가산점 어떤 키로 무엇을 막았는지 로그로 남기고, 오차단이 의심되면 되돌릴 수 있어야 한다. 그리고 4-4에서 말한 해석된 클라이언트 IP · 원래 소켓 주소 · XFF 원본 세 가지를 함께 남겨두면, 나중에 판단을 재검토하고 과거 로그를 소급 재계산할 수 있다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

소켓 주소가 위조 불가인 이유 한 문장?
출발지를 위조하면 SYN+ACK가 위조한 IP로 가서 시퀀스 번호를 모르니 ACK를 못 만든다 → 연결이 없으면 HTTP도 없다.
XFF의 규칙 한 줄?
각 프록시가 "나에게 보낸 상대의 소켓 주소"를 뒤에 append한다. 들어온 값의 진위는 검사하지 않는다.
왼쪽 값을 쓰면 뚫리는 4종?
제·차·허·로 — rate 제한 · IP 차단 · 관리자 허용목록 · 감사 로그.
올바른 알고리즘 4단계?
정·잇·걷·멈 — 목록 정의 · 소켓 주소 잇기 · 오른쪽부터 걷어내기 · 처음 만난 바깥 값에서 멈춤.
왜 하필 오른쪽부터인가?
오른쪽은 관측, 왼쪽은 전언. 왼쪽부터 걸으면 공격자가 신뢰 대역 IP를 앞에 채워 원하는 값을 고르게 만들 수 있다.
Nginx에서 가장 자주 놓치는 것?
real_ip_recursive의 기본값이 off. 프록시가 2단 이상이면 앞단 프록시 IP가 클라이언트로 잡힌다.
internalProxies vs trustedProxies?
둘 다 걷어내지만 internal은 조용히, trusted는 X-Forwarded-By에 기록하며. 후자가 CDN용.
native vs framework 한 줄?
framework는 신뢰 프록시 지정이 없어 헤더를 무조건 신뢰하고 필터 순서에 의존한다. 보안 판단에 쓸 IP라면 native.
신뢰 홉 수 방식의 실패 조건?
실제 홉이 설정보다 적어지는 순간(경로가 둘, 프록시 제거) 위조값을 고른다. 에러 없이 조용히 틀린다.
헤더 신뢰의 인프라 전제?
프록시를 우회해 앱에 도달할 경로가 없어야 한다 — 사설 IP + 보안 그룹(LB 그룹에서만) + NetworkPolicy.
IP 식별자의 한계 3종?
공·넓·많 — NAT 공유 · IPv6 프리픽스 · 대량 IP 확보. 그래서 보조 신호로만 쓴다.
로그에 함께 남길 세 가지?
해석된 IP · 소켓 주소 · XFF 원본. 하나만 남기면 그 하나가 틀렸을 때 되돌릴 수 없다.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

XFF에 IP가 여러 개 들어 있으면 어떤 값을 써야 하나요? 필수힌트: 값을 고르는 규칙이 아니라 "왜 그 방향인가"를 설명해야 답이 완성된다

가장 왼쪽 값이 아니다. 오른쪽 끝(소켓 주소)에서 시작해 내가 신뢰하는 프록시 목록에 있는 IP인 동안 계속 걷어내고, 처음 만나는 신뢰 목록 밖의 값이 실제 클라이언트 IP다.

왜 오른쪽부터인지가 답변의 핵심이다. XFF의 각 항목은 그것을 붙인 프록시가 자기 소켓에서 직접 관측한 주소다. 오른쪽으로 갈수록 우리 인프라에 가까운 장비가 적은 값이라 위조가 불가능하고, 왼쪽으로 갈수록 "전달받아 적혔을 뿐"이라 진위를 보증할 수 없다. 특히 가장 왼쪽 값은 클라이언트가 요청을 만들 때 직접 넣어 보낸 것일 수 있다 — 프록시는 들어온 값을 검사하지 않고 뒤에 덧붙이기만 하기 때문이다.

방향이 반대인 구현은 위험하다. "왼쪽부터 걸으며 신뢰 대역을 건너뛴다"로 짜면 공격자가 신뢰 대역 IP를 앞에 여러 개 채워 넣어 자기가 원하는 값이 선택되게 만들 수 있다. 오른쪽에서 출발하는 것 자체가 안전성의 근거다.

직접 구현할 필요는 없다. Nginx의 real_ip_recursive on, Tomcat RemoteIpValve의 internalProxies/trustedProxies가 이 알고리즘의 구현체다. 다만 real_ip_recursive의 기본값이 off라서 프록시가 2단 이상이면 앞단 프록시 IP가 클라이언트로 잡힌다는 것은 알아둬야 한다.

그럼 헤더 말고 getRemoteAddr()만 쓰면 안전한 것 아닌가요? 필수힌트: "안전"과 "쓸모"를 갈라서 말한다

안전하지만 쓸모가 없다. 이 둘을 구분해 말하는 것이 답의 핵심이다.

getRemoteAddr()는 TCP 소켓의 상대 주소이므로 위조되지 않는다. 3-way handshake가 성립해야 HTTP 요청을 보낼 수 있고, 출발지 IP를 위조하면 서버의 응답을 받지 못해 handshake 자체가 완료되지 않기 때문이다.

문제는 프록시 뒤에서는 그 값이 언제나 프록시 IP라는 것이다. 모든 사용자가 같은 IP로 보인다. 이 상태에서 IP 기반 rate limit을 걸면 전체 트래픽이 키 하나에 몰려 임계값을 즉시 넘고, 그 키를 차단하는 순간 전면 장애가 된다. 접근 로그도 전부 같은 값이라 사고 조사가 불가능하다.

그래서 답은 둘 중 하나를 고르는 것이 아니라 결합이다. 소켓 주소의 "위조 불가능성"과 헤더의 "정보 전달"을 합친 것이 신뢰 프록시 기반 해석이다 — 소켓 주소에서 출발해 내가 아는 프록시들을 걷어내며 헤더를 따라 바깥으로 걸어 나간다.

위조 불가능한 값에서 출발해, 내가 아는 만큼만 바깥으로 신뢰를 확장한다

덧붙여, 프록시가 없어 앱이 직접 노출된 서버라면 getRemoteAddr()만으로 충분하고 XFF는 오히려 무시해야 한다는 대비까지 말하면 좋다. 그 환경에서 XFF를 읽는 코드는 순수한 취약점이다 — 얻는 것은 없고 위조 통로만 하나 여는 셈이다.

신뢰 프록시 대역을 알 수 없는 환경입니다. "오른쪽에서 2개 걷어내기"처럼 홉 수로 정하면 안 되나요? 시니어 변별힌트: 언제 깨지는지를 구체적 경로 두 개로 보여준다

차선책은 되지만 원칙은 아니다. 두 방식의 기준이 다르다 — 목록 방식은 "이 값을 누가 적었나"를 보고, 홉 수 방식은 "오른쪽에서 몇 번째인가"만 센다. 후자는 "우리 구성이 항상 이 모양"이라는 가정을 숫자에 박아 넣는 것이다.

깨지는 순간이 구체적이다. 앱에 도달하는 경로가 둘일 때(CDN 경유 경로와 미경유 경로), 프록시가 추가·제거될 때, 그리고 공격자가 항목을 미리 채워 넣었을 때다. 마지막 경우가 특히 위험하다 — 실제 홉이 1단인데 홉 수를 2로 설정해 두면, 공격자가 X-Forwarded-For: 9.9.9.9를 붙여 보내는 것만으로 체인이 [9.9.9.9, 공격자실제IP, LB]가 되고 오른쪽에서 2개를 걷어낸 결과는 위조값 9.9.9.9가 된다.

가장 나쁜 성질은 "조용함"이다. 형식이 멀쩡한 IP가 반환되므로 예외도 나지 않고 지표도 정상으로 보인다. 구성 변경은 코드 밖(인프라)에서 일어나므로 배포와 무관하게 어느 날 어긋난다.

그래도 홉 수를 써야 한다면 두 조건을 함께 건다 — ①앱에 도달하는 경로를 하나로 강제(직접 접근 차단, 헬스체크 경로 분리)하고, ②최전선에서 XFF를 append가 아니라 덮어쓰기로 재시작해 체인 길이를 우리가 통제한다. 이 둘이 없으면 홉 수는 "오늘 우연히 맞는 숫자"일 뿐이다.

같은 이름의 X-Forwarded-For 헤더가 요청에 두 개 들어오면 어떻게 되나요? 함정힌트: 서블릿 API의 메서드 이름 두 개가 답이다

HTTP는 같은 이름의 헤더가 여러 번 등장하는 것을 허용한다. 그리고 서블릿 API의 getHeader(String)은 그중 첫 번째 것만 돌려준다.

그래서 공격자가 자기 X-Forwarded-For 헤더를 하나 보내고 프록시가 값을 별도 헤더로 추가하는 구성이라면, getHeader는 프록시가 붙인 헤더가 아니라 공격자의 헤더를 읽는다. 직접 파싱한다면 getHeaders로 전부 모아 순서대로 이어 붙여야 한다.

더 나은 대응은 애초에 직접 파싱하지 않는 것이고(8절), 그다음은 최전선에서 헤더를 하나로 정규화하는 것이다 — 최전선 프록시에서 XFF를 덮어쓰기로 재시작하면 뒤 계층에 도착하는 헤더가 항상 하나이므로 이 함정 자체가 사라진다. "파싱을 잘하기"보다 "파싱할 일이 없게 만들기"가 항상 낫다.

CDN(Cloudflare, CloudFront) 뒤에 있으면 어떻게 달라지나요?힌트: 두 가지가 달라지고 둘 다 함정이 있다

첫째, 신뢰 목록에 CDN의 엣지 IP 대역을 넣어야 한다. 그런데 이 대역은 사업자가 공개하지만 수시로 바뀐다. 갱신을 자동화하지 않으면 어느 날 새로 추가된 엣지 대역이 "신뢰 밖"으로 분류되고, 그 엣지를 거친 요청의 클라이언트 IP가 엣지 IP로 잡힌다. 증상이 일부 사용자에게만 나타나 원인 파악이 어렵다. 사업자가 제공하는 IP 목록 엔드포인트를 주기적으로 받아 설정을 갱신하는 자동화가 필요하다.

둘째, CDN이 주는 전용 헤더를 쓰는 방법이 있다. Cloudflare의 CF-Connecting-IP, 일부 CDN이 제공하는 True-Client-IP처럼 CDN이 자기 소켓에서 직접 관측한 클라이언트 IP만 담은 단일 값 헤더다. 체인을 파싱할 필요가 없어 훨씬 단순하다.

하지만 이 헤더 역시 그냥 믿으면 안 된다 이것도 결국 HTTP 헤더이므로 누구나 만들어 보낼 수 있다. CDN을 우회해 오리진에 직접 요청하면 CF-Connecting-IP: 1.2.3.4를 위조해 꽂을 수 있다. 즉 이 헤더의 안전성은 헤더 자체가 아니라 "오리진에는 CDN을 통해서만 도달할 수 있다"는 보장에서 나온다.

그래서 오리진 보호가 반드시 짝으로 간다. 오리진 방화벽에서 CDN의 IP 대역만 허용하거나, CDN과 오리진 사이에 공유 비밀값(전용 헤더나 mTLS)을 두어 CDN을 거치지 않은 요청을 거부한다. 오리진의 실제 IP를 숨기는 것만으로는 부족하다 — DNS 이력이나 인증서 투명성 로그로 노출되는 경우가 많다.

"CDN 전용 헤더는 편리하지만, 그 편리함의 근거는 오리진 보호"라는 인과를 말할 수 있어야 한다
L4 LB 뒤에서는 XFF를 못 쓰지 않나요? 가산점힌트: 대안의 이름과, 그 대안이 안고 있는 같은 문제까지

맞다. XFF는 HTTP 헤더이므로 HTTP를 해석하는 L7 장비만 붙일 수 있다. L4 로드밸런서는 TCP/UDP 수준에서 패킷을 전달할 뿐 페이로드를 들여다보지 않으므로 헤더를 추가할 방법 자체가 없다(16-l4-vs-l7-load-balancer). TLS를 종료하지 않고 그대로 통과시키는 구성이라면 애초에 암호화돼 있어 손댈 수도 없다.

대안이 PROXY protocol이다. TCP 연결이 수립된 직후 애플리케이션 데이터보다 먼저 원 클라이언트의 주소 정보를 담은 짧은 전문을 한 번 보내기로 하는 약속이다. HTTP보다 아래 층에서 동작하므로 HTTP가 아닌 프로토콜(데이터베이스 연결, WebSocket, 원시 TCP)에도 쓸 수 있다는 것이 장점이다.

주의할 점이 둘 있다. 첫째, 양쪽 모두 활성화해야 한다. 보내는 쪽만 켜면 뒤 서버가 그 전문을 HTTP 요청의 첫 줄로 해석해 400을 뱉고, 받는 쪽만 켜면 정상 요청의 첫 줄을 전문으로 오해해 연결이 깨진다. 통신 자체가 안 되므로 배포 순서를 맞춰야 한다.

둘째, 이것도 신뢰 문제를 그대로 안고 있다. PROXY protocol 전문 역시 연결을 맺는 쪽이 쓰는 값이므로, 아무나 그 포트에 접속해 전문을 보낼 수 있다면 위조가 된다. 그래서 받는 쪽에 "이 대역에서 온 연결의 전문만 신뢰한다"는 설정(Nginx의 set_real_ip_from이 여기에도 쓰인다)이 필요하고, 10절의 네트워크 차단 전제도 똑같이 필요하다. 계층이 바뀌어도 "신뢰 경계를 어디에 긋는가"라는 문제는 그대로 따라온다.

헬스체크처럼 체인이 전부 신뢰 프록시일 때는 무엇을 반환해야 하나요? 함정힌트: 여기서 "그럼 왼쪽 값이라도"로 돌아가면 지금까지가 무의미해진다

소켓 주소를 반환한다 — 안전한 실패다. 체인의 모든 항목이 신뢰 목록 안이라는 것은 요청이 내부에서 발생했다는 뜻이다(LB 헬스체크, 내부 서비스 간 호출, 모니터링 프로브).

절대 하면 안 되는 것은 fallback으로 "가장 왼쪽 값"으로 되돌아가는 것이다. 예외 상황에서 왼쪽 값으로 떨어지는 코드가 있으면, 공격자는 그 예외 상황을 만들어 내는 방법을 찾는다 — 예컨대 체인 전체를 사설 대역 IP로 채워 보내는 것만으로 fallback이 발동한다. 공격자가 조건을 만족시킬 수 있는 fallback은 fallback이 아니라 우회로다.

운영에서 함께 챙길 것: 내부 요청은 rate limit·차단 대상에서 아예 분리하는 편이 낫다. 헬스체크가 "클라이언트 IP = LB"로 집계되면 내부 트래픽이 임계값을 잠식하고, 최악의 경우 LB IP가 차단돼 전 인스턴스가 비정상 판정을 받는 자해 장애가 난다.

실제 클라이언트 IP를 rate limiting이나 차단 키로 쓸 때의 한계는? 시니어 변별힌트: 문제를 두 개로 쪼개는 문장으로 시작한다

IP를 정확히 얻는 것과, 그 IP를 얼마나 믿고 결정에 쓸 것인가는 별개의 설계 문제다. 이 구분에서 시작하는 것이 답이다. 앞의 내용을 완벽히 구현해도 IP라는 식별자 자체에 한계가 있다 — 공·넓·많.

① 공 — 여러 사람이 한 IP를 공유한다. 통신사의 대규모 NAT나 기업 프록시 뒤에서는 수백에서 수천 명이 같은 공인 IP로 나온다. 학교나 공공 와이파이도 마찬가지다. 여기서 IP 단위 차단을 걸면 한 명의 공격자를 막으면서 같은 IP를 쓰는 무고한 사용자 전부를 함께 막는다.

② 넓 — IPv6에서는 정반대 문제. 가입자 한 명에게 /64 이상의 블록을 통째로 할당하는 것이 보통이라, 같은 사용자가 요청마다 다른 주소를 쓸 수 있어 IP 단위 제한이 무의미해진다. 그래서 개별 주소가 아니라 /64 같은 프리픽스 단위로 묶어 카운트해야 한다. IPv4와 IPv6에 같은 로직을 쓰면 한쪽은 반드시 틀린다.

③ 많 — 공격자는 IP를 대량 확보할 수 있다. 봇넷·프록시 풀·모바일 프록시로 수만 개의 IP를 돌려가며 쓴다. IP 단위 제한은 비용을 조금 올릴 뿐 막지는 못한다.

그래서 IP는 단독 키가 아니라 보조 신호다

실무의 조합은 이렇게 간다 — 계정 단위 제한을 1차로(로그인 시도는 대상 계정 기준이 IP 기준보다 정확하다. 공격자가 IP를 바꿔도 표적 계정은 그대로다), 기기 지문·세션 식별자를 함께, IP는 위험 점수를 올리는 가중치로 쓰고 점수가 높으면 차단 대신 추가 인증(CAPTCHA·2차 인증)으로 마찰을 올린다. 차단이 불가피하면 기간을 짧게 범위를 좁게. 마지막으로 관측 가능성 — 무엇을 어떤 키로 막았는지 남기고, 해석된 IP·소켓 주소·XFF 원본을 함께 기록해 판단을 재검토할 수 있게 한다.

앱 앞에 프록시가 없는데도 XFF를 읽는 코드가 있습니다. 그냥 둬도 되나요? 함정힌트: 얻는 것과 잃는 것을 세어 본다

순수한 취약점이므로 제거한다. 프록시가 없으면 정상 요청에는 XFF가 애초에 없다 — 즉 그 코드가 값을 읽어 쓰는 경우는 공격자가 넣어 보냈을 때뿐이다. 얻는 것은 0이고 여는 것은 위조 통로 하나다.

"나중에 프록시가 생길 수도 있으니 미리 넣어 뒀다"는 것도 위험하다. 프록시가 생기는 시점과 신뢰 목록이 설정되는 시점 사이의 공백이 그대로 취약 구간이 된다. 순서는 반대여야 한다 — 프록시를 두고, 신뢰 목록을 설정하고, 그다음에 해석을 켠다. 그리고 해석은 앱 코드가 아니라 8절의 표준 구현으로 켠다.

이 신뢰 모델을 팀에 정착시키려면 무엇을 문서·코드로 남겨야 하나요? 가산점힌트: "조심하자"는 정착되지 않는다

사람의 주의력이 아니라 구조에 남긴다. 네 가지다.

① 신뢰 목록을 설정 한 곳에
코드에 흩어진 IP 대역 리터럴을 없앤다. 목록이 곧 신뢰 경계이므로 어디에 적혀 있는지 모르면 경계가 없는 것이다.
② 앱 코드의 헤더 접근 금지 규칙
getHeader("X-Forwarded-For")를 정적 분석 규칙으로 막거나 removeOnly로 헤더 자체를 없앤다.
③ 해석 결과를 검증하는 테스트
위조 XFF를 넣은 요청이 클라이언트 IP로 소켓 주소를 돌려주는지를 통합 테스트로 고정한다. 설정 변경으로 조용히 깨지는 것을 막는 유일한 방법이다.
④ 네트워크 차단을 코드로
보안 그룹·NetworkPolicy를 IaC로 관리해 "앱이 직접 노출되지 않는다"는 전제를 리뷰 가능한 형태로 만든다. 이 전제가 깨지는 변경은 반드시 리뷰를 거치게 한다.

면접에서 이 답의 값어치는 "헤더 파싱은 절반이고 나머지 절반은 인프라와 팀 규약"이라는 시야를 보여준다는 점에 있다.

한 줄 요약
프록시 뒤에서 소켓 주소는 프록시 IP이므로 실제 클라이언트 IP는 X-Forwarded-For로 전달받지만, 이 헤더는 클라이언트가 처음부터 아무 값이나 넣어 보낼 수 있고 프록시는 그 뒤에 덧붙이기만 하므로 체인의 왼쪽은 전부 위조값일 수 있다 — 그래서 split(",")[0]은 rate limit·차단·관리자 allowlist·감사 로그를 한 줄로 우회시키고, 올바른 해석은 위조 불가능한 소켓 주소에서 출발해 신뢰 프록시를 오른쪽부터 걷어내며 처음 만나는 바깥 값을 취하는 것(Nginx real_ip_recursive, Tomcat RemoteIpValve)을 한 곳에 일원화하는 것이다. 이 신뢰 모델은 앱에 프록시를 우회해 도달할 경로가 없다는 네트워크 차단이 있어야 성립하고(CDN 전용 헤더의 안전성도 오리진 보호에서 나온다), 그렇게 정확히 얻은 IP조차 NAT 공유와 IPv6 프리픽스 문제 때문에 단독 차단 키가 아니라 계정·기기 지문과 조합하는 보조 신호로 써야 한다.
