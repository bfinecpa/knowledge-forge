웹소켓 / SSE / 폴링
실시간의 세 가지 구현과 "몇 초의 실시간인가"라는 되물음

면접 질문: "웹소켓과 SSE, 폴링의 차이와 선택 기준은?"

핵심 관전 포인트 — 셋의 차이는 "누가, 어느 방향으로, 어떤 커넥션 위에서 데이터를 흘리는가"다. 폴링은 클라이언트가 주기적으로 물어보는 방식이라 연결을 유지하지 않고, SSE는 HTTP 응답 본문을 끝내지 않은 채 서버→클라이언트 한 방향으로만 계속 흘리는 방식이며, 웹소켓은 HTTP 요청으로 시작해 101 Switching Protocols로 프로토콜을 갈아탄 뒤 그 TCP 연결이 더 이상 HTTP가 아니게 되는 양방향 전용선이다. 이 마지막 사실이 웹소켓 비용의 근원이다 — 중간 프록시가 업그레이드를 이해하지 못하면 연결을 끊고, 자동 재연결·유실 복구가 표준에 없어 직접 만들어야 하며, 그 대가로 SSE에는 EventSource의 자동 재연결과 Last-Event-ID 기반 재전송이 공짜로 딸려 온다. 선택은 기술 우열이 아니라 판단 순서다 — ① 요구되는 실시간이 실제 몇 초인지 되묻고(수십 초가 허용되면 폴링이 정답), ② 데이터가 한 방향으로만 흐르면 SSE로 충분하며, ③ 양방향 고빈도일 때만 웹소켓의 인프라 비용을 지불한다. 그 인프라 비용의 실체는 넷이다: LB·프록시의 유휴 타임아웃이 장수 커넥션을 끊으므로 하트비트 주기를 경로상 가장 짧은 유휴 상한보다 짧게 잡아야 하고, 프록시 응답 버퍼링이 SSE의 실시간성을 무력화하며, scale-out하는 순간 "이벤트가 난 인스턴스"와 "커넥션이 붙은 인스턴스"가 어긋나 Redis Pub/Sub 같은 백플레인이 필요해지고, 커넥션마다 스레드를 묶는 구현은 수천 커넥션에서 스레드 풀을 고갈시킨다. 여기에 L4 LB가 커넥션 단위로만 분배한다는 성질이 겹치면 장수 커넥션은 스케일 아웃해도 새 인스턴스가 비어 있는 부하 편중까지 만든다.
  • 1
    셋은 HTTP의 한 가지 제약에서 갈라져 나온 세 갈래다 — HTTP는 "물어봐야 답하는" 규약이라 서버가 먼저 말을 걸 수 없다. 그래서 답이 셋뿐이다: 계속 물어보거나(폴링), 응답 하나를 안 끝내거나(SSE), HTTP를 버리거나(웹소켓, 101 이후 그 연결은 HTTP가 아니다).
  • 2
    선택은 스펙 비교가 아니라 세 질문을 순서대로 던지는 것이다 — ①몇 초인가(수십 초 허용이면 폴링에서 끝) → ②어느 방향인가(단방향이면 SSE) → ③역방향이 고빈도인가(간헐적이면 SSE + 평범한 POST, 고빈도일 때만 웹소켓).
  • 3
    웹소켓·SSE를 고르는 순간 인프라 비용 다섯을 함께 사는 것이다 — 유휴 타임아웃(하트비트를 가장 짧은 상한의 절반 이하로), 프록시 버퍼링(경로 단위 해제), scale-out 시 이벤트 전파(백플레인, 단 영속 경로와 분리), 커넥션당 스레드 점유(비동기 서블릿/이벤트 루프), L4 LB 부하 편중(커넥션 최대 수명·드레인).

0. 질문 + 출제 의도

질문: "웹소켓과 SSE, 폴링의 차이와 선택 기준은?"

출제 의도: 실시간성 요구(댓글, 알림)를 구현 비용·인프라 제약(LB의 장수 커넥션 처리)과 함께 판단하는지를 본다. 기술 스펙 비교 암기가 아니라, "요구사항의 실시간이 진짜 몇 초 수준인지"를 되묻고 가장 싼 수단부터 검토하는 사람인지 — 요구사항을 구현 비용으로 번역하는 능력을 확인하는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① 스펙 표를 외워서 나열하는 것 → 1절에서 셋을 HTTP의 한 가지 제약에서 논리적으로 갈라져 나온 세 갈래로 재구성한다. 표를 못 외워도 답이 유도된다.
② "실시간이니까 웹소켓"이라는 반사적 선택 → 6절에서 Q1을 되묻는 것이 왜 답변 전체의 출발점인지, 그리고 폴링 비용을 동접 ÷ 주기 × 조회 비용으로 계산하는 법을 다룬다.
③ 앱 코드만 알고 중간 계층을 모르는 것 → 7~11절에서 "앱은 맞는데 인프라 때문에 끊긴다"는 이 영역 장애의 대부분을 계층별로 분해한다. 특히 9절의 scale-out은 시니어 변별 포인트다.

1. 왜 방법이 셋뿐인가 — HTTP의 제약

세 방식이 왜 하필 셋인지부터 짚으면 나머지가 전부 유도된다. HTTP는 요청-응답(request-response) 규약이다. 클라이언트가 요청을 하나 보내면 서버가 응답을 하나 돌려주고, 그것으로 한 쌍이 끝난다. 서버가 자기 마음대로 먼저 말을 걸 수단이 규약 안에 없다. 서버는 "누가 지금 접속해 있는지"조차 요청이 오는 순간에만 안다.

그런데 알림, 채팅, 실시간 대시보드는 전부 "서버 쪽에 새 소식이 생겼을 때 클라이언트에게 알려주는" 일이다. 서버가 먼저 말을 걸 수 없다면 답은 논리적으로 셋뿐이다.

세 갈래를 생활 비유로 붙여 두기

폴링 = 택배 확인
3분마다 현관문을 열어 택배가 왔는지 본다. 대부분은 헛걸음이고, 물건이 와 있어도 최대 3분 늦게 안다.
SSE = 신문 구독
한 번 구독하면 뉴스가 생길 때마다 배달원이 알아서 문 앞에 놓고 간다. 배달은 한 방향 — 신문사에 할 말이 있으면 따로 전화한다.
웹소켓 = 전화 통화
회선을 열어 두고 양쪽이 아무 때나 말한다. 대신 회선을 잡고 있는 비용을 내고, 끊기면 다시 거는 것도 내 몫이다.

2. 네 방식을 한 장의 타임라인으로

세부로 들어가기 전에 같은 사건을 네 방식이 각각 어떻게 처리하는지를 한 장에 겹쳐 놓는다. 상황은 하나다 — t = 17초에 사용자 A에게 알림 하나가 생겼다. 이 그림에서 읽어야 할 것은 세 가지다: 커넥션이 몇 개 생겼다 사라지는가, 화살표가 어느 방향으로 나 있는가, 이벤트가 사용자에게 언제 도착하는가.

3. 폴링과 롱 폴링 — 반복해서 물어보기

3-1. 폴링 — 가장 싸고 가장 보편적인 수단

폴링(polling)은 클라이언트가 일정 주기로 평범한 HTTP 요청을 보내 "새 소식 있나요?"를 확인하는 방식이다. 이름은 여론조사(poll)에서 왔다 — 주기적으로 물어보고 다닌다는 뜻이다.

t=0s    클라이언트 → GET /api/notifications?since=41   HTTP 요청 (완결된 한 쌍)
        서버       → 200 OK  {"items": []}             응답, 연결 정리 가능

t=3s    클라이언트 → GET /api/notifications?since=41   또 한 쌍
        서버       → 200 OK  {"items": []}

t=6s    클라이언트 → GET /api/notifications?since=41
        서버       → 200 OK  {"items": [{"seq":42, ...}]}   ← 이번에야 소식이 있다

얻는 것 — "그냥 HTTP다"

  • LB, 리버스 프록시, 방화벽, CDN, 회사 보안 게이트웨이 어디를 지나도 특별 취급이 필요 없다.
  • 서버가 상태를 안 들고 있으니 인스턴스를 마음대로 늘리고 줄이고 껐다 켤 수 있다.
  • 디버깅은 개발자 도구 네트워크 탭에서 요청 하나 클릭이면 끝.

치르는 대가 — 둘뿐이고, 둘 다 계산 가능하다

  • 변경이 없어도 요청이 발생한다. 위 예시의 t=0, t=3 요청은 빈 배열을 받아 왔다 — 왕복 2번과 조회 2번이 헛수고.
  • 실시간성이 주기에 묶인다. 소식이 t=3.1s에 생겨도 t=6s에야 안다. 평균 지연 = 주기 ÷ 2, 최악 = 주기 전체.

폴링의 비용은 외우는 게 아니라 두 줄로 계산하는 것이다

초당 요청 수 = 동시 접속자 수 ÷ 폴링 주기(초)   |   총비용 = 초당 요청 수 × 요청 1건의 조회 비용
1,000명 / 5초
= 200 req/s — 평범한 서버 한 대로 충분
10,000명 / 3초
≈ 3,333 req/s — 조회가 싸다면 아직 감당 가능
100,000명 / 3초
≈ 33,333 req/s — 여기서부터는 다시 계산해야 한다

갈리는 것은 요청 수 자체가 아니라 둘째 줄이다. 조회가 캐시 히트로 끝나면 33,000 req/s도 감당할 수 있고, 매 요청이 DB 조인을 때리면 3,000 req/s에서도 이미 위험하다. 그래서 면접에서는 "폴링은 비쌉니다"가 아니라 "폴링 주기 × 조회 비용이 감당 가능한지로 계산합니다"라고 말해야 한다.

주기를 줄이는 것은 공짜가 아니다 주기와 요청 수는 반비례다. 3초를 1초로 줄이면 지연은 1/3이 되지만 초당 요청 수는 33,000 → 100,000으로 세 배가 된다. 이 트레이드오프를 숫자로 말할 수 있으면 "폴링을 안 써본 사람"으로 보이지 않는다.

3-2. 롱 폴링 — 응답을 보류하는 절충안

빈 응답 낭비를 줄이는 변형이 롱 폴링(long polling)이다. 서버가 "없어요"를 즉시 응답하지 않고, 새 데이터가 생기거나 정해둔 시간이 지날 때까지 응답을 보류한다. 클라이언트는 응답을 받는 즉시 다시 요청을 건다.

t=0s     클라이언트 → GET /api/notifications?since=41
         서버       ... 응답을 붙들고 대기 (소식이 없으므로 아직 안 보냄)
t=17.4s  ★ 소식 발생
         서버       → 200 OK {"items":[{"seq":42,...}]}    ← 발생 즉시 응답
t=17.4s  클라이언트 → GET /api/notifications?since=42      ← 받자마자 다시 건다
         서버       ... 또 대기
t=47.4s  서버       → 200 OK {"items": []}                 ← 30초 상한에 걸려 빈 응답
t=47.4s  클라이언트 → GET /api/notifications?since=42      ← 다시 건다
롱 폴링의 정체 — "부담은 다 지고 이득은 절반만" 얻는 것은 명확하다: 빈 응답이 "30초에 한 번" 수준으로 줄고, 소식이 생기면 거의 즉시 전달되며, 그러면서도 개별 요청-응답이라는 HTTP의 형태를 그대로 유지한다. 그러나 서버는 응답 대기 중인 요청을 계속 물고 있어야 한다. 이 순간부터 장수 커넥션의 세계이고, 7~11절의 함정이 그대로 적용된다 — 특히 스레드 모델(10절)과 중간 계층 타임아웃(7절). 사실상 장수 커넥션의 부담은 다 지면서 진짜 푸시의 효율은 못 얻는 중간 형태라, 신규 설계에서 1순위로 고를 이유는 적다.
그래도 롱 폴링이 여전히 값을 하는 자리 — 폴백 계층 SSE·웹소켓이 막히는 보수적인 네트워크 환경(응답을 끝까지 버퍼링하는 구형 프록시, 업그레이드를 차단하는 기업망)에서도 롱 폴링은 그냥 HTTP라서 동작한다. 실시간 라이브러리들이 최후의 폴백 계층으로 롱 폴링을 두는 이유가 이것이다. 환경 제약이 확인되지 않은 상태라면 SSE를 기본으로, 실패 시 롱 폴링으로 내려가는 단계적 저하(graceful degradation)를 설계에 넣는 편이 안전하다.
롱 폴링을 쓴다면 반드시 맞춰야 하는 값 — 보류 상한을 경로상 가장 짧은 유휴 타임아웃보다 짧게 잡아야 한다. 보류 30초에 프록시 유휴 상한이 60초면 안전하지만, 보류 90초라면 프록시가 먼저 끊어 매번 에러가 난다. (7절의 하트비트 규칙과 정확히 같은 구조다.)

4. SSE — 끝나지 않는 응답

SSE(Server-Sent Events, 서버 전송 이벤트)는 이름 그대로 "서버가 보내는 이벤트"다. 클라이언트가 요청을 한 번 보내면, 서버는 Content-Type: text/event-stream으로 응답을 열고 응답 본문을 끝내지 않은 채 이벤트가 생길 때마다 텍스트 조각을 이어서 내려보낸다.

"응답을 안 끝낸다"가 무슨 뜻인가 보통의 HTTP 응답은 Content-Length로 길이를 밝히거나 청크 전송으로 마지막 조각을 표시해 끝을 알린다. SSE는 그 끝을 영원히 미룬다. 클라이언트 입장에서는 "다운로드가 끝나지 않는 파일 하나"를 계속 읽고 있는 셈이고, 서버는 그 파일에 계속 줄을 덧붙이고 있는 셈이다.

4-1. 회선 위에서 실제로 오가는 것

요청은 평범하다. 특별한 것은 Accept 하나뿐이고, Last-Event-ID는 재연결일 때만 붙는다.

요청 그냥 GET이다
GET /api/notifications/stream HTTP/1.1
Host: api.example.com
Accept: text/event-stream
Last-Event-ID: 41   ← 재연결일 때만, 브라우저가 자동으로
응답 평범한 200이다
HTTP/1.1 200 OK
Content-Type: text/event-stream

SSE 포맷의 규칙은 다섯 줄로 끝난다. 필드 이름 그대로 본문 · 이름 · 번호 · 간격 · 주석으로 외우면 빠지지 않는다.

SSE 구현에서 가장 흔한 사고 — 빈 줄을 안 보낸 것

빈 줄 하나가 이벤트 하나의 끝이다 — 즉 \n\n이어야 한다

빈 줄을 보기 전까지 브라우저는 "아직 이 이벤트가 안 끝났다"고 보고 계속 기다린다. "서버는 보냈다는데 클라이언트에 아무것도 안 온다"의 흔한 원인 중 하나가 \n\n을 \n 하나로 쓴 것이다. (또 하나의 흔한 원인은 8절의 프록시 버퍼링이다 — 증상이 똑같아서 헷갈린다.)

4-3. 서버 구현 — 서블릿 스택(SseEmitter)

Before 컨트롤러 안에서 직접 루프를 돌며 흘린다 — 스레드가 잠긴다
@GetMapping(value = "/api/notifications/stream", produces = "text/event-stream")

        // 기본 스레드 풀이 200이므로 200번째 구독자부터는 아예 접속이 안 된다.

After SseEmitter를 반환하고 요청 스레드는 즉시 놓아준다
@RestController
@RequiredArgsConstructor
class NotificationStreamController {

    private final EmitterRegistry registry;   // userId -> 열려 있는 emitter 목록
    private final EventStore eventStore;      // Last-Event-ID 재전송용 최근 이벤트 보관소

    @GetMapping(value = "/api/notifications/stream",
                produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public SseEmitter subscribe(
            @AuthenticationPrincipal Long userId,
            // 브라우저가 재연결할 때 자동으로 붙여 보내는 헤더. 최초 접속에는 없다.
            @RequestHeader(value = "Last-Event-ID", required = false) String lastEventId) {

        // 타임아웃을 명시한다. 지정하지 않으면 spring.mvc.async.request-timeout을 따라가는데,
        // 그 값이 짧으면 "아무 이유 없이 30초마다 끊기는 스트림"이 된다.
        // 여기서 지정한 시간이 지나면 onTimeout이 불리고 응답이 정상 종료되며,
        // 브라우저는 이것을 끊김으로 보고 자동 재연결한다 — 의도된 순환이다 (11절).
        SseEmitter emitter = new SseEmitter(Duration.ofMinutes(30).toMillis());

        registry.add(userId, emitter);

        // 종료 훅 셋을 반드시 다 건다. 하나라도 빠지면 이미 끊긴 커넥션의 emitter가
        // 레지스트리에 영원히 남아 (a) 메모리 누수, (b) 죽은 커넥션에 send()를 시도하며
        // 매번 IOException을 만드는 비용을 낳는다.
        emitter.onCompletion(() -> registry.remove(userId, emitter));
        emitter.onTimeout(()    -> registry.remove(userId, emitter));
        emitter.onError(e       -> registry.remove(userId, emitter));

        // 재연결이라면 놓친 구간부터 다시 보낸다. 이 코드가 없으면
        // Last-Event-ID 헤더는 그냥 버려지고 유실 복구는 일어나지 않는다.
        if (lastEventId != null) {
            eventStore.findAfter(userId, Long.parseLong(lastEventId))
                      .forEach(e -> send(emitter, e));
        }

        return emitter;   // ★ 여기서 요청 스레드는 풀로 반환된다 (서블릿 비동기 — 10절)
    }

    private void send(SseEmitter emitter, NotificationEvent e) {
        try {
            emitter.send(SseEmitter.event()
                    .id(String.valueOf(e.seq()))    // → id:    브라우저가 기억할 값
                    .name("notification")           // → event: 클라이언트가 골라 받을 이름
                    .reconnectTime(5000)            // → retry: 끊기면 5초 뒤 재연결하라
                    .data(e.payload()));            // → data:
        } catch (IOException ex) {
            // 이미 끊긴 커넥션이다. 예외를 던져 올릴 일이 아니라 정리 대상이다.
            emitter.completeWithError(ex);
        }
    }
}
return emitter 한 줄이 이 코드의 요점 컨트롤러 메서드가 즉시 반환되고 요청 스레드는 풀로 돌아가지만, HTTP 응답은 아직 끝나지 않은 상태로 남는다. 이것이 서블릿 3.0의 비동기 요청 처리이고, SseEmitter는 그 위에 SSE 포맷을 씌운 것이다. 나중에 다른 스레드(Redis 리스너, 스케줄러)가 emitter.send(...)를 부르면 그 열린 응답에 조각이 추가된다.

리액티브 스택(Flux<ServerSentEvent>) — 하트비트까지 스트림으로 합친다

@GetMapping(value = "/api/notifications/stream",
            produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<ServerSentEvent<NotificationPayload>> stream(@AuthenticationPrincipal Long userId) {

    Flux<ServerSentEvent<NotificationPayload>> events =
        notificationSink.asFlux()
            .filter(e -> e.userId().equals(userId))
            .map(e -> ServerSentEvent.<NotificationPayload>builder()
                    .id(String.valueOf(e.seq()))
                    .event("notification")
                    .data(e.payload())
                    .build());

    // 하트비트. 이벤트가 없어도 15초마다 주석 라인(": ping")을 흘려
    // 경로상의 유휴 타이머를 리셋한다 (7절). comment()는 data 없는
    // 주석 이벤트를 만드는 것이라 클라이언트 코드는 이것을 보지 못한다.
    Flux<ServerSentEvent<NotificationPayload>> heartbeat =
        Flux.interval(Duration.ofSeconds(15))
            .map(i -> ServerSentEvent.<NotificationPayload>builder()
                    .comment("ping")
                    .build());

    return Flux.merge(events, heartbeat);
}

4-4. SSE의 대가 셋

① 단방향이다
클라이언트가 서버로 보내려면 별도의 일반 HTTP 요청을 써야 한다. 다만 이것이 항상 단점은 아니다 — 읽음 처리 정도의 간헐적 요청은 POST /api/notifications/42/read 한 방이 웹소켓 위에 자체 메시지 규약을 만드는 것보다 단순하다.
② 텍스트 기반이다
UTF-8 텍스트 줄들의 나열이라 이진 데이터를 그대로 실을 수 없다. 굳이 보내려면 Base64로 인코딩해야 하는데 크기가 약 1.33배로 늘어난다.
③ HTTP/1.1에서 연결 수 제한
브라우저의 호스트당 동시 연결 수 제한(보통 6개) 중 하나를 SSE가 영구 점유한다. 탭을 여러 개 열면 새 요청이 줄을 선다. HTTP/2에서는 사실상 사라진다 — 멀티플렉싱 덕에 연결 하나가 아니라 스트림 하나만 쓰기 때문.
그래서 실무 권고가 나온다 — "SSE를 쓸 거면 HTTP/2를 켜라"

5. 웹소켓 — 101 이후는 HTTP가 아니다

프로토콜 업그레이드(protocol upgrade)는 HTTP가 스스로를 위해 마련해 둔 탈출구다. "지금 맺어져 있는 이 TCP 연결을 유지한 채, 이 위에서 말하는 규약만 다른 것으로 바꾸자"고 합의하는 절차다. 연결을 새로 맺는 것이 아니라 이미 맺어진 연결의 용도를 바꾸는 것이 핵심이다.

왜 이런 방식을 택했나 — 방화벽을 통과하기 위해서다 웹소켓 전용 포트를 새로 뚫는 방법도 있었지만, 그러면 회사 방화벽과 프록시가 그 포트를 막아둔 환경에서 아예 못 쓴다. 80/443 포트에 HTTP로 들어가서 안에서 갈아타면 기존 인프라를 그대로 통과할 수 있다 — 적어도 이론상으로는. 실제로는 7절·8절의 문제가 남는다.

5-3. 프레임 — 회선 위에 쓰는 단위

101 이후로 오가는 것은 프레임(frame)이다. HTTP/2의 프레임과 같은 발상이다 — 가변 길이 데이터에 길이와 종류를 붙여 "여기부터 여기까지가 한 조각"을 정한다. 실무에서 알아야 할 것은 셋이다.

opcode (연산 부호)
이 프레임이 무엇인지 나타내는 번호. 텍스트 / 이진 메시지, 그리고 제어 프레임인 ping · pong · close. ping/pong이 프로토콜에 내장돼 있다는 점이 SSE와의 결정적 차이 — SSE는 하트비트를 주석 라인이라는 편법으로 흉내 낸다.
FIN 비트
큰 메시지를 여러 프레임으로 쪼개 보낼 수 있는데, 마지막 조각인지를 표시한다.
masking (마스킹)
클라이언트→서버 프레임은 반드시 32비트 난수 키로 페이로드를 XOR 마스킹한다. 암호화가 아니다(키가 프레임 안에 그대로 있다). 목적은 낡은 캐시 프록시를 속이는 공격 차단 — 마스킹이 없으면 프레임 안에 HTTP 요청처럼 생긴 바이트열을 심어 프록시가 별개 요청으로 오인하게 만들 수 있었다. 서버→클라이언트 방향은 마스킹하지 않는다.

웹소켓이 얻는 것

  • 진짜 양방향. 채팅에서 "내가 보낸 메시지"와 "상대가 보낸 메시지"가 같은 연결 위를 반대 방향으로 흐른다.
  • 메시지 하나당 오버헤드가 작다. HTTP 요청은 매번 헤더 수백 바이트~수 KB(쿠키, User-Agent, Accept)를 끌고 다니지만 웹소켓 프레임 헤더는 몇 바이트다.
  • 그래서 본령은 "작고 잦은" 트래픽 — 협업 편집기의 커서 위치, 실시간 호가, 게임 조작 입력.

웹소켓이 치르는 대가 셋

  • ① HTTP가 아니게 되는 순간부터 인프라 비용이 시작된다. LB·프록시 설정, L7 기능 상실, 별도 관측 수단.
  • ② 재연결과 유실 복구가 표준에 없다. WebSocket API는 끊기면 onclose를 부르고 끝. 우리가 만들 것이 최소 넷 — 끊김 감지, 지수 백오프+지터 재연결(11절), "어디까지 받았는지" 알리는 자체 프로토콜 메시지, 서버 재전송 로직.
  • ③ 서버가 stateful이 된다. 커넥션 목록이 인스턴스 메모리에 있으므로 아무 인스턴스나 껐다 켤 수 없고, scale-out하면 9절의 분산 문제가 생긴다.

6. 선택 기준 — 세 질문과 대조표

기술 스펙을 비교해서 고르는 것이 아니다. 질문을 순서대로 던져 내려가면 답이 나오는 구조다. 그리고 이 순서에서 가장 중요한 것은 첫 질문이다 — 그것을 건너뛰면 나머지 판단이 전부 무의미해진다.

판단 3문은 순서까지 외운다 — 초 → 방 → 빈

Q1 초 — 몇 초인가?→ Q2 방 — 어느 방향인가?→ Q3 빈 — 역방향이 얼마나 빈번한가?

면접에서 "먼저 요구되는 실시간이 실제로 몇 초인지 되묻겠습니다"로 답을 시작하면, 그 자체가 "요구사항을 구현 비용으로 번역할 줄 아는 사람"이라는 신호가 된다. 순서를 거꾸로 가면(웹소켓부터 검토) 이 신호가 사라진다.

6-1. Q1 — "실시간"이라는 말이 실제로 몇 초를 뜻하는가

"실시간 알림이 필요하다"는 요구는 기획서에 자주 등장하지만, 그 문장 안에 허용 지연이 적혀 있는 경우는 거의 없다. 그리고 파고들어 보면 요구되는 지연이 훨씬 느슨한 경우가 많다.

3초 폴링으로 충분한 요구에 웹소켓을 쓰면 무엇을 새로 지불하는가
프록시·LB 업그레이드 설정하트비트 설계재연결·백오프 클라이언트 코드유실 복구 프로토콜scale-out용 백플레인배포 시 커넥션 드레인 절차HTTP 지표로 안 보이는 트래픽의 별도 관측
얻는 것은 "지연 3초가 지연 0.1초가 되는 것" 하나뿐인데, 사용자는 그 차이를 인지하지도 못한다.

6-2. Q2 — 데이터가 어느 방향으로 흐르는가

Q1을 통과했다면(수 초 이내가 정말 필요하다면) 다음 질문은 방향이다. 서버가 밀어주기만 하면 되는 것이 압도적으로 많다 — 알림 스트림, 작업 진행률, 대시보드 지표 갱신, 새 댓글 스트림, 경매 현재가 표시, 배포 로그 tail. 이 전부가 SSE로 충분하다.

단방향 요구에 웹소켓을 쓰면 기능은 그대로인데 만들 것만 늘어난다 — 대가는 다 내고, 유일한 추가 능력은 안 쓰며, SSE가 공짜로 주던 자동 재연결·Last-Event-ID 복구까지 스스로 만들어야 한다

6-3. Q3 — 역방향이 정말 고빈도인가

"클라이언트도 뭔가 보내야 하는데요"라는 반문이 여기서 나온다. 그때 물을 것은 빈도다.

간헐적 — 사용자가 클릭할 때 한 번 (분당 몇 건)

  • 알림 읽음 처리 · 대시보드 필터 변경 · 구독 대상 변경
  • → 평범한 POST /api/notifications/42/read 한 방이 훨씬 단순하다.
  • HTTP API는 이미 인증·로깅·에러 처리·재시도·모니터링이 다 갖춰져 있는 길이고, 웹소켓 메시지는 그 전부를 새로 만드는 길이다.

고빈도 — 역방향 메시지가 초 단위로 계속 나간다

  • 채팅 · 협업 편집(커서 위치, 편집 조작) · 실시간 게임 · 실시간 호가 입력

7-1. 왜 끊는가 — 중간 장비 입장에서는 합리적인 규칙이다

경로상의 모든 중간 장비 — 클라우드 LB, Nginx, 회사 방화벽, NAT 게이트웨이 — 는 유휴(idle) 타임아웃을 갖고 있다. "이 커넥션으로 아무 바이트도 안 오간 지 N초가 지났으면 죽은 것으로 보고 정리한다"는 규칙이다.

이 규칙 자체는 합리적이다. 중간 장비는 커넥션마다 상태(NAT 매핑 테이블 항목, 프록시 버퍼)를 들고 있는데, 클라이언트가 노트북을 덮거나 지하철에서 신호가 끊기면 FIN이 오지 않은 채 그냥 사라진다. 그런 유령 커넥션을 청소하지 않으면 테이블이 가득 찬다. 그래서 시간으로 끊는다.

문제는 정상적인 SSE·웹소켓 커넥션이 이 규칙에 걸린다는 것 알림 서비스에서 이벤트가 5분 동안 없는 것은 지극히 정상인데, 중간 장비 입장에서는 5분 동안 조용한 커넥션과 죽은 커넥션이 구분되지 않는다. 
Nginx의 proxy_read_timeout 기본값 = 60초

t =   0s   웹소켓 핸드셰이크 성공, 채팅방 입장
t =  10s   메시지 몇 개 오감
t =  70s   조용한 채팅방. 60초간 무통신.

t =  70s   브라우저: onclose 발생. 사용자는 아무것도 안 했는데 연결이 끊겼다.

증상이 두 얼굴로 나타난다 계층 하나만 관여하면 "1분쯤 가만히 두면 연결이 끊긴다"는 재현 가능한 패턴으로 보이고, 계층마다 값이 다르면 "간헐적으로 끊긴다"는 유령 현상으로 보인다. 후자가 훨씬 흔하고, 그래서 앱 코드를 파다가 시간을 다 쓴다.

7-2. 대응① 하트비트로 커넥션을 살려둔다

하트비트(heartbeat, 심장 박동)는 보낼 데이터가 없어도 주기적으로 의미 없는 바이트를 흘려 "나 살아 있다"를 알리는 기법이다. 중간 장비의 유휴 타이머는 바이트가 오가면 리셋되므로, 주기적으로 뭔가를 흘리면 타이머가 만료에 도달하지 못한다.

SSE 주석 라인을 쓴다 — 클라이언트가 무시하므로 앱 로직에 영향이 없다
@Scheduled(fixedRate = 15_000)
public void heartbeat() {
    for (SseEmitter emitter : registry.all()) {
        try {
            // comment()는 ": ping\n\n"을 내보낸다. 클라이언트는 이것을 보지 못하지만
            // 경로상의 모든 중간 장비의 유휴 타이머는 이 바이트로 리셋된다.
            emitter.send(SseEmitter.event().comment("ping"));
        } catch (IOException e) {
            // ★ 하트비트의 두 번째 값: 죽은 커넥션이 여기서 드러난다.
            //   보내보기 전에는 커넥션이 살았는지 알 방법이 없다.
            emitter.completeWithError(e);
        }
    }
}
웹소켓 ping/pong 제어 프레임 — 프로토콜에 내장돼 있어 앱 메시지와 섞이지 않는다
@Scheduled(fixedRate = 20_000)
public void ping() {
    ByteBuffer payload = ByteBuffer.wrap(new byte[0]);
    for (WebSocketSession session : sessionRegistry.all()) {
        if (!session.isOpen()) { sessionRegistry.remove(session); continue; }
        try {
            session.sendMessage(new PingMessage(payload));
            // 상대가 pong을 돌려주지 않으면 그 커넥션은 죽은 것이다.
            // pong 수신 시각을 기록해두고, 일정 시간 이상 pong이 없으면
            // 서버가 먼저 세션을 닫아 좀비 커넥션을 정리한다.
        } catch (IOException e) {
            sessionRegistry.remove(session);
        }
    }
}
STOMP 프레임워크가 대신 해준다 — 단, 스케줄러를 안 주면 동작하지 않는다
@Override
public void configureMessageBroker(MessageBrokerRegistry registry) {
    registry.enableSimpleBroker("/topic")
            // {서버가 보내는 주기, 서버가 클라이언트에게 기대하는 주기} 밀리초.
            // 양쪽 모두 지정해야 어느 방향으로도 유휴가 생기지 않는다.
            .setHeartbeatValue(new long[]{15_000, 15_000})
            // 하트비트를 흘릴 스케줄러. 지정하지 않으면 하트비트가 동작하지 않는다.
            .setTaskScheduler(heartbeatScheduler());
}

8. 함정② 프록시 버퍼링이 SSE를 무력화한다

먼저 — 버퍼링은 원래 좋은 기본값이다 Nginx는 기본적으로 업스트림(뒤쪽 서버) 응답을 버퍼에 모았다가 클라이언트에게 내려보낸다(proxy_buffering on이 기본값). 이유가 있다 — 느린 클라이언트가 응답을 다 받을 때까지 Tomcat 스레드가 붙들려 있는 것을 막아주기 때문이다. Tomcat은 빠른 로컬 네트워크로 Nginx에게 응답을 던지고 즉시 스레드를 놓아주고, 느린 클라이언트를 상대하는 일은 Nginx가 맡는다. (12-nginx-roles-and-event-driven-architecture.md 2절)
그런데 SSE의 존재 이유는 "조각을 생기는 즉시 흘리는 것"이고, 버퍼링은 정확히 그 반대인 "조각을 모았다가 한꺼번에 흘리는 것"이다 — 목적이 정면으로 충돌한다

8-1. 대응 — 두 가지 방법 중 하나면 된다

방법 ① 인프라 설정 — 실시간 경로만 끈다
location /api/notifications/stream {
    proxy_pass http://app;
    proxy_buffering off;   # 받는 즉시 클라이언트로
    proxy_cache off;       # 캐시가 스트림을 저장하는 사고도 막는다
    proxy_read_timeout 3600s;
    proxy_http_version 1.1; # 청크 전송은 1.1이 필요
}
방법 ② 앱이 응답 헤더로 선언한다
@GetMapping(value = "/api/notifications/stream",
            produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public ResponseEntity<SseEmitter> subscribe(...) {
    return ResponseEntity.ok()
            // Nginx가 이 헤더를 보면 "해당 응답만" 버퍼링을 끈다.
            // 인프라 팀에 설정 변경을 요청하지 않아도 되므로 협업 비용이 낮다.
            .header("X-Accel-Buffering", "no")
            .header("Cache-Control", "no-cache")
            .body(emitter);
}

전역 proxy_buffering off는 금지 — 그리고 압축도 같은 이유로 끈다

전역 해제는 모든 응답에서 "느린 클라이언트 격리" 효과를 버리는 것이고, Tomcat 스레드가 전송 속도에 묶이게 만든다. 반드시 경로 단위로 한다.

같은 이유로 응답 압축(gzip)도 실시간 경로에서는 주의 대상이다. 압축기는 효율을 위해 입력을 일정량 모았다가 압축하므로 그 자체가 또 하나의 버퍼가 된다. 이벤트마다 압축 스트림을 플러시하면 압축률이 크게 떨어져 얻는 것이 별로 없다 — 실시간 경로는 압축을 끄는 것이 보통이다. (21-response-compression-tradeoffs.md와 같은 판단 축)

9. 함정③ scale-out하는 순간 "누구에게 보낼지"가 분산 문제가 된다 시니어 변별

서버가 1대일 때는 아무 문제가 없다. 사용자 A의 커넥션이 그 서버의 메모리에 있고 이벤트도 그 서버에서 발생하므로 registry.get(userId).send(...) 한 줄이면 끝난다. 서버가 3대가 되는 순간 이 가정이 깨진다.

            // 이 인스턴스에 해당 사용자의 커넥션이 있는지 확인하지 않는다.
            // 확인하려면 "누가 어디 붙어 있는지"라는 또 하나의 분산 상태가
            // 필요해지고, 그 상태는 커넥션이 끊길 때마다 갱신돼야 한다.
            // 그냥 전부에게 뿌리는 편이 훨씬 단순하다.
            redis.convertAndSend("notifications",
                                 mapper.writeValueAsString(event));
        } catch (JsonProcessingException e) {
            throw new IllegalStateException("이벤트 직렬화 실패", e);
        }
    }
}

9-1. Redis Pub/Sub의 성질과 한계 — 그리고 "유실돼도 되게 만들기"

장점 — fire-and-forget의 단순함

  • 극단적으로 단순하고 빠르다. 저장하지 않으므로 디스크도 안 쓰고, 컨슈머 그룹·오프셋 관리 개념이 아예 없다.
  • Redis를 이미 쓰고 있다면 추가 인프라가 0이다.

한계 — 발행한 메시지를 저장하지 않는다

  • 인스턴스가 잠깐이라도 Redis와 끊겨 있으면 그동안 발행된 메시지를 영영 못 받는다.
  • 재시작 중인 인스턴스, 네트워크 순단, Redis 페일오버 순간이 전부 유실 구간이다.
  • 그런데 알림 그 자체는 유실되면 안 되는 데이터인 경우가 많다.

실무의 정석 — 두 경로를 분리한다

영속
이벤트 발생 → DB에 알림 레코드 INSERT — 진실의 원천(source of truth). 사용자가 새로고침하거나 재연결하면 여기서 조회해 복구된다. Last-Event-ID 재전송의 데이터 출처도 이 DB다.
전파
Redis PUBLISH → 붙어 있는 커넥션에 즉시 전달 — 편의(빠르게 보이게 하는 수단). 전파가 유실돼도 알림 자체는 DB에 남아 있다.
"Pub/Sub이 유실되면 어쩌나"의 답은 "유실돼도 되게 만든다" — Redis Pub/Sub은 전달을 보장하는 수단이 아니라 빠르게 보이게 하는 수단이다

9-2. 브로커 릴레이 — 전달 보장이 필요할 때, 그리고 여기에 함정이 하나 있다

유실을 감당할 수 없거나 인스턴스 수가 많아 Redis 채널의 팬아웃 부하가 부담이면, 메시지 브로커를 백플레인으로 쓴다. 이때 평소에 쓰는 작업 큐 구성 — 큐 하나에 컨슈머 여러 개 — 을 그대로 쓰면 틀린다.

10. 함정④ 커넥션마다 스레드를 물면 안 된다

Tomcat 같은 전통적 서블릿 컨테이너는 요청 하나에 워커 스레드 하나를 배정한다. 요청이 짧으면 이 모델이 훌륭하게 동작한다 — 스레드가 빠르게 회전하므로 200개짜리 풀로 초당 수천 건을 처리한다. 장수 커넥션은 이 전제를 정면으로 깬다.

10-1. 비동기로 바꿔도 남는 블로킹 지점이 하나 있다

emitter.send() 자체가 블로킹 쓰기다 클라이언트가 느리거나(모바일 3G) 데이터를 안 읽고 있으면 소켓 송신 버퍼가 차고, 그러면 send()를 호출한 스레드가 그 자리에서 멈춘다. 7절의 하트비트 스케줄러가 이 상황을 만나면 — 커넥션 하나 때문에 전체 하트비트 루프가 멈춰 나머지 커넥션이 전부 유휴 타임아웃으로 끊기는 연쇄가 생긴다.
대응 — 전송을 별도의 제한된 스레드 풀에서 하고, 그 풀이 포화되면 해당 커넥션을 버린다(느린 소비자를 끊는다). 이것이 백프레셔의 한 형태다

10-2. WebFlux/Netty가 이 영역에서 유리한 진짜 이유

리액티브 스택이 유리한 이유는 "비동기라서"가 아니라 쓰기까지 논블로킹이기 때문이다. Netty는 Nginx와 같은 이벤트 루프 모델을 쓴다 — 적은 수의 스레드(보통 CPU 코어 수)가 커널의 이벤트 통지(리눅스의 epoll)에 "이 소켓들 중 뭔가 읽거나 쓸 수 있게 되면 알려줘"라고 등록해 두고, 준비된 소켓만 처리하고 즉시 다음으로 넘어간다. 소켓이 아직 쓸 준비가 안 됐으면 기다리지 않고 다른 일을 하러 간다 — 이것이 블로킹 쓰기와의 결정적 차이다.

거기에 리액티브 스트림의 백프레셔가 얹힌다. Flux는 구독자가 "몇 개까지 받을 수 있다"를 요청(request)하는 구조라, 느린 클라이언트에게는 자연스럽게 덜 흘려보낸다. 서블릿 스택에서 직접 만들어야 했던 느린 소비자 방어가 프로그래밍 모델 안에 들어 있는 셈이다.

정직하게 짚을 것 — 이벤트 루프의 급소도 똑같이 적용된다 루프 안에서 블로킹 호출(JDBC 같은 블로킹 드라이버, 무거운 CPU 연산)을 하면 그 루프가 담당한 모든 커넥션이 멈춘다. 그래서 WebFlux로 갈아탄다는 것은 실시간 계층뿐 아니라 그 아래 데이터 접근까지 논블로킹으로 맞춰야 한다는 뜻이고, 작은 결정이 아니다.

현실적인 결론 — 규모로 갈라 말한다

수백~수천 커넥션

11. 함정⑤ L4 LB의 부하 편중과 재연결 폭풍 가산점

L4 로드밸런서는 커넥션 단위로 분배한다. 클라이언트가 TCP 연결을 맺을 때 백엔드 하나를 고르고, 이후 그 커넥션의 모든 패킷은 계속 그 서버로 간다. 짧은 요청에서는 이것이 훌륭하게 동작한다 — 커넥션이 초당 수천 개씩 새로 맺어지고 끊어지므로 분배가 계속 다시 일어나면서 자연스럽게 고르게 퍼진다.

장수 커넥션에서는 이 자정 작용이 사라진다 — 분배는 "지금 이 순간의 배정"이 아니라 "과거의 배정이 누적된 결과"가 된다

대응 셋 — 전부 "커넥션은 상태다"라는 인식에서 나온다

1
커넥션에 최대 수명을 준다. 서버가 일정 시간(예: 30~60분)마다 커넥션을 정상 종료하면 클라이언트가 재연결하면서 LB의 분배를 다시 받는다. SSE라면 EventSource가 자동 재연결하므로 사용자 경험에 영향이 없다. "강제로 섞어주는" 장치인 셈 — 4절에서 SseEmitter 타임아웃을 30분으로 준 것에는 이 의미도 있다.
2
재연결에 지수 백오프 + 지터를 넣는다. 그리고 SSE라면 한 수 더 있다 — retry: 필드로 서버가 재연결 간격을 조종할 수 있으므로, 서버가 과부하면 retry 값을 크게 실어 보내 클라이언트들이 천천히 돌아오게 만든다.
3
배포는 커넥션을 서서히 빼는(drain) 방식으로. 인스턴스를 즉시 죽이는 대신 먼저 LB 분배 대상에서 제외해 새 커넥션을 안 받게 하고, 기존 커넥션은 순차적으로 종료하며 클라이언트가 재연결할 시간을 준다.
커넥션 = 서버가 들고 있는 상태 → 무상태 서버처럼 막 껐다 켤 수 없다

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

셋의 차이를 한 문장으로?
HTTP가 서버 푸시를 못 하니 답이 셋뿐 — 계속 물어보거나(폴링) 응답 하나를 안 끝내거나(SSE) HTTP를 버리거나(웹소켓).
판단 3문의 순서?
초 → 방 → 빈. ①몇 초인가(수십 초면 폴링에서 끝) ②어느 방향인가(단방향이면 SSE) ③역방향이 고빈도인가(간헐적이면 SSE+POST).
폴링 비용 계산식 두 줄?
초당 요청 = 동접 ÷ 주기, 총비용 = 그것 × 조회 1건 비용. 10만 명 / 3초 ≈ 33,333 req/s. "폴링이 비싸다"가 아니라 "주기 × 조회 비용이 감당 가능한가".
SSE 포맷 다섯 줄과 끝 표시?
본문·이름·번호·간격·주석 = data/event/id/retry/:. 그리고 빈 줄 하나가 이벤트 하나의 끝(\n\n).
EventSource가 공짜로 주는 것 / 우리 몫?
공짜: 끊김 감지 · 재연결 · 마지막 id 기억 · Last-Event-ID 첨부. 우리 몫: 그 id 이후 이벤트를 보관하는 저장소와 재전송 — 복구의 프로토콜은 주지만 복구의 데이터는 안 준다.
101의 의미 한 문장?
이 응답 이후의 모든 바이트는 HTTP가 아니다. 그래서 경로 라우팅·요청 로그·상태코드 지표·WAF가 전부 적용되지 않고, 이해 못 하는 중간 장비는 연결을 끊는다.
인프라 비용 다섯 가지?
타·버·백·스·편 — 유휴 타임아웃, 프록시 버퍼링, 백플레인, 스레드 점유(스), 부하 편중.
하트비트 주기 규칙과 근거?
경로상 가장 짧은 유휴 상한의 절반 이하. 근거는 한 번 유실되면 간격이 2주기로 벌어지기 때문 — 55초 주기·60초 상한은 한 번만 밀려도 110초가 되어 끊긴다.
scale-out 시 생기는 문제 셋?
①메시지 라우팅(알림이 조용히 사라진다) ②재연결 폭풍(백오프+지터, 드레인) ③L4 부하 편중(커넥션 최대 수명). 하나만 말하면 절반의 답.
Nginx 웹소켓 설정 세 줄 세트?
proxy_http_version 1.1 + Upgrade + Connection — 버전 줄이 세트의 일부다. Nginx는 업스트림에 기본 HTTP/1.0으로 말하므로 그 줄이 없으면 나머지 둘도 소용없다.
Redis Pub/Sub의 한계와 대응?
fire-and-forget — 잠깐 끊긴 구간은 영영 못 받는다. 대응은 "유실 없애기"가 아니라 "유실돼도 되게 만들기" = 영속 경로(DB) + 전파 경로(Pub/Sub) 분리.
RabbitMQ 백플레인의 함정?
큐 하나 + 컨슈머 여럿은 일감 나누기라 틀린다. 백플레인은 같은 소식 뿌리기 → 팬아웃 익스체인지 + 인스턴스별 전용 임시 큐.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

SSE가 웹소켓보다 나은 경우는 언제인가요? 필수힌트: 이유 둘 다 "기능이 필요 없는데 비용을 낼 이유가 없다"로 수렴한다. 그리고 반대 경우까지 말하면 한 칸 더 간다

데이터가 서버→클라이언트 단방향일 때다. 알림 스트림, 작업 진행률, 대시보드 갱신, 배포 로그 tail이 대표적이다.

첫째, 여전히 HTTP다. 응답 본문이 끝나지 않을 뿐 요청-응답의 형태를 지키므로 인증 헤더·쿠키·CORS·접근 로그·경로 기반 라우팅 같은 기존 HTTP 인프라가 그대로 적용된다. 웹소켓은 101 이후로 HTTP가 아니게 되므로 이 전부를 다시 고민해야 한다.

둘째, 재연결과 유실 복구가 표준에 들어 있다. EventSource가 끊기면 자동 재연결하고 마지막 id:를 Last-Event-ID로 되돌려준다. 웹소켓이라면 끊김 감지, 백오프 재연결, 수신 위치 추적, 서버로의 위치 전달 프로토콜을 전부 직접 만들어야 한다.

정직하게 덧붙일 것: 서버 쪽 재전송(그 id 이후 이벤트를 실제로 갖고 있다가 다시 보내는 것)은 SSE에서도 우리 몫이다 — 표준이 주는 것은 복구의 프로토콜이지 복구의 데이터가 아니다.

클라이언트→서버 방향의 간헐적 요청은 일반 HTTP API로 보내면 된다. 읽음 처리·필터 변경·구독 변경은 분당 몇 건 수준이므로 평범한 POST 한 방이 훨씬 단순하다. 양방향이 조금 필요하다고 바로 웹소켓으로 갈 이유는 없다.

① 메시지 라우팅 — 커넥션이 붙은 인스턴스와 이벤트가 발생한 인스턴스가 어긋난다. A의 커넥션은 인스턴스 1에 있는데 A에 대한 이벤트는 인스턴스 2에서 발생하고, 인스턴스 2는 A를 모르므로 알림이 조용히 사라진다. 에러도 안 나고 로그에도 안 남는다는 점이 고약하다.

그리고 Redis Pub/Sub은 fire-and-forget이라 인스턴스가 잠깐 끊겨 있으면 그 구간을 영영 못 받는다는 한계까지 말할 수 있어야 한다. 대응은 "유실을 없애기"가 아니라 "유실돼도 되게 만들기"다 — 알림 자체는 DB에 남기고(영속 경로), Pub/Sub은 빠르게 보이게 하는 수단(전파 경로)으로만 쓴다. 재연결 시 Last-Event-ID로 복구되면 유실 구간이 자동으로 메워진다.

② 재배포·장애 시 재연결 폭풍 — 인스턴스 하나를 내리면 그 인스턴스의 수천~수만 커넥션이 동시에 끊기고 일제히 재연결한다. 순간적인 핸드셰이크 폭주가 남은 인스턴스를 때리고, 그것이 다시 넘어가면 연쇄 장애가 된다. 대응은 지수 백오프 + 지터와 배포 시 커넥션 드레인.

③ L4 LB의 부하 편중 — 커넥션 단위 분배 + 긴 커넥션 수명이 겹치면 스케일 아웃해도 새 인스턴스가 비어 있다. 기존 커넥션은 옮겨갈 방법이 없기 때문이다. 대응은 커넥션에 최대 수명을 줘서 주기적으로 재분배를 유도하는 것.

단점이 명확하다. 서버가 보류 중인 요청을 계속 물고 있어야 하므로 장수 커넥션 문제를 그대로 물려받는다 — 비동기 처리가 아니면 스레드를 잠식하고(10절), 중간 계층 유휴 타임아웃에 걸리며(그래서 보류 상한을 타임아웃보다 짧게 잡아야 한다), 커넥션 상태 관리가 필요하다. 사실상 장수 커넥션의 부담은 다 지면서 진짜 푸시의 효율은 못 얻는 중간 형태다.

그래서 결론은 "신규 설계에서 1순위로 고를 이유는 적지만, 폴백 계층으로서의 값은 여전히 있다"이다. 환경 제약이 확인되지 않은 상태에서 웹소켓 하나에 전부를 걸기보다, SSE를 기본으로 하고 실패 시 롱 폴링으로 내려가는 단계적 저하를 설계에 넣는 것이 안전하다.

① 웹소켓의 업그레이드 통과. 프록시가 Upgrade와 Connection 헤더를 업스트림으로 전달하도록 명시해야 한다. 이 헤더들은 홉 단위(hop-by-hop) 헤더 — 다음 중계 지점까지만 유효하고 그 너머로 자동 전달되지 않는 헤더 — 라서, 명시하지 않으면 프록시가 벗겨낸다. 그러면 업스트림은 평범한 GET을 받은 것으로 보고 101 대신 200이나 404를 돌려준다.

# 같은 location에 웹소켓이 아닌 요청이 들어올 수 있기 때문이다.
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

location /ws/ {
    proxy_pass http://app;

    # 업그레이드는 HTTP/1.1의 기능이다. Nginx는 업스트림에 기본적으로 HTTP/1.0으로
    # 말하므로, 이 줄이 없으면 아래 두 줄을 넣어도 업그레이드가 성립하지 않는다.
    proxy_http_version 1.1;
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection $connection_upgrade;

55초 주기 / 60초 상한으로 계산해 보면 바로 드러난다. 0초에 보내고 55초에 보내면 간격 55초로 안전하다. 그런데 55초 것이 한 번 밀리면 다음은 110초이므로 실제 무통신 간격이 110초가 되고, 60초 지점에서 끊긴다. 주기가 상한보다 짧았는데도 끊기는 것이다.

15초 주기 / 60초 상한이면 한 번 밀려도 간격은 30초라 여유가 남는다. 그래서 "상한의 절반 이하"가 실무 기준이 된다.

밀리는 이유는 실제로 흔하다 — 스케줄러 스레드 지연, GC 정지, 스레드 풀 대기, 그리고 10절에서 본 느린 클라이언트 하나가 send()에서 블로킹돼 하트비트 루프 전체를 멈추는 경우. 마지막 것은 커넥션 하나 때문에 나머지 전부가 유휴 타임아웃으로 끊기는 형태라 특히 나쁘다.

한 칸 더 간다면 — 경로상 가장 짧은 상한을 실제로 아는지가 관건이다. 클라우드 LB, Nginx, 방화벽·NAT의 세션 타임아웃 중 하나만 놓쳐도 그것이 실질 상한이 된다. "가장 짧은 값을 모른 채 하트비트 주기를 정하는 것은 추측"이라고 말하면 좋다.

서버는 그 웹소켓 커넥션이 살아 있는지 어떻게 아나요?힌트: TCP는 상대가 사라진 것을 알려주지 않을 수 있다

보내보기 전에는 알 수 없다. 이것이 출발점이다. 정상 종료라면 FIN이 오므로 서버가 알지만, 클라이언트가 노트북을 덮거나 지하철에서 신호가 끊기면 FIN이 오지 않은 채 그냥 사라진다. 서버 입장에서 그 소켓은 여전히 열려 있는 것처럼 보인다 — 이것이 좀비 커넥션이다.

그래서 하트비트에는 두 번째 값이 있다. 첫 번째 값이 "중간 장비의 유휴 타이머 리셋"이라면, 두 번째 값은 "죽은 커넥션을 드러내는 것"이다. ping을 보냈을 때 IOException이 나거나 pong이 돌아오지 않으면 그 커넥션은 죽은 것이다.

구체적인 정리 절차는 이렇다 — pong 수신 시각을 세션마다 기록해 두고, 일정 시간 이상 pong이 없으면 서버가 먼저 세션을 닫는다. SSE라면 pong이 없으므로 주석 전송 시 예외가 나는 것이 유일한 신호이고, 그래서 emitter.completeWithError()로 레지스트리에서 정리한다.

정리를 안 하면 무슨 일이 생기는지까지 말하면 완성된다 — 끊긴 커넥션의 emitter/세션이 레지스트리에 남아 ①메모리 누수, ②이벤트마다 죽은 커넥션에 전송을 시도하며 예외를 만드는 비용이 생긴다. 그래서 4절 코드에서 onCompletion·onTimeout·onError 세 훅을 전부 거는 것이다.

Last-Event-ID가 있으면 유실이 없는 건가요? 함정힌트: 표준이 주는 것과 우리가 만들어야 하는 것의 경계를 그어야 한다

아니다. 표준이 주는 것은 "복구의 프로토콜"이지 "복구의 데이터"가 아니다. 브라우저가 Last-Event-ID: 42를 보내줘도, 서버가 "42 이후의 이벤트"를 실제로 갖고 있지 않으면 되돌려줄 것이 없다. 이벤트를 메모리에서 만들어 쏘고 버리는 구현이라면 헤더는 그냥 버려지고 유실은 그대로 남는다.

그래서 필요한 것이 이벤트 보관소다. 설계할 때 정할 것이 셋이다.

보관 범위
사용자별로 최근 N건 또는 N분. 무한 보관은 불가능하므로 상한을 정한다.
상한을 넘겼을 때
"그 사이를 다 재생할 수 없다"는 상황이 생긴다 → 클라이언트에게 전체 새로고침을 지시하는 경로가 필요하다.
id 채번
사용자별로 단조 증가해야 "이후"라는 비교가 성립한다. 인스턴스마다 따로 매기면 비교가 깨진다.

9절의 영속/전파 분리와 이어 붙이면 그림이 완성된다 — 알림 자체는 DB에 INSERT(진실의 원천)하고 Redis Pub/Sub은 즉시 보여주기 위한 편의로만 쓴다. 그러면 Last-Event-ID 재전송의 데이터 출처가 그 DB가 되므로, Pub/Sub 유실 구간이 재연결 시 자동으로 메워진다. 두 장치가 하나의 설계로 맞물리는 지점이다.

HTTP/2를 켜면 SSE의 단점이 다 없어지나요?힌트: 해소되는 것은 딱 하나다

해소되는 것은 "브라우저의 호스트당 동시 연결 수 제한(보통 6개)" 하나뿐이다. HTTP/2의 멀티플렉싱(하나의 물리 연결에 스트림 ID로 구분되는 여러 논리 통로를 겹쳐 싣는 기법) 덕에 SSE 스트림이 연결 하나가 아니라 스트림 하나만 쓰기 때문이다. 그래서 "SSE를 쓸 거면 HTTP/2를 켜라"는 권고가 나온다.

나머지는 그대로다. 단방향이라는 성질은 프로토콜 버전과 무관하고, 텍스트 포맷이라 이진 데이터를 못 싣는 것도 그대로다.

그리고 중간 계층 문제는 하나도 해결되지 않는다. 유휴 타임아웃(7절), 프록시 버퍼링(8절), scale-out 시 이벤트 전파(9절), 스레드 점유(10절), L4 부하 편중(11절)은 HTTP 버전이 아니라 "커넥션이 오래 산다"는 사실에서 나오는 비용이기 때문이다. 버전 업그레이드로 지워지는 비용과 지워지지 않는 비용을 구분해 말하는 것이 이 질문의 채점 포인트다.

실시간 알림을 넣었더니 "배포할 때마다 알림이 몇 개씩 사라진다"는 제보가 옵니다. 어디를 보시겠습니까? 시니어 변별힌트: 원인이 하나가 아니라 세 겹으로 쌓여 있다. 그리고 "배포할 때만"이라는 단서가 범위를 좁혀준다

"배포할 때만"이라는 단서가 결정적이다 — 배포는 커넥션이 대량으로 동시에 끊기는 유일한 정기 이벤트이기 때문이다. 원인은 세 겹으로 쌓여 있고, 셋을 다 짚어야 한다.

1
끊긴 구간의 이벤트가 아무에게도 안 갔다. 인스턴스가 내려가고 클라이언트가 재연결하기까지의 수 초~수십 초 동안 발생한 이벤트는 전달 대상이 없다. Redis Pub/Sub은 fire-and-forget이라 그 구간을 저장하지도 않는다.
2
재연결 후 재전송이 없다. 브라우저는 Last-Event-ID를 보내는데 서버가 그 헤더를 읽지 않거나, 읽어도 "그 이후 이벤트"를 갖고 있지 않으면 유실은 그대로 남는다.
3
재연결 폭풍이 겹치면 더 나빠진다. 수천 커넥션이 동시에 돌아오면서 남은 인스턴스가 흔들리고, 그 여파로 또 끊기는 2차 유실이 생긴다.

그래서 처방도 세 겹이다. ① 영속 경로 분리 — 알림을 DB에 먼저 INSERT하고 Pub/Sub은 전파용으로만 쓴다(전파가 유실돼도 데이터는 남는다). ② Last-Event-ID 재전송 구현 — 재연결 시 그 DB에서 "그 id 이후"를 조회해 다시 보낸다. ③ 배포 절차 개선 — LB 분배 대상에서 먼저 빼고(새 커넥션 차단) 기존 커넥션을 순차 종료(drain)하며, 클라이언트 재연결에는 지수 백오프 + 지터를 넣는다.

마무리 한 문장 — "실시간 전달은 '보장'이 아니라 '편의'로 설계하고, 보장은 영속 계층에 맡깁니다. 그러면 배포·장애로 커넥션이 끊기는 것이 데이터 유실이 아니라 화면 갱신 지연으로만 남습니다."

채팅을 만들라는 요구를 받았습니다. 바로 웹소켓으로 가도 되나요?힌트: 이 문서에서 유일하게 "웹소켓이 맞다"가 빠르게 나오는 케이스다. 그래도 되물을 것이 남아 있다

판단 3문을 그대로 통과하므로 웹소켓이 맞다. ①초: 1초를 넘으면 대화가 안 되므로 수 초 허용이 아니다. ②방: 내가 보내고 상대가 보내므로 양방향이 필수다. ③빈: 타이핑 표시·읽음 표시까지 포함하면 역방향이 초 단위로 계속 나간다. 세 관문을 다 통과하는 드문 케이스다.

그래도 되물을 것은 남아 있다. "채팅"이라는 말 안에 서로 다른 요구가 섞여 있기 때문이다 — 1:1 상담 채팅은 동시 접속이 상담사 수만큼이라 규모가 작고, 대규모 오픈 채팅은 한 메시지를 수천 명에게 팬아웃해야 해서 완전히 다른 설계가 된다. "동시 접속 규모와 한 메시지의 수신자 수"를 먼저 묻는 것이 맞다.

그리고 "웹소켓으로 간다"는 결정에는 인프라 비용 다섯이 자동으로 따라온다는 것을 같은 호흡에 말해야 한다 — 업그레이드 통과 설정, 하트비트(ping/pong), 백플레인(방을 여러 인스턴스가 나눠 갖게 되므로 필수), 스레드 모델, 배포 시 드레인. "웹소켓이 맞습니다"에서 끝내면 절반이고, "그래서 이것들을 준비해야 합니다"까지 가야 답이다.

한 가지 더 — 채팅에서도 메시지 자체는 DB에 저장되어야 한다. 웹소켓은 "지금 보고 있는 사람에게 즉시 보여주는 수단"이고, 과거 대화 조회·미접속자 알림·유실 복구는 전부 영속 계층의 일이다. 9절의 영속/전파 분리가 여기서도 그대로 적용된다.

한 줄 요약
폴링은 클라이언트가 반복해서 물어보는 보편·저비용 수단, SSE는 HTTP 응답을 끝내지 않고 서버가 data:/id:/retry: 줄을 이어 흘리며 EventSource의 자동 재연결과 Last-Event-ID 복구를 공짜로 얻는 단방향 푸시, 웹소켓은 101 Switching Protocols 이후 그 TCP 연결이 HTTP가 아니게 되는 양방향 전용선이다 — 선택은 "요구되는 실시간이 실제 몇 초인가"를 되묻는 데서 시작해 단방향이면 SSE, 역방향이 고빈도일 때만 웹소켓으로 올라가되, 장수 커넥션이 중간 계층 유휴 타임아웃(→ 하트비트를 가장 짧은 상한의 절반 이하로), 프록시 버퍼링(→ 경로 단위 해제), scale-out 시의 이벤트 전파(→ Redis Pub/Sub 또는 브로커 팬아웃 백플레인, 단 영속 경로와 분리), 커넥션당 스레드 점유(→ 비동기 서블릿 또는 이벤트 루프), L4 LB의 부하 편중(→ 커넥션 최대 수명과 드레인)이라는 인프라 비용을 동반한다는 것까지 계산에 넣는 판단이다.
