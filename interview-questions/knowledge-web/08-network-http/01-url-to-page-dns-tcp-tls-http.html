URL 입력 후 일어나는 일
요청이 지나는 전체 경로의 지도 — DNS → TCP → TLS → HTTP

면접 질문: "브라우저에 URL을 입력했을 때 일어나는 일을 설명해주세요. (DNS → TCP → TLS → HTTP)"

핵심 관전 포인트 — URL 입력부터 화면 표시까지는 4개의 큰 관문을 순서대로 통과한다: DNS 조회(도메인 이름 → IP 주소), TCP 3-way handshake(연결 수립), TLS handshake(암호화 채널 협상, HTTPS인 경우), HTTP 요청/응답(실제 데이터 교환). 이 관문들은 전부 네트워크 왕복(RTT)을 소모하며, 왕복 횟수는 서버 성능이나 대역폭으로 줄일 수 없다 — 물리적 거리가 정하는 값이기 때문이다. 그래서 본문이 1바이트여도 첫 요청은 DNS + TCP 1 RTT + TLS 1~2 RTT를 선불로 낸다. 그리고 각 관문은 실패할 때의 증상이 서로 다르다 — DNS는 UnknownHostException, TCP는 ConnectException이나 connect timeout, TLS는 SSLHandshakeException, HTTP는 상태 코드가 붙은 응답이나 read timeout이다. 결정적으로 TCP·TLS 단계의 실패는 애플리케이션 로그에 아무것도 남기지 않는다 — 요청이 내 코드에 도달하기 전에 반려됐기 때문이다. 이 지도를 갖고 있으면 "안 돼요"라는 장애 신고를 "어느 구간에서 실패했는가"로 분해할 수 있고, 개발자도구 Network 탭의 Timing이나 curl -w의 타이밍 출력이 그 분해를 그대로 숫자로 보여준다 — 모든 네트워크 디버깅과 성능 최적화의 밑그림이다.
  • 1
    브라우저가 하는 일은 결국 네 가지다 — 이름을 주소로 바꾸고(DNS), 그 주소로 회선을 뚫고(TCP), 회선을 암호로 감싸고(TLS), 그 위에 요청을 써 보낸다(HTTP). 순서가 고정된 이유는 뒤 단계가 앞 단계의 결과물 위에서만 성립하기 때문이다 — IP를 모르면 패킷을 어디로 보낼지 정할 수 없고, 연결이 없으면 암호화할 통로 자체가 없다.
  • 2
    이 직렬 구조가 곧 지연의 누적이고, 단위는 RTT다 — TCP 1 RTT + TLS 1~2 RTT가 본 요청을 보내기도 전에 나간다. RTT 110ms 경로에서 TLS 1.2면 준비에만 약 380ms다. RTT는 서버를 좋은 걸로 바꾸거나 대역폭을 늘려도 줄지 않으므로, 최적화는 왕복 횟수를 줄이거나(keep-alive·커넥션 풀) 왕복 거리를 줄이는(CDN) 둘 중 하나다.
  • 3
    그래서 이 지도는 성능뿐 아니라 장애 진단의 도구다 — 관문마다 실패 증상이 달라 증상만 보고 막힌 구간을 역추적할 수 있고, 특히 TCP·TLS 실패는 앱 로그에 남지 않으므로 "앱 로그에 그 요청이 없다"를 "요청이 안 왔다"가 아니라 "앞 구간에서 반려됐을 수 있다"로 읽어야 한다. 분해 도구는 DevTools Timing과 curl -w다.

0. 질문 + 출제 의도

질문: "브라우저에 URL을 입력했을 때 일어나는 일을 설명해주세요. (DNS → TCP → TLS → HTTP)"

출제 의도: 요청이 지나는 전체 경로의 지도를 갖고 있는지 보는 질문. 이 지도가 있어야 "어느 구간에서" 실패했는지 분해할 수 있다 — 모든 네트워크 디버깅의 밑그림이다.

이 페이지가 겨냥하는 약점 세 가지 ① 관문 이름만 순서대로 나열하는 것 → 1·2절에서 각 관문이 몇 RTT를 쓰는지를 숫자로 붙여, 나열이 아니라 비용이 붙은 지도로 만든다.
② "느리다"를 서버 처리 시간 문제로만 보는 것 → 2절에서 첫 요청 615ms 중 380ms가 요청을 보내기 전에 나간다는 것을 시간축으로 보여준다.
③ 장애 신고를 관문별로 못 쪼개는 것 → 9·10절에서 증상 → 관문 역추적 표와 curl -w 뺄셈 계산으로 "어느 구간의 실패인가"를 숫자로 답하는 법을 만든다.
한 문장 비유 — 전화를 거는 순서와 정확히 같다 전화번호부에서 번호를 찾고(DNS) → 전화를 걸어 상대가 받고 서로 목소리를 확인하고(TCP 3-way) → 도청을 막으려 암호 규칙과 상대 신원을 먼저 합의하고(TLS) → 그제서야 본론을 말한다(HTTP). 순서를 바꿀 수 없다는 것도 같다 — 번호를 모르면 걸 수 없고, 통화가 연결되지 않으면 암호 규칙을 정할 수도 없다.

1. 전제 지식 — RTT가 무엇이고 왜 줄일 수 없는가

이 문서 전체를 관통하는 단위가 하나 있다. RTT(round-trip time, 왕복 시간)는 내가 보낸 패킷이 상대에게 도착하고 그 응답이 나에게 돌아오기까지 걸리는 시간이다. "왕복"이라는 이름 그대로 편도가 아니라 갔다 오는 한 세트를 센다. 아래 모든 관문의 비용은 결국 "몇 RTT인가"로 환산된다.

RTT를 결정하는 것 ① 물리적 거리
신호는 광케이블 안에서 빛의 속도의 약 3분의 2로 움직인다. 거리가 멀면 그만큼 시간이 든다 — 돈으로 못 사는 값이다.
RTT를 결정하는 것 ② 중간 장비와 대기
라우터·스위치·방화벽을 지날 때마다 패킷은 큐에 잠깐씩 줄을 선다. 홉이 많을수록, 혼잡할수록 늘어난다.

가장 자주 틀리는 지점 — 대역폭을 늘려도 RTT는 그대로다

대역폭은 "한 번에 얼마나 굵게 보낼 수 있나"이고 RTT는 "한 번 갔다 오는 데 얼마나 걸리나"다. 8차선 도로를 16차선으로 넓혀도 서울에서 부산까지의 거리는 그대로인 것과 같다. 서버 사양을 올려도, 회선을 증설해도 이 값은 안 움직인다.

그래서 이 경로의 최적화는 거의 전부 둘 중 하나다.

① 왕복 횟수를 줄인다 (keep-alive · 커넥션 풀 · TLS 1.3 · HTTP 캐시)  |  ② 왕복 거리를 줄인다 (CDN · 엣지 종단)
대략적인 감각. 정확한 값이 아니라 자릿수를 외운다 — 같은 데이터센터는 1ms 미만, 국내는 수십 ms, 대양 횡단은 100ms대.
구간대략적인 RTT이 값이 뜻하는 것
같은 데이터센터 내부 (서버 ↔ DB)1ms 미만왕복 몇 번은 눈에 안 띈다 — 대신 N+1처럼 수백 번이면 보인다
같은 도시/리전 안 (사용자 ↔ 서울 서버)5~30mshandshake 3회라도 100ms 안쪽
국내 사용자 ↔ 미국 서부 서버100~180mshandshake만으로 0.4초 — 아래 계산
모바일 셀룰러망위 값 + 수십 ms기지국 구간이 통째로 더해진다
"우리 API 응답시간 30ms인데 왜 느리다고 하죠?"의 정체 미국 서부 서버에 RTT가 130ms라고 하자. TCP 1 RTT + TLS 1.2의 2 RTT = 3 RTT이므로 130 × 3 = 390ms다. 서버 코드가 0ms에 끝나도 사용자는 이미 0.4초를 기다린 뒤다. 서버에서 잰 30ms와 사용자가 겪는 시간이 다른 것은 버그가 아니라 지도의 구조다.

2. 전체 지도 — 시간축으로 펼친 6개 관문

먼저 왜 이 순서여야 하는지를 짚고 간다. 뒤 단계는 앞 단계의 결과물 위에서만 성립한다. IP 주소를 모르면 어디로 패킷을 보낼지 정할 수 없으니 DNS가 먼저다. 연결이 없으면 암호화할 통로 자체가 없으니 TCP가 그다음이다. 암호화 채널이 없으면 HTTPS 요청을 평문으로 흘리게 되니 TLS가 그다음이다. 각 관문은 앞 관문이 끝나야 시작할 수 있고, 이 직렬 구조가 곧 지연의 누적이 된다.

2-1. 텍스트 지도 — 관문 6개와 각각의 조건

1
URL 파싱 · 캐시 확인 — 스킴(https) / 호스트(example.com) / 포트(생략 → 443) / 경로(/page)로 분리한다. 브라우저 HTTP 캐시에 유효한 사본이 있으면 여기서 끝이다 — 네트워크 0회.
2
DNS 조회 — example.com → 93.184.216.34. 캐시 적중이면 0 RTT, 완전 미적중이면 최대 3~4 왕복.
3
TCP 3-way handshake — SYN → SYN+ACK → ACK. 1 RTT. 여기까지는 아직 평문이다.
4
TLS handshake — 암호 방식 협상 + 인증서 검증 + 키 교환. TLS 1.3 = 1 RTT / TLS 1.2 = 2 RTT / 세션 재개 = 0~1 RTT. http://면 이 관문이 통째로 빠진다.
5
HTTP 요청/응답 — GET /page → 200 OK + HTML. 0.5 RTT(요청 전달) + 서버 처리 시간 + 본문 전송 시간. 여기서부터 내 코드가 실행된다.
6
렌더링 + 서브리소스 반복 — HTML을 파싱하며 CSS/JS/이미지마다 [2]~[5]를 재실행한다. 같은 호스트면 [2][3][4]는 재사용으로 건너뛴다.

비용도 같은 순서로 붙여 외운다 — DNS 0~4 왕복 / TCP 1 RTT / TLS 1~2 RTT / HTTP 0.5 RTT + 서버 시간. 관문 이름만 말하는 답과, 관문마다 비용을 붙여 말하는 답은 완전히 다르게 들린다.

3. [1] URL 파싱 — 그리고 네트워크를 아예 타지 않는 경우

URL은 문자열이 아니라 구조다. 그리고 그 구조의 각 조각이 뒤 관문의 입력값이 된다 — 어느 조각이 어느 관문을 결정하는지를 보면 파싱이 왜 0번 관문인지가 드러난다.

모든 관문을 한꺼번에 0으로 만드는 유일한 최적화

브라우저는 [2]로 넘어가기 전에 자신의 HTTP 캐시부터 확인한다. Cache-Control: max-age=3600으로 받아둔 사본이 아직 유효하면 네트워크를 한 번도 타지 않고 그 사본을 그대로 쓴다. 개발자도구 Network 탭에서 크기 칸에 (memory cache) 또는 (disk cache)로 뜨는 것이 이 경우다.

캐싱 헤더 설계가 성능 작업에서 가장 큰 효과를 내는 이유 — [2]~[5] 관문 전체를 0으로 만드는 유일한 수단이기 때문

헤더별 동작과 304 Not Modified 협상은 20-http-caching-headers-and-304.md에서 다룬다.

4. [2] DNS 조회 — 이름을 주소로 바꾸는 계층형 전화번호부

4-1. 왜 이 단계가 필요한가

전제부터 깔자. 패킷의 헤더에는 도메인 이름이 들어갈 자리가 없다. IP 패킷 헤더에 있는 것은 출발지 IP와 목적지 IP라는 숫자뿐이고, 중간의 라우터들은 그 숫자만 보고 다음 홉을 정한다. 라우터는 example.com이라는 문자열이 무엇인지 전혀 모른다. 그래서 사람이 기억하는 이름과 기계가 쓰는 숫자 사이에 번역기가 필요하고, 그 번역기가 DNS(Domain Name System)다.

4-2. 왜 하나의 큰 서버가 아니라 계층인가

대부분의 설명이 건너뛰는 지점이다. "루트 → TLD → 권한 네임서버"라는 순서만 외우면 왜 그렇게 나뉘어 있는지를 설명할 수 없다. 세상 모든 도메인의 IP를 한 곳이 전부 들고 있다고 상상하면 세 가지 문제가 동시에 터진다.

① 단일 장애점
그 서버가 죽으면 인터넷 전체의 이름 조회가 죽는다.
② 권한 독점
내 회사 도메인의 IP를 바꾸려면 그 조직에 요청해야 한다.
③ 부하 집중
전 세계의 초당 수억 건 질의를 한곳에서 받아야 한다.

그래서 DNS는 이름 자체를 점(.)으로 쪼개 관리 주체를 나눴다. www.example.com을 오른쪽부터 읽으면 루트 → .com → example.com → www 순으로 위임이 이어진다. 각 계층은 "내가 답을 아는 것이 아니라, 답을 아는 다음 서버가 누구인지를 안다"는 구조다. 이 위임(delegation) 덕분에 example.com의 IP를 바꾸는 일은 그 회사가 자기 네임서버에서 혼자 처리하면 되고, 루트나 .com 서버는 아무것도 몰라도 된다.

회사 안내데스크 비유 로비 안내데스크(루트)는 직원 개개인의 자리를 모른다 — 아는 것은 "개발본부는 7층 데스크에 물어보세요"뿐이다. 7층 데스크(TLD)도 개인 자리는 모르고 "그 팀은 저쪽 팀 비서에게"라고만 안다. 최종 답은 그 팀의 비서(권한 네임서버)만 갖고 있다. 이 구조 덕분에 팀 내 자리 배치가 바뀌어도 로비에는 알릴 필요가 없다.
재귀 리졸버 (recursive resolver)
클라이언트를 대신해 답이 나올 때까지 계속 물어봐 주는 대리인. "재귀"는 답을 받을 때까지 자기가 반복해서 질의를 이어간다는 뜻이다. 통신사 DNS나 8.8.8.8 같은 공용 DNS. 클라이언트는 한 번만 묻고 최종 답을 받는다.
루트 네임서버
계층의 꼭대기. 아는 것은 오직 "각 최상위 도메인(.com, .net, .kr)을 관리하는 서버들의 주소" 목록뿐이다.
TLD 네임서버
TLD = top-level domain(최상위 도메인). .com을 맡는 서버는 .com으로 끝나는 도메인들이 각각 어느 권한 네임서버에 위임돼 있는지를 안다.
권한 네임서버 (authoritative)
그 도메인에 대한 최종 답을 낼 권한을 가진 서버. "권한"은 이 답이 복사해 온 캐시가 아니라 원본이라는 뜻이다. 직접 운영하거나 Route 53 같은 관리형 서비스에 맡긴다.

4-3. 실제 조회 흐름 — 캐시를 먼저 뒤지고, 없으면 계층을 탄다

4-4. TTL과 캐시 — 백엔드가 실제로 부딪히는 지점

응답에는 TTL(time to live)이 함께 온다. 이름 그대로 "이 답이 살아 있는 시간"이고 초 단위다. 경로상의 모든 캐시가 그 시간만큼 결과를 기억한다.

캐시가 한 곳이 아니라 계층 전체에 흩어져 있다는 것이 문제의 출발점이다.
캐시 계층무효화 방법백엔드가 겪는 문제
브라우저 DNS 캐시브라우저 재시작 또는 내부 설정 화면개발자 본인 PC에서만 안 바뀌어 혼란
OS 캐시 / hosts 파일캐시 플러시 명령, hosts 수정로컬 테스트용 hosts 항목이 남아 오동작
재귀 리졸버 캐시기다리는 수밖에 없음 (TTL 만료)IP 전환이 TTL만큼 지연된다
JVM InetAddress 캐시JVM 옵션 / 보안 속성DNS의 TTL을 무시하고 오래 붙들 수 있다

"DNS 바꿨는데 왜 아직 옛 서버로 오지?"의 정체

서버 IP를 바꿔도(배포, failover, 마이그레이션) TTL이 지나기 전까지는 옛 주소로 트래픽이 계속 온다. 레코드는 바뀌었는데 트래픽은 여전히 옛 서버로 오는 구간이 반드시 존재한다.

정석: 전환 작업 전에 TTL을 미리 짧게 줄여둔다 (예: 300초 → 60초) → 전환 → 안정되면 원래대로

"미리"가 중요하다 — 기존에 뿌려진 캐시는 옛 TTL로 만료되기를 기다려야 하므로, 전환 직전에 줄여봐야 이미 늦다. 전환 전략 전반은 19-dns-ttl-failover-traffic-switching.md에서 다룬다.

JVM은 별도로 조심해야 한다. Java의 InetAddress는 자체 DNS 캐시를 갖고 있고, DNS 응답의 TTL이 아니라 JVM 자신의 정책을 따른다. 정책 값은 JDK 버전과 보안 설정에 따라 달라지므로, 값을 짐작하지 말고 명시적으로 지정하는 편이 안전하다.

Before DNS 캐시 정책을 손대지 않은 상태
// RDS 엔드포인트나 내부 API 도메인이 failover로 IP가 바뀌어도
// JVM이 옛 IP를 계속 붙들고 있어 재기동 전까지 장애가 이어질 수 있다.

// 더 나쁜 점: "가끔 몇몇 인스턴스만 안 붙는다"처럼
// 부분 장애로 나타나 DNS가 원인이라는 것을 알아채기 어렵다.
//   → 어떤 인스턴스는 새 IP를 조회했고
//     어떤 인스턴스는 옛 IP를 캐시에 붙들고 있기 때문

// (설정 없음 — JDK 기본 정책에 맡긴 상태)
After 시작 시점에 캐시 수명을 명시한다
public class DnsCacheConfig {
    static {
        // 성공한 조회를 30초만 기억한다.
        // failover 후 최대 30초 뒤에는 새 IP로 붙는다는
        // 상한을 코드로 보장하는 것이 목적이다.
        java.security.Security.setProperty(
            "networkaddress.cache.ttl", "30");

        // 실패한 조회(NXDOMAIN 등)를 오래 기억하면 잠깐의
        // DNS 장애가 복구된 뒤에도 계속 실패로 남는다.
        java.security.Security.setProperty(
            "networkaddress.cache.negative.ttl", "0");
    }
}

UnknownHostException

패킷을 한 개도 보내지 못한 상태라는 뜻이다. 방화벽도 서버 상태도 아직 관련이 없다.

  • 도메인 오타
  • DNS 레코드 존재 여부
  • 사내 DNS 서버 자체의 장애

dig로 두 실패를 갈라낸다

  • NXDOMAIN — "그런 이름은 없다"는 확정적 답변. 레코드가 없거나 오타 → 우리 설정 문제
  • SERVFAIL — "물어봤는데 답을 못 받았다". DNS 서버 장애, DNSSEC 검증 실패 → 조회 경로 문제

5. [3] TCP 연결 — 대화 전에 회선부터 뚫는다

5-1. 전제 지식 — 연결은 4개의 숫자로 식별된다

하나의 서버는 수만 개의 연결을 동시에 유지한다. 도착한 패킷이 그중 어느 연결의 것인지를 어떻게 판별할까. 답은 4-튜플(4-tuple)이다.

출발지 IP
클라이언트마다 다름
출발지 포트
임시 포트 — 유일한 변수
목적지 IP
우리 서버 — 고정
목적지 포트
443 — 고정

웹 서버에 붙는 연결들은 목적지 IP와 목적지 포트가 전부 같으므로, 실제로 연결들을 구분하는 것은 출발지 IP와 출발지 포트다. 여기서 임시 포트(ephemeral port) 개념이 나온다 — 클라이언트는 자기 출발지 포트를 직접 고르지 않고 OS에게 맡기고, OS는 미리 정해진 범위(리눅스는 보통 32768~60999)에서 아직 안 쓰는 번호를 하나 골라준다. "임시"는 연결이 끝나면 반납되고 다음 연결은 다른 번호를 받는다는 뜻이다.

이 전제가 나중에 어떤 장애로 돌아오는가 — 임시 포트 고갈 한 대의 서버가 같은 목적지로 짧은 연결을 초당 수천 개씩 만들면, 4-튜플 중 세 개가 고정돼 있으므로 남는 변수는 임시 포트 하나뿐이다. 그 범위(보통 2만~3만 개)가 다 소진되면 새 연결을 아예 만들 수 없다(Cannot assign requested address). 평소에는 멀쩡하다가 트래픽이 올라간 순간 급격히 무너지는 형태라 원인 파악이 늦어진다. (10-keepalive-connection-pool-time-wait.md에서 TIME_WAIT과 함께 다룬다.)

5-2. 3-way handshake — 왜 세 번이고 왜 1 RTT인가

5-3. 이 관문의 실패 증상 — 두 가지를 반드시 구분한다

TCP 연결 실패는 겉보기에 "연결이 안 된다" 하나지만, 실제로는 성격이 완전히 다른 두 가지가 있다. 이 구분이 실무 진단에서 가장 값이 크다.

즉시 거절 — Connection refused

서버가 RST 패킷으로 명확히 거절했다. 즉 패킷은 그 기계까지 도달했다. 다만 그 포트에서 대기 중인 프로세스가 없다.

  • 특징: 밀리초 단위로 즉시 실패
  • 볼 곳: 프로세스 생존 여부
  • 볼 곳: 실제 리스닝 포트 번호
  • 볼 곳: 바인딩 주소 (0.0.0.0 vs 127.0.0.1)

connect timeout — SocketTimeoutException

보낸 SYN에 아무 응답도 오지 않아 기다리다 포기했다. 즉 패킷이 어딘가에서 조용히 버려졌다.

  • 특징: 설정한 타임아웃을 꽉 채우고 실패
  • 볼 곳: 보안그룹 / 방화벽 DROP 규칙
  • 볼 곳: 라우팅 · 경로 존재 여부
  • 볼 곳: 서버 과부하 (SYN 처리 불가)

암기 장치 — "즉시면 포트, 지연이면 방화벽"

실패까지 걸린 시간이 곧 원인의 힌트다 — 즉시 실패 = 기계는 살아 있고 그 포트만 안 열렸다 / 타임아웃 = 패킷이 중간에서 사라졌다

두 경우 모두 애플리케이션 로그에는 아무것도 남지 않는다. 커널이 처리했거나 패킷이 아예 도달하지 않았으므로 서블릿 필터도 인터셉터도 실행되지 않는다.

6. [4] TLS handshake — 평문 회선을 암호 채널로 바꾼다

6-1. 왜 필요한가

TCP는 뚫렸지만 아직 평문이다. 지금 상태에서 보내는 데이터는 카페 와이파이의 공유기, 통신사 장비, 중간의 모든 라우터가 그대로 읽을 수 있다. 쿠키에 담긴 세션 ID도, 로그인 폼의 비밀번호도 마찬가지다. TLS(Transport Layer Security)는 이 회선 위에 암호 계층을 얹어 세 가지를 확보한다.

기밀성
중간에서 내용을 읽지 못하게 한다
무결성
중간에서 내용을 바꾸면 들키게 한다
신원 확인
지금 연결된 상대가 진짜 example.com이 맞는지 증명한다
세 번째가 특히 중요한 이유 암호화만 하고 상대가 누군지 확인하지 않으면, 중간자가 자기와 암호 통신을 하게 만들 수 있다. "암호화되어 있으니 안전하다"가 아니라 "올바른 상대와 암호화되어 있어야 안전하다"가 정확한 문장이다.

6-2. handshake에서 실제로 합의하는 것

SNI (Server Name Indication)
handshake 첫 메시지에서 "나는 이 도메인에 연결하려 한다"를 알려주는 확장. 하나의 IP에 여러 도메인이 붙어 있을 수 있어서 서버가 어느 인증서를 제시할지 알아야 하는데, HTTP의 Host 헤더는 암호화 이후에나 읽을 수 있어 너무 늦다. 그래서 평문으로 먼저 알린다.
CA (Certificate Authority)
"이 공개키가 정말 이 도메인의 것"이라고 서명해 주는 제3자. 브라우저·OS는 신뢰하는 CA 목록(신뢰 저장소)을 미리 갖고 있고, 서버가 제시한 인증서의 서명을 따라가 그 목록의 CA에 닿으면 통과시킨다. 이 따라가는 경로가 인증서 체인이다.

6-3. 대칭키와 비대칭키를 왜 둘 다 쓰는가

TLS가 두 가지 암호를 섞어 쓰는 이유는 각각의 장단점이 정확히 반대이기 때문이다.

대칭키 — 빠르지만 열쇠 전달이 문제

암호화와 복호화에 같은 열쇠를 쓴다. 대용량 데이터를 처리하기에 충분히 빠르다. 문제는 그 열쇠를 어떻게 안전하게 전달하느냐다 — 평문으로 보내면 중간에서 그것도 읽히므로 아무 의미가 없다.

비대칭키 — 열쇠 전달을 풀지만 느림

공개키와 개인키가 짝을 이룬다. 공개키로 잠근 것은 개인키로만 열 수 있으므로 공개키는 아무에게나 뿌려도 된다 — 열쇠 전달 문제를 원천적으로 푼다. 문제는 계산 비용이 훨씬 크다는 것이다.

6-4. 이 관문의 실패 증상

Java에서는 대부분 SSLHandshakeException으로 오지만, 메시지에 따라 원인이 갈린다. 6-2의 검증 3단계와 대응시켜 보면 외울 것이 없다.

메시지 조각검증 단계원인
PKIX path building failed① 체인인증서 체인이 신뢰 저장소의 CA까지 이어지지 않음 — 중간 인증서 누락이거나 사설 CA를 신뢰 저장소에 안 넣음
certificate expired② 유효기간인증서 유효기간 만료 — 갱신 자동화가 실패한 전형적 사고
No name matching ... found③ 도메인인증서의 도메인과 접속한 호스트명이 다름
handshake_failure협상 자체TLS 버전이나 암호 스위트 합의 실패 — 서버가 구버전 TLS를 껐는데 클라이언트가 신버전을 못 하는 경우
이 실패들 역시 애플리케이션 로그에 남지 않는다 더구나 TLS 종단이 로드밸런서에 있으면 애플리케이션 서버는 이런 요청이 있었다는 사실조차 모른다. 인증서 만료로 전체 서비스가 죽어도 앱 로그는 평온하다 — 볼 곳은 앱이 아니라 LB 액세스 로그와 인증서 만료일이다. (TLS를 어디서 종단할지의 판단은 17-tls-termination-lb-vs-app.md)

7. [5] HTTP 요청/응답 — 여기서부터 내 코드가 실행된다

암호 채널이 뚫렸으니 이제 그 위로 요청을 쓴다. HTTP/1.1의 요청은 텍스트다.

요청 브라우저가 채널 위에 써 보내는 것
GET /page HTTP/1.1          ← 요청 라인: 메서드 / 경로 / 프로토콜 버전
Host: example.com           ← 어느 도메인에 대한 요청인지 (한 IP에 여러 사이트가 있을 수 있으므로 필수)
Cookie: session=abc123      ← 인증 상태를 실어 보내는 자리
Accept: text/html           ← 어떤 형식의 응답을 원하는지
User-Agent: Mozilla/5.0 ...
                            ← 빈 줄 = 헤더 끝 표시
여기서 Host 헤더와 [4]의 SNI가 같은 값을 두 번 말한다 둘 다 "나는 example.com에 접속하려 한다"는 뜻인데, SNI는 암호화 전에(서버가 인증서를 고르려고), Host는 암호화 후에(서버가 가상 호스트를 고르려고) 필요하다. 하나의 IP가 여러 사이트를 서비스하는 구조가 두 계층 모두에 흔적을 남긴 셈이다.

7-1. 요청은 곧장 내 코드에 닿지 않는다 — 홉과 TTFB

응답 후 커넥션을 바로 닫지 않는다 — keep-alive 같은 페이지의 CSS·JS·이미지 요청이 [3]과 [4]를 다시 치르지 않게 하기 위해서다. HTTP/1.1은 keep-alive가 기본 동작이고, 2절의 "두 번째 요청 235ms"가 바로 이것 덕분이다.

이 구간의 실패는 앞 관문들과 성격이 다르다. 서버가 요청을 받고 판단해서 답한 것이므로 상태 코드가 붙어 있고, 애플리케이션 로그에도 흔적이 남는다. 관문 [2]~[4]와 [5]를 가르는 선이 바로 "내가 로그로 볼 수 있는가"다.

8. [6] 렌더링 — 그리고 관문의 반복

브라우저는 받은 HTML을 위에서부터 파싱하며 DOM 트리를 만들고, 그 과정에서 <link>, <script>, <img> 같은 태그를 만날 때마다 추가 요청을 발생시킨다. 여기서 지도가 한 번 더 쓰인다.

9. 실패 지도 — "안 돼요"를 "어느 구간의 실패인가"로 분해한다

지도의 두 번째 가치는 성능이 아니라 장애 진단에 있다. 각 관문은 서로 다른 예외와 증상으로 실패하므로, 증상만 보고 어느 관문에서 막혔는지 역추적할 수 있다.

11. 서버 간 호출에서 관문 비용을 없애기 가산점

거치는 관문은 브라우저와 완전히 동일하다. 달라지는 것은 그 비용을 누가 관리하느냐다. 브라우저는 DNS 캐시·커넥션 재사용·TLS 세션 재개·동시 연결 수 제한을 전부 알아서 처리해 주지만, 서버 간 호출에서는 이것들이 HTTP 클라이언트의 설정 항목이 되어 개발자에게 넘어온다.

Before 요청마다 클라이언트를 새로 만든다
// 새 클라이언트는 커넥션 풀도 비어 있으므로,
// 호출 한 번마다 [2] DNS + [3] TCP + [4] TLS를 전부 다시 치른다.
// → 10-2의 계산대로면 요청당 389ms의 준비 비용을 매번 지불.
//
// 더 나쁜 것: 연결을 계속 새로 만들고 닫으면서
// 임시 포트를 소진해, 부하가 올라간 순간
// "Cannot assign requested address"로 무너진다.
public PaymentResult call(PaymentRequest req) {
    RestClient client = RestClient.create();  // 매 호출마다 새 클라이언트
    return client.post()
        .uri("https://pg.example.com/payments")
        .body(req)
        .retrieve()
        .body(PaymentResult.class);
}
After 커넥션 풀을 가진 클라이언트를 빈으로 재사용
@Configuration
public class PaymentClientConfig {

    @Bean
    public RestClient paymentClient() {
        PoolingHttpClientConnectionManager pool =
            new PoolingHttpClientConnectionManager();
        // 이 앱이 동시에 유지할 연결의 상한
        pool.setMaxTotal(100);
        // 목적지(라우트)당 상한 — 기본값이 작아서 이걸 안 올리면
        // 풀은 여유가 있는데 특정 호스트 호출만 줄을 선다.
        pool.setDefaultMaxPerRoute(50);

        RequestConfig requestConfig = RequestConfig.custom()
            // [3] 연결까지의 상한. 방화벽 DROP처럼 응답이 아예
            // 없는 상황에서 스레드가 무한정 묶이는 것을 막는다.
            .setConnectTimeout(Timeout.ofSeconds(2))
            // [5] 응답을 기다리는 상한. connect와 분리해야
            // "연결은 되는데 느린" 문제와 "연결이 안 되는"
            // 문제를 구분할 수 있다.
            .setResponseTimeout(Timeout.ofSeconds(3))
            // 풀에서 연결을 빌려오기까지의 상한. 없으면 풀 고갈 시
            // 호출 스레드가 조용히 쌓여 장애가 뒤늦게 드러난다.
            .setConnectionRequestTimeout(Timeout.ofSeconds(1))
            .build();

        CloseableHttpClient httpClient = HttpClients.custom()
            .setConnectionManager(pool)
            .setDefaultRequestConfig(requestConfig)
            .build();

        return RestClient.builder()
            .requestFactory(new HttpComponentsClientHttpRequestFactory(httpClient))
            .build();
    }
}
after가 하는 일을 지도의 언어로 다시 말하면 한 번 뚫어둔 [3]과 [4]를 여러 요청이 나눠 쓰게 만들어, 두 번째 요청부터는 [5]만 남긴다. 커넥션 풀이 "성능 옵션"이 아니라 이 지도의 직접적인 귀결이라는 것을 알면, 풀 크기나 타임아웃 값을 감이 아니라 근거로 정할 수 있다. (10-keepalive-connection-pool-time-wait.md, 07-traffic-performance/10-timeout-layers-and-budget.md)

한 걸음 더 — 재시도의 안전성도 이 지도로 갈린다

connect timeout → 재시도 비교적 안전

요청이 서버에 도달하지 않았을 가능성이 높다 — 연결 자체가 성립하지 않았으므로 서버가 무언가를 처리했을 리 없다.

read timeout → 재시도 위험

서버가 이미 처리했을 수 있다. 멱등하지 않은 요청(결제·주문 생성)을 재시도하면 이중 처리가 된다.

"타임아웃이면 재시도"가 아니라 "어느 관문의 타임아웃인가"를 먼저 묻는 것 — 지도가 있으면 이 판단을 근거를 갖고 할 수 있다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

관문 4개와 순서가 고정된 이유?
이·회·암·요 — 이름을 주소로(DNS) · 회선을 뚫고(TCP) · 암호로 감싸고(TLS) · 요청을 써 보낸다(HTTP). 뒤 단계는 앞 단계의 결과물 위에서만 성립하므로 순서를 바꿀 수 없다.
관문별 RTT 비용?
DNS 0(캐시)~3~4 왕복 · TCP 1 RTT · TLS 1.3=1 / 1.2=2 / 재개=0~1 · HTTP 0.5 RTT + 서버 시간.
RTT는 무엇으로 줄이나?
서버 사양·대역폭으로는 안 줄어든다. 왕복 횟수(keep-alive·풀·TLS 1.3·캐시) 또는 왕복 거리(CDN) 둘 중 하나.
첫 요청 vs 두 번째 요청?
RTT 110ms 예시에서 615ms → 235ms. 사라진 380ms가 곧 [2][3][4] 재사용의 값이다.
실패 증상 4종?
못 찾음(UnknownHostException) · 못 붙음(refused / connect timeout) · 못 믿음(SSLHandshakeException) · 못 기다림(상태 코드 / read timeout).
앱 로그의 경계는?
[3][4] 실패는 앱 로그에 안 남는다. "앱 로그에 그 요청이 없다" ≠ "요청이 안 왔다".
refused와 timeout 구분?
즉시면 포트, 지연이면 방화벽. 즉시 실패 = 기계는 살아 있고 포트만 안 열림 / 타임아웃 = SYN이 중간에서 DROP.
DNS TTL의 실무 함의?
경로상의 모든 캐시가 TTL만큼 옛 IP를 붙든다. 전환은 레코드 수정 시점이 아니라 TTL 만료 후 완료 — 미리 TTL을 줄여둔다.
curl -w의 함정?
출력은 구간 시간이 아니라 누적 시각 — 뺄셈해야 한다. time_connect − time_namelookup이 곧 1 RTT.
서버 간 호출은 뭐가 다른가?
관문은 완전히 동일하고, 브라우저가 자동으로 해 주던 재사용을 개발자가 커넥션 풀·타임아웃·JVM DNS 캐시로 직접 설정해야 한다.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

HTTPS 첫 요청은 왜 느리고, 두 번째 요청부터는 왜 빨라지나요? 필수힌트: "캐시돼서요"로 끝내지 말고, 무엇이 캐시되고 무엇이 재사용되는지를 관문 이름으로 나눠 말한다

첫 요청은 본론에 들어가기 전에 준비 비용을 선불로 전부 치르기 때문이다. DNS 조회(캐시가 비어 있으면 최대 3~4 왕복) + TCP handshake 1 RTT + TLS handshake 1~2 RTT가 요청을 보내기도 전에 나간다. RTT 110ms 경로에서 TLS 1.2면 이 준비만으로 400ms에 가깝다.

두 번째 요청부터 빨라지는 이유는 그 준비물이 전부 캐시되거나 재사용되기 때문이다 — DNS는 브라우저·OS·리졸버 캐시에서 즉시 나오고, TCP 연결은 keep-alive로 그대로 살아 있으며, 연결이 끊겼더라도 TLS는 세션 재개로 협상을 축약한다. 그래서 두 번째 요청에 남는 것은 순수한 요청-응답 왕복뿐이다.

여기서 한 걸음 더 나가면 좋다. 서버 간 통신에서 커넥션 풀을 쓰는 이유가 정확히 같다. 브라우저가 자동으로 해 주는 이 재사용을 서버에서는 개발자가 명시적으로 구현하는 것이고, 그것을 안 하면 요청마다 [2]~[4]를 다시 치르는 코드가 된다.

이 과정 중 어디가 실패하면 어떤 증상으로 나타나나요? 필수힌트: 예외 이름 나열에서 멈추지 말고, 마지막에 "앱 로그 경계"를 얹어야 답이 완성된다

관문마다 증상이 다르다는 것을 예외 이름으로 짚는다. DNS 실패는 UnknownHostException — 아직 패킷을 한 개도 못 보낸 상태다. TCP 실패는 두 가지로 갈리는데, Connection refused는 기계까지는 갔지만 그 포트에 프로세스가 없다는 뜻이고(즉시 실패), connect timeout은 SYN이 어딘가에서 조용히 버려졌다는 뜻이다(방화벽 DROP 의심, 타임아웃을 꽉 채우고 실패). TLS 실패는 SSLHandshakeException이며 메시지에 따라 체인 문제(PKIX path building failed), 만료, 호스트명 불일치, 버전 협상 실패로 나뉜다. HTTP 단계는 상태 코드가 붙은 응답이나 read timeout이다.

가장 중요한 구분: [3]과 [4]의 실패는 애플리케이션 로그에 남지 않는다

요청이 서블릿에 도달하기 전에 반려됐기 때문이다. 그래서 "앱 로그에 그 요청이 없다"를 "요청이 안 왔다"로 읽으면 안 되고, "앞 구간에서 반려됐을 수 있다"로 읽어야 한다. 이 경우 확인할 곳은 애플리케이션이 아니라 로드밸런서 액세스 로그, 보안그룹 규칙, 인증서 만료일이다.

DNS 결과는 어디에 캐싱되고, 그게 배포/전환에 어떤 영향을 주나요? 함정힌트: 캐시 계층을 나열한 뒤, "TTL을 무시하는 계층"까지 가야 한 칸 더 간다

브라우저 캐시, OS 캐시(+hosts 파일), 재귀 리졸버 캐시까지 경로상의 모든 계층에 TTL만큼 캐시된다. 그래서 서버 IP를 바꾸는 전환(failover, 리전 마이그레이션)은 DNS 레코드를 수정한 순간이 아니라 각 캐시의 TTL이 만료된 뒤에야 완료된다. 레코드는 바뀌었는데 트래픽은 여전히 옛 서버로 오는 구간이 반드시 존재한다.

그래서 정석은 전환 작업 전에 TTL을 미리 짧게 줄여두는 것이다. 평소 300초로 두다가 전환 며칠 전에 60초로 낮추고(기존에 뿌려진 캐시가 옛 TTL로 만료되기를 기다려야 하므로 미리 해야 한다), 전환 후 안정되면 다시 올린다.

여기에 함정이 하나 더 있다. TTL을 무시하는 계층이 존재한다. JVM의 InetAddress 캐시가 대표적인데 DNS 응답의 TTL이 아니라 JVM 자신의 정책을 따르므로, 짧은 TTL을 걸어둬도 애플리케이션이 옛 IP를 계속 붙들 수 있다. 일부 리졸버도 지나치게 짧은 TTL을 자체 하한으로 올려 잡는다.

결론: DNS는 "빠른 전환 수단"이 아니라 "느리지만 확실한 전환 수단" — 초 단위 전환이 필요하면 LB 대상 그룹 교체처럼 DNS에 의존하지 않는 방법을 쓴다
브라우저가 아니라 서버 간 호출이면 무엇이 다른가요? 가산점힌트: "같다"로 시작하는 것이 좋은 답이다. 그다음 누가 관리하느냐로 넘어간다

거치는 관문은 완전히 동일하다. 달라지는 것은 그 비용을 누가 관리하느냐다. 브라우저는 DNS 캐시·커넥션 재사용·TLS 세션 재개·동시 연결 수 제한을 전부 알아서 처리해 준다. 서버 간 호출에서는 이것들이 HTTP 클라이언트의 설정 항목이 되어 개발자에게 넘어온다 — 커넥션 풀(전체 크기와 목적지당 크기), connect/read 타임아웃 분리, JVM DNS 캐시 정책이 그것이다.

이걸 놓쳤을 때의 전형적 장애 패턴을 함께 말하면 좋다. 요청마다 클라이언트를 새로 만드는 코드는 요청마다 [2]~[4]를 다시 치르므로 지연이 몇 배로 늘고, 더 심각하게는 연결을 계속 새로 만들고 닫으면서 TIME_WAIT 소켓이 쌓여 임시 포트가 고갈된다. 4-튜플 중 세 개가 고정이라 임시 포트 하나가 유일한 변수이고, 그 범위(보통 2만~3만 개)를 다 쓰면 Cannot assign requested address로 새 연결이 아예 안 된다.

평소에는 멀쩡하다가 트래픽이 올라간 순간 급격히 무너지는 형태라 원인 파악이 늦어지는 것이 이 장애의 특징이다.

이 경로에서 지연을 줄일 수 있는 지점은 각각 어디인가요? 시니어 변별힌트: 관문별로 나눠 답하고, 마지막에 "물리적 거리"를 별도의 축으로 세운다

[2] DNS는 TTL 설계와 캐싱이다. 다만 이 구간은 절대값이 작아서(보통 수십 ms) 최적화 우선순위가 낮고, 오히려 TTL을 너무 길게 잡아 전환이 느려지는 쪽이 실무에서 더 자주 문제가 된다.

[3][4] TCP·TLS는 handshake 자체를 재사용해 없애는 것이 정답이다. keep-alive와 커넥션 풀로 연결을 살려 쓰고, TLS 세션 재개로 협상을 축약하고, TLS 1.3으로 올려 왕복을 하나 줄인다. 여기가 개선 효과가 가장 확실한 구간이다 — 10-2의 예에서 준비 비용이 389ms였던 것을 기억하면, 재사용은 그 전체를 0으로 만드는 조치다.

물리적 거리는 별도의 축이다. 앞의 모든 handshake 비용이 RTT에 비례하므로, RTT 자체를 줄이면 모든 관문이 동시에 빨라진다. CDN이나 엣지에서 TLS를 종단해 사용자 가까이에서 연결을 맺게 하는 것이 이 접근이고, 왕복 횟수를 줄이는 것보다 왕복 거리를 줄이는 쪽이 효과가 더 클 때도 많다.

[5] HTTP는 세 갈래다 — 프로토콜 버전을 올려 요청들을 한 연결에 겹쳐 보내고(HTTP/2 멀티플렉싱), 캐싱 헤더로 요청 자체를 없애며(가장 강력하다 — 관문 전체가 0이 된다), 응답 압축으로 본문 전송 시간을 줄인다.

"서버 처리 시간만 줄이는 것이 성능 최적화가 아니다 — 요청이 서버에 도달하기 전 구간에도, 응답이 사용자에게 닿는 구간에도 최적화 여지가 있다"

그리고 어디를 손댈지는 감이 아니라 10절의 구간 분해로 측정한 뒤에 정한다는 순서까지 말하면 설계 감각이 드러난다.

curl로는 잘 되는데 애플리케이션에서만 SSLHandshakeException이 납니다. 왜 그럴까요? 시니어 변별힌트: 같은 서버, 같은 인증서인데 결과가 다르다면 다른 것은 "검증하는 쪽"이다

TLS 검증 3단계 중 ① 체인 검증은 "누구를 신뢰하는가" 목록에 의존하는데, 그 목록이 도구마다 다르다. curl은 보통 OS의 신뢰 저장소를 쓰고, JVM 애플리케이션은 JVM 자신의 신뢰 저장소(cacerts)를 쓴다. 그래서 사내 사설 CA로 발급한 인증서나 OS에는 설치돼 있지만 JVM에는 없는 루트/중간 인증서가 걸리면 같은 서버인데 curl은 성공, 앱은 PKIX path building failed가 된다.

확인 순서도 같이 말하면 좋다. openssl s_client -connect ... -servername ...로 서버가 실제로 어떤 체인을 내려주는지 먼저 본다 — 서버가 중간 인증서를 빼먹고 내려주는 경우가 흔한데, 이때는 중간 인증서를 이미 캐시한 클라이언트만 성공해서 "어떤 환경에서는 되고 어떤 환경에서는 안 되는" 증상이 된다.

고치는 방향은 두 갈래다 — 서버가 체인을 완전하게 내려주도록 고치는 것이 정석이고, 사내 사설 CA라면 그 CA를 JVM 신뢰 저장소에 넣는 것이 정답이다. 검증을 끄는 것은 답이 아니다 — 그 순간 6-1의 "신원 확인"이 통째로 사라진다.

서버에서는 localhost로 잘 붙는데 외부에서는 Connection refused가 납니다. 함정힌트: "즉시 실패"라는 사실이 이미 절반을 알려준다

즉시 실패라는 것 자체가 방화벽 문제가 아니라는 신호다. 방화벽 DROP이면 타임아웃을 꽉 채우고 실패한다. 즉시 RST가 왔다는 것은 패킷이 그 기계까지 도달했고, 커널이 "그 포트엔 아무도 없다"고 답했다는 뜻이다.

가장 흔한 원인은 바인딩 주소다. 프로세스가 127.0.0.1에만 바인딩되어 있으면 루프백으로 들어온 연결만 받고 외부 인터페이스로 들어온 연결은 거절한다. 0.0.0.0(모든 인터페이스)으로 바인딩해야 외부에서 붙는다. 그다음으로 흔한 것은 포트 번호 착각(컨테이너 내부 포트와 게시 포트 혼동)과 프로세스가 아직 부팅 중인 경우다.

확인은 리스닝 소켓의 바인딩 주소를 직접 보는 것으로 끝난다 — 0.0.0.0:8080인지 127.0.0.1:8080인지가 그대로 답이다.

DNS 조회는 왜 UDP를 쓰나요? TCP면 안 되나요?힌트: 이 문서 전체의 단위(RTT)로 답하면 된다

질의와 응답이 작고 한 왕복으로 끝나기 때문이다. TCP로 하면 데이터를 주고받기 전에 3-way handshake 1 RTT를 먼저 내야 하는데, 정작 주고받을 내용은 패킷 하나 분량이다. 연결 수립 비용이 본 작업보다 비싼 상황이라 연결 없는 UDP가 합리적이다 — 응답이 안 오면 그냥 다시 물어보면 된다.

다만 응답이 커서 잘리는 경우가 있는데, 이때는 같은 질의를 TCP로 다시 보낸다. 그래서 "DNS는 UDP"라고만 외우면 방화벽에서 53번 TCP를 막아 간헐적 조회 실패가 나는 상황을 설명하지 못한다 — DNS는 UDP를 주로 쓰지만 TCP도 쓴다가 정확한 문장이다.

SNI가 평문으로 나간다면 프라이버시 문제가 아닌가요?힌트: 무엇이 보호되고 무엇이 보호되지 않는지를 나눠 말한다

맞다 — SNI는 handshake 초반에 평문으로 나가므로 "어느 도메인에 접속하려 하는지"는 중간에서 관찰될 수 있다. TLS가 보호하는 것은 그 뒤에 오갈 내용(경로, 헤더, 쿠키, 본문)이지, 접속 대상 자체는 아니다.

그런데도 평문인 이유는 순서 때문이다. 서버는 어느 인증서를 제시할지 정해야 handshake를 진행할 수 있는데, 그 정보를 알려주는 Host 헤더는 암호 채널이 열린 뒤에야 읽을 수 있다. 암호화하려면 인증서가 필요하고, 인증서를 고르려면 도메인이 필요한 순환을 끊기 위해 첫 메시지에 평문으로 싣는 것이다.

면접에서는 여기까지만 말해도 충분하고, 이 평문 노출을 감추려는 확장이 논의·도입되고 있다는 정도를 덧붙이면 최신 흐름을 아는 인상을 준다.

Timing에서 Queueing만 크고 TTFB는 작습니다. 서버는 한가한데 왜 느릴까요?힌트: 관문 이전에서 기다리는 중이다

서버 문제가 아니라 브라우저 쪽 동시 연결 제한일 가능성이 크다. HTTP/1.1에서는 같은 호스트로 동시에 열 수 있는 연결 수가 제한(보통 6개)되어 있어서, 리소스가 수십 개면 나머지는 슬롯이 빌 때까지 관문에 들어가지도 못하고 줄을 선다. 이때 개별 요청의 TTFB는 정상이므로 서버 지표에는 아무 이상이 없다.

대응은 요청 개수를 줄이거나(번들링·스프라이트) 한 연결에 여러 요청을 겹쳐 보내는 것이다 — 후자가 HTTP/2 멀티플렉싱이다. 이 판단이 "서버 증설"이라는 잘못된 처방을 막는다. (09-http1-http2-http3-hol-blocking.md)

HTTP/2나 HTTP/3를 쓰면 이 지도가 어떻게 달라지나요? 가산점힌트: 어떤 관문이 그대로이고 어떤 관문이 합쳐지는지로 답한다

HTTP/2에서 [2] DNS · [3] TCP · [4] TLS는 그대로다. 달라지는 것은 [5]의 사용 방식이다 — 한 연결 위에 여러 요청을 동시에 겹쳐 보낼 수 있어(멀티플렉싱) 앞 질문의 "같은 호스트 6개 제한"과 그로 인한 줄서기가 사라진다. 즉 관문 개수는 그대로인데 관문을 여는 횟수가 줄어든다.

HTTP/3는 전송 계층이 QUIC(UDP 기반)으로 바뀌면서 [3]과 [4]가 하나로 합쳐진다 — 연결 수립과 암호 협상을 함께 처리해 준비 왕복을 더 줄이는 방향이다. 지도의 관점에서 보면 "관문을 없애는" 최적화의 가장 근본적인 형태다. (상세: 09-http1-http2-http3-hol-blocking.md)

사용자는 느리다는데 서버 응답시간 지표는 정상입니다. 무엇부터 확인하나요? 함정힌트: "둘 다 맞다"에서 출발해 구간 분해 순서를 말한다

먼저 두 숫자가 다른 것이 정상이라는 것부터 짚는다 — 서버 지표에는 DNS·TCP·TLS·네트워크 전송이 통째로 빠져 있다. 같은 요청이 서버 로그에 30ms, 브라우저에 480ms로 찍히는 것은 모순이 아니라 "차이만큼이 네트워크 구간"이라는 정보다.

그다음은 구간 분해다. 브라우저가 있으면 Network 탭 Timing에서 DNS Lookup / Initial connection / SSL / TTFB / Content Download 중 어느 항목이 큰지 본다. 서버 환경이면 curl -w의 누적 시각을 빼서 같은 분해를 만든다.

그리고 어느 항목이 큰지가 곧 처방을 정한다 — TTFB면 백엔드, Content Download면 응답 크기·압축, Initial connection·SSL이면 연결 재사용과 TLS 버전, Queueing이면 프로토콜·리소스 개수, DNS면 캐시와 리졸버다. 측정 없이 처방부터 고르지 않는 것이 이 답의 핵심이다.

한 줄 요약
URL 입력 후에는 DNS(이름 → 주소) → TCP(연결 수립) → TLS(암호 채널 협상) → HTTP(요청/응답)의 관문을 차례로 지나며, 각 관문은 RTT라는 줄일 수 없는 비용을 소모하고 실패 증상도 서로 다르므로 — 특히 TCP·TLS 실패는 애플리케이션 로그에 흔적을 남기지 않으므로 — 이 지도를 갖고 있으면 "안 돼요"를 "어느 구간의 실패인가"로 분해할 수 있고, 개발자도구 Timing과 curl -w가 그 분해를 그대로 숫자로 보여준다.
