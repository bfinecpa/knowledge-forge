Nginx-Tomcat 타임아웃/버퍼 불일치
계층 간 설정이 어긋나면 생기는 유령 현상

면접 질문: "Nginx와 Tomcat 사이의 타임아웃/버퍼 설정 불일치로 생길 수 있는 문제는?"

핵심 관전 포인트 — 요청 하나는 Nginx와 Tomcat 양쪽의 설정 나사를 모두 통과하는데, 두 계층은 서로의 설정값을 모른다. 이 불일치가 앱 로그에 흔적을 안 남기는 유령 현상을 만든다 — Nginx의 응답 대기(proxy_read_timeout)가 Tomcat의 처리 시간보다 짧으면 사용자는 504를 봤는데 Tomcat은 끝까지 처리해 커밋해버리는 "유령 성공", 유휴 연결을 닫는 타이머가 어긋나면 Tomcat이 방금 닫은 연결에 Nginx가 요청을 실어 보내는 간헐적 502, 본문 크기 한도가 앱 설정과 어긋나면 "특정 크기 근처에서만 실패하는 업로드", 응답 헤더가 proxy_buffer_size를 넘으면 "특정 사용자만 502"가 된다. 정렬 규칙은 방향이 둘로 갈린다 — 응답을 기다리는 상한은 바깥 계층이 안쪽보다 길어야 하고(클라이언트 ≥ CDN ≥ LB ≥ Nginx ≥ 앱의 최악 처리), 유휴 연결의 수명은 반대로 재사용하는 쪽이 닫는 쪽보다 짧아야 한다. 그리고 무엇이 어긋났는지는 Nginx error log의 문구가 지문처럼 알려준다.
  • 1
    불일치가 만드는 현상은 넷이고, 공통점은 "앱 로그가 깨끗하다"는 것 — 504 뒤의 유령 성공(응답 대기 < 처리 시간), 간헐적 502(유휴 연결 수명 경쟁), 특정 크기에서만 실패하는 업로드(본문 한도 불일치), 특정 사용자만 502(응답 헤더 > proxy_buffer_size). 전부 Nginx가 만든 응답이거나 앱은 성공으로 끝낸 뒤라서, 앱 지표만 보면 영원히 못 찾는다.
  • 2
    정렬 규칙은 두 개이고 방향이 서로 반대다 — 대기 상한은 바깥이 길게(클라이언트 ≥ CDN ≥ LB ≥ Nginx ≥ 앱), 유휴 수명은 재사용하는 쪽이 짧게(Nginx upstream keepalive_timeout < Tomcat keepAliveTimeout). 이유까지 말해야 한다 — 대기는 안쪽 일이 완주하도록 바깥이 더 기다려야 하고, 유휴는 닫는 결정을 재사용하는 쪽이 먼저 내려야 경쟁이 성립하지 않는다.
  • 3
    값을 제대로 정하려면 두 가지 사실을 알아야 한다 — proxy_read_timeout은 전체 응답 시간의 상한이 아니라 "아무 바이트도 안 오는 침묵 구간"의 상한이고(그래서 스트리밍은 몇 시간이어도 안 걸린다), Tomcat에는 "처리가 N초를 넘으면 중단"이라는 나사가 아예 없다(그래서 안쪽 상한은 앱이 @Transactional(timeout)·외부 호출 타임아웃으로 직접 만들어야 한다). 진단은 Nginx error log 문구 + $upstream_response_time으로 확정한다.

0. 질문 + 출제 의도

질문: "Nginx와 Tomcat 사이의 타임아웃/버퍼 설정 불일치로 생길 수 있는 문제는?"

출제 의도: 계층 간 설정 불일치가 만드는 유령 현상(업로드가 특정 크기에서만 실패, 간헐적 502)의 정체를 아는지 — 시스템을 자기 앱이 아니라 계층 스택 전체로 보는 시야를 확인한다. 이런 장애는 앱 로그에 단서가 없어서, 겪어본(또는 원리로 예측할 수 있는) 사람과 아닌 사람의 초동 대응이 극명하게 갈린다.

이 페이지가 겨냥하는 약점 세 가지 ① proxy_read_timeout을 "응답 전체 시간의 상한"으로 오해하는 것 → 3절에서 "침묵 구간의 상한"이라는 정확한 정의를 타임라인으로 갈라놓는다. 이 오해를 가진 채로는 SSE가 왜 안 끊기는지도, 왜 끊기는지도 설명할 수 없다.
② "타임아웃 늘리면 되죠"로 끝내는 것 → 4·6절에서 Tomcat에는 처리 시간 상한이 없다는 사실과 커밋이 응답 쓰기보다 먼저라는 순서를 보여주고, 값을 감이 아니라 안쪽에서 쌓아 올려 정하는 절차를 계산한다.
③ 설정 이름은 아는데 "어느 로그를 보고 판정하는지"를 못 말하는 것 → 10절에서 error log 문구 → 어긋난 나사 매핑과 $upstream_response_time이 타임아웃 값에 딱 붙어 있으면 성능 문제가 아니라 설정 부정합의 물증이라는 판정법을 만든다.

1. 나사는 양쪽에 — 요청 하나가 통과하는 상한 지도

요청 하나가 사용자에게서 DB까지 갔다 오는 길에는 계층마다 독립적으로 걸려 있는 상한이 여럿 있다. 그런데 각 계층은 자기 나사만 알고 상대의 나사를 모른다. Nginx는 Tomcat이 이 요청을 처리하는 데 얼마나 걸릴지 모르고, Tomcat은 Nginx가 언제쯤 기다리기를 포기할지 모른다. 두 값을 맞춰주는 자동 장치는 없다 — 사람이 손으로 맞춰야 한다.

비유 — 각자 다른 스톱워치를 든 두 사람 Nginx와 Tomcat은 같은 요청을 함께 처리하지만 서로의 스톱워치를 볼 수 없는 두 사람이다. Nginx는 자기 스톱워치가 15초를 가리키면 "이 사람 안 오는구나" 하고 자리를 뜨고, Tomcat은 그 사실을 통보받는 경로가 없어서 계속 일한다. 게다가 둘은 재는 단위도 다르다 — Nginx가 재는 것은 "상대가 말을 걸어온 시각 이후 흐른 시간"이고, Tomcat이 재는 것은 "네트워크에서 뭔가 오기를 기다린 시간"일 뿐 자기 일에 걸린 시간은 아무도 재지 않는다. 이 셋(서로 못 봄 · 통보 없음 · 재는 대상이 다름)이 이 문서 전체의 출발점이다.

1-1. 사람은 대개 한쪽만 만진다 — 그래서 어긋난다

업로드 크기를 늘려달라는 요구가 오면 Spring 설정만 고치고, 응답이 느리다는 말을 들으면 Nginx 타임아웃만 늘린다. 그렇게 두 값이 어긋난 채로 배포되면 어긋난 구간에 들어오는 요청만 실패한다. 이것이 유령 현상의 공통 구조이고, 특징이 셋이다.

유령 현상의 3특징 — 조 · 재 · 로

조건부로만 터진다
10MB짜리 파일만, 처리가 12초를 넘는 요청만, 권한이 많은 특정 사용자만 실패한다. 대부분의 요청은 멀쩡하므로 지표 대시보드에서는 잘 안 보인다.
재현이 어렵다
"어제는 됐는데요"가 나오는 이유는 어제 올린 파일이 8MB였기 때문이다. 조건이 데이터에 숨어 있어서 같은 조작을 반복해도 재현되지 않는다.
앱 로그에 아무것도 없다
반려 주체가 Nginx라 요청이 앱에 도달조차 안 했거나(413, 헤더 502), 앱은 성공으로 끝냈기 때문(504 유령 성공)이다.
"사용자는 에러를 봤는데 우리 로그는 깨끗하다" → 계층 간 불일치를 의심하는 것이 첫 반사 행동

2. 각 나사가 "무엇을 재는가" 사전

설정 이름만 나열하면 외울 수 없다. 각각이 어느 구간의 시간을 재는지를 정의하고 넘어가야, 나중에 로그를 보고 어느 나사가 터졌는지 짚을 수 있다. 아래 표의 맨 오른쪽 칸("터졌다는 뜻")이 실전에서 쓰는 부분이다.

계층별 나사 사전. 파란 줄은 "구간의 시간", 붉은 줄은 "유휴의 수명" — 6절에서 이 둘의 정렬 방향이 반대라는 이야기로 이어진다.
나사주체재는 구간이 값이 터졌다는 뜻

같은 이름, 다른 나사 — keepalive_timeout이 두 군데에 있다

http / server 블록의 것

  • 클라이언트 방향 유휴 연결의 수명
  • 브라우저·모바일 앱과 Nginx 사이
  • 여기를 고쳐도 백엔드 방향은 그대로다

upstream 블록 안의 것

  • 백엔드 방향 유휴 연결의 수명
  • Nginx와 Tomcat 사이 — 5절 간헐적 502의 주인공
  • 이름이 같아서 한쪽을 고치고 다른 쪽이 바뀌었다고 착각하는 일이 잦다

진단 팁: "keep-alive 값을 조정했는데 502가 그대로다"라는 상황이면 고친 쪽이 어느 블록이었는지부터 확인한다. nginx -T로 실제 적용된 전체 설정을 덤프하면 어느 블록에 어떤 값이 들어갔는지가 눈에 보인다.

Tomcat에 없는 나사 — 이 문서에서 가장 중요한 한 줄

타임아웃은 처리를 중단시키는 게 아니라 기다림을 중단시킬 뿐이다

connectionTimeout도 keepAliveTimeout도 전부 "네트워크에서 무언가 오기를 기다리는 시간"이다. "이 요청 처리가 N초를 넘으면 스레드를 끊는다"는 설정은 Tomcat에 없다. 그래서 Nginx가 포기해도 Tomcat 스레드를 멈출 방법이 인프라 설정에는 존재하지 않는다.

안쪽의 시간 상한은 애플리케이션이 스스로 만들어야 한다 — 외부 API 호출의 connect/read 타임아웃, @Transactional(timeout = ...), JDBC 문장의 queryTimeout, 비동기 요청이라면 spring.mvc.async.request-timeout. 이 값들의 합이 사실상 우리 서비스의 최악 처리 시간이 되고, 6절의 정렬은 그 합에서 출발한다.

3. proxy_read_timeout은 전체 응답 시간의 상한이 아니다

2절 표에서 두 번 언급한 "연속된 두 번의 읽기 사이"라는 단서를 따로 떼어 설명한다. 이 오해가 이 주제에서 가장 흔하고, 오해한 채로는 설명이 안 되는 현상이 여럿 생기기 때문이다.

흔한 오해

proxy_read_timeout 10s
= "응답 전체가 10초 안에 끝나야 한다"

  • 이 오해로는 "30초 걸리는 다운로드는 왜 안 끊기지?"를 설명할 수 없다
  • "SSE 연결은 왜 몇 시간씩 유지되지?"도 설명할 수 없다

정확한 정의

proxy_read_timeout 10s
= "백엔드로부터 아무 바이트도 못 받은 채로 10초가 지나면 포기"

  • 타이머는 바이트가 하나라도 도착할 때마다 0으로 초기화된다
  • 즉 재는 것은 총 시간이 아니라 "침묵 구간의 길이"다

이 성질에서 바로 나오는 실무 결론 셋

SSE는 하트비트로 지킨다
보낼 이벤트가 없으면 침묵 구간이 타임아웃을 넘겨 끊긴다. 타임아웃을 몇 시간으로 늘리는 대신 하트비트 주기를 타임아웃보다 짧게 잡는 것이 더 나은 해법이다 — 값을 늘리면 진짜로 멈춘 백엔드도 몇 시간 붙들게 되기 때문이다.
느린 업로드에 proxy_send_timeout은 헛다리
모바일 회선에서 5분이 걸려도 클라이언트가 계속 조금씩 보내고 있다면 이 값에 걸리지 않는다. 업로드 실패의 진짜 원인은 대개 크기 한도(7절) 쪽이다.
위험한 것은 "한 번에 몰아 쓰는" 응답
처리를 다 끝낸 뒤 응답을 한 번에 쓰는 일반적인 JSON API가 정확히 케이스 A다. 처리 시간 전체가 그대로 침묵 구간이 되므로, 이 API들에서만 504가 난다.

4. 유령 성공 — 504를 보낸 뒤에도 Tomcat 스레드는 돈다

Nginx의 응답 대기 상한이 Tomcat의 실제 처리 시간보다 짧을 때 벌어지는 일이다. 무거운 통계 쿼리나 느린 외부 API 호출이 끼어 있는 API에서 전형적으로 나온다. 2절에서 짚었듯이 Tomcat에는 처리를 중단시키는 나사가 없으므로, Nginx가 포기해도 Tomcat은 아무 일 없다는 듯 일을 계속한다.

4-1. 대응은 세 방향이고, 순서가 있다

1
근본 — 그 요청이 왜 그렇게 오래 걸리는지를 고친다. 쿼리를 튜닝하거나, 애초에 동기 요청으로 처리할 일이 아니면 비동기로 바꾼다 — 즉시 "접수했습니다"를 202로 응답하고 실제 처리는 뒤에서 하며, 클라이언트는 폴링이나 알림으로 결과를 받는다. 10초 넘게 걸리는 동기 HTTP 요청은 대개 설계가 잘못된 것이라는 인식이 먼저다.
2
계층 간 타임아웃을 정렬한다. Nginx의 대기 상한이 Tomcat의 최악 처리 시간(관측된 p99에 여유를 더한 값)보다 길게 만든다. 다만 무작정 늘리는 것은 답이 아니다 — 상한을 60초로 키우면 느린 요청 하나가 Nginx 커넥션과 Tomcat 스레드를 60초씩 붙들게 허용하는 것이고, 그런 요청이 몰리면 스레드 풀이 고갈돼 전체 장애가 된다. 늘리기 전에 "이 시간이 정말 허용 가능한가"를 먼저 물어야 한다. (절차는 6절)
3
쓰기 API를 멱등하게 만든다. 타임아웃은 아무리 정렬해도 완전히 없앨 수 없다. 같은 요청이 두 번 와도 결과가 한 번 실행한 것과 같도록 멱등성 키를 도입하는 것이 최종 방어선이다. (04-http-method-idempotency-and-safety.md 3절)
Before 안쪽 상한이 아예 존재하지 않는 상태
// PG사가 응답을 안 주면 Tomcat 스레드는 무한정 붙들린다.
// Nginx만 혼자 포기해 504 + 유령 성공이 된다.
@Bean
RestClient pgClient() {
    return RestClient.create("https://pg.example.com");타임아웃 없음
}

// 트랜잭션에도 상한이 없다 — 락 대기나 느린 쿼리로
// 커넥션이 무한정 묶이면 최악 처리 시간을 계산할 수 없다.
@Transactionaltimeout 미지정
public OrderResult placeOrder(OrderCommand command) { ... }
After 안쪽 상한을 앱이 스스로 만든다
@Bean
RestClient pgClient() {
    var factory = new SimpleClientHttpRequestFactory();
    // TCP 연결 수립까지. 같은 리전이면 1초면 충분하고, 이 값이
    // 터진다는 것은 상대가 느린 게 아니라 닿지 않는다는 뜻이다.
    factory.setConnectTimeout(Duration.ofSeconds(1));
    // 응답 대기 상한. 없으면 스레드가 영원히 묶인다.
    factory.setReadTimeout(Duration.ofSeconds(2));
    return RestClient.builder()
            .baseUrl("https://pg.example.com")
            .requestFactory(factory).build();
}

// 이 값들의 합이 사실상 우리 서비스의 최악 처리 시간이 된다.
// Nginx의 proxy_read_timeout은 이 합보다 길어야 한다.
@Transactional(timeout = 5)안쪽 상한 확정
public OrderResult placeOrder(OrderCommand command) { ... }
이 코드를 고치는 것이 "타임아웃 늘리기"보다 먼저인 이유 Nginx 값을 정하려면 안쪽 최악 처리 시간이라는 숫자가 먼저 있어야 한다. Before 상태에서는 그 숫자가 존재하지 않으므로(무한대), Nginx 값을 아무리 늘려도 근거 없는 추측이 된다. 안쪽에 상한을 만드는 것이 곧 정렬의 출발점을 만드는 일이고, 그래서 6절의 계산은 항상 가장 안쪽 호출부터 시작한다.

5. keep-alive 유휴 경쟁 → 부하와 무관한 간헐적 502

이번에는 시간의 길이가 아니라 누가 먼저 연결을 닫느냐의 순서가 문제가 되는 경우다. 전제부터 깔자. Nginx와 Tomcat 사이의 연결을 요청마다 새로 맺으면 handshake 비용을 매번 치르고 TIME_WAIT도 쌓이므로, upstream 블록에 keepalive를 설정해 유휴 연결을 풀에 넣어두고 재사용한다. 그런데 이 유휴 연결을 "언제 닫을지" 결정하는 타이머가 양쪽에 따로 있다.

유휴 연결 수명의 정렬 규칙

연결을 재사용하는 쪽(Nginx)의 유휴 상한이  <  연결을 들고 있다가 닫는 쪽(Tomcat)의 유휴 상한

6절에서 보겠지만 이 방향은 대기 상한의 정렬 방향과 정반대다. 두 규칙을 구분해 말하는 것이 이 주제의 채점 포인트다.

Nginx upstream keep-alive의 정석 세트 — 다섯 줄이 한 묶음
upstream tomcat_upstream {
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;

    # 워커 프로세스 "하나가" 유지할 유휴 업스트림 연결 수.
    # 전체가 아니라 워커당이므로, worker_processes를 곱한 값이
    # Tomcat의 최대 커넥션 수용량을 넘지 않아야 한다.
    keepalive 64;

    # ★ 이 절의 핵심. Tomcat의 keepAliveTimeout보다 확실히 짧게.
    keepalive_timeout 30s;upstream 블록 = 백엔드 방향 전용

    # 연결 하나로 몇 건까지 나른 뒤 폐기할지. 너무 작으면 재사용
    # 이득이 사라지고, 무한정 두면 백엔드를 교체해도 옛 인스턴스에
    # 계속 붙어 있게 된다.
    keepalive_requests 1000;
}

server {
    location /api/ {
        proxy_pass http://tomcat_upstream;

        # keep-alive는 HTTP/1.1의 기능이다. Nginx는 업스트림에
        # 기본적으로 HTTP/1.0으로 말하므로, 이 줄이 없으면
        # 위의 keepalive 설정이 전부 무용지물이 된다.
        proxy_http_version 1.1;
        # Nginx는 업스트림 요청에 기본으로 Connection: close를 붙인다.
        # 빈 문자열로 덮어 헤더를 없애면 HTTP/1.1 기본값(유지)이 적용.
        proxy_set_header Connection "";
    }
}
Spring Boot 닫는 쪽 — 위 Nginx 값보다 넉넉해야 한다
server:
  tomcat:
    # 명시하지 않으면 connectionTimeout 값을 따라가므로,
    # "안 건드렸다"는 것은 "값을 모른다"와 같은 뜻이 된다.
    # 반드시 박아둔다.
    keep-alive-timeout: 60sNginx 30s의 2배

    # 연결 하나로 받을 최대 요청 수. 이 값이 작으면 Tomcat이
    # 먼저 끊는 일이 잦아져 Nginx의 재사용 이득이 사라지고
    # 경쟁 창도 자주 열린다.
    max-keep-alive-requests: 1000
두 값이 짝을 이루지 않으면 생기는 두 번째 함정 maxKeepAliveRequests가 Nginx의 keepalive_requests보다 작으면, 유휴 타이머를 아무리 잘 맞춰도 Tomcat이 요청 건수를 채워 먼저 닫는 같은 경쟁이 반복된다. 수명은 시간과 건수 두 축으로 관리된다는 것을 함께 기억한다.

5-1. 여기에 proxy_next_upstream이 얽힌다 — "같은 버그가 운영에서만 보이는" 이유

이 지시자는 "업스트림에서 어떤 실패가 났을 때 다음 서버로 요청을 넘길지"를 정하고, 기본값은 error timeout이다. keep-alive 경쟁으로 인한 끊김은 error로 분류되므로 다음과 같이 갈린다.

업스트림 그룹에 서버가 여러 대면

  • Nginx가 조용히 다른 서버로 넘겨 사용자 눈에는 502가 안 보일 수 있다
  • 대신 증상이 숨겨진 채 재시도 비용만 계속 나간다

서버가 한 대뿐인 그룹이면

  • 넘길 곳이 없어 그대로 502가 된다
  • 같은 버그가 스테이징에서는 안 보이고 운영에서만 보이거나 그 반대인 이유가 대개 이것이다

프록시의 재시도도 멱등성 검토 대상이다

넘긴다는 것은 같은 요청을 한 번 더 실행한다는 뜻이므로, 비멱등 요청(POST)이라면 중복 처리 위험이 생긴다. 다행히 최근 Nginx는 요청을 이미 업스트림에 보낸 뒤라면 POST 같은 비멱등 메서드를 기본적으로 다음 서버로 넘기지 않는다 — 이 동작을 굳이 허용하는 non_idempotent 파라미터가 따로 있고, 그것을 켜는 순간 중복 처리가 가능해진다.

더 자주 놓치는 것은 timeout이 기본 재시도 조건에 이미 들어 있다는 점이다. GET처럼 멱등으로 "선언된" 메서드가 실제로는 부작용을 만드는 코드라면, 프록시 계층이 조용히 그것을 두 번 실행시킨다.

Nginx 기본값을 "그냥 두는 것"과 "알고 두는 것"은 다르다
location /api/ {
    proxy_pass http://tomcat_upstream;

    # 아래는 "연결 단계 실패만 넘긴다"는 보수적 선택 —
    # 요청이 백엔드에 닿기 전이므로 중복 실행 위험이 없다.
    proxy_next_upstream error;기본값의 timeout을 뺀 것

    # 넘기는 횟수와 총 시간에도 상한을 둔다. 없으면 장애 시 한 요청이
    # 모든 백엔드를 순회하며 전체 응답 시간을 몇 배로 키운다.
    proxy_next_upstream_tries 2;
    proxy_next_upstream_timeout 5s;
}

6. 정렬 규칙은 둘이고, 방향이 서로 반대다 시니어 변별

실제 요청 경로는 Nginx와 Tomcat 두 층이 아니다. 클라이언트 → CDN → LB → Nginx → Tomcat → 앱의 외부 호출처럼 더 길고, 각 층이 전부 자기 대기 상한을 들고 있다. 여기에 유휴 연결 수명이라는 방향이 정반대인 규칙이 하나 더 겹친다.

이 문서에서 외울 것이 하나뿐이라면 이것 — 대바깥 · 유안쪽

대기 상한은 바깥이 길게

클라이언트 ≥ CDN ≥ LB ≥ Nginx ≥ 앱의 최악 처리

  • 왜: 대기 상한은 "일이 끝나기를 기다리는 시간"이라, 바깥이 더 오래 기다려야 안쪽 일이 완주한다
  • 어기면 → 유령 성공(4절). 층이 여러 개면 그 사고가 층마다 반복된다

유휴 수명은 안쪽이 길게

재사용하는 쪽 < 닫는 쪽

  • 왜: 유휴 수명은 "쓰지 않는 연결을 들고 있는 시간"이라, 재사용하는 쪽이 먼저 정리해야 "이미 닫힌 연결에 요청을 싣는" 경쟁이 안 생긴다
  • 어기면 → 간헐적 502(5절)
"대기 상한은 바깥이 길게, 유휴 수명은 안쪽이 길게" — 이 두 문장을 구분해서, 이유까지 말하면 한 번 정리해 본 사람으로 들린다

6-1. 값을 정하는 절차 — 감이 아니라 안쪽에서 쌓아 올린다

1
가장 안쪽 호출의 상한을 합산한다. 예시: PG사 호출 1회 = connect 1s + read 2s = 3.0s → 재시도 1회 + 백오프 0.5s = 3.0 + 0.5 + 3.0 = 6.5s → DB 쿼리 + 비즈니스 로직 최악 +1.5s → 앱 내부 최악 처리 시간 합 = 8.0s. 재시도와 백오프를 빼먹으면 계산이 통째로 틀어진다는 것이 여기서 가장 자주 나는 실수다.
2
층을 올라갈 때마다 여유를 더한다. 8s에 +2s(스레드 배정 대기, GC 정지) → 앱 자체 가드 10s. 여기에 +5s씩 더해 Nginx 15s → LB 20s → CDN 25s → 클라이언트 30s.
3
하향식으로도 계산해 중간에서 만나는지 검산한다. 사용자 응답 SLO에서 출발해 바깥에서 안으로 예산을 나눠주는 계산(타임아웃 예산)을 함께 한다. 상향식으로 쌓은 8초가 하향식으로 나눈 예산을 넘어서면, 타임아웃을 조정할 게 아니라 그 처리 자체를 바꿔야 한다는 신호다.
여유를 두는 이유 — "아직 시작도 못 한 시간"이 층 사이에 끼어 있다 안쪽 값에 딱 붙여 놓으면 안 되는 것은, 요청이 Nginx에 도착한 뒤 Tomcat의 스레드를 배정받기까지 큐에서 기다리는 시간, 네트워크 왕복, GC 정지 같은 것이 층과 층 사이에 끼어 있기 때문이다. 이 시간은 안쪽 처리 시간에 포함되지 않는데 바깥 타이머는 이미 돌고 있다. 부하가 올라갈수록 이 "끼인 시간"이 커지므로, 여유가 없는 정렬은 트래픽이 늘 때 먼저 무너진다.

7. 크기 불일치 → 413, 그리고 이분 탐색 진단

이번에는 시간이 아니라 크기의 불일치다. 증상은 "작은 파일은 되는데 큰 파일만 안 된다"로 나타난다. Nginx의 client_max_body_size는 클라이언트가 보낸 요청 본문의 최대 크기이고 기본값은 1MB다. 이 값을 넘는 요청은 Tomcat에 도달하기 전에 Nginx가 413으로 반려한다.

Nginx는 본문을 다 받아보고 판단하지 않는다
Content-Length 헤더 값을 보고 즉시 거절한다. 그래서 100MB 파일을 올리면 100MB를 다 전송한 뒤 실패하는 게 아니라 시작하자마자 413이 온다. 대역폭을 아끼는 좋은 동작이지만, 아래 maxSwallowSize 이야기의 배경이기도 하다.
413의 이름이 두 개인 이유
Nginx 기본 에러 페이지에는 413 Request Entity Too Large로 나오는데, 최신 HTTP 명세에서는 같은 코드가 Content Too Large로 개명됐다. 같은 것이다.

7-1. max-file-size와 max-request-size — 같은 값으로 두면 경계에서 어긋난다

단위 함정 — 사람이 보는 MB와 서버가 재는 MB가 다를 수 있다

Nginx의 m과 Spring의 MB는 둘 다 1024×1024 기준이라 서로 어긋나지 않는다. 다만 운영체제 파일 탐색기가 보여주는 "MB"는 1,000,000 기준일 수 있어서, 경계 근처에서는 사람이 보는 숫자와 서버가 재는 숫자가 다르다. 경계 테스트는 바이트 단위로 만든 파일로 해야 한다.

Before 기본값 1m — 앱 로그에 흔적조차 없다
# 프로필 이미지 2MB 업로드가 413으로 반려된다.
# 앱에는 요청이 도달조차 하지 않으므로
# 앱 로그에는 아무 흔적이 없다.
server {
    # client_max_body_size 미지정 → 기본 1m1MB
    location /api/ {
        proxy_pass http://tomcat_upstream;
    }
}
After 판정자를 앱으로 두고 Nginx는 살짝 크게

8. 응답 헤더 > proxy_buffer_size → "특정 사용자만 502"

이번 불일치는 본문이 아니라 응답 헤더의 크기에서 난다. 그리고 증상이 특이해서 원인을 모르면 아주 오래 헤맨다.

전제 — 헤더는 버퍼 하나에 통째로 들어가야 한다

Nginx는 백엔드 응답의 상태 줄과 헤더 전체를 proxy_buffer_size 하나에 담아야 한다. 헤더가 여러 버퍼에 나뉘어 담기는 구조가 아니다. 기본값은 4KB 또는 8KB(플랫폼의 메모리 페이지 크기)인데, 정확한 값은 빌드에 따라 다르므로 nginx -T로 확인하는 편이 낫다. 넘으면 upstream sent too big header를 남기고 502다.

Before 기본 버퍼
# 권한 클레임이 많은 사용자의 JWT가 헤더에 실리면
# upstream sent too big header 로그와 함께 502.
location /api/ {
    proxy_pass http://tomcat_upstream;proxy_buffer_size 미지정 = 4k/8k
}
After 헤더 버퍼를 키운다 — 단, 대증요법임을 알고
location /api/ {
    proxy_pass http://tomcat_upstream;

    # 응답 상태 줄 + 헤더 전체가 이 한 조각에 들어가야 한다.
    # 실제 헤더 크기를 측정한 뒤 여유를 두고 정한다(감으로 X).
    proxy_buffer_size 16k;

    # 응답 "본문"을 담을 버퍼들. 헤더 판정과는 별개지만,
    # 헤더를 키울 때 본문 버퍼도 함께 검토하는 것이 관례다.
    proxy_buffers 8 16k;
}
설정을 키우는 것은 대증요법이다 — 근본은 헤더에 큰 데이터를 싣지 않는 것 권한 정보 전체를 JWT에 넣는 대신 필요한 최소 클레임만 넣고 나머지는 서버에서 조회하거나, 응답 본문으로 내리는 설계가 맞다. 헤더는 모든 프록시가 버퍼에 담아야 하는 공용 자원이므로 커질수록 모든 계층에서 문제가 된다 — 오늘 Nginx 버퍼를 키워도 내일 CDN이나 LB에서 같은 벽을 만난다.

혼동하기 쉬운 것 — 요청 헤더가 큰 경우는 완전히 다른 나사다

응답 헤더가 큰 경우

  • 관할: proxy_buffer_size
  • 결과: 502 (Nginx가 백엔드 응답을 못 담음)
  • 방향: 백엔드 → Nginx

요청 헤더가 큰 경우

  • 관할: large_client_header_buffers (완전히 다른 지시자)
  • 결과: 4xx 계열
  • 방향: 클라이언트 → Nginx. Tomcat/Spring 쪽에도 요청 헤더 상한이 따로 있다

"쿠키가 커서 안 된다"는 증상은 요청 방향인지 응답 방향인지부터 갈라야 한다. 상태 코드가 5xx면 응답 방향, 4xx면 요청 방향이라는 것이 1차 분기다.

9. 버퍼링 off의 대가와 X-Accel-Buffering

여기서는 좋은 기본값이 특정 요구와 정면으로 충돌하는 사례를 다룬다. proxy_buffering은 기본이 on이고, 이 상태에서 Nginx는 Tomcat의 응답을 자기 버퍼에 최대한 빨리 받아 챙긴 뒤 Tomcat 스레드를 즉시 놓아주고, 클라이언트에게는 그쪽 속도에 맞춰 천천히 흘려보낸다. 느린 클라이언트로부터 비싼 WAS 스레드를 격리하는 장치다. (버퍼링의 원리와 처리량 효과는 12-nginx-roles-and-event-driven-architecture.md 5절)

그런데 이 좋은 기본값이 스트리밍 응답과는 정면으로 충돌한다 SSE는 서버가 이벤트를 만들 때마다 즉시 흘려보내는 방식인데, 버퍼링이 켜져 있으면 Nginx가 이벤트를 버퍼에 모아두고 있어서 실시간성이 깨지거나 버퍼가 찰 때까지 아무것도 전달되지 않는다. "로컬에서는 알림이 즉시 오는데 배포하면 안 온다"는 제보의 단골 원인이다.

지금까지 본 불일치들은 전부 Nginx error log에 서로 다른 문구를 남긴다. 그래서 로그 한 줄만 읽으면 어느 나사가 어긋났는지 바로 좁혀진다. 이 매핑이 이 주제에서 실무적으로 가장 값나가는 지식이다.

error log만으로는 "어느 요청이었는지"를 액세스 로그와 이어 붙이기 어렵다. 그래서 액세스 로그에 업스트림 관련 변수를 미리 남겨둬야 한다. 장애가 난 뒤에 추가하면 그 장애는 이미 놓친 것이다.

Nginx 계층 간 불일치를 판정하기 위한 최소 로그 포맷
log_format upstreamlog
    '$remote_addr "$request" '
    # 내가 클라이언트에게 내보낸 코드
    'status=$status '
    # 업스트림이 나에게 준 코드. 비어 있으면(-) 응답을 아예 못 받았다는 뜻이고,
    # 그 경우 그 코드는 "Nginx가 만든 것"이 확정된다.
    'upstream_status=$upstream_status '
    # 연결 수립까지 걸린 시간. proxy_connect_timeout에 붙어 있으면 연결 단계 문제.
    'ucon=$upstream_connect_time '
    # 응답 헤더의 첫 바이트까지 걸린 시간 = 백엔드의 실질 처리 시간.
    'uhdr=$upstream_header_time '
    # 업스트림 응답 전체 시간. ★ 이 값이 proxy_read_timeout에 딱 붙어 있으면
    #   "백엔드가 느렸다"가 아니라 "Nginx가 못 기다렸다"는 확정 증거다.
    'ures=$upstream_response_time';

불일치가 만드는 현상 4종?
504+유령 성공(대기<처리) · 간헐적 502(유휴 수명 경쟁) · 특정 크기 업로드 실패(본문 한도) · 특정 사용자만 502(응답 헤더>버퍼). 공통점은 앱 로그가 깨끗하다.
정렬 규칙 두 문장?
대바깥 · 유안쪽 — 대기 상한은 바깥이 길게(완주 보장), 유휴 수명은 재사용하는 쪽이 짧게(닫는 순서 보장). 방향이 반대인 이유까지 말해야 한다.
proxy_read_timeout의 정확한 정의?
전체 응답 시간이 아니라 "아무 바이트도 안 오는 침묵 구간"의 상한. 바이트가 오면 타이머가 0으로 리셋. 그래서 스트리밍은 몇 시간이어도 안 걸린다.
유령 성공의 핵심 한 문장?
커밋이 응답 쓰기보다 먼저다. 타임아웃은 처리를 중단시키는 게 아니라 기다림을 중단시킬 뿐이고, Tomcat에는 처리 시간 상한이라는 나사가 없다.
유휴 경쟁을 Nginx가 못 피하는 이유?
Tomcat의 FIN은 "내 송신 방향이 끝났다"는 통보라 Nginx의 송신은 열려 있고 write()가 성공해 버린다. 실패는 응답을 읽으려는 순간에야 드러난다.
max-file-size와 max-request-size?
전자는 파일 하나, 후자는 요청 전체(파일+폼 필드+경계 문자열+파트 헤더). 같은 값으로 두면 정확히 그 크기 파일이 후자에 걸린다.
"413 대신 연결이 끊긴다"의 범인?
maxSwallowSize. 반려 후 남은 본문을 삼킬 수 없으면 연결을 그냥 닫아, 클라이언트가 에러 응답을 읽기 전에 끊김을 먼저 감지한다.
응답 헤더가 커지는 원인 셋?
쿠 · 토 · 리 — 여러 Set-Cookie · 권한 많은 사용자의 JWT · OIDC Location의 state/nonce. 관할은 proxy_buffer_size(응답 전용).
error log 동사 5개?
connecting(못 닿음·504) / reading+timed out(못 기다림·504) / prematurely closed(상대가 끊음·502) / too big header(못 담음·502) / too large body(반려·413).
설정 부정합의 물증 한 가지?
$upstream_response_time이 타임아웃 값에 소수점까지 딱 붙어 뭉쳐 있는 요청들. + $upstream_status가 -면 그 5xx는 Nginx가 만든 것.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

간헐적으로 502가 나는데 Tomcat 메트릭은 멀쩡합니다. 뭘 의심하겠어요? 필수힌트: "무엇을 의심한다"보다 "어디를 보고 판단한다"를 먼저 말해야 한다

먼저 Nginx error log의 문구를 본다. 이 질문에서 가장 중요한 것은 "무엇을 의심하겠다"보다 "어디를 보고 판단하겠다"를 먼저 말하는 것이다. 502는 Nginx가 만든 코드이므로 1차 증거가 Nginx에 있다. 그다음 문구별로 갈린다.

prematurely closed
keep-alive 유휴 경쟁이 1순위 가설. Tomcat이 유휴 연결을 닫는 순간과 Nginx가 재사용하는 순간이 겹친 것이고, FIN을 받아도 write()는 성공하므로 Nginx가 미리 알 수 없다. 대응은 upstream keepalive_timeout < Tomcat keepAliveTimeout 정렬.
Connection refused
발생 시각이 배포 시점과 겹친다면 롤링 재시작의 틈을 의심한다. graceful shutdown이 없거나, LB 대상 제외보다 프로세스 종료가 먼저 일어나는 순서 문제다.
too big header
응답 헤더 크기. "간헐적"으로 보이는 이유가 시간이 아니라 사용자에 따라 다르기 때문이므로, 실패한 요청들의 계정 특성(권한 수, 소속 조직 수)을 확인한다.
핵심은 "Tomcat이 멀쩡해 보여도 두 계층 사이의 연결 수명 관리나 버퍼 크기 문제일 수 있다"는 방향 전환 — Tomcat 지표만 계속 들여다보면 영원히 못 찾는다
Nginx가 504를 반환한 뒤 Tomcat에서 처리 중이던 요청은 어떻게 되나요? 필수힌트: "취소됩니다"라고 답하면 절반이 아니라 0점이다. 그리고 방어를 세 겹으로 말한다

그대로 끝까지 실행된다. 타임아웃은 Nginx의 기다림을 끊을 뿐 Tomcat의 처리를 중단시키지 않는다. 더 정확히 말하면 Tomcat에는 "처리 시간이 N초를 넘으면 중단"이라는 나사 자체가 없다 — connectionTimeout이나 keepAliveTimeout은 전부 네트워크에서 무언가를 기다리는 시간이지 로직 실행 시간의 상한이 아니다.

그래서 트랜잭션은 커밋되고, 그 뒤에 응답을 쓰려다 이미 닫힌 소켓을 만나 ClientAbortException이 난다. 커밋이 응답 쓰기보다 먼저라는 순서가 유령 성공의 전부다. 사용자는 실패로 인지하고 재시도하므로 쓰기 요청이면 중복 처리가 된다.

방어는 세 겹으로 말하면 좋다.

(1) 안쪽 상한을 앱이 만든다
외부 호출 타임아웃, @Transactional(timeout), 쿼리 타임아웃. 인프라가 안 해주므로 앱이 해야 한다.
(2) 계층 간 타임아웃 정렬
바깥 상한 안에 안쪽 최악 소요가 들어오게. 값은 감이 아니라 안쪽에서 쌓아 올려 정한다.
(3) 멱등성 키
타임아웃은 완전히 없앨 수 없으므로 최종 방어선은 애플리케이션 레벨이다.

"타임아웃 뒤 재시도는 멱등성과 세트"라는 원칙이 프록시 계층에도 그대로 적용된다는 것이 이 질문의 결론이다 — proxy_next_upstream의 기본값에 timeout이 들어 있다는 사실이 그 증거다.

업로드가 10MB 근처에서만 실패한다는 제보를 받으면 어떤 순서로 봅니까? 함정힌트: 설정 이름을 나열하기 전에 "층이 다섯 개뿐"이라는 프레이밍을 먼저 깔아야 한다

크기 의존적 실패는 경로상 어딘가의 크기 한도이고, 층이 최대 다섯 개(CDN → LB → Nginx → Tomcat → Spring)뿐이므로 이분 탐색으로 두세 번이면 좁혀진다는 것을 먼저 말한다.

0단계, 경계를 바이트 단위로 확정한다. "10MB쯤"으로는 판단이 흔들린다 — 파일 탐색기의 MB는 1,000,000 기준일 수 있고 서버는 1,048,576 기준으로 재기 때문이다.

1단계, 실패 응답의 지문을 본다. 413에 Nginx 기본 에러 페이지면 client_max_body_size, 413이나 500에 우리 서비스의 에러 JSON이면 Spring multipart 한도, 연결이 그냥 끊기면 maxSwallowSize를 의심한다. 마지막 것을 알고 있으면 확실히 변별된다.

2단계, 층을 건너뛰고 직접 때려본다. Nginx를 건너뛰고 Tomcat 사설 IP:8080으로 같은 파일을 보내서 성공하면 경계는 Nginx 이상에 있고, 실패하면 앱 쪽이다. 이것이 이분 탐색의 본체다.

3단계, 로그로 확정한다. Nginx의 client intended to send too large body: N bytes에서 N이 서버가 실제로 본 크기이므로, 사람이 말한 숫자와 다르면 multipart 오버헤드나 단위 착오가 끼어 있다는 뜻이다.

여기에 max-file-size와 max-request-size의 차이를 덧붙이면 답이 완성된다. 전자는 파일 하나, 후자는 요청 전체(여러 파일 + 폼 필드 + multipart 경계·파트 헤더)이므로, 둘을 같은 값으로 잡으면 정확히 그 크기의 파일 하나가 오버헤드 때문에 후자에 걸린다.

근본 대응은 파일 크기 요구사항이 바뀔 때 전 계층 한도를 함께 바꾸는 체크리스트 — 한 층만 늘리면 다음 층에서 같은 장애가 반복된다
계층별 타임아웃 값은 어떤 원칙으로 정하나요? 시니어 변별힌트: 규칙이 두 개이고 방향이 반대라는 것을 "구분해서" 말하는 것이 채점 포인트다

규칙이 두 개이고 방향이 서로 반대라는 것을 구분해 말하는 것이 이 질문의 채점 포인트다.

첫째, 대기 상한은 바깥이 길어야 한다. 클라이언트 ≥ CDN ≥ LB ≥ Nginx ≥ 앱의 최악 처리 시간 순이다. 이유는 명확하다 — 안쪽이 아직 일하고 있는데 바깥이 먼저 끊으면 유령 성공이 생기고, 층이 여러 개면 그 사고가 층마다 반복된다.

둘째, 유휴 연결 수명은 안쪽이 길어야 한다. 재사용하는 쪽(Nginx)의 유휴 상한이 연결을 들고 있는 쪽(Tomcat)보다 짧아야, 닫는 결정을 재사용하는 쪽이 먼저 내리게 되어 경쟁 조건이 성립하지 않는다.

두 규칙이 반대인 이유까지 말해야 외운 게 아닌 것으로 들린다. 대기 상한은 "일이 끝나기를 기다리는 시간"이라 바깥이 더 오래 기다려야 안쪽 일이 완주하고, 유휴 수명은 "쓰지 않는 연결을 들고 있는 시간"이라 재사용하는 쪽이 먼저 정리해야 사고가 안 난다.

값을 정하는 방법도 함께 말한다. 감으로 정하는 게 아니라 안쪽에서 바깥으로 쌓아 올린다 — 외부 호출 타임아웃과 재시도·백오프를 합쳐 최악 소요를 구하고, 스레드 배정 대기와 GC 정지를 감안한 여유를 더해 상위 층 값을 정한다. 동시에 사용자 응답 SLO에서 출발해 바깥에서 안으로 나눠주는 하향식 계산도 해서 둘이 중간에서 만나는지 검산한다. 만나지 않으면 타임아웃을 조정할 게 아니라 그 처리 자체를 바꿔야 한다는 신호다.

마지막으로 "Tomcat에는 처리 시간 상한이라는 나사가 없으므로 안쪽 상한은 앱이 스스로 만들어야 한다"까지 말하면, 설정 표를 외운 게 아니라 구조를 이해한 것으로 들린다.

proxy_buffering은 끄는 게 좋은가요, 켜는 게 좋은가요? 가산점힌트: "SSE 때문에 끕니다"에서 멈추면 절반이다. 무엇을 포기하는 것인지를 말해야 한다

기본은 켠다. 버퍼링은 Tomcat의 응답을 Nginx가 빠르게 받아 챙기고 Tomcat 스레드를 즉시 놓아주는 장치이므로, 느린 클라이언트로부터 비싼 WAS 스레드를 격리하는 보호막이다. 이것을 전역으로 끄면 응답 전송이 클라이언트 속도에 묶여 Tomcat 스레드 점유 시간이 늘고, 모바일 사용자가 많으면 스레드 풀이 고갈된다.

끄는 것은 즉시성이 필수인 특정 경로에 한해 location 단위로 한다. SSE나 스트리밍 다운로드가 그것이다. 버퍼링이 켜져 있으면 이벤트가 버퍼에 갇혀 "로컬에서는 되는데 배포하면 알림이 안 온다"가 된다.

여기서 한 걸음 더 들어가면 변별이 된다. 버퍼링을 끄는 순간 그 보호 효과를 스스로 걷어내는 것이므로, SSE 경로는 인프라 설정만으로 끝나지 않는다. SSE는 애초에 서블릿 스레드를 붙들지 않는 비동기 방식(SseEmitter, 리액티브 스택)으로 구현해야 동시 접속자 수가 스레드 풀 크기에 묶이지 않는다. "버퍼링만 끄면 된다"는 답은 절반이다.

그리고 X-Accel-Buffering: no 응답 헤더로 앱이 응답 단위로 선언하는 방법까지 말하면 인프라와 앱의 협업 방식을 아는 것으로 보인다. location 블록을 고치려면 인프라 담당자를 거쳐야 하지만, 이 헤더는 앱 코드만으로 끝난다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

proxy_read_timeout을 60초로 늘리면 504가 사라지지 않나요? 함정힌트: 사라진다. 그런데 무엇을 대신 지불하는지를 말해야 한다

504는 사라진다. 문제는 그 대가를 계산했느냐다. 상한을 60초로 키운다는 것은 느린 요청 하나가 Nginx 커넥션과 Tomcat 스레드를 60초씩 붙들게 허용한다는 뜻이다. 스레드 풀이 200이라면 그런 요청 200개면 서비스 전체가 멈춘다 — 특정 API의 504가 전체 서비스 장애로 승격되는 것이다.

게다가 504가 사라졌다고 유령 성공이 사라진 것도 아니다. 처리 시간이 60초를 넘는 날이 오면 같은 일이 그대로 반복되고, 그때는 더 많은 스레드가 묶인 상태에서 벌어진다.

순서는 이렇다 — ① 왜 오래 걸리는지를 고친다(쿼리 튜닝, 또는 202 + 비동기 처리로 설계 변경). ② 그래도 필요한 만큼만 정렬한다(6절의 상향식 계산). ③ 멱등성 키로 최종 방어선을 만든다. "늘리기 전에 이 시간이 정말 허용 가능한가를 먼저 묻는다"가 핵심 문장이다.

덧붙이면 좋은 한마디 — 타임아웃을 늘리는 것은 "실패를 성공으로 바꾸는" 조치가 아니라 "빠른 실패를 느린 실패로 바꾸는" 조치일 때가 많다. 백엔드가 진짜로 멈춘 경우, 짧은 타임아웃은 빨리 포기하고 자원을 회수하지만 긴 타임아웃은 멈춘 백엔드를 몇 분씩 붙들고 있게 한다.

keep-alive 타임아웃을 조정했는데 502가 그대로입니다. 무엇을 확인하나요? 함정힌트: 이 설정에는 이름이 같은 형제가 있다

고친 쪽이 어느 블록이었는지부터 확인한다. Nginx에는 keepalive_timeout이라는 이름의 지시자가 두 군데 있다.

http/server 블록

  • 클라이언트 방향 유휴 연결의 수명
  • 여기를 고쳐도 백엔드 방향은 그대로다

upstream 블록 안

  • 백엔드 방향 — 502의 원인이 되는 쪽
  • 여기를 안 고쳤다면 아무것도 안 바뀐 것

확인 방법은 nginx -T다. 실제 적용된 전체 설정을 덤프하면 어느 블록에 어떤 값이 들어갔는지가 눈에 보인다. include가 여러 겹인 구성에서는 어느 파일의 값이 최종적으로 이겼는지가 파일만 봐서는 안 보인다.

그다음 확인할 것 셋 — ① proxy_http_version 1.1과 proxy_set_header Connection ""이 있는지(없으면 keep-alive 자체가 동작하지 않는다). ② 건수 축도 맞는지(Tomcat maxKeepAliveRequests vs Nginx keepalive_requests). ③ Tomcat의 keepAliveTimeout을 명시했는지 — 미지정이면 connectionTimeout을 따라가므로 내가 아는 값이 아닐 수 있다.

$request_time과 $upstream_response_time이 크게 다릅니다. 무슨 뜻인가요? 시니어 변별힌트: 두 값의 "포함 범위"가 다르다. 차이 자체가 진단 정보다

두 값의 재는 범위가 다르고, 그 차이가 곧 "Nginx 바깥에서 흐른 시간"이다.

$upstream_response_time
Nginx ↔ 백엔드 구간만. 업스트림에 요청을 보내기 시작해 응답을 다 받을 때까지.
$request_time
클라이언트에서 요청의 첫 바이트를 읽기 시작해 마지막 응답 바이트를 클라이언트에게 보낼 때까지 — 즉 클라이언트 방향 구간이 함께 들어 있다.

$request_time만 크고 $upstream_response_time은 작다면 백엔드는 빨랐고 시간이 클라이언트 쪽에서 흘렀다는 뜻이다 — 느린 회선의 업로드(요청 본문을 다 받는 데 오래 걸림)나 느린 다운로드(응답을 다 보내는 데 오래 걸림)다. 이때 백엔드를 튜닝하는 것은 헛수고다.

반대로 두 값이 거의 같고 둘 다 크다면 백엔드 처리가 진짜로 느린 것이다. 여기에 $upstream_connect_time과 $upstream_header_time을 더해 보면 구간이 더 쪼개진다 — connect가 크면 연결 단계, header가 크면 백엔드의 실질 처리 시간, header는 작은데 response가 크면 본문 전송 구간이다.

버퍼링이 켜져 있으면 이 분리가 더 선명해진다. Nginx가 응답을 다 받아 챙긴 시점에 $upstream_response_time이 확정되고, 느린 클라이언트에게 흘려보내는 시간은 $request_time에만 쌓이기 때문이다. 즉 두 값의 차이가 곧 "버퍼링이 흡수해 준 시간"이다.

업로드 크기 판정은 Nginx와 앱 중 어디서 해야 하나요? 가산점힌트: 정답이 하나가 아니다. 무엇을 얻고 무엇을 잃는지로 답한다

트레이드오프이고, 중요한 것은 "어느 쪽이 판정자인지를 의식적으로 정해두는 것"이다. 모르고 두면 사용자가 받는 에러가 그때그때 다르다.

Nginx를 작게 두어 Nginx가 판정

  • 대역폭과 디스크를 아낀다 — 거대한 본문이 앱까지 오지 않는다
  • Content-Length만 보고 즉시 거절하므로 전송 자체가 시작되지 않는다
  • 대가: Nginx의 밋밋한 HTML 에러 페이지가 나가고 앱 로그에 흔적이 없다

Nginx를 크게 두어 앱이 판정

  • 에러 응답의 일관성 — 우리 포맷의 JSON, 사용자에게 보여줄 메시지
  • 앱 로그에 MaxUploadSizeExceededException이 남아 추적이 된다
  • 대가: 큰 본문이 앱까지 전송되고, maxSwallowSize 함정을 밟을 수 있다

실무의 절충안은 Nginx를 앱 한도보다 살짝 크게(예: 앱 25MB, Nginx 21m이 아니라 앱 20MB, Nginx 21m처럼 정책 값 + 오버헤드 여유) 두어 정상 범위의 판정은 앱이 하되 터무니없이 큰 본문은 Nginx가 막는 형태다. 이때 maxSwallowSize도 함께 점검해야 "에러 메시지 대신 연결이 끊기는" 증상을 피한다.

proxy_next_upstream 기본값을 그대로 두면 어떤 위험이 있나요? 시니어 변별힌트: 기본값에 무엇이 들어 있는지부터 말한다

기본값은 error timeout이다. 즉 연결 단계 실패뿐 아니라 "타임아웃"까지 재시도 조건에 들어 있다. 여기서 두 가지 위험이 나온다.

① 증상이 숨겨진다. keep-alive 경쟁으로 인한 끊김은 error로 분류되므로, 업스트림 그룹에 서버가 여러 대면 Nginx가 조용히 다른 서버로 넘겨 사용자 눈에는 502가 안 보인다. 문제가 없어진 게 아니라 재시도 비용을 계속 지불하며 가려져 있는 것이다. 같은 버그가 스테이징(1대)에서는 502로 보이고 운영(여러 대)에서는 안 보이거나 그 반대인 이유가 대개 이것이다.

② 비멱등 요청이 두 번 실행될 수 있다. 다행히 최근 Nginx는 요청을 이미 업스트림에 보낸 뒤라면 POST 같은 비멱등 메서드를 기본적으로 넘기지 않는다 — 이를 허용하는 non_idempotent 파라미터가 따로 있고, 그것을 켜는 순간 중복 처리가 가능해진다. 켜기 전에 그 엔드포인트가 멱등한지 반드시 확인해야 한다.

더 자주 놓치는 함정은 GET처럼 "멱등으로 선언된" 메서드가 실제로는 부작용을 만드는 코드인 경우다. 규약을 어긴 GET은 프록시 계층이 조용히 두 번 실행시킨다. 프록시의 재시도도 애플리케이션 재시도와 똑같이 멱등성 검토 대상이라는 것이 요점이고, 실무에서는 proxy_next_upstream error(연결 단계만) + proxy_next_upstream_tries · _timeout 상한을 명시적으로 적어두는 것이 안전하다.

알림(SSE)이 로컬에서는 즉시 오는데 배포하면 안 옵니다. 어디를 봅니까?힌트: 로컬에는 없고 배포 환경에만 있는 것이 무엇인지 먼저 떠올린다

로컬에는 없고 배포 환경에만 있는 것 — 앞단 프록시다. 브라우저가 Tomcat에 직접 붙는 로컬에서는 이벤트가 그대로 흐르지만, 배포 환경에서는 Nginx가 proxy_buffering on 상태로 이벤트를 버퍼에 모아두고 있다.

확인 순서 — ① 해당 location에 proxy_buffering off(또는 앱의 X-Accel-Buffering: no)가 있는지. ② proxy_http_version 1.1이 있는지(HTTP/1.0으로 말하면 청크 스트리밍이 성립하지 않는다). ③ 앞단이 Nginx만이 아닐 수 있다 — CDN이나 LB도 자체 버퍼링·아이들 타임아웃을 갖고 있으므로 층을 건너뛰고 직접 붙어 보는 것이 확실하다(7-3절의 이분 탐색과 같은 방법).

그다음이 "잠시 오다가 끊기는" 증상이다. 이것은 버퍼링이 아니라 침묵 구간 문제다 — 보낼 이벤트가 없는 동안 proxy_read_timeout을 넘겨 연결이 끊긴 것이다. 대응은 앱이 주기적으로 하트비트(: ping 같은 주석 줄)를 흘려보내 타이머를 초기화하는 것이고, 타임아웃 값을 몇 시간으로 키우는 것보다 이 편이 낫다.

마지막으로 앱 구현을 확인한다. proxy_buffering off는 Tomcat 스레드가 연결 내내 붙들린다는 뜻이므로, 동기 방식으로 SSE를 구현했다면 동시 접속자 수가 스레드 풀 크기에 묶인다. 인프라 설정과 앱 구현을 함께 말해야 답이 완성된다.

사용자는 결제 실패를 봤다는데 DB에는 주문이 있습니다. 지금 무엇부터 합니까?힌트: 원인 규명보다 먼저 해야 할 일이 있다

① 지금 벌어지고 있는 피해를 먼저 막는다. 유령 성공은 사용자 재시도로 중복 결제가 쌓이는 현상이므로, 원인 규명보다 중복 건 식별과 환불·취소 절차가 먼저다. 같은 사용자·같은 금액·짧은 시간 간격의 주문을 뽑아 대조한다.

② 증거를 확보한다. Nginx error log에서 upstream timed out ... while reading response header를 찾고, 액세스 로그에서 $upstream_response_time이 proxy_read_timeout 값에 붙어 있는 요청들을 뽑는다. 앱 로그에서는 같은 시각의 ClientAbortException과 "성공"으로 남은 주문 생성 로그를 대조한다. 이 세 가지가 맞물리면 유령 성공이 확정된다.

③ 즉시 조치와 근본 조치를 나눈다. 즉시는 타임아웃 정렬(그리고 필요하면 해당 엔드포인트만 한시적으로 상한 조정), 근본은 멱등성 키 도입과 처리 시간 자체를 줄이거나 비동기(202 + 결과 알림)로 바꾸는 설계 변경이다.

이 답의 채점 포인트는 순서다. "타임아웃을 늘리겠습니다"로 시작하면 이미 발생한 중복 결제를 방치하는 답이 되고, "멱등성 키를 도입하겠습니다"로 시작하면 지금 당장의 피해를 못 막는 답이 된다.

한 줄 요약
Nginx와 Tomcat은 서로의 설정값을 모르는 채 각자의 타임아웃·버퍼·크기 한도를 적용하므로, 어긋난 값 사이의 좁은 구간에서만 터지는 유령 현상(504 뒤의 유령 성공과 중복 처리, keep-alive 유휴 경쟁이 만드는 간헐적 502, 특정 크기 근처에서만 실패하는 업로드, 특정 사용자만 502가 나는 큰 응답 헤더)이 생긴다 — 정렬 규칙은 방향이 둘로 갈려서 응답을 기다리는 대기 상한은 바깥 계층이 안쪽보다 길게, 유휴 연결의 수명은 재사용하는 쪽이 닫는 쪽보다 짧게 잡아야 하고, proxy_read_timeout이 전체 응답 시간이 아니라 "아무 바이트도 안 오는 구간"의 상한이라는 것과 Tomcat에는 처리 시간 상한이라는 나사가 아예 없다는 것을 알아야 값을 제대로 정할 수 있으며, 무엇이 어긋났는지는 Nginx error log의 문구와 $upstream_response_time이 지문처럼 알려준다.
