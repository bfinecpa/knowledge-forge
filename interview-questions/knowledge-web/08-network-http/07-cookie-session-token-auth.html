쿠키 · 세션 · 토큰 인증
상태를 어디에 두고, 무엇으로 실어 나르는가

면접 질문: "쿠키와 세션, 토큰 기반 인증의 차이는?"

핵심 관전 포인트 — 셋은 같은 층위의 선택지가 아니다. HTTP는 무상태(stateless)라 "이 요청이 누구인지"를 매 요청 다시 증명해야 하는데, 쿠키는 그 증명을 브라우저가 자동으로 실어 나르는 운반 수단이고, 세션과 토큰은 인증 상태를 어디에 두느냐의 두 방식이다 — 세션은 상태를 서버에 두고 쿠키로는 열쇠(세션 ID)만 나르며, 토큰(JWT)은 상태 자체를 서명해 클라이언트에 들려 보내고 서버는 서명만 검증한다. 그래서 세션은 서버를 늘릴 때 상태 공유가 문제가 되고, 토큰은 서버가 기억하지 않으므로 확장은 쉽지만 즉시 무효화가 어렵다. 쿠키를 쓴다면 HttpOnly(XSS 탈취 차단)·Secure(평문 전송 차단)·SameSite(CSRF 차단) 세 속성이 사실상 필수이고, JWT를 쓴다면 서명은 위조를 막을 뿐 내용을 숨기지 않는다(payload는 누구나 디코딩 가능)는 것이 전제다. 선택은 확장성 · 탈취 대응 · 클라이언트 종류(웹/앱)가 얽힌 트레이드오프다.
  • 1
    축이 둘이라는 것부터 말한다 — 쿠키는 운반 수단(브라우저가 자동 첨부), 세션과 토큰은 상태를 어디에 두느냐의 답이다. 셋을 나란히 비교하면 층위가 꼬인다. 운반 수단 × 상태 위치의 2×2로 놓으면 네 조합이 모두 실재한다.
  • 2
    세션은 번호표, 토큰은 신분증이다 — 세션은 상태를 서버 저장소에 두고 무작위 식별자만 내려주므로 지우면 그 순간 로그아웃(즉시 무효화가 쉽다)이지만 요청마다 저장소 조회와 서버 증설 시 상태 공유가 숙제다. 토큰은 서명된 상태를 통째로 들려 보내 저장소 조회 없이 서명만 검증하므로 확장이 쉽지만 발급한 뒤 회수할 수단이 없다.
  • 3
    그래서 실무는 절충형이다 — 쿠키를 쓰면 HttpOnly·Secure·SameSite가 짝으로 붙고, JWT를 쓰면 payload는 누구나 읽는다는 전제 위에서 짧은 무상태 access + 상태 있는 refresh(회전 + 재사용 탐지)로 간다. 완전한 무상태는 "즉시 무효화 포기"와 교환한 것이라는 말까지 해야 답이 닫힌다.

0. 질문 + 출제 의도

질문: "쿠키와 세션, 토큰 기반 인증의 차이는?"

출제 의도: 인증 방식 선택은 확장성(서버 상태), 보안(탈취 대응), 클라이언트 종류(웹/앱)가 얽힌 실무 결정이다. IAM·인증 기능을 다루는 백엔드의 상시 업무이므로, 용어 암기가 아니라 "무엇을 포기하고 무엇을 얻었는가"를 말할 수 있는지를 본다.

이 페이지가 겨냥하는 약점 네 가지 ① 셋을 같은 층위로 나열하는 것 → 4절에서 운반 수단 × 상태 위치 2×2로 축을 갈라 놓는다. "세션=쿠키, 토큰=헤더"는 관행이지 규칙이 아니다.
② 쿠키 속성을 "그냥 붙이는 것"으로 아는 것 → 2·3절에서 XSS와 CSRF를 먼저 분리한 뒤 HttpOnly·Secure·SameSite가 각각 어느 경로를 끊는지로 정리한다.
③ "JWT는 암호화돼 있어 안전하다"는 오해 → 6절에서 Base64URL 디코딩 한 줄로 payload가 그대로 보이는 것을 보여주고, 서명이 보장하는 것과 보장하지 않는 것을 표로 못 박는다.
④ "JWT를 쓰면 서버가 가벼워집니다"에서 멈추는 것 → 8·9절에서 무효화 요구를 만나면 상태가 되돌아온다는 것을, refresh 회전 코드가 서버 저장소를 다시 쓰고 있다는 사실로 보여준다.

1. 출발점 — 무상태 HTTP와 운반 수단으로서의 쿠키

1-1. "무상태"가 정확히 무슨 뜻인가

무상태(stateless)는 "서버가 요청과 요청 사이에 아무것도 기억하지 않는다"가 아니라, HTTP 프로토콜 자체에는 요청을 이어 붙일 장치가 없다는 뜻이다. 서버는 방금 로그인한 사용자의 다음 요청을, 처음 보는 요청과 프로토콜 차원에서 구분할 방법이 없다.

"TCP 연결이 유지되면 같은 사람 아닌가?" — 아니다 HTTP/1.1의 keep-alive로 연결이 재사용되더라도, 서버 앞에는 대개 로드밸런서와 리버스 프록시가 있어 연결과 요청이 1:1로 대응하지 않고, 서버가 여러 대면 다음 요청은 다른 서버로 갈 수도 있다. 연결은 신원의 근거가 될 수 없다.

비유 — 매번 다른 창구 직원을 만나는 은행. 직원은 방금 옆 창구에서 무슨 일이 있었는지 모른다. 그래서 매 요청에 "나는 아까 그 사람"이라는 증표를 직접 들고 가야 하고, 이 증표를 나르는 대표 수단이 쿠키다.

1-2. 쿠키의 동작 — 헤더 두 개와, 브라우저가 대신 해주는 일

쿠키의 프로토콜 자체는 헤더 두 개가 전부다. 서버가 응답에 Set-Cookie로 증표를 심어 주면, 브라우저가 이후 요청에 Cookie 헤더로 되돌려 보낸다.

http 헤더 두 개가 쿠키의 전부다
# 서버 -> 브라우저: 응답에 증표를 심는다
HTTP/1.1 200 OK
Set-Cookie: SESSION=a1b2c3; Path=/; HttpOnly; Secure; SameSite=Lax

# 브라우저 -> 서버: 이후 같은 도메인의 요청에 자동 첨부
GET /orders HTTP/1.1
Host: app.example.com
Cookie: SESSION=a1b2c3

여기서 3년차가 가장 감을 못 잡는 지점은 "그래서 코드로 뭘 해야 하나"다. 답은 아무것도 안 해도 된다이다. 아래 다섯 단계를 브라우저가 개발자 대신 전부 처리한다.

2. 공격 두 가지 — XSS와 CSRF는 완전히 다르다

쿠키 속성 이야기를 하려면 각 속성이 무엇을 막는지를 알아야 하고, 그러려면 공격 두 개를 먼저 알아야 한다. 이름이 비슷해 헷갈리지만 완전히 다른 문제다.

XSS — 훔쳐 가는 공격

  • 공격자가 심은 자바스크립트가 우리 사이트의 페이지 안에서 실행된다. 게시글 본문에 <script>를 넣었는데 그대로 렌더링되는 경우가 전형.
  • 이 스크립트는 우리 출처의 코드로 취급되므로 document.cookie를 읽고 localStorage를 뒤질 수 있다.
  • 침해되는 것은 기밀성 — 증표가 공격자 서버로 넘어간다.

CSRF — 시키는 공격

  • 공격자 사이트(evil.com)가 방문자의 브라우저를 시켜 우리 사이트로 요청을 보내게 만든다.
  • 브라우저는 목적지가 우리 도메인이니 쿠키를 자동으로 붙인다. 공격자는 응답을 읽지 못하지만 부수효과(송금·비밀번호 변경·탈퇴)는 이미 일어난다.
  • 침해되는 것은 무결성 — 훔치는 게 아니라 시키는 것이다.

3. 쿠키 속성 — 각각이 어떤 공격을 막는가

Set-Cookie에 줄줄이 붙는 속성들은 장식이 아니다. 하나씩 무엇을 막으려고 존재하는지 보자.

세 속성 = 세 개의 다른 문을 잠그는 것 필수 암기

못 읽게 HttpOnly  ·  못 엿듣게 Secure  ·  못 시키게 SameSite
HttpOnly
막는 것: XSS 탈취
스크립트의 document.cookie에서 아예 보이지 않는다. 브라우저가 HTTP 전송 경로에만 쓰고 스크립트에는 넘기지 않는다.
Secure
막는 것: 평문 스니핑
HTTPS 요청에만 첨부한다. 없으면 http://로 한 번만 접속해도 세션 ID가 평문으로 네트워크에 흘러 나간다.
SameSite
막는 것: CSRF
다른 사이트에서 시작된 요청에 이 쿠키를 붙일지 결정한다. Strict / Lax / None 세 값.

3-1. SameSite 세 값 — 무엇을 허용하고 무엇을 대가로 치르나

SameSite는 "다른 사이트에서 시작된 요청에도 이 쿠키를 붙일 것인가"를 결정한다.
값언제 쿠키를 붙이는가대가
Strict같은 사이트에서 시작된 요청에만외부 링크로 우리 사이트에 들어오면 첫 요청에 쿠키가 안 붙어 비로그인 화면이 보인다
Lax같은 사이트 요청 + 최상위 화면 이동(링크 클릭 등)의 GET교차 사이트 POST · fetch · iframe · img에는 안 붙는다
None교차 사이트라도 항상 붙인다CSRF 방어가 사라지므로 Secure 필수 + 별도 CSRF 대책 필요
왜 Lax가 기본값으로 자리 잡았나 — 공격 유형과 정상 사용을 실용적으로 가른 선 CSRF의 주력은 상태를 바꾸는 POST·PUT·DELETE인데 Lax는 그것들을 전부 차단한다. 반면 "메신저로 받은 링크를 눌러 우리 사이트에 들어오는" 최상위 GET 이동은 정상 사용이므로 허용한다. 검색 결과에서 들어와도 로그인이 유지되는 것은 이 예외 덕분이다.

SameSite=None을 쓰려면 Secure가 반드시 필요하다

None은 "어떤 사이트에서 시작된 요청에도 이 쿠키를 실어 보내라"는 선언이다. 즉 이 쿠키는 우리가 통제하지 못하는 온갖 페이지에서, 우리가 모르는 타이밍에 네트워크로 나간다 — 노출 기회가 구조적으로 가장 많은 쿠키다. 그런 쿠키가 평문 HTTP로도 나갈 수 있다면 스니핑 위험이 폭증하므로, 브라우저는 아예 규칙으로 못을 박았다.

SameSite=None인데 Secure가 없으면 그 쿠키는 저장 자체가 거부된다

실무에서 부딪히는 자리는 프론트가 https://app.example.com, API가 https://api.example.com처럼 브라우저가 교차 사이트로 판정하는 구조다. 쿠키 세션을 유지하려면 SameSite=None; Secure가 필요하고, 서버 쪽에는 CORS의 자격증명 허용 설정이 짝으로 따라온다(08-cors-and-preflight.md). 그리고 이때 CSRF 방어를 스스로 껐다는 사실도 함께 인식해 CSRF 토큰이나 커스텀 헤더 검증을 반드시 얹는다.

http 교차 출처 구조에서 쿠키 세션을 유지하려면 이 조합이 강제된다
Set-Cookie: SESSION=a1b2c3; Path=/; HttpOnly; Secure; SameSite=None
// Secure를 빼면 브라우저가 쿠키를 저장조차 하지 않는다 — "로그인이 안 되는데 에러도 없는" 증상

3-2. 범위와 수명 — Domain · Path · Max-Age

Domain
쿠키가 어느 호스트까지 따라갈지
지정하지 않으면 내려준 그 호스트에만 붙는다. Domain=example.com이면 api.·blog.·admin. 모든 서브도메인 요청에 붙는다. 편해 보이지만 곧 공격면이다 — 마케팅팀의 event.example.com 하나에 XSS가 터지면 그 스크립트가 우리 세션 쿠키를 다룰 수 있는 위치에 선다.
Path
경로 범위를 좁힌다
Path=/admin이면 /admin 이하 요청에만 붙는다. 다만 보안 경계가 아니다 — 같은 출처 안의 스크립트라면 숨겨진 iframe을 만드는 등으로 다른 경로의 쿠키에 접근할 여지가 있다. 전송량을 줄이는 정리 수단으로 보고 격리를 기대하지 않는다.
Max-Age / Expires
수명을 정한다
둘 다 없으면 세션 쿠키 — 브라우저를 닫으면 사라진다(세션 복원 기능 때문에 실제로는 살아남기도 한다). 값을 주면 영속 쿠키가 되어 디스크에 저장되고 재부팅 후에도 남는다. "로그인 상태 유지" 체크박스가 이 둘을 가르는 스위치다.
쿠키의 범위는 신뢰 경계와 같아야 한다 — 서브도메인 전체를 같은 수준으로 신뢰할 수 없다면 Domain을 넓히지 않는다

3-3. before / after — 속성 없이 심은 쿠키와, 무엇을 막는지 알고 붙인 쿠키

before 세 가지 방어가 전부 빠져 있다
@PostMapping("/login")
public void login(HttpServletResponse response, LoginRequest req) {
    String sessionId = sessionService.create(authenticate(req));

    Cookie cookie = new Cookie("SESSION", sessionId);
    cookie.setPath("/");
    response.addCookie(cookie);

    // XSS 한 방이면 document.cookie로 통째로 유출된다   (HttpOnly 없음)
    // http로 접속하면 평문으로 흘러 나간다              (Secure 없음)
    // evil.com의 폼 POST에도 자동 첨부된다              (SameSite 없음)
}
after 각 줄이 어떤 공격을 막는지 안다
@PostMapping("/login")
public void login(HttpServletResponse response, LoginRequest req) {
    String sessionId = sessionService.create(authenticate(req));

    ResponseCookie cookie = ResponseCookie.from("SESSION", sessionId)
            .httpOnly(true)   // 스크립트가 못 읽음  -> XSS 통째 탈취 차단
            .secure(true)     // HTTPS에서만 전송     -> 평문 스니핑 차단
            .sameSite("Lax")  // 교차 사이트 POST 제외 -> CSRF 차단
            .path("/")
            .maxAge(Duration.ofHours(2))  // 없으면 브라우저 종료 시 소멸
            .build();

    // ResponseCookie를 쓰는 이유: 서블릿 Cookie 클래스에는
    // SameSite를 직접 설정하는 API가 없어 헤더를 문자열로 조립해야 한다.
    response.addHeader(HttpHeaders.SET_COOKIE, cookie.toString());
}

여기까지가 쿠키의 역할이다. 쿠키는 증표를 나르는 봉투일 뿐이고, "봉투 안에 무엇이 들었는가"부터가 세션과 토큰의 갈림길이다.

4. 두 축 — 운반 수단 × 상태 위치 2×2

이 질문에 셋을 나란히 비교해 답하면 층위가 꼬인다. 쿠키는 운반 수단이고, 세션과 토큰은 상태를 어디에 두느냐의 답이다. 축이 둘이라는 것을 먼저 말하고 시작하는 것이 정리된 답변이다.

첫 문장을 이렇게 연다 필수

"쿠키는 운반 수단이고, 세션과 토큰은 상태를 어디에 두느냐의 두 방식입니다. 축이 둘이라 셋을 나란히 비교하기는 어렵습니다."

5. 세션 — 물품보관함 번호표

로그인이 성공하면 서버가 사용자 정보를 자기 저장소(톰캣 메모리, Redis 등)에 넣고, 그 항목을 가리키는 무작위 식별자(세션 ID)만 쿠키로 내려준다.

비유 — 물품보관함 번호표. 번호표(세션 ID)에는 아무 정보도 없다. 누가 번호표를 주워도 물건은 보관함(서버)에 있고, 관리인이 번호표를 무효 처리하면 그 순간부터 아무 소용이 없다.

강점 — 전부 "서버가 상태의 주인"에서 파생된다

  • 로그아웃 — 저장소에서 지우면 끝
  • 관리자에 의한 강제 로그아웃
  • 비밀번호 변경 후 전 기기 로그아웃
  • 권한 변경 즉시 반영 — 저장소 값을 고치면 끝
  • 사용자별 활성 세션 목록을 들고 있으면 "다른 기기 모두 로그아웃"도 자연스럽다

대가 — 둘

  • 모든 요청이 저장소 조회를 거친다. 초당 1만 요청이면 초당 1만 번의 조회다.
  • 서버가 여러 대로 늘어나면 "2번 서버에 저장된 세션을 3번 서버가 어떻게 아나"라는 상태 공유 문제가 생긴다 → 8절의 실무 사례.

세션 고정 공격(session fixation) — 직접 세션을 다룰 때 반드시 챙기는 한 줄

공격자가 자기가 아는 세션 ID를 피해자 브라우저에 미리 심어 놓고, 피해자가 그 ID로 로그인하기를 기다리는 공격이다. 로그인 전후로 같은 세션 ID를 계속 쓰면 성립한다.

방어는 한 줄 — 인증에 성공한 시점에 세션 ID를 새로 발급하면 공격자가 아는 ID는 무효가 된다

Spring Security는 이 처리를 기본으로 수행하므로, 직접 세션을 다루는 코드를 짤 때만 신경 쓰면 된다.

6. 토큰(JWT) — 서명된 신분증

로그인이 성공하면 서버가 사용자 정보(사용자 ID, 권한, 만료시각)를 담은 데이터에 서버만 아는 키로 서명해 통째로 내려준다. 이후 요청마다 클라이언트가 이 토큰을 붙이면, 서버는 저장소 조회 없이 서명 검증만으로 "내가 발급했고 위조되지 않은 증표"임을 확인한다.

비유 — 신분증. 번호표와 달리 신분증에는 내용(이름, 생년월일)이 적혀 있고, 위조 방지 장치(홀로그램 = 서명)가 함께 붙어 있다. 발급 기관에 전화해 확인할 필요 없이 그 자리에서 검증된다. 그리고 바로 그 때문에 이미 발급한 신분증을 원격으로 회수할 방법이 없다.

6-1. JWT의 구조 — 점 두 개로 나뉜 세 조각

JWT(JSON Web Token)는 점(.) 두 개로 나뉜 문자열이다. 각 조각은 Base64URL로 인코딩돼 있다. Base64URL은 임의의 바이트를 URL·헤더에 안전한 문자만으로 표현하는 인코딩으로, +와 / 대신 -와 _를 쓰는 Base64 변형이다.

6-2. 반드시 짚어야 할 오해 — 서명은 위조를 막을 뿐, 내용을 숨기지 않는다

JWT는 암호화가 아니다

payload는 Base64URL로 "인코딩"돼 있을 뿐이고, 인코딩은 비밀이 필요 없는 표현 변환이다.

넣어도 되는 것은 "노출돼도 그 자체로는 해가 없는 식별자"뿐이다

그래서 payload에 넣으면 안 되는 것이 분명하다 — 주민등록번호, 전화번호, 이메일, 내부 시스템의 상세 권한 구조.

bash 서버의 비밀키 없이, 셸 한 줄이면 내용이 그대로 보인다
# JWT는 Base64URL 패딩('=')을 떼고 쓰므로, 길이가 4의 배수가 아니면 '='을 붙여 준다.
# (아래 payload는 마침 80자라 그대로 디코딩된다.)
$ echo 'eyJzdWIiOiI0MiIsInJvbGUiOiJVU0VSIiwiaWF0IjoxNzM1Njg5NjAwLCJleHAiOjE3MzU2OTMyMDB9' | base64 -d
{"sub":"42","role":"USER","iat":1735689600,"exp":1735693200}
서명이 보장하는 것과 보장하지 않는 것. 이 네 줄이 JWT 질문의 채점표다.
항목보장하는가왜
내용 기밀성 (남이 못 읽음)보장하지 않음Base64URL은 암호가 아니라 인코딩이다
무결성 (내용 변조 탐지)보장함비밀키 없이는 서명을 다시 만들 수 없다
진위 (내가 발급한 것인가)보장함서명을 검증할 수 있는 것은 발급자뿐이다
유출 후 무효화보장하지 않음서버가 발급 사실을 기억하지 않기 때문이다

세 글자로 인출하기 필수 암기

JWT는 읽힌다 · 못 바꾼다 · 못 지운다

읽힌다(기밀성 없음) → payload 설계 원칙으로 이어지고, 못 바꾼다(무결성·진위) → 서명의 존재 이유이며, 못 지운다(무효화 불가) → 9절의 refresh 회전으로 이어진다. 세 갈래가 모두 다음 절의 입구다.

6-3. 검증에서 자주 무너지는 지점 — alg를 토큰이 시키는 대로 따르기

서명 검증 코드에서 실수하면 서명이 있어도 의미가 없어진다. 대표적인 것이 알고리즘을 토큰이 시키는 대로 따르는 것이다. header의 alg는 공격자가 조작할 수 있는 값인데, 라이브러리에 그대로 넘기면 alg를 none(서명 없음)으로 바꾼 토큰이나, 공개키 방식(RS256)을 대칭키 방식(HS256)으로 뒤바꿔 공개키를 비밀키처럼 쓰게 만드는 토큰에 속을 수 있다.

before 토큰이 주장하는 알고리즘을 그대로 믿는다
Claims claims = Jwts.parser()
        .setSigningKey(secretKey)   // alg는 토큰 header에 적힌 대로 따라간다
        .parseClaimsJws(token)
        .getBody();

// 공격자가 header를 {"alg":"none"} 으로 바꾸면
//   → 서명 없는 토큰이 통과할 수 있다
// RS256을 HS256으로 바꾸면
//   → 공개된 공개키가 HMAC 비밀키로 쓰여 위조가 가능해진다
after 서버가 알고리즘을 못 박고, 만료·발급자까지 검증
Claims claims = Jwts.parser()
        .verifyWith(secretKey)
        .sig().add(Jwts.SIG.HS256).and()  // HS256만 허용 — alg 조작 원천 차단
        .requireIssuer("https://auth.example.com") // 다른 시스템 토큰 유입 차단
        .build()
        .parseSignedClaims(token)   // 서명 불일치·만료면 여기서 예외
        .getPayload();

// exp 검증을 빼먹지 않는 것도 중요하다. 만료시각은 payload에
// 적혀 있을 뿐이므로, 서버가 확인하지 않으면 만료된 토큰이 영원히 통과한다.
한 문장으로 기억하기 토큰이 스스로 "나를 이렇게 검증하라"고 말하게 두지 않는다. 알고리즘·발급자·수신자(aud)는 서버가 기대값을 못 박고 대조하는 것이지, 토큰에서 읽어 오는 것이 아니다.

7. 운반 수단의 차이가 공격면을 가른다

같은 증표라도 쿠키로 나르느냐 Authorization 헤더로 나르느냐에 따라 노출되는 공격이 달라진다.

2절의 XSS·CSRF 구분이 여기서 그대로 표로 떨어진다.
축쿠키로 운반Authorization 헤더로 운반
첨부 방식브라우저가 자동클라이언트 코드가 수동
CSRF취약(자동 첨부가 원인) — SameSite·CSRF 토큰 필요강함(브라우저가 헤더를 자동으로 붙여주지 않는다)
XSS로 탈취HttpOnly면 스크립트가 못 읽음JS가 접근 가능한 곳에 두면 그대로 유출
교차 도메인 · 모바일 앱도메인 규칙에 묶여 설정이 늘어남자유로움
http 토큰 방식의 전형적 요청 — 코드가 직접 헤더를 붙인다
GET /orders HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI0MiJ9.dBjftJeZ...
Bearer는 "소지자"라는 뜻이다 가진 사람이 곧 권한자라는 이 방식의 성격을 이름이 그대로 드러낸다 — 그래서 유출 자체가 곧 침해이고, 전송 구간 보호(HTTPS)와 짧은 수명이 필수 조건이 된다.
헤더 방식이 CSRF에 강한 이유를 정확히 말하기 시니어 변별 "공격자 사이트가 헤더를 넣을 수 없어서"가 아니라, 정확히는 브라우저가 자동으로 붙여주지 않기 때문이다. <form> 제출이나 <img> 로드에는 커스텀 헤더를 넣을 방법이 없고, 스크립트로 fetch를 호출해 헤더를 붙이더라도 응답을 읽으려면 CORS 허가가 필요하다. 즉 CSRF 내성은 토큰이라는 형식에서 오는 게 아니라 "자동 첨부가 없다"는 운반 수단의 성질에서 온다.

8. 실무 사례 — 서버를 늘렸더니 로그인이 풀린다

세션을 톰캣 로컬 메모리에 두는 기본 구성은 서버가 1대일 때만 성립한다. 트래픽이 늘어 scale-out으로 2대가 되고 로드밸런서가 요청을 번갈아 보내는 순간, 문제가 시작된다.

before 로컬 메모리 세션 — 인스턴스마다 각자 기억하므로 확장 시 깨진다
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("userId", authenticate(req)); // 이 서버의 힙에만 존재
}

선택지는 셋이다. 어느 것도 공짜가 아니고, 각각 무엇을 포기하는지가 이 질문의 트레이드오프다.

8-1. 선택지 ① 스티키 세션 — 같은 사용자를 같은 서버로 고정

스티키 세션(sticky session)은 로드밸런서가 "이 사용자는 서버 A"라고 기록해 두고 이후 요청을 계속 A로 보내는 방식이다. 세션 어피니티(session affinity, 친화성)라고도 부른다. 구현은 LB가 자기 쿠키를 하나 더 심거나, 클라이언트 IP를 해시해 서버를 고르는 식이다.

nginx IP 해시로 고정하는 예 — 애플리케이션 코드 변경이 전혀 없다
upstream backend {
    ip_hash;                 # 같은 클라이언트 IP는 항상 같은 업스트림으로
    server app-a:8080;
    server app-b:8080;
}

얻는 것

  • 애플리케이션을 한 줄도 고치지 않고 당장 증상이 사라진다. 급한 불을 끌 때의 가치가 크다.

포기하는 것 — 셋

  • 부하가 고르게 안 퍼진다. 무거운 사용자가 몰린 서버는 계속 무겁다.
  • 그 서버가 죽으면 거기 붙어 있던 사용자 세션이 통째로 사라진다. 배포 때마다 일부가 로그아웃되는 것도 그대로 남는다.
  • 스케일 아웃의 효과가 반감된다. 새 서버를 붙여도 기존 사용자는 옮겨오지 않아 새 서버는 놀고 기존 서버는 붐빈다.
스티키 세션은 "서버는 여전히 상태를 갖고 있다"는 사실을 감춘 것이지 해결한 것이 아니다

8-2. 선택지 ② 세션 저장소 외부화 — 상태를 서버 밖으로 옮긴다

세션을 애플리케이션 프로세스 밖의 공용 저장소(주로 Redis)에 두는 방식이다. 서버는 요청마다 그 저장소에서 세션을 읽어 오므로 어느 서버가 받아도 같은 세션을 본다. Spring에서는 Spring Session이 이 교체를 대신해 준다. 핵심은 애플리케이션 코드가 그대로라는 것 — HttpSession 인터페이스는 유지한 채 구현체만 Redis 기반으로 바뀐다.

설정 의존성 + 설정만으로 구현이 교체된다
// build.gradle
implementation 'org.springframework.boot:spring-boot-starter-data-redis'
implementation 'org.springframework.session:spring-session-data-redis'

# application.yml
spring:
  session:
    store-type: redis
    timeout: 30m          # 세션 만료 — Redis 키의 TTL로 관리된다
  data:
    redis:
      host: session-redis.internal
      port: 6379
after 코드는 before와 한 글자도 다르지 않다
@PostMapping("/login")
public void login(HttpSession session, LoginRequest req) {
    session.setAttribute("userId", authenticate(req)); // Redis에 저장, 전 서버 공유
}

// 바뀐 것은 "저장 위치"뿐이다.
// 서버는 무상태에 가까워져 자유롭게 늘리고 줄일 수 있고,
// 배포해도 로그인이 유지된다.
// 그러면서 즉시 무효화라는 세션의 강점은 그대로 남는다
//   — Redis에서 키를 지우면 그 순간 로그아웃.
포기하는 것 — Redis가 "전 요청의 의존점"이 된다 Redis가 죽으면 모든 사용자가 동시에 로그아웃되고, Redis 지연이 곧 전체 API 지연이 된다. 그래서 이 선택은 "Redis를 붙인다"로 끝나지 않고 가용성 설계(Sentinel이나 Cluster 구성, 장애 시 동작 정의)까지 포함한 결정이다.

실무에서 자주 밟는 함정 두 개

① 세션에 넣는 객체는 직렬화돼 Redis로 나가므로 Serializable이어야 한다(JSON 직렬화로 바꾸면 이 제약은 풀리지만 타입 정보 설정이 필요하다).
② 세션에 큰 객체를 담으면 매 요청마다 그만큼을 직렬화·역직렬화하며 왕복시키게 된다.

세션에는 식별자 수준의 작은 값만 담는다

8-3. 선택지 ③ 토큰 — 상태 자체를 없앤다

after 토큰 발급 — 서버는 어떤 상태도 보관하지 않는다
@PostMapping("/login")
public TokenResponse login(LoginRequest req) {
    Long userId = authenticate(req);
    // 서명된 토큰을 클라이언트가 보관하고, 서버는 검증만 한다.
    // 서버 어디에도 "이 토큰을 발급했다"는 기록이 남지 않는다.
    return new TokenResponse(jwtProvider.issue(userId));
}

얻는 것: 세션 저장소라는 의존점이 사라진다. 서버 간 호출이 잦은 MSA에서 매 홉마다 세션 조회를 하지 않아도 되고, 모바일 앱이나 외부 파트너 API처럼 쿠키를 쓰기 어려운 클라이언트도 같은 방식으로 인증된다.

포기하는 것: 즉시 무효화다. 그리고 이것은 "포기하고 끝"이 아니라 다음 절의 숙제로 이어진다.

9. 토큰을 택하면 따라오는 숙제 — 짧은 수명과 refresh 회전

토큰의 즉시 무효화 문제를 정면으로 푸는 방법은 없다. 대신 실무는 피해가 지속되는 시간을 줄이는 쪽으로 설계한다. 그 장치가 access token과 refresh token의 분리다.

왜 둘로 나누는가 — 한 장짜리 토큰은 두 요구가 한 값에 묶여 있다 필수

수명을 길게 하면 탈취당했을 때 오래 악용되고, 짧게 하면 사용자가 하루에도 몇 번씩 다시 로그인해야 한다. 둘로 나누면 이 결합이 풀린다.

access token
매 요청에 실려 다닌다 = 노출 빈도 높음
그래서 수명을 짧게(분 단위) 둔다. 탈취되더라도 곧 만료된다. 무상태 유지.
refresh token
재발급할 때만 전송된다 = 노출 적음
수명을 길게(일 단위) 두는 대신 서버 저장소에 기록해 통제 지점으로 삼는다.
한 문장으로 — "자주 노출되는 것은 짧게, 통제 지점은 서버에"

9-1. refresh token 회전(rotation)과 재사용 탐지

회전은 재발급 요청이 올 때마다 새 refresh token을 함께 내려주고 쓰던 것은 즉시 폐기하는 방식이다. 회전이 없으면 refresh token 하나가 만료일까지 계속 유효해 탈취 시 피해가 길어지지만, 회전을 걸면 한 토큰은 딱 한 번만 쓸 수 있는 일회용이 된다.

before refresh token이 만료 전까지 계속 재사용된다
@PostMapping("/reissue")
public TokenResponse reissue(@RequestBody String refreshToken) {
    Long userId = jwtProvider.parseRefresh(refreshToken).userId();
    return new TokenResponse(jwtProvider.issueAccess(userId));

    // 서버는 이 refresh token이 몇 번 쓰였는지 모른다.
    // 탈취되면 만료일까지 무한히 access token을 찍어낼 수 있다.
}
after 회전 + 재사용 탐지
@Transactional
@PostMapping("/reissue")
public TokenResponse reissue(@RequestBody String refreshToken) {
    RefreshRecord record = refreshRepository.findByToken(refreshToken)
            .orElseThrow(() -> new UnauthorizedException("unknown refresh token"));

    // 이미 사용돼 폐기된 토큰이 다시 왔다 = 복사본이 돌아다닌다는 신호.
    // 개별 요청만 거절하면 공격자가 계속 시도하므로, 계열 전체를 끊는다.
    if (record.isUsed()) {
        refreshRepository.revokeAllByUserId(record.userId());
        alertService.notifyTokenReuse(record.userId());
        throw new UnauthorizedException("refresh token reuse detected");
    }

    record.markUsed();  // 한 번 쓴 refresh token은 즉시 소진시킨다
    String newRefresh = jwtProvider.issueRefresh(record.userId());
    refreshRepository.save(RefreshRecord.of(record.userId(), newRefresh));

    return new TokenResponse(jwtProvider.issueAccess(record.userId()), newRefresh);
}

이 코드에서 놓치면 안 되는 사실 시니어 변별

이 코드는 refreshRepository라는 서버 저장소를 쓰고 있다

즉 토큰을 택해 없앤 줄 알았던 서버 상태가, 무효화 요구를 만나 다시 돌아왔다. "JWT를 쓰면 서버가 무상태가 됩니다"라고 말한 뒤 이 코드를 짜고 있다면, 이미 절충형을 쓰고 있는 것이다. 이 되돌아옴을 스스로 짚는 것이 설계 경험이 드러나는 지점이다.

10. 선택 기준 — 클 · 확 · 무

"그래서 무엇을 언제 선택하나요?"는 가산점이 걸린 마무리 질문이다. 기준 세 가지로 답한다.

① 클라이언트 종류
브라우저 단일 도메인 서비스면 쿠키 + 세션(또는 쿠키에 담은 토큰)이 자연스럽다 — 브라우저가 자동으로 해주는 일이 많아 구현이 단순하고 HttpOnly의 이점을 그대로 받는다. 모바일 앱 · 외부 API · 여러 도메인이 얽히면 토큰이 자연스럽다.
② 확장과 아키텍처
서버 간 호출이 많은 MSA는 홉마다 세션 저장소를 조회하는 비용이 커서 자가 검증되는 토큰이 유리하다. 반대로 단일 애플리케이션에 Redis가 이미 있다면 세션 외부화가 훨씬 적은 변경으로 끝난다.
③ 무효화 요구의 강도
강제 차단과 권한 즉시 반영이 중요한 도메인(관리자 콘솔, 금융, 결제)일수록 세션이나 상태 있는 절충형으로 기운다. "5분 지연된 차단"이 허용되지 않는 요구가 있다면 그것만으로 방식이 결정된다.

세 기준을 세 글자로 가산점

클라이언트 종류 · 확장 구조 · 무효화 요구

마무리는 "정답이 아니라 요구사항의 함수"라는 태도다. 실제 답변에서는 여기에 현재 시스템의 제약(이미 있는 인프라, 팀의 운영 역량, 클라이언트 구성)을 얹어 하나를 고르고, 고르면서 무엇을 포기했는지까지 말하는 것이 이 질문의 모범 답안 골격이다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

첫 문장을 어떻게 여는가?
축이 둘이다 — 쿠키는 운반 수단, 세션·토큰은 상태를 어디에 두느냐. 2×2로 놓으면 네 칸이 전부 실재한다.
쿠키 세 속성과 각각 막는 것?
못 읽게 HttpOnly(XSS 탈취) · 못 엿듣게 Secure(평문 스니핑) · 못 시키게 SameSite(CSRF). 셋 중 하나만 빠져도 그 갈래는 열려 있다.
XSS와 CSRF 한 줄 구분?
XSS는 훔쳐 가는 공격(우리 페이지 안에서 실행 · 기밀성), CSRF는 시키는 공격(남의 페이지가 우리 서버로 요청 · 무결성). 응답을 못 읽어도 이체는 끝난다.
SameSite 세 값과 강제 규칙?
Strict / Lax(+ 최상위 이동 GET) / None. None은 Secure가 없으면 저장 자체가 거부되고, CSRF 방어를 스스로 끈 것이므로 별도 대책 필수.
JWT 세 조각과 세 글자?
header . payload . signature. 성질은 읽힌다 · 못 바꾼다 · 못 지운다 — 기밀성 없음 / 무결성·진위 있음 / 무효화 불가.
세션 vs 토큰 비유와 대가?
번호표(상태는 서버 · 즉시 무효화 쉬움 / 요청마다 저장소 왕복 + 상태 공유) vs 신분증(자가 검증 · 확장 쉬움 / 회수 불가).
스케일아웃 세 선택지?
스티키(감춘 것) · Redis 외부화(새 의존점) · 토큰(회수 불가). 가르는 줄은 "서버 무상태"와 "새 의존점".
refresh 회전의 진짜 값?
재사용 탐지 — 폐기된 토큰이 다시 들어오면 복사본이 있다는 증거이므로 계열 전체 무효화. 탈취를 막진 못해도 탐지는 된다.
웹에서 토큰 저장 위치 기본값?
HttpOnly + Secure + SameSite 쿠키. 이유는 "확실히 막을 수 있는 쪽(CSRF)을 떠안는" 선택이기 때문.
선택 기준 셋?
클 · 확 · 무 — 클라이언트 종류 / 확장 구조 / 무효화 요구. 마무리는 "정답이 아니라 요구사항의 함수".

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

JWT를 쓰면 세션 저장소가 정말 필요 없어지나요? 시니어 변별힌트: "이론상은 그렇다"로 시작해서, 상태가 어디로 되돌아오는지를 말한다

이론상은 그렇다. 하지만 실무 요구가 상태를 다시 불러온다.

돌아보면 요구는 전부 같은 모양이다. 로그아웃한 토큰 즉시 차단, 비밀번호 변경·계정 탈취 시 강제 만료, 관리자의 강제 로그아웃, 권한 변경 즉시 반영 — 전부 "이미 발급된 토큰을 회수"해야 하는데, 무상태 토큰에는 회수 대상이 없다.

대응은 셋이고, 각각 무엇을 치르는지가 답변의 핵심이다.

①
access token을 짧게 하고 refresh로 재발급한다. 무효화가 아니라 피해 시간창을 줄이는 완화다. "로그아웃 후 최대 5분간은 탈취된 access token이 유효하다"를 받아들이는 것. 무상태는 완전히 유지된다.
②
refresh token을 서버 저장소에 두고 그것을 무효화 지점으로 삼는다(9절). 강제 로그아웃은 refresh 레코드를 지우는 것으로 구현되고, 그 뒤로는 재발급이 막히므로 access token 수명이 다하면 끝난다. 대신 재발급 경로에는 상태가 생긴다. 실무에서 가장 흔한 절충이다.
③
차단 목록(blacklist)을 두고 매 요청 조회한다. 즉시 차단이 가능해지지만 매 요청 저장소 조회가 되살아나므로 토큰을 택한 이유(무상태)가 상당 부분 사라진다. 다만 차단 목록은 활성 세션 전체가 아니라 "차단된 것만" 담고 만료 항목은 TTL로 사라지므로 세션 저장소보다 훨씬 작고 가볍다는 반론도 함께 말하면 좋다.
완전한 무상태는 "즉시 무효화 포기"와 교환한 것이고, 실제 시스템은 대부분 짧은 무상태 access + 상태 있는 refresh를 쓴다

"JWT를 쓰면 서버가 가벼워집니다"에서 멈추지 않고 어디에 상태가 되돌아오는지, 그것이 왜 받아들일 만한지까지 말하면 설계 경험이 드러난다.

access token과 refresh token은 왜 나누나요? 필수힌트: "보안 때문에"가 아니라 "한 값에 묶여 있던 두 요구를 푼다"로 답한다

한 장짜리 토큰은 탈취 피해 시간과 재로그인 빈도가 한 값에 묶여 있어, 어느 쪽을 개선해도 다른 쪽이 나빠진다. 둘로 나누면 이 결합이 끊어진다.

매 요청에 실려 노출이 잦은 access token은 수명을 짧게 해 탈취 피해를 시간으로 제한하고, 재발급 때만 오가는 refresh token은 노출이 적으니 길게 두되 서버 저장소에 기록해 통제 지점으로 쓴다.

한 문장으로 — "자주 노출되는 것은 짧게, 통제 지점은 서버에"

여기에 회전과 재사용 탐지를 얹으면 답이 완성된다(9절). refresh token을 일회용으로 만들고, 폐기된 토큰이 다시 들어오면 탈취 신호로 보아 해당 사용자의 토큰 계열 전체를 무효화한다. "탈취를 막을 수는 없어도 탈취를 탐지할 수는 있다"는 관점을 보여주는 대목이다.

토큰은 클라이언트 어디에 저장해야 하나요? 필수힌트: "localStorage는 위험합니다"로 끝내면 절반. 무엇과 무엇을 맞바꾸는지 말한다

웹이라면 localStorage vs 쿠키의 트레이드오프이고, 본질은 XSS와 CSRF 중 어느 쪽 위험을 떠안을 것인가다.

localStorage

  • JS가 명시적으로 읽어 헤더에 붙이므로 자동 첨부가 없다 → CSRF와는 무관
  • 대신 스크립트가 접근할 수 있는 곳이라 XSS 한 방에 토큰이 통째로 유출되고, 유출된 토큰은 만료까지 어디서든 쓰인다

HttpOnly 쿠키

  • 스크립트가 읽을 수 없어 XSS로 훔쳐 가는 것은 막는다
  • 대신 브라우저가 자동 첨부하므로 CSRF 대비(SameSite, CSRF 토큰)가 필요하고, HttpOnly도 만능은 아니다 — XSS가 터지면 그 페이지 안에서 요청을 보내는 것까지는 못 막는다

그래서 정답은 하나가 아니고 조건부다. 웹은 HttpOnly + Secure + SameSite 쿠키 조합이 무난한 기본값이다 — XSS는 완전 방어가 어려운 반면 CSRF는 SameSite와 CSRF 토큰으로 비교적 확실하게 막을 수 있어서, "확실히 막을 수 있는 쪽을 떠안는" 선택이기 때문이다.

모바일 앱은 애초에 쿠키·CSRF 구도가 아니므로 OS의 보안 저장소(안드로이드 Keystore, iOS Keychain)를 쓴다. 어느 쪽이든 저장 위치보다 XSS를 애초에 막는 것(출력 이스케이프, CSP)이 상위 방어선이라는 점을 덧붙이면 좋다.

세션 ID나 토큰이 통째로 탈취되면 각각 어떻게 대응하나요? 필수힌트: "대응 방법"보다 "대응 가능성 자체가 다르다"를 먼저 말한다

구조가 다르므로 대응 가능성 자체가 다르다는 것부터 말한다.

세션은 서버가 상태의 주인이라 저장소에서 해당 세션을 지우면 그 순간 차단된다. 사용자별 활성 세션 목록을 관리해 두면 "다른 기기 모두 로그아웃"이나 "의심 세션만 선택 종료"도 구현된다. 탈취 대응력은 세션이 본질적으로 유리하다.

토큰은 개별 회수가 안 되므로 만료까지 유효한 것이 기본이고, 차단하려면 결국 차단 목록이나 refresh 폐기 같은 서버 상태가 필요하다. 그래서 토큰 쪽 대응은 "차단"이 아니라 "짧은 수명으로 피해 창을 줄이는 완화"가 기본이고, 여기에 refresh 회전의 재사용 탐지를 얹어 탈취를 사후에라도 알아채는 장치를 만든다.

탈취 경로 자체를 줄이는 것이 사후 대응보다 앞선다

전송·저장 단계의 방어를 함께 언급하면 가산점이다 — Secure로 평문 전송을 막고, HttpOnly로 스크립트 접근을 막고, 로그인 시 세션 ID를 재발급해 세션 고정을 막고, 서버 로그·APM에 토큰이나 세션 ID가 그대로 찍히지 않게 마스킹한다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

SameSite=Lax만 걸면 CSRF는 다 막히나요? 함정힌트: Lax가 "허용하는 예외"가 무엇이었는지 되짚는다

아니다. Lax는 "최상위 화면 이동의 GET"을 허용한다는 예외를 갖고 있고, 그 예외가 그대로 구멍이 될 수 있다.

① GET으로 상태를 바꾸는 엔드포인트가 있으면 뚫린다. GET /admin/users/42/delete 같은 API가 남아 있으면, 공격자가 그 URL로 링크를 클릭하게 만드는 것만으로 쿠키가 붙어 나간다. 그래서 상태 변경은 반드시 POST·PUT·DELETE로라는 원칙(04-http-method-idempotency-and-safety.md)이 여기서 보안 요구로 다시 등장한다.

② "같은 사이트" 판정은 출처(origin)보다 넓다. 스킴과 등록 가능한 상위 도메인 기준이라 서브도메인끼리는 same-site로 취급된다. 즉 서브도메인 하나를 장악당하면 SameSite는 그 요청을 막아주지 않는다. 3절에서 Domain을 함부로 넓히지 말라고 한 것과 같은 이야기다.

결론: SameSite는 비용 대비 효과가 가장 큰 1차 방어선이지 유일한 방어선이 아니다. 상태 변경은 안전하지 않은 메서드로, 여기에 CSRF 토큰이나 Origin/커스텀 헤더 검증을 얹는 것이 정석이다. SameSite=None을 써야 하는 구조라면 이 추가 장치가 선택이 아니라 필수가 된다.

payload가 그대로 읽히는데, 그럼 JWT는 왜 쓰나요?힌트: "숨기는 것"과 "증명하는 것"은 다른 목적이다

JWT의 목적은 내용을 숨기는 것이 아니라 "이 내용이 서버가 발급한 그대로임"을 증명하는 것이기 때문이다. 신분증에 이름과 생년월일이 적혀 있는 것이 결함이 아닌 것과 같다 — 신분증의 가치는 홀로그램(서명)에 있지 내용을 가리는 데 있지 않다.

그래서 얻는 것이 자가 검증(self-contained)이다. 서버는 저장소를 조회하지 않고 "이 요청의 주체는 42번 사용자이고 권한은 USER이며 만료는 언제"를 토큰만 보고 알 수 있다. 확장성의 근거가 전부 여기서 나온다.

정말로 내용을 숨겨야 한다면 방법은 둘이다 — ① 민감 정보를 payload에 아예 넣지 않고 식별자만 넣는다(대부분 이 선택으로 충분하다), ② 암호화까지 필요하면 JWE(암호화된 JWT)를 쓴다. "JWS(서명)와 JWE(암호화)가 다른 것"이라는 구분을 아는 것 자체가 변별점이다.

JWT payload에 role을 담았습니다. 권한을 강등하면 즉시 반영되나요? 함정힌트: "못 지운다"가 여기서도 그대로 적용된다

반영되지 않는다. 이미 발급된 토큰에는 옛 권한이 적힌 채 서명까지 붙어 있고, 서버는 그 토큰을 "내가 발급한 정품"으로 정상 검증한다. 즉 관리자 권한을 회수해도 그 토큰의 만료시각까지는 관리자로 행동할 수 있다.

대응은 무효화 문제와 같은 모양이다. ① access token 수명을 짧게(분 단위) 잡아 반영 지연을 그 시간 안으로 묶는다. ② 권한 변경 시 refresh 레코드를 폐기해 재발급 시점부터 새 권한이 실리게 한다. ③ 즉시성이 정말 필요하면 민감한 작업만 서버에서 권한을 다시 조회한다 — 이때 토큰의 role은 빠른 1차 필터이고 최종 판단은 서버 상태가 한다.

설계 원칙 한 줄: 자주 바뀌는 정보일수록 토큰에 넣기 나쁘다. 토큰에 담기 좋은 것은 토큰 수명 동안 바뀌지 않는 값(사용자 식별자, 발급자, 만료)이다.

HttpOnly 쿠키를 쓰면 XSS는 신경 안 써도 되나요? 함정힌트: 훔쳐 가는 것과 그 자리에서 쓰는 것을 나눈다

아니다. HttpOnly는 완전 방어가 아니라 피해 축소다.

쿠키를 못 읽더라도 공격 스크립트는 그 페이지 안에서 fetch('/api/transfer', ...)를 호출할 수 있고, 그때도 쿠키는 브라우저가 자동으로 붙여 준다. 즉 훔쳐 가서 다른 곳에서 쓰는 것은 막지만 그 자리에서 사용하는 것은 못 막는다.

게다가 XSS가 터진 페이지에서는 화면을 통째로 바꿔 가짜 로그인 폼을 띄우거나, 사용자의 입력을 가로채는 것도 가능하다. 쿠키 탈취는 XSS로 할 수 있는 일 중 하나일 뿐이다.

쿠키 속성은 피해를 줄이는 2차 방어선이고, 1차는 XSS를 애초에 안 만드는 것(출력 이스케이프 · 입력 검증 · CSP)이다
세션을 Redis로 옮겼습니다. 그 Redis가 죽으면 어떻게 되나요? 시니어 변별힌트: "전 요청의 의존점"이라는 말의 무게를 계산해 본다

모든 사용자가 동시에 로그아웃된다. 세션 조회가 실패하면 서버는 "세션 없음"으로 판단하고 로그인 페이지로 보내므로, 단일 컴포넌트 장애가 전 사용자 장애로 즉시 번진다. 게다가 Redis 지연이 곧 전체 API 지연이 된다 — 모든 요청이 그 앞을 지나가기 때문이다.

그래서 이 선택은 "Redis를 붙인다"로 끝나지 않는다. 함께 결정해야 할 것이 가용성 구성(Sentinel이나 Cluster로 페일오버 확보), 타임아웃과 실패 시 동작(짧은 타임아웃 + 재시도 제한 — 여기서 지연이 길면 커넥션 풀이 마르면서 장애가 전파된다), 영속성 정책(재시작 시 세션을 살릴 것인가), 세션 데이터 크기(직렬화 왕복 비용)다.

한 칸 더 간다면 — 로그인 경험이 최우선이고 즉시 무효화 요구가 약한 서비스라면, 짧은 수명의 무상태 토큰으로 읽기 경로를 태우고 무효화가 필요한 지점만 저장소를 태우는 절충으로 "전 요청 의존"을 "일부 요청 의존"으로 낮추는 설계도 가능하다. 어느 쪽이든 "무엇이 전 요청 경로에 들어가는가"를 의식하는 것이 요점이다.

프론트는 app.example.com, API는 api.example.com입니다. 쿠키 세션을 유지하려면? 함정힌트: 쿠키 속성만으로 끝나지 않는다. 서버 쪽 짝이 하나 더 있다

브라우저가 교차 사이트로 판정하는 구조이므로 쿠키가 자동으로 붙지 않는다. 필요한 것은 세 가지가 한 세트다.

1
쿠키에 SameSite=None; Secure — None인데 Secure가 없으면 브라우저가 쿠키를 저장조차 하지 않는다. "로그인이 안 되는데 에러도 없는" 증상이 여기서 나온다.
2
클라이언트가 자격증명을 실어 보내도록 명시 — fetch(..., { credentials: 'include' }). 기본값으로는 교차 출처 요청에 쿠키가 실리지 않는다.
3
서버의 CORS 설정 — 자격증명 허용을 켜야 하고, 이때 허용 출처에 와일드카드를 쓸 수 없다(정확한 출처를 명시해야 한다). 상세는 08-cors-and-preflight.md.

그리고 반드시 덧붙일 한 문장 — SameSite=None을 켜는 순간 CSRF 방어를 스스로 껐다. CSRF 토큰이나 커스텀 헤더 검증을 반드시 함께 얹는다. 대안으로 같은 사이트로 묶는 구성(리버스 프록시로 app.example.com/api에 API를 붙이는 방식)을 제시하면 "설정으로 뚫지 말고 구조로 피한다"는 감각이 드러난다.

로그아웃을 세션과 토큰에서 각각 어떻게 구현하나요?힌트: 한쪽은 "지운다", 다른 쪽은 "버린다"이다 — 이 동사 차이가 전부다

세션은 서버가 지운다. 저장소에서 해당 세션을 삭제하고(session.invalidate()), 클라이언트 쪽 쿠키도 같은 이름·경로·도메인으로 Max-Age=0을 내려 정리한다. 지운 순간부터 그 세션 ID는 아무 의미가 없다.

토큰은 기본적으로 클라이언트가 버린다. 그런데 이것은 "내 손에서 놓았다"일 뿐 무효화가 아니다 — 탈취된 복사본은 만료까지 그대로 유효하다. 그래서 실무의 로그아웃은 보통 세 겹으로 구성된다.

  • 클라이언트 저장소에서 access·refresh token 제거
  • 서버의 refresh 레코드 폐기 — 재발급 경로를 끊는다(이것이 실질적 로그아웃)
  • 즉시성이 필요하면 남은 수명 동안만 차단 목록에 올린다(TTL = 토큰의 잔여 수명 → 목록이 무한히 커지지 않는다)

면접에서 값이 나가는 한 문장: "토큰 방식에서 로그아웃은 '차단'이 아니라 '재발급 차단 + 잔여 수명 감수'입니다. 그 잔여 수명이 곧 access token의 수명을 짧게 잡는 이유입니다."

쿠키 대신 헤더로 세션 ID를 보내면 CSRF가 사라지나요? 가산점힌트: 4절의 2×2를 떠올린다 — 무엇을 바꾼 것인지 정확히 짚는다

그렇다. 그리고 그 사실 자체가 이 질문의 핵심을 증명한다. CSRF 내성은 "세션이냐 토큰이냐"(상태 위치)에서 오는 것이 아니라 "자동 첨부가 있느냐"(운반 수단)에서 온다. 세션 ID를 Authorization 헤더로 나르면 브라우저가 알아서 붙여주지 않으므로 교차 사이트 요청에 실리지 않는다.

대신 다른 것을 잃는다. ① 헤더로 나르려면 클라이언트가 값을 어딘가에 보관해야 하고, JS가 접근 가능한 곳에 두면 XSS 노출이 생긴다(HttpOnly의 보호를 포기하는 것). ② 브라우저가 해주던 저장·만료·매칭을 직접 구현해야 한다. ③ 일반 링크 이동(<a> 클릭)에는 헤더를 붙일 수 없어 서버 사이드 렌더링 페이지와 잘 맞지 않는다.

그래서 이 조합은 드물지만 실재한다(4절 2×2의 우상단 칸). "운반 수단과 상태 위치는 독립 축"이라는 답변을 구체적인 반례로 뒷받침할 수 있다는 점에서 말할 값이 있다.

세션 고정 공격(session fixation)은 무엇이고 어떻게 막나요?힌트: 훔치는 게 아니라 "미리 심어두는" 공격이다

공격자가 자기가 아는 세션 ID를 피해자 브라우저에 미리 심어 놓고, 피해자가 그 ID로 로그인하기를 기다리는 공격이다. 로그인이 성공하면 그 세션 ID가 인증된 세션으로 승격되는데, 공격자는 이미 그 값을 알고 있으므로 그대로 피해자 계정에 올라탄다.

성립 조건은 하나다 — 로그인 전후로 같은 세션 ID를 계속 쓰는 것. 그러므로 방어도 하나다.

인증에 성공한 시점에 세션 ID를 새로 발급한다 — 공격자가 아는 ID는 그 순간 무효가 된다

Spring Security는 이 처리를 기본으로 수행하므로 대개는 신경 쓸 일이 없고, 직접 세션을 다루는 코드를 짤 때만 챙기면 된다. 참고로 토큰 방식에는 이 공격이 성립하지 않는다 — 인증 성공 후 서버가 새로 만들어 내려주는 값이라 공격자가 미리 심을 대상이 없기 때문이다. "방식이 다르면 공격면도 다르다"는 예시로 쓰기 좋다.

한 줄 요약
쿠키는 무상태 HTTP 위에서 증표를 브라우저가 자동으로 실어 나르는 운반 수단이고(HttpOnly는 XSS 탈취를, Secure는 평문 전송을, SameSite는 CSRF를 막는 짝이며 None은 Secure가 강제된다), 세션은 상태를 서버에 두고 열쇠만 보내는 방식(즉시 무효화가 쉽고 확장 시 상태 공유가 숙제), 토큰은 서명된 상태를 클라이언트에 들려 보내는 방식(확장이 쉽고 서명은 위조만 막을 뿐 payload는 누구나 읽으며 즉시 무효화가 어렵다)이다 — 운반 수단과 저장 위치라는 두 축으로 나눠 놓고, 클라이언트 종류·확장 구조·무효화 요구에 따라 스티키 세션 · Redis 세션 · 짧은 access + 상태 있는 refresh 중 하나로 절충하는 것이 실무의 선택이다.
