CORS와 Preflight
"CORS 에러 나요"에 원리로 답하기

면접 질문: "CORS란 무엇이고 preflight 요청은 왜 필요한가요?"

핵심 관전 포인트 — CORS(Cross-Origin Resource Sharing, 교차 출처 자원 공유)는 브라우저의 동일 출처 정책(Same-Origin Policy, SOP)이 막아 놓은 교차 출처 접근을, 서버가 응답 헤더로 "이 출처는 허용한다"고 명시적으로 동의해 줄 때만 풀어주는 브라우저 시스템이다. 가장 먼저 바로잡아야 할 오해는 CORS가 요청을 막는 것이 아니라 응답을 읽는 것을 막는다는 점이다 — 그래서 "서버 로그에는 200인데 프론트에는 에러"가 나고, 그래서 CORS는 서버의 보안 장치가 아니다(curl과 서버 간 호출에는 아무 효력이 없다). preflight는 본 요청이 서버에 도달하기 전에 브라우저가 OPTIONS로 "이런 메서드·헤더의 요청을 보내도 되나요?"라고 미리 허락을 구하는 절차이며, CORS 이전 시대에 만들어진 서버들이 예상하지 못한 형태의 교차 출처 요청(PUT/DELETE, application/json, 커스텀 헤더)에 무방비로 노출되지 않도록 존재한다. 쿠키를 실어 보내려면 클라이언트의 credentials: 'include'와 서버의 Access-Control-Allow-Credentials: true가 짝이어야 하고 이때 Access-Control-Allow-Origin: *는 금지된다. 집행자는 언제나 브라우저이므로, CORS는 인증·인가의 대체재가 아니라 "필요한 출처에만, 필요한 만큼만" 여는 설정의 문제다.
  • 1
    순서를 뒤집지 않는다 — 막는 것은 SOP, 여는 것이 CORS다. 브라우저는 원래 교차 출처 응답을 스크립트가 읽지 못하게 막아 놓았고(SOP), CORS는 그 차단을 서버의 동의가 있을 때만 풀어주는 예외 절차다. "CORS 때문에 막혔다"는 정확히는 "SOP 때문에 막혔고 CORS 설정이 없어서 안 열렸다"는 뜻이다.
  • 2
    막는 대상은 요청이 아니라 응답 읽기다. 요청은 서버에 도달했고, 처리됐고, 200이 돌아왔다. 브라우저가 그 응답을 손에 쥐고도 Access-Control-Allow-Origin이 없으면 스크립트에 넘기지 않고 폐기할 뿐이다. 그래서 "서버 로그 200 + 프론트 CORS 에러"가 정상적으로 발생하고, 부수효과가 있는 요청이었다면 그 효과는 이미 일어났다.
  • 3
    preflight는 "옛날 서버 보호 장치"이고, 집행자는 언제나 브라우저다. PUT/DELETE·application/json·커스텀 헤더는 CORS 이전 서버가 교차 출처로 올 리 없다고 전제하던 형태라, 브라우저가 OPTIONS로 먼저 허락을 구해 부수효과가 있는 본 요청이 도달조차 하지 않게 한다. 그리고 집행자가 브라우저이므로 curl·서버 간 호출·모바일 앱에는 아무 효력이 없다 — CORS는 인증·인가의 대체재가 아니다.

0. 질문 + 출제 의도

질문: "CORS란 무엇이고 preflight 요청은 왜 필요한가요?"

출제 의도: 프론트엔드와 협업하는 백엔드가 가장 자주 받는 질문("CORS 에러 나요")에 원리로 답할 수 있는지 본다. 원리를 모르면 스택오버플로 복붙 설정(* 허용)으로 보안 구멍을 만든다 — 에러를 없애는 사람이 아니라, 왜 막혔는지 이해하고 필요한 만큼만 여는 사람인지를 가리는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① "CORS가 요청을 막는다"는 오해 → 6절에서 서버 로그에 200이 찍히는 시퀀스를 그려, 차단선이 서버 앞이 아니라 브라우저 안에 있다는 것을 위치로 보여준다.
② preflight를 "그냥 브라우저가 하는 이상한 짓"으로 아는 것 → 7·8절에서 단순 요청의 기준이 "옛날 HTML 폼"이라는 근거를 세우고, 거기서 벗어난 요청에만 preflight가 붙는 이유를 역산한다.
③ "CORS 설정했으니 안전하다"는 착각 → 6·9절에서 curl 한 줄과 * + credentials 금지 규칙으로, CORS가 지키는 범위가 "브라우저 안에서 남의 사이트 스크립트가 응답을 읽는 것" 하나뿐임을 못 박는다.

1. 순서를 뒤집지 않는다 — 막는 것은 SOP, 여는 것이 CORS

CORS를 이해하려면 순서가 중요하다. 원래 브라우저는 교차 출처 요청의 응답을 스크립트가 읽지 못하게 막아 놓았다. 이 기본 차단을 동일 출처 정책(Same-Origin Policy, SOP)이라고 부른다. CORS는 이 차단을 "서버의 동의가 있을 때만" 풀어주는 예외 절차다.

이 한 줄을 먼저 고정한다

CORS는 뭔가를 막는 기술이 아니라 열어주는 기술이다

그래서 "CORS 때문에 막혔다"는 말은 정확히는 "SOP 때문에 막혔고, CORS 설정이 없어서 안 열렸다"는 뜻이다. 이 순서를 잡고 있으면 뒤의 모든 규칙이 "그래서 무엇을 열어줄지 서버가 어떻게 말하는가" 하나로 정리된다.

SOP — 기본 차단(교차 출처 응답 읽기 금지)→ 서버가 응답 헤더로 동의 표시→ CORS — 동의한 범위만큼 차단 해제

2. 출처(origin)란 정확히 무엇인가

출처(origin)는 스킴 + 호스트 + 포트의 조합이다. 셋 중 하나라도 다르면 다른 출처다. 도메인만 보고 판단하면 틀린다.

같은 출처인가 판정 — 기준 URL은 https://app.example.com
비교 대상같은 출처인가이유
https://app.example.com/orders/42같음경로는 출처의 구성 요소가 아니다
https://api.example.com다름호스트가 다르다 — 같은 상위 도메인이어도 소용없다
http://app.example.com다름스킴이 다르다 (http ↔ https)
http://localhost:8080 (기준이 http://localhost:3000일 때)다름포트가 다르다 — 로컬 개발에서 CORS를 만나는 자리

3. 왜 이런 정책이 있는가 — 브라우저에는 "자동으로 실리는 권한"이 있다

SOP가 없다면 무슨 일이 생기는지가 이 정책의 존재 이유다.

브라우저에는 사용자의 쿠키(로그인 세션)가 들어 있고, 이 쿠키는 목적지 도메인에 맞춰 자동으로 첨부된다. 즉 브라우저는 사용자 몰래도 인증된 요청을 만들어낼 수 있는 권한을 상시 들고 다니는 도구다. 이런 성질을 앰비언트 권한(ambient authority, 주변에 늘 깔려 있는 권한)이라고 부른다.

이 문서에서 가장 많이 재활용되는 한 문장

요청은 나갈 수 있어도, 응답은 못 읽는다

6절의 "서버 로그 200", 8절의 "preflight가 필요한 이유", 그리고 4절의 "CSRF는 따로 막아야 한다"가 전부 이 한 문장에서 파생된다.

비유 — 아파트 경비실 다른 동(다른 출처)에서 온 사람이 우편함에 편지를 넣고 가는 것(요청)은 막지 않는다. 그러나 답장을 대신 받아 가는 것(응답 읽기)은 수신 세대(서버)가 "그 사람에게 전달해도 됩니다"라고 명시한 경우에만 허용한다. 그리고 규칙을 집행하는 주체는 각 세대가 아니라 경비실(브라우저)이다 — 이 마지막 문장이 6절과 14절까지 계속 따라붙는 핵심이다.

4. SOP가 모든 것을 막지는 않는다 — 이 예외가 CSRF를 낳는다

한 가지를 더 짚어야 다음 절이 자연스럽다. SOP는 스크립트의 응답 읽기를 막는 정책이지, 교차 출처 로드 전부를 막는 정책이 아니다. 웹은 원래 교차 출처로 자원을 가져다 쓰도록 설계됐고, 다음은 지금도 자유롭게 나간다.

허용 SOP가 막지 않는 교차 출처 로드
<img src="https://other.com/a.png">                      다른 출처 이미지 로드 — 허용 (내용 읽기는 불가)
<script src="https://cdn.com/lib.js">                    다른 출처 스크립트 실행 — 허용
<link rel="stylesheet" href="https://cdn.com/a.css">     다른 출처 CSS — 허용
<form action="https://bank.com/transfer" method="post">  교차 출처 폼 제출 — 허용 ← 여기가 문제다

마지막 줄이 문제다. 폼 제출은 브라우저가 응답을 읽어 스크립트에 주는 것이 아니라 화면을 이동시키는 동작이므로 SOP의 대상이 아니다. 그런데 요청은 쿠키와 함께 실제로 서버에 도달하고 이체는 실행된다. 이것이 CSRF(Cross-Site Request Forgery)가 성립하는 자리다.

여기서 반드시 구분해야 할 것 — CORS와 CSRF는 서로 다른 문제를 푼다

CORS가 막는 것

  • 공격자가 노리는 것: 응답의 내용
  • 막는 방식: 응답을 스크립트에 넘기지 않음
  • 부수효과: 이미 일어났을 수 있다

CSRF가 막아야 하는 것

  • 공격자가 노리는 것: 부수효과(이체·삭제)
  • 응답은 애초에 읽을 생각이 없다
  • 방어 수단: SameSite 쿠키 속성 + CSRF 토큰

CORS를 아무리 엄격하게 잠가도 폼 제출 기반 CSRF는 그대로 성립한다 — 공격자는 애초에 응답을 읽으려는 게 아니기 때문이다. 이 구분이 14절 꼬리질문에서 시니어 변별 포인트로 되돌아온다.

5. CORS 동작 — 서버의 동의를 헤더로 주고받는다

프론트(https://app.example.com)가 API(https://api.example.com)를 호출하는 상황이다.

요청 브라우저가 출처를 자동으로 붙인다
GET /me HTTP/1.1
Host: api.example.com
Origin: https://app.example.com

// Origin은 브라우저가 붙이며,
// 스크립트가 값을 바꿀 수 없다.
응답 서버가 동의를 표시하면 읽을 수 있다
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Content-Type: application/json

{"userId":42,"name":"..."}
Origin은 왜 위조할 수 없는가 — 이 통제가 있어야 서버가 이 값을 근거로 쓸 수 있다 fetch의 헤더 옵션으로 Origin을 지정해도 무시된다. 브라우저가 통제하는 금지된 헤더 목록(forbidden header names)에 들어 있기 때문이다. 서버는 이 값을 보고 허용 대상이면 응답에 Access-Control-Allow-Origin을 실어 준다. 브라우저는 응답을 받은 뒤 이 헤더를 확인하고, 요청의 Origin과 맞으면 응답을 스크립트에 넘겨주고 아니면 넘겨주지 않는다.
단, 이 통제는 브라우저 안에서만 성립한다 — curl이나 서버 간 호출은 Origin을 마음대로 위조할 수 있다(6절).

6. 가장 중요한 오해 — CORS는 요청을 막지 않는다, 응답 읽기를 막는다

서버가 Access-Control-Allow-Origin을 내려주지 않으면 어떻게 되는가. 여기가 3년차가 가장 자주 잘못 알고 있는 지점이다. 답은 이렇다 — 요청은 서버에 도달했고, 정상 처리됐고, 200이 돌아왔다. 그런데 브라우저가 응답을 스크립트에 주지 않고 콘솔에 CORS 에러를 띄운다.

이 구조에서 두 가지 결론이 나온다.

결론 ① "CORS 에러 = 요청이 안 갔다"가 아니다
7절에서 볼 단순 요청은 이미 서버에서 실행됐을 수 있다. 그래서 CORS 에러가 났다고 "요청이 서버에 도달 안 했겠지"라고 판단하면 원인 분석이 어긋난다.
결론 ② CORS는 서버의 보안 장치가 아니다
집행자가 브라우저이므로, 브라우저가 아닌 클라이언트에게는 아무 효력이 없다. 이것을 아는지가 시니어 변별점이다.
증명 CORS를 아무리 엄격하게 잠가도 이 호출에는 아무 영향이 없다
# curl은 SOP를 집행하지 않는다 — 응답이 그대로 출력된다.
$ curl -H 'Origin: https://evil.com' https://api.example.com/me
{"userId":42,"name":"..."}

# 서버 간 호출, 모바일 앱, 스크립트 도구, 공격자의 프록시 — 전부 마찬가지다.
# CORS는 "브라우저에서 실행되는 남의 사이트 스크립트가 우리 응답을 읽어가는 것"만 막는다.
에러 메시지를 읽는 감각 — 상태 코드조차 전달되지 않는다 CORS로 차단된 응답은 상태 코드조차 스크립트에 전달되지 않는다. fetch는 TypeError: Failed to fetch로 실패하고 response.status를 볼 수 없다. 그래서 프론트 개발자는 "500인지 403인지도 모르겠다"고 말하게 되고, 이때 원인은 개발자도구 네트워크 탭이나 서버 로그에서 확인해야 한다. (12절에서 볼 always 누락처럼 오류 응답에만 CORS 헤더가 빠지는 구성이 이 혼란의 단골 원인이다.)

7. 단순 요청 — preflight 없이 바로 나가는 요청

브라우저는 교차 출처 요청을 두 부류로 나눈다. 그냥 보내는 것과 미리 물어보고 보내는 것이다. 전자를 단순 요청(simple request)이라고 부른다. 기준은 세 가지가 동시에 성립할 때다.

단순 요청의 세 조건 — 메 · 헤 · 타 (메서드 · 헤더 · 콘텐트타입)

① 메서드
GET, HEAD, POST 중 하나.
PUT·DELETE·PATCH는 해당 없음
② 헤더
직접 붙인 헤더가 안전 목록(CORS-safelisted) 안에만 있을 것 — Accept, Accept-Language, Content-Language, Content-Type(③ 조건 하)
③ Content-Type
application/x-www-form-urlencoded
multipart/form-data
text/plain — 이 셋 중 하나
셋이 동시에 성립해야 단순 요청이다 — 하나라도 어긋나면 preflight
기준을 외우기보다 "왜 그 조건인지"로 답한다 필수 "옛날 HTML 폼으로도 보낼 수 있던 요청"이 기준이기 때문이다. <form> 태그는 CORS가 생기기 훨씬 전부터 교차 출처 제출이 가능했고, 메서드는 GET/POST뿐, enctype은 위 세 가지뿐이었다. 즉 이런 요청은 CORS가 없던 시절부터 서버가 이미 받아오던 형태라 새로운 위협이 아니다. 그래서 preflight 없이 그대로 통과시킨다. — 이 한 문장을 말할 수 있으면 8절의 preflight 존재 이유가 역산으로 따라 나온다.

7-1. 여기서 3년차가 가장 자주 부딪히는 지점

우리가 만드는 JSON API는 거의 전부 Content-Type: application/json이다. 그런데 application/json은 위 세 목록에 없다. 따라서 JSON을 POST하는 순간 그것은 단순 요청이 아니고, preflight가 붙는다.

판정 예시 같은 API인데 왜 어떤 건 preflight가 붙는가
// ① 단순 요청 — preflight 없이 바로 나간다
fetch('https://api.example.com/search?q=hello');

// ② 단순 요청이 아니다 — Content-Type이 application/json이라서 preflight가 붙는다
fetch('https://api.example.com/orders', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },   관문 ③ 탈락
  body: JSON.stringify({ productId: 7 })
});

// ③ 이것도 preflight 대상 — GET이지만 Authorization은 안전 목록 밖 헤더다
fetch('https://api.example.com/me', {
  headers: { 'Authorization': 'Bearer ...' }         관문 ② 탈락
});
"우리 API는 GET인데 왜 preflight가 뜨죠?"의 답은 대개 여기 있다 메서드가 아니라 헤더 때문인 경우가 많다. Authorization, X-Requested-With, X-Trace-Id 같은 헤더를 하나라도 직접 붙이면 관문 ②에서 탈락한다.
부수적인 함정 하나 더 — XMLHttpRequest의 업로드 진행률 이벤트를 등록하면 단순 요청 조건에서 빠진다. 파일 업로드에 진행 바를 붙였더니 갑자기 preflight가 생기는 경우가 여기 해당한다.

8. Preflight — 본 요청 전에 허락을 구한다

8-1. 왜 필요한가 — 7절의 논리를 뒤집으면 답이 나온다

CORS로 인해 브라우저가 새롭게 보낼 수 있게 된 요청들이 있다 — PUT/DELETE/PATCH, Content-Type: application/json, Authorization 같은 커스텀 헤더. 이런 요청은 옛날 폼으로는 만들 수 없었다.

문제는 세상의 서버들이 대부분 CORS라는 개념이 생기기 전에 만들어졌고, "이런 요청이 브라우저에서 교차 출처로 올 리 없다"는 전제로 설계돼 있다는 것이다.

preflight가 없다면 벌어지는 일

브라우저가 DELETE /orders/42를 그냥 보내버린다면, CORS를 모르는 낡은 서버는 그것을 받아 실제로 삭제한 다음 응답을 돌려줄 것이다. 브라우저가 그 응답을 스크립트에 안 넘겨준들, 이미 삭제는 끝났다.

preflight의 존재 이유 = 허락이 없으면 부수효과가 있는 본 요청이 서버에 도달조차 하지 않게 하는 것

OPTIONS가 쓰이는 것도 이유가 있다. 원래 HTTP에서 OPTIONS는 "이 자원에 어떤 동작이 가능한지 묻는" 메서드이고 부수효과가 없다. 물어보는 행위 자체가 서버 상태를 바꾸면 안 되므로 자연스러운 선택이다.

8-2. 왕복의 실제 모습

8-3. 응답 헤더 정리 — 각각 무슨 질문에 답하는가

헤더를 "답하는 질문"으로 외우면 어느 응답에 붙여야 하는지가 저절로 따라온다.
헤더답하는 질문붙는 곳놓치기 쉬운 점
Access-Control-Allow-Origin어느 출처에게 응답을 읽게 할 것인가preflight 응답 + 본 응답값은 하나만 올 수 있다 — 콤마 나열 불가
Access-Control-Allow-Methods어떤 메서드를 허용하는가preflight 응답본 응답에는 의미가 없다
Access-Control-Allow-Headers어떤 요청 헤더를 달아도 되는가preflight 응답빠뜨린 헤더 하나로 본 요청이 안 나간다
Access-Control-Max-Age이 허가를 몇 초 동안 재사용해도 되는가preflight 응답브라우저마다 상한이 있다 (13절)
Access-Control-Allow-Credentials쿠키를 실은 요청도 허용하는가preflight 응답 + 본 응답Allow-Origin: *와 조합 금지 (9절)
Access-Control-Expose-Headers스크립트가 읽어도 되는 응답 헤더는 무엇인가본 응답지정하지 않으면 헤더가 없는 것처럼 보인다
덜 알려졌지만 실무에서 부딪히는 것 — Access-Control-Expose-Headers 교차 출처 응답에서 스크립트가 읽을 수 있는 응답 헤더는 기본적으로 극히 일부(Content-Type 등)로 제한된다. 그래서 페이징 총건수를 X-Total-Count로 내려주거나 생성된 자원 위치를 Location으로 주면, 프론트에서는 그 헤더가 없는 것처럼 보인다. 서버가 명시적으로 노출해 줘야 읽힌다. 
Access-Control-Expose-Headers: X-Total-Count, Location

9. 자격증명(쿠키)을 실어 보낼 때 — 규칙이 한 단계 엄격해진다

교차 출처 요청에는 기본적으로 쿠키가 실리지 않는다. 쿠키의 자동 첨부는 동일 출처가 전제이고, 교차 출처에서는 스크립트가 명시적으로 요구해야 한다. 그리고 이것을 켜려면 양쪽이 짝을 이뤄야 한다 — 한쪽만 해서는 동작하지 않는다.

클라이언트 쿠키를 실어 보내겠다고 선언
// fetch
fetch('https://api.example.com/me', { credentials: 'include' });

// axios
axios.get('https://api.example.com/me', { withCredentials: true });
서버 자격증명이 실린 요청도 허용한다고 응답
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true

// Allow-Origin에 * 를 쓰면 이 조합은 거부된다

절대 규칙 — 자격증명이 실린 요청에 *는 금지다

Access-Control-Allow-Origin: * + Allow-Credentials: true → 브라우저가 응답을 거부

이유는 *의 의미를 따져 보면 자명하다. *는 "누가 읽어가도 상관없는 공개 자원"이라는 선언인데, 여기에 "사용자의 로그인 쿠키를 실은 요청도 받겠다"를 더하면 "아무 사이트나 방문자의 로그인 세션으로 우리 API를 호출하고 그 응답을 읽어가도 된다"가 된다. 이것은 3절에서 SOP가 막으려던 바로 그 시나리오다. SOP가 지켜주던 것을 우리 손으로 여는 셈이므로 스펙이 조합 자체를 금지한다.

같은 이유로 자격증명 모드에서는 Access-Control-Allow-Headers: *와 Access-Control-Allow-Methods: *의 와일드카드도 와일드카드로 해석되지 않고 문자 그대로의 이름으로 취급된다. 자격증명을 켜는 순간 모든 허용 항목을 명시해야 한다고 기억하면 된다.

9-1. 크로스 도메인 쿠키 세션은 셋이 한 세트다

쿠키 자체에도 조건이 붙는다. 교차 사이트로 나가는 쿠키이므로 SameSite=None; Secure가 필요하다. 즉 "프론트와 API가 다른 도메인인데 쿠키 세션을 쓴다"는 결정은 다음 셋을 한 세트로 요구한다.

자격증명 3종 세트 — 클 · 서 · 쿠 (클라이언트 · 서버 CORS · 쿠키 속성)

클라이언트
credentials: 'include'
빠지면: 쿠키가 아예 안 실린다
서버 CORS
Allow-Credentials: true
Allow-Origin: https://app.example.com
빠지면: 응답을 못 읽는다
쿠키 속성
Set-Cookie: ...; Secure; SameSite=None
빠지면: 브라우저가 쿠키를 안 보낸다

셋 중 하나만 빠져도 "쿠키가 안 실린다" 또는 "응답을 못 읽는다"로 나타난다. 그리고 SameSite=None은 CSRF 방어를 스스로 끄는 선택이므로 CSRF 토큰 같은 별도 장치가 함께 와야 한다(4절).

10. Spring 설정 — * 복붙이 만드는 구멍

Spring에는 CORS 설정 위치가 여러 곳이라 헷갈리기 쉽다. 무엇이 어디까지 담당하는지부터 정리한다.

@CrossOrigin
컨트롤러·메서드에 붙이는 국소 설정. 편하지만 설정이 코드 곳곳에 흩어져 "지금 어느 출처에 열려 있는가"를 한눈에 볼 수 없다.
WebMvcConfigurer#addCorsMappings
애플리케이션 전역 설정. 경로 패턴 단위로 허용 규칙을 정의한다. 보안 설정은 한곳에 모으는 편이 낫다.
CorsConfigurationSource + http.cors()
Spring Security를 쓸 때의 정답 자리(11절). CorsFilter가 인증 앞단에 배치된다.
before "일단 되게" — 모든 출처 + 자격증명 허용
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOriginPatterns("*")   아무 사이트나
                .allowCredentials(true);      쿠키까지
    }
}

// 이 조합이 왜 위험한가:
//   악성 사이트가 방문자의 로그인 세션으로 우리 API를 호출하고
//   응답까지 읽어간다. SOP가 막아주던 것을 직접 연 셈이다.
//
// allowedOrigins("*") + allowCredentials(true)는 스펙 위반이라
// Spring이 기동 시점에 예외를 던진다. 그래서 이를 우회하려고
// allowedOriginPatterns("*")를 쓰는데, 이쪽은 요청의 Origin을
// 그대로 되비추어(echo) 응답하므로 사실상 전 출처 허용이 된다.
//   → 검증기를 통과할 뿐 위험은 그대로다.
after 신뢰하는 출처만 명시적으로 허용
@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")              열 경로만
                .allowedOrigins("https://app.example.com")  완전 일치
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("Authorization", "Content-Type")
                .exposedHeaders("X-Total-Count")      프론트가 읽어야 함
                .allowCredentials(true)
                .maxAge(3600);                        preflight 캐시
    }
}

// 허용 출처가 특정돼 있으므로 allowCredentials(true)가 성립한다.
// exposedHeaders를 지정해야 프론트가 X-Total-Count를 읽을 수 있다.
// maxAge로 같은 조건의 반복 요청에서 preflight 왕복이 사라진다.

핵심 원칙 — *를 쓸 수 있는 자리는 정해져 있다

Access-Control-Allow-Origin: *는 "누가 읽어가도 상관없는 공개 리소스"에만 쓴다

공개 폰트, 공개 시세 API, 로그인이 필요 없는 조회 API 같은 것들이다. 쿠키나 토큰이 실리는 API라면 반드시 허용 목록(allowlist) 방식이어야 한다.

Access-Control-Allow-Origin은 값이 하나만 올 수 있다 — 그래서 Vary: Origin이 필요하다 시니어 변별 출처를 여럿 허용하려면 콤마로 나열하는 것이 아니라, 서버가 요청의 Origin을 허용 목록과 대조해 일치하면 그 값 하나를 되비추어(echo) 응답한다. Spring은 이 처리를 대신해 준다.
다만 이 방식은 응답이 요청 헤더에 따라 달라진다는 뜻이므로, 앞단에 캐시(CDN, 프록시)가 있다면 Vary: Origin을 함께 내려야 A 출처용 응답이 B 출처에 재사용되는 사고를 막는다. Spring의 CORS 처리는 이 헤더를 붙여 주지만, 직접 필터를 구현했다면 빠뜨리기 쉽다.

11. Spring Security를 쓰면 위 설정이 안 먹는다 — 필터 체인 순서 문제

전형적인 사고가 하나 있다. addCorsMappings로 CORS를 잘 설정했는데도 프론트에서는 계속 CORS 에러가 나고, 개발자도구를 보면 OPTIONS 요청이 401로 떨어져 있다. 원인은 처리 순서다.

before Security가 preflight까지 인증 대상으로 삼는다
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults());
    // cors() 설정이 없다 → CorsFilter가 체인에 없다
    // → OPTIONS도 인증 검사를 받고 401 → preflight 실패
    return http.build();
}
after CorsFilter가 인증 앞단에서 preflight를 처리한다
@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.cors(Customizer.withDefaults())   CorsConfigurationSource 빈 사용
        .csrf(csrf -> csrf.disable())      // 토큰 인증이라면(쿠키 세션이면 켜 둔다)
        .authorizeHttpRequests(auth -> auth.anyRequest().authenticated());
    return http.build();
}

@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration config = new CorsConfiguration();
    config.setAllowedOrigins(List.of("https://app.example.com"));
    config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
    config.setAllowedHeaders(List.of("Authorization", "Content-Type"));
    config.setAllowCredentials(true);
    config.setMaxAge(3600L);

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/api/**", config);
    return source;
}
자주 보이는 잘못된 처방 — OPTIONS를 통째로 permitAll auth.requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()로 증상을 없애는 방법이다. 401은 사라진다. 그러나 CORS 응답 헤더를 붙여주는 주체가 여전히 없으므로 결국 preflight가 실패하거나, 운 좋게 동작해도 "CORS 설정이 어디에 있는지 알 수 없는" 구성이 남는다.
CORS는 CORS 처리기가 담당하게 하는 것이 올바른 해법이다
커스텀 JWT 인증 필터를 직접 만들었다면 한 줄 더 필요하다 체인에 직접 끼워 넣은 필터 안에서도 preflight를 건너뛰도록 해야 한다. Spring이 판정 유틸을 제공한다. 
// 커스텀 인증 필터: preflight는 인증 대상이 아니므로 그냥 흘려보낸다
@Override
protected boolean shouldNotFilter(HttpServletRequest request) {
    return CorsUtils.isPreFlightRequest(request);
}

12. Nginx·LB 이중 헤더 · 환경별 허용 목록

12-1. 헤더를 한 번 더 붙이면 브라우저가 거부한다

인프라 앞단에서 CORS를 처리하는 구성도 흔하다. 문제는 애플리케이션도 붙이고 앞단도 붙이는 이중 설정이다. Access-Control-Allow-Origin 헤더가 응답에 두 개 실리면 브라우저는 값이 맞는지 따지지 않고 응답을 거부한다. 콘솔에는 The 'Access-Control-Allow-Origin' header contains multiple values 류의 메시지가 뜬다 — 값이 둘 다 옳아도 마찬가지다. 스펙상 이 헤더는 하나여야 하기 때문이다.

before 백엔드가 이미 붙이는데 nginx가 한 번 더 붙인다
location /api/ {
    proxy_pass http://backend;
    add_header 'Access-Control-Allow-Origin' 'https://app.example.com' always;
    # 백엔드 응답에도 같은 헤더가 있으므로 최종 응답에 두 개가 실린다
    # → 브라우저가 응답 자체를 거부한다
}

after (방법 1) — 애플리케이션 한 곳에서만 처리

location /api/ {
    proxy_pass http://backend;
    # 헤더를 추가하지 않는다.
    # 책임 지점을 하나로 유지하는 것이 핵심.
}

after (방법 2) — 앞단에서 처리하기로 했다면 백엔드 것을 걷어낸다

location /api/ {
    proxy_pass http://backend;
    proxy_hide_header 'Access-Control-Allow-Origin';
    add_header 'Access-Control-Allow-Origin' 'https://app.example.com' always;
    add_header 'Access-Control-Allow-Credentials' 'true' always;
    add_header 'Vary' 'Origin' always;
}

nginx에서만 나오는 함정 둘

① always를 빼면 "가끔 나는 CORS 에러"가 된다
이 지시어가 없으면 nginx는 성공 계열 응답에만 헤더를 붙이고 4xx·5xx에는 붙이지 않는다. 그러면 서버가 500을 낼 때만 CORS 에러로 바뀌어, 프론트에서는 진짜 원인(500)이 보이지 않는다. always를 붙이면 오류 응답에도 헤더가 실려 프론트가 상태 코드를 읽을 수 있다.
② add_header의 상속 규칙
nginx는 하위 블록에 add_header가 하나라도 있으면 상위 블록의 add_header를 전부 무시한다. server 레벨에 CORS 헤더를 정의해 놓고 특정 location에 캐시 헤더 하나를 추가했더니 그 경로에서만 CORS가 깨지는 일이 여기서 생긴다.
CORS 헤더를 붙이는 지점은 시스템 전체에서 한 곳이어야 한다 — 정하고, 나머지는 손대지 않는다

12-2. 환경별 허용 목록 관리 — 운영에 localhost가 남는 사고

개발(http://localhost:3000), 스테이징, 운영은 도메인이 다르므로 허용 목록을 환경설정으로 분리해야 한다. 코드에 출처를 하드코딩하면 그것이 그대로 전 환경에 배포된다.

설정 프로파일별로 허용 목록을 분리한다
# application-prod.yml — 운영에는 운영 도메인만
cors:
  allowed-origins:
    - https://app.example.com
    - https://admin.example.com

# application-local.yml — 로컬에만 개발 서버 출처
cors:
  allowed-origins:
    - http://localhost:3000
주입 하드코딩하지 않고 설정에서 받는다
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Value("${cors.allowed-origins}")
    private List<String> allowedOrigins;

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
                .allowedOrigins(allowedOrigins.toArray(String[]::new))
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
// 코드에 localhost가 박혀 있으면 그것이 운영에도 그대로 배포된다.
사고 ① 운영 설정에 localhost가 남아 배포된다
공격자가 자기 PC에서 localhost:3000으로 페이지를 띄워 놓고 피해자를 유인해, 피해자의 운영 세션 쿠키로 운영 API를 호출하고 응답을 읽어갈 수 있다.
"로컬이니까 나만 쓰는 주소"라는 감각이 틀린 이유는, localhost가 공격자의 로컬이기도 하기 때문이다.
사고 ② 서브도메인 와일드카드를 정규식으로 직접 구현
*.example.com을 허용하려고 정규식을 손으로 짜면 경계 처리를 빠뜨리기 쉽다. 점을 이스케이프하지 않거나 끝 앵커를 빼면 evil-example.com이나 example.com.evil.com 같은 도메인이 통과한다.

출처 검증의 원칙

문자열 완전 일치 목록이 가장 안전하다 — 패턴이 꼭 필요하면 직접 짜지 말고 검증된 구현을 쓴다

Spring의 allowedOriginPatterns처럼 검증된 구현을 쓰고, 배포 파이프라인에 운영 프로파일의 허용 목록을 점검하는 단계를 두면 더 좋다.

13. 성능 — preflight 왕복을 줄이는 세 가지 방향

preflight는 본 요청 앞에 왕복(RTT, round-trip time — 요청을 보내고 응답을 받기까지 걸리는 왕복 시간)을 하나 더 얹는다. 국내 서버라면 수 밀리초지만 해외 리전이라면 수십에서 백여 밀리초가 요청마다 추가될 수 있다. 화면 하나가 API를 열 번 호출한다면 그만큼이 곱해진다.

preflight 줄이기 세 방향 — 캐 · 단 · 구 (캐시 · 단순요청 · 구조)

① 캐시
Access-Control-Max-Age로 허가를 캐시한다. 브라우저가 결과를 그 초 동안 기억하고 같은 조건의 요청에는 다시 묻지 않는다.
반복 호출의 왕복이 사라진다.
② 단순 요청
조건에 맞으면 preflight 자체가 생기지 않는다.
다만 이를 위해 JSON 대신 폼 인코딩을 쓴다거나 Authorization을 포기하는 식으로 설계를 비틀 필요는 없다 — 얻는 것보다 잃는 것이 크다.
③ 구조
교차 출처 상황 자체를 없앤다. 같은 도메인 아래에서 리버스 프록시가 경로로 라우팅하면 브라우저 입장에서 동일 출처이므로 CORS라는 개념이 아예 등장하지 않는다.
Max-Age의 한계 두 가지 — 여기까지 말하면 답이 정확해진다 가산점 ① 브라우저마다 상한이 있다. 아무리 큰 값을 줘도 그 이상은 캐시되지 않는다. 상한 값은 브라우저와 버전마다 다르므로 "하루로 설정했으니 하루 동안 안 물어본다"고 가정하면 안 된다.
② 캐시는 요청 URL 단위다. 엔드포인트가 100개면 각각 첫 호출 때 preflight가 발생한다. 즉 Max-Age는 반복 호출을 줄여 줄 뿐, 첫 진입 시의 왕복은 없애지 못한다.
"Max-Age를 크게 주면 해결"이 아니라 — 반복 호출은 캐시로, 첫 진입 비용은 구조로
설정 한 도메인 아래로 프론트와 API를 모은다
server {
    server_name app.example.com;

    location /api/ {
        proxy_pass http://backend:8080/;   # 브라우저는 동일 출처로 인식한다
    }

    location / {
        proxy_pass http://frontend:3000/;
    }
}

14. 인출 카드 · 꼬리질문 셀프 테스트

14-1. CORS 에러 디버깅 순서 — 개발자도구에서 무엇부터 보는가

1
네트워크 탭에 OPTIONS 요청이 있는가를 먼저 본다. 이 한 가지로 탐색 범위가 절반으로 줄어든다 — preflight가 필요한 요청인지 아닌지가 여기서 갈린다.
2
OPTIONS가 있고 실패했다면 → 본 요청은 아예 나가지 않았다. 대표 원인은 Security 필터의 401(11절)과 Allow-Headers 누락이다. 응답 상태 코드와 Access-Control-Allow-Methods·Allow-Headers 값을 확인한다.
3
OPTIONS가 없는데 에러라면 → 단순 요청이 서버까지 갔다가 응답 헤더가 없어 막힌 것이다. 문제는 본 응답에 Access-Control-Allow-Origin을 붙이는 것으로 좁혀진다. 그리고 부수효과는 이미 일어났다고 가정하고 데이터를 확인한다.
4
OPTIONS는 204인데 본 요청에서 또 에러라면 → 본 응답에 허용 헤더를 안 붙인 구성이다(8-2절). preflight만 처리하는 필터를 쓰고 있지 않은지 본다.
5
그래도 원인이 안 보이면 서버 로그를 본다. 서버가 500을 냈을 때도 CORS 에러로 보인다 — 오류 응답에 CORS 헤더가 빠지는 구성(always 누락, 예외 핸들러 우회)이 많기 때문이다. "CORS 에러인데 알고 보니 500이었다"는 사례가 흔하다.
디버깅 비용을 크게 줄이는 설정 하나 오류 응답에도 CORS 헤더가 실리게 하는 것. 그래야 프론트가 response.status를 읽어 "500이구나"라고 말할 수 있고, "가끔 CORS 에러가 난다"는 신고가 사라진다.

14-2. 3초 인출 카드 — 보기 전에 먼저 답해보기

CORS 한 문장 정의?
SOP가 막아 놓은 교차 출처 응답 읽기를, 서버가 응답 헤더로 동의한 범위만큼 풀어주는 브라우저 시스템. 막는 건 SOP, 여는 게 CORS.
CORS가 막는 것은?
요청이 아니라 응답 읽기. 그래서 서버 로그 200 + 프론트 CORS 에러가 정상이고, 부수효과는 이미 일어났다.
출처(origin)의 구성?
스 · 호 · 포 — 스킴 + 호스트 + 포트. 하나라도 다르면 남남. 경로는 무관. localhost:3000 ↔ :8080이 대표 사례.
단순 요청 세 조건?
메 · 헤 · 타 — GET/HEAD/POST · 안전 목록 헤더만 · Content-Type이 폼 3종. 근거는 "옛날 HTML 폼으로 보낼 수 있던 요청".
preflight의 존재 이유?
CORS 이전 서버 보호. 허락이 없으면 부수효과가 있는 본 요청이 도달조차 하지 않는다. OPTIONS인 이유는 부수효과가 없는 메서드라서.
자격증명 3종 세트?
클 · 서 · 쿠 — credentials:'include' / Allow-Credentials: true + 구체 Origin / Secure; SameSite=None.
절대 금지 조합?
Allow-Origin: * + Allow-Credentials: true. SOP가 지켜주던 것을 우리 손으로 여는 셈이라 스펙이 조합 자체를 금지.
본 응답에도 필요한 헤더 둘?
Access-Control-Allow-Origin, Access-Control-Allow-Credentials. "보내도 된다"와 "읽어도 된다"는 별개의 동의.
프론트가 응답 헤더를 못 읽을 때?
Access-Control-Expose-Headers 미지정. X-Total-Count·Location은 명시 노출해야 읽힌다.
Security에서 OPTIONS가 401인 이유?
preflight에는 쿠키도 Authorization도 실리지 않는다. 해법은 http.cors()로 CorsFilter를 인증 앞단에 두는 것.
preflight 줄이는 세 방향?
캐 · 단 · 구 — Max-Age 캐시 · 단순 요청 유지 · 구조적으로 동일 출처화. 반복은 캐시로, 첫 진입은 구조로.
CORS가 실제로 지키는 것 하나?
"브라우저에서 실행되는 다른 사이트의 스크립트가, 방문자의 인증 상태를 빌려 우리 응답을 읽어가는 것" — 그 범위 밖은 지키지 않는다.

14-3. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

서버 로그에는 200인데 프론트에서 CORS 에러가 납니다. 왜죠? 필수힌트: "집행자가 누구인가"로 시작하고, 디버깅 순서까지 붙이면 답이 완성된다

차단의 집행자가 서버가 아니라 브라우저이기 때문이라고 먼저 말한다.

단순 요청은 서버까지 가서 정상 처리되고 200 응답까지 돌아온다. 브라우저는 그 응답을 손에 쥔 상태에서 Access-Control-Allow-Origin을 확인하고, 없거나 맞지 않으면 스크립트에 전달하는 단계에서 폐기한다. 서버는 자기 몫을 다 했으므로 로그에 이상이 없다.

"CORS 에러 = 요청이 안 갔다"가 아니다 — 부수효과가 있는 요청이었다면 그 효과는 이미 일어났다

디버깅 순서까지 붙이면 답이 완성된다. 먼저 개발자도구 네트워크 탭에서 OPTIONS 요청이 있는지 본다. 있다면 preflight가 필요한 요청이고, 그것이 실패했다면 본 요청은 아예 나가지 않았다는 뜻이다(대표 원인: Security의 401). OPTIONS가 없는데 에러라면 단순 요청이 서버까지 갔다가 응답 헤더가 없어 막힌 것이므로, 본 응답에 허용 헤더를 붙이는 문제로 좁혀진다.

한 가지 더 얹으면 좋다. 서버가 500을 냈을 때도 CORS 에러로 보인다. 오류 응답에는 CORS 헤더가 빠지는 구성이 많아(nginx의 always 누락, 예외 핸들러 우회 등) 브라우저가 상태 코드를 스크립트에 넘겨주지 않기 때문이다. 그래서 오류 응답에도 CORS 헤더가 실리게 하는 것이 디버깅 비용을 크게 줄인다.

CORS를 설정했으니 우리 API는 안전한 건가요? 시니어 변별힌트: "아니다"로 시작하고, 지키는 범위를 한 문장으로 좁혀 말한 뒤 CSRF와의 구분으로 마무리한다

아니다. CORS는 브라우저 안에서만 작동하는 규칙이다.

curl, 서버 간 호출, 모바일 앱, 스크립트 도구, 공격자가 만든 프록시에는 아무 제약이 없다. Origin 헤더를 마음대로 위조할 수도 있다 — 브라우저만 위조를 막을 뿐, 브라우저가 아닌 도구는 무엇이든 보낼 수 있다. 따라서 CORS는 인증·인가를 대체하지 못하고, "교차 출처 요청 자체"를 막는 수단도 아니다. 인증 토큰 검증, 권한 검사, 입력 검증은 CORS와 무관하게 전부 있어야 한다.

CORS가 지키는 것은 하나 — "브라우저에서 실행되는 다른 사이트의 스크립트가, 방문자의 인증 상태를 빌려 우리 응답을 읽어가는 것"

여기에 CSRF와의 구분을 덧붙이면 답이 완성된다. CORS를 완벽하게 잠가도 폼 제출 기반 CSRF는 그대로 성립한다 — 공격자는 응답을 읽으려는 게 아니라 부수효과만 노리기 때문이다. CORS와 CSRF 방어는 서로 다른 문제를 푼다는 구분이 시니어의 답변이다.

preflight 때문에 API가 느려진다는데, 줄이는 방법은?힌트: 세 방향을 나누고, 마지막에 "캐시로 안 되는 것"을 덧붙인다

① Access-Control-Max-Age로 preflight 결과를 브라우저에 캐시시킨다. 같은 조건의 반복 요청에서 왕복이 사라진다.

② 요청을 단순 요청 조건 안에 유지할 수 있다면 preflight 자체가 생기지 않는다. 다만 이를 위해 API 설계를 비틀 필요는 없다 — JSON을 폼 인코딩으로 바꾸거나 Authorization을 포기하면 얻는 것보다 잃는 것이 크다.

③ 구조적으로는 교차 출처 상황을 없앤다. 같은 도메인 아래에서 리버스 프록시가 /api를 백엔드로 라우팅하면 브라우저 입장에서 동일 출처가 되어 CORS가 아예 등장하지 않는다.

(가산점) preflight 캐시의 한계까지 말하면 좋다. 캐시는 요청 URL 단위라 엔드포인트가 많으면 첫 호출들에는 여전히 preflight가 발생하고, 브라우저마다 Max-Age 상한이 있어 설정한 값이 그대로 적용된다는 보장도 없다. 그래서 "Max-Age를 크게 주면 해결된다"가 아니라 "반복 호출은 캐시로, 첫 진입 비용은 구조로"라고 나눠 답하는 편이 정확하다.

어떤 요청이 preflight 없이 나가나요? (단순 요청의 조건) 필수힌트: 세 조건을 나열한 뒤, 반드시 "왜 그 조건인지"로 넘어간다

세 조건이 동시에 성립할 때다. ① 메서드가 GET/HEAD/POST이고, ② 직접 붙인 헤더가 안전 목록(Accept, Accept-Language, Content-Language, Content-Type) 안에만 있고, ③ Content-Type이 application/x-www-form-urlencoded, multipart/form-data, text/plain 중 하나일 때다.

기준을 외우기보다 "왜 그 조건인지"로 답하는 편이 낫다. "옛날 HTML 폼으로도 보낼 수 있던 요청"이 단순 요청이다. 이런 요청은 CORS가 없던 시절부터 서버가 받아오던 형태라 새로운 위협이 아니므로 그냥 통과시킨다.

반대로 Content-Type: application/json이거나 Authorization 헤더 하나만 붙어도 preflight 대상이 된다. JSON API 호출 대부분에 preflight가 따라붙는 이유가 이것이고, "GET인데 왜 preflight가 뜨냐"는 질문의 답도 대개 메서드가 아니라 헤더 쪽에 있다.

CORS 허용 출처를 환경별로 관리하다 겪는 문제는? 함정힌트: localhost가 "누구의" 로컬인지를 뒤집어 말하면 임팩트가 있다

개발(localhost:3000), 스테이징, 운영의 도메인이 다르므로 허용 목록을 프로파일별 설정으로 분리해야 한다. 코드에 출처를 하드코딩하면 그것이 그대로 전 환경에 배포된다.

① 운영 설정에 localhost가 남아 배포되는 것. localhost는 "나만 쓰는 주소"가 아니라 공격자의 로컬이기도 하므로, 공격자가 자기 PC에서 페이지를 띄워 피해자의 운영 세션으로 운영 API를 호출하고 응답을 읽어갈 수 있다.

② 서브도메인 와일드카드를 정규식으로 직접 구현하다 우회당하는 것. 점을 이스케이프하지 않거나 끝 앵커를 빠뜨리면 evil-example.com, example.com.evil.com 같은 도메인까지 매칭된다.

출처 검증은 문자열 완전 일치 목록이 가장 안전하다 — 패턴이 필요하면 검증된 구현을 쓰고, 배포 파이프라인에 운영 프로파일 허용 목록 점검 단계를 둔다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

OPTIONS는 204로 잘 오는데 본 요청에서 다시 CORS 에러가 납니다.힌트: preflight의 허가가 무엇에 대한 허가였는지를 되짚는다

preflight를 통과했다고 본 응답을 읽을 수 있는 것이 아니다. ②의 허가는 "보내도 된다"였을 뿐이고, "읽어도 된다"는 본 응답에서 다시 말해야 하는 별개의 동의다. 즉 본 응답에도 Access-Control-Allow-Origin이 있어야 한다(자격증명을 쓴다면 Access-Control-Allow-Credentials: true도 함께).

전형적인 구성 실수는 preflight만 가로채 응답하는 필터나 프록시 규칙을 두고, 본 요청은 그대로 흘려보내는 경우다. 이때 증상이 정확히 "OPTIONS는 204인데 본 요청에서 또 CORS 에러"로 나타난다.

확인 순서: 본 요청의 응답 헤더를 네트워크 탭에서 직접 펼쳐 Access-Control-Allow-Origin이 실제로 있는지 본다. 있는데도 실패한다면 값이 요청의 Origin과 문자 그대로 일치하는지(끝의 슬래시, 포트 유무, http/https)를 본다.

Access-Control-Allow-Origin에 허용 출처 두 개를 콤마로 나열하면 안 되나요? 시니어 변별힌트: 안 된다고 답한 뒤, 그 대신 쓰는 방식이 만드는 부작용까지 말한다

안 된다. 이 헤더는 값이 하나만 올 수 있다. 출처를 여럿 허용하려면 서버가 요청의 Origin을 허용 목록과 대조해, 일치하면 그 값 하나를 되비추어(echo) 응답한다. Spring은 이 처리를 대신해 준다.

여기서 한 칸 더 나가는 것이 부작용이다. 이 방식은 응답이 요청 헤더(Origin)에 따라 달라진다는 뜻이므로, 앞단에 캐시(CDN, 프록시)가 있으면 A 출처용 응답이 B 출처에 그대로 재사용되는 사고가 생긴다. 그래서 Vary: Origin을 함께 내려 캐시 키에 Origin을 포함시켜야 한다.

Spring의 CORS 처리는 이 헤더를 붙여 주지만, 직접 필터를 구현했거나 nginx에서 add_header로 처리했다면 빠뜨리기 쉽다. 12절의 방법 2 예시에 add_header 'Vary' 'Origin' always;가 들어 있는 이유가 이것이다.

서버가 X-Total-Count를 내려주는데 프론트에서는 헤더가 없다고 합니다.힌트: 응답 본문과 응답 헤더는 노출 규칙이 다르다

교차 출처 응답에서 스크립트가 읽을 수 있는 응답 헤더는 기본적으로 극히 일부(Content-Type 등)로 제한된다. 본문은 Allow-Origin만 있으면 읽히지만, 헤더는 별도로 열어줘야 한다.

그래서 페이징 총건수를 X-Total-Count로 내려주거나 생성된 자원 위치를 Location으로 주면 프론트에서는 그 헤더가 없는 것처럼 보인다. 서버가 명시적으로 노출해야 읽힌다.

Access-Control-Expose-Headers: X-Total-Count, Location
preflight OPTIONS에는 왜 인증 정보가 실리지 않나요? 필수힌트: 이 사실이 11절 사고의 뿌리다

preflight는 "허락을 구하는 요청"이지 "일을 시키는 요청"이 아니기 때문이고, 브라우저가 그렇게 보내도록 정해져 있다. OPTIONS에는 쿠키도 Authorization 헤더도 붙지 않는다. 대신 무엇을 보내려 하는지만 Access-Control-Request-Method와 Access-Control-Request-Headers로 알린다.

그래서 인증 필터가 preflight까지 검사하면 반드시 막힌다. Spring Security에서 OPTIONS가 401로 떨어지는 사고의 뿌리가 정확히 이 지점이고(11절), 해결은 http.cors()로 CorsFilter를 인증 앞단에 배치해 preflight를 인증 검사에 도달하기 전에 처리하는 것이다.

설계 관점으로 한 문장 더 — 이 규칙은 합리적이다. 서버가 "이 메서드·헤더를 허용하는가"를 답하는 데 사용자 인증은 필요 없고, 오히려 인증을 요구하면 "허락을 받으려면 먼저 요청을 보내야 하는" 순환이 생긴다.

Access-Control-Allow-Origin: *는 언제 써도 되나요? 함정힌트: "쓰면 안 된다"가 아니라 "쓸 수 있는 자리가 정해져 있다"로 답한다

*는 "누가 읽어가도 상관없는 공개 리소스"라는 선언이다. 그러니 공개 폰트, 공개 시세 API, 로그인이 필요 없는 조회 API 같은 것에는 정당한 선택이다.

반대로 쿠키나 토큰이 실리는 API라면 반드시 허용 목록(allowlist) 방식이어야 한다. 특히 자격증명이 실린 요청에는 스펙이 *를 아예 금지한다 — * + Allow-Credentials: true 조합은 "아무 사이트나 방문자의 로그인 세션으로 우리 API를 호출하고 응답을 읽어가도 된다"가 되어, SOP가 지켜주던 것을 우리 손으로 여는 셈이기 때문이다.

우회 시도까지 알고 있으면 좋다. Spring에서 allowedOrigins("*") + allowCredentials(true)는 기동 시점에 예외가 난다. 그래서 allowedOriginPatterns("*")로 바꾸는 코드를 자주 보는데, 이쪽은 요청의 Origin을 그대로 되비추므로 사실상 전 출처 허용이다. 검증기를 통과할 뿐 위험은 그대로다.

백엔드와 nginx 양쪽에 CORS를 설정했더니 오히려 깨졌습니다.힌트: 값이 옳은지 그른지의 문제가 아니다

Access-Control-Allow-Origin이 응답에 두 개 실렸기 때문이다. 브라우저는 값이 맞는지 따지지 않고 응답 자체를 거부한다 — 값이 둘 다 옳아도 마찬가지다. 스펙상 이 헤더는 하나여야 하기 때문이다. 콘솔에는 ...header contains multiple values 류의 메시지가 뜬다.

CORS 헤더를 붙이는 지점은 시스템 전체에서 한 곳이어야 한다

해법은 둘 중 하나다. ① 애플리케이션에서만 처리하고 프록시는 전달만 한다. ② 앞단에서 처리하기로 했다면 proxy_hide_header로 백엔드 헤더를 걷어낸 뒤 붙인다.

nginx라면 함정 둘을 같이 말한다. add_header에 always가 없으면 4xx·5xx 응답에 헤더가 안 붙어 "가끔 CORS 에러"가 되고, 하위 블록에 add_header가 하나라도 있으면 상위 블록의 add_header가 전부 무시되어 특정 경로에서만 CORS가 깨진다.

프론트와 API 도메인을 분리할지 합칠지, 어떤 기준으로 결정하나요? 시니어 변별힌트: CORS 하나만 보고 결정하는 게 아니라, 따라오는 것들을 세트로 본다

도메인을 합치면(리버스 프록시로 경로 라우팅) 세 가지가 한꺼번에 사라진다 — preflight 왕복, SameSite=None 요구(같은 사이트가 되므로), CORS 허용 목록 유지보수. 그래서 "CORS 문제를 푸는 가장 좋은 방법이 CORS를 만들지 않는 것"인 경우가 실제로 많다.

반대로 분리를 택하는 이유도 있다 — API를 여러 프론트(웹·모바일웹·파트너)가 공유하거나, 프론트를 CDN/정적 호스팅에 그대로 올리고 싶을 때, 혹은 조직상 프론트와 백엔드의 배포·운영 경계를 나누고 싶을 때다. 이때는 교차 출처가 전제이므로 CORS를 제대로 설계해야 한다.

판단 기준을 한 문장으로: "이 API를 우리 프론트 하나만 쓰는가, 여러 클라이언트가 쓰는가". 전자면 합치는 쪽이 운영 비용이 낮고, 후자면 어차피 허용 목록을 관리해야 하므로 분리해도 잃는 것이 적다. 그리고 쿠키 세션을 쓰는데 도메인을 분리한다면 SameSite=None으로 CSRF 방어를 스스로 끄는 것이므로 CSRF 토큰을 반드시 함께 설계한다.

한 줄 요약
CORS는 브라우저의 동일 출처 차단을 서버가 응답 헤더로 동의한 범위만큼 풀어주는 절차이고, 막는 것은 요청이 아니라 응답 읽기여서 "서버 로그 200 + 프론트 CORS 에러"가 정상적으로 발생하며, preflight는 CORS 이전 시대 서버들이 예상 못 한 형태의 요청(PUT/DELETE, application/json, 커스텀 헤더)이 도달하기 전에 브라우저가 OPTIONS로 미리 허락을 구하는 보호 장치다 — 쿠키를 실으려면 credentials: 'include'와 Allow-Credentials: true가 짝을 이뤄야 하고 그때 *는 금지되며, 집행자는 언제나 브라우저이므로 CORS는 인증·인가의 대체재가 아니라 "필요한 출처에만, 필요한 만큼만" 여는 설정의 문제다.
