HTTP 캐싱 헤더와 304
백엔드가 내려주는 헤더가 브라우저·CDN 모두를 조종한다

면접 질문: "HTTP 캐싱 헤더(Cache-Control, ETag, Last-Modified)와 304 응답 흐름을 설명해주세요. CDN 캐시 제어와는 어떻게 연결되나요?"

핵심 관전 포인트 — HTTP 캐싱은 2단계로 동작한다. ① 신선도(freshness) — Cache-Control: max-age가 정한 기간 안에서는 캐시가 서버에 묻지도 않고 자기 사본으로 응답한다. 요청이 네트워크를 타지 않으므로 왕복이 0이고, 이것이 가장 강력한 단계다. ② 재검증(revalidation) — 신선도가 끝나면 캐시가 보관해 둔 검증자(ETag/Last-Modified)를 조건부 요청(If-None-Match/If-Modified-Since)에 실어 보내고, 내용이 그대로면 서버는 본문 없는 304 Not Modified만 돌려준다. 본문 전송은 아끼지만 왕복 1회는 그대로 내는 두 번째 단계다. 그래서 Cache-Control은 지시자를 나열식으로 외우는 게 아니라 저장 범위(public/private/no-store)·신선도(max-age/s-maxage)·재검증 강제(no-cache/must-revalidate)라는 서로 다른 세 축으로 갈라 봐야 하고, 이름 때문에 가장 많이 오해받는 no-cache는 "캐시하지 마라"가 아니라 "저장은 하되 쓰기 전에 반드시 물어봐라"다. 브라우저 캐시든 CDN이든 이 헤더 계약을 실행하는 대리인일 뿐이므로 주도권은 헤더를 내려주는 백엔드에 있고, 정적 자원의 정답은 파일명에 내용 해시를 박아 URL 자체를 불변으로 만든 뒤 max-age=31536000, immutable을 거는 것(HTML만 no-cache)이며 304는 그것이 불가능할 때의 차선책이다. 그리고 이 강력함의 이면 — 개인화 응답에 public을 잘못 걸면 CDN이 A의 응답을 B에게 서빙하는 정보 유출이 되고, 서버를 재배포해도 캐시에 남은 사본은 사라지지 않는다.
  • 1
    캐싱은 "묻지 않기"와 "싸게 묻기"의 2단계다 — max-age 기간 안에는 네트워크로 나가는 패킷 자체가 없고(왕복 0), 만료된 뒤에는 사본을 버리는 대신 검증자를 조건부 요청에 실어 보내 본문 없는 304로 끝낸다(왕복 1 + 본문 0). 그래서 304는 공짜가 아니다 — 아낀 것은 바이트일 뿐 왕복은 그대로 낸다.
  • 2
    Cache-Control은 한 덩어리가 아니라 축이 다른 세 질문의 조합이다 — 누가 보관하나(public/private/no-store) · 얼마나 안 묻나(max-age/s-maxage/immutable) · 쓰기 전에 묻나(no-cache/must-revalidate). 축이 다르므로 public, max-age=0, s-maxage=30처럼 하나씩 골라 조합한다. no-store가 "저장 금지", no-cache가 "확인 없이 쓰지 마"다.
  • 3
    그래서 목표는 304를 많이 받는 게 아니라 애초에 묻지 않아도 되게 만드는 것이다 — 파일명에 내용 해시를 박아 URL을 불변으로 만들면 max-age=31536000, immutable로 왕복이 0이 되고, HTML만 no-cache로 두어 항상 최신 파일명을 가리키게 한다. 동시에 public 한 단어가 개인화 응답을 공유 캐시에 남기는 유출 경계선이라, 캐시 헤더는 성능 설정이자 접근 제어의 일부다.

0. 질문 + 출제 의도

질문: "HTTP 캐싱 헤더(Cache-Control, ETag, Last-Modified)와 304 응답 흐름을 설명해주세요. CDN 캐시 제어와는 어떻게 연결되나요?"

출제 의도: CDN·브라우저 캐시는 백엔드가 내려주는 헤더로 조종된다. 콘텐츠 서비스에서 Cache-Control 설계는 성능 도구이자, 잘못 쓰면 개인화 응답이 공유 캐시에 남는 보안 사고의 원인 — 이 양면을 다 아는지 본다. 캐시를 "인프라 팀 일"로 미루는 사람인지, 응답 헤더가 캐시 계층 전체의 리모컨임을 아는 사람인지 가리는 질문이다.

이 페이지가 겨냥하는 약점 네 가지 ① 지시자를 평평한 목록으로 외우는 것 → 4절에서 Cache-Control을 저장 범위·신선도·재검증 강제라는 세 축으로 분해해 "조합"으로 읽게 만든다.
② no-cache를 "캐시 금지"로 아는 것 → 5절에서 두 지시자가 같은 요청에서 각각 무엇을 하는지를 나란히 놓고 본다.
③ "304 = 최적화 완료"라고 믿는 것 → 2절의 비용 사다리 3칸으로 304는 가운데 칸임을 못박고, 12절에서 맨 위 칸으로 올리는 처방을 준다.
④ 캐시를 성능 설정으로만 보는 것 → 13절에서 public 한 단어가 정보 유출이 되는 시나리오를 시간 순으로 따라간다. 캐시는 인증 계층보다 앞에 있다.

1. 전제 — 여기서 말하는 "캐시"는 Redis가 아니다

용어를 좁히고 시작하자. 백엔드 개발자가 "캐시"라고 하면 보통 Redis를 떠올린다. 그것은 애플리케이션이 자기 판단으로 관리하는 저장소다 — 무엇을 넣을지, 언제 지울지를 우리 코드가 직접 정한다.

이 문서가 다루는 것은 다른 종류다. HTTP 캐시는 요청과 응답 사이에 끼어 있는 중간 참여자들이 응답 헤더에 적힌 지시를 읽고 스스로 사본을 보관·재사용하는 장치다. 우리 코드는 그들에게 명령을 직접 내리지 않는다. 응답에 헤더를 적어 보내면 그 헤더를 읽은 각 계층이 알아서 행동한다. 그래서 이것은 명령이 아니라 계약이다.

개인 캐시 (private cache)
사용자 한 명에게만 속한 캐시. 브라우저가 디스크에 저장하는 캐시가 대표적이다. 여기 저장된 사본은 그 사람 말고는 볼 수 없다. 대신 서버가 원격으로 지울 방법도 없다(12절의 핵심).
공유 캐시 (shared cache)
여러 사용자의 요청이 함께 지나가는 지점의 캐시. CDN 엣지, 리버스 프록시(Nginx proxy_cache), 사내 포워드 프록시. 한 번 저장된 사본이 다음에 오는 다른 사람에게 그대로 나간다 — 성능의 핵심이자 사고의 원인(13절).

2. 캐시가 사본 앞에서 던지는 두 개의 질문 — 그리고 비용 사다리 3칸

캐시가 저장해 둔 사본을 가지고 있을 때, 새 요청이 들어오면 순서대로 두 가지를 판단한다. HTTP 캐싱 전체가 이 두 질문의 구조다. 이 절만 제대로 잡으면 나머지 헤더는 전부 "이 두 질문의 답을 조정하는 손잡이"로 읽힌다.

질문 ① 이 사본은 아직 신선한가?
신선하면 서버에 묻지 않고 그대로 응답한다. 요청이 네트워크를 타지 않으므로 왕복 0회. 판단 기준을 정하는 것이 Cache-Control: max-age. 이 단계가 신선도(freshness)다.
질문 ② 내용이 그대로인지 싸게 확인할 방법이 있나?
만료된 사본을 곧바로 버리는 것은 아깝다. 그래서 "내가 가진 게 아직 최신인가?"만 묻는다. 재료가 ETag·Last-Modified. 이 단계가 재검증(revalidation)이다.

비유로 잡아두면 잊지 않는다 — 냉장고 우유

유통기한 = max-age. 기한 안이면 아무 확인 없이 그냥 마신다(서버에 가지 않는다). 기한이 지났다고 바로 버리지는 않는다 — 냄새를 맡아 본다(재검증). 멀쩡하면 유통기한만 새로 붙이고 계속 마신다(304를 받고 신선도 갱신).

냄새 맡기(왕복 1회)는 마트에 다시 다녀오기(본문 전체 재전송)보다 훨씬 싸다 — 하지만 냉장고 문을 열지 않는 것(왕복 0)보다는 비싸다. 이 마지막 문장이 12절의 결론으로 이어진다.

같은 요청의 세 가지 결과. 면접에서 값이 나가는 줄은 "네트워크 왕복" 열이다 — 304와 신선 히트를 가르는 것이 그 열이다.

여기서 나오는 핵심 결론 하나 — 304는 공짜가 아니다

리소스가 40개인 페이지에서 전부 304가 나오면 왕복도 40번 일어난다. 모바일 회선처럼 왕복 시간(RTT)이 큰 환경에서는 이 40번이 그대로 체감 지연이 된다. 응답 본문이 작은 리소스일수록 본문 전송보다 왕복 비용이 지배적이라 304의 이득도 작다.

성능 설계의 목표는 "304를 많이 받는 것"이 아니라 애초에 묻지 않아도 되는 상태로 올리는 것

이 결론이 12절의 불변 자산 전략으로 그대로 이어진다. 304는 "URL을 바꿀 수 없는데 갱신 가능성은 있는" 리소스의 차선책이지, 정적 자원의 1차 전략이 아니다.

3. 헤더를 안 주면 캐시가 없어지는 게 아니라 통제를 잃는다

주니어가 가장 많이 하는 오해가 이것이다. 캐시 헤더를 아무것도 안 붙이면 "캐시가 안 되겠지"라고 생각한다. 실제로는 반대다.

HTTP 명세는 캐시에게 휴리스틱 캐싱(heuristic caching)을 허용한다. 응답에 명시적 수명이 없어도, 캐시가 다른 단서로 수명을 스스로 추정해 저장할 수 있다는 규칙이다. 널리 쓰이는 추정식은 Last-Modified가 있을 때 "(현재 시각 − Last-Modified)의 10%"를 신선 기간으로 삼는 것이다. 한 달 전에 수정된 파일이라면 사흘쯤 신선하다고 간주해 버린다는 뜻이다.

그래서 헤더가 없는 응답의 상태는 "캐시 안 됨"이 아니다 "캐시 동작이 계층마다 제각각이고 우리가 모름"이다. 이런 상태에서 나오는 것이 재현이 안 되는 버그다 — 내 브라우저에서는 재현되지 않고, 문제를 겪는 사용자도 며칠 뒤에는 저절로 사라진다. 원인을 찾을 수 없는 것이 가장 큰 비용이다.
Before 아무 캐시 헤더도 없는 응답
HTTP/1.1 200 OK
Content-Type: application/json
Last-Modified: Mon, 25 Aug 2025 09:00:00 GMT

# 명시적 수명이 없다. 그런데 Last-Modified 는 있다.
# → 캐시가 휴리스틱으로 수명을 "발명"할 재료를 준 셈.
#
# 증상: "배포했는데 일부 사용자만 옛 응답을 본다."
# 원인: 각 캐시가 제각기 다른 수명을 붙였다.
#       브라우저 A는 3일, 프록시 B는 2시간, CDN C는 안 함.
#       → 재현 불가 · 원인 추적 불가
After 응답의 성격을 명시적으로 선언
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache       축③ 매번 재검증
ETag: "a3f8c2"             재검증에 쓸 검증자
Last-Modified: Mon, 25 Aug 2025 09:00:00 GMT

# 이제 모든 계층이 같은 규칙으로 움직인다.
#  - 저장은 한다 (no-cache 는 저장 금지가 아니다 → 5절)
#  - 쓰기 전에 반드시 물어본다
#  - 안 바뀌었으면 304 → 본문 전송은 여전히 절약
#
# 얻은 것은 성능이 아니라 "예측 가능성"이 먼저다.
모든 응답에 캐시 정책이 명시돼 있어야 한다 — 캐시 헤더를 쓰는 첫 번째 이유는 성능이 아니라 동작을 예측 가능하게 만드는 것

4. Cache-Control은 한 덩어리가 아니라 세 개의 축이다

Cache-Control을 어려워하는 이유는 대부분 지시자를 한 줄에 나열된 평평한 목록으로 외우기 때문이다. public, max-age=3600, must-revalidate를 보면 세 단어가 같은 종류처럼 보인다. 실제로는 서로 다른 세 가지 질문에 답하는, 축이 다른 값들이다. 축이 다르므로 서로 조합된다.

이 세 글자만 외우면 Cache-Control은 끝난다 — 저 · 신 · 재

축① 저장 범위
누가 이 응답을 보관해도 되는가
public · private · no-store
축② 신선도
보관했다면 얼마 동안 안 묻고 써도 되는가
max-age=N · s-maxage=N · immutable
축③ 재검증 강제
쓰기 전에 반드시 물어야 하는가
no-cache · must-revalidate · stale-while-revalidate=N

헤더 하나를 만나면 "이건 저·신·재 중 어느 축인가"부터 묻는다. 세 축의 값을 하나씩 골라 조합한 것이 실무의 헤더다 — public, max-age=0, s-maxage=30은 축①+축②+축②, public, max-age=0, must-revalidate는 축①+축②+축③이다.

4-1. 축별로 하나씩 — 놓치기 쉬운 디테일만

max-age 의 기준 시각
서버 시각이 아니라 "응답을 받은 시점부터의 경과"다. 그래서 서버와 클라이언트의 시계가 어긋나도 안전하다. 옛 Expires: <절대 시각>이 시계 오차에 취약했던 문제를 max-age가 해결한 것이고, 둘 다 있으면 max-age가 이긴다.
s-maxage 의 s
shared(공유)의 s. 이 값이 있으면 공유 캐시는 max-age를 무시하고 이 값을 쓴다. 브라우저와 CDN의 수명을 다르게 주고 싶을 때 쓴다 (→ 10절).
immutable
"이 URL의 내용은 절대 바뀌지 않는다"는 약속. 신선 기간 안에서도 사용자가 새로고침을 누르면 브라우저가 재검증을 시도하는 경우가 있는데, immutable이 붙으면 그 시도조차 생략한다. 해시가 박힌 자원에서 진가를 발휘한다.
must-revalidate 가 진짜로 막는 것
캐시는 만료된 사본을 가진 상태에서 오리진이 죽어 재검증에 실패하면 사정에 따라 오래된 사본을 그대로 내보내는(stale) 선택을 할 수 있다. 가용성엔 고맙지만 재고 수량·잔액처럼 틀린 값을 보이면 안 되는 응답에는 위험하다. must-revalidate는 "확인 못 하면 차라리 오류를 내라"는 선언이다.
반대 방향의 지시자 — stale-while-revalidate=30 가산점 "만료된 뒤 30초 동안은 일단 옛 사본으로 즉시 응답하고, 뒤에서 조용히 재검증하라"는 뜻이다. 사용자는 기다리지 않고, 다음 사람부터 새 응답을 본다. 신선도를 조금 양보해 체감 지연을 없애는 거래다. 그래서 must-revalidate와는 정반대 방향이라 같이 쓰면 의미가 상충한다 — 만료된 사본 제공을 금지하는 쪽이 이기면 stale-while-revalidate의 효과는 사라진다. "낡아도 빠르게"와 "느려도 정확하게" 중 하나를 고르는 자리다.

5. no-cache vs no-store — 이 문서에서 가장 중요한 함정

no-cache가 이 주제에서 이름과 뜻이 가장 크게 어긋나는 지시자다. no-cache는 "캐시하지 마라"가 아니다. 정확한 뜻은 "저장은 해도 좋다. 다만 그 사본을 쓰기 전에는 매번 반드시 서버에 물어봐라"이다. 즉 신선도 단계를 건너뛰고 항상 재검증 단계로 들어가라는 지시다. 그래서 no-cache가 붙은 응답도 304를 받을 수 있고, 내용이 안 바뀌었다면 본문 전송은 여전히 절약된다.

이름이 왜 이렇게 됐는지를 알면 다시는 안 헷갈린다

no-cache의 원래 의미는 "검증 없이는(without validation) 캐시된 것을 쓰지 마라"이고, 저장 자체를 금지하는 쪽에는 no-store라는 별도 이름이 붙었다.

no-store="저장하지 마" | no-cache="확인 없이 쓰지 마"

store = 창고에 넣는 행위, cache = 그것을 꺼내 쓰는 행위로 갈라 읽으면 짝이 맞는다. "캐시하지 마"라는 의도로 no-cache를 쓰면 사본은 여전히 디스크에 남는다 — 이것이 이 질문의 함정이다.

선택 기준은 성능이 아니라 "흔적이 남아도 되는가"다.

함께 붙어 다니는 Pragma와 Expires는 무엇인가 Spring Security가 보호된 응답에 자동으로 붙이는 헤더가 Cache-Control: no-cache, no-store, max-age=0, must-revalidate / Pragma: no-cache / Expires: 0이다. Pragma와 Expires는 Cache-Control을 이해하지 못하는 아주 오래된 캐시를 위한 보험이고, Cache-Control이 있으면 그쪽이 우선한다. 그래서 사고는 대개 이 기본값을 성능 목적으로 직접 덮어썼을 때 난다 (→ 13절).

6. 검증자 — ETag와 Last-Modified가 하는 일

재검증 단계로 넘어가려면 캐시가 서버에게 "내가 가진 게 이건데, 아직 최신인가?"를 물어야 한다. 그러려면 자기가 가진 사본을 가리키는 식별표가 필요하다. 이 식별표를 검증자(validator)라고 부른다. 서버가 응답에 실어 내려보내면 캐시가 그것을 사본과 함께 보관했다가, 다음 요청 때 이름을 바꿔 되돌려 보낸다.

Last-Modified — 마지막 수정 시각

사람이 읽을 수 있어 디버깅에 편하다. 그러나 한계가 둘이다.

  • 초 단위 정밀도. HTTP 날짜 형식이 초까지만 표현하므로 같은 1초 안에 두 번 수정되면 두 버전이 같은 값을 갖는다 → 캐시가 "안 바뀌었다"고 판단해 옛 사본을 계속 쓴다.
  • 내용과 무관하게 값이 변한다. 파일을 열어 아무것도 안 고치고 다시 저장하거나, 배포 과정에서 파일을 새로 복사하면 내용은 그대로인데 수정 시각만 바뀐다 → 불필요한 200 + 본문 전체. 배포할 때마다 안 바뀐 JS·CSS가 전부 다시 내려가는 낭비가 여기서 나온다.

ETag — 이 응답 내용의 지문

entity tag(개체 태그). 보통 본문의 해시값을 쓴다. 내용이 같으면 같은 값, 다르면 다른 값이 되므로 왼쪽의 두 한계를 모두 피한다.

  • 둘 다 있으면 캐시는 ETag 쪽을 우선한다.
  • 그렇다고 Last-Modified를 뺄 이유는 없다 — 휴리스틱 캐싱의 재료가 되고 디버깅에도 쓰인다.
  • 값은 큰따옴표로 감싸는 것이 규격이다. 따옴표를 빼면 일부 캐시가 값을 잘못 해석한다.

6-1. 강한 검증자와 약한 검증자 — W/가 붙는 이유

ETag: "a3f8c2"        # 강한 검증자 — 바이트 단위로 완전히 동일함을 보증한다
ETag: W/"a3f8c2"      # 약한 검증자 — 의미상 같지만 바이트가 동일하다고는 보증하지 않는다

왜 이런 구분이 필요한가. 두 응답이 "같은 콘텐츠"이면서 바이트는 다를 수 있기 때문이다. 같은 JSON을 압축해 보낸 것과 압축 없이 보낸 것은 내용은 같지만 바이트는 완전히 다르다. 응답을 조립하는 과정에서 광고 슬롯이나 타임스탬프처럼 의미 없는 부분만 달라지는 경우도 있다.

이 구분이 실무에서 걸리는 지점 — 이어받기(range request)가 깨진다 큰 파일을 이어받기 할 때 클라이언트는 "이 파일의 5MB 지점부터 주세요"라고 요청한다. 그러려면 서버가 가진 파일이 내가 앞부분을 받아둔 그 파일과 바이트 단위로 완전히 같아야 한다 — 조금이라도 다르면 이어붙인 파일이 깨진다. 그래서 이어받기에 쓰는 If-Range는 강한 검증자만 받아들이고, 약한 ETag밖에 없으면 이어받기가 성립하지 않아 처음부터 다시 받는다.

여기서 응답 압축과 이어진다. 압축 필터가 본문 바이트를 바꾸므로, 압축을 적용하면서 원본의 강한 ETag를 그대로 유지하면 그것은 거짓말이 된다. 그래서 압축 계층을 통과한 응답의 ETag는 약한 검증자로 낮아지거나 아예 제거된다(Nginx는 약한 ETag로 낮춘다). "압축을 켰더니 대용량 파일 이어받기가 안 되더라"는 현상의 정체가 이것이다.

6-2. 검증자와 조건부 요청 헤더는 짝이 정해져 있다

서버가 내려주는 헤더 이름과 클라이언트가 되돌려 보내는 헤더 이름이 다르다. 이 표를 외워두면 네트워크 탭을 읽을 때 헤맬 일이 없다.

7. 304 재검증 왕복을 한 단계씩 — 타임라인

이제 실제 왕복을 따라가 보자. /articles/42를 max-age=60으로 내려주는 API를 예로 든다. 시간축을 따라 네 번 요청이 들어온다.

7-1. 주니어가 자주 놓치는 세 가지

① 304는 "신선도의 연장"이다
단순히 "본문 안 보냄"이 아니라, 응답에 실려 온 Cache-Control로 신선 기간이 다시 시작된다. 위 예에서 t=75의 재검증 이후 t=135까지는 다시 아무것도 묻지 않는다.
② 304에는 본문이 없다
상태 코드 304는 본문을 갖지 않도록 정해져 있다. 서버가 실수로 본문을 붙이면 클라이언트가 응답 경계를 잘못 읽어 깨진다. 프레임워크가 알아서 처리하지만, 직접 응답을 조립하는 필터를 짤 때는 주의해야 한다.
③ 애플리케이션 코드는 304를 못 본다
재검증은 캐시와 서버 사이에서 일어나고, 브라우저의 자바스크립트에는 캐시가 200으로 되돌려준다. "네트워크 탭에는 304인데 코드에는 정상 데이터가 들어온다"는 상황이 정상이다.
그래서 304 응답에 어떤 헤더를 실어야 하는가 가산점 캐시는 304에 실려 온 헤더로 저장된 헤더를 갱신한다. 그러므로 Cache-Control·ETag·Vary처럼 "저장된 사본의 메타데이터를 갱신할 헤더"는 304에도 넣어야 한다. 특히 Cache-Control을 빠뜨리면 신선도 연장이 안 되어 다음 요청에서 또 재검증이 일어난다. 반대로 Content-Length·Content-Type 같은 본문에 관한 헤더는 보낼 본문이 없으므로 의미가 없다.

8. Spring 구현 — 어느 층위가 무엇을 아끼는가

Spring MVC에서 캐시 헤더를 내려주는 방법은 다섯 층위가 있고, 각 층위가 아끼는 비용이 다르다는 점이 핵심이다. 여기를 정확히 말할 수 있으면 "ETag를 붙여봤다"와 "ETag가 무엇을 아끼는지 안다"가 갈린다.

8-1. ① 개별 응답에 직접 선언 — ResponseEntity

@GetMapping("/articles/{id}")
public ResponseEntity<ArticleDto> get(@PathVariable Long id) {
    Article article = articleService.find(id);

    return ResponseEntity.ok()
            // CacheControl 은 4절의 세 축을 메서드 체인으로 조립하는 빌더다.
            // maxAge(축②) + cachePublic(축①) 조합.
            .cacheControl(CacheControl.maxAge(Duration.ofMinutes(5)).cachePublic())
            // ETag 값은 큰따옴표로 감싸는 것이 규격이다. 따옴표를 빼면
            // 일부 캐시가 값을 잘못 해석한다.
            .eTag("\"" + article.contentHash() + "\"")
            .body(ArticleDto.from(article));
}

이 코드는 응답을 전부 만든 뒤에 헤더를 붙인다. 그래서 다음 요청에서 304가 나가더라도 DB 조회와 DTO 변환은 그대로 일어난다. 아끼는 것은 전송량뿐이다.

8-2. ② 서버 연산까지 아끼는 방식 — checkNotModified

진짜 이득은 본문을 만들기 전에 304 여부를 판정할 때 나온다. 리소스에 수정 시각이나 버전 컬럼이 있으면 그것만 가볍게 조회해 검증자를 만들 수 있다.

Before 본문을 다 만든 뒤 ETag 계산 — 전송량만 절약
@GetMapping("/articles/{id}")
public ResponseEntity<ArticleDto> before(@PathVariable Long id) {

    Article article = articleService.findWithComments(id);
    // ↑ 무거운 조회가 "항상" 실행된다

    String etag = "\"" + DigestUtils.md5Hex(toJson(article)) + "\"";
    // ↑ 직렬화까지 끝낸 뒤에 해시한다

    return ResponseEntity.ok().eTag(etag)
                         .body(ArticleDto.from(article));
}

// 304가 나가도 아낀 것: 네트워크 바이트
// 그대로 낸 것:        DB 조회 + 직렬화 + CPU
After 검증자를 먼저 얻어 판정 — 서버 연산까지 절약
@GetMapping("/articles/{id}")
public ResponseEntity<ArticleDto> after(@PathVariable Long id,
                                        WebRequest webRequest) {

    long version = articleService.findVersion(id);   // 인덱스 1행
    String etag = "\"v" + version + "\"";

    // 요청의 If-None-Match 와 비교 → 같으면 응답에 304를
    // 세팅하고 true 를 반환한다.
    if (webRequest.checkNotModified(etag)) {
        return null;   // 세팅된 304 를 그대로 내보낸다
    }

    Article article = articleService.findWithComments(id);
    // ↑ 정말 필요할 때만 실행
    return ResponseEntity.ok().eTag(etag)
                         .body(ArticleDto.from(article));
}
ETag의 진짜 값은 전송량이 아니라 본문 생성을 건너뛰는 지점에 있다

8-3. ③ 전체 응답에 일괄 적용 — ShallowEtagHeaderFilter와 그 한계

@Bean
public FilterRegistrationBean<ShallowEtagHeaderFilter> shallowEtagFilter() {
    var registration = new FilterRegistrationBean<>(new ShallowEtagHeaderFilter());
    registration.addUrlPatterns("/api/reports/*");   // 적용 범위를 좁게 잡는 것이 중요하다
    return registration;
}

동작은 이렇다. 필터가 응답 본문을 메모리 버퍼에 전부 받아 해시를 계산하고, 요청의 If-None-Match와 같으면 본문을 버리고 304만 내보낸다. 여기서 한계 셋이 나온다.

① 서버 연산을 전혀 못 아낀다
컨트롤러와 서비스는 이미 다 실행됐다. 절약되는 것은 네트워크 바이트뿐 — "얕은(shallow)"의 뜻이 이것이다.
② 응답 전체를 버퍼링한다
큰 응답이나 파일 다운로드 경로에 걸면 힙을 그대로 먹는다.
③ 스트리밍과 충돌한다
SSE처럼 조금씩 흘려보내는 응답은 본문이 끝나야 해시를 낼 수 있으므로 버퍼링이 스트리밍을 깨뜨린다. 응답 압축의 버퍼링 문제와 뿌리가 같다.

8-4. ④ 경로 패턴별 일괄 정책 — WebContentInterceptor

@Configuration
public class CachePolicyConfig implements WebMvcConfigurer {

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        WebContentInterceptor interceptor = new WebContentInterceptor();

        // 기본값을 안전한 쪽으로 깐다. 명시적으로 완화한 경로만 캐시되게 하는
        // allowlist 방식이 개인화 응답 유출(13절)의 1차 방어선이다.
        interceptor.addCacheMapping(CacheControl.noStore(), "/**");

        // 공개 카탈로그처럼 누구에게나 같은 응답만 골라 공유 캐시를 허용한다.
        interceptor.addCacheMapping(
                CacheControl.maxAge(Duration.ofMinutes(5)).cachePublic(),
                "/api/public/**");

        registry.addInterceptor(interceptor);
    }
}

  web:
    resources:

chain.strategy.content는 12절에서 설명할 파일명 해시 전략을 서버 쪽에서 구현한 것이다. app.js를 요청하면 내용 해시가 들어간 app-a1b2c3.js 경로로 서빙되고, 템플릿의 링크도 그 경로로 치환된다.

9. 다중 인스턴스에서 ETag가 갈리는 함정 시니어 변별

실제로 겪기 전에는 상상하기 어려운 실무 함정이다. 서버를 여러 대로 늘렸더니 304가 사라지고 항상 200이 나가는 현상이 있다.

원인은 ETag를 만드는 재료에 있다. 웹서버가 정적 파일의 ETag를 자동 생성할 때, 파일 내용을 해시하는 대신 파일 메타데이터를 조합하는 구현이 있다. 대표적으로 아파치 계열의 전통적 기본값은 파일의 inode 번호(파일 시스템이 파일에 붙이는 내부 일련번호), 수정 시각, 크기를 조합한다. inode 번호는 파일 시스템마다 다르게 붙는 값이라, 같은 내용의 파일이라도 서버 A와 서버 B에서 다르다.

대응 — ETag의 재료를 "서버에 종속되지 않는 것"으로 바꾼다

정적 파일
내용 해시. 같은 내용이면 어느 서버에서 계산해도 같은 값. 빌드 시점에 계산해 파일명이나 매니페스트에 박아두면 런타임 계산 비용도 없다.
API 응답
리소스의 버전 컬럼이나 수정 시각. DB에 있는 값이므로 모든 인스턴스가 같은 값을 본다. 8-2의 checkNotModified와 그대로 맞물린다.
웹서버 설정
inode 기반 생성을 쓰는 웹서버라면 그 설정을 끄거나 재료에서 inode를 뺀다.

10. CDN — 새로운 제어 체계가 아니라 계층이 하나 더

캐시 관점에서 CDN을 이해하는 요령은 하나다. CDN은 새로운 제어 체계가 아니라 1절에서 정의한 공유 캐시의 한 종류다. 지금까지 본 헤더 계약이 그대로 적용된다. 달라지는 것은 계층이 하나 더 생긴다는 점이고, 그 결과 재검증도 두 군데서 각각 일어난다.

이 조합이 값을 하는 자리 — 요청 병합(request coalescing) 트래픽이 몰리는 목록 API에서 초당 1만 건이 들어와도 오리진이 실제로 처리하는 것은 60초에 한 번뿐이다. 이렇게 다수의 동시 요청을 캐시가 한 건으로 접어 오리진에 전달하는 성질을 요청 병합이라 하고, 대부분의 CDN·리버스 프록시가 지원한다. 오리진 보호 관점에서는 캐시 히트율보다 이쪽이 더 중요할 때가 많다.
Age
공유 캐시가 붙이는 "이 응답이 캐시에 들어온 지 몇 초 됐는가". Age: 42이고 s-maxage=60이면 앞으로 18초 더 엣지에서 응답한다는 뜻이다. 운영 중 캐시가 실제로 먹고 있는지 확인하는 가장 빠른 방법. 업체별 진단 헤더(X-Cache: HIT/MISS 형태가 흔하다)를 함께 보면 어느 계층에서 응답했는지 판별된다.
CDN-Cache-Control
표준 Cache-Control 하나로 브라우저와 CDN을 동시에 조종하기 어려울 때를 위해 CDN에만 적용되는 별도 캐시 제어 필드가 표준화돼 있다. 이 필드가 있으면 CDN은 그것을 따르고 Cache-Control은 브라우저용으로만 남는다. 업체별 전용 헤더를 쓰기 전에 이런 표준이 있다는 것 정도는 알아두면 좋다.

무효화 전략(버전드 URL과 purge의 선택), 오리진 실드, 이미지 리사이징 같은 CDN 아키텍처 자체는 07-traffic-performance/05-cdn-webtoon-image-serving에서 다룬다. 이 문서의 초점은 그 CDN을 조종하는 헤더가 어떻게 동작하는가다.

11. Vary — 캐시 키를 확장하는 헤더

캐시는 저장한 사본을 키로 찾는다. 기본 키는 요청 메서드와 URL이다. 그런데 같은 URL인데 응답이 달라져야 하는 경우가 있다. 가장 흔한 예가 압축이다 — 같은 /api/articles라도 Accept-Encoding: gzip을 보낸 클라이언트에게는 압축된 바이트를, 지원하지 않는 클라이언트에게는 원본 바이트를 줘야 한다. 캐시가 URL만으로 키를 만들면 이 둘이 한 칸에 섞인다.

Vary는 서버가 캐시에게 "이 응답은 URL만으로 식별하지 마라. 다음 요청 헤더 값도 키에 포함시켜라"라고 알려주는 헤더다. 이름 그대로 "이 헤더에 따라 응답이 달라진다(vary)"는 선언이다.

Vary에 넣어도 되는 헤더의 판단 기준 — 한 문장

값의 가짓수가 적고, 응답에 실제로 영향을 주는 헤더만 넣는다

그리고 개인화 응답을 지키려고 Vary: Cookie를 붙이는 발상은 방향은 맞지만 도구가 틀렸다. 안전은 얻지만 캐시를 끈 것과 같아진다. 개인화 응답은 Vary로 쪼개는 게 아니라 private/no-store로 공유 캐시에서 아예 빼는 것이 정답이다 (→ 13절).

12. "배포했는데 사용자가 옛 화면을 봅니다" — 불변 자산 전략

이 주제의 실무적 결론이다. 이 현상의 근본 원인은 하나로 압축된다 — "같은 URL의 내용이 바뀌는 것".

/static/app.js에 max-age=86400(하루)을 걸었다면, 오늘 배포한 새 코드는 어제 이 파일을 받아간 사용자에게 내일까지 도달하지 못한다. 브라우저 캐시는 서버가 원격으로 지울 수 없기 때문이다. CDN은 purge로 지울 수 있지만 브라우저는 방법이 없다. 그렇다고 max-age를 짧게 잡으면 캐시의 이득이 사라진다. 이 딜레마를 문제 자체를 없애는 방식으로 푸는 것이 불변 자산 전략이다.

핵심 아이디어 — 내용이 바뀌면 URL도 바뀌게 만든다. 그러면 "같은 URL의 내용이 바뀌는 상황"이 원천적으로 발생하지 않는다

외워둘 두 줄과, 숫자 하나의 검산

대상캐시 헤더이유
파일명에 해시가 박힌 JS/CSS/이미지public, max-age=31536000, immutableURL이 곧 버전이므로 무한정 캐시해도 안전
진입점 HTMLno-cache항상 최신 파일명을 가리켜야 한다. 안 바뀌었으면 304로 싸게 끝난다

max-age=31536000이 왜 1년인지 직접 검산해 두자. 1분 = 60초 → 1시간 = 60 × 60 = 3,600초 → 하루 = 3,600 × 24 = 86,400초 → 1년(365일) = 86,400 × 365 = 31,536,000초. 표준이 권장하는 실질적 상한이 1년이라 이 숫자가 관용적으로 쓰인다.

빌드 도구가 이 파일명을 만들어 주고(대부분의 프론트엔드 번들러가 기본 지원한다), 서버 렌더링을 쓴다면 8-5의 chain.strategy.content 설정으로 같은 일을 할 수 있다. Nginx로 직접 서빙한다면 경로 패턴으로 두 정책을 나눠 준다.

# 파일명에 해시가 박힌 빌드 산출물 — 내용이 바뀌면 이름이 바뀌므로 1년 캐시
location ~* "^/static/.+\.[0-9a-f]{6,}\.(js|css|woff2)$" {
    root /var/www;
    add_header Cache-Control "public, max-age=31536000, immutable";
}

# 진입점 HTML — 항상 확인시킨다. 안 바뀌었으면 Nginx가 304로 끝낸다.
location = /index.html {
    root /var/www;
    add_header Cache-Control "no-cache";
}

13. 개인화 응답이 공유 캐시에 남는 사고 시니어 변별

이제 캐시의 어두운 면이다. 지금까지 본 모든 성능 이득은 "같은 URL에는 같은 응답"이라는 전제 위에 서 있다. 로그인 사용자마다 다른 응답을 주는 API에서는 이 전제가 깨지고, 그때 public 한 단어가 정보 유출이 된다.

13-1. 방어는 한 겹으로 하지 않는다

1
애플리케이션 기본값을 안전한 쪽으로 깐다. 인증이 필요한 응답의 기본 캐시 정책을 no-store(최소한 private)로 강제하고, 캐시를 허용할 경로만 명시적으로 완화하는 allowlist 방식으로 만든다. 8-4의 WebContentInterceptor가 정확히 이 구조다.
여기서 알아둘 것 — Spring Security는 이미 이 방어를 기본으로 하고 있다. 보호된 요청의 응답에 Cache-Control: no-cache, no-store, max-age=0, must-revalidate / Pragma: no-cache / Expires: 0을 자동으로 붙인다. 사고는 대개 이 기본값을 성능 목적으로 직접 덮어썼을 때 난다.
2
CDN 쪽에도 같은 규칙을 건다. Authorization 헤더나 세션 쿠키가 붙은 요청은 캐시하지 않도록 설정한다. 애플리케이션 실수가 그대로 유출로 이어지지 않게 막는 두 번째 그물이다.
3
캐시 대상 경로를 명시적으로 관리한다. "전부 캐시하고 예외를 뺀다"가 아니라 "아무것도 캐시하지 않고 허용 경로만 연다"로 방향을 뒤집는다. 전자는 새 엔드포인트가 추가될 때마다 사고 가능성이 생기지만, 후자는 새 엔드포인트가 기본적으로 안전하다.
4
개인화된 부분과 공용 부분을 URL로 분리한다 — 근본 처방. /api/articles/42(누구에게나 같음, public 캐시)와 /api/articles/42/my-status(내 좋아요·구독 여부, private)를 나누면, 무거운 공용 응답은 캐시로 흡수하고 개인화 부분만 매번 오리진이 처리한다. 캐시 히트율과 안전성을 동시에 얻는 유일한 방향이다.

15-2. 꼬리질문 — 먼저 스스로 답한 뒤 펼친다

no-cache와 no-store의 차이는 뭔가요? 필수힌트: "저장"과 "사용"을 분리해 말하고, 마지막에 고르는 기준 한 문장을 얹는다

no-cache는 저장을 허용한다. 다만 그 사본을 사용하기 전에 매번 서버에 재검증을 요청하도록 강제한다. 신선도 단계를 통째로 건너뛰고 항상 재검증 단계로 들어가는 것이다. 그래서 내용이 안 바뀌었으면 304가 나가고 본문 전송은 절약된다 — 왕복은 매번 내고 본문은 아끼는 모드다.

no-store는 저장 자체를 금지한다. 사본이 없으니 재검증도 304도 없고, 매 요청이 전부 오리진까지 가서 전체 응답을 받아온다. 대신 디스크에 흔적이 남지 않는다.

고르는 기준은 성능이 아니라 "흔적이 남아도 되는가"

성능 목적으로 "항상 최신을 보여주고 싶다"면 no-cache가 맞다. 결제 정보나 개인정보처럼 공용 PC의 디스크 캐시에 남는 것 자체가 위험하다면 no-store여야 한다. "캐시하지 마"라는 의도로 no-cache를 쓰면 사본은 여전히 디스크에 남는다는 것이 이 질문의 함정이다.

304를 받는데도 페이지가 느립니다. 왜죠? 함정힌트: "304는 무엇을 아끼고 무엇을 안 아끼는가"로 답을 시작한다

304는 본문 전송(대역폭)만 아낄 뿐 왕복 자체는 그대로 발생하기 때문이다. 2절의 비용 사다리에서 304는 가운데 칸이지 맨 위 칸이 아니다.

리소스가 40개인 페이지에서 전부 304가 나오면 재검증 왕복도 40번 일어난다. 모바일 회선처럼 왕복 시간이 큰 환경에서는 이것만으로 수백 밀리초가 쌓인다. 게다가 응답 본문이 작은 리소스일수록 본문 전송보다 왕복 비용이 지배적이라 304의 이득 자체도 작다.

처방은 재검증 단계를 최적화하는 것이 아니라 신선도 단계로 올리는 것이다. 파일명에 내용 해시를 박아 URL을 불변으로 만들고 max-age=31536000, immutable을 걸면 재검증 요청 자체가 사라져 왕복이 0이 된다.

정리하면 304는 "URL을 바꿀 수 없는데 갱신 가능성은 있는" 리소스의 차선책이지, 정적 자원의 1차 전략이 아니다. HTML 진입점처럼 URL을 고정해야만 하는 대상에 쓰는 것이다.

개인화 응답에 캐시 헤더를 잘못 주면 어떤 사고가 나나요? 시니어 변별힌트: 사고의 "성질" 세 가지를 짚고, 방어를 네 겹으로 나눠 말한다

/api/me 같은 응답에 Cache-Control: public이 나가면 CDN이 그 응답을 저장했다가 다음에 오는 다른 사용자에게 그대로 서빙한다. A의 이름·전화번호가 B의 화면에 뜨는 정보 유출이다.

① 인증 로직은 정상이었다. B는 자기 세션으로 정상 로그인했고 서버 코드도 멀쩡하다. 요청이 서버에 도달조차 하지 않았을 뿐이다. 캐시는 인증 계층보다 앞에 있으므로, 캐시 헤더는 성능 설정이 아니라 접근 제어의 일부다.

② 서버 재배포로 복구되지 않는다. 잘못된 사본이 이미 엣지에 있으므로, 코드 수정 배포와 해당 경로 purge가 반드시 짝으로 가야 한다.

③ 피해 규모가 트래픽에 비례한다. 캐시 히트가 많은 인기 엔드포인트일수록 더 많은 사람에게 남의 정보가 나간다.

방어는 다층으로. ① 인증이 필요한 응답의 기본값을 private(민감하면 no-store)으로 강제 — Spring Security가 기본으로 하는 일이므로 그것을 임의로 덮어쓰지 않는 것부터가 방어다. ② CDN 쪽에서도 Authorization·세션 쿠키가 붙은 요청은 캐시하지 않는 설정. ③ 캐시 대상 경로를 allowlist로 관리해 새 엔드포인트가 기본적으로 안전하게. ④ 근본적으로는 공용 데이터와 개인화 데이터를 다른 URL로 분리.

Vary: Cookie로 막으려는 발상은 방향은 맞지만 도구가 틀렸다. 쿠키 값이 사람마다 다르므로 캐시가 사용자 수만큼 쪼개져 히트율이 0에 수렴한다 — 안전은 얻지만 캐시를 끈 것과 같아진다. 개인화 응답은 키를 쪼개는 게 아니라 공유 캐시에서 빼는 것이 정답이다.

ETag는 어떻게 생성하는 게 좋나요? API 응답에도 쓸 수 있나요? 필수힌트: 정적/API를 나누고, API는 "어디서 판정하느냐"에 따라 이득의 종류가 달라진다는 축으로 답한다

정적 파일은 내용 해시가 정석이다. 이유는 다중 인스턴스 때문이다. inode나 파일 수정 시각처럼 서버에 종속된 값을 재료로 쓰면 서버마다 다른 ETag가 나와 재검증이 항상 실패하고, 서버 대수를 늘릴수록 캐시 적중률이 구조적으로 무너진다. 내용 해시는 어느 서버에서 계산해도 같은 값이라 이 문제가 없다.

API 응답에도 쓸 수 있지만, 어떻게 만드느냐에 따라 이득의 종류가 달라진다. 본문을 직렬화한 뒤 해시하는 방식(Spring의 ShallowEtagHeaderFilter)은 컨트롤러와 서비스가 이미 다 실행된 뒤이므로 서버 연산은 하나도 아끼지 못한다. 절약되는 것은 네트워크 바이트뿐이고, 응답 전체를 메모리에 버퍼링하는 비용까지 새로 든다.

진짜 이득은 본문을 만들기 전에 판정할 때 나온다. 리소스에 수정 시각이나 버전 컬럼이 있으면 그 값만 가볍게 조회해 ETag를 만들고, WebRequest.checkNotModified(etag)로 304 여부를 먼저 판정한 뒤 필요할 때만 무거운 조회와 직렬화를 실행한다. 이러면 전송량뿐 아니라 DB 부하와 CPU까지 아낀다.

한 걸음 더 — 같은 ETag를 낙관적 동시성 제어에 재사용할 수 있다 가산점. 클라이언트가 조회할 때 받은 ETag를 수정 요청의 If-Match에 실어 보내게 하면, 서버는 "네가 읽었던 그 버전이 아직 그대로일 때만" 수정을 허용하고 아니면 412 Precondition Failed를 준다. 다른 사람이 그 사이 고친 것을 덮어쓰는 lost update를 HTTP 계층에서 막는 것이다. 읽기 캐시 효율과 쓰기 충돌 감지가 같은 값 하나로 해결된다.

배포 직후 사용자들이 옛 화면을 봅니다. 캐시 관점에서 원인은? 필수힌트: 계층별로 ①HTML ②CDN ③브라우저 순서로 짚어 내려간다. 결론은 "사후 대응보다 설계"

① 진입점 HTML에 긴 max-age가 걸려 있는 경우 — 가장 흔한 원인. 브라우저가 어느 JS를 받을지는 HTML의 링크가 정하는데, HTML 자체가 캐시돼 있으면 여전히 옛 파일명을 가리킨다. 새 자원을 아무리 잘 배포해도 아무도 그것을 요청하지 않는다. 정석은 HTML은 no-cache, 그 HTML이 참조하는 JS/CSS는 파일명에 내용 해시 + max-age=31536000, immutable.

② CDN 엣지에 옛 사본이 남아 있는 경우. s-maxage가 아직 안 지났으면 엣지가 옛 응답을 계속 준다. 배포 파이프라인에 해당 경로의 purge를 포함시켜야 한다. Age 헤더로 엣지 사본의 나이를 확인하면 진단이 빠르다.

③ 이미 브라우저에 저장된 캐시는 서버가 원격으로 지울 수 없다 — 이것이 결론이다. CDN은 purge할 수 있지만 사용자 브라우저 디스크에 들어간 사본은 만료될 때까지 손댈 방법이 없다. 그래서 사후 대응보다 설계가 중요하다 — "오래 캐시할 것은 URL에 버전을 박는다"는 원칙을 지키면 이 문제 자체가 발생하지 않는다. 긴 max-age를 거는 순간 그 기간만큼의 되돌릴 수 없는 약속을 한다는 것을 알고 걸어야 한다.

덧붙여, 이미 사고가 난 상태에서 URL을 바꿀 수 없다면 쿼리 문자열을 붙여(?v=2) 새 URL로 만드는 임시 대응이 가능하지만, 이것은 응급처치이지 설계가 아니다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

max-age=0과 no-cache는 결국 같은 것 아닌가요?힌트: "효과가 거의 같다"에서 멈추지 말고, 어느 축의 지시자인지로 갈라 답한다

효과는 대부분 같지만 축이 다르고, 그래서 보장의 성격이 다르다. max-age=0은 신선도 축(②)의 값으로 "받자마자 만료됐다"는 선언이고, no-cache는 재검증 강제 축(③)의 값으로 "쓰기 전에 반드시 확인하라"는 선언이다.

차이가 드러나는 지점은 만료된 사본(stale)을 예외적으로 쓰는 상황이다. max-age=0만 있으면 사본은 "만료된 응답"이 되는데, 캐시는 사정에 따라(오리진 장애 등) 만료된 응답을 그대로 내보내는 선택을 할 수 있다. no-cache는 사용 전 재검증을 명시적으로 요구하므로 그 여지를 남기지 않는다.

확실히 하고 싶으면 의도대로 쓴다 — "항상 확인시켜라"면 no-cache, 굳이 신선도 축으로 표현하려면 max-age=0, must-revalidate처럼 ③번 축의 지시자를 함께 붙인다. 실무에서 public, max-age=0, s-maxage=30처럼 쓰는 것은 "브라우저는 확인, CDN은 30초"라는 두 계층 분리가 목적이지 no-cache의 대체가 아니다.

브라우저의 "새로고침"과 "강력 새로고침"은 캐시 동작이 어떻게 다른가요?힌트: 요청 쪽에도 Cache-Control이 있다는 사실이 답의 열쇠다

Cache-Control은 응답 전용 헤더가 아니다 — 요청에도 붙는다. 이 사실을 알면 세 동작이 한 줄로 정리된다.

① 링크 이동·주소창 입력: 일반 캐시 규칙이 그대로 적용된다. 신선하면 요청 자체가 나가지 않는다.
② 일반 새로고침(F5): 브라우저가 대체로 조건부 요청을 보내 재검증한다. 신선 기간이 남았어도 확인하러 가는 것이다 — 그래서 "새로고침하면 되는데요?"라는 말이 사용자 문제를 대변하지 못한다.
③ 강력 새로고침(Ctrl/Cmd+Shift+R): 요청에 Cache-Control: no-cache를 붙여 캐시를 우회하고 오리진에서 다시 받는다.

여기서 immutable의 존재 이유가 나온다. ②의 재검증 시도조차 불필요한 왕복이므로, "이 URL은 절대 안 바뀐다"고 선언해 그 시도까지 생략시키는 것이다.

디버깅에 쓸 팁 — 개발자 도구의 "Disable cache"는 요청에 캐시 우회 헤더를 붙이는 것이므로, 그 상태로 본 네트워크 탭은 실제 사용자의 캐시 동작이 아니다. 캐시 정책을 검증할 때는 반드시 꺼놓고 봐야 한다.

응답 압축(gzip)을 켰더니 대용량 파일 이어받기가 깨졌습니다. 캐싱 헤더와 무슨 관계인가요? 시니어 변별힌트: 강한 검증자와 약한 검증자, 그리고 If-Range

압축 필터가 본문 바이트를 바꾸기 때문이다. 강한 ETag는 바이트 단위로 완전히 동일함을 보증하는 값인데, 압축된 응답에 원본의 강한 ETag를 그대로 붙이면 그것은 거짓말이 된다. 그래서 압축 계층을 통과한 응답의 ETag는 약한 검증자(W/)로 낮아지거나 제거된다(Nginx는 약한 ETag로 낮춘다).

이어받기에 쓰는 If-Range는 강한 검증자만 받아들인다. 앞부분을 받아둔 파일과 서버의 파일이 바이트 단위로 같아야 이어붙인 결과가 온전하기 때문이다. 그래서 약한 ETag밖에 없으면 이어받기가 성립하지 않고 처음부터 다시 받는다.

처방은 "압축 대상에서 빼는 것"이다. 대용량 바이너리·이미 압축된 포맷(zip, jpg, mp4)은 압축해도 이득이 거의 없으므로 압축 대상에서 제외하면 강한 ETag가 유지되고 이어받기도 살아난다. 함께 기억할 것 — 압축을 쓰는 순간 Vary: Accept-Encoding은 선택이 아니라 필수다(11절).

CDN 히트율은 높은데 오리진 부하가 안 줄었습니다. 어디를 봐야 하나요?힌트: 캐시 "키"가 몇 개로 쪼개졌는지, 그리고 Age를 본다

먼저 캐시 키가 쪼개졌는지 본다. Vary에 Cookie·User-Agent처럼 값의 가짓수가 큰 헤더가 들어가 있으면 사본이 사용자 수만큼 만들어져 전체 히트율 숫자와 무관하게 오리진 요청이 줄지 않는다. CDN 설정에서 쿼리 문자열 전체를 키에 포함하는 경우도 같다 — 추적용 파라미터(?utm_source=...)가 붙으면 같은 콘텐츠가 서로 다른 칸에 저장된다. 키에서 무의미한 파라미터를 제거하는 것이 즉효 처방이다.

다음으로 Age와 s-maxage를 확인한다. Age가 항상 작은 값이면 사본이 금방 만료되고 있다는 뜻이다. s-maxage가 없어서 max-age를 짧게 잡은 값이 CDN에도 그대로 적용되고 있는 경우가 흔하다 — 브라우저는 짧게, CDN은 길게로 분리한다(10절).

마지막으로 "히트"의 정의를 확인한다. 재검증 요청도 히트로 집계되는 경우가 있는데, 그때는 본문 전송은 줄어도 오리진은 매번 요청을 받는다. 오리진 보호 관점의 지표는 히트율이 아니라 "오리진에 도달한 요청 수(origin offload)"다.

POST 응답도 캐시되나요? GET이 아닌 메서드는 어떻게 다루나요?힌트: "안 된다"가 아니라 "사실상 안 된다"이고, 그 이유가 캐시 키에 있다

기본적으로 캐시되지 않는다고 보면 된다. 명세상으로는 명시적 신선도 정보가 있으면 POST 응답도 캐시될 여지가 있지만, 실무의 대부분 캐시 구현은 이를 지원하지 않는다. 캐시 키가 메서드 + URL이고 POST는 본문에 따라 응답이 달라지는데 본문은 키에 들어가지 않기 때문이다.

그래서 "조회인데 파라미터가 많아서 POST로 만들었다"는 설계는 캐시를 통째로 포기하는 선택이 된다. 조회는 GET으로 두고 파라미터를 쿼리 문자열에 담는 편이 캐시·재시도·로그·북마크 모두에 유리하다.

반대 방향도 알아두자. POST·PUT·DELETE 같은 변경 메서드가 성공하면, 그 URL에 대해 캐시가 갖고 있던 사본은 무효화되도록 규정돼 있다. 다만 이는 같은 URL에 대해서만이고, 연관된 목록 URL(/articles)까지 알아서 지워주지는 않는다 — 목록 캐시의 갱신은 s-maxage를 짧게 두거나 purge로 직접 처리해야 한다.

Redis 캐싱과 HTTP 캐싱은 언제 각각 쓰나요? 둘 다 쓰면 중복 아닌가요?힌트: "무엇을 아끼는가"의 위치가 다르다 — 계층 그림으로 답한다

아끼는 지점이 다르다. HTTP 캐시는 요청이 우리 서버에 도달하는 것 자체를 막고(왕복·대역폭·서버 진입 전부 절약), Redis 캐시는 이미 도달한 요청 안에서 DB 조회를 막는다(DB 부하만 절약). 바깥쪽에서 막을수록 싸다는 원칙이 그대로 적용되므로, 둘은 대체재가 아니라 바깥부터 안쪽으로 쌓는 층이다.

따라서 판단 기준도 다르다. HTTP 캐시는 "모든 사용자에게 같은 응답인가"가 조건이고 무효화를 우리가 통제하기 어렵다(브라우저 사본은 못 지운다). Redis는 사용자별 데이터도 담을 수 있고 우리가 원할 때 즉시 삭제할 수 있다.

실무 조합은 이렇게 나온다 — 공개 목록 API에 public, max-age=0, s-maxage=30을 걸어 CDN이 30초의 트래픽을 흡수하고, 그래도 30초에 한 번 오는 오리진 요청은 Redis 캐시가 DB 조회 없이 처리한다. 개인화 응답은 HTTP 계층에서 private으로 빼고 Redis로만 가속한다.

한 줄 요약
HTTP 캐싱은 Cache-Control이 정하는 "묻지 않는 기간"(신선도)과 ETag/Last-Modified 재검증이 만드는 "본문 없는 304"의 2단계 구조이고, Cache-Control은 저장 범위·신선도·재검증 강제라는 서로 다른 세 축의 조합이며(no-cache는 "저장 금지"가 아니라 "쓰기 전에 반드시 물어라"), 브라우저와 CDN은 모두 이 헤더 계약을 실행하는 대리인일 뿐이다 — 그래서 정적 자원은 파일명에 내용 해시를 박아 URL을 불변으로 만든 뒤 max-age=31536000, immutable로 왕복을 0으로 없애고 HTML만 no-cache로 두는 것이 정답이며, 동시에 public 한 단어가 개인화 응답을 공유 캐시에 남기는 유출 사고의 경계선이 된다는 점에서 캐시 헤더는 성능 설정이자 접근 제어의 일부다.
