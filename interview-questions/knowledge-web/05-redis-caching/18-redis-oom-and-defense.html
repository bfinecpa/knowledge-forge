Redis 메모리 포화(OOM)
가득 차면 무슨 일이 벌어지고, 어떻게 막는가

면접 질문: "Redis 메모리가 가득 찼을 때(OOM) 서비스에 어떤 일이 벌어지나요? 사전 방어책은?"

핵심 관전 포인트 — 가득 찼을 때 벌어지는 일은 설정이 결정한다. noeviction이면 메모리를 더 쓰는 명령만 골라 에러로 실패하고 읽기는 멀쩡한 반쪽 장애가 되고, eviction 정책이면 기존 키를 지워 자리를 만드는데 세션·락·발급 카운터처럼 "지워지면 안 되는 데이터"가 섞여 있으면 에러 한 줄 없는 조용한 유실이 된다. maxmemory를 아예 안 잡으면 더 나쁘다 — 스왑으로 지연이 폭발하거나(싱글 스레드라 한 명령의 디스크 대기가 뒤에 줄 선 전부의 지연이 된다) 커널의 OOM killer가 프로세스를 통째로 죽인다. 게다가 maxmemory 안에서도 터진다 — fork의 copy-on-write·클라이언트 버퍼·복제 버퍼·단편화가 데이터 바깥에서 메모리를 더 먹기 때문이다. 그래서 방어는 사후가 아니라 사전이다.
  • 1
    증상은 설정이 정한다 — noeviction은 쓰기만 실패하는 반쪽 장애(로그인 불가), eviction 정책은 에러 없는 조용한 유실(무작위 로그아웃), maxmemory 미설정은 스왑·OOM killer로 인스턴스 통째 사망이다.
  • 2
    maxmemory 안에서도 터진다 — 그 값이 통제하는 것은 데이터에 쓰는 몫뿐이고, fork CoW·클라이언트 버퍼·복제 버퍼·단편화가 그 바깥에서 물리 메모리를 밀어낸다. 그래서 물리보다 충분히 낮게 잡는다.
  • 3
    방어는 네 겹 — 용도별 인스턴스 분리, 전 키 TTL 규율, 사용률·evicted_keys·단편화 비율 알람, 캐시 실패를 삼키는 애플리케이션 코드. 목록이 아니라 "사고의 어느 단계를 어느 방어선이 끊는가"로 말한다.

0. 질문 + 출제 의도

질문: "Redis 메모리가 가득 찼을 때(OOM) 서비스에 어떤 일이 벌어지나요? 사전 방어책은?"

출제 의도: "캐시가 죽으면 서비스가 어떻게 되는가"를 미리 그려보고 방어(메모리 알람, eviction 정책, 키 TTL 규율)를 깔아두는 운영 성숙도를 확인한다. 증상 나열이 아니라 "우리 설정에서는 이렇게 되고, 그래서 이런 방어를 깔아뒀다"는 구체적인 시나리오를 그릴 수 있는지 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "메모리가 차면 에러가 난다"는 뭉뚱그린 답 → 1~4절에서 설정에 따라 갈리는 세 갈래로 쪼갠다. 갈래마다 누가 판단하고, 프로세스가 사는지, 데이터가 남는지가 전부 다르다.
② maxmemory만 잡으면 안전하다는 착각 → 5절에서 데이터 바깥에서 메모리를 먹는 네 가지를 도식으로 분리한다.
③ 방어책을 목록으로 나열하는 답 → 10절에서 실제 사고 타임라인 위에 네 방어선이 각각 어느 단계를 끊는지 매핑한다.

1. 전제 — 같은 "가득 참"이 세 갈래로 갈린다

같은 메모리 포화라도 결과가 완전히 달라진다. 그 결과를 정하는 설정이 두 개다.

maxmemory
Redis가 스스로에게 거는 상한선. "데이터가 이만큼을 넘으면 더 자라지 않겠다"고 자기 자신에게 선언하는 값이다. 물리 메모리가 얼마든 상관없이 이 값에 닿으면 행동이 바뀐다.
maxmemory-policy
그 상한선에 닿았을 때 무엇을 할지 정하는 규칙. eviction은 "쫓아냄"이라는 뜻으로, 자리를 만들기 위해 기존 키를 골라 지우는 동작이다.

기본값 조합이 이미 함정이다 — 둘의 기본값이 서로 다른 방향을 가리킨다

maxmemory-policy
기본값 noeviction — "아무것도 안 지운다"
maxmemory
기본값 0 = 상한 없음 — 그래서 정책이 발동할 계기 자체가 없다

그래서 아무것도 설정하지 않고 띄운 Redis는 갈래 ③(스왑·OOM killer)에 놓여 있다. 뒤에 나올 최악의 갈래가 사실은 "손대지 않은 기본 상태"라는 뜻이다. 이 한 줄을 면접에서 짚으면 "설정을 실제로 열어본 사람"으로 들린다.

정책 이름은 외울 필요가 없다. 앞부분이 축출 후보 범위, 뒷부분이 고르는 기준이다. allkeys-는 모든 키, volatile-은 TTL이 걸린 키만을 대상으로 삼는다. LRU는 Least Recently Used(가장 오래 안 쓴 것), LFU는 Least Frequently Used(가장 적게 쓴 것)의 약자다.

정책축출 후보고르는 기준이 문서에서의 의미
noeviction없음 (아무것도 안 지움)—갈래 ① — 쓰기만 실패
allkeys-lru전체 키가장 오래 안 쓴 것갈래 ② — 지우며 버틴다
allkeys-lfu전체 키가장 적게 쓴 것갈래 ② — 지우며 버틴다
allkeys-random전체 키무작위갈래 ② — 지우며 버틴다
volatile-lruTTL이 걸린 키만가장 오래 안 쓴 것② → 후보가 마르면 ①로 합류
volatile-ttlTTL이 걸린 키만만료가 가장 임박한 것② → 후보가 마르면 ①로 합류

정책 8종의 선택 기준과 LRU/LFU 내부 동작은 04번(TTL·만료·eviction 정책) 문서에서 다룬다. 여기서는 "가득 찬 순간의 진단과 방어"에 집중한다.

2. 갈래 ① noeviction — 쓰기만 골라 실패하는 반쪽 장애

이 조합에서는 상한에 닿아도 Redis가 아무것도 지우지 않는다. 대신 메모리를 더 쓰는 명령을 거부한다.

redis-cli 같은 인스턴스, 같은 키인데 결과가 갈린다
127.0.0.1:6379> SET user:1001 "{...}"
(error) OOM command not allowed when used memory > 'maxmemory'.

127.0.0.1:6379> GET user:1001
"{...}"          <- 읽기는 정상 동작한다

127.0.0.1:6379> PING
PONG             <- 헬스체크도 통과한다. 대시보드는 초록불이다

2-1. 왜 쓰기는 실패하고 읽기는 되는가

오류가 났으면 다 나야 자연스러워 보이는데 그렇지 않다. 이유는 Redis가 명령마다 "이 명령은 메모리를 더 쓸 수 있는 명령인가"라는 표시를 미리 붙여두기 때문이다. Redis 내부에는 모든 명령의 목록이 있고 각 명령에 성격을 나타내는 표식이 달려 있는데, 그중 하나가 "메모리를 늘릴 수 있음"이라는 표식이다. 메모리가 상한에 닿아 자리를 확보하지 못하면 Redis는 그 표식이 붙은 명령만 골라 거부한다.

2-2. 서비스 관점에서 이 반쪽 장애가 어떻게 보이는가

캐시 put 실패
코드가 예외를 감싸두지 않았다면 캐시에 저장하는 그 줄에서 예외가 터져 조회 API 자체가 500을 낸다. DB에서 데이터를 이미 잘 읽어왔는데도 응답을 못 준다.
세션 저장 실패
로그인은 세션을 쓰는 동작이라 신규 로그인이 전면 불가가 된다. 이미 로그인한 사용자는 세션을 읽기만 하므로 멀쩡하다.
분산 락 획득 실패
분산 락은 보통 SET key value NX로 잡는다. 이것도 쓰기이므로 실패하고, 락이 필요한 기능 전체가 정지한다.

"캐시가 꽉 찼을 뿐인데 로그인이 안 되는" 장애의 정확한 경로

캐시 키가 메모리를 다 먹음→ maxmemory 도달→ 세션 SET 거부→ 신규 로그인 불가

가장 헷갈리게 만드는 지점 — 사내에서 테스트하는 사람들은 대개 이미 로그인 상태라 "잘 되는데요?"라고 답한다. 증상을 겪는 집단과 확인하는 집단이 다르다는 것이 이 장애의 추적을 어렵게 만든다.

3. 갈래 ② eviction 정책 — 에러 없이 조용히 사라진다

allkeys-lru 같은 정책이 걸려 있으면 Redis는 에러를 내는 대신 기존 키를 지워 자리를 만들고 쓰기를 성공시킨다. 캐시 전용 인스턴스라면 이것은 장애가 아니라 정상 동작이다. 캐시는 원래 지워져도 DB에서 다시 읽어오면 그만인 데이터니까.

문제는 세 가지 상황에서 생긴다.

3-1. (1) 혼합 사용의 함정 — 로그에 아무것도 안 남는 장애

캐시와 세션·분산 락·쿠폰 발급 카운터가 한 인스턴스에 같이 있으면, allkeys-lru는 이 둘을 구분하지 못한다. LRU는 "가장 오래 안 쓴 키"를 지울 뿐이고, 한동안 활동이 없던 사용자의 세션이 딱 그 조건에 들어맞는다.

왜 원인 추적이 지독하게 어려운가 — 아무도 실패하지 않았기 때문이다 Redis 입장에서는 설정대로 정상 동작한 것이고, 애플리케이션 입장에서는 "세션 키를 조회했더니 없더라 = 로그인 안 한 사용자"로 해석될 뿐이다. 예외도, 에러 로그도, 실패 메트릭도 없다. 사용자만 무작위로 튕긴다.
세션이 축출되면
에러 한 줄 없이 사용자가 무작위로 로그아웃된다. 애플리케이션 로그에는 아무것도 안 남는다.
발급 카운터가 축출되면 — 더 나쁘다
카운터가 사라지면 발급 수가 0부터 다시 세지므로 한정 수량을 초과 발급하게 된다. 데이터 유실이 비즈니스 사고로 바뀌는 지점이다.

3-2. (2) volatile-* 정책의 축출 후보 고갈 설정만 봐서는 안 보인다

volatile-lru처럼 TTL이 걸린 키만 지우는 정책을 골랐는데, 정작 인스턴스 안에 TTL 있는 키가 다 소진되면 어떻게 될까. 지울 후보가 없으므로 Redis는 자리를 못 만들고, 결국 noeviction과 똑같이 쓰기 에러로 넘어간다.

이것이 함정인 이유 — 설정 파일만 보면 안전해 보인다

설정 파일에서 읽히는 것
volatile-lru라고 적혀 있으니 "가득 차면 알아서 지우겠지"
실제로 일어난 것
TTL 없는 키가 메모리를 다 먹었고 그 키들은 축출 대상이 아니라서 갈래 ①의 증상이 그대로 나온다

진단 신호: 사용률이 100%인데 evicted_keys가 늘지 않는다면 이 상태이거나 noeviction이다. "정책이 무엇인가"와 "그 정책이 실제로 지울 수 있는 키가 있는가"는 다른 질문이다.

3-3. (3) 축출 자체의 2차 효과 — Redis 문제가 DB 장애의 방아쇠가 된다

eviction이 격하게 돈다→ 지우는 작업이 CPU를 먹어 응답 지연이 튄다
지워진 캐시만큼 요청이 DB로 내려간다→ DB 부하가 함께 오른다→ DB 장애

즉 Redis 메모리 부족이 DB 장애의 방아쇠가 될 수 있다. 이 연결은 19번(캐시 무력화 방어) 문서의 주제로 이어진다. 면접에서 "축출은 캐시니까 괜찮다"에서 멈추지 말고 "축출된 만큼 DB로 흘러간다"까지 붙이면 한 단계 위로 들린다.

4. 갈래 ③ maxmemory 미설정 — 스왑과 OOM killer

상한이 없으면 Redis는 데이터가 들어오는 대로 계속 자란다. 그러다 OS 수준에서 터진다. 여기서 벌어지는 두 가지는 앞의 두 갈래와 성격이 완전히 다르다 — 앞의 둘은 Redis가 스스로 판단해서 취하는 행동이지만, 이번 둘은 Redis가 아니라 운영체제가 개입하는 사건이다.

4-1. 첫 번째 — 스왑(swap): 죽지도 살지도 않은 상태

스왑은 물리 메모리가 부족해질 때 당장 안 쓰는 메모리 페이지를 디스크로 밀어내 공간을 확보하는 OS의 기능이다. 그 자체로는 고마운 기능이고, 일반적인 애플리케이션이라면 잠깐 느려지고 말 일이다. 그런데 Redis에게는 치명적이다. 이유가 두 겹이다.

① 메모리에 두는 것이 존재 이유다
디스크로 밀려난 페이지에 접근하는 순간, 나노초 단위였던 메모리 접근이 밀리초 단위의 디스크 접근으로 바뀐다. 메모리 DB의 장점이 통째로 사라진다.
② 명령을 하나의 스레드로 처리한다
명령들이 한 줄로 줄을 서 있고 앞사람이 끝나야 뒷사람 차례가 온다. 스왑에 걸린 명령 하나가 디스크를 기다리는 동안 뒤에 줄 선 모든 요청이 함께 기다린다.

4-2. 두 번째 — OOM killer: 왜 하필 Redis가 뽑히는가

OOM killer는 리눅스 커널이 시스템 전체 메모리가 바닥났을 때 프로세스 하나를 골라 강제 종료하는 기능이다. 이름 그대로 "메모리 부족(Out Of Memory) 상황의 처형자"다. 커널 입장에서는 메모리를 확보할 방법이 더 없을 때, 시스템 전체가 멈추는 것보다 프로세스 하나를 죽이는 쪽이 낫다고 판단하는 것이다.

선정 기준 한 줄 — 그래서 Redis는 항상 1순위 후보다

커널은 죽였을 때 확보되는 메모리가 큰 프로세스에 높은 점수를 준다 → 그 서버의 최대 메모리 소비자는 대체로 Redis다

5. maxmemory 안에서도 터진다 — 데이터 바깥의 네 몫 가산점

"그럼 maxmemory를 물리 메모리와 똑같이 잡으면 되는 것 아닌가?" 자연스러운 생각이지만 위험하다. 이유는 하나로 요약된다.

maxmemory가 통제하는 것은 Redis가 "데이터"에 쓰는 메모리뿐인데, Redis 프로세스는 데이터 말고도 메모리를 쓴다

그 바깥의 몫이 물리 메모리를 밀어내면 결국 갈래 ③(스왑·OOM killer)으로 떨어진다. 데이터 바깥에서 메모리를 먹는 것이 네 가지다.

네 가지를 외우는 방법 — 1 + 2 + 1로 묶는다

복사본 하나(fork CoW) · 버퍼 둘(클라이언트 · 복제본) · 빈틈 하나(단편화)

"넷을 나열하세요"보다 "1+2+1"로 묶으면 인출이 훨씬 쉽다. 그리고 이 넷 중 가장 결정적인 것은 ①이다 — 나머지 셋은 서서히 늘지만, CoW는 스냅샷이 도는 그 순간에 급격히 튄다. 최악의 경우 스냅샷 도중에 전체 데이터가 한 번씩 바뀌면 메모리가 두 배까지 갈 수 있고, 이 순간이 OOM killer가 방문하는 대표적인 시점이다.

얼마나 낮춰야 하는가 — 고정된 숫자로 외우지 않는다 여유의 크기는 쓰기 비율(CoW 양을 좌우)과 클라이언트 수(버퍼 개수를 좌우)에 따라 달라진다. 그래서 "몇 %"를 외우는 것보다 위 네 항목이 우리 인스턴스에서 실제로 얼마나 먹고 있는지를 관측해 정하는 것이 맞다. 면접에서도 숫자를 단정하기보다 "이 네 가지를 관측해서 역산한다"고 답하는 편이 정확하고 강하다.

6. 방어선 1 — 용도별 인스턴스 분리 (구조)

여기서부터가 방어책이다. 방어는 네 겹이고, 각각 사고의 다른 단계를 끊는다.

eviction 정책은 인스턴스당 하나다 — 이 한 문장이 이 방어선의 전부다

한 Redis 인스턴스 안에 "지워도 되는 데이터"와 "지우면 안 되는 데이터"가 섞여 있으면, 어떤 정책을 골라도 한쪽이 틀린다. 이것은 설정을 잘 고르면 해결되는 문제가 아니라 구조의 문제다.

캐시 인스턴스
allkeys-lru 또는 allkeys-lfu. 가득 차면 안 쓰는 것부터 지우는 것이 정답인 데이터다.
세션 · 원본 인스턴스
noeviction + 넉넉한 용량 + 알람. 데이터가 조용히 사라지는 것보다 쓰기 에러를 내고 사람이 개입하는 편이 낫다.

이 판단의 본질을 한 문장으로

에러는 시끄럽고, 유실은 조용하다 — 그래서 원본 데이터에는 시끄러운 실패를 고른다

면접에서 noeviction을 고르는 이유를 "안전해서"라고 답하면 절반이다. "실패를 감지 가능하게 만들려고"라고 답하면 운영 관점이 드러난다.

7. 방어선 2 — TTL 규율 (누수 차단)

TTL(Time To Live, 키의 수명) 없는 캐시 키는 메모리 누수다

한 번 쓰이고 다시는 조회되지 않는 키가 영원히 남아 자리를 차지한다. 자바의 메모리 누수와 구조가 똑같다 — 아무도 안 쓰는데 회수되지 않는 것.

이 누수가 위험한 진짜 이유 — "깜빡함"으로 발생하고, 아무 데서도 안 걸린다 TTL을 빼먹은 코드는 정상 동작한다. 테스트도 통과하고 코드 리뷰에서도 눈에 안 띈다. 몇 주 뒤 메모리가 찼을 때야 드러난다. 그러니 개인의 주의력이 아니라 구조로 막아야 한다.
Before 지워질 계기가 아예 없는 키
// TTL 없는 캐시 put
// 이 키가 지워질 계기는 eviction뿐이다.
redis.set("product:detail:" + id, json);

// noeviction 인스턴스라면?
// 축출도 안 일어나므로 지워질 계기가
// 아예 없어 영구히 남는다.
// = 되돌릴 수 없는 단방향 누수
After 타입 시그니처가 규율을 강제한다
// TTL을 인자로 강제하는 래퍼를 팀 표준으로
cacheClient.set("product:detail:" + id, json,
                Duration.ofMinutes(30));

// 래퍼 내부에서 TTL 미지정·과도한 TTL을
// 예외로 막거나 기본값을 넣는다.
// TTL 인자가 필수이므로 "깜빡함"이
// 컴파일 단계에서 불가능해진다.

요점은 "TTL을 걸자"가 아니라 규율의 위치를 옮기는 것이다

코드 리뷰가 잡는 규칙 → 타입 시그니처가 강제하는 규칙

면접에서 "TTL을 꼭 겁니다"는 누구나 말한다. "TTL 인자를 필수로 받는 래퍼를 두어 빼먹는 것 자체를 불가능하게 만듭니다"는 같은 사고를 두 번 겪지 않으려는 사람의 답이다.

7-1. TTL이 있어도 남는 "주인 잃은 키"

버려진 구버전 키
키 이름 규칙을 바꾸면서 남겨진 product:v1:* 같은 것들. 아무도 조회하지 않는데 메모리에는 남아 있다.
정리되지 않은 임시 키
배치가 만들고 지우지 않은 중간 결과. 배치가 돌 때마다 쌓인다.

이런 키는 SCAN으로 키 공간을 조금씩 훑어 주기적으로 점검한다.

왜 KEYS가 아니라 SCAN인가 — 운영 중인 Redis에 KEYS를 날리면 안 되는 이유 KEYS *는 전체 키를 한 번에 훑는 동안 싱글 스레드를 통째로 점유해 그 사이 모든 요청을 멈춰 세운다. SCAN은 조금씩 끊어 순회하므로 다른 명령이 사이사이 처리된다. 메모리를 정리하러 들어갔다가 정리하는 행위 자체로 장애를 만드는 것이 이 실수의 결말이다. (자세한 내용은 12번 문서)

8. 방어선 3 — 관측과 알람 (조기 경보)

가득 찬 뒤에 아는 것과 70%에서 아는 것의 차이가 장애의 유무를 가른다

70%에서 알면 키를 정리하거나 증설할 시간이 있고, 100%에서 알면 이미 사용자가 로그인을 못 하고 있다. INFO memory가 내주는 지표 중 봐야 할 것들을 하나씩 뜯어보자.

8-1. used_memory 대비 maxmemory 비율 — 임계치를 정하는 기준

숫자를 외우지 말고 기준을 외운다

임계치는 "조치할 시간이 남아 있는 지점"에서 울리게 정한다 — 사람이 움직이는 데 걸리는 시간을 역산한다

보통 70~80%를 쓰지만, 중요한 것은 그 숫자가 아니라 "이 알람이 울리고 나서 우리가 할 수 있는 일이 남아 있는가"다. 증설에 반나절이 걸리는 조직이라면 70%도 늦다.

8-2. used_memory와 used_memory_rss — 두 개의 장부

이 둘의 뜻이 다르다는 것을 아는 것이 해석의 출발점이다.

지표누구의 장부인가무엇을 세는가
used_memoryRedis의 장부Redis가 자기가 데이터에 쓰고 있다고 스스로 계산한 양
used_memory_rssOS의 장부OS가 이 프로세스에 실제로 할당해 준 물리 메모리 양
RSS = Resident Set Size, "메모리에 상주하고 있는 크기"

두 장부가 다른 이유는 5절에서 본 그대로다 — Redis는 데이터 바깥에서도 메모리를 쓰고, 반납한 메모리가 OS에 즉시 돌아가지 않아 빈틈으로 남기 때문이다. 그리고 이 둘의 비율이 mem_fragmentation_ratio다. 값 하나로 서로 다른 두 문제를 진단할 수 있다는 점이 이 지표의 묘미다.

비율이 1보다 작다는 것이 왜 스왑을 뜻하는가 — 한 번 더 짚는다

Redis의 주장
"나는 4GB어치 데이터를 갖고 있다"
OS의 답변
"이 프로세스는 물리 메모리에 3GB만 올라와 있다"

차이인 1GB는 사라진 게 아니라 디스크로 밀려나 있는 것이다. 이 지표가 1 아래로 내려가면 응답 시간이 이미 튀고 있을 가능성이 높다.

8-3. evicted_keys — 이 값의 해석은 정책에 따라 정반대다

축출로 지워진 키의 누적 개수다. Redis가 시작된 이후 eviction 정책에 의해 삭제한 키가 몇 개인지 세는 카운터다. TTL 만료로 자연히 사라진 키는 여기 안 들어간다 — 오직 "자리가 모자라서 강제로 지운" 키만 센다.

어디서 봤나값해석해야 할 일
noeviction 인스턴스0이 아니다정책상 축출이 일어날 수 없다 → 누군가 정책을 바꿨거나 설정이 의도와 다르다즉시 조사
캐시 인스턴스증가 중이미 한계에 닿아 아슬아슬하게 돌고 있다. 지금 당장 에러는 안 나지만 캐시 히트율이 떨어지고 그만큼 DB 부하가 오르고 있다용량 계획 재검토
캐시 인스턴스증가율이 급등용량 부족 또는 어딘가의 키 누수를 의심한다키 패턴별 점유 조사
big key 감시도 같이 건다 멤버가 수백만 개인 리스트나 셋 하나가 있으면 용량 계획 자체가 무의미해진다. 게다가 그런 키를 DEL로 지우는 순간 싱글 스레드가 오래 붙잡혀 전체 지연이 튄다. --bigkeys 스캔 등으로 주기 점검한다.

8-4. 헬스체크가 PING만 확인하면 갈래 ①을 절대 못 잡는다

2절에서 본 대로 PING은 메모리를 쓰지 않는 명령이라 OOM 상태에서도 성공한다. 관측을 아무리 촘촘히 깔아도 헬스체크가 읽기 계열만 확인하고 있다면 이 상태를 원천적으로 감지할 수 없다.

Before 쓰기가 죽어도 초록불
// 겉보기 헬스체크
redis.ping();   // PONG -> UP

// maxmemory에 닿아 세션 SET이 전부
// 실패하는 중에도 이 체크는 통과한다.
// 대시보드는 전부 초록불이고
// 장애 인지가 CS 문의로부터 시작된다.
After 쓰기 경로까지 확인한다
// 짧은 TTL을 건 프로브 키에 실제로 써 본다
redis.set("healthcheck:probe", "1",
          Duration.ofSeconds(10));

// OOM이면 여기서 즉시 예외가 나므로
// 알람이 "Redis 쓰기 실패"를 바로 가리킨다.
// TTL을 걸어 프로브 키 자체가
// 누수가 되지 않게 한다.

이 방어의 값어치는 "장애를 막는 것"이 아니라 "추적 시간을 없애는 것"이다

읽기만 확인하는 헬스체크는 반쪽만 본다 — 쓰기 프로브 한 줄이 몇 시간의 원인 추적을 지운다

9. 방어선 4 — 애플리케이션 방어 (폭발 반경 축소)

앞의 세 방어선을 다 깔아도 캐시는 언젠가 실패한다. 그 전제에서 마지막 방어선은 캐시 에러가 서비스 에러로 전파되지 않게 막는 것이다.

Before 캐시 put 실패가 그대로 조회 API의 500이 된다
public Product getProduct(Long id) {
    Product p = repository.findById(id);
    redis.set(key(id), serialize(p), TTL);   // OOM 에러가 그대로 위로 전파된다
    return p;
    // DB에서 데이터를 이미 성공적으로 읽어왔는데도,
    // "캐시에 넣어두려던" 부수적 동작 하나 때문에 응답을 못 준다.
}
After 캐시는 최선노력(best-effort) — 실패해도 본 기능은 산다
public Product getProduct(Long id) {
    Product p = repository.findById(id);
    try {
        redis.set(key(id), serialize(p), TTL);
    } catch (RedisException e) {
        // 삼키되 반드시 남긴다. 조용히 무시하면 캐시가 몇 주째
        // 동작하지 않고 있어도 아무도 모르는 상태가 된다.
        log.warn("cache put failed, serving without cache", e);
        cacheFailureCounter.increment();   // 메트릭 -> 알람으로 연결
    }
    return p;   // 응답은 정상. 사용자는 조금 느릴 뿐 실패하지 않는다.
}

반드시 함께 말해야 하는 이면 — 이 방어는 문제를 없앤 게 아니라 옮긴 것이다

캐시 put이 계속 실패→ 캐시에 아무것도 안 쌓인다→ 모든 조회가 DB로 직행→ DB가 평소의 몇 배를 맞는다

서비스는 죽지 않았지만 부하가 통째로 DB로 넘어간다. 즉 이 방어선은 "캐시 장애를 DB 부하 문제로 바꿔치기한 것"이다. 그래서 "DB가 캐시 없는 트래픽을 견딜 수 있는가"가 곧바로 다음 질문이 되고, 그것이 19번 문서(캐시 무력화 방어)의 주제다. 두 문항이 한 몸이라는 것을 아는 것이 이 방어선의 마무리다.

예외를 삼킬 때의 두 가지 규칙 ① 로그를 남긴다 — 조용히 무시하면 캐시가 몇 주째 동작하지 않아도 아무도 모른다. ② 메트릭으로 센다 — 실패 카운터를 알람에 연결해야 "삼킨 실패"가 관측 가능해진다. 삼키는 것과 없는 척하는 것은 다르다.

10. 실무 시나리오 — "배포 후 로그인이 안 돼요"

혼합 사용 + noeviction 인스턴스에서 전형적으로 벌어지는 사고다. 결론을 먼저 말하지 않고 증상에서 출발해 어떻게 원인에 도달하는지 순서대로 따라가 보자. 면접에서 값어치가 있는 것은 결론이 아니라 이 추적 순서다.

들어온 신고는 이 한 줄뿐이다

"어제 배포 이후로 로그인이 안 된다는 문의가 늘고 있어요."

10-1. 추적 순서 — 다섯 걸음

1
"로그인만 안 된다"에서 공통점을 찾는다.
작동하는 것과 안 되는 것을 갈라 놓고 본다. 기존 사용자의 조회는 되고 신규 로그인은 안 된다. 로그인은 세션을 쓰는 동작이고, 기존 사용자의 요청은 세션을 읽는 동작이다. 여기서 가설이 하나 선다 — "읽기는 되는데 쓰기만 안 되는 상태 아닌가?"
PING이 성공한다는 사실이 왜 도움이 안 됐는지도 이 순간 이해된다PING은 메모리를 쓰지 않는 명령이라 OOM 상태에서도 성공한다. 헬스체크가 읽기 계열만 확인하고 있었다면 이 상태를 감지할 방법이 없었다.
2
가설을 직접 검증한다. Redis에 붙어 아무 키나 하나 써 본다.

(error) OOM command not allowed when used memory > 'maxmemory'.

여기서 원인의 성격이 확정된다. 애플리케이션 버그도 네트워크 문제도 아니고 Redis 메모리 포화다. 한 줄로 판정이 끝났다.

3
얼마나 찼고 정책이 무엇인지 본다.

여기까지로 "왜 이런 증상이 나오는가"가 완전히 설명된다. 갈래 ①의 교과서적 전개다.

4
그럼 무엇이 메모리를 먹었는가 — 원인을 찾는다.
증상의 원인은 알았지만 메모리가 찬 원인은 아직 모른다. 여기서 멈추고 재시작하면 며칠 뒤 똑같은 일이 반복된다. 키 패턴별로 얼마를 쓰는지 본다 — --bigkeys로 거대한 키가 있는지, SCAN으로 접두사별 키 개수를 세어 어떤 패턴이 비정상적으로 많은지 확인한다. 
키 패턴별 개수 (SCAN 샘플링)

5
결론이 조립된다.
어제 배포된 검색 결과 캐시가 TTL 없이 키를 만들고 있었다. 검색어 조합마다 키가 하나씩 생기므로 증가 속도가 대단히 빨랐고, 하루 만에 남은 메모리를 다 먹었다.
그리고 세션과 캐시가 같은 인스턴스에 있었기 때문에, 캐시가 먹어치운 메모리가 곧바로 세션 쓰기의 실패로 나타났다. 캐시 기능의 결함이 인증 기능의 장애가 된 것이다.

10-2. 네 방어선이 각각 어느 단계를 끊는가

이 사고가 흥미로운 이유는, 앞의 네 방어선 중 어느 하나만 있었어도 여기까지 오지 않았다는 점이다.

11. 이미 섞여 운영 중이라면 — 무중단 분리 이행 시니어 변별

한 번에 못 바꾼다. 그러니 이행 계획을 말해야 한다. "분리해야 합니다"까지만 말하면 문제 인식만 있고 실행 경험은 없는 사람으로 들린다.

1
현황 파악. SCAN으로 키 패턴별 개수와 메모리 점유를 샘플링해 캐시와 세션의 비중을 수치화한다. 새 인스턴스의 용량을 정하려면 이 숫자가 필요하고, 분리 후에도 캐시 쪽이 여전히 부족할지를 여기서 판단한다.
2
신규 인스턴스 준비. 세션용으로 noeviction 인스턴스를 따로 띄운다. 세션이 옮겨 가는 쪽이 되는 이유는, 세션이 "지우면 안 되는" 데이터라 정책 요구가 더 엄격하기 때문이다.
3
이중 쓰기 → 읽기 전환 → 구 데이터 소멸 대기. 여기가 핵심이고, 세션의 TTL 특성을 이관 전략에 활용하는 것이 판단 포인트다.
4
기존 인스턴스를 캐시 전용으로 확정. 세션이 빠졌으니 정책을 allkeys-lru로 바꾼다. 이제 축출이 돌아도 지워지는 것은 캐시뿐이다.

분리의 근거는 "eviction 정책 하나로 두 용도를 동시에 만족시킬 수 없다"는 것이고,
무중단 이행의 열쇠는 "세션에는 TTL이 있으므로 기다리면 저절로 넘어간다"는 성질이다

noeviction으로 가득 찬 상태에서 읽기도 실패하나요?힌트: 아니오 → 이유(표식) → 그래서 무엇이 문제인가, 3단으로

아니다. 메모리를 추가로 쓸 수 있는 명령만 거부된다. GET, DEL, EXPIRE(수명을 줄이는 방향), EXISTS 같은 명령은 그대로 동작한다.

이 비대칭이 나오는 이유는 Redis가 명령마다 "메모리를 늘릴 수 있음" 표식을 미리 붙여두고, 상한을 넘었을 때 그 표식이 붙은 명령만 골라 막기 때문이다. 실행해 보고 판단하는 게 아니라 명령 테이블에 이미 표시돼 있다.

그래서 이 상태는 반쪽 장애가 된다. PING이나 GET으로 하는 겉보기 헬스체크는 멀쩡히 통과하는데 쓰기 경로만 죽어 있다.

결론까지 붙인다 — "헬스체크에 실제 쓰기 확인을 포함해야 한다. 짧은 TTL을 건 프로브 키에 SET 한 번이면 충분하다"
사용률이 100%인데 evicted_keys가 0입니다. 무슨 상황인가요?힌트: 후보가 없거나, 애초에 안 지우는 설정이거나

둘 중 하나다.

① 정책이 noeviction이다. 애초에 축출이 일어나지 않는 설정이므로 카운터가 0인 것이 정상이고, 지금 쓰기는 전부 OOM 에러로 실패하고 있을 것이다. SET 프로브 한 번으로 즉시 확인된다.

② 정책은 volatile-*인데 축출 후보가 고갈됐다. TTL이 걸린 키만 지울 수 있는데 TTL 없는 키가 메모리를 다 먹은 상태라면 지울 대상이 없다. 그러면 설정 파일에는 축출 정책이 적혀 있는데 실제 동작은 noeviction과 똑같아진다.

이 질문이 좋은 이유는 "정책이 무엇인가"와 "그 정책이 실제로 지울 수 있는 키가 있는가"가 다른 질문이라는 것을 드러내기 때문이다. 확인 방법도 같이 말하면 좋다 — SCAN으로 훑어 TTL이 -1인 키의 비중을 세어 보면 후보 고갈 여부가 바로 나온다.

maxmemory를 물리 메모리와 같게 잡으면 왜 위험한가요?힌트: 그 값이 통제하는 범위가 어디까지인지부터

maxmemory가 통제하는 것은 데이터에 쓰는 메모리뿐인데, Redis 프로세스는 데이터 바깥에서도 메모리를 쓰기 때문이다. 그 바깥의 몫이 물리 메모리를 넘기면 OS 레벨에서 스왑이나 OOM killer가 발동한다.

바깥의 몫이 넷이다 — 복사본 하나, 버퍼 둘, 빈틈 하나.

  1. fork 자식의 copy-on-write 몫 — RDB 스냅샷이나 AOF rewrite 중 부모가 변경한 페이지만큼 복사본이 생긴다. 쓰기가 많으면 순간 사용량이 크게 뛴다. 가장 결정적인 항목이다.
  2. 클라이언트별 입출력 버퍼 — 연결 수에 비례해 늘고, 큰 응답을 내보낼 때 부푼다.
  3. 복제본에 보낼 버퍼 — 복제본이 느리거나 끊기면 계속 쌓인다.
  4. 메모리 단편화 — 잦은 할당·해제로 생긴 빈틈. mem_fragmentation_ratio로 관측한다.

딱 맞춰 잡으면 스냅샷이 도는 순간 OOM killer가 방문할 수 있다. 그리고 이때는 쓰기 몇 개가 실패하는 게 아니라 프로세스가 통째로 사라진다. 여유분을 남기는 것이 원칙이고, 여유의 크기는 쓰기 비율·클라이언트 수를 관측해 정한다고 답하는 것이 숫자를 단정하는 것보다 정확하다.

mem_fragmentation_ratio가 0.85로 나옵니다. 어떻게 읽어야 하나요?힌트: 1보다 작다는 것은 어느 쪽이 더 작다는 뜻인가

단편화가 적어서 좋은 상태가 아니라, 스왑이 발생하고 있다는 신호다. 이 지표를 "단편화 지표"로만 외운 사람이 정확히 여기서 틀린다.

비율은 used_memory_rss ÷ used_memory다. 1보다 작다는 것은 "OS가 물리 메모리에 올려둔 양"이 "Redis가 데이터라고 계산한 양"보다 적다는 뜻이다. Redis는 "나는 4GB를 갖고 있다"는데 OS는 "이 프로세스는 물리에 3.4GB만 있다"고 답하는 상황이고, 차이는 사라진 게 아니라 디스크로 밀려나 있다.

대응은 즉시다. 이 상태는 싱글 스레드가 디스크를 기다리는 구간이 이미 생겼다는 뜻이라 응답 시간이 튀고 있을 가능성이 높다. 반대로 1.5보다 크게 높으면 단편화 쪽이고, 큰 값의 잦은 삽입·삭제가 원인인 경우가 많다. 이쪽은 즉시 장애는 아니지만 용량 계획이 계산과 어긋나기 시작했다는 신호다.

한 문장 — "1보다 작으면 디스크로 샌 것, 1.5보다 크면 빈틈이 많은 것"
Redis 프로세스가 흔적 없이 사라졌습니다. OOM killer인지 어떻게 확인하나요?힌트: Redis 로그가 아니라 다른 쪽 로그를 봐야 한다

커널 로그를 본다. OOM killer는 Redis가 스스로 종료한 것이 아니라 커널이 죽인 것이므로, 판정 근거도 Redis 쪽이 아니라 커널 쪽에 남는다. dmesg나 시스템 로그에서 "Out of memory: Killed process ... (redis-server)" 형태의 줄을 찾으면 확정이다.

Redis 자체 로그의 모양도 단서가 된다. 정상 종료라면 종료 절차 로그가 남는데, OOM killer에 당하면 아무 마무리 로그 없이 뚝 끊기고 바로 재기동 로그가 이어진다. "정상 종료 흔적이 없다"는 것 자체가 외부에서 강제 종료됐다는 신호다.

여기서 한 발 더 나가면 좋다 — 강제 종료라서 Redis는 마무리 작업을 할 기회조차 없다. 종료 시점에 스냅샷을 남기지도 못하므로, 영속화 설정이 없거나 마지막 스냅샷이 오래됐다면 그 사이 데이터는 전부 사라진다. 갈래 ③이 "부분 실패"가 아니라 "복구 작업"인 이유가 이것이다.

캐시 인스턴스에 allkeys-lru를 걸어두면 OOM 에러는 절대 안 나나요?힌트: 지울 게 있느냐, 그리고 maxmemory 바깥은 어떤가

"에러가 안 나니까 안전하다"로 답하면 절반만 맞다. 두 가지를 짚어야 한다.

① 정책이 지킬 수 있는 범위는 maxmemory 안쪽뿐이다. 축출은 데이터 영역의 자리를 만드는 동작이므로, fork CoW·클라이언트 버퍼·복제 버퍼가 물리 메모리를 밀어내는 상황은 어떤 정책으로도 막지 못한다. 그쪽은 갈래 ③의 영역이다.

② 에러가 안 나는 것과 문제가 없는 것은 다르다. 축출이 격하게 돌면 지우는 작업 자체가 CPU를 먹어 응답 지연이 튀고, 지워진 캐시만큼 요청이 DB로 내려가 DB 부하가 오른다. 즉 Redis의 메모리 부족이 DB 장애의 방아쇠가 될 수 있다.

그래서 캐시 인스턴스라도 evicted_keys 증가율을 알람에 걸어둔다. "에러가 없다"가 아니라 "조용히 히트율을 잃고 있다"를 감지하기 위해서다.

세션에도 TTL이 걸려 있는데, 왜 세션 인스턴스에 volatile-lru가 아니라 noeviction인가요?힌트: TTL이 있다는 것과 지워도 된다는 것은 같은 말인가

TTL이 있다는 것은 "언젠가 만료된다"는 뜻이지 "지금 지워도 된다"는 뜻이 아니기 때문이다. 이 구분이 이 질문의 전부다.

volatile-lru를 걸면 축출 후보는 TTL이 걸린 키 전체가 된다. 세션에 TTL이 있으니 세션이 곧 후보가 되고, 메모리가 차면 아직 만료되지 않은 살아 있는 세션이 축출된다. 결과는 에러 한 줄 없는 무작위 로그아웃 — 우리가 피하려던 바로 그 장애다.

세션 인스턴스에서 원하는 행동은 "자리가 없으면 시끄럽게 실패하고 사람을 부르는 것"이다. 그래서 noeviction + 넉넉한 용량 + 알람이 답이 된다.

TTL은 데이터의 수명을 정하는 장치이고, eviction 정책은 자리가 없을 때의 행동을 정하는 장치다 — 둘은 다른 축이다
Redis의 LRU는 정확한 LRU인가요?힌트: 정확히 하려면 무엇이 필요한지부터 세어 보라

아니다. 근사(approximated) LRU다.

정확한 LRU를 구현하려면 모든 키를 최근 사용 순서로 정렬한 연결 리스트로 관리해야 한다. 키가 하나 접근될 때마다 그 키를 맨 앞으로 옮겨야 하고, 그 리스트를 유지하는 포인터들이 키마다 추가 메모리를 먹는다. 메모리를 아끼려고 도입한 기능이 메모리를 더 먹는 역설이 생긴다.

그래서 Redis는 타협한다. 축출이 필요할 때 키 몇 개를 무작위로 뽑아(샘플링) 그중 가장 오래 안 쓴 것을 지운다. 전체에서 가장 오래된 키가 아니라 "뽑힌 것 중 가장 오래된 키"다. 샘플 개수는 maxmemory-samples로 조절하며, 늘리면 정확도가 오르고 CPU를 더 쓴다 — 정확도와 비용 사이의 다이얼이다.

(가산점) LFU까지 얹으면 좋다. LRU는 "언제 마지막으로 썼는가"만 보므로 한 번의 대량 스캔에 취약하다. 배치가 상품 100만 건을 한 번씩 훑고 지나가면 그 100만 개가 전부 "방금 쓴 키"가 되어 원래 자주 쓰이던 인기 키를 밀어낸다. 캐시 히트율이 배치 한 번에 무너지는 것이다. allkeys-lfu는 "얼마나 자주 썼는가"를 보므로 한 번 스쳐간 키는 빈도가 낮아 우선 축출된다.

이미 70~80% 알람이 울렸습니다. 당장 뭘 하나요?힌트: 답을 두 갈래로 나누는 것 자체가 답의 절반이다

단기 대응과 구조 대응을 나눠서 답한다.

단기 — 무엇이 먹고 있는지부터 확인한다. INFO memory로 현재 사용량과 단편화 비율을 보고, --bigkeys와 SCAN 샘플링으로 어떤 키 패턴이 메모리를 점유하는지 찾는다. 원인을 모르는 채 용량부터 올리면 같은 일이 곧 반복된다.

그다음 TTL 없는 키·버려진 구버전 키를 정리한다. 이때 대형 컬렉션은 DEL 대신 UNLINK를 쓴다. DEL은 키를 지우는 작업 전부를 그 자리에서 처리하므로, 멤버가 수백만 개인 키를 지우면 싱글 스레드가 오래 붙잡혀 전체 요청이 그동안 멈춘다. UNLINK는 키 공간에서 참조만 즉시 끊고 실제 메모리 회수는 백그라운드로 넘긴다 — 이름 그대로 "링크만 끊는다"는 뜻이다.

정말 급하면 maxmemory를 올린다. 단 물리 여유 안에서 올려야 한다. 여기서 물리 메모리에 붙여 올리면 OOM killer를 부르게 되어 상황이 더 나빠진다.

구조 — 증가 추세를 분석해 용량 증설이나 용도 분리를 계획한다. 최근 며칠의 사용량 곡선을 보면 "정상적으로 늘어난 것"인지 "새 기능이 누수를 만든 것"인지 갈린다. 전자면 증설, 후자면 해당 키의 TTL 규율을 잡는 것이 답이다.

"일단 재시작"은 답이 아니다 — 원인이 누수면 며칠 뒤 다시 차고, 영속화가 없으면 캐시가 전부 비어 모든 요청이 DB로 쏟아지는 2차 장애를 스스로 만드는 셈이 된다
"느려진 Redis가 죽은 Redis보다 나쁘다"는 말은 무슨 뜻인가요? 가산점힌트: 클라이언트 입장에서 두 상황을 비교하라

죽으면 클라이언트가 즉시 연결 실패를 받고 폴백 경로로 갈 수 있지만, 느려지면 모두가 그 앞에 줄을 서서 기다리기 때문이다.

스왑에 걸린 Redis는 죽지도 살지도 않은 상태가 된다. PING은 (오래 걸릴지언정) 결국 성공하므로 헬스체크 대시보드는 초록불인데, 사용자는 응답을 못 받는다. Redis가 싱글 스레드라 한 명령의 디스크 대기가 뒤에 줄 선 전부의 지연이 된다는 점이 이 상황을 증폭시킨다.

애플리케이션 쪽 결말까지 붙이면 완성된다. 응답이 늦어지면 그 호출을 붙잡고 있는 애플리케이션 스레드가 반환되지 않고 쌓이므로, Redis 하나의 지연이 애플리케이션 서버 전체의 스레드 고갈로 번진다. 그래서 대응은 "Redis를 빠르게"만이 아니라 타임아웃을 짧게 잡아 실패를 빨리 확정하는 것이 함께 가야 한다. (이 논점은 19번 문서로 이어진다)

캐시와 세션이 이미 한 인스턴스에 섞여 운영 중입니다. 어떻게 풀어가나요? 시니어 변별힌트: "분리해야 합니다"에서 멈추면 감점이다

한 번에 못 바꾼다. 그러니 이행 계획을 말해야 한다. "분리해야 합니다"까지만 말하면 문제 인식만 있고 실행 경험은 없는 사람으로 들린다.

1단계 — 현황 파악. SCAN으로 키 패턴별 개수와 메모리 점유를 샘플링해 캐시와 세션의 비중을 수치화한다. 새 인스턴스 용량을 정하려면 이 숫자가 필요하고, 분리 후에도 캐시 쪽이 여전히 부족할지를 여기서 판단한다.

2단계 — 신규 인스턴스 준비. 세션용으로 noeviction 인스턴스를 따로 띄운다. 세션이 옮겨 가는 쪽인 이유는 정책 요구가 더 엄격하기 때문이다.

3단계 — 이중 쓰기 → 읽기 전환 → 구 데이터 소멸 대기. 세션 쓰기를 양쪽에 하고 읽기는 기존에 둔다(이 시점에는 아무 위험이 없다). 세션 TTL이 30분이라면 30분 뒤 신규 인스턴스에 "살아 있는 모든 세션"이 들어와 있다 — 만료된 세션은 옮길 필요가 없기 때문이다. 그다음 읽기를 신규로 돌리고(쓰기는 아직 양쪽이라 롤백이 안전하다), 마지막으로 이중 쓰기를 끝낸다. 기존 인스턴스의 세션 키는 TTL이 지나며 자연 소멸하므로 명시적으로 지울 필요조차 없다.

4단계 — 기존 인스턴스를 캐시 전용으로 확정. 정책을 allkeys-lru로 바꾼다. 이제 축출이 돌아도 지워지는 것은 캐시뿐이다.

"분리의 근거는 eviction 정책 하나로 두 용도를 만족시킬 수 없다는 것이고, 무중단 이행의 열쇠는 세션에는 TTL이 있으므로 기다리면 저절로 넘어간다는 성질입니다"
한 줄 요약
Redis가 가득 찼을 때의 증상은 설정이 결정한다 — noeviction이면 "메모리를 늘리는 명령" 표식이 붙은 쓰기만 골라 실패해 로그인이 막히는 반쪽 장애가 되고, eviction 정책이면 (캐시와 세션을 섞어 쓴 경우) 에러 없이 세션이 사라지는 조용한 유실이 되며, maxmemory 미설정이면 싱글 스레드가 스왑에 걸려 전체 요청이 줄줄이 밀리거나 커널 OOM killer가 프로세스를 통째로 죽인다 — 그래서 방어는 용도별 인스턴스 분리와 그에 맞는 eviction 정책, 전 키 TTL 규율, 사용률·evicted_keys·단편화 비율 알람, 캐시 실패를 삼키는 애플리케이션 코드로 가득 차기 전에 겹겹이 깔아둬야 하고, maxmemory는 fork의 copy-on-write·클라이언트 버퍼·복제 버퍼·단편화가 데이터 바깥에서 먹는 몫만큼 물리 메모리보다 낮게 잡아야 한다.
