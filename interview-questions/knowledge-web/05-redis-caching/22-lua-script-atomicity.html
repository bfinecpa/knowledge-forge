Redis Lua 스크립트
"확인하고 행동하는" 두 걸음을 한 걸음으로

면접 질문: "Lua 스크립트는 어떤 문제를 해결하나요? 사용 시 주의점은?"

핵심 관전 포인트 — Lua 스크립트는 "값을 조회해서 그 결과를 보고 조건 분기한 뒤 다음 명령을 실행"하는 check-then-act 로직을 Redis 서버 안에서 하나의 원자적 단위로 실행해, 명령과 명령 사이에 다른 클라이언트가 끼어드는 race condition을 없앤다. 락 소유자 검증 후 해제, 선착순 쿠폰의 잔여 수량 확인 후 발급, rate limiter가 대표 사례다. MULTI/EXEC로는 이걸 못 하는데, MULTI는 명령을 큐에 쌓아뒀다가 몰아 실행하는 구조라 중간 조회 결과를 받아 분기할 수 없기 때문이다. 대신 Redis는 명령 실행이 싱글 스레드라 스크립트가 도는 동안 다른 모든 명령이 멈추므로, 긴 스크립트는 서버 전체를 세우는 블로킹 폭탄이 된다 — 게다가 이미 쓰기를 한 스크립트는 SCRIPT KILL로 죽일 수도 없어서(절반만 반영된 상태를 남기면 원자성이 깨지므로 Redis가 거부한다) 남는 선택지가 SHUTDOWN NOSAVE뿐이다. 짧고 단순하게 유지하고, 접근하는 키는 반드시 KEYS 인자로 선언하며(클러스터가 라우팅할 노드를 판단하는 근거다), EVALSHA의 NOSCRIPT 폴백까지 아는 것이 주의점의 골자다.
  • 1
    무엇을 푸는가 — "읽고 → 판단하고 → 쓴다"는 형태를 서버 안에서 끼어들 틈 없는 한 덩어리로 만든다. 락 소유자 검증 해제, 선착순 쿠폰, rate limiter가 전부 이 형태다.
  • 2
    왜 되는가 — 락을 걸어서가 아니라 명령 실행 스레드가 하나뿐이라 애초에 끼어들 틈이 없기 때문이다. MULTI/EXEC는 중간 결과를 받아 분기할 수 없어 대체가 안 된다.
  • 3
    대가는 무엇인가 — 그 독점이 그대로 위험이 된다. 길면 전 서비스가 정지하고, 이미 쓰기를 했다면 SCRIPT KILL조차 거부돼 SHUTDOWN NOSAVE밖에 남지 않는다. 그래서 짧게 · KEYS로 · EVALSHA 폴백 · 결정적으로가 규율이다.

0. 질문 + 출제 의도

질문: "Lua 스크립트는 어떤 문제를 해결하나요? 사용 시 주의점은?"

출제 의도: check-then-act(조회 후 조건부 갱신)를 원자화하는 실무 도구(쿠폰 발급, 락 소유자 검증 해제)를 다뤄봤는지, 동시에 긴 스크립트가 싱글 스레드 전체를 세우는 양날의 검임을 아는지 본다 — 도구의 효용과 위험을 함께 말할 수 있는지가 관전 포인트다.

이 페이지가 겨냥하는 약점 세 가지 ① "Lua는 원자적이다"라는 암기로 끝나는 것 → 3절에서 원자성의 출처가 싱글 스레드 독점이라는 사실로 바꾸고, 7절에서 그 출처가 그대로 위험이 되는 구조까지 잇는다.
② 원자성을 RDB 트랜잭션과 같은 것으로 착각하는 것 → 5절에서 격리는 주지만 롤백은 주지 않는다는 경계를 긋고, "검증 앞·쓰기 뒤"라는 순서 설계로 대응한다.
③ 주의점을 "짧게 쓰세요" 한 줄로 끝내는 것 → 7~10절에서 폭주 시 대응 절차(BUSY → SCRIPT KILL → UNKILLABLE → SHUTDOWN NOSAVE), 클러스터 라우팅, NOSCRIPT 폴백, 결정성까지 네 갈래로 벌린다.

1. 무엇을 푸는가 — 명령과 명령 사이의 틈

1-1. 전제: check-then-act가 무엇인가

이 주제 전체가 이 용어 위에 서 있으므로 정의부터 하자. check-then-act는 이름 그대로 "값을 확인한(check) 뒤 그 결과에 따라 행동하는(act)" 코드 형태다. "재고를 조회해서 0보다 크면 하나 깎는다", "락의 주인이 나인지 확인해서 맞으면 지운다", "요청 카운트를 읽어서 한도 미만이면 1 올린다" — 전부 같은 모양이다.

문제는 확인과 행동이 서로 다른 명령이라는 데 있다. 확인 명령을 보내고 응답을 받아 애플리케이션에서 조건을 따지고 다시 행동 명령을 보내는 동안, 짧지만 분명한 시간이 흐른다. 그 사이에 다른 요청이 같은 데이터를 바꾸면 내가 손에 쥔 확인 결과는 이미 낡은 정보가 된다. 낡은 정보를 근거로 행동하니 틀린 결과가 나온다.

check-then-act의 결함은 코드가 틀린 것이 아니라 "확인한 사실이 행동하는 순간에도 참"이라는 가정이 틀린 것이다
비유 — 좌석이 하나 남은 공연장 두 사람이 같은 좌석표를 각자 들여다보고 "아직 비어 있네"를 확인한 뒤 각자 그 자리로 걸어간다. 표를 본 순간에는 둘 다 맞았다. 문제는 표를 본 시점과 자리에 앉는 시점이 다르다는 것이다. Lua가 하는 일은 자리를 늘리는 것이 아니라, "표 확인 → 착석"을 매표소 안에서 한 사람씩 끝내게 만드는 것이다.

2. 대표 사고 — 분산 락 해제

check-then-act가 만드는 사고 중 가장 조용하고 가장 치명적인 것이 분산 락 해제다. 다른 사고들은 최소한 에러라도 남기는데, 이건 아무것도 남기지 않는다.

BeforeGET과 DEL 사이에 틈이 있다 (Java)
// ① 지금 이 락의 주인이 나인지 확인
String owner = redis.get("lock:order:42");

if (myToken.equals(owner)) {
    // ← 바로 이 순간 락 TTL이 만료되고
    //    다른 프로세스 B가 락을 새로 획득하면?
    redis.del("lock:order:42");  // ② B의 락을 내가 지운다
}

// 결과: B는 락을 쥐고 있다고 믿는데 락 키는 사라졌다.
//       그래서 제3의 프로세스 C도 락 획득에 성공한다.
//       임계 구역에 B와 C가 동시 진입.
//       그런데 어디에도 에러가 찍히지 않는다.
After확인과 삭제를 서버 안에서 한 덩어리로 (Lua 관용구)
-- KEYS[1] = 락 키, ARGV[1] = 내 소유 토큰

if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])  -- 내 토큰일 때만
else
    return 0                          -- 남의 락이면 손대지 않는다
end

-- GET과 DEL 사이의 틈이 없어졌다.
-- 정확히는, 그 틈에 다른 클라이언트가 들어올 수 없게 됐다.
-- 반환값 1 = 내가 해제함 / 0 = 이미 남의 락이었음

이 코드의 결함을 한 문장으로 지목하면

"예외 처리가 없는 것"이 아니라 "①에서 확인한 사실이 ②를 실행하는 시점에도 참이라는 보장이 없는 것"

더 무서운 점은 끼어드는 주체가 다른 요청이 아니어도 된다는 것이다. 위 사고에서 실제로 끼어든 것은 TTL 만료 — 내 코드와 무관하게 시간이 알아서 일으키는 사건이다. 그래서 "동시 요청이 몰릴 일 없는 배치라 괜찮다"는 판단이 통하지 않는다.

반대 방향의 같은 사고 — 락 연장 "내 락을 조금 더 붙잡아 두자"며 확인 없이 PEXPIRE로 TTL만 연장하는 코드도 같은 결함을 갖는다. 이미 남에게 넘어간 락이라면 남의 락 수명을 내가 늘려주는 꼴이 된다. 소유자 검증과 연장도 반드시 한 덩어리여야 한다.

3. 원자성의 정체 — 락이 아니라 싱글 스레드 독점

Lua 스크립트가 원자성을 얻는 이유는 락을 걸어서가 아니다. Redis가 명령 실행을 스레드 하나로 처리하기 때문이다. EVAL이 시작되면 그 메인 스레드는 스크립트가 끝날 때까지 다른 클라이언트의 명령을 하나도 처리하지 않는다. 다른 클라이언트들의 명령은 소켓 버퍼에서 순서를 기다린다. 즉 스크립트 전체가 바깥에서 보면 하나의 명령처럼 보인다.

원자성의 출처를 정확히 말하는 법

원자성을 "락을 걸어서" 얻는 게 아니라, "애초에 끼어들 틈이 존재하지 않는 실행 모델"에서 얻는다

이 문장은 7절에서 그대로 뒤집혀 위험의 근거가 된다 — 공짜가 아니라 다른 계정으로 청구된 것이었다는 사실이 거기서 드러난다.

4. MULTI/EXEC로는 왜 안 되나

"Redis에도 트랜잭션이 있지 않나?"가 자연스러운 반문이다. 있다. 그런데 이름만 같고 동작이 다르다.

MULTI/EXEC는 명령들을 서버 쪽 큐에 쌓아뒀다가 EXEC를 만나면 한꺼번에 순서대로 실행하는 장치다. 큐에 쌓는 단계에서는 각 명령이 실행되지 않으므로 응답도 오지 않는다 — QUEUED라는 접수증만 돌아온다. 실제 결과들은 EXEC가 끝난 뒤 배열로 한 번에 온다.

MULTI/EXEC결과를 받는 시점이 너무 늦다
MULTI
GET stock      → QUEUED   결과가 아직 없다
DECR stock     → QUEUED
EXEC           → [1, 0]   여기서 처음 결과를 본다

# "GET 결과가 0보다 크면" 이라는 조건을
# 쓸 자리가 어디에도 없다.
# 판단할 시점에는 이미 다 실행된 뒤다.
Lua결과를 그 자리에서 변수에 받는다
EVAL ...
  local stock = tonumber(redis.call('GET', KEYS[1]))
  if stock > 0 then            여기서 분기한다
      redis.call('DECR', KEYS[1])
  end

-- 서버 안에서 GET 결과를 즉시 받아
-- if 문에 쓴다. 왕복도, 재시도도 없다.

WATCH를 곁들이면 우회는 된다. WATCH key는 "이 키가 EXEC 전에 다른 클라이언트에 의해 바뀌면 EXEC를 통째로 실패시켜라"라고 예약하는 명령이다. 이런 방식을 낙관적 잠금(optimistic locking)이라 부른다 — 충돌이 드물 것이라 낙관하고 일단 진행한 뒤, 충돌이 감지되면 그때 실패시키고 처음부터 다시 하는 전략이다.

문제는 "처음부터 다시"의 비용이다. 선착순 쿠폰처럼 수만 요청이 같은 키 하나에 몰리는 상황에서는 대부분의 EXEC가 실패하고, 실패한 요청들이 일제히 재시도하며 다시 충돌한다. 경합이 심할수록 재시도가 폭증하는 구조라 정확히 필요한 순간에 무너진다.

수단중간 결과로 분기원자성경합이 심할 때한 줄 특징
MULTI/EXEC불가일괄 실행 보장해당 없음큐잉 후 몰아 실행일 뿐
WATCH + MULTI간접 (재시도)낙관적재시도 폭증충돌을 감지해 실패시키는 전략
Lua 스크립트가능전체 원자재시도 없이 한 번에check-then-act 정공법
면접에서 선을 긋는 문장 "같은 '트랜잭션'이라는 단어지만 RDB 트랜잭션과는 전혀 다른 보장"이라고 못 박는다. MULTI/EXEC가 주는 것은 "묶어서 순서대로 실행"이지 "실패 시 되돌림"이 아니다. 두 수단의 더 깊은 비교는 별도 문서(27-multi-exec-watch-vs-lua)의 몫이고, 이 질문에서는 "중간 결과로 분기할 수 없다" 한 가지만 정확히 말하면 충분하다.

5. 원자성은 격리이지 롤백이 아니다

여기가 RDB 트랜잭션에 익숙한 사람이 가장 잘 헛디디는 지점이다. Lua가 주는 원자성은 격리(다른 클라이언트가 중간 상태를 보거나 끼어들 수 없음)이지, RDB의 롤백(실패하면 앞의 변경을 되돌림)이 아니다. 스크립트 중간에 에러가 나면 이미 실행된 쓰기는 그대로 남는다.

Lua중간에 에러가 나도 앞의 쓰기는 남는다
redis.call('SET', KEYS[1], 'hello')   -- 성공한다. 그리고 남는다.
redis.call('INCR', KEYS[1])           -- 'hello'는 숫자가 아니다 → 에러 → 스크립트 중단
-- 위의 SET은 롤백되지 않는다. 키에는 'hello'가 남아 있다.

왜 롤백이 없는가. Redis에는 변경 전 값을 따로 보관해 두는 장치가 없기 때문이다. PostgreSQL은 MVCC로 이전 튜플 버전을 남겨두고 WAL에 변경 이력을 적어두므로 되돌릴 근거가 있지만, Redis는 메모리 위 자료구조를 그 자리에서 고친다. 되돌릴 재료가 애초에 없다.

Lua의 원자성이 주는 것과 주지 않는 것 — 이 세 칸을 통째로 외운다

주는 것 · 격리
실행 중 다른 클라이언트가 끼어들거나 중간 상태를 볼 수 없다. 이것이 전부이자 핵심이다.
안 주는 것 · 롤백
에러가 나도 앞의 쓰기는 남는다. 되돌릴 이전 값을 보관하지 않기 때문.
안 주는 것 · 내구성
유실 여부는 AOF fsync 정책과 복제 지연에 달렸다. Lua는 동시성 도구이지 내구성 도구가 아니다.

5-1. redis.call vs redis.pcall

redis.call
명령이 에러를 내면 스크립트 전체가 그 자리에서 중단되고 에러가 클라이언트로 반환된다. 그 전까지의 쓰기는 남는다. 기본값으로 쓴다 — 예상 못 한 상황에서 빨리 멈추는 편이 안전하다.
redis.pcall
에러를 예외처럼 터뜨리지 않고 에러 정보를 담은 값(테이블)으로 돌려준다. 스크립트가 계속 실행되며 직접 확인해 처리할 수 있다. p는 protected call의 약자. 정리 작업이나 메시지 변환이 필요한 지점에만 국소적으로 쓴다.
local res = redis.pcall('INCR', KEYS[1])
-- 반환값이 err 필드를 가진 테이블이면 에러가 났다는 뜻이다.
if type(res) == 'table' and res.err then
    -- 여기서 정리 작업을 하거나, 의미 있는 에러 메시지로 바꿔 반환할 수 있다.
    return redis.error_reply('counter is not an integer')
end
return res

5-2. 롤백이 없는 세계의 규율 — 검증은 앞에, 쓰기는 뒤에

이 절의 인출 문장

"Lua는 격리는 주지만 롤백은 주지 않는다 — 그래서 검증을 앞에, 쓰기를 뒤에 둔다"

6. 대표 실무 사례

6-1. 선착순 쿠폰 — 잔여 확인과 차감을 원자로

1절의 타임라인이 그대로 재현되는 현장이다. 여기에 "이미 받은 사람인가"라는 중복 검사까지 얹히면서 check-then-act가 두 겹이 된다.

Before확인(GET)과 차감(DECR) 사이로 다른 요청이 들어온다
long remaining = Long.parseLong(
        redis.get("coupon:event1:stock"));

if (remaining > 0) {
    redis.decr("coupon:event1:stock");  // 동시에 1000명이
    issueCoupon(userId);                // 여기 도달하면?
}
// 재고 100개짜리 이벤트에 1000장 발급 (초과 발급)
// 게다가 같은 사용자가 두 번 눌러도 막을 방법이 없다
After중복 검사 + 재고 확인 + 차감을 한 번에
-- KEYS[1] = 재고 키, KEYS[2] = 발급자 Set 키, ARGV[1] = userId
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -1                            -- 이미 받은 사용자
end
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil or stock <= 0 then          nil 검사 필수
    return 0                             -- 소진
end
-- 여기까지가 검증이다. 걸러지면 아무것도 쓰지 않았다.
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 1                                 -- 발급 성공
테스트에서 절대 안 잡히는 한 줄 — stock == nil 검사 키가 없으면 GET은 Lua에서 false를 돌려주고 tonumber(false)는 nil이 된다. 이 검사를 빼면 nil과 숫자를 비교하는 순간 Lua 에러가 나 스크립트가 중단된다. 이벤트 키가 아직 세팅되지 않았거나 TTL로 사라진 순간에만 터지는 버그라, 정상 시나리오 테스트로는 영원히 발견되지 않는다.
호출부키는 KEYS로, 값은 ARGV로 — 반환값은 코드로 약속한다 (Java)
Long result = redis.execute(
        couponScript,
        List.of("coupon:{event1}:stock", "coupon:{event1}:issued"),  // KEYS
        userId);                                                      // ARGV

// 스크립트는 숫자만 돌려줄 수 있으므로
// 성공/소진/중복을 코드로 약속해 두고 호출부에서 의미로 되돌린다.
if (result == 1)       issueCouponInDb(userId);
else if (result == 0)  throw new SoldOutException();
else                   throw new AlreadyIssuedException();

동시에 몇만 요청이 몰려도 스크립트는 한 번에 하나씩 실행되므로 초과 발급과 중복 발급이 구조적으로 불가능해진다. 키 이름의 {event1} 중괄호는 8절의 해시 태그이고, 이 사례의 전체 설계는 별도 문서(17-flash-sale-coupon-issuance-design)에 있다.

6-2. Rate limiter — 이번엔 "부분 실행"이 문제다

두 번째 단골이다. "현재 카운트를 확인해서 한도 미만이면 증가시키고 TTL을 건다"는 로직인데, Lua가 필요한 이유가 조금 다르다.

BeforeINCR과 EXPIRE 사이에 프로세스가 죽으면?
long count = redis.incr("rate:" + userId);   // ① 카운터 증가
if (count == 1) {
    redis.expire("rate:" + userId, 60);      // ② 첫 요청일 때만 TTL
}
// ①과 ② 사이에 이 인스턴스가 죽거나 네트워크가 끊기면
// TTL 없는 영구 카운터가 남는다
// → 그 사용자는 영원히 차단된다 (자연 회복 불가)
After증가와 TTL 설정이 한 덩어리
-- KEYS[1] = 카운터 키, ARGV[1] = 한도, ARGV[2] = 윈도우(초)
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[2])   첫 요청일 때만
end
if current > tonumber(ARGV[1]) then
    return 0    -- 한도 초과, 차단
end
return 1        -- 통과
-- 매 요청마다 EXPIRE를 걸면 창이 계속 밀려 윈도우가 무한정 늘어난다
여기서 Lua가 막는 것은 race condition이 아니다 두 요청이 서로를 방해하는 문제가 아니라 "두 명령 중 하나만 실행된 채 남는" 부분 실행을 막는 것이다. check-then-act의 사촌이고, 원자성이 푸는 문제라는 점은 같다. 면접에서 사례를 둘 들 때 이 둘을 고르면 "원자성이 푸는 문제가 한 종류가 아니다"라는 인식까지 보여줄 수 있다.

6-3. 그 밖의 단골 — 공통 형태를 잡는다

락 연장 (lease 갱신)
"내 락인지 확인 → 맞으면 PEXPIRE로 연장". 2절의 락 해제와 똑같은 소유자 검증 패턴이고, 검증 없이 연장하면 남의 락 수명을 내가 늘려주는 반대 방향의 사고가 난다.
조건부 갱신 (compare-and-set)
"저장된 버전 번호보다 큰 값일 때만 SET". 늦게 도착한 오래된 갱신이 새 값을 덮어쓰는 것을 막는다. 메시지 순서가 뒤집혀 도착하는 비동기 환경에서 특히 필요하다.

코드 리뷰에서 반사적으로 반응해야 할 형태

"읽고 → 판단하고 → 쓴다"가 서로 다른 두 명령으로 흩어져 있으면, 그 사이는 언제나 열려 있다

쿠폰(GET+DECR), 락 해제(GET+DEL), 락 연장(GET+PEXPIRE), rate limit(INCR+EXPIRE), CAS(GET+SET) — 전부 같은 형태다. 이 형태가 보이면 Lua(또는 그에 준하는 원자적 수단)를 떠올리는 것이 반사신경이 돼야 한다.

7. 원자성의 청구서 ① 긴 스크립트 = 서버 전체 정지 시니어 변별

3절에서 원자성을 "공짜로 얻는다"고 썼다. 정확히는 다른 계정으로 청구된다. 그 청구서가 이 절이다.

원자성의 원천이 "싱글 스레드가 스크립트를 독점한다"이므로, 그 시간 동안 Redis의 다른 모든 명령이 대기한다. 스크립트 안에서 수십만 멤버를 루프 돌거나 big key를 순회하면 캐시 조회 · 세션 확인 · 락 획득 등 그 Redis를 쓰는 전 서비스가 함께 멈춘다. 운영에서 KEYS 명령을 금지하는 것과 정확히 같은 원리의 함정이다.

여기서 대부분의 설명이 끝나는데, 시니어를 가르는 것은 그다음 질문이다 — 그래서 폭주하면 어떻게 멈추는가?

SHUTDOWN NOSAVE가 정확히 무엇을 뜻하는가 NOSAVE는 종료 시 RDB 스냅샷을 남기지 말라는 뜻이다. 반쯤 반영된 상태를 디스크에 굳혀버리지 않기 위해서다. 대신 마지막 저장 이후의 데이터를 잃고, 복제 구성이라면 페일오버가 일어난다. "수습 수단"이 아니라 "더 큰 사고로 갈아타는 것"이라고 이해해야 한다.

이 절의 결론 — 방어는 사후가 아니라 사전이다

긴 스크립트는 사고가 나면 되돌릴 방법이 사실상 없다
① 짧은 한 덩어리로만
스크립트는 명령 몇 개 + 분기 하나 수준의 check-then-act로만 쓴다.
② 루프가 보이면 반려
배치 · 순회 작업을 Lua에 넣지 않는다. 멤버 수에 비례하는 루프는 그 자리에서 반려한다.
③ 스크립트도 리뷰 대상
본문이 문자열 안에 있어서 코드 리뷰에서 그냥 넘어가기 쉽다. 명시적으로 리뷰 항목에 올린다.
④ SLOWLOG 모니터링
EVAL/EVALSHA가 SLOWLOG에 찍히는지 본다. 느려지는 중을 사고 전에 잡는 유일한 신호다.

8. 청구서 ② 접근하는 키는 반드시 KEYS 배열로 선언

먼저 KEYS와 ARGV가 각각 무엇인지부터.

KEYS
이 스크립트가 접근할 키의 이름 목록. KEYS[1], KEYS[2]처럼 1부터 시작하는 배열로 참조한다.
ARGV
키가 아닌 그 밖의 값 목록. 사용자 ID, 한도, 타임스탬프, 소유 토큰 같은 것들.

호출 형태를 뜯어보면 둘의 경계가 어떻게 정해지는지 보인다.

EVAL <script> 2 coupon:{event1}:stock coupon:{event1}:issued 12345
              ^  ^--------KEYS[1]-------^ ^--------KEYS[2]-------^ ^ARGV[1]
              |
              키의 개수. "여기서부터 2개는 키, 그 뒤는 값"이라는 경계 선언이다.

왜 키를 굳이 KEYS로 넘겨야 하는가. 단일 인스턴스만 보면 아무 차이가 없다. 키를 ARGV로 넘기든 스크립트 본문에 하드코딩하든 잘 돈다. 차이는 Redis Cluster에서 드러난다.

Redis Cluster는 데이터를 16384개의 해시 슬롯에 나눠 담고, 슬롯들을 여러 노드에 분배한다. 키가 어느 슬롯에 속하는지는 CRC16(키 이름) mod 16384로 정해진다. 클라이언트는 명령을 보내기 전에 그 명령이 다루는 키 이름을 보고 슬롯을 계산해, 그 슬롯을 담당하는 노드로 보낸다.

이 함정의 성질 — 조용히 깨지지도 않는다

단일 인스턴스에서 잘 돌다가 클러스터로 옮기는 순간 깨지는 대표적 코드

그것도 데이터가 조용히 틀어지는 게 아니라 라우팅 단계에서 깨지므로, 이관 당일 대량 에러로 한꺼번에 나타난다. 확장 계획이 있다면 단일 노드일 때부터 KEYS 규율과 해시 태그를 지켜 두는 것이 유일한 예방책이다.

9. 청구서 ③ EVALSHA와 스크립트 캐시 — NOSCRIPT 대비 가산점

EVAL은 호출할 때마다 스크립트 본문 전체를 네트워크로 보낸다. 수십 줄짜리 스크립트를 초당 수만 번 호출하면 그 자체가 대역폭 낭비다. 그래서 실무에서는 스크립트를 한 번 등록해 두고 이후에는 그 본문의 SHA1 해시값(40자 16진수 문자열)만 보내는 EVALSHA를 쓴다.

폴백NOSCRIPT는 장애가 아니라 "캐시가 비었다"는 신호다 (Java)
try {
    return redis.evalsha(sha, keys, args);
} catch (RedisNoScriptException e) {
    // 본문을 보내 재등록하면서 실행한다. 다음 호출부터는 다시 EVALSHA가 먹힌다.
    return redis.eval(scriptBody, keys, args);
}
운영 경험이 드러나는 지점 Spring Data Redis의 DefaultRedisScript나 Redisson 같은 클라이언트는 이 폴백을 내장하고 있다. 그래서 직접 짤 일은 드물지만, "페일오버 직후 잠깐 NOSCRIPT 에러 로그가 왜 찍혔는지"를 설명할 수 있는지가 변별 지점이다. 장애가 아니라 캐시가 비었다가 다시 채워지는 정상 과정이라고 답하면 된다.

10. 청구서 ④ 결정적(deterministic)으로 작성

결정적이라는 것은 "같은 입력에 대해 언제 어디서 실행해도 같은 결과가 나온다"는 성질이다. 왜 이게 문제가 되는가.

Redis의 쓰기는 그 노드에만 머물지 않는다. 복제본으로 전파되고, AOF(명령 로그)에 기록됐다가 재시작 시 다시 실행되어 상태를 복원한다. 그러니 같은 스크립트가 원본과 복제본에서, 또는 지금과 AOF 재생 시점에 서로 다른 결과를 만들면, 그 순간부터 데이터가 갈라진다.

랜덤 값과 현재 시각이 대표적인 비결정 요소다. 이것을 스크립트 안에서 구해 데이터에 그대로 쓰면 위험하다.

Before스크립트 안에서 시각을 구해 데이터에 쓴다
local now = redis.call('TIME')[1]   -- 실행할 때마다 값이 다르다
redis.call('ZADD', KEYS[1], now, ARGV[1])
-- 그 값이 그대로 데이터로 남는다
-- → 원본과 복제본의 점수가 달라질 수 있다
After시각은 애플리케이션이 정해 ARGV로 넘긴다
-- ARGV[1] = 호출 시각(ms), ARGV[2] = 멤버
redis.call('ZADD', KEYS[1], ARGV[1], ARGV[2])
-- 같은 인자로 다시 실행하면 언제나 같은 결과
-- = 결정적이다
정직하게 짚어둘 대가 — 이걸 덧붙이면 답이 완성된다 시각을 애플리케이션이 넘기면 이번엔 앱 서버들의 시계가 서로 어긋나는 문제가 생긴다. 여러 인스턴스의 시계가 수백 ms씩 다르면 윈도우 경계가 인스턴스마다 미세하게 달라진다. NTP 동기화를 전제로 하되, 그것도 완벽하지 않다는 것을 알고 쓰는 것이 정확한 이해다. rate limiter나 슬라이딩 윈도우 구현에서 특히 흔한 함정이다.

규율 한 줄

스크립트 안에서 랜덤 · 시각을 만들어 데이터에 쓰지 않는다. 필요하면 호출하는 쪽이 정해서 ARGV로 넘긴다

11. "Lua를 쓸까"의 판단 기준

원자성이 필요 없는데 Lua를 쓰는 것도 잘못된 선택이다. 세 갈래로 갈린다.

A
명령 2~3개 + 분기 하나 수준의 짧은 check-then-act → Lua가 정답이다. 이 페이지의 사례들이 전부 여기 속한다. 락 해제, 쿠폰 발급, rate limit, CAS.
B
왕복만 줄이고 싶고 분기가 없다 → Lua가 아니라 파이프라인이나 MGET이 맞는 도구다. 파이프라인은 여러 명령을 한 번에 보내 네트워크 왕복 횟수를 줄이는 기법일 뿐 원자성은 주지 않는다. 원자성이 필요 없는 상황에서 Lua를 쓰면 7절의 위험만 떠안는 셈이다.
C
정확성이 돈과 직결되는데(쿠폰 · 재고 · 락) 로직이 길고 복잡하다 → Lua에 다 넣지 말고 분해를 먼저 고민한다. Redis에는 원자적 판정만 남기고("발급 가능한가, 가능하면 재고 하나 차감") 나머지 비즈니스 로직은 애플리케이션이나 DB로 옮긴다.

스크립트가 길어질 때 스스로에게 던질 질문

Lua가 길어진다는 것은 대개 Redis가 하지 않아도 될 일까지 떠안았다는 신호다

"이 스크립트에서 원자적이어야 하는 부분은 정확히 어디까지인가?"를 물으면 대부분 판정과 그 판정에 딸린 한두 개의 쓰기로 줄어든다. 나머지는 스크립트 밖으로 나갈 수 있다.

주의점 4종 연상 — "짧 · 키 · 해 · 결" (짧게 쓰고 · 키는 KEYS로 · 해시(EVALSHA)는 폴백과 함께 · 결정적으로). 폭주 대응 연상 — "쓰기 전이면 KILL, 쓴 뒤면 SHUTDOWN".

첫 답변을 이 순서로 말하면 빠짐이 없다 check-then-act를 원자화→ 사례 2개 (락 해제 · 쿠폰)→ MULTI로는 분기 불가→ 그런데 그 원자성의 출처가 싱글 스레드 독점→ 길면 전면 정지 · 쓰기 후엔 kill 불가→ 그래서 짧 · 키 · 해 · 결

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼쳐서 맞춰 본다. 답을 눈으로 읽는 것보다 인출 훈련이 훨씬 오래 간다.

MULTI/EXEC 트랜잭션으로는 같은 걸 못 하나요? 최다 빈출힌트: "결과를 언제 받느냐"로 답한다

못 한다. MULTI는 명령을 큐에 모았다가 EXEC에서 일괄 실행하는 구조라 중간 조회 결과를 받아 분기할 수 없다 — GET의 결과 자체가 EXEC 이후에야 온다. 판단할 시점에는 이미 모든 명령이 실행되고 난 뒤다.

check-then-act를 하려면 WATCH로 낙관적 잠금을 걸고 충돌 시 재시도하는 우회가 필요한데, 경합이 심한 상황(선착순)에서는 재시도 폭풍이 된다 — 대부분의 EXEC가 실패하고 그 요청들이 일제히 다시 몰린다. Lua는 서버 안에서 분기하므로 재시도 없이 한 번에 끝난다.

"같은 '트랜잭션'이라는 단어지만 RDB 트랜잭션과 전혀 다른 보장" — MULTI/EXEC가 주는 것은 "묶어서 순서대로 실행"이지 "실패 시 되돌림"이 아니다
스크립트가 5초씩 걸리면 무슨 일이 벌어지나요? 시니어 변별힌트: 대응 절차까지 말해야 끝난다

싱글 스레드가 스크립트에 붙잡혀 있으므로 그 Redis를 쓰는 모든 서비스의 모든 명령이 대기한다 — 캐시 조회, 세션 확인, 락 획득 전부. 애플리케이션에서는 타임아웃과 에러 폭증으로 나타나고, 커넥션 풀이 마르면서 그 뒤의 요청까지 밀린다.

임계 시간(busy-reply-threshold, 예전 이름 lua-time-limit, 기본 5초)을 넘기면 다른 클라이언트에 BUSY 에러가 나가기 시작하는데, 이때도 스크립트는 계속 돈다. BUSY는 중단 신호가 아니라 "지금 바쁘니 기다리지 말고 실패하라"는 안내다.

그리고 여기서 한 발 더 들어가야 한다. 이미 쓰기를 수행한 스크립트는 SCRIPT KILL로도 못 죽인다(UNKILLABLE). 중간에 죽이면 절반만 반영된 상태가 남고, 그건 이미 복제본과 AOF로 흘러가고 있어 되돌릴 수 없기 때문이다. 남는 선택지는 SHUTDOWN NOSAVE로 서버를 내리는 것뿐인데, 이건 마지막 저장 이후 데이터를 버리고 페일오버를 유발하는 사고 확대다.

핵심 문장 — "원자성의 원천(싱글 스레드 독점)이 곧 위험의 원천"

그래서 방어는 사후가 아니라 사전이다 — 스크립트를 짧게 유지하는 코드 리뷰 규율, SLOWLOG 모니터링, 루프가 보이면 반려.

Cluster 환경에서 Lua 쓸 때 뭐가 다른가요?힌트: 두 가지. 라우팅 근거와 슬롯 제약

첫째, 접근하는 키를 전부 KEYS 배열로 선언해야 한다. 클러스터는 명령에 등장하는 키 이름으로 슬롯을 계산해 노드를 고르는데(CRC16(키) mod 16384), 키가 ARGV에 숨어 있거나 스크립트 안에서 조립되면 그 판단을 할 수 없다.

둘째, 한 스크립트의 모든 키가 같은 해시 슬롯에 있어야 한다. 슬롯이 다르면 서로 다른 노드에 있을 수 있고, 한 노드가 남의 노드 데이터를 만질 수 없기 때문이다. 여러 키를 다루면 해시 태그(coupon:{event1}:stock)로 슬롯을 맞춘다 — 중괄호 안의 문자열만으로 슬롯을 계산한다.

이는 MGET·MULTI와 같은 멀티 키 제약의 연장선이고, "단일 노드에서 잘 돌던 스크립트가 Cluster 전환 때 깨지는" 대표 사례라 확장 계획 단계에서 미리 알아야 하는 제약이다.

Lua 실행 도중 Redis가 죽으면 절반만 실행된 상태가 남나요?힌트: 원자성 질문과 내구성 질문을 분리하라

살아 있는 서버 기준으로 "절반 실행된 상태를 다른 클라이언트가 보는 일"은 없다 — 원자적이라 그 사이에 조회가 끼어들 수 없기 때문이다.

장애 시에는 스크립트의 효과가 통째로 반영됐거나 통째로 유실되는 쪽에 가깝다. 그러나 여기서 주의할 것은 Redis의 내구성 자체가 설정에 달려 있다는 점이다 — AOF의 fsync 정책, 복제 지연에 따라 "커밋됐다고 응답받은 쓰기가 재시작 후 사라지는" 창이 존재한다.

즉 Lua는 동시성(원자성) 문제를 푸는 도구이지 내구성을 주는 도구가 아니다

쿠폰 발급처럼 유실이 치명적인 데이터는 Redis에서 원자적으로 판정한 뒤 DB에 기록하는 등 내구성 설계를 따로 얹어야 한다.

스크립트 중간에 에러가 나면 앞의 쓰기는 롤백되나요?힌트: "되돌릴 재료가 있는가"부터

롤백되지 않는다. Lua의 원자성은 격리(끼어들기 방지)이지 RDB의 롤백이 아니다. Redis에는 변경 전 값을 보관하는 장치가 없어서 되돌릴 재료 자체가 없다 — 메모리 위 자료구조를 그 자리에서 고치기 때문이다.

redis.call은 에러 발생 시 스크립트를 그 자리에서 중단시키고, 그 전까지의 쓰기는 그대로 남는다. redis.pcall은 에러를 예외로 터뜨리지 않고 값(테이블)으로 돌려주므로 스크립트 안에서 확인해 직접 처리할 수 있다.

설계 규율은 "검증을 앞에, 쓰기를 뒤에" — 롤백이 없는 세계에서 정합성을 지키는 방법은 되돌리기가 아니라 순서 설계다

실패할 수 있는 판단을 전부 앞쪽에서 끝내면, 걸러졌을 때 아직 아무것도 쓰지 않은 상태이므로 "실패 = 아무 일도 없었음"이 성립한다.

매번 스크립트 본문을 전송하나요? 가산점힌트: 캐시가 어디에 사는지

아니다. SCRIPT LOAD로 등록해두고 SHA1 해시(40자)로 EVALSHA를 호출하는 것이 정석이다 — 본문 전송 비용이 사라지고 해시만 오간다.

단 스크립트 캐시는 서버 메모리에만 있고 영속화되지 않는다. 재시작하면 비어 있고, 페일오버로 승격된 노드에 그 스크립트가 있다는 보장도 없다. 그래서 EVALSHA가 NOSCRIPT 에러를 반환하면 EVAL로 폴백해 본문을 다시 보내며 재등록하는 처리가 필요하다.

클라이언트 라이브러리가 대부분 자동 처리하지만, 페일오버 직후 잠깐의 NOSCRIPT 에러 로그가 왜 찍히는지 설명할 수 있으면 운영 경험이 드러난다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

스크립트 안에서 KEYS 명령이나 SCAN을 써도 되나요? 시니어 변별힌트: 두 가지 이유로 안 된다

쓰면 안 된다. 이유가 둘이다.

① 블로킹이 원자 구간 안으로 들어온다. KEYS는 전체 키 공간을 훑는 O(N) 명령이고, 그것이 중간에 양보할 수 없는 스크립트 안에서 실행되면 7절의 폭탄이 그대로 터진다. SCAN은 원래 "호출과 호출 사이에 다른 명령이 끼어들 수 있어서" 안전한 명령인데, 스크립트 안에서 루프로 돌리면 그 끼어들 틈을 스스로 없애 버리는 셈이라 이점이 사라진다.

② 클러스터에서 키를 선언할 수 없다. 이런 명령은 실행해 보기 전에는 어떤 키를 만질지 알 수 없으므로 KEYS 배열로 선언한다는 규칙 자체가 성립하지 않는다. 8절의 라우팅 근거가 무너진다.

덧붙여 키 순회 결과의 순서가 보장되지 않는다는 점에서 결정성 문제까지 겹친다. "스크립트는 자기가 만질 키를 미리 아는 짧은 로직이어야 한다"는 원칙으로 답하면 세 이유가 한 문장에 담긴다.

redis.call과 redis.pcall 중 무엇을 기본으로 써야 하나요?힌트: 롤백이 없다는 전제에서 생각한다

기본은 redis.call이다. 롤백이 없는 환경에서는 예상 못 한 상태를 만나면 즉시 멈추는 것(fail-fast)이 안전하다. 에러를 삼키고 계속 진행하면 잘못된 전제 위에서 쓰기를 이어가 피해가 커진다.

redis.pcall은 국소적으로 쓴다 — ① 에러가 정상 흐름의 일부인 경우(예: 타입이 안 맞을 수 있는 값을 다룰 때), ② 의미 있는 에러 메시지로 바꿔 클라이언트에 돌려주고 싶을 때(redis.error_reply), ③ 실패 시 남은 정리 작업이 필요할 때.

주의할 점은 pcall이 롤백을 주지 않는다는 것이다. 에러를 값으로 받아 직접 처리할 뿐이고, 이미 실행된 쓰기는 여전히 남는다. 그래서 pcall을 쓰더라도 "검증 앞 · 쓰기 뒤" 원칙은 그대로 유효하다.

동시에 몰린 요청들은 "먼저 요청한 순서"대로 처리되나요? 시니어 변별힌트: 직렬화와 공정성은 다른 이야기다

직렬화는 보장되지만 공정성은 보장되지 않는다. 스크립트가 한 번에 하나씩 실행된다는 것은 확실하지만, 어느 클라이언트의 요청이 먼저 실행되는지는 네트워크 지연, 커넥션 상태, 이벤트 루프가 소켓을 읽는 순서에 좌우된다.

그래서 선착순 쿠폰에서 "먼저 버튼을 누른 사람"과 "먼저 처리된 사람"은 다를 수 있다. Lua가 보장하는 것은 "재고보다 많이 나가지 않는다"는 정확성이지 "요청 순서대로 발급된다"는 공정성이 아니다.

Lua는 초과 발급을 막는 도구이지 줄 세우기를 보장하는 도구가 아니다

엄밀한 순서가 요구된다면 도착 순서를 별도로 기록하는 설계(대기열 자료구조, 타임스탬프 부여 주체를 하나로 모으기)가 따로 필요하다 — 그리고 그 타임스탬프를 스크립트 안에서 만들면 안 된다는 것이 10절의 이야기와 이어진다.

스크립트의 반환값은 어떻게 넘어오나요? 주의할 변환 규칙이 있나요?힌트: 숫자와 불리언에서 갈린다

Lua의 값은 Redis 응답 타입으로 변환되어 클라이언트에 전달되는데, 여기서 자주 걸리는 규칙이 셋이다.

① 숫자는 정수로 변환되며 소수점 이하가 잘린다. Lua에서 3.7을 반환하면 3이 온다. 비율이나 평균 같은 값을 그대로 반환하면 조용히 값이 깨지므로, 문자열로 바꿔 반환하거나 정수 단위(예: 1000배)로 올려서 넘기는 것이 안전하다.

② false는 "값 없음(nil)"으로, true는 1로 변환된다. 그래서 Lua에서 불리언을 그대로 돌려주면 클라이언트에서는 null과 1이라는 비대칭적인 값으로 보인다. 이 페이지의 예제들이 1/0/-1 같은 정수 코드로 결과를 약속한 이유가 여기 있다.

③ 테이블(배열)을 반환할 때 중간에 nil이 있으면 거기서 잘린다. 배열의 일부만 도착하는 형태라 원인을 찾기 어렵다.

실무 규율은 하나로 정리된다 — 스크립트는 정수 코드나 문자열처럼 변환이 명확한 값만 반환하고, 그 의미는 호출부와 코드로 약속한다.

Redis 7의 Functions는 EVAL과 무엇이 다른가요? 가산점힌트: 9절에서 문제였던 것이 무엇이었나

Redis 7에서 추가된 Functions는 스크립트를 이름 붙은 함수로 라이브러리에 등록해 두고 호출하는 방식이다(FUNCTION LOAD → FCALL). EVAL/EVALSHA가 "애플리케이션이 들고 있다가 그때그때 보내는 스크립트"라면, Functions는 "서버에 배포해 두는 코드"에 가깝다.

가장 실질적인 차이는 9절에서 문제였던 지점이다 — Functions로 등록한 라이브러리는 서버의 데이터와 함께 영속화되고 복제본에도 전파되므로, NOSCRIPT 폴백을 애플리케이션이 떠안을 필요가 없다. 또 해시값 대신 사람이 읽을 수 있는 함수 이름으로 호출한다.

다만 원자성과 블로킹의 성질은 완전히 같다. 여전히 싱글 스레드를 독점하므로 길면 서버가 멈추고, 키는 여전히 KEYS로 선언해야 하며, 결정성 규율도 그대로다. "운영·배포 모델이 개선된 것이지, 이 페이지의 주의점이 사라진 것은 아니다"라고 선을 그으면 정확한 답이다.

Lua 스크립트를 직접 짜지 않고 Redisson 같은 라이브러리를 쓰면 이 주의점들은 신경 안 써도 되나요?힌트: 감싸는 것과 감싸지 못하는 것

절반만 맞다. Redisson의 분산 락이나 Spring Data Redis의 스크립트 지원은 내부적으로 이 페이지의 Lua 관용구를 그대로 쓰고 있고, EVALSHA와 NOSCRIPT 폴백도 대신 처리해 준다. 그 부분은 확실히 덜어 준다.

그러나 라이브러리가 감싸 주지 못하는 것들이 있다. ① 내가 직접 작성한 스크립트의 길이는 아무도 대신 줄여 주지 않는다. ② 클러스터의 키 슬롯 정렬은 내가 키 이름을 어떻게 짓느냐의 문제다. ③ 장애 시 무슨 일이 일어나는지 설명하는 능력은 라이브러리가 대신해 주지 않는다 — 그리고 면접에서 묻는 것은 대개 이 세 번째다.

면접에서는 "라이브러리를 쓰지만 안에서 무엇이 벌어지는지 안다"는 태도가 가장 잘 통한다. 예를 들어 "Redisson의 락 해제도 결국 소유자 토큰을 검증하는 Lua"라는 한마디가 그 태도를 드러낸다.

한 줄 요약
Lua 스크립트는 "읽고 → 판단하고 → 쓴다"는 check-then-act를 싱글 스레드 Redis 안에서 끼어들 틈 없는 한 덩어리로 실행해 락 소유자 검증 해제 · 선착순 쿠폰 같은 정확성 문제를 푸는 도구이고 MULTI/EXEC로는 중간 결과 분기가 불가능해 대체되지 않지만, 바로 그 실행 모델 때문에 긴 스크립트는 서버 전체를 세우는 블로킹 폭탄이 되며 이미 쓰기를 한 스크립트는 SCRIPT KILL조차 거부돼 SHUTDOWN NOSAVE 말고는 수습 수단이 없으므로 — 짧은 원자 단위로만 쓰고, 키는 KEYS로 선언해 클러스터 라우팅이 가능하게 하며, EVALSHA의 NOSCRIPT 폴백과 "원자성은 롤백도 내구성도 아니다"라는 경계까지 아는 것이 완성된 답이다.
