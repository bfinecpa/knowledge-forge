질문: "Local cache(Caffeine) + Redis 2단 캐시 구조의 장단점과 무효화 전파 방법은?" — 구조 한 줄 → 대가 한 줄 → 전파 한 줄 → 안전망 한 줄 순서로 말하면 첫 답변이 끝난다.

2단 캐시는 L1(Caffeine, JVM 힙 안 — 네트워크 없이 나노초~마이크로초)과 L2(Redis, 공유 저장소 — 네트워크 왕복 포함 밀리초 미만)를 겹쳐서, Redis 왕복조차 아까운 초고빈도 읽기를 로컬에서 끝내는 구조다. 대가는 "노드마다 다른 값을 들고 있을 수 있다"는 인스턴스 간 불일치이고, 무효화는 Redis pub/sub 브로드캐스트로 전파하는 것이 정석이다. 단 pub/sub은 메시지 유실 시 재전달이 없으므로 무효화 전파는 불완전하며, 짧은 로컬 TTL을 최후의 안전망으로 반드시 함께 둬야 한다. 이 복잡도를 감수할 만한 데이터(초고빈도 읽기 + 변경 드묾 + 짧은 불일치 허용)인지 판별하는 것이 설계의 핵심이다.
출제 의도 — 빠른 구조를 아는지가 아니라, 복잡도를 추가하는 결정을 어떻게 내리는지를 본다
채점 포인트가 둘이다. ① 로컬 캐시의 노드 간 불일치라는 새 문제를 감수할 만큼 이득이 큰 상황(초고빈도 읽기)을 판별할 수 있는가. ② pub/sub 무효화 같은 해법의 불완전함(메시지 유실 시 불일치가 TTL까지 지속)까지 짚을 수 있는가. 그래서 이 페이지의 무게중심은 "빨라진다"(§2)가 아니라 §4 불일치·§7 pub/sub의 급소·§10 도입 판단에 있다.

1. L1·L2 — 번호는 "빠르기 등급"이 아니라 "요청 지점으로부터의 거리"다

이 주제에서 L1, L2라는 표기가 설명 없이 튀어나오는 경우가 많은데, 이 이름은 CPU 캐시 계층에서 빌려온 관례다. CPU는 연산 장치 바로 옆에 아주 작고 아주 빠른 메모리를 두고, 그 바깥에 조금 더 크고 느린 메모리를 둔다. 연산 장치에 가장 가까운 것이 레벨 1이고, 멀어질수록 번호가 커진다.

애플리케이션 캐시도 이 관례를 그대로 쓴다. 여기서 "요청 지점"은 요청을 처리하는 우리 애플리케이션 코드다.

막대 길이가 아니라 눈금 사이의 간격을 보라 — 한 칸이 10배다. DB → Redis로 옮겨서 얻은 것만큼의 이득이, Redis → 로컬로 옮길 때 한 번 더 남아 있다.
이 한 줄에서 모든 장단점이 나온다
L1은 네트워크가 없는 캐시, L2는 네트워크가 있는 캐시.

장점(왕복 제거)도 여기서 나오고 단점(네트워크가 없으니 다른 노드와 이야기할 수단도 없다 → 불일치)도 똑같이 여기서 나온다. 하나의 성질이 이득과 대가를 동시에 만든다는 것이 이 구조를 이해하는 열쇠다.

1-1. Caffeine이 무엇이고, 왜 HashMap이면 안 되는가

Caffeine은 자바용 로컬(local) 캐시 라이브러리다. "로컬"이 핵심인데, 캐시된 데이터가 애플리케이션 프로세스 자신의 힙 메모리 안에 들어 있다는 뜻이다. 조회에 네트워크가 전혀 개입하지 않아, 코드 입장에서는 HashMap.get()과 같은 층위의 연산이다.

그냥 HashMap을 쓰면 캐시가 아니다
  • 크기 상한이 없다 — 무한히 쌓여 힙이 터진다
  • 만료가 없다 — 낡은 값이 영원히 산다
Caffeine이 더해 주는 것 그래서 캐시다
  • maximumSize · expireAfterWrite
  • 무엇을 먼저 버릴지 정하는 축출 정책, 히트율 통계
  • Spring 캐시 추상화(@Cacheable)의 흔한 구현체

2. 조회는 가까운 쪽부터 내려가고, 채우기는 먼 쪽부터 올라온다

2단 캐시의 동작은 두 방향으로 읽어야 한다. 찾을 때는 가까운 곳부터 아래로 내려가고, 찾은 값을 채울 때는 먼 곳부터 역순으로 올라온다. 이 두 번째 방향이 면접에서 자주 빠지는 부분이다.

채우기가 역순인 이유가 오른쪽 아래 빨간 상자다 — L2를 먼저 채워 놓아야 뒤에 오는 다른 인스턴스의 요청이 DB까지 내려가지 않는다.
기대 효과는 곱으로 나타난다
L1 히트율 95% → 응답 시간에서 왕복이 사라지고, 동시에 Redis 트래픽이 1/20이 된다.

한 번의 도입이 지연(클라이언트 쪽 이득)과 부하(서버 쪽 이득)를 동시에 줄인다는 점이 2단 캐시의 매력이다. 이 매력 때문에 대가를 과소평가하기 쉽다는 것이 §4의 주제다.

3. before/after — "요청마다 20번 읽히는 기능 플래그"

가장 좋은 후보는 요청마다 반드시 읽히는 데이터다. 요청 하나를 처리하며 20번 읽히는 설정값이라면, 2단 캐시가 없애는 것은 왕복 1회가 아니라 왕복 20회다. 전형적인 대상은 시스템 설정, 기능 플래그, 권한/역할 정의, 카테고리 트리, 공통 코드 테이블처럼 읽기가 폭발적으로 많고 · 잘 안 바뀌고 · 크기가 작은 데이터다.

✕ before — 모든 조회가 Redis 왕복
public boolean isFeatureEnabled(String featureKey) {
    return redisTemplate.opsForValue()
            .get("feature:" + featureKey) != null;   // 네트워크 1회
}

// 요청당 이런 조회가 20번이면 요청당 Redis 왕복 20회.
// 왕복 0.5ms 기준 → 요청당 10ms를 네트워크에서만 쓴다.
// Redis도 (인스턴스 수 x 초당 요청 수 x 20)만큼의 명령을 받는다.
✓ after — 대부분의 조회가 JVM 안에서 끝난다
private final Cache<String, Boolean> localCache = Caffeine.newBuilder()
        .maximumSize(10_000)                        // ① 힙 방어
        .expireAfterWrite(Duration.ofSeconds(30))   // ② 불일치의 상한
        .build();

public boolean isFeatureEnabled(String featureKey) {
    // get(key, loader)는 L1에 없을 때만 loader를 부른다.
    // 즉 L2(Redis) 왕복은 L1 미스일 때만 발생한다.
    return localCache.get(featureKey, key ->
            redisTemplate.opsForValue().get("feature:" + key) != null);
}
① maximumSize 빠지면 OOM

이 한 줄이 없으면 캐시가 힙을 무한히 먹는다. 로컬 캐시로 인한 OOM은 대부분 이 줄이 빠져서 생긴다. 캐시는 "있으면 좋은 것"이므로 버려도 되는 크기로 상한을 두는 것이 기본이다.

② expireAfterWrite(30s) 성능 값이 아니다

이 30초는 튜닝 파라미터가 아니라 "인스턴스 간 값이 어긋난 채로 있을 수 있는 최대 시간"이다. 무효화 전파가 전부 실패해도 30초 뒤에는 맞는 값으로 돌아온다는 약속이다(§7).

4. 지불하는 것 ① — 인스턴스 간 불일치 (가장 큰 비용)

이 구조의 본질적 대가는 하나로 압축된다
L1은 인스턴스마다 따로 있고, 서로 모른다. 서버 A에서 데이터가 바뀌면 A는 자기 L1을 갱신할 수 있지만, B에서는 아무 일도 일어나지 않았다. 무효화가 B까지 전파되기 전까지 B의 힙에는 옛 값이 그대로 살아 있다.
사용자 눈에는 이것이 "새로고침할 때마다 값이 바뀌었다 안 바뀌었다 한다"로 보인다. 애플리케이션 로그는 전부 정상이라 원인을 찾기가 특히 어렵다.
도입 결정의 진짜 의미
2단 캐시를 얹는 결정은 곧
"이 데이터는 잠깐 어긋나도 되는가"에 예라고 답하는 결정이다.

그래서 판단의 첫 질문은 성능이 아니라 불일치 허용치다. 잔액·재고·권한 회수처럼 즉시 일관성이 필요한 데이터는 애초에 후보가 아니다. 성능 이득을 재기 전에 허용치를 먼저 묻는 순서 자체가 면접에서 보려는 태도다.

5. 지불하는 것 ② — 메모리 · 중복 · 복잡도 · 디버깅

JVM 메모리 점유와 GC 압박 힙에 산다

maximumSize 없이 쓰면 로컬 캐시가 OOM의 직접적 원인이 된다. 그 정도가 아니어도 힙에 오래 살아남는 객체가 늘면 GC가 훑을 양이 늘어 정지 시간이 길어진다.

메모리 중복 인스턴스 수만큼 복제

인스턴스 20대면 같은 카테고리 트리가 힙에 20벌 존재한다. "크기가 작아야 한다"는 조건이 바로 여기서 나온다.

무효화 복잡도 분산 문제가 된다

Redis 한 곳만 지우면 끝나던 일이 전 인스턴스의 L1까지 지워야 하는 분산 문제로 바뀐다. §6~§9 전체가 이 한 줄의 비용이다.

디버깅 난이도 계층이 하나 늘었다

"이 값이 L1 것인가, L2 것인가, DB 것인가"를 매번 따져야 한다. 게다가 로컬 캐시는 밖에서 들여다볼 수단이 기본으로는 없어서, 어느 인스턴스의 L1인지까지 좁혀야 한다.

거래의 요약 — 한 문장
속도와 부하를 얻고, 일관성과 단순함을 판다.

6. 무효화 전파의 정석 — Redis pub/sub 브로드캐스트

무효화 전파의 정석은 Redis의 pub/sub(발행/구독)을 방송 채널로 쓰는 것이다. 어떤 클라이언트가 채널에 메시지를 발행(PUBLISH)하면, 그 채널을 구독(SUBSCRIBE)하고 있는 모든 클라이언트에게 Redis가 그 메시지를 뿌려준다. 데이터를 변경한 인스턴스가 L2를 지우고 채널에 키 이름을 발행하면, 전 인스턴스가 받아 각자의 L1에서 그 키를 지운다.

발행자와 구독자는 별개의 역할이 아니라서 A가 발행한 메시지는 A 자신에게도 배달된다. 삭제는 멱등이라 대부분 그냥 받고 처리하면 된다.
변경 지점에서 외울 3박자
커밋 → 삭제 → 방송

(1) DB 커밋 · (2) L2 DEL · (3) PUBLISH. 이 순서에서 (2)와 (3)이 뒤집히면 무효화가 통째로 무력화된다 — 아래가 그 이유다.

6-1. 순서 함정 — L2 삭제가 전파보다 먼저여야 한다

✕ 전파 먼저 — 옛 값이 도로 들어앉는다
featureRepository.update(featureKey, enabled);
redisTemplate.convertAndSend("cache-invalidation", key); // (2) 방송
redisTemplate.delete(key);                              // (3) L2 삭제

// 그 사이에 B에서 벌어지는 일:
//  1. 메시지 수신 → B가 자기 L1을 지운다
//  2. 곧장 다음 요청 → L1 미스 → L2를 읽는다
//  3. A가 아직 L2를 안 지웠다 → 옛 값을 읽어 L1에 도로 채운다
//  → 이 값은 다음 무효화나 TTL까지 살아남는다
✓ L2 삭제 먼저 — 경합이 성립하지 않는다
public void updateFeature(String featureKey, boolean enabled) {
    featureRepository.update(featureKey, enabled);        // (1) DB
    redisTemplate.delete("feature:" + featureKey);        // (2) L2 삭제
    redisTemplate.convertAndSend("cache-invalidation",    // (3) 방송
            "feature:" + featureKey);
}

// B가 메시지를 받고 곧바로 L2를 읽어도, L2는 이미 비어 있다.
// → DB에서 새 값을 가져와 채운다.

6-2. 구독 측 — 지우기만 한다

public void onInvalidationMessage(String key) {
    // 새 값을 채우지 않고 지우기만 한다. 다음 조회가 L2/DB에서 최신 값을 가져온다.
    // 지우는 동작은 몇 번을 해도 결과가 같아서(멱등) 중복 수신·자기 수신에 안전하다.
    localCache.invalidate(key);
}
자기 메시지, 그냥 받고 처리 기본값

A가 이미 지운 키를 한 번 더 지워도 아무 해가 없다. 대부분 이걸로 충분하다.

발행자 ID로 자기 것 무시 필요할 때만

인스턴스마다 고유 ID를 만들어 {"key":"feature:x","from":"instance-7"}로 보내고 from이 자기면 건너뛴다. 메시지가 아주 잦아 무효화 작업 자체가 부담일 때만 필요한 최적화다.

7. 급소 — Redis pub/sub은 유실되면 그걸로 끝이다 이 질문의 채점 포인트

Redis pub/sub은 메시지를 저장하지 않는다
발행 시점에 그 채널을 구독하고 있는 연결에만 즉시 뿌리고, 뿌린 뒤에는 잊는다. 큐처럼 쌓아뒀다가 나중에 접속한 구독자에게 주는 일이 없고, 못 받은 구독자에게 재전달하는 일도 없다. 이런 전달 보장을 at-most-once(최대 1회)라고 부른다 — "많아야 한 번 도착한다", 즉 0번 도착할 수도 있다는 뜻이다.
배포 중 재시작 유실

롤링 배포로 인스턴스가 하나씩 내려갔다 올라오는 동안, 내려가 있던 서버는 구독자가 아니다. 그 사이의 무효화는 이 서버에게 없었던 일이 된다.

네트워크 순단 유실

커넥션이 흔들려 재접속하는 몇 초 사이의 메시지가 사라진다.

Redis 페일오버 유실

마스터가 교체되는 동안 구독 연결이 끊겼다가 새 마스터로 재접속하는데, 그 틈의 메시지는 어디에도 없다.

메시지를 놓친 노드는 자기 L1이 낡았다는 사실 자체를 알 방법이 없다. 아무 신호도 못 받았으니 정상이라고 믿고 옛 값을 계속 서빙한다. 그리고 이 상태는 그 키의 로컬 TTL이 다할 때까지 지속된다. 바로 이것이 짧은 L1 TTL이 선택이 아니라 필수인 이유다.

두 경로가 같은 지점에서 출발해 다른 시간에 도착한다는 점이 핵심이다 — 도착 자체를 보장하는 것은 위쪽(pub/sub)이 아니라 아래쪽(TTL)이다.
역할 분리 — 이 한 문장이 답변의 급소다
pub/sub 전파는 "빠른 경로"이고,
정합성의 보장은 TTL이 진다.

전파가 하는 일은 불일치를 30초에서 5밀리초로 줄이는 것이지 불일치를 없애는 것이 아니다. 없앨 수 없는 나머지를 TTL이 유한한 시간 안에 정리한다. 그래서 실무에서는 "무효화가 전부 유실돼도 최대 30초 뒤에는 맞는 값"처럼 상한을 설계값으로 명시해 둔다 — TTL 숫자는 성능 튜닝 파라미터가 아니라 비즈니스와 합의한 불일치 허용치다.

7-1. 방어를 한 겹 더 — 재연결 시 L1 전체 clear 가산점

끊겨 있던 동안 무엇을 놓쳤는지는 알 수 없지만, "끊겨 있었다"는 사실 자체는 클라이언트가 안다. 그러면 놓친 후보를 특정하는 대신 전부 버리면 된다.

public void onSubscriptionReconnected() {
    // 구독 커넥션이 끊겼다 다시 붙었다 = "그 사이 무엇을 놓쳤는지 모른다"
    // 놓친 후보를 특정할 수 없으니 전부 버린다.
    localCache.invalidateAll();
}

대가는 재연결 직후 잠깐 L1 미스가 몰리는 것이고, 그 대가로 "끊긴 동안 놓친 것"의 대부분을 커버한다. 미스가 몰리는 것이 부담이라면 그 순간이 곧 캐시 스탬피드의 조건과 겹친다는 점까지 짚으면 좋다.

8. TTL 설계 — L1은 짧게, L2는 길게

둘 다 TTL이 있는데 왜 L1이 더 짧아야 하는가. 근거는 성능이 아니라 두 캐시의 무효화 신뢰도가 다르다는 데 있다.

L2는 전 인스턴스가 공유하는 한 곳이라 확실히 지울 수 있고, L1은 인스턴스마다 따로라 확실히 지울 수단이 없다. 그 차이가 그대로 TTL 길이의 차이가 된다.
외울 부등호
L1 TTL  <  L2 TTL  — 전형은 L1 수 초~수십 초 / L2 수 분~수 시간

9-1. 직접 만든 pub/sub vs client-side caching — 갈라 두면 가산점

직접 만든 pub/sub 브로드캐스트
  • 누가 감지하나 — 애플리케이션이 변경 지점마다 PUBLISH를 심는다. 변경 경로가 여럿이면(관리자 API·배치·마이그레이션 스크립트) 하나를 빠뜨리기 쉽고, 빠뜨린 경로의 변경은 영원히 전파되지 않는다.
  • 누구에게 보내나 — 채널 하나에 다 뿌린다. 내가 캐시하지도 않은 키의 무효화까지 받아서 버린다.
client-side caching 서버가 골라 보낸다
  • 누가 감지하나 — Redis 서버가 키 변경을 감지한다. 변경이 어느 경로로 일어나든 누락될 여지가 구조적으로 없다.
  • 누구에게 보내나 — 추적해 둔 "그 키를 캐시한 클라이언트"에게만. 내가 관심 있는 키만 받는다는 점이 결정적 차이다.
  • 키 하나씩이 아니라 접두사 단위로 알림받는 브로드캐스트 모드도 있다 — 서버 추적 부담이 줄지만 관심 없는 키의 알림도 받는다.
그래도 같은 한계 — 반드시 덧붙일 문장
둘 다 "연결이 끊긴 사이의 무효화는 보장하지 못한다"는 점은 같다.

그래서 방어도 동일하게 필요하다 — 끊김을 감지하면 로컬 캐시를 비우고, 짧은 TTL을 최후의 안전망으로 둔다. 새 기능이 안전망을 대체하지 못한다는 점을 말할 수 있어야 한다.

복잡도를 추가하지 않는 것도 유효한 설계 선택이다
하루에 한 번 바뀌는 설정에 pub/sub 구독자 + 발행 코드 + 재연결 처리를 붙이는 것은, 얻는 것에 비해 유지보수할 코드가 너무 많다. "몇 초 불일치 허용 + 변경 드묾"이라면 짧은 TTL 하나로 끝내는 것이 정답인 경우가 많다.

10. 도입 판단 — "많·안·짧·작" 넷을 다 만족해야 한다

2단 캐시는 문제를 하나 풀고(지연·부하) 문제를 하나 만든다(불일치·복잡도). 그래서 도입이 정당해지는 조건을 체크리스트로 두고 판단한다. 하나라도 어긋나면 Redis 단독(1단)이 정답이다.

안

작
크기가 작은가 힙에 인스턴스 수만큼 복제돼도 부담 없는 크기인가. 큰 객체는 GC 압박을 그 배수로 만든다.
면접 답변의 골격
"무조건 2단이 빠르니 좋다"가 아니라
"이 조건일 때만 복잡도가 정당화된다"는 판별 기준을 먼저 말한다.

10-1. 절대 넣으면 안 되는 데이터 시니어 변별

권한 · 세션 회수 보안 사고 경로

관리자가 계정을 차단했는데 어떤 노드의 L1에 옛 권한이 TTL 동안 남아 있으면, 차단된 사용자가 그 노드로 라우팅되는 동안 계속 접근할 수 있다. 여기서는 "짧은 불일치" = "짧은 무단 접근 시간"이라 허용치를 0으로 잡을 수밖에 없다.

결제 · 잔액 · 재고 차감 즉시 일관성

낡은 값이 잘못된 행동(품절 상품 구매, 초과 차감)을 유발한다. 애초에 캐시 후보가 아니다.

변경이 잦은 데이터 이득이 증발

무효화 전파가 상시 가동돼 히트율이 낮아진다. 이득은 사라지고 복잡도만 남는다.

히트율 낮은 롱테일 키 L1이 낭비

사용자별 키처럼 종류가 수백만이면 다시 조회되기 전에 축출되므로 L1이 사실상 놀고 있다.

11. 실무 감각 — "설정을 저장했는데 적용이 안 돼요"

상황
운영자가 관리자 화면에서 설정을 바꾸고 저장했다. 그런데 새로고침할 때마다 새 값이 보였다 안 보였다 한다. 애플리케이션 로그에는 아무 에러가 없고, DB에는 새 값이 정확히 들어가 있다. 인스턴스는 4대다.
1
먼저 "몇 번 중 몇 번"인지 센다 — 이 비율이 곧 진단이다 4번 중 1번만 새 값이면 1대만 갱신됐다는 뜻이고, 이건 전파가 아예 안 걸린 얼굴이다(변경을 처리한 그 인스턴스만 자기 L1을 갱신). 4번 중 3번이 새 값이면 한 대만 메시지를 놓친 얼굴이다 — 그 한 대가 방금 배포로 재시작했거나 커넥션이 끊겼던 인스턴스인지 확인한다.
2
Redis(L2)에 옛 값이 남아 있는지 본다 L2에 옛 값이 그대로면 문제는 L1이 아니라 L2 삭제 자체가 누락된 것이다. 반대로 L2는 비었는데 특정 인스턴스만 옛 값을 준다면 L1 무효화 전파의 문제로 좁혀진다. 계층을 하나씩 배제하는 순서가 2단 캐시 디버깅의 전부다.
3
이 변경 경로에 PUBLISH가 심어져 있는지 본다 관리자 API에는 있는데 배치나 마이그레이션 스크립트에는 없는 경우가 전형이다(§9-1). 직접 만든 pub/sub의 구조적 약점이 변경 경로 누락이라는 것을 알고 있으면 여기를 먼저 본다.
4
시간을 재서 "TTL 뒤에는 맞는가"를 확인한다 30초쯤 기다렸다가 전부 새 값이 되면 안전망은 정상이고 전파만 실패한 것이다. TTL이 지나도 계속 옛 값이라면 상황이 다르다 — L1 TTL이 없거나, 값을 영구 보관하는 자료구조에 따로 들고 있는 코드를 의심한다.
이 지식의 실행 가능한 형태
"버그처럼 보이는 현상"을 보고 설계상 예정된 불일치 창임을 알아보고,
몇 초 뒤에는 스스로 맞아야 한다는 상한까지 말할 수 있는가.

12. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 시니어 변별·가산점 문항은 정답 하나가 아니라 판단 기준을 말하는 연습을 한다.

pub/sub 무효화 메시지가 유실되면 어떻게 되나요?

놓친 노드의 L1에 낡은 값이 남고, 그 노드 스스로는 낡았다는 걸 알 수 없어 불일치가 로컬 TTL 만료까지 지속된다. pub/sub이 저장도 재전달도 하지 않는 at-most-once 방송이기 때문이다.

그래서 방어를 겹으로 둔다.

  1. 짧은 로컬 TTL — 불일치 지속 시간의 상한을 만든다. 이것이 없으면 상한 자체가 없다.
  2. 구독 재연결 시 L1 전체 clear — 끊겨 있던 동안 놓친 것을 특정할 수 없으니 전부 버린다(§7-1).
  3. 유실이 정말 치명적이면 전파 채널을 바꾼다 — 버전 키 폴링처럼 가져오는 방식이나, 메시지가 저장되는 Redis Streams로 옮긴다.

한 문장으로 정리하면 "pub/sub 전파는 최적화이고, 정합성의 보장은 TTL이 진다"는 역할 분리다.

로컬(L1) TTL은 Redis(L2) TTL보다 길게 잡나요, 짧게 잡나요?

짧게 잡는다. 근거는 성능이 아니라 두 캐시의 무효화 신뢰도가 다르다는 데 있다.

  • L2는 전 인스턴스가 공유하는 한 곳이라 DEL 한 번이면 확실히 지워진다 → 불일치 상한이 필요 없다.
  • L1은 인스턴스마다 따로라 무효화가 방송에 의존하고, 그 방송은 유실될 수 있다 → L1의 불일치 상한이 곧 L1 TTL이다.

전형적인 구성은 L1 수 초~수십 초 / L2 수 분~수 시간이다. 거꾸로 L1을 길게 잡으면 역전이 생긴다 — L2는 이미 갱신됐는데 L1이 옛 값을 더 오래 붙들고 서빙하므로, L2를 갱신한 의미가 그 인스턴스에서 사라진다.

캐시 무효화(evict)와 캐시 갱신(put) 중 무엇을 전파해야 하나요?

삭제(evict)를 전파한다.

새 값을 메시지에 실어 각 노드가 자기 L1에 put하게 만들면 순서 역전 문제가 생긴다. 값을 연속으로 두 번 바꿔 메시지가 두 개 나갔는데 첫 번째가 두 번째보다 늦게 도착하면, 늦게 도착한 옛 값이 이미 들어와 있던 새 값을 덮어쓴다. 그리고 이 잘못된 값은 다음 변경이나 TTL까지 살아남는다.

삭제는 이 문제가 없다. 몇 번을 어떤 순서로 적용해도 결과가 "그 키가 없음"으로 같기 때문(멱등)이다. 비어 있는 자리는 다음 조회가 L2/DB에서 최신 값으로 채운다.

"캐시 갱신 vs 삭제"라는 일반론과 같은 논리인데, 전파 채널에는 순서 보장이 없다는 조건이 더해져 더 극적으로 적용되는 셈이다.

이 구조를 도입하면 안 되는 데이터는 무엇인가요? 시니어 변별

즉시 일관성이 요구되는 데이터다. 결제·잔액·재고 차감이 대표이고, 특히 위험한 것이 권한/세션 회수다.

관리자가 계정을 차단했는데 어떤 노드의 L1에 옛 권한이 TTL 동안 남아 있으면, 차단된 사용자가 그 노드로 라우팅되는 동안 계속 접근할 수 있다. 성능 최적화가 보안 사고로 이어지는 경로다. 세션·권한은 "짧은 불일치"가 곧 "짧은 무단 접근 시간"이라 허용치를 0으로 잡을 수밖에 없다.

그 밖의 부적합 대상도 이유가 각각이다.

  • 변경이 잦은 데이터 — 무효화 전파가 상시 가동돼 히트율이 낮아지고, 이득은 사라지고 복잡도만 남는다.
  • 큰 객체 — 인스턴스 수만큼 힙에 복제되므로 GC 압박을 그 배수로 만든다.
  • 히트율이 낮은 롱테일 키 — 다시 조회되기 전에 축출되므로 L1이 사실상 낭비다.

핵심은 판별을 기술이 아니라 요구사항으로 한다는 점이다. "이 데이터의 불일치 상한(L1 TTL)을 비즈니스가 견딜 수 있는가" 한 문장으로 판단한다는 것이 시니어의 답이다.

Redis 6의 client-side caching은 직접 구현한 pub/sub 무효화와 뭐가 다른가요? 가산점

차이가 두 가지다.

첫째, 무효화를 누가 감지하는가. 직접 구현은 애플리케이션이 변경 지점마다 PUBLISH를 심어야 한다. 변경 경로가 여럿이면(관리자 API, 배치, 마이그레이션 스크립트) 하나를 빠뜨리기 쉽고, 빠뜨린 경로로 값이 바뀌면 그 변경은 영원히 전파되지 않는다. client-side caching은 Redis 서버가 키 변경을 감지하므로 변경 경로 누락이 구조적으로 없다.

둘째, 누구에게 보내는가. 직접 구현은 채널 하나에 뿌리는 브로드캐스트라 모든 인스턴스가 모든 무효화를 다 받는다. client-side caching은 서버가 각 클라이언트가 어떤 키를 읽어 갔는지 추적해 두었다가 그 키를 캐시한 클라이언트에게만 밀어준다 — "내가 관심 있는 키만" 받는다는 점이 결정적 차이다.

대신 전제와 비용이 있다. RESP3와 클라이언트 라이브러리 지원이 필요하고, 서버가 추적 정보를 들고 있는 부담이 생긴다.

그리고 마지막 문장이 중요하다 — 둘 다 "연결이 끊긴 사이의 무효화는 보장하지 못한다"는 한계는 같다. 그래서 방어는 동일하게 필요하다: 끊김을 감지하면 로컬 캐시를 비우고, 짧은 TTL을 최후의 안전망으로 둔다.

Redis가 죽으면 2단 캐시는 어떻게 동작하나요? 추가

좋은 면과 나쁜 면이 동시에 나타난다. 둘 다 말해야 답이 닫힌다.

  • 좋은 면 — L1이 완충재가 된다. 1단 캐시라면 Redis가 죽는 순간 전 트래픽이 DB로 직행해 DB까지 무너진다. 2단이면 L1에 살아 있는 데이터로 당분간 버틸 수 있다.
  • 나쁜 면 — 무효화 전파도 함께 죽는다. pub/sub 채널이 바로 그 Redis 위에 있기 때문이다. 즉 Redis 장애 구간에서는 정합성 장치가 TTL 하나만 남는다.

그래서 두 가지를 덧붙이면 좋다. 첫째, L1 TTL이 만료되면 결국 L2를 보러 가야 하므로 완충은 TTL 길이만큼만 유효하다 — Redis 조회 실패 시의 폴백(DB로 갈지, 낡은 값을 더 쓸지)을 미리 정해 둬야 한다. 둘째, Redis 복구 직후에는 구독 재연결 시 L1 전체 clear(§7-1)가 특히 중요하다 — 장애 구간에 놓친 무효화가 그때 한꺼번에 정리된다.

무효화 메시지를 받아 전 인스턴스가 동시에 L1을 비운 직후, 그 인기 키에 요청이 몰리면? 추가

전 인스턴스가 "같은 순간에" 같은 키의 미스를 본다. 브로드캐스트라서 무효화가 거의 동시에 도달하기 때문이다. 로컬 캐시가 흡수해 주던 트래픽이 그 순간 한꺼번에 L2로 쏟아진다.

  • L2에 값이 있으면 여기서 멈춘다 — Redis가 순간적으로 스파이크를 맞지만 대개 감당한다.
  • 문제는 L2도 방금 삭제된 경우다(정석 순서가 "L2 삭제 → 방송"이므로 기본적으로 이 상황이다). 그러면 전 인스턴스가 DB로 직행한다 — 캐시 스탬피드와 같은 얼굴이다.

대응은 스탬피드의 도구를 그대로 쓴다 — 재계산을 1회로 묶는 락(single flight), 논리적 만료, 또는 변경 측이 삭제 대신 L2를 새 값으로 갱신해 두어 DB까지 내려가지 않게 하는 것이다. 다만 마지막 방법은 L2 갱신과 무효화 순서 문제를 다시 불러오므로, 재계산이 비싼 키에만 선택적으로 쓴다.

이 질문의 요지는 "무효화가 잘 전파될수록 미스가 동기화된다"는 역설이다. 전파의 성공이 부하 스파이크를 만든다는 점을 짚으면 좋다.

2단 캐시를 넣었는데 L1 히트율이 20%밖에 안 나옵니다. 무엇을 의심하나요? 추가

의심할 곳이 넷이고, "많·안·짧·작" 체크리스트를 역순으로 되짚는 것이 가장 빠르다.

  1. 키 종류가 너무 많다(롱테일) — maximumSize 안에 들어오기 전에 축출된다. 캐시 대상 키의 카디널리티부터 센다. 이 경우 L1은 구조적으로 맞지 않는다.
  2. TTL이 너무 짧다 — 다음 조회가 오기 전에 만료된다. 키당 조회 간격과 TTL을 나란히 놓고 비교한다.
  3. 변경이 잦아 상시 무효화 — 전파가 계속 들어와 L1이 계속 비워진다. "안 바뀌는가" 조건을 잘못 판정한 경우다.
  4. 인스턴스가 너무 많다 — 전체 트래픽은 커도 인스턴스당 같은 키를 다시 만나는 빈도가 낮으면 L1은 채워지기만 하고 쓰이지 않는다. L1 히트율은 전체 QPS가 아니라 인스턴스당 QPS가 결정한다는 점이 자주 놓치는 부분이다.

확인 수단도 말하면 좋다 — Caffeine의 recordStats()로 히트율·축출 수·평균 적재 시간을 지표로 내보내면 위 넷 중 어느 것인지 대부분 바로 갈린다. 추정이 아니라 측정이 되는 지점이다.

2단 캐시를 넣기 전에 먼저 시도해 볼 것은 없나요? 추가

있다. 아끼려는 대상이 "Redis의 일"이 아니라 "왕복 그 자체"라면, 왕복 횟수부터 줄이는 것이 순서상 먼저다.

  • 요청당 조회 횟수 줄이기 — 같은 값을 한 요청 안에서 20번 읽고 있다면, 요청 스코프에서 한 번만 읽어 재사용하는 것만으로 왕복 20회가 1회가 된다. 노드 간 불일치를 전혀 만들지 않는다는 점이 결정적 장점이다(그 요청이 끝나면 사라지므로).
  • 여러 키를 한 번에 — 루프 GET 대신 MGET이나 pipeline으로 묶으면 왕복 N회가 1회가 된다.

이 둘로 충분하지 않을 때 — 즉 요청 하나짜리로는 줄일 수 없는, 전 요청에 걸친 초고빈도 읽기일 때 비로소 2단 캐시가 정당해진다. "복잡도가 낮은 수단부터 순서대로 시도했는가"를 보여주는 답변이라 그 자체로 점수가 된다.

한 줄 요약
2단 캐시는 Redis 왕복조차 병목인 초고빈도 읽기를 JVM 안(Caffeine)에서 끝내 지연과 Redis 부하를 없애는 대신 "노드마다 값이 다를 수 있다"는 불일치를 지불하는 구조로, 무효화는 Redis pub/sub 브로드캐스트로 전파하되 pub/sub은 유실 시 재전달이 없어 불완전하므로 짧은 L1 TTL을 불일치의 상한이자 최후의 안전망으로 반드시 함께 두고 — 애초에 이 복잡도는 "초고빈도 읽기 + 변경 드묾 + 짧은 불일치 허용" 조건을 만족하는 데이터에서만 정당화된다.
