선착순 쿠폰 10만 장 설계 — 판정은 Redis 원자 연산으로, 원장은 DB로

원본: interview-questions/knowledge/05-redis-caching/17-flash-sale-coupon-issuance-design.md

30초 카드 — 골격 한 줄 + 두 축
질문: "선착순 쿠폰 발급 10만 건을 Redis로 설계해보세요. 정확성(중복/초과 발급 방지)과 내구성을 어떻게 보장하나요?" — 기법을 나열하지 말고 역할을 둘로 쪼개는 것부터 말하면 첫 답변이 끝난다.
Redis = 판정기"발급 가능/불가"를 초고속으로 결정한다. 커넥션도 디스크도 붙잡지 않는다. 잃어도 되는 것만 둔다.
DB = 원장(최종 진실)발급 사실을 보관한다. 판정이 끝난 결과만 비동기로 받으므로 경합이 없다. 유니크 제약이 최종 방어선.
① 정확성중복은 SADD 0/1, 초과는 SCARD — 둘을 Lua 하나로
② 내구성이벤트 → DB 원장 + UNIQUE, 유실 시 fail-closed
③ 분산 락 없음잠글 틈이 없다 — 병목과 실패 모드만 추가
핵심 관전 포인트 — 그대로 말하기
역할을 둘로 쪼개는 것이 설계의 골격이다 — Redis는 "발급 가능/불가"를 초고속으로 판정하는 판정기, DB는 발급 사실을 보관하는 원장(최종 진실). ① 정확성: 중복 발급은 사용자 Set(SADD의 0/1 반환)으로, 초과 발급은 발급 수 카운트로 막되, "확인하고 발급"이라는 두 동작을 Lua 스크립트 하나로 원자화한다 — Set 하나가 중복 방지와 카운트(SCARD)를 겸하면 카운터 불일치 여지도 사라진다. 분산 락은 쓰지 않는다 — Redis 명령 자체가 원자적이라 잠글 대상이 없고, 락은 병목과 실패 모드만 추가한다. ② 내구성: Redis는 어떤 설정으로도 유실 가능성이 남으므로(AOF everysec의 마지막 ~1초, 비동기 복제 failover) 발급 사실을 이벤트로 흘려 DB에 비동기 반영하고, DB의 유니크 제약을 최종 방어선으로 삼는다. Redis 데이터가 유실되면 발급을 멈추고(fail-closed) DB 원장에서 Set을 재구축한 뒤 재개한다.
출제 의도 — 지식의 보유가 아니라 조합을 본다
rationale은 이렇게 적고 있다 — "정확성(원자적 카운트), 내구성(Redis 유실 시), 공정성, DB 반영의 비동기화까지 — 한 문제에 이 섹션 전체 지식을 조합해야 한다." 그래서 채점 지점은 개별 명령어가 아니라 ① 경합 지점을 원자 연산으로 접는 판단 ② "Redis는 유실될 수 있다"는 전제에서 출발하는 내구성 설계 ③ 판정 경로와 영속화 경로를 분리하고 그 사이의 실패를 처리하는 구성력이다. SADD를 안다고 점수가 나지 않고, §3의 구조 그림과 §10의 복구 절차를 시간 순서로 말할 수 있어야 점수가 난다.

1. 부하의 모양 — "10만 번의 쓰기"가 아니라 "수백만 번의 판정"

쿠폰 10만 장 이벤트에 들어오는 요청은 10만 건이 아니다. 수십만에서 수백만 건이 수 초에서 수 분 안에 몰린다. 발급받지 못할 사람들도 전부 요청을 보내기 때문이고, 실패하면 다시 누르기 때문이다.

설계의 전제 — 여기서부터 시작한다
성공하는 요청보다 거절되는 요청이 훨씬 많다.
그 거절을 얼마나 싸게 처리하느냐가 설계의 절반이다.

이 문장을 먼저 깔면 뒤의 모든 선택이 자연스럽게 이어진다 — 판정을 O(1) 원자 연산으로 접는 이유(§5)도, 소진 플래그를 API 서버 앞으로 당기는 이유(§11)도 전부 "거절 한 건의 단가를 낮춘다"는 같은 목표에서 나온다.

2. DB 직행이 무너지는 메커니즘 — 정확성이 아니라 처리량이 죽는다

가장 단순한 구현부터 본다. 그리고 이 문장이 틀려서 배제되는 게 아니라는 점을 먼저 짚어야 한다.

-- 모든 요청이 이 한 행을 두드린다
UPDATE coupon_event SET issued = issued + 1
WHERE  id = 1 AND issued < 100000;
이 SQL은 정확하다 — 그래서 반박이 필요하다
issued = issued + 1과 issued < 100000 검사가 한 문장 안에 있으므로 초과 발급은 나지 않는다. PostgreSQL은 이 행에 배타 락을 걸고 갱신하며, 영향 행 수가 0이면 소진이라는 뜻이다. "DB로는 정확성이 안 지켜져서"라고 말하면 틀린 답이다. 무너지는 것은 처리량이다.

같은 행을 갱신하려는 트랜잭션은 앞선 트랜잭션이 커밋할 때까지 그 행의 락을 기다린다. 즉 모든 요청이 단일 행 락 위에서 한 줄로 직렬화된다. 수백만 건이 한 줄로 서면 뒤쪽은 사실상 영원히 못 들어온다. 그리고 진짜 사고는 그다음이다.

락 대기가 커넥션 점유로 번지고, 커넥션 고갈이 전체 장애로 번진다. 쿠폰 이벤트 하나가 로그인·주문까지 끌고 들어가는 경로가 이것이다.
방향 전환 — 이 한 줄이 §3의 골격을 낳는다
해법은 "더 빠른 DB를 고른다"가 아니라
"경합과 영속을 서로 다른 시스템에 배치한다"이다.
경합 지점(판정)Redis 메모리. 원자 연산 하나로 끝난다. 커넥션을 붙잡지 않는다.
영속 지점(원장)DB. 판정이 끝난 결과만 비동기로 받아 쌓는다. 경합이 없다.

3. 골격 — 판정기와 원장의 분리 (전체 구조)

답변의 첫 그림은 이것이다. 요청 하나가 지나는 길을 동기 구간과 비동기 구간으로 나눠 그리면, 뒤에 나올 모든 세부 결정이 이 그림 위의 한 점으로 설명된다.

보라색 점선 왼쪽이 사용자가 체감하는 전부다. 오른쪽은 늦어도 되고, 실패해도 재시도된다 — 이 경계를 그은 것이 설계의 본체다.

3-1. 요청 하나의 시간 순서 — 대기열 → 판정 → 응답 → 비동기 발급

사용자는 ⑤에서 이미 끝났다. ⑥⑦이 몇 초 늦어도, 컨슈머가 잠시 죽어도 발급 사실은 큐에 남아 있다 — "판정 즉시 확정, 원장 반영은 지연 가능"이 이 설계가 사용자와 맺는 계약이다.
면접에서 이 순서로
기법이 아니라 경계선부터 말한다 — "동기 판정 / 비동기 원장"
그다음에 각 구간의 정확성과 실패 처리를 채운다.

SADD·Lua·유니크 제약은 전부 이 그림 위의 한 점이다. 그림 없이 기법부터 나열하면 "아는 것을 쏟아낸 답변"이 되고, 그림을 먼저 그리면 뒤의 모든 이야기가 그 위에 얹힌다.

4. 정확성① — SADD의 0/1: 확인과 선점을 한 걸음으로

막아야 할 것은 둘이다. 중복 발급(한 사람이 두 장 받는 것)과 초과 발급(총량이 10만 장을 넘는 것). 둘 다 "확인하고 발급"이라는 두 걸음 사이에서 새어 나간다.

Redis가 싱글 스레드라 안전하다? — 절반만 맞는 말이다
명령 하나는 원자적이지만, 명령과 명령 사이는 아무것도 보장하지 않는다. 오히려 처리 속도가 빠른 만큼 그 틈에 더 많은 요청이 들어온다. check-then-act를 여러 문장으로 쓰면 뚫리는 것은 DB든 Redis든 같은 원리다.
거꾸로 말하면, SISMEMBER로 확인한 뒤 SADD하는 코드는 SADD가 이미 원자적으로 해주는 일을 굳이 두 걸음으로 되돌린 것이다. 조회 한 번 느려지는 게 아니라 정확성이 깨진다.
암기 — 이 시리즈를 관통하는 한 패턴
명령을 나누지 말고, 조건을 명령 안에 실어 보낸다.
R
SADD key member → 1 / 0 "없으면 넣기"와 "이미 있는지 확인"이 한 명령. 1 = 내가 선점, 0 = 중복.
R
SET key val NX → OK / nil 분산 락의 핵심(16번 문서). "없을 때만 쓴다"가 한 명령 안에 있다.
R
INSERT … ON CONFLICT DO NOTHING DB 쪽의 같은 발상(§9). 유니크 제약과 결합하면 확인과 선점이 DB 안에서 한 번에 일어난다.

셋 다 "확인 → 행동"의 틈을 없애는 같은 기법이다. 하나를 설명하면서 나머지 둘을 함께 묶으면, 암기가 아니라 원리를 쥔 답변이 된다.

5. 정확성② — 남은 조건은 수량, 그래서 Lua로 묶는다

중복은 SADD 하나로 해결됐다. 그런데 조건이 하나 더 있다. "10만 장을 넘지 않았는가"다. 이 판정에는 지금까지 몇 장 나갔는지를 읽는 명령이 따로 필요하므로 다시 명령이 둘이 된다.

SCARD coupon:{1}:users   → 99,999 (아직 남았다)
   ← 이 틈에 다른 요청 수백 개가 같은 판정을 통과한다
SADD  coupon:{1}:users u1

두 명령 사이가 또 뚫린다. 그래서 두 명령을 Redis 서버 안에서 한 덩어리로 실행시켜야 하고, 그 도구가 Lua 스크립트다. Redis는 Lua 스크립트를 실행하는 동안 다른 클라이언트의 명령을 끼워 넣지 않는다.

중
① 중복 검사
SISMEMBER → 이미 받았나
수
② 수량 검사
SCARD → 아직 남았나
선
③ 선점
SADD → 자리를 잡는다

"중·수·선" — 이 세 줄의 순서와 세 줄이 한 덩어리라는 사실만 기억하면 스크립트는 그 자리에서 복원된다.

✕ before — 애플리케이션에서 나눠 실행
// 왕복 3번, 그 사이는 무방비
if (redis.sIsMember(key, userId)) return DUP;
if (redis.sCard(key) >= 100000) return SOLD_OUT;
// ← 여기서 수백 개가 동시에 통과한다
redis.sAdd(key, userId);
return OK;

// 결과: 초과 발급 · 중복 발급 둘 다 가능
// 트래픽이 적을 땐 "잘 되는 것처럼" 보인다
✓ after — Lua 한 덩어리 (왕복 1번, 원자)
-- KEYS[1]=coupon:{1}:users  ARGV[1]=userId  ARGV[2]=100000
if redis.call("SISMEMBER", KEYS[1], ARGV[1]) == 1 then
    -- 중복과 소진을 구분해 응답하려고 이 검사를 먼저 둔다
    return -1
end
if redis.call("SCARD", KEYS[1]) >= tonumber(ARGV[2]) then
    -- 집합 크기가 곧 발급 수다
    -- ARGV는 항상 문자열 → tonumber 필요
    return 0
end
redis.call("SADD", KEYS[1], ARGV[1])
return 1
-- 세 명령이 한 스크립트 안 → 검사와 추가 사이에 틈이 없다
소진된 뒤에 같은 사용자가 다시 눌러도 "이미 받으셨습니다"가 나가야 하므로 중복 검사가 앞이다. SADD 반환값만으로도 원자성은 같지만, 그 순서를 바꾸면 사용자에게 나가는 문구가 바뀐다.

5-1. KEYS와 ARGV — 왜 키를 굳이 따로 넘기나

EVAL <스크립트> 1 coupon:{1}:users u1 100000
                ^ 뒤따르는 인자 중 앞의 몇 개가 "키"인지를 알려주는 숫자
                  → 키 1개:  KEYS[1] = "coupon:{1}:users"
                  → 나머지:  ARGV[1] = "u1",  ARGV[2] = "100000"
                     (Lua의 배열은 1부터 센다)
키를 ARGV에 섞으면? Cluster에서 깨진다

Redis Cluster는 이 스크립트를 어느 노드로 보낼지 정해야 하는데, 그 판단을 KEYS에 적힌 키로 한다. 키를 ARGV에 숨기면 엉뚱한 노드로 가서 깨진다. 단일 노드에서는 아무 문제 없이 동작하다가 Cluster로 옮기는 순간 터지는 종류의 버그다.

coupon:{1}:users의 중괄호 해시 태그 · 가산점

Cluster는 키를 해시해 슬롯을 정하는데, 중괄호가 있으면 중괄호 안의 부분만 해시한다. 그래서 coupon:{1}:users와 coupon:{1}:soldout은 반드시 같은 슬롯, 같은 노드에 놓인다. 스크립트가 여러 키를 만질 때 Cluster로 전환해도 깨지지 않게 미리 깔아두는 장치다.

5-2. 왜 MULTI/EXEC가 아니라 Lua인가

한 문장 반박
MULTI는 명령을 큐에 모아 한꺼번에 실행할 뿐 중간 조회 결과로 분기할 수 없다. "SCARD 결과가 한도 미만이면 SADD"라는 조건문을 표현할 방법이 없다. check-then-act를 원자화하려면 WATCH 기반 낙관적 재시도나 Lua가 필요한데, 경합이 극심한 이 시나리오에서 WATCH는 재시도 폭풍이 된다. (상세: 27번 — MULTI/EXEC와 WATCH vs Lua)
Lua로 묶을 때 반드시 함께 말할 안전 조건
이 스크립트가 쓰는 세 명령이 모두 O(1)이라는 점.

SISMEMBER·SCARD·SADD가 전부 상수 시간이라, 스크립트가 Redis의 싱글 스레드를 붙잡는 시간이 집합 크기와 무관하게 일정하다. 이 성질이 없으면 — 예컨대 안에서 SMEMBERS나 KEYS를 부르면 — Lua로 묶는 순간 그 스크립트가 서버 전체를 멈추는 흉기가 된다. "원자성을 얻는 대신 무엇을 조심해야 하는가"까지 말하는 것이 이 절의 채점 포인트다.

6. Set 하나가 카운터를 겸하게 하는 이유와 그 대가

발급 수를 세는 방법은 둘이다. INCR로 올리는 별도 카운터 키를 두거나, 집합의 크기(SCARD)를 그대로 발급 수로 쓰거나. 여기서는 후자를 택했다.

선택의 이유 — 한 줄
Set 하나가 유일한 진실이면, 어긋날 대상 자체가 없다.

카운터를 따로 두면 "Set에는 들어갔는데 카운터가 안 올라간" 상태가 존재할 수 있고, 그 순간 시스템에는 서로 다른 두 개의 답이 생긴다. Lua로 묶여 있으니 스크립트 안에서는 어긋나지 않겠지만 — 어긋남은 스크립트 밖에서 온다.

"스크립트 밖"이 구체적으로 어디인가
1
장애 복구로 Set을 DB 원장에서 재구축할 때 (§10) 카운터도 별도로 다시 계산해 맞춰야 한다. 하나를 빠뜨리면 그때부터 두 값이 어긋난 채로 운영된다.
2
운영자가 수동 보정을 할 때 특정 사용자를 Set에서 빼는 작업을 해도 카운터는 따라 내려가지 않는다.
3
마이그레이션·부분 만료 한쪽만 사라질 수 있다. 그러면 두 값을 맞추는 로직도, 어긋났을 때의 대사 절차도 전부 새로 필요해진다.
시간 문제없음

SCARD는 O(1)이다. Redis가 집합의 원소 개수를 따로 들고 있어서 세지 않고 바로 답한다. 10만이든 1000만이든 같은 시간이다.

메모리 멤버 수에 비례

카운터는 정수 하나지만 Set은 발급받은 사용자 ID를 전부 들고 있어야 한다. 10만 멤버라면 메가바이트 단위에 그치므로 이 설계에서는 문제가 아니다. 다만 이 비례가 다음 절의 상한을 만든다.

6-1. 이 설계가 감당하는 규모의 상한 — big key 경계 시니어 변별

10만 멤버 Set은 걱정할 크기가 아니다. 그러나 이 설계를 그대로 수백만·수천만 규모로 늘리면 그 Set은 big key가 된다. big key란 값 하나가 지나치게 큰 키를 말하고, 문제는 Redis가 싱글 스레드라는 점에서 나온다 — 그 키를 통째로 훑는 명령이 들어오면 그 명령이 끝날 때까지 다른 모든 요청이 대기한다.

위험한 곳은 판정 경로가 아니라 그 바깥이다
발급 판정은 O(1) 명령만 쓰므로 안전하다. 사고는 운영 명령에서 난다.
· 상태 확인 — 운영자가 SMEMBERS를 치는 순간 수백만 멤버를 전부 직렬화하는 동안 서버가 멈춘다. 커서로 조금씩 훑는 SSCAN을 쓴다.
· 이벤트 종료 정리 — DEL도 큰 키의 메모리를 그 명령 안에서 회수하므로 같은 일이 생긴다. Redis 4.0에서 추가된 UNLINK는 키를 즉시 네임스페이스에서 떼어내고 메모리 회수는 백그라운드 스레드에 맡긴다. (상세: 23번 — big key의 위험과 UNLINK)
이 설계의 상한을 정확히 말하는 법
상한은 "발급 대상 수"가 아니라
"Set 하나가 커졌을 때 그 키를 만지는 모든 경로"에 있다.

규모가 더 커지면 사용자 ID를 여러 Set으로 나누거나(그러면 SCARD 겸용을 포기해야 한다), 중복 방지 자체를 DB 유니크 제약 쪽으로 옮기는 재설계가 필요해진다. "10만에서는 최선인 선택이 1000만에서는 아니다"를 조건과 함께 말하는 것이 이 절의 값어치다.

7. 분산 락으로 감싸지 않는 이유 — 먼저 말해야 하는 쪽

분산 락을 쓰지 않는 이유를 먼저 말하는 것이 이 문항의 변별 지점 중 하나다. "동시성 제어니까 락"이라는 반사작용을 끊을 수 있는지를 본다.

한 문장 — 이대로 말한다
잠글 틈이 존재하지 않는다.

경합 지점(중복 확인 + 수량 확인 + 기록)이 이미 Lua 한 덩어리로 원자화되어 있고, Redis는 그 스크립트를 실행하는 동안 다른 명령을 끼워 넣지 않는다. 락이란 "여러 명령 사이의 틈을 막는 장치"인데, 막을 틈이 없으면 락은 할 일이 없다.

얹으면 잃는 것 ① 처리량

락 획득 왕복 한 번, 해제 왕복 한 번이 매 요청마다 추가된다. 판정 자체(O(1) 명령 3개)보다 락 처리가 더 비싸진다. §1에서 말한 "거절 단가"가 몇 배로 뛴다.

얹으면 잃는 것 ② 실패 모드

TTL 만료로 락이 남에게 넘어가거나, 해제가 누락되어 이벤트 자체가 멈추는 상황이 새로 생긴다. 워치독·소유자 검증 같은 부품도 따라 들어온다(16번 문서).

판단 순서를 그대로 적용하면 1단계에서 끝난다
분산 락 문서의 순서는 "한 문장짜리 원자 연산으로 못 푸나?"부터 묻는 것이다. 이 문제는 그 답이 "된다"이므로 더 내려갈 필요가 없다. 분산 락이 정당한 자리는 여러 시스템에 걸친 절차를 조정할 때이지, 단일 Redis 안의 원자 연산으로 끝나는 문제가 아니다.

8. 내구성① — "Redis는 유실될 수 있다"에서 출발한다

Redis는 데이터를 메모리에 두고 디스크에는 부차적으로 남긴다. 그래서 어떤 설정을 골라도 유실 가능성이 남는다. 선택지마다 무엇을 잃는지부터 정리한다.

영속화 설정동작크래시 시 잃는 것이 시나리오에서
RDB 스냅샷주기적으로 메모리 전체를 파일로 떠둔다마지막 스냅샷 이후 발급 기록 전부통째로 사라짐 — 단독으로는 논외
AOF everysec쓰기 명령을 기록하되 fsync는 1초에 한 번마지막 약 1초 분량평소엔 무시할 양이지만, 이 트래픽에서 1초는 수천 건
AOF always매 쓰기마다 fsync유실 최소화모든 쓰기가 디스크를 기다림 → "Redis로 받는 이유" 자체가 약해진다
복제 + failover마스터가 응답한 뒤 비동기로 레플리카에 전달복제 전에 죽으면 그 쓰기들AOF 설정과 무관하게 남는 구멍 — 아래에서 따로 본다

8-1. failover가 카운터를 과거로 되돌리는 메커니즘 시니어 변별

전제 — 이 한 줄이 시나리오를 만든다
Redis 복제는 비동기다. 마스터가 보낸 OK는
"복제됐다"는 뜻이 아니다.

마스터는 클라이언트에게 먼저 응답하고 그 뒤에 레플리카로 내용을 흘려보낸다. 그래서 어느 순간에도 "마스터에는 있지만 아직 레플리카에는 없는 쓰기"가 존재한다.

"응답은 나갔는데 기록은 없는 상태"가 핵심이다. 마스터가 응답한 OK는 취소되지 않는다 — 그런데 시스템의 기억에서는 그 발급이 사라졌다. 이 한 상태가 초과 발급과 중복 발급을 동시에 만든다.
WAIT으로 막을 수 있지 않나요? — 정확한 표현을 준비해 둔다
Redis의 WAIT 명령은 지정한 수의 레플리카가 쓰기를 확인할 때까지 응답을 미룬다. 구멍을 좁히는 수단은 된다. 그러나 응답 지연을 사게 되고, 그마저도 모든 failover 시나리오를 막아주는 완전한 보장은 아니다. 그래서 답은 "복제 지연 창을 좁힐 수는 있어도 없앨 수는 없다"가 정확하다.
내구성 설계의 출발점
"AOF 켰으니 안전"이 아니라
유실이 곧 정확성 붕괴로 직결되는 구조임을 인정하는 것.

Set이 과거로 돌아가 SCARD가 줄면 초과 발급, 이미 받은 사용자가 Set에서 사라지면 중복 발급이다. §4·§5에서 애써 만든 정확성이 §8의 유실 한 번으로 전부 무효가 된다 — 그래서 다음 절의 구조가 필요하다.

9. 내구성② — 원장 경로와 유니크 제약이라는 최종 방어선

Redis가 유실될 수 있다면, 잃어도 되는 것만 Redis에 두면 된다. 발급 사실의 최종 진실은 DB에 둔다 — §3의 그림에서 보라색 점선 오른쪽이 담당하는 일이다.

①
판정 — §5의 Lua 사용자는 여기서 바로 "발급 완료" 응답을 받는다. DB를 기다리지 않으므로 응답이 밀리초 단위로 끝난다.
②
이벤트 적재 — 큐(Kafka 또는 Redis Streams) Redis Streams: 판정 Lua 안에서 XADD까지 한 덩어리로 묶을 수 있어 "판정은 됐는데 이벤트가 안 남는" 틈이 사라진다. 대신 내구성이 다시 Redis에 묶인다. Kafka: 내구성은 강해지지만 "Lua 성공 후 발행 실패"라는 틈이 새로 생긴다 — 발행 재시도와 ③의 멱등성으로 메운다.
③
원장 기록 — 컨슈머가 DB에 INSERT (coupon_event_id, user_id) 유니크 제약이 있으므로 같은 이벤트가 두 번 소비돼도(재시도, 유실 후 재구축) 중복 발급으로 이어지지 않는다 — 소비가 멱등해진다. 
CREATE TABLE coupon_issue (
    id              bigserial   PRIMARY KEY,
    coupon_event_id bigint      NOT NULL,
    user_id         bigint      NOT NULL,
    issued_at       timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT uq_coupon_issue UNIQUE (coupon_event_id, user_id)
);
-- 이 제약이 최종 방어선이다. 앞단의 Redis 판정이 어떤 이유로 뚫려도
-- 같은 사용자에게 같은 이벤트의 쿠폰이 두 줄 들어가는 일은 DB 가 거부한다.
✕ before — 조회로 확인한 뒤 INSERT
SELECT 1 FROM coupon_issue
 WHERE coupon_event_id = 1 AND user_id = 77;
-- 없네? 넣자
--   ← 이 사이에 같은 이벤트가 또 소비되면
INSERT INTO coupon_issue (coupon_event_id, user_id)
VALUES (1, 77);

-- §4에서 본 check-then-act 그대로다
-- 확인과 삽입 사이가 뚫린다
✓ after — 확인 없이 넣고, 충돌은 제약이 흡수
INSERT INTO coupon_issue (coupon_event_id, user_id)
VALUES (1, 77)
ON CONFLICT (coupon_event_id, user_id) DO NOTHING;

-- 이미 있으면 예외 없이 조용히 흡수된다
-- 확인과 선점이 DB 안에서 한 번에, 원자적으로
-- → 컨슈머 재시도가 몇 번 일어나도 결과가 같다(멱등)
여기서 말할 수 있어야 하는 한 줄
락이 아니라 제약이 최종 진실을 지킨다.

그리고 이 ON CONFLICT는 §4의 SADD 반환값과 정확히 같은 발상이다 — 확인과 선점을 한 걸음으로 접는 것. Redis 쪽 판정과 DB 쪽 방어선이 같은 원리로 설계됐다고 말하면 답변이 한 덩어리로 묶인다.

10. fail-closed와 복구 절차 — 각 계층의 실패는 어떻게 흡수되는가

구조를 그렸다면 다음은 "그래서 각 지점이 죽으면 무슨 일이 나는가"다. 이 답이 설계의 핵심이다.

컨슈머 · DB 일시 장애 흡수됨

이벤트가 큐에 남아 있으므로 복구 후 이어서 처리된다. 발급 응답은 이미 나갔지만 원장 반영이 늦을 뿐, 발급 사실을 잃지는 않는다.

Redis 유실 (failover 포함) 즉시 발급 중단

판정의 근거가 사라졌으므로 발급을 즉시 멈춘다. 이 판단의 이름이 fail-closed다.

10-1. fail-closed란 무엇인가 — 이름은 문에서 왔다

fail-closed는 시스템이 정상 판단을 할 수 없는 상태가 됐을 때 허용이 아니라 차단 쪽으로 기우는 설계 원칙이다. 잠금장치가 고장 났을 때 문이 닫힌 채로 멈추면 fail-closed, 열린 채로 멈추면 fail-open이다.

fail-open (계속 발급)fail-closed (발급 중단)
잘못됐을 때 생기는 일초과 발급받을 수 있었던 사람이 못 받음
되돌릴 수 있나이미 나간 쿠폰은 회수 불가재개하면 그 사람들이 다시 받을 수 있음
판단 기준 — 이 문장이 시니어 답변이다
기준은 "차단이 안전한가"가 아니라
"어느 쪽으로 실패해야 되돌릴 수 있는가"다.

초과 발급은 회수가 불가능하다. 이미 "발급 완료"라고 응답한 쿠폰을 나중에 뺏는 것은 기술 문제가 아니라 신뢰 문제이고, 이미 사용된 쿠폰이라면 회수 자체가 성립하지 않는다. 반면 발급 중단은 불편하지만 재개하면 복구된다.
fail-closed가 언제나 정답인 것은 아니다 — 캐시가 죽었을 때 요청을 DB로 흘려보내는 fail-open이 맞는 경우도 있다(19번 — 캐시 장애와 DB 보호). 같은 원칙을 반대 방향으로 적용하는 사례를 함께 들면 원칙을 외운 게 아니라 이해한 것으로 읽힌다.

10-2. 복구 절차 — 멈·소·재·재

멈
① 멈춤
fail-closed로 발급 차단
소
② 소진
큐의 미반영분을 DB까지
재
③ 재구축
원장 → Set 복원
재
④ 재개
스위치 원복
③ 재구축은 DB 원장만 읽는다. 그러니 큐에만 있고 DB에는 아직 없는 발급은 재구축 시점에 존재하지 않는 것이 된다 — 그래서 ②가 ③보다 먼저다.
-- ③ 재구축: 원장이 진실이므로, 원장에서 Set을 다시 만든다
SELECT user_id FROM coupon_issue WHERE coupon_event_id = 1;

# 애플리케이션 쪽 (의사 코드)
#   1,000개씩 묶어 SADD 로 보내면 10만 명 기준 왕복 100번 — 초 단위로 끝난다
for chunk in chunks(userIds, 1000):
    redis.sadd("coupon:{1}:users", *chunk)   # 한 번에 여러 멤버 추가 가능

# 재구축이 끝난 뒤에야 ④ 발급 스위치를 되돌린다
기술로 0으로 만들 수 없는 부분 가산점
잔여 위험을 식별하고 처리 정책을 미리 정해두는 것까지가 설계다.

유실 직전에 판정만 통과하고 이벤트로 남지 못한 소량의 발급은 어떤 절차로도 되살릴 수 없다. 그래서 DB 원장 기준으로 실제 발급 수를 재검증하고, 소진 초과분은 비즈니스 결정(그대로 인정할지, 안내 후 회수할지)으로 처리한다. "전부 막았습니다"보다 "여기까지는 기술로, 여기서부터는 정책으로"가 더 신뢰받는 답변이다.

11. 앞단 방어 — 소진 이후의 수백만 요청을 어디서 거절하나

10만 번째 발급이 끝난 뒤에도 요청은 계속 온다. §1에서 본 대로 거절되는 요청이 성공하는 요청보다 훨씬 많으므로, 거절을 어디서 하느냐가 전체 비용을 결정한다. 원리는 단순하다 — 요청은 안쪽으로 들어올수록 더 비싼 자원을 잡는다.

이 사다리를 알고 나면 대응이 자연스럽게 나온다 — 거절할 요청은 최대한 바깥에서 거절한다.
소진 플래그를 앞으로 당긴다 즉시 적용 가능

소진되는 순간 별도 플래그 키(coupon:{1}:soldout)를 세우고, API 서버는 이 값을 로컬 캐시(수 초 TTL)로 들고 있다가 즉시 "소진" 응답을 돌려준다.

  • 소진 직후 수 초간은 캐시가 갱신되지 않은 서버에서 Redis까지 가는 요청이 남는다 — 무해하다. Lua가 정확히 판정한다.
  • 반대로 취소·반환으로 재고가 생겼을 때는 수 초간 잘못 거절할 수 있는데, 이것은 fail-closed 방향의 오차이므로 허용 가능하다.
유입 자체가 감당 밖이면 대기열 가상 대기실

진입 토큰을 발급해 초당 유입을 평탄화한다. 뒤쪽 계층이 감당 가능한 속도로만 요청을 흘려보낼 수 있다는 것이 핵심이다.

  • 선착순의 "순서"가 발급 요청 시점에서 대기열 진입 시점으로 옮겨질 뿐이다.
  • 사용자는 "지금 몇 번째" 같은 정보를 받으므로 오히려 예측 가능해진다.
  • 그리고 그 진입 시각은 기록으로 남길 수 있다 — 공정성 분쟁의 근거가 된다(§12).
설계 결정 드릴 — 이렇게 하면 무엇이 깨지나?

각 줄을 읽고 깨지는 지점을 먼저 말한 뒤 눌러서 확인한다. 8개 중 6개 이상이 즉답으로 나오면 이 문서는 인출 가능한 상태다.

12. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 시니어 변별 문항은 정답 하나가 아니라 판단 기준과 순서를 말하는 연습을 한다.

왜 분산 락으로 안 감싸나요?

잠글 틈이 없기 때문이다. 경합 지점(중복 확인 + 수량 확인 + 기록)이 이미 Lua 한 덩어리로 원자화되어 있고, Redis는 싱글 스레드라 스크립트 실행 중 다른 명령이 끼어들 수 없다. 락은 "명령 사이의 틈을 막는 장치"인데 막을 틈이 없으면 할 일이 없다.

락을 얹으면 얻는 것 없이 락 왕복 지연이 매 요청에 붙고, TTL 만료나 오해제라는 실패 모드만 추가된다(16번 문서).

마무리는 경계 짓기다 — 분산 락이 정당한 건 여러 시스템에 걸친 절차를 조정할 때이지, 단일 Redis 안의 원자 연산으로 끝나는 문제가 아니다. "락을 모른다"가 아니라 "여기서는 쓸 자리가 아니다"라는 걸 보여주는 것이 이 질문의 요지다.

failover로 카운터가 과거로 돌아갔다면 어떻게 감지하고 무엇부터 하나요? 시니어 변별

감지 수단은 둘이다.

  1. failover 이벤트 자체를 알람으로 받는다 — Sentinel이나 관리형 서비스의 알림.
  2. 대사(reconciliation) — DB 원장 건수와 SCARD를 주기적으로 맞춰본다. 두 값이 벌어지면 어딘가에서 기록이 사라졌다는 뜻이다.

대응은 §10-2의 순서 그대로 멈춤 → 소진 → 재구축 → 재개다. 먼저 발급을 fail-closed로 멈추고, 큐에 남은 미반영 이벤트를 DB까지 밀어 넣고, DB 원장으로 Set을 재구축한 뒤 재개한다.

순서를 지키지 않으면 — 특히 재구축을 큐 소진보다 먼저 하면 — 큐에만 있고 DB에 없는 발급이 Set에서 빠져 중복 발급 여지가 생긴다. "장애 시 절차"를 시간 순서로 말할 수 있는지가 운영 성숙도의 지표다.

컨슈머가 DB INSERT에 실패하면 사용자는 이미 '발급 완료'를 봤는데요?

이벤트가 큐에 남아 있으므로 재시도로 결국 반영된다(at-least-once 전달 — "적어도 한 번은 도착한다"는 보장이지 "정확히 한 번"이 아니다).

재시도로 같은 이벤트가 두 번 처리되는 경우는 유니크 제약이 흡수한다. 소비가 멱등해야 한다는 요구가 여기서 나온다(§9의 ON CONFLICT DO NOTHING).

계속 실패하는 독약 이벤트는 DLQ(dead letter queue, 처리에 반복 실패한 메시지를 따로 모아두는 큐)로 빼고 알람을 울린다. 그냥 두면 그 한 건이 뒤의 모든 이벤트를 막는다.

사용자 관점의 계약은 "판정 즉시 확정, 원장 반영은 지연 가능"이다. 그리고 쿠폰을 사용하는 시점에는 원장을 확인하므로, 반영 지연이 길어지면 사용 실패로 드러난다. 그래서 반영 지연(큐 lag) 자체를 모니터링 지표로 둔다.

10만 명이 같은 키를 치면 hot key 아닌가요? Cluster로 분산하면요? 시니어 변별

맞다, 구조적으로 hot key다 — 특정 키 하나에 요청이 집중되는 상태다. 그리고 Cluster는 이 문제의 해법이 아니다.

Cluster는 키를 해시해 슬롯으로 나누고 슬롯을 노드에 배분한다. 그런데 같은 키는 언제나 같은 슬롯, 즉 한 노드로만 간다. 노드를 100대로 늘려도 이 키를 처리하는 것은 여전히 한 대다. 분산의 단위가 키이기 때문에, 키가 하나면 분산되지 않는다(13번 — hot key).

그래서 순서는 이렇다.

  1. 먼저 산수로 검증한다. O(1) 명령 몇 개짜리 Lua면 단일 노드로도 초당 수만 건 수준을 처리한다. 여기에 §11의 앞단 방어로 유입을 깎으면 대부분의 이벤트는 단일 키로 충분하다. 필요 없는 복잡도를 사지 않는 것이 먼저다.
  2. 정말 초과하면 카운터 샤딩을 검토한다. 재고를 N조각(coupon:{1}:shard:0 ~ shard:N)으로 나눠 요청을 무작위 조각에 붙인다. 대신 대가가 크다 — 한 조각만 소진됐을 때 다른 조각으로 재시도하는 로직, 중복 방지 Set을 어떻게 나눌지, 전체 발급 수를 알려면 N개를 다 더해야 한다는 문제가 전부 따라온다.

필요가 증명되기 전에는 꺼내지 않는다가 결론이다.

'선착순'인데 정말 먼저 요청한 사람이 먼저 받나요?

엄밀한 전역 순서는 보장하지 않으며, 보장할 수 있는 시스템은 사실상 없다는 것까지 말해야 한다.

사용자 단말에서 LB, 서버, Redis까지 이어지는 경로마다 지연 편차가 있다. 통신사 회선, 지리적 거리, 서버별 부하가 다르므로 "버튼을 먼저 누른 순서"와 "Redis에 도착한 순서"는 얼마든지 달라진다. 이 편차를 없애려면 모든 사용자의 네트워크 지연을 통제해야 하는데, 그건 불가능하다.

시스템이 보장하는 것은 "Redis에 도착한 순서대로의 공정한 직렬 처리"다. 싱글 스레드가 도착순으로 하나씩 실행하므로, 도착한 뒤로는 뒤집히지 않는다.

이 정의를 비즈니스와 미리 합의해 두는 것이 분쟁을 막는 실무 답이다. 더 엄격한 공정성이 요구되면 대기열 진입 시각을 기준으로 순서를 박제하는 설계로 옮긴다(§11의 가상 대기실). 그러면 순서 결정 시점이 발급 요청보다 앞으로 당겨지고, 그 시각은 기록으로 남길 수 있다.

발급 응답이 타임아웃 났습니다. 사용자가 다시 누르면 어떻게 되나요? 추가

이 설계는 재시도에 안전하다 — 그 이유를 SADD에서 끌어내면 된다.

타임아웃은 "실패했다"가 아니라 "결과를 모른다"는 뜻이다. Redis에서는 이미 SADD가 성공했는데 응답만 못 받았을 수 있다. 그 상태에서 사용자가 다시 누르면 두 번째 SADD는 0을 반환하고, 스크립트는 -1(중복)을 돌려준다. 즉 "이미 발급받으셨습니다"가 나가고 두 장이 나가지 않는다. 같은 입력으로 몇 번을 눌러도 결과가 같다 — 판정이 멱등하다.

다만 사용자 경험 관점의 마무리가 필요하다. "이미 받으셨습니다"만 뜨면 사용자는 정말 받은 건지 알 수 없으므로, 발급 내역 조회 API를 함께 두고 그 화면으로 유도한다. 이 조회는 원장(DB)을 본다.

여기서 한 가지 주의를 덧붙이면 좋다 — 이벤트 적재가 실패한 채 판정만 성공한 요청은 Redis에는 남고 원장에는 없다. 그래서 발행 재시도가 필요하고, 그럼에도 새어 나간 건은 §10의 대사에서 잡힌다.

Lua 스크립트를 매 요청마다 EVAL로 통째로 보내나요? 추가

아니다. 스크립트 본문을 매번 보내면 그만큼의 네트워크 대역과 파싱 비용을 요청 수만큼 곱해서 낸다. 수백만 요청에서는 무시할 수 없다.

  • SCRIPT LOAD로 스크립트를 서버에 한 번 등록하면 SHA1 해시를 돌려받는다.
  • 이후에는 EVALSHA <sha> …로 해시만 보낸다 — 본문은 서버가 이미 알고 있다.
  • 서버가 그 스크립트를 모르면 NOSCRIPT 오류를 돌려주므로, 클라이언트는 그때만 EVAL로 본문을 다시 보내 등록한다. 실무 클라이언트 라이브러리는 이 폴백을 자동으로 해준다.

주의할 점은 스크립트 캐시가 영구적이지 않다는 것이다 — 서버 재시작이나 SCRIPT FLUSH 후에는 캐시가 비어 있다. 그래서 "한 번 로드했으니 끝"이 아니라 NOSCRIPT 폴백 경로가 반드시 있어야 한다. 이 답변이 나오면 운영에서 Lua를 써 봤는지가 드러난다.

쿠폰 취소·반환이 생기면 Set 설계가 어떻게 되나요? 추가

§6에서 택한 "Set 하나가 카운터를 겸한다"가 깨지는 지점이다. 이 질문의 값어치는 내가 고른 설계의 유효 범위를 스스로 아는지에 있다.

Set에서 SREM으로 사용자를 빼면 SCARD가 줄어 재고는 늘어난다. 그런데 동시에 그 사용자가 다시 받을 수 있게 된다 — 중복 방지가 함께 풀린다. 한 자료구조가 두 의미를 겸하고 있으므로 하나만 되돌릴 수 없다.

그래서 취소가 요건에 들어오는 순간 둘을 분리해야 한다.

  • 발급 이력 Set — 한 번 들어가면 빼지 않는다(중복 방지 전용).
  • 재고 카운터 — 취소 시 되돌릴 수 있는 별도 값으로 관리한다.

대신 §6에서 피했던 "두 값이 어긋날 수 있다"는 문제를 되사오는 것이므로, 대사 절차가 필수가 된다. 정리하면 — "취소가 없는 이벤트라면 겸용이 최선, 취소가 생기면 분리가 불가피하고 그 대가는 대사 비용"이다.

판정용 키에 TTL을 걸어도 되나요? 이벤트가 끝나면 어떻게 정리하죠? 추가

이벤트가 진행되는 동안 이 Set이 사라지면 그 자체가 §8의 유실과 같은 사고다. 판정의 근거가 통째로 없어지면서 초과 발급과 중복 발급이 동시에 열린다.

  • TTL을 이벤트 기간에 아슬아슬하게 맞추지 않는다. 이벤트 종료 후로 넉넉한 여유를 둬야 한다 — 마감 직후에도 "이미 받으셨습니다"를 정확히 응답하려면 Set이 살아 있어야 하고, §10의 대사도 이 Set을 본다.
  • 정리는 명시적으로 한다. 이벤트가 끝나고 원장 대사까지 마친 뒤에 지운다. 이때 큰 키라면 DEL이 아니라 UNLINK다(§6-1).
  • 그럼에도 TTL은 남겨두는 편이 낫다 — 정리 배치가 유실되거나 실패했을 때 키가 영원히 남는 것을 막는 안전망이기 때문이다. 요컨대 "TTL은 만료 수단이 아니라 누수 방지용 안전망"으로 쓴다.

여기에 하나 더 — Redis의 maxmemory 정책으로 이 키가 evict될 수 있는지도 확인 대상이다. 판정 키가 캐시 데이터와 같은 인스턴스, 같은 eviction 정책 아래 있으면 메모리 압박 때 밀려날 수 있다. 발급 판정처럼 잃으면 안 되는 데이터는 캐시와 인스턴스를 분리하는 것이 안전하다.

"이 설계로 초과 발급이 절대 없다"고 말해도 되나요? 시니어 변별 추가

안 된다. 그리고 그렇게 말하지 않는 것이 이 문항의 마지막 변별 지점이다.

정확히 구분해서 말하면 이렇다.

  • 정상 동작 중에는 초과 발급이 없다. 판정이 Lua 한 덩어리로 원자화되어 있고 SCARD가 유일한 진실이므로, 동시성 때문에 초과가 나는 경로는 없다.
  • 장애 중에는 잔여 위험이 남는다. 비동기 복제 + failover는 마지막 쓰기들을 없던 일로 만들 수 있고(§8-1), 그 순간에 이미 나간 응답은 회수되지 않는다. WAIT으로 창을 좁힐 수는 있어도 없앨 수는 없다.
  • 그래서 답은 "정상 경로에서는 보장, 장애 경로에서는 상한 관리 + 사후 대사 + 비즈니스 정책"이다.

면접에서 "절대"라는 단어는 대개 실패 모드를 안 그려봤다는 신호로 읽힌다. 반대로 보장 범위와 잔여 위험을 갈라 말하고, 잔여 위험의 처리 정책까지 준비해 두는 것이 신뢰를 만든다 — §10의 마지막 카드와 같은 태도다.

한 줄 요약
선착순 쿠폰의 정확성은 "확인 후 발급"을 Lua 한 덩어리로 원자화한 판정기(SADD의 0/1 반환이 중복 확인과 선점을 한 명령에 담고, Set 하나가 SCARD로 카운트까지 겸해 카운터 불일치 여지를 없앤다)가, 내구성은 판정 즉시 이벤트로 흘려 DB 원장에 멱등하게 쌓는 비동기 경로와 유니크 제약이라는 최종 방어선이 지키며 — 분산 락은 잠글 틈이 없어 불필요하고, 비동기 복제 때문에 failover가 마지막 쓰기들을 없던 일로 만들 수 있으므로 Redis 유실 시에는 되돌릴 수 있는 쪽으로 실패하도록 멈추고(fail-closed) 큐를 소진시킨 뒤 원장에서 재구축하고 재개한다는 절차까지 말해야 설계가 완성된다.
