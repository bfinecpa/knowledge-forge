분산 락의 함정 세 가지는 전부 한 문장으로 수렴한다 — "내가 락을 쥐고 있다"는 프로세스의 믿음과 락의 실제 상태가 어긋나는 순간, 임계 구간에 두 프로세스가 동시에 들어간다. ① TTL 만료: GC 일시 정지나 네트워크 지연으로 작업이 TTL보다 길어지면, 락은 만료되어 이미 남에게 넘어갔는데 원래 주인은 그걸 모른 채 계속 쓴다. ② 소유자 검증 없는 해제: DEL은 주인을 가리지 않는다. 늦게 깨어난 프로세스가 남의 락을 지우는 사고를 막으려면 락 값에 고유 토큰을 넣고 "내 토큰일 때만 삭제"를 Lua로 원자화해야 한다. ③ 시계 문제: Redlock은 락 유효 시간 판정을 각 노드의 물리 시계에 의존하는데, 시계가 점프하면(NTP 보정, 관리자 조작) 안전성 가정이 무너진다. Redlock 논쟁에 대한 내 기준은 이렇다 — 분산 락은 "같은 일을 두 번 하지 않기 위한 효율성 장치"로만 신뢰하고, 정확성(돈·정합성)이 걸린 작업의 최종 방어선은 락이 아니라 데이터 쪽(DB 유니크 제약·조건부 갱신·fencing token)에 둔다. 이 기준이면 단일 Redis + SET NX PX로 충분하며, Redlock의 복잡도는 사지 않는다.
출제 의도 — 명령어 암기가 아니라 타이밍과 기준을 본다
rationale은 이렇게 적고 있다 — "TTL 만료 후에도 자기가 락 주인인 줄 아는 프로세스, 남의 락 해제 — 이 함정들은 '락을 얻었다'는 착각 속에 정합성을 조용히 깬다. Redlock 논쟁에 견해를 묻는 건 정답이 아니라 안전성과 실용성의 트레이드오프에 자기 기준이 있는지를 보기 위해서다." 즉 채점 지점은 셋이다 — ① 각 함정이 어떤 타이밍에, 왜 발생하는지를 그림으로 그릴 수 있는가(§4·§7·§8) ② 함정마다 어디까지가 방어 가능하고 어디부터는 구조적으로 불가능한지를 구분하는가(§5·§6) ③ 그 불가능성 위에서 자기 기준을 세웠는가(§9·§10).

1. 자물쇠를 바깥에 두는 순간 — 분산 락이 무엇을 하는 물건인가

용어부터 정리하자. 락(lock, 자물쇠)은 "한 번에 한 명만 이 구간에 들어오게 한다"는 장치이고, 그 구간을 임계 구간(critical section)이라고 부른다 — 여러 실행 주체가 동시에 들어오면 결과가 깨지는 코드 구간이라는 뜻이다.

한 JVM 안이라면 synchronized나 ReentrantLock으로 끝난다. 자물쇠의 상태가 그 JVM의 메모리에 있고, 그 메모리를 모든 스레드가 함께 보기 때문이다. 그런데 같은 애플리케이션을 서버 3대로 늘리는 순간 이 전제가 무너진다.

3대의 JVM은 서로의 메모리를 볼 수 없으므로 각자 자기 자물쇠를 잡고 셋이 동시에 들어간다. 그래서 자물쇠의 상태를 모두가 볼 수 있는 바깥의 한곳에 두는 것이 분산 락이고, 그 바깥을 Redis로 삼은 것이다.
이 페이지 내내 쓸 비유 — 좌석과 이름표
Redis 키 하나 = 한 칸짜리 좌석, 키의 값 = 거기 앉은 사람의 이름표, TTL = 안 돌아오면 치우는 시각

이 비유 하나로 세 함정이 전부 설명된다 — 만: 자리를 비운 사이 이름표가 치워졌는데 본인은 모른다. 해: 자리를 뜨면서 남의 이름표를 치운다. 시: 치울 시각을 각자 다른 손목시계로 판정한다.

2. 왜 SET NX PX "한 문장"인가 — 두 문장으로 나누면 그 사이가 뚫린다

락 구현의 첫 함정은 알고리즘이 아니라 명령을 몇 개로 쪼갰는가에서 나온다. 흔히 시도하는 두 가지 형태가 각각 다른 방식으로 실패한다.

2-1. 실패 1 — "있는지 확인하고 없으면 잡는다"를 두 문장으로

check-then-act(확인하고 행동하기) 결함의 전형. 그 사이에 다른 프로세스가 끼어들면 두 프로세스가 똑같이 "내가 처음이다"라고 판단한다.

2-2. 실패 2 — "잡고 나서 TTL을 건다"를 두 문장으로

✕ before 1 — 확인과 쓰기를 나눔
// 프로세스 A와 B가 같은 순간에 실행
EXISTS lock:order:42   // → 0 (둘 다 0을 본다)
SET    lock:order:42 "A"
// 둘 다 "내가 처음이다"라고 판단한다
// → 임계 구간 동시 진입
✕ before 2 — 획득과 TTL을 나눔
SETNX  lock:order:42 "1"   // → 1 (획득 성공)
// ← 바로 여기서 프로세스가 죽는다
//    (배포 중 SIGKILL, OOM Kill, 크래시)
EXPIRE lock:order:42 30    // 실행되지 못한다

// 만료 시간이 없는 키가 Redis에 영원히 남는다.
// 사람이 손으로 지울 때까지 아무도 못 잠근다.

SETNX는 "없을 때만 SET"을 해주는 명령이라 실패 1은 막아준다. 그런데 만료 시간을 붙이는 EXPIRE가 별도 명령이라, 그 사이에 죽으면 영구 락이 남는다. 락이 정합성을 지키는 장치가 아니라 서비스를 멈추는 장치가 되는 것이다.

이 실패가 특히 고약한 이유 — 조용하다
예외도 알람도 없이 그 자원만 영원히 잠긴 채로, 나중에 "왜 이 배치가 며칠째 안 돌지?"로 발견된다. 이 문서의 함정들이 전부 공유하는 성질이다 — 명령은 전부 정상 성공으로 응답하고, 깨지는 것은 정합성뿐이다.

2-3. 인자를 하나씩 뜯어보면

두 실패를 동시에 없애는 방법은 하나다. 획득 판정과 만료 설정을 명령 하나에 담는 것.

SET lock:order:42 "550e8400-…-c8f1" NX PX 30000
키
lock:order:42 — 잠글 대상을 가리키는 이름(좌석 이름). "주문 42번"이라는 자원 하나에 좌석 하나가 대응되도록 자원 식별자를 키에 넣는다. 여기를 lock:order처럼 뭉뚱그리면 서로 상관없는 주문끼리 줄을 서게 되어 처리량이 죽는다.
값
"550e8400-…-c8f1" — 요청마다 새로 만든 고유 문자열(UUID 등). "이 좌석에 앉은 사람이 누구인가"를 적어두는 이름표다. "1" 같은 상수가 아니라 고유 값이어야 하는 이유는 §7에서 회수한다.
NX
Not eXists의 줄임. 키가 없을 때만 설정하고, 이미 있으면 아무것도 하지 않고 nil을 돌려준다. 반대 옵션 XX는 키가 있을 때만 설정한다. 이 두 글자가 "빈 좌석일 때만 앉는다"는 경쟁 판정을 애플리케이션에서 Redis 안으로 밀어 넣는다.
PX 30000
만료 시간을 밀리초 단위로 지정. 30000ms = 30초. 초 단위로 주고 싶으면 EX 30.

핵심은 이 네 가지가 한 명령이라는 점이다. Redis는 명령 하나를 처리하는 동안 다른 클라이언트의 명령을 끼워 넣지 않으므로, "없는지 확인 + 값 쓰기 + 만료 설정"이 쪼개지지 않는다. §2-1과 §2-2의 두 실패가 함께 사라진다.

이 문서 전체를 관통하는 원리 — 여기서 한 번 붙잡고 간다
명령을 나누지 말고, 조건을 명령 안에 실어 보낸다.

이 발상은 뒤의 Lua 해제(§7), fencing token의 조건부 UPDATE(§6), 그리고 락 없이 푸는 재고·쿠폰 문제(§10)까지 그대로 이어진다. 함정을 하나씩 외우는 대신 이 한 줄에서 파생시키면 답변이 흔들리지 않는다.

3. TTL은 정합성 장치가 아니라 가용성 장치다

왜 애초에 만료 시간을 거는지 정확히 말할 수 있어야 한다. 락을 쥔 프로세스가 죽으면 해제 명령을 실행할 주체가 사라진다. TTL이 없으면 §2-2의 영구 락이 남는다. 그래서 TTL은 "주인이 돌아오지 않으면 좌석을 강제로 비운다"는 규칙이다.

한 문장으로 고정 — 여기서 답변의 층이 갈린다
TTL이 지키는 것은 정합성이 아니라 가용성이다.
그리고 "강제로 비운다"는 것은 주인이 아직 일하고 있어도 비운다는 뜻이다.

보험이 그대로 다음 함정의 원인이 된다 — §4의 TTL 만료 함정은 TTL의 버그가 아니라 TTL이 설계대로 동작한 결과다. 이 인과를 뒤집어 말하는 순간 "TTL을 잘 잡으면 되는 문제"로 답이 후퇴한다.

락의 안전성과 가용성이 TTL 하나를 사이에 두고 서로를 밀어내는 구조 — 이 긴장을 인식하는 것이 이 문항의 절반이다. "TTL을 얼마로 잡나요?"라는 꼬리질문이 오면 값이 아니라 이 그림을 먼저 꺼낸다.

4. 함정① TTL 만료 — 작업이 락보다 오래 사는 순간

4-1. 전제 지식 — GC 일시 정지(stop-the-world)란 무엇인가

TTL을 30초로 잡았다고 하자. "30초면 충분하지"라는 가정은 애플리케이션이 그동안 멈추지 않는다는 가정 위에 서 있다. 그런데 JVM은 멈춘다.

JVM은 개발자 대신 메모리를 정리한다. 더 이상 참조되지 않는 객체를 찾아 회수하는 일이 가비지 컬렉션(GC)이다. 회수 대상을 판정하는 도중에 애플리케이션 스레드가 계속 참조 관계를 바꾸면 판정이 어긋나므로, GC는 특정 구간 동안 애플리케이션 스레드를 전부 멈춘다. 세상이 통째로 정지한 것처럼 보인다고 해서 stop-the-world(STW) 일시 정지라고 부른다.

애플리케이션 코드 입장에서 STW가 어떻게 보이는가 — 이게 결정적이다
long t1 = System.currentTimeMillis();
// ← 여기서 STW 정지가 일어난다.
//    이 스레드는 아무것도 하지 않은 채 시간만 흐른다.
long t2 = System.currentTimeMillis();

// t2 - t1 이 800ms 일 수 있다. 두 줄 사이에 아무 코드도 없는데도.
이 함정의 심장 — 외울 것은 이 한 줄
한 줄과 다음 줄 사이에서 수백 ms에서 수 초가 사라지고,
스레드는 자기가 멈췄었다는 사실을 모른다.

깨어나서 그냥 다음 줄을 실행한다. "내가 5초 동안 정지해 있었으니 락을 다시 확인해야지"라는 판단 자체가 불가능하다. 이 불가능성이 §5(watchdog으로도 못 막는 이유)와 §6(그래서 방어선을 자원 쪽으로 옮기는 이유)의 근거가 된다.

최신 수집기(G1, ZGC 등)는 정지 시간을 짧게 유지하도록 설계돼 있지만 0이 되지는 않고, 힙이 크거나 메모리 압박이 심하면 여전히 긴 정지가 나온다. 그리고 같은 효과를 내는 원인이 GC만도 아니다.

컨테이너 CPU 스로틀링 k8s에서 가장 흔함

CPU limit을 넘긴 파드는 다음 주기까지 CPU를 배정받지 못한다. 스레드는 실행 가능 상태로 대기만 한다 — GC 로그에는 아무것도 안 찍히는데 시간은 사라진다.

스왑 · 디스크 I/O 블로킹 OS 계층

페이지 폴트 한 번이 수십에서 수백 ms를 먹는다. 애플리케이션은 그냥 느린 메모리 접근으로만 인식한다.

네트워크 지연 임계 구간을 늘린다

Redis 호출이 나갔다가 돌아오는 시간 자체도 임계 구간에 포함된다. 단절되면 연장 요청조차 도달하지 못한다(§5).

VM 라이브 마이그레이션 · 스냅샷 복원 인프라 계층

게스트 전체가 잠깐 멈춘다. 그리고 스냅샷 복원은 §8의 시계 점프까지 함께 데려온다.

정리 — TTL 30초의 진짜 의미
TTL 30초는 "작업이 30초 안에 끝난다"가 아니라 "작업 시간 + 그 사이에 끼어들 수 있는 모든 정지의 합이 30초 안"이라야 성립한다. 그리고 두 번째 조건은 애플리케이션이 통제할 수 없는 것들로 채워져 있다.

4-2. 사고의 타임라인 — 이 그림 하나가 답변의 절반

파란 점선이 A의 믿음, 가운데 줄이 락의 실제 상태다. 두 줄이 t=30s부터 어긋나 있고, 그 어긋남을 A만 모른다 — 이 페이지의 모든 함정이 이 그림의 변주다.
"그럼 쓰기 직전에 락이 아직 내 것인지 확인하면 되지 않나?" — 답이 아니다
확인과 쓰기 사이에서 또 멈출 수 있기 때문이다. 확인은 그 순간의 사실일 뿐 다음 순간을 보장하지 않는다. 이 구조는 분산 락 논의 내내 반복해서 나온다 — 어떤 검사도 검사와 행동 사이의 시간을 없애지는 못한다. §2-1의 check-then-act와 정확히 같은 결함이고, 이번에는 명령을 합쳐서 해결할 수도 없다(행동이 Redis 밖에서 일어나므로).

5. 완화책① watchdog 락 연장 — 완화지 해결이 아니다

watchdog(감시견)은 락을 잡은 클라이언트가 별도의 백그라운드 스레드를 띄워, 락을 쥐고 있는 동안 주기적으로 TTL을 원래 값으로 다시 밀어주는 기능이다. Redisson의 락이 이 방식을 쓴다. 주차 미터기에 동전을 계속 넣어 주차 시간을 이어가는 것과 같고, 다르게 말하면 "내가 아직 살아 있다"는 심장박동을 Redis에 계속 보내는 셈이다.

watchdog이 실제로 지우는 문제 효과는 분명하다
  • 작업 시간이 예상보다 길어져도 프로세스가 살아 있는 한 락이 만료되지 않는다.
  • 프로세스가 죽으면 연장하는 주체가 사라지므로 TTL이 자연 소멸한다 — §2-2의 영구 락 문제도 재발하지 않는다.
  • 즉 "작업 시간을 잘못 예측했다"는 가장 흔한 원인 하나를 지워준다.
그래도 남는 구조적 한계 여기가 채점 지점
  • 연장 스레드도 같은 JVM 안에 있다. STW GC는 애플리케이션 스레드를 전부 멈추므로, 워커가 멈출 때 연장 스레드도 함께 멈춘다.
  • 정지가 TTL보다 길면 §4의 타임라인이 그대로 재현된다.
  • 네트워크가 끊겼다면 연장 요청 자체가 Redis에 도달하지 못한다.
두 트랙의 차이는 "연장 스레드가 살아서 돌 수 있느냐" 하나다. 그리고 그 조건이 깨지는 상황이 바로 이 함정이 실제로 터지는 상황이라는 것이 watchdog의 역설이다.
한 줄로 정리 — 꼬리질문 단골
watchdog은 "살아서 정상 동작 중인 프로세스의 시간 예측 실패"를 막을 뿐,
"프로세스 자신이 인지하지 못하는 정지"는 못 막는다.
실무 함정 — Redisson을 쓴다고 자동으로 연장되는 것이 아니다 디테일
Redisson에서 임대 시간을 명시적으로 지정하면(lock(10, TimeUnit.SECONDS) 같은 형태) watchdog은 동작하지 않고 그 시간이 지나면 그냥 만료된다. "Redisson을 쓰니 알아서 연장되겠지"라고 믿으면서 임대 시간을 지정하는 조합이 실제 사고로 이어진다.

6. 완화책② fencing token — 방어선을 락에서 자원 쪽으로 옮긴다

지금까지의 대응은 전부 락을 더 정확하게 만들려는 시도였다. 그런데 "정지를 인지하지 못하는 프로세스"라는 근본 문제는 락 쪽에서 풀 수 없다는 것이 §5에서 드러났다. 그래서 발상을 뒤집는다.

발상의 전환 — 이 문장이 §9(논쟁)와 §10(실무 기준)의 뼈대다
락을 쥔 쪽이 아무리 착각해도,
자원을 받는 쪽이 낡은 요청을 거부하면 결과는 안전하다.

fencing token은 락을 발급할 때마다 1씩 증가시켜 함께 내주는 번호다. 이름은 울타리(fence)에서 왔다 — 자원 앞에 "이 번호 미만은 들어올 수 없음"이라는 울타리를 세워두고, 새 주인이 다녀갈 때마다 그 울타리를 한 칸씩 올린다. 뒤늦게 깨어난 옛 주인은 자기 번호가 울타리보다 낮아서 튕겨 나간다.

1
락 서비스가 락을 줄 때마다 단조 증가 번호를 함께 발급한다 단조 증가(monotonically increasing) = 절대 줄어들지 않는다는 뜻이다. A가 33번을 받았다면 그다음 주인 B는 반드시 그보다 큰 번호를 받는다.
2
자원을 만지는 모든 요청이 그 번호를 실어 보낸다 번호를 안 실은 경로가 하나라도 남아 있으면 그 경로로 낡은 쓰기가 통과한다 — 울타리에 난 구멍이다.
3
자원(DB·스토리지)이 지금까지 본 번호보다 큰 요청만 받아들인다 나머지는 거부한다. 판정하는 주체가 락이 아니라 자원이라는 점이 핵심이다.
A의 락은 여전히 틀렸다 — 달라진 것은 그 틀림이 자원에 반영되지 않는다는 점이다. 판정 주체가 락에서 자원으로 옮겨 갔다.
✕ before — 락만 믿고 무조건 쓴다
-- 락을 잡았으니 내가 주인이라고 가정한다
UPDATE resource
   SET data = ?
 WHERE id = ?
-- 낡은 주인의 쓰기도 그대로 통과한다.
-- 자원은 "누가 지금 주인인지" 알 방법이 없다.
✓ after — 자원이 낡은 토큰을 직접 거부한다
UPDATE resource
   SET data = ?, fence = ?   -- fence = 내 토큰(33)
 WHERE id = ?
   AND fence < ?             -- 기록된 토큰보다 클 때만

-- 영향 행 수 0 = 나보다 새 주인이 이미 다녀갔다
--            → 내 작업 결과를 버린다
여기서 무슨 일이 일어났는지 정확히 짚자
정확성의 근거가 "락이 옳았다"에서 "자원이 검사했다"로 옮겨 갔다.

락은 여전히 틀릴 수 있다. 하지만 락이 틀려도 자원이 막아주므로 최종 결과는 깨지지 않는다. 즉 fencing token이 있으면 정확성이 더 이상 락의 정확성에 의존하지 않는다. 락은 "대부분의 경우 헛수고를 줄여주는 최적화"로 강등되고, 정확성은 자원 쪽 조건부 쓰기가 책임진다. — 락을 강화하는 방향과 자원을 방어하는 방향 중, 뚫렸을 때 잃는 것이 클수록 후자가 답이다.

낯선 구조가 아니다 — JPA @Version 낙관적 락과 같은 뼈대
조건을 갱신문 안에 넣고, 영향 행 수 0으로 "내가 낡았다"를 감지한다는 점이 동일하다. 다른 점은 비교 대상이 그 행의 버전이 아니라 락 발급 순번이라는 것뿐이다. 그리고 §2-3의 원리 — "조건을 명령 안에 실어 보낸다" — 가 여기서 세 번째로 반복된다.
전제 — 자원이 조건부 쓰기를 지원해야 한다 한계

DB라면 WHERE에 조건을 얹으면 되지만, "메일 발송 API 호출", "외부 결제 승인 요청"처럼 조건부 쓰기를 받아주지 않는 자원은 fencing으로 보호할 수 없다. 이때 다음 수단은 그 자원 쪽에 멱등성 키를 받아주는 API가 있는지 확인하는 것이다.

Redlock은 fencing token을 제공하지 않는다 가산점 포인트

여러 노드에 각각 독립적으로 SET NX를 할 뿐이라, "전역에서 단조 증가하는 번호"를 만들어 낼 수단이 알고리즘 안에 없기 때문이다. §9 Kleppmann 비판의 핵심 중 하나가 여기다.

7. 함정② 락 해제 — DEL은 주인을 확인하지 않는다

DEL은 "이 키를 지워라"라는 명령일 뿐이다. 누가 요청했는지, 그 사람이 지금 주인인지 묻지 않는다. 그래서 §4에서 지연됐던 A는 자기 락을 정리한다고 믿으면서 B의 락을 지운다.

무서운 점은 연쇄다. A의 지연 하나가 B의 락을 지우고, 그 빈자리가 C를 불러들이고, C가 작업을 마치며 또 남의 락을 지운다. 그리고 이 붕괴는 로그를 남기지 않는다 — DEL도 SET NX도 전부 정상 성공으로 응답하기 때문이다.

7-1. 해제의 올바른 형태 — 소유자 확인과 삭제를 한 덩어리로

§2-3에서 락 값에 상수가 아니라 요청마다 고유한 토큰을 넣은 이유가 여기서 회수된다. 해제할 때 "지금 이 키에 적힌 이름표가 내 것인가"를 확인하고, 내 것일 때만 지우면 된다. 단, 확인과 삭제를 두 문장으로 쓰면 §2-1과 똑같은 구멍이 다시 열린다.

✕ before — check-then-act를 두 문장으로
GET lock:order:42
// → "내 토큰이 맞네"

// ← 이 찰나에 TTL이 만료되고
//    B가 락을 획득한다

DEL lock:order:42
// → B의 락을 지운다

// 토큰을 넣어 뒀는데도 뚫렸다.
// 문제는 토큰이 아니라 "두 문장"이었다.
✓ after — Lua 스크립트 하나로 (Redis가 원자적으로 실행)
-- KEYS[1] = "lock:order:42"
-- ARGV[1] = 내 소유자 토큰(UUID)
if redis.call("GET", KEYS[1]) == ARGV[1] then
    -- 이름표가 내 것일 때만 지운다.
    -- GET 과 DEL 사이에 다른 명령이 못 끼어든다.
    return redis.call("DEL", KEYS[1])
else
    -- 남의 락이거나 이미 만료돼 사라진 상태.
    -- 예외를 던지지 않는 이유: 해제 실패는 오류가 아니라
    -- "TTL 이 나보다 먼저 일했다"는 정상적 결과이기 때문.
    return 0
end
왜 MULTI/EXEC가 아니라 Lua인가 — 자주 묻는다
MULTI는 명령들을 큐에 모아 한꺼번에 실행할 뿐 중간 조회 결과를 보고 분기할 수 없다. "GET 결과가 내 토큰이면 DEL, 아니면 아무것도 안 함"이라는 조건 분기를 표현할 방법이 없는 것이다. 반면 Redis는 Lua 스크립트를 한 덩어리로 실행하며 그 사이에 다른 클라이언트의 명령을 끼워 넣지 않고, 스크립트 안에서는 조회 결과로 자유롭게 분기할 수 있다.
이 스크립트가 0을 돌려줬다면 — 그냥 넘기지 않는다
0 = "작업하는 동안 내가 락을 쥐고 있었다는 보장이 이미 깨졌다"는 신호

예외는 아니지만 무의미한 값도 아니므로, 로그나 메트릭으로 남겨 그 빈도를 본다. 이 값이 늘어난다면 TTL이 작업 시간에 비해 짧다는 증거다 — §3의 다이얼을 조정하거나 watchdog을 도입할 근거가 여기서 나온다. "측정 가능한 신호로 바꿔 둔다"는 대답이 실무 경험의 신호가 된다.

7-2. 여기까지가 단일 Redis 기준의 완성형

외울 조합 — 이 네 개가 한 세트
SET NX PX + 요청마다 고유한 소유자 토큰 + Lua 해제 (+ 필요 시 watchdog)

Redisson의 락이 대략 이 구성이다. 그리고 직접 구현하지 않고 검증된 라이브러리를 쓰는 것 자체가 실무 답안의 일부다 — 재진입(같은 스레드가 같은 락을 중첩해서 잡는 경우) 처리, 대기 중인 클라이언트를 pub/sub으로 깨우는 로직, 연장 스레드의 수명 관리 같은 것을 직접 만들면 그 구현 자체가 새로운 버그의 원천이 된다.

8. 함정③ failover 유실과 시계 문제 — Redlock이 나온 자리

8-1. 단일 Redis에 남은 구멍 — 복제는 비동기다

§7까지 만들어도 구멍이 하나 남는다. Redis 복제는 비동기다. 마스터는 쓰기를 받아 자기 메모리에 반영하고 클라이언트에 OK를 먼저 응답한 뒤에 그 내용을 레플리카로 흘려보낸다. 응답과 복제가 묶여 있지 않다.

이건 락의 존재 자체가 유실되는 문제라 소유자 토큰 검증으로도 못 막는다 — A와 B가 각자 정당한 토큰을 들고 있고, 서로의 존재를 알 방법이 없기 때문이다. Redlock은 정확히 이 구멍을 메우기 위해 제안됐다.

8-2. Redlock 알고리즘 — 절차를 그대로 따라가 보면

Redlock은 서로 복제 관계가 아닌, 완전히 독립적인 Redis 마스터 N대(관례적으로 5대)를 두고 다수결로 락을 판정하는 알고리즘이다. 노드끼리 복제하지 않으므로 한 대가 죽어도 다른 노드의 기억이 함께 사라지지 않는다.

1
현재 시각을 밀리초 단위로 기록한다 뒤에서 "획득에 얼마나 걸렸는지"를 계산해야 하기 때문이다.
2
N대 전부에 순서대로 락 획득을 시도한다 모든 노드에 같은 키, 같은 소유자 토큰, 같은 TTL로 SET NX PX를 보낸다. 이때 노드별 요청 타임아웃을 락 TTL보다 훨씬 짧게 잡는다(TTL이 10초라면 노드당 수십 ms 수준). 응답 없는 노드 하나에 오래 붙잡혀 있으면 절차 전체가 늦어지므로, 빠르게 실패로 치고 다음 노드로 넘어가야 한다.
3
성공한 노드 수를 세고, 걸린 시간을 계산한다 걸린 시간 = "지금 시각 − 1에서 기록한 시각".
4
성공 조건은 두 개이고 둘 다 만족해야 한다 (가) 과반, 즉 N/2 + 1대 이상에서 성공했다(5대라면 3대). (나) 획득에 쓴 시간이 TTL보다 충분히 짧다.
5
실제로 쓸 수 있는 유효 시간 = TTL − 획득 소요 시간 − 시계 오차 여유 TTL이 10초인데 획득에 3초가 걸렸다면 남은 유효 시간은 약 7초다. 이 시간이 남아 있는 동안만 임계 구간을 실행하고, 계산 결과가 0 이하이면 획득 실패로 처리한다.
6
실패하면 성공했던 노드들까지 포함해 모든 노드에 해제를 보낸다 일부 노드에만 락이 남아 있으면 다음 시도들이 계속 과반을 못 채워 아무도 락을 못 잡는 상태가 되기 때문이다. 해제는 §7의 Lua(내 토큰일 때만 삭제)를 그대로 쓴다.
4의 (나) 조건이 가장 헷갈리는데, 이유는 이렇다 — 락의 TTL은 첫 번째 노드에 SET이 성공한 순간부터 이미 흐르기 시작한다. 5대를 도는 데 시간이 걸리므로, 마지막 노드에서 성공을 확인한 시점에는 첫 노드의 TTL이 이미 상당히 소진돼 있다. 그래서 "걸린 시간을 빼고 남은 만큼만 내 것"이라고 계산한다.

8-3. 시계 점프란 무엇인가 — 세 번째 함정의 실체

서버의 물리 시계는 조금씩 어긋나고, NTP(Network Time Protocol)가 이를 표준 시각에 맞춘다. 보통은 시계가 가는 속도를 미세하게 조정해 서서히 맞추지만, 오차가 크면 시각을 한 번에 건너뛰게 만든다. 관리자가 수동으로 시각을 바꾸거나, 가상 머신이 스냅샷에서 복원되거나, 윤초 처리가 어긋나도 같은 일이 생긴다.

시계 점프가 락에 하는 일 — 한 문장
시각이 앞으로 확 뛰면, Redis가 보기에 아직 안 끝난 TTL이 이미 지난 것으로 판정된다.

비유하면 심판 다섯 명이 각자 자기 손목시계로 경기 종료를 판정하는 것과 같다. 한 명의 시계가 2초 앞으로 튀면 그 심판만 먼저 종료를 선언하고, 그 순간 과반 계산이 무너진다. 그리고 결정적으로 — 노드를 5대로 늘리는 것은 노드 장애에 대한 대비이지 시계 오작동에 대한 대비가 아니다. 다섯 개의 시계가 함께 틀릴 수 있고, 늘어난 노드 수만큼 틀릴 시계도 늘어난다.

9. Redlock 논쟁 — 두 사람은 서로 다른 층위에서 말하고 있다

Kleppmann의 비판 "보장이란 무엇인가"의 층위

『Designing Data-Intensive Applications』 저자. 논지를 한 문장으로 압축하면 — Redlock의 안전성은 타이밍 가정(프로세스가 오래 멈추지 않는다, 시계가 튀지 않는다, 네트워크 지연에 상한이 있다) 위에 서 있는데, 비동기 네트워크에서는 그 가정 중 어느 것도 성립을 보장할 수 없으므로 Redlock은 안전성을 증명할 수 없다.

  • 시계 점프에 취약하다 — 유효 시간 계산과 각 노드의 만료 판정이 물리 시계에 기대고 있다. 노드 5대는 노드 장애의 대비이지 시계 오작동의 대비가 아니다.
  • 프로세스 정지에는 어차피 똑같이 뚫린다 — 유효 시간을 확인한 직후에 STW 정지가 오면 §4의 타임라인이 그대로 반복된다. 노드 수를 늘려도 이 구멍은 그대로다.
  • fencing token이 없다 — 락이 뚫렸을 때 자원을 지켜줄 마지막 수단이 알고리즘 안에 없다(§6).
antirez의 반박 "실무에서 무엇을 위해 락을 쓰는가"의 층위

Redis 창시자. 요지도 셋이다.

  • 다수 사용례는 효율성 목적이다 — 배치 중복 실행 방지처럼 뚫려도 "일을 두 번 한다"로 끝나는 용도가 압도적으로 많고, 그 목적에는 Redlock의 보장 수준이 충분하다.
  • 시계 점프는 운영으로 통제 가능하다 — 시각을 건너뛰지 않고 미세 조정하도록 NTP를 설정하고, 관리자의 수동 시각 변경을 금지하면 실무 빈도가 크게 낮아진다. 이론적 가능성과 운영상의 발생 확률은 다르다.
  • 유효 시간 확인 이후의 정지는 Redlock만의 결함이 아니다 — fencing 없이는 어떤 락 시스템도 그 구멍을 막지 못한다. 그리고 획득 과정 중에 생긴 지연은 유효 시간 계산이 이미 걸러낸다.
두 사람이 끝내 합의하지 못한 이유는 서로 다른 층위에서 말하고 있기 때문이다. 면접에서 한쪽 편을 드는 답변보다, 이 그림처럼 층위를 분리해 보이는 답변이 강하다.

9-1. 내 견해 — "효율성의 락"과 "정확성의 락"을 나누면 논쟁이 정리된다

이 논쟁에서 가장 값진 산출물은 승패가 아니라 Kleppmann이 제시한 구분이다. 락을 쓰는 이유가 무엇인지를 먼저 물으면 두 층위가 갈라지고, 답도 함께 갈라진다.

효율성(efficiency)의 락 — 뚫려도 "일을 두 번 함"

목적: 같은 계산, 같은 배치, 같은 캐시 갱신을 여러 인스턴스가 중복 수행하지 않게 한다.

뚫리면 잃는 것: 중복 실행 비용뿐이다 — 결과 자체는 여전히 옳다.

→ 단일 Redis + SET NX PX + 고유 토큰 + Lua 해제로 충분하다. 드물게 중복 실행되는 비용보다 독립 Redis 5대를 운영하는 비용이 크다. 여기에 Redlock은 과잉이다.

정확성(correctness)의 락 — 뚫리면 돈이 새거나 데이터가 깨짐

예: 중복 결제, 이중 차감, 재고 초과 판매.

어떤 Redis 락도, Redlock을 포함해서, 단독으로는 부족하다. §4의 정지 문제와 §6의 fencing 부재가 그대로 남기 때문이다.

→ 방어선을 데이터 쪽에 이중으로 깐다. DB 유니크 제약, 조건부 갱신(영향 행 수 확인), 멱등성 키. 락은 있어도 "경합을 줄여 재시도 횟수를 낮추는 성능 최적화"일 뿐, 정합성의 근거가 아니다.

면접에서 이 순서로 — 견해 질문의 답변 골격
① 두 사람이 다른 층위임을 짚고 → ② 효율성/정확성으로 용도를 가르고 → ③ 각각에 내 선택을 붙인다

"Redlock은 좋다/나쁘다"로 답하면 어느 쪽을 골라도 반쪽이 된다. "이 락이 뚫리면 무엇을 잃는가"라는 질문으로 되돌린 뒤 답을 두 갈래로 나누는 것이 이 문항이 실제로 요구하는 형태다.

12. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 시니어 변별 문항은 정답 하나를 고르지 말고 판단 기준을 말하는 연습을 한다.

TTL을 아주 길게(10분) 잡으면 만료 문제가 없어지지 않나요?

만료 함정(§4)이 발생할 확률은 줄지만 반대쪽 비용이 그만큼 커진다. §3의 다이얼을 그대로 꺼내 답하면 된다.

락 주인이 크래시로 죽으면 그 자원은 TTL이 다할 때까지 아무도 못 잠근다 — 10분짜리 부분 장애다. 게다가 TTL을 길게 잡아도 §4의 근본 문제는 남는다. 정지가 10분보다 짧아지는 것이 아니라 "10분보다 긴 정지"의 확률이 낮아질 뿐이고, 확률을 0으로 만들 수는 없다.

그래서 실무 답은 조합이다. 작업 예상 시간보다 여유 있게 잡고 + watchdog으로 연장하고 + 그래도 뚫리는 경우는 fencing이나 데이터 제약으로 받는다. TTL은 안전성과 가용성 사이의 다이얼이지, 한쪽으로 끝까지 돌려서 해결되는 값이 아니다.

Redisson watchdog이 있으면 TTL 만료 문제는 해결된 것 아닌가요?

아니다. watchdog은 "살아 있는 프로세스의 시간 예측 실패"만 지운다.

연장 스레드도 같은 JVM 안에 있으므로 STW GC나 컨테이너 스로틀링 앞에서는 워커 스레드와 함께 멈춘다. 네트워크가 끊기면 연장 요청 자체가 Redis에 도달하지 못한다(§5).

"자신이 정지했다는 사실을 인지하지 못한 채 재개하는 프로세스"라는 근본 문제는 락 쪽에서 풀 수 없고, 자원 쪽 방어(fencing token, 조건부 갱신)로만 막을 수 있다.

여기에 더해 Redisson에서 임대 시간을 명시하면 watchdog이 아예 동작하지 않는다는 점도 함께 말하면, 라이브러리를 읽어본 사람이라는 신호가 된다.

락 획득에 실패한 요청은 어떻게 처리하나요?

용도에 따라 갈라서 답한다. 이 구분을 못 하면 모든 실패를 재시도로 처리하게 되고, 그게 장애로 번진다.

  • 중복 실행 방지 목적이면 즉시 포기가 정답이다. 락을 못 잡았다는 것은 "누군가 이미 그 일을 하고 있다"는 뜻이므로 기다릴 이유가 없다. 기다렸다가 잡아서 또 하면 애초에 막으려던 중복 실행을 스스로 하는 셈이다.
  • 순서 대기 목적이면 재시도(스핀) 또는 대기다. 다만 스핀 재시도는 Redis에 폴링 부하를 만들므로 재시도 간격과 상한을 둬야 하고, Redisson처럼 pub/sub으로 "락이 해제됐다"는 신호를 받아 깨어나는 구현이 폴링보다 낫다.

어느 쪽이든 대기 시간 상한과 실패 응답 경로가 반드시 있어야 한다. 없으면 락 경합이 스레드 고갈로 번진다 — 대기하는 스레드가 톰캣 워커를 붙잡고, 워커가 마르면 락과 무관한 API까지 함께 죽는다. 비관적 락이 커넥션을 고갈시키는 것과 정확히 같은 구조의 문제다.

그냥 DB 비관적 락(SELECT FOR UPDATE)을 쓰면 안 되나요? 언제 Redis 분산 락이 필요한가요? 시니어 변별

보호 대상이 그 DB 안에 있다면 DB 락이 우선이다.

이유는 실패 모드의 개수다. 락과 데이터가 같은 시스템이면 "락은 살았는데 데이터 시스템만 죽는" 반쪽 실패가 없고, 트랜잭션 롤백과 락 해제가 원자적으로 묶인다. 반면 Redis 락 + PostgreSQL 데이터 조합은 두 시스템이 각각 죽을 수 있고, 그 조합마다 다른 사고가 난다.

Redis 분산 락이 정당해지는 경우는 둘이다.

  1. 보호 대상이 DB 바깥일 때. 외부 API 호출, 파일 작업, 여러 저장소에 걸친 절차처럼 DB의 행 락으로는 감쌀 수 없는 자원이다.
  2. DB 커넥션을 락 대기에 붙잡아두는 비용이 감당 불가일 때. 대기 줄을 DB 밖으로 빼야 커넥션 풀이 마르지 않는다.

단, 2의 경우에도 순서가 있다. 대기 줄을 옮기기 전에 임계 구간 자체를 줄이는 설계(조건부 UPDATE 한 문장으로 접기)가 먼저다.

"분산 환경이니까 분산 락"은 근거가 아니다 — 분산 환경에서도 경합 지점이 단일 DB면 그 DB가 이미 훌륭한 조정자다.

Redlock 5대 중 2대가 죽으면 어떻게 되나요? 가산점

과반인 3대가 살아 있으므로 락 발급은 계속된다. 그게 Redlock의 설계 목적이므로 여기까지는 정상 동작이다.

진짜 문제는 다른 시나리오다. 락을 발급한 노드 중 하나가 디스크 영속화 없이 재시작하면 그 노드는 자기가 발급했던 락을 잊은 채 돌아온다. 그러면 다른 클라이언트가 "그 노드 + 원래 실패했던 노드들"로 새 과반을 만들어 같은 락을 획득할 수 있다. 노드가 죽지도 않았는데 과반이 두 개가 되는 것이다.

그래서 antirez는 delayed restart — 재시작한 노드가 락 TTL만큼 기다린 뒤에야 요청을 받게 하는 방식 — 를 제안했다. 그 시간이 지나면 자기가 잊은 락들도 어차피 만료됐을 것이기 때문이다.

이 답을 할 수 있으면 "알고리즘을 외운 사람"과 "실패 모드를 따져본 사람"이 갈린다.

반드시 커밋이 먼저, 락 해제가 나중이다. 순서가 뒤집히면 락을 제대로 구현해 놓고도 정합성이 깨진다.

왜인지 그림으로 보면 이렇다 — 락을 먼저 풀면 다음 획득자가 "아직 커밋되지 않은 상태"의 데이터를 읽고 판단한다. 재고 차감이라면, B는 A가 이미 차감했지만 아직 커밋 전인 값을 보고 "재고가 남아 있네"라고 결론 내린다. 임계 구간을 한 명씩 통과시켰는데도 결과는 동시 진입과 똑같아진다.

스프링에서 이 사고가 나는 전형적인 모양이 있다.

  • ✕ 위험 — @Transactional이 붙은 메서드 안에서 락을 잡고 풀면, 락 해제가 커밋(메서드 종료 시점)보다 먼저 실행된다.
  • ✓ 안전 — 락을 잡는 계층이 트랜잭션보다 바깥이어야 한다. 락을 잡는 메서드가 @Transactional 메서드를 호출하는 구조로 두면, 호출이 반환될 때 커밋이 끝나 있고 그 뒤에 락을 푼다.

정리하면 락의 범위는 트랜잭션의 범위를 완전히 감싸야 한다. 이 질문에 답할 수 있으면 "락을 써 본 사람"과 "락과 트랜잭션을 함께 써 본 사람"이 갈린다.

락 키는 어떻게 설계하나요? 추가

기준은 "동시에 만지면 깨지는 자원 하나 = 좌석 하나"다. 그 자원의 식별자를 키에 넣는다(lock:order:42). 여기서 양쪽으로 실수할 수 있다.

  • 너무 굵으면(lock:order) 서로 상관없는 주문끼리 줄을 서게 되어 처리량이 죽는다. 정합성은 지켜지지만 락이 병목 그 자체가 된다.
  • 너무 잘게 쪼개면 보호 범위가 새어 나간다. 한 작업이 자원 두 개를 함께 바꿔야 하는데 각각 잠그면, 그 사이에 다른 프로세스가 한쪽만 바꿔 어긋난 중간 상태를 만든다.
  • 자원 두 개를 잠가야 한다면 획득 순서를 고정한다(예: 항상 키 문자열이 작은 쪽부터). 순서가 뒤섞이면 서로가 서로를 기다리는 데드락이 생긴다. — 이건 락 일반의 규칙이고, 분산 락이라고 예외가 아니다.

운영 관점도 하나 붙이면 좋다 — lock: 같은 접두사로 네임스페이스를 분리해 두면, 사고 시 "지금 잡혀 있는 락이 무엇인가"를 SCAN으로 확인하기 쉽고 캐시 키와 섞이지 않는다.

ZooKeeper나 etcd는 왜 fencing token을 줄 수 있나요? 가산점 추가

노드들이 합의(consensus) 알고리즘으로 "연산의 순서"를 하나로 확정하기 때문이다. 순서가 확정되면 그 순서 자체가 전역에서 단조 증가하는 번호가 된다 — ZooKeeper의 순차 노드 번호나 트랜잭션 ID(zxid), etcd의 revision이 그 역할을 한다. 그 번호를 그대로 fencing token으로 쓸 수 있다.

반면 Redlock은 노드들이 서로 조율하지 않는다. 클라이언트가 독립적인 마스터 N대에 각각 따로 SET NX를 보낼 뿐이라, "전역에서 하나뿐인 순서"라는 개념이 알고리즘 안에 존재하지 않는다. 그래서 단조 증가 번호를 만들어 낼 수단도 없다(§6).

대가도 함께 말해야 균형이 잡힌다 — 합의 기반 시스템은 쓰기마다 노드 간 합의 왕복이 필요해 Redis보다 느리고, 클러스터를 하나 더 운영해야 한다. 그래서 답은 "정확성이 걸린 락이 정말 필요하다면 합의 기반 시스템을 쓰거나, 애초에 정확성을 락이 아닌 데이터 쪽에서 지킨다"이고, 실무에서는 후자가 훨씬 자주 정답이다.

재진입(reentrant) 락은 왜 필요하고, 값이 단순 토큰이면 왜 안 되나요? 추가

재진입은 같은 실행 주체가 이미 자기가 쥔 락을 한 번 더 잡는 것이다. 예를 들어 락을 잡은 메서드가 내부에서 같은 락을 잡는 다른 메서드를 호출하는 경우다. 재진입이 안 되면 자기가 자기를 기다리는 교착이 발생한다 — 상대가 없는데도 영원히 대기한다.

값이 단순 문자열 토큰이면 이걸 표현할 수 없다. "몇 번 잡았는지"를 셀 자리가 없기 때문이다. 안쪽 메서드가 끝나며 락을 풀어 버리면, 바깥 메서드는 아직 임계 구간에 있는데 좌석이 비어 버린다.

그래서 Redisson은 락 키를 Hash 자료구조로 두고 "누가(스레드 식별자) 몇 번 잡았는지"를 카운터로 관리한다. 잡을 때 카운트를 +1, 풀 때 −1, 0이 되는 순간에만 키를 삭제한다. 이 판정도 당연히 Lua로 원자화되어 있다(§7의 원리 그대로다).

이 답의 실전 가치는 결론에 있다 — 재진입, pub/sub 대기 해제, watchdog 수명 관리처럼 직접 만들면 새 버그가 되는 요소들이 이미 라이브러리에 들어 있다는 것이 "직접 구현하지 말라"의 구체적 근거다.

이 락이 실제로 잘 동작하는지 어떻게 확인하나요? 어떤 지표를 보나요? 시니어 변별 추가

먼저 "락 지표만으로는 이 문제를 볼 수 없다"는 점을 짚는 것이 이 질문의 핵심이다. 동시 진입이 일어나도 Redis 명령은 전부 정상 성공으로 응답하기 때문이다(§7). 그래서 락 쪽 지표와 자원 쪽 지표를 함께 본다.

락 쪽 — "위험이 커지고 있다"는 선행 신호

  • 락 보유 시간 p99 ÷ TTL. 이 비율이 1에 가까워지면 만료 함정이 곧 열린다. 단일 지표로 가장 유용하다.
  • 해제 Lua의 0 반환 횟수 — "내 락이 이미 남에게 넘어갔다"가 실제로 발생한 횟수다(§7-1).
  • watchdog 연장 횟수가 예상 밖으로 많으면 작업 시간 추정이 틀린 것이고, 갑자기 끊기면 정지나 네트워크 문제다.
  • 획득 실패율과 대기 시간 — 락이 병목이 되고 있는지(키가 너무 굵은지) 판단하는 근거.

자원 쪽 — "실제로 뚫렸다"는 확정 신호

  • fencing 조건에 걸려 영향 행 0으로 거부된 건수. 이 값이 0이 아니라는 것은 락이 이미 뚫렸고 데이터 쪽 방어선이 실제로 일했다는 뜻이다.
  • DB 유니크 제약 위반 건수, 멱등성 키 중복 감지 건수도 같은 성격의 신호다.

정리하면 "락이 뚫렸다"를 감지할 수 있는 유일한 지점은 방어선을 깔아 둔 자원 쪽이다. 방어선을 깔면 안전해질 뿐 아니라 관측 가능해진다는 것까지 말하면 답변이 닫힌다.

한 줄 요약
Redis 분산 락의 세 함정 — TTL 만료(자신의 정지를 인지하지 못한 채 재개하는 프로세스), 소유자 미검증 해제(DEL은 주인을 안 가림), 시계 의존(Redlock의 유효 시간 판정) — 은 모두 "락을 쥐고 있다는 믿음"과 실제의 어긋남이며, SET NX PX(없을 때만 설정 + 밀리초 TTL을 한 명령으로) + 고유 토큰 + Lua 해제 + watchdog까지가 방어 가능한 영역이고 그 너머는 구조적으로 남는다. 그래서 Redlock 논쟁의 내 결론은 락의 용도 구분이다 — 효율성(중복 작업 방지)은 단일 Redis 락으로 충분하고, 정확성이 걸린 작업은 Redlock으로 락을 강화할 게 아니라 최종 방어선을 데이터 쪽(유니크 제약·조건부 갱신·fencing token)에 두고 락은 경합 완화 최적화로 강등시킨다.
