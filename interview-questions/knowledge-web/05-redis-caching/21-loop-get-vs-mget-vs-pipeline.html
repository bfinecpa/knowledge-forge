루프 GET vs MGET vs Pipeline
Redis 성능의 지배 요인은 명령 처리가 아니라 네트워크 왕복이다

면접 질문: "여러 키를 조회할 때 루프 GET, MGET, pipeline의 차이는?"

핵심 관전 포인트 — Redis에서 키 100개를 조회할 때 진짜 비용은 명령 처리(마이크로초 단위)가 아니라 네트워크 왕복(RTT, 밀리초 단위)이다. 루프 GET은 왕복 100번 = RTT × 100이고, MGET과 pipeline은 왕복 1번으로 줄인다 — 같은 데이터를 가져오는데 지연이 수십 배 차이난다. 둘의 구분은 이렇다. MGET은 "같은 종류(String 조회)의 멀티 키 명령 하나"라서 가장 단순하지만 String GET에만 쓸 수 있고 Cluster에서는 해시 슬롯 제약을 받는다. pipeline은 "서로 다른 명령 여러 개를 응답을 기다리지 않고 몰아 보내는 전송 방식"이라 조합이 자유롭지만, 트랜잭션이 아니므로 원자성은 없다. 리뷰에서 루프 안의 GET N번을 잡아내는 눈이 이 지식의 실전 형태다.
  • 1
    비용의 정체 — Redis가 값 하나를 찾는 데는 마이크로초가 걸리는데 한 번 오가는 데는 0.5밀리초 안팎이 든다. 즉 비용의 대부분이 이동 시간이라, 질문은 "어떤 명령이 빠른가"가 아니라 "왕복을 몇 번으로 줄이는가"다.
  • 2
    세 방식의 차이 — 루프 GET은 응답을 기다렸다 다음을 보내므로 왕복 N번, MGET과 pipeline은 왕복 1번이다. 키 100개 기준 50.1ms 대 0.6ms, 약 83배이고 서버가 한 일의 양은 셋 다 똑같다.
  • 3
    MGET과 pipeline의 층위 — MGET은 명령이라 통째로 실행되어 중간 개입이 없지만 String 전용이고, pipeline은 전송 방식이라 명령 조합이 자유롭지만 사이에 남의 명령이 끼어들 수 있다. 원자성이 필요하면 MULTI/EXEC나 Lua다.

0. 질문 + 출제 의도

질문: "여러 키를 조회할 때 루프 GET, MGET, pipeline의 차이는?"

출제 의도: Redis 성능의 실제 지배 요인이 명령 처리 속도가 아니라 네트워크 왕복임을 아는지 본다. 루프 안에서 GET을 N번 치는 코드를 리뷰에서 잡는 눈 — "Redis는 빠르니까"라는 막연한 믿음이 아니라 지연이 어디서 생기는지를 분해해 본 경험이 있는지가 드러난다.

이 페이지가 겨냥하는 약점 세 가지 ① "Redis는 빠르니 몇 번 더 불러도 된다"는 감각 → 1~2절에서 µs와 ms의 자릿수를 분해하고 시간축에 실제 비례로 그려서 감각을 바꾼다.
② MGET과 pipeline을 "둘 다 묶는 것"으로 뭉뚱그리는 것 → 5~6절에서 명령(실행) vs 전송 방식이라는 층위 차이로 다시 세우고, 원자성이 왜 없는지를 도식으로 본다.
③ "왕복 1번이 정답"이라는 단순화 → 9절에서 거대한 단일 명령이 그 자체로 블로킹이 되는 반대편 함정과 배치 분할의 균형점을 다룬다.

1. RTT — 비용의 대부분은 "일한 시간"이 아니라 "오간 시간"이다

이 주제의 모든 논의가 RTT라는 약어 위에 서 있으니 먼저 풀고 가자. RTT는 Round Trip Time, 즉 "왕복 시간"이다. 요청이 클라이언트를 떠나 서버에 도착하고, 서버의 응답이 다시 클라이언트로 돌아오기까지 걸리는 전체 시간을 말한다. 편지를 부치고 답장을 받기까지의 시간이라고 보면 된다.

여기서 중요한 것은 이 시간의 대부분이 Redis가 일한 시간이 아니라 그냥 오가는 데 쓰인 시간이라는 점이다.

구간하는 일대략적 시간
명령 처리메모리의 해시 테이블에서 값 하나 찾아 반환마이크로초(µs) 단위
네트워크 왕복소켓 → 커널 → NIC → 스위치 → 반대 방향같은 데이터센터 안이라도 0.5ms 안팎

1-1. 비유 두 개로 감각을 고정한다

택배 비유 — 물건 포장(명령 처리)은 10초인데 배송 왕복이 이틀인 상황이다. 이런 상황에서 전체 시간을 결정하는 것은 포장 속도가 아니라 물건 100개를 한 상자에 담아 한 번 보내느냐, 100번 따로 보내느냐다.

장보기 비유 — 마트가 아무리 가까워도 사올 물건마다 한 번씩 다녀오면 100번을 걷는다. 계산대가 빠른 것과는 아무 상관이 없다. 목록을 적어 한 번에 다녀오는 것이 유일한 해법이다.

2. 키 100개를 세 방식으로 — 시간축에 실제 비율로 그려 본다

계산에 쓸 가정은 셋뿐이다. 이 숫자를 머리에 넣고 시작하자.

RTT (같은 데이터센터 가정)
1µs
키 하나당 서버 처리 시간 = 0.001ms
100개
조회할 키

2-1. 세 방식이 각각 무슨 일을 하는가

루프 GET
GET key1을 보내고 응답이 올 때까지 기다렸다가 GET key2를 보낸다. 앞 응답을 받아야 다음을 보내는 직렬 구조라 왕복이 키 수만큼 발생한다.
MGET
MGET key1 … key100이라는 명령 하나를 보낸다. 왕복은 1번이고, 서버는 그 안에서 100개를 찾는다.
pipeline
GET을 100개 연달아 밀어 넣고 응답 100개를 몰아서 받는다. 왕복은 역시 1번이다.
방식왕복 횟수왕복 시간서버 처리 시간합계
루프 GET1000.5ms × 100 = 50ms0.001ms × 100 = 0.1ms50.1ms
MGET10.5ms × 1 = 0.5ms0.001ms × 100 = 0.1ms0.6ms
pipeline10.5ms × 1 = 0.5ms0.001ms × 100 = 0.1ms0.6ms

2-2. 같은 시간축 위에 겹쳐 보면

여기서 나오는 흔한 오답

"루프 GET이 느린 건 Redis에 부하를 100번 주기 때문" — 틀렸다. 서버가 한 일은 0.1ms로 동일하다. 명령 파싱·디스패치가 100번 일어나는 만큼의 미세한 추가 부담은 있지만, 50ms를 만든 주범은 아니다. 주범은 "응답을 기다렸다가 다음을 보내는" 대기 100번이다.

느린 곳은 서버가 아니라 클라이언트가 기다리며 서 있는 시간이다

3. 루프 GET의 숨은 비용 — 지연보다 무서운 커넥션 풀 고갈

지연 말고 하나가 더 있다. 왕복 한 번마다 커넥션 하나를 그 시간 동안 점유하므로, 루프 GET은 커넥션 풀 고갈을 부른다.

커넥션 풀은 미리 만들어 둔 Redis 연결을 여러 스레드가 빌려 쓰고 반납하는 구조다. 요청 하나가 Redis 호출을 100번 한다면 그 요청은 커넥션을 50ms 동안 붙들고 있는 셈이다. 동시 요청이 조금만 늘어도 풀의 커넥션이 전부 대여 중이 되고, 뒤늦게 온 요청은 커넥션을 기다리는 시간이 지연에 추가로 가산된다.

왜 "비선형"인가 — 면접에서 한 줄 더 붙일 지점

커넥션이 남아 있는 동안에는 지연이 50ms에서 멈춘다. 그런데 풀이 다 차는 순간부터는 "커넥션을 기다린 시간 + 50ms"가 되고, 대기열이 길어질수록 앞사람의 50ms가 뒷사람에게 누적된다. 트래픽 증가는 선형인데 응답 시간은 어느 지점에서 절벽처럼 꺾인다.

공유 자원을 오래 붙드는 코드는 자기 지연이 아니라 남의 지연을 만든다

4. 코드 — 리뷰에서 잡아야 할 형태와 고친 형태

before 루프 GET — 왕복 100번, 커넥션 점유 50ms
List<Product> products = new ArrayList<>();
for (Long id : productIds) {                        // id가 100개라면
    String json = redis.opsForValue().get("product:" + id);여기서 왕복 1번 + 응답 대기
    products.add(parse(json));
}
// 이 한 줄이 "요청 보내고 응답 올 때까지 대기"다.
// 루프를 도는 동안 왕복 100번, 커넥션 점유 50ms.
after MGET — 왕복 1번
List<String> keys = productIds.stream()
        .map(id -> "product:" + id)
        .toList();

List<String> jsons = redis.opsForValue().multiGet(keys);MGET 하나 = 왕복 1회

// 반환 리스트는 요청한 키 순서와 같고, 존재하지 않는 키의 자리는 null이다.
// 그래서 인덱스로 원래 키와 짝지을 수 있고, null 체크는 호출부의 책임이다.

MGET 반환 규약 — 이 두 줄을 모르면 버그가 난다

① 순서가 보장된다
요청한 키 순서와 같은 순서로 돌아온다. 그래서 인덱스로 원래 키·ID를 되찾을 수 있다.
② 없는 키는 자리를 지킨 null
결과에서 빠지는 것이 아니라 null이 그 자리에 들어온다. 빠졌다고 가정하고 짝을 맞추면 전부 밀린다.

4-1. 한 걸음 더 — 부분 캐시 미스 처리까지가 실전 형태 가산점

캐시에서 100개를 요청하면 일부만 있고 일부는 없는 것이 정상이다. 여기서 "없는 것만 골라 DB에서 한 번에 가져오는" 형태까지 가야 왕복이 다시 늘지 않는다. null을 발견할 때마다 DB를 한 번씩 치면, Redis에서 없앤 N+1을 DB에서 그대로 재현하는 꼴이다.

패턴 MGET → 미스만 모아 벌크 조회 → 벌크 적재
List<String> jsons = redis.opsForValue().multiGet(keys);   // 왕복 1

List<Long> missed = new ArrayList<>();
for (int i = 0; i < keys.size(); i++) {
    if (jsons.get(i) == null) missed.add(productIds.get(i));자리(index)로 원래 id를 되찾는다
}

if (!missed.isEmpty()) {
    List<Product> fromDb = productRepository.findAllById(missed);DB도 IN 절 한 번
    // 캐시에 되채우는 것도 pipeline이나 MSET으로 묶어 한 왕복에 끝낸다.
}
// 흔한 실수: null을 만날 때마다 DB를 한 번씩 조회 → Redis에서 없앤 N+1이 DB에서 부활한다.

5. MGET vs pipeline — "명령 하나" vs "전송 방식"

둘 다 왕복을 1번으로 줄이지만 층위가 다르다. MGET은 Redis가 제공하는 명령이고, pipeline은 클라이언트가 명령들을 보내는 방식이다. 명령과 전송 방식은 애초에 같은 종류의 것이 아니다. 이 문장을 먼저 말하고 시작하면 답이 흔들리지 않는다.

비유로 고정하기 — 주문서 한 장 vs 봉투 하나

MGET = 품목 100개가 적힌 주문서 한 장
창구 직원은 이 한 장을 처리하는 동안 다른 주문서를 받지 않는다. 대신 이 주문서 양식에는 "String 조회"만 적을 수 있다.
pipeline = 주문서 100장을 한 봉투에 넣어 보내기
봉투 덕분에 배달은 한 번이지만, 창구는 봉투를 뜯어 한 장씩 처리한다. 그 사이에 남이 낸 주문서가 끼어들 수 있다. 대신 양식은 자유다.
봉투는 묶어줄 뿐 지켜주지 않는다 — pipeline에 원자성이 없다는 말의 비유적 표현

5-1. MGET은 명령이다 — 통째로 실행된다

MGET은 "String 타입 키 여러 개를 한 번에 읽는" 하나의 명령이다. 서버는 이것을 명령 하나로 받아 통째로 실행한다.

Redis는 명령을 한 번에 하나씩 실행한다(명령 실행이 단일 스레드로 이뤄진다). 그래서 한 명령이 실행되는 동안에는 다른 클라이언트의 명령이 중간에 끼어들 수 없다. MGET이 키 100개를 읽는 동안 다른 클라이언트가 그중 50번째 키를 바꾸는 일은 일어나지 않는다. 즉 MGET의 결과는 어느 한 시점의 일관된 스냅샷이다.

대신 제약이 분명하다. GET의 묶음만 가능하다. Hash를 읽거나(HGETALL) TTL을 갱신하는(EXPIRE) 명령을 섞을 수 없다. 쓰기 쪽 짝으로는 MSET이 있다.

5-2. pipeline은 전송 방식이다 — "몰아 보낸다"의 실체

pipeline을 "명령을 몰아 보내는 것"이라고만 설명하면 감이 안 오니, 실제로 무슨 일이 일어나는지 풀어 보자.

보통의 요청-응답은 핑퐁이다. 클라이언트는 명령 하나를 소켓에 쓰고, 응답이 돌아올 때까지 블로킹된 채 기다리고, 응답을 읽은 뒤에 다음 명령을 쓴다. 이 "기다림"이 왕복 시간이고, 명령 수만큼 반복된다.

pipeline은 이 기다림을 없앤다. 클라이언트는 응답을 기다리지 않고 명령 1, 2, 3, …, 100을 연달아 소켓에 밀어 넣는다. 그리고 나서 응답 100개를 순서대로 읽는다. 서버는 서버대로 소켓에 도착하는 명령들을 받는 대로 처리해 응답을 차례로 돌려보낸다.

code pipeline — 서로 다른 명령을 한 왕복에 (Spring Data Redis)
List<Object> results = redisTemplate.executePipelined(
    (RedisCallback<Object>) conn -> {
        for (Long id : productIds) {
            conn.stringCommands().get(("product:" + id).getBytes());버퍼에 담기만 한다
        }
        // 여기서 각 호출은 "명령을 버퍼에 담는" 동작이다.
        // 응답을 기다리지 않으므로 반환값도 이 자리에서는 의미가 없다.

        conn.hashCommands().hGetAll("category:map".getBytes());MGET으로는 불가능한 부분
        // 타입이 다른 명령을 같은 왕복에 섞는다 — pipeline만 되는 일.

        return null;
        // 콜백의 반환값은 무시된다. 결과는 executePipelined가
        // 응답을 보낸 순서대로 모아 List로 돌려준다.
    });

6. "pipeline에는 원자성이 없다" — 그 말의 실체

여기서 결정적인 사실이 나온다. pipeline 안의 명령들 사이에는 다른 클라이언트의 명령이 끼어들 수 있다.

서버 입장에서 pipeline으로 온 100개는 "한 덩어리"가 아니라 그냥 순서대로 도착한 개별 명령 100개다. 다른 클라이언트가 보낸 명령이 그 사이에 도착하면 서버는 그것도 순서대로 처리한다.

헷갈리기 쉬운 지점 — "원자성이 없다"가 "응답이 뒤섞인다"는 뜻은 아니다 내 응답이 남의 응답과 섞여 오는 일은 없다. Redis는 커넥션마다 그 커넥션이 보낸 명령의 순서대로 응답을 돌려주므로, 내가 GET a, GET b, GET c를 이 순서로 밀어 넣었다면 응답도 정확히 그 순서로 내 소켓에 들어온다. 그래서 결과 리스트의 i번째가 i번째 명령의 결과라는 짝짓기는 안전하다.
깨지는 것은 순서가 아니라 시점의 일관성이다 — "내 명령들 사이에 남의 쓰기가 실행될 수 있다"가 정확한 표현이다.

7. pipeline vs MULTI/EXEC vs Lua — 축을 나누면 흔들리지 않는다

원자적 일괄 실행이 필요하다면 pipeline이 아니라 MULTI/EXEC다. MULTI를 보내면 서버는 그 뒤에 오는 명령들을 실행하지 않고 큐에 쌓아둔다. EXEC를 받는 순간 쌓아둔 명령들을 통째로 실행하고, 그 사이에 다른 클라이언트의 명령이 끼어들지 않는다.

둘은 배타적이지 않다. MULTI/EXEC 자체를 pipeline에 실어 보내면 원자성을 얻으면서 왕복도 아낄 수 있다. "둘 중 하나"가 아니라 "서로 다른 층의 도구"라는 것이 이 표의 진짜 메시지다.

8. Cluster에서는 MGET이 그냥 안 된다 확장 시 코드가 깨지는 지점

단일 인스턴스에서 잘 돌던 MGET이 Redis Cluster로 옮기는 순간 깨진다. 원리를 알아야 미리 대비할 수 있으니 순서대로 보자.

1
Cluster는 키를 슬롯으로 나눠 노드에 분산한다. Redis Cluster는 전체 키 공간을 16384개의 해시 슬롯으로 나눠 두고, 키 이름을 해싱해서 그 키가 어느 슬롯에 속하는지 정한다. 그리고 각 노드가 슬롯 범위를 나눠 가진다. 노드가 3대라면 대략 5461개씩 맡는 식이다.
2
그리고 한 명령은 한 노드에서만 실행된다. 클라이언트가 명령을 보낼 때 그 명령이 다루는 키의 슬롯을 계산해 담당 노드로 보내는데, 명령 하나가 여러 노드에 걸쳐 실행되는 메커니즘은 없다.
3
둘을 합치면 결론이 나온다. MGET의 키들이 서로 다른 슬롯에 속하면 서로 다른 노드에 있고, 한 명령으로는 실행할 수 없다. 그래서 Redis는 CROSSSLOT 에러를 돌려준다.

이 제약이 중요한 진짜 이유

"단일 인스턴스에서 Cluster로 확장하는 순간 애플리케이션 코드가 깨지는" 대표 사례이기 때문이다. 확장은 보통 트래픽이 감당이 안 될 때 급하게 하는 일이라, 그 시점에 코드가 깨지는 것을 발견하면 최악이다.

확장 계획 단계에서 미리 아는 것이 이 지식의 값이다

9. 몰아 보내기도 과하면 블로킹 폭탄 가산점 포인트

왕복을 아끼는 것이 좋다고 해서 한 번에 수만 개를 묶으면 반대편 문제가 생긴다. 이유는 Redis가 명령을 한 번에 하나씩 처리한다는 데 있다.

① 거대한 MGET = 절대적 블로킹
키 10만 개짜리 MGET은 명령 하나다. 다 찾을 때까지 Redis는 다른 어떤 명령도 처리하지 못한다. 키 하나에 1µs만 잡아도 100ms 동안 서버 전체가 멈춘다.
② 거대한 pipeline도 정도만 덜하다
사이에 다른 클라이언트가 끼어들 수는 있지만, 서버는 읽어 들인 명령들을 연달아 처리한다. 10만 개를 소화하는 동안 다른 클라이언트의 대기 시간이 계속 늘어난다.
③ 응답 쪽도 부담이다
10만 개의 응답은 클라이언트가 다 읽어 갈 때까지 서버의 출력 버퍼에 쌓여 메모리를 부풀리고, 클라이언트에서도 결과 리스트 10만 개가 힙에 통째로 올라온다.

요청은 작은데 응답이 거대한 비대칭이 여기서 생긴다. 보내는 쪽은 짧은 명령 목록이라 부담이 없어 보이지만, 돌아오는 쪽은 데이터 전체다. KEYS 명령이 위험한 것과 정확히 같은 계열의 문제다.

after+ 배치로 잘라 보내기 — 상한이 없는 목록에는 필수
static final int BATCH = 500;

List<String> result = new ArrayList<>(keys.size());
for (int i = 0; i < keys.size(); i += BATCH) {왕복 1번짜리 호출을 여러 번
    List<String> chunk = keys.subList(i, Math.min(i + BATCH, keys.size()));
    result.addAll(redis.opsForValue().multiGet(chunk));
}
// 키 10,000개 → 왕복 20번 = 약 10ms.
// 루프 GET(5초)과는 비교가 안 되면서, 서버를 한 번에 오래 붙들지도 않는다.

목표를 정확히 표현하면 — 이 문장이 시니어 신호다

"왕복 1번"이 목표가 아니라, 키 수 N에 비례하던 왕복을 N과 무관한 상수 몇 번으로 만드는 것이 목표다

왕복 최소화와 단일 명령 비대화 사이에 균형점이 있다는 감각까지 말하면 답이 완성된다. "무조건 묶어라"로 끝나는 답과 여기서 갈린다.

10. 리뷰의 눈 — "루프 × 원격 호출"은 저장소를 가리지 않는다 시니어 변별

루프 안의 원격 호출을 보면 반사적으로 두 가지를 묻는다. "N이 얼마까지 커질 수 있는가", "왕복당 비용이 얼마인가". 이 두 질문이 습관이 되어 있는지가 리뷰어의 수준을 가른다.

그리고 이 패턴은 Redis만의 것이 아니다. JPA의 N+1 문제와 구조가 완전히 같다. N+1은 주문 목록 10건을 조회하고(쿼리 1번), 각 주문의 회원을 지연 로딩으로 꺼내면서(쿼리 10번) 총 11번의 쿼리가 나가는 현상이다. 여기서 왕복 10번을 만드는 것은 루프 안에 원격 호출이 들어 있다는 사실 그 자체다.

10-1. 리뷰 코멘트의 형태 — 네 가지가 한 세트다

이렇게 쓴다 "productIds가 화면 요구사항상 최대 몇 개인가요? 100개면 이 루프가 왕복 100번이라 p99가 수십 ms 늘어납니다. multiGet으로 묶고, 상한이 없다면 1,000개 단위로 잘라주세요."
① 문제 지적
루프 안 GET N번
② 근거
왕복 100번 → p99 수십 ms
③ 대안
multiGet으로 묶기
④ 상한 확인
N이 무한하면 배치 분할까지

"N+1이네요"라고만 쓰면 상대는 무엇을 얼마나 고쳐야 하는지 모른다. 특히 마지막의 상한 확인이 중요한데, N이 무한히 커질 수 있는 코드는 묶는 것만으로는 해결되지 않고 배치 분할까지 필요하기 때문이다(9절).

11. 면접 전날 인출 카드 · 꼬리질문 셀프 테스트

이 주제에서 반드시 입에 붙여야 할 여섯 개

① µs vs ms
처리는 마이크로초, 왕복은 밀리초. 비용의 약 500배가 이동 시간
② 50.1ms vs 0.6ms
키 100개 기준 약 83배. 서버 처리량은 셋 다 0.1ms로 동일
③ 명령 vs 전송 방식
MGET = 명령(통째 실행·String 전용) / pipeline = 전송(조합 자유·원자성 없음)
④ 성능 vs 원자성
pipeline = 성능, MULTI/Lua = 원자성. 분기까지면 Lua
⑤ CROSSSLOT
Cluster는 16384 슬롯, 한 명령은 한 노드 → 해시 태그 {}(편중 대가) 또는 노드별 분배
⑥ 상수 왕복 + 배치
목표는 "1번"이 아니라 "N과 무관한 상수". 한 덩어리는 수백~수천으로

세 개의 연상 — "MGET은 주문서 한 장, pipeline은 봉투 하나"(층위 구분) · "봉투는 묶어줄 뿐 지켜주지 않는다"(원자성 없음) · "루프 안의 원격 호출을 보면 N을 묻는다"(JPA N+1과 같은 냄새).

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼쳐서 맞춰 본다. 답을 눈으로 읽는 것보다 인출 훈련이 훨씬 오래 간다.

MGET과 pipeline으로 GET을 묶는 것, 결과가 같다면 무엇을 쓰나요? 최다 빈출힌트: 이유가 셋이다 — 서버 · 코드 · 시점

String 조회만이라면 MGET이 낫다. 이유가 셋이다.

① 서버 부담이 적다. 명령 파싱과 디스패치가 100번이 아니라 1번이다.
② 코드가 단순하다. multiGet(keys) 한 줄과 콜백 안의 루프는 읽는 부담이 다르다.
③ 한 명령이라 그 시점의 일관된 조회가 된다. pipeline은 명령 사이에 남의 쓰기가 끼어들 수 있어 100개가 서로 다른 시점의 값일 수 있다.

pipeline은 명령 종류가 섞일 때, 또는 Cluster에서 노드별 분배가 필요할 때 꺼내는 도구다.

한 줄로는 — "기본은 MGET, 조합이 필요하면 pipeline"
pipeline과 MULTI/EXEC의 차이는요?힌트: 해결하는 문제가 애초에 다르다 + 배타적이지 않다

pipeline은 전송 최적화(왕복 절약)이고 MULTI/EXEC는 실행 보장(원자적 일괄 실행)이다. 해결하는 문제 자체가 다르다.

pipeline 안의 명령들 사이에는 다른 클라이언트의 명령이 끼어들 수 있다. MULTI/EXEC는 명령을 큐에 쌓아뒀다가 EXEC 시점에 통째로 실행하므로 중간 개입이 없다.

둘은 배타적이지 않다. MULTI/EXEC 자체를 pipeline에 실어 보내면 원자성을 얻으면서 왕복도 아낄 수 있다.

다만 MULTI/EXEC에도 한계가 있다. 중간 조회 결과로 분기하지 못한다 — 큐에 쌓인 명령들은 서로의 결과를 볼 수 없기 때문이다. "값을 읽어 보고 조건에 맞으면 쓴다"는 check-then-act가 필요하면 WATCH(감시하던 키가 바뀌면 EXEC를 실패시키는 낙관적 방식)나 Lua 스크립트로 가야 한다.

루프 GET인데 왕복을 못 줄이는 상황도 있나요?힌트: 다음 키를 미리 알 수 있는가

있다. 앞 조회의 결과가 다음 조회의 키를 결정하는 의존 체인이면 묶을 수 없다. 예를 들어 GET session:abc로 얻은 userId로 GET user:{userId}를 조회해야 한다면, 두 번째 키를 미리 알 수 없으므로 한 왕복에 담을 수가 없다.

이때의 답은 둘이다.

① Lua 스크립트로 체인 전체를 서버에서 실행한다. 왕복 1번으로 보내고 서버 안에서 "읽고 → 그 값으로 다음 키를 만들고 → 또 읽는" 과정을 끝낸다.
② 자료구조 설계를 바꿔 한 번에 읽히게 만든다. 함께 읽히는 필드를 Hash 한 키에 모아두면 HGETALL 한 번으로 끝난다.

여기서 한 걸음 더 — "왕복 수는 코드가 아니라 데이터 모델이 결정할 때가 많다"

루프를 아무리 고쳐도 안 줄어드는 왕복은 대개 키를 잘못 쪼개 놓은 결과이고, 진짜 해법은 키 설계로 돌아가는 것이다.

이 지식이 코드 리뷰에서 어떻게 쓰이나요? 시니어 변별힌트: 두 개의 질문 + 네 개의 코멘트 구성 요소

루프 안의 원격 호출을 보면 반사적으로 두 가지를 묻는다. "N이 얼마까지 커질 수 있는가", "왕복당 비용이 얼마인가".

그리고 이 패턴은 Redis만의 것이 아니다. JPA의 N+1과 구조가 완전히 같다 — 루프 안에 원격 호출이 있다는 사실 그 자체가 왕복 N번을 만든다. 해법의 형태도 같다(fetch join · @BatchSize ↔ MGET · pipeline). HTTP API 호출도 마찬가지고, 답은 벌크 엔드포인트다.

코멘트는 네 가지가 한 세트다 — 문제 지적 + 근거 + 대안 + 상한 확인. "N+1이네요"라고만 쓰면 상대는 무엇을 얼마나 고쳐야 하는지 모른다. 특히 상한 확인이 중요한데, N이 무한히 커질 수 있는 코드는 묶는 것만으로는 해결되지 않고 배치 분할까지 필요하기 때문이다.

"루프 × 네트워크 왕복"은 저장소가 무엇이든 지연을 N배로 만든다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

pipeline으로 보낸 명령 중 하나가 에러나면 나머지는 어떻게 되나요? 시니어 변별힌트: pipeline은 트랜잭션이 아니다 — 그 말의 실무적 귀결

나머지는 그대로 실행된다. pipeline은 트랜잭션이 아니므로 롤백이라는 개념 자체가 없다. 실패한 명령의 응답 자리에 에러가 담겨 돌아오고, 앞뒤 명령의 결과는 정상적으로 반영된다.

그래서 코드에서 결과 리스트를 순회하며 항목별로 확인해야 한다. "예외가 안 났으니 다 성공"이라고 가정하는 것이 가장 흔한 실수다 — 부분 성공이 정상 동작인 도구다.

MULTI/EXEC로 바꾸면 해결될까? 여기서 한 칸 더 들어갈 수 있다. MULTI/EXEC는 중간 개입을 막아줄 뿐, "실행 중 하나가 실패하면 앞의 것을 되돌린다"는 RDB식 롤백을 제공하지 않는다. 그래서 "부분 실패를 어떻게 감지하고 보정할 것인가"는 어느 쪽을 쓰든 애플리케이션이 설계해야 하는 문제다.

"묶어 보냈다"와 "다 되거나 다 안 되거나"는 완전히 다른 이야기다
여러 스레드가 동시에 각자 pipeline을 보내면 응답이 섞이지 않나요?힌트: "원자성이 없다"와 "순서가 깨진다"는 다른 말이다

섞이지 않는다. Redis는 커넥션마다 그 커넥션이 보낸 명령의 순서대로 응답을 돌려준다. 내가 GET a → GET b → GET c 순으로 밀어 넣었다면 응답도 정확히 그 순서로 내 소켓에 들어오고, 결과 리스트의 i번째는 i번째 명령의 결과다.

깨지는 것은 순서가 아니라 시점의 일관성이다. 다른 클라이언트의 명령이 서버의 실행 순서 사이에 들어올 수 있다는 것이지, 내 응답 스트림에 남의 응답이 섞여 오는 것이 아니다. 이 둘을 구분해 말하면 "원자성 없음"을 정확히 이해한 것으로 들린다.

실무적으로 주의할 것은 오히려 다른 쪽이다 — 커넥션 풀에서 빌린 커넥션 위에서 pipeline이 진행되므로, 그 커넥션을 다른 스레드와 공유하는 구조라면 문제가 된다. 그래서 pipeline은 커넥션 하나를 그 작업 동안 온전히 점유하는 방식으로 구현된다.

비동기·논블로킹 클라이언트를 쓰면 pipeline이 따로 필요 없나요?힌트: pipeline의 본질은 "기다리지 않고 보내는 것"이었다

본질을 보면 같은 이야기다. pipeline이 없앤 것은 "응답을 기다리는 시간"이었다. 그러므로 논블로킹 API로 명령들을 먼저 다 보내 놓고 나중에 결과를 모으는 방식이라면, 형태는 달라도 왕복이 겹쳐지는 효과는 같다.

다만 착각하기 쉬운 지점이 있다. 같은 라이브러리를 쓰더라도 동기(블로킹) API를 호출하는 한 루프는 여전히 왕복 N번이다. "비동기 클라이언트를 쓰니 괜찮다"가 아니라 "응답을 기다린 뒤 다음을 보내는 코드인가"가 판단 기준이다.

그리고 어느 방식이든 9절의 균형은 그대로 적용된다 — 한 번에 너무 많은 명령을 밀어 넣으면 서버 점유와 버퍼 부담은 똑같이 생긴다.

기준은 API의 이름이 아니라 "기다림이 루프 안에 있는가"다
MGET 결과에서 값이 없는 키는 어떻게 표현되나요? 캐시 미스 처리는요?힌트: 자리를 지키는 null + 미스를 다시 N번 조회하지 않기

없는 키의 자리에는 null이 들어온다. 결과에서 빠지는 것이 아니라 요청한 순서 그대로 자리를 지키므로, 인덱스로 원래 키·ID와 짝지을 수 있다. 반대로 "없는 건 빠져서 온다"고 가정하면 짝이 전부 밀려 엉뚱한 데이터를 반환하는 버그가 난다.

미스 처리에서 실수가 나온다. null을 만날 때마다 DB를 한 번씩 조회하면, Redis에서 없앤 N+1을 DB에서 그대로 재현하는 꼴이다. 올바른 형태는 미스된 키들을 모아 한 번에 벌크 조회하고(IN 절 등), 되채우기도 pipeline이나 MSET으로 묶는 것이다.

한 걸음 더 나가면 — "없음"이라는 사실 자체를 캐싱할지도 결정해야 한다. 존재하지 않는 키를 매번 DB까지 물어보는 구조는 캐시가 막아주지 못하는 트래픽을 만든다.

Cluster에서 어차피 노드별로 쪼개 보낸다면, MGET을 쓸 이유가 있나요? 시니어 변별힌트: 왕복 수는 노드 수에 비례하지 키 수에 비례하지 않는다

있다. 쪼갠 뒤에도 각 노드로 가는 것은 그 노드 몫의 키를 담은 MGET 한 번이기 때문이다. 노드가 3대라면 왕복은 키 수 N이 아니라 노드 수 3에 비례하고, 그마저 병렬로 나가면 체감 지연은 사실상 왕복 1번에 가깝다.

즉 목표는 그대로 유지된다 — "N에 비례하던 왕복을 N과 무관한 상수로". Cluster에서는 그 상수가 1이 아니라 노드 수가 될 뿐이다.

다만 확인할 것이 셋이다. ① 쓰는 라이브러리가 자동으로 쪼개 주는지, ② 쪼갠 요청을 병렬로 보내는지 순차로 보내는지(순차면 왕복이 노드 수만큼 직렬로 쌓인다), ③ 결과를 원래 요청 순서로 되돌려 주는지. 이 셋을 확인해 봤다고 말하면 실제로 써 본 사람으로 들린다.

왕복 비용을 줄인다면서 Lua 스크립트를 남발하면 어떤 문제가 생기나요?힌트: 원자성의 대가는 무엇이었나

Lua 스크립트는 실행되는 동안 원자적이다. 뒤집어 말하면 그 시간 내내 다른 어떤 명령도 처리되지 않는다. 왕복을 아끼려고 무거운 로직을 스크립트로 옮기면, 9절의 "거대한 단일 명령" 문제를 그대로 만드는 것이 된다.

그래서 판단 기준은 이렇다. Lua는 "원자성이 필요할 때" 쓰는 도구이지 "왕복을 줄이려고" 쓰는 도구가 아니다. 왕복만이 목적이라면 MGET이나 pipeline이 더 나은 선택이다 — 서버를 오래 붙들지 않기 때문이다.

쓰더라도 짧게 유지하고, 루프 안에서 방대한 키를 도는 스크립트는 피한다. 원자성이라는 이득과 서버 점유라는 비용을 함께 말하면 균형 잡힌 답이 된다.

배치 크기는 어떻게 정하나요? "수백~수천"의 근거가 뭔가요?힌트: 고정된 정답이 아니라 두 곡선이 만나는 지점

고정된 정답은 없다. 두 가지 비용이 반대 방향으로 움직이기 때문이다 — 배치를 키우면 왕복 수가 줄고(이득), 한 명령의 서버 점유 시간과 응답 크기가 커진다(비용). 균형점은 값 하나의 크기, 서버가 감당해야 하는 다른 트래픽, 허용 지연에 따라 달라진다.

결정하는 방식으로 답하면 좋다. ① 값 하나가 크다면(수십 KB) 배치를 작게 — 응답 총량이 먼저 문제가 된다. ② 실제로 재 본다 — 배치 크기를 바꿔 가며 p99와 서버 지표를 관찰하면 효과가 평평해지는 구간이 보인다. ③ 상한을 코드에 박아 둔다 — 입력 목록 크기에 상한이 없으면 언젠가 사고가 난다.

핵심은 "왕복이 N에 비례하지 않게 만드는 것"이 목적이고, 배치 크기는 그 목적을 지키는 선에서 서버를 오래 붙들지 않을 만큼 작게 잡는다는 것이다.

루프 GET을 그냥 병렬 스레드로 100개 동시에 날리면 안 되나요?힌트: 왕복은 줄었는가, 아니면 자원으로 덮었는가

지연은 줄어든다. 그러나 문제를 자원으로 덮은 것이다. 왕복 100번은 그대로 있고, 그것을 동시에 진행시키기 위해 커넥션 100개와 스레드 100개를 쓴 것뿐이다.

대가가 분명하다. ① 커넥션 풀이 그만큼 소모되어 같은 풀을 쓰는 다른 요청이 밀린다(3절). ② 스레드 생성·컨텍스트 스위칭 비용이 붙는다. ③ 동시 요청이 늘면 이 방식은 곱하기로 커진다 — 요청 10개면 커넥션 1,000개다.

반면 MGET·pipeline은 왕복 자체를 없앤다. 커넥션 하나로 같은 일을 끝내므로 동시성이 늘어도 자원 사용이 선형으로 폭증하지 않는다.

"병렬로 덮기"와 "왕복을 없애기"는 부하가 늘었을 때 완전히 다르게 무너진다
한 줄 요약
여러 키 조회의 비용은 명령 처리(µs)가 아니라 네트워크 왕복(ms)이 지배하므로 루프 GET(왕복 N번)은 MGET이나 pipeline(왕복 1번)으로 묶어야 한다 — MGET은 String 전용 단일 명령이라 중간 개입 없이 통째로 실행되는 반면 pipeline은 전송 방식일 뿐이라 명령 사이에 남의 명령이 끼어들 수 있고(원자성 없음, 원자성이 필요하면 MULTI/EXEC나 Lua), 여기에 Cluster의 해시 슬롯 제약과 "너무 큰 배치는 그 자체가 블로킹"이라는 균형까지 말하면 왕복을 분해해 본 경험이 증명된다.
