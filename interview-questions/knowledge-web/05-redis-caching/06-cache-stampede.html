캐시 스탬피드는 "동시 요청이 몰리는 인기 키"가 "만료되는 순간", 재계산이 끝나기 전까지 도착하는 모든 요청이 전부 미스를 보고 전부 DB로 직행하는 현상이다. 발생 조건은 ① 인기 키 ② 비싼 재계산 ③ 만료 순간의 동시 미스 — 셋이 겹칠 때만 터지므로 트래픽이 적은 환경에서는 존재하지 않는 문제다. 해결은 락(single flight)으로 재계산 횟수를 1회로 묶거나, 논리적 만료(soft TTL)로 물리적 미스 자체를 없애거나, TTL 지터·사전 갱신(refresh-ahead)으로 만료 순간의 동시성을 흩뜨리는 것 — 각각 "미스 후 수습 / 미스 제거 / 만료 분산"이라는 다른 지점을 공략하고 각각 다른 대가(락은 대기와 새 장애점, 논리적 만료는 의도적으로 낡은 값을 서빙)를 치른다.
출제 의도 — 해법의 개수가 아니라 문제의 발생 조건을 본다
인기 키 하나의 만료가 DB를 뚫는 이 현상은 "트래픽이 많아야만 존재하는 문제"의 대표라, 대용량 경험의 진위를 가리는 데 효과적이다. 질문은 "3가지 이상"을 요구하지만, 실제 채점은 해결책을 여러 개 아는지보다 문제의 발생 조건을 정확히 그리는지에서 갈린다. 그래서 이 페이지의 무게중심은 해법 목록(§7~§10)이 아니라 §2 세 조건과 §3 자기 강화 붕괴에 있다.

1. 미스 창 — look-aside에 원래부터 뚫려 있는 구멍

Look-aside(cache-aside) 패턴의 기본 흐름은 "캐시 조회 → 미스면 DB 조회 → 캐시 적재"다. 이 흐름 자체에 구조적 빈틈이 하나 있다.

미스를 확인한 시점과 캐시가 다시 채워지는 시점 사이에는 시간이 흐른다. DB 쿼리를 실행하고 결과를 받고 가공해서 Redis에 넣는 시간이다. 그리고 그 시간 동안 도착하는 모든 요청도 똑같이 미스를 본다. 캐시는 아직 비어 있으니까.

이 페이지의 모든 것이 여기서 나온다
캐시에는 "지금 누가 채우는 중"이라는 상태를 표현할 방법이 없다.

그래서 미스를 본 요청들은 서로의 존재를 모른 채 각자 DB로 간다. 이 구간을 미스 창(window)이라고 부르자 — 창이 열려 있는 동안 들어온 요청은 전부 밖(DB)으로 나간다. 뒤에 나올 해법 넷은 전부 "이 창을 어떻게 할 것인가"에 대한 서로 다른 답이다.

창이 열려 있는 동안 도착한 요청은 전부 밖으로 나간다. 평소에 문제가 안 되는 이유는 창이 좁고(재계산이 빠르고) 그 사이 도착하는 요청이 몇 개 없기 때문이지, 이 구멍이 없어서가 아니다.

재계산이 5ms 걸리고 그 키가 초당 2번 읽힌다면 창 안에 들어오는 요청은 사실상 0개다. 같은 코드, 같은 구멍인데도 아무 일이 일어나지 않는다. 그래서 이 문제는 코드 리뷰만으로는 잡히지 않고, 트래픽을 대입해 봐야 보인다.

2. 세 조건 — "인·비·만"이 겹칠 때만 터진다

스탬피드는 다음 세 조건이 동시에 겹칠 때 터진다. 하나라도 빠지면 안 터진다는 점이 이 문항의 핵심이다.

인
① 인기 키
모두가 같은 키 하나를 읽는가
비
② 비싼 재계산
그 키를 채우는 쿼리가 느린가
만
③ 만료 순간
그 키가 물리적으로 사라지는가
인
인기 키 — 그 키 하나에 초당 수백~수천 요청이 몰린다 메인 페이지 인기 목록, 실시간 랭킹처럼 모든 사용자가 같은 키를 읽는 데이터가 전형이다. 반대로 사용자별로 키가 갈리는 데이터(user:{id}:profile)는 한 키에 요청이 몰리지 않으므로 애초에 대상이 아니다. 전체 트래픽이 아무리 커도 키가 잘게 쪼개져 있으면 스탬피드는 성립하지 않는다.
비
비싼 재계산 — 캐시를 채우는 원본 쿼리가 느리다 집계, 다중 조인, 수백 ms~수 초. 창의 폭이 곧 재계산 시간이므로 느릴수록 창이 넓어지고 그만큼 많은 요청이 창 안에 들어온다. 이 조건은 다음 절의 악순환에서 스스로 악화되는 유일한 조건이라는 점에서 특히 중요하다.
만
만료 순간 — TTL이 다해 그 키가 캐시에서 사라진다 창이 열리는 계기다. 조건 ①②는 평소에도 계속 참이지만 아무 일도 없다가, ③이 성립하는 그 한 순간에 터진다. 그래서 "잘 돌던 서비스가 특정 시각에만 갑자기"라는 얼굴로 나타난다.
해법 넷은 이 곱셈식에서 어느 항을 0에 가깝게 만드는가로 갈린다 — 락은 결과값을 1로, 논리적 만료는 ③을 제거, 지터는 ③의 동시성을 흩뜨린다.
면접에서 이 순서로
정의 → 세 조건 → 그 조건에 숫자 대입 → 그다음에야 해법

"해결 방법 3가지"라는 질문을 받자마자 해법부터 나열하면 외운 목록이 된다. "초당 1,000 요청 × 재계산 500ms = 창 안 500개"처럼 숫자를 대입해 보이는 한 문장이 들어가면, 그 뒤의 해법 목록이 전부 그 숫자를 줄이려는 시도로 읽힌다.

3. 진짜 문제는 "N번 중복 실행"이 아니라 자기 강화 붕괴다

§1의 타임라인에는 거짓말이 하나 섞여 있다
실제로는 t=500ms에 안 끝난다. 500개가 동시에 때린 순간부터 그 500ms라는 전제 자체가 무너지기 때문이다. 이 절이 주니어 답변과 시니어 답변이 갈리는 지점이다.
왼쪽은 같은 키 안에서의 악화, 오른쪽은 다른 기능으로의 전파. 스탬피드가 "성능 낭비"가 아니라 "장애"인 이유는 오른쪽 때문이다.

애플리케이션의 DB 커넥션 풀은 유한하고(보통 인스턴스당 수십 개), 스탬피드에 걸린 요청들이 그 커넥션을 전부 점유한다. 그러면 그 키와 아무 상관 없는 다른 API의 쿼리까지 커넥션을 못 얻어 대기한다. 캐시 하나의 문제가 공유 자원(커넥션 풀)을 통해 서비스 전체로 번지는 경로다.

한 문장으로 고정 — 여기서 답변 수준이 갈린다
"쿼리가 N번 중복 실행돼서 비효율적이다"가 아니라
"자기 강화 붕괴가 시작되고 그것이 서비스 전체로 번진다"까지 그려야 한다.

앞 문장은 낭비를 말하고 뒤 문장은 장애를 말한다. 같은 현상을 설명해도 이 차이가 "겪어 봤는가"의 신호로 읽힌다.

3-1. 이름의 유래 — 그림이 곧 정의다

thundering herd 천둥 치듯 몰려드는 소떼

문(캐시)이 열려 있을 때는 소떼가 각자 흩어져 아무 일도 없다가, 문이 닫히는 순간 소떼 전체가 울타리(DB)로 한꺼번에 돌진한다.

stampede 가축 떼의 일제 질주

가축 떼가 놀라 일제히 같은 방향으로 내달리는 것을 가리키는 말이다. 개체 수가 문제가 아니라 방향과 시각이 같다는 것이 재앙의 이유다.

두 단어 모두 "평소엔 조용하다가 한 순간에 전부가 같은 방향으로 몰린다"는 성질을 짚고 있고, 그것이 이 문제의 본질이다. 이름을 풀어 설명하는 것만으로 정의의 절반이 끝난다.

4. 스탬피드가 아닌 것 — 증상이 같아도 처방이 다르다

비슷해 보이는 문제들과 반드시 갈라 놔야 한다. 증상(미스가 DB를 때린다)이 같아도 원인이 다르면 처방이 다르기 때문이다. 실제 장애 대응에서 이 판별을 틀리면 엉뚱한 처방으로 시간을 버린다 — 관통에 락을 걸어 봐야 락 뒤에도 값은 없다.

스탬피드는 이 중 "멀쩡히 운영 중인 캐시에서, 인기 키 하나의 만료"라는 가장 국소적인 조건으로 터진다. 캐시는 정상이고 히트율도 높은데 특정 순간에만 DB가 뚫린다는 것이 이 문제의 얼굴이다.

5. 전제 지식 — 왜 synchronized로는 안 되는가

첫 번째 해법(락)에 들어가기 전에 깔아야 할 것이 있다. 락은 "동시에 한 명만 들어갈 수 있는 문"이다. 자바의 synchronized나 ReentrantLock은 JVM 힙에 있는 객체를 그 문으로 삼는다. 그래서 조율 범위가 그 JVM 안의 스레드들로 한정된다.

JVM마다 별개의 락 객체가 있으므로 서버 대수만큼 락이 존재하고, 결국 재계산도 서버 대수만큼 일어난다. 락의 개수를 세어 보는 것이 이 그림의 요점이다.
SET lock:ranking <내 식별자> NX PX 10000
# NX = Not eXists, 즉 "그 키가 없을 때만 쓴다"
#      → 이미 누가 잡았으면 실패한다. 성공한 한 명만 락 소유자다.
# PX 10000 = 락에 10초 수명을 준다
#      → 잡은 프로세스가 죽어도 10초 뒤 자동 해제된다.
#        이게 없으면 아무도 재계산하지 못하는 영구 교착이 된다.
암기 — NX 한 글자가 핵심이다
"있는지 확인하고 없으면 쓴다"를 두 명령으로 나누면 그 사이에 다른 서버가 끼어든다.
SET NX는 확인과 선점이 Redis 안에서 한 번에 원자적으로 일어난다.

뒤따르는 세부 사항(락 소유자 검증, 재계산이 락 TTL보다 오래 걸릴 때의 워치독 연장)은 §12 꼬리질문에서 다룬다. Redisson의 RLock은 이 세부 사항들을 감싸 놓은 구현체다.

7. 해법① 락 / single flight — 재계산을 "한 놈만" 하게

이름이 곧 설명 — 비유로 고정
같은 목적지(DB)로 가려는 승객이 수백 명이어도
비행기는 한 편만 띄우고 모두 그 편에 태운다 — single flight.

즉 같은 키에 대한 재계산을 한 요청만 실제로 수행하고, 나머지 요청은 그 하나의 결과를 나눠 갖는 기법이다. Go 표준 확장 라이브러리의 singleflight 패키지로 널리 알려진 이름이라, 용어를 그대로 쓰면 의사소통이 빨라진다.

구현은 §5의 분산 락으로 한다. 미스를 본 요청 중 하나만 락을 잡아 재계산하고, 나머지는 결과를 기다리거나(대기) 이전 값을 받는다(stale 반환).

✕ before — 순진한 look-aside: 동시 미스 = 동시 재계산
public Ranking getRanking() {
    Ranking cached = redis.get("ranking");
    if (cached != null) return cached;

    // 미스를 본 요청들이 서로를 모르므로
    // 전부 calculate()를 실행한다
    Ranking fresh = rankingRepository.calculate();
    redis.set("ranking", fresh, TTL);
    return fresh;
}
// 창 안에 들어온 500개가 전부 이 줄을 지난다.
✓ after — 분산 락으로 클러스터 전체에서 1회
public Ranking getRanking() {
    Ranking cached = redis.get("ranking");
    if (cached != null) return cached;

    RLock lock = redisson.getLock("lock:ranking");
    if (lock.tryLock()) {          // 내가 재계산 담당
        try {
            // double-check: 기다리는 사이 앞사람이
            // 이미 채웠을 수 있다
            Ranking again = redis.get("ranking");
            if (again != null) return again;

            Ranking fresh = rankingRepository.calculate();
            redis.set("ranking", fresh, TTL);
            return fresh;
        } finally {
            lock.unlock();  // 예외가 나도 반드시 푼다
        }
    }
    // 락 획득 실패 = 다른 요청이 재계산 중
    return waitAndRetryOrServeStale();
}
이 코드에서 가장 자주 빠뜨리는 두 줄
① double-check(again 재조회). 이 재조회가 없으면 락을 순서대로 통과한 요청들이 차례로 한 번씩 재계산해 버린다. 락은 "동시에"를 막을 뿐 "차례로"를 막지 않는다 — 락을 걸었는데도 쿼리가 여러 번 나가는 사고의 단골 원인이다.
② finally의 unlock(). 안 풀면 락 TTL이 만료될 때까지 다른 요청 전부가 재계산을 못 한다. 예외 경로에서 락이 남는 것이 특히 위험하다.

7-1. 스프링 내장 장치 — @Cacheable(sync = true)와 "먼저 따질 것"

스프링에는 같은 발상의 내장 장치가 있다. @Cacheable(sync = true)는 같은 키에 대한 로더 실행을 한 스레드로 직렬화한다. 단 같은 JVM 안에서만 그렇다(§5). 서버가 N대면 재계산이 최대 N번까지 일어난다.

성급한 점프를 막는 한 문장
"그러니 분산 락"으로 가기 전에 "N번이면 감당 가능한가"를 먼저 따진다.

원래 문제가 "수천 번의 중복 실행"이었다면 인스턴스 10대에 쿼리 10번은 대부분 무해하다. 문제였던 것은 1,000번이지 10번이 아니다. 승격 기준까지 말하면 더 좋다 — 재계산이 정말 비싸거나(수 초짜리 집계) DB에 여력이 없을 때만 분산 락으로 올린다.

7-2. 락 방식이 치르는 대가 — 셋 다 말해야 한다

1
대기 시간이 생긴다 — DB를 지키려다 애플리케이션이 먼저 죽는다 락을 못 잡은 요청은 기다려야 하고, 그 대기 동안 애플리케이션 스레드가 붙잡혀 있다. 대기자가 쌓이면 DB를 지키려다 애플리케이션의 스레드 풀이 먼저 고갈된다. 그래서 대기에는 반드시 타임아웃을 건다. 방어 장치가 새로운 병목이 되는 전형적인 패턴이다.
2
락 자체가 새로운 장애점이 된다 락 저장소(Redis)가 느려지거나 죽으면 모든 요청이 락 획득 단계에서 막힌다. 캐시는 죽어도 DB로 우회할 수 있었는데, 락은 그 우회로마저 좁힌다. 그래서 락 획득 실패 시의 정책을 미리 정해야 한다 — "그냥 재계산한다"(스탬피드 감수)인지 "실패로 응답한다"(가용성 포기)인지.
3
새 복잡도를 데려온다 락 TTL, 소유자 검증, 워치독 연장, 해제 실패 — 전부 다음에 관리해야 할 항목들이다. 라이브러리(Redisson)가 감춰 주더라도 장애가 나면 결국 이 층을 열어 봐야 한다.

8. 해법② 논리적 만료(soft TTL) — 물리적 미스 자체를 없애기

이름부터 풀기 — soft는 hard의 반대말이다
hard TTL(단단한 만료): 지나면 키가 실제로 사라진다
soft TTL(무른 만료): 지나도 값은 그대로 남고, 단지 "갱신할 때가 됐다"는 표시일 뿐이다

구현은 이렇다 — 키의 물리적 TTL은 아주 길게(또는 없이) 잡아 두고, 값 안에 "논리적 만료 시각"을 함께 저장한다. 조회 시 논리 만료가 지났으면 미스로 처리하는 게 아니라, 일단 그 낡은 값을 즉시 반환하면서 뒤에서 한 요청만 갱신을 수행한다. HTTP 캐시 명세에도 같은 발상이 stale-while-revalidate(재검증하는 동안 낡은 값을 쓴다)라는 이름으로 들어 있다.

락 방식이 "창이 열린 뒤 몰려드는 것을 막는" 사후 대응이라면, 이쪽은 창 자체를 없애는 접근이다.
// 캐시에 저장하는 값에 논리 만료 시각을 함께 넣는다.
// 물리 TTL과 논리 만료를 분리하는 것이 이 기법의 전부다.
record CachedRanking(Ranking data, Instant logicalExpiry) {}

public Ranking getRanking() {
    // 물리 TTL이 길어서 거의 항상 히트한다 — 미스 창이 열릴 일이 없다.
    CachedRanking cached = redis.get("ranking");

    if (cached.logicalExpiry().isBefore(Instant.now())) {
        // 논리적으로 만료됐다. 그래도 이 요청은 기다리지 않는다.
        // 갱신은 락을 잡은 한 요청만 백그라운드에서 수행한다.
        if (tryLock("lock:ranking:refresh")) {
            asyncExecutor.submit(this::refreshRanking);
        }
    }
    // 갱신 중이든 아니든 즉시 값을 돌려준다.
    // DB로 가는 요청이 0이므로 스탬피드가 성립할 수 없다.
    return cached.data();
}

8-1. 논리적 만료가 치르는 대가

1
낡은 값을 의도적으로 돌려준다 — 실수가 아니라 설계다 갱신이 진행되는 동안 도착한 모든 요청은 이전 값을 받고, 그 값은 논리 만료 시각을 이미 지난 값이다. 채택 여부는 "이 데이터가 몇 초 낡아도 되는가"라는 정합성 요구로 결정된다. 인기 목록·랭킹처럼 원래부터 근사값인 데이터에는 최적이고, 재고 수량처럼 낡은 값이 잘못된 행동(품절 상품 구매 시도)을 유발하는 데이터에는 쓸 수 없다.
2
메모리를 오래 점유한다 물리 TTL이 길다는 것은 안 쓰이게 된 키도 오래 남는다는 뜻이다. 키 수가 많은 데이터에 무차별 적용하면 메모리 압박으로 되돌아온다.
3
최초 적재 순간은 여전히 무방비다 돌려줄 낡은 값이 있어야 이 기법이 성립하는데, 캐시가 처음부터 비어 있는 상태(배포 직후, cold cache)에서는 그 값이 없다. 첫 적재만큼은 락이나 사전 워밍으로 따로 막아야 한다. 이 한 문장을 덧붙이는지가 "책에서 읽은 기법"과 "돌려 본 기법"을 가른다.
① 락 / single flight② 논리적 만료 (soft TTL)
공략 지점창이 열린 뒤의 수습창 자체를 없앰
응답 값최신 값갱신 중에는 낡은 값
응답 지연대기하면 재계산 시간만큼 늘어남항상 즉시
새 위험락 저장소가 장애점, 스레드 대기낡음의 허용, 최초 적재는 무방비
맞는 데이터낡으면 안 되는 값 (재고·잔액)몇 초 낡아도 되는 값 (랭킹·인기 목록)

9. 해법③ TTL 지터 · ④ refresh-ahead — 만료를 흩뜨리거나, 앞질러 가거나

9-1. TTL 지터(jitter) — 규칙성을 의도적으로 깨기

지터(jitter)는 원래 신호가 규칙적인 주기에서 미세하게 흔들리는 현상을 가리키는 말인데, 여기서는 의도적으로 흔들림을 넣어 규칙성을 깬다는 뜻으로 쓴다.

막으려는 상황은 이것이다. 같은 시각에 대량 적재된 키들이 같은 시각에 일제히 만료되는 것. 배치가 밤 12시에 10만 건을 TTL 24시간으로 적재하면, 다음 날 밤 12시에 10만 개가 한꺼번에 사라진다. 적재 시각이 같으면 만료 시각도 같기 때문이다.

막대의 높이가 그 순간 DB가 맞는 미스의 양이다. 지터는 높이를 낮추는 도구이지 막대를 없애는 도구가 아니다.
✕ before — 전 키에 TTL 고정
// 적재가 몰리면 만료도 정확히 같은 순간에 몰린다.
redis.set(key, value, Duration.ofHours(1));
✓ after — 1시간에 0~300초 무작위를 더한다
// 만료 시각이 3600~3900초 구간에 흩어진다.
Duration ttl = Duration.ofHours(1)
        .plusSeconds(ThreadLocalRandom.current().nextLong(300));
redis.set(key, value, ttl);
반드시 짚어야 할 한계 — 이 구분이 채점 포인트다
지터는 "여러 키의 동시 만료"를 분산하는 도구이지,
"단일 인기 키 하나가 만료되는 순간의 요청 폭주"는 못 막는다.

키가 하나뿐이면 그 하나의 만료 시각을 아무리 흔들어도, 흔들린 그 시각에 여전히 요청 1,000개가 동시에 미스를 본다. 그건 §7과 §8의 몫이다. 그래서 결론은 이렇게 고정한다 — 지터는 값싸고 부작용이 없어 항상 깔아두는 기본기이지, 인기 키 스탬피드의 해법이 아니다.

9-2. 사전 갱신(refresh-ahead) — 만료가 오기 전에 미리 채우기

이름 그대로 만료가 오기 전에(ahead) 미리 갱신(refresh)한다는 뜻이다. 만료를 기다렸다가 반응하는 것이 아니라 앞질러 처리하므로, 사용자 요청은 항상 히트만 본다. 두 가지 형태가 있다.

로컬 캐시의 내장 기능 라이브러리가 대신 해 준다

Caffeine의 refreshAfterWrite가 대표적이다. 쓴 지 N분이 지난 키에 접근이 오면 낡은 값을 즉시 반환하면서 백그라운드로 갱신한다.

  • 발상은 §8 논리적 만료와 같다 — 다른 점은 그 처리를 직접 짜느냐 라이브러리가 해 주느냐다.
Redis라면 배치로 구현 요청 경로 바깥

"인기 키 상위 N개를 주기적으로 재적재하는 스케줄러"를 둔다. 사용자 요청 경로와 무관하게 돌아가므로 요청은 항상 히트한다.

  • 스케줄러가 실패하면 조용히 낡아 간다 — 갱신 실패에 대한 알림이 함께 있어야 한다.
대상 선정이 곧 설계다
모든 키에 적용하면 아무도 안 읽는 키까지 계속 갱신하는 낭비가 되고,
그 갱신 부하가 원래 막으려던 DB 부하를 대체할 뿐이다.

대상 키가 명확하고 수가 적은 핵심 데이터(메인 페이지 구성 요소, 전사 랭킹)에 한정해 쓴다. "적용 범위를 좁히는 것이 이 기법의 본체"라고 말할 수 있으면 충분하다.

10. 가산점 — 확률적 조기 재계산(PER) 가산점

PER(Probabilistic Early Recomputation, 확률적 조기 재계산)은 만료 시각이 가까워질수록 각 요청이 스스로 "내가 미리 재계산하겠다"고 나설 확률을 높이는 기법이다. XFetch라는 이름으로도 알려져 있다.

아이디어의 핵심은 이렇다. 만료까지 여유가 많으면 아무도 나서지 않고, 만료가 임박할수록 나설 확률이 커진다. 그래서 만료 시각이 되기 전에 누군가가 자연스럽게 값을 갱신해 두게 되고, 정작 만료 시각에는 이미 새 값이 들어 있어 창이 열리지 않는다. 락 인프라 없이 조회 코드 몇 줄로 된다는 것이 최대 장점이다.

now - delta * beta * ln(rand())  >=  expiry   이면 재계산에 나선다

  delta : 이 값을 재계산하는 데 걸리는 시간 (직전 재계산 소요 시간을 함께 저장해 둔다)
  beta  : 공격성 계수. 1이 기본. 키우면 더 일찍 나선다
  rand(): 0과 1 사이의 균등 난수
  expiry: 이 키의 만료 시각

식을 뜯어보면 왜 그렇게 동작하는지 검산할 수 있다. rand()는 0과 1 사이이므로 ln(rand())는 항상 음수이고, 앞에 붙은 마이너스 때문에 - delta * beta * ln(rand())는 항상 양수다. 즉 이 식은 "현재 시각을 무작위 크기만큼 미래로 밀어 본 뒤, 그래도 만료 시각을 넘으면 재계산한다"는 뜻이다.

남은 TTL을 r = expiry - now라고 두면 재계산에 나설 확률은 다음과 같이 정리된다.

P(재계산) = P( -delta*beta*ln(rand()) >= r )
          = P( rand() <= e^(-r / (delta*beta)) )
          = e^(-r / (delta*beta))
남은 TTL이 줄어들수록 확률이 매끄럽게 올라가고, 그 상승 속도의 기준이 되는 것이 재계산 소요 시간 δ(delta)라는 점이 이 식의 우아한 부분이다.
남은 TTL r재계산에 나설 확률 (beta = 1)읽는 법
3 × delta약 5%아직 여유가 많다 — 거의 아무도 나서지 않는다
1 × delta약 37%"재계산에 걸리는 시간"만큼 남았다 — 슬슬 누군가 나선다
0 (만료 시각)100%여기까지 왔다면 무조건 나선다
이 식이 우아한 이유 — 한 문장
기준이 되는 것이 재계산 소요 시간 delta라서,
재계산이 비싼 값일수록 더 일찍 나선다 — 갱신에 걸리는 시간만큼 앞당겨 준비하는 셈이다.

대가는 보장이 없다는 것이다. 확률적으로 동작하므로 운 나쁘면 아무도 안 나선 채 만료 시각을 맞을 수 있고, 반대로 여러 요청이 동시에 나서 중복 재계산이 일어날 수도 있다(그 수는 락 없는 상태보다 훨씬 적다). 락처럼 "정확히 1회"를 보장하지는 않되, 인프라 없이 확률을 크게 낮추는 절충이라고 정리하면 된다. 존재를 알고 트레이드오프를 말하는 것만으로 가산점이다.

"이 키는 만료 순간 동시 미스가 몇 개나 되나요? 재계산 쿼리가 느리다면 그 수만큼 DB에 중복 실행됩니다(스탬피드)." §2의 세 조건을 그 코드에 대입해 묻는 질문이다. 답이 "초당 5건"이면 문제가 없고 "초당 2,000건"이면 조치가 필요하다. 단정이 아니라 조건을 묻는 형태로 쓰는 이유는, 이 문제가 코드가 아니라 트래픽에 달려 있기 때문이다. 리뷰어가 트래픽을 모르는 채로 "락을 거세요"라고 쓰면 그게 오히려 과잉 설계가 된다.
2
"적재 시각이 몰리면 만료도 몰립니다 — TTL에 지터를 섞으면 좋겠습니다." 값싸고 부작용이 없으므로 조건을 따지지 않고 바로 제안할 수 있는 항목이다(§9-1). 리뷰 코멘트에도 "조건부 제안"과 "무조건 제안"을 구분해 쓰는 것이 신뢰를 만든다.
3
"이 데이터는 몇 분 낡아도 되는 성격이니, 물리 만료 대신 논리 만료 + 백그라운드 갱신이 더 안전해 보입니다." 데이터의 성격을 먼저 판정하고 그에 맞는 기법을 고르는 순서다(§8). "낡아도 되는가"라는 질문을 먼저 던졌다는 점이 이 코멘트의 핵심이다 — 기법을 먼저 고르고 데이터를 끼워 맞추면 재고·잔액 같은 데이터에 stale을 서빙하는 사고가 난다.

12. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 시니어 변별 표시된 문항은 정답 하나를 고르지 말고 판단 기준을 말하는 연습을 한다.

락 방식에서, 락을 잡은 요청이 죽어버리면 어떻게 되나요?

락에 TTL이 없으면 아무도 재계산을 못 하는 영구 교착이 된다. 락을 쥔 프로세스가 죽으면서 해제 코드를 실행하지 못했고, 그 키는 Redis에 영원히 남기 때문이다. 그래서 분산 락에는 반드시 락 TTL을 건다(§5의 PX 옵션) — 잡은 쪽이 죽어도 TTL이 지나면 자동 해제된다.

그런데 여기서 새로운 함정이 생긴다. 재계산이 락 TTL보다 오래 걸리면 락이 먼저 풀린다. 그러면 두 번째 요청이 락을 잡고 또 재계산에 들어가고, 이제 두 요청이 동시에 같은 키를 계산하고 있다. 더 나쁜 것은 첫 번째 요청이 뒤늦게 끝나 unlock()을 호출하면 두 번째 요청이 잡고 있는 남의 락을 풀어 버린다는 점이다.

대응이 둘이다.

  • 락 소유자 검증 — 락 값에 자기 식별자를 넣어 두고, 해제할 때 그 값이 내 것인지 확인한 뒤에만 지운다(확인과 삭제를 원자적으로 하려고 Lua 스크립트를 쓴다).
  • 워치독(watchdog) 연장 — 별도 스레드가 주기적으로 락 TTL을 갱신해, 작업이 진행되는 동안은 락이 풀리지 않게 한다. Redisson의 RLock은 워치독을 기본 제공한다.

마지막으로 반대편도 반드시 말한다. 락을 못 잡은 요청들의 대기에도 반드시 타임아웃을 걸어야 한다. 무한 대기는 스레드 풀 고갈로 이어지고, 그러면 DB를 지키려다 애플리케이션이 먼저 죽는다.

락을 못 잡은 요청은 대기시키나요, 이전 값을 주나요? 시니어 변별

정합성과 지연의 트레이드오프 문제다. 둘 다 정답이 아니고, 데이터의 성격이 답을 정한다.

  • 대기 — 모두가 최신 값을 받는다는 장점이 있지만, 응답이 재계산 시간만큼 늦어지고 대기자가 쌓이면 스레드 풀을 위협한다.
  • stale 반환 — 응답이 즉시 나가지만, 재계산이 끝날 때까지 낡은 값이 서빙된다.

판단 기준은 낡은 값이 어떤 결과를 낳는가다. 인기 목록·랭킹은 몇 초 낡아도 아무도 모르고 아무 일도 안 생기므로 stale 반환이 정답에 가깝다. 반면 재고 수량처럼 낡은 값이 잘못된 행동(품절 상품 구매 시도, 그리고 이어지는 결제 실패)을 유발하는 데이터는 대기가 맞거나, 애초에 캐시하지 않는 것이 맞다.

"무엇을 캐시했는가에 따라 다르다"를 근거와 함께 말하는 것이 시니어 답변이다. 기법을 아는 것과 어디에 쓸지 판단하는 것은 다른 능력이다.

TTL 지터만 넣으면 스탬피드가 해결되나요?

아니다. 지터는 여러 키가 같은 시각에 만료되는 것을 흩뜨릴 뿐, 단일 인기 키가 만료되는 그 순간의 동시 미스는 그대로 남는다.

구체적으로 반박하면 좋다 — 메인 페이지 인기 목록 키가 하나뿐이고 초당 수천 요청을 받는다면, 그 키의 만료 시각을 아무리 흔들어도 흔들린 그 시각에 여전히 수천 개가 동시에 미스를 본다. 흩뜨릴 대상이 하나뿐이면 흩뜨릴 것이 없다.

정리는 이렇다. 지터는 값싸고 부작용이 없어 항상 깔아두는 기본기이고, 인기 키에는 그 위에 락이나 논리적 만료를 얹는다. "어느 지점을 공략하는 도구인지"의 구분이 이 꼬리질문의 핵심이다.

@Cacheable(sync = true)를 썼는데 서버가 10대라면?

sync = true는 스프링이 같은 JVM 안에서 같은 키의 로더를 한 스레드만 실행하도록 직렬화하는 장치다. JVM이 10개면 락도 10개이므로 최악의 경우 재계산이 10번 동시에 실행된다.

여기서 바로 "그러니 분산 락"으로 점프하지 않는 것이 변별 포인트다. 먼저 10번이 감당 가능한지부터 따진다. 원래 문제가 "수천 번의 중복 실행"이었다면 10번은 대부분 무해하다. 그리고 분산 락은 락 TTL, 소유자 검증, 워치독, 해제 실패, 락 저장소라는 새 장애점을 전부 데려온다.

승격 기준을 말할 수 있으면 좋다 — 재계산이 정말 비싸거나(수 초짜리 집계) DB에 여력이 없을 때만 분산 락으로 올린다. 복잡도를 추가하는 결정에 근거를 대는 모습 자체가 답변의 수준을 보여준다.

캐시 관통(penetration)과는 뭐가 다른가요?

축이 다르다.

  • 스탬피드는 존재하는 인기 키의 만료 순간에 폭주가 일어나는 시간 축의 문제다. 평소에는 아무 일도 없다가 특정 순간에만 터진다.
  • 관통은 애초에 존재하지 않는 키를 반복 조회하는 키 공간의 문제다. 만료와 무관하게 매 요청이 미스이므로 특정 순간이랄 것이 없다.

원인이 다르니 처방도 다르다. 관통에는 락도 지터도 소용없다 — 락을 걸어도 그 뒤에 다시 없는 값이고, 지터는 만료가 있어야 의미가 있다. 해법은 null 캐싱("없음"이라는 사실을 짧은 TTL로 기억해 두기)이나 블룸 필터(존재할 리 없는 키를 DB에 가기 전에 걸러내는 확률적 자료구조)다.

둘 다 "미스가 DB를 때린다"는 증상이 같아 혼동하기 쉬운데, 원인이 다르면 처방이 다르다는 점이 이 질문의 요지다(§4).

락을 제대로 걸었는데도 DB 쿼리가 여러 번 나갑니다. 무엇을 의심하나요? 추가

의심할 곳이 넷이고, 위에서부터 확인하면 대개 걸린다.

  1. double-check 누락 — 락을 잡은 뒤 캐시를 다시 조회하지 않으면 락을 차례로 통과한 요청들이 한 번씩 순차로 재계산한다. 락은 "동시에"를 막을 뿐 "차례로"를 막지 않는다(§7).
  2. JVM 로컬 락 — synchronized나 @Cacheable(sync = true)였다면 서버 대수만큼 나간다(§5). 쿼리 수가 인스턴스 수와 비슷하다면 이쪽이 유력하다.
  3. 락 TTL < 재계산 시간 — 재계산 중에 락이 먼저 풀려 다음 요청이 또 들어간다. 워치독 연장이 필요한 상황이다.
  4. 락 키 설계 — 락 키가 캐시 키와 1:1로 대응하지 않으면(예: 파라미터를 빠뜨려 여러 캐시 키가 한 락을 공유하거나, 반대로 같은 캐시 키가 매번 다른 락 키를 만들거나) 락이 의도한 범위를 지키지 못한다.

이 목록을 "현상 → 가설 → 확인 순서"로 말할 수 있으면 디버깅 경험이 드러난다.

스탬피드가 났다는 걸 어떻게 알아차리나요? 어떤 지표를 보나요? 추가

단일 지표로는 안 보이고, 두 지표가 "같은 순간에" 움직이는지를 본다. 스탬피드의 얼굴은 "캐시는 멀쩡한데 DB만 뚫린다"이기 때문이다.

  • 캐시 히트율은 전체적으로 높은데, DB QPS와 커넥션 풀 대기 시간이 짧고 날카로운 스파이크로 튄다.
  • 그 스파이크가 TTL 주기와 같은 간격으로 반복된다 — 이것이 가장 강한 증거다. 만료가 계기이므로 주기성이 생긴다.
  • DB의 slow query 로그에 같은 쿼리가 같은 시각에 무더기로 찍힌다.
  • p99 응답 시간이 튀는 동안 그 키와 무관한 API의 지연까지 같이 튄다(커넥션 풀 고갈, §3).

사전에 심어 둘 것을 말하면 더 좋다 — 캐시 키(또는 키 접두사) 단위의 미스 카운터와 재계산 실행 횟수 카운터다. "재계산이 초당 몇 번 일어났는가"를 직접 세면 추정이 아니라 측정이 된다.

락과 논리적 만료는 양자택일인가요? 추가

아니다. 실무 조합은 오히려 둘을 겹쳐 쓰는 쪽이다. §8의 코드에도 이미 tryLock이 들어 있다.

  • 논리적 만료가 바깥 틀을 맡는다 — 사용자 요청은 절대 DB로 보내지 않고 항상 캐시 값을 즉시 준다.
  • 락은 그 안쪽에서 백그라운드 갱신을 1회로 묶는다 — 논리 만료가 지난 순간 도착한 수백 요청이 전부 갱신 작업을 띄우면 그것대로 스탬피드다.
  • 최초 적재(값이 아예 없을 때)만큼은 락이 필수다 — 논리적 만료는 돌려줄 낡은 값이 있을 때만 성립하기 때문이다(§8-1).

여기에 지터는 항상 깔고, 핵심 키에는 refresh-ahead를 얹는다. "해법 4개 중 하나를 고르는 문제가 아니라, 데이터 성격에 맞게 층을 쌓는 문제"로 정리하면 답변이 닫힌다.

PER에서 beta를 키우면 무슨 일이 생기나요? 추가

확률식이 e^(-r / (delta*beta))이므로 beta가 커지면 지수의 절댓값이 작아져 같은 남은 TTL에서도 확률이 올라간다. 즉 더 일찍, 더 자주 재계산에 나선다.

  • 이득 — 만료 시각에 값이 이미 갱신되어 있을 가능성이 커진다. "아무도 안 나선 채 만료를 맞는" 최악의 경우가 줄어든다.
  • 대가 — 아직 멀쩡한 값을 미리 버리고 다시 계산하는 횟수가 늘고, 동시에 여러 요청이 나설 확률도 함께 올라간다. 결국 DB 재계산 부하와 안전 마진을 맞바꾸는 손잡이다.

그래서 기본값 1에서 시작해, 그 키의 만료 시점에 실제로 미스가 관측되면 조금씩 올린다는 순서가 자연스럽다. "이 파라미터가 무엇과 무엇을 맞바꾸는지"를 말하는 것이 이 질문의 채점 포인트다.

TTL을 아주 길게 잡거나 아예 없애면 스탬피드는 사라지지 않나요? 추가

조건 ③(만료 순간)을 없앤다는 발상 자체는 맞다 — §8 논리적 만료가 정확히 그 길이다. 다만 "TTL만 지우는 것"과 "논리적 만료"는 전혀 다르다.

  • TTL만 지우면 갱신 수단이 사라진다. 값이 언제 낡았는지 아무도 모르고, 무효화가 한 번 유실되면 그 낡은 값이 영원히 산다. TTL은 성능 장치이기 전에 정합성의 최후 안전망이다.
  • 논리적 만료는 TTL을 지우는 게 아니라 둘로 쪼갠다 — 물리 TTL(안전망)은 길게 남겨 두고, 갱신 시점을 값 안의 논리 만료 시각으로 따로 관리한다. 그래서 "낡음을 끝내는 장치"를 잃지 않는다.
  • 게다가 스탬피드의 계기는 만료만이 아니다 — eviction(메모리 부족으로 키가 밀려남), 캐시 노드 재시작, 배포로 인한 키 버전 변경도 같은 순간에 창을 연다. TTL을 지운다고 창이 열릴 계기가 없어지지 않는다.

그래서 답은 "만료를 없애는 게 아니라, 물리 만료와 논리 만료를 분리하는 것"이다.

한 줄 요약
캐시 스탬피드는 인기 키 · 비싼 재계산 · 만료 순간이라는 세 조건이 겹칠 때 미스 창에 도착한 요청 전부가 DB로 직행해 자기 강화 붕괴를 만드는 현상이고 — 락/single flight(재계산을 1회로 제한하되 대기와 락 장애점을 감수), 논리적 만료(미스 창 자체를 제거하되 낡은 값을 의도적으로 서빙), TTL 지터(여러 키의 동시 만료만 분산), refresh-ahead(만료 전 선제 갱신)가 각각 다른 지점을 공략하므로, 데이터의 낡음 허용치와 인프라 복잡도를 저울질해 조합하는 것이 답이다.
