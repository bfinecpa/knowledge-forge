TTL 1시간 캐시 PR 리뷰 — "테스트 통과"가 보증하지 않는 것

30초 카드 — 붕괴 지점 3 + 확인 요청 1
질문: "동료의 PR: 인기 목록 조회를 TTL 1시간 캐시로 감쌌고 테스트도 통과했습니다. 트래픽이 10배가 되면 생길 수 있는 문제를 리뷰 코멘트로 남겨보세요." — 답의 최종 형태는 개념 설명이 아니라 PR에 그대로 붙일 수 있는 문장이다.

핵심 관전 포인트 — 그대로 말하기
테스트 통과는 "요청 하나가 기능적으로 맞다"는 증명일 뿐이고, 캐시가 무너지는 방식은 전부 동시성과 규모에서 나오므로 테스트에는 애초에 등장하지 않는 조건이다. 인기 목록처럼 모두가 같은 키 하나를 보는 캐시는 트래픽 10배에서 세 곳이 무너진다 — ① 키가 하나면 만료 시각도 하나뿐이라 매 정시마다 전 서버의 미스가 동시에 터지는 캐시 스탬피드(1시간마다 반복되는 정기 미니 장애), ② 배포·재시작 직후 캐시가 빈 채로 전체 트래픽을 맞는 cold cache, ③ 키 하나에 조회가 집중돼 클러스터로도 못 나누는 hot key. 여기에 TTL 1시간이라는 신선도 결정이 비즈니스와 합의된 것인지도 물어야 한다. sync = true는 JVM 안에서만 유효한 잠금이라 서버가 10대면 재계산이 10번 남으므로 완화이지 해결이 아니다. 그리고 이 지식의 결과물은 개념 설명이 아니라 동료의 PR에 실제로 남길 문장이며, 그 문장은 "지금 코드가 틀렸다"가 아니라 "트래픽 조건이 바뀌면 여기가 깨진다 + 이렇게 보완하자"의 형태여야 한다.
출제 의도 — 지식이 실행 가능한 형태로 나오는지를 본다
캐시 스탬피드 개념 문항(06-cache-stampede)과 짝을 이루는 상황 인지 검사다. "지금 잘 동작하는 코드"에서 트래픽 조건이 바뀌었을 때의 붕괴 지점(동시 만료, 미스 폭주)을 배포 전에 말할 수 있는지, 그리고 그 지식이 리뷰 코멘트라는 실행 가능한 형태로 나오는지를 본다. 그래서 이 페이지의 결승선은 개념 목록이 아니라 §6의 코멘트 문장이고, §1~§5는 전부 그 문장을 쓰기 위한 근거다.

1. 축이 다르다 — 테스트가 통과한 것은 "다른 시험"이다

1-1. 리뷰 대상 코드 — 먼저 인정하고 시작한다

PR의 코드 — 잘못된 곳이 하나도 없다
// TTL 1시간은 CacheManager 설정에
@Cacheable(cacheNames = "popularList")
public List<Product> getPopularList() {
    return productRepository.findPopular();   // 비싼 집계 쿼리
}
리뷰가 어려운 이유가 여기 있다
한 줄 어노테이션이고, 테스트도 통과한다. 이 코드는 지금 트래픽에서는 정말로 맞는 코드다. 그래서 이 리뷰는 틀린 것을 찾는 작업이 아니라, 조건이 바뀌면 틀려지는 것을 찾는 작업이다. 이 인정에서 출발하지 않으면 코멘트의 톤이 처음부터 어긋난다(§6).

1-2. 테스트가 검증하는 것과, 여기서 터지는 것

기능 테스트가 검증하는 것은 이것이다 — "첫 호출은 DB를 읽고, 두 번째 호출은 캐시를 읽는다." 이 검증이 성립하는 세계를 정확히 보자. 테스트는 요청을 하나씩 순서대로 넣고 출력을 확인한다. 입력 하나에 출력 하나를 대응시키는 구조이므로, 검증 대상은 "요청 하나의 정확성"이다.

그런데 캐시가 무너지는 방식은 전부 다른 두 축에서 나온다.

동시성 같은 순간에 몇 개가 겹치는가

만료되는 그 찰나에 동시에 미스를 보는 요청이 1개인지 500개인지. 테스트는 요청을 하나씩 넣으므로 이 축의 값이 항상 1이다.

규모 캐시가 비었을 때 DB가 맞는 배수

히트율 99%를 전제로 잡힌 용량에서 히트율이 0%가 되면 DB가 몇 배를 맞는가. 테스트는 캐시가 빈 상태를 한 번, 요청 하나로만 지난다.

이 문서 전체의 출발점
테스트가 통과하는 것은 당연하고, 통과했다는 사실이 아무것도 보증하지 않는다.

"테스트 통과 = 배포 가능"이 성립하지 않는 이유는 테스트가 부실해서가 아니라 검증 대상의 축 자체가 다르기 때문이다. 이 진단을 먼저 세워야 §1-3의 처방(부하 테스트·카나리·지표)이 "테스트를 더 잘 짜자"가 아닌 "다른 도구를 쓰자"로 나온다.

코드는 한 점이 아니라 이 평면 위에서 트래픽에 따라 이동하는 점이다. 테스트는 원점 부근만 검사하므로, 붕괴 지점 셋이 모두 검사 밖에 있다. "코드 리뷰만으로는 못 잡고, 트래픽을 대입해야 보인다"는 말의 그림이 이것이다.

1-3. 그럼 무엇으로 잡는가 — 축이 다르면 도구도 다르다

부하 테스트 유일한 사전 검증

동시성과 규모를 인위적으로 만들어 보는 것. 다만 "그냥 부하를 준다"로는 부족하다.

  • 시나리오에 "캐시 만료 직후"와 "cold cache 상태"를 명시적으로 넣는다.
  • 데워진 캐시에 부하를 주면 히트율 99%짜리 예쁜 그래프만 얻고 끝난다.
카나리 배포 피해 범위 제한

새 코드를 전체가 아니라 인스턴스 한 대에만 먼저 흘리고 지표를 본다. 문제가 있어도 피해가 전체의 몇 분의 일로 제한된다.

지표 알람 사후 감지

캐시 히트율, 원본 쿼리 실행 횟수, 그리고 TTL 주기와 일치하는 DB 부하 패턴.

  • 매시 정각에 DB 부하가 튀는 톱니 그래프는 스탬피드의 서명이다.
리뷰어의 자리 — 이 한 문장이 문항의 이유다
위 셋은 전부 배포 이후의 장치다. 배포 전에 이 문제를 잡을 수 있는 유일한 장치가 코드 리뷰다.

리뷰어의 역할이 정확히 여기다 — 트래픽이라는 숨은 입력이 10배가 됐을 때 이 코드의 어디가 깨지는지를, 아직 안 깨졌을 때 말로 만들어내는 것.

2. 붕괴 지점 ① 캐시 스탬피드 — 1시간마다 반복되는 정기 미니 장애

스탬피드가 무엇인가 — 이름이 곧 정의다
캐시 스탬피드(cache stampede, 또는 thundering herd — 우르르 몰려드는 무리)는 캐시가 없는 상태에서 같은 데이터를 요구하는 요청들이 동시에 도착해 전부가 각자 원본 계산을 실행해 버리는 현상이다. 문 하나가 열리는 순간 밖에서 기다리던 무리가 한꺼번에 밀려 들어가는 그림이다 — 한 마리만 들어가서 먹이를 가져와 나눠 주면 될 일을, 전부가 각자 들어간다. 핵심은 "필요한 계산은 1번인데 실제로는 N번 실행된다"는 낭비이고, 그 N번이 전부 비싼 집계 쿼리라면 DB가 그 순간을 못 버틴다.

2-1. 왜 하필 정확히 1시간마다 반복되는가 — 인과를 한 단계씩

이 사슬의 어느 고리도 코드가 틀려서 생긴 것이 아니다. "인기 목록"이라는 데이터의 성격에서 자동으로 따라 나온다 — 그래서 코드만 봐서는 안 보인다.
A의 초록 구간이 길수록 안전해 보이지만 그 반대다 — 1시간 동안 시스템 전체가 "이 캐시는 항상 있다"는 전제로 굳어지고, 그만큼 B의 스파이크 낙차가 커진다.

2-2. 동시 미스 수는 계산할 수 있다 — 이 식이 "10배"를 대답한다

암기 — 리뷰 코멘트에 숫자를 넣는 근거
동시 미스 수  ≈  초당 요청 수 × 원본 계산 소요 시간
1x
초당 100 요청 × 0.5초 = 50개 티가 안 난다. 그래서 "지금 문제없다"는 관측은 사실이고 정확하다.
10x
초당 1,000 요청 × 0.5초 = 500개 DB가 못 버틴다. 동시 미스 수는 트래픽에 정비례하므로, 트래픽이 10배면 동시 미스도 정확히 10배가 된다.

"지금 문제없음"이 "10배에서 문제없음"의 근거가 못 되는 이유가 이 식에 그대로 있다. 리뷰 코멘트에서 이 곱셈 한 줄을 보여 주면, 동료는 반박이 아니라 자기 서비스의 숫자를 대입하기 시작한다.

2-3. 500개가 동시에 오면 실제로 무슨 일이 벌어지나

왼쪽은 공유 자원을 통한 전파, 오른쪽은 자기 강화. 그리고 마지막 상자가 이 장애의 진짜 성질이다 — 자동 복구되므로 티켓이 열리지 않고, "가끔 느려요"라는 CS만 쌓인다.

2-4. 이 PR에만 있는 성질 두 가지 — 리뷰에서 반드시 짚을 것

(1) TTL이 길수록 한 방이 크다 직관과 반대

1시간 캐시는 미스 빈도가 낮다(하루 24번). 그런데 그동안 시스템 전체가 "이 캐시는 항상 있다"는 전제로 용량이 잡히기 때문에, 만료 순간의 낙차가 그만큼 크다.

  • 미스가 드물다는 것이 안전을 뜻하지 않는다.
(2) TTL 지터로는 못 푼다 해법 오매칭 주의

만료 시각에 랜덤 오차를 주는 기법은 키가 여러 개일 때 서로 다른 시각에 만료되게 하는 해법이다. 여기는 키가 하나라 흩뜨릴 대상이 없다.

  • 필요한 것은 단일 키 스탬피드용 해법 — "재계산을 하나로 직렬화"다.

3. 붕괴 지점 ① 의 해법 4단 — 그리고 sync = true가 해결이 아닌 이유

해법을 한 문장으로 묶으면
전부 "재계산은 한 놈만"을 어디까지 밀어붙이느냐의 차이다.

JVM 안에서 한 놈(완화 1) → 전 시스템에서 한 놈(완화 2) → 사용자 요청 경로 밖에서 한 놈(완화 3) → 아예 요청과 무관하게 미리 한 놈(완화 4). 오른쪽으로 갈수록 효과가 커지고 구조 변경도 커진다.

3-1. 완화 1 — sync = true: 가장 싸고, 가장 먼저 붙이고, 가장 오해받는다

✕ before — PR의 현재 상태
@Cacheable(cacheNames = "popularList")
public List<Product> getPopularList() {
    return productRepository.findPopular();
}
// 만료 순간 미스를 본 요청이 전부 여기로 들어온다.
// 같은 JVM 안에서도 서로의 존재를 모른다.
△ after — 완화이지 해결은 아니다
@Cacheable(cacheNames = "popularList", sync = true)
public List<Product> getPopularList() {
    return productRepository.findPopular();
}
// 같은 JVM 안에서는 한 스레드만 재계산하고
// 나머지는 그 결과를 기다렸다가 받아 간다.
가운데 패널이 이 절의 핵심이다. 500 → 10은 대단한 개선이지만, 남은 10은 "서버 대수"라는 새 변수에 비례한다 — 오토스케일링이 켜져 있으면 트래픽이 늘수록 이 숫자도 함께 늘어난다.
코멘트에 반드시 함께 적을 한계
sync = true는 JVM 안에서만 유효한 잠금이다.
서버가 10대면 재계산이 10번 남으므로 완화이지 해결이 아니다.

애플리케이션 프로세스 내부의 동기화 장치를 쓰는 것이라, 다른 서버에서 같은 순간 벌어지는 재계산에 대해서는 아무것도 모른다. 부수 효과도 하나 있다 — 기다리는 490개 요청의 응답 시간은 여전히 집계 쿼리 소요 시간만큼 늘어난다. DB 부하는 줄었지만 사용자가 겪는 지연은 남아 있다.

3-2. 완화 2·3·4 — 조율 지점을 JVM 밖으로

2
분산 락 — 전 시스템에서 1개만 재계산 서버가 몇 대든 재계산을 하나로 줄인다. 락을 못 잡은 요청은 잠깐 대기 후 캐시를 다시 조회하거나 낡은 값을 받는다. 다만 분산 락 자체의 운영 복잡도(락 TTL을 얼마로 잡을지, 해제 실패 시 어떻게 되는지)가 새로 생긴다 — 그래서 우선순위에서는 뒤로 둔다(§8 첫 문항).
3
soft TTL / 백그라운드 갱신 — 사용자가 미스를 아예 경험하지 않는다 가산점 물리 TTL은 길게 잡고(예: 2시간), 논리 만료 시각(예: 55분)을 값과 함께 저장해 둔다. 논리 만료가 지나면 일단 낡은 값을 그대로 반환하면서 백그라운드로 한 번만 재계산한다. 캐시는 물리적으로 살아 있으므로 "빈 순간"이 존재하지 않고, 갱신은 요청 경로 밖에서 일어난다. 인기 목록처럼 "몇 분 낡아도 되는" 데이터에 가장 잘 맞는다.
4
스케줄러 선갱신 — 구조를 뒤집는다 인기 목록을 "누가 조회해서 채우는" 캐시가 아니라 "주기적으로 만들어 밀어 넣는" 데이터로 바꾼다. 5분마다 배치가 갱신하고 TTL은 갱신 주기보다 넉넉히 잡으면 요청 경로에서 미스라는 개념 자체가 사라진다. 조회 빈도가 압도적으로 높은 소수 키에는 이 구조 전환이 근본 해법이고, §4의 cold cache까지 함께 없앤다.
✓ 완화 3 — 값 안에 논리 만료 시각을 함께 저장
// 물리 TTL 2시간, 논리 만료 55분

@Scheduled(fixedDelay = 5 * 60 * 1000)   // 5분마다
public void refreshPopularList() {
    List<Product> list = productRepository.findPopular();
    // TTL은 갱신 주기보다 넉넉히 (예: 30분)

4. 붕괴 지점 ② cold cache — 배포·장애 복구 직후에는 캐시가 없다

cold cache(차가운 캐시)는 캐시가 비어 있어 히트율이 0%에 가까운 상태를 말한다. 반대말인 warm(데워진) 상태는 자주 쓰이는 데이터가 이미 캐시에 올라와 있어 대부분의 요청이 히트하는 상태다.

이 상태가 왜 위험한지는 "용량 산정"과 연결해야 보인다
히트율 99%를 전제로 운영되는 시스템은, 사실상
"DB는 전체 트래픽의 1%만 감당하면 되는" 용량으로 굳어 있다.

그 전제가 사라지는 순간 DB는 자기가 한 번도 겪어 본 적 없는 부하를 맞는다. "캐시는 성능 최적화일 뿐"이 아니라 "캐시가 이미 용량 설계의 일부"라는 것이 이 절의 요지다.

막대 높이는 비교를 위한 것이고 실제 배수는 적힌 숫자 그대로다. 트래픽 1x일 때는 어찌어찌 버티던 cold start가 10x에서는 즉시 장애라는 점이 이 그림의 전부다 — 두 위험이 곱해지기 때문이다.

4-1. 이 PR에서 캐시가 비는 순간은 생각보다 자주 온다

Redis 재시작·장애 복구 계획 밖

복구된 직후가 가장 취약한 순간이다. 장애에서 막 빠져나온 시스템이 곧바로 전체 트래픽을 DB로 받는다.

배포 계획된 것인데도

캐시 키 버전을 올렸거나 flush했다면 배포 시각이 곧 cold 시각이다. 배포는 매주 있는 일이라는 점이 더 나쁘다.

신규 인스턴스 투입 오토스케일

로컬 캐시가 빈 새 인스턴스가 트래픽이 몰리는 바로 그때 투입된다. 스케일 아웃이 트리거되는 시점이 곧 부하가 높은 시점이다.

대응은 두 가지
① 배포 절차에 캐시 워밍을 넣는다 — 트래픽을 받기 전에 인기 키를 미리 적재하는 단계. ② 3-2의 완화 4(스케줄러 선갱신) 구조로 바꾸면 자연히 해소된다 — 요청과 무관하게 배치가 채워 두므로 캐시가 빈 채로 트래픽을 맞는 상황 자체가 생기지 않는다. 붕괴 지점 ①과 ②를 하나의 조치로 함께 없앨 수 있다는 점이, 리뷰에서 완화 4를 제안할 근거가 된다.

5. 붕괴 지점 ③ hot key — 그리고 ④ TTL 1시간이라는 신선도 결정

hot key(뜨거운 키)는 접근이 특정 소수의 키에 집중돼, 그 키를 가진 노드 하나만 과부하되는 현상이다. 핵심은 Redis Cluster로 확장해도 해결되지 않는다는 점이다.

모든 사용자가 같은 popularList 키 하나를 본다는 조건이 §2 스탬피드의 원인이었는데, 같은 조건이 hot key의 원인이기도 하다. 원인이 하나이므로 대응 하나로 둘을 같이 줄일 수 있다는 것이 다음 카드다.
암기 — 로컬 캐시를 겹치면 Redis 조회의 분모가 바뀐다
Redis 조회 횟수  ∝  요청 수  →  서버 대수 ÷ 로컬 TTL

앞단에 로컬 캐시(Caffeine)를 수 초~수십 초 TTL로 겹치면 조회 횟수가 트래픽에서 분리된다 — 서버 10대에 로컬 TTL 5초면 Redis 조회는 초당 2회다. 인기 목록은 몇 초의 불일치를 허용하므로 로컬 캐시와 궁합이 좋다. 덤으로 이것이 §2의 스탬피드도 함께 완화한다 — Redis 키가 만료돼도 각 서버의 로컬 캐시가 살아 있는 동안은 미스가 그쪽까지 도달하지 않기 때문이다.

5-1. 붕괴 지점 ④ — TTL 1시간은 기술 설정이 아니라 비즈니스 결정이기도 하다

세 붕괴 지점은 전부 기술 문제다. 그런데 리뷰에서 놓치기 쉬운 항목이 하나 더 있다. "인기 목록이 최장 1시간 낡아도 되는가"라는 질문이다.

방금 급상승한 상품 1시간 동안 안 보여도 되나

인기 목록의 존재 이유가 "지금 뜨는 것"을 보여주는 것이라면, 1시간 지연은 기능 자체를 무의미하게 만들 수 있다.

품절된 상품 1시간 동안 남아 있어도 되나

클릭했더니 품절인 상품이 목록 상단에 1시간 남는다면 사용자 경험과 CS 비용의 문제가 된다.

이 합의 없이 정한 TTL이라면 그 자체가 리뷰 코멘트감이다
개발자가 혼자 정할 수 있는 값이 아니다. 그래서 이 항목만은 "고쳐 주세요"가 아니라 "확인 부탁해요"로 남긴다(§6-1).
TTL 튜닝만으로는 이 딜레마를 못 푼다. 3-2의 완화 3·4가 좋은 해법인 이유가 여기 있다 — 신선도를 짧은 주기로 확보하면서 미스를 요청 경로 밖으로 빼기 때문에 두 축을 동시에 개선한다.

스탬피드도, hot key도, 지터가 무력한 것도 전부 이 조건의 결과다. 그래서 리뷰에서 가장 먼저 확인할 것은 TTL 값이 아니라 "이 캐시의 키가 몇 개로 갈리는가"다. 키가 사용자별로 갈렸다면 이 코멘트의 대부분은 쓸 필요가 없다.

8. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 시니어 변별 표시 문항은 정답 하나를 고르지 말고 판단 기준과 다음 행동을 말하는 연습을 한다.

제안한 해법 중 뭐부터 적용하겠습니까? 우선순위 기준은? 시니어 변별

비용 대비 효과 순으로 간다.

  1. sync = true는 코드 한 줄이라 즉시 적용한다. 서버가 N대면 동시 재계산이 N개로 줄어드는 것뿐이지만, 500 → 10이면 이미 대부분의 위험이 제거된다. 완전한 해결이 아니라는 이유로 미루는 것보다, 지금 당장 위험의 대부분을 없애는 쪽이 낫다.
  2. 그걸로 부족하다는 신호가 보이면 soft TTL / 백그라운드 갱신을 도입한다. 신호란 구체적으로 만료 시각과 일치하는 DB 스파이크가 모니터링에 계속 보이는 것이다. 짐작이 아니라 지표를 근거로 다음 단계를 결정한다.
  3. 스케줄러 선갱신은 구조 변경이라 가장 크지만, 이 키가 서비스의 간판 조회라면 투자 가치가 있다. 미스라는 개념 자체를 없애면서 cold cache까지 함께 해소된다.

분산 락은 순위에서 뒤로 둔다. 락 자체의 운영 복잡도(락 TTL 설정, 해제 실패 시 교착)가 새로 생기므로, 같은 효과를 내는 soft TTL이 가능하면 그쪽을 먼저 고려한다.

"전부 다 하자"가 아니라 모니터링 신호를 근거로 단계적으로 간다는 것이 시니어의 답이다.

TTL을 10분으로 줄이거나 10시간으로 늘리면 해결되나요?

어느 쪽도 스탬피드를 해결하지 못한다. 만료라는 이벤트가 존재하는 한, 그 순간의 동시 미스는 그대로 발생하기 때문이다.

  • 줄이면: 신선도는 좋아지지만 만료가 6배 잦아져 스탬피드에 노출되는 횟수가 늘어난다.
  • 늘리면: 만료 빈도는 줄지만 한 번 터질 때의 낙차(그동안 커진 트래픽을 전제로 용량이 잡혀 있다)와 데이터 신선도 문제가 커진다.

정리하면 TTL 튜닝은 "빈도 대 신선도"의 트레이드오프 조절일 뿐이고, 스탬피드는 "재계산을 하나로 직렬화"라는 별도의 축으로 풀어야 한다. 두 축을 구분하는 것이 이 질문의 포인트다(§5-1의 그림).

TTL에 지터(랜덤 오차)를 주는 건 여기서 효과가 있나요?

거의 없다. 지터는 수많은 키가 같은 시각에 일제히 만료되는 것(대량 적재 후 동시 만료)을 시간축으로 흩뜨리는 해법이다. 흩뜨릴 대상이 여러 개일 때 성립한다.

이 PR은 키가 하나라서 분산할 대상이 없다. 만료 시각을 랜덤하게 흔들어도 여전히 시각은 하나이고, 그 하나의 순간에 동시 요청이 몰리는 구조는 그대로다.

여기에 맞는 정답은 single-flight(재계산을 1개로 직렬화) 계열이다. 해법을 문제 유형에 매칭할 수 있는지(다중 키 동시 만료 대 단일 키 미스 폭주)를 보는 꼬리질문이다.

이런 문제를 테스트로 미리 잡을 수는 없나요?

단위·통합 테스트로는 어렵다(§1-2). 잡으려면 조건 자체를 재현해야 한다.

  1. 부하 테스트 시나리오에 조건을 명시적으로 넣는다. "캐시 만료 직후"와 "cold cache 상태"를 시나리오로 만들고, k6나 Gatling 등으로 만료 시점에 동시 요청을 주입한다. 데워진 캐시에 부하를 주는 테스트는 아무것도 검증하지 못한다.
  2. 재계산 동시 실행 수를 검증하는 동시성 테스트는 단위 레벨로도 가능하다. 스레드 N개가 동시에 미스를 보게 만들고 원본 메서드가 몇 번 호출됐는지를 세는 테스트다. sync = true가 실제로 작동하는지를 이걸로 확인할 수 있다.
  3. 더 현실적으로는 운영 모니터링으로 잡는다. 캐시 히트율, 원본 쿼리 실행 횟수의 시간대별 스파이크, 그리고 만료 주기와 일치하는 DB 부하 패턴. 매시 정각의 톱니 모양 그래프가 보이면 스탬피드다.

"테스트 통과"의 공백을 부하 시나리오와 모니터링으로 메운다는 답의 구조가 중요하다. 테스트를 더 잘 짜면 잡힌다는 답이 아니라, 축이 다르니 다른 도구가 필요하다는 답이어야 한다.

인기 목록 hot key가 실제로 문제인지 어떻게 감지하나요?

세 레벨로 접근한다.

  • Redis 레벨: redis-cli --hotkeys(축출 정책이 LFU일 때만 키별 접근 빈도 카운터가 존재하므로 LFU 필요), 그리고 Cluster라면 노드별 CPU·네트워크 지표의 불균형 — 전체는 여유인데 한 노드만 튀는 패턴이 hot key의 서명이다.
  • 프록시/클라이언트 레벨: 키별 조회 카운트를 앞단에서 집계한다. Redis 서버는 기본적으로 키별 호출 횟수를 기록하지 않으므로, 상시 감지는 호출하는 쪽에서 하는 것이 정확하다.
  • 애플리케이션 레벨: 키 prefix별 조회 메트릭을 직접 심는다. 키 전체가 아니라 prefix 단위로 묶어야 메트릭 태그 수가 폭발하지 않는다.

감지 후 해소는 앞단 로컬 캐시로 Redis 조회 자체를 줄이는 것이 우선이고, 읽기 replica 분산이나 키 복제(popular:1 ~ popular:N에 같은 값을 두고 랜덤 조회)는 그다음 단계다. 로컬 캐시가 먼저인 이유는 효과가 가장 크고(Redis 조회가 서버 대수에 비례하도록 바뀐다) 인프라 변경이 없기 때문이다.

코멘트를 남겼더니 동료가 "지금 트래픽에선 문제없잖아요"라고 답합니다. 어떻게 이어가나요? 추가

먼저 그 말이 맞다고 인정하는 것에서 출발한다. 실제로 지금 트래픽에서는 문제가 없고(§1-1), 부정하면 대화가 사실과 어긋난다.

그다음 논점을 "맞다/틀리다"에서 "언제부터"로 옮긴다. 쓸 수 있는 문장이 셋이다.

  • 숫자로 옮기기 — "동시 미스 ≈ 초당 요청 수 × 집계 시간이라, 지금 50건이 10배면 정확히 500건이 됩니다. 트래픽에 정비례하니 어느 배수에서 넘어가는지만 계산하면 돼요."
  • 기한을 붙이기 — "그 10배가 언제 오는 트래픽인지가 기준이겠네요. 다음 프로모션 전이라면 지금 sync = true 한 줄만 넣고 나머지는 티켓으로 남기죠."
  • 비용을 비교하기 — "지금 한 줄이 1분이고, 터진 뒤 원인을 찾는 건 매시 정각에 몇 초씩 느려진다는 CS부터 시작합니다. 자동 복구돼서 장애로 안 잡히는 종류라 더 오래 걸려요."

그래도 합의가 안 되면 "막지 말고 남긴다"로 마무리한다 — approve 하고 티켓과 알람 조건(만료 주기와 일치하는 DB 스파이크)을 남기면, 신호가 실제로 뜰 때 이미 결론이 적혀 있는 상태가 된다. 리뷰의 목적은 이기는 것이 아니라 다음 행동을 정하는 것이다.

그래서 이 PR을 approve 하나요, request changes 하나요? 추가

기준을 먼저 세운다 — "지금 배포하면 깨지는가"와 "트래픽이 바뀌면 깨지는가"는 다른 등급이다. 이 PR은 후자이고, 지금 코드는 기능적으로 옳다.

  • 블로킹으로 요구할 것: 사실상 sync = true 한 줄 정도다. 비용이 0에 가깝고 효과가 가장 크다(500 → 10).
  • 티켓으로 남길 것: soft TTL / 스케줄러 선갱신, 캐시 워밍 절차, 로컬 캐시. 구조 변경이므로 이 PR의 범위가 아니다.
  • 답변을 받아야 넘어갈 것: TTL 1시간의 기획 합의 여부. 코드 수정이 아니라 확인이므로 코멘트 답글로 해소된다.

"전부 고쳐야 머지"는 §6-3의 결론과 모순된다 — 제안을 난이도 순으로 배열해 놓고 전부를 블로킹으로 걸면, 그 배열이 아무 의미가 없어진다. 배열의 목적은 이 PR의 경계선을 긋는 것이다.

로컬 캐시(Caffeine)를 겹치면 새로 생기는 문제는 없나요? 추가

있다. 캐시 계층을 하나 더 얹는 것이므로 불일치 구간도 하나 더 생긴다.

  • 서버마다 값이 다를 수 있다 — 각 서버의 로컬 TTL이 서로 다른 시각에 만료되므로, 같은 사용자가 새로고침할 때마다 목록이 살짝 달라 보일 수 있다.
  • 무효화가 즉시 전파되지 않는다 — Redis 키를 지워도 각 서버의 로컬 캐시는 자기 TTL이 끝날 때까지 낡은 값을 준다. 즉시 반영이 필요하면 별도의 무효화 전파(pub/sub 등)가 필요하고, 그만큼 복잡도가 는다.
  • 메모리와 GC — 목록 값이 수십~수백 KB라면 인스턴스마다 그만큼을 들고 있게 된다.

그래서 TTL을 수 초~수십 초로 짧게 잡는 것이 이 기법의 핵심이다. 불일치 구간을 "사용자가 신경 쓰지 않을 길이"로 묶어 두고, 그 대가로 Redis 조회를 트래픽에서 분리한다. 인기 목록은 몇 초 낡아도 아무 일이 안 생기는 데이터라 이 교환이 성립하지만, 재고·잔액처럼 낡은 값이 잘못된 행동을 유발하는 데이터에는 같은 논리를 쓰면 안 된다.

sync = true를 붙였는데도 만료 시각의 DB 스파이크가 남아 있습니다. 무엇을 확인하나요? 추가

먼저 "남아 있는 게 정상인지"부터 가른다. 스파이크의 크기를 세어 서버 대수와 비슷하면 설계대로 동작하는 것이고(§3-1), 수백 건이면 sync가 실제로는 안 걸리고 있는 것이다. 이 구분이 첫 갈림길이다.

  1. 서버 대수 확인 — 오토스케일링으로 인스턴스가 늘었다면 남은 재계산 수도 그만큼 늘어난다. 스파이크가 서서히 커지는 패턴이면 이쪽이 유력하다.
  2. sync가 실제로 로더를 직렬화하는지 확인 — 스레드 N개로 동시에 미스를 유발하고 원본 메서드 호출 횟수를 세는 동시성 테스트로 검증한다(위 "테스트로 잡을 수 있나" 문항 ②). 짐작 대신 숫자를 얻는 것이 핵심이다.
  3. 재계산 시간이 길어졌는지 확인 — 창의 폭이 곧 재계산 시간이므로, 집계 쿼리가 느려지면 같은 트래픽에서도 스파이크가 커진다. 쿼리 자체의 튜닝이 더 싼 해결일 수도 있다.
  4. 그래도 남으면 조율 지점을 JVM 밖으로 — soft TTL / 스케줄러 선갱신으로 올린다. 지표가 근거를 만들어 준 뒤에 올라가는 것이 §8 첫 문항의 우선순위 원칙과 같은 순서다.
한 줄 요약
"테스트 통과"는 요청이 하나씩 올 때의 정확성 증명일 뿐이고 캐시는 동시성과 규모에서 무너지므로, 단일 키 · TTL 1시간 · 인기 목록이라는 조합에서 트래픽 10배가 되면 만료 시각이 하나뿐이라 매시간 전 서버의 미스가 동시에 DB를 때리는 스탬피드, 배포 직후의 cold cache, 키 하나에 몰리는 hot key가 붕괴 지점이 된다 — 리뷰 코멘트는 이를 "증상 + 조건 + 파급 + 난이도순 제안"(JVM 안에서만 유효해 완화에 그치는 sync=true → soft TTL/백그라운드 갱신 → 선갱신 구조 → 로컬 캐시)의 실행 가능한 형태로, 판정이 아니라 조건 변화를 근거로 남기는 것까지가 답이다.
