Redis 5대 자료구조
"빠른 Map"을 넘어서는 설계 도구함 — 자료구조를 고른다는 건 연산을 서버로 옮긴다는 뜻

면접 질문: "Redis의 주요 자료구조(String, Hash, List, Set, Sorted Set)와 각각의 사용 사례는?"

핵심 관전 포인트 — Redis는 key-value 저장소지만 value가 단순 문자열이 아니라 자료구조다. String은 캐시·카운터·분산 락, Hash는 객체의 필드 단위 저장과 부분 갱신, List는 큐와 최근 목록, Set은 중복 방지와 집합 연산, Sorted Set은 score 정렬이 필요한 랭킹·지연 큐에 쓴다. 자료구조가 왜 필요한지는 없을 때를 보면 안다 — 값을 애플리케이션에서 읽어(조회) 고쳐서(수정) 다시 쓰면(저장) 그 사이에 끼어든 다른 요청의 변경이 덮여 사라지는 lost update가 나고, 목록 전체가 네트워크를 두 번 오간다. Redis 자료구조는 그 연산을 서버 안으로 옮긴 것이고, 명령 실행이 싱글 스레드라 옮겨진 연산은 전부 원자적이다 — 중간 상태가 남에게 보이지 않고 전부 실행되거나 전혀 실행되지 않는다. 즉 자료구조를 맞게 고른다는 것은 동시성 처리와 네트워크 왕복을 Redis에 떠넘긴다는 뜻이고, 이것이 명령어를 외우는 것과 구분되는 실익이다.
  • 1
    정의 — Redis의 value는 자료구조다. String(통값·원자 증감) / Hash(필드 단위) / List(순서·양끝) / Set(중복 없음) / Sorted Set(score 정렬 유지).
  • 2
    존재 이유 — 앱에서 하던 "읽고-고치고-쓰기"를 서버 명령 하나로 옮긴 것. 명령 하나는 원자적이라 lost update가 성립할 틈이 사라지고, 값이 네트워크를 오가지 않는다.
  • 3
    선택 기준 — "이 데이터가 무엇인가"가 아니라 "이 데이터에 필요한 연산이 무엇인가". 자료구조가 연산을 대신 못 하면 앱에서 조회-수정-저장을 하게 되고 그 순간 원자성과 성능을 둘 다 잃는다.

0. 질문 + 출제 의도

질문: "Redis의 주요 자료구조(String, Hash, List, Set, Sorted Set)와 각각의 사용 사례는?"

출제 의도: Redis를 "빠른 Map"으로만 쓰는 사람과 Sorted Set으로 랭킹을, Set으로 중복 방지를 설계하는 사람의 활용 폭 차이. 도구의 표현력을 아는 만큼 설계 선택지가 넓어진다.

그래서 이 페이지가 겨냥하는 약점 두 가지 ① 명령어 나열로 끝내는 답 — "String은 SET/GET, List는 LPUSH/RPOP…"은 도구 목록이지 설계가 아니다. 1절의 lost update를 축으로, 각 자료구조를 "어떤 종류의 읽고-고치고-쓰기를 서버로 옮겨 주는가"로 다시 읽는다.
② "왜 그 자료구조인가"에서 막히는 문제 — 4절의 선택 결정 트리와 각 절의 규칙 카드로, 데이터의 모양이 아니라 연산에서 출발하는 판단 순서를 고정한다.

1. 왜 자료구조가 5개나 있나 — "연산을 서버로 옮기기 위해"

이 절이 문서 전체의 축이다. 다섯 자료구조를 각각 외우기 전에, 자료구조가 없었다면 무슨 일이 벌어지는지를 먼저 본다. 없을 때의 고통이 곧 각 자료구조의 존재 이유다.

1-1. 전제 지식 — lost update가 무엇인가

lost update (갱신 유실)

두 요청이 같은 값을 각자 읽어 각자 수정하고 각자 저장했을 때,
나중에 저장한 쪽이 앞선 쪽의 변경을 덮어써서 한쪽 변경이 흔적 없이 사라지는 현상

무서운 점은 아무 에러도 나지 않는다는 것이다. 두 요청 모두 정상 응답을 받고, 로그에도 예외가 남지 않으며, 데이터만 조용히 틀려 있다. 그래서 발견이 늦고, 발견해도 재현이 어렵다.

Redis가 단순한 key→문자열 저장소였다면 목록에 항목 하나를 추가하는 데도 이 문제가 그대로 생긴다. 클라이언트가 전체를 읽고 → 수정하고 → 전체를 다시 쓰는 3단계를 거쳐야 하기 때문이다.

1-2. 전제 지식 — "원자적"이란 무슨 뜻인가

이 문제의 해법을 말하려면 원자성부터 정의해야 한다.

원자적(atomic)

어떤 작업이 전부 실행되거나 전혀 실행되지 않으며,
그 중간 상태가 다른 클라이언트에게 절대 보이지 않는 성질

더 이상 쪼갤 수 없는 단위(atom)라는 어원에서 왔다. 앞의 lost update를 이 말로 다시 쓰면 이렇게 된다 — "읽고-고치고-쓰기"가 원자적이지 않아서 그 중간에 남이 끼어들 틈이 있었다.

Redis에서는 명령 하나가 원자성의 단위다. 명령을 실행하는 스레드가 하나뿐이라 명령과 명령은 언제나 순서대로 실행되고, 한 명령의 실행 도중에 다른 명령이 끼어들 물리적 틈이 없다. 그래서 LPUSH 한 번은 "리스트를 읽고, 맨 앞에 붙이고, 다시 저장하는" 세 동작을 포함하지만 그 전체가 쪼개지지 않는다.

같이 외워야 할 반쪽 — 명령 두 개는 원자적이지 않다

LPUSH 한 번=원자적 ✓ / LPUSH → LTRIM=그 사이에 끼어들 수 있다 ✗

여러 명령을 한 덩어리로 묶으려면 MULTI/EXEC나 Lua 스크립트가 필요하다. "Redis는 싱글 스레드라 다 원자적이다"라고 뭉뚱그리면 이 지점에서 반례를 맞는다. (5절 꼬리질문에서 다시 다룬다.)

1-3. 자료구조 = 연산을 서버 안으로 옮긴 것

이제 정리가 된다. Redis 자료구조의 본질은 애플리케이션이 하던 "읽고-고치고-쓰기"를 서버 안의 명령 하나로 옮긴 것이다. "리스트 왼쪽에 추가", "집합에 없으면 넣기", "score 1 올리기"가 각각 명령 하나이고, 명령 하나는 원자적이므로 끼어들 틈이 사라진다. 덤으로 목록 전체가 네트워크를 오갈 필요도 없어진다.

before String에 JSON 목록을 통째로
// 조회-수정-저장. 경합 시 유실.
String json = redis.get("recent:user:1");   // ["A","B"]
List<String> items = parse(json);
items.add(0, "C");          // ← 이 사이 다른 요청이 끼면redis.set("recent:user:1", toJson(items));// → 한쪽 갱신이 증발(lost update)
after List 자료구조
// 값이 앱으로 나오지 않고 서버 안에서 바뀐다.
// 명령 하나라서 원자적이고,
// 그래서 경합 자체가 성립하지 않는다.


redis.lpush("recent:user:1", "C");

2. 다섯 가지 자료구조와 사용 사례

먼저 "value 자리에 무엇이 들어 있는가"를 그림으로 한 번에 본다. 다섯 자료구조의 차이는 결국 이 그림의 차이이고, 그 모양이 곧 가능한 연산을 결정한다.

2-1. String — 만능 기본형: 캐시, 카운터, 분산 락

가장 단순한 "key 하나 = 값 하나"다. 값은 텍스트뿐 아니라 직렬화된 객체, 숫자, 바이너리까지 담는다.

언제 String을 고르는가

값을 언제나 통째로 읽고 통째로 쓰는 경우

이 값의 일부만 따로 읽거나 고칠 일이 없고, 원소를 하나씩 더하거나 빼는 일도 없다면 더 복잡한 자료구조를 쓸 이유가 없다. 조회 결과를 JSON으로 직렬화해 캐시하는 경우가 전형적이다. 여기에 예외가 하나 — 값이 정수라면 String은 INCR 계열로 덧셈만은 서버에서 원자적으로 해 준다. 그래서 카운터도 String의 영역이다.

캐시
조회 결과(JSON)를 SET key value EX 300으로 TTL과 함께 저장. look-aside 캐시의 기본형.
카운터
INCR/INCRBY가 원자적이라 조회수, 재고 차감, API 호출 횟수 제한(rate limit)에 바로 쓴다.
분산 락
SET key val NX PX 3000 — "없을 때만 넣기(NX)"가 원자적이라 락 획득 경쟁을 명령 하나로 판정한다.
명령 String 대표 3종
SET  product:1234 '{"name":"콜라","price":1500}' EX 300   # TTL 캐시
INCR view:product:1234                                     # 원자 카운터
SET  lock:coupon <소유자토큰> NX PX 3000                    # 분산 락 획득

분산 락이 왜 SET NX 한 방이어야 하는지가 이 자료구조의 압축된 교훈이다. 1절의 lost update와 정확히 같은 구조의 문제다 — 확인과 행동 사이가 벌어져 있다.

before 있는지 보고 없으면 넣기
if (redis.get("lock:coupon") == null) {   // 둘 다 "없다"를 본다    redis.set("lock:coupon", token);      // 둘 다 여기 도달}
// → 락이 락이 아니다. 확인과 선점 사이가 벌어져 있다.
after 없을 때만 넣기(NX)
// 확인과 선점이 한 덩어리라
// 두 요청 중 정확히 하나만 true를 받는다.
Boolean acquired = redis.setIfAbsent(    "lock:coupon", token, Duration.ofSeconds(3));// PX(만료)는 락을 쥔 프로세스가 죽어도 풀리게 하는 안전장치

2-2. Hash — 객체를 필드 단위로: 부분 조회 / 부분 갱신

key 하나 아래 field → value 쌍들을 담는다. 객체를 통째로 직렬화하지 않고 필드별로 저장하므로, 한 필드만 읽거나 고칠 수 있다.

언제 Hash를 고르는가

한 덩어리로 묶이는 값인데 접근 단위가 필드 하나일 때
그리고 — 필드별 원자적 증감이 필요하면 무조건 Hash

사용자 프로필 전체를 매번 읽어야 한다면 String-JSON이 낫지만, 등급만 확인하거나 포인트만 증감하는 호출이 잦다면 Hash가 맞다. 판단 기준을 한 문장으로 하면 "전체 역직렬화 비용을 매번 낼 가치가 있는가"다. String-JSON에서는 수량 하나를 올리는 데도 전체를 읽고 써야 하고, 그 순간 lost update가 열린다.

비유 — 문서 통째 복사 vs 서랍 칸막이 String-JSON은 문서를 통째로 복사해 와서 한 줄 고친 뒤 원본 자리에 통째로 되돌려 놓는 방식이다. 내가 고친 건 한 줄인데, 되돌려 놓는 건 문서 전체다. 그 사이 남이 다른 줄을 고쳐 놨다면 그 수정까지 내 옛날 복사본으로 덮인다. Hash는 서랍 칸을 나눠 두고 내 칸만 열어 고치는 방식이라, 남의 칸은 내 관심 밖이라 덮일 일이 없다.
자주 부분 갱신되는 객체
사용자 프로필, 장바구니(field=상품ID, value=수량 — HINCRBY로 수량만 원자 증감).
여러 카운터를 한 키에
상품별 일간 통계(field=날짜)처럼 관련 카운터를 묶어 키 수를 줄인다.
명령 Hash 대표 3종
HSET user:1 name "kim" grade "VIP" point 1200
HGET user:1 grade              # grade만 — 전체 역직렬화 불필요
HINCRBY cart:1 product:99 2    # 장바구니 수량만 원자 증가
before String에 JSON 통째로
// 포인트만 바꾸려 해도 객체 전체를 읽고 쓴다
String json = redis.get("user:1");
// {"name":"kim","grade":"VIP","point":1200}
User u = parse(json);
u.setPoint(u.getPoint() + 100);
redis.set("user:1", toJson(u));// 그사이 남이 grade를 GOLD로 바꿔 저장했다면,
// 이 SET이 예전 grade가 담긴 통째 객체로 덮어쓴다.
// → 내가 만지지도 않은 필드까지 lost update 사정권.
after 필드 하나만 원자 증가
// 건드리는 필드만 서버에서 원자적으로 증가시킨다.
// 다른 필드는 이 명령의 관심 밖이라
// 덮일 일이 없다.




redis.hincrBy("user:1", "point", 100);

String-JSON과의 선택 기준은 5절 첫 꼬리질문에서 한 번 더 다룬다 — 이 비교가 실무 판단력을 보여주는 지점이다.

2-3. List — 순서 있는 양방향 목록: 큐, 최근 본 상품

양쪽 끝에서 넣고 뺄 수 있는 연결 리스트다. 끝 연산(LPUSH/RPUSH/LPOP/RPOP)은 O(1), 중간 접근은 O(N)이다.

언제 List를 고르는가

삽입 순서가 의미를 갖고, 다루는 지점이 목록의 끝(맨 앞이나 맨 뒤)일 때

"가장 최근 것부터 N개", "먼저 들어온 것부터 하나씩 꺼내기"가 그렇다. 반대로 "가운데에서 특정 항목을 찾아 지운다"거나 "전체를 훑어 조건에 맞는 것을 고른다"가 주 용도라면 List는 잘못된 선택이다 — 그 연산이 O(N)이고, 싱글 스레드에서 그 O(N)은 곧 서버 전체를 세우는 비용이다.

같은 값이 여러 번 들어와도 자연스럽다→List / 한 번만 있어야 한다→Set
간단한 작업 큐
생산자가 LPUSH, 소비자가 BRPOP(비어 있으면 대기하는 블로킹 팝)으로 폴링 없이 큐를 구현한다.
최근 본 상품 / 최신 피드
LPUSH + LTRIM으로 "최근 N개만 유지"를 두 명령으로 끝낸다.
명령 최근 N개 유지 관용구
LPUSH recent:user:1 "product:99"
LTRIM recent:user:1 0 9          # 항상 최근 10개만 유지 — 무한 성장 방지
before "최근 10개 유지"를 앱에서
// 목록 전체가 네트워크를 두 번 오간다
List<String> recent = parse(redis.get("recent:user:1"));
recent.add(0, "product:99");
if (recent.size() > 10) recent = recent.subList(0, 10);
redis.set("recent:user:1", toJson(recent));// 경합 시 다른 탭의 조회 기록이 증발
after 두 명령, 목록은 서버에 머문다

List의 두 가지 주의점

LRANGE key 0 -1
전체 조회는 O(N). 리스트가 크면 싱글 스레드를 그만큼 점유해 블로킹 폭탄이 된다.
ack가 없다

2-4. Set — 중복 없는 집합: 중복 방지, 집합 연산

순서가 없고 중복이 없는 멤버 집합이다. SADD는 "이미 있으면 0, 새로 넣었으면 1"을 반환하므로 존재 확인과 추가가 원자적으로 한 번에 이뤄진다.

언제 Set을 고르는가

"이미 있는가?"가 핵심 질문일 때

중복 응모 차단, 출석 체크, 좋아요 여부처럼 같은 값이 두 번 들어가면 안 되는 데이터가 여기 해당한다. 판단의 결정적 근거는 SADD의 반환값이다 — 애플리케이션이 "조회해서 없으면 넣는다"를 할 필요 없이, 판정 자체를 서버가 원자적으로 내려 준다. 여러 집합을 겹쳐 봐야 한다면(공통 팔로워, 아직 안 본 항목) Set 말고 다른 선택지는 사실상 없다. 반대로 순서가 의미 있거나 같은 값이 여러 번 들어와야 한다면 Set은 답이 아니다.

암기 장치 — SADD는 "번호표 뽑기" 번호표를 뽑으면 새 번호가 나오거나(1 = 처음이다), 이미 뽑은 사람이면 거절당한다(0 = 이미 있다). 뽑는 행위 하나에 판정이 들어 있어서, "뽑아도 되는지 먼저 물어보는" 단계가 필요 없다. 이 "물어보는 단계가 사라졌다"가 곧 원자성이다.
중복 방지
이벤트 중복 응모 차단, 오늘 출석 체크, "이 공지를 이미 본 사용자" — SADD의 반환값이 곧 "처음인가?"의 답.
좋아요 / 팔로워
SISMEMBER로 "내가 눌렀나"를 O(1)로 확인하고, SCARD로 개수를 센다.
집합 연산
SINTER(교집합 — 공통 팔로워, 함께 아는 친구), SDIFF(차집합 — 아직 안 본 항목).
before DB에서 SELECT 후 INSERT
// 확인 시점과 삽입 시점이 벌어져 있어
// 그 틈에 상대가 끼어든다.
if (!db.existsEntry(userId)) { db.insertEntry(userId); }// → 동시 요청이 둘 다 통과 = 중복 응모 발생
after SADD 반환값으로 판정
// 확인과 삽입이 서버 안에서 한 덩어리다.
// 동시 요청 둘 중 정확히 하나만 1을 받는다.
Long added = redis.sadd("event:2026-08:entries", userId);if (added == 0) throw new AlreadyEnteredException();
주의 — 큰 Set의 전체 순회 SMEMBERS(전체 조회)와 SINTER는 O(N)이라 수백만 멤버 Set에서는 서버를 세운다. 큰 집합 순회는 SSCAN으로 나눠서 한다.

2-5. Sorted Set — score로 정렬된 집합: 랭킹, 지연 큐

Set에 score(실수)가 붙어, 멤버들이 항상 score 순으로 정렬된 상태로 유지된다. 추가와 score 변경, 순위 조회가 O(log N)이다. "정렬 상태의 실시간 유지"가 이 자료구조의 존재 이유다.

언제 Sorted Set을 고르는가

데이터마다 "크기"를 뜻하는 숫자가 있고, 그 숫자 순서로 조회해야 할 때

점수 순 상위 10개, 시각 순으로 지금 실행할 것들, 최근 60초 안의 요청들 — 전부 같은 모양이다. 반대로 순위나 범위 조회 없이 값만 꺼내 쓴다면 score는 낭비다.

갈림길 하나 더 — 정렬을 언제 하느냐

RDB 랭킹
조회할 때 정렬한다. 조회마다 정렬 비용을 내거나, 배치로 미리 계산해 스냅샷을 뜬다(= 실시간 포기).
Sorted Set
쓰기 순간마다 정렬 상태를 유지한다. 조회는 이미 정렬된 구간을 잘라 오는 일이 된다.

그래서 "실시간 순위"라는 요구가 있으면 Sorted Set이 정답에 가깝다. 비용을 조회 쪽에서 쓰기 쪽으로 옮긴 것이고, 랭킹은 보통 조회가 훨씬 잦다.

실시간 랭킹
조회/좋아요마다 ZINCRBY, 상위 10개는 ZREVRANGE, 내 순위는 ZREVRANK.
지연 큐 / 스케줄링
score를 실행 예정 시각(epoch)으로 넣고, 워커가 ZRANGEBYSCORE queue 0 <now>로 "지금 실행할 것"만 꺼낸다.
슬라이딩 윈도우 rate limiter
score를 요청 시각으로 넣고, 오래된 것은 ZREMRANGEBYSCORE로 제거한 뒤 ZCARD로 최근 N초 요청 수를 센다.
명령 랭킹 3종 세트
ZINCRBY  ranking:daily 1 "webtoon:55"       # 조회 1건 → score +1
ZREVRANGE ranking:daily 0 9 WITHSCORES      # 실시간 TOP 10
ZREVRANK ranking:daily "webtoon:55"         # 내 순위 (0부터)
before 관계형 DB로 랭킹
-- 증가와 정렬이 따로 논다
UPDATE webtoon SET view_count = view_count + 1 WHERE id = 55;SELECT id, view_count FROM webtoon  ORDER BY view_count DESC LIMIT 10;-- 인덱스를 걸어도 조회수가 바뀔 때마다 인덱스가 갱신되고,
-- 규모가 커지면 결국 집계 배치 + 랭킹 스냅샷 테이블로
-- 도망가게 된다 (= 실시간 포기).
after Sorted Set
// 증가와 정렬 유지가 한 명령이다.
redis.zincrby("ranking:daily", 1, "webtoon:55");// 조회는 정렬된 구간을 잘라 오는 것뿐이다.
Set<TypedTuple<String>> top10 =    redis.reverseRangeWithScores("ranking:daily", 0, 9);

동점 처리 규칙 — 시험에 잘 나온다

score가 같은 멤버끼리는 멤버 문자열의 사전순으로 정렬된다

"동점일 때 먼저 올린 사람이 앞서야 한다"는 요구가 있다면 그 순서를 score 안에 섞어 넣는 설계가 필요하다 (예: score를 점수 - 시각/큰수 형태로 만들어 미세하게 차등을 준다).

3. 내부 구조 — 스킵 리스트가 무엇인가 가산점 포인트

Sorted Set은 스킵 리스트 + 해시테이블 이중 구조다. 그런데 "스킵 리스트"라는 이름만 던지면 설명이 안 된다. 이 자료구조가 왜 필요했는지부터 쌓아야 이름이 의미를 갖는다.

3-0. 출발점 — 정렬 유지와 빠른 탐색을 동시에 못 하는 문제

랭킹은 두 가지를 다 요구한다. 값이 수시로 바뀌고(ZINCRBY), 정렬된 구간을 잘라 와야 한다(ZREVRANGE 0 9). 그런데 기본 자료구조는 둘 중 하나만 준다.

탐색중간 삽입
정렬된 배열O(log N) — 이진 탐색O(N) — 뒤쪽 원소를 전부 밀어야 한다
정렬된 연결 리스트O(N) — 앞에서 하나씩 따라간다O(1) — 포인터 두 개만 바꾼다
넘어가면 안 되는 지점 — 왜 정렬된 연결 리스트에서는 이진 탐색을 못 쓰나 이진 탐색은 "가운데로 점프"가 전제인 알고리즘이다. 배열은 원소가 메모리에 연속으로 놓여 있어 arr[n/2]라는 주소 계산 한 번으로 가운데를 짚는다. 연결 리스트는 원소들이 메모리 여기저기 흩어져 있고 앞 노드가 다음 노드의 주소만 들고 있어서, 가운데 노드가 어디 있는지는 거기까지 걸어가 봐야 안다. 점프 능력이 없으니 "절반을 버린다"는 전략 자체를 세울 수 없다. 그래서 정렬돼 있어도 O(N)이다.
스킵 리스트의 아이디어는 한 줄이다 — 연결 리스트에 점프 능력을 인위적으로 달아 주자.

3-1. 1단계 — 급행 노선을 얹는다

지하철을 떠올리면 정확하다. 완행은 모든 역에 서고 급행은 주요 역만 선다. 목적지 근처까지 급행으로 크게 이동한 뒤 완행으로 갈아타 좁힌다.

3-2. 2단계 — 탐색 규칙은 딱 두 줄이다

스킵 리스트 탐색 규칙 — 이 두 줄이 전부다

① 오른쪽 값 ≤ 찾는 값
오른쪽으로 간다
② 아니면 (지나치거나 nil)
한 층 내려간다

"내려간다"가 곧 탐색 범위를 좁히는 행위다. 3층에서 55에 멈춘 순간 "답은 55 이후에 있다"가 확정되고, 이후로는 그 뒤쪽만 본다. 이진 탐색이 절반을 버리는 것과 같은 일을 포인터 따라가기만으로 해내고 있다.

#현재 위치오른쪽판단행동
13층 head5555 < 62오른쪽으로 → 55
23층 55nil갈 수 없다한 층 내려감
32층 557878 > 62한 층 내려감
41층 557878 > 62한 층 내려감
50층 5562일치찾았다

3-3. 3단계 — 왜 동전 던지기인가

여기가 스킵 리스트의 핵심이고, 보통 가장 안 잡히는 부분이다.

앞에서 그린 "매 2번째 노드를 급행역으로" 같은 이상적인 모양은 삽입 한 번에 무너진다. 맨 앞에 원소 하나가 들어오면 짝수/홀수 번째가 전부 뒤집히니, 급행역을 다시 지정하려면 전체를 훑어야 한다 — O(N)이다. 랭킹은 초당 수천 번 갱신되는데 이런 비용은 낼 수 없다.

균형 트리(레드-블랙 트리)는 이 문제를 회전(rotation)으로 푼다. 삽입할 때마다 균형이 깨졌는지 검사하고 서브트리를 돌려 모양을 강제로 복구한다. 동작하지만 처리해야 할 경우의 수가 많아 구현이 복잡하다.

스킵 리스트는 정반대를 택한다 — "정확한 모양"을 포기하고 "평균적으로 그 모양"에 만족한다.
삽입 시 층수를 동전으로 정한다
level = 1
while (동전이 앞면):      // 확률 p
    level += 1

// → 이 노드는 level 층까지 링크를 갖는다
결과 p = 1/2일 때 분포
1층까지만  : 1/2      ← 절반은 급행역이 되지 못한다
2층까지    : 1/4
3층까지    : 1/8
...
// 아무도 조정하지 않았는데 "층마다 절반"이
// 확률적으로 저절로 만들어진다.

결정적인 이득 — 재균형이라는 개념이 아예 없다

노드의 층수는 삽입 시점에 정해지고 그 뒤로 절대 바뀌지 않는다

다른 노드가 들어오거나 빠져도 내 층수는 그대로다. 그래서 삽입은 각 층에서 "내 왼쪽이 될 노드"의 포인터를 고쳐 끼우는 일뿐이고, 그 왼쪽 노드들은 탐색 경로에서 이미 다 지나온 노드들이다. 따로 찾을 필요가 없다.

3-4. 4단계 — 무작위인데 어떻게 믿나

최악의 경우는 실제로 O(N)이다. 모든 동전이 뒷면이면 전부 1층짜리, 즉 평범한 연결 리스트가 된다. 원소 100만 개에서 그 일이 벌어질 확률은 계산할 의미가 없는 수준이다.

다만 확률이 작다는 것보다 더 중요한 성질이 있다.

이 설계의 세련된 부분

스킵 리스트의 모양은 입력 데이터에 전혀 의존하지 않는다
이진 탐색 트리
정렬된 데이터를 순서대로 넣으면 한쪽으로 늘어져 연결 리스트가 된다. 즉 입력 패턴이 성능을 결정하고, 그래서 악의적인 입력으로 성능을 무너뜨릴 수 있다(해시테이블의 충돌 공격도 같은 종류).
스킵 리스트
모양은 오직 내부 난수가 결정하므로 어떤 순서로 넣어도 기대 성능이 같다. 무작위성이 데이터 쪽이 아니라 자료구조 안에 있다.

3-5. 5단계 — Redis가 더 붙인 두 가지

(1) Redis의 스킵 리스트 상수

p = 0.25
ZSKIPLIST_P
승격 확률을 1/2이 아니라 1/4로 잡았다. 확률을 낮춰 노드당 포인터 개수를 줄인 것(평균 링크 수 2개 → 1.33개). 탐색 단계는 조금 늘지만, 수억 개 멤버를 담는 서버에서는 메모리가 더 비싼 자원이라는 판단이다.
최대 32층
ZSKIPLIST_MAXLEVEL
p=1/4에서 원소 264개 규모까지 커버한다.

(2) span — 순위 계산의 비밀. ZRANK나 ZRANGE 0 9처럼 인덱스로 자르는 조회가 어떻게 O(log N)인지를 설명하는 부분이다. Redis의 각 층 링크는 "이 링크가 0층 기준 몇 칸을 건너뛰는가"를 함께 저장한다. 이것이 span이다.

0층이 "정렬된 이중 연결 리스트"라는 사실이 값을 하는 곳 범위 조회가 "시작 지점을 O(log N)으로 찾은 뒤 옆으로 걸어가는" 일로 끝난다. 게다가 Redis는 0층에 뒤로 가는 포인터를 하나 더 달아 뒀다. 랭킹 조회는 대부분 역순(ZREVRANGE로 상위 N명)이므로, 이 디테일이 실용적으로 큰 차이를 만든다.

3-6. 해시테이블은 무엇을 하나 — 이중 인덱스

스킵 리스트만 있으면 "멤버 이름으로 score를 찾기"에는 탐색이 필요하다. 스킵 리스트는 score 순으로만 정렬돼 있을 뿐, 멤버 이름 순으로는 아무 질서가 없기 때문이다. 그래서 해시테이블을 병행해 "멤버 → score"를 O(1)로 답하게 한다. ZSCORE나 ZINCRBY가 빠른 이유가 이것이다.

Redis는 명령 실행이 싱글 스레드다. 이 목록의 명령이 오래 걸리면 그 시간 동안 다른 모든 클라이언트가 대기한다. "느린 쿼리 하나"가 아니라 "서버 전체의 정지"라는 점이 RDB와 다르다.

(가산점 포인트) 작은 컬렉션은 압축 인코딩으로 저장된다

모든 컬렉션형은 멤버가 적을 때 listpack(Redis 7.0 이전에는 ziplist)이라는 압축 인코딩으로 저장된다. 원소들을 연속된 바이트 배열에 촘촘히 이어 붙이는 방식이라 포인터 부담이 없어 메모리를 크게 아낀다. 정수만 담긴 작은 Set은 intset이라는 전용 인코딩을 쓴다.

실무적 함의 작은 Hash 여러 개가 큰 Hash 하나보다 메모리 효율이 좋을 수 있다. 반대로 임계를 살짝 넘긴 컬렉션이 수십만 개 있으면 메모리가 예상보다 훨씬 크게 잡힌다. 메모리 산정이 빗나갔을 때 이 인코딩 전환을 의심 목록에 올릴 수 있으면 좋다.

5. 꼬리질문 셀프 테스트

질문만 보고 소리 내어 답한 뒤 펼쳐서 확인한다. 답에 이 문서의 축(연산을 서버로 · 명령 하나 = 원자적 · 접근 패턴 · O(N)은 서버 정지)이 들어갔는지 스스로 채점한다.

객체 캐시는 String에 JSON으로 넣나요, Hash로 쪼개 넣나요? 핵심힌트: 기준은 하나 — 접근 패턴. 그리고 마지막에 TTL 이야기를 붙인다

기준은 접근 패턴이다.

항상 통째로 읽고 통째로 갱신하는 조회 캐시라면 String-JSON이 낫다. 단순하고, 직렬화가 한 번이면 끝이라 오히려 빠르다. Hash로 쪼개면 필드마다 오버헤드가 붙고 HGETALL로 전부 읽어 조립하는 비용이 든다.

특정 필드만 자주 읽거나 갱신한다면(장바구니 수량, 포인트) Hash가 맞다. 부분 갱신이 원자적이고, 전체 역직렬화 비용이 없으며, 2-2절에서 본 "내가 만지지도 않은 필드가 덮이는" lost update가 원천적으로 없다.

결정적 차이 하나를 덧붙이면 답이 완성된다 — TTL은 기본적으로 key 단위

Hash 하나에 담긴 필드들은 수명을 공유한다는 뜻이다. (Redis 7.4에서 HEXPIRE 계열로 필드 단위 만료가 추가됐지만, 운영 클러스터의 버전을 확인해야 쓸 수 있는 이야기이고 설계의 기본값은 여전히 key 단위 TTL이다.) 그래서 "필드마다 수명이 달라야 한다"면 Hash 하나가 아니라 key를 쪼개는 설계를 먼저 검토한다.

Sorted Set은 어떻게 O(log N)으로 정렬을 유지하나요? 가산점힌트: 이름만 대면 반쪽. "왜 층을 얹어야 했나" → "왜 확률인가" → "해시테이블은 왜"

스킵 리스트(skip list) 덕분이다. 정렬된 연결 리스트에 "급행 노선" 층을 확률적으로 여러 겹 얹은 구조로, 탐색할 때 위층에서 크게 건너뛰다가 목표를 지나치면 아래층으로 내려와 좁혀 간다. 층이 올라갈수록 원소가 절반씩 줄도록 만들어지므로 층수가 log N에 비례하고, 그래서 탐색·삽입·삭제가 O(log N)이다.

① 왜 연결 리스트에 층을 얹어야 했는지를 한 마디 붙이면 답의 급이 달라진다. 이진 탐색은 "가운데로 점프"가 전제인데, 연결 리스트는 주소가 흩어져 있어 가운데가 어디인지 걸어가 봐야 안다. 그래서 정렬돼 있어도 O(N)이고, 스킵 리스트는 그 점프 능력을 상위 층 링크로 인위적으로 만들어 준 것이다.

② 층수를 확률로 정하는 이유까지 답하면 완성된다. "매 2번째를 급행역으로" 같은 정확한 모양은 삽입 한 번에 무너져 재구성에 O(N)이 든다. 그래서 정확한 모양을 포기하고 동전 던지기로 평균적인 모양만 얻는다. 대신 노드의 층수가 삽입 시점에 고정되어 재균형(회전)이 아예 없다 — 균형 트리와 같은 성능을 훨씬 단순한 구현으로 얻는 것이 채택 이유다. 덧붙여 스킵 리스트의 모양은 난수만으로 결정되므로 입력 순서에 성능이 흔들리지 않는다(정렬된 데이터에 한쪽으로 늘어지는 이진 탐색 트리와 대비된다).

③ 해시테이블을 병행해 "멤버로 score 찾기"는 O(1)로 처리한다. 두 자료구조가 같은 멤버를 가리키는 이중 인덱스 구조라고 답하면 정확하다. 범위 조회가 빠른 이유까지 덧붙이면 좋다 — 스킵 리스트의 맨 아래층이 정렬된 연결 리스트라서 시작점만 찾으면 옆으로 걸어가면 된다. Redis는 여기에 역순 조회(ZREVRANGE)를 위해 맨 아래층에 뒤로 가는 포인터까지 달아 뒀다.

④ ZRANK가 어떻게 O(log N)인지 물어 오면 span을 말하면 된다. 각 층 링크가 "0층 기준 몇 칸을 건너뛰는가"를 함께 저장하므로, 내려오며 지나온 span을 더하면 그것이 곧 순위다. 세어 보지 않고 탐색 한 번으로 순위가 나온다.

List를 메시지 큐로 쓰면 어떤 한계가 있나요? 핵심힌트: 세 가지. 그리고 요구사항을 가르는 축 하나
① ack가 없다
BRPOP으로 꺼내는 순간 메시지는 큐에서 사라진다. 소비자가 처리 도중에 죽으면 그 메시지는 어디에도 남지 않는다. "처리 완료를 확인한 뒤 지운다"는 개념 자체가 없다.
② 소비자 그룹이 없다
여러 소비자에게 나눠 주기, 실패한 것 재전송, 각 소비자가 어디까지 읽었는지 관리 같은 것이 제공되지 않는다.
③ 재소비(replay) 불가
꺼낸 메시지는 사라지므로 "어제 것을 다시 처리"가 안 된다.
요구사항을 가르는 축은 "유실 허용 여부"

그래서 "유실돼도 되는 가벼운 작업"까지가 List 큐의 영역이고, 유실 불가·다중 소비자·재처리가 요구되면 Redis Streams나 Kafka로 넘어가야 한다. 이 축을 먼저 짚고 나서 대안을 말하는 순서가 좋다 — 도구 이름부터 말하면 "왜"가 빠진다.

랭킹 Sorted Set의 멤버가 수억 개가 되면 어떤 문제가 있나요? 시니어 변별힌트: big key. 세 방향으로 터지고, 대응은 "만들어진 뒤"가 아니다

big key 문제다. 세 방향으로 터진다.

① 메모리와 분산
그 키 하나가 수 GB를 점유하고, Redis Cluster는 키 단위로 노드에 분산하므로 이 거대한 키가 한 노드에 통째로 얹힌다. 아무리 노드를 늘려도 이 키는 쪼개지지 않는다.
② O(N) 위험
ZRANGE 범위가 크거나 집계형 연산이 들어가면 O(N)에 가까워지고, 싱글 스레드를 그 시간만큼 점유해 서버 전체를 세운다.
③ 삭제·마이그레이션·복제
DEL 하나가 수억 개 원소의 메모리를 해제하느라 초 단위로 멈추므로 UNLINK가 필요해지는 지점이고, 클러스터 슬롯 마이그레이션이나 복제 동기화에서도 이 키가 통째로 움직이며 지연을 만든다.
대응은 만들어진 뒤가 아니라 키 설계 단계에서 한다
  1. 기간별로 분할 — ranking:2026-08-31처럼 일/주 단위 키 + 만료.
  2. 상위 N만 유지 — 주기적 ZREMRANGEBYRANK.
  3. 요구사항을 되묻는다 — "전체 정밀 순위가 정말 필요한가?" 실제로는 상위 100위와 "내 순위 근처"만 필요한 경우가 대부분이다.

3번까지 말하는 것이 시니어 변별 지점이다. 앞의 둘은 기술적 완화이고, 3번은 문제 자체를 없애는 접근이다.

String의 INCR로 만든 조회수 카운터, 어떤 점을 주의해야 하나요?힌트: 셋 — 유실 / 키 수명 / 타입 규율
① Redis는 유실될 수 있다
카운터가 정산이나 광고비 산정처럼 돈에 연결된다면 Redis를 원본으로 삼으면 안 된다. 주기적으로 DB에 반영하는(write-behind) 구조를 함께 설계하고, "유실 시 어디까지 되돌아가는가"를 정해 둬야 한다.
② TTL 없는 키가 무한히 쌓인다
대상(상품, 게시글)이 많으면 키 수가 그만큼 늘어나고 아무도 지우지 않는다. 키 수명 정책을 함께 설계해야 한다 — 일자별 키로 만들어 만료를 거는 방식이 흔하다.
③ INCR은 정수일 때만 동작
값은 문자열로 저장되지만 INCR은 정수로 해석 가능할 때만 동작한다. 같은 키를 SET으로 JSON을 덮어쓰는 코드가 어딘가에 섞이면 그다음 INCR이 런타임 에러를 낸다.
③은 자료구조 문제가 아니라 키 네이밍과 소유권 규율의 문제다

한 키는 한 용도, 한 팀이 소유한다는 규칙이 없으면 언젠가 부딪힌다. 이렇게 답하면 "명령어를 아는 사람"이 아니라 "운영을 아는 사람"으로 읽힌다.

추가 꼬리질문 — 원자성의 경계를 콕 찍어 묻는 것들

"Redis는 싱글 스레드라 원자적이다"는 어디까지 맞는 말인가요? 약점 겨냥힌트: 단위가 무엇인지 말하지 않으면 틀린 말이 된다

원자성의 단위는 "명령 하나"다. 거기까지가 맞는 말이다. LPUSH 한 번은 내부적으로 "읽고-붙이고-저장"이지만 다른 명령이 그 사이에 끼어들 물리적 틈이 없어 원자적이다.

그러나 명령 두 개는 원자적이지 않다. LPUSH 다음에 LTRIM을 보내면 두 명령 사이에 다른 클라이언트의 명령이 들어올 수 있다. 앱이 GET → 계산 → SET을 하는 것도 마찬가지고, 이건 1절의 lost update와 정확히 같은 구조다.

묶으려면 — MULTI/EXEC 또는 Lua 스크립트

차이도 한 마디 붙일 수 있으면 좋다. MULTI/EXEC는 여러 명령을 한 번에 실행해 주지만 중간 결과를 보고 분기할 수 없다(명령들이 미리 다 정해져 있어야 한다). Lua는 서버에서 스크립트를 실행하므로 "읽은 값에 따라 다르게 행동하는" 로직까지 한 덩어리로 만들 수 있다. 그래서 "값을 확인하고 조건이 맞으면 지운다" 같은 것은 Lua의 영역이다(다음 문항).

SET NX로 분산 락을 잡았습니다. 해제는 어떻게 하나요? 시니어 변별힌트: 그냥 DEL 하면 무슨 사고가 나는지부터

그냥 DEL하면 남의 락을 푼다. 시나리오는 이렇다 — 프로세스 A가 락을 잡고 작업이 길어져 PX 만료 시간이 지나 락이 자동 해제된다. 그 틈에 프로세스 B가 같은 키로 락을 새로 잡는다. 그때 A가 작업을 마치고 DEL lock:coupon을 호출하면 A가 B의 락을 지워 버린다. 그다음부터는 락이 락이 아니다.

그래서 락 값에 소유자 토큰(UUID 같은 것)을 넣어 두고, 해제할 때 "이 락의 값이 내 토큰일 때만 지운다"를 해야 한다. 그런데 이걸 GET → 비교 → DEL로 하면 명령이 세 개라 원자적이지 않다 — 비교와 삭제 사이에 만료가 일어나면 똑같은 사고가 난다.

"값을 확인하고 조건이 맞으면 지운다"는 한 덩어리여야 한다 → Lua 스크립트

정리하면 획득은 SET NX PX 한 명령, 해제는 토큰 비교 + DEL을 묶은 Lua 한 덩어리다. 이 문제도 결국 이 문서의 축 그대로다 — 확인과 행동 사이가 벌어지면 사고가 난다.

장바구니를 만들려고 합니다. 목록처럼 생겼는데 왜 List가 아닌가요? 약점 겨냥힌트: 명사가 아니라 동사에서 출발한다

4절의 원칙을 그대로 적용하는 문제다. "장바구니 = 목록"은 데이터의 모양이고, 자료구조를 정하는 건 연산이다. 장바구니에 실제로 하는 일을 적어 보면 — "상품 A의 수량을 2 늘린다", "상품 B를 뺀다", "상품 C가 담겨 있나 본다". 전부 특정 항목을 지목하는 연산이고, 순서는 의미가 없다.

List로 하면 "상품 A 찾기"가 O(N)이고 수량 변경은 결국 전체를 읽어 고쳐 쓰는 앱 로직이 된다 — 1절의 lost update 그대로다. Hash로 field = 상품ID, value = 수량을 쓰면 HINCRBY cart:1 product:99 2 한 명령으로 해당 수량만 원자적으로 바뀐다.

"~처럼 생겼다"로 고르면 틀리고, "~를 해야 한다"로 고르면 맞는다

같은 함정의 다른 예 — "랭킹은 목록이니 List"(→ Sorted Set), "태그는 목록이니 List"(→ 중복이 없어야 하고 "이 태그 있나"를 물으므로 Set).

Set으로 중복 응모를 막았는데 몇 달 뒤 그 키가 수백만 멤버가 됐습니다. 무엇을 잘못했나요?힌트: 자료구조 선택은 맞았다. 빠진 건 하나

자료구조 선택은 옳았다 — "이미 있는가?"가 핵심 질문이니 Set이 맞다. 빠진 것은 키의 수명 설계다. 이벤트 응모 기록은 영원히 필요한 데이터가 아닌데 키가 하나뿐이면 계속 쌓이기만 한다. 그리고 커진 키는 앞 문항의 big key 문제를 그대로 물려받는다 — Cluster에서 한 노드에 얹히고, SMEMBERS·SINTER가 O(N)이라 서버를 세우고, DEL조차 위험해진다.

고치는 방향은 랭킹 big key와 완전히 같다.

  • 기간·대상 단위로 키를 쪼갠다 — event:2026-08:entries처럼 이벤트/기간을 키에 넣는다.
  • TTL을 건다 — 이벤트 종료 + 정산 기간이 지나면 자동 소멸.
  • 영구 보존이 필요한 기록이라면 원본은 DB에 두고, Redis Set은 "동시 요청 판정용 단기 캐시"로만 쓴다.
Redis 설계에서 "이 키는 언제 사라지는가"는 자료구조 선택과 동급의 질문이다
Sorted Set 랭킹에서 동점자 순서를 "먼저 달성한 사람이 위"로 하려면? 가산점힌트: Redis는 동점을 어떻게 정렬하는지부터

먼저 기본 규칙을 안다는 걸 보여야 한다 — score가 같으면 멤버 문자열의 사전순으로 정렬된다. 즉 아무것도 안 하면 순서는 업무적으로 무의미한 기준(ID 문자열)으로 정해진다.

Redis에는 "2차 정렬 키"가 없으므로, 필요한 순서를 score 하나에 접어 넣어야 한다. 점수가 주 기준이고 시각이 보조 기준이라면 같은 점수 안에서 먼저 달성한 쪽이 아주 미세하게 높은 score를 갖도록 만든다 — 예를 들어 점수 - 시각/큰수 형태로, 시각이 이를수록 빼는 값이 작아지게 한다.

주의 — 정밀도 score는 실수라 표현 가능한 자릿수에 한계가 있다. 점수 부분과 시각 부분이 서로의 자릿수를 침범하면 순위가 뒤집힌다. "큰수"를 얼마로 잡을지는 점수의 최대 범위와 시각의 해상도(초/밀리초)를 함께 보고 정해야 하고, 안 되면 순위 계산을 애플리케이션이나 DB로 넘기는 것도 선택지다.
Redis 자료구조를 잘 고르면 락이 필요 없어지나요?힌트: 원자성이 커버하는 범위가 어디까지인지

"한 키 안에서 끝나는 읽고-고치고-쓰기"라면 그렇다. INCR, HINCRBY, SADD, ZINCRBY는 각각 명령 하나라서 그 자체로 경합이 없고, 이런 경우 별도의 락은 불필요한 비용이다.

그러나 여러 키에 걸친 작업이나 Redis 밖까지 이어지는 작업은 명령 하나로 표현되지 않는다. "재고를 줄이고 → 주문을 DB에 만들고 → 실패하면 되돌린다" 같은 것이 그렇다. 여기서는 여전히 조율 장치가 필요하고, 그게 분산 락이거나 Lua로 묶기다(Lua는 Redis 안에서 끝나는 여러 키 작업까지 커버한다).

자료구조의 원자성은 키 하나 안에서 강력하다 — 경계를 넘으면 별도의 장치가 필요하다

답의 순서를 이렇게 잡으면 좋다. ① 먼저 "락 없이 되는 경우"를 정확히 말하고 ② 경계를 긋고 ③ 그 밖에서 쓰는 도구를 든다. "Redis니까 락 필요 없어요"도, "무조건 분산 락"도 둘 다 반쪽이다.

한 줄 요약
Redis 자료구조를 안다는 건 명령어 목록 암기가 아니라 "조회-수정-저장 3단계 + 락"으로 풀던 문제를 "원자적 명령 한 방"으로 옮길 줄 아는 것 — String · Hash · List · Set · Sorted Set 각각이 어떤 연산을 서버에서 대신해 주는지가 곧 설계 선택지의 폭이다.
