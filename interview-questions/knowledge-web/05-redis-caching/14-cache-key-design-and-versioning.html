역직렬화 실패 장애의 세 얼굴 — "배·히·롤". 이 셋을 말하면 겪어 본 사람의 답변이 된다.

핵심 관전 포인트 — 그대로 말하기
캐시 키는 서비스:엔티티:버전:식별자처럼 계층적 네임스페이스로 설계하고, 결과를 가르는 조회 조건(테넌트·사용자·로케일·페이지 등)을 빠짐없이 키에 넣는다 — 하나라도 빠지면 먼저 조회한 사람이 채운 캐시를 다른 조건의 사람이 받아가는, 성능 버그가 아니라 데이터 유출 사고가 된다. 그리고 배포로 캐시 객체의 구조가 바뀌면 Redis에 남아 있던 구버전 데이터를 신버전 코드가 역직렬화하다 실패하고, 그 예외가 캐시 미스로 강등되지 않고 요청 전체를 500으로 떨어뜨린다. 해법은 키 버저닝 — member:v2:{id}처럼 신버전 코드는 새 키 공간을 쓰고 구버전 데이터는 TTL로 자연 소멸시킨다. 롤링 배포로 신구 코드가 공존해도 각자 자기 버전 키만 읽으므로 서로를 깨뜨리지 않고 롤백해도 안전하다. 대가는 전환 기간(구버전 TTL) 동안 같은 데이터가 두 벌 존재해 메모리가 최대 2배가 된다는 것이다.
출제 의도 — 캐시를 "저장소"로 보는가 "배포와 함께 움직이는 계약"으로 보는가
이 문항은 두 개의 서로 다른 실수를 한 번에 묻는다. 키에 조건을 빠뜨리는 설계 실수(§3)와 구조가 바뀐 객체를 옛 바이트로 만나는 배포 실수(§6)다. 둘의 공통점은 "캐시는 애플리케이션과 독립적으로 존재하는 공유 상태"라는 사실을 잊었을 때 생긴다는 것 — 그래서 채점은 기법 암기가 아니라 롤링 배포 중 신구 코드가 같은 캐시를 읽는 순간까지 상상하는가(§9), 그리고 롤백이 통하지 않는다는 데까지 가는가에서 갈린다.

1. 왜 키 설계가 이름 짓기가 아니라 데이터 모델링인가

RDB에는 스키마가 있다. product 테이블의 price 컬럼이 numeric이라는 사실이 DB 안에 선언돼 있고, 어긋나는 값은 DB가 거부한다. 무엇이 어디에 있고 어떤 타입인지를 저장소가 알고 있다.

Redis에는 그런 것이 없다. 테이블도 컬럼도 타입 선언도 없다. 키 하나가 "이게 무슨 데이터이고, 누구의 것이고, 어떤 조건으로 만들어졌는지"를 전부 표현해야 한다. 키 이름이 곧 스키마이자 계약서인 셈이다.

이 문서 전체가 여기서 나온다
Redis는 키가 무엇을 뜻하는지 모른다.
그래서 키에 적지 않은 것은 이 세상에 없는 것이다.

테넌트를 안 적었으면 Redis에게 그 값은 "모든 테넌트의 것"이고, 버전을 안 적었으면 "모든 버전의 것"이다. Redis는 키가 같으면 같은 데이터라는 규칙 하나만 지킬 뿐, 그 판단이 옳은지는 검사해 주지 않는다. §3의 유출 사고와 §6의 배포 장애는 둘 다 이 한 문장의 서로 다른 결과다.

오른쪽의 빈칸을 채우는 유일한 수단이 키 이름이다. 그래서 키 설계는 이름 짓기가 아니라 스키마 설계다.

2. 원칙① 계층적 네임스페이스 — 콜론으로 소속을 표현한다

{서비스/도메인}:{엔티티}:{버전}:{식별자}

member:v1:1234                        # 회원 1234의 캐시
ranking:webtoon:v2:daily:2026-08-31   # 일간 웹툰 랭킹
session:a1b2c3...                     # 세션
세 이득 모두 평소에는 없어도 아무 지장이 없다. 아무 규칙 없이 만든 키의 무서움은 문제가 터진 그 순간에 손댈 방법이 없다는 데 있다.
규칙 없는 키의 정확한 대가 — 한 문장
아무 규칙 없이 만든 키는 "지울 수도, 셀 수도, 추적할 수도 없는" 데이터가 된다. 잘 동작하는 동안에는 아무 문제가 없다가, 문제가 생긴 그 순간에만 대가를 청구한다는 것이 이 실수의 성격이다.

3. 원칙② 결과를 가르는 조건은 전부 키에 — 하나 빠지면 남의 데이터가 보인다

철칙 — 이 한 문장만 외워도 절반은 끝난다
메서드의 반환값을 바꾸는 입력은 전부 키에 들어가야 한다.

이유를 원칙으로 외우면 잊는다. 사고가 나는 과정을 한 번 따라가면 몸에 남는다. 아래 시퀀스를 그림으로 한 번, 코드로 한 번 본다.

비유 — 캐시 키는 택배 송장의 주소다
송장에 "○○아파트 101동"까지만 쓰고 호수를 안 썼다. 택배 기사는 규칙대로 그 주소에 배달하고, 먼저 문을 연 집이 물건을 받는다. 기사에게는 아무 잘못이 없다 — 주소에 적히지 않은 것을 알아낼 방법이 없기 때문이다. Redis도 똑같다. 키에 테넌트를 안 적었다면 그 값은 "먼저 온 사람의 것"이 아니라 "그 주소를 쓰는 모두의 것"이 된다.
✕ before — 회사(테넌트) 구분이 키에서 빠졌다
// 반환값은 companyId에 따라 달라지는데
// 키는 menuId만 보고 있다
@Cacheable(cacheNames = "menu", key = "#menuId")
public MenuAuth findMenuAuth(Long companyId,
                             Long menuId) { ... }

// 실제 키: "menu::7"
// companyId 100과 200이 같은 칸을 쓴다
✓ after — 결과를 바꾸는 입력을 모두 키에
// companyId가 다르면 키가 달라지므로
// 서로의 캐시를 만날 수 없다
@Cacheable(cacheNames = "menu",
           key = "#companyId + ':' + #menuId")
public MenuAuth findMenuAuth(Long companyId,
                             Long menuId) { ... }

// 실제 키: "menu::100:7" / "menu::200:7"
"먼저 채운 쪽이 이긴다"가 TTL 내내 유지된다. 캐시 값이 조회 데이터였다면 정보 유출, 권한 데이터였다면 인가 우회다.

3-1. 이 사고의 성질 셋 — 왜 "성능 버그"가 아닌가

1
성능 버그가 아니라 보안 사고다 캐시 값이 단순 조회 데이터였다면 남의 데이터가 화면에 뜨는 정보 유출이고, 위 예시처럼 권한 데이터였다면 인가 우회다. 캐시 코드에서 시작했지만 결과는 보안 결함으로 분류된다.
2
간헐적이지 않다 — TTL 동안 확정적으로 틀리다 캐시가 살아 있는 동안 먼저 채운 쪽이 계속 이긴다. "가끔 이상하다"가 아니라 "TTL 동안 전원이 같은 오답을 본다"이므로 피해 범위가 시간에 비례해 커진다.
3
기능 테스트로는 절대 못 잡는다 테스트는 대개 단일 테넌트로 돈다. companyId=100으로만 테스트하면 키가 충돌할 상대가 없어서 영원히 통과한다. 테스트에 두 개 이상의 테넌트가 등장하지 않는 한, 이 버그를 잡는 곳은 코드 리뷰뿐이다.

3-2. 로케일도 정확히 같은 구조다

✕ before — 로케일 누락
@Cacheable(cacheNames = "notice", key = "#noticeId")
public NoticeView findNotice(Long noticeId,
                             Locale locale) { ... }

// 첫 조회자가 한국인이면 그 TTL 동안
// 전 세계가 한국어 공지를 본다
✓ after — locale도 결과를 바꾸므로 키에
@Cacheable(cacheNames = "notice",
           key = "#noticeId + ':' + #locale")
public NoticeView findNotice(Long noticeId,
                             Locale locale) { ... }

// ko / ja / en이 각자의 칸을 쓴다

3-3. 진짜 위험한 것은 파라미터가 아닌 입력이다

메서드 시그니처에 보이는 입력은 그나마 눈에 띈다. 결과를 바꾸지만 파라미터가 아닌 것이 훨씬 위험하다 — 시그니처만 봐서는 존재 자체가 안 보이기 때문이다.

리뷰에서 그대로 쓰는 점검 문장
"이 메서드의 반환값을 바꾸는 것이 무엇인가?
파라미터든 아니든, 그것이 전부 키에 있는가?"
  • 테넌트 / 회사 ID — 멀티 테넌트 서비스에서 가장 자주 빠지고, 빠졌을 때 가장 크게 터진다
  • 로그인 사용자 ID — SecurityContext에서 꺼내 쓰는 경우 파라미터에 없다 최다 사고
  • 권한 / 역할 — 같은 데이터라도 역할에 따라 마스킹 결과가 달라진다면 키에 들어가야 한다
  • 로케일 / 타임존 / 통화 — 요청 헤더나 LocaleContextHolder에서 오므로 역시 파라미터에 없다
  • 페이지 · 정렬 · 필터 조건 — 목록 캐시에서 page만 넣고 sort를 빠뜨리는 실수가 흔하다
  • 스레드 로컬 컨텍스트 전반 — 값이 어디서 오든 결과를 바꾸면 키에 들어간다가 유일한 기준이다

4. 반대 방향의 실수 — 결과와 무관한 값이 키에 섞이면

빠뜨리는 것만 문제가 아니다. 반대로 결과에 영향을 주지 않는 값(요청 시각, 랜덤 값, 트레이스 ID 등)이 키에 섞이면 매 요청마다 다른 키가 만들어진다.

그러면 캐시는 항상 미스가 되고, 그 위에 아무도 다시 읽지 않을 데이터가 계속 쌓여 메모리까지 먹는다. 히트율 0%짜리 캐시는 없는 것보다 나쁘다 — DB 부하는 그대로인데 Redis 왕복 시간과 메모리만 추가로 낸다.

왼쪽은 정합성이 깨지고, 오른쪽은 효용이 사라진다. 왼쪽이 더 무서운 이유는 히트율 지표가 오히려 좋아 보여서 모니터링에 걸리지 않는다는 점이다.
양방향 원칙 — 카드로 외운다
키 = 결과를 결정하는 입력의 집합 — 그 이상도 이하도 아니게.

모자라면 남의 데이터를 받고, 넘치면 캐시가 동작하지 않는다. 두 실수는 반대 방향이지만 판정 기준은 하나다 — "이 값이 반환값을 바꾸는가?"

5. 원칙③ 키 자체의 위생 — 길이, 가변 문자열, big key

5-1. 사용자 입력을 키에 그대로 넣지 않는다

검색어처럼 사용자가 만든 문자열을 키에 그대로 넣으면 두 가지가 무너진다. 길이가 폭주해 수 KB짜리 키가 생길 수 있고, 입력에 콜론이 섞이면 계층 구분자가 망가진다. 후자는 단순한 미관 문제가 아니라 다른 캐시의 키와 겹치는 문자열을 사용자가 만들어낼 수 있다는 뜻이다.

✕ before — 검색어를 날것으로
String key = "search:" + keyword;

// keyword = "노트북"          → search:노트북
// keyword = 2KB짜리 문장      → 키가 2KB
// keyword = "a:v9:1"          → search:a:v9:1
//   사용자가 계층 구조를 흉내 낼 수 있다
✓ after — 해시로 길이·문자를 정규화
String norm = keyword.trim().toLowerCase();
String h = sha256Hex(norm).substring(0, 16);
String key = "search:v1:" + h;

// 어떤 입력이든 길이가 고정된다
// 콜론·공백·개행 같은 문자가 사라진다
// 원문이 필요하면 값(value)에 함께 담는다

해시를 잘라 쓰면 서로 다른 입력이 같은 키가 될 확률이 생긴다. 자릿수를 넉넉히 잡는 것이 1차 방어이고, 그 위에 값에 원본 조건을 함께 저장해 두고 읽을 때 대조하면 충돌해도 잘못된 값을 반환하지 않는다(§14 꼬리질문).

5-2. big key — 키 설계 단계에서 막는다 가산점

왜 Redis에서 "큰 값 하나"가 유독 위험한가
Redis는 명령을 단일 스레드로 처리한다 —
큰 값 하나를 다루는 동안 다른 모든 명령이 대기한다.

컬렉션형 키 하나에 수백만 멤버를 쌓는 설계(big key)는 조회·삭제·마이그레이션 전부를 블로킹 폭탄으로 만든다. 다른 저장소라면 "느린 쿼리 하나"로 끝날 일이 여기서는 인스턴스 전체의 정지가 된다. 그래서 대응은 사후 튜닝이 아니라 키 설계 단계의 샤딩이다 — 날짜별·범위별로 쪼개 ranking:daily:2026-08-31처럼 키를 나누어 크기의 상한을 만든다.

6. 배포가 캐시를 깨뜨리는 순간 — 역직렬화 실패 장애의 해부

6-1. 전제 — 캐시에는 객체가 아니라 바이트가 들어 있다

Redis에 자바 객체를 그대로 넣을 수는 없다. 객체를 바이트 배열로 펼쳐서(직렬화) 저장하고, 꺼낼 때 그 바이트를 다시 객체로 되살린다(역직렬화). 여기서 결정적인 사실이 둘이다.

① 바이트는 그때 코드의 스냅샷 과거가 박제된다

어떤 필드가 어떤 순서로 어떤 타입으로 있었는지가 그 바이트에 반영돼 있다. 저장하는 순간의 클래스 구조가 그대로 굳어 Redis에 남는다.

② 캐시는 배포 대상이 아니다 코드만 바뀐다

애플리케이션을 새 버전으로 교체해도 Redis 안의 바이트는 그대로다. 코드는 새것, 데이터는 옛것 — 이 어긋남이 장애의 씨앗이다.

비유 — 납작포장 가구와 조립 설명서
직렬화는 가구를 부품으로 분해해 납작한 상자에 넣는 것이고, 역직렬화는 설명서를 보며 다시 조립하는 것이다. 창고(Redis)에는 작년 모델의 부품 상자가 쌓여 있는데, 배포로 손에 들린 설명서는 올해 모델용이다. 설명서에 없는 부품(category)이 나오고, "다리 4개" 자리에 전혀 다른 규격의 부품(int → Money)이 들어 있다. 부품도 설명서도 각자는 멀쩡한데, 조립만 실패한다.
배포 전(v1) 코드가 캐시에 저장한 구조
public class ProductView {
    private Long id;
    private String name;
    private int price;          // 이때는 int였다
    private String category;    // v2에서 삭제될 필드
}
배포 후(v2) 코드 — 타입 변경 + 필드 삭제
public class ProductView {
    private Long id;
    private String name;
    private Money price;        // int → Money 객체
    // category 필드는 삭제됐다
}

6-2. 왜 배포 직후에만 터지는가 — 다섯 단계

위 트랙(코드)은 배포 시각에 갈아 끼워지지만, 아래 트랙(데이터)은 TTL이라는 자기 시계로 움직인다. 두 트랙의 시차가 곧 장애 구간이다.

7. 왜 미스가 아니라 500이 되는가 — 예외가 캐시 계층에서 삼켜지지 않는다

"역직렬화가 실패했으면 캐시에 없는 셈 치고 DB에서 읽으면 되지 않나"가 자연스러운 기대다. 그런데 기본 동작은 그렇지 않다.

Spring Cache에서 캐시 조회 중 발생한 예외를 처리하는 것은 CacheErrorHandler인데, 기본 구현은 예외를 그대로 위로 다시 던진다. 캐시 계층에서 삼키지 않는다는 뜻이다.

두 트랙의 차이는 단 하나의 분기다. 그런데 그 분기 하나가 "500 장애"와 "일시적 히트율 저하"를 가른다.
가장 이상한 부분을 한 문장으로
DB는 멀쩡하고 쿼리도 문제없는데,
캐시 하나 때문에 기능 전체가 죽는다.

메서드 본문이 실행조차 되지 않는다는 점이 핵심이다. 캐시는 원래 "있으면 빠르게, 없으면 원래대로"인 부가 장치인데, 이 순간만큼은 있으면 죽고 없으면 사는 정반대 성질로 돌변한다.

8. JDK 직렬화와 JSON은 다르게 실패한다 — "JSON 쓰면 되잖아요"의 정리

JDK 기본 직렬화 즉시, 시끄럽게 실패

JdkSerializationRedisSerializer. 자바 직렬화 바이트에는 serialVersionUID라는 클래스 구조의 지문이 함께 박힌다. 명시하지 않으면 컴파일러가 필드·메서드 구성으로 자동 계산하는데, 필드를 하나만 추가해도 값이 달라진다.

  • 바이트에 박힌 값 ≠ 현재 클래스의 값 → 그 자리에서 예외
  • serialVersionUID를 손으로 고정해도 int price → Money price 같은 타입 변경은 결국 실패
  • 실패가 즉시 드러난다는 점은 역설적으로 장점이다
JSON 직렬화 조용히 살아남는다 — 그게 더 나쁠 수 있다

JSON에는 필드 이름과 값만 있고 클래스 구조의 지문이 없다. 그래서 모르는 필드를 만났을 때의 행동이 설정에 달려 있다.

  • 알 수 없는 필드를 무시하도록 설정(Jackson FAIL_ON_UNKNOWN_PROPERTIES 끔) → v1이 남긴 category를 무시하고 통과
  • v2에서 새로 추가한 필드는 구 데이터에 없으므로 null(원시 타입이면 0)이 들어간다 — 예외도 로그도 없이
진짜 함정 — 두 번째 줄
예외는 스택 트레이스가 남고 알람이 울린다.
조용히 들어간 null과 0은 한참 뒤 엉뚱한 곳에서 나타난다.

뒤늦은 NullPointerException이면 그나마 낫고, 더 나쁘게는 0으로 계산된 금액이 정상처럼 서빙된다. "터지는 버그"보다 "틀린 값을 성공적으로 응답하는 버그"가 훨씬 찾기 어렵고 피해도 크다.

JSON은 "버저닝이 필요한 횟수를 줄여 주는 도구"이지 버저닝의 대체재가 아니다. 관대한 범위는 필드 추가·삭제라는 좁은 구간뿐이고, 타입·의미가 바뀌는 순간 JDK 직렬화와 똑같이 무너지거나 더 조용하게 무너진다.

9. 롤링 배포 — 신구 코드가 공존하는 몇 분 여기서 답변 수준이 갈린다

지금까지는 "v1이 남긴 데이터를 v2가 읽는" 한 방향만 봤다. 실제 배포는 순간에 끝나지 않는다. 롤링 배포는 인스턴스를 한 대씩 교체하므로, 그 몇 분 동안 v1과 v2가 동시에 떠서 같은 Redis를 본다. 그러면 오염이 양방향으로 일어난다.

파란 사각형이 v1, 보라 사각형이 v2 인스턴스다. t1의 ★가 분기점 — v2는 아무 잘못 없이 정상 동작하면서 캐시를 오염시킨다.
t4가 이 사고의 가장 악명 높은 지점
캐시라는 공유 상태는 코드 버전과 독립적으로 존재한다 —
그래서 코드만 되돌려서는 세상이 원래대로 돌아가지 않는다.

원인을 한 문장으로 압축하면 이렇다. 캐시에 저장된 데이터의 구조는 코드와 함께 배포되지도, 함께 롤백되지도 않는다. "롤백했는데 왜 안 낫지?"가 이 사고의 전형적 전개이고, 이때는 캐시를 직접 지우기 전까지 낫지 않는다.

10. 해법 — 키 버저닝으로 신구를 공존시킨다

✕ before — 버전 없는 키
String key = "product:" + productId;

// 구조 변경 배포마다 §9의 지뢰밭을 밟는다
✓ after — 키에 버전 세그먼트를 포함
static final String CACHE_VERSION = "v2";
String key = "product:" + CACHE_VERSION
           + ":" + productId;

// 캐시에 들어가는 클래스의 구조가 바뀌는
// 배포에서 v3으로 올린다
효과의 전부를 한 문장으로
신버전 코드가 구버전 데이터를 아예 만나지 않는다.

§6~§9에서 본 모든 문제가 "만나기 때문에" 생겼다. 그러니 만나지 않게 하면 전부 사라진다. 새로운 방어 장치를 추가하는 것이 아니라 문제가 성립할 조건 자체를 없애는 해법이라는 점이 중요하다.

키 버저닝의 값어치는 배포 중 몇 분을 넘기는 데 있는 것이 아니라, 문제가 생겼을 때 되돌릴 수 있게 만드는 데 있다. 이 문장까지 말하면 상급 답변이다.

10-1. §9의 타임라인이 어떻게 바뀌는가 — 대비표

시점버전 없는 키버전 있는 키
t1 공존 시작 v2가 v1 데이터를 히트 → 역직렬화 실패 → 500. 동시에 v2가 미스 시 신 구조를 써 넣어 오염이 시작된다. v2는 product:v2:*를 보는데 아무것도 없다 → 전부 미스 → DB에서 읽어 v2 구조로 채운다. v1은 여전히 자기 구조만 만난다.
t2 양방향 오염 v1도 v2도 상대가 남긴 데이터에 걸려 넘어진다. 요청이 어느 인스턴스로 갔느냐에 따라 성패가 뒤섞인다. 두 키 공간이 겹치지 않으므로 오염이라는 사건 자체가 없다.
t3 전량 교체 후 t1 이전 v1이 남긴 데이터가 TTL 동안 살아 있어 산발적 500이 계속된다. product:v1:*는 아무도 읽지 않게 되고 TTL이 다하면 자연 소멸한다. 지우는 작업조차 필요 없다.
t4 롤백 캐시에 신 구조가 가득해 롤백해도 장애가 안 낫는다. 캐시를 직접 지워야 한다. v1은 다시 product:v1:*를 본다. 자기가 이해할 수 있는 데이터만 있다 — 롤백이 제대로 작동한다.

10-2. Spring Cache에 적용하기

키를 문자열로 직접 조립하지 않고 @Cacheable을 쓴다면, 캐시 이름이나 key prefix에 버전을 넣는다.

RedisCacheConfiguration config = RedisCacheConfiguration.defaultCacheConfig()
        // 실제 키가 "myapp:product:v2:1234" 형태로 만들어진다
        .computePrefixWith(cacheName -> "myapp:" + cacheName + ":v2:")
        .entryTtl(Duration.ofMinutes(30));
전역 적용의 대가 — 편한 만큼 비싸다
버전을 올리면 모든 캐시가 한꺼번에 새 공간으로 옮겨 간다. 구조가 바뀌지 않은 캐시까지 전부 미스가 되어 다시 채워야 하므로, 사실상 전면 flush와 같은 순간(§12-3의 cold cache)을 만든다. 캐시 종류가 많고 그중 하나만 바뀌었다면 캐시 이름 단위로 버전을 관리하는 편이 낫다.

10-3. 버전 값을 어떻게 관리하나 — 자동화의 함정

자동 버전 (구조 해시 · 배포 버전) 부작용이 명확

클래스 구조 해시나 배포 버전을 자동으로 키에 넣으면 사람이 깜빡할 일이 없다. 그런데 구조가 안 바뀐 배포에서도 캐시가 통째로 리셋된다.

  • 하루에 몇 번씩 배포하는 팀이라면 그때마다 캐시가 비고
  • 그 순간마다 DB가 전체 트래픽을 맞는다(cold cache)
  • 결국 배포가 곧 장애 위험이 된다
수동 버전 + 안전망 실무 절충

버전을 손으로 올리는 상수로 두면 깜빡할 수 있다. 그래서 "캐시 구조에 영향을 주는 변경"과 함께 리뷰에 걸리도록 한 곳에 모아 관리한다.

  • 구조가 실제로 바뀔 때만 수동으로 올린다
  • 깜빡한 경우는 §12-1의 안전망이 받는다
  • 사람의 규율과 구조적 안전망을 겹쳐서 쓴다

11. 대가 — 전환 기간의 이중 메모리

키 버저닝이 공짜는 아니다. 전환 기간 동안 같은 데이터가 두 벌 존재한다. 이 대가를 먼저 말하는 것이 기법을 외운 사람과 써 본 사람의 차이다.

배포 → 최대 8GB → TTL 경과 후 다시 4GB. 피크의 높이는 정해져 있고(2배), 피크의 길이만 TTL이 정한다.
①
회수 기간을 줄인다 — SCAN + UNLINK로 점진 삭제 배포 후 구버전 prefix를 골라 지운다. KEYS는 전체 키스페이스를 한 번에 훑으며 서버를 블로킹하므로 운영에서 금지다. SCAN은 커서로 조금씩 나눠 훑고, UNLINK는 삭제를 백그라운드 스레드에 넘기므로 큰 값을 지울 때도 서버가 멈추지 않는다(DEL은 그 자리에서 회수한다).
②
최악의 경우를 OOM이 아니라 축출로 만든다 maxmemory와 eviction 정책(예: allkeys-lru)이 설정돼 있는지 확인한다. 설정돼 있으면 메모리가 차더라도 오래된 키부터 밀려날 뿐이지만, 설정이 없으면 쓰기가 거부되거나 프로세스가 죽는다. 이중 메모리를 감당할 수 있는 상태인지가 여기서 갈린다.
이 대가를 말하는 방식 — 결론 문장
"일시적 2배 메모리"는 역직렬화 장애와 롤백 불능을 피하는
값싼 보험료다.

대가를 숨기지 않고 먼저 꺼내되, 그것이 무엇과 교환되는지를 같은 문장 안에 넣는 것이 요령이다. "메모리가 두 배 듭니다"에서 멈추면 단점 보고이고, "2배 메모리 ↔ 장애 + 롤백 불능"으로 저울을 보여 주면 설계 판단이 된다.

12. 안전망 3종 — 해법이 아니라 보조 수단이라는 순서를 지킨다

순서를 먼저 못 박는다
아래 셋은 전부 유용하지만 어느 것도 §10의 키 버저닝을 대체하지 못한다. 면접에서 이 순서가 뒤집히면("역직렬화 예외를 잡아서 처리하면 됩니다") 증상 처리와 원인 제거를 구분하지 못하는 답변이 된다. 해법은 만나지 않게 하는 것이고, 아래는 만났을 때를 대비하는 것이다.

12-1. 안전망① 역직렬화 실패를 캐시 미스로 강등한다

§7에서 본 대로 기본 동작은 예외를 위로 던지는 것이다. 이 기본값을 뒤집어 두면, 버전 올리는 걸 깜빡한 배포에서도 장애 대신 성능 저하로 끝난다.

public Optional<ProductView> getFromCache(String key) {
    try {
        return Optional.ofNullable(redisTemplate.opsForValue().get(key));
    } catch (SerializationException e) {
        // 읽을 수 없는 데이터는 남겨 둘 이유가 없다.
        // 지워야 다음 요청이 DB에서 읽어 새 구조로 다시 채운다.
        redisTemplate.delete(key);
        // 조용히 넘기면 안 된다. 이 로그가 "버전을 안 올렸다"는 유일한 신호다.
        log.warn("cache deserialization failed, treat as miss: {}", key, e);
        // 빈 결과 = 캐시 미스. 호출부는 평소처럼 DB에서 읽는다.
        return Optional.empty();
    }
}

Spring Cache를 쓴다면 같은 효과를 CacheErrorHandler를 커스터마이징해 전역으로 걸 수 있다. 조회 예외를 미스로 처리하도록 바꾸는 것이다. 가산점

이것만 있고 버저닝이 없으면 — 사실상 전면 flush
배포 직후 캐시 전체가 한 번씩 실패하고 지워지므로 결과적으로 전면 flush와 같아진다. 장애(500)는 면하지만 DB가 그 순간 전체 트래픽을 맞는 위험은 그대로 남는다. 그래서 이것은 "버전을 깜빡했을 때의 최후 방어선"이지 평시 설계가 아니다. 그리고 로그를 반드시 남기는 이유도 여기 있다 — 조용히 성공하면 깜빡한 사실 자체를 아무도 모른 채 매 배포마다 캐시가 통째로 날아간다.

12-2. 안전망② 구조 변화에 강한 직렬화 포맷을 고른다

§8의 결론대로 JDK 기본 직렬화는 피하고 JSON을 기본으로 쓴다. 필드 추가·삭제 정도는 버전 업 없이 흡수되므로 버전을 올려야 하는 횟수 자체가 줄어든다. 단, JSON도 타입 변경과 의미 변경 앞에서는 무력하고 오히려 조용히 틀린 값을 서빙할 수 있으므로 "JSON이면 버저닝이 필요 없다"는 오답이다.

12-3. 안전망③ 배포 시 전체 flush는 최후의 수단

(1) cold cache 2차 장애

캐시 전체가 비는 순간 DB가 원래 트래픽을 그대로 맞는다. 캐시 히트율 99%를 전제로 용량이 잡힌 시스템이라면 DB에 평소의 100배가 몰린다는 뜻이다. 트래픽이 낮은 시간대가 아니면 그 자체가 2차 장애가 된다.

(2) 롤링 배포와 충돌 오염원이 살아 있다

flush를 해도 아직 v1 인스턴스가 남아 있으면 v1이 다시 구 구조로 캐시를 채우고, v2가 그걸 읽다 또 깨진다. flush는 한 시점의 청소일 뿐이고 오염원은 아직 살아 있다. 청소가 한 번으로 끝나지 않는다.

키 버저닝을 다시 정의하면
키 버저닝은 이 flush를 "필요 없는 작업"으로 만드는 설계다.

신버전은 애초에 빈 키 공간에서 시작하므로 청소할 대상이 없고, 구 데이터는 아무도 안 읽는 채로 TTL을 기다리다 사라진다. 게다가 신버전 캐시는 요청이 오는 대로 점진적으로 채워지므로 flush처럼 한 순간에 전부 미스가 되지도 않는다.

12-4. 사람 쪽 규율 — 리뷰에서 "버전 올릴 변경"을 알아보는 법

①
캐시에 들어가는 DTO를 별도 패키지·네이밍으로 격리한다 그러면 "이 클래스를 고쳤다 = 캐시 계약을 고쳤다"가 diff에서 눈에 보인다. 반대로 엔티티를 그대로 캐시에 넣으면 이 신호가 사라진다 — 도메인 로직 때문에 필드를 고쳤을 뿐인데 캐시 계약이 함께 깨지고, 리뷰어는 그 사실을 알아챌 단서가 없다.
②
판단 기준은 API 하위 호환성과 동일하다 필드 추가는 호환(버전 유지 가능), 타입 변경 · 삭제 · 의미 변경은 비호환(버전 업). 새 기준을 만들 필요 없이 이미 팀이 공유하고 있는 API 호환성 감각을 그대로 가져다 쓴다는 점이 이 방법의 강점이다.
③
규율과 안전망을 겹친다 §12-1의 CacheErrorHandler를 전역에 깔아 두면 사람이 놓친 경우에도 장애가 아니라 "일시적 히트율 저하 + 경고 로그"로 끝난다. 규율만 있으면 언젠가 놓치고, 안전망만 있으면 놓친 줄도 모른 채 성능이 새어 나간다.

14. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 시니어 변별 문항은 정답 하나를 고르지 말고 판단 기준을 말하는 연습을 한다.

배포할 때마다 캐시를 전부 지우면 간단하지 않나요?

동작은 하지만 비용이 두 가지 크다.

  • ① cold cache. 캐시 히트율을 전제로 용량이 설계된 시스템에서 캐시가 비는 순간 DB가 전체 트래픽을 직격으로 맞는다. 히트율 99%를 전제했다면 DB에 평소의 100배가 몰린다는 뜻이고, 트래픽이 높은 시간대 배포라면 그 자체가 장애다.
  • ② 롤링 배포와 충돌. flush 후에도 구버전 인스턴스가 남아 있으면 구버전이 다시 구 구조로 캐시를 채우고, 신버전이 그걸 읽다 또 깨진다. 오염원이 살아 있는 한 청소는 한 번으로 끝나지 않는다.

키 버저닝은 flush 없이(따라서 cold cache 없이) 신버전만 새 공간에서 점진적으로 캐시를 채우게 하므로 두 문제를 모두 피한다. "전부 지우기"와 "새 공간에서 시작하기"의 차이가 곧 이 문항의 요지다.

롤링 배포 중 신구 코드가 같은 캐시를 읽으면 정확히 무슨 일이 벌어지나요? 시니어 변별

버전 없는 키라면 양방향으로 깨진다(§9의 타임라인).

  1. 구버전 인스턴스가 구 구조로 저장 → 신버전이 히트해서 역직렬화 실패.
  2. 반대로 신버전이 신 구조로 저장 → 구버전이 히트해서 실패.

즉 배포가 진행되는 내내 양쪽 모두에서 산발적으로 에러가 난다. 어느 인스턴스로 요청이 갔느냐에 따라 성패가 갈리므로 재현이 안 되는 것처럼 보인다.

가장 아픈 지점은 그다음이다. 롤백해도 신 구조 데이터가 캐시에 남아 있어 롤백 후에도 장애가 계속된다. "롤백했는데 왜 안 낫지?"가 이 사고의 전형적 전개이고, 이때는 캐시를 직접 지우기 전까지 낫지 않는다.

키 버저닝이면 신구가 각자의 키 공간을 쓰므로 배포 중에도, 롤백 후에도 서로 간섭이 없다. 이 롤백 안전성까지 짚는 것이 상급이다.

키에 버전을 넣으면 전환 기간 동안 메모리가 이중으로 들지 않나요?

맞다. v1과 v2가 공존하는 동안 그 캐시의 메모리가 일시적으로 최대 2배가 되고, 그 기간은 구버전 데이터의 TTL만큼이다. TTL 30분이면 30분, 하루면 하루다.

그래서 두 가지로 관리한다.

  • 메모리 여유가 빠듯하면 배포 후 구버전 prefix를 SCAN + UNLINK로 점진 삭제해 회수 기간을 줄인다(KEYS는 서버를 블로킹하므로 운영 금지, UNLINK는 삭제를 백그라운드로 넘긴다).
  • maxmemory와 eviction 정책(예: allkeys-lru)이 설정돼 있는지 확인해, 최악의 경우에도 OOM이 아니라 오래된 키부터 밀려나게 해 둔다.

"일시적 2배 메모리는 역직렬화 장애와 롤백 불능을 피하는 값싼 보험료"라는 게 결론이다.

JSON 직렬화를 쓰면 버저닝 없이도 되지 않나요?

부분적으로만 맞다. JSON은 필드 추가(구 데이터에 없는 필드 → 기본값)와 필드 삭제(모르는 필드 무시 설정 시)에는 관대하다.

하지만 다음은 못 막는다.

  1. 필드 타입 변경(int → 객체)은 예외가 난다.
  2. 같은 필드의 의미·단위 변경(원 → 달러)은 타입도 이름도 그대로라 아무도 못 알아채고 조용히 잘못된 값으로 읽힌다.
  3. enum 상수 제거는 사라진 이름을 만나면 예외가 난다.

그리고 JSON이 "관대하게" 넘어가는 경우도 마냥 좋은 게 아니다. v2에서 새로 추가한 필드는 구 데이터에 없으므로 null로 들어오고, 예외도 로그도 없다. 예외는 알람이라도 울리지만, 의미가 바뀐 값이 정상처럼 서빙되는 쪽이 훨씬 찾기 어렵고 피해가 크다.

실무 규칙은 "JSON을 기본 포맷으로 쓰되, 하위 호환이 깨지는 변경에는 반드시 키 버전을 올린다"이다. JSON은 버저닝의 대체재가 아니라 버저닝 횟수를 줄여 주는 도구다.

버전을 올려야 하는 변경인지 아닌지, 어떻게 리뷰에서 잡나요?

첫걸음은 캐시에 들어가는 DTO를 별도 패키지나 네이밍으로 격리하는 것이다. 그러면 "이 클래스를 고쳤다 = 캐시 계약을 고쳤다"가 diff에서 눈에 보인다.

반대로 엔티티를 그대로 캐시에 넣으면 이 신호가 사라진다 — 도메인 로직 때문에 필드를 고쳤을 뿐인데 캐시 계약이 함께 깨지고, 리뷰어는 그 사실을 알아챌 단서가 없다.

판단 기준은 API 하위 호환성과 동일하다. 필드 추가는 호환(버전 유지 가능), 타입 변경·삭제·의미 변경은 비호환(버전 업).

여기에 역직렬화 실패를 미스로 강등하는 CacheErrorHandler를 전역 안전망으로 깔아 두면, 사람이 놓친 경우에도 장애가 아니라 "일시적 히트율 저하 + 경고 로그"로 끝난다. 사람의 규율과 구조적 안전망을 겹치는 것이 정답이다 — 규율만 있으면 언젠가 놓치고, 안전망만 있으면 놓친 줄도 모른 채 성능이 새어 나간다.

@Cacheable에서 key를 아예 생략하면 안전한가요? 추가

"파라미터에 관해서는" 안전하고, "파라미터가 아닌 입력에 관해서는" 전혀 안전하지 않다.

key를 생략하면 스프링의 기본 키 생성기가 메서드 파라미터로 키를 만든다. 파라미터가 하나면 그 값이, 여러 개면 그것들을 묶은 복합 키가 된다. 그래서 "파라미터를 빠뜨리는" 실수는 구조적으로 막힌다 — §13의 1·2번 유형은 자동으로 방어된다.

문제는 파라미터가 아닌 입력이다. SecurityContext의 로그인 사용자, 요청 헤더의 로케일, 스레드 로컬의 테넌트는 시그니처에 없으므로 절대 키에 들어가지 않는다. §13의 3번 유형(남의 주문 목록이 보이는 사고)은 key를 생략해도 그대로 난다.

주의할 점이 둘 더 있다.

  • 키에 쓰이는 파라미터 객체의 equals/hashCode가 값 기반이 아니면 같은 조건인데도 다른 키가 되어 히트율이 무너진다(§4의 과잉 방향 실수).
  • 자동 생성 키는 사람이 읽기 어려운 형태가 되기 쉬워 §2의 판독 가능성·prefix 조작이라는 이득을 잃는다.

정리하면 "암묵적 컨텍스트를 파라미터로 끌어올려 시그니처에 드러나게 만드는 것"이 근본 처방이다. 보이지 않는 입력은 키에도 리뷰에도 잡히지 않는다.

검색어를 해시로 잘라 키에 넣으면 충돌 걱정은 없나요? 추가

해시를 자르는 순간 충돌 가능성은 원리상 생긴다. 그리고 충돌하면 결과가 §3과 똑같아진다 — 다른 조건의 사람이 남의 결과를 받는다. 조건을 빠뜨린 것과 사실상 같은 사고다.

대응은 두 겹이다.

  • 자릿수를 넉넉히 잡는다. 짧게 자를수록 충돌 확률이 급격히 올라가므로, "키가 조금 길어지는 것"과 "충돌"을 저울에 올리면 답은 명확하다.
  • 값에 원본 조건을 함께 저장하고 읽을 때 대조한다. 캐시 값 안에 정규화된 원본 검색어를 넣어 두고, 꺼낸 값의 원본이 지금 요청의 원본과 다르면 미스로 취급한다. 그러면 충돌이 나도 잘못된 값을 반환하지 않고 성능만 조금 손해본다.

두 번째가 이 문서 전체의 반복되는 패턴이다 — 확률적으로 드문 사고를 "틀린 응답"이 아니라 "미스"로 강등시키는 것(§12-1과 같은 발상).

TTL 없이 영구 보관하는 캐시라면 키 버저닝이 어떻게 되나요? 시니어 변별 추가

키 버저닝의 가장 우아한 부분이 사라진다. "구버전 데이터는 TTL로 자연 소멸한다"는 문장은 TTL이 있다는 전제 위에서만 성립하기 때문이다.

TTL이 없으면 이렇게 된다.

  • 버전을 올린 뒤 구버전 키가 영원히 남아 메모리를 계속 점유한다. 버전을 올릴 때마다 쓰레기 층이 하나씩 쌓인다.
  • 따라서 명시적 삭제(SCAN + UNLINK)가 선택이 아니라 필수 작업이 되고, 배포 절차에 그 단계를 넣어야 한다.
  • maxmemory + allkeys-lru가 걸려 있다면 축출이 대신 정리해 주기는 하지만, 그때는 구버전만 골라 밀어내는 게 아니라 신버전의 콜드한 키까지 함께 밀린다.

한 단계 더 나아가면 이런 정리가 나온다. TTL은 성능 장치이기 전에 "잘못된 것을 스스로 청소하는 장치"다. 무효화 유실, 구조 변경, 조건 누락 — 어떤 실수든 TTL이 있으면 유한한 시간 안에 끝나지만, TTL이 없으면 영원히 남는다. 그래서 "영구 캐시"는 캐시가 아니라 사실상 저장소로 취급해 설계해야 한다.

구버전 키를 SCAN + UNLINK로 지울 때 주의할 점은? 추가

먼저 왜 KEYS가 아니라 SCAN인지가 핵심이다. Redis는 명령을 단일 스레드로 처리하므로, 전체 키스페이스를 한 번에 훑는 KEYS는 그 시간 동안 모든 명령을 대기시킨다. 키가 수백만 개면 그 자체가 장애다. SCAN은 커서로 조금씩 나눠 훑어 각 호출을 짧게 유지한다.

실무에서 챙길 것들.

  • SCAN은 스냅샷이 아니다. 순회 중 계속 존재한 키는 반환이 보장되지만, 같은 키가 여러 번 나올 수 있고 순회 도중 새로 생긴 키는 보장이 없다. 삭제 작업이라면 중복 반환은 무해하지만, "한 번의 순회로 전부 지웠다"고 가정하면 안 된다 — 나중에 한 번 더 돌린다.
  • UNLINK로 지운다. DEL은 큰 값을 그 자리에서 회수하므로 큰 컬렉션 하나가 서버를 멈출 수 있다. UNLINK는 회수를 백그라운드 스레드에 넘긴다(Redis 4.0부터).
  • 배치로 묶고 속도를 조절한다. 한 번에 지우는 개수를 제한하고 사이에 짧은 간격을 두면, 삭제 작업이 평시 트래픽의 지연에 영향을 주지 않는다.
  • 클러스터에서는 노드마다 돌려야 한다. 키 공간이 노드별로 나뉘어 있으므로 한 노드에서만 SCAN하면 일부만 지워진다.

그리고 순서를 잊지 않는다 — 이 청소는 "메모리를 빨리 회수하고 싶을 때의 선택지"이지, 키 버저닝이 동작하기 위한 필수 절차가 아니다. TTL이 있으면 가만히 둬도 사라진다.

로컬 캐시(Caffeine 같은 프로세스 내 캐시)에도 같은 문제가 있나요? 추가

역직렬화 문제는 없다. 왜 없는지를 설명하는 것이 이 문항의 요지다.

로컬 캐시는 객체를 바이트로 펼치지 않고 힙에 그대로 들고 있다. 그리고 그 힙은 애플리케이션 프로세스와 생사를 같이한다. 배포로 프로세스가 교체되면 캐시도 함께 사라지므로 "옛 구조 데이터를 새 코드가 만나는" 상황 자체가 성립하지 않는다. 캐시가 코드와 함께 배포되는 셈이다.

다만 문제가 사라지는 게 아니라 다른 문제로 바뀐다.

  • 인스턴스마다 값이 다르다. 무효화가 특정 인스턴스에만 반영되면 어느 서버로 붙었느냐에 따라 다른 값이 보인다.
  • 배포마다 전부 cold start다 — 모든 인스턴스의 캐시가 동시에 비므로 그 순간 부하가 뒤로 밀린다.
  • §3의 조건 누락 사고는 그대로 있다. 키에 테넌트를 빠뜨리면 로컬 캐시에서도 똑같이 남의 데이터를 받는다. 직렬화와 무관한, 순수한 키 설계 문제이기 때문이다.

정리하면 "§6~§11(버저닝)은 원격 캐시의 문제, §1~§5(키 설계)는 캐시 종류와 무관한 문제"로 갈라 말할 수 있으면 이해도가 드러난다.

버전을 키 세그먼트에 넣는 것과 캐시 이름(cacheNames)을 바꾸는 것은 뭐가 다른가요? 추가

Redis 입장에서 얻는 효과는 같다 — 둘 다 "새 키 공간에서 시작"이다. cacheNames가 키 앞부분에 붙으므로 product → product2로 바꿔도 옛 키와 겹치지 않는다. 차이는 운영 지점에 있다.

  • 캐시 이름을 바꾸면 그 이름에 걸어 둔 설정이 따라오지 않는다. TTL, 직렬화기, 통계 같은 캐시 이름 단위 설정을 새 이름에도 다시 걸어야 하고, 빠뜨리면 조용히 기본값으로 동작한다.
  • 모니터링과 운영 스크립트가 깨진다. 대시보드·알람·삭제 스크립트가 옛 이름을 가리킨 채 남는다. 버전 세그먼트는 이름을 유지하므로 product:* 기준의 집계가 그대로 살아 있고, product:v1:*만 따로 지목할 수도 있다.
  • 의미가 다르다. 캐시 이름은 "무슨 데이터인가"이고 버전은 "어떤 구조인가"다. 서로 다른 축을 한 문자열에 뭉치면 1년 뒤 product2가 왜 2인지 아무도 모른다.

그래서 실무 권장은 이름은 의미로 고정하고 버전은 별도 세그먼트로 분리하는 쪽이다. "효과가 같아 보이는 두 방법 중 하나를 고르는 근거를 운영 관점에서 대는 것"이 이 문항의 채점 포인트다.

한 줄 요약
캐시 키는 계층적 네임스페이스에 "결과를 가르는 조건 전부 + 버전"을 담는 계약서다 — 조건이 빠지면 먼저 채운 사람의 결과를 다른 조건의 사람이 받아가 남의 데이터가 화면에 뜨고, 버전이 없으면 구조 변경 배포 순간 구버전 데이터의 역직렬화 실패가 캐시 미스로 강등되지 않고 500으로 터져 "배포 직후에만, 히트일 때만, 롤백해도 안 낫는" 장애가 되므로, 키 버저닝으로 신구 코드가 각자의 키 공간을 쓰게 하고 구데이터는 TTL로 자연 소멸시키되 그 기간 동안의 이중 메모리를 대가로 인정하는 것이 캐시를 배포와 함께 움직이는 계약으로 다루는 방법이다.
