05 · Redis / 캐싱 — 캐시 도입 판단

캐시 도입 판단 기준 — 캐시는 "정합성 완화"라는 비용을 지불하는 결정이다

원본: interview-questions/knowledge/05-redis-caching/03-cache-suitability-criteria.md

Q. "캐시를 도입하면 좋은 데이터와 도입하면 안 되는 데이터의 기준은?"
핵심 관전 포인트 — 면접 첫 답변으로 이 네 덩어리를 그대로 말한다
① 프레임 — 캐시는 거래다 캐시는 원본의 사본이고, 사본은 원본이 바뀌는 순간부터 낡는다. 그래서 캐시 도입은 언제나 "응답 속도와 DB 부하 경감을 얻는 대신, 사용자가 낡은 값을 보는 시간 창과 무효화 로직의 복잡도를 지불하는" 거래다.
② 좋은 후보 — 네 조건 ⓵ 읽기가 쓰기보다 압도적으로 많고 ⓶ 자주 바뀌지 않으며 ⓷ 잠깐 낡은 값이어도 비즈니스가 허용하고 ⓸ 원본 조회·계산 비용이 비싼 데이터.
③ 금지 — 낡음이 곧 사고인 데이터 계좌 잔액·재고 차감 판단·권한처럼 낡은 값이 곧 돈이나 보안 사고가 되는 데이터는 캐시하면 안 된다.
④ 진짜 기준 — 데이터가 아니라 "읽기의 용도" 시니어 변별 같은 잔액이라도 마이페이지에 보여 주는 조회는 3초 낡아도 화면이 잠깐 옛날 금액이었을 뿐이지만, 출금 가능 여부를 판단하는 조회는 3초 낡은 값 하나가 이중 출금이라는 되돌릴 수 없는 결과를 만든다. 즉 "이 값이 몇 초 낡아도 되는가"를 비즈니스에 물어보고, 그 답을 read path별로 따로 받는 것이 캐시 도입 결정의 본질이다.
  • 0질문 + 출제 의도
  • 1캐시가 하는 거래
  • 2좋은 후보 네 조건
  • 3캐시 금지 네 종류
  • 4진짜 기준은 read path
  • 5도입 전 체크리스트 6
  • 6셀프 테스트
  • ★한 줄 요약

0. 질문 + 출제 의도

출제 의도 캐시 도입은 "정합성 완화"라는 비용을 지불하는 결정이다. 잔액을 캐시하면 안 되는 이유를 즉답 못 하는 사람에게 결제 시스템을 맡길 수 없다 — 성능 개선 수단을 아는지가 아니라, 그 수단의 대가를 알고 트레이드오프를 판단할 수 있는지를 보는 질문이다.
채점 ⑴ 프레임

"빨라진다"가 아니라 "무엇을 팔아서 무엇을 사는가"로 시작하는가.

채점 ⑵ 금지 근거

잔액을 캐시하면 안 되는 이유를 이중 출금이라는 구체적 사고로 즉답하는가.

채점 ⑶ 한 걸음 더

"잔액은 금지"에서 멈추지 않고 read path별 판단까지 가는가.

이 페이지를 관통하는 비유 — 은행 창구의 환율 전광판

전광판(캐시)은 5분마다 갱신된다. 지나가며 구경하는 사람에게 5분 전 환율은 아무 문제가 없다. 하지만 실제 환전 계약 금액은 전광판이 아니라 그 순간의 딜링룸 시세(DB)로 체결한다.

전광판을 없애면 창구 직원이 매번 시세를 물어보느라 줄이 늘어선다(DB 부하). 전광판으로 계약을 체결하면 손실이 난다(이중 출금). 같은 숫자여도 "보여 주기"와 "체결하기"의 정답이 다르다 — 이 페이지의 결론(§4)이 이 비유 안에 전부 들어 있다.

1. 캐시가 하는 거래 — 성능을 사고, 정합성을 판다

1-1. 먼저 장면부터 — "낡은 값"은 구체적으로 어떤 사고가 되는가

"정합성 완화"라는 말은 추상적이다. 실제로 무슨 일이 벌어지는지부터 보자. 상품 상세 조회 결과를 Redis에 300초 TTL로 캐시하는, 아주 평범한 구조를 가정한다.

버그를 낸 코드는 한 줄도 없다. 캐시는 시킨 대로 300초를 살았고, DB는 정확한 값을 들고 있었다. 그저 두 곳의 값이 180초 동안 달랐을 뿐이다.
암기 — 용어 하나로 고정

staleness(낡음) = 캐시에 담긴 사본이 원본과 달라져 있는 상태, 그리고 그 상태가 지속되는 시간

"얼마나 낡았는가"는 곧 "원본이 바뀐 뒤 캐시가 그것을 따라잡을 때까지의 시간 창"이다. 그래서 캐시 도입 판단이란 결국 "이 데이터에 그 시간 창이 열려도 되는가"를 묻는 일이다.

1-2. 왜 그 창을 0으로 만들 수 없는가

낡은 값을 줄이는 수단은 두 가지다. 둘 다 창을 좁힐 수는 있어도 없앨 수는 없다.

수단 ① TTL (Time To Live)

캐시에 값을 넣을 때 함께 정하는 수명이다. 그 시간이 지나면 값이 자동으로 사라지고, 다음 조회는 캐시에 없으므로 원본에서 다시 읽어 채운다.

TTL 300초 = 최악의 경우 300초 동안 낡은 값을 보여 준다는 뜻. 5초로 줄이면 창은 5초로 좁아지지만 원본 조회가 60배 늘어난다.

수단 ② 무효화 (invalidate / evict)

원본이 바뀌는 시점에 우리가 캐시 키를 명시적으로 지우거나 새 값으로 덮어쓰는 것이다. 가격 수정 트랜잭션이 커밋된 직후 product:1234를 지우면 된다.

TTL 만료를 기다리지 않으므로 창이 훨씬 짧아진다. 하지만 0은 되지 않는다 — 아래 그림이 그 이유다.

용어 주의 — 같은 "eviction"이지만 주체와 이유가 다르다 Redis가 maxmemory에 도달했을 때 Redis가 알아서 키를 지우는 것도 eviction이라고 부른다. 여기서 말하는 무효화는 우리가 의도적으로 지우는 것이고, 그쪽은 메모리가 부족해 Redis가 마음대로 지우는 것이다.
캐시를 붙인 순간부터 "낡은 값을 보는 사용자가 존재한다"는 것은 버그가 아니라 설계의 일부가 된다.
이 손잡이의 눈금을 정하는 사람은 개발자가 아니라 비즈니스다 — "몇 초까지 낡아도 되나요?"를 묻고 숫자로 받아 오는 것이 캐시 설계의 첫 단계다.

1-3. 거래 명세서

항목구체적으로
얻는 것응답 속도메모리 조회는 디스크 접근과 쿼리 파싱·실행을 거치는 원본 조회보다 수십에서 수백 배 빠르다
얻는 것DB 부하 감소읽기 트래픽을 캐시가 흡수해 DB의 커넥션과 CPU에 여유가 생긴다
잃는 것정합성사용자가 낡은 값을 보는 시간 창이 열린다 (§1-2의 이유로 0이 될 수 없다)
잃는 것복잡도무효화 로직, 캐시 장애 시나리오, 모니터링 대상이 하나씩 늘어난다
면접 첫 문장으로 그대로

"캐시 붙이면 빨라지니까 좋다"가 아니라 "이 데이터는 낡아도 되는가?"를 먼저 묻는 것이 올바른 순서다.

이 프레임(비용을 지불하는 결정)을 첫 문장으로 깔면 이후 답변 전체에 설득력이 생긴다.

네 가지를 동시에 만족할수록 캐시 효과가 크다. 하나만 만족하는 데이터는 대개 캐시해도 본전이거나 손해다. 그리고 ③ '늦'만은 거부권을 가진다 — ①②④가 아무리 좋아도 ③이 아니면 캐시는 금지다(§3).

①

읽기가 쓰기보다 압도적으로 많다

먼저 용어부터. 조회 요청이 캐시에서 곧바로 답을 얻으면 히트(hit), 캐시에 없어서 원본까지 다녀오면 미스(miss)다. 히트율(hit rate)은 전체 조회 요청 중 히트의 비율이다.

캐시의 이득은 오직 히트에서 나온다. 반대로 쓰기는 매번 무효화나 갱신 비용을 낸다. 읽기 100 대 쓰기 1이면 캐시를 한 번 채워 100번 우려먹지만, 읽기 1 대 쓰기 1이면 채우자마자 지우는 헛수고를 반복하게 된다.

②

변경이 드물다

카테고리 트리, 공통 코드, 정책·설정값처럼 하루에 몇 번 바뀌지 않는 데이터는 TTL을 길게 줘도 안전하다. 변경 빈도가 낮다는 것은 곧 "낡아 있는 시간의 비율"이 낮다는 뜻이기 때문이다.

반대로 초 단위로 바뀌는 값은 TTL이 아무리 짧아도 낡아 있는 비율이 높다. 1초마다 바뀌는 값에 TTL 5초를 걸면 캐시된 값은 수명의 80퍼센트를 틀린 상태로 보낸다.

③

잠깐 낡아도 비즈니스가 허용한다 (staleness 허용) 가장 중요

앞의 두 기준은 성능 계산이지만, 이것은 사고 여부를 가르는 기준이다. 그래서 이 조건만 거부권을 가진다.

"인기 웹툰 목록이 30초 전 기준이어도 되는가?" → 된다.   "출금 가능 잔액이 30초 전 기준이어도 되는가?" → 안 된다. 이중 출금이 난다.

주목할 점은 이 질문의 답이 기술이 아니라 비즈니스 요구사항에서 나온다는 것이다. 캐시 TTL을 정하는 일은 사실 성능 튜닝이 아니라 기획·도메인과의 협상이다.

④

원본 조회 / 계산이 비싸다

5개 테이블을 조인하고 집계하는 대시보드 통계, 외부 API를 호출해 받아 오는 결과처럼 한 번 만드는 데 비싼 값일수록 캐시 한 번의 이득이 크다.

반대로 PK 단건 조회처럼 이미 인덱스로 밀리초 안에 끝나는 쿼리는 캐시를 붙여도 체감 이득이 작다. 게다가 미스가 나면 캐시 조회 + DB 조회 + 캐시 적재로 왕복이 오히려 늘어난다(§3-③에서 숫자로 확인).

가로축(①②)과 세로축(③)은 성격이 다르다. 가로축은 "얼마나 이득인가", 세로축은 "해도 되는가"다. 아래쪽 붉은 띠에 들어가면 오른쪽 끝에 있어도 캐시하지 않는다.
전형적인 좋은 후보 — 공통점 한 문장으로 인기 콘텐츠 목록 · 카테고리/메뉴 트리 · 상품 상세(설명·이미지 URL) · 공통 코드 · 화면 표시용 환율 · 집계성 통계. 전부 "많이 읽히고, 덜 바뀌고, 잠깐 낡아도 화면 문제로 끝나고, 만들기 비싼" 데이터다.

3-①. 낡은 값이 곧 돈 사고 — 잔액, 포인트, 재고 "차감 판단"

캐시된 잔액으로 출금 가능 여부를 판단하면 어떻게 되는지, 두 요청을 나란히 놓고 보자. 전제는 잔액 캐시 TTL 60초, 현재 캐시와 DB 모두 10,000원이다.

암기 — 비가역적 결정 (irreversible decision)

출금 승인 · 재고 차감 · 쿠폰 발급처럼, 한 번 실행되면 취소가 아니라 반대 방향의 보상 거래(환급, 재고 복구, 쿠폰 회수)로만 수습할 수 있는 결정.

그 보상마저 실패하면 사람이 개입해야 한다. 낡은 값이 화면에 잠깐 남는 것과, 낡은 값이 돈을 움직이는 것은 사고의 등급이 다르다. 그래서 이런 판단은 반드시 원본(DB)에서, 그것도 조건부 연산으로 해야 한다.

before — 미리 읽어둔 값으로 판단한다
Long balance = cache.get("balance:" + userId);
// ↑ 낡은 값일 수 있다
if (balance >= amount) {
    accountRepository.withdraw(userId, amount);
}

// 캐시를 안 쓰고 DB에서 SELECT 했더라도
// 문제는 남는다. 판단(if)과 차감(withdraw)
// 사이에도 시간이 벌어져 있어서,
// 그 틈에 다른 요청이 같은 판단을
// 통과할 수 있기 때문이다.

// UPDATE account
//    SET balance = balance - :amount

//    AND balance >= :amount   ← 조건이 UPDATE 안으로

int updated =
    accountRepository.withdrawIfEnough(userId, amount);

if (updated == 0) {
    // 갱신된 행이 0건 = 조건 불만족 = 잔액 부족
    throw new InsufficientBalanceException();
}
after가 왜 안전한가 — 락과 재평가 PostgreSQL에서 이 UPDATE는 대상 행에 락을 잡는다. 동시에 들어온 두 번째 트랜잭션은 첫 번째가 커밋될 때까지 기다렸다가 "갱신된 최신 행"으로 조건을 다시 평가한다. 그래서 잔액이 모자라면 조건에 걸려 0행이 갱신된다 — 두 요청이 나란히 통과할 수 없다.

3-②. 즉시 회수가 요구되는 보안 데이터 — 권한, 세션 차단 상태

퇴사자 계정을 차단했는데 권한 캐시 TTL이 10분이라면, 차단 후 10분 동안 그 계정은 살아 있다. 시스템은 정상 동작 중이고 로그에도 이상이 없다. 단지 낡은 권한 정보로 통과시켰을 뿐이다.

한 줄로 고정

TTL은 "최악의 경우 이만큼은 낡아 있다"는 상한선이지, 반영 수단이 아니다.

"권한 변경은 즉시 반영"이 보안 요구사항이라면 캐시하지 않거나, 캐시하더라도 변경 이벤트로 즉시 무효화하는 경로를 반드시 함께 깔아야 한다. TTL만 믿으면 안 된다.

3-③. 히트율이 안 나오는 데이터 — 개인화 · 롱테일

캐시의 이득은 같은 키가 반복 조회될 때 나온다. 한 번 채운 값을 여러 번 우려먹어야 이득인데, 그 전제가 깨지는 데이터가 있다. 하나는 사용자마다 결과가 다른 개인화 데이터다. 사용자가 100만 명이면 키도 100만 개이고, 각 키는 그 사용자만 조회한다.

다른 하나는 롱테일(long tail) 데이터다. 롱테일은 소수의 인기 항목이 대부분의 조회를 가져가는 분포가 아니라, 아주 많은 항목이 각각 아주 드물게 조회되는 분포를 말한다. 조회수를 내림차순으로 그래프에 그리면 앞쪽 봉우리 뒤로 낮은 꼬리가 길게 이어지는 모양이라 붙은 이름이다.

롱테일을 캐시하면 매 요청이 "캐시 조회(미스) → DB 조회 → 캐시 적재"가 되어 캐시가 없을 때보다 오히려 느려지고, 적재된 값은 다시 안 읽히면서 메모리만 차지해 정작 인기 키를 밀어낸다(eviction).

숫자로 확인 — 히트율이 낮으면 정말로 손해인가

[가정] 캐시 왕복 0.2ms · DB 조회 5ms · 캐시 적재 0.2ms

캐시 없음          : 5ms                      (DB 조회 한 번)
히트일 때          : 0.2ms
미스일 때          : 0.2 + 5 + 0.2 = 5.4ms    (왕복이 오히려 늘어난다)

히트율 p일 때 평균 = 0.2p + 5.4(1 - p) = 5.4 - 5.2p

  p = 0.9  ->  5.4 - 4.68 = 0.72ms   (캐시 없을 때의 약 1/7)
  p = 0.5  ->  5.4 - 2.60 = 2.80ms
  p = 0.1  ->  5.4 - 0.52 = 4.88ms   (5ms와 거의 차이 없다)

손익분기: 5.4 - 5.2p = 5  ->  p = 0.4 / 5.2 = 약 7.7%
그래서 히트율이 낮은 캐시는 "손해는 아니지만 비용만 내는 구조물"이 된다. 실무 기준선은 이 8%보다 훨씬 높다.

3-④. 쓰기가 잦은 데이터

변경 때마다 무효화가 따라붙으므로 히트율은 낮아지고, 캐시와 DB를 함께 바꾸는 지점이 많아질수록 순서가 뒤집히는 등 정합성이 깨질 기회만 늘어난다. 읽기 대 쓰기 비율이 낮으면 캐시 후보에서 뺀다.

4. 진짜 기준은 "데이터 종류"가 아니라 "읽기의 용도" 시니어 변별

여기서 변별이 갈린다. "잔액은 캐시하면 안 된다"에서 멈추지 말고 한 걸음 더 들어가야 한다. 같은 데이터, 같은 낡음(3초)을 두 개의 읽기 경로에 각각 넣어 보자.

공통 전제 잔액 캐시 TTL 60초. t=0에 DB 잔액이 10,000원 → 0원으로 바뀌었고, 캐시에는 아직 10,000원이 남아 있다. 지금은 t=3.
경로 A — 잔액을 "보여 주는" 조회
  • t=3 마이페이지 화면에 10,000원이 표시된다.
  • t=5 무효화가 반영되거나 사용자가 새로고침하면 0원으로 바뀐다.
  • 결과 사용자가 잠깐 옛 금액을 봤다. 불쾌할 수는 있지만 시스템 상태는 아무것도 바뀌지 않았다. 되돌릴 것이 없다.
VS
경로 B — 출금 가능 여부를 "판단하는" 조회
  • t=3 서버가 10,000원을 근거로 "출금 가능" 판정을 내린다.
  • t=3 출금이 실행된다.
  • 결과 DB 잔액이 −10,000원이 됐다. 돈이 이미 나갔다. 수습하려면 환급이라는 새 거래가 필요하고, 그 환급도 실패할 수 있다.
이 페이지의 결론 — 그대로 인출한다

캐시 가능 여부는 "잔액이라는 데이터"에 붙는 성질이 아니라 읽기 경로(read path)에 붙는 성질이다.

경로 A에서 낡은 값은 화면에 잠깐 머물다 사라지는 정보이고, 경로 B에서 낡은 값은 되돌릴 수 없는 부작용을 만드는 근거다. 같은 값, 같은 3초인데 결과가 완전히 다르다 — 차이를 만든 것은 데이터가 아니라 "그 값을 근거로 무엇을 했는가"다.

4-1. 그래서 경로를 분리한다

경로를 분리하면 "잔액 조회 트래픽 때문에 DB가 힘든데 캐시는 못 쓰는" 딜레마가 풀린다. 트래픽의 대부분은 표시용 조회이고, 판단용 조회는 실제 결제 시도에만 발생하므로 양이 훨씬 적다.
가능 표시용 읽기

마이페이지에 잔액 보여 주기. 몇 초 낡아도 사용자 경험 문제일 뿐 사고가 아니다.

짧은 TTL(수 초) 캐시 + 변경 시 무효화로 캐시 가능.

불가 판단용 읽기

출금 승인 여부 결정. 낡은 값이 곧 이중 출금이다.

캐시 불가이고, DB가 조건부 연산으로 최종 판단을 내려야 한다.

재고도 정확히 같은 구조다 상품 목록에 "품절 임박" 배지를 띄우는 것은 캐시로 해도 된다 — 실제 재고가 3개인데 배지가 5개 기준으로 잠깐 늦게 뜬 것은 사고가 아니다. 반면 주문 시점의 재고 차감 판단은 DB의 조건부 UPDATE나 Redis 원자 연산으로 해야 한다.
가산점 포인트 — 이 문장을 명시적으로 말한다

"캐시 가능 여부는 데이터가 아니라 read path별로 판단합니다."

이렇게 말하는 순간, 면접관에게는 이 관점을 갖고 있다는 신호가 된다.

4-2. 표시용 캐시의 무효화는 "커밋 후"여야 한다 보강

경로 A를 캐시로 돌리기로 했다면, 남은 일은 잔액 변경 시 무효화다. 여기서 흔한 실수가 하나 있다 — 트랜잭션 안에서 캐시를 지우는 것이다.

before — 커밋 전에 지운다
@Transactional
public void withdraw(Long userId, long amount) {
    accountRepository.withdrawIfEnough(userId, amount);
    redis.delete("balance:" + userId);  // 아직 커밋 전
}

// 문제 ① 지운 직후 ~ 커밋 사이에 다른 요청이
//        조회하면, 아직 커밋 안 된 "옛 잔액"을
//        DB에서 읽어 캐시에 다시 채운다.
//        -> 낡은 값이 TTL 만료까지 눌러앉는다.
// 문제 ② 이후 롤백되면 멀쩡한 캐시만 날린 셈이다.
after — 커밋이 끝난 뒤에 지운다
@Transactional
public void withdraw(Long userId, long amount) {
    accountRepository.withdrawIfEnough(userId, amount);
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override public void afterCommit() {
                redis.delete("balance:" + userId);
            }
        });
}

// (Spring 이벤트를 쓴다면
//  @TransactionalEventListener(phase = AFTER_COMMIT)도
//  같은 타이밍을 보장한다)
그래도 남는 것 — §1-2로 돌아간다 afterCommit과 delete 사이의 수 밀리초는 여전히 남고, delete 자체가 실패할 수도 있다. 그래서 짧은 TTL을 안전망으로 겹쳐 둔다. 무효화는 창을 좁히는 수단이고, TTL은 그 수단이 실패했을 때의 피해 상한이다.

5. 도입 전 체크리스트 — 여섯 개를 순서대로 묻는다

암기 문장 — 여섯 항목을 한 줄로 꿴다

"읽고 · 낡아도 되면 · 값비싼 것을 골라 · 히트율을 보고 · 무효화 길을 깔고 · 죽을 때를 대비한다"

읽기비율 → staleness → 원본비용 → 히트율 → 무효화 경로 → 캐시 장애. 마지막 하나가 운영 감각 가산점이다.

  1. 읽기 대 쓰기 비율 — 읽기가 압도적인가. 아니면 채우자마자 지우는 구조인가.
  2. 허용 staleness — 몇 초 낡아도 되는지 비즈니스와 숫자로 합의했는가. (기술로 정하는 값이 아니다)
  3. 원본 비용 — 캐시 한 번으로 아끼는 것이 큰가. 비싼 조인·집계·외부 호출인가, 아니면 PK 단건 조회인가.
  4. 예상 히트율 — 같은 키가 반복 조회되는 분포인가, 롱테일인가. 그리고 도입 후 실제 히트율을 볼 지표가 있는가.
  5. 무효화 경로 — 변경 지점이 한 곳인가. 배치나 어드민, 다른 서비스가 DB를 직접 고치는 경로는 없는가.
  6. 캐시 장애 시나리오 — 캐시가 죽으면 DB가 그 트래픽을 버티는가. 운영 감각
그래서 캐시는 "있으면 빨라지는 것"이 아니라 "없으면 무너지는 의존성"이 되어 있는지를 도입 전에 확인해야 한다.

6. 셀프 테스트 — 먼저 답해 보고 펼친다

질문만 읽고 소리 내어 답해 본 뒤 펼쳐서 확인한다. 막히면 해당 절로 돌아간다.

Q1. "잔액 조회 트래픽이 너무 많아서 DB가 힘들면 그래도 캐시 못 쓰나요?" 시니어 변별

쓸 수 있다 — 단, 용도를 분리해서다.

  1. 표시용 조회는 짧은 TTL 캐시 + 잔액 변경 트랜잭션 커밋 후 즉시 무효화로 흡수한다. 이쪽이 트래픽의 대부분이다.
  2. 출금·결제 판단은 반드시 DB의 조건부 UPDATE(원자적 판단 + 차감)로 남긴다.

여기서 한 걸음 더 나가면 상급이다. 판단 트래픽 자체가 병목이라면 캐시가 아니라 Redis 원자 연산(DECRBY + Lua 스크립트)으로 판단 자체를 Redis로 옮기는 설계를 검토한다. 선착순 쿠폰과 같은 계열이다.

다만 이것은 "캐시"가 아니라 "판단 저장소의 이전"이다. 사본을 두는 것이 아니라 그 값의 주인을 옮기는 것이므로 정합성 책임도 함께 옮겨간다 — Redis가 유실되면 판단 근거가 사라지므로 영속화, 복구, DB와의 대사(對査) 설계가 따라붙는다. 이 구분을 명확히 말하면 캐시와 저장소의 경계를 이해하고 있다는 신호가 된다.

Q2. "쓰기가 많은 데이터를 캐시하면 구체적으로 무슨 일이 벌어지나요?"

세 가지가 동시에 일어난다.

  1. 히트율이 떨어진다. 변경 때마다 무효화가 따라붙으니 채우자마자 지우는 일이 반복된다. 캐시를 유지하는 비용은 그대로인데 우려먹는 횟수가 없다.
  2. 정합성이 깨질 기회가 늘어난다. 캐시와 DB를 함께 바꾸는 지점이 많아질수록 순서가 뒤집힐 확률이 올라간다. 대표적으로 "A가 DB를 읽고 → B가 DB를 쓰고 캐시를 지우고 → A가 자기가 읽은 낡은 값을 캐시에 적재"하면 낡은 값이 TTL 만료까지 눌러앉는다.
  3. 결과적으로 이득 없이 비용만 낸다. 무효화 로직, 정합성 리스크, 캐시 왕복이 전부 지출인데 히트라는 수입이 없는 구조다.
Q3. "히트율이 낮으면 캐시가 왜 '없느니만 못한' 게 되나요?"

미스 경로는 "캐시 조회 → 미스 → DB 조회 → 캐시 적재"라서, 캐시가 없을 때(DB 조회 한 번)보다 네트워크 왕복이 2~3배다.

히트율이 낮으면 대부분의 요청이 이 비싼 경로를 타고, 적재된 데이터는 다시 안 읽혀 메모리만 차지하며 인기 키를 밀어낸다. §3-③의 계산처럼 지연만 따지면 손익분기가 약 7.7%로 낮게 나오지만, 거기에 메모리 비용 · 무효화 복잡도 · 캐시라는 새 장애 지점을 더하면 실질 기준선은 훨씬 높아진다.

그래서 캐시 도입 후에는 히트율 모니터링이 필수다. 히트율이 안 나오면 캐시를 빼는 것도 결정이다 — 한 번 넣은 캐시를 성역으로 두지 않는 태도까지 말하면 좋다.

Q4. "권한 정보를 캐시했는데 '차단 즉시 반영' 요건이 생기면 어떻게 하나요?"

TTL만으로는 못 지킨다. TTL 동안은 차단된 계정이 살아 있기 때문이다.

  1. 권한 변경 시 해당 키를 즉시 무효화하는 이벤트 경로를 깐다. 같은 서비스 안이면 트랜잭션 커밋 후 evict, 다른 서비스에 캐시가 있으면 pub/sub이나 메시지로 무효화를 전파한다.
  2. 무효화 유실에 대비해 짧은 TTL을 안전망으로 겹친다. 무효화 메시지가 유실되거나 컨슈머가 죽어 있었을 때 최대 피해 시간을 TTL로 상한 지어 두는 것이다.

그래도 전파 지연 수 초는 남는다. 그래서 마지막 단계는 기술이 아니다. "즉시"의 허용 오차(수 초인가 0초인가)를 보안팀과 합의하는 것까지가 설계다. 진짜 0초가 요구된다면 캐시를 포기하는 것이 답이다.

Q5. "캐시 도입 전에 확인할 것을 체크리스트로 말해보세요"

여섯 개. 읽고 · 낡아도 되면 · 값비싼 것 · 히트율 · 무효화 길 · 죽을 때

  1. 읽기 대 쓰기 비율 — 읽기가 압도적인가.
  2. 허용 staleness — 몇 초 낡아도 되는지 비즈니스와 숫자로 합의했는가.
  3. 원본 비용 — 캐시 한 번으로 아끼는 것이 큰가(비싼 조인·집계·외부 호출인가).
  4. 예상 히트율 — 같은 키가 반복 조회되는 분포인가, 롱테일인가.
  5. 무효화 경로 — 변경 지점이 한 곳인가. 배치나 어드민, 다른 서비스가 DB를 직접 고치는 경로는 없는가.
  6. 캐시 장애 시나리오 — 캐시가 죽으면 DB가 그 트래픽을 버티는가.

⑥까지 말하면 운영 감각 가산점이다. 평소 히트율 95%로 DB가 편안했다면 캐시가 죽는 순간 DB가 받는 읽기는 20배가 된다(§5 그림). 캐시는 "있으면 빨라지는 것"이 아니라 "없으면 무너지는 의존성"이 되어 있는지를 도입 전에 확인해야 한다.

Q6. TTL을 1초로 아주 짧게 주면 잔액도 출금 판단에 써도 되지 않나요? 추가

안 된다. 이유가 두 겹이다.

  1. 기준은 창의 길이가 아니라 그 창에 걸린 결과의 성격이다. 1초든 3초든 이중 출금은 똑같이 성립한다(§3-① 시퀀스에서 t=0과 t=3의 간격을 1초로 줄여도 그림은 그대로다). 낡은 값이 비가역적 결정의 근거가 되는 순간, 창의 길이는 사고 확률만 줄일 뿐 사고 자체를 막지 못한다.
  2. 이득도 거의 사라진다. TTL을 1초로 줄이면 그만큼 미스가 잦아져 히트율이 떨어지고, 캐시가 흡수해 주는 DB 부하도 함께 줄어든다. "위험은 그대로 남고 이득만 줄어드는" 최악의 조합이다.

정답은 TTL을 줄이는 것이 아니라 경로를 나누는 것이다 — 표시용은 캐시, 판단용은 DB의 조건부 UPDATE(§4).

Q7. 무효화를 확실히 하려면 DB 트랜잭션 안에서 캐시를 지우면 되지 않나요? 추가

오히려 더 나쁘다. 두 가지가 생긴다.

  • 낡은 값을 다시 심는다. 캐시를 지운 시점부터 커밋 전까지, 다른 요청이 조회하면 아직 커밋되지 않은 옛 값을 DB에서 읽어 캐시에 채운다. 그 값은 TTL 만료까지 눌러앉는다 — 지우기 전보다 상황이 나빠졌다.
  • 롤백되면 헛일이다. 트랜잭션이 롤백돼도 캐시는 이미 지워졌으니, 멀쩡한 캐시만 날리고 미스를 유발한 셈이 된다.

그래서 무효화는 커밋이 끝난 뒤여야 한다(§4-2의 afterCommit). 그리고 커밋과 evict 사이의 틈은 없앨 수 없으므로 짧은 TTL을 안전망으로 겹친다(§1-2).

Q8. 히트율이 높으면 좋은 캐시라고 봐도 되나요? 추가

아니다. 히트율은 성능 지표이지 정합성 지표가 아니다.

  • 히트율 99%여도 그 값이 비가역 판단의 근거로 쓰이고 있다면 그것은 훌륭한 캐시가 아니라 대기 중인 사고다(조건 ③ 위반).
  • 히트율이 높은 이유가 TTL을 요구사항보다 길게 잡았기 때문일 수도 있다. 히트율은 올라가지만 그만큼 사용자가 낡은 값을 오래 본다.

그래서 캐시는 항상 두 지표를 같이 봐야 한다 — 히트율(이득이 나오는가)과 허용 staleness 준수(비용이 계약 범위 안인가).

Q9. 그럼 캐시 대신 읽기 전용 복제본(read replica)으로 보내면 되지 않나요? 추가 시니어 변별

읽기 부하 분산에는 좋은 수단이지만, 이 문항의 판단 기준은 그대로 적용된다. 복제본은 원본을 따라오는 데 시간이 걸리고(복제 지연), 그 지연은 staleness의 또 다른 형태이기 때문이다.

  • 표시용 읽기 → 복제본으로 보내도 된다. 캐시와 같은 이유로 괜찮다.
  • 판단용 읽기 → 복제본으로 보내면 캐시로 판단한 것과 똑같은 이중 출금이 난다. 복제 지연이 0이라는 보장이 없기 때문이다.

즉 "Redis냐 복제본이냐"는 수단의 차이일 뿐, "사본으로 비가역 결정을 내리지 않는다"는 원칙은 동일하다. 이 문항의 결론이 Redis에만 해당하는 이야기가 아니라는 것까지 말하면 이해의 폭을 보여 준다.

Q10. 표시용 잔액을 캐시했더니 "출금했는데 마이페이지 잔액이 그대로"라는 CS가 들어옵니다. 추가

표시용 캐시가 허용하는 staleness에도 예외 구간이 하나 있다는 신호다 — 자기가 방금 만든 변경은 자기 눈에 바로 보여야 한다(read-your-writes).

남이 바꾼 값이 3초 늦게 보이는 것은 아무도 눈치채지 못하지만, 내가 방금 누른 출금 버튼의 결과가 안 보이면 사용자는 즉시 "고장"으로 인식하고 한 번 더 누른다. 이건 UX 문제를 넘어 중복 요청까지 부른다.

대응은 세 가지다.

  1. 변경 트랜잭션 커밋 직후 그 사용자 키를 무효화한다(§4-2). 대부분은 여기서 해결된다.
  2. 변경 직후의 화면 한 번은 캐시를 우회해 원본에서 읽는다(본인 요청에 한정).
  3. 애초에 변경 결과 화면은 변경 응답이 돌려준 값으로 그린다 — 다시 조회하지 않는 것이 가장 확실하다.

핵심은 "허용 staleness는 전역 상수가 아니라 상황별 값"이라는 것이다. 같은 표시용 경로라도 남의 변경과 내 변경에 대한 허용치가 다르다.

한 줄 요약
캐시 도입은 "속도를 사고 정합성을 파는 거래"라서 — 읽기가 압도적이고 변경이 드물며 낡아도 되는 비싼 데이터에는 이득이고, 잔액·재고 차감·권한처럼 낡은 값이 곧 사고인 데이터에는 금지이며, 진짜 판단 기준은 데이터 종류가 아니라 읽기의 용도 (표시용은 캐시, 비가역 판단용은 DB가 최종 심판)라는 것까지 말해야 트레이드오프를 아는 답변이 된다.
