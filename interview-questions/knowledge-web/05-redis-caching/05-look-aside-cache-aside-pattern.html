Look-aside(Cache-aside) 패턴 — 애플리케이션이 캐시를 "옆에 두고" 직접 채우는 기본기와 그 빈틈

원본: interview-questions/knowledge/05-redis-caching/05-look-aside-cache-aside-pattern.md

30초 카드 — 흐름 5단계 + 쓰기 규칙 + 빈틈 4개
질문: "Look-aside(Cache-aside) 패턴을 설명해주세요." — 아래 5칸을 순서대로 말하고, 쓰기 한 줄을 붙이고, 빈틈 4개를 예고하면 첫 답변이 끝난다.
① 캐시 조회DB보다 먼저
② 히트 → 반환DB 안 감. 끝
③ 미스 → DB앱이 직접 읽음
④ 캐시 적재TTL 필수
⑤ 값 반환

쓰기는 별도 규칙 — DB에 쓰고(커밋), 캐시는 갱신이 아니라 삭제.

핵심 관전 포인트 — 그대로 말하기
Look-aside는 앱이 ① 캐시를 먼저 조회 → ② 히트면 반환 → ③ 미스면 DB에서 읽어 → ④ 캐시에 적재 후 반환하는 패턴이다. 캐시는 get/set만 받는 수동적 저장소일 뿐이고 적재 책임이 애플리케이션에 있다는 것이 핵심이며, 이 점이 캐시가 스스로 원본을 읽는 read-through, 쓰기까지 캐시가 대신하는 write-through/write-behind와 갈리는 지점이다. 쓰기는 DB에 쓰고 캐시를 삭제하는 조합이 정석이다. 실무 기본값인 이유는 캐시가 통째로 죽어도 모든 읽기가 DB로 흘러 서비스가 살아남고, 무엇을 어떤 키로 얼마나 캐시할지를 조회 경로별로 통제할 수 있기 때문이다 — 대신 이 패턴에는 미스 시 왕복 비용, 동시 미스 폭주(스탬피드), 그리고 읽기가 DB에서 읽은 값을 적재하기 직전에 쓰기가 끼어들어 옛 값이 최종 승자가 되는 경합 창이 구조적으로 내장되어 있다. 이 창은 읽기와 쓰기가 서로를 모르는 별개 경로라 완전히 막을 수 없고, 그래서 TTL은 성능 장치가 아니라 정합성의 최후 안전망이다.
출제 의도 — "흐름을 그리는가"에서 끝나지 않고 "그 흐름의 어디서 문제가 자라는가"까지 본다
기본 패턴의 흐름을 알아야 그 패턴의 빈틈(미스 폭주, 갱신 경합)을 논할 수 있다. 이후 고난이도 질문들(스탬피드 · 캐시-DB 정합성 · 캐시 장애 방어)의 공통 기반이 되는 문항이다. 그래서 이 페이지의 무게중심은 §1~§5(흐름)가 아니라 §6~§9(빈틈 4종), 그중에서도 §8 경합 창에 있다.

1. 패턴 4종 — 갈리는 축은 "그 코드가 어디 사는가" 하나뿐이다

"look-aside가 표준이다"부터 말하면 왜 그것인지가 빠진다. 선택지가 무엇이고 어떤 축으로 갈리는지를 먼저 세운 다음 결론으로 가자.

캐시를 쓰는 코드에는 반드시 있어야 하는 일이 둘 있다. 캐시에 없을 때 원본(DB)을 다녀와 채우는 일, 그리고 원본이 바뀌었을 때 캐시를 맞추는 일이다. 패턴을 나누는 축은 하나다 — 그 일을 하는 코드가 어디에 사는가.

축 하나로 전부 정리된다
그 코드가 애플리케이션 안에 있으면 look-aside,
캐시 계층(라이브러리·미들웨어) 안에 숨어 있으면 read/write-through·write-behind.

이름이 넷이라 복잡해 보이지만 외울 것은 이 한 줄이다. 나머지는 이 축에서 따라 나오는 결과다.

왼쪽 하나만 캐시가 옆에 있고, 오른쪽 셋은 캐시가 요청 경로 위에 있다. 이 그림 하나가 네 패턴의 전부다.
이름이 곧 구조 — 연상법
aside = 옆 → 내가 고개를 돌려 본다 → 내(앱)가 다녀온다
through = 관통 → 요청이 캐시를 뚫고 DB까지 간다 → 캐시가 다녀온다

패턴 이름을 잊어도 이 두 단어의 뜻만 기억하면 구조를 되짚을 수 있다. 면접에서도 "이름의 뜻이 구조를 그대로 말해 줍니다"로 시작하면 정의가 흔들리지 않는다.

패턴원본을 다녀오는 코드의 위치특징대가
Look-aside애플리케이션미스 시 앱이 DB를 읽고 직접 적재미스 왕복·스탬피드·경합 창을 앱이 떠안음
Read-through캐시 계층미스 시 캐시가 등록된 로더로 원본을 읽어 채움캐시가 경로 위에 있어 죽으면 경로가 끊김
Write-through캐시 계층쓰기를 캐시에 하면 캐시가 DB까지 동기 반영쓰기 지연 = 캐시+DB · 안 읽힐 값도 적재
Write-behind캐시 계층캐시에 먼저 쓰고 DB 반영은 비동기(배치·병합)flush 전 노드 장애 시 쓰기 유실

1-1. read-through는 실제로 어떻게 생겼나 — Caffeine CacheLoader

look-aside 코드(§3)와 나란히 놓고 보면 차이가 한눈에 들어온다. 여기엔 미스 분기도, DB 조회도, 적재도 호출부에 없다. 캐시를 만들 때 "이 키가 없으면 이 함수로 값을 만들어라"를 미리 등록해 뒀기 때문이다.

// read-through: 로더를 캐시에 등록해 두면 미스 처리는 캐시가 알아서 한다
LoadingCache<Long, Product> cache = Caffeine.newBuilder()
        .expireAfterWrite(Duration.ofMinutes(5))
        .build(id -> productRepository.findById(id)   // ← 이것이 로더
                .orElseThrow(ProductNotFoundException::new));

// 호출부에는 캐시 조회 한 줄뿐. 미스/DB조회/적재가 전부 캐시 안에 있다.
Product product = cache.get(id);

2. 왜 look-aside가 실무 기본값인가 — 근거 셋

없다
Redis엔 선택지가
Redis는 당신의 DB를 모른다
산다
캐시가 죽어도
캐시는 선택적 최적화 계층
정한다
무엇을 캐시할지 앱이
키·TTL·조건을 경로별로
1
Redis에는 애초에 다른 선택지가 없다 read-through·write-through는 캐시 계층이 DB를 읽고 쓸 줄 알아야 성립한다. 그런데 Redis는 여러분의 DB를 모른다 — 어떤 테이블에서 어떤 조건으로 읽어야 하는지 알려줄 방법 자체가 없다. 그러니 누군가가 채워야 하고, 그 누군가는 애플리케이션이다. Caffeine 같은 인프로세스(같은 JVM 안에서 도는) 캐시는 로더를 자바 함수로 등록할 수 있어 read-through가 되지만, 네트워크 건너편의 Redis에는 그 방법이 없다.
2
캐시가 죽어도 서비스가 산다 look-aside에서 캐시는 선택적 최적화 계층으로 남는다. 캐시 조회가 실패하면 그것은 미스와 같은 상황이고 코드는 DB로 간다. Redis 클러스터가 통째로 내려가도 모든 읽기가 DB로 흘러 기능은 유지된다 — 성능 저하이지 기능 장애가 아니다. read-through에서는 캐시가 요청 경로 위에 있으므로 캐시 계층이 죽으면 그 경로 자체가 끊긴다. 단, 이 장점에는 조건이 붙는다 — DB가 그 트래픽을 버틸 때만이다(§9).
3
무엇을 캐시할지를 애플리케이션이 통제한다 같은 상품 데이터라도 목록 조회에는 요약 형태를, 상세 조회에는 전체 형태를 캐시하고 싶을 수 있다. 로그인 사용자에게만, 결과가 비어 있으면 아주 짧은 TTL만. 키 설계·TTL·캐시 여부를 조회 경로별로 다르게 정하는 자유는 적재 코드가 애플리케이션에 있기 때문에 생긴다.
답변 순서 팁 — 근거 ①이 가장 강하다
"표준이라서"가 아니라 "Redis라는 도구의 성질상 다른 패턴이 성립하지 않는다"로 시작하면 그 뒤 ②·③이 선택의 이유가 아니라 따라오는 이득으로 정리된다. 그리고 ②를 말할 때 스스로 조건("DB가 버틸 때만")을 붙이는 것이 §9로 가는 다리가 된다.

3. 읽기 흐름 5단계 — 그림 그대로 다섯 줄이 된다

③과 ④는 같은 순간이 아니다. 그 사이의 짧은 틈이 이 문서에서 가장 중요한 §8의 무대다.
public Product findProduct(Long id) {
    String key = "product:" + id;

    // ① 캐시 먼저. DB보다 먼저 보는 것이 look-aside의 출발점이다.
    Product cached = redisTemplate.opsForValue().get(key);
    if (cached != null) {
        return cached;                                       // ② 히트 → 즉시 반환
    }

    // ③ 미스 → 원본으로. 이 코드가 애플리케이션에 있다는 것이
    //    look-aside를 read-through와 가르는 지점이다.
    Product product = productRepository.findById(id)
            .orElseThrow(ProductNotFoundException::new);

    // ④ 적재. TTL을 반드시 함께 준다 — §8의 경합으로 옛 값이 들어갔을 때
    //    그 낡음을 끝내주는 유일한 장치가 TTL이기 때문이다.
    redisTemplate.opsForValue()
            .set(key, product, Duration.ofMinutes(5));
    return product;                                          // ⑤ 반환
}
한 문장으로 고정 — 적재 책임의 소재
캐시는 get/set만 받는 수동적 저장소이고, 무엇을·어떤 키로·언제·얼마 동안 넣을지는 전부 애플리케이션 코드가 정한다.

이것이 §2 근거 ③(통제권)의 실체이자, 동시에 뒤에 나올 모든 빈틈의 원인이다. 캐시가 아무것도 조율해 주지 않으므로, 조율이 필요한 상황은 전부 애플리케이션이 직접 처리해야 한다. §6~§9의 빈틈들은 하나같이 "캐시가 대신 해 주지 않는 조율"의 목록이다.

가산점 포인트 — 스프링 @Cacheable과의 연결 가산점
@Cacheable은 이 look-aside 흐름을 프록시가 대신 해 주는 선언적 구현이다. 메서드 호출을 가로채 캐시를 먼저 보고, 없으면 원래 메서드를 실행해 그 반환값을 캐시에 넣는다. "직접 짜면 위 코드고, 애너테이션을 붙이면 프록시가 똑같은 일을 한다"로 연결하면 좋다. 다만 프록시가 대신 해 주는 것은 흐름일 뿐 조율이 아니다 — §6~§9의 빈틈은 @Cacheable을 써도 그대로 남는다.

4. 게으른 적재(lazy loading) vs 캐시 워밍 — 언제 채우는가

§3 흐름의 첫 번째 성질이 게으른 적재다. 여기서 "게으르다"는 미리 준비해 두지 않고, 실제로 그 데이터를 달라는 요청이 왔을 때 비로소 채운다는 뜻이다. 캐시에 무엇이 들어갈지를 미리 계획하지 않고 트래픽이 알아서 결정하게 두는 것이다.

게으른 적재 기본값

수요가 공급을 부른다. 요청이 온 키만 캐시에 산다.

  • 이득 — 메모리 효율. 상품이 100만 개라도 실제 조회되는 것이 1만 개라면 캐시에는 1만 개만 산다.
  • 대가 — 첫 요청은 반드시 비용을 낸다. 어떤 키든 처음 읽히는 순간과 만료 직후 다시 읽히는 순간에는 반드시 미스가 난다.
  • 즉 캐시의 이득은 "두 번째 이후 요청"에만 생긴다.
캐시 워밍(예열) 소수의 핵심 키에만

공급을 미리 깔아 둔다. 요청을 기다리지 않고 미리 채운다.

  • 배포 직후 배치가 인기 상품 상위 N개를 미리 적재해 두면 사용자 첫 요청부터 히트가 된다.
  • 전체에 적용하면 안 된다 — 게으른 적재의 이득(메모리 효율)을 통째로 버리는 셈이 된다.
  • 워밍이 배포 절차에 들어가는 진짜 이유는 §6의 cold cache 때문이다.
실무의 조합 — 한 문장
기본은 게으른 적재로 두고, 미스 비용을 감당할 수 없는 소수의 핵심 키에만 워밍을 얹는다.

5. 쓰기 흐름 — DB에 쓰고, 캐시는 갱신이 아니라 삭제한다

look-aside는 이름 그대로 읽기 패턴이다. 쓰기를 어떻게 할지는 별도로 정해야 하고, 정석 조합은 DB에 먼저 쓰고(커밋), 캐시를 삭제(evict)하는 것이다. 삭제해 두면 다음 읽기가 자연스럽게 미스 → DB의 새 값 적재로 이어진다.

✕ 흔한 실수 — 트랜잭션 안에서 캐시를 "갱신"
@Transactional
public void updatePrice(Long id, long newPrice) {
    productRepository.updatePrice(id, newPrice);

    // 새 값을 아니까 캐시도 채워두자?
    redisTemplate.opsForValue()
        .set("product:" + id, load(id));
}
// 문제 ①  동시 쓰기 시 SET 도착 순서가 역전되면
//         DB=3000인데 캐시=2000이 TTL까지 남는다
// 문제 ②  커밋 전이라 롤백되면 캐시에 '유령 값'이 남는다
// 문제 ③  TTL도 없다 → 잘못 들어간 값이 영원히 산다
✓ 정석 — 커밋 "후" 삭제
@Transactional
public void updatePrice(Long id, long newPrice) {
    productRepository.updatePrice(id, newPrice);   // ① DB 갱신

    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override public void afterCommit() {
                redisTemplate.delete("product:" + id); // ② 삭제
            }
        });
}
// 커밋 "후"여야 하는 이유: 커밋 전에 지우면, 그 사이 들어온
// 읽기가 아직 롤백될지 모르는 상태의 DB를 읽어 캐시에 올린다.
// (전개는 07-cache-db-consistency 문서에서 상세히)

역
동시 쓰기의 순서가 역전될 수 있다 쓰기 A(가격 2000)와 쓰기 B(가격 3000)가 거의 동시에 들어왔다고 하자. DB에서는 락이 순서를 정리해 주므로 최종 값이 확정된다. 그런데 캐시 갱신은 그 락 바깥에서 일어나는 별도의 네트워크 호출이라, DB에는 B가 마지막으로 반영됐는데 캐시 SET은 A가 나중에 도착하는 역전이 가능하다. 그러면 캐시 2000 / DB 3000이 TTL까지 지속된다. 삭제는 이 문제가 없다 — 둘 다 "삭제"이므로 어느 쪽이 나중에 도착하든 결과는 "키 없음"으로 같고, 다음 읽기가 DB의 진실을 가져온다.
결
쓰기 경로가 캐시의 값 형태를 만들 수 있다는 보장이 없다 캐시에 든 것이 단순 엔티티가 아니라 여러 테이블을 조인해 만든 화면용 DTO이거나 집계 결과라면, 가격만 바꾸는 쓰기 경로가 그 전체 형태를 다시 만들어야 한다. 이는 쓰기 코드가 읽기 코드의 조회 로직을 복제해 갖게 되는 결합이다. 삭제는 "이 값은 이제 못 믿는다"는 신호만 보내고, 새 값을 만드는 일은 읽기 경로에 그대로 남겨 둔다.
낭
읽히지도 않을 값을 미리 계산하는 낭비 쓰기가 잦고 읽기가 드문 키라면 매 쓰기마다 캐시를 갱신해 봐야 대부분 읽히기 전에 다시 덮어써진다. 삭제는 다음 읽기가 있을 때만 값을 만든다 — §4의 게으른 적재 원칙과 일관된다.
이 문서에서 말할 범위
갱신 vs 삭제 논쟁에는 더 들어갈 층이 있고 그것은 별도 문서 07-cache-db-consistency-update-vs-delete.md의 몫이다. 여기서는 "기본값은 삭제이고, 그 근거는 순서 역전·결합·낭비 셋"까지 말할 수 있으면 된다.

6. 빈틈① 미스 비용과 cold cache

이 절부터가 이 문항의 무게중심이다
Look-aside를 "설명할 줄 안다"와 "빈틈을 안다"의 차이가 변별점이다. 아래 넷은 구현을 잘못해서 생기는 버그가 아니라 패턴의 구조에서 필연적으로 나오는 성질이다.

빈틈 4종은 "차·폭·경·직"으로 인출한다 — 차가운 캐시, 폭주, 경합, 직격.

6-1. 미스 한 번은 왕복 3회 — 캐시를 안 쓴 것보다 2회 더 간다

평소엔 문제가 안 된다. 히트율이 높으면 대부분 1회로 끝나고, 미스가 내는 3회는 평균에 묻힌다.

6-2. 문제는 히트율이 0이 되는 순간 — cold cache

배포 직후나 캐시 장애 복구 직후에는 캐시가 통째로 비어 있다. 이 상태를 cold cache(차가운 캐시)라고 부른다 — 데워지지 않았다는 뜻이다. 이때 들어오는 모든 요청이 미스이므로 DB는 캐시가 없던 시절의 트래픽을 그대로 맞고, 게다가 요청마다 쓸모없는 캐시 왕복 2회가 얹힌다.

캐시 히트율 90%를 전제로 DB 스펙을 잡았다면, DB는 평소 트래픽의 10분의 1만 감당하도록 준비된 상태다. 그래서 캐시 워밍이 배포 절차에 들어간다.

7. 빈틈② 동시 미스 폭주 — 캐시 스탬피드

인기 키 하나가 만료되는 순간을 생각해 보자. 그 키를 초당 1,000번 읽던 요청들이 전부 동시에 미스를 본다. 그리고 전부 DB로 가서 같은 쿼리를 1,000번 실행하고, 전부 같은 값을 캐시에 적재한다.

§3에서 본 대로 캐시는 아무것도 조율해 주지 않고, 각 요청 스레드는 다른 스레드가 지금 같은 키를 재계산 중이라는 사실을 알 방법이 없다.
분산 락 한 명만

한 요청만 재계산하게 하고 나머지는 대기시킨다.

TTL 지터 만료 분산

만료 시각 자체를 흩뿌린다. 단일 인기 키 하나의 폭주는 못 막는다.

refresh-ahead 미리 갱신

만료 전에 백그라운드로 값을 새로 만들어 둔다.

sync = true 스프링

@Cacheable(sync = true)로 같은 키 재계산을 한 번으로 묶는다.

답변 순서가 중요하다 — 진단 먼저, 해법 나중
"1,000개가 몰리니 락을 겁니다"로 시작하면 도구 나열이 된다. "look-aside의 미스 처리에 '한 명만 다녀와라'라는 조정 장치가 없어서 생기는 구조적 문제"라고 원인을 먼저 진단하고 해법을 붙인다. 각 도구가 무엇을 공략하고 어떤 대가를 치르는지는 06번 문서(캐시 스탬피드)의 몫이다.

8. 빈틈③ 읽기·쓰기 경합 — 옛 값이 늦게 적재되는 창 ★

이 문서에서 가장 중요한 대목 시니어 변별
look-aside를 쓰는 한 반드시 존재하고, 이 창을 시간축에 그릴 수 있는지가 변별의 실체다. 문제의 씨앗은 §3 읽기 흐름에 있다 — ③ DB 조회와 ④ 캐시 적재는 같은 순간이 아니다. 그 사이에는 값을 가공하고, 직렬화하고, Redis로 네트워크 요청을 보내는 시간이 있다. 짧지만 0은 아니다. 그리고 그 사이에 쓰기 요청이 통째로 지나갈 수 있다.
두 경로를 한 시간축에 겹쳐 그려야만 보이는 문제다. 이 그림을 그릴 수 있는 것 자체가 분산 환경 타이밍 사고력의 증명이다.
이 시나리오의 고약한 점 — 한 문장
누구도 잘못하지 않았다.

읽기 A는 look-aside를 교과서대로 수행했고, 쓰기 B도 "DB 쓰고 캐시 삭제"라는 정석을 정확히 지켰다. 삭제 호출이 실패한 것도 아니다 — 성공했는데 지울 것이 그 시점에 없었을 뿐이다. 그리고 그 뒤에 A가 자기 손에 들고 있던 과거의 값을 되살렸다.

8-1. 왜 이 창을 완전히 막을 수 없는가

막으려면 "A가 t1에 읽은 값이 t4 시점에도 여전히 최신인가"를 A가 알아야 한다. 그런데 look-aside에서 읽기 경로와 쓰기 경로는 서로의 존재를 모르는 완전히 별개의 코드 경로다. 같은 트랜잭션도 아니고, 같은 락도 공유하지 않는다.

막는 방법이 없진 않다 이론상
  • 키마다 버전 번호를 두고 적재 시점에 버전이 그대로인지 확인(비교 후 교환)
  • 읽기와 쓰기가 같은 분산 락을 잡게 하기
그런데 비용이 성립하지 않는다 핵심
  • 읽기 경로에 락을 거는 순간 캐시를 도입한 이유가 사라진다. 캐시는 읽기를 빠르게 하려고 넣은 것인데 모든 읽기가 락을 기다린다면 목적과 정면 충돌이다.
  • 버전 검사도 왕복과 복잡도를 늘린다.
  • 발생 확률은 매우 낮은데(미스 처리 중 정확히 그 키를 쓰는 요청이 끼어들어야 한다) 막는 비용은 상시로 발생한다.
그래서 실무의 답
막지 않고, 낡음의 지속 시간을 유한하게 만든다. 그 장치가 TTL이다.

8-2. TTL의 성격이 여기서 새로 정의된다

어떤 경합으로 옛 값이 들어갔든, 어떤 삭제 호출이 유실됐든 — TTL이 지나면 그 값은 반드시 사라진다.
암기 — TTL의 정체
TTL은 메모리를 아끼는 성능 장치가 아니라, 정합성의 최후 안전망이다.
그래서 무한 TTL(만료 없는 캐시)은 금물 — 이 창을 영구화한다.

9. 빈틈④ 캐시 장애 = DB 직격 — "히트율이 높을수록 충격이 크다"는 역설

§2에서 look-aside의 장점으로 꼽은 "캐시가 죽어도 DB로 동작한다"에는 반드시 조건이 붙는다. DB가 그 트래픽을 버틸 때만 성립한다.

숫자로 고정 — 캐시 장애 시 DB 부하 배수
배수 = 1 ÷ (1 − 히트율)
히트율 90%

DB는 평소 읽기의 10%만 받는 중 → 장애 시 10배

히트율 99%

DB는 평소 읽기의 1%만 받는 중 → 장애 시 100배

그래서 역설

히트율이 높을수록 캐시 장애의 충격이 크다. 캐시가 잘 일할수록 DB는 그만큼 준비가 안 된 상태가 된다.

9-1. 방어책 넷 — 각각 다른 지점을 막는다

1
캐시 클라이언트에 짧은 타임아웃 — fail-fast(빨리 실패하기) Redis가 응답하지 않을 때 기본 타임아웃(수 초)을 기다리면 그 대기가 애플리케이션 스레드를 붙잡아 캐시 장애가 응답 지연으로 전파된다. 짧게 잡아 즉시 포기하고 DB로 넘어가게 만든다.
2
DB 앞에 서킷 브레이커 DB가 이미 밀리기 시작했다면 요청을 더 보내 봐야 전부 타임아웃이 되고 커넥션 풀만 고갈된다. 실패율이 임계치를 넘으면 회로를 끊어 즉시 실패를 반환해 DB에 회복할 틈을 준다.
3
캐시를 단일 장애점으로 만들지 않는다 레플리카·Sentinel·클러스터 구성으로 노드 하나의 장애가 캐시 전체의 장애가 되지 않게 한다.
4
용량 계획에서 히트율 전제를 검증한다 — 가장 근본적인 방어 "캐시 히트율 90%를 전제로 DB를 잡았다"면 그 순간 캐시는 성능 최적화 장치가 아니라 필수 구성 요소가 된 것이고, 그렇다면 캐시의 가용성 요구 수준도 DB와 같아야 한다. 이 점검을 안 하면 가용성을 높이려고 넣은 캐시가 실제로는 장애 지점을 하나 추가한 구조가 된다.

9-2. 코드에서의 fail-fast — 캐시 예외는 "미스"다

✕ 캐시 장애가 곧 요청 실패
public Product findProduct(Long id) {
    String key = "product:" + id;

    // Redis가 죽으면 여기서 예외 → 요청 자체가 실패
    Product cached = redis.opsForValue().get(key);
    if (cached != null) return cached;

    Product p = repo.findById(id).orElseThrow();
    redis.opsForValue().set(key, p, TTL); // 여기서도 터진다
    return p;
}
// look-aside의 장점("캐시가 죽어도 산다")을
// 코드가 스스로 버린 형태다.
✓ 캐시 실패 = 미스로 취급하고 DB로
public Product findProduct(Long id) {
    String key = "product:" + id;

    Product cached = null;
    try { cached = redis.opsForValue().get(key); }
    catch (RuntimeException e) { log.warn("cache down", e); }
    if (cached != null) return cached;

    Product p = repo.findById(id).orElseThrow();
    try { redis.opsForValue().set(key, p, TTL); }
    catch (RuntimeException e) { log.warn("cache set fail", e); }
    return p;
}
// + 클라이언트 타임아웃을 짧게(fail-fast)
// + DB 앞엔 서킷 브레이커 — 폴백이 DB를 죽이지 않게
폴백만 넣고 끝내면 절반이다
예외를 삼켜 DB로 넘기는 것은 "기능을 지키는" 처리일 뿐, 그 순간 DB로 쏟아지는 트래픽은 §6의 cold cache와 같은 크기다. 그래서 폴백(코드) · 타임아웃(클라이언트) · 서킷 브레이커(DB 앞) · 용량 검증(설계) 넷이 한 세트다.
적재(SET)할 때 챙길 것 — 체크리스트
① TTL
첫 번째 답이다. 무한 캐시는 무효화 유실이나 경합으로 들어간 옛 값이 영원히 남는 구조다. 아무리 짧더라도 만료를 준다 — 정합성 안전망이면서 동시에 메모리 보호 장치.
② null/부재 결과
존재하지 않는 키를 캐시하지 않으면 그 키를 반복 조회하는 요청이 매번 캐시를 그냥 지나쳐 DB를 때린다 — 이것이 캐시 관통(cache penetration)이다. 대응은 "없음"이라는 사실도 아주 짧은 TTL로 캐시하는 절충. TTL을 짧게 두는 이유는 그 사이 실제로 데이터가 생겼을 때 "없음"이 오래 남지 않게 하기 위해서다. 가산점
③ 직렬화·키 버저닝
캐시에 넣는 객체 구조가 배포로 바뀌면 이전 형식으로 직렬화된 값을 새 코드가 역직렬화하다 예외가 난다. 캐시 미스도 아니고 예외라서 요청이 그대로 실패한다. 그래서 키에 버전을 넣어(product:v2:42) 배포와 함께 키 공간을 갈아탄다. 가산점

10. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 특히 시니어 변별 표시된 문항은 말로 설명하지 말고 시간축을 그려서 답해 본다.

Read-through와 Look-aside의 차이는 무엇인가요?

한 줄로 원본을 다녀오는 코드의 위치다.

  • Look-aside: 애플리케이션이 미스를 직접 확인하고 DB를 읽어 적재한다.
  • Read-through: 캐시에 로더를 등록해 두면 미스 시 캐시가 알아서 원본을 읽어 채우고, 애플리케이션은 캐시만 바라본다.

기술 스택으로 연결하면 구체적이 된다 — Redis는 로더 개념이 없어 look-aside로 쓸 수밖에 없고, Caffeine의 CacheLoader나 스프링 @Cacheable은 read-through 형태를 제공한다.

마지막에 차이의 의미까지 붙이면 좋다. 동작 결과는 비슷해도 "적재 로직을 누가 소유하느냐"가 다르고, look-aside는 그만큼 제어권(키 설계·TTL·조건부 캐싱)이 애플리케이션에 있다.

캐시(Redis)가 통째로 죽으면 서비스는 어떻게 되나요?

기능은 유지된다 — 모든 읽기가 미스 경로처럼 DB로 간다. 여기까지가 look-aside의 장점이다.

문제는 성능과 용량이다. 캐시가 흡수하던 읽기 트래픽을 DB가 그대로 맞으므로 히트율 90%였다면 DB 부하가 10배가 된다. DB가 밀리기 시작하면 캐시 장애가 전체 장애로 번진다.

  1. 캐시 호출에 짧은 타임아웃 — 캐시 장애가 응답 지연으로 전파되지 않게(fail-fast).
  2. DB가 버틸 수 없는 구조라면 서킷 브레이커·요청 제한으로 DB를 보호.
  3. 애초에 "캐시 히트율 전제 없이 DB가 버티는가"를 용량 계획에서 따진다.

"캐시가 가용성을 높인 게 아니라 장애 지점을 추가한 구조인지를 점검한다"고 말하면 상급이다 — 캐시 없이는 못 버티는 시스템에서 캐시는 최적화가 아니라 의존성이기 때문이다.

인기 키가 만료되는 순간 동시 요청 1,000개가 들어오면 어떻게 되나요?

캐시 스탬피드다. 1,000개가 전부 미스 → 전부 같은 DB 쿼리 → 전부 같은 값을 적재한다.

답변 순서가 중요하다. 원인 진단을 먼저 말한다 — "look-aside의 미스 처리에 '한 명만 다녀와라'라는 조정 장치가 없어서 생기는 구조적 문제"라고. 그다음 해법을 붙인다.

  • 분산 락(또는 스프링 sync = true)으로 한 요청만 재계산하고 나머지는 대기
  • TTL 지터로 대량 동시 만료 자체를 분산
  • refresh-ahead(soft TTL) — 만료 전에 백그라운드에서 미리 갱신

단, 지터는 여러 키의 동시 만료를 흩뜨리는 도구라서 단일 인기 키 하나의 만료 폭주는 못 막는다는 구분까지 말하면 도구의 적용 범위를 아는 것이 된다.

Look-aside에서 캐시와 DB가 달라지는 시나리오를 구체적으로 그려보세요 시니어 변별

두 개를 그릴 수 있어야 한다.

① 읽기-쓰기 경합 (§8 타임라인). 읽기가 미스로 DB의 옛 값을 읽은 뒤, 아직 적재하기 전에 쓰기가 DB 갱신 + 캐시 삭제를 끝낸다. 삭제 시점에는 지울 것이 없으므로 삭제는 아무 일도 하지 않고, 그 뒤 읽기가 손에 들고 있던 옛 값을 적재한다. 누구도 실수하지 않았는데 옛 값이 최종 승자가 된다.

② 삭제 실패/유실. DB 커밋은 성공했는데 캐시 삭제 호출이 실패하면(네트워크 순단, Redis 재시작, 타임아웃) 캐시에 옛 값이 그대로 남는다. 이쪽은 ①과 달리 실패가 실제로 일어난 경우다.

두 시나리오의 성격이 다르다는 점도 짚는다 — ①은 정상 동작들의 인터리빙이고 ②는 호출 실패다. ②는 재시도나 삭제 이벤트 발행으로 확률을 더 낮출 수 있지만, ①은 앞서 본 대로 비용 없이는 막을 수 없다.

결론으로 묶는다 — "캐시-DB 정합성은 완전히 보장하는 것이 아니라 확률적으로 좁히는 것이고, TTL이 최후 안전망이다." 그리고 이 두 타임라인을 그리는 능력 자체가 분산 환경 타이밍 사고력의 증명이다. 동시성 문제는 "언제 무엇이 끼어들 수 있는가"를 시간축에 그려야만 보인다.

적재(SET)할 때 꼭 챙겨야 할 것은 무엇인가요?

TTL이 첫 번째 답이다. 무한 캐시는 무효화 유실이나 경합으로 들어간 옛 값이 영원히 남는 구조이므로, 아무리 짧더라도 만료를 준다. 정합성 안전망이면서 동시에 메모리 보호 장치다.

여기에 둘을 더 붙이면 실무 경험이 드러난다. 가산점

  • null/부재 결과 처리 — 없는 키를 캐시하지 않으면 그 키 조회가 매번 캐시 관통(cache penetration)으로 DB를 때린다. "없음"도 아주 짧은 TTL로 캐시하는 절충.
  • 직렬화 형식과 키 버저닝 — 객체 구조가 배포로 바뀌면 옛 형식 값을 역직렬화하다 예외가 난다(미스가 아니라 실패다). product:v2:42처럼 키에 버전을 넣어 배포와 함께 키 공간을 갈아탄다.
@Cacheable 하나 붙이면 look-aside는 다 된 것 아닌가요? 추가

흐름은 되고, 조율은 안 된다. 프록시가 대신 해 주는 것은 §3의 "캐시 먼저 보고 없으면 메서드 실행해 반환값을 적재"라는 흐름이다. §6~§9의 빈틈은 그대로 남는다 — cold cache도, 스탬피드도(sync = true를 켜지 않는 한), 읽기·쓰기 경합 창도, 캐시 장애 시 DB 직격도.

그래서 애너테이션을 쓰더라도 직접 정해야 하는 것들이 그대로 남는다 — TTL은 캐시 매니저 설정에서 반드시 주고, 쓰기 경로에는 @CacheEvict를 커밋 후에 걸고, 인기 키에는 sync나 워밍을 얹는다.

덧붙일 만한 함정 하나 — 같은 클래스 안에서 자기 메서드를 직접 호출하면 프록시를 거치지 않아 캐시가 아예 동작하지 않는다(self-invocation). "애너테이션을 붙였는데 히트율이 0"인 사고의 단골 원인이다.

TTL이 어차피 있는데, 쓰기 때 캐시 삭제까지 꼭 해야 하나요? 추가

둘은 대체재가 아니라 역할이 다르다.

  • 삭제(evict)는 기대 낡음 시간을 거의 0으로 만든다 — 값이 바뀐 걸 아는 쪽이 즉시 무효화하는 능동적 장치.
  • TTL은 최악의 낡음 시간에 상한을 씌운다 — 삭제가 유실됐거나(§10 시나리오 ②) 경합으로 옛 값이 재적재됐을 때(§8) 그것을 끝내는 수동적 장치.

TTL만 두면 정상적인 갱신조차 TTL만큼 늦게 반영된다. 삭제만 두면 삭제가 실패하거나 §8 경합이 터진 순간 낡음이 영원해진다. 그래서 둘 다가 정답이고, 이 조합이 "정합성을 보장하는 게 아니라 확률적으로 좁힌다"는 말의 실체다.

캐시 삭제를 커밋 전에 하면 정확히 무엇이 잘못되나요? 추가

커밋 전에 지우면 지운 직후~커밋 사이에 들어온 읽기가 미스를 내고 아직 롤백될지 모르는 상태의 DB를 읽어 캐시에 올린다.

  • 그 읽기가 커밋 전의 옛 값을 읽어 적재하면 → 커밋 후 캐시에는 옛 값이 남는다(§8과 같은 결과).
  • 격리 수준·구현에 따라 결국 롤백될 값을 캐시에 올릴 위험도 생긴다 — DB에는 존재한 적 없는 값이 캐시에 사는 셈이다.

그래서 무효화는 커밋이 확정된 뒤에 실행한다(afterCommit). 다만 이렇게 해도 커밋과 삭제 사이의 창은 남는다 — 이 창을 어떻게 다룰지가 07-cache-db-consistency 문서의 주제다.

cold cache 대비로 워밍 말고 할 수 있는 게 없나요? 추가

워밍은 "미스를 없앤다"는 접근이고, 나머지는 "미스가 나도 DB가 안 죽게 한다"는 접근이다. 셋을 같이 말하면 답이 입체가 된다.

  • 트래픽 램프업 — 배포 직후 인스턴스에 트래픽을 한 번에 100% 주지 않고 서서히 올려서, 캐시가 데워지는 동안 DB가 받는 미스 총량을 시간에 흩뿌린다.
  • 스탬피드 방어를 켜 둔다 — cold cache 상태에서는 같은 키에 대한 동시 미스가 특히 많다. 락이나 sync로 키당 DB 쿼리를 1회로 묶으면 미스 수는 그대로여도 DB 쿼리 수는 크게 준다.
  • 서킷 브레이커·요청 제한 — 그래도 DB가 밀리면 전부 죽는 대신 일부를 빨리 실패시켜 회복 여지를 남긴다.

그리고 근본은 §9의 넷째 — "히트율 전제 없이 DB가 버티는가"를 용량 계획에서 미리 따지는 것이다.

히트율이 낮을 것 같은 데이터에도 일단 캐시를 붙여두면 손해는 없지 않나요? 추가

손해가 있다. 미스는 왕복 3회(GET + DB + SET)로, 캐시를 안 썼을 때(1회)보다 2회 더 간다(§6). 히트가 거의 없다면 그 2회는 전부 순손실이고, 캐시 메모리도 다시 읽히지 않을 값으로 채워진다(그리고 그 값이 다른 유용한 키를 밀어낸다).

그래서 캐시를 붙일지 판단하는 질문은 "느린가"가 아니라 "같은 값이 다시 읽히는가(재사용성)"이고, 여기에 변경 빈도와 낡아도 되는 정도가 함께 걸린다 — 이 판단 기준은 03-cache-suitability-criteria 문서의 주제다.

한 가지 유의 — 왕복 횟수와 시간은 다르다. 캐시 왕복은 대개 아주 싸고 DB 조회는 비싸므로, 실제 손익은 "아낀 DB 조회 × 히트율" vs "추가된 캐시 왕복 × 전체 요청"으로 따진다. 재사용성이 낮으면 앞쪽 항이 0에 수렴한다는 것이 핵심이다.

한 줄 요약
Look-aside는 애플리케이션이 캐시를 먼저 보고 미스면 DB에서 읽어 직접 적재하는(쓰기는 DB에 쓰고 캐시는 갱신이 아니라 삭제) 패턴으로, Redis에는 애초에 다른 선택지가 없고 캐시가 죽어도 서비스가 살며 무엇을 캐시할지 통제할 수 있어 실무 기본값이 되었지만 — 적재 책임이 앱에 있고 읽기와 쓰기가 서로를 모르는 구조라서 cold cache, 미스 폭주(스탬피드), 읽기가 든 옛 값이 쓰기의 삭제 뒤에 적재되는 경합, 캐시 장애 시 DB 직격이라는 빈틈이 내장되어 있고, 이 창들을 TTL이라는 최후 안전망과 워밍·락·타임아웃으로 어떻게 좁히는지까지 말해야 패턴을 "운영해 본" 답변이 된다.
