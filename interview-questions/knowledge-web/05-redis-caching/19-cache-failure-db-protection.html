핵심 관전 포인트 — 그대로 말하기
캐시는 언젠가 죽는다는 전제에서 출발해야 한다. 히트율 90% 시스템에서 캐시가 죽으면 DB는 평소의 10배 트래픽을 맞는데(히트율이 높을수록 배수가 커진다 — 99%면 100배다), DB가 그걸 못 견디는 구조라면 캐시는 가용성을 높인 게 아니라 장애 지점을 하나 추가한 것이다. 더 위험한 것은 죽은 캐시가 아니라 느려진 캐시다 — 죽으면 연결이 즉시 거부돼 바로 DB로 넘어가지만, 느려지면 요청마다 타임아웃까지 스레드를 붙잡아 결국 캐시를 쓰지 않는 API까지 처리할 스레드가 없어진다. 방어는 계층별로 깐다 — 캐시 호출에 짧은 타임아웃과 서킷 브레이커, DB 앞에 커넥션 풀 상한과 부하 차단, 그 위에 성능 저하 모드, 로컬 캐시 폴백, 그리고 캐시 자체의 HA. 핵심 설계 질문은 하나다 — "캐시 없이 DB가 트래픽의 몇 %를 견디는지 알고 있는가, 그 초과분을 어디서 어떻게 떨어뜨릴 것인가."
출제 의도 — 방어 장치의 이름 목록이 아니라 가용성의 역설을 아는지 본다
캐시는 언젠가 죽는다는 전제에서 출발하는지를 본다. 캐시 장애가 곧 DB 장애가 되는 구조라면 캐시는 가용성을 높인 게 아니라 장애 지점을 추가한 것 — 이 역설을 스스로 먼저 말하고 시작하면 질문의 절반은 답한 것이다. 그래서 이 페이지의 무게중심은 장치 소개(§5~§9)가 아니라 §2 가용성의 역설과 §3 느려진 캐시, 그리고 §10 "몇 %를 견디는가"에 있다.

1. 히트율의 두 얼굴 — "잘 돌고 있다"이자 "죽으면 몇 배를 맞는다"

캐시 히트율은 전체 조회 요청 중 캐시에서 답을 찾은 비율이다. 히트율 90%란 요청 1,000건 중 900건은 캐시가 답하고 100건만 DB까지 내려간다는 뜻이다. 그런데 이 90%는 성능 지표로 끝나지 않는다. 시스템 전체가 이 숫자를 전제로 만들어진다.

1
DB 사양이 그 전제 위에서 정해졌다 인스턴스 사양을 고를 때 "우리 DB에는 트래픽의 10%만 온다"를 전제로 잡는다. 커넥션 풀 크기도, 인덱스 튜닝의 목표치도 같은 전제 위에 있다.
2
그 위에서 트래픽이 계속 자란다 전체 요청이 두 배가 되어도 DB가 받는 몫은 여전히 10%이므로 DB는 계속 여유로워 보인다. 그래서 아무도 이 전제를 다시 검토하지 않는다.
3
그리고 그 전제는 코드 어디에도 적혀 있지 않다 캐시는 성능만 올린 것이 아니라 DB 용량 계획의 전제 자체를 바꿔놓았다. 이 사실이 캐시 장애를 다른 장애와 다르게 만든다.
암기 — 공식 하나면 이 절이 끝난다
부하 배수 = 1 / (1 − 히트율)
90% → 10배 · 95% → 20배 · 99% → 100배

배수는 히트율에 비례해서 늘지 않는다. 히트율이 1에 가까워질수록 가파르게 폭발한다. "10배"를 문장으로 외우지 말고 이 분수를 외워 두면, 면접에서 히트율이 몇으로 주어지든 즉석에서 계산해 답할 수 있다.

빨간 막대는 네 경우 모두 같은 높이다 — 변하는 것은 평소 DB가 받던 양(초록)뿐이고, 배수는 그 초록 막대가 얼마나 작았는지에서 나온다.
히트율평소 DB 도달 (요청 1,000 기준)캐시 사망 후 DB 도달부하 배수
80%2001,0005배
90%1001,00010배
95%501,00020배
99%101,000100배
이 절의 한 문장 — 히트율 그래프를 두 번 읽기
캐시 히트율은 "캐시가 얼마나 잘 돌고 있는가"인 동시에
"캐시가 죽으면 DB가 몇 배를 맞는가"이기도 하다.

히트율 99%는 자랑스러운 숫자다. 그런데 바로 그 이유로 캐시가 죽는 순간 100배를 맞는다. 캐시를 잘 튜닝할수록 캐시 장애의 피해가 커지는 구조이고, 이 역설을 인식하는 것이 이 문항의 출발점이다.

2. 연쇄 장애의 전파 경로 — DB에서 끝나지 않는다

DB가 10배를 맞으면 무슨 일이 벌어지는가. 여기서 멈추지 않고 어디까지 번지는지를 끝까지 따라가는 것이 이 질문의 핵심이다.

[8]이 이 도식의 핵심이다. 한 컴포넌트의 고장이 옆으로, 다시 그 옆으로 도미노처럼 넘어가는 형태 — 그 통로는 스레드 풀과 커넥션 풀이라는 공유 자원이다.

2-1. 가용성의 역설 — 컴포넌트를 늘렸는데 더 잘 죽는다

우리는 캐시를 "성능 개선 + DB 보호 장치"로 도입했다. 그런데 방어 설계 없이 도입하면 결과가 정반대가 된다.

방어 설계의 목표를 한 줄로 말하면 이것이다 — 캐시 장애를 "장애"에서 "성능 저하"로 강등시키는 것.
면접 첫 문장으로 쓰기 좋은 역설
컴포넌트가 하나 늘었는데 "둘 중 하나만 죽어도 장애"라면
산술적으로 가용성이 내려간 것이다.

캐시를 넣어서 시스템이 더 잘 죽게 된 셈이다. 이 역설을 스스로 먼저 말하고 시작하면 질문의 절반은 답한 것이다 — 면접관이 이 질문으로 확인하려는 것이 정확히 그 인식이기 때문이다.

3. 더 흔하고 더 음험한 쪽 — 죽은 캐시가 아니라 "느려진" 캐시 여기서 갈린다

직관과 반대라서 이 절이 이 문서에서 가장 중요한 통찰이다
실무에서 더 자주 겪고 더 위험한 것은 캐시가 죽지 않고 느려지는 경우다. 왜 "완전히 죽는" 쪽이 차라리 나은지, 메커니즘을 정확히 뜯어봐야 한다. 차이는 단 하나 — 스레드를 붙잡는 시간이다.
왼쪽은 문제가 DB에서 멈추고, 오른쪽은 애플리케이션의 전체 가용성을 먹는다. 그래서 방어의 1번이 락도 폴백도 아닌 캐시 호출의 타임아웃이다.
비교 축죽은 캐시 (프로세스 사라짐)느려진 캐시 (살아서 응답만 지연)
연결 시도 결과OS가 즉시 "연결 거부"연결은 성립, 응답만 안 옴
요청당 스레드 점유1ms 미만 ≈ 0타임아웃 시각까지 (예: 3초)
1차 피해 지점DB (부하 10배)애플리케이션 스레드 풀 — DB는 아직 멀쩡하다
캐시와 무관한 API대체로 영향 없음함께 죽는다 (로그인·헬스체크·주문)
감지 난이도에러율이 즉시 튄다에러율은 낮고 지연만 오른다 — 늦게 발견
발생 빈도드물다훨씬 잦다 (순단·긴 명령·페일오버·스왑)
1차 처방폴백 경로 확보짧은 타임아웃 → 서킷 브레이커(느린 호출도 실패로 집계)
암기 — 방어 순서가 이렇게 정해지는 이유
첫째 짧은 타임아웃(붙잡히는 시간 자체를 줄인다)
둘째 서킷 브레이커("느림"을 실패로 승격시켜 아예 호출하지 않는다)

순서를 이렇게 잡는 이유를 말할 수 있으면 이 문제의 구조를 이해한 것이다. 여기서 핵심 설정 하나 — 서킷 브레이커가 "느린 호출"을 실패로 집계하도록 켜 두어야 이 조합이 완성된다. 실패를 안 내고 느리기만 한 캐시는, 그 설정이 없으면 서킷이 영영 열리지 않는다.

4. 방어 계층 지도 — 요청이 지나는 순서대로 깐다

방어는 하나의 장치가 아니라 계층이다. 요청이 지나가는 길을 따라 앞에서부터 차례로 깐다. 아래 그림 한 장이 이 문항의 답변 골격이고, §5부터는 각 계층을 하나씩 뜯는다.

빨리 포기(타) → 아예 안 감(서) → 적게 보냄(깎) → 덜 줌(낮) → 딴 데서 흡수(로) → 애초에 덜 죽게(HA)
화살표가 DB에 닿기 전에 몇 번 걸러지는지를 보는 그림이다. 캐시가 사라진 순간, 이 경로에서 무엇도 걸러내지 않으면 §1에서 계산한 배수가 그대로 DB에 도착한다.
계층무엇을 줄이나이것만으로는 부족한 이유 / 대가
① 짧은 타임아웃 + 예외 격리요청 하나가 캐시에 붙잡히는 시간개별 요청은 살지만, 전 요청이 동시에 폴백을 타면 DB 폭주는 그대로다
② 서킷 브레이커죽은 캐시에 계속 노크하는 낭비서킷이 열려도 트래픽은 100% DB로 간다 — DB를 보호하진 않는다
③ 커넥션 풀 상한 · 부하 차단DB에 실제로 도달하는 양일부 사용자에게 의도적으로 실패를 준다 (그 대신 나머지를 살린다)
④ 성능 저하 모드애초에 필요한 조회의 양무엇을 포기할지 평시에 정해두지 않으면 장애 당일에 쓸 수 없다
⑤ 로컬 캐시 폴백인기 키 몫의 DB 조회노드마다 값이 다르고, 롱테일은 그대로 DB로 간다 — ③을 대체 못 한다
⑥ 캐시 HA무력화가 일어날 확률페일오버 공백이 있고, 노드가 살아 있는 무력화는 못 막는다

5. ① 캐시 호출 — 짧은 타임아웃 + 예외 격리 ("캐시는 best-effort")

캐시는 없어도 되는 계층이다. 원본 데이터는 DB에 있고, 캐시는 그것의 사본일 뿐이다. 이 사실 하나에서 규칙 두 개가 곧바로 나온다.

규칙 1 전파 금지

캐시 조회 실패가 요청 실패로 전파되면 안 된다. 사본을 못 읽었다고 원본을 못 읽는 것은 아니니까.

규칙 2 대기 금지

캐시 응답을 오래 기다려도 안 된다. 사본을 기다리느니 원본을 읽는 게 빠른 순간부터 캐시는 존재 이유를 잃는다.

✕ before — 예외가 요청을 죽이고, 타임아웃은 기본값(수 초)
public Product getProduct(Long id) {
    Product cached = redis.get(key(id));   // 다운 -> 예외 -> 500 응답
    if (cached != null) return cached;     // 느림 -> 여기서 수 초 대기
    return productRepository.findById(id);
}

// 문제가 둘이다.
//  (1) 예외가 그대로 올라가, DB에는 데이터가
//      멀쩡히 있는데도 500이 나간다.
//  (2) 타임아웃이 길어 §3의 스레드 고갈
//      경로로 직행한다.
✓ after — 캐시 실패는 삼키고(단, 기록하고) DB로 폴백
public Product getProduct(Long id) {
    try {
        Product cached = redis.get(key(id));
        if (cached != null) return cached;
    } catch (CacheAccessException e) {
        // 삼키되 반드시 기록한다. 조용히 무시하면
        // 캐시가 몇 시간째 죽어 있어도 아무도 모르는 채
        // DB만 얻어맞는 상태가 된다.
        log.warn("cache unavailable, fallback to DB", e);
        cacheFailureCounter.increment();   // 알람·서킷·저하 모드 트리거
    }
    return productRepository.findById(id);  // 캐시 없이도 동작하는 경로
}

타임아웃 자체는 코드가 아니라 클라이언트 설정에서 잡는다. 애플리케이션 로직마다 try를 흩뿌리는 대신, 캐시 클라이언트의 커맨드 타임아웃을 짧게 고정해 두는 것이 출발점이다.

✓ 클라이언트 커맨드 타임아웃을 짧게 고정 (Lettuce 예시)
LettuceClientConfiguration config = LettuceClientConfiguration.builder()
        .commandTimeout(Duration.ofMillis(50))   // 정상 응답(1ms 미만)의 수십 배
        .build();

// 숫자 자체보다 "무엇의 몇 배로 잡았는가"를 말할 수 있어야 한다.
// 같은 데이터센터 안의 Redis 조회는 정상일 때 1ms를 넘지 않는다.
// 수십 ms면 이미 정상 응답의 수십 배 -> 네트워크 지터·GC 정지를
// 흡수하기에 충분한 여유이고, 그보다 길게 잡을 이유가 없다.
타임아웃 값을 정하는 근거 — 비대칭을 말하라
길게 잡아 얻는 것: 가끔 느린 응답을 성공으로 건지는 것
길게 잡아 잃는 것: 장애 시 스레드를 그 시간만큼 붙잡는 것

§3의 계산(3초면 66 req/s, 50ms면 4,000 req/s)이 그 대가의 크기를 보여준다. 이 비대칭이 "짧게 잡는다"의 근거다. 한 문장으로는 이렇게 고정한다 — "DB 쿼리보다 오래 기다리는 캐시 조회는 존재 이유가 없다." 숫자를 외워 답하면 어디서 읽은 값이 되고, 기준을 말하면 자기 시스템에서도 정할 줄 아는 사람이 된다.

여기서 멈추면 안 되는 이유 — 폴백은 "개별 요청 하나를 살리는 장치"일 뿐
전 요청이 동시에 폴백을 타는 순간 §1에서 계산한 DB 10배 폭주로 그대로 돌아온다. "폴백으로 DB에 간다"까지만 말하면 폭주를 방어한 게 아니라 폭주를 DB에 전달한 것이다. 그래서 §7의 유입 제어가 반드시 뒤따라야 한다.

6. ② 서킷 브레이커 — 죽은 캐시에 계속 노크하지 않기

서킷 브레이커(circuit breaker)는 실패가 일정 비율을 넘으면 호출 자체를 시도하지 않고 즉시 실패시키는 장치다. 이름은 집 두꺼비집에 달린 전기 차단기에서 왔다. 과전류가 흐르면 차단기가 회로를 끊는다 — 계속 흘려보내면 배선이 타기 때문이다. 소프트웨어도 발상이 같다. 이미 문제가 생긴 곳으로 호출을 계속 보내면 상황이 더 나빠지므로, 아예 회로를 끊는다.

왜 ①의 타임아웃만으로는 부족한가 — 숫자로
타임아웃을 50ms로 줄여도, Redis가 죽어 있는 동안 모든 요청이 매번 50ms씩 버린다. 답이 안 올 것을 이미 아는데도 매번 다시 시도하고 매번 기다린다. 초당 500 요청이면 초당 25초어치의 스레드 시간이 그냥 증발한다. 게다가 그 호출 시도들이 이미 힘들어하는 Redis에 계속 부하를 얹는다.
소프트웨어의 직관("닫혔다 = 막혔다")과 반대라서 자주 틀린다. 전기 회로 그림으로 외우면 다시 헷갈리지 않는다.
1
빠른 실패 요청마다 타임아웃만큼 기다렸다 실패하는 낭비가 사라진다. OPEN 상태에서는 캐시 호출이 마이크로초 단위로 끝난다.
2
복구 여유 죽어가는 Redis에 연결 시도를 퍼붓지 않으므로 Redis가 숨 쉴 틈을 얻는다. 페일오버 중이라면 이 여유가 특히 중요하다.
3
자동 복구 감지 HALF_OPEN이 사람 없이 회복을 알아챈다. 운영자가 "이제 Redis 살아났으니 서킷 닫아주세요"를 할 필요가 없다.
4
상태 그 자체가 신호 — 이것이 ④와 이어진다 서킷이 열렸다 = "지금 우리는 캐시 없이 운영 중이다"라는 상태가 명확한 값으로 존재하는 것이다. 알람·대시보드에 직결시키고 §8 성능 저하 모드를 발동시키는 트리거로 쓴다. 애플리케이션이 자기 상태를 스스로 아는 셈이다.
✓ 설정에서 반드시 켜야 하는 항목 — "느린 호출"도 실패로 집계
# 개념만 가져간다. 속성 이름은 라이브러리·버전마다 다르다.
# (Java 진영에서는 Resilience4j 같은 라이브러리로 구현하는 것이 일반적)

failure-rate-threshold: 50            # 실패율이 이 %를 넘으면 OPEN
slow-call-duration-threshold: 50ms    # 이만큼 넘게 걸린 호출은 "느린 호출"
slow-call-rate-threshold: 50          # 느린 호출 비율이 이 %를 넘어도 OPEN  <- 핵심
wait-duration-in-open-state: 10s      # OPEN 유지 후 HALF_OPEN으로
permitted-calls-in-half-open: 5       # 시험 호출 수

# 이 두 줄이 없으면, "실패는 안 나고 느리기만 한 캐시"(§3)에서
# 서킷이 영영 열리지 않는다 — 가장 위험한 시나리오를 놓치는 설정이다.
서킷 브레이커의 한계 — 이걸 같이 말해야 답이 닫힌다
서킷이 열리면 캐시 호출은 사라지지만,
트래픽은 100% DB로 간다. 서킷은 앱을 지키는 장치이지 DB를 지키는 장치가 아니다.

서킷 OPEN은 "캐시를 건너뛴다"는 뜻이므로, DB 입장에서 보면 §1의 배수가 가장 깨끗하게 전달되는 상태다. 그래서 ②는 반드시 ③(유입 제어)·④(저하 모드)와 세트로 설계한다.

7. ③ DB 앞 — 유입량 자체를 깎는다 이 질문의 본론

①과 ②는 "캐시가 죽어도 개별 요청은 살아남게" 만든 것이지 폭주를 막은 것이 아니다. 캐시가 사라진 순간 DB로 향하는 트래픽을 DB가 견디는 수준으로 깎아내는 장치가 따로 필요하다.

7-1. 커넥션 풀 상한 — 이미 갖고 있는 스로틀

커넥션 풀은 원래 "커넥션 생성 비용을 아끼려고" 만든 것이지만, 부하 제어 장치의 역할도 겸한다. 풀 크기가 20이면 동시에 DB에 던져지는 쿼리는 최대 20개이고, 21번째 요청은 DB에 닿지 못하고 풀 대기에서 걸린다. DB가 동시에 처리할 수 있는 수준으로 풀을 잡아 두면 그 자체가 문지기가 된다.

✕ before — 문지기는 세웠는데 줄이 무한히 길다
maximum-pool-size: 20
connection-timeout: 30000   # 기본값 30초 — 풀 대기 30초

# 커넥션을 30초씩 기다리는 요청이
# 그동안 애플리케이션 스레드를 붙잡는다.
# -> DB 커넥션 고갈이 스레드 풀 고갈로
#    그대로 전이된다 (§2의 [5]->[6]->[7]).
# 문지기 앞의 줄을 방치하면
# 문지기가 없는 것과 같다.
✓ after — 짧게 기다리고 빨리 실패시킨다
maximum-pool-size: 20       # DB가 동시에 감당하는 수준
connection-timeout: 250     # 못 받으면 즉시 실패 (예시)

# 대기 타임아웃을 짧게 잡는 이유는 §3과 완전히 같다.
# "기다리는 시간 = 스레드가 묶이는 시간"이기 때문이다.
#
# 두 숫자 모두 §10에서 측정한
# "DB가 캐시 없이 견디는 양"에서 나와야 한다.
# 감으로 정한 값이면 방어가 아니라 장식이다.

7-2. 부하 차단(load shedding) — 일부를 일찍 버려 나머지를 살린다

들어온 요청을 전부 처리하려다 전부 실패하느니, 일부를 일찍 거절해서 나머지를 정상 처리하는 기법이다. 이름은 배에서 왔다 — 폭풍 속에서 가라앉을 것 같으면 짐(load)을 바다에 버려(shed) 배를 띄운다. 화물 일부를 잃는 것은 확정된 손실이지만, 안 버리면 배와 화물 전부를 잃는다. 전력망에서도 같은 용어를 쓴다 — 전력이 모자라면 일부 지역을 계획적으로 정전시켜 전체 정전을 막는 것이 load shedding이다.

소프트웨어에서는 이렇게 구현한다. 처리 용량을 넘는 요청은 큐에 쌓지 말고 입구에서 즉시 429(Too Many Requests)나 503(Service Unavailable)으로 거절한다. 큐에 쌓아두면 결국 그 요청도 타임아웃으로 실패하는데, 그때까지 자원만 붙잡고 있기 때문이다.

0%와 70%의 차이다. 그리고 오른쪽은 부하가 걷히는 즉시 정상으로 돌아오지만, 왼쪽은 큐가 가득 찬 상태라 부하가 줄어도 곧바로 회복되지 않는다.
암기 — 이 한 문장이 load shedding 정당화 논리 전체다
load shedding은 "실패를 만드는 것"이 아니라
어차피 발생할 실패를 빠르고 싸게, 통제된 위치에서 발생시키는 것이다.

왜 "싼" 실패인가. 5초 걸려 타임아웃 나는 실패는 5초 동안 스레드와 커넥션을 붙잡아 다른 요청까지 방해한다. 1ms 만에 503을 반환하는 실패는 자원을 거의 안 쓰므로 남은 700건에 아무 피해를 주지 않는다. 같은 "실패"라도 시스템에 미치는 비용이 다르다.

7-3. 벌크헤드 — 침수를 한 구역에 가둔다 보강

벌크헤드(bulkhead)는 배의 격벽이다. 선체를 여러 구역으로 나눠 두면 한 구역이 침수돼도 물이 배 전체로 퍼지지 않아 배가 뜬 채로 남는다. 소프트웨어에서는 스레드 풀이나 커넥션 풀을 기능별로 쪼개는 것이 이에 해당한다.

이것이 이 문서에서 중요한 이유는 §2의 [8] 때문이다. 캐시 장애가 로그인까지 죽이는 통로는 "모두가 같은 스레드 풀·커넥션 풀을 공유한다"는 사실 하나였다. 격벽을 세우면 그 통로가 끊긴다 — 상품 조회용 자원이 다 타 버려도 결제·로그인용 자원은 남아 있다.

얻는 것 전파 차단

한 기능의 폭주가 다른 기능의 자원을 먹지 못한다. 장애의 범위를 미리 정해두는 셈이다.

대가 활용률과 복잡도

자원을 쪼개면 한쪽이 놀아도 다른 쪽이 못 빌려 쓴다 — 전체 활용률이 떨어지고 풀을 몇 개나 어떻게 나눌지 관리 부담이 생긴다.

7-4. 재시도 규율 — 이게 없으면 위 장치가 전부 무의미해진다

503을 받은 클라이언트가 즉시 다시 요청하면 유입량이 오히려 늘어난다. 100건을 거절했더니 100건이 곧바로 다시 들어오는 것이다. 이것을 재시도 폭풍(retry storm)이라고 부른다.

1
지수 백오프 — 재시도 간격을 1초, 2초, 4초, 8초로 늘린다 실패가 이어질수록 스스로 물러나 준다. 회복 중인 시스템에 다시 몰리지 않게 하는 최소한의 예의다.
2
재시도 횟수 상한 상한이 없으면 백오프를 걸어도 결국 계속 온다. 몇 번 만에 포기할지가 정해져 있어야 한다.
3
지터(무작위 흔들림)를 더한다 백오프만 있으면 거절당한 클라이언트들이 정확히 같은 시각에 다시 몰린다. 간격에 무작위를 섞어야 그 동기화가 풀린다.

8. ④ 성능 저하 모드(graceful degradation) — 낡은 값으로 버티기

기능을 전부 잃는 대신 품질을 낮춰서라도 서비스를 유지하는 방식이다. graceful은 "우아한", degradation은 "품질 저하" — 직역하면 "우아하게 나빠지기"다. 갑자기 뚝 끊기는 대신 서서히 품질을 낮추며 버틴다는 뜻이다.

발상의 전환 — 캐시 장애에서 특히 잘 통하는 이유
"정확한 응답을 못 준다 = 에러"가 아니다.
애초에 캐시에 넣었다는 것 자체가 "이 데이터는 조금 낡아도 된다"는 판단이었다.

TTL 30분짜리 캐시를 쓰고 있었다면 이미 최대 30분 낡은 값을 보여주기로 합의한 것이다. 그렇다면 장애 상황에서 두 시간 낡은 값을 보여주는 것도 협상 가능한 선택지다. 이 논리를 먼저 세우고 선택지를 나열하면 "대충 때우기"가 아니라 설계로 들린다.

낡은 스냅샷 노출 가장 강력

인기 목록·랭킹·추천처럼 무거운 집계 결과는 주기적으로 떠서 서버 메모리·파일·CDN에 정적으로 올려둔다. Redis가 죽어도 이 스냅샷은 살아 있다.

  • "1시간 전 인기 목록"은 에러 페이지보다 백 배 낫다.
개인화 끄기 조회 수를 나눈다

"당신을 위한 추천"은 사용자별 조회가 필요하지만 "전체 인기 상품"은 모두에게 같은 값이라 하나만 만들어두면 된다.

  • DB 조회 수가 사용자 수만큼 나누어 줄어든다.
목록 개수 축소 쿼리 비용 절감

한 페이지에 50개 대신 10개만 보여준다. 조회 범위가 줄어 쿼리 비용이 내려간다.

비핵심 기능을 피처 플래그로 끄기 여력 몰아주기

추천 위젯·조회수 표시·연관 상품을 끄고 핵심 경로(상품 조회·주문·결제)에 DB 여력을 몰아준다.

✓ ②의 서킷 상태를 ④의 트리거로 — 두 계층이 이어지는 지점
public List<Product> popularProducts() {
    if (cacheCircuit.isOpen() || degradeMode.isOn()) {
        // "지금 우리는 캐시 없이 운영 중"이라는 상태가 값으로 존재하므로
        // 사람의 판단을 기다리지 않고 코드가 스스로 저하 모드로 내려간다.
        return staticSnapshot.popularProducts();   // 평시에 떠 둔 스냅샷
    }
    return cachedOrDb();
}

// 스위치(degradeMode)는 수동으로도 켤 수 있어야 한다 —
// 자동 판정이 못 잡는 상황에서 운영자가 즉시 내릴 수 있는 손잡이.
이 절에서 가장 중요한 한 문장
이 모드에서 "무엇을 보여줄지"는 장애 당일에 정할 수 없다.
평시에 무엇을 포기할지 정해두고 스위치만 준비해 두는 것이 방어 설계의 실체다.

장애 한복판에서 "추천 위젯을 끌까요?"를 논의하고 코드를 고쳐 배포할 시간은 없다. 설계라는 말이 여기서 문자 그대로의 의미를 갖는다.

9. ⑤ 로컬 캐시 폴백 · ⑥ 캐시 자체의 HA

9-1. ⑤ 로컬 캐시 — Redis가 죽어도 남는 계층

Caffeine 같은 로컬 캐시를 Redis 앞에 한 겹 더 두는 방법이다. 로컬 캐시는 애플리케이션 인스턴스의 자기 힙 메모리에 값을 담아두므로 네트워크를 건너지 않아 훨씬 빠르고, Redis가 죽어도 영향을 받지 않는다.

평시에는 Redis 왕복을 아끼는 성능 장치, 장애 시에는 완충재. 다만 완충재는 인기 상위 몇천 건까지이고 그 밖은 그대로 DB로 간다.
대가를 반드시 함께 말한다 — 이 장치는 공짜가 아니다
① 값이 노드마다 다르다 · ② 롱테일은 그대로 DB로 간다

로컬 캐시는 인스턴스마다 따로 존재하므로 서버 A와 B가 같은 상품에 다른 값을 갖고 있을 수 있다. 사용자가 새로고침할 때마다 다른 서버에 붙으면 값이 왔다 갔다 하는 게 보인다. 수정 시 이걸 맞추려면 모든 인스턴스에 무효화를 전파하는 장치가 따로 필요하고, 그 자체가 새 문제가 된다. 그래서 "초고빈도 읽기 + 낡음 허용" 데이터에 한정해 도입한다. 이 조건을 만족하지 않는 데이터에 걸면 불일치 문제만 얻는다.

9-2. ⑥ 캐시 HA — 확률을 줄이되, 방어 전제는 유지한다

HA(High Availability, 고가용성)는 장애가 나도 서비스가 계속되도록 여벌을 준비해 두는 구성이다. Redis에서는 복제본(replica)을 두고 Sentinel이 주 노드의 죽음을 감지해 복제본을 자동 승격시키거나, Cluster로 데이터를 여러 노드에 나눠 한 노드가 죽어도 나머지가 살아 있게 만든다. 이것으로 "캐시가 통째로 사라지는" 확률 자체를 줄인다. 다만 두 가지를 반드시 함께 말해야 한다.

자동 승격은 즉시 일어나지 않는다 — 판정 · 합의 · 재연결에 시간이 든다. 게다가 승격 이후에도 비어 있는 캐시라는 두 번째 구간이 남는다.
암기 — HA가 못 막는 무력화 4종 · "망 · 플 · 버 · 콜"
공통점: 노드는 살아 있는데 캐시가 무력화된 상황이다.
HA는 노드의 죽음을 다루는 장치이므로 이 유형에는 손을 쓸 수 없다.
망 (네트워크)
전 노드에 동시에 영향을 주는 네트워크 장애 — 복제본에도 못 닿는다.
플 (플러시)
잘못된 배포로 인한 캐시 전체 플러시 — 노드는 다 살아 있는데 데이터만 사라진다.
버 (버전)
키 이름 규칙(버전) 변경 — 모든 키가 한순간에 미스가 된다. 노드는 멀쩡하다.
콜 (cold)
복구는 됐지만 데이터가 비어 있는 상태 — 살아난 직후가 오히려 가장 위험하다.
이 질문의 함정
"Sentinel로 HA를 구성했으니 방어 설계는 필요 없다"

HA는 "무력화 확률을 줄이는" 축이고, 방어 설계는 "무력화가 그래도 일어났을 때"의 축이다. 서로 대체재가 아니라 보완재다. 이 문장을 그대로 말할 수 있으면 이 함정은 지나간다.

10. 설계 질문 하나로 요약 — "캐시 없이 DB가 몇 %를 견디는가"

지금까지의 방어 장치들을 관통하는 사전 숙제가 하나 있다. 그리고 이것이 실은 이 문항 전체의 답이다.

이 문항의 최종 답 — 장치 이름이 아니라 숫자다
캐시를 끄고 부하 테스트를 해서,
DB가 단독으로 트래픽의 몇 %를 견디는지 숫자로 알고 있어야 한다.

이 숫자가 없으면 앞의 어떤 계층도 설정할 수 없다. 커넥션 풀 크기도, 차단 임계치도, 무엇을 끌지도 전부 기준선이 이 숫자에서 나온다.

"몇 %를 견디는가"가 ③에서 어디까지 흘려보내고 어디부터 떨어뜨릴지의 기준선이고, ④에서 어떤 기능을 꺼야 할지의 근거다.

10-1. 가산점 — 카오스 엔지니어링 가산점

장애를 우연히 기다리는 대신 의도적으로 일으켜 방어가 실제로 동작하는지 검증하는 방법론이다. 스테이징에서 주기적으로 "캐시 강제 다운" 훈련을 돌려, 폴백이 정말 타는지 · 서킷이 정말 열리는지 · 저하 모드 스위치가 정말 켜지는지 확인한다.

왜 의미가 있는가 — 이 한 문장이 핵심이다
방어 코드는 평소에 실행되지 않는 코드다.

catch 블록도, 서킷 브레이커의 OPEN 경로도, 저하 모드 분기도 정상 상황에서는 한 줄도 안 돌아간다. 그래서 조용히 망가져 있어도 아무도 모른다. 리팩터링 중에 폴백 경로가 끊겼거나 저하 모드 피처 플래그가 언젠가부터 동작하지 않게 되었어도, 장애가 나기 전까지는 알 수 없다. 훈련은 그 코드를 주기적으로 실행시켜 방어 설계를 문서가 아니라 동작하는 코드로 유지한다. 여기까지 말하면 운영 성숙도가 드러난다.

11. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 시니어 변별 문항은 정답 하나를 고르지 말고 판단 기준을 말하는 연습을 한다.

총 10문항 · 5문항은 원본 md, 5문항은 파고들기용 추가
Redis가 완전히 죽은 것보다 느려진 게 왜 더 위험한가요?

차이는 스레드를 붙잡는 시간에 있다.

죽은 캐시는 연결이 즉시 거부되므로 애플리케이션이 1ms도 안 되어 실패를 받고 DB 폴백으로 넘어간다. 스레드 점유가 사실상 0이다. 부하는 DB로 가지만 문제는 DB에서 끝난다.

느린 캐시는 요청마다 타임아웃 직전까지 스레드를 붙잡는다. 타임아웃이 3초라면 스레드 하나가 3초씩 묶인다. 톰캣 스레드 200개 기준으로 초당 처리 가능 요청이 약 66건까지 떨어진다(200 / 3초). 그러면 DB는 멀쩡한데 애플리케이션 스레드 풀이 먼저 고갈되고, 캐시를 쓰지 않는 API — 로그인·헬스체크·주문 — 까지 함께 응답 불가가 된다.

감지도 늦다. 요청들이 실패하는 게 아니라 느릴 뿐이므로 에러율은 낮고 지연만 오른다. 에러율 대시보드만 보고 있으면 초록불이다.

그래서 방어 순서가 이렇게 정해진다 — 첫째 짧은 command timeout(붙잡히는 시간 자체를 줄인다), 둘째 서킷 브레이커("느림"을 실패로 승격시켜 아예 호출하지 않게 만든다). 서킷 브레이커가 느린 호출을 실패로 집계하도록 설정하는 것이 이 조합의 핵심이다(§6).

캐시 장애면 그냥 전부 DB로 보내면 되는 것 아닌가요?

DB 용량이 "히트율만큼 깎인 트래픽" 전제 위에서 설계되고 성장해 왔다는 게 함정이다.

히트율 90%였다면 폴백은 DB에 10배 부하를 의미한다(1 / (1 − 0.9) = 10). 그리고 이 배수는 히트율이 높을수록 커진다 — 95%면 20배, 99%면 100배다. 캐시를 잘 튜닝해 둔 시스템일수록 폴백의 충격이 크다는 역설이다.

DB가 그 부하에 무너지면 캐시 장애가 데이터 원본 장애로 승격된다. 성격이 완전히 달라진다 — 캐시는 죽어도 다시 띄우고 데워주면 되지만, DB가 무너지면 복구 시간도 위험도도 차원이 다르다.

그래서 폴백(①)은 반드시 유입 제어(③)와 한 몸으로 설계해야 한다. 폴백만 있고 유입 제어가 없으면 그것은 방어가 아니라 폭주를 DB로 안내하는 통로다. 그리고 "DB가 캐시 없이 몇 %를 견디는지"를 측정해 둔 숫자가 그 제어의 기준선이 된다(§10).

일부 요청을 일부러 실패시키는 결정을 어떻게 정당화하나요? 시니어 변별

전부 받으면 전부 느려지고, 결국 전부 실패한다. 이것이 출발점이다.

용량을 넘는 요청을 다 받으면 큐와 커넥션 대기가 쌓이고 100%의 요청이 타임아웃 근처의 지연을 겪는다. 정상 응답을 받는 사용자는 0%가 되고, 큐가 가득 찬 상태라 부하가 줄어도 시스템이 곧바로 회복되지 못한다.

용량의 70%만 받고 30%를 즉시 거절하면 70%는 정상 품질로 서빙되고 시스템은 안정 상태를 유지한다. 30%는 밀리초 안에 503을 받으므로 자원을 거의 쓰지 않아 나머지 70%를 방해하지 않는다.

0%와 70%의 비교다. 그래서 load shedding은 "실패를 만드는 것"이 아니라 이미 발생할 실패를 빠르고 싸게, 통제된 위치에서 발생시키는 것이다. 같은 실패라도 5초 걸려 타임아웃 나는 실패는 그동안 자원을 붙잡아 남을 방해하지만, 1ms 만에 거절하는 실패는 아무도 방해하지 않는다.

여기에 우선순위를 얹으면 더 좋은 답이 된다. 30%를 무작위로 고르는 것이 아니라 결제·주문 같은 핵심 경로는 보호하고 조회성·비핵심 트래픽부터 떨어뜨리는 차등 차단을 한다. 매출이 걸린 요청과 추천 위젯 요청을 같은 무게로 버릴 이유가 없다.

"무엇을 먼저 포기할지"가 기술 판단이 아니라 비즈니스 판단과 연결돼 있음을 말하는 것이 이 질문의 시니어 변별 지점이다. 그리고 그 우선순위는 장애 당일이 아니라 평시에 합의해 두어야 한다는 점까지 붙이면 완성된다.

서킷 브레이커는 캐시 호출에 거나요, DB 호출에 거나요?

둘은 목적이 다르고, 서킷 브레이커가 맞는 쪽은 캐시다.

캐시 호출의 서킷은 죽거나 느린 캐시를 건너뛰어 빠른 실패와 복구 여유를 주기 위한 것이다. 이것이 성립하는 이유는 캐시에는 건너뛸 대안이 있기 때문이다. 회로를 열면 요청은 폴백(DB) 경로로 간다 — 서킷을 여는 행위가 사용자에게 실패를 주지 않는다.

DB 쪽은 서킷보다 벌크헤드나 스로틀 성격이 맞다. DB는 원본이므로 건너뛸 폴백이 없다. 여기서 회로를 열면 갈 곳이 없어 전 요청이 그냥 실패한다. 즉 DB에 서킷을 걸면 "일부를 보호"하는 게 아니라 "전부를 죽이는" 스위치가 된다.

DB 보호의 실체는 회로를 끊는 것이 아니라 유입량을 깎는 것이다 — 커넥션 풀 상한으로 동시 실행 수를 묶고, 대기 타임아웃을 짧게 해서 대기 줄이 스레드 풀을 먹지 않게 하고, 입구의 load shedding으로 애초에 들어오는 양을 줄인다.

판단 기준은 하나로 요약된다 — 폴백이 있는 호출에는 서킷, 폴백이 없는 호출에는 유입 제한. "어디에 왜 거는지"를 구분해 말하는 것은 도구를 패턴 이름이 아니라 목적으로 이해한다는 신호다.

Sentinel로 HA를 구성했는데도 이 방어들이 필요한가요?

필요하다. HA와 방어 설계는 서로 다른 축을 담당한다.

첫째, 페일오버에는 공백이 있다. 장애 감지 → 복제본 승격 → 클라이언트 재연결까지 수 초에서 수십 초가 걸린다. 그 공백 동안 들어오는 트래픽은 ①~④가 받아내야 한다.

둘째, HA가 못 막는 무력화 유형이 있다. (§9-2의 "망·플·버·콜")

  • 망 — 전 노드에 영향을 주는 네트워크 장애: 복제본에도 못 닿는다.
  • 플 — 잘못된 배포로 인한 캐시 전체 플러시: 노드는 다 살아 있는데 데이터만 없다.
  • 버 — 키 이름 규칙(버전) 변경: 모든 키가 한순간에 미스가 된다.
  • 콜 — 복구는 됐지만 데이터가 비어 있는 cold cache: 히트율이 0%이므로 DB 부하는 캐시가 죽었을 때와 같다.

이 목록의 공통점은 "노드가 살아 있는데도 캐시가 무력화된" 상황이라는 것이다. HA는 노드의 죽음을 다루는 장치이므로 이 유형에는 손을 쓸 수 없다.

정리 문장은 그대로 외워 둔다 — HA는 "무력화 확률을 줄이는" 축이고, 방어 설계는 "무력화가 그래도 일어났을 때"의 축이다. 서로 대체재가 아니라 보완재다.

캐시 타임아웃을 몇 ms로 잡을지, 그 숫자의 근거를 어떻게 대나요? 추가

숫자를 외워 답하면 "어디서 읽은 값"이 되고, 기준을 말하면 자기 시스템에서도 정할 줄 아는 사람이 된다. 근거는 두 방향에서 댄다.

  1. 위쪽 근거 — 정상 응답 시간의 몇 배인가. 같은 데이터센터 안의 Redis 조회는 정상일 때 1ms를 넘지 않는다. 그렇다면 수십 ms의 타임아웃도 이미 정상 응답의 수십 배이므로 일시적인 네트워크 지터나 GC 정지를 흡수하기에 충분한 여유다. 그보다 훨씬 길게 잡을 이유가 없다.
  2. 아래쪽 근거 — 비대칭. 길게 잡아 얻는 것은 "가끔 느린 응답을 성공으로 건지는 것"뿐인데, 잃는 것은 장애 시 스레드를 그 시간만큼 붙잡는 것이다. §3의 계산(3초 → 66 req/s, 50ms → 4,000 req/s)이 그 대가의 크기를 보여준다.

한 문장으로 닫는다 — DB 쿼리보다 오래 기다리는 캐시 조회는 존재 이유가 없다. 캐시가 DB보다 느리게 답할 거라면 그냥 DB에 물어보는 게 낫기 때문이다.

덧붙이면 좋은 것: 연결 타임아웃과 커맨드 타임아웃은 다른 값이고, 재시도가 붙으면 실질 대기 시간은 타임아웃 × 시도 횟수가 된다. "타임아웃 50ms인데 3번 재시도"면 실제로는 150ms를 붙잡는 셈이라, 캐시 조회에는 재시도를 안 거는 편이 자연스럽다(어차피 폴백 경로가 있으므로).

서킷이 OPEN이면 이제 안전한 건가요? 그동안 DB는 괜찮나요? 추가

아니다. 서킷 OPEN은 "캐시를 건너뛴다"는 뜻이므로, 그 순간 트래픽의 100%가 DB로 간다. DB 입장에서는 §1의 부하 배수가 가장 깨끗하게 전달되는 상태다.

여기서 각 계층이 무엇을 지키는지를 구분해 말할 수 있어야 한다.

  • ①②(타임아웃·서킷)가 지키는 것은 애플리케이션이다 — 스레드가 캐시 대기로 묶이는 것을 막는다.
  • DB를 지키는 것은 ③④⑤다 — 유입량을 깎고(③), 필요한 조회 자체를 줄이고(④), 다른 계층에서 흡수한다(⑤).

그래서 "서킷 브레이커를 걸었습니다"로 답을 끝내면 절반만 답한 것이다. 오히려 서킷이 열린 직후가 DB에 부하가 가장 정직하게 도달하는 구간이므로, 서킷 OPEN 이벤트는 저하 모드를 켜는 트리거로 이어져야 한다(§8).

"캐시 실패는 삼킨다"고 했는데, 캐시 삭제·무효화 실패도 삼켜도 되나요? 시니어 변별 추가

아니다. "삼켜도 된다"는 규칙은 조회(읽기)에만 적용된다. 이유는 무엇을 잃는가가 다르기 때문이다.

  • 조회 실패를 삼키면 잃는 것은 성능뿐이다. 사본을 못 읽었을 뿐, 원본을 읽으면 답은 정확하다.
  • 무효화(삭제) 실패를 삼키면 잃는 것은 정합성이다. DB는 새 값인데 캐시에는 옛 값이 남고, 아무도 그 사실을 모른 채 낡은 값이 계속 서빙된다.

그래서 무효화 실패에는 다른 처방이 붙는다 — 재시도, 실패를 잃어버리지 않도록 큐·아웃박스에 적재, 그리고 최후의 TTL 안전망(무효화가 유실돼도 TTL이 지나면 낡은 값이 사라진다). 어느 것도 "조용히 무시"는 아니다.

정리하면 이렇다 — 캐시는 읽기에서는 best-effort지만, 쓰기(무효화)에서는 best-effort가 아니다. 이 구분을 스스로 짚는 것이 변별 지점이다.

참고로 조회 실패도 "삼키되 반드시 기록한다"는 조건이 붙어 있었다(§5). 로그와 메트릭 없이 조용히 무시하면 캐시가 몇 시간째 죽어 있어도 아무도 모르는 채 DB만 얻어맞는 상태가 된다.

Redis가 복구돼서 다시 떴습니다. 이제 안심해도 되나요? 추가

복구 직후가 오히려 가장 위험한 구간일 수 있다. 비어 있는 캐시는 히트율이 0%이므로, 그 순간의 DB 부하는 캐시가 죽어 있을 때와 똑같다. "Redis 살아났다"는 알람은 DB 부하가 끝났다는 신호가 아니다.

게다가 이 시점에는 조건이 하나 더 나쁘다. 장애 동안 쌓인 재시도와 대기 중이던 요청이 한꺼번에 몰릴 수 있어서, 평소보다 많은 트래픽이 텅 빈 캐시를 통과해 DB로 내려간다.

그래서 복구 절차에 이런 것들이 따라붙는다.

  • 저하 모드를 성급히 끄지 않는다 — 히트율이 어느 정도 올라온 것을 지표로 확인한 뒤에 끈다.
  • 캐시 워밍 — 인기 키부터 미리 채워 넣어 히트율을 인위적으로 끌어올린다.
  • ③의 유입 제어는 마지막에 푼다 — 캐시가 데워지는 동안에도 DB 앞의 문지기는 그대로 서 있어야 한다.

이 cold cache 문제는 배포 직후에도 똑같이 발생한다는 점을 덧붙이면 좋다 — 장애가 아니어도 캐시가 비어 있는 상태로 트래픽을 받는 순간은 주기적으로 찾아온다.

이 방어 계층들 중 하나만 먼저 넣어야 한다면 무엇부터 넣나요? 추가

캐시 호출의 짧은 타임아웃과 예외 격리(①)다. 이유를 비용과 효과로 나눠 말하면 답이 깔끔해진다.

  • 비용이 가장 싸다 — 설정 한 줄과 try/catch 한 겹이다. 새 인프라도, 새 장애점도 추가하지 않는다.
  • 가장 흔한 시나리오를 막는다 — 완전한 다운보다 느려진 캐시가 훨씬 자주 일어나고(§3), 그때 앱 전체를 죽이는 경로가 정확히 이 지점이다.
  • 다른 계층의 전제가 된다 — 서킷 브레이커도 "실패/느림"을 판정하려면 타임아웃이라는 기준선이 먼저 있어야 한다.

그다음 순서를 붙이면 더 좋다 — ② 서킷(낭비 제거와 저하 모드 트리거 확보) → ③ 유입 제어(DB를 실제로 지키는 계층) → ④ 저하 모드(포기할 목록을 평시에 합의) 순이다. ⑤ 로컬 캐시와 ⑥ HA는 값이 크지만 그만큼 새 복잡도(불일치 전파, 운영 부담)를 데려오므로 나중이다.

다만 반드시 덧붙일 단서 — ①만 넣고 멈추면 "폭주를 DB에 전달하는" 상태가 된다. 순서를 말할 때 "어디까지가 미완성인지"를 함께 말하는 것이 중요하다.

한 줄 요약
캐시 장애가 곧 DB 장애가 되는 구조라면 캐시는 가용성을 높인 게 아니라 장애 지점을 추가한 것이므로 — 히트율 90%면 캐시 사망 시 DB가 10배(99%면 100배)를 맞는다는 계산에서 출발해, 캐시 호출엔 정상 응답 시간의 수십 배 수준으로 짧게 잡은 타임아웃과 서킷 브레이커 (느려진 캐시가 죽은 캐시보다 위험한 이유는 요청마다 스레드를 타임아웃까지 붙잡아 캐시와 무관한 API까지 죽이기 때문이다), DB 앞엔 커넥션 풀 상한과 부하 차단(전부 받아 0%가 성공하느니 70%를 살리는 의도적 실패), 그 위에 낡은 스냅샷과 기능 축소로 버티는 성능 저하 모드와 로컬 캐시 완충, HA까지 계층으로 깔되 — 출발점은 "캐시 없이 DB가 몇 %를 견디는지"를 숫자로 알고 초과분을 어디서 떨어뜨릴지 미리 정해두는 것이다.
