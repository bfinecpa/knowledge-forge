Sentinel vs Cluster
고가용성과 샤딩, 그리고 해시 슬롯이 코드에 남기는 청구서

면접 질문: "Redis Sentinel과 Cluster의 차이는? Cluster에서 멀티 키 연산의 제약(해시 슬롯)은?"

핵심 관전 포인트 — Sentinel은 "한 대의 마스터"를 감시하다가 죽으면 복제본을 승격시키는 자동 failover 장치(고가용성)이고, Cluster는 데이터를 16384개 해시 슬롯으로 쪼개 여러 마스터에 나눠 담는 샤딩 + 고가용성 체계다. 즉 Sentinel은 죽어도 서비스가 이어지게, Cluster는 한 대에 다 안 들어가는 데이터·쓰기량을 수평 확장하게 해준다. 대가로 Cluster에서는 여러 키를 한 번에 다루는 연산(MGET, 트랜잭션, Lua)이 같은 슬롯의 키끼리만 가능해진다 — 인프라 확장이 애플리케이션 코드를 바꾸는 대표 사례다.
  • 1
    둘은 다른 문제를 푼다 — Sentinel은 가용성(데이터는 여전히 마스터 1대에 전부, 서버만 여러 대), Cluster는 용량·쓰기 처리량(데이터를 여러 마스터에 분할). Cluster는 failover까지 내장하므로 Sentinel의 일을 포함한다.
  • 2
    해시 슬롯은 간접 계층 — hash % 노드수는 노드를 늘리는 순간 키의 75%가 이사한다. 그래서 키 → 고정 16384 슬롯 → 노드로 한 겹을 끼워, 노드가 바뀌어도 뒤쪽 화살표(슬롯 배정)만 고치게 만든다.
  • 3
    대가는 CROSSSLOT — 원자적 멀티 키 연산은 같은 슬롯일 때만 된다. 해시 태그 {}로 묶거나 앱에서 쪼개야 하고, 그래서 전환은 인프라 작업이 아니라 애플리케이션 프로젝트다.

0. 질문 + 출제 의도

질문: "Redis Sentinel과 Cluster의 차이는? Cluster에서 멀티 키 연산의 제약(해시 슬롯)은?"

출제 의도: Cluster 전환 시 멀티 키 연산(MGET, 트랜잭션)이 깨지는 것은 "인프라 확장이 애플리케이션 코드를 바꾸는" 사례다. 확장 계획을 세울 때 이 제약을 미리 아는 사람과 전환 후에 아는 사람의 차이는 크다 — 두 구성의 목적 차이(가용성 vs 확장)를 구분하고, 전환의 비용을 코드 수준까지 내려가 말할 수 있는지 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "둘 다 Redis 여러 대로 묶는 것" 이라는 뭉뚱그림 → 1절에서 데이터가 나뉘는가를 기준으로 두 구조를 나란히 도식화한다.
② "해시 슬롯은 그냥 Redis가 알아서 나누는 것" 이라는 블랙박스 이해 → 4절에서 mod N이 왜 안 되는지를 숫자로 깔고, 슬롯이 간접 계층임을 보인다.
③ "Cluster로 가면 서버만 늘리면 된다" 는 비용 과소평가 → 8~12절에서 CROSSSLOT → 해시 태그 → 키 마이그레이션으로 이어지는 청구서를 따라간다.

1. 먼저 문제를 구분한다 — 가용성이냐 확장이냐

Sentinel과 Cluster를 "둘 다 Redis를 여러 대로 묶는 것"으로 뭉뚱그리면 이 질문에 답할 수 없다. 둘은 애초에 다른 문제를 푼다. 각각이 던지는 질문 자체가 다르다.

Sentinel이 던지는 질문

"마스터가 죽으면 누가 그것을 알아채고, 복제본 중 하나를 자동으로 승격시키고, 클라이언트에게 새 주소를 알려주는가?"

데이터는 여전히 마스터 한 대에 전부 들어 있다. 서버를 여러 대 띄우지만 데이터를 나누지는 않는다. → 가용성(availability) 문제.

Cluster가 던지는 질문

"데이터가 한 대의 메모리에 안 들어가거나, 쓰기가 한 대의 처리량을 넘으면 어떻게 하는가?"

답은 데이터를 여러 마스터에 나눠 담는 것(샤딩, sharding)이다. 각 마스터에 복제본을 붙여 failover까지 자체 처리하므로 Cluster는 Sentinel이 하던 일을 포함한다.

비유 — 주방장이 쓰러지는 문제 vs 주문이 넘치는 문제 Sentinel은 주방장 한 명에 대기 주방장을 두고, 감독관들이 주방장이 쓰러지는지 지켜보는 구조다. 쓰러지면 대기 주방장이 즉시 자리를 잇는다. 하지만 일은 여전히 한 명이 다 한다 — 주문이 두 배로 늘어도 처리량은 그대로다.
Cluster는 주방을 여러 개로 나누고 메뉴(키)마다 담당 주방을 정해두는 구조다. 주방이 늘어난 만큼 처리량이 는다. 대신 여러 주방의 재료를 한 접시에 담는 요리(멀티 키 연산)가 어려워진다 — 이 제약이 8절부터의 주제다.

한 문장으로 구분하는 법

Sentinel = 같은 데이터를 여러 대가 들고 있다 (복제)  ·  Cluster = 다른 데이터를 여러 대가 나눠 들고 있다 (샤딩 + 복제)

그래서 Sentinel은 한 대가 감당할 수 있는 양 자체를 늘려주지 않는다. 마스터가 죽어도 서비스가 이어지게 할 뿐이다. 이 문장이 11절 선택 기준의 뿌리다.

2. Sentinel — 감시자 여러 대, 정족수, 자동 failover

Sentinel은 Redis 본체가 아니라 별도의 감시 프로세스들이다. 데이터를 저장하지 않고, 마스터와 복제본을 지켜보는 일만 한다. 보통 3대 이상 홀수로 띄우는데, 왜 여러 대이고 왜 홀수인지가 이 절의 핵심이다.

2-1. 왜 감시자가 여러 대인가 — 한 대의 시야는 믿을 수 없다

감시자가 한 대뿐이라면, 그 감시자가 "마스터가 응답이 없다"고 판단했을 때 그것이 정말 마스터가 죽은 것인지, 아니면 감시자와 마스터 사이의 네트워크만 끊긴 것인지 구분할 방법이 없다. 마스터는 멀쩡히 살아서 다른 모든 클라이언트의 요청을 처리하고 있는데, 이 감시자 하나가 자기 네트워크 문제로 오판해 멀쩡한 마스터를 끌어내리고 failover를 일으킬 수 있다.

한 대의 시야는 그 한 대의 네트워크 상태와 구분되지 않는다

그래서 Sentinel은 판정을 두 단계로 나눈다.

SDOWN — 주관적 다운
Subjectively Down
"내가 보기에 마스터가 응답이 없다." 감시자 한 대의 개인 의견이다. 이것만으로는 아무 일도 일어나지 않는다.
ODOWN — 객관적 다운
Objectively Down
감시자들끼리 "너도 안 보이니?"라고 물어서 정해진 수 이상이 동의했을 때 내려지는 판정. 여기부터 failover가 시작된다.

여기서 그 "정해진 수"가 정족수(quorum)다. 즉 정족수란 마스터가 죽었다고 결론 내리기 위해 동의해야 하는 최소 감시자 수다. Sentinel 3대에 quorum 2로 설정했다면, 두 대 이상이 "안 보인다"고 해야 failover가 시작된다. 한 대만의 오판으로는 아무 일도 안 일어난다.

2-2. 여기에 한 겹이 더 있다 — 판정과 실행은 다른 문턱을 넘는다

객관적 다운 판정과 별개로, 실제 failover를 수행할 Sentinel 리더를 뽑을 때는 전체 Sentinel의 과반이 필요하다. 그래서 quorum을 아무리 낮게 잡아도 Sentinel 다수가 서로를 못 보는 상황에서는 failover가 진행되지 않는다.

홀수로 띄우는 이유가 여기 있다 — 네트워크가 둘로 갈렸을 때 한쪽만 과반이 되도록 만들어, 양쪽이 동시에 failover를 벌이는 일을 줄이기 위해서다.

암기 — 문턱이 두 개다

판정의 문턱 = quorum
"죽었다"고 결론내는 데 필요한 동의 수. 설정값이다.
실행의 문턱 = 전체의 과반
리더를 뽑아 실제로 승격시키는 데 필요한 수. 설정으로 못 낮춘다.
"판정은 정족수, 실행은 과반" — 그래서 quorum을 1로 낮춰도 소수 구획은 failover하지 못한다
Sentinel의 한계는 명확하다 쓰기와 메모리는 여전히 마스터 한 대의 한계를 넘지 못한다. 읽기는 복제본으로 분산할 수 있지만(복제 지연을 감수한다면), 쓰기 확장은 안 된다. 마스터가 죽어도 서비스가 이어지게 할 뿐, 마스터가 감당할 수 있는 양 자체를 늘려주지는 않기 때문이다.

3. 스플릿 브레인 — failover가 만들어내는 위험

Sentinel을 이야기할 때 반드시 따라오는 개념이 있다. 스플릿 브레인(split-brain, 갈라진 뇌)이란 네트워크가 둘로 갈려서 양쪽이 각자 자기 마스터를 갖게 되는 상황이다. 하나여야 할 뇌가 둘이 됐다는 뜻의 이름이다.

3-1. 완화책 — min-replicas-to-write, 그리고 그 대가

min-replicas-to-write
"복제본이 N대 이상 붙어 있을 때만 쓰기를 받는다"는 설정. 고립된 구 마스터는 복제본을 잃은 상태이므로 이 조건에 걸려 스스로 쓰기를 거부하게 된다.
min-replicas-max-lag
함께 쓰는 짝. "몇 초 이내에 응답한 복제본만 살아 있는 것으로 센다"를 정한다. 연결만 남고 응답하지 않는 복제본을 머릿수에서 빼는 장치다.

이 둘이 걸려 있으면 갈라진 동안 고립된 쪽에 쌓이는 쓰기 자체가 없어져 유실 폭이 줄어든다. 다만 대가를 함께 말해야 답이 완성된다.

이 설정은 유실을 없애는 것이 아니라 "유실을 에러로 바꾸는" 것이다

조용한 유실 → 눈에 보이는 쓰기 실패로 형태만 바뀔 뿐, 요청이 다 성공하게 되지는 않는다. 그래서 애플리케이션 쪽에는 이 실패를 재시도로 견디는 설계가 반드시 함께 가야 한다. "인프라 설정 하나로 해결됩니다"라고 답하면 절반짜리다.

4. 왜 해시 슬롯인가 — 노드 수로 나누면 안 되는 이유

Cluster의 문제는 단순해 보인다. 키를 여러 노드에 나눠 담아야 하니, 어떤 키가 어느 노드로 갈지 정하는 규칙이 필요하다. 가장 먼저 떠오르는 방법은 키를 정수로 바꿔 노드 수로 나눈 나머지를 쓰는 것이다.

naive 계산은 빠르고 분포도 균등하다 — 노드 수가 고정이라면
노드 번호 = hash(key) mod N     # N = 노드 수

# 노드가 3대면 mod 3 으로 0, 1, 2번 노드에 고르게 흩어진다.
# 그런데 노드를 하나 추가하는 순간 규칙 자체가 바뀐다 → 거의 모든 키의 소속이 바뀐다

그래서 Redis Cluster는 키를 노드에 직접 매핑하지 않는다. 대신 중간에 한 겹을 끼운다.

해시 슬롯을 한 문장으로 외운다

간접 계층을 하나 끼워서 변화의 범위를 가둔다

비유 — 우편번호. 택배사가 주소(키)를 배송센터(노드)에 직접 대응시켜 두면, 센터를 하나 새로 지을 때마다 전국 모든 주소의 담당 센터를 다시 계산해야 한다. 그래서 실제로는 주소를 우편번호에 먼저 매핑하고, 우편번호 구간을 센터에 배정한다. 센터가 늘면 우편번호 구간 배정표만 고치면 되고, 주소 → 우편번호 규칙은 손대지 않는다. 16384개 슬롯이 바로 이 우편번호다.

5. 슬롯 계산과 배정 — 조회가 아니라 계산으로 찾는다

공식 이 한 줄이 Cluster 라우팅의 전부다
슬롯 번호 = CRC16(key) mod 16384      # 결과 범위: 0 ~ 16383

CRC16은 임의의 문자열을 16비트 정수 하나로 바꾸는 체크섬 함수다. 원래는 데이터 전송 오류를 검출하려고 만든 계산식인데, 빠르고 결과가 고르게 흩어져서 여기서는 키를 숫자로 바꾸는 용도로 쓰인다. 암호학적 해시가 아니므로 보안 목적은 없고, 필요한 성질은 "같은 키는 항상 같은 숫자, 다른 키는 되도록 다른 숫자"뿐이다. 16비트 정수의 범위는 0~65535인데 여기에 mod 16384를 하니 결과가 슬롯 번호가 된다.

숫자 세 개만 외운다

16384
슬롯 개수 (고정)
214 — 클러스터의 상수. 노드 수와 무관하다
0 ~ 16383
슬롯 번호 범위
모든 슬롯에 주인이 있어야 클러스터가 정상 상태다
CRC16
키 → 숫자 변환
체크섬 함수. 빠르고 고르게 흩어지는 것이 채택 이유

6. MOVED와 ASK — 클라이언트가 엉뚱한 노드에 물었을 때

클라이언트가 캐싱한 배정표는 낡을 수 있다. 리샤딩으로 슬롯이 옮겨갔는데 클라이언트가 아직 모르면, 그 키를 더 이상 갖고 있지 않은 노드에 명령을 보내게 된다. 이때 노드는 에러를 내고 마는 대신 "그 키는 저쪽에 있다"고 알려준다. 응답이 두 종류인데, 둘의 차이가 이 절의 전부다.

MOVED / ASK 한 줄 암기

MOVED = 이사 완료, 주소록을 고쳐라  /  ASK = 이사 중, 이번 건만 새 주소로 가라

연상법 — MOVED는 Map을 고친다(Modify the map). ASK는 A once, 딱 한 번만 물어본다. 앞 글자로 붙여두면 시험장에서 헷갈리지 않는다.

7. 리샤딩과 내장 failover — 노드를 늘리고 줄이는 일

리샤딩(resharding)은 슬롯을 노드 사이에서 옮기는 작업이다. 노드를 추가하면 기존 노드들에게서 슬롯을 조금씩 떼어 새 노드에 주고, 노드를 빼면 그 노드의 슬롯을 남은 노드들에 나눠준다. 4절에서 본 대로 이동하는 슬롯에 속한 키만 영향을 받고, 나머지는 그대로다. 이동 중에도 클러스터는 ASK 리다이렉션 덕분에 계속 서비스한다.

7-1. failover는 Cluster가 자체 수행한다

각 마스터에 복제본을 붙여두면, 마스터가 응답하지 않을 때 다른 마스터들이 그 사실에 동의하고 복제본을 승격시킨다. Sentinel 같은 별도 프로세스가 필요 없다 — 노드들이 서로를 감시하는 역할까지 겸하기 때문이다. 그래서 Cluster는 샤딩 + Sentinel 역할까지 내장한 구성이라고 말한다.

여기서 조심할 것 — 복제본 없는 마스터는 "부분 서비스 불가"의 씨앗이다

어떤 마스터의 슬롯을 아무도 담당하지 않게 되면, 그 슬롯에 속한 키에 대한 요청은 전부 실패한다. 마스터 하나가 죽었는데 복제본이 없으면 클러스터의 일부 키 공간이 통째로 서비스 불가가 된다는 뜻이다. "노드가 3대 중 1대만 죽었으니 2/3는 돌아가겠지"가 아니라, 담당자가 사라진 슬롯 범위는 조회도 쓰기도 안 된다.

Cluster를 쓴다는 것 = 마스터 대수만큼 복제본도 함께 늘어난다는 뜻 (마스터 3대 → 최소 6대) — 이것이 운영 비용의 실체

8. CROSSSLOT — 인프라가 코드를 바꾸는 지점 면접의 핵심

여러 키를 원자적으로 다루는 연산은 Cluster에서 모든 키가 같은 슬롯에 있을 때만 가능하다. 이유는 근본적이다. 슬롯이 다르면 키가 서로 다른 노드에 있고, 서로 다른 노드에 흩어진 데이터를 하나의 원자 연산으로 묶을 방법이 없다. 노드 A와 노드 B에 걸친 "전부 성공 아니면 전부 실패"를 만들려면 분산 트랜잭션이 필요한데, Redis는 그런 것을 제공하지 않는다. 그래서 아예 시도조차 하지 않고 에러로 거절한다.

before 단일 Redis(Sentinel 구성)에서는 잘 돌던 코드
// Sentinel 구성: 데이터가 마스터 한 대에 다 있으므로 아무 문제 없다
mget("user:1:name", "user:2:name", "user:3:name");Cluster에서 폭발
//   (error) CROSSSLOT Keys in request don't hash to the same slot

// 같은 제약을 받는 것들 — 전부 "여러 키를 한 번에" 다루는 연산이다
//   MULTI / EXEC 트랜잭션, Lua 스크립트(KEYS가 여러 개), SINTERSTORE, RENAME ...

Cluster 전환 시 깨지는 멀티 키 연산 — 코드 검색용 목록

MGET / MSET
여러 키를 한 번에 읽고 쓰기
MULTI / EXEC
여러 키에 걸친 트랜잭션
Lua (KEYS 다수)
스크립트가 건드리는 키가 여러 슬롯
RENAME
원본 키와 대상 키가 다른 슬롯
SINTERSTORE 등
집합 연산 + 결과 저장 (SUNIONSTORE, SDIFFSTORE)
ZUNIONSTORE 등
여러 Sorted Set을 묶는 연산

기억할 규칙 하나 — "명령 하나가 키를 두 개 이상 만진다면 전부 의심 대상"이다. 개별 명령 이름을 외우기보다 이 규칙으로 코드베이스를 훑는 편이 빠지는 것이 없다.

9. 해법 1 — 해시 태그로 같은 슬롯에 모으기

Redis는 이 제약을 우회할 문법을 제공한다. 키 이름에 중괄호 {}가 있으면, 슬롯 계산에 키 전체가 아니라 중괄호 안쪽만 사용한다. 이 중괄호 부분을 해시 태그(hash tag)라고 부른다.

해시 태그 규칙 — 조건을 정확히 외운다

키에 {가 있고 그 뒤에 }가 있으며 그 사이 내용이 비어 있지 않으면, 그 사이의 문자열만 CRC16에 넣는다. 조건에 안 맞으면(중괄호가 없거나, 짝이 없거나, 안이 비었으면) 키 전체를 해싱한다.

키실제로 해싱되는 문자열이유
{user:42}:cartuser:42정상적인 해시 태그
user:42:cartuser:42:cart중괄호가 없다 → 키 전체
{}:cart{}:cart중괄호 안이 비었다 → 키 전체
{user}:{42}user첫 {와 그 뒤 첫 } 사이만 본다
before 슬롯이 제각각
// 같은 사용자의 데이터인데도
// 키 전체를 해싱하므로 소속이 흩어진다
"user:42:cart"  // CRC16(전체) → 슬롯 X
"user:42:wish"  // CRC16(전체) → 슬롯 Y

// → MGET, MULTI, Lua로 함께 다룰 수 없다
//    (error) CROSSSLOT ...
after 중괄호 안쪽만 해싱
// 두 키가 반드시 같은 슬롯에 놓인다
// = 반드시 같은 노드에 있다
"{user:42}:cart"  // CRC16("user:42") → 슬롯 S
"{user:42}:wish"  // CRC16("user:42") → 슬롯 S

// → MULTI/EXEC, Lua로 원자적으로 다룰 수 있다
//    (스크립트의 KEYS도 같은 슬롯이 된다)

핵심은 "함께 원자적으로 다뤄야 하는 키들을 의도적으로 같은 슬롯에 배치하는" 설계 도구라는 것이다. 슬롯 배치를 우연에 맡기지 않고 키 이름으로 통제한다.

9-1. 태그를 굵게 잡으면 샤딩 자체가 무의미해진다

해시 태그의 유일한 원칙

원자성이 꼭 필요한 최소 단위로만 묶는다

그 단위는 "한 번의 연산에 같이 들어가는 묶음"이다 — 사용자 1명, 주문 1건, 상품 1개. 태그가 커질수록 원자성은 편해지고 분산은 무너진다. 이 둘은 정확히 반대 방향으로 당기는 힘이라, 태그 설계는 어디까지 원자성이 필요한가를 정하는 작업과 같다.

10. 해법 2 — 애플리케이션에서 쪼개기, 그리고 그 외 깨지는 것들

모든 멀티 키 연산에 해시 태그를 붙일 필요는 없다. 먼저 물어야 할 것은 "이 연산에 원자성이 정말 필요한가"다. 여기서 답이 갈린다.

라이브러리가 MGET을 대신 쪼개준다면 CROSSSLOT은 사라진 것인가 아니다. 에러가 사라졌을 뿐 원자성은 돌아오지 않는다. 노드별로 나눠 보낸 요청은 각각 다른 시점에 처리되므로, 그 사이에 다른 클라이언트가 값을 바꾸면 서로 다른 시점의 값이 한 결과에 섞인다. 조회라면 대부분 괜찮지만, "이 값들이 같은 순간의 상태여야 한다"는 요구가 있는 곳이라면 라이브러리의 분할 실행은 해결이 아니라 은폐다.

10-1. (가산점 포인트) 그 외 Cluster 전환 시 깨지는 것들 가산점

CROSSSLOT만 이야기하면 절반이다. 멀티 키가 아닌데도 깨지는 것들이 있고, 이것들은 대개 배치와 운영 스크립트에 숨어 있어 배포 후에야 발견된다.

SELECT (DB 번호)
0번만 지원한다. 단일 Redis에서 "개발용은 1번 DB, 캐시는 2번 DB" 식으로 논리적 분리를 해뒀다면 그 구조가 통째로 사라진다. 접두어(prefix)로 대체해야 한다.
SCAN (키스페이스 순회)
한 노드에 SCAN을 걸면 그 노드가 가진 슬롯의 키만 나온다. 전체를 훑는 배치가 있다면 노드 목록을 받아 순회하도록 고쳐야 한다.
파이프라인
여러 명령을 몰아 보내는 파이프라인은 한 노드에 대해서만 성립한다. 키가 흩어져 있으면 노드별로 쪼개져 왕복 절감 효과가 줄어든다.

이 셋의 공통점 — "전체를 하나로 보던 가정"이 깨진 것이다

단일 Redis에서는 인스턴스 = 하나의 키 공간 = 하나의 접속이었다. Cluster에서는 그 셋이 전부 노드 수만큼 쪼개진다. 그래서 "전체를 대상으로" 무언가를 하던 코드(DB 번호로 나누기, 전수 순회, 한 번에 몰아 보내기)가 전부 손봐야 할 목록에 오른다. CROSSSLOT은 이 붕괴가 가장 시끄럽게 드러나는 한 지점일 뿐이다.

11-1. 양쪽으로 흔한 실수

함정 "확장 대비"로 처음부터 Cluster를 까는 것

아직 필요 없는 복잡도(노드 대수, 복제본, 리샤딩 운영, 멀티 키 제약)를 미리 사는 셈이다. 트래픽이 그 지점에 도달하지 않으면 그 비용은 영영 회수되지 않는다.

함정 반대의 실수 — 전환이 재개발이 되는 것

Sentinel에서 멀티 키 연산을 마음껏 쓰다가, 나중의 Cluster 전환이 사실상 재개발이 된다. 이쪽이 더 아프다 — 이미 쌓인 키와 코드를 전부 되돌려야 하기 때문이다.

가산점 절충안 — 지금은 Sentinel이어도 키 이름은 미리 Cluster용으로

키 설계 단계에서부터 해시 태그 규칙을 잡아두면 전환 비용이 크게 줄어든다. 지금 당장은 Sentinel이라 아무 효과가 없는 {user:42}:cart 같은 키 이름을 미리 쓰는 것이다.

비용은 거의 0인데, 나중에 키 마이그레이션이라는 가장 무거운 작업을 건너뛸 수 있다

단일 Redis에서 {}는 그냥 이름의 일부일 뿐 아무 동작도 하지 않는다. 즉 지금은 무해하고 나중에 유효해지는 결정이다 — 이런 선택을 골라낼 줄 아는 것이 설계 감각이다.

12. Sentinel → Cluster 전환, 무엇부터 점검하나 시니어 변별

네 갈래로 답한다. 순서 자체가 "이것은 인프라 작업이 아니다"라는 메시지를 담고 있다.

1
코드 전수 조사 — MGET/MSET, MULTI/EXEC, Lua 스크립트, RENAME, SINTERSTORE 등 멀티 키 연산 사용처를 전부 찾는다. 같은 슬롯 보장이 없으면 전부 CROSSSLOT으로 깨진다. 이것이 가장 먼저인 이유는, 여기서 나온 목록이 뒤의 작업 범위를 결정하기 때문이다.
2
키 설계 변경 (= 사실상 마이그레이션) — 원자성이 필요한 묶음에 해시 태그를 도입한다. 그런데 태그를 붙이면 키 이름이 바뀌고, 키 이름이 바뀌면 슬롯이 바뀐다. 기존 키를 읽어 새 이름으로 다시 쓰는 작업과, 그동안 양쪽 키를 함께 다루는 과도기 코드가 필요하다. 전환 프로젝트에서 가장 무거운 부분이 여기다.
3
클라이언트 교체와 설정 — 쓰는 클라이언트가 클러스터 프로토콜(MOVED/ASK)을 이해하는지, 슬롯 배정표를 캐싱하고 갱신하는지, MGET과 파이프라인을 노드별로 분할 실행해 주는지 확인한다. 라이브러리 버전과 설정을 함께 봐야 한다.
4
운영 체계 재구성 — SELECT로 다중 DB를 쓰던 곳을 접두어 방식으로 걷어내고, 키스페이스를 순회하는 배치(SCAN)를 노드별 실행으로 고치고, 모니터링·알림을 노드 단위로 재구성한다. 백업과 장애 대응 절차도 노드 수만큼 늘어난다.

순서를 통째로 외우는 장치

코 → 키 → 클 → 운  :  코드 전수 조사 → 키 설계(마이그레이션) → 클라이언트 → 운영 체계

이 순서가 뒤집히면(먼저 노드를 띄우고 나중에 코드를 본다면) 운영 중인 클러스터 위에서 키 마이그레이션을 하게 된다. 앞의 두 단계가 뒤의 두 단계를 위한 범위 산정이라는 점이 이 순서의 이유다.

마무리 문장: "전환은 인프라 작업이 아니라 애플리케이션 프로젝트다."

13. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼쳐서 맞춰 본다. 답을 눈으로 읽는 것보다 인출 훈련이 훨씬 오래 간다.

failover가 일어나는 몇 초 동안 쓰기는 어떻게 되나요?힌트: 두 가지가 일어난다. 구분해서 답한다

실패와 유실, 두 가지가 일어난다. 이 둘을 구분해 답하는 것이 포인트다.

① 실패는 예상 가능한 쪽이다. 새 마스터가 승격될 때까지의 짧은 시간 동안 쓰기는 에러나 타임아웃을 받는다. 클라이언트가 새 마스터 주소를 알아내는 데도 시간이 조금 더 걸린다.

② 더 위험한 것은 유실이다. Redis 복제는 비동기다 — 마스터는 복제본의 확인을 기다리지 않고 클라이언트에게 먼저 OK를 응답한다. 그래서 마스터가 받아서 OK까지 응답했지만 복제본에는 아직 도착하지 않은 쓰기가 항상 존재하고, 그 상태에서 마스터가 죽어 복제본이 승격되면 그 쓰기들은 사라진다. 클라이언트는 성공 응답을 받았는데 데이터는 없는 상태가 된다.

여기에 스플릿 브레인까지 얹으면 답이 완성된다(3절). 네트워크 분리로 구 마스터가 잠시 살아서 쓰기를 계속 받으면 마스터가 둘이 되고, 복구 시 한쪽 데이터가 통째로 버려진다.

완화책으로 min-replicas-to-write(복제본 N대가 살아 있을 때만 쓰기 허용)를 언급하면 좋고, 마지막으로 "이 몇 초의 실패·유실을 견디는 재시도·멱등 설계가 애플리케이션 쪽에 필요하다"까지 가면 강하다.

인프라는 100%를 보장하지 못한다 — 그것을 전제로 애플리케이션을 설계하는 태도를 보여주는 대목
해시 태그를 쓰면 다 해결되나요?힌트: 슬롯은 통째로만 움직인다

아니다. 태그로 묶인 키들은 같은 슬롯에 들어가고, 슬롯은 통째로만 이동하므로 그 묶음은 영원히 같은 노드에 산다.

여기서 두 가지 문제가 나온다. 묶음이 커지면 그 노드만 메모리와 트래픽이 몰리는 핫스팟이 되고, 더 나쁜 것은 그것을 리샤딩으로 쪼갤 수 없다는 점이다. 리샤딩은 슬롯 단위로만 데이터를 옮기는데 그 키들은 전부 한 슬롯 안에 있으니, 노드를 아무리 늘려도 나뉘지 않는다. 해결하려면 키 이름 자체를 바꿔야 하고, 그것은 곧 마이그레이션이다.

그래서 원칙은 둘이다. 원자성이 필요한 최소 단위로만 묶는다. 그리고 큰 집계는 태그로 묶지 말고 애플리케이션에서 합친다.

해시 태그는 "분산을 포기하는 대가로 원자성을 사는" 거래 — 공짜 옵션이 아니다
Cluster에서 MULTI/EXEC 트랜잭션과 Lua는 못 쓰나요?힌트: 조건부로 가능하다 → 그 조건을 설계로 만든다

쓸 수 있다 — 단, 관련된 키가 전부 같은 슬롯일 때만. Lua 스크립트도 KEYS로 넘기는 키들이 같은 슬롯이어야 한다.

여기서 한 걸음 더 나가면 좋다. 분산 락, 선착순 발급처럼 원자성이 본질인 설계는 Cluster 전제라면 처음부터 "연산 단위 = 슬롯 단위"가 되도록 키를 설계해야 한다. 예를 들어 한 상품의 재고와 발급 이력을 Lua로 함께 다뤄야 한다면, 두 키를 {product:77}:stock과 {product:77}:issued처럼 같은 태그로 묶어두는 것이 설계의 출발점이다.

키 이름이 곧 원자성 경계가 된다 — 이 감각을 보여주면 변별된다
읽기 확장만 필요하면 어떤 구성이 낫나요?힌트: 쓰기가 한 대로 되는지부터 본다 → 조건 하나가 붙는다

쓰기는 한 대로 충분하고 읽기만 많다면 Cluster까지 갈 필요가 없다. Sentinel 구성에 복제본을 붙이고 읽기를 복제본으로 분산하는 편이 훨씬 단순하다. 멀티 키 연산 제약도 없다.

단, 조건이 하나 붙는다. 복제는 비동기라 방금 쓴 값이 복제본에서 아직 안 보일 수 있다(복제 지연). "내가 방금 쓴 글이 목록에 없어요" 같은 문의로 이어지는 지점이다.

그래서 읽기 분산 대상은 지연을 허용하는 조회로 한정한다고 답한다. 인기 목록·통계·추천처럼 몇백 밀리초 늦어도 되는 조회는 복제본으로 보내고, "방금 내가 한 행동의 결과를 확인하는 조회"는 마스터로 보낸다. 이 분류를 코드에서 어떻게 하는지(읽기 전용 커넥션을 따로 두는 등)까지 말하면 실무 감각이 드러난다.

덧붙일 거리 — Cluster에서도 복제본 읽기는 기본이 아니다. 복제본에 붙은 연결에서 READONLY를 선언해야 그 복제본이 자기 마스터가 담당하는 슬롯의 읽기를 처리한다. 선언하지 않으면 마스터로 가라는 MOVED가 돌아온다.

Sentinel 구성에서 Cluster로 전환한다면 무엇부터 점검하나요? 시니어 변별힌트: 네 갈래. 순서 자체가 메시지다

1. 코드 전수 조사 — 멀티 키 연산 사용처를 전부 찾는다. 여기서 나온 목록이 뒤의 작업 범위를 결정하므로 가장 먼저다.

2. 키 설계 변경 — 해시 태그를 도입한다. 태그를 붙이면 키 이름이 바뀌고, 이름이 바뀌면 슬롯이 바뀐다 — 즉 사실상 키 마이그레이션이다. 과도기에 양쪽 키를 함께 다루는 코드까지 필요하다. 전환에서 가장 무거운 부분.

3. 클라이언트 교체와 설정 — MOVED/ASK 처리, 슬롯 배정표 캐싱·갱신, MGET·파이프라인의 노드별 분할 실행 지원 여부를 확인한다.

4. 운영 체계 재구성 — SELECT 제거(접두어로 대체), SCAN 배치의 노드별 실행, 노드 단위 모니터링·백업·장애 대응 절차.

마무리: "전환은 인프라 작업이 아니라 애플리케이션 프로젝트다."
슬롯이 왜 하필 16384개인가요?힌트: 이 질문의 정답은 "아는 만큼만 말하는 것"이다

확신 없는 이유를 지어내지 않는 것이 이 질문의 정답이다. 말할 수 있는 사실은 이것이다.

Cluster의 노드들은 서로 상태를 주고받는 통신(클러스터 버스)에서 "어느 노드가 어떤 슬롯을 갖고 있는지"를 비트맵으로 실어 보낸다. 슬롯 하나당 1비트이므로 16384비트 = 2048바이트, 즉 2KB다. 슬롯 수를 크게 잡을수록 이 정보가 커지고 노드 간 통신 부담이 늘어난다는 점과 관련이 있다.

여기까지만 말하고, 그 이상의 구체적 근거를 확신 없이 덧붙이지 않는 편이 낫다.

"정확히 아는 부분과 모르는 부분을 구분해 말하는 것" 자체가 면접에서는 감점이 아니라 신뢰 요인이다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

Sentinel을 2대만 띄우면 무엇이 문제인가요? 약점 겨냥힌트: 문턱이 두 개였다

failover를 실행할 수 없는 구성이 되기 쉽다. 판정(quorum)은 설정으로 낮출 수 있지만, 실제 승격을 수행할 리더를 뽑는 데는 전체 Sentinel의 과반이 필요하기 때문이다.

2대라면 과반은 2다. 즉 Sentinel 한 대만 죽어도(또는 두 대가 서로 못 보게 되어도) 남은 한 대로는 과반을 못 채워 failover가 진행되지 않는다. 감시자를 하나 늘렸지만 고장 지점만 늘린 셈이다.

3대면 과반이 2이므로 한 대가 죽어도 남은 2대로 승격이 가능하다. "홀수로 3대 이상"이 관례가 된 이유가 이것이고, 실무에서는 세 대를 서로 다른 장애 도메인(호스트·랙·가용영역)에 흩어 놓는 것까지 함께 말하면 좋다 — 3대를 한 서버에 띄우면 대수만 3이지 고장은 하나다.

quorum을 1로 낮추면 failover가 빨라지나요?힌트: 빨라지는 것과 위험해지는 것을 나눠 말한다

판정은 빨라지지만, 실행은 빨라지지 않는다. quorum은 ODOWN(죽었다고 결론 내기)의 문턱일 뿐이고, 그 뒤 리더 선출은 여전히 전체의 과반을 요구하기 때문이다. 그래서 quorum을 1로 낮춰도 소수 구획에 갇힌 Sentinel은 failover를 못 한다.

대신 위험은 확실히 커진다. 감시자 한 대의 네트워크 문제만으로 ODOWN이 선언되므로, 멀쩡한 마스터를 끌어내리는 불필요한 failover가 늘어난다. 그리고 모든 failover에는 비동기 복제로 인한 유실 구간이 딸려 있다(첫 꼬리질문).

불필요한 failover는 "무해한 오작동"이 아니라 매번 유실 가능성을 동반하는 사건이다
Cluster에서도 스플릿 브레인이 생기나요? 시니어 변별힌트: 완전히 막히지는 않지만 창이 닫힌다

구조는 비슷하되, 소수 구획이 스스로 멈추는 장치가 들어 있다. 네트워크가 갈리면 다수 구획의 마스터들이 합의해 고립된 마스터의 복제본을 승격시킨다. 그동안 고립된 구 마스터가 계속 쓰기를 받으면 Sentinel과 같은 그림이 된다.

차이는 이것이다. 다수 구획과 통신하지 못하는 마스터는 cluster-node-timeout이 지나면 스스로 요청을 거부한다. 자기가 소수 쪽에 있다는 것을 노드 간 통신 두절로 감지하기 때문이다. 그래서 유실이 쌓일 수 있는 창(window)이 그 타임아웃 안쪽으로 제한된다.

다만 그 창 안에서 받은 쓰기는 여전히 사라질 수 있다. 복제가 비동기인 이상 "OK를 받았지만 승격된 새 마스터에는 없는 쓰기"는 어느 구성에서도 남는다. "완전히 막았다"가 아니라 "노출 시간을 설정으로 통제한다"가 정확한 답이다.

클라이언트 라이브러리가 MGET을 알아서 쪼개준다면, CROSSSLOT은 더 이상 문제가 아니지 않나요? 함정힌트: 사라진 것은 에러이지 보장이 아니다

사라진 것은 에러이지 원자성이 아니다. 라이브러리는 키를 슬롯별로 그룹핑해 노드마다 요청하고 결과를 순서대로 합쳐 준다. 편의는 얻지만, 그 요청들은 서로 다른 시점에 각각 처리된다.

그래서 결과에 서로 다른 순간의 값이 섞일 수 있다. 단순 조회라면 대개 문제가 없지만, "이 값들이 같은 순간의 상태여야 한다"는 요구가 있는 곳(잔액과 한도, 재고와 예약 수)에서는 해결이 아니라 은폐다.

덧붙일 것 — 쓰기 쪽은 더 명확하다. MSET을 노드별로 쪼개면 일부 노드만 성공하고 일부는 실패하는 부분 성공이 가능해진다. 단일 Redis에서는 존재하지 않던 상태다. 원자성이 필요하면 해시 태그로 같은 슬롯에 모으거나, 그 연산을 DB로 옮겨야 한다.

키에 중괄호가 여러 개 있으면 어디가 해시 태그인가요? {}만 있으면요?힌트: 규칙을 조건 그대로 적용한다

규칙은 "첫 {와 그 뒤에 나오는 첫 } 사이, 단 그 사이가 비어 있지 않을 것"이다.

  • {user}:{42} → user만 해싱한다. 뒤의 {42}는 보지 않는다.
  • {}:cart → 중괄호 사이가 비었으므로 규칙에 해당하지 않는다 → 키 전체를 해싱한다.
  • {user:42 (닫는 괄호 없음) → 짝이 없으므로 키 전체를 해싱한다.

실무적 함의가 하나 있다. 키에 사용자 입력이 섞여 들어가면 의도치 않은 태그가 만들어질 수 있다. 검색어나 파일명처럼 중괄호가 들어갈 수 있는 값을 키에 그대로 붙이면, 우연히 같은 태그를 공유해 특정 슬롯으로 몰리는 사고가 난다. 키 조립 지점을 한 곳으로 모으고 입력값을 정제하는 것이 방어책이다.

Lua 스크립트에서 KEYS로 선언하지 않고 스크립트 안에서 키 이름을 만들어 쓰면 어떻게 되나요? 시니어 변별힌트: 라우팅은 실행 전에 결정된다

Cluster에서는 성립할 수 없는 코드다. 클러스터에서 명령을 어느 노드로 보낼지는 실행 전에 키 이름으로 결정된다. 스크립트가 실행 도중 키 이름을 만들어 낸다면, 클러스터는 그 키가 이 노드의 슬롯인지 검증할 방법이 없다.

그래서 스크립트가 만지는 키는 전부 KEYS로 선언해야 하고, 그 키들이 모두 같은 슬롯이어야 한다. 선언하지 않은 키에 접근하는 스크립트는 클러스터 환경에서 거부되거나, 단일 인스턴스에서는 돌지만 클러스터에서만 깨지는 형태가 된다 — 테스트 환경이 단일 Redis라면 운영에서만 터지는 전형적인 케이스다.

실무 결론은 명확하다. Cluster를 쓸 계획이 있다면 Lua는 처음부터 "KEYS 선언 + 같은 해시 태그"를 규약으로 잡는다. 나중에 고치는 것보다 훨씬 싸다.

클라이언트는 슬롯 배정표를 어떻게 얻고 언제 갱신하나요?힌트: 최초 조회 + 리다이렉션 신호

접속 시 클러스터에 물어서 받아 캐싱한다. CLUSTER SLOTS나 CLUSTER NODES 같은 명령으로 "어느 슬롯 범위를 어느 노드가 담당하는지"를 받아 메모리에 들고 있다가, 명령마다 키로 슬롯을 계산해 곧장 해당 노드로 보낸다.

갱신 계기는 MOVED 응답이다. 배정이 바뀌었다는 신호이므로 클라이언트는 배정표를 다시 받아 온다(ASK는 갱신 계기가 아니다 — 6절). 그래서 MOVED가 계속 쏟아진다면 클라이언트가 갱신을 제대로 하지 않고 있다는 뜻이고, 매 요청이 2회 왕복이 되어 지연이 눈에 띄게 오른다.

이것이 12절 3단계에서 "클라이언트 라이브러리를 확인하라"고 한 이유다. 클러스터 지원이 없는 라이브러리는 MOVED를 그냥 에러로 애플리케이션에 던져 버린다.

Cluster에서 노드 하나가 죽었는데 어떤 키는 되고 어떤 키는 에러가 납니다. 왜죠?힌트: 실패의 단위가 인스턴스가 아니다

죽은 마스터가 담당하던 슬롯 범위만 서비스 불가가 됐기 때문이다. Cluster에서 장애의 단위는 인스턴스 전체가 아니라 슬롯 구간이다. 그 구간에 속한 키만 실패하고 나머지는 정상 동작하므로, "일부 기능만 죽은" 것처럼 보인다.

원인은 둘 중 하나다. ① 그 마스터에 복제본이 없었다 — 승격시킬 대상이 없으니 슬롯이 주인을 잃는다. ② 복제본이 있었지만 승격이 아직 진행 중이다 — 이 경우는 잠시 뒤 회복된다.

여기서 답을 운영 결론까지 끌고 가면 좋다. Cluster의 가용성은 "마스터 수"가 아니라 "모든 슬롯에 대기 후보가 있는가"로 결정된다. 그래서 마스터를 늘릴 때는 복제본도 같이 늘어야 하고, 모니터링도 인스턴스 생사가 아니라 슬롯 커버리지(빈 슬롯이 있는가)를 봐야 한다.

Cluster를 쓰면 트래픽이 자동으로 고르게 분산되나요? 함정힌트: 슬롯이 고르다는 것과 부하가 고르다는 것은 다르다

슬롯 개수가 고른 것과 부하가 고른 것은 다르다. CRC16은 키를 고르게 흩어주지만, 그것은 키의 개수 기준이다. 실제 부하는 어떤 키가 얼마나 자주 읽히고 얼마나 큰가에 달려 있다.

그래서 쏠림은 세 방향에서 생긴다. ① 핫 키 — 전체 트래픽의 상당량이 특정 키 하나(인기 상품, 메인 배너)에 몰리면 그 키가 있는 노드만 뜨거워진다. 이 경우 슬롯을 옮겨도 해결되지 않는다 — 키 하나는 쪼갤 수 없기 때문이다. ② 과도한 해시 태그(9절) — 태그를 넓게 잡아 인위적으로 한 슬롯에 몰아 넣은 경우. ③ 큰 값 — 개수는 같아도 값 크기가 크게 다르면 메모리 사용이 기운다.

정리하면 Cluster는 "키 공간을 나누는 장치"이지 "부하를 균등하게 만드는 장치"가 아니다. 균등은 키 설계와 접근 패턴이 만든다.

한 줄 요약
Sentinel은 감시자 여러 대가 정족수로 합의해 마스터 한 대의 죽음을 자동 failover로 견디게 하는 가용성 장치, Cluster는 hash % 노드수의 재배치 폭발을 피하려고 키 → 16384개 고정 슬롯 → 노드라는 간접 계층을 두어 메모리·쓰기를 수평 확장하는 장치다 — 그리고 Cluster의 대가는 "같은 슬롯의 키끼리만 멀티 키 연산이 된다"는 제약이라, 확장 계획은 서버 증설이 아니라 해시 태그를 포함한 키 설계와 코드 전수 조사에서 시작해야 한다.
