Sorted Set 실시간 랭킹 설계 — 기본 설계는 10분, 시간 윈도우와 규모 검증이 진짜 문제

30초 카드 — 답변은 반드시 3단으로
질문: "랭킹(실시간 인기 웹툰) 기능을 Sorted Set으로 설계해보세요. 대규모에서의 한계는?" — 1단에서 멈추면 절반이다. 아래 3단을 순서대로 밟는 것이 이 문항의 답변 골격이다.
① 기본 설계ZINCRBY + ZREVRANGE
여기까지는 10분
② 시간 윈도우버킷 키 + TTL + ZUNIONSTORE
"실시간"의 진짜 요구
③ 규모 한계hot key · big key · 읽기→쓰기 역전
승부처

면접관이 보는 것은 ①의 정답 여부가 아니라 시키지 않아도 ②와 ③으로 넘어가는지다.

핵심 관전 포인트 — 그대로 말하기
Sorted Set은 (멤버, 점수) 쌍을 항상 점수순 정렬 상태로 유지해 주는 자료구조다. 그래서 조회가 일어날 때마다 ZINCRBY로 점수를 1 올리고 화면에서는 ZREVRANGE로 위에서부터 M개를 꺼내면, 정렬 코드를 한 줄도 쓰지 않고 랭킹이 완성된다 — 갱신 O(log N), 상위 M개 조회 O(log N + M). 여기까지가 출발점이다. 진짜 문제는 그다음부터인데, 첫째로 "실시간 인기"는 누적 점수가 아니라 최근 N시간의 점수이므로 키를 시간 단위로 쪼개 쌓고 조회 시 최근 버킷들을 ZUNIONSTORE로 합산하는 윈도우 설계가 따로 필요하다. 둘째로 규모가 커지면 구조 자체에서 한계가 나온다 — 랭킹 키는 하나뿐이라 Redis Cluster를 써도 그 키를 가진 한 노드에만 부하가 몰리고(hot key), 여기에 "조회 이벤트마다 쓰기"라는 구조가 겹쳐 읽기 트래픽이 그대로 쓰기 트래픽으로 바뀌어 그 한 노드를 때린다. 멤버가 수억이면 big key가 되어 O(N) 명령 한 방이 싱글 스레드를 세우고, ZUNIONSTORE는 멀티 키 명령이라 Cluster에서 같은 슬롯 제약까지 붙는다. 도구를 적용하는 답이 아니라 이 규모 한계를 스스로 짚는 답을 해야 한다.
출제 의도 — "도구 적용"과 "규모 검증"을 함께 하는 습관을 본다
실시간 인기 웹툰은 이 회사의 실제 기능이다. Sorted Set으로 기본 설계를 하는 것은 출발점이고, "시간 윈도우는 어떻게 처리할지, 멤버가 수억이면 어떻게 되는지"의 한계 인식까지 가는지를 본다. 그래서 이 페이지의 무게중심은 명령어 목록(§2)이 아니라 §5 시간 버킷과 §10 읽기→쓰기 역전에 있다.

1. 랭킹이라는 요구 — RDB의 인덱스 구조와 상성이 나쁘다

랭킹을 데이터 관점으로 번역하면 두 동작의 조합이다.

쓰기 초당 수천 번

조회수·좋아요 같은 값이 쉬지 않고 바뀐다.

읽기 정렬 후 상위 10개

그 값 기준으로 정렬해서 위에서부터 뽑는다.

RDB로 하면 ORDER BY view_count DESC LIMIT 10이다. 실행 자체는 된다. 문제는 이 두 동작이 RDB 안에서 서로를 방해한다는 점이다.

같은 요구를 두 저장소가 처리하는 방식. RDB는 "값 갱신"과 "정렬 유지"를 두 개의 일로 처리하고 그 사이에 락 경합이 낀다. Sorted Set은 그 둘이 하나의 연산이다 — "빠른 Map"을 넘어선 Redis의 표현력이란 이런 것이다.
내부 구조는 한 줄로만 짚고 넘어간다
Sorted Set은 해시테이블(멤버 → 점수를 O(1)로)과 스킵 리스트(점수순 정렬 유지, O(log N))를 같이 들고 있는 이중 인덱스다. 같은 데이터를 두 벌로 들고 있으니 메모리를 더 쓴다 — 그 대가로 "점수로 찾기"와 "순위로 찾기"가 둘 다 빠르다. 이 메모리 오버헤드는 §9 big key에서 그대로 되돌아온다. (스킵 리스트의 층 구조·확률적 승격 같은 내부 동작은 02-redis-data-structures-use-cases 문서에서 따로 다룬다. 이 문항의 승부처는 자료구조 내부가 아니라 랭킹 시나리오다.)

2. 명령 4종 세트 — 랭킹 화면 한 장이 이 넷으로 끝난다

랭킹을 만드는 데 필요한 연산이 명령어 하나씩으로 이미 존재한다. 외울 때는 명령 이름이 아니라 화면의 어느 부분을 만드는지로 묶어 두는 편이 인출이 빠르다.

읽기 셋은 화면의 서로 다른 자리를 만들고, 쓰기 하나는 화면 밖에서 계속 돈다. 이 그림이 곧 §10의 복선이다 — 화면 밖의 저 초록 명령이 사용자 수만큼 호출되는 쓰기다.
암기 카드 — 랭킹 4종 세트
ZINCRBYO(log N)
올린다. 멤버가 없으면 0에서 시작해 만들어 준다 — "처음 조회된 웹툰인가" 분기가 코드에 필요 없다.
ZREVRANGEO(log N + M)
위에서부터 꺼낸다. ZRANGE는 낮은 순이라 랭킹에는 REV를 쓴다. 0 9가 TOP 10.
ZREVRANKO(log N)
내 자리를 묻는다. 0-based이므로 화면 표기는 +1.
ZSCOREO(1)
내 점수를 묻는다. 해시테이블이 바로 답하므로 유일한 O(1).

N은 그 Sorted Set의 전체 멤버 수, M은 꺼내오는 개수. 여기서 결정적인 것은 TOP 10을 꺼내는 비용이 전체 멤버 수에 거의 영향받지 않는다는 점이다 — 멤버가 100만이든 1000만이든 log 차이뿐이다.

3. 기본 설계 — 그리고 시키지 않아도 짚어야 할 두 함정

// 조회 이벤트 발생 시 — 점수 +1
// incrementScore는 ZINCRBY다. 해당 웹툰이 키에 없으면 0에서 시작해
// 자동으로 만들어 주므로 "처음 조회된 웹툰인가" 분기가 필요 없다.
redisTemplate.opsForZSet().incrementScore("ranking:webtoon", webtoonId, 1);

// 랭킹 화면 — TOP 10 (점수 높은 순)
// reverseRangeWithScores는 ZREVRANGE ... WITHSCORES다.
// 0..9는 0-based 구간이라 1위부터 10위까지를 뜻한다.
Set<TypedTuple<String>> top10 = redisTemplate.opsForZSet()
        .reverseRangeWithScores("ranking:webtoon", 0, 9);

// "이 웹툰은 현재 몇 위?" — ZREVRANK. 0-based라 화면 표기는 +1
Long rank = redisTemplate.opsForZSet().reverseRank("ranking:webtoon", webtoonId);

여기서 멈추면 절반이다. 면접에서 시키지 않아도 두 가지를 스스로 짚어야 한다.

3-1. 멤버에는 ID만 넣는다 — 멤버 문자열이 곧 정체성이다

Sorted Set은 멤버 문자열이 같으면 같은 항목으로, 한 글자라도 다르면 다른 항목으로 취급한다. 그래서 제목·썸네일 같은 메타데이터를 멤버에 직렬화해 넣으면 사고가 난다.

Before — 멤버에 메타데이터를 실었다
zSet.incrementScore("ranking:webtoon",
    "812|나 혼자만 레벨업|/thumb/812_v1.jpg", 1);

// 편집자가 제목 오타를 수정하는 순간 —
zSet.incrementScore("ranking:webtoon",
    "812|나 혼자만 레벨 업|/thumb/812_v1.jpg", 1);
//        ↑ 한 글자 차이 = Redis에게는 전혀 다른 웹툰

// 결과
//  · 옛 멤버: 그동안 쌓인 8,120점을 그대로 들고 남는다
//  · 새 멤버: 0점부터 다시 시작
//  → 같은 웹툰이 랭킹에 두 줄로 나오거나,
//    1위였던 작품이 오타 수정 한 번에 순위권 밖으로 사라진다
After — 랭킹은 ID 목록만 준다
zSet.incrementScore("ranking:webtoon",
    String.valueOf(webtoonId), 1);   // "812"

// 조회는 ID 목록만 받고, 화면 조립은 따로
Set<TypedTuple<String>> top = zSet
        .reverseRangeWithScores("ranking:webtoon", 0, 9);

List<Long> ids = toIds(top);
Map<Long, WebtoonMeta> metas = metaCache.getAll(ids);
// 제목이 바뀌어도 ID는 그대로 → 점수가 끊기지 않는다

// 원칙: 랭킹 키에는 "변하지 않는 식별자"만 넣는다
규칙 카드
랭킹 키에는 변하지 않는 식별자(ID)만 넣는다.
제목·썸네일 같은 메타데이터는 그 ID로 별도 조회해 조합한다.

이유를 한 문장으로: 멤버 문자열이 곧 그 항목의 정체성이라, 문자열이 바뀌면 Redis에게는 새로운 항목이 된다.

3-2. 동점 처리 — 그리고 "점수는 double"이라는 사실

점수가 같은 멤버가 여럿이면 Redis는 멤버 문자열의 사전순(바이너리 비교)으로 정렬한다. 숫자 크기순이 아니라 문자열 비교라서 "10"이 "9"보다 앞에 온다.

"먼저 도달한 쪽이 위" 같은 비즈니스 규칙이 필요하면 점수 하나에 두 정보를 실어야 한다. 흔한 기법이 합성 점수다 — 정수부에는 조회수를, 소수부에는 타임스탬프를 역산해(먼저일수록 큰 값이 되도록) 심어서, 조회수가 같으면 소수부가 승부를 가르게 만든다.

그런데 여기서 반드시 짚어야 할 사실이 있다.

암기 숫자 — Sorted Set의 점수는 정수가 아니라 double이다
253 = 9,007,199,254,740,992
배정도 부동소수점의 가수는 53비트(저장되는 52비트 + 항상 1인 앞자리 1비트) —
절댓값이 이 값 이하인 정수까지만 정확히 표현된다.

그 위로 넘어가면 무슨 일이 생기는지가 중요하다. 표현 가능한 값들의 간격이 1보다 커지므로, 1을 더해도 값이 그대로인 구간이 생긴다.

9007199254740992     (= 2^53)  까지는 정수가 정확히 표현된다
9007199254740992 + 1 을 double로 계산하면?
  -> 9007199254740992   (변하지 않는다. 이 구간의 표현 간격이 2이기 때문)

즉 점수가 253을 넘어선 뒤로는 ZINCRBY key 1 member를 아무리 호출해도 점수가 오르지 않는다. 조회수 카운터로 쓸 때 이 값에 현실적으로 도달할 일은 없지만, "점수는 정수가 아니라 double이다"라는 사실 자체는 두 군데에서 실제로 문제가 된다.

① 합성 점수의 자릿수 예산 설계

정수부(조회수)와 소수부(타임스탬프)가 53비트를 나눠 쓴다. 소수부에 자릿수를 많이 줄수록 정수부가 정확히 표현되는 상한이 내려간다. 무한정 정밀하게 심을 수 없다는 뜻이다.

② 금액·정밀 소수를 점수로 쓸 때 오차 누적

0.1 같은 값은 이진 부동소수점으로 정확히 표현되지 않으므로 더하다 보면 오차가 쌓인다. 돈을 다루는 랭킹이라면 원 단위 정수로 환산해 넣는 편이 안전하다.

면접 가산점 한 문장
"점수는 double이라 253까지의 정수만 정확합니다 — 그래서 합성 점수를 쓸 때 정수부와 소수부가 그 비트 예산을 나눠 씁니다."

4. "실시간 인기"의 진짜 문제 — 누적 랭킹에는 시간 축이 없다

§3까지의 설계에는 아직 시간이라는 축이 없다. 키 하나에 계속 ZINCRBY하면 그건 서비스 개시 이래의 역대 누적 랭킹이다. 왜 문제인지는 숫자로 보면 분명하다.

같은 데이터인데 시간 축 하나를 넣었을 뿐으로 랭킹이 뒤집힌다. 누적 랭킹에서 1위는 사실상 영구 지정석이고 "지금 뜨는 작품"은 절대 보이지 않는다 — 사용자가 실시간 인기 랭킹에서 기대하는 것과 정반대의 결과다.
문제의 본질 — 한 문장
ZINCRBY로 올린 점수는 한 번 올라가면 절대 내려오지 않는다.
그런데 "실시간 인기"는 오래된 점수가 랭킹에서 빠지기를 기대한다.

Sorted Set에는 "이 점수는 1시간 뒤 만료" 같은 개념이 없다. TTL은 키 전체에만 걸 수 있지 멤버별·점수 증분별로는 걸 수 없다. 그래서 우회한다 — 점수에 유효기간을 걸 수 없다면, 키를 시간으로 쪼개서 키 자체에 TTL을 건다.

5. 시간 버킷 — 키가 생기고 사라지는 타임라인이 이 패턴의 전부다

시간 버킷은 "이 시간대의 점수만 담는 통"이다. 키 이름에 시각을 박아서 시간대마다 다른 키를 쓰고, 각 키에 윈도우 길이만큼의 TTL을 건다. 그러면 오래된 시간대의 점수는 애플리케이션이 지울 필요 없이 키째로 자연 소멸한다.

비유 — 시간대별 투표함
한 시간에 하나씩 새 투표함을 꺼내 놓고, 그 시간 동안 들어오는 표는 지금 열린 함에만 넣는다. 개표할 때는 선반에 남아 있는 최근 24개 함을 한꺼번에 쏟아 센다. 함마다 "25시간 뒤 폐기" 도장이 찍혀 있어서, 오래된 함은 아무도 손대지 않아도 알아서 없어진다. "오래된 표를 골라내 빼는 작업"이 이 설계에 존재하지 않는 이유다.
쓰기는 파란 칸 하나로만 들어가고, 읽기는 초록 괄호가 덮는 범위를 합산한다. 시간이 흐르면 새 칸이 오른쪽에 자동으로 생기고 왼쪽 끝이 TTL로 사라진다 — 그것이 윈도우가 "움직이는" 실체다.
1
애플리케이션은 아무것도 지우지 않는다 윈도우에서 빠지는 일은 Redis의 TTL이 알아서 한다. "오래된 점수를 찾아 빼는" 배치 잡이 이 설계에는 존재하지 않는다. 지우는 코드가 없다는 것 자체가 이 패턴의 이득이다.
2
쓰기는 항상 현재 버킷 하나에만 들어간다 지금 시각으로 키 이름을 만들어 ZINCRBY하면 끝이다. 새 버킷이 처음 생길 때도 ZINCRBY가 알아서 만들어 주므로(§2) 초기화 코드가 필요 없다.
3
TTL은 윈도우보다 넉넉히 잡는다 — 24시간 윈도우에 TTL 25시간 TTL을 정확히 24시간으로 걸면, 합산하려는 순간 가장 오래된 버킷이 방금 만료돼 사라져 있을 수 있다. 그 한 시간치가 조용히 빠진 랭킹이 나가고, 아무 에러도 나지 않아서 눈치채기 어렵다. 여유를 둬서 25시간으로 건다.

6. ZUNIONSTORE — 합산하되, 요청마다 하지는 않는다

조회할 때는 최근 24개 버킷의 점수를 웹툰별로 더해야 한다. 이걸 하는 명령이 ZUNIONSTORE다. ZUNIONSTORE 결과키 키개수 키1 키2 ... 형태로 쓰며, 여러 Sorted Set의 합집합을 구하되 같은 멤버가 여러 키에 들어 있으면 점수를 더해서 결과 키에 저장한다.

랭킹 합산에 필요한 동작이 정확히 이 "같은 멤버면 점수 합산"이다. 그리고 STORE라는 이름이 다음 절의 해법을 이미 품고 있다 — 결과를 키에 남기니 미리 만들어 두고 여러 요청이 나눠 쓸 수 있다.
// ① 쓰기: 현재 시간 버킷 키에 적재 (시간 단위 버킷)
String bucket = "ranking:webtoon:" + now.format(yyyyMMddHH);  // ranking:webtoon:2026090114
zSet.incrementScore(bucket, webtoonId, 1);
// TTL은 윈도우(24h)보다 넉넉히. 합산 직전에 가장 오래된 버킷이
// 만료돼 사라지는 것을 막기 위한 여유분이다.
redisTemplate.expire(bucket, Duration.ofHours(25));

// ② 읽기: 최근 24개 버킷을 합산한 결과 키를 만들어 조회
List<String> last24 = recentBucketKeys(24);          // 최근 24시간 버킷 키 목록
// unionAndStore는 ZUNIONSTORE. 같은 웹툰이 여러 버킷에 있으면
// 점수를 더해서 merged 키에 저장한다.
zSet.unionAndStore("ranking:webtoon:2026090114", last24, "ranking:webtoon:merged");
// merged는 파생 데이터라 오래 두면 낡은 랭킹이 된다. 짧은 TTL로 안전장치를 건다.
redisTemplate.expire("ranking:webtoon:merged", Duration.ofMinutes(1));

6-1. 합산을 요청마다 하면 싱글 스레드가 멈춘다

ZUNIONSTORE의 시간 복잡도는 O(N) + O(M log M)이다. 앞의 O(N)은 모든 입력을 한 번씩 훑는 비용, 뒤의 O(M log M)은 합산 결과를 정렬된 자료구조로 만드는 비용이다.

숫자를 대입해 본다
웹툰 2만 개 × 버킷 24개 = 최악의 경우 입력 멤버 48만 개. 이걸 랭킹 화면 요청마다 실행하면 — Redis는 싱글 스레드라서 그 계산이 도는 동안 다른 모든 명령이 줄을 선다. 랭킹 페이지 조회 1,000 QPS에 이 명령이 그대로 붙는 구조는 성립하지 않는다.
Before — 요청마다 합산
public List<RankItem> top10() {
    zSet.unionAndStore(head, last24, MERGED);  // 요청마다 O(N)
    return read(zSet.reverseRangeWithScores(MERGED, 0, 9));
}
// 조회 1,000 QPS = 초당 1,000번의 48만 멤버 스캔
// 그동안 다른 클라이언트의 GET 하나까지 전부 대기한다
After — 스케줄러가 미리 만들어 둔다
@Scheduled(fixedDelay = 60_000)   // 1분마다 한 번
public void rebuildMerged() {
    zSet.unionAndStore(head, last24, MERGED);
    // TTL은 재생성 주기(1분)보다 넉넉히 — 스케줄러가 한 번 밀려도
    // 랭킹이 통째로 비지 않게. 버킷 TTL과 같은 논리다.
    redisTemplate.expire(MERGED, Duration.ofMinutes(5));
}

public List<RankItem> top10() {
    return read(zSet.reverseRangeWithScores(MERGED, 0, 9));
}
// 조회 경로에는 O(log N + M) 명령 하나만 남는다
이건 기술 결정이 아니라 요구사항 협상이다
1분마다 갱신한다는 것은 "랭킹이 최대 1분 낡을 수 있다"는 뜻이다.

실시간 인기 랭킹이 60초 낡아도 되는지를 기획과 합의하고 나서야 이 설계가 성립한다. 랭킹처럼 "근사해도 되는" 데이터에서 정확도를 조금 내주고 비용을 크게 줄이는 협상이 설계의 일부라는 것을 보여주는 지점이다 — 이 협상 카드는 §10에서 한 번 더 쓰인다.

7. 버킷 크기 — 정밀도와 비용의 트레이드오프

버킷을 1시간 단위로 잡으면 윈도우가 1시간씩 뚝뚝 움직인다. 14:59에 보던 "최근 24시간"과 15:00에 보는 "최근 24시간"이 한 시간치만큼 달라진다는 뜻이다. 더 부드럽게 움직이게 하려면 버킷을 잘게 쪼갠다.

버킷 크기24시간 윈도우의 버킷 수윈도우가 움직이는 단위대가
1시간24개1시간씩 — 뚝뚝합산 비용·키 개수 최소
10분144개10분씩 — 부드러움 6배합산 대상 키 6배 · 같은 웹툰이 144개 버킷에 나뉨
1분1,440개1분씩한 명령에 1,440개 키 — 현실적이지 않다
답의 형태
"정답이 있는 문제가 아니라 협상 결과입니다. 윈도우가 얼마나 부드럽게 움직여야 하는지를 제품 요구사항에서 정하고, 그로부터 버킷 크기를 역산합니다." — 기술로 정하는 값이 아니라 요구사항에서 역산하는 값이라는 점이 답의 골자다.

8. 대규모의 한계 — 이 질문의 승부처

지금까지의 설계는 웹툰 수만 개, 조회 수천 QPS 규모에서는 잘 돈다. 여기서부터는 그 설계를 100배 규모에 놓았을 때 어디가 먼저 무너지는지의 이야기다. 한계는 넷이고, 넷이 따로 노는 게 아니라 서로를 부른다.

"핫 · 빅 · 역 · 슬" 넷을 순서대로 꺼내되, 가장 중요한 것은 세 번째 "역"이다 — 그것이 "핫"의 진짜 원인이기 때문이다.

8-1. 랭킹 키 하나는 클러스터로도 분산되지 않는다 (hot key)

Redis Cluster는 키 단위로 샤딩한다. 키 이름을 해싱해 16,384개의 해시 슬롯 중 하나에 배정하고, 각 노드가 슬롯 범위를 나눠 맡는다. 즉 하나의 키는 통째로 한 노드에 산다. 키를 쪼개서 여러 노드에 나눠 담는 기능은 없다.

전 서비스의 조회 쓰기와 랭킹 읽기가 키 하나로 수렴하고, 그 키는 한 노드에 산다. 이렇게 특정 키에 트래픽이 몰려 그 노드가 병목이 되는 현상이 hot key다.
읽기 쪽 완화책 로컬 캐시

merged 결과를 애플리케이션 로컬 캐시로 내린다. TOP N은 ID와 점수 몇십 개뿐이라 몇 KB밖에 안 된다. 서버 각자가 몇 초간 들고 있으면 랭킹 읽기 QPS가 Redis에 거의 도달하지 않는다.

  • 대가는 지연 — merged가 1분마다 갱신되고 로컬 캐시가 5초를 더 얹으면 사용자가 보는 랭킹은 최대 1분 5초 낡는다.
쓰기 쪽은? §10에서

읽기는 위처럼 흡수할 수 있지만 쓰기는 그렇지 않다. 그리고 hot key의 진짜 원인은 쓰기 쪽이다 — §10이 그 이야기다.

9. 한계② big key — 같은 설계를 "전체 유저 랭킹"에 옮기면

웹툰은 많아야 수만 개라 이 설계로 충분하다. 문제는 같은 설계를 그대로 "전체 유저 게임 점수 랭킹"에 옮겼을 때다. 멤버가 수억 개가 된다. big key는 하나의 키가 담고 있는 데이터가 지나치게 큰 상태를 말하고, 세 방향에서 터진다.

1
메모리가 한 노드에 몰린다 Sorted Set은 멤버 하나마다 멤버 문자열 + 스킵 리스트 노드 + 해시테이블 엔트리를 함께 들고 있다(§1의 이중 인덱스). 멤버당 수십~수백 바이트가 붙으므로 수억 멤버면 수십 GB가 되고, 그 전부가 한 노드에 올라간다 — §8-1의 이유로 쪼갤 수 없다.
2
O(N) 명령 한 방이 서버를 세운다 Redis는 싱글 스레드다. ZUNIONSTORE나 ZRANGEBYSCORE처럼 멤버 수에 비례하는 명령을 수억 멤버 키에 치면, 그 명령이 끝날 때까지 다른 모든 클라이언트의 GET 하나까지 전부 대기한다.
3
삭제와 마이그레이션도 폭탄이다 큰 컬렉션을 DEL로 지우면 그 해제 작업이 이벤트 루프에서 돌아 그 시간만큼 서버가 멈춘다. 클러스터에서 슬롯을 다른 노드로 옮길 때도 큰 키 하나가 통째로 이동해야 해서 그동안 지연이 튄다.
대응은 기술이 아니라 질문에서 시작한다
"정말 수억 명 전원의 정확한 순위가 필요합니까,
아니면 TOP 1000만 정확하면 됩니까?"

이 되물음이 대응 방법을 결정한다. 요구사항을 그대로 받아 기술로 버티려 하면 답이 없고, 요구사항을 깎으면 세 문제가 한꺼번에 사라진다.

TOP N만 필요하다면 크기를 상수로

ZREMRANGEBYRANK로 주기적으로 하위를 잘라낸다. 순위 구간을 지정해 그 구간의 멤버를 지우는 명령이다 — 예를 들어 상위 1000명만 남기고 나머지를 날린다.

  • 멤버 수가 1000으로 고정되면 위의 세 문제가 전부 사라진다.
"내 순위"까지 전원에게 줘야 한다면 근사

점수 구간별 카운트(히스토그램)로 근사 순위를 준다. 구간마다 인원 수만 세어 두고 "내 점수보다 높은 구간들의 인원 합 + 1"로 계산해 "상위 12% (약 3만 등)"처럼 보여준다.

  • 정확한 등수를 포기하는 대신 수억 멤버를 다 들고 있지 않아도 된다.

10. 한계③ 조회 트래픽이 그대로 쓰기 트래픽이 된다 이 문서에서 가장 중요

캐시에 대한 직관이 여기서 뒤집힌다
캐시는 보통 읽기를 흡수하는 장치다. DB로 갈 조회를 Redis가 대신 받아 주니 DB 부하가 줄어든다 — "캐시를 도입하면 시스템 전체 부하가 내려간다"는 직관은 여기서 온다. 그런데 랭킹은 정반대로 동작한다. 조회 이벤트가 발생할 때마다 ZINCRBY를 쳐야 하는데, ZINCRBY는 값을 바꾸는 쓰기 명령이다. 즉 랭킹 집계는 페이지뷰라는 읽기 트래픽을 Redis 쓰기 트래픽으로 변환하는 구조다.
이 세 줄이 이어지는 것이 hot key의 정체다. ZINCRBY 하나가 O(log N)으로 빠르다는 사실은 여기서 도움이 안 된다 — 명령 하나의 비용이 아니라 한 노드가 받는 명령의 개수가 병목이기 때문이다.

10-1. 해법 — 집계의 지연을 허용해 쓰기 횟수를 줄인다

Before — 이벤트마다 Redis 왕복
public void onView(long webtoonId) {
    zSet.incrementScore(bucket(), String.valueOf(webtoonId), 1);
}
// 조회 QPS가 그대로 쓰기 QPS가 된다
// 사용자가 늘어난 만큼 정확히 그만큼 마스터를 때린다
After — 로컬에서 모았다가 주기적으로 한 번에
// LongAdder는 여러 스레드가 동시에 증가시킬 때 경합을 분산시키는 카운터다.
// 이 서버가 5초 동안 본 조회 횟수를 웹툰별로 메모리에 쌓아 둔다.
private final ConcurrentHashMap<Long, LongAdder> buffer = new ConcurrentHashMap<>();

public void onView(long webtoonId) {
    buffer.computeIfAbsent(webtoonId, k -> new LongAdder()).increment();
}

@Scheduled(fixedDelay = 5_000)
public void flush() {
    // 버퍼를 통째로 스냅샷 떠서 비우고, 웹툰별 누적 횟수를
    // ZINCRBY 한 번씩으로 반영한다. 파이프라인으로 묶어 보내면
    // 네트워크 왕복 횟수까지 한 번으로 줄어든다.
}
이 구조의 한계도 함께 알고 있어야 한다 — 조회가 아주 많은 종류에 얇게 흩어져 있으면(한 서버가 같은 웹툰을 한두 번밖에 못 보면) 압축 효과가 거의 없다.
대가는 두 가지 — 명시적으로 말해야 하는 부분
1
랭킹이 최대 5초 늦게 반영된다 버퍼에 머무는 시간만큼 지연이 붙는다. §6의 merged 1분, §8-1의 로컬 캐시 5초와 합쳐져 쌓인다.
2
서버가 플러시 전에 죽으면 버퍼의 조회수가 유실된다 랭킹은 화면용 근사치이므로 감수할 만하지만, "유실될 수 있다"는 사실을 아는 채로 선택했는지가 답변의 질을 가른다.

"정확·즉시"를 "근사·지연 허용"으로 협상해서 비용을 낮췄다는 사실 자체를 문장으로 말해야 한다.

지연은 쌓인다 — 최종 사용자가 보는 값의 나이를 계산해 둔다
로컬 버퍼5초§10
merged 재생성1분§6
로컬 캐시5초§8-1
사용자가 보는 랭킹최대 1분 10초낡음
세 완화책을 다 넣으면 지연이 더해진다. 각각은 합리적인데 합쳐 놓고 보면 기획이 기대한 "실시간"이 아닐 수 있다 — 그래서 최종 지연을 먼저 계산해 합의하고 거기서 각 구간의 예산을 나누는 순서가 맞다.

10-2. 같은 원리의 다른 형태 — Kafka와 샘플링

Kafka 이벤트 스트림 버퍼의 위치만 다르다

조회 이벤트를 Kafka로 흘려보내고 컨슈머가 일정 시간 단위로 집계해 반영하는 구조도 같은 원리다. 버퍼가 애플리케이션 메모리 대신 Kafka에 있다는 차이다.

  • 이점 — 서버가 죽어도 이벤트가 유실되지 않는다.
  • 비용 — 인프라 한 겹이 늘어난다.

11. 한계④ 클러스터의 멀티 키 제약이 hot key를 되부른다

마지막 한계는 앞의 것들이 서로 엮여서 나온다. ZUNIONSTORE는 여러 키를 한 명령에서 다루는 멀티 키 명령이다. 그런데 Redis Cluster에서 키들은 각자 다른 노드에 흩어져 있을 수 있고, 한 명령은 한 노드 안에서만 실행된다. 그래서 클러스터는 조건을 건다 — 명령에 등장하는 모든 키가 같은 해시 슬롯에 있어야 한다. 아니면 CROSSSLOT 오류가 난다.

문제를 푸는 장치가 그 문제를 더 확실하게 만든다. 해시태그는 CROSSSLOT을 해결하지만, 그 대가로 hot key를 구조적으로 고정한다.

13. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답한 뒤 펼쳐서 확인한다. 시니어 변별은 정답 하나를 고르지 말고 판단 기준과 순서를 말하는 연습을, 추가는 원문에 없지만 실제로 자주 이어지는 질문이다.

이 설계를 그대로 두고 트래픽이 100배가 되면 어디가 먼저 무너지나요? 시니어 변별

순서를 짚어서 답한다. 전체 그림은 §12에 있다.

  1. 쓰기 경로가 먼저 무너진다. 조회 QPS와 같은 수의 ZINCRBY가 랭킹 키를 가진 단일 노드로 몰린다(§10의 읽기→쓰기 역전 + §8-1의 hot key). 쓰기는 replica로 분산되지 않으므로 여기서 가장 먼저 한계에 닿는다.
  2. 스케줄러의 ZUNIONSTORE 합산이다. 멤버가 늘수록 O(N) + O(M log M)의 N과 M이 커지고, 싱글 스레드를 그만큼 오래 점유한다.
  3. 메모리다. 멤버 수 × (문자열 + 스킵 리스트 노드 + 해시테이블 엔트리)가 한 노드에 쌓인다.

그리고 방어도 같은 순서로 간다 — ① 로컬 버퍼링 + 파이프라인으로 쓰기 횟수를 묶고, ② merged TOP N을 로컬 캐시로 내려 읽기가 Redis에 도달하지 않게 하고, ③ ZREMRANGEBYRANK로 하위 랭크를 잘라 크기를 상수로 유지한다.

"어디가 병목인지의 순서"를 짚는 것 자체가 규모 검증 습관의 증거다. 모든 한계를 한꺼번에 나열하는 답과, 무엇이 먼저 무너지는지 순서를 매기고 방어도 그 순서로 배치하는 답의 차이가 이 질문의 변별점이다.

점수가 같은 웹툰끼리의 순서는 어떻게 되나요?

멤버 문자열의 사전순(바이너리 비교)이다. 숫자 크기순이 아니라 문자열 비교라 "10"이 "9"보다 앞에 온다.

비즈니스 규칙(선점순 등)이 필요하면 점수를 합성한다 — 예를 들어 정수부는 조회수, 소수부는 1 - (timestamp / 최댓값)처럼 먼저 도달할수록 큰 값이 되게 만든다. 그러면 조회수가 같을 때 소수부가 승부를 가른다.

여기에 §3-2의 사실을 얹으면 답이 정확해진다. 점수는 double이고 정수를 정확히 표현할 수 있는 상한이 253 = 9,007,199,254,740,992이므로, 정수부와 소수부가 그 53비트 예산을 나눠 쓴다. 소수부에 자릿수를 많이 줄수록 정수부(조회수)의 정확 표현 상한이 내려간다는 것까지 말하면 좋다.

최근 1시간 랭킹인데 10분 전 조회까지만 반영하고 싶다면?

버킷 정밀도의 문제다(§7). 1시간 윈도우를 10분 단위로 움직이려면 10분 버킷 6개를 합산한다.

정밀도를 올릴수록 버킷 개수, ZUNIONSTORE 합산 비용, 키 관리 비용이 함께 늘어난다. 그래서 "윈도우가 얼마나 부드럽게 움직여야 하는가"를 제품 요구사항과 협상해서 버킷 크기를 정한다고 답하면 된다.

기술로 정하는 값이 아니라 요구사항에서 역산하는 값이라는 점이 답의 골자다.

"내 웹툰은 지금 몇 위" 조회는 비싸지 않나요?

명령 자체는 싸다. ZREVRANK는 O(log N)이라 멤버가 많아도 조회 한 번의 비용은 문제가 안 된다.

진짜 문제는 그 명령을 쓰려면 전체 멤버를 다 들고 있어야 한다는 것이다. 순위를 매기려면 나보다 위에 몇 명이 있는지 알아야 하고, 그러려면 전원이 Sorted Set 안에 있어야 한다. 멤버가 수억이면 §9의 big key 문제로 그대로 돌아간다.

그래서 TOP N만 유지하는 잘린 랭킹에서는 순위권 밖 멤버의 순위를 줄 수 없다. 선택지는 둘이다 — "순위권 밖"이라고만 표시하고 타협하거나, 점수 히스토그램으로 "상위 12%" 같은 근사 순위를 주거나. 어느 쪽이든 정확한 등수를 포기하는 대가로 크기를 상수로 유지하는 거래다.

DB에도 어차피 조회수를 저장할 텐데, 랭킹도 DB로 하면 안 되나요?

ORDER BY view_count DESC LIMIT 10은 실행할 수는 있다. 안 되는 이유는 셋이다(§1).

  1. 조회수 컬럼 인덱스는 초당 수천 번의 갱신마다 재정렬 비용을 낸다.
  2. 인기 행에 UPDATE가 몰려 락 경합이 생긴다 — 인기가 많을수록 느려지는 역설.
  3. 시간 윈도우 랭킹은 컬럼 하나 정렬로 안 된다. 이벤트 로그 테이블을 GROUP BY로 집계해야 해서 훨씬 비싸진다.

다만 Redis 편만 들면 답이 반쪽이다. Redis 랭킹은 재시작이나 장애로 유실될 수 있다. 그래서 실무의 정석은 역할 분리다 — 정산·통계처럼 정확해야 하는 수치는 DB(이벤트 적재)가 원본이고, Redis는 화면에 보여 줄 실시간 근사치다.

둘은 경쟁 관계가 아니라 용도가 다른 두 저장소이고, 어긋나도 되는 데이터와 어긋나면 안 되는 데이터를 구분했다는 점이 답의 핵심이다.

ZINCRBY 대신 ZADD로 점수를 넣으면 안 되나요? 추가

ZADD는 점수를 "설정"하는 명령이라 덮어쓴다. 그래서 증가를 구현하려면 읽고 → 더하고 → 쓰는 세 단계가 되는데, 이 사이에 다른 요청이 끼어들면 lost update가 난다.

// 두 요청이 동시에 도착하면
A: ZSCORE key m  -> 100      B: ZSCORE key m  -> 100
A: ZADD  key 101 m           B: ZADD  key 101 m
// 조회가 2번인데 점수는 101 — 1이 사라진다

ZINCRBY는 서버 안에서 읽기·더하기·쓰기가 한 명령으로 끝나고, Redis는 싱글 스레드라 그 사이에 아무도 끼어들 수 없다. 원자성이 명령 자체에 들어 있는 것이 ZINCRBY를 쓰는 이유다.

참고로 ZADD에 INCR 옵션을 주면 ZINCRBY와 같은 동작이 되고, "기존 점수보다 클 때만 갱신" 같은 조건부 옵션도 있다 — 최고 기록(best score) 랭킹처럼 "누적"이 아니라 "최댓값"이 필요한 경우에 쓰는 형태다. 랭킹의 점수 의미가 누적인지 최댓값인지부터 정하는 것이 명령 선택의 출발점이다.

이벤트마다 ZINCRBY 뒤에 EXPIRE를 또 부르면 왕복이 두 배 아닌가요? 추가

맞다. 그리고 정확히 이 지적이 나와야 한다. 정리하면 이렇다.

  • 정확성 문제는 없다. EXPIRE는 O(1)이고 몇 번 걸든 결과가 같은(멱등) 연산이라, 매번 다시 걸어도 TTL이 그 시점 기준으로 갱신될 뿐이다. 오히려 "버킷이 처음 생기는 순간을 판별해서 그때만 걸기"가 경합 때문에 더 까다롭다.
  • 진짜 비용은 네트워크 왕복이다. Redis 성능의 지배 요인은 명령 처리 시간이 아니라 왕복 횟수라, 명령이 2배가 되면 왕복도 2배가 된다.

해법은 셋 중 하나다 — 파이프라인으로 두 명령을 한 왕복에 묶거나, Lua 스크립트로 한 번에 보내거나, §10의 로컬 버퍼링을 도입해 애초에 flush 주기마다 한 번만 나가게 하거나. 버퍼링을 넣으면 이 문제는 저절로 사라진다 — 5초에 한 번 나가는 flush에서 EXPIRE 한 번 더 부르는 것은 아무 부담이 아니다.

스케줄러가 여러 대인데 ZUNIONSTORE가 중복 실행되면 어떻게 되나요? 합산 도중에 조회하면 반쪽 랭킹이 보이나요? 추가

두 질문을 나눠서 답한다.

① 중복 실행 — 결과는 깨지지 않지만 비용이 배로 든다. ZUNIONSTORE는 같은 입력에 같은 결과를 만드는 멱등 연산이라 결과 키는 정상이다. 문제는 O(N) 명령이 서버 대수만큼 실행되어 싱글 스레드를 그만큼 더 오래 점유한다는 것이다. 대응은 리더 선출이나 분산 락으로 한 대만 돌게 하기, 또는 합산 작업을 별도의 단일 워커로 분리하기다.

② 중간 상태는 보이지 않는다. ZUNIONSTORE는 명령 하나이고 Redis는 싱글 스레드라, 그 명령이 도는 동안 다른 클라이언트의 조회는 실행되지 못하고 대기한다. 그래서 "절반만 합산된 랭킹"을 읽는 일은 생기지 않는다.

다만 바로 그 "대기"가 대가다. 합산이 오래 걸릴수록 그 시간만큼 전체 Redis가 멈춘다 — §12에서 두 번째 병목으로 꼽은 이유가 이것이다. 그래서 합산 주기를 늘리거나, 버킷 수를 줄이거나, 애초에 멤버 수를 잘라 이 명령이 짧게 끝나도록 관리한다.

조회는 1점, 좋아요는 5점처럼 가중치를 주고 싶다면? 최근 버킷에 더 큰 가중치를 주려면? 추가

두 층에서 각각 가중치를 걸 수 있다.

  • 이벤트 가중치 — ZINCRBY의 증가량을 이벤트 종류마다 다르게 준다(조회 1, 좋아요 5). 가장 단순하지만 나중에 가중치를 바꾸면 이미 쌓인 점수는 옛 가중치로 남는다는 성질이 있다.
  • 이벤트 종류별로 키를 나눈다 — ...:view:2026090114, ...:like:2026090114로 따로 쌓고 합산할 때 ZUNIONSTORE의 WEIGHTS 옵션으로 키마다 배수를 곱해서 더한다. 가중치를 나중에 바꿔도 원본 카운트가 그대로 남아 있어 재계산이 가능하다는 것이 큰 이점이다.

그리고 같은 WEIGHTS로 "시간 감쇠"도 구현된다. 최근 버킷에 큰 가중치를, 오래된 버킷에 작은 가중치를 주면 윈도우 안에서도 최근 것이 더 세게 반영된다 — §4에서 본 "누적 랭킹의 고인 물" 문제를 윈도우 안에서 한 번 더 완화하는 장치다.

대가는 키 개수와 합산 비용이다. 종류를 나눌수록 ZUNIONSTORE의 입력 키가 배수로 늘어난다(§7의 트레이드오프와 같은 축).

Redis가 재시작되면 랭킹이 통째로 사라지는데, 괜찮은가요? 추가

"괜찮다"가 아니라 "이 데이터는 유실돼도 되는 종류라고 판정했다"가 정확한 답이다. 세 갈래로 나눠 말한다.

  • 지속성 설정으로 줄일 수는 있다. RDB 스냅샷이나 AOF를 켜면 유실 폭이 줄어든다. 다만 유실을 0에 가깝게 만들수록 쓰기 비용을 더 낸다는 트레이드오프가 있고, 랭킹은 초당 수만 건이 들어오는 쓰기 부하가 큰 키라 이 비용이 가볍지 않다.
  • 원본은 DB의 이벤트 로그다. 정산·통계에 쓰는 정확한 수치는 DB에 적재하고, Redis는 화면용 근사치로 둔다. 그러면 유실은 "랭킹 화면이 잠깐 빈다"로 끝나고, 배치로 최근 N시간 이벤트를 다시 집계해 버킷을 재구축하는 복구 경로가 생긴다.
  • 시간 버킷 설계에는 자가 치유 성질이 있다. 버킷은 어차피 TTL로 계속 교체되므로, 유실 후에도 윈도우 길이만큼 시간이 지나면 랭킹이 저절로 정상 상태로 수렴한다. 누적 랭킹이었다면 3년 치를 다시 쌓아야 하지만, 24시간 윈도우는 24시간이면 복구된다.

"유실되면 무엇이 깨지는가"를 먼저 따지고, 그다음에 지속성 설정을 말하는 순서가 좋다. 순서를 뒤집으면 "AOF 켜면 됩니다"라는 도구 답변이 된다.

TOP 10이 아니라 100위까지 페이지네이션하면 뒤쪽 페이지가 더 비싸지 않나요? 추가

순위 기반 조회는 뒤쪽 페이지라고 더 비싸지지 않는다. ZREVRANGE key 0 9든 ZREVRANGE key 90 99든 복잡도는 O(log N + M)이다 — 스킵 리스트가 순위로 시작 지점을 바로 찾을 수 있기 때문이다.

RDB의 LIMIT ... OFFSET과 대비해서 말하면 좋다. SQL의 깊은 OFFSET은 건너뛸 행을 실제로 읽고 버려야 해서 페이지가 깊어질수록 느려진다. Sorted Set의 순위 조회에는 그 성질이 없다.

다만 진짜 조심할 것은 M이다. ZREVRANGE key 0 -1처럼 전체를 한 번에 꺼내면 M이 곧 N이 되어 O(N) 명령이 되고, 거기에 수십 MB를 직렬화해 내보내는 네트워크 비용까지 붙어 싱글 스레드를 오래 붙잡는다(§9). "깊은 페이지"가 아니라 "큰 페이지"가 위험하다는 것이 이 질문의 요지다.

한 줄 요약
Sorted Set은 ZINCRBY(없으면 0에서 만들어 주는 점수 증가)와 ZREVRANGE(점수 높은 순 M개)만으로 O(log N) 랭킹을 주는 최적의 도구지만, "실시간 인기"는 누적이 아니라 최근 N시간이므로 시간 버킷 키 + TTL + ZUNIONSTORE 합산이라는 윈도우 설계가 따로 필요하고, 대규모에서는 랭킹 키가 하나뿐이라 클러스터로도 분산되지 않는 hot key에 "조회 이벤트마다 쓰기"라는 읽기·쓰기 역전이 겹쳐 단일 노드가 먼저 무너지며, 그 뒤로 수억 멤버 big key와 멀티 키 슬롯 제약이 따라오므로 — 로컬 버퍼링으로 쓰기를 묶고, 결과를 로컬 캐시로 내리고, 하위 랭크를 잘라내고, "정확·즉시"를 "근사·지연 허용"으로 협상하는 것까지 붙여야 규모를 견디는 설계가 된다.
