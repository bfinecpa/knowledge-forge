ThreadLocal — 값은 ThreadLocal이 아니라 Thread 안에 있다
그래서 스레드가 살아 있는 한 값도 살아 있다 — 톰캣은 스레드를 버리지 않고 재사용하므로, remove()를 안 하면 보안 사고와 메모리 누수가 동시에 터진다

면접 질문: "ThreadLocal은 언제 쓰고, 톰캣 같은 스레드풀 환경에서 어떤 위험이 있나요?"

핵심 관전 포인트 — ThreadLocal은 "같은 변수인데 스레드마다 다른 값"을 갖게 해주는 스레드 전용 저장소다. 인증 정보·트랜잭션 커넥션·로그 traceId처럼 모든 메서드에 파라미터로 넘기기 어려운 요청 문맥을 실어 나르는 데 쓴다. 위험은 전부 저장 구조에서 나온다 — 값은 ThreadLocal 객체가 아니라 Thread 객체 안의 ThreadLocalMap에 들어가고, ThreadLocal 인스턴스는 그 맵의 키일 뿐이다. 톰캣은 스레드를 만들고 버리는 게 아니라 풀에서 재사용하므로, 스레드가 살아 있는 한 그 맵도 값도 그대로 살아 있다. 그래서 remove()를 안 하면 ① 이전 요청의 데이터가 다음 요청(다른 사용자)에게 그대로 보이는 보안 사고와 ② 값이 GC되지 않는 메모리 누수가 동시에 생긴다. 요청 경계의 finally에서 remove()가 철칙이고, 비동기로 작업을 넘기면 반대로 문맥이 아예 전파되지 않는다.
  • 1
    쓰는 곳은 "파라미터로 넘길 수 없는 요청 문맥"입니다. 인증 정보, 로그 traceId, 트랜잭션 커넥션처럼 여러 계층을 가로지르는 값을 시그니처가 아니라 스레드에 실어 나릅니다. SecurityContextHolder, MDC, @Transactional이 전부 이 구조입니다.
  • 2
    위험은 저장 위치에서 나옵니다. 값은 ThreadLocal이 아니라 Thread 객체 안의 ThreadLocalMap에 들어가고, 톰캣은 워커 스레드를 재사용합니다. 그래서 remove()를 빠뜨리면 다음 요청이 이전 사용자의 값을 그대로 읽고, 값은 GC되지 않고 워커 수만큼 상주합니다.
  • 3
    대응은 두 방향입니다. 요청 경계(필터·인터셉터)의 finally에서 반드시 remove()하고, 스레드가 바뀌는 순간(@Async·CompletableFuture)에는 문맥이 전파되지 않으므로 TaskDecorator로 제출 시점에 복사합니다. InheritableThreadLocal은 생성 시점 복사라 스레드풀에서는 오답입니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "ThreadLocal은 언제 쓰고, 톰캣 같은 스레드풀 환경에서 어떤 위험이 있나요?"

출제 의도 — 톰캣은 스레드를 재사용하므로 정리 안 한 ThreadLocal은 "다른 사용자의 인증 정보가 섞여 보이는" 류의 보안 사고로 직결된다. 프레임워크가 숨겨준 실행 모델을 이해하고 쓰는지 확인하는 질문이다.

약점 A"스레드마다 값을 따로 갖는 변수입니다"에서 끝나는 답 — 정의는 맞지만 값이 어디에 저장되는지를 말하지 못한다. 저장 위치를 모르면 위험도 설명할 수 없고, "그럼 왜 위험하죠?" 한 번에 막힌다.
약점 B"메모리 누수가 생깁니다"만 말하는 답 — 실무에서 훨씬 무서운 데이터 오염(다른 사용자 정보 노출)을 빠뜨린다. 누수는 힙이 커지는 문제지만, 오염은 보안 사고다.
약점 C"키가 약한 참조라 GC됩니다"로 안심하는 답 — 약한 참조인 것은 키뿐이고 값은 강한 참조다. 이 비대칭을 못 짚으면 누수의 원인을 정반대로 이해한 것이다.
약점 D비동기 전파를 InheritableThreadLocal로 해결한다는 답 — 복사 시점이 스레드 생성 순간이라 풀에서는 오답이다. 틀린 값이 그럴듯하게 나오는, null보다 나쁜 결과가 된다.
합격선"값은 ThreadLocal이 아니라 Thread 안에 있다"는 저장 구조를 먼저 그리고, 거기서 오염 · 누수 · 전파 단절 세 위험을 연역해서 말한 뒤, 대응으로 finally + remove()와 제출 시점 복사를 짝지어 닫는 것.
이 문서의 진행 방향 — 그림 한 장을 먼저 세운다 ThreadLocal의 위험 세 개는 전부 한 장의 저장 구조 그림에서 연역된다. 그래서 1~3절에서 ①톰캣의 스레드 재사용 ②ThreadLocal의 의미 ③실제 저장 위치를 먼저 세우고, 4절에서 그 그림에서 나오는 세 결론을 못 박은 뒤, 7~10절에서 그 결론을 하나씩 사고로 풀어낸다. 외울 것은 그림 한 장과 결론 세 줄이고, 나머지는 거기서 다시 만들어낼 수 있다.

1. 전제 — 톰캣은 요청마다 스레드를 만들지 않는다

먼저 깔아야 할 사실이 하나 있다. 톰캣은 요청마다 스레드를 새로 만들지 않는다. 애플리케이션이 뜰 때 워커 스레드를 미리 만들어 풀에 담아두고, 요청이 오면 그중 한 개를 빌려주고, 응답을 보내고 나면 그 스레드를 죽이지 않고 풀로 되돌려 다음 요청에 다시 빌려준다. 스프링 부트의 톰캣 기본 최대 워커 수는 200개다.

스레드를 매번 만들지 않는 이유는 비용 때문이다. OS 스레드 하나를 만들면 커널 자료구조와 스택 메모리(보통 1MB 수준)가 딸려 오는데, 초당 수천 건의 요청마다 이걸 만들고 버리면 그 비용이 실제 업무 처리 비용을 압도한다. 그래서 미리 만들어 돌려 쓴다.

이 문서 전체를 지탱하는 한 문장

요청이 끝나는 것과 ThreadLocal 값이 사라지는 것은 아무 관계가 없다

사라지는 것은 스택이고, ThreadLocal 값은 스택이 아니라 Thread 객체에 매달려 있다. 값의 수명을 정하는 것은 요청의 수명이 아니라 스레드의 수명이며, 톰캣에서 스레드의 수명은 사실상 애플리케이션의 수명이다.

2. ThreadLocal이란 — 스레드마다 칸이 다른 사물함

ThreadLocal은 같은 변수를 여러 스레드가 읽고 써도 각 스레드가 자기 값만 보게 해주는 저장소다.

private static final ThreadLocal<String> currentUser = new ThreadLocal<>();

// 스레드 A                             // 스레드 B
currentUser.set("alice");               currentUser.set("bob");
currentUser.get();  // "alice"          currentUser.get();  // "bob"

currentUser는 분명히 static 필드 하나인데, A는 "alice"를 보고 B는 "bob"을 본다. 보통의 static 필드였다면 나중에 쓴 값이 앞의 값을 덮어썼을 것이다.

3. 저장 구조 — Thread → ThreadLocalMap → Entry

이름이 ThreadLocal이라 값이 ThreadLocal 객체 안에 들어 있다고 착각하기 쉽지만 정반대다. 값은 Thread 객체 안에 들어간다.

Thread 클래스에는 threadLocals라는 필드가 있고, 그 타입이 ThreadLocalMap이다. 이름 그대로 맵(키-값 저장소)이며, 키가 ThreadLocal 인스턴스, 값이 우리가 set()으로 넣은 값이다.

세 메서드는 전부 "현재 스레드"를 기준으로 동작한다

set(v)
Thread.currentThread()를 찾아 그 스레드의 맵에 (this, v)를 넣는다.
get()
Thread.currentThread()를 찾아 그 스레드의 맵에서 this를 키로 조회한다.
remove()
그 스레드의 맵에서 this 항목을 지운다.
실행 중인 스레드가 바뀌면 뒤지는 맵 자체가 바뀐다

이 한 줄을 쥐고 있으면 10절의 비동기 전파 단절은 따로 외울 필요가 없다. @Async가 값을 못 읽는 이유는 특별한 규칙이 아니라 이 정의의 당연한 귀결이다.

4. 이 한 그림에서 나오는 세 가지 결론

방금 본 구조에서 이 문서의 위험 세 개가 전부 따라 나온다. 미리 한 번 짚고 가면 뒤가 쉬워진다.

a스레드가 살아 있는 한 값도 살아 있다. 값은 Thread 객체가 붙잡고 있으므로 스레드의 수명이 곧 값의 수명이다. 요청이 끝나는 것과 값이 사라지는 것은 아무 관계가 없다.→ 7·8절
b그래서 톰캣 풀에서는 요청 A의 값이 요청 B에 새어 나간다. 스레드 #7이 요청 A를 처리하며 넣은 값은 응답 후에도 #7의 맵에 남아 있고, #7이 요청 B에 빌려지면 요청 B의 코드가 그 값을 그대로 읽는다.→ 7절 오염
c키는 약한 참조인데 값은 강한 참조라, 값이 GC되지 않는다. Entry는 키(ThreadLocal)만 약하게 붙잡고 값은 강하게 붙잡는다. 키가 사라져도 Thread → ThreadLocalMap → Entry → value라는 강한 참조 사슬이 남는다.→ 8절 누수
여기에 네 번째가 붙는다 — 방향이 반대인 위험 (a)(b)(c)가 "지워야 할 값이 남는" 문제라면, 맵이 스레드마다 따로 있다는 사실은 반대 방향의 위험도 만든다 — 스레드가 바뀌면 있어야 할 값이 없다. @Async·CompletableFuture·parallelStream()이 여기 해당하며 10절에서 다룬다. 원인은 하나(값이 스레드에 붙어 있다)인데 증상이 정반대라는 점이 이 주제를 헷갈리게 만드는 핵심이다.

5. 언제 쓰나 — 파라미터로 넘길 수 없는 요청 문맥

한 요청을 처리하는 동안 컨트롤러에서 서비스, 서비스에서 리포지터리, 그 사이의 유틸리티까지 수십 개 메서드를 거친다. 그런데 그 깊은 곳에서 "지금 요청한 사람이 누구인지"나 "이 요청의 추적 ID가 뭔지"가 필요해진다.

가장 정직한 방법은 파라미터로 넘기는 것이다. 문제는 중간에 그 값을 전혀 쓰지 않는 메서드들까지 전부 시그니처를 바꿔야 한다는 점이다.

문제 쓰지도 않는 값을 전달하려고 시그니처가 오염된다
// 컨트롤러 — 받아서 그대로 넘기기만 한다
public Order create(OrderRequest req, User user, String traceId) {
    return orderProcessor.process(req, user, traceId);  // 여기선 안 씀
}

// 중간 계층 — 역시 안 쓰는데 시그니처만 부풀었다
public Order process(OrderRequest req, User user, String traceId) {
    validator.validate(req, user, traceId);
    return repository.save(req, user, traceId);
}
// 문맥이 하나 늘 때마다 이 경로의 모든 메서드를 다시 고쳐야 한다.
개선 요청 경계에서 한 번 넣고, 필요한 곳에서만 꺼낸다
// 컨트롤러 — 업무에 필요한 것만 받는다
public Order create(OrderRequest req) {
    return orderProcessor.process(req);   // 중간 계층은 문맥을 몰라도 된다
}

// 실제로 필요한 딱 그 지점에서만 꺼내 쓴다
public void writeAuditLog(Order order) {
    User user = UserContext.currentUser();   // 내부적으로 ThreadLocal
    auditRepository.save(order, user);
}
// 문맥이 늘어도 중간 계층 시그니처는 그대로다.

이렇게 여러 계층을 가로질러 필요한 관심사를 횡단 관심사(cross-cutting concern)라고 부른다. 계층을 세로로 자르는 게 아니라 가로로 관통한다고 해서 "횡단"이다. 인증 정보, 로그 추적 ID, 트랜잭션 커넥션, 다국어 로케일이 전형적인 예다.

6. 이미 매일 쓰고 있다 — 프레임워크 기능들의 정체

ThreadLocal을 직접 써본 적이 없더라도, 스프링 애플리케이션을 만들었다면 이미 하루에도 수백 번 쓰고 있다. 아래 기능들이 전부 ThreadLocal 위에 서 있다.

SecurityContextHolder
아무 서비스 메서드에서나 현재 사용자가 나오는 이유. 인증 필터가 요청 초입에서 인증 결과를 ThreadLocal에 넣어둔다.
@Transactional
획득한 DB 커넥션을 TransactionSynchronizationManager가 ThreadLocal에 바인딩한다. 같은 커넥션을 써야 같은 트랜잭션이 된다.
MDC
Mapped Diagnostic Context. 초입에서 MDC.put("traceId", …) 해두면 그 스레드의 모든 로그에 자동으로 붙는다.

네 번째 용도 — 스레드 안전하지 않은 객체를 스레드별로 하나씩

여러 스레드가 같이 쓰면 깨지는 객체를 공유하는 대신, 스레드마다 자기 인스턴스를 갖게 하는 방식이다.

문제 가변 상태를 가진 객체를 static으로 공유
// SimpleDateFormat은 내부에 가변 Calendar 필드를 두고
// 거기에 파싱 중간 결과를 쌓는다.
private static final SimpleDateFormat FMT =
        new SimpleDateFormat("yyyy-MM-dd");

// 여러 스레드가 한 인스턴스를 동시에 쓰면 서로의 중간 결과를
// 덮어써서 날짜가 뒤섞이거나 예외가 튄다.
Date d = FMT.parse(input);   // 간헐적으로 엉뚱한 값 / 예외
차선책 공유 자체를 없앤다 — 스레드마다 자기 인스턴스
// withInitial: "그 스레드에서 처음 get() 할 때
//              이 함수로 값을 만들어라"
private static final ThreadLocal<SimpleDateFormat> FMT =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

Date d = FMT.get().parse(input);   // 내 것만 쓴다
// 단, 값이 스레드 수만큼 생긴다는 비용은 그대로 남는다.
단, 이 용법에는 단서가 붙는다 가산점 진짜 정답은 불변이라 애초에 공유해도 안전한 DateTimeFormatter로 갈아타는 것이고, ThreadLocal은 레거시 코드를 당장 걷어낼 수 없을 때의 차선책이다. 가변 상태를 없애는 게 아니라 스레드별로 격리하는 대증요법이기 때문이다. 격리는 스레드 수만큼의 인스턴스라는 비용을 남기고, 11절에서 보듯 가상 스레드 환경에서는 그 비용이 정면으로 문제가 된다. (22-static-simpledateformat-shared-mutable-state에서 이 판단을 자세히 다룬다.)

7. 위험 ① 데이터 오염 — 다른 사용자의 정보가 보인다

1절에서 본 대로 톰캣은 워커 스레드를 재사용한다. 여기에 4절의 결론 (a) "스레드가 살아 있는 한 값도 살아 있다"를 겹치면, "스레드가 죽으면 ThreadLocal 값도 사라진다"는 안전장치가 아예 작동하지 않는 환경이 된다.

문제 넣기만 하고 지우지 않는 인증 필터
void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
    currentUser.set(authenticate(request));   // alice로 인증해 스레드에 붙인다
    chain.doFilter(request, response);
    // remove()가 없다. 스레드는 alice를 담은 채 그대로 풀로 반납된다.
}

이 코드가 만드는 사고를 타임라인으로 보면 이렇다.

이 버그가 악랄한 이유 — 재현이 안 된다

사고가 성립하려면 두 조건이 동시에 맞아야 한다. 어느 요청이 어느 스레드에 배정될지는 그때그때 다르므로, 조건이 겹치는 순간은 부하가 높을수록 자주 만들어진다.

CS 문의 한 줄로 의심하는 법

"가끔 다른 사람 이름이 보인대요" = 정리되지 않은 ThreadLocal을 1순위로 의심

증상의 특징 세 가지를 함께 외운다 — ① 재현이 안 된다 · ② 트래픽이 많을 때만 난다 · ③ 특정 사용자가 아니라 "직전에 그 워커를 쓴 사람"의 데이터가 보인다. 세 번째가 결정적 단서다. 로그에서 사고 요청 직전에 같은 스레드 이름(http-nio-8080-exec-7 등)으로 처리된 요청을 찾으면 유출된 데이터의 원주인이 나온다.

8. 위험 ② 메모리 누수 — 약한 키, 강한 값

4절의 결론 (c)를 여기서 풀어 본다. 먼저 두 참조의 뜻을 못 박고 간다.

강한 참조 (strong reference)

우리가 평소에 쓰는 보통의 참조다. 강한 참조로 붙잡혀 있는 객체는 GC가 절대 회수하지 않는다.

약한 참조 (weak reference)

"붙잡고는 있지만 GC가 회수해도 좋다"는 뜻의 약한 연결이다. 다른 강한 참조가 없으면 GC가 그냥 가져간다.

누수 규모는 곱셈으로 계산된다

워커 스레드 200개 × 요청마다 넣은 객체 1MB = 200MB 상주

요청마다 파싱 결과나 조회 캐시 같은 큰 객체를 ThreadLocal에 넣고 지우지 않으면, 모든 워커가 한 번씩 그 코드를 지나간 시점부터 그만큼이 힙에서 회수되지 않는 상태로 고정된다. 새 요청이 값을 덮어쓰면 이전 값은 회수되지만, 항상 워커 수만큼의 객체는 상시 살아 있게 된다. 힙 덤프에서 보면 GC Root가 Thread인 객체가 워커 수만큼 나란히 잡히는 특징적인 모양이 된다.

재배포 시에는 더 큰 문제로 번진다 — 클래스로더 누수 시니어 변별

값 객체가 우리 애플리케이션의 클래스를 참조하고 있으면, 그 값을 통해 이전 버전의 클래스로더 전체가 붙잡힌다. 톰캣은 재배포 시 워커 스레드를 그대로 두고 애플리케이션만 갈아 끼우므로, 살아남은 스레드의 맵이 옛 클래스로더를 놓아주지 않는다.

9. 올바른 사용 — 요청 경계의 finally에서 remove()

오염과 누수는 원인이 하나이므로 대응도 하나다. 값을 넣은 스레드가 풀로 돌아가기 전에 반드시 지운다.

문제 정상 경로에서만 지운다 — 예외가 나면 값이 남는다
void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
    currentUser.set(authenticate(req));
    chain.doFilter(req, res);        // ← 여기서 예외가 터지면
    currentUser.remove();          // 이 줄은 실행되지 않는다
}
// 예외는 오히려 흔하다. 그럴 때마다
// 오염된 스레드가 하나씩 늘어난다.
개선 요청 경계에서 넣고, 반드시 finally에서 지운다
void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
    currentUser.set(authenticate(req));
    try {
        chain.doFilter(req, res);
    } finally {
        currentUser.remove();      // 정상·예외 어느 경로든 실행
    }
}
// 아래 체인에서 예외가 터져도 스레드는 어차피 풀로 반납된다.

철칙 — 이 짝을 깨지 않는다

set() 한 곳이 요청 경계이고, 같은 경계의 finally에서 remove() 한다
어디서 set 하나
필터 / 인터셉터 — 요청이 들어오고 나가는 지점이 한 곳으로 모이는 자리.
어디서 remove 하나
같은 필터의 finally — set과 remove가 같은 파일에서 눈에 함께 보여야 한다.
최악의 구조
서비스 계층 여기저기서 set하고 아무도 remove하지 않는 형태. 짝을 보장할 지점이 사라진다.
프레임워크가 정리해 준다 — 우리가 손댈 필요 없음
  • Spring Security — 컨텍스트 유지 필터가 요청 종료 시 컨텍스트를 지운다.
  • @Transactional — 트랜잭션 매니저가 커밋·롤백 후 커넥션 바인딩을 해제한다.
  • 스프링이 관리하는 MDC 필터 — 요청 종료 시 정리한다.

즉 ThreadLocal이 안전해서가 아니라, 넣은 쪽이 지우기까지 책임지기 때문에 문제가 없다.

우리가 정리해야 한다 — 사고의 대부분
  • 직접 선언한 ThreadLocal — UserContext, TenantContext, 요청 단위 캐시 등.
  • 직접 넣은 MDC 키 — MDC.put을 우리가 했다면 MDC.remove도 우리 몫이다.
  • 필터 체인 밖의 실행 경로 — 스케줄러·메시지 컨슈머·배치 잡에는 서블릿 필터가 걸리지 않는다.

세 번째가 특히 놓치기 쉽다 — "웹은 멀쩡한데 배치에서만 값이 섞인다"는 사고가 여기서 나온다.

세 가지 위험 한눈에 — 원인은 하나, 증상은 셋
위험직접 원인증상탐지 방법대응
① 데이터 오염 스레드 재사용 + remove() 누락 다른 사용자의 정보가 보인다 (보안 사고) 재현 불가 CS 문의 · 같은 스레드 이름의 직전 요청 추적 요청 경계 finally에서 remove()
② 메모리 누수 값이 강한 참조로 Thread에 매달림 힙 상주량 증가 · 재배포 시 Metaspace 누적 힙 덤프에서 GC Root가 Thread인 객체 · 톰캣 종료 경고 동일 — remove()
③ 전파 단절 실행 스레드가 바뀌면 맵이 바뀜 비동기 구간에서 null · traceId 유실 · 트랜잭션 밖 실행 비동기 로그에 traceId 없음 · 인가 검사 실패 제출 시점 복사(TaskDecorator) + 실행 후 정리
가상 스레드 스레드를 풀링하지 않는다 ① 오염은 사라진다 — 대신 스레드 수 = 값 개수 비용이 새로 생긴다

10. 위험 ③ 비동기 — 문맥이 아예 전파되지 않는다

오염이 "지워야 할 값이 남는" 문제라면, 이번엔 반대로 있어야 할 값이 없는 문제다. 원인은 같다 — ThreadLocal은 스레드에 붙어 있다.

문제 @Async 메서드는 톰캣 워커가 아니라 다른 풀의 다른 스레드에서 실행된다
@Async
public void sendMail() {
    User user = currentUser.get();   // null
    // 톰캣 워커의 맵에 있던 값이지, 이 실행 스레드의 맵에는 없다.
}

해결 — 작업을 제출하는 시점에 값을 복사해서 넘긴다

호출 스레드에서 값을 캡처해 두었다가, 실행 스레드에서 set → 작업 실행 → finally에서 remove 하는 껍데기로 작업을 감싼다.

개선 스프링의 TaskDecorator로 제출 시점의 문맥을 복사한다
public class ContextCopyingDecorator implements TaskDecorator {
    @Override
    public Runnable decorate(Runnable task) {
        // ↓ 이 줄은 '제출하는 스레드'(톰캣 워커)에서 실행된다 — 지금 캡처해야 한다.
        Map<String, String> mdc = MDC.getCopyOfContextMap();
        SecurityContext security = SecurityContextHolder.getContext();

        return () -> {
            // ↓ 이 안쪽은 '실행하는 스레드'(비동기 풀)에서 실행된다.
            if (mdc != null) MDC.setContextMap(mdc);
            SecurityContextHolder.setContext(security);
            try {
                task.run();
            } finally {
                // 비동기 풀의 스레드도 재사용되므로, 7절의 오염과 8절의 누수가
                // 여기서 그대로 재발한다. 정리는 여기서도 필수다.
                MDC.clear();
                SecurityContextHolder.clearContext();
            }
        };
    }
}

InheritableThreadLocal로 해결하려는 시도는 스레드풀에서 실패한다

InheritableThreadLocal은 이름 그대로 상속되는 ThreadLocal인데, 상속이 일어나는 시점이 자식 스레드를 new Thread()로 생성하는 그 순간이다. 스레드풀은 스레드를 애초에 딱 한 번 만들어놓고 계속 재사용하므로, 풀 스레드가 물려받는 것은 "풀이 스레드를 만들던 시점"의 값이지 "지금 작업을 제출한 요청"의 값이 아니다.

비동기 문맥 전파 — 세 가지 접근의 비교
방식복사 시점스레드풀에서정리 책임
InheritableThreadLocal스레드 생성 시점오답 — 옛날 값이 그대로 보인다여전히 우리 몫 (게다가 값도 틀림)
TaskDecorator / DelegatingSecurityContextExecutor작업 제출 시점정답 — 매 작업마다 그 순간의 값실행 스레드의 finally에서 반드시
파라미터로 명시 전달복사 개념 없음항상 옳다필요 없음 — 스택에 있으므로
가장 흔한 실수 — 데코레이터를 붙이고 정리를 빼먹는 것 문맥 복사만 넣고 실행 후 정리를 빠뜨리면, 이번에는 비동기 풀 쪽에서 7절의 오염과 8절의 누수가 똑같이 시작된다. 톰캣 풀만 재사용되는 게 아니라 비동기 실행기 풀도 똑같이 재사용된다. 복사와 정리는 언제나 한 쌍이다.

11. 가상 스레드와 ScopedValue — 전제가 뒤집힌다 시니어 변별

가상 스레드(virtual thread)는 JVM이 관리하는 가벼운 스레드로, OS 스레드에 1:1로 묶이지 않아 수십만 개를 만들어도 부담이 적다. 여기서 ThreadLocal의 전제가 뒤집힌다.

이 지점에서 ScopedValue가 나온 배경이 설명된다. 가상 스레드와 함께 프리뷰로 도입된 API로, ThreadLocal과 문제 의식은 같지만 설계가 반대다.

ThreadLocal vs ScopedValue — 설계 방향이 반대다
ThreadLocalScopedValue
값가변 — 아무 때나 set으로 바꿈불변 — 바인딩 시점에 정해짐
수명스레드 수명 (직접 remove 필요)정해진 실행 범위 (자동 해제)
정리 누락오염·누수로 이어짐구조적으로 불가능
 
// ScopedValue: 값이 유효한 범위를 코드 블록으로 명시한다
private static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

ScopedValue.where(CURRENT_USER, alice).run(() -> {
    handleRequest();   // 이 블록 안에서만 CURRENT_USER.get() 이 alice
});
// 블록을 벗어나면 바인딩이 자동으로 풀린다 — remove()를 잊을 방법이 없다
ThreadLocal의 손익은 스레드의 수명 모델에 종속된다
풀(재사용) → 오염·누수  |  가상 스레드(대량 생성) → 개수 비용

12. 판단 순서와 코드 리뷰 체크리스트

도입 전에 이 순서로 자문한다

1파라미터로 넘길 수 있는가? 관통하는 계층이 한두 개면 파라미터가 낫다. 의존성이 드러나고 테스트가 쉽다.먼저 검토
2진짜 횡단 관심사인가? 여러 계층을 관통하고 중간 계층 대부분이 그 값을 쓰지도 않는다면 ThreadLocal이 맞다.도입 근거
3넣는 지점과 지우는 지점이 한 쌍으로 보이는가? 요청 경계 하나에서 set·finally remove가 같이 보여야 한다.필수
4이 값이 비동기 경계를 넘는가? 넘는다면 TaskDecorator로 복사 + 실행 후 정리까지 설계에 포함한다.필수
5전용 접근자 뒤에 감췄는가? UserContext.currentUser()처럼 감싸면 저장 방식이 바뀌어도 호출부가 안 바뀌고, set/remove 지점이 한 클래스로 좁혀진다.권장

코드 리뷰 체크리스트 — 이 넷을 본다

  • new ThreadLocal이나 MDC.put이 보이면 같은 파일에서 remove를 찾는다. 없으면 그 자리에서 지적한다.
  • remove()가 finally 밖에 있는가 — 예외 경로에서 새어 나간다.
  • set이 서비스 계층 여기저기에 흩어져 있는가 — 짝을 보장할 지점이 없다는 뜻이다.
  • @Async·CompletableFuture·parallelStream 안에서 문맥을 꺼내 쓰는 코드가 있는가 — 데코레이터 없이는 null이다.

덧붙일 다섯 번째 — 필터 체인 밖의 진입점(스케줄러·컨슈머·배치)에서 문맥을 세팅하는 코드. 프레임워크의 정리가 닿지 않는 영역이라 같은 사고가 조용히 재현된다.

30초 답변 조립 — 이 순서로 말한다

1용도를 먼저 세운다 — "파라미터로 넘기기 어려운 요청 문맥(인증·traceId·트랜잭션 커넥션)을 스레드에 실어 나릅니다. SecurityContextHolder·MDC·@Transactional이 전부 이 구조입니다."10초
2저장 구조로 위험을 연역한다 — "값은 Thread 객체의 ThreadLocalMap에 들어가고 톰캣은 스레드를 재사용하므로, remove()를 빠뜨리면 다음 요청이 이전 사용자 값을 읽고, 값은 GC되지 않습니다."10초
3대응 두 방향으로 닫는다 — "요청 경계의 finally에서 remove()가 철칙이고, 반대로 스레드가 바뀌는 비동기 구간에서는 문맥이 전파되지 않아 TaskDecorator로 제출 시점 복사가 필요합니다."10초

시간이 더 주어지면 붙일 카드 — 약한 키·강한 값의 비대칭, 재배포 시 클래스로더 누수, InheritableThreadLocal이 오답인 이유, 가상 스레드에서 걱정거리가 뒤집히는 것. 넷 다 "그래서 어디에 무엇을 쓰느냐"로 되돌아와야 지식 자랑이 아니라 판단으로 들린다.

13. 꼬리질문 셀프 테스트 (13문항)

질문만 먼저 읽고 소리 내어 답해본 뒤 펼친다. 막히면 그 자리가 다시 읽어야 할 절이다.

ThreadLocalMap의 키는 약한 참조라던데, 그런데도 왜 메모리 누수가 생기나요?핵심힌트: 약한 참조인 것은 둘 중 어느 쪽인가

약한 참조인 것은 키(ThreadLocal 객체) 쪽뿐이고, 값은 강한 참조이기 때문이다.

ThreadLocal 객체가 다른 곳에서 참조를 잃으면 키는 GC되어 Entry가 stale entry(키가 null인 항목)가 된다. 하지만 Thread → ThreadLocalMap → Entry → value 사슬에서 값 쪽은 여전히 강한 참조라 값은 살아남는다. 키가 없어 꺼낼 수도 없는 값이 힙을 차지하는 상태다.

stale entry는 이후 그 맵에 set/get/remove가 일어날 때 부수적으로 청소될 수 있지만 보장이 없다. 그 스레드가 해당 맵을 다시 건드리지 않으면 영원히 남는다.

정리하면 약한 참조 키는 안전망이 아니라 미봉책이고, 확실한 해제는 remove() 하나뿐이다. (약한 참조 자체의 동작은 31-reference-types-weakhashmap과 연결된다.)

static final로 선언한 ThreadLocal도 누수가 되나요?함정힌트: 사라지는 것은 stale entry 문제뿐이다

된다. 오히려 stale entry 문제만 없어질 뿐 값 누수는 그대로다.

static final이면 ThreadLocal 객체가 애플리케이션이 사는 동안 강하게 참조되므로 키가 GC될 일이 없다 — 즉 stale entry는 생기지 않는다. 여기까지만 보고 "그럼 안전하겠네"로 넘어가는 것이 흔한 오해다.

값 쪽 이야기는 전혀 달라지지 않는다. remove()하지 않으면 워커 스레드 수만큼의 값이 상시 살아 있고, 재배포 환경에서는 그 값이 이전 앱의 클래스로더를 붙잡아 Metaspace 누수로 번진다.

선언 방식과 무관하게 원칙은 하나다 — 쓰고 나면 remove.

@Async나 CompletableFuture로 작업을 넘기면 ThreadLocal 값은 어떻게 되나요?핵심힌트: get()이 뒤지는 맵은 누구의 것인가

안 넘어간다. get()은 실행 중인 스레드의 맵을 뒤지는데 실행 스레드가 바뀌었기 때문이다. 값은 톰캣 워커의 맵에 있고, 비동기 풀 스레드의 맵은 그 문맥에 대해 비어 있다.

해결은 제출 시점 복사다. 작업을 감싸는 데코레이터에서 호출 스레드의 값(MDC 맵, SecurityContext 등)을 캡처해 두었다가, 실행 스레드에서 set하고 작업이 끝나면 finally에서 정리한다. 스프링이라면 Executor에 TaskDecorator를 끼우는 것이 표준적이고, Spring Security는 DelegatingSecurityContextExecutor를 제공한다.

가산점 여기에 정리(finally remove)를 빼먹으면 비동기 풀에서 오염과 누수가 그대로 재발한다는 것까지 말하면 좋다. 톰캣 풀만 재사용되는 게 아니라 비동기 실행기 풀도 똑같이 재사용된다.

InheritableThreadLocal을 쓰면 해결되지 않나요?함정힌트: 값이 복사되는 "시점"이 언제인가

스레드풀에서는 해결되지 않고, null이 나오는 것보다 나쁜 결과가 나온다.

InheritableThreadLocal이 값을 복사하는 시점은 자식 스레드를 생성하는 순간이다. 스레드풀은 스레드를 한 번만 만들어놓고 계속 재사용하므로, 풀 스레드가 물려받은 값은 "풀이 스레드를 만들던 시점"의 값이다. 지금 작업을 제출한 요청과는 아무 관계가 없다.

그래서 요청마다 다른 문맥을 기대했는데 모든 요청이 같은 옛날 값을 보게 된다. null이면 즉시 NPE로 드러나기라도 하는데, 그럴듯한 값이 나오면 발견이 한참 늦는다. Spring Security의 MODE_INHERITABLETHREADLOCAL 설정이 스레드풀 환경에서 권장되지 않는 이유이기도 하다.

풀 환경의 답은 상속이 아니라 제출 시점 복사(데코레이터)다.

Virtual Thread 환경에서는 ThreadLocal을 어떻게 봐야 하나요?시니어 변별힌트: 걱정거리가 사라지는 게 아니라 반대로 바뀐다

전제가 뒤집히므로 걱정거리도 바뀐다고 답하는 것이 핵심이다.

가상 스레드도 ThreadLocal을 지원하지만, 스레드를 풀링하지 않고 작업마다 새로 만들어 버리는 모델이라 재사용 오염 위험은 사라진다. 요청이 끝나면 스레드와 함께 맵도 값도 회수된다.

대신 반대편 비용이 커진다. 값은 스레드마다 하나씩 존재하므로 스레드가 수십만 개가 되면 값도 수십만 개다. "스레드당 하나씩 만들어 재사용해 비용을 아낀다"는 전제(예: SimpleDateFormat 재사용) 자체가 무너진다.

그래서 "값을 계속 바꿔 끼우는 가변 저장소"라는 용법 대신, 정해진 실행 범위 동안 불변 값을 공유하는 ScopedValue 같은 대안이 나왔다. 범위를 벗어나면 바인딩이 자동으로 풀리므로 remove() 누락이라는 사고 유형 자체가 사라진다.

한 문장으로 정리하면 ThreadLocal의 손익은 스레드의 수명 모델에 종속된다 — 풀(재사용)에서는 오염과 누수를, 가상 스레드(대량 생성)에서는 개수 비용을 걱정해야 한다.

remove() 대신 set(null)을 해도 되지 않나요?함정힌트: 지워지는 것과 덮어쓰는 것은 다르다

절반만 맞고, 권장되지 않는다.

set(null)은 Entry를 지우는 게 아니라 값 자리에 null을 덮어쓰는 것이다. 방금까지 붙잡고 있던 큰 객체에 대한 강한 참조는 끊기므로 그 객체의 누수는 막힌다. 여기까지는 맞다.

하지만 Entry 자체는 맵에 그대로 남는다. 그래서 ① 맵의 항목 수가 줄지 않아 맵이 커진 채로 유지되고, ② 무엇보다 get()이 null을 "값이 없음"이 아니라 "값이 null"로 돌려준다 — withInitial/initialValue로 초기값을 지정해 두었다면 초기화 로직이 다시 돌지 않는다. 있어야 할 기본값 대신 null을 받는 미묘한 버그가 여기서 나온다.

remove()는 Entry를 실제로 제거하므로 다음 get()이 "없음"으로 판정되어 초기화가 정상 동작한다. 정리 의도라면 언제나 remove()다.

Spring Security나 @Transactional도 ThreadLocal인데, 그것도 제가 remove()해야 하나요?힌트: 누가 set 했는지가 곧 누가 remove 해야 하는지다

프레임워크가 넣은 것은 프레임워크가 지운다. Spring Security의 컨텍스트 유지 필터는 요청이 끝나면 컨텍스트를 정리하고, 트랜잭션 매니저는 커밋·롤백 후 커넥션 바인딩을 해제한다. 스프링의 MDC 관련 필터도 마찬가지다.

위험한 것은 우리가 직접 선언한 ThreadLocal이다. 직접 set했다면 remove의 짝도 우리 책임이고, 그 짝을 보장할 수 있는 유일한 자리는 요청 경계(필터·인터셉터)의 finally다.

예외 상황도 있다. 필터 체인 바깥에서 도는 코드(스케줄러, 메시지 컨슈머, 배치 잡)는 서블릿 필터가 걸리지 않으므로 프레임워크의 정리도 기대할 수 없다. 그런 실행 경로에서 컨텍스트를 직접 세팅했다면 그 경로에서 직접 정리해야 한다. "웹 요청은 괜찮은데 배치에서만 값이 섞인다"는 유형의 사고가 여기서 나온다.

ThreadLocal 오염 사고는 왜 로컬 테스트에서 재현되지 않나요?힌트: 사고가 나려면 조건 두 개가 겹쳐야 한다

사고가 성립하려면 두 조건이 동시에 맞아야 하기 때문이다. ① 직전에 그 스레드를 쓴 요청이 값을 남겼고, ② 지금 요청은 그 값을 덮어쓰지 않는 경로(인증 불필요 API, 인증 실패 경로, 예외로 set을 건너뛴 경로)여야 한다.

개발자가 혼자 테스트하면 요청이 순차적이라 스레드가 한두 개만 돌고, 매 요청이 같은 경로로 들어가 값을 매번 덮어쓰므로 오염이 드러나지 않는다. 반대로 트래픽이 많은 운영에서는 워커 수십 개가 뒤섞이며 두 조건이 수시로 맞아떨어진다.

그래서 "가끔 다른 사람 이름이 보인대요" 같은 재현 불가 CS 문의는 정리되지 않은 ThreadLocal을 가장 먼저 의심해야 한다. 방어선은 테스트가 아니라 코드 리뷰에서 set과 remove의 짝을 확인하는 것이다.

톰캣이 종료할 때 "이 웹 애플리케이션이 ThreadLocal을 정리하지 않았다"는 경고를 남깁니다. 무슨 뜻인가요?시니어 변별힌트: 재배포하면 무엇이 갈리고 무엇이 남는가

클래스로더 누수(Metaspace 누수) 경고다. 톰캣은 재배포할 때 워커 스레드는 그대로 두고 애플리케이션만 갈아 끼운다. 그런데 살아남은 워커의 ThreadLocalMap에 이전 앱의 클래스로 만들어진 값 객체가 남아 있으면, 그 객체 → 그 객체의 클래스 → 그 클래스를 로딩한 이전 앱의 클래스로더 전체가 강하게 붙잡힌다.

결과적으로 이전 버전 앱의 모든 클래스 메타데이터가 Metaspace에서 회수되지 않고, 재배포를 반복할수록 쌓여 결국 OutOfMemoryError: Metaspace로 간다. "몇 번 배포하면 서버를 재시작해야 한다"는 관행이 생기는 원인 중 하나다.

톰캣은 종료 시점에 각 워커의 맵을 훑어 웹앱 클래스로더가 로딩한 클래스의 인스턴스가 남아 있는지 검사하고, 있으면 그 경고를 찍는다. 즉 이 경고는 곧 "요청 경계에서 remove()를 빠뜨린 코드가 있다"는 뜻이다.

ThreadLocal에 담으면 스레드 안전해지는 것 아닌가요?함정힌트: 격리되는 것은 "참조"이지 "객체"가 아니다

격리되는 것은 스레드마다 하나씩 갖는 참조일 뿐, 그 참조가 가리키는 객체가 자동으로 복제되지는 않는다.

그래서 여러 스레드의 ThreadLocal이 같은 객체를 가리키게 만들면 격리가 전혀 없다. 전형적인 실수가 이것이다.

// 잘못: 인스턴스를 하나 만들어 두고 그것을 초기값으로 준다
static final SimpleDateFormat SHARED = new SimpleDateFormat("yyyy-MM-dd");
static final ThreadLocal<SimpleDateFormat> FMT = ThreadLocal.withInitial(() -> SHARED);
// 모든 스레드가 같은 SHARED 하나를 본다 — ThreadLocal로 감쌌을 뿐 공유는 그대로다

static final ThreadLocal<SimpleDateFormat> FMT =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
// 람다가 스레드마다 실행되어 각자 새 인스턴스를 갖는다

같은 맥락에서 ThreadLocal에 담은 가변 컬렉션의 참조를 다른 스레드에 넘기면 그 순간 격리가 깨진다. ThreadLocal은 "공유하지 않게 해주는 도구"가 아니라 "공유하지 않도록 자리를 나눠주는 도구"다 — 공유 여부는 여전히 우리가 결정한다.

왜 ThreadLocal이 맵을 갖지 않고 Thread가 맵을 갖도록 설계했나요?시니어 변별힌트: 반대로 설계했다면 무엇이 필요해질까

반대 설계, 즉 ThreadLocal 안에 Map<Thread, Value>를 두는 방식을 상상해 보면 이유가 드러난다.

① 동기화가 필요해진다. 여러 스레드가 하나의 공유 맵에 동시에 쓰게 되므로 그 맵 자체를 동시성 자료구조로 만들거나 락을 걸어야 한다. 지금 구조는 각 스레드가 자기 맵만 건드리므로 동기화가 아예 필요 없다 — ThreadLocal.get()이 싼 결정적 이유다.

② 스레드가 죽어도 정리가 안 된다. 지금은 Thread 객체가 회수되면 그 안의 맵과 값이 통째로 함께 회수된다. 반대 설계라면 스레드가 끝나도 공유 맵에 항목이 남아, 죽은 스레드를 키로 하는 항목을 누군가 청소해야 한다.

③ 크기 특성이 유리하다. 한 스레드가 실제로 쓰는 ThreadLocal은 보통 몇 개뿐이라 스레드별 맵은 아주 작다. 반면 반대 설계의 맵은 스레드 수만큼 커진다. 정리하면 지금 구조는 동기화 제거 + 자동 회수를 얻은 설계이고, 그 대가로 "스레드가 죽지 않으면 값도 안 죽는다"는 이 문서의 모든 위험을 떠안은 것이다.

WebFlux 같은 리액티브 환경에서는 ThreadLocal을 쓸 수 있나요?가산점힌트: "한 요청 = 한 스레드"라는 전제가 아직 유효한가

쓸 수 없다고 보는 편이 안전하다. ThreadLocal이 성립하는 근거는 "한 요청은 한 스레드가 끝까지 처리한다"는 서블릿 모델의 전제인데, 리액티브에서는 그 전제가 깨진다.

리액티브 체인은 적은 수의 이벤트 루프 스레드가 여러 요청의 조각들을 번갈아 처리하고, publishOn/subscribeOn이나 비동기 I/O 콜백을 만날 때마다 실행 스레드가 바뀔 수 있다. 요청 초입에서 set한 값이 다음 연산자에서는 다른 스레드라 없을 수도 있고, 더 나쁘게는 다른 요청의 값이 남아 있는 스레드일 수도 있다.

그래서 리액티브에서는 문맥을 스레드가 아니라 실행 체인 자체에 매다는 방식(Reactor의 Context/contextWrite)을 쓴다. 발상은 ScopedValue와 같다 — "스레드에 붙인다"에서 "정해진 실행 범위에 붙인다"로 옮기는 것이다. 이 관점을 말할 수 있으면 ThreadLocal의 본질을 이해했다는 신호가 된다.

그냥 파라미터로 넘기면 되는 값을 ThreadLocal에 넣고 있지는 않은지, 판단 기준이 있나요?시니어 변별힌트: ThreadLocal은 숨겨진 전역 변수이기도 하다

ThreadLocal은 시그니처에 드러나지 않는 입력이다. 즉 스레드 범위의 전역 변수다. 그래서 남용하면 전역 변수의 모든 단점을 그대로 얻는다 — 메서드만 봐서는 무엇에 의존하는지 알 수 없고, 단위 테스트에서는 값을 미리 심어주지 않으면 NPE가 나며, 호출 순서에 따라 결과가 달라진다.

판단 기준은 "이 값을 파라미터로 넘겼을 때 시그니처가 오염되는 계층이 몇 개인가"다.

  • 한두 계층이면 파라미터가 낫다. 의존성이 명시적으로 드러나고 테스트가 쉽다.
  • 여러 계층을 관통하고, 중간 계층 대부분이 그 값을 쓰지도 않는다면 — 즉 진짜 횡단 관심사라면 ThreadLocal이 맞다. 인증 주체, traceId, 트랜잭션 커넥션, 로케일이 전형이다.

실무적 절충안도 말할 수 있으면 좋다. ThreadLocal을 코드 전체에 노출하지 말고 UserContext.currentUser() 같은 전용 접근자 뒤에 감춘다. 그러면 저장 방식(ThreadLocal → ScopedValue → Reactor Context)이 바뀌어도 호출부를 고칠 필요가 없고, set/remove를 부를 수 있는 지점도 한 클래스로 좁혀져 정리 누락을 구조적으로 줄일 수 있다.

한 줄 요약
ThreadLocal의 값은 ThreadLocal 객체가 아니라 Thread 객체 안의 ThreadLocalMap에 ThreadLocal 인스턴스를 키로 저장되므로 스레드가 살아 있는 한 값도 살아 있고, 톰캣은 워커 스레드를 재사용하기 때문에 요청 경계의 finally에서 remove()하지 않으면 이전 요청의 데이터가 다음 사용자에게 보이는 보안 사고와 (키는 약한 참조지만 값은 강한 참조라) GC되지 않는 메모리 누수가 함께 터진다 — 반대로 @Async·CompletableFuture처럼 스레드가 바뀌는 순간에는 문맥이 전파되지 않으므로 TaskDecorator로 제출 시점에 복사해야 하고 (InheritableThreadLocal은 생성 시점 복사라 풀에서는 오답), 가상 스레드에서는 재사용 오염이 사라지는 대신 스레드 수만큼의 값이 부담이 되어 ScopedValue가 등장했다.
