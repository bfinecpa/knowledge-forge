String 불변성과 StringBuilder — 불변이 공짜로 주는 것, 그리고 그 비용
"안 바뀐다"는 성질 하나에서 pool·스레드 안전·해시 캐싱·보안이 전부 파생된다

면접 질문: "String이 불변(immutable)인 이유와 그로 인한 장점은 무엇인가요? StringBuilder는 언제 쓰나요?"

핵심 관전 포인트 — 불변이란 "객체가 만들어진 뒤로는 그 상태가 절대 바뀌지 않는다"는 뜻이고, 그래서 String에서 값을 바꾸는 것처럼 보이는 메서드는 전부 원본을 그대로 둔 채 새 String을 만들어 돌려준다. String은 내부 문자 배열을 private final로 감추고 밖으로 절대 내주지 않으며 클래스 자체가 final이라 상속으로도 뚫을 수 없게 만들어 이 성질을 지킨다. 여기서 나머지가 전부 따라 나온다 — 바뀌지 않으니 같은 리터럴을 여러 참조가 공유해도 안전하고, 그래서 JVM이 String pool에 하나만 만들어 재사용하며(Java 7부터 힙에 있다), 바뀌지 않으니 hashCode를 한 번 계산해 캐싱할 수 있어 HashMap 키로 최적이고, 바뀌지 않으니 여러 스레드가 동기화 없이 읽어도 되고, 바뀌지 않으니 보안 검증을 통과한 값이 사용 시점까지 그대로임이 보장된다. 비용은 "수정처럼 보이는 모든 연산이 새 객체 생성"이라는 것이고, 루프 안에서 +=로 누적하면 매 회전마다 지금까지의 전체를 복사하므로 총 복사량이 0+1+2+…+(n-1) = n(n-1)/2, 즉 O(n²)가 된다. 그래서 반복 누적 지점에서만 내부 배열을 고쳐 쓰는 StringBuilder로 비용을 지불한다 — 반대로 한 표현식 안의 + 연결은 컴파일러가 알아서 한 번에 처리하므로 손대지 않는다.
  • 1
    정의와 지키는 방법을 먼저 못박습니다. 불변은 "생성 이후 상태가 절대 바뀌지 않는다"는 뜻이고, toUpperCase() 같은 메서드는 원본을 두고 새 String을 반환합니다. String은 세 자물쇠로 이 성질을 지킵니다 — ① 문자 배열을 private final로 은닉, ② 그 배열을 밖으로 절대 안 내주고 복사본만(방어적 복사), ③ 클래스를 final로 만들어 가변 하위 클래스를 원천 봉쇄.
  • 2
    장점 네 가지가 나란한 항목이 아니라 전부 같은 뿌리에서 나온다고 말합니다. 안 바뀌니 공유가 안전해서 JVM이 String pool로 리터럴을 하나만 두고(Java 7부터 힙, 그 전엔 PermGen), 안 바뀌니 가변 상태가 없어 동기화·방어적 복사가 불필요하고, 안 바뀌니 hashCode를 필드에 캐싱할 수 있어 HashMap 키로 최적이며, 안 바뀌니 검증한 값이 사용 시점까지 동일해서 TOCTOU 취약점이 성립하지 않습니다.
  • 3
    비용과 판단 기준으로 닫습니다. 대가는 수정마다 새 객체이고, 루프 누적에서 총 복사량 n(n-1)/2의 O(n²)로 터집니다. 그래서 루프·분기를 넘나드는 누적 구간에만 StringBuilder를 씁니다. 반대로 한 표현식 안의 +는 손대지 않습니다 — Java 9부터 invokedynamic의 makeConcatWithConstants로 컴파일되어 JVM이 최적 코드를 만들어 주기 때문입니다. 공유가 없는 지역 버퍼라면 StringBuffer가 아니라 StringBuilder가 기본값입니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "String이 불변(immutable)인 이유와 그로 인한 장점은 무엇인가요? StringBuilder는 언제 쓰나요?"

출제 의도 — 불변 객체가 왜 스레드 안전과 캐싱(String pool)을 공짜로 주는지 이해하는지를 본다. 이 감각이 있는 사람은 도메인 객체 설계에서도 불변을 기본값으로 두어 동시성 버그의 반을 원천 차단한다.

질문이 두 문장인 것에 주목한다. 앞 문장("불변인 이유와 장점")은 원리를 묻고, 뒤 문장("StringBuilder는 언제")은 그 원리의 비용을 아는가를 묻는다. 즉 이 질문은 "불변의 좋은 점을 외웠는가"가 아니라 "좋은 점과 대가를 함께 저울에 올릴 수 있는가"를 본다. 장점만 나열하고 끝내면 절반만 답한 것이다.

이 문서가 겨냥하는 약점 — "String은 불변이라 스레드 안전하고 String pool을 쓴다"는 문장은 대부분 갖고 있다.
그런데 그 다음이 안 나온다. "불변이 정확히 뭔데요?", "그런데 s += "x"는 되잖아요?", "pool 때문에 불변인가요, 불변이라 pool인가요?" — 여기서 갈린다.
갈리는 원인은 하나다. 네 가지 장점을 서로 무관한 항목으로 외웠기 때문이다. 실제로는 전부 "안 바뀐다" 하나에서 유도된다. 그래서 이 문서는 1절을 "불변의 정의"로 시작해서 네 갈래를 그 뿌리에서 뻗어 나가게 배치했다.

이렇게 답하면 반쪽이다

  • "String pool 때문에 불변입니다" — 인과가 거꾸로다. 불변이 먼저이고 pool은 그 결과로 가능해진 최적화다.
  • "불변이라 값을 바꿀 수 없습니다" — 그럼 s += "x"는 왜 되냐는 반문에서 무너진다. 바뀌는 건 참조다.
  • "문자열 연결은 무조건 StringBuilder" — 과잉 반응. 한 표현식 안의 +는 컴파일러가 이미 처리한다.
  • "StringBuffer가 더 안전하니 그걸 쓰죠" — 공유되지 않는 지역 버퍼에 락을 거는 것은 순수한 낭비다. 게다가 순서를 보장해 주지도 않는다(10절).
  • "String pool은 Metaspace(PermGen)에 있습니다" — Java 6 이전 지식. Java 7부터 일반 힙이다.
  • "불변이라 항상 좋습니다" — 비밀번호는 반례다. 지울 수 없다는 것이 단점이 되는 경우가 있다.

이 문서가 채워 주는 것

  • 불변의 정의부터 — "화살표를 바꾸는 것"과 "상자 안을 바꾸는 것"의 구분을 도식으로 못박는다.
  • 세 자물쇠와 각 자물쇠가 없으면 뚫리는 구멍을 하나씩 짝지어 본다 — 그대로 불변 VO 설계 체크리스트가 된다.
  • 네 가지 장점을 뿌리에서 유도하는 순서로 배치한다. 외울 항목이 넷이 아니라 하나가 된다.
  • O(n²)의 실체를 복사량 누적표와 도식으로 — "느리다"가 아니라 몇 글자를 복사하는지로.
  • StringBuilder의 배열 확장과 초기 용량이 왜 이득인지.
  • 고치지 말아야 할 곳(한 표현식의 +)과 고쳐야 할 곳(루프 누적)을 바이트코드가 놓이는 위치로 구분한다.

이 문서 전체를 지탱하는 문장 하나

불변은 "안 바뀐다"는 성질 하나이고,
장점 넷과 비용 하나는 전부 거기서 유도된다

네 가지 장점을 각각 외우려 하면 면접장에서 하나쯤 빠진다. 대신 "안 바뀌니까 ○○해도 된다"라는 틀 하나를 잡고 공유해도 / 동기화 없이 읽어도 / 해시를 저장해 둬도 / 검증 결과를 믿어도 네 개를 채우면 된다. 인출 단서가 하나라서 무너지지 않는다.

1. 불변이란 무엇인가 — 참조 재할당 vs 상태 변경

"String은 불변이다"라는 문장을 외우기 전에 불변이 무엇인지부터 정해야 한다. 여기가 흐릿한 채로 넘어가면 뒤에 나오는 String pool도, 해시 캐싱도 전부 따로 노는 암기 항목이 된다.

불변(immutable) = 객체가 생성된 이후로 그 상태가 절대 바뀌지 않는다

한 번 "hello"라는 내용으로 태어난 String 객체는 세상이 끝날 때까지 "hello"다. 어떤 메서드를 불러도, 어떤 스레드가 건드려도 그 객체의 내용은 그대로다.

1-1. 그러면 toUpperCase()는 무엇을 하는가

원본은 손대지 않고 결과를 담은 새 String을 만들어 돌려준다. 이 사실은 코드 한 줄로 손에 잡힌다.

String s = "hello";

s.toUpperCase();   // 반환값을 아무 데도 안 받았다
System.out.println(s);
// 출력: hello
// 대문자로 바뀌지 않았다. toUpperCase()가 만든 "HELLO"는
// 어디에도 담기지 않은 채 버려졌고, s가 가리키는 객체는 그대로다.

String upper = s.toUpperCase();   // 반환값을 받아야 쓸 수 있다
System.out.println(s + " / " + upper);
// 출력: hello / HELLO
// "HELLO"는 별개의 새 객체다. s는 여전히 "hello"를 가리킨다.

Java를 막 시작한 사람이 가장 흔히 밟는 지뢰가 빨간 줄이다. s.toUpperCase();라고만 쓰고 s가 바뀌었을 거라 기대하는 것 — 이 코드가 아무 일도 안 하는 이유가 곧 불변의 정의다.

외우는 대신 알아채는 법 — 반환 타입을 본다 String의 "값을 바꾸는 것처럼 보이는" 메서드는 전부 String을 반환한다(toUpperCase, trim, replace, concat, substring, strip…). 반환값이 있다는 것 자체가 "결과는 여기 새로 담아 준다"는 신호다. 반대로 진짜로 자기를 바꾸는 메서드는 void이거나 자기 자신을 반환한다(StringBuilder의 append). 시그니처만 봐도 불변인지 가변인지 짐작할 수 있다.

1-2. 반드시 갈라야 하는 것 — 화살표와 상자

"참조를 다른 객체로 바꿔 끼우는 것"과 "객체의 내용을 바꾸는 것"은 완전히 다른 일이다.

String s = "hello";에서 변수 s의 칸에 들어 있는 것은 문자열 자체가 아니라 그 String 객체가 힙 어디에 있는지를 가리키는 주소값이다. 그래서 s = s.toUpperCase();가 하는 일은 아래 그림처럼 화살표를 옮기는 일이다.

가장 흔한 오답 — "불변인데 s += "x"는 왜 되나요?"

s += "x"는 "지금까지의 s와 x를 합친 새 String을 만들어, 그 주소를 s에 다시 대입하라"로 번역된다. 원래 객체는 손대지 않았다. 이 질문은 "참조의 재할당"과 "객체 상태의 변경"을 구분하는지만 본다. 그 구분을 말하지 않고 "새 객체가 생깁니다"라고만 답하면 절반이다.

2. 세 개의 자물쇠 — String이 불변을 지키는 법

"바꾸는 메서드를 안 만들었다"만으로는 불변이 지켜지지 않는다. 우회로가 여럿 있기 때문이다. String은 그 우회로를 하나씩 막아 놓았고, 그 방법 세 가지가 그대로 불변 객체를 만드는 교과서 패턴이다.

2-1. 자물쇠 ① — 상태를 private final로 감춘다

실제로 String 클래스의 내부를 들여다보면 이렇게 되어 있다(리플렉션으로 필드 목록을 뽑아 확인한 결과다).

// String 클래스의 필드 목록
value : private final byte[]     // 실제 문자들이 담긴 배열
coder : private final byte       // 1바이트로 저장했는지 2바이트로 저장했는지
hash  : private int               // final이 아니다 — 지연 초기화 캐시 (5절)

value가 실제 문자들이 담긴 배열이다. private이라 클래스 밖에서는 접근 자체가 안 되고, final이라 String 자기 코드조차 다른 배열로 바꿔 끼울 수 없다.

배열이 char[]가 아니라 byte[]인 이유 가산점 Java 9부터 Compact Strings라는 최적화가 들어가, 문자열이 라틴-1 범위(한 글자를 1바이트로 표현할 수 있는 문자)로만 이루어져 있으면 글자당 2바이트가 아니라 1바이트로 저장한다. 어느 방식으로 저장했는지를 표시하는 것이 coder 필드다. 대부분의 실무 문자열(ID, 코드값, 영문 로그)이 라틴-1이라 힙 사용량이 눈에 띄게 준다. Java 8까지는 private final char[] value였다.

2-2. 자물쇠 ② — 내부 배열을 밖으로 절대 내주지 않는다

필드를 private으로 감춰도, 그 배열을 그대로 반환하는 메서드가 하나라도 있으면 불변이 무너진다. 받은 쪽에서 배열 원소를 바꾸면 String 내용이 바뀌기 때문이다.

가정 만약 내부 배열을 그대로 반환했다면
// 실제 String에는 이런 메서드가 없다
char[] leaked = s.getInternalArray();  // 내부 배열 그대로
leaked[0] = 'X';                        // String 내용이 밖에서 바뀐다

System.out.println(s);   // "Xello"  ← 불변 붕괴

// 이 순간 무너지는 것들:
//  · pool에서 이 객체를 공유하던 모든 코드가 함께 오염
//  · 캐싱해 둔 hashCode가 거짓말을 시작
//  · 검증을 통과한 경로 문자열이 다른 경로로 둔갑
실제 항상 복사본을 준다 — 방어적 복사
char[] copy = s.toCharArray();   // 새 배열에 복사해서 반환
copy[0] = 'X';                     // 복사본만 바뀐다

System.out.println(s);      // "hello"  ← 무사하다
System.out.println(copy);   // "Xello"

// 대가: 배열 길이만큼의 복사 비용을 매번 낸다.
// 불변을 지키기 위해 성능을 지불한 지점이다.

방어적 복사(defensive copy)

내부에 든 가변 물건을 밖으로 내보낼 때 원본 대신 복제품을 주는 기법이다. "방어"라는 이름은 "밖에서 원본을 건드리는 것을 미리 막는다"는 뜻이다. 받을 때도 똑같이 적용해야 한다 — 생성자로 배열이나 컬렉션을 받아서 그대로 필드에 저장하면, 넘겨준 쪽이 여전히 그 원본을 들고 있으므로 나중에 바꿀 수 있다. 들어올 때 복사, 나갈 때 복사 — 이 두 방향을 세트로 기억한다.

2-3. 자물쇠 ③ — 클래스를 final로 만들어 상속을 봉쇄한다

앞의 둘을 다 해도 구멍이 하나 남는다. 누군가 String을 상속해서 가변인 하위 클래스를 만들면, 그 객체는 String 타입 자리에 들어갈 수 있으면서 내용이 바뀐다.

// 만약 String이 final이 아니었다면 가능했을 공격
class EvilString extends String {
    private String current;
    @Override public boolean equals(Object o) {
        current = flipEveryOtherCall();   // 부를 때마다 다른 답을 준다
        return …;
    }
}

// 이 객체를 String 파라미터 자리에 넘기면, 받는 쪽은
// "String이니까 안 바뀐다"고 믿고 검증 한 번 하고 그 값을 계속 쓴다
//  → 그 믿음이 깨진다. 검증 때와 사용 때의 답이 다르다.

java.lang.String은 실제로 final class다(Modifier.isFinal(String.class.getModifiers())가 true를 반환한다). 그래서 이 공격 코드는 애초에 컴파일되지 않는다.

왜 이 자물쇠가 가장 잊히기 쉬운가 앞의 둘은 "내가 안 바꾸면 되잖아"라는 감각으로 이해되는데, 세 번째는 "제3자가 타입 시스템을 속인다"는 시나리오라 잘 안 떠오른다. 그런데 실무에서 이 구멍이 실제로 문제가 되는 자리가 있다 — 불변 VO를 만들었는데 클래스를 final로 안 잠근 경우다. 누군가 상속해 getAmount()가 호출마다 다른 값을 주게 만들면, 그 VO를 신뢰한 모든 계산이 깨진다. record가 암묵적으로 final인 이유가 이것이다.

3. 파생 ① 안전한 공유 — String pool은 원인이 아니라 결과다

String pool을 먼저 설명하고 "그래서 불변이어야 한다"고 말하는 순서를 자주 보는데, 인과가 거꾸로다.

불변이 먼저이고 pool이 나중이다

같은 내용의 문자열을 여러 곳이 하나의 객체로 공유한다고 해 보자. 만약 String이 가변이라면 어떤 일이 벌어지는가.

3-1. 확인 코드 — ==가 갈리는 지점

String a = "hello";
String b = "hello";
System.out.println(a == b);        // 출력: true  ← 같은 pool 객체

String c = new String("hello");
System.out.println(a == c);        // 출력: false ← 내용은 같은데 다른 객체
System.out.println(a.equals(c));   // 출력: true  ← 값 비교는 언제나 이쪽

System.out.println(c.intern() == a);  // 출력: true  ← pool 대표를 달라고 요청
1
a == b가 true인 이유
두 변수가 pool에 있는 같은 하나의 객체를 가리키기 때문이다. ==는 값이 같은지 묻는 연산자가 아니라 "두 참조가 같은 객체를 가리키는가"를 묻는 참조 비교다. 값이 같아서 true가 나온 게 아니라 진짜로 같은 객체여서다.

new는 건너뛴다
3

대표 요청

문자열 값 비교에 ==를 쓰면 안 되는 이유가 정확히 여기 있다

리터럴끼리는 우연히 맞고, 런타임에 만들어진 문자열(HTTP 파라미터, DB 조회 결과, substring 결과)이 끼는 순간 틀린다.

그리고 이 버그는 로컬 테스트에서는 잘 통과한다 — 테스트에 쓰는 문자열은 대부분 리터럴이기 때문이다

"운영에서만 터지는 버그"의 전형이다. 코드 리뷰에서 str1 == str2를 보면 테스트가 초록불이어도 무조건 지적해야 하는 이유가 이것이다.

4. 파생 ② 스레드 안전 — 문제를 푼 게 아니라 조건을 없앴다

동시성 버그의 근원을 한 문장으로 줄이면 "공유된 가변 상태(shared mutable state)"다. 여러 스레드가 같은 데이터를 보는데(공유) 그 데이터가 바뀔 수 있으면(가변), 읽는 도중에 바뀌거나 두 스레드의 수정이 서로를 덮어쓰는 사고가 생긴다.

불변은 이 조합에서 '가변'을 제거한다. 공유는 그대로 두되 바뀔 수가 없게 만드는 것이다. 그러면 경쟁 상태(race condition)가 성립할 여지 자체가 사라진다 — 아무리 여러 스레드가 동시에 읽어도 읽는 값은 언제나 같다.

문제를 해결한 게 아니라 문제가 생길 조건을 없앤 것 — 이것이 불변 설계의 가장 큰 값이다

4-1. 정확히 반대 사례 — static SimpleDateFormat

이 대비를 알아 두면 불변의 값이 훨씬 선명해진다. SimpleDateFormat은 내부에 파싱 중간 상태를 들고 있는 가변 객체인데 static 필드에 담아 공유하는 순간, 위 매트릭스의 빨간 칸으로 정확히 들어간다.

Before 공유 + 가변 = 빨간 칸
public class DateUtil {
    private static final SimpleDateFormat FMT =
        new SimpleDateFormat("yyyy-MM-dd");   // 가변 객체를 static으로

    public static String format(Date d) {
        return FMT.format(d);   // 두 요청이 서로의 중간 계산을 덮어쓴다
    }
}
// 증상: 평소엔 멀쩡하다가 부하가 걸리면
//       엉뚱한 날짜가 나오거나 예외가 터진다.
//       재현이 안 돼서 원인 찾기가 가장 어려운 유형.
After 불변 타입으로 = 파란 칸
public class DateUtil {
    private static final DateTimeFormatter FMT =
        DateTimeFormatter.ofPattern("yyyy-MM-dd");  // 불변 타입

    public static String format(LocalDate d) {
        return FMT.format(d);   // 상태를 안 들고 있으므로 공유해도 안전
    }
}
// DateTimeFormatter는 불변이라 static 공유가 오히려 권장된다.
// 같은 static 필드인데 결과가 정반대인 이유 = 가변이냐 불변이냐.
여기서 얻어야 할 판단 기준 static 필드 자체가 나쁜 게 아니다. static + 가변이 나쁜 것이다. 그래서 필드를 static으로 올릴 때 던져야 할 질문은 "이 타입이 불변인가?" 하나다. 불변이면 공유가 오히려 이득(객체 하나만 만들면 된다)이고, 가변이면 재현 안 되는 버그의 씨앗이다. String이 static 상수로 아무 걱정 없이 쓰이는 것도 같은 이유다.

5. 파생 ③ hashCode 캐싱 — 불변이 아니면 불가능한 최적화

HashMap의 키로 가장 많이 쓰이는 타입이 String이다. 그리고 HashMap은 조회할 때마다 키의 hashCode()를 호출한다(2단계 조회 중 1단계 — 해시값으로 버킷을 고르는 단계).

여기서 문제가 하나 보인다. 문자열의 해시는 글자를 전부 훑어야 계산된다. 길이 100인 URL을 키로 쓰면 조회 한 번마다 100글자를 다 도는 셈이다. 그런데 String은 이 비용을 한 번만 낸다.

5-1. 왜 이 캐싱이 불변일 때만 가능한가

내용이 바뀔 수 있는 객체라면, 저장해 둔 해시값은 내용이 바뀌는 순간 틀린 값이 된다. 그래서 가변 객체는 매번 다시 계산할 수밖에 없다. 그런데 문제는 성능만이 아니다.

규칙 — HashMap·HashSet의 키로 쓸 타입은 반드시 불변으로

String, Integer 같은 기본 타입 래퍼, LocalDate는 전부 불변이라 안전하다. 반대로 직접 만든 가변 클래스를 키로 쓰면 위 사고가 난다. 불가피하다면 최소한 "맵에 넣은 뒤에는 절대 수정하지 않는다"는 규약을 두어야 하는데, 규약은 언젠가 깨진다. 타입 자체를 불변으로 만드는 것이 정공법이다.

5-2. hash 필드에 대해 덧붙이면 가산점 가산점

① hash는 왜 final이 아닌가

앞의 필드 목록에서 봤듯 private int hash로 final이 아니다. 최초 호출 시점에 계산해 채우는 지연 초기화 방식이기 때문이다.

여러 스레드가 동시에 처음 hashCode()를 부르면 각자 계산해 각자 필드에 쓸 수 있는데, 이것이 문제가 안 되는 이유는 어차피 계산 결과가 항상 같은 값이라 누가 써도 결과가 동일하기 때문이다. 그래서 동기화 없이 둔다. 이런 형태를 무해한 경쟁(benign data race)이라고 부른다.

② hashIsZero라는 boolean이 하나 더 있다

hash의 초기값이 0인데 실제 해시가 0인 문자열도 존재한다(빈 문자열이 그렇다).

그래서 "아직 계산 안 함"과 "계산했더니 0"을 구분할 방법이 필요하고, 그 구분자가 이 필드다. 없으면 해시가 0인 문자열은 조회마다 계산을 반복하게 된다.

이 두 가지가 왜 "가산점"인가 "불변이라 캐싱할 수 있다"까지는 많이들 말한다. 그 다음 "그런데 그 캐시 필드는 final이 아닌데 왜 스레드 안전한가?"는 불변과 스레드 안전의 관계를 진짜로 이해했는지 확인하는 지점이다. 답의 핵심은 "입력이 불변이라 계산이 순수 함수이고, 그래서 경쟁이 무해하다"는 한 줄이다.

6. 파생 ④ 보안 — TOCTOU가 성립하지 않는 이유

파일 경로, DB 접속 URL, 클래스 이름, 리다이렉트 대상 주소는 전부 String으로 오간다. 이런 값은 대개 "검증하고 → 쓴다"는 두 단계를 거친다.

public void serve(String path) {
    if (!path.startsWith("/public/")) {   // ① 검증: 공개 디렉토리인가
        throw new AccessDeniedException();
    }
    // ... 다른 처리 (여기서 시간이 흐른다) ...
    Files.readAllBytes(Path.of(path));    // ② 사용: 실제로 파일을 연다
}

인출 카드 — 파생 네 가지를 한 틀로

① 안 바뀌니 공유해도 된다
→ JVM이 리터럴을 하나만 만들어 재사용 = String pool (Java 7부터 힙)
② 안 바뀌니 동기화 없이 읽어도 된다
→ "공유 + 가변"에서 가변이 빠져 경쟁 상태가 성립 불가
③ 안 바뀌니 해시를 저장해 둬도 된다
→ hashCode 캐싱, 그리고 유령 항목 사고가 구조적으로 불가능
④ 안 바뀌니 검증 결과를 믿어도 된다
→ 검사와 사용 사이에 바뀔 수 없음 = TOCTOU 회피
넷을 따로 외우지 않는다 — "안 바뀌니까 ○○해도 된다" 하나로 인출한다

6-1. 반대 방향의 예외 — 비밀번호 가산점

비밀번호는 오히려 String이 아니라 char[]로 다루라는 권고가 있다. 이유가 정확히 불변 때문이다 — String은 내용을 덮어쓸 수 없으므로, 다 쓰고 나서도 GC가 회수할 때까지 평문 비밀번호가 힙에 남는다. 그 사이에 힙 덤프를 뜨면 그대로 노출된다.

가능
char[]는 다 쓴 직후 Arrays.fill(pw, '\0')으로 내용을 그 자리에서 지울 수 있다. JPasswordField.getPassword()나 Console.readPassword()가 char[]를 반환하는 것이 그래서다.
불가능
String은 참조를 null로 만들어도 힙의 평문은 그대로 남는다. 심지어 리터럴이거나 intern()을 거쳤다면 pool에 남아 애플리케이션 수명 내내 살아 있을 수도 있다.
불변이 항상 이득인 것은 아니다 —
"지울 수 있어야 하는 값"에는 오히려 단점이 된다

여기까지 말하면 도구의 양면을 보는 사람으로 읽힌다. 장점만 줄줄 외운 사람과 갈리는 지점이 바로 이 한 문장이다.

7. 비용 — 루프 누적이 O(n²)인 이유를 실제로 더해 본다

불변의 대가는 명확하다. 수정처럼 보이는 모든 연산이 새 객체를 만든다. 대부분의 상황에서는 문제가 안 되는데, 딱 한 곳에서 심각해진다. 루프 안에서 문자열을 누적할 때다.

String csv = "";
for (int i = 0; i < n; i++) {
    csv += "x";        // 매 회전마다 무슨 일이 일어나는가?
}

csv += "x"는 "csv 뒤에 x를 덧붙인다"처럼 읽히지만, 불변이므로 그런 일은 일어날 수 없다. 실제로 일어나는 일은 지금까지의 csv 전체를 새 배열로 복사하고 그 뒤에 "x" 한 글자를 붙여 새 String을 만든 뒤, 변수 csv가 그 새 객체를 가리키게 하는 것이다. 이전 객체는 버려져 GC 대상이 된다.

회전마다 실제로 무슨 일이 일어나는가 — 복사량을 직접 센다

8. StringBuilder — 내부 배열을 늘려가며 재사용한다

StringBuilder는 불변 원칙을 의도적으로 버린 가변 문자 버퍼다. 내부에 char[](정확히는 byte[]) 하나를 들고 있고, append()는 새 객체를 만드는 대신 그 배열의 뒤쪽 빈 자리에 글자를 써 넣는다. 배열이 꽉 차면 더 큰 배열을 새로 만들어 옮기고, 이후에는 다시 그 배열을 계속 쓴다.

Before 루프 안 +=
// 회전마다 지금까지의 전체를 복사한다
String csv = "";
for (Order o : orders) {          // 주문 1만 건이면
    csv += o.getId() + ",";       // 약 5천만 글자 복사
                                  // + 버려진 객체 1만 개
}
// 매 회전: 새 배열 할당 → 전체 복사 → 조각 붙이기 → 이전 객체 폐기
After StringBuilder
// 하나의 버퍼에 이어 붙이고 마지막에 한 번만 String을 만든다
StringBuilder sb = new StringBuilder();
for (Order o : orders) {
    sb.append(o.getId()).append(',');   // 버퍼 끝에 쓰기만
                                        // 복사 없음
}
String csv = sb.toString();   // 여기서 딱 한 번 String이 생긴다

8-1. 배열이 늘어나는 방식 — 두 배씩

StringBuilder sb = new StringBuilder();
System.out.println(sb.capacity());              // 출력: 16   (기본 용량)

sb.append("0123456789ABCDEF");                  // 딱 16글자
System.out.println(sb.capacity());              // 출력: 16   (아직 안 넘침)

sb.append("G");                                 // 17번째 글자 → 확장 발생
System.out.println(sb.capacity());              // 출력: 34   (16*2+2로 확장)

System.out.println(new StringBuilder("abc").capacity());  // 출력: 19  (16 + 초기 문자열 길이)

초기 용량을 주면 확장 복사를 아예 없앨 수 있다 가산점

최종 크기를 대충이라도 알면 초기 용량을 주는 것이 이득이다.

StringBuilder sb = new StringBuilder(orders.size() * 20);  // 넉넉히 잡아 둔다
// → 확장 복사가 한 번도 일어나지 않는다

선을 그어 두는 것이 중요하다. 이건 수십만 건을 다루는 배치 같은 곳에서 의미 있는 최적화이고, 일반 요청 처리에서는 기본값으로 충분하다. 면접에서 이 말을 덧붙이면 "최적화를 알지만 남발하지 않는 사람"으로 읽힌다.

설계 패턴으로 읽으면 — "안에서는 가변, 밖으로는 불변" StringBuilder로 조립하다가 toString()으로 뽑는 순간 결과는 불변 String이 된다. 가변의 편의는 메서드 안에 가두고, 밖으로 나가는 값은 불변으로 확정하는 것 — 이것이 String / StringBuilder 쌍이 보여 주는 패턴이고, 불변 VO에 빌더를 붙이는 설계가 그대로 같은 모양이다(11절).

9. 한 표현식의 +는 컴파일러가 처리한다 — 손대지 마라

여기서 자주 나오는 과잉 반응이 있다. "문자열 연결은 무조건 StringBuilder로 바꿔야 한다"는 것인데, 틀렸다. 한 표현식 안에서 끝나는 + 연결은 컴파일러가 이미 효율적인 코드로 바꿔 준다.

9-1. 컴파일러는 무엇을 해 주고 무엇을 안 해 주는가

Java 9부터 문자열 연결은 invokedynamic이라는 바이트코드 명령으로 컴파일되고, 실행 시점에 JVM(StringConcatFactory)이 그 연결에 가장 맞는 코드를 만들어 준다. 전체 길이를 미리 계산해 딱 맞는 버퍼를 한 번 잡고 채우는 식이라, 손으로 StringBuilder를 쓰는 것보다 나을 때도 있다. Java 8까지는 컴파일러가 StringBuilder 체인으로 바꿔 넣었는데, 어느 쪽이든 개발자가 손으로 고칠 이유가 없다는 결론은 같다.

그러면 왜 루프는 안 구해주는가? 최적화의 단위가 하나의 표현식이기 때문이다. 컴파일러는 한 회전 안의 s + x + ","를 효율적으로 만들어 줄 뿐, 회전과 회전 사이에 버퍼를 이어 쓰는 판단까지는 하지 않는다. 그건 프로그램의 의도를 바꾸는 변형이기 때문이다.

"의도를 바꾸는 변형"이라는 말의 뜻 루프를 StringBuilder로 바꾸려면 컴파일러가 "중간 결과인 s를 아무도 안 본다"는 것을 증명해야 한다. 그런데 루프 안에서 s를 로깅하거나, 조건에 따라 밖으로 내보내거나, 다른 변수에 담을 수도 있다. 그 모든 경우를 안전하게 판별하는 것보다, 개발자가 "여기는 누적 구간"이라고 명시하는 편이 훨씬 확실하다. 그래서 이 판단만은 사람의 몫으로 남아 있다.

11. 불변 VO로 확장 · 전체 한 장 · 인출 카드

12. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 펼쳐서 읽기만 하면 "아는 것 같은 느낌"만 남고 인출은 안 된다. 막힌 질문은 해당 절로 돌아간다.

new String("hello")와 리터럴 "hello"의 차이는? intern()은 언제 쓰나요?힌트: 결론은 "그러니까 값 비교는 항상 equals"로 닫아야 한다 핵심

리터럴은 String pool에 있는 공유 객체를 재사용하고, new String(...)은 그 pool 공유를 일부러 건너뛰고 힙에 새 객체를 하나 더 만든다. 그래서 리터럴끼리는 ==가 true인데 new가 끼는 순간 false가 된다.

a == b → true  ·  a == c → false  ·  a.equals(c) → true  ·  c.intern() == a → true

여기서 반드시 이어 붙여야 할 결론은 이것이다 — "그러니까 문자열 값 비교는 항상 equals()". ==는 애초에 값을 비교하는 연산이 아니라 "두 참조가 같은 객체를 가리키는가"를 묻는 참조 비교이고, 리터럴에서 우연히 맞아떨어질 뿐이다.

이 버그가 위험한 진짜 이유 — 테스트를 통과한다 테스트 코드에 쓰는 문자열은 대부분 리터럴이라 == 비교가 잘 통과한다. 그런데 운영에서는 HTTP 파라미터·DB 조회 결과·substring 결과처럼 런타임에 만들어진 문자열이 들어온다. 로컬에서는 절대 재현되지 않고 운영에서만 틀리는 버그가 되는 것이 이 실수의 특징이다.

intern()은 "이 문자열과 같은 내용의 pool 대표 객체를 달라"는 메서드다. pool에 없으면 넣고 그 객체를 돌려준다. 실무에서 직접 부를 일은 드물고, 쓴다면 같은 값이 수백만 번 반복되는 대용량 파싱에서 중복 객체를 줄이려는 목적이다. 다만 pool도 결국 해시 테이블이라 항목이 폭증하면 조회가 느려지므로 무턱대고 쓸 것은 아니다.

이 질문의 진짜 의도 — 대개 "pool의 존재를 아는가"를 확인하는 것에 가깝다. 그러니 pool → 불변이 전제 → 그래서 ==가 아니라 equals까지 한 호흡으로 이어 말하면 의도를 정확히 맞춘 답이 된다.

String이 불변인데 s += "x"는 왜 되나요?힌트: 바뀐 것이 상자인가 화살표인가 함정

변수가 다른 새 객체를 가리키도록 참조가 바뀐 것이지, 원래 객체의 내용이 바뀐 것이 아니다. s += "x"는 "지금까지의 s와 x를 합친 새 String을 만들어, 그 주소를 s에 다시 대입하라"로 번역된다. 원래 객체는 손대지 않은 채 그대로 있다가 아무도 안 가리키게 되면 GC 대상이 된다.

바뀐 것은 화살표가 향하는 곳이지 상자 안의 글자가 아니다

그래서 final String s는 재할당만 막을 뿐이고, 불변은 객체 쪽의 성질이라 서로 다른 층위라는 것까지 말하면 정리가 깔끔하다.

final — 화살표를 고정한다

변수의 성질이다. 재할당을 금지한다. final List<String> l이라도 l.add(...)는 된다 — 리스트 내용은 얼마든지 바뀐다.

불변 — 상자 안을 고정한다

객체의 성질이다. 상태 변경 자체가 불가능하다. 변수는 얼마든지 다른 객체로 갈아 끼울 수 있다.

한 문장으로 — final은 변수를 묶고, 불변은 객체를 묶는다. 둘 다 있어야 "이 이름이 가리키는 값이 앞으로 절대 안 변한다"가 된다.

불변이면 매번 객체가 생기는데 성능이 더 나쁜 것 아닌가요?힌트: 사라진 비용은 눈에 안 보인다 핵심

반복 수정 지점에서는 맞다. 루프 누적이 O(n²)가 되는 것이 그 증거이고, 그래서 StringBuilder가 존재한다. 이 사실을 먼저 인정하고 시작해야 답이 방어적으로 들리지 않는다.

하지만 전체 그림에서는 반대 이득이 훨씬 크다. 공유가 안전해져 같은 리터럴이 하나로 합쳐지고(pool), 방어적 복사가 필요 없어지고, 동기화 비용이 사라지고, 해시를 한 번만 계산한다.

"수정마다 새 객체"라는 비용은 눈에 잘 보이고, 그 대가로 사라진 비용들은 눈에 안 보일 뿐이다

객체 생성 자체가 생각보다 싸다는 점도 덧붙일 만하다. JVM은 스레드마다 Eden의 한 조각을 미리 떼어 주고(TLAB) 그 안에서는 포인터만 앞으로 밀어 할당하므로, 짧게 살다 죽는 객체는 생성도 회수도 저렴하다.

불변으로 안전을 기본값으로 깔고,
측정으로 병목이 확인된 지점만 가변 버퍼로 푼다

이 프레임이 중요한 이유 — 반대로 하면(성능이 걱정돼서 처음부터 전부 가변으로) 동시성 버그라는, 훨씬 잡기 어려운 비용을 떠안게 된다. 성능 문제는 프로파일러로 위치가 찍히지만, 공유 가변 상태 버그는 재현조차 안 된다.

"hel" + "lo"도 pool의 "hello"와 ==가 true인가요?힌트: 컴파일 시점에 값이 정해지는가 함정

갈리는 기준은 딱 하나 — "컴파일 시점에 값이 확정되는 상수식인가"다.

String lit = "hello";

String a = "hel" + "lo";          // 리터럴끼리 → 컴파일 시점에 "hello"로 합쳐진다(상수 폴딩)
System.out.println(a == lit);        // true — 같은 pool 객체

final String p = "hel";             // final + 컴파일 타임 상수
String b = p + "lo";               // 역시 상수식 → 컴파일 시점에 확정
System.out.println(b == lit);        // true

String q = "hel";                   // final 아님 → 값이 바뀔 수 있는 변수
String c = q + "lo";               // 런타임 연결 → 힙에 새 객체가 생긴다
System.out.println(c == lit);        // false
System.out.println(c.equals(lit));   // true — 값은 같다

왜 이렇게 갈리는가. pool에 자동으로 들어가는 것은 클래스 파일에 리터럴로 박혀 있는 문자열이다. "hel" + "lo"처럼 컴파일러가 미리 계산할 수 있는 식은 컴파일 단계에서 "hello" 하나로 접혀(상수 폴딩) 클래스 파일에 리터럴로 들어가므로 pool 대표와 같은 객체가 된다. 반면 런타임 변수가 끼면 값이 실행 시점에야 정해지므로 새 객체다.

이 질문이 함정인 이유 == 결과가 사람이 예측하기 매우 어렵게 갈린다는 것을 보여 주는 문제다. final이 붙었는지, 값이 컴파일 타임 상수인지 같은 겉으로 안 보이는 조건에 결과가 달라진다. 그래서 결론은 "규칙을 외워서 ==를 잘 쓰자"가 아니라 "==를 쓰지 말자"다.

실무 연결 — 필요하면 c.intern() == lit으로 명시적으로 pool 대표를 얻어 비교할 수는 있지만, 그럴 이유가 있는 상황이 거의 없다. equals()가 정답이다.

불변이라면서 hash 필드는 왜 final이 아닌가요? 스레드 안전은 깨지지 않나요?힌트: 여러 스레드가 각자 계산해도 결과가 같다면? 가산점

hash는 생성자에서 채우는 게 아니라 hashCode()가 처음 호출될 때 계산해 채우는 지연 초기화(lazy initialization) 방식이기 때문에 final일 수 없다. 문자열은 한 번도 해시가 필요 없을 수 있는데 생성 때마다 전체 문자를 훑는 것은 낭비다.

그런데 동기화가 없다. 여러 스레드가 동시에 처음 hashCode()를 부르면 각자 계산해 각자 필드에 쓸 수 있다. 이것이 문제가 안 되는 이유는 하나다 —

입력이 불변이므로 누가 계산해도 결과가 항상 같은 값이다 — 누가 마지막에 써도 결과가 동일하다

계산이 중복될 수는 있어도 틀린 값이 보일 수는 없다. 이런 형태의 경쟁을 무해한 경쟁(benign data race)이라고 부른다. 락을 걸어 얻을 이득(계산 1회 절약)보다 모든 hashCode() 호출에 락 비용을 얹는 손해가 훨씬 크기 때문에 일부러 동기화하지 않은 것이다.

덧붙이면 가산점 — hashIsZero라는 boolean이 하나 더 있다 hash의 초기값이 0인데 실제 해시가 0인 문자열도 존재한다(빈 문자열이 그렇다). 그래서 "아직 계산 안 함"과 "계산했더니 0"을 구분할 방법이 필요하고, 그 구분자가 이 필드다. 없으면 해시가 0인 문자열은 조회할 때마다 계산을 반복하게 된다.

일반화하면 — 이 패턴(불변 입력 + 순수 계산 + 결과 캐싱)은 불변 객체에서만 안전하게 쓸 수 있는 기법이다. 가변 객체에 같은 짓을 하면 내용이 바뀌는 순간 캐시가 거짓말을 시작한다.

String의 해시는 왜 하필 31을 곱하나요?힌트: 홀수 소수 + 곱셈을 안 해도 된다 가산점

두 가지 이유가 겹친다.

분산홀수인 소수라 곱했을 때 비트가 고르게 섞인다. 짝수를 곱하면 곱할 때마다 하위 비트가 0으로 밀려 나가 정보가 버려지고, 결국 서로 다른 문자열이 같은 해시가 되는 충돌이 늘어난다. 속도31 * i는 (i << 5) - i와 같다. 곱셈 없이 시프트 한 번과 뺄셈 한 번으로 계산할 수 있어서, JVM이 이 최적화를 적용한다.

답할 때 더 중요한 것은 31이라는 숫자 자체가 아니라 "왜 계산식이 이렇게 생겼는가"다. 자리마다 다른 가중치를 곱해 누적하기 때문에 같은 글자를 순서만 바꾼 문자열이 다른 해시를 갖는다. 만약 그냥 코드값을 더하기만 했다면 "ab"와 "ba"가 같은 해시가 되어 버킷이 몰린다.

h = 31·h + c  를 글자마다 반복  →  "자리(순서)"가 결과에 반영된다

주의해서 말할 것 — String의 해시값은 명세에 정의되어 있어 어떤 JVM에서도 같다. 편리해 보이지만 이 값을 영속 저장하거나 샤딩 키로 쓰는 것은 위험하다. 해시는 동등성 판정을 빠르게 하기 위한 값이지 고유 식별자가 아니고, 서로 다른 문자열이 같은 해시를 가질 수 있기 때문이다.

substring()은 원본의 문자 배열을 공유하나요?힌트: 공유하면 빠르지만 무엇이 위험한가 가산점

지금은 공유하지 않는다 — 필요한 구간만 새 배열로 복사해 새 String을 만든다. 그래서 substring()의 비용은 잘라낸 길이에 비례한다.

과거에는 공유하던 시절이 있었다는 점이 이 질문의 핵심이다. 원본 배열을 그대로 두고 시작 위치와 길이만 기록하면 substring()이 상수 시간에 끝난다 — 원본이 불변이니 공유해도 안전하다는 논리였다. 그런데 여기에 함정이 있었다.

배열 공유가 낳는 메모리 누수 10MB짜리 문자열에서 10글자만 잘라 보관했는데, 그 조각이 원본 배열 전체를 붙잡고 있어서 10MB가 회수되지 않는다. 원본 String 참조를 아무 데도 안 남겨도 조각이 배열을 살려 둔다. 로그 파싱·HTML 스크래핑처럼 큰 문자열에서 작은 조각을 다량으로 뽑아 보관하는 코드에서 실제로 힙이 터졌다.
그래서 지금 구현은 항상 복사한다 — "자를 때 O(n) 비용을 내고, 조각은 원본과 완전히 분리한다"는 쪽으로 트레이드오프를 바꾼 것이다.

실무 함의 — 아주 긴 문자열에서 substring()을 루프 안에서 반복 호출하면 매번 복사 비용이 든다. 그럴 때는 잘라내지 말고 인덱스만 들고 다니며 원본을 직접 읽는 방식(charAt, regionMatches, CharSequence의 부분 뷰)을 고려한다.

이 사례가 알려주는 것 — 불변이 공유를 안전하게 만들어 준다는 것과, 공유가 항상 좋은 선택이라는 것은 다른 얘기다. 안전하게 공유할 수 있어도 수명이 긴 큰 객체를 붙잡는 공유는 메모리 관점에서 손해일 수 있다.

StringBuilder를 필드나 static으로 두고 재사용해도 되나요?힌트: StringBuilder가 버린 게 정확히 뭐였는지 함정

지역 변수로 쓰는 것이 원칙이고, 필드로 올리는 순간 문제가 두 개 생긴다. StringBuilder는 불변을 의도적으로 버린 가변 객체라는 사실을 그대로 되짚으면 답이 나온다.

① 공유 가변 상태가 된다

static이거나 싱글턴 빈의 필드에 두면 모든 요청 스레드가 같은 버퍼에 쓴다. 동기화가 없으니 A 요청의 내용에 B 요청의 조각이 섞여 나가고, 심하면 내부 배열 인덱스가 깨진다. 이것은 static SimpleDateFormat과 정확히 같은 유형의 사고다.

② 버퍼가 안 줄어든다

한 번 큰 문자열을 조립하면 내부 배열이 그만큼 커진 채 남는다. 필드로 오래 살면 최대 사용량이 그대로 상주 메모리가 된다. 지역 변수라면 메서드가 끝나는 즉시 회수 대상이 된다.

재사용이 정당한 유일한 형태 — 한 스레드 안에서만 타이트한 루프에서 매 회전 새 StringBuilder를 만드는 대신 setLength(0)으로 비워 재사용하는 것은 그 객체가 메서드 밖으로 새어 나가지 않는 한 안전하고 효과도 있다. 확장으로 커진 배열을 다음 회전에 그대로 재활용하기 때문이다. 다만 이것은 수십만 회전급에서 의미 있는 최적화다.

덧붙이면 좋은 것 — 조립한 뒤 toString()으로 뽑아낸 String은 불변이라 안전하게 반환·공유해도 된다. "가변 버퍼는 안에서 쓰고, 밖으로는 불변으로 내보낸다"가 String / StringBuilder 쌍이 보여주는 설계 패턴이다.

String은 내용을 덮어쓸 수 없으므로 다 쓰고 난 뒤에도 평문 비밀번호가 힙에 그대로 남는다. 참조를 끊어도 GC가 실제로 회수하기 전까지는 메모리에 존재하고, 그 사이에 힙 덤프를 뜨거나 코어 덤프가 남으면 그대로 노출된다. 게다가 그 값이 리터럴이거나 intern()을 거쳤다면 pool에 남아 애플리케이션 수명 내내 살아 있을 수도 있다.

// Before — 다 쓴 뒤에도 지울 방법이 없다
String pw = request.getPassword();

Kotlin에서도 String은 같은가요? val이 불변 아닌가요?힌트: val이 묶는 것은 화살표다 가산점

JVM에서 실행되는 Kotlin의 String은 결국 java.lang.String이므로 불변성·pool·해시 캐싱이 전부 그대로다. 달라지는 것은 문법과 표현이지 메커니즘이 아니다.

주의val은 재할당 금지이지 불변이 아니다. Java의 final과 같은 층위다. val list = mutableListOf<String>()이어도 list.add(...)는 된다 — 화살표를 묶었을 뿐 상자를 묶은 게 아니다. 이 문서 1절의 구분이 Kotlin에서 특히 자주 헷갈리는 지점이다. 템플릿문자열 템플릿 "id=$id, amt=$amt"도 Java의 + 연결과 마찬가지로 한 표현식이므로 컴파일러가 처리한다. 손으로 StringBuilder로 바꿀 이유가 없다. 누적루프 누적이 O(n²)라는 함정은 Kotlin에서도 똑같다. var s = ""에 루프로 +=하면 Java와 같은 문제가 난다. Kotlin은 이 지점에 buildString { }이라는 전용 표현을 제공한다 — 내부에서 StringBuilder를 만들어 넘겨주고 마지막에 toString()까지 해 준다. 
// Before — 언어가 바뀌어도 O(n²)는 그대로다
var csv = ""
for (o in orders) csv += "${o.id},"

// After — 누적 구간을 가변 버퍼로 감싼다
val csv = buildString {
    for (o in orders) append(o.id).append(',')
}

// 컬렉션을 잇기만 하면 되는 경우엔 이쪽이 더 낫다
val csv2 = orders.joinToString(",") { it.id }

정리 — Kotlin은 불변을 더 쉽게 쓰도록 문법을 얹었을 뿐, 밑바닥 규칙은 같다. data class와 val 프로퍼티로 불변 값 객체를 만들기가 훨씬 쉬워졌다는 것이 실질적인 차이이고, 그래도 "필드에 가변 컬렉션을 담으면 val이어도 불변이 아니다"는 함정은 그대로 남는다.

String에서 배운 불변을 도메인 객체 설계에 어떻게 적용하나요?힌트: 전부 불변으로 만드는 게 답이 아니다 — 선을 어디에 긋는가 시니어 변별

Money, 기간, 좌표 같은 값 객체(VO, Value Object) — 식별자가 아니라 값 자체로 의미를 갖는 객체 — 를 String과 똑같은 방식으로 만든다. 2절의 세 자물쇠를 그대로 옮기면 된다.

  • 모든 필드 private final
  • setter 없음. 수정은 새 객체를 반환하는 메서드로 — money.plus(other)
  • 클래스 final (또는 record — 필드 final과 접근자 생성이 기본으로 딸려 온다)
  • 가변 객체를 필드로 받거나 반환할 때는 방어적 복사

효과는 String이 이미 증명한 그대로다. 스레드 간 공유가 안전하고, 해시 컬렉션의 키로 안전하고, "이 값을 누가 언제 바꿨나"를 추적할 일 자체가 없어진다.

프레임워크가 상태 변경을 전제하는 곳이라 그대로 적용하기 어렵다. 엔티티는 기본 생성자와 필드 변경을 요구하고, 애초에 식별자로 동일성을 판단하는 객체라 값 객체와 성격이 다르다.
