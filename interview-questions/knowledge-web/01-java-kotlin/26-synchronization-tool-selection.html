동기화 도구 선택 — synchronized vs ReentrantLock vs StampedLock vs Atomic(CAS)
네 도구를 나열하는 순간 진다. 먼저 "무엇을 기준으로 갈리는가" 네 축을 세우고, 거기서 기본값은 synchronized라는 결론을 유도한다

면접 질문: "synchronized, ReentrantLock, StampedLock, CAS 기반 Atomic 클래스의 차이와 선택 기준은?"

핵심 관전 포인트 — 네 도구를 나열하기 전에 "무엇을 기준으로 갈리는가"를 먼저 말해야 한다 — 보호 대상이 변수 하나인가 여러 줄의 로직인가, 읽기와 쓰기의 비율이 어떤가, 경합이 실제로 있는가, 대기를 중간에 포기할 수 있어야 하는가. 이 네 축으로 정리하면 결론은 단순하다. 기본값은 synchronized다 — 바이어스드 락은 걷혔지만 경량 락과 JIT의 락 생략·락 병합이 남아 있어 저경합에서는 여전히 좋고, 무엇보다 블록을 벗어나면 반드시 풀리므로 실수가 원천 봉쇄된다. ReentrantLock으로 올라가는 이유는 성능이 아니라 기능이다(tryLock 타임아웃, lockInterruptibly, 공정성, 여러 개의 Condition) — 대신 finally의 unlock()을 빠뜨리면 영구 정지다. StampedLock은 읽기가 압도적일 때의 특화 도구로 낙관적 읽기(도장 받고 → 읽고 → validate로 그 사이 쓰기가 있었는지 확인)를 제공하지만 재진입 불가와 Condition 미지원이라는 함정이 있다. Atomic은 변수 하나짜리 논블로킹 도구이며 경합이 극심하면 CAS 재시도가 폭증한다. 그리고 이 넷보다 먼저 물을 질문은 "직접 동기화가 필요하긴 한가?"다.
  • 1
    도구 목록이 아니라 네 축으로 답합니다. ①보호 대상이 변수 하나인가 여러 줄 로직인가, ②읽기/쓰기 비율, ③경합이 실측됐는가, ④대기를 포기할 수 있어야 하는가. 이 넷이 정해지면 도구는 자동으로 결정됩니다 — 변수 하나면 Atomic, 읽기 압도 + 긴 임계 영역이면 읽기-쓰기 분리, 타임아웃·인터럽트·공정성·여러 Condition이 필요하면 ReentrantLock, 나머지 전부 synchronized입니다.
  • 2
    기본값이 synchronized인 이유를 성능과 안전성 두 겹으로 말합니다. 바이어스드 락은 JDK 15에서 기본 비활성화·폐기 예고된 뒤 제거됐지만, 경량 락(경합 없으면 CAS 한 번)·적응형 스핀·락 생략·락 병합이 남아 있어 저경합에서는 여전히 쌉니다. 그리고 더 중요한 건 블록을 벗어나면 JVM이 반드시 푼다는 것 — ReentrantLock의 최다 사고인 unlock() 누락(영구 정지)이 문법적으로 불가능합니다.
  • 3
    넷을 비교하기 전에 "직접 동기화가 필요하긴 한가"부터 묻습니다. 맵·큐라면 ConcurrentHashMap·BlockingQueue, 통째로 교체하는 데이터라면 불변 객체 + volatile 참조, 공유할 필요가 없다면 스레드 한정(ThreadLocal·요청 스코프)으로 끝납니다. 직접 동기화는 이 셋으로 안 될 때 남는 선택지이지 첫 선택지가 아닙니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "synchronized, ReentrantLock, StampedLock, CAS 기반 Atomic 클래스의 차이와 선택 기준은?"

출제 의도 — 동기화 도구 선택은 경합 정도와 읽기/쓰기 비율에 따른 트레이드오프 판단이다. 항상 synchronized만 쓰는 사람은 고경합 지점에서 병목을 만들고, 항상 lock-free를 쓰는 사람은 검증 불가능한 코드를 만든다 — 도구별 진짜 선택 근거를 말할 수 있는지를 본다.

약점 A스펙 나열형 답 — "synchronized는 키워드고, ReentrantLock은 tryLock이 있고, StampedLock은 낙관적 읽기가 있고…". 넷을 평등한 선택지처럼 늘어놓으면 고르는 기준이 없다는 뜻이다. 축을 먼저 세워야 한다.
약점 B"synchronized는 느리니 ReentrantLock을 씁니다" — 초기 JVM 시절의 벤치마크가 아직 떠도는 것이다. 바이어스드 락 제거를 근거로 이 오해를 강화하면 더 나쁘다. 남아 있는 최적화 넷을 말할 수 있어야 한다.
약점 C경합을 측정하지 않고 도구를 바꾸는 태도 — "동기화가 걸려 있다"와 "경합이 있다"는 완전히 다른 말이다. 경합 없는 자리의 도구 교체는 얻는 것 없이 unlock() 누락 위험만 늘리는 일이다.
약점 DAtomic을 여러 개 늘어놓고 "동기화했다"고 생각하는 것 — 원자적 연산 여러 개의 합은 원자적이 아니다. 여기서 갈리는 사람이 많다.
약점 EStampedLock을 "가장 빠른 락"으로 추천하는 것 — 재진입 불가·Condition 미지원·패턴 강제를 함께 말하지 못하면, 가장 성능 좋은 도구가 아니라 가장 오용하기 쉬운 도구를 고른 셈이 된다.
합격선네 축을 먼저 세우고 → "직접 동기화가 필요한가"를 0번 질문으로 두고 → 기본값이 synchronized인 이유를 성능과 안전성 두 겹으로 말하고 → 올라갈 조건(기능/읽기 비율/실측된 경합)을 각각 대고 → 도구별로 스레드 덤프에 어떻게 보이는지까지.
이 문서의 진행 방향 — 축 → 도구 → 선택 1절은 동기화가 해결하는 두 문제(상호 배제·가시성), 2~3절은 선택의 네 축과 그보다 앞선 0번 질문, 4~7절은 도구별 동작과 함정, 8~9절은 경합 스펙트럼과 결정 트리, 10~11절은 관측 방식과 실무 판단이다. 면접 답변 순서도 같다 — 축으로 신뢰를 얻고, 기본값의 근거로 점수를 얻는다.

1. 전제 — 동기화 도구가 해 주는 일은 두 가지다

도구를 비교하려면 먼저 동기화가 무엇을 해결하는 장치인지를 정리해야 한다. 서로 다른 두 가지 문제가 있고, 도구마다 둘 중 무엇을 어떻게 주는지가 다르다.

상호 배제 (mutual exclusion)

여러 스레드가 동시에 같은 데이터를 고쳐서 서로의 갱신을 덮어쓰는 것을 막는 일. count++는 소스에서 한 줄이지만 실제로는 읽기 → 계산 → 쓰기 세 단계라, 그 사이에 끼어들면 두 번 증가시켰는데 결과가 한 번인 갱신 유실이 생긴다.

가시성 (visibility)

한 스레드가 쓴 값이 다른 스레드에게 보이게 만드는 일. CPU 코어마다 전용 캐시(L1·L2)를 갖고 그 복사본으로 일하기 때문에, 한 코어가 고친 값이 다른 코어에게 언제 도착할지, 도착하기는 할지 기본적으로는 보장되지 않는다.

이 문서의 네 도구는 전부 두 가지를 함께 준다

락을 잡고 푸는 동작에는 메모리 배리어가 함께 들어간다. 그래서 락으로 보호한 구간의 쓰기는 다음에 그 락을 잡는 스레드에게 반드시 보인다. Atomic의 CAS도 마찬가지다.

"락을 걸었는데 가시성도 따로 챙겨야 하나요"라는 걱정은 필요 없다 — 같은 락으로 보호하고 있다면 이미 해결돼 있다

단서는 "같은 락으로"다. 어떤 스레드는 락을 잡고 쓰는데 다른 스레드가 락 없이 읽으면 보장은 깨진다. 읽기 경로에도 동기화가 필요한 이유가 이것이다.

2. 선택의 네 축 — 도구를 나열하기 전에 물을 것

네 도구는 평등한 선택지가 아니다. 아래 네 개의 질문에 답하면 도구는 거의 자동으로 결정된다. 면접에서도 도구 이름보다 이 축을 먼저 꺼내는 것이 훨씬 강한 답이다.

1

축 하나 — 보호 대상이 변수 하나인가, 여러 줄의 로직인가

가장 먼저 갈리는 축이고, 가장 자주 틀리는 축이기도 하다.

변수 하나에 대한 단일 연산이라면 락이 필요 없다. AtomicLong.incrementAndGet() 하나로 끝난다. 반면 두 개 이상의 변수가 함께 일관돼야 하거나, 여러 줄의 로직이 한 덩어리로 실행돼야 한다면 Atomic으로는 불가능하다.

문제 Atomic 두 개 = 원자적 이체가 아니다
private final AtomicLong balanceA = new AtomicLong(10_000);
private final AtomicLong balanceB = new AtomicLong(0);

public void transfer(long amount) {
    balanceA.addAndGet(-amount);   // 여기까지 실행된 순간
    balanceB.addAndGet(amount);    // 다른 스레드가 두 잔액을 함께 조회하면
}                                  // 총합이 맞지 않는 중간 상태가 보인다

addAndGet 각각은 완벽하게 원자적이다. 그런데 "둘 다 바뀌었거나 둘 다 안 바뀌었거나"라는 불변식은 지켜지지 않는다.

개선 불변식의 범위를 한 덩어리로 잠근다
private final Object lock = new Object();
private long balanceA = 10_000, balanceB = 0;

public void transfer(long amount) {
    synchronized (lock) {        // 두 갱신을 한 덩어리로
        balanceA -= amount;
        balanceB += amount;
    }   // 중간 상태는 밖에서 관측되지 않는다
}                                  // 조회도 같은 lock으로 감싸야 완성

(가산점) 락 없이 가려면 두 잔액을 불변 객체 하나로 묶어 AtomicReference로 통째 교체한다 — 참조 교체 한 번이 곧 원자적 상태 전이다.

원자적 연산 여러 개의 합은 원자적이 아니다

같은 이유로 검사 후 행동(check-then-act) — "재고를 확인하고 조건이 맞으면 차감한다", "null이면 초기화한다" — 도 락의 영역이다. 검사와 행동 사이에 다른 스레드가 끼어들 수 있기 때문이다.

2

축 둘 — 읽기와 쓰기의 비율

읽기만 하는 스레드끼리는 서로를 막을 이유가 없다. 아무도 값을 바꾸지 않으니 갱신 유실이 생길 수 없다.

그런데 synchronized나 ReentrantLock은 이 사실을 모르고 읽기든 쓰기든 무조건 한 명만 통과시킨다. 읽기가 99%인 워크로드에서는 이것이 순수한 낭비다. 여기서 읽기-쓰기 락이라는 갈래가 나온다 — 읽기 락은 여러 스레드가 동시에 잡을 수 있고 쓰기 락은 혼자만 잡을 수 있다(ReentrantReadWriteLock). StampedLock은 여기서 한 발 더 나가 읽을 때 락을 아예 잡지 않고, 다 읽은 뒤에 "그동안 아무도 안 고쳤는지"만 확인한다(→ 6절).

함정 — 읽기가 많다고 읽기-쓰기 락이 항상 이득인 것은 아니다 읽기 락도 "지금 몇 명이 읽고 있는가"를 세는 공유 카운터를 CAS로 갱신해야 하고, 그 카운터가 곧 새로운 경합 지점이 된다. 임계 영역이 충분히 길어야 그 부대비용을 상쇄한다. 필드 두 개 읽고 나오는 정도의 짧은 구간이라면 그냥 synchronized가 더 빠른 경우가 흔하다.
3

축 셋 — 경합이 실제로 있는가

"동기화가 걸려 있다"와 "경합이 있다"는 완전히 다른 말이다.

경합(contention)은 한 스레드가 락을 쥐고 있는 동안 다른 스레드가 그 락을 요청하는 상황을 가리킨다. 락이 걸려 있어도 실제로 겹치는 일이 없으면 경합은 0이고, 현실의 코드는 대부분 여기에 해당한다.

경합이 없을 때

어떤 도구든 CAS 한두 번 수준으로 싸다. 네 도구의 차이가 거의 없다. 이 자리에서 도구를 바꾸는 것은 얻는 것 없이 unlock() 누락 위험만 늘리는 일이다.

경합이 있을 때

락은 스레드를 재웠다 깨우는 비용(컨텍스트 스위칭)을 치르고, CAS는 재시도를 반복하며 CPU를 태운다. 여기서 비로소 도구 선택이 성능에 영향을 준다.

"성능 때문에 도구를 바꾼다"는 판단은 경합이 실측된 뒤에야 유효하다
4

축 넷 — 대기를 중간에 포기할 수 있어야 하는가

마지막 축은 성능이 아니라 제어 가능성이다.

synchronized는 한번 기다리기 시작하면 포기할 방법이 없다. 타임아웃도 없고, 인터럽트로 깨울 수도 없다. 락을 쥔 스레드가 영원히 안 놓으면 대기하는 스레드도 영원히 그 자리에 있는다.

데드락 회피
락 순서를 통제할 수 없는 구조라면 "정해진 시간 안에 못 잡으면 쥔 것을 놓고 물러나기"가 유일한 대응이다.
응답 시간 상한
사용자 요청 처리 중이라면 "3초 안에 락을 못 잡으면 실패로 응답"이 무한 대기보다 낫다. 무한 대기는 스레드를 붙잡고, 스레드가 마르면 무관한 API까지 죽는다.
graceful shutdown
종료 신호를 받으면 정리하고 나가야 하는데, synchronized 대기 중인 스레드는 인터럽트로 깨울 수 없어 종료가 그 스레드에서 멈춘다.
이 셋 중 하나라도 해당하면 ReentrantLock으로 올라갈 이유가 생긴다 — 해당 없으면 올라갈 이유가 없다

3. 축 0 — 직접 동기화가 필요하긴 한가

도구를 고르기 전에 마지막으로 확인할 것이 있다. 동기화 코드를 우리가 직접 쓰지 않고 끝낼 수 있는가. 이 질문을 네 축보다 앞에 두는 것이 이 주제의 핵심 구조다.

관문 ① — 동시성 컬렉션으로 대체 가능한가

문제 맵을 직접 잠그고 있다
private final Map<String, Session> sessions = new HashMap<>();
private final Object lock = new Object();

public Session get(String id) {
    synchronized (lock) { return sessions.get(id); }  // 읽기도 한 명씩
}
public void put(String id, Session s) {
    synchronized (lock) { sessions.put(id, s); }        // 맵 전체가 하나의 병목
}
개선 컬렉션에게 맡긴다
private final Map<String, Session> sessions = new ConcurrentHashMap<>();

public Session get(String id) { return sessions.get(id); }
public void put(String id, Session s) { sessions.put(id, s); }

// 검사 후 행동이 필요하면 "원자적 복합 연산"을 쓴다
sessions.computeIfAbsent(id, k -> new Session(k));  // if(!has) put 금지
// 버킷 단위로만 잠그므로 서로 다른 키는 병렬로 통과한다
단, 컬렉션이 보장하는 것은 "개별 연산"까지다 containsKey 뒤에 put을 이어 붙이면 그 조합은 원자적이 아니다. 이건 축 하나에서 본 "Atomic 두 개를 이어 붙이면 안 된다"와 정확히 같은 함정이다. 답은 락을 추가하는 게 아니라 putIfAbsent·computeIfAbsent·merge처럼 컬렉션이 제공하는 원자적 복합 연산을 쓰는 것이다.

관문 ② — 불변 객체로 만들 수 있는가

문제 필드를 하나씩 고치니 락이 필요해진다
public class RateLimitConfig {
    private int limit;        // 갱신 중간 상태가 읽힐 수 있다
    private long windowMs;    // limit만 새 값, window는 옛 값

    public synchronized void reload(int l, long w) { limit = l; windowMs = w; }
    public synchronized int limit() { return limit; }   // 읽기마다 락
}
개선 통째로 교체 — 읽기에 락이 사라진다
record RateLimitConfig(int limit, long windowMs) {}   // 불변

private volatile RateLimitConfig cfg = new RateLimitConfig(100, 1000);

public void reload(int l, long w) { cfg = new RateLimitConfig(l, w); }  // 참조 교체 한 번
public RateLimitConfig current() { return cfg; }  // 락 없음. 항상 일관된 한 벌

참조 교체는 그 자체로 원자적이고 volatile이 가시성을 준다. 읽는 쪽은 옛 한 벌 아니면 새 한 벌을 보고, 섞인 상태는 존재하지 않는다.

관문 ③ — 스레드 한정으로 갈 수 있는가

데이터를 스레드마다 하나씩 나눠 주면(ThreadLocal, 요청 스코프 객체) 공유 자체가 없어진다. 공유가 없으면 동기화도 없다. 대표적인 예가 스레드 안전하지 않은 포매터·파서를 필드로 공유하다 생기는 사고인데, 이 경우 해답은 락을 거는 것이 아니라 매번 새로 만들거나, 스레드마다 하나씩 갖게 하거나, 애초에 불변인 대체제를 쓰는 것이다.

ThreadLocal은 공짜가 아니다 스레드풀에서는 스레드가 재사용되므로, 요청이 끝날 때 remove()로 정리하지 않으면 다음 요청이 이전 요청의 값을 보거나 값이 계속 쌓여 메모리 누수가 된다. "공유를 없앤다"는 이득과 "생애주기를 직접 관리한다"는 비용을 함께 봐야 한다.

축 0 — 순서를 밝히는 것이 도구 비교보다 먼저다

① 동시성 컬렉션맵·큐를 synchronized로 감싸고 있다면 ConcurrentHashMap·BlockingQueue가 답이다. 생산자-소비자 구조라면 BlockingQueue가 대기와 신호를 전부 처리해 준다.
② 불변 객체아무도 안 고치는 데이터에는 동기화가 필요 없다. 통째로 교체하는 구조라면 불변 객체 + volatile 참조 하나로 끝난다.
③ 스레드 한정데이터를 스레드마다 나눠 주면 공유 자체가 없어진다(ThreadLocal, 요청 스코프).
④ 직접 동기화위 셋으로 안 될 때 남는 선택지라는 순서를 밝히는 것이, 네 도구를 비교하는 것보다 먼저다.

4. synchronized — "느린 옛날 것"이라는 오해부터 깬다

JVM이 언어 차원에서 제공하는 잠금이다. 블록이나 메서드에 붙이면 그 구간에 한 번에 한 스레드만 들어간다.

기본 이 도구의 최대 장점은 성능이 아니라 마지막 줄의 주석이다
private final Object lock = new Object();
private int count = 0;

public void increment() {
    synchronized (lock) {   // 한 번에 한 스레드만 진입
        count++;
    }                       // 블록을 벗어나면 자동 해제. 예외로 튀어나가도 해제된다
}

락 해제가 언어 문법에 묶여 있어서 까먹을 수가 없다. 예외가 터져 스택을 거슬러 올라가도, return으로 중간에 나가도, JVM이 반드시 푼다. 5절에서 볼 ReentrantLock의 가장 흔한 사고가 여기서는 원천적으로 불가능하다.

바이어스드 락이 사라진 것이 "이제 느리다"는 뜻은 아니다

synchronized가 느리다는 인식에는 오래된 뿌리가 있다. 초기 JVM에서는 경합이 없어도 OS 수준의 무거운 락을 잡았고, 그 시절의 벤치마크와 조언이 지금까지 떠돈다.

5. ReentrantLock — 기능을 사고 해제 책임을 진다

synchronized가 못 하는 것들을 메서드로 제공하는 잠금 클래스다. 이름의 "재진입 가능(reentrant)"은 같은 스레드가 이미 쥔 락을 다시 잡아도 막히지 않는다는 뜻인데, 이건 synchronized도 마찬가지라 차별점이 아니다. 진짜 차이는 아래 네 가지다.

tryLock()
tryLock(t, unit)
대기를 포기할 수 있다
락을 "시도"만 해 보고 못 얻으면 즉시 또는 시간 뒤에 포기한다.
필요한 상황 — ①락 순서를 통제할 수 없어 데드락 예방이 불가능할 때 "못 잡으면 쥔 것을 놓고 물러나기", ②응답 시간 상한, ③배치·스케줄러의 "이미 돌고 있으면 이번 회차는 건너뛴다"(이땐 타임아웃 없는 형태가 정확히 맞는다).
lockInterruptibly()
대기 중 인터럽트로 깨울 수 있다
락 대기에 갇힌 스레드를 밖에서 깨워 정리 코드로 보낼 수 있다.
필요한 상황 — 취소와 종료. 사용자가 요청을 취소했거나 애플리케이션이 종료 중일 때. synchronized 대기는 인터럽트에 반응하지 않으므로 graceful shutdown이 그 스레드에서 막힌다.
new ReentrantLock(true)
공정 모드 — 오래 기다린 쪽 우선
기본값은 비공정(unfair)이고, 비공정 락은 막 도착한 스레드가 줄을 무시하고 채가는 것(barging)을 허용한다.
비공정이 빠른 이유 — 대기 큐의 스레드를 깨워 실행시키는 데 시간이 걸리고, 그 사이 이미 CPU에 올라와 있는 스레드가 처리하고 나가는 편이 전체적으로 빠르다. 대신 기아(starvation) 위험.
lock.newCondition()
대기실을 용도별로 나눈다
4절에서 본 wait/notify의 "대기실이 하나" 한계를 정확히 해결한다.
필요한 상황 — 유한 큐처럼 "자리를 기다리는 쪽"과 "물건을 기다리는 쪽"이 동시에 존재하는 구조. 대기실이 여러 개 필요한가가 ReentrantLock을 고를 실질적 이유 중 하나다.
공정 모드가 필요한 상황은 하나뿐이다 "어떤 요청도 수십 초씩 밀리면 안 된다"는 지연 시간 요구가 처리량보다 중요할 때다. 그리고 처리량 하락은 각오해야 한다. 기본값이 비공정인 것은 대부분의 경우 처리량이 더 중요하기 때문이지, 설계 실수가 아니다.

올바른 패턴 — lock()은 try 밖에, unlock()은 finally에

문제 두 가지 실수가 함께 들어 있다
private final ReentrantLock lock = new ReentrantLock();

public void process() {
    try {
        lock.lock();       // ① lock()이 try 안에 있다
        doWork();
        lock.unlock();     // ② 예외가 나면 이 줄에 도달하지 못한다
    } catch (Exception e) {
        log.error("실패", e);   // 락은 잠긴 채로 남는다 → 영구 정지
    }
}
  • ②가 터지면 그 락은 아무도 다시 못 잡는다. 요청 스레드가 하나씩 쌓이다 스레드풀이 마르면 무관한 API까지 죽는다.
  • ①은 finally를 붙여도 문제다 — 락 획득에 실패했을 때도 unlock()이 실행돼 IllegalMonitorStateException이 나고, 진짜 원인이 그 예외에 가려진다.
개선 기능(타임아웃)을 쓰면서 해제를 보장한다
public boolean process() throws InterruptedException {
    // 1초 안에 못 얻으면 포기 — synchronized로는 불가능
    if (!lock.tryLock(1, TimeUnit.SECONDS)) {
        return false;   // 무한 대기 대신 실패로 응답한다
    }
    try {                 // 획득 성공을 확인한 "뒤에" try에 들어간다
        doWork();
        return true;
    } finally {
        lock.unlock();    // 이 한 줄을 빠뜨리면 아무도 이 락을 다시 못 잡는다
    }
}
  • 획득 성공을 확인한 뒤에만 try에 진입한다.
  • 예외로 튀어나가도 finally가 반드시 푼다.
  • 실패 경로(return false)를 호출자가 처리해야 완성이다 — 안 그러면 조용히 유실되는 요청이 생긴다.

unlock() 누락은 데드락보다 찾기 어렵다

증상은 데드락과 똑같은 "멈춤"인데, 원인은 순환이 아니라 해제 누락이라 JVM 자동 탐지에는 절대 안 잡힌다.

덤프에서는 이렇게 보인다 — 수십 개 스레드가 WAITING (parking) + parking to wait for <0x..> (a ...ReentrantLock$NonfairSync)에 몰려 있는데, jstack -l로 소유자를 찾아보면 그 락을 쥐고 있다는 스레드가 이미 다른 일을 하고 있거나 아예 없다. 이 그림이 나오면 해제 누락을 의심한다.

lock()은 try 밖에, unlock()은 finally에 — 그리고 이 규칙을 지킬 필요가 없는 자리라면 애초에 synchronized가 낫다

여러 개의 Condition — 대기실을 용도별로 나눈다

패턴 유한 크기 큐 — 대기실을 두 개로 나눈다
private final ReentrantLock lock = new ReentrantLock();
private final Condition notFull  = lock.newCondition();   // "자리가 나기를" 기다리는 방
private final Condition notEmpty = lock.newCondition();   // "물건이 들어오기를" 기다리는 방

public void put(E item) throws InterruptedException {
    lock.lock();
    try {
        while (count == items.length) {   // if가 아니라 while — 깨워졌다고 조건이 만족된다는 보장은 없다
            notFull.await();              // 자리가 없다 → "자리 대기실"에서 잔다
        }
        enqueue(item);
        notEmpty.signal();                // 물건이 생겼으니 "물건 대기실"만 정확히 깨운다
    } finally {
        lock.unlock();
    }
}
while로 조건을 다시 확인하는 것은 Condition에서도 필수다 깨워졌다고 조건이 만족된다는 보장은 없다. 깨어나서 락을 다시 잡는 사이에 다른 스레드가 먼저 들어와 자리를 채웠을 수 있고, 구현에 따라 아무도 신호하지 않았는데 깨어나는 경우(spurious wakeup)도 있다. if로 쓰면 조건이 거짓인 채로 진행하게 된다.

6. StampedLock — 읽을 때 락을 잡지 않는다

읽기가 압도적으로 많은 구조를 위한 특화 도구다. 핵심 아이디어는 낙관적 읽기(optimistic read) — "읽는 동안 아무도 안 고치겠지"라고 낙관하고 락 없이 읽은 뒤, 다 읽고 나서 그 낙관이 맞았는지 검증한다.

"낙관적"이라는 이름은 DB의 낙관적 락과 같은 발상이다 충돌이 드물다고 가정하고 일단 진행한 뒤, 충돌이 실제로 있었으면 그때 다시 하는 것. 가정이 맞으면 대부분의 경우 아무 비용도 치르지 않는다. 가정이 틀리면 했던 일을 버리고 다시 한다 — 그래서 가정이 자주 틀리는 환경에서는 손해라는 점까지 같다.
정석 패턴 도장 → 지역 복사 → validate → 실패 시 정식 락
private final StampedLock sl = new StampedLock();
private double x, y;

public double distanceFromOrigin() {
    long stamp = sl.tryOptimisticRead();   // 락을 잡지 않고 도장만 받는다
    double cx = x, cy = y;                 // 반드시 지역 변수로 복사한다

    if (!sl.validate(stamp)) {             // 읽는 사이에 쓰기가 있었나
        stamp = sl.readLock();             // 있었다면 그때만 진짜 읽기 락을 잡고 다시 읽는다
        try {
            cx = x;
            cy = y;
        } finally {
            sl.unlockRead(stamp);          // 여기도 stamp를 넘겨야 한다
        }
    }
    // validate를 통과한 뒤에야 값을 사용한다.
    // 통과 전에 cx, cy로 계산을 하거나 다른 객체를 참조하면
    // 찢어진 값으로 계산·역참조하는 결과가 된다.
    return Math.sqrt(cx * cx + cy * cy);
}

반드시 지역 변수로 복사해야 하는 이유

낙관적 읽기 구간에는 아무 보호가 없다. 필드를 여러 개 읽는 동안 쓰기가 끼어들면 앞의 필드는 옛 값, 뒤의 필드는 새 값인 조합을 읽게 된다 — 존재한 적 없는 상태다.

특히 참조 필드를 읽었다면 validate 전에 역참조하면 안 된다 — 이미 무효가 된 객체를 따라가게 되고, 그 결과는 드물게 터지고 재현되지 않는 NullPointerException·ArrayIndexOutOfBoundsException이다.

함정 — 성능이 아니라 오용 가능성이 선택 기준에 들어간다

재진입이 안 된다
synchronized·ReentrantLock은 같은 스레드가 이미 쥔 락을 다시 잡아도 통과시키지만, StampedLock은 자기 자신을 상대로 교착한다. 쓰기 락을 쥔 채 같은 락의 쓰기 락을 다시 요청하면 그 스레드는 영원히 멈춘다. 락을 잡은 상태에서 다른 메서드를 호출하는 구조라면 위험하다.
Condition을 지원하지 않는다
"조건이 만족될 때까지 기다렸다 깨어나기"가 필요한 구조에는 쓸 수 없다. 생산자-소비자류는 애초에 대상이 아니다.
기본 잠금은 인터럽트에 반응하지 않는다
인터럽트가 필요하면 readLockInterruptibly() / writeLockInterruptibly()를 따로 써야 한다.
stamp를 잃어버리면 풀 수 없다
해제할 때 잡을 때 받은 stamp를 그대로 넘겨야 한다. 변수를 덮어쓰거나 잘못 전달하면 해제에 실패한다.
코드 패턴을 정확히 지켜야만 안전하다 위 예제의 구조 — 도장 받기 → 지역 복사 → validate → 실패 시 정식 락 — 를 매번 손으로 쓰는데, 한 군데만 틀려도 조용히 잘못된 값을 읽는다. 실수 여지가 큰 도구라는 점 자체가 선택 기준에 들어가야 한다 — 자칫 성능이 가장 좋은 도구가 아니라 가장 오용하기 쉬운 도구를 고르는 셈이 된다.

StampedLock을 쓸 조건 — 다섯 개가 모두 참일 때만 암기

  • 읽기가 극단적으로 많다 (그리고 읽기 구간이 짧아 쓰기가 끼어들 확률이 낮다)
  • 성능 병목이 실측됐다 (프로파일러·JFR로 그 락에서의 대기를 확인했다)
  • 재진입이 없다 (락을 쥔 채 다른 메서드를 부르지 않는다)
  • Condition이 필요 없다 (조건 대기 구조가 아니다)
  • 코드 패턴을 정확히 지킬 수 있다 (팀 전체가, 앞으로도)
하나라도 어긋나면 ReentrantReadWriteLock이나 synchronized가 낫다
(가산점) 읽기 도장을 쓰기 락으로 승격시키기 tryConvertToWriteLock(stamp)으로 읽기 도장을 쓰기 락으로 승격시킬 수 있다. "읽어 보고 조건이 맞으면 고친다"를 락을 놓았다 다시 잡지 않고 처리할 때 쓴다. 승격에 실패하면 0을 돌려주므로, 그때는 정식으로 쓰기 락을 잡아야 한다(그리고 놓았다 잡는 사이에 상태가 바뀌었을 수 있으므로 조건을 다시 검사해야 한다).

7. Atomic(CAS) — 변수 하나를 락 없이 지킨다

AtomicInteger, AtomicLong, AtomicReference 등은 락 대신 CPU의 CAS(Compare-And-Swap) 명령을 쓴다. CAS는 "이 메모리 값이 내가 읽었던 값 그대로면 새 값으로 바꿔라"를 CPU가 하나의 명령으로 처리하는 원자 연산이다. 비교와 교체 사이에 다른 스레드가 끼어들 틈이 없다는 것을 소프트웨어가 아니라 하드웨어가 보장한다.

전 락으로 상호 배제 — 못 잡은 스레드는 잠든다
private int count = 0;
public synchronized void increment() { count++; }
// 경합하면 커널 대기 → 컨텍스트 스위칭 비용
후 CAS — 스레드가 잠들지 않는다
private final AtomicInteger count = new AtomicInteger();
public void increment() { count.incrementAndGet(); }
// 실패하면 곧바로 재시도 — 경합이 짧으면 훨씬 싸다
내부 incrementAndGet()은 이런 루프다
do {
    int current = get();          // ① 현재 값을 읽고
    int next = current + 1;       // ② 새 값을 계산한 뒤
} while (!compareAndSet(current, next));
//        ③ "아직 current인가?"를 확인하면서 교체한다.
//        그 사이 누가 바꿨으면 실패하고, 실패하면 ①부터 다시 한다.

한계 — 변수 하나, 그리고 고경합

① 변수 하나짜리 연산에만 쓸 수 있다

축 하나에서 본 대로 "A에서 빼고 B에 더하기"처럼 두 변수가 함께 일관돼야 하는 작업은 CAS로 안 된다. 검사 후 행동도 마찬가지다.

(가산점) 우회 기법 — 여러 필드를 불변 객체 하나로 묶고 그 참조를 AtomicReference로 통째로 교체한다. 상태 전체가 한 객체 안에 있으므로 참조 교체 한 번이 곧 원자적 상태 전이다. 다만 갱신마다 객체를 새로 만드는 비용이 붙는다.

② 경합이 극심하면 재시도가 폭증한다

스레드가 여덟 개면 한 번의 성공마다 일곱 번의 실패가 나오고, 실패한 스레드는 다시 읽고 다시 시도한다. CPU는 바쁜데 실제로 처리되는 증가는 한 번에 하나뿐이다.

락이 없을 뿐 "경합 지점이 하나"라는 문제는 그대로 남아 있다. 여기서부터는 경합 지점 자체를 쪼개는 LongAdder의 영역이고, 그 지점에서 다시 캐시 라인 문제(false sharing)가 등장한다.

③ 대기 상태가 없어서 스레드 덤프에 안 보인다 시니어 변별

CAS 재시도로 CPU를 태우는 스레드는 RUNNABLE로 찍힌다. 락 경합처럼 BLOCKED나 parking으로 드러나지 않으므로, 스레드 덤프만 봐서는 병목인 줄 모른다. CPU 사용률과 함께 봐야 한다.

(가산점) ABA 문제 — 값은 같은데 그 사이에 일이 있었다 값이 A → B → A로 돌아오면 CAS는 "안 바뀌었다"고 판단해 성공한다. CAS가 확인하는 건 "지금 값이 내가 읽었던 값과 같은가"이지 "그 사이 아무 일도 없었는가"가 아니기 때문이다. 단순 카운터에서는 문제가 안 되지만, 스택·큐처럼 노드 참조를 다루는 자료구조에서는 이미 회수된 노드를 되살리는 버그가 된다. AtomicStampedReference가 값에 버전 번호를 함께 실어 이걸 막는다 — DB 낙관적 락의 버전 컬럼과 같은 발상이다.

8. 경합 스펙트럼 — 비용은 경합에서만 갈린다

지금까지 본 네 도구를 하나의 축 위에 올려놓으면 선택 기준이 눈에 보인다. 축은 경합의 정도다. 왼쪽 끝(경합 없음)에서는 넷이 사실상 같고, 오른쪽으로 갈수록 성격이 갈린다.

스펙트럼을 한 문장씩으로 암기

volatile
가시성만 준다. "플래그 하나를 켜고 끄는" 수준이면 여기서 끝. 읽은 값을 근거로 쓰는 순간(count++) 부족해진다.
Atomic
변수 하나에 대한 읽고-계산하고-쓰기를 락 없이. 실패해도 잠들지 않는다는 게 이점이자, 고경합에서는 CPU를 태우는 원인.
락
여러 변수의 불변식과 여러 줄의 로직을 한 덩어리로. 못 잡으면 잠든다 — CPU는 안 태우지만 컨텍스트 스위칭 비용.
LongAdder
경합 지점 자체를 여러 개로 쪼갠다. 갱신이 극단적으로 잦은 통계 카운터 전용. 조회가 잦거나 정확한 순간값이 필요하면 오히려 손해.
오른쪽으로 가는 조건은 "경합이 실측됐다" 하나뿐이다 — 실측 전에는 왼쪽에서 시작한다

10. 비용·관측 비교표와 자주 틀리는 지점

비용과 관측 — 같은 "멈춤"도 도구마다 다르게 보인다

도구별 비용 구조와 스레드 덤프에서의 표기
도구보호 단위대기 중 스레드 상태경합 없을 때 비용경합 심할 때 비용고를 이유 한 줄
synchronized 블록 / 메서드 BLOCKED (on object monitor) CAS 한 번 수준 모니터 승격 + 컨텍스트 스위칭 기본값 — 해제를 까먹을 수 없다
ReentrantLock 블록 (직접 관리) WAITING (parking) CAS 한 번 수준 대기 큐 + 컨텍스트 스위칭 기능 — tryLock · 인터럽트 · 공정성 · 여러 Condition
ReentrantReadWriteLock 블록 (읽기/쓰기 분리) WAITING (parking) CAS 한 번 + 읽기 카운터 읽기 카운터 자체가 경합 지점 읽기 병렬 — 단, 임계 영역이 길 때만 이득
StampedLock (낙관적 읽기) 블록 (읽기/쓰기 분리) 대기 자체가 없음 사실상 0 쓰기가 잦으면 validate 실패 → 재읽기 읽기 극단 편중 — 조건 5개가 모두 참일 때만
Atomic (CAS) 변수 하나 RUNNABLE (잠들지 않음) CAS 한 번 재시도 폭증 + 캐시 라인 경합 변수 하나의 논블로킹 갱신

오른쪽 두 칸의 대비가 축 셋에서 말한 내용의 요약이다. 경합이 없으면 넷 다 비슷하게 싸고, 경합이 있어야 성격이 갈린다.

실무 판단 — 자주 틀리는 지점들

1성능을 이유로 synchronized를 피하는 것은 대부분 근거 없는 최적화다. 경량 락·적응형 스핀·락 생략·락 병합이 살아 있어 경합 없는 synchronized는 지금도 싸다. 바꾸려면 먼저 경합을 측정한다 — 프로파일러의 락 경합 뷰나 JFR의 jdk.JavaMonitorEnter 이벤트로 "실제로 이 락에서 얼마나 기다렸는가"를 본 뒤에 판단한다.
2ReentrantLock을 고르는 이유는 성능이 아니라 기능이라고 말해야 한다. tryLock · lockInterruptibly · 공정성 · 여러 Condition 중 실제로 쓰는 것 하나를 대라고 했을 때 대답이 안 나오면 그 자리에는 synchronized가 맞다.
3StampedLock은 조건이 전부 맞을 때만 쓴다. "읽기가 극단적으로 많다 + 병목이 실측됐다 + 재진입이 없다 + Condition이 필요 없다 + 패턴을 정확히 지킬 수 있다" 다섯 개가 모두 참일 때다. 하나라도 어긋나면 성능이 가장 좋은 도구가 아니라 가장 오용하기 쉬운 도구를 고르는 셈이 된다.
4읽기가 많다고 무조건 읽기-쓰기 락이 아니다. 읽기 락 자체도 공유 카운터 갱신 비용을 치르므로 임계 영역이 짧으면 synchronized보다 느려질 수 있다. 필드 하나 읽고 나오는 정도라면 그냥 volatile이나 synchronized가 답이다.
5Atomic을 여러 개 늘어놓고 "동기화했다"고 생각하지 않는다. 원자적 연산 여러 개의 합은 원자적이 아니다. 지켜야 할 것은 개별 연산의 원자성이 아니라 불변식이다.
6락 안에서 외부 호출을 하지 않는다. 어떤 도구를 쓰든 마찬가지다. 락을 쥔 채 HTTP·DB·남이 등록한 콜백을 부르면 락을 쥔 시간이 상대 시스템의 응답 시간에 종속되고, 상대가 느려지는 순간 우리 쪽 대기가 폭발한다.
정리도구 선택보다 임계 영역의 내용이 더 중요한 경우가 많다. 어떤 락을 쓰든 락을 쥔 시간이 짧고 예측 가능해야 한다.

요즘은 바이어스드 락도 제거됐다던데, synchronized는 이제 느린 것 아닌가요?시니어 변별힌트: 제거된 것과 느려진 것은 다른 이야기다 (→ 4절)

제거된 것과 느려진 것은 다른 이야기라는 것을 구분하는지 보는 질문이다.

바이어스드 락은 "대부분의 락은 사실 한 스레드만 쓴다"는 가정에 기대, 락 객체 헤더에 "이 락은 이 스레드 것"이라고 새겨 두고 그 스레드는 CAS조차 없이 진입하게 하던 최적화였다. JDK 15에서 기본 비활성화·폐기 예고된 뒤 제거됐다.

제거 이유는 성능이 나빠서가 아니라 가정이 안 맞게 됐기 때문이다. 람다·스트림·스레드풀이 흔해지면서 락 하나를 여러 스레드가 돌아가며 쓰는 패턴이 늘었고, 가정이 깨졌을 때 되돌리는(revocation) 비용과 JVM 코드 복잡도가 이득을 넘어섰다.

바이어스드 락이 빠지고도 남아 있는 것이 넷이다.

  • 경량 락 — 경합이 없으면 OS로 내려가지 않고, 스택에 락 레코드를 만든 뒤 객체 헤더를 CAS 한 번으로 바꾸는 것으로 진입이 끝난다.
  • 적응형 스핀 — 경합이 생겨도 곧바로 재우지 않는다. 곧 풀릴 것 같으면 잠깐 제자리에서 돈다. 재웠다 깨우는 비용이 짧은 대기보다 비싸기 때문이다.
  • 락 생략 — JIT가 탈출 분석으로 "이 객체는 메서드 밖으로 안 나간다"를 증명하면 그 락을 아예 지운다.
  • 락 병합 — 같은 락을 짧은 간격으로 잡았다 놨다 반복하면 JIT가 하나의 큰 구간으로 합친다.

그리고 성능 얘기 뒤에 더 중요한 근거를 붙인다. synchronized의 진짜 강점은 블록을 벗어나면 반드시 풀린다는 것이다. 예외로 튀어나가도 JVM이 푼다. ReentrantLock의 가장 흔한 사고인 unlock() 누락이 원천적으로 불가능하다. 성능이 비슷하다면 실수할 수 없는 쪽이 옳은 기본값이다.

ReentrantLock에서 unlock()을 빠뜨리면 어떻게 되나요? 어떻게 발견하나요?힌트: 증상은 데드락과 같은데 자동 탐지에는 안 잡힌다 (→ 5절)

그 락은 영구히 잠긴다. 쥔 스레드가 다른 일을 하러 가 버렸으니 아무도 풀어 줄 수 없고, 이후 그 락을 요청하는 모든 스레드가 하나씩 쌓인다. 요청 처리 스레드가 하나씩 갇히다가 스레드풀이 마르면 그 락과 무관한 API까지 함께 죽는다.

증상은 데드락과 똑같은 "멈춤"인데 JVM 자동 탐지에는 안 잡힌다. 원인이 순환이 아니라 해제 누락이기 때문이다. 데드락 탐지기는 "A가 B를 기다리고 B가 A를 기다린다"는 사이클을 찾는데, 여기엔 사이클 자체가 없다 — 소유자가 아무도 기다리지 않고 그냥 떠났을 뿐이다.

그래서 덤프를 이렇게 읽는다.

"http-nio-8080-exec-12" #212 ... java.lang.Thread.State: WAITING (parking) at jdk.internal.misc.Unsafe.park(Native Method) - parking to wait for <0x000000071b2c0f80> (a java.util.concurrent.locks.ReentrantLock$NonfairSync) ... 같은 주소를 기다리는 스레드가 40개 ... $ jstack -l <pid> | grep -A2 "Locked ownable synchronizers" → <0x000000071b2c0f80> 을 "소유"한다고 나오는 스레드가 없다 ← 해제 누락 확정

즉 수십 개 스레드가 WAITING (parking)으로 같은 주소에 몰려 있는데, jstack -l의 "Locked ownable synchronizers"로 소유자를 찾아보면 그 락을 쥔 스레드가 이미 다른 일을 하고 있거나 아예 없다. 이 조합이면 해제 누락이다.

예방은 규칙을 기계적으로 지키는 것이다. lock()은 try 밖에, unlock()은 finally에. lock()을 try 안에 넣는 실수도 흔한데, 이 경우 락 획득에 실패했을 때도 finally의 unlock()이 실행돼 IllegalMonitorStateException이 난다.

그리고 근본적인 답을 덧붙인다. ReentrantLock의 기능이 실제로 필요 없다면 synchronized로 돌아가는 것이 최선의 예방책이다.

StampedLock의 낙관적 읽기가 항상 이득인가요?시니어 변별힌트: 판단 기준은 읽기 비율이 아니다 (→ 6절)

아니다. "낙관"이라는 이름 그대로 가정이 맞을 때만 이득이다.

비용 구조는 이렇다. 쓰기가 드물면 validate가 거의 항상 통과하므로 읽기 비용이 사실상 0이다 — 락을 잡지도 않고 카운터를 갱신하지도 않는다. 반대로 쓰기가 잦으면 validate가 자주 실패하고, 실패할 때마다 정식 읽기 락을 잡고 처음부터 다시 읽는다. 헛일을 한 번 더 한 셈이라 그냥 읽기 락을 잡는 것보다 느려진다.

판단 기준은 읽기 비율이 아니라 "읽는 도중에 쓰기가 끼어들 확률"이다

읽기 구간이 길수록 그 확률이 올라간다. 그래서 읽기가 아무리 많아도 읽기 자체가 오래 걸리는 구조라면 낙관적 읽기는 잘 안 맞는다.

여기에 오용 위험을 함께 말해야 답이 완성된다. 재진입이 안 되므로 락을 쥔 채 다른 메서드를 부르는 구조에서는 자기 자신과 교착하고, Condition이 없어 조건 대기 구조에는 쓸 수 없으며, 반드시 지역 변수로 복사한 뒤 validate를 통과해야만 값을 쓸 수 있다 — 이 패턴을 어기면 앞 필드는 옛 값, 뒤 필드는 새 값인 찢어진 상태로 계산하게 되고, 참조 필드였다면 이미 무효가 된 객체를 따라간다.

결론. "읽기가 극단적으로 많다 + 병목이 실측됐다 + 재진입 없다 + Condition 필요 없다 + 패턴을 정확히 지킬 수 있다"가 모두 참일 때만 쓴다. 하나라도 걸리면 ReentrantReadWriteLock이 안전하다.

읽기가 많으면 ReadWriteLock이 항상 synchronized보다 빠른가요?힌트: 읽기 락은 무엇을 CAS로 갱신하는가 (→ 2절 축 둘)

아니다. 임계 영역이 짧으면 오히려 느릴 수 있다.

읽기 락이 "여러 스레드가 동시에 통과"를 구현하는 방법은 "지금 몇 명이 읽고 있는가"를 세는 공유 카운터다. 읽기 락을 잡을 때마다 그 카운터를 CAS로 올리고, 놓을 때 내린다. 즉 읽기 스레드들이 서로를 막지는 않지만, 같은 카운터를 두고 경합하는 것은 마찬가지다. 읽기 스레드가 많아질수록 이 카운터가 새로운 경합 지점이 된다.

그래서 손익 구조가 이렇게 된다. 임계 영역 안에서 하는 일이 충분히 길어야 병렬로 읽어서 버는 시간이 카운터 경합 비용을 넘는다. 필드 두 개 읽고 나오는 정도의 짧은 구간이라면 부대비용만 치르고 이득은 없다.

판단 순서를 이렇게 말하면 좋다. 필드 하나만 읽으면 volatile → 짧은 임계 영역이면 synchronized → 임계 영역이 길고 읽기가 압도적일 때 비로소 ReentrantReadWriteLock → 거기서 더 짜내야 하고 조건이 맞으면 StampedLock. 그리고 이 판단은 전부 측정 뒤에 한다.

네 도구 중 무엇을 쓸지 판단이 안 서면 어떻게 하나요?힌트: "판단이 안 선다"는 것 자체가 신호다 (→ 3절)

"판단이 안 선다"는 것 자체가 대개 신호다 — 직접 동기화가 아니라 다른 층에서 풀어야 한다는 신호다.

먼저 세 가지를 확인한다. 공유하는 것이 맵이나 큐라면 ConcurrentHashMap·BlockingQueue 같은 동시성 컬렉션으로 대체된다. 데이터를 통째로 교체하는 구조라면 불변 객체 + volatile 참조로 끝난다. 애초에 공유하지 않아도 되는 데이터라면 스레드 한정으로 공유 자체를 없앤다. 이 셋 중 하나로 풀리는 경우가 생각보다 많다.

그래도 직접 동기화가 필요하다면 synchronized로 시작한다. 이유는 셋이다. ①경합이 없으면 비용이 거의 없고, ②해제를 까먹을 수 없어 사고가 안 나며, ③나중에 실측으로 병목이 확인되면 그때 바꾸면 된다. 반대 방향 — 정교한 도구로 시작했다가 버그를 만나 단순한 쪽으로 돌아오는 것 — 이 훨씬 비싸다.

그리고 도구 선택보다 먼저 볼 것이 하나 더 있다. 임계 영역 안에 무엇이 들어 있는가다. 락 안에서 HTTP나 DB를 호출하고 있다면 어떤 도구로 바꿔도 문제는 해결되지 않는다. 그 호출을 락 밖으로 빼는 것이 도구를 바꾸는 것보다 훨씬 큰 개선이다.

AtomicLong 두 개로 계좌 이체를 구현했습니다. 각 연산이 원자적이니 안전한 것 아닌가요?힌트: 원자적 연산의 합은 원자적인가 (→ 2절 축 하나)

안전하지 않다. 원자적인 연산을 여러 개 이어 붙인다고 그 전체가 원자적이 되지는 않는다.

balanceA.addAndGet(-amount)와 balanceB.addAndGet(amount)는 각각은 완벽하게 원자적이다. 그런데 두 호출 사이에 다른 스레드가 두 잔액을 함께 조회하면 A에서는 이미 빠졌는데 B에는 아직 안 들어온 중간 상태가 보인다. 총합이 맞지 않는, 존재해서는 안 되는 상태다.

지켜야 할 것은 개별 연산의 원자성이 아니라 "둘 다 바뀌었거나 둘 다 안 바뀌었거나"라는 불변식이고, 이 불변식은 Atomic으로 표현할 수 없다. 여러 변수가 함께 일관돼야 하면 그 자리에는 락이 필요하다.

같은 이유로 검사 후 행동(check-then-act) — "재고를 확인하고 조건이 맞으면 차감", "null이면 초기화" — 도 Atomic의 영역이 아니다. 검사와 행동 사이에 다른 스레드가 끼어들 수 있기 때문이다.

(가산점) 락 없이 가는 방법이 하나 있긴 하다. 두 잔액을 불변 객체 하나로 묶고 그 참조를 AtomicReference로 통째로 교체하는 것이다. 상태 전체가 한 객체 안에 있으므로 참조 교체 한 번이 곧 원자적 상태 전이가 된다. 대신 갱신마다 객체를 새로 만드는 비용이 붙고, compareAndSet 실패 시 재시도 루프를 직접 써야 한다.

CAS 경합이 병목인지 스레드 덤프로 알 수 있나요?시니어 변별힌트: CAS는 스레드를 재우지 않는다 (→ 10절)

알 수 없다. 이게 CAS 병목의 가장 고약한 점이다.

락 경합은 스레드가 잠들기 때문에 덤프에 흔적을 남긴다 — synchronized는 BLOCKED (on object monitor), ReentrantLock은 WAITING (parking). 그런데 CAS는 실패해도 잠들지 않고 곧바로 다시 시도한다. 그래서 재시도로 CPU를 태우는 스레드가 전부 RUNNABLE로 찍힌다. 겉보기에는 "열심히 일하는 중"과 구별되지 않는다.

여기서 나오는 대표적 오판"덤프에 BLOCKED가 하나도 없으니 락 문제는 아니다" — BLOCKED는 synchronized 진입 대기에만 붙는다. ReentrantLock 대기는 WAITING (parking), CAS 경합은 아예 RUNNABLE이다.

그래서 판별은 이렇게 한다.

  • CPU 사용률과 함께 본다. 처리량은 안 오르는데 CPU만 높고, 덤프의 RUNNABLE 스레드들이 같은 incrementAndGet / getAndAdd 프레임에 몰려 있으면 CAS 재시도를 의심한다.
  • 여러 장을 짧은 간격으로 뜬다. 같은 스레드가 계속 같은 CAS 루프 안에 있으면 진전이 없는 것이다.
  • 스레드 수를 줄여 본다. 스레드를 줄였는데 오히려 처리량이 늘면 경합 지점 하나에 몰린 것이다.
  • 프로파일러·JFR로 확인한다. 락 경합은 JFR의 jdk.JavaMonitorEnter 이벤트로 보이지만, CAS 재시도는 이벤트가 없으므로 CPU 프로파일에서 해당 프레임의 비중으로 판단한다.

그리고 결론을 붙인다. 락이 없을 뿐 "경합 지점이 하나"라는 문제는 그대로 남아 있다. 여기서부터는 도구를 바꾸는 게 아니라 경합 지점 자체를 쪼개는 방향(LongAdder, 샤딩)으로 가야 한다.

ReentrantLock의 "재진입 가능"이 synchronized와의 차별점인가요? 그리고 왜 기본이 비공정 모드인가요?힌트: 이름은 차별점이 아니다 / barging (→ 5절)

재진입은 차별점이 아니다. synchronized도 같은 스레드가 이미 쥔 락을 다시 잡으면 그냥 통과시킨다. 이름에 들어 있어서 특징처럼 들릴 뿐, 두 도구가 공유하는 성질이다. (오히려 StampedLock이 재진입을 지원하지 않는 쪽이라 그게 특징이다.) 진짜 차별점은 tryLock · lockInterruptibly · 공정성 · 여러 Condition 넷이다.

비공정이 기본인 이유는 처리량이다. 비공정 락은 막 도착한 스레드가 대기 줄을 무시하고 먼저 채가는 것(barging)을 허용한다. 불공평해 보이지만, 대기 큐에서 스레드를 깨워 CPU에 올리는 데는 시간이 걸리고 그 사이 이미 CPU 위에 올라와 있는 스레드가 처리하고 나가는 편이 전체적으로 빠르다. 깨우는 동안 락이 놀고 있는 시간을 없애는 셈이다.

대가는 기아(starvation)다. 운 나쁜 스레드가 계속 밀려 지연 시간이 튈 수 있다.

그래서 공정 모드가 필요한 상황은 "어떤 요청도 수십 초씩 밀리면 안 된다"는 지연 시간 요구가 처리량보다 중요할 때뿐이고, 처리량 하락은 각오해야 한다. 참고로 공정 모드에서도 tryLock()(타임아웃 없는 형태)은 barging 성질을 유지해서, 대기 줄이 있어도 락이 비어 있으면 즉시 가져간다.

lock()을 try 블록 안에 넣으면 무슨 일이 생기나요?힌트: 락 획득에 실패했을 때 finally가 무엇을 하는가 (→ 5절)

락 획득에 실패했을 때도 finally의 unlock()이 실행돼 IllegalMonitorStateException이 난다.

lock()이 예외를 던지며 실패했다면 이 스레드는 락을 쥐지 않은 상태다. 그런데 try 안에서 실패했으므로 finally는 정상적으로 실행되고, 쥐지도 않은 락을 풀려고 시도한다. 자바는 "소유하지 않은 락을 푸는 것"을 IllegalMonitorStateException으로 막는다.

결과가 더 나쁜 이유는 원래 문제(락 획득 실패)가 이 예외에 가려진다는 것이다. 로그에는 진짜 원인이 아니라 IllegalMonitorStateException만 남는다.

그래서 규칙은 기계적으로 외운다lock()은 try 밖에, unlock()은 finally에. tryLock()을 쓸 때도 마찬가지로 성공을 확인한 뒤에 try에 들어간다.

이 실수가 존재한다는 사실 자체가 synchronized를 기본값으로 두는 근거이기도 하다. 문법이 해제를 보장하는 쪽에는 이런 실수의 여지가 없다.

StampedLock에서 지역 변수로 복사하지 않고 필드를 바로 쓰면 구체적으로 무슨 값을 읽게 되나요?시니어 변별힌트: 앞 필드와 뒤 필드 (→ 6절)

"존재한 적 없는 조합"을 읽게 된다. 낙관적 읽기 구간에는 아무 보호가 없다. 필드를 여러 개 읽는 동안 쓰기가 끼어들면 앞의 필드는 옛 값, 뒤의 필드는 새 값인 조합이 나온다. 좌표 (x,y)를 (0,0)에서 (100,100)으로 옮기는 쓰기 중간에 읽으면 (0,100)이라는 한 번도 실제로 존재한 적 없는 좌표를 얻는다. 이걸 찢어진 값(torn read)이라고 부른다.

더 위험한 경우는 참조 필드다. validate 전에 역참조하면 이미 무효가 된 객체를 따라가게 된다 — 교체된 배열의 옛 참조를 들고 인덱스를 접근하면 ArrayIndexOutOfBoundsException이 나거나, 정리된 객체의 필드를 읽어 NullPointerException이 날 수 있다. 그것도 매우 드물게, 재현이 안 되는 형태로.

그래서 패턴이 고정돼 있다.

  1. long stamp = sl.tryOptimisticRead() — 도장만 받는다(락 없음).
  2. 필드를 전부 지역 변수로 복사한다. 여기서는 계산도 역참조도 하지 않는다.
  3. sl.validate(stamp) — 통과하면 지역 변수를 그대로 쓴다.
  4. 실패하면 readLock()으로 정식으로 다시 읽고 finally에서 unlockRead(stamp).

이 패턴을 매번 손으로 써야 하고 한 군데만 틀려도 조용히 잘못된 값을 읽는다는 점 자체가 선택 기준에 들어가야 한다. "성능이 가장 좋은 도구"가 아니라 "가장 오용하기 쉬운 도구"를 고르는 셈이 될 수 있다.

CAS의 ABA 문제가 무엇인가요? 단순 카운터에서도 문제가 되나요?가산점힌트: 값은 같은데 의미가 다를 수 있다 (→ 7절)

값이 A에서 B로 갔다가 다시 A로 돌아오면, CAS는 "안 바뀌었다"고 판단해 성공한다. CAS가 확인하는 것은 "지금 값이 내가 읽었던 값과 같은가"이지 "그 사이에 아무 일도 없었는가"가 아니기 때문이다.

단순 카운터에서는 문제가 되지 않는다. 값이 5였다가 7이 됐다가 다시 5로 돌아왔다면, 그 5는 의미상으로도 5다. 우리가 하려는 일(5를 6으로 바꾸기)의 결과도 옳다.

문제는 값이 "상태의 대표"일 때 — 특히 노드 참조를 다루는 lock-free 스택·큐다. 스택 top이 노드 A였는데, 그 사이 A가 pop되고 다른 노드가 push됐다가 회수된 A가 재사용돼 다시 top이 되면, CAS는 성공하지만 A가 가리키는 next는 이미 완전히 다른 리스트다. 결과적으로 이미 제거된 노드를 되살리거나 리스트가 끊긴다.

해법은 값에 버전 번호를 함께 싣는 것이다. AtomicStampedReference가 (참조, 스탬프) 쌍을 함께 CAS하므로 값이 A로 돌아와도 스탬프가 달라 실패한다. "변경 여부"를 값이 아니라 버전으로 판정한다는 점에서 DB의 낙관적 락(버전 컬럼)과 같은 발상이다.

락 안에서 외부 API를 호출하고 있습니다. 도구를 ReentrantLock으로 바꾸면 나아지나요?힌트: 도구 선택보다 임계 영역의 내용 (→ 10절)

거의 나아지지 않는다. 문제는 도구가 아니라 임계 영역의 내용이다.

락을 쥔 채 HTTP·DB·남이 등록한 콜백을 부르면 락을 쥔 시간이 상대 시스템의 응답 시간에 종속된다. 상대가 평소 50ms인데 장애로 5초가 되면 우리 쪽 락 대기는 100배로 늘어난다. 대기 스레드가 쌓이고, 스레드풀이 마르고, 그 락과 무관한 API까지 함께 죽는다. 남의 장애를 우리 장애로 수입하는 구조다.

순서는 이렇게 잡는다.

  1. 외부 호출을 락 밖으로 뺀다. 락 안에서는 메모리 상태만 읽고 쓰고, 계산이나 I/O는 밖에서 한다. 상태를 스냅샷으로 복사해 나온 뒤 호출하고, 필요하면 다시 짧게 락을 잡아 반영한다.
  2. 콜백은 락 밖에서 실행한다. 리스너 목록은 락 안에서 복사만 하고, 실제 호출은 락을 놓은 뒤에 한다. 남이 등록한 코드가 무엇을 할지(다른 락을 잡을지) 알 수 없기 때문이다 — 여기서 데드락도 생긴다.
  3. 그래도 남는 대기에는 상한을 건다. 이때 비로소 tryLock(timeout)이 의미를 갖는다. 다만 이건 완화이지 해결이 아니다.

한 문장으로 정리하면 "도구 선택보다 임계 영역의 내용이 더 중요한 경우가 많다." 어떤 락을 쓰든 락을 쥔 시간이 짧고 예측 가능해야 한다.

락을 걸었으면 가시성도 따로 챙겨야 하나요? volatile을 같이 붙여야 하는 건가요?힌트: 락 획득/해제에 무엇이 함께 들어가는가 (→ 1절)

필요 없다. 네 도구 모두 상호 배제와 가시성을 함께 준다.

락을 잡고 푸는 동작에는 메모리 배리어가 함께 들어간다. 그래서 같은 락으로 보호한 구간에서 쓴 값은, 다음에 그 락을 잡는 스레드에게 반드시 보인다. Atomic의 CAS도 마찬가지다. "락을 걸었는데 가시성도 따로 챙겨야 하나요"라는 걱정은 필요 없다.

단, 조건이 하나 붙는다 — "같은 락으로"어떤 스레드는 락을 잡고 쓰는데 다른 스레드는 락 없이 읽는다면 보장은 깨진다. 보호는 그 변수에 접근하는 모든 경로에 걸려 있어야 한다. 읽기에도 락이 필요한 이유가 이것이다 — 읽기끼리 막을 필요가 없다는 것과, 읽기에 아무 동기화도 필요 없다는 것은 다른 말이다.

반대로 volatile은 가시성만 주고 상호 배제는 주지 않는다. count++처럼 읽고-계산하고-쓰는 복합 연산에는 volatile로 부족하다. 그래서 역할이 이렇게 갈린다 — "플래그 하나를 켜고 끄는" 수준이면 volatile, "읽은 값을 근거로 쓰는" 순간부터는 Atomic이나 락이다.

고경합 카운터라 LongAdder를 쓰라고 하는데, AtomicLong과 무엇이 다르고 언제 쓰면 안 되나요?가산점힌트: 경합 지점 하나를 어떻게 처리하는가 (→ 7·8절)

AtomicLong은 경합 지점이 하나이고, LongAdder는 그 지점을 여러 개로 쪼갠다.

AtomicLong은 스레드가 몇이든 같은 변수 하나를 CAS로 다툰다. 스레드가 여덟이면 한 번의 성공마다 일곱 번의 실패가 나오고, 실패한 스레드는 다시 읽고 다시 시도한다. CPU는 바쁜데 실제 증가는 한 번에 하나뿐이다.

LongAdder는 내부에 여러 개의 셀을 두고 스레드를 서로 다른 셀로 흩어 보낸다. 경합이 감지되면 셀을 늘려 각 스레드가 다른 메모리 위치를 갱신하게 만든다. 합계가 필요하면 sum()으로 셀들을 훑어 더한다. "경합을 이기는" 게 아니라 "경합할 일을 없애는" 접근이다.

그래서 쓰면 안 되는 자리가 분명하다.

  • 읽기가 잦으면 손해다. AtomicLong.get()은 필드 하나 읽기지만, LongAdder.sum()은 셀 전체를 순회한다. 갱신은 드문데 조회가 잦은 값이라면 AtomicLong이 낫다.
  • sum()은 "그 순간의 정확한 스냅샷"이 아니다. 순회하는 동안에도 다른 스레드가 셀을 갱신할 수 있으므로, 동시 갱신 중에 얻은 합계는 근사값으로 봐야 한다. 모니터링 지표에는 충분하지만 잔액·재고처럼 정확한 값을 근거로 판단하는 자리에는 부적합하다.
  • compareAndSet류가 없다. "값을 읽고 조건에 따라 바꾸기"가 필요하면 LongAdder로는 안 된다. 용도가 더하기 전용 통계 카운터다.
  • 메모리를 더 쓴다. 셀 배열이 있고, 셀들이 같은 캐시 라인에 몰리지 않도록 패딩도 들어간다.

기준 문장은 이렇다. "갱신이 극단적으로 잦고 조회는 가끔인 통계 카운터"면 LongAdder, 그 외에는 AtomicLong. 그리고 여기서 등장하는 캐시 라인 경합(false sharing)은 별도 주제로 이어진다.

모든 걸 ConcurrentHashMap으로 바꾸면 동기화 고민이 끝나나요?힌트: 컬렉션이 보장하는 단위는 무엇인가 (→ 3절)

끝나지 않는다. 동시성 컬렉션이 보장하는 것은 "개별 연산의 원자성"이지 "내가 짠 여러 줄의 원자성"이 아니다.

가장 흔한 사고가 이것이다.

if (!map.containsKey(k)) {   // ① 없는 걸 확인하고
    map.put(k, newValue());  // ② 넣는다 — 사이에 다른 스레드가 넣으면 덮어쓴다
}

containsKey도 put도 각각 원자적이지만, 둘을 이어 붙인 "검사 후 행동"은 원자적이 아니다. 이건 2절 축 하나에서 본 "Atomic 두 개를 이어 붙이면 안 된다"와 정확히 같은 함정이다.

답은 락을 추가하는 것이 아니라 컬렉션이 제공하는 원자적 복합 연산을 쓰는 것이다.

map.putIfAbsent(k, v);                 // 없을 때만 넣기 — 한 번의 원자적 연산
map.computeIfAbsent(k, key -> init()); // 없으면 만들어 넣고 그 값을 돌려준다
map.merge(k, 1L, Long::sum);           // 있으면 합치고 없으면 넣기
computeIfAbsent의 함정매핑 함수는 해당 버킷의 락을 쥔 채 실행된다. 그 안에서 같은 맵을 다시 건드리거나(IllegalStateException 또는 교착) 오래 걸리는 I/O를 하면 그 버킷 전체가 멈춘다. 함수는 짧고 순수하게 유지한다.

그리고 하나 더. size()·isEmpty()·순회는 "그 순간의 정확한 스냅샷"이 아니다. ConcurrentHashMap의 이터레이터는 약한 일관성(weakly consistent)이라 순회 중 다른 스레드의 변경이 보일 수도, 안 보일 수도 있다. 예외를 던지지 않는 대신 정확한 시점 일관성을 포기한 것이다. 순회 결과를 근거로 판단해야 한다면 그 판단 자체를 락으로 감싸거나 설계를 바꿔야 한다.

한 줄 요약
동기화 도구는 네 축 — 보호 대상이 변수 하나인가 여러 줄의 로직인가, 읽기/쓰기 비율은 어떤가, 경합이 실측됐는가, 대기를 포기할 수 있어야 하는가 — 로 갈리며, 그 답은 변수 하나면 Atomic(고경합 통계 카운터면 LongAdder), 읽기가 압도적이고 임계 영역이 길면 StampedLock 또는 ReentrantReadWriteLock, 타임아웃·인터럽트·공정성·여러 Condition이 필요하면 ReentrantLock, 나머지는 전부 synchronized다 — synchronized가 기본값인 이유는 바이어스드 락이 걷힌 뒤에도 경량 락·적응형 스핀·락 생략·락 병합이 남아 저경합에서 여전히 싸고, 무엇보다 블록을 벗어나면 반드시 풀려 unlock() 누락이라는 영구 정지 사고가 원천 봉쇄되기 때문이며, 그 넷을 고르기 전에 반드시 먼저 물을 질문은 "동시성 컬렉션·불변 객체·스레드 한정으로 직접 동기화를 피할 수 있는가"다.
