HashMap 내부 동작 — 배열 한 칸을 고르고, 그 칸 안에서만 찾는다
본체는 Node 배열 하나. 같은 칸에 겹치면 리스트로 잇고, 그래도 심하면 그 칸만 레드-블랙 트리로 바꾼다

면접 질문: "HashMap의 내부 동작(해시 충돌 처리, 리사이징, 트리화)을 설명해주세요."

핵심 관전 포인트 — HashMap은 "배열(버킷) + 충돌 시 연결 리스트, 심하면 레드-블랙 트리"다. key의 hashCode를 상위 비트와 섞어(spread) (n-1) & hash로 배열 인덱스를 정하고, 같은 칸에 충돌하면 리스트로 연결해 equals로 찾는다. 원소 수가 용량 × 0.75를 넘으면 배열을 2배로 늘려 전체 재배치하며(그래서 대량 삽입 전 초기 용량 지정이 유효한 최적화), 한 버킷의 리스트가 8을 넘고 테이블이 64 이상이면 그 버킷만 트리로 바꿔 최악 성능을 O(n)에서 O(log n)으로 방어한다.
  • 1
    본체는 Node 배열 하나입니다. hashCode를 spread로 한 번 섞은 뒤 (n-1) & hash로 칸(버킷)을 고르고, 조회는 그 칸 하나만 열어봅니다. 이 "칸 고르기 → 칸 안에서 equals 대조"의 2단계가 평균 O(1)의 정체입니다.
  • 2
    같은 칸에 겹치면 연결 리스트로 이어 붙입니다(분리 연결법). 리스트가 길어지면 O(1)이 무너지므로 두 개의 방어선이 있습니다 — 전체가 붐비면 용량 × 0.75에서 2배 리사이징, 특정 칸에만 몰리면 그 칸만 트리화입니다.
  • 3
    원인이 다르니 처방도 다릅니다. 칸이 부족한 것이면 늘리면 되지만(리사이징), hashCode가 나쁘거나 해시 플러딩 공격이면 칸을 늘려도 소용없어 자료구조 자체를 바꿉니다(트리화). 그래서 트리화 조건에 "테이블 64 이상"이라는 오진 방지 단서가 붙습니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "HashMap의 내부 동작(해시 충돌 처리, 리사이징, 트리화)을 설명해주세요."

출제 의도 — 자료구조 하나를 끝까지 파본 적 있는지의 표본 검사다. HashMap은 모두가 매일 쓰지만 내부를 열어본 사람은 드물다. 그리고 리사이징 비용을 아는 사람은 초기 용량 지정 같은 사소하지만 대량 처리에서 유의미한 최적화를 자연스럽게 한다. 면접관은 "이 사람이 쓰는 도구를 이해하고 쓰는가"를 여기서 가늠한다.

약점 A"충돌하면 리스트로 연결됩니다"에서 끝나는 답 — 그 리스트가 길어지면 어떻게 되는지, 두 개의 방어선(리사이징 · 트리화)이 왜 둘인지를 못 짚으면 여기서 멈춘다.
약점 B숫자만 외운 답 — "0.75, 8, 64"를 말하면서 근거를 못 대는 경우. 이 문서의 절반은 그 숫자들이 왜 그 값인지에 대한 것이다.
약점 C"hashCode % 배열길이로 인덱스를 구합니다" — 실제 코드는 %를 쓰지 않는다. (n-1) & hash이고, 왜 그런지 · 그 대가가 무엇인지가 이 질문에서 가장 깊이 파고들 수 있는 지점이다.
합격선"배열 + 체이닝"에서 출발해 "리스트가 길어지는 원인이 둘이고, 원인이 다르니 처방도 둘"까지 한 호흡에 이어 말하는 것.
이 문서의 전제 — 규약이 아니라 구조를 본다 equals / hashCode 규약 자체(왜 같이 재정의해야 하는지, 대칭성·일관성 등)는 03 equals·hashCode 규약 문서에서 다뤘다. 여기서는 그 규약이 어떤 내부 구조에서 도출되는지만 짧게 짚고, 버킷 배열 · 체이닝 · 리사이징 · 트리화라는 내부 메커니즘에 집중한다. 동시성 대안인 ConcurrentHashMap은 13번 문서로 넘긴다.

1. 본체는 Node 배열 하나 — 아파트 우편함

HashMap의 본체는 Node 배열 하나다(내부 필드 이름이 그대로 table이다). 각 칸을 버킷(bucket, 양동이)이라 부른다.

비유 — 아파트 우편함 key의 hashCode는 "몇 호 우편함에 넣을지"를 정하는 주소 계산이고, get은 그 우편함 한 칸만 열어보는 것이다. 1층 우편함 전체를 뒤지지 않으니 평균 O(1)이다 — HashMap의 존재 이유가 이 한 줄이다.
개념 코드 put(key, value)의 뼈대 — 이 세 줄이 문서 전체의 지도다
int hash  = spread(key.hashCode());     // ① 해시 보정 (4절)
int index = (table.length - 1) & hash;  // ② 버킷 인덱스 결정 (2절)
// ③ table[index]가 비었으면 새 Node, 있으면 충돌 처리 (5절)

이 세 줄 중 ①과 ②가 전부 비트 연산이다. 이 문서에서 가장 중요한 부분이고, 동시에 눈으로만 훑으면 절대 이해되지 않는 부분이다. 비트를 실제로 늘어놓고 한 단계씩 계산해 보자.

2. (n-1) & hash가 왜 hash % n과 같은가

hashCode는 32비트 정수라서 값의 범위가 배열 길이보다 훨씬 넓다. "apple".hashCode()는 93029210인데 배열 길이는 16이다. 그러니 넓은 값을 0~15 사이로 접어 넣어야 한다. 이 "접기"의 교과서적 방법이 나머지 연산 hash % 16이다.

그런데 HashMap의 실제 코드는 %를 쓰지 않는다. (n-1) & hash를 쓴다. 이 둘이 같은 값이 나오는 이유부터 보자.

2의 거듭제곱에서 1을 빼면 자릿수가 하나 내려가며 하위 비트가 전부 1인 형태가 된다. n = 16 = 0001 0000 → n-1 = 15 = 0000 1111 n = 32 = 0010 0000 → n-1 = 31 = 0001 1111 n = 64 = 0100 0000 → n-1 = 63 = 0011 1111

그래서 HashMap의 용량은 항상 2의 거듭제곱이다

생성자에 17을 넘겨도 내부에서 32로 올려 잡는다. 2의 거듭제곱이 아니면 n-1이 깔끔한 마스크가 되지 않아 이 트릭 자체가 성립하지 않기 때문이다.

2^k 용량 · (n-1) & hash 인덱싱 · spread — 셋은 따로 고른 것이 아니라 한 몸이다

바꾸는 이유는 둘이다 — 속도와 음수

3. 하위 비트만 쓰는 데서 생기는 약점

방금 본 계산에는 대가가 있다. (n-1) & hash는 hash의 하위 몇 비트만 보고 상위 비트는 통째로 버린다. 테이블이 16이면 하위 4비트, 나머지 28비트는 결과에 아무 영향도 주지 못한다.

극단적인 예를 보자. hashCode가 65536의 배수로 나오는 클래스가 있다고 하자(직접 만든 hashCode가 어떤 값에 큰 상수를 곱하는 형태면 충분히 생길 수 있다).

──────── 상위 16비트 ──────── ──────── 하위 16비트 ──────── & 1111 0 0000 0000 0000 0000 0000 0000 0000 0000 → 0번 칸 65536 0000 0000 0000 0001 0000 0000 0000 0000 → 0번 칸 131072 0000 0000 0000 0010 0000 0000 0000 0000 → 0번 칸 196608 0000 0000 0000 0011 0000 0000 0000 0000 → 0번 칸 ↑ 여기는 다 다른데 ↑ 여기가 전부 0이라 ↑ 결과가 같다

4. spread — 상위 비트의 정보를 하위로 끌어내린다

HashMap은 인덱스를 계산하기 전에 hashCode를 한 번 가공한다. 이 가공을 spread(퍼뜨리기)라고 부른다.

JDK HashMap.hash() — 실제 소스
static final int hash(Object key) {
    int h;
    // key.hashCode()를 그대로 쓰지 않고, 상위 16비트를 하위 16비트에 XOR로 섞는다.
    // 인덱스 계산이 하위 비트만 보므로, 버려질 상위 비트의 정보를
    // 미리 하위로 끌어내려 반영해 두는 것이다.
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

>>> — 부호 없는 오른쪽 시프트

  • 부호를 무시하고 오른쪽으로 미는 시프트
  • h >>> 16 = 32비트 값을 16칸 밀어 원래 상위 16비트를 하위 16비트 자리로 옮긴 값
  • 왼쪽 빈자리는 부호와 무관하게 0으로 채운다

^ — XOR (배타적 논리합)

  • 두 비트가 다르면 1, 같으면 0
  • 섞는 데 쓰는 이유: 한쪽 비트가 바뀌면 결과 비트도 반드시 바뀐다
  • AND·OR는 한쪽이 0이나 1로 고정되면 다른 쪽 변화를 삼켜 버린다
3절에서 전부 0번 칸으로 몰렸던 값들에 spread를 적용해 보자. [h = 65536] h 0000 0000 0000 0001 0000 0000 0000 0000 h >>> 16 0000 0000 0000 0000 0000 0000 0000 0001 ← 상위 16비트가 내려왔다 XOR 0000 0000 0000 0001 0000 0000 0000 0001 & 1111 0001 → 1번 칸 [h = 131072] h 0000 0000 0000 0010 0000 0000 0000 0000 h >>> 16 0000 0000 0000 0000 0000 0000 0000 0010 XOR 0000 0000 0000 0010 0000 0000 0000 0010 & 1111 0010 → 2번 칸 [h = 196608] h 0000 0000 0000 0011 0000 0000 0000 0000 h >>> 16 0000 0000 0000 0000 0000 0000 0000 0011 XOR 0000 0000 0000 0011 0000 0000 0000 0011 & 1111 0011 → 3번 칸
spread는 해결책이 아니라 값싼 보정이다 상위 16비트를 하위에 섞을 뿐이므로, 애초에 hashCode가 전부 같은 값이면 spread를 해도 전부 같다. 입력이 같으면 출력도 같다는 당연한 사실이다. 근본적인 분산 품질은 여전히 hashCode 구현의 책임이고, 그래서 트리화라는 별도의 방어선이 필요하다(11절).
null key가 허용되는 이유가 이 한 줄에 있다 (key == null) ? 0 : … — key가 null이면 hash를 아예 0으로 정해 항상 0번 칸으로 보낸다. NullPointerException이 날 자리를 분기 하나로 우회하는 것이고, HashMap이 null key를 하나 허용하는 방식이 바로 이것이다.

5. 충돌 처리 — 분리 연결법과 2단계 조회

서로 다른 key가 같은 인덱스를 받는 일은 — hashCode가 같아서든, 달라도 3절처럼 하위 비트가 같아서든 — 반드시 생긴다. 유한한 배열에 무한한 값을 넣는 이상 피할 수 없다. 이것을 해시 충돌이라 하고, HashMap의 대응은 그 칸의 노드들을 연결 리스트로 이어 붙이는 것이다. 칸 하나에 여러 개를 매달아 둔다고 해서 분리 연결법(separate chaining)이라 부른다.

put — 리스트를 순회한 뒤

  • hash가 같고 equals도 true인 노드가 있으면 value를 교체
  • 없으면 리스트 끝에 추가 (tail insert)
  • 끝에 붙이는 이유는 7절에서 다룬다

get — 2단계로 찾는다

  • ① 인덱스로 칸을 고른다 (상수 시간)
  • ② 그 칸의 리스트를 순회하며 equals로 확인
  • 비교 순서는 hash 먼저, 통과하면 equals — hash 비교는 int 비교라 훨씬 싸다

6. key는 왜 불변이어야 하는가

같은 구조에서 두 번째 실무 규칙이 나온다. 가변 객체를 key로 쓰면 안 된다. 넣은 뒤 key의 필드를 바꿔 hashCode가 달라지면, 그 엔트리는 "옛 주소의 우편함"에 남아 있는데 조회는 새 주소의 우편함을 연다. HashMap은 필드 변경을 통지받는 장치가 없으므로 되돌릴 방법이 없다.

before 가변 객체를 key로 — 시한폭탄
// hashCode가 name 기반이라고 하자
Member m = new Member("kim");
map.put(m, profile);

m.setName("lee");      // key의 해시가 바뀌었다

map.get(m);     // null — 다른 칸을 연다
map.remove(m);  // 삭제도 실패
map.size();    // 1 — 유령이 남아 있다
after key는 불변으로
// 불변 필드만으로 equals/hashCode를 구성한다
record MemberKey(String id) {}
// record = 모든 필드 final
//        + equals/hashCode 자동 생성

map.put(new MemberKey("kim-001"), profile);

// id는 바뀌지 않으므로 해시도 고정
// → 넣은 칸에서 영원히 찾을 수 있다

key 선택 규칙 — 이 순서로 고른다

  1. 불변 타입을 최우선 — String, 박싱 타입, record, enum. 이미 검증된 hashCode를 얻는다.
  2. 직접 만든다면 불변 필드만으로 equals / hashCode를 구성한다. "id만으로" 가 대개 정답이다.
  3. 엔티티(JPA)를 key로 쓸 때 특히 주의 — 필드가 계속 바뀌는 대표적인 가변 객체다. id 기반 키 객체로 감싸는 편이 안전하다.
  4. 이미 넣은 key는 절대 건드리지 않는다. 꼭 바꿔야 하면 remove → 수정 → put 순서로, 반드시 꺼낸 뒤에 바꾼다.

7. Java 7 무한 루프 — 삽입 위치가 바뀐 이유 가산점

Java 7까지는 충돌 시 리스트의 머리에 삽입했다(head insert). 새 노드를 맨 앞에 꽂는 편이 리스트 끝까지 걸어가지 않아도 되어 빨랐기 때문이다. 문제는 리사이징과 겹칠 때였다.

Java 7 → 8에서 무엇이 바뀌고 무엇이 그대로인가
항목Java 7Java 8 이상
충돌 시 삽입 위치리스트 머리 (head insert)리스트 끝 (tail insert)
리사이징 시 순서뒤집힌다보존된다
동시 리사이징 → 순환 고리발생 (CPU 100% 무한 루프)이 형태는 사라짐
버킷 자료구조연결 리스트만리스트 + 레드-블랙 트리
동시 쓰기 시 put 유실발생여전히 발생
동시 쓰기 시 size 불일치발생여전히 발생 (size++는 원자적이지 않다)
thread-safe 여부아니다아니다 (동기화가 전혀 없다)

여기서 결론을 잘못 내리면 안 된다

tail insert로 이 형태의 무한 루프는 사라졌다. 하지만 HashMap은 여전히 동기화가 전혀 없는 thread-unsafe 자료구조이고, 동시 쓰기에서 put이 유실되거나 size가 실제 원소 수와 어긋나는 일은 그대로 일어난다.

"Java 8이라 괜찮다"가 아니라 "규약 위반이므로 어떤 버전에서도 동시 사용 자체가 버그"다

동시 접근이 있으면 ConcurrentHashMap을 쓴다(→ 13-concurrenthashmap-internals). 그리고 "어쩌다 한 번의 동시 쓰기쯤은 괜찮겠지"라는 타협이 가장 나쁘다 — 평상시에는 겹칠 확률이 낮아 몇 달간 멀쩡하다가 부하가 몰리는 날에만 재현되는 버그가 된다.

8. 리사이징 ① 언제 · 얼마나 늘리는가

1~7절을 합치면 HashMap의 성능은 한 가지 조건에 걸려 있다. 한 칸에 매달린 리스트가 짧아야 한다. 리스트가 길어지면 2단계 순회 비용이 그대로 올라가 O(1)이 무너진다. 그런데 리스트가 길어지는 원인은 둘이고, 원인이 다르니 처방도 다르다.

기준 — threshold(임계값)

원소 수 > 용량 × load factor → resize
이 곱셈 결과를 내부에서는 threshold라 부른다 · load factor 기본값 0.75

load factor 0.75는 왜 그 값인가

공간과 시간의 절충점이다.

낮추면 (예: 0.5)
  • 배열이 절반만 차도 확장 → 칸이 널널해 충돌이 줄고 조회가 빨라진다
  • 대신 빈 칸이 많아 메모리 낭비
  • 확장이 더 자주 일어나 리사이징 비용 증가
0.75
높이면 (예: 0.95)
  • 배열을 거의 꽉 채워 쓰므로 메모리 효율은 좋다
  • 대신 칸당 평균 원소 수가 올라가 리스트 순회 비용이 커진다
  • 트리화 임계 8의 전제가 흔들린다 (12절)
0.75의 자리 "충돌 확률을 충분히 낮게 유지하면서 공간 낭비도 참을 만한" 지점으로 잡은 기본값이다. 그리고 이 값은 12절의 트리화 임계값 8과 연결되어 있다 — 0.75라는 전제 위에서 계산했기 때문에 8이라는 숫자가 의미를 갖는다.
실무에서 이 값을 바꿀 일은 사실상 없다. 조정할 것이 있다면 load factor가 아니라 초기 용량이다.

9. 리사이징 ② hash & oldCap 한 번의 묘수

리사이징에서 노드를 옮길 때, 각 노드의 새 인덱스를 다시 계산해야 할 것 같다. 그런데 Java 8은 재계산하지 않는다. 비트 하나만 확인한다. 왜 그것으로 충분한지 실제 비트로 확인해 보자.

3절에서 같은 7번 칸에 있던 hash 23과 39로 따라가 보자. [hash = 23] 0001 0111 옛 인덱스 & 0 1111 0000 0111 = 7 새 인덱스 & 1 1111 0001 0111 = 23 = 7 + 16 → 옮겨야 한다 판정에 쓰는 연산: hash & oldCap 0001 0111 & 0001 0000 (= 16) ----------- 0001 0000 != 0 → "새 비트가 1이다" → index + oldCap [hash = 39] 0010 0111 옛 인덱스 & 0 1111 0000 0111 = 7 새 인덱스 & 1 1111 0000 0111 = 7 = 제자리 → 안 옮겨도 된다 판정에 쓰는 연산: hash & oldCap 0010 0111 & 0001 0000 (= 16) ----------- 0000 0000 == 0 → "새 비트가 0이다" → 제자리

재배치 판정 — 이 두 줄이 전부다

hash & oldCap == 0 → 제자리 (index 그대로)
hash & oldCap != 0 → index + oldCap 으로 이동

해시를 다시 계산할 필요도, 노드를 하나씩 새 위치에 삽입할 필요도 없다. AND 한 번이면 끝나고, 통계적으로 절반은 이사조차 하지 않는다.

오해 금지 — 값싸졌다는 것이지 공짜가 된 것이 아니다 전체 노드를 한 번씩 만져 lo/hi를 판정해야 하므로 O(n) 비용 자체는 그대로 남는다. 사라진 것은 ① 해시 재계산, ② 노드별 개별 삽입, ③ 순서 뒤집힘(=Java 7식 순환 고리)이다. "절반은 안 옮기니까 비용도 절반"은 오답이고, 그래서 다음 절의 초기 용량 최적화가 여전히 유효하다.

10. 리사이징 ③ 대량 삽입 전 초기 용량 지정

리사이징 비용을 아는 사람이 자연스럽게 하는 한 줄짜리 최적화가 있다. 이 질문의 출제 의도가 겨냥하는 지점이 정확히 여기다.

before 기본 용량 16에서 시작
Map<String, Order> map = new HashMap<>();
for (Order o : orders) {
    map.put(o.getId(), o);
}
// 10만 건을 넣는 동안
// 16 → 32 → 64 → … → 262144
// 리사이징이 십수 회 일어난다.
// 확장 때마다 그 시점의 전체 노드를
// 한 번씩 만져 lo/hi로 재배치한다.
after 예상 원소 수를 0.75로 나눠 초기 용량으로
Map<String, Order> map =
    new HashMap<>((int)(orders.size() / 0.75f) + 1);
for (Order o : orders) {
    map.put(o.getId(), o);
}
// 리사이징 0회

// Java 19+ 라면 같은 계산을 대신 해준다
Map<String, Order> map = HashMap.newHashMap(orders.size());

가장 흔한 실수 — 생성자 인자에 "원소 수"를 그대로 넣는다

생성자 인자는 "담을 원소 수"가 아니라 용량(배열 길이)이다. 여기에 load factor가 다시 곱해진다.

new HashMap<>(100_000) 을 쓴 경우 용량은 2의 거듭제곱으로 올림 → 131,072 threshold = 131,072 x 0.75 = 98,304 10만 건을 넣으면 98,304를 넘는다 → 결국 리사이징이 한 번 일어난다 new HashMap<>((int)(100_000 / 0.75f) + 1) 을 쓴 경우 인자 133,334 → 용량 262,144 로 올림 threshold = 262,144 x 0.75 = 196,608 10만 건은 여유롭게 들어간다 → 리사이징 0회
트레이드오프도 같이 말할 수 있어야 한다 리사이징을 없앤 대가로 배열을 더 크게 잡아 메모리를 더 쓴다. 위 예에서 후자는 용량 262,144짜리 배열을 처음부터 들고 있는다. 원소 수를 미리 알 수 있는 대량 적재에서는 남는 장사지만, 실제로는 훨씬 적게 들어올 Map에 큰 초기 용량을 박아 두면 빈 배열만 낭비하는 셈이 된다.

11. 트리화 ① 리스트의 최악을 O(log n)으로 방어

리사이징으로도 해결되지 않는 경우가 있다. 원소가 특정 칸에만 몰릴 때다. 칸을 아무리 늘려도 전부 한 칸으로 간다면 아무 소용이 없다. 이런 상황은 두 경로로 생긴다.

① hashCode 품질이 나쁠 때

  • 극단적으로 return 1; 같은 상수를 반환하는 hashCode
  • 큰 상수를 곱해 하위 비트가 항상 0이 되는 형태(3절)
  • 실수로 만들어지는 경우가 대부분이다

② 공격받을 때 — 해시 플러딩 DoS

  • 해시가 충돌하는 key를 의도적으로 대량 주입하는 공격
  • 요청 파라미터가 그대로 Map의 key가 되는 웹 서버에서 실제 공격 사례가 있었다
  • 파라미터 수백 개짜리 요청 몇 개로 CPU를 태울 수 있다

두 경우 모두 리스트 하나에 전부 매달려 조회가 O(n)으로 전락한다. Java 8부터는 여기에 방어선을 하나 둔다. 한 버킷이 임계를 넘으면 그 버킷만 레드-블랙 트리로 바꾼다.

왜 8인가 — 정상 상황에서는 절대 도달하지 않는 선이다

hashCode가 제대로 흩어져 있다면 원소들은 버킷에 랜덤하게 떨어진다. 이때 "한 버킷에 k개가 들어갈 확률"은 포아송 분포(드물게 일어나는 사건이 정해진 구간 안에 몇 번 일어날지의 확률 분포)를 따른다.

이 분포의 평균값 λ는 칸 하나당 평균 원소 수다. load factor가 0.75이므로 확장 직전에는 칸당 0.75개, 막 2배로 확장한 직후에는 절반인 0.375개다. 즉 실제 운영 중 평균은 대략 0.5 언저리를 오간다. λ = 0.5로 계산한 확률표가 JDK 소스 주석에 그대로 실려 있다.

13. 트리화 ③ 트리 안에서는 무엇으로 정렬하나 가산점

이진 탐색 트리는 원소 사이에 순서가 있어야 성립한다. 그런데 Map의 key는 아무 타입이나 될 수 있고, 순서가 정의돼 있으리라는 보장이 없다. HashMap은 이 문제를 3단계로 푼다.

실무적 함의는 2번에 있다

hashCode가 전부 같아도 key가 Comparable이면 O(log n)이 온전히 보장된다

해시 플러딩 공격의 주된 표적인 String이 Comparable이므로, 이 방어가 가장 필요한 자리에서 가장 잘 작동한다. 반대로 hashCode가 전부 같으면서 Comparable도 아닌 커스텀 key는 3번 tie-break에 의존하게 되어, 트리 안에서도 탐색 범위를 깔끔히 반으로 줄이지 못한다 — 트리화가 만능이 아닌 유일한 구멍이다.

14. put이 겪는 일 — 전체 흐름 한 장

흐름에서 놓치기 쉬운 두 가지 ① value만 교체될 때는 size가 늘지 않으므로 리사이징 검사도 없다. 같은 key로 100만 번 put해도 배열은 그대로다.
② 버킷 조건(8/64)과 전체 조건(0.75)은 별개로 매번 확인된다. 한 put에서 트리화와 리사이징이 둘 다 관여할 수 있다.

이 문서에서 나오는 실무 습관 3가지 — 원리와 함께

  • 대량 삽입 전 초기 용량 지정 — 리사이징이 O(n)이고 십수 회 반복되기 때문. 단 인자는 원소 수가 아니라 원소 수 / 0.75
  • key는 불변으로 — 넣은 뒤 hashCode가 바뀌면 옛 칸에 유령 엔트리가 남아 get·remove가 모두 실패하기 때문
  • 동시 접근이면 ConcurrentHashMap — HashMap은 동기화가 전혀 없고, Java 8에서도 put 유실·size 불일치는 그대로이기 때문

16. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 막히면 옆에 적힌 절로 돌아간다.

용량이 왜 하필 2의 거듭제곱이어야 하나요?힌트: 세 가지 설계가 한 몸이다 핵심

인덱스 계산 (n-1) & hash 때문이다. n이 2^k이면 n-1이 하위 k비트가 전부 1인 마스크가 되어, 나머지 연산을 비트 AND 한 번으로 대체할 수 있다(2절). 나눗셈은 수십 사이클, AND는 1사이클이고 이 자리는 모든 조회가 반드시 통과하는 자리다. 덤으로 음수 hash에서도 항상 0 이상의 인덱스가 나온다.

리사이징에서도 값을 한다. 용량을 정확히 2배로 늘리면 마스크에 비트가 정확히 하나 늘어나므로, "새로 보게 된 비트 하나"만 확인해 제자리 / +oldCap 두 그룹으로 쪼개는 값싼 재배치가 가능해진다(9절).

대신 하위 비트만 쓰게 되는 약점이 생기는데, 그것을 메우는 장치가 상위 16비트를 XOR로 섞는 spread다. 세 설계(2^k 용량, & 인덱싱, spread)는 따로 고른 것이 아니라 한 몸이라고 말하면 이해했다는 신호가 된다.

hashCode가 전부 같은 key 100만 개를 넣으면 어떻게 되나요?힌트: "방어된다"와 "괜찮다"는 다르다 함정

전부 한 칸으로 몰린다. spread를 거쳐도 입력이 같으면 출력도 같으므로 소용이 없다.

Java 7이라면 리스트 하나에 노드 100만 개가 매달린다. get/put이 O(n)이라 사실상 서비스 불능이고, 이것이 해시 플러딩 DoS가 노린 지점이다.

Java 8 이상이라면 8개를 넘는 순간 그 칸이 트리화되어 O(log n)으로 방어된다. 다만 조건이 하나 붙는다는 것까지 말해야 정확하다 — 트리 안에서 순서를 정할 수 있어야 하고, hash가 전부 같은 상황에서는 key가 Comparable인지에 달려 있다(13절). String처럼 Comparable이면 온전히 O(log n)이 보장된다.

그리고 결론은 "방어된다"이지 "괜찮다"가 아니다. 정상 O(1)로 돌아오지는 않으므로 근본 해법은 hashCode 품질이다. 외부 입력이 그대로 Map의 key가 되는 경로라면 key 개수 상한을 두는 것도 함께 검토한다.

리사이징 도중 다른 스레드가 접근하면 무슨 일이 생기나요?힌트: "Java 8이라 괜찮다"는 오답이다 시니어 변별

HashMap은 동기화가 전혀 없으므로 동작이 정의되지 않는다.

Java 7에서는 head insert 방식 탓에 동시 리사이징이 리스트에 순환 고리를 만들어, get이 null을 영영 만나지 못하고 무한 루프에 빠지는 장애가 있었다(7절). CPU가 100%에 고정된 채 응답이 멎는 증상이다.

Java 8에서 tail insert로 바뀌며 그 형태는 사라졌지만, put 유실과 size 불일치는 여전히 일어난다. 두 스레드가 같은 칸에 동시에 tail insert하면 한쪽 노드가 통째로 사라질 수 있고, size는 그냥 ++이라 갱신이 겹치면 실제 원소 수와 어긋난다.

핵심은 "Java 8이라 괜찮다"가 아니라 규약 위반이므로 어떤 버전에서도 동시 사용 자체가 버그라는 것이다. 동시 접근이 있으면 ConcurrentHashMap을 쓴다.

한 마디 덧붙이면 좋다. "어쩌다 한 번의 동시 쓰기쯤은 괜찮겠지"라는 타협이 가장 나쁘다. 평상시 트래픽에서는 겹칠 확률이 낮아 몇 달간 멀쩡하다가, 부하가 몰리는 날에만 재현되는 최악의 버그가 된다.

load factor 0.75는 왜 그 값인가요? 바꿔도 되나요?힌트: 바꾸면 8이라는 숫자의 전제가 흔들린다

공간과 시간의 절충점이다. 낮추면 칸이 널널해 충돌이 줄지만 빈 칸이 많아 메모리를 낭비하고 확장이 잦아진다. 높이면 메모리 효율은 좋아지지만 칸당 평균 원소 수가 올라가 리스트 순회가 길어진다.

바꿀 수는 있지만 실무에서 바꿀 일은 거의 없다. 조정할 것이 있다면 load factor가 아니라 초기 용량 쪽이 답인 경우가 대부분이다 — 리사이징 횟수를 줄이는 쪽이 실익이 훨씬 크기 때문이다(10절).

가산점 0.75를 함부로 바꾸면 안 되는 이유가 하나 더 있다. 트리화 임계값 8이 load factor 0.75를 전제로 계산된 값이라는 점이다(12절). load factor를 크게 올리면 칸당 평균 원소 수 λ가 올라가 8개가 쌓일 확률도 함께 올라가고, "8 = 비정상 신호"라는 전제가 흔들려 정상 상황에서도 트리화가 일어나기 시작한다.

HashMap 순회 순서는 왜 보장되지 않고, 순서가 필요하면 뭘 쓰나요?힌트: 리사이징 한 번이면 순서가 통째로 바뀐다

순회는 배열을 0번 칸부터 훑는 방식이고, 각 원소의 저장 위치는 hashCode와 현재 용량의 함수다. 따라서 순회 순서는 우리가 넣은 순서와 아무 관계가 없고, 리사이징 한 번이면 순서가 통째로 바뀐다(9절에서 본 대로 통계적으로 절반이 다른 칸으로 이사하기 때문이다).

순서가 필요하면 용도에 맞는 구현을 쓴다. 삽입 순서가 필요하면 LinkedHashMap(각 노드를 이중 연결 리스트로도 꿰어 둔다), 정렬 순서가 필요하면 TreeMap(전체가 레드-블랙 트리, 조회 O(log n))이다.

실무 사례를 곁들이면 좋다. "HashMap 순회 결과를 그대로 비교하는 테스트"가 JDK 버전이나 데이터 양이 바뀌면 갑자기 깨진다. 순서가 보장되지 않는데 우연히 맞아 왔을 뿐인 테스트다. 검증할 때는 순서에 의존하지 않는 비교를 쓰거나 정렬한 뒤 비교해야 한다.

spread에서 왜 하필 XOR인가요? OR나 AND로 섞으면 안 되나요?힌트: 정보를 삼키지 않는 연산이 무엇인가 가산점

섞는 연산에 필요한 성질은 "한쪽 비트가 바뀌면 결과 비트도 반드시 바뀐다"는 것이다. XOR은 이 성질을 만족한다 — 다른 쪽 비트가 0이든 1이든, 내 비트를 뒤집으면 결과가 뒤집힌다.

AND / OR — 정보를 삼킨다

  • x & 0은 x가 무엇이든 0. 상대가 0이면 내 정보가 사라진다
  • x | 1은 x가 무엇이든 1. 상대가 1이면 내 정보가 사라진다
  • 비트를 섞을수록 0 쪽이나 1 쪽으로 쏠려 분산이 오히려 나빠진다

XOR — 정보를 보존하며 섞는다

  • x ^ 0 = x, x ^ 1 = ~x — 어느 쪽이든 x의 변화가 결과에 그대로 전달
  • 0과 1의 분포가 치우치지 않는다
  • 비용은 1사이클. 시프트 하나와 XOR 하나가 전부다

"왜 16칸이냐"도 같은 맥락이다. 32비트를 절반으로 접는 값이라 상위 절반 전체의 정보가 하위 절반에 한 번씩 겹쳐진다. 더 정교한 해시 함수를 쓸 수도 있지만, HashMap의 선택은 "완벽한 해시가 아니라 값싼 보정"이다 — 근본적인 분산 품질은 여전히 hashCode 구현의 책임이다(4절).

트리화 임계는 8인데 해제는 왜 6인가요? 7이면 안 되나요?힌트: 온도 조절기

경계에서의 진동(thrashing)을 막기 위해서다. 임계값이 8 하나뿐이라면 노드 수가 7과 8 사이를 오갈 때마다 트리화와 해제라는 비싼 작업이 매번 반복된다. 해제를 7로 두어도 마찬가지다 — 8에서 트리, 7에서 리스트라 여전히 한 칸 왕복으로 뒤집힌다.

6으로 두면 왕복하려면 2칸을 움직여야 하므로, 7 근처에서 넣었다 뺐다 하는 정도로는 자료구조가 바뀌지 않는다. 이렇게 켜는 기준과 끄는 기준을 벌려 놓는 기법을 히스테리시스(hysteresis)라 하고, 온도 조절기가 설정 온도 정확히에서 껐다 켰다 하지 않는 것과 같은 발상이다.

이 이름을 아는 것 자체가 가산점이 된다. 같은 패턴이 인프라 전반에 반복되기 때문이다 — 서킷 브레이커의 open/close 임계, 오토스케일링의 scale-out/scale-in 임계, 알람의 발생/해제 임계가 모두 같은 이유로 벌어져 있다.

테이블이 64 미만일 때 트리화 대신 리사이징을 하는 이유는요?힌트: 같은 증상, 다른 병 핵심

원인 진단이 다르기 때문이다. 테이블이 작을 때(16, 32) 한 칸에 8개가 몰리는 것은 hashCode가 나빠서가 아니라 칸이 부족해서일 가능성이 높다. 칸이 16개뿐인데 원소가 12개면 해시가 아무리 좋아도 어딘가는 몰린다.

이 경우 올바른 처방은 트리화가 아니라 칸을 늘리는 것이다. 트리 노드는 일반 노드보다 대략 두 배 무겁고, 리사이징으로 흩어지면 문제가 자연히 해소된다.

그리고 이 조건이 진단 도구가 된다는 점이 핵심이다. 리사이징으로 칸을 넉넉히 늘렸는데도(64 이상) 여전히 한 칸에 8개가 쌓인다면, 그때야말로 "진짜 나쁜 해시"라는 진단이 선다. 8은 "비정상 판정선", 6은 "진동 방지", 64는 "오진 방지"다.

이미 트리가 된 버킷에서 리사이징이 일어나면 트리는 어떻게 되나요?힌트: 리스트와 같은 규칙으로 쪼갠다 시니어 변별

리스트와 똑같이 hash & oldCap으로 lo / hi 두 그룹으로 쪼갠다. 트리라고 예외가 아니다 — 재배치 규칙은 자료구조와 무관하게 "새로 보게 된 비트 하나"만 보기 때문이다(9절).

다른 점은 쪼갠 뒤의 판정이다. 쪼개진 쪽의 노드 수가 6 이하로 줄면 트리를 유지할 이유가 없으므로 리스트로 되돌린다(untreeify). 8을 넘어 트리가 됐던 버킷이라도, 확장으로 반씩 갈리면 자연히 리스트로 돌아가는 경우가 많다.

여기서 두 방어선의 관계가 드러난다. 트리화는 영구적인 승격이 아니라 임시 방어이고, 리사이징이 근본 원인(칸 부족)을 해소하면 스스로 물러난다. "트리가 됐다 = 영원히 트리다"라고 답하면 여기서 갈린다.

new HashMap<>(100_000)에 10만 건을 넣으면 리사이징이 안 일어나겠죠?힌트: 생성자 인자의 단위가 무엇인가 함정

일어난다. 생성자 인자는 "담을 원소 수"가 아니라 용량(배열 길이)이고, 여기에 load factor가 다시 곱해지기 때문이다.

100,000 을 넘기면 용량은 2의 거듭제곱으로 올림 131,072 threshold = 131,072 x 0.75 = 98,304 10만 건 > 98,304 → 리사이징 1회 발생 (int)(100,000 / 0.75f) + 1 = 133,334 를 넘기면 용량은 2의 거듭제곱으로 올림 262,144 threshold = 262,144 x 0.75 = 196,608 10만 건 < 196,608 → 리사이징 0회

그래서 예상 원소 수를 0.75로 나눈 값을 넘겨야 한다. Java 19 이상이면 같은 계산을 대신 해주는 HashMap.newHashMap(int numMappings)가 있다. 트레이드오프도 같이 말하면 좋다 — 리사이징을 없앤 대가로 배열을 더 크게 잡아 메모리를 더 쓴다.

재배치에서 절반은 제자리라면, 리사이징 비용도 절반인가요?힌트: 옮기지 않아도 만져는 봐야 한다 함정

아니다. O(n)은 그대로 남는다. "절반은 이사하지 않는다"는 옮기는 비용에 관한 이야기이고, 어느 쪽인지 판정하려면 모든 노드를 한 번씩은 만져야 한다. 각 칸의 리스트를 끝까지 순회하며 hash & oldCap을 계산해 lo / hi 두 줄로 나눠 꿰는 작업 자체가 전체 노드 수에 비례한다.

Java 8의 개선으로 사라진 것은 따로 있다. ① 해시 재계산이 필요 없고, ② 노드를 하나씩 새 위치에 삽입할 필요 없이 lo/hi 두 리스트를 통째로 걸며, ③ 삽입 순서가 뒤집히지 않아 Java 7식 순환 고리가 생기지 않는다.

정리하면 "값싸졌다"이지 "공짜가 됐다"가 아니다. 이 구분을 하면 10절의 초기 용량 최적화가 여전히 유효한 이유가 자연히 설명된다.

원소를 전부 remove하면 배열도 다시 줄어드나요?힌트: HashMap에는 축소가 없다

줄어들지 않는다. HashMap에는 축소(shrink) 로직이 아예 없다. 한 번 커진 table 배열은 그 크기를 유지하고, clear()를 호출해도 각 칸을 null로 비울 뿐 배열 길이는 그대로다.

이유는 리사이징과 대칭이다. 줄이려면 다시 O(n) 재배치가 필요한데, 줄인 직후 다시 늘어나면 그 비용을 또 낸다. 게다가 "언제 줄일지"의 기준을 잘못 잡으면 확장과 축소가 번갈아 일어나는 진동이 생긴다(6/8 히스테리시스와 같은 문제다).

실무 함의가 있다. 일시적으로 크게 부풀었다 비워지는 캐시성 Map을 오래 살려 두면, 원소가 0이어도 큰 빈 배열이 계속 힙을 차지한다. 이런 자리는 Map을 새로 만들어 갈아 끼우는 것이 정답이고, 그래서 캐시는 clear()보다 참조 교체 방식으로 비우는 구현을 자주 본다.

HashSet은 HashMap과 어떤 관계인가요?힌트: 새로 만든 자료구조가 아니다

HashSet의 내부는 HashMap 하나가 전부다. 원소를 key로 넣고, value 자리에는 의미 없는 공유 더미 객체 하나를 넣는다. add는 map.put(e, PRESENT), contains는 map.containsKey(e)다.

그래서 이 문서의 내용이 HashSet에 그대로 적용된다. 버킷 인덱싱, 체이닝, 0.75 리사이징, 8/64 트리화, 순회 순서 미보장, 가변 객체를 넣으면 못 찾는 문제까지 전부 같다.

면접에서 "Set에 넣은 객체의 필드를 바꾸면 contains가 false를 반환한다"는 사례로 이어 말하면, 두 자료구조를 따로 외운 것이 아니라 같은 메커니즘으로 이해했다는 신호가 된다.

한 줄 요약
HashMap은 "spread로 상위 비트를 섞은 hash를 2^k 배열에 (n-1) &로 인덱싱하고, 충돌은 리스트로 이어 붙이며, 0.75를 넘으면 2배 리사이징(hash & oldCap 한 번으로 lo/hi 분리), 한 칸이 8을 넘고 테이블이 64 이상이면 그 칸만 레드-블랙 트리"라는 한 문장으로 요약된다 — 그리고 이 내부를 아는 사람은 초기 용량 지정 · 불변 key · 동시 접근 금지라는 실무 습관이 왜 필요한지를 관행이 아니라 원리로 설명할 수 있다.
