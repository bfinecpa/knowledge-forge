equals()와 hashCode() 동시 재정의 — "분명 넣었는데 못 찾는" 버그의 뿌리
해시 컬렉션의 조회는 2단계다 — hashCode로 칸을 고르고, 그 칸 안에서만 equals로 대조한다 · 1단계가 어긋나면 equals는 단 한 번도 호출되지 않는다

면접 질문: "equals()와 hashCode()를 함께 재정의해야 하는 이유는 무엇인가요?"

핵심 관전 포인트 — HashMap/HashSet은 값을 찾을 때 두 단계를 밟는다 — 먼저 hashCode()로 버킷(저장 칸)을 하나 고르고, 그 칸 안에 든 후보들만 equals()로 대조한다. 1단계에서 다른 칸을 열면 2단계는 아예 실행되지 않으므로, equals()만 재정의하고 hashCode()를 그대로 두면 "논리적으로 같은 객체"가 서로 다른 칸으로 흩어져 영영 못 찾는다. 여기서 규약이 도출된다 — equals()가 true인 두 객체는 반드시 같은 hashCode()를 반환해야 한다. 이 규약 위반은 컴파일 에러도 예외도 내지 않고 조용히 틀리기 때문에, 중복 처리 실패나 캐시 미스 폭증처럼 원인과 동떨어진 증상으로만 드러난다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "equals()와 hashCode()를 함께 재정의해야 하는 이유는 무엇인가요?"

출제 의도 — HashMap/Set에 넣은 객체가 "분명 넣었는데 못 찾는" 버그는 재현이 어렵고 증상이 엉뚱한 곳(중복 처리 실패, 캐시 미스 폭증)에서 나타난다. 이 규약을 모르면 그 버그를 몇 시간씩 엉뚱한 데서 찾는다. AI가 생성한 엔티티/VO 코드에서 이 실수를 리뷰로 잡아낼 수 있는지도 본다.

그래서 이 질문은 "규약을 외웠는가"를 묻는 게 아니다. "왜 그 규약이 필요한지를 조회 절차로 설명할 수 있는가"를 묻는다. 결론("hashCode도 같이 재정의해라")만 아는 사람과 절차의 어느 지점이 무너지는지 아는 사람은 꼬리질문 한 번에 갈린다.

이 질문의 정체 — "규약을 아느냐"가 아니라 "규약이 왜 그 모양인지 아느냐"다.
규약은 한 방향으로만 강제된다. 왜 한쪽만인지를 설명하려면 조회가 2단계라는 사실을 반드시 거쳐야 한다 — 그래서 이 하나로 암기한 사람과 이해한 사람이 분리된다.

이렇게 답하면 반쪽이다

  • "규약이라서요 / 같이 재정의해야 한다고 배웠습니다" — 근거가 없다. 이어지는 "왜요?"에 바로 막힌다.
  • "hashCode가 다르면 다른 객체로 인식돼서요" — 말은 맞는데 메커니즘이 없다. 어디서 어떻게 인식이 갈리는지(= 버킷 선택)를 못 대면 equals만 재정의해도 되지 않냐는 반문에 답할 수 없다.
  • "equals 비교가 실패합니다" — 틀린 진단이다. equals는 정확하다. 호출되지 않았을 뿐이다. 이 구분이 이 문서의 핵심이다.
  • "hashCode가 같으면 같은 객체입니다" — 규약을 거꾸로 알고 있다. hashCode가 같아도 equals는 다를 수 있고, 그게 충돌이다.
  • "Lombok 붙이면 됩니다" — 쌍은 보장되지만 어떤 필드를 기준으로 할지·그 필드가 가변인지는 그대로 남는다. 엔티티에서 사고가 난다.
  • 규약만 말하고 가변 필드 이야기가 없음 — 규약을 지켜도 무너지는 경우(유령 항목)를 모르는 것이다. 실무 경험을 묻는 자리에서 여기가 갈린다.

이 문서가 채워 주는 것

  • 조회의 2단계를 버킷 배열 그림으로 — "1단계가 틀리면 2단계는 실행조차 안 된다"는 문장의 근거.
  • Object 기본 구현의 정체 — this == obj와 식별 해시, 그리고 "주소를 그대로 쓴다"는 흔한 오해의 교정.
  • 규약이 비대칭인 이유 — 같은 칸에 모이는 건 2단계가 걸러 주지만, 칸이 갈리는 건 복구 불가능하다.
  • 유령 항목 타임라인 — 규약을 지켜도 넣은 뒤 필드를 바꾸면 무슨 일이 벌어지는지 t0~t2로.
  • JPA 엔티티의 두 함정 — null id의 두 경로와 프록시 때문에 getClass()를 못 쓰는 이유.
  • 왜 테스트가 통과하는가 — this == o 지름길과 "값은 같고 참조는 다른 객체"가 만들어지는 순간들.
  • 리뷰 체크 3종 — AI 생성 코드에서 기계적으로 확인할 지점.

이 문서를 관통하는 한 문장

동등성의 정의를 바꿨으면 칸 배정 기준도 같이 바꿔야 한다

equals()를 재정의한다는 것은 "이 타입의 같음은 값 기준"이라고 선언하는 일이다. 그런데 hashCode()를 그대로 두면 칸 배정은 여전히 "객체마다 다르다" 기준으로 돌아간다. 두 기준이 같은 필드를 보도록 맞춰야 조회가 성립한다 — 이것이 규약의 실체이고, 나머지는 전부 여기서 파생된다.

0-1. 답변 흐름 한 장 — 이 순서를 지키면 질문이 끝난다

1. 출발점 — Object가 기본으로 주는 두 메서드

결론("hashCode를 같이 재정의해라")부터 외우면 응용이 안 된다. HashMap이 값을 찾는 절차를 먼저 보고, 그 절차의 어느 지점이 무너지는지를 짚는 순서로 간다. 그 전에 아무것도 안 썼을 때 무엇이 주어져 있는지부터 확인해야 한다.

모든 클래스는 Object를 상속하므로, 아무것도 안 써도 equals()와 hashCode()를 이미 갖고 있다. 문제는 그 기본 구현이 무엇을 기준으로 삼느냐다.

Object.equals() — 참조 동일성
return (this == obj);

기본 구현은 딱 이 한 줄이다. 즉 "메모리에서 같은 객체를 가리키는가"만 본다. 이것을 참조 동일성(reference identity)이라 부른다. 필드 값이 아무리 똑같아도 new를 두 번 했으면 다른 객체이므로 false다.

Object.hashCode() — 식별 해시
객체마다 고유하게 부여되는 정수 하나

JVM이 객체마다 한 번 만들어 객체 헤더에 기록해 두는 이 값을 식별 해시(identity hash)라고 한다. 값을 어떻게 만드는지는 JVM 구현에 달렸지만, 우리에게 중요한 성질은 하나뿐이다.

이 문서 전체 문제의 출발점이 되는 한 문장

필드 값이 완전히 같아도, 서로 다른 객체면 hashCode도 서로 다르다

흔한 오해 하나를 여기서 교정한다 — "hashCode는 객체의 메모리 주소다"라는 설명은 정확하지 않다. 값을 만드는 방식은 JVM 구현에 달려 있고(난수·카운터 등), GC가 객체를 옮겨도 값은 변하지 않는다. 우리가 기댈 수 있는 성질은 위 한 줄뿐이다.

확인값이 같은 두 객체의 기본 hashCode
Money a = new Money("KRW", 1000);
Money b = new Money("KRW", 1000);

a.hashCode();  // 예: 1173230247
b.hashCode();  // 예: 856419764   -- 값이 같아도 다른 객체라 다른 수가 나온다

2. 조회의 2단계 — 칸을 고르고, 칸 안에서 대조한다

HashMap의 본체는 배열 하나다. 각 칸을 버킷(bucket, 양동이)이라 부른다. 값을 찾을 때 배열 전체를 훑으면 O(n)이라 아무 이득이 없으므로, HashMap은 "이 key라면 몇 번 칸에 있을 것"을 계산으로 알아내고 그 칸 하나만 열어본다. 이 계산에 쓰는 것이 hashCode()다.

그런데 hashCode는 32비트 정수라 값의 범위가 배열 길이보다 훨씬 넓다. 그래서 배열 길이로 접어 넣는다(길이 16이면 0~15 사이로). 그 결과 서로 다른 key가 같은 칸을 배정받는 일이 반드시 생긴다. 이것을 해시 충돌(collision)이라 한다. 그래서 한 칸에는 여러 후보가 매달릴 수 있고, 그중 진짜를 골라내는 마지막 확인이 equals()다.

두 단계, 두 기준 — 이 대응표가 머리에 있어야 한다

1단계 · 칸 고르기
담당: hashCode()
어디를 열어볼지를 정한다. 틀리면 2단계가 실행되지 않는다. → 복구 불가
2단계 · 후보 대조
담당: equals()
연 칸 안에서 진짜를 고른다. 후보가 많아지면 느려질 뿐 틀리지는 않는다. → 성능 문제

1단계의 실수는 정확성 사고, 2단계의 부담은 성능 문제 — 규약이 왜 한 방향으로만 강제되는지가 이 한 줄에 이미 들어 있다.

가산점 한 줄 — "접는다"는 게 정확히 무엇인가 자바 8 이후 HashMap은 hashCode를 그대로 쓰지 않는다. h ^ (h >>> 16)으로 상위 16비트를 하위로 섞어 내린 뒤(spread) (n-1) & hash로 인덱스를 구한다. 배열 길이가 2의 거듭제곱이라 하위 비트만 인덱스에 쓰이는데, 상위 비트만 다른 해시들이 전부 같은 칸으로 몰리는 것을 완화하려는 장치다. "hashCode를 대충 만들어도 HashMap이 어느 정도 방어해 준다"는 사실은 알아 두되, equals와 필드 집합이 어긋난 것은 이 장치로 절대 구제되지 않는다.

3. 무너지는 지점은 비교가 아니라 칸 선택이다

이제 1절의 사실을 2절의 절차에 대입해 보자. equals()만 재정의한 Money 두 개, new Money("KRW", 1000)을 각각 만들어 하나는 Set에 넣고 다른 하나로 contains를 부른다.

진단을 틀리게 만드는 문장 이 상황에서 "equals가 잘못돼서 false가 났다"고 말하면 틀린 진단이다. equals는 정확하다. 호출되지 않았을 뿐이다. 실제 디버깅에서 equals()에 브레이크포인트를 걸어 두고 "왜 안 걸리지?" 하며 몇 시간을 보내는 일이 정확히 이 지점에서 벌어진다. 브레이크포인트가 안 걸린다는 사실 자체가 이미 답이다.

4. 규약 — 왜 한쪽 방향만 강제되는가

Object 클래스의 Javadoc이 명시하는 계약(contract)은 이것이다.

① 강제된다 — 지키지 않으면 사고
a.equals(b) == true  ⟹  a.hashCode() == b.hashCode()

equals가 true인 두 객체는 반드시 같은 hashCode를 반환해야 한다. 어기면 칸부터 갈리므로 복구할 방법이 없다. 2단계는 실행조차 되지 않는다.

② 강제되지 않는다 — 어겨도 무해
a.hashCode() == b.hashCode()  ⟹̸  a.equals(b)

hashCode가 같아도 equals는 다를 수 있다. 같은 hashCode는 "같은 칸에 모인다"는 뜻일 뿐이고, 2단계에서 equals가 걸러 준다. 정확성에 아무 해가 없고 성능만 나빠진다.

4-1. 비유 — 도서관의 서가 번호와 책 제목

hashCode는 도서관의 서가 번호, equals는 책 제목 대조다. 이 비유 하나로 비대칭이 직관적으로 설명된다.

규약 인출 카드 — 이 세 줄만 기억한다

필수 방향
equals가 true → hashCode 동일. 어기면 정확성 사고.
자유 방향
hashCode 동일 → equals는 자유. 그게 충돌이고 성능 문제일 뿐.
이유 한 줄
칸이 갈리면 2단계가 없고, 칸이 겹치면 2단계가 걸러 준다.

5. 코드로 확인 — before / after

5-1. equals만 재정의한 클래스

BEFOREequals만 재정의 — hashCode 누락 (AI 생성 코드에서 흔한 형태)
public class Money {
    private final String currency;
    private final long amount;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Money)) return false;
        Money m = (Money) o;
        return amount == m.amount
            && currency.equals(m.currency);
    }
    // hashCode() 재정의 없음
    // -> Object의 identity hash를 그대로 쓴다규약 위반
}

Set<Money> paid = new HashSet<>();
paid.add(new Money("KRW", 1000));
paid.contains(new Money("KRW", 1000));
// false — 다른 칸을 열어봤다
상태 요약"값이 같으면 같다"는 equals의 선언과 칸 배정 기준이 어긋난 상태. equals는 정확하지만 호출되지 않는다.
AFTERequals가 보는 필드와 hashCode가 쓰는 필드를 정확히 일치시킨다
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Money)) return false;
    Money m = (Money) o;

8. JPA 엔티티의 두 함정 — null id와 프록시 시니어 변별

엔티티는 일반 값 객체와 사정이 다르다. 함정이 둘 겹친다. 이 둘을 구분해서 말할 수 있으면 "실제로 JPA를 써 본 사람"으로 읽힌다.

8-1. 함정 1 — id는 영속화 전까지 null이다

@GeneratedValue로 id를 받는 엔티티는 persist 전에는 id가 없다. 여기서 "id로 equals/hashCode를 만들면 된다"는 단순한 답이 두 방향으로 깨진다.

BEFOREid만으로 equals/hashCode — 영속화 전후로 정체성이 흔들린다
@Entity
public class Order {
    @Id @GeneratedValue private Long id;   // persist 전에는 null

    @Override public boolean equals(Object o) { /* id끼리 비교 */ }
    @Override public int hashCode() { return Objects.hash(id); }두 방향으로 깨진다
}

8-2. 대응은 두 갈래고, 둘 다 트레이드오프가 있다

① 비즈니스 키(자연 키) — 가장 깨끗한 답

  • 주문번호·사업자등록번호·이메일처럼 DB가 만들어 주는 것이 아니라 도메인이 태어날 때부터 갖고 있고 이후 바뀌지 않는 값
  • 영속화 전후로 값이 변하지 않으므로 경로 A·B가 모두 사라진다
  • 대가: 그런 키가 없는 엔티티도 많고, "이후 바뀌지 않는다"는 보장을 도메인이 실제로 지켜 줘야 한다

② hashCode 고정값 + equals는 id 있을 때만

  • 마땅한 비즈니스 키가 없을 때 쓰는 절충
  • hashCode가 항상 같은 값이면 같은 타입 엔티티가 전부 한 칸에 몰려 해시 분산은 포기하게 된다
  • 그러나 값이 변하지 않으므로 규약 위반은 없다 — 4절의 "hashCode가 겹쳐도 정확성은 유지된다"는 성질을 의도적으로 활용하는 설계다
  • 컬렉션에 담기는 엔티티 개수가 적다면 실무에서 감당할 만한 절충
AFTER생성 시점에 정해지고 이후 불변인 비즈니스 키를 쓴다
@Entity
public class Order {
    @Id @GeneratedValue private Long id;                // 대리 키(surrogate key) — 정체성 판단에는 쓰지 않는다

    @Column(unique = true, updatable = false)
    private String orderNo;                              // 비즈니스 키: 주문 생성 시 부여, 이후 불변이 필드가 정체성

    @Override
    public boolean equals(Object o) {
        // getClass() 대신 instanceof: 아래 '함정 2'(프록시) 때문이다
        if (!(o instanceof Order other)) return false;
        return orderNo != null && orderNo.equals(other.orderNo);
    }

    @Override
    public int hashCode() {
        // 영속화 전후로 절대 변하지 않는 값만 쓴다. id를 넣으면 안 되는 이유가 경로 B.
        return Objects.hash(orderNo);
    }
}

8-3. 함정 2 — 지연 로딩 프록시

JPA는 지연 로딩을 위해 엔티티를 상속한 프록시(proxy) 클래스를 만들어 대신 넘겨준다. 그래서 getClass()로 타입을 비교하면 실제 엔티티와 프록시가 다른 클래스로 판정돼 실패한다.

전형적인 리뷰 지적 대상 모든 필드를 넣는 Lombok @EqualsAndHashCode나 IDE 자동 생성을 엔티티에 그대로 붙이는 것. 연관 관계 필드까지 포함되면 equals 한 번에 지연 로딩 쿼리가 줄줄이 나가고, updatedAt 같은 가변 필드가 섞이면 컬렉션 안에서 유령 항목이 생긴다. 특히 양방향 연관에서는 equals가 서로를 호출하며 무한 재귀로 이어지기도 한다.

  • 불변: 안 된다

10. equals 5대 규약과 대칭성이 깨지는 자리

지금까지는 equals와 hashCode의 관계만 봤다. equals 자체에도 지켜야 할 일반 규약이 다섯 가지 있다.

Object.equals의 다섯 가지 규약 — 실무에서 깨지는 것은 사실상 하나뿐이다
규약내용깨지는 자리
반사성x.equals(x)는 항상 true거의 깨지지 않는다 (일부러 이상하게 짜야 한다)
대칭성x.equals(y)가 true면 y.equals(x)도 true상속 — 부모와 자식이 서로 다른 필드를 볼 때. 실무에서 가장 자주 깨진다.

12. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 각 답의 마지막에 있는 "정리 문장"은 면접에서 그대로 말할 수 있는 형태로 다듬어 두었다.

hashCode만 같고 equals가 다르면 어떻게 되나요?힌트: 이건 버그가 아니라 이름이 따로 붙어 있는 정상 현상이다 핵심

규약 위반이 아니다. 그것이 바로 해시 충돌(collision)이고, 충돌은 오류가 아니라 유한한 배열에 사실상 무한한 값을 밀어 넣는 이상 반드시 생기는 정상 현상이다.

같은 칸에 여러 객체가 모이면 2단계에서 equals 비교 횟수가 늘어난다. 즉 동작은 정확하고 성능만 저하된다. 극단적으로 모든 객체가 hashCode()에서 상수를 반환하면 전부 한 칸에 몰려 HashMap이 사실상 연결 리스트가 되고, 조회가 O(1)에서 O(n)으로 나빠진다.

가산점 포인트 — 최악조차 방어된다 자바 8부터 HashMap은 한 버킷에 항목이 일정 수 이상 쌓이면 그 버킷만 연결 리스트에서 레드-블랙 트리로 바꿔(트리화) 최악을 O(log n)으로 완화한다. (OpenJDK 구현 기준으로 버킷 항목 8개 이상 + 테이블 크기 64 이상이 조건이고, 줄어들면 다시 리스트로 되돌린다.) "정확성은 유지되고 성능만 나빠지며, 그 최악조차 어느 정도는 방어된다"까지 말하면 비대칭 규약의 이유가 완성된다.

정리 문장 — "hashCode가 겹치는 것은 규약 위반이 아니라 충돌이고, 2단계의 equals가 걸러 주므로 정확성은 그대로입니다. 대가는 성능뿐이고, 자바 8 이후엔 버킷 트리화로 최악도 O(log n)으로 막습니다."

반대로 equals는 그대로 두고 hashCode만 재정의하면 어떻게 되나요?힌트: 1단계는 고쳐졌다. 그럼 2단계는? 함정

규약 자체는 깨지지 않는다. equals가 참조 동일성이면 "equals가 true인 두 객체"는 같은 객체뿐이고, 같은 객체는 당연히 같은 hashCode를 낸다. 그래서 형식적으로는 합법이다.

하지만 목적은 하나도 달성되지 않는다. 값이 같은 두 객체는 이제 같은 칸까지는 무사히 도착한다. 그런데 2단계에서 equals가 여전히 this == o로 비교하므로 "같은 칸에 있는 남"으로 판정되고 결과는 여전히 false다. 게다가 값이 같은 객체들이 같은 칸에 계속 쌓이기만 해서 충돌만 늘어난다.

1단계만 고치면 "만나기는 하는데 서로를 못 알아본다"

정리 문장 — "규약 위반은 아니지만 동작은 그대로 실패합니다. 칸은 맞게 찾아가고 equals에서 떨어지기 때문입니다. 두 메서드는 같은 필드 집합을 보는 한 쌍이라야 의미가 생깁니다."

가변 필드로 hashCode를 만들면 무슨 일이 생기나요?힌트: 컬렉션은 필드가 바뀌었다는 사실을 통지받는 장치가 없다 핵심

Set에 넣은 뒤 그 필드를 수정하면 hashCode는 바뀌지만 객체는 옛 해시값 기준 칸에 그대로 남는다. 컬렉션은 필드 변경을 통지받는 장치가 없기 때문이다. 재해싱을 해 주려면 모든 원소의 모든 필드 변경을 감시해야 하는데, 그건 해시 컬렉션이 지향하는 O(1)과 정면으로 충돌한다.

이후 contains는 새 해시값의 칸을 열어보므로 못 찾고, remove도 같은 이유로 실패한다. 그런데 size()에는 잡히고 순회에는 나온다(순회는 칸 계산 없이 배열을 처음부터 훑기 때문이다) — 찾을 수도 지울 수도 없는 유령 항목이 된다.

가장 기괴한 증상set.contains(m)에 넣었던 그 객체 자신을 넘겨도 false가 나온다. 참조까지 완전히 같은데도 그렇다 — 1단계에서 이미 다른 칸으로 가 버리기 때문이다.

정리 문장 — "해시 컬렉션은 넣는 순간의 hashCode로 자리를 정하고 다시 계산하지 않습니다. 그래서 기준 필드는 불변이거나, 최소한 컬렉션에 담긴 동안 바뀌지 않아야 합니다. record·final 필드로 값 객체를 설계하는 이유 중 하나가 이것입니다."

JPA 엔티티에서는 equals/hashCode를 어떻게 재정의하나요?힌트: 함정이 둘 겹친다 — 하나는 id의 생애주기, 하나는 클래스의 정체 시니어 변별

엔티티는 일반 값 객체와 사정이 다르다. 함정이 둘 겹친다.

함정 1 — id는 영속화 전까지 null이다

@GeneratedValue로 id를 받는 엔티티는 persist 전에는 id가 없다. 그래서 "id로 equals/hashCode를 만들면 된다"는 단순한 답이 두 방향으로 깨진다.

깨지는 경로 A — 저장 전 두 엔티티

  • new Order(), new Order() 둘 다 id = null
  • id가 둘 다 null이라 "같다"고 판정된다. 서로 다른 주문인데.
  • Set에 두 개를 넣으면 하나만 들어간다.

깨지는 경로 B — 넣고 나서 저장

  • t0 id=null → hashCode 기준 칸에 들어감
  • t1 persist → id가 채워지며 hashCode가 바뀐다
  • t2 contains → false. 가변 필드 문제의 특수한 형태다.

id는 "우리가 안 바꾸는 필드"처럼 보이지만, 실제로는 JPA가 저장 시점에 채워 넣는 가변 필드다. 이 한 문장이 경로 B를 설명한다.

대응은 두 갈래, 둘 다 트레이드오프가 있다

① 비즈니스 키(자연 키) — 가장 깨끗한 답

  • 주문번호·사업자등록번호·이메일처럼 DB가 만들어 주는 게 아니라 도메인이 태어날 때부터 갖고 있고 이후 바뀌지 않는 값
  • 영속화 전후로 값이 변하지 않으므로 두 함정이 모두 사라진다
  • 단, 그런 키가 없는 엔티티도 많다

② hashCode 고정값 + equals는 id 있을 때만

  • 마땅한 비즈니스 키가 없을 때의 절충
  • hashCode가 항상 같으면 같은 타입 엔티티가 한 칸에 몰려 해시 분산은 포기
  • 그러나 값이 변하지 않으므로 규약 위반은 없다 — 앞의 "충돌은 정확성에 무해" 성질을 의도적으로 활용하는 설계
  • 컬렉션에 담기는 엔티티 수가 적다면 감당할 만하다

함정 2 — 지연 로딩 프록시

JPA는 지연 로딩을 위해 엔티티를 상속한 프록시 클래스를 만들어 대신 넘겨준다. 그래서 getClass()로 타입을 비교하면 실제 엔티티와 프록시가 다른 클래스로 판정돼 실패한다. instanceof는 상속 관계를 인정하므로 안전하다. 또한 프록시 안에서는 필드에 직접 접근하면 아직 로딩되지 않은 빈 값이 나올 수 있으므로 getter를 거쳐야 프록시가 실제 데이터를 채워 넣는다.

전형적인 리뷰 지적 대상모든 필드를 넣는 Lombok @EqualsAndHashCode나 IDE 자동 생성을 엔티티에 그대로 붙이는 것. 연관 관계 필드까지 포함되면 equals 한 번에 지연 로딩 쿼리가 줄줄이 나가고, updatedAt 같은 가변 필드가 섞이면 컬렉션 안에서 유령 항목이 생긴다.

정리 문장 — "엔티티의 id는 JPA가 저장 시점에 채우는 가변 필드라, id 기반 equals/hashCode는 저장 전 충돌(경로 A)과 저장 후 이동(경로 B)으로 깨집니다. 불변 비즈니스 키가 있으면 그것을 쓰고, 없으면 hashCode를 고정값으로 두고 equals만 id로 하는 절충을 택합니다. 그리고 프록시 때문에 getClass()가 아니라 instanceof를 씁니다."

record나 Lombok을 쓰면 신경 안 써도 되나요?힌트: 언어가 강제해 주는 조건은 "쌍"과 "불변" 둘인데, 하나는 도구가 대신 못 해 준다

record는 모든 컴포넌트를 기준으로 equals와 hashCode를 항상 쌍으로 자동 생성하고 필드가 전부 final이므로, 값 객체에는 가장 안전한 선택이다. "쌍으로 만드는 것"과 "불변인 것" 두 조건을 언어가 강제해 준다.

Lombok @EqualsAndHashCode도 쌍은 보장한다. 다만 어떤 필드를 기준으로 삼을지는 여전히 사람의 판단이고(기본값은 모든 필드), 그 판단이 틀리면 위 엔티티 함정으로 그대로 들어간다. @Data는 여기에 setter까지 함께 열어 주므로 가변 필드 문제까지 얹힌다.

정리 문장 — "도구는 '쌍으로 만드는 것'까지만 대신해 줍니다. 어떤 필드를 정체성으로 볼 것인가와 그 필드가 불변인가는 여전히 설계 판단이고, 그 둘이 틀리면 도구를 써도 같은 버그가 납니다."

equals 재정의 시 지켜야 할 일반 규약은 무엇인가요?힌트: 다섯 가지인데, 실무에서 깨지는 건 거의 하나뿐이다

다섯 가지다. 반사성(자기 자신과는 항상 같다), 대칭성(a가 b와 같으면 b도 a와 같다), 추이성(a=b이고 b=c면 a=c), 일관성(필드가 안 변하면 몇 번을 호출해도 결과가 같다), null과는 항상 false.

실무에서 가장 자주 깨지는 것은 대칭성이고, 깨지는 자리는 거의 항상 상속이다. 부모 Point는 좌표만 보고 자식 ColorPoint는 좌표와 색을 본다고 하면 p.equals(cp)는 true, cp.equals(p)는 false가 된다. 컬렉션은 어느 방향으로 비교할지 보장하지 않으므로, 이 상태에서는 contains의 결과가 원소 순서에 따라 달라지는 예측 불가능한 동작이 된다.

가산점 포인트 — instanceof vs getClass()여기서 그 오래된 트레이드오프가 나온다. getClass()는 대칭성을 지키는 대신 하위 클래스를 영영 같지 않게 만들어 리스코프 치환 원칙과 충돌하고, instanceof는 그 반대다. 값 객체라면 상속 자체를 피하고 클래스를 final로 막는 것이 정석이고, 자바에서 record가 암묵적으로 final인 이유이기도 하다. 다만 JPA 엔티티는 프록시 때문에 getClass()를 쓸 수 없으므로 instanceof 쪽을 택할 수밖에 없다.

정리 문장 — "반사·대칭·추이·일관·null 다섯 가지인데, 실무에서 깨지는 건 상속이 낀 대칭성입니다. 그래서 값 객체는 final(또는 record)로 막는 것이 규약을 지키는 가장 싼 방법입니다."

hashCode()가 항상 0을 반환하도록 만들면 프로그램이 깨지나요?힌트: 깨지는 것과 느려지는 것을 구분하라

깨지지 않는다. 느려질 뿐이다. "equals가 true면 hashCode도 같다"를 가장 게으른 방법으로 만족시킨 것이기 때문이다. 모든 객체가 0번 칸에 몰리므로 HashMap은 사실상 연결 리스트(또는 트리)가 되고 조회가 O(n)/O(log n)으로 떨어지지만, 2단계의 equals가 정확하다면 결과는 항상 맞다.

이 성질은 이론적 호기심이 아니다. 위 JPA 절충안(hashCode 고정값 + equals는 id로)이 정확히 이 성질을 의도적으로 이용한다. "분산을 포기하고 안정성을 산다"는 거래다.

해시 함수의 품질은 정확성 문제가 아니라 성능 문제다

정리 문장 — "hashCode의 품질은 정확성이 아니라 성능을 결정합니다. 상수 반환도 규약은 지키므로 동작은 정확하고 조회만 느려집니다 — 그래서 안정성이 더 중요한 상황에서는 일부러 고정값을 쓰기도 합니다."

hashCode() 값을 DB에 저장하거나 다른 서버로 보내서 식별자로 써도 되나요?힌트: "같은 실행 안에서만"이라는 단서가 규약에 붙어 있다 함정

쓰면 안 된다. 규약이 보장하는 일관성은 "같은 실행(JVM 프로세스) 안에서, 필드가 변하지 않는 동안"까지다. 애플리케이션을 재시작하면 같은 객체라도 다른 값이 나올 수 있고, 이것은 버그가 아니라 명세가 허용하는 범위다. 특히 Object의 식별 해시는 JVM이 실행 시점에 부여하므로 실행마다 달라진다.

일부 예외는 명세로 고정돼 있다. 예를 들어 String.hashCode()는 계산식이 Javadoc에 명시돼 있어 어떤 JVM·어떤 실행에서도 같은 값이 나온다. 하지만 이건 예외이지 일반 규칙이 아니고, 이런 세부에 기대는 코드는 위험하다.

게다가 hashCode는 32비트 정수라 충돌이 흔하다. "해시가 같으니 같은 데이터" 같은 판단은 애초에 성립하지 않는다 — 그 용도라면 UUID 같은 명시적 식별자나 SHA-256 같은 암호학적 해시를 써야 한다.

정리 문장 — "hashCode는 같은 실행 안에서 버킷을 고르기 위한 값이지 영속 식별자가 아닙니다. 재시작하면 값이 바뀔 수 있고 32비트라 충돌도 흔하므로, 저장·전송용 식별에는 UUID나 암호학적 해시를 씁니다."

TreeMap/TreeSet에 넣을 때도 equals/hashCode가 중요한가요?힌트: 정렬 컬렉션은 애초에 hashCode를 호출하지 않는다 시니어 변별

아니다. 정렬 컬렉션은 equals도 hashCode도 쓰지 않는다. TreeMap/TreeSet은 오직 compareTo(또는 생성자에 준 Comparator)의 결과가 0인가로 같음을 판정한다. 그래서 equals/hashCode를 아예 재정의하지 않아도 정렬 컬렉션에서는 잘 동작하고, 반대로 둘을 완벽히 재정의해도 compareTo가 엉망이면 정렬 컬렉션에서는 못 찾는다.

여기서 "compareTo는 equals와 일관되게(consistent with equals) 구현하라"는 권고가 나온다. 강제는 아니지만, 어기면 같은 원소를 담았는데 컬렉션 종류에 따라 크기가 달라지는 상황이 생긴다.

교과서적 사례 — BigDecimalnew BigDecimal("1.0")과 new BigDecimal("1.00")은 equals로는 false(스케일까지 비교)지만 compareTo로는 0(수치만 비교)이다. 그래서 둘을 다 넣으면 HashSet의 크기는 2, TreeSet의 크기는 1이 된다. 같은 데이터, 같은 API, 다른 결과다.

정리 문장 — "해시 컬렉션은 hashCode+equals, 정렬 컬렉션은 compareTo로 동일성을 판정합니다. 그래서 둘 중 하나만 맞춰 놓으면 다른 쪽에서 어긋나고, BigDecimal처럼 equals와 compareTo가 불일치하는 타입에서는 컬렉션 종류에 따라 크기까지 달라집니다."

Objects.hash(...)를 쓰면 되는데 왜 어떤 코드는 31을 곱하고 있나요?힌트: 정확성 문제가 아니다. 그리고 인자가 하나일 때 함정이 하나 더 있다 가산점

Objects.hash(a, b, c)는 가변인자(varargs)라 호출할 때마다 배열을 하나 만들고, 기본형 인자는 박싱한다. 대부분의 코드에서는 무시할 비용이지만, 초당 수백만 번 호출되는 핫패스의 키 객체라면 측정 대상이 된다. 그래서 성능이 중요한 자리에서는 int h = 31 * currency.hashCode() + Long.hashCode(amount);처럼 직접 계산하거나, 불변 객체라면 결과를 필드에 캐싱한다(String이 실제로 그렇게 한다).

인자가 하나일 때의 함정Objects.hash(x)와 x.hashCode()는 다른 값이다. 전자는 내부적으로 배열 해시 계산을 거치기 때문이다. 값 자체는 규약과 무관하지만, "이 필드의 hashCode를 그대로 쓰겠다"는 의도라면 Objects.hashCode(x)(단수형, null 안전)를 써야 헷갈리지 않는다.

정리 문장 — "어떤 함수를 쓰느냐는 성능·가독성 문제일 뿐 정확성 문제가 아닙니다. 규약이 요구하는 건 equals와 같은 필드 집합을 입력으로 쓰는 것 하나뿐이고, Objects.hash는 배열 생성·박싱 비용이 있어 핫패스에서만 대안을 고민합니다."

Kotlin data class를 쓰면 이 문제가 전부 사라지나요?힌트: 대상 필드의 범위와 var 두 가지를 확인하라 시니어 변별

절반만 사라진다. data class는 equals/hashCode/toString/copy를 항상 쌍으로 생성하므로 "한쪽만 재정의" 실수는 구조적으로 불가능하다. 여기까지는 완전한 해결이다.

그런데 두 가지가 남는다.

① 주 생성자 프로퍼티만 대상이다

  • data class User(val id: Long) { val name: String = "" }에서 name은 equals/hashCode에 들어가지 않는다
  • 본문에 선언한 프로퍼티는 조용히 제외된다 — 컴파일 경고도 없다

② var면 여전히 가변이다

  • data class P(var x: Int)는 equals 기준 필드가 바뀔 수 있다
  • Set에 넣고 x를 바꾸면 유령 항목이 그대로 재현된다
  • 해시 키로 쓸 타입은 val만으로 선언해야 한다

덧붙여 JPA 엔티티에 data class를 쓰는 것은 권장되지 않는다. 모든 주 생성자 프로퍼티가 equals에 들어가 연관 관계 지연 로딩을 유발하고, copy()가 엔티티 정체성을 흐리며, 기본적으로 final 클래스라 프록시 생성에도 걸린다(그래서 allopen/noarg 같은 플러그인을 쓴다).

정리 문장 — "data class는 '쌍으로 만드는 것'은 언어가 강제하지만, 대상 필드는 주 생성자 프로퍼티로 고정되고 var면 여전히 가변입니다. 그래서 해시 키로 쓸 타입은 val만으로 짜고, JPA 엔티티에는 쓰지 않습니다."

이 버그는 왜 단위 테스트를 통과하나요? 어떤 테스트를 짜야 잡히나요?힌트: equals의 첫 줄이 무엇이었는지 떠올려 보라 핵심

단위 테스트는 대개 같은 참조를 넣고 같은 참조로 검증한다. 그러면 equals의 첫 줄 if (this == o) return true;가 걸리고 hashCode도 같은 객체라 당연히 같으므로 전부 통과한다. 테스트가 이 버그를 건드리지도 않은 것이다.

이 버그가 드러나는 것은 값은 같지만 참조는 다른 객체가 만들어지는 순간 — DB 조회로 엔티티를 다시 읽거나, JSON/직렬화 데이터를 역직렬화하거나, 다른 요청에서 새로 생성한 객체가 들어올 때뿐이다. 그 조건은 대개 운영에서만 갖춰진다.

TEST잡아내는 테스트 — 반드시 "다른 인스턴스"를 만든다
Money a = new Money("KRW", 1000);
Money b = new Money("KRW", 1000);   // 값은 같고 참조는 다르다 — 이게 핵심

assertThat(a).isEqualTo(b);
assertThat(a.hashCode()).isEqualTo(b.hashCode());  // 이 줄이 없으면 버그를 못 잡는다

Set<Money> s = new HashSet<>();
s.add(a);
assertThat(s.contains(b)).isTrue();   // 조회 2단계를 통째로 검증
assertThat(s.add(b)).isFalse();       // 중복이 실제로 걸러지는가

정리 문장 — "같은 참조로 검증하면 this == o 지름길에 걸려 항상 통과합니다. 그래서 값이 같은 별개 인스턴스 두 개를 만들어 equals·hashCode·Set.contains를 함께 검증해야 하고, 이게 역직렬화·DB 재조회 상황을 테스트로 앞당기는 방법입니다."

equals/hashCode를 아예 재정의하지 않는 게 정답인 경우도 있나요?힌트: "정체성이 값에 있는가, 존재 자체에 있는가" 가산점

있다. 오히려 그쪽이 기본값이어야 하는 타입도 많다. 재정의는 "이 타입의 정체성은 값에 있다"고 선언하는 행위다. 그 선언이 참이 아닌 타입에 재정의를 붙이면 없느니만 못하다.

재정의해야 하는 타입 — 값이 곧 정체성

  • 값 객체(VO): Money, Email, Period, 좌표
  • Map의 키·Set의 원소로 쓰이는 모든 타입
  • DTO 중 비교·중복 제거 대상이 되는 것

그냥 두는 게 맞는 타입 — 존재가 곧 정체성

  • 서비스·리포지토리·컨트롤러 같은 스프링 빈 — 값이 없고 인스턴스가 곧 정체성
  • 스레드·커넥션·소켓 등 자원 핸들 — 두 커넥션이 "값이 같다"는 말 자체가 성립하지 않는다
  • 가변 상태 덩어리 — 재정의하면 컬렉션에서 유령 항목의 씨앗이 된다

정리 문장 — "재정의는 '정체성을 값으로 정의하겠다'는 선언입니다. 값 객체와 해시 키에는 반드시 필요하고, 빈·자원 핸들처럼 존재 자체가 정체성인 타입은 Object의 참조 동일성이 정답입니다."

암기 대상 여섯 줄

조회는 2단계
hashCode로 칸을 고르고 → 그 칸 안에서만 equals로 대조한다.
1단계가 틀리면 끝
equals는 호출조차 되지 않는다. 그래서 "equals가 실패했다"는 틀린 진단이다.
규약은 한 방향
equals true ⟹ hashCode 동일. 역은 강제 아님(=충돌, 성능 문제).
비대칭의 이유
칸이 갈리면 복구 불가, 칸이 겹치면 2단계가 걸러 준다.
필드 집합 규칙
hashCode 입력이 equals보다 넓으면 위반, 좁으면 손해, 같으면 정답.
불변 조건
기준 필드가 담긴 동안 변하면 유령 항목 — 못 찾고 못 지우는데 size엔 잡힌다.

30초 답변 대본 — 이 순서로 말한다

  1. 절차: "해시 컬렉션의 조회는 hashCode로 칸을 고르고 equals로 대조하는 2단계입니다."
  2. 실패: "equals만 재정의하면 2단계 기준만 값으로 바뀌고 1단계는 객체 기준인 채 남아, 값이 같은 두 객체가 다른 칸으로 갈립니다. 그러면 equals는 호출조차 되지 않습니다."
  3. 규약: "그래서 equals가 true면 hashCode도 같아야 한다는 규약이 나옵니다. 반대 방향은 강제가 아닌데, 겹치는 건 2단계가 걸러 주므로 성능 문제일 뿐이기 때문입니다."
  4. 조건: "덧붙여 기준 필드는 컬렉션에 담긴 동안 불변이어야 합니다. 바뀌면 옛 칸에 남아 유령 항목이 됩니다."
  5. 실무: "그래서 값 객체는 record로, JPA 엔티티는 @GeneratedValue id 대신 불변 비즈니스 키로 만듭니다."

2번을 건너뛰고 3번(규약)부터 말하면 암기한 사람으로 들린다. 반드시 절차 → 실패 → 규약 순서로 간다.

한 줄 요약
해시 컬렉션은 hashCode로 칸을 고르고 equals로 대조하는 2단계이고 1단계가 어긋나면 2단계는 호출조차 되지 않으므로, 동등성의 정의를 값 기준으로 바꿨다면(equals 재정의) 칸 배정 기준(hashCode)도 정확히 같은 필드로 함께 바꿔야 한다 — 그리고 그 기준 필드는 컬렉션에 담긴 동안 절대 변하지 않아야 한다. 한쪽만 바꾸거나 나중에 값이 변하면 "넣었는데 못 찾는" 버그가 예외 하나 없이 조용히 시작된다.
