try-with-resources — finally로 닫으면 진짜 원인이 사라진다
새 문법이 생긴 이유는 "더 간결해서"가 아니라 finally 방식이 예외를 삼키기 때문이다 — 그리고 자원 누수는 GC가 구제해 주지 않는 종류의 누수다

면접 질문: "try-with-resources는 어떤 문제를 해결하나요? 자원 누수가 발생하는 전형적인 코드 패턴은?"

핵심 관전 포인트 — "finally에서 close하면 되는데 왜 새 문법이 필요한가"에 대한 답은 "더 간결해서"가 아니라 "finally 방식은 예외를 삼킨다"는 것이다. try 본문에서 예외 A가 나고 finally의 close()에서 예외 B가 나면, 자바는 진행 중이던 A를 버리고 B를 던진다 — 로그에는 "닫기 실패"만 남고 진짜 원인인 "읽기 실패"는 흔적도 없이 사라진다. try-with-resources는 반대로 A를 주 예외로 던지고 B를 suppressed로 A에 매달아 둘 다 보존한다. 여기에 더해 여러 자원을 선언의 역순(나중에 연 것을 먼저)으로 전부 닫아 주고, 하나의 close가 실패해도 나머지 close를 계속 실행한다. 자원 누수는 GC가 구제해 주지 않는 종류의 누수라(외부 자원은 close를 불러야만 반환된다) 평소엔 조용하다가 트래픽이 몰리는 날 커넥션 풀 고갈이나 Too many open files로 한꺼번에 터진다. 그래서 이 습관은 취향이 아니라 자원 생명주기를 의식하는지의 표본이고, 운영에서는 HikariCP의 leakDetectionThreshold와 풀 지표로 누수 지점을 특정하는 절차까지 갖춰야 한다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "try-with-resources는 어떤 문제를 해결하나요? 자원 누수가 발생하는 전형적인 코드 패턴은?"

출제 의도 — 커넥션·스트림 누수는 평소엔 멀쩡하다가 트래픽이 몰리는 날 풀 고갈로 터진다. finally 수동 정리의 실수 가능성(예외 중첩, 반환 누락)을 언어 기능으로 제거하는 습관 — 자원의 생명주기를 의식하며 코드를 쓰는지의 표본으로 본다.

약점 A"코드가 간결해집니다"에서 끝나는 답 — 틀린 말은 아니지만 취향 문제로 들린다. 진짜 답은 "finally는 예외를 삼킨다"이고, 이걸 말하지 못하면 이후 꼬리질문(suppressed, 우선순위)이 전부 막힌다.
약점 B"close를 안 하면 메모리 누수가 납니다"라고 뭉뚱그리는 답 — 왜 GC가 구제해 주지 않는지를 설명하지 못한다. 자원은 힙 밖에 있고 개수가 정해져 있다는 두 가지를 짚어야 "평소엔 조용하다가 한꺼번에 터지는" 증상까지 연역된다.
약점 C누수 패턴을 "부주의 목록"으로만 나열하는 답 — 네 패턴은 전부 코드 리뷰와 테스트를 통과한다. 왜 사람이 반복해서 실수하는가를 대지 못하면 "잘 짜면 되지 않나"라는 반문에 답할 수 없다.
약점 D운영에서의 추적 절차가 없는 답 — "풀 크기를 늘린다"로 끝나면 감점이다(누수라면 시간만 버는 조치). 누수와 순수 부하를 지표로 구분하고 leakDetectionThreshold로 지점을 특정하는 순서까지가 시니어 변별선이다.
합격선"finally는 예외를 삼킨다"는 메커니즘을 먼저 세우고 → suppressed로 우선순위가 정확히 반대임을 대비하고 → 누수 4패턴이 왜 반복되는지를 사람의 실행 모델로 설명하고 → Stream·스트리밍 조회 같은 경계 밖 자원을 짚고 → 운영 추적 6단계로 닫는 것.
이 문서의 진행 방향 — 두 개의 축을 분리해서 기억한다 이 주제는 서로 다른 두 문제가 한 문법으로 풀린다는 점 때문에 헷갈린다. 축 ①은 "예외 은폐"(3·4·8절) — 자원을 닫기는 닫았는데 진짜 원인이 로그에서 사라지는 문제다. 축 ②는 "자원 누수"(1·2·5·10~12절) — 애초에 닫히지 않아 한도가 고갈되는 문제다. try-with-resources는 이 둘을 동시에 막는다. 면접 답변도 이 순서로 하면 겹치지 않는다.

1. 전제 — 자원은 힙 밖에 있다, GC는 그 선을 넘지 못한다

먼저 이 문서에서 말하는 자원(resource)을 정의하고 가자. 자원은 자바 힙 바깥의 무언가를 점유하는 객체다. DB 커넥션, 파일 핸들, 소켓, 네이티브 메모리 같은 것들이다.

여기서 "힙 바깥"이 핵심이다. new ArrayList<>()로 만든 리스트는 힙 안에만 존재하므로, 아무도 참조하지 않게 되면 GC가 알아서 회수한다. 우리가 신경 쓸 일이 없다. 그런데 dataSource.getConnection()으로 받은 커넥션 객체는 다르다. 자바 객체는 힙에 있지만, 그 객체가 붙잡고 있는 진짜 자원은 힙 바깥에 있다.

비유 — GC는 집 안 청소부, 자원은 도서관에서 빌린 책 GC는 내 방 안에 굴러다니는 쓰레기는 알아서 치워 준다. 그런데 도서관에서 빌린 책은 내 방에서 사라졌다고 반납되지 않는다. 대출 기록은 도서관 쪽에 남아 있고, 내가 반납 창구에 갖다 놓기 전까지 다음 사람은 그 책을 빌릴 수 없다. 더 나쁜 것은 도서관의 대출 한도다 — 한 사람이 10권까지만 빌릴 수 있는데 반납을 안 하면, 어느 순간부터 아무 책도 못 빌린다. 커넥션 풀이 정확히 이 구조다.

자원 누수가 "조용하다가 한꺼번에" 터지는 이유 — 두 문장

① 힙 밖에 있다
GC의 관할이 아니므로 close를 부르지 않으면 영원히 반환되지 않는다. 자바 객체가 회수되는 것과 자원이 반환되는 것은 별개다.
② 개수가 정해져 있다
풀 최대 크기, OS의 파일 디스크립터 한도. 하나씩 새는 동안에는 무증상이고, 한도에 닿는 순간 그 자원을 쓰는 모든 코드가 동시에 죽는다.
새는 속도는 요청량에 비례한다 → 피크 트래픽에서 한도에 훨씬 빨리 도달한다

2. 누수의 시간축 — 조용하다가 한꺼번에 터진다

자원 누수가 위험한 이유는 새는 순간과 터지는 순간이 멀리 떨어져 있기 때문이다. 누수 코드를 배포한 날 아무 일도 일어나지 않고, 며칠 뒤 트래픽이 몰리는 시간대에 아무 배포도 하지 않았는데 서비스가 멈춘다. 그래서 원인을 코드 변경에서 찾기가 어렵다.

한도에 도달했을 때 나타나는 얼굴 — 자원별로 메시지가 다르다

커넥션 풀
Connection is not available
커넥션 대기 타임아웃. DB는 멀쩡한데 애플리케이션 전체가 멈춘다.
파일 디스크립터
Too many open files
프로세스가 새 파일도 새 소켓도 열지 못한다. 로그 기록조차 실패할 수 있다.
HTTP 커넥션 풀
연결 획득 대기
외부 API 호출이 전부 대기에 걸려 연쇄적으로 스레드까지 고갈된다.

세 증상 모두 "코드를 바꾸지 않았는데 갑자기" 발생한다는 공통점이 있다. 배포 이력에서 원인을 찾을 수 없을 때 누수를 1순위로 의심하는 이유다.

3. finally의 진짜 결함 — 예외를 삼킨다

"자원은 finally에서 닫으면 되지 않나"가 자연스러운 반응이다. 실제로 자바 7 이전에는 그것이 유일한 방법이었다. 그리고 close 호출 자체는 확실히 보장된다. 문제는 다른 데 있다.

Before finally에서 닫는 고전적 형태 — close는 불리지만…
static String readFirstLine(Path path) throws IOException {
    BufferedReader reader = Files.newBufferedReader(path);
    try {
        return reader.readLine();   // (A) 여기서 읽기가 실패한다고 하자
    } finally {
        reader.close();             // (B) 닫기도 실패한다고 하자
    }
}

(A)와 (B)가 둘 다 예외를 던지면 이 메서드 밖으로 나가는 것은 무엇인가.

Exception in thread "main" java.io.IOException: 닫기 실패(B) at java.base/java.io.BufferedReader.close(BufferedReader.java:...) at com.example.FileReader.readFirstLine(FileReader.java:9) at ... ★ (A)는 어디에도 없다. 로그 어디를 뒤져도 "읽기 실패"라는 단어가 나오지 않는다.
진짜 원인인 A가 사라지고 부수적인 B만 남았다 —
이것이 "간결함" 같은 취향 문제가 아닌 이유다

3-1. 왜 이렇게 되는가 — finally 규칙 한 줄

finally 블록이 예외를 던지며 끝나면, 그 예외가 진행 중이던 예외를 대체한다. try에서 던져지던 A는 finally가 정상적으로 끝나야만 계속 전파되는데, finally 자신이 B를 던지면 메서드는 B와 함께 종료되고 A는 그냥 버려진다. 자원과 무관하게 이 규칙만 떼어 보면 더 분명하다.

try {
    throw new IllegalStateException("A");
} finally {
    throw new IllegalArgumentException("B");
}
// 밖으로 나가는 것은 B뿐이다. A는 어디에도 기록되지 않고 사라진다.
// finally의 return도 같은 방식으로 try의 return을 덮어쓴다.

3-2. "close가 예외를 던지는 일이 실제로 있나?" — 하필 가장 나쁜 타이밍에 있다

BufferedWriter.close()는 내부적으로 버퍼를 비우는 flush()를 하므로 디스크가 가득 찼거나 네트워크가 끊겼으면 실패한다. 소켓의 close도 실패할 수 있고, DB 커넥션의 close도 마찬가지다. 그런데 결정적인 것은 빈도가 아니라 타이밍이다.

왜 하필 장애 때 원인이 사라지는가 — 두 예외는 독립 사건이 아니다

DB 커넥션이 끊김→쿼리 실패 (A)＋끊긴 커넥션의 close도 실패 (B)
네트워크 단절→읽기 실패 (A)＋닫기 실패 (B)
디스크 가득 참→쓰기 실패 (A)＋flush 포함 close 실패 (B)
두 예외가 함께 나는 것은 우연이 아니라 상관관계가 있는 사건이다 →
진짜 심각한 장애일수록 원인이 은폐될 확률이 높다

평소에는 잘 돌다가 진짜 장애 때만 로그가 쓸모없어지는 최악의 조합이다. "close가 실패하는 일이 드물다"는 반론이 통하지 않는 이유가 여기 있다 — 드문 그 순간이 정확히 원인을 알아야 하는 순간이다.

4. try-with-resources — A를 던지고 B를 매달아 둔다

After 자원을 try의 괄호 안에서 선언한다
static String readFirstLine(Path path) throws IOException {
    try (BufferedReader reader = Files.newBufferedReader(path)) {
        return reader.readLine();   // (A) 읽기 실패
    }                               // (B) 블록을 벗어나며 close, 그것도 실패
}
Exception in thread "main" java.io.IOException: 읽기 실패(A) at com.example.FileReader.readFirstLine(FileReader.java:8) at ... Suppressed: java.io.IOException: 닫기 실패(B) at java.base/java.io.BufferedReader.close(BufferedReader.java:...) at com.example.FileReader.readFirstLine(FileReader.java:9) ... 1 more ★ 주 예외 자리에 A가 있고, B는 그 아래 "Suppressed:" 블록으로 붙어 있다. 둘 다 남았고, 우선순위도 우리 직관과 일치한다.

억제된 예외(suppressed exception)는 "주 예외가 전파되는 동안 부수 경로에서 발생해 삼켜질 뻔한 예외를 주 예외 객체에 매달아 두는" 장치다. 삼켜지는(suppressed) 대신 붙어 있다는 뜻으로 이런 이름이 붙었다. try-with-resources를 만들면서 자바 7에서 Throwable에 addSuppressed()와 getSuppressed()가 추가됐다.

스택트레이스에만 찍히는 것이 아니라 코드로도 꺼낼 수 있다.

try {
    readFirstLine(path);
} catch (IOException e) {
    System.out.println("주 예외: " + e.getMessage());        // 주 예외: 읽기 실패(A)
    for (Throwable s : e.getSuppressed()) {
        System.out.println("  억제됨: " + s.getMessage());   //   억제됨: 닫기 실패(B)
    }
}
두 방식의 차이를 한 줄로 — 우선순위가 정확히 반대다
try 본문의 예외 A (진짜 원인)close의 예외 B (부수 사고)로그로 확인 가능한 것
finally 수동 정리사라진다밖으로 던져진다"닫기 실패"만
try-with-resources밖으로 던져진다A에 suppressed로 매달린다둘 다

이 한 줄이 이 주제의 이해도를 가른다 가산점

finally는 나중에 난 예외가 이기고, try-with-resources는 원래 예외가 이긴다

외우는 방식: finally는 "덮어쓰기", try-with-resources는 "덧붙이기". 전자는 대체(replace), 후자는 첨부(attach)다.

5. 누수가 나는 전형적 패턴 4가지 — 왜 사람이 계속 실수하는가

예외 은폐가 finally의 결함이라면, 자원 누수는 그보다 더 흔한 실수다. 패턴이 네 가지인데, 중요한 것은 패턴 자체가 아니라 왜 이 실수가 반복되는가다. 근본 원인은 하나로 모인다 — 블록을 벗어나는 경로는 여러 개인데, 손으로 쓴 close()는 그중 하나에만 놓여 있다.

패턴 ①
try 블록 없이, 마지막 줄에서 close
InputStream in = new FileInputStream(path);
process(in.read());   // 여기서 예외가 나면
in.close();           // 이 줄은 실행되지 않는다
왜 계속 실수하는가. 이 코드는 위에서 아래로 읽으면 완벽히 자연스럽다 — 열고, 쓰고, 닫는다. 사람의 머릿속 실행 모델은 "코드는 위에서 아래로 순서대로 실행된다"인데, 예외는 그 순서를 가로지르는 보이지 않는 탈출구다. in.read() 한 줄만 봐서는 여기서 밖으로 튈 수 있다는 사실이 코드 모양에 전혀 드러나지 않는다.
패턴 ②
finally는 썼지만, 자원이 여러 개일 때 일부만 닫힘
} finally {
    conn.close();   // 여기서 예외가 나면
    stmt.close();   // 이 줄과
    rs.close();     // 이 줄은 건너뛴다 → 누수
}
왜 계속 실수하는가. 순서를 바꿔도 해결되지 않는다 — 셋 중 어느 것이든 close가 던지면 뒤가 전부 건너뛰어진다. "제대로" 하려면 close마다 null 체크와 개별 try-catch가 필요한데, 그러면 정리 코드가 본문보다 길어진다. 사람은 길고 반복적이며 "아무 일도 안 하는 것처럼 보이는" 장식 코드를 본능적으로 줄이려 하고, 줄이는 순간 틀린다.
패턴 ③
예외 은폐 — 3절에서 본 그것
try {
    return parse(in);      // 여기서 난 예외가
} finally {
    in.close();            // 여기 예외에 덮여 사라진다
}
왜 계속 실수하는가. 이건 앞의 셋과 성격이 다르다. 실수했다는 자각조차 없다. 코드는 정확히 의도대로 짜였고 close도 확실히 불리고 있다. 문제는 언어의 finally 규칙이 개발자의 직관과 다르다는 것이고, 이건 배우지 않으면 알 방법이 없다. 그리고 배우지 않아도 평소에는 아무 문제가 없다 — close가 실패하는 진짜 장애 때만 조용히 손해를 본다.
패턴 ④
조기 반환 경로에서 반환 누락
Connection conn = dataSource.getConnection();
if (alreadyProcessed(id)) return;  // 미반납
...
conn.close();   // 40줄 아래에 있다
왜 계속 실수하는가. 범인은 대개 나중에 추가된 조기 반환이다. 처음 짤 때는 맞는 코드였다. 몇 달 뒤 누군가 "이미 처리된 건은 빨리 건너뛰자"며 return 한 줄을 추가하는데, 그 사람의 시야에는 40줄 아래의 close()가 보이지 않는다. 리뷰어에게도 마찬가지다 — diff에는 return; 한 줄만 찍혀 있고, 그 한 줄은 어느 모로 봐도 무해하다.
패턴 ②를 "제대로" 손으로 쓰면 이렇게 된다 — 이 코드를 매번 정확히 쓸 자신이 있는가 
} finally {
    if (rs   != null) { try { rs.close();   } catch (SQLException ignored) {} }
    if (stmt != null) { try { stmt.close(); } catch (SQLException ignored) {} }
    if (conn != null) { try { conn.close(); } catch (SQLException ignored) {} }
}   // 누수는 막았지만 close 예외를 전부 버렸다 — 이번엔 진단 정보가 사라진다
"제대로" 쓴 버전조차 완벽하지 않다는 점이 핵심이다. catch (…) {}로 삼킨 close 예외는 어디에도 남지 않는다. try-with-resources는 같은 상황에서 그 예외들을 suppressed로 보존한다.
After 네 패턴이 전부 같은 한 가지로 사라진다
try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql);
     ResultSet rs = stmt.executeQuery()) {

    if (alreadyProcessed(id)) return;   // ④ 조기 반환? 게이트를 지나며 닫힌다
    while (rs.next()) { parse(rs); }     // ①③ 예외 탈출? 마찬가지로 닫힌다

}   // ② rs → stmt → conn 역순으로 전부 닫힌다. 하나가 실패해도 나머지는 계속.

자원은 한 번에 하나씩 새는 것이라 테스트에서는 증상이 없고, 리뷰에서는 위에서 아래로 읽으면 멀쩡해 보인다. "잘 짜면 된다"가 아니라 사람이 반복하는 실수를 언어 기능으로 제거해야 하는 이유가 여기에 있다. 그리고 하나 더 — 자원의 획득과 반환이 물리적으로 떨어져 있는 코드는 시간이 지나면 반드시 샌다.

6. 동작 ① 대상 · 기본형 · close는 선언의 역순

6-1. 기본 형태와 대상

// try의 괄호 안에서 선언한 자원은 블록을 벗어나는 모든 경로에서 자동으로 닫힌다
try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql);
     ResultSet rs = stmt.executeQuery()) {
    while (rs.next()) { ... }
}   // 여기서 rs -> stmt -> conn 순으로 전부 close
대상은 AutoCloseable을 구현한 객체다 — 그리고 그것이 곧 표지판이다 이 인터페이스를 구현했다는 것 자체가 "나는 닫아야 하는 자원이다"라는 언어 수준의 표시다. 어떤 객체를 닫아야 하는지 헷갈리면 그 타입이 AutoCloseable을 구현했는지 보면 된다. IDE에서 타입 선언으로 한 번 들어가 보는 것으로 판정이 끝난다.

자바 9부터는 블록 밖에서 만든 변수도 사실상 final(effectively final, 한 번 대입하고 다시 대입하지 않는 변수)이면 이름만 넣을 수 있다.

Connection conn = dataSource.getConnection();
try (conn) { ... }   // Java 9+

6-2. close 순서 — 선언의 역순

여러 자원을 선언하면 선언의 역순으로 닫힌다. 말로만 들으면 헷갈리니 실행 순서를 직접 찍어 보자.

실험 자원 세 개를 열고 닫아 본다
class Res implements AutoCloseable {
    private final String name;
    Res(String name) { this.name = name; System.out.println("open  " + name); }
    @Override public void close() { System.out.println("close " + name); }
}

try (Res a = new Res("A");
     Res b = new Res("B");
     Res c = new Res("C")) {
    System.out.println("본문 실행");
}
출력 열기는 순서대로, 닫기는 거꾸로
open  A     ← 위에서부터 순서대로 열리고
open  B
open  C
본문 실행
close C     ← 닫을 때는 거꾸로
close B
close A

외울 문장 하나

선언 순서대로 열리고, 선언의 역순으로 닫힌다 — 나중에 연 것을 먼저 닫는다

면접에서는 여기에 이유를 붙여야 완성이다. "의존 관계 때문" — ResultSet은 Statement가, Statement는 Connection이 살아 있어야 유효하므로 의존하는 쪽부터 풀어야 한다.

7. 동작 ② 하나가 실패해도 나머지는 닫는다

패턴 ②에서 finally가 못 했던 것이 이것이다. try-with-resources는 한 자원의 close가 예외를 던져도 나머지 자원의 close를 계속 실행한다. 실패한 close의 예외는 버리지 않고 모아 두었다가 주 예외에 suppressed로 첨부한다.

자원 생성 중에 실패하는 경우도 안전하다 두 번째 자원을 만들다 예외가 나면 이미 만들어진 첫 번째 자원은 닫아 준다. 이걸 수동으로 하려면 생성 단계마다 try를 중첩해야 한다 — 자원이 세 개면 3중 중첩이다. 
try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql)) {  // ← 여기서 실패해도
    ...
}   // conn은 정상적으로 닫힌 뒤 예외가 밖으로 나간다

try-with-resources가 보장하는 세 가지 — 탈 · 역 · 보 암기

탈
모든 탈출 경로
정상 종료 · 예외 · return · break — 블록을 벗어나는 어떤 방법으로든 close가 따라 나간다.
역
역순으로 전부
선언의 역순으로 닫고, 하나가 실패해도 나머지를 계속 닫는다. 생성 도중 실패해도 만들어진 것만 닫는다.
보
예외를 보존
본문 예외를 주 예외로 유지하고 close 예외를 suppressed로 첨부한다. 어느 쪽도 사라지지 않는다.

면접에서 "세 가지를 보장합니다"로 운을 떼고 이 순서로 말하면 답변이 흐트러지지 않는다. 그리고 셋 다 "사람이 손으로 하면 자주 틀리는 일"이라는 점이 공통 근거다.

8. 컴파일러가 대신 써 주는 코드

지금까지의 보장이 마법이 아니라 컴파일러가 생성하는 평범한 코드라는 것을 보면 이해가 굳어진다. 아래는 자원 하나 기준의 개념 형태다 — 우리가 쓰는 세 줄이 어떤 구조로 펼쳐지는지 본다.

개념 코드 컴파일러가 만들어 내는 구조를 자바 코드로 쓰면
Resource r = acquire();
Throwable primary = null;          // try 본문에서 난 "진짜" 예외를 기억해 둘 자리
try {
    ...본문...
} catch (Throwable t) {
    primary = t;                   // 기억해 두고
    throw t;                       // 그대로 다시 던진다
} finally {
    if (r != null) {
        if (primary != null) {
            // 본문에서 이미 예외가 났다면, close의 예외로 그것을 덮으면 안 된다.
            // 그래서 close를 별도로 try로 감싸 잡고, 주 예외에 매달아 둔다.
            try { r.close(); }
            catch (Throwable sup) { primary.addSuppressed(sup); }
        } else {
            // 본문이 정상이었다면 close의 예외는 감출 이유가 없으므로 그대로 전파한다.
            r.close();
        }
    }
}
5절에서 "직접 하려면 이렇게 해야 한다"고 본 그 귀찮은 코드를 컴파일러가 정확하게 써 준다
try-with-resources가 하는 일은 새로운 능력을 주는 것이 아니라, 사람이 매번 정확히 하기 어려운 일을 기계가 대신하게 한 것이다
면접에서 이 절을 쓰는 법 이 코드를 통째로 외워 읊을 필요는 없다. 대신 "컴파일러가 primary 변수를 하나 만들어 본문 예외를 붙잡아 두고, close를 별도 try로 감싸 그 예외를 addSuppressed로 매답니다" 한 문장이면 충분하다. 이 문장 하나가 3절(예외 은폐)·4절(suppressed)·7절(하나 실패해도 계속)을 전부 설명하므로, 꼬리질문이 어느 쪽으로 와도 같은 근거로 답할 수 있다.

이유는 현실의 호출 습관에 있다. 자원을 넘겨받은 코드가 "혹시 안 닫혔을까 봐" 한 번 더 닫는 방어적 호출을 하는 일이 흔하다. 멱등하지 않으면 그 선의의 호출이 두 번째 close에서 예외를 만들고, 그 예외는 suppressed에 묻혀 진단을 흐린다.

public class TempDir implements AutoCloseable {
    private final Path dir;
    private boolean closed = false;        // 멱등을 위한 플래그

    @Override public void close() throws IOException {
        if (closed) return;                  // 두 번째 호출은 조용히 반환
        closed = true;
        deleteRecursively(dir);
    }
}   // throws는 실제로 던질 수 있는 예외로 좁힌다 — Exception 그대로 두지 않는다

13. 30초 답변 스크립트 · 암기 카드 총정리

"try-with-resources는 어떤 문제를 해결하나요?" — 이 순서로 말한다
1
"두 가지 문제를 동시에 해결합니다. 하나는 예외 은폐, 하나는 자원 누수입니다." — 먼저 축을 나눠 두면 답이 섞이지 않는다.
2
"finally에서 close하면 close는 불리지만, 본문 예외 A와 close 예외 B가 함께 나면 자바의 finally 규칙상 A가 버려지고 B만 남습니다. 그런데 본문 실패와 close 실패는 원인이 대개 같아서, 심각한 장애일수록 진짜 원인이 은폐됩니다. try-with-resources는 A를 던지고 B를 suppressed로 매달아 둘 다 보존합니다 — 우선순위가 정확히 반대입니다."
3
"보장은 세 가지입니다. 모든 탈출 경로에서 닫고, 선언 역순으로 전부 닫고(하나가 실패해도 나머지 계속), close 예외를 보존합니다. 이건 컴파일러가 primary 변수로 본문 예외를 붙잡아 두고 close를 별도 try로 감싸는 코드를 생성해서 얻는 결과입니다."
4
"누수 패턴은 네 가지인데, 공통점은 전부 리뷰와 테스트를 통과한다는 점입니다. 마지막 줄 close, 자원 여러 개일 때 일부만 닫힘, 예외 은폐, 나중에 추가된 조기 반환. 자원의 획득과 반환이 물리적으로 떨어져 있으면 시간이 지나면서 반드시 샙니다."
5
"자원은 힙 밖에 있어 GC가 회수하지 않고 개수가 정해져 있어서, 평소엔 조용하다가 피크에 풀 고갈이나 Too many open files로 한꺼번에 터집니다. 그래서 운영에서는 풀 지표로 누수와 순수 부하를 먼저 구분하고, leakDetectionThreshold로 대여 지점 스택트레이스를 잡습니다. 풀 크기를 늘리는 건 누수라면 시간만 버는 조치입니다."
경험을 묻는 후속 질문이 붙는다면 — 이런 형태로 답한다 "트래픽 피크에 커넥션 대기 타임아웃이 났는데 배포 이력이 없었습니다. 저점 시간대 지표를 보니 트래픽은 내려갔는데 active가 그대로여서 누수로 판단했고, leakDetectionThreshold를 걸어 나온 스택트레이스에서 스트리밍 조회 결과를 닫지 않는 export 경로를 찾았습니다. try-with-resources로 감싸 해결한 뒤, 같은 실수가 다시 들어오지 못하도록 정적 분석 규칙을 CI에 추가했습니다."

14. 꼬리질문 셀프 테스트 (15문항)

질문만 먼저 보고 소리 내어 답해 본 뒤 펼친다. 답이 30초 안에 나오지 않으면 해당 절로 돌아간다.

finally에서 close하면 되는데 try-with-resources가 굳이 왜 필요한가요?핵심힌트: "간결해서"는 절반짜리 답이다 (→ 3·4절)

"간결해서"라고 답하면 절반만 답한 것이다. 핵심은 finally 방식이 예외를 삼킨다는 것이다.

try 본문에서 진짜 원인 예외 A가 나고 finally의 close()에서 예외 B가 나면, 자바의 finally 규칙상 A는 버려지고 B만 밖으로 나간다. 로그에는 "닫기 실패"만 남고 "읽기 실패"는 흔적도 없다. 게다가 본문이 실패한 원인과 close가 실패한 원인은 대개 같으므로(커넥션이 끊기면 쿼리도 close도 실패한다), 진짜 심각한 장애일수록 원인이 은폐될 확률이 높다.

try-with-resources는 A를 주 예외로 던지고 B를 suppressed로 A에 매달아 둘 다 보존한다. 우선순위가 정확히 반대다.

여기에 두 가지를 더 얹으면 답이 완성된다. 자원이 여러 개일 때 finally는 하나의 close 실패가 나머지 close를 건너뛰게 만들지만 try-with-resources는 나머지를 계속 닫는다. 그리고 자원의 수명이 블록 범위로 묶이므로, 나중에 누가 조기 반환을 추가해도 close가 따라 나간다. 한 문장으로 정리하면 "할 수는 있지만 사람이 매번 정확히 하기 어려운 일을 컴파일러가 생성하는 코드로 내린 것"이다.

자원을 여러 개 선언하면 close 순서는? 하나가 close 중 예외를 던지면요?핵심힌트: 옷을 벗는 순서 (→ 6·7절)

선언의 역순으로 닫는다. Connection → PreparedStatement → ResultSet 순으로 선언했으면 ResultSet → PreparedStatement → Connection 순으로 닫힌다.

이유는 의존 관계다. 나중에 만든 자원이 먼저 만든 자원 위에 얹혀 있으므로(ResultSet은 Statement가, Statement는 Connection이 살아 있어야 유효하다), 의존하는 쪽부터 풀어야 한다. 옷을 벗을 때 코트부터 벗는 것과 같다.

하나의 close가 예외를 던져도 나머지 자원의 close는 계속 실행된다. 그 예외들은 밖으로 전파되는 주 예외에 suppressed로 첨부된다. finally 수동 정리가 못 하는 부분이 정확히 이것이다 — finally에서는 첫 close가 던지는 순간 그 뒤의 close들이 전부 건너뛰어져 나머지 자원이 그대로 샌다.

suppressed exception이 뭔가요? catch한 예외에서 어떻게 확인하나요?가산점힌트: 확인 방법 두 가지 + 우선순위 대비 (→ 4절)

주 예외가 전파되는 동안 close 같은 부수 경로에서 발생해 삼켜질 뻔한 예외를, 주 예외 객체에 addSuppressed()로 매달아 두는 장치다. try-with-resources를 위해 자바 7에서 Throwable에 추가됐다.

확인하는 방법은 두 가지다. 스택트레이스 출력에 Suppressed: ... 블록으로 함께 찍히고, 코드에서는 e.getSuppressed()가 배열로 돌려준다.

catch (IOException e) {
    log.error("주 예외: {}", e.getMessage());
    for (Throwable s : e.getSuppressed()) log.error("  억제됨: {}", s.getMessage());
}

여기서 반드시 덧붙일 것이 우선순위 대비다. finally 수동 정리는 나중에 난 close 예외가 이기고 원래 예외가 소멸하는 반면, try-with-resources는 원래 예외가 이기고 close 예외가 매달린다. 정확히 반대다. 이 차이를 말할 수 있으면 문법을 외운 것이 아니라 왜 만들어졌는지를 이해한 것으로 읽힌다.

AutoCloseable과 Closeable의 차이는?힌트: 역사 순서로 답한다 (→ 9절)

Closeable(java.io, 자바 5)이 먼저 있었고 close() throws IOException을 선언한다. IO 스트림용으로 만들어졌기 때문이다.

try-with-resources를 만들면서 IO 이외의 자원(DB 커넥션, 락, 네이티브 핸들)도 담아야 했는데 IOException으로는 표현이 안 됐다. 그래서 상위 인터페이스 AutoCloseable(java.lang, 자바 7)을 새로 만들어 close() throws Exception으로 선언하고, Closeable이 그것을 상속하게 했다.

계약상의 차이도 하나 있다. Closeable의 close는 멱등(여러 번 불러도 안전)이어야 한다고 명세되어 있고, AutoCloseable은 멱등을 권장하되 요구하지는 않는다. 요구하지 않는 이유는 락 해제처럼 두 번 부르면 실제로 문제가 되는 자원까지 담아야 했기 때문이다. 새 자원 클래스를 만들 때는 가능하면 멱등하게 구현하는 것이 안전하다 — 넘겨받은 쪽이 방어적으로 한 번 더 닫는 일이 흔하기 때문이다.

커넥션 누수가 의심될 때 운영에서 어떤 순서로 추적하겠습니까?시니어 변별힌트: 6단계. ②를 빼먹으면 방향을 잘못 잡는다 (→ 12절)

순서를 갖고 답하는 것이 중요하다.

① 증상 확인. 풀 지표(active/idle/pending)를 본다. active가 최대치에 붙어 있고 pending이 쌓이면 고갈이다. 이때 "풀 크기를 늘린다"는 누수라면 시간만 버는 오답이다 — 새는 속도가 그대로면 더 큰 풀도 결국 고갈되고, 그동안 DB 서버 쪽 세션만 늘어난다.

② 누수 vs 순수 부하 구분. 트래픽이 줄어도 active가 안 내려오면 누수, 트래픽과 함께 내려오면 용량 문제다. 이 구분이 이후 방향을 완전히 갈라놓는다.

③ 지점 특정. HikariCP의 leakDetectionThreshold를 걸어 미반납 커넥션의 대여 지점 스택트레이스를 수집한다. 임계값은 정상적으로 가장 오래 걸리는 작업보다 넉넉히 위로 잡아야 정상 배치가 경고로 도배되지 않는다. DB 쪽에서는 PostgreSQL의 pg_stat_activity에서 idle in transaction 상태로 오래 머무는 세션 목록으로 교차 확인한다.

④ 스레드 덤프로 확정. 다수의 스레드가 HikariPool.getConnection에서 대기 중이면 지금 병목이 커넥션 풀이라는 것이 확정된다. 느림의 원인이 GC인지 외부 API인지 커넥션 대기인지 가르는 용도다.

⑤ 수정. 해당 경로를 try-with-resources로 바꾸거나 프레임워크가 관리하는 트랜잭션 범위로 편입시킨다. 조기 반환 분기와 예외 경로가 단골 범인이라는 것까지 말하면 좋다.

⑥ 재발 방지. 정적 분석 도구의 "AutoCloseable을 닫지 않음" 규칙을 CI에 걸어 사람 리뷰 이전에 잡히게 한다. OS 레벨에서는 lsof -p <pid>로 열린 파일 디스크립터 개수 추이를 함께 본다.

try-with-resources에 catch·finally를 붙일 수 있나요? 그러면 close는 언제 실행되나요?힌트: catch에서 이미 자원은 닫혀 있다

붙일 수 있다. 그리고 순서가 중요하다 — 자원의 close가 먼저 실행되고, 그 뒤에 같은 try 문의 catch와 finally가 실행된다.

try (BufferedReader r = Files.newBufferedReader(path)) {
    return r.readLine();
} catch (IOException e) {
    // 여기 도달했을 때 r은 이미 닫혀 있다. e.getSuppressed()에 close 예외가 붙어 있을 수 있다.
    return null;
}

실무적 함의가 두 가지다. 첫째, catch 블록 안에서 그 자원을 다시 쓰려고 하면 안 된다 — 이미 닫혔다. 둘째, catch에서 잡은 예외에 close 예외가 suppressed로 붙어 있을 수 있으므로, 로깅할 때 예외 객체를 통째로 넘겨야(메시지만 찍지 말고) 억제된 예외까지 남는다.

자원을 두 개 선언했는데 두 번째를 만들다 예외가 나면 첫 번째는 닫히나요?힌트: 수동으로 하려면 try를 중첩해야 하는 그 경우

닫힌다. try-with-resources는 이미 성공적으로 만들어진 자원만 골라 역순으로 닫는다. 아래에서 prepareStatement가 던지면 conn은 정상적으로 close되고, 그 예외가 밖으로 나간다.

try (Connection conn = dataSource.getConnection();
     PreparedStatement stmt = conn.prepareStatement(sql)) {   // 여기서 실패해도
    ...
}   // conn은 닫힌다

이걸 손으로 하려면 생성 단계마다 try를 중첩해야 한다("커넥션을 얻었고, 그 다음 스테이트먼트를 만들다 실패했으니 커넥션만 닫는다"). 자원이 세 개면 3중 중첩이다. 사람이 정확히 쓰기 어려운 코드를 컴파일러가 대신 쓴다는 이 주제의 요지가 여기서도 그대로 나온다.

try 괄호 안에서 선언한 자원 변수에 재대입이 안 되는 이유는? 자바 9의 try (conn) 형태는 뭐가 다른가요?힌트: 닫을 대상을 잃어버리면 안 된다

자원 변수는 암묵적으로 final이다. 재대입을 허용하면 블록 끝에서 닫아야 할 대상이 원래 열었던 자원이 아니게 되고, 원래 자원은 참조를 잃어 영원히 못 닫는다. 즉 재대입 금지는 "닫을 대상을 잃어버리지 않게" 하는 안전장치다.

자바 9부터는 블록 밖에서 만든 변수도 사실상 final(effectively final)이면 이름만 넣을 수 있다.

Connection conn = dataSource.getConnection();
try (conn) { ... }   // Java 9+

주의점은 자원 획득이 try 문 밖에서 일어난다는 것이다. 획득한 뒤 try에 진입하기 전 사이에 무슨 일이 생기면 그 구간은 보호받지 못한다. 그래서 가능하면 괄호 안에서 선언하는 형태를 기본으로 쓰고, 이미 밖에서 넘겨받은 자원을 이 블록에서 책임지고 닫아야 할 때만 쓰는 것이 안전하다.

자원 참조가 null이면 close에서 NPE가 나나요?함정힌트: 컴파일러가 생성하는 코드를 떠올린다 (→ 8절)

나지 않는다. 8절에서 본 컴파일러 생성 코드에 if (r != null) 검사가 들어 있다 — 자원 참조가 null이면 close()를 아예 호출하지 않는다. 팩토리 메서드가 null을 돌려주는 경우에도 try-with-resources 자체가 NPE를 만들지는 않는다.

다만 이건 "null이어도 안전하다"이지 "null이어도 정상"이라는 뜻은 아니다. 자원이 null이라는 것은 획득에 실패했다는 뜻이므로 본문에서 그 자원을 쓰는 순간 NPE가 난다. 자원을 돌려주는 메서드는 실패 시 null이 아니라 예외를 던지도록 설계하는 것이 맞다.

직접 AutoCloseable 자원 클래스를 만든다면 close() 구현에서 지킬 것은?가산점힌트: 멱등 · 던지는 예외 · 인터럽트
  • 멱등하게 만든다. 이미 닫혔으면 조용히 반환한다. 자원을 넘겨받은 코드가 "혹시 안 닫혔을까 봐" 한 번 더 닫는 방어적 호출이 흔하기 때문이다.
  • close()가 던지는 예외를 최대한 좁힌다. 인터페이스 선언은 throws Exception이지만, 구현에서는 실제로 던질 수 있는 예외만 선언하거나 아예 던지지 않게 만든다. 그래야 호출부가 catch (Exception e)로 뭉뚱그리지 않는다.
  • InterruptedException은 던지지 않는다. AutoCloseable 문서가 강하게 권고하는 항목이다. close 예외는 suppressed로 매달려 조용히 넘어갈 수 있는데, 인터럽트가 그렇게 묻히면 스레드의 인터럽트 신호가 사라져 종료 처리가 망가진다.
  • close 안에서 오래 걸리는 작업이나 블로킹을 피한다. close는 예외 전파 경로에서도 불리므로, 여기서 멈추면 장애 상황에서 스레드가 함께 묶인다.

그리고 클래스가 AutoCloseable을 구현한다는 것 자체가 "나는 닫아야 하는 자원이다"라는 언어 수준의 선언이라는 점을 기억한다. 닫을 필요가 없는 클래스에 습관적으로 붙이면 호출부에 불필요한 규율을 강요하게 된다.

어떤 Stream을 닫아야 하나요? list.stream()도 닫아야 하나요?함정힌트: 원본이 무엇인지로 가른다 (→ 10절)

원본이 IO 자원인 스트림만 닫는다. Files.lines(), Files.walk(), Files.list(), DB 커서를 흘려보내는 스트리밍 조회가 여기 해당한다. 이들은 파일 디스크립터나 ResultSet·커넥션을 연 채로 우리에게 넘어온다.

list.stream(), Arrays.stream(arr)는 닫을 필요가 없다. 힙 안의 데이터만 훑으므로 닫을 것이 없다. Stream이 AutoCloseable을 구현하고 있는 것은 그 소수의 IO 기반 스트림을 위해서다.

가장 자주 놓치는 이유는 Stream이 닫아야 할 자원이라는 사실 자체를 모르기 때문이다. .toList() 같은 종단 연산이 끝나면 다 끝난 것처럼 보이지만 종단 연산은 파일을 닫지 않는다. "이 스트림의 원본이 파일인가 DB인가"를 묻는 습관 하나면 걸러진다.

HikariCP의 leakDetectionThreshold를 켜면 새는 커넥션을 회수해 주나요?함정힌트: 탐지와 회수는 다르다 (→ 12절)

회수하지 않는다. 설정한 시간 안에 반납되지 않은 커넥션이 있으면 그 커넥션을 빌려간 지점의 스택트레이스를 경고 로그로 남길 뿐이다. 커넥션을 강제로 끊거나 풀로 되돌리지 않는다.

그래서 이 설정은 치료제가 아니라 탐지기다. 값을 켰다고 누수가 완화되지는 않고, "어느 코드가 범인인지" 위치를 찍어 주는 것이 전부다. 그 위치를 받아 코드를 고치는 것은 우리 몫이다.

임계값 설정에도 요령이 있다. 정상적으로 가장 오래 걸리는 작업보다 넉넉히 위로 잡아야 한다. 너무 짧으면 정상적인 장시간 배치가 전부 경고로 찍혀 노이즈가 되고, 노이즈가 되면 아무도 안 본다. HikariCP는 2초(2000) 미만 값은 받지 않는다.

@Transactional을 쓰면 커넥션 누수 걱정은 안 해도 되나요?시니어 변별힌트: 경계 안이냐 밖이냐 (→ 11절)

경계 안에 있는 동안만 안전하다. @Transactional 메서드 안에서 JdbcTemplate이나 리포지터리를 평범하게 호출하는 코드는 프레임워크가 커넥션 획득·Statement·ResultSet·역순 close까지 전부 처리하므로 우리가 닫을 것이 없다.

문제는 그 경계를 넘는 코드다. 세 가지가 단골이다.

  • 스트리밍 조회(queryForStream, getResultStream) — ResultSet과 커넥션을 연 채로 스트림이 우리에게 넘어온다. 우리가 닫아야 반납된다.
  • 파일·HTTP 클라이언트 — 엑셀/CSV 생성, 업로드 저장, 외부 API 응답 바디는 프레임워크가 닫아 주지 않는다. 응답 바디를 소비하거나 닫지 않으면 HTTP 커넥션도 풀로 돌아가지 않는다.
  • 직접 만든 자원 클래스 — 락, 임시 디렉터리, 네이티브 핸들 래퍼.

한 줄로는 "프레임워크가 관리하는 경로에 있으면 안전하고, 그 경로 밖으로 나오는 순간 우리 책임"이다. 그리고 누수 사고는 대개 그 경계를 넘는 코드에서 난다.

try 본문은 정상인데 close만 실패하면 어떻게 되나요?힌트: 이때는 감출 이유가 없다

close의 예외가 그대로 주 예외로 밖에 던져진다. 본문에서 난 예외가 없으니 감출 대상 자체가 없고, 억누르면 오히려 실패를 숨기는 셈이 된다. 8절의 컴파일러 생성 코드에서 primary == null인 분기가 정확히 이 경우다.

이게 중요한 이유는 쓰기 작업 때문이다. BufferedWriter의 close()는 내부적으로 flush()를 하므로, 본문이 전부 성공했더라도 close에서 실패하면 버퍼에 남아 있던 데이터가 실제로는 기록되지 않은 것이다. 그래서 쓰기 자원은 close 예외를 절대 무시하면 안 되고, "성공적으로 저장했다"는 응답은 close가 끝난 뒤에 내보내야 한다.

코틀린에는 try-with-resources 문법이 없는데 같은 일을 어떻게 하나요?힌트: 문법이 아니라 표준 라이브러리 함수다

코틀린은 이걸 언어 문법이 아니라 표준 라이브러리의 확장 함수 use로 제공한다. Closeable/AutoCloseable에 붙는 인라인 함수이며, 블록을 벗어날 때 close를 부르고 본문 예외가 있으면 close 예외를 그 예외에 suppressed로 매단다 — 자바의 try-with-resources와 같은 우선순위 규칙이다.

fun readFirstLine(path: Path): String? =
    Files.newBufferedReader(path).use { it.readLine() }   // 블록을 벗어나면 close

// 자원이 여러 개면 중첩한다 — 안쪽부터 닫히므로 역순 규칙도 그대로다
input.use { i -> output.use { o -> i.copyTo(o) } }

면접에서 덧붙이면 좋은 포인트는 "자바는 문법으로, 코틀린은 고차 함수로 같은 보장을 얻는다"는 대비다. 코틀린은 인라인 람다가 있어 굳이 새 문법을 만들지 않고도 자원 수명을 블록에 묶는 같은 효과를 라이브러리 수준에서 표현할 수 있었다.

한 줄 요약
try-with-resources는 "close를 대신 불러 주는 문법"이 아니라 사람이 finally로는 매번 정확히 할 수 없는 세 가지 — 모든 탈출 경로에서 닫기, 여러 자원을 선언 역순으로 하나도 빠짐없이 닫기, 그리고 close의 예외가 진짜 원인을 덮어쓰지 않게 suppressed로 보존하기 — 를 컴파일러 생성 코드로 보장하는 장치이고, 힙 밖의 자원은 GC가 회수해 주지 않아 누수가 평소엔 조용하다가 피크 트래픽에 풀·파일 디스크립터 고갈로 한꺼번에 터지므로, AutoCloseable 자원(커넥션, 스트림, Files.lines가 돌려주는 Stream, 스트리밍 조회 결과까지)은 예외 없이 이 문법으로 다루고 운영에서는 풀 지표와 leakDetectionThreshold로 누수 지점을 특정하는 절차까지 갖추는 것이 완성형이다.
