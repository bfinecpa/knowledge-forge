제네릭의 타입 소거 — 컴파일러만 아는 타입, 그리고 그 대가
타입 검사를 전부 끝낸 뒤 타입 파라미터를 지우고 꺼내는 자리에 캐스트를 심는다 — 그래서 실행 중인 JVM은 List<String>과 List<Integer>를 구분하지 못한다

면접 질문: "타입 소거란? 런타임에 타입 정보가 없어서 생기는 실무 제약은? 와일드카드(? extends, ? super)의 사용 기준(PECS)은?"

핵심 관전 포인트 — Java 제네릭은 "컴파일러만 아는 타입"이다. 컴파일러가 타입 검사를 전부 끝낸 뒤 타입 파라미터를 지우고(제약이 없으면 Object, T extends Number면 Number로 치환) 값을 꺼내는 자리마다 캐스트를 심는 방식이라, 실행 중인 JVM은 List<String>과 List<Integer>를 구분하지 못한다. Java 5에서 제네릭을 도입할 때 이미 세상에 배포돼 있던 List 코드·바이너리와 그대로 섞여 돌아가야 했기 때문에 선택한 설계이고, 그 대가로 "런타임에 T가 뭔지 알아야 하는 모든 일"이 막힌다 — new T[], instanceof List<String>, 타입 인자만 다른 오버로딩이 전부 불가능하고, raw type으로 검사를 우회하면 힙 오염이 생긴다. 실무에서는 JSON 역직렬화에서 가장 자주 부딪히며, 클래스 선언문의 제네릭 시그니처는 소거되지 않는다는 예외를 이용한 super type token(TypeReference의 익명 하위 클래스)으로 푼다. 그리고 제네릭은 무공변이라 List<String>이 List<Object>의 하위 타입이 아니므로, API 시그니처는 PECS — 읽기만 하는 파라미터는 ? extends, 쓰기만 하는 파라미터는 ? super — 로 유연성을 되찾는다.
  • 1
    소거는 "검사를 끝낸 뒤 지우고, 꺼낼 때 캐스트를 심는" 컴파일러 변환입니다. 바이트코드에 남는 것은 add(Object)·get()Object + checkcast뿐이라 런타임에는 List<String>과 List<Integer>가 같은 클래스입니다. Java 5가 기존 바이너리와 섞여 돌아가는 마이그레이션 호환성을 산 대가입니다.
  • 2
    그래서 런타임에 T를 알아야 하는 일이 전부 막힙니다. new T()·new T[]·instanceof List<String>·타입 인자만 다른 오버로딩이 불가능하고, raw type이나 제네릭 가변인자로 검사를 건너뛰면 원인과 폭발 지점이 어긋나는 힙 오염이 생깁니다. 실무 조우 지점은 JSON 역직렬화이고, 클래스 선언문의 제네릭은 소거되지 않는다는 예외를 쓴 TypeReference(super type token)로 풉니다.
  • 3
    PECS는 무공변이 만든 뻣뻣함을 푸는 장치입니다. 파라미터가 값을 내놓기만 하면 ? extends T, 받아 담기만 하면 ? super T, 둘 다면 T, 반환 타입에는 쓰지 않습니다. Collections.copy(List<? super T> dest, List<? extends T> src) 한 줄에 규칙이 다 들어 있습니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "제네릭의 타입 소거(type erasure)란? 런타임에 타입 정보가 없어서 생기는 실무 제약은? 와일드카드(? extends, ? super)의 사용 기준(PECS)은?"

출제 의도 — 제네릭이 컴파일 타임 전용 장치임을 알아야 런타임 타입 분기가 안 되는 이유, 직렬화 라이브러리가 TypeReference 같은 우회를 쓰는 이유가 이해된다. PECS는 공통 모듈·라이브러리의 API 시그니처를 설계하는 사람과 소비만 하는 사람을 가르는 표지다.

약점 A"컴파일 타임에만 존재하고 런타임에는 지워집니다"에서 끝나는 답 — 문장은 맞지만 무엇이 어떻게 지워지는지를 말하지 못한다. "지운 자리에 캐스트를 심는다"까지 말해야 이후 모든 제약이 연역된다.
약점 B"제네릭 정보가 전부 사라진다"고 단정하는 답 — 인스턴스의 타입 인자는 사라지지만 클래스 선언문의 제네릭 시그니처는 남는다. 이 구분을 못 하면 TypeReference가 왜 동작하는지 설명할 수 없다(가장 잘 갈리는 지점).
약점 C"소거는 Java의 실수"라고 말하는 답 — 마이그레이션 호환성이라는 요구 조건과의 트레이드오프였다. 배경을 모르면 "왜 C#처럼 안 했나" 꼬리질문에서 무너진다.
약점 DPECS를 "생산자는 extends, 소비자는 super"라고 외워서만 답하는 것 — 무공변이라는 전제와 왜 반대쪽이 막히는지를 못 대면 규칙을 암기한 것으로 보인다. 실무 시그니처(Collections.copy, Comparator<? super E>) 한 줄이 붙어야 한다.
합격선"검사를 끝낸 뒤 지우고 캐스트를 심는다"는 메커니즘을 먼저 세우고 → 런타임 제약 목록을 거기서 연역하고 → 힙 오염이라는 뒷문을 짚고 → Signature 속성이라는 예외로 실무 해법(super type token)을 잇고 → 무공변 → PECS로 API 설계까지 닫는 것.
이 문서의 진행 방향 — 메커니즘 한 장에서 전부 연역한다 외울 것은 사실 한 문장이다. "컴파일러가 검사를 전부 끝낸 뒤 타입 파라미터를 지우고, 꺼내는 자리에 캐스트를 심는다." 1~4절에서 이 문장을 바이트코드로 확인하고 왜 이렇게 만들었는지까지 세운 뒤, 5~9절에서 그 청구서(못 하는 일·힙 오염·JSON 역직렬화)를 하나씩 갚는다. 10~12절의 PECS는 소거와는 다른 축이다 — 런타임이 아니라 컴파일 타임에 API를 어떻게 쓰느냐의 문제라는 것을 구분해서 기억한다.

1. 타입 소거란 — 소스 · 컴파일러 · 바이트코드를 나란히

타입 소거를 설명하는 문장은 대개 이렇게 시작한다. "제네릭 타입 정보는 컴파일 타임에만 존재하고 런타임에는 지워진다." 맞는 말이지만 처음 읽으면 아무 실감이 없다. 내가 쓴 List<String>이 어느 순간에 어떻게 사라진다는 것인지가 그려지지 않기 때문이다.

그래서 같은 코드를 세 단계로 나란히 놓고 본다. ① 내가 쓴 소스, ② 컴파일러가 타입 검사를 마친 뒤 만들어내는 코드, ③ 실제로 클래스 파일에 남은 바이트코드.

바이트코드에서 세 줄만 짚는다

이 절에서 외울 한 문장

제네릭의 가치는 "캐스트가 없어졌다"가 아니라
"컴파일러가 검사를 끝낸 뒤에 캐스트를 넣어주므로 그 캐스트가 실패할 수 없다"는 것이다.

결과 — 런타임의 JVM은 두 리스트를 구분하지 못한다

new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()   // true

<String>도 <Integer>도 실행 코드에 남지 않았으니, 두 객체는 똑같이 java.util.ArrayList 클래스의 인스턴스다. 클래스 객체가 하나뿐이므로 ==가 참이다.

비유 — 제네릭은 라벨을 붙이지 않는 공장 검수원 제네릭은 공장 검수원이다. 부품을 조립 라인에 올리기 전에 규격이 맞는지 전부 확인하고, 통과한 것만 상자에 담아 내보낸다. 그런데 상자에는 "String 전용"이라는 라벨을 붙이지 않는다 — 검수를 이미 끝냈으니 라벨이 필요 없다는 판단이다. 검수원이 제대로 일한 한 문제가 없다. 문제는 누군가 검수를 건너뛰고 상자에 물건을 넣을 때(6절 raw type) 생긴다. 라벨이 없으니 아무도 못 막는다.

2. 컴파일러가 하는 일 세 가지 — 지운다 · 캐스트 · 브리지

1절에서 본 변형을 정리하면 컴파일러의 작업은 정확히 셋이다. 이 셋만 기억하면 소거를 처음부터 다시 설명할 수 있다.

1
타입 파라미터를 지운다
경계가 없으면 Object, <T extends Number>면 첫 번째 경계인 Number로 치환한다.
2
꺼내는 자리에 캐스트를 심는다
1절에서 본 checkcast. 검사를 통과한 코드에만 심으므로 실패할 수 없는 캐스트다.
3
브리지 메서드를 만든다
소거 때문에 어긋난 시그니처를 잇는 다리 메서드를 몰래 하나 더 생성한다.

① 무엇으로 지우나 — 경계(bound)가 갈림길이다

경계란 T extends Number처럼 "T는 적어도 이것의 하위 타입이어야 한다"고 적어 둔 상한이다. 경계가 있으면 그것으로, 없으면 Object로 치환한다.

소거 규칙 — 두 줄로 끝난다

<T> → Object
경계가 없으면 최상위 타입
<T extends X> → X
경계가 있으면 첫 번째 경계로 치환 (여럿이면 맨 앞)

③ 브리지 메서드 — 소거가 어긋뜨린 시그니처를 잇는 다리

Comparable<T>는 소거되면 compareTo(Object)가 된다. 그런데 내가 Comparable<Money>를 구현하며 쓴 메서드는 compareTo(Money)다. 시그니처가 다르므로 이대로는 인터페이스를 구현한 것이 되지 않는다. JVM은 compareTo(Object)를 찾는데 클래스에는 compareTo(Money)밖에 없기 때문이다.

이 틈을 메우려고 컴파일러가 compareTo(Object)를 하나 더 만들어 준다. 다리를 놓아 준다고 해서 브리지(bridge) 메서드다.

3. 소거되지 않는 예외 — 클래스 파일의 Signature 속성

2절의 <T extends Number> T first(List<T>)를 javap으로 다시 보면 이상한 점이 하나 보인다.

  static <T extends java.lang.Number> T first(java.util.List<T>);   <- ① 제네릭이 그대로 적혀 있다
    descriptor: (Ljava/util/List;)Ljava/lang/Number;                <- ② 여기는 소거된 모습
                                    ^^^^^^^^^^^^^^^^^
                        T가 Number로 치환됐고, List<T>는 그냥 List가 됐다

descriptor는 소거됐는데 그 위 선언 줄에는 제네릭이 살아 있다. javap이 지어낸 것이 아니다. 클래스 파일에는 실행에 쓰이는 descriptor와 별개로 Signature 속성이라는 자리가 있고, 컴파일러가 원래의 제네릭 선언을 거기에 문자열로 기록해 둔다.

가장 잘 갈리는 한 문장 — 지금 외운다

인스턴스의 타입 인자는 지워지고,
클래스 선언문에 적은 제네릭 시그니처는 남는다.
"실행 중에 흘러가는 정보"는 지워지고 "소스에 고정된 텍스트"는 기록된다
// 남아 있으니 리플렉션으로 읽을 수 있다
Type t = MyRef.class.getGenericSuperclass();
// -> TypeReference<java.util.List<OrderDto>>     살아 있다
Type inner = ((ParameterizedType) t).getActualTypeArguments()[0];
// -> java.util.List<OrderDto>                    전달하고 싶던 바로 그 정보

4. 왜 이렇게 설계했나 — 2004년에 이미 세상에 있던 코드

"C#은 런타임에도 제네릭 타입을 유지하는데 Java는 왜 지웠나"는 질문에는 역사적 배경이 답이다. 결론만 외우면 꼬리질문에서 무너지므로 상황부터 본다.

제네릭이 Java에 들어온 것은 Java 5(2004년)다. Java 1.0이 1996년이니 그 시점에 이미 8년치 코드가 세상에 깔려 있었고, 그 코드들은 전부 이렇게 생겼다.

List list = new ArrayList();          // 타입 인자가 없다. 당시엔 문법 자체가 없었다
list.add("hello");
String s = (String) list.get(0);      // 캐스트는 사람이 직접 썼다

이 상태에서 제네릭을 도입하려면 답해야 하는 질문이 하나 있다. "List<String>은 기존의 List와 같은 것인가, 다른 것인가?" 이 질문의 답에 따라 길이 두 갈래로 갈린다.

"왜 C#처럼 안 했나요?" 30초 답변 골격

  1. 시점 — Java 5는 2004년, Java 1.0은 1996년. 그 사이 8년치 바이너리가 이미 배포돼 있었다.
  2. 요구 — 재컴파일 없이 섞여 돌아가야 한다(마이그레이션 호환성). 소거면 List<String>도 결국 List라 공짜로 성립한다.
  3. C# — 2005년 C# 2.0에서 CLR을 직접 고쳐 실체화를 넣었다. .NET은 2002년생이라 감당할 배포 자산이 훨씬 적었다.
  4. 결론 — "어느 쪽이 옳다기보다 처한 상황이 달랐다"로 닫는다.

5. 소거가 막는 것들 — 컴파일조차 안 되는 코드 7종

지금부터는 청구서다. 규칙은 단 하나 — "런타임에 T가 무엇인지 알아야 하는 일은 전부 막힌다." 아래 일곱 개를 개별로 외우지 말고 이 한 문장에서 매번 다시 만들어내는 것이 목표다.

소거 때문에 컴파일 자체가 안 되는 코드 — 오른쪽 칸이 "왜"의 전부다
못 쓰는 코드막히는 이유그래서 실무에서는
new T()런타임에 T가 무엇인지 모르니 어느 클래스의 생성자를 부를지 결정할 수 없다Supplier<T>나 Class<T>를 파라미터로 받아 getDeclaredConstructor().newInstance()
new T[10]배열은 실행 중에 원소 타입을 기억하고 검사하는데, T를 모르니 기억시킬 타입이 없다내부는 Object[]로 들고 꺼낼 때 캐스트 (ArrayList도 Object[] elementData)
o instanceof List<String>실행 중에는 전부 그냥 List라 <String> 여부를 판정할 수단이 없다o instanceof List<?>만 허용 — 원소 타입은 묻지 않는다
T.class, List<String>.class그런 Class 객체가 아예 존재하지 않는다. List.class 하나뿐이다타입 토큰(Class<T>)이나 super type token(TypeReference)을 넘긴다 → 8절
catch (T e)예외 매칭은 실행 중 타입 비교로 이뤄진다catch (Exception e) 후 Class<T>로 판별하거나 함수형 핸들러로 분리
static 필드에 T 사용static은 클래스당 하나인데 T는 인스턴스마다 다르다인스턴스 필드로 두거나, static 메서드에 자체 타입 파라미터를 선언한다
f(List<String>)과 f(List<Integer>) 오버로딩소거하면 둘 다 f(List)가 되어 시그니처가 충돌한다메서드 이름을 나누거나(fUsers/fOrders) 타입 토큰을 파라미터로 받는다

실제 컴파일 에러 메시지 (JDK 21 기준)

error: generic array creation
    T[] make() { return new T[10]; }

error: Object cannot be safely cast to List<String>
    boolean check(Object o) { return o instanceof List<String>; }

error: non-static type variable T cannot be referenced from a static context
    static T shared;

error: name clash: f(List<Integer>) and f(List<String>) have the same erasure
    void f(List<Integer> a) {}

이 중 셋은 이유를 한 겹 더 들어간다

new T[10]
배열은 제네릭과 반대로 실체화돼 있다. new String[10]은 자기가 String 전용임을 실행 중에도 기억하고 저장할 때마다 JVM이 확인한다. new T[10]은 만드는 시점에 T를 모르니 기억시킬 타입 자체가 없다 — 배열의 자기 검사 기능이 성립하지 않는다.
instanceof List<String>
instanceof는 실행 중에 객체의 실제 클래스를 확인하는 연산이다. 그런데 실행 중의 리스트는 전부 똑같은 ArrayList다. 확인할 근거가 존재하지 않으므로 컴파일러가 문법으로 막는다. List<?>는 "원소 타입은 묻지 않는다"는 뜻이라 판정이 가능해 허용된다.
static 필드의 T
이건 소거와 결이 다른 더 근본적인 모순이다. Box<String>과 Box<Integer>를 만들어도 클래스는 Box 하나이고 static 필드도 하나다. 그런데 T는 인스턴스마다 달라야 한다. 소거가 없더라도 이 모순은 남는다.

6. 힙 오염 — 소거가 열어 둔 뒷문(raw type)

정의부터 정확히 힙 오염(heap pollution)은 List<String>이라고 선언된 변수가 가리키는 실제 객체 안에 String이 아닌 것이 들어가 있는 상태다. "변수의 선언 타입"과 "힙에 놓인 객체의 실제 내용물"이 어긋난 것이고, 그 어긋난 객체가 힙에 존재하므로 힙이 오염됐다고 부른다.

이 상태가 만들어지는 뒷문이 raw type — 타입 인자를 아예 붙이지 않고 쓰는 List 같은 형태다. Java 5 이전 코드와 섞여 돌아가야 했으므로(4절) raw type은 지금도 컴파일 에러가 아니라 경고로만 처리된다.

단계별로 누가 왜 못 막는지
단계무슨 일이 일어나나왜 아무도 못 막나
② 대입strings와 raw가 같은 ArrayList 객체를 가리키게 된다raw type은 "옛날 방식으로 쓰겠다"는 선언이라 경고만 하고 허용한다
③ addInteger 42가 List<String> 안으로 들어간다컴파일러는 raw type이라 검사하지 않고, 런타임은 소거 때문에 이 객체가 String용이었다는 사실 자체를 모른다
③ 직후아무 예외도 안 터진다 — 시한폭탄만 설치된 상태이 순간이 힙 오염이다
④ get컴파일러가 심어 둔 checkcast String에서 터진다꺼낸 것이 Integer이기 때문

대비 — 배열이었다면 넣는 즉시 터진다

제네릭넣을 때 통과, 꺼낼 때 폭발
List<String> strings = new ArrayList<>();
List raw = strings;
raw.add(42);        // 조용히 통과 (힙 오염)
String s = strings.get(0);
// ClassCastException — 한참 뒤, 다른 곳에서
배열넣는 그 줄에서 즉시 폭발
Object[] arr = new String[10];
arr[0] = 42;
// ArrayStoreException: java.lang.Integer
// 원인 줄과 예외 줄이 같다

힙 오염에서 얻을 통찰 두 가지

① 방어선은 컴파일러 하나뿐
컴파일러는 안 봤고(raw type이라서), 런타임은 볼 능력이 없다(소거되어서). 그래서 unchecked 경고를 무시하는 것은 유일한 방어선을 끄는 일이다.
② 원인과 폭발 지점이 어긋난다
원인은 add, 예외는 get. 배열은 넣는 줄에서 터지고 제네릭은 꺼내는 줄에서 터진다 — 둘 다 막긴 하지만 제네릭에는 건너뛸 뒷문이 있다.

7. 제네릭 가변인자와 @SafeVarargs

힙 오염이 raw type 없이도 생기는 자리가 하나 더 있다. 제네릭 가변인자(T... args)다.

가변인자는 컴파일러가 배열을 하나 만들어서 넘기는 문법 설탕이다. 그런데 T...의 T는 소거되므로 실제로 만들어지는 배열은 T[]가 아니라 Object[]다. 여기서 5절의 "제네릭 배열은 못 만든다"는 제약과 정면으로 부딪힌다.

위험배열 참조를 밖으로 내보낸다
// Effective Java의 고전적 예 — 실제로 터진다
static <T> T[] toArray(T... args) { return args; }  // 실체는 Object[]
static <T> T[] pick(T a, T b) { return toArray(a, b); }

public static void main(String[] x) {
    String[] s = pick("a", "b");    // 여기서 터진다
}
warning: [unchecked] Possible heap pollution from parameterized vararg type T
warning: [unchecked] unchecked generic array creation for varargs parameter of type T[]
안전읽기만 하고 내용을 복사해 담는다
@SafeVarargs
static <T> List<T> listOf(T... args) {
    return new ArrayList<>(Arrays.asList(args));
    // 배열을 읽기만 하고, 배열 자체를 내보내지 않는다
}
// JDK가 이 애너테이션을 달고 있는 메서드들
List.of(...)      Arrays.asList(...)      EnumSet.of(...)
// 전부 "내용을 복사해 담기만" 한다

@SafeVarargs의 의미 — 자주 틀리는 지점

"컴파일러가 검사해 줬다"가 아니라
"이 배열에 저장하지 않고, 참조를 밖으로 내보내지도 않는다고 내가 보증한다"는 선언

8. JSON 역직렬화와 super type token

실무에서 소거를 처음 만나는 자리는 대부분 여기다. 컴파일도 되고 역직렬화도 "성공"하는데, 원하는 대로 동작하지 않는다.

List<OrderDto> orders = objectMapper.readValue(json, List.class);
String id = orders.get(0).getId();
// ClassCastException: LinkedHashMap cannot be cast to OrderDto

Jackson은 JSON의 각 객체를 어떤 클래스로 만들지 실행 중에 알아야 한다. 그런데 우리가 넘긴 정보는 List.class 하나뿐이고 거기에는 "원소가 OrderDto다"라는 내용이 없다 — 소거됐기 때문이다. 정보가 없으니 Jackson은 기본값인 LinkedHashMap으로 각 원소를 채운다. 그리고 6절과 똑같은 패턴으로 넣는 시점이 아니라 꺼내 쓰는 시점에 터진다.

해법의 출발점 — 타입 토큰, 그리고 그 한계

단일 타입이면 타입 토큰으로 해결된다

OrderDto order = mapper.readValue(json, OrderDto.class);

타입 토큰(type token) — 타입 정보를 실어 나르는 증표로 Class 객체를 같이 넘기는 것이다. 런타임에 클래스를 알려 줬으므로 잘 동작한다.

제네릭 앞에서는 무력해진다

List<OrderDto>.class 라는 문법이 존재하지 않는다(5절 표).

증표로 쓸 물건 자체를 만들 수 없다. 여기서 막히는 것이 이 문제의 본질이다.

탈출구 — 소거가 못 지우는 곳이 하나 있다

3절에서 기억해 두라고 한 예외가 여기서 쓰인다. 인스턴스의 타입 인자는 지워지지만, 클래스 선언문에 적은 제네릭은 클래스 파일의 Signature 속성에 남는다.

비유 — 물건에는 꼬리표가 안 붙지만, 설계도에 적힌 글자는 남는다 인스턴스의 타입 인자는 실행 중에 흘러가는 정보라 지워지지만, extends 절에 적은 것은 소스에 고정된 텍스트라서 컴파일러가 클래스 파일에 문서처럼 기록해 둔다. 그러니 전달하고 싶은 타입을 extends 절에 적어 둔 일회용 클래스를 만들어 넘기면 된다 — 이것이 트릭의 전부다.
Before원소 타입이 전달되지 않는다
List<OrderDto> orders =
    mapper.readValue(json, List.class);
String id = orders.get(0).getId();
// ClassCastException:
//   LinkedHashMap cannot be cast to OrderDto

// RestTemplate도 같은 함정
List<OrderDto> r = restTemplate.getForObject(url, List.class);
After익명 하위 클래스에 타입을 실어 보낸다
List<OrderDto> orders = mapper.readValue(
        json, new TypeReference<List<OrderDto>>() {});

// Spring도 같은 원리의 전용 타입을 제공한다
ResponseEntity<List<OrderDto>> res = restTemplate.exchange(
        url, HttpMethod.GET, null,
        new ParameterizedTypeReference<List<OrderDto>>() {});
주의 — 만능이 아니다. extends 절에 구체 타입을 적을 때만 동작한다 
<T> List<T> parse(String json) {
    return mapper.readValue(json, new TypeReference<List<T>>() {});   // 동작하지 않는다
    // 클래스 파일에 박히는 것은 문자 그대로 "List<T>"이고,
    // T가 실제로 무엇인지는 여전히 어디에도 없다
}
이런 경우에는 우회할 방법이 없다. 호출자에게서 타입 토큰을 파라미터로 넘겨받아야 한다(Class<T> type 또는 JavaType·TypeReference를 그대로 받는다).

9. 캐시 · 프레임워크 — 같은 문제의 다른 얼굴

9-1. 캐시 계층 — 같은 문제인데 더 멀리서 터진다

Redis 등에 JSON으로 저장한 제네릭 컬렉션을 꺼낼 때 8절과 완전히 같은 문제가 재현된다. 역직렬화기가 원소 타입을 모르므로 List<LinkedHashMap>이 돌아온다. 캐시에서 더 고약한 것은 두 가지다.

① 터지는 위치가 더 멀다
캐시 조회는 성공으로 끝나고, 한참 뒤 DTO 필드에 접근하는 지점에서 ClassCastException이 난다. "이게 캐시 문제였구나"를 알아채기까지 시간이 걸린다.
② 캐시가 채워진 뒤에만 재현된다
캐시 미스일 때는 원본 조회 경로를 타서 멀쩡히 동작한다. 로컬에서는 안 나고 운영에서만, 그것도 워밍업 이후에만 나는 성격이 붙는다.

예방 — 캐시 값의 타입을 설계 단계에서 명시한다

  • 타입별로 캐시 매니저(직렬화기)를 나눈다 — 캐시 이름마다 값 타입이 고정되므로 역직렬화기가 헤맬 여지가 없다.
  • 컬렉션을 감싼 래퍼 DTO를 캐시 단위로 쓴다 — List<OrderDto> 대신 OrderList처럼 필드 선언에 제네릭이 박힌 클래스를 저장하면 Signature 속성이 살아 있어(3절) 원소 타입이 전달된다.
  • 직렬화 시 타입 정보를 함께 기록한다(Jackson의 activateDefaultTyping 계열) — 단, 역직렬화 시 임의 클래스를 만들 여지가 있어 보안상 신중해야 한다.

9-2. 프레임워크·공용 유틸을 만들 때

소거가 만드는 제약과 실무 관용구
막히는 것관용구
타입별 분기가 안 된다instanceof List<String>이 불가능하므로 Class<T>를 파라미터로 명시적으로 받는다. public <T> T fromJson(String json, Class<T> type) — 타입을 값으로 받아 오는 것이다.
제네릭 배열을 못 만든다컬렉션·유틸 내부에서는 (T[]) new Object[n] 같은 unchecked 캐스트가 불가피하다. 이 캐스트는 배열이 밖으로 새어 나가지 않는다는 전제에서만 안전하다 — 7절 @SafeVarargs의 조건과 같은 이야기다.
타입 인자만 다른 오버로딩이 안 된다process(List<UserDto>)와 process(List<OrderDto>)를 나란히 둘 수 없다. 메서드 이름을 나누거나(processUsers/processOrders) 타입 토큰을 파라미터로 받아 구분한다.
반대로 — 남아 있는 시그니처를 이용하는 쪽Spring이 List<UserHandler> 같은 제네릭 빈 주입을 해내는 것이 그렇다. 주입 지점(필드·생성자 파라미터)의 시그니처에 적힌 제네릭은 클래스 메타데이터에 남으므로, Spring은 그것을 ResolvableType으로 읽어 어떤 타입의 빈을 모아 넣을지 판단한다. 8절 TypeReference와 정확히 같은 원리다.

10. 무공변 — 배열은 공변, 제네릭은 무공변

여기서부터는 축이 바뀐다 소거가 "런타임에 못 하는 일"이라면, 지금부터는 "컴파일 타임에 API를 어떻게 써야 유연해지는가"의 문제다. 두 축을 섞어 말하면 답변이 흐려지므로 구분해서 기억한다. 출발점은 리스코프 치환이 제네릭에서는 성립하지 않는다는 사실이다.

10-1. 전제 — List<String>은 List<Object>의 하위 타입이 아니다

리스코프 치환 원칙(LSP)은 "하위 타입은 상위 타입이 오는 자리에 대신 들어갈 수 있어야 한다"는 규칙이다. String은 Object의 하위 타입이므로 Object를 받는 자리에 String을 넘길 수 있다. 그렇다면 List<String>도 List<Object> 자리에 들어갈 수 있을까? 직관은 "그렇다"고 답하지만 컴파일러는 거부한다.

List<Integer> ints = List.of(1, 2, 3);
double total = sum(ints);
// error: incompatible types: List<Integer> cannot be converted to List<Number>

왜 막는지는 허용했다고 가정해 보면 바로 드러난다.

List<String> names = new ArrayList<>();
List<Object> objs = names;      // 가정: 이 대입이 허용된다면
objs.add(42);                   // objs는 Object 리스트니까 Integer도 넣을 수 있다
String s = names.get(0);        // 같은 객체인데 Integer가 나온다 -> ClassCastException

허용하는 순간 6절의 힙 오염이 raw type 없이도 만들어진다. 그래서 제네릭은 무공변(invariant)으로 설계됐다 — 타입 인자가 조금이라도 다르면 서로 아무 관계도 아니라는 뜻이다.

11. 와일드카드와 PECS — 파라미터가 하는 일로 고른다

11-1. 무공변의 대가 — API가 뻣뻣해진다

무공변은 안전하지만 너무 뻣뻣하다. 방금 본 예제를 다시 보자.

// Before: 무공변 때문에 호출자가 좁아진다
public static double sum(List<Number> numbers) {
    double total = 0;
    for (Number n : numbers) total += n.doubleValue();   // 읽기만 한다
    return total;
}

List<Integer> ints = List.of(1, 2, 3);
sum(ints);   // 컴파일 에러: List<Integer> cannot be converted to List<Number>

이 메서드는 리스트에서 값을 꺼내 읽기만 한다. List<Integer>를 받아도 안전하다는 것을 사람은 알 수 있다. 그런데 시그니처가 List<Number>라 컴파일러는 거부하고, List<Integer>·List<Double>·List<BigDecimal>용 메서드를 따로 만들 수도 없다(5절 오버로딩 제약).

와일드카드 ?의 의미 — 이 한 줄이 전부의 열쇠다 ?는 "어떤 타입인지는 모르지만 하나로 고정된 어떤 타입"이라는 뜻이다. 여기에 경계를 붙여 범위를 좁힌다.
? extends Number
Number이거나 그 하위 타입 중 하나인데, 어느 것인지는 모른다
? super Integer
Integer이거나 그 상위 타입 중 하나인데, 어느 것인지는 모른다
"어느 것인지는 모른다"에서 무엇이 되고 무엇이 안 되는지가 전부 결정된다.

11-2. 방향 하나로 읽는 그림 — 왜 한쪽만 막히나

에러 메시지의 CAP#1이 컴파일러의 사고를 그대로 보여준다 
error: incompatible types: int cannot be converted to CAP#1
    src.add(1);
            ^
  where CAP#1 is a fresh type-variable:
    CAP#1 extends Number from capture of ? extends Number
CAP#1은 컴파일러가 "이 자리의 실제 타입 인자"에 임시로 붙인 이름이다(capture, 포획). 이름은 붙였지만 정체는 모르므로 그 자리에 넣을 값을 만들어 낼 방법이 없다. 예외는 null 하나뿐이다 — null은 모든 참조 타입의 값이라 무엇이든 상관없기 때문이다.

11-3. PECS — 파라미터가 하는 일을 보고 고른다

PECS: Producer-Extends, Consumer-Super

파라미터가 읽기 전용이면 ? extends · 쓰기 전용이면 ? super
둘 다 하면 T · 반환 타입이면 와일드카드를 쓰지 않는다

11-4. JDK 시그니처를 이 눈으로 다시 읽는다

// src에서 읽어 dest에 쓴다. src는 생산자, dest는 소비자 — PECS가 한 줄에 다 들어 있다
public static <T> void copy(List<? super T> dest, List<? extends T> src)

// coll에서 원소를 꺼내 비교만 한다 — 생산자
public static <T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll)

// mapper는 T를 받아(소비) R을 내놓는다(생산)
<R> Stream<R> map(Function<? super T, ? extends R> mapper)

// 정렬기는 리스트의 원소를 받아 비교한다 — 원소의 소비자
void sort(Comparator<? super E> c)

마지막 Comparator<? super E>가 실무에서 가장 자주 마주치는 형태다. 이 ? super 덕분에 상위 타입용으로 만들어 둔 비교기를 하위 타입 리스트 정렬에 재사용할 수 있다.

Comparator<Object> byString = Comparator.comparing(Object::toString);

List<String> names = new ArrayList<>(List.of("b", "a"));
names.sort(byString);   // Comparator<String>이 아닌데도 통과한다
// 시그니처가 Comparator<E>였다면 여기서 컴파일 에러가 났을 것이다

11-5. before/after — 바뀌는 것은 시그니처 한 줄뿐이다

Before호출자가 정확히 그 타입으로만 리스트를 만들어야 한다
public static double sum(List<Number> numbers)
public static void collectIds(List<Long> dst, List<Order> orders)

// 호출부
List<Integer> ints = List.of(1, 2, 3);
sum(ints);                // 컴파일 에러
List<Object> log = new ArrayList<>();
collectIds(log, orders);  // 컴파일 에러
After파라미터가 하는 일에 맞춰 와일드카드를 붙인다
public static double sum(List<? extends Number> numbers)   // 읽기만
public static void collectIds(List<? super Long> dst, ...)  // 쓰기만

// 호출부 — 한 글자도 바뀌지 않았다
List<Integer> ints = List.of(1, 2, 3);
sum(ints);                // 통과
List<Object> log = new ArrayList<>();
collectIds(log, orders);  // 통과

이 변경의 비용 구조 — 면접에서 한 줄 더 붙일 포인트

와일드카드는 API를 만드는 쪽이 감당하고, 쓰는 쪽은 이득만 본다.
호출자 코드는 한 글자도 바뀌지 않고, 바뀌는 것은 "어떤 리스트를 넘길 수 있느냐"뿐이다 — 그래서 공용 모듈일수록 챙길 가치가 크다

12. 와일드카드를 쓰면 안 되는 자리 · 캡처 도우미

12-1. 반환 타입에는 쓰지 않는다 — 전염되기 때문이다

반환 타입에 와일드카드가 있으면 그것을 받는 쪽 변수에도 와일드카드가 따라붙고, 그 변수를 넘기는 다음 메서드에도 번져 나간다. 유연성을 주는 게 아니라 호출자 코드 전체에 와일드카드를 전염시킨다.

// 이렇게 하지 않는다
public static List<? extends Number> loadAll() { ... }

List<? extends Number> ns = loadAll();
ns.add(BigDecimal.ONE);   // 호출자는 이제 아무것도 넣을 수 없다
와일드카드는 "받는 쪽(파라미터)"의 문법이다 — 파라미터에 쓰면 받을 수 있는 것이 넓어지고, 반환 타입에 쓰면 호출자가 할 수 있는 것이 좁아진다.

12-2. 여러 자리를 같은 타입으로 묶어야 하면 와일드카드로는 안 된다 가산점

?는 "이름 없는 하나의 타입"이라 두 자리가 같은 타입이라는 것을 표현하지 못한다. 그래서 다음 코드는 컴파일되지 않는다.

컴파일 에러?에는 아무것도 넣을 수 없다
public static void swap(List<?> list, int i, int j) {
    list.set(i, list.set(j, list.get(i)));
    // error: incompatible types:
    //   Object cannot be converted to CAP#1
}

사람은 "같은 리스트니 당연히 같은 타입"이라고 알지만, 컴파일러에게는 get이 준 CAP#1과 set이 요구하는 CAP#1이 같다는 것을 표현할 문법이 없다.

캡처 도우미와일드카드에 이름을 붙여 준다
// 공개 시그니처는 와일드카드로 유연하게 두고
public static void swap(List<?> list, int i, int j) {
    swapHelper(list, i, j);   // 여기서 ?가 T로 포획된다
}
// 내부에서는 T라는 이름이 생겨 같은 타입임을 표현할 수 있다
private static <T> void swapHelper(List<T> list, int i, int j) {
    list.set(i, list.set(j, list.get(i)));
}

와일드카드 판단 순서 — 이 네 줄이면 끝난다

1
파라미터가 값을 꺼내 읽기만 하는가 → ? extends T
생산자
2
파라미터가 값을 받아 담기만 하는가 → ? super T
소비자
3
둘 다 하는가 → 와일드카드를 쓰지 않고 List<T>
불가
4

금지

13. 대비 — Kotlin reified, C# 실체화

Kotlin은 JVM 위에서 돌아가므로 기본은 Java와 같은 소거다. 다만 inline fun <reified T>라는 탈출구가 있다. inline 함수는 호출 지점에 함수 본문이 그대로 복사되는데, 그때 T 자리에 실제 타입이 문자 그대로 박힌다. 그래서 T::class, is T가 가능해진다.

// Jackson의 Kotlin 확장 — TypeReference 없이 동작하는 이유가 reified다
val orders: List<OrderDto> = objectMapper.readValue(json)
Kotlin reified — 소거를 없앤 것이 아니다

4절에서 본 대로 CLR을 고쳐 실체화를 넣었으므로 typeof(T), 제약이 있으면 new T()가 그냥 된다. 대가는 그 시점에 런타임을 고쳤다는 것이다.

코드 리뷰 체크리스트 — 이 문서의 내용을 실제 코드에서 잡아내는 법

  • raw type이 있는가 — List, Map처럼 타입 인자 없는 선언. 없애거나 최소한 List<?>로 바꾼다.
  • unchecked 경고를 통째로 억제하고 있지 않은가 — @SuppressWarnings("unchecked")가 클래스나 메서드 전체에 붙어 있으면 변수 선언 단위로 좁히고 이유를 주석으로 남긴다.
  • readValue(..., List.class) / getForObject(..., List.class) — 컬렉션·제네릭 반환에 .class를 쓰는 자리는 전부 타입 토큰으로 교체한다.
  • 캐시에 컬렉션을 넣고 있지 않은가 — 값 타입이 고정된 캐시 매니저 또는 래퍼 DTO로 바꾼다.
  • T... 파라미터가 있는가 — 배열에 저장하거나 반환하지 않는지 확인하고, 안전하면 @SafeVarargs를 붙여서 의도를 명시한다.
  • 공용 유틸의 컬렉션 파라미터에 와일드카드가 빠져 있지 않은가 — 읽기 전용이면 ? extends, 쓰기 전용이면 ? super.
  • 리플렉션으로 메서드를 순회하는가 — isBridge() 필터가 있는지 확인한다(2절).

15. 꼬리질문 셀프 테스트 (15문항)

사용법 — 펼치기 전에 소리 내어 답해 본다 질문만 먼저 읽고 30초 안에 입으로 답을 만들어 본 뒤 펼쳐서 대조한다. 막힌 문항은 옆에 적힌 절로 돌아가 그림 한 장만 다시 본다. 검은 배지는 시니어 변별 포인트, 빨간 배지는 많이 틀리는 함정이다.
소거되는데 컴파일러는 어떻게 타입 안전을 보장하나요?힌트: 검사와 실행의 시간 차이 (→ 1·2절)

검사가 전부 컴파일 타임에 끝나기 때문이다. 컴파일러가 모든 add·get의 타입을 확인하고, 통과한 코드에만 캐스트(checkcast)를 심은 뒤 타입 파라미터를 지운다. 검사를 이미 통과했으므로 그 캐스트는 실패할 수 없다. 제네릭의 가치는 "캐스트가 없어졌다"가 아니라 "실패할 수 없는 캐스트를 컴파일러가 대신 써 준다"는 것이다.

뒤집으면 컴파일러 검사가 유일한 방어선이라는 뜻이기도 하다. raw type이나 unchecked 캐스트로 검사를 건너뛰면 런타임은 아무것도 막아주지 못한다(힙 오염, 6절). 그래서 unchecked 경고는 지우지 말고, 안전하다고 확신할 때만 @SuppressWarnings("unchecked")를 가능한 가장 좁은 범위(변수 선언 단위)에 붙이고 왜 안전한지 주석을 남기는 것이 관행이다.

런타임에 제네릭 정보가 "전부" 사라지나요? new TypeReference<List<OrderDto>>() {}의 {}는 왜 붙나요?시니어 변별힌트: 인스턴스 vs 클래스 메타데이터 (→ 3·8절)

아니다. 이 구분을 못 하면 TypeReference를 설명할 수 없다.

  • 인스턴스는 타입 인자를 모른다. new ArrayList<String>()으로 만든 객체는 자기가 String용이라는 사실을 어디에도 갖고 있지 않다.
  • 클래스 메타데이터의 제네릭 시그니처는 남는다. 필드 선언, 메서드 선언, extends/implements 절에 적은 제네릭은 클래스 파일의 Signature 속성에 문자열로 기록되고 리플렉션으로 읽을 수 있다.

차이는 "실행 중에 흘러가는 정보인가, 소스에 고정된 텍스트인가"다. 전자는 지워지고 후자는 남는다.

그래서 {}가 필요하다. {}는 문법 장식이 아니라 "이름 없는 하위 클래스를 하나 정의하라"는 명령이다. 컴파일하면 호출클래스$1.class가 실제로 생기고 그 파일에 "부모는 TypeReference<List<OrderDto>>"가 기록된다. Jackson은 넘겨받은 객체의 getClass().getGenericSuperclass()로 그 기록을 읽는다. {}를 빼면 클래스 파일이 안 생기므로 타입을 실을 곳이 사라진다(TypeReference가 추상 클래스라 애초에 컴파일도 안 된다).

new ArrayList<String>().getClass() == new ArrayList<Integer>().getClass()의 결과와 이유는?힌트: 클래스 객체는 몇 개인가 (→ 1절)

true다. <String>도 <Integer>도 실행 코드에 남지 않았으므로 두 객체는 똑같이 java.util.ArrayList 클래스의 인스턴스다. ArrayList에 대응하는 Class 객체는 클래스로더당 하나뿐이므로 ==가 참이다.

이 한 줄이 런타임 타입 분기가 불가능한 이유의 전부다. instanceof List<String>이 막히는 것도, List<String>.class가 존재하지 않는 것도, f(List<String>)과 f(List<Integer>) 오버로딩이 충돌하는 것도 전부 여기서 나온다.

<T extends Number>는 무엇으로 소거되나요? 왜 Object가 아닌가요?힌트: 소거 후에도 doubleValue()가 호출돼야 한다 (→ 2절)

첫 번째 경계인 Number로 치환된다. 경계가 없는 <T>만 Object가 된다.

이유는 메서드 호출이 바이트코드에서도 성립해야 하기 때문이다. T 자리에 무엇이 오든 최소한 Number이므로, Number로 적어 두면 n.doubleValue() 호출이 그대로 유효하다. Object로 지워 버리면 그 호출이 깨진다.

// 소스
static <T extends Number> T first(List<T> list)
// descriptor(실행에 쓰이는 시그니처)
(Ljava/util/List;)Ljava/lang/Number; <- T가 Number로 치환

경계가 여럿인 <T extends Number & Comparable<T>>도 맨 앞 경계(Number)로 소거된다. 나머지 경계에 속한 메서드를 호출하는 자리에는 컴파일러가 필요한 캐스트를 따로 심는다.

브리지 메서드는 왜 생기고, 실무에서 언제 문제가 되나요?힌트: 리플렉션으로 메서드를 훑을 때 (→ 2절)

소거 때문에 시그니처가 어긋나서다. Comparable<T>는 소거되면 compareTo(Object)인데, 내가 구현한 것은 compareTo(Money)다. JVM 관점에서는 완전히 다른 메서드라 이대로는 인터페이스를 구현한 것이 되지 않는다. 그래서 컴파일러가 compareTo(Object)를 하나 더 만들어 인자를 캐스트한 뒤 진짜 메서드로 위임한다. 다리를 놓아 준다고 해서 브리지다.

결과적으로 소스에는 메서드가 하나인데 클래스 파일에는 둘이다. 리플렉션으로 메서드 목록을 뽑았을 때 같은 이름이 두 개 보이는 이유가 이것이다.

문제가 되는 자리는 애너테이션 기반 프레임워크나 AOP를 직접 만들 때다. getDeclaredMethods()로 훑으면 하나뿐인 메서드가 둘로 잡혀 같은 처리를 두 번 하게 된다. 그래서 Method.isBridge()가 true인 것을 걸러내야 한다(Spring의 BridgeMethodResolver가 하는 일도 이것이다).

배열은 되는데 제네릭 배열(new T[10])은 왜 안 되나요?힌트: 두 가지 이유가 얽혀 있다 (→ 5·10절)

첫째, 배열은 실체화(reified)되어 있다. 배열 객체는 자기 원소 타입을 실행 중에도 기억하고 저장할 때마다 검사한다(그래서 ArrayStoreException이 존재한다). new T[10]을 지원하려면 만드는 순간 T를 알아야 하는데, 소거 때문에 기억시킬 타입 자체가 없다.

둘째, 배열은 공변이고 제네릭은 무공변이라 섞이면 안전성이 무너진다. new T[]가 허용되면 그 배열을 Object[]에 대입하고 아무 값이나 넣는 경로가 열린다. 7절의 제네릭 가변인자 사고가 바로 이 조합이 실제로 만들어 내는 결과다.

그래서 컬렉션 구현체 내부는 Object[]를 들고 꺼낼 때 캐스트하는 관용구를 쓰고(ArrayList 내부도 Object[] elementData다), Effective Java는 배열보다 리스트를 권한다.

힙 오염은 정확히 어떤 상태이고, 왜 추적이 어렵나요?힌트: 원인 줄과 예외 줄이 다르다 (→ 6절)

List<String>이라고 선언된 변수가 가리키는 실제 객체 안에 String이 아닌 것이 들어 있는 상태다. "변수의 선언 타입"과 "힙에 놓인 객체의 실제 내용물"이 어긋났고, 그 어긋난 객체가 힙에 있으니 힙이 오염됐다고 부른다.

추적이 어려운 이유는 터지는 위치와 원인 위치가 다르기 때문이다. 원인은 raw type으로 add한 줄인데, 예외는 한참 뒤 get에서 컴파일러가 심어 둔 checkcast가 실패하며 난다. 실무에서 이 둘은 다른 클래스, 다른 모듈, 심지어 다른 날일 수 있고, 스택트레이스는 무고한 get 쪽만 가리킨다.

대비를 함께 말하면 좋다. 배열은 실체화돼 있어 arr[0] = 42; 하는 그 줄에서 ArrayStoreException으로 잡아낸다. 제네릭은 컴파일에 잡고 배열은 실행에 잡는데, 제네릭에는 검사를 건너뛸 뒷문(raw type)이 있다는 것이 결정적 차이다.

@SafeVarargs는 무엇을 보장하나요? 붙여도 되는 조건은?함정힌트: 컴파일러가 검사해 주는 것이 아니다 (→ 7절)

컴파일러가 검사해 준다는 뜻이 아니다. "이 메서드는 안전하다고 내가 보증하니 경고를 끄라"는 개발자의 선언이다. 보증 내용은 둘이다.

  • 가변인자 배열에 아무것도 저장하지 않는다 (읽기만 한다).
  • 그 배열의 참조를 밖으로 내보내지 않는다 (반환하거나 다른 곳에 대입하지 않는다).

이 조건이 필요한 이유는 T...가 만드는 실제 배열이 T[]가 아니라 소거된 Object[]이기 때문이다. 그 배열이 밖으로 새어 나가 String[]에 대입되는 순간 ClassCastException: [Ljava.lang.Object; cannot be cast to [Ljava.lang.String;이 호출자 쪽에서 터진다.

두 조건 중 하나라도 어기면 애너테이션이 거짓말이 된다. static <T> T[] toArray(T... args) { return args; }는 절대 붙이면 안 되는 전형이다. List.of, Arrays.asList, EnumSet.of가 이 애너테이션을 달고 있는 이유는 내용을 복사해 담기만 하기 때문이다.

List<?>, List<Object>, raw List는 어떻게 다른가요?시니어 변별힌트: 검사를 하느냐, 안 하느냐, 못 하느냐 (→ 6·11절)
형태의미넣기꺼내기안전성
List<?>원소 타입이 어떤 하나로 고정돼 있는데 그게 뭔지 모른다불가 (null만)Object로만타입 안전 — 컴파일러가 검사한다
List<Object>원소 타입이 정확히 Object인 리스트무엇이든 가능Object로타입 안전 — 단 List<String>을 대입할 수 없다(무공변)
raw List제네릭 검사 자체를 포기한 옛날 방식무엇이든 가능Object로위험 — 검사를 안 하므로 힙 오염의 뒷문

핵심은 List<?>는 "모른다"이고 raw List는 "안 본다"라는 것이다. 모르기 때문에 컴파일러가 넣기를 막아 안전을 지키는 쪽이 List<?>이고, 안 보기 때문에 아무거나 들어가 사고가 나는 쪽이 raw type이다. 그래서 "타입을 신경 안 쓰는 컬렉션 파라미터"에는 raw type이 아니라 반드시 List<?>를 쓴다.

List<? extends Number>에 null만 넣을 수 있는 이유는? 에러의 CAP#1은 뭔가요?힌트: "하나로 고정됐지만 어느 것인지 모른다" (→ 11절)

? extends Number는 "Number의 하위 타입 중 하나인데, 그게 어느 것인지는 모른다"는 뜻이다. 실제로는 List<Integer>일 수도, List<Double>일 수도 있다. 여기에 Integer를 넣었는데 실제가 List<Double>이면 힙 오염이다. 무엇을 넣어야 맞는지 결정할 수 없으니 전부 막는다.

null만 예외인 이유는 null은 모든 참조 타입의 값이라 실제 타입이 무엇이든 문제가 없기 때문이다.

error: incompatible types: int cannot be converted to CAP#1
  where CAP#1 is a fresh type-variable:
    CAP#1 extends Number from capture of ? extends Number

CAP#1은 컴파일러가 "이 자리의 실제 타입 인자"에 임시로 붙인 이름이다(capture, 포획). 이름은 붙였지만 정체는 모르므로 그 자리에 넣을 값을 만들어 낼 방법이 없다 — 에러 메시지가 컴파일러의 사고 과정을 그대로 보여주는 셈이다.

swap(List<?> list, int i, int j)는 왜 컴파일 에러이고, 캡처 도우미로 어떻게 푸나요?가산점힌트: ?는 두 자리가 같은 타입임을 표현하지 못한다 (→ 12절)

list.set(i, list.get(j))는 꺼낸 것을 같은 리스트에 다시 넣는 동작이다. 사람은 "같은 리스트니 당연히 같은 타입"이라고 알지만, ?는 이름 없는 하나의 타입이라 컴파일러 입장에서 get이 돌려준 CAP#1과 set이 요구하는 CAP#1이 같다는 것을 표현할 문법이 없다. 그래서 Object cannot be converted to CAP#1이 난다.

해법은 와일드카드에 이름을 붙여 주는 것이다. 제네릭 메서드로 위임하면 그 순간 T라는 이름이 생겨 두 자리가 같은 타입임을 표현할 수 있다.

// 공개 시그니처는 와일드카드로 유연하게 두고
public static void swap(List<?> list, int i, int j) {
    swapHelper(list, i, j);   // 여기서 ?가 T로 "포획"된다
}
// 내부에서는 T라는 이름이 생겨 같은 타입임을 표현할 수 있다
private static <T> void swapHelper(List<T> list, int i, int j) {
    list.set(i, list.set(j, list.get(i)));
}

설계 의도까지 말하면 완성이다. 공개 API는 와일드카드로 넓게, 구현은 타입 파라미터로 정확하게 — 호출자는 아무 List나 넘길 수 있고 구현부는 타입 안전을 유지한다.

왜 C#처럼 실체화 제네릭으로 만들지 않았나요? Kotlin의 reified는 소거를 없앤 건가요?힌트: 2004년 · 인라인 복사 (→ 4·13절)

시점의 문제였다. 제네릭이 들어간 Java 5는 2004년이고 Java 1.0은 1996년이다. 그 8년 동안 raw type 기반 코드와 컴파일된 바이너리가 세상에 쌓여 있었다. 실체화를 하려면 JVM을 고쳐야 하고, 기존 바이트코드가 새 타입 체계에서 어떤 위치인지가 애매해진다.

소거를 택하면 List<String>도 결국 같은 List 클래스이므로 기존 라이브러리를 재컴파일하지 않고 섞어 쓸 수 있고, 표준 라이브러리를 제네릭화해도 기존 호출부가 그대로 컴파일된다. 이 마이그레이션 호환성이 런타임 타입 능력보다 우선순위가 높다고 판단한 것이다. C#은 2005년(C# 2.0)에 CLR을 고쳐 실체화를 넣었는데, .NET이 2002년에 나온 신생 플랫폼이라 감당해야 할 배포 자산이 훨씬 적었다. 어느 쪽이 옳다기보다 처한 상황이 달랐다로 정리하는 편이 정확하다.

이어서 Kotlin을 묻는 경우가 많은데, reified도 소거를 없앤 것이 아니다. Kotlin 역시 JVM 위에서 돌아가므로 기본은 같은 소거다. inline fun <reified T>는 함수 본문이 호출 지점에 그대로 복사되면서 T 자리에 실제 타입이 문자 그대로 박히는 컴파일 트릭이다. 증거는 제약 자체다 — reified는 inline 함수에서만 쓸 수 있고 클래스의 타입 파라미터에는 붙일 수 없다. 인라인될 자리가 없으면 트릭이 성립하지 않기 때문이다.

PECS를 실무 시그니처로 설명해 보세요.시니어 변별힌트: 전제(무공변)부터 깔고 시작한다 (→ 10·11절)

전제부터 깐다. 제네릭은 무공변이라 List<Integer>를 List<Number> 자리에 넘길 수 없다. 허용하면 그 리스트에 Double을 넣는 경로가 열려 힙 오염이 되기 때문이다. 그래서 안전하지만 뻣뻣하다.

와일드카드가 그 뻣뻣함을 푸는 장치이고, 어느 쪽을 쓸지는 그 파라미터가 메서드 안에서 무엇을 하는지로 정한다.

  • 값을 꺼내 읽기만 하면 생산자 → ? extends T. 실제 타입이 무엇이든 T의 하위 타입이라 읽어서 T에 담는 것은 항상 안전하고, 무엇을 넣어야 맞는지는 알 수 없어 쓰기가 막힌다.
  • 값을 받아 담기만 하면 소비자 → ? super T. 실제 타입이 무엇이든 T의 상위 타입이라 T를 넣는 것은 항상 안전하고, 꺼내면 Object까지만 보장된다.
  • 읽고 쓰기를 둘 다 하면 와일드카드를 쓰지 않고 List<T>로 둔다.
// 한 시그니처 안에 소비자와 생산자가 나란히 — PECS의 교과서
public static <T> void copy(List<? super T> dest, List<? extends T> src)
// 실무에서 가장 자주 만나는 형태
void sort(Comparator<? super E> c) // 상위 타입용 비교기를 하위 타입 리스트에 재사용

"반환 타입에는 쓰지 않는다"는 단서까지 붙이면 완성이다. 그리고 한 줄 더 — 이 변경으로 호출자 코드는 한 글자도 바뀌지 않고 받을 수 있는 타입만 넓어진다. 즉 와일드카드는 API를 만드는 쪽이 감당하고 쓰는 쪽은 이득만 보는 비용 구조라서, 공용 모듈일수록 챙길 가치가 크다.

반환 타입에 와일드카드를 쓰면 왜 안 되나요?힌트: 전염된다 (→ 12절)

반환 타입에 와일드카드가 있으면 그것을 받는 쪽 변수에도 와일드카드가 따라붙고, 그 변수를 넘기는 다음 메서드로 계속 번져 나간다. 유연성을 주는 게 아니라 호출자 코드 전체에 제약을 전염시킨다.

// 이렇게 하지 않는다
public static List<? extends Number> loadAll() { ... }

List<? extends Number> ns = loadAll();
ns.add(BigDecimal.ONE);   // 호출자는 이제 아무것도 넣을 수 없다

기억하는 방식은 간단하다. 와일드카드는 "받는 쪽(파라미터)"의 문법이다. 파라미터에 쓰면 받을 수 있는 것이 넓어지고, 반환 타입에 쓰면 호출자가 할 수 있는 것이 좁아진다 — 방향이 정반대다.

Spring은 List<UserHandler> 같은 제네릭 빈 주입을 소거된 환경에서 어떻게 해내나요?가산점힌트: TypeReference와 같은 원리 (→ 3·9절)

주입 지점의 시그니처가 클래스 메타데이터에 남아 있기 때문이다. 필드 선언이나 생성자 파라미터에 적은 List<UserHandler>는 소스에 고정된 텍스트라서 클래스 파일의 Signature 속성에 기록된다. Spring은 이것을 ResolvableType으로 읽어 어떤 타입의 빈을 모아 넣을지 판단한다.

즉 TypeReference·ParameterizedTypeReference·Gson과 Guava의 TypeToken·Spring의 제네릭 빈 주입이 전부 같은 예외 한 줄("클래스 선언에 적은 제네릭은 소거되지 않는다")을 이용한다. 이 공통점을 짚으면 개별 API를 외운 것이 아니라 원리를 안다는 인상을 준다. 같은 원리로 @Bean 메서드의 반환 타입 제네릭이나 ResponseEntity<List<Dto>>의 변환도 해석된다.

한 줄 요약
타입 소거는 컴파일러가 제네릭 타입 검사를 전부 끝낸 뒤 타입 파라미터를 경계(없으면 Object)로 치환하고 꺼내는 자리에 캐스트를 심어 바이트코드에는 타입 인자를 남기지 않는 Java 5의 마이그레이션 호환성 설계이고, 그 대가로 new T[]·instanceof List<String>·타입 인자만 다른 오버로딩이 막히며 raw type이나 제네릭 가변인자로 검사를 우회하면 원인과 폭발 지점이 어긋나는 힙 오염이 생긴다 — 실무에서는 JSON 역직렬화에서 List.class로 원소 타입을 전달하지 못해 LinkedHashMap이 돌아오는 문제로 가장 자주 만나고, "클래스 선언문의 제네릭 시그니처는 소거되지 않는다"는 예외를 이용한 super type token(TypeReference의 익명 하위 클래스)으로 풀며, 여기에 더해 제네릭이 무공변이라 생기는 API의 뻣뻣함은 읽기 전용 파라미터에 ? extends, 쓰기 전용 파라미터에 ? super를 붙이는 PECS로 푸는 것까지가 이 질문의 완성형이다.
