Optional — null을 대체하는 범용 타입이 아니라, 반환 전용 컨테이너다
"이 메서드는 결과가 없을 수도 있다"는 사실을 시그니처에 적어 넣기 위한 장치다. 그 사실을 건네주는 순간에만 의미가 있으므로, 보관하는 자리(필드)와 받는 자리(파라미터)에서는 손해만 남는다.

면접 질문: "Optional을 필드나 메서드 파라미터에 쓰지 말라는 권고의 이유는? 실무에서 Optional의 올바른 사용 범위는 어디까지인가요?"

핵심 관전 포인트 — Optional은 "null을 대체하는 범용 타입"이 아니라 "이 메서드는 결과가 없을 수도 있다"는 사실을 시그니처에 적어 넣기 위한 반환 전용 컨테이너다. Java 8 이전에는 메서드가 null을 돌려줄 수 있다는 사실이 시그니처 어디에도 안 적혀 있어서 호출자가 문서를 읽거나 운영 중 NPE를 맞고 배워야 했고, Optional은 그 사실을 타입으로 끌어올린 장치다. 설계자 Brian Goetz가 "라이브러리 메서드의 반환 타입에 한정한 장치"라고 못 박았고, 필드에 쓰는 순간 상태가 줄기는커녕 null / Optional.empty() / 값 존재의 셋으로 늘어나 null을 없애려던 도구가 null 검사와 isPresent 검사를 둘 다 요구하는 역설에 빠진다. 여기에 직렬화 불가, JPA 매핑 불가, 객체 할당 비용이 얹힌다. 파라미터에 쓰면 호출자 전원에게 포장 의무만 지우고 정작 null 유입은 못 막는다. 올바른 범위는 조회성 메서드의 반환 타입 + map/orElseThrow 체이닝으로 즉시 소비하는 데까지이고, 그 안에서도 isPresent()+get()은 if (x != null)의 장황한 재현일 뿐이며 orElse는 값이 있어도 인자를 먼저 평가한다는 함정이 남는다.

0. 질문 + 출제 의도 · 겨냥하는 약점

질문 — "Optional을 필드나 메서드 파라미터에 쓰지 말라는 권고의 이유는? 실무에서 Optional의 올바른 사용 범위는 어디까지인가요?"

출제 의도 — Optional을 필드·파라미터·컬렉션 원소에 쓰는 코드는 "null 안전"이 아니라 관용구 위반이다. 이 질문이 실제로 보는 것은 API 암기가 아니라 도구의 설계 의도를 이해하고 쓰는가 — 편리해 보이는 API를 원래 목적 밖으로 확장할 때 멈출 수 있는 절제가 있는지다.

약점 A"Optional = null 안전"에서 멈춘다 — 무엇을 대체하러 나온 물건인지 모른다. 그러면 "왜 반환 타입만인가"를 설명하지 못하고 "권고라서"로 끝난다(1·2절).
약점 B필드 금지 이유를 "안 예뻐서"로 답한다 — 가장 강한 논거인 "상태가 2개에서 3개로 늘어난다"를 못 꺼낸다. 직렬화·JPA·비용은 그 다음 논거다(3~6절).
약점 C파라미터도 "시그니처에 적히니 좋은 것 아닌가"라고 본다 — 규약을 지켜야 하는 사람 수가 반환과 파라미터에서 다르다는 것을 놓친다. f(x, null)은 그냥 컴파일된다(7절).
약점 D반환 타입에 잘 썼다고 끝이라 생각한다 — 소비를 isPresent()+get()으로 하면 if (x != null)을 이름만 바꿔 다시 쓴 것이다. 얻은 것 없이 줄만 길어진다(10절).
약점 EorElse와 orElseGet을 스타일 차이로 안다 — 인자 평가 시점의 문제이며, orElse(loadFromDb())는 값이 있어도 매번 DB를 때린다. 눈으로 안 보여서 조용히 사고를 낸다(11절).
합격선"Optional은 '없을 수 있음'을 반환 타입에 적기 위한 장치라 그 자리에서만 값을 합니다. 필드에 쓰면 null/empty/값의 세 상태가 생겨 검사가 두 겹이 되고 직렬화·JPA·할당 비용까지 붙습니다. 파라미터는 호출자 전원에게 포장만 시키고 null은 못 막습니다. 그래서 조회 반환 타입 + 즉시 체이닝 소비까지만 쓰고, 필드는 nullable + getter ofNullable, 파라미터는 오버로딩이나 @Nullable로 대체합니다."
08번 문서와의 분담 Stream·Optional·람다의 기본 사용법은 08번(Java 8 실무 활용)이 본체다. 이 문서는 그 위층 — "Optional을 어디까지 써도 되는가"라는 경계 한 가지에만 집중한다. 그래서 여기서는 자리(위치)가 주인공이고, API 목록은 배경으로만 등장한다.

1. Optional 이전 — "없을 수 있다"는 사실이 타입 밖에 있었다

"Optional은 반환 타입 전용"이라는 결론부터 외우면 왜 그런지가 남지 않는다. 그러니 Optional이 없던 시절에 무엇이 불편했는지부터 보자. 이 순서를 밟아야 3절부터의 "쓰면 안 되는 자리" 논거가 암기가 아니라 추론이 된다.

Member findByEmail(String email); // 이 시그니처를 보고 답할 수 있는가?

이메일이 없는 회원을 조회하면 무엇이 반환되는가? 가능한 답이 셋이다 — null을 반환할 수도, 예외를 던질 수도, 빈 Member 객체를 줄 수도 있다. 시그니처는 이 중 어느 것인지 한 글자도 말해주지 않는다.

1-1. null 반환이 고약한 진짜 이유 — 터지는 곳이 원인에서 멀다

null을 반환하면 그 자리에서 터지지 않는다. null은 조용히 대입되고, 조용히 전달되고, 조용히 저장된다. NPE는 한참 뒤 전혀 다른 코드에서 난다.

Java 8 이전, "결과가 없을 수 있는 메서드"를 만드는 사람의 선택지 — 둘 다 나빴다
방식무엇이 문제인가호출자 입장
null 반환호출자가 null 검사를 잊으면 위 그림처럼 한참 뒤 엉뚱한 곳에서 NPE가 난다. 시그니처만 봐서는 null 가능성 자체를 알 수 없다알 방법이 없다
예외 던지기"없음"이 정상 흐름인데 예외로 표현하게 된다. 제어 흐름을 예외로 다루는 것도 문제고, 스택트레이스를 채우는 비용도 붙는다catch를 강제받거나(checked) 역시 모른다
Optional 반환"없을 수 있음"이 타입에 적힌다. 값을 꺼내려면 부재 처리를 같은 표현식에 써야 한다시그니처만 보고 안다
비유 — 경고문이 인쇄된 상자 Optional은 "내용물이 없을 수도 있음"이라고 인쇄된 상자다. 상자 자체가 경고문이라, 받는 사람이 뜯기 전에 그 가능성을 인지한다. 예전에는 상자 없이 물건을 그냥 건넸고, 손이 비어 있어도 받는 사람은 뭔가 받았다고 생각한 채 걸어가다 넘어졌다.
여기서 이미 Optional이 어느 위치에서만 값을 하는지가 드러난다 — 경고문은 "건네는 순간"에만 의미가 있다. 물건을 창고에 보관하는 데 이 상자를 쓰면 창고 공간만 먹고, 상자 자체를 잃어버릴 수도 있다. 그게 3절부터의 이야기다.

필드·파라미터·컬렉션 원소 금지가 전부 이 한 문장에서 나온다. 보관(필드)·수령(파라미터)·나열(컬렉션)은 "건네주는 순간"이 아니다. 꼬리질문이 어디로 튀어도 이 문장으로 되돌아오면 된다.

2. 설계자가 못 박은 범위 — 써야 할 자리와 쓰면 안 되는 자리의 경계도

이건 관습이나 스타일 취향이 아니다. Java 8의 람다·스트림 설계를 이끈 Brian Goetz가 Optional 도입 직후 공개 답변에서 범위를 명시적으로 좁혔다.

"Optional is intended to provide a limited mechanism for library method return types where there needed to be a clear way to represent 'no result', and using null for such was overwhelmingly likely to cause errors." — Brian Goetz (Java 언어 아키텍트), Optional 도입 직후 공개 답변

문장에서 두 단어가 핵심이다. limited(제한적인)와 return types(반환 타입). 즉 반환 타입, 그중에서도 "없음이 정상인 조회 결과"가 유일한 설계 목적이었다. 필드·파라미터·컬렉션 원소는 처음부터 용도 밖이다.

그래서 이 질문의 답은 "필드에 쓰면 좀 안 예쁘다"가 아니라 "애초에 그 자리를 위해 만들어진 물건이 아니고, 그 자리에 두면 구체적으로 이런 손해가 난다"가 되어야 한다. 그 손해를 자리별로 지도에 그리면 이렇게 된다.

3. 필드 ① — 상태가 줄지 않고 늘어난다 (가장 강한 논거)

// null을 없애려고 감쌌다. 그런데… private Optional<String> nickname;

이 필드가 가질 수 있는 상태를 세어 보면 늘어나 있다. 면접에서 필드 금지 이유를 물으면 직렬화나 성능보다 이 논거를 먼저 꺼내야 한다. 다른 논거들은 "그럼 그 문제만 피하면 되지 않나"로 받아칠 수 있지만, 이 논거는 Optional을 쓰는 목적 자체를 무너뜨리기 때문이다.

세 상태가 각각 어떻게 만들어지는가 — "실수로만 생기는 상태"가 아니라는 점이 중요하다

왜 정확히 셋인가 — 네 번째는 없다 Optional.of(null)은 존재하지 않는다. Optional.of는 인자가 null이면 그 자리에서 NPE를 던지고, Optional.ofNullable(null)은 두 번째 상태로 수렴한다. 그래서 정확히 셋이다. 면접에서 "세 개"라고 답한 뒤 이 근거까지 붙이면 외운 답이 아니라는 게 드러난다.

AFTER(?) Optional 필드 — 검사 두 번
private Optional<String> nickname;

// 상태는 셋. 그중 둘이 같은 뜻
if (nickname != null && nickname.isPresent()) {
    use(nickname.get());   더 길어졌다
}
FIX 필드는 nullable 실제 타입, 부재 가능성은 getter의 반환 타입으로 알린다
private String nickname;   // 상태 2개. 직렬화·JPA 매핑·할당 문제가 전부 없다

public Optional<String> getNickname() {
    return Optional.ofNullable(nickname);   // 호출자에게는 "없을 수 있음"을 알린다
}

// 호출자 입장에서는 Optional 필드였을 때와 똑같이 쓸 수 있다 — 손해만 사라졌다

반문에 대비 — "필드가 null이 될 일 없게 잘 짜면 되지 않나?" 이 반문에는 "지켜야 할 사람 수"로 답한다(2절 하단 도식). 반환값의 규약은 그 메서드를 구현한 한 명이 지키면 끝나고 코드도 한 곳에 있다. 필드의 규약은 생성자·세터·리플렉션으로 객체를 만드는 프레임워크·나중에 필드를 하나 더 추가하는 사람까지 전부가 지켜야 한다. 언어가 강제하지 못하는 규약은 참여자가 늘어날수록 반드시 깨진다. 필드는 참여자가 많은 자리다.

4. 필드 ② — 직렬화가 안 된다

Optional은 Serializable을 구현하지 않는다. 실수가 아니라 의도된 설계다. 반환 전용 장치라면 객체의 상태로 저장될 일이 없어야 한다는 입장이 코드로 표현된 것이다. 그래서 이 제약은 "불편한 버그"가 아니라 "설계 의도의 증거"로 읽어야 한다.

5. 필드 ③ — 프레임워크가 못 다룬다

5-1. JPA / Hibernate — 매핑 대상 타입이 아니다

엔티티 필드는 DB 컬럼과 매핑되는 실제 타입이어야 한다. Optional<String>은 매핑 대상 타입이 아니라 그대로 두면 매핑에 실패한다. 절충안은 3절에서 본 것과 같다 — 필드는 nullable 실제 타입으로 두고 getter에서 감싼다.

BAD 엔티티 필드를 Optional로
@Entity
public class Member {
    private Optional<String> nickname;   컬럼과 대응 안 됨
}
GOOD 필드는 실제 타입, getter에서 감싼다
@Entity
public class Member {
    private String nickname;   // DB 컬럼과 1:1

    public Optional<String> getNickname() {
        return Optional.ofNullable(nickname);
    }
}

5-2. Jackson — 모듈이 있어도 역직렬화 함정이 남는다

Optional은 그냥 두면 Jackson이 평범한 객체로 보고 그 안의 isPresent() 게터를 읽어 {"present": true} 같은 엉뚱한 JSON을 만든다. 제대로 다루려면 jackson-datatype-jdk8 모듈이 등록돼 있어야 한다(Spring Boot는 자동 등록해 준다).

모듈이 등록돼 있어도 역직렬화 쪽에는 함정이 하나 남는다. 그리고 이것이 실무에서 실제로 NPE를 만드는 경로다.

5-3. JavaBeans 규약 — 프로퍼티 타입 추론과 어긋난다

게터가 Optional<String>을 반환하면 "프로퍼티 nickname의 타입은 String"이라는 규약과 어긋난다. 리플렉션으로 프로퍼티 타입을 추론하는 도구(일부 매핑 라이브러리, 폼 바인딩, 리포팅 툴)에서 마찰이 생길 수 있다. Optional 반환 getter를 도입할 때 알고 감수하는 단서로 기억해 두면 된다.

6. 필드 ④ — 비용: 수명과 래핑 두 겹

비용 이야기는 순서를 틀리면 틀린 답이 된다. "Optional은 객체라서 느리다"는 과장이고, "요즘 JIT가 다 없애준다"도 절반만 맞다. 정확한 답은 "위치에 따라 결론이 갈린다"이다.

한 가지 더 — 값 기반 클래스(value-based class) Optional은 값 기반 클래스로 지정돼 있다. "이 타입의 인스턴스는 값으로만 다뤄야 하며 개별 객체의 정체성에 의존하지 말라"는 뜻이라, ==로 비교하거나 synchronized (opt)로 락을 잡는 사용이 금지 대상이다(지금 동작하더라도 미래에 깨질 수 있다). 이 조항이 주제와 이어지는 지점은 이것이다 — 오래 살아남는 자리(필드)에 둘수록 누군가 그런 코드를 쓸 여지가 커진다. 값 비교가 필요하면 equals를 쓴다(담긴 값끼리 비교한다).

7. 메서드 파라미터 — 부담만 넘기고 막지는 못한다

// 잘못됨 void updateProfile(String name, Optional<String> nickname) { ... }
BEFORE 호출부마다 포장이 반복된다

updateProfile("kim", Optional.ofNullable(nickname));

updateProfile("park", null);   컴파일된다

반환 O · 파라미터 X를 한 문장으로 설명하는 법

반환은 지킬 사람이 1명이라 규약이 유지되고,
파라미터는 지킬 사람이 N명이라 규약이 유지되지 않는다

그래서 파라미터의 Optional은 비용(포장 의무)만 N명에게 지우고 이득(부재 강제)은 0인 거래가 된다. 이 문장 하나로 "둘 다 시그니처에 적히는 건 같지 않나요?"라는 반문을 정면으로 받을 수 있다.

8. 그 밖에 쓰지 말아야 하는 자리

컬렉션의 원소로 쓰지 않는다

List<Optional<String>>은 "없음"을 두 겹으로 표현한 것이다. 리스트는 이미 "그 자리에 원소가 있다/없다"를 표현할 수 있다.

  • 값이 없는 원소는 애초에 리스트에 넣지 않으면 된다.
  • 순회할 때마다 매 원소를 푸는 비용만 남는다.
  • 스트림에서 걸러 낼 때는 .flatMap(Optional::stream)(Java 9+)이나 .filter(Objects::nonNull)로 파이프라인 안에서 처리하고, 결과 컬렉션에는 값만 담는다.
컬렉션 자체를 감싸지 않는다

Optional<List<Item>>은 안티패턴이다. 컬렉션에는 이미 "없음"을 표현하는 수단 — 빈 컬렉션 — 이 있기 때문이다.

  • Optional.empty()와 Optional.of(List.of())가 사실상 같은 뜻이라 3절의 "의미 중복" 문제가 재현된다.
  • 호출자가 두 단계로 풀어야 한다.
  • Effective Java Item 54("null이 아닌, 빈 컬렉션이나 배열을 반환하라")가 정확히 이 이야기다. 빈 컬렉션 반환은 Optional 이전부터 정답이었고 Optional이 그것을 대체하지 않는다.
BAD 호출자가 두 단계로 풀어야 한다
Optional<List<Item>> findItems(Long id);

findItems(id).orElse(List.of()).forEach(...);
//           ^^^^^^^^^^^^^^^^^^ 매 호출부마다 반복
GOOD 없으면 빈 리스트 — 분기 없이 바로 순회

// 호출자는 "없음"을 따로 생각하지 않아도 된다

8-1. 모든 반환 타입에 기계적으로 붙이지 않는다

"항상 값이 있어야 하는" 메서드까지 Optional로 감싸면 호출자에게 의미 없는 없음 처리를 강제하게 된다. 값이 없는 것이 버그이거나 복구 불가능한 상황이라면 그냥 예외를 던지는 것이 맞다.

GOOD 없으면 그건 데이터 이상이다

// → 이상 상황이 로그와 알림에 드러난다
BAD 이상 상황이 조용히 기본값으로 덮인다

Optional을 붙일지 말지 — 판단 기준은 한 줄

"없음"이 예외 상황이면 예외
정상 흐름 → Optional

Effective Java Item 55의 제목 그대로다 — "Optional은 신중하게 반환하라(Return optionals judiciously)". 반환에만, 컬렉션은 감싸지 말고, 성능이 민감한 구간은 한 번 더 생각하라.

10. 소비 패턴 ① — isPresent() + get()은 null 검사의 장황한 재현

반환 타입에 제대로 썼더라도 소비하는 방식이 틀리면 얻는 것이 없다. 가장 흔한 것이 이 패턴이다.

BEFORE Optional을 쓰기 전
Member member = repo.findByEmail(email);
if (member != null) {
    sendMail(member);
}
AFTER(?) Optional을 썼지만 구조가 똑같다
Optional<Member> found = repo.findByEmail(email);
if (found.isPresent()) {
    sendMail(found.get());   한 단계 늘었을 뿐
}

두 코드를 나란히 놓으면 하는 일이 완전히 같다. if (x != null)이 if (found.isPresent())로 이름만 바뀌었고, 값을 꺼내는 .get()이 한 단계 추가됐을 뿐이다. 얻은 것은 없고 줄만 길어졌다.

게다가 get()은 안전한 접근자가 아니다 빈 Optional에 get()을 부르면 NoSuchElementException을 던진다. isPresent() 검사를 빼먹으면 NPE 대신 다른 예외가 날 뿐 아무것도 나아지지 않는다. 실제로 JDK는 이 위험 때문에 get()에 orElseThrow()라는 같은 동작의 대체 이름을 추가했다(Java 10) — 이름 자체로 "빈 값이면 예외가 난다"를 드러내기 위해서다. get()이라는 이름이 list.get(0)·map.get(k)와 같은 어휘라서 안전해 보이는 것이 문제였다.

Optional을 제대로 쓴다는 것은 분기를 직접 쓰지 않고 Optional이 제공하는 연산에 맡기는 것이다.

AFTER 부재 처리를 연산에 맡긴다
// 값이 있을 때만 하는 일 — 분기 자체가 사라진다
repo.findByEmail(email).ifPresent(this::sendMail);

// 값을 꺼내야 하면 "없을 때 무엇을 할지"를 같은 표현식에 적는다
String name = repo.findByEmail(email)
        .map(Member::getName)
        .orElse("탈퇴한 회원");

Member member = repo.findByEmail(email)
        .orElseThrow(() -> new MemberNotFoundException(email));

// 검증도 분기 없이 — 조건에 안 맞으면 empty로 바뀐다
Member active = repo.findByEmail(email)
        .filter(Member::isActive)
        .orElseThrow(() -> new InactiveMemberException(email));

11. 소비 패턴 ② — orElse vs orElseGet: 인자가 언제 평가되는가

이 둘의 차이는 "스타일"이 아니라 실행 순서의 문제다. 그리고 코드를 눈으로 보면 차이가 안 보이기 때문에 실무에서 조용히 사고를 낸다.

핵심 전제 — Java의 평가 규칙 Java는 메서드를 호출하기 전에 인자를 먼저 전부 평가한다. orElse도 평범한 메서드이므로 이 규칙에서 예외가 아니다. 즉 "Optional이 알아서 필요할 때만 실행해 주겠지"라는 기대 자체가 성립할 수 없다 — 인자는 orElse에 도착하기 전에 이미 계산이 끝나 있다.

암기 — 판단 기준은 한 줄

기본값이 이미 있는 상수면 orElse
만드는 데 비용이 드는 것이면 orElseGet
opt.orElse("");                        // 문자열 상수 - orElse로 충분하다

opt.orElse(new ArrayList<>());         // 매번 리스트를 하나씩 만들어 버린다
opt.orElseGet(ArrayList::new);         // 없을 때만 만든다

opt.orElse(repository.findDefault());  // 값이 있어도 매번 DB를 때린다
opt.orElseGet(repository::findDefault);

orElseThrow(Supplier)도 같은 이유로 Supplier를 받는다. 예외 객체를 만드는 순간 스택트레이스가 채워지는데, 값이 있을 때는 그 비용을 낼 이유가 없기 때문이다.

12. 규약 파괴 — Optional을 반환한다고 해놓고 null을 반환할 때

절대 금지 규약 파괴
Optional<Member> findByEmail(String email) {
    Member m = ...;
    if (m == null) return null;   규약 파괴
    return Optional.of(m);
}
FIX 한 줄로 끝난다
Optional<Member> findByEmail(String email) {
    Member m = ...;
    return Optional.ofNullable(m);
}
이건 "Optional을 안 쓴 것보다 나쁘다" 단순한 실수가 아니라 Optional의 존재 이유를 정면으로 무너뜨리는 코드다. 호출자는 시그니처를 믿고 곧바로 .map(...)이나 .orElseThrow(...)를 부를 텐데, 거기서 NPE가 난다. Optional을 안 썼다면 호출자가 null을 의심이라도 했을 텐데, Optional이 그 의심을 껐기 때문에 방어가 사라진 상태에서 맞는다.
없으면 Optional.empty()를, 값이 null일 수 있으면 Optional.ofNullable(m)을 쓴다. 팀 차원으로는 정적 분석 규칙으로 잡는 것이 좋다 — 사람이 지켜야 하는 규약을 도구로 옮기는 전형적인 자리다.

13. 언어 차원 대비 — Java는 왜 이 어정쩡한 도구를 갖게 됐나

Kotlin과 C#은 nullable을 언어 문법에 넣었다. String은 null이 될 수 없고 String?은 될 수 있다. 그리고 컴파일러가 모든 위치에서 — 필드든 파라미터든 반환이든 — 검사한다.

15. 꼬리질문 셀프 테스트

펼치기 전에 소리 내어 답해 본 뒤 열어라. 막히는 항목이 있으면 괄호 안 절로 돌아간다.

Optional<String> nickname; 필드가 가질 수 있는 상태는 몇 가지인가요? 그게 왜 문제인가요?힌트: 개수보다 "의미가 겹치는 상태"가 있는지를 보라 핵심

세 가지다. ① 참조 자체가 null인 상태, ② Optional.empty(), ③ 값이 든 상태. Optional.of(null)은 생성 시점에 NPE라 존재하지 않고, Optional.ofNullable(null)은 ②로 수렴하므로 정확히 셋이다.

문제는 개수가 아니라 ①과 ②가 "닉네임이 없다"는 같은 의미의 다른 표현이라는 점이다. 그냥 String nickname이면 상태는 둘(null 또는 값)인데, null을 없애려고 감쌌더니 하나 늘었다. 방어적으로 짜면 nickname != null && nickname.isPresent()가 되어 검사가 두 겹이 된다.

"필드가 null이 될 일 없게 잘 짜면 되지 않나"는 반문에는 규약을 지켜야 하는 사람 수로 답한다. 반환값은 그 메서드를 구현한 한 명이 지키면 되지만, 필드는 생성자·세터·리플렉션으로 객체를 만드는 프레임워크·나중에 필드를 추가하는 사람까지 전부가 지켜야 한다. 언어가 강제하지 못하는 규약은 참여자가 늘어날수록 반드시 깨진다(3절).

orElse와 orElseGet의 차이는 뭔가요?힌트: "스타일" 차이가 아니라 실행 순서 차이다 핵심

인자가 평가되는 시점이 다르다. Java는 메서드를 호출하기 전에 인자를 먼저 전부 평가하고 orElse도 평범한 메서드이므로, orElse(x)의 x는 Optional에 값이 있든 없든 항상 실행된다. 반면 orElseGet(supplier)는 값이 없을 때만 supplier를 호출한다.

opt.orElse(loadFromDb());        // 값이 있어도 DB를 때린다. 그 결과는 그냥 버려진다
opt.orElseGet(this::loadFromDb); // 없을 때만 DB를 때린다

판단은 "기본값이 이미 있는 상수인가, 만드는 데 비용이 드는가"로 한다. 상수 문자열이나 이미 계산된 값이면 orElse가 읽기 좋고, 객체 생성·DB 조회·외부 호출이 들어가면 반드시 orElseGet이다. orElseThrow(Supplier)가 Supplier를 받는 것도 같은 이유다 — 예외 객체 생성은 스택트레이스를 채우는 비용이 있는데, 값이 있을 때 그 비용을 낼 이유가 없다(11절).

getter가 Optional을 반환하는 건 괜찮나요?힌트: 그 자리는 "필드"인가 "반환 타입"인가

널리 쓰이는 절충안이다. 필드는 nullable 실제 타입으로 두고, getter에서만 감싼다.

private String nickname;   // 직렬화·JPA 매핑·비용 문제가 없다

public Optional<String> getNickname() {
    return Optional.ofNullable(nickname);   // 호출자에게는 "없을 수 있음"을 알린다
}

이러면 3~6절의 손해(3-상태, 직렬화 불가, JPA 매핑 불가, 인스턴스마다 곱해지는 할당)를 전부 피하면서 호출자에게는 반환 타입으로 부재 가능성을 알릴 수 있다. Optional의 설계 의도와도 정확히 맞는다 — 어차피 반환 타입이기 때문이다.

단서는 둘. JavaBeans 프로퍼티 규약에 민감한 도구와 마찰이 생길 수 있고, 이 getter를 그대로 JSON 직렬화 경로에 태우면 5절의 Jackson 이슈를 다시 만난다.

Optional을 쓰면 NPE가 사라지나요? 성능 부담은 어느 정도인가요?힌트: 예외 이름이 바뀐 것과 위험이 사라진 것은 다르다 시니어 변별

사라지지 않는다. 이 지점을 정확히 답하는지가 "유행어로 아는 사람"과 갈리는 자리다.

  • 빈 Optional에 get()을 부르면 NoSuchElementException이 난다. 예외 이름만 바뀐 것이다.
  • Optional 참조 자체가 null이면 여전히 NPE다(3절).
  • Optional.of(null)은 그 자리에서 NPE다.

Optional의 가치는 NPE 제거가 아니라 "없을 수 있음"을 시그니처에 드러내 호출자가 처리하도록 유도하는 것이다. 그래서 그 유도가 작동하는 위치, 즉 반환 타입에서만 의미가 있다. 필드에 쓰면 유도할 호출자가 없으니 비용만 남는다.

성능은 위치에 따라 결론이 갈린다. 반환 후 즉시 소비하는 정상 용법에서는 호출당 객체 하나이고, JIT의 탈출 분석으로 할당 자체가 사라지는 경우도 많아 대부분의 비즈니스 로직에서 무시할 수준이다. 문제가 되는 것은 둘이다 — 필드로 장기 보유해 인스턴스 수만큼 곱해질 때, 그리고 루프 안에서 원시값을 Optional<Integer>로 이중 박싱할 때. 후자는 OptionalInt/OptionalLong/OptionalDouble로 박싱 한 겹을 없앤다(6절).

모든 반환 타입에 Optional을 붙이면 안 되나요?힌트: "없음"이 정상인가 이상인가

안 된다. 판단 기준은 "없음"이 정상 흐름인가 아닌가다.

값이 없는 것이 정상적으로 일어나는 일이면 Optional이 맞다(이메일로 회원 조회, 스트림의 최댓값). 반면 값이 없는 것이 버그이거나 복구 불가능한 데이터 이상이면 그냥 예외를 던지는 것이 맞다. 결제 건에 금액이 없다면 그건 정상 흐름이 아니다. Optional로 감싸면 호출자마다 의미 없는 orElse(0L)이 붙고, 진짜 이상 상황이 조용히 기본값으로 덮인다.

컬렉션은 특히 감싸면 안 된다. Optional<List<Item>>은 "없음"을 표현하는 수단이 이미 있는 타입을 또 감싼 것이다. 없으면 빈 컬렉션을 반환하면 호출자는 분기 없이 바로 순회할 수 있다(Effective Java Item 54). 같은 이유로 List<Optional<T>>처럼 원소를 감싸는 것도 안티패턴이다 — 값이 없는 원소는 애초에 넣지 않으면 된다(8절).

반환 타입은 되고 파라미터는 안 되는 이유가 정확히 뭔가요? 둘 다 "시그니처에 적는" 것 아닌가요?힌트: 규약을 지켜야 하는 사람이 몇 명인지 세어 보라 시니어 변별

둘 다 시그니처에 적히는 것은 맞다. 갈리는 지점은 "그 약속을 지켜야 하는 주체가 누구이고 몇 명인가"다.

  • 반환 타입 — "여기서 null은 절대 안 나온다"는 약속을 지켜야 하는 사람은 그 메서드를 구현한 한 명이고, 코드도 한 곳에 있다. 그래서 지켜지고, 호출자는 그 약속을 믿고 .map()을 바로 부를 수 있다. 강제되지 않아도 유지되는 규모다.
  • 파라미터 — 약속을 지켜야 하는 쪽이 호출자 전원이고, 그들을 강제할 수단이 없다. updateProfile("kim", null)은 그냥 컴파일된다. Optional이 여기서 보장해 주는 것이 하나도 없다.

그래서 파라미터 자리의 Optional은 호출부 전원에게 Optional.ofNullable(...) 포장 의무를 지우면서 정작 null 유입은 막지 못하는 순손해가 된다. 같은 의도는 오버로딩(없는 호출을 시그니처로 분리)이나 @Nullable + 정적 분석으로 표현하는 것이 맞고, 선택 인자가 많으면 정적 팩토리 메서드나 빌더다. IntelliJ·SonarQube·Error Prone이 모두 이걸 경고 규칙으로 갖고 있다(Sonar java:S3553)(7절).

Optional을 반환한다고 선언한 메서드가 null을 반환하면 무슨 일이 생기나요?힌트: 호출자는 무엇을 믿고 코드를 썼는가

Optional을 안 썼을 때보다 나쁘다. 이건 사소한 실수가 아니라 Optional의 존재 이유를 정면으로 무너뜨리는 코드다.

호출자는 시그니처를 믿고 곧바로 .map(...)이나 .orElseThrow(...)를 부른다. 거기서 NPE가 난다. Optional을 안 썼다면 호출자가 null을 의심이라도 했을 텐데, Optional이 그 의심을 껐기 때문에 방어가 사라진 상태에서 맞는다.

없으면 Optional.empty()를, 값이 null일 수 있으면 Optional.ofNullable(m)을 쓰면 한 줄로 끝난다. 팀 차원으로는 정적 분석 규칙으로 잡는 것이 좋다 — 사람이 지켜야 하는 규약을 도구로 옮기는 전형적인 자리다(12절).

get()이 이미 있는데 JDK는 왜 orElseThrow()라는 같은 동작의 메서드를 또 만들었나요?힌트: 동작이 아니라 이름이 문제였다 가산점

동작을 바꾼 게 아니라 이름으로 위험을 드러내려고 추가한 것이다. 인자 없는 orElseThrow()는 get()과 동작이 같다 — 값이 있으면 값을, 없으면 NoSuchElementException을 던진다.

get()이라는 이름은 "그냥 꺼내는 안전한 접근자"처럼 읽힌다. list.get(0), map.get(k)와 같은 어휘이기 때문이다. 그래서 사람들이 isPresent() 검사 없이 습관적으로 불렀고, 이름 자체가 오용을 유도한다는 문제 제기가 계속 있었다. orElseThrow라는 이름은 "빈 값이면 예외가 난다"를 호출부에 그대로 써 붙인다.

이 인자 없는 형태는 Java 10에서 추가됐다. 참고로 Java 9에서는 ifPresentOrElse·or·stream이 추가돼, 분기를 직접 쓰지 않고 연산으로 표현할 수 있는 범위가 넓어졌다(10절).

Optional은 왜 Serializable이 아닌가요? 빠뜨린 건가요?힌트: 직렬화되는 것은 "상태"다 시니어 변별

빠뜨린 게 아니라 의도된 설계다. 직렬화 대상이 된다는 것은 "이 객체가 어딘가에 상태로 저장될 수 있다"는 뜻인데, Optional은 애초에 반환값으로 잠깐 존재했다 사라지는 장치로 설계됐다. 즉 "필드로 쓰지 말라"는 권고를 코드로 못 박은 것에 가깝다.

결과적으로 Optional 필드를 가진 클래스는 Java 직렬화를 쓰는 모든 경로에서 즉시 깨진다 — java.io.NotSerializableException: java.util.Optional. 실무에서 이 경로는 생각보다 여러 곳이다: Java 직렬화 기반 세션 저장소(Spring Session의 기본 직렬화 설정, 톰캣 세션 복제), 일부 캐시 구현체, RMI 계열 통신.

주의할 점은 이게 JSON 직렬화와는 다른 얘기라는 것이다. Jackson은 jackson-datatype-jdk8 모듈이 등록돼 있으면 Optional을 다룰 수 있다(Spring Boot는 자동 등록). 그래도 역직렬화 쪽 함정은 남는다(5절).

Optional을 ==로 비교하거나 synchronized (opt)로 락을 잡아도 되나요?힌트: 값 기반 클래스(value-based class) 시니어 변별

안 된다. Optional은 값 기반 클래스(value-based class)로 지정돼 있다. "이 타입의 인스턴스는 값으로만 다뤄야 하며 개별 객체의 정체성(identity)에 의존하지 말라"는 뜻이다. 구체적으로 == 비교, 객체를 락으로 쓰는 것(synchronized), 정체성 해시에 기대는 사용이 금지 대상이다. 구현이 인스턴스를 캐시하거나 합칠 자유를 남겨 두기 위한 규정이라, 지금 우연히 동작하더라도 미래에 깨질 수 있는 코드다.

이 조항이 이 문서의 주제와 이어지는 지점이 있다. 오래 살아남는 자리(필드)에 둘수록 누군가 그런 코드를 쓸 여지가 커진다. 반환 즉시 소비하고 버리는 용법에서는 ==로 비교할 기회 자체가 거의 생기지 않는다. 값 비교가 필요하면 equals를 쓴다 — Optional의 equals는 담긴 값끼리 비교한다(6절).

Optional<List<Item>>을 반환하면 뭐가 문제인가요?힌트: 그 타입에는 이미 "없음"이 있다

"없음"을 두 겹으로 표현한 것이라 호출자가 같은 질문에 두 번 답해야 한다. 컬렉션에는 이미 부재를 표현하는 수단 — 빈 컬렉션 — 이 있다.

// 잘못됨: 호출자가 두 단계로 풀어야 한다
Optional<List<Item>> findItems(Long id);
findItems(id).orElse(List.of()).forEach(...);

// 이렇게: 없으면 빈 리스트. 호출자는 분기 없이 바로 순회한다
List<Item> findItems(Long id);
findItems(id).forEach(...);

게다가 Optional.empty()와 Optional.of(List.of())가 사실상 같은 뜻인데 표현이 갈리므로, 3절의 "의미 중복 상태" 문제가 반환 타입에서 재현된다. Effective Java Item 54("null이 아닌, 빈 컬렉션이나 배열을 반환하라")가 정확히 이 이야기이고, 빈 컬렉션 반환은 Optional 이전부터 정답이었으며 Optional이 그것을 대체하지 않는다(8절).

map과 flatMap은 언제 갈리나요?힌트: 매퍼가 무엇을 돌려주는가 가산점

매퍼 함수가 이미 Optional을 반환하는가로 갈린다.

  • map(f) — f가 평범한 값을 반환할 때. 결과는 알아서 Optional로 감싸진다. opt.map(Member::getName) → Optional<String>.
  • flatMap(f) — f가 이미 Optional을 반환할 때. map을 쓰면 Optional<Optional<String>>이라는 겹친 상자가 나온다.
// getNickname()이 Optional<String>을 반환하는 경우
Optional<Optional<String>> bad  = repo.findById(id).map(Member::getNickname);   상자 두 겹
Optional<String>           good = repo.findById(id).flatMap(Member::getNickname);

실무에서 Optional 반환 getter를 도입한 클래스를 체이닝할 때 이 구분이 바로 필요해진다. 참고로 filter는 조건에 맞지 않으면 empty()로 바꿔 주므로, opt.filter(Member::isActive).orElseThrow(...)처럼 검증도 분기 없이 표현할 수 있다(10절).

필드에 Optional을 쓰면 안 된다면, "선택적으로 존재하는 값"을 DTO나 엔티티에서는 어떻게 표현하나요?힌트: 자리마다 대체 도구가 따로 있다

자리별로 정해진 대체 도구가 있다. "Optional 말고 뭘 쓰냐"에 막히면 결론만 외운 것이다.

  • 필드 — nullable 실제 타입으로 두고, 필요하면 getter에서 Optional.ofNullable로 감싸 반환한다. JPA 엔티티는 반드시 이 방식이어야 한다. 필드 자체가 Optional<String>이면 컬럼 매핑 대상 타입이 아니다.
  • 파라미터 — 오버로딩으로 "없는 호출"을 시그니처로 분리하거나, @Nullable + 정적 분석으로 계약을 표현한다. 선택 인자가 많으면 정적 팩토리 메서드나 빌더.
  • 컬렉션 — 빈 컬렉션. 감싸지도 말고 원소를 감싸지도 않는다.
  • 도메인 의미가 있는 부재 — 값이 없는 이유가 여러 가지라면 전용 타입/열거형으로 표현하는 편이 낫다. "닉네임 미설정"과 "탈퇴로 인한 익명화"는 둘 다 empty()지만 의미가 다르다.

공통 원칙은 하나다 — Optional은 "값을 보관하는 방법"이 아니라 "값을 건네주는 방법"이다(9절).

Kotlin으로 짜는 프로젝트에서도 Optional을 써야 하나요?힌트: 왜 Optional이라는 절충안이 필요했는지를 뒤집어 보라 시니어 변별

쓰지 않는다. Kotlin에는 nullable 타입(String?)이 언어 문법으로 있고, 컴파일러가 필드·파라미터·반환 모든 위치에서 검사한다. Optional은 Java가 그 언어 기능을 넣지 못해 만든 라이브러리 절충안이므로, 언어가 이미 해 주는 곳에서는 상자만 하나 더 얹는 순손해다.

차이를 정확히 말하면 상태 개수다. String?의 상태는 여전히 둘(null 또는 값)이다 — 타입에 표시를 붙였을 뿐 객체를 하나 더 만들지 않는다. 반면 Optional<String> 필드는 셋이 된다. Kotlin에서 Optional<String>? 같은 타입을 만들면 그 모순이 눈에 보이게 드러난다.

경계에서만 조심하면 된다. Java 라이브러리(Spring Data JPA의 findById, Stream의 findFirst)가 돌려주는 Optional은 받는 즉시 Kotlin nullable로 바꿔 흘린다 — orElse(null)이나 표준 라이브러리의 getOrNull() 확장을 쓴다. Optional을 Kotlin 코드 안쪽까지 끌고 들어가지 않는 것이 요령이다(13절).

한 줄 요약
Optional은 "이 메서드는 결과가 없을 수도 있다"는, 예전에는 시그니처 어디에도 안 적혀 있던 사실을 타입으로 끌어올리기 위해 설계자가 반환 타입 전용으로 만든 장치이므로 — 필드에 쓰면 null/empty()/값의 세 상태가 되어 null을 없애려던 도구가 검사를 이중으로 만들고 직렬화 불가·JPA 매핑 불가·인스턴스마다 곱해지는 할당까지 얹으며, 파라미터에 쓰면 호출자 전원에게 포장 부담만 지우고 정작 null 유입은 못 막는다. 올바른 범위는 "없음이 정상"인 조회 메서드의 반환 타입 + map/ifPresent/orElseThrow 체이닝으로 즉시 소비하는 데까지이고, 그 안에서도 isPresent()+get()은 null 검사의 장황한 재현일 뿐이며 orElse는 값이 있어도 인자를 먼저 평가한다 — 필드·파라미터의 null 계약은 nullable 필드 + getter의 ofNullable, 오버로딩, @Nullable + 정적 분석으로 각각 대체한다.
