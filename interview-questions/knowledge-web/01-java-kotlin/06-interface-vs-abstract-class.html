인터페이스 vs 추상 클래스 — 확장 지점을 어디에, 어떻게 설계하는가
둘은 경쟁 관계가 아니다 — 공통점이 훨씬 많고, 갈리는 지점은 딱 둘이며, 그 둘은 사실 하나다

면접 질문: "인터페이스와 추상 클래스의 차이, 각각 언제 사용하나요?"

핵심 관전 포인트 — 둘은 경쟁 관계가 아니라 공통점이 훨씬 많다. 둘 다 "미구현 메서드를 자식에게 강제하는 상위 타입"이고, 그 자체로는 인스턴스를 만들 수 없다. 갈리는 지점은 딱 둘이다 — 추상 클래스만 인스턴스 필드(상태)와 생성자를 가질 수 있고, 인터페이스만 한 클래스에 여러 개를 동시에 붙일 수 있다. 그리고 이 둘은 같은 뿌리에서 나온 하나의 사실이다 — 클래스 다중 상속이 금지된 진짜 이유는 메서드가 겹쳐서가 아니라 물려받을 상태가 두 벌 생기기 때문이고(다이아몬드 문제), 상태가 없는 인터페이스는 애초에 그 문제가 없어서 여러 개를 붙여도 안전하다. default 메서드끼리 겹치는 경우는 컴파일 에러로 "어느 쪽인지 명시하라"고 강제하는 것으로 기계적으로 해결된다. 관계의 의미도 여기서 갈린다 — 인터페이스는 can-do(이 타입은 이걸 할 수 있다), 추상 클래스는 is-a(이 타입은 저 계열의 일종이다). 실무 기본값은 인터페이스로 계약을 끊고, 구현체들 사이에 중복이 실제로 생기면 그때 계약 아래에 골격 구현(추상 클래스)을 끼우는 것이다. 이 주제의 진짜 실무 핵심은 이미 배포된 구현체가 있는 인터페이스에 메서드를 추가할 때 벌어지는 일이다 — 추상 메서드를 추가하면 남의 저장소에 있는 구현체까지 전부 깨지고, Java 8의 default 메서드가 정확히 그 문제(Stream 도입 때 Collection에 stream()을 추가해야 했던 상황)를 풀려고 나왔지만, 구현체가 알 수 없는 기본 동작을 조용히 물려받아 틀린 결과를 내는 새로운 위험을 함께 들여온다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "인터페이스와 추상 클래스의 차이, 각각 언제 사용하나요?"

출제 의도 — 실제로는 "확장 지점을 어떻게 설계하는가"의 질문이다. 외부 연동(PG사가 3곳)처럼 구현이 여럿인 지점에서 추상화 경계를 어디에 둘지 결정해 본 사람인지를 본다.

문법 차이 암기가 아니라, 새 구현체가 추가될 때 기존 코드를 안 건드리는 구조를 만들 수 있는지가 관건이다. 그래서 "필드를 가질 수 있다/없다"만 나열하고 끝내면 질문의 절반도 답하지 못한 것이 된다.

이 문서가 겨냥하는 약점 — "인터페이스는 계약, 추상 클래스는 골격"이라는 요약은 대부분 갖고 있다.
그런데 그 다음이 안 나온다. "그럼 인터페이스는 계약만 걸고 추상 클래스는 계약을 못 거나요?", "왜 클래스는 하나만 상속되죠?", "default가 생겼으니 추상 클래스는 이제 필요 없지 않나요?" — 여기서 갈린다.
갈리는 원인은 하나다. 둘을 경쟁하는 두 선택지로 외웠기 때문이다. 실제로는 공통점이 훨씬 많고 갈리는 지점은 딱 둘이며, 그 둘조차 "상태를 갖는가"라는 하나의 사실에서 파생된다. 그래서 이 문서는 1절을 공통점 확정으로 시작해서, 갈림 두 개 → 그 둘이 하나인 이유(다이아몬드) → 실무 조립법 → 배포된 계약의 진화 순으로 쌓는다.

이렇게 답하면 반쪽이다

  • "인터페이스는 계약, 추상 클래스는 구현 공유" — 요약은 맞지만 계약을 거는 능력은 추상 클래스도 갖고 있다. 공통점을 지운 요약이라 다음 질문에서 무너진다.
  • "인터페이스는 다중 구현이 되고 클래스는 안 됩니다" — 왜가 없다. 이유를 못 대면 암기한 표를 읽은 것으로 들린다.
  • "다이아몬드 문제는 메서드가 겹쳐서 생깁니다" — 틀렸다. 메서드 충돌은 default에서도 생기지만 컴파일 에러로 해결된다. 금지 사유는 상태다.
  • "default가 생겼으니 인터페이스가 상위 호환입니다" — 상태·생성자·protected·final가 남는다.
  • "스프링은 인터페이스가 있어야 트랜잭션이 걸립니다" — 부트 기본은 CGLIB이다. 오래된 지식이 드러나는 지점.
  • "확장을 위해 인터페이스를 미리 다 만들어 둡니다" — 구현이 하나뿐인 Impl 양산은 비용만 남긴다.

이 문서가 채워 주는 것

  • 공통점을 먼저 확정한다 — 외울 것이 차이표 6줄이 아니라 갈림 2개로 줄어든다.
  • 다이아몬드 문제를 상태 충돌로 도식화한다. "금지와 허용을 가른 것은 상태의 유무" 한 문장으로 압축된다.
  • 분기 산탄(shotgun surgery)이 실제로 어떻게 번지는지, 인터페이스가 그걸 어떻게 끊는지를 before/after 코드로 본다.
  • 골격 구현이 계약과 층이 다르다는 것을 3층 도식과 JDK 실물(List/AbstractList/ArrayList)로 확인한다.
  • 템플릿 메서드 vs 전략을 곱셈과 덧셈으로 판정하는 기준을 준다.
  • 소스 호환 vs 바이너리 호환을 나눠 AbstractMethodError가 왜 배포 후에야 터지는지를 타임라인으로 못박는다.

1. 공통점 — 둘 다 "구현을 강제하는 상위 타입"이다

1-1. 상위 타입이 하는 일은 호출부에서 구현을 지우는 것이다

인터페이스든 추상 클래스든, 존재 이유는 하나로 같다. 호출하는 쪽이 "누가 이 일을 하는지" 모르게 만드는 것이다.

PaymentService가 TossGateway를 직접 알고 있으면, 카카오페이가 추가되는 순간 PaymentService를 고쳐야 한다. 반면 PaymentService가 PaymentGateway라는 상위 타입만 알고 있으면, 카카오페이 구현을 새로 만들어 끼워 넣어도 PaymentService는 한 글자도 안 바뀐다. 이것이 "확장에는 열려 있고 수정에는 닫혀 있다"는 개방-폐쇄 원칙(OCP, Open-Closed Principle)의 실체다.

이 효과를 얻으려면 상위 타입이 두 가지를 해 줘야 한다.

① 이름과 시그니처를 못 박는다
호출부가 부를 메서드가 미리 정해져 있어야 구현이 아직 없어도 호출 코드를 쓸 수 있다.
② 자식이 반드시 채우게 강제한다
안 채우면 컴파일이 안 되게 해야 "약속했는데 안 지킨 구현체"가 생기지 않는다.
인터페이스와 추상 클래스는 둘 다 이 둘을 해 준다
여기까지는 차이가 없다. 이 사실을 먼저 깔고 시작해야 뒤에 나오는 "갈리는 지점 둘"이 정확히 무엇의 차이인지 선명해진다.

1-2. 공통점을 먼저 확정하자

구체적으로 두 가지가 같다.

공통 ① 그 자체로는 new 할 수 없다

미완성이기 때문이다. new PaymentGateway()도 new AbstractPaymentGateway()도 컴파일 에러다. 둘 다 "실체가 아니라 자리"다.

공통 ② 미구현 메서드를 자식에게 강제한다

인터페이스의 메서드 선언과 추상 클래스의 abstract 메서드는 이 점에서 완전히 같은 일을 한다. 구현하지 않은 자식은 컴파일 에러다.

같다 이 둘은 "자식에게 pay 구현을 강제한다"는 점에서 동일하다
interface PaymentGateway {
    PayResult pay(PayRequest request);                  // 몸통 없음 = 자식이 채워라
}

abstract class AbstractPaymentGateway {
    public abstract PayResult pay(PayRequest request);  // 역시 자식이 채워라
}

// 둘 다 인스턴스화 불가
PaymentGateway g1 = new PaymentGateway();          // 컴파일 에러
AbstractPaymentGateway g2 = new AbstractPaymentGateway();  // 컴파일 에러

먼저 외우면 오히려 헷갈리는 요약

"인터페이스는 계약이고 추상 클래스는 골격이다" — 이 문장부터 외우면 막힌다. 골격을 물려주는 능력은 갈리는 지점 중 하나(상태)의 결과일 뿐이고, 계약을 거는 능력은 양쪽 모두 갖고 있기 때문이다.

진짜 차이는 딱 둘이다 — ① 상태를 가질 수 있는가 ② 여러 개를 붙일 수 있는가

2. 갈리는 지점 ① — 상태(인스턴스 필드)를 가질 수 있는가

추상 클래스는 인스턴스 필드를 가질 수 있고,
인터페이스는 가질 수 없다

여기서 인스턴스 필드란 "인스턴스마다 따로 존재하는 값을 담는 칸"이다. TossGateway 인스턴스와 KakaoGateway 인스턴스가 각각 자기 몫의 로거·설정값·연결 정보를 들고 있으려면 인스턴스 필드가 필요하다.

인터페이스에도 필드를 쓸 수는 있다. 다만 거기 쓴 것은 전부 암묵적으로 public static final이 붙는다. 즉 인스턴스마다 따로 있는 값이 아니라, 타입 전체가 하나만 공유하는 상수다.

interface PaymentGateway {
    int TIMEOUT_MS = 3000;   // 이렇게만 써도 public static final이 자동으로 붙는다
                             // 인스턴스별 상태가 아니라 타입이 하나만 갖는 상수다
}

2-1. 상태가 있으면 생성자가 따라 나오고, 생성자가 있으면 강제가 따라 나온다

상태를 가질 수 있다는 것에서 생성자를 가질 수 있다는 성질이 따라 나온다. 필드가 있으니 그것을 초기화할 시점이 필요하기 때문이다. 그리고 생성자가 있으면 자식에게 초기화를 강제할 수 있다 — 자식의 생성자는 부모 생성자를 반드시 호출해야 하므로, 부모가 요구하는 값을 안 넘기면 컴파일이 안 된다.

public abstract class AbstractPaymentGateway implements PaymentGateway {
    private final PgApiLogger logger;      // 인스턴스 필드 = 상태

    // 생성자가 있으니 "로거 없이는 이 계열의 게이트웨이를 만들 수 없다"를 강제한다
    protected AbstractPaymentGateway(PgApiLogger logger) {
        this.logger = logger;
    }
}

class TossGateway extends AbstractPaymentGateway {
    TossGateway() { }                       // 컴파일 에러 — 부모 기본 생성자가 없다
    TossGateway(PgApiLogger logger) { super(logger); }   // 이렇게만 만들 수 있다
}
인스턴스 필드를 가질 수 있다→ 초기화 시점이 필요하다→ 생성자를 갖는다→ 자식에게 초기화를 강제할 수 있다
이 연쇄가 면접에서 값을 하는 이유 "추상 클래스는 생성자가 있고 인터페이스는 없다"를 따로 외운 항목으로 말하면 암기로 들린다. "상태가 있으니 생성자가 있고, 생성자가 있으니 강제가 된다"로 유도해서 말하면 이해로 들린다. 외울 것은 맨 앞의 하나뿐이다.

3. 갈리는 지점 ② — 여러 개를 동시에 붙일 수 있는가

클래스는 하나만 상속할 수 있고(extends는 한 개),
인터페이스는 여러 개를 구현할 수 있다(implements A, B, C)

이것을 실무 감각으로 옮기면 이렇다. 상속은 슬롯이 하나뿐인 희소 자원이다. 어떤 클래스에 추상 클래스를 상속시키는 순간 그 클래스는 다른 어떤 클래스도 상속할 수 없게 된다. 반면 인터페이스는 몇 개를 붙이든 서로 자리를 뺏지 않는다.

// 슬롯이 하나뿐인 extends는 여기서 끝이다
class TossGateway extends AbstractPaymentGateway { }   // 다른 클래스는 더 못 붙인다

// implements는 몇 개든 붙는다
class TossGateway implements PaymentGateway, HealthCheckable, Closeable { }

여기까지가 "차이" 전부다 — 두 줄로 인출하라

① 상태
추상 클래스만 인스턴스 필드 + 생성자를 갖는다 → 초기화 강제가 가능하다.
② 개수
인터페이스만 한 클래스에 여러 개 붙는다 → 능력을 조합할 수 있다.

그리고 다음 절에서 이 둘이 사실 하나라는 것을 본다. ②가 되는 이유가 정확히 ①이기 때문이다.

4. 두 지점은 사실 하나다 — 다이아몬드 문제

여기서 자연스러운 질문이 나온다. "왜 클래스는 하나만 상속되는데 인터페이스는 여러 개가 되는가?" 답은 2절에 이미 있다. 상태 때문이다.

클래스 다중 상속을 허용했다고 가정해 보자. 두 부모가 각각 같은 이름의 필드를 갖고 있으면 자식 인스턴스에는 그 필드가 몇 벌 있어야 하는가.

4-1. default가 생긴 뒤에도 다이아몬드 문제는 생기지 않는다

Java 8에서 default 메서드가 생기면서 인터페이스도 "구현"을 실어 나를 수 있게 됐지만, 다이아몬드 문제는 여전히 생기지 않는다. default 메서드는 동작만 있고 상태가 없기 때문이다. 그래서 겹치는 것은 "어느 메서드 몸통을 쓸 것인가" 하나뿐이고, 이건 컴파일러가 기계적으로 처리할 수 있다 — 컴파일 에러를 내고 명시적 선택을 강제한다.

충돌 컴파일이 거부한다
interface A { default String name() { return "A"; } }
interface B { default String name() { return "B"; } }

class C implements A, B { }

// error: types A and B are incompatible;
//   class C inherits unrelated defaults
//   for name() from types A and B

// 언어가 임의로 A를 고르거나 B를 고르지 않는다.
// "네가 정하라"고 컴파일 단계에서 되돌려준다.
해소 자식이 어느 쪽인지 명시한다
class C implements A, B {
    @Override
    public String name() {
        return A.super.name();   // 인터페이스명.super.메서드()
    }
}

// 물론 둘 다 쓰거나, 완전히 새로 쓸 수도 있다
//   return A.super.name() + B.super.name();
//   return "C";

이 절 전체를 한 문장으로

금지와 허용을 가른 것은 상태의 유무다

면접에서 "왜 클래스는 다중 상속이 안 되나요?"에 "메서드가 겹쳐서요"라고 답하면 바로 반례를 맞는다 — default는 메서드가 겹쳐도 허용된다. "물려받을 상태가 두 벌이 되기 때문"이 정답이고, "동작 충돌은 컴파일 에러로 명시를 강제하면 끝나기 때문에 허용됐다"까지 붙이면 완결된다.

5. 문법 차이 정리 · can-do와 is-a

앞의 두 갈림에서 나머지 문법 차이가 전부 따라 나온다. 표를 외우는 게 아니라 "상태 / 개수"에서 유도되는지 확인하며 읽는다.

인터페이스 vs 추상 클래스 — 결정적인 것만 추린 문법 차이 (오른쪽 열이 "왜 그런가")
구분인터페이스추상 클래스어느 갈림에서 나오는가
인스턴스 필드(상태)불가 — public static final 상수만 가능가능갈림 ① 그 자체
생성자없음있음 (자식에게 초기화 강제 가능)갈림 ① — 채울 칸이 있으니 채울 시점이 필요
한 클래스에 붙는 개수여러 개 구현 가능하나만 상속 가능갈림 ② — 그리고 그 원인은 다시 갈림 ①
구현이 담긴 메서드default / static / private(Java 9+)제한 없음갈림 ① — 상태를 못 쓰니 담을 수 있는 코드가 제한됨
멤버 접근 제어기본이 publicprotected 등 세밀한 제어 가능갈림 ① — 자식만 쓰는 도구를 숨겨서 물려줄 수 있는가
final 메서드불가 (default는 항상 재정의 가능)가능 — 흐름을 고정할 수 있다템플릿 메서드가 추상 클래스의 자리인 이유 (8절)
Object 메서드 재정의불가 (toString/equals/hashCode)가능"클래스가 이긴다" 규칙의 귀결 (13절)
표현하는 관계can-do — 이 타입은 이걸 할 수 있다is-a — 이 타입은 저 계열의 일종이다개수 규칙과 의미가 정확히 맞아떨어진다
표에서 실무적으로 은근히 큰 줄 — 접근 제어 추상 클래스는 protected 헬퍼 메서드를 둘 수 있어서 "자식만 쓰는 도구"를 외부에 노출하지 않고 물려줄 수 있다. 인터페이스는 (Java 9의 private 메서드로 default끼리 코드를 공유하는 것 말고는) 자식에게 물려주는 것이 곧 세상에 공개하는 것이다.
추상 클래스 숨겨서 물려줄 수 있다
public abstract class AbstractPaymentGateway {
    protected String signature(PayRequest r) {   // 자식만 쓴다
        return HmacUtils.sha256(secret, r.toRaw());
    }
    // 외부(호출부)에는 이런 게 있는지도 안 보인다
}
인터페이스 물려주면 곧 공개다
public interface PaymentGateway {
    default String signature(PayRequest r) { ... }  // public이다

    private String hmac(String raw) { ... }  // Java 9+ : default끼리만 공유
    // private 메서드는 구현체에게도 물려주지 못한다
}

5-1. 관계의 의미 — can-do와 is-a

이 문법 차이는 두 상위 타입이 표현하는 관계의 성격으로 이어진다.

인터페이스 = can-do

"이 타입은 이 일을 할 수 있다"는 능력의 선언이다.

  • Comparable — 비교될 수 있다
  • Closeable — 닫힐 수 있다
  • PaymentGateway — 결제를 처리할 수 있다

능력은 여러 개를 동시에 가질 수 있다. 어떤 클래스가 비교도 되고 닫히기도 하는 데 아무 모순이 없다. → 다중 구현 허용이 이 의미와 정확히 맞아떨어진다.

vs
추상 클래스 = is-a

"이 타입은 저 계열의 일종이다"는 분류 선언이다.

  • ArrayList extends AbstractList — 리스트 계열의 한 종류
  • Integer extends Number — 수 계열의 한 종류

분류는 본질적으로 하나다. 어떤 것이 동시에 두 계열의 일종이라는 말은 대체로 분류를 잘못 그었다는 신호다. → 단일 상속만 허용되는 것 역시 이 의미와 맞는다.

설계 중 자문할 한 문장 — 이것만 외운다

"이건 이 타입이 할 수 있는 일인가(can-do),
아니면 이 타입의 정체 자체인가(is-a)?"

can-do면 인터페이스 — 여러 개 붙여도 되니 비용이 낮다. is-a면 추상 클래스를 고려한다 — 다만 자식의 유일한 상속 슬롯을 쓰므로 중복이 실제로 확인된 뒤에 넣는다(7절).

6. 기본값은 인터페이스 — 분기 산탄을 끊는다

구현이 여럿이거나 여럿이 될 지점 — 외부 연동, 알림 채널, 저장소 — 에서는 인터페이스로 계약을 끊는다. 왜 그런지는 분기문이 어떻게 번지는지를 보면 안다.

Before 분기 산탄 — PG사가 늘 때마다 이 메서드를 수정해야 한다
public PayResult pay(Order order, String pgType) {
    if ("TOSS".equals(pgType)) {
        // 토스 API 호출...
    } else if ("KAKAO".equals(pgType)) {
        // 카카오 API 호출...
    } else if ("NICE".equals(pgType)) {
        // 나이스 API 호출...
    }
    ...
}

문제는 이 메서드 하나가 아니다. 같은 모양의 분기가 취소·조회·정산 리포트에도 하나씩 생긴다. PG사를 하나 추가하는 작업이 "코드베이스 곳곳에 흩어진 분기를 전부 찾아 고치기"가 되고, 하나라도 빠뜨리면 그 기능만 조용히 새 PG사를 지원하지 않는 상태가 된다.

하나의 변경을 위해 여러 곳을 흩어서 고쳐야 하는 구조 = 산탄 수술(shotgun surgery)
After 계약(인터페이스) + 구현체 — 새 PG사 추가 = 클래스 하나 추가로 끝난다
public interface PaymentGateway {
    PayResult pay(PayRequest request);
    CancelResult cancel(String transactionId);

    // 어떤 PG 요청을 감당하는지 구현체가 스스로 선언한다.
    // 이 한 줄이 있어야 호출부에 "어느 구현을 고를지"의 분기가 남지 않는다.
    boolean supports(PgType type);
}

@Component class TossGateway  implements PaymentGateway { ... }
@Component class KakaoGateway implements PaymentGateway { ... }

@Service
public class PaymentService {
    // 스프링은 같은 인터페이스를 구현한 빈을 전부 모아 List로 주입해 준다.
    // 새 구현체가 @Component로 등록되기만 하면 이 리스트에 자동으로 합류한다.
    private final List<PaymentGateway> gateways;

    public PaymentService(List<PaymentGateway> gateways) {
        this.gateways = gateways;
    }

    public PayResult pay(Order order, PgType type) {
        return gateways.stream()
                .filter(g -> g.supports(type))   // 어느 구현이 맡을지 구현체에게 묻는다
                .findFirst()
                .orElseThrow(() -> new UnsupportedPgException(type))
                .pay(PayRequest.from(order));
    }
}
이 코드에서 놓치면 안 되는 한 줄 — supports(PgType) 인터페이스만 뽑고 호출부에 if (type == TOSS) return tossGateway;를 그대로 두면 분기는 사라지지 않는다. 단지 한 곳으로 모였을 뿐이고 새 PG마다 여전히 그 파일을 고쳐야 한다. "어느 구현이 맡을지"를 구현체 자신에게 묻는 supports가 있어야 호출부에서 분기가 완전히 사라진다.

PaymentService는 어떤 PG사가 존재하는지 모른다. 새 PG사가 추가돼도 이 클래스는 한 글자도 바뀌지 않는다. 1절에서 말한 OCP가 실제 코드로 성립한 상태다.

확장 지점 판별 — 이 셋이면 인터페이스로 끊는다

외부 연동
PG사, 문자/알림 채널, 외부 인증 — 남이 정하는 규격은 반드시 여럿이 된다.
정책·전략
수수료·할인·등급 산정 — 비즈니스가 바뀌면 갈아 끼우는 것들.
저장/전달 수단
저장소, 캐시, 메시지 발행 — 테스트에서 가짜로 바꿔야 하는 것들.

7. 중복이 보이면 그때 골격 구현을 끼운다

6절 구조를 운영하다 보면 구현체마다 같은 코드가 반복되기 시작한다 — 요청/응답 로깅, 타임아웃 처리, 공통 응답 검증. 이때 계약(인터페이스)은 그대로 두고, 계약과 구현체 사이에 추상 클래스를 한 겹 끼운다.

용어 — 골격 구현(skeletal implementation) "공통 뼈대만 미리 채워 두고 다른 부분만 구멍으로 남긴 부분 구현"을 말한다. 뼈대(skeleton)만 있고 살은 자식이 붙인다는 뜻이다. 이름 관례도 정해져 있다 — Abstract + 인터페이스명(AbstractList, AbstractPaymentGateway).
Before 구현체마다 같은 코드가 반복된다
class TossGateway implements PaymentGateway {
    private final PgApiLogger logger;

    public PayResult pay(PayRequest r) {
        logger.request(r);              // 중복
        PgResponse res = callToss(r);   // 여기만 다르다
        validate(res);                  // 중복
        logger.response(res);           // 중복
        return toResult(res);           // 중복
    }
}

class KakaoGateway implements PaymentGateway {
    // 위와 글자 하나까지 같은 코드가 또 있다
    // 로깅 규칙이 바뀌면 N개 파일을 전부 고쳐야 한다
}
After 계약 아래에 골격을 한 겹 끼운다
public abstract class AbstractPaymentGateway
                       implements PaymentGateway {
    private final PgApiLogger logger;   // 인터페이스로는 불가

    protected AbstractPaymentGateway(PgApiLogger logger) {
        this.logger = logger;            // 생성자로 초기화 강제
    }

    // final: "로깅 -> 호출 -> 검증 -> 변환" 순서는 정책이다
    @Override
    public final PayResult pay(PayRequest request) {
        logger.request(request);
        PgResponse response = callPgApi(request);  // 구멍
        validate(response);
        logger.response(response);
        return toResult(response);
    }

    protected abstract PgResponse callPgApi(PayRequest r);
}

class TossGateway extends AbstractPaymentGateway {
    @Override
    protected PgResponse callPgApi(PayRequest r) {
        /* 토스 API 호출만 작성 */
    }
}

7-1. 골격이 고정하는 것은 "코드"가 아니라 "순서"다

pay()에 final을 붙인 이유를 정확히 말할 수 있어야 한다. "로깅 → 호출 → 검증 → 변환" 순서는 정책이므로 자식이 건드리면 안 된다. 자식이 흐름을 바꿀 수 있으면 어떤 PG는 로그가 안 남고 어떤 PG는 검증을 건너뛰는 상태가 조용히 생긴다.

골격 구현을 끼우는 시점 — 순서를 뒤집지 마라

1확장 지점을 인터페이스로 먼저 끊는다 — 계약이 먼저다항상
2구현체를 둘 이상 만들어 본다 — 중복은 추측이 아니라 관찰로 확인한다항상
3중복이 실제로 보이면 그때 계약 아래에 골격을 끼운다조건부
4구현체가 하나뿐인데 미리 Abstract~부터 만든다피한다

골격을 먼저 만들면 두 번째 구현이 나타났을 때 골격이 그 구현에 안 맞는다는 것을 알게 되고, 그때는 이미 자식들의 상속 슬롯을 다 쓴 상태다.

8. 템플릿 메서드 vs 전략 — 상속으로 끼울 것인가, 합성으로 끼울 것인가

7절의 AbstractPaymentGateway가 쓴 기법에는 이름이 있다. 템플릿 메서드 패턴이다. 그리고 6절에서 PaymentGateway 구현체를 갈아 끼운 것은 전략 패턴이다. 둘 다 "공통 흐름은 두고 다른 부분만 갈아 끼운다"는 같은 목적을 가지는데, 끼우는 메커니즘이 다르다.

상속 템플릿 메서드 — 흐름이 부모에 있고, 구멍만 자식이 채운다
public abstract class AbstractSettlementJob {

    // final: 이 순서는 정책이므로 자식이 못 바꾼다
    public final void run(LocalDate date) {
        List<Order> orders = load(date);
        BigDecimal fee = calculateFee(orders);   // 여기만 갈린다
        report(date, orders, fee);
    }

    protected abstract BigDecimal calculateFee(List<Order> orders);
}

class TossSettlementJob extends AbstractSettlementJob {
    @Override protected BigDecimal calculateFee(List<Order> o) { ... }
}

// 사용: "무엇을 끼울지"가 곧 클래스 선택이다
new TossSettlementJob().run(date);
합성 전략 — 갈리는 부분이 독립된 타입이 되고, 인스턴스를 갈아 끼운다
public interface FeePolicy {
    BigDecimal calculate(List<Order> orders);
}

public class SettlementJob {

    private final FeePolicy feePolicy;   // 갈아 끼울 부분을 필드로

    public SettlementJob(FeePolicy feePolicy) {
        this.feePolicy = feePolicy;
    }

    public void run(LocalDate date) {
        List<Order> orders = load(date);
        BigDecimal fee = feePolicy.calculate(orders);
        report(date, orders, fee);
    }
}

new SettlementJob(new FlatFeePolicy()).run(date);

테스트자식을 만들어야 함가짜 전략을 넣으면 끝

8-1. 결정적 차이 — 축이 둘 이상일 때 곱셈과 덧셈이 갈린다

언제 템플릿 메서드가 맞는가

  • 흐름의 순서 자체가 지켜야 할 정책일 때 (로깅 → 호출 → 검증)
  • 갈리는 부분이 그 흐름 밖에서는 아무 의미가 없을 때 — callPgApi는 PG 호출 흐름에서 떼어 놓으면 의미 없는 조각이다
  • 자식이 부모의 보호된 도구(protected 헬퍼, 공유 로거)를 써야 할 때

언제 전략이 맞는가

  • 갈리는 부분이 그 자체로 이름을 가진 독립된 개념일 때 (수수료 정책, 할인 정책, 재시도 정책)
  • 다른 곳에서도 재사용되거나, 런타임 조건에 따라 골라야 할 때
  • 갈리는 축이 둘 이상일 때 — 이 조건이 결정적이다

실무에서는 둘을 겹쳐 쓴다 — 6절과 7절이 정확히 그 예다

바깥 계약은 전략(인터페이스 주입)으로 끊고,
구현체들 내부의 중복은 템플릿 메서드로 걷어낸다

PaymentService가 List<PaymentGateway>를 주입받는 것은 전략이고, 그 구현체들이 AbstractPaymentGateway를 상속해 로깅 흐름을 공유하는 것은 템플릿 메서드다. 둘 중 하나를 고르는 문제가 아니다.

9. 구현체가 하나뿐일 때 인터페이스를 둘 것인가

실무에서 가장 자주 부딪히는 판단이 이것이다. OrderService 하나에 OrderServiceImpl 하나. 이 인터페이스는 값을 하는가.

9-1. 먼저 흔한 오해 하나를 걷어낸다 — "스프링 AOP가 인터페이스를 요구한다"

이 말은 요즘 기준으로 틀렸다. 스프링이 @Transactional 같은 부가 기능을 붙이는 방법은 두 가지다.

테스트 대역도 자동 정당화가 되지 않는다 Mockito는 바이트코드를 생성해 구체 클래스도 mock 할 수 있다. 그러니 mock을 쓸 목적이라면 인터페이스가 없어도 된다. 다만 mock이 아니라 손으로 만든 가짜 구현(fake) — 예를 들어 HashMap으로 동작하는 InMemoryOrderRepository — 을 쓰고 싶다면 갈아 끼울 상위 타입이 필요하므로 이때는 인터페이스가 값을 한다.

9-2. 인터페이스가 실제로 값을 하는 조건 — 셋뿐이다

1
두 번째 구현이 실제로 예정돼 있다. "언젠가 생길지도 모른다"가 아니라 "다음 분기에 카카오페이가 붙는다" 수준의 구체성이어야 한다.
2
아키텍처 경계에서 의존 방향을 뒤집어야 한다. 이것이 가장 강한 근거다. 멀티모듈에서 domain 모듈이 infra 모듈을 컴파일 의존하면 안 되는데, 도메인은 저장을 해야 한다. 이때 OrderRepository 인터페이스를 domain 모듈에 두고 구현체를 infra 모듈에 두면 화살표가 infra → domain 한 방향으로만 흐른다. 이것이 의존성 역전 원칙(DIP)이다.
3
갈아 끼울 가짜 구현이 테스트에 실제로 필요하다. 느린 외부 API, 결제 승인, 메일 발송처럼 테스트에서 진짜로 부르면 안 되는 의존이다.

세 조건 중 하나도 아닌데 Impl을 찍어내면 생기는 일

파일 수와 탐색 비용만 늘어난다. 인터페이스를 타고 들어가면 구현이 하나뿐인 경험이 반복되면, 개발자는 인터페이스를 신뢰하지 않게 되고 결국 IDE의 "구현으로 이동"만 누르게 된다. 그 순간 그 인터페이스는 아무 정보도 주지 않는 중간 파일이 된다.

미래를 위한 추상화는 대체로 틀린 추상화가 되고,
두 번째 구현이 생긴 뒤에 뽑은 인터페이스가 정확한 인터페이스다
관례적 낭비 조건 하나도 없이 1:1 Impl
// OrderService.java
public interface OrderService {
    OrderResult place(OrderCommand cmd);
    void cancel(Long orderId);
}

// OrderServiceImpl.java  — 유일한 구현
@Service
public class OrderServiceImpl implements OrderService {
    // 인터페이스와 시그니처가 글자 하나까지 같다
    // 메서드를 하나 추가할 때마다 두 파일을 고친다
}
기본값 클래스로 두고, 필요해지면 뽑는다
// OrderService.java  — 클래스 하나로 시작한다
@Service
public class OrderService {
    public OrderResult place(OrderCommand cmd) { ... }
    public void cancel(Long orderId) { ... }
}

10. 실무 함정 — 배포된 인터페이스에 메서드 추가하기

이 절이 이 주제의 실무 핵심이다. 인터페이스를 쓰기 시작한 순간부터 계속 부딪히게 되는 문제이고, Java 8이 default 메서드를 도입한 이유 자체가 여기 있다.

10-1. 추상 메서드를 추가하면 이미 배포된 구현체가 전부 깨진다

public interface PaymentGateway {
    PayResult pay(PayRequest request);
    CancelResult cancel(String transactionId);

    RefundResult partialCancel(String txId, Money amount);   // 새로 추가
}

이 인터페이스를 구현한 모든 클래스가 그 순간 컴파일 에러가 된다. 구현하지 않은 추상 메서드가 생겼기 때문이다.

우리 저장소 안에 구현체가 셋뿐이라면 셋을 고치면 된다. 문제는 구현체가 우리 손 밖에 있을 때다.

10-2. default 메서드가 정확히 이 문제를 풀려고 나왔다

default 메서드란 인터페이스가 메서드의 기본 구현까지 함께 제공해서, 구현체가 재정의하지 않으면 그 기본 구현이 실행되게 하는 문법이다. 구현체 입장에서는 아무것도 안 해도 메서드가 생긴 셈이라 재컴파일 없이 그대로 동작한다.

public interface PaymentGateway {
    PayResult pay(PayRequest request);

    // 새 기능을 default로 추가한다. 기존 구현체는 손대지 않아도 컴파일되고,
    // 호출하면 아래 기본 구현이 실행된다.
    default boolean supportsPartialCancel() {
        return false;   // 보수적 기본값 — 지원하는 구현체만 재정의한다
    }
}
이 기본값이 왜 false인지가 중요하다 기존 구현체는 부분 취소를 구현한 적이 없으므로 "지원하지 않는다"가 사실이다. 기본값이 true였다면, 아무것도 안 한 기존 구현체들이 갑자기 "부분 취소를 지원한다"고 거짓말을 하게 되고 호출부는 그 말을 믿고 부분 취소를 시도한다.
default의 기본값은 "기능을 켜는 쪽"이 아니라 "끄는 쪽"으로 잡는다

10-3. 소스 호환과 바이너리 호환은 다르다 가산점

메서드 추가의 영향을 정확히 말하려면 두 종류의 호환성을 구분해야 한다.

소스 호환
source compatibility — 기존 소스 코드를 다시 컴파일했을 때 성공하는가
바이너리 호환
binary compatibility — 이미 컴파일된 .class 파일을 재컴파일 없이 그대로 실행했을 때 링크가 되는가
배포된 인터페이스를 바꿀 때 — 무엇이 언제 깨지는가
변경소스 호환 (재컴파일)바이너리 호환 (링크)실행 시 무슨 일이 일어나는가
추상 메서드 추가즉시 깨짐 — 컴파일 에러유지됨 — 링크는 된다기동은 정상. 그 메서드를 처음 호출하는 순간 AbstractMethodError
default 메서드 추가유지됨유지됨재정의하지 않은 구현체는 default 구현이 실행된다
default 메서드 추가 + 다른 인터페이스에 같은 시그니처 존재깨질 수 있음 — inherits unrelated defaults대체로 유지재컴파일할 때 드러난다 — 둘 다 구현한 클래스만 영향
메서드 제거 / 시그니처 변경깨짐깨짐NoSuchMethodError — 공개 API에서는 사실상 금지

진단 카드 — AbstractMethodError를 보면 이 순서로 확인한다

1스택트레이스의 메서드가 인터페이스에 최근 추가된 것인지 확인 — 라이브러리 릴리스 노트를 본다먼저
2그 인터페이스의 구현체가 우리 저장소 밖에 있는지 확인 — 있으면 원인 확정확정
3임시 조치: 라이브러리 버전 롤백 또는 구현체 재컴파일 후 메서드 구현조치
4근본 조치: 우리가 라이브러리 쪽이라면 추상 메서드를 default로 되돌리고 보수적 기본값을 넣는다예방

11. default는 만능이 아니다 — 조용히 틀린 값을 물려준다

10절에서 멈추면 절반만 아는 것이다. default 메서드는 하위 호환을 지키는 대신 다른 위험을 들여온다.

default는 구현체가 "요청한 적 없는 동작"을 물려받게 만든다

문제의 뿌리는 이렇다. 추상 메서드였다면 구현체 작성자가 반드시 그 메서드를 보고 직접 판단해서 코드를 썼을 텐데, default라서 아무도 보지 않은 채 동작이 생긴다.

위험 도메인 값을 기본 구현이 마음대로 정한다
public interface PaymentGateway {
    PayResult pay(PayRequest request);

    default Money fee(Money amount) {
        // "대부분의 PG가 3%니까 기본으로 3%를 계산해 주자"
        return amount.multiply(new BigDecimal("0.03"));
    }
}

// 수수료가 1.8%인 PG사 구현체 — fee()를 재정의하지 않았다.
// 작성자는 이 메서드가 인터페이스에 생겼다는 사실 자체를 모른다.
class NiceGateway implements PaymentGateway {
    @Override public PayResult pay(PayRequest request) { ... }
    // fee()를 안 썼는데 컴파일이 된다. 그리고 3%를 반환한다.
}
안전 판단이 필요한 값은 추상으로 남긴다
public interface PaymentGateway {
    PayResult pay(PayRequest request);

    Money fee(Money amount);   // 추상 — 구현체가 반드시 답해야 한다

    // 진화가 꼭 필요하다면 "틀릴 수 없는 값"만 default로
    default boolean supportsPartialCancel() { return false; }
    default List<Receipt> receipts() { return List.of(); }
}

class NiceGateway implements PaymentGateway {
    @Override public PayResult pay(PayRequest request) { ... }
    @Override public Money fee(Money amount) {          // 강제된다
        return amount.multiply(new BigDecimal("0.018"));  // 1.8%
    }
}

11-1. 또 하나의 얼굴 — default는 상태에 접근할 수 없다(자기 사용)

인터페이스에는 인스턴스 필드가 없으므로(2절), default 메서드가 뭔가 계산하려면 같은 인터페이스의 다른 추상 메서드를 호출하는 수밖에 없다.

public interface Cart {
    List<Item> items();                        // 추상

    default Money total() {
        return items().stream()                // 자기 인터페이스의 다른 메서드를 부른다
                      .map(Item::amount)
                      .reduce(Money.ZERO, Money::plus);
    }
}

default 메서드 사용 4원칙 — 그대로 인출한다

  1. 용도는 "인터페이스 진화"이지 "구현 재사용"이 아니다. 코드를 나눠 쓰고 싶으면 추상 클래스(골격 구현)를 쓰는 것이 맞다.
  2. 기본값은 보수적으로. "기능 없음", "지원 안 함", "빈 결과"처럼 틀릴 수 없는 값을 준다. 도메인 값을 추측해서 채우지 않는다.
  3. 구현체가 반드시 자기 사정에 맞게 판단해야 하는 것은 default로 만들지 않는다. 컴파일 에러를 감수하고 추상 메서드로 두는 것이 안전한 경우가 있다.
  4. 자기 사용(self-use) 구조는 문서화한다. 어떤 추상 메서드를 호출하는지 적어야 구현체가 성능·동시성 측면을 판단할 수 있다.

12. 선택 기준 · 인출 카드

12-1. 선택 기준 요약 — 세 줄

1
구현이 여럿이거나 여럿이 될 확장 지점 → 인터페이스 (기본값)
2
그 구현체들이 상태나 흐름을 실제로 공유하기 시작함 → 인터페이스 아래에 추상 클래스(골격 구현) 추가
3
추상 클래스 단독 사용은 계약을 외부에 노출할 필요가 없고 상속 계층 내부 전용일 때 정도로 제한한다 — 자식의 단일 상속 슬롯을 영구히 소비하므로 비용이 크다

12-2. 인출 카드 — 면접 전날 이것만

① 공통점 · 갈림 (여기서 시작한다)

공통 2가지
둘 다 new 불가 · 둘 다 미구현 메서드 강제 → 계약은 양쪽 다 건다
갈림 2가지
① 상태(필드)+생성자는 추상 클래스만 ② 다중 부착은 인터페이스만
②가 되는 이유가 ①이다 — 금지와 허용을 가른 것은 상태의 유무

② 실무 조립 순서 (세 단계)

인터페이스로 계약→ 중복 관찰 후 골격 추상 클래스→ 축이 둘 이상이면 전략(합성)

겹쳐 쓴다 — 바깥 계약은 전략, 내부 중복 제거는 템플릿 메서드.

③ 배포된 인터페이스에 메서드를 추가할 때 (이 주제의 핵심)

추상 추가

④ 자주 나오는 반문에 대한 한 줄 대응

반문"default 있으니 추상 클래스 불필요?" → 상태 · 생성자 · protected/final 셋이 남는다. 반문"다중 상속 왜 금지?" → 메서드가 아니라 상태가 겹쳐서. 동작 충돌은 컴파일 에러로 명시 강제. 반문"구현 하나인데 인터페이스?" → 두 번째 구현 예정 · DIP 경계 · 테스트 fake 셋 중 하나일 때만. 반문"AOP 때문에 필요하지 않나?" → 부트 기본은 CGLIB이라 인터페이스 없이도 걸린다. 반문"템플릿 vs 전략?" → 축이 둘 이상이면 전략(곱셈 vs 덧셈).

13. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 펼쳐서 읽기만 하면 "아는 것 같은 느낌"만 남고 인출은 안 된다. 막힌 질문은 해당 절로 돌아간다.

Java 8부터 인터페이스도 default 메서드로 구현을 가질 수 있는데, 이제 추상 클래스는 필요 없는 것 아닌가요?힌트: 남는 차이가 정확히 셋이다 — 그리고 목적이 애초에 다르다 핵심

아니다. 남는 차이가 셋이다.

1인스턴스 필드. default 메서드는 상태를 가질 수 없다. 공유 캐시·로거·커넥션 설정처럼 인스턴스마다 들고 있어야 하는 것이 필요한 공통 로직은 추상 클래스만 가능하다. 인터페이스의 필드는 전부 public static final 상수라 인스턴스별 상태가 아니다. 2생성자. 자식에게 초기화를 강제하고 불변 필드를 세팅할 수 있다. "로거 없이는 이 계열의 객체를 만들 수 없다"를 컴파일러가 지키게 하려면 생성자가 필요하다. 3접근 제어와 final. protected 헬퍼로 자식에게만 도구를 물려주는 것, final 메서드로 템플릿 흐름을 고정해 자식이 순서를 못 바꾸게 하는 것 — 둘 다 추상 클래스의 영역이다.

그리고 결론으로 이걸 붙이면 좋다.

default의 진짜 용도는 "구현 재사용"이 아니라 "이미 배포된 구현체를 깨지 않고 인터페이스를 진화시키는 것"이다

목적이 다르기 때문에 추상 클래스를 대체하지 못한다. 코드를 나눠 쓰고 싶으면 골격 구현(추상 클래스)이 맞고, 배포된 계약에 메서드를 하나 더 얹고 싶을 때가 default다.

왜 클래스 다중 상속은 안 되는데 인터페이스는 여러 개 구현할 수 있나요?힌트: 겹치는 게 "메서드"인지 "필드"인지 핵심

다이아몬드 문제의 핵심은 메서드 충돌이 아니라 상태(필드) 충돌이기 때문이다.

두 부모 클래스가 각자 필드를 갖고 있으면 — 자식 인스턴스에 그 필드가 한 벌인지 두 벌인지, 어느 생성자를 어떤 순서로 돌려야 하는지, super가 어느 쪽을 가리키는지 언어가 임의로 정하지 않으면 답이 없다. Java는 이 모호함을 문법으로 떠넘기는 대신 아예 금지했다.

인터페이스에는 물려받을 상태가 없으므로 이 문제가 발생하지 않는다. 겹칠 수 있는 것은 default 메서드의 몸통뿐이고, 그건 컴파일 에러(inherits unrelated defaults)로 자식에게 명시적 선택을 강제하면 끝난다 — A.super.name()처럼 어느 부모인지 지목하면 된다.

금지와 허용을 가른 것은 상태의 유무다

한 걸음 더 — C++는 같은 문제를 가상 상속(virtual inheritance)이라는 문법으로 프로그래머에게 떠넘겼다. 즉 "다중 상속은 원리적으로 불가능한 것"이 아니라 Java가 복잡도를 언어에서 걷어내기로 선택한 것이라고 말하면 정확도가 올라간다.

구현체가 하나뿐인데도 인터페이스를 미리 만들어야 하나요?힌트: 흔히 대는 근거 두 개는 요즘 기준으로 성립하지 않는다 시니어 변별

기계적으로 만들면 안 된다. 그리고 흔히 대는 근거 두 개는 요즘 기준으로 성립하지 않는다.

성립하지 않는 근거

  • "스프링 AOP 때문에 필요하다" — 틀렸다. 스프링 부트의 기본 프록시는 CGLIB(대상 클래스를 상속)이라 인터페이스 없이도 @Transactional이 걸린다. 인터페이스가 반드시 필요한 것은 JDK 동적 프록시 쪽인데 부트의 기본값이 아니다.
  • "테스트 때문에 필요하다" — 절반만 맞다. Mockito는 바이트코드를 생성해 구체 클래스도 mock 할 수 있다. 다만 mock이 아니라 손으로 만든 fake(InMemoryOrderRepository 같은)를 끼우고 싶다면 갈아 끼울 상위 타입이 필요하다.

실제로 값을 하는 조건 셋

  • 두 번째 구현이 구체적으로 예정 — "언젠가"가 아니라 "다음 분기에 PG사 하나 더".
  • 아키텍처 경계에서 의존 방향 역전(DIP) — 도메인 모듈에 OrderRepository를 두고 구현을 인프라 모듈에 두면 컴파일 의존이 인프라 → 도메인 한 방향이 된다. 가장 강한 근거는 이것이다.
  • 갈아 끼울 가짜 구현이 테스트에 실제로 필요 — 느린 외부 API, 결제 승인, 메일 발송.

이 셋에 해당 없이 서비스마다 1:1로 Impl을 찍어내는 것은 파일 수와 탐색 비용만 늘린다. 인터페이스를 타고 들어가면 구현이 하나뿐인 경험이 반복되면 개발자는 인터페이스를 신뢰하지 않게 되고 결국 IDE의 "구현으로 이동"만 누르게 된다.

지금은 클래스로 두고,
두 번째 구현이 생기는 순간 Extract Interface로 뽑는다

이 한마디를 붙이면 설계 감각이 드러난다 — 미래를 위해 미리 만든 추상화는 대체로 틀린 추상화가 되고, 두 번째 구현을 보고 뽑은 인터페이스가 정확한 인터페이스다. IDE의 Extract Interface는 호출부를 자동으로 바꿔 주므로 나중에 뽑는 비용이 거의 없다.

템플릿 메서드 패턴과 전략 패턴의 차이는 무엇인가요?힌트: 목적은 같다 — 갈리는 것은 "끼우는 메커니즘" 핵심

목적은 같고 끼우는 메커니즘이 다르다. 템플릿 메서드는 상속 — 추상 클래스가 흐름을 final로 고정하고 abstract 구멍만 자식이 채운다. 전략은 합성 — 갈리는 부분을 인터페이스로 뽑아 구현체를 필드로 주입받아 갈아 끼운다.

전략이 유리한 지점은 셋이다. 런타임에 바꿔 끼울 수 있고, 단일 상속 슬롯을 소비하지 않으며, 테스트에서 가짜 전략만 넣으면 된다.

상속: 3 × 2 = 6개 서브클래스   vs   합성: 3 + 2 = 5개 조각 + 조합

결정적인 차이는 갈리는 축이 둘 이상일 때 나온다. 수수료 정책 3가지 × 리포트 형식 2가지를 상속으로 표현하면 서브클래스가 6개 필요하지만, 전략으로는 3 + 2 = 5개를 만들어 조합한다. 축이 하나 늘 때 상속은 곱하기로, 합성은 더하기로 늘어난다. "상속보다 합성"이라는 격언의 구체적 근거가 이 곱셈과 덧셈의 차이다.

반대로 템플릿 메서드가 맞는 자리도 분명하다. ① 흐름의 순서 자체가 지켜야 할 정책이고, ② 갈리는 조각이 그 흐름 밖에서는 의미가 없으며, ③ 자식이 부모의 protected 상태를 써야 할 때다.

실무에서는 겹쳐 쓴다 — 바깥 계약은 전략(인터페이스 주입)으로 끊고, 구현체들 내부의 중복은 템플릿 메서드로 걷어낸다.

인터페이스에 default 메서드를 추가하면 이미 배포된 구현체에는 무슨 일이 생기나요?힌트: 소스 호환과 바이너리 호환을 나눠서 답한다 가산점

소스 호환과 바이너리 호환을 나눠서 답하면 정확해진다.

default 메서드 추가 — 둘 다 유지

재컴파일 없이 링크가 되고, 구현체가 재정의하지 않았으면 호출 시 인터페이스의 default 구현이 실행된다. 그래서 공개 인터페이스의 진화는 default + 보수적 기본값이 정석이다.

추상 메서드 추가 — 소스 호환 즉시 파괴

구현체를 다시 컴파일하면 컴파일 에러다. 그런데 바이너리 호환은 유지되므로 기존 .class는 링크되고 기동도 정상이다. 문제는 그 메서드를 실제로 호출하는 순간 AbstractMethodError가 터진다는 것.

이 조합이 위험한 이유 — 발견이 늦다 배포는 성공하고 헬스체크도 통과하는데, 그 코드 경로를 처음 타는 요청에서만 죽는다. 라이브러리 버전만 올렸는데 특정 API에서만 AbstractMethodError가 나는 상황이 대개 이 구조다. "컴파일한 버전"과 "실행 중인 버전"이 다르다는 것이 신호다.

다만 default가 만병통치는 아니라는 점까지 덧붙이면 좋다 — 구현체가 자기 사정에 맞게 반드시 판단해야 하는 값(수수료율 같은)을 default로 채워 두면, 재정의하지 않은 구현체가 조용히 틀린 값을 반환하고 예외 없이 잘못된 결과가 흘러간다. 기본값은 "기능 없음", "지원 안 함", "빈 결과"처럼 틀릴 수 없는 쪽으로 잡는다.

추상 클래스의 메서드와 인터페이스의 default 메서드가 같은 시그니처로 겹치면 누가 이기나요?힌트: "클래스가 이긴다" 가산점

클래스가 이긴다(class wins). 슈퍼클래스에서 상속한 구체 메서드가 있으면, 인터페이스의 default 구현은 아예 후보에서 밀려난다. 컴파일 에러도 나지 않고 조용히 클래스 쪽이 선택된다.

interface Greeter { default String hello() { return "from interface"; } }

class Base { public String hello() { return "from class"; } }

class Child extends Base implements Greeter { }   // 컴파일 OK

// new Child().hello()  ->  "from class"   (클래스가 이긴다)

규칙은 세 단계로 정리된다.

  1. 클래스 > 인터페이스 — 슈퍼클래스의 구체 메서드가 최우선.
  2. 더 구체적인 인터페이스가 우선 — B extends A일 때 B의 default가 A의 것을 덮는다.
  3. 둘 다 아니면 컴파일 에러 — 서로 무관한 두 인터페이스의 default가 겹치면 자식이 A.super.x()로 명시해야 한다.
실무 함정 이 규칙 때문에 골격 추상 클래스를 상속하면서 동시에 default를 가진 인터페이스를 구현하면, 내가 기대한 default가 조용히 무시될 수 있다. "인터페이스에 default를 넣었는데 왜 안 불리지?"의 정체가 대개 이것이다.
인터페이스에서 toString(), equals()를 default로 제공할 수 있나요?힌트: 위 "클래스가 이긴다" 규칙의 필연적 귀결 가산점

불가능하다. 컴파일 에러다. 인터페이스는 Object의 public 메서드(toString, equals, hashCode)를 default로 구현할 수 없다.

이유는 앞 질문과 같은 뿌리다. 모든 클래스는 Object를 상속하므로 이미 그 메서드의 구체 구현을 갖고 있다. "클래스가 이긴다" 규칙에 따라 그 default는 어떤 경우에도 선택될 수 없는 죽은 코드가 된다. 절대 실행되지 않을 코드를 쓰게 두면 "왜 내 toString이 안 불리지?"라는 혼란만 남으므로 언어가 아예 금지한 것이다.

인터페이스는 "할 수 있는 일"을 정의하지
"동일성·표현" 같은 객체의 정체성은 정의하지 않는다

대신 이렇게 한다 — 인터페이스에 String describe(); 같은 별도 이름의 추상/기본 메서드를 두거나, 공통 toString이 정말 필요하면 골격 추상 클래스에 둔다. AbstractList가 equals/hashCode/toString을 대신 구현해 주는 것이 정확히 그 자리다.

추상 메서드가 하나도 없는 추상 클래스는 왜 만드나요?힌트: abstract가 막는 것은 "구현 누락"만이 아니다  심화 

abstract 키워드가 하는 일은 두 가지인데, 그중 "인스턴스화 금지"는 추상 메서드가 없어도 유효하다. 그래서 다음 세 용도로 쓴다.

1인스턴스화 자체를 막는다. AbstractOrderEvent처럼 "이 타입 자체로는 존재할 수 없고 반드시 구체 이벤트여야 한다"를 컴파일러가 지키게 한다. 2어댑터(adapter). 메서드가 많은 인터페이스의 모든 메서드를 빈 몸통으로 미리 구현해 두고, 구현자는 필요한 것만 재정의하게 한다. Swing의 MouseAdapter가 고전적 예다. 3공통 상태·생성자만 물려주는 골격. 추상 메서드는 없지만 protected 로거·타임아웃 설정·protected 헬퍼를 물려주는 베이스. 다만 이 경우 "상속을 강제할 만큼 값을 하는가"를 한 번 의심해야 한다 — 자식의 단일 상속 슬롯을 영구히 소비하기 때문이다.

반대 방향의 함정 — 단지 인스턴스화를 막고 싶은 유틸 클래스라면 abstract가 아니라 final 클래스 + private 생성자가 정확한 도구다. abstract로 막으면 "상속해서 쓰라"는 잘못된 신호를 준다.

추상 클래스의 생성자에서 추상 메서드를 호출하면 어떤 일이 생기나요?힌트: 부모 생성자가 먼저 끝난다 함정

자식의 필드가 아직 초기화되지 않은 상태에서 자식의 오버라이드 메서드가 실행된다. 결과는 null이나 0이고, 운이 나쁘면 NullPointerException이다.

abstract class AbstractJob {
    AbstractJob() { init(); }          // 부모 생성자가 자식 메서드를 부른다
    protected abstract void init();
}

class ReportJob extends AbstractJob {
    private final List<String> rows = new ArrayList<>();
    protected void init() { rows.add("header"); }  // rows가 아직 null -> NPE
}

실행 순서가 원인이다. new ReportJob() → 자식 생성자 진입 → super()가 먼저 완주 → 그 안에서 init()이 자식 버전으로 디스패치 → 자식의 필드 초기화는 아직 시작도 안 함 → rows는 null.

생성자에서는 재정의 가능한 메서드를 호출하지 않는다

해법 셋. ① 초기화가 필요하면 생성자 파라미터로 받아 부모가 직접 세팅한다(그래서 생성자 강제가 값을 한다). ② 그 메서드를 final 또는 private로 만들어 디스패치 자체를 없앤다. ③ 정말 시점이 필요하면 생성 이후 별도의 start()/afterPropertiesSet() 단계로 분리한다.

이 함정이 이 주제와 이어지는 지점 — 인터페이스에는 생성자가 없으니 이 문제 자체가 없다. 추상 클래스는 "상태와 생성자"를 얻은 대가로 "초기화 순서"라는 새 위험을 함께 받는다.

골격 구현(추상 클래스)을 쓰고 싶은데 그 클래스가 이미 다른 클래스를 상속 중이면 어떻게 하나요?힌트: 슬롯이 없으면 "가진다"로 바꾼다 시니어 변별

골격 구현을 상속하는 대신 "안에 하나 만들어 들고 위임"한다. 이 기법을 시뮬레이트한 다중 상속(simulated multiple inheritance)이라고 부른다.

// 이미 LegacyBase를 상속 중이라 extends 슬롯이 없다
class TossGateway extends LegacyBase implements PaymentGateway {

    // 골격 구현을 상속한 private 내부 클래스를 하나 만들어 들고 있는다
    private class Skeleton extends AbstractPaymentGateway {
        Skeleton(PgApiLogger logger) { super(logger); }
        protected PgResponse callPgApi(PayRequest r) {
            return TossGateway.this.callToss(r);   // 바깥 인스턴스로 되돌린다
        }
    }

    private final Skeleton skeleton = new Skeleton(logger);

    public PayResult pay(PayRequest r) { return skeleton.pay(r); }  // 전달(forwarding)
}

얻는 것 — 골격의 공통 흐름(로깅 → 호출 → 검증)을 그대로 재사용하면서도 단일 상속 슬롯은 LegacyBase에 남겨 둔다. 치르는 값은 전달 메서드를 손으로 써야 하는 보일러플레이트다.

이 답이 시니어 신호인 이유 "골격 구현은 상속으로만 쓸 수 있다"는 제약이 절대적이지 않다는 것을 알고 있다는 뜻이고, 동시에 단일 상속 슬롯이 유한 자원이라는 인식이 몸에 배어 있다는 뜻이다. 같은 발상이 "상속 대신 위임"(예: ArrayList를 상속하지 말고 필드로 들고 감싸기)으로 이어진다.
배포된 인터페이스에 메서드를 추가해야 하는데 default로도 안전한 기본값을 못 정하겠다면?힌트: 인터페이스를 늘리지 말고 "쪼갠다" 시니어 변별

기존 인터페이스를 건드리지 말고, 새 능력을 별도의 능력 인터페이스(capability interface)로 뽑는다.

// 기존 계약은 그대로 둔다 — 아무도 안 깨진다
public interface PaymentGateway { PayResult pay(PayRequest r); }

// 새 능력은 "붙일 수 있는 인터페이스"로 따로 만든다
public interface PartialCancelable {
    RefundResult partialCancel(String txId, Money amount);
}

// 지원하는 구현체만 추가로 붙인다 — 다중 구현이 되니까 가능한 설계다
class TossGateway implements PaymentGateway, PartialCancelable { ... }
class NiceGateway implements PaymentGateway { ... }        // 손 안 댐

// 호출부는 능력을 질의한다
if (gateway instanceof PartialCancelable pc) {
    pc.partialCancel(txId, amount);
} else {
    throw new UnsupportedOperationException("부분 취소 미지원 PG");
}

이 설계가 성립하는 이유가 곧 이 문서의 갈림 ②다 — 인터페이스는 여러 개를 붙일 수 있으니 "능력 단위로 쪼개기"가 가능하다. 추상 클래스로는 슬롯이 하나라 이 방법 자체가 없다. 인터페이스를 작게 유지하라는 인터페이스 분리 원칙(ISP)의 실전형이기도 하다.

대안 1 — 능력 인터페이스 (권장)

기존 구현체 전부 무손상. 호출부에 instanceof/supports() 질의가 생기는 것이 값이다. 능력이 정말 선택적일 때 맞다.

대안 2 — 버전 인터페이스

PaymentGatewayV2 extends PaymentGateway로 새 계약을 상속으로 확장하고 호출부를 점진 이전. 능력이 결국 전부 필수가 될 예정일 때 쓴다.

마지막 카드 — default로 throw new UnsupportedOperationException()을 던지게 두는 방법도 있다. 컴파일은 깨지지 않고 틀린 값 대신 명확한 실패가 나므로, "조용히 틀리는 것"보다는 낫다. 다만 런타임에야 드러나는 계약이므로 능력 인터페이스가 우선이다.

Kotlin 인터페이스는 프로퍼티를 선언할 수 있던데, 그럼 상태를 가질 수 있는 건가요?힌트: 프로퍼티 선언과 backing field는 다르다  Kotlin 

아니다. Kotlin 인터페이스의 프로퍼티는 backing field(값을 실제로 담는 칸)를 가질 수 없다. 선언은 추상 프로퍼티이거나 getter를 직접 구현한 계산 프로퍼티여야 한다. 즉 값을 실제로 저장하는 것은 구현 클래스의 몫이고, 결론은 Java와 같다 — 인터페이스에는 인스턴스 상태가 없다.

interface Gateway {
    val name: String                      // 추상 — 구현체가 제공해야 한다
    val label: String get() = "PG:$name"   // 계산 프로퍼티 — 저장하지 않는다
    var retryCount: Int = 0                // 컴파일 에러 — 인터페이스 프로퍼티는 초기화 불가
}

class TossGateway : Gateway {
    override val name = "toss"              // 여기서 비로소 저장 칸이 생긴다
}

같이 알아 둘 Kotlin 차이 셋.

1클래스가 기본 final이다. 상속하려면 open이나 abstract를 명시해야 한다 — "상속은 설계된 경우에만"이 언어 기본값으로 들어와 있다. 2충돌 해소 문법이 다르다. Java의 A.super.name()이 Kotlin에서는 super<A>.name()이다. 겹치면 명시하라는 규칙 자체는 같다. 3by 위임이 언어 기능이다. Java에서 손으로 쓰던 전달 메서드를 class Toss(g: Gateway) : Gateway by g로 대체할 수 있어 "상속보다 합성"의 비용이 더 싸다.
인터페이스에 상수만 잔뜩 모아 두고 implements 해서 쓰는 방식은 어떤가요?힌트: 그 상수는 곧 공개 API가 된다 함정

상수 인터페이스(constant interface)는 안티패턴이다. 이유가 셋이다.

  • 구현 세부사항이 공개 API로 샌다. 어떤 상수를 쓰는지는 내부 사정인데, implements 하는 순간 그 상수들이 클래스의 공개 멤버가 되어 하위 클래스와 사용자에게 노출된다.
  • 제거할 수 없게 된다. 이미 공개된 이상 바이너리 호환 때문에 나중에 지우기 어렵다.
  • 타입의 의미를 오염시킨다. 인터페이스는 "이 타입은 무엇을 할 수 있는가"를 말하는 자리인데, 아무 능력도 선언하지 않은 타입이 만들어진다.

이렇게 하지 않는다

interface PgConstants {
    int TIMEOUT_MS = 3000;
    String VERSION = "v1";
}
class TossGateway implements PgConstants { }

이렇게 한다

public final class PgConstants {
    private PgConstants() {}      // 인스턴스화 금지
    public static final int TIMEOUT_MS = 3000;
}
// 값들이 한 묶음의 타입이라면 enum이 더 낫다

연결 포인트 — 인터페이스에 필드를 쓰면 자동으로 public static final이 붙는다는 사실(2절)은 "상수를 두라"는 초대장이 아니다. 오히려 "인터페이스에는 인스턴스 상태를 둘 수 없다"는 제약의 부산물로 이해해야 한다.

한 줄 요약
인터페이스와 추상 클래스는 둘 다 "미구현 메서드를 자식에게 강제하는 상위 타입"이라는 점에서 같고, 갈리는 지점은 상태(인스턴스 필드)를 가질 수 있는가와 여러 개를 동시에 붙일 수 있는가 둘뿐이며, 이 둘은 사실 하나의 사실이다 — 다중 상속이 금지된 진짜 이유가 물려받을 상태가 두 벌 생기는 다이아몬드 문제이고 상태 없는 인터페이스에는 그 문제가 없기 때문이다. 그래서 실무 기본형은 확장 지점을 인터페이스(can-do 계약)로 끊고, 구현체들의 중복이 실제로 생기면 그 아래에 골격 구현(추상 클래스)을 끼우는 것이며, 여기서 한 걸음 더 들어가는 지점은 이미 배포된 구현체가 있는 인터페이스에 메서드를 추가할 때 — 추상 메서드는 소스 호환을 즉시 깨고 바이너리로는 AbstractMethodError를 남기며, 그것을 풀려고 나온 default 메서드조차 구현체가 알 수 없는 기본 동작을 조용히 물려줘 틀린 결과를 낼 수 있으므로 기본값은 "틀릴 수 없는 값"으로만 잡는다는 것까지가 이 주제의 완성이다.
