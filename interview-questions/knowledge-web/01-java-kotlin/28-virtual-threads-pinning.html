Virtual Thread(Java 21+) — 스레드 모델의 차이, Continuation 원리, pinning, @Transactional 함정
"가상 스레드는 빨라진다"가 아니다. 대기 중 동시성을 높이는 기술이고, 그 대가로 pinning과 커넥션 풀 고갈이라는 두 함정이 따라온다

면접 질문: "Virtual Thread(Project Loom)는 기존 스레드 모델과 무엇이 다른가요? pinning 문제란?"

핵심 관전 포인트 — 가상 스레드는 처리 속도가 아니라 "대기 중 동시성"을 높이는 기술이다. 스레드란 결국 "콜 스택 + 실행 위치"라는 데이터인데, 과거엔 블로킹이 커널 안에서 일어나 JVM이 개입할 타이밍이 없었기에 1:1일 수밖에 없었다. Loom은 JDK가 시스템 콜 직전 경로를 소유한다는 점을 이용해, 블로킹 대신 "epoll 등록 + 스스로 스택을 힙에 얼리고(freeze) 물러나기"로 바꿔치기했다 — 블로킹 스타일 코드 그대로 리액티브급 동시성을 얻는다. 도입 시 함정 두 가지: (1) JVM이 경로를 소유하지 못한 지점(synchronized·JNI)에서 블로킹하면 캐리어에 못박히는 pinning(JDK 24의 JEP 491에서 synchronized는 해소, 네이티브는 그대로), (2) 가상 스레드는 스레드만 해방시킬 뿐 DB 커넥션은 못 푼다 — @Transactional 안 외부 API 콜은 동시성이 폭증한 만큼 커넥션 풀 고갈로 더 크게 터진다.
  • 1
    모델의 차이부터 한 문장으로. 기존 플랫폼 스레드는 OS 스레드와 1:1이라 "자바 스레드가 기다린다 = 비싼 OS 스레드가 논다"였는데, 가상 스레드는 M:N입니다 — 블로킹을 만나면 실행 상태(콜 스택)를 힙으로 옮기고 캐리어 스레드에서 내려와, 그 OS 스레드는 즉시 다른 가상 스레드를 태웁니다. 덕분에 블로킹 스타일 코드를 그대로 두고도 수만 건의 대기를 담을 수 있습니다.
  • 2
    pinning은 "내려오지 못하는 경우"입니다. 원인이 둘인데 성격이 다릅니다 — synchronized는 모니터 소유자가 OS 스레드 단위로 기록돼 프레임만 옮기면 잠금 장부가 어긋나므로 JVM이 옮기지 않는 쪽을 택한 것이고(JDK 21~23), 네이티브(JNI) 프레임은 JVM이 구조를 몰라 힙으로 옮길 수 없어 구조적으로 남습니다. 핀이 나면 캐리어(=코어 수만큼뿐인 OS 스레드)가 통째로 잠들어 확장성이 무너집니다.
  • 3
    버전과 실무 함정까지 붙이면 완성입니다. synchronized 핀은 JDK 24의 JEP 491에서 해소됐지만 잠금의 직렬화는 그대로이고, 네이티브 핀은 남습니다(탐지는 JFR jdk.VirtualThreadPinned — -Djdk.tracePinnedThreads는 JDK 24에서 제거). 더 실무적인 함정은 가상 스레드가 값싸게 만든 것은 자바 스레드일 뿐 DB 커넥션이 아니라는 것 — 톰캣 200 스레드가 해 주던 암묵적 부하 제한이 사라져 커넥션 풀 고갈이 더 크게 터집니다.

0. 질문 + 출제 의도 · 버전 범위 선언

질문 — "Virtual Thread(Project Loom)는 기존 스레드 모델과 무엇이 다른가요? pinning 문제란?"

출제 의도 — 이 질문은 새 기술 도입 판단의 시금석이다. "가상 스레드 쓰면 다 해결"이 아니라 pinning 같은 제약과 기존 코드베이스의 궁합을 먼저 따지는 사람인지 — 즉 하이프와 실제를 구분하는 습관이 있는지를 본다.

약점 A"가상 스레드는 빠릅니다" — 속도와 동시성을 구분하지 못하는 답. 요청 하나가 350ms 걸리던 것이 300ms가 되지는 않는다. 늘어나는 것은 "동시에 기다릴 수 있는 개수"다.
약점 B"OS 스레드보다 가벼운 스레드입니다"에서 멈추는 것 — 왜 가벼운지, 즉 "스택을 상시 보유하지 않고 대기 중엔 힙에 쓴 만큼만 얼려 둔다"는 메커니즘을 대지 못하면 외운 문장이다.
약점 Cpinning을 "synchronized 쓰면 문제된다"로만 아는 것 — 왜 못 내려오는지(모니터 소유자가 OS 스레드 단위로 기록됨)와 구조적으로 남는 원인(네이티브 프레임)을 나눠 말하지 못하면 암기다.
약점 D버전을 뭉개는 것 — JDK 24의 JEP 491로 synchronized 핀은 해소됐다. "핀 됩니다"만 말해도, "이제 안 됩니다"만 말해도 둘 다 반쪽이다.
약점 E도입 함정을 스레드 안에서만 찾는 것 — 실무에서 실제로 터지는 것은 @Transactional + 외부 API + 커넥션 풀이다. 가상 스레드는 스레드를 해방시킬 뿐 커넥션을 풀어 주지 않는다.
합격선모델 차이(1:1 → M:N)를 "실행 상태의 소유권 이동"으로 설명하고 → freeze/thaw로 메커니즘을 대고 → pinning 원인 둘을 성격별로 나누고 → 버전(21~23 / 24+)을 명시하고 → 커넥션 풀·부하 제한까지 끌고 간다.
이 문서가 다루는 버전 범위 — 먼저 못 박고 시작한다 기준선은 JDK 21(가상 스레드가 정식 기능이 된 첫 LTS)이다. JDK 24에서 pinning 동작이 크게 바뀌었으므로, 달라지는 지점마다 "JDK 21~23 기준 / JDK 24 이후"를 명시해 구분한다. 이 구분을 흐리게 말하면 면접에서 오답이 되기 쉬운 주제다.
이 문서의 진행 방향 — 문제 → 메커니즘 → 함정 1절은 왜 필요했나(플랫폼 스레드 1:1의 청구서), 2~5절은 어떻게 동작하나(캐리어 · Continuation · freeze/thaw · 타임라인), 6~7절은 왜 지금에서야 가능한가(개입 타이밍 · GC 능력의 재활용 · 역할 분담), 8~11절은 실무 함정(pinning · 트랜잭션 · ThreadLocal · 도입 체크포인트)이다. 면접 답변 순서도 같다 — 메커니즘으로 신뢰를 얻고, 함정으로 점수를 얻는다.

1. 왜 필요한가 — 플랫폼 스레드 1:1의 청구서

지금까지 우리가 써 온 new Thread(), 톰캣의 워커 스레드, Executors.newFixedThreadPool(200)이 만드는 스레드는 전부 같은 종류다. 운영체제가 만들어 준 진짜 스레드 하나를 자바 객체로 얇게 감싼 것이고, 가상 스레드와 구분하기 위해 이것을 플랫폼 스레드(platform thread)라 부른다. "플랫폼"은 그 아래 깔린 실행 플랫폼, 즉 OS의 스레드에 그대로 대응한다는 뜻이다.

자바 스레드에 대해 하는 모든 일은 OS에 그대로 청구서로 넘어간다
"스레드 하나에 1MB"는 어림값이다 — 정확히 말하는 법 
$ java -XX:+PrintFlagsFinal -version | grep ThreadStackSize
     intx ThreadStackSize     = 2048     {pd product} {default}

# macOS / AArch64 / OpenJDK 21 기준 = 2048KB = 2MB
# 리눅스 x86-64에서는 통상 1024KB(1MB)가 기본값이다
플래그 옆의 {pd product}가 platform dependent(플랫폼 의존) 표시다. 그러니 정확한 문장은 "수백 KB~2MB 수준이며 플랫폼과 JVM 설정에 따라 다르다"이다.

1-1. 낭비의 구조 — 스레드가 "일하는 데"가 아니라 "기다리는 데" 쓰인다

// 톰캣 기본 스레드 풀 200개인 서버에서
public Order getOrder(Long id) {
    Member member = memberClient.get(id);   // 외부 API 300ms — 이 워커는 잠들어 있다
    Order order = orderRepository.find(id); // DB 조회 50ms — 여기서도 잠들어 있다
    return order;                           // 계산은 몇 ms면 끝난다
}

이게 처리량 상한으로 어떻게 이어지는지 한 단계씩 계산해 보자.

① 동시 진행 가능한 요청 = 워커 수 = 200건 ② 워커 하나의 초당 처리량 = 1 / 0.35s = 2.86 건/s ③ 서버 전체 처리량 상한 = 200 × 2.86 = 571 req/s ← 여기서 막힌다 ④ 그때 실제 필요한 CPU = 571 × 5ms = 2.9초/초 ≈ 코어 3개면 충분 ⇒ 8코어 서버라면 CPU 사용률 36% 언저리에서 처리량이 막힌다. ⇒ 201번째 요청은? 워커가 빌 때까지 톰캣 수락 큐에서 대기 — 사용자에겐 "CPU는 노는데 느린 서버"

방향 A — 기다림을 스레드에 담지 않는다

"결과를 기다렸다가 다음 줄로 간다" 대신 "결과가 오면 이 함수를 실행해 달라"고 콜백을 등록하고 스레드는 즉시 반납한다.

  • 스레드 몇 개로 수만 건의 대기를 감당
  • 대가: 코드를 전부 바꿔야 한다
VS
방향 B — 기다림을 담는 그릇을 싸게 만든다

코드는 그대로 두고 스레드의 구현만 갈아 끼운다. 기다림의 비용을 OS 스레드에서 힙의 몇 KB짜리 객체로 낮춘다.

  • 가상 스레드(Project Loom)
  • 순차·블로킹 스타일 그대로
  • 대가: pinning과 부하 제한 소실(8·9절)
// 리액티브: 기다리지 않고 "오면 이걸 해라"를 등록한다
public Mono<Order> getOrder(Long id) {
    return memberClient.get(id)
            .flatMap(member -> orderRepository.find(id))
            .map(this::toResponse);
}
리액티브의 대가 — 핵심은 "호출 스택이 사라진다"는 것 예외가 터지면 스택트레이스에 내 비즈니스 로직 대신 리액터 내부 프레임이 잔뜩 찍히고, "어느 요청 처리 중이었는지"를 알려면 별도 장치가 필요하다. 디버거로 한 줄씩 따라가는 것도, try-catch-finally도, ThreadLocal 기반 도구(트랜잭션 · MDC · SecurityContext)도 그대로는 안 통한다. 게다가 이 전염은 국소적이지 않다 — 경로 위의 라이브러리 하나라도 블로킹이면 전체가 무너지므로 스택 전체를 리액티브로 바꿔야 한다.

2. 2층 구조 — 캐리어 위에 올라타는 가상 스레드

가상 스레드(virtual thread)는 OS 스레드와의 1:1 매핑을 끊고 JVM이 직접 스케줄링하는 경량 스레드다. 이걸 만든 OpenJDK 프로젝트의 코드명이 Loom이다. 2017년에 시작해 2023년 Java 21에 정식 기능으로 들어갔다. loom은 "베틀"이라는 뜻으로, 스레드(실)를 짜는 도구라는 말장난이다.

동작의 뼈대는 네 줄이다 — 이 네 줄이 답변의 골격

1
소수의 OS 스레드가 실행대 역할을 한다. 이 스레드를 캐리어 스레드(carrier thread)라 부른다 — 가상 스레드를 태워 나른다(carry)는 뜻이다.
기본 개수 = CPU 코어 수
2
가상 스레드는 캐리어 위에 올라타서(mount) 실행된다.
이 순간엔 평범한 스레드
3
블로킹 I/O를 만나면 JVM이 그 가상 스레드의 실행 상태를 힙에 떼어 저장하고 캐리어에서 내린다(unmount).
여기가 핵심
4
비워진 캐리어는 즉시 다른 가상 스레드를 태운다. I/O가 끝나면 그 가상 스레드는 아무 캐리어에나 다시 올라타 이어서 실행된다.
캐리어를 갈아타도 무방

}

spring.threads.virtual.enabled=true   // 이 한 줄이 부하 제한기를 걷어낸다는 사실은 9절에서
가장 큰 가치 — 코드 스타일을 바꾸지 않아도 된다

리액티브처럼 코드를 뒤집지 않고, 지금까지처럼 순차적 · 블로킹 스타일로 쓰면 JVM이 알아서 논블로킹처럼 굴려 준다.

스택트레이스도, 디버거도, try-catch-finally도, ThreadLocal 기반 도구도 그대로 살아 있다.

여기서 못 박아 둘 오해 — "빨라진다"가 아니다

가상 스레드는 처리 속도를 높이는 게 아니라 "대기 중 동시성"을 높이는 기술이다.

요청 하나가 350ms 걸리던 것이 300ms가 되지는 않는다. CPU 연산 위주 작업에는 이득이 아예 없다 — 어차피 코어 수만큼만 동시에 돌 수 있으니까.

3. 스레드의 정체 — "콜 스택 + 실행 위치"라는 데이터

여기서부터가 이 문서의 핵심 난관인 Continuation이다. 결론부터 말하면 "스택을 힙에 저장했다가 되살린다"인데, 이 문장이 손에 잡히려면 먼저 스택이 무엇으로 이루어져 있는지를 다시 확인해야 한다.

3-1. 그럼 이 데이터는 어디에 사는가 — 언제냐에 따라 두 곳을 오간다

가상 스레드의 콜 스택이 사는 곳
가상 스레드의 상태콜 스택이 사는 곳그때의 성격
실행 중 (캐리어에 mount됨)캐리어의 진짜 스택 — 캐리어 스택을 빌려 쓴다그 순간엔 평범한 스레드와 완전히 동일하게 동작 (오버헤드 0)

비용 차이의 정체는 "쓴 만큼만"이라는 네 글자다

플랫폼 스레드
태어날 때 수백 KB~2MB를 예약받는다. 실제로 3단 깊이만 쓰든 300단을 쓰든 예약량은 같다.
가상 스레드
자기만의 스택을 상시 보유하지 않는다. 실행할 때만 캐리어 스택을 빌리고, 물러날 때는 쓴 만큼만 힙으로 챙겨 간다.

그래서 생성 비용도 갈린다 — 플랫폼 스레드 생성은 커널에 clone 시스템 콜을 하고 스택 몇 MB를 예약하는 일이지만, 가상 스레드 생성은 커널 시스템 콜 없이 힙에 VirtualThread 객체 하나 할당 + 스케줄러 대기열 등록이 전부다. 객체 new 수준으로 싸다 — "요청마다 만들고 버리는" 모델이 성립하는 근거가 여기 있다.

4. freeze / thaw — 스택과 힙을 오간다

이제 실제로 옮겨지는 그림을 보자. 캐리어 #3 위에서 가상 스레드 V-42가 돌다가 블로킹을 만나는 상황이다. 왼쪽이 캐리어의 진짜 스택, 오른쪽이 힙이고, 세 컷을 나란히 놓으면 무엇이 어디로 가는지가 그대로 보인다.

4-1. "실행 위치"는 왜 따로 백업하지 않는가 — 협조적 스케줄링

freeze는 아무 데서나 일어나지 않고 항상 Continuation.yield()라는 정해진 메서드 호출 지점에서 일어난다. 메서드를 호출한 지점이라는 것은 곧 "돌아올 위치가 이미 스택 프레임의 리턴 주소로 기록돼 있다"는 뜻이다. 그래서 CPU 레지스터를 따로 챙길 필요가 없다.

커널의 방식 — 선점(preemption)
언제든 스레드를 강제로 끊을 수 있다. 그래서 끊긴 순간의 레지스터와 프로그램 카운터를 전부 저장해야 하고, 그 저장소는 커널 안에 있다.

기절한 사람의 기억을 나중에 꺼내는 방식

가상 스레드 — 협조적(cooperative)
본인이 정해진 지점에서 스스로 물러난다. 물러나기 직전이므로 스택에 이미 다 적혀 있다 — 따로 백업할 레지스터가 없다.

잠들기 전에 본인이 일기를 써 두는 방식

왜 JVM만 이걸 할 수 있나 — GC가 쓰던 능력의 재활용

스택 프레임을 힙으로 복사하려면 스택 안에 뭐가 어디 있는지 완벽히 알아야 한다. 어떤 4바이트가 int 값이고 어떤 4바이트가 객체를 가리키는 참조인지 구분하지 못하면, 옮긴 뒤에 GC가 그 참조를 추적하지 못해 살아 있는 객체를 회수해 버린다.

자바 프레임 — JVM이 전부 안다

모든 프레임을 자기가 만들었고, 각 칸이 무엇인지 기록한 메타데이터를 들고 있다 — GC가 스택을 훑으며 살아 있는 참조를 찾을 때 쓰던 바로 그 능력이다.

그래서 힙의 StackChunk로 옮긴 뒤에도 GC가 그 안의 참조를 정상적으로 추적한다.

네이티브(JNI) 프레임 — 옮길 수가 없다

C로 컴파일된 프레임은 JVM이 내부 구조를 모른다. 어떤 칸이 참조인지 알 수 없어 GC 추적이 불가능하다.

게다가 C 코드는 스택 주소 자체를 포인터로 들고 있을 수 있어서, 프레임을 옮기는 순간 그 포인터가 엉뚱한 곳을 가리킨다.

→ 이것이 구조적 pinning의 근본 원인이다(8절).

또 하나. 블로킹을 "epoll 등록 + yield"로 바꿔치기하려면 그 경로가 전부 JDK 진영의 코드여야 한다 — 뒤집어 말하면 블로킹이 일어나는 JDK의 모든 지점을 재작성해야 했다는 뜻이다. 이것이 Loom이 6년(2017~2023) 걸린 가장 큰 이유다.

5. 블로킹 한 번의 타임라인 — 플랫폼 vs 가상

애플리케이션 코드가 쓰는 문장은 양쪽 모두 똑같다. 이 한 줄 아래에서 벌어지는 일이 완전히 다르다.

socket.getInputStream().read(buf);   // 응답 도착까지 300ms 걸린다고 하자

5-1. epoll이란 무엇인가 — 스레드 하나가 소켓 1만 개를 감시하는 진동벨

캐리어에 대한 오해도 여기서 걷어낸다 — 캐리어는 마법이 아니다 OS 입장에서 보면 new Thread()로 만든 것과 아무 차이 없는 평범한 OS 스레드이고, 특별한 커널 기능도 쓰지 않는다. 다만 그 스레드가 실행하는 프로그램이 "대기열에서 얼려진 가상 스레드 꺼내기 → thaw → 실행 → yield하면 다음 것 꺼내기"라는 루프일 뿐이다. 목수 8명이 의뢰 10만 건을 처리하는 것은 작업대가 마법이어서가 아니라 "재료를 기다리게 된 작업은 하다 만 상태 그대로 서랍에 넣고 다른 의뢰를 꺼낸다"는 규칙 덕분이다.
마법은 작업대(캐리어)가 아니라 서랍(Continuation의 freeze/thaw)에 있다

6. 왜 과거엔 못 했나 — 개입 타이밍과 그린 스레드

흔한 오해 — "스택이 OS 소유라서 JVM이 못 읽는다"

아니다. OS 스레드의 스택은 내 프로세스의 주소 공간 안에 있는 평범한 유저 메모리이고, JVM은 언제든 읽고 쓸 수 있다.

OS가 진짜로 쥐고 있던 것 — 두 가지 통제권

① 스케줄링 권한 — 스레드를 언제 재우고 언제 깨울지는 커널만 결정한다.

② 끊긴 순간의 실행 위치 — 선점으로 끊으면 레지스터와 PC는 커널의 컨텍스트 저장소로 들어간다. JVM은 임의 시점의 이 정보에 접근할 수 없다.

6-1. 1:1을 깬 본질 — "실행 상태의 소유권" 이동

소유권이란 "멈춘 작업을 이어가는 데 필요한 데이터를 누가 쥐고 있고, 재개 시점을 누가 결정하는가"를 말한다.

플랫폼 스레드 — 소유자가 커널
블로킹하면 그 순간의 실행 상태는 커널의 컨텍스트 저장소에 들어가고, 깨우는 시점도 커널만 결정한다.

그 작업을 이어갈 수 있는 유일한 존재가 바로 그 OS 스레드가 된다.

→ 자바 스레드 100만 개를 원하면 OS 스레드도 100만 개(1:1 강제)

가상 스레드 — 소유자가 힙(=JVM)
멈춘 상태가 힙의 평범한 자바 객체라서 아무 OS 스레드 위에서나 복원할 수 있는 이동식 데이터가 된다.

재개 시점도 JVM 스케줄러가 정한다.

→ 실행 상태 100만 개를 OS 스레드 8개가 돌려가며 재생(M:N)

6-2. 왜 한 번 버렸다가 돌아왔는가 — 그린 스레드의 실패와 부활

이 아이디어는 새것이 아니다. 자바 1.0~1.2 시절 "그린 스레드(green threads)"라는 이름으로 정확히 이 발상이 있었다. OS 스레드 하나 위에서 JVM이 여러 자바 스레드를 스케줄링하는 방식, 즉 M:1이다. 1.3 즈음 이것을 걷어내고 OS 스레드 1:1로 갈아탔다.

그린 스레드가 실패한 이유와, 가상 스레드에서 그것이 해소된 방식
그린 스레드가 실패한 이유당시의 사정가상 스레드에서 해소된 방식
M:1이라 멀티코어를 못 씀OS 스레드 하나 위의 다중화라 코어가 몇 개든 하나만 썼다. 막 SMP 서버가 퍼지던 시기라 치명적이었다.M:N — 캐리어를 코어 수만큼 두고 work-stealing 스케줄러(ForkJoinPool)로 분배
블로킹 콜 하나가 전체 마비그린 스레드 하나가 파일 읽기로 블로킹되면 유일한 OS 스레드가 잠들어 나머지 전부가 정지했다. 당시 OS에는 epoll/kqueue가 없거나 미성숙했다.epoll/kqueue + 자바 NIO 위에서 JDK 블로킹 API의 겉모습은 그대로 두고 속만 재작성
(기술 부족)스택을 힙으로 옮기고 GC와 JIT가 그것을 감당하게 만드는 기술 자체가 없었다.힙에 얼린 스택의 GC 추적, JIT 프레임 freeze/thaw 등 Continuation을 감당할 JVM 기술이 성숙
필요가 크지 않았음 + OS 스레드가 좋아짐리눅스 NPTL 등으로 커널 스레드가 빨라지면서 "그냥 OS에 맡기는 게 단순하고 충분히 빠르다"가 합리적이었다.마이크로서비스 시대에 I/O 대기형 워크로드가 폭증했고, Go의 고루틴이 M:N이 실전에서 통함을 증명
개념이 없어서가 아니라 구현할 기반 기술이 없었고 당시 워크로드에선 필요도 크지 않았다 —
가상 스레드는 실패 원인이 전부 해소된 형태로 돌아온 부활이다

7. 역할 분담과 오버헤드 — 마법은 캐리어가 아니다

mount/unmount를 지휘하는 별도의 "관리자 스레드"는 없다. 역할이 넷으로 나뉘어 있고, 이 넷을 구분해 말하면 "동작 원리를 안다"는 인상이 확실해진다.

암기 문장 — 만드는 건 아무나, 내리는 건 본인, 올리는 건 캐리어, 깨우는 건 poller

만드는 건 — 아무나
Thread.ofVirtual().start()
생성 API를 호출한 스레드가 만든다. Spring Boot에서 spring.threads.virtual.enabled=true면 톰캣 내부 스레드가 요청마다 호출한다.

실체는 커널 시스템 콜 없이 힙에 객체 하나 할당 + 대기열 등록이 전부다.

내리는 건 — 본인
Continuation.yield()
블로킹 직전, 아직 멀쩡히 실행 중인 가상 스레드가 자기 스택을 힙에 복사하고 스스로 물러난다.

외부의 누가 떼어 내는 게 아니다 — 협조적 스케줄링.

올리는 건 — 캐리어
ForkJoinPool worker loop
캐리어가 도는 코드가 곧 무한 루프다 — "대기열에서 하나 꺼냄 → thaw → 실행 → yield/종료하면 → 다시 꺼냄".

mount는 캐리어가 자기 일감을 집어 드는 행위 그 자체다.

깨우는 건 — poller
JVM 내부 poller 스레드
epoll을 감시하다가 "데이터 도착" 알림을 받으면, 얼려져 있던 해당 가상 스레드를 스케줄러 대기열에 다시 넣는다.

직접 실행하지 않는다 — 줄만 세워 준다.

이 넷을 나눠 말할 수 있으면 "관리자 스레드가 스케줄링한다" 같은 잘못된 그림이 자동으로 걷힌다.

7-1. 오버헤드는 없나 — "코드가 늘었으니 느려진 것 아닌가"

가상 스레드용 분기와 freeze/thaw 코드가 추가된 것은 사실이다. JDK 블로킹 API 내부가 개념적으로 이렇게 바뀌었다.

// JDK 내부 read()의 개념적 모습
if (현재 스레드가 가상 스레드인가?) {
    소켓을 epoll에 등록;
    Continuation.yield();     // freeze하고 물러남
    // ... 깨어나면 여기부터 재개 — 데이터가 와 있으니 논블로킹 read
} else {
    기존 블로킹 시스템 콜;      // 플랫폼 스레드는 예전 경로 그대로
}

프록시처럼 앞뒤로 로직을 덧댄 게 맞다. 단, 덧댄 위치가 애플리케이션 코드가 아니라 JDK 라이브러리 내부다. 그래서 비용이 붙는 위치를 정확히 봐야 한다.

CPU로 계산하는 동안 — 오버헤드 0

mount된 가상 스레드는 캐리어 스택 위에서 평범한 스레드와 똑같은 기계어로 돈다.

명령어마다 붙는 세금 같은 건 없다.

블로킹 지점에만 — 분기 + freeze/thaw

분기 체크 한 번과 프레임 복사다. 그런데 비교 대상을 정확히 잡아야 한다 — 플랫폼 스레드도 블로킹이 공짜가 아니다.

OS 컨텍스트 스위칭(커널 진입 · 레지스터 저장 · CPU 캐시 오염)이라는 비용을 치르며, freeze/thaw는 이와 비슷하거나 오히려 싸다.

대기가 전혀 없는 단일 작업이라면 이득은 없고 미세한 손해가 있을 수 있다 — 이 기술은 요청 하나를 빠르게 하는 게 아니라 "동시에 기다릴 수 있는 개수"를 폭증시키는 것이다

8. pinning — 왜 캐리어에서 못 내려오는가

가상 스레드의 마법은 "블로킹 시 캐리어에서 내린다"인데, 내리지 못하는 경우가 있다. 이걸 pinning(고정, 못박힘)이라고 한다. 가상 스레드가 캐리어에 못박히면 그 블로킹이 끝날 때까지 캐리어(OS 스레드)가 통째로 잠든다 — 플랫폼 스레드 시절로 퇴행하는 것이다.

원인은 둘뿐인데, 성격이 완전히 다르다 — 이 구분이 답변의 핵심

원인 1 — synchronized (JDK 21~23)

모니터 소유자가 OS 스레드 단위로 기록되기 때문. 프레임만 옮기면 잠금 장부가 어긋난다.

성격: 구현상의 제약 → JDK 24의 JEP 491에서 해소됐다.

원인 2 — 네이티브(JNI)·VM 프레임

JVM이 내부 구조를 모르는 C 스택이라 애초에 얼릴 수 없다. 블로킹도 커널로 직행해 바꿔치기할 지점이 없다.

성격: 구조적 제약 → 어떤 JDK 버전에서도 사라지지 않는다.

8-1. 원인 1 — 모니터가 OS 스레드에 묶여 있다

먼저 synchronized가 실제로 무엇을 하는지 짚자. 자바의 모든 객체에는 모니터(monitor)라는 잠금 장치가 하나씩 딸려 있고, synchronized는 그 모니터를 획득했다가 반납하는 문법이다. 모니터에는 최소한 두 가지가 기록된다 — 지금 누가 들어와 있는지(소유자)와 몇 번 중첩해 들어왔는지(재진입 횟수).

문제의 한 줄 — JDK 21의 HotSpot은 이 소유자를 OS 스레드 단위로 기록한다 잠금 기록(락 레코드)도 그 OS 스레드의 스택 프레임 안에 자리 잡는다. 그래서 프레임을 힙으로 옮기는 순간 장부가 실제와 어긋난다.

8-2. 왜 위험한가 — 캐리어는 코어 수만큼뿐이다

8-3. 회피 방법 (JDK 21~23 기준) — before / after

before synchronized 안에서 I/O — 캐리어가 못박힌다
private final Object lock = new Object();

public void call() {
    synchronized (lock) {
        callExternalApi();   // 300ms 동안 캐리어 하나가 통째로 잠든다
    }
}

// 소유자를 'OS 스레드'로 기록 → 프레임을 옮기면
// 장부가 어긋나므로 JVM이 옮기지 않는다
after ReentrantLock — 보유 중에도 unmount 가능
private final ReentrantLock lock = new ReentrantLock();

public void call() {
    lock.lock();          // 소유자를 '자바 객체 안의 필드'로 기록하므로
                          // 프레임을 힙으로 옮겨도 장부가 어긋나지 않는다
    try {
        callExternalApi();
    } finally {
        lock.unlock();   // synchronized와 달리 자동 반납이 없다 — finally가 필수
    }
}
ReentrantLock이 괜찮은 이유는 정확히 원인 1의 뒤집힘이다 —
소유자를 힙의 자바 객체 필드에 기록하므로, 캐리어를 갈아타도 소유권이 따라다닌다

교체 체크리스트 — "전부 바꾼다"는 과잉이다

  • 오래 블로킹하는 구간을 감싸는 synchronized만 ReentrantLock으로 교체한다.
  • 짧은 인메모리 연산만 보호하는 synchronized는 실질적으로 문제가 없다 — 오히려 바꾸면 unlock() 누락(영구 정지) 위험만 새로 들인다.
  • 의존 라이브러리(JDBC 드라이버 · 커넥션 풀 · HTTP 클라이언트)가 내부에서 synchronized + I/O를 하는지 점검한다.
  • 소스를 다 뒤질 수는 없으니, 실제로는 탐지 도구(JFR)로 잡는 편이 확실하다.

8-4. 버전 범위 — JDK 24의 JEP 491이 바꾼 것 가산점

synchronized로 인한 pinning은 JDK 24의 JEP 491("Synchronize Virtual Threads without Pinning")에서 해소됐다. 모니터 소유권을 OS 스레드가 아니라 가상 스레드 단위로 추적하도록 구현을 바꿔서, synchronized 블록 안에서 블로킹해도, Object.wait()로 대기해도 캐리어에서 내려올 수 있게 됐다.

이 주제는 반드시 버전을 명시해서 말해야 한다
JDK 21~23JDK 24 이후
synchronized 안 블로킹핀 된다 — ReentrantLock으로 교체가 필요핀 되지 않는다 — 교체 부담이 사라짐 (JEP 491)
네이티브(JNI)·VM 프레임핀 된다여전히 핀 된다 (구조적 제약)
탐지 도구-Djdk.tracePinnedThreads=full
또는 JFR jdk.VirtualThreadPinned		-Djdk.tracePinnedThreads는 제거됐다.
JFR jdk.VirtualThreadPinned 이벤트로 본다
잠금의 직렬화양쪽 모두 그대로 남는다 — JEP 491이 푼 것은 "캐리어가 묶이는 문제"일 뿐이다

-Djdk.tracePinnedThreads가 없어진 이유는 JEP 491이 밝혀 두었다 — 진단 옵션으로서 문제가 많았고 synchronized 핀이 사라진 뒤로는 쓸모도 없어졌다는 것이다. 대신 JFR의 jdk.VirtualThreadPinned 이벤트가 확장되어, 네이티브/VM 프레임 때문에 핀 된 상태에서 park하거나 모니터를 기다리거나 Object.wait() 하는 경우를 기록한다. 즉 JDK 24 이후 핀 조사는 JFR이 정식 경로다.

여기서 한 걸음 더 나가면 시니어 답변이 된다 — 핀이 사라져도 직렬화는 남는다

JEP 491이 푼 것은 "캐리어가 묶이는 문제"일 뿐, 잠금 자체의 직렬화는 그대로 남는다.

300ms짜리 외부 호출을 synchronized로 감쌌다면 그 구간의 처리량 = 1 / 0.3s = 초당 3건 가상 스레드가 1만 개여도 변하지 않는다. 장애의 모양만 바뀐다: "서버 전체 멈춤" → "그 구간만 극심한 대기"

긴 I/O를 잠금으로 감싸는 설계 자체가 잘못이라는 점은 버전과 무관하게 그대로다.

9. @Transactional — 스레드는 풀렸는데 커넥션이 안 풀린다

이 절이 이 문서에서 가장 실무적인 대목이다 —
가상 스레드가 값싸게 만든 것은 "자바 스레드"이지 "DB 커넥션"이 아니다

9-1. 원래 문제 — 가상 스레드와 무관하게 존재한다

@Transactional
public void placeOrder(OrderRequest req) {
    orderRepository.save(order);          // 이 시점에 이미 DB 커넥션을 하나 쥐고 있다
    paymentClient.approve(req);           // 외부 API 300ms — 이 동안에도 커넥션은 반납되지 않는다
    orderRepository.update(order);
}

@Transactional 메서드는 시작할 때 커넥션 풀(HikariCP)에서 DB 커넥션을 하나 꺼내 메서드가 끝날 때까지 쥐고 있다. 트랜잭션이라는 개념 자체가 "하나의 커넥션 위에서 열리고 닫히는 것"이기 때문에 중간에 반납할 방법이 없다. 그래서 외부 API를 기다리는 300ms 동안 그 커넥션은 아무 쿼리도 실행하지 않으면서 점유돼 있다. HikariCP 기본 풀 크기는 10개뿐이다 — "트랜잭션 안에서 외부 API 콜 금지"가 정석인 이유가 이것이다.

9-2. 가상 스레드를 도입하면 — 병목이 이동하며 증폭된다

대기 중 점유하는 자원이 두 개라는 것을 구분하는 게 핵심이다.

대기 중 점유하는 자원 — 무엇이 풀리고 무엇이 안 풀리는가
대기 중 점유하는 자원플랫폼 스레드가상 스레드
스레드톰캣 워커 1개가 묶인다해결됨 — unmount되어 캐리어는 다른 일을 한다
DB 커넥션1개가 묶인다그대로 묶인다 — 커넥션은 스레드가 아니라 트랜잭션에 묶인 자원이다

이제 숫자로 확인해 보자. 커넥션 풀을 실무에서 흔한 20개로 올려 뒀다고 하고, 트랜잭션 하나가 커넥션을 350ms(외부 API 300ms + 쿼리 50ms) 점유한다고 하자.

① 커넥션 하나의 초당 처리량 = 1 / 0.35s = 2.86 건/s ② 풀 전체의 처리량 상한 = 20 × 2.86 = 57 req/s → 스레드를 몇 개로 늘리든 이 값은 변하지 않는다.

9-3. 초당 1,000건이 들어오면 — 여기서 역설이 나온다

가상 스레드는 요청을 더 많이 "받게" 해 줄 뿐, 더 많이 "처리하게" 해 주지 않는다 —
하류(DB, 외부 API)의 처리량이 그대로면 늘어난 것은 대기 행렬뿐이다

9-4. pinning과도 얽힌다 (JDK 21~23 기준)

트랜잭션 경로에 synchronized가 숨어 있을 수 있다 커넥션 하나를 여러 스레드가 동시에 쓰지 못하게 막는 가장 자연스러운 구현이 synchronized라, 드라이버들이 오랫동안 그렇게 만들어져 왔다. 이 경우 DB I/O 대기 중에 unmount조차 못 하고 캐리어가 핀 된다.

그래서 가상 스레드 + @Transactional 조합을 검토할 때는 드라이버 · 커넥션 풀 버전 점검과 JFR jdk.VirtualThreadPinned 이벤트 감시가 체크리스트에 들어간다. JDK 24 이후라면 이 걱정은 크게 줄어든다.

9-5. 올바른 설계는 가상 스레드가 있든 없든 동일하다

답은 하나다 — 외부 API 콜을 트랜잭션 밖으로 뺀다
before 하나의 트랜잭션이 외부 호출을 품고 있다 — 커넥션 350ms 점유
@Transactional
public void placeOrder(OrderRequest req) {
    orderRepository.save(order);
    paymentClient.approve(req);        // 300ms 동안 커넥션이 '놀면서' 묶여 있다
    orderRepository.update(order);
}

// 커넥션 점유 350ms  →  20 / 0.35 ≈ 57 req/s
after 트랜잭션 경계를 잘게 쪼갠다 — 점유는 쿼리 시간만큼만
public void placeOrder(OrderRequest req) {
    orderService.saveOrder(order);     // @Transactional — 커넥션 점유 25ms
    paymentClient.approve(req);        // 트랜잭션 밖 — 커넥션을 안 쥔 채로 300ms 대기
    orderService.confirmOrder(order);  // @Transactional — 커넥션 점유 25ms
}

// 커넥션 점유 50ms  →  20 / 0.05 = 400 req/s  (같은 풀 20개로 7배)
효과 — 가상 스레드보다 이 변경의 효과가 훨씬 크다 커넥션 점유 시간이 350ms → 50ms로 줄어, 같은 풀 20개로 20 / 0.05 = 400 req/s를 감당하게 된다. 처리량 상한 식이 풀 크기 ÷ 점유 시간이므로 분모를 줄이는 쪽이 압도적으로 효율이 좋다.
대가 — 공짜는 아니다 트랜잭션을 쪼갠 만큼 원자성이 깨지므로, 중간 실패 시 보상 처리나 상태 기반 재시도 같은 정합성 설계가 반드시 따라와야 한다. 이 대가를 함께 말해야 답이 완성된다.

10. ThreadLocal — 고장 나는 건 도구가 아니라 사용 패턴

이 절의 논지를 먼저 못 박는다 —
가상 스레드에서 ThreadLocal은 "고장 나지" 않는다. 고장 나는 것은 우리가 ThreadLocal을 써 온 방식이다

10-1. 값은 캐리어가 아니라 "가상 스레드 객체"에 붙는다

ThreadLocal은 값을 자기 안에 담고 있는 게 아니다. 실제 값은 각 Thread 객체 안의 ThreadLocalMap에 저장되고, ThreadLocal 인스턴스는 그 맵을 여는 키 역할만 한다.

// ThreadLocal.get()이 내부적으로 하는 일 (개념적으로)
Thread t = Thread.currentThread();   // ① 지금 실행 중인 스레드가 누구인가?
return t.threadLocals.get(this);     // ② '그 스레드의' 맵에서 this를 키로 꺼낸다

그러니 질문은 ①로 좁혀진다. 가상 스레드가 캐리어 위에서 도는 동안 currentThread()는 누구를 돌려주는가 — 가상 스레드다. mount하는 순간 JVM이 "현재 스레드" 정체성을 가상 스레드로 바꿔 끼우고, 캐리어 자신의 ThreadLocal은 그동안 가려져 아무도 보지 못한다.

10-2. 그런데 왜 "주의"인가 — 스레드당 캐싱 패턴의 전제가 무너진다

// 플랫폼 스레드 풀 시절엔 합리적이었던 패턴
private static final ThreadLocal<SimpleDateFormat> FORMAT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

이 패턴은 "SimpleDateFormat은 thread-safe하지 않으니 스레드마다 하나씩 만들어 두고 계속 재사용하자"는 발상이다. 이게 이득이 되려면 전제가 두 개 필요하다. 그리고 가상 스레드에서는 둘 다 무너진다.

스레드당 캐싱 패턴의 두 전제가 어떻게 무너지는가
전제플랫폼 스레드 풀가상 스레드
스레드 개수가 적다200개 → 객체도 최대 200개수만~수백만 개 → 객체도 그만큼 (메모리 폭탄)
스레드가 오래 살며 재사용된다풀에서 계속 재사용 → 초기화 비용을 상환일회용 — 작업 하나 끝나면 죽음 → 캐시 적중이 아예 없음
이득은 0, 비용만 폭증 — 캐싱의 근거 자체가 사라진다

대응 규칙 — 용도를 둘로 나눈다

유지 — 문맥 전달용

traceId, 인증 정보, MDC. 요청 하나 = 가상 스레드 하나 구도에서 그대로 잘 동작하고, 오히려 재사용 오염이 사라져 더 안전해진다.

제거 — 스레드당 캐싱용

비싼 객체를 스레드마다 하나씩 두던 패턴. SimpleDateFormat 같은 경우는 애초에 불변이라 공유해도 되는 DateTimeFormatter로 바꾸는 것이 정답이다.

10-3. 후속 — ScopedValue: 수명을 스레드가 아니라 블록에 매단다

지금까지의 문제를 한 줄로 모으면 이렇다. ThreadLocal의 손익은 스레드의 수명 모델에 종속된다 — 풀(재사용)에서는 오염과 누수를, 가상 스레드(대량 생성)에서는 개수 비용을 걱정해야 한다. 이 종속을 끊으려고 Loom 팀이 만든 후속 API가 ScopedValue다. JDK 21에 프리뷰로 처음 나와 JDK 25에서 정식 기능이 됐다(JEP 506).

before ThreadLocal — 수명이 스레드와 같다
ThreadLocal<User> USER = new ThreadLocal<>();

USER.set(user);   // 아무 데서나 바꿀 수 있고,
                  // remove() 안 하면 계속 남는다
after ScopedValue — 불변 + 블록 범위
static final ScopedValue<User> USER = ScopedValue.newInstance();

ScopedValue.where(USER, user).run(() -> {
    handleRequest();  // 이 안에서 호출되는 모든 코드가 USER.get() 가능
});                   // 블록을 벗어나면 바인딩이 자동으로 풀린다
                      // → remove() 누락 사고가 원천 차단된다
값이 불변이라는 점이 개수 비용까지 해결한다 값을 바꿀 수 없으니 자식 작업에 넘길 때 복사가 아니라 참조 공유로 끝난다. StructuredTaskScope로 만든 하위 작업이 부모의 ScopedValue를 공짜로 물려받는 것도 이 덕분이다. 수백만 스레드 규모를 전제로 설계된 대체재다.

10-4. InheritableThreadLocal — 복사의 트리거는 요청이 아니라 "스레드 생성"

InheritableThreadLocal은 스레드가 생성되는 순간 부모의 값 테이블을 자식에게 복사한다 — 달라지는 건 생성 빈도다
플랫폼 스레드 풀가상 스레드 (요청당 생성)
스레드 생성 시점서버 시작 때 200개 만들고 끝톰캣이 요청마다 새로 생성
복사 발생 횟수시작 때 200번뿐요청 수만큼 (부모에 값이 있는 한)
요청 문맥 상속무용지물 — 스레드가 요청보다 먼저 태어나 물려받을 게 없다생성 시점의 부모 값이 상속된다
판단 기준은 "내가 만들었나"가 아니라 "요청마다 새 스레드가 태어나는 모델인가"다

11. 도입 체크포인트 다섯 · 관측 지표 재설계

도입 판단 체크포인트 — 이 다섯 개를 순서대로 외운다

① 커넥션 풀스레드 상한이 사라지면 다음 병목은 반드시 커넥션 풀이다. 다만 "풀을 1,000개로 늘리자"는 오답 — 커넥션은 DB 쪽에도 자원을 요구한다. 먼저 할 일은 트랜잭션 점유 시간을 줄이는 것이고, 풀 크기 조정은 그다음이다.
② Semaphore가상 스레드에는 개수 제한이 없으므로, 하류 자원(외부 API · 레거시)을 보호하려면 별도의 문지기가 필요하다. 스레드 풀이 하던 부하 제한 역할을 대신 맡길 도구가 Semaphore다.
③ 풀링 금지가상 스레드는 일회용이다. 풀에 넣어 재사용하면 (a) 재사용 오염이 다시 생기고 (b) 개수 상한이 다시 생겨 이점이 사라진다. 개수 제한이 목적이면 스레드 풀이 아니라 Semaphore다.
④ 관측 재설계ThreadMXBean 기반 지표는 가상 스레드를 세지 않는다. "스레드 풀 포화" 알람이 영원히 울리지 않게 된다 — 대체 지표를 먼저 세워야 한다.
⑤ CPU 바운드 제외이득은 오직 I/O 대기가 많은 워크로드에서 나온다. 이미지 변환 · 암호 연산처럼 CPU를 계속 쓰는 작업은 어차피 코어 수만큼만 동시에 돌 수 있으므로 바꿔도 얻는 게 없다.

11-1. 동시성 제한은 Semaphore로 건다

// Semaphore = "동시 통행증 N장" — 표를 받은 만큼만 안으로 들어갈 수 있다
private final Semaphore outboundLimit = new Semaphore(50);

public PaymentResult approve(OrderRequest req) throws InterruptedException {
    outboundLimit.acquire();     // 표가 없으면 여기서 대기한다.
                                 // 이 대기는 park 기반이라 가상 스레드가 unmount된다 — 캐리어는 안 묶인다.
    try {
        return paymentClient.approve(req);
    } finally {
        outboundLimit.release(); // 반드시 반납. 누락되면 통행증이 영구히 줄어 서서히 마비된다.
    }
}
이름이 주는 오해 하나 — newVirtualThreadPerTaskExecutor()는 스레드 풀이 아니다 반환 타입이 ExecutorService라 풀처럼 보이지만, 이 executor는 이름 그대로 작업(task)마다 가상 스레드를 하나씩 새로 만들고 끝나면 버린다. 재사용도 없고 개수 상한도 없다. 그래서 close()(또는 try-with-resources 블록 탈출)의 의미도 "풀을 접는다"가 아니라 "제출된 작업이 전부 끝날 때까지 기다린다"로 달라진다.

11-2. 모니터링 지표가 무의미해지는 것을 대비한다

"OS는 가상 스레드를 모른다"(2절)의 결과가 여기서 나타난다 ThreadMXBean 기반 지표(마이크로미터의 jvm.threads.live 등)는 캐리어만 센다. 그래서 부하가 아무리 몰려도 항상 코어 수 근처에서 평평하고, 그동안 그 지표를 포화 감지에 써 왔다면 알람이 영원히 울리지 않는다.

12. 리액티브와의 선택 · 30초 답변 스크립트 · 암기 총정리

12-1. 가상 스레드 vs 리액티브(WebFlux)

푸는 문제는 같다 — "기다림 때문에 OS 스레드가 낭비되는 것"이다. 리액티브는 코드를 바꿔서 스레드를 안 붙잡고, 가상 스레드는 스레드를 바꿔서 붙잡아도 싸게 만든다.

비용이 갈리는 지점 다섯
리액티브가상 스레드
코드 스타일콜백/체이닝으로 전면 전환기존 블로킹 코드 그대로
디버깅 · 스택트레이스끊어져서 어렵다그대로 살아 있다
ThreadLocal 기반 도구그대로는 안 통한다 (Reactor Context 등 별도 장치)그대로 동작한다
전염성경로 위 라이브러리 하나만 블로킹이어도 무너진다블로킹 라이브러리를 그대로 써도 된다
스트림 / 배압 제어연산자로 정교하게 표현된다언어 차원의 도구가 없어 직접 만들어야 한다
가상 스레드가 낫다 대부분의 CRUD · 오케스트레이션 API. 얻는 동시성은 비슷한데 학습 · 유지보수 비용이 비교가 안 되게 싸다.
리액티브가 여전히 유리하다 SSE · WebSocket 같은 스트리밍, 백프레셔가 본질적인 파이프라인, 그리고 이미 Reactor로 잘 돌고 있는 시스템. 특히 마지막이 중요하다 — 잘 돌아가는 리액티브 코드를 가상 스레드로 되돌릴 이유는 없다.

12-2. 30초 답변 스크립트

  1. 모델 차이를 소유권으로 요약한다. "플랫폼 스레드는 OS 스레드와 1:1이라 블로킹하면 실행 상태가 커널 컨텍스트로 들어가 그 OS 스레드만이 그 작업을 이어갈 수 있었습니다. 가상 스레드는 멈춘 상태가 힙의 자바 객체라 아무 캐리어에서나 복원 가능한 이동식 데이터가 됩니다 — 그래서 M:N이 됩니다."
  2. 메커니즘을 한 문장으로. "블로킹 시스템 콜에 들어가는 대신, JDK가 소유한 시스템 콜 직전 경로에서 epoll에 등록하고 아직 깨어 있는 스레드가 스스로 자기 스택을 힙으로 복사(freeze)한 뒤 캐리어에서 내려옵니다. 데이터가 오면 아무 캐리어에나 다시 올려(thaw) 이어 달립니다."
  3. pinning을 원인별로 나눈다. "synchronized는 모니터 소유자가 OS 스레드 단위로 기록돼 프레임만 옮기면 장부가 어긋나므로 JVM이 안 옮기는 쪽을 택한 것이고 — JDK 24의 JEP 491에서 해소됐습니다. 네이티브(JNI) 프레임은 JVM이 구조를 몰라 옮길 수 없어 어떤 버전에서도 남습니다."
  4. 실무 함정으로 마무리한다. "다만 가상 스레드가 값싸게 만든 것은 자바 스레드일 뿐 DB 커넥션이 아닙니다. @Transactional 안 외부 콜은 커넥션을 계속 쥐고 있고, 톰캣 200 스레드가 해 주던 암묵적 부하 제한이 사라져 오히려 더 크게 터집니다. 그래서 도입의 본질은 암묵적 제한을 명시적 제한(Semaphore·타임아웃·서킷 브레이커)으로 바꾸는 일이라고 봅니다."

JDK 21

13. 꼬리질문 셀프 테스트 (16문항)

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼쳐서 대조한다. 막히면 괄호 안 절로 돌아간다.

가상 스레드를 도입하면 처리량이 몇 배 늘어나나요?힌트: 배수가 어디서 나오는 수인지부터 말한다 (→ 1절, 9절)

"워크로드에 따라 다르고, 늘어난다면 그 배수는 대기 시간 / CPU 시간 비율에서 나온다"로 답하는 것이 정확하다. "몇 배"라는 숫자를 그냥 말하면 하이프를 옮긴 것이고, 배수의 출처를 말하면 이해한 것이다.

1절의 예를 그대로 쓰면 계산이 보인다. 요청 하나가 350ms 중 5ms만 CPU를 쓴다면 대기 비중이 98%이고, 스레드 상한 200이 걷히는 순간 처리량은 CPU가 감당하는 지점까지 올라갈 수 있다. 반대로 CPU를 100% 쓰는 작업이라면 이론상 이득이 0이고, 분기와 freeze/thaw 비용 때문에 미세하게 손해일 수도 있다.

여기에 한 문장을 붙이면 완성된다. "단, 상류의 상한이 걷혔다고 하류도 늘어나는 것은 아니다." DB·외부 API·커넥션 풀의 처리량이 그대로면 늘어나는 것은 처리량이 아니라 대기 행렬이다(9절).

pinning은 JDK 24에서 해결됐다는데, 이제 synchronized를 그냥 써도 되나요?시니어 변별힌트: 핀과 직렬화는 다른 문제다 (→ 8절)

"핀은 사라졌지만 직렬화는 남는다"가 핵심이다. 3단으로 나눠 답한다.

(1) 무엇이 해결됐는지 정확히. JEP 491(JDK 24)이 모니터 소유권을 OS 스레드가 아니라 가상 스레드 단위로 추적하도록 바꿔서, synchronized 안에서 블로킹해도, Object.wait()로 대기해도 캐리어에서 내려올 수 있게 됐다. "캐리어가 묶여 서버 전체가 멈추는" 문제는 이것으로 해소된다.

(2) 무엇이 남았는지. 잠금은 여전히 잠금이다. 300ms짜리 외부 호출을 synchronized로 감쌌다면 그 구간의 처리량은 초당 3건이고, 가상 스레드가 1만 개여도 변하지 않는다. 장애의 모양이 "전체 멈춤"에서 "그 구간만 극심한 대기"로 바뀔 뿐이다. 긴 I/O를 잠금으로 감싸는 설계 자체가 잘못이라는 점은 그대로다.

(3) 네이티브 pinning은 구조적으로 남는다. JNI 프레임은 JVM이 구조를 몰라 힙으로 옮길 수 없으므로 어떤 버전에서도 얼릴 수 없다. 그래서 JFR jdk.VirtualThreadPinned 이벤트는 JDK 24 이후에도 계속 필요하다 — 다만 이제 그 이벤트가 잡아 주는 것은 대체로 네이티브/VM 프레임이다.

마지막으로 -Djdk.tracePinnedThreads가 JDK 24에서 제거됐다는 것까지 말하면 버전 감각이 드러난다. 이 옵션을 그대로 붙여 둔 채 "핀이 안 잡히네" 하는 오해가 실제로 생긴다.

가상 스레드를 켰더니 오히려 장애가 늘었습니다. 왜일까요?시니어 변별힌트: 톰캣 200 스레드가 사실 무엇이었는지 (→ 9절, 11절)

"부하 제한기가 사라졌기 때문"이라고 답하는 것이 이 질문의 정답이다.

톰캣의 워커 200개는 성능 제약처럼 보였지만, 실제로는 공짜로 얻고 있던 admission control(부하 제한)이었다. 동시에 200건까지만 안으로 들여보내 주었기 때문에 그 뒤의 모든 자원 — 커넥션 풀, 외부 API, 레거시 시스템 — 도 200 이상의 경쟁을 겪지 않았다. spring.threads.virtual.enabled=true 한 줄은 그 문을 활짝 여는 것이다.

구체적 증상은 셋으로 나온다.

  1. 커넥션 풀 고갈 — Connection is not available, request timed out after 30000ms. 9절의 계산 그대로다.
  2. 하류 서비스 과부하 전파 — 우리가 안 죽는 대신 외부 API나 레거시 시스템이 죽는다. 우리 서버가 던지던 백프레셔(더 못 받겠다는 신호)가 사라진 결과다.
  3. 메모리 증가 — 요청 하나가 붙잡고 있던 객체들이 이제 수만 건 분량으로 힙에 동시에 존재한다.

대응은 부하 제한을 명시적으로 다시 세우는 것이다. Semaphore로 하류 호출의 동시성을 제한하고, 커넥션 풀 대기 지표를 감시하고, 타임아웃과 서킷 브레이커를 손본다. "암묵적 제한이 명시적 제한으로 바뀌었다"가 도입의 본질이다.

가상 스레드와 리액티브(WebFlux) 중 무엇을 고르겠습니까?시니어 변별힌트: 푸는 문제는 같고 비용 구조가 다르다 (→ 12절)

"둘 다 같은 문제를 푸는 다른 방법이고, 비용 구조가 다르다"에서 출발한다.

푸는 문제는 같다 — "기다림 때문에 OS 스레드가 낭비되는 것"이다. 리액티브는 코드를 바꿔서 스레드를 안 붙잡고, 가상 스레드는 스레드를 바꿔서 붙잡아도 싸게 만든다.

비용이 갈리는 지점은 코드 스타일 전환 여부, 스택트레이스·디버깅, ThreadLocal 기반 도구의 동작, 전염성(경로 위 라이브러리 하나만 블로킹이어도 무너지는가), 스트림·배압 제어의 표현력 다섯이다(12절 표).

대부분의 CRUD·오케스트레이션 API라면 가상 스레드가 낫다. 얻는 동시성은 비슷한데 학습·유지보수 비용이 비교가 안 되게 싸기 때문이다.

리액티브가 여전히 유리한 영역을 말하면 답이 균형을 얻는다 — SSE·WebSocket 같은 스트리밍, 백프레셔가 본질적인 파이프라인, 이미 Reactor로 잘 돌고 있는 시스템이다. 특히 마지막이 중요하다. 잘 돌아가는 리액티브 코드를 가상 스레드로 되돌릴 이유는 없다.

가상 스레드 환경에서 ThreadLocal을 써도 되나요?힌트: 동작과 사용 패턴을 분리한다 (→ 10절)

"써도 된다. 다만 용도를 나눠야 한다"로 답한다.

동작은 안전하다. 값은 캐리어가 아니라 힙에 사는 가상 스레드 객체에 붙으므로 캐리어를 갈아타도 따라다니고, 다른 가상 스레드에게 새지 않는다(10절). 오히려 스레드 풀 시절의 최대 사고였던 재사용 오염이 사라진다 — 스레드가 재사용되지 않으니까.

깨지는 것은 "캐싱" 용도다. "스레드가 적고 오래 산다"를 전제로 스레드마다 비싼 객체를 하나씩 만들어 두던 패턴은, 스레드가 수만 개 일회용이 되는 순간 캐시 적중 0, 메모리만 수만 배가 된다.

정리는 이렇다. 문맥 전달(traceId, 인증 정보)은 유지, 스레드당 캐싱은 제거. 그리고 이 종속 자체를 끊으려는 후속이 불변 · 블록 범위의 ScopedValue(JDK 21 프리뷰 → JDK 25 정식, JEP 506)라는 데까지 연결하면 좋다.

Executors.newVirtualThreadPerTaskExecutor()는 결국 스레드 풀 아닌가요?가산점힌트: 반환 타입이 ExecutorService라는 것과 풀이라는 것은 다른 말 (→ 11절)

아니다. 반환 타입이 ExecutorService라 풀처럼 보이지만, 이름 그대로 작업마다(per-task) 가상 스레드를 하나 새로 만들고 끝나면 버린다. 재사용도 없고 개수 상한도 없다.

이 차이가 실무에서 드러나는 지점이 셋이다.

  1. 개수 제한 수단이 아니다. 하류를 보호하려면 Semaphore를 따로 걸어야 한다(11절).
  2. close()의 의미가 다르다. "풀을 접는다"가 아니라 "제출된 작업이 전부 끝날 때까지 기다린다"이다. ExecutorService가 AutoCloseable이 되면서 try-with-resources로 쓰는 것이 자연스러워졌다.
  3. 가상 스레드를 풀링하려 드는 것은 안티패턴이다. 풀링하는 순간 재사용 오염과 개수 상한이 함께 돌아와 이점이 사라진다.

한 문장으로 정리하면 "개수 제한이 목적이면 스레드 풀이 아니라 Semaphore"다.

캐리어 스레드 개수를 늘리면 pinning 문제가 해결되나요?시니어 변별힌트: 늘려서 사는 시간이 무엇을 사는지 (→ 8절)

완화는 되지만 해결은 아니다. 캐리어를 늘리는 것은 "핀이 나도 죽지 않을 여유분을 사는 것"이지 핀 자체를 없애는 게 아니다.

이유는 셋이다.

  • 캐리어는 진짜 OS 스레드다. 늘리는 만큼 스택 예약·컨텍스트 스위칭 비용이 그대로 돌아온다. 무한정 늘리면 결국 플랫폼 스레드 풀로 되돌아가는 것과 같아진다.
  • 핀 되는 비율이 그대로면 늘려도 같은 비율로 묶인다. 트래픽이 2배가 되면 다시 전부 묶인다 — 시간을 벌 뿐이다.
  • 원인 제거가 훨씬 싸다. 긴 I/O를 감싼 synchronized를 ReentrantLock으로 바꾸거나(JDK 21~23), 애초에 잠금 밖으로 I/O를 빼는 편이 근본 해결이다.

그래서 답의 형태는 "임시 방편으로는 유효하고(장애 대응), 항구적 해법으로는 틀렸다(설계)"가 된다. 덧붙여 핀 상태에서 진행이 아예 불가능해지는 상황(모두가 핀 + 잠금 대기)을 막기 위해 JDK가 캐리어를 일시적으로 보충할 수 있다는 점은 알아 두되, 그 보충을 성능 대책으로 기대하면 안 된다.

Thread.sleep()은 캐리어를 묶나요? BlockingQueue.take()는요?힌트: 판단 기준은 "그 경로를 누가 소유하는가" (→ 6절)

둘 다 묶지 않는다 — 가상 스레드는 unmount된다. 그리고 이 답을 암기가 아니라 기준으로 말해야 한다.

기준은 "블로킹 지점이 JDK가 소유한 자바 코드인가" 하나다

Thread.sleep, Socket/InputStream의 I/O, BlockingQueue, ReentrantLock·Semaphore의 대기 — 이들은 전부 JDK 내부가 LockSupport.park 또는 epoll 등록으로 구현되어 있어 "시스템 콜 직전에 끼어들 지점"이 있다. 그래서 JDK가 블로킹 대신 freeze + yield로 바꿔칠 수 있다.

반대로 JVM이 그 경로를 소유하지 못하는 곳은 못 바꾼다 — 네이티브(JNI) 호출 안의 블로킹이 대표다. 커널로 직행하므로 끼어들 지점이 없고, 프레임도 옮길 수 없다.

주의할 표현 하나. "sleep은 이제 공짜"가 아니다. unmount 덕분에 OS 스레드를 안 묶을 뿐, 그 가상 스레드는 여전히 그 시간 동안 진행하지 않고 힙 객체로 남아 있다.

가상 스레드 수만 개가 도는 서버에서 스레드 덤프는 어떻게 뜨나요?가산점힌트: jstack이 보여주는 것은 무엇인가 (→ 11절)

전통적인 jstack으로는 가상 스레드가 보이지 않는다. jstack이 열거하는 것은 OS 스레드에 대응하는 플랫폼 스레드뿐이라, 캐리어 몇 개와 GC/JIT 스레드만 나오고 정작 일하는 가상 스레드 수만 개는 목록에 없다.

대신 JDK 21+의 jcmd <pid> Thread.dump_to_file을 쓴다. 이 덤프는 가상 스레드까지 포함하며, 파일로 떨어뜨리는 형태이고 JSON 형식도 지원한다.

이 사실이 그대로 모니터링 함정으로 이어진다. ThreadMXBean 기반 지표(마이크로미터의 jvm.threads.live 등)도 가상 스레드를 세지 않는다. 캐리어만 세기 때문에 부하가 아무리 몰려도 항상 코어 수 근처에서 평평하다 — 즉 "스레드 풀 포화" 알람이 영원히 울리지 않는다.

그래서 대체 지표를 먼저 세운다. 커넥션 풀 대기(hikaricp.connections.pending, acquire 지연) → 하류 응답 시간·타임아웃·에러율 → JFR 이벤트(jdk.VirtualThreadPinned, jdk.VirtualThreadStart/End) 순이다.

가상 스레드도 -Xss만큼 스택을 예약하나요? 왜 수백만 개가 가능한가요?힌트: 스택이 "어디에" 있는지가 답이다 (→ 3·4절)

예약하지 않는다. 플랫폼 스레드는 태어날 때 네이티브 메모리에 수백 KB~2MB 수준의 스택을 미리 예약받는다(-Xss/ThreadStackSize, 값은 플랫폼 의존). 반면 가상 스레드는 자기만의 스택을 상시 보유하지 않는다.

  • 실행 중(mount)이면 캐리어의 진짜 스택을 빌려 쓴다. 이 순간엔 평범한 스레드와 기계어 수준에서 동일하다.
  • 대기 중(unmount)이면 쓴 만큼만 힙의 객체(JVM 내부에서 StackChunk)로 챙겨 간다.

"쓴 만큼만"이 비용 차이의 정체다. 얕은 스택으로 대기 중인 가상 스레드는 힙에서 몇 KB짜리 객체일 뿐이라, 생성도 커널 시스템 콜 없이 객체 new 수준으로 끝난다. "요청마다 만들고 버린다"는 모델이 성립하는 근거가 여기 있다.

덧붙일 정밀함 하나. 플랫폼 스레드의 예약도 예약(reserve)이지 즉시 소모하는 물리 메모리는 아니다. 그래도 주소 공간과 커널 자료구조는 스레드 수에 정직하게 비례하므로, 힙이 남아돌아도 unable to create new native thread로 실패한다.

가상 스레드로 바꾸면서 synchronized를 전부 ReentrantLock으로 치환하면 되나요?힌트: 무엇을 감싼 synchronized인가 (→ 8절)

전부 바꾸는 것은 과잉이다. 판단 기준은 "그 잠금이 감싸고 있는 것이 무엇인가" 하나다.

  • 바꾼다 — 오래 블로킹하는 구간(외부 API 호출, DB I/O, 큐 대기)을 감싼 synchronized. 여기가 캐리어를 못박는 지점이다(JDK 21~23).
  • 그대로 둔다 — 짧은 인메모리 연산만 보호하는 synchronized. 핀이 나도 지속 시간이 마이크로초 수준이라 실질적 영향이 없고, 오히려 ReentrantLock으로 바꾸면 finally의 unlock() 누락이라는 새 위험(영구 정지)을 들여오게 된다.

ReentrantLock이 괜찮은 이유는 정확히 synchronized 문제의 뒤집힘이다. 소유자를 힙의 자바 객체 필드에 기록하므로 가상 스레드가 캐리어를 갈아타도 소유권이 따라다닌다.

현실적으로 더 중요한 것은 내 코드가 아니라 의존 라이브러리다. JDBC 드라이버·커넥션 풀·HTTP 클라이언트 내부의 synchronized + I/O는 소스를 다 뒤질 수 없으니 JFR jdk.VirtualThreadPinned로 잡는 편이 확실하다. JDK 24 이후라면 이 걱정은 크게 줄어든다.

이거 예전 "그린 스레드"랑 같은 것 아닌가요? 자바가 한 번 버렸던 방식인데요시니어 변별힌트: 발상은 같고 기반 기술이 다르다 (→ 6절)

발상은 같지만 실패 원인이 전부 해소된 형태다. "같다"고만 하면 반쪽, "다르다"고만 하면 근거가 없다. 버린 이유 셋을 대고 각각이 어떻게 풀렸는지를 말해야 한다.

  1. 멀티코어를 못 썼다(M:1). 그린 스레드는 OS 스레드 하나 위의 다중화라 코어가 몇 개든 하나만 썼다. → 가상 스레드는 M:N이다. 캐리어를 코어 수만큼 두고 work-stealing 스케줄러(ForkJoinPool)로 분배한다.
  2. 블로킹 콜 하나가 전체를 마비시켰다. 유일한 OS 스레드가 잠들면 전부 정지했는데, 피하려면 논블로킹 I/O 인프라가 필요했지만 당시엔 epoll/kqueue가 없거나 미성숙했다. → 지금은 epoll/kqueue + 자바 NIO 위에서 JDK 블로킹 API의 겉모습은 그대로 두고 속만 재작성했다.
  3. OS 스레드가 좋아졌다. 리눅스 NPTL 등으로 커널 스레드가 빨라지면서 "그냥 OS에 맡기자"가 당시로선 합리적이었다. → 마이크로서비스 시대에 I/O 대기형 워크로드가 폭증했고, Go의 고루틴이 M:N이 실전에서 통함을 증명했다.

여기에 기술적 전제 하나를 더하면 답이 두터워진다 — 힙에 얼린 스택의 GC 추적, JIT 프레임의 freeze/thaw 같은 Continuation을 감당할 JVM 기술이 그동안 성숙했다. 개념이 없어서가 아니라 구현할 기반이 없었던 것이다.

이미지 변환·암호 연산 같은 CPU 작업에 가상 스레드를 쓰면 어떻게 되나요?힌트: 이득의 출처가 무엇이었는지 (→ 7절, 11절)

이득이 없고, 미세한 손해가 있을 수 있다. 이유는 단순하다 — 이득의 출처가 "대기하는 동안 OS 스레드를 놓아주는 것"인데, CPU 바운드 작업에는 놓아줄 대기가 없다. 어차피 동시에 도는 개수는 코어 수가 상한이다.

비용이 붙는 위치를 정확히 보면 이렇다.

  • CPU로 계산하는 동안엔 오버헤드가 0이다. mount된 가상 스레드는 캐리어 스택 위에서 평범한 스레드와 똑같은 기계어로 돈다. 명령어마다 붙는 세금 같은 건 없다.
  • 비용은 블로킹 지점에만 붙는다 — 분기 체크 한 번과 freeze/thaw 복사. 그런데 플랫폼 스레드의 블로킹도 공짜가 아니다(커널 진입, 레지스터 저장, 캐시 오염). freeze/thaw는 이와 비슷하거나 오히려 싸다.

그래서 답은 "대기 없는 단일 작업이면 이득 0, 미세 손해 가능"이고, 실무 지침은 CPU 집약 작업은 코어 수 기반의 고정 플랫폼 스레드 풀에 그대로 둔다가 된다.

가상 스레드가 unmount됐다가 다른 캐리어에서 재개돼도 정말 괜찮나요? 무엇이 그것을 보장하나요?시니어 변별힌트: 옮긴 것이 무엇인지 (→ 4절)

괜찮다. 옮긴 것이 "실행 중인 스레드"가 아니라 데이터이기 때문이다.

freeze는 콜 스택 프레임들을 힙의 StackChunk 객체로 복사하는 작업이고, thaw는 그것을 아무 캐리어의 스택 위에나 다시 펼치는 작업이다. 프레임 안에는 지역변수 테이블·피연산자 스택·리턴 주소가 들어 있으므로, 어느 실행대에 올려도 멈췄던 자리에서 그대로 이어 달린다.

"실행 위치(레지스터·PC)"를 따로 백업하지 않아도 되는 이유가 결정적이다. freeze는 아무 데서나 일어나지 않고 항상 Continuation.yield()라는 정해진 메서드 호출 지점에서 일어난다. 메서드를 호출한 지점이라는 것은 곧 "돌아올 위치가 이미 스택 프레임의 리턴 주소로 기록돼 있다"는 뜻이다.

이 점이 커널과 결정적으로 다르다. 커널은 선점(preemption)으로 언제든 끊을 수 있어 끊긴 순간의 레지스터를 전부 저장해야 하지만, 가상 스레드는 본인이 정해진 지점에서 스스로 물러난다 — 협조적(cooperative) 스케줄링이다. 기절한 사람의 기억을 꺼내는 게 아니라 잠들기 전에 본인이 일기를 써 두는 방식이다.

그리고 참조의 정합성은 JVM이 프레임의 각 칸이 값인지 참조인지를 아는 메타데이터(GC가 스택을 훑을 때 쓰던 그 능력)를 갖고 있어 보장된다. 바로 이 능력이 없는 네이티브 프레임은 옮길 수 없고, 그것이 구조적 pinning의 근거다.

커넥션 풀을 200개로 늘리면 @Transactional 문제가 해결되나요?힌트: 풀 크기와 점유 시간 중 무엇이 지배적인가 (→ 9절, 11절)

오답에 가깝다. 커넥션은 DB 쪽에도 프로세스·메모리를 요구하는 자원이라, 무작정 늘리면 애플리케이션이 버티는 대신 DB가 먼저 무너진다.

순서가 정해져 있다. 먼저 할 일은 트랜잭션의 커넥션 점유 시간을 줄이는 것이고, 풀 크기 조정은 그다음이다. 처리량 상한 식이 풀 크기 ÷ 점유 시간이므로 분모를 줄이는 쪽이 훨씬 효율이 좋다.

20 ÷ 0.35s ≈ 57 req/s  →  (외부 콜을 트랜잭션 밖으로)  20 ÷ 0.05s = 400 req/s

같은 풀 20개로 7배가 된다. 풀을 200개로 늘려서 같은 효과를 보려면 DB에 그만큼의 부담을 지워야 한다.

다만 공짜는 아니다. 트랜잭션을 쪼갠 만큼 원자성이 깨지므로, 중간 실패 시 보상 처리나 상태 기반 재시도 같은 정합성 설계가 반드시 따라와야 한다. 이 대가를 함께 말해야 답이 완성된다.

InheritableThreadLocal은 왜 다시 점검해야 하나요?가산점힌트: 복사의 트리거가 무엇인가 (→ 10절)

복사의 트리거가 "요청"이 아니라 스레드 생성이기 때문이다. 이 한 줄이 답의 전부다.

InheritableThreadLocal은 스레드가 생성되는 순간 부모(그 생성 코드를 실행한 스레드)의 값 테이블을 자식에게 복사한다. 그러니 생성 빈도가 그대로 복사 빈도가 된다.

  • 플랫폼 스레드 풀 — 서버 시작 때 200개 만들고 끝이므로 복사도 200번뿐이다. 게다가 그 200번이 물려받는 건 풀을 만든 스레드(main 등)의 값이라 요청 문맥 전달용으로는 애초에 쓸모가 없었다. 그래서 풀 시대 프레임워크는 상속 대신 요청마다 set/remove를 썼다.
  • 가상 스레드(요청당 생성) — 내 코드가 가상 스레드를 안 만들어도 톰캣이 요청마다 만든다. 부모에 inheritable 값이 있는 한 요청 수만큼 복사가 일어난다.

그래서 판단 기준은 "내가 스레드를 만들었나"가 아니라 "요청마다 새 스레드가 태어나는 모델인가"다. 근본적인 대안은 값의 수명을 스레드가 아니라 코드 블록 범위에 매다는 ScopedValue인데, 불변이라 자식 작업에 넘길 때 복사가 아니라 참조 공유로 끝난다는 점이 개수 비용까지 해결한다.

"캐리어 스레드"는 특별한 OS 기능인가요? 어떻게 8개가 100만 개를 감당하죠?힌트: 마법이 어디에 있는지 (→ 7절)

특별하지 않다. OS 입장에서 캐리어는 new Thread()로 만든 것과 아무 차이 없는 평범한 OS 스레드이고, 특별한 커널 기능도 쓰지 않는다. 사실 OS는 가상 스레드의 존재를 전혀 모른다 — OS가 보는 것은 "이 자바 프로세스에 스레드가 8개 있네"뿐이다.

다른 것은 그 스레드가 실행하는 프로그램이다. 캐리어(ForkJoinPool 워커)가 도는 코드는 결국 무한 루프다 — "대기열에서 가상 스레드 하나 꺼냄 → thaw → 실행 → 걔가 yield하거나 끝나면 → 다시 꺼냄".

마법은 작업대(캐리어)가 아니라 서랍(Continuation의 freeze/thaw)에 있다

목수 8명이 의뢰 10만 건을 처리할 수 있는 것은 작업대가 마법이어서가 아니라 "재료를 기다리게 된 작업은 하다 만 상태 그대로 서랍에 넣고 다른 의뢰를 꺼낸다"는 규칙 덕분이다. 그리고 그 규칙을 실행하는 주체도 나뉘어 있다 — 내리는 건 본인, 올리는 건 캐리어, 깨우는 건 poller(7절). 별도의 관리자 스레드는 없다.

한 줄 요약
가상 스레드는 "스레드가 기다린다 = 비싼 OS 스레드가 논다"는 등식을 깬 기술이다 — 스레드의 정체가 "콜 스택 + 실행 위치"라는 데이터임을 이용해, 블로킹 시스템 콜에 들어가는 대신 JDK가 소유한 시스템 콜 직전 경로에서 "epoll 등록 + 아직 깨어 있는 스레드가 스스로 자기 스택 프레임을 힙으로 복사(freeze)하고 캐리어에서 물러나기"로 바꿔치기했고, 데이터가 도착하면 아무 캐리어에나 다시 올려(thaw) 이어 달린다(내리는 건 본인, 올리는 건 캐리어, 깨우는 건 poller — 마법은 캐리어가 아니라 Continuation에 있다). 그 대가로 JVM이 경로를 소유하지 못한 지점에서 pinning이 생기는데, synchronized는 모니터 소유자가 OS 스레드에 묶여 있어 프레임만 옮기면 잠금 장부가 어긋나기 때문이고(JDK 21~23에서는 ReentrantLock으로 교체, JDK 24의 JEP 491에서 해소 — 다만 잠금의 직렬화는 그대로 남는다), JNI 프레임은 JVM이 구조를 몰라 옮길 수 없어 어떤 버전에서도 남는다(탐지는 JDK 24부터 -Djdk.tracePinnedThreads가 제거되고 JFR jdk.VirtualThreadPinned가 정식 경로다). 그리고 가장 실무적인 함정은 가상 스레드가 값싸게 만든 것은 자바 스레드일 뿐 DB 커넥션이 아니라는 것 — 트랜잭션은 커넥션에 묶여 있고 풀은 여전히 20개라 처리량 상한 57 req/s는 그대로인데, 톰캣 200 스레드가 해 주던 암묵적 부하 제한만 사라져 대기 행렬이 무한정 길어지고 커넥션 타임아웃으로 더 크게 터진다. 그러니 도입의 본질은 암묵적 제한을 명시적 제한으로 바꾸는 일이다 — 외부 콜을 트랜잭션 밖으로 빼고, Semaphore로 동시성을 직접 제한하고, 스레드 수 대신 커넥션 풀 대기와 JFR 이벤트를 보도록 관측 지표를 다시 세우고, ThreadLocal은 문맥 전달만 남기고 스레드당 캐싱은 걷어낸다(후속은 불변 · 블록 범위의 ScopedValue, JDK 25 정식).
