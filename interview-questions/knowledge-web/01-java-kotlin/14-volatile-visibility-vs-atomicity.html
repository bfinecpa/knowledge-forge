volatile — 보이게는 해주지만, 끼어들기는 못 막는다
가시성은 "보이느냐"의 문제, 원자성은 "끼어들 수 있느냐"의 문제 — 서로 다른 문제이고 volatile은 앞의 것만 해결한다

면접 질문: "volatile 키워드는 무엇을 보장하고, 무엇을 보장하지 못하나요? (가시성 vs 원자성)"

핵심 관전 포인트 — volatile은 두 가지를 보장한다 — ① 가시성(한 스레드가 쓴 값이 다른 스레드에게 반드시 보인다), ② 그 변수를 기준으로 한 재배치 방지. 그러나 원자성은 보장하지 않는다 — volatile int count의 count++는 읽기·계산·쓰기 3단계로 이루어진 복합 연산이라, 그 사이에 다른 스레드가 끼어드는 것을 volatile은 전혀 막지 못한다. 그래서 volatile은 "한 스레드가 쓰고 여러 스레드가 읽는 플래그·상태 발행"에만 적합하고, 읽고-고치고-쓰는 복합 연산에는 AtomicInteger(CAS)나 락이 필요하다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "volatile 키워드는 무엇을 보장하고, 무엇을 보장하지 못하나요? (가시성 vs 원자성)"

출제 의도 — volatile int counter++ 같은 코드가 왜 틀렸는지 즉시 보이는지를 확인한다. 동시성 버그는 테스트를 통과하고 운영에서만 터지므로, 코드 리뷰 단계에서 잡을 수 있는 사람의 가치가 특히 크다.

약점 A"volatile은 동기화 키워드"라고 뭉뚱그리는 답 — 가시성과 원자성을 한 덩어리로 붙여 놓고 있으면, "그럼 count++는요?"라는 한 번의 되물음에 무너진다.
약점 B"volatile은 값을 메인 메모리에서 읽어옵니다"에서 끝나는 답 — 두 번째 보장인 재배치 방지를 말하지 못한다. DCL 싱글턴·안전 발행 질문으로 넘어가면 답이 막힌다.
약점 C"두 스레드가 서로 다른 값을 읽어서 틀린다"는 오해 — 갱신 유실은 두 스레드가 모두 최신 값을 정확히 읽고도 발생한다. 이 지점을 뒤집어 설명하지 못하면 원인을 잘못 짚은 것이다.
합격선"volatile은 보이게는 해주지만 끼어들기는 못 막는다"를 count++ 3단계 타임라인으로 한 호흡에 증명하고, 이어서 맞는 자리(플래그·참조 교체)와 틀린 자리(복합 연산·검사 후 행동)를 나눠 말하는 것.
이 문서의 진행 방향 — 두 개의 전제 지식을 먼저 깐다 volatile의 두 보장은 각각 "왜 안 보일 수 있는가(캐시·컴파일러)"와 "왜 순서가 바뀌는가(재배치)"를 알아야 이해된다. 그래서 1·3절에서 이 두 전제를 먼저 세우고, 5절부터 volatile이 손대지 못하는 영역(원자성)으로 넘어간다. 공식적인 근거인 happens-before 규칙은 15-jmm-happens-before에서 다루고, 여기서는 결론과 그림만 쥐고 간다.

1. 전제 ① 왜 "안 보일" 수 있는가 — CPU 캐시 계층

"한 스레드가 쓴 값이 다른 스레드에게 안 보일 수 있다"는 말은 처음 들으면 납득이 안 된다. 같은 프로세스 안의 같은 변수인데 왜 안 보인다는 말인가. 답은 CPU가 메인 메모리를 직접 읽고 쓰지 않는다는 사실에 있다.

현대 CPU에게 메인 메모리(RAM)는 너무 느리다. L1 캐시 접근 비용을 1이라 치면 메인 메모리 접근은 수십에서 수백 배에 달한다. 그래서 CPU는 자주 쓰는 데이터를 자기 가까이에 복사해 두고 그 복사본으로 일한다. 이 복사본 저장소가 캐시이고, 속도와 크기를 절충해 여러 층으로 쌓여 있다.

비유 — 원본은 창고에, 복사본은 내 책상에 각 스레드는 원본 문서(메인 메모리)의 복사본(캐시)을 자기 책상에 놓고 일한다. 누가 원본을 고쳐도 내 책상의 복사본만 계속 들여다보면 알 길이 없다. volatile은 그 변수에 "이건 복사본으로 처리하지 말고 항상 원본을 확인하고, 고쳤으면 즉시 원본에 반영해라"는 표시를 붙이는 것이다.

여기에 문제 하나가 더 겹친다 — JIT 컴파일러의 최적화

컴파일러가 "이 루프 안에서 stopRequested를 바꾸는 코드가 없네"라고 판단하면, 매번 메모리를 확인하는 대신 값을 레지스터에 한 번만 담아두고 계속 쓰도록 코드를 바꾼다. 단일 스레드 기준으로는 완벽하게 옳은 최적화지만, 다른 스레드가 그 값을 바꾼다는 사실은 컴파일러가 알 도리가 없다.

가시성(visibility)이란 — 이 한 줄로 외운다

한 스레드가 쓴 값을 다른 스레드가 언제 볼지, 심지어 보기는 할지 보장되지 않는 성질

원인은 두 층이다 — 하드웨어(코어 전용 캐시의 복사본)와 소프트웨어(컴파일러·JIT가 값을 레지스터에 승격). volatile은 두 층을 한꺼번에 막는다. 캐시 관점에서는 "항상 공유 지점까지 읽고 쓰라", 컴파일러 관점에서는 "이 읽기를 루프 밖으로 끌어올리지 말라"는 지시가 동시에 걸린다.

2. before/after — 영원히 안 멈추는 워커 스레드

가시성 문제가 실제 코드에서 어떤 모습으로 나타나는지, 가장 유명한 사례로 본다. "종료 신호를 보냈는데 스레드가 안 멈춘다"는 장애다.

문제 volatile이 없어서 종료 신호가 워커에게 도달하지 않을 수 있다
class Worker implements Runnable {
    private boolean stopRequested = false;  // 잘못됨: volatile이 없다

    public void run() {
        while (!stopRequested) {   // JIT가 "이 루프 안에서
            doWork();              // 안 바뀌는 값"으로 판단해
        }                          // 읽기를 루프 밖으로 끌어올릴 수 있다.
    }                              // 사실상 while(true)로 컴파일된 것과 같아진다.

    public void stop() { stopRequested = true; }
}   // 다른 스레드가 이걸 호출해도 워커의 캐시/레지스터에는 안 보일 수 있다
개선 volatile 하나로 가시성을 확보한다
class Worker implements Runnable {
    private volatile boolean stopRequested = false;

    public void run() {
        while (!stopRequested) {   // 매 반복마다 실제로 읽는다
            doWork();
        }
    }

    public void stop() { stopRequested = true; }
}
// 쓰기는 즉시 다른 코어가 볼 수 있는 곳까지 발행되고,
// 읽기는 캐시된 옛 값이 아니라 최신 값을 가져오도록 강제된다.
// 컴파일러도 이 변수의 읽기를 루프 밖으로 끌어올리지 못한다.
이 버그가 특히 고약한 이유 — 로컬에서는 대부분 잘 멈춘다 짧게 도는 코드는 JIT가 아직 공격적으로 최적화하지 않은 인터프리터 단계에 머무르고, 그 상태에서는 매번 메모리를 읽으므로 정상 동작한다. 오래 돌면서 JIT가 충분히 최적화한 운영 서버에서만 안 멈추는 스레드가 나타난다. 출제 의도가 짚는 "테스트를 통과하고 운영에서만 터지는" 버그의 전형이다.

3. 전제 ② 재배치(reordering)란 무엇인가

volatile의 두 번째 보장을 이해하려면 재배치를 먼저 알아야 한다.

컴파일러와 CPU는 성능을 위해 명령의 실행 순서를 바꾼다. 임의로 바꾸는 것은 아니고 지켜야 할 선이 하나 있다 — 단일 스레드에서 관측되는 결과가 같기만 하면 순서를 바꿔도 된다. 이 규칙을 as-if-serial(마치 순차 실행한 것처럼) 원칙이라 부른다.

그래서 필요한 장치 — 메모리 배리어

그 최적화를 특정 지점에서만 제한하는 장치가 필요해진다. 그것이 메모리 배리어(memory barrier) — "이 지점을 넘어 읽기·쓰기를 재배치하지 말고, 여기까지의 쓰기를 다른 코어가 볼 수 있게 하라"고 CPU에 지시하는 특수 명령이다. volatile 변수를 읽고 쓸 때 컴파일러가 이 배리어를 자동으로 끼워 넣는다.

4. 보장 ② 재배치 방지와 안전 발행

volatile 변수에 대한 읽기·쓰기는 그 앞뒤 코드가 이 변수를 넘어 재배치되는 것을 막는다. 그래서 volatile 변수 하나가 "그 이전에 쓴 일반 변수들까지 통째로 발행하는" 다리 역할을 하게 된다.

패턴 일반 변수 + volatile 스위치 — 안전 발행(safe publication)
int data = 0;                    // 일반 변수 (volatile 아님)
volatile boolean ready = false;  // 발행 스위치 역할

// 스레드 A                       // 스레드 B
data = 42;      // ①              if (ready) {       // ready == true를 봤다면
ready = true;   // ② 발행              print(data);   // data == 42도 반드시 보인다
                                  }

data에는 volatile이 없는데도 42가 보장된다는 것이 이 패턴의 요점이다. ready = true라는 volatile 쓰기가 그 이전의 모든 쓰기를 함께 밀어내고, ready를 읽은 스레드는 그 시점 이전의 쓰기를 전부 이어받기 때문이다.

이 절에서 외울 것은 이 한 문장이다

volatile 쓰기 이전의 모든 쓰기는, 그 volatile을 읽은 스레드에게 함께 보인다

이 보장의 공식적인 근거는 happens-before 규칙과 그 이행성이며 15-jmm-happens-before에서 다룬다. 이 문서에서는 결론만 쥐고 가면 된다. 실무에서 이 문장이 쓰이는 자리는 설정 리로드(새 객체를 다 채운 뒤 참조 교체), 초기화 완료 신호, double-checked locking(13절) 셋이다.

여기까지가 volatile이 하는 일의 전부다

✓
보장 ① 가시성
쓴 값이 다른 스레드에게 반드시 보인다. 캐시·레지스터의 옛 복사본으로 처리되지 않는다.
✓
보장 ② 재배치 방지
그 변수를 기준선으로 앞뒤 명령의 순서가 뒤집히지 않는다. 앞선 쓰기까지 함께 발행된다.
✗
미보장 — 원자성
읽고-고치고-쓰는 복합 연산 중간에 다른 스레드가 끼어드는 것은 전혀 막지 못한다. 5절부터가 이 이야기다.

5. 원자성이란 — count++는 3단계다

원자성(atomicity)의 정의 — 가시성과 나란히 놓고 외운다

여러 단계로 이루어진 연산이 중간에 끼어들 틈 없이 하나의 덩어리로 처리되는 성질

더 이상 쪼갤 수 없다는 뜻에서 "원자"라 부른다. 가시성이 "보이느냐"의 문제라면 원자성은 "끼어들 수 있느냐"의 문제다 — 완전히 다른 문제이고, volatile은 앞의 것만 해결한다.

count++는 소스에서 한 줄이지만 실제로는 세 단계다. volatile은 ①이 최신 값을 읽게 하고 ③이 즉시 발행되게 할 뿐, ①·②·③ 사이에 다른 스레드가 끼어드는 것은 전혀 막지 못한다.

6. 갱신 유실 타임라인 — 최신 값을 읽고도 틀린다

count가 5인 상태에서 두 스레드가 동시에 증가시키는 과정을 시간순으로 따라가 보자. 두 변수 모두 volatile int count다 — 즉 아래 그림에서 가시성은 완벽하게 지켜지고 있다.

두 스레드가 volatile int count(초기값 5)를 각각 한 번씩 증가시킬 때
시각스레드 A스레드 B이 시점 count의 값
t1① 읽기 → 5—5
t2—① 읽기 → 5 (최신 값이 맞다)5
t3② 5 + 1 = 6—5
t4—② 5 + 1 = 65
t5③ 6 쓰기—6
t6—③ 6 쓰기 (A의 결과를 덮는다)6  ← 7이어야 한다
두 스레드 모두 최신 값을 정확히 읽었는데도 결과가 틀렸다.
그러므로 이것은 가시성 문제가 아니다 — volatile로는 절대 고쳐지지 않는다.

7. 가시성 vs 원자성 — 다른 문제, 다른 도구

이 절이 이 문서의 축이다. 두 문제를 한 화면에 나란히 놓고 어디가 다른지 본다.

가시성 문제와 원자성 문제 — 증상·원인·도구가 전부 다르다
구분가시성 (visibility)원자성 (atomicity)
묻는 것내가 쓴 값이 남에게 보이는가내 연산 묶음 중간에 끼어들 수 있는가

8. 해법 ① CAS — AtomicInteger는 왜 락이 없어도 되나

문제 volatile을 붙였으니 안전하다는 착각
class HitCounter {
    private volatile int count = 0;   // volatile은 여기서 무력하다

    public void hit() {
        count++;      // 읽기·계산·쓰기 3단계 → 갱신 유실
    }
    public int get() { return count; }
}
// 1,000개 스레드가 1,000번씩 hit()을 호출해도
// 결과는 1,000,000보다 작게 나온다. 그것도 매번 다르게.
개선 1 AtomicInteger — CAS로 원자적 증가
class HitCounter {
    private final AtomicInteger count = new AtomicInteger();

    public void hit() {
        count.incrementAndGet();   // 읽기+증가+쓰기가 한 덩어리
    }
    public int get() { return count.get(); }
}
// CAS = "이 값이 내가 읽었던 값 그대로면 새 값으로 바꿔라"를
// CPU가 한 명령으로 처리하는 원자 연산.
// 실패해도 스레드가 잠들지 않아 락보다 싸다.

CAS를 세 박자로 외운다

① 읽는다 (기대값 확보)→ ② 계산한다→ ③ "아직 기대값이면" 바꾼다→ 실패하면 ①로 (잠들지 않음)

면접 답변에서 반드시 붙여야 할 한마디 — "비교와 교체 사이에 끼어들 틈이 없다는 것을 소프트웨어가 아니라 CPU가 보장합니다." 이 문장이 있어야 "락 없이 어떻게 안전하냐"는 되물음이 닫힌다.

9. 해법 ② synchronized · 둘의 갈림길

개선 2 synchronized — 상호배제로 끼어들기 자체를 차단
private int count = 0;   // volatile이 필요 없다 — 락이 가시성까지 준다

public synchronized void increment() { count++; }
public synchronized int get() { return count; }   // 읽기도 같은 락으로 감싸야 한다
// A가 ①~③을 끝낼 때까지 B는 아예 진입하지 못한다.
// 대신 락을 못 잡은 스레드는 잠들었다 깨어나는 비용(컨텍스트 스위칭)을 치른다.
자주 나오는 반쪽 동기화 — 쓰기만 감싸고 읽기는 맨몸으로 increment()만 synchronized로 감싸고 get()은 그냥 두면 원자성은 지켜지지만 가시성은 보장되지 않는다. 락의 가시성 보장은 "같은 락을 잡았다 푸는 두 스레드 사이"에서 성립하기 때문이다. 읽는 쪽도 같은 락을 잡거나, 필드를 volatile로 두거나, Atomic*을 쓰는 것 중 하나를 골라야 한다.
동기화 도구 4종 — 무엇을 주고 무엇을 안 주는가
도구가시성단일 읽기·쓰기 원자성복합 연산 원자성재배치 방지스레드 블로킹맞는 자리
volatile○○ (long/double 포함)✕○없음상태 플래그 · 불변 객체 참조 교체 · DCL 필드
AtomicInteger 등 (CAS)○○○ (제공되는 연산에 한해)○없음 (실패 시 재시도)카운터 · 조건부 갱신 · "한 번만 실행"
synchronized / ReentrantLock○ (같은 락으로 읽을 때)○○ (구간 전체)○있음여러 변수의 불변식 · 긴 임계 구역
final + 불변 객체○ (생성자에서 this 유출 없을 때)해당 없음해당 없음 (상태가 안 바뀜)○ (final 필드 보장)없음애초에 공유 가변 상태를 없애는 설계
표에서 한 칸만 외운다면 volatile의 "복합 연산 원자성 ✕" 한 칸이다. 나머지 칸은 전부 ○인데 딱 그 한 칸이 비어 있고, 실무 버그의 대부분이 정확히 그 칸에서 나온다.

10. 검사 후 행동(check-then-act)도 같은 구조다

원자성 문제는 ++에만 있는 게 아니다. "읽어서 판단하고, 그 판단에 따라 쓰는" 모든 코드가 같은 구조다.

문제 검사와 행동 사이가 비어 있다
private volatile Connection conn;

public Connection get() {
    if (conn == null) {        // 검사(check)
        conn = create();       // 행동(act)
    }
    return conn;
}
// 두 스레드가 나란히 null을 보면 create()가 두 번 실행된다.
// 커넥션 하나가 누수되고, 둘 중 하나만 살아남는다.
개선 묶거나(락), 원자 연산으로 바꾼다(CAS)
private final AtomicReference<Connection> ref = new AtomicReference<>();

public Connection get() {
    Connection cur = ref.get();
    if (cur != null) return cur;
    Connection created = create();
    if (ref.compareAndSet(null, created)) return created;
    close(created);            // 경쟁에서 진 쪽은 자기 것을 정리
    return ref.get();          // 이긴 쪽의 것을 쓴다
}
// 또는: synchronized로 검사+행동을 한 덩어리로 묶는다.
// 생성 비용이 크고 낭비가 아까우면 락, 값싸면 위 방식이 낫다.

이름만 다른 같은 버그 — 코드에서 이 형태를 보면 멈춘다

null 체크 후 초기화
객체가 두 번 만들어지고 하나가 누수된다
잔액 확인 후 차감
잔액이 음수가 된다
재고 확인 후 감소
재고보다 많이 팔린다(오버셀)
중복 검사 후 INSERT
중복 행이 들어간다 — DB 유니크 제약이 최후 방어선
파일 존재 확인 후 생성
서로의 파일을 덮어쓴다
"아직 처리 전이면 처리"
같은 메시지를 두 번 처리한다

공통 형태는 if (조건) { 그 조건에 의존하는 쓰기 }다. 조건을 읽은 순간과 쓰는 순간 사이에 세계가 바뀔 수 있다는 것만 기억하면 된다. 단일 JVM 안이면 락·CAS, 여러 서버로 흩어져 있으면 DB 유니크 제약·조건부 UPDATE·분산 락으로 같은 원리를 올려 쓴다.

11. 예외 하나 — long/double 워드 티어링 가산점

volatile이 원자성을 전혀 안 준다는 말에는 한 가지 예외가 있다.

long과 double은 64비트 값인데, JLS는 volatile이 없는 long/double에 대해 읽기·쓰기 자체가 32비트씩 두 번으로 쪼개지는 것을 허용한다. 그러면 한 스레드가 상위 32비트만 쓴 시점에 다른 스레드가 읽어서 앞쪽은 새 값, 뒤쪽은 옛 값인 "존재하지 않았던 숫자"를 얻을 수 있다.

이 예외가 만드는 두 개의 함정

함정 A — "volatile long이면 카운터도 안전하다"
아니다. volatile long counter의 counter++는 여전히 갱신을 유실한다. 보장된 것은 읽기 1회·쓰기 1회가 쪼개지지 않는다는 것뿐이다.
함정 B — "int는 32비트니까 아무 문제 없다"
티어링은 없지만 가시성 문제는 그대로다. 티어링이 없다는 것과 다른 스레드에게 보인다는 것은 완전히 별개다.

면접 답변으로 정리하면 — "volatile은 long/double의 단일 읽기·쓰기 원자성까지는 보장하지만, 그 이상(복합 연산)은 보장하지 않습니다." 이 한 문장이면 예외까지 아는 사람으로 보이면서 결론도 흐려지지 않는다.

12. 맞는 자리 / 틀린 자리 — 3조건 판정

volatile로 충분한 조건 — 셋 다 만족해야 하고, 하나라도 어긋나면 올라간다

1쓰기가 현재 값에 의존하지 않는다 — 단순 대입이지 ++가 아니다어긋나면 → CAS / 락
2다른 변수와 함께 지켜야 하는 불변식이 없다어긋나면 → 락
3쓰는 스레드가 사실상 하나다 (읽는 쪽은 여럿이어도 된다)어긋나면 → 재검토

외우는 방법 — "의존하지 않고, 얽히지 않고, 한 명만 쓴다." 세 조건 모두 쓰기 쪽에 대한 조건이라는 점이 힌트다. volatile은 읽기를 아무리 많이 해도 안전하고, 문제는 언제나 쓰기에서 생긴다.

맞는 자리 ② 불변 객체 참조 교체 — 설정 리로드

정답 사례 새 객체를 통째로 만들어 참조만 바꿔치기한다
private volatile Config config;   // Config는 불변(immutable) 객체여야 한다

public void reload() {
    config = loadNewConfig();
    // 참조 대입 한 번 = 단일 쓰기이므로 원자적이다.
    // 읽는 쪽은 "온전한 옛 설정" 아니면 "온전한 새 설정"만 보고,
    // 필드 일부만 바뀐 중간 상태는 존재할 수 없다.
}
// Config가 가변 객체라면 이 보장이 무너진다 — 읽는 쪽이 참조를 잡은 뒤
// 그 내부 필드가 바뀌면 그건 volatile이 관여하지 않는 영역이다.
맞는 자리 — "한 명이 쓰고, 여럿이 읽는" 구조
  • 종료·상태 플래그 — volatile boolean shutdown. 쓰는 쪽은 관리 스레드 하나, 읽는 쪽은 워커 여럿. 쓰기가 true 대입 한 번이라 쪼개질 여지가 없다.
  • 불변 객체 참조 교체 — 설정 리로드, 라우팅 테이블 스왑, 캐시 스냅샷 교체.
  • double-checked locking의 인스턴스 필드 — 여기서는 가시성보다 재배치 방지가 결정적이다(13절).
  • 단발성 초기화 완료 신호 — ready를 켜기 전에 채운 데이터까지 함께 발행된다(4절).
틀린 자리 — 여기 있으면 도구를 올린다
  • 카운터·누적 합계 등 읽고-고치고-쓰는 모든 것 — Atomic*이나 락으로 올라가야 한다.
  • 검사 후 행동 — null 체크 후 초기화, 조건 확인 후 갱신. 락 또는 CAS 루프가 필요하다.
  • 두 변수가 함께 일관돼야 하는 불변식 — 각각의 읽기·쓰기는 원자적이지만 "두 값을 함께"는 원자적이지 않다.
  • 가변 객체를 가리키는 참조 — 참조 교체는 보호되지만 객체 내부 변경은 보호되지 않는다.

13. double-checked locking의 volatile

volatile의 두 번째 보장(재배치 방지)이 결정적으로 필요한 유일한 유명 사례다. 가시성 이야기만 알고 오면 이 질문에서 막힌다.

패턴 매번 락을 잡는 비용을 피하려고 락 없이 먼저 확인하는 구조
private static volatile Holder instance;   // 이 volatile이 없으면 깨진다

static Holder get() {
    if (instance == null) {                // ① 락 없이 하는 1차 검사 (빠른 경로)
        synchronized (Holder.class) {
            if (instance == null) {        // ② 락 안에서 하는 2차 검사
                instance = new Holder();   // ③ 이 한 줄이 사실은 3단계다
            }
        }
    }
    return instance;
}

이 패턴은 매번 락을 잡는 비용을 피하려고 ①에서 락 없이 먼저 확인하는 구조다. 그런데 락 없이 읽는 경로가 존재한다는 바로 그 이유 때문에 재배치에 취약해진다.

가산점 — 요즘은 이 패턴을 직접 쓸 이유가 거의 없다 클래스 로딩의 초기화 보장을 이용하는 holder 클래스 관용구나 enum 싱글턴이 더 단순하고 안전하며, 무엇보다 volatile을 빠뜨릴 여지가 없다. 스프링을 쓴다면 빈 스코프가 이미 이 문제를 대신 해결해 준다는 점도 짚을 만하다.
대안 holder 클래스 관용구 — JVM의 클래스 초기화 보장에 맡긴다
class Singleton {
    private Singleton() {}

    private static class Holder {                 // 처음 참조될 때 로딩된다
        static final Singleton INSTANCE = new Singleton();
    }

    static Singleton get() { return Holder.INSTANCE; }
}
// 클래스 초기화는 JVM이 락으로 보호하며 정확히 한 번만 수행한다.
// 지연 초기화 + 스레드 안전 + 코드에 동기화 키워드 0개.

14. 비용과 코드 리뷰 체크리스트

비용 ① 최적화가 금지된다

값을 레지스터나 캐시에 오래 담아두고 재사용하는 최적화, 루프 밖으로 읽기를 끌어올리는 최적화가 막힌다. 매번 실제로 읽어야 한다.

비용 ② 메모리 배리어가 들어간다

재배치 금지와 발행을 위해 CPU에 특수 명령이 삽입되고, 이는 CPU 파이프라인과 쓰기 버퍼 최적화를 제한한다.

다만 이 비용은 락과 성격이 다르다 volatile은 스레드를 블로킹하지도, 컨텍스트 스위칭을 유발하지도 않는다. 그래서 일반적으로 락보다 훨씬 싸다. 결론은 "그러니 아무 데나 붙이자"가 아니다. 실제로 여러 스레드가 공유하는 변수에만 정확히 붙이는 것이 맞다 — 단일 스레드만 접근하는 필드에 붙은 volatile은 얻는 것 없이 최적화만 막는다.

코드 리뷰 체크리스트 — AI 생성 코드 검증 포함

AI가 생성한 동시성 코드에서 특히 자주 보이는 오류가 "동기화가 필요하다는 건 알았는데 volatile을 만능으로 쓴" 형태다. 리뷰할 때 이 셋을 본다.

1volatile 변수에 ++, +=, --가 있는가 — 있으면 그 자리에서 지적한다. 복합 연산이므로 무조건 틀렸다.무조건 결함
2volatile 변수를 if로 검사한 뒤 그 결과에 따라 쓰기를 하는가 — 검사 후 행동이다.무조건 결함
3쓰는 스레드가 정말 하나인가 — 둘 이상이 쓴다면 volatile로 충분한 경우가 드물다.근거 요구

덧붙일 만한 네 번째 — volatile이 가리키는 객체가 가변인가. volatile Config가 있는데 config.setTimeout(...) 같은 세터 호출이 함께 보이면, 그 코드는 보호되지 않는 영역을 보호되는 것처럼 다루고 있다.

이 체크리스트가 유효한 이유는 동시성 버그가 테스트로 잘 안 잡히기 때문이다. 대부분의 경합은 타이밍이 맞아떨어져야 재현되고, 그 타이밍은 부하가 높은 운영 환경에서 훨씬 자주 만들어진다. 리뷰에서 잡지 못하면 그 다음 방어선은 장애다.

30초 답변 조립 — 이 순서로 말한다

1보장 둘을 먼저 세운다 — "volatile은 가시성과 그 변수 기준의 재배치 방지를 보장합니다."10초
2못 하는 것을 반례로 못 박는다 — "count++는 읽기·계산·쓰기 3단계라, 두 스레드가 모두 최신 값을 정확히 읽고도 갱신이 유실됩니다."10초
3자리로 닫는다 — "그래서 한 명이 쓰고 여럿이 읽는 플래그·참조 교체에는 volatile, 읽고-고치고-쓰는 연산에는 Atomic*(CAS)나 락을 씁니다."10초

시간이 더 주어지면 붙일 카드 — 안전 발행(volatile 쓰기가 앞선 쓰기를 함께 발행), DCL의 반쪽짜리 객체, long/double 워드 티어링, volatile 읽기가 락보다 싼 이유. 넷 다 "그래서 어디에 쓰느냐"로 되돌아와야 지식 자랑이 아니라 판단으로 들린다.

15. 꼬리질문 셀프 테스트 (13문항)

질문만 먼저 읽고 소리 내어 답해본 뒤 펼친다. 막히면 그 자리가 다시 읽어야 할 절이다.

volatile int count에 count++를 하면 정확히 무엇이 어떻게 깨지나요?핵심힌트: "틀린 값을 읽어서"가 아니다

count++는 읽기 → 계산 → 쓰기 3단계이고, volatile은 이 묶음을 원자적으로 만들지 않는다.

count가 5일 때 두 스레드가 나란히 5를 읽으면, 각자 6을 계산해서 각자 6을 쓴다. 두 번 증가시켰는데 결과는 7이 아니라 6이다. 이것이 갱신 유실(lost update)이다.

여기서 강조할 점은 두 스레드 모두 최신 값을 정확히 읽었다는 것이다. volatile은 자기 일을 했다. 문제는 한쪽이 읽고-계산하고-쓰기를 끝내기 전에 다른 쪽이 읽었다는 것, 즉 가시성이 아니라 끼어들기다.

해결은 AtomicInteger.incrementAndGet()(CAS)이나 synchronized다. 가시성 문제가 아니라 상호배제 문제이기 때문에 도구가 달라진다.

AtomicInteger는 락 없이 어떻게 원자성을 보장하나요?힌트: 소프트웨어가 아니라 CPU가 보장한다

CAS(Compare-And-Swap) — "이 메모리 값이 내가 읽었던 값 그대로면 새 값으로 바꿔라"를 CPU가 하나의 하드웨어 명령으로 처리한다. 비교와 교체 사이에 다른 스레드가 끼어들 틈이 없다는 것을 소프트웨어가 아니라 CPU가 보장한다.

동작은 이렇다. 현재 값을 읽고, 새 값을 계산하고, "아직 아까 그 값이면 새 값으로" 교체를 시도한다. 그 사이 누가 값을 바꿨으면 교체가 실패하고, 실패하면 잠들지 않고 곧바로 다시 읽어 재시도한다.

락과의 결정적 차이가 이 지점이다. 락은 못 잡으면 스레드가 커널에 의해 대기 상태로 내려갔다가 깨워져야 해서 컨텍스트 스위칭 비용이 든다. CAS는 그게 없어 경합이 짧을 때 훨씬 싸다. 반대로 경합이 극심하면 재시도가 반복되며 CPU만 태우므로 항상 유리한 것은 아니다.

volatile과 synchronized의 차이는? 언제 volatile로 충분한가요?시니어 변별힌트: 락은 두 가지 일을 동시에 한다

synchronized는 가시성과 상호배제 둘 다 주고, volatile은 가시성(과 재배치 방지)만 준다. 락이 두 가지 일을 동시에 하기 때문에 흔히 "동기화 = 락"으로 뭉뚱그려지는데, 이 둘을 분리해서 볼 수 있느냐가 갈림길이다.

volatile로 충분한 조건은 셋이고, 하나라도 어긋나면 락이나 CAS로 올라가야 한다.

  1. 쓰기가 현재 값에 의존하지 않는다(단순 대입이지 ++가 아니다).
  2. 다른 변수와 함께 지켜야 하는 불변식이 없다.
  3. 쓰는 스레드가 사실상 하나다.

이 조건을 만족하는 전형이 상태 플래그와 불변 객체 참조 교체다.

비용 관점을 덧붙이면 설계 판단으로 보인다. volatile 읽기는 락 획득보다 훨씬 싸다 — 스레드를 재우지 않기 때문이다. 그래서 "쓰기는 드물고 읽기가 압도적으로 많은 발행·구독 구조"에서는 volatile을 고르는 것이 성능상 의미 있는 선택이 된다. 반대로 불변식을 지켜야 하는 자리에 비용을 이유로 volatile을 고르는 것은 선택이 아니라 오류다.

double-checked locking 싱글턴에서 volatile은 왜 필요한가요?힌트: 가시성보다 재배치 방지가 결정적이다

new Holder()는 실제로 "메모리 할당 → 생성자 실행 → 참조를 변수에 대입"의 3단계인데, volatile이 없으면 생성자 실행과 참조 대입의 순서가 뒤바뀔 수 있다. 단일 스레드에서는 결과가 같으므로 허용되는 재배치다.

문제는 그 사이를 다른 스레드가 락 없이 하는 1차 검사에서 들여다볼 때다. 참조는 이미 대입돼 null이 아닌데 필드는 아직 초기화 전인 반쪽짜리 객체를 받아 쓰게 된다. 필드가 전부 기본값(0, null)인 객체가 정상인 척 돌아다니는 것이다.

volatile은 두 가지 일로 이걸 막는다. 그 재배치를 금지하고, 쓰기 이전의 모든 쓰기(생성자가 채운 필드들)를 함께 발행한다.

가산점 요즘은 이 패턴을 직접 쓸 이유가 거의 없다. 클래스 로딩의 초기화 보장을 이용하는 holder 클래스 관용구나 enum 싱글턴이 더 단순하고 안전하며, 무엇보다 volatile을 빠뜨릴 여지가 없다. 스프링을 쓴다면 빈 스코프가 이미 이 문제를 대신 해결해 준다는 점도 짚을 만하다.

volatile 읽기·쓰기에는 비용이 없나요?힌트: 공짜는 아니지만 락과는 성격이 다르다

공짜는 아니다. 두 가지 비용이 있다.

① 최적화가 금지된다. 값을 레지스터나 캐시에 오래 담아두고 재사용하는 최적화, 루프 밖으로 읽기를 끌어올리는 최적화가 막힌다. 매번 실제로 읽어야 한다.

② 메모리 배리어가 들어간다. 재배치 금지와 발행을 위해 CPU에 특수 명령이 삽입되고, 이는 CPU 파이프라인과 쓰기 버퍼 최적화를 제한한다.

다만 이 비용은 락과는 성격이 다르다. volatile은 스레드를 블로킹하지도, 컨텍스트 스위칭을 유발하지도 않는다. 그래서 일반적으로 락보다 훨씬 싸다.

결론은 "그러니 아무 데나 붙이자"가 아니다. 실제로 여러 스레드가 공유하는 변수에만 정확히 붙이는 것이 맞다. 단일 스레드만 접근하는 필드에 붙은 volatile은 얻는 것 없이 최적화만 막는다.

synchronized도 가시성을 보장한다면, volatile은 애초에 필요 없는 것 아닌가요?시니어 변별힌트: 필요 없어지려면 "읽는 쪽도" 락을 잡아야 한다

맞다. 락도 가시성을 보장한다. 락을 푸는 시점까지의 모든 쓰기는, 같은 락을 그다음에 잡는 스레드에게 보인다. 그래서 기능만 놓고 보면 volatile이 하는 일을 락으로 대체할 수 있다.

다만 두 가지 조건이 붙는다. 첫째, 읽는 쪽도 같은 락을 잡아야 한다. 쓰기만 synchronized로 감싸고 읽기는 맨몸으로 하는 코드는 가시성이 보장되지 않는다 — 실무에서 아주 흔한 반쪽 동기화다. 둘째, 읽기마다 락을 잡는 비용을 치른다.

그래서 판단은 이렇게 갈린다. 지켜야 할 불변식이 있으면 락, 단순 상태 하나를 발행하고 읽기가 압도적으로 많으면 volatile이다. "락으로도 되니까 전부 락"은 읽기가 많은 구조에서 불필요한 직렬화를 만든다.

volatile boolean과 AtomicBoolean 중 무엇을 쓰나요?힌트: Atomic 계열은 "volatile + CAS 연산"이다

Atomic* 클래스의 내부 값 필드는 volatile이다. 그래서 get()/set()은 volatile 읽기·쓰기와 사실상 같고, 여기에 compareAndSet·getAndSet 같은 원자적 복합 연산이 더 붙은 것이 AtomicBoolean이라고 이해하면 된다.

따라서 판단 기준은 하나다. 필요한 연산이 "단순 대입 + 읽기"뿐이면 volatile boolean으로 충분하다. 종료 플래그가 여기 해당한다.

반면 "단 한 번만 실행되게 하고 싶다"처럼 검사와 변경이 한 덩어리여야 하면 AtomicBoolean이 필요하다. if (!closed) { closed = true; cleanup(); }는 두 스레드가 함께 통과할 수 있지만, if (closed.compareAndSet(false, true)) { cleanup(); }는 정확히 한 스레드만 true를 받는다.

volatile int[] arr이라고 쓰면 배열 원소도 volatile인가요?함정힌트: volatile이 붙은 대상이 무엇인지 정확히 보라

아니다. volatile이 걸린 것은 배열 참조를 담고 있는 그 필드 하나다. arr = newArray처럼 참조를 바꾸는 것은 가시성이 보장되지만, arr[3] = 7처럼 원소를 읽고 쓰는 것은 평범한 접근이라 가시성도 재배치 방지도 없다.

같은 함정이 참조 필드 전반에 있다. volatile Config config는 "참조 교체"만 보호할 뿐, 그 객체 내부 필드가 바뀌는 것은 volatile이 관여하지 않는 영역이다. 그래서 이 패턴은 Config가 불변 객체일 때만 성립한다.

원소 단위 보장이 필요하면 AtomicIntegerArray·AtomicReferenceArray를 쓰거나, 배열 전체를 락으로 감싸야 한다.

가시성 버그는 왜 로컬 테스트에서 재현되지 않나요?힌트: JIT는 처음부터 최적화하지 않는다

짧게 도는 코드는 JVM이 아직 인터프리터/저단계 컴파일로 실행하는 구간에 머무른다. 그 상태에서는 대체로 매번 메모리를 읽으므로 volatile이 없어도 정상 동작하는 것처럼 보인다.

같은 코드가 오래 돌아 JIT가 충분히 최적화한 뒤에야 "읽기를 루프 밖으로 끌어올리는" 최적화가 적용되고, 그때부터 안 멈추는 스레드가 나타난다. 게다가 로컬은 코어도 부하도 적어 두 스레드가 실제로 동시에 부딪히는 타이밍이 잘 만들어지지 않는다.

그래서 동시성 버그의 방어선은 테스트가 아니라 코드 리뷰다. "테스트가 통과했으니 괜찮다"가 성립하지 않는 몇 안 되는 영역이라는 점을 말할 수 있으면 좋다.

volatile 변수 두 개로 두 값의 불변식을 지킬 수 있나요?시니어 변별힌트: 각각은 원자적인데 "함께"는 아니다

안 된다. volatile long balance와 volatile List history가 항상 짝이 맞아야 한다고 하자. 각각의 읽기·쓰기는 원자적이지만 "두 값을 함께" 읽거나 쓰는 것은 원자적이지 않다. 다른 스레드가 그 사이를 관측해 잔액은 갱신됐는데 이력은 아직인 상태를 볼 수 있다.

해법은 둘이다. ① 락으로 두 갱신을 하나로 묶는다. 가장 직관적이다.

② 두 값을 한 불변 객체에 담고 그 참조 하나만 volatile로 교체한다. volatile AccountState state를 두고 새 AccountState(balance, history)를 통째로 만들어 대입하면, 참조 대입 한 번이 곧 두 값의 동시 교체가 되어 중간 상태가 원천적으로 존재할 수 없다. 읽는 쪽은 락 없이 읽을 수 있어 읽기가 많은 구조에서 특히 좋다. 다만 갱신이 현재 상태에 의존하면(잔액에서 차감 등) 그 자리는 다시 CAS(AtomicReference.compareAndSet)나 락이 필요하다.

CAS에도 한계가 있나요? ABA 문제가 뭔가요?시니어 변별힌트: CAS가 비교하는 것은 "값"뿐이다

CAS는 "지금 값이 내가 읽었던 값과 같은가"만 본다. 그래서 그 사이에 값이 A → B → A로 돌아왔다면, CAS는 "아무 일도 없었다"고 오판하고 성공한다. 이것이 ABA 문제다.

단조 증가하는 카운터라면 값이 되돌아올 일이 사실상 없어 문제가 되지 않는다. 위험한 것은 노드를 재사용하는 자료구조다. 스택의 top이 A였다가 A가 제거·재삽입되어 다시 A가 되면, 그 사이 뒤쪽 연결이 완전히 달라졌는데도 CAS가 통과해 자료구조가 깨진다.

해법은 값에 버전(스탬프)을 함께 붙여 비교하는 것이다. 자바에서는 AtomicStampedReference(정수 스탬프)나 AtomicMarkableReference(불리언 표시)가 이 역할을 한다.

또 하나의 한계는 경합 폭주다. 여러 스레드가 같은 주소에 몰리면 CAS 실패·재시도가 반복되며 진행은 없이 CPU만 태운다. 이때는 락이 오히려 낫거나, 아예 경합 지점을 나누는 설계로 가야 한다.

갱신이 극단적으로 잦은 카운터라면 AtomicLong도 부족한가요?가산점힌트: 경합 지점을 하나로 두지 않는다

AtomicLong은 모든 스레드가 같은 하나의 주소에 CAS를 건다. 코어가 많고 갱신이 초당 수백만 건이면 그 한 칸이 병목이 되어 CAS 실패가 폭증한다.

LongAdder는 내부에 여러 칸(cell)을 두고 스레드마다 다른 칸에 더한 뒤, 값을 물을 때 sum()으로 합산한다. 경합 자체를 쪼개는 접근이라 갱신 처리량이 크게 올라간다.

대가는 읽기다. sum()은 여러 칸을 훑는 동안에도 갱신이 계속되므로 어느 한 순간의 정확한 스냅샷이 아니다. "쓰기가 압도적으로 많고 읽기는 가끔(모니터링 지표 등)"이면 LongAdder, "매번 정확한 현재 값이 필요하다"면 AtomicLong이다. 자세한 내부는 27-longadder-false-sharing에서 다룬다.

final 필드는 동기화 없이도 안전하게 보이나요?가산점힌트: 불변 객체가 동시성에서 강한 진짜 이유

그렇다. 자바 메모리 모델은 final 필드에 특별한 보장을 준다. 생성자가 정상적으로 끝난 객체의 final 필드는, 그 객체 참조를 받은 다른 스레드에게 동기화 없이도 초기화된 값으로 보인다. 앞의 DCL 사례에서 본 "반쪽짜리 객체"가 final 필드에 대해서는 생기지 않는 것이다.

단, 전제가 있다. 생성자 안에서 this가 새어 나가면 안 된다. 생성 도중에 자신을 리스너로 등록하거나 다른 스레드에 넘기면, 아직 final 필드가 채워지기 전의 자기 자신을 남에게 보여주게 되어 보장이 무너진다.

이것이 불변 객체가 동시성에서 강한 이유다. 모든 필드가 final인 객체는 발행 자체가 안전하고, 상태가 바뀌지 않으니 원자성 문제도 애초에 생기지 않는다. 그래서 이 문서의 결론 중 하나는 "동기화 도구를 고르기 전에, 그 상태를 불변으로 만들 수 있는지부터 본다"가 된다.

한 줄 요약
volatile은 "쓴 값이 다른 스레드에게 반드시 보이고, 그 변수를 기준으로 순서가 뒤집히지 않는다"(가시성 + 재배치 방지)까지만 보장하는 도구라서, 한 스레드가 쓰고 여럿이 읽는 종료 플래그·불변 객체 참조 교체에는 정답이지만, count++처럼 읽고-고치고-쓰는 복합 연산은 두 스레드가 각각 최신 값을 정확히 읽고도 갱신이 유실되는 구조이므로 — 가시성 문제가 아니라 끼어들기 문제이므로 — 그 자리에는 CAS(Atomic*)나 락을 써야 한다.
