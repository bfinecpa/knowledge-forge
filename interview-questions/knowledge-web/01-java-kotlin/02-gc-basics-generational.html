GC 동작 원리와 세대별 수집 — Young/Old를 나누는 이유
GC의 질문은 하나뿐이다 — "GC 루트에서 참조를 따라가 닿을 수 있는가" · 세대 분리는 "대부분 금방 죽는다"는 관찰을 돈으로 바꾼 최적화

면접 질문: "GC가 동작하는 원리를 설명해주세요. Young/Old 영역은 왜 나뉘어 있나요?"

핵심 관전 포인트 — GC는 "GC 루트에서 참조를 따라가 닿을 수 있는가(reachability)"로 살릴 객체를 표시(mark)하고, 닿지 않는 객체를 회수한다. Young/Old를 나누는 이유는 세대 가설 — "대부분의 객체는 만들어지자마자 죽는다" — 때문이다. 전체 힙을 매번 뒤지는 대신, 객체가 태어나는 좁은 Young만 자주·싸게 수집(Minor GC)하고 오래 살아남은 소수만 Old로 승격시키면, 비싼 전체 수집(Full GC)의 빈도를 극적으로 줄일 수 있다.
  • 1
    판정 원리부터 말합니다. GC의 어려운 일은 치우는 것이 아니라 "이제 아무도 안 쓴다"를 증명하는 것입니다. JVM은 그걸 도달 가능성으로 정의합니다 — GC 루트(스레드 스택의 지역변수·파라미터, static 필드, JNI 참조 등 힙 바깥에서 힙 안을 가리키는 출발점)에서 참조를 따라가 닿으면 살리고, 안 닿으면 회수합니다. 참조 카운팅이 아니라 이 방식이라서 순환 참조도 섬째로 회수됩니다.
  • 2
    그다음 세대 분리의 근거를 댑니다. 약한 세대 가설 — 대부분의 객체는 생성 직후 죽고, 오래 산 객체는 계속 오래 삽니다. 그래서 죽을 확률이 높은 놈들만 좁은 Eden에 몰아넣고 거기만 자주 치웁니다. Minor GC는 살아있는 것만 Survivor로 복사하고 죽은 것은 쳐다보지도 않은 채 영역을 통째로 비우므로, 400MB Eden을 치우는 데 실제로 만지는 것은 8MB뿐입니다. 죽은 객체의 비용이 0이라는 게 세대 분리의 전부입니다.
  • 3
    마지막에 실무로 접습니다. 이 구조 때문에 객체를 필요 이상 오래 쥐는 코드가 GC 관점에서 가장 비쌉니다. 생존율이 오르면 Survivor가 넘치고 → 조기 승격 → Old가 임시 객체로 차오르고 → Full GC 빈발 → 응답 스파이크로 이어집니다. 그래서 캐시 크기를 정하는 일이 곧 "Old에 상주시킬 메모리를 얼마로 허락할 것인가"라는 GC 설계 결정이고, 튜닝은 옵션이 아니라 GC 로그로 유형(누수형·조기승격형·설정형)을 가리는 것부터입니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "GC가 동작하는 원리를 설명해주세요. Young/Old 영역은 왜 나뉘어 있나요?"

출제 의도 — GC 로그와 pause 그래프를 읽는 능력의 기초다. "왜 트래픽 피크마다 응답이 200ms 튀는가"의 범인이 GC인지 아닌지를 가려내려면 세대별 수집의 동작을 알아야 한다. 또한 "객체를 오래 들고 있는 코드가 왜 비싼지"를 체감하는 사람만 캐시 크기 같은 결정을 제대로 한다.

질문이 두 문장인 것에 주목한다. 앞 문장("동작 원리")은 판정 알고리즘을 묻고, 뒤 문장("왜 나뉘어 있나")은 그 알고리즘을 싸게 만드는 최적화의 근거를 묻는다. 앞만 답하면 "교과서를 읽은 사람"이고, 뒤 문장에 "세대 가설"과 "죽은 객체의 비용이 0"까지 말하면 "왜 그렇게 설계됐는지 아는 사람"이 된다.

이 질문의 정체 — "GC를 아느냐"가 아니라 "GC가 무엇을 아끼려고 그런 구조가 됐는지 아느냐"다.
아끼려는 것은 딱 하나, Stop-The-World 시간이다. 도달 가능성 판정도, Young/Old 분리도, 복사 알고리즘도 전부 이 하나를 향한 수단이다.

이렇게 답하면 반쪽이다

  • "참조가 없으면 회수합니다" — 방향이 반대다. GC는 "참조가 없음"을 세지 않고 "루트에서 닿는가"를 확인한다. 이 구분을 못 하면 순환 참조 질문에서 그대로 막힌다.
  • "Young은 자주, Old는 가끔 치웁니다"에서 멈춤 — 현상만 말했다. 면접관이 원하는 건 "왜 그래도 되는가(세대 가설)"와 "왜 그게 싼가(죽은 객체 비용 0)"다.
  • "Minor GC는 STW가 없어서 빠릅니다" — 사실이 아니다. Minor GC도 STW이고, 짧은 이유는 복사량이 생존 객체에만 비례하기 때문이다.
  • "Survivor가 2개인 건 번갈아 쓰려고요" — 맞지만 이유가 빠졌다. 복사 알고리즘이 "빈 공간 하나"를 전제로 하기 때문이고, 대가는 한 칸을 늘 놀리는 것이다.
  • "Full GC가 잦으면 힙을 늘립니다" — 가장 위험한 답. 누수라면 터지는 시점만 미루고 STW는 오히려 길어진다.
  • "메모리 정리는 System.gc()로" — 요청일 뿐 보장이 아니고, 돌면 가장 비싼 전체 수집이다.

이 문서가 채워 주는 것

  • 왜 참조 카운팅이 아니라 도달 가능성인가 — 순환 참조가 실무에 널려 있다는 구체적 근거(양방향 JPA 연관·트리·콜백).
  • GC 루트의 공통 성질 한 문장 — 목록 암기 대신 "힙 바깥에서 힙 안을 가리키는 출발점".
  • Mark 비용이 살아있는 객체 수에 비례한다는 사실에서 세대 분리의 이득 전부가 파생되는 인과.
  • 400MB Eden에서 실제로 만지는 것은 8MB라는 숫자로 된 설명과 Full GC와의 자릿수 비교.
  • Eden → Survivor → Old 이동을 t0~t6 타임라인으로 따라가며 "안 하는 일"까지 확인.
  • 조기 승격의 사슬 — 코드 한 줄에서 응답 스파이크까지 이어지는 6단계.
  • 카드 테이블·쓰기 배리어 — 세대 분리가 공짜가 아니라 상시 비용을 내고 산 최적화라는 시니어 포인트.

이 문서를 관통하는 한 문장

GC의 모든 설계는 "STW를 짧게, 그리고 예측 가능하게" 하나를 향한다

도달 가능성 판정도, Young/Old 분리도, 복사 알고리즘도, 카드 테이블도 전부 여기서 파생된다. "GC를 덜 돌리기"는 목표가 아니다 — 자주 돌아도 짧으면 좋은 상태이고, 드물어도 길면 나쁜 상태다. 이 감각이 3절 이후의 진단을 전부 지배한다.

0-1. 답변 흐름 한 장 — 이 순서를 지키면 질문이 끝난다

1. 진짜 어려운 문제는 "치우기"가 아니라 "판정"이다

C에서는 malloc으로 받은 메모리를 개발자가 free로 직접 돌려준다. Java에는 그런 게 없다. new만 있고 delete는 없다. 그럼 누가 언제 메모리를 돌려주는가 — 그 일을 하는 것이 GC(Garbage Collector, 쓰레기 수집기)다.

여기서 GC의 진짜 문제가 무엇인지를 정확히 짚어야 뒤가 풀린다. 메모리를 반환하는 것 자체는 어렵지 않다. 어려운 것은 "이 객체는 이제 아무도 안 쓴다"를 어떻게 확신하느냐다. 하나라도 잘못 판정해서 아직 쓰는 객체를 회수해 버리면 프로그램은 즉시 죽는다. 그래서 GC는 반드시 "확실히 안 쓴다"고 증명할 수 있는 객체만 회수해야 한다.

그 증명을 어떻게 하는가. 변수에 담기는 것은 객체가 아니라 객체가 있는 힙 주소값, 즉 참조다. 그러니 "아무도 안 쓴다"는 것은 "그 객체를 가리키는 참조를 따라 도달할 방법이 하나도 남지 않았다"로 번역할 수 있다. 아무도 찾아갈 수 없는 집은, 그 집에 뭐가 들어 있든 프로그램에 아무 영향을 줄 수 없기 때문이다.

이 번역 하나가 GC 전체를 지탱한다

"아무도 안 쓴다"  →  "참조를 따라 도달할 방법이 하나도 없다"

이 번역이 왜 정당한지를 한 문장으로 말할 수 있어야 한다 — "프로그램이 객체에 접근하는 유일한 통로가 참조이므로, 참조로 닿을 수 없다면 그 객체는 프로그램에 어떤 영향도 줄 수 없다." GC는 "안 쓰는 것"이 아니라 "못 닿는 것"을 회수한다는 문장도 여기서 나온다.

2. 도달 가능성 — GC의 유일한 질문

GC의 질문은 하나뿐이다. "이 객체에 아직 닿을 수 있는가?"

도달 가능성(reachability)이란 말 그대로 "출발점에서 참조를 따라가면 그 객체에 도달(reach)할 수 있는가"를 뜻한다. 도달할 수 있으면 살아있는 것으로 보고, 도달할 수 없으면 쓰레기로 판정한다.

2-1. 비유 — 지하철 노선도

지하철 노선도를 떠올리면 된다. 우리가 서 있는 역(출발점)에서 선로를 따라가 닿을 수 있는 역은 전부 "살아있는 역"이다. 어느 선로와도 이어져 있지 않아 그 안에 열차가 몇 대 있든 아무도 갈 수 없는 고립된 역이 있다면, 그 역과 그 안의 열차는 전부 없앨 수 있다.

비유에서 꼭 가져올 문장 "역 안에 열차가 서로 오가고 있는지 없는지는 판정과 무관하다 — 바깥에서 들어갈 방법이 없다는 것만이 기준이다." 이 문장을 그대로 말할 수 있으면 순환 참조 질문(4절)의 답은 이미 끝난 것이다.

3. GC 루트 — 출발점의 정체와 누수의 원리

그렇다면 "출발점"은 무엇인가. 이것이 GC 루트(GC Root)다. 프로그램이 지금 이 순간 확실히 붙잡고 있다고 말할 수 있는, 참조 그래프 탐색의 시작점들을 가리킨다. 나무의 뿌리(root)에서 가지를 따라 뻗어나가듯 여기서부터 참조를 따라간다고 해서 루트다.

스레드 스택의 지역변수·파라미터
지금 실행 중인 코드가 손에 들고 있는 것들. 프레임이 걷히면 함께 사라진다.
static 필드
클래스가 로딩된 동안 계속 살아 있으므로 영구적인 출발점이 된다. 누수의 1순위 경로.
JNI(네이티브) 참조
네이티브 코드가 쥔 참조. JVM 힙 바깥의 세계에서 안을 가리킨다.
실행 중인 스레드 · 모니터
살아있는 스레드 객체 자체, 동기화 모니터를 쥔 객체 등.

GC 루트 = 힙 바깥에서 힙 안을 가리키는, 프로그램이 지금 확실히 붙잡고 있는 출발점

힙 안의 객체가 다른 객체를 가리키는 것은 루트가 아니다 — 그 객체 자신이 살아 있다는 보장이 없기 때문이다. 이 조건 하나로 "무엇이 루트인가"를 매번 재구성할 수 있다.

3-1. 코드로 보는 루트의 생성과 소멸

void handle() {
    Order order = new Order();   // 스택의 order가 루트다.
                                 // 루트 -> Order 경로가 있으므로 살아있음.
}                                // 리턴하면 프레임이 걷히며 order가 사라진다.
                                 // 루트에서 Order로 가는 경로가 끊김 -> 회수 후보.

여기서 실무적으로 중요한 사실 두 가지가 나온다.

① order = null은 굳이 필요 없다

루트에서 닿는 경로가 끊기는 순간 이미 회수 후보다. 메서드 끝에서 지역변수를 null로 밀어 넣는 코드는 대부분 의미가 없다.

예외 — 아주 긴 메서드 안에서 거대한 객체를 다 쓰고 난 뒤, 메서드가 끝나기까지 한참 남았을 때 정도다.

② static 컬렉션에 넣은 객체는 절대 회수되지 않는다

static 필드가 루트이므로 루트에서 영원히 닿는다. 이것이 Java 메모리 누수의 가장 전형적인 형태다.

Java에는 "누수"가 없다고들 하지만, 정확히는 "실수로 참조를 놓치는 누수는 없고, 실수로 참조를 붙잡는 누수는 있다"가 맞다.

4. 왜 참조 카운팅이 아닌가 — 순환 참조 가산점

도달 가능성 말고 다른 방법도 있다. 참조 카운팅(reference counting)은 객체마다 "나를 가리키는 참조가 몇 개인가"를 세는 카운터를 두고, 누군가 나를 가리키면 +1, 참조를 끊으면 −1 하다가 0이 되는 순간 즉시 회수하는 방식이다. 구현이 단순하고, 쓰레기가 되는 즉시 회수되니 지연도 없다.

그런데 이 방식에는 원리적으로 못 푸는 구멍이 있다. 서로가 서로를 참조하는 순환 구조다. 코드로 보면 한눈에 들어온다.

class Node {
    String name;
    Node partner;          // 다른 Node를 가리키는 참조 필드
    Node(String name) { this.name = name; }
}

void makeCycle() {
    Node a = new Node("a");
    Node b = new Node("b");

    a.partner = b;         // a 객체가 b 객체를 가리킨다  -> b의 참조 카운트 = 2 (지역변수 b + a.partner)
    b.partner = a;         // b 객체가 a 객체를 가리킨다  -> a의 참조 카운트 = 2 (지역변수 a + b.partner)
}

//
// [참조 카운팅이라면]
//   a의 카운트: 2 -> 1 (b.partner가 여전히 가리킴)

// [도달 가능성이라면]
//   루트(스택)에서 a, b로 들어가는 경로가 하나도 없다.

5. 회수의 기본 동작 — Mark · Sweep · Compact · Copy

살릴 것과 버릴 것을 가르고 나면 실제로 공간을 되찾아야 한다. 어떤 GC 알고리즘이든 이 세(넷) 동작의 조합이다.

Mark (표시)
루트에서 그래프를 순회하며 도달한 객체에 "살아있음" 표시. 비용은 살아있는 객체 수에 비례한다 — 죽은 객체는 애초에 방문하지 않으므로.
Sweep (쓸어내기)
표시되지 않은 자리를 "빈 공간"으로 등록. 문제는 빈틈(단편화) — 총 빈 공간 100MB인데 연속 자리는 2MB뿐이면 10MB 배열 하나에 OOM이 날 수 있다.
Compact (압축)
살아있는 객체를 한쪽 끝으로 밀어 모아 빈 공간을 하나의 연속 덩어리로. 단편화는 없애지만 이동 + 모든 참조 주소 수정이 비싸다.
Copy (복사)
Compact의 사촌. 살아있는 객체를 다른 영역으로 옮겨 담고 원래 영역을 통째로 비운다. 옮기며 자연히 몰리므로 단편화가 없다. Young에서 극도로 저렴한 이유는 10절에서 숫자로 본다.

이 절에서 인출할 것 — 비용의 위치

Mark 비용 ∝ 살아있는 객체 수  /  Sweep 비용 ∝ 빈틈 관리  /  Compact·Copy 비용 ∝ 옮기는 바이트 수

세 비용이 전부 "살아있는 것"에만 붙어 있다는 점이 핵심이다. 죽은 객체는 어느 항목에도 등장하지 않는다. 이 사실 하나에서 "거의 다 죽은 영역만 따로 모아 두면 수집이 거의 공짜"라는 세대 분리의 아이디어가 그대로 나온다.

6. Stop-The-World — GC가 응답시간 스파이크의 범인인 이유

이 작업들의 상당 부분은 작업 도중 객체 그래프가 변하면 안 된다. mark 중에 애플리케이션 스레드가 참조를 바꿔버리면 이미 지나간 객체가 새로 살아나거나, 살아있는 객체를 놓칠 수 있기 때문이다. compact 중이라면 더 심각하다 — 객체를 옮기는 중에 누가 옛 주소로 접근하면 그대로 깨진다.

그래서 GC는 애플리케이션 스레드를 전부 멈춰 세우고 자기 일을 하는 구간을 갖는다. 이 구간을 Stop-The-World(STW)라고 부른다. 그 순간 애플리케이션의 시간이 완전히 정지하고, 세상이 멈춘다고 해서 붙은 이름이다.

오해 정정 — 문제는 CPU 사용이 아니다 GC가 CPU를 쓰는 것 자체는 별로 문제가 아니다. 문제는 그 사이 아무도 일을 못 한다는 것이다. 그래서 "GC CPU 사용률이 5%밖에 안 되는데 왜 문제냐"는 반문은 지표를 잘못 고른 것이다 — 봐야 할 것은 사용률이 아니라 정지 시간의 분포다.

GC 튜닝의 목표를 한 문장으로

"GC를 덜 돌리기"가 아니라 "STW 시간을 짧게, 그리고 예측 가능하게 만들기"

컬렉터가 세대를 나누고(7절 이후), 동시(concurrent) 수행을 늘려온 역사가 전부 이 목표를 향한 것이다. 자주 돌아도 짧으면 건강하고, 드물어도 길면 병이라는 감각이 여기서 나온다.

7. 세대 가설 — 수명 분포는 양극단에 몰려 있다

약한 세대 가설(weak generational hypothesis)은 실측에서 나온 경험칙이다. 내용은 두 문장이다.

약한 세대 가설 — 두 문장

① 대부분의 객체는 생성 직후 금방 죽는다
② 오래 살아남은 객체는 앞으로도 계속 오래 산다

"세대(generation)"라는 이름은 객체를 태어난 시기별로 묶어 다룬다는 뜻에서 왔다. ①이 Young을 자주 치우는 근거이고, ②가 Old를 아껴 치우는 근거다. 두 문장이 각각 다른 결정을 정당화한다는 점을 짚으면 이해한 답이 된다.

웹 서버로 생각하면 자명하다. 요청 하나를 처리하며 만드는 것들을 떠올려 보자.

왜 "골짜기"가 중요한가 만약 수명이 고르게 퍼져 있었다면 Young을 아무리 자주 치워도 생존율이 높아 복사 비용이 커지고, 승격되는 양도 많아 Old가 빨리 찼을 것이다. 양극단 분포라는 사실이 "Young은 거의 다 죽어 있다"를 보장하고, 그 보장 위에서만 10절의 "만지는 것은 2%뿐"이 성립한다.

8. 힙의 물리적 구획과 용어 정의

이 관찰을 어떻게 이용하는가. 죽을 확률이 높은 놈들만 좁은 곳에 몰아넣고 거기만 자주 치운다. 그래서 힙을 이렇게 나눈다.

8-1. 용어를 하나씩 못박기

Eden
새 객체가 태어나는 곳. new로 만든 객체는 예외적인 경우를 빼면 전부 여기 놓인다. 모든 것이 시작되는 동산이라는 뜻의 이름이다.
Survivor
이름 그대로 Minor GC에서 살아남은 객체가 잠시 머무는 대기실. S0, S1 두 개가 있고 항상 하나는 비어 있다(이유는 11절).
Minor GC
Young 영역만 대상으로 하는 수집. "작은(minor)" 수집이라는 뜻이고, Young GC라고도 부른다.
승격(promotion)
Young에서 여러 번 살아남은 객체를 Old로 옮기는 것. "이 객체는 요절하지 않는 부류인 것 같으니 이제 자주 검사하지 않는 곳으로 보내자"는 판단이다. 승진과 같은 단어를 쓰는 이유가 이것이다.
나이(age)
객체가 Minor GC를 몇 번 살아남았는지를 세는 카운터. 객체 헤더에 몇 비트로 기록되고, Minor GC를 한 번 견딜 때마다 1씩 오른다.
Old
승격된 객체들이 사는 곳. Major GC / Full GC는 Old까지 포함해 수집하는 것을 가리키며, 훨씬 비싸다.

나이 임계치 — 숫자보다 "동적"이라는 사실

HotSpot 기본 상한은 15 — 그러나 실제 임계치는 고정이 아니다

Survivor가 넘칠 것 같으면 JVM이 임계치를 그보다 낮춰 더 일찍 승격시키기도 한다. 그래서 "평소보다 어린 나이에 승격이 일어난다" = "Survivor에 압력이 걸리고 있다"로 읽어야 한다. 숫자 15만 외우면 이 신호를 못 읽는다.

9. Eden → Survivor → Old 이동을 타임라인으로 보기

말로만 들으면 이동 경로가 잘 안 그려진다. 시간 순으로 따라가 보자. 알파벳 하나가 객체 하나이고, 뒤의 숫자는 나이다.

타임라인의 결론

Minor GC는 죽은 객체를 처리하지 않는다

살아있는 것만 들어내고 나면 나머지는 어차피 통째로 버릴 것이므로 개별적으로 손댈 이유가 없다. "쓰레기를 치운다"는 이름 때문에 죽은 객체를 하나하나 지운다고 오해하기 쉬운데, 정반대다 — 살아있는 것만 건드리고 나머지는 존재조차 확인하지 않는다.

여기서 자연스럽게 나오는 의문 "Eden을 통째로 비운다면, Old에 있는 객체가 Eden의 객체를 가리키고 있었다면 어떻게 되는가?" — 정확한 질문이고, 세대 분리의 구멍이다. 답은 14절(카드 테이블)에서 다룬다.

10. Minor GC가 싼 진짜 이유 — 복사 방식을 숫자로 풀어 보기

"Minor GC는 싸다"는 말을 숫자로 확인하자.

전제 — 아래 수치는 가정한 예시다 환경마다 다르지만 자릿수의 차이가 어디서 오는지는 그대로다. 면접에서도 "가정치를 놓고 계산해 보면"이라고 전제를 밝히고 말하면 된다.

Minor GC — 전제

  • Eden 크기: 400MB
  • 객체 평균 크기: 100 바이트
  • Young 생존율: 2% (Minor GC 시점에 아직 살아있는 비율)

Full GC — 전제

  • Old 크기: 3GB
  • 객체 평균 크기: 동일하게 100B
  • Old 생존율: 90% (원래 오래 사는 것들만 있으므로)
Minor GC 한 번의 작업량 — 단계별 계산
  1. Eden에 들어간 객체 수 = 400MB ÷ 100B = 400만 개
  2. 그중 살아남는 객체 수 = 400만 × 2% = 8만 개
  3. 죽은 객체 수 = 400만 − 8만 = 392만 개
  4. Mark 비용 = 살아있는 8만 개만 순회. 392만 개는 애초에 방문조차 하지 않는다.
  5. Copy 비용 = 8만 개 × 100B = 8MB를 Survivor로 옮긴다.
  6. 죽은 392만 개를 처리하는 비용 = 0. Eden의 할당 포인터를 맨 앞으로 되돌리는 것으로 끝난다.
400MB짜리 영역을 치우는데 실제로 만지는 것은 8MB, 400만 개 중 8만 개 — 나머지 98%는 존재조차 확인하지 않는다
Full GC 한 번의 작업량 — 같은 방식으로
  1. Old의 살아있는 객체 수 = 3GB × 90% ÷ 100B = 2,700만 개
  2. Mark 비용 = 2,700만 개 전부 순회
  3. Compact 비용 = 2.7GB를 옮기고, 옮긴 객체들을 가리키던 참조를 전부 고쳐 씀

10-1. 덤으로 따라오는 이점 — 단편화가 없다

여기에 하나 더 붙는 이점이 있다. 복사 방식은 살아있는 객체를 새 영역에 차곡차곡 이어 붙이며 옮기므로 결과가 자동으로 연속 공간이 된다. 즉 단편화가 원천적으로 생기지 않는다. Sweep 방식처럼 빈틈을 관리할 자료구조도 필요 없다.

이 절을 한 문장으로 압축하면

"죽은 객체의 비용이 0"이라는 말의 정확한 의미 = 죽은 객체는 방문·이동·정리 어디에도 등장하지 않는다

그래서 Young 수집의 비용은 "영역 크기"가 아니라 "그 순간 살아있던 객체의 양"으로 결정된다. Eden을 두 배로 키워도 생존율이 그대로면 한 번의 비용은 크게 안 변한다는 따름 정리가 여기서 나온다 — 대신 한 번에 훑을 절대량은 늘어난다.

11. Survivor가 왜 2개인가

복사 방식을 쓰기로 한 이상 복사해 넣을 빈 공간이 반드시 있어야 한다. 이것이 Survivor가 두 개인 이유다.

항상 한쪽(예: S1)을 완전히 비워 두고, Minor GC 때 Eden + 사용 중인 Survivor(S0)의 생존자를 전부 빈 쪽(S1)으로 몰아 복사한다. 복사가 끝나면 Eden과 S0을 통째로 비우고, 다음 회차에는 S1이 "사용 중", S0이 "빈 쪽"이 된다. 역할이 매번 교대된다.

Survivor가 하나뿐이라면

  • 새 생존자를 넣을 자리를 그 안에서 골라야 한다.
  • 죽은 객체가 남긴 빈틈을 관리해야 한다.
  • 결국 단편화 처리가 필요해진다.
  • 즉 복사 방식의 이점이 통째로 사라진다.

Survivor가 담당하는 또 하나의 역할

"이놈이 진짜 오래 살 놈인지" 몇 번 더 지켜보는 관찰 기간이기도 하다.

이 관찰 없이 Eden에서 한 번 살아남았다고 바로 Old로 보내면, 잠깐 살다 죽을 객체까지 Old를 채우게 된다. 12절의 조기 승격이 정확히 이 관찰 기간이 생략되는 사고다.

11-1. 정리 — 분리가 만드는 이득

세대 분리의 목표는 단 하나

Full GC 빈도의 최소화

세대 분리는 결국 "싸게 자주 치울 수 있는 곳과 비싸서 아껴 치워야 하는 곳을 물리적으로 갈라놓은 것"이다. 그러면 이런 질문이 자연스럽게 따라온다 — "그럼 Full GC를 늘리는 코드는 어떤 코드인가?" 답은 다음 절이다.

12. 실무 — "객체를 오래 들고 있는 코드"가 비싼 이유

이 구조를 알면, 같은 메모리양을 쓰더라도 객체의 수명 패턴이 GC 비용을 좌우한다는 것이 보인다. 100MB를 쓰는 코드 두 개가 있을 때, 요청마다 만들고 버리는 100MB와 계속 붙잡고 있는 100MB는 GC 입장에서 전혀 다른 부담이다.

12-1. 사례: 트래픽 피크마다 응답이 200ms 튀는 서비스

1
트래픽이 늘면 요청당 임시 객체 생성 속도가 올라가 Eden이 빨리 차고 Minor GC가 잦아진다.
정상
2
여기까지는 문제가 아니다 — 10절에서 봤듯 Minor GC는 싸므로, 자주 돌아도 각각이 짧으면 괜찮다.
정상
3
문제는 그다음. 요청 처리 중 객체를 필요 이상 오래 들고 있으면 Minor GC 시점에 그 객체들이 아직 살아 있다. 생존율 2%를 전제로 잡았던 계산이 무너진다.
전제 파손
4
Survivor는 크지 않다. 복사해야 할 생존자가 Survivor 용량을 넘기면 JVM은 넘치는 분을 나이가 어린데도 곧바로 Old로 보낸다 = 조기 승격(premature promotion).
사고
5
"오래 살 놈인지 지켜보는" 관찰 기간을 건너뛰고, 곧 죽을 임시 객체가 Old로 들어가 버린다. Old가 이런 임시 객체들로 차오른다.
오염
6
결국 Full GC가 돈다. 10절의 계산대로 Minor GC보다 자릿수가 다르게 비싸고, 수백 ms의 STW가 응답시간 그래프에 그대로 스파이크로 찍힌다.
스파이크

인과를 한 줄로 이으면

객체를 오래 쥠→ Minor GC 시점 생존율 상승→ Survivor 넘침→ 조기 승격→ Old가 임시 객체로 차오름→ Full GC 빈발→ 응답 스파이크

"피크마다 200ms 튀는" 그래프의 전형적인 범인이 이 사슬이다. 그리고 이 사슬의 시작점이 코드이지 GC 옵션이 아니라는 점이 중요하다.

12-2. before / after — 무경계 캐시가 Old를 채우는 코드

가장 흔한 형태는 상한 없는 캐시다.

Before 크기 제한 없는 static 캐시 — 시한폭탄
public class ProductCache {
    // static 필드는 GC 루트다(3절).
    // 여기 담긴 것은 프로세스가 사는 내내 루트에서 닿는다.
    private static final Map<Long, Product> CACHE
            = new HashMap<>();

    public Product get(Long id) {
        return CACHE.computeIfAbsent(id, this::loadFromDb);
        // 한 번 들어온 Product는 참조가 영원히 끊기지
        // 않는다 -> 절대 회수 불가.
        // Minor GC를 계속 살아남아 전부 Old로 승격되고,
        // Old를 잠식한다.
        // 결과: Full GC 빈발 -> STW 누적
        //      -> 최후에는 OutOfMemoryError: Java heap space.
        // 상품 수가 늘어나는 만큼 힙 사용량이 선형으로
        // 늘어나는데, 상한이 없으므로 "언제 터질지"가
        // 데이터 증가 속도에 달려 있다 — 시한폭탄에 가깝다.
    }
}
After 크기 상한 + 퇴출 정책 (예: Caffeine)
public class ProductCache {
    private final Cache<Long, Product> cache =
        Caffeine.newBuilder()
            .maximumSize(10_000)
            // 상한을 두면 Old 점유량의 최댓값을 미리
            // 계산할 수 있다. 항목당 2KB라면 최대 20MB —
            // 힙 예산에 넣을 수 있는 숫자가 된다.
            .expireAfterWrite(Duration.ofMinutes(10))
            // 수명을 명시하면 만료된 항목의 참조가 실제로
            // 끊긴다. 참조가 끊겨야 비로소 GC의
            // 회수 대상이 된다(2절).
            .build();

    public Product get(Long id) {
        return cache.get(id, this::loadFromDb);
    }
}
after가 나은 이유를 "메모리를 덜 쓴다"로 정리하면 절반만 맞다 진짜 차이는 점유량의 상한이 예측 가능해졌다는 것이다. 상한이 있으면 Old에 상주할 양을 힙 크기 대비 몇 %로 계획할 수 있고, 그래야 Full GC 주기를 설계할 수 있다.

이 절의 인출 문장

캐시 크기를 정하는 일 = "Old에 상주시킬 메모리를 얼마로 허락할 것인가"라는 GC 설계 결정

이것을 아는 사람과 그냥 Map에 쌓는 사람의 차이가 여기서 갈린다. 면접에서 이 문장을 쓰면 "GC를 아는 사람"에서 "GC를 근거로 설계 결정을 하는 사람"으로 올라간다.

13. GC 로그를 읽는 첫 기준 — 세 신호

Minor GC가 잦은 것 자체는 문제가 아니다. 각각이 짧고(수 ms~수십 ms) 회수량이 크면 건강한 상태다. 오히려 "Minor GC가 많네요, 줄여야겠어요"라며 Young을 무작정 키우면, 한 번의 Minor GC가 훑을 양이 늘어 개별 pause가 길어질 수 있다.

경계해야 할 신호는 셋이다.

① Survivor 넘침과 조기 승격의 흔적
  • GC 로그에서 Minor GC 직후 Old 사용량이 눈에 띄게 뛰었다면 승격이 일어난 것이다.
  • 매 회차마다 이런 패턴이면 12절의 사슬이 돌고 있다.
② Full GC 빈도 증가
  • Full GC는 드물어야 정상이다.
  • 빈도가 오르는 추세라면 Old가 차는 속도가 빨라졌다는 뜻이다.
③ Full GC 후에도 Old 바닥이 상승
  • 가장 명확한 누수 신호.
  • 가장 비싼 수집을 다 하고도 안 치워지는 잔량이 회차마다 늘고 있다면, 참조가 끊기지 않는 코드가 있다.

세 신호의 결정적 차이

①·②는 튜닝으로도 완화되지만 ③은 코드를 고치기 전에는 절대 안 잡힌다

그래서 진단의 첫 갈림길은 항상 ③의 판별이다. ③이면 힙을 키우는 모든 조치는 폭발을 미루면서 폭발의 크기를 키우는 것이다 — 힙이 커진 만큼 그 한 번의 Full GC STW가 길어지기 때문이다.

14. 카드 테이블 — 세대 분리가 치르는 상시 비용 시니어 변별

9절 끝에서 남겨 둔 질문을 이제 푼다. "Old의 객체가 Young의 객체를 참조하고 있으면, Young만 수집하는 Minor GC는 그걸 어떻게 알죠?"

// Old에 있는 장수 객체(캐시)가, 방금 Eden에 만들어진 객체를 참조한다
oldCache.put(key, new Product(...));   // Product는 Eden에 있고, 참조는 Old에서 온다

이때 Minor GC가 Young만 보고 판정하면, 이 Product는 "루트에서 닿지 않는다"고 오판돼 회수된다. 그러면 oldCache가 들고 있던 참조는 이미 없어진 객체를 가리키게 되고 프로그램이 깨진다.

그러니 Minor GC는 "Old에서 Young으로 들어오는 참조"도 루트처럼 취급해야 한다. 문제는 그걸 찾겠다고 Old 전체를 스캔하면 세대 분리의 의미가 통째로 사라진다는 것이다 — 싸게 하려고 나눴는데 매번 Old를 다 훑으면 남는 게 없다.

이 질문의 진짜 관전 포인트

"공짜 점심은 없다" — GC 때 아낀 비용은 평소의 쓰기 배리어로 미리 지불된 것이다

이 거래 구조를 말할 수 있으면 "GC 옵션을 아는 사람"이 아니라 "GC 설계를 아는 사람"으로 보인다. 덧붙일 수 있는 한 문장 — "그래서 컬렉터를 바꾼다는 것은 GC 시간만 바꾸는 게 아니라 애플리케이션의 상시 비용 구조까지 바꾸는 일"이다.

15-1. 전체 한 장 — 판정 원리에서 실무 사슬까지

15-2. 인출 카드 — 눈으로 읽지 말고 답부터 말해 본다

Q. GC의 유일한 질문은?
"GC 루트에서 참조를 따라가 이 객체에 닿을 수 있는가." 닿으면 생존, 못 닿으면 쓰레기. 객체끼리 서로 가리키는지는 무관하다.
Q. GC 루트의 공통 성질은?
힙 바깥에서 힙 안을 가리키는, 프로그램이 지금 확실히 붙잡고 있는 출발점. 목록보다 이 한 문장으로 답한다.
Q. 참조 카운팅의 구멍은?
순환 참조. 서로가 서로를 살려 카운트가 0이 안 된다. 양방향 JPA 연관·트리·콜백이 전부 순환이라 실무에서 흔한 구조다.
Q. 도달 가능성이 치르는 대가는?
즉시성 상실(GC가 돌 때 한꺼번에 판정)과 그래프 순회 비용. 이 둘을 줄이려는 것이 세대 분리다.
Q. Mark 비용은 무엇에 비례?
살아있는 객체 수. 죽은 객체는 애초에 방문하지 않는다. 그래서 거의 다 죽은 Young은 싸고, 거의 다 산 Old는 비싸다.
Q. STW가 필요한 이유는?
작업 도중 객체 그래프가 변하면 안 되기 때문. mark 중 참조가 바뀌면 오판하고, compact 중 옛 주소로 접근하면 깨진다.
Q. 세대 가설 두 문장은?
대부분의 객체는 생성 직후 죽는다. 오래 살아남은 객체는 앞으로도 오래 산다. 수명 분포가 양극단에 몰려 있다.
Q. Minor GC가 싼 진짜 이유는?
죽은 객체를 처리하지 않기 때문. 산 것만 복사하고 할당 포인터를 앞으로 되돌려 영역 전체를 빈 것으로 선언한다.
Q. Survivor가 2개인 이유는?
복사할 빈 공간이 반드시 하나 있어야 하기 때문. 대가는 Survivor 하나만큼을 늘 놀리는 것이다.
Q. 승격 판단 기준은?
나이(age) — Minor GC를 몇 번 견뎠는지. HotSpot 기본 상한 15지만 Survivor가 넘칠 것 같으면 JVM이 임계치를 낮춘다.
Q. 조기 승격이란?
생존자가 Survivor 용량을 넘겨 나이가 어린데도 곧바로 Old로 보내지는 것. "지켜보는 관찰 기간"이 통째로 생략된다.
Q. 가장 명확한 누수 신호는?
Full GC 후에도 Old 사용량의 바닥이 계속 상승. 가장 비싼 수집을 하고도 안 줄면 코드를 고치기 전엔 안 잡힌다.
Q. Old→Young 참조는 어떻게 아나?
remembered set(HotSpot 구현: 카드 테이블). 쓰기 배리어가 참조 대입 때 카드를 dirty로 찍고, Minor GC는 dirty 카드만 훑는다.
Q. 세대 분리의 진짜 가격은?
모든 참조 대입마다 쓰기 배리어를 실행하는 상시 비용. 평소 조금씩 내고 GC 때 크게 아끼는 거래다.
Q. Java에 메모리 누수가 있나?
"실수로 참조를 놓치는 누수는 없고, 실수로 참조를 붙잡는 누수는 있다." static 컬렉션·미해제 ThreadLocal이 단골.
Q. 캐시 크기를 정하는 일의 정체는?
"Old에 상주시킬 메모리를 얼마로 허락할 것인가"라는 GC 설계 결정. 상한이 있어야 Full GC 주기를 설계할 수 있다.
40초 답변 스크립트 — 이 순서로 말한다 ① "GC의 어려운 일은 치우는 게 아니라 '이제 아무도 안 쓴다'를 증명하는 것입니다" → ② "그래서 GC 루트에서의 도달 가능성으로 판정합니다. 루트는 힙 바깥에서 힙 안을 가리키는 출발점이고요. 참조 카운팅이 아니라서 순환 참조도 섬째로 회수됩니다" → ③ "판정 뒤에는 mark·sweep·compact 또는 copy가 오고, 그래프가 고정돼야 하므로 STW가 생깁니다 — 이게 응답 스파이크의 정체죠" → ④ "Young/Old를 나누는 건 세대 가설 때문입니다. 대부분 금방 죽으니 좁은 Eden만 자주 치우고, 살아남은 것만 복사합니다" → ⑤ "그래서 죽은 객체의 비용이 0입니다. 400MB Eden에서 실제로 만지는 건 생존 8MB뿐이라, Full GC와 자릿수가 다릅니다" → ⑥ "역으로 객체를 오래 쥐면 이 전제가 깨져 조기 승격 → Full GC → 스파이크로 갑니다. 그래서 캐시 상한을 두는 게 곧 GC 설계입니다." ⑥번까지 스스로 가는 것이 이 답변의 핵심이다.

15-3. 꼬리질문 셀프 테스트 — 답을 소리 내어 말한 뒤 펼친다

GC 루트에는 구체적으로 뭐가 있나요?힌트: 목록을 외우기보다 "공통 성질" 한 문장으로 답한다 핵심

스레드 스택의 지역변수·파라미터가 쥔 참조, static 필드, JNI 전역/지역 참조, 살아있는 스레드 객체 등이다. 여기에 동기화 모니터를 쥔 객체도 포함된다.

다만 목록을 나열하는 것보다 공통 성질로 답하는 편이 낫다 — "힙 바깥에서 힙 안을 가리키는, 프로그램이 지금 확실히 붙잡고 있는 출발점"이다. 실행 중인 코드가 손에 쥐고 있거나(스택), 클래스가 로딩된 동안 영구히 쥐고 있는(static) 것들이 여기 해당한다.

힙 안의 객체가 다른 객체를 가리키는 것은 루트가 아니다 — 그 객체 자신이 살아 있다는 보장이 없기 때문이다

그래서 static 컬렉션에 쌓기만 하는 코드가 누수의 단골이 된다. 루트에 직접 매달려 있으므로 아무리 GC를 돌려도 닿지 않을 방법이 없다. 같은 이유로 ThreadLocal에 담아 두고 remove()를 안 하는 코드도 위험하다 — 스레드 객체가 살아있는 동안 루트에서 닿기 때문인데, 스레드풀에서는 스레드가 재사용되며 사실상 영구히 산다.

정리 문장 — "루트는 '지금 확실히 쓰이고 있다'고 말할 수 있는 힙 바깥의 출발점입니다. 그래서 루트에 직접 매달리는 static과 ThreadLocal이 누수의 대표 경로가 됩니다."

Survivor 영역은 왜 하나가 아니라 2개인가요?힌트: 알고리즘이 무엇을 전제로 하는지부터 말한다 핵심

복사(copy) 방식을 쓰기 때문이다. 복사해 넣을 빈 공간이 반드시 하나 있어야 한다.

항상 한쪽을 완전히 비워 두고, Minor GC 때 Eden + 사용 중 Survivor의 생존자를 빈 쪽으로 몰아 복사한 뒤 역할을 교대한다. 이렇게 하면 생존자가 항상 연속된 공간에 몰려 단편화가 원천적으로 없고, sweep 없이 원본 영역을 통째로 비울 수 있다.

Survivor가 하나라면

  • 새 생존자를 넣을 자리를 그 안에서 골라야 한다.
  • 죽은 객체가 남긴 빈틈을 관리하는 자료구조가 필요하다.
  • 결국 단편화 처리가 붙는다 — 복사 방식의 이점이 통째로 사라진다.

둘이라서 얻는 것

  • 단편화 0 — 차곡차곡 이어 붙이며 옮기므로.
  • 정리 비용 0 — 원본은 통째로 비운다.
  • 관찰 기간 — 왕복을 견딜 때마다 나이를 먹여 "진짜 오래 살 놈인지" 지켜본다.
대가는 명확하다 — Survivor 하나만큼의 공간을 항상 놀린다

정리 문장 — "'빈 공간 하나를 통째로 확보해 두는 것'이 복사 알고리즘의 전제 조건이고, 그 대가로 Survivor 한 칸을 늘 비워 두는 공간 낭비를 지불합니다." 이 트레이드오프까지 말해야 외운 답이 아니라 이해한 답이 된다.

Minor GC도 Stop-The-World인가요?힌트: "짧다"와 "없다"는 전혀 다른 말이다 함정

그렇다. Minor GC도 STW다. 다만 생존 객체 수에 비례하는 복사 작업이라 대개 매우 짧아 체감이 적을 뿐이다. "Minor는 STW 없음"은 흔한 오답이다.

Old를 다루는 수집도 컬렉터에 따라 상당 부분을 애플리케이션과 동시(concurrent)에 수행하지만(G1, ZGC 등), mark의 시작·종료 지점처럼 그래프가 고정돼야 하는 구간의 STW는 여전히 남는다.

한 문장 덧붙이면 좋다 컬렉터 진화의 역사가 곧 "STW를 얼마나 줄이느냐"의 역사다. Serial → Parallel → CMS → G1 → ZGC의 흐름은 처리량을 올린 역사라기보다, 멈추는 시간을 짧게 그리고 힙 크기와 무관하게 예측 가능하게 만들어 온 역사다.

왜 이 오답이 자주 나오는가도 짚어 두면 좋다. Minor GC 한 번이 수 ms 수준이라 애플리케이션 지표에 잘 안 잡히기 때문이다. 하지만 초당 수십 번 돌면 그 합은 무시할 수 없고, 무엇보다 "짧다"는 것은 생존율이 낮다는 전제 위에서만 참이다 — 생존율이 오르면 Minor GC도 얼마든지 길어질 수 있다.

정리 문장 — "Minor GC도 STW입니다. 다만 복사량이 생존 객체에만 비례해 짧을 뿐이고, 생존율이 오르면 Minor GC의 pause도 함께 길어집니다."

Old의 객체가 Young의 객체를 참조하고 있으면, Young만 수집하는 Minor GC는 그걸 어떻게 알죠?힌트: 세대 분리가 뚫어 놓은 구멍이다. "Old를 다 훑으면?"이라고 되물어 본다 시니어 변별

이 질문은 세대 분리의 구멍을 정확히 찌른다. 먼저 문제 상황을 그려 보자.

// Old에 있는 장수 객체(캐시)가, 방금 Eden에 만들어진 객체를 참조한다
oldCache.put(key, new Product(...));   // Product는 Eden에 있고, 참조는 Old에서 온다

이때 Minor GC가 Young만 보고 판정하면, 이 Product는 "루트에서 닿지 않는다"고 오판돼 회수된다. 그러면 oldCache가 들고 있던 참조는 이미 없어진 객체를 가리키게 되고 프로그램이 깨진다.

그러니 Minor GC는 "Old에서 Young으로 들어오는 참조"도 루트처럼 취급해야 한다. 문제는 그걸 찾겠다고 Old 전체를 스캔하면 세대 분리의 의미가 통째로 사라진다는 것이다 — 싸게 하려고 나눴는데 매번 Old를 다 훑으면 남는 게 없다.

카드 테이블
HotSpot의 전통적 구현. Old를 작은 구획(카드)으로 나누고, 구획마다 1바이트짜리 표시 자리를 둔 배열.
쓰기 배리어
참조 대입이 일어날 때마다 JVM이 몰래 끼워 넣는 짧은 코드. 해당 카드를 dirty로 표시한다.

그러면 Minor GC는 Old 전체가 아니라 dirty로 표시된 카드만 훑으면 된다.

이 질문의 진짜 관전 포인트

세대 분리는 공짜가 아니라 "모든 참조 대입마다 쓰기 배리어를 실행하는 상시 비용"을 치르고 산 최적화다

애플리케이션이 평소에 조금씩 대가를 내고, GC 때 크게 아끼는 거래다. 이 거래 구조를 말할 수 있으면 "GC 옵션을 아는 사람"이 아니라 "GC 설계를 아는 사람"으로 보인다.

Full GC가 자주 발생하면 코드에서 무엇부터 의심하겠습니까?힌트: 조치를 말하기 전에 "유형을 가른다"고 말한다 핵심

Old가 빨리 차는 원인을 세 유형으로 나눠 보고, 유형을 먼저 가린 다음 조치를 정한다.

① 누수형
  • static 컬렉션 · 무경계 캐시
  • 판별: Full GC 후에도 Old 바닥이 계속 상승
  • 조치: 코드 수정 (힙 덤프로 범인 확인)
② 조기 승격형
  • 대형 임시 객체 · 객체를 오래 쥠
  • 판별: Minor GC 직후 Old가 눈에 띄게 증가, 단 Full GC 후엔 잘 줄어듦
  • 조치: 코드 수정 또는 Survivor 크기 조정
③ 설정형
  • Young이 너무 작아 정상 부하에도 승격 과다
  • 판별: 코드에 문제가 없는데 ②와 비슷한 증상
  • 조치: 힙 영역 비율 조정
핵심은 순서다 — GC 옵션을 먼저 만지는 것이 아니라 GC 로그로 유형을 가리는 것이 먼저다

왜 순서가 중요한가. 세 유형은 조치가 완전히 다르다. 유형을 안 가리고 힙만 키우면 ①은 터지는 시점만 미뤄지고, 그동안 Full GC 한 번의 STW는 오히려 길어진다. 힙이 커진 만큼 mark·compact 대상이 늘기 때문이다 — 증상을 완화한 게 아니라 폭발을 키운 것이다.

정리 문장 — "먼저 GC 로그에서 Full GC 후 Old의 바닥이 상승하는지를 봅니다. 상승하면 누수형이라 힙 덤프로 가고, 안 그러면 Minor GC 직후 Old 증가폭을 봐서 조기 승격형인지 판단합니다. 코드가 깨끗한데도 승격이 과하면 그때 Young 크기를 봅니다."

참조 카운팅은 순환 참조 말고도 문제가 있나요? 반대로 장점은 없나요?힌트: 멀티스레드 환경에서 카운터를 올리고 내린다는 게 무슨 뜻인지 생각해 본다 가산점

순환 참조가 원리적으로 못 푸는 결정적 결함이지만, 비용 측면의 문제도 있다.

  • 상시 비용이 크다. 참조를 대입할 때마다 카운터를 갱신해야 한다. 참조 대입은 프로그램에서 가장 흔한 연산 중 하나라, 이 비용이 전 구간에 깔린다.
  • 멀티스레드에서 더 비싸다. 여러 스레드가 같은 객체를 동시에 참조할 수 있으므로 카운터 증감이 원자적이어야 한다. 원자 연산은 일반 대입보다 훨씬 비싸고, 인기 있는 객체의 카운터에 경합이 몰린다.
  • 해제가 연쇄로 번진다. 큰 객체 그래프의 루트 카운트가 0이 되면 그 아래 전부가 도미노처럼 해제되면서 예상치 못한 지점에서 긴 정지가 생길 수 있다. "지연이 없다"는 장점이 항상 참은 아닌 것이다.
  • 카운터를 담을 공간이 객체마다 필요하다.

반대로 장점

구현이 단순하고, 쓰레기가 되는 즉시 회수되니 회수 지연이 없다. STW가 필요 없고 메모리 사용량의 고점이 낮게 유지된다. 그래서 그래프에 순환이 거의 없고 즉시 해제가 중요한 영역에서는 여전히 쓰인다.

면접에서의 좋은 마무리 "두 방식은 우열이 아니라 교환입니다. 참조 카운팅은 상시 비용을 내고 즉시성을 사고, 도달 가능성은 즉시성을 포기하고 상시 비용을 없앱니다. JVM처럼 순환이 흔하고 처리량이 중요한 런타임은 후자를 고릅니다."
다 쓴 객체는 null을 대입해 주는 게 GC에 도움이 되나요?힌트: 회수 후보가 되는 조건이 정확히 무엇이었는지 돌아본다 함정

대부분의 경우 의미가 없다. 회수 후보가 되는 조건은 "루트에서 닿는 경로가 끊기는 것"인데, 메서드가 리턴하면 스택 프레임이 걷히면서 지역변수는 그 순간 사라진다. 굳이 null을 넣지 않아도 이미 경로가 끊긴다.

void handle() {
    Order order = new Order();   // 스택의 order가 루트다
    process(order);
    order = null;                  // 바로 아래에서 프레임이 걷힌다 — 하는 일이 없다
}                                // 프레임이 걷히며 루트 → Order 경로가 끊김 = 회수 후보

예외적으로 의미가 있는 경우는 있다. 아주 긴 메서드 안에서 거대한 객체를 다 쓰고 난 뒤, 메서드가 끝나기까지 한참 남았을 때다. 그 사이에 GC가 돌면 그 거대한 객체가 아직 루트에서 닿아 살아남고, 심하면 승격까지 되기 때문이다.

진짜 문제는 "참조를 안 지운 것"이 아니라 "참조를 오래 붙잡는 자료구조"다

그래서 null 대입을 습관처럼 넣는 코드는 가독성만 해치고 효과는 없는 경우가 대부분이다. 같은 노력을 들일 곳은 static 컬렉션·캐시·ThreadLocal처럼 실제로 참조를 오래 붙잡는 지점이다.

정리 문장 — "지역변수는 프레임이 걷히는 순간 이미 끊깁니다. null 대입이 유효한 경우는 거대 객체 + 긴 메서드라는 좁은 조합뿐이고, 누수의 실제 원인은 자료구조가 붙잡는 참조입니다."

System.gc()를 호출하면 GC가 도나요?힌트: "명령"인지 "요청"인지를 먼저 구분한다 함정

보장되지 않는다. System.gc()는 "수집을 해 달라"는 요청(힌트)이고, JVM은 이를 무시할 수 있다. 실제로 명시적 GC를 아예 막는 옵션(-XX:+DisableExplicitGC)도 존재한다.

더 중요한 것은 돌았을 때가 더 문제라는 점이다. 이 호출은 대개 Old까지 포함한 전체 수집을 유발하므로, 가장 비싼 STW를 개발자가 손으로 불러오는 셈이 된다. 트래픽이 몰리는 시간에 이게 불리면 그 자체가 응답 스파이크다.

실무에서 이 호출이 나오는 맥락 "메모리가 안 줄어드는 것 같아서" 넣는 경우가 대부분인데, 안 줄어드는 이유가 누수라면 System.gc()로도 절대 안 줄어든다. 회수 대상이 아니기 때문이다. 즉 이 호출이 필요하다고 느끼는 상황 자체가 진단이 안 됐다는 신호다.

정리 문장 — "요청일 뿐 보장이 아니고, 설령 돌아도 가장 비싼 전체 수집이라 운영 코드에서는 쓰지 않습니다. 메모리가 안 줄면 System.gc()가 아니라 힙 덤프를 봐야 합니다."

Minor GC가 너무 잦아 보입니다. Young을 키우면 되나요?힌트: "빈도"와 "한 번의 길이"는 반대로 움직인다

Minor GC가 잦은 것 자체는 문제가 아니다. 각각이 짧고(수 ms~수십 ms) 회수량이 크면 건강한 상태다. "많으니 줄이자"는 지표를 오독한 판단일 수 있다.

Young을 키우면 얻는 것

  • Minor GC 횟수가 준다 — Eden이 차는 데 오래 걸리므로.
  • 객체가 Young에서 죽을 시간을 더 번다 → 승격이 줄어 Old 증가 속도가 느려질 수 있다.

Young을 키우면 잃는 것

  • 한 번의 Minor GC가 훑을 양이 늘어 개별 pause가 길어질 수 있다.
  • 힙 총량이 고정이라면 Old가 줄어 Full GC가 더 빨리 올 수 있다.
"GC를 덜 돌리기"가 목표가 아니다 — 목표는 "STW를 짧게, 그리고 예측 가능하게"다

그래서 튜닝 전에 물어야 할 것은 "횟수가 몇 번인가"가 아니라 "한 번의 pause가 얼마이고, 그 합이 응답시간 예산의 몇 %인가"다. 초당 20번 × 3ms(합 60ms)와 초당 2번 × 40ms(합 80ms) 중 어느 쪽이 나은지는 서비스가 평균에 민감한지 꼬리 지연에 민감한지에 따라 갈린다.

정리 문장 — "빈도가 아니라 pause의 길이와 총합을 봅니다. Young 확대는 횟수를 줄이는 대신 한 번을 길게 만드는 교환이라, 승격이 과다한 게 확인된 경우에 쓰는 카드입니다."

모든 객체는 반드시 Eden에서 태어나나요?힌트: 원문의 "예외적인 경우를 빼면"이 가리키는 것들 가산점

원칙은 그렇지만 예외가 있다. "거의 모든 객체는 Eden에 할당된다"가 정확한 표현이다.

  • Eden에 담기 어려울 만큼 큰 객체는 Young을 거치지 않고 Old에 바로 할당될 수 있다. 거대한 배열을 Young에 넣으면 복사 비용만 반복해서 물게 되기 때문이다. 임계 크기와 동작은 컬렉터와 설정에 따라 다르다.
  • 이스케이프 분석으로 메서드 밖으로 새어 나가지 않는다고 판단된 객체는 JIT 최적화로 힙 할당 자체가 사라질 수 있다(스칼라 치환 등). 이 경우 GC의 대상이 애초에 되지 않는다.
  • Survivor를 넘칠 만큼 생존자가 많으면 나이가 어려도 Old로 직행한다 — 조기 승격이다.
면접에서의 안전한 답변 폭 "기본은 Eden, 예외는 대형 객체와 조기 승격, 그리고 이스케이프 분석으로 할당 자체가 없어지는 경우" 정도로 유형만 말하는 것이 좋다. 구체적 임계값은 컬렉터·버전·옵션에 따라 달라지므로 숫자를 단언하지 않는 편이 안전하다.
승격 나이 임계치는 항상 15인가요?힌트: JVM이 그 값을 바꾸고 싶어지는 순간이 있다

아니다. HotSpot의 기본 상한이 15인 것은 맞지만, 실제로 적용되는 임계치는 고정이 아니다. Survivor가 넘칠 것 같으면 JVM이 임계치를 그보다 낮춰 더 일찍 승격시킨다.

이유는 간단하다. 복사 알고리즘은 "빈 Survivor에 생존자가 다 들어간다"를 전제로 한다. 그 전제가 깨질 것 같으면 넘칠 분량을 Old로 흘려보내는 것 말고는 방법이 없다. 즉 임계치의 동적 하향은 고장이 아니라 설계된 안전밸브다.

여기서 나오는 진단 감각 "평소보다 어린 나이에 승격이 일어난다"는 것은 곧 "Survivor에 압력이 걸리고 있다"는 신호다. 그래서 Minor GC 직후 Old 증가가 조기 승격형의 판별 기준이 된다. 나이 상한만 외우고 있으면 이 신호를 못 읽는다.

정리 문장 — "상한은 15지만 실효 임계치는 JVM이 Survivor 점유율을 보고 동적으로 낮춥니다. 그래서 어린 나이의 승격이 관측되면 Survivor가 좁다는 뜻으로 읽습니다."

Java에는 메모리 누수가 없다고 하던데, 맞나요?힌트: 문장을 반으로 쪼개면 반은 맞고 반은 틀리다 함정

정확히는 이렇다 — "실수로 참조를 놓치는 누수는 없고, 실수로 참조를 붙잡는 누수는 있다."

C의 전형적 누수는 free를 깜빡해서 아무도 못 쓰는 메모리가 남는 것이다. Java에서는 아무도 못 쓰는 메모리는 GC가 반드시 회수하므로 이런 누수는 없다. 하지만 "프로그램이 논리적으로는 더 안 쓰는데 참조는 여전히 붙어 있는" 상태는 얼마든지 만들 수 있고, GC는 그걸 살아있는 객체로 판정한다. GC는 "쓸모"를 모른다 — 오직 도달 가능성만 안다.

전형적인 누수 경로

static 컬렉션
static 필드가 GC 루트이므로 담긴 것은 프로세스가 사는 내내 닿는다. 상한 없는 캐시가 대표.
ThreadLocal 미제거
스레드가 살아있는 동안 닿는다. 스레드풀에서는 스레드가 재사용되며 사실상 영구히 산다.
해제 안 된 리스너·콜백
등록만 하고 해제하지 않으면 발행자가 구독자를 계속 붙잡는다.
키가 살아있는 맵
엔트리를 지우는 코드가 없는 맵은 사실상 무한 성장 자료구조다.

정리 문장 — "GC는 '안 쓰는 것'이 아니라 '못 닿는 것'을 회수합니다. 그래서 논리적으로는 버렸는데 참조는 남아 있는 코드가 Java식 누수이고, static·ThreadLocal·리스너·무경계 컬렉션이 그 단골 경로입니다."

"Mark 비용이 살아있는 객체 수에 비례한다"는 사실이 왜 그렇게 중요한가요?힌트: 이 한 문장에서 세대 분리의 이득이 전부 파생된다 핵심

이 사실이 세대 분리를 정당화하는 유일한 근거이기 때문이다. 거꾸로 말하면, 만약 mark 비용이 "영역 크기"에 비례했다면 Young/Old를 나눌 이유가 훨씬 약했다.

Young — 거의 다 죽어 있다

영역은 400MB인데 살아있는 건 2%. mark는 8만 개만 방문한다. 죽은 392만 개는 존재조차 확인하지 않는다.

VS

Old — 거의 다 살아 있다

3GB에 생존율 90%. mark는 2,700만 개 전부를 순회하고, compact는 2.7GB를 옮기며 참조까지 고쳐 쓴다.

같은 알고리즘인데 대상 영역의 "생존율"이 다르다는 것만으로 비용이 자릿수 단위로 갈린다

실무적 따름 정리도 나온다. 힙을 키우면 Minor GC는 여전히 싸지만 Full GC는 더 비싸진다. Young을 키워도 mark 대상은 생존자뿐이라 크게 안 늘지만, Old를 키우면 살아있는 객체가 늘어난 만큼 mark와 compact가 그대로 늘어나기 때문이다. "힙을 키우면 GC 문제가 해결된다"가 절반만 맞는 이유가 여기 있다.

힙에 빈 공간이 충분한데도 OOM이 날 수 있나요?힌트: "총량"과 "연속된 한 덩어리"는 다른 말이다 가산점

가능하다. 단편화(fragmentation) 때문이다. 총 빈 공간은 100MB인데 연속된 자리는 최대 2MB뿐이라면, 10MB짜리 배열 하나를 할당하지 못해 OOM이 날 수 있다. 배열 같은 객체는 연속된 메모리를 요구하기 때문이다.

이것이 Sweep만 하고 Compact를 하지 않는 방식의 근본 약점이다. 그래서 GC들은 어느 시점엔가 반드시 압축(또는 복사)을 수행한다 — 단편화는 미룰 수는 있어도 없앨 수는 없는 청구서다.

Sweep 계열

  • 객체를 안 옮겨서 싸다
  • 대신 빈틈이 흩어지고, 빈 공간 목록을 관리하는 자료구조가 필요하다
  • 결국 대형 객체 할당에서 터진다

Copy / Compact 계열

  • 단편화가 원천적으로 없다 — 차곡차곡 이어 붙인다
  • 대신 이동 비용 + 참조 갱신 비용을 낸다
  • Young에서는 옮길 게 거의 없어서 이 비용이 사실상 무료다

정리 문장 — "OOM은 '총 빈 공간 부족'이 아니라 '요청한 크기의 연속 공간 부족'일 수 있습니다. 그래서 단편화를 어떻게 처리하느냐가 컬렉터 설계의 핵심 축이고, Young이 복사 방식을 쓰는 이유도 여기에 있습니다."

STW가 아예 없는 GC도 있나요? 최신 컬렉터는 무엇이 달라진 건가요?힌트: "짧아졌다"와 "없어졌다"의 차이, 그리고 "힙 크기와 무관하게"라는 표현 시니어 변별

"완전히 없다"고 말하기는 어렵다. 최신 컬렉터들은 mark와 이동(재배치)의 상당 부분을 애플리케이션과 동시에 수행하지만, 그래프가 고정돼야 하는 짧은 구간의 STW는 남는다(mark의 시작·종료 지점 등).

진짜 달라진 것은 "STW의 길이가 무엇에 비례하느냐"다. 전통적인 컬렉터는 힙이 커지면 pause도 함께 커졌다. 최신 컬렉터의 목표는 힙 크기와 무관하게 pause를 짧고 예측 가능하게 유지하는 것이다 — "평균을 낮추는 것"이 아니라 "꼬리를 자르는 것"이 목적이다.

정리 문장 — "STW가 0인 컬렉터는 아니고, '남는 STW를 힙 크기와 무관하게 짧게 만든' 컬렉터입니다. 그래서 선택 기준도 '얼마나 빠른가'가 아니라 '어떤 pause 특성을 원하는가'가 됩니다."

Minor GC 직후 Old 사용량이 오르는 건 항상 이상 신호인가요?힌트: 승격 자체는 설계된 정상 동작이다

아니다. 승격은 설계된 정상 동작이다. 스프링 빈, 커넥션 풀, 정상적인 장수 캐시는 애초에 Old로 가야 하는 객체다. 그러니 Old가 오르는 것 자체가 아니라 어떻게 오르는가를 봐야 한다.

같은 "Old 증가"라도 읽는 법이 다르다
패턴해석조치
기동 직후 한 번 오르고 평평정상 — 장수 객체가 자리를 잡은 것없음
완만히 오르다 Full GC 후 원래 바닥으로 복귀정상 — 승격된 객체가 결국 회수되고 있다없음
Minor GC마다 계단식으로 뚜렷하게 상승조기 승격 의심 — Survivor에 압력임시 객체 수명 단축 · Survivor 크기 점검
Full GC 후에도 바닥이 계속 상승누수 — 회수 불가능한 객체가 쌓인다힙 덤프 · 코드 수정

구분의 핵심은 "Full GC 후의 바닥"이다. 바닥이 제자리로 돌아오면 회수되고 있는 것이고, 바닥 자체가 우상향이면 회수 불가능한 것이 쌓이는 것이다. 전자는 튜닝의 영역이고 후자는 코드의 영역이다.

정리 문장 — "승격은 정상이고, 문제는 '얼마나 빨리·무엇이' 승격되느냐입니다. Full GC 후 Old의 바닥선 하나로 튜닝 문제인지 코드 문제인지가 갈립니다."

한 줄 요약
GC는 GC 루트에서 참조를 따라가 닿지 않는 객체를 회수하는 장치이고(그래서 순환 참조도 섬째로 회수된다), Young/Old 분리는 "대부분 금방 죽는다"는 세대 가설에 기대 좁은 Young을 복사 방식으로 싸게 자주 치우고 비싼 전체 수집을 아끼는 전략이다 — 그러므로 객체를 필요 이상 오래 쥐는 코드는 그 전제를 깨뜨려 조기 승격과 Full GC를 부르는, GC 관점에서 가장 비싼 코드다.
