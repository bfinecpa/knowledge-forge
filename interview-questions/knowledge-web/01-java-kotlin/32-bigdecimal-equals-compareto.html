그래서 equals가 false인 것은 버그가 아니라 계약을 지킨 결과이고, 진짜 사고는 hashCode까지 스케일을 반영해 HashSet·HashMap이 예외 하나 없이 조용히 틀리는 자리에서 난다.

면접 질문: "BigDecimal의 equals와 compareTo가 다르게 동작하는 경우는? 금액 비교 코드에서 어떤 버그를 만드나요?"

핵심 관전 포인트 — BigDecimal은 숫자를 부호 있는 정수 unscaledValue와 소수점 위치 scale 두 개로 나눠 담는다 — 1.0은 (10, 1), 1.00은 (100, 2)라서 수학적으로는 같은 값인데 객체의 상태가 실제로 다르다. 그래서 equals가 false인 것은 버그가 아니라 "필드가 전부 같아야 같다"는 상태 동등성 계약을 그대로 지킨 결과이고, 수학적 값만 견주고 싶으면 스케일을 맞춘 뒤 비교하는 compareTo를 써야 한다. 문제는 hashCode도 스케일을 반영한다는 것이다 — 1.0은 311, 1.00은 3102라서 HashSet·HashMap에서 아예 다른 버킷으로 가고, 여기서는 compareTo를 끼워 넣을 방법조차 없어 예외 하나 없이 조용히 틀린다. 그리고 스케일은 생각보다 쉽게 어긋난다 — PostgreSQL NUMERIC(19,2) 조회 결과는 scale 2로 오는데 코드에서 만든 BigDecimal.valueOf(100)은 scale 0이고, setScale·곱셈(스케일 합산)·나눗셈(스케일 뺄셈)이 전부 스케일을 바꾼다. 값 비교는 예외 없이 compareTo(...) == 0(0 비교는 signum() == 0)으로 하고, 컬렉션에 넣거나 저장할 값은 경계에서 스케일을 통일해 문제를 애초에 안 만드는 것이 정공법이다.

0. 질문 + 출제 의도 · 겨냥하는 약점

질문 — "BigDecimal의 equals와 compareTo가 다르게 동작하는 경우는? 금액 비교 코드에서 어떤 버그를 만드나요?"

출제 의도 — 1.0과 1.00이 equals로는 다르고 compareTo로는 같다는 스케일 함정은 "금액 일치 검증이 간헐적으로 실패하는" 재현 어려운 버그를 만든다. 금액을 다루는 타입의 미묘한 규약까지 확인해 봤는지 — "금액에 double 쓰지 마세요"의 다음 단계 디테일을 아는지를 본다.

약점 A"1.0과 1.00은 equals가 false예요"에서 멈춘다 — 현상만 외운 것이다. unscaledValue와 scale 두 조각이라는 내부 표현을 깔지 못하면 "왜 hashCode도 달라지는가", "왜 0.00이 ZERO와 다른가", "왜 100과 1.00은 unscaledValue가 같은가" 앞에서 다시 막힌다(1절).
약점 Bequals의 동작을 "버그"라고 부른다 — 규약을 어긴 것이 아니라 지킨 것이다. 더 나아가 BigDecimal은 Comparable의 "자연 순서와 equals를 일치시키라"는 권장을 의도적으로 깬 드문 표준 클래스이고, Javadoc이 그 사실을 명시한다는 데까지 가야 답이 닫힌다(2·4절).
약점 C"compareTo 쓰면 됩니다"로 끝낸다 — 진짜 위험은 compareTo를 끼워 넣을 자리조차 없는 곳에 있다. HashSet·HashMap·List.contains는 equals와 hashCode로만 동작하도록 만들어져 있어 비교 방식을 주입할 파라미터가 없다(5·6절).
약점 D"우리는 스케일을 통일하니까 괜찮다"고 답한다 — 스케일은 명시적으로 지정하지 않아도 DB NUMERIC(19,2), 요청 파라미터, 코드 상수, 산술 연산 결과, setScale로 계속 어긋난다. 경로를 댈 수 있어야 방어선을 어디에 칠지 말할 수 있다(7·8절).
약점 E인접 함정을 못 본다 — new BigDecimal(0.1)이 55자리를 만드는 이유, 반올림 없는 divide가 나누어떨어지는 테스트 데이터에서만 통과하는 이유, stripTrailingZeros()가 1E+2를 뱉는 이유는 전부 같은 뿌리(스케일)다(9절·꼬리질문).
합격선"BigDecimal은 값을 unscaledValue와 scale로 나눠 들고 있어서 1.0은 (10,1), 1.00은 (100,2)입니다. 필드가 다르니 equals가 false인 것은 규약을 지킨 결과이고, 수학적 값 비교는 스케일을 맞춘 뒤 비교하는 compareTo(...) == 0이 담당합니다. 더 위험한 것은 hashCode도 스케일을 반영한다는 점입니다 — 100과 100.00은 해시가 달라 HashMap에서 다른 버킷으로 가고, 거기서는 compareTo를 끼워 넣을 방법이 없어 중복 결제 감지가 예외 없이 조용히 통과합니다. 스케일은 DB NUMERIC(19,2)·산술 연산·setScale로 쉽게 어긋나므로, 비교 규칙만 정하지 말고 경계에서 스케일을 통일한 Money 값 객체로 가두는 것이 정공법입니다."
이 문서를 관통하는 한 문장 equals는 표현을 묻고, compareTo는 값을 묻는다 — 그리고 hashCode는 표현 편에 서 있다. 마지막 절반이 이 문서의 전부다. equals만 문제였다면 "값 비교는 compareTo로"라는 규칙 하나로 끝났을 텐데, hashCode가 스케일을 반영하는 순간 해시 기반 컬렉션 전체가 함께 넘어간다. 그래서 이 문서는 세 방향으로 갈라진다 — 왜 그렇게 설계됐나(1~4절), 어디서 조용히 틀리나(5·6절), 스케일은 어디서 어긋나고 어떻게 막나(7~12절).

1. 전제 — BigDecimal은 숫자를 두 조각으로 나눠 들고 있다

"equals가 스케일까지 본다"는 결론부터 외우면 납득이 안 된다. BigDecimal이 내부에 무엇을 들고 있는지를 먼저 보면 그 결론이 자연스럽게 유도되고, 뒤에 나오는 hashCode·컬렉션·연산 규칙까지 전부 같은 그림에서 설명된다.

double은 숫자 하나를 부호·지수·가수라는 정해진 비트 묶음에 밀어 넣는다. 그래서 2진수로 딱 떨어지지 않는 0.1 같은 값은 애초에 정확히 담기지 않는다. BigDecimal은 이 문제를 피하려고 접근을 아예 바꿨다 — 숫자를 두 개의 값으로 나눠 담는다.

unscaledValue
소수점을 없앤 정수. 자릿수 제한이 없는 BigInteger다.
scale
소수점을 왼쪽으로 몇 칸 옮겨야 하는지를 나타내는 int.
값 = unscaledValue × 10−scale
비유 — BigDecimal은 "금액"이 아니라 "영수증"이다

"1,000원"이라고 적힌 영수증과 "1,000.00원"이라고 적힌 영수증은 같은 금액에 대한 서로 다른 두 장의 종이다. 두 장을 겹쳐 놓고 글자가 똑같은지 대조하면 다르고(equals), 적힌 금액만 읽어서 견주면 같다(compareTo).

BigDecimal이 두 번째 종이의 .00을 지우지 않고 보관하는 이유는, 계량·회계에서 "소수점 둘째 자리까지 실제로 측정했다"는 것 자체가 정보이기 때문이다. 저울이 1kg을 가리킨 것과 1.00kg을 가리킨 것은 정밀도가 다른 진술이다.

그래서 이 타입을 "숫자를 담는 상자"로만 보면 계속 배신당하고, "숫자 + 그 숫자의 정밀도를 함께 적어 둔 기록"으로 보면 모든 동작이 예측 가능해진다.

세 개만 외우면 나머지는 유도된다

(10, 1)
1.0
(100, 2)
1.00
(100, 0)
100

면접에서 이 세 쌍을 먼저 칠판에 적고 시작하면 — equals가 false인 이유도, hashCode가 다른 이유도, 0.00 ≠ ZERO인 이유도 같은 그림 위에서 손가락으로 짚어 설명할 수 있다.

2. equals는 표현을 묻는다 — false는 계약을 지킨 결과다

Object.equals의 계약은 "논리적으로 같은 객체인가"이고, 값 객체에서 그 판단 기준은 통상 필드가 전부 같은가다. 1.0과 1.00은 필드가 다르므로 equals는 false를 반환해야 한다. 규약을 어긴 것이 아니라 규약대로 동작한 것이다.

BigDecimal a = new BigDecimal("1.0");
BigDecimal b = new BigDecimal("1.00");

System.out.println(a.equals(b));         // 출력: false
System.out.println(a.compareTo(b));      // 출력: 0
System.out.println(a.compareTo(b) == 0); // 출력: true

3. compareTo는 값을 묻는다 — 스케일을 맞춘 뒤 비교한다

compareTo는 다른 질문에 답한다. 두 값의 스케일을 큰 쪽에 맞춰 정렬시킨 뒤 수학적 크기만 비교한다. 1.0을 1.00으로 맞춰 놓고 보면 같으므로 0을 돌려준다.

같은 두 객체를 놓고 두 메서드가 서로 다른 질문에 답한다
비교 기준답하는 질문1.0 vs 1.00쓰는 자리

세 줄 규칙 — 이것만 지키면 비교 시점은 뚫리지 않는다

값이 같은지  →  a.compareTo(b) == 0
0인지  →  a.signum() == 0  (compareTo(ZERO) == 0보다 짧고 의도가 직접적)
금지  →  a.equals(b) · a.equals(BigDecimal.ZERO)

단, 이 세 줄로는 6절의 컬렉션 버그를 못 막는다. 거기는 우리가 비교문을 쓰는 자리가 아니기 때문이다 — 그래서 11절의 경계 정규화가 따로 필요하다.

4. 자연 순서와 equals가 어긋난, 드문 표준 클래스

여기서 짚고 갈 것이 하나 더 있다. Comparable 인터페이스는 x.compareTo(y) == 0과 x.equals(y)가 일치할 것을 "강력히 권장"한다. 정렬 순서와 동등성 판단이 어긋나면 정렬 기반 컬렉션(TreeSet·TreeMap)이 Set·Map 인터페이스의 일반 계약과 어긋나게 동작하기 때문이다.

BigDecimal은 이 권장을 의도적으로 깬 드문 표준 클래스이고, Javadoc에도 "자연 순서가 equals와 일관되지 않는다"고 명시돼 있다. 즉 숨겨진 버그가 아니라 문서화된 성질이다 — 면접에서 "명세에 적혀 있는 동작"이라고 말할 수 있으면 인상이 달라진다.
보통의 클래스 (String, Integer, LocalDate…)
  • compareTo == 0 ⟺ equals == true
  • HashSet이든 TreeSet이든 같은 결과
  • 어느 컬렉션을 쓰는지 신경 쓸 필요가 없다
vs
BigDecimal
  • compareTo == 0 인데 equals == false가 가능
  • HashSet은 2개, TreeSet은 1개로 답이 갈린다
  • 어떤 컬렉션을 골랐는지가 도메인 결과를 바꾼다

왜 그런 선택을 했는지는 14절 첫 꼬리질문에서 다룬다. 요약하면 둘 중 하나는 반드시 깨야 하는 구조였고, "정렬이 수학적 크기순으로 동작하는 쪽"을 살렸다.

5. hashCode도 스케일을 반영한다 — 여기서 진짜 문제가 시작된다

equals만 다르면 "값 비교할 때 compareTo 쓰자"로 끝난다. 문제는 hashCode도 스케일을 반영한다는 것이다.

System.out.println(new BigDecimal("1.0").hashCode());     // 출력: 311
System.out.println(new BigDecimal("1.00").hashCode());    // 출력: 3102
System.out.println(new BigDecimal("100").hashCode());     // 출력: 3100
System.out.println(new BigDecimal("100.00").hashCode());  // 출력: 310002

6. Set·Map에서 결과가 갈라지는 그림 — 조용히 틀리는 자리

왜 이게 치명적인지는 HashMap이 값을 찾는 절차를 알아야 보인다(규약 본편은 03-equals-hashcode-contract에 있다). HashMap은 두 단계를 밟는다.

1
칸 선택 — key.hashCode()로 정수를 얻고, 그것을 섞어 배열 인덱스(버킷)를 계산한다.
2
후보 대조 — 그 칸에 매달린 후보들만 꺼내 key.equals(후보)로 대조한다.
비유 — 서가 번호가 다르면 사서는 영원히 못 찾는다

hashCode는 "이 책을 몇 번 서가에 꽂을지 정하는 번호"다. 사서는 번호를 계산해 그 서가 하나만 뒤진다. 온 도서관을 다 뒤지지 않기 때문에 빠른 것이고, 바로 그래서 번호가 어긋나면 책이 있어도 "없습니다"라고 답한다.

결정적인 부분은 이것이다 — 사서에게 "제목을 조금 느슨하게 봐 주세요"라고 부탁할 창구가 없다. HashMap.get에는 비교 함수를 넘기는 파라미터가 아예 없기 때문이다. TreeMap은 Comparator를 받으니 부탁할 창구가 있고, 그래서 다르게 동작한다(14절).

Set<BigDecimal> paidAmounts = new HashSet<>();
paidAmounts.add(new BigDecimal("100.00"));           // DB에서 온 값 (NUMERIC(19,2) -> scale 2)

System.out.println(paidAmounts.contains(new BigDecimal("100")));   // 출력: false   <- 중복 결제 감지 실패

paidAmounts.add(new BigDecimal("100"));
System.out.println(paidAmounts);        // 출력: [100.00, 100]   같은 금액이 두 항목으로 들어갔다
System.out.println(paidAmounts.size()); // 출력: 2

System.out.println(List.of(new BigDecimal("100.00")).contains(new BigDecimal("100")));
// 출력: false        List.contains도 equals 기반이라 같다

7. 스케일이 어긋나는 다섯 갈래 경로 — "우리는 통일하니까 괜찮다"가 안 통하는 이유

"우리 코드는 스케일을 통일하니까 이 문제가 없다"고 생각하기 쉽다. 그런데 스케일은 우리가 명시적으로 지정하지 않아도 여러 경로로 달라진다. 경로를 하나씩 확인해 두면 어디에 방어선을 쳐야 하는지가 정해진다.

① DB — 가장 흔한 출처
PostgreSQL NUMERIC(19,2)는 항상 소수점 둘째 자리까지 저장한다. JDBC가 읽어 오면 scale 2다. 값이 100원이어도 (10000, 2).
→ scale 2 고정
② 요청 파라미터
폼·쿼리스트링·JSON의 "100"을 그대로 파싱하면 사용자가 친 자릿수가 곧 scale이 된다. 입력에 따라 매번 다르다.
→ scale 0 (또는 입력한 자릿수)
③ 코드 상수
BigDecimal.valueOf(100L), BigDecimal.ZERO, ONE, TEN은 전부 scale 0이다. 여기가 0 비교 버그의 진원지다.
→ scale 0
④ 산술 연산
연산 결과의 스케일이 연산 종류에 따라 자동으로 정해진다. 우리가 지정하지 않았는데 바뀌는 유일한 경로다(8절).
→ 연산 규칙이 결정
⑤ setScale
유일하게 의도적인 변경. 자리를 늘리는 건 0을 붙이면 되지만 줄일 때는 반올림 모드가 필수다(9절).
→ 지정한 scale

8. 연산별 스케일 규칙 — 지수 법칙 그대로다

연산 결과의 스케일은 자동으로 정해지는데, 규칙이 연산마다 다르다. 직접 돌려본 결과를 보자.

new BigDecimal("50.5").multiply(new BigDecimal("2"));     // 101.0    scale = 1
new BigDecimal("100.00").add(new BigDecimal("50.5"));     // 150.50   scale = 2
new BigDecimal("100.00").subtract(new BigDecimal("100")); // 0.00     scale = 2  <- 0이 아니라 0.00
new BigDecimal("100.00").divide(new BigDecimal("4"));    // 25.00    scale = 2
연산결과 스케일위 예시주의
add · subtract두 피연산자 스케일 중 큰 쪽max(2, 1) = 2정밀한 쪽으로 끌려간다
multiply두 피연산자 스케일의 합1 + 0 = 1반복 곱셈에서 스케일이 계속 불어난다
divide피제수 스케일 빼기 제수 스케일
(나누어떨어질 때)		2 − 0 = 2나누어떨어지지 않으면 예외(14절)
setScale지정한 값0 → 2줄일 때는 RoundingMode 필수

가장 자주 밟는 지뢰 — 0.00은 BigDecimal.ZERO가 아니다

100.00 − 100  =  0.00  (값은 0, scale은 2)

BigDecimal.ZERO·ONE·TEN 같은 상수는 전부 scale 0이다. 반면 계산으로 나온 0은 피연산자의 스케일을 물려받아 0.00이 되는 경우가 흔하다. 그래서 equals(BigDecimal.ZERO)는 사실상 늘 위험한 코드이고, "잔액이 0인지" 검사가 조용히 실패하는 전형적인 경로가 바로 여기다.

0 판정은 signum() == 0 — 음수 판정도 signum() < 0으로 같은 계열이다

9. 생성자 세 가지와 double의 정체

이 셋은 이름이 비슷한데 결과가 다르다. 1.0만 보면 그냥 scale이 다른 정도로 보인다.

new BigDecimal("1.0")        // 1.0    scale = 1
BigDecimal.valueOf(1.0)      // 1.0    scale = 1
new BigDecimal(1.0)          // 1      scale = 0

0.1을 넣어 보면 진짜 문제가 드러난다.

생성자 3순위 — 한 줄로 외운다
문자열 > valueOf > (금지) new BigDecimal(double)

new BigDecimal(double)이 필요한 상황은 딱 하나 — "이 double의 비트가 실제로 무슨 값인지 조사할 때"다. 금액 코드에서 그럴 일은 없다.

setScale에서 자주 놓치는 두 가지

① 줄일 때 반올림 모드가 없으면 예외

new BigDecimal("100.50").setScale(0);
// ArithmeticException: Rounding necessary

자리를 늘리는 쪽은 0을 붙이면 되니 안전하다. 줄이는 쪽은 버릴 자리를 어떻게 처리할지 정해야 하고, 안 정해 주면 임의로 버리지 않고 예외를 던진다.

② 원본을 바꾸지 않고 새 객체를 반환

amount.setScale(2, HALF_UP);        // 아무 일도 안 일어난다
amount = amount.setScale(2, HALF_UP); // 반환값을 받아야 한다

BigDecimal은 불변 객체이기 때문이다(04-string-immutability-stringbuilder의 String과 같은 성질). add·multiply도 전부 새 객체를 반환한다.

11. 방어는 네 겹으로 — 비교 시점에서만 막으면 새어 나간다

버그 세 개를 다 보면 방어선이 어디에 있어야 하는지가 정해진다. 비교 시점에서만 막으면 버그 2(컬렉션)는 못 막는다. 우리가 equals를 직접 호출하는 자리가 아니기 때문이다. 그래서 층을 나눈다.

1겹
값 비교는 예외 없이 compareTo(...) == 0, 0 비교는 signum() == 0. 이건 사람이 기억해서 지킬 규칙이 아니라 도구로 강제해야 하는 규칙이다 — ErrorProne의 BigDecimalEquals처럼 BigDecimal에 equals를 쓰면 빌드를 실패시키는 정적 분석 규칙을 켜 두면, 신규 입사자나 AI가 생성한 코드에서도 이 실수가 통과하지 못한다.
2겹
경계에서 스케일을 정규화한다 — 진짜 정공법. 값이 시스템 안으로 들어오는 지점(DB 조회 후 도메인 객체 생성, 외부 API 응답 파싱, 요청 DTO 변환)에서 setScale(2, RoundingMode.HALF_UP)으로 통일하면, 그 이후로는 시스템 안에 스케일이 다른 같은 금액이 존재하지 않는다. 비교 문제도 컬렉션 문제도 함께 사라진다.
3겹
컬렉션 키로 써야 한다면 정규화된 값만 넣는다. 2겹이 되어 있으면 자동으로 해결된다. 대안인 TreeSet/TreeMap은 compareTo로 판정하니 동작은 하지만, Set의 일반 계약에서 벗어난 상태라는 점을 주석이나 타입 이름으로 드러내야 한다.
4겹
출력 정규화에 stripTrailingZeros()를 쓸 때는 함정을 알고 쓴다. 뒤에 붙은 0을 떼어 1.00을 1로 만들어 주지만, 정수에 쓰면 지수 표기가 튀어나온다 — new BigDecimal("100").stripTrailingZeros()는 1E+2(scale −2)다. 반드시 toPlainString()과 짝지어 쓴다.
System.out.println(new BigDecimal("1.00").stripTrailingZeros());   // 출력: 1
System.out.println(new BigDecimal("100").stripTrailingZeros());    // 출력: 1E+2   <- 응답에 그대로 나가면 사고
System.out.println(new BigDecimal("100").stripTrailingZeros().scale());  // 출력: -2
System.out.println(new BigDecimal("100").stripTrailingZeros().toPlainString()); // 출력: 100
비교 목적은 compareTo, stripTrailingZeros는 표시 목적으로 쓰되 반드시 toPlainString()과 짝지어 쓴다

12. 팀 표준 금액 타입 — 규칙을 지키게 하지 말고, 규칙이 필요 없게 만든다

"compareTo를 씁시다"라는 규칙만 정하는 것으로는 부족하다. 사람이 매번 기억해야 하는 규칙은 반드시 새는데, 이 버그는 새도 티가 안 나기 때문이다. 그래서 틀린 코드를 애초에 쓸 수 없게 만드는 쪽으로 설계한다.

public record Money(BigDecimal amount, Currency currency) {
    private static final int SCALE = 2;

    public Money {
        // 경계 정규화: 어떤 경로로 들어온 값이든 여기서 스케일이 통일된다.
        // 이 한 줄이 6절의 컬렉션 버그를 구조적으로 없앤다.
        amount = amount.setScale(SCALE, RoundingMode.HALF_UP);
    }

    public boolean isSameAmount(Money other) {
        // 밖으로는 compareTo 기반 비교만 노출한다.
        // 호출자가 equals를 잘못 쓸 기회 자체를 주지 않는다.
        return currency.equals(other.currency)
            && amount.compareTo(other.amount) == 0;
    }

    public boolean isZero() { return amount.signum() == 0; }

    public Money plus(Money other) { /* 통화 검증 후 더한다 */ }
}
정규화를 생성자에 두는 것이 핵심이다 Money 객체는 만들어지는 순간 항상 scale 2이므로, record가 자동 생성해 준 equals/hashCode도 그대로 안전해진다. HashMap 키로 써도 되고 Set에 넣어도 된다. "값 비교는 compareTo"라는 규칙이 타입 안으로 흡수되어 사라진 것이다.
경계 1
DB
JPA 컨버터나 @Embeddable로 막는다. 컬럼은 NUMERIC(19,2) — double precision이면 저장 계층에서 오차가 생겨 애플리케이션이 아무리 BigDecimal을 써도 소용없다.
경계 2
API · JSON
커스텀 역직렬화로 막는다. 금액이 double로 표현되는 지점 자체를 없애는 것이 목표다 — DTO 필드 타입까지 BigDecimal이나 문자열로.
정책
스케일과 반올림
저장 스케일(원화 0, 달러 2), 나눗셈 자릿수, 부가세·수수료 절사 규칙을 정책 문서에서 가져와 상수 한 곳에 모은다. 흩어진 setScale(2, HALF_UP)은 정책이 바뀔 때 전부 찾아 고쳐야 한다.
잔여
정적 분석
그래도 BigDecimal을 직접 써야 하는 자리는 남는다. ErrorProne BigDecimalEquals 같은 규칙을 CI에서 켜 equals 사용을 빌드 실패로 잡는다.
트레이드오프까지 말해야 답이 닫힌다 Money 타입을 도입하면 초반에 변환 코드가 늘고, 이미 BigDecimal이 시그니처에 박혀 있는 레거시 코드에서는 경계 어댑터가 필요하다. 그래서 현실적인 순서는 신규 도메인부터 Money를 쓰고, 레거시는 정적 분석으로 equals만 먼저 막은 뒤 점진적으로 흡수하는 것이다.

값 비교에 쓰지 않는다. compareTo(...) == 0.
D — Double 생성자
new BigDecimal(0.1) 금지. 문자열 또는 valueOf.
D — Divide 맨몸

14. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 막히면 그 절로 돌아간다.

equals가 스케일까지 보는 건 잘못 설계된 것 아닌가요? 왜 안 고쳤을까요?핵심"의도된 설계"라는 인정에서 출발해야 한다

먼저 의도된 설계라는 것부터 인정하고 시작한다. BigDecimal은 "수 하나"가 아니라 "수 + 그 수가 소수점 아래 몇 자리까지 유효한가"를 함께 표현하는 타입이다. 회계·계량 도메인에서 1.0과 1.00은 정밀도가 다른 서로 다른 진술이고, equals가 그 차이를 지워 버리면 그 정보를 다시 얻을 방법이 없어진다.

Comparable의 권장을 깬 대가로 얻은 것도 있다. compareTo가 스케일을 무시하기 때문에 정렬은 우리가 기대하는 대로 수학적 크기순으로 동작한다. 만약 두 메서드를 일치시키려고 compareTo가 스케일까지 봤다면 1.0과 1.00 사이에 임의의 순서가 생겨 훨씬 이상한 정렬이 됐을 것이다. 둘 중 하나는 규약을 깰 수밖에 없는 구조였고, 값 비교 쪽을 살린 것이다.

이제 와서 고칠 수 없는 이유도 명확하다. equals의 동작을 바꾸면 기존에 HashMap 키나 Set 원소로 쓰던 모든 코드의 동작이 조용히 달라진다. 컴파일 에러도 예외도 나지 않는 변경이라 어떤 코드가 영향을 받는지 알 방법조차 없다. 그래서 Javadoc에 "자연 순서가 equals와 일관되지 않는다"고 명시하고 사용자에게 알리는 쪽을 택했다.

정리 문장 — "잘못 설계된 게 아니라, 잘못 쓰기 쉬운 설계"
new BigDecimal(0.1)과 BigDecimal.valueOf(0.1)은 뭐가 다른가요?핵심긴 숫자가 나오는 이유를 double 쪽에서 설명해야 한다

new BigDecimal(double)은 double이 실제로 들고 있는 2진 근사값을 한 자리도 버리지 않고 그대로 10진수로 옮긴다.

new BigDecimal(0.1)      // 0.1000000000000000055511151231257827021181583404541015625  (scale 55)
BigDecimal.valueOf(0.1)  // 0.1  (scale 1)
new BigDecimal("0.1")    // 0.1  (scale 1)

0.1은 2진 분수로 정확히 표현되지 않으므로 double에는 가장 가까운 근사값이 담기는데, 그 근사값의 정확한 10진 표기가 위의 긴 숫자다. BigDecimal은 잘못한 게 없다 — double이 이미 갖고 있던 오차를 정직하게 드러냈을 뿐이다.

valueOf가 안전한 이유는 내부에서 Double.toString(d)를 거치기 때문이다. Double.toString은 "다시 읽으면 같은 double이 되는 가장 짧은 표기"를 주므로 "0.1"이 나오고, 그것을 파싱하니 우리가 의도한 값이 된다.

실무 기준은 셋이다. 문자열 생성자를 1순위로, double을 이미 들고 있으면 valueOf, new BigDecimal(double)은 쓰지 않는다. 근본 대응은 금액이 double이 되는 지점 자체를 없애는 것 — JSON 역직렬화 설정, DTO 필드 타입, 외부 API 응답 매핑을 전부 BigDecimal이나 문자열로 받으면 이 질문 자체가 사라진다.

stripTrailingZeros()로 스케일을 없애고 equals로 비교하면 되지 않나요?함정"동작은 한다"로 시작해서 두 가지 이유로 반박한다

동작은 한다. 1.0과 1.00을 둘 다 1로 만든 뒤 equals로 비교하면 true가 나온다. 그런데 비교 목적으로 쓰기에는 두 가지 이유로 나쁜 선택이다.

첫째, 정수에서 지수 표기가 튀어나온다.

new BigDecimal("100").stripTrailingZeros();                // 1E+2   (scale = -2)
new BigDecimal("100").stripTrailingZeros().toString();     // "1E+2"
new BigDecimal("100").stripTrailingZeros().toPlainString(); // "100"

뒤쪽 0 두 개를 떼면 unscaledValue가 1이 되므로 원래 값 100을 유지하려면 scale이 -2가 되어야 하고, scale이 음수면 toString()이 지수 표기를 쓴다. 비교만 하고 버릴 값이면 상관없지만, 그 객체가 로그·응답·다음 계산으로 흘러가면 1E+2가 그대로 노출된다.

둘째, 정규화 후 equals는 compareTo보다 느리고 의도가 덜 드러난다. 새 객체를 만드는 비용이 붙고, 읽는 사람은 "왜 여기서 0을 떼고 있지?"를 한 번 더 생각해야 한다. compareTo(other) == 0은 그 자체로 "값이 같은지 본다"는 뜻이다.

역할 분담 — 비교는 compareTo, 표시 정규화는 stripTrailingZeros + toPlainString

다만 표시 목적이라도 대개는 setScale(2, HALF_UP)이나 NumberFormat으로 자릿수를 고정하는 편이 낫다. 금액 화면에서 1000원과 1000.00원이 섞여 나오는 것도 결함이기 때문이다.

divide()를 쓸 때 주의할 점은 무엇인가요?핵심예외가 나는 이유와, 그 예외가 잠복 버그인 이유

반올림 모드를 안 주면 예외가 난다는 것이 첫 번째다.

new BigDecimal("10").divide(new BigDecimal("3"));
// ArithmeticException: Non-terminating decimal expansion; no exact representable decimal result.

10을 3으로 나누면 3.333…으로 무한히 이어진다. BigDecimal은 유한한 자릿수만 표현할 수 있으므로 "어디서 끊을지"를 알려주지 않으면 계산을 시작조차 못 한다. 값을 대충 잘라 반환해 오차를 조용히 만드는 것보다 예외로 멈추는 편이 낫다는 판단이다.

new BigDecimal("10").divide(new BigDecimal("3"), 2, RoundingMode.HALF_UP);   // 3.33  스케일 직접 지정
new BigDecimal("10.00").divide(new BigDecimal("3"), RoundingMode.HALF_UP);   // 3.33  피제수 스케일(2) 사용
이 예외가 잠복 버그인 이유divide(a, b)처럼 반올림 없이 쓴 코드는 나누어떨어지는 값에서는 아무 문제 없이 돌아간다. 개발·테스트 데이터가 100 / 4처럼 딱 떨어지면 전부 통과하고, 운영에서 3으로 나누는 케이스가 들어오는 순간 터진다. 그래서 팀 규칙으로 divide 호출에는 항상 스케일과 RoundingMode를 명시하도록 강제하는 편이 좋다.

반올림 모드 선택도 도메인 판단이다. HALF_UP(5는 올림)이 일반적인 감각과 맞지만, 회계·통계 영역에서는 반올림 편향을 줄이는 HALF_EVEN(5는 짝수 쪽으로)을 쓰기도 한다. 부가세나 수수료는 절사할지 올림할지가 계약서에 적혀 있는 경우가 많으므로 그 문서를 따라야 한다.

TreeSet·TreeMap을 쓰면 해결되는 것 아닌가요?함정동작은 하는데, 대신 다른 계약을 깬다

스케일 문제는 실제로 사라진다. 정렬 기반 컬렉션은 equals/hashCode가 아니라 compareTo(또는 주입한 Comparator)로 중복을 판정하기 때문이다.

Set<BigDecimal> hashSet = new HashSet<>();
hashSet.add(new BigDecimal("100.00"));
hashSet.add(new BigDecimal("100"));
System.out.println(hashSet.size());   // 2  — equals 기반이라 둘 다 들어간다

Set<BigDecimal> treeSet = new TreeSet<>();
treeSet.add(new BigDecimal("100.00"));
treeSet.add(new BigDecimal("100"));
System.out.println(treeSet.size());   // 1  — compareTo 기반이라 같은 값으로 본다
System.out.println(treeSet);          // [100.00]   먼저 들어온 쪽이 남는다

여기에 트레이드오프가 붙는다. TreeSet은 이제 "정렬 순서가 equals와 일관되지 않은" 상태가 되어 Set 인터페이스의 일반 계약에서 벗어난다. 우리가 원하는 동작이긴 하지만, 그 코드를 읽는 다른 사람은 Set의 표준 동작(중복 판정이 equals 기준)을 가정한다. 그래서 왜 TreeSet인지 주석이나 타입 이름으로 드러내야 한다.

부가 비용도 말할 수 있으면 좋다. 탐색이 O(1)에서 O(log n)이 되고, 트리 노드 오버헤드가 붙으며, null을 넣을 수 없다. 더 나은 답은 "정규화된 값만 넣어서 HashSet을 그대로 쓴다"이고, TreeSet은 정규화를 강제할 수 없는 레거시 경계에서의 차선책이다.

1.0과 1.00이 섞인 리스트를 정렬하면 순서가 어떻게 되나요?가산점compareTo가 0을 돌려줄 때 정렬은 무엇을 하는가

compareTo가 0을 돌려주므로 정렬은 둘 사이에 순서를 만들지 않고, 입력 순서가 그대로 유지된다. Collections.sort/List.sort는 안정 정렬(stable sort)임이 명세로 보장되기 때문이다.

List<BigDecimal> list = new ArrayList<>(List.of(
        new BigDecimal("1.00"), new BigDecimal("1.0"), new BigDecimal("0.5")));
Collections.sort(list);
// [0.5, 1.00, 1.0]   <- 1.00과 1.0의 상대 순서는 넣은 순서 그대로

여기서 짚을 것 — 정렬 결과가 "틀리지는 않았지만 재현 가능하지도 않다"는 점이다. 데이터가 들어온 순서가 바뀌면 출력도 바뀐다. 금액 목록을 정렬해 화면에 뿌리거나 페이지네이션 커서로 쓰는 자리라면 이것만으로 같은 조건에 다른 결과가 나올 수 있으므로, thenComparing으로 id 같은 확정적 2차 정렬 키를 붙여야 한다.

참고로 equals는 여전히 false지만 정렬은 정상이라는 이 조합이, 4절에서 말한 "값 비교 쪽을 살린 선택"의 결과물이다.

같은 리스트인데 contains는 못 찾고 binarySearch는 찾습니다. 왜죠?가산점두 메서드가 서로 다른 판정 기준을 쓴다

List.contains는 equals로, Collections.binarySearch는 compareTo로 판정하기 때문이다. 같은 자료구조를 놓고 기준이 두 개인 셈이다.

List<BigDecimal> sorted = List.of(new BigDecimal("100.00"));

sorted.contains(new BigDecimal("100"));                // false  (equals 기준)
Collections.binarySearch(sorted, new BigDecimal("100"));  // 0  = 찾음 (compareTo 기준)

이 대비가 이 문서 전체의 축소판이다. "이 값이 컬렉션 안에 있는가"라는 같은 질문에 대해 JDK의 두 API가 다른 답을 낸다. 어느 쪽도 버그가 아니고, 애초에 두 종류의 동등성이 존재한다는 사실이 표면으로 올라온 것뿐이다.

그래서 코드를 읽을 때 "이 API는 equals파인가 compareTo파인가"를 항상 물어야 한다. equals파: HashSet·HashMap·List.contains·indexOf·remove(Object)·distinct(). compareTo파: TreeSet·TreeMap·sort·binarySearch·max/min.

테스트에서 assertEquals(new BigDecimal("100"), actual)이 실패합니다.함정"테스트가 틀린" 경우와 "코드가 틀린" 경우를 구분해야 한다

JUnit의 assertEquals는 이름 그대로 equals로 판정하므로, 값이 맞아도 스케일이 다르면 실패한다. 실패 메시지도 expected: <100> but was: <100.00>처럼 눈으로는 같아 보이는 형태라 한참 헤맨다.

이렇게 쓰면 스케일에 걸린다

assertEquals(new BigDecimal("100"), actual);
// expected: <100> but was: <100.00>

값만 보고 싶으면

// AssertJ
assertThat(actual).isEqualByComparingTo("100");
// JUnit만 쓴다면
assertEquals(0, actual.compareTo(new BigDecimal("100")));
그런데 무조건 isEqualByComparingTo로 바꾸는 것이 정답은 아니다스케일 자체가 명세인 자리도 있다. "저장 금액은 항상 소수점 2자리"가 요구사항이라면, equals로 검증해서 scale까지 고정하는 것이 오히려 맞다. 판단 기준은 하나 — 그 테스트가 검증하려는 것이 "값"인가 "표현"인가. 값이면 compareTo, 표현 명세면 equals 또는 assertThat(actual.scale()).isEqualTo(2)를 함께 쓴다.

덧붙일 만한 실무 포인트 — 이 테스트가 통과하도록 프로덕션 코드에 setScale을 끼워 넣는 것은 최악이다. 테스트를 맞추려고 도메인 계산 규칙을 바꾼 것이기 때문이다. 정규화는 경계에서 정책으로 하고, 테스트는 그 정책을 검증해야 한다.

stream().distinct()나 Collectors.groupingBy의 키로 쓰면 어떻게 되나요?가산점둘 다 어느 파인지 떠올려 본다

둘 다 equals/hashCode파라서 6절의 버그가 그대로 재현된다.

  • distinct() — equals 기준으로 중복을 제거하므로 100과 100.00이 둘 다 살아남는다.
  • Collectors.groupingBy — 내부가 HashMap이므로 같은 금액이 두 개의 그룹으로 쪼개진다. 금액별 집계 리포트가 합계는 맞는데 행 수가 이상한 형태로 틀어진다.
  • Collectors.toSet()도 HashSet이므로 같다.

증상이 특히 고약한 이유는 합계·평균 같은 숫자 집계는 정상이기 때문이다. sum()은 add로 더하니 값이 맞고, "그룹 개수"·"중복 제거 결과"만 조용히 틀린다. 대시보드에서 총액은 맞는데 건수가 안 맞는 전형적인 형태다.

회피는 동일하다 — 스트림에 넣기 전에 스케일을 통일하거나, 애초에 Money 값 객체로 감싸서 흘린다. 급하다면 groupingBy(m -> m.setScale(2, HALF_UP))처럼 키 추출 함수에서 정규화하는 방법도 있지만, 그건 같은 정규화를 여러 곳에 흩뿌리는 선택임을 알고 써야 한다.

JPA 엔티티의 equals/hashCode에 금액 필드를 넣어도 되나요?시니어 변별DB를 한 번 왕복하면 무슨 일이 생기는지

넣지 않는 것이 기본이고, BigDecimal이면 이유가 하나 더 붙는다.

일반 원칙부터 — 엔티티의 equals/hashCode는 가변 필드가 아니라 비즈니스 키(또는 식별자)로 구성한다. 값이 바뀌는 필드를 넣으면 HashSet에 넣어 둔 엔티티의 해시가 도중에 변해 그 원소를 다시는 찾지 못하게 된다.

BigDecimal 고유의 문제는 "DB 왕복"이다. 저장 전 인스턴스의 금액은 코드에서 만든 100(scale 0)인데, 같은 행을 다시 읽어 오면 NUMERIC(19,2) 정의에 따라 100.00(scale 2)이 된다. 같은 데이터인데 equals가 false가 되는 것이다.

저장 전 객체 amount = 100 (scale 0) | INSERT -> NUMERIC(19,2) v 다시 읽은 객체 amount = 100.00 (scale 2) before.equals(after) -> false 같은 행인데도

이 차이가 1차 캐시가 없는 경로(새 트랜잭션, 캐시 역직렬화, DTO 비교, 테스트의 저장-조회 비교)에서 드러난다. 테스트에서 "저장한 것과 읽은 것이 같은지"를 equals로 검증하면 여기서 깨진다.

대응은 이 문서의 결론과 같다 — 금액 필드를 @Embeddable Money로 만들고 생성자에서 scale을 통일해 두면, 어느 경로로 만들어진 객체든 항상 같은 scale이라 이 문제가 구조적으로 사라진다. 그리고 엔티티 동등성은 여전히 식별자 기준으로 두는 편이 안전하다.

금액을 long(원 단위 정수)으로 다루면 이 문제가 다 사라지지 않나요?시니어 변별사라지는 것과 새로 생기는 것을 둘 다 말해야 한다

맞다. 사라진다. 다만 문제를 없앤 게 아니라 옮긴 것이라는 인식이 있어야 한다.

얻는 것

  • 스케일 개념 자체가 없다. equals·hashCode·== 전부 안전하고, Map 키로 써도 된다.
  • 연산이 CPU 정수 연산이라 빠르고 객체 할당이 없다.
  • DB도 BIGINT라 부동소수점이 끼어들 여지가 없다.

새로 생기는 것

  • 단위가 타입에 안 적힌다. long amount가 원인지 전(錢)인지 센트인지는 사람이 기억해야 한다 — 이게 가장 큰 위험이다.
  • 나눗셈 정책을 직접 짜야 한다. 할인율·이자·환율에서 반올림을 손으로 구현하게 된다.
  • 통화별 소수 자릿수가 다르다. 원·엔은 0자리, 달러·유로는 2자리, 일부 중동 통화는 3자리다. 다통화면 "최소 화폐 단위"를 통화와 함께 들고 다녀야 한다.
  • 오버플로가 조용하다. BigDecimal은 자릿수 제한이 없지만 long은 넘치면 음수로 뒤집힌다.

실무 판단은 이렇게 정리한다. 단일 통화(원화)이고 소수 금액이 없는 시스템이라면 long 기반이 단순하고 안전하다. 다통화·이자·세금 계산이 있는 시스템이면 BigDecimal을 Money 안에 가두는 쪽이 낫다.

어느 쪽을 고르든 결론은 같다 — 원시 타입을 도메인에 날것으로 노출하지 않고 Money라는 한 타입에 가둔다

덧붙이면, long을 고르더라도 Money 값 객체는 여전히 필요하다. 단위와 통화를 타입으로 표현해야 "센트를 원에 더하는" 사고를 컴파일 타임에 막을 수 있기 때문이다.

String의 == 함정이나 Integer 캐시 함정과는 뭐가 다른가요?핵심"한 단계 더 깊다"는 것이 답의 뼈대

앞의 둘은 equals로 옮기면 끝나지만, BigDecimal은 equals로 옮겨도 안 끝난다. 그게 결정적 차이다.

함정무엇을 잘못 물었나해결
String s1 == s2참조를 물었다 (값을 물어야 했다)equals로 바꾸면 끝
Integer a == b참조를 물었다 (값을 물어야 했다)equals로 바꾸면 끝
BigDecimal a.equals(b)표현을 물었다 (값을 물어야 했다)equals가 이미 정답인데도 틀림 → compareTo

뿌리는 같다 — 셋 다 "같다"에 여러 층위가 있는데 코드가 그중 하나만 고른다는 문제다. ==는 동일성(identity), equals는 상태 동등성(state equality), compareTo == 0은 값 동등성(value equality)이다. BigDecimal은 상태와 값이 갈라지는 드문 타입이라 세 번째 층이 필요해진 것이다.

위험의 성질도 한 단계 더 나쁘다. Integer 캐시 버그는 "값이 작으면 우연히 맞는" 형태라 큰 값에서 재현이라도 된다. BigDecimal 스케일 버그는 같은 값에서도 어느 경로로 만들어졌느냐에 따라 갈리므로, 값을 키워도 재현되지 않고 "DB를 한 번 거쳤는가"라는 코드 밖 조건에 달려 있다.

외울 문장 — ==는 참조를, equals는 표현을, compareTo는 값을 묻는다
금액 타입을 팀 표준으로 정한다면 어떻게 설계하시겠습니까?시니어 변별"compareTo를 씁시다"라는 규칙으로는 부족하다는 인식에서 출발

"compareTo를 씁시다"라는 규칙만 정하는 것으로는 부족하다는 인식에서 출발해야 한다. 사람이 매번 기억해야 하는 규칙은 반드시 새는데, 이 버그는 새도 티가 안 나기 때문이다. 그래서 틀린 코드를 애초에 쓸 수 없게 만드는 쪽으로 설계한다.

(1) 금액 전용 값 객체를 만들고 BigDecimal을 그 안에 가둔다.

public record Money(BigDecimal amount, Currency currency) {
    private static final int SCALE = 2;

    public Money {
        // 경계 정규화: 어떤 경로로 들어온 값이든 여기서 스케일이 통일된다.
        amount = amount.setScale(SCALE, RoundingMode.HALF_UP);
    }

    public boolean isSameAmount(Money other) {
        // 밖으로는 compareTo 기반 비교만 노출한다.
        return currency.equals(other.currency)
            && amount.compareTo(other.amount) == 0;
    }

    public boolean isZero() { return amount.signum() == 0; }

    public Money plus(Money other) { /* 통화 검증 후 더한다 */ }
}

정규화를 생성자에 두는 것이 핵심이다. Money 객체는 만들어지는 순간 항상 scale 2이므로, record가 자동 생성한 equals/hashCode도 그대로 안전해진다. HashMap 키로 써도 되고 Set에 넣어도 된다. "값 비교는 compareTo"라는 규칙이 타입 안으로 흡수되어 사라진 것이다.

(2) 경계를 한 겹으로 좁힌다. 정규화가 의미를 가지려면 Money를 거치지 않고 금액이 들어오는 경로가 없어야 한다. JPA 컨버터나 @Embeddable로 DB 경계를, 커스텀 역직렬화로 API 경계를 막는다. 경계가 여러 곳이면 정규화도 여러 곳에서 새고, 그러면 처음 문제로 돌아간다.

(3) 스케일과 반올림 정책을 도메인 규칙으로 명시한다. 저장 스케일(원화 0, 달러 2), 나눗셈 자릿수와 RoundingMode, 부가세·수수료 절사 규칙을 정책 문서에서 가져와 상수 한 곳에 모은다. 여기저기 흩어진 setScale(2, HALF_UP)은 정책이 바뀔 때 전부 찾아 고쳐야 한다.

(4) DB 컬럼 타입을 맞춘다. 금액은 NUMERIC(19, 2)처럼 정밀도와 스케일을 명시한 NUMERIC으로 잡는다. double precision이나 real로 잡으면 부동소수점 오차가 저장 계층에서 생기므로 애플리케이션이 아무리 BigDecimal을 써도 소용없다.

(5) 정적 분석으로 잔여 경로를 막는다. 그래도 BigDecimal을 직접 써야 하는 자리는 남으므로, ErrorProne의 BigDecimalEquals 같은 규칙을 CI에서 켜 equals 사용을 빌드 실패로 잡는다.

트레이드오프까지 말해야 답이 닫힌다Money 타입을 도입하면 초반에 변환 코드가 늘고, 이미 BigDecimal이 시그니처에 박혀 있는 레거시에서는 경계 어댑터가 필요하다. 그래서 현실적인 순서는 신규 도메인부터 Money를 쓰고, 레거시는 정적 분석으로 equals만 먼저 막은 뒤 점진적으로 흡수하는 것이다.

BigDecimal은 값을 unscaledValue와 scale 두 개로 나눠 들고 있어 1.0은 (10, 1), 1.00은 (100, 2)로 객체 상태가 실제로 다르므로, equals가 false인 것은 계약을 지킨 결과이고 수학적 값 비교는 compareTo(...) == 0(0 판정은 signum() == 0)의 몫이다 — 문제는 hashCode도 스케일을 반영해 HashSet·HashMap에서 다른 버킷으로 갈라지는데 거기서는 비교 방식을 바꿔 낄 수조차 없다는 것이므로, DB NUMERIC(19,2)·setScale·산술 연산·double 생성자로 스케일이 어긋나기 전에 경계에서 스케일을 통일한 금액 값 객체로 가두는 것이 정공법이다.
