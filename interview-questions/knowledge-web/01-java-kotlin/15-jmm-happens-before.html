happens-before — "먼저 실행된다"가 아니라 "반드시 보인다"
시간에 대한 진술이 아니라 가시성과 순서 관측에 대한 보장이다. 이름을 다시 짓는다면 is-visible-to.

면접 질문: "Java Memory Model에서 happens-before 관계란 무엇인가요?"

핵심 관전 포인트 — happens-before는 시간 순서가 아니라 가시성 보장이다. "A happens-before B"는 "A가 시계상 먼저 실행된다"는 뜻이 아니라 "A에서 한 모든 메모리 쓰기가 B에서 반드시 보인다"는 뜻이며, 이 오해를 깨는 것이 이 질문의 절반이다. 나머지 절반은 왜 이런 규칙이 필요한가다 — CPU 캐시와 컴파일러·CPU의 재배치 때문에 스레드 간 가시성은 기본적으로 보장되지 않고, 하드웨어마다 그 규칙마저 다르기 때문에, 자바는 "어떤 하드웨어에서 돌아도 이만큼은 보장한다"는 최소선을 JMM(Java Memory Model)이라는 언어 차원의 명세로 정의했다. happens-before는 그 최소선을 표현하는 언어이고, 프로그램 순서·모니터 락·volatile·start/join 규칙이 이 관계를 만들며, 이행성으로 이어 붙여 안전 발행(safe publication)을 완성한다. 이 관계가 없는 공유 접근이 곧 데이터 레이스다.
  • 1
    시간이 아니라 가시성입니다. "A happens-before B"는 A가 수행한 모든 메모리 쓰기가 B에서 반드시 보이고, 두 연산의 순서가 B의 관점에서 뒤집혀 관측되지 않는다는 뜻입니다. 시계상 먼저 실행됐다는 사실은 아무 보장도 만들지 않습니다. 이름을 다시 짓는다면 is-visible-to에 가깝습니다.
  • 2
    왜 언어 차원의 명세가 필요하냐면, CPU가 코어별 캐시로 일하고 컴파일러·CPU가 순서를 재배치하는데 그 재배치를 어디까지 허용하는지가 아키텍처마다 다르기 때문입니다. 그래서 자바는 "어떤 CPU에서 돌아도 이만큼은 보장한다"는 최소선을 JMM으로 못 박고, JVM이 각 하드웨어에 맞는 메모리 배리어로 번역합니다.
  • 3
    이 관계는 저절로 생기지 않고 정해진 규칙에서만 생깁니다. 프로그램 순서, 모니터 락(같은 락의 unlock HB lock), volatile(같은 변수의 write HB read), start()/join() — 그리고 이행성으로 이어 붙이면 volatile 하나가 일반 변수 여럿을 실어 나르는 안전 발행이 됩니다. 이 관계 없이 공유 변수를 건드리는 것이 데이터 레이스이고, 그 결과에 대해 JMM은 아무것도 보장하지 않습니다.

0. 질문 + 출제 의도 · 겨냥하는 약점

질문 — "Java Memory Model에서 happens-before 관계란 무엇인가요?"

출제 의도 — 동시성 코드의 정확성을 "돌려보니 되던데요"가 아니라 규칙으로 논증할 수 있는지를 본다. 이게 되는 사람만 lock-free 코드나 AI가 생성한 동시성 코드를 검증할 수 있다. 동시성 버그는 테스트로 잡히지 않는다 — 재현이 안 되는 것이 정상이기 때문에, 코드를 읽고 "여기에 어떤 규칙이 걸려 있는가"를 말할 수 있어야 한다.

약점 A이름 그대로 시간 순서로 읽는다 — "A가 먼저 실행되니까 B에서 보이겠죠". 그러면 "시계상 먼저인데도 안 보이는" 사례를 설명하지 못한다(4절).
약점 B규칙 목록을 대지 못하고 도구 이름만 댄다 — "volatile 쓰면 됩니다". 관계가 어디서 생기는지를 모르면 "같은 락", "같은 변수"라는 조건이 빠진 코드를 안전하다고 판단한다(5·7절).
약점 C이행성으로 논증하지 못한다 — "data에는 volatile이 없는데 왜 42가 보이나요?"에서 막힌다. 실무에서 happens-before가 쓸모 있어지는 이유의 전부가 여기 있다(10절).
약점 D가시성과 원자성을 한 덩어리로 본다 — "happens-before가 있으니 count++도 안전하겠죠". 보이느냐와 끼어들 수 있느냐는 별개의 축이다(15절).
합격선"시간이 아니라 가시성입니다. A의 모든 쓰기가 B에서 반드시 보인다는 뜻이고, 이 관계는 프로그램 순서·같은 락의 unlock/lock·같은 변수의 volatile write/read·start/join에서만 생기며, 이행성으로 이어 붙인 것이 안전 발행입니다." — 여기에 데이터 레이스의 정의까지 붙이면 완결된다.
14번 문서와의 분담 volatile이 가시성은 주지만 원자성은 주지 않는다는 이야기는 14번(volatile 가시성 vs 원자성)이 본체다. 이 문서는 그 위층 — "그 가시성 보장은 대체 무슨 규칙에서 나오는가", 즉 happens-before 규칙 체계에 집중한다. volatile은 여기서 여덟 규칙 중 하나로만 등장한다.

1. 전제 ① 가시성 — 쓴 값이 안 보일 수 있다

// 스레드 A                        // 스레드 B
sharedFlag = true;                 while (!sharedFlag) { }   // 영원히 안 끝날 수 있다

이 코드가 안 끝날 수 있다는 말은 처음 들으면 납득이 안 된다. 같은 프로세스, 같은 변수인데 왜 안 보인다는 말인가. 원인은 둘이고, 둘 다 "버그"가 아니라 정상 동작이다.

2. 전제 ② 재배치 — 순서가 뒤집혀 보일 수 있다

컴파일러와 CPU는 성능을 위해 명령의 실행 순서를 바꾼다. 다만 지켜야 할 선이 하나 있다 — 단일 스레드에서 관측되는 결과가 같기만 하면 순서를 바꿔도 된다.

두 전제를 한 문장으로 — 이 둘이 happens-before가 존재하는 이유다

가시성 (1절)

  • 코어별 캐시 + JIT 레지스터 재사용
  • 쓴 값이 언제 보일지, 보이기는 할지 보장 없음

재배치 (2절)

  • 단일 스레드 결과만 같으면 순서 변경 자유
  • 다른 스레드에게는 순서가 뒤집혀 관측됨

그래서 happens-before는 이 둘을 한꺼번에 막는 보장으로 정의된다 — "A의 쓰기가 B에서 보인다(가시성) + 그 순서가 뒤집혀 관측되지 않는다(재배치)". 정의에 두 문장이 붙어 있는 이유가 여기 있다.

3. 왜 언어 차원의 명세인가 — 하드웨어마다 규칙이 다르다

여기까지가 "왜 동기화가 필요한가"인데, JMM이 왜 존재하는지는 한 걸음 더 들어가야 나온다. 재배치를 어디까지 허용하는지가 CPU 아키텍처마다 다르기 때문이다.

"제 노트북에선 잘 되는데요"가 통하지 않는 진짜 이유 가산점 x86 계열은 메모리 순서 규칙이 비교적 엄격해서 쓰기와 쓰기 사이의 순서를 잘 뒤집지 않는다. 반면 ARM 계열은 훨씬 느슨해서 같은 코드가 훨씬 자유롭게 재배치된다. 그래서 동기화가 빠진 똑같은 코드가 개발자의 x86 장비에서는 몇 년째 멀쩡히 돌다가, ARM 기반 서버로 옮기는 순간 터지는 일이 실제로 벌어진다. 로컬은 x86, 운영은 ARM 인스턴스라면 남 얘기가 아니다.

4. happens-before의 정확한 뜻 — 이 오해부터 깬다

이름이 오해를 부른다. happens-before를 직역하면 "먼저 일어난다"이므로 십중팔구 시간 순서로 읽게 된다. 그 독해가 틀렸다.

DEFINITION
연산 A happens-before 연산 B라는 것은,
A가 수행한 모든 메모리 쓰기가 B에서 반드시 보이고,
A와 B의 순서가 B의 관점에서 뒤집혀 관측되지 않는다는 뜻이다.
즉 시간에 대한 진술이 아니라 가시성과 순서 관측에 대한 보장이다. 정의에 문장이 두 개인 이유는 1절(가시성)과 2절(재배치)을 한꺼번에 막아야 하기 때문이다.
오해 ① "시계상 먼저 실행되면 happens-before다"

틀렸다. 스레드 A가 밀리초 단위로 먼저 data = 42를 실행했더라도, 규칙이 하나도 걸려 있지 않으면 B는 그 42를 영영 못 볼 수도 있다.

시간은 보장을 만들지 않는다.

오해 ② "happens-before면 시계상 먼저 실행된다"

이것도 정확한 진술이 아니다. JMM이 요구하는 것은 "그렇게 보인다"이지 "실제로 그 순서로 실행된다"가 아니다.

JVM과 CPU는 보장만 지켜진다면 내부적으로 얼마든지 재배치한다.

굳이 이름을 다시 짓는다면 is-visible-to(에게 보인다) 쪽이 실체에 가깝다.
면접에서 이 한 줄을 먼저 말하고 시작하면 나머지 설명이 전부 제자리를 찾는다.

성질 하나 더 — happens-before는 부분 순서(partial order)다

모든 연산 쌍에 순서가 정해져 있는 게 아니라, 5절의 규칙에 해당하는 쌍에만 관계가 생긴다. 관계가 없는 두 연산은 서로에게 어떤 순서로든 보일 수 있고, 그 상태가 곧 데이터 레이스다(13절).

그래서 동시성 코드를 검증한다는 것은 이 그래프에서 간선을 찾는 일이 된다. 찾지 못하면 그 코드는 테스트가 통과했더라도 틀린 코드다.

5. 규칙 목록 — 관계는 여기서만 생긴다

happens-before 관계는 저절로 생기지 않는다. JLS §17.4.5가 정한 규칙에 해당할 때만 생긴다. 목록을 먼저 통째로 보고, 다음 절부터 하나씩 코드와 짝지어 본다.

규칙에 붙은 두 글자 조건 — 이게 빠지면 전부 무효다

모니터 락 = 같은 락

  • 인스턴스 메서드는 this, static 메서드는 클래스 객체 → 다른 락
  • 락 필드를 재대입하면 관계가 끊긴다 → 락 필드는 final

volatile = 같은 변수

  • 서로 다른 volatile 변수 사이에는 아무 관계도 없다
  • "둘 다 volatile이니까 괜찮겠지"가 대표적인 오답

6. 프로그램 순서와 그 함정

한 스레드 안에서는 코드에 먼저 나온 연산이 뒤에 나온 연산보다 happens-before다.

이 규칙만 보면 "그럼 재배치는 안 일어나는 것 아닌가" 싶지만 아니다. 이 보장은 그 스레드 자신의 관점에서만 유효하다. 재배치는 여전히 일어나며, 단지 그 스레드 혼자 볼 때 결과가 코드 순서와 같을 뿐이다.

7. 모니터 락 — unlock HB 그 다음 lock

synchronized 블록을 빠져나가는 것(unlock)이, 같은 락 객체에 대한 이후의 진입(lock)보다 happens-before다.

락이 상호배제만 하는 도구라고 생각하면 이 규칙을 놓친다. 락은 상호배제와 가시성 두 가지를 함께 제공한다. A가 락 안에서 한 모든 쓰기는, 그 락을 이어받은 B에게 전부 보인다.

문제 두 스레드가 서로 다른 락을 잡는다
private final Object lockA = new Object();
private final Object lockB = new Object();
private int data = 0;

void writer() { synchronized (lockA) { data = 42; } }락 A
void reader() { synchronized (lockB) { print(data); } }락 B

// 둘 다 synchronized 를 썼으니 안전해 보이지만,
// 락 객체가 다르므로 unlock HB lock 이 성립하지 않는다.
// reader 는 0 을 볼 수 있다.
// 상호배제도 안 된다 — 서로 다른 문이라 동시에 들어간다.
개선 같은 락으로 묶어야 관계가 생긴다
private final Object lock = new Object();
private int data = 0;


void writer() { synchronized (lock) { data = 42; } }같은 락
void reader() { synchronized (lock) { print(data); } }같은 락

// writer 의 unlock HB reader 의 lock 이 성립한다.
// → data = 42 가 reader 에서 반드시 보인다.
// 락 필드를 final 로 두는 이유도 여기 있다 —
// 중간에 재대입되면 "같은 락"이 아니게 된다.
실무에서 실제로 나오는 형태 — 인스턴스 락 vs static 락 여러 메서드에 synchronized를 붙였는데 어떤 것은 인스턴스 메서드(락 = this)이고 어떤 것은 static 메서드(락 = 클래스 객체)인 경우가 대표적이다. 코드만 보면 둘 다 동기화된 것처럼 보이지만 둘은 서로 다른 락이므로 아무 관계도 만들지 못한다. 공유 상태가 static 필드인데 보호는 인스턴스 락으로 하고 있다면, 인스턴스가 두 개만 돼도 방어선이 사라진다.

8. volatile — 쓰기 HB 그 다음 읽기

volatile 변수에 대한 쓰기가, 같은 변수에 대한 이후의 읽기보다 happens-before다.

락 없이 happens-before를 만들 수 있는 가장 가벼운 수단이다. 상호배제는 주지 않고 가시성과 순서만 준다.

문제 ready에 volatile이 없다
int data = 0;
boolean ready = false;일반 필드

// 스레드 A                   // 스레드 B
data = 42;                    if (ready)        // true 를 볼 수도 있는데
ready = true;                     print(data);  // data 는 0 일 수 있다

// 두 스레드를 잇는 규칙이 하나도 없다 → 데이터 레이스
개선 volatile 하나가 다리를 놓는다
int data = 0;                    // volatile 이 아니어도 된다
volatile boolean ready = false;다리

// 스레드 A                   // 스레드 B
data = 42;                    if (ready)        // true 를 봤다면
ready = true;                     print(data);  // 반드시 42

// 다리 역할을 하는 것은 volatile 변수 하나뿐이다
이 패턴의 묘미 — data에 volatile이 없는데도 42가 보장된다 모든 공유 변수에 volatile을 붙일 필요가 없다. 다리 하나만 volatile이면 그 앞에 쓴 일반 변수들이 함께 건너간다. 근거는 이행성이고, 그 유도가 다음 절(10절)에 있다. 면접에서 "왜 data는 volatile이 아니어도 되나요?"라는 반문이 나오면 정확히 이 지점을 묻는 것이다.
경계 긋기 — volatile은 원자성을 주지 않는다 14번 문서 volatile int count의 count++는 여전히 깨진다. 읽기 → +1 → 쓰기 세 단계 사이에 다른 스레드가 끼어드는 것을 volatile은 막지 않기 때문이다. 이 주제의 본체는 14번(volatile 가시성 vs 원자성)이다. 이 문서에서는 "happens-before는 보이느냐에 대한 보장이지 끼어들 수 있느냐에 대한 보장이 아니다"라는 경계만 정확히 잡고 간다(15절).

9. start() / join() — 스레드 경계를 건너는 기본 통로

thread.start() 호출 이전의 모든 연산 HB 새 스레드 안의 모든 연산
스레드 안의 모든 연산 HB 그 스레드에 대한 join()의 반환

둘은 방향만 반대인 한 쌍이다. start()는 부모가 준비한 데이터를 자식에게 내려보내는 통로, join()은 자식이 만든 결과를 부모가 받아오는 통로다.

개선 join()이 결과의 가시성까지 보장한다
Worker w = new Worker();
Thread t = new Thread(w);
t.start();
t.join();HB 규칙
print(w.result);   // 워커가 채운 result 가 반드시 보인다
                   // result 가 volatile 이 아니어도 된다
문제 직접 기다리면 그 보장이 사라진다
t.start();
while (t.isAlive()) { }끝난 건 안다
print(w.result);       // 가시성을 보장하는 규칙이 없다

t.start();
Thread.sleep(1000);더 나쁨
print(w.result);       // 끝났다는 보장조차 없다

"끝난 것을 아는 것"과 "그 결과가 보이는 것"은 별개다

대기 수단종료 감지happens-before비고
t.join()○○ 명세에 명시스레드 안의 모든 연산 HB join 반환
future.get()○○ 명세에 명시태스크 안의 모든 연산 HB get 반환
latch.await()○○ 명세에 명시countDown() 이전 연산 HB await 반환

while (t.isAlive()) {}○✕ 없음결과 필드 읽기가 데이터 레이스가 된다
Thread.sleep(1000)✕✕ 없음둘 다 잃는다 — 최악의 선택

문서화된 대기 수단을 쓰라는 실무 규율의 근거가 이 표다. "이쯤이면 끝났겠지"는 규칙이 아니다.

흔한 오해 — start() 규칙은 "호출 이전"에만 적용된다 이 규칙은 start() 호출 이전의 쓰기에만 적용된다. start() 이후에 부모가 바꾼 값은 이 규칙과 무관하며, 그건 다시 일반적인 가시성 문제다. 스레드를 띄워 놓고 나중에 필드를 바꿔 신호를 주려는 코드는 별도의 다리(volatile 또는 락)가 필요하다.

10. 이행성 — 규칙들을 이어 붙이는 접착제

A HB B 이고 B HB C 이면 A HB C 다.

목록의 마지막 줄에 붙은 한 줄짜리 규칙이지만, 실무에서 happens-before가 쓸모 있어지는 이유의 전부가 여기 있다. 앞의 규칙들은 각각 특정 지점 하나만 연결하는데, 이행성이 그것들을 이어 붙여 스레드를 가로지르는 긴 다리를 만든다.

int data = 0; // 일반 변수 (volatile 아님) volatile boolean ready = false; // 스레드 A // 스레드 B data = 42; // ① if (ready) { // ③ ready = true; // ② print(data); // ④ 반드시 42 } ① HB ② : 프로그램 순서 (같은 스레드 A 안, ①이 코드상 먼저) ② HB ③ : volatile 규칙 (같은 변수 ready 에 대한 쓰기 → 읽기) ③ HB ④ : 프로그램 순서 (같은 스레드 B 안, ③이 코드상 먼저) ────────────────────────────────────────────────────────── ∴ ① HB ④ : 이행성으로 연결 → data = 42 가 ④에서 반드시 보인다

면접에서 그대로 쓸 수 있는 논증 템플릿 — 4줄

동시성 코드의 정확성을 물으면 이 4줄 구조로 답한다. 규칙 이름을 붙이는 것이 핵심이다.

1발행하는 쪽의 프로그램 순서 — "일반 쓰기들 HB 동기화 쓰기"프로그램 순서
2스레드를 건너는 다리 — "volatile write HB 같은 변수의 read" 또는 "unlock HB 같은 락의 lock"락 / volatile
3받는 쪽의 프로그램 순서 — "동기화 읽기 HB 일반 읽기들"프로그램 순서
4이행성으로 연결 — "∴ 발행 쪽의 모든 쓰기가 받는 쪽에서 보인다"이행성

synchronized도 구조가 완전히 같다. unlock 이전의 모든 쓰기가 같은 락의 lock 이후에 전부 보인다. 다리를 놓는 도구가 volatile이냐 락이냐만 다르다.

11. java.util.concurrent가 대신 놓아주는 다리

이 패키지의 클래스들은 API 문서에 자신이 제공하는 happens-before를 명시한다. 이것이 중요한 이유는 직접 volatile이나 락을 쓰지 않아도 이 클래스들을 통과하는 것만으로 다리가 놓인다는 뜻이기 때문이다.

실무 결론 — 직접 다리를 놓기 전에 이미 놓인 다리를 찾는다 생산자-소비자 구조를 BlockingQueue로 짜면 큐에 넣는 객체에 volatile을 붙일 필요가 없다. 마찬가지로 스레드 풀·래치·세마포어·ConcurrentHashMap 모두 문서에 보장이 적혀 있다. "이 클래스가 어떤 happens-before를 준다고 문서에 적혀 있는가"를 확인하는 습관이 직접 volatile을 배치하는 것보다 안전하다.

12. 안전 발행 — 다리 놓기 패턴

10절에서 본 구조에는 이름이 있다. 안전 발행(safe publication) — 완성된 데이터를 다른 스레드가 반쪽짜리로 보지 않게 넘기는 것이다.

일반 변수들에 값을 다 채워 넣은 다음, 마지막에 동기화 연산(volatile 쓰기 또는 unlock)을 한다.
받는 쪽은 그 동기화 연산(volatile 읽기 또는 lock)을 먼저 통과한 뒤 데이터를 읽는다.

암기 — 객체를 안전하게 발행하는 방법 넷

① static 초기화로 만든다
클래스 초기화가 JVM에 의해 동기화된다. 가장 단순하고 가장 안전한 발행.
② volatile 필드 / AtomicReference 에 대입
쓰기 HB 읽기 규칙이 붙는다. 참조를 바꿔야 하는 경우의 기본형.
③ final 필드에 대입
happens-before 규칙은 아니지만 별도의 보장이 있다(14절). 불변 객체의 근거.
④ 락으로 보호되는 필드에 대입
또는 ConcurrentHashMap 같은 스레드 안전 컬렉션에 넣는다.

넷 중 어느 것도 안 쓰고 그냥 일반 필드에 대입해 다른 스레드에 넘기는 것이 불안전 발행(unsafe publication)이고, 받는 쪽은 반쪽짜리 객체를 볼 수 있다.

13. 다리가 없으면 — 데이터 레이스의 정확한 정의

14. final 필드의 특별 보장

final은 happens-before 규칙 목록에 없는데도 안전 발행의 수단으로 쓰인다. 별도의 보장이 따로 있기 때문이다.

FINAL FIELD SEMANTICS
객체의 생성자가 정상적으로 끝나면, 그 객체의 final 필드에 생성자에서 넣은 값은
다른 스레드에게도 완성된 상태로 보인다.
그 객체의 참조를 어떤 방식으로 넘겨받든, 심지어 동기화 없이 넘겨받아도 그렇다. 불변 객체가 동기화 없이 안전하게 공유되는 근거가 정확히 이것이다.
문제 생성자에서 this가 새어 나간다
public final class Money {
    private final long amount;
    private final String currency;

    public Money(long amount, String currency) {
        REGISTRY.add(this);      // ← this 탈출
        this.amount = amount;   // 아직 안 채워졌다
        this.currency = currency;
    }
}
// 다른 스레드가 REGISTRY 에서 이 객체를 꺼내면
// amount == 0, currency == null 인 상태를 볼 수 있다.
// final 을 붙였는데도 보장이 무너진 경우다.
개선 생성자는 자기 필드만 채우고 끝낸다
public final class Money {
    private final long amount;final
    private final String currency;final

    public Money(long amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }                            // 여기서 값이 확정된다
}
// 등록이 필요하면 생성 이후 팩토리 메서드에서 한다:
//   Money m = new Money(...); REGISTRY.add(m);
// 이 객체의 참조를 어떤 방식으로 넘겨도 반쪽짜리로 보이지 않는다.

16. 실전 연결 — ConcurrentHashMap의 무락 읽기

13번 문서에서 본 "get이 락 없이도 안전한 이유"가 정확히 이 문서의 내용이다. 두 규칙이 각자 다른 일을 맡고 있다.

volatile — 값의 최신성을 맡는다

  • Node.val, Node.next, table이 volatile이다
  • → put 스레드의 쓰기 HB get 스레드의 읽기가 성립
  • → 락 없이도 최신 값이 보인다

final — 노드의 완성 상태를 맡는다

  • Node.key, Node.hash가 final이다
  • → 생성자 완료 후 안전 발행이 보장된다
  • → 갓 만들어진 노드를 다른 스레드가 발견해도 key가 null인 반쪽짜리 상태를 볼 수 없다

여기서 읽어낼 설계 감각 — "락 = 동기화"라는 등식을 깼다

락은 가시성과 상호배제를 함께 주는 도구인데, 읽기 경로에는 가시성만 필요하다. 그래서 ConcurrentHashMap은 둘을 분리했다.

volatile로 해결 — 모든 읽기 경로에 적용, 비용이 낮다

이 분리가 가능하려면 "무엇이 무엇을 보장하는가"를 규칙 수준에서 알아야 한다. 그것이 이 질문을 묻는 이유이고, lock-free 코드를 읽고 쓸 수 있느냐의 갈림길이다.

일반 쓰기들 ─ 프로그램 순서 ─▶ 동기화 쓰기(volatile write / unlock) 동기화 쓰기 ─ 다리 규칙 ─▶ 동기화 읽기(volatile read / lock) 동기화 읽기 ─ 프로그램 순서 ─▶ 일반 읽기들 ∴ 이행성으로 연결 — 발행 쪽의 모든 쓰기가 받는 쪽에서 보인다

④ 함정 여섯 — 이 중 하나라도 걸리면 그 코드는 틀렸다

1
시간 순서를 근거로 든다 — "A가 먼저 실행되니까 보이겠죠". 시간은 보장을 만들지 않는다.
2
다른 락 — 인스턴스 락과 static 락 혼용, 락 필드 재대입. synchronized를 붙였는데 얻은 게 없다.
3
다른 volatile 변수 — "둘 다 volatile이니까 괜찮겠지". 다리는 같은 변수로만 놓인다.
4
발행 이후에 데이터를 더 채운다 — 그 쓰기는 다리 위에 실리지 않는다. 발행은 마지막 줄이어야 한다.
5
isAlive() 폴링 · sleep으로 대기 — 끝난 건 알지만 결과는 안 보인다. join()·Future.get()·await()를 쓴다.
6
생성자에서 this가 샌다 — final을 붙였어도 보장이 무너진다. 생성자는 자기 필드만 채우고 끝낸다.

그리고 데이터 레이스가 있는 프로그램에 대해 JMM은 읽기 결과를 사실상 보장하지 않는다 — "가끔 이상한 값"이 아니라 "무슨 값이 나와도 명세 위반이 아니다"에 가깝다. 그래서 테스트 통과는 정확성의 근거가 아니다.

18. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼쳐서 대조한다. 막히는 항목이 곧 다시 볼 절이다.

happens-before가 "시간상 먼저 일어난다"는 뜻 아닌가요?힌트: 이름이 오해를 부른다. 양방향으로 다 틀리다 핵심

아니다. 시간에 대한 진술이 아니라 가시성에 대한 보장이다. "A happens-before B"는 "A에서 한 모든 메모리 쓰기가 B에서 반드시 보이고, 두 연산의 순서가 B의 관점에서 뒤집혀 관측되지 않는다"는 뜻이다.

양방향으로 오해가 생기므로 둘 다 짚는 것이 좋다.

  • "시계상 먼저 실행되면 happens-before다" — 틀렸다. 스레드 A가 밀리초 단위로 먼저 data = 42를 실행했더라도, 두 스레드 사이에 happens-before를 만드는 규칙이 하나도 걸려 있지 않으면 B는 그 42를 영영 못 볼 수도 있다. 캐시와 재배치가 그대로 작동하기 때문이다.
  • "happens-before면 시계상 먼저 실행된다" — 이것도 정확하지 않다. JMM이 요구하는 것은 "그렇게 보인다"이지 "실제로 그 순서로 실행된다"가 아니다. JVM과 CPU는 보장만 지켜지면 얼마든지 재배치한다.

마무리로 "이름을 다시 짓는다면 is-visible-to에 가깝습니다"라고 덧붙이면 이해했다는 신호가 된다(4절).

한 스레드 안에서는 재배치가 안 일어나나요?힌트: 프로그램 순서 규칙이 보장하는 것은 "누구의 관점"인가 함정

일어난다. 프로그램 순서 규칙은 "재배치가 없다"가 아니라 "그 스레드 혼자 볼 때 결과가 코드 순서대로 보인다"는 뜻이다.

컴파일러와 CPU는 단일 스레드의 관측 결과만 같으면 순서를 자유롭게 바꾼다. 그 재배치는 다른 스레드가 중간을 들여다볼 때 관측된다. data = 42; ready = true;가 뒤집혀 실행되면 다른 스레드는 ready == true인데 data == 0인 상태를 볼 수 있다.

그래서 스레드 사이에는 반드시 volatile이나 락으로 별도의 다리를 놓아야 한다. 프로그램 순서 규칙은 다리의 양쪽 끝을 잇는 데 쓰일 뿐, 그 자체로는 스레드 경계를 넘지 못한다(6절).

volatile 변수 하나로 일반 변수 여러 개의 가시성을 보장할 수 있는 근거는?힌트: 규칙 세 개를 이어 붙여 논증한다 시니어 변별

이행성(transitivity)이다. 말로만 "volatile이라 보입니다"가 아니라 규칙 이름을 붙여 유도할 수 있어야 한다.

① data = 42 (스레드 A) ② ready = true (스레드 A, volatile 쓰기) ③ if (ready) (스레드 B, volatile 읽기) ④ print(data) (스레드 B) ① HB ② : 프로그램 순서 ② HB ③ : volatile 쓰기 HB 같은 변수의 읽기 ③ HB ④ : 프로그램 순서 ──────────────────────────────────────── ∴ ① HB ④ : 이행성 → data = 42가 반드시 보인다

말로 옮기면 volatile 쓰기는 그 이전의 모든 쓰기를 함께 발행하고, volatile 읽기는 그 이후 읽기의 가시성 기준점이 된다. 이 패턴이 안전 발행(safe publication)이고, synchronized도 unlock/lock으로 구조가 같다.

한 걸음 더 나가면 좋은 지점이 있다. 이 보장은 "먼저 데이터를 다 채우고 마지막에 발행한다"는 순서를 지킬 때만 성립한다. 발행 이후에 데이터를 더 채우면 그 쓰기는 다리 위에 실리지 않는다. 발행이 마지막이어야 한다는 것이 이 패턴의 유일한 규율이다(12절).

데이터 레이스의 정확한 정의는 무엇인가요?힌트: 세 조건. 세 번째가 정의의 중심이다 핵심

세 조건이 동시에 성립하는 상태다.

  1. 서로 다른 스레드의 두 접근이 같은 변수를 대상으로 하고,
  2. 그중 적어도 하나가 쓰기이며,
  3. 두 접근 사이에 happens-before 관계가 없다.

세 번째가 정의의 중심이다. 여러 스레드가 같은 변수를 건드리는 것 자체는 레이스가 아니다 — 관계 없이 건드리는 것이 레이스다. 반대로 모두가 읽기만 한다면 관계가 없어도 레이스가 아니다.

그리고 JMM은 데이터 레이스가 있는 프로그램의 읽기 결과를 사실상 보장하지 않는다. "가끔 오래된 값이 보인다" 수준이 아니라 "어떤 값이 나와도 명세 위반이 아니다"에 가깝다. 그래서 "돌려보니 되던데요"는 정확성의 근거가 되지 못한다(13절).

빈 synchronized 블록도 happens-before 효과가 있나요?힌트: 이론과 실무의 답이 다르다 시니어 변별

이론적으로는 있다. 두 스레드가 같은 락을 잡는다면 블록 안이 비어 있어도 unlock HB lock이 성립하므로, 앞선 쓰기들이 뒤에 보인다.

그런데 실무에서 이 용법에 의존하면 안 된다. 이유가 둘이다.

  • JIT가 아무 효과 없어 보이는 락을 제거(lock elision)할 수 있다. 락 객체가 그 스레드 밖으로 새지 않는다고 판단하면 락 자체를 지워버린다. 의도한 배리어가 사라진다.
  • 의도가 코드에 드러나지 않는다. 다음 사람이 "비어 있으니 지워도 되겠네"라고 판단할 여지가 크고, 그 순간 재현이 극히 어려운 버그가 들어온다.

목적이 가시성이라면 그 목적에 정확히 대응하는 도구인 volatile을 쓰는 것이 맞다. 코드가 의도를 말하게 된다.

join() 대신 isAlive() 폴링이나 Thread.sleep()으로 기다리면 뭐가 다른가요?힌트: "끝난 것을 아는 것"과 "결과가 보이는 것" 함정 가산점

"끝난 것을 아는 것"과 "그 결과가 보이는 것"은 별개라는 것이 핵심이다. isAlive() 폴링은 앞의 것만 주고 뒤의 것은 주지 않는다.

HB가 문서화된 대기 수단

join() · Future.get() · CountDownLatch.await() · BlockingQueue.take() — 명세에 happens-before 보장이 명시되어 있다.

HB가 없는 대기 흉내

while (t.isAlive()) {} · Thread.sleep(1000) — 어떤 규칙도 걸리지 않는다. 결과 필드 읽기가 그대로 데이터 레이스가 된다.

덧붙이면 sleep 쪽은 "끝났다는 보장"조차 없다. 두 가지를 한꺼번에 잃는다(9절).

happens-before가 성립하면 원자성도 보장되나요? volatile int count의 count++는 왜 깨지나요?힌트: "보이느냐"와 "끼어들 수 있느냐"는 다른 축이다 핵심

보장되지 않는다. 가시성과 원자성은 별개의 축이다. happens-before는 "보이느냐"에 대한 보장이지 "끼어들 수 있느냐"에 대한 보장이 아니다.

count++는 읽기 → +1 → 쓰기의 세 단계다. volatile은 각 읽기와 각 쓰기가 최신 값을 보게 만들지만, 세 단계 사이에 다른 스레드가 끼어드는 것은 막지 않는다. 두 스레드가 같은 값을 읽으면 둘 다 같은 값을 쓰고, 두 번 증가시켰는데 1만 늘어난다(갱신 유실).

필요한 것은 읽고-고치고-쓰기를 하나로 묶는 도구다 — AtomicInteger(CAS)나 synchronized. 이 주제는 14번 문서(volatile 가시성 vs 원자성)가 본체이므로, 면접에서는 "happens-before는 원자성과 다른 축입니다"로 경계만 정확히 긋고 넘어가는 것이 좋다(15절).

메서드마다 synchronized를 다 붙였는데도 값이 어긋납니다. 무엇을 의심해야 하나요?힌트: 규칙에 붙은 두 글자 조건 함정

"같은 락"인지부터 의심한다. 모니터 락 규칙은 같은 락 객체에 대해서만 unlock HB lock을 만든다. 서로 다른 락을 잡으면 상호배제도 안 되고 가시성도 안 생긴다.

실무에서 자주 나오는 형태가 셋이다.

  • 인스턴스 메서드와 static 메서드의 혼용 — 앞은 this, 뒤는 클래스 객체에 락을 건다. 둘은 서로 다른 락이다.
  • 락 객체를 필드로 두고 중간에 재대입 — 잡는 시점마다 다른 객체가 되면 관계가 끊긴다. 락 필드는 final이어야 한다.
  • 인스턴스가 여러 개 — this 락은 인스턴스마다 다르다. 공유 상태가 static이면 인스턴스 락으로는 보호되지 않는다.

같은 논리가 volatile에도 그대로 적용된다. 다리는 "같은 락", "같은 변수"로만 놓인다(7절).

서로 다른 volatile 변수에 쓰고 읽으면 다리가 놓이나요?힌트: 규칙의 문장을 그대로 읽어본다 시니어 변별

놓이지 않는다. volatile 규칙의 문장은 "volatile 변수에 대한 쓰기가 같은 변수에 대한 이후의 읽기보다 happens-before다"이다. 변수가 다르면 이 규칙에 해당하는 쌍 자체가 아니다.

즉 스레드 A가 volatile flagA = true를 쓰고 스레드 B가 volatile flagB를 읽는 것으로는 두 스레드가 연결되지 않는다. 둘 다 volatile이라는 사실만으로는 아무 관계도 생기지 않는다.

모니터 락의 "같은 락"과 완전히 대칭인 조건이다. 실무 규율로 압축하면 "발행하는 쪽과 소비하는 쪽이 정확히 같은 동기화 변수(또는 같은 락)를 통과해야 한다"이다. 두 개의 플래그로 신호를 주고받는 설계는 이 지점에서 거의 항상 틀린다(5절 · 7절).

x86 장비에서 몇 년째 잘 돌던 코드가 ARM 서버로 옮기면 깨질 수 있나요?힌트: 재배치 허용 범위는 아키텍처마다 다르다 가산점

그럴 수 있다. 그리고 이것이 JMM이 존재하는 이유 자체다.

재배치를 어디까지 허용하는지가 CPU 아키텍처마다 다르다. x86 계열은 메모리 순서 규칙이 비교적 엄격해서 쓰기와 쓰기 사이의 순서를 잘 뒤집지 않는다. 반면 ARM 계열은 훨씬 느슨해서 같은 코드가 훨씬 자유롭게 재배치된다.

그래서 동기화가 빠진 똑같은 코드가 개발자의 x86 장비에서는 멀쩡히 돌다가, ARM 기반 서버로 옮기는 순간 터지는 일이 실제로 벌어진다. 로컬은 x86인데 운영은 ARM 인스턴스라면 "여기선 잘 되는데요"가 정확성의 근거가 될 수 없는 구체적인 이유가 하나 더 생긴다.

중요한 것은 이것이 JMM 위반이 아니라는 점이다. 동기화가 없었던 코드는 애초에 JMM이 아무것도 보장하지 않는 코드였고, x86에서 돌던 것은 하드웨어가 우연히 관대했던 것뿐이다(3절).

final 필드의 보장은 happens-before 규칙인가요?힌트: 목록에 없는데도 안전 발행 수단으로 쓰인다 시니어 변별

happens-before 규칙 목록에는 없다. JMM이 final에 대해 따로 정한 별도의 보장이다.

내용은 이렇다. 객체의 생성자가 정상적으로 끝나면, 그 객체의 final 필드에 생성자에서 넣은 값은 다른 스레드에게도 완성된 상태로 보인다. 그 객체의 참조를 어떤 방식으로 넘겨받든, 심지어 동기화 없이 넘겨받아도 그렇다.

이 보장이 왜 필요한지는 volatile 없는 double-checked locking이 깨지는 이유와 같다. new Holder()는 메모리 할당 → 생성자 실행 → 참조 대입의 3단계인데, 재배치로 참조 대입이 생성자 실행보다 먼저 보일 수 있다. 그러면 다른 스레드가 참조는 있는데 필드는 아직 기본값인 반쪽짜리 객체를 잡는다. final 필드에 대해서는 JMM이 이 재배치를 금지해 그런 상태를 원천 차단한다.

단, 조건이 하나 붙는다 — 생성자가 끝나기 전에 this 참조가 밖으로 새어 나가면 안 된다. 생성자 안에서 자신을 리스너로 등록하거나, 자기 참조를 static 필드·컬렉션에 넣거나, 내부 스레드를 시작해 this를 넘기는 경우다. 아직 완성되지 않은 객체를 다른 스레드가 볼 수 있게 되므로 보장이 무너진다. 이것을 this 탈출(this escape)이라 부른다(14절).

BlockingQueue로 객체를 넘길 때 그 객체의 필드에 volatile을 붙여야 하나요?힌트: 이 패키지의 클래스들은 문서에 무엇을 명시하는가

붙이지 않아도 된다. java.util.concurrent의 클래스들은 API 문서에 자신이 제공하는 happens-before를 명시한다. BlockingQueue의 보장은 "원소를 put하기 이전의 연산 HB 다른 스레드가 그 원소를 take한 이후의 연산"이다.

즉 큐가 다리 역할을 대신해 준다. 생산자가 큐에 넣기 전에 채워 둔 일반 필드들은, 소비자가 꺼낸 뒤 읽을 때 전부 보인다. 같은 성격의 보장이 여럿 있다.

  • ExecutorService.submit() 이전의 연산 HB 그 태스크의 실행
  • 태스크 안의 모든 연산 HB Future.get()의 반환
  • CountDownLatch.countDown() 이전의 연산 HB await()의 반환

주의할 것은 가시성이 보장된다고 해서 그 객체를 이후에 계속 고쳐도 된다는 뜻은 아니라는 점이다. 보장되는 것은 "넣기 이전에 한 쓰기"까지다. 넘긴 뒤에도 생산자가 그 객체를 수정하면 그 수정에는 아무 다리가 없다 — 넘기는 객체는 불변으로 만들거나 소유권을 넘기고 손을 떼는 것이 원칙이다(11절 · 12절).

happens-before는 모든 연산 쌍에 정의되나요?힌트: 전체 순서가 아니라 부분 순서 가산점

아니다. happens-before는 부분 순서(partial order)다. 모든 연산 쌍에 순서가 정해져 있는 게 아니라, 규칙에 해당하는 쌍에만 관계가 생긴다.

관계가 없는 두 연산은 서로에게 어떤 순서로든 보일 수 있다. 스레드 A가 보기엔 X가 먼저이고 스레드 B가 보기엔 Y가 먼저인 상황도 배제되지 않는다. 그리고 그 상태가 곧 데이터 레이스다(조건 3).

그래서 동시성 코드를 검증한다는 것은 결국 이 그래프에서 간선을 찾는 일이다. "이 공유 변수의 쓰기와 읽기 사이에 happens-before를 만드는 규칙이 무엇인가?"에 규칙 이름으로 답할 수 없다면, 테스트가 통과했더라도 그 코드는 틀렸다(4절 · 13절).

한 줄 요약
happens-before는 JMM이 정의한 연산 간의 부분 순서로, "A happens-before B"는 A가 시간적으로 먼저 실행된다는 뜻이 아니라 A에서 한 모든 메모리 쓰기가 B에서 반드시 보인다는 가시성 보장이며 — 하드웨어마다 재배치 규칙이 다르기 때문에 자바가 "어떤 CPU에서도 이만큼은 보장한다"는 최소선을 언어 차원에서 명세한 것이 그 배경이다 — 프로그램 순서 · 모니터 락(unlock HB lock) · volatile(write HB read) · start() · join() 같은 규칙으로 만들어지고 이행성으로 이어 붙여 안전 발행 패턴을 완성하며, 이 관계 없이 이루어지는 공유 변수 접근이 곧 데이터 레이스이고 그 결과에 대해 JMM은 아무것도 보장하지 않는다.
