enum 활용 패턴 — 상수 집합을 넘어 전략·상태 머신으로
전제는 딱 하나 — "enum은 클래스다". 상수는 값이 아니라 인스턴스이고, 상수별 바디는 진짜 익명 하위 클래스다

면접 질문: "enum을 단순 상수 집합 이상으로 활용하는 패턴(전략 메서드 보유, 허용 상태 전이 정의)을 설명해주세요."

핵심 관전 포인트 — 이 주제는 "enum은 클래스다"라는 전제 하나에서 전부 따라 나온다. 바이트코드로 보면 enum Grade는 java.lang.Enum을 상속한 클래스로 컴파일되고, BASIC·VIP 같은 상수는 그 클래스의 public static final 필드에 담긴 인스턴스이며, 상수별로 { ... } 블록을 달면 그 상수만의 익명 하위 클래스(Grade$1)가 실제로 만들어진다. 클래스이므로 필드·생성자·메서드를 가질 수 있고, 상수마다 메서드를 다르게 구현할 수 있다 — "enum 안에 로직을 넣는다"는 말이 자연스러워지는 근거가 이것이다. 여기서 두 패턴이 나온다. 패턴 ① 전략 메서드 보유는 상수마다 갈리는 동작을 switch 대신 추상 메서드 + 상수별 구현으로 옮기는 것인데, 진짜 이득은 코드가 짧아지는 것이 아니라 새 상수를 추가할 때 구현 누락을 컴파일러가 잡아준다는 데 있다 — 흩어진 switch를 하나 빼먹어 런타임에 조용히 잘못된 분기로 흘러가는 산탄 수술(shotgun surgery)이 구조적으로 불가능해진다. 패턴 ② 허용 상태 전이는 "어느 상태에서 어디로 갈 수 있는가"의 표를 enum이 직접 소유하게 해 코드가 곧 상태 전이 다이어그램이 되게 하는 것이다. 여기서 초기화 순서가 함정이 되는데 — enum 상수는 클래스 초기화(static 블록)에서 선언 순서대로 만들어지므로 생성자에서 아직 만들어지지 않은 뒤쪽 상수나 정적 필드를 건드리면 컴파일 에러이고, 정적 메서드를 한 단계 끼워 그 검사를 우회하면 ExceptionInInitializerError를 감싼 NullPointerException으로 터진다. 마지막으로 DB 저장에서 ordinal()은 절대 쓰지 않는다. 상수 순서를 바꾸거나 중간에 하나 끼워 넣는 순간 저장된 모든 행의 의미가 통째로 밀리기 때문이다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "enum을 단순 상수 집합 이상으로 활용하는 패턴(전략 메서드 보유, 허용 상태 전이 정의)을 설명해주세요."

출제 의도 — enum을 상수 나열로만 쓰는 사람과 동작(전략 메서드)·허용 전이(상태 머신)를 타입에 싣는 사람은 코드 전반의 분기문 산탄(if-else 산재) 양이 다르다. "타입 시스템에 규칙을 실어 컴파일러가 지키게 한다"는 사고를 Java에서 실천할 수 있는지 — Kotlin sealed class 문항과 같은 사고의 Java 판이다.

즉 "enum이 뭐냐"를 묻는 질문이 아니다. 타입 안전한 상수 집합이라는 설명은 10초면 끝나고, 진짜 질문은 그다음 "그래서 그 안에 무엇을 넣을 수 있고, 어디까지 넣어야 하는가"에서 시작한다. 여기서 enum을 상수로만 쓴 사람과 클래스로 쓴 사람이 갈린다.

이 질문의 정체 — "패턴 두 개를 아느냐"가 아니라 "enum이 클래스라는 사실을 어디까지 활용해 봤느냐"다.
패턴 이름은 두 문장이면 끝난다. 변별은 왜 그게 가능한지(상수 = 인스턴스, 상수별 바디 = 익명 하위 클래스)와, 실제로 만들어 본 사람만 밟는 세 개의 지뢰(초기화 순서 · ordinal() 저장 · enum의 상한선)에서 난다.

이렇게 답하면 반쪽이다

  • "enum은 타입 안전한 상수 집합입니다"에서 끝 — 질문이 "그 이상"을 물었는데 그 이하를 답한 것.
  • "switch보다 깔끔합니다" — 미적 취향으로 들린다. 진짜 이득은 누락이 컴파일 에러가 되는 것이지 코드 길이가 아니다.
  • "enum에 필드랑 메서드를 넣을 수 있습니다"까지만 — 사실 나열. 왜 가능한지(상수가 인스턴스라서)가 빠지면 외운 것으로 들린다.
  • "생성자에서 다른 상수를 참조하면 NPE가 납니다" — 부정확하다. 직접 참조는 컴파일 에러로 막힌다. 런타임까지 가는 것은 정적 메서드로 우회한 경우뿐이다.
  • "ordinal()은 쓰지 말라고 배웠습니다" — 왜 위험한지, 그리고 JPA 기본값이 그쪽이라는 점을 못 말하면 지식이 아니라 구호다.
  • 상한선 이야기가 없음 — enum에 전부 밀어 넣자는 답은 실무에서 스프링 빈 주입이 필요해지는 순간을 겪어 보지 않았다는 신호다.

이 문서가 채워 주는 것

  • javap로 본 enum의 실체 — 모든 답의 출발점. 상수 = static final 인스턴스, 생성은 static {} 안에서.
  • 상수별 바디 = Grade$1 — 실제로 .class 파일이 몇 개 생기는지까지.
  • 산탄 수술 도식 — switch가 나쁜 게 아니라 번지는 방식이 문제라는 것.
  • 상태 전이 다이어그램 ↔ 코드 — 그림과 코드가 1:1로 대응하게 만드는 방법.
  • 클래스 초기화 타임라인 — <clinit> 안에서 상수가 정적 필드보다 먼저 만들어지는 순서 한 장.
  • ordinal() 밀림 시뮬레이션 — DB 한 행도 안 바뀌었는데 결제 완료가 결제 대기가 되는 과정.
  • 세 개의 경계 — enum이 식별자로 되돌아가야 하는 정확한 신호.
  • Kotlin sealed와의 갈림길 — 상태별 데이터가 필요한가 한 문장으로 정리.

이 문서를 관통하는 한 문장

enum 상수는 값이 아니라 인스턴스다 — 그래서 다형성이 된다

BASIC은 "0"도 "문자열"도 아니고 Grade 타입의 객체 한 개다. 객체라면 자기 상태(필드)를 들 수 있고, 자기 동작(메서드)을 다르게 구현할 수 있다. 패턴 ①(동작)과 패턴 ②(규칙)는 이 한 문장의 두 가지 응용일 뿐이다. 그리고 그 객체가 클래스 초기화 시점에 딱 한 번 만들어지는 싱글턴이라는 사실에서 이 문서의 함정 세 개(초기화 순서 · ordinal() · 스프링 주입 불가)가 전부 따라 나온다.

0-1. 답변 흐름 한 장 — 이 순서를 지키면 질문이 끝난다

1. 전제 — enum은 클래스다 (int 상수 시절부터)

이 문서의 두 패턴은 전부 이 절 하나에서 유도된다. 여기를 대충 넘기면 뒤의 모든 것이 "그렇게 쓰라고 하더라"가 된다.

1-1. enum 이전에는 무엇을 썼고 왜 위험했나

enum이 없던 시절, "값이 몇 가지로 정해져 있는 것"은 int 상수로 표현했다.

public static final int GRADE_BASIC = 0;
public static final int GRADE_VIP   = 1;
public static final int GRADE_VVIP  = 2;

public BigDecimal discount(int grade, BigDecimal price) { ... }

이 방식의 문제는 타입이 int라는 것이다. discount(999, price)도, discount(userId, price)도 컴파일이 된다. 등급 자리에 회원 번호를 넣는 실수를 컴파일러가 잡아 줄 방법이 없다. 값을 출력해도 1이라고만 나와서 로그를 봐도 무슨 뜻인지 모른다.

1-2. 상수 하나하나가 그 타입의 인스턴스다

enum은 문법 설탕이 아니라 진짜 클래스로 컴파일된다. 컴파일 결과를 직접 열어 보면 분명하다.

소스두 줄짜리 enum
public enum Simple { A, B }
javap컴파일 결과의 실체
$ javap -p Simple.class

public final class Simple extends java.lang.Enum<Simple> {
  public static final Simple A;   // 인스턴스다
  public static final Simple B;
  private static final Simple[] $VALUES;
  public static Simple[] values();
  public static Simple valueOf(java.lang.String);
  private Simple();                     // private 생성자
  static {};                          // 여기서 A, B가 생성
}

javap 한 장에서 뽑아 두는 세 문장

extends java.lang.Enum
name()·ordinal()·compareTo()가 이미 붙어 있다. 그리고 상속 슬롯이 이미 소비돼 다른 클래스는 상속할 수 없다. 인터페이스 구현은 자유(§4-3).
public static final Simple A
상수처럼 보이지만 실체는 그 클래스의 인스턴스이고, JVM이 한 번 만들고 다시는 안 만든다. 상수 하나 = 싱글턴 하나.
private Simple(); static {};
생성자가 private이라 밖에서 새로 못 만든다. 인스턴스는 전부 클래스 초기화 블록에서 선언 순서대로 생성된다.

1-3. 클래스이므로 필드·생성자·메서드를 가질 수 있다

인스턴스라면 자기 상태를 가질 수 있다. 상수마다 다른 값을 들려 보내려면 생성자에 넘기면 된다.

public enum Grade {
    BASIC(0), VIP(5), VVIP(10);   // 괄호 안이 생성자 인자다. 각각이 Grade의 인스턴스가 된다

    private final int discountRate;   // 상수마다 다른 값을 담는 인스턴스 필드

    // 생성자는 항상 private이다. 밖에서 Grade를 새로 만들 수 없으므로
    // "이 타입의 인스턴스는 선언된 세 개가 전부"라는 것이 언어 차원에서 보장된다.
    Grade(int discountRate) {
        this.discountRate = discountRate;
    }

    public int discountRate() {
        return discountRate;
    }
}
읽는 방식이 달라진다Grade.VIP.discountRate()가 자연스럽게 읽히는 이유는 VIP가 값이 아니라 객체이기 때문이다. "VIP에게 물어보니 할인율이 5라고 답한다"는 구조다. int 상수 시절에는 값을 어딘가의 표에서 찾아보는 구조였다면, 이제는 값에게 직접 묻는 구조가 된다.

2. 상수별 바디 = 진짜 익명 하위 클래스

한 걸음 더 나가면, 상수마다 메서드를 다르게 구현할 수도 있다. 상수 뒤에 { ... } 블록을 붙이면 된다. 이것을 상수별 클래스 바디(constant-specific class body)라고 부른다.

public enum Grade {
    BASIC { public int rate() { return 0;  } },
    VIP   { public int rate() { return 5;  } },
    VVIP  { public int rate() { return 10; } };

    public abstract int rate();
}

문법이 낯설어 보이지만, 컴파일 결과를 보면 무슨 일이 일어나는지 정확히 드러난다. .class 파일의 개수부터 다르다.

$ javac Grade.java && ls *.class
Grade$1.class  Grade$2.class  Grade$3.class  Grade.class      // 클래스가 4개 생겼다

$ javap -p Grade.class
public abstract class Grade extends java.lang.Enum<Grade> {   // final이 풀리고 abstract가 됐다
  public static final Grade BASIC;
  ...
  public abstract int rate();
}

$ javap -p 'Grade$1.class'
final class Grade$1 extends Grade {     // BASIC 전용 익명 하위 클래스
  public int rate();
}

여기서 확보해야 할 문장 — 이걸 말하면 나머지 답이 전부 "유도된 것"이 된다

"enum 안에 로직을 넣는다"는 것은 특별한 문법이 아니라 그냥 다형성이다

상위 타입(Grade)이 추상 메서드를 선언하고, 하위 클래스(각 상수)가 그것을 다르게 구현한다 — 자바에서 매일 쓰는 그 구조다. 다만 하위 클래스의 개수와 인스턴스가 컴파일 타임에 고정돼 있을 뿐이다. 이 문장을 먼저 깔아야 §3(동작)과 §5(규칙)가 "패턴 이름 두 개"가 아니라 "같은 원리의 두 응용"으로 들린다.

같이 알아 둘 비용상수별 바디는 상수 개수만큼 클래스 파일이 늘어난다. 상수가 20개면 .class가 21개다. 클래스 로딩 관점에서 무시할 만한 수준이긴 하지만, 한 줄짜리 동작 하나를 위해 이 구조를 쓰는 것은 과하다 — 그 경우의 대안이 §4-2의 함수형 필드다.

3. 패턴 ① 전략 메서드 — 산탄 수술을 컴파일 에러로

3-1. 먼저 문제를 정의하자 — 산탄 수술이란

switch가 나쁘다는 말부터 하면 안 된다. 문제는 switch 자체가 아니라 그것이 번지는 방식이다.

등급별 할인율이 필요해서 switch를 하나 썼다고 하자. 얼마 뒤 등급별 적립률이 필요해져 또 하나, 등급별 무료배송 기준에 또 하나, 등급 표시 색상에 또 하나. 같은 모양의 switch가 코드베이스 곳곳에 흩어진다.

이제 GOLD 등급을 추가한다. 고쳐야 할 곳은 한 군데가 아니라 그 흩어진 switch 전부다. 어디에 몇 개가 있는지 아는 사람은 없다.

산탄 수술(shotgun surgery)하나의 개념적 변경을 반영하려면 여러 곳을 흩어서 고쳐야 하는 구조를 산탄총으로 쏜 자국 같다고 해서 이렇게 부른다. 문제의 본질은 손이 많이 가는 것이 아니라, 하나를 빠뜨렸을 때 아무도 모른다는 것이다.

3-2. Before / After — 같은 요구사항, 다른 실패 방식

Before할인 계산이 서비스 코드에 switch로 존재한다
public BigDecimal discount(Grade grade, BigDecimal price) {
    switch (grade) {
        case BASIC: return BigDecimal.ZERO;
        case VIP:   return price.multiply(new BigDecimal("0.05"));
        case VVIP:  return price.multiply(new BigDecimal("0.10"));
        default:    throw new IllegalStateException();  // 방어 코드까지 필요하다
    }
}

// GOLD를 추가하고 이 메서드를 고치는 것을 잊으면?
//  → 컴파일은 성공한다 (default가 있어 문법적으로 완전하므로)
//  → GOLD 회원의 첫 결제에서 IllegalStateException
//  → default가 ZERO였다면 예외조차 없이 할인 0원으로 계산된다
After추상 메서드 + 상수별 구현
public enum Grade {
    BASIC {
        @Override public BigDecimal discount(BigDecimal price) {
            return BigDecimal.ZERO;
        }
    },
    VIP {
        @Override public BigDecimal discount(BigDecimal price) {
            return price.multiply(new BigDecimal("0.05"));
        }
    },
    VVIP {
        @Override public BigDecimal discount(BigDecimal price) {
            return price.multiply(new BigDecimal("0.10"));
        }
    };

    // 이 한 줄이 "모든 상수는 자기 할인 규칙을 반드시 갖는다"는 계약이 된다
    public abstract BigDecimal discount(BigDecimal price);
}
호출부분기가 통째로 사라진다
BigDecimal discounted = price.subtract(member.getGrade().discount(price));

실수 ① 바디 없이 추가

코드가 짧아지는 것이 아니라, 규칙을 기억에서 꺼내 타입 시스템에 실어 컴파일러가 대신 지키게 하는 것

사람은 잊지만 컴파일러는 잊지 않는다. 면접에서 "코드가 깔끔해집니다"라고 답하면 취향으로 들리고, "누락이 컴파일 에러가 됩니다"라고 답하면 설계 판단으로 들린다. 같은 패턴을 설명해도 이 한 문장에서 갈린다.

4. switch 식과의 균형 · 함수형 필드 · 인터페이스

여기서 "그럼 switch는 언제나 나쁜가"라고 물으면 답은 "아니다"다. 이 절이 면접에서 균형 감각을 보여 주는 자리다.

4-1. 최신 switch 식과의 균형 잡힌 비교

최신 자바의 switch 식(화살표 문법)은 default 없이 쓰면 완전성 검사(exhaustiveness check)를 해준다. enum 상수를 하나라도 안 다루면 컴파일 에러다.

누락default를 쓰지 않은 switch 식
static int rate(Grade g) {
    return switch (g) {        // default 없음
        case BASIC -> 0;
        case VIP   -> 5;
        // VVIP를 빠뜨렸다
    };
}
$ javacerror: the switch expression does not cover
       all possible input values
함정default를 넣는 순간
static int rate(Grade g) {
    return switch (g) {
        case BASIC -> 0;
        case VIP   -> 5;
        default    -> 0;   // "혹시 모르니" 한 줄
    };
}
// 컴파일 성공. VVIP도 GOLD도 조용히 0이 된다.
// 완전성 검사를 스스로 반납한 것이다.

default는 안전장치가 아니라 검사 해제 스위치다

"혹시 모르니 default도 넣자"는 습관은 컴파일러의 도움을 스스로 반납하는 행위다. enum을 다루는 switch 식에서는 default를 쓰지 않는 것이 기본값이고, 정말 모든 나머지를 한 갈래로 묶고 싶을 때만 의식적으로 쓴다. "컴파일 에러가 나서 default를 넣었다"면 방향이 정확히 반대다 — 그 에러가 알려 주려던 것이 바로 누락이다.

그 분기가 지금 한 곳에만 있고, 앞으로도 그럴 것 같은가?
그렇다switch 식으로 충분하다. default를 쓰지 않아 완전성 검사가 살아 있게만 하면 된다. enum을 굳이 무겁게 만들 이유가 없다.
같은 축의 분기가 둘 이상 생겼다enum 안으로 옮긴다. 두 번째 switch가 생기는 순간이 산탄 수술의 시작점이다. 세 번째가 생긴 뒤에 옮기면 이미 늦다.
애매하다기준을 하나 더 준다 — 그 분기가 "도메인 규칙"인가 "표현 방식"인가. 할인율·전이 허용은 도메인 규칙이라 enum이 소유하는 편이 낫고, 화면 표시 문자열이나 색상은 표현 계층이라 enum에 넣으면 도메인이 화면을 알게 된다.

4-2. 로직이 가벼우면 함수형 필드로 가산점

상수별 바디는 상수마다 익명 하위 클래스를 만들어 낸다(§2). 로직이 한 줄짜리라면 동작 자체를 필드에 담는 방식이 훨씬 짧다.

public enum Operation {
    PLUS ((a, b) -> a + b),
    MINUS((a, b) -> a - b);

    private final IntBinaryOperator op;   // 동작을 "값"으로 들고 있는다

    Operation(IntBinaryOperator op) {
        this.op = op;
    }

    public int apply(int a, int b) {
        return op.applyAsInt(a, b);
    }
}
이 방식도 누락은 컴파일 에러다새 상수를 추가하면 생성자 인자를 반드시 넘겨야 하므로, 동작을 빠뜨리면 "생성자를 찾을 수 없다"로 그 자리에서 막힌다. §3에서 얻은 이득이 그대로 유지된다는 점이 중요하다 — 이 둘은 "엄격함 vs 편의"의 트레이드오프가 아니라 "표현 방식"의 차이다.
같은 목적의 세 가지 표현 — 무엇을 기준으로 고르는가
상수별 클래스 바디함수형 필드생성자 값 필드
담는 것상수 전용 메서드 구현상수 전용 함수 객체상수 전용 데이터
예시VIP { discount(){...} }PLUS((a,b) -> a+b)VIP(5)
누락 시컴파일 에러 (미구현)컴파일 에러 (인자 없음)컴파일 에러 (인자 없음)
메서드 여러 개자연스럽다 — 상수마다 여러 메서드 재정의필드가 늘어나 지저분해진다해당 없음
공통 헬퍼 공유enum의 protected/private 메서드를 호출 가능람다 안에서 인스턴스 상태 접근이 제한적해당 없음

4-3. enum은 인터페이스를 구현할 수 있다

§1에서 본 대로 enum은 이미 java.lang.Enum을 상속하고 있어 다른 클래스는 상속할 수 없다. 하지만 인터페이스 구현에는 제약이 없다.

public interface DiscountPolicy {
    BigDecimal discount(BigDecimal price);
}

public enum Grade  implements DiscountPolicy { ... }
public enum Coupon implements DiscountPolicy { ... }

// 호출부는 Grade인지 Coupon인지 모른 채 같은 방식으로 다룬다
List<DiscountPolicy> policies = List.of(member.getGrade(), order.getCoupon());

서로 다른 enum들을 하나의 상위 타입으로 묶어 다형적으로 다룰 수 있다는 뜻이다. 상수 집합을 확장할 수는 없어도(enum은 상속으로 늘릴 수 없다), 여러 enum이 같은 계약을 구현하게 해서 계약 단위의 확장은 열 수 있다.

이때 포기하는 것 — 반드시 같이 말한다상수 집합이 여러 enum으로 흩어지면 "이게 전부다"를 컴파일러가 보장할 수 없다. switch의 완전성 검사도 못 쓴다. 확장성과 완전성은 맞바꾸는 관계이므로, 주문 상태처럼 집합이 닫혀 있어야 하는 도메인에서는 확장 가능하게 만들지 않는 것이 옳다.

5. 패턴 ② 허용 상태 전이 — 코드가 곧 다이어그램

패턴 ①이 상수마다 갈리는 동작을 옮긴 것이라면, 패턴 ②는 상수들 사이의 규칙을 옮긴다. 같은 다형성의 다른 응용이다.

5-1. 먼저 규칙을 그림으로 확정한다

주문 상태처럼 "어떤 상태에서 어떤 상태로만 갈 수 있다"는 규칙이 있는 도메인을 생각하자. 이런 규칙의 집합을 상태 머신(state machine)이라 하고, 그것을 그린 것이 상태 전이 다이어그램이다.

같은 규칙을 표로 옮긴 것 — 표에 없는 전이는 전부 금지다
현재 상태갈 수 있는 다음 상태그 뜻
CREATEDPAID, CANCELED결제하거나 취소하거나 — 둘뿐이다
PAIDSHIPPED, CANCELED출고 전까지는 아직 취소할 수 있다
SHIPPEDDELIVERED취소가 사라졌다 — 출고 시점이 정책의 경계선
DELIVERED(없음 — 종착)더 갈 곳이 없다
CANCELED(없음 — 종착)취소는 되돌릴 수 없다

5-2. Before — 전이 규칙이 서비스 코드에 흩어진다

public void cancel(Order order) {
    // 취소 가능 상태 검사를 이 메서드가 직접 알고 있다
    if (order.getStatus() == OrderStatus.PAID
            || order.getStatus() == OrderStatus.CREATED) {
        order.setStatus(OrderStatus.CANCELED);
    }
    // else가 없다 — 조건에 안 맞으면 아무 일도 안 하고 조용히 끝난다
}

ship(), deliver(), refund()에도 같은 성격의 if가 하나씩 생긴다. 표가 코드베이스에 흩어져 있고, 어디에도 표 전체가 보이는 곳이 없다. §3-1의 산탄 수술이 이번에는 분기가 아니라 규칙에서 재현된 것이다.

그리고 실패 방식이 더 나쁘다위 코드는 조건에 안 맞으면 아무 일도 안 하고 조용히 끝난다. 호출한 쪽은 취소가 된 줄 알고 다음 단계로 넘어간다. 환불 처리, 재고 복구, 알림 발송이 취소되지 않은 주문에 대해 실행된다. 예외도 로그도 없다.

5-3. After — 전이 규칙을 enum이 소유한다

허용 전이 집합을 enum이 직접 들고 있게 만든다. 아래 static 블록 다섯 줄이 §5-1의 그림 그 자체다.

public enum OrderStatus {
    CREATED, PAID, SHIPPED, DELIVERED, CANCELED;

    private Set<OrderStatus> allowedNext;   // 이 상태에서 갈 수 있는 다음 상태들

    static {
        // 왜 생성자가 아니라 static 블록인지는 §6에서 다룬다
        CREATED.allowedNext   = EnumSet.of(PAID, CANCELED);
        PAID.allowedNext      = EnumSet.of(SHIPPED, CANCELED);
        SHIPPED.allowedNext   = EnumSet.of(DELIVERED);
        DELIVERED.allowedNext = EnumSet.noneOf(OrderStatus.class);
        CANCELED.allowedNext  = EnumSet.noneOf(OrderStatus.class);
    }

    public boolean canTransitionTo(OrderStatus next) {
        return allowedNext.contains(next);
    }
}
// 도메인 객체는 전이할 때 이 관문 하나만 통과시킨다
public void changeStatus(OrderStatus next) {
    if (!status.canTransitionTo(next)) {
        // 조용히 무시하지 않고 예외로 드러낸다.
        // 허용되지 않은 전이를 시도했다는 것은 호출부에 버그가 있다는 뜻이므로,
        // 아무 일도 안 하고 넘어가면 그 버그가 영영 안 보인다.
        throw new IllegalStateException(
            "허용되지 않는 상태 전이: " + status + " -> " + next);
    }
    this.status = next;
}
① 한곳에 모인다
정책이 바뀌면 static 블록만 고친다. "취소 가능 조건이 어디에 있죠?"에 파일 하나로 답할 수 있다.
② 살아 있는 문서
그 코드 블록 자체가 §5-1 다이어그램의 역할을 한다. 위키 문서와 달리 코드와 어긋날 수 없다.
③ 실패가 드러난다
위반이 조용한 무시가 아니라 예외다. 메시지에 SHIPPED -> CANCELED가 그대로 찍혀 원인 추적이 즉시 된다.

EnumSet을 쓴 이유 가산점

EnumSet은 enum 전용 Set 구현체로, 내부적으로 각 상수를 비트 하나에 대응시킨 비트 벡터로 원소를 표현한다(상수가 64개 이하면 long 하나로 끝난다). 그래서 contains가 비트 연산 한 번이고, HashSet처럼 해시 계산이나 버킷 탐색이 없다. enum을 키로 쓰는 Map에는 같은 이유로 EnumMap이 우선이다.

enum이 키/원소면 무조건 EnumSet · EnumMap부터 떠올린다

6. 초기화 순서의 함정 — 왜 생성자가 아니라 static 블록인가

여기가 이 패턴에서 가장 자주 막히는 지점이고, 면접에서도 가장 자주 되묻는 자리다. 왜 전이 규칙을 생성자에서 넘겨받지 않는가?

§1-2에서 본 사실을 다시 꺼내야 한다. enum 상수는 클래스 초기화 시점의 static {} 안에서 위에서 아래로 하나씩 만들어진다. 그러니 CREATED의 생성자가 도는 시점에는 PAID가 아직 존재하지 않는다.

6-1. 자바는 이 상황을 컴파일 단계에서 막는다

(1) 생성자 인자로 다른 상수를 넘기면

public enum T2 {
    CREATED(PAID),      // 아직 만들어지지 않은 PAID를 참조
    PAID();
    private final T2 next;
    T2(T2... next) { ... }
}
$ javac T2.javaerror: illegal forward reference

(2) 생성자 본문에서 상수(정적 필드)를 읽으면

public enum T1 {
    CREATED, PAID, SHIPPED;
    private final Set<T1> allowedNext;
    T1() {
        this.allowedNext = EnumSet.of(PAID);  // 정적 필드 읽기
    }
}
$ javac T1.javaerror: illegal reference to static field from initializer
그래서 이 실수는 런타임까지 가지 않는다둘 다 컴파일 에러다. 자바 언어 명세가 enum의 생성자·인스턴스 초기화 블록에서 정적 필드에 접근하는 것을 아예 금지해 두었기 때문이다. "생성자에서 다른 상수를 참조하면 NPE가 난다"는 답이 부정확한 이유가 이것이다.

6-2. 다만 우회 경로가 하나 열려 있고, 그쪽으로 가면 런타임에 터진다

정적 필드를 직접 읽는 대신 정적 메서드를 호출하면 컴파일러의 검사를 통과한다. 컴파일러는 메서드 안에서 무엇을 하는지까지는 보지 않기 때문이다.

public enum T4 {                                                  // 1
    A, B;                                                         // 2
    private static final Map<String, T4> INDEX = new HashMap<>(); // 3
                                                                  // 4
    T4() { register(this); }                                      // 5  컴파일은 된다
    private static void register(T4 v) { INDEX.put(v.name(), v); }  // 6
}
$ java T4Exception in thread "main" java.lang.ExceptionInInitializerError
Caused by: java.lang.NullPointerException:
    Cannot invoke "java.util.Map.put(Object, Object)" because "T4.INDEX" is null
        at T4.register(T4.java:6)
        at T4.<init>(T4.java:5)
        at T4.<clinit>(T4.java:3)

스택트레이스를 아래에서 위로 읽으면 순서가 그대로 보인다. <clinit>(클래스 초기화)이 시작 → 상수 A의 생성자 <init> 실행 → register 호출 → 그런데 INDEX = new HashMap<>() 줄은 상수 생성 다음에 있으므로 아직 null.

이 절에서 외울 세 줄 — 순서 · 컴파일 에러 · 런타임 에러

1
순서 — 상수가 정적 필드보다 먼저 초기화된다. 둘 다 <clinit> 안에서 실행되지만 상수 생성이 맨 앞에 놓인다.
2
직접 참조는 컴파일 에러 — 인자로 넘기면 illegal forward reference, 생성자 본문에서 읽으면 illegal reference to static field from initializer. 런타임까지 가지 않는다.
3
정적 메서드 우회는 런타임 폭발 — ExceptionInInitializerError가 NullPointerException을 감싼 형태. 이후 접근은 NoClassDefFoundError.
결론 — 상수들 사이의 관계는 모든 상수 생성이 끝난 뒤인 static 블록에서 연결한다

7. 전이 규칙도 컴파일러가 강제하게 만들기 가산점

§5-3의 static 블록 방식에는 약점이 하나 있다. 눈치챘다면 이미 절반은 시니어다.

static 블록 방식의 구멍새 상태를 추가했을 때 static 블록에 그 상태의 줄을 넣는 것을 잊어도 컴파일이 된다. 그러면 allowedNext가 null인 상수가 생기고, 그 상태에서 전이를 시도하는 순간 NullPointerException이 난다. 패턴 ①에서 얻었던 "컴파일러가 누락을 잡아준다"는 이득이 여기서는 빠져 있는 것이다.
public enum OrderStatus {
    CREATED, PAID, SHIPPED, DELIVERED, CANCELED, REFUNDED;   // 새 상태 추가

    private Set<OrderStatus> allowedNext;

    static {
        CREATED.allowedNext   = EnumSet.of(PAID, CANCELED);
        PAID.allowedNext      = EnumSet.of(SHIPPED, CANCELED);
        SHIPPED.allowedNext   = EnumSet.of(DELIVERED);
        DELIVERED.allowedNext = EnumSet.noneOf(OrderStatus.class);
        CANCELED.allowedNext  = EnumSet.noneOf(OrderStatus.class);
        // REFUNDED 줄을 빠뜨렸다 → 컴파일 성공 → REFUNDED.allowedNext == null
    }
}

패턴 ①의 방식을 그대로 가져오면 이 약점이 사라진다. 전이 집합을 필드가 아니라 추상 메서드로 선언하는 것이다.

public enum OrderStatus {
    CREATED   { public Set<OrderStatus> allowedNext() { return EnumSet.of(PAID, CANCELED); } },
    PAID      { public Set<OrderStatus> allowedNext() { return EnumSet.of(SHIPPED, CANCELED); } },
    SHIPPED   { public Set<OrderStatus> allowedNext() { return EnumSet.of(DELIVERED); } },
    DELIVERED { public Set<OrderStatus> allowedNext() { return EnumSet.noneOf(OrderStatus.class); } },
    CANCELED  { public Set<OrderStatus> allowedNext() { return EnumSet.noneOf(OrderStatus.class); } };

    public abstract Set<OrderStatus> allowedNext();

    public boolean canTransitionTo(OrderStatus next) {
        return allowedNext().contains(next);
    }
}
"어? 메서드 안에서는 다른 상수를 참조해도 되나요?" — 된다§6의 제약은 "생성자와 인스턴스 초기화 시점"에 걸리는 것인데, 이 메서드는 클래스 초기화가 전부 끝난 뒤 호출되는 시점에 실행되기 때문이다. 제약의 대상은 "상수"가 아니라 "시점"이다. 이 구분을 말할 수 있으면 §6을 진짜로 이해한 것이다.
전이 표를 담는 두 가지 방식 — 어느 쪽이 옳은 게 아니라 무엇을 사는지가 다르다
static 블록 + 필드 (§5-3)추상 메서드 + 상수별 바디 (§7)
상태 추가 시 누락하면컴파일 성공 → 그 상태 전이 시 NullPointerException컴파일 에러 → 그 자리에서 막힘
표를 한눈에 보기다섯 줄이 나란히 — 다이어그램에 가장 가깝다상수 선언에 섞여 세로로 길어진다
EnumSet 생성 시점클래스 초기화 때 한 번 만들고 재사용호출할 때마다 새로 만든다
클래스 파일 수1개1 + 상수 개수만큼(§2)
고르는 기준호출 빈도가 아주 높고 상태 목록이 안정적일 때상태가 계속 추가될 가능성이 있을 때 (대부분의 경우)
절충안추상 메서드로 선언하되 반환값을 상수별 private final 필드에 캐싱하거나, static 블록 방식에 모든 상수가 채워졌는지 검증하는 assert를 static 블록 끝에 넣는다 — 후자는 컴파일 타임은 아니지만 기동 즉시 터지므로 배포 전에 잡힌다.

절충안이 실무에서 가장 자주 쓰이는 형태

    static {
        CREATED.allowedNext   = EnumSet.of(PAID, CANCELED);
        // ... 나머지 ...

        // 표를 채우지 않은 상수가 하나라도 있으면 애플리케이션이 뜨지 않는다
        for (OrderStatus s : values()) {
            if (s.allowedNext == null) {
                throw new IllegalStateException("전이 표 누락: " + s);
            }
        }
    }

컴파일 타임 검사는 아니지만, 클래스가 처음 로딩되는 시점 — 대개 애플리케이션 기동 중 — 에 즉시 터진다. "운영 중 특정 상태에서만 NPE"가 "기동 실패"로 바뀌는 것이고, 이 정도만 되어도 사고의 성격이 완전히 달라진다. §6에서 본 ExceptionInInitializerError가 이번에는 우리 편이 되는 셈이다.

8. DB 저장 — ordinal()이 왜 위험한가

enum을 DB에 저장하는 방법은 크게 둘이다. 선언 순서를 나타내는 정수(ordinal())를 저장하거나, 상수 이름 문자열(name())을 저장하거나.

가장 먼저 알아야 할 사실 — JPA의 기본값이 위험한 쪽이다

@Enumerated를 안 붙이거나 그냥 붙이면 = EnumType.ORDINAL

아무 생각 없이 매핑하면 위험한 쪽이 선택된다. "실수해야 사고가 나는" 게 아니라 "아무것도 안 하면 사고가 나는" 구조라서, 이 항목은 코드 리뷰 체크리스트에 올려 둘 가치가 있다.

8-1. 무엇이 위험한지 실제 데이터로 보자

결제 대기 상태가 필요해져서 CREATED 다음에 PAYMENT_PENDING을 끼워 넣는다. enum 선언 한 줄을 추가했을 뿐이고, DB는 한 행도 건드리지 않았다.

8-2. 대응은 두 단계다

1
기본은 문자열 저장. JPA라면 @Enumerated(EnumType.STRING)을 명시한다. 순서를 어떻게 바꾸든 "PAID"는 PAID다. DB를 직접 조회했을 때 의미가 읽힌다는 부수 효과도 크다 — 장애 대응 중 status=2를 보고 코드를 찾아보는 시간이 사라진다. 
@Enumerated(EnumType.STRING)   // 이 한 줄을 빼먹으면 기본값인 ORDINAL이 된다
@Column(length = 20, nullable = false)
private OrderStatus status;
2
이름 변경까지 견디려면 별도 코드값 필드를 둔다. 문자열 저장은 순서 변경에는 안전하지만 상수 이름을 리팩터링하면 깨진다. CANCELED를 CANCELLED로 고치는 순간 기존 데이터를 못 읽는다. 그래서 저장용 코드값을 enum이 따로 들고, 변환기(AttributeConverter)로 매핑한다. 
public enum OrderStatus {
    CREATED("C"), PAID("P"), SHIPPED("S"), DELIVERED("D"), CANCELED("X");

    private final String code;   // DB에 저장되는 값. 상수 이름과 분리돼 있다

    OrderStatus(String code) { this.code = code; }

    public String code() { return code; }

    public static OrderStatus from(String code) {
        return Arrays.stream(values())
                     .filter(s -> s.code.equals(code))
                     .findFirst()
                     .orElseThrow(() -> new IllegalArgumentException("알 수 없는 코드: " + code));
    }
}
저장된 값과 코드의 이름이 분리되므로, 상수 이름은 리팩터링해도 DB는 안 건드린다. 저장 값과 코드의 결합을 한곳에서 통제할 수 있다는 것이 이 방식의 값이다. 가산점

9. enum에 로직을 넣는 것이 과해지는 지점 시니어 변별

지금까지 "enum 안으로 옮겨라"라고 말했지만, 여기에는 분명한 상한선이 있다. 이 선을 아는 것이 패턴을 아는 것보다 중요하다 — 패턴은 책에 있지만 경계는 겪어야 안다.

경계 ① 도메인 의존성 역류
신호: "여기서 DB를 한 번 조회하면 되는데..."

enum 상수는 JVM이 클래스 로딩 시점에 만드는 싱글턴이다(§1-2). 그래서 스프링 컨테이너가 관여할 여지가 없다 — 리포지토리나 외부 API 클라이언트를 주입받을 방법이 없다.

흔한 회피책이 정적 홀더에 빈을 넣어 두고 enum이 꺼내 쓰는 것인데, 이건 의존성을 숨긴 전역 상태라 테스트에서 갈아 끼울 수 없고 초기화 순서에도 취약하다.

경계 ② 테스트 가능성
신호: 상수별 바디가 수십 줄로 자란다

상수는 인스턴스를 새로 만들 수 없으므로 테스트에서 상태를 주입하거나 협력 객체를 대역으로 바꿔 끼울 수 없다.

결국 Grade.VVIP.discount(...)처럼 실제 상수를 그대로 불러 결과만 검증하게 되고, 로직이 커질수록 준비할 수 있는 조건이 부족해진다.

경계 ③ 배포 주기 불일치
신호: "이 값 좀 바꿔 주세요"가 반복된다

할인율 같은 것은 마케팅 판단으로 수시로 바뀐다. enum에 하드코딩하면 값 하나 바꾸는 데 배포가 필요하다.

이건 enum의 잘못이 아니라 애초에 코드가 아니라 설정이나 DB에 있어야 할 값을 코드에 둔 것이다. 구조와 값을 분리하면 된다.

경계를 넘은 뒤의 모습enum은 "무엇인지"만 남고, "어떻게 하는지"는 빈으로 나간다
// 전략은 인터페이스 + 스프링 빈으로
public interface DiscountPolicy {
    BigDecimal discount(Member member, BigDecimal price);
}

@Service
public class DiscountService {
    // enum을 키로 쓰는 전략 맵. 스프링이 구현체들을 모아 넣어 준다.
    private final Map<Grade, DiscountPolicy> policies;

    public BigDecimal discount(Member member, BigDecimal price) {
        return policies.get(member.getGrade()).discount(member, price);
    }
}

세 경계를 한 문장으로 묶으면

enum 전략은 "규칙이 타입과 함께 컴파일 타임에 고정되어도 좋은, 외부 의존이 없는 가벼운 로직"까지가 적정선

이 선을 넘으면 enum은 식별자로 돌아가고 로직은 빈으로 나간다. 면접에서 이 문장을 먼저 말하고 세 경계를 근거로 붙이면, "패턴을 아는 사람"이 아니라 "패턴의 적용 범위를 판단해 본 사람"으로 들린다.

10. Kotlin이라면 — sealed class와의 경계

출제 의도에 "Kotlin sealed class 문항과 같은 사고의 Java 판"이라고 적혀 있다. 즉 이 비교를 먼저 꺼내면 출제자가 원한 지점을 정확히 짚는 것이 된다.

같은 문제를 Kotlin은 sealed class/sealed interface + when의 완전성 검사로 푼다. sealed는 "이 타입을 상속할 수 있는 하위 타입이 컴파일 타임에 전부 정해져 있다"는 선언이라, when에서 하위 타입을 하나라도 빠뜨리면 컴파일 에러가 난다. enum의 추상 메서드가 주는 이득과 정확히 같은 성격이다.

같은 목적, 다른 표현력 — 무엇으로 고르는가

검사가 꺼지는 조건switch에 default를 쓸 때when에 else를 쓸 때

인스턴스 개수상수당 정확히 1개 (싱글턴)하위 타입마다 여러 개 생성 가능

11-4. 코드 리뷰 체크리스트

이렇게 되어 있으면 통과

  • enum의 인스턴스 필드가 전부 final이다
  • 상수 사이의 관계는 static 블록이나 메서드에서 연결한다
  • @Enumerated(EnumType.STRING)이 명시되어 있다
  • enum이 키/원소인 자료구조는 EnumMap·EnumSet이다
  • enum을 다루는 switch 식에 default가 없다
  • 상태 전이는 관문 메서드 하나를 통과하고, 위반 시 예외가 난다

이게 보이면 지적한다

  • 같은 축의 switch가 두 군데 이상 있다 → 산탄 수술 시작점
  • "혹시 모르니" 넣은 default → 완전성 검사 해제
  • enum에 가변 필드가 있다 → 사실상 전역 변수
  • @Enumerated가 없거나 인자 없이 붙어 있다 → ORDINAL
  • 전이 검사가 if로 서비스 곳곳에 흩어져 있다
  • 조건 불일치 시 아무 일도 안 하고 리턴한다 → 조용한 실패
  • enum 안에서 정적 홀더로 스프링 빈을 꺼내 쓴다 → 숨은 전역 의존

12. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 펼치기 전에 답이 안 나오면 그 항목이 오늘 다시 볼 지점이다.

switch로도 되는데, 굳이 enum 안에 로직을 넣는 이유는?힌트: 코드 길이가 아니라 "누락을 누가 잡아 주느냐" 핵심

핵심은 코드 길이가 아니라 누락을 누가 잡아 주느냐다.

switch는 로직이 enum 밖에 있어서 같은 축의 분기가 여러 곳에 복제된다(할인, 적립, 배송비, 표시 색상...). 상수를 하나 추가할 때 그 흩어진 switch를 전부 찾아 고쳐야 하는데, 하나를 빠뜨려도 컴파일은 성공한다. default 절이 있으니 문법적으로 완전하기 때문이다. 그리고 새 상수가 처음 들어오는 순간 런타임 예외가 나거나, 더 나쁘게는 default의 기본값이 조용히 반환된다. 이렇게 하나의 변경을 위해 여러 곳을 흩어서 고쳐야 하는 구조를 산탄 수술(shotgun surgery)이라 부른다.

전략 메서드는 상수 추가 시 구현이 없으면 그 자리에서 컴파일 에러다. 규칙을 지키는 책임이 사람의 기억에서 컴파일러로 옮겨 간다.

균형 잡힌 마무리까지 붙이면 좋다. 최신 자바의 switch 식(화살표 문법)은 default 없이 쓰면 enum 상수를 전부 다루는지 컴파일러가 검사해 주므로, 한 곳에서만 쓰는 분기라면 switch 식도 충분히 좋은 선택이다. 다만 default를 넣는 순간 그 검사가 꺼진다는 점, 그리고 같은 축의 분기가 두 번째로 생기는 순간이 enum으로 옮길 신호라는 점까지 말하면 정리가 깔끔하다.

정리 문장 — "얻는 것은 짧은 코드가 아니라 컴파일러의 강제입니다. 같은 축의 분기가 두 번째로 생기는 순간이 enum 안으로 옮길 신호이고, 한 곳뿐이면 default 없는 switch 식으로도 충분합니다."

상태 전이 정의에서 왜 생성자가 아니라 static 블록을 썼나요?힌트: CREATED의 생성자가 도는 시점에 PAID는 존재하는가 핵심

enum 상수가 만들어지는 시점 때문이다.

enum 상수는 클래스 초기화(static {}) 안에서 선언 순서대로 하나씩 생성된다. 그래서 CREATED의 생성자가 도는 시점에는 PAID가 아직 존재하지 않는다. 자바는 이 상황을 컴파일 단계에서 금지한다 — 생성자 인자로 뒤의 상수를 넘기면 illegal forward reference, 생성자 본문에서 상수(정적 필드)를 읽으면 illegal reference to static field from initializer가 난다.

여기서 반쯤 아는 답이 갈린다"그래서 런타임 NPE가 난다"고 답하면 부정확하다 — 직접 참조는 컴파일러가 막으므로 런타임까지 가지 않는다. 다만 정적 메서드를 한 단계 끼워 우회하면 컴파일러 검사를 통과하고, 그때는 ExceptionInInitializerError로 감싸인 NullPointerException이 난다. 상수가 정적 필드보다 먼저 초기화되기 때문이다. 한번 초기화에 실패한 클래스는 이후 접근마다 NoClassDefFoundError를 던져서 진짜 원인이 처음 한 번만 로그에 남는다는 점도 알아 두면 좋다.

정리 문장 — "상수들 사이의 관계는 모든 상수 생성이 끝난 뒤인 static 블록에서 연결합니다. 한 걸음 더 나가면 추상 메서드로 선언해 상수별 바디에서 반환하는 방식도 있습니다 — 메서드 본문은 클래스 초기화가 끝난 뒤 실행되므로 다른 상수를 자유롭게 참조할 수 있고, 새 상태 추가 시 구현 누락을 컴파일러가 잡아 준다는 이점까지 붙습니다."

enum을 DB에 저장할 때는 어떻게 하나요? ordinal 저장의 위험은?힌트: DB는 한 행도 안 바뀌었는데 의미가 바뀐다 함정

ordinal() 저장은 상수 순서를 바꾸거나 중간에 하나 추가하는 순간 기존 데이터 전체의 의미가 밀린다.

{CREATED, PAID, SHIPPED} 상태에서 1로 저장된 행은 PAID인데, CREATED 다음에 PAYMENT_PENDING을 끼워 넣으면 같은 1이 PAYMENT_PENDING으로 읽힌다. 결제 완료된 주문이 결제 대기가 되고 출고된 주문이 결제 완료로 되돌아가는데, DB는 한 행도 안 바뀌었고 예외도 나지 않는다. 값이 유효 범위 안이라 아무도 문제를 못 느낀다.

JPA의 기본값이 EnumType.ORDINAL이라는 점을 반드시 언급해야 한다. @Enumerated를 생략하거나 그냥 붙이면 위험한 쪽이 선택되므로, @Enumerated(EnumType.STRING)을 명시하는 것이 원칙이다.

한 단계 더 들어가면 문자열 저장도 완전하지 않다 — 상수 이름을 리팩터링하면 기존 데이터를 못 읽는다. 그래서 enum에 저장용 코드값 필드(CREATED("C"))를 따로 두고 AttributeConverter로 매핑하면, 상수 이름과 저장 값이 분리되어 이름 변경에도 안전해진다. 저장 값과 코드의 결합을 한곳에서 통제할 수 있다는 것이 이 방식의 값이다. 가산점

enum에 로직을 넣는 게 과해지는 지점은 어디인가요?힌트: 세 개의 경계 — 의존성·테스트·배포 주기 시니어 변별

세 가지 경계로 답한다.

1
도메인 의존성이 enum으로 역류할 때. enum 상수는 JVM이 클래스 로딩 시점에 만드는 싱글턴이라 스프링 빈(리포지토리, 외부 API 클라이언트)을 주입받을 수 없다. 로직이 DB 조회나 외부 호출을 필요로 하는 순간 enum을 벗어나야 한다. 정적 홀더에 빈을 넣어 두고 enum이 꺼내 쓰는 회피책은 의존성을 숨긴 전역 상태라 테스트에서 갈아 끼울 수 없으므로 답이 아니다. 옳은 방향은 전략을 빈으로 옮기고 enum은 그 전략을 고르는 키로 되돌리는 것이다 — Map<Grade, DiscountPolicy> 형태.
2
상수마다 로직이 크게 갈려 테스트가 어려워질 때. 상수는 인스턴스를 새로 만들 수 없으므로 테스트에서 상태를 주입하거나 협력 객체를 대역으로 바꿔 끼울 수 없다. 로직이 커질수록 준비할 수 있는 조건이 모자라진다.
3
값이 배포 없이 바뀌어야 할 때. 할인율처럼 마케팅 판단으로 수시로 바뀌는 값을 enum에 하드코딩하면 값 하나 바꾸는 데 배포가 필요하다. 이건 애초에 코드가 아니라 설정이나 DB에 있어야 할 값이다.

정리 문장 — "enum 전략은 '규칙이 타입과 함께 컴파일 타임에 고정되어도 좋은, 외부 의존이 없는 가벼운 로직'까지가 적정선입니다. 이 선을 넘으면 enum은 식별자로 돌아가고 로직은 빈으로 나갑니다."

Kotlin이라면 어떻게 풀겠어요?힌트: 같은 사고, 다른 도구 — 갈리는 지점은 하나다 시니어 변별

같은 문제를 Kotlin은 sealed class/sealed interface + when의 완전성 검사로 푼다.

sealed는 "이 타입을 상속할 수 있는 하위 타입이 컴파일 타임에 전부 정해져 있다"는 선언이라, when에서 하위 타입을 하나라도 빠뜨리면 컴파일 에러가 난다. enum의 추상 메서드가 주는 이득과 정확히 같은 성격이다.

차이는 상태를 담을 수 있느냐다. sealed 하위 타입은 각자 다른 필드를 가질 수 있어서 Canceled(val reason: String)처럼 그 상태에서만 의미 있는 데이터를 붙일 수 있고, 인스턴스도 여러 개 만들 수 있다. enum 상수는 인스턴스가 하나씩 고정이라 이런 표현이 불가능하다. 반대로 상태별 데이터가 필요 없다면 Kotlin에서도 enum이 더 간결하다.

정리 문장 — "둘 다 규칙을 타입 시스템에 실어 컴파일러가 지키게 한다는 점은 같고, 상태별 데이터가 필요한가에서 갈립니다."

enum 상수는 왜 ==로 비교해도 안전한가요? equals와 차이는?힌트: 인스턴스가 몇 개인지 언어가 보장한다

상수 하나당 인스턴스가 정확히 하나뿐이기 때문이다. 상수는 클래스 초기화 시점에 static {}에서 딱 한 번 만들어지고, 생성자가 private이라 밖에서 새로 만들 수 없다. 그러니 같은 상수라면 반드시 같은 주소이고, ==(주소 비교)가 곧 equals(동등성 비교)와 결과가 같다.

실제로 java.lang.Enum의 equals는 final로 선언되어 있고 내부가 this == other다. 즉 재정의할 수도 없고, 재정의할 이유도 없다.

==를 권하는 이유

  • null에 안전 — status == OrderStatus.PAID는 status가 null이어도 false일 뿐 예외가 안 난다. status.equals(...)는 NPE다.
  • 타입 오류를 컴파일러가 잡는다 — 서로 다른 enum 타입을 ==로 비교하면 컴파일 에러다. equals는 그냥 false를 반환하고 조용히 지나간다.

단 하나의 예외 상황

  • 같은 enum 클래스가 서로 다른 클래스로더로 두 번 로딩되면 이름이 같아도 다른 클래스이고 상수도 다른 객체다. 이때는 ==도 equals도 false다.
  • 플러그인 구조나 핫 리로드 환경의 이야기이고, 일반 애플리케이션에서는 신경 쓸 일이 아니다.

정리 문장 — "상수가 싱글턴이라 ==가 곧 동등성이고, Enum.equals는 final로 ==를 그대로 씁니다. 실무에서는 null 안전성과 타입 오류를 컴파일러가 잡아 준다는 이유로 ==를 씁니다."

EnumSet·EnumMap은 HashSet·HashMap과 뭐가 다른가요?힌트: 원소가 "몇 번째 상수인지"를 이미 알고 있다 가산점

키가 될 수 있는 값이 컴파일 타임에 전부 정해져 있고 각자 순번(ordinal)을 가진다는 사실을 자료구조가 활용한다.

EnumSet
각 상수를 비트 하나에 대응시킨 비트 벡터로 원소를 표현한다. 상수가 64개 이하면 long 하나로 집합 전체가 표현된다. 그래서 contains가 비트 연산 한 번이고, 합집합·교집합도 비트 연산이다. 해시 계산도 버킷 탐색도 없다.
EnumMap
내부가 ordinal을 인덱스로 쓰는 배열 하나다. 조회가 배열 인덱싱이라 해시 충돌 개념 자체가 없고, 반복 순서가 항상 상수 선언 순서로 고정된다.

부수 효과도 크다. HashMap은 반복 순서가 정의되지 않지만 EnumMap은 선언 순서라서 로그나 응답의 순서가 예측 가능해진다. 상태 전이표처럼 모든 상수에 대해 값을 채우는 자료구조일수록 이 특성이 잘 맞는다.

주의 — 성능이 유일한 이유는 아니다둘 다 null 키/원소를 허용하지 않는다. "null이 들어오면 조용히 담기는" 대신 NullPointerException으로 즉시 드러난다는 것도 이 자료구조를 고르는 이유다.

정리 문장 — "enum 키의 개수와 순번이 고정이라는 사실을 자료구조가 쓸 수 있어서, EnumSet은 비트 벡터, EnumMap은 ordinal 인덱스 배열로 구현됩니다. 더 빠르고, 순서가 예측 가능하고, null을 막아 줍니다."

"싱글턴은 enum으로 만들라"는 조언은 왜 나온 건가요?힌트: 직렬화와 리플렉션을 스스로 막아 주는 유일한 방식 가산점

직접 만든 싱글턴이 깨지는 두 경로를 언어가 대신 막아 주기 때문이다.

1
리플렉션 — 보통의 private 생성자는 setAccessible(true)로 열어 두 번째 인스턴스를 만들 수 있다. 반면 Constructor.newInstance는 enum 타입에 대해 명시적으로 거부하도록 정의되어 있어 이 경로가 막혀 있다.
2
직렬화·역직렬화 — 일반 클래스는 역직렬화할 때마다 새 객체가 만들어져 싱글턴이 깨진다. 막으려면 readResolve를 직접 구현해야 한다. enum은 이름만 기록되고 역직렬화 시 기존 상수를 찾아 돌려주는 방식이라 추가 코드 없이 인스턴스가 하나로 유지된다.
3
초기화의 스레드 안전 — 상수 생성이 클래스 초기화(<clinit>) 안에서 일어나고, JVM은 클래스 초기화를 딱 한 번, 다른 스레드는 기다리게 보장한다. 이중 검사 잠금 같은 관용구가 필요 없는 이유다.

단점도 같이 말하면 좋다. enum 싱글턴은 상속을 쓸 수 없고 지연 초기화를 세밀하게 제어하기 어렵다. 그리고 이 문서의 §9와 같은 이유로 스프링 빈을 주입받을 수 없어서, 스프링을 쓰는 애플리케이션에서는 애초에 싱글턴 스코프 빈이 그 역할을 한다.

정리 문장 — "리플렉션과 역직렬화라는 두 우회 경로를 언어가 막아 주기 때문입니다. 다만 스프링 환경에서는 컨테이너가 싱글턴을 관리하므로, enum 싱글턴은 의존성이 없는 순수 유틸리티 정도에서 의미가 있습니다."

enum 상수에 가변 필드를 두면 어떻게 되나요?힌트: 그 필드는 사실상 전역 변수다 함정

그 순간 그 필드는 "JVM 전체에서 공유되는 전역 가변 상태"가 된다. 상수는 클래스당 하나뿐인 싱글턴이므로, 어떤 요청 스레드가 Grade.VIP.count++를 하면 모든 요청이 같은 변수를 건드린다.

문제상수에 카운터를 달았다
public enum Grade {
    BASIC, VIP, VVIP;
    private int orderCount;   // 가변 필드
    public void increase() { orderCount++; }
}
// 모든 스레드가 같은 VIP 객체의 같은 필드를 갱신한다
// → 경쟁 조건 + 앱 재시작 전까지 값이 계속 누적
개선상태는 상수 밖으로
public enum Grade { BASIC, VIP, VVIP; }

// 카운트는 요청/엔티티/캐시 등 "그 값이 속한 곳"에
private final Map<Grade, Long> counts
        = new EnumMap<>(Grade.class);

// enum 필드는 final 상수 데이터만 담는다

단, "상수마다 다른 고정값"은 전혀 문제가 아니다. VIP(5)처럼 생성자로 받아 final 필드에 담는 것은 불변이고 스레드 안전하다. 문제가 되는 것은 런타임에 바뀌는 필드다.

정리 문장 — "enum 필드는 final만 둡니다. 상수가 싱글턴이라 가변 필드는 곧 전역 변수이고, 동시성 문제와 애플리케이션 수명 내내 남는 상태 오염을 만듭니다. 변하는 값은 enum을 키로 쓰는 바깥 자료구조에 둡니다."

values()는 호출할 때마다 배열을 새로 만든다던데, 무슨 뜻인가요?힌트: 배열은 불변이 될 수 없다 가산점

배열은 내용을 막을 방법이 없어서, 컴파일러가 values()를 "내부 배열의 복사본을 돌려주는 메서드"로 만들어 주기 때문이다.

§1에서 본 javap 출력에 private static final Simple[] $VALUES;가 있었다. 이 원본 배열을 그대로 돌려주면 누구든 Grade.values()[0] = null;로 enum 타입 전체를 오염시킬 수 있다. 그래서 values()는 매번 $VALUES.clone()을 반환한다.

그래서 실무에서 조심할 자리뜨거운 경로에서 values()를 반복 호출하면 배열이 계속 새로 만들어진다. 반복문 조건이나 매 요청마다 순회하는 코드라면 private static final Grade[] VALUES = values();처럼 한 번 만들어 캐싱하고, 외부에 노출할 때는 List.of(VALUES)처럼 불변 리스트로 감싼다. 성급한 최적화가 아니라, "이 메서드는 매번 복사본"이라는 사실을 알고 쓰는 것이 요점이다.

정리 문장 — "배열은 불변으로 만들 수 없어 values()가 매번 내부 배열의 clone()을 돌려줍니다. 그래서 호출이 잦은 자리에서는 한 번 만들어 캐싱하고 불변 리스트로 노출하는 것이 정석입니다."

enum을 API 응답이나 메시지 페이로드에 그대로 쓸 때 주의할 점은?힌트: 상수를 추가한 쪽과 읽는 쪽의 배포 시점이 다르다 시니어 변별

enum은 "가능한 값의 집합"을 컴파일 타임에 고정하는 도구인데, 분산 환경에서는 그 집합이 서비스마다 다른 시점에 갱신된다. 여기서 문제가 생긴다.

1
모르는 값이 오면 역직렬화가 통째로 실패한다. 생산자가 PAYMENT_PENDING을 추가해 먼저 배포하면, 아직 옛 버전인 소비자는 그 문자열을 매핑하지 못해 메시지 하나가 아니라 그 요청/컨슈머 전체가 실패할 수 있다. 대비는 알 수 없는 값을 null이나 UNKNOWN 상수로 흡수하는 역직렬화 설정이고, 그 값을 로그·메트릭으로 반드시 드러내는 것이 짝이다.
2
배포 순서에 제약이 생긴다. "새 상수를 쓰는 메시지"는 소비자가 먼저 그 상수를 아는 버전으로 배포된 뒤에 나가야 한다. 상수 추가 → 소비자 배포 → 생산자 배포 순서를 지키는 것이 안전하고, 이건 DB 컬럼 추가와 같은 성격의 스키마 변경으로 다뤄야 한다.
3
상수 이름 변경·삭제는 호환성 파괴다. §8의 DB 이야기와 완전히 같은 이유다. 외부로 나가는 값이라면 상수 이름과 전송 값을 분리해(코드값 필드 + 변환기) 이름 리팩터링이 계약을 깨지 않게 만든다.

정리 문장 — "enum은 컴파일 타임에 값 집합을 고정하는데 분산 환경에서는 그 집합이 서비스마다 다른 시점에 갱신됩니다. 그래서 모르는 값을 흡수하는 역직렬화 정책, 소비자 먼저 배포하는 순서, 이름과 전송 값의 분리 셋을 스키마 변경처럼 다룹니다."

enum은 상속이 안 되는데, "확장 가능한 enum"이 필요하면 어떻게 하나요?힌트: 상수 집합은 못 늘려도 계약은 늘릴 수 있다

enum은 이미 java.lang.Enum을 상속하고 있어 단일 상속 슬롯이 소비된 상태라 다른 클래스를 상속할 수 없고, enum끼리 상속도 안 된다. 하지만 인터페이스 구현에는 제약이 없다.

그래서 "연산의 집합"처럼 나중에 늘어날 수 있는 대상은 인터페이스를 계약으로 두고, 여러 enum이 각자 그 계약을 구현하게 만든다.

public interface Operation {
    int apply(int a, int b);
}

// 기본 연산 집합
public enum BasicOp implements Operation {
    PLUS  { public int apply(int a, int b) { return a + b; } },
    MINUS { public int apply(int a, int b) { return a - b; } };
}

// 나중에 다른 모듈이 집합을 "추가"한다 — 기존 enum은 손대지 않는다
public enum ExtendedOp implements Operation {
    POWER { public int apply(int a, int b) { return (int) Math.pow(a, b); } };
}

// 호출부는 어느 enum인지 모른 채 동일하게 다룬다
List<Operation> all = new ArrayList<>();
all.addAll(List.of(BasicOp.values()));
all.addAll(List.of(ExtendedOp.values()));
이때 포기하는 것완전성 검사가 사라진다. 상수 집합이 여러 enum으로 흩어지면 "이게 전부다"를 컴파일러가 보장할 수 없고, switch의 완전성 검사도 못 쓴다. 확장성과 완전성은 맞바꾸는 관계이므로, 집합이 닫혀 있어야 하는 도메인(주문 상태 등)에서는 확장 가능하게 만들지 않는 것이 옳다.

정리 문장 — "상수 집합 자체는 확장할 수 없지만, 인터페이스를 계약으로 두고 여러 enum이 구현하게 하면 계약 단위의 확장은 열립니다. 대신 '이게 전부'라는 완전성 보장을 포기하는 트레이드오프가 있어서, 도메인 상태처럼 닫혀 있어야 하는 집합에는 쓰지 않습니다."

상태 전이를 enum에 넣는 것과 별도의 상태 머신 라이브러리를 쓰는 것은 어떻게 고르나요?힌트: 전이에 딸려 오는 것이 "허용 여부"뿐인가 시니어 변별

전이에 "허용 여부" 말고 무엇이 더 딸려 오는지로 가른다.

enum이 적당한 경우

  • 전이의 관심사가 "이 전이가 허용되는가"뿐이다.
  • 상태 개수가 손에 잡히고 전이 표가 한 화면에 들어온다.
  • 전이에 외부 호출·DB 조회가 필요 없다(§9의 경계 ①).
  • 규칙이 코드와 함께 배포되어도 좋다.

바깥으로 나가야 하는 경우

  • 전이할 때마다 부수 작업(알림 발송, 정산 반영, 외부 API 호출)이 따라붙는다 → 도메인 서비스 + 도메인 이벤트로.
  • 전이 조건이 데이터에 따라 달라진다(금액·회원 등급·시간). enum은 상수만 보고 판단할 수 있어야 한다.
  • 전이 규칙 자체를 운영자가 화면에서 바꿔야 한다 → 설정·DB로(§9의 경계 ③).
  • 병렬 상태·중첩 상태·타임아웃 전이 같은 본격적인 상태 차트가 필요하다 → 전용 라이브러리.

중간 답도 있다. enum은 "허용 전이 표"만 소유하고, 전이에 딸린 부수 작업은 도메인 객체의 메서드가 canTransitionTo 관문을 통과한 뒤 처리하게 나눈다. enum은 게이트, 부수 작업은 도메인 — 이 분리가 실무에서 가장 오래 버틴다.

정리 문장 — "전이의 관심사가 허용 여부뿐이면 enum이 가장 싸고 정확합니다. 전이에 부수 작업이나 데이터 의존 조건이 붙기 시작하면 enum은 게이트 역할만 남기고 나머지는 도메인 서비스로 뺍니다."

switch 식의 완전성 검사가 있는데도 상태 전이를 enum에 넣어야 하나요?힌트: 검사해 주는 대상이 무엇인지 비교해 보라

완전성 검사가 보장해 주는 범위가 다르다.

"이 switch 하나가 모든 상수를 다루는가". 즉 한 곳의 완전성이다. 같은 축의 switch가 다섯 군데면 다섯 군데 모두 컴파일 에러로 알려 주긴 하지만, 여전히 다섯 군데를 각각 고쳐야 한다. 그리고 그중 하나라도 default가 붙어 있으면 그 자리만 검사에서 빠진다.
전략 메서드가 강제하는 것
"이 상수가 모든 계약을 구현했는가". 즉 상수 쪽의 완전성이다. 고칠 자리가 상수를 추가한 그 한 곳으로 모이고, default 같은 검사를 끄는 구멍이 없다.

그래서 판단 기준은 분기의 개수다. 한 곳뿐이면 default 없는 switch 식으로 충분하고, 같은 축의 분기가 둘 이상 생기는 순간 enum 안으로 옮긴다. 상태 전이 규칙은 대개 cancel()·ship()·refund()처럼 애초에 여러 곳에서 물어보는 규칙이라 두 번째 조건에 바로 걸린다.

정리 문장 — "switch 식은 '이 분기가 완전한가'를, 전략 메서드는 '이 상수가 완전한가'를 검사합니다. 분기가 한 곳이면 switch 식, 둘 이상이면 enum 안으로 옮기는 것이 기준이고, default를 쓰는 순간 검사가 꺼진다는 점은 어느 쪽이든 기억해야 합니다."

30초 답변 대본 — 이 순서로 말한다

  1. 전제: "enum은 java.lang.Enum을 상속한 진짜 클래스로 컴파일되고, 상수 하나하나가 그 타입의 인스턴스입니다. 상수 뒤에 바디를 달면 익명 하위 클래스가 실제로 만들어집니다."
  2. 패턴 ①: "그래서 상수마다 갈리는 동작을 추상 메서드 + 상수별 구현으로 옮길 수 있습니다. 이득은 코드 길이가 아니라 상수를 추가할 때 구현 누락이 컴파일 에러가 되는 것 — 산탄 수술이 구조적으로 불가능해집니다."
  3. 패턴 ②: "상수 사이의 규칙, 즉 허용 상태 전이 표를 enum이 직접 소유하게 하면 코드가 곧 상태 전이 다이어그램이 되고, 위반이 조용한 무시가 아니라 예외로 드러납니다."
  4. 함정: "구현할 때 걸리는 건 초기화 순서입니다. 상수가 정적 필드보다 먼저 만들어져서 생성자에서 다른 상수를 못 봅니다 — 직접 참조는 컴파일 에러, 정적 메서드 우회는 ExceptionInInitializerError입니다. 그래서 static 블록이나 추상 메서드로 연결합니다."
  5. 경계: "DB에는 ordinal() 말고 문자열이나 코드값을 저장하고(JPA 기본값이 ORDINAL이라 명시가 필요합니다), 외부 의존이 생기거나 값이 배포 없이 바뀌어야 하면 enum은 식별자로 돌아가고 로직은 빈으로 나갑니다."

1번(전제)을 건너뛰면 2·3번이 전부 "외운 패턴 이름"으로 들린다. 전제에 10초, 패턴에 10초, 함정과 경계에 10초.

한 줄 요약
enum은 java.lang.Enum을 상속한 클래스로 컴파일되고 상수 하나하나가 그 타입의 인스턴스이며 상수별 바디는 실제 익명 하위 클래스가 되므로, "enum 안에 로직을 넣는다"는 것은 특별한 문법이 아니라 그냥 다형성이다 — 그래서 상수마다 갈리는 동작은 추상 메서드 + 상수별 구현으로, 상수 사이의 규칙(허용 상태 전이)은 enum이 소유한 표로 옮길 수 있고, 이때의 진짜 이득은 코드가 짧아지는 것이 아니라 흩어진 switch 하나를 빠뜨려 런타임에 조용히 틀리는 산탄 수술이 컴파일 에러로 바뀐다는 데 있다. 다만 세 가지 경계를 알아야 실무가 된다 — 상수는 클래스 초기화 중 생성되므로 생성자에서 서로를 참조할 수 없고(직접 참조는 컴파일 에러, 정적 메서드 우회는 ExceptionInInitializerError), DB에는 ordinal()이 아니라 문자열이나 별도 코드값을 저장해야 하며(순서를 바꾸는 순간 저장된 모든 행의 의미가 소리 없이 밀린다), 외부 의존이 필요해지거나 값이 배포 없이 바뀌어야 하는 순간 enum은 식별자로 돌아가고 로직은 스프링 빈으로 나가야 한다.
