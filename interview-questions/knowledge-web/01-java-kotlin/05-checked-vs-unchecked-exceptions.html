Checked vs Unchecked 예외 — 컴파일러가 강제하느냐, 그리고 그 강제가 실무에서 무너진 이유
둘을 가르는 기준은 딱 하나, 컴파일러가 처리를 강제하느냐 · 무너진 방향도 딱 둘, 던져서 오염시키거나 잡아서 은폐하거나

면접 질문: "Checked Exception과 Unchecked Exception의 차이는? 실무에서 어떤 기준으로 선택하나요?"

핵심 관전 포인트 — 둘을 가르는 기준은 딱 하나, 컴파일러가 처리를 강제하느냐다. 예외 계층에서 Error 가지와 RuntimeException 가지는 강제하지 않고(unchecked), 그 둘을 뺀 나머지 Exception 전부가 강제된다(checked). 원래 설계 의도는 "호출자가 복구할 수 있는 외부 상황 = checked, 코드의 버그 = unchecked"였는데 실무에서 두 갈래로 무너졌다 — 저수준의 SQLException이 throws를 타고 컨트롤러까지 번져 계층을 결합시키는 시그니처 오염, 그리고 컴파일 에러만 없애려고 만든 빈 catch가 장애를 은폐하는 기계적 catch. 그래서 실무는 도메인 예외를 RuntimeException으로 통일하고 시스템 경계(전역 핸들러) 한 곳에서 일괄 변환하는 쪽으로 수렴했다. 여기서 반드시 챙겨야 할 함정이 @Transactional의 기본 롤백 규칙이다 — 기본값은 RuntimeException과 Error에서만 롤백이고 checked 예외에서는 그냥 커밋된다. 예외 선택이 문법 취향이 아니라 데이터 정합성 문제가 되는 지점이 정확히 여기다.
  • 1
    정의부터 한 문장으로 자릅니다. 두 예외를 가르는 것은 심각도가 아니라 컴파일러가 처리를 강제하는가 하나입니다. 강제의 실체는 "catch로 잡거나 throws로 선언하거나, 둘 중 하나를 안 하면 컴파일이 안 된다"는 것이고, 대상은 계층도에서 Error 가지와 RuntimeException 가지를 뺀 나머지 전부입니다. checked는 목록이 아니라 뺄셈으로 정의됩니다.
  • 2
    원래 의도와 그것이 무너진 방식을 말합니다. 의도는 복구 가능한 외부 상황은 checked, 코드 버그는 unchecked였습니다. 그런데 "예외를 만난 계층"과 "예외를 처리할 수 있는 계층"이 실제로는 다르기 때문에 두 갈래로 무너졌습니다 — 처리 못 해서 위로 던지면 throws가 컨트롤러까지 번지는 시그니처 오염, 컴파일 에러만 없애려고 잡으면 빈 catch가 장애를 은폐합니다.
  • 3
    그래서 실무 기본값과 함정을 붙입니다. 도메인 예외는 RuntimeException으로 통일하고, 외부 checked는 만난 자리에서 cause를 보존해 즉시 번역하며, 처리는 @RestControllerAdvice 같은 경계 한 곳에 모읍니다. 여기에 @Transactional의 기본 롤백 대상은 RuntimeException과 Error뿐이라 checked 예외는 예외가 던져졌는데도 커밋된다는 사실까지 붙이면, 이 선택이 문법 취향이 아니라 데이터 정합성 문제라는 결론이 완성됩니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "Checked Exception과 Unchecked Exception의 차이는? 실무에서 어떤 기준으로 선택하나요?"

출제 의도 — 팀의 예외 처리 컨벤션(어디서 잡고, 어디서 변환하고, 무엇을 롤백시키는가)을 설계하거나 따를 때 필요한 판단을 본다. 실무에서 catch (Exception e) {}로 삼켜진 예외가 장애 원인 은폐의 단골이라, 예외를 문법이 아니라 "설계의 일부"로 보는 사람인지 확인한다.

즉 이 질문은 정의 두 줄을 묻는 게 아니다. 정의는 30초면 끝나고, 진짜 질문은 그 뒤 "그래서 실무에서는 어떤 기준으로 고르냐"에서 시작한다. 여기서 교과서만 읽은 사람과 사고를 겪어 본 사람이 갈린다.

이 질문의 정체 — "차이를 아느냐"가 아니라 "원래 의도가 왜 실무에서 무너졌는지 아느냐"다.
정의는 계층도 한 장이면 끝난다. 변별은 무너진 두 갈래(던져서 오염 / 잡아서 은폐)와, 그 결과로 실무가 도착한 기본값, 그리고 @Transactional 롤백 함정에서 난다.

이렇게 답하면 반쪽이다

  • "checked는 컴파일 시점, unchecked는 런타임 시점 예외입니다" — 가장 흔한 오답 문장. checked 예외도 실제로 던져지는 건 런타임이다. 컴파일 시점에 일어나는 건 발생이 아니라 검사다.
  • "checked는 심각한 예외, unchecked는 가벼운 예외" — 심각도와 무관하다. NullPointerException(unchecked)이 파일 없음(checked)보다 가벼울 이유가 없다.
  • "복구 가능하면 checked를 씁니다"에서 끝 — 교과서 답이지만 실무 답이 아니다. 이어지는 "그럼 왜 스프링·Kotlin은 반대로 갔죠?"에 막힌다.
  • "실무에선 그냥 RuntimeException 씁니다" — 결론은 맞는데 근거가 없다. 왜 그렇게 수렴했는지를 못 대면 관행을 따라 하는 사람으로 들린다.
  • 롤백 이야기가 안 나옴 — 이 주제가 데이터 정합성과 연결되는 지점을 모르는 것이다. 실무 경험을 묻는 자리에서 여기가 갈린다.
  • "try-catch로 처리하면 안전합니다" — catch가 곧 처리라는 착각. 이 문서 5절 전체가 이 착각을 겨냥한다.

이 문서가 채워 주는 것

  • 계층도에서 정의를 뽑는 법 — checked는 목록이 아니라 뺄셈이라는 관점.
  • "강제"의 실체 — 문이 두 개(catch / throws)뿐이고 둘 다 안 지나면 컴파일이 멈춘다.
  • 무너진 두 갈래 — 던져서 생기는 오염과 잡아서 생기는 은폐가 정반대 방향이라는 구조.
  • 7시간짜리 타임라인 — 삼켜진 예외의 비용이 "안 보인다"가 아니라 "인지·원인 확정이 늦어진다"임을 시간으로.
  • 경계 한 곳 처리 — 강제를 포기하는 게 아니라 그물의 위치를 옮기는 설계.
  • @Transactional 롤백 함정 — 프록시가 예외 타입을 보고 판정한다는 메커니즘과, 그 기본값이 왜 그런지까지.
  • cause 보존 — 한 인자 차이가 로그에서 어떻게 달라지는지 실제 출력으로.

이 문서를 관통하는 한 문장

예외를 만난 계층과 처리할 수 있는 계층은 대개 다르다

checked 예외는 그 둘이 같다고 가정하고 만든 장치다. 계층이 여러 겹 쌓인 실제 애플리케이션에서 그 가정이 깨지므로, 개발자는 처리할 수 없는데 처리를 요구받는다. 그때 나오는 선택이 "위로 던진다(→ 시그니처 오염)"와 "형식만 처리한다(→ 장애 은폐)" 둘뿐이다. 두 갈래는 같은 뿌리에서 갈라진 가지다 — 그래서 처방도 하나다. 처리를 처리할 수 있는 한 곳으로 모은다.

0-1. 답변 흐름 한 장 — 이 순서를 지키면 질문이 끝난다

1. 계층도 한 장 — checked는 목록이 아니라 뺄셈이다

1-1. 전제 — 예외도 그냥 객체이고, 상속 계층을 이룬다

throw new IllegalArgumentException("...")을 보면 알 수 있듯 예외는 특별한 문법 요소가 아니라 우리가 new로 만드는 평범한 객체다. 다른 객체와 다른 점은 단 하나, Throwable이라는 클래스를 상속했다는 것뿐이다. 자바는 throw 뒤에 Throwable의 후손만 올 수 있게 제한한다.

그래서 "checked냐 unchecked냐"는 예외에 붙은 별도의 표식이나 어노테이션이 아니다. 그 예외 클래스가 상속 계층의 어느 가지에 속하는가로 결정된다. 계층도를 먼저 보면 정의가 저절로 따라 나온다.

그래서 우리가 쓰는 extends 한 단어가 판정을 결정한다도메인 예외를 만들 때 extends RuntimeException이라고 쓰느냐 extends Exception이라고 쓰느냐가 이 판정을 그대로 결정한다. extends Exception이라고 쓰는 순간 그 예외는 checked가 되고, 그 순간부터 컴파일러가 개입하기 시작한다.

1-2. 계층도 — 가지 두 개만 기억하면 된다

암기는 이 방향으로 — "목록 외우기"가 아니라 "두 가지만 알기"

checked = Throwable − Error 가지 − RuntimeException 가지

"checked 예외 목록을 외운다"는 접근으로는 새로운 예외 클래스를 만났을 때 판정할 수 없다. "unchecked인 두 가지를 알면 나머지는 자동으로 checked"라고 잡아야 처음 보는 라이브러리 예외도 즉시 분류된다. 판정법은 상속 계보를 따라 올라가 보는 것 — 올라가다 RuntimeException이나 Error를 만나면 unchecked, 못 만나고 Exception에 닿으면 checked다.

Error 가지
unchecked
JVM 자체가 무너진 상황. 잡아서 복구할 대상이 아니다.
RuntimeException 가지
unchecked
코드의 버그. 고쳐야 할 대상이지 처리할 대상이 아니다.
나머지 Exception
checked
컴파일러가 catch 또는 throws를 요구하는 그룹.

2. "컴파일러가 강제한다"의 실체 — 문은 두 개뿐

말로만 들으면 추상적이니 코드로 보자. 강제의 실체는 "잡거나(catch), 던진다고 선언하거나(throws), 둘 중 하나를 하지 않으면 컴파일이 안 된다"는 것이다. 제3의 선택지는 없다.

컴파일 실패checked 예외 — 컴파일러가 개입한다
public String read(Path path) {
    return Files.readString(path);   // 컴파일 에러: unhandled exception IOException
}
문 ①여기서 잡는다
public String read(Path path) {
    try {
        return Files.readString(path);
    } catch (IOException e) {
        return "";
    }
}
문 ②시그니처에 적어 호출자에게 떠넘긴다
public String read(Path path) throws IOException {
    return Files.readString(path);
}
// "나는 이걸 던질 수 있다"고 선언한 것.
// 이제 강제는 호출자에게 넘어간다.
대조unchecked 예외 — 컴파일러가 아무 말도 하지 않는다
public int parse(String s) {
    return Integer.parseInt(s);   // NumberFormatException(RuntimeException 하위)을 던질 수 있지만
}                                 // 잡으라고도, 선언하라고도 하지 않는다. 그냥 컴파일된다.

여기까지가 "문법"이다 — 그리고 면접의 진짜 질문은 그다음부터다

checked의 강제 = catch 또는 throws, 문은 두 개뿐 · 제3의 선택지는 없다

이 두 문이 무너짐의 씨앗이다. 문 ②를 계속 고르면 4절의 시그니처 오염이 되고, 문 ①을 형식적으로 고르면 5절의 장애 은폐가 된다. 두 갈래의 붕괴는 "선택지가 두 개뿐"이라는 이 구조에서 그대로 나온다.

면접에서 가장 흔한 오답 문장"checked는 컴파일 시점에 발생하는 예외" — 틀렸다. 예외가 실제로 던져지는 것은 언제나 런타임이다. 컴파일 시점에 일어나는 것은 발생이 아니라 검사(처리 여부 확인)다. IOException은 파일을 실제로 읽는 순간, 즉 런타임에 던져진다.

남는 자리호출자가 반드시 복구 분기를 타야 하는 라이브러리 경계그 외 대부분그 자리마저 요즘은 Result 타입으로 옮겨 간다

4. 무너진 갈래 ① 시그니처 오염 — 던져서 생기는 문제

원래 의도가 무너진 이유는 checked 예외의 이론이 틀려서가 아니다. "호출자가 복구할 수 있다"는 전제가 계층이 여러 겹 쌓인 실제 애플리케이션에서 거의 성립하지 않기 때문이다. 무너지는 방식이 두 갈래인데, 두 갈래는 정반대 방향으로 문제를 만든다.

갈래 ①
처리하지 않고 위로 던져서 생긴다
컴파일러의 문 ②를 계속 고른 결과 — throws가 호출 체인을 타고 끝까지 올라간다.
  • 증상: 컨트롤러 시그니처에 SQLException
  • 비용: 계층 결합 · 추상화 누수 · 교체 시 광범위 수정
  • 드러나는 시점: 코드를 읽거나 고칠 때 (조용한 설계 부채)
갈래 ②
처리한 척 잡아서 생긴다
컴파일러의 문 ①을 형식적으로 고른 결과 — 빈 catch가 실패를 성공처럼 보이게 만든다.
  • 증상: 에러율 0%인데 데이터가 비어 있다
  • 비용: 장애 인지 지연 + 원인 확정 지연
  • 드러나는 시점: 사고가 난 다음 날 아침 (조용한 운영 부채)

암기 장치 — 무너진 방향은 딱 둘

던지면 오염, 잡으면 은폐

면접에서 "왜 무너졌나요"에 답할 때 이 네 글자만 기억하면 두 갈래가 다 나온다. 그리고 둘의 뿌리는 하나다 — 예외를 만난 계층이 그 예외를 처리할 수 있는 계층이 아니기 때문이다. 처리할 수 있으면 잡아서 처리하면 그만이고, 그럴 때는 checked가 아무 문제도 일으키지 않는다.

4-1. 저수준 예외가 컨트롤러까지 번진다

전형적인 스프링 애플리케이션은 컨트롤러 → 서비스 → 저장소의 세 계층으로 나뉜다. 저장소가 JDBC를 직접 다루다 SQLException(checked)을 만나면 어떻게 되는지 따라가 보자.

Beforechecked 예외를 처리하지 않고 그대로 전파하면 이렇게 된다
public Order findById(Long id) throws SQLException { ... }               // 저장소 — 여기까지는 자연스럽다
public OrderDto getOrder(Long id) throws SQLException { ... }            // 서비스 — SQL을 한 줄도 안 쓰는데 SQLException을 안다
public ResponseEntity<OrderDto> get(Long id) throws SQLException { ... }  // 컨트롤러 — HTTP만 다루는데 SQLException을 안다
용어 정리 — 추상화 누수(leaky abstraction)감춰야 할 구현 세부사항이 위로 새어 나왔다는 뜻이다. 저장소가 "어떻게 저장하는지"는 숨기기로 한 약속인데, throws SQLException 한 줄이 그 약속을 시그니처로 깨뜨린다. 인터페이스를 잘 나눠 놓고도 예외 하나 때문에 결합이 생기는 전형적인 사례다.

4-2. 자바 8 이후 하나가 더 붙었다 — 람다·Stream과 궁합이 최악이다

표준 함수형 인터페이스(Function, Supplier 등)는 checked 예외를 던지도록 선언돼 있지 않다. 그래서 람다 안에서 checked 예외를 만나면 탈출구가 없다.

컴파일 실패람다 안의 checked 예외
List<String> contents = paths.stream()
        .map(p -> Files.readString(p))   // 컴파일 에러
        .toList();
// unhandled exception IOException
// map()이 받는 Function은 throws를 선언하지
// 않으므로 "떠넘기기(문 ②)"가 불가능하다.
// 남은 선택은 문 ① 하나뿐이다.
현실결국 이렇게 감싸게 된다
List<String> contents = paths.stream()
        .map(p -> {
            try {
                return Files.readString(p);
            } catch (IOException e) {
                throw new UncheckedIOException(e);
            }
        })
        .toList();
// 정작 하려던 일보다 장식이 길어진다.
JDK 스스로의 인정JDK가 이 변환 전용으로 UncheckedIOException을 따로 만들어 둔 것 자체가, "checked를 unchecked로 바꿔야 하는 자리"가 흔하다는 인정이다. 언어 설계가 밀어붙인 강제를 표준 라이브러리가 우회 통로를 만들어 완화하고 있는 셈이다.

5. 무너진 갈래 ② 기계적 catch — 잡아서 생기는 문제

두 번째 갈래는 반대 방향이다. 컴파일러가 "처리하라"고 강제하면, 마감에 쫓기는 개발자는 "처리한 척"을 한다.

Before최악의 패턴 — IDE가 만들어 준 catch 블록에 손을 대지 않은 코드
try {
    reader.read();
} catch (IOException e) {
    // TODO: 나중에 처리
}
// 파일을 못 읽었는데 아무 일 없다는 듯 다음 로직이 진행된다.

이 코드가 왜 이렇게 흔한지는 IDE의 동작을 보면 알 수 있다. 컴파일 에러 위에서 "빠른 수정"을 누르면 IDE가 빈 catch 블록을 자동으로 만들어 준다. 에러 표시가 사라지고 코드는 컴파일된다. 그 순간 개발자의 문제는 해결됐고, 시스템의 문제는 시작됐다.

로그를 남기는 것도 본질은 같을 수 있다.

Before로그는 남지만 실패가 "결과 없음"으로 번역돼 버린다
} catch (SQLException e) {
    log.error("DB 오류", e);   // 기록은 남지만
    return null;               // 호출자는 실패했다는 사실을 모른 채 null을 받는다
}
// 호출자는 "조회 결과가 없구나"로 해석하고 진행한다.
// 실패와 "정상적으로 결과 없음"이 구분 불가능해졌다.

삼켜진 예외의 진짜 비용

"예외가 안 보인다"가 아니라 "장애를 인지하고 원인을 찾는 시간이 길어진다"이다

이 문장은 추상적으로 들리지만 시간으로 바꾸면 체감이 다르다. 아래 타임라인은 배치의 광범위 catch가 커넥션 풀 고갈과 만났을 때 실제로 벌어지는 일이다.

5-1. 실제로 자주 나오는 형태 — 배치의 광범위 catch

Before건별 실패를 건너뛰려는 의도로 짠 코드
for (Payment p : payments) {
    try {
        settle(p);
    } catch (Exception e) {                        // 일시적 오류를 건너뛰려던 의도였지만
        log.warn("정산 실패 skip: {}", p.getId());  // 예외 객체 e를 로그에 넘기지 않았다
    }
}

① 인지가 늦은 이유 — 실패가 성공처럼 보였다

  • 예외를 잡아서 밖으로 안 던졌으니 에러율 지표가 오르지 않았다
  • 배치의 종료 코드도 정상이었다 → 모니터링이 울릴 근거가 없다
  • 대응 — "건너뛸 수 있는 실패"와 "중단해야 하는 실패"를 예외 타입으로 구분하고 후자는 전파한다
  • 특정 결제 건의 데이터 이상은 건너뛰어도 되지만, 커넥션을 못 얻는 인프라 장애는 즉시 배치를 세우고 알림을 울려야 하는 사건이다

② 원인 확정이 늦은 이유 — 스택트레이스가 없었다

  • 로그에 남은 것은 우리가 쓴 문장뿐이고, 예외 타입도 발생 위치도 없었다
  • 대응 — 광범위 catch를 쓰더라도 예외 객체를 반드시 로그에 포함한다
  • log.warn("...{}", id, e) — 마지막 인자로 예외를 주면 로거가 스택트레이스 전체를 함께 출력한다
  • t5의 3시간이 이 인자 하나로 몇 분이 된다
After예외 객체를 로그에 넘기고, 중단해야 할 실패는 구분해 전파한다
for (Payment p : payments) {
    try {
        settle(p);
    } catch (DataAccessResourceFailureException e) {   // ① 중단해야 하는 실패를 먼저 좁게 잡는다
        // 커넥션을 못 얻는 등의 인프라 장애. 다음 건도 똑같이 실패할 것이므로
        // 건너뛰는 것은 의미가 없고 5만 건을 헛돌게 만들 뿐이다. 즉시 중단한다.
        throw e;
    } catch (Exception e) {                              // ② 건별로 건너뛸 실패만 넓게 잡는다
        // 두 번째 인자로 e를 넘기면 로거가 스택트레이스 전체를 함께 출력한다.
        log.warn("정산 실패 skip: {}", p.getId(), e);
    }
}

넓게 잡을 때의 최소 규칙 두 줄

  • 좁은 catch를 위에, 넓은 catch를 아래에 — 중단해야 할 실패를 먼저 걸러 다시 던진다
  • 로그의 마지막 인자로 예외 객체를 반드시 넘긴다 — log.warn("msg {}", id, e)

인자 하나 차이가 원인 분석 3시간과 3분을 가른다. 이것이 이 문서에서 가장 값싼 개선이다.

그래서 언어와 프레임워크가 움직였다checked 예외의 강제가 이런 형식적 catch를 양산해 실패를 조용히 성공처럼 보이게 만든다는 것 — 이것이 Kotlin, C#이 checked 예외를 아예 언어에서 뺀 이유이고, 스프링이 JDBC의 SQLException(checked)을 DataAccessException(unchecked) 계층으로 전부 변환해서 넘겨주는 이유이기도 하다.

6. 실무의 기본값 — unchecked 도메인 예외 + 경계 한 곳 처리

두 갈래의 원인을 정리하면 결론이 따라 나온다. 문제는 "예외를 만난 계층"과 "예외를 처리할 수 있는 계층"이 다르다는 데 있었다. checked는 그 둘이 같다고 가정하고 만든 장치다.

그렇다면 처리를 처리할 수 있는 한 곳으로 모으고, 그때까지는 예외가 조용히 위로 흐르게 두면 된다. 그게 실무의 기본값이다.

After실무 기본형 — ① unchecked 도메인 예외 ② 던지기만 ③ 경계에서 처리
// ① 도메인 예외는 unchecked로 만든다 — extends RuntimeException
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(Long orderId) {
        super("주문을 찾을 수 없습니다: " + orderId);
    }
}

// ② 비즈니스 코드는 시그니처를 더럽히지 않고 던지기만 한다
public Order findOrder(Long id) {                       // throws가 없다
    return orderRepository.findById(id)
            .orElseThrow(() -> new OrderNotFoundException(id));
}

// ③ 처리는 시스템 경계 한 곳에서 — 스프링이면 @RestControllerAdvice
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ErrorResponse> handle(OrderNotFoundException e) {
        // 여기가 "예외를 HTTP 응답으로 번역할 수 있는" 유일한 계층이다.
        // 중간 계층은 이 예외의 존재조차 몰라도 된다.
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(ErrorResponse.of(e.getMessage()));
    }
}

6-1. 자주 나오는 반문 — "컴파일러의 강제를 포기하면 처리를 잊어버리지 않나?"

걱정의 내용

unchecked로 만들면 아무도 잡으라고 알려 주지 않는다. 그러면 처리를 빠뜨린 예외가 그대로 사용자에게 노출되지 않겠는가?

→

답 — "잊어도 안전하도록 경계를 만들어 두었다"

잡히지 않은 예외는 전역 핸들러까지 올라가고, 거기서 500 응답과 에러 로그가 남는다. 강제의 위치를 옮긴 것이지 안전을 포기한 게 아니다.

이 대비를 한 문장으로

checked = 구멍 날 수 있는 그물을 여러 겹 · 경계 처리 = 구멍 없는 그물을 한 겹

checked 방식의 강제는 빈 catch 한 줄로 무력화된다. 반면 경계 방식은 개발자가 아무것도 안 해도 예외가 반드시 한 곳에 도착한다. 그래서 "강제가 없어서 위험하다"는 직관과 달리, 실제 안전성은 경계 방식이 높다.

6-2. 그래도 checked를 고려할 좁은 경우 — 그리고 그마저 옮겨 가는 중

남아 있는 자리

  • 호출자가 그 자리에서 반드시 복구 분기를 타야 하고, 그걸 잊으면 안 되는 API를 설계할 때
  • 예: 라이브러리 경계에서 "이 실패는 재시도하면 성공할 수 있다"는 사실을 강제로 인지시키고 싶은 경우
  • 즉 "복구가 정상 시나리오의 일부"일 때다

요즘의 답 — 예외가 아니라 결과 타입 가산점

  • Optional, sealed 인터페이스로 만든 Result 타입
  • 호출자가 분기를 빠뜨릴 수 없다 — 컴파일러가 검사한다
  • 예외 생성 비용이 없다 (스택 캡처가 없다)
  • 람다 안에서도 자연스럽게 흐른다

"실패가 정상 흐름의 일부"라면 예외가 아니라 반환값으로 모델링하는 게 낫다. 컴파일러 강제라는 목표는 유지하되, 그 수단을 예외에서 타입으로 옮긴 것이다.

7. 경계에서 만난 checked는 즉시 번역 — cause를 반드시 넘겨서

외부 라이브러리가 던지는 checked 예외는 우리가 없앨 수 없다. Files.readString은 IOException을 던지고, JDBC는 SQLException을 던진다. 그래서 실무 규칙은 "만난 자리에서 즉시 우리 도메인의 unchecked 예외로 번역한다"가 된다.

이때 반드시 지켜야 할 것이 하나 있다. 원인 예외를 cause로 넘겨주는 것이다.

Before원인 유실 — 스택트레이스가 여기서 끊긴다
} catch (IOException e) {
    throw new FileProcessingException("파일 처리 실패");
}
// e를 버렸다. 이 catch 블록이 원인을 삭제한다.
Aftercause 체이닝 — 로그에 "Caused by:"로 이어진다
} catch (IOException e) {
    throw new FileProcessingException("파일 처리 실패: " + path, e);
}
// 두 번째 인자 e 하나가 원인 블록 전체를 살린다.

번역할 때 지키는 세 가지

cause를 넘긴다
new DomainException(msg, e) — 두 번째 인자를 습관으로 만든다.
맥락을 메시지에
"파일 처리 실패: /data/settle/2026-09-01.csv" — 어느 대상인지를 메시지에 넣는다.
로그는 한 곳에서만
던질 거면 여기서 로그를 남기지 않는다. 중복 기록은 노이즈다.
감쌀 때는 어휘를 바꾸는 것이지 정보를 버리는 것이 아니다
"log and rethrow" 안티패턴잡아서 다시 던질 거면 로그는 남기지 않는다. 잡는 곳마다 로그를 찍으면 같은 예외가 세 번, 네 번 중복 기록돼 "이게 몇 건 발생한 사건인가"를 판단할 수 없게 된다. 원칙은 하나다 — 던질 거면 로그는 남기지 말고, 로그를 남길 거면 거기서 처리를 끝낸다.

8. 실무 함정 — @Transactional의 롤백 규칙 사고 다발 지점

이 절이 이 주제에서 가장 실무적인 부분이다. checked/unchecked 선택이 문법 취향이 아니라 데이터가 깨지느냐 마느냐의 문제가 되는 지점이기 때문이다.

8-1. 전제 — 롤백을 결정하는 것은 DB가 아니라 스프링이다

먼저 오해를 하나 풀어야 한다. DB는 "예외가 났으니 롤백하라"는 것을 스스로 알지 못한다. DB 입장에서 트랜잭션은 COMMIT 또는 ROLLBACK 명령을 받아야 끝나고, 애플리케이션에서 예외가 났다는 사실은 DB에 전달되지 않는다.

그럼 누가 결정하는가. @Transactional이 붙은 메서드는 스프링이 만든 프록시로 감싸여 있다.

8-2. 기본 규칙 — checked 예외에서는 롤백하지 않고 커밋한다

읽고 넘어가면 안 되는 한 문장

RuntimeException과 Error에서만 롤백 · checked 예외에서는 롤백하지 않고 커밋한다

예외가 밖으로 던져졌는데도 트랜잭션은 커밋된다. 호출자는 예외를 받아 "실패했구나"라고 판단하는데, DB에는 그 실패 직전까지의 변경이 남아 있다.

RuntimeException · Error → Rollback   /   Checked → Commit

암기 장치 — 앞글자가 짝을 이룬다. C끼리 짝(Checked → Commit)이 함정이다.

Before사고가 나는 코드
@Transactional
public void placeOrder(OrderRequest req) throws StockException {   // StockException은 checked
    orderRepository.save(order);   // ① 주문이 INSERT 된다
    stockService.decrease(req);    // ② 재고가 부족해 StockException(checked)을 던진다
}
[실행 결과]
  ① 주문 INSERT     -> 커밋된다   ★
  ② 재고 차감 실패   -> 예외가 호출자에게 던져진다

  결과: "재고가 없어 실패했다"는 응답을 받았는데 DB에는 주문이 남아 있다.
        결제되지 않은 주문, 재고와 맞지 않는 주문이 쌓인다.
!
이 사고가 늦게 발견되는 이유 — 이상 징후가 어디에도 없다
예외는 제대로 던져졌고, 커밋도 정상적으로 성공했다. 애플리케이션 로그도, DB 에러 로그도, APM 지표도 전부 정상이다. 그래서 데이터가 어긋난 채 며칠이 지난 뒤 정산 대사에서 발견되는 것이 보통이다. 5절의 "삼킨 예외"보다 더 조용한 사고다.

8-3. 해결은 둘 — 어느 쪽을 고르느냐가 이 문서의 결론과 이어진다

해결 ① 권장도메인 예외를 unchecked로 설계한다
public class StockException extends RuntimeException { ... }

// 이제 프록시가 RuntimeException으로 판정해 롤백한다.
// 이후 이 예외를 던지는 모든 트랜잭션이
// 자동으로 안전해진다.

@Transactional
public void placeOrder(OrderRequest req) {   // throws도 사라진다
    orderRepository.save(order);
    stockService.decrease(req);
}
해결 ②checked를 유지해야 한다면 롤백 대상을 명시
@Transactional(rollbackFor = StockException.class)
public void placeOrder(OrderRequest req)
        throws StockException { ... }

// 이 방식의 약점: 이 메서드 하나만 안전해진다.
// 같은 예외를 던지는 다른 트랜잭션 메서드에도
// 매번 붙여야 하고, 새로 추가되는 메서드에서
// 빠뜨리면 같은 사고가 다시 난다.
반대 방향의 설정도 있다특정 unchecked 예외에서 롤백을 막고 싶으면 noRollbackFor를 쓴다. "이 예외는 비즈니스적으로 정상 흐름이라 지금까지의 작업은 유지하고 싶다"는 드문 경우에 쓴다.
롤백 판정 요약 — 세 축(예외 타입 · 설정 · 예외가 프록시에 닿았는가)의 조합
상황프록시가 보는 것결과
RuntimeException 전파롤백 대상 타입ROLLBACK
Error 전파롤백 대상 타입ROLLBACK
checked 예외 전파 (기본 설정)롤백 대상 아님COMMIT ★ 함정
checked 예외 + rollbackFor 지정지정된 롤백 대상ROLLBACK
unchecked + noRollbackFor 지정롤백 제외 대상COMMIT (의도한 것)
메서드 안에서 예외를 잡아 삼킴예외 자체를 못 본다COMMIT (타입 무관)

9. 왜 그런 기본값인가 — 전제가 어긋난 자리 시니어 변별

"기본값이 잘못됐다"고만 외우면 다른 프레임워크에서 다시 헷갈린다. 그 기본값이 왜 그렇게 정해졌는지를 알면 규칙이 하나의 이야기로 붙는다. 이유는 두 겹이다.

예상된 갈림길에서 지금까지 한 일을 전부 무효화하는 것이 항상 옳지는 않다. "쿠폰이 이미 사용됨"이라는 checked 예외를 만든 설계자는 호출자가 그것을 잡아 다른 쿠폰으로 재시도하기를 기대했을 수 있다. 반대로 NullPointerException은 그냥 버그이므로 지금까지 한 일을 신뢰할 수 없고, 전부 되돌리는 것이 안전하다.

여기서 이 문서 전체를 관통하는 결론이 나온다

규칙을 외워서 피하는 것보다 규칙이 필요 없는 설계로 가는 쪽이 안전하다

6절에서 정한 "도메인 예외는 unchecked로 통일"이라는 원칙은 시그니처를 깨끗하게 하려는 취향 문제가 아니다. 그 원칙을 지키면 롤백 함정 자체가 생기지 않는다. rollbackFor를 빠뜨렸는지 매번 검사하는 대신, 빠뜨릴 것이 없는 구조로 옮기는 것이다.

10. 예외를 삼키면 롤백은 후보에도 없다

5절의 "예외 삼키기"와 8절의 "롤백 규칙"이 만나면 더 조용한 사고가 된다.

Before트랜잭션 안에서 예외를 잡아 삼킨다
@Transactional
public void placeOrder(OrderRequest req) {
    orderRepository.save(order);
    try {
        stockService.decrease(req);
    } catch (Exception e) {
        log.warn("재고 차감 실패, 주문은 그대로 진행");   // 예외를 밖으로 안 던진다
    }
}

여기서는 checked냐 unchecked냐를 따질 것도 없다

예외가 프록시까지 올라가지 않으면 롤백은 처음부터 후보에 없다

8절의 함정이 "타입을 잘못 골라서" 생긴다면, 이 절의 함정은 "판정 기회 자체를 없애서" 생긴다. catch 한 줄이 트랜잭션 설계를 덮어쓴다.

10-1. 의도적으로 일부만 실패해도 진행하고 싶다면 — 그것대로 설계한다

별도 트랜잭션으로 분리
재고 차감을 REQUIRES_NEW로 떼어내 실패해도 주문 트랜잭션에 영향이 없게 만든다.
실패를 기록해 후처리
실패 건을 별도 테이블에 남기고 재처리 배치나 알림으로 이어 붙인다.
비동기 이벤트로 분리
커밋 이후에 처리해도 되는 일이라면 트랜잭션 경계 밖으로 밀어낸다.

어느 쪽이든 — "잡아서 로그만 남기고 넘어간다"는 코드가 데이터 정합성 결정을 내리고 있다는 사실을 인지한 상태여야 한다. 그 결정이 의식적이면 설계고, 무의식적이면 사고다.

11. 전체 한 장 · 인출 카드

11-1. 실무 결정 트리 — "이 실패를 무엇으로 표현할까"

11-2. 인출 카드 — 면접 전날 이것만 다시 본다

① 정의 · 판정

checked = Throwable − Error 가지 − RuntimeException 가지
강제의 실체 = catch 하거나 throws 하거나 (문은 두 개뿐)
판정법 = 상속 계보를 올라가다 RuntimeException·Error를 만나면 unchecked

② 무너진 두 갈래 — 네 글자로

던지면 오염 · 잡으면 은폐
오염 (throws)
SQLException이 컨트롤러까지 → 추상화 누수, 교체 시 전 파일 수정, 람다와 비호환

③ 실무 3원칙

  • 도메인 예외는 extends RuntimeException — 중간 계층 시그니처를 더럽히지 않는다
  • 처리는 경계 한 곳 — @RestControllerAdvice가 그물이고, 잊어도 500과 로그가 남는다
  • 외부 checked는 만난 자리에서 번역 + cause 보존 — 감싸는 건 어휘 변경이지 정보 삭제가 아니다

④ 롤백 3조건 — 하나라도 어긋나면 커밋된다

① 프록시를 거쳤나
자기 호출(this.method())·비공개 메서드면 @Transactional 자체가 무효
② 예외가 올라갔나
안에서 삼키면 프록시는 정상 반환으로 인식 → 판정 기회 없음
③ 롤백 대상 타입인가
기본은 RuntimeException·Error뿐 — checked는 커밋

11-3. 코드 리뷰에서 기계적으로 확인할 지점

1
빈 catch 블록 / 주석만 있는 catch — // TODO가 들어 있으면 거의 확실히 은폐다. 예외 객체를 로그에 넘겼는지부터 본다.
2
catch (Exception e) 안에서 return null / return 빈 리스트 — 실패와 "정상적으로 결과 없음"이 섞인다. 호출자는 구분할 방법이 없다.
3
감싸면서 cause를 안 넘긴 throw new ...Exception("메시지") — 인자 하나가 빠졌는지만 보면 된다.
4
서비스·컨트롤러 시그니처의 throws — 저수준 예외가 올라오고 있다는 신호다. 번역 지점이 없다는 뜻.
5
@Transactional 메서드가 checked 예외를 던지는데 rollbackFor가 없다 — 커밋된다. 예외 계층을 unchecked로 바꾸는 쪽을 먼저 제안한다.
6
@Transactional 메서드 안의 try-catch — 롤백 의도가 있는지 확인한다. 삼키면 롤백은 후보에도 없다.
7
같은 예외에 대한 로그가 여러 계층에 있다 — "log and rethrow" 중복이다. 최종 처리 지점 한 곳으로 모은다.

12. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 각 답 마지막의 "정리 문장"은 면접에서 그대로 말할 수 있는 형태로 다듬어 두었다.

Spring @Transactional은 Checked 예외가 발생하면 롤백하나요?힌트: 직관과 반대다. 그리고 "그래서 저는 이렇게 합니다"까지 붙여야 답이 끝난다 핵심

기본 설정으로는 롤백하지 않고 커밋한다. 기본 롤백 대상은 RuntimeException과 Error뿐이다. 예외는 호출자에게 정상적으로 던져지는데 DB에는 그 직전까지의 변경이 커밋된 채로 남는다.

checked 예외로도 롤백하려면 @Transactional(rollbackFor = MyCheckedException.class)를 명시해야 한다. 반대로 특정 unchecked 예외에서 롤백을 막고 싶으면 noRollbackFor를 쓴다.

여기까지가 사실 관계이고, 그다음에 "그래서 저는 이렇게 합니다"를 붙이는 것이 좋다. 실무에서는 도메인 예외를 처음부터 RuntimeException 기반으로 설계해 이 함정 자체를 없애는 편이 안전하다. rollbackFor는 메서드마다 붙여야 하므로 새로 추가되는 메서드에서 빠뜨릴 여지가 계속 남지만, 예외 계층을 바꾸면 한 번에 전부 해결된다.

가산점 — 기본값의 유래EJB 시절의 컨테이너 관리 트랜잭션 관례를 계승한 것이고, "checked = 복구 가능한 비즈니스 상황이므로 지금까지의 작업은 유효하다"는 원래 의미에서는 일관적인 규칙이다. 우리가 checked를 그 의미대로 쓰지 않기 때문에 함정이 되는 것이다.

정리 문장 — "기본값은 커밋입니다. 롤백 대상은 RuntimeException과 Error뿐이라 rollbackFor를 명시하지 않으면 checked 예외에서는 커밋됩니다. 저는 rollbackFor를 메서드마다 붙이는 대신 도메인 예외를 unchecked로 통일해 함정 자체를 없애는 쪽을 택합니다."

왜 Kotlin이나 C# 같은 최신 언어는 Checked 예외를 없앴나요?힌트: 잃은 것이 셋이다. 그리고 "목표까지 버린 건 아니다"로 닫아야 완성이다 시니어 변별

이론은 좋았지만 대규모 코드베이스에서 얻는 것보다 잃는 것이 많다는 경험적 결론이 쌓였기 때문이다. 잃은 것이 셋이다.

① 처리할 수 없는 중간 계층까지 시그니처가 오염된다. 저장소의 SQLException이 서비스와 컨트롤러의 시그니처에 번져 구현 세부사항이 위로 새어 나온다(추상화 누수). 저장소를 교체하면 그 예외가 지나간 모든 파일을 고쳐야 한다.

② 강제된 catch가 형식적 처리(삼키기)를 양산했다. 컴파일 에러를 없애려고 만든 빈 catch 블록이 장애를 은폐한다. 강제의 목적은 안전이었는데 결과는 정반대가 됐다.

③ 람다·고차함수와 조합이 안 된다. 표준 함수형 인터페이스가 checked를 던질 수 없어 Stream 안에서 매번 try-catch로 감싸야 하고, 그러면 결국 unchecked로 바꿔 던지게 된다.

그렇다고 "복구 가능성을 타입으로 강제한다"는 목표까지 버린 것은 아니라는 점을 덧붙이면 답이 완성된다. 그 목표는 예외가 아니라 반환 타입으로 옮겨 갔다 — Kotlin의 sealed class나 Result 타입처럼 "실패가 정상 흐름의 일부"인 경우를 값으로 표현하는 방식이다. 반환값이면 호출자가 분기를 빠뜨릴 수 없고, 람다 안에서도 자연스럽게 흐르며, 예외 생성 비용도 들지 않는다.

정리 문장 — "시그니처 오염, 형식적 catch, 람다 비호환 셋 때문입니다. 다만 강제라는 목표를 버린 게 아니라 그 수단을 예외에서 반환 타입(Result·sealed)으로 옮긴 것이라고 보는 게 정확합니다."

예외를 감쌀 때(wrapping) 꼭 지켜야 할 것은?힌트: 두 번째 인자 하나 · 그리고 로그를 몇 번 남길 것인가 핵심

원인 예외를 cause로 반드시 전달하는 것이다 (new DomainException(msg, e)).

cause를 빼뜨리면 스택트레이스 체인이 끊겨 로그에 최종 예외만 남는다. "파일 처리 실패"라는 우리 메시지는 남지만 어떤 파일이 왜 실패했는지(권한인지, 없는 파일인지, 디스크가 찼는지)는 사라진다. cause를 넘기면 로그에 Caused by: 블록으로 원본 예외의 타입과 스택트레이스가 이어져 나온다.

여기에 하나 더 얹으면 좋다. 잡아서 다시 던질 거면 로그는 한 군데서만 남긴다. 잡는 곳마다 로그를 찍으면 같은 예외가 세 번, 네 번 중복 기록돼 로그 노이즈가 되고, 정작 "이게 몇 건 발생한 사건인가"를 판단하기 어려워진다. 이것을 "log and rethrow" 안티패턴이라고 부른다.

던질 거면 로그는 남기지 말고, 로그를 남길 거면 거기서 처리를 끝낸다

정리 문장 — "두 번째 인자로 원본 예외를 넘겨 Caused by: 체인을 살리는 것이 첫째고, 로그는 최종적으로 처리하는 한 곳에서만 남기는 것이 둘째입니다. 감싸는 목적은 상위 계층 어휘로 번역하는 것이지 정보를 버리는 게 아니니까요."

Error는 catch하면 안 되나요? OutOfMemoryError는요?힌트: catch 블록이 하려는 일 대부분이 "새 객체 생성"이다

Error는 JVM 수준에서 이미 무너진 상태를 알리는 것이라 애플리케이션이 잡아서 복구할 대상이 아니다. 잡아서 무엇을 하려 해도 그 코드가 정상 동작한다는 보장이 없다.

OutOfMemoryError가 대표적이다. 이 예외가 나왔다는 것은 힙에 새 객체를 만들 공간이 없다는 뜻인데, catch 블록에서 하는 거의 모든 일(로그 문자열 만들기, 예외 객체 만들기, 컬렉션에 담기)이 새 객체를 필요로 한다. 잡아서 진행하면 어느 지점에서 다시 터질지 알 수 없고, 이미 다른 스레드가 같은 이유로 실패해 애플리케이션 상태가 부분적으로 깨져 있을 가능성도 높다.

실무 대응은 catch가 아니라 사후 분석 준비다. -XX:+HeapDumpOnOutOfMemoryError 옵션을 걸어두면 OOM 발생 시점의 힙 덤프가 파일로 남고, 그 덤프를 열어 무엇이 힙을 채웠는지 분석한다. 프로세스는 재시작하는 것이 맞다.

가산점 — Throwable을 잡는 정당한 자리 하나프레임워크의 최상위 루프(스레드풀의 작업 래퍼, 배치의 스텝 실행기)에서는 Throwable을 잡는다. 목적이 "복구"가 아니라 "기록하고 격리"이기 때문이다. 작업 하나가 Error로 죽었을 때 그 사실을 로그로 남기고 워커 스레드는 살려 다음 작업으로 넘어가게 하려는 것이지, Error 상황을 정상으로 되돌리려는 게 아니다.

정리 문장 — "복구 목적으로는 잡지 않습니다. OOM은 catch 블록 자체가 객체를 필요로 해서 잡아도 진행이 보장되지 않으니, 힙 덤프 옵션을 걸어 두고 프로세스를 재시작합니다. 다만 최상위 루프에서 기록·격리 목적으로 Throwable을 잡는 것은 다른 이야기입니다."

예외를 흐름 제어(if 대용)로 쓰면 왜 안 되나요?힌트: 성능은 두 번째 이유다. 첫 번째는 관측 가능성이다

이유가 둘인데, 성능보다 첫 번째가 더 중요하다.

① 의미론이 왜곡된다. 예외는 "예외적 상황"이라는 신호다. 정상 분기에 쓰면 코드를 읽는 사람이 "여기가 실패 경로구나"라고 오해하고, 모니터링 시스템도 함께 속는다. APM의 에러율 지표나 예외 발생 건수 알림이 정상 흐름 때문에 계속 올라가면, 진짜 장애가 났을 때 그 신호가 묻힌다. 관측 가능성이 망가지는 쪽이 실무에서는 더 아프다.

② 비용이 든다. 예외 객체를 만들 때 fillInStackTrace()가 호출되어 그 시점의 호출 스택 전체를 캡처한다. 스택이 깊을수록 비싸지므로 루프 안에서 예외로 분기하면 성능이 눈에 띄게 나빠진다. 일반적인 if 분기와는 비교가 안 되는 비용이다.

"없음이 정상"인 경우는 예외가 아니라 Optional 반환이나 boolean을 돌려주는 검사 메서드로 모델링하는 게 맞다. findById가 없는 id에 예외를 던지는 게 아니라 Optional.empty()를 돌려주는 이유가 이것이다.

가산점예외를 제어 흐름에 의도적으로 쓰는 일부 라이브러리는 Throwable의 생성자 옵션 writableStackTrace=false로 스택트레이스 캡처를 아예 생략한다. 비용의 대부분이 스택 캡처라는 것을 역으로 보여주는 사례다.

정리 문장 — "의미론과 관측 가능성이 먼저고, fillInStackTrace()의 스택 캡처 비용이 그다음입니다. 실패가 정상 흐름의 일부라면 예외가 아니라 Optional·Result 같은 반환값으로 모델링합니다."

rollbackFor까지 붙였는데도 롤백이 안 되는 경우가 있나요?힌트: 롤백이 일어나려면 조건이 셋인데, 예외 타입은 그중 하나일 뿐이다 함정

있다. 롤백 판정은 프록시가 하기 때문에 조건이 셋이고, rollbackFor는 그중 세 번째만 해결한다.

1
프록시를 거쳐서 호출됐는가 — 같은 클래스 안에서 this.otherMethod()로 부르면(자기 호출) 프록시를 통과하지 않아 @Transactional이 아예 적용되지 않는다. 프록시 모드에서는 public이 아닌 메서드에 붙인 경우도 마찬가지로 적용되지 않는다.
2
예외가 프록시까지 올라갔는가 — 메서드 안에서 catch로 삼키면 프록시 입장에서는 정상 반환이므로 커밋한다. 롤백은 후보에도 오르지 않는다.
3
그 예외가 롤백 대상인가 — 여기서야 RuntimeException/Error냐, rollbackFor에 해당하냐를 따진다.

정리 문장 — "롤백은 프록시가 예외를 봐야 판정합니다. 그래서 ①자기 호출로 프록시를 안 거쳤거나 ②안에서 예외를 삼켰거나 ③타입이 롤백 대상이 아니거나 셋 중 하나면 커밋됩니다. rollbackFor는 ③만 고치는 처방이라, ①·②를 먼저 확인합니다."

트랜잭션 안에서 예외를 잡아 로그만 남겼는데 UnexpectedRollbackException이 났습니다. 왜죠?힌트: 안쪽 메서드도 @Transactional이었다면, 예외를 잡은 것과 별개로 이미 남은 표시가 있다 시니어 변별

안쪽에서 호출한 메서드도 @Transactional이고 전파 속성이 기본값(REQUIRED)이면 새 트랜잭션이 아니라 바깥 트랜잭션에 참여한다. 그 안쪽이 예외로 끝나면 스프링은 공유 중인 트랜잭션에 "이건 롤백해야 함(rollback-only)" 표시를 남긴다.

바깥에서 그 예외를 잡아 삼키고 정상 반환해도 표시는 지워지지 않는다. 커밋을 시도하는 순간 스프링이 "롤백 표시가 된 트랜잭션을 커밋하려 한다"며 UnexpectedRollbackException을 던지고 실제로는 전부 롤백된다.

대응은 설계를 명확히 하는 것이다 — 정말 실패를 격리하고 싶다면 안쪽을 REQUIRES_NEW로 분리해 별도 트랜잭션으로 만들거나, 애초에 트랜잭션 경계 밖에서 호출하도록 구조를 바꾼다.

정리 문장 — "안쪽 @Transactional이 바깥 트랜잭션에 참여한 상태에서 실패해 rollback-only 표시가 찍혔기 때문입니다. 예외를 잡아도 표시는 남으니 커밋 시점에 UnexpectedRollbackException이 납니다. 부분 실패를 허용하려면 REQUIRES_NEW로 트랜잭션을 분리해야 합니다."

그럼 Checked 예외를 쓸 자리는 이제 없나요?힌트: 좁게 남아 있다. 그리고 그 자리마저 요즘은 다른 수단으로 옮겨 간다

좁게 남아 있다. 호출자가 그 자리에서 반드시 복구 분기를 타야 하고, 그걸 잊으면 안 되는 API를 설계할 때다. 예를 들어 라이브러리 경계에서 "이 실패는 재시도하면 성공할 수 있다"는 사실을 호출자에게 강제로 인지시키고 싶은 경우다.

다만 요즘은 이것도 예외 대신 결과 타입으로 표현하는 흐름이 강하다. Optional, sealed 인터페이스로 만든 Result 타입 같은 것들이다. "실패가 정상 흐름의 일부"라면 예외가 아니라 반환값으로 모델링하는 게 낫다. 반환값이면 호출자가 분기를 빠뜨릴 수 없고(컴파일러가 검사한다), 예외 생성 비용도 없으며, 람다 안에서도 자연스럽게 흐른다.

컴파일러 강제라는 목표는 유지하되, 수단을 예외에서 타입으로 옮긴 것

정리 문장 — "호출자가 반드시 복구 분기를 타야 하는 라이브러리 경계 정도가 남습니다. 다만 요즘은 그마저 Optional·Result 같은 반환 타입으로 옮겨 갑니다 — 강제라는 목표는 같고 수단이 더 낫기 때문입니다."

try-with-resources에서 본문과 close()가 둘 다 예외를 던지면 어떤 게 올라오나요?힌트: 하나는 전파되고, 다른 하나는 "붙어서" 따라온다 시니어 변별

본문에서 던진 예외가 호출자에게 전파되고, close()가 던진 예외는 거기에 "억제된 예외(suppressed)"로 첨부된다. 로그에는 Suppressed: 블록으로 함께 출력되고, 코드에서는 e.getSuppressed()로 꺼낼 수 있다.

이 설계가 왜 중요한지는 try-with-resources 이전의 수동 finally 코드와 비교하면 보인다. finally 안에서 close()가 예외를 던지면 본문의 진짜 원인 예외가 덮어써져 사라졌다. 원인이 통째로 증발하는 이 사고를 언어 차원에서 막은 것이 억제된 예외다.

같은 결의 규칙이 문서의 cause 보존과 목적이 같다 — "예외를 다루는 모든 자리에서 원인 정보를 잃지 않는다." cause 체이닝, 억제된 예외, 로그에 예외 객체 넘기기가 전부 같은 원칙의 세 얼굴이다.

정리 문장 — "본문 예외가 전파되고 close() 예외는 억제된 예외로 첨부됩니다. 수동 finally에서는 close 예외가 원인 예외를 덮어써 버리던 문제를 언어가 해결한 것입니다."

Kotlin에서 자바의 checked 예외를 호출하면 어떻게 되나요? @Throws는 왜 있나요?힌트: Kotlin에는 checked가 없는데, JVM 바이트코드에는 throws 정보가 남는다

Kotlin에는 checked 예외 개념 자체가 없다. 자바의 IOException을 던지는 메서드를 호출해도 Kotlin 컴파일러는 catch도 선언도 요구하지 않는다. 안 잡으면 그냥 런타임에 위로 전파된다.

그래서 반대 방향이 문제가 된다 — Kotlin 함수를 자바에서 호출하는 경우다. Kotlin이 컴파일한 메서드에는 throws 정보가 붙지 않으므로, 자바 호출자는 그 메서드가 checked 예외를 던진다는 사실을 알 수 없고 잡을 수도 없다. @Throws(IOException::class)는 생성되는 바이트코드에 throws 절을 넣어 달라는 지시이고, 목적은 자바 상호운용이다.

정리 문장 — "Kotlin은 checked를 강제하지 않으므로 호출 쪽은 아무 제약이 없습니다. @Throws는 Kotlin을 위한 게 아니라 자바 호출자에게 throws 시그니처를 노출하기 위한 상호운용 장치입니다."

catch (Exception e)로 넓게 잡는 건 항상 나쁜가요?힌트: 자리에 따라 다르다. 나쁜 건 넓이가 아니라 그 안에서 하는 일이다

항상 나쁜 것은 아니다. 시스템 경계(전역 핸들러)나 배치 스텝, 스레드풀 작업 래퍼처럼 "여기서 끝내야 하는 자리"에서는 오히려 넓게 잡는 것이 맞다. 안 그러면 예상 못 한 예외 하나가 워커 스레드를 죽이거나 응답 대신 스택트레이스를 노출한다.

문제는 넓이가 아니라 그 안에서 하는 일이다. 넓게 잡을 때 지켜야 할 것이 셋이다.

  • 예외 객체를 반드시 로그에 넘긴다 — log.warn("...{}", id, e). 이 인자 하나가 원인 분석 시간을 몇 시간에서 몇 분으로 줄인다.
  • 중단해야 하는 실패는 구분해 먼저 잡고 다시 던진다 — 인프라 장애를 건별 실패와 같이 취급하면 5만 건을 헛돈다.
  • "처리했다"고 말할 수 있어야 한다 — 응답으로 바꿨거나, 대체 경로로 갔거나, 실패를 기록해 후처리 대상으로 만들었거나. 아무것도 안 했으면 그건 삼킨 것이다.

정리 문장 — "경계에서는 넓게 잡는 게 정상입니다. 나쁜 건 넓이가 아니라 로그에 예외를 안 넘기고, 중단할 실패를 구분하지 않고, 아무 조치 없이 계속 진행하는 것입니다."

InterruptedException은 왜 특별 취급하나요? 로그만 남기면 안 되나요?힌트: 이 예외를 잡는 순간 사라지는 상태가 하나 있다 시니어 변별

InterruptedException은 "누군가 이 스레드에게 그만두라고 요청했다"는 신호다. 그런데 이 예외가 던져지는 순간 스레드의 인터럽트 상태 플래그가 초기화된다. 그래서 잡아서 로그만 남기고 넘어가면 "중단 요청이 있었다"는 사실이 그 자리에서 증발하고, 바깥의 루프나 스레드풀은 아무 일 없다는 듯 계속 돈다. 종료가 안 되는 애플리케이션의 흔한 원인이 이것이다.

대응은 둘 중 하나다 — 그대로 다시 던지거나, 던질 수 없는 자리(예: Runnable.run())라면 Thread.currentThread().interrupt()로 플래그를 복원하고 작업을 스스로 중단한다.

이 문서와 이어지는 지점이것도 결국 "삼킴"의 한 형태다. 다른 점은 삼켜지는 것이 장애 정보가 아니라 제어 신호라는 것뿐이다. catch가 정보를 없애는 자리라는 관점은 그대로 적용된다.

정리 문장 — "예외가 던져지면서 인터럽트 플래그가 초기화되기 때문입니다. 로그만 남기면 중단 요청이 사라져 스레드가 안 멈추므로, 다시 던지거나 Thread.currentThread().interrupt()로 복원합니다."

throws Exception이라고 뭉뚱그려 선언하면 뭐가 문제인가요?힌트: 호출자가 잡을 수 있는 것과 잡아야 하는 것이 달라진다

정보가 사라진다. 호출자는 실제로 무엇이 날아올 수 있는지 알 수 없고, 구체 타입별로 다르게 처리하고 싶어도 catch (Exception e) 하나로 뭉갤 수밖에 없다. 그러면 정말 잡으면 안 되는 예외까지 함께 잡힌다.

전파도 막힌다. throws Exception은 호출 체인 전체에 그대로 번지기 때문에 상위 계층까지 같은 선언을 달아야 하고, 4절의 시그니처 오염을 최대치로 만든다.

선언을 좁히면 자바가 도와주는 것도 있다 — multi-catch(catch (IOException | SQLException e))로 중복을 줄이고, 정밀한 재던지기(precise rethrow) 덕분에 catch (Exception e) { throw e; }를 써도 컴파일러가 실제 던져질 수 있는 타입만 추론해 준다.

정리 문장 — "호출자가 구체 타입별로 대응할 방법을 잃고, 잡으면 안 되는 예외까지 함께 잡히기 때문입니다. 선언은 실제로 던지는 타입만 좁게 적고, 중복은 multi-catch로 줄입니다."

도메인 예외 계층은 어떻게 설계하나요? 예외마다 클래스를 다 만드나요?힌트: 경계에서 무엇을 보고 응답을 만들지 먼저 정하면 답이 나온다

기준은 하나다 — 경계(전역 핸들러)가 응답을 만들 때 필요한 구분만 타입으로 만든다.

타입으로 나눌 가치가 있는 것

  • HTTP 상태·처리 방식이 달라지는 축 — "없음(404)", "권한 없음(403)", "규칙 위반(409/422)", "외부 연동 실패(502)"
  • 호출자가 코드로 분기해야 하는 구분 (재시도 가능 / 불가능)

타입 말고 데이터로 담을 것

  • 같은 404 안에서의 세부 사유 — 주문 없음/쿠폰 없음
  • 사용자 메시지, 에러 코드, 파라미터 → 에러 코드 enum + 메시지 필드로

실무에서 흔한 형태는 최상위 BusinessException extends RuntimeException 하나 + 에러 코드 enum이고, 상태 코드가 갈리는 몇 개만 하위 타입으로 둔다. 예외 클래스가 수백 개로 늘어나는 설계는 경계 핸들러를 감당 못 하게 만든다.

정리 문장 — "경계에서 응답이 달라지는 축만 타입으로 나누고, 나머지 구분은 에러 코드로 담습니다. 기준을 "응답이 달라지는가"에 두면 계층이 필요 이상으로 커지지 않습니다."

스프링은 왜 SQLException을 DataAccessException으로 바꿔서 주나요?힌트: 이 문서의 두 갈래를 프레임워크가 대신 해결해 준 사례다

이 문서의 처방을 프레임워크가 대신 실행해 준 것이다. JDBC의 SQLException은 checked라서 그대로 두면 저장소→서비스→컨트롤러로 throws가 번진다. 스프링은 그것을 unchecked인 DataAccessException 계층으로 변환해 넘긴다.

이득이 둘이다. ① 시그니처가 깨끗해지고, ② 벤더 종속이 사라진다. SQLException은 무엇이 잘못됐는지를 벤더마다 다른 에러 코드로 알려 주기 때문에, 그것으로 분기하면 DB를 바꾸는 순간 코드가 깨진다. 스프링은 그 코드를 해석해 DuplicateKeyException·DataIntegrityViolationException처럼 의미가 드러나는 타입으로 바꿔 준다.

그리고 unchecked라서 @Transactional의 기본 롤백 규칙과도 자연스럽게 맞물린다 — 이 문서 8절의 함정이 스프링 데이터 접근 계층에서는 애초에 생기지 않는 이유다.

정리 문장 — "checked인 SQLException이 상위 계층까지 번지는 것을 막고, 벤더마다 다른 에러 코드를 의미 있는 타입으로 번역하기 위해서입니다. 결과적으로 기본 롤백 규칙과도 맞아떨어집니다."

30초 답변 대본 — 이 순서로 말한다

  1. 정의: "가르는 기준은 컴파일러가 처리를 강제하는가 하나입니다. Error와 RuntimeException 가지가 unchecked이고, 그 둘을 뺀 나머지가 checked입니다."
  2. 강제의 실체: "강제란 catch하거나 throws로 선언하거나 둘 중 하나를 안 하면 컴파일이 안 된다는 뜻입니다."
  3. 의도와 붕괴: "의도는 복구 가능한 외부 상황 = checked였는데, 예외를 만난 계층과 처리할 수 있는 계층이 달라서 시그니처 오염과 기계적 catch 두 갈래로 무너졌습니다."
  4. 실무 기본값: "그래서 도메인 예외는 unchecked로 통일하고, 처리는 전역 핸들러 한 곳에 모읍니다. 외부 checked는 만난 자리에서 cause를 보존해 즉시 번역합니다."
  5. 함정: "여기에 @Transactional의 기본 롤백 대상이 RuntimeException과 Error뿐이라는 점을 덧붙입니다. checked는 예외가 던져져도 커밋되므로, unchecked 통일은 정합성 대책이기도 합니다."

3번(왜 무너졌는가)을 빼면 "문법은 아는 사람"에서 끝난다. 정의는 짧게, 붕괴와 함정에 시간을 쓴다.

한 줄 요약
checked와 unchecked를 가르는 것은 컴파일러의 강제 여부 하나이고 계층도에서 Error와 RuntimeException 가지를 뺀 나머지가 checked라는 정의가 전부지만, "복구 가능하면 checked"라는 원래 의도는 저수준 예외가 컨트롤러까지 번지는 시그니처 오염과 컴파일 에러만 없애려는 빈 catch의 장애 은폐라는 두 갈래로 무너졌기 때문에, 실무는 도메인 예외를 unchecked로 통일하고 시스템 경계에서 일괄 처리하며, 외부의 checked는 만난 자리에서 cause를 보존해 즉시 번역하고, @Transactional이 checked에서는 롤백하지 않고 커밋한다는 기본값까지 챙기는 것으로 수렴했다 — 예외를 문법이 아니라 데이터 정합성과 장애 대응 시간을 좌우하는 설계 요소로 다루는 것이 이 질문의 본체다.
