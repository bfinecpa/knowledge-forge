Java record — "이 타입의 상태는 헤더에 적힌 컴포넌트가 전부다"라는 선언
보일러플레이트를 줄이는 문법 설탕이 아니다. 의미 선언이 먼저고 자동 생성은 그 결과다 — 그래서 진짜 가치는 줄 수 절약이 아니라 버그 계열 하나의 원천 차단이다

면접 질문: "Java의 record는 언제 쓰나요?"

핵심 관전 포인트 — record는 보일러플레이트를 줄이는 문법 설탕이 아니라 "이 타입의 상태는 헤더에 적힌 컴포넌트가 전부이고, 상태가 같으면 같은 것으로 취급한다"는 의미 선언이다. 그 선언을 했기 때문에 컴파일러가 equals/hashCode/toString/접근자를 대신 만들어 줄 수 있는 것이고, 순서가 반대가 아니다. 그래서 진짜 가치는 타이핑 절약이 아니라 필드를 추가했는데 equals를 갱신하지 않아 HashMap에서 조용히 못 찾게 되는 버그 계열의 원천 차단이다. DTO·값 객체·복합 키·스트림 중간 결과처럼 "상태가 곧 정체성"인 자리에 쓰고, 검증과 정규화는 컴팩트 생성자에 둔다. 반대로 JPA 엔티티에는 쓸 수 없고(기본 생성자 없음, 필드가 final이라 리플렉션 주입과 더티 체킹 불가, 클래스가 final이라 지연 로딩 프록시 불가, 그리고 근본적으로 식별자 정체성과 값 정체성의 충돌), 가변 컬렉션을 컴포넌트로 받으면 얕은 불변에 그치므로 컴팩트 생성자에서 List.copyOf로 방어적 복사를 해야 한다.
  • 1
    인과의 방향부터 뒤집어 말합니다. record는 "DTO를 짧게 쓰는 문법"이 아니라 "이 타입의 상태는 헤더의 컴포넌트가 전부다"라는 약속입니다. 그 약속이 참이면 "같음"의 기준이 유일하게 정해지고(모든 컴포넌트가 같으면 같다), 그제서야 컴파일러가 equals/hashCode/toString/접근자를 만들 수 있습니다. 보일러플레이트 제거는 목적이 아니라 결과입니다.
  • 2
    그래서 실무 가치는 줄 수가 아니라 버그 차단입니다. 손으로 쓴 equals는 필드가 추가될 때 조용히 깨집니다 — 새 필드를 안 보는 equals/hashCode가 남으면 HashMap이 남의 값을 돌려주는데 컴파일러는 아무 말도 하지 않습니다. record는 컴포넌트 정의에서 매번 다시 생성되므로 "필드는 늘었는데 equals는 옛날"이라는 상태 자체가 존재할 수 없습니다. 쓸 자리는 DTO·조회 프로젝션·값 객체·복합 키·로컬 튜플·설정 바인딩이고, 검증과 정규화는 컴팩트 생성자에 둡니다.
  • 3
    경계까지 말하면 완성됩니다. record가 보장하는 것은 필드 재대입 금지뿐이라 가변 컬렉션을 받으면 얕은 불변에 그치므로 컴팩트 생성자에서 List.copyOf로 방어적 복사를 해야 하고, JPA 엔티티로는 쓸 수 없습니다 — 기본 생성자가 없고, 필드가 리플렉션으로도 주입되지 않아 더티 체킹이 성립하지 않고, final 클래스라 지연 로딩 프록시를 못 만들며, 무엇보다 엔티티의 정체성은 식별자, record의 정체성은 값 전체라 모델이 충돌합니다. 한 줄로 "엔티티는 클래스, 계층을 오가는 데이터는 record"입니다.

0. 질문 + 출제 의도 — 무엇을 보는 질문인가

질문 — "Java의 record는 언제 쓰나요?"

출제 의도는 세 겹이다. 불변 데이터 캐리어를 언어가 직접 지원하는 흐름(record는 Java 16에서 정식)을 따라오고 있는지, DTO 보일러플레이트를 어떻게 줄이는지 — 즉 언어 버전 업의 이점을 실무에 수용하는 속도를 본다. 그리고 결정적으로 "record가 뭔지"보다 "우리 코드베이스의 어떤 클래스를 record로 바꿨고 어떤 클래스는 안 바꿨는가"의 판단을 본다.

이렇게 답하면 "문법을 아는 사람"
  • "DTO 만들 때 씁니다. 코드가 짧아져요."
  • "equals, hashCode, toString을 자동으로 만들어 줍니다."
  • "Lombok @Value 같은 겁니다."

틀린 말은 없다. 그런데 전부 결과에 대한 서술이고, 왜 그게 가능한지와 어디에 쓰면 안 되는지가 없다.

이렇게 답하면 "경계를 아는 사람"
  • 인과를 뒤집어 말한다 — 의미 선언이 먼저, 자동 생성은 결과.
  • 막아 주는 버그를 구체적으로 든다 — 필드 추가 후 equals 미갱신 → HashMap 오작동.
  • 못 쓰는 자리를 이유와 함께 든다 — JPA 엔티티, 가변 컬렉션 컴포넌트.

1. 인과의 방향 — 문법 절약이 아니라 의미 선언

1-1. 출발점 — 값 세 개를 나르는 데 필요했던 코드

Java 16 이전, 필드 몇 개를 담는 불변 클래스 하나를 규약에 맞게 만들려면 이만큼이 필요했다.

before 하는 일은 값 세 개를 담아 나르는 것뿐인데
public final class OrderSummary {
    private final Long orderId;
    private final String customerName;
    private final long amount;

    public OrderSummary(Long orderId,
            String customerName, long amount) {
        this.orderId = orderId;
        this.customerName = customerName;
        this.amount = amount;
    }
    public Long getOrderId() { return orderId; }
    public String getCustomerName() { return customerName; }
    public long getAmount() { return amount; }

    @Override public boolean equals(Object o) { /* 필드 3개 비교 */ }
    @Override public int hashCode() { /* 필드 3개 조합 */ }
    @Override public String toString() { /* 필드 3개 나열 */ }
}

붉게 칠한 두 줄이 3절에서 조용히 썩는 곳이다.

after 같은 것이 한 줄이다
public record OrderSummary(Long orderId,
        String customerName, long amount) {}
여기서 대부분의 설명이 멈춘다 "50줄이 한 줄이 됐다, 편하다." 그런데 이렇게만 소개하면 절반만 전달된다.
왜 컴파일러가 이 코드를 대신 써 줄 수 있는지가 빠져 있기 때문이다. 그 이유를 아는 것이 어디에 쓰고 어디엔 못 쓰는지를 아는 것과 같은 문제다.

1-2. 컴파일러가 대신 써 줄 수 있는 이유 — 내가 무엇을 약속했는가

일반 클래스에서 컴파일러는 equals를 대신 만들어 줄 수 없다. 무엇이 "같음"의 기준인지 알 방법이 없기 때문이다. Member 클래스에 id, email, lastLoginAt 세 필드가 있다고 하자. 두 Member가 같다는 것은 무슨 뜻인가?

record 선언은 "이 타입의 상태는 헤더에 적힌 컴포넌트가 전부다"라는 약속이고, 여기서 두 가지가 자동으로 따라 나온다.

  • 숨은 상태가 없으므로, 모든 컴포넌트가 같으면 두 인스턴스는 구별할 방법이 없다. 즉 값 의미론(value semantics)이 성립한다.
  • 상태가 전부 드러나 있으므로, toString에 무엇을 찍을지도 자명하다.
용어 — 명목 튜플(nominal tuple) 튜플은 값을 순서대로 묶어 놓은 것이고, 명목(nominal)은 거기에 OrderSummary라는 이름을 붙였다는 뜻이다. Object[]나 Map.Entry로 얼버무리던 "값 묶음"에 타입 이름과 컴포넌트 이름을 준 것이 record다.

1-3. 정리하면 순서는 이렇다

면접에서 그대로 쓰는 한 문장

record는 "상태가 곧 정체성"이라는 선언이고,
자동 생성은 그 선언에서 따라 나오는 결과다

이 문장을 먼저 던지고 나서 "그래서 자동 생성되는 것은…"으로 내려가면, 같은 내용이 문법 나열이 아니라 설계 판단으로 들린다.

1-4. record 선언 자체가 문서다

한 가지 더. record라는 키워드 하나가 읽는 사람에게 언어 차원의 보증을 준다 — "이 타입은 불변이고, 상태가 같으면 같은 것으로 취급하며, 숨은 필드가 없다."

Lombok이 붙은 클래스와 대비해 보면 차이가 분명하다. @Data가 붙은 클래스를 만나면 어노테이션 조합을 하나씩 확인해야 그 성질을 알 수 있고, 어노테이션 프로세서 동작을 알아야 정확히 무엇이 생성됐는지 안다. record는 키워드 하나로 끝난다.

2. 컴파일러가 만들어 주는 것 / 끝까지 안 해 주는 것

한 줄짜리 선언에서 무엇이 생겨나는지를 정확히 알아야, 무엇이 여전히 내 몫인지도 안다. 아래 도식의 오른쪽 칸이 이 문서 후반부(4·6·8절)의 주제다.

자동 생성되는 다섯 가지 — 정확한 형태

전부 재정의할 수도 있다 — 다만 권장 순서가 있다 자동 생성된 것들은 직접 써서 덮어쓸 수 있다. 접근자를 재정의할 수도, 표준 생성자를 전부 적을 수도 있다. 그런데 자동 생성된 equals/hashCode/toString은 접근자가 아니라 컴포넌트에서 파생되므로, 접근자만 손보면 "접근자가 말하는 값"과 "equals가 비교하는 값"이 어긋날 수 있다. 그래서 값에 손을 대야 한다면 접근자가 아니라 생성자에서 하는 것이 원칙이다(4절·6절).

3. 진짜 가치 — equals가 조용히 깨지는 버그의 원천 차단

자동 생성의 실무적 가치가 어디서 나오는지 구체적으로 보자. 손으로 쓴 equals/hashCode가 조용히 깨지는 시나리오다. 이 절이 "record 왜 씁니까"에 대한 진짜 답이다.

시나리오 처음엔 맞았던 코드가 6개월 뒤 틀린 코드가 된다
// 처음: 필드 2개로 만들었고 equals/hashCode도 맞게 썼다
public final class CacheKey {
    private final Long memberId;
    private final String category;
    @Override public boolean equals(Object o) { /* memberId, category 비교 */ }
    @Override public int hashCode() { return Objects.hash(memberId, category); }
}

// 6개월 뒤: 요구사항이 늘어 필드를 하나 추가했다
public final class CacheKey {
    private final Long memberId;
    private final String category;
    private final String region;   // 추가. 그런데 equals/hashCode는 그대로다
    ...
}

추가한 사람은 잘못한 게 없다고 느낀다. 필드 하나 늘렸을 뿐이고, 컴파일은 통과하고, 기존 테스트도 다 초록색이다. 그런데 이 순간 무슨 일이 생기는지 따라가 보자.

before 사람이 관리하는 두 개의 진실
// 진실 1: 필드 목록
private final Long memberId;
private final String category;
private final String region;

// 진실 2: equals가 보는 목록 (손으로 동기화)
Objects.hash(memberId, category)   // 어긋났다
after 진실이 하나뿐이다
public record CacheKey(Long memberId,
        String category, String region) {}

// 컴포넌트를 추가하면 equals/hashCode/toString이
// 전부 함께 갱신된다 — 어긋날 자리가 없다

이 절의 결론 — "편의"가 아니라 "버그 계열의 소멸"

record에서는 "필드는 늘었는데 equals는 옛날"이라는 상태 자체가 존재할 수 없다

그래서 복합 키·캐시 키·값 객체처럼 equals가 틀리면 즉시 사고가 나는 자리에서 record는 편의 도구가 아니라 안전 장치다. 같은 이유로, AI가 생성한 DTO 코드를 리뷰할 때도 equals 구현을 한 줄씩 검증하는 것보다 "record인지 확인하는 쪽"이 훨씬 싸다.

4. 컴팩트 생성자 — 검증과 정규화의 자리

record가 자동으로 만들어 주는 표준 생성자는 값을 그대로 필드에 넣기만 한다. 그런데 값 객체라면 유효하지 않은 상태의 인스턴스가 애초에 만들어지지 못하게 막고 싶다. 그 자리가 컴팩트 생성자(compact constructor)다.

public record Money(long amount, String currency) {

    public Money {          // 파라미터 목록을 적지 않는다. 이 형태가 컴팩트 생성자다
        // ① 검증: 유효하지 않으면 인스턴스가 존재조차 못 하게 막는다
        if (amount < 0) throw new IllegalArgumentException("음수 금액: " + amount);

        // ② 정규화: 파라미터에 재대입한다. this.currency = 가 아니라는 점이 핵심이다
        currency = currency.toUpperCase();

        // ③ 여기서 필드 대입이 자동으로 일어난다.
        //    this.amount = amount; this.currency = currency; 를 컴파일러가 써 넣는다
    }
}

4-1. 본문이 끝나는 지점에 대입이 있다 — 시점을 그림으로

실제로 실행해 보면 이렇다.

System.out.println(new Money(100, "krw"));
// 출력: Money[amount=100, currency=KRW]     <- 소문자로 넣었는데 대문자로 저장됐다

// java.lang.IllegalArgumentException: 음수 금액: -1

① 의심할 거리가 하나 사라진다

요청 객체가 불변이면 "컨트롤러나 서비스 어딘가에서 요청 객체를 수정했나?"를 의심할 필요가 없어진다. 요청 DTO를 중간에 고쳐 놓고 나중에 다시 읽는 코드는 추적이 매우 어려운데, 그 가능성 자체가 없어진다.

② 도착한 객체가 이미 유효하다

요청 DTO에 4절의 컴팩트 생성자 검증을 넣으면 컨트롤러에 도달한 객체는 이미 유효한 상태다. 검증을 통과하지 못한 요청은 객체가 되지 못한다.

5-2. 조회 전용 프로젝션 — 엔티티 노출 안티패턴을 막는 장치

JPA에서 화면에 필요한 컬럼만 담는 DTO 프로젝션 대상으로 record를 쓴다. 여기서 record가 주는 것은 "이 조회 결과는 수정해도 DB에 반영되지 않는다"는 사실이 타입으로 표현된다는 점이다.

5-3. 값 객체 — 도메인의 Money, Period, 좌표

"상태가 같으면 같은 것으로 취급해야 하는" 개념들이다. 1절에서 본 대로 record의 값 의미론이 정확히 이 요구와 일치하므로 equals가 공짜로 맞아 들어가고, 4절의 컴팩트 생성자를 곁들이면 불변식(invariant)까지 언어가 지켜 준다.

비유 — 지폐와 사람 만 원짜리 두 장은 일련번호가 달라도 "만 원"으로서 같다(값 정체성). 쌍둥이는 아무리 닮아도 다른 사람이다(식별자 정체성). Money는 지폐 쪽이고 Member 엔티티는 사람 쪽이다 — 이 구분이 7절의 결론으로 그대로 이어진다.

5-5. sealed interface와의 조합 가산점

record의 값을 극대화하는 조합이 있다. 닫힌 타입 계층 + 불변 데이터 + 패턴 매칭이다. sealed는 "이 인터페이스를 구현할 수 있는 타입은 여기 적힌 것들뿐"이라고 못 박는 키워드(Java 17 정식)이고, 구현체가 유한하게 닫혀 있으므로 컴파일러가 "전부 다뤘는지"를 검사할 수 있게 된다(switch 패턴 매칭은 Java 21 정식).

5-6. 설정 바인딩

@ConfigurationProperties(prefix = "payment")
public record PaymentProperties(String apiKey, Duration timeout, int retryCount) {}

"설정은 기동 시점에 정해지고 그 뒤로는 바뀌지 않는다"는 성질과 불변 타입이 정확히 맞는 자리다. 세터가 없으므로 런타임에 누가 설정을 바꿔 놓는 경로 자체가 없다. 스프링 부트가 생성자 바인딩으로 값을 채우고, 기본값이 필요하면 @DefaultValue를 컴포넌트에 붙인다.

6. 얕은 불변의 구멍 — record라고 다 불변이 아니다 함정 1

이것이 이 주제의 시니어 포인트다. record가 보장하는 것은 "필드 재대입 금지"뿐이고, 참조 너머의 내용물은 보호하지 않는다. 이것을 얕은 불변(shallow immutability)이라고 한다.

문제 컴포넌트로 가변 리스트를 그대로 받는다
public record Order(Long id, List<Item> items) {}

// 무슨 일이 일어나는지 실제로 실행해 보면
List<Item> items = new ArrayList<>(List.of(new Item("book")));
Order order = new Order(1L, items);

items.add(new Item("pen"));      // 밖에 남아 있는 원본 리스트를 수정한다

System.out.println(order.items());
// 출력: [Item[name=book], Item[name=pen]]
//       -> order를 만든 뒤에 order의 내용이 바뀌었다
개선 받은 순간 불변 복사본으로 교체한다
public record Order(Long id, List<Item> items) {
    public Order {
        items = List.copyOf(items);
    }
}

// 같은 시나리오를 다시 실행하면
List<Item> items = new ArrayList<>(List.of(new Item("book")));

제약왜 그런가실무 대응

마이그레이션에서 실제 작업량이 되는 두 가지 (1) 접근자 이름이 getX()에서 x()로 바뀌므로 호출부를 전부 고쳐야 한다. (2) 자바빈즈 프로퍼티 규약에 의존하는 도구(일부 매핑 라이브러리, 폼 바인딩, 리포팅 툴)의 동작을 확인해야 한다. 그래서 현실적인 접근은 "신규 타입부터 record를 기본값으로"이지 일괄 교체가 아니다.

record가 더 엄격하고(불변 강제, 숨은 상태 금지) data class가 더 편리하다(copy(), 구조 분해). 대신 record는 로컬 선언·sealed·switch 패턴 매칭이 Java 표준 문법으로 맞물려 있다.

9-1. 판단 트리 — 이 타입을 record로 둘까

  1. 정의를 뒤집어 시작한다. "record는 보일러플레이트를 줄이는 문법이 아니라 '이 타입의 상태는 헤더의 컴포넌트가 전부이고, 상태가 같으면 같은 것'이라는 의미 선언입니다. 그 선언 덕분에 컴파일러가 equals·hashCode·toString·접근자를 만들 수 있는 것이지, 자동 생성이 목적인 게 아닙니다."
  2. 실무 가치를 버그로 말한다. "그래서 진짜 이득은 줄 수 절약이 아니라 필드를 추가하고 equals 갱신을 잊어 HashMap이 남의 값을 돌려주는 버그가 구조적으로 사라진다는 겁니다. 복합 키나 캐시 키에서 특히 큽니다."
  3. 쓰는 자리를 기준으로 든다. "DTO·조회 프로젝션·값 객체·복합 키·스트림 중간 결과·설정 바인딩에 기본값으로 씁니다. 검증과 정규화는 컴팩트 생성자에 두고요."
  4. 경계로 닫는다. "다만 가변 컬렉션을 컴포넌트로 받으면 얕은 불변이라 List.copyOf로 방어적 복사가 필요하고, JPA 엔티티에는 못 씁니다 — 기본 생성자가 없고 리플렉션 주입도 막혀 더티 체킹이 안 되고 final이라 프록시도 못 만드는데, 무엇보다 식별자 정체성과 값 정체성이 충돌합니다. 엔티티는 클래스, 계층을 오가는 데이터는 record로 나눕니다."

10. 꼬리질문 셀프 테스트 (14문항)

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 막히는 문항이 있으면 괄호 안의 절로 돌아간다.

record면 불변이 완전히 보장되나요?시니어 변별힌트: record가 막는 것은 "무엇의" 변경인지 (→ 6절)

"아니다. 얕은 불변이다"가 정답이다. record가 막는 것은 필드 재대입뿐이고, 컴포넌트가 List·배열·Date 같은 가변 객체면 그 내용물은 밖에서 바뀔 수 있다.

record Order(Long id, List<Item> items) {}

List<Item> items = new ArrayList<>(List.of(new Item("book")));
Order order = new Order(1L, items);
items.add(new Item("pen"));          // 밖에 남아 있는 원본을 수정
System.out.println(order.items());   // [Item[name=book], Item[name=pen]]

이유는 하나다 — 생성자에 넘긴 쪽이 같은 리스트 객체의 참조를 계속 들고 있기 때문이다. 해법은 컴팩트 생성자에서 items = List.copyOf(items);. 이 한 줄이 원본과의 연결을 끊고(복사) 결과를 수정 불가능하게(불변) 만들어, 밖의 변경과 꺼내 간 쪽의 변경을 둘 다 막는다.

한 겹 더 들어가면, 그래도 원소 자체가 가변이면(Item에 세터가 있으면) 그 안은 여전히 바뀐다. 깊은 불변이 필요하면 원소 타입까지 불변이어야 한다. "record니까 스레드 세이프"라는 코드 리뷰 코멘트를 보면 이 지점을 확인한다.

JPA 엔티티를 record로 선언하면 왜 안 되나요?힌트: 기술적 이유 셋 + 개념적 이유 하나 (→ 7절)

막연히 "안 된다"가 아니라 넷으로 쪼개서 답한다.

기술적으로는 셋이다. ① JPA는 인자 없는 생성자로 빈 객체를 먼저 만드는데 record에는 그것이 없다. ② 그 뒤 리플렉션으로 필드에 값을 주입하는데 record의 필드는 setAccessible(true)를 해도 수정이 거부된다(일반 클래스의 private final 필드와 다른 대우다). 같은 이유로 더티 체킹도 성립하지 않는다 — 바꿀 수 없는 필드에는 감지할 변경이 없다. ③ 지연 로딩 프록시는 엔티티를 상속해 만드는데 record는 암묵적으로 final 클래스라 상속할 수 없다.

개념적으로는 동일성의 기준이 다르다. 엔티티의 정체성은 식별자(id)이고 상태는 생명주기 동안 변하는 것이 정상이다(닉네임이 바뀌어도 같은 회원이다). record는 모든 상태가 곧 정체성인 값 의미론이라 컴포넌트가 하나라도 다르면 다른 것이다. 기술적 제약이 전부 풀리더라도 이 충돌은 남는다.

대신 조회 프로젝션과 DTO 자리에서는 record가 정확히 맞는 도구다. "엔티티는 클래스, 계층을 오가는 데이터는 record"라는 경계까지 말하면 깔끔하다.

Lombok의 @Value나 @Data를 쓰고 있는데 record로 갈아탈 가치가 있나요?시니어 변별힌트: "상위 호환"과 "전부는 아니다"를 같이 말한다 (→ 9절)

불변 데이터 캐리어 자리(@Value)는 record가 상위 호환에 가깝다. 근거가 셋이다.

  • 어노테이션 프로세싱이라는 빌드 의존성 없이 언어가 보증한다. Lombok은 컴파일 과정에 개입해 AST를 조작하는 방식이라 JDK 버전이 오를 때마다 호환성 이슈를 겪어 왔다.
  • 읽는 사람이 키워드 하나로 성질을 안다. @Data가 붙은 클래스는 어노테이션 조합을 확인해야 불변인지 가변인지, equals에 무엇이 들어가는지 알 수 있다.
  • IDE·디버거·리플렉션이 record를 언어 구성 요소로 인식한다(Class.isRecord(), getRecordComponents()).

그런데 전부는 대체하지 못한다. 이 단서를 말할 수 있어야 균형이 잡힌다.

  • 가변 객체의 @Getter/@Setter — JPA 엔티티 등. record는 애초에 불변이라 대응물이 없다.
  • @Builder — 컴포넌트가 많고 선택 인자가 섞인 타입에서 record는 표준 생성자 호출이 길어진다.
  • @Slf4j 같은 부가 어노테이션 — record와 무관하게 계속 쓰인다.

그래서 현실적 판단은 "일괄 교체"가 아니라 경계 설정이다 — 신규 DTO·값 객체·프로젝션은 record를 기본값으로, 엔티티와 빌더가 필요한 타입은 Lombok 유지. 마이그레이션 시 챙길 것도 짚으면 좋다: 접근자 이름이 getX()에서 x()로 바뀌므로 호출부를 전부 고쳐야 하고, 자바빈즈 프로퍼티 규약에 의존하는 도구(일부 매핑 라이브러리, 폼 바인딩, 리포팅 툴)에 영향이 갈 수 있다.

record의 equals/hashCode 자동 생성이 실무에서 왜 그렇게 중요한가요?힌트: "편하다"가 아니라 "무엇이 조용히 깨지는가" (→ 3절)

손으로 쓴 equals/hashCode는 필드가 추가될 때 조용히 깨지기 때문이다.

필드를 하나 추가하고 equals 갱신을 잊으면, 새 필드가 다른 두 객체가 서로 같다고 판정된다. 그러면 HashSet이 중복으로 보고 하나를 버리고, HashMap이 남의 값을 돌려주고, 테스트의 동등성 단언이 통과하지 말아야 할 때 통과한다. 그런데 컴파일러는 아무 말도 하지 않는다. 운영에서는 "가끔 남의 캐시 데이터가 보인다" 같은 형태로 나타나 원인 추적이 매우 어렵다.

record는 컴포넌트 정의로부터 매번 다시 생성되므로 "필드는 늘었는데 equals는 옛날"이라는 상태 자체가 존재할 수 없다. 이건 편의가 아니라 버그 계열 하나를 구조적으로 없애는 일이다.

부수적 효과도 있다. AI가 생성한 DTO 코드를 리뷰할 때 equals 구현을 한 줄씩 검증하는 것보다 record인지 확인하는 쪽이 훨씬 싸다.

Kotlin의 data class와 무엇이 다른가요?가산점힌트: 방향은 같고 차이는 셋 (→ 9절)

방향은 같다. 데이터 캐리어를 언어가 직접 지원하고, equals/hashCode/toString을 자동 생성한다.

차이는 셋이다.

  • 불변성 강제 — data class는 var 프로퍼티를 허용해 가변일 수 있다. record는 전 컴포넌트가 final이라 불변이 강제된다.
  • 부분 수정 사본 — data class에는 copy()와 구조 분해 선언(val (a, b) = obj)이 있다. record에는 대응물이 없어 전 컴포넌트를 나열해야 한다.
  • 언어 통합 — record는 로컬 선언, sealed 인터페이스, switch 패턴 매칭과의 결합이 Java 표준 문법으로 들어와 있다.

한 줄로 말하면 record가 더 엄격하고(불변 강제, 숨은 상태 금지) data class가 더 편리하다(copy, 구조 분해).

컴팩트 생성자 안에서 this.currency = currency.toUpperCase(); 라고 쓰면 어떻게 되나요?힌트: 대입은 누가 언제 하는가 (→ 4절)

컴파일 에러다. 컴팩트 생성자의 본문에서 record의 인스턴스 필드에 직접 대입하는 것은 금지되어 있다.

이유는 대입의 주체와 시점에 있다. 컴팩트 생성자의 본문은 "필드에 넣기 직전의 파라미터를 손볼 기회"이고, 본문이 끝나는 지점에서 컴파일러가 그 시점의 파라미터 값들을 필드에 대입한다. 사람이 본문에서 먼저 필드에 넣어 버리면 final 필드에 두 번 대입하는 셈이 되므로 언어가 아예 막아 둔 것이다.

그래서 정규화는 currency = currency.toUpperCase(); 처럼 파라미터에 재대입한다. this.가 붙어 있는지 없는지 한 글자 차이지만, 이걸 정확히 설명하면 "써 본 사람"과 "본 적 있는 사람"이 갈린다. 파라미터를 손대지 않고 완전히 다른 값으로 필드를 채우고 싶다면 컴팩트 생성자가 아니라 표준 생성자를 직접 전부 적는 형태로 쓰면 된다.

방어적 복사를 생성자 말고 접근자에서 하면 안 되나요? public List<Item> items() { return List.copyOf(items); }시니어 변별힌트: 밖에 남아 있는 원본 참조는 누가 막나 (→ 6절)

부족하다. 방어적 복사의 자리는 생성자다. 이유가 셋이다.

① 들어오는 구멍이 그대로 열려 있다. 접근자를 아무리 손봐도 생성자에 리스트를 넘긴 호출자가 원본 참조를 계속 들고 있다. 밖에서 items.add(...) 하면 record의 상태가 바뀐다 — 6절의 그 장면이 그대로 재현된다. 접근자 복사는 나가는 구멍만 막는다.

② 자동 생성된 equals/hashCode/toString은 접근자가 아니라 컴포넌트에서 파생된다. 그래서 접근자만 고쳐 두면 "접근자가 말하는 값"과 "equals가 비교하는 값"이 어긋날 여지가 생긴다. 생성자에서 값을 정규화해 두면 그런 이중 진실이 생기지 않는다.

③ 비용이 호출마다 붙는다. 생성 시 한 번이면 될 복사를 접근자를 부를 때마다 한다.

덧붙여 Collections.unmodifiableList(items)로 감싸는 것도 답이 아니다 — 그것은 복사가 아니라 뷰라서 원본이 바뀌면 뷰에 그대로 비친다. List.copyOf가 "복사 + 불변"을 한 번에 해준다는 점이 핵심이고, 원소에 null이 섞여 있으면 그 자리에서 NPE를 던져 검증 역할까지 한다.

record를 @RequestBody DTO로 쓰면 역직렬화는 어떻게 되나요? 기본 생성자가 없는데요힌트: JPA가 못 하는 걸 Jackson은 왜 하나 (→ 5절, 7절)

된다. 그리고 "왜 JPA는 안 되는데 Jackson은 되는가"를 대비해 말하면 이해가 드러난다.

Jackson은 빈 객체를 먼저 만들고 채우는 방식만 쓰는 것이 아니라, JSON을 다 읽어 값을 모은 뒤 표준 생성자를 호출해 한 번에 만드는 경로를 쓸 수 있다. record는 컴포넌트 이름이 클래스 파일에 항상 남기 때문에(리플렉션의 getRecordComponents()) JSON 키와 파라미터를 이름으로 짝지을 수 있다 — 일반 클래스의 생성자 파라미터 이름이 컴파일 옵션에 따라 지워지는 것과 다른 점이다. Jackson은 2.12부터 record를 기본 지원한다.

반면 하이버네이트가 막히는 이유는 "만드는 시점에 값을 다 알 수 없어서"다 — 지연 로딩·프록시·더티 체킹처럼 객체를 먼저 만들어 두고 나중에 손대는 생명주기가 전제이기 때문이다. 한 번 만들고 끝나는 쪽(Jackson)은 되고, 계속 손대야 하는 쪽(JPA)은 안 된다가 두 경우를 가르는 선이다.

실무 주의점 하나. 컴팩트 생성자의 검증이 역직렬화 시점에 실행되므로, 잘못된 JSON은 컨트롤러에 도달하기 전에 생성자 예외로 터진다. 이 경우 @Valid의 필드 단위 에러 응답이 아니라 메시지 변환 실패 경로로 흐르므로, 에러 응답 포맷을 통일하려면 그 경로도 핸들링해야 한다.

record의 자바 직렬화는 일반 클래스와 무엇이 다른가요?가산점힌트: 역직렬화가 생성자를 부르는가 건너뛰는가 (→ 4절)

일반 클래스의 역직렬화는 생성자를 건너뛴다. 스트림에서 읽은 값을 필드에 직접 밀어 넣기 때문에, 생성자에 아무리 검증을 넣어 두어도 역직렬화 경로로는 그 검증을 우회한 인스턴스가 만들어질 수 있다. "불변식을 지키려면 readObject에서도 검증하고 방어적 복사를 다시 하라"는 오래된 조언이 여기서 나온다.

record는 다르다. 컴포넌트 값을 읽은 뒤 표준 생성자를 호출해서 인스턴스를 만든다. 그래서 컴팩트 생성자의 검증과 방어적 복사가 역직렬화에서도 반드시 실행된다. 우회 경로가 없다는 뜻이고, 직렬화 관련 공격 표면이 그만큼 줄어든다.

대가는 커스터마이즈 불가다. record에서는 readObject/writeObject 같은 훅으로 직렬화 형태를 바꿀 수 없다. "불변식을 우회할 수 없는 대신 마음대로 손댈 수도 없다"가 정확한 요약이다.

record로 바꿨더니 컴포넌트를 하나 추가할 때마다 호출부가 전부 깨집니다. 단점 아닌가요?힌트: 3절의 버그와 나란히 놓고 본다

"그게 이 도구가 파는 물건입니다"로 답하는 것이 정확하다. 3절의 CacheKey와 나란히 놓으면 대비가 분명하다.

손으로 쓴 클래스에 필드 추가

컴파일은 통과한다. 대신 equals가 조용히 틀린 채 운영에 나가 몇 달 뒤 "가끔 남의 데이터가 보인다"로 돌아온다.

record에 컴포넌트 추가

생성 지점이 전부 컴파일 에러로 뜬다. 아프지만 목록이 즉시 손에 쥐어지고 30분이면 끝난다.

조용히 틀리는 것보다 시끄럽게 깨지는 편이 압도적으로 싸다. 컴파일 에러는 "여기도 챙겨야 한다"는 목록을 컴파일러가 대신 뽑아 준 것이다.

그래도 아프면 완화책이 있다. 정적 팩토리 메서드로 생성 경로를 한곳에 모으거나, 자주 바꾸는 컴포넌트에 대해 withAmount(...) 같은 메서드를 직접 추가하거나, 관련 컴포넌트를 중첩 record로 묶는다. 그런데 인자가 계속 늘어난다면 이 타입이 record로 맞는 모양인지부터 의심하는 것이 낫다(8절).

접근자에 get이 없는데 기존 도구·프레임워크와 충돌하지 않나요?힌트: 자바빈즈 규약에 의존하는 쪽이 어디인지 (→ 8절)

이름이 getOrderId()가 아니라 orderId()인 것은 실수가 아니라 의도다. getX()는 "이 객체에게 X를 계산해서 달라고 요청한다"는 뉘앙스지만, x()는 "이 값이 곧 그것이다"에 가깝다 — 자바빈즈 규약을 따르는 대신 값을 그대로 드러낸다는 표현이다.

현대적인 스택은 대체로 문제가 없다. Jackson과 스프링 MVC는 record를 인식하고, JPA의 DTO 프로젝션도 생성자 기반이라 접근자 이름과 무관하다.

영향을 받는 것은 자바빈즈 프로퍼티 규약에 의존하는 쪽이다 — 폼 바인딩, 일부 매핑·리포팅 라이브러리처럼 get 접두사로 프로퍼티를 찾는 도구들이다. 그래서 기존 Lombok 클래스를 record로 바꾸는 마이그레이션에서는 (1) 호출부의 getX() → x() 일괄 변경과 (2) 프로퍼티 규약에 의존하는 도구의 동작 확인이 실제 작업량이다. 신규 타입부터 record를 기본값으로 두는 접근이 안전한 이유이기도 하다.

런타임에 record인지 어떻게 알 수 있고, 그게 왜 쓸모 있나요?가산점힌트: Lombok 결과물에는 남지 않는 정보다

Class.isRecord()가 true를 돌려주고, Class.getRecordComponents()가 컴포넌트의 이름·타입·접근자를 순서대로 알려 준다. 즉 "이 타입은 값 캐리어이고 그 상태는 이 목록이 전부"라는 사실이 클래스 파일에 구조로 남아 있다.

이 정보가 프레임워크를 바꾼다. Jackson이 별도 어노테이션 없이 생성자 바인딩을 고를 수 있는 것도, 스프링이 @ConfigurationProperties 생성자 바인딩을 자연스럽게 처리하는 것도, IDE와 디버거가 record를 특별히 표시하는 것도 여기서 나온다.

Lombok과의 결정적 차이가 이 지점이다. Lombok은 컴파일 시점에 코드를 만들어 넣는 방식이라, 결과물은 그냥 평범한 클래스다 — 런타임에 "이건 원래 값 타입이었다"는 정보가 남지 않는다. record는 언어의 1급 개념이라 도구 생태계 전체가 그 사실을 활용할 수 있다.

sealed interface + record 조합은 구체적으로 무엇이 좋은가요?가산점힌트: 이득은 "지금"이 아니라 "케이스가 하나 늘 때" 나온다 (→ 5절)

닫힌 타입 계층 + 불변 데이터 + 패턴 매칭의 조합이다. sealed는 "이 인터페이스를 구현할 수 있는 타입은 여기 적힌 것들뿐"이라고 못 박는 키워드이고(Java 17 정식), 구현체가 유한하게 닫혀 있으므로 컴파일러가 "전부 다뤘는지"를 검사할 수 있게 된다.

public sealed interface PaymentResult permits Approved, Declined {}
public record Approved(String approvalCode) implements PaymentResult {}
public record Declined(String reason) implements PaymentResult {}

String message = switch (result) {
    case Approved a -> "승인 " + a.approvalCode();
    case Declined d -> "거절: " + d.reason();
    // default가 필요 없다 — permits 목록을 전부 다뤘음을 컴파일러가 안다
};

진짜 이득은 나중에 결과 타입이 하나 늘어날 때 나온다. permits에 Pending을 추가하는 순간, 이 switch를 포함해 모든 분기 지점에서 컴파일 에러가 난다. "새 케이스를 처리하지 않은 곳"을 사람이 찾아다니는 대신 컴파일러가 목록으로 뽑아 준다.

결제 결과, 도메인 이벤트, 상태 표현처럼 "경우의 수가 정해져 있고 하나 늘 때마다 전부 챙겨야 하는" 모델링에 맞는다. Kotlin의 sealed class + data class로 하던 설계의 Java 판이고, switch 패턴 매칭은 Java 21에서 정식이 됐다.

엔티티가 안 된다면 @Embeddable 값 타입은 record로 해도 되나요?힌트: 같은 제약이 걸리는 이유부터 (→ 7절)

개념적으로는 가장 어울리는 자리인데, 기술적으로는 같은 벽에 부딪힌다. 임베디드 값 타입은 "상태가 곧 정체성"이라는 점에서 record와 의미가 딱 맞지만, JPA 명세는 @Embeddable에도 인자 없는 생성자를 요구하고 구현체는 필드 주입으로 값을 채운다 — 7절에서 본 제약 ①·②가 그대로 걸린다.

이 영역은 구현체와 버전에 따라 지원 범위가 달라지는 부분이라, 면접에서 "된다/안 된다"를 단정하기보다 제약의 이유를 말하고 실무 기본값을 제시하는 편이 안전하다.

실무 기본값은 이렇다. 영속 계층에 붙는 값 타입(@Embeddable)은 클래스로 두고 equals/hashCode를 명시하고, 계층을 오가는 값 객체·DTO·프로젝션은 record로 둔다. 도메인의 Money를 record로 만들고 영속 매핑용 타입과 분리하는 것도 흔한 선택이다 — "저장 모델과 표현 모델을 같은 클래스로 겸업시키지 않는다"는 원칙의 한 사례다.

한 줄 요약
record는 "이 타입의 상태는 헤더의 컴포넌트가 전부이고 상태가 같으면 같은 것"이라는 의미 선언이며 equals/hashCode/toString/접근자 자동 생성은 그 선언에서 따라 나오는 결과이므로, 진짜 가치는 줄 수 절약이 아니라 필드 추가 시 equals 갱신을 잊어 HashMap이 조용히 오작동하는 버그 계열의 원천 차단에 있다 — DTO·조회 프로젝션·값 객체·복합 키·로컬 튜플·설정 바인딩에는 기본값으로 쓰고 검증과 정규화는 컴팩트 생성자에 두되, 가변 컬렉션을 컴포넌트로 받으면 얕은 불변에 그치므로 List.copyOf로 방어적 복사를 해야 하고, 기본 생성자 부재 · 리플렉션 주입 불가 · final 클래스로 인한 프록시 불가에 더해 식별자 정체성과 값 정체성이 충돌하는 JPA 엔티티에는 쓸 수 없다는 경계까지 아는 것이 실무 수용의 완성이다.
