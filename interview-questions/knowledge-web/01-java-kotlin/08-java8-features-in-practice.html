Java 8+ 기능의 실무 활용 — Stream·Optional·람다는 "쓰는 것"보다 "절제"가 실력
세 기능은 문법 세 개가 아니라 각각 다른 제약을 푼 도구 세 개다 — 그리고 실무 변별점은 언제 멈추느냐에 있다

면접 질문: "Java 8 이후 추가된 주요 기능(Stream, Optional, 람다)을 실무에서 어떻게 활용했나요?"

핵심 관전 포인트 — Java 8의 세 기능은 문법 세 개가 아니라 각각 다른 제약을 푼 도구다. 람다는 "자바에서는 데이터만 값처럼 넘길 수 있고 동작은 넘길 수 없다"는 제약을 풀었고(익명 클래스가 그 우회로였는데, 람다는 그것의 축약이 아니라 invokedynamic으로 처리되어 클래스 파일조차 만들지 않는 다른 메커니즘이다), Stream은 "순회하는 방법(how)"을 코드에서 걷어내고 "무엇을 원하는가(what)"만 남겼으며, Optional은 "결과가 없을 수 있다"는 사실을 주석이 아니라 시그니처에 못 박았다. Stream을 예쁜 for문과 가르는 것은 지연 평가다 — 중간 연산은 최종 연산이 붙기 전까지 한 줄도 실행되지 않고, 실행될 때도 단계별이 아니라 원소 하나가 파이프라인 끝까지 갔다 오는 방식이라 findFirst가 첫 원소에서 순회를 멈출 수 있다. 그리고 실무 역량이 갈리는 지점은 문법이 아니라 절제다 — 스트림 안에서 외부 컬렉션을 건드리는 사이드이펙트(병렬로 바뀌는 순간 실제로 데이터가 유실된다), 퍼즐이 된 긴 체이닝, 아무 근거 없는 parallelStream(), 반환 타입 밖으로 새어 나간 Optional을 알아보고 for문이나 if로 되돌리는 판단까지가 답이다.
  • 1
    기능 소개가 아니라 "무엇이 불편했는지"로 시작합니다. 람다는 동작을 값처럼 넘길 수 없다는 제약을, Stream은 순회 방법이 코드에 다 드러난다는 제약을, Optional은 결과 없음이 시그니처에 안 보인다는 제약을 풀었습니다. 셋은 나란한 문법이 아니라 서로 다른 문제를 푼 도구입니다.
  • 2
    Stream을 예쁜 for문과 가르는 것은 지연 평가입니다. 중간 연산은 최종 연산이 붙기 전까지 한 줄도 실행되지 않고, 실행될 때도 단계별이 아니라 원소 하나가 파이프라인 끝까지 갔다 옵니다. 그래서 걸러진 원소에는 map이 호출조차 안 되고, findFirst는 첫 원소에서 순회를 멈출 수 있습니다.
  • 3
    실무에서 갈리는 건 절제입니다. 계층 변환·집계·정렬·"없음" 흐름 통일이 관용구라면, 변별 지점은 스트림 안 사이드이펙트(parallelStream으로 바뀌는 순간 데이터가 조용히 유실됩니다), 퍼즐이 된 체이닝, 근거 없는 병렬화, 경계를 넘은 Optional을 알아보고 for문과 if로 되돌린 경험입니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "Java 8 이후 추가된 주요 기능(Stream, Optional, 람다)을 실무에서 어떻게 활용했나요?"

출제 의도 — 버전별 문법 암기가 아니다. "팀 코드베이스의 관용구를 읽고 쓸 수 있는가"와, Stream 남용(가독성 해치는 체이닝, 스트림 안 사이드이펙트)을 분별하는 감각을 본다.

즉 "기능을 아느냐"가 아니라 "언제 쓰고 언제 멈추느냐"를 말할 수 있는지가 관전 포인트다. 그래서 이 질문은 경험 질문이고, 기능 목록으로 답하면 "면접 대비로 세 개 외웠구나"로 들린다.

이 문서가 겨냥하는 약점 — "Stream은 이렇게 쓰고요, Optional은 이렇게 쓰고요"까지는 대부분 말한다.
그런데 그 다음이 안 나온다. "그게 for문보다 뭐가 나은가요?", "람다는 익명 클래스를 짧게 쓴 거 아닌가요?", "스트림 안에서 리스트에 add하면 뭐가 문제죠?", "parallelStream 붙이면 빨라지지 않나요?" — 여기서 갈린다.
갈리는 원인은 하나다. 세 기능을 "새로 생긴 문법 세 개"로 외웠기 때문이다. 실제로는 서로 다른 제약을 푼 도구 세 개이고, 각 도구가 무엇을 대가로 치르는지까지 알아야 절제가 나온다. 그래서 이 문서는 "없던 시절에 무엇이 불편했는가"로 시작해서 → 지연 평가라는 진짜 정체 → 실무 장면 다섯 → 남용 다섯 종 순으로 쌓는다.

이렇게 답하면 반쪽이다

  • "Stream으로 리스트를 필터링하고 map으로 변환했습니다" — 기능 사용 보고서다. 무엇이 좋아졌는지가 없다.
  • "람다는 익명 클래스를 짧게 쓴 문법입니다" — 틀렸다. 바이트코드 수준에서 다른 메커니즘(invokedynamic)이다.
  • "Stream이 for문보다 성능이 좋습니다" — 근거 없다. 대부분 병목이 아니고, 오히려 순차 루프가 빠른 경우도 많다. Stream의 이득은 가독성과 검증 생략이다.
  • "Optional을 써서 NPE를 없앴습니다" — 어디에 썼는지가 빠지면 위험하다. 필드·파라미터에 썼다면 상태를 늘린 것이다.
  • "데이터가 많으면 parallelStream을 씁니다" — 공유 풀과 컨텍스트 유실을 모르는 답이다.
  • "스트림 안에서 리스트에 add하는 건 스타일 문제 아닌가요" — 잠복 버그다. 병렬로 바뀌는 순간 데이터가 조용히 사라진다.

이 문서가 채워 주는 것

  • "없던 시절의 불편"에서 시작하는 답변 순서를 준다 — 같은 내용이 문법 암기가 아니라 설계 이해로 들린다.
  • 람다 ≠ 익명 클래스를 컴파일 산출물과 invokedynamic 링킹 도식으로 확인한다.
  • 지연 평가를 말이 아니라 실제 실행 순서 출력과 대비 다이어그램으로 본다 — "상상하는 그림"이 왜 틀렸는지까지.
  • 병렬 ArrayList 손상이 어떻게 예외 없이 데이터를 지우는지를 실측 숫자와 도식으로 못박는다.
  • Stream이 유리한 자리 / for문이 유리한 자리를 표와 우선순위 사다리로 정리한다.
  • 면접 전날 인출 카드 — 규칙·목록·숫자를 본문에서 분리해 따로 모아 둔다.

1. 람다 — "동작은 넘길 수 없다"는 제약을 푼 것

답변 순서가 인상을 바꾼다 이 질문에 "Stream은 이렇게 쓰고요, Optional은 이렇게 쓰고요"라고 기능을 소개하는 순서로 답하면 문법 암기로 들린다. 각 기능이 없던 시절에 무엇이 불편했는지부터 말하는 순서로 가면 같은 내용이 설계 이해로 들린다.

1-1. 자바가 넘길 수 있었던 것과 없었던 것

메서드에 인자로 넘길 수 있는 것을 떠올려 보자. int, String, Order 객체, 리스트. 전부 데이터다. 자바에서 값처럼 다룰 수 있는 것은 데이터뿐이었고, "이렇게 처리하라"는 동작 자체는 넘길 수 없었다.

그런데 실무에서 넘기고 싶은 것은 자주 동작이다. 정렬 로직을 예로 들면, "리스트를 순회하며 비교해 자리를 바꾼다"는 부분은 어디서나 똑같고 딱 한 조각, 무엇을 기준으로 비교하는가만 다르다. 그 한 조각을 넘길 수 없으니 정렬 알고리즘 전체를 매번 다시 쓰거나, 기준마다 다른 메서드를 만들어야 했다.

자바가 마련한 우회로가 익명 클래스다. 동작을 직접 넘길 수는 없으니 인터페이스로 한 겹 감싸 객체로 만들어 넘기는 것이다. 넘어가는 것은 여전히 객체(데이터)지만, 그 객체 안에 우리가 원하는 동작이 들어 있다.

1-2. before / after — 5줄 중 의미 있는 것은 1줄

before 익명 클래스

Collections.sort(members, new Comparator<Member>() {
    @Override
    public int compare(Member a, Member b) {
        return a.getName().compareTo(b.getName());
    }
});
// 위 5줄 중 "이름순"이라는 정보를 담고 있는 것은
// 강조된 compareTo 한 줄뿐이다.
// 나머지 4줄은 "동작을 객체로 포장하기 위한" 껍데기다.
after 람다 · 메서드 참조
// 껍데기가 사라지고 의도만 남는다

람다는 새 문법이 아니라 "동작을 값처럼 넘길 수 없다"는 제약을 푼 것이다

면접에서 그대로 쓸 한 문장 — "익명 클래스 5줄 중 의미를 담은 줄은 하나였고, 나머지 넷은 동작을 객체로 포장하기 위한 껍데기였습니다. 람다는 그 껍데기를 걷어낸 것이고, 그 결과 원래 하고 싶었던 일이 코드에 그대로 드러납니다."

2. 람다는 익명 클래스의 축약이 아니다 가산점

여기서 흔한 오해가 하나 있다. "람다는 익명 클래스를 짧게 쓴 문법 설탕(syntactic sugar)"이라는 것인데, 바이트코드 수준에서 아예 다른 메커니즘이다. 실제로 두 형태를 컴파일해 산출물을 비교해 보면 차이가 바로 보인다.

실험 같은 인터페이스를 두 가지 방식으로 만든다
public class Lam {
    Comparator<String> anon() {                          // 익명 클래스
        return new Comparator<String>() {
            @Override public int compare(String a, String b) { return a.compareTo(b); }
        };
    }
    Comparator<String> lambda() { return (a, b) -> a.compareTo(b); }   // 람다
}

3. 함수형 인터페이스 — 람다가 들어갈 수 있는 자리의 정의

람다를 아무 데나 쓸 수 있는 것은 아니다. 람다는 결국 "추상 메서드가 딱 하나뿐인 인터페이스"의 구현체 자리에만 들어간다. 추상 메서드가 하나여야 "이 람다가 그 메서드다"라는 대응이 애매하지 않기 때문이다. 이런 인터페이스를 함수형 인터페이스(functional interface)라고 부른다.

@FunctionalInterface   // 추상 메서드가 2개 이상이면 컴파일 에러로 잡아준다
public interface RetryAction<T> {
    T execute() throws Exception;
}
@FunctionalInterface는 필수가 아니라 안전장치다 붙이지 않아도 추상 메서드가 하나면 함수형 인터페이스로 동작한다. 붙여 두면 나중에 누군가 메서드를 하나 더 추가할 때, 그 인터페이스를 쓰던 모든 람다가 깨지기 전에 컴파일 단계에서 막아 준다. "이 인터페이스는 람다로 쓰라고 만든 것"이라는 의도 표시이기도 하다.

3-1. 표준 네 가지 — 이름이 곧 성질이다

Java 8은 매번 이런 인터페이스를 직접 만들지 않아도 되도록 java.util.function 패키지에 표준 세트를 넣었다. 실무에서 압도적으로 자주 보는 것은 넷이다.

실무에서 압도적으로 자주 보는 네 가지
인터페이스추상 메서드하는 일전형적 자리
Function<T, R>R apply(T t)받아서 다른 것으로 변환map
Predicate<T>boolean test(T t)받아서 참/거짓 판정filter
Consumer<T>void accept(T t)받아서 소비(반환 없음)forEach, ifPresent
Supplier<T>T get()아무것도 안 받고 만들어 냄orElseGet, 지연 생성

연상법 — 이름이 곧 성질이라 외울 것이 별로 없다

Function
받아서 바꾸면
function = 변환 함수
Predicate
받아서 판정하면
predicate = 술어(참/거짓)
Consumer
받아서 삼키면
consume = 소비
Supplier
안 받고 내놓으면
supply = 공급

팀 전체가 이 표준 타입을 공유하게 됐다는 것 자체가 실무적으로 큰 의미다. 예전이라면 팀마다 이름이 다른 콜백 인터페이스(Callback, Handler, Action...)를 따로 만들었을 자리가 표준으로 통일됐다.

3-2. 진짜 활용처는 "쓰는 쪽"이 아니라 "받는 API를 설계하는 쪽"이다

이 감각이 있는지가 실무 답변의 깊이를 가른다. 람다를 소비하는 코드는 누구나 쓰지만, 동작을 파라미터로 받는 API를 직접 설계해 본 사람은 다르게 말한다.

답변에 넣을 한 문장 — "람다를 쓰는 것보다 동작을 받는 API를 설계해 본 경험이 진짜 활용이다"

4. Stream — "어떻게"를 "무엇을"로

before 반복문 — '방법'이 전부 드러난다
List<String> names = new ArrayList<>();
for (Order o : orders) {          // 어떻게 순회할지
    if (o.isPaid()) {             // 어떻게 걸러낼지
        names.add(o.getCustomerName());   // 어떻게 모을지
    }
}
after Stream — '의도'만 남는다
// "결제된 주문의 고객명 목록"
List<String> names = orders.stream()
        .filter(Order::isPaid)
        .map(Order::getCustomerName)
        .toList();

선언형의 실질적 이득은 "짧아진 것"이 아니다. before를 읽는 사람은 names라는 빈 리스트가 어디서 어떻게 채워지는지를 눈으로 따라가며 수집 로직에 버그가 없는지 검증해야 한다. after를 읽는 사람은 그 검증을 생략할 수 있다 — 수집은 라이브러리가 하기 때문이다.

여기까지만 말하면 절반이다 "for문보다 읽기 좋다"는 누구나 하는 말이다. 면접에서 갈리는 지점은 다음 절 — "그러면 Stream은 결국 예쁜 for문 아닌가?"라는 반문에 답할 수 있는가다. 그 답이 지연 평가다.

5. 지연 평가 — 이게 없으면 Stream은 그냥 예쁜 for문이다 핵심

5-1. 연산은 두 종류로 나뉜다

중간 연산 (intermediate operation)

Stream을 받아 Stream을 돌려준다. 그래서 계속 이어 붙일 수 있다.

filtermapsortedpeeklimitflatMap

최종 연산이 붙기 전까지 단 한 줄도 실행되지 않는다.

최종 연산 (terminal operation)

Stream을 받아 Stream이 아닌 것(리스트, 숫자, Optional)을 돌려주거나 아무것도 안 돌려준다.

toListcountfindFirstforEachcollectanyMatch

이게 붙는 순간 파이프라인이 흐른다. 그래서 딱 한 번만 붙일 수 있다.

중간 연산은 최종 연산이 붙기 전까지 단 한 줄도 실행되지 않는다. 이것을 지연 평가(lazy evaluation)라고 한다. "게으르다"는 이름은 시켜도 당장 안 하고 결과가 정말 필요해질 때까지 미룬다는 뜻이다.

5-2. 실행 순서를 직접 찍어 보면

(1) 최종 연산 없이 파이프라인만 만들어 둔다
List<String> names = List.of("kim", "lee", "park", "choi");

Stream<String> s = names.stream()
    .filter(n -> { System.out.println("  filter: " + n); return n.length() == 3; })
    .map(n -> { System.out.println("  map: " + n); return n.toUpperCase(); });
System.out.println("여기까지 출력 없음 = 아무것도 실행 안 됨");
--- (1) 최종 연산 없음 ---
여기까지 출력 없음 = 아무것도 실행 안 됨

filter와 map 안의 println이 한 번도 실행되지 않았다. 파이프라인을 조립해 뒀을 뿐 아직 아무 일도 하지 않은 것이다.

(2) 최종 연산을 붙이면 그때 흐른다
List<String> r = s.toList();
--- (2) toList() 붙였을 때 ---
  filter: kim
  map: kim
  filter: lee
  map: lee
  filter: park      <- map이 없다
  filter: choi      <- map이 없다
결과: [KIM, LEE]

이 출력이 지연 평가의 두 번째 얼굴을 보여준다. 순서를 잘 보면 filter가 네 원소를 다 돌고 나서 map이 도는 것이 아니다. kim이 filter를 통과하자마자 곧바로 map으로 가고, 그다음에야 lee가 filter로 들어간다.

5-3. 사람들이 상상하는 그림과 실제 동작

5-4. 단락(short-circuit) 연산 — 조건을 만족하는 순간 포기한다

Optional<String> f = names.stream()
    .filter(n -> { System.out.println("  filter: " + n); return n.length() == 3; })
    .map(n -> { System.out.println("  map: " + n); return n.toUpperCase(); })
    .findFirst();
--- (3) findFirst() 단락 ---
  filter: kim
  map: kim
결과: KIM
// lee, park, choi는 쳐다보지도 않았다

지연 평가 3문장 — 이대로 말하면 된다

1
중간 연산은 최종 연산이 붙기 전까지 한 줄도 실행되지 않는다. 파이프라인을 조립만 해 둔 상태다.
조립
2
실행될 때도 단계별이 아니라 원소 단위다. 원소 하나가 파이프라인 끝까지 갔다 온 뒤 다음 원소가 들어간다 — 그래서 중간 리스트가 없고 원본을 한 번만 순회한다.
원소 단위
3
그 구조 덕분에 순회를 중간에 멈출 수 있다. findFirst·anyMatch·limit이 단락 연산이다.
단락
지연 평가가 없다면 Stream은 문법이 예쁜 for문일 뿐이다
— 단계마다 중간 리스트를 만들고 전부 순회한다면, 짧게 쓴 대신 메모리와 순회를 더 쓰는 손해 보는 거래가 된다

6. 집계 — groupingBy와 다운스트림 컬렉터

실무 최다 빈출은 변환이 아니라 집계다. 손으로 짜면 "Map에 키가 있나 없나" 분기부터 시작하는 10줄인 코드가 한 줄로 줄어드는 자리이기 때문이다.

before 손으로 묶기
Map<OrderStatus, List<Order>> byStatus = new HashMap<>();
for (Order o : orders) {
    List<Order> bucket = byStatus.get(o.getStatus());
    if (bucket == null) {              // 키 존재 분기
        bucket = new ArrayList<>();
        byStatus.put(o.getStatus(), bucket);
    }
    bucket.add(o);
}
after groupingBy
Map<OrderStatus, List<Order>> byStatus = orders.stream()
        .collect(Collectors.groupingBy(Order::getStatus));

// 상태별 금액 합계 — groupingBy의 두 번째 인자로
// "각 그룹을 리스트로 모으는 대신 합계로 접어라"를 지시한다
Map<OrderStatus, Long> amountByStatus = orders.stream()
        .collect(Collectors.groupingBy(Order::getStatus,
                 Collectors.summingLong(Order::getAmount)));
여기서 한 걸음 더 나가면 실무 답변이 된다 시니어 변별 "이 집계를 SQL로 내릴지 애플리케이션에서 묶을지"의 판단 기준까지 말하면 좋다 — 데이터가 크면 DB에서 집계해 결과만 가져오고(네트워크로 실어 나르는 행 수가 줄고 인덱스를 쓸 수 있다), 이미 다른 이유로 메모리에 올라와 있는 목록이면 애플리케이션에서 묶는 편이 왕복을 아낀다. "Stream으로 할 수 있으니 Stream으로 한다"가 아니라 "어느 쪽이 싼가"로 판단한다는 신호다.

7. Optional — "결과 없음"을 시그니처에 노출

before null 반환
// 시그니처만 봐서는 null 가능성을 알 수 없다
Member findByEmail(String email);

// 호출자가 체크를 잊으면
// 한참 뒤 엉뚱한 곳에서 NPE가 터진다
Member m = repo.findByEmail(email);
m.getName();   // 여기서 터지지만 원인은 위에 있다
after Optional 반환
// '없음' 처리를 하지 않고는 값을 꺼낼 수 없다
Optional<Member> findByEmail(String email);

Member member = memberRepository.findByEmail(email)
        .orElseThrow(() -> new MemberNotFoundException(email));
// 이 줄을 지나면 member는 반드시 값이 있다
// 예외 메시지에 식별자가 담겨 장애 추적도 쉽다

핵심은 "없을 수 있다"는 사실이 주석이나 팀 구전이 아니라 타입에 박혀 있어 컴파일러가 강제한다는 것이다. 문서로 적어 둔 규칙은 지켜지지 않지만, 타입은 지켜진다.

Optional은 쓸 자리가 좁게 정해진 도구다

설계자가 명시적으로 "메서드 반환 타입"용으로 만들었고, 필드·파라미터·컬렉션 원소에 쓰는 순간 오히려 상태가 하나 늘어나는 역설이 생긴다. null인 Optional 필드가 실제로 존재할 수 있다는 사실이 그 역설을 그대로 보여준다.

반환 타입 한정 · 반환 직후 체이닝으로 소비

경계의 상세한 근거는 별도 문서(Optional 사용 경계)에 본편이 있다. 이 질문에서는 이 선만 긋고 넘어가는 것이 맞다 — 여기서 길게 끌면 정작 배점이 큰 남용 분별까지 못 간다.

8. 같이 언급하면 좋은 나머지 축 가산점

이 질문에 Stream·Optional·람다만 말하면 "면접 대비로 세 개만 외웠구나"로 보인다. 나머지 축을 하나만 얹어도 인상이 달라진다.

축 4
java.time
Date와 SimpleDateFormat이 가변인 데다 스레드 안전하지 않아 생기던 사고를 LocalDateTime·DateTimeFormatter라는 불변 타입으로 해소했다.
이전 — static SimpleDateFormat을 공유하면 동시 요청에서 날짜가 뒤섞이거나 파싱 예외가 난다
실무 체감이 가장 큰 것이 이것인 경우가 많다. "Java 8 활용"에 이걸 넣으면 운영을 해 본 사람으로 들린다
축 5
CompletableFuture
외부 API를 여러 개 병렬 호출하고 결과를 조합하는 비동기 파이프라인. 콜백 중첩을 체이닝으로 편 것이다.
이전 — 콜백 안에 콜백이 들어가 실패 처리와 타임아웃이 흩어진다
thenCombine·allOf로 조합 지점이 한곳에 모인다. 람다가 없었다면 이 API 자체가 쓸 만하지 않았다는 연결까지 말하면 좋다
축 6
인터페이스 default 메서드
이미 배포된 인터페이스에 메서드를 추가해도 기존 구현체가 깨지지 않게 하는 장치다.
이것이 없었다면 — Collection에 stream()을 추가하는 순간 세상의 모든 Collection 구현체가 컴파일 에러
Stream이 기존 컬렉션에 소급 적용될 수 있었던 것 자체가 default 메서드 덕분이라는 연결이 이 절의 하이라이트다
답변 마무리용 한 줄 — "세 기능은 따로 추가된 문법이 아니라 서로를 가능하게 한 한 세트였습니다"

9. "어떻게 활용했나"에 답하는 골격 — 기능이 아니라 장면으로

경험 질문이므로 기능 나열이 아니라 구체적인 장면으로 답해야 한다. 다섯 개면 충분하다. 각 장면은 "무엇을 썼다"가 아니라 "무엇이 좋아졌다"까지가 한 세트다.

1
계층 간 변환. 엔티티 목록을 응답 DTO 목록으로 바꾸는 orders.stream().map(OrderResponse::from).toList().
→ 좋아진 것: 팀 전체가 같은 모양으로 쓰면 리뷰어가 "여기 변환 로직에 버그 없나"를 확인할 필요가 없어져 리뷰 비용이 준다. 관용구의 가치는 짧아지는 것이 아니라 읽는 사람이 검증을 생략할 수 있게 되는 것이다.
2
집계와 그룹핑. 관리자 화면 통계를 groupingBy + counting()/summingLong() 조합으로.
→ 한 걸음 더: "이걸 SQL로 내릴지 애플리케이션에서 묶을지"의 판단 기준까지 말한다. 데이터가 크면 DB에서 집계해 결과만 가져오고, 이미 다른 이유로 메모리에 올라와 있는 목록이면 애플리케이션에서 묶는 편이 왕복을 아낀다.
3
다중 기준 정렬. Comparator.comparing(...).thenComparing(...).reversed().
→ 좋아진 것: 정렬 요구가 바뀌어도 비교 알고리즘이 아니라 체인만 고치면 된다. 1절의 "동작을 값처럼 넘긴다"가 실무에서 가장 자주 체감되는 자리.
4
"없음" 흐름의 통일. 리포지토리 반환을 전부 Optional로 통일하고 서비스 계층에서 orElseThrow로 도메인 예외로 바꾸는 것.
→ 좋아진 것: null 체크 누락으로 인한 NPE가 구조적으로 줄고, 예외 메시지에 식별자가 담기므로 장애 추적도 쉬워진다. "규칙을 문서로 적었다"가 아니라 "타입으로 강제했다"는 점이 핵심.
5
절제한 경험. 10~14절의 남용 사례 중 하나를 실제로 겪고 "그래서 되돌렸다"까지 말하는 것.
→ 앞의 넷은 누구나 말할 수 있지만 이건 겪어야 나오는 이야기라, 이 질문의 진짜 변별 지점이 여기다. 되돌린 근거(가독성/안전성)와 되돌린 뒤 무엇이 나아졌는지를 함께 말한다.

장면 하나를 말하는 3단 틀 — 어떤 사례든 이 틀에 넣는다

① 상황 — 무엇을 하려 했고 그때 코드가 어떤 모양이었나
② 적용 — 어떤 도구를 어디에 썼나 (한 줄이면 충분하다)
③ 결과 — 무엇이 좋아졌나 · 리뷰 비용 / 버그 종류 / 장애 추적 / 변경 범위

③이 없으면 기능 사용 보고서다. 반대로 ③만 잘 말하면 사례가 소박해도 통한다 — 면접관이 보는 것은 기술의 화려함이 아니라 판단의 근거이기 때문이다.

10. 남용 ① 스트림 안 사이드이펙트 — 가장 위험하다 함정

사이드이펙트(side effect, 부수 효과)란 어떤 코드가 자기 결과를 돌려주는 것 말고 바깥 세상의 상태까지 바꾸는 것을 말한다. 스트림의 람다 안에서 스트림 밖의 변수나 컬렉션을 건드리는 것이 대표적이다.

나쁜 예 스트림 밖의 리스트를 안에서 변경
List<String> result = new ArrayList<>();
orders.stream()
      .filter(Order::isPaid)
      .forEach(o -> result.add(o.getCustomerName()));
//              ^^^^^^^^^^ 외부 상태 변경
올바른 예 수집은 스트림 자신이 한다
List<String> result = orders.stream()
        .filter(Order::isPaid)
        .map(Order::getCustomerName)
        .toList();
// 담을 그릇을 만들 필요조차 없다

10-1. 왜 문제인가 — 명세가 요구하는 두 가지

무상태 (stateless)
"이전 원소를 처리한 결과를 기억하지 않는다" — 각 원소 처리가 독립적이어야 한다
무간섭 (non-interfering)
"순회 중에 원본 데이터를 건드리지 않는다"

스트림 명세는 중간·최종 연산에 넘기는 동작 파라미터가 이 둘을 만족할 것을 요구한다. 위 코드는 무상태 조건을 어긴다 — 바깥 리스트라는 상태를 원소마다 누적하고 있기 때문이다.

그런데 자연스러운 반문이 하나 나온다. "지금은 잘 돌아가는데 왜 문제냐?"
답은 이것이다 — 누군가 .stream()을 .parallelStream()으로 바꾸는 순간 조용히 틀리기 시작한다. ArrayList는 스레드 안전하지 않아서, 여러 스레드가 동시에 add하면 크기 필드와 배열 쓰기가 어긋난다.

10-2. ArrayList.add가 병렬에서 깨지는 자리

이 숫자 세 개를 그대로 외운다 — 면접에서 설득력이 다르다

32 / 40
데이터 유실 (예외 없음)
6 / 40
ArrayIndexOutOfBounds
2 / 40
정상
"지금은 순차라 맞다"는 안전하다는 뜻이 아니라 아직 안 터졌다는 뜻이다

정리 — 수집은 스트림에게 맡긴다. toList()·collect()는 병렬로 바뀌어도 안전하게 합치는 방법(결합 단계)까지 라이브러리가 책임진다. 손으로 add하는 순간 그 책임이 작성자에게 넘어온다.

11. 남용 ② peek — 실행조차 안 될 수 있다 함정

같은 이유(사이드이펙트 금지)로 peek에 로깅 이상의 로직을 넣는 것도 금물이다. 그런데 peek에는 고유의 위험이 하나 더 있다 — 중간 연산이라 최종 연산이 무엇이냐에 따라 실행 여부가 달라진다.

// 최종 연산이 없으면 peek는 한 번도 실행되지 않는다
names.stream().peek(n -> System.out.println("  peek: " + n));
// 출력: (없음)

// count()는 원소를 실제로 훑지 않고 크기만으로 답할 수 있으면 그렇게 한다
long c = names.stream().peek(n -> System.out.println("  peek: " + n)).count();
// 출력: count=4     <- peek 출력이 한 줄도 안 찍혔다
무서운 것은 트리거가 무해해 보인다는 점이다 peek에 상태 변경 로직을 넣어 뒀다면, 최종 연산을 toList()에서 count()로 바꾸는 것 같은 수정 하나가 그 로직을 통째로 삭제한다. 리뷰에서도 잡히지 않는다 — 바뀐 줄은 count() 한 곳뿐이기 때문이다.
peek는 디버깅용 관찰창이다 — 없어도 결과가 같아야 한다

12. 남용 ③ 퍼즐이 된 체이닝 — for문으로 되돌릴 용기

나쁜 예 중첩 스트림 + 긴 체인
var top = teams.stream()
    .flatMap(t -> t.getMembers().stream()
        .filter(m -> m.getJoinedAt().isAfter(base))
        .map(m -> Map.entry(t.getName(), score(m, t.getWeight()))))
    .sorted(Map.Entry.<String, Integer>comparingByValue().reversed())
    .limit(10)
    .toList();

13. 남용 ④ parallelStream — 편해 보이는 API의 숨은 공유 자원

.stream()을 .parallelStream()으로 바꾸는 데 드는 타이핑이 8글자라는 점이 함정이다. 비용이 0처럼 보이지만 실제로는 JVM 전체가 공유하는 단 하나의 ForkJoinPool.commonPool()을 쓴다. 그 풀의 워커 수는 기본적으로 코어 수 - 1이라 8코어 서버에서 7명뿐인데, 톰캣은 이미 수백 개 요청을 동시에 처리하고 있다.

병렬을 정말 써야 한다면 — 대안까지 말해야 완성이다

전용 ForkJoinPool
전용 풀에 submit해서 그 안에서 스트림을 돌린다. 공용 풀 오염을 막는다.
ExecutorService
애초에 명시적으로 스레드를 다룬다. 풀 크기·큐·거절 정책을 내가 정한다.
가상 스레드 (Java 21)
I/O 병렬화라면 parallelStream이 풀지 못한 문제에 다른 답을 준다.

이 주제는 별도 문서(parallelStream 함정)에 본편이 있다. 면접에서는 원칙 한 줄 + 조건 넷 + 컨텍스트 유실까지만 말하고 넘어가는 것이 시간 배분상 맞다.

14. 남용 ⑤ Optional 남용 — 문법만 갈아입은 null 체크

14-1. isPresent() + get() — 단계만 하나 늘었다

나쁜 예 null 체크를 Optional 문법으로 옮겨 적음
Optional<Member> opt = repo.findByEmail(email);
if (opt.isPresent()) {
    Member m = opt.get();
    sendMail(m.getEmail());
}
// null 체크와 구조가 똑같고, 단계만 하나 늘었다
올바른 예 체이닝으로 소비
repo.findByEmail(email)
    .map(Member::getEmail)
    .ifPresent(this::sendMail);

// 값이 반드시 있어야 하는 자리라면
Member m = repo.findByEmail(email)
    .orElseThrow(() -> new MemberNotFoundException(email));

14-2. orElse(비싼호출()) — 값이 있어도 항상 평가된다

자바의 메서드 호출은 인자를 먼저 계산한 뒤 넘긴다. 그래서 orElse에 넣은 표현식은 Optional에 값이 있든 없든 무조건 실행된다.

Optional<String> present = Optional.of("real");

present.orElse(expensive());        // expensive()가 실행된다. 결과는 "real"
present.orElseGet(Misc::expensive); // expensive()가 실행되지 않는다. 결과는 "real"
orElse:   expensive() 호출됨
real
orElseGet: real

Optional 인출 규칙 세 줄

기본값이 상수면 orElse, 계산·조회가 들어가면 orElseGet
isPresent() + get()이 보이면 체이닝으로 바꿀 자리다
Optional은 "반환 타입" 도구지 "null 체크 대체 문법"이 아니다

세 번째 줄이 가장 자주 위반된다. 단순 null 분기 하나를 Optional.ofNullable(x).map(...).orElse(...)로 포장하는 코드가 대표적인데, 이 경우는 if 한 줄이 더 읽힌다. "Optional을 썼다"가 목표가 되는 순간 도구가 목적을 잡아먹은 것이다.

16. 꼬리질문 셀프 테스트

질문만 보고 먼저 스스로 답해 본 뒤 펼친다. 답이 3문장 안에 안 나오면 해당 절로 돌아간다.

Stream과 for문 중 무엇을 쓸지, 팀 기준을 정한다면 어떻게 정하겠습니까?힌트: 성능으로 정하는 순간 근거 없는 논쟁이 된다 시니어 변별

스트림 안에서 외부 컬렉션에 add하는 코드, 뭐라고 리뷰하겠습니까?힌트: 근거가 두 겹이다 함정

collect(또는 toList())로 바꾸라고 한다. 근거는 두 겹이다.

첫째, 잠복 버그다. 스트림의 동작 파라미터는 무상태(stateless)여야 한다는 명세 위반이고, 누군가 parallelStream()으로 바꾸는 순간 ArrayList 동시 수정으로 데이터가 유실된다. 10절에서 확인했듯 20만 건 기준 40회 중 32회 유실, 6회 예외, 정상은 2회뿐이었다. 예외가 안 나는 쪽이 더 위험하다 — 건수가 조용히 줄어든 채로 배포된다.

둘째, 선언형의 이점이 사라진다. 수집을 스트림 밖 변수로 빼는 순간, 읽는 사람은 "이 리스트가 어디서 어떻게 채워지는지"를 다시 눈으로 따라가야 한다. Stream을 쓴 명분 자체가 없어진 것이다.

리뷰 코멘트로 쓸 한 문장 — "지금은 순차라 맞지만, 이 코드는 .parallel() 한 단어로 깨지는 상태입니다. 수집은 toList()에 맡겨 주세요."

람다가 캡처하는 지역 변수는 왜 effectively final이어야 하나요?힌트: 스택 프레임의 수명과 람다의 수명 핵심
int count = 0;
xs.forEach(x -> System.out.println(count));   // count를 캡처
count = 1;                                  // 이후에 재대입 -> 컴파일 에러
error: local variables referenced from a lambda expression
       must be final or effectively final

effectively final이란 "final 키워드가 붙어 있지는 않지만 한 번 대입된 뒤 다시 대입되지 않아서 사실상 final인 상태"를 말한다. 위 코드는 count = 1이 있어서 그 조건을 깬다.

왜 이런 제약이 있는가. 람다가 캡처하는 것은 변수 자체가 아니라 그 시점의 값을 복사한 것이기 때문이다. 그리고 왜 복사할 수밖에 없냐면, 지역 변수는 스택 프레임에 살고 그 프레임은 메서드가 리턴하는 순간 통째로 걷히기 때문이다.

실무에서 만나는 장면과 그 신호. 루프 카운터를 람다에서 쓰려다 이 에러를 만나면 int[] count = new int[1]처럼 배열 한 칸에 담아 우회하는 코드를 종종 본다. 그건 사이드이펙트를 억지로 만들어 넣는 신호이므로 리팩터링 대상이다. 대개는 IntStream.range나 collect로 다시 표현할 수 있다.

map과 flatMap의 차이는 무엇인가요?힌트: 개수가 변하는가 핵심

map은 원소를 1:1로 변환한다. Stream<Order>에 map(Order::getCustomerName)을 걸면 원소 하나당 문자열 하나가 나오므로 Stream<String>이 된다. 개수가 변하지 않는다.

flatMap은 원소 하나가 0개에서 N개로 펼쳐질 때 그것을 한 층으로 평탄화한다. 팀 하나에 멤버가 여럿이므로 Stream<Team>에서 멤버를 꺼내면 원소당 여러 개가 나온다. 여기에 map을 쓰면 Stream<List<Member>>(스트림 안에 리스트가 들어 있는 상태)가 되어 다음 연산을 걸 수 없는데, flatMap을 쓰면 Stream<Member>로 펴진다. "flat"이 평평하게 편다는 뜻이고, 중첩된 한 겹을 벗기는 것이다.

// map — 한 겹이 남는다
Stream<List<Member>> wrong = teams.stream().map(Team::getMembers);

// flatMap — 한 겹을 벗긴다
Stream<Member> right = teams.stream().flatMap(t -> t.getMembers().stream());
판별 기준 — Stream<List<T>>나 Stream<Stream<T>>가 중간에 보이면 거기가 flatMap 자리다

Optional에도 같은 구분이 있다. 변환 함수가 이미 Optional을 반환하는데 map을 쓰면 Optional<Optional<T>>가 되므로, 그럴 때는 flatMap을 쓴다. 원리가 같다 — 둘 다 "값을 담는 상자"이고, 변환 결과가 또 상자면 한 겹을 벗겨야 한다.

람다는 익명 클래스의 문법 설탕(syntactic sugar)인가요?힌트: 컴파일 산출물을 세어 보면 답이 나온다 함정

아니다. 바이트코드 수준에서 아예 다른 메커니즘이다. 컴파일 산출물을 비교하면 바로 드러난다.

익명 클래스

  • 컴파일 시점에 Lam$1.class가 하나 더 생긴다
  • 실행 시점에 그 클래스를 로딩해 인스턴스를 만든다
  • 루프 안에서 반복 생성하면 인스턴스가 매번 새로 생긴다

람다

  • 클래스 파일이 생기지 않는다
  • 본문은 같은 클래스 안의 private static 메서드로 들어가고, 그 자리에는 invokedynamic 명령 하나만 남는다
  • 상태를 캡처하지 않는 람다는 인스턴스가 재사용된다

invokedynamic은 "여기서 무엇을 부를지는 실행 시점에 정한다"는 뜻의 바이트코드 명령이다. 처음 실행될 때 JVM(LambdaMetafactory)이 그 자리에 맞는 구현체를 만들어 끼워 넣고, 이후에는 재사용한다.

실무에서 이 차이가 드러나는 지점이 둘. ① 클래스 파일이 안 늘어나므로 클래스 로딩 부담과 Metaspace 사용이 줄고, ② 상태를 캡처하지 않는 람다는 인스턴스를 매번 새로 만들지 않는다. 다만 이걸 "그래서 람다가 빠릅니다"로 과장하지는 않는 편이 좋다 — 첫 호출 시 링킹 비용이 있고, 대부분의 애플리케이션에서 병목은 여기가 아니다.

람다 안에서 this는 무엇을 가리키나요? 익명 클래스와 같나요?힌트: 람다는 새 스코프를 만들지 않는다 시니어 변별

다르다. 익명 클래스 안의 this는 그 익명 클래스 인스턴스 자신을 가리키고, 람다 안의 this는 람다를 감싸고 있는 바깥 클래스의 인스턴스를 가리킨다.

class Outer {
    String name = "outer";

    Runnable anon() {
        return new Runnable() {
            String name = "anon";
            public void run() { System.out.println(this.name); }  // "anon"
        };
    }

    Runnable lambda() { return () -> System.out.println(this.name); }  // "outer"
}

이유는 "람다가 새로운 스코프를 만들지 않기 때문"이다. 람다는 별도의 클래스가 아니라 바깥 메서드 안에 그대로 놓인 코드 조각처럼 취급된다(실제로 컴파일하면 바깥 클래스의 private 메서드가 된다). 그래서 this·지역 변수 이름·super가 모두 바깥 문맥 그대로다. 이것을 렉시컬 스코프(lexical scope)를 그대로 물려받는다고 표현한다.

여기서 파생되는 실무 규칙 람다 안에서는 바깥 메서드의 지역 변수와 같은 이름의 파라미터를 선언할 수 없다(variable x is already defined). 익명 클래스는 새 스코프라 가려쓰기(shadowing)가 되지만, 람다는 안 된다. "람다는 스코프를 새로 만들지 않는다"는 한 문장으로 this 동작과 이름 충돌을 동시에 설명할 수 있다.
peek에 로깅 말고 다른 로직을 넣으면 왜 위험한가요?힌트: 최종 연산이 무엇이냐에 따라 실행 여부가 달라진다 함정

peek는 중간 연산이라 최종 연산이 무엇이냐에 따라 실행 여부가 달라진다. 두 가지 방식으로 통째로 사라질 수 있다.

// (1) 최종 연산이 없으면 peek는 한 번도 실행되지 않는다
names.stream().peek(n -> System.out.println("  peek: " + n));
// 출력: (없음)

// (2) count()는 원소를 실제로 훑지 않고 크기만으로 답할 수 있으면 그렇게 한다
long c = names.stream().peek(n -> System.out.println("  peek: " + n)).count();
// 출력: count=4     <- peek 출력이 한 줄도 안 찍혔다

count()는 원소를 세는 연산인데, 원본 소스가 크기를 알고 있고 그 사이에 개수를 바꾸는 연산(filter 같은)이 없으면 순회 자체를 생략하고 크기만 돌려준다. 그래서 peek 안의 코드는 실행되지 않는다.

무서운 지점은 트리거가 무해해 보인다는 것이다. peek에 상태 변경 로직을 넣어 뒀다면, 최종 연산을 toList()에서 count()로 바꾸는 것 같은 수정 하나가 그 로직을 통째로 삭제한다. 리뷰에서도 잡히지 않는다 — 바뀐 줄은 count() 한 곳뿐이기 때문이다.

peek는 디버깅용 관찰창이다 — 없어도 결과가 같아야 한다

정리하면 — 변환이 필요하면 map, 소비가 필요하면 forEach, 수집이 필요하면 collect. peek가 답인 경우는 "잠깐 찍어 보고 지울 때"뿐이다.

orElse와 orElseGet은 언제 갈리나요?힌트: 자바의 인자 평가 시점 함정

orElse(비싼호출())은 값이 있어도 인자가 항상 평가된다. 자바의 메서드 호출은 인자를 먼저 계산한 뒤 넘기기 때문이다.

Optional<String> present = Optional.of("real");

present.orElse(expensive());        // expensive()가 실행된다. 결과는 "real"
present.orElseGet(Misc::expensive); // expensive()가 실행되지 않는다. 결과는 "real"
orElse:   expensive() 호출됨
real
orElseGet: real

orElseGet은 Supplier를 받으므로 정말 필요할 때만 get()을 부른다. 즉 값이 없을 때만 실행된다.

기본값이 상수면 orElse, 계산이나 조회가 들어가면 orElseGet

왜 이게 단순 성능 문제가 아닌가. orElse(saveDefault())처럼 부작용이 있는 호출을 넣었다면, 값이 있는 정상 경로에서도 DB에 기본값이 저장된다. 성능이 아니라 동작이 틀리는 문제로 번진다. 같은 이유로 orElseThrow(() -> new XxxException())가 Supplier를 받는 것도 예외 객체 생성(스택 트레이스 채우기)을 정말 던질 때만 하기 위해서다.

Optional을 필드나 파라미터에 쓰면 왜 안 되나요?힌트: 상태가 하나 늘어난다 핵심

Optional은 설계자가 명시적으로 "메서드 반환 타입"용으로 만든 도구다. 다른 자리에 놓으면 없애려던 문제를 오히려 늘린다.

자리무슨 일이 생기나대안
반환 타입의도한 용도 — "없을 수 있음"이 시그니처에 박히고 컴파일러가 처리를 강제한다그대로 쓴다
필드상태가 null / Optional.empty() / 값 있음 3가지로 늘어난다. Serializable도 아니다필드는 그냥 null 허용, 게터에서 Optional로 감싸 반환
파라미터호출부가 Optional.of(x)로 포장하는 수고를 매번 하고, null을 넘길 수도 있어 체크가 늘어난다메서드 오버로딩 또는 기본값
컬렉션 원소List<Optional<T>>는 "빈 값을 담은 칸"이라는 무의미한 상태를 만든다애초에 걸러서 담는다

핵심 논리 한 줄 — Optional이 없애려던 것이 "값이 없을 수 있는 상태"인데, 필드에 두면 그 상태를 하나 더 만든다. null인 Optional 필드가 실제로 존재할 수 있다는 사실이 이 역설을 그대로 보여준다.

실무 선 긋기 — "반환 타입 한정, 반환 직후 체이닝으로 소비". 리포지토리가 Optional<Member>를 돌려주면 서비스 계층 첫 줄에서 orElseThrow로 벗겨 아래 계층으로는 Member만 흘려보낸다.

이미 소비한 Stream을 다시 쓰면 어떻게 되나요?힌트: 컬렉션과 달리 재사용 가능한 자료구조가 아니다 함정

IllegalStateException: stream has already been operated upon or closed가 던져진다. Stream은 데이터를 담는 컨테이너가 아니라 "한 번 흘려보내는 파이프라인"이기 때문이다.

Stream<Order> paid = orders.stream().filter(Order::isPaid);
long cnt = paid.count();
List<Order> list = paid.toList();   // IllegalStateException

실무에서 이 함정이 나오는 전형적 장면은 "Stream을 메서드 반환 타입이나 필드로 들고 다닐 때"다. 호출자가 두 번 쓰면 터진다. 여러 번 쓸 값이면 스트림이 아니라 컬렉션으로 돌려준다.

재사용이 필요한데 스트림을 들고 있다

두 번째 소비에서 런타임 예외. 테스트에서 한 번만 쓰면 안 잡힌다.

해법

① toList()로 한 번 확정한 뒤 여러 번 쓴다. ② 매번 새 파이프라인이 필요하면 Supplier<Stream<T>>로 넘겨 호출할 때마다 새로 만든다. ③ 한 번 순회로 두 결과가 필요하면 Collectors.teeing(Java 12).

연결 포인트 — 이 제약도 지연 평가의 뒷면이다. 파이프라인이 중간 결과를 저장하지 않기 때문에 메모리를 아끼는 대신, 다시 흘려보낼 원본이 남아 있지 않다.

실무 기본값은 stream.toList()다. 짧고, 반환된 리스트를 누가 몰래 수정하는 사고를 원천 차단하기 때문이다. 다만 기존 코드가 반환값을 sort하거나 add하고 있었다면 바꾸는 순간 런타임에서 터진다 — 일괄 치환할 때 이 점을 봐야 한다.

덧붙일 한 줄 — Collectors.toList()의 반환 타입이 "수정 가능한 ArrayList"라는 것은 구현 세부사항이지 계약이 아니다. 그것에 기대는 코드는 이미 위태로운 코드다.

람다 안에서 체크 예외를 던지는 호출을 해야 하면 어떻게 하나요?힌트: 함수형 인터페이스 시그니처가 허용하지 않는다 시니어 변별

Function·Consumer 같은 표준 함수형 인터페이스의 추상 메서드에는 throws가 없다. 그래서 람다 안에서 IOException을 던지는 호출을 하면 컴파일 에러가 나고, 억지로 try-catch로 감싸면 체인이 누더기가 된다.

paths.stream().map(p -> Files.readString(p)).toList();  // IOException — 컴파일 에러

// 억지로 감싼 결과 — Stream을 쓴 명분이 사라졌다
paths.stream().map(p -> {
    try { return Files.readString(p); }
    catch (IOException e) { throw new UncheckedIOException(e); }
}).toList();

판단 기준 한 줄 — 예외를 "여기서 처리해야 하는 것"으로 볼 것인가, "위로 올려보낼 사고"로 볼 것인가. 전자면 for문, 후자면 경계 메서드에서 언체크로 바꾸고 스트림을 유지한다.

메서드 참조는 몇 가지 형태가 있고, Order::getName은 왜 Function이 되나요?힌트: 수신 객체를 어디서 받는가 가산점

네 가지다. 구분 기준은 "메서드를 호출할 대상(수신 객체)을 어디서 가져오는가" 하나다.

형태표기수신 객체대응 람다
정적 메서드Integer::parseInt없음s -> Integer.parseInt(s)
특정 객체의 인스턴스 메서드logger::info이미 정해진 그 객체m -> logger.info(m)
임의 객체의 인스턴스 메서드Order::getName인자로 들어온 원소o -> o.getName()
생성자OrderResponse::new없음(새로 만든다)o -> new OrderResponse(o)

질문의 핵심인 세 번째 형태가 헷갈리는 이유는 인자가 하나 사라진 것처럼 보이기 때문이다. getName()은 인자를 받지 않는데 Function<Order, String>은 Order를 받는다. 스트림에서 흘러온 원소가 인자가 아니라 "호출 대상"으로 들어가기 때문이다 — o.getName()의 o 자리다.

임의 객체 참조 — 흘러온 원소가 점(.) 앞에 놓인다

실무 팁 — 람다가 "인자를 그대로 한 메서드에 넘기기만 하는 형태"(o -> o.getName(), s -> log.info(s))면 메서드 참조로 바꿀 수 있다는 신호다. 반대로 인자 순서를 바꾸거나 가공이 섞이면 메서드 참조로 억지로 바꾸지 않는다 — 짧아지는 대신 읽기 어려워진다.

parallelStream이 이득을 내는 조건을 말해 보세요. 웹 요청 처리에서는 왜 거의 해당하지 않나요?힌트: 조건이 넷이고 전부 맞아야 한다 시니어 변별

조건은 넷이고, 하나라도 빠지면 대개 손해다.

① CPU 바운드
계산이 오래 걸려야 한다. 블로킹 I/O가 섞이면 워커가 잠들어 병렬화가 아니라 풀 고갈이 된다.
② 충분히 큰 데이터
분할·병합·스레드 조율 고정 비용을 넘겨야 이득이 남는다.
③ 분할이 싼 소스
ArrayList·배열·IntStream.range는 반씩 자르기 쉽다. LinkedList·Stream.iterate는 처음부터 훑어야 해서 분할 자체가 비싸다.
④ 상태 없는 연산
공유 상태를 건드리면 동기화 비용이거나 데이터 유실이다.

웹 요청 처리에서 다루는 것은 대개 "수백 건 DTO 변환"이다. ①도 ②도 아니고, 그 안에 DB 조회가 섞이면 ①을 정면으로 위반한다. 넷 중 하나도 맞지 않는다.

그리고 비용이 자기 기능에만 청구되지 않는다. parallelStream은 JVM 전체가 공유하는 ForkJoinPool.commonPool()을 쓰고 워커 수는 기본 코어 수 - 1이다. 8코어면 7명인데, 그 사이 톰캣은 수백 개 요청을 처리하고 있다. 한 기능의 부하가 아무 상관 없는 다른 기능까지 굶긴다.

기본은 순차, 병렬은 측정 후 — 그리고 웹 요청 경로에서는 전용 풀을 쓴다

대안까지 말하면 완성이다. 정말 병렬이 필요하면 전용 ForkJoinPool에 submit해서 실행하거나(공용 풀 오염을 막는다), 애초에 ExecutorService로 명시적으로 다룬다. I/O 병렬화라면 Java 21 가상 스레드가 parallelStream이 풀지 못한 문제에 다른 답을 내놓았다는 것까지 연결하면 좋다.

한 걸음 더 — Java 21의 가상 스레드가 parallelStream이 풀지 못한 "블로킹 I/O 병렬화" 문제에 다른 답을 내놓았다는 것까지 연결하면 좋다. parallelStream은 CPU 바운드 계산을 나눠 돌리는 도구였지 대기 시간을 겹치는 도구가 아니었고, 그 자리를 가상 스레드가 채웠다.

한 줄 요약
Java 8의 세 기능은 각각 "동작을 값처럼 넘길 수 없다"(람다, 그리고 그것은 익명 클래스의 축약이 아니라 클래스 파일조차 만들지 않는 invokedynamic 메커니즘이다), "순회 방법이 코드에 다 드러난다"(Stream, 그것을 예쁜 for문과 가르는 것은 원소가 파이프라인을 하나씩 통과하며 필요한 만큼만 도는 지연 평가다), "결과 없음이 시그니처에 안 보인다"(Optional, 반환 타입 한정)는 서로 다른 제약을 푼 도구이고 — 실무 역량은 관용구를 팀의 공용어로 쓰는 것과, 스트림 안 사이드이펙트 · 퍼즐이 된 체이닝 · 근거 없는 parallelStream · 경계를 넘은 Optional을 알아보고 for문과 if로 되돌리는 절제에서 갈린다.
