JVM 메모리 구조 — 객체는 힙에, 참조는 스택에, 설계도는 Metaspace에
변수에 담기는 것은 객체가 아니라 객체가 있는 주소값이라는 한 줄에서 지도 전체가 유도된다

면접 질문: "JVM 메모리 구조(Heap, Stack, Metaspace)를 설명해주세요. 객체는 어디에 생성되나요?"

핵심 관전 포인트 — 객체는 전부 Heap에 생성된다(정확히는 대부분 Young 영역의 Eden). Stack에는 객체가 아니라 "객체를 가리키는 참조"와 기본형 값, 메서드 호출 프레임이 스레드별로 쌓인다. Metaspace는 클래스의 설계도(메타데이터)가 올라가는 네이티브 메모리 영역이다. 이 지도가 머릿속에 있어야 OOM 메시지를 보고 "어느 영역이 터졌고, 어떤 덤프를 떠야 하는지"를 바로 판단할 수 있다.
  • 1
    세 영역을 한 문장씩 못박습니다. new로 만든 객체와 배열의 실체는 전부 Heap이고, 새 객체는 Young 영역의 Eden(정확히는 그 스레드의 TLAB)에 놓입니다. Stack에는 객체가 없습니다 — 힙 객체의 주소값(참조)과 기본형 값, 그리고 메서드 호출 프레임만 있습니다. Metaspace에는 값이 아니라 클래스의 구조 정보(설계도)가 힙 밖 네이티브 메모리에 올라갑니다.
  • 2
    가르는 기준을 말합니다 — "공유냐 스레드별이냐". Heap과 Metaspace는 모든 스레드가 공유해서 동시성 문제와 GC의 무대가 되고, Stack은 스레드마다 하나라 지역변수는 그 자체로 thread-safe합니다(단, 그 변수가 가리키는 힙 객체까지 안전한 건 아닙니다). 그리고 Metaspace는 힙 밖이라 -Xmx로는 통제되지 않습니다 — 회계 장부가 아예 다른 축입니다.
  • 3
    실무 접점으로 닫습니다 — OOM 메시지가 곧 영역 지도입니다. Java heap space는 객체 문제 → 힙 덤프, Metaspace는 클래스 문제 → 로딩 클래스 추이와 클래스 로더 누수, unable to create new native thread는 힙과 무관한 네이티브 문제 → 스레드 덤프이고 여기서는 -Xmx를 오히려 줄여야 합니다. 이 분기가 지도를 아는 사람과 모르는 사람의 첫 수 차이입니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "JVM 메모리 구조(Heap, Stack, Metaspace)를 설명해주세요. 객체는 어디에 생성되나요?"

출제 의도 — 운영 중 메모리 지표(heap 사용률, Metaspace 증가)를 읽고 "정상인지 누수인지"를 판단하는 첫 관문이다. 이 지도가 없으면 모니터링 대시보드의 그래프가 그냥 그림이고, OOM 알람이 왔을 때 어느 영역 덤프를 떠야 할지조차 정할 수 없다.

질문이 두 문장인 것에 주목한다. 앞 문장("구조를 설명해 주세요")은 암기 확인이고, 뒤 문장("객체는 어디에 생성되나요")이 진짜 질문이다. 뒤 문장은 "세 영역을 나열할 줄 아는 것"과 "그 사이를 값과 참조가 어떻게 오가는지 아는 것"을 가르기 위해 붙어 있다.

이 문서가 겨냥하는 약점 — "Heap은 객체, Stack은 지역변수, Metaspace는 클래스"라는 세 줄 암기는 대부분 갖고 있다.
그런데 그 다음이 안 나온다. "지역변수가 객체면요?", "static은요?", "그래서 Metaspace가 늘면 힙을 늘리면 되나요?" — 이 세 질문에서 갈린다.
갈리는 원인은 하나다. "참조"가 무엇인지를 건너뛰고 세 줄만 외웠기 때문이다. 그래서 이 문서는 1절을 참조의 정의로 시작한다.

이렇게 답하면 반쪽이다

  • "Heap은 객체, Stack은 지역변수" — 가장 흔한 반쪽 답. "지역변수가 객체면 어디 있죠?"에서 바로 무너진다. 정확히는 "Stack에는 지역변수 칸이 있고, 그 칸에 담기는 건 값이거나 주소"다.
  • "static은 Metaspace에 있습니다" — Java 7 이전 지식. static 변수도 String 풀도 지금은 힙이다(7절).
  • "Metaspace가 늘어나서 -Xmx를 올렸습니다" — 다른 메모리다. 효과가 없을 뿐 아니라 네이티브 여유를 줄여 상황을 악화시킨다.
  • "스레드를 많이 만들면 힙이 부족해집니다" — 스택은 네이티브다. 힙에 여유가 넘쳐도 unable to create new native thread가 난다.
  • "참조가 끊기면 메모리가 반환됩니다" — 반환이 아니라 회수 후보가 될 뿐이다. delete가 아니다.
  • "메모리 그래프가 계속 차오릅니다, 누수 같아요" — 톱니는 정상이다. 봐야 할 것은 모양이 아니라 GC 직후의 바닥선(10절).

이 문서가 채워 주는 것

  • 참조의 정의부터 — "변수에 담기는 건 객체가 아니라 주소"라는 택배 송장 비유로 지도 전체를 유도한다.
  • Person p = new Person() 한 줄이 실행될 때 세 영역에서 각각 무슨 일이 일어나는지를 단계별 도식으로.
  • Eden·TLAB까지 내려가 "객체 생성은 왜 싼가"를 설명한다 — 가산점 포인트.
  • static·문자열 리터럴이라는 최다 실점 구간의 현재 정답과 그 이유.
  • OOM 메시지 4종 → 영역 → 첫 조치의 결정 트리. 암기표가 아니라 지도에서 유도되는 것으로.
  • 모니터링 그래프 읽는 법과 실제 누수 코드의 before/after 3종.

이 문서 전체를 지탱하는 문장 하나

값을 담는 것은 힙, 구조를 설명하는 것은 Metaspace,
주소를 적어 두는 종이는 스택

뒤에 나오는 거의 모든 판단(static은 어디? 리터럴은 어디? Metaspace가 늘면 뭘 봐야 하나?)이 이 한 문장에서 유도된다. 표를 외우는 대신 이 문장을 외운다.

1. 전제 — "참조"가 무엇인지 먼저 알아야 지도가 읽힌다

이 문서의 결론은 "객체는 힙에, 참조는 스택에"다. 그런데 이 문장이 정말로 이해되려면 그 전에 "참조가 뭔데?"에 답이 있어야 한다. 여기서 막힌 채로 뒤를 읽으면 문장은 외워지지만 그림은 안 그려진다.

1-1. 변수에 담기는 것은 객체가 아니다

Person p = new Person("한주덕", 30);

우리는 흔히 "변수 p에 Person 객체가 들어 있다"고 말한다. 그런데 실제로 p라는 변수 칸에 들어 있는 값은 Person 객체가 아니라 숫자 하나다. 그 숫자는 "Person 객체의 실물이 놓여 있는 메모리 위치"를 가리키는 주소값이다. 이 주소값을 참조(reference)라고 부른다. 말 그대로 "저기를 참조하라"는 안내표지다.

비유 — 참조는 택배 송장에 적힌 주소다

송장(변수)에 적힌 것은 집 자체가 아니라 "서울시 ○○구 ○○로 12"라는 짧은 문자열이고, 집(객체)은 그 주소가 가리키는 땅 위에 실제로 서 있다. 송장을 복사해 열 장을 만들어도 집이 열 채가 되지는 않는다. 반대로 송장을 전부 찢어버리면 집은 여전히 그 자리에 있지만 아무도 찾아갈 수 없는 집이 된다.

이 마지막 문장이 GC를 이해하는 출발점이기도 하다. "아무도 찾아갈 수 없게 된 집"이 곧 GC가 회수하는 대상이다.

주소를 적어 두는 종이(변수 칸)와 집이 서 있는 땅(객체 실물)은 서로 다른 장소에 있다. 종이는 작고, 개수가 정해져 있고, 금방 버려진다. 집은 크고, 오래 남을 수 있다. JVM은 이 성질 차이 때문에 둘을 아예 다른 메모리 영역에 나눠 담는다. 종이가 놓이는 곳이 Stack, 집이 서는 땅이 Heap이다.

여기까지 왔으면 "객체는 힙에, 참조는 스택에"는 암기가 아니라 당연한 결론이 된다

1-2. 기본형은 예외다 — 값이 직접 들어간다

int age = 30;의 30은 주소가 아니라 값 그 자체다. 30이라는 숫자는 집처럼 클 것이 없어서 굳이 땅에 세워놓고 주소를 적을 이유가 없다. 그래서 기본형(int, long, double, boolean, char 등)은 변수 칸에 값이 직접 들어가고, 참조형만 주소가 들어간다.

기본형 — 값 자체가 스택 칸에

int age = 30;
// 스택 칸 age 안에 30이 직접 들어 있다
// 힙에는 아무것도 안 생긴다

참조형 — 주소가 스택 칸에

Integer age = 30;
// 힙에 Integer 객체가 생기고(또는 캐시 재사용)
// 스택 칸 age에는 그 객체의 주소가 들어간다
같은 30인데 왜 다른가 int는 언어가 정한 원시 값이라 그 자체로 완결이지만, Integer는 클래스다. 클래스의 인스턴스는 예외 없이 힙에 만들어지고, 변수 칸에는 주소만 들어간다. 대용량 수치 처리에서 박싱 타입을 피하라는 조언의 뿌리가 이 그림이다 — 값 하나마다 객체 하나 + 참조 한 번 더 따라가기가 붙는다.

1-3. 용어를 여기서 정리하고 간다

뒤에서 계속 쓰이는 말들이라 지금 뜻을 못박아 둔다. 이 다섯 개가 흔들리면 뒤의 설명이 전부 안개가 된다.

참조(reference)
객체의 실물이 놓인 힙 주소값. 변수 칸이나 다른 객체의 필드에 담긴다. 객체 자체가 아니다.
GC
Garbage Collector, 쓰레기 수집기. 더 이상 쓰이지 않는 객체를 찾아 메모리를 되돌려주는 JVM의 장치.
GC 대상 영역
GC가 자동으로 청소해 주는 영역. 힙이 그렇다. 스택은 GC가 청소하지 않는다 — 메서드가 리턴할 때 프레임이 걷히며 자동 정리되므로 청소부가 필요 없는 구조다.
네이티브 메모리
JVM이 힙으로 미리 떼어 관리하는 영역이 아니라, JVM 프로세스가 운영체제에 직접 요청해 받아 쓰는 메모리. C 프로그램이 malloc으로 받는 그 메모리와 같은 것이라 "네이티브(원래의)"라 부른다.
메타데이터
"데이터에 대한 데이터". 여기서는 객체가 담고 있는 값이 아니라, 그 객체가 어떻게 생겼는지를 설명하는 정보. age = 30은 데이터, "Person에는 age라는 int 필드가 있다"는 메타데이터.

2. 한 줄의 해부 — Person p = new Person()이 실행되면 어디에 무엇이 생기는가

이제 그 한 줄을 실행할 때 스택과 힙과 Metaspace에 각각 무엇이 생기는지를 그림으로 본다. 메서드 하나가 실행 중이라고 가정한다.

public class OrderService {
    public void register() {
        int discount = 30;                          // (1)
        Person p = new Person("한주덕", discount);   // (2)
    }
}

2-1. 실행 순서 — 힙이 먼저, 스택 대입이 마지막

한 줄처럼 보이지만 순서가 있다. 그리고 이 순서를 알면 "왜 =가 복사가 아닌가"가 자연히 이해된다.

이 절에서 인출할 것 — 세 화살표

스택 → 힙
지역변수 p
객체의 주소값. 프레임이 걷히면 이 화살표가 사라진다.
힙 → 힙
참조형 필드 name
객체가 객체를 가리킨다. GC가 훑는 그래프의 간선이다.
힙 → Metaspace
헤더의 클래스 포인터
"나는 어느 클래스의 인스턴스인가". 모든 객체가 갖는다.

3. 전체 지도 — 공유 영역 vs 스레드별 영역

이제 지도 전체를 펼친다. JVM 메모리를 가르는 첫 번째 기준은 "모든 스레드가 함께 쓰는가, 스레드마다 따로 갖는가"다.

Heap — 공유 Metaspace — 공유 Stack — 스레드별
영역별 소유 구분 — 첫 번째 분류 기준
구분영역담기는 것
모든 스레드 공유Heap객체와 배열의 실체 (GC 대상)
모든 스레드 공유Metaspace클래스 메타데이터 (클래스 구조, 메서드 바이트코드 등)
스레드마다 하나Stack메서드 호출 프레임 — 지역변수(기본형 값 + 객체 참조), 리턴 주소
스레드마다 하나PC 레지스터, 네이티브 메서드 스택현재 실행 위치, JNI 호출용 스택
Heap
팀 전체의 공용 창고
  • 주소만 알면 누구나 꺼내 쓸 수 있다
  • 물건(객체)이 크고 오래 남을 수 있다
  • 그래서 청소부(GC)가 필요하다
Stack
각자 책상 위의 작업 메모지
  • 남이 볼 수 없다
  • 작업이 끝나면(메서드 리턴) 바로 버려진다
  • 청소부가 필요 없다 — 구조적으로 정리된다
Metaspace
창고 물건들의 설계도 보관실
  • 물건이 아니라 물건을 만드는 도면
  • 같은 물건 100만 개여도 도면은 한 장
  • 창고(-Xmx)와 예산이 다르다

3-1. 이 구분이 실무에서 갈리는 지점 셋

1
Heap은 공유라서 동시성 문제와 GC의 무대가 된다. 여러 스레드가 같은 주소를 들고 같은 객체를 동시에 건드릴 수 있으므로, synchronized나 락이 필요해지는 지점이 전부 여기다. 반대로 말하면 "이 객체의 주소가 다른 스레드에 도달할 수 있는가"가 동시성 판단의 유일한 질문이 된다.
2
Stack은 스레드 전용이라 지역변수는 그 자체로 thread-safe다. 다른 스레드는 내 스택 프레임을 볼 방법이 아예 없다. 다만 주의할 것 — "지역변수가 안전"한 것이지 "지역변수가 가리키는 객체가 안전"한 것은 아니다. 그 객체가 힙에 있고 다른 스레드도 같은 주소를 안다면 그 객체는 공유 자원이다.
3
Metaspace는 힙 밖의 네이티브 메모리라서 -Xmx로는 통제되지 않는다. 힙과는 회계 장부가 완전히 다른 축이므로, -Xmx를 아무리 줄여도 Metaspace 누수는 막히지 않는다. 반대도 마찬가지 — Metaspace가 터졌을 때 -Xmx를 올리는 것은 아무 효과가 없고 네이티브 여유만 갉아먹는다.

4. Heap — 객체가 태어나고 죽는 곳

new로 만드는 모든 객체와 배열은 Heap에 생성된다. GC가 관리하는 유일한 영역이며, 내부는 다시 Young(Eden + Survivor 2개)과 Old로 나뉜다.

-Xms / -Xmx
시작 크기 / 최대 크기
운영에서는 둘을 같게 잡는 경우가 많다 — 힙이 실행 중에 늘었다 줄었다 하면서 생기는 확장 비용과 예측 불가능성을 없애기 위해서다.
OOME: Java heap space
가득 차서 GC로도 못 비움
"객체가 너무 많거나 안 죽는다"는 뜻. 첫 조치는 힙 덤프이지 -Xmx 상향이 아니다 — 누수라면 큰 힙은 터지는 시점만 미룬다.

4-1. Eden에서 자리를 잡는 방법 — TLAB 가산점

새 객체가 Eden에 놓일 때 정확히 어떻게 자리를 잡는지도 알아 두면 좋다. JVM은 Eden을 통째로 두고 모든 스레드가 경쟁하게 두지 않는다. 그렇게 하면 객체를 하나 만들 때마다 "다음 빈 자리 포인터"를 두고 스레드끼리 원자적 연산으로 다퉈야 해서 할당이 비싸진다.

대신 스레드마다 Eden의 한 조각을 미리 통째로 떼어 준다. 이 조각을 TLAB(Thread-Local Allocation Buffer, 스레드 전용 할당 버퍼)이라고 부른다.

면접에서 이렇게 한 줄 얹으면 좋다

"객체는 힙에 생성됩니다 — 정확히는 Young 영역의 Eden, 더 정확히는 그 스레드에 배정된 TLAB에 생성됩니다. 스레드별 조각이라 경쟁이 없어서, 할당은 포인터를 앞으로 미는 수준으로 값쌉니다."

5. Stack — 메서드 호출의 발자취

스레드가 메서드를 호출할 때마다 프레임(frame) 하나가 쌓이고, 리턴하면 걷힌다. 프레임 안에는 지역변수 테이블(기본형 값과 객체 참조), 계산 중간값을 올려두는 피연산자 스택, 리턴 주소가 있다.

프레임이 "쌓이고 걷힌다"는 표현이 곧 스택이라는 이름의 이유다. 가장 나중에 호출된 메서드가 가장 먼저 리턴하므로, 접시를 쌓았다가 위에서부터 걷어내는 구조(LIFO)와 정확히 같다.

객체는 절대 없다
스택에는 힙 객체의 주소값(참조)만 있다. "지역변수로 선언했으니 스택"이라는 말은 변수 칸에 대한 말이다.

재귀가 너무 깊어 프레임이 한도를 넘음. 힙과 무관한 에러이고 힙을 늘려도 안 잡힌다.

5-1. 스레드 수 × -Xss — 힙을 키울수록 여기가 좁아진다

스택은 스레드마다 하나씩 네이티브 메모리에 잡힌다. 그래서 같은 프로세스 예산 안에서 힙과 스택은 서로의 여유를 갉아먹는 관계다. 이 그림을 갖고 있어야 unable to create new native thread에서 -Xmx를 줄이는 판단이 나온다.

5-2. before / after — 요청마다 스레드를 만드는 코드

스택이 네이티브에 잡힌다는 사실이 코드에서 어떻게 사고로 이어지는지를 본다.

before 스레드를 무한 생성 — 스택이 네이티브를 먹어치운다
public class NotifyService {

    public void notifyAll(List<Long> userIds) {
        for (Long id : userIds) {
            new Thread(() -> send(id)).start();  요청 1건 = 스레드 1개
        }
    }
}

// 스레드 하나가 만들어질 때마다
//   네이티브 메모리에서 -Xss 만큼(통상 수백 KB~1MB) 스택을 뗀다.
// userIds가 5,000건이면 스택만으로 수 GB를 요구하게 된다.
//
// 증상: OutOfMemoryError: unable to create new native thread
//   - 힙 사용률은 멀쩡하다 (30%대일 수도 있다)
//   - 힙 덤프를 떠 봐야 아무것도 안 나온다
//   - -Xmx를 올리면 오히려 빨리 죽는다
after 상한 있는 풀 + 상한 있는 큐 + 거부 정책
public class NotifyService {

    private final ExecutorService pool = new ThreadPoolExecutor(
            8, 16,                              // core / max — 스레드 수에 천장
            60L, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(2_000),      // 큐에도 천장
            new ThreadPoolExecutor.CallerRunsPolicy()); // 넘치면 호출자가 직접 처리 = 자연스러운 백프레셔

    public void notifyAll(List<Long> userIds) {
        for (Long id : userIds) {
            pool.submit(() -> send(id));       스레드 수는 16으로 고정
        }
    }
}

// 네이티브 스택 소비량이 "스레드 16개분"으로 상한이 걸린다.
// 부하가 몰리면 스레드가 늘어나는 게 아니라 큐가 길어지고,
// 큐마저 차면 거부 정책이 작동해 "터지는" 대신 "느려진다".
여기서 놓치기 쉬운 것 — 무제한 큐도 함정이다 Executors.newFixedThreadPool()은 내부적으로 무제한 큐를 쓴다. 스레드 수는 고정되니 unable to create new native thread는 안 나지만, 이번에는 큐에 쌓인 작업 객체가 힙을 채워 Java heap space로 터진다. 한쪽 문을 막으면 다른 쪽으로 나온다는 것이 이 지도의 교훈이다 — 그래서 스레드 수와 큐 길이 양쪽 모두에 상한이 필요하다.

6. Metaspace — 클래스의 설계도 보관실

클래스 로더가 클래스를 로딩하면 그 클래스의 구조(필드/메서드 정보, 메서드 바이트코드, 상수 풀 등)가 Metaspace에 올라간다. 인스턴스를 몇 개 만들든 설계도는 클래스당 한 벌이면 충분하므로, Person 인스턴스가 100만 개여도 Metaspace의 Person 항목은 하나다.

힙은 인스턴스 수에 비례해 자라고, Metaspace는 클래스 수에 비례해 자란다

이 한 줄이 진단의 출발점이다. Metaspace가 자란다는 것은 객체가 늘어난 게 아니라 클래스가 늘어났다는 뜻이고, 정상적인 애플리케이션이라면 기동 후 클래스 수는 평평해져야 한다.

6-1. PermGen이 무엇이었고, 무엇이 바뀌었나

Java 8에서 PermGen을 대체하며 도입됐다. PermGen이 무엇이었는지부터 짚자. PermGen(Permanent Generation, 영구 세대)은 Java 7까지 클래스 메타데이터가 올라가던 영역으로, 힙 안에 미리 잘라놓은 고정 크기 구획이었다. "영구"라는 이름은 여기 올라간 것들이 애플리케이션이 사는 내내 남을 거라는(그래서 일반 객체와 달리 자주 청소할 필요가 없다는) 초기 가정에서 왔다.

7. 자주 틀리는 포인트 — static 변수와 문자열 리터럴의 위치 가산점

"클래스에 딸린 정보니까 static도 Metaspace겠지"라고 답하기 쉽지만 틀렸다. 이 절은 이 문서에서 실점이 가장 많이 나오는 구간이다.

흔한 오답

  • "static 변수는 Metaspace에 있습니다"
  • "문자열 리터럴은 PermGen… 아 지금은 Metaspace요"
  • "클래스 관련된 건 다 Metaspace입니다"

공통점 — "클래스에 붙어 있는가"를 기준으로 판단했다. 그런데 기준이 그게 아니다.

현재의 정답

  • static 변수는 Java 8부터 힙 — 그 클래스를 대표하는 Class 객체(클래스 미러)와 함께 놓인다.
  • String 상수 풀도 Java 7부터 힙.
  • Metaspace에는 클래스의 구조 정보만 — 필드·메서드 정의와 바이트코드.

기준 — "클래스에 붙어 있는가"가 아니라 "값을 담는가, 구조를 설명하는가"다.

이 절의 인출 문장 — 이것만 외우면 전부 유도된다

값을 담는 것은 힙 · 구조를 설명하는 것은 Metaspace

age = 30은 값이고, "Person에는 age라는 int 필드가 있다"는 구조다. static 필드에 담기는 것도 결국 값이거나 다른 객체를 가리키는 참조이므로 값 쪽이다. 그래서 힙이다.

7-1. String 상수 풀이란 무엇인가

String pool(문자열 상수 풀)이란, 코드에 직접 쓴 문자열 리터럴("ORD-" 같은 것)을 같은 내용이면 하나만 만들어 두고 재사용하는 저장소다. "ORD-"가 코드 수백 군데에 나와도 String 객체는 하나만 만들어지고 전부 그 하나의 주소를 참조한다.

가능한 이유는 문자열이 불변(immutable)이기 때문이다. 공유해도 누가 바꿔서 남에게 피해를 줄 일이 없다. 만약 String이 가변이었다면 이 최적화는 한 군데서 바꾸면 전부 바뀌는 재앙이 됐을 것이다.

7-2. 언제 무엇이 옮겨졌나 — 타임라인

정리 Metaspace에는 "클래스의 구조 정보"만 있고, 값을 담는 것들은 전부 힙이다. 이 두 가지를 구분해서 말하면 PermGen 시절 지식과 현재를 구분하는 사람으로 보인다.

8. 코드 한 줄씩 배치 확인 · "객체는 어디에"의 정답

public class OrderService {
    private static final String PREFIX = "ORD-";   // ① 리터럴 "ORD-"의 실체는 힙(String pool).
                                                   //    PREFIX라는 static 필드 칸도 힙(Class 객체 안).
                                                   //    Metaspace에는 "PREFIX라는 static String 필드가 있다"는 구조 정보만.

    public Order create(long amount) {             // ② amount는 기본형 → 값 자체가 스택 프레임에 들어감
        String id = PREFIX + amount;               // ③ 새 String 객체의 실체는 힙(Eden).
                                                   //    지역변수 id에는 그 힙 주소만 담긴다.
                                                   //    (연결로 만들어진 문자열은 리터럴이 아니라 새 객체다)
        Order order = new Order(id, amount);       // ④ Order 실체는 힙(Eden). order에는 주소만.
                                                   //    Order 안의 id 필드에도 ③ String의 주소가 들어간다.
        return order;                              // ⑤ 리턴은 "객체를 복사해 돌려주는" 게 아니라
    }                                              //    주소값을 호출자에게 넘기는 것이다.
}                                                  //    프레임은 걷히지만 호출자가 그 주소를 받아 들고 있으므로
                                                   //    힙의 Order 객체는 계속 살아 있다.

주석 ⑤가 1절의 송장 비유와 정확히 이어진다. 프레임이 걷히며 이 메서드의 송장은 버려지지만, 호출자가 같은 주소가 적힌 송장을 새로 들고 있으므로 집은 여전히 찾아갈 수 있다.

8-1. 이 코드의 요소별 배치 — 한 표로

8-2. before / after — "참조 대입은 복사가 아니다"가 만드는 버그

1절의 송장 비유가 그대로 버그가 되는 가장 흔한 형태다. 이 코드는 컴파일도 되고 테스트도 통과하다가 운영에서 이상한 데이터를 만든다.

before 주소만 복사해 놓고 "복사본"이라고 믿는다
public class CartService {

    public Cart applyCoupon(Cart origin, Coupon c) {

        items.removeIf(i -> !c.covers(i));      원본 장바구니가 파괴된다
        return new Cart(items);
    }
}

// items와 origin의 내부 리스트는 "같은 힙 객체"다.
// 변수 칸이 두 개일 뿐, 리스트는 하나뿐이다.
//
// 증상:
//   - 쿠폰 미리보기를 눌렀을 뿐인데 실제 장바구니가 비워진다
//   - 단위 테스트에서는 안 잡힌다 (origin을 다시 안 보니까)

    }
}

//   getItems() { return List.copyOf(this.items); }

OutOfMemoryError는 하나의 에러가 아니라 "어느 영역이 터졌는지"를 메시지로 알려주는 에러 집합이고,

9-1. 네 메시지가 각각 무슨 말인가

Java heap space
Heap
객체가 너무 많거나 안 죽는다는 뜻이다. 그래서 "어떤 객체가 얼마나 있고 누가 붙잡고 있는가"를 봐야 하고, 그 정보가 들어 있는 것이 힙 덤프다.
GC overhead limit exceeded
Heap — 조금 다른 상황
힙이 완전히 찬 것은 아닌데 GC가 계속 돌면서도 회수량이 거의 없는 상태다. 애플리케이션은 일을 못 하고 GC만 CPU를 태우므로 JVM이 "이건 가망 없다"고 판단해 던진다. 곧 터질 Java heap space의 전조이므로 같은 조치를 취하되 GC 로그를 함께 본다.

unable to create new native thread
스레드 스택 (네이티브) — 힙과 무관
스택은 스레드마다 네이티브 메모리에 잡히므로, 스레드 수가 폭증하면 힙에 여유가 넘쳐도 이 에러가 난다. 여기서 -Xmx를 늘리는 것은 오히려 역효과다 — 힙이 커진 만큼 네이티브에 남는 여유가 줄기 때문이다.

가장 비싼 실수 셋 — 이것만 피해도 절반은 간다

  • 메시지를 안 읽고 -Xmx부터 올린다. 네 경우 중 둘은 무효이고 하나는 악화다.
  • Metaspace OOM에 힙 덤프를 뜬다. 몇 GB짜리 파일을 만들고 몇 시간 분석해도 범인은 그 안에 없다.
  • 누수인데 힙만 키운다. 누수는 속도의 문제가 아니라 방향의 문제다 — 큰 힙은 터지는 시각만 뒤로 미룬다.

10. 모니터링 그래프를 읽는 기준도 이 지도에서 나온다

힙 그래프에서 봐야 할 것은 모양이 아니라 바닥선이다

정상 — 톱니

차오르다가 GC로 뚝 떨어지고 다시 차오르는 패턴이 건강한 상태다. 톱니를 보고 "메모리가 계속 차네요"라고 놀랄 필요가 없다.

누수 — 바닥선 상승

GC 직후의 바닥이 회차마다 조금씩 올라가는 패턴 — 아무리 치워도 안 치워지는 잔량이 누적되는 모양 — 이 누수의 시그니처다.

10-1. before / after ① 상한 없는 static 캐시 — 바닥선을 올리는 대표 코드

before 캐시라고 부르지만 실은 "영원히 자라는 Map"
public class PriceCache {
    private static final Map<String, Price> CACHE = new HashMap<>(); 상한 없음 · 만료 없음

    public static Price get(String sku) {
        return CACHE.computeIfAbsent(sku, PriceCache::load);
    }
}

// static 필드는 GC 루트다. → CACHE는 절대 회수되지 않는다.
// CACHE가 살아 있으면 그 안의 Price 객체들도 전부 살아 있다.
//
// sku 종류가 유한하면 문제가 없어 보이지만,
// 잘못된 sku·테스트 트래픽·봇 요청까지 전부 키가 되어 들어온다.
//
// 그래프 증상: 톱니는 정상, 그러나 GC 직후 바닥이 매일 조금씩 상승
// 최후: OutOfMemoryError: Java heap space (배포 후 3~7일쯤)
after 상한과 만료를 둔다 — "캐시의 정의는 버릴 수 있다는 것"
public class PriceCache {
    private static final Map<String, Price> CACHE =
        Collections.synchronizedMap(new LinkedHashMap<>(16, 0.75f, true) {
            protected boolean removeEldestEntry(Map.Entry<String, Price> e) {
                return size() > 10_000;          // 크기 상한 = 메모리 상한
            }
        });

    public static Price get(String sku) {
        return CACHE.computeIfAbsent(sku, PriceCache::load);
    }
}

// 핵심은 자료구조가 아니라 원칙이다:
//   "얼마나 커질 수 있는지 답할 수 없는 컬렉션은 캐시가 아니라 누수다"
// 실무에서는 Caffeine 같은 라이브러리로 크기·TTL·통계를 함께 건다.
힙 누수를 만드는 문장은 대개 하나다 — "언젠간 지워지겠지"

10-2. before / after ② Metaspace를 밀어 올리는 코드

Metaspace가 꾸준히 우상향하면 클래스가 계속 새로 로딩되고 있다는 뜻이다. 리플렉션이나 동적 프록시(CGLIB)를 반복 생성하는 코드, 스크립트 엔진의 반복 컴파일, 핫 리로드 후 남은 이전 클래스 로더 등 클래스 로더 누수를 의심한다. 이 축은 힙 튜닝으로 절대 안 잡힌다 — 애초에 다른 메모리이기 때문이다.

before 요청마다 새 클래스를 찍어낸다
public class RuleEngine {

    public boolean evaluate(String expression, Order order) {
        ScriptEngine engine = new ScriptEngineManager()
                .getEngineByName("groovy");        호출마다 새 엔진
        return (Boolean) engine.eval(expression); 호출마다 새 클래스 생성
    }
}

// 스크립트 한 번 컴파일 = 새 클래스 1개(+ 내부 클래스들) 로딩
// 초당 100회 호출이면 초당 수백 개 클래스가 Metaspace에 쌓인다.
//
// 증상:
//   - 힙은 완벽하게 정상 (톱니, 바닥선 평평)
//   - Metaspace만 일직선으로 우상향
//   - -Xmx를 늘려도 아무 변화 없음
//   - 결말: OutOfMemoryError: Metaspace
//          (상한 미설정이면 OOM Killer의 SIGKILL)
after 컴파일 결과를 재사용한다 — 클래스는 유한하게
public class RuleEngine {
    private final ScriptEngine engine = new ScriptEngineManager()
            .getEngineByName("groovy");            // 엔진 1개 재사용
    private final Map<String, CompiledScript> compiled =
            new ConcurrentHashMap<>();                 // 표현식별 1회만 컴파일

    public boolean evaluate(String expression, Order order) {
        CompiledScript cs = compiled.computeIfAbsent(expression,
                e -> ((Compilable) engine).compile(e));  클래스 수 = 표현식 종류 수
        return (Boolean) cs.eval();
    }
}

// 표현식 종류가 유한하면 로딩되는 클래스도 유한해진다.
// 단, 표현식이 "사용자 입력"이라면 이 Map 자체가 무한히 자랄 수 있으므로
// 여기에도 상한이 필요하다 — 10-1과 같은 원칙이다.
//
// 안전망: -XX:MaxMetaspaceSize 로 상한을 걸어 둔다.

10-3. before / after ③ ThreadLocal 미정리 — 스레드풀에서 특히 치명적

before 넣기만 하고 지우지 않는다
public class TenantContext {
    private static final ThreadLocal<Tenant> CURRENT = new ThreadLocal<>();

    public static void set(Tenant t) { CURRENT.set(t); }
    public static Tenant get()      { return CURRENT.get(); }
    // clear()가 없다 — 그리고 아무도 안 지운다
}

// 요청 스레드는 풀에서 재사용된다 = 스레드가 죽지 않는다.
// 스레드가 살아 있으면 그 스레드의 ThreadLocalMap도 살아 있고,
// 거기 담긴 Tenant도, Tenant가 붙잡은 것들도 전부 살아 있다.
//
// 이중 피해:
//   ① 힙 누수 — 스레드 수 × 컨텍스트 크기만큼 영구 점유
//   ② 데이터 오염 — 다음 요청이 이전 요청의 Tenant를 본다(보안 사고)
//   ③ 클래스 로더 누수 — 웹앱 재배포 시 이전 로더가 여기 묶여 안 죽는다
after 넣은 쪽이 반드시 지운다 — finally로 강제
public class TenantContext {
    private static final ThreadLocal<Tenant> CURRENT = new ThreadLocal<>();

    public static void set(Tenant t) { CURRENT.set(t); }
    public static Tenant get()      { return CURRENT.get(); }
    public static void clear()    { CURRENT.remove(); }   반드시 제공
}

// 호출부 — 인터셉터/필터에서 요청 경계마다 정리
try {
    TenantContext.set(resolve(request));
    chain.doFilter(request, response);
} finally {
    TenantContext.clear();      예외가 나도 지워진다
}

// 원칙: ThreadLocal은 "스레드의 수명"이 아니라
//       "요청의 수명"에 맞춰 정리해야 한다.
//       스레드풀에서는 이 둘이 절대 같지 않다.

대시보드에서 매일 볼 세 줄

힙 — GC 직후 사용량
최대값이 아니라 바닥값을 시계열로 본다. 이 선이 우상향하면 누수다.

카드 2 — 판단 규칙 넷

규칙값을 담는 것은 힙, 구조를 설명하는 것은 Metaspace. → static·리터럴 질문은 전부 이걸로 해결된다. 규칙"지역변수로 선언했다"는 변수 칸이 스택에 있다는 뜻이지 객체가 스택에 있다는 뜻이 아니다. 규칙참조가 끊긴다 = 회수 후보가 된다이지, 메모리가 즉시 반환된다가 아니다. 규칙스택·Metaspace는 네이티브다. → -Xmx와 예산이 다르고, 서로 여유를 갉아먹는다.

카드 3 — 답이 직관과 반대인 것 셋 (함정 목록)

11-2. 스스로 점검 — 막히면 해당 절로 돌아간다

  • 참조가 무엇인지를 비유 없이, 그리고 비유로 각각 설명할 수 있다. (1절)
  • Person p = new Person()에서 스택·힙·Metaspace에 각각 무엇이 생기는지를 그릴 수 있다. (2절)
  • "지역변수는 thread-safe"의 정확한 범위를 한 문장으로 좁혀 말할 수 있다. (3절)
  • TLAB이 무엇이고 왜 객체 생성이 싼지 설명할 수 있다. (4절)
  • StackOverflowError와 Java heap space의 차이를 옵션 이름까지 붙여 말할 수 있다. (5절)
  • PermGen → Metaspace 변경을 "출처가 바뀌었다"와 "문제의 성격이 바뀌었다" 두 층으로 말할 수 있다. (6절)
  • static과 문자열 리터럴의 위치를 버전과 함께, 그리고 왜 그런지까지 말할 수 있다. (7절)

  • 힙 그래프에서 누수를 판정하는 기준이 "모양"이 아님을 설명할 수 있다. (10절)

12. 꼬리질문 셀프 테스트 — 답을 소리 내어 말한 뒤 펼친다

질문만 먼저 보고 입으로 답해 본 다음 펼친다. 눈으로 읽고 "아 그렇지"는 인출이 아니다. 이 문서에서 가장 자주 실제로 나오는 다섯은 핵심, 답이 직관과 반대인 것은 함정, 여기까지 말하면 급이 달라지는 것은 시니어로 표시했다.

static 변수와 문자열 리터럴은 어디에 저장되나요?힌트: "클래스에 딸린 것"과 "값을 담는 것"은 다른 질문이다 핵심

둘 다 힙이다. static 변수는 Java 8부터 해당 클래스를 대표하는 Class 객체(클래스 미러)와 함께 힙에 있고, String 상수 풀은 Java 7부터 힙으로 옮겨졌다. Metaspace에는 클래스의 구조 정보(필드·메서드 정의, 바이트코드)만 있다.

기준 한 문장: 값을 담는 것은 힙, 구조를 설명하는 것은 Metaspace

왜 그래야만 하는지까지 말하면 암기가 아니라 이해로 보인다. static 필드에 담기는 것도 결국 값이거나 다른 객체를 가리키는 참조다. 참조를 담는 칸은 GC가 추적할 수 있는 자리에 있어야 한다 — GC는 힙을 훑는 장치이므로, static 필드가 힙 밖에 있으면 "static이 붙잡고 있는 객체"를 살아 있다고 판정할 근거를 만들기가 어색해진다. (실제로 static 필드는 GC 루트의 하나로 취급된다.)

"Metaspace요"라고 답하면 PermGen 시절 지식으로 멈춰 있다는 인상을 준다. Java 6 이전에는 실제로 String 풀과 static이 PermGen에 있었기 때문에, 오래된 자료를 그대로 외운 사람이 정확히 이렇게 답한다. "둘 다 힙이고, Metaspace에는 구조 정보만"이 현재의 정답이다.

덧붙이면 좋은 한 줄 — "String 풀이 힙으로 온 덕분에 풀에 있는 문자열도 참조가 끊기면 GC 대상이 됩니다. PermGen 시절에는 사실상 안 죽어서 intern() 남용이 PermGen space OOM의 단골 원인이었습니다."

지역변수로 선언한 객체도 힙에 생기나요? 그럼 스택에는 뭐가 있죠?힌트: "지역변수로 선언했다"가 수식하는 대상은 객체가 아니라 변수 칸이다 핵심

그렇다. Order order = new Order()에서 Order 인스턴스는 힙(Eden)에 생기고, 스택의 지역변수 order에는 그 힙 주소(참조)만 담긴다.

"지역변수로 선언했다"는 그 변수 칸이 스택에 있다는 뜻일 뿐, 객체가 스택에 있다는 뜻이 아니다

스택에 값 자체가 들어가는 것은 기본형 지역변수뿐이다(int, long, double, boolean, char …). 참조형은 예외 없이 주소값이다.

그래서 메서드가 리턴해 스택 프레임이 통째로 걷혀도 힙의 객체는 그 자리에 남는다. 다만 그 객체를 가리키는 참조가 전부 끊긴 시점부터 GC 회수 후보가 될 뿐이고, "참조가 끊긴다 = 즉시 메모리가 반환된다"가 아니다. C++의 delete와 갈리는 지점이 여기다.

가산점 한 줄 — "엄밀히는 JIT의 탈출 분석(escape analysis)이 '이 객체는 메서드 밖으로 안 나간다'고 판단하면 스칼라 치환으로 힙 할당 자체가 생략될 수 있습니다. 다만 개념 모델로는 '객체는 힙'이 정답입니다."

Metaspace 사용량이 계속 증가하면 무엇을 의심하겠습니까?힌트: 늘어나는 것은 객체가 아니라 무엇인가 핵심

클래스가 계속 새로 로딩되고 있다는 신호이므로 클래스 로더 누수를 의심한다. 힙 덤프를 아무리 뒤져도 원인이 안 나오는 종류의 문제다 — 문제가 객체가 아니라 클래스이기 때문이다.

전형적 원인 3종 — 이대로 외운다

  1. 동적 클래스 생성을 루프/요청마다 반복 — 리플렉션, CGLIB 프록시, 람다·핸들의 무제한 생성.
  2. 스크립트 엔진의 반복 컴파일 — Groovy·JS 스크립트를 매번 새로 컴파일하면 컴파일 결과가 매번 새 클래스다.
  3. 핫 리로드/재배포 후 이전 클래스 로더가 안 죽음 — 어딘가에서 참조로 붙잡혀 언로드되지 않는 경우.

③이 왜 그렇게 크게 터지는지를 설명할 수 있어야 한다. 클래스가 Metaspace에서 내려가려면 그 클래스를 로딩한 클래스 로더가 통째로 회수돼야 한다. 그런데 클래스 로더는 자기가 로딩한 모든 클래스를 붙잡고 있고, 그 클래스들의 인스턴스가 어딘가(다른 로더가 관리하는 static 필드, ThreadLocal, 스레드풀에 남은 스레드 등)에 하나라도 살아 있으면 로더 전체가 회수되지 않는다.

클래스 하나가 아니라 로더 단위로 통째로 남는다 — 그래서 재배포 한 번에 수천 개 클래스가 통째로 눌러앉는다

조치 순서

  1. -verbose:class나 JFR로 로딩 클래스 수의 추이를 본다 — 우상향이면 확정이다.
  2. 어떤 이름 패턴의 클래스가 늘어나는지 본다. $Proxy123, ...$$EnhancerByCGLIB$$..., Script1234 같은 일련번호가 붙은 이름이면 동적 생성이 범인이다.
  3. -XX:MaxMetaspaceSize로 상한을 건다. 고치기 전이라도 상한이 있어야 OS 메모리를 잠식해 프로세스가 OOM Killer에 죽는 사태를 막고 JVM이 던지는 OOM으로 받아낼 수 있다.

절대 하지 말 것 — -Xmx를 만지는 것. 다른 메모리라서 아무 효과가 없고, 원인 추적 시간만 버린다.

PermGen에서 Metaspace로 왜 바뀌었나요?힌트: 이름이 바뀐 게 아니라 메모리의 "출처"가 바뀌었다 시니어 변별

PermGen(Permanent Generation, 영구 세대)은 힙 안에 미리 잘라놓은 고정 크기 구획이었고, 여기서 두 가지 고질병이 나왔다.

병 하나 — 크기를 미리 맞출 수 없다

애플리케이션이 클래스를 몇 개 로딩할지를 배포 전에 알기 어렵다. 특히 웹 컨테이너 재배포 환경에서 심했다 — 재배포할 때마다 새 클래스 로더가 클래스를 다시 로딩하는데 이전 로더가 완전히 회수되지 않으면 PermGen이 조금씩 차올라, 몇 번 재배포하면 터졌다. "배포 3번 하면 톰캣 재시작"이 관행이던 시절의 원인이 이것이다.

병 둘 — 힙 튜닝과 얽힌다

힙 안에 있으니 힙을 늘리면 PermGen 몫은 어떻게 되는가까지 함께 고민해야 했다. 서로 다른 성질의 두 자원(객체와 클래스)이 하나의 예산을 나눠 쓰는 구조 자체가 문제였다.

Metaspace는 이를 메모리의 출처를 바꿔 풀었다 — 힙 안이 아니라 네이티브 메모리를 쓰고, 기본적으로 자동 확장된다. 크기를 미리 맞출 필요 자체가 사라졌다.

"영역 이름이 바뀐 게 아니라 메모리의 출처(힙 → 네이티브)가 바뀐 것"

여기서 한 문장 더 붙이면 트레이드오프를 보는 사람이 된다.

이 변경은 문제를 없앤 것이 아니라, "터지는 문제"를 "잠식하는 문제"로 성격을 바꾼 것이다.
PermGen은 일찍, 시끄럽게 터졌다. Metaspace는 조용히 OS 메모리를 먹다가 컨테이너 환경에서는 JVM 에러가 아니라 OOM Killer의 SIGKILL로 나타난다 — 덤프도 스택트레이스도 안 남는다.

그래서 운영에서는 -XX:MaxMetaspaceSize 상한 설정과 모니터링이 관례가 됐다. 자동 확장이 편의가 아니라 "상한을 네가 정하라"는 위임이라는 관점으로 말하면 좋다.

스레드를 아주 많이 만들면 어떤 메모리가 부족해지나요?힌트: 대응이 직관과 정반대다 함정

힙이 아니라 네이티브 메모리가 부족해진다. 스택은 스레드당 하나씩 네이티브 메모리에 할당되므로(-Xss, 통상 수백 KB~1MB 수준), 스레드가 수천 개면 힙에 여유가 넘쳐도 OutOfMemoryError: unable to create new native thread가 난다.

이 질문의 함정 — 대응이 직관과 반대다

"메모리가 부족하다"니까 -Xmx를 늘리면 오히려 악화된다. 같은 프로세스 안에서 힙이 가져가는 몫이 커지면 네이티브에 남는 여유는 줄기 때문이다. 급한 불은 -Xmx를 줄여서 끈다.

급한 불(운영 조치)과 정공법(설계 수정)을 나눠 말하면 좋다.

급한 불

  • -Xmx를 줄여 네이티브 여유 확보
  • -Xss를 낮춰 스레드당 스택 축소 주의 — 너무 낮추면 깊은 재귀에서 StackOverflowError가 난다
  • OS의 프로세스당 스레드/파일 디스크립터 한도 확인

정공법

  • 요청마다 new Thread를 하는 구조 제거
  • 상한 있는 스레드풀 + 상한 있는 큐 + 거부 정책
  • 블로킹 I/O 대기로 스레드를 태우고 있다면 비동기·논블로킹으로 전환 검토

진단 한 줄 — 이 에러가 났을 때 떠야 할 것은 힙 덤프가 아니라 스레드 덤프(jcmd <pid> Thread.print)다. 같은 이름 패턴의 스레드가 수천 개 찍히면 어떤 풀이 범인인지 이름만으로 바로 보인다.

String s = "abc"와 String s = new String("abc")는 무엇이 다른가요?힌트: 객체가 몇 개 만들어지는지 세어 본다

만들어지는 객체 수가 다르다.

String s = "abc";

리터럴이므로 String 상수 풀(힙 안)에 이미 있으면 그 주소를 그대로 받는다. 새 객체는 안 만들어진다. 같은 리터럴을 쓴 코드 백 군데가 전부 같은 객체 하나를 가리킨다.

String s = new String("abc");

new가 있으므로 풀의 객체와 별개로 힙(Eden)에 String 인스턴스를 하나 더 만든다. 내용은 같지만 주소가 다른 객체가 된다.

그래서 ==(주소 비교) 결과가 갈린다.

String a = "abc";
String b = "abc";
a == b            // true  — 같은 풀 객체의 주소
String c = new String("abc");
a == c            // false — 힙의 다른 객체 주소
a.equals(c)       // true  — 내용 비교니까 당연히 같다
a == c.intern()  // true  — intern()은 "풀에 있는 같은 내용의 주소"를 돌려준다
==가 문자열에서 위험한 이유가 이것이다 — 비교하는 것은 내용이 아니라 주소다

그래서 new String(...)은 실무에서 쓸 이유가 거의 없다. 같은 내용의 객체를 하나 더 만들어 Eden을 쓰고 GC 일감을 늘릴 뿐이다.

이 문서와의 연결 — 여기서 "풀도 힙 안에 있다"는 7절의 사실이 쓰인다. 풀이 힙에 있으므로 참조가 끊긴 풀 문자열도 GC 대상이고, 그래서 intern()을 남용해도 예전 PermGen 시절처럼 영구히 눌러앉지는 않는다.

StackOverflowError가 났습니다. -Xmx를 늘리면 해결되나요?힌트: 두 에러는 이름만 비슷하고 사는 동네가 다르다 함정

전혀 해결되지 않는다. StackOverflowError는 스레드 스택이 넘친 것이고, -Xmx는 힙의 최대 크기다. 서로 다른 메모리다.

진짜 첫 조치는 옵션이 아니라 스택트레이스 읽기다. StackOverflowError의 스택트레이스에는 같은 메서드 이름이 수천 줄 반복되어 찍히므로, 어떤 사이클이 도는지가 그 자체로 드러난다.

재귀가 없는데도 나는 경우 상호 호출 사이클이 흔한 범인이다. 대표적으로 양방향 연관 엔티티의 toString()·equals()·JSON 직렬화가 서로를 계속 호출하며 무한히 내려간다. "재귀 함수를 안 썼는데요?"라고 말하기 전에 스택트레이스에서 반복되는 두 메서드 쌍을 먼저 찾는다.

-Xss를 올려도 되는 경우는 있다 — 알고리즘상 깊이가 정당하게 깊은 경우(깊은 트리 순회 등)다. 하지만 이때도 스레드마다 그 크기가 잡히므로 스레드 수 × 스택 크기만큼 네이티브 메모리를 더 쓴다는 대가를 알고 올려야 한다. 가능하면 재귀를 반복문 + 명시적 스택으로 바꾸는 쪽이 정공법이다.

int[] arr = new int[1000] — 기본형만 담은 배열도 힙인가요?힌트: 배열의 정체가 무엇인지부터

힙이다. 배열도 객체이기 때문이다. new가 붙었다는 것이 이미 답을 말하고 있다.

정리하면 이렇게 세 층으로 나뉜다.

스택지역변수 arr 칸 — 배열 객체의 주소값 하나만 들어간다. 배열 길이와 무관하게 주소 하나 크기다. 힙배열 객체의 실체 — 헤더 + 길이 정보 + 요소 1000칸. int이므로 값 1000개가 그 안에 직접 놓인다. 비교Integer[]였다면 요소 1000칸에 들어가는 것은 값이 아니라 Integer 객체 1000개의 주소다 — 힙에 객체가 1001개(배열 1 + 요소 1000)가 된다.
기본형 배열과 기본형 변수는 다르다 — 배열은 객체라서 힙, 변수는 값이라서 스택

실무로 잇는 한 줄 — 이 차이가 메모리 사용량에서 크게 벌어진다. int[]는 값이 촘촘히 붙어 있지만 Integer[]는 요소마다 객체 헤더가 붙고 참조를 한 번 더 따라가야 한다. 대용량 수치 배열에서 박싱 타입을 피하라는 조언의 근거가 이것이다.

덧붙일 것 — 아주 큰 배열은 Eden을 거치지 않고 바로 Old에 할당될 수 있다(humongous/large object 취급). "새 객체는 Eden"이라는 규칙의 예외로 알아두면 좋다.

Metaspace도 GC 대상인가요? 클래스는 언제 내려가나요?힌트: 회수 단위가 클래스가 아니다 시니어 변별

회수 자체는 일어난다. 다만 단위가 다르다 — 힙은 객체 단위로 회수되지만, Metaspace는 클래스 로더 단위로 통째로 회수된다. 이것을 클래스 언로딩(class unloading)이라고 한다.

조건을 정확히 말하면 이렇다. 어떤 클래스 로더가 회수 가능해지면, 그 로더가 로딩한 모든 클래스가 함께 내려간다. 로더가 회수 가능해지려면 그 로더 자신, 그 로더가 로딩한 클래스들의 Class 객체, 그리고 그 클래스들의 인스턴스가 전부 참조되지 않아야 한다.

그래서 하나만 붙잡혀도 전부 남는다 로더가 로딩한 클래스 중 인스턴스 하나가 다른 로더의 static 필드나 ThreadLocal에 남아 있으면, 그 인스턴스 → 클래스 → 로더 → 로더가 로딩한 나머지 수천 개 클래스 전부가 살아남는다. 이 연쇄가 클래스 로더 누수의 정체다(바로 앞 꼬리질문의 원인 ③).

일반 애플리케이션 코드에서는 사실상 언로딩이 안 일어난다는 점도 알아 둘 만하다. 애플리케이션 클래스 로더는 JVM이 살아 있는 동안 계속 살아 있으므로, 그 로더가 로딩한 우리 코드의 클래스들은 내려갈 일이 없다. 언로딩이 실제로 의미 있는 곳은 재배포·핫 리로드·동적 프록시·스크립트 엔진처럼 로더를 따로 만들어 쓰는 상황이다.

확인 방법 — -Xlog:class+unload(또는 구버전의 -XX:+TraceClassUnloading)로 언로딩 로그를 보고, 로딩 수는 계속 느는데 언로딩이 0이면 로더가 안 죽고 있다는 뜻이다. "로딩 수만 보지 말고 언로딩 수와 함께 보라"가 실전 팁이다.

힙을 -Xmx 2g로 잡았는데 컨테이너 한도 4g에서 프로세스가 죽습니다. 왜죠?힌트: JVM이 쓰는 메모리가 힙뿐인가 시니어 변별

-Xmx는 힙만 통제하고, 컨테이너 한도는 프로세스 전체 메모리를 본다. 둘 사이의 차이만큼이 사각지대다.

JVM 프로세스가 쓰는 메모리 = 힙 + α (α가 작지 않다)

  • Metaspace — 클래스 설계도. 상한 안 걸면 자동 확장.
  • 스레드 스택 — 스레드 수 × -Xss. 스레드가 많으면 여기가 크다.
  • 코드 캐시 — JIT가 컴파일한 기계어를 담는 영역.
  • GC 자체의 자료구조 — 카드 테이블, 리멤버드 셋 등 힙 크기에 비례해 커진다.
  • 다이렉트 버퍼 / 네이티브 라이브러리 — NIO DirectByteBuffer, 압축·암호화 네이티브 코드 등.

그래서 -Xmx를 컨테이너 한도에 바짝 붙여 잡으면 안 된다. 힙이 정직하게 2g를 다 쓰고 α가 2g를 넘는 순간, JVM은 아무 에러도 던지지 못한 채 커널의 OOM Killer에게 SIGKILL을 맞는다.

이 죽음에는 스택트레이스도 힙 덤프도 남지 않는다 — 로그의 마지막 줄이 평범한 상태로 끊긴다

구분법

  • JVM이 던진 OOM — 로그에 java.lang.OutOfMemoryError와 스택트레이스가 남는다. 어느 영역인지 메시지가 알려준다.
  • OOM Killer — 애플리케이션 로그에 아무것도 없고, 컨테이너/노드 이벤트에 OOMKilled 또는 종료 코드 137이 남는다.

조치 — ① -Xmx를 컨테이너 한도보다 여유 있게 잡거나 -XX:MaxRAMPercentage로 비율 지정, ② -XX:MaxMetaspaceSize 상한, ③ 스레드 수 상한, ④ 그래도 원인이 안 보이면 네이티브 메모리 추적(-XX:NativeMemoryTracking=summary 후 jcmd <pid> VM.native_memory summary)으로 어느 카테고리가 먹고 있는지 본다.

이 질문이 시니어를 가르는 이유 — "힙 = JVM 메모리"라고 생각하는 사람은 이 현상을 영원히 설명하지 못한다. 3절의 "Metaspace는 -Xmx 밖"이라는 사실을 Metaspace 하나가 아니라 α 전체로 확장해서 이해하고 있느냐를 본다.

탈출 분석 얘기를 하셨는데, 그럼 "객체는 항상 힙"은 틀린 말인가요?힌트: 규칙과 최적화는 층위가 다르다 가산점

개념 모델로는 맞고, 실행 시점의 사실로는 예외가 있다고 답하는 것이 정확하다. 둘의 층위가 다르다는 점을 짚는 게 핵심이다.

언어·명세 층위

new는 힙에 객체를 만든다. 프로그래머가 기대해도 되는 모델이고, 면접에서 요구하는 답도 이것이다.

JIT 최적화 층위

JIT가 탈출 분석(escape analysis)으로 "이 객체는 메서드 밖으로 절대 새어 나가지 않는다"고 증명하면, 힙 할당을 생략하고 객체의 필드들을 지역변수처럼 흩어 놓을 수 있다. 이것이 스칼라 치환(scalar replacement)이다.

흔한 오해 — "스택에 객체를 할당한다"가 아니다 많이들 "탈출 분석이 되면 객체가 스택에 생긴다"고 말하는데, 실제로 일어나는 일은 객체 형태를 아예 없애고 필드들을 낱개의 값(스칼라)으로 분해하는 것에 가깝다. 분해된 값들은 레지스터나 스택 슬롯에 놓인다. "객체가 통째로 스택에 놓인다"보다 "객체가 사라진다"가 실상에 가깝다.

왜 이걸 믿고 설계하면 안 되는지도 말해야 한다. 탈출 분석은 JIT가 충분히 실행된 뜨거운 코드에서, 상황이 맞을 때만 적용된다. 인라이닝이 안 되거나, 참조가 다른 스레드·필드·컬렉션으로 새어 나가면 즉시 포기하고 평범한 힙 할당으로 돌아간다. 결과가 코드에서 보이지 않고 예측하기도 어렵다.

말하는 순서 추천 — "객체는 힙입니다"를 먼저 확실히 못박고, 그 다음에 "다만 JIT의 탈출 분석이 스칼라 치환을 하면 할당 자체가 생략될 수 있는데, 이건 최적화이지 규칙이 아닙니다"로 붙인다. 순서를 뒤집으면 기본을 모르는 것처럼 들린다.

힙 덤프는 어떻게 뜨고, 열어서 무엇부터 보나요?힌트: "무엇이 많은가"만 봐서는 범인이 안 잡힌다

뜨는 방법

  • 사후 자동 — -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/경로. 운영 JVM에는 기본으로 켜 두는 것이 관례다. OOM은 재현이 어려워서 터진 그 순간의 덤프가 유일한 증거인 경우가 많다.
  • 수동 — jcmd <pid> GC.heap_dump /경로/heap.hprof 또는 jmap -dump:live,format=b,file=heap.hprof <pid>.
뜰 때의 대가 힙 덤프는 애플리케이션을 멈춘 채(stop-the-world) 힙 전체를 파일로 쏟아낸다. 힙이 크면 수 초~수십 초 멈추고 디스크에 힙 크기만큼의 파일이 생긴다. 피크 시간대에 아무 예고 없이 뜨면 그것 자체가 장애다. 그리고 :live 옵션은 덤프 전에 Full GC를 유발한다는 점도 알고 써야 한다.

지역변수가 thread-safe하다면서, 왜 동기화가 필요한 코드가 생기나요?힌트: 안전한 것은 "칸"이지 "칸이 가리키는 것"이 아니다 함정

안전한 것은 변수 칸이지, 그 칸이 가리키는 객체가 아니다. 이 한 문장이 답의 전부다.

스택은 스레드마다 하나씩이므로 다른 스레드는 내 스택 프레임을 들여다볼 방법이 아예 없다. 그래서 기본형 지역변수는 정말로 안전하다. 하지만 참조형 지역변수는 힙에 있는 객체의 주소를 담고 있을 뿐이고, 같은 주소를 다른 스레드도 알고 있다면 그 객체는 공유 자원이다.

public class Counter {
    private static final Map<String, Integer> SHARED = new HashMap<>();  // 힙, 공유

    public void hit(String key) {
                int local = 1;                 // 스택 · 완전히 안전
                Map<String, Integer> m = SHARED;  // 변수 칸 m은 스택(안전)
                m.merge(key, local, Integer::sum);  // 그러나 m이 가리키는 객체는 힙의 공유 객체 → 동기화 필요
    }
}

m이라는 칸은 이 스레드만의 것이지만, 그 칸에 적힌 주소가 가리키는 HashMap은 모든 스레드가 함께 쓰는 그 한 개다. 여러 스레드가 동시에 merge를 부르면 갱신 유실이 나고 HashMap의 내부 구조가 깨질 수도 있다.

"스레드 전용"인 것은 스택 프레임이지 참조가 가리키는 힙 객체가 아니다

그래서 판별 기준은 하나다

"이 객체의 주소를 나 말고 다른 스레드도 알 수 있는 경로가 있는가?" — static 필드, 다른 객체의 필드, 컬렉션, 스레드에 넘긴 람다의 캡처 등 경로가 하나라도 있으면 공유 자원이다. 메서드 안에서 만들어 메서드 안에서만 쓰고 밖으로 안 내보내는 객체는 반대로 완전히 안전하다 — 이것이 지역 변수 한정(confinement)이라는 가장 값싼 동시성 대책이다.

흥미로운 연결 — 이 "밖으로 안 새어 나간다"는 조건은 JIT의 탈출 분석이 보는 조건과 정확히 같다. 안전한 객체가 곧 최적화하기 좋은 객체인 셈이다.

객체 하나가 힙에서 차지하는 크기는 어떻게 정해지나요?힌트: 그 계산을 하려면 어느 영역의 정보가 필요한가 가산점

세 조각의 합이다 — 객체 헤더 + 필드들 + 정렬 패딩.

헤더마크워드(해시코드·GC 나이·락 상태 등 JVM이 쓰는 관리 정보)와 클래스 포인터(이 객체가 어느 클래스의 인스턴스인지 → Metaspace의 설계도를 가리킨다). 배열이면 길이 정보가 더 붙는다. 필드기본형은 값의 크기만큼, 참조형은 주소 하나 크기. 객체를 필드로 갖는다고 그 객체가 안에 포함되는 게 아니라 주소만 들어간다는 점이 중요하다. 패딩CPU가 메모리를 다루기 좋게 일정 단위로 정렬하기 위해 남는 자리를 채운다. 그래서 필드를 하나 늘려도 크기가 그대로이거나, 1바이트 늘렸는데 객체가 통째로 한 칸 커지는 일이 생긴다.

이 질문이 이 문서와 이어지는 지점은 여기다 — JVM은 이 계산을 어떻게 하는가? new 시점에 "이 객체가 몇 바이트인지"를 알아야 힙에서 자리를 떼어 줄 수 있는데, 그 정보(필드가 몇 개이고 각각 몇 바이트이며 어디에 배치되는지)는 Metaspace에 있는 클래스 설계도에 적혀 있다.

Metaspace가 없으면 힙에 자리를 뗄 수조차 없다 — 설계도가 크기를 알려 주기 때문이다

실무 함의 둘.

  • 작은 객체를 아주 많이 만들면 헤더 비용이 무시할 수 없다. 필드 하나짜리 객체 수백만 개는 실제 데이터보다 헤더와 참조가 더 클 수 있다. Integer[] 대신 int[]를 권하는 이유가 이것이다.
  • 참조 폭도 변수다. -XX:+UseCompressedOops가 켜져 있으면 참조를 좁게 표현해 객체가 작아진다 — 힙이 아주 커지면 이 최적화가 꺼져서 힙을 늘렸는데 담기는 객체 수는 그만큼 안 늘어나는 현상이 생길 수 있다.

정확한 수치가 궁금하면 추측하지 말고 JOL(Java Object Layout) 같은 도구로 실제 실행 환경에서 찍어 보는 것이 맞다. 헤더 크기와 정렬 단위는 JVM 구현·버전·옵션에 따라 달라지기 때문이다. 면접에서도 "환경마다 다르므로 구조로 설명드리면"이라고 여는 편이 안전하다.

한 줄 요약
변수에 담기는 것은 객체가 아니라 객체가 있는 힙 주소값(참조)이라는 사실에서 출발하면, 객체의 실체는 힙(새 객체는 Eden), 스택에는 스레드별 호출 프레임과 참조만, Metaspace에는 클래스 설계도만 있다는 지도가 자연히 그려진다 — 그리고 이 지도를 알아야 OOM 메시지와 메모리 그래프를 보고 "어느 영역의 문제이고 무슨 덤프를 떠야 하는지"를 첫 수에 판단할 수 있다.
