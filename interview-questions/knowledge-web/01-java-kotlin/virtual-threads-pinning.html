Virtual Thread(Java 21+) — 스레드 모델의 차이, Continuation 원리, pinning, @Transactional 함정

📖 약 27분 🧩 9개 섹션 0/9 섹션 이해
🎯 핵심 관전 포인트

가상 스레드는 처리 속도가 아니라 "대기 중 동시성"을 높이는 기술이다. 스레드란 결국 "콜 스택 + 실행 위치"라는 데이터인데, 과거엔 블로킹이 커널 안에서 일어나 JVM이 개입할 타이밍이 없었기에 1:1일 수밖에 없었다. Loom은 JDK가 시스템 콜 직전 경로를 소유한다는 점을 이용해, 블로킹 대신 "epoll 등록 + 스스로 스택을 힙에 얼리고(freeze) 물러나기"로 바꿔치기했다 — 블로킹 스타일 코드 그대로 리액티브급 동시성을 얻는다. 도입 시 함정 두 가지: (1) JVM이 경로를 소유하지 못한 지점 (synchronized/JNI)에서 블로킹하면 캐리어에 못박히는 pinning (Java 24 JEP 491에서 synchronized는 해소), (2) 가상 스레드는 스레드만 해방시킬 뿐 DB 커넥션은 못 푼다 — @Transactional 안 외부 API 콜은 동시성이 폭증한 만큼 커넥션 풀 고갈로 더 크게 터진다.

"Virtual Thread(Project Loom)는 기존 스레드 모델과 무엇이 다른가요? pinning 문제란?"

출제 의도새 기술 도입 판단의 시금석이다. "가상 스레드 쓰면 다 해결"이 아니라 pinning(synchronized 블록 내 블로킹) 같은 제약과 기존 코드베이스의 궁합을 먼저 따지는 사람인지 — 즉 하이프와 실제를 구분하는 습관이 있는지를 본다.
1

기존 스레드 모델(플랫폼 스레드)의 문제

▾

지금까지 자바의 Thread는 OS 스레드와 1:1로 묶인 얇은 포장지였다 (플랫폼 스레드). OS 스레드는 비싼 자원이다 — 스택으로 스레드당 약 1MB 메모리를 예약하고, 생성/컨텍스트 스위칭에 커널이 개입하며, 한 머신에서 수천 개 이상 만들기 어렵다.

그래서 서버는 스레드 풀로 개수를 제한하는데, 여기서 병목이 생긴다:

java
// 톰캣 기본 스레드 풀 200개인 서버에서
public Order getOrder(Long id) {
    Member member = memberClient.get(id);   // 외부 API 호출 300ms — 스레드는 그동안 '잠들어서' 대기
    Order order = orderRepository.find(id); // DB 조회 50ms — 또 대기
    return order;
}

요청 하나가 350ms 동안 스레드를 점유하지만, 그중 CPU를 실제로 쓰는 시간은 몇 ms뿐이다. 스레드가 일을 안 하고 "기다리는 데" 소모된다. 동시 요청이 200개를 넘으면 CPU가 놀고 있는데도 처리량이 막힌다 — I/O 대기가 많은 전형적인 웹 서버에서 스레드 수가 곧 동시성의 상한이 되는 구조다.

이걸 피하려던 기존 답이 리액티브(WebFlux 등)인데, 코드 전체를 콜백/체이닝 스타일로 바꿔야 해서 작성·디버깅·스택트레이스가 모두 어려워지는 대가를 치렀다.

2

Virtual Thread — 스레드를 OS가 아니라 JVM이 관리한다

▾

Virtual Thread는 OS 스레드와 1:1 매핑을 끊은, JVM이 스케줄링하는 경량 스레드다. (이걸 만든 OpenJDK 프로젝트의 코드명이 Loom — 2017년 시작해 2023년 Java 21에 정식 포함됐다. loom은 "베틀"이라는 뜻으로, 스레드(실)를 짜는 도구라는 말장난이다.)

동작 방식:

  1. 소수의 OS 스레드(캐리어 스레드, 기본값 = CPU 코어 수)가 실행대 역할을 한다.
  2. 가상 스레드는 캐리어 위에 올라타서(mount) 실행되다가,
  3. 블로킹 I/O를 만나면 JVM이 가상 스레드의 실행 상태(스택)를 힙에 떼어 저장하고 캐리어에서 내린다(unmount).
  4. 비워진 캐리어는 즉시 다른 가상 스레드를 실행한다. I/O가 끝나면 그 가상 스레드는 다시 아무 캐리어에나 올라타 이어서 실행된다.

"JVM이 스케줄링한다"는 말은 OS 스케줄러가 교체됐다는 뜻이 아니라 2층 구조가 됐다는 뜻이다:

text
가상 스레드 수만 개
   ↓  JVM 스케줄러(JDK 안의 ForkJoinPool — 자바 코드다)가
      "어느 캐리어에서 실행할지" 배정
캐리어 스레드 8개 (평범한 OS 스레드)
   ↓  OS 스케줄러가 "어느 CPU 코어에서 실행할지" 배정 — 여전히 일한다
CPU 코어 8개

OS는 가상 스레드의 존재를 전혀 모른다 — 그냥 "자바 프로세스에 스레드 8개가 있네"라고만 본다.

즉, "스레드가 기다린다 = OS 스레드가 논다"라는 등식을 깬 것이다. 기다림의 비용이 힙에 저장된 몇 KB의 스택으로 줄어들어, 가상 스레드는 수백만 개도 만들 수 있다.

✕ BEFORE스레드 풀로 개수를 아껴 쓰는 모델
ExecutorService pool = Executors.newFixedThreadPool(200);
✓ AFTER작업마다 가상 스레드 하나 — 풀링 자체가 불필요
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
executor.submit(() -> {
    Member member = memberClient.get(id);   // 블로킹처럼 '보이지만' 캐리어는 안 묶임
    return orderRepository.find(id);
});
// Spring Boot 3.2+: spring.threads.virtual.enabled=true 한 줄이면 톰캣이 요청마다 가상 스레드 사용

가장 큰 가치는 코드 스타일을 바꾸지 않아도 된다는 점이다. 리액티브처럼 코드를 뒤집지 않고, 지금까지처럼 순차적·블로킹 스타일로 쓰면 JVM이 알아서 논블로킹처럼 굴려준다.

주의할 오해 하나: 가상 스레드는 처리 속도를 높이는 게 아니라 "대기 중 동시성"을 높이는 기술이다. CPU 연산 위주 작업에는 이득이 없다 — 어차피 코어 수만큼만 동시에 돌 수 있으니까.

3

원리 — 스레드의 정체와 Continuation (freeze/thaw)

▾

3-1. 스레드의 정체: 실행 상태 = 데이터

스레드라는 건 결국 두 가지다:

  1. 콜 스택 — 지금까지 어떤 메서드를 타고 들어왔고, 각 지역 변수가 뭔지
  2. 실행 위치 — 지금 어느 명령어까지 실행했는지 (프로그램 카운터, 레지스터)

콜 스택은 신비로운 게 아니라 그냥 메모리 덩어리다. 메서드를 호출할 때마다 "스택 프레임"(지역 변수 값 + 계산 중간값 + 돌아갈 위치)이 차곡차곡 쌓인다.

text
handleRequest() 실행 중의 스택 (아래에서 위로 쌓임):

│ getUser() 프레임       │ ← 지금 여기 실행 중 (지역변수: userId=42, conn=...)
│ handleRequest() 프레임 │ (지역변수: request=..., 돌아갈 위치: 137번째 줄)
│ run() 프레임           │
└───────────────────────┘

핵심 통찰: "프로그램이 어디까지 진행됐는가"라는 정보 전체가 이 메모리 덩어리 안에 데이터로 들어 있다. 실행 상태란 곧 데이터이고, 데이터라면 저장했다가 복원할 수 있다 — 이게 전환의 이론적 근거다.

그럼 가상 스레드의 이 데이터는 어디에 저장되는가 — 언제냐에 따라 두 곳을 오간다:

가상 스레드의 상태콜 스택이 사는 곳
실행 중 (캐리어에 mount됨)캐리어(OS 스레드)의 진짜 스택 — 캐리어 스택을 빌려 쓰며, 그 순간엔 평범한 스레드와 완전히 동일하게 동작
대기 중 (unmount됨)힙의 StackChunk 객체 (freeze의 결과물, 3-3절)

가상 스레드는 자기만의 스택을 상시 보유하지 않는다. 올라탄 캐리어의 스택 위에 프레임을 쌓으며 실행되다가, 블로킹을 만나면 그 프레임들을 힙으로 복사해 내고 캐리어 스택은 원상복구된다. "실행 위치"도 마찬가지 — 실행 중엔 CPU 레지스터(프로그램 카운터)에 있지만, freeze는 항상 yield()라는 정해진 메서드 호출 지점에서 일어나므로 "돌아올 위치 = yield 다음 줄"이 스택 프레임의 리턴 주소로 이미 기록돼 있다. 레지스터를 따로 백업할 필요가 없는 이유다.

3-2. 과거 1:1의 진짜 장벽 — 메모리 소유가 아니라 "개입 타이밍"

흔한 오해: "스택이 OS 소유라서 JVM이 못 읽는다" — 아니다. OS 스레드의 스택은 내 프로세스의 주소 공간 안에 있는 평범한 유저 메모리이고, JVM은 언제든 읽고 쓸 수 있다. OS가 진짜로 소유한 건 두 가지 통제권이다:

  1. 스케줄링 권한 — 스레드를 언제 재우고 깨울지는 커널만 결정
  2. 끊긴 순간의 실행 위치 — 커널이 선점(preempt)으로 끊으면 레지스터/PC 상태는 커널의 컨텍스트 저장소에 들어가고, JVM은 임의 시점의 이 정보에 접근 못 함

과거의 진짜 장벽: read()를 호출하면 곧장 블로킹 시스템 콜로 들어가고, 잠드는 위치가 커널 안이라 JVM이 끼어들 지점이 0곳이었다. "잠깐, 재우지 말고 그 스택만 나한테 줘"라고 말할 타이밍 자체가 없었던 것이다.

3-3. Loom의 해법 — 잠들기 전에 스스로 얼린다

결정적 아이디어: 가상 스레드는 블로킹 시스템 콜에 아예 들어가지 않는다. 잠든 다음 밖에서 상태를 꺼내는 게 아니라, 잠들 상황이 오면 아직 멀쩡히 실행 중인 스레드가 자기 손으로 자기 스택을 힙에 복사하고 물러난다.

java
socket.getInputStream().read(buf);   // 애플리케이션은 그냥 이렇게 호출

이 아래에서 벌어지는 일 (가상 스레드일 때):

text
1. JDK 내부의 read 구현 실행 — 아직 시스템 콜 안 함, 그냥 자바 코드
2. "지금 가상 스레드 위에서 돌고 있네?" 확인
3. 소켓을 논블로킹 모드로 epoll(OS의 이벤트 알림 장치)에 등록:
   "이 소켓에 데이터 오면 알려줘" — 즉시 리턴됨, 안 잠듦
4. Continuation.yield() 호출
   ★ 바로 이 순간 freeze — 스레드는 깨어서 실행 중이므로 자기가 어느
     메서드의 어느 지점에 있는지 스스로 정확히 안다. 가상 스레드 시작
     지점부터 현재까지의 프레임들을 힙 객체(StackChunk)로 복사하고,
     캐리어 스택은 되감아(rewind) 캐리어에서 내려옴
5. 캐리어는 즉시 다음 가상 스레드 실행 (캐리어는 한순간도 안 잠)
   ...
6. 데이터 도착 → epoll을 감시하던 JVM 내부 poller가 감지
   → 스케줄러에 그 가상 스레드 재등록
7. 아무 캐리어가 thaw(스택을 캐리어 위에 복원) → yield 다음 줄부터 재개
   → 데이터가 와 있으니 논블로킹 read로 즉시 읽고 리턴
  • epoll이란: 리눅스 커널이 제공하는 "I/O 이벤트 알림 서비스"다. 블로킹 방식이 주문마다 직원 한 명이 주방 앞에 서서 음식을 기다리는 것이라면, epoll은 진동벨이다 — "이 소켓 1만 개 등록해둘게, 데이터 도착한 놈 생기면 알려줘"라고 커널에 부탁하면 스레드 하나가 소켓 1만 개를 감시할 수 있다. JVM 내부엔 이 epoll을 감시하는 전담 스레드(poller)가 있다. (macOS는 kqueue, 윈도우는 IOCP가 같은 역할.)
  • 게임 세이브와 같은 개념이다: 진행 상태 전부를 파일로 저장해두면 다른 컴퓨터에서도 이어서 할 수 있다. 얼려진 실행 상태는 힙에 사는 평범한 자바 객체(몇 KB)라서 수백만 개 보관 가능 — OS 스택의 1MB 예약과 대비.
  • 기절한 사람의 기억을 꺼내는 게 아니라 잠들기 전에 본인이 일기를 써두는 방식이다. 커널 선점처럼 아무 데서나 끊기는 게 아니라 정해진 지점(yield)에서 스스로 전환하므로, 실행 위치를 커널에 물어볼 필요가 없다 — 선점형과 대비해 협조적(cooperative) 스케줄링이라 부른다.
  • 캐리어는 마법이 아니다 — OS 입장에서 보면 new Thread()로 만든 것과 아무 차이 없는 평범한 OS 스레드다. 특별한 커널 기능도 안 쓴다. 다만 그 스레드가 실행하는 프로그램이 "대기열에서 얼려진 가상 스레드 꺼내기 → thaw → 실행 → yield하면 다음 것"이라는 루프일 뿐이다. 목수 8명이 의뢰 10만 건을 처리하는 건 작업대가 마법이어서가 아니라 "재료 기다림에 걸린 작업은 하다 만 상태 그대로 서랍에 넣고 다른 의뢰를 꺼낸다"는 규칙 덕분인 것과 같다 — 마법은 작업대(캐리어)가 아니라 서랍(Continuation의 freeze/thaw)에 있다.
  • 1:1을 깬 본질은 "실행 상태의 소유권" 이동이다. 소유권이란 "멈춘 작업을 이어가는 데 필요한 데이터를 누가 쥐고 있고, 재개 시점을 누가 결정하는가"다. 플랫폼 스레드가 블로킹하면 그 순간의 실행 상태는 커널의 컨텍스트 저장소에 들어가고 깨우는 시점도 커널만 결정한다 — 그 작업을 이어갈 수 있는 유일한 존재가 바로 그 OS 스레드가 되므로, 자바 스레드 100만 개를 원하면 OS 스레드도 100만 개 필요했다(1:1 강제). 가상 스레드는 멈춘 상태가 힙의 평범한 자바 객체라서 아무 OS 스레드 위에서나 복원 가능한 이동식 데이터가 된다 — 실행 상태 100만 개를 OS 스레드 8개가 돌려가며 재생할 수 있다(M:N). 세이브 파일이 게임기 본체에 잠겨 있어 게임 수만큼 본체가 필요했는데, 이동식 카드가 되면서 본체 8대로 게임 100만 개를 이어할 수 있게 된 것.

3-4. 왜 JVM만 이걸 할 수 있나

스택 복사가 가능하려면 스택 안에 뭐가 어디 있는지 완벽히 알아야 한다. JVM은 모든 프레임을 자기가 만들었고, 각 칸이 int인지 객체 참조인지 메타데이터를 이미 갖고 있다 — GC가 스택을 훑으며 살아있는 참조를 찾을 때 쓰던 바로 그 능력이다. 그래서 힙으로 옮긴 뒤에도 GC가 StackChunk 안의 참조를 정상 추적한다.

반면 C로 컴파일된 네이티브(JNI) 프레임은 JVM이 내부 구조를 모르고, C 코드는 스택 주소 자체를 포인터로 들고 있을 수 있어 옮기는 순간 깨진다. → 네이티브 프레임이 스택에 끼면 얼릴 수 없다 — pinning의 근본 원인 (4절).

또 하나: 블로킹을 "epoll 등록 + yield"로 바꿔치기하려면 그 경로가 JVM 진영의 코드여야 한다. Socket, InputStream, Thread.sleep, BlockingQueue, JDBC 아래의 소켓... 블로킹이 일어나는 JDK의 모든 지점을 재작성해야 했고, 이게 Loom이 6년(2017~2023) 걸린 가장 큰 이유다.

3-5. 역할 분담 — 내리는 건 본인, 올리는 건 캐리어, 깨우는 건 poller

참고로 만드는 것은 아무 스레드나 한다 — Thread.ofVirtual().start() 같은 생성 API를 호출한 스레드가 만들며(Spring Boot에선 spring.threads.virtual.enabled=true를 켜면 톰캣 내부 스레드가 요청마다 호출해준다), 그 실체는 커널 시스템 콜 없이 힙에 VirtualThread 객체 하나 할당 + 스케줄러 대기열 등록이 전부다. 플랫폼 스레드 생성이 커널에 clone 시스템 콜을 하고 스택 1MB를 예약하는 것과 달리 객체 new 수준으로 싸다 — "요청마다 만들고 버리는" 모델이 성립하는 근거다.

만들어진 뒤의 mount/unmount를 지휘하는 별도의 "관리자 스레드"는 없다. 역할이 셋으로 나뉜다:

  1. freeze + unmount → 가상 스레드 본인. 블로킹 직전, 아직 멀쩡히 실행 중인 가상 스레드가 Continuation.yield()를 실행하며 자기 스택을 힙에 복사하고 스스로 물러난다. 외부의 누가 떼어내는 게 아니다.
  2. 다음 가상 스레드 mount → 캐리어 본인. 캐리어(ForkJoinPool 워커)가 도는 코드가 곧 무한 루프다: "대기열에서 가상 스레드 하나 꺼냄 → thaw → 실행 → 걔가 yield하거나 끝나면 → 다시 꺼냄". mount는 캐리어가 자기 일감을 집어드는 행위 그 자체다.
  3. I/O 끝난 가상 스레드를 대기열에 재등록 → JVM 내부 poller 스레드. epoll을 감시하다 "데이터 도착" 알림을 받으면, 얼려져 있던 해당 가상 스레드를 스케줄러 대기열에 다시 넣는다.

3-6. 오버헤드는 없나 — "코드가 늘었으니 느려진 것 아닌가"

가상 스레드용 분기와 freeze/thaw 코드가 추가된 건 사실이다. JDK 블로킹 API 내부가 개념적으로 이렇게 바뀌었다:

java
// JDK 내부 read()의 개념적 모습
if (현재 스레드가 가상 스레드인가?) {
    소켓을 epoll에 등록;
    Continuation.yield();     // freeze하고 물러남
    // ...깨어나면 여기부터 재개 — 데이터가 와 있으니 논블로킹 read
} else {
    기존 블로킹 시스템 콜;      // 플랫폼 스레드는 예전 경로 그대로
}

프록시처럼 앞뒤로 로직을 덧댄 게 맞다 — 단, 덧댄 위치가 애플리케이션 코드가 아니라 JDK 라이브러리 내부다. 그래서 비용이 붙는 위치를 정확히 봐야 한다:

  • CPU로 계산하는 동안엔 오버헤드 0 — mount된 가상 스레드는 캐리어 스택 위에서 평범한 스레드와 똑같은 기계어로 돈다. 명령어마다 붙는 세금 같은 건 없다.
  • 비용은 블로킹 지점에만 붙는다 — 분기 체크 + freeze/thaw 복사. 그런데 플랫폼 스레드도 블로킹이 공짜가 아니다: OS 컨텍스트 스위칭 (커널 진입, 레지스터 저장, CPU 캐시 오염)이라는 비용을 치르며, freeze/thaw는 이와 비슷하거나 오히려 싸다.

정리: 대기가 전혀 없는 단일 작업이라면 이득은 없고 미세한 손해가 있을 수 있다(2절의 "CPU 바운드에 무의미"가 이 얘기). 이 기술은 요청 하나를 빠르게 하는 게 아니라 "동시에 기다릴 수 있는 개수"를 폭증시키는 것이다.

4

역사 — 사실 자바는 이 기술을 갖고 있다가 버렸다

▾

자바 1.0~1.2 시절 "그린 스레드(green threads)"라는 이름으로 정확히 이 아이디어가 있었다. OS 스레드 하나 위에서 JVM이 여러 자바 스레드를 스케줄링하는 방식(M:1). 1.3 즈음 걷어내고 OS 스레드 1:1로 갈아탄 이유:

  1. 멀티코어를 못 썼다 — OS 스레드 하나 위의 다중화(M:1)라서 코어가 몇 개든 하나만 사용. 당시 막 SMP 서버가 퍼지던 시기라 치명적.
  2. 블로킹 시스템 콜 하나가 전체를 마비시켰다 — 그린 스레드 하나가 파일 읽기로 블로킹되면 유일한 OS 스레드가 잠들어 나머지 전부 정지. 피하려면 모든 I/O를 논블로킹으로 감싸야 하는데, 당시 OS에는 epoll/kqueue 같은 논블로킹 I/O 인프라가 없거나 미성숙했다.
  3. OS 스레드가 좋아졌다 — 리눅스 NPTL 등 커널 스레드 구현이 빨라지며 "그냥 OS에 맡기는 게 단순하고 충분히 빠르다"가 당시의 합리적 결론.

즉 개념이 없어서가 아니라, 구현할 기반 기술이 없었고 당시 워크로드에선 필요도 크지 않았다. Virtual Thread는 실패 원인이 전부 해소된 형태로 돌아온 부활이다:

  1. M:1이 아니라 M:N — 캐리어를 코어 수만큼 두고 work-stealing 스케줄러(ForkJoinPool)로 분배 → 멀티코어 활용 (1번 해결)
  2. 논블로킹 I/O 인프라 성숙 — epoll/kqueue + 자바 NIO(1.4+) 위에서 JDK 블로킹 API를 겉모습 그대로 속만 재작성 (2번 해결)
  3. Continuation을 감당할 JVM 기술 — 힙에 얼린 스택의 GC 추적, JIT 프레임 freeze/thaw 등 고난도 엔지니어링이 가능해짐
  4. 필요가 폭발 — 마이크로서비스 시대에 I/O 대기형 워크로드가 폭증했고, Go의 고루틴이 이 모델(M:N + 런타임 스케줄링)이 실전에서 통함을 증명
5

Pinning — 캐리어에서 못 내려오는 상황

▾

가상 스레드의 마법은 "블로킹 시 캐리어에서 내린다"인데, 내리지 못하는 경우가 있다. 이걸 pinning(고정)이라고 한다. 가상 스레드가 캐리어에 못박히면 그동안 그 캐리어(OS 스레드)가 통째로 잠든다 — 플랫폼 스레드 시절로 퇴행하는 것이다.

핀 되는 대표 상황 (Java 21 기준)

java
// 1. synchronized 블록/메서드 안에서 블로킹
synchronized (lock) {
    String result = httpClient.send(request);  // 이 대기 동안 캐리어가 통째로 묶임!
}

// 2. 네이티브 코드(JNI) 호출 중 블로킹

원리(3절)와 연결하면 이유가 명확하다:

  • JNI: 네이티브 프레임은 JVM이 구조를 모르는 C 스택이라 얼릴 수 없다 (3-4절). 블로킹도 커널로 직행하므로 바꿔치기할 지점이 없다.
  • synchronized: 잠금 소유 기록이 "힙의 객체"가 아니라 "OS 스레드 (캐리어)"에 결부돼 있어서, 스택만 떠서 옮기면 잠금 정보가 따라가지 못한다.

왜 위험한가

캐리어는 기본 CPU 코어 수만큼(예: 8개)뿐이다. 가상 스레드 8개가 synchronized 안에서 긴 I/O에 핀 되면 캐리어 전원이 묶여서, 나머지 수만 개의 가상 스레드가 전부 멈춘다. 커넥션 풀 대기 등과 얽히면 데드락으로도 이어질 수 있다. 실제로 초기에 커넥션 풀 라이브러리(HikariCP 등)나 낡은 드라이버 내부의 synchronized가 문제가 됐다.

회피 방법

✕ BEFOREsynchronized 안에서 I/O → pinning
private final Object lock = new Object();
synchronized (lock) {
    callExternalApi();
}
✓ AFTERReentrantLock은 pinning 없음 — 잠금 대기·보유 중에도 unmount 가능
private final ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    callExternalApi();
} finally {
    lock.unlock();
}
  • 오래 블로킹하는 구간을 감싸는 synchronized를 ReentrantLock으로 교체 (짧은 인메모리 연산만 보호하는 synchronized는 실질 문제 없음)
  • 의존 라이브러리가 내부에서 synchronized + I/O를 하는지 점검
  • 탐지: -Djdk.tracePinnedThreads=full 실행 옵션 또는 JFR의 jdk.VirtualThreadPinned 이벤트로 핀 발생 지점 확인

버전 맥락 (말하면 플러스)

synchronized pinning은 Java 24(JEP 491)에서 해소 — 잠금 기록 방식을 바꿔 synchronized 안에서도 unmount가 가능해졌다. 즉 "Java 21~23에서 도입한다면 반드시 점검할 사항, 24+라면 부담이 크게 줄어든 사항"이라고 버전 맥락까지 말하면 좋다. (JNI pinning은 구조상 그대로다.)

6

@Transactional 안 외부 API 콜 — 가상 스레드가 못 푸는 문제

▾

원래 문제 (가상 스레드와 무관하게 존재)

java
@Transactional
public void placeOrder(OrderRequest req) {
    orderRepository.save(order);          // DB 커넥션 사용
    paymentClient.approve(req);           // 외부 API 300ms~수 초 — 그동안 DB 커넥션을 쥔 채 대기!
    orderRepository.update(order);
}

@Transactional 메서드는 시작할 때 커넥션 풀(HikariCP)에서 DB 커넥션을 하나 꺼내서 메서드가 끝날 때까지 쥐고 있다. 외부 API를 기다리는 동안 그 커넥션은 아무 쿼리도 안 하면서 반납되지 않는다. HikariCP 기본 풀은 10개뿐이라, 동시 요청 10개면 나머지는 전부 커넥션 대기에 걸린다. 그래서 "트랜잭션 안에서 외부 API 콜 금지"가 정석이다.

가상 스레드를 도입하면 — 병목이 이동하며 증폭된다

대기 중 점유하는 자원이 두 개라는 걸 구분하는 게 핵심이다:

대기 중 점유하는 자원플랫폼 스레드가상 스레드
스레드톰캣 스레드 1개 묶임해결됨 — unmount 되어 캐리어는 다른 일 함
DB 커넥션1개 묶임그대로 묶임 — 커넥션은 스레드가 아니라 트랜잭션에 묶인 자원

가상 스레드가 해방시켜 주는 건 스레드뿐이다. 외부 API를 기다리는 동안 캐리어는 다른 요청을 처리하러 가지만, 그 가상 스레드가 쥔 DB 커넥션은 여전히 반납되지 않는다.

여기서 역설이 생긴다. 예전에는 톰캣 스레드 200개가 동시성의 상한이라 커넥션 풀 경쟁도 최대 200까지였는데, 가상 스레드로 동시 요청이 수만 개로 늘어나면 그 수만 개가 전부 커넥션 10개를 두고 경쟁한다. 병목이 "스레드 부족"에서 "커넥션 부족"으로 이동하면서 트랜잭션 안 외부 API 콜의 피해가 오히려 증폭된다 — 커넥션 타임아웃(connection is not available) 장애가 터지기 훨씬 쉬워진다.

pinning 관점의 연관도 있다: Java 21~23 기준으로 트랜잭션 경로에는 JDBC 드라이버나 커넥션 풀 내부의 synchronized가 끼어 있을 수 있다(구버전 MySQL Connector/J가 대표 사례). 이 경우 DB I/O 대기 중 unmount조차 못 하고 캐리어가 핀 된다. 그래서 가상 스레드 + @Transactional 조합 검토 시 드라이버/풀 라이브러리 버전 점검과 jdk.VirtualThreadPinned JFR 이벤트 감시가 체크리스트에 들어간다.

올바른 설계는 가상 스레드가 있든 없든 동일하다

외부 API 콜을 트랜잭션 밖으로 빼는 것.

java
// 트랜잭션 경계를 좁힌다
public void placeOrder(OrderRequest req) {
    orderService.saveOrder(order);        // @Transactional — 커넥션 점유는 짧게
    paymentClient.approve(req);           // 트랜잭션 밖 — 커넥션 안 쥐고 대기
    orderService.confirmOrder(order);     // @Transactional — 별도의 짧은 트랜잭션
}

(이렇게 쪼개면 원자성이 깨지므로, 중간 실패 시 보상 처리나 상태 기반 재시도 같은 정합성 설계가 따라와야 한다.)

7

ThreadLocal — 동작은 안전하다, 깨지는 건 사용 패턴이다

▾

7-1. 값은 캐리어가 아니라 "가상 스레드 객체"에 붙는다

ThreadLocal은 값을 자기 안에 담고 있는 게 아니다. 실제 값은 각 Thread 객체 안의 필드(threadLocals라는 맵)에 저장되고, ThreadLocal 객체는 그 맵을 여는 "열쇠" 역할만 한다:

java
// ThreadLocal.get()이 내부적으로 하는 일 (개념적으로)
Thread t = Thread.currentThread();   // ① 지금 실행 중인 스레드가 누구?
return t.threadLocals.get(this);     // ② '그 스레드의' 맵에서 꺼냄

그러니 질문은 ①로 좁혀진다: 가상 스레드가 캐리어 위에서 도는 동안 currentThread()는 누구인가 — 가상 스레드다. mount하는 순간 JVM이 "현재 스레드" 정체성을 가상 스레드로 바꿔치기하고, 캐리어 자신의 ThreadLocal은 그동안 숨겨져 아무도 못 본다.

text
캐리어 #3 (OS 스레드)
│  ├─ 캐리어 자신의 threadLocals ← mount 동안 숨겨짐
│
└─ 지금 올라탄 가상 스레드 V-42 (힙에 사는 객체)
      └─ V-42의 threadLocals ← ThreadLocal.get()이 보는 곳 ★

가상 스레드의 실체는 힙 객체이므로(3-1절), 이 맵도 unmount 시 얼려진 스택과 함께 힙에 남아 캐리어를 갈아타도 가상 스레드를 따라다닌다. 만약 캐리어에 붙어 있었다면 같은 캐리어를 번갈아 쓰는 가상 스레드 수만 개가 서로의 값(남의 SecurityContext!)을 봤을 텐데, 그런 일은 일어나지 않는다. Spring Security의 SecurityContext, 로깅 MDC 같은 ThreadLocal 기반 프레임워크도 "요청 하나 = 가상 스레드 하나" 구도에서 그대로 동작한다.

7-2. 그런데 왜 "주의"인가 — 스레드당 캐싱 패턴의 전제가 무너진다

java
// 플랫폼 스레드 풀 시절엔 합리적이었던 패턴
private static final ThreadLocal<SimpleDateFormat> FORMAT =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));

이 패턴이 성립했던 전제 두 가지가 모두 무너진다:

전제플랫폼 스레드 풀가상 스레드
스레드 개수가 적다200개 → 객체도 최대 200개수백만 개 → 객체도 수백만 개 (메모리 폭탄)
스레드가 오래 살며 재사용된다풀에서 계속 재사용 → 캐싱 이득일회용 — 작업 하나 끝나면 죽음 → 캐시 적중 자체가 없음

가상 스레드는 풀링하지 않고 작업마다 새로 만드는 게 정석이라(8절 "풀링 금지"), "스레드가 오래 살아 초기화 비용을 상환한다"는 캐싱의 근거가 사라진다. 만들어봤자 한 번 쓰고 스레드와 함께 버려지며, 동시 요청이 수만 개면 그 비싼 객체가 수만 개 동시에 생긴다 — 이득은 0, 비용만 폭증한다.

7-3. InheritableThreadLocal — 복사의 트리거는 요청이 아니라 "스레드 생성"

InheritableThreadLocal은 스레드가 생성되는 순간 부모(그 생성 코드를 실행한 스레드)의 값 테이블을 자식에게 복사해 주는 장치다. 이 복사 비용은 예전에도 있었다 — 차이는 생성 빈도다:

플랫폼 스레드 풀가상 스레드 (요청당 생성)
스레드 생성 시점서버 시작 때 200개 만들고 끝톰캣이 요청마다 새로 생성
복사 발생 횟수시작 때 200번뿐요청 수만큼 (부모에 값이 있는 한)
요청 컨텍스트 상속무용지물 — 스레드가 요청보다 먼저 태어나 물려받을 게 없음생성 시점의 부모 값이 상속됨

풀 모델에서는 복사가 시작 때 200번으로 끝나지만, 그 200번이 물려받는 건 풀을 만든 스레드(main 등)의 값이라 요청 컨텍스트 전달용으론 애초에 쓸모가 없었다(그래서 풀 시대의 프레임워크는 상속 대신 요청마다 직접 set/remove하는 방식을 썼다). 가상 스레드 모델에서는 내 코드가 가상 스레드를 안 만들어도 톰캣이 요청마다 만들기 때문에, 부모에 inheritable 값이 있는 한 복사가 요청마다 일어난다. 판단 기준은 "내가 만들었나"가 아니라 "요청마다 새 스레드가 태어나는 모델인가"다.

7-4. 후속 — ScopedValue (Java 25 정식)

이 문제들 때문에 Loom 팀이 ThreadLocal의 후속으로 만든 게 ScopedValue다:

✕ BEFOREThreadLocal — 언제든 set 가능, 수명이 스레드와 같음
ThreadLocal<User> USER = new ThreadLocal<>();
USER.set(user);            // 아무 데서나 변경 가능, remove() 안 하면 계속 남음
✓ AFTERScopedValue — 불변 + 코드 블록 범위로 수명 한정
static final ScopedValue<User> USER = ScopedValue.newInstance();
ScopedValue.where(USER, user).run(() -> {
    handleRequest();       // 이 블록 안에서만 USER.get() 가능
});                        // 블록 끝나면 자동으로 사라짐 — remove 누락 사고 원천 차단

값이 불변이라 상속도 복사가 아니라 참조 공유로 끝난다 — StructuredTaskScope로 만든 하위 작업이 부모의 ScopedValue를 공짜로 물려받는다. 수백만 스레드 규모를 전제로 설계된 대체재다.

8

그 외 도입 체크포인트

▾
  • 풀링 금지: 가상 스레드는 일회용이다. 풀에 넣어 재사용하면 이점이 사라진다. 개수 제한이 목적이면 스레드 풀 대신 Semaphore를 쓴다.
  • ThreadLocal 점검: 동작은 안전하지만 스레드당 캐싱 패턴은 메모리 폭탄이 된다(7절).
  • CPU 바운드 작업엔 무의미: 이득은 오직 I/O 대기가 많은 워크로드에서 나온다.
✅ 한 줄 요약
  • Virtual Thread: OS 스레드와의 1:1 매핑을 끊고, 블로킹 시 JVM이 스레드를 캐리어에서 떼어내 "대기가 OS 스레드를 낭비하지 않게" 만든 경량 스레드 — 블로킹 스타일 코드 그대로 리액티브급 동시성을 얻는다.
  • 원리: 스레드란 "콜 스택 + 실행 위치"라는 데이터다. 과거의 장벽은 메모리 소유가 아니라 "커널 안에서 잠들면 개입 타이밍이 없다"는 것 — 그래서 가상 스레드는 블로킹 콜에 아예 들어가지 않고, JDK가 소유한 시스템 콜 직전 경로에서 "epoll 등록 + 아직 깨어 있는 스레드가 스스로 자기 스택을 힙에 복사(freeze)하고 물러나기"로 바꿔치기했다. 내리는 건 본인, 올리는 건 캐리어, 깨우는 건 poller — 캐리어는 평범한 OS 스레드일 뿐, 마법은 Continuation이다.
  • 역사: 이 아이디어는 초기 자바의 그린 스레드로 존재했지만 멀티코어 활용 불가·블로킹 콜 전체 마비·미성숙한 논블로킹 I/O 때문에 버려졌고, epoll/NIO·M:N 스케줄러·JVM 기술이 쌓이고 I/O 대기형 워크로드가 폭증한 지금에야 실패 원인이 모두 해소된 형태로 부활했다.
  • pinning: JVM이 경로를 소유하지 못한 지점 — 구조를 몰라 얼릴 수 없는 JNI 프레임, OS 스레드에 잠금이 결부된 synchronized(Java 24에서 해소) — 에서 블로킹하면 캐리어에 못박혀 시스템 전체가 멈출 수 있다. 블로킹 구간의 synchronized를 ReentrantLock으로 바꾸고 JFR로 핀 이벤트를 감시한다.
  • @Transactional + 외부 API 콜: 가상 스레드는 "대기가 스레드를 낭비하는 문제"만 풀지 "대기가 DB 커넥션을 낭비하는 문제"는 못 푼다. 동시성이 폭증한 만큼 커넥션 풀 고갈로 더 크게 터진다 — 어느 쪽이든 외부 콜은 트랜잭션 밖으로 빼는 게 답이다.
  • ThreadLocal: 값이 캐리어가 아니라 힙의 가상 스레드 객체에 붙어 캐리어를 갈아타도 따라다니므로 동작은 안전하다. 깨지는 건 "스레드가 적고 오래 산다"를 전제한 스레드당 캐싱 패턴 — 수백만 개 일회용 환경에선 캐시 이득 0, 메모리만 폭증. InheritableThreadLocal 복사의 트리거는 요청이 아니라 스레드 생성이라, 요청당 생성 모델에선 요청마다 일어난다. 후속은 불변·블록 범위의 ScopedValue(Java 25).
