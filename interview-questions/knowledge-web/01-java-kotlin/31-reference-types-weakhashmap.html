약한 것은 객체가 아니라 화살표다
GC는 "도달 가능하면 살린다" 규칙 하나로만 움직인다. 참조 강도는 그 규칙밖에 없는 GC에게 "이건 버려도 된다"고 말하는 유일한 수단이고, WeakHashMap은 그 수단을 키에만 적용한 맵이다.

면접 질문: "Strong/Soft/Weak 참조의 차이는? WeakHashMap은 어떤 용도에 쓰나요?"

핵심 관전 포인트 — GC는 "GC 루트에서 도달 가능하면 살린다"는 규칙 하나로 움직이는데, 그 규칙만으로는 개발자가 GC에게 의사를 전달할 방법이 없다. "메모리가 부족하면 이건 버려도 좋다", "내가 붙잡고 있다는 사실이 이 객체를 살리는 근거가 되면 안 된다"는 요구를 표현할 수단이 필요해서 Java 1.2에 참조 강도가 들어왔다. 네 등급은 전부 "GC가 언제 회수하는가" 하나의 축 위에 있다 — Strong은 도달 가능한 한 절대 회수되지 않고, Soft는 도달 가능해도 메모리가 부족해지면 OOM 대신 먼저 버려지고, Weak는 약한 참조만 남는 순간 다음 GC에 회수되고, Phantom은 회수가 확정된 뒤 정리 훅을 실행하기 위해서만 존재한다. 여기서 중요한 건 강도가 객체의 성질이 아니라 그 객체를 가리키는 참조의 성질이라는 점이다 — 같은 객체를 strong 하나와 weak 하나가 동시에 가리키면 strong이 이긴다. WeakHashMap은 Entry가 WeakReference를 상속해 키만 약하게 잡고 값은 강하게 잡는 맵이라, 키를 아무도 안 쓰게 되면 엔트리가 알아서 사라진다. 대신 함정이 둘 있다 — 값이 자기 키를 참조하면 엔트리는 영원히 죽지 않고, String 리터럴이나 −128~127 Integer를 키로 쓰면 풀과 박싱 캐시가 강하게 붙들고 있어 절대 회수되지 않는다. 그리고 엔트리는 GC 순간이 아니라 그 다음에 맵의 메서드가 호출될 때 expungeStaleEntries()로 정리된다.

    네 등급은 하나의 축입니다. GC는 도달 가능성만 보므로 "산다/죽는다" 두 단계밖에 표현하지 못합니다. 그 사이를 채우려고 만든 것이 참조 강도이고, 축은 "언제 회수되는가" 하나입니다 — Strong은 OOM이 나도 유지, Soft는 OOM 직전에 반드시 정리, Weak는 다음 GC에 즉시 회수, Phantom은 회수가 확정된 뒤 정리 훅용입니다.
  • 2
    강도는 객체가 아니라 화살표의 성질입니다. 한 객체에 여러 화살표가 닿을 수 있고, GC는 그중 가장 강한 경로로 판정합니다. 그래서 강한 참조가 하나라도 남아 있으면 약한 참조를 아무리 만들어도 회수되지 않습니다. 약한 참조는 강한 참조가 전부 사라진 순간에 비로소 의미를 갖습니다.
  • 3
    WeakHashMap은 Entry가 WeakReference를 상속해 키만 약하게 잡습니다. 그래서 원본 객체에 부가 정보를 붙이되 그 부가 정보가 원본을 살리면 안 되는 자리(수정 불가능한 객체의 메타데이터, 클래스로더 단위 캐시)에 씁니다. 다만 값이 자기 키를 참조하면 무력화되고, 리터럴·박싱 캐시를 키로 쓰면 애초에 회수되지 않으며, 정리는 GC가 아니라 다음에 맵을 건드릴 때 일어나므로 size()는 스냅샷일 뿐입니다. 이 도구는 생명주기 연동용이지 캐시가 아닙니다.

0. 질문 + 출제 의도 · 겨냥하는 약점

질문 — "Strong/Soft/Weak 참조의 차이는? WeakHashMap은 어떤 용도에 쓰나요?"

출제 의도 — 로컬 캐시·리스너 보관 자료구조에서 메모리 누수를 만들지 않는 도구(WeakHashMap 등)의 기반 지식이다. GC와 참조의 상호작용까지 아는 깊이의 표본으로, 힙에 오래 남는 자료구조를 설계할 때 생명주기를 의식하는 사람인지를 본다.

약점 A등급을 네 개의 독립된 항목으로 외운다 — "Soft는 메모리 부족할 때, Weak는 바로"에서 멈추면 왜 그런 등급이 필요했는지를 설명하지 못한다. 네 등급은 "언제 회수하는가" 하나의 축 위에서 회수 시점을 앞으로 당긴 순서다(3절).
약점 B"이 객체는 weak 객체다"라고 말한다 — 강도는 객체가 아니라 화살표(참조)의 성질이다. 이 전제가 없으면 "WeakHashMap을 썼는데 안 지워져요"류의 문제를 하나도 설명하지 못한다(4절).
약점 CWeakHashMap을 캐시라고 답한다 — 가장 흔한 오답이다. 캐시가 값을 들고 있어야 할 바로 그 구간에 WeakHashMap은 항목을 버린다. 히트율이 0에 수렴하는 구조다(14절 · 꼬리질문 3).
약점 D값도 약하게 잡힌다고 생각한다 — 키만 약하다. 그래서 값이 자기 키를 참조하는 순간 약한 참조가 통째로 무력화된다(9·10절).
약점 E정리 시점을 "GC 순간"이라고 답한다 — GC는 ReferenceQueue에 넣기까지만 한다. 테이블에서 실제로 떼어내는 것은 그 다음에 맵의 메서드가 호출될 때 도는 expungeStaleEntries()다(12절).
합격선"참조 강도는 도달 가능성 규칙 하나뿐인 GC에게 의사를 전달하는 유일한 수단이고, 네 등급은 회수 시점 하나의 축 위에 있습니다. Strong은 OOM이 나도 유지, Soft는 OOM 직전에 반드시 정리, Weak는 약한 참조만 남으면 다음 GC에 회수, Phantom은 회수 확정 후 정리 훅용입니다. 강도는 객체가 아니라 화살표의 성질이라 강한 경로가 하나라도 있으면 그것이 이깁니다. WeakHashMap은 Entry가 WeakReference를 상속해 키만 약하게 잡는 맵이라, 수정할 수 없는 객체에 부가 정보를 붙이거나 클래스로더 단위 캐시를 만들 때 씁니다. 다만 값이 자기 키를 참조하면 무력화되고, 정리는 GC가 아니라 다음에 맵을 건드릴 때 일어나므로 size()는 스냅샷입니다. 캐시 용도로는 부적합합니다."
이 문서를 관통하는 두 문장 ① 약한 것은 객체가 아니라 화살표다 — 그래서 가장 강한 경로가 이긴다. ② 참조 강도는 생명주기를 연동하는 도구이지 캐시 정책 도구가 아니다 — 그래서 WeakHashMap은 "누가 아직 이걸 쓰고 있는가"에는 답하지만 "나중에 또 쓸 것인가"에는 답하지 못한다. 이 문서의 모든 절은 이 두 문장을 확장한 것이다.

1. 전제 — 도달 가능성 규칙의 표현력은 두 단계뿐이다

GC의 판정 규칙은 하나다. GC 루트(스레드 스택의 지역변수, static 필드처럼 힙 바깥에서 힙 안을 가리키는 참조들)에서 출발해 참조를 따라가며 닿는 객체에 "살아있음" 표시(mark)를 남기고, 끝내 닿지 않은 객체를 회수한다. 이것이 도달 가능성(reachability) 판정이다.

이 규칙은 정확하지만 표현력이 딱 두 단계뿐이다. 참조가 있으면 산다, 없으면 죽는다. 그 사이가 없다. 그런데 실무에는 그 사이에 놓이는 요구가 분명히 존재한다.

참조 강도가 존재하는 이유 — 한 문장

강한 참조로는 "내가 붙잡고 있다는 사실을 살릴 근거로 세지 말라"는 말을 할 수 없다. 그 말을 할 수 있게 만든 것이 Java 1.2의 java.lang.ref다.

2. 해법 — 참조를 "상자"로 만들어 한 단계를 거친다

Java 1.2에서 java.lang.ref 패키지가 들어왔다. 참조를 객체를 감싼 상자로 만들어서, 상자의 종류로 GC에게 "이 객체를 얼마나 붙잡아 달라고 부탁하는지"를 전달한다. 이 부탁의 세기가 참조 강도(reference strength)다.

// 지금까지 써온 방식 — 변수가 객체를 직접 가리킨다. 이게 강한 참조다.
byte[] thumbnail = loadThumbnail(id);

// 상자에 넣어 가리키는 방식 — 상자의 종류가 곧 부탁의 세기다.
SoftReference<byte[]> boxed = new SoftReference<>(loadThumbnail(id));
byte[] thumbnail = boxed.get();   // 꺼낼 때는 get(). 이미 회수됐으면 null이 나온다.

핵심 차이는 한 단계를 거친다는 것이다. boxed라는 변수는 상자를 강하게 가리키고, 상자가 안의 배열을 약하게(soft하게) 가리킨다. GC는 이 상자를 특별 취급해서, 안쪽 화살표를 "살려야 할 근거"로 세지 않는다.

여기서 오해가 하나 생긴다 "약한 참조를 만들었으니 이 객체는 약해졌다"가 아니다. 상자를 하나 더 만들었을 뿐이고, 원래 있던 강한 참조는 그대로 살아 있다. 다음 절이 이 이야기다.

3. 네 등급 — 전부 "GC가 언제 회수하는가" 하나의 축이다

등급이 네 개라고 하면 네 개를 따로 외워야 할 것 같지만 그렇지 않다. 전부 "GC가 이 객체를 회수해도 되는 시점이 언제인가"라는 하나의 축 위에서 회수 시점을 앞으로 당긴 순서다.

4. 가장 자주 어긋나는 지점 — 강도는 객체가 아니라 "화살표"의 성질이다

"이 객체는 weak 객체다" 같은 말은 성립하지 않는다. 약한 것은 객체가 아니라 화살표다.

한 객체를 여러 화살표가 동시에 가리킬 수 있고, 그중 종류가 섞여 있을 수 있다. 이때 GC의 판정 기준은 "그 객체에 닿는 경로 중 가장 강한 것"이다. 강한 경로가 하나라도 있으면 그 객체는 강하게 도달 가능하고, 그러면 다른 화살표가 아무리 약해도 회수되지 않는다.

한 객체의 운명은 그 객체에 닿는 모든 경로 중 가장 강한 것이 정한다 
Object shared = new Object();                                    // 강한 참조 하나
WeakReference<Object> weakOnShared = new WeakReference<>(shared);  // 약한 참조 하나, 같은 객체

System.gc();
System.out.println(weakOnShared.get() != null);   // true — 강한 참조가 이긴다

shared = null;                                     // 강한 참조를 끊는다
System.gc();
System.out.println(weakOnShared.get() == null);   // true — 이제 약한 참조만 남았으므로 회수됐다

등급의 정의 자체가 "위 등급에 해당하지 않을 때"를 전제로 쌓여 있다는 점을 보면 "가장 강한 경로가 이긴다"가 규칙이 아니라 정의임을 알 수 있다. 그래서 weak 참조를 아무리 많이 만들어도 강한 참조 하나를 이기지 못한다.

System.gc()에 대한 단서 System.gc()는 "GC를 지금 돌려 달라"는 힌트일 뿐 보장이 아니다. JVM은 무시할 수 있고 -XX:+DisableExplicitGC가 켜져 있으면 실제로 무시한다. 이 문서의 모든 실측 결과는 "이 환경(OpenJDK 21)에서 이렇게 관측됐다"는 뜻이지 명세의 보장이 아니다. 학습·실험용 코드이지 프로덕션 코드가 아니다.

5. 쓰는 쪽이 지켜야 하는 계약 — get()은 언제든 null이다

참조 강도를 쓰기로 했다면 사용하는 쪽 코드가 반드시 달라져야 한다. get()은 언제든 null을 돌려줄 수 있다. 심지어 if (ref.get() != null)로 검사한 직후에도, 그 사이에 GC가 돌면 다음 get()은 null일 수 있다.

문제검사와 사용 사이에 GC가 끼어든다
if (soft.get() != null) {
    process(soft.get());   // 여기서 null이 들어갈 수 있다
}

// 왜 위험한가:
// get()이 돌려준 값을 어떤 변수에도 담지 않았으므로
// 이 두 줄 사이에는 강한 참조가 존재하지 않는다.
// 그 틈에 GC가 돌면 referent가 지워진다.
개선지역 변수로 꺼내 강하게 고정한다
byte[] cached = soft.get();   // 이 순간 강한 참조가 된다
                              // 이 변수가 살아 있는 한 회수되지 않는다
if (cached == null) {
    cached = loadExpensiveData();          // 회수됐으면 재생성
    soft = new SoftReference<>(cached);
}
process(cached);              // 이제 null일 수 없다

개선 코드의 핵심은 byte[] cached = soft.get() 한 줄이다. 이 대입으로 지역 변수라는 강한 참조가 생기므로, 그 뒤로는 4절의 규칙에 따라 회수되지 않는다.

Soft/Weak를 다루는 코드의 기본형 — 이 세 단계 외의 형태는 전부 의심한다

① 꺼낸다
T v = ref.get() — 딱 한 번만 호출한다
② 고정한다
지역 변수에 담긴 순간 강한 참조가 되어 안전해진다
③ null이면 재생성
없으면 다시 만들고 상자를 새로 만들어 넣는다
꺼내서 강하게 고정하고, null이면 재생성한다
여기서 따라오는 설계 제약 재생성이 가능한 데이터에만 쓸 수 있다. 다시 만들 수 없는 유일한 데이터를 soft/weak로 들고 있다가 회수되면 복구할 방법이 없다. "메모리를 아끼려고" 참조 강도를 낮추기 전에, 이 데이터를 언제든 다시 만들 수 있는가를 먼저 답해야 한다.

6. Soft — "죽는 실패"를 "느려지는 실패"로 바꾼다

6-1. 강한 참조 캐시는 줄어드는 경로가 없다

문제강한 참조 캐시 — 캐시가 힙을 다 먹고 OOM
public class ThumbnailCache {
    private final Map<Long, byte[]> cache = new HashMap<>();

    public byte[] get(long imageId) {
        // 넣은 배열은 강한 참조로 맵에 붙잡힌다.
        // 이미지 종류가 늘수록 맵은 단조 증가하고,
        // 줄어드는 경로가 하나도 없다.
        return cache.computeIfAbsent(imageId, this::render);
    }
}
개선soft 참조 캐시 — 힙이 부족하면 JVM이 먼저 비운다
public class ThumbnailCache {
    private final Map<Long, SoftReference<byte[]>> cache = new HashMap<>();

    public byte[] get(long imageId) {
        SoftReference<byte[]> ref = cache.get(imageId);
        byte[] data = (ref == null) ? null : ref.get();  // 회수됐으면 null
        if (data == null) {                       // 없거나 회수됐으면 재생성
            data = render(imageId);
            cache.put(imageId, new SoftReference<>(data));
        }
        return data;
    }
}

강한 참조 캐시의 문제는 "느리다"가 아니라 "줄어드는 경로가 없다"는 것이다. 힙이 꽉 차도 GC는 이 배열들을 회수할 수 없다 — 맵이 강하게 잡고 있으니 도달 가능하고, 도달 가능하면 살려야 하기 때문이다. 결국 OutOfMemoryError: Java heap space로 프로세스가 죽는다. 캐시 때문에 서비스가 죽는 것이 강한 참조 캐시의 전형적 실패다.

강한 참조 캐시
힙이 부족하면 OOM으로 프로세스가 죽는다
→
soft 참조 캐시
힙이 부족하면 캐시 미스가 늘어 느려질 뿐이다

6-3. 그럼에도 실무 로컬 캐시를 SoftReference로 만들지 않는 이유

이유는 성능이 아니라 예측 가능성이다.

이유 1
언제 비워질지 모른다
판단식이 남은 힙 크기에 좌우되므로 같은 코드가 트래픽 패턴에 따라 히트율이 요동친다. 히트율이 재현되지 않으면 성능 회귀를 추적할 수 없다.
이유 2
비워지는 단위를 고를 수 없다
GC는 "덜 중요한 항목"을 모른다. 방금 만든 비싼 항목과 거의 안 쓰이는 항목을 구분하지 않는다.
이유 3
GC 부담이 늘어난다
soft 참조는 회수 판정을 GC가 매번 다시 해야 하는 대상이라 수가 많아지면 GC 시간이 늘어난다. Old로 승격된 soft 참조는 Full GC를 유발하는 쪽으로 작용한다.
실무 기본형비워지는 조건을 코드가 정한다
Cache<Long, byte[]> cache = Caffeine.newBuilder()
        .maximumSize(5_000)                       // 개수 상한이 곧 메모리 상한의 근거가 된다
        .expireAfterWrite(Duration.ofMinutes(10))  // 신선도 요구를 시간으로 표현한다
        .recordStats()                             // 히트율을 지표로 뽑아 튜닝 근거로 삼는다
        .build();
SoftReference는 "OOM 방어의 마지막 안전판"으로는 의미가 있지만 "캐시 정책"으로는 부족하다 — 캐시를 비우는 기준은 메모리 압박이 아니라 사용 패턴이어야 하기 때문이다

7. Weak — 부가 정보를 곁들이되, 그 정보 때문에 원본이 살아 있으면 안 될 때

Weak가 필요한 상황은 캐시와 성격이 다르다. 어떤 객체에 곁다리 정보를 붙여두고 싶은데, 그 객체의 클래스를 내가 수정할 수 없을 때 생긴다.

예를 들어 외부 라이브러리가 주는 Connection 객체마다 "이 커넥션을 언제 빌려 갔는지"를 기록해 두고 싶다고 하자. Connection 클래스에 필드를 추가할 수는 없으니 바깥에 맵을 하나 둔다.

문제강한 참조 맵에 부가 정보를 붙인다
public class LeaseTracker {
    private static final Map<Connection, Instant> leasedAt = new HashMap<>();

    public static void onBorrow(Connection c) {
        leasedAt.put(c, Instant.now());
    }
    // onReturn 을 호출해 remove 하는 것을 한 번이라도 빠뜨리면,
    // static 맵은 GC 루트이므로 그 Connection 은 영원히 회수되지 않는다.
}
개선키를 약하게 잡는 맵
private static final Map<Connection, Instant> leasedAt =
        Collections.synchronizedMap(new WeakHashMap<>());

// 원본(Connection)이 죽으면 기록도 함께 사라진다.
// remove 를 빠뜨려도 원본의 수명이 추적기에 묶이지 않는다.
// (동기화가 필요한 이유는 15절)

문제 코드가 만드는 것은 전형적인 누수 형태다 — "실수로 참조를 놓치는 누수는 없고, 실수로 참조를 붙잡는 누수는 있다." 부가 정보를 붙였을 뿐인데 원본의 수명이 추적기의 수명에 묶여 버렸다.

weak는 "언젠가 다시 쓸 것"을 담는 용도가 아니다 weak 참조만 남으면 다음 GC에 바로 사라지므로, "지금은 안 쓰지만 나중에 필요할 것"을 담아 두면 그냥 없어진다.
Weak가 답하는 질문은 "누가 아직 이걸 쓰고 있는가"이지 "나중에 필요한가"가 아니다

8. Phantom — finalize()가 폐기된 자리 가산점

Phantom을 이해하려면 먼저 "객체가 회수될 때 뒷정리를 실행하고 싶다"는 요구가 왜 생기는지를 봐야 한다. Java 객체 중에는 힙 바깥의 자원을 대표하는 것들이 있다 — 파일 디스크립터, 소켓, 네이티브 메모리(DirectByteBuffer가 잡는 오프힙 버퍼). GC는 힙만 관리하므로 자바 객체가 회수돼도 그 객체가 붙잡고 있던 OS 자원은 자동으로 풀리지 않는다.

Java가 처음 내놓은 답이 Object.finalize()였고, 결함이 심해 결국 폐기됐다. 이유가 셋이다.

결함 1
객체를 되살릴 수 있다
finalize() 안에서 this를 static 필드에 대입하면 GC가 "죽었다"고 판정한 객체가 살아 돌아온다. 애플리케이션 코드가 GC의 판정을 뒤집는다는 뜻이고, 이것만으로 GC 알고리즘의 전제가 무너진다.
결함 2
실행 시점이 보장되지 않는다
별도 finalizer 스레드가 큐에서 꺼내 실행하는데 언제 스케줄될지 알 수 없다. 프로세스가 끝날 때까지 한 번도 안 불릴 수도 있다 — 파일 디스크립터가 고갈된 뒤에야 정리가 도는 상황.
결함 3
회수가 최소 두 사이클
GC가 처음 만나면 회수하지 못하고 큐에 등록만 하고 지나간다. 실제 회수는 finalize 실행 후 다음 GC다. 게다가 finalize() 안의 예외는 조용히 무시돼 정리가 안 된 채로 넘어간다.
public class Res {
    static Res zombie;
    @Override protected void finalize() { zombie = this; }   // 회수 직전에 자기 자신을 되살린다
    public static void main(String[] a) throws Exception {
        new Res();                     // 아무도 참조하지 않는 객체
        System.gc(); Thread.sleep(300);
        System.out.println(zombie != null);
    }
}
실행 결과
true // 죽었다고 판정된 객체가 살아 돌아왔다
대체재는 두 겹이다 — 순서를 틀리면 안 된다 첫째, 대부분의 정답은 try-with-resources다. 자원 해제를 GC에 맡기지 않고 코드가 명시적으로, 정해진 시점에 한다. 둘째, 안전망이 필요하면 Cleaner(Java 9+)를 쓴다. GC 기반 정리는 "혹시 개발자가 빠뜨렸을 때의 안전망"이지 1차 수단이 아니다.
기본형Cleaner — 정리 작업은 반드시 static 클래스로
public class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();

    // 정리 작업은 반드시 static 클래스여야 한다.
    // 내부 클래스로 만들면 바깥 인스턴스(NativeBuffer)를 암묵적으로 참조하게 되고,
    // 그러면 정리 대상이 강하게 도달 가능해져 영원히 정리가 돌지 않는다.
    private static class ReleaseTask implements Runnable {
        private final long address;        // 해제에 필요한 값만 복사해 든다
        ReleaseTask(long address) { this.address = address; }
        @Override public void run() { freeNative(address); }
    }

    private final Cleaner.Cleanable cleanable;

    public NativeBuffer(long size) {
        long address = allocateNative(size);
        this.cleanable = CLEANER.register(this, new ReleaseTask(address));
    }

    @Override public void close() {
        cleanable.clean();   // 1차 수단: 명시적 해제. 여러 번 불러도 한 번만 실행된다.
    }
}

실무에서 가장 자주 밟는 지점

CLEANER.register(this, task)에서 task가 this를 참조하면 this가 영원히 강하게 도달 가능해져서 정리가 절대 실행되지 않는다. 람다로 쓰면 캡처가 눈에 잘 안 보이고, 비-static 내부 클래스는 컴파일러가 바깥 인스턴스 참조를 보이지 않는 필드로 넣어 준다.

정리 작업은 해제에 필요한 원시 값만 복사해 들고 있어야 한다

수단실행 시점객체 부활지위

9. WeakHashMap — Entry가 WeakReference를 상속한다

9-1. 일반 HashMap이 만드는 누수

HashMap은 키와 값을 둘 다 강한 참조로 들고 있다. 그래서 맵에 넣는 순간 그 객체의 수명은 맵의 수명에 묶인다.

문제맵이 살아 있는 한 키도 값도 회수되지 않는다
Map<User, Session> sessions = new HashMap<>();

User user = new User("kim");
sessions.put(user, new Session(user));

user = null;   // 바깥에서 참조를 끊어도

// sessions -> Entry -> key(User) 라는 강한 사슬이 남는다.
// sessions 가 static 필드나 싱글톤 빈이면
// 이 사슬은 애플리케이션이 사는 내내 유지된다.
개선키를 아무도 안 쓰게 되면 엔트리가 사라진다

User user = new User("kim");
sessions.put(user, someSession);

Object k2 = new Object();

System.out.println(m.size());   // 2

    }
}

Entry가 WeakReference를 상속한다는 것이 전부다. WeakReference가 물려주는 referent 자리에 키를 넣고, 값은 평범한 value 필드로 들고 있다. 그리고 생성자에 ReferenceQueue를 함께 넘긴다는 점도 눈여겨봐 두자(12절의 출발점이다).

같은 설계를 이미 본 적이 있다 ThreadLocalMap의 Entry가 정확히 같은 구조다 — 키(ThreadLocal 인스턴스)만 약하게, 값은 강하게. 같은 설계에서 같은 종류의 문제가 나오므로, 한쪽을 이해하면 다른 쪽도 같이 이해된다. 차이는 누가 맵을 붙잡고 있느냐인데, 이는 꼬리질문에서 다룬다.

10. 함정 ① — 값이 자기 키를 참조하면 엔트리는 영원히 죽지 않는다 함정

Map<User, Session> sessions = new WeakHashMap<>();

값이 키에 닿는 것을 구조적으로 막는 방법은 하나뿐 — 값을 원시 값이나 불변 DTO로 좁힌다

12. 엔트리는 정확히 언제 사라지나 — ReferenceQueue와 expungeStaleEntries()

"키가 회수되면 엔트리도 사라진다"는 문장은 결과만 맞고 시점이 틀렸다. 정확한 순서를 알아야 size()가 이상하게 보이는 상황을 설명할 수 있다.

먼저 ReferenceQueue가 무엇인지

ReferenceQueue는 "당신이 감싸 둔 객체가 방금 회수됐습니다"라는 통지를 받는 우편함이다. 참조 상자를 만들 때 큐를 함께 넘겨 두면, GC가 그 객체를 회수하면서 참조 상자 자체를 그 큐에 넣어 준다. 그러면 우리는 큐를 폴링해서 "회수된 상자들"을 꺼내 뒷정리를 할 수 있다. 우편함에 편지가 오는 것이지, 우체부가 우리 집 청소까지 해 주지는 않는다 — 이것이 다음 문단의 핵심이다.

WeakHashMap은 내부에 이 큐를 하나 갖고 있고(private final ReferenceQueue<Object> queue), 모든 Entry를 이 큐에 등록해 만든다. 그리고 큐를 비우며 죽은 엔트리를 테이블에서 떼어내는 메서드가 expungeStaleEntries()다. expunge는 "지워 없애다", stale entry는 "키가 이미 null이 된 낡은 항목"을 뜻한다.

문제는 이 메서드가 GC에 의해 호출되지 않는다는 것이다 — GC는 큐에 넣기까지만 한다

12-1. 리플렉션으로 t2 상태를 직접 관측한다

이걸 실제로 관측하려면 맵의 어떤 public 메서드도 호출하지 않고 내부 상태를 봐야 한다 — size()를 부르는 순간 t3가 일어나 버리기 때문이다. 리플렉션으로 table과 size 필드를 직접 읽어 확인한 결과다.

F1 GC 직후, 맵 메서드 호출 전 raw table 상태 = 테이블에 남은 Entry 2개(그중 키가 이미 null인 것 1개), size 필드 = 2 F2 size() 호출 = 1 F3 size() 이후 raw table 상태 = 테이블에 남은 Entry 1개(그중 키가 이미 null인 것 0개), size 필드 = 1

F1이 t2 상태다. GC는 이미 끝났고 키도 null이 됐는데 엔트리는 테이블에 그대로 있고 size 필드도 2다. F2에서 size()를 부르는 순간 정리가 일어나 1이 되고, F3에서 테이블에서도 실제로 사라졌음이 확인된다.

여기서 나오는 두 가지 실무적 결론

① 아무도 맵을 건드리지 않으면 정리도 안 된다
"만들어 두고 가끔만 조회하는" WeakHashMap은 키가 죽은 뒤에도 상당 기간 엔트리와 값 객체를 힙에 붙잡고 있을 수 있다. 값이 무거우면 이것 자체가 누수처럼 보인다.
② size()는 스냅샷이다
JDK 소스의 size() 주석도 그렇게 말한다 — "This result is a snapshot." 아무것도 넣거나 빼지 않았는데 두 번 부른 size()가 다를 수 있다. 용량 제한·검증 같은 단정적 판단에 쓰면 안 된다.

참고로 isEmpty()는 내부적으로 size() == 0을 호출하므로 정리를 유발한다. 반대로 정리 없이 즉시 답하는 메서드는 없다고 보면 된다 — getTable()을 거치는 거의 모든 조회·수정 메서드가 첫 줄에서 expungeStaleEntries()를 부른다.

13. 찾는 것은 equals, 살려두는 것은 인스턴스

또 하나 자주 어긋나는 지점이다. WeakHashMap은 키를 equals/hashCode로 찾는다. 참조 동일성(==)으로 찾는 것이 아니다 — 그건 IdentityHashMap이다. 그런데 엔트리를 살려두는 판정은 equals가 아니라 "맵에 저장된 그 키 인스턴스가 도달 가능한가"로 한다.

Map<String, String> em = new WeakHashMap<>();
String stored = new String("주문-42");
em.put(stored, "값");

String lookup = new String("주문-42");        // 내용은 같지만 다른 인스턴스
System.out.println(stored == lookup);         // false
System.out.println(em.get(lookup));           // "값"  <- equals 로 찾으므로 조회된다

stored = null;                                 // 맵에 "저장된" 인스턴스만 참조를 끊는다
System.gc(); Thread.sleep(200);

System.out.println(em.size());                 // 0
System.out.println(em.get(lookup));            // null  <- lookup 은 멀쩡히 살아 있는데도
적합한 키 — 인스턴스 자체가 도메인에서 의미를 갖는다
  • 커넥션 객체 — "그 커넥션 하나"가 곧 대상
  • 클래스로더 · Class 객체 — 인스턴스가 곧 식별자
  • 세션 객체 · 컴포넌트 인스턴스
부적합한 키 — 값이 같으면 같은 것으로 취급되고 매번 새로 만들어진다
  • 주문번호 문자열 — 요청마다 새 인스턴스
  • 사용자 id (Long·String) — 역직렬화마다 새 객체
  • 결과: 조회는 되는데 언제 사라질지 모르는 자료구조

가산점 — Guava·Caffeine의 weakKeys()는 의도적으로 다르게 동작한다

이들은 키 비교를 동일성(==)으로 한다. 이유는 일관성이다 — 약한 키의 수명은 인스턴스 단위로 결정되는데 조회는 equals 단위로 한다면, 방금 get으로 찾아지던 키가 다음 순간 사라지는 혼란이 그대로 남는다. 그래서 아예 조회 기준까지 인스턴스로 맞췄다.

WeakHashMap → Guava/Caffeine 마이그레이션은 컴파일 에러 없이 조용히 동작이 바뀌는 지점이다

쓰는 자리 1

프레임워크가 Map<ClassLoader, …>나 Map<Class<?>, …>로 메타데이터를 캐싱할 때, 강한 참조로 잡으면 재배포해도 옛 클래스로더가 회수되지 않아 Metaspace 누수가 난다(톰캣에 war를 반복 배포할 때의 전형). 키를 약하게 잡으면 클래스로더가 언로드될 때 캐시도 함께 사라진다.
쓰는 자리 3
리스너/콜백 레지스트리 — 조건부
"해제를 깜빡해도 안전하다"가 아니라 반대로 터진다 — 리스너를 붙잡는 다른 강한 참조가 없으면 등록하자마자 다음 GC에 증발한다. 게다가 캡처 람다는 사라지고 비캡처 람다는 남아 결과가 뒤집힌다.
성립 조건: 리스너의 수명을 대신 책임지는 소유자가 반드시 있어야 한다(꼬리질문 10).
쓰지 않는 자리 — 일반적인 캐시
  • WeakHashMap은 "지금 쓰고 있는가"에는 답하지만 "나중에 또 쓸 것인가"에는 답하지 못한다.
  • 캐시가 값을 들고 있어야 할 바로 그 구간(아무도 안 쓰는 구간)에 항목을 버린다 → 히트율 0에 수렴
  • 대안: Caffeine의 maximumSize · expireAfterWrite · recordStats
쓰지 않는 자리 — 값이 무겁고 맵을 자주 안 건드리는 경우
  • 정리는 맵의 메서드가 호출될 때만 돈다(12절)
  • 키가 죽어도 엔트리와 값 객체가 통째로 힙에 남아 누수처럼 보인다
  • 대안: 명시적 remove() 또는 값에 가벼운 DTO만 담기
WeakHashMap은 생명주기 연동 도구이지 캐시 정책 도구가 아니다

카드 1 — 네 등급 (회수 시점 한 축)

  • "WeakHashMap은 Entry가 WeakReference를 상속해 키만 약하게 잡고, 값은 평범한 필드로 강하게 잡습니다."
  • "정리는 GC가 하는 게 아니라 다음에 맵을 건드릴 때 expungeStaleEntries()가 합니다. 그래서 size()는 스냅샷입니다."
  • "참조 강도는 생명주기 연동 도구이지 캐시 정책 도구가 아닙니다. 캐시는 '지금 누가 쓰는가'가 아니라 '또 쓸 확률이 얼마인가'로 비워야 합니다."
  • "SoftReference는 '죽는 실패'를 '느려지는 실패'로 바꾸는 안전판이지, 캐시 정책으로는 예측 가능성이 부족합니다."

17. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 답을 눈으로 읽는 것은 인출 연습이 아니다.

WeakHashMap은 값도 weak인가요?핵심이 질문에 "네"라고 답하면 나머지 답이 전부 어긋난다

아니다. 키만 약한 참조이고 값은 강한 참조다. Entry가 WeakReference를 상속해서 물려받은 referent 자리에 키를 넣고, 값은 평범한 value 필드로 들고 있기 때문이다(9절).

그래서 값이 자기 키를 참조하면 약한 참조가 무력화된다. 루트 → 맵 → Entry → value → key라는 강한 경로가 생겨 키가 강하게 도달 가능해지고, 키가 안 죽으니 엔트리도 안 죽는다(10절). 실측으로도 확인된다 — 값이 키를 잡는 맵은 GC 후에도 size()가 1이고, 안 잡는 맵은 0이 된다.

값 객체가 간접적으로 키에 닿는 경우가 더 위험하다. Session → Order → Customer → User처럼 몇 단계를 건너도 결과는 같으므로, 값에는 원시 값이나 키를 참조하지 않는 불변 DTO만 담는 것이 안전하다.

엔트리는 정확히 언제 사라지나요?핵심"키가 회수되는 순간"이라고 답하면 절반만 맞다

키가 회수되는 순간이 아니다. 두 단계로 나뉜다.

  1. GC가 키를 회수하면서 Entry의 referent 자리를 null로 지우고, Entry 자체를 맵 내부의 ReferenceQueue에 넣는다. 이 시점에는 테이블에 엔트리가 그대로 있고 size 필드도 안 줄어든다.
  2. 그 다음 누군가 맵의 메서드(size(), get(), put(), entrySet() 등)를 호출하면, 그 메서드가 첫 줄에서 expungeStaleEntries()를 불러 큐를 비우며 엔트리를 테이블에서 떼고 size-- 한다.

리플렉션으로 내부를 직접 들여다보면 두 단계가 분리돼 있음이 그대로 보인다 — GC 직후에도 "테이블에 Entry 2개(그중 키가 null인 것 1개), size 필드 = 2"이고, size()를 한 번 부르면 그제서야 1이 된다(12절).

실무적 함의는 둘이다. 아무도 맵을 건드리지 않으면 정리도 안 되므로 값이 무거우면 그동안 그 값이 힙을 계속 차지한다. 그리고 size()는 스냅샷이라 아무것도 넣거나 빼지 않아도 값이 달라질 수 있으므로 용량 판단의 근거로 쓰면 안 된다.

그러면 캐시를 WeakHashMap으로 만들면 되지 않나요?시니어 변별"질문이 다르다"는 한 문장으로 정리할 수 있어야 한다

안 된다. 캐시가 답해야 하는 질문과 WeakHashMap이 답하는 질문이 다르기 때문이다.

캐시의 존재 이유는 "지금은 아무도 안 쓰지만 곧 또 쓸 것"을 미리 들고 있는 것이다. 조회가 끝나 아무도 안 붙잡고 있는 값을 그래도 보관하고 있다가 다음 요청에 바로 내주는 것이 캐시다.

그런데 WeakHashMap이 유지해 주는 조건은 정확히 "키를 지금 누군가 강하게 붙잡고 있는가"다. 아무도 안 붙잡는 순간 사라진다. 즉 캐시가 값을 들고 있어야 할 바로 그 구간에 WeakHashMap은 항목을 버린다. 히트율이 사실상 0에 수렴하는 구조라, 캐시의 모양을 하고 있지만 캐시로 동작하지 않는다.

SoftReference 캐시는 이 문제는 없지만 다른 문제가 있다(6절) — 비워지는 조건이 메모리 압박이라 트래픽 패턴에 따라 히트율이 요동치고, 어떤 항목이 버려질지 고를 수 없고, soft 참조가 많아지면 GC 부담이 늘어난다.

캐시를 비우는 기준은 메모리 압박이 아니라 사용 패턴이어야 한다

그래서 실무의 답은 Caffeine처럼 maximumSize·expireAfterWrite·recordStats로 정책을 코드가 선언하고 히트율을 지표로 확인할 수 있는 도구다. 정리하면 참조 강도는 "생명주기 연동" 도구이지 "캐시 정책" 도구가 아니다.

ThreadLocal의 메모리 누수와 어떻게 이어지나요?시니어 변별"구조가 같다"에서 그치지 말고 "무엇이 다른가"까지

구조가 정확히 같다. Thread 객체 안의 ThreadLocalMap도 Entry가 WeakReference를 상속해 키(ThreadLocal 인스턴스)만 약하게, 값은 강하게 잡는다.

같은 설계이므로 같은 결과가 나온다. 키가 죽어도 값은 안 죽는다. ThreadLocal 인스턴스가 어디서도 참조되지 않아 키가 회수되면 그 Entry는 stale entry가 되는데, Thread → ThreadLocalMap → Entry → value 사슬에서 값 쪽은 여전히 강한 참조라 키가 없어 꺼낼 수조차 없는 값이 힙에 남는다.

정리 시점의 문제도 같다. ThreadLocalMap도 GC가 아니라 그 맵에 set()/get()이 일어날 때 지나가는 김에 stale entry를 치운다. 해당 스레드가 그 맵을 다시 안 건드리면 영원히 안 치워진다.

차이는 누가 맵을 붙잡고 있느냐다. WeakHashMap은 우리가 만든 맵이라 맵 자체를 버리면 끝이지만, ThreadLocalMap은 톰캣 워커 스레드가 붙잡고 있고 그 스레드는 풀에서 재사용되며 애플리케이션 내내 죽지 않는다. 그래서 ThreadLocal 쪽이 훨씬 위험하다.

결론도 같은 방향이다약한 참조 키는 안전망이 아니라 미봉책이고, 확실한 해제는 요청 경계의 finally에서 remove()를 부르는 것 하나뿐이다.
WeakHashMap은 스레드 안전한가요? 대안은 뭐가 있나요?함정"읽기만 하는 스레드"라는 개념이 성립하는지 생각해 보라

안전하지 않다. HashMap과 마찬가지로 동기화가 전혀 없다. 게다가 WeakHashMap에는 일반 HashMap에 없는 위험이 하나 더 있다 — 조회 메서드조차 내부 상태를 바꾼다. get()이 getTable()을 거치며 expungeStaleEntries()로 테이블과 size를 수정하기 때문이다.

그래서 WeakHashMap에는 "읽기만 하는 스레드"라는 개념이 성립하지 않는다

선택지는 셋이다.

  • Collections.synchronizedMap(new WeakHashMap<>()) — 가장 단순하다. 모든 메서드를 하나의 락으로 감싼다. 다만 순회할 때는 사용하는 쪽이 직접 맵 객체에 synchronized 블록을 걸어야 하고, 락 경합이 있으면 처리량이 떨어진다.
  • Guava new MapMaker().weakKeys().makeMap() — 동시성을 지원하는 약한 키 맵. 다만 키 비교가 equals가 아니라 ==라는 결정적 차이가 있다(13절).
  • Caffeine Caffeine.newBuilder().weakKeys().build() — 캐시 정책(크기·만료·통계)과 약한 키를 함께 쓸 수 있다. 캐시가 목적이라면 이쪽이 맞다.

참고로 ConcurrentHashMap에는 약한 키 버전이 없다. "동시성 + 약한 키"가 동시에 필요하면 JDK 표준만으로는 답이 없고 위 라이브러리 중 하나를 골라야 한다.

Soft와 Weak의 차이가 "메모리 압박 조건" 하나뿐인가요? 회수 시점을 조절할 수 있나요?가산점HotSpot에는 튜닝 손잡이가 하나 있다

동작 규칙의 차이는 그 하나가 맞다. soft·weak 모두 "강한 참조가 없을 때"가 전제이고, soft에만 "그리고 메모리가 부족해지면"이라는 조건이 붙는다. 명세가 보장하는 것은 "OOM을 던지기 전에 softly reachable한 객체는 전부 정리한다"는 것이고, 그 전에 언제 정리할지는 JVM 재량이다.

HotSpot의 실제 판단식에는 손잡이가 있다. -XX:SoftRefLRUPolicyMSPerMB가 그것으로, "마지막 접근 이후 경과 시간"과 "남은 힙 크기"를 곱해 살릴지를 정한다. OpenJDK 21 기준 기본값 1000 — 남은 힙 1MB당 1000ms(1초)만큼 살려둔다는 뜻이다.

  • 남은 힙 100MB → 최근 100초 안에 쓴 것은 유지
  • 남은 힙 5MB → 5초 넘게 안 쓴 것부터 버림

힙이 줄수록 자동으로 공격적이 되는 구조다. 다만 이 식 자체가 "캐시 히트율이 남은 힙 크기에 좌우된다"는 뜻이므로, 이것이 곧 SoftReference를 캐시 정책으로 쓰면 안 되는 이유가 된다(6절).

if (ref.get() != null)로 검사한 다음에 쓰면 안전한가요?함정검사와 사용 사이에 무엇이 끼어들 수 있는가

안전하지 않다. 검사와 사용 사이에 GC가 돌면 두 번째 get()은 null일 수 있다. ref.get()이 돌려준 값을 어떤 변수에도 담지 않았으므로 그 사이에는 강한 참조가 존재하지 않기 때문이다.

// (문제) 검사와 사용 사이에 GC가 끼어들 수 있다
if (soft.get() != null) {
    process(soft.get());          // 여기서 null이 들어갈 수 있다
}

// (개선) 지역 변수로 한 번만 꺼내 강한 참조로 고정한 뒤 쓴다
byte[] cached = soft.get();      // 이 순간 cached는 강한 참조가 된다
if (cached == null) {
    cached = loadExpensiveData(); // 회수됐으면 다시 만든다
    soft = new SoftReference<>(cached);
}
process(cached);
Soft/Weak를 다루는 코드의 기본형: 꺼내서 강하게 고정하고, null이면 재생성한다

여기서 따라오는 설계 제약이 하나 있다. 재생성이 가능한 데이터에만 쓸 수 있다. 다시 만들 수 없는 유일한 데이터를 soft/weak로 들고 있다가 회수되면 복구할 방법이 없다.

finalize()는 왜 폐기됐나요? Cleaner로 바꾸면 무엇이 달라지나요?가산점결함 셋 중 하나는 "GC의 판정을 뒤집을 수 있다"이다

결함이 셋이다.

  1. 객체를 되살릴 수 있다. finalize() 안에서 this를 static 필드에 대입하면 GC가 "죽었다"고 판정한 객체가 다시 도달 가능해진다. 실제로 실행하면 zombie != null이 true다. 애플리케이션 코드가 GC의 판정을 뒤집는다는 뜻이고, 이것만으로 GC 알고리즘의 전제가 무너진다.
  2. 실행 시점이 보장되지 않는다. 별도 finalizer 스레드가 큐에서 꺼내 실행하는데 언제 스케줄될지 알 수 없다. 프로세스가 끝날 때까지 한 번도 안 불릴 수도 있다 — 파일 디스크립터가 고갈된 뒤에야 정리가 도는 상황이 벌어진다.
  3. 회수가 최소 두 사이클로 늘어난다. finalize()를 가진 객체는 GC가 처음 만나면 회수하지 못하고 큐에 등록만 하고 지나간다. 실제 회수는 finalize 실행 후 다음 GC다. 게다가 finalize() 안의 예외는 조용히 무시된다.

그래서 Object.finalize()는 Java 9에서 deprecated, Java 18에서 제거 예정(deprecated for removal)이 됐고, Java 18부터는 --finalization=disabled 옵션으로 기능 자체를 꺼 볼 수 있다.

Cleaner는 내부적으로 PhantomReference를 쓴다. Phantom의 get()이 항상 null인 이유가 여기서 풀린다 — 객체를 꺼낼 수 없게 만들어야 되살릴 방법이 원천 차단되기 때문이다. 결함 (1)을 설계로 막은 것이다.

순서를 기억하라1차 수단은 try-with-resources다. GC 기반 정리는 "혹시 개발자가 빠뜨렸을 때의 안전망"이지 1차 수단이 아니다. Cleaner는 그 안전망 자리에만 놓는다.
Cleaner에 등록하는 정리 작업을 람다나 내부 클래스로 써도 되나요?함정실무에서 가장 자주 밟는 지점이다

안 된다 — 정리 작업이 this를 참조하는 순간 정리가 영원히 실행되지 않는다.

CLEANER.register(this, task)는 "this가 도달 불가능해지면 task를 실행하라"는 등록이다. 그런데 task가 this를 강하게 참조하면 this는 영원히 강하게 도달 가능해진다. 정리가 돌 조건이 정리 작업 자신에 의해 깨지는 것이다.

// (문제) 람다가 바깥 인스턴스를 캡처한다 — 정리가 절대 안 돈다
CLEANER.register(this, () -> freeNative(this.address));

// (개선) 해제에 필요한 값만 복사해 든 static 클래스
private static class ReleaseTask implements Runnable {
    private final long address;   // 값만 복사 — 바깥 인스턴스를 모른다
    ReleaseTask(long address) { this.address = address; }
    public void run() { freeNative(address); }
}
CLEANER.register(this, new ReleaseTask(address));

비-static 내부 클래스도 같은 이유로 금지다 — 컴파일러가 바깥 인스턴스 참조를 보이지 않는 필드로 넣어 주기 때문이다. 정리 작업은 "해제에 필요한 원시 값"만 들고 있어야 한다.

리스너 레지스트리를 WeakHashMap으로 만들면 해제를 깜빡해도 안전한가요?함정교과서적 설명과 실제가 반대 방향으로 터진다

반대 방향으로 터진다. "등록만 하고 해제를 깜빡해도 누수가 안 난다"가 교과서적 설명인데, 실제로는 리스너를 붙잡는 다른 강한 참조가 없으면 등록하자마자 다음 GC에 사라진다.

Map<Runnable, Boolean> listeners = new WeakHashMap<>();

String name = "주문-리스너";
listeners.put(() -> System.out.println(name), Boolean.TRUE);        // 캡처 람다
listeners.put(new Runnable() { public void run() {} }, Boolean.TRUE); // 익명 클래스
System.out.println(listeners.size());   // 2

System.gc(); Thread.sleep(200);
System.out.println(listeners.size());   // 0  <- 등록한 리스너가 전부 증발했다

예외도 안 나고 로그도 안 남고, 그냥 이벤트가 조용히 안 온다. 추적이 극도로 어려운 형태의 버그다.

더 나쁜 것은 캡처 여부에 따라 결과가 뒤집힌다는 점이다. name 캡처를 없애 () -> System.out.println("이벤트")처럼 아무것도 캡처하지 않는 람다로 바꾸면 GC 후에도 사라지지 않는다 — 비캡처 람다는 호출 지점마다 인스턴스를 하나만 만들어 재사용하고, 그 인스턴스를 호출 지점이 붙잡고 있기 때문이다.

// (개선) 리스너의 수명을 붙잡는 주체를 명시한다
public class OrderPanel {
    private final Runnable listener = () -> refresh();   // 패널이 자기 리스너를 필드로 붙잡는다
    public OrderPanel(EventBus bus) { bus.register(listener); }
}
약한 레지스트리가 성립하려면 "리스너의 수명을 대신 책임지는 소유자"가 반드시 있어야 한다
String 리터럴이나 작은 Integer를 키로 쓰면 왜 안 사라지나요?함정"우리가 모르는 강한 참조가 하나 더 있다"

애초에 회수될 수 없는 객체이기 때문이다. 그런 키를 넣으면 WeakHashMap은 그냥 안 비워지는 HashMap이 된다.

  • String 리터럴 — 소스에 등장하는 문자열 리터럴은 String pool에 하나만 만들어져 공유되고, 그 코드가 속한 클래스의 런타임 상수 풀이 강하게 참조한다. 클래스가 로딩돼 있는 한 강하게 도달 가능하다. 실측하면 new String("런타임-키")로 만든 키는 사라지고 리터럴 키만 남는다(2 → 1).
  • 박싱된 작은 Integer — Integer.valueOf는 −128~127을 IntegerCache.cache 배열에서 꺼내 주는데, 이 배열은 static 필드이므로 GC 루트다. 125~130을 넣고 GC를 돌리면 [125, 126, 127]만 남는다. 정확히 캐시 상한에서 갈린다.
가장 나쁜 성질개발 환경에서는 정상처럼 보인다. id가 1, 2, 3으로 도는 동안에는 엔트리가 전부 남아 "잘 동작"하고, 운영에서 id가 128을 넘는 순간부터 엔트리가 사라지기 시작한다. 30번 문서의 Integer 캐시 버그와 같은 뿌리, 반대 증상이다.

정리하면 WeakHashMap의 키는 "실제로 회수될 수 있는 객체"여야 한다. 리터럴·박싱 캐시·enum 상수·Class 객체처럼 어딘가가 강하게 붙들고 있는 것을 키로 쓰면 약한 참조가 아무 일도 하지 않는다.

Guava의 MapMaker().weakKeys()는 왜 equals가 아니라 ==로 키를 찾나요?시니어 변별"수명 판정 기준과 조회 기준을 일치시킨 것"

수명 판정과 조회 기준을 일치시키기 위해서다.

WeakHashMap은 찾을 때는 equals/hashCode, 살려둘 때는 "저장된 그 인스턴스가 도달 가능한가"로 판정한다. 이 둘이 어긋나면 이상한 동작이 나온다 — 내용이 같은 lookup 문자열을 손에 쥐고 있어도, 맵에 저장된 stored 인스턴스의 강한 참조가 끊기면 엔트리가 사라진다. 방금 get으로 찾아지던 키가 다음 순간 사라진다.

Guava와 Caffeine의 weakKeys()는 이 혼란을 없애려고 조회 기준까지 인스턴스(==)로 맞췄다.

ConcurrentMap<String, String> m = new MapMaker().weakKeys().makeMap();
String stored = new String("주문-42");
m.put(stored, "값");
String lookup = new String("주문-42");

m.get(lookup);   // null   <- equals가 아니라 ==로 찾는다
m.get(stored);   // "값"
마이그레이션 주의WeakHashMap을 이 라이브러리로 갈아탈 때 컴파일 에러 없이 조용히 동작이 바뀌는 지점이다. 내용이 같은 새 인스턴스로 조회하던 코드가 전부 null을 받게 된다.
System.gc()를 부르면 weak 참조가 확실히 정리되나요?함정실험 코드와 프로덕션 코드의 경계

보장되지 않는다. System.gc()는 "GC를 지금 돌려 달라"는 힌트일 뿐이다. JVM은 이 요청을 무시할 수 있고, -XX:+DisableExplicitGC가 켜져 있으면 실제로 무시한다.

그래서 이 문서의 모든 실측 결과는 "OpenJDK 21(G1 GC) 환경에서 이렇게 관측됐다"는 뜻이지 명세의 보장이 아니다. 학습·실험용 코드이지 프로덕션 코드가 아니다.

정리 시점에 의존하는 코드를 쓰면 안 되는 이유가 여기 있다. weak 참조 기반 정리는 "언젠가 일어난다"까지만 설계에 넣을 수 있고, "언제 일어난다"는 넣을 수 없다. 확정적인 해제가 필요하면 try-with-resources·finally의 명시적 호출로 가야 한다.

덧붙여 System.gc()는 대개 Full GC를 유발하므로 운영 중 호출은 그 자체로 지연 사고의 원인이 된다.

WeakHashMap 대신 IdentityHashMap을 쓰면 되지 않나요?가산점두 맵이 다루는 축이 서로 직교한다

축이 다르다. 두 맵은 대체재가 아니라 서로 직교하는 두 선택이다.

키를 찾는 기준키 참조 강도
HashMapequals/hashCode강한 참조
IdentityHashMap==강한 참조
WeakHashMapequals/hashCode약한 참조(키만)
Guava weakKeys()==약한 참조(키만)

IdentityHashMap은 "찾는 기준"만 인스턴스로 바꾼 것이고 수명은 여전히 강하게 붙잡는다. 그래서 누수 방지 용도로는 아무 도움이 안 된다. 반대로 WeakHashMap은 "수명"만 약하게 바꾸고 찾는 기준은 그대로 equals다. 두 축을 모두 인스턴스 기준으로 맞춘 것이 Guava/Caffeine의 weakKeys()다(13절).

"WeakHashMap을 썼는데 힙이 안 줄어든다"는 신고를 받으면 무엇부터 확인하나요?시니어 변별원인 후보 네 가지를 순서대로 댈 수 있어야 한다

원인 후보는 네 가지이고, 확인 순서가 있다.

  1. 값이 자기 키를 (간접적으로라도) 참조하는가 — 가장 흔하다. 힙 덤프에서 키 객체의 GC 루트까지의 최단 강한 경로를 보면 맵 → Entry → value → … → key가 그대로 드러난다(10절).
  2. 키가 애초에 회수 불가능한 객체인가 — String 리터럴, −128~127 Integer, enum 상수, Class·ClassLoader 상수 등(11절).
  3. 맵을 아무도 안 건드리고 있는가 — 정리는 expungeStaleEntries()가 하고, 그것은 맵의 메서드가 호출될 때만 돈다. 키는 이미 회수됐는데 엔트리와 값 객체가 통째로 남아 있는 상태일 수 있다(12절).
  4. 키에 대한 강한 참조가 다른 곳에 남아 있는가 — 다른 컬렉션, 캐시, static 필드, 스레드 로컬 등. 강한 경로가 하나라도 있으면 그것이 이긴다(4절).
확인 도구힙 덤프를 뜬 뒤 MAT의 Path to GC Roots(exclude weak references)로 보면 약한 참조를 제외한 강한 경로만 남으므로, 위 1·2·4번이 바로 눈에 들어온다. 3번은 경로가 안 나오고 "키가 null인 Entry가 테이블에 쌓여 있는" 모습으로 보인다.
한 줄 요약
참조 강도는 도달 가능성 규칙 하나뿐인 GC에게 "이건 메모리가 부족하면 버려도 되고(Soft), 이건 내가 붙잡고 있다는 사실을 살릴 근거로 세지 말라(Weak)"고 말하는 유일한 수단이고 — 강도는 객체가 아니라 화살표의 성질이라 강한 화살표가 하나라도 있으면 그것이 이긴다 — WeakHashMap은 Entry가 WeakReference를 상속해 키만 약하게 잡는 맵이라 키를 아무도 안 쓰면 엔트리가 사라지지만, 값이 자기 키를 참조하면 무력화되고, 리터럴이나 −128~127 Integer를 키로 쓰면 애초에 회수되지 않으며, 정리는 GC 순간이 아니라 그 다음에 맵을 건드릴 때 expungeStaleEntries()로 일어나므로 size()는 스냅샷일 뿐이다. 그리고 이 도구는 생명주기 연동을 위한 것이지 캐시가 아니다 — 캐시는 "지금 누가 쓰는가"가 아니라 "또 쓸 확률이 얼마인가"로 비워야 하므로 Caffeine 같은 정책 기반 도구가 맞다.
