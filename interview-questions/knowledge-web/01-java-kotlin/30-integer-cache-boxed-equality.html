==는 한 번도 값을 비교한 적이 없다
127에서 true가 나온 것은 오토박싱이 Integer.valueOf로 번역되면서 −128~127 캐시의 같은 객체를 재사용한 우연일 뿐이다. 그래서 이 버그는 작은 값에서는 맞고, 운영 데이터가 커지는 순간에만 틀린다.

면접 질문: "Integer a = 127, b = 127일 때 a == b는 true인데 128이면 false인 이유는? 이런 코드의 위험은 무엇인가요?"

핵심 관전 포인트 — 박싱된 Integer는 primitive가 아니라 힙에 놓인 객체이고, 객체끼리의 ==는 처음부터 "같은 객체를 가리키는가"를 묻는 참조 비교다. Integer a = 127은 컴파일러가 Integer.valueOf(127) 호출로 바꾸는데, valueOf는 −128~127 범위의 객체를 미리 만들어 둔 캐시에서 꺼내 주므로 두 변수가 같은 객체가 되어 ==가 우연히 true가 된다. 128은 캐시 범위 밖이라 매번 새 객체이므로 false다. 위험은 여기 있다 — ==는 애초에 값을 비교한 적이 없는데 작은 값에서만 우연히 맞으므로, id가 1, 2, 3으로 도는 테스트와 개발 환경은 전부 통과하고 운영 데이터가 127을 넘는 순간에만 틀리는 재현 불가능한 버그가 된다. 래퍼 타입 비교는 예외 없이 equals(null이 섞이면 Objects.equals)를 쓴다.

0. 질문 + 출제 의도 · 겨냥하는 약점

질문 — "Integer a = 127, b = 127일 때 a == b는 true인데 128이면 false인 이유는? 이런 코드의 위험은 무엇인가요?"

출제 의도 — ==와 equals 혼동이 만드는 "작은 값 테스트는 전부 통과하고 운영 데이터에서만 틀리는" 버그의 대표 사례. 언어의 미묘한 규칙이 재현 안 되는 버그로 나타나는 전형을 아는지 본다. 캐시 범위를 외웠는지가 아니라, 왜 그 현상이 "우연"인지를 설명할 수 있는지가 갈림길이다.

약점 A"−128~127이 캐시라서요"에서 멈춘다 — 범위를 외운 것이다. ==가 애초에 참조 비교라는 전제를 깔지 못하면 Long으로 바뀌거나, 조건 연산자가 끼거나, Map 키 타입이 어긋나는 변형 앞에서 다시 막힌다(1·2절).
약점 B"왜 컴파일 에러가 아닌가"를 설명하지 못한다 — 컴파일러는 질문이 성립하는지만 검사하고, 그 질문이 우리가 하려던 질문인지는 검사하지 않는다. Integer == Long은 실제로 에러가 난다는 대비까지 들어야 답이 완성된다(2절).
약점 C위험을 "false가 나와서 틀린다"로만 말한다 — 진짜 위험은 작은 값에서 true라는 것이다. 테스트·개발환경·코드 리뷰가 동시에 통과하고, 배포와 증상 발생 사이에 몇 달의 시차가 생긴다(11·14절).
약점 DInteger만 알고 Long을 놓친다 — 실무의 id 타입은 대부분 Long이고, 사고는 Integer가 아니라 Long에서 난다. 더구나 Long의 캐시는 언어 명세의 보장이 아니라 구현의 선택이다(6·7절).
약점 E박싱만 보고 언박싱 쪽 사고(NPE)를 못 본다 — 오토박싱에는 짝이 되는 언박싱이 있고, 언박싱은 소스에 보이지 않는 메서드 호출이라 조건 연산자·== 혼합·누적 변수에서 NPE로 터진다(8·9·10절).
합격선"박싱된 Integer는 힙 객체이고 래퍼끼리의 ==는 처음부터 참조 비교입니다. Integer a = 127은 컴파일러가 Integer.valueOf(127)로 바꾸는데, valueOf는 −128~127 구간을 미리 만들어 둔 캐시에서 꺼내 주므로 두 변수가 같은 객체가 되어 ==가 우연히 true가 됩니다. 128은 캐시 밖이라 매번 새 객체라 false입니다. 위험은 ==가 값을 비교한 적이 없는데 작은 값에서만 우연히 맞는다는 것이고, 그래서 테스트와 코드 리뷰가 동시에 통과한 채 운영 데이터가 커지는 순간에만 틀립니다. 래퍼 비교는 예외 없이 Objects.equals로 하고 정적 분석 도구로 강제합니다."
이 문서를 관통하는 한 문장 ==는 한 번도 값을 비교한 적이 없다. 127에서 true가 나온 것은 정답이 아니라 우연이고, 128에서 false가 나온 것은 버그가 아니라 원래 동작이다. 이 문서의 모든 절은 이 한 문장을 세 방향으로 확장한 것이다 — 어디까지가 우연인가(캐시 범위·6·7절), 왜 아무도 못 막았나(컴파일러·테스트·리뷰·2·14절), 박싱의 반대편에는 무엇이 있나(언박싱·NPE·8~10절).

1. 전제 1 — 래퍼는 객체이고, 변수 칸에는 주소가 들어 있다

"127은 true, 128은 false"라는 현상부터 외우면 캐시 범위를 암기하는 데서 끝난다. 그러면 Long으로 바뀌거나, 조건 연산자가 끼거나, Map의 키 타입이 어긋나는 변형 앞에서 다시 막힌다. 현상보다 먼저 깔아야 할 전제가 둘 있고, 1절과 2절이 그 둘이다.

자바의 값에는 두 종류가 있다. primitive(기본형)는 int, long, boolean처럼 값 자체가 변수 자리에 그대로 들어 있는 타입이다. 객체가 아니므로 메서드도 없고 null도 될 수 없다. 래퍼(wrapper) 타입은 Integer, Long, Boolean처럼 그 값을 객체 안에 담아 놓은 타입이다. 이름 그대로 primitive를 한 겹 싸맨(wrap) 것이고, 이 경우 변수 칸에 들어 있는 것은 숫자가 아니라 그 객체가 힙 어디에 있는지를 가리키는 참조(reference)다.

명함과 사람 — ==와 equals가 던지는 서로 다른 질문

래퍼 변수는 사람이 아니라 명함이다. 명함에는 그 사람이 사는 집 주소만 적혀 있다.

질문코드실제로 묻는 것
==a == b"두 명함에 적힌 주소가 같은가?" — 같은 집을 가리키면 true. 옆집에 똑같이 생긴 사람이 살아도 false다.
equalsa.equals(b)"두 집에 사는 사람이 같은 사람인가?" — 집을 찾아가 안을 들여다본다. 주소가 달라도 안의 값이 같으면 true.

127이 true였던 이유는 이 비유로 이렇게 된다 — 자바가 −128~127번 주민에게는 미리 지어 둔 공용 주택 하나씩을 배정해 놓아서, 127을 찾는 두 명함에 같은 주소가 찍힌 것이다. 128부터는 배정된 집이 없어 요청할 때마다 새 집을 짓는다.

그런데 왜 이렇게 번거로운 래퍼가 필요한가. 두 가지 이유다. 제네릭에 primitive를 쓸 수 없어서(List<int>는 문법 오류다) 컬렉션에 담으려면 래퍼가 필요하고, null로 "값 없음"을 표현해야 하는 자리(아직 저장 안 한 엔티티의 id, 선택 입력 필드)가 있기 때문이다. 이 두 가지가 래퍼를 쓸 수밖에 없는 이유이자, 이 문서의 모든 함정이 들어오는 문이다.

2. 전제 2 — 그럼 왜 Integer a == Integer b는 컴파일 에러가 아닌가

==가 하는 일은 피연산자의 종류에 따라 달라진다. 피연산자가 primitive면 값을 비교하고, 둘 다 참조면 참조를 비교한다 — 즉 "두 변수가 힙의 같은 객체를 가리키는가"를 묻는다.

여기서 반드시 짚고 넘어갈 질문이 하나 있다. 그렇게 위험하면 컴파일러가 막아 주면 되지 않나?

에러가 아닌 이유는 그것이 문법적으로 완전히 유효한 연산이기 때문이다. 자바에서 참조끼리의 ==는 "같은 객체인지" 묻는 정상적인 질문이고, 실제로 그 질문이 필요한 자리도 있다(싱글턴 인스턴스 확인, enum 상수 비교 등). 컴파일러 입장에서 a == b는 올바르게 쓰인 문장이다. 우리가 그것으로 "값이 같은가"를 물으려 했다는 의도는 컴파일러가 알 도리가 없다.

반대로, 문법적으로 성립하지 않는 조합은 실제로 컴파일 에러가 난다. 이 대비를 보면 컴파일러가 무엇을 검사하고 무엇을 검사하지 않는지가 분명해진다.

Integer i = 1;
Long    l = 1L;
i == l;   // 컴파일 에러: incomparable types: Integer and Long
          // Integer와 Long은 서로 형변환이 불가능한 별개의 클래스라
          // "같은 객체인가"라는 질문 자체가 성립하지 않는다.

Integer a = 1, b = 1;
a == b;   // 컴파일 통과. 같은 타입이니 "같은 객체인가"는 성립하는 질문이다.
          // 다만 우리가 알고 싶었던 것은 그 질문이 아니었을 뿐이다.

3. 오토박싱의 실체는 Integer.valueOf() 호출이다

전제가 하나 더 남았다. Integer a = 127;이라고 쓰면 우변은 int 리터럴인데 좌변은 Integer다. 타입이 다른데 어떻게 대입이 되는가. 컴파일러가 중간에 변환 코드를 끼워 넣기 때문이다. primitive를 래퍼로 자동 변환하는 것을 오토박싱(autoboxing), 그 반대를 언박싱(unboxing)이라 한다.

번역 규칙을 두 글자로 붙잡는다
박싱 = 밸류오브  /  언박싱 = 인트밸류

"박은 밸, 언은 인" — 박싱은 valueOf(캐시를 거친다 → 참조가 우연히 같아진다), 언박싱은 intValue()·longValue()(메서드 호출이다 → null이면 NPE). 이 문서의 두 계열 사고가 정확히 이 두 메서드에서 갈린다.

4. valueOf 안의 캐시 — 여기서 127과 128이 갈린다

Integer.valueOf의 구현은 대략 이렇게 생겼다. 이 분기 한 줄이 현상의 전부다.

public static Integer valueOf(int i) {
    // 캐시 범위 안이면 미리 만들어 둔 배열에서 "이미 존재하는 객체"를 꺼내 준다.
    // 새로 만들지 않는다는 것이 핵심 — 같은 값이면 매번 똑같은 객체가 나온다.
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];

    // 범위 밖이면 그때그때 새 객체를 만든다. 호출할 때마다 다른 객체다.
    return new Integer(i);
}

IntegerCache는 클래스가 처음 로딩될 때 −128부터 127까지의 Integer 객체 256개를 미리 만들어 배열에 채워 두는 내부 클래스다. 작은 정수는 루프 인덱스, 상태 코드, 소량의 id 등으로 압도적으로 자주 쓰이므로, 미리 만들어 재사용하면 객체 생성과 GC 부담을 줄일 수 있다는 판단에서 나온 최적화다.

5. 127과 128이 갈리는 그림 — 이 한 장이 답이다

Integer a = 127, b = 127;
// 둘 다 Integer.valueOf(127) 호출 -> 캐시 배열의 같은 칸을 반환
a == b;      // true  — 두 변수가 힙의 "같은 객체 하나"를 가리킨다

Integer c = 128, d = 128;
// 둘 다 Integer.valueOf(128) 호출 -> 캐시 범위 밖이라 각각 new
c == d;      // false — 값은 같지만 서로 다른 객체 둘이다
c.equals(d); // true  — equals는 안에 든 값을 비교하므로 당연히 같다

6. 캐시 범위는 어디까지 믿을 수 있는가

여기서 "그럼 −128~127만 조심하면 되겠네"로 끝내면 안 된다. 캐시 범위는 고정된 상수가 아니다.

가산점 — 언어 명세가 보장하는 부분이 따로 있다 자바 언어 명세(JLS)는 박싱 결과가 항상 같은 객체여야 하는 범위를 규정한다 — boolean의 true/false, byte 전체, char의 0~127, 그리고 short와 int의 −128~127이다. 즉 JVM 구현이 마음대로 정하는 디테일이 아니라 명세가 요구하는 동작이다. 다만 Long은 이 목록에 없다 — Long.valueOf가 −128~127을 캐시하는 것은 표준 라이브러리 구현의 선택이지 명세의 보장이 아니다. 실무적 결론은 같지만("어느 쪽도 ==로 비교하지 않는다"), 근거의 층위가 다르다는 것을 아는 편이 정확하다.

7. 래퍼별 캐시 범위 총정리 — 실무에서 진짜 위험한 것은 Long이다

래퍼 타입별 캐시 범위 — 암기 대상
래퍼 타입캐시 범위근거의 층위실무에서 주의할 점
Byte−128~127 (byte의 전 범위)명세 보장범위 밖이 존재하지 않아 사실상 항상 같은 객체다. 그래도 ==를 쓰면 안 되는 것은 같다.
Short−128~127명세 보장타입 전체 범위(−32768~32767)에 비하면 극히 일부만 캐시된다.
Integer−128~127명세 보장상한만 -XX:AutoBoxCacheMax로 이동 가능. 하한 −128은 고정.
Long−128~127구현의 선택실무 사고의 주범. id 타입이 대부분 Long이고, AutoBoxCacheMax 영향도 받지 않는다.
Character0~127 (ASCII 구간)명세 보장음수가 없는 타입이라 하한이 0이다.
Booleantrue, false 두 개명세 보장값이 둘뿐이라 항상 같은 객체. 그래도 Boolean.TRUE.equals(x)가 null 안전해서 낫다.
Float, Double캐시 없음—0.0조차 매번 새 객체다. 실수는 ==를 쓰면 안 되는 이유가 하나 더 있다(정밀도).
표를 통째로 외우지 말고 세 갈래로 접는다
정수 계열 = 바이트 한 칸(−128~127)  /  Character = 아스키(0~127)  /  실수 = 없음
  • 정수 계열(Byte·Short·Integer·Long)은 전부 "바이트 한 칸" — byte가 표현하는 범위 −128~127 그대로다.
  • Character는 음수가 없으니 0부터 — 0~127, 즉 ASCII 구간.
  • Boolean은 값이 둘뿐이라 캐시라고 말할 것도 없다.
  • 실수(Float·Double)만 예외적으로 캐시 없음 — "자주 쓰는 실수 구간"이라는 게 정의되지 않는다.

한 겹 더 접으면 — "보장되는 것은 정수 계열 중 Long을 뺀 나머지". Long만 구현의 선택이라는 예외를 기억하면 가산점 답변까지 나온다.

8. 반대 방향의 함정 — 언박싱과 NPE

== 문제만 알고 끝내면 절반이다. 오토박싱에는 짝이 되는 언박싱이 있고, 언박싱은 NullPointerException이라는 다른 계열의 사고를 만든다. 원인은 하나다 — 래퍼는 null이 될 수 있는데 primitive는 될 수 없다.

// 잘못됨: 조회 결과가 null일 수 있는데 primitive로 받았다
Integer stock = stockMap.get("A-001");   // 없는 키면 null이 반환된다
int quantity = stock;                     // 여기서 NullPointerException

컴파일러는 int quantity = stock;을 int quantity = stock.intValue();로 번역한다. 즉 언박싱은 래퍼 객체의 메서드를 호출하는 일이고, 대상이 null이면 그 자리에서 NPE다.

이 NPE가 특히 불친절한 이유는 소스 코드에 메서드 호출이 보이지 않는다는 점이다. stock.intValue()라고 쓰여 있으면 "아 null 체크를 해야겠다"고 생각하지만, int quantity = stock;은 그냥 대입문처럼 보인다. 스택 트레이스도 이 줄을 가리킬 뿐 왜 여기서 NPE가 나는지 설명해 주지 않는다.

AFTERnull 가능성을 코드에 드러낸다
// 이렇게: null일 수 있음을 코드에 드러내고 기본값을 정한다
Integer stock = stockMap.get("A-001");
int quantity = (stock != null) ? stock : 0;

// 또는 조회 단계에서 없앤다 — 의도가 더 명확하다
int quantity = stockMap.getOrDefault("A-001", 0);

9. ==의 세 경우 — 이걸 나눠 말해야 정확한 설명이다

==의 규칙에는 세 번째 경우가 있다. 한쪽이 primitive면 다른 쪽이 언박싱되어 값 비교가 된다. 캐시 범위와 무관하게 항상 값 비교이므로 이것 자체는 문제가 아니다. 문제는 여기에도 언박싱이 숨어 있다는 것이다.

Integer boxed = 128;
int primitive = 128;
boxed == primitive;   // true — boxed가 언박싱되어 int 128 == int 128 이 된다

Integer nullBoxed = null;
nullBoxed == primitive;   // NullPointerException — 비교하기 전에 언박싱부터 한다

== 세 경우 — 한 줄로 붙잡기

둘 다 래퍼면 주소, 하나라도 primitive면 값 (그리고 그 래퍼가 null이면 NPE)

실무 규칙은 여기서 한 단계 더 단순해진다 — 세 경우를 매번 판별하지 말고 "래퍼가 하나라도 끼면 ==를 안 쓴다"로 통일한다. 판별에 드는 비용보다 판별을 안 해도 되게 만드는 규칙이 싸다.

10. 조건 연산자가 몰래 언박싱을 시킨다

가장 발견하기 어려운 형태다. 조건 연산자 ? :의 두 갈래가 래퍼와 primitive로 섞이면, 자바는 전체 표현식의 타입을 primitive로 정하고 래퍼 쪽을 언박싱한다.

BEFORE두 갈래가 Integer와 int로 섞였다
Integer discount = hasCoupon ? coupon.getAmount() : 0;
// getAmount()의 타입은 Integer, 반대편 0은 int 리터럴.
// 조건 연산자 전체 타입이 int로 정해지고 Integer 쪽이 언박싱된다.
// hasCoupon이 true이고 getAmount()가 null이면 바로 그 지점에서 NPE.
AFTER섞이지 않게 하거나, null을 명시적으로 처리한다
// 방법 1: 양쪽 갈래의 타입을 래퍼로 맞춰 언박싱 자체를 없앤다
Integer discount = hasCoupon ? coupon.getAmount() : Integer.valueOf(0);

// 방법 2: null 가능성을 명시적으로 처리하고 primitive로 확정한다 (권장)
int discount = (hasCoupon && coupon.getAmount() != null) ? coupon.getAmount() : 0;

규칙으로 기억할 것

조건 연산자의 두 갈래에 래퍼와 primitive를 섞지 않는다

섞이는 순간 언박싱이 끼어들고, 그 언박싱은 소스 어디에도 보이지 않는다. 특히 : 0, : -1, : 0L 같은 "기본값 리터럴"이 primitive라는 것을 잊기 쉽다 — 안전해 보이는 기본값이 NPE의 방아쇠가 된다.

12. 사고 2 — Map<Long, ?>에 int 키로 조회해 못 찾는다

같은 뿌리에서 나오지만 증상이 다른 사고다.

// 잘못됨: 키 타입은 Long인데 int 리터럴로 조회한다
Map<Long, Order> byId = new HashMap<>();
byId.put(1L, order);

byId.get(1);    // null!   — 분명 넣었는데 못 찾는다
byId.get(1L);   // order   — 이렇게 해야 나온다

왜 컴파일 에러가 안 나는가

Map.get의 시그니처가 V get(Object key)이기 때문이다. 제네릭 타입 K가 아니라 Object를 받는다. 그래서 int 1이 오토박싱으로 Integer 1이 되어 아무 불평 없이 들어간다. 같은 이유로 remove(Object), containsKey(Object)도 타입 검사를 못 한다.

왜 못 찾는가

HashMap의 조회는 "hashCode로 칸을 고르고 equals로 대조"하는 2단계인데, 해시는 우연히 같아서 1단계를 통과하고 2단계의 타입 검사에서 갈린다. 해시까지 달랐다면 오히려 이해하기 쉬웠을 텐데, 같은 칸까지 도달하는 것이 혼란을 키운다.

AFTER키 타입을 코드에 명시한다
byId.get(1L);
byId.get(orderId);                 // orderId가 Long이면 그대로

// 또는 조회 지점에서 변환을 강제한다
byId.get(Long.valueOf(someInt));

실무에서는 컨트롤러가 int로 받은 파라미터를 Map<Long, ?> 캐시에 그대로 넘기는 경로에서 자주 나온다. 타입 경계를 넘을 때 래퍼 타입을 통일하는 것이 예방책이다.

13. 올바른 비교 — before / after 정리

BEFORE캐시 범위에서만 우연히 정답
if (order.getUserId() == currentUserId) { … }
// 참조 비교. 값이 127을 넘는 순간부터 항상 false.
// 테스트·리뷰가 동시에 통과하므로 아무도 못 막는다.
AFTER세 가지 정답 — 성격이 다르다
// 1) equals — 값을 비교한다. 단 좌변이 null이면 NPE
if (order.getUserId().equals(currentUserId)) { … }

// 2) Objects.equals — 양쪽 모두 null 안전. 실무 기본값
//    내부에서 (a == b) || (a != null && a.equals(b)) 를 수행
if (Objects.equals(order.getUserId(), currentUserId)) { … }

// 3) null이 아님이 확실하면 primitive로 꺼내 비교
//    longValue()를 명시했으므로 "여기서 언박싱한다"가 보인다
if (order.getUserId().longValue() == currentUserId.longValue()) { … }
세 가지 모두 정답이지만 성격이 다르다 — 어느 쪽이 맞는지는 그 필드에 null이 정상 값인지에 달렸다

a.equals(b)좌변만 위험좌변 null → NPE
우변 null → false		해당 없음좌변이 절대 null이 아님이 구조적으로 보장되는 자리. 리팩터링에는 약하다.
Objects.equals(a, b)완전 안전둘 다 null → true
한쪽만 null → false		해당 없음실무 기본값. null 처리를 잊어도 NPE가 아니라 false로 수렴한다.

Objects.equals가 기본값인 이유 — 그리고 기본값이 아닐 때

Objects.equals를 쓴다
  • null이 정상 값인 필드 — 아직 저장 안 한 엔티티의 id, 선택 입력 필드
  • null 처리를 잊어도 false로 수렴하므로 방어적이다
  • 리팩터링으로 좌우가 바뀌어도 동작이 변하지 않는다
오히려 언박싱을 명시해 빨리 터뜨린다
  • null이면 안 되는 자리 — 인증된 사용자 id, 이미 저장된 주문의 id
  • Objects.equals는 null을 조용히 false로 삼켜서, "id가 null인 채 흘러 들어왔다"는 더 근본적인 버그를 '권한 없음'으로 위장시킨다
  • longValue()를 명시하면 NPE로 즉시 드러난다

"사람의 주의력 대신 도구로 강제한다"고 답하면 가산점이다 이유는 분명하다 — 이 버그는 코드 리뷰에서 눈에 잘 안 띄고(참조 비교라는 사실이 코드에 드러나지 않는다), 테스트도 통과하므로(11절) 사람과 테스트라는 두 방어선이 동시에 뚫리는 유형이다. 남는 방어선은 컴파일 타임 도구뿐이다.

15. String ==와 같은 뿌리다 — 두 사례를 연결해야 원리를 아는 것이다

같은 뿌리다 — 참조 비교와 값 비교의 혼동, 그리고 "특정 조건에서만 우연히 같은 객체가 되는" 최적화가 겹쳐 만든 착시다.

두 사례를 연결해 설명하면 캐시 범위를 암기한 것이 아니라 원리를 이해했다는 신호가 된다. 면접에서는 "같은 뿌리입니다"로 시작해서 "둘 다 참조 비교인데, 최적화 때문에 특정 조건에서만 우연히 같은 객체가 됩니다"라고 묶은 뒤, 경계 조건이 각각 무엇인지(값의 크기 / 생성 방식)를 덧붙이면 답이 완성된다.

17. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 펼쳐서 읽기만 하면 아는 것 같은 착각만 남는다.

왜 하필 −128~127만 캐시하나요?핵심"자주 쓰니까"에서 한 걸음 더 — 왜 하필 그 숫자인가

이유는 둘로 나뉜다 — "왜 캐시하는가"와 "왜 하필 그 경계인가".

왜 캐시하는가. 작은 정수는 압도적으로 자주 쓰인다 — 루프 인덱스, 상태 코드, 소량의 id. 그 구간만 미리 만들어 재사용하면 객체 생성과 GC 부담을 눈에 띄게 줄일 수 있다. 클래스가 처음 로딩될 때 Integer 객체 256개를 만들어 배열에 채워 두는 비용은 한 번뿐이고, 그 뒤로는 계속 재사용된다.

왜 하필 −128~127인가. byte 하나로 표현되는 범위가 정확히 −128~127이기 때문이다. 자연스러운 경계선이라 기본값으로 채택됐다. 이 한 줄을 덧붙이면 "외운 범위"가 아니라 "근거를 아는 범위"가 된다.

상한은 -XX:AutoBoxCacheMax로 올릴 수 있지만 하한 −128은 고정이고, 이 옵션은 Integer에만 적용되며 Long 등 다른 래퍼에는 영향이 없다. 무엇보다 옵션에 따라 같은 코드의 결과가 뒤집히므로 이 옵션은 해결책이 아니다.

Integer 말고 다른 래퍼 타입도 캐시가 있나요?가산점범위를 나열한 뒤 "명세 보장 vs 구현 선택"까지 가면 만점

Byte는 −128~127(byte의 전 범위), Short와 Long도 −128~127, Character는 0~127, Boolean은 true/false 두 개를 캐시한다. 반면 Float와 Double은 캐시가 없다 — 실수에서는 "자주 쓰이는 값 구간"을 정의하기 어렵기 때문이다.

실무에서 짚어야 할 것은 id 타입으로 가장 흔한 Long에 같은 함정이 그대로 있다는 점이다. 실제 사고는 Integer가 아니라 Long에서 난다(11절).

가산점 — 근거의 층위를 구분한다boolean, byte, char의 0~127, short와 int의 −128~127은 언어 명세(JLS)가 동일 객체를 보장하는 범위다. 반면 Long의 캐시는 표준 라이브러리 구현의 선택일 뿐 명세의 보장이 아니다. 실무 결론은 "어느 쪽도 ==로 비교하지 않는다"로 같지만, 근거의 층위가 다르다는 것까지 구분하면 정확한 답이 된다.
new Integer(127) == new Integer(127)은 어떻게 되나요?핵심답은 한 단어. 중요한 건 여기서 얻는 교훈이다

false다. new는 정의상 반드시 새 객체를 만드는 연산이므로 캐시를 거치지 않는다. 두 번 호출하면 반드시 서로 다른 객체 둘이 나온다.

이것이 래퍼 생성자가 deprecated된 이유 중 하나다. valueOf(또는 오토박싱)를 쓰면 캐시를 활용해 불필요한 객체 생성을 피할 수 있다.

여기서 잘못된 교훈을 얻으면 안 된다valueOf를 쓴다고 ==가 안전해지는 것이 아니다. 128 이상에서는 valueOf도 새 객체를 만든다. 참조를 비교한다는 사실 자체는 그대로다. "new를 안 쓰면 되겠네"는 이 문서에서 가장 흔한 오독이다.
String의 == 비교와 같은 문제인가요?시니어 변별"같다/다르다"가 아니라 어디까지 같고 어디부터 다른지

같은 뿌리다 — 참조 비교와 값 비교의 혼동, 그리고 "특정 조건에서만 우연히 같은 객체가 되는" 최적화가 겹쳐 만든 착시다.

String은 컴파일 타임 리터럴을 String pool이라는 공용 저장소에 모아 재사용하므로 리터럴끼리는 ==가 true다. 반면 new String(...)이나 런타임에 조합된 문자열(사용자 입력, DB 조회 결과, 문자열 연결의 결과)은 별개의 객체라 false다.

String a = "order", b = "order";
a == b;                      // true  — 둘 다 pool의 같은 객체

String c = new String("order");
a == c;                      // false — c는 pool 밖의 새 객체
a.equals(c);                 // true

"리터럴이나 작은 값으로 도는 테스트에서는 통과하고 실데이터에서 틀린다"는 버그 패턴까지 완전히 동일하다. 두 사례를 연결해 설명하면 캐시 범위를 암기한 것이 아니라 원리를 이해했다는 신호가 된다.

차이도 하나 짚으면 좋다. Integer 캐시의 경계는 값의 크기(−128~127)로 갈리고, String pool의 경계는 문자열이 만들어진 방식(리터럴이냐 런타임 생성이냐)으로 갈린다. 경계 조건은 다르지만 "경계 안쪽에서만 우연히 맞는다"는 구조는 같다.

그럼 처음부터 primitive를 쓰면 되지 않나요? 래퍼는 언제 필요한가요?시니어 변별"primitive가 기본값"을 인정한 뒤 예외 둘 — 트레이드오프를 아는지 본다

성능과 안전 면에서 primitive가 기본값인 것은 맞다. 객체 생성이 없고, null이 될 수 없어 언박싱 NPE도 없고, ==가 애초에 값 비교다. 세 가지 함정이 전부 사라진다.

그러나 래퍼가 반드시 필요한 자리가 둘 있다.

(1) null이 의미를 갖는 필드. JPA 엔티티의 id는 영속화 전까지 값이 없어야 하고, "입력하지 않음"과 "0을 입력함"을 구분해야 하는 DTO 필드도 마찬가지다. primitive는 0과 "없음"을 구분하지 못한다. int discountRate = 0이 "할인 없음"인지 "아직 안 정함"인지 알 방법이 없다.

(2) 제네릭. List<int>는 문법 오류다. 타입 파라미터 자리에는 참조 타입만 올 수 있으므로 컬렉션에 담으려면 래퍼여야 한다.

답은 "primitive만 쓴다"가 아니라
래퍼를 쓰는 자리를 의도적으로 한정한다
그리고 그 자리에는 == 금지와 null 처리라는 비용이 따라온다는 것을 인지하고 설계한다
가산점 — 성능 이야기를 얹는다컬렉션이나 루프에서 박싱이 반복되면 매 연산마다 객체가 하나씩 생겨 GC 압력이 된다. 대표적인 안티패턴이 합계 계산에 Long sum을 쓰는 것이다. 한 글자 차이지만 100만 건 루프에서는 100만 개의 임시 객체가 생기느냐 마느냐의 차이다(아래 별도 질문 참조).
Integer boxed = 128; int p = 128;일 때 boxed == p는요?함정true다. 그런데 안심하면 안 되는 이유가 있다

true다. ==의 규칙에는 세 번째 경우가 있다 — 한쪽이 primitive면 다른 쪽이 언박싱되어 값 비교가 된다. boxed가 boxed.intValue()로 풀려 int 128 == int 128이 되므로 캐시 범위와 무관하게 항상 값 비교다.

그래서 이것 자체는 문제가 아니다. 문제는 여기에도 언박싱이 숨어 있다는 것이다.

Integer boxed = null;
int primitive = 128;
boxed == primitive;   // NullPointerException — 비교하기 전에 언박싱부터 한다

그리고 더 나쁜 것은 이 규칙이 "안전한 코드"라는 착각을 만든다는 점이다. "래퍼랑 int를 비교하면 값 비교니까 괜찮네"라고 배운 사람이 나중에 양쪽 다 래퍼가 되도록 리팩터링하면(예: 파라미터 타입을 int에서 Integer로 바꾸면) 비교의 의미가 조용히 참조 비교로 바뀐다. 컴파일도 되고 테스트도 통과한다.

타입 하나만 바뀌어도 ==의 의미가 통째로 바뀐다 — 그래서 래퍼가 하나라도 끼면 ==를 안 쓴다
Integer discount = hasCoupon ? coupon.getAmount() : 0;에서 NPE가 나는 이유를 설명해 보세요.시니어 변별좌변이 Integer인데 왜 null을 못 받나

조건 연산자의 타입이 먼저 정해지고, 대입은 그 다음이기 때문이다. 순서를 뒤집어 생각하면 영원히 이해가 안 된다.

coupon.getAmount()의 타입은 Integer, 반대편 0은 int 리터럴이다. 두 갈래가 래퍼와 primitive로 섞이면 자바는 조건 연산자 전체의 타입을 primitive(int)로 정하고, 래퍼 쪽을 언박싱한다. 그래서 hasCoupon이 true이고 getAmount()가 null이면 대입에 도달하기도 전에 언박싱 시점에서 NPE가 난다.

좌변이 Integer라 null을 받을 수 있어 보이는 것이 착시를 키운다. 좌변 타입은 "언박싱된 int를 다시 박싱해서 담을 그릇"일 뿐, 조건 연산자 내부에서 이미 벌어진 언박싱을 되돌리지 못한다.

그리고 보이는 것은 삼항 연산자와 대입뿐이고 어디에도 메서드 호출이 없다. 스택 트레이스도 이 줄을 가리킬 뿐 왜 NPE인지 설명하지 않는다.

// 이렇게 1: 양쪽 갈래의 타입을 래퍼로 맞춰 언박싱 자체를 없앤다
Integer discount = hasCoupon ? coupon.getAmount() : Integer.valueOf(0);

// 이렇게 2: null 가능성을 명시적으로 처리하고 primitive로 확정한다 (권장)
int discount = (hasCoupon && coupon.getAmount() != null) ? coupon.getAmount() : 0;
조건 연산자의 두 갈래에 래퍼와 primitive를 섞지 않는다 — 섞이는 순간 소스에 보이지 않는 언박싱이 끼어든다
Map<Long, Order>에 get(1)이 null인 이유는? 왜 컴파일 에러가 아닌가요?함정두 질문이다 — 컴파일이 되는 이유와 못 찾는 이유

왜 컴파일 에러가 안 나는가. Map.get의 시그니처가 V get(Object key)이기 때문이다. 제네릭 타입 K가 아니라 Object를 받는다. 그래서 int 1이 오토박싱으로 Integer 1이 되어 아무 불평 없이 들어간다. (같은 이유로 remove(Object), containsKey(Object)도 타입 검사를 못 한다.)

왜 못 찾는가. HashMap의 조회는 "hashCode로 칸을 고르고 equals로 대조"하는 2단계인데, 여기서는 2단계에서 갈린다.

  • 1단계 통과 — Long.valueOf(1L).hashCode()도 1, Integer.valueOf(1).hashCode()도 1이다. 해시가 같아서 정확히 같은 칸으로 간다.
  • 2단계 탈락 — 칸 안의 후보 Long(1)과 찾는 키 Integer(1)을 equals로 대조하는데, Long.equals(Object o)의 첫 줄은 "o가 Long인가?" 타입 검사다. Integer는 Long이 아니므로 false → "없음"으로 판정.

같은 칸까지 정확히 찾아가 놓고 마지막 타입 검사에서 탈락한다. 그래서 디버거로 보면 맵 안에 값이 멀쩡히 들어 있고 get만 null을 반환한다 — "분명히 넣었는데 없다"는 가장 헷갈리는 증상이 나온다.

실무에서는 컨트롤러가 int로 받은 파라미터를 Map<Long, ?> 캐시에 그대로 넘기는 경로에서 자주 나온다. 타입 경계를 넘을 때 래퍼 타입을 통일하는 것이 예방책이다.

equals와 Objects.equals 중 무엇을 기본값으로 하고 왜인가요?핵심"null 안전"에서 멈추지 말고 "언제 그게 오히려 나쁜지"까지

기본값은 Objects.equals다. 이유는 null 처리를 잊어도 NPE가 아니라 false로 수렴하기 때문이다. 내부적으로 (a == b) || (a != null && a.equals(b))를 수행하므로 양쪽 다 null이면 true, 한쪽만 null이면 false가 되어 어느 경우에도 터지지 않는다.

반대로 a.equals(b)는 좌변이 null이면 NPE다. "좌변은 절대 null이 아니다"를 코드 밖의 지식으로 알고 있어야 안전한 형태라 리팩터링에 약하다.

그런데 항상 Objects.equals가 옳은 것은 아니다"null이면 안 되는 자리"라면 오히려 언박싱을 명시해 NPE로 빨리 터뜨리는 편이 나을 수 있다(a.longValue() == b.longValue()). Objects.equals는 null을 조용히 false로 삼켜서, "id가 null인 채로 여기까지 흘러 들어왔다"는 더 근본적인 버그를 권한 없음으로 위장시킬 수 있다.

판단 기준은 하나다 — 그 필드에 null이 정상 값인가. 정상 값이면 Objects.equals, 비정상이면 빨리 터지는 쪽. 이 구분을 말하면 "규칙을 외운 사람"이 아니라 "규칙의 근거를 아는 사람"으로 읽힌다.

compareTo도 같은 계열의 답이다. a.compareTo(b) == 0은 값 기준 비교이므로 안전하고, 정렬이나 대소 비교가 함께 필요한 자리에서는 이쪽을 쓴다.

-XX:AutoBoxCacheMax=100000을 주면 이 문제가 해결되나요?함정"해결된다"고 답하면 원리를 모른다는 신호

아니다. 원래 버그보다 더 나쁜 형태로 바뀐다.

이 옵션은 확실히 동작한다 — 상한을 2000으로 올리면 Integer 1000 == 의 결과가 false에서 true로 뒤집힌다. 하지만 그것이 바로 문제다. 같은 소스가 실행 옵션에 따라 다른 답을 낸다는 뜻이기 때문이다.

  • 환경 의존이 생긴다. 로컬에서는 통과하고 운영 JVM 옵션이 다르면 틀린다. 재현 조건이 코드 밖으로 나가 버린다.
  • Integer에만 적용된다. Long에는 영향이 없어서, 정작 사고가 나는 id 비교(Long)는 그대로 남는다.
  • 상한을 아무리 올려도 위쪽 경계는 남는다. 10만으로 올리면 10만 1번 유저에서 터진다. 경계를 미루는 것이지 없애는 것이 아니다.
  • 메모리를 그만큼 쓴다. 상한만큼 Integer 객체를 미리 만들어 배열에 들고 있게 된다.
이 옵션의 진짜 의미는 "해결책"이 아니라 "참조 비교에 기대면 안 된다는 증거"다 — 코드를 안 고쳤는데 결과가 바뀐다는 것이 그 증거다
코드 리뷰와 테스트로 이 버그를 잡을 수 있나요?시니어 변별"두 방어선이 동시에 뚫린다"가 핵심 문장

둘 다 구조적으로 못 잡는다. 이 질문의 정답은 "그래서 도구로 강제한다"이다.

  • 코드 리뷰가 못 잡는 이유 — if (a == b)는 참조 비교라는 사실이 코드 어디에도 드러나지 않는다. 타입 선언은 저 위 필드나 메서드 시그니처에 있고, 리뷰어의 눈에는 "값 비교하는 조건문"으로 읽힌다. 변수 이름이 userId면 더더욱 숫자처럼 보인다.
  • 테스트가 못 잡는 이유 — 테스트 픽스처의 id는 대부분 1L, 2L, 100L이다. 전부 캐시 범위 안이라 버그가 있는 코드가 초록불로 통과한다. 테스트가 "정상 동작을 증명"해 버리는 것이 가장 나쁘다.

사람과 테스트라는 두 방어선이 동시에 뚫리는 유형이므로 남는 방어선은 컴파일 타임 도구뿐이다.

  • IntelliJ의 "Number comparison using ==" 인스펙션
  • ErrorProne의 BoxedPrimitiveEquality 검사
  • SonarQube의 해당 룰

여기에 설계 차원의 예방을 얹으면 좋다 — null 표현이 필요 없는 필드는 처음부터 primitive로 선언한다(long id). 래퍼를 쓰는 자리를 줄이면 실수할 자리 자체가 줄어든다.

그리고 AI 생성 코드 리뷰의 체크포인트로도 쓰인다. 이런 코드는 생성 시점에 그럴듯하고 테스트도 통과하므로, "래퍼 타입 + ==" 조합 자체를 기계적으로 걸러내는 눈이 필요하다 — 의미를 따지기 전에 형태로 먼저 거른다.

List<Integer> list에서 list.remove(1)은 무엇을 지우나요?가산점같은 계열의 오토박싱 함정

값 1이 아니라 인덱스 1번을 지운다.

List에는 remove(int index)와 remove(Object o) 두 오버로드가 있는데, primitive int는 오버로드 해석에서 박싱보다 "정확한 일치"가 우선이라 remove(int)가 선택되기 때문이다.

List<Integer> list = new ArrayList<>(List.of(10, 20, 30));

list.remove(1);                  // 인덱스 1 삭제 -> [10, 30]
list.remove(Integer.valueOf(1)); // 값 1 삭제 (없으면 아무 일도 안 일어남)

교훈은 이 문서 전체와 같다 — 박싱은 자동으로 일어나지만, 자동으로 일어나는 것과 우리가 의도한 것이 항상 같지는 않다. Map.get(Object)가 타입 검사를 못 하는 것도, 조건 연산자가 몰래 언박싱하는 것도 전부 같은 뿌리다.

Long sum = 0L;로 100만 건 합계를 내면 무슨 일이 생기나요?가산점한 글자 차이가 만드는 것

반복마다 언박싱 → 덧셈 → 다시 박싱이 일어나 원소 수만큼 Long 객체가 생긴다. 100만 건이면 100만 개의 임시 객체가 만들어졌다 버려지고, 그만큼 GC 압력이 된다. 게다가 합계는 대부분 127을 훌쩍 넘으므로 캐시 재사용도 전혀 못 받는다.

// 잘못됨: 반복마다 언박싱 -> 덧셈 -> 다시 박싱
Long sum = 0L;
for (Order o : orders) sum += o.getAmount();

// 이렇게: 누적 변수는 primitive로 — 객체가 하나도 안 생긴다
long sum = 0L;
for (Order o : orders) sum += o.getAmount();

sum += x가 sum = Long.valueOf(sum.longValue() + x)로 번역된다는 것을 말할 수 있으면 정확한 답이 된다. 한 글자 차이지만 대량 루프에서는 결과가 완전히 다르다.

덤으로 NPE 위험도 있다 — sum이 null인 상태에서 +=를 하면 언박싱에서 바로 터진다.

Integer i = 1; Long l = 1L;일 때 i == l은요?핵심이건 컴파일 에러다 — 그 이유가 이 문서의 절반이다

컴파일 에러다 — incomparable types: Integer and Long.

Integer와 Long은 서로 형변환이 불가능한 별개의 클래스라, "같은 객체인가"라는 질문 자체가 성립하지 않는다. 절대 같은 객체일 수 없는 두 타입을 비교하는 것은 명백한 실수이므로 컴파일러가 막아 준다.

이 대비가 중요한 이유는 "컴파일러가 무엇을 검사하는가"를 드러내기 때문이다.

Integer == Long
  • 질문 자체가 성립하지 않음
  • 따라서 컴파일 에러
vs
Integer == Integer
  • 질문은 성립함 ("같은 객체인가")
  • 따라서 컴파일 통과
  • 다만 우리가 하려던 질문이 아닐 뿐

컴파일러는 질문이 성립하는지만 검사하고, 그 질문이 우리가 하려던 질문인지는 검사하지 않는다. 이 버그가 조용한 이유의 절반이 여기에 있다.

참고로 i.equals(l)은 컴파일은 되지만 항상 false다(Integer.equals의 타입 검사에서 탈락). 에러도 안 나고 값도 틀리는 더 나쁜 형태이므로, 타입이 다르면 i.longValue() == l처럼 명시적으로 폭을 맞춰 비교해야 한다.

같은 유저가 어떤 화면에서는 되고 어떤 화면에서는 안 되는 이유는 뭔가요?시니어 변별간헐성의 정체 — 이걸 설명하면 실제로 겪어 본 사람으로 읽힌다

참조가 같아지는 경로와 달라지는 경로가 섞여 있기 때문이다. 값은 항상 같은데 객체가 같을 때도 있고 다를 때도 있다.

  • 같은 트랜잭션 안에서 JPA 1차 캐시(영속성 컨텍스트)가 같은 엔티티 인스턴스를 돌려주는 경로 — 이때 order.getUserId()와 세션의 currentUserId가 우연히 같은 객체일 수 있어 ==가 통과한다.
  • 새로 DB에서 조회했거나 다른 트랜잭션에서 넘어온 경로 — 값은 같아도 새로 박싱된 다른 객체라 ==가 실패한다.
  • 캐시(Redis 등)에서 역직렬화된 경로 — 역시 새 객체다.

그래서 증상이 "화면마다 다름", "새로고침하면 됨", "특정 유저만 그럼"처럼 규칙을 찾기 어려운 형태로 나타난다. 로그만 봐서는 패턴이 안 잡힌다.

여기에 시차까지 겹친다문제의 코드는 몇 달 전에 배포됐고, 오늘 터진 이유는 가입자 수가 128을 넘었기 때문이다. "최근 배포한 게 뭐지"로 시작하는 통상적인 장애 추적이 통하지 않는다. 입력 데이터의 크기에 따라 정답 여부가 갈리는 버그는 재현 조건을 못 찾아 며칠을 태우는 유형의 대표다.
한 줄 요약
==는 처음부터 끝까지 참조만 비교했고, 127에서 true가 나온 것은 오토박싱이 Integer.valueOf로 번역되면서 −128~127 캐시의 같은 객체를 재사용한 우연일 뿐이다 — 그런데 참조 비교는 문법적으로 유효하므로 컴파일러가 막아 주지 않고 작은 값으로 도는 테스트도 전부 통과하니, 래퍼 타입 비교는 예외 없이 equals / Objects.equals(또는 compareTo)로 쓰고 그 규칙을 정적 분석 도구로 강제하는 데까지 가야 한다.
