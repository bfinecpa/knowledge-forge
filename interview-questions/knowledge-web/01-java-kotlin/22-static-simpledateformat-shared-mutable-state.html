static SimpleDateFormat과 공유 가변 상태 — 함정을 "목록"이 아니라 "유형"으로 찾기
스레드 안전하지 않은 것은 우연이 아니라 구현 사실이다 — 내부에 Calendar 작업대가 하나 있고, 호출마다 거기에 쌓았다가 읽는다

면접 질문: "AI가 생성한 코드에서 SimpleDateFormat을 static 필드로 공유하고 있습니다. 무엇이 문제이고, 같은 유형(공유 가변 상태)의 함정을 코드베이스 어디에서 더 찾아보겠습니까?"

핵심 관전 포인트 — SimpleDateFormat이 스레드 안전하지 않은 것은 우연이 아니라 구현 사실이다. 내부에 Calendar 필드를 하나 두고 format()/parse()가 호출될 때마다 그 하나의 Calendar에 중간 결과를 쌓았다가 읽는 구조다. static으로 공유하면 톰캣의 동시 요청 스레드들이 그 Calendar를 서로 덮어써서, 예외 없이 남의 날짜가 응답에 실리거나 간헐적으로 NumberFormatException이 튄다. 예외가 항상 나는 게 아니라 가끔만 난다는 것이 이 버그를 무섭게 만든다 — 단일 스레드 테스트는 전부 통과하고, 운영에서도 에러율 그래프에 안 잡히며, 조용히 틀린 데이터만 쌓인다. 해법은 불변이라 공유해도 안전한 java.time.DateTimeFormatter로 교체하는 것이 1순위다. 그리고 이 문서의 진짜 주제는 SimpleDateFormat이 아니라 "static 필드에 가변 상태를 두는 것" 일반이다 — 스프링 빈은 싱글톤이라 그 인스턴스 필드도 사실상 static과 같은 공유이므로, 컨트롤러·서비스 빈에 요청 처리 중간 상태를 필드로 두면 정확히 같은 사고가 난다.
  • 1
    스레드 안전하지 않은 이유를 구현으로 말합니다. SimpleDateFormat은 부모 DateFormat에 Calendar 필드 하나를 두고 이걸 작업대(scratch space)로 씁니다. format()은 "calendar에 쓰고 → 다시 읽어 조립"하는 2단계라, 인스턴스를 공유하면 작업대를 공유하는 것입니다.
  • 2
    증상은 예외가 아니라 "조용히 틀린 값"이 주력입니다. 두 스레드가 겹치면 A의 응답에 B의 날짜가 실려 나갑니다. 에러율 0%, 로그 정상, 단위 테스트 100% 통과. 고치는 순서는 가변 제거(DateTimeFormatter) → 공유 제거(지역 변수) → 격리(ThreadLocal) → 직렬화(synchronized)이고, 아래로 갈수록 문제를 없애는 게 아니라 안고 관리합니다.
  • 3
    진짜 정체는 static도 날짜도 아니라 "가변 상태 × 공유 스코프"라는 유형입니다. 그래서 수색 대상은 ① 가변 static 필드와 ② 싱글톤 빈의 인스턴스 필드 둘입니다. @Service·@RestController는 인스턴스가 하나라 그 필드는 static과 등가이고, 마지막에는 SpotBugs STCAL 같은 정적 분석 룰을 CI에 걸어 재발을 막습니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "AI가 생성한 코드에서 SimpleDateFormat을 static 필드로 공유하고 있습니다. 무엇이 문제이고, 같은 유형(공유 가변 상태)의 함정을 코드베이스 어디에서 더 찾아보겠습니까?"

출제 의도 — 스레드 안전하지 않은 객체의 공유는 테스트를 전부 통과하고 동시 요청에서만 값이 섞이는 유형이라, 리뷰어의 머릿속 모델만이 방어선이다. 한 사례를 같은 패턴(가변 static, 싱글턴 빈의 상태 필드)으로 일반화해 찾는지 — 함정을 "목록"이 아니라 "유형"으로 아는지, AI가 생성한 코드를 검증할 수 있는 사람인지를 본다.

약점 A"스레드 안전하지 않습니다"에서 끝나는 답 — 외운 문장이다. 왜 그런지를 구현(Calendar 작업대 하나 + 쓰고-읽는 2단계)으로 대지 못하면, 처음 보는 클래스를 만났을 때 판단할 수 없는 사람으로 읽힌다.
약점 B증상을 "예외가 납니다"로만 말하는 답 — 주력 증상은 예외가 아니라 조용히 틀린 값이다. 에러율 0%·로그 정상이라는 점을 짚지 못하면 "왜 운영에서 못 잡았나"라는 후속 질문에 무너진다.
약점 Csynchronized나 ThreadLocal을 정답처럼 내미는 답 — 동작은 한다. 그러나 가변 제거 → 공유 제거 → 격리 → 직렬화라는 서열과 그 이유를 말하지 못하면 "대증요법을 근본 해법으로 아는 사람"이 된다.
약점 D질문의 뒷부분(어디서 더 찾겠는가)에 답하지 않는 답 — 여기가 진짜 배점이다. 싱글톤 빈의 인스턴스 필드가 static과 등가라는 연결을 못 하면 사례 하나를 아는 사람에서 멈춘다.
합격선구현으로 원인을 세우고(작업대 하나) → 증상의 비결정성을 설명하고 → 해법을 서열로 제시하고 → "가변 × 공유" 2축으로 일반화해 수색 대상 둘(가변 static 필드 · 싱글톤 빈 필드)을 대고 → CI 정적 분석으로 재발을 막는 것까지.
이 문서의 진행 방향 — 사례 하나에서 유형 하나로 1~7절은 SimpleDateFormat이라는 사례를 구현 수준까지 파고든다(원인 → 증상 → 해법 서열). 8~11절은 그 사례를 "가변 상태 × 공유 스코프"라는 유형으로 들어올려 코드베이스 전체를 훑는 방법으로 바꾼다. 면접 답변도 이 순서다 — 사례로 신뢰를 얻고, 유형으로 점수를 얻는다.

1. 전제 — 내 코드는 워커 200개가 동시에 실행한다

컨트롤러와 서비스를 짤 때 대개 의식하지 않는 사실부터 깔아야 한다. 톰캣은 요청마다 스레드를 새로 만들지 않는다. 애플리케이션이 뜰 때 워커 스레드를 미리 만들어 풀에 담아두고, 요청이 오면 하나를 빌려주고, 응답이 끝나면 죽이지 않고 풀로 되돌려 다음 요청에 다시 빌려준다. 스프링 부트의 기본 최대 워커 수는 200개다.

그러니까 같은 메서드를 최대 200개 스레드가 동시에 실행하고 있다. 그런데도 평소에 동시성을 걱정하지 않는 이유는, 지역 변수와 파라미터가 스레드마다 따로 있는 스택에 올라가기 때문이다. 스레드 A의 지역 변수와 스레드 B의 지역 변수는 애초에 다른 메모리다. 섞일 수가 없다.

스택 바깥에 있는 것만 공유된다. static 필드는 클래스에 하나만 존재하므로 모든 스레드가 같은 것을 본다.

그래서 이 질문의 코드는 이렇게 읽어야 한다

Before AI가 자주 생성하는 전형적 패턴 (오래된 코드에서 흔했던 관용구다)
public class DateUtils {
    private static final SimpleDateFormat SDF =
            new SimpleDateFormat("yyyy-MM-dd HH:mm:ss");   공유 1개

    public static String format(Date date) {
        return SDF.format(date);   // 톰캣 워커 200개가 '같은 객체'를 동시에 두드린다
    }
}

이 절에서 가져갈 문장 두 개

지역 변수는 안전하다
스레드마다 다른 스택에 만들어진다. 다른 스레드가 접근할 경로 자체가 없다 — 그래서 대부분의 코드는 동시성을 신경 쓰지 않아도 된다.
스택 바깥만 위험하다
static 필드와 싱글톤 빈의 인스턴스 필드. 이 두 자리에 가변 객체가 놓이는 순간 200개 스레드의 충돌 지점이 된다.

2. static final의 착각 — final은 참조만 고정한다

static final이라 상수처럼 보이고, 상수는 안전하다고 느낀다. 여기가 첫 번째 오해다.

final은 "이 변수에 다른 객체를 다시 대입할 수 없다"는 뜻일 뿐,
"이 객체의 내용이 바뀌지 않는다"는 뜻이 아니다
착각 final이니까 안전하다
private static final List<String> NAMES
        = new ArrayList<>();

NAMES = new ArrayList<>();  // 컴파일 에러
NAMES.add("alice");         // 통과!
// 내용물은 얼마든지 바꿀 수 있다
사실 안전을 결정하는 것은 타입의 불변성
private static final List<String> NAMES
        = List.of("alice", "bob");

NAMES = List.of();      // 컴파일 에러
NAMES.add("carol");   // 런타임 예외 — 못 바꾼다
// 불변이므로 static 공유가 오히려 정석
같은 계열의 착각 세 개 — 묶어서 기억한다 ① final이니까 안전하다 → 재대입만 막는다. ② private이니까 안전하다 → private은 다른 클래스의 접근을 막는 것이지 다른 스레드의 접근을 막는 것이 아니다. 접근 제어자와 동시성은 아무 관계가 없다. ③ 읽기만 하니까 안전하다 → format()은 이름이 "읽기"처럼 보여도 내부적으로 쓴다. 메서드 이름이 아니라 구현이 상태를 바꾸는지가 기준이다.

3. 내부 구조 — Calendar라는 작업대 하나

"스레드 안전하지 않다"는 말을 외우는 것과 왜 그런지 구현으로 아는 것은 다르다. 후자여야 처음 보는 클래스를 만났을 때도 판단할 수 있다.

SimpleDateFormat(정확히는 부모인 DateFormat)은 인스턴스 필드로 Calendar calendar 하나를 들고 있다. 그리고 format()과 parse()는 이 하나의 Calendar를 작업대(scratch space)로 쓴다. 결과를 바로 만들어 반환하는 게 아니라, 중간 결과를 이 작업대에 쌓았다가 다시 읽어서 최종 결과를 만든다.

여기서 파생되는 판별 기준 — 처음 보는 클래스에도 쓴다

"결과를 즉석에서 만들어 반환하는가, 아니면 자기 필드에 중간 결과를 쌓았다가 읽는가"

후자면 공유하면 안 되는 객체다. SimpleDateFormat·Calendar·DecimalFormat·MessageDigest·Matcher가 전부 후자다. 반대로 DateTimeFormatter·Pattern·String은 호출마다 지역 상태만 쓰고 자기 필드를 건드리지 않으므로 공유가 정석이다.

4. 두 스레드가 겹치는 순간 — format · parse 타임라인

이 절의 두 그림이 이 문서에서 가장 중요한 그림이다. 답변할 때도 이 타임라인을 말로 그려 주는 것이 "안전하지 않습니다"를 열 번 말하는 것보다 낫다.

4-1. format() — 예외 없이 결과가 뒤섞인다

4-2. parse() — 여기서는 예외가 튈 수도 있다

실패의 3형태 — 이 순서로 외운다 (위험한 순서다)

① 조용히 틀림
가장 흔하고 가장 위험
남의 날짜가 응답·DB에 그대로 들어간다. 흔적이 남지 않는다.
② 가끔 예외
그나마 운이 좋은 경우
NumberFormatException 등. 스택 트레이스라도 남는다 — 대신 "일시적 오류"로 오분류되기 쉽다.
③ 대부분 정상
그래서 발각되지 않는다
경합 구간이 마이크로초라 대다수 호출은 멀쩡히 동작한다. 이것이 ①·②를 감춘다.
면접에서 강조할 문장: "예외가 나는 쪽이 오히려 다행인 케이스입니다"

5. "가끔만 난다"가 이 버그를 무섭게 만든다

경합이 실제로 겹치는 구간은 마이크로초 단위다. 두 스레드가 하필 그 짧은 구간에 겹쳐 들어와야 사고가 난다. 그래서 이 코드는 우리가 가진 방어선을 전부 통과한다.

같은 코드가 환경에 따라 다르게 보인다
상황결과놓치는 이유
단위 테스트 (단일 스레드)100% 통과경합할 상대가 없다
로컬 수동 테스트100% 통과요청을 한 번에 하나씩 보낸다
코드 리뷰그냥 넘어간다컴파일되고 테스트도 통과하니 이상 신호가 없다
운영 (초당 수십~수백 건)하루에 몇 건, 몇십 건씩 조용히 틀린다실패의 대부분이 예외가 아니라 잘못된 값이다
"가끔 틀린다" (이 버그)
  • 배포가 무사히 나간다
  • 몇 주 뒤 데이터가 이미 오염된 뒤 드러난다
  • 재현이 안 되니 예외마저 "일시적 오류"로 분류되어 재시도 로직에 묻힌다
  • 발견 시점에 복구 방법이 새로운 문제로 따라온다
더 나쁜 쪽은?
"항상 틀린다" (차라리 나은 쪽)
  • 첫 요청에서 바로 발각된다
  • 배포 전에 막힌다
  • 재현이 100%라 원인 규명이 즉시 끝난다
  • 오염된 데이터가 없다
이 유형은 테스트로 잡는 버그가 아니라 리뷰어의 머릿속 모델로 잡는 버그다

6. 해법 4종 — 가변 제거 · 공유 제거 · 격리 · 직렬화

원인이 "가변 객체를 여러 스레드가 공유한다"이므로, 고치는 방향도 논리적으로 셋뿐이다 — 가변을 없애거나, 공유를 없애거나, 스레드별로 격리하거나. 여기에 "접근을 직렬화한다"(synchronized)를 더하면 실무에서 마주치는 선택지 넷이 전부 나온다.

6-1. 대안 ① DateTimeFormatter — 가변 상태 자체를 없앤다 (1순위)

Before 가변 + 공유
public class DateUtils {
    private static final SimpleDateFormat SDF =
            new SimpleDateFormat("yyyy-MM-dd HH:mm:ss");
    // 내부에 Calendar 작업대를 하나 두고
    // 호출마다 거기에 쓰고 → 읽는다.

    public static String format(Date date) {
        return SDF.format(date);   200개가 한 책상
    }
}
After ① 불변 + 공유 (안전)
public class DateUtils {
    private static final DateTimeFormatter FMT =
            DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
    // 불변 객체다. 포맷 도중 자기 필드에 중간 결과를
    // 쌓지 않고 호출마다 지역 상태만 쓴다.

    public static String format(LocalDateTime dt) {
        return dt.format(FMT);   static 공유가 정석
    }
}

java.time 계열(LocalDateTime, Instant, DateTimeFormatter)은 전부 불변으로 설계됐다. 불변 객체란 생성된 뒤 내부 상태가 절대 바뀌지 않는 객체를 말한다. 상태가 안 바뀌면 덮어쓸 것도 없으니 동시 접근이라는 개념 자체가 성립하지 않는다.

여기서 반드시 짚어야 할 것 — static이 문제였던 게 아니다 DateTimeFormatter도 똑같이 static final로 선언했는데 안전하다. 즉 문제는 "가변 + 공유"라는 조합이었고, 가변을 없애면 공유는 아무 문제가 아니게 된다. 오히려 매번 만드는 게 낭비라서 static 공유가 정석이다. 이 대비를 말할 수 있으면 "static은 나쁘다"고 외운 사람과 즉시 구별된다.

트레이드오프: 사실상 없다. 비용은 마이그레이션 노동뿐이다. Date를 쓰는 레거시 API 경계가 있으면 Date.toInstant() / Date.from(Instant)로 변환 계층을 두면 된다. 신규 코드에서는 고민할 이유가 없다.

6-2. 대안 ② 매번 새 인스턴스 — 공유를 없앤다 (가장 단순)

After ② 호출할 때마다 새로 만든다 — 공유 자체를 제거
public static String format(Date date) {
    // 지역 변수이므로 스레드마다 각자의 스택에 각자의 인스턴스를 갖는다.
    // 다른 스레드가 접근할 경로가 아예 없다.
    return new SimpleDateFormat("yyyy-MM-dd").format(date);
}

가장 이해하기 쉽고 틀릴 여지가 없는 방법이다. 정확성만 보면 완벽하다. 트레이드오프는 할당 비용이다 — SimpleDateFormat 생성자는 패턴 문자열을 파싱해 내부 구조를 만들고 Calendar와 NumberFormat까지 함께 생성하므로, 문자열 하나 만드는 것치고는 무거운 편이다.

다만 이 비용을 과대평가하지 않는 것도 실력이다 요청당 몇 번 부르는 정도라면 DB 조회 한 번에 비하면 무시할 수준이고, 짧게 살다 죽는 객체는 GC가 가장 잘 처리하는 부류다(젊은 세대에서 거의 공짜로 회수된다). 실제로 문제가 되는 것은 수만 건 루프 안에서 매번 만드는 것 같은 핫 패스뿐이다. 선택 기준: 호출 빈도가 낮거나 보통이면 이걸로 충분하다. 측정해서 진짜 병목으로 확인됐을 때만 다음 대안을 검토한다.

6-3. 대안 ③ ThreadLocal — 스레드별로 격리한다 (레거시 핫패스용)

After ③ 스레드마다 자기 인스턴스를 갖게 한다
private static final ThreadLocal<SimpleDateFormat> SDF =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
        // withInitial: 각 스레드가 처음 get() 할 때 이 함수로 자기 인스턴스를 만든다

public static String format(Date date) {
    return SDF.get().format(date);   // 스레드마다 다른 인스턴스가 나온다
}

인스턴스를 재사용하면서도 공유는 하지 않으므로, 정확성과 할당 비용을 동시에 잡는 것처럼 보인다. 하지만 대가가 셋 따라온다.

(1) 정리 문제
값은 Thread 객체 안에 저장되므로 스레드가 살아 있는 한 값도 산다. 톰캣 워커는 재사용되며 계속 살아 있으니 remove()하지 않으면 워커 수만큼 상주하고, 재배포 시 이전 클래스로더를 붙잡아 Metaspace 누수로 번진다.
(2) 가상 스레드
"스레드당 하나씩 만들어 재사용해 비용을 아낀다"는 계산은 스레드가 200개일 때 성립한다. 수십만 개가 되면 인스턴스도 수십만 개가 되어 아끼려던 비용이 오히려 부담이 된다.
(3) 퇴행에 취약
가장 실질적인 위험이다. 다음 사람이 "이 ThreadLocal 껍데기는 왜 있지" 하고 걷어내 그냥 static 필드로 되돌리는 순간 버그가 부활한다. 불변으로 만들면 그런 퇴행이 원천적으로 불가능하다.
선택 기준 — 이 두 조건이 동시에 참일 때만 ① Date/SimpleDateFormat을 당장 걷어낼 수 없는 레거시 경계이고, ② 측정 결과 매번 생성이 실제 병목인 핫 패스일 때. 이때도 remove() 정책을 어디서 어떻게 보장할지(요청 필터의 finally, 인터셉터의 afterCompletion 등)를 함께 정해야 답이 완성된다.

7. synchronized는 왜 답이 아닌가

"공유가 문제면 락을 걸면 되지 않나"는 자연스러운 발상이고, 실제로 정확성은 확보된다. 한 번에 한 스레드만 들어가므로 작업대를 덮어쓸 일이 없다.

동작은 한다 그러나 대가가 잘못됐다
public static synchronized String format(Date date) {   JVM 전체에서 1줄
    return SDF.format(date);
}
문제는 성능이 아니라 성능의 성격이다
락이 정당한 경우
  • 본질적으로 공유해야 하는 상태가 있을 때 (계좌 잔액, 재고 수량)
  • 공유를 없앨 방법이 없고, 일관성이 처리량보다 중요할 때
  • 임계 구역이 짧고 호출 빈도가 낮을 때
이 사례가 그렇지 않은 이유
  • 공유해야 할 이유가 전혀 없다 — 포맷터는 각자 가져도 결과가 같다
  • 호출 빈도가 최상위권이라 병목 효과가 극대화된다
  • 락을 없애는 방법(불변 타입 교체)이 이미 존재한다

면접에서 synchronized를 반박하는 3단 논리

1
정확성은 인정한다. "동작은 합니다"로 시작해야 트집으로 들리지 않는다.
인정
2
대가를 특정한다. "JVM 전체에서 한 줄로 직렬화되고, 날짜 포맷은 곳곳에서 불리므로 거의 모든 요청이 이 지점을 통과합니다. 코어를 늘려도 처리량이 안 늘어납니다."
비용
3
구조를 지적한다. "무엇보다 락으로 지키려는 공유 상태 자체가 애초에 필요 없던 것입니다. 없어도 되는 공유를 만들어 놓고 락으로 지키는 구조입니다."

8. 진짜 주제 — "가변 × 공유" 2축

면접의 진짜 배점은 여기다. SimpleDateFormat 하나를 고치는 것은 지식의 문제지만, 같은 유형이 코드베이스 어디에 또 있는지 찾아내는 것은 모델의 문제다. 질문이 "어디에서 더 찾아보겠습니까"로 끝나는 이유다.

8-1. 공유 스코프는 둘이다 — static 필드와 싱글톤 빈의 인스턴스 필드

일반화의 첫 단계는 "공유되는 자리"의 목록을 정확히 아는 것이다. 자바 웹 애플리케이션에서 여러 스레드가 같은 객체를 보게 되는 경로는 크게 둘이다.

수색 대상은 이 둘뿐이다 — 범위를 좁히는 것이 실전 기술이다

① 가변 static 필드
static이면서 final이 아니거나, final이어도 타입이 가변인 것. (9절)
② 싱글톤 빈의 인스턴스 필드
필드에 요청 처리 중간 상태가 있으면 즉시 용의자. (10절)
지역 변수·파라미터는 볼 필요조차 없다 → 리뷰 범위가 수십 분의 일로 줄어든다

9. 수색 1순위 — 가변 static 필드와 단골 용의자

후보 뽑기 grep은 넓게 훑는 용도다
# ① static 인데 final 이 아닌 필드 — 재대입까지 가능한 전역 상태
grep -rn --include='*.java' -E '(private|protected|public)[[:space:]]+static[[:space:]]' . \
  | grep -v ' final '

# ② final 이어도 '타입이 가변'이면 용의자다 (final은 참조만 고정 — 2절 참고)
grep -rn --include='*.java' -E \
  'static +final +(SimpleDateFormat|DateFormat|Calendar|DecimalFormat|NumberFormat|MessageDigest|Matcher|StringBuilder|HashMap|ArrayList|HashSet)' .

grep은 후보를 넓게 뽑는 용도이고, 정확도는 IDE의 구조 검색(필드 선언만 대상으로 하는 검색)이 낫다. 중요한 것은 명령어가 아니라 무엇을 용의자로 볼지의 기준이다.

스레드 안전하지 않은 단골 — 유형별로 기억한다

포맷 계열 전반
SimpleDateFormat · DateFormat · Calendar · DecimalFormat · NumberFormat
전부 내부에 작업대를 두는 같은 구조다. 하나를 알면 나머지가 따라온다.
MessageDigest
해시를 계산할 때 데이터를 조금씩 흘려 넣고 마지막에 결과를 뽑는 누적 상태를 갖는다. 공유하면 두 스레드의 입력이 섞여 엉뚱한 해시가 나온다.
Matcher
정규식 매칭이 어디까지 진행됐는지를 담은 상태 객체다. 호출마다 새로 만들어 지역 변수로 쓴다. (Pattern은 반대다 — 아래 참고)
StringBuilder
문자를 이어붙이는 버퍼 자체가 가변 상태다. static 필드에 두면 여러 요청의 문자열이 한 버퍼에 뒤엉킨다.
HashMap · ArrayList
static final Map<…> CACHE = new HashMap<>()가 전형이다. 동시에 put하면 값이 유실될 수 있고, 리사이징이 겹치면 자료구조가 깨진다. → ConcurrentHashMap 교체 대상.
반대편 — 공유가 정석인 것들
Pattern · DateTimeFormatter · String · ObjectMapper(설정을 끝낸 뒤에는) · List.of(...)
불변이거나 상태를 안 바꾸므로 static 공유가 오히려 이득이다.
판별 기준은 하나 — "자기 필드에 중간 결과를 쌓는가?"
Javadoc이 판단 기준을 준다 — 없으면 "가변으로 간주"가 안전한 기본값 SimpleDateFormat의 Javadoc에는 "Date formats are not synchronized. … 스레드마다 별도의 인스턴스를 만들 것을 권장한다"는 취지의 문구가 명시돼 있다. 반대로 Pattern·DateTimeFormatter에는 불변이며 여러 스레드가 안전하게 사용할 수 있다는 취지의 문구가 있다. 명시가 아예 없는 서드파티 클래스라면 "안전하지 않다"로 간주하고 공유하지 않는 것이 기본값이다 — 틀렸을 때의 비용이 양쪽으로 대칭이 아니기 때문이다(잘못 공유하면 데이터 오염, 안 공유하면 약간의 할당 비용).

10. 수색 2순위 — 싱글톤 빈의 인스턴스 필드

SimpleDateFormat을 static으로 두는 것과 정확히 같은 사고가 여기서 난다. 다만 겉모습이 평범한 서비스 코드라 훨씬 발견하기 어렵다.

Before 요청 처리 중간 상태를 필드에 둔 정산 서비스
@Service
public class SettlementService {

    private final MerchantRepository merchantRepository;

    // 여기부터가 문제다. @Service 는 싱글톤이므로 이 필드들은
    // 모든 요청 스레드가 공유하는 '하나의' 변수다 — static 과 다를 게 없다.
    private Merchant currentMerchant;      // 지금 처리 중인 가맹점
    private List<Row> buffer = new ArrayList<>();
    private long totalAmount;

    public Report build(SettlementRequest req) {
        currentMerchant = merchantRepository.find(req.merchantId());
        buffer.clear();                    // 다른 요청이 모아둔 행을 지운다
        totalAmount = 0;

        for (Payment p : loadPayments(req)) {
            buffer.add(toRow(p));          // 여러 스레드가 같은 리스트에 동시에 add
            totalAmount += p.amount();     읽기-더하기-쓰기 3단계
        }
        return new Report(currentMerchant, List.copyOf(buffer), totalAmount);
    }
}

무슨 일이 벌어지는지 타임라인으로 보자. 가맹점 A와 가맹점 B의 정산 요청이 동시에 들어온 상황이다.

고치는 방향은 단순하다. 중간 상태를 필드에서 스택으로 내린다.

After 요청 처리 중간 상태를 전부 지역 변수로 옮긴다
@Service
public class SettlementService {

    // 필드에는 '주입받은 협력자'와 '불변 설정'만 남긴다.
    // 이 둘은 생성 후 바뀌지 않으므로 공유되어도 안전하다.
    private final MerchantRepository merchantRepository;
    private static final DateTimeFormatter FMT =
            DateTimeFormatter.ofPattern("yyyy-MM-dd");   // 불변이라 static 공유 OK

    public Report build(SettlementRequest req) {
        // 지역 변수는 스레드마다 각자의 스택에 만들어진다.
        // 다른 스레드가 접근할 경로가 아예 없으므로 동기화가 필요 없다.
        Merchant merchant = merchantRepository.find(req.merchantId());
        List<Row> rows = new ArrayList<>();
        long total = 0;

        for (Payment p : loadPayments(req)) {
            rows.add(toRow(p, FMT));
            total += p.amount();          // 지역 변수이므로 += 도 안전하다
        }
        return new Report(merchant, rows, total);
    }
}

점검 기준을 한 문장으로

요청 처리 중간 상태가 필드에 있으면 즉시 용의자다.

13. 꼬리질문 셀프 테스트 (15문항)

질문만 먼저 보고 소리 내어 답해 본 뒤 펼친다. 답이 30초 안에 나오지 않으면 해당 절로 돌아간다.

SimpleDateFormat이 왜 스레드 안전하지 않은지 구현으로 설명해 보세요.핵심힌트: "안전하지 않다"를 외운 것과 "왜"를 아는 것은 다르다 (→ 3절)

부모인 DateFormat이 인스턴스 필드로 Calendar를 하나 들고 있고, format()·parse()가 그 하나를 작업대(scratch space)로 쓰기 때문이다. 결과를 즉석에서 만들어 반환하는 게 아니라 중간 결과를 작업대에 쌓았다가 다시 읽는다.

format(Date)는 ① calendar.setTime(date)로 작업대에 날짜를 올리고 ② 거기서 연·월·일·시·분·초를 하나씩 읽어 패턴대로 문자열을 조립한다. parse(String)는 방향만 반대로 ① 문자열에서 조각을 뽑고 ② calendar.clear() 후 써넣고 ③ getTime()으로 꺼낸다.

둘 다 "쓰고 → 읽는" 2단계이고, 그 사이에 상태가 작업대에 노출된 채 남는다. 작업대가 인스턴스당 하나뿐이므로 인스턴스를 공유하면 작업대를 공유하는 것이다.

작업대는 하나 더 있다. DateFormat은 숫자 변환용 NumberFormat 필드도 들고 있고, 그 실체인 DecimalFormat 역시 내부에 가변 버퍼를 갖는다. 이쪽이 NumberFormatException의 출처다.

static final인데도 위험한가요? final이 막아 주는 것 아닌가요?핵심힌트: final이 고정하는 대상은 무엇인가 (→ 2절)

final은 "이 변수에 다른 객체를 다시 대입할 수 없다"는 뜻일 뿐, "이 객체의 내용이 바뀌지 않는다"는 뜻이 아니다. 참조를 고정할 뿐 내용물을 얼리지 않는다.

private static final List<String> NAMES = new ArrayList<>();

NAMES = new ArrayList<>();   // 컴파일 에러 — final이 막는다
NAMES.add("alice");          // 통과 — 내용물은 얼마든지 바꿀 수 있다

SDF도 같다. 갈아 끼우지는 못하지만 그 객체 안의 상태는 호출될 때마다 바뀐다. 그리고 SimpleDateFormat은 바로 그 "호출될 때마다 안이 바뀌는" 방식으로 동작한다. final은 불변(immutable)이 아니라 재대입 금지다.

왜 테스트에서는 안 잡히나요? 잡으려면 어떻게 해야 하나요?핵심힌트: 비용이 싼 순서로 3가지 (→ 5·11절)

단위 테스트가 단일 스레드로 돌기 때문이다. 경쟁 상태는 두 스레드의 실행이 특정 구간에서 겹쳐야 드러나는데, 스레드가 하나면 겹칠 상대가 없다.

잡는 방법을 비용이 싼 순서로 말하면 좋다.

  1. 정적 분석으로 패턴 자체를 차단한다 (SpotBugs STCAL 계열 등). 가장 싸고 확실하다 — 실행조차 필요 없다.
  2. 동시성 유닛 테스트를 쓴다. 수십 개 스레드로 같은 포맷터를 수천 번 두들기고 결과 문자열을 검증하면, 이 정도의 좁은 경합 구간도 거의 확실히 재현된다.
  3. 부하 테스트에서 응답 데이터의 정합성까지 본다. 보통은 응답 시간과 에러율만 보는데, 이 유형은 둘 다 정상으로 나온다. 값이 맞는지까지 봐야 잡힌다.

마지막에 한 줄 덧붙인다. "재현이 어려우니 운영 로그로 발견한다"는 것은 이미 데이터가 오염된 뒤라는 뜻이고, 발견 시점이 곧 복구 비용이다.

ThreadLocal로 감싸면 되는데 왜 굳이 DateTimeFormatter로 바꾸나요?시니어 변별힌트: 대증 vs 근본 + 대가 3가지 (→ 6절)

둘의 성격이 다르다는 것부터 구분한다. ThreadLocal은 "가변 상태를 스레드별로 격리"하는 대증요법이고, DateTimeFormatter는 "가변 상태 자체를 제거"하는 근본 해법이다. 문제를 안고 관리하느냐, 문제를 없애느냐의 차이다.

ThreadLocal이 치르는 대가 셋:

  1. 정리 문제. 값은 Thread 객체 안에 저장되므로 스레드가 살아 있는 한 값도 산다. 톰캣 워커는 재사용되며 계속 살아 있으니 remove()하지 않으면 워커 수만큼의 인스턴스가 상주하고, 재배포 시 이전 클래스로더를 붙잡아 Metaspace 누수로 번진다.
  2. 가상 스레드에서 전제가 무너진다. "스레드당 하나씩 만들어 재사용해 비용을 아낀다"는 계산은 스레드가 200개일 때 성립한다. 수십만 개가 되면 인스턴스도 수십만 개가 되어 아끼려던 비용이 부담이 된다.
  3. 퇴행에 취약하다. 다음 사람이 "이 ThreadLocal 껍데기는 왜 있지" 하고 걷어내 그냥 static 필드로 되돌리는 순간 버그가 부활한다. 불변으로 만들면 그런 퇴행이 원천적으로 불가능하다.

선택 기준까지 말하면 완성이다 — Date/SimpleDateFormat을 당장 걷어낼 수 없는 레거시 경계이고 측정 결과 매번 생성이 실제 병목인 핫 패스일 때만 쓰며, 이때도 remove() 정책을 어디서 보장할지 함께 정한다.

그럼 synchronized로 감싸는 건요? 동작은 하잖아요.힌트: 성능이 아니라 "성능의 성격" (→ 7절)

정확성은 확보된다. 한 번에 한 스레드만 들어가므로 작업대를 덮어쓸 일이 없다. 문제는 성능이 아니라 성능의 성격이다.

이 메서드는 JVM 전체에서 한 줄로 직렬화된다. 워커 200개가 동시에 날짜를 포맷하려 하면 199개가 줄을 선다. 서버를 8코어로 바꿔도 이 구간의 처리량은 그대로다. 날짜 포맷은 애플리케이션 곳곳에서 아주 자주 불리는 연산이라 직렬화 구간으로 삼기에 최악의 후보다.

가장 강한 한 문장은 이거다. 이 락은 아무 이득을 사지 못한다 — 락으로 지키려는 공유 상태 자체가 애초에 필요 없는 것이었기 때문이다. 없어도 되는 공유를 만들어 놓고 락으로 지키는 구조다.

Pattern.compile()을 static으로 두는 것도 위험한가요?가산점힌트: 이 대비가 이해도를 그대로 보여준다 (→ 8·9절)

아니다. 그리고 이 대비가 이 주제의 이해도를 그대로 보여준다.

Pattern은 컴파일된 정규식을 담은 불변 객체다. 매칭 과정에서 자기 상태를 바꾸지 않으므로 static 공유가 오히려 정석이다. 정규식 컴파일은 비싼 작업이라 매 호출마다 Pattern.compile()을 부르는 쪽이 진짜 성능 문제다.

위험한 것은 pattern.matcher(input)이 돌려주는 Matcher 쪽이다. Matcher는 "지금 몇 번째 글자까지 매칭했는지", "그룹별로 무엇이 잡혔는지" 같은 진행 상태를 담은 가변 객체다. 공유하면 안 되고, 호출마다 새로 만들어 지역 변수로 쓴다.

// 올바른 사용: Pattern은 static 공유, Matcher는 매번 새로
private static final Pattern EMAIL = Pattern.compile("^[\\w.]+@[\\w.]+$");

public boolean isValid(String input) {
    return EMAIL.matcher(input).matches();   // Matcher는 지역에서 만들어 지역에서 버린다
}

즉 규칙은 "static이 나쁘다"가 아니라 "불변은 공유해도 되고, 가변은 공유하면 안 된다"이다. 8절의 2축 질문이 그대로 적용된 사례다.

스프링 싱글톤 빈은 인스턴스가 하나인데 왜 대부분 문제가 없나요?핵심힌트: 싱글톤이라서 안전한 게 아니다 (→ 10절)

빈이 상태를 갖지 않기 때문이다(stateless). 싱글톤이라서 안전한 게 아니라 무상태라서 안전하다는 구분이 답의 핵심이다.

통상의 서비스 빈 필드에는 생성자로 주입받은 다른 빈 참조와 설정값만 있다. 둘 다 생성 후 바뀌지 않는다. 요청 처리에 쓰이는 값들은 전부 파라미터와 지역 변수, 즉 스레드마다 따로 있는 스택 위에 있다. 그래서 여러 스레드가 같은 인스턴스의 메서드를 동시에 실행해도 서로 건드릴 것이 없다.

필드에 요청 처리 상태를 넣는 순간 static SimpleDateFormat과 정확히 같은 유형의 함정이 된다. "인스턴스가 하나이고 스레드가 여럿"이라는 조건이 똑같기 때문이다.

상태가 꼭 필요하면 순서대로 검토한다. 지역 변수로 내리는 것이 1순위 → 요청 스코프 빈(@Scope("request")) → 진짜 공유해야 하면 AtomicLong·ConcurrentHashMap 같은 동시성 안전 구조 → 여러 인스턴스에 걸쳐 정확해야 하면 DB나 Redis로 내보낸다.

AI 생성 코드에서 이런 유형을 리뷰할 때의 체크 순서를 말해 주세요.시니어 변별힌트: 개별 지적이 아니라 "순서"를 말한다 (→ 11·12절)

개별 지적이 아니라 순서를 말하는 것이 "유형으로 아는" 답변이다.

  1. 공유 스코프부터 본다. 새로 등장한 static 필드와 빈의 인스턴스 필드를 먼저 훑는다. 지역 변수는 볼 필요가 없으므로 검토 범위가 크게 줄어든다.
  2. 그 타입이 가변인지 확인한다. Javadoc에 스레드 안전성 명시가 없으면 가변으로 간주한다. "명시가 없으면 안전하지 않다고 본다"가 안전한 기본값이다.
  3. 가변 + 공유가 확인되면 해법을 서열대로 고른다. 불변 대체재(java.time, 불변 컬렉션) → 공유 제거(지역 변수화) → 격리(ThreadLocal) → 동기화 순.
  4. 재발을 막는다. 같은 패턴이 다시 들어오지 않게 정적 분석 룰을 CI에 추가한다.

이 네 단계(스코프 → 가변성 → 해법 서열 → 재발 방지)를 말하면 한 사례를 고치는 사람이 아니라 유형을 관리하는 사람으로 읽힌다. 톤도 중요하다 — "AI가 틀린 코드를 준다"가 아니라 "AI가 주는 코드 중 이 유형은 사람 눈으로 걸러지지 않으니 자동화된 관문이 필요하다"로 정리하는 편이 낫다.

parse()에서 왜 하필 NumberFormatException이 나나요? 날짜 파싱인데요.가산점힌트: 작업대는 하나가 아니다 (→ 3·4절)

날짜 문자열을 파싱하는 일의 대부분이 실은 "숫자 파싱"이기 때문이다. "2026-01-15"에서 2026, 01, 15를 뽑는 것은 DateFormat이 들고 있는 NumberFormat(실체는 DecimalFormat)의 일이고, 이 객체 역시 내부에 자릿수를 모으는 가변 버퍼를 갖는다. 두 번째 작업대인 셈이다.

한 스레드가 자릿수를 모으는 도중에 다른 스레드가 그 버퍼를 초기화하면, 말이 안 되는 입력을 파싱한 꼴이 된다 — "multiple points"처럼 소수점이 두 개인 문자열이나 빈 문자열이 만들어져 NumberFormatException이 튀고, 인덱스가 어긋나 ArrayIndexOutOfBoundsException이 나기도 한다.

면접에서 중요한 것은 예외 이름이 아니다. 같은 코드가 어떤 때는 예외를 던지고, 어떤 때는 조용히 틀린 값을 돌려주고, 대부분의 경우에는 멀쩡히 동작한다는 비결정성이 핵심이고, 그래서 스택 트레이스가 있는 예외는 오히려 운이 좋은 경우라고 덧붙이면 좋다.

static final Map<String, X> CACHE = new HashMap<>()는 무엇이 문제인가요? ConcurrentHashMap으로 바꾸면 끝인가요?시니어 변별힌트: 자료구조를 바꿔도 안 풀리는 게 하나 남는다 (→ 9절)

먼저 문제부터. HashMap은 동시에 put하면 값이 유실될 수 있고, 리사이징이 겹치면 내부 자료구조 자체가 깨진다. final이 지키는 것은 참조뿐이라 아무 도움이 안 된다.

ConcurrentHashMap으로 바꾸면 "개별 연산의 안전성"은 해결된다. put·get·computeIfAbsent 하나하나는 원자적으로 동작한다.

그래도 남는 것이 둘 있다.

  • 복합 연산은 여전히 안전하지 않다. if (!map.containsKey(k)) map.put(k, v);는 두 연산 사이에 다른 스레드가 끼어들 수 있다. 이런 건 putIfAbsent나 computeIfAbsent 한 번의 호출로 바꿔야 한다.
  • 맵에 담긴 값이 가변이면 원점이다. ConcurrentHashMap<String, List<X>>에서 꺼낸 ArrayList를 여러 스레드가 고치면 똑같은 사고다. 안전한 것은 맵이지 그 안의 값이 아니다.

그리고 캐시라면 질문이 하나 더 붙는다 — 제거 정책이 없는 static 맵은 그 자체가 메모리 누수다. 무한히 자라는 캐시는 Caffeine 같은 크기·만료 정책이 있는 캐시로 옮기는 것이 정답에 가깝다.

totalAmount += p.amount() 한 줄은 왜 별도의 문제인가요? AtomicLong으로 바꾸면 되나요?힌트: 3단계 복합 연산 + 그런데 애초에 필드일 이유가 있나 (→ 10절)

+=는 한 줄처럼 보이지만 "읽기 → 더하기 → 쓰기"의 3단계 복합 연산이다. 두 스레드가 같은 값을 읽고 각자 더해 쓰면 한쪽의 증가분이 통째로 사라진다. (합계가 틀리는 방향도 항상 "작아지는 쪽"이라 정산에서는 특히 조용히 넘어가기 쉽다.)

volatile을 붙여도 해결되지 않는다. volatile은 가시성(다른 스레드가 최신 값을 본다)만 보장하고 원자성(3단계가 쪼개지지 않는다)은 보장하지 않기 때문이다.

AtomicLong으로 바꾸면 증가 연산 자체는 원자적이 된다. 하지만 이 사례에서 진짜 답은 "애초에 필드일 이유가 없다"이다. 이 합계는 요청 하나에 속한 중간 계산값이므로 지역 변수 long total로 내리면 동기화도 원자 연산도 필요 없다. AtomicLong은 진짜로 요청들 사이에 공유해야 하는 값(예: 애플리케이션 전체 처리 건수 카운터)일 때 쓴다.

이미 조용히 틀린 데이터가 저장된 걸 나중에 알았습니다. 어떤 순서로 대응하겠습니까?시니어 변별힌트: 코드 수정은 1번이 아니다 (→ 5절)

이 유형의 진짜 비용은 버그 수정이 아니라 오염된 데이터의 복구다. 순서로 말한다.

  1. 출혈 차단. 문제 코드를 먼저 고쳐 배포한다(DateTimeFormatter 교체 또는 지역 변수화). 오염이 계속 쌓이는 동안 조사해 봐야 대상 범위가 계속 늘어난다.
  2. 오염 구간 특정. 그 코드가 배포된 시점부터 수정 배포 시점까지가 후보 구간이다. 배포 이력으로 시간 경계를 먼저 자른다.
  3. 오염 레코드 식별. 값이 스스로 모순되는지로 찾는다 — 예를 들어 결제일 < 주문일, 정산 합계 ≠ 명세 합계, 동일 배치 내 날짜가 특정 값으로 몰림 같은 신호다. 원본(로그·원장·외부 시스템 응답)이 남아 있으면 대사(reconciliation)가 가장 확실하다.
  4. 복구. 원본이 있으면 재계산해 정정하고, 없으면 영향 범위를 고객·회계 쪽에 알린다. 조용히 덮는 선택지는 없다.
  5. 재발 방지. 정적 분석 룰 추가 + 같은 유형의 다른 지점 수색(2축 질문으로 코드베이스 훑기).

면접에서 이 답의 가치는 "발견 시점이 곧 복구 비용"이라는 인식을 보여 준다는 데 있다. 그래서 1순위 방어선은 사후 추적이 아니라 CI의 정적 분석이라는 결론으로 연결하면 앞뒤가 맞는다.

DateTimeFormatter는 불변이라는데, 그럼 타임존이나 로케일은 어떻게 바꾸나요?가산점힌트: 불변 객체가 설정을 바꾸는 유일한 방법

바꾸지 않는다. 바꾼 새 인스턴스를 돌려받는다. withZone(...), withLocale(...)는 자기 자신을 수정하는 setter가 아니라 "그 설정만 다른 새 DateTimeFormatter"를 반환하는 메서드다. 원본은 그대로 남는다.

private static final DateTimeFormatter BASE =
        DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");

// 반환값을 받아야 의미가 있다 — 원본 BASE는 전혀 바뀌지 않는다
DateTimeFormatter seoul = BASE.withZone(ZoneId.of("Asia/Seoul"));
BASE.withZone(ZoneId.of("Asia/Seoul"));  // 흔한 실수: 반환값을 버리면 아무 일도 안 일어난다

이 "변경 대신 새 인스턴스 반환" 패턴이 불변 객체가 스레드 안전한 이유 그 자체다. 아무도 기존 객체를 건드리지 않으니 덮어쓸 것이 없다. String·LocalDate·Instant가 전부 같은 규약을 따르고, 그래서 "반환값을 버리면 아무 일도 안 난다"는 실수도 같은 계열로 묶어서 기억하면 된다.

코틀린으로 짜면 이 함정이 없어지나요?힌트: object·companion object가 무엇인지 생각해 보라

없어지지 않는다. 오히려 이름만 바뀐 채 그대로 있다.

  • object / companion object의 프로퍼티는 자바의 static 필드와 같은 공유 스코프다. object DateUtils { val SDF = SimpleDateFormat("yyyy-MM-dd") }는 문제의 코드와 완전히 동일한 함정이다.
  • val은 final과 같다. 재대입만 막고 내용물은 얼리지 않는다. 코틀린에서 안전한 것은 val이라서가 아니라 그 타입이 불변일 때다.
  • @Service 코틀린 클래스의 var 프로퍼티도 싱글톤 빈의 가변 인스턴스 필드다. 자바와 똑같이 위험하다.

코틀린이 실제로 주는 이점은 기본값이 안전한 쪽이라는 것뿐이다 — listOf(...)가 읽기 전용 리스트를 돌려주고 val이 기본 권장이라 가변을 쓰려면 var·mutableListOf로 명시해야 한다. 가변임이 코드에 드러나므로 리뷰에서 눈에 띌 확률이 올라갈 뿐, 언어가 공유 가변 상태를 막아 주지는 않는다.

"가상 스레드에서 ThreadLocal의 전제가 무너진다"는 게 정확히 무슨 뜻인가요?시니어 변별힌트: 절약의 계산식이 무엇이었는지 되짚는다 (→ 6절)

ThreadLocal 캐싱의 이득은 "스레드 수 << 호출 수"라는 전제 위에서만 성립한다. 워커가 200개인 플랫폼 스레드 모델에서는 인스턴스 200개를 만들어 수백만 번의 호출에 재사용하므로 압도적으로 이득이다.

가상 스레드는 요청마다 하나씩 만들고 끝나면 버리는 모델이다. 스레드가 수십만 개가 되면 ThreadLocal 값도 수십만 개가 만들어지고, 각 스레드는 그 값을 몇 번 쓰지도 못하고 함께 사라진다. "만들어 재사용한다"가 "요청마다 새로 만든다"와 사실상 같아지고, 여기에 ThreadLocal 조회 비용과 메모리 부담만 얹힌다.

그래서 결론이 뒤집힌다 — 가상 스레드 환경에서는 ThreadLocal 캐싱이 "최적화"가 아니라 "그냥 매번 새로 만드는 것보다 나쁠 수 있는 선택"이 된다. 이런 식으로 미래에 전제가 무너질 수 있는 최적화라는 점이, 불변 대체재를 1순위로 두는 또 하나의 이유다.

한 줄 요약
SimpleDateFormat이 위험한 이유는 내부에 Calendar 작업대를 하나 두고 호출마다 거기에 중간 결과를 쌓았다 읽는 구조이기 때문이고, 이것을 static으로 공유하면 톰캣 워커들이 그 작업대를 서로 덮어써서 예외 없이 남의 날짜가 응답에 실리거나 가끔씩만 NumberFormatException이 튀는 — 그래서 테스트로도 에러율 그래프로도 안 잡히는 — 사고가 난다. 해법은 격리(ThreadLocal)나 직렬화(synchronized)보다 가변 상태를 아예 없애는 DateTimeFormatter가 1순위이며, 무엇보다 이 문제의 정체는 static도 날짜도 아닌 "가변 상태 × 공유 스코프"라는 유형이므로 — 스프링 빈은 싱글톤이라 그 인스턴스 필드가 static과 같은 공유라는 점까지 포함해 — 코드베이스 전체를 그 2축으로 훑고, 마지막에는 정적 분석 룰로 재발을 막는다.
