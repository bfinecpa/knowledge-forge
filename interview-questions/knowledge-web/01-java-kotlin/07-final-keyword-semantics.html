final의 세 가지 얼굴 — 변경 가능 지점을 의도적으로 줄이는 어휘
붙는 자리마다 금지 대상이 다르다 — 클래스=상속, 메서드=재정의, 변수=재할당 · 그리고 이 문서의 중심은 "final 참조 ≠ 불변 객체" 하나다

면접 질문: "final 키워드가 클래스/메서드/변수에 붙었을 때 각각 어떤 의미인가요?"

핵심 관전 포인트 — final은 붙는 위치마다 금지 대상이 다르다 — 클래스에 붙으면 상속 금지, 메서드에 붙으면 재정의 금지, 변수에 붙으면 재할당 금지. 셋의 공통 정신은 "여기는 바뀌지 않는다"를 컴파일러에게 선언해 나중에 코드를 읽는 사람과 최적화기와 프레임워크가 그 사실에 기댈 수 있게 만드는 것이다. 이 주제의 중심은 "final 참조 ≠ 불변 객체" 하나다 — 객체를 담은 변수 칸에 실제로 들어 있는 것은 객체가 아니라 힙 어딘가를 가리키는 주소값이고, final이 잠그는 것은 그 주소 칸이지 그 주소가 가리키는 상자가 아니다. 그래서 final List에도 add가 그대로 되고, 진짜 불변을 원하면 final 위에 불변 컬렉션 또는 방어적 복사를 얹고 클래스까지 final로 봉인하는 세 겹이 필요하다. 여기서 파생되는 세 가지가 실무 변별점이다 — 람다가 지역변수를 값으로 복사해 가기 때문에 원본이 바뀌면 어느 쪽이 진짜인지 정할 수 없어 effectively final을 요구한다는 것, CGLIB은 대상 클래스를 상속한 자식을 만들어 메서드를 재정의하는 방식이라 final 메서드에 붙은 @Transactional이 예외 하나 없이 조용히 무시된다는 것, 그리고 final 필드에는 JMM이 별도 보장을 주어 생성자가 정상 종료하면 this가 새지 않는 한 다른 스레드에도 완성된 값이 보인다는 것이다.
  • 1
    세 자리를 한 문장으로 자릅니다. final은 붙는 위치마다 금지 대상이 다릅니다 — 클래스=상속 금지, 메서드=재정의 금지, 변수=재할당 금지. 셋의 공통 정신은 같습니다. "여기는 바뀌지 않는다"를 컴파일러에게 선언해서, 읽는 사람도 최적화기도 프레임워크도 그 사실에 기대어 판단할 수 있게 만드는 것입니다. 금지가 목적이 아니라, 금지해서 얻는 단언이 목적입니다.
  • 2
    가장 중요한 구분을 바로 붙입니다. final 참조는 불변 객체가 아닙니다. 객체 변수 칸에 든 것은 객체가 아니라 힙 주소값이고, final이 잠그는 것은 그 칸이지 그 주소가 가리키는 상자가 아니기 때문입니다. 그래서 final List에 add·clear가 전부 통과합니다. 진짜 불변은 ①필드 final + ②불변 컬렉션·방어적 복사 + ③클래스 final의 세 겹으로만 완성됩니다.
  • 3
    여기서 파생되는 실무 세 가지로 마무리합니다. 람다는 지역변수를 값으로 복사해 가는데 원본 스택 프레임은 메서드가 끝나면 사라지므로 effectively final을 요구하고, CGLIB은 대상 클래스를 상속한 자식을 만들어 재정의하는 방식이라 final 메서드의 @Transactional이 예외 없이 조용히 꺼지며, final 필드에는 JMM이 안전 발행 보장을 주어 생성자가 정상 종료하고 this가 새지 않으면 다른 스레드도 완성된 값만 봅니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "final 키워드가 클래스/메서드/변수에 붙었을 때 각각 어떤 의미인가요?"

출제 의도 — 사소해 보이지만, "변경 가능 지점을 의도적으로 줄이는 습관"이 있는지를 드러낸다. 코드 리뷰에서 동료의 가변 상태를 지적할 수 있는 최소 어휘다. 문법 암기를 넘어 "final 참조 ≠ 불변 객체" 구분과 불변이 주는 실익(스레드 안전, 추론 용이)까지 말할 수 있는지를 본다.

즉 세 줄짜리 정의를 묻는 질문이 아니다. 정의는 10초면 끝나고, 진짜 질문은 그다음 "그래서 final List는 불변인가요?"에서 시작한다. 여기서 문법을 외운 사람과 메모리 그림을 가진 사람이 갈린다.

이 질문의 정체 — "세 자리를 아느냐"가 아니라 "final이 정확히 무엇을 잠그는지 아느냐"다.
세 자리 정의는 표 한 장이면 끝난다. 변별은 변수 칸에 든 것이 객체가 아니라 주소값이라는 그림과, 거기서 기계적으로 따라 나오는 세 갈래(람다 캡처 · CGLIB 프록시 · JMM 안전 발행)에서 난다.

이렇게 답하면 반쪽이다

  • "상수를 만들 때 씁니다" — static final 하나만 떠올린 답. 클래스·메서드 자리를 아예 못 짚는다.
  • "final이면 값을 못 바꿉니다" — 가장 흔한 위험한 요약. 못 바꾸는 것은 변수 칸이지 객체의 값이 아니다. 이 문장을 쓰면 바로 final List 반례가 들어온다.
  • "final 컬렉션은 불변이라 스레드 안전합니다" — 정합성 사고로 이어지는 오답. 여러 스레드가 같은 ArrayList에 add하는 코드가 그대로 남는다.
  • "람다에서는 final이어야 한대요"에서 끝 — 규칙만 알고 이유를 모른다. "왜죠?"에 스택 프레임과 값 복사가 안 나오면 암기로 들린다.
  • 프록시 이야기가 안 나옴 — final이 실무에서 실제로 사고를 내는 유일한 자리를 모르는 것이다.
  • "성능 때문에 붙입니다" — 근거가 약한 통념. JIT가 이미 하는 일을 final의 공으로 돌리면 되묻기에 무너진다.

이 문서가 채워 주는 것

  • 변수 칸 vs 힙 상자 그림 — 모든 답의 출발점. 이 그림 하나에서 나머지가 전부 유도된다.
  • "금지 → 보장" 짝 — 자리마다 무엇을 못 하게 만들어서 무엇을 단언할 수 있게 되는가.
  • String이 final인 진짜 이유 — 문자열 풀·HashMap 키·보안 검사가 무엇에 기대고 있는지.
  • 세 겹 불변 공식 — final만으로 부족한 이유와 경계에서 복사하는 자리.
  • 람다 캡처 타임라인 — "왜 안 되지"가 아니라 "허용하면 정답이 없어진다".
  • CGLIB 상속 구조 한 장 — final 메서드가 왜 예외도 없이 조용히 꺼지는지.
  • JMM 재배치 타임라인 — 반쪽짜리 객체가 보이는 순간과 final이 그것을 막는 지점.
  • static final 인라이닝 — "공통 모듈만 재배포했는데 옛날 값"의 정체.

이 문서를 관통하는 한 문장

final은 화살표를 잠그고, 상자 안은 놔둔다

객체를 담은 변수 칸에 실제로 들어 있는 것은 객체가 아니라 힙 주소값이다. final이 고정하는 것은 그 칸이므로 "다른 상자를 가리키게 만들 수 없다"까지가 보장의 전부다. 상자 안에서 벌어지는 일은 final의 관할이 아니다. 그래서 final List에 add가 되고, 진짜 불변은 상자 자체를 불변으로 바꾸는 두 번째 겹과 자식이 가변성을 덧붙이지 못하게 봉인하는 세 번째 겹이 있어야 완성된다.

0-1. 답변 흐름 한 장 — 이 순서를 지키면 질문이 끝난다

1. 전제 — 변수 칸에 든 것은 객체가 아니라 주소다

final이 정확히 무엇을 잠그는지 이해하려면 먼저 이 사실 하나를 확정해야 한다. 이 절만 제대로 세워 두면 이 문서의 나머지는 전부 여기서 유도된다.

자바에서 객체를 담은 변수에 실제로 들어 있는 것은 객체 자체가 아니라, 그 객체가 힙 어디에 있는지를 가리키는 주소값이다. 이 주소값을 참조(reference)라고 부른다.

이 절에서 가져갈 문장 하나

참조형 변수에 든 것은 객체가 아니라 객체가 있는 곳의 주소다

면접에서 final List가 불변이냐는 질문을 받으면 답을 외워서 말하는 대신 이 그림을 말로 그리면 된다. "변수 칸에는 주소가 들어 있고 final은 그 칸을 잠그는 것이라, 상자 안은 그대로 열려 있습니다." 그림을 가진 사람은 이 질문의 변형(배열·record·Map·필드 주입)에도 전부 같은 방식으로 답한다.

3. 클래스의 final — String이 봉인된 진짜 이유

금지되는 것
extends 불가

이 클래스를 상속한 자식 타입 자체를 만들 수 없다. 컴파일 에러다.

그래서 얻는 것
"이 타입이면 반드시 이렇다"

이 클래스가 지키기로 한 규칙을 자식이 우회할 수 없다는 확신이다.

왜 자식이 규칙을 깰 수 있는지부터 보자. 자식은 부모의 메서드를 재정의할 수 있고, 부모 타입 자리에는 어디든 자식이 들어갈 수 있다. 그래서 String을 받는 메서드가 실제로는 재정의된 가짜 String을 받게 되는 상황이 원리적으로 가능해진다.

"String은 불변"이라는 보장은 필드 final만으로 완성되지 않는다

클래스가 final이어야 완성된다. 자식이 가변성을 덧붙일 수 있으면 그 보장은 "이 클래스에 한해서"라는 단서가 붙어 버리고, 단서가 붙은 보장은 String을 받는 쪽에서 쓸 수 없다 — 받는 쪽은 그것이 진짜 String인지 자식인지 구분할 방법이 없기 때문이다.

3-1. before / after — 값 객체를 열어 두면 무슨 일이 생기는가

Before필드만 final, 클래스는 열려 있다
public class Money {              // 상속 가능
    private final long amount;   // 필드는 잠갔다

    public Money(long amount) { this.amount = amount; }

    public long amount() { return amount; }  // 재정의 가능
}

// 자식이 부모의 보장 "밖"에 새 상태를 만든다
public class FakeMoney extends Money {
    private long fake;                // 가변 상태 추가

    public FakeMoney(long a) { super(a); }

    public void set(long v) { this.fake = v; }
    @Override public long amount() { return fake; }
}

// 받는 쪽은 이것이 진짜 Money인지 알 수 없다

public final class Money {        // 상속 불가
    private final long amount;
    private final String currency;

    public Money(long amount, String currency) {
        this.amount = amount;
        this.currency = currency;

    public long amount() { return amount; }
}

public interface Priced { Money price(); }

public final class DiscountedItem implements Priced {
    private final Money base;      // 갖고 있는다(합성)
    private final int percent;

    public Money price() {
        return new Money(base.amount() * (100 - percent) / 100,
                         "KRW");
    }
}
// 봉인하되 확장 지점은 인터페이스로 열어 준다
봉인은 "확장 금지"가 아니라 "확장 통로의 교체"다면접에서 "상속을 막으면 확장이 안 되지 않나요?"라는 되물음이 반드시 온다. 답은 "상속이라는 통로를 닫고 인터페이스 + 합성이라는 통로를 연다"이다. 상속은 부모의 내부 구현에 자식이 결합되지만, 합성은 공개된 계약(인터페이스)에만 의존하므로 부모 내부가 바뀌어도 안 깨진다. 봉인과 확장 지점 제공은 한 세트로 말해야 완성된 답이다.

4. 메서드의 final — 흐름의 이 부분은 고정

금지되는 것
@Override 불가

상속 자체는 허용하되 특정 메서드만 잠근다. 클래스 final보다 훨씬 좁은 봉인이다.

그래서 얻는 것
"순서가 계층 전체에서 같다"

그 메서드가 정한 절차와 순서가 어떤 자식에게도 동일하다는 보장이다.

대표적인 자리가 템플릿 메서드 패턴이다. 전체 흐름은 부모가 고정하고, 갈리는 부분만 abstract 메서드로 구멍을 낸다. 이때 뼈대 메서드에 final을 붙이지 않으면 패턴이 성립하지 않는다 — 자식이 뼈대를 통째로 갈아치울 수 있기 때문이다.

코드템플릿 메서드 — final이 붙는 자리와 구멍이 뚫리는 자리
public abstract class AbstractPaymentGateway {

    // final: "로깅 -> 호출 -> 검증 -> 변환" 이 순서 자체가 정책이다.
    // 자식이 로깅을 건너뛰거나 검증 순서를 바꾸면 감사 요구가 깨지므로 잠근다.
    public final PayResult pay(PayRequest request) {
        log(request);
        PgResponse response = callPgApi(request);   // 이 구멍만 자식 몫
        validate(response);
        return toResult(response);
    }

    protected abstract PgResponse callPgApi(PayRequest request);
}

final이 없으면 자식이 pay를 통째로 재정의해서 로깅과 검증을 빼먹을 수 있다. 그러면 부모가 "모든 PG 호출은 로그가 남는다"고 단언할 근거가 사라진다.

메서드 final은 자리를 가려서 쓴다

붙이는 자리

  • 템플릿 메서드의 뼈대 — 순서가 곧 정책인 흐름
  • 불변식을 지키는 검증·계산 — 자식이 우회하면 규칙이 깨지는 것
  • 생성자가 호출하는 메서드 — 재정의되면 초기화가 끝나기 전의 자식 메서드가 불려 필드가 기본값인 채로 동작한다

붙이면 안 되는 자리

  • 스프링 빈의 public 메서드 — AOP가 침묵 실패한다(10절). 이 문서에서 실제 사고가 나는 유일한 자리다.
  • JPA 엔티티의 접근자 — 지연 로딩 프록시가 재정의로 동작한다
  • 테스트에서 대역으로 바꿔야 하는 메서드 — 상속 기반 모킹이 막힌다

"생성자가 호출하는 메서드는 final이거나 private이어야 한다"는 규칙은 따로 외워 둘 값어치가 있다. 부모 생성자는 자식 필드가 초기화되기 전에 실행되므로, 그 안에서 재정의된 메서드를 부르면 자식의 필드가 전부 기본값(0/null)인 상태로 자식 코드가 돌아간다.

5. 변수의 final — 화살표를 잠근다

금지되는 것
두 번째 대입

필드든 지역변수든 파라미터든, 정확히 한 번 대입되고 나면 그 뒤의 대입은 컴파일 에러다.

그래서 얻는 것
"이 이름의 대상은 안 바뀐다"

이 이름이 가리키는 대상이 도중에 바뀌지 않는다. 내용물 이야기가 아니다.

private final OrderRepository orderRepository;      // 여기서는 값을 안 넣었다 (blank final)

public OrderService(OrderRepository orderRepository) {
    this.orderRepository = orderRepository;         // 생성자에서 딱 한 번 대입
}

public void reconfigure(OrderRepository other) {
    this.orderRepository = other;                   // 컴파일 에러 — 두 번째 대입은 불가
}

여기서 정확히 무엇이 잠기는지를 1절의 그림 위에 얹어 봐야 한다. 변수 칸에 들어 있는 것은 주소값이었다. final은 그 칸의 값을 못 바꾸게 한다. 다시 말해 "다른 객체를 가리키게 만들 수 없다"는 뜻이다.

판정 규칙 — 등호 왼쪽에 그 변수가 혼자 있는가

items = ... → 차단  ·  items.무엇이든(...) → 통과

변수 이름 뒤에 점(.)이 찍히는 순간 그것은 final의 관할 밖이다. 점 뒤에서 벌어지는 일은 객체의 문제이지 변수의 문제가 아니기 때문이다. 배열도 똑같다 — arr = new int[3]은 막히고 arr[0] = 9는 통과한다. 대괄호도 점과 같은 편이라고 기억하면 된다.

그래서 얻는 보장의 정확한 크기변수 final이 주는 것은 "이 이름이 가리키는 대상이 도중에 바뀌지 않는다"이다. 이것은 디버깅에서 매우 유용한 보장이다 — 어떤 필드를 추적할 때 "중간에 다른 객체로 갈아끼워졌을 가능성"을 아예 후보에서 지울 수 있기 때문이다. 다만 "그 대상의 내용물이 안 바뀐다"와는 전혀 다른 말이고, 이 구분이 이 문서의 중심이라 절을 따로 뗀다(7절).

6. 람다와 effectively final — 값을 복사해 가기 때문이다

지역변수를 람다나 익명 클래스 안에서 쓰려고 하면 그 변수는 final이거나 사실상 final(effectively final)이어야 한다는 제약을 만난다.

public Runnable make() {
    int count = 0;
    Runnable r = () -> System.out.println(count);
    count = 1;        // 컴파일 에러: 람다에서 참조한 지역변수는 final이거나 사실상 final이어야 한다
    return r;
}
effectively final의 정의final 키워드를 안 붙였지만 실제로 한 번도 재할당되지 않아서, 컴파일러가 final로 취급해 주는 변수다(Java 8+). 사실상(effectively) final이라는 이름이 그 뜻 그대로다. 그래서 실무에서는 키워드를 안 붙여도 재할당만 안 하면 대부분 그냥 통과한다.

6-1. 왜 이런 제약이 있는가 — 지역변수가 어디에 사는지를 보면 나온다

지역변수는 스택 프레임 안에 산다. 스택 프레임은 메서드 호출 하나마다 만들어졌다가 그 메서드가 끝나면 통째로 사라지는 메모리 구역이다. 반면 람다로 만든 객체는 힙에 살면서 메서드가 끝난 뒤에도 살아남는다 — 위 코드처럼 반환되기도 하고, 다른 스레드에서 나중에 실행되기도 한다.

6-2. 복사본이 생긴 뒤에 원본이 바뀌면 — 정답이 없어진다

같은 람다 안인데 왜 필드는 자유롭고 지역변수는 막히는가 — 사는 곳이 다르기 때문이다.
캡처 대상사는 곳람다가 접근하는 방식재할당이유
지역변수 · 파라미터스택 프레임값을 복사해서 보관금지 (effectively final 필요)메서드가 끝나면 원본이 사라져 복사밖에 방법이 없고, 복사 후 원본이 바뀌면 어느 쪽이 진짜인지 정할 수 없다
인스턴스 필드힙 (객체 안)this 참조를 캡처해 매번 원본을 읽음자유객체가 살아 있는 한 필드도 사라지지 않으므로 따라갈 원본이 항상 있다
static 필드힙 (클래스 단위)클래스를 통해 매번 원본을 읽음자유같은 이유. 클래스가 언로드되지 않는 한 존재한다

"필드는 되는데 지역변수는 왜 안 되지?"의 정답 한 줄

사는 곳이 다르다 — 지역변수는 값이 복사되고, 필드는 원본을 계속 읽는다

그래서 필드 캡처는 편한 대신 위험하다는 짝까지 알아 두면 좋다. 람다가 다른 스레드에서 나중에 실행될 때, 필드는 그 시점의 최신 값을 읽으므로 값이 바뀌어 있을 수 있고 동기화 문제도 그대로 따라온다. 지역변수 캡처가 컴파일 에러로 막히는 것과 달리, 필드 캡처는 아무 경고 없이 통과한다 — 조용한 쪽이 더 위험하다는 점은 이 문서 10절과 같은 구조다.

7. 중심 구분 — final 참조는 불변 객체가 아니다

이 문서에서 딱 하나만 가져간다면 이 절이다.
5절의 그림을 한 문장으로 요약하면 이렇다 — final은 변수 칸의 주소값을 고정할 뿐, 그 주소가 가리키는 객체의 내용물에는 아무 힘도 미치지 않는다. 
private final List<OrderItem> items = new ArrayList<>();

items = new ArrayList<>();   // 컴파일 에러 — 화살표를 다른 상자로 옮기는 행위. final이 막는 건 이것뿐이다
items.add(newItem);          // 통과 — 상자 안에 물건을 넣는 행위. final과 무관하다
items.clear();               // 통과 — 상자를 전부 비워도 final은 침묵한다

final List는 불변 리스트가 아니다

코드 리뷰에서 가장 흔한 착각이고, 자바에서 가장 자주 오해되는 지점 중 하나다. 이 오해가 위험한 이유는 "불변이니까 스레드 안전하다"까지 연쇄로 따라오기 때문이다 — 여러 스레드가 같은 final ArrayList에 add하는 코드가 "안전하다고 믿는 상태로" 남는다.

7-1. 진짜 불변 객체는 세 겹이다

그럼 밖에서 손댈 수 없는 객체를 만들려면 무엇이 더 필요한가. final 필드 위에 두 겹을 더 얹어야 한다.

Beforefinal만 믿고 내부 리스트를 그대로 주고받는다
public class Order {
    private final List<OrderItem> items;

    public Order(List<OrderItem> items) {
        this.items = items;      // 호출자가 넘긴 리스트를 그대로 들고 있는다
    }                            // 호출자도 같은 리스트의 참조를 계속 갖고 있다

    public List<OrderItem> getItems() {
        return items;           // 내부 참조를 그대로 밖으로 내보낸다
    }
}

// 밖에서 이렇게 하면 주문 내용물이 증발한다
order.getItems().clear();

// 넣어 준 쪽에서도 뚫린다
List<OrderItem> mine = new ArrayList<>(...);
Order order = new Order(mine);
mine.add(evilItem);          // order 내부도 함께 바뀐다
After들어올 때 복사해 불변화하고, 클래스까지 봉인
public final class Order {          // (3) 자식이 가변성 못 덧붙임
    private final List<OrderItem> items;   // (1) 화살표 고정

    public Order(List<OrderItem> items) {
        // (2) 들어오는 순간 복사해 불변 리스트로 만든다.
        //     복사이므로 호출자가 원본을 나중에 바꿔도
        //     우리 것은 안 바뀌고, 불변이므로 밖으로 나간 뒤
        //     수정 시도는 예외로 즉시 드러난다.
        this.items = List.copyOf(items);
    }

    public List<OrderItem> getItems() {
        return items;    // 이미 불변이라 그냥 반환해도 안전
    }
}

// order.getItems().clear() -> UnsupportedOperationException
// mine.add(...)            -> order 내부에는 영향 없음
1
필드를 final로 — 화살표 고정
이 이름이 다른 상자를 가리키게 되는 일을 막는다. 여기까지가 final 혼자 할 수 있는 전부다.
2
가리키는 객체를 불변으로 — 상자 봉인 여기가 실무 핵심
경계(생성자)에서 List.copyOf로 복사한다. 복사여서 호출자가 들고 있는 원본과 끊기고, 불변이어서 밖으로 나간 뒤의 수정 시도가 예외로 드러난다. 두 성질을 한 번에 얻는 것이 요점이다.
3
클래스를 final로 — 우회로 봉인
자식이 가변 필드를 추가하거나 접근자를 재정의해 보장을 무너뜨리는 길을 막는다. String이 이 세 겹을 다 갖춘 표준 사례다.
!
그래도 남는 것 — 얕은 복사의 한계
List.copyOf가 하는 복사는 얕은 복사다. 리스트라는 상자는 새로 만들어지지만 그 안의 OrderItem들은 복제되지 않고 주소값만 옮겨진다. 그래서 OrderItem에 세터가 있으면 order.getItems().get(0).changeQuantity(999)로 여전히 뚫린다. 완전한 방어는 원소 타입까지 불변일 때 성립한다.
"불변처럼 보이는" 네 가지를 구분한다 — 어디까지 막아 주는가가 전부 다르다.
형태재할당컬렉션 내용 변경원본 쪽 변경이 비치는가원소 내부 변경한 줄 평
final List<T> items = new ArrayList<>()차단가능—가능불변이 아니다. 가장 흔한 오해
Collections.unmodifiableList(src)—차단(예외)비친다 — 원본에 add하면 뷰도 커진다가능뷰일 뿐이라 경계 방어로는 부족
List.copyOf(src) / List.of(...)—차단(예외)안 비친다 (복사본)가능경계에서 쓸 기본형. 얕은 복사 한계는 남음
final 필드 + List.copyOf + 원소도 불변 + 클래스 final차단차단안 비친다차단완전한 불변. String·값 객체가 여기

8. 그래서 final 필드가 실무에서 무엇을 벌어 주는가

① 컴파일 에러로 만든다
생성자 주입과 짝을 이뤄 의존성 누락을 빌드 시점에 잡는다
② 추론 비용을 줄인다
"이게 중간에 바뀌나?"를 추적할 필요가 없어진다
③ 스레드 안전의 절반
"공유 + 가변" 조합에서 가변 쪽을 줄인다

8-1. 생성자 주입과 짝을 이뤄 의존성 누락을 컴파일 에러로 만든다

@Service
public class SettlementService {
    private final OrderRepository orderRepository;   // final이라 반드시 대입돼야 한다

    public SettlementService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}

필드가 final이면 모든 생성자에서 반드시 값을 채워야 하므로, 의존성을 하나 추가하고 생성자에 넣는 것을 잊으면 그 자리에서 컴파일이 실패한다. 그리고 빈이 완성된 뒤에 누군가 의존성을 바꿔 끼울 가능성이 원천 차단된다.

Before필드 주입 — final을 쓸 수 없다
@Service
public class SettlementService {

    @Autowired private OrderRepository orderRepository;
    @Autowired private LedgerClient ledgerClient;

    // 문제 1) final을 못 붙인다
    //   → 객체를 먼저 만들고 나중에 리플렉션으로 값을 밀어 넣는
    //     방식이라 "생성자에서 한 번만 대입"과 양립할 수 없다.

    // 문제 2) 완성된 뒤에도 누가 바꿔 끼울 수 있다
    public void setLedger(LedgerClient c) { this.ledgerClient = c; }

    // 문제 3) 의존성이 하나 늘어도 컴파일은 그대로 통과한다
    //   → 누락은 기동 시점이나 런타임 NPE로 미뤄진다.
}

// 순수 자바 테스트에서 객체를 만들 방법이 없다
new SettlementService();   // 의존성이 전부 null인 껍데기가 만들어진다
After생성자 주입 — final이 규율을 강제한다
@Service
public class SettlementService {

    private final OrderRepository orderRepository;
    private final LedgerClient ledgerClient;

    // 생성자가 하나면 @Autowired 생략 가능
    public SettlementService(OrderRepository orderRepository,
                             LedgerClient ledgerClient) {
        this.orderRepository = orderRepository;
        this.ledgerClient = ledgerClient;
    }

    // 이득 1) 의존성을 추가하고 생성자를 안 고치면 컴파일 실패
    // 이득 2) 완성 후 교체 불가 — 세터를 만들려 해도 컴파일 에러
    // 이득 3) 필드가 많아지면 "이 클래스 일이 너무 많다"는
    //        신호가 생성자 인자 수로 눈에 보인다
}

// 테스트에서 대역을 그냥 넣어 주면 된다
new SettlementService(fakeRepo, fakeLedger);
@Autowired 필드 주입은 final을 쓸 수 없다는 점 자체가 필드 주입을 피할 이유 중 하나다필드 주입은 객체를 먼저 만들고 나중에 리플렉션으로 값을 밀어 넣는 방식이라, "생성자에서 한 번만 대입"이라는 final의 요구와 양립하지 않는다. 즉 "편해서 필드 주입을 쓴다"의 대가가 final이 주는 보장 전부다 — 컴파일 시점 누락 검출, 교체 불가, 그리고 9절의 JMM 안전 발행까지 함께 포기하게 된다.

8-2. 읽는 사람의 추론 비용을 줄인다

final 필드는 "생성 시점의 값이 곧 이 객체의 평생 값"이다. 그래서 이 필드를 쓰는 코드를 읽을 때 "이게 중간에 어디선가 바뀌지는 않나"를 추적할 필요가 없다. 500줄짜리 클래스에서 필드 하나를 추적하는 데 드는 시간을 생각하면 이 보장의 값이 보인다.

코드 리뷰에서 바로 쓸 수 있는 질문

"이 필드 final 가능한데 안 붙어 있네요 — 어딘가에서 재할당한다는 뜻인가요?"

이 질문이 강력한 이유는 둘 중 하나의 답만 나오기 때문이다. "아뇨, 그냥 안 붙였습니다"면 붙이면 되고, "네, 저기서 바꿉니다"면 그 자리가 바로 숨어 있던 가변 상태다. final을 못 붙이는 필드의 목록이 곧 그 클래스의 가변 지점 목록이라는 관점으로 보면, 리뷰가 취향 논쟁이 아니라 설계 점검이 된다.

8-3. 스레드 안전의 "절반"을 가져간다

동시성 버그의 상당수는 "공유 + 가변"의 조합에서 나온다. 여러 스레드가 같은 객체를 보는데 그 객체가 도중에 바뀌기 때문이다. 상태가 아예 안 바뀌는 객체는 동기화 없이 마음껏 공유해도 안전하다. final은 이 조합에서 "가변" 쪽을 줄이는 도구다.

왜 "절반"인가

  • final이 잠그는 것은 화살표뿐이라, 가리키는 객체가 가변이면 여전히 공유 가변 상태다.
  • private final Map<String,Integer> counts = new HashMap<>()는 final이지만 전혀 안전하지 않다.
  • 나머지 절반은 7절의 겹 ②(가리키는 객체도 불변)가 채운다.

절반이 채워지면 무엇이 달라지나

  • 동기화 자체가 필요 없어진다 — 락도, volatile도, 원자 클래스도.
  • 객체를 여러 스레드·여러 캐시에 마음껏 복제·공유할 수 있다.
  • 그 근거가 JMM의 final 필드 보장이다 — 바로 다음 절이 그 이야기다.

9. final 필드의 JMM 특별 보장 — 안전 발행과 this 탈출 가산점

final 필드에는 자바 메모리 모델(JMM)이 주는 별도의 보장이 하나 더 있다. 이것이 8-3의 "안전하다"를 실제로 떠받치는 근거다.

보장의 내용 — 이 문장을 그대로 외운다

어떤 객체의 생성자가 정상적으로 끝나면, 그 객체의 final 필드에 생성자에서 넣은 값은 다른 스레드에게도 완성된 상태로 보인다

그 객체의 참조를 어떤 방식으로 넘겨받든, 심지어 동기화 없이 넘겨받아도 그렇다. 일반 필드에는 이 보장이 없다는 대비가 핵심이다.

왜 이런 보장이 따로 필요한지는 new가 실제로 어떻게 실행되는지를 보면 안다. new Money(1000, "KRW")는 한 덩어리의 동작이 아니다.

public final class Money {
    private final long amount;      // final이라 안전 발행이 보장된다
    private final String currency;

    public Money(long amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }
}

this 탈출(this escape)이 되는 코드 세 가지 — 생성자 안에서

  • 자기 자신을 리스너·콜백으로 등록 — eventBus.register(this);
  • static 필드나 공유 컬렉션에 this를 담기 — INSTANCES.add(this);
  • 내부 스레드를 시작하면서 this를 넘기기 — new Thread(this).start();

셋 다 아직 완성되지 않은 객체를 다른 스레드가 볼 수 있게 만든다. 대응은 같다 — 등록·시작은 생성자가 아니라 팩토리 메서드에서 객체를 완성한 뒤에 한다. "생성자에서는 필드만 채운다"가 그래서 좋은 규칙이다.

이 절의 결론"불변 객체는 동기화 없이 공유해도 안전하다"는 말의 JMM적 근거가 이것이라, 불변 객체의 필드는 습관적으로 final로 선언하는 것이 좋다. 반대로 말하면 final이 아닌 필드로 만든 "불변처럼 보이는 객체"는 그 근거가 없다 — 단일 스레드에서는 잘 돌다가 공유되는 순간 반쪽짜리로 보일 수 있다. 더 자세한 것은 15-jmm-happens-before 문서에서 다룬다.

10. 실무 버그 — final 메서드와 스프링 프록시 함정

10-1. 먼저 CGLIB이 무엇을 하는지 알아야 한다

스프링의 @Transactional, @Cacheable, @Async 같은 기능은 여러분이 만든 객체가 직접 수행하는 것이 아니다. 스프링이 그 객체를 감싼 대역(프록시)을 만들어 빈으로 등록하고, 호출은 전부 그 대역을 먼저 거치게 한다. 대역이 앞뒤에 트랜잭션 시작·커밋 코드를 끼워 넣고 가운데서 원본을 부르는 식이다.

이 절의 모든 함정이 이 한 문장에서 기계적으로 나온다

CGLIB은 대상 클래스를 상속한 자식 클래스를 만들어 메서드를 재정의한다

대역을 만드는 방법은 두 가지인데 스프링 부트의 기본값은 CGLIB이다. 개입 수단이 "재정의"라는 사실 하나만 붙들면, final 메서드가 왜 뚫리는지, final 클래스가 왜 기동에서 죽는지, Kotlin이 왜 플러그인을 필요로 하는지가 전부 따라 나온다.

10-2. final 메서드에 붙은 @Transactional은 조용히 무시된다

@Service
public class SettlementService {

    @Transactional
    public final void settle(Long orderId) {   // 문제 지점 — final이라 프록시가 재정의할 수 없다
        ...                                    // 트랜잭션 없이 그냥 실행된다
    }
}

무서운 것은 결과가 아니라 아무 일도 일어나지 않는다는 점이다. 예외도 나지 않고 기동도 성공한다(스프링 버전에 따라 "final이라 프록시할 수 없다"는 취지의 로그가 남기도 하지만, 애플리케이션 로그에 묻히기 쉬운 수준이다). 그래서 증상이 이렇게 나타난다.

t0
배포 — 아무 문제 없이 기동된다프록시는 만들어졌고, 다른 메서드의 트랜잭션은 정상 동작한다. 헬스체크도 통과한다.
t1
평소 요청은 전부 정상 처리된다예외가 안 나면 트랜잭션이 없어도 결과가 같기 때문이다. ★ 트랜잭션이 안 걸렸다는 사실이 아무 데도 드러나지 않는다. 통합 테스트도 초록불이다.
t2
(며칠 뒤) settle 중간에서 예외가 터진다앞부분에서 실행된 UPDATE는 이미 커밋돼 있고, 뒷부분은 실행되지 않았다. 롤백이 없으므로 데이터가 반쪽만 반영된 상태로 남는다.
t3
정산 대사에서 "금액이 안 맞는 건이 있습니다"로 처음 발견된다발견 시점에는 이미 며칠치 데이터가 오염돼 있고, 어디부터 어디까지가 오염됐는지 따로 조사해야 한다.
!
원인과 증상이 멀리 떨어져 있는 전형적인 조용한 버그
t2의 스택트레이스는 예외가 터진 그 줄을 가리킬 뿐, final 키워드를 가리키지 않는다. 조사하는 사람은 "왜 롤백이 안 됐지"를 먼저 의심하고 트랜잭션 전파 설정, 예외 타입, 자기 호출을 차례로 뒤진 뒤에야 메서드 시그니처의 final에 도달한다.

10-3. final 클래스는 오히려 낫다 — 기동할 때 터지기 때문이다

여기서 얻을 교훈은 "final을 쓰지 마라"가 아니다프록시 기반 프레임워크가 상속으로 개입하는 지점(스프링 빈의 public 메서드)에서는 final이 프레임워크 기능을 침묵 속에 꺼버릴 수 있다는 것을 알고, 그 자리만 예외로 두라는 것이다. 도메인 값 객체, DTO, 유틸리티 클래스에는 여전히 final이 기본값이어야 한다.

같은 뿌리에서 나오는 형제 함정들 — "프록시는 상속으로 개입한다"

1
final 메서드 — 재정의 불가 → 그 메서드만 조용히 원본
2
private 메서드 — 애초에 상속 대상이 아니므로 같은 이유로 가로채지지 않는다
3
자기 호출(this.method()) — 프록시를 거치지 않고 원본 안에서 직접 부르므로 가로채기 자체가 일어나지 않는다
4
Kotlin의 기본 final — allopen 플러그인이 @Component·@Transactional 붙은 클래스를 컴파일 시점에 open으로 바꿔서 해결한다. 플러그인이 빠지면 전면적인 침묵 실패가 된다

"AOP가 안 걸린다"는 증상을 만나면 이 네 가지를 순서대로 확인한다. 넷의 원인은 전부 하나 — 프록시가 개입할 수 있는 통로는 "상속한 자식이 재정의한 public 메서드를 외부에서 호출하는 경로"뿐이라는 것이다.

11. static final 상수의 컴파일 타임 인라이닝 가산점

static final에 컴파일 타임 상수(기본형이나 String 리터럴을 상수식으로 대입한 것)를 담으면, 컴파일러가 그 값을 사용하는 쪽 바이트코드에 그대로 박아 넣는다. 사용하는 쪽 .class 파일 안에는 "저 클래스의 그 필드를 읽어라"가 아니라 숫자나 문자열 자체가 들어간다.

1처음 컴파일 — 모듈 A와 B를 함께 빌드
// Const.java (모듈 A)
public class Const {
    public static final int MAX = 100;
    public static final String NAME = "old";
    public static final Integer BOXED = 100;   // Integer는 컴파일 타임 상수가 아니다
}

// Use.java (모듈 B) — Const를 참조한다
System.out.println(Const.MAX);     // 100
System.out.println(Const.NAME);    // old
System.out.println(Const.BOXED);   // 100
2Const.java만 고쳐 재컴파일 — Use는 그대로
public class Const {
    public static final int MAX = 999;
    public static final String NAME = "new";
    public static final Integer BOXED = 999;
}

// 같은 Use 를 그대로 실행하면
Const.MAX     -> 100     // 999로 바꿨는데 옛날 값이 나온다
Const.NAME    -> "old"   // 마찬가지
Const.BOXED   -> 999     // 이건 새 값이 나온다
무엇이 컴파일 타임 상수인가 — "기본형 또는 String이면서, 상수식으로 초기화된 static final"만 해당한다.
선언컴파일 타임 상수사용처 .class에 남는 것정의 모듈만 재배포하면
static final int MAX = 100;O값 100이 박힘옛날 값으로 동작
static final long T = 3 * 1000;O (상수식도 상수)값 3000이 박힘옛날 값으로 동작
static final String NAME = "old";O문자열 "old"가 박힘옛날 값으로 동작
static final Integer BOXED = 100;X (박스 타입은 객체)필드를 읽는 명령새 값 반영
static final String S = new String("old");X (new는 상수식이 아님)필드를 읽는 명령새 값 반영
static final List<String> R = List.of(...);X필드를 읽는 명령새 값 반영
static final int MAX = readConfig();X (메서드 호출은 상수식이 아님)필드를 읽는 명령새 값 반영

실무에서 이 함정이 걸리는 자리 — 여러 배포 단위가 상수를 공유할 때

공통 모듈에 public static final int MAX_RETRY = 3;을 두고 여러 서비스가 그 값을 쓰고 있다면, 공통 모듈만 새 버전으로 배포해도 각 서비스는 옛날 값으로 계속 동작한다.

대응 ① — 함께 재빌드

상수를 바꿨으면 의존하는 모든 모듈을 함께 재빌드·재배포한다. CI에서 공통 모듈 변경 시 하위 모듈 전체 빌드가 걸려 있는지 확인하는 것이 실질적인 방어다.

대응 ② — 애초에 상수로 두지 않기

런타임에 읽히는 형태(설정 파일, static 메서드 반환값, DB 값)로 뺀다. 배포 없이 바뀌어야 하는 값이라면 후자가 맞다.

판단 기준은 하나다 — "이 값이 바뀔 때 모든 사용처를 다시 빌드할 수 있는가?" 없다면 상수가 아니라 설정이다.

인라이닝은 버그가 아니라 기능이기도 하다컴파일 타임 상수만 쓸 수 있는 자리가 있다 — switch의 case 라벨과 애노테이션 속성값이 대표적이다. @RequestMapping(PATH) 같은 코드가 되는 이유가 PATH가 컴파일 시점에 값으로 확정되기 때문이다. 그 편의의 대가가 위의 배포 함정이라고 이해하면 둘이 한 몸이라는 게 보인다.

프록시 침묵 실패
CGLIB = 상속한 자식이 재정의. final 메서드는 조용히 원본 실행, final 클래스는 기동 실패. 조용한 쪽이 더 위험.
JMM 안전 발행
생성자가 정상 종료하면 final 필드 값은 다른 스레드에도 완성된 채로 보인다. 단 this 탈출이 없어야 한다.

13. 꼬리질문 셀프 테스트 — 먼저 답해 보고 펼친다

질문만 보고 소리 내어 30초 안에 답해 본 뒤 펼쳐서 대조한다. 각 답의 마지막 "정리 문장"이 면접에서 실제로 말할 형태다.

final List 필드면 그 리스트는 불변인가요?힌트: 잠긴 것은 화살표인가 상자인가 핵심

아니다. final은 변수 칸에 든 주소값을 고정할 뿐이고, 그 주소가 가리키는 객체의 내용물에는 아무 힘이 없다. items = new ArrayList<>()는 컴파일 에러지만 items.add(...), items.clear()는 전부 통과한다.

진짜 불변을 만들려면 세 겹이 필요하다. ① 필드를 final로 두고, ② 그 필드가 가리키는 객체를 불변 컬렉션(List.copyOf)으로 만들거나 방어적 복사를 하고, ③ 클래스를 final로 봉인해 자식이 가변성을 덧붙이지 못하게 한다.

들어오는 쪽도 막아야 한다는 점을 덧붙이면 좋다. 생성자에서 받은 리스트를 그대로 보관하면 호출자가 그 리스트의 참조를 계속 들고 있으므로, 나중에 호출자가 원본을 수정하면 내부 상태도 함께 바뀐다. 그래서 경계에서 복사한다.

한계까지 말하면 완성된다 — 컬렉션 복사는 얕은 복사라서 원소가 가변 객체면 원소를 통해 여전히 뚫린다. 완전한 방어는 원소 타입까지 불변일 때 성립한다.

정리 문장 — "아닙니다. final은 참조를 고정할 뿐 객체 내용은 그대로 가변입니다. 불변은 final 필드 + 불변 컬렉션(또는 방어적 복사) + 클래스 final의 세 겹이고, 그마저 얕은 복사라 원소가 가변이면 뚫립니다."

람다나 익명 클래스에서 지역변수는 왜 final(effectively final)이어야 하나요?힌트: 지역변수와 람다는 사는 곳도 수명도 다르다 핵심

지역변수와 람다의 수명이 다르기 때문이다.

지역변수는 스택 프레임에 살고 메서드가 끝나면 프레임과 함께 사라진다. 반면 람다 객체는 힙에 살면서 그보다 오래 살아남고, 나중에 다른 스레드에서 실행될 수도 있다. 그래서 자바는 람다를 만드는 시점에 지역변수의 값을 한 벌 복사해서 람다 안에 넣어 둔다(캡처).

복사본이 생긴 뒤에 원본이 바뀌면 둘 중 어느 쪽이 진짜인지 정할 수 없다. 복사본을 따르면 "분명히 바꿨는데 반영이 안 된다"가 되고, 원본을 따르려면 이미 사라진 스택 프레임을 읽어야 한다. 정답이 없는 상황 자체를 만들지 않으려고 재할당을 금지한 것이다.

effectively final은 final 키워드가 없어도 재할당이 한 번도 없는 변수를 컴파일러가 final로 취급해 주는 것(Java 8+)이라, 실제로는 키워드를 안 붙여도 대부분 통과한다.

인스턴스 필드에는 이 제약이 없다는 대비까지 말하면 이해도가 드러난다. 필드는 스택이 아니라 힙에 살아서 사라지지 않으므로, 람다가 값을 복사하는 대신 객체 참조를 통해 원본 필드를 계속 읽기 때문이다.

final 필드가 멀티스레드 환경에서 주는 특별한 보장이 있나요?힌트: new는 한 덩어리 동작이 아니다 가산점

있다. 자바 메모리 모델(JMM)이 final 필드에 한해 별도 보장을 준다.

객체의 생성자가 정상적으로 끝나면, 그 객체의 final 필드에 생성자에서 넣은 값은 다른 스레드에게도 완성된 상태로 보인다. 참조를 동기화 없이 넘겨받아도 그렇다.

왜 이 보장이 필요한지는 new의 실체를 보면 안다. new는 할당 → 생성자 실행 → 참조 대입의 3단계인데, 재배치로 참조 대입이 생성자 실행보다 먼저 보일 수 있다. 그러면 다른 스레드가 참조는 있는데 필드는 아직 기본값(0/null)인 반쪽짜리 객체를 잡는다. final 필드에 대해서는 JMM이 이 재배치를 금지해 그 상태를 원천 차단한다. 이렇게 완성된 객체만 보이게 만드는 것을 안전 발행(safe publication)이라 한다.

조건이 하나 붙는다는 것까지 말해야 정확하다 — 생성자가 끝나기 전에 this 참조가 밖으로 새면(생성자 안에서 자기를 리스너로 등록하거나 static 컬렉션에 넣거나 스레드에 넘기면) 보장이 무너진다. 이를 this 탈출(this escape)이라 한다.

정리 문장 — "불변 객체는 동기화 없이 공유해도 안전하다"는 말의 JMM적 근거가 이것이라, 불변 객체의 필드는 습관적으로 final로 선언하는 것이 좋습니다."

클래스에 final을 붙여 상속을 막는 설계는 언제 정당한가요?힌트: 트레이드오프다. 막는 근거와 여는 근거를 다 대야 한다 시니어 변별

트레이드오프 판단이므로 양쪽 근거를 다 대는 것이 좋다.

막는 쪽의 근거. 상속을 안전하게 허용하려면 자식이 어느 메서드를 재정의해도 깨지지 않도록 내부에서 자기 메서드를 어떻게 호출하는지(self-use) 구조까지 설계하고 문서화해야 한다. 그 비용을 치르지 않았다면 봉인이 정직한 선택이다 — "상속을 위해 설계하고 문서화하지 않았으면 상속을 금지하라"는 원칙이 그 뜻이다. 그리고 불변 클래스는 자식이 가변성을 추가하는 순간 보장이 깨지므로 final이 사실상 필수다(3절의 String).

여는 쪽의 근거. 10절의 프록시 문제처럼 프레임워크가 상속으로 개입하는 클래스는 final이면 안 된다. 스프링 빈이 대표적이고, 테스트에서 라이브러리 클래스를 상속해 대역을 만들어야 하는 경우도 있다.

도메인 값 객체는 봉인 기본 · 프레임워크가 프록시할 빈은 열어 둠 · 확장은 상속이 아니라 인터페이스 + 합성

정리 문장 — "자리마다 기본값이 다릅니다. 불변 값 객체는 final 기본, 프록시 대상 빈은 열어 둡니다. 상속을 봉인하는 대신 확장 지점을 인터페이스와 합성으로 열어 준다는 짝까지 갖추면 봉인이 정당해집니다."

static final 상수는 그냥 final 필드와 무엇이 다른가요?힌트: 값이 사용처 .class 안으로 들어간다 가산점

컴파일 타임 상수는 사용하는 쪽 바이트코드에 값이 박힌다는 점이 다르다.

static final에 기본형이나 String 리터럴을 상수식으로 대입하면, 컴파일러가 그 값을 사용처의 .class 파일에 직접 써 넣는다. 그래서 상수를 정의한 모듈만 새로 배포하고 사용하는 모듈을 재컴파일하지 않으면 사용처는 옛날 값으로 계속 동작한다. 실제로 int MAX = 100을 999로 바꾸고 정의 모듈만 재컴파일하면, 사용 모듈은 여전히 100을 출력한다.

박스 타입은 다르게 동작한다는 것까지 알면 정확도가 올라간다 — public static final Integer BOXED = 100;은 컴파일 타임 상수가 아니라서 인라이닝되지 않고, 정의 모듈만 다시 빌드해도 새 값이 반영된다.

정리 문장 — "여러 배포 단위가 공유하는 상수를 바꿀 때는 의존 모듈을 전부 재빌드·재배포해야 하고, 배포 없이 바뀌어야 하는 값이라면 애초에 상수가 아니라 설정이나 DB로 빼는 것이 맞습니다."

final 메서드에 붙인 @Transactional은 왜 예외도 없이 무시되나요? final 클래스는 왜 다른가요?힌트: CGLIB의 개입 수단이 곧 final이 막는 그것이다 함정

CGLIB이 대상 클래스를 상속한 자식을 만들어 메서드를 재정의하는 방식이기 때문이다. final 메서드는 재정의가 금지되므로 가로챌 방법 자체가 사라진다.

그런데 클래스 상속은 여전히 되기 때문에 프록시는 정상적으로 만들어진다. 나머지 메서드는 다 가로채지고 final 메서드만 원본 그대로 남는다. 그래서 기동도 성공하고 예외도 없다. 스프링 버전에 따라 "final이라 프록시할 수 없다"는 취지의 로그가 남기도 하지만 애플리케이션 로그에 묻히기 쉽다.

final 클래스는 오히려 낫다. CGLIB이 상속 자체를 못 하므로 프록시 생성이 실패하고 기동 시점에 예외가 난다. 배포가 실패하니 즉시 안다. 시끄럽게 실패하는 쪽이 안전하다 — final 메서드가 더 위험한 이유는 문제의 크기가 아니라 발견 시점이 늦다는 것이다.

정리 문장 — "프록시가 상속·재정의로 개입하는데 final이 그 수단을 막기 때문입니다. 클래스에 붙으면 기동 실패로 즉시 드러나고, 메서드에 붙으면 그 메서드만 조용히 원본으로 남아 예외가 터진 날 정산 불일치로 처음 발견됩니다."

Kotlin은 클래스·메서드가 기본 final인데 스프링에서는 어떻게 동작하나요?힌트: 컴파일러 플러그인이 하나 끼어 있다 시니어 변별

Kotlin은 클래스와 메서드가 기본적으로 final이고 open을 붙여야 상속·재정의가 가능하다. 그대로면 모든 스프링 빈이 프록시 불가가 된다.

그래서 스프링 부트의 Kotlin 지원 플러그인(kotlin-allopen 계열)이 @Component, @Transactional 등이 붙은 클래스를 컴파일 시점에 자동으로 open으로 바꿔 준다. 소스에는 open이 안 보이는데 바이트코드에서는 열려 있는 상태가 된다.

"코틀린으로 바꿨더니 트랜잭션이 안 걸린다"는 증상이 나오면 이 플러그인이 빠졌거나 대상 애노테이션 목록에 그 애노테이션이 없는 경우를 먼저 의심한다.

정리 문장 — "Kotlin의 기본 final이 프록시와 정면으로 충돌하므로, allopen 계열 플러그인이 스프링 애노테이션이 붙은 클래스를 컴파일 시점에 open으로 열어 줍니다. 이 플러그인이 없으면 자바에서는 안 나던 침묵 실패가 전면적으로 발생합니다."

Collections.unmodifiableList와 List.copyOf는 뭐가 다른가요?힌트: 하나는 복사본이고 하나는 원본을 덮어쓴 유리창이다 함정

unmodifiableList는 원본을 감싼 "뷰(view)"이고, List.copyOf는 진짜 복사본이다. 둘 다 수정 시도에는 UnsupportedOperationException을 던지지만, 원본이 바뀔 때의 행동이 정반대다.

unmodifiableList — 뷰

  • 원본 리스트를 그대로 참조한다.
  • 원본에 add하면 뷰에도 그대로 비친다. 뷰를 받은 쪽은 "불변인 줄 알았는데 크기가 변하는" 리스트를 잡는다.
  • 원본 참조를 가진 사람이 남아 있으면 방어가 아니다.

List.copyOf — 복사본

  • 호출 시점의 내용을 새 불변 리스트로 복사한다.
  • 원본이 나중에 어떻게 바뀌든 영향이 없다.
  • null 원소는 허용하지 않는다. 이미 불변 리스트면 구현이 복사를 생략하고 그대로 돌려주기도 한다.

정리 문장 — "unmodifiableList는 원본 변경이 그대로 비치는 뷰라 경계 방어로는 부족합니다. 경계에서는 List.copyOf로 복사하고, 그마저 얕은 복사라 원소가 가변이면 원소를 통해 뚫린다는 한계는 남습니다."

파라미터나 지역변수에 final을 붙이는 건 의미가 있나요?힌트: 컴파일러에게 주는 정보 + 읽는 사람에게 주는 정보

동작을 바꾸지는 않지만 의미는 있다. 셋으로 나뉜다.

  • 파라미터 재할당 금지 — 파라미터를 메서드 중간에 다른 값으로 덮어쓰는 코드는 디버깅할 때 "이 시점의 userId가 넘어온 그 값인가"를 매번 확인하게 만든다. final은 그 확인을 없앤다.
  • 읽는 사람에게 주는 신호 — "이 이름은 여기서 끝까지 같은 대상"이라는 단언. 긴 메서드일수록 값이 크다.
  • 람다 캡처 사전 방지 — 나중에 그 변수를 람다에서 쓸 때 재할당 때문에 컴파일이 깨지는 상황을 미리 막는다. 다만 Java 8+의 effectively final 덕분에 재할당만 안 하면 키워드 없이도 캡처된다.

실무 관행은 팀 컨벤션 문제다. 모든 지역변수에 final을 붙이면 시야 소음이 커진다는 반론이 있어서, 필드에는 기본으로 붙이고 지역변수·파라미터는 팀 규칙을 따르는 절충이 흔하다.

정리 문장 — "런타임 동작은 같고, 얻는 것은 재할당 사고 방지와 읽는 사람의 추론 비용 절감입니다. 필드의 final은 설계이고, 지역변수의 final은 스타일이라고 구분해서 말합니다."

final 필드를 리플렉션으로 바꿀 수 있나요?힌트: 된다 해도 "바꾼 값이 보인다"는 별개 문제다 시니어 변별

"할 수 있느냐"와 "해도 되느냐"와 "해도 보이느냐"가 전부 다른 질문이라는 점이 핵심이다.

1
할 수 있느냐 — JDK 버전이 올라가면서 계속 좁아졌다. static final과 record의 필드는 막혀 있고, 일반 인스턴스 final 필드도 모듈 접근 제어를 열어야 접근이 가능해진다. "예전에 되던 트릭"이지 지금도 되는 보장이 아니다.
2
해도 보이느냐 — 안 보일 수 있다. JIT는 final이라는 선언을 믿고 그 값을 상수로 접어(constant folding) 코드에 박아 둘 수 있다. 값을 바꿔도 이미 컴파일된 코드는 옛 값을 계속 쓴다. "바꿨는데 반영이 안 된다"가 아니라 어디는 반영되고 어디는 안 되는 상태가 된다.
3
JMM 보장이 깨진다 — 9절의 final 필드 안전 발행 보장은 "생성자에서 확정된 뒤 변하지 않는다"는 전제 위에 있다. 그 전제를 깨면 다른 스레드에 어떤 값이 보이는지 아무도 정의해 주지 않는다.

정리 문장 — "테스트 프레임워크나 직렬화 라이브러리 같은 인프라 코드의 영역이고, 애플리케이션 코드에서는 쓰지 않습니다. 가능하더라도 JIT의 상수 접기와 JMM 보장이 전제를 깨뜨려 결과가 정의되지 않기 때문입니다."

final 필드를 선언만 했더니 "초기화되지 않았을 수 있다"고 컴파일 에러가 납니다. 대입 규칙이 뭔가요?힌트: "정확히 한 번"의 판정 범위가 어디까지인가

값을 나중에 넣는 final 필드를 blank final이라 부른다. 규칙은 "모든 경로에서 정확히 한 번"이다.

인스턴스 final 필드
선언부 · 인스턴스 초기화 블록 · 모든 생성자 중 어디든 좋지만, 객체가 만들어지는 모든 경로에서 빠짐없이 한 번 대입돼야 한다. 생성자가 셋이면 셋 다 대입해야 하고, this(...)로 위임했다면 위임받은 쪽에서 대입한다(그 경우 위임한 생성자에서 또 대입하면 두 번이라 에러다).
static final 필드
선언부 또는 static 초기화 블록에서 한 번. 클래스 로딩 시점에 확정된다.

컴파일러는 이것을 확정 대입 분석(definite assignment)으로 검사한다. if 한쪽 갈래에서만 대입하면 "대입 안 되는 경로가 있다"고 거절하고, 양쪽 갈래 모두에서 대입하면 통과한다.

정리 문장 — "선언·초기화 블록·모든 생성자를 통틀어 어느 경로로 객체가 만들어져도 정확히 한 번이 규칙입니다. 그래서 의존성을 추가하고 생성자에 넣는 걸 잊으면 그 자리에서 컴파일이 깨지는 효과가 나옵니다."

final을 붙이면 성능이 좋아지나요?힌트: 자리에 따라 다르고, 메서드 쪽은 기대만큼이 아니다 시니어 변별

자리마다 다르고, 성능을 이유로 붙일 만한 자리는 사실상 하나뿐이다.

효과가 분명한 자리

  • static final 컴파일 타임 상수 — 값이 사용처 바이트코드에 박히고, JIT도 상수로 접어 최적화한다. 다만 11절의 배포 함정이 딸려 온다.
  • final 필드 — JMM 보장(9절) 덕분에 동기화 없이 공유할 수 있다는 것이 사실상 가장 큰 성능 이득이다.

기대만큼이 아닌 자리

  • final 메서드 · final 클래스 — "가상 호출이 정적 호출로 바뀌어 빨라진다"는 설명이 흔하지만, HotSpot은 실제로 로드된 클래스 계층을 분석해 구현이 하나뿐이면 final이 없어도 가상 호출을 없애고 인라이닝한다.
  • 그래서 성능을 이유로 메서드에 final을 붙이는 것은 근거가 약하고, 대신 10절의 프록시 부작용을 떠안게 된다.

정리 문장 — "final은 성능 키워드가 아니라 설계 키워드입니다. 성능으로 말할 수 있는 건 상수 접기와, 불변 덕분에 동기화를 안 해도 되는 것이고, 메서드 final의 호출 최적화는 JIT가 이미 해 줍니다."

effectively final 제약을 int[] holder = {0} 같은 배열 한 칸으로 우회하는 코드, 괜찮나요?힌트: 컴파일러가 막던 이유가 사라진 게 아니다 함정

컴파일은 통과하지만, 컴파일러가 막으려던 문제를 그대로 되살린 것이다. 배열 참조는 안 바뀌므로 캡처 규칙을 만족하고, 값은 holder[0]으로 얼마든지 바꿀 수 있다. 규칙의 글자는 지키고 취지는 버린 코드다.

단일 스레드 반복문이라면 동작은 한다. 문제는 같은 람다가 병렬 스트림이나 스레드풀에서 실행될 때다. 여러 스레드가 holder[0]을 동시에 읽고 쓰면 갱신 유실과 가시성 문제가 그대로 생기고, 버그는 코드가 아니라 실행 환경이 바뀔 때 나타난다.

이렇게 쓰지 않는다

  • 합계·카운트를 배열 칸에 누적하는 람다
  • forEach 안에서 바깥 컬렉션에 add하는 코드

대신 이렇게 쓴다

  • 결과를 반환값으로 — mapToLong(...).sum(), collect(...)처럼 스트림이 값을 돌려주게 만든다.
  • 정말 여러 스레드가 하나의 카운터를 갱신해야 한다면 AtomicLong·LongAdder처럼 동시성을 스스로 책임지는 타입을 쓴다.

정리 문장 — "컴파일은 되지만 캡처 규칙이 막으려던 공유 가변 상태를 되살린 우회입니다. 누적은 스트림의 반환값으로 표현하고, 불가피하면 AtomicLong처럼 동시성을 보장하는 타입을 씁니다."

record는 final과 어떤 관계인가요? record면 자동으로 불변인가요?힌트: record가 주는 것은 두 겹까지다

record는 7절의 세 겹 중 ①과 ③을 언어가 대신 해 준다. record 클래스는 암묵적으로 final이라 상속할 수 없고(③), 컴포넌트 필드는 전부 private final로 만들어진다(①).

하지만 ②는 여전히 개발자 몫이다. 컴포넌트가 List나 배열처럼 가변 객체면 그 내용물은 그대로 바뀐다. record Order(List<OrderItem> items)에서 order.items().clear()는 막히지 않는다.

그래서 컴팩트 생성자에서 방어적 복사를 넣는 것이 정석이다.

public record Order(List<OrderItem> items) {
    // 컴팩트 생성자 — 파라미터를 손보면 그 값이 필드에 대입된다
    public Order {
        items = List.copyOf(items);   // (2) 들어오는 순간 불변 복사본으로
    }
}

정리 문장 — "record는 클래스 final과 필드 final까지 자동이지만 "필드가 가리키는 객체의 불변"은 자동이 아닙니다. 가변 컴포넌트는 컴팩트 생성자에서 List.copyOf 같은 복사를 넣어야 세 겹이 완성됩니다."

public static final String[] ROLES = {"USER","ADMIN"};는 안전한 상수인가요?힌트: 배열도 객체다 함정

안전하지 않다. 자바에서 가장 유명한 "가짜 상수"다. final이 고정한 것은 배열 객체의 주소일 뿐이라, 아무나 Const.ROLES[0] = "HACKED";로 내용을 바꿀 수 있다. public이라 그 변경은 JVM 전체에 즉시 공유된다.

더 나쁜 것은 범인을 찾기 어렵다는 점이다. 값이 바뀐 시점과 이상 동작이 관측되는 시점이 멀고, 어느 코드가 바꿨는지 스택트레이스에 남지 않는다.

문제이름만 상수
public static final String[] ROLES =
        {"USER", "ADMIN"};

// 어디서든 이게 통과한다
Const.ROLES[0] = "HACKED";
개선불변 리스트로 노출
private static final String[] ROLES_ARR =
        {"USER", "ADMIN"};
public static final List<String> ROLES =
        List.of(ROLES_ARR);

// ROLES.set(...) 은 UnsupportedOperationException

정리 문장 — "배열도 객체라서 final은 주소만 고정합니다. public static final 배열은 전역 가변 상태이므로, 불변 리스트(List.of)로 노출하거나 복사본을 돌려주는 메서드로 바꿉니다."

필드에 final을 못 붙이는 상황이면 어떻게 하나요? (지연 초기화·JPA 엔티티 등)힌트: 프레임워크가 요구하는 것과 설계가 원하는 것을 분리해서 말한다

세 가지 자리를 구분해서 말하면 정확해진다.

1
JPA 엔티티 — 하이버네이트는 기본 생성자로 객체를 만든 뒤 필드를 채우고, 지연 로딩을 위해 엔티티를 상속한 프록시를 만들기도 한다. 그래서 엔티티 클래스는 final이면 안 되고, 필드도 final로 두기 어렵다. 대신 세터를 열지 않고 의미 있는 도메인 메서드로만 상태를 바꾸는 방식으로 가변 지점을 좁힌다.
2
스프링 빈 — 필드는 final로 두되 클래스는 열어 둔다. 생성자 주입을 쓰면 필드 final이 가능하고, 클래스와 public 메서드에는 final을 붙이지 않아 프록시가 동작한다. @Autowired 필드 주입은 final과 양립할 수 없다는 점 자체가 생성자 주입을 쓸 이유다.
3
지연 초기화가 꼭 필요한 값 — final을 포기하는 대신 가변 지점을 한 곳으로 몰고 그 자리에 동시성 대책을 붙인다. 캐시 성격이면 volatile + 이중 검사나 홀더 클래스(정적 중첩 클래스의 static final) 같은 정형화된 관용구를 쓴다.

정리 문장 — "프레임워크가 상속·리플렉션으로 개입하는 자리만 예외로 열고, 나머지는 final을 기본값으로 둡니다. 열어야 하는 자리에서는 final 대신 "가변 지점을 좁히고 그 자리에 규율을 붙이는 것"으로 같은 목표를 지킵니다."

30초 답변 대본 — 이 순서로 말한다

  1. 세 자리: "클래스면 상속 금지, 메서드면 재정의 금지, 변수면 재할당 금지입니다. 공통 정신은 '여기는 안 바뀐다'를 컴파일러에게 선언하는 것입니다."
  2. 중심 구분: "가장 중요한 건 final 참조가 불변 객체가 아니라는 것입니다. 변수 칸에 든 건 주소값이라 final은 화살표를 잠그고 상자 안은 놔둡니다. 그래서 final List에 add가 됩니다."
  3. 세 겹: "진짜 불변은 필드 final + 불변 컬렉션이나 방어적 복사 + 클래스 final 세 겹입니다. String이 정확히 그 조합입니다."
  4. 파생 셋: "여기서 람다의 effectively final(값 복사), final 메서드에서 조용히 꺼지는 @Transactional(CGLIB이 상속·재정의로 개입하니까), final 필드의 JMM 안전 발행이 따라 나옵니다."
  5. 실무 기본값: "그래서 필드는 final 기본, 값 객체는 클래스까지 final, 프록시 대상 빈의 클래스·public 메서드만 예외로 둡니다."

2번(주소값 그림)을 못 그리면 나머지 답이 전부 암기로 들린다. 정의는 10초, 나머지 20초를 2·4번에 쓴다.

한 줄 요약
final은 클래스에서 상속을, 메서드에서 재정의를, 변수에서 재할당을 막아 "여기는 바뀌지 않는다"를 컴파일러 수준에서 선언하는 어휘이지만, 변수의 final이 잠그는 것은 주소값이 든 변수 칸이지 그 주소가 가리키는 객체가 아니므로 final List에 add는 그대로 되고 진짜 불변은 final + 불변 컬렉션(또는 방어적 복사) + 클래스 final의 세 겹으로만 완성된다 — 여기서 파생되는 세 가지가 실무 어휘의 시작이다. 람다는 지역변수의 값을 복사해 가는데 원본 스택 프레임은 메서드가 끝나면 사라지므로 원본이 바뀌면 어느 쪽이 진짜인지 정할 수 없어 effectively final을 요구하고, CGLIB은 대상 클래스를 상속한 자식을 만들어 재정의하는 방식이라 final 메서드에 붙은 @Transactional이 예외 하나 없이 조용히 꺼지며, final 필드에는 JMM이 별도 보장을 주어 생성자가 정상 종료하고 this가 새지 않으면 다른 스레드에도 완성된 값이 보인다.
