ConcurrentHashMap 내부 — 락의 범위를 버킷 1개까지 좁히고, 읽기는 락에서 아예 빼냈다
쓰기는 빈 버킷이면 CAS · 노드가 있으면 그 버킷의 첫 노드에 synchronized, 읽기는 volatile이 주는 가시성에 기대어 무락

면접 질문: "ConcurrentHashMap은 어떻게 thread-safe를 보장하나요? Collections.synchronizedMap과의 차이는?"

핵심 관전 포인트 — 동시성 자료구조의 설계는 결국 "락의 범위를 얼마나 좁히고, 어디까지 락 없이 처리하느냐"의 문제다. Collections.synchronizedMap은 맵 전체에 락 하나를 걸어 동시에 한 스레드만 들여보내지만, ConcurrentHashMap은 쓰기를 "빈 버킷이면 CAS, 노드가 이미 있으면 그 버킷의 첫 노드에 synchronized"로 나눠 락의 범위를 버킷 1개까지 좁혔고, 읽기는 volatile이 만드는 가시성 보장에 기대어 락을 아예 없앴다. 그 대가가 약한 일관성 — 순회는 진행 중인 변경을 볼 수도 안 볼 수도 있고 size()는 근사값이다. 그리고 맵이 thread-safe해도 "읽고 판단해서 쓰는" 복합 연산은 여전히 원자적이지 않다는 것이 이 질문의 본체다.
  • 1
    쓰기의 락 범위를 버킷 1개로 좁혔습니다. 슬롯이 비어 있으면 casTabAt으로 락조차 잡지 않고 꽂고, 이미 노드가 있을 때만 그 버킷의 첫 노드 객체에 synchronized를 겁니다. 서로 다른 버킷을 건드리는 스레드는 서로 다른 객체에 락을 걸므로 아무도 기다리지 않습니다.
  • 2
    읽기는 락이 아예 없습니다. 락은 상호배제 + 가시성 두 가지를 하는 도구인데 읽기에는 가시성만 필요합니다. 그래서 Node.val·next·table을 volatile로, key·hash를 final로 두어 가시성만 확보했습니다. 그래서 get은 쓰기 경합이 아무리 심해도 블로킹되지 않습니다.
  • 3
    대가는 약한 일관성이고, 진짜 함정은 따로 있습니다. 순회는 ConcurrentModificationException을 던지지 않고 size()는 근사값인데 이건 의도된 교환입니다. 실무 사고는 "thread-safe 맵이니 안전하다"고 믿고 get 후 put 하는 복합 연산에서 나며, 그 자리에는 merge·compute·putIfAbsent를 써야 합니다.

0. 질문 + 출제 의도 · 겨냥하는 약점

질문 — "ConcurrentHashMap은 어떻게 thread-safe를 보장하나요? Collections.synchronizedMap과의 차이는?"

출제 의도 — "thread-safe 컬렉션을 쓰면 안전하다"는 착각을 갖고 있는지의 검사다. 이 착각은 부하가 걸려야만 드러나는 최악의 버그를 만든다. 평상시에는 몇 달간 멀쩡하다가 트래픽이 몰리는 날에만 카운트가 어긋나고, 재현이 안 되니 원인도 못 찾는다. 그래서 면접관은 내부 락 구조까지 정확한 동작 모델을 갖고 있는지를 본다.

약점 A"thread-safe라서 안전합니다"에서 끝나는 답 — 무엇이 원자적이고 무엇이 아닌지의 경계를 못 긋는다. 이 맵이 보장하는 단위는 "키 하나에 대한 메서드 하나"일 뿐이다(12절).
약점 B"세그먼트로 나눠서 락을 겁니다" — Java 7 지식에서 멈춘 답이다. Java 8에서 세그먼트는 제거됐고 버킷의 첫 노드 자체가 락이 됐다(5절).
약점 C"get에는 왜 락이 없나요"에 답하지 못함 — 락이 상호배제와 가시성 두 가지를 하는 도구라는 것을 모르면 여기서 막힌다. 이 맵은 그 둘을 분리했다(8절).
합격선"쓰기는 빈 버킷이면 CAS, 아니면 그 버킷 첫 노드에 synchronized. 읽기는 volatile로 가시성만 확보해 무락." 이 한 문장을 먼저 던지고, 그 대가(약한 일관성)와 진짜 함정(복합 연산)까지 이어 말하는 것.
이 문서의 전제 — 12번에서 이어진다 버킷 배열 · 해시 인덱싱 · 체이닝 · 트리화 · 리사이징이라는 기본 구조는 12 HashMap 내부 동작 문서에서 다뤘고, ConcurrentHashMap도 그 구조를 그대로 쓴다(내부는 똑같이 Node<K,V>[] table 하나다). 이 문서는 그 구조 위에 락과 CAS를 어떻게 얹었는지, 즉 동시성 처리의 차이에만 집중한다.

1. 락은 왜 비싼가 — 문제는 "문이 닫혀 있을 때"다

ConcurrentHashMap의 설계를 이해하려면 먼저 락이 정확히 무엇을 비싸게 만드는지를 알아야 한다. 여기를 건너뛰면 뒤에 나오는 CAS가 "그냥 뭔가 빠른 것" 정도로만 남는다.

synchronized는 한 번에 한 스레드만 들여보내는 문이다. 문이 비어 있을 때 들어가는 비용 자체는 크지 않다. 문제는 문이 닫혀 있을 때 생긴다. 이미 다른 스레드가 안에 있으면, 뒤에 온 스레드는 CPU를 계속 붙잡고 기다리는 게 아니라 커널에 의해 대기 상태로 내려간다. 잠드는 것이다.

락의 비용은 "잡는 값"이 아니라 "못 잡았을 때의 값"이다

경합이 없을 때

  • 문이 비어 있으면 들어가는 비용 자체는 작다
  • JVM의 락 최적화도 이 경로를 노린다

경합이 있을 때

  • 커널 개입 · 컨텍스트 저장/복원
  • 캐시가 식는다 — 다시 메모리에서 읽어야 함
  • 지키려던 작업보다 비용이 더 클 수 있다
"락이 느리다"가 아니라 "경합한 락이 느리다" — 그래서 해법은 락을 없애는 것이 아니라 경합할 자리를 줄이는 것이다

2. CAS — 예상값이 맞을 때만 바꾸는 원자 연산

CAS(Compare-And-Swap) = "이 메모리 위치의 값이 내가 예상한 값과 같으면 새 값으로 바꿔라.
다르면 아무것도 하지 마라" 를 CPU가 단 하나의 명령으로 처리해 주는 원자 연산

x86의 CMPXCHG 같은 하드웨어 명령이 실체이고, 자바에서는 Atomic* 클래스나 VarHandle을 통해 쓴다. "원자(atomic)"는 더 쪼갤 수 없다는 뜻이다 — 비교와 교체 사이에 다른 스레드가 끼어들 틈이 없고, 그 틈 없음을 소프트웨어가 아니라 CPU가 보장한다.

비유 — 화이트보드에 적힌 숫자 고치기 락 방식은 화이트보드 앞에 줄을 서서 한 명씩 들어가는 것이다. CAS 방식은 줄을 서지 않고 그냥 다가가되 "내가 아까 본 값이 아직 그대로면 고치고, 누가 이미 바꿔놨으면 손대지 않고 물러나서 다시 본다"는 규칙으로 움직이는 것이다. 아무도 없을 때는 CAS가 압도적으로 빠르고, 사람이 몰리면 물러났다 다시 오기를 반복하게 된다.
개념 코드 AtomicInteger.incrementAndGet()의 동작 원리 — CAS 재시도 루프의 원형
int current, next;
do {
    current = value;              // 1. 현재 값을 읽는다
    next    = current + 1;      // 2. 새 값을 계산한다
} while (!compareAndSet(current, next));
// 3. "아직 current 그대로면 next로 바꿔라"를 시도한다.
//    false = 그 사이 다른 스레드가 값을 바꿨다는 뜻이므로
//    잠들지 않고 곧바로 루프를 돌아 다시 읽고 다시 시도한다.

count++가 왜 이런 장치를 필요로 하는지 보면 쓰임새가 분명해진다. count++는 한 줄이지만 실제로는 "현재 값 읽기 → +1 계산 → 결과 쓰기" 세 단계이고, 두 스레드가 같은 값을 읽어버리면 증가 한 번이 사라진다. 락으로 감싸면 해결되지만 1절에서 본 블로킹 비용을 매번 치른다.

CAS에서 반드시 챙길 성질 3가지

잠들지 않는다
실패해도 커널에 내려가지 않는다. 논블로킹 / 락 프리라 부르는 이유이고, 컨텍스트 스위칭이 없다는 것이 락 대비 이득의 실체다.
항상 빠르진 않다
경합이 적으면 락보다 훨씬 싸고, 경합이 극심하면 오히려 손해다. "CAS가 락보다 항상 빠르다"는 명제는 틀렸다.
모든 Atomic의 토대
AtomicInteger·AtomicReference·LongAdder가 전부 이 위에 서 있다. 내부적으로 Unsafe/VarHandle의 compareAndSet 계열을 호출한다.
이 성질을 알아야 다음이 이해된다 — ConcurrentHashMap은 빈 버킷은 CAS, 충돌하면 락

3. CAS의 함정 — ABA 문제

CAS에는 알려진 함정이 하나 있다. 값이 A였다가 B로 바뀌었다가 다시 A로 돌아오면, CAS는 "예상값 A와 현재 값 A가 같으니 아무 일도 없었다"고 판단한다. 실제로는 두 번의 변경이 있었는데도 말이다.

ABA가 문제가 되는 곳과 안 되는 곳 — 구별해서 말해야 한다

대개 문제가 안 된다

  • 단순 카운터, 값 자체가 의미의 전부인 참조 교체
  • 이유: 값이 같으면 결과도 같기 때문

깨진다

  • "그 사이에 아무 일도 없었어야" 정확한 로직
  • 예: 락 프리 스택에서 팝한 노드를 재활용하는 경우 — 같은 주소가 재사용되면 다른 노드인데 같아 보인다
해결은 값 하나를 비교하지 말고 값 + 버전 스탬프를 함께 비교하는 것 — AtomicStampedReference

4. 비교 대상 — synchronizedMap은 무엇을 하는가

질문이 짝지어 물어보는 Collections.synchronizedMap(new HashMap<>())은 구조가 훨씬 단순하다. 평범한 HashMap을 감싸는 래퍼(wrapper)를 만들고, 모든 메서드를 synchronized 블록으로 덮은 것이다.

실제 구조의 요지 Collections.SynchronizedMap
public V get(Object key) {
    synchronized (mutex) { return m.get(key); }   // mutex = 맵 하나당 락 객체 하나
}
public V put(K key, V value) {
    synchronized (mutex) { return m.put(key, value); }
}

5. Java 7 세그먼트 락 → Java 8 버킷 락

ConcurrentHashMap의 내부는 HashMap과 마찬가지로 Node<K,V>[] table 배열 하나다. 배열의 각 칸을 버킷이라 부르고, 해시가 같은 칸에 걸린 키들은 그 칸에서 연결 리스트로 이어진다. 여기까지는 HashMap과 같다. 다른 것은 그 위에 락을 어떻게 얹느냐뿐이다.

Java 7까지의 답은 락 스트라이핑(lock striping)이었다. 스트라이프(stripe)는 줄무늬라는 뜻으로, 테이블을 여러 구획으로 나누고 각 구획에 별도의 락을 두는 기법이다. 구획 하나를 Segment라 불렀고 기본 개수는 16이었다.

가산점 — "Segment가 아직 있던데요"라는 반문에 대비 Java 8 이후에도 소스 코드에는 Segment 클래스가 껍데기로 남아 있다. 동작에는 쓰이지 않고, 예전 버전에서 직렬화한 맵을 읽을 수 있게 하는 호환용이다. 이 한 문장을 준비해 두면 반문이 나와도 흔들리지 않는다.

6. 쓰기 ① 빈 버킷이면 CAS로 끝낸다 (락 없음)

putVal()은 버킷의 상태를 먼저 보고 두 전략 중 하나를 고른다. 첫 번째는 그 칸이 비어 있는 경우다.

JDK 코드 putVal() — 빈 슬롯 경로
if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
    // 그 슬롯이 "여전히 null이면" 새 노드를 꽂는다 — 비교와 교체가 한 덩어리.
    // 락을 잡지 않으므로 컨텍스트 스위칭 비용이 0이다.
    if (casTabAt(tab, i, null, new Node<>(hash, key, value)))
        break;   // 성공. 여기서 put이 끝난다.
    // 실패했다면 그 찰나에 다른 스레드가 먼저 꽂았다는 뜻이므로
    // 루프를 다시 돌아 아래의 락 경로로 넘어간다.
}
틈이 있다 확인과 선점을 나누면
if (tab[i] == null) {          // ① 확인
    // ←←← 여기서 다른 스레드가 먼저 꽂을 수 있다
    tab[i] = new Node<>(...);   // ② 덮어쓰기
}
// 결과: 먼저 꽂힌 노드가 조용히 사라진다 (갱신 유실)
// 예외도 안 나고 로그도 안 남는다
틈이 없다 CAS로 묶으면
casTabAt(tab, i, null, new Node<>(...));
// "아직 null이면 꽂아라"가 CPU 명령 하나
// 비교와 교체 사이에 끼어들 틈이 없다
// 실패하면 false가 돌아올 뿐 — 남의 노드를
// 덮어쓰는 일은 절대 일어나지 않는다

7. 쓰기 ② 노드가 이미 있으면 그 첫 노드에 synchronized

버킷이 비어 있지 않다면 체인을 순회하며 같은 키를 찾아 값을 덮어쓰거나 꼬리에 노드를 붙여야 한다. 이건 여러 단계를 거치는 작업이라 CAS 한 번으로는 안 된다. 이때만 락을 잡는다.

JDK 코드 putVal() — 충돌 경로
synchronized (f) {            // f = 이 버킷의 첫 노드. 락의 범위가 곧 이 버킷 하나다.
    if (tabAt(tab, i) == f) { // 락을 얻기까지 기다리는 동안 head가 그대로였는지 재확인
        // 체인을 순회하며 같은 키면 덮어쓰고, 없으면 꼬리에 새 노드를 붙인다
    }
}
락의 대상이 맵도 아니고 세그먼트도 아니라 그 버킷의 첫 노드 객체라는 점이 핵심
→ 서로 다른 버킷을 건드리는 스레드들은 서로 다른 객체에 락을 걸므로 아무도 기다리지 않는다

그런데 tabAt(tab, i) == f를 다시 확인하는 이유는 짚고 넘어갈 만하다. 이 두 줄이 이 문서에서 가장 시니어스러운 지점이다.

쓰기 경로 — 세 갈래를 이 순서로 외운다

락 없음슬롯이 비었으면 → casTabAt 한 번. 성공하면 그대로 끝. 대부분의 put이 여기서 끝난다.
버킷 1개노드가 이미 있으면 → synchronized (f). 그 버킷의 첫 노드에만 락. 다른 버킷은 영향 없음.
버킷 1개표지판(ForwardingNode)을 만나면 → 기다리지 않고 helpTransfer()로 이사에 합류(10절).
한 문장으로 — "빈 버킷이면 CAS, 노드가 있으면 그 버킷의 첫 노드에 synchronized"

8. 읽기 — get에 락이 전혀 없는 이유

JDK 코드 get() — 동기화 장치가 하나도 없다
public V get(Object key) {
    // synchronized도 없고, CAS 재시도 루프도 없다. 그냥 읽는다.
    Node<K,V> e = tabAt(tab, (n - 1) & h);
    // ... 체인/트리를 따라가며 키를 비교하고 값을 반환
}

락을 안 잡는데 어떻게 안전한가. 근거는 가시성(visibility)을 락 대신 volatile로 확보했다는 데 있다.

여기서 가시성이란 한 스레드가 메모리에 쓴 값을 다른 스레드가 볼 수 있는가의 문제다. CPU 코어마다 자기 캐시를 갖고 있고 컴파일러도 값을 레지스터에 눌러 담아두는 최적화를 하기 때문에, 아무 표시 없는 일반 필드는 한 스레드가 바꾼 값이 다른 스레드에게 언제 보일지, 심지어 보이기는 할지 보장되지 않는다.

무락 읽기를 떠받치는 세 가지 선언 — 필드별로 이유가 다르다
필드선언그 선언이 하는 일
Node.val, Node.nextvolatile쓰기 스레드의 갱신이 읽기 스레드에 반드시 보인다
tablevolatile + 슬롯 접근은 tabAt()새 테이블·새 노드의 발행이 읽기 스레드에 보인다
Node.key, Node.hashfinal생성 후 절대 안 바뀜 — 안전 발행(safe publication)이 보장된다
왜 tabAt()이라는 헬퍼가 따로 필요한가 자바에서는 배열의 원소 하나하나에 volatile을 붙일 수 없다. volatile Node[] table은 "table이라는 참조 변수"가 volatile일 뿐, table[3]을 읽는 것까지 volatile 읽기가 되지는 않는다. 그래서 ConcurrentHashMap은 슬롯을 직접 읽지 않고 tabAt(tab, i)를 통해 읽는다. 이 헬퍼가 저수준 API를 써서 원소 하나에 대한 volatile 읽기에 준하는 접근을 수행한다. 슬롯에 값을 꽂을 때 쓰는 casTabAt, setTabAt도 같은 계열이다.
key·hash가 final인 것도 우연이 아니다 — 안전 발행 final 필드는 생성자가 끝나는 시점에 다른 스레드에게도 완성된 값으로 보인다는 특별한 보장을 JMM(자바 메모리 모델)으로부터 받는다. 그래서 다른 스레드가 갓 만들어진 노드를 발견하더라도 "참조는 보이는데 key는 아직 null인" 반쪽짜리 상태를 볼 수 없다.

결론적으로 읽기 스레드가 하는 일은 어느 시점엔가 실제로 유효했던 노드들을 따라가는 것뿐이고, 쓰는 쪽과 다툴 것이 없다. 그래서 get은 쓰기 경합이 아무리 심해도 절대 블로킹되지 않는다. 그리고 바로 이 성질의 대가가 11절의 약한 일관성이다.

9. size() 집계 — 카운터를 일부러 쪼갠다 (CounterCell)

원소 개수를 세는 방법으로 가장 단순한 것은 int count 필드 하나를 두고 put·remove마다 갱신하는 것이다. 그런데 이 맵에서는 그게 곧바로 병목이 된다.

이유는 2절에서 본 CAS의 성질에 있다. 모든 스레드가 같은 하나의 필드를 CAS로 갱신하면, 버킷을 아무리 잘게 쪼개 놓았어도 결국 전원이 이 필드 하나 앞에서 재시도 경쟁을 벌인다. 버킷 락을 없앤 자리에 카운터라는 새 병목을 세우는 꼴이다.

가산점 — size() 대신 mappingCount() size()는 반환 타입이 int라 원소가 Integer.MAX_VALUE를 넘으면 표현할 수 없다. Java 8부터는 long을 반환하는 mappingCount()가 있고, 대용량 맵에서는 그쪽이 권장된다.

10. 협력적 리사이즈 — 기다리는 대신 함께 옮긴다

맵이 커지면 테이블을 2배로 늘리고 모든 노드를 새 테이블로 옮겨야 한다. 이 이사 작업은 시간이 걸리는데, 그동안 다른 스레드를 전부 세워두면 그 순간만큼은 맵 전체에 락을 건 것과 다를 바 없어진다. 버킷 단위로 락을 좁혀 놓은 노력이 리사이즈 한 번에 무너지는 것이다.

ConcurrentHashMap은 이 구간을 협력 작업으로 만들었다. 이사가 끝난 버킷 자리에는 ForwardingNode라는 표지판 노드를 꽂아둔다. 해시값이 MOVED라는 특수한 음수 값이라 일반 노드와 구별되고, 새 테이블을 가리키는 참조를 들고 있다.

ForwardingNode — 표지판 하나가 하는 세 가지 일

구별

연결

11. 약한 일관성 — 버그가 아니라 설계 선택

락 없는 읽기에는 대가가 따른다. ConcurrentHashMap의 읽기 계열 동작은 약한 일관성(weakly consistent)을 가진다. 구체적으로 셋이다.

12. thread-safe 맵인데도 깨지는 것 — 복합 연산

이 문서에서 실무 사고와 가장 가까운 지점이다.

ConcurrentHashMap이 보장하는 것은 "메서드 하나하나가 원자적"이라는 것뿐이지,
"내가 쓴 코드 블록이 원자적"이라는 것이 아니다
Before 맵은 thread-safe인데 코드는 깨진다
ConcurrentHashMap<String, Integer> counter = new ConcurrentHashMap<>();

Integer c = counter.get(key);① 원자적
counter.put(key, (c == null ? 0 : c) + 1);② 원자적

// 그런데 ①과 ② 사이는 아무도 지켜주지 않는다.
// 두 스레드가 나란히 ①에서 5를 읽으면 둘 다 6을 쓰고,
// 두 번 증가시켰는데 결과는 6이 된다 — 갱신 유실.

// synchronized (map) 으로 감싸도 소용없다.
// 내부 락이 버킷 단위로 흩어져 있어 다른 스레드의
// put은 그 락을 무시하고 그대로 통과한다.
After 원자적으로 설계된 전용 메서드로 넘긴다
counter.merge(key, 1, Integer::sum);
// "없으면 1로 넣고, 있으면 기존 값과 1을 sum으로 합쳐라"가
// 버킷 락 안에서 한 번에 일어난다

Session s = sessions.computeIfAbsent(id, k -> loadSession(k));
// "확인하고 없으면 만든다"가 원자적이라
// loadSession이 중복 호출되지 않는다

Object prev = registry.putIfAbsent(key, value);
if (prev != null) { /* 다른 스레드가 이미 등록함 */ }

map.replace(key, oldValue, newValue);값이 oldValue일 때만
map.remove(key, expectedValue);값이 expectedValue일 때만

원자적 메서드 — 상황별로 짝지어 외운다

merge(k, v, fn)
누적·집계. "없으면 v, 있으면 fn으로 합쳐라". 카운터의 정답이다.
computeIfAbsent(k, fn)
지연 초기화. "없을 때만 만든다" — 중복 초기화를 막는다.
putIfAbsent(k, v)
선점 등록. 이미 있으면 기존 값을 반환하고 넣지 않는다.
compute(k, fn)
조건부 갱신·삭제. fn이 null을 반환하면 매핑이 제거된다.
replace(k, old, new)
조건부 교체. 값이 old일 때만 바꾼다 — CAS의 맵 버전.
remove(k, expected)
조건부 삭제. 값이 expected일 때만 지운다.
복합 연산이 보이면 "이걸 한 번의 호출로 바꿀 수 있나"를 먼저 묻는다
함정 — synchronizedMap과 달리 외부 락 우회가 통하지 않는다 Collections.synchronizedMap도 복합 연산의 원자성은 보장하지 않는다. 다만 그쪽은 락이 맵 하나에 하나뿐이라 synchronized (map) { ... }로 외부에서 같은 락을 잡아 묶는 우회가 가능하다. ConcurrentHashMap에는 그 우회가 통하지 않는다. 내부 락이 버킷 단위로 흩어져 있어서, 외부에서 맵 객체에 락을 걸어봐야 그 락을 존중하는 것은 나뿐이고 다른 스레드의 put은 그대로 통과한다. 해법은 우회가 아니라 전용 메서드다.
시니어 변별 포인트 — 람다는 버킷 락을 쥔 채로 실행된다 compute, computeIfAbsent, merge에 넘기는 람다는 해당 버킷의 락을 쥔 채로 실행된다. 따라서 두 가지 금기가 따라온다.
① 오래 걸리는 작업(원격 호출, 파일 I/O)을 넣으면 그 버킷이 그동안 막힌다.
② 람다 안에서 같은 맵을 다시 수정하면 안 된다 — 이미 쥔 락과 얽혀 교착이나 무한 대기로 갈 수 있다.
computeIfAbsent에 DB 조회를 그대로 넣은 코드는 실무에서 흔히 보이는데, 그것이 락 구간을 늘린다는 사실은 인지하고 써야 한다.

대조표 — 이 두 줄만 정확하면 질문의 절반은 끝난다

Collections.synchronizedMap
  • 락 1개 (맵 전체의 mutex)
  • 읽기도 락을 잡는다
  • 무관한 키끼리도 직렬화
  • 복합 연산은 synchronized (map)으로 묶을 수 있다
  • null 키·값 허용(내부가 HashMap)
VS
ConcurrentHashMap
  • 락 버킷당 1개 (빈 버킷은 CAS, 락 0)
  • 읽기는 락이 없다 (volatile)
  • 다른 버킷이면 완전 병렬
  • 복합 연산은 전용 메서드로만 해결 (외부 락 우회 불가)
  • null 키·값 금지 (NPE)

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼친다. 막히면 옆에 적힌 절로 돌아간다.

Collections.synchronizedMap과 정확히 무엇이 다른가요?힌트: 세 가지를 나눠 말한다 — 락의 개수 · 락의 범위 · 읽기의 처리 핵심

락의 개수와 범위, 그리고 읽기의 처리 방식이 다르다.

synchronizedMap은 평범한 HashMap을 감싸 모든 메서드를 하나의 락(mutex)으로 덮은 래퍼다. 읽기든 쓰기든, 서로 무관한 키든, 이 맵을 지나는 모든 스레드가 락 하나를 다툰다. 코어를 늘려도 이 맵을 통과하는 처리량은 늘지 않는다(4절).

ConcurrentHashMap은 쓰기의 락 범위를 버킷 1개로 좁혔고 — 빈 버킷은 CAS로 락조차 잡지 않는다 — 읽기는 volatile이 주는 가시성 보장에 기대어 락 없이 수행한다(6~8절).

한 가지 덧붙이면 좋다. 둘 다 복합 연산의 원자성은 보장하지 않는다. 차이는 대응 방법에 있다. synchronizedMap은 synchronized (map) { ... }로 외부에서 같은 락을 잡아 묶는 우회가 가능하지만, ConcurrentHashMap은 내부 락이 버킷 단위로 흩어져 있어 그 우회가 통하지 않으므로 merge·compute·putIfAbsent 같은 원자적 메서드를 써야 한다(12절).

get이 락 없이도 안전한 근거를 설명해주세요.힌트: 락이 하는 일은 사실 두 가지다 핵심

가시성을 락이 아니라 volatile로 확보했기 때문이다.

락은 상호배제(한 번에 하나만)와 가시성(내가 쓴 값이 남에게 보임) 두 가지를 함께 제공하는 도구인데, 읽기에는 상호배제가 필요 없고 가시성만 필요하다. 그래서 Node.val과 Node.next를 volatile로 선언해 쓰기 스레드의 갱신이 읽기 스레드에 반드시 보이게 만들었다.

table 슬롯 접근도 tabAt() 헬퍼를 통해 volatile 읽기에 준하는 방식으로 이루어진다 — 자바에서는 배열 원소 하나에 volatile을 붙일 수 없기 때문에 헬퍼가 필요하다. volatile Node[] table은 "table이라는 참조 변수"만 volatile이지 table[3] 읽기까지 volatile이 되지는 않는다.

여기에 Node.key와 hash가 final이라는 점이 더해진다. final 필드는 생성자가 끝나면 다른 스레드에게도 완성된 값으로 보인다는 보장이 있어서, 갓 만들어진 노드를 다른 스레드가 발견해도 "참조는 보이는데 key는 아직 null인" 반쪽짜리 상태를 볼 수 없다(안전 발행).

읽기 스레드는 어느 시점엔가 유효했던 노드를 따라가기만 하면 되므로 쓰기와 충돌할 일이 없고, 그래서 경합이 아무리 심해도 get은 블로킹되지 않는다.

CAS가 락보다 항상 빠른가요?힌트: 이 맵이 둘을 섞어 쓰는 이유가 곧 답이다 시니어 변별

아니다. 정답은 "경합의 정도에 따라 뒤집힌다"이다.

CAS는 실패해도 스레드를 재우지 않기 때문에 컨텍스트 스위칭 비용이 없다. 그래서 경합이 적으면 락보다 훨씬 싸다. 그런데 경합이 극심하면 재시도 루프가 계속 헛돌면서 CPU만 태운다. 이때는 차라리 잠들었다가 깨어나는 락이 낫다.

ConcurrentHashMap의 설계가 이 판단을 그대로 코드로 옮겨 놓았다. 빈 버킷은 경합이 거의 없을 자리이므로 CAS를 한 번 시도하고, 실패하거나 이미 노드가 있으면(= 경합이 있다는 신호) 곧바로 synchronized로 내려간다. 둘 중 하나를 고르는 게 아니라 상황에 따라 섞어 쓴다는 것이 요점이다(6~7절).

같은 이유로 size() 카운터도 CAS 하나로는 안 됐다. 모든 스레드가 같은 필드를 CAS하면 그 자체가 새 병목이라 CounterCell[]로 대상을 흩어야 했다(9절).

size()가 근사값이고 순회 중 예외도 안 나는데, 이건 문제 아닌가요?힌트: 정확하게 만들려면 무엇을 포기해야 하는지 되물어 본다

설계상 의도된 교환이다. 이유는 두 가지다.

첫째, 정확한 크기를 보장하려면 집계하는 동안 맵 전체의 변경을 막아야 하고, 그 순간 무락 읽기라는 이 자료구조의 존재 이유가 사라진다. Collections.synchronizedMap으로 되돌아가는 셈이다.

둘째, 동시에 변하는 맵에서 "정확한 크기"는 반환되는 순간 이미 과거다. 락을 걸고 정확히 1,000을 얻어냈어도 호출자에게 돌아가는 순간 999거나 1,002다. 비싼 값을 치르고 얻은 정확함이 즉시 무의미해진다.

ConcurrentModificationException을 안 던지는 것도 같은 맥락이다. 그 예외는 "단일 스레드용 컬렉션인데 순회 중 수정이 일어났다 — 버그다"라는 신고인데, ConcurrentHashMap에서는 순회 중 다른 스레드의 수정이 정상적이고 의도된 사용법이다. 정상 동작에 예외를 던질 이유가 없다.

실무 기준은 이렇다. 모니터링 지표·로그처럼 근사값으로 충분한 곳에는 그대로 쓴다. "정확히 N개일 때만 처리 시작" 같은 판단 근거로 size()를 쓰고 있다면 자료구조 선택이 잘못된 것이다. 가산점 대용량 맵에서는 int 범위를 넘길 수 있으므로 long을 반환하는 mappingCount()를 쓴다.

리사이즈 중에는 다른 스레드가 멈추나요?힌트: 기다리게 하는 대신 시킨다 핵심

멈추지 않는다. 오히려 이사를 돕는다.

이사가 끝난 버킷에는 ForwardingNode(해시값 MOVED, 특수한 음수)라는 표지판 노드가 꽂힌다. 이 노드는 새 테이블을 가리키는 참조를 들고 있다.

put 하러 온 스레드가 이 표지판을 만나면 리사이즈가 끝나기를 기다리는 대신 helpTransfer()를 호출해 아직 안 옮긴 버킷 구간을 자기 몫으로 받아 함께 옮긴다. 일손이 늘어 리사이즈가 빨리 끝나고, 대기하는 스레드도 생기지 않는다.

get 하러 온 스레드는 표지판이 가리키는 새 테이블로 넘어가 읽기를 계속하므로 리사이즈 중에도 읽기는 한 번도 멈추지 않는다(10절).

한 줄로 요약하면 "긴 작업 구간을 락으로 보호하는 대신, 참여자 전원이 나눠 처리하도록 만들었다"이고, 이 설계 감각이 이 자료구조 전체를 관통한다.

왜 하필 버킷의 첫 노드를 락 객체로 쓰나요? 별도의 락 객체 배열을 두면 안 되나요?힌트: 자바에서는 아무 객체나 락이 될 수 있다

된다. 실제로 Java 7까지가 정확히 그 방식(별도 락 객체를 가진 Segment 배열)이었다. Java 8이 그것을 버린 이유는 둘이다.

① 공짜다. 자바에서는 모든 객체가 모니터 락을 하나씩 갖고 있으므로, 이미 그 자리에 있는 head 노드에 synchronized를 걸면 락 전용 객체를 따로 할당할 필요가 없다. 세그먼트라는 중간 계층과 그 객체들이 쓰던 메모리가 통째로 사라진다.

② 락 단위가 최소가 된다. 별도 배열을 둔다 해도 그 배열 크기만큼만 락이 쪼개진다(Java 7은 기본 16). head 노드를 쓰면 락의 개수가 버킷 수와 같아지고, 버킷 수는 리사이즈하면 함께 늘어난다 — 맵이 커질수록 동시 쓰기 상한도 같이 커진다(5절).

대신 대가가 있다. 락 객체가 "그 자리에 있는 노드"라서 리사이즈·트리화로 교체될 수 있다. 그래서 락을 잡은 직후 tabAt(tab, i) == f로 내가 건 락이 아직 유효한지 재확인하는 코드가 반드시 따라붙는다(7절).

락을 잡은 직후 tabAt(tab, i) == f를 다시 확인하는 이유는요?힌트: 락을 기다리는 동안에도 맵은 계속 변한다 시니어 변별

내가 잡은 락이 "이미 버려진 옛 노드에 걸린 무효한 락"일 수 있기 때문이다.

순서를 따라가 보면 분명해진다. ① 슬롯을 읽어 head 노드 f를 얻는다 → ② synchronized (f)에서 다른 스레드가 락을 놓기를 기다린다 → ③ 그 대기 시간 동안 맵은 계속 변한다.

대기 중에 일어날 수 있는 일이 구체적으로 셋이다. 리사이즈가 진행되어 이 슬롯이 ForwardingNode로 교체됐거나, 트리화로 head가 TreeBin으로 바뀌었거나, remove로 head 노드가 체인에서 빠졌을 수 있다.

그 상태로 체인을 수정하면 아무도 참조하지 않는 자료구조를 고치는 셈이 된다. 내가 넣은 노드는 어느 스레드에게도 보이지 않고 조용히 사라진다 — 예외도 안 나는 갱신 유실이다.

그래서 락을 얻은 직후 "내가 락을 건 그 노드가 아직 이 슬롯의 head가 맞나"를 확인하고, 아니면 락을 풀고 바깥 for(;;) 루프로 돌아가 처음부터 다시 시도한다. "락을 잡았다 ≠ 상태가 그대로다"가 락 프리 계열 코드를 읽는 핵심 감각이다.

computeIfAbsent 안에서 DB를 조회해도 되나요?힌트: 그 람다가 어디에서 실행되는지 생각해 본다 시니어 변별

동작은 하지만 그 시간만큼 버킷이 통째로 막힌다는 사실을 알고 써야 한다.

핵심은 compute·computeIfAbsent·merge에 넘긴 람다가 해당 버킷의 락을 쥔 채로 실행된다는 점이다. 그래서 두 가지 금기가 따라온다.

  • 오래 걸리는 작업(원격 호출, 파일 I/O, DB 조회)을 넣으면 그 버킷에 해시가 걸리는 다른 키의 쓰기까지 함께 막힌다. 락 구간 = 네트워크 지연이 된다.
  • 람다 안에서 같은 맵을 다시 수정하면 안 된다. 이미 쥔 락과 얽혀 교착이나 무한 대기로 갈 수 있다.

다만 오해하면 안 되는 것이 있다. 이 원자성이 "중복 초기화 방지"라는 진짜 이득을 준다. get 후 put으로 짜면 같은 키에 대해 loadSession이 여러 번 호출되지만, computeIfAbsent는 딱 한 번만 호출됨을 보장한다.

그래서 판단 기준은 "중복 실행을 막는 값어치가 락 구간이 길어지는 대가보다 큰가"다. 순수 계산이면 그대로 쓰고, 무거운 I/O라면 값 대신 Future/CompletableFuture를 맵에 넣어 자리 선점만 원자적으로 하고 실제 로딩은 락 밖에서 수행하는 패턴을 쓴다.

ConcurrentHashMap은 왜 null 키·null 값을 허용하지 않나요?힌트: get이 null을 반환했을 때 그 뜻이 하나로 정해지는가 가산점

HashMap과 달리 null 키·null 값을 넣으면 NullPointerException이 난다. 이유는 단일 스레드에서는 풀 수 있던 모호함이 동시 환경에서는 풀리지 않기 때문이다.

map.get(k)가 null을 돌려줬다고 하자. 뜻이 둘이다 — "그 키가 없다"거나 "키는 있는데 값이 null이다". HashMap이라면 containsKey(k)를 한 번 더 불러 구별하면 된다.

그런데 동시 맵에서는 그 후속 확인이 답이 되지 못한다. get과 containsKey 사이에 다른 스레드가 그 키를 넣거나 지울 수 있어, 두 번의 호출이 서로 다른 시점의 맵을 본다. 즉 모호함을 해소할 방법이 원리적으로 없다.

그래서 null을 아예 금지해 "get이 null이면 매핑이 없다"를 예외 없는 규칙으로 고정했다. 실무 함의도 있다 — HashMap을 ConcurrentHashMap으로 갈아 끼우는 순간, null 값을 넣던 코드가 런타임에 NPE로 터진다. 값이 없음을 표현해야 한다면 Optional이나 빈 값을 뜻하는 전용 상수 객체를 넣는다.

ConcurrentHashMap을 쓰는데도 카운터 값이 틀리게 나옵니다. 원인이 뭘까요?힌트: 맵은 잘못이 없다 함정

거의 확실히 get → 계산 → put으로 짠 복합 연산이다. 이 맵이 보장하는 것은 "메서드 하나하나가 원자적"이라는 것뿐이지 "내가 쓴 코드 블록이 원자적"이라는 것이 아니다.

Integer c = counter.get(key);                  // ① 이 호출은 원자적
counter.put(key, (c == null ? 0 : c) + 1);     // ② 이 호출도 원자적
// 그런데 ①과 ② 사이는 아무도 지켜주지 않는다 → 갱신 유실(lost update)

두 스레드가 나란히 ①에서 5를 읽으면 둘 다 6을 쓴다. 두 번 증가시켰는데 결과는 6이다. 이 패턴을 검사 후 행동(check-then-act) 또는 읽고-고치고-쓰기(read-modify-write)라 부른다.

해법은 맵 내부의 한 번의 원자적 연산으로 넘기는 것이다.

counter.merge(key, 1, Integer::sum);   // 버킷 락 안에서 한 번에 일어난다

증상의 특징도 같이 말하면 좋다. 이 버그는 부하가 걸려야만 드러난다. 평상시에는 두 스레드가 같은 키를 같은 찰나에 건드릴 확률이 낮아 몇 달간 멀쩡하다가, 트래픽이 몰리는 날에만 카운트가 조금씩 모자라게 나온다(12절).

synchronized (map) { get 후 put }으로 외부에서 묶으면 되지 않나요?힌트: 그 락을 존중하는 것은 누구인가 함정

통하지 않는다. 이것이 synchronizedMap과 ConcurrentHashMap의 실무적으로 가장 중요한 차이다.

synchronizedMap은 내부에서 쓰는 락과 외부에서 잡을 수 있는 락이 같다. 그래서 synchronized (map) { ... }로 감싸면 그 블록 동안 다른 스레드의 get·put도 같은 락에 막혀 복합 연산이 실제로 원자적이 된다(Collections.synchronizedMap은 반환된 맵 자신을 mutex로 쓴다).

ConcurrentHashMap은 내부 락이 버킷 단위로 흩어져 있다. 외부에서 맵 객체에 락을 걸어봐야 그 락을 존중하는 것은 같은 규칙을 지키는 코드뿐이고, 다른 스레드의 put은 버킷 락만 잡고 그대로 통과한다. "동기화한 것처럼 보이지만 실제로는 아무것도 막지 못하는" 가장 위험한 형태의 코드가 된다.

그래서 답은 우회가 아니라 전용 메서드다 — merge, compute, computeIfAbsent, putIfAbsent, replace(k, old, new), remove(k, expected). 모든 스레드가 예외 없이 지켜야만 성립하는 규칙은 실무에서 반드시 깨진다는 점도 함께 말하면 좋다.

여러 키를 한꺼번에 원자적으로 바꿔야 하면 어떻게 하나요?힌트: 이 자료구조가 보장하는 단위가 무엇인지 되짚는다 시니어 변별

ConcurrentHashMap은 그 보장을 하지 않는다. 원자성의 단위가 "키 하나에 대한 연산 하나"이기 때문이다. 계좌 A에서 빼서 계좌 B에 더하는 식의 다중 키 트랜잭션은 이 맵의 기능 범위 밖이다.

선택지는 셋이다.

  • 함께 변해야 하는 값들을 하나의 불변 객체로 묶어 한 키에 넣는다. 그러면 compute나 replace(k, old, new) 한 번으로 원자 갱신이 된다 — 가장 먼저 검토할 답이다.
  • 외부 락으로 보호한다. 단, 그 순간 맵의 무락 이점을 상당 부분 반납하는 것이고, 모든 접근 경로가 같은 락 규칙을 지켜야 성립한다.
  • 진짜 트랜잭션이 필요하면 자료구조가 아니라 저장소의 문제다. DB 트랜잭션이나 전용 동시성 제어로 올린다.

면접에서는 "이 맵이 보장하는 단위는 키 하나입니다"라고 경계를 먼저 긋는 것이 좋은 답이다. 도구의 보장 범위를 정확히 아는 것이 그 도구를 잘 쓰는 것보다 중요할 때가 많다.

Java 8 이후인데 소스에 Segment 클래스가 아직 있던데요?힌트: 동작이 아니라 호환 가산점

동작에는 쓰이지 않는 껍데기다. 예전 버전에서 직렬화한 맵을 읽을 수 있게 하려는 호환용으로 남아 있다.

직렬화 포맷은 클래스 구조에 묶여 있어서, Java 7에서 writeObject로 저장한 ConcurrentHashMap 바이트 스트림을 Java 8 이상에서 역직렬화하려면 그 포맷이 참조하는 클래스가 존재해야 한다. 그래서 클래스만 남기고 실제 락 구조는 버킷 단위로 완전히 대체했다.

이 반문이 나왔을 때 "있긴 하지만 쓰이지 않습니다, 직렬화 호환용입니다"라고 바로 답하면, 소스를 실제로 열어봤다는 신호가 된다(5절).

ConcurrentHashMap에서도 버킷이 트리화되나요? 그러면 락은 어디에 걸리나요?힌트: 락 대상은 언제나 "그 슬롯의 첫 자리에 있는 것"이다

트리화된다. 기본 구조는 HashMap과 같아서, 한 버킷의 노드 수가 8에 이르면 레드-블랙 트리(TreeBin)로 바꿔 최악 탐색을 O(n) → O(log n)으로 방어한다. 기준도 같아서 테이블 길이가 64 미만이면 트리화 대신 테이블을 2배로 늘린다 — 테이블이 작아서 생긴 충돌은 트리화가 아니라 확장으로 푸는 것이 맞기 때문이다(12번 문서).

락은 규칙이 동일하다. 그 슬롯의 첫 자리에 있는 객체에 synchronized를 거는데, 트리화된 버킷에서는 그 자리를 TreeBin 노드가 차지하고 있으므로 락이 TreeBin에 걸린다.

이것이 7절의 재확인이 필요한 또 하나의 이유다. 락을 기다리는 사이에 그 버킷이 트리화되면 내가 락을 건 옛 head 노드는 더 이상 슬롯의 첫 자리가 아니다. 그래서 tabAt(tab, i) == f 검사에서 걸러지고 처음부터 다시 시도하게 된다.

한 줄 요약
ConcurrentHashMap은 쓰기를 "빈 버킷이면 CAS, 노드가 있으면 그 버킷의 첫 노드에 synchronized"로 나눠 락 범위를 버킷 1개까지 좁히고, 읽기는 volatile(val·next·table)과 final(key·hash)이 주는 가시성·안전 발행 보장에 기대어 락 없이 수행함으로써, 맵 전체에 락 하나를 거는 Collections.synchronizedMap과 처리량에서 갈린다 — 그 대가로 순회·size()는 약한 일관성을 갖지만 이는 무락 읽기를 지키기 위한 의도된 교환이고, 정작 실무에서 사고를 내는 것은 "thread-safe 맵이니 안전하다"고 믿고 get 후 put 하는 복합 연산이므로 그 자리에는 merge·compute·putIfAbsent 같은 원자적 메서드를 써야 한다.
