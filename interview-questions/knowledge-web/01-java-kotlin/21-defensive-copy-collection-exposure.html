핵심 관전 포인트 — 문제의 본질은 "참조 공유"다. return lines;가 돌려주는 것은 리스트의 복사본이 아니라 같은 ArrayList 객체를 가리키는 주소값이므로, 호출자와 도메인 객체가 하나의 리스트를 함께 들게 된다. 그 결과 필드가 private final이고 addLine()이 최대 개수를 검증해도, 외부는 getLines().add(...)로 그 검증을 통째로 건너뛴다 — 캡슐화는 접근 제어자가 아니라 "내부 가변 상태의 참조가 밖으로 새지 않는가"에서 완성된다. 실무에서 이 버그가 무서운 이유는 예외가 안 나기 때문이다. 외부가 리스트를 수정한 시점과 불변식이 깨진 채로 저장·정산되는 시점이 멀리 떨어져 있어서 스택트레이스가 범인을 가리키지 못한다. 방어는 반환 방식 3종의 트레이드오프로 갈린다 — 방어적 복사(new ArrayList<>, 매번 비용·완전 독립), 수정 불가 뷰(unmodifiableList, 싸지만 원본이 바뀌면 뷰도 바뀐다), 불변 복사본(List.copyOf, null 원소 불가). 여기에 얕은 복사의 한계(원소가 가변이면 원소를 통해 여전히 뚫린다), 생성자 인자도 복사해야 한다는 것, 그리고 복사한 뒤 복사본을 검증해야 TOCTOU가 안 생긴다는 순서까지가 이 주제의 전부다.

0. 질문 + 출제 의도 · 겨냥하는 약점

질문 — "방어적 복사(defensive copy)란? getter로 내부 컬렉션을 그대로 반환하면 어떤 문제가 생기나요?"

출제 의도 — getter로 내부 List를 그대로 반환하면 외부가 도메인 객체의 불변식을 우회해 상태를 바꿀 수 있다. 이 질문이 보는 것은 API 암기가 아니라 캡슐화가 메서드 시그니처가 아니라 "참조 공유" 수준에서 깨지는 지점을 아는지다. "불변을 기본값으로 두는 설계 습관"의 실전 검증이기도 하다.

약점 A"private final인데 왜 뚫리죠?"에서 막힌다 — private이 막는 것(이름)과 final이 막는 것(참조 재대입)을 구분하지 못한다. final List는 불변 리스트가 아니다(1·3절).
약점 B"복사해서 주면 됩니다"에서 끝난다 — 왜 실무에서 이 버그가 특히 비싼지(예외가 안 나서 변경 지점과 증상 지점이 멀다)를 말하지 못하면 경험 없이 외운 답으로 들린다(5절).
약점 CunmodifiableList를 "복사"로 안다 — 뷰는 원본이 바뀌면 함께 바뀐다. 이걸 모르면 "감쌌으니 안전"이라고 답하고, 실제로는 스냅샷이 아닌 것을 스냅샷처럼 쓰게 된다(8절).
약점 D얕은 복사에서 멈춘다 — 리스트를 복사해도 원소는 그대로 공유된다. 원소가 가변이면 방어가 절반만 된 것이다(9절).
약점 Egetter만 막고 생성자를 잊는다 — 호출자가 넘긴 리스트의 참조를 계속 들고 있다. 게다가 검증 → 복사 순서로 쓰면 검증한 객체와 보관하는 객체가 다르다(TOCTOU)(10절).
합격선"getter는 복사본이 아니라 주소값을 넘기므로 호출자와 객체가 같은 리스트를 함께 듭니다. 그러면 addLine의 검증이 getLines().add()로 우회되고, 예외가 안 나서 며칠 뒤 정산에서야 드러납니다. 그래서 나갈 때는 List.copyOf 같은 불변 스냅샷을 주고(뷰는 원본을 비추므로 목적에 따라 고르고), 들어올 때는 복사 먼저 하고 그 복사본을 검증합니다. 다만 컬렉션 복사는 전부 얕은 복사라 원소가 가변이면 여전히 뚫리므로, 근본적으로는 원소를 불변으로 만들거나 컬렉션을 통째로 노출하지 않습니다."
이 문서를 관통하는 한 장면 아래 2절의 그림 하나가 이 문서의 전부다. 화살표는 둘인데 상자는 하나인 상태 — 불변식 우회, 시점이 어긋난 버그, 동시성 문제, 얕은 복사의 한계는 전부 그 그림에서 따라 나오는 결과일 뿐이다. 외울 것이 많아 보이면 그림 하나로 되돌아오면 된다.

1. 전제 — 변수에 든 것은 객체가 아니라 주소다

이 문서의 모든 내용이 한 가지 사실에서 나온다. 먼저 이것부터 확정하고 간다.

자바에서 객체를 담은 변수에 실제로 들어 있는 것은
객체 자체가 아니라, 그 객체가 힙 어디에 있는지를 가리키는 주소값이다.

이 주소값을 참조(reference)라고 부른다. 그리고 대입도, 인자 전달도, 메서드 반환도 전부 이 주소값을 한 벌 더 복사해 주는 것이다. 객체가 복제되는 일은 어디에서도 일어나지 않는다. new를 부르거나 명시적으로 복사하지 않는 한 힙의 객체는 계속 하나다.

같은 뿌리, 다른 질문 같은 사실을 == 비교의 관점에서 다룬 것이 30-integer-cache-boxed-equality.md다. 거기서는 "두 변수가 같은 객체를 가리키는가"가 문제였고, 여기서는 "두 코드가 같은 객체를 함께 만지게 되는가"가 문제다. 뿌리는 같다.

2. getter가 실제로 하는 일 — 참조가 새는 두 구멍

이제 문제의 코드를 본다. 이 한 줄이 무슨 일을 하는가가 전부다.

Before 내부 참조를 그대로 내주는 getter
public class Order {
    private final List<OrderLine> lines = new ArrayList<>();

    public List<OrderLine> getLines() {
        return lines;      // 이 한 줄이 무슨 일을 하는가?복제 아님
    }
}

return lines;는 리스트를 복제해서 주는 것이 아니다. 변수 lines에 들어 있는 주소값을 그대로 호출자에게 건네준다.

2-1. 새는 구멍은 두 개다 — 출구(getter)와 입구(생성자)

대부분은 getter만 떠올리지만 참조는 양방향으로 샌다. 나갈 때만 막으면 정확히 절반이다.

인출 카드 — 유출 지점은 둘

출구
getter가 return lines;
호출자가 내 리스트를 받아 간다. add·clear·removeIf·sort 전부 내 상태에 반영된다.
입구
생성자·수정자가 this.lines = lines;
호출자가 넘긴 리스트의 참조를 계속 들고 있다. 나중에 그쪽에서 바꾸면 내 상태가 바뀐다.
"들어올 때 복사, 나갈 때 복사" — 두 관문을 세트로 외운다

3. private final이 왜 못 막는가

여기서 자연스러운 반문이 나온다. "필드가 private final인데 어떻게 밖에서 바꾸나?" 두 키워드가 각각 무엇을 막는지 정확히 보면 답이 나온다.

private — 이름을 감춘다

외부가 order.lines라고 직접 쓰는 것을 막는다. 그런데 우리는 getLines()라는 공개 통로로 그 주소값을 자발적으로 건네주고 있다.

final — 주소값을 고정한다

this.lines = 다른리스트;처럼 그 변수 칸의 값을 바꾸는 것을 막는다. 그런데 우리가 하려는 것은 그 주소가 가리키는 객체의 내용물을 바꾸는 것이다.

가장 자주 오해되는 한 줄

final List ≠ 불변 리스트  /  참조 고정 ≠ 내용 고정

이 구분은 String 불변성 문항과 같은 뿌리다. 진짜 불변 리스트는 List.of(...)·List.copyOf(...)처럼 구현체 자체가 수정 연산을 거부하는 것이지, 필드에 final을 붙여 얻어지는 것이 아니다.

4. 불변식 우회 — 문 옆에 뚫린 구멍

도메인 객체가 지키려는 규칙을 불변식(invariant)이라고 부른다. "언제 봐도 변하지 않고 참이어야 하는 조건"이라는 뜻이다 — "주문 항목은 최대 100개", "주문에는 최소 1개의 항목이 있어야 한다", "합계 금액은 항목 금액의 합과 같다" 같은 것들이다.

객체지향에서 불변식을 지키는 방법은 상태를 감추고 → 바꾸는 통로를 메서드로 좁히고 → 그 메서드에서 검증하는 것이다. 그런데 그 노력이 getter 한 줄로 무력화된다.

Before 검증까지 갖췄는데 뚫려 있다
public class Order {
    private final List<OrderLine> lines = new ArrayList<>();

    public void addLine(OrderLine line) {
        if (lines.size() >= 100) {              // 불변식
            throw new IllegalStateException("주문 항목 초과");
        }
        lines.add(line);
    }

    public List<OrderLine> getLines() {
        return lines;   // 내부 참조를 그대로 내준다구멍
    }
}
호출부 검증을 전부 우회한다
Order order = ...;

// 통로 ① — 검증을 통과해야 한다
order.addLine(line);

order.getLines().add(line);   // 통로 ② 검증 미실행
order.getLines().clear();     // 항목 전부 삭제
order.getLines().sort(cmp);   // 순서까지 바뀐다
order.getLines().set(0, hack);// 항목 바꿔치기

// 컴파일 통과 · 예외 없음 · 로그 없음
// 101번째 항목이 조용히 들어간다

이 절의 결론 한 줄

캡슐화는 접근 제어자가 아니라 "내부 가변 상태의 참조가 밖으로 새지 않는가"에서 완성된다

5. 조용한 버그 — t0에서 t4까지

이 유형이 실무에서 특히 위험한 이유는 우회 자체가 아니다. 예외가 안 나기 때문이다.

getLines().removeIf(...)는 완벽히 합법적인 자바 코드다. 컴파일러도, 런타임도, 로그도 아무 말을 하지 않는다. 그래서 잘못된 시점에 아무 일도 일어나지 않고, 한참 뒤 전혀 다른 곳에서 결과만 드러난다.

일반적인 버그

  • 스택트레이스가 범인을 가리킨다
  • NPE가 나면 그 줄을 보면 된다
  • 재현 → 수정 → 확인이 한 줄기

참조 유출 버그

  • 범인이 흔적을 남기지 않고 떠난 뒤 피해자만 발견된다
  • 디버깅이 "누가 이 리스트를 건드렸는가"를 코드 전체에서 역추적하는 일이 된다
  • getLines() 호출 지점 전부를 하나씩 검토해야 한다
t0의 코드를 짠 사람에게 책임을 묻기 어렵다 받아온 리스트를 가공하는 것은 지극히 자연스러운 행동이기 때문이다. 정렬하려고 sort()를 부르는 것, 화면용으로 걸러내려고 removeIf()를 부르는 것 — 전부 평범한 코드다. 잘못은 그런 코드를 짠 사람이 아니라 살아 있는 내부 리스트를 내준 설계에 있다.

이 버그가 비싼 이유 — 면접에서 이 문장을 꺼내라

"예외가 안 나서 변경 지점과 증상 지점이 멀어진다"

여기서 List.copyOf의 가치가 분명해진다 — 조용히 틀어지는 버그를 시끄러운 예외로 바꾼다. t0에서 UnsupportedOperationException이 즉시 터지면 t4까지 갈 일이 없다.

6. 동시성이 얹히면 더 나빠진다

내부 컬렉션의 참조가 여러 스레드로 퍼지면 문제가 한 겹 더 쌓인다.

그나마 나은 경우 — ConcurrentModificationException

한 스레드가 순회하는 중에 다른 스레드가 그 리스트를 수정하면 예외가 난다. 예외가 나므로 문제를 알아챌 수 있다.

더 나쁜 경우 — 조용한 불일치

예외 없이 일관성 없는 상태를 읽어 간다. 합계는 갱신 전 값, 항목 목록은 갱신 후 값 같은 찢어진 스냅샷이 그대로 저장·전송된다.

진짜 이득은 "동기화 범위를 확정할 수 있게 된다"는 것 참조를 밖으로 내보내지 않으면 이 문제 자체가 다르게 다뤄진다. 동기화를 걸어야 할 범위를 객체 내부로 한정할 수 있기 때문이다. 리스트를 만지는 코드가 이 클래스 안에만 있다면 이 클래스 안에서 동기화를 완결할 수 있다. 반면 참조가 밖으로 나가면 그 리스트를 만지는 코드가 어디까지 퍼졌는지 알 수 없으므로, 동기화 범위를 확정하는 것 자체가 불가능해진다.

혼동 주의 — 스레드 안전과 캡슐화는 다른 축이다

동시성 컬렉션
"동시에 만져도 자료구조가 안 깨진다"를 보장한다. "아무나 못 만진다"는 보장하지 않는다.
참조 비공개
"만질 수 있는 코드의 범위"를 좁힌다. 그 결과 동기화 설계가 가능해진다.

CopyOnWriteArrayList를 써서 ConcurrentModificationException이 사라지면, 증상이 더 조용해질 뿐 불변식 우회는 그대로다.

7. 방어적 복사란 — 막아야 할 두 관문

방어적 복사(defensive copy) — 가변 객체를 주고받을 때 원본 대신 복사본을 써서 참조 공유를 끊는 기법

2절 그림에서 화살표 두 개가 같은 상자를 가리키던 상황을, 상자를 하나 더 만들어 각자 자기 것을 가리키게 바꾸는 것이다. 방어할 지점은 두 곳이다.

출구
나갈 때 (getter)
내부 객체를 복사하거나 수정 불가 형태로 반환한다. → 호출자가 반환값을 바꿔도 내 상태는 안전하다.
입구
들어올 때 (생성자·수정자)
외부에서 받은 객체를 복사해서 보관한다. → 호출자가 나중에 원본을 바꿔도 내 상태는 안전하다.

9. 얕은 복사의 한계 — 원소가 가변이면

여기까지 하면 다 막은 것 같지만 아니다. 리스트를 복사해도 그 안의 원소는 복사되지 않는다.

List<OrderLine> copy = new ArrayList<>(lines);
copy.get(0).changeQuantity(999);   // 원본 리스트의 [0]도 함께 바뀐다뚫림

왜 그런지는 1절의 사실을 다시 적용하면 된다. 리스트에 들어 있는 것도 객체가 아니라 주소값이다. 리스트를 복사한다는 것은 그 주소값들을 새 상자에 옮겨 담는 것이지, 주소가 가리키는 객체들까지 복제하는 것이 아니다.

얕은 복사 4형제 — 전부 한 겹만 복사한다

new ArrayList<>(c)
가변 스냅샷
List.copyOf(c)
불변 스냅샷
c.clone()
같은 타입 스냅샷
stream().toList()
불변 스냅샷
방어의 완성도는 API 선택이 아니라 "원소 타입이 불변인가"가 결정한다

원소가 불변 타입이면 — 얕은 복사로 충분

String, Integer, LocalDate, BigDecimal 같은 타입. 원소를 통해 바꿀 수 있는 것이 애초에 없다.

원소가 세터를 가진 가변 객체면 — 여전히 뚫린다

리스트를 아무리 잘 막아도 원소를 통해 뚫린다. getLines().get(0).setQuantity(999)는 불변 리스트에서도 성공한다.

10. 들어올 때의 방어와 TOCTOU 순서

지금까지는 나가는 쪽만 봤다. 그런데 들어오는 쪽도 똑같이 뚫려 있다.

Before 받은 리스트를 그대로 보관
public Order(List<OrderLine> lines) {
    this.lines = lines;   // 호출자가 넘긴 그 리스트공유
}
호출부 나중에 원본을 만진다
List<OrderLine> myLines = new ArrayList<>();
myLines.add(line1);
Order order = new Order(myLines);

myLines.add(line2);   // ★ 호출자는 아직 참조를 들고 있다
myLines.clear();      // order의 항목이 전부 사라진다
"소유권이 넘어갔다"는 착각 new Order(myLines)로 소유권이 넘어간 것처럼 보이지만 실제로는 주소값을 한 벌 나눠 가진 것뿐이고, 호출자의 변수도 여전히 같은 객체를 가리킨다. getter를 아무리 잘 막아도 이 통로가 열려 있으면 절반만 막은 것이다.

10-1. 순서가 문제다 — 검증 먼저면 TOCTOU

Before 검증 → 복사 (틀린 순서)
public Order(List<OrderLine> lines) {
    validate(lines);                     // ① 남의 원본을 검증
    this.lines = new ArrayList<>(lines); // ② 그 뒤에 복사
}
// 검증한 대상과 보관되는 대상이 '다른 객체'다
After 복사 → 검증 (올바른 순서)
public Order(List<OrderLine> lines) {
    this.lines = new ArrayList<>(lines); // ① 먼저 내 것으로
    validate(this.lines);              // ② 그 복사본을 검증
}
// 검증한 것과 보관되는 것이 '같은 객체'임이 보장된다

두 줄의 순서만 바뀌었는데 왜 중요한가. ①과 ② 사이에 원본이 바뀔 수 있기 때문이다.

순서 암기 — 이 네 글자만 기억한다

복사 → 검증   (copy first, then validate)

거꾸로 하면 "검증한 객체 ≠ 보관하는 객체"가 되어 TOCTOU가 열린다. 가산점 Effective Java가 명시적으로 경고하는 순서다.

여기서도 남는 한계 그 복사도 얕은 복사다(9절). 리스트 자체는 스냅샷이 됐지만 원소가 가변이면 원소를 통한 바꿔치기는 여전히 가능하다. 완전한 방어는 원소까지 불변일 때 성립한다.

11. 컬렉션만의 문제가 아니다 — Date·배열

지금까지 컬렉션으로 설명했지만 원인이 "참조 공유"이므로 가변 객체 전반에 똑같이 적용된다.

Before 가변 객체를 그대로 노출
// Date는 가변이다 — setTime()으로 시각을 바꿀 수 있다
public Date getStart() { return start; }
// order.getStart().setTime(0) → 주문 시각이 바뀐다

// 배열도 마찬가지 — length만 고정이고 원소는 얼마든지 바뀐다
public String[] getTags() { return tags; }
// order.getTags()[0] = "조작됨" 이 가능하다
After 불변 타입으로 갈아타거나 복사한다
// 근본 해법 — 자바 8 날짜 타입은 전부 불변이다
private final Instant start;             // Date 대신
public Instant getStart() { return start; } // 방어 불필요

// 배열은 방어 수단이 없다 — 복사하거나 List로 노출
public String[] getTags() { return tags.clone(); }
public List<String> tags() { return List.of(tags); }

배열은 특히 놓치기 쉽다

배열에는 unmodifiableList 같은 방어 수단이 없다

복사(Arrays.copyOf, clone())하거나, 애초에 배열 대신 List로 노출하는 수밖에 없다. public static final String[] NAMES 같은 상수 배열이 전역 가변 상태가 되는 것도 같은 이유다 — final은 배열 참조만 고정하고 원소는 누구나 바꾼다.

먼저 물어야 할 질문 "getter를 어떻게 방어할까"보다 "내부 상태를 애초에 불변으로 둘 수 없을까"가 먼저다.
  • Date 대신 LocalDateTime·Instant — 자바 8 날짜 타입은 전부 불변이라 방어적 복사가 필요 없다.
  • 상태를 담는 컬렉션은 생성 시점에 List.copyOf로 고정해 내부 표현 자체를 불변으로 만든다. 그러면 getter가 그대로 반환해도 안전해지고 매 호출 복사 비용도 사라진다.

12. 가장 캡슐화다운 해법 — 통째로 주지 않기

한 걸음 더 나가면 질문 자체를 되돌릴 수 있다.

되물을 질문 — "이 컬렉션을 통째로 밖에 줘야 하는 이유가 무엇인가?"

호출자가 실제로 원하는 것은 대개 리스트 자체가 아니라 그것으로 얻으려는 결과다. 개수를 세거나, 순회하거나, 특정 조건의 항목을 찾거나, 합계를 구하는 것이다. 그렇다면 그 결과를 주는 메서드를 노출하면 된다.

Before 컬렉션을 통째로 노출하고 그 위에서 방어를 고민
public List<OrderLine> getLines() { return List.copyOf(lines); }

// 호출부 — 계산 로직이 도메인 밖에 흩어진다

        .reduce(BigDecimal.ZERO, BigDecimal::add);   // 여러 곳에 복제됨
After 호출자가 실제로 필요로 하는 질의만 노출
public int lineCount() { return lines.size(); }
public BigDecimal totalAmount() { ... }
public Stream<OrderLine> lines() { return lines.stream(); }순회만
public boolean contains(ProductId id) { ... }

// 호출부 — 계산은 데이터를 가진 쪽에서 한다
BigDecimal total = order.totalAmount();
그래도 컬렉션 자체가 필요한 자리는 있다 화면에 목록을 그려야 하는 등 컬렉션 자체가 필요한 자리도 있다. 그때는 8절의 세 방식 중에서 고르면 된다. 다만 "통째로 줄 필요가 있는가"를 먼저 물어보는 순서가 중요하다.
주의 — Iterator 반환은 방어가 아니다 타입이 좁아 보여 안전해 보이지만 Iterator에는 remove()가 있고, 그것은 원본 컬렉션에서 원소를 지운다. "통째로 주지 않기"의 수단은 Stream·질의 메서드이지 Iterator가 아니다.

13. record는 이 문제를 풀어주지 않는다 함정

여기부터 3개 절은 실무 경계 — 원칙이 자동으로 통하지 않는 자리들이다.

record는 불변 데이터를 담기 위해 나온 문법이므로 "record를 쓰면 방어적 복사가 필요 없지 않나"라는 기대가 자연스럽다. 아니다.

record가 보장하는 것은 얕은 불변(shallow immutability)이다
필드 재대입만 막을 뿐, 컴포넌트가 가변 객체면 그 내용은 얼마든지 바뀐다
Before record라서 안전할 것 같지만 뚫려 있다
public record Cart(List<Item> items) { }

List<Item> myItems = new ArrayList<>();
Cart cart = new Cart(myItems);

myItems.add(item);        // 입구 — 넘긴 참조로 내부가 바뀐다
cart.items().add(item);   // 출구 — 접근자가 내부 참조를 그대로
After 컴팩트 생성자에서 방어적 복사
public record Cart(List<Item> items) {
    public Cart {
        items = List.copyOf(items);  // 저장 직전에 바꿔치기관용구
    }
}
// 저장 시점에 이미 불변 → 접근자는 손대지 않아도 안전하다

얕은 불변 vs 깊은 불변 — 이 구분을 말할 수 있어야 한다

얕은 불변 (record가 주는 것)
필드 재대입 불가. 컴포넌트가 List·배열·Date면 그 내용은 바뀐다.
깊은 불변 (우리가 원하는 것)
컴포넌트까지 전부 불변. 컴팩트 생성자의 List.copyOf + 원소 타입도 불변일 때 성립.

14. JPA 엔티티 — 원칙이 뒤집히는 자리

지금까지의 원칙에 정면으로 예외가 되는 자리가 있다. JPA 엔티티다.

이유는 JPA의 동작 방식에 있다. 하이버네이트는 엔티티를 영속 상태로 만들 때 컬렉션 필드를 자기 구현체(PersistentBag, PersistentSet 등)로 바꿔치기한다. 그 구현체가 "어떤 원소가 추가됐고 삭제됐는지"를 기록하고 있다가, 트랜잭션 커밋 시점에 그 기록을 보고 INSERT/DELETE SQL을 만든다. 이것이 변경 감지(dirty checking)의 실체다.

결론 ① 필드 교체 금지

하이버네이트가 추적하던 인스턴스가 사라져 변경 감지가 끊긴다. orphanRemoval·cascade = ALL이면 아예 예외가 난다 — "cascade가 걸린 컬렉션이 더 이상 소유 엔티티에서 참조되지 않는다"는 취지의 HibernateException이다. 통째로 바꿔야 하면 같은 인스턴스에 clear() 후 addAll().

결론 ② 복사본 반환의 부작용

이건 사실 우리가 원하던 보호이기도 하다. 다만 결과가 조용하다는 것이 문제다. 호출자가 order.getLines().add(line)을 했는데 예외도 안 나고 DB에도 안 들어가면 "왜 저장이 안 되지?"를 한참 헤매게 된다.

패턴 엔티티에서 일반적으로 쓰는 형태
@Entity
public class Order {
    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();

    // 조회: 뷰로 감싸 반환한다. 복사가 아니라 뷰인 것이 여기서는 오히려 맞다 —
    // 엔티티의 생명주기 안에서는 "지금 상태를 비춘다"가 자연스러운 의미이고,
    // 하이버네이트가 추적하는 원본 인스턴스는 그대로 유지된다.
    public List<OrderLine> getLines() {
        return Collections.unmodifiableList(lines);뷰가 정답
    }

    // 수정: 의도가 드러나는 메서드로만 열어 준다.
    // 원본 인스턴스에 직접 add/remove 하므로 변경 감지가 정상 동작한다.
    public void addLine(OrderLine line) {
        if (lines.size() >= 100) throw new IllegalStateException("주문 항목 초과");
        lines.add(line);          // 추적 중인 인스턴스에 직접
        line.assignTo(this);      // 양방향 연관관계의 반대편도 맞춰 준다
    }

    public void removeLine(OrderLine line) {
        lines.remove(line);       // orphanRemoval이 DELETE를 만들어 준다
    }
}

엔티티에서의 규칙

엔티티에서는 뷰로 반환하고, 수정은 메서드로만

8절에서 뷰의 단점으로 지적한 "원본이 바뀌면 뷰도 바뀐다"는 성질이, 엔티티의 생명주기 안에서는 오히려 원하는 동작이 된다. 원칙이 통째로 뒤집히는 게 아니라 프레임워크의 제약 때문에 선택지가 하나로 좁혀지는 것이라고 이해하면 된다.

15. Kotlin의 List는 절반만 안전하다

Kotlin으로 넘어가면 타입 시스템이 도와주지만 완전하지는 않다.

Kotlin은 List와 MutableList를 나눠 두었고, List에는 add나 remove가 아예 선언되어 있지 않다. 그래서 List를 반환하면 호출자가 수정 메서드를 부를 방법이 없다 — 타입 시스템이 "수정할 의도가 없다"를 표현해 준다는 점에서 자바보다 큰 진전이다.

그런데 List는 읽기 전용 인터페이스이지 불변 보장이 아니다
class Order {
    private val _lines = mutableListOf<OrderLine>()
    val lines: List<OrderLine> get() = _lines   // 읽기 전용 '타입'으로 노출
}

// 실제 객체는 여전히 MutableList다
(order.lines as MutableList).add(item)   // 캐스팅하면 수정된다
// 자바 코드에서 보면 그냥 java.util.List라 add()를 부를 수 있다
진전
타입으로 의도를 표현
List 반환은 "수정하지 마라"를 컴파일러가 강제한다. 자바의 List 반환에는 그런 표현이 없다.
한계 ①
캐스팅·자바 상호운용
as MutableList로 뚫린다. 그리고 자바 코드로 넘어가는 순간 구분이 사라진다 — 거기서는 그냥 java.util.List다.
한계 ②
원본이 바뀌면 반환값도 바뀐다
_lines를 그대로 노출한 것이므로 unmodifiableList 뷰와 같은 성격이다. 스냅샷이 아니다.
읽기 전용 타입 노출
val lines: List<T> get() = _lines
= 뷰. 원본을 비춘다
진짜 격리는
복사해서 반환
val lines: List<T> get() = _lines.toList()
= 스냅샷. 이것이 방어적 복사에 해당한다
정리 — 언어가 바뀌어도 질문은 같다 Kotlin은 "수정 메서드를 부를 수 있는가"는 타입으로 막아 주지만, "내용이 나중에 바뀔 수 있는가"는 여전히 복사했는지 아닌지가 결정한다. 뷰냐 스냅샷이냐라는 8절의 질문은 언어와 무관하게 남는다.

16. 인출 카드 — 면접 전날 이것만

암기 ① 한 장면 — 이것만 기억하면 나머지는 유도된다

화살표는 둘, 상자는 하나 — return lines;는 주소값을 한 벌 더 건네주는 것

암기 ② 뚫리는 이유 6종 — 하나씩 짚을 수 있어야 한다

① 출구
return lines; → getLines().add()로 검증 우회
② 입구
this.lines = lines; → 호출자가 참조를 계속 든다
③ 순서
검증 → 복사 → TOCTOU. 검증한 것과 보관한 것이 다르다
④ 원소
얕은 복사라 원소를 통해 뚫린다

암기 ③ 규칙 4줄 — 그대로 외운다

  • 들어올 때 복사, 나갈 때 복사 — 관문은 둘이다
  • 복사 먼저, 검증은 그 복사본에 — 순서를 바꾸면 TOCTOU
  • 기본값은 List.copyOf — 뷰는 "원본을 비춘다"를 알고 고를 때만
  • 가장 좋은 방어는 복사가 필요 없게 만드는 것 — 내부 표현을 불변으로, 컬렉션은 통째로 안 준다

암기 ④ 헷갈리는 짝 — 한 줄로 구분한다

final vs 불변
final은 참조 고정, 불변은 내용 고정. final List는 불변 리스트가 아니다.

복사는 사진(그 시점 고정), 뷰는 창문(지금을 비춘다).

얕은 불변 vs 깊은 불변
record가 주는 것은 얕은 불변(필드 재대입 금지)뿐이다.
스레드 안전 vs 캡슐화
동시성 컬렉션은 "안 깨진다"를 줄 뿐 "아무나 못 만진다"를 주지 않는다.

암기 ⑤ 30초 답변 스크립트

문제"getter는 복사본이 아니라 주소값을 넘깁니다." 그 순간 호출자와 도메인 객체가 같은 리스트를 함께 들게 되어, addLine()의 검증이 getLines().add()로 통째로 우회됩니다. private은 이름을, final은 참조를 막을 뿐 내용물은 못 막습니다.
비용"게다가 예외가 안 납니다." 화면 계층에서 removeIf를 한 것이 그대로 저장되고, 며칠 뒤 정산 대사에서야 드러나며 스택트레이스는 배치만 가리킵니다.
해법"나갈 때는 List.copyOf, 들어올 때는 복사 후 검증"입니다. 뷰는 원본이 바뀌면 함께 바뀌므로 목적에 따라 고릅니다. 단 복사는 전부 얕은 복사라 원소가 가변이면 남습니다.
확장"근본적으로는 내부 표현을 불변으로 만들거나, 컬렉션을 통째로 노출하지 않습니다." record는 얕은 불변이라 컴팩트 생성자에서 복사해야 하고, JPA 엔티티는 예외로 뷰 + 도메인 메서드가 정답입니다.

17. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해 본 뒤 펼쳐서 확인한다. 시니어 변별 배지가 붙은 것은 "아는가"가 아니라 "트레이드오프를 판단할 수 있는가"를 보는 질문이다.

생성자에서 받은 컬렉션도 복사해야 하나요? 검증과 복사의 순서는?md의 대표 꼬리질문 — 순서를 못 말하면 절반만 아는 것이다

해야 한다. getter만 막으면 절반이다. 호출자가 생성자에 넘긴 리스트의 참조를 계속 들고 있다가 나중에 수정하면 내부 상태가 함께 바뀐다. new Order(myLines)로 소유권이 넘어간 것처럼 보이지만 실제로는 주소값을 나눠 가진 것뿐이다.

순서는 반드시 복사 먼저, 그다음 검증이다. 검증을 먼저 하면 검증한 객체와 실제로 보관하는 객체가 다른 객체가 된다. 그 사이에 호출자(또는 다른 스레드)가 원본을 바꾸면 검증을 통과했다는 기록만 남고 검증되지 않은 데이터가 보관된다. 이런 결함을 TOCTOU(time-of-check to time-of-use)라고 부르며, 파일 권한을 검사한 뒤 여는 사이에 심볼릭 링크로 바꿔치기하는 고전적 보안 취약점과 같은 구조다. 가산점 Effective Java가 명시적으로 경고하는 순서다.

복사를 먼저 하면 그 복사본은 아무도 손댈 수 없는 우리만의 객체이므로, 검증한 것과 보관되는 것이 같은 객체임이 보장된다.

한계까지 덧붙이면 좋다 — 그 복사도 얕은 복사이므로 원소가 가변이면 원소를 통한 바꿔치기는 여전히 가능하다. 완전한 방어는 원소 타입까지 불변일 때 성립한다.

매 호출마다 복사하면 성능이 걱정되지 않나요?시니어 변별"괜찮습니다"로 끝내면 감점 — 양쪽 비용을 견줘야 한다

트레이드오프 판단 문제이므로 양쪽 비용을 견줘서 답한다.

대부분의 도메인 객체 컬렉션은 원소가 수십에서 수백 개다. 그 정도 크기의 얕은 복사는 참조 값을 옮겨 담는 것뿐이라 비용이 사실상 무시 가능하다. 반면 참조 공유 버그의 추적 비용은 훨씬 비싸다 — 변경 시점과 증상 시점이 떨어져 있어 스택트레이스가 범인을 가리키지 않으므로 며칠에 걸친 역추적이 되기 쉽다. 측정되지 않은 성능 우려로 확정된 안전을 포기하는 거래는 대체로 손해다.

그래도 실제로 병목이 측정되면 선택지가 셋이다.

  • ① unmodifiableList 뷰 — 래퍼 객체 하나 비용만 낸다. 대신 "원본이 바뀌면 반환값도 바뀐다"를 받아들이고 문서화해야 한다.
  • ② 내부 표현 자체를 불변 컬렉션으로 — 생성 시점에 List.copyOf로 고정해 두면 getter는 그대로 반환해도 안전하고, List.copyOf가 이미 불변인 인자는 그대로 돌려주는 최적화까지 얹혀 매 호출 복사가 사라진다. 가장 근본적인 해법이다.
  • ③ 컬렉션을 통째로 노출하지 않는다 — lineCount(), totalAmount(), Stream<OrderLine> lines() 같은 질의 메서드로 좁힌다.

③이 가장 캡슐화다운 해법이고, "getter를 어떻게 방어하나"에서 "왜 컬렉션을 통째로 줘야 하나"로 질문을 되돌리는 답변이 설계 감각을 보여준다. 계산 로직이 데이터를 가진 객체 쪽으로 옮겨 오면서 방어 고민이 자연히 사라지기 때문이다.

Collections.unmodifiableList로 감싸 반환하면 충분한가요?뷰와 복사의 차이를 아는지가 전부다

목적에 따라 다르다. unmodifiableList는 복사가 아니라 뷰(원본을 들여다보는 창문)다. 호출자의 수정은 UnsupportedOperationException으로 막지만, 원본이 바뀌면 이미 나간 반환값의 내용도 함께 바뀐다.

반환받은 쪽이 그 리스트를 오래 들고 있다가 다시 읽으면 "받았을 때와 내용이 다른" 상황을 만나고, 순회 중에 원본이 수정되면 ConcurrentModificationException까지 난다 — 호출자는 "수정 불가 리스트라며 받았는데 왜 동시 수정 예외가 나지?"라는 상황에 빠진다.

그래서 "밖에서 못 고치게 한다"가 목적이면 충분하고, "받은 시점의 상태를 보장한다"가 목적이면 부족하다. 후자에는 List.copyOf가 맞다.

비용 대비로는 뷰가 래퍼 하나라 싸고 복사는 원소 수에 비례한다. 그리고 JPA 엔티티에서는 뷰가 오히려 정답이다 — 하이버네이트가 추적하는 원본 인스턴스를 유지해야 변경 감지가 동작하고, 엔티티 생명주기 안에서는 "지금 상태를 비춘다"는 성질이 자연스럽기 때문이다.

record를 쓰면 이 문제가 해결되나요?"record니까 불변"을 무비판적으로 받아들이는지 본다

아니다. record가 보장하는 것은 얕은 불변(shallow immutability)이다. 필드 재대입만 막을 뿐, 컴포넌트가 가변 객체(List, 배열, Date)면 참조 공유 문제는 그대로다.

record Cart(List<Item> items)의 자동 생성 접근자는 return items;와 동일해서 내부 참조를 그대로 돌려주고, 생성자에 넘긴 리스트의 참조도 호출자가 계속 들고 있다.

그래서 record에서도 컴팩트 생성자에서 items = List.copyOf(items);가 관용구다. 컴팩트 생성자는 필드에 대입되기 직전에 실행되므로, 여기서 파라미터를 바꿔 두면 저장 시점에 이미 불변이 된다. 불변 객체의 참조는 아무리 공유해도 안전하므로 접근자는 손대지 않아도 된다.

JPA 엔티티의 컬렉션 필드에도 방어적 복사를 적용하나요?시니어 변별원칙을 기계적으로 적용하면 오히려 버그가 난다

여기서는 원칙이 아니라 프레임워크 제약이 선택지를 좁힌다. 하이버네이트는 엔티티를 영속 상태로 만들 때 컬렉션 필드를 자기 구현체(PersistentBag, PersistentSet 등)로 바꿔치기하고, 그 구현체가 추가·삭제를 기록했다가 커밋 시점에 SQL로 바꾼다. 이것이 변경 감지(dirty checking)다. 그래서 두 가지 제약이 생긴다.

① 필드 자체를 새 컬렉션으로 교체하면 안 된다. 하이버네이트가 추적하던 인스턴스를 잃어 변경 감지가 끊기고, orphanRemoval이나 cascade = ALL이 걸려 있으면 "cascade가 걸린 컬렉션이 더 이상 소유 엔티티에서 참조되지 않는다"는 취지의 예외가 난다. 통째로 바꿔야 하면 같은 인스턴스에 clear() 후 addAll()을 한다.

② getter가 복사본을 반환하면 그 복사본에 대한 수정이 DB에 반영되지 않는다. 보호로는 맞지만 호출자에게는 "예외도 안 나고 저장도 안 되는" 혼란이 된다.

그래서 실무 패턴은 getter는 Collections.unmodifiableList로 감싸 반환하고, 추가·삭제는 addLine()/removeLine() 같은 의도가 드러나는 메서드로만 열어 주는 것이다. 그 메서드 안에서는 원본 인스턴스에 직접 add/remove를 하므로 변경 감지가 정상 동작하고, 불변식 검증도 그 자리에서 할 수 있다. 반환이 뷰라 내부 변경이 비쳐 보이는 것은 엔티티 생명주기 안에서는 오히려 자연스럽다.

List.copyOf(items)와 Collections.unmodifiableList(new ArrayList<>(items))는 같은 것 아닌가요?둘 다 "불변 스냅샷"을 만든다 — 그래도 남는 차이가 있다

효과는 거의 같지만 세 가지가 다르다.

  • 객체 수 — unmodifiableList(new ArrayList<>(...))는 복사본 + 래퍼 두 개를 만든다. List.copyOf는 전용 불변 구현 하나로 끝난다.
  • null 원소 — List.copyOf는 null 원소를 허용하지 않아 NullPointerException을 던진다. 래핑 방식은 null이 그대로 담긴다. 함정 기존 코드에 copyOf를 적용할 때 실제로 걸리는 지점이다.
  • 재복사 최적화 — List.copyOf는 인자가 이미 불변 리스트면 복사하지 않고 그대로 돌려주는 최적화가 있다. 내부 표현이 이미 불변이면 반복 호출 비용이 사라진다. 래핑 방식은 매번 두 객체를 새로 만든다.

핵심은 둘 다 "그 시점의 스냅샷"이라는 점이다. 위험한 오해는 unmodifiableList(items)처럼 복사 없이 원본을 바로 감싸는 것을 스냅샷이라고 착각하는 쪽이다 — 그건 뷰다.

스트림의 .toList()로 반환하면 안전한가요? Collectors.toList()와 무엇이 다릅니까?수정 가능성 · null 허용 · 얕은 복사 세 가지로 나눠 답한다

세 가지를 구분해야 한다.

  • Collectors.toList() — 규약상 수정 가능 여부가 보장되지 않는 리스트를 준다(관행적으로 ArrayList). 그대로 반환하면 호출자가 수정할 수 있다. 다만 그것은 새로 만들어진 리스트이므로 원본 컬렉션에는 영향이 없다 — 즉 구조 공유는 끊겨 있다.
  • Stream.toList()(Java 16+) — 수정 불가 리스트를 준다. 다만 List.of/List.copyOf와 달리 null 원소를 허용한다는 차이가 있다.
  • Collectors.toUnmodifiableList() — 수정 불가이면서 null 원소를 허용하지 않는다.

그리고 셋 다 공통으로 얕은 복사다. 리스트 상자는 새로 생겨도 원소 객체는 원본과 같은 것이므로, 원소가 가변이면 result.get(0).setX(...)로 여전히 뚫린다. "어떤 컬렉터를 쓰느냐"는 리스트 한 겹의 문제일 뿐, 원소의 가변성은 별개의 문제다.

그럼 항상 깊은 복사를 하면 되지 않나요?"왜 하지 않는가"를 세 가지로 댈 수 있어야 한다

대부분의 경우 답은 아니다. 이유가 셋이다.

  • 비용 — 원소 수 × 원소 크기만큼 실제 객체를 만든다. 얕은 복사(참조 옮겨 담기)와는 차원이 다른 비용이다.
  • 경계의 모호함 — 원소가 또 다른 객체를 참조하면 어디까지 복사해야 하는지가 정해지지 않는다. OrderLine이 Product를 들고 있으면 Product도 복사하나? 그 안의 Category는?
  • 순환 참조 — 서로를 가리키는 객체가 있으면 무한 루프에 빠진다. 방문 집합을 들고 다니는 순간 복사 코드가 그래프 순회 코드가 된다.

현실적인 답은 원소 타입을 불변으로 만드는 것이다. OrderLine에서 세터를 없애고 수량 변경은 withQuantity(999)처럼 새 인스턴스를 만들어 돌려주는 방식으로 설계하면, 원소를 통한 우회가 원천적으로 불가능해지고 리스트 한 겹만 방어하면 끝난다. "불변을 기본값으로"라는 습관이 방어 코드의 양을 줄이는 구체적 이득이 여기서 나타난다.

getter가 Iterator나 Stream을 반환하면 안전한가요?시니어 변별둘의 안전도가 다르다

같지 않다. Iterator는 안전하지 않고 Stream은 (구조 변경에 한해) 안전하다.

Iterator에는 remove()가 있다. 그리고 그 remove()는 원본 컬렉션에서 원소를 지운다. 즉 getLines().iterator()를 넘겨주는 것은 삭제 권한을 넘겨주는 것이다. 반환값 타입이 좁아 보여서 오히려 방심하기 쉬운 함정이다.

Stream은 소비만 가능하고 소스에 대한 구조 변경 연산이 없으므로 리스트 한 겹은 안전하다. 다만 두 가지가 남는다 — ① 원소가 가변이면 forEach(l -> l.setX(...))로 여전히 뚫린다(얕은 복사와 같은 한계). ② 스트림은 지연 평가라 소비 시점에 원본을 읽으므로, 그 사이 원본이 바뀌면 뷰와 같은 성질을 갖고 ConcurrentModificationException도 날 수 있다.

정리하면 Stream 반환은 "통째로 주지 않기"의 좋은 수단이고, Iterator 반환은 방어가 아니다.

생성자 파라미터를 clone()으로 복사하면 되나요?시니어 변별파라미터 타입이 final이 아니면 답이 달라진다

파라미터 타입이 final이 아니면 clone()을 신뢰하면 안 된다.

clone()은 인스턴스의 실제 타입이 결정한다. 파라미터로 Date를 받았지만 실제로 들어온 것이 Date를 상속한 공격자(또는 남의 코드)의 하위 클래스라면, 그 clone()은 원본에 대한 참조를 몰래 남겨 두는 인스턴스를 돌려줄 수 있다. 복사한 줄 알았는데 여전히 남이 만질 수 있는 물건인 것이다.

그래서 신뢰할 수 없는 하위 타입이 섞일 수 있는 자리에서는 new Date(d.getTime())처럼 "내가 아는 타입의 새 인스턴스"를 직접 만든다. 컬렉션도 마찬가지로 list.clone()이 아니라 new ArrayList<>(list)·List.copyOf(list)를 쓴다.

물론 근본 해법은 여기서도 같다 — Date 대신 Instant·LocalDateTime처럼 불변 타입을 쓰면 이 고민 자체가 사라진다.

CopyOnWriteArrayList나 ConcurrentHashMap을 쓰면 이 문제가 사라지나요?스레드 안전과 캡슐화는 다른 축이다

아니다. 두 가지는 다른 문제를 푼다.

동시성 컬렉션이 보장하는 것은 "여러 스레드가 동시에 만져도 자료구조가 깨지지 않는다"이다. "아무나 만지지 못한다"가 아니다. 내부 참조를 그대로 반환하면 외부는 여전히 add/remove를 할 수 있고, 불변식 우회는 그대로 일어난다. 달라지는 것은 ConcurrentModificationException이 안 난다는 점뿐인데, 그건 오히려 증상을 더 조용하게 만든다.

거꾸로도 성립하지 않는다 — 방어적 복사를 해도 복합 연산의 원자성(예: "확인 후 추가")은 보장되지 않는다. 캡슐화(참조를 안 내보낸다)와 동시성 제어(연산을 직렬화한다)는 각각 따로 설계해야 한다.

다만 참조를 안 내보내면 동시성 설계가 쉬워진다는 연결은 있다. 그 컬렉션을 만지는 코드가 이 클래스 안에만 있으면 동기화 범위를 클래스 안에서 완결할 수 있기 때문이다.

Map이나 Set도 같은가요? Collections.unmodifiableMap은 값(value)까지 지켜 주나요?'한 겹'이 어디까지인지 정확히 말해야 한다

원인이 "참조 공유"이므로 Map·Set·배열 전부 같다. 그리고 unmodifiableMap이 막는 것은 구조 변경(put/remove/clear)뿐이다.

값이 가변 객체면 map.get(k).setX(...)로 얼마든지 바뀐다. 값이 컬렉션이면 더 눈에 띈다 — unmodifiableMap(m).get(k).add(x)는 예외 없이 성공한다. Map.copyOf도 마찬가지로 얕은 복사다.

또 하나 놓치기 쉬운 것이 entrySet()·values()·keySet()도 전부 뷰라는 점이다. 원본 맵의 unmodifiable 래퍼는 이 뷰들도 수정 불가로 감싸 주지만, 맵 자체를 그대로 노출했다면 values().clear() 한 줄로 맵이 비워진다. 컬렉션을 반환할 때 "이건 뷰인가 복사본인가"를 항상 되물어야 하는 이유다.

이미 getLines()가 수십 군데에서 쓰이는 레거시에서는 어떻게 바꾸나요?시니어 변별"copyOf로 바꾸겠습니다"는 운영 사고를 낸다

단번에 List.copyOf로 바꾸면 지금까지 조용히 성공하던 호출들이 UnsupportedOperationException으로 한꺼번에 터진다. 컴파일은 통과하므로 런타임에, 그것도 운영에서 드러난다. 순서를 나눠야 한다.

  • ① 호출부를 먼저 센다 — getLines() 호출 지점을 전부 찾아 읽기만 하는 곳 / 수정하는 곳으로 분류한다. 수정하는 곳이 진짜 버그 후보다.
  • ② 수정하는 호출부부터 도메인 메서드로 옮긴다 — getLines().add(x) → order.addLine(x). 이 단계에서 비로소 불변식 검증이 붙는다.
  • ③ 그다음 반환 타입을 조인다 — 수정 호출부가 사라진 뒤에 List.copyOf(또는 뷰)로 바꾼다. 이때부터는 예외가 나면 새로 생긴 위반이라는 뜻이라 신호가 깨끗하다.
  • ④ 필요하면 관측을 먼저 붙인다 — 당장 다 못 고칠 규모면, 반환 전에 호출 스택을 로깅하는 단계를 잠깐 두어 실제 수정 호출부를 운영에서 수집한 뒤 ②로 간다.

요지는 "방어를 먼저 세우고 깨지는 곳을 찾는" 순서가 아니라 "깨질 곳을 먼저 없애고 방어를 세우는" 순서라는 것이다.

한 줄 요약
private은 필드 이름을 숨길 뿐이고 final은 참조를 고정할 뿐이라 상태를 지켜 주지 못한다 — return lines;가 돌려주는 것은 복사본이 아니라 같은 객체를 가리키는 주소값이므로 그 순간 도메인 객체의 검증 메서드는 전부 우회 가능해지고, 게다가 그 우회는 예외 없이 조용히 일어나 며칠 뒤 정산에서야 드러나기 때문에 스택트레이스가 범인을 가리키지 못한다. 그러니 들어올 때는 복사한 뒤 복사본을 검증하고(TOCTOU 방지), 나갈 때는 List.copyOf 같은 불변 스냅샷을 내보내되(뷰는 원본이 바뀌면 함께 바뀐다는 것을 알고 고르고), 원소가 가변이면 얕은 복사로는 못 막는다는 한계까지 인지하는 것이 이 주제의 완성이며 — 가장 좋은 방어는 애초에 내부 상태를 불변으로 만들어 복사가 필요 없게 하거나, 컬렉션을 통째로 노출하지 않는 것이다.
