REST vs GraphQL vs gRPC
기술이 아니라 "누가 쓰는가"로 고른다 — 계약을 어디에 적어 두느냐가 다른 세 스타일

면접 질문: "REST vs GraphQL vs gRPC — 어떤 기준으로 선택하나요?"

핵심 관전 포인트 — 셋은 세대 교체 관계가 아니라 계약을 어디에 적어 두느냐가 다른 세 스타일이다. REST는 URL과 HTTP 메서드에, GraphQL은 타입 스키마에, gRPC는 IDL 한 장에 적는다. 그래서 선택 축은 유행이 아니라 그 계약을 읽고 코드를 짜는 사람이 누구인가다. 불특정 다수·외부 파트너가 쓰는 공개 API는 REST — HTTP 생태계(캐시·브라우저·curl·상태 코드 기반 모니터링)를 그대로 물려받고 온보딩 비용이 가장 낮다. 화면이 다양하고 클라이언트가 조회 형태를 주도해야 하는 자사 멀티 클라이언트는 GraphQL — 응답 형태의 결정권이 서버에 있다는 REST의 전제에서 나오는 두 증상, 즉 over-fetching(안 쓰는 필드까지 통째로 받음)과 under-fetching(한 번 받아도 모자라 또 부름)을 클라이언트 쿼리로 한꺼번에 없애되, HTTP 캐싱 무력화 · 필드 단위 인가 · 쿼리 비용 통제 · 리졸버 N+1이라는 서버 복잡도를 대가로 치른다. 내부 서비스 간 고빈도 호출은 gRPC — 필드를 이름이 아니라 번호로 직렬화하는 Protobuf 바이너리와 HTTP/2 멀티플렉싱으로 성능을 얻고, proto 한 장에서 여러 언어의 스텁을 생성하므로 컴파일러가 계약을 강제한다. 대신 최종 상태 코드를 본문 뒤에 오는 트레일러 헤더에 싣기 때문에 브라우저 fetch/XHR로는 읽을 수 없어 외부 경계에 놓을 수 없다. 그래서 실무의 결론은 셋 중 하나를 고르는 것이 아니라 경계별 혼용이다 — 바깥은 REST/GraphQL, 안쪽은 gRPC. 각 기술의 전제(소비자 특성)가 없는 자리에 유행으로 결론만 들여오는 것이 가장 흔한 실패다.
  • 1
    셋은 우열이 아니라 계약의 위치가 다릅니다 — REST는 URL과 메서드에 적고 사람이 쓴 문서가 강제하고, GraphQL은 타입 스키마에 적고 쿼리 검증기가 강제하고, gRPC는 IDL(proto)에 적고 컴파일러가 강제합니다. 그래서 비교의 진짜 질문은 "무엇이 더 빠른가"가 아니라 "그 계약을 누가 읽고, 어긋나면 언제 알게 되는가"입니다.
  • 2
    그래서 선택 축은 소비자입니다 — ①소비자를 우리가 통제할 수 있는가, ②응답 형태를 누가 정해야 하는가, ③왕복 1회의 단가가 얼마인가. ①이 통제 불가면 접근성이 최우선이라 REST로 거의 결정되고, ①이 통제 가능일 때에만 ②(화면 조합 폭발 → GraphQL)와 ③(내부 고빈도 → gRPC)이 갈립니다.
  • 3
    실무 결론은 경계별 혼용입니다 — 계층마다 그 계약을 읽는 사람이 다르므로 바깥엔 접근성(REST)·클라이언트 유연성(GraphQL)을, 안쪽엔 성능과 강타입 계약(gRPC)을 둡니다. 변별이 되는 건 장점 나열이 아니라 배제 논리입니다 — "파트너에게 proto 배포와 코드 생성을 요구하게 되므로 외부에 gRPC는 아니다"처럼 말할 수 있어야 합니다.

0. 질문 + 출제 의도

질문: "REST vs GraphQL vs gRPC — 어떤 기준으로 선택하나요?"

출제 의도: 유행이 아니라 소비자 특성(외부 공개냐, 내부 서비스 간이냐, 클라이언트 주도 조회냐)으로 선택하는지 — 기술 선택의 축이 "누가 쓰는가"에 있음을 아는지 확인한다. 각 기술의 장점 나열이 아니라, "이 상황에서는 이것이 부적합하다"는 배제 논리를 갖고 있는지가 변별점이다.

이 페이지가 겨냥하는 약점 세 가지 ① 셋을 "구세대 → 신세대"로 줄 세우는 것 → 1절에서 비교 축을 계약의 위치와 강제자로 갈아 끼운다. 이 축을 세우면 "무엇이 더 좋냐"는 질문 자체가 성립하지 않는다는 게 보인다.
② 장점만 나열하고 배제를 못 하는 것 → 9절에서 자리별로 무엇이 왜 탈락하는지를 표로 정리한다. 면접에서 값이 나가는 문장은 "gRPC는 빠릅니다"가 아니라 "파트너 인프라에 HTTP/2 프록시를 요구하게 되므로 외부엔 못 놓습니다"다.
③ GraphQL·gRPC의 대가를 모르는 것 → 7·8절에서 캐싱 무력화·필드 단위 인가·리졸버 N+1과 트레일러 헤더 때문에 브라우저에서 못 쓴다를 도식으로 못박는다.
이 페이지가 다루지 않는 것 — 다른 문서에 있다 RTT·멀티플렉싱·BFF·N+1의 정의와 왕복 비용 계산은 07-chatty-api-call-explosion.md, HTTP/1.1·2·3의 HOL 블로킹 상세는 08-network-http/09-http1-http2-http3-hol-blocking.md, 자원·표현·메서드 시맨틱은 01-restful-design-principles-resource-naming.md, 계약의 하위 호환 규율은 03-api-versioning-strategies.md·08-backward-compatible-api-changes.md에 있다. 이 페이지는 그 위에서 "세 기술의 계약 단위가 어떻게 다르고, 그 차이가 어떤 소비자에게 값을 내는가"만 본다.

1. 축 세우기 — 계약이 어디에 적혀 있고, 누가 그것을 강제하는가

비교를 시작하기 전에 축을 하나 세우자. 이 축을 세우지 않으면 답변이 "GraphQL은 필요한 것만 받아서 좋고, gRPC는 빨라서 좋다"는 카탈로그 나열로 끝난다.

먼저 용어 하나 — API 계약(contract)

계약은 "무엇을 어떤 형태로 주고받기로 한다"는 서버와 클라이언트 사이의 약속이다. 어떤 요청을 보낼 수 있는지, 그 요청에 무엇을 실어야 하는지, 응답에 어떤 필드가 어떤 타입으로 들어 있는지가 계약의 내용이다.

계약이 왜 중요한가. 서버와 클라이언트는 서로 다른 사람이, 서로 다른 언어로, 서로 다른 시점에 만들기 때문이다. 안드로이드 앱 개발자는 우리 서버 코드를 읽지 않는다. 그 사람이 참조하는 것은 오직 계약뿐이고, 계약이 애매하면 그 애매함이 그대로 버그가 된다.

그래서 진짜 질문은 "무엇이 더 빠른가"가 아니라 — 그 계약이 어디에 적혀 있고, 누가 그것을 강제하는가?

암기 장치 — 계약 3줄과 강제자 "문 · 검 · 컴"

REST = URL·메서드→문서가 강제 GraphQL = 스키마→검증기가 강제 gRPC = IDL→컴파일러가 강제

첫 답변은 이 세 줄로 시작하면 된다. 강제자 셋의 앞 글자만 따서 "문 · 검 · 컴"으로 붙잡아 두면, 나머지(응답 결정권·직렬화·브라우저 가능 여부)는 전부 이 세 줄에서 파생시켜 말할 수 있다.

2. REST — 계약은 URL과 메서드에 있고, 강제하는 주체가 없다

REST에서 "무엇을 할 수 있는가"는 URL 목록으로, "그것에 무엇을 하는가"는 HTTP 메서드로 표현된다. GET /orders/42라는 한 줄이 곧 "42번 주문의 표현을 달라"는 요청 전체다.

요청 클라이언트가 보낸 것 전부
GET /orders/42 HTTP/1.1
Host: api.example.com
Accept: application/json

// 응답의 "모양"에 대해 클라이언트가
// 한 마디도 하지 않았다는 점을 보라.
응답 서버가 정한 7개 필드
{
  "id": 42,                     서버가 고른 필드
  "status": "SHIPPED",
  "totalAmount": 45000,
  "userId": 7,
  "shippingAddress": "서울시 ...",
  "createdAt": "2026-08-30T12:34:56Z",
  "updatedAt": "2026-08-31T09:00:00Z"
}
여기서 눈여겨볼 한 줄 — 응답 형태의 결정권이 100% 서버에 있다 요청에는 "42번 주문을 달라"만 있고, 그 주문을 몇 개의 필드로 어떻게 그려서 줄지는 전부 서버가 정했다. 이 사실 하나가 3절에서 GraphQL이 등장하는 이유 전체이고, 7절의 over-fetching / under-fetching이라는 두 증상의 유일한 원인이다. "REST의 단점"이 아니라 "REST의 전제"라고 부르는 편이 정확하다.

두 번째로 짚어야 할 것 — 계약을 강제하는 주체가 없다

서버가 어느 날 totalAmount를 숫자에서 문자열로 바꿔 내려보내도 HTTP는 아무것도 막지 않는다. 클라이언트는 이미 배포된 앱 안에서 파싱 에러로 죽고 나서야 안다. 스토어 심사를 거치는 모바일 앱이라면 되돌리는 데 며칠이 걸린다.

그래서 REST 진영은 OpenAPI 스펙 · 스펙 diff 검사 · 계약 테스트(consumer-driven contract test) 같은 별도의 장치를 덧대어 계약을 강제한다. 계약 관리 부담이 없는 것이 아니라, 프로토콜 밖에 있는 것이다 — 4절 gRPC의 "컴파일 에러로 잡힌다"와 정확히 대비되는 지점이다.

대신 얻는 것 — HTTP 생태계를 통째로 물려받는다 6절 선택 기준의 근거 계약이 URL과 메서드라는 것은, 이미 세상에 깔려 있는 모든 HTTP 인프라가 우리 API를 이해한다는 뜻이기도 하다. CDN·브라우저·프록시의 HTTP 캐싱이 그대로 붙고(캐시 키가 정확히 "메서드 + URL"이므로), 표준 상태 코드 기반 모니터링·알람이 붙고, 로드밸런서의 L7 경로 라우팅이 붙는다. 우리가 아무것도 만들지 않아도 되는 것이 REST의 가장 큰 자산이다.

3. GraphQL — 계약은 스키마에 있고, 요청이 곧 응답의 설계도다

GraphQL은 서버가 가진 데이터 전체를 하나의 타입 그래프로 정의해 두고, 클라이언트가 그 그래프에서 필요한 부분만 골라 오려내는 질의 언어다. 이름 그대로 "그래프에 대한 질의 언어(Graph Query Language)"다.

3-1. 스키마 — 클라이언트가 물어볼 수 있는 것의 전부

# 스키마 — 이 파일이 계약이다. 클라이언트가 물어볼 수 있는 것의 전부가 여기 있다.
type Order {
  id: ID!
  status: OrderStatus!
  totalAmount: Int!
  user: User!              # 주문 -> 주문자로 이어지는 간선
  items: [OrderItem!]!     # 주문 -> 주문 항목들로 이어지는 간선
}

type User {
  id: ID!
  name: String!
  grade: String!
  email: String!
}

# Query 타입은 "그래프에 들어가는 입구" 목록이다.
type Query {
  order(id: ID!): Order
}
! 한 글자가 계약의 일부라는 점 !는 "null이 될 수 없다"는 표시다. REST에서는 "이 필드가 null일 수 있는가"가 대개 문서의 산문으로만 존재하는데(그래서 자주 틀린다), GraphQL에서는 타입 시스템이 그것을 들고 있다. 계약의 정밀도가 한 칸 올라간 지점이다.

3-2. 요청과 응답이 키 하나까지 대응한다 — 결정권이 넘어간 자리

3-3. 리졸버 — 이 응답을 서버가 어떻게 만드는가, 그리고 N+1이 태어나는 자리

리졸버(resolver)

GraphQL 서버가 쿼리에 등장하는 필드 하나하나마다 호출하는 함수다. "해결한다(resolve)", 즉 "이 필드의 값이 무엇인지 알아낸다"는 뜻에서 온 이름이다. REST 컨트롤러는 엔드포인트 하나에 함수 하나가 붙지만, GraphQL은 필드 단위로 함수가 붙는다. 이 성질 하나가 GraphQL의 유연성과 N+1을 동시에 낳는다.

4. gRPC — IDL 한 장이 컴파일러가 강제하는 계약이 된다

gRPC는 "원격 프로시저 호출(RPC, Remote Procedure Call)" 방식의 통신 프레임워크다. RPC란 네트워크 너머의 함수를 마치 내 코드 안의 함수처럼 부르는 방식을 말한다. REST가 "자원에 무엇을 한다"는 문법이라면, RPC는 "함수를 부른다"는 문법이다.

IDL(Interface Definition Language) — 왜 굳이 "중립" 문법인가

특정 프로그래밍 언어에 속하지 않는 중립적인 문법으로 "이 서비스에 어떤 메서드가 있고, 각 메서드가 무엇을 받아 무엇을 돌려주는가"를 적어 둔 파일이다.

한 파일에서 여러 언어의 코드를 생성해야 하기 때문에 중립이어야 한다. 계약을 Java 인터페이스로 적어 두면 Go 서비스는 그것을 읽을 수 없다. 어느 언어에도 속하지 않는 문법으로 적어 두면 Java 스텁도 Go 스텁도 Kotlin 스텁도 같은 파일에서 생성된다.

그리고 이 "생성"이 계약을 강제하는 힘의 정체다. 양쪽 코드가 같은 파일에서 기계적으로 생성됐으므로, 계약과 구현이 어긋나면 코드가 아예 컴파일되지 않는다. 2절 REST에서는 문서와 구현이 따로 놀 수 있지만, 여기서는 원리적으로 불가능하다. gRPC가 쓰는 IDL이 Protocol Buffers(Protobuf) 문법이고, 확장자가 .proto라 흔히 "proto 파일"이라 부른다.

syntax = "proto3";

service OrderService {
  // 단발 요청 -> 단발 응답
  rpc GetOrder (GetOrderRequest) returns (Order);
  // 요청 1회 -> 응답이 스트림으로 계속 흘러나온다 (서버 스트리밍)
  rpc WatchOrderEvents (WatchRequest) returns (stream OrderEvent);
}

message GetOrderRequest {
  int64 order_id = 1;   // 이 "= 1"은 기본값이 아니라 필드 번호다
}

message Order {
  int64  id           = 1;
  string status       = 2;
  int64  total_amount = 3;
}

4-1. = 1은 기본값이 아니라 필드 번호다 — 여기서 gRPC의 성질 둘이 한꺼번에 나온다

4-2. 생성된 스텁 — "네트워크 호출인데 함수 호출처럼 보인다"

proto 파일을 컴파일하면 각 언어의 스텁(stub)이 생성된다. 스텁은 "그루터기"라는 뜻으로, 실제 구현은 원격에 있고 내 프로세스 안에는 그 자리를 대신하는 껍데기만 있다는 의미에서 붙은 이름이다.

// 배포된 뒤 사용자 기기에서.

OrderServiceGrpc.OrderServiceBlockingStub stub =

6. 선택의 축 셋 — "누가 쓰는가"에서 기술이 따라 나온다

세 기술 중 하나를 고르는 일은 사실상 아래 세 질문에 답하는 일이다. 답이 정해지면 기술은 따라 나온다. 순서가 반대가 되는 순간(기술을 먼저 고르고 근거를 찾는 순간) 10절의 실패 사례가 된다.

암기 장치 — 판단의 축 셋 "통 · 형 · 단"

① 통 — 소비자를 통제할 수 있나
통제 불가(파트너·불특정 다수)면 접근성이 최우선 가치가 된다. 우리가 상대의 언어·프레임워크·빌드 환경을 고를 수 없기 때문.
② 형 — 응답 형태를 누가 정하나
화면 조합이 폭발하면 결정권을 클라이언트로 넘기는 값이 커진다. 넘기지 않으면 백엔드 팀이 화면 요구의 병목이 된다.
③ 단 — 왕복 1회의 단가는
데이터센터 내부(1ms 미만)냐 모바일 셀룰러망(수십~수백 ms)이냐. 단가가 싸면 대신 횟수가 압도적으로 많아진다.
①이 "통제 불가"면 REST로 거의 결정되고, ①이 "통제 가능"일 때에만 ②와 ③이 GraphQL과 gRPC를 가른다

6-1. 축 ① 상세 — 왜 통제 불가면 REST로 거의 결정되는가

(1) 진입 비용이 사실상 0
HTTP 클라이언트가 없는 언어·환경은 없다. curl 한 줄로 시연과 디버깅이 되고, 온보딩 문서가 "이 URL로 GET 하세요"에서 끝난다. 문제가 생겼을 때 상대가 자기 손으로 재현해 볼 수 있다는 게 실무에서 생각보다 큰 값이다.
(2) HTTP 생태계를 공짜로 물려받는다
CDN·프록시의 HTTP 캐싱(키 = 메서드 + URL), 표준 상태 코드 기반 모니터링·알람, 로드밸런서의 L7 경로 라우팅. 우리가 아무것도 만들지 않아도 이미 있는 인프라가 우리 API를 이해한다.
(3) 계약이 오래 산다
공개 API는 한번 내면 몇 년을 유지해야 하는데 HTTP 시맨틱은 20년 넘게 안정적이었다. 특정 프레임워크 버전에 묶이지 않는다는 뜻이다.
여기서 배제 논리까지 말해야 답이 완성된다 — 이 자리에 gRPC를 놓으면 무엇이 무너지나 ① 파트너마다 proto 파일 배포와 코드 생성 도구 셋업을 요구하게 되고, ② 바이너리라 상대가 자기 쪽 문제인지 우리 쪽 문제인지 눈으로 확인할 수 없으며, ③ 중간 프록시가 HTTP/2와 트레일러를 온전히 지원하는지까지 파트너사 인프라 사정에 걸린다. 한 문장으로 — 접근성이 가치인 자리에 성능 도구를 놓은 미스매치다.

7. GraphQL의 청구서 — 유연성을 서버 복잡도로 사 오는 거래

7-1. 먼저 무엇을 사는가 — over-fetching과 under-fetching은 한 원인의 두 얼굴

over-fetching (과다 인출)
화면이 실제로 쓰지 않는 필드까지 응답에 통째로 실려 오는 것. 목록 화면이 이름과 등급만 그리는데 응답에 30개 필드가 오면 나머지 28개는 네트워크와 파싱 비용만 쓰고 버려진다.
under-fetching (과소 인출)
한 번 받아서는 화면을 못 그려서 또 호출해야 하는 것. 상세 화면이 주문 + 주문자 + 상품을 필요로 하는데 API가 주문만 주면 왕복을 두 번 더 낸다.
before REST — 한 벌의 응답으로 서로 다른 화면을 감당한다
GET /users/42
-> { id, name, email, address, grade, joinedAt, ... 30개 필드 }

증상 1 (over-fetching)
  모바일 목록 화면은 name과 grade 둘만 그리는데 30개를 다 받는다.
  셀룰러망에서 전송량과 파싱이 낭비된다.

증상 2 (under-fetching)
  상세 화면은 유저 + 주문목록 + 쿠폰이 필요해서
    GET /users/42 -> GET /users/42/orders -> GET /users/42/coupons
  3번 왕복한다. RTT 100ms면 이것만 300ms.

증상 3 (변종 엔드포인트 증식)
  화면별 맞춤 응답을 만들다 보면 /users/42?view=mobile-list 같은
  것이 하나씩 는다. 화면이 늘 때마다 백엔드 팀에 요청이 쌓인다.
after GraphQL — 클라이언트가 필요한 형태를 쿼리로 선언. 왕복 1회
# 상세 화면이 보내는 쿼리
query {
  user(id: 42) {
    name
    grade
    orders(last: 5) { id status }   연관 데이터도 같은 왕복에
    coupons { name expiresAt }
  }
}

# 목록 화면이 보내는 쿼리 — 서버 코드는 한 줄도 안 바뀐다
query {
  user(id: 42) { name grade }
}

# 원인(응답 형태의 결정권)이 사라졌으므로
# 증상 1·2가 함께 사라지고, 증상 3의 변종 엔드포인트도
# 만들 이유가 없어진다.

7-2. 그리고 무엇을 지불하는가 — 대가 넷 "캐 · 인 · 비 · 엔"

GraphQL 도입 청구서 네 줄 — 이걸 못 대면 "장점만 아는 사람"이 된다

캐 — HTTP 캐싱 무력화
HTTP 캐시의 키는 "메서드 + URL"인데 GraphQL은 대개 /graphql 하나에 POST로 보낸다. URL이 항상 같고 메서드가 POST이므로 중간 캐시(CDN·프록시)가 개입할 근거 자체가 없다. → 네트워크 계층 캐시를 잃고 애플리케이션 계층 캐시로 보상하는 구조(7-4).
인 — 인가가 필드 단위로
REST는 "이 엔드포인트를 이 역할이 부를 수 있는가"만 판정하면 되지만, GraphQL은 클라이언트가 조합을 자유롭게 만드니 "이 사용자가 이 필드를 볼 수 있는가"를 필드마다 판정해야 한다. user { email }을 본인은 되고 남은 안 된다면 그 판정이 리졸버 안에 들어간다.
비 — 쿼리 비용을 클라이언트가 정한다
깊이 제한과 복잡도 제한이 없으면 한 줄짜리 쿼리가 DB를 눕힌다. 쿼리 깊이 상한 · 필드별 비용 점수 합산 · 타임아웃을 서버가 갖춰야 한다. (등록된 쿼리만 허용하면 이 위험이 함께 막힌다 — 7-4)
엔 — N+1이 서버 안으로 들어온다
3-3에서 본 리졸버 구조 때문이다. DataLoader 같은 배칭 계층이 사실상 필수이고, 이는 문제를 없앤 것이 아니라 우리 쪽으로 옮긴 것이다(7-3).
GraphQL은 클라이언트의 유연성을 서버의 복잡도로 사 오는 거래다 — 화면이 몇 개 안 되고 요구가 안정적이면 손해 보는 거래다
대가 하나 더 — 관측 체계를 다시 세워야 한다 가산점 GraphQL은 필드 오류가 나도 대개 HTTP 200에 errors 배열을 담아 응답한다. 응답의 일부는 성공하고 일부는 실패하는 부분 성공이 정상 동작이기 때문이다. 그래서 "5xx 비율" 기반 알람과 대시보드가 그대로 통하지 않는다. 지표를 operationName이나 등록된 쿼리 ID 단위로 다시 잡고, errors 배열을 파싱해 실패율을 세는 계층을 따로 만들어야 한다. 캐싱 말고도 잃는 것이 하나 더 있다는 뜻이다.

7-3. 대가 "엔" 갚기 — DataLoader와 "틱"이라는 단위

DataLoader

리졸버들이 개별적으로 요청한 조회를 즉시 실행하지 않고 잠깐 모아 뒀다가, 모인 키를 하나의 WHERE user_id IN (...) 질의로 바꿔 한 번에 실행한 뒤 각 리졸버에 결과를 나눠 주는 계층이다. 같은 키를 두 번 요청하면 캐시된 결과를 준다.

before 필드 리졸버 — 주문 하나마다 호출된다
@Controller
class OrderController {

    @SchemaMapping(typeName = "Order", field = "user")
    User user(Order order) {
        // 목록 20건이면 이 메서드가 20번 불린다
        return userRepository.findById(order.getUserId());
    }
}

// 쿼리 21회. 코드만 보면 잘못된 곳이 없어 보이는 것이
// 이 함정의 고약한 점이다 — 문제는 "호출 횟수"에 있다.
after 배치 매핑 — 같은 요청의 Order들을 한꺼번에 받는다
@Controller
class OrderController {

    @BatchMapping(typeName = "Order", field = "user")
    Map<Order, User> user(List<Order> orders) {  List로 받는다
        List<Long> ids = orders.stream()
                .map(Order::getUserId).distinct().toList();

        Map<Long, User> found = userRepository.findAllById(ids)
                .stream().collect(toMap(User::getId, identity()));

        return orders.stream().collect(
                toMap(identity(), o -> found.get(o.getUserId())));
    }
}
// 쿼리 2회. "1 + N"이 "1 + 1"이 된다.
JPA의 N+1과 연결하면 가산점이다 원리(개별 지연 조회의 반복)가 같고 해법(배치 로딩)도 같다. @BatchSize나 fetch join이 하던 일을 DataLoader가 리졸버 계층에서 하는 것이다. 다만 층위가 다르다 — JPA는 엔티티 그래프를, DataLoader는 GraphQL 필드 그래프를 대상으로 한다. 두 층에서 각각 N+1이 날 수 있으므로 둘 다 막아야 한다는 것까지 말하면 한 칸 더 간다.

7-4. 대가 "캐" 갚기 — 잃은 네트워크 캐시를 무엇으로 보상하나

(1) persisted query — URL을 되살린다
쿼리 본문을 서버에 미리 등록해 두고, 클라이언트는 해시 ID만 GET으로 보내는 방식. GET /graphql?id=a3f8c2&variables={"id":42}가 되므로 URL이 다시 캐시 키가 되어 CDN 캐싱이 되살아난다.
부수 효과가 더 크다 — 등록되지 않은 쿼리는 아예 실행할 수 없으므로 대가 "비"(임의의 비싼 쿼리)가 함께 막히고, 긴 쿼리 문자열을 매번 보내지 않아 요청 크기도 준다. Apollo의 APQ는 이 등록을 자동화한다.
(2) 클라이언트 정규화 캐시
응답을 화면 단위로 통째로 저장하지 않고, 객체를 타입명 + id를 키로 잘게 쪼개 저장하는 캐시. "정규화"는 DB 정규화와 같은 뜻 — 같은 객체를 여러 벌 중복 저장하지 않는다.
화면 단위 캐시라면 "주문 상세"와 "주문 목록"이 같은 유저 정보를 각자 들고 따로 낡지만, 정규화 캐시에서는 그 유저가 한 벌만 존재하므로 불일치가 생기지 않는다. Apollo Client가 이 방식이다.
(3) 서버 내부 데이터 소스 캐싱
리졸버가 부르는 저장소 계층 앞에 Redis 등을 두는 것. 가장 익숙한 방식이지만 네트워크 왕복은 그대로 난다는 점에서 (1)·(2)와 성격이 다르다 — 서버 부하는 줄지만 사용자 체감 지연은 덜 준다.

8. gRPC가 이기는 자리와, 브라우저라는 벽

내부 서비스 간 호출은 소비자가 "우리가 배포하고 통제하는 소수의 서버"다. 6절의 축 ①이 통제 가능이므로 접근성의 값이 급격히 떨어지고, 대신 축 ③(왕복 단가는 싸지만 횟수가 압도적으로 많다)과 계약의 엄격함이 전면에 나선다.

암기 장치 — gRPC가 내는 값 넷 "직 · 멀 · 스 · 생"

직 — Protobuf 바이너리 직렬화
키 이름을 빼고 번호와 타입만 압축해 싣는다. 페이로드가 작고 파싱 CPU가 낮다. 줄어드는 것이 네트워크 시간만이 아니라 CPU 시간이기도 하다는 게 핵심 — 데이터센터 내부는 어차피 RTT가 1ms 미만이라 실제 이득의 상당 부분이 직렬화 비용 쪽에서 나온다.
멀 — HTTP/2 멀티플렉싱 위의 커넥션 재사용
서비스 A가 B를 초당 3천 번 부를 때 커넥션 하나에 요청을 겹쳐 보낼 수 있다는 것은 커넥션 풀 관리 부담과 handshake 비용이 사라진다는 뜻이다. (프로토콜 상세는 08-network-http/09)
스 — 스트리밍이 계약에 들어 있다
returns (stream OrderEvent)처럼 스트림이 IDL의 일급 문법이다. REST에서 서버 푸시를 하려면 SSE나 WebSocket이라는 별개의 기술을 덧붙이고 그 계약을 따로 문서화해야 하지만, 여기서는 같은 proto에 함께 적히고 같은 생성기가 스텁을 만든다.
생 — 코드 생성이 곧 강타입 계약
4절에서 본 그대로다. 다언어(polyglot) 조직에서 특히 값이 크다 — Java 팀과 Go 팀이 같은 proto를 보고 각자 생성하면 두 언어 사이의 필드명·타입 불일치가 원리적으로 생기지 않는다.
전제 확인 — gRPC는 HTTP/2를 "요구"한다 선택 사항이 아니라 전제다. HTTP/1.1은 한 커넥션에 요청 하나만 흘릴 수 있고(응답에 "몇 번 요청의 답"이라는 식별자가 없어 순서로만 짝을 맞추므로), HTTP/2는 모든 조각에 스트림 ID를 붙이는 이진 프레이밍으로 그 제약을 푼다. 이 사실 하나가 gRPC의 장점("멀")이자 한계(아래 브라우저 문제)의 뿌리다. 프로토콜별 상세는 08-network-http/09-http1-http2-http3-hol-blocking.md에 있다.

8-1. 한계 ① 브라우저가 gRPC를 직접 말하지 못한다 — 이유는 "트레일러 헤더"

트레일러 헤더(trailer header)

응답 본문이 다 끝난 뒤에 오는 헤더다. 보통의 헤더는 본문보다 앞에 오지만, "본문을 다 만들어 봐야 알 수 있는 정보"는 앞에 실을 수 없으므로 뒤에 붙일 자리를 마련해 둔 것이다. 편지의 추신(P.S.)과 자리가 같다. gRPC는 호출의 최종 상태 코드(grpc-status)를 바로 이 트레일러에 싣는다 — 응답을 10분간 흘려보내다 중간에 실패할 수도 있는데 그 결과를 응답 맨 앞에 미리 적을 수는 없기 때문이다. 스트리밍이 있는 프로토콜이라 당연한 설계다.

한계 ② 디버깅에 전용 도구가 필요하다 4절에서 본 대로 바이너리라 패킷을 떠도 읽히지 않는다. 내부에서는 grpcurl과 서버 리플렉션(서버가 자기 proto 정의를 런타임에 알려 주는 기능)으로 감당할 수 있지만, 통제 밖의 소비자에게 이 부담을 지울 수는 없다. — 두 한계 모두 "통제 가능한 안쪽에서는 감당되고, 통제 불가한 바깥에서는 감당 안 된다"는 같은 모양이라는 점이 중요하다.

8-2. gRPC 계약을 바꾸는 규율 — 전부 "번호"에서 나온다 시니어 변별

출발점은 4절에서 본 사실 하나다 — Protobuf는 필드를 이름이 아니라 번호로 직렬화한다. 그래서 호환성 규칙이 전부 "번호"를 중심으로 정해진다.

proto 계약 변경의 안전 지도. 번호를 건드리는 변경은 전부 위험이고, 이름을 건드리는 변경은 와이어에는 안전하지만 소스는 깨진다는 두 줄로 압축된다.
하려는 변경안전한가이유
새 필드를 새 번호로 추가안전구버전은 모르는 번호를 만나면 무시한다 — Tolerant Reader가 런타임에 내장돼 있다
기존 필드의 번호 변경위험같은 데이터가 다른 필드로 해석된다. 에러 없이 조용히 값이 뒤바뀐다
기존 필드의 타입 변경위험번호는 같은데 해석 방식이 달라져 역직렬화가 깨지거나 값이 망가진다
필드 이름만 변경와이어 호환은 안전바이트에는 이름이 없다. 다만 생성된 코드의 접근자 이름이 바뀌므로 양쪽 소스 코드는 깨진다
필드 삭제조건부 안전번호를 reserved로 묶어 재사용을 금지해야 안전하다 — 아래 도식
03·08번과 나란히 놓으면 시각의 일관성이 드러난다 시니어 변별 두 문서의 대원칙은 "추가는 안전, 삭제·의미 변경은 파괴적 변경"이었고, 추가가 안전한 근거는 받는 쪽 파서가 모르는 것을 무시한다는 규약(Tolerant Reader)이었다. proto는 그 규약을 사람의 약속이 아니라 도구로 강제한다 — REST에서는 "모르는 필드는 무시하도록 파싱하십시오"를 문서에 적어 부탁해야 하지만, Protobuf 런타임은 모르는 번호를 항상 무시한다. 대신 REST에는 없는 제약이 하나 생긴다(번호는 되돌릴 수 없다). 한 문장으로 — 계약 관리의 부담이 사라진 것이 아니라 문서에서 도구로 옮겨간 것이다.

9. 배제 논리 — "이 자리에 이건 아니다"

면접에서 변별이 되는 것은 장점 나열이 아니라 배제 논리다. "gRPC는 빠릅니다"는 누구나 말하지만, "파트너 인프라에 HTTP/2 프록시 지원까지 요구하게 되므로 외부엔 못 놓습니다"는 써 본 사람만 말한다. 축 ①(소비자 통제 가능 여부)을 기준으로 정리하면 이렇게 된다.

표의 오른쪽 열이 이 페이지에서 가장 먼저 외워야 할 칸이다 — 고른 이유가 아니라 버린 이유가 판단력을 보여준다.

10. 실무의 결론 — 하나를 고르는 게 아니라 경계별로 혼용한다

한 문장으로 — 바깥 경계는 접근성(REST) 또는 클라이언트 유연성(GraphQL), 안쪽은 성능과 강타입 계약(gRPC)

10-1. 흔한 실패 둘 — 공통 구조가 있다

실패 ① 사내 어드민 CRUD에 GraphQL 도입

  • 화면이 3개뿐이고 소비자가 자사 프론트엔드 하나인데 GraphQL을 얹었다.
  • 결과는 7-2의 대가 넷만 고스란히 떠안는 것 — HTTP 캐싱 무력화, 필드 단위 인가, 쿼리 비용 제한, DataLoader 배칭.
  • 그런데 정작 얻어야 할 이득인 "클라이언트가 조합을 스스로 만든다"는 쓰이지 않았다. 화면이 3개면 조합도 3개이고, 그 3개는 REST 엔드포인트 3개로 충분했다.
  • 진단: "클라이언트 다양성"이라는 GraphQL의 전제가 없는 자리였다.

실패 ② 외부 파트너 연동 API를 gRPC로 공개

  • 파트너사마다 proto 배포 → 코드 생성 환경 구성 → HTTP/2를 온전히 지원하는 프록시 확인을 거치느라 온보딩이 몇 주씩 걸렸다.
  • 장애가 나면 "우리 쪽 문제인지 확인해 달라"는 요청이 오갔는데, 파트너가 자기 손으로 요청을 떠서 볼 수 없으니 확인이 항상 우리를 거쳐야 했다.
  • 결국 REST 래퍼를 다시 만들었다.
  • 진단: 처음부터 소비자를 봤다면 피할 수 있던 이중 비용이다.

두 실패의 공통 구조 — 이 한 문장이 이 페이지의 결론이다

기술의 전제 조건을 확인하지 않고 결론만 들여왔다
GraphQL의 전제=클라이언트가 여럿이고 조합이 폭발한다 gRPC의 전제=소비자를 우리가 통제한다

전제가 없으면 대가만 남는다. 그래서 면접에서 "왜 이걸 골랐나"보다 "이 전제가 우리 상황에 있는지 어떻게 확인했나"에 답하는 편이 언제나 강하다.

10-2. 도입 순서 — REST에서 얼마나 갈 수 있는지 먼저 본다

새 기술을 검토할 때의 순서도 답변의 일부다. 문제 크기와 도구 크기를 맞추는 판단을 보여주는 자리이기 때문이다.

1
지금 REST의 무엇이 아픈가를 증상으로 특정한다. over-fetching이 아픈가? under-fetching(왕복 수)이 아픈가? 아니면 백엔드 팀이 화면 요구의 병목이 된 것이 아픈가? — 셋은 처방이 전부 다르다.
2
07번의 REST 내 처방으로 풀리는가. 목록 DTO 확장 → 벌크 조회 → expand(깊이 1) → BFF 순으로 올라간다. 여기서 풀리면 여기서 멈춘다.
3
조합의 수가 조직의 처리 능력을 넘어섰는가. 클라이언트 종류 × 화면 수 × 필드 조합이 폭발해 BFF 엔드포인트 추가 요청이 백엔드 팀에 쌓이는가. — 이건 느낌이 아니라 백로그로 실측되는 값이다.
4
그렇다면 GraphQL 검토. 단, 7-2의 대가 넷을 감당할 준비(캐싱 대안, 필드 인가 설계, 쿼리 비용 제한, DataLoader)와 함께 도입한다. 넷을 나중에 하겠다고 미루면 실패 ①이 된다.
내부 통신을 gRPC로 옮기는 판단도 같은 방식이다 먼저 "지금 내부 호출의 무엇이 아픈가"를 특정한다 — ①호출량이 많아 직렬화 CPU가 눈에 띄는가, ②서비스 간 계약 불일치로 인한 장애가 반복되는가, ③서버 푸시가 필요한가. 셋 중 하나라도 실측으로 확인되면 도입 근거가 되지만, "요즘 다 쓴다"는 근거가 아니다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

세 기술의 계약 3줄?
REST = URL·메서드에 적고 문서가 강제 / GraphQL = 스키마에 적고 검증기가 강제 / gRPC = IDL에 적고 컴파일러가 강제. 강제자만 따면 "문·검·컴".
선택의 축 셋?
"통·형·단" — ①소비자를 통제할 수 있나 ②응답 형태를 누가 정하나 ③왕복 단가는 얼마인가. ①이 통제 불가면 REST로 거의 결정.
over/under-fetching의 원인?
하나다 — 응답 형태의 결정권이 서버에 있다. 넘치면 over, 모자라면 under. 진단명이 둘일 뿐 병은 하나. under = 07번의 chatty/N+1.
GraphQL의 대가 넷?
"캐·인·비·엔" — HTTP 캐싱 무력화 / 필드 단위 인가 / 쿼리 비용을 클라이언트가 정함 / 리졸버 N+1. (+관측 체계 재구축)
gRPC가 내는 값 넷?
"직·멀·스·생" — Protobuf 직렬화 / HTTP/2 멀티플렉싱 / 스트리밍이 IDL 일급 문법 / 코드 생성이 곧 강타입 계약.
gRPC를 브라우저에서 못 쓰는 이유?
최종 상태 코드 grpc-status가 본문 뒤에 오는 트레일러 헤더에 있고 fetch/XHR은 트레일러를 JS에 노출하지 않는다. → grpc-web + 프록시 필요.
= 1의 의미와 파생 효과?
기본값이 아니라 필드 번호. 이름 대신 번호로 직렬화 → ①작고 빠르다 ②사람이 못 읽는다 ③호환성 규칙이 전부 번호 중심. 1~15번은 태그 1바이트.
캐싱을 되살리는 유일한 수단?
persisted query — 쿼리를 서버에 등록하고 해시 ID만 GET으로 → URL이 다시 캐시 키. 덤으로 임의의 비싼 쿼리도 차단된다.
배제 논리 한 줄씩?
외부에 gRPC = proto·코드생성·프록시를 파트너에게 요구 / 화면 3개에 GraphQL = 대가만 떠안고 유연성은 안 쓰임 / 브라우저에 gRPC = 트레일러.
두 실패의 공통 구조?
전제를 확인하지 않고 결론만 들여왔다. GraphQL의 전제 = 클라이언트 다양성, gRPC의 전제 = 소비자 통제 가능. 전제가 없으면 대가만 남는다.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

GraphQL의 N+1 문제는 왜 생기고 어떻게 해결하나요? 필수힌트: "리졸버가 필드 단위"라는 성질에서 출발해야 원인 설명이 된다

원인은 리졸버가 필드 단위로 호출된다는 성질에 있다(3-3). 목록 안의 연관 필드는 그 "필드 단위"가 "항목 단위"로 번역되므로, users(10명) { orders } 쿼리 하나가 users 조회 1회 + orders 조회 10회 = 11회가 된다. 07번에서 정의한 N+1(1 + N)과 같은 산수다.

해결은 DataLoader 패턴이다. 리졸버들이 개별적으로 요청한 조회를 즉시 실행하지 않고 잠깐 모아 뒀다가, 모인 키를 하나의 WHERE id IN (...) 질의로 바꿔 한 번에 실행한 뒤 각 리졸버에 결과를 나눠 주는 계층이다. 같은 키를 두 번 요청하면 캐시된 결과를 준다.

"잠깐 모아 둔다"가 얼마 동안인지가 이 패턴의 핵심인데, 흔히 "같은 실행 틱(tick) 안에서 모은다"고 설명된다. 틱은 이벤트 루프가 한 바퀴 도는 단위이고, 실무적으로는 "같은 GraphQL 요청을 처리하는 동안 서로 다른 리졸버가 낸 조회는 하나로 합쳐진다"는 뜻이다.

요청 사이에는 합쳐지지 않으므로 DataLoader 인스턴스는 요청마다 새로 만든다 — 공유하면 A가 조회한 결과가 B의 요청에 캐시로 나가는 인가 사고가 된다

Java 진영에서는 java-dataloader와 Spring for GraphQL의 BatchLoaderRegistry·@BatchMapping이 같은 일을 한다. 마무리로 "JPA의 N+1과 원리(개별 지연 조회의 반복)가 같고 해법(배치 로딩)도 같다 — @BatchSize·fetch join이 하던 일을 DataLoader가 리졸버 계층에서 한다"고 연결하면 가산점이다.

gRPC는 왜 브라우저에서 직접 못 쓰나요? 필수힌트: "브라우저가 지원 안 해서"로 끝내면 0점. 어떤 데이터가 어디에 실리는지를 말해야 한다

최종 상태 코드가 트레일러 헤더에 있기 때문이다(8-1). 트레일러 헤더는 응답 본문이 다 끝난 뒤에 오는 헤더이고, gRPC는 호출 결과인 grpc-status를 거기에 싣는다. 스트리밍 응답에서는 결과를 미리 알 수 없으므로 뒤에 붙일 수밖에 없는 설계다.

그런데 브라우저의 fetch/XHR은 본문까지만 노출하고 트레일러는 자바스크립트에 넘겨주지 않는다. 그래서 브라우저는 gRPC 호출의 성공/실패를 판정할 방법이 없다. 이 밖에도 브라우저는 HTTP/2 프레임을 직접 제어할 수 없어 gRPC가 요구하는 세밀한 스트림 조작이 불가능하다.

대응은 grpc-web + 중간 프록시(Envoy 등)다. 프록시가 트레일러를 본문 끝에 데이터 프레임으로 밀어 넣어, 브라우저가 본문만 읽고도 상태를 알 수 있게 변환한다.

여기서 한 걸음 더 나가면 좋다. "이 프록시 계층이 반드시 추가된다는 사실 자체가 gRPC를 외부 경계에 두지 않는 이유 중 하나"라고 묶으면, 기술적 사실을 아키텍처 판단으로 잇는 답이 된다.

GraphQL을 쓰면 HTTP 캐싱이 왜 무력화되나요? 대안은? 필수힌트: 캐시 키가 무엇인지부터 말하면 자동으로 설명된다

전제가 깨지기 때문이다. REST의 HTTP 캐싱은 GET + 고유 URL = 캐시 키라는 전제 위에 서 있다. GraphQL은 대개 /graphql 단일 엔드포인트에 POST로 쿼리를 보내므로 URL이 캐시 키 역할을 못 하고, POST 응답은 HTTP 시맨틱상 중간 캐시가 재사용하지 않는다. CDN과 프록시가 개입할 근거 자체가 사라진 것이다.

대안 셋(7-4).

(1) persisted query — 쿼리 본문을 서버에 미리 등록해 두고 클라이언트는 해시 ID만 GET으로 보낸다. GET /graphql?id=a3f8c2&variables=...가 되므로 URL이 다시 캐시 키가 되어 CDN 캐싱이 되살아난다. 부수 효과도 크다 — 등록되지 않은 쿼리는 아예 실행할 수 없으므로 "클라이언트가 임의의 비싼 쿼리를 만든다"는 위험이 함께 막히고, 요청 크기도 준다. Apollo의 APQ는 이 등록을 자동화한다.

(2) 클라이언트 정규화 캐시 — 객체를 타입명 + id를 키로 잘게 쪼개 저장한다. 화면 단위 캐시라면 "주문 상세"와 "주문 목록"이 같은 유저 정보를 각자 들고 따로 낡지만, 정규화 캐시에서는 그 유저가 한 벌만 존재하므로 불일치가 생기지 않는다. Apollo Client가 이 방식이다.

(3) 서버 내부의 데이터 소스 캐싱 — 리졸버가 부르는 저장소 앞에 Redis 등. 가장 익숙하지만 네트워크 왕복은 그대로 나므로 (1)·(2)와 성격이 다르다.

정리하면 "네트워크 계층 캐시를 잃고 애플리케이션 계층 캐시로 보상하는 구조"

덧붙여 "GraphQL은 필드 오류가 나도 대개 HTTP 200에 errors 배열을 담아 응답하므로 상태 코드 기반 알람·대시보드가 그대로 통하지 않는다"까지 말하면, 잃는 것이 캐싱 말고 하나 더 있다는 걸 아는 답이 된다.

REST로도 필드 선택 파라미터나 BFF로 over-fetching을 풀 수 있는데, 그래도 GraphQL을 택하는 기준은? 시니어 변별힌트: 이 질문의 정답은 성능이 아니라 조직 이야기다

정확한 지적이고, 실제로 그 순서로 검토해야 한다(10-2). ?fields=name,grade 같은 부분 응답 파라미터나 화면 전용 BFF 엔드포인트로 충분하면 REST에 머무는 것이 총비용이 낮다.

여기서 07번이 정의한 BFF(Backend For Frontend, 특정 프론트엔드 하나를 위한 전용 백엔드)의 성격을 정확히 옮겨 오면 논지가 선명해진다. BFF는 재사용성을 대가로 왕복을 사는 거래다. "화면마다 다른 API"는 REST의 미덕인 재사용성을 정면으로 버리는 선택이지만, 대신 그 화면이 필요한 것을 정확히 한 번에 준다.

그렇다면 GraphQL은 언제 이기는가. BFF의 대가가 "재사용성"에서 "조직의 처리 속도"로 바뀌는 지점이다.

BFF로 충분한 구간

  • 화면이 새로 필요하면 → 백엔드 팀이 BFF 엔드포인트를 하나 추가한다
  • 화면 수가 적으면 이 추가가 부담이 아니다

BFF가 병목이 되는 구간

  • 클라이언트 종류(iOS·안드로이드·웹·태블릿) × 화면 수 × 필요 필드 조합 → 조합이 폭발한다
  • 엔드포인트 추가/수정 요청이 백엔드 팀 백로그에 쌓인다
  • 프론트 팀이 화면 하나 바꾸려고 다음 스프린트를 기다린다 ← 여기가 진짜 비용
GraphQL이 이기는 지점은 성능이 아니라 대기 시간이다 — 조합을 만드는 일을 클라이언트 팀에 넘겨 팀 간 대기 비용을 없앤다

즉 기술 선택처럼 보이지만 실은 팀 간 의존 구조를 바꾸는 결정이고, 그 필요가 없다면 도입하지 않는다. 판단 기준을 한 줄로 주면 — "백엔드 팀이 화면 요구의 병목이 되고 있는가"가 실측되면 GraphQL, 아니면 REST + BFF. 이렇게 조직 관점까지 답하면 시니어 변별이 된다.

gRPC(proto) 계약은 어떻게 하위 호환을 지키며 바꾸나요? 시니어 변별힌트: 규칙을 외우지 말고 "번호로 직렬화한다"에서 전부 유도한다

출발점은 사실 하나다 — Protobuf는 필드를 이름이 아니라 번호로 직렬화한다. 그래서 호환성 규칙이 전부 "번호"를 중심으로 정해진다(8-2 표).

새 번호로 추가는 안전(구버전은 모르는 번호를 무시한다), 번호 변경·타입 변경은 위험(같은 데이터가 다른 필드로 해석되거나 역직렬화가 깨진다), 이름만 변경은 와이어 호환은 안전하지만 생성된 코드의 접근자가 바뀌어 양쪽 소스가 깨진다, 삭제는 reserved로 번호를 못박아야 조건부 안전이다.

reserved가 왜 필요한지가 이 질문의 핵심이다. 3번 필드를 지운 뒤 나중에 누군가 새 필드에 3번을 붙이면, 아직 구버전 proto를 들고 있는 서비스는 새 데이터를 옛 3번 필드로 해석한다. 타입까지 우연히 맞으면 에러도 나지 않고 값만 엉뚱해진다. 그래서 지운 번호는 무덤에 이름표를 세우듯 못박아 둔다 — reserved 3, 7 to 9;와 reserved "legacy_status";로 번호와 이름을 함께 막는다.

실무 디테일 하나 — 자주 쓰는 필드는 1~15번에 배치한다. 태그 바이트가 1~15번은 1바이트, 16번부터는 2바이트를 쓰기 때문이다.

마지막으로 03·08번의 원칙과 나란히 놓으면 시각의 일관성이 드러난다. 두 문서의 대원칙("추가는 안전, 삭제·의미 변경은 파괴적 변경")의 근거는 Tolerant Reader였고, proto는 그 규약을 사람의 약속이 아니라 도구로 강제한다. 대신 번호는 유한하고 되돌릴 수 없다는 제약이 생긴다 — 계약 관리의 부담이 사라진 게 아니라 문서에서 도구로 옮겨간 것이다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

내부 통신이라면 무조건 gRPC가 낫지 않나요? JSON/REST는 느린데요.힌트: 6절 흐름도의 오른쪽 아래 잎(REST 유지)이 왜 있는지를 설명하는 문제다

아니다. "내부"는 gRPC의 필요조건이지 충분조건이 아니다. 6절 흐름도에서 서버↔서버 가지 아래에 다시 질문이 하나 더 있는 이유가 이것이다.

먼저 성능 이야기의 크기를 정확히 잡아야 한다. 데이터센터 내부는 RTT가 1ms 미만이라 페이로드 몇 백 바이트 차이는 대개 눈에 띄지 않는다. gRPC의 성능 이득이 실제로 나오는 자리는 ①초당 수천 건 규모라 직렬화 CPU가 누적되는 경로, ②페이로드가 큰 경로, ③커넥션 수립 비용이 반복되는 경로다. 하루 수백 건 도는 내부 배치 API라면 이 셋 중 어디에도 해당하지 않는다.

그리고 gRPC에도 비용이 있다. proto 관리와 코드 생성이 빌드 파이프라인에 들어가고, 디버깅에 grpcurl 같은 전용 도구가 필요하고, 기존 HTTP 기반 관측·게이트웨이 설정을 gRPC용으로 다시 갖춰야 한다. 팀에 이 경험이 없으면 이 학습 비용이 직렬화 이득보다 크다.

gRPC의 진짜 값은 성능보다 "컴파일러가 강제하는 계약"인 경우가 많다 — 특히 다언어 조직에서

그래서 답은 이렇게 된다 — "호출량·계약 불일치 장애·서버 푸시 중 실측된 통증이 있으면 gRPC, 없으면 REST를 유지합니다. 내부라는 사실만으로는 근거가 안 됩니다."

GraphQL을 도입하면 기존 REST 엔드포인트는 전부 없애야 하나요?힌트: GraphQL이 잘 못하는 일 목록을 떠올린다

아니다. 공존이 정상이다. GraphQL이 푸는 문제는 "조회 응답의 형태를 클라이언트가 정하게 하는 것" 하나이므로, 그 문제가 아닌 곳까지 옮길 이유가 없다.

REST에 남기는 게 나은 자리들.

  • 파일 업로드·다운로드 — 바이너리 스트림은 JSON 응답 모델과 잘 맞지 않고, 브라우저·CDN의 기본 동작(Range 요청, 이어받기)을 그대로 쓰는 편이 낫다.
  • CDN 캐싱이 중요한 공개 조회 — 7-4에서 본 대로 GraphQL은 캐싱을 잃는다. 변하지 않는 공개 데이터를 URL로 노출해 두면 CDN이 대신 감당한다.
  • 외부에서 들어오는 웹훅 수신, 헬스체크, 결제사 콜백 — 상대가 정해 준 계약이라 우리가 형태를 못 고른다.
  • 외부 파트너 API — 9절 배제 논리 그대로.

현실적인 도입 모습은 "전면 교체"가 아니라 "자사 앱의 화면 조회 경로만 GraphQL로 옮기고 나머지는 REST로 둔다"는 형태다. 그리고 이 그림이 곧 10절의 경계별 혼용이다 — 같은 시스템 안에 두 스타일이 공존하는 게 실패가 아니라 설계다.

GraphQL은 왜 하필 POST 단일 엔드포인트인가요? GET으로 하면 캐싱 문제가 없을 텐데요.힌트: 할 수는 있다. 왜 기본이 되지 못했는지를 말해야 한다

GET으로도 할 수 있다. 쿼리를 쿼리스트링에 실어 GET /graphql?query=...로 보내는 것은 규격상 가능하고, 많은 서버가 지원한다. 그런데 기본이 POST인 이유가 셋 있다.

  • ① 쿼리가 길다. GraphQL 쿼리는 필드를 전부 나열하므로 수백~수천 자가 되기 쉽다. URL 길이는 서버·프록시마다 상한이 제각각이라 "어디선가는 잘린다"는 위험을 안고 가야 한다.
  • ② mutation은 부작용이 있다. 같은 엔드포인트로 조회와 변경을 모두 보내는데 변경을 GET으로 보내면 안전(safe) 메서드 시맨틱을 깨뜨린다 — 중간 캐시나 프리페치가 임의로 재실행할 수 있다.
  • ③ 인코딩이 번거롭다. 중첩 중괄호와 변수 JSON을 URL 인코딩해 넣는 것은 가능하지만 사람이 읽기 어렵고 도구마다 처리가 갈린다.

그래서 나온 절충이 persisted query다(7-4). 긴 쿼리는 서버에 등록해 두고 짧은 해시 ID만 GET으로 보내면 ①과 ③이 동시에 해결되고, 조회만 GET으로 보내면 ②도 지켜진다. 즉 persisted query는 캐싱 회복 수단이자 "GET을 되찾는 수단"이라고 정리하면 앞뒤가 이어진다.

바깥은 REST, 안쪽은 gRPC로 하면 계약이 두 벌입니다. 스키마 중복은 어떻게 관리하나요? 시니어 변별힌트: "자동 변환하면 되죠"라고 답하면 오히려 감점 요소가 있다

먼저 전제를 뒤집어야 한다 — 두 벌인 것이 문제가 아니라 의도된 것이다. 09번(파트너 API vs 내부 API)의 결론과 같다. 내부 모델을 그대로 외부에 내보내면, 우리에겐 삭제 예정인 필드가 파트너에겐 계약된 필드가 되어 리팩터링이 몇 달짜리 폐기 절차에 묶인다. 계층마다 계약이 다른 것은 중복이 아니라 격리다.

그럼에도 관리 부담은 실재하므로 두 가지를 함께 쓴다.

  • 단일 원천(single source of truth)을 정한다. 내부 proto를 원천으로 삼고 외부 REST DTO는 손으로 쓰되, 매핑 코드가 컴파일 시점에 proto 변경을 감지하게 둔다. proto에서 필드가 사라지면 매핑 코드가 컴파일 에러를 낸다 — 이게 gRPC를 안쪽에 두는 부수 이득이다.
  • 외부 계약은 자동 생성하지 않는다. proto를 그대로 JSON으로 변환해 노출하는 방식(자동 트랜스코딩)은 편하지만, 내부 리팩터링이 그대로 외부 파괴적 변경이 되는 통로를 열어 준다. "편의를 위해 격리를 없애는" 선택이라는 걸 알고 써야 한다.

한 줄로 — "계약을 한 벌로 줄이는 게 목표가 아니라, 안쪽 변경이 바깥 계약을 흔들지 않게 하는 게 목표"다. 그래서 중간에 번역 계층(게이트웨이·BFF)을 두고, 그 계층을 의도적으로 유지비로 인정한다.

gRPC의 에러는 HTTP 상태 코드와 어떻게 다른가요?힌트: 8-1의 트레일러 도식을 그대로 재활용하면 된다

gRPC는 자기만의 상태 코드 집합을 쓰고, 그 값은 HTTP 상태 코드가 아니라 트레일러의 grpc-status에 실린다. 그래서 gRPC 호출이 실패해도 HTTP 계층에서는 대개 200으로 보인다 — 8-1 도식의 상태줄이 200 OK였던 이유가 이것이다.

운영에서 이 사실이 중요한 이유는 REST와 정반대의 함정이 생기기 때문이다. HTTP 상태 코드만 보는 대시보드·알람은 gRPC 서비스의 실패를 전부 놓친다. 로드밸런서의 "5xx 비율" 그래프가 평평한데 서비스는 죽어 있는 상황이 나온다. 그래서 gRPC 구간의 관측은 grpc-status를 읽을 수 있는 계층(gRPC 인식 프록시·인터셉터·전용 메트릭)에서 해야 한다.

공통점도 짚으면 좋다. 상태 코드 집합 자체는 REST의 4xx/5xx 구분과 발상이 같다 — "호출자가 고쳐야 하는 문제"(INVALID_ARGUMENT, NOT_FOUND, UNAUTHENTICATED)와 "우리가 고쳐야 하는 문제"(INTERNAL, UNAVAILABLE)를 가른다. 그리고 DEADLINE_EXCEEDED처럼 gRPC가 계약에 내장한 개념도 있는데, 클라이언트가 설정한 데드라인이 호출 체인을 타고 전파된다는 점이 REST의 개별 타임아웃 설정과 다른 지점이다.

"셋 중 뭘 좋아하세요"라고 물으면 어떻게 답해야 하나요? 함정힌트: 취향을 묻는 질문이 아니다

선호를 말하는 순간 이 질문의 의도에서 벗어난다. 이 질문은 "기술을 도구로 보는가, 정체성으로 보는가"를 보는 자리다.

답의 형태는 세 단계로 잡으면 안전하다.

1
축을 먼저 세운다 — "셋은 계약을 어디에 적고 누가 강제하는지가 다른 스타일이라, 선호보다 소비자가 누구인지로 갈립니다."
2
자리별로 배치한다 — "외부에는 REST, 화면 조합이 폭발하는 자사 클라이언트에는 GraphQL, 내부 고빈도 호출에는 gRPC를 씁니다."
3
경험을 배제 논리로 붙인다 — "제가 다뤄 본 건 REST가 대부분인데, 그 자리에 GraphQL을 넣지 않은 이유는 화면 조합이 적어 대가만 남는 거래였기 때문입니다." 안 쓴 이유를 대는 것이 써 본 것보다 강할 때가 많다.

피해야 할 답은 두 가지다 — "요즘은 GraphQL이 대세라 선호합니다"(전제 없이 결론만 들여오는 10-1의 실패 그 자체)와 "상황에 따라 다릅니다"에서 멈추는 것(맞는 말이지만 아무것도 말하지 않은 것). "상황에 따라 다릅니다 — 그 상황을 가르는 질문은 이 셋입니다"까지 가야 답이 된다.

한 줄 요약
REST/GraphQL/gRPC는 우열이 아니라 계약을 어디에 적고 누가 강제하는지가 다른 세 스타일이므로(URL과 메서드에 적고 문서가 강제 / 타입 스키마에 적고 검증기가 강제 / IDL 파일에 적고 컴파일러가 강제), 선택 축은 그 계약을 읽고 코드를 짜는 사람이 누구인가다 — 통제할 수 없는 외부에는 HTTP 생태계를 통째로 물려받는 REST, 응답 형태의 결정권이 서버에 있어 생기는 over/under-fetching이 화면 조합의 폭발로 백엔드 팀을 병목으로 만드는 자사 멀티 클라이언트에는 GraphQL(캐싱 무력화·필드 단위 인가·쿼리 비용·리졸버 N+1을 대가로), 우리가 배포하고 통제하는 서버 사이의 고빈도 호출에는 필드 번호 기반 바이너리 직렬화와 HTTP/2 멀티플렉싱의 gRPC(트레일러 헤더 때문에 브라우저에서는 프록시 없이 못 쓴다) — 그리고 실무는 경계마다 소비자가 다르므로 셋을 혼용하되, 각 기술의 전제가 없는 자리에 결론만 들여오면 이득 없이 대가만 남는다.
