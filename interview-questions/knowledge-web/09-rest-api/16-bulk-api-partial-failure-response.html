벌크 API의 부분 실패 응답 설계
성공/실패 이분법을 넘는 응답 모델 — "97건은 성공했다"를 어디에 적을 것인가

면접 질문: "여러 건을 한 번에 처리하는 벌크 API에서 일부만 실패하면 응답을 어떻게 설계하나요?"

핵심 관전 포인트 — 첫 결정은 기술이 아니라 도메인 질문이다. 이 묶음이 원자적(전부 성공 아니면 전부 취소, 중간 상태가 남지 않음)이어야 하는가, 부분 성공을 허용하는가. 원자적이면 전체를 한 트랜잭션으로 묶고 일반 에러 응답 하나로 끝나지만, 묶음이 클수록 트랜잭션이 길어지고 1건 때문에 99건이 계속 반려되는 처리량 문제를 떠안는다. 부분 성공이면 응답이 "항목별 결과 배열"로 바뀐다 — 클라이언트가 항목마다 부여한 식별자로 매칭하고(배열 인덱스에 의존하면 서버가 중복 제거·재정렬·병렬 처리를 하는 순간 대응이 어긋난다), 항목마다 성공/실패와 표준 에러 code를 담고, 전체 HTTP status는 200으로 준다. 200인 이유가 이 문제의 채점 포인트다 — 4xx를 주면 클라이언트 HTTP 라이브러리와 게이트웨이의 공통 재시도 로직이 바디를 열어보지 않고 상태 코드 숫자만으로 전체 실패로 판정해 요청 전체를 재시도하고, 이미 성공한 97건이 중복 처리된다. 대신 요청 수준의 실패(바디 파싱 불가, 인증 실패, 건수 초과)는 항목별 결과 이전의 문제이므로 4xx가 맞다 — "요청 수준은 status, 항목 수준은 바디"로 층을 나누는 것이 계약의 골격이다. 그리고 실패 항목만 골라 재시도할 수 있도록 재시도 가능 여부를 드러내고, itemId를 항목별 멱등성 키로 삼아 이미 성공한 항목의 재전송이 저장된 결과의 재생으로 흡수되게 만드는 것까지가 계약이다 — 이 결정이 클라이언트의 재시도 코드 구조를 결정한다.
  • 1
    스키마보다 앞선 결정이 하나 있다 — "일부 실패라는 상태를 허용할 것인가"다. 이체의 출금+입금처럼 묶음 전체가 하나의 의미 단위면 원자적으로 묶어 에러 응답 하나로 끝내고, 초대 100건처럼 항목이 서로 독립이면 부분 성공을 택한다. 바로 스키마부터 그리면 결정 하나를 건너뛴 답이 된다.
  • 2
    부분 성공을 택하면 응답은 "항목별 결과 배열"이 된다 — {"success":false,"message":"3건 실패"} 같은 요약만 주면 소비자에게 남는 선택지는 전체 재전송뿐이다. 결과마다 클라이언트가 부여한 itemId를 되돌려주고(배열 인덱스는 서버가 중복 제거·재정렬·병렬화하는 순간 깨진다), 항목 에러는 단건 API와 같은 표준 에러 스키마로 담고, summary로 최상단 분기를 열어 준다.
  • 3
    전체 status는 200 — 4xx를 주면 바디를 안 읽는 층이 전체 실패로 판정해 97건이 중복 처리된다. 대신 파싱 불가·인증 실패·건수 초과는 항목별 결과가 생기기 전의 문제라 4xx다. 여기에 재시도가 성립하려면 매칭 키 · 재시도 가능 여부 · itemId 멱등성 셋이 함께 있어야 하고, 하나라도 빠지면 소비자는 다시 전체 재시도로 몰린다.

0. 질문 + 출제 의도 — 가로(벌크) vs 세로(조합)

질문: "여러 건을 한 번에 처리하는 벌크 API에서 일부만 실패하면 응답을 어떻게 설계하나요?"

출제 의도: 100건 중 3건 실패 시 전체 롤백인지 부분 성공인지는 클라이언트의 재시도 설계까지 바꾸는 계약 결정이다. 성공/실패 이분법을 넘어 응답 모델을 설계하는지 확인한다.

이 페이지가 겨냥하는 약점 세 가지 ① 스키마부터 그리기 시작하는 것 → 1절에서 "원자적이냐 부분 성공이냐"라는 앞선 결정과 원자성이 청구하는 대가 두 가지를 먼저 세운다.
② "3건 실패했으니 400"이라는 직관 → 5절에서 바디를 열어보지 않는 층이 어떻게 97건을 중복 처리시키는지 인과 사슬로 편다. 결과가 아니라 메커니즘으로 말하는 것이 채점 포인트다.
③ 응답을 설계했는데 재시도가 안 되는 것 → 8절에서 매칭 키 · 재시도 가능 여부 · 멱등성 셋이 왜 세트로만 작동하는지, 9절에서 건수 한도를 감이 아니라 곱셈으로 정하는 법을 다룬다.

0-1. 먼저 자리를 잡자 — 이 문서의 "부분 실패"는 가로 방향이다

"부분 실패"라는 말은 두 가지 완전히 다른 상황에 쓰인다. 면접에서 이 둘을 섞으면 답이 흐려지므로, 시작할 때 어느 쪽 이야기인지 스스로 못 박고 들어가는 것이 좋다.

벌크 계약의 다른 축은 이미 다뤘다 — 여기서는 부분 실패만 판다 벌크 조회 API를 왜 만드는지(왕복 폭발, N+1의 위치 이동), 그리고 벌크 계약의 세 항목 "상·누·길"(상한 건수 · 누락 처리 · 길이 제한)은 07-chatty-api-call-explosion.md가 다룬다. 이 문서는 그중 쓰기 벌크에서 결과가 갈릴 때의 응답 모델만 파고든다.

1. 첫 결정 — 원자성은 도메인이 정한다

"일부 실패 시 어떻게 응답하나"보다 앞선 질문이 있다. 일부 실패라는 상태를 허용할 것인가. 이건 기술 선택이 아니라 업무 요구다. 이 갈림길을 건너뛰고 바로 스키마를 그리기 시작하면 결정 하나를 통째로 빠뜨린 답이 된다.

1-1. 전제 — 원자성이 정확히 무엇인가

원자성(atomicity)은 "전부 성공하거나 전부 없던 일이 되거나, 그 중간 상태가 남지 않는 성질"이다. 이름은 더 이상 쪼갤 수 없는 알갱이(atom)에서 왔다. 안에 여러 단계가 들어 있어도 바깥에서 보면 하나의 알갱이처럼 통째로 일어나거나 통째로 안 일어난다는 뜻이다.

이미 써 본 적이 있는 개념이다. 트랜잭션의 성질을 부르는 ACID의 A가 바로 이 원자성이고, @Transactional을 붙였을 때 얻는 것이 그것이다. 메서드 안에서 INSERT를 세 번 하다가 두 번째에서 예외가 나면 첫 번째 INSERT도 남지 않는다. 세 개의 쓰기가 하나의 알갱이로 묶였기 때문이다.

벌크 API의 첫 질문은 알갱이의 크기를 어디까지로 볼 것인가다

요청에 담긴 100건 전체가 하나의 알갱이인가,
아니면 100개의 알갱이가 한 봉투에 담겨 온 것인가

봉투(HTTP 요청 하나)와 알갱이(원자 단위)는 다른 개념인데, 벌크 API에서는 이 둘이 겹쳐 보여서 헷갈린다. "한 번에 보냈으니 한꺼번에 처리되겠지"는 봉투를 알갱이로 착각한 것이다. 답이 갈리는 순간 응답 모델 전체가 갈린다.

1-2. 두 갈래 — 무엇이 이 결정을 정하는가

한 줄 비유 — 이사와 편지 100통 이사는 짐의 절반만 옮겨진 상태가 의미가 없다. 전부 옮기거나 원래 집에 그대로 있거나다 — 원자적. 편지 100통 발송은 3통의 주소가 틀렸다고 나머지 97통을 회수하지 않는다 — 부분 성공. 어느 쪽인지는 짐과 편지의 성질이 정하는 것이지, 우체국의 기술이 정하는 것이 아니다.

1-3. 원자성은 공짜가 아니다 — 대가 둘

원자적 묶음 쪽을 고를 때 함께 떠안는 대가가 둘 있다. 이걸 알고 고르는 것과 모르고 고르는 것이 다르고, 면접에서는 그 차이가 그대로 드러난다.

① 묶음이 클수록 트랜잭션이 길어진다
100건을 한 트랜잭션으로 묶으면 그 트랜잭션은 100건이 다 끝날 때까지 열려 있고, 그동안 잡은 행 잠금도 계속 유지된다. 잠금 유지 시간이 길어지면 같은 행을 건드리는 다른 요청들이 줄줄이 대기하고, 트랜잭션 자체가 타임아웃에 걸릴 위험도 커진다.
② 1건의 반복 실패가 전체 배치를 영구 반려시킨다
3번 항목의 데이터가 잘못돼 있으면 그것이 고쳐질 때까지 나머지 99건은 몇 번을 재전송해도 계속 반려된다. 소비자가 할 수 있는 일은 실패 원인을 추측해 항목을 하나씩 빼 보는 것뿐이다 — 100건짜리 배치에서 이건 사실상 수작업이다.
그래서 면접에서의 순서 — 결정 → 대가 → 절충 "부분 성공으로 하겠습니다"만 말하면 선택의 절반만 보여준 것이다. "원자성이 필요한지를 먼저 묻고 → 원자성을 택하면 트랜잭션 길이와 영구 반려라는 대가가 따라오며 → 그래서 원자 단위를 최소로 쪼개고 그 사이를 부분 성공으로 두는 것이 현실적 절충"까지 세 박자로 말하면, 스키마 이야기가 결정 위에 얹힌 이야기가 된다.

2. 응답은 항목별 결과의 목록이 된다

부분 성공을 허용하는 순간, "성공했나요?"라는 단일 질문에 대한 단일 답은 성립하지 않는다. 응답이 어떻게 바뀌어야 하는지는 "이 응답을 받은 소비자가 무엇을 할 수 있는가"를 따져 보면 바로 나온다.

before 요약만 주는 응답
HTTP/1.1 200 OK

{
  "success": false,
  "message": "100건 중 3건 실패"
}

// 소비자가 할 수 있는 일:
//  · 실패한 3건이 무엇인지 → 모른다
//  · 그 3건만 고쳐서 재전송 → 불가능
//  · 남은 선택지 = 100건 전체 재전송
//    → 이미 성공한 97건이 중복 처리된다
after 항목별 결과 + 요약
POST /users/bulk-invite   // 요청
{
  "items": [
    { "itemId": "req-001", "email": "a@example.com" },
    { "itemId": "req-002", "email": "b@example" },
    { "itemId": "req-003", "email": "c@example.com" }
  ]                        itemId는 클라이언트가 부여
}

HTTP/1.1 200 OK           // 응답
{
  "summary": { "total": 3, "succeeded": 2, "failed": 1 },
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "results": [
    { "itemId": "req-001", "status": "SUCCESS", "userId": 501 },
    { "itemId": "req-002", "status": "FAILED",
      "code": "USER-002", "message": "이메일 형식이 아닙니다" },
    { "itemId": "req-003", "status": "SUCCESS", "userId": 502 }
  ]
}
before가 나쁜 이유는 "정보가 적어서"가 아니다 — 소비자를 가장 위험한 선택지로 몰기 때문이다 요약만 받은 소비자에게 남는 유일한 행동은 전체 재전송이고, 그건 이 문서 전체가 막으려는 중복 처리다. 응답 설계의 품질은 "소비자에게 남는 선택지"로 평가한다 — 이 관점이 3절(매칭 키)·8절(멱등성)까지 그대로 이어진다.

부분 성공 응답이 갖춰야 할 요소 넷 — "키 · 상 · 에 · 요"

① 매칭 키 — itemId→ ② 상태 — SUCCESS / FAILED→ ③ 에러 — 표준 code · message→ ④ 요약 — summary

이 넷이 각각 소비자의 서로 다른 행동을 떠받친다 — ①은 어느 항목인지 찾기, ②는 골라내기, ③은 고칠지 재시도할지 판단하기, ④는 배열을 열어볼지 말지 결정하기. 하나씩 3~4절에서 따로 본다.

3. 매칭 키 — 배열 인덱스는 어떻게 깨지는가

응답의 결과 하나가 요청의 어느 항목에 대한 답인지를 소비자가 알아내야 한다. 가장 손쉬운 방법은 배열 인덱스다 — "요청의 n번째 항목에 대한 답이 응답의 n번째 결과"라고 약속하는 것이다.

이 약속의 문제는 어디에도 적혀 있지 않다는 데 있다. 응답 JSON 어디에도 "이건 3번째 항목의 결과입니다"라는 정보가 없고, 순서라는 암묵적 계약만 있다. 그리고 암묵적 계약은 서버가 그 사실을 잊는 순간 조용히 깨진다.

한 줄 비유 — 이름표 없는 세탁물 세탁소에 옷 100벌을 맡기면서 "세 번째로 드린 게 제 코트예요"라고만 말하는 것과 같다. 세탁소가 같은 옷을 한 벌로 합치거나, 얼룩 심한 것부터 먼저 처리하거나, 두 대의 세탁기에 나눠 돌리는 순간 그 약속은 끝난다. 옷에 이름표를 붙이는 것이 itemId다.

3-1. 인덱스 대응을 깨는 네 가지 — 전부 "정상적인 개선"이다

서버 코드 요청 100건이 들어왔다. 아래 넷 중 하나라도 하면 인덱스 대응이 깨진다
// ① 중복 제거 — 같은 이메일이 두 번 들어왔으니 하나로 합친다
List<Item> targets = items.stream().distinct().toList();
// 요청은 100건인데 결과는 98건. 99번째부터 전부 한 칸씩 밀린다.

// ② 유효성 검사에서 걸린 항목을 앞으로 모은다 — "에러부터 보여주자"
List<Result> results = new ArrayList<>();
results.addAll(invalidItems.stream().map(Result::validationFailed).toList());
results.addAll(processed);
// 개수는 100건 그대로인데 순서가 완전히 뒤바뀐다. 개수가 맞아서 더 위험하다.

// ③ 병렬 처리 후 완료 순서로 결과를 담는다 — 처리량을 4배로 올렸다
items.parallelStream().forEach(item -> results.add(process(item)));
// 완료 순서는 비결정적이다. 같은 요청을 두 번 보내면 결과 순서가 다를 수도 있다.

// ④ 실패 항목을 재시도 큐로 빼고 성공분만 즉시 응답한다
// 요청 100건, 응답 97건.

인덱스를 깨는 네 가지 — "중 · 재 · 병 · 분"

① 중복 제거 ② 재정렬 ③ 병렬 처리 ④ 분리(큐로 이관)

외워야 할 진짜 포인트는 목록 자체가 아니라 이것이다 — 넷 다 서버 입장에서는 지극히 정상적인 개선이다. "순서를 지키자"는 규율로 막을 수 있는 문제가 아니라는 뜻이고, 그래서 규율이 아니라 스키마로 막아야 한다.

이 필드는 나중에 두 번째 임무를 맡는다 매칭을 위해 도입한 itemId가 8절에서 항목별 멱등성 키로 재활용된다. 한 필드가 "어느 결과인가"와 "다시 보내도 안전한가"를 동시에 떠받치는 것이 이 설계의 좋은 점이다 — 그래서 itemId는 있으면 좋은 필드가 아니라 계약의 축이다.

4. 항목 에러 스키마와 summary

4-1. 항목별 에러는 단건 API와 같은 모양으로

항목 하나가 실패했을 때 그 실패를 무슨 모양으로 담을 것인가. 답은 새로 만들지 말고 이미 있는 표준 에러 스키마를 그대로 쓰는 것이다.

기준 단건 API 실패 — 표준 에러 스키마
// POST /users 하나가 실패했을 때 (05번 문서의 표준)
{
  "code":    "USER-002",          기계 판독용
  "message": "이메일 형식이 아닙니다",  사람용
  "errors": [                      검증 상세
    { "field": "email",
      "reason": "이메일 형식이 아닙니다" }
  ],
  "traceId": "4bf92f35...e4736"      추적 진입점
}
벌크 항목 실패 — 매칭 키와 상태만 얹는다
// results[] 안의 실패 항목 하나
{
  "itemId": "req-002",              // 얹는 것 ①
  "status": "FAILED",               // 얹는 것 ②
  "code":    "USER-002",          // ↓ 아래는 왼쪽과
  "message": "이메일 형식이 아닙니다",  //   완전히 같은 모양
  "errors": [
    { "field": "email",
      "reason": "이메일 형식이 아닙니다" }
  ]
}
// traceId는 요청 전체에 하나뿐이므로
// 항목마다 반복하지 않고 응답 최상위에 한 번
같은 모양으로 맞추는 이유 = 소비자의 코드 재사용
소비자는 이미 단건 API용 에러 처리 로직을 갖고 있다 — code로 분기해 화면을 정하고, 모르는 코드는 status 기반으로 폴백하고, errors[]의 field를 보고 폼의 해당 칸에 빨간 줄을 긋는 코드다. 항목 에러가 같은 모양이면 그 함수를 항목 하나하나에 그대로 돌려 쓸 수 있다.
다른 모양을 쓰면 표준화가 절반만 성립한다
벌크 API만 {"reason": "..."} 같은 다른 모양을 쓰면, 소비자는 같은 실패를 두 가지 방식으로 처리하는 코드를 갖게 된다. 에러 스키마 표준화의 목적이 "파서를 한 번만 짜게 하는 것"이었는데, 벌크에서 그 원칙이 깨지면 표준화가 절반짜리가 된다.

4-2. summary — 대다수 소비자는 "전부 성공했는지"만 궁금하다

"summary": { "total": 100, "succeeded": 97, "failed": 3 }
① 순회 코드를 소비자마다 짜지 않게
요약이 없으면 소비자는 "전부 성공했는가"를 알기 위해 결과 100건을 전부 순회하며 세어야 하고, 그 순회 코드는 모든 소비자가 각자 짜게 된다. 서버가 이미 알고 있는 숫자이므로 그냥 실어 주는 편이 낫다.
② 정상 경로에서 배열을 아예 안 열게
failed가 0인지 아닌지로 최상단 분기가 가능해지므로 정상 경로에서는 결과 배열을 열어보지 않아도 된다. 100건 중 100건 성공이 압도적 다수인 API에서 이 분기 하나가 소비자 코드를 크게 단순화한다.
실물에도 같은 필드가 있다 Elasticsearch _bulk 응답의 "errors": true/false 불리언이 정확히 이 역할이다(11절). "실패가 하나라도 있으면 true" 하나로 소비자가 배열을 열지 말지 정한다.

5. 왜 200인가 — 4xx가 만드는 인과 사슬

여기가 이 문제의 채점 포인트다. "3건이 실패했으니 400이 맞지 않나"는 직관이 왜 위험한지를, 결과가 아니라 인과로 설명할 수 있어야 한다.

먼저 깔아야 할 전제 한 줄

HTTP 상태 코드는 우리 API를 직접 쓰는 클라이언트 코드만 읽는 것이 아니다
그리고 그 중간의 독자들은 바디를 열어보지 않는다

요청과 응답이 지나가는 길목의 여러 층 — HTTP 클라이언트 라이브러리, API 게이트웨이, 리버스 프록시, APM — 이 전부 이 숫자를 읽고 자기 동작을 결정한다. 이들이 바디를 안 읽는 것은 게을러서가 아니라, 바디를 파싱하려면 우리 API의 스키마를 알아야 하는데 알 방법이 없기 때문이다. (이 이중 축 이야기는 05-error-response-body-standardization.md 2-1·2-2가 자세히 다룬다.)

부작용은 재시도만이 아니다 — 성공분이 유실된 것처럼 보이는 문제 클라이언트 애플리케이션 코드에도 대개 "HTTP 에러면 공통 에러 핸들러로 보낸다"는 인터셉터가 있고, 그 핸들러는 바디를 성공 응답 파서로 넘기지 않는다. 그래서 화면에는 "요청에 실패했습니다"만 뜨고, 실제로는 97명이 초대된 상태가 된다. 사용자는 실패했다고 믿고 다시 누른다 — 재시도가 사람 손으로도 한 번 더 일어난다.

200의 의미를 정확히 번역하면

200 = "모든 항목이 성공했다"가 아니라
"이 요청을 우리가 제대로 받아 끝까지 처리했다"

등기 우편 접수증 비유가 이 감각을 잘 잡아 준다. 창구에서 100통을 접수하면 접수증(200)을 준다. 그 접수증은 "100통이 다 배달됐다"는 뜻이 아니라 "접수 절차가 정상적으로 끝났다"는 뜻이고, 통마다의 결과는 접수증에 붙은 목록(바디)에 적힌다.

같은 논리로 전 건이 실패해도 200 + 전부 FAILED가 일관적이다. 처리 자체는 정상적으로 끝났기 때문이다. "실패가 절반을 넘으면 status를 바꾼다" 같은 혼합 규칙은 금물이다 — 소비자 분기를 복잡하게 만들 뿐이고, 임계값을 넘나드는 요청마다 클라이언트의 처리 경로가 달라지는 불안정한 계약이 된다.

6. 207 Multi-Status와 206 Partial Content

상태 코드 목록을 뒤지다 보면 이 상황에 맞아 보이는 코드가 둘 나온다. 하나는 의미가 정확히 맞고, 다른 하나는 이름만 비슷할 뿐 완전히 다른 것이다. 둘 다 정확히 짚어야 한다.

207 Multi-Status — 의미는 정확히 맞다

  • WebDAV 명세(RFC 4918)에서 정의된 코드로, "여러 리소스에 대한 결과를 한 응답에 담는다"는 뜻이다.
  • WebDAV는 HTTP를 파일 시스템처럼 쓰기 위한 확장이라 "이 폴더 아래 파일 전부를 옮겨라" 같은 요청이 자연스럽고, 그때 파일마다 결과가 다를 수 있어서 이 코드가 만들어졌다.
  • 의미상으로는 벌크 API의 부분 실패와 정확히 같은 상황이다. 이 문서의 results[]가 곧 "여러 리소스에 대한 결과"다.

그런데 얻는 것이 별로 없다 — 인지도 문제

  • 일반 REST 생태계에서 이 코드를 아는 클라이언트 라이브러리·게이트웨이·모니터링 도구가 드물다.
  • 다행히 207은 2xx 계열이라 대부분의 도구가 "성공"으로 분류하므로 5절의 재시도 사슬 문제는 생기지 않는다. 이 점은 반드시 짚어야 한다 — 207은 안전하지만 무익한 쪽이지 위험한 쪽이 아니다.
  • 다만 특별 취급을 기대할 수 없으므로 결국 소비자가 바디를 열어봐야 하는 것은 200일 때와 같다.
쓴다면 반드시 함께 오는 조건 "우리 API에서 207은 항목별 결과를 확인하라는 뜻"임을 문서에 명시해야 한다. 표준 코드조차 계약 없이는 안전하지 않다는 것이 여기서 얻을 교훈이다. 조합 API의 부분 실패를 다루는 13-aggregation-api-partial-failure-contract.md도 같은 결론에 도달하는데, 그쪽은 "섹션별 성패"를, 이 문서는 "항목별 성패"를 다룰 뿐 코드 선택의 근거는 동일하다.

206 Partial Content — 이름 때문에 자주 오해받는다

206의 "부분"은 결과의 일부가 아니라 자원의 일부 바이트 구간이다
206이 실제로 쓰이는 곳
Range 요청 전용이다 — 클라이언트가 Range: bytes=1000-1999 같은 헤더로 "이 파일의 1000번째부터 1999번째 바이트만 달라"고 요청했을 때, 서버가 "요청한 구간만 보낸다"는 뜻으로 돌려주는 코드다. 동영상을 중간부터 재생할 때, 끊긴 다운로드를 이어받을 때 쓰인다.
벌크 응답에 쓰면 생기는 일
"항목 100개 중 97개만 성공했다"와는 아무 관계가 없다. Range를 이해하는 중간 장비가 Content-Range 헤더를 찾다가 없어서 혼란스러워할 수 있고, 얻는 것은 하나도 없다. "이름이 비슷해서 골랐다"는 인상만 남는다.
세 코드의 판정 — 면접에서는 "200을 씁니다"가 아니라 "셋을 다 검토했고 200을 씁니다"가 답이다.
코드원래 의미벌크 부분 실패에 쓸 수 있나판정
200 OK요청을 정상 처리했다쓴다. "요청을 제대로 받아 끝까지 처리했다"는 뜻으로 해석하고 항목별 성패는 바디에 담는다기본값 — 도구 전체가 이해한다
207 Multi-Status여러 리소스에 대한 결과를 한 응답에 담음 (WebDAV / RFC 4918)의미는 정확히 맞다. 2xx라 재시도 사슬 문제도 없다. 다만 일반 REST 도구가 특별 취급하지 않아 실익이 없다써도 되지만 문서에 의미 명시가 조건
206 Partial ContentRange 요청에 대해 자원의 일부 바이트 구간을 반환아니다 — 결과의 일부와 무관하다. Content-Range를 기대하는 중간 장비를 혼란시킬 수 있다쓰지 않는다
4xx요청 자체에 문제가 있다항목 실패에는 아니다(5절). 단, 요청 수준 실패에는 맞다 → 7절층을 갈라서 판단

7. 요청 수준 / 항목 수준 — 층으로 가른다

5절에서 "부분 실패에 4xx를 주면 안 된다"고 했지만, 4xx가 맞는 경우는 따로 있다. 이 구분을 못 하면 "벌크 API는 무조건 200"이라는 잘못된 규칙이 된다 — 그리고 그 규칙을 그대로 따르면 JSON이 깨진 요청에도 200을 주는 이상한 API가 나온다.

판정 기준은 딱 한 문장이다

그 실패가 항목별 결과를 만들기 전에 일어났는가?
= 응답에 담을 results 배열이 존재할 수 있는가
층별 판정표 — 면접에서 이 표의 가운데 열(항목별 결과가 존재하는가)을 근거로 말하면 규칙이 아니라 원리로 들린다.

거절할 때는 한도를 알리는 에러 code를 함께 줘야 소비자가 "몇 건까지 되는지"를 코드로 알 수 있다. "요청이 잘못되었습니다"만 주면 소비자는 건수를 줄여 가며 이진 탐색을 하게 된다.

8. 재시도 3요소 — 매칭 · 판별 · 멱등

부분 성공 계약의 진짜 어려움은 응답 그 자체가 아니라 그다음 동작에 있다. 소비자는 응답을 받고 나서 실패한 3건만 골라 다시 보내게 되는데, 그 재시도가 안전하게 성립하려면 응답 모델이 몇 가지를 더 갖춰야 한다.

실패 3건만 재시도하게 하려면 응답에 무엇이 있어야 하나 — "매 · 재 · 멱"

① 매칭 — 어느 항목인지 (itemId)→ ② 재시도 판별 — 다시 보낼 가치가 있는지→ ③ 멱등 — 다시 보내도 안전한지
셋 중 하나라도 빠지면 소비자는 "전체 재시도"라는 가장 위험한 선택지로 몰린다

순서에도 의미가 있다. ①이 없으면 ②·③을 물어볼 대상 자체가 없고, ②가 없으면 무엇을 다시 보낼지 못 정하고, ③이 없으면 정했어도 보낼 수 없다. 셋은 세트로만 작동한다 — 이것이 이 절의 결론이다.

8-1. ② 재시도 가능 여부를 항목 에러에 담는다

실패한 3건을 그대로 다시 보내면 되는가. 실패의 종류에 따라 다르다.

비재시도성 — "이메일 형식이 아닙니다"

  • 데이터를 고치지 않는 한 몇 번을 다시 보내도 똑같이 실패한다.
  • 사용자에게 노출해 고치게 해야 할 문제다.
  • 자동 재시도 대상으로 잡으면 형식 오류 항목을 영원히 반복 전송하게 된다.

재시도성 — "일시적 저장 실패"

  • 잠시 후 다시 보내면 성공할 수 있다.
  • 사람 개입 없이 자동 재시도 대상으로 삼아도 된다.
  • 사용자에게 노출하면 자동으로 회복될 수 있었던 항목까지 사람 손을 타게 된다.

이 구분이 응답에 드러나지 않으면 소비자는 실패 3건 전부를 같은 방식으로 다룰 수밖에 없다. 드러내는 방법은 둘이고, 어느 쪽이든 목적은 하나 — 소비자가 재시도 대상을 사람 판단 없이 기계적으로 고를 수 있게 하는 것이다.

방법 A — 에러 code 체계 자체에 드러낸다
검증 실패 계열과 일시 오류 계열의 접두사를 나눈다. 이미 표준 에러 code 체계가 있다면 추가 필드 없이 구분이 따라온다는 것이 장점이다.
방법 B — retryable: true/false 필드를 따로 둔다
소비자가 code 목록을 몰라도 필드 하나로 분기할 수 있다. 새 에러 코드가 늘어나도 소비자 코드를 안 고쳐도 된다는 것이 장점이다.
운영 관점의 부산물 — 알람이 의미를 갖는다 항목 실패 중 서버 오류 비율은 서버 상태를 보여주는 지표라 집계·알람 대상이지만, 입력 오류 비율은 소비자의 데이터 품질 문제라 알람으로 울리면 노이즈다. 구분이 없으면 이 둘이 한 지표에 섞여 — 파트너가 잘못된 CSV를 올린 날 서버 알람이 울린다.

8-2. ③ 항목 처리는 멱등해야 한다 — itemId를 항목별 멱등성 키로

재시도 설계에서 가장 중요한 대목이다. 먼저 상황을 정확히 그려야 한다. 소비자가 항상 "실패한 3건만" 골라 보내는 것은 아니다. 응답을 아예 못 받는 경우가 있기 때문이다.

응답을 못 받은 클라이언트가 아는 것은 "응답을 못 받았다"뿐이다 서버가 100건을 다 처리하고 응답을 쓰는 도중에 연결이 끊기면, 클라이언트는 몇 건이 처리됐는지, 아니 하나라도 처리됐는지조차 모른다. 이 불확실성은 원리적으로 해소할 수 없다(06-idempotency-key-design.md 1-2). 그래서 클라이언트의 유일한 선택지는 요청 전체를 그대로 재전송하는 것이 되고, 그 순간 이미 성공한 97건이 두 번 처리될 위험이 생긴다.

해법은 06번 문서의 설계를 항목 단위로 축소해 적용하는 것이다. 요청의 itemId를 항목별 멱등성 키로 삼는다. 06번의 두 핵심 개념을 그대로 가져온다.

선점 후 처리
"이미 처리했나?"를 조회로 확인하고 없으면 처리하는 것이 아니라, 유니크 제약이 걸린 키를 먼저 꽂아 보고 꽂혔으면 내가 처음이라고 판정한다. 검사와 선점이 SQL 한 문장에서 원자적으로 끝나므로 동시에 도착한 두 요청이 나란히 통과하는 틈이 없다.
재생(replay)
이미 처리된 키로 다시 온 요청에는 처리를 다시 하지 않고 저장해 둔 최초 결과를 그대로 돌려준다. 실패를 알리는 것이 아니라 성공했을 때와 같은 답을 주는 것이 핵심이다 — 그래야 소비자가 "1번 보낸 것과 2번 보낸 것"을 구분할 수 없게 된다.

8-3. 반드시 정해야 하는 세부 — itemId는 어느 범위에서 유일해야 하는가

요청 하나 안에서만 유일하면 안 된다 어제 보낸 배치의 req-001과 오늘 보낸 배치의 req-001이 다른 사람인데 같은 키가 되어, 오늘의 초대가 어제 결과의 재생으로 삼켜진다. 이번엔 중복이 아니라 누락이다 — 그리고 응답은 SUCCESS로 나가므로 아무도 눈치채지 못한다. 06번 문서가 키 스코프를 (user_id, idempotency_key)로 잡았던 것과 정확히 같은 문제다.
선택지 A — itemId 자체를 소비자 단위로 유일하게(UUID 등)
서버 구현이 단순하다. 대신 "요청마다 새 값을 만들지 말고, 같은 항목의 재전송에는 같은 값을 유지하라"까지 계약에 적어야 한다 — 이걸 안 적으면 소비자가 재전송 때 UUID를 새로 만들어 멱등성이 통째로 무력화된다.
선택지 B — 배치 키 + itemId 복합 키
요청 수준의 배치 키를 따로 받고 (배치 키, itemId)를 복합 키로 쓴다. itemId는 배치 안에서만 유일하면 되므로 소비자 부담이 적다. 대신 재전송할 때 배치 키도 같이 유지해야 한다.
TTL은 성능 파라미터가 아니라 안전 파라미터다 멱등성 레코드의 보관 기간도 같은 이유로 계약이다. 보관 기간이 지난 뒤에 도착한 재전송은 "처음 보는 키"로 처리되므로 그대로 중복이 된다. 06번 2-7의 결론이 여기에도 그대로 적용된다 — 어느 선택지를 고르든, 그리고 TTL이 얼마든, 계약 문서에 적어야 계약이 된다.

8-4. 순서와 독립성도 계약에 적는다

응답 모델만큼이나 자주 빠지는 계약 항목이 있다. 항목 간 순서를 보장하는가, 앞 항목의 실패가 뒤 항목 처리에 영향을 주는가.

계약이 없으면 소비자가 잘못된 가정 위에 요청을 만든다

"1번 항목에서 그룹을 만들고 2번 항목에서 그 그룹에 사용자를 넣는" 요청을 보내는 소비자가 나온다. 서버가 병렬로 처리한다면 이 요청은 대부분 실패하고 가끔 우연히 성공한다 — 가장 나쁜 종류의 버그다. 재현이 안 되고, 부하가 낮은 스테이징에서는 잘 되기까지 한다.

부분 성공 모델과 짝을 이루는 계약

"각 항목은 독립적으로 처리되며 순서는 보장하지 않는다." 항목이 서로 독립적이라는 것이 애초에 부분 성공을 선택한 근거였으므로(1절) 이 문장이 일관적이다. 그리고 순서를 보장하지 않는다고 명시해야 3절의 병렬 처리·중복 제거 같은 최적화를 나중에 자유롭게 넣을 수 있다.

9. 건수 한도 — 곱셈 하나로 검산한다

벌크 API에는 요청당 최대 건수를 계약에 명시한다. 무제한이면 페이로드 크기·처리 시간·트랜잭션 길이가 전부 소비자 손에 좌우되고, 타임아웃과 부분 실패 확률만 커지기 때문이다. 문제는 그 한도를 어떻게 정하느냐다 — "1,000건쯤이면 되겠지"는 근거가 아니다.

근거는 곱셈 하나로 나온다

건당 처리 시간 × 한도 ≤ 이 요청의 실질 타임아웃 상한

여기서 "실질 타임아웃 상한"이 무엇인지가 중요하다. 요청 하나는 클라이언트 SDK · CDN · 로드밸런서 · Nginx · 앱이라는 여러 층을 지나고 각 층이 자기 대기 상한을 들고 있으므로 그중 가장 짧은 값이 이 요청의 실질 상한이다. 잘 정렬된 스택에서도 그 값은 10초 안팎이다(08-network-http/13-nginx-tomcat-timeout-buffer-mismatch.md의 정렬 예시 기준으로 앱 자체 가드가 10초, 그 안쪽 최악 처리 시간이 8초다).

역산 표 — 병렬 행이 흥미롭다. 병렬화를 하려면 itemId 매칭이 먼저 있어야 한다는 뜻이기 때문이다(3절과의 연결).

10. 구현이 계약을 깨는 자리 — 트랜잭션 경계 시니어 변별

여기까지가 계약이었다. 그런데 계약을 정확히 정해 놓고도 구현 한 줄 때문에 그 계약이 성립하지 않는 지점이 하나 있다. 면접에서 이 자리를 짚으면 "스펙을 그려 본 사람"과 "만들어 본 사람"이 갈린다.

"부분 성공"을 계약으로 정했는데 서비스 메서드 전체에 @Transactional이 붙어 있다면 1절에서 정한 알갱이의 크기가 구현에서 다시 100건 전체로 되돌아간 것이다. 그리고 이 되돌아감은 조용하지 않다 — 아래처럼 커밋 시점에 예외로 터진다.
before 항목마다 try/catch 했는데 커밋에서 전부 터진다
@Transactional                       알갱이 = 100건 전체
public BulkResponse invite(BulkRequest req) {
  var results = new ArrayList<Result>();
  for (var item : req.items()) {
    try {
      var user = userService.invite(item);  // 내부도 @Transactional
      results.add(Result.success(item.itemId(), user.id()));
    } catch (BusinessException e) {          // 삼켰다고 생각하지만
      results.add(Result.failed(item.itemId(), e.code()));
    }
  }
  return new BulkResponse(results);
}
// 내부 @Transactional은 기본 전파(REQUIRED)라 바깥 트랜잭션에
// 참여한다. 거기서 예외가 나면 그 트랜잭션은 rollback-only로
// 표시되고, 바깥에서 예외를 삼켜도 표시는 지워지지 않는다.
// → 메서드가 끝나고 커밋할 때 UnexpectedRollbackException.
//   97건도 전부 롤백. 계약은 부분 성공인데 결과는 전부 실패다.
after 알갱이를 항목으로 — 오케스트레이션에는 트랜잭션을 걸지 않는다
// 바깥: 트랜잭션 없음. 결과를 모으기만 한다
public BulkResponse invite(BulkRequest req) {
  validateBatchSize(req);          층① 요청 수준 (7절)
  var results = new ArrayList<Result>();
  for (var item : req.items()) {
    results.add(itemProcessor.process(req.batchKey(), item));
  }
  return BulkResponse.of(results);   summary는 여기서 집계
}

// 안쪽: 항목 하나가 트랜잭션 하나 = 알갱이 하나
@Transactional
public Result process(String batchKey, Item item) {
  try {
    if (!keys.tryInsert(batchKey, item.itemId())) {  // 선점 후 처리
      return keys.replay(batchKey, item.itemId());   // 재생 (8-2)
    }
    var user = userService.invite(item);
    return keys.saveAndReturn(Result.success(item.itemId(), user.id()));
  } catch (BusinessException e) {
    return Result.failed(item.itemId(), e.code(), e.retryable());
  }                                  이 항목만 롤백된다
}
왜 조용하지 않은가
Spring 기본 전파는 REQUIRED라 내부 호출이 바깥 트랜잭션에 참여한다. 거기서 런타임 예외가 나면 그 트랜잭션에 rollback-only 표시가 찍히고, 바깥에서 예외를 catch해도 그 표시는 지워지지 않는다. 그래서 커밋 시점에 UnexpectedRollbackException이 난다.
catch 위치를 옮기는 것만으로는 안 된다
try/catch를 안쪽으로 옮겨도 트랜잭션 경계가 바깥에 있으면 같은 일이 일어난다. 고쳐야 하는 것은 예외 처리 위치가 아니라 트랜잭션 경계다 — 이것이 "알갱이의 크기"를 코드로 말한 것이다.
경계를 옮기면 따라오는 것들
항목마다 커밋이 나므로 잠금 유지 시간이 항목 단위로 짧아지고(1-3의 대가 ①이 해소된다), 실패 항목만 롤백되며, 선점 후 처리·재생을 항목 트랜잭션 안에 자연스럽게 넣을 수 있다.
한 가지 더 — REQUIRES_NEW로 때우려 할 때의 함정 "바깥 @Transactional은 두고 안쪽만 REQUIRES_NEW로" 하면 예외는 격리되지만, 바깥 트랜잭션이 커넥션을 붙잡은 채 안쪽이 커넥션을 하나 더 꺼내 쓴다. 벌크 요청 하나가 커넥션 2개를 물게 되고, 동시 벌크 요청이 늘면 풀이 마르면서 서로가 서로를 기다리는 상황이 된다. 더 나은 형태는 오케스트레이션 메서드에 아예 트랜잭션을 걸지 않는 것이다 — 애초에 그 층에서 원자성이 필요 없다는 것이 1절의 결정이었기 때문이다.

11. 실무 사례 — ES _bulk · SQS SendMessageBatch 가산점

"성공 응답 안에 실패가 들어 있는" 모양은 처음엔 어색하지만, 항목 독립적인 벌크 처리의 표준 형태다. 대형 API들이 이미 같은 결론에 도달해 있다는 것을 사례로 들면 설득력이 붙는다.

11-1. Elasticsearch _bulk — 200 + errors 플래그 + 항목별 status

사례 색인·수정·삭제 여러 건을 한 번에 보내는 API의 응답
// POST /_bulk 응답 — HTTP 상태 코드는 200이다
{
  "took": 30,
  "errors": true,          // 요약 플래그: 실패가 하나라도 있으면 true
  "items": [               // 항목별 결과 배열 — 요청 순서와 같은 순서로 담긴다
    { "index": { "_id": "1", "status": 201, "result": "created" } },
    { "index": { "_id": "2", "status": 400,
                 "error": { "type": "...", "reason": "..." } } }
  ]
}
첫째 — 개별 항목이 실패해도 HTTP는 200
5절의 결론과 같다. "요청을 제대로 받아 끝까지 처리했다"가 200의 뜻이라는 것을 실물이 보여준다.
둘째 — errors 불리언이 summary 역할
4-2의 요약 필드다. 전수 순회 없이 최상단 분기가 가능하다.
셋째 — 항목마다 HTTP status 형태의 status
항목 결과를 단건 API의 결과와 같은 어휘로 표현한 것이라, 4-1의 "항목 에러는 단건 API와 같은 스키마로"와 같은 발상이다.

참고로 ES는 요청당 건수 상한을 못 박기보다 요청 크기와 노드 부담을 기준으로 조정하라고 안내한다 — 9절에서 "건수와 본문 크기 중 먼저 걸리는 쪽이 실질 한도"라고 한 것과 같은 관점이다.

11-2. AWS SQS SendMessageBatch — 클라이언트 Id · 두 목록 · SenderFault

요청의 각 엔트리에 클라이언트가 부여한 Id
그 값은 배치 안에서 유일해야 한다. 3절의 itemId가 이것이고, 8-3의 선택지 B(배치 스코프)에 해당한다.
응답이 Successful과 Failed 두 목록으로
각 엔트리가 자기 Id를 달고 돌아온다. 실패 엔트리에는 에러 Code와 Message가 담긴다.
SenderFault 불리언
8-1과 정확히 같은 정보다 — 실패의 책임이 보낸 쪽에 있는지(그러면 요청을 고치기 전엔 재시도가 무의미하다) 서비스 쪽에 있는지(그러면 재시도로 회복될 수 있다)를 기계가 판단할 수 있게 해 준다.
요청당 최대 10건
9절의 "건수 한도는 계약에 적는다"의 실물이다. 숫자가 작다는 것도 시사적이다 — 한도는 관대할수록 좋은 값이 아니다.
두 목록으로 나눌 것인가, 하나의 배열에 담을 것인가 두 목록(SQS 방식)은 소비자가 실패분을 골라내는 필터링이 필요 없어 재시도 코드가 짧아진다. 하나의 배열(ES 방식)은 요청 순서와의 대응이 남아 있어 화면에 그대로 늘어놓기 좋다. 어느 쪽이든 "매칭 키가 결과에 실려 있다"는 것이 본질이고, 배열이냐 두 목록이냐는 그 위의 취향이다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

이 문서의 뼈대 셋 — "결정 → 모델 → 재시도"

① 결정 — 원자적인가 부분 성공인가→ ② 모델 — 200 + itemId 매칭 결과 배열→ ③ 재시도 — 매 · 재 · 멱

순서에 의미가 있다. ①이 정해져야 응답 모델이 정해지고, ②가 정해져야 재시도가 성립한다. 그래서 스키마부터 그리기 시작하는 답은 첫 칸을 비워 놓은 답이 되고, 응답까지만 말하는 답은 마지막 칸을 비워 놓은 답이 된다.

첫 문장은 무엇으로 시작하나?
스키마가 아니라 도메인 질문으로. "이 묶음이 원자적이어야 하는지부터 정해야 합니다 — 한 항목이 실패했을 때 나머지를 살려도 업무적으로 말이 되는가."
원자성의 대가 둘?
① 트랜잭션이 길어져 잠금 유지 시간·타임아웃 위험 증가. ② 1건의 반복 실패가 전체 배치를 영구 반려시킨다. 그래서 원자 단위를 최소로 쪼개고 그 사이는 부분 성공이 절충.
부분 성공 응답의 4요소?
"키·상·에·요" — 매칭 키(itemId) · 상태(SUCCESS/FAILED) · 에러(표준 code) · 요약(summary).
인덱스 매칭을 깨는 넷?
"중·재·병·분" — 중복 제거 · 재정렬 · 병렬 · 분리. ②재정렬이 가장 위험하다 — 개수가 같아 감지가 안 된다.
왜 200인가? (한 문장)
"4xx를 주면 바디를 열어보지 않는 HTTP 라이브러리·게이트웨이가 전체 실패로 판정해 요청 전체를 재시도하고, 이미 성공한 97건이 중복 처리됩니다."
그럼 4xx는 언제?
요청 수준일 때 — 파싱 불가·인증 실패·건수 초과. 기준은 "results 배열이 존재할 수 있는가". 규칙 한 줄: 요청 수준은 status, 항목 수준은 바디.
207 / 206 판정?
207(WebDAV·RFC 4918)은 의미는 맞고 2xx라 안전하지만 실익이 없다 — 쓰려면 문서에 명시. 206은 Range 전용이고 "부분"이 바이트 구간을 뜻하므로 무관하다.
실패 3건만 재시도하려면?
"매·재·멱" — 매칭 키 · 재시도 가능 여부 · 멱등성. 하나라도 빠지면 소비자는 전체 재시도로 몰린다.
멱등성의 두 동작?
선점 후 처리(유니크 키를 먼저 꽂아 보고 꽂히면 내가 처음) + 재생(이미 처리된 키엔 저장된 최초 결과를 그대로 반환). 실패를 알리는 게 아니라 같은 답을 준다.
itemId 스코프를 안 정하면?
어제의 req-001과 오늘의 req-001이 충돌해 오늘의 초대가 어제 결과의 재생으로 삼켜진다 — 중복이 아니라 누락이고, 응답은 SUCCESS라 아무도 모른다. TTL도 같은 이유로 안전 파라미터.
건수 한도의 근거는?
건당 처리 시간 × 한도 ≤ 실질 타임아웃 상한. 20ms × 1,000 = 20초인데 실질 상한은 10초 안팎 → 이미 깨진 값. 예산 8초로 역산하면 400건, 여유 두면 200건.
구현에서 계약이 깨지는 자리?
오케스트레이션 메서드의 @Transactional. 항목별 try/catch를 해도 rollback-only 표시가 남아 커밋에서 UnexpectedRollbackException — 고칠 것은 예외 처리 위치가 아니라 트랜잭션 경계다.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

부분 성공일 때 HTTP 상태코드는 뭘로 주나요? 207을 써도 되나요? 필수힌트: "200입니다"로 끝내면 절반이다. 4xx가 만드는 인과 사슬을 결과가 아니라 메커니즘으로 말하고, 4xx가 맞는 경우까지 층을 갈라 닫는다

200 + 바디의 항목별 결과가 일반적 관례다. 핵심은 그 이유를 인과로 말하는 것이다 — 부분 실패를 4xx/5xx로 주면 HTTP 계층(라이브러리 재시도, 게이트웨이, 모니터링)이 바디를 열어보지 않고 전체 실패로 해석해, 성공분까지 재시도되는 중복 처리가 난다.

400 응답→ 중간 층은 바디를 안 읽는다→ "전체 실패" 판정→ 100건 전체 재시도→ 97건 중복 처리

여기에 "성공분이 유실된 것처럼 보이는" 부작용을 얹으면 답이 두꺼워진다 — 클라이언트의 공통 에러 인터셉터도 바디를 성공 파서로 넘기지 않으므로 화면엔 "요청에 실패했습니다"만 뜨고, 실제로는 97명이 초대돼 있다. 사용자가 다시 누르면서 재시도가 사람 손으로도 한 번 더 일어난다.

207 Multi-Status는 WebDAV(RFC 4918)에서 온 코드로 의미상으로는 정확하지만, WebDAV 밖에서는 인지도가 낮아 특별 취급을 기대할 수 없다. 다만 2xx 계열이라 위 사슬 문제는 생기지 않으므로 "위험하다"가 아니라 "실익이 없다"가 정확한 평가다. 채택하려면 문서에 의미를 명시해야 한다. 206 Partial Content는 이 상황과 무관하다 — Range 요청 전용이고, 여기서 "부분"은 결과의 일부가 아니라 자원의 일부 바이트 구간을 뜻한다.

단, 바디 파싱 불가·인증 실패·건수 초과처럼 "요청 수준"의 실패는 항목별 결과 이전의 문제라 4xx가 맞다

요청 수준과 항목 수준을 층으로 나눠 답하는 것이 이 질문의 마무리다. 그래야 "무조건 200"이라는 잘못된 규칙으로 들리지 않는다.

실패한 3건만 재시도하게 하려면 응답에 무엇이 있어야 하나요?힌트: 셋을 나열하고 끝내지 말고, "하나라도 빠지면 어떻게 되는지"로 닫으면 왜 세트인지가 드러난다
1
어느 항목이 실패했는지 특정할 매칭 키 — 배열 인덱스 의존보다 클라이언트가 부여한 itemId가 안전하다. 서버가 중복 제거를 하거나, 유효성 실패 항목을 앞으로 모으거나, 병렬 처리 후 완료 순서로 담는 순간 인덱스 대응이 어긋나기 때문이다. 특히 재정렬은 개수가 같아 클라이언트가 감지조차 못 한다.
2
재시도할 가치가 있는지 판단할 정보 — 항목별 에러 code에 검증 실패(비재시도성)와 일시 오류(재시도성)의 구분이 드러나야 한다(또는 retryable 필드). 없으면 소비자는 전부 자동 재시도(형식 오류를 영원히 반복)하거나 전부 사람에게 노출(자동 회복 가능한 것까지 수작업)하는 양극단 중 하나를 고르게 된다.
3
재시도가 안전하다는 보장 — itemId를 항목별 멱등성 키로 삼아 이미 처리된 항목의 재전송이 저장된 결과의 재생으로 흡수되게 한다. 이게 필요한 이유는 소비자가 항상 "실패한 3건만" 보내는 것이 아니기 때문이다 — 응답을 아예 못 받으면 전체 재전송 말고 선택지가 없다.
셋 중 하나라도 빠지면 소비자는 "전체 재시도"라는 가장 위험한 선택지로 몰린다

이 한 줄로 닫으면 세 요소가 왜 함께여야 하는지가 드러난다. 나열이 아니라 구조로 들린다.

전체 롤백(원자적)과 부분 성공은 어떤 기준으로 정하나요? 시니어 변별힌트: 기준을 말한 뒤 두 가지를 얹는다 — "누가 정하는가"와 "원자성의 청구서"

기준은 항목 간 의존성과 실패의 업무적 의미다. 항목들이 하나의 의미 단위(이체의 출금+입금, 분개의 차변+대변)면 원자적이어야 하고, 서로 독립(초대 100건, 태그 일괄 지정)이면 부분 성공이 소비자 가치가 크다.

여기에 두 가지를 얹으면 시니어답다.

① 백엔드 혼자 정할 수 없는 제품 결정이다
같은 "실패 3건"도 화면에서 무엇을 보여줄지가 완전히 달라진다 — 전체 롤백이면 "다시 시도하세요" 하나지만, 부분 성공이면 성공 목록과 실패 목록을 나눠 그리고 실패분만 수정·재전송하는 UI가 필요하다. 그래서 기획·프론트와 합의해 스펙에 명시해야 한다.
② 원자성은 공짜가 아니다
묶음이 클수록 트랜잭션이 길어져 락 유지 시간과 타임아웃 위험이 커지고, 1건의 반복 실패가 전체 배치를 영구 반려시킨다 — 소비자는 원인을 추측해 항목을 하나씩 빼 보는 수밖에 없다.
결론은 "원자성이 꼭 필요한 최소 단위로 묶음을 쪼개고, 그 사이는 부분 성공으로"

이체 100건이라면 "출금+입금" 쌍 하나가 원자 단위이고 100개의 쌍 사이에는 원자성이 필요 없다. 그러면 응답은 자연히 "쌍 100개 중 97쌍 성공"이라는 부분 성공 모델이 된다 — 두 선택지가 배타적이지 않다는 것이 이 답의 핵심이다.

벌크 요청의 건수 제한은 왜 필요한가요? 얼마로 정하나요?힌트: "타임아웃 때문에"까지는 누구나 말한다. 숫자로 검산하고, 한도를 넘는 작업의 대안까지 말한다

무제한 벌크는 처리 시간과 페이로드 크기를 소비자가 결정하게 만든다. 건수가 커질수록 HTTP 타임아웃 안에 못 끝날 확률 · 메모리 사용량 · (원자적 설계라면) 트랜잭션 길이가 함께 자란다. 그리고 타임아웃으로 응답을 못 받으면 소비자는 전체 재시도를 하게 되어 부분 실패 문제를 더 키운다.

숫자로 근거를 대면 답의 무게가 달라진다.

20ms × 1,000건 = 20초
감으로 정한 한도의 최악 시간
실질 상한 ≈ 10초
계층 스택에서 가장 짧은 값
예산 8초 → 400건 / 여유 두면 200건
8,000 ÷ 20 으로 역산

"그 한도는 이미 지켜질 수 없는 값"이라는 판정이 이 답의 포인트다 — 한도를 둔 목적이 타임아웃 방지였는데 한도 자체가 타임아웃을 보장하고 있다.

그래서 요청당 최대 건수를 계약에 명시하고 초과 시 요청 수준 4xx로 거절하며, 그 한도를 넘는 작업은 여러 요청으로 나누거나 비동기 작업(202 + 상태 조회) 모델로 넘긴다. 10만 건짜리 작업은 한도를 조절할 문제가 아니라 모델을 바꿔야 할 문제라는 선까지 그으면 좋다. 덧붙여 본문 크기 한도도 함께 적어야 한다 — 건수와 크기 중 먼저 걸리는 쪽이 실질 한도다.

일부는 입력 오류, 일부는 서버 오류로 실패했다면 응답에서 구분해야 하나요?힌트: "해야 한다"의 근거를 소비자의 다음 행동에서 찾고, 운영 관점(알람)을 하나 더 얹는다

구분해야 한다 — 소비자의 다음 행동이 다르기 때문이다. 입력 오류 항목은 데이터를 고치기 전엔 재시도가 무의미하므로 사용자에게 노출해야 하고, 서버 오류 항목은 그대로 재시도하면 되므로 자동 재시도 대상이다. 항목별 에러를 표준 에러 code 체계로 담으면 이 구분이 자연히 따라온다(또는 retryable 필드를 명시적으로 둔다).

운영 관점을 함께 말하면 좋다 항목 실패 중 서버 오류 비율은 서버 상태의 지표라 집계·알람 대상이지만, 입력 오류는 소비자의 데이터 품질 문제라 알람 노이즈다. 구분이 없으면 이 둘이 한 지표에 섞여, 파트너가 잘못된 CSV를 올린 날 서버 알람이 울린다. 그리고 그런 알람이 몇 번 반복되면 팀이 그 알람을 무시하기 시작한다 — 지표 하나가 죽는 것이다.

SQS SendMessageBatch의 SenderFault 불리언이 정확히 이 정보다 — 실패의 책임이 보낸 쪽인지 서비스 쪽인지를 기계가 판단할 수 있게 해 준다. 실물 사례를 하나 들면 "그럴듯한 아이디어"가 "널리 쓰이는 형태"가 된다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

100건이 전부 실패해도 200인가요? 실패율이 높으면 status를 바꾸는 게 낫지 않나요? 함정힌트: 200의 뜻을 정확히 번역하면 답이 나온다. 그리고 "임계값 규칙"이 만드는 부작용을 하나 든다

전 건 실패여도 200 + 전부 FAILED가 일관적이다. 200이 뜻하는 것은 "모든 항목이 성공했다"가 아니라 "이 요청을 우리가 제대로 받아 끝까지 처리했다"이기 때문이다. 100건을 다 검사하고 100건 다 형식 오류라고 판정한 것은 처리가 정상적으로 끝난 것이다.

"실패가 절반을 넘으면 status를 바꾼다" 같은 혼합 규칙은 두 가지를 망가뜨린다.

① 소비자 분기가 두 배가 된다
같은 API가 때로는 200, 때로는 400을 주므로 소비자는 양쪽 경로를 모두 구현해야 한다. 그런데 바디는 어느 쪽이든 똑같다 — 즉 얻는 정보 없이 분기만 늘어난다.
② 임계값 근처에서 동작이 흔들린다
실패 49건이면 200, 51건이면 400. 같은 종류의 요청이 데이터에 따라 다른 처리 경로를 타고, 400이 된 순간 게이트웨이 재시도까지 붙는다(5절의 사슬). 가장 실패가 많은 요청이 가장 위험하게 다뤄지는 셈이다.

"전 건 실패도 200"이 어색하게 느껴진다면 그건 계약이 잘못된 게 아니라 관측이 빠진 것이다 — 아래 모니터링 질문에서 이어진다.

itemId를 서버가 생성해서 응답에 담아 주면 안 되나요? 함정힌트: 매칭은 될지 몰라도 셋 중 하나가 무너진다. "언제 만들어지는가"를 따져 본다

매칭(①)은 절반쯤 되지만 멱등성(③)이 통째로 무너진다. 이유는 키가 만들어지는 시점에 있다.

서버가 만들면

  • 키는 서버가 요청을 받은 뒤에 생긴다.
  • 그러면 응답을 못 받은 클라이언트는 그 키를 모른다.
  • 재전송하면 서버는 또 새 키를 만들고, 이전 처리와 연결할 방법이 없다 → 그대로 중복 처리.
  • 8절 타임라인의 t4(재생)가 성립할 수 없다.

클라이언트가 만들면

  • 키는 요청을 보내기 전에 생긴다.
  • 응답을 못 받아도 클라이언트는 같은 키를 그대로 다시 보낼 수 있다.
  • 서버는 "이 키는 이미 처리했다"고 판정해 저장된 결과를 재생한다.
  • 이것이 06-idempotency-key-design.md의 Idempotency-Key를 클라이언트가 만드는 이유와 정확히 같다.

"매칭만 필요하고 멱등성은 필요 없다"면 서버 생성도 가능하다 — 조회 벌크처럼 부수효과가 없는 경우다. 다만 그때도 응답 배열의 순서가 요청 순서와 다를 수 있다면 서버가 요청 항목의 어떤 값(예: 조회 대상 id)을 결과에 되돌려 담아야 매칭이 성립한다.

계약에 반드시 함께 적을 문장: "같은 항목을 재전송할 때는 같은 itemId를 유지하라." 이 문장이 없으면 소비자가 재전송 때 UUID를 새로 만들어 멱등성이 조용히 무력화된다 — 클라이언트가 키를 만든다는 설계는 클라이언트에게 규율을 요구하는 설계이고, 그 규율은 문서에 적혀야 한다.

항목 실패가 200으로 나가면 5xx 대시보드에 안 잡히는데, 모니터링은 어떻게 하나요? 시니어 변별힌트: 5절에서 "중간 층이 바디를 안 읽는다"고 했다 — 그 성질은 모니터링에도 그대로 적용된다

지적이 정확하다. 200으로 주기로 한 순간 게이트웨이·프록시의 에러율 지표에서 항목 실패가 사라진다. 그 층은 바디를 안 읽기 때문이다 — 그러니 같은 이유로 얻은 이득(재시도 방지)의 대가이고, 애플리케이션 지표로 메워야 한다.

① 항목 실패율
failed / total. 반드시 재시도성(서버 오류)과 비재시도성(입력 오류)을 나눠 집계한다 — 알람은 서버 오류 계열에만 건다(8-1).
② 부분 실패 응답 비율
"200인데 failed > 0"인 응답의 비율. 소비자 눈에 보이는 불완전함에 가장 가까운 숫자다.
③ 배치 크기 분포
요청당 total의 분포. 한도(9절)를 다시 계산할 때 필요한 입력이고, 소비자가 한도에 계속 부딪히는지도 여기서 보인다.

로그·추적도 층을 나눈다. traceId는 요청 하나에 하나이므로 응답 최상위에 두고, 항목별 실패는 그 trace 안에서 itemId + 에러 code로 남긴다. 항목마다 span을 만들면 100건 요청 하나가 span 100개를 만들어 추적 시스템 비용이 튀므로, 실패 항목만 이벤트로 남기거나 샘플링하는 편이 현실적이다.

이 답의 마무리는 13번 문서와 같은 문장이다 — "부분 실패를 200으로 감추는 것이 목적이 아니라, 사용자에게는 안 보이게 하되 운영에게는 보이게 하는 것이 목적"이다. 운영에게도 안 보이면 그건 은폐다.

1,000건 요청에 결과 1,000건을 다 돌려주면 응답이 너무 큽니다. 실패만 주면 안 되나요?힌트: 두 가지를 먼저 물어야 한다 — 성공 항목에 서버가 만든 값이 있는가, 그리고 응답이 큰 진짜 원인이 무엇인가

"성공 항목에 소비자가 받아야 할 값이 있는가"에 따라 갈린다.

성공에 서버 생성 값이 있는 경우 (생성 API)
초대 결과의 userId처럼 소비자가 그 값을 받아야만 다음 일을 할 수 있다면 성공분을 빼면 안 된다. 대신 성공 항목은 {itemId, userId}만 담아 축소하고(상태 문자열·메시지 생략), 실패 항목만 상세를 싣는다.
성공에 돌려줄 값이 없는 경우 (태그 지정·삭제 등)
summary + 실패 목록만 주는 계약도 성립한다. 단 "성공 목록은 생략된다"를 계약에 명시해야 한다 — 안 적으면 소비자는 응답에 없는 itemId를 실패로 오해하거나 반대로 누락으로 의심한다.

그런데 이 질문은 대개 다른 문제의 신호다. 응답이 부담스러울 만큼 크다면 요청 건수 자체가 9절의 검산을 통과하지 못하는 값일 가능성이 높다 — 1,000건이 응답 크기 문제를 일으키기 전에 이미 타임아웃 문제를 일으키고 있다. 한도를 200~400건으로 낮추면 응답 크기 문제도 같이 사라진다.

피해야 할 선택은 "옵션 파라미터로 응답 모드를 고르게 하는 것"이다(?include=failed-only 같은 것). 계약이 두 벌이 되고 테스트도 두 벌이 되는데, 실제로 얻는 것은 수십 KB다.

조회(GET) 벌크는 이 설계가 어떻게 달라지나요?힌트: 부수효과가 없으면 셋 중 하나가 쉬워진다. 대신 쓰기에는 없던 질문이 하나 생긴다

쉬워지는 것 — 멱등성(③). 조회는 부수효과가 없으므로 몇 번을 다시 보내도 안전하다. 8절의 선점·재생 장치가 필요 없고, 클라이언트는 전체 재시도를 마음껏 해도 된다. 그래서 벌크 조회의 부분 실패는 훨씬 가벼운 문제다.

대신 새로 생기는 질문 — "없는 id는 실패인가 결과 없음인가". 100개 id로 조회했는데 3개가 존재하지 않을 때 이걸 항목 실패로 볼지, 정상 결과의 "없음"으로 볼지를 계약이 정해야 한다.

권장 — "없음"은 실패가 아니다
요청한 id 중 존재하지 않는 것은 결과에서 빠지거나 found: false로 표시하고, 응답은 200이다. 벌크 조회에 404를 주는 것은 성립하지 않는다 — 97건은 찾았기 때문이다. 항목 수준의 사실을 요청 수준 status로 표현하려는 순간 5절과 같은 종류의 오류가 된다.
반드시 계약에 적을 것 — 누락 처리
"요청한 개수와 응답 개수가 다를 수 있다"를 안 적으면 소비자는 개수가 같다고 가정한 코드를 짠다(3절의 인덱스 문제가 조회에서 재현된다). 이 항목이 07-chatty-api-call-explosion.md의 벌크 계약 "상·누·길" 중 누락 처리다.

그리고 매칭 키(①)는 조회에서도 그대로 필요하다. 다만 클라이언트가 새 itemId를 만들 필요는 없고 — 조회 대상 id 자체를 결과에 되돌려 담으면 그것이 매칭 키 역할을 한다.

13번의 조합 API 부분 실패와 이 문서의 벌크 부분 실패는 결국 같은 이야기 아닌가요? 시니어 변별힌트: 공통 원리 하나와, 방향이 달라서 생기는 고유 문제 각각을 짚는다

공통 원리는 하나다 — "전송/접수는 성공했고 결과가 부분적으로 다르다"면 상태 코드가 아니라 바디로 표현하고, 중간 층이 바디를 안 읽는다는 사실 위에서 status를 고른다. 그래서 둘 다 200 + 명시적 상태 필드라는 같은 결론에 도달한다.

단, 멱등성 레코드와 실제 처리가 같은 트랜잭션에 있어야 한다 "처리 커밋 → 별도로 키 저장"처럼 나뉘어 있으면 그 사이에 죽었을 때 처리는 됐는데 키가 없는 상태가 되어 재전송이 그대로 중복이 된다. 10절의 항목 하나 = 트랜잭션 하나 구조가 이 문제까지 함께 막아 준다 — 키 선점·실제 처리·결과 저장이 한 알갱이 안에 있기 때문이다.

반대로 원자적 설계였다면 서버가 죽는 순간 전부 롤백되므로 상태는 깨끗하지만, 클라이언트는 여전히 결과를 모른다. 즉 "결과 불명"은 어느 설계를 골라도 남는 문제이고, 그래서 멱등성은 부분 성공 모델의 부속품이 아니라 벌크 API 전반의 필수품이다.

한 줄 요약
벌크 API의 부분 실패 설계는 "원자적이냐 부분 성공이냐"라는 도메인 결정에서 출발한다 — 부분 성공을 택했다면 응답은 200 + 클라이언트가 부여한 식별자로 매칭되는 항목별 결과 배열(표준 에러 code 포함)이 되어야 하고, 200인 이유는 4xx를 주는 순간 바디를 열어보지 않는 HTTP 계층이 전체 실패로 판정해 이미 성공한 97건까지 재시도시키기 때문이며, 대신 파싱 불가·인증 실패·건수 초과 같은 요청 수준 실패는 4xx로 층을 갈라야 한다. 여기에 실패 항목만 안전하게 재시도할 수 있도록 재시도 가능 여부 구분과 itemId 기반 항목별 멱등성(선점 후 처리 + 재생)을 갖추고, 건수 한도는 감이 아니라 "건당 처리 시간 × 한도 ≤ 실질 타임아웃 상한"으로 검산해 정하는 것 — 성공/실패 이분법이 아니라 소비자의 재시도 설계까지 포함한 계약을 만드는 일이다.
