Chatty API 개선
HTTP 왕복은 공짜가 아니다 — N+1은 네트워크에서도 일어난다

면접 질문: "목록 조회 + 상세 N건 조회로 인한 API 호출 폭증(chatty API)을 어떻게 개선하나요?"

핵심 관전 포인트 — 목록 1회 + 상세 N회는 JPA에서 겪는 N+1 문제가 위치만 바꿔 네트워크 계층에서 반복되는 것이다. 결정적 차이는 단가다 — 애플리케이션↔DB 왕복은 1ms 미만이지만 클라이언트↔서버 왕복(RTT)은 모바일에서 수십~수백 ms라, 같은 21번이어도 후자는 화면이 멈추는 시간이 된다. 그리고 RTT는 서버를 좋은 걸로 바꿔도 줄지 않는다(물리적 거리와 홉 수가 정한다) — 그래서 유일한 처방이 왕복 횟수를 줄이는 것이다. 병렬 호출은 왕복 "시간"만 줄일 뿐 요청 "수"는 그대로라, HTTP/1.1의 호스트당 커넥션 6개 제한과 HTTP/2 멀티플렉싱은 이 계산의 상수만 바꾼다 — 서버 처리·직렬화·인증 검사라는 요청당 고정 비용은 여전히 N배이고, 요청이 많을수록 그중 하나가 p99에 걸릴 확률이 커져 tail latency가 화면 완성 시간을 지배한다. 처방은 층위별로 넷이다: ①목록 응답에 화면이 그리는 요약 필드 포함 ②벌크 조회(?ids=1,2,3) ③expand/embed 파라미터 ④BFF 계층. 본질은 "리소스별로 단순한 API"라는 백엔드 편의와 "화면당 한 번의 호출"이라는 클라이언트 효율 사이의 긴장이고, 어느 층에서 조율할지 정하는 게 설계다.
  • 1
    같은 N+1인데 단가가 다릅니다 — JPA에서 겪던 "목록 1 + 항목마다 N"이 위치만 바꿔 네트워크 계층에서 그대로 반복되는 구조입니다. 앱↔DB 왕복은 1ms 미만이라 21번이 21ms로 끝나지만, 모바일↔서버 왕복은 100ms라 같은 21번이 2,100ms가 됩니다 — 구조가 아니라 단가가 100~300배입니다.
  • 2
    RTT는 우리가 못 줄이므로 줄일 수 있는 건 왕복 "횟수"뿐입니다 — RTT는 물리적 거리와 홉 수가 정하므로 서버를 아무리 좋게 해도 그대로입니다. 그래서 병렬화와 HTTP/2는 왕복 시간만 줄이고 서버가 받는 요청 수 21건은 그대로입니다 — 요청당 고정 비용도 21배 그대로고, 21개 중 하나가 p99에 걸릴 확률은 1 − 0.99²¹ ≈ 19%라 다섯 화면에 한 번은 느려집니다.
  • 3
    처방은 층위별로 넷 — "목·벌·펼·비"입니다. 목록 DTO에 화면 요약 필드 포함 → 벌크 조회 → 펼치기(expand) → 비싼 BFF 순으로 아래로 갈수록 강력하지만 비쌉니다. 다만 본질은 기술 선택이 아니라 백엔드 편의와 클라이언트 효율의 긴장이라, "화면당 호출 수 예산(예: 초기 렌더링 3회 이내)"이라는 팀 계약으로 조율합니다.

0. 질문 + 출제 의도

질문: "목록 조회 + 상세 N건 조회로 인한 API 호출 폭증(chatty API)을 어떻게 개선하나요?"

출제 의도: 모바일 환경(높은 왕복 지연)에서 API 호출 수가 곧 체감 속도다. 백엔드 편의(리소스별 단순 API)와 클라이언트 효율의 긴장을 인식하고 조율해본 경험을 본다 — "서버 응답은 50ms인데 왜 화면이 느리냐"는 상황에서 원인을 네트워크 왕복 구조로 진단할 수 있는지가 관전 포인트다.

이 페이지가 겨냥하는 약점 세 가지 ① "호출이 많으면 느리죠"에서 멈추는 것 → 3·4·5절에서 왕복 단가(RTT)라는 단위를 세우고, 21회가 21ms인 경우와 2,100ms인 경우를 같은 산수로 계산해 근거를 만든다.
② "병렬로 쏘면 되지 않나요"라는 오해 → 5절에서 왕복 시간과 요청 수를 분리해, HTTP/1.1 커넥션 6개 제한과 HTTP/2 멀티플렉싱이 상수만 바꾸고 요청 수 21건은 못 바꾼다는 것을 표 한 줄로 보여준다.
③ 처방을 나열만 하고 대가를 못 말하는 것 → 7~11절에서 각 처방이 캐시 효율과 계약 안정성 중 무엇을 지불하는지를 축으로 세운다. 공짜인 칸이 없다는 것이 이 문항의 결론이다.
이 문서의 자리 — 이미 다룬 것과 여기서 파고드는 것 조합 API가 부분 실패했을 때의 응답 계약은 13-aggregation-api-partial-failure-contract.md, 게이트웨이와 BFF의 책임 경계는 14-gateway-vs-service-responsibility-boundary.md, GraphQL·gRPC와의 비교는 11-rest-vs-graphql-vs-grpc.md가 다룬다. 이 페이지는 "왕복 횟수"라는 하나의 축으로 문제를 진단하고 층위별 처방 넷과 각각의 대가를 고르는 데 집중한다.

1. chatty ↔ chunky — 좋고 나쁨이 아니라 스펙트럼의 양 끝

chatty API는 "수다스러운 API"라는 뜻이다. 한 번에 할 말을 다 하지 않고 짧은 말을 여러 번 주고받는 대화처럼, 화면 하나를 그리는 데 서버와 여러 번 왕복하는 호출 구조를 가리킨다. 반대말은 chunky API다. "덩어리진"이라는 뜻으로, 한 번에 큰 응답을 통째로 주고받는 구조다.

먼저 오해를 걷어내야 답이 산다 이 두 단어는 좋고 나쁨의 이름이 아니라 스펙트럼의 양 끝 이름이다. 그래서 이 문서의 결론도 "chunky로 가자"가 아니라 "어느 지점이 이 화면에 맞는가"다. 면접에서 "한 번에 다 주면 되죠"라고 답하면 반대편 비용(12-3절의 god endpoint)을 모르는 사람이 된다.

2. 발생 경로 — 잘 만든 REST API가 chatty를 만든다

chatty는 누가 실수해서 생기는 것이 아니다. 교과서대로 리소스 지향 설계를 하면 자연히 도달하는 상태다. 이 점을 먼저 말하고 시작하면 답변이 "누구 잘못인가"가 아니라 "구조를 어떻게 조율하는가"로 바로 넘어간다.

리소스 중심 정직하게 설계하면 이렇게 된다 — 그리고 각 줄은 전부 옳다
GET /orders            → 주문 id 목록          (백엔드 입장: 깔끔한 단일 책임)
GET /orders/1          → 주문 1 상세
GET /orders/2          → 주문 2 상세
...
GET /users/42          → 주문자 이름 표시용
GET /products/77       → 상품 썸네일 표시용

각 API는 단순하고 재사용 가능하고 캐시하기 좋다 — 리소스별로는 전부 옳은 설계다. 문제는 화면이 리소스 단위가 아니라 조합 단위로 그려진다는 데 있다.

3. N+1의 위치 이동 — 같은 구조, 100배 다른 단가

N+1은 이름 자체가 산수다. 목록을 가져오는 호출 1번, 그리고 목록에 들어 있는 항목 하나하나마다 추가 호출 N번. 합해서 N+1번이다. 항목이 20개면 1 + 20 = 21번이다.

3년차라면 이 구조를 이미 JPA에서 만나봤을 가능성이 높다. 주문 20건을 조회한 뒤 각 주문의 orderItems를 지연 로딩으로 건드리면, 목록 SELECT 1번 + 주문마다 연관 SELECT 20번 = 21번의 쿼리가 나가는 그 문제다.

이 문서에서 가장 먼저 외울 문장

chatty API는 JPA의 N+1이 위치만 바꿔 네트워크 계층에서 그대로 반복되는 것이다

"구조가 비슷하다"가 아니라 "같은 문제"다. 그래서 처방까지 1:1로 대응한다 — fetch join ↔ 목록 DTO 확장, batch size ↔ 벌크 조회. 면접에서 이 대응을 먼저 말하면 이미 아는 것 위에 새 지식을 얹는 답이 되어 설명이 짧아진다.

JPA의 N+1과 HTTP의 chatty는 같은 문제의 두 위치다. 강조된 줄이 이 문항의 핵심.

"N"에 해당하는 것항목마다 연관 SELECT N번GET /orders/{id} N회항목 20개면 양쪽 다 21번

4. RTT — 무엇이고, 왜 우리가 못 줄이는가

앞 표의 "단가"를 이해하려면 단위 하나를 먼저 잡아야 한다.

RTT (round-trip time, 왕복 시간)
내가 보낸 요청이 상대에게 도착하고 그 응답이 나에게 돌아오기까지 걸리는 시간. "왕복"이라는 이름 그대로 편도가 아니라 갔다 오는 한 세트를 센다.
RTT를 정하는 것 — 둘 다 우리 손 밖이다
① 물리적 거리 — 신호는 광케이블 안에서 빛의 속도의 약 3분의 2로 움직인다. ② 중간 장비의 수와 대기 — 라우터·스위치·기지국을 지날 때마다 패킷이 큐에 줄을 선다.

이 문서에 나오는 모든 처방의 공통 원리

RTT는 서버를 좋은 것으로 바꾸거나 코드를 최적화해도 줄어들지 않는다
→ 줄일 수 있는 것은 왕복 시간이 아니라 왕복 횟수뿐이다

비유로 못 박아 두면 면접에서 그대로 쓸 수 있다 — 8차선 도로를 16차선으로 넓혀도 서울에서 부산까지의 거리는 그대로다. 서버 응답이 50ms에서 5ms가 되어도 왕복 100ms는 그대로 남는다. 그래서 "서버를 증설했는데 앱이 여전히 느리다"는 이상한 일이 아니라 당연한 일이다.

RTT 감각 수치. 첫 줄과 셋째 줄의 차이가 곧 "네트워크 N+1을 서버 안의 조합으로 옮기면 왜 이득인가"의 답이다. (08-network-http/01-url-to-page-dns-tcp-tls-http.md 1-2와 같은 기준)
구간대략적인 RTT이 값이 뜻하는 것
같은 데이터센터 내부 (서버 ↔ DB, 서버 ↔ 서버)1ms 미만서버가 대신 왕복해 주면 사실상 공짜 — 모든 처방의 근거
같은 도시/리전 안 (사용자 ↔ 서울 서버, 유선)5~30msPC 웹에서는 chatty가 덜 아프게 느껴지는 이유
국내 모바일 셀룰러망 (위 값 + 기지국 구간)30~100ms이 문항의 기본 전제 — 21회면 2초대
전파가 나쁜 셀 가장자리 · 혼잡 시간대200~300ms같은 코드가 6.3초가 되는 구간 — VOC가 여기서 나온다
국내 사용자 ↔ 미국 서부 서버100~180ms리전 배치가 왕복 단가를 바꾼다
서버가 대신 왕복하는 게 왜 이득인지, 한 문장으로 서버가 대신 20번 왕복해도 그건 1ms짜리 왕복이고, 클라이언트가 20번 왕복하면 그건 100ms짜리 왕복이다. 이 한 문장이 7~10절의 네 처방을 전부 정당화한다. 조합을 없앤 것이 아니라, 조합의 청구서를 100배 싼 통화로 갈아 끼운 것이다.

5. 비용 계산 — 순차와 병렬은 다르고, 프로토콜이 상수를 바꾼다

이제 실제로 계산해 보자. 항목 20개짜리 목록 화면, 목록 1회 + 상세 20회 = 21회 호출이 전제다. 가장 단순한 경우는 클라이언트가 응답을 하나 받고 다음을 부르는 순차 호출이다.

순차 호출: 21회 × RTT

  RTT 100ms → 21 × 100 = 2,100ms  (2.1초)
  RTT 300ms → 21 × 300 = 6,300ms  (6.3초)   ← 화면이 "느리다"의 정체

그런데 실제 클라이언트는 대개 상세 20건을 병렬로 쏜다. 여기서 "그럼 20건이 동시에 나가니 1 RTT로 끝나는 것 아닌가"라고 생각하기 쉬운데, 그렇지 않다. 동시에 몇 개까지 보낼 수 있는지를 프로토콜이 제한하기 때문이다.

HTTP/1.1 — 병렬성을 커넥션 개수로 만든다

  • 한 커넥션에 요청 하나만 흘릴 수 있다. 응답에 "이건 몇 번 요청의 답이다"라는 식별자가 없어서 요청 순서와 응답 순서가 같아야만 짝이 맞기 때문이다.
  • 그래서 브라우저는 같은 호스트에 동시에 여는 커넥션을 보통 6개로 제한한다. 무한정 늘리면 서버 부담이 커지고, 커넥션마다 TCP slow start를 따로 치러 이득이 줄기 때문이다.
  • 결과: 요청 20개가 한 번에 못 나가고 6개씩 묶인 파도(wave)로 나간다. 20 ÷ 6 = 3.33 → 올림해서 4번의 파도.

HTTP/2 — 멀티플렉싱으로 그 제약을 푼다

  • 모든 조각에 길이와 스트림 ID를 붙이는 이진 프레이밍 덕분에 한 커넥션에 여러 요청을 뒤섞어 실어 보낼 수 있다.
  • 멀티플렉싱(multiplexing) = 하나의 물리적 통로에 여러 논리적 통로를 겹쳐 보내는 기법. 그래서 상세 20건이 한 커넥션에서 동시에 나간다.
  • 다만 여기서 바뀌는 것은 왕복 횟수라는 상수뿐이다 — 서버가 받는 요청 수는 그대로다. (프로토콜 상세: 08-network-http/09-http1-http2-http3-hol-blocking.md)
네 가지 경우 비교. 서버 처리 시간을 0으로 두고 왕복만 센 값이고, 커넥션은 이미 맺혀 있다고(keep-alive) 가정한다.

5-1. 표에 안 나오는 비용 — tail latency

병렬 호출에는 표에 안 나오는 비용이 하나 더 있다. 파도 하나는 그 안에서 가장 느린 응답이 돌아와야 끝난다 — 이걸 tail latency(꼬리 지연)라 한다. 응답 시간 분포의 꼬리(느린 쪽 끝)가 전체를 지배한다는 뜻이다.

숫자로 보면 무섭다. 호출 하나가 500ms를 넘길 확률이 1%(즉 p99가 500ms)라고 하자. 호출이 21개면 그중 적어도 하나가 500ms를 넘길 확률은

1 − 0.9921 ≈ 19%   →   서버의 p99는 그대로인데 화면 다섯 번에 한 번은 느려진다

검산: 0.9921 ≈ 0.8097 → 1 − 0.8097 = 0.1903. 호출 수를 줄인다는 것은 이 확률을 줄인다는 뜻이기도 하다 — 호출이 1개면 확률은 그대로 1%로 돌아온다. 병렬화는 이 확률을 전혀 줄이지 않는다. (꼬리 지연의 일반론: 07-traffic-performance/01-throughput-latency-p99.md)

8. 처방 ② 벌크 조회 — "만들었다"가 아니라 "계약을 어떻게 정했나"

목록과 무관하게 "id 여러 개의 상세"가 필요한 경우의 처방이다. 장바구니에 담긴 상품들, 알림 목록에 붙는 발신자 프로필들처럼 클라이언트가 이미 id 집합을 손에 쥐고 있는 상황이다. 이때는 단건 API를 없애지 말고 그 옆에 복수 조회를 추가한다.

Before: 클라이언트가 루프를 돈다
  for id in [1, 2, 3, ..., 20]:
      GET /products/{id}            → 20 왕복 (RTT 100ms면 최소 2초)

After: 벌크 조회 1회
  GET /products?ids=1,2,3,...,20    → 1 왕복 (100ms)

벌크 API 계약의 세 가지 — 상 · 누 · 길

상 — 개수 상한
최대 100개처럼 계약에 명시한다. 상한 없는 벌크는 언젠가 "id 10만 개" 요청이 되어 DB 조회 폭발과 응답 비대를 부른다. 넘으면 400으로 거절하고, 상한값을 문서와 에러 메시지에 함께 적는다.
누 — 누락 계약
일부 id가 존재하지 않을 때 무엇을 돌려줄지 정한다. 있는 것만 조용히인지, found/missing을 나눠 명시인지. 안 정하면 "요청 20개, 응답 18개"에서 어느 2개가 빠졌는지 알아내려고 클라이언트가 또 루프를 돈다.
길 — URL 길이
id가 아주 많으면 URL 길이 한계에 걸린다. 조회여도 POST /products:batchGet처럼 본문에 담는 절충이 실무 관행이다(→ 13절 꼬리질문에서 실제 숫자로 계산).
before 상한도 누락 계약도 없는 벌크 — "만들기만" 한 상태
@GetMapping("/products")
public List<ProductDto> getMany(@RequestParam List<Long> ids) {

            .map(ProductDto::from)              // ③ 없는 id는 조용히 예외 or null → 누락 계약 없음
            .toList();

// 응답이 18건일 때 "어느 2건이 빠졌는지" 알 길이 없어서
// 클라이언트가 결국 다시 루프를 돈다 — chatty를 고치려다 chatty를 다시 만든다.
good 상 · 누 · 길을 모두 계약에 넣은 벌크
static final int MAX_IDS = 100;   // 문서에 적힌 숫자와 동일한 상수 하나를 쓴다

@GetMapping("/products")
public BatchResponse getMany(@RequestParam List<Long> ids) {
    if (ids.size() > MAX_IDS)                                          // ① 상 — 개수 상한
        throw new BadRequestException("ids는 최대 " + MAX_IDS + "개까지 (요청: " + ids.size() + ")");

    List<Product> found = productRepository.findAllByIdIn(ids);       // ② 저장소까지 한 방으로

    Set<Long>  foundIds = found.stream().map(Product::getId).collect(toSet());
    List<Long> missing  = ids.stream().filter(id -> !foundIds.contains(id)).toList();

    return new BatchResponse(found.stream().map(ProductDto::from).toList(), missing); // ③ 누 — 누락 명시
}

// 응답 예: { "found": [ {...}, {...} ], "missing": [ 77, 91 ] }
//   → 클라이언트가 빠진 id를 알아내려고 다시 물어볼 필요가 없다.
// id가 아주 많으면(③ 길) GET 대신 POST /products:batchGet + 본문으로 절충한다.
한 칸 더 — 저장소 계층까지 한 방으로 내려가야 개선이 완성된다 가산점 벌크 API의 서버 구현이 내부에서 단건 조회를 루프로 돌면 네트워크 N+1을 서버 안 N+1로 옮겼을 뿐이다. PostgreSQL이라면 WHERE id IN (...)보다 WHERE id = ANY(?)로 배열 파라미터 하나를 넘기는 형태가 낫다 — id 개수가 달라질 때마다 SQL 문자열이 달라져 실행 계획 캐시가 개수별로 따로 쌓이는 일을 피할 수 있다. MSA라면 내부 서비스 간 호출도 벌크 API로 뚫려 있어야 한다(안 그러면 BFF가 대신 N번 돈다).

9. 처방 ③ expand/embed — 연관 리소스를 옵션으로 실어 주기

expand(또는 embed) 파라미터는 클라이언트가 "이 자원에 딸린 연관 자원까지 같은 응답에 실어 달라"고 요청하는 쿼리 파라미터다. "펼치다(expand)", "끼워 넣다(embed)"라는 이름 그대로, 평소에는 id 참조로만 있던 연관 자원을 요청 시 객체로 펼쳐 준다. Stripe, GitHub 같은 공개 API들이 쓰는 패턴이다.

깊이 1까지만 · 허용 키는 화이트리스트 · expand별 비용을 문서화

여기에 expand 조합별 응답 시간을 별도 메트릭으로 태깅해 두면 "누가 비싼 조합을 쓰는지"를 사후가 아니라 상시로 볼 수 있다.

10. 처방 ④ BFF — 비싼 왕복 하나를 싼 왕복 여럿으로

BFF는 Backend For Frontend, 즉 "특정 프론트엔드 하나를 위한 전용 백엔드"다. 이름이 곧 정의다. 모든 클라이언트가 함께 쓰는 범용 API 위에, 모바일 앱 전용 백엔드 하나, 웹 전용 백엔드 하나를 따로 두는 구조다.

왜 이런 것이 필요한가. 범용 API 하나로 모바일과 웹과 파트너를 전부 만족시키려 하면 모든 화면을 만족시키려다 아무 화면도 만족시키지 못하는 상태에 빠지기 때문이다.

모바일: 데이터가 모자라 여러 번 부른다 (과소 전송)+ 웹: 쓰지도 않는 필드를 잔뜩 받는다 (과다 전송)= 요구는 다른데 계약이 하나뿐인 것이 뿌리

BFF는 여기서 재사용성을 포기하는 대신 왕복을 줄이는 거래를 한다. "화면마다 다른 API"는 REST의 미덕인 재사용성을 정면으로 버리는 선택이지만, 대신 그 화면이 필요한 것을 정확히 한 번에 준다.

BFF의 대가 넷 — 컴 · 엔 · 로 · 소 (반드시 함께 말해야 한다)

컴 — 운영할 컴포넌트가 는다
클라이언트 종류만큼 BFF가 생기므로 배포·모니터링·온콜 대상이 그 수만큼 늘어난다.
엔 — 화면이 늘면 엔드포인트가 는다
BFF는 화면 단위 계약이라 화면 추가가 곧 엔드포인트 추가다. 유지보수 대상이 화면 수에 비례해 자란다.
로 — 도메인 로직이 새어 들어간다
"이 조건이면 할인율을 이렇게"가 하나씩 들어오면 새로운 모놀리스가 된다 — 모든 팀의 변경이 그 한 곳의 배포에 줄을 선다. MSA로 풀었던 문제가 되돌아온다.
소 — 소유권을 정해야 한다
프론트 팀 것인지 백엔드 팀 것인지 합의되지 않으면 화면 요구가 바뀔 때마다 팀 간 협상이 붙는다. 통상은 그 화면을 만드는 클라이언트 팀이 소유하는 편이 낫다.
그래서 팀 규모가 작고 클라이언트가 하나면 처방 ①(목록 DTO 확장)로 충분한 경우가 대부분이다

"로"의 경로와 방어책은 14-gateway-vs-service-responsibility-boundary.md에서 자세히 다룬다. 부분 실패 시 응답 계약은 13-aggregation-api-partial-failure-contract.md.

12. 실무 흐름 — 진단 · 조율 · 역방향 함정

12-1. 진단 — 서버 메트릭에 답이 없다

증상은 보통 이렇게 온다. "앱이 느리다는 VOC가 오는데 서버 APM은 전부 초록색"이다. 6절에서 본 이유 때문이다 — 서버 응답 시간(p99 50ms)만 보면 문제가 없고, 화면 완성 시간은 서버 메트릭에 없다. 그래서 진단은 클라이언트 관점에서 한다.

1
한 화면 진입이 만드는 요청 수를 센다. 앱·브라우저의 네트워크 탭이나 액세스 로그에서 본다. 같은 사용자·짧은 시간 창에 GET /orders/{id}가 연달아 20건 찍히면 chatty의 서명이다.
2
"화면당 요청 수 × RTT"로 체감 시간을 추정한다. 게이트웨이 메트릭이면 충분하다 — 5절의 표가 그 계산식이다. 여기서 "2.1초"라는 숫자가 나오면 그때부터 대화가 달라진다.
3
가능하면 실사용자 측정(RUM)으로 화면 완성 시간을 직접 잰다. 추정이 아니라 실측이 있으면 조율(12-2) 논의가 훨씬 빨리 끝난다 — "느낌"이 "숫자"가 되는 순간이다.

12-2. 조율 — 이 문항의 진짜 주제

chatty API는 백엔드 혼자 만든 문제도, 혼자 고칠 문제도 아니다.

클라이언트 팀: "API가 잘게 쪼개져 있어서"↔ 백엔드 팀: "필요한 조합을 안 알려줘서"→ 양쪽 다 맞는 말이라 기술만으로는 안 끝난다

실무 해법은 화면 설계 단계에서 "이 화면은 API 몇 번으로 그려지는가"를 리뷰 항목으로 두는 것이다. 그리고 화면당 호출 수 예산(예: 초기 렌더링 3회 이내)을 팀 계약으로 합의한다. 2~11절의 기술 선택은 그 계약을 지키는 수단이지, 그 자체가 목표가 아니다.

"호출 수를 줄이자"는 합의는 지켜지지 않지만 "3회 이내"는 리뷰에서 위반이 눈에 보인다
숫자가 없으면 매번 개별 협상이 된다 — 이것이 예산이라는 형태가 중요한 이유다

12-3. 역방향 함정 — chunky로 너무 멀리 가기

chatty를 피하려고 모든 것을 한 응답에 담은 비대한 API(god endpoint, "전지전능 엔드포인트")로 가면 반대편 비용을 낸다.

god endpoint가 부르는 네 가지

  • 응답 크기가 커져 모바일 데이터와 파싱 시간을 낭비한다.
  • 어느 화면도 안 쓰는 필드까지 매번 조회하므로 DB 부하가 늘어난다.
  • 응답 안에 변경 주기가 다른 데이터가 섞여 캐시를 걸 수 없다 — 1초마다 바뀌는 재고와 한 달에 한 번 바뀌는 상품 설명이 한 응답에 있으면 TTL을 짧은 쪽에 맞춰야 한다.
  • 모든 화면이 그 하나의 응답에 결합돼, 한 화면 때문에 바꾼 필드가 전 화면의 회귀 테스트 대상이 된다.

그래서 기준은 가운데다

  • 1절에서 말했듯 chatty ↔ chunky는 스펙트럼이고, 기준은 양 끝이 아니라 "화면이 실제로 그리는 데이터를 한 번에"라는 가운데 지점이다.
  • 판별 질문 하나로 줄이면 — "이 필드를 이 화면이 지금 그리는가?" 아니라면 목록이 아니라 상세로 민다.
  • 반대 방향 판별 질문 — "이걸 빼면 클라이언트가 한 번 더 불러야 하는가?" 그렇다면 넣는다.
  • 두 질문이 동시에 "예"가 되는 필드가 진짜 애매한 필드이고, 그때가 ③ expand나 ④ BFF로 분기할 신호다.

13. 인출 카드 · 꼬리질문 셀프 테스트

13-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

chatty가 뭔지 한 문장?
화면 하나를 그리는 데 서버와 여러 번 왕복하는 구조. 반대말 chunky. 둘은 좋고 나쁨이 아니라 스펙트럼의 양 끝.
JPA N+1과의 관계?
같은 문제의 위치 이동. 앱↔DB(1ms 미만) → 클라↔서버(30~300ms). 21번이 21ms vs 2,100ms — 단가가 100~300배.
RTT를 정하는 것 둘?
물리적 거리(광케이블 안 빛의 2/3 속도) + 홉 수와 큐 대기. 둘 다 우리 손 밖 → 줄일 수 있는 건 왕복 횟수뿐.
병렬/HTTP2로 안 되는 이유?
왕복 시간만 줄고 요청 수 21건은 그대로. 인증·로깅·직렬화 등 요청당 고정 비용이 21배로 남는다.
RTT 100ms일 때 네 숫자?
순차 2,100 / HTTP1.1 병렬 500(1+⌈20÷6⌉=5) / HTTP2 200(1+1) / 구조 변경 100ms.
tail latency 확률 계산?
개별 p99가 500ms면 21개 중 하나가 넘길 확률 1 − 0.99²¹ ≈ 19% → 다섯 화면에 한 번.
처방 네 개 순서?
목 · 벌 · 펼 · 비 — 목록 DTO 확장 → 벌크 → 펼치기(expand) → BFF. 아래로 갈수록 강력하고 비싸다.
벌크 계약 세 가지?
상 · 누 · 길 — 개수 상한(400 거절), 누락 계약(found/missing), URL 길이(POST batchGet).
expand 실무 선?
깊 · 화 · 문 — 깊이 1까지, 허용 키는 화이트리스트, expand별 비용 문서화(+조합별 메트릭 태깅).
BFF의 대가 넷?
컴 · 엔 · 로 · 소 — 컴포넌트 증가, 엔드포인트가 화면 수만큼, 도메인 로직 유입(새 모놀리스), 소유권 합의.
표를 읽는 한 문장?
왕복을 줄이는 값은 캐시 효율과 계약 안정성 중 하나로 지불한다. 공짜인 칸이 없다.
호출 수를 줄였는데도 느리면?
수 · 직 · 크 · 캐 · 프 — 호출 수 → 직렬 의존 → 응답 크기 → 캐싱 → 프로토콜 순.

13-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

벌크 조회에서 id가 수백 개면 GET URL 길이 제한에 걸리지 않나요? 필수힌트: "URL은 2,048자까지"라고 스펙인 양 말하면 오히려 감점이다

먼저 사실관계부터 정확히 짚는 것이 좋다 — HTTP 스펙에는 URL 길이 상한이 없다. 실질적 한계를 정하는 것은 브라우저·서버·프록시의 구현이다.

주체실질 한계초과 시
RFC 7230 권고서버는 최소 8,000 옥텟의 요청 라인을 지원할 것 (하한 권고이지 상한이 아니다)—
Nginxlarge_client_header_buffers 기본값 4 8k → 요청 라인이 8KB를 넘으면 거절414 URI Too Long
TomcatmaxHttpHeaderSize 기본 8,192바이트400 또는 414
통념상 안전선2,000자 안팎 (옛 IE의 2,083자 제약에서 굳어진 관행)—

직접 계산해 보면 감이 잡힌다. 답의 핵심은 "id의 형태에 달렸다"이다.

숫자 id (8자리 + 콤마 = 9바이트)
2,000자 안전선 → 약 220개 / Nginx 기본 8KB → 약 900개. 수백 개여도 대체로 안 걸린다.
UUID (36자 + 콤마 = 37바이트)
2,000자에 겨우 54개 / 8KB에도 221개. 수십 개에서 이미 안전선을 넘는다.

실무 선택지는 둘이다. ① 개수 상한을 안전선 안으로 낮게 잡아 GET을 유지하고, 초과분은 클라이언트가 나눠 부르게 한다. ② POST /products:batchGet처럼 조회 의도를 이름에 드러낸 POST + 본문으로 받는다.

②의 대가는 캐시를 포기하는 것이다. POST 응답은 HTTP 시맨틱상 중간 캐시가 재사용하지 않는다. "REST 순수성 대 실용"의 절충임을 인지하고, 문서에 조회 전용임을 명시하는 것이 포인트다.

expand 파라미터를 계속 허용하다 보면 어떤 문제가 생기나요?힌트: "복잡해진다"가 아니라 "무엇을 예측할 수 없게 되는가"로 답한다

허용 키를 화이트리스트로 묶지 않으면 조합 수가 폭발해 성능을 예측할 수 없는 API가 된다. expand 하나하나가 조인 또는 내부 호출이므로, 클라이언트가 비싼 조합을 마음대로 만들 수 있게 되는 셈이다. 어제까지 잘 돌던 API가, 오늘 어떤 클라이언트가 expand를 세 개 붙인 순간 DB를 눕힐 수 있다.

중첩 expand까지 열면 사실상 쿼리 언어를 재발명하는 셈이다. 그 지경이면 GraphQL 같은 검증된 도구를 검토하는 게 낫다.

실무 선은 셋 — 깊이 1까지만 · 허용 키는 화이트리스트 · expand별 비용을 문서화

여기에 expand 조합별 응답 시간을 별도 메트릭으로 태깅해 두면 "누가 비싼 조합을 쓰는지"를 사후가 아니라 상시로 볼 수 있다.

HTTP/2를 쓰면 멀티플렉싱 덕분에 chatty는 문제가 아니게 되지 않나요? 함정힌트: 5절 표의 마지막 열 하나로 답이 끝난다. 그다음 남는 비용 다섯 개를 센다

절반만 맞다. HTTP/2가 푸는 것은 커넥션 수 제약 하나뿐이다. 5절의 표를 다시 보면 답이 나온다 — HTTP/1.1에서 5 왕복이던 것이 HTTP/2에서 2 왕복이 되지만, 서버가 받는 요청은 세 경우 모두 21건으로 동일하다.

남는 비용은 이렇다.

  • 요청당 고정 비용이 그대로 N배다. 인증 토큰 검증, rate limit 카운팅, 로깅, 트레이싱 컨텍스트 생성, 컨트롤러 진입까지의 필터 체인 — 이 전부를 21번 낸다.
  • 서버 처리와 직렬화가 N배다. 응답 JSON 21개를 만들고 21번 직렬화한다.
  • tail latency는 오히려 더 드러난다. 21건이 동시에 나가면 그중 하나가 p99에 걸릴 확률은 1 − 0.99²¹ ≈ 19%다. 병렬은 이 확률을 줄이지 않는다.
  • 서버에도 동시 스트림 상한이 있다. HTTP/2는 커넥션당 동시 스트림 수를 서버가 정해 알려주며(Nginx 기본값은 128), 상한을 넘는 요청은 대기한다. 무한 병렬이 아니다.
  • 동시 21건이 서버 스레드 풀·커넥션 풀에 한꺼번에 꽂힌다. 사용자 100명이 같은 화면에 들어오면 2,100건이 된다. 왕복이 짧아진 만큼 부하는 더 뾰족해진다.
HTTP/2는 chatty의 지연을 완화하지만 chatty의 비용을 없애지는 않는다

마무리 한 문장 — "프로토콜은 우리가 통제할 수 없는 클라이언트 환경에 달려 있는 반면, 응답 구조는 우리가 정할 수 있습니다. 통제 가능한 쪽부터 고치는 것이 순서입니다."

그냥 GraphQL을 도입하면 해결되는 것 아닌가요?힌트: 먼저 인정하고 시작한다. 그다음 "문제를 없앤 게 아니라 옮긴 것"을 짚는다

GraphQL은 클라이언트가 필요한 필드와 연관을 쿼리로 선언해 한 번에 받는 모델이라, chatty 문제의 정면 해법이 맞다. 인정하고 시작하는 것이 좋다. 하지만 비용이 따라온다.

  • N+1이 서버 내부로 이동한다. 리졸버(필드마다 값을 채우는 함수)가 순진하게 구현되면 필드 하나당 쿼리 하나가 나간다. DataLoader 같은 배칭 계층이 사실상 필수다 — 즉 문제를 없앤 게 아니라 우리 쪽으로 옮긴 것이다. (7절의 "서버 안에서 N+1 재현" 함정과 같은 이야기다.)
  • 비싼 쿼리를 클라이언트가 만들 수 있다. 쿼리 깊이·복잡도 제한이 없으면 한 줄짜리 쿼리가 DB를 눕힌다. (expand의 화이트리스트와 같은 문제가 더 큰 규모로 온다.)
  • HTTP 캐싱과 모니터링 관행이 REST와 다르다. 단일 엔드포인트에 POST로 쿼리를 보내는 형태라 URL 기반 캐시·상태 코드 기반 알람이 그대로 통하지 않는다. 운영 체계를 다시 세워야 한다.
판단 기준은 규모다 — "화면 몇 개가 chatty한 수준"이면 ①~②로 충분하고,
클라이언트 주도 조회 요구가 광범위하고 화면이 계속 늘어나는 조직일 때 도입할 도구다

문제 크기와 도구 크기를 맞추는 판단을 보여 주는 게 핵심이다. (자세한 비교: 11-rest-vs-graphql-vs-grpc.md)

목록 응답에 필드를 계속 추가하다 보면 목록 API가 비대해지는데, 어디까지 허용하나요? 시니어 변별힌트: "한 번의 추가는 싸다"에서 시작해 "누적되면 무엇이 동시에 나빠지는가"로 간다

목록 DTO 확장(처방 ①)의 누적 비용을 아는지 묻는 질문이다. 한 번의 추가는 싸지만, 추가가 쌓이면 세 가지가 동시에 나빠진다.

전송
화면 A를 위해 넣은 필드를 화면 B는 안 쓰는데도 전송 비용은 모두가 낸다.
쿼리
필드 하나하나가 조인이라 목록 쿼리가 점점 무거워진다.
캐시
응답 안의 데이터마다 변경 주기가 달라 TTL을 가장 짧은 것에 맞춰야 한다.

관리 원칙은 셋이다.

1
목록 DTO는 "이 목록을 그리는 대표 화면"의 계약으로 정의하고, 화면별 요구가 갈라지기 시작하면 필드를 더 넣는 대신 expand나 BFF로 분기한다. 갈라지는 시점이 곧 ③·④로 옮겨갈 신호다.
2
무거운 필드(집계값, 대용량 텍스트, 다른 서비스 호출이 필요한 값)는 목록에 넣지 않고 상세로 민다.
3
추가 전에 "누가 쓰는가"를 확인한다. 이유는 비대칭이다 — 필드 추가는 하위 호환 변경이라 자유롭지만, 제거는 파괴적 변경이라 소비자 전수 확인과 마이그레이션 절차가 필요하다.
넣기는 쉽고 빼기는 어려우므로, 판단의 무게는 넣는 쪽에 실려야 한다

화면당 호출 수를 줄였는데도 느리면 다음은 무엇을 보나요? 필수힌트: 병목을 옮겨 가며 잡는 "순서 감각"을 보는 질문이다 — 수·직·크·캐·프

"호출 수 → 직렬성 → 크기 → 캐시 → 프로토콜" 순으로 답한다. 외우는 장치는 수 · 직 · 크 · 캐 · 프.

1
직렬 의존 체인. A의 응답을 받아야 B를 부를 수 있는 구조면 호출 수가 적어도 RTT가 그대로 더해진다 — 호출 3번이라도 순차면 3 RTT다. API 간 의존을 끊어 병렬화하거나, 아예 서버에서 조합해 1회로 만든다.
2
응답 크기. 왕복 횟수를 다 줄였는데도 느리면 이제 전송 시간이 병목이다. 압축(gzip·brotli), 안 쓰는 필드 제거, 이미지 URL의 해상도 분기를 본다.
3
캐싱. 상품 정보처럼 잘 안 변하는 리소스는 ETag·Cache-Control로 조건부 요청을 만들면 왕복은 남아도 본문 전송이 사라진다(304).
4
프로토콜. HTTP/2·HTTP/3 적용 여부, keep-alive와 커넥션 재사용 여부를 본다. 여기는 앞의 셋을 다 하고 나서 볼 곳이지, 먼저 손댈 곳이 아니다.

순서 자체가 답의 핵심이다 — 프로토콜부터 말하면 "가장 통제하기 어렵고 효과가 작은 것부터 손대는 사람"이 된다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

벌크 조회나 조합 API에서 일부만 실패하면 상태 코드를 무엇으로 주나요?힌트: "전체 실패냐 부분 성공이냐"를 계약으로 먼저 정해야 한다

먼저 정해야 할 것은 코드가 아니라 계약이다 — 이 API가 "전부 아니면 전무(all-or-nothing)"인가, "부분 성공을 허용"하는가. 벌크 조회는 대개 후자가 자연스럽다.

부분 성공을 허용한다면, HTTP 상태 코드는 "요청 자체가 처리되었는가"를 나타내는 데 쓰고(200), 어느 항목이 성공·실패했는지는 본문에서 명시한다 — 8절의 found/missing 계약이 그 형태다. 클라이언트가 본문을 안 보고 상태 코드만으로 성공을 판단할 수 없다는 점을 문서에 분명히 적어야 한다.

전부 실패했을 때는 다르게 취급하는 것이 친절하다. 요청한 20건이 하나도 조회되지 않았다면 "빈 배열 + 200"보다 왜 전부 실패했는지(권한·잘못된 id 형식·다운스트림 장애)를 구분해 주는 편이 클라이언트의 재시도 판단에 도움이 된다.

가장 나쁜 것은 계약을 정하지 않는 것이다 — 그러면 클라이언트마다 해석이 갈리고, "요청 20개, 응답 18개"에서 빠진 2개를 알아내려고 결국 루프를 돌게 된다. chatty를 고치려다 chatty를 다시 만드는 셈이다. (상세: 13-aggregation-api-partial-failure-contract.md)

expand와 ?fields= 같은 필드 선택은 같은 건가요?힌트: 하나는 과소 전송을, 하나는 과다 전송을 푼다

방향이 반대인 두 도구다. 헷갈리기 쉬워서 구분해 말하면 점수가 된다.

expand / embed — 더하는 쪽
연관 자원을 응답에 끌어온다. 푸는 문제는 과소 전송(under-fetching) — 데이터가 모자라서 왕복이 더 필요한 상황. 즉 이 문서의 주제인 chatty를 겨냥한다.
field selection — 빼는 쪽
응답에서 안 쓰는 필드를 덜어낸다. 푸는 문제는 과다 전송(over-fetching) — 왕복 수는 그대로이고 응답 크기가 줄 뿐이다. 12-3절의 god endpoint 완화책에 가깝다.

그래서 효과의 성격이 다르다. expand는 왕복 횟수를 줄여 RTT × N을 지우고, fields는 전송 바이트를 줄여 전송 시간을 줄인다. 앞의 것이 대개 훨씬 크다 — 수·직·크·캐·프 순서에서 fields는 "크"에 해당하는 세 번째 카드다.

대가는 공유한다. 둘 다 같은 URL이 파라미터에 따라 다른 모양을 내므로 캐시 키가 조합만큼 분화하고, 문서·타입 정의가 조합마다 갈린다. 그래서 두 파라미터를 동시에 열 때는 조합 폭발을 화이트리스트로 막는 원칙이 똑같이 필요하다.

BFF와 API 게이트웨이는 어떻게 다른가요? 게이트웨이에서 조합하면 안 되나요? 시니어 변별힌트: "누구를 위한 것인가"와 "무엇을 알아도 되는가"로 가른다

가르는 축은 둘이다 — 누구를 위한 컴포넌트인가, 그리고 도메인을 알아도 되는가.

API 게이트웨이
모든 클라이언트가 공통으로 지나는 관문. 인증, 라우팅, rate limit, 로깅처럼 도메인을 몰라도 되는 횡단 관심사를 맡는다. 클라이언트가 늘어도 하나로 유지된다.
BFF
특정 클라이언트 하나를 위한 백엔드. "이 화면이 필요한 조합"을 알아야 하므로 화면 지식을 갖는다. 클라이언트 종류만큼 여러 개가 생긴다.

게이트웨이에서 조합하면 왜 위험한가. 게이트웨이는 모든 트래픽이 지나는 단일 지점이다. 여기에 화면 조합 로직이 들어가기 시작하면 ① 모든 팀의 변경이 그 한 곳의 배포에 줄을 서고, ② 한 화면의 조합 버그가 전 서비스 트래픽에 영향을 주며, ③ 도메인 지식이 스며들어 10절의 "로"(새로운 모놀리스)가 그대로 재현된다.

게이트웨이는 도메인을 모르는 채로 모두를 위해 일하고, BFF는 한 화면을 아는 채로 그 클라이언트만을 위해 일한다

실무에서는 게이트웨이 뒤에 BFF를 두는 배치가 흔하다 — 인증·rate limit은 게이트웨이가 끝내고, BFF는 이미 인증된 요청의 조합에만 집중한다. (책임 경계 상세: 14-gateway-vs-service-responsibility-boundary.md)

목록 DTO 확장은 캐시에 좋고 벌크 조회는 캐시에 나쁘다고 했는데, 왜 그런가요?힌트: 캐시 키가 무엇으로 만들어지는지 떠올린다

HTTP 캐시의 키는 기본적으로 URL이다. 그래서 URL이 안정적으로 반복되는가가 캐시 재사용률을 결정한다.

① 목록 DTO 확장 — 좋음
GET /orders?cursor=X는 같은 사용자가 같은 화면에 들어올 때마다 같은 URL이다. URL 하나 = 캐시 키 하나라서 CDN·브라우저 캐시·ETag 조건부 요청이 전부 정상적으로 작동한다.
② 벌크 조회 — 나쁨
?ids=1,2,3과 ?ids=1,2,4는 완전히 다른 캐시 엔트리다. 장바구니 구성처럼 id 조합이 사용자마다·시점마다 다르면 캐시 적중이 거의 일어나지 않는다.

여기서 한 칸 더 들어가면 좋다 — 벌크의 캐시는 HTTP 계층이 아니라 애플리케이션 계층에서 되찾는다. 서버가 id 단위로 캐시(예: Redis에서 product:77)해 두면, 벌크 요청이 오면 캐시에서 찾은 것은 건너뛰고 없는 id만 DB에서 조회할 수 있다. URL 조합은 매번 달라도 캐시 재사용은 id 단위로 살아난다.

그리고 순서를 정규화하면 조금 더 낫다 — ?ids=3,1,2와 ?ids=1,2,3이 다른 캐시 키가 되지 않도록 서버가 정렬된 형태를 정본으로 계약하거나, 클라이언트에게 정렬해 보내도록 문서에 적는 방법이다. 근본 해결은 아니지만 같은 집합을 다른 순서로 보내 캐시를 낭비하는 일은 막는다.

"화면당 호출 수 3회 이내"라는 예산을 정했는데, 화면이 복잡해서 못 지키면 어떻게 하나요?힌트: 예산의 목적은 금지가 아니라 "위반이 보이게 하는 것"이다

예산의 목적은 호출을 금지하는 게 아니라 위반을 눈에 보이게 만드는 것이라는 데서 출발한다. 못 지키는 화면이 나왔다는 것은 실패가 아니라 신호가 제대로 울린 것이다.

먼저 무엇을 세는지 정의를 분리한다. 예산은 대개 "초기 렌더링에 필요한 호출"에 건다. 스크롤 후 지연 로딩, 사용자 조작 후 호출, 백그라운드 갱신은 같은 바구니에 넣지 않는다 — 안 그러면 예산이 지켜질 수 없는 숫자가 되어 아무도 안 보게 된다.

그다음 초과분을 처방으로 흡수한다. 초기 렌더링이 5회로 나왔다면 "어느 2회를 서버가 대신 왕복할 수 있는가"를 묻는다 — 이 질문의 답이 곧 목 · 벌 · 펼 · 비 중 하나다. 여러 화면에서 같은 초과가 반복되면 그때가 ④ BFF로 넘어갈 신호다(개별 화면의 예외 처리로 계속 때우는 것이 더 비싸지는 지점).

그래도 안 되면 예산을 고친다 — 다만 명시적으로. "이 화면은 예외적으로 5회"라고 기록하고 이유를 남기면 예산은 살아 있다. 위험한 것은 예산을 조용히 무시하는 것이다 — 그러면 다시 "호출 수를 줄이자"는 지켜지지 않는 합의로 돌아간다.

한 줄 요약
chatty API는 JPA에서 익숙한 N+1이 애플리케이션↔DB(1ms)에서 클라이언트↔서버(수십~수백 ms)로 자리를 옮긴 것이라 호출 수가 곧 체감 속도가 되는 문제이고, RTT는 서버 성능으로 줄일 수 없으니 처방은 오직 왕복 횟수를 줄여 서버 안의 싼 조합으로 치환하는 것 — 목록 DTO에 화면 요약 필드 포함, 상한·누락 계약을 갖춘 벌크 조회, 깊이 1로 제한한 expand, 클라이언트가 여럿이면 BFF — 이며, 병렬화나 HTTP/2 멀티플렉싱은 왕복 시간만 줄일 뿐 요청 수(21건)와 tail latency(1 − 0.99²¹ ≈ 19%)는 그대로 남기므로, 본질은 리소스별 단순함(백엔드 편의)과 화면당 한 번(클라이언트 효율)의 긴장을 "화면당 호출 수 예산"이라는 팀 계약으로 조율하는 일이다.
