외부 파트너 API vs 내부 API
신뢰 경계가 바뀌면 설계가 바뀐다 — 공개는 한 방향 문이다

면접 질문: "외부 파트너사에 제공하는 API(콘텐츠 연동)와 내부 API 설계의 차이점은? (인증, rate limit, 문서화, SLA)"

핵심 관전 포인트 — 둘의 차이는 기능이 아니라 신뢰 경계다. 신뢰 경계란 "이 선을 넘어오는 요청은 우리가 통제하지 못하는 쪽에서 온다"고 선언하는 자리이고, 내부 API가 느슨해도 되는 이유는 안전해서가 아니라 호출자를 우리가 고칠 수 있어서다. 파트너는 고칠 수 없으므로 ①인증은 "누구인지"를 넘어 자격증명의 생명주기(발급·무중단 로테이션·HMAC 요청 서명·스코프·즉시 회수)까지, ②rate limit은 파트너별 쿼터와 429 + Retry-After + 남은 한도 헤더라는 응답 계약까지 — 파트너가 자기 소진량을 볼 수 없으면 한도는 보호 장치일 뿐 상품 조건이 되지 못한다 — ③문서는 참고자료가 아니라 파트너가 그것만 보고 구현하는 계약서로, ④약속은 SLI(측정하는 지표) → SLO(내부 목표) → SLA(어기면 환불·크레딧이 따르는 계약)의 3단으로 명문화하되 SLA는 계측 오차를 흡수하고 위반 전에 개입할 시간을 벌기 위해 반드시 SLO보다 느슨하게 잡는다. 그리고 한 번 공개한 필드는 회수에 몇 달이 걸리므로 "최소한으로 공개하고, 외부 전용 계약 층을 내부 API 위에 얹는다"가 원칙이다 — 공개는 한 방향 문이다.
  • 1
    차이의 뿌리는 신뢰 경계 하나입니다 — 내부 API가 느슨해도 되는 건 안전해서가 아니라 호출자를 우리가 고칠 수 있어서입니다. 사내에도 폭주하는 배치는 있지만, 그 팀에 연락해 롤백시킬 수 있죠. 파트너는 코드도 배포 일정도 재시도 로직도 우리가 못 건드립니다 — 사후 개입이 불가능하니 방어를 사전에 시스템으로 심는 것이고, 인증·한도·문서·SLA 네 축은 전부 여기서 따라 나옵니다.
  • 2
    그래서 네 축이 한 단계씩 올라갑니다 — 인증은 식별 → 자격증명 생명주기(파트너별 발급, 겹침 기간을 둔 무중단 로테이션, HMAC 서명, scope, 즉시 회수)로, rate limit은 없음 → 파트너별 쿼터 + 응답 계약으로, 문서는 참고자료 → 유일한 구현 근거로, 약속은 SLO(내부 목표) → SLA(대가가 따르는 계약)로. 신뢰 경계를 넘는 순간 약속의 층위 자체가 한 칸 올라갑니다.
  • 3
    구현은 "내부 API 위에 외부 전용 계약 층을 어댑터로 얹는" 형태입니다 — 내부 모델을 그대로 내보내면 우리에겐 삭제 예정 필드가 파트너에겐 계약된 필드가 되어 리팩터링이 몇 달짜리 폐기 절차에 묶입니다. 전용 DTO·전용 엔드포인트·전용 게이트웨이로 분리하면 내부는 계속 빠르게 바꾸고 외부 계약은 안정적으로 유지할 수 있습니다. 공개는 되돌릴 수 없는 결정이라 느리게 해야 합니다.

0. 질문 + 출제 의도

질문: "외부 파트너사에 제공하는 API(콘텐츠 연동)와 내부 API 설계의 차이점은? (인증, rate limit, 문서화, SLA)"

출제 의도: 신뢰 경계가 바뀌면 설계가 바뀐다(인증 강화, rate limit, 문서가 곧 계약)는 것을 아는지 본다. 콘텐츠 연동 업무의 실제 형태라, 외부와의 기술 계약을 다뤄본 경험을 검증한다.

이 페이지가 겨냥하는 약점 세 가지 ① "외부는 위험하고 내부는 안전하다"로 이해하는 것 → 2절에서 인과를 뒤집어 "고칠 수 있느냐"가 진짜 변수임을 보인다. 이 오해를 하면 사내에서 벌어지는 사고를 설명하지 못한다.
② 네 축을 나열만 하고 이유를 못 대는 것 → 3~8절에서 각 축이 통제 불가라는 전제에서 어떻게 따라 나오는지를 도식과 숫자로 잇는다.
③ rate limit·SLA를 "숫자를 정하는 일"로만 아는 것 → 6절에서 한도는 응답 계약이 없으면 상품이 못 된다는 것을, 8절에서 SLA를 SLO에 붙여 놓으면 계측 오차가 곧 분쟁이 된다는 것을 계산으로 보여준다.

1. 신뢰 경계 — 이 선 너머의 호출자는 우리가 고칠 수 없다

이 문서의 모든 결론이 하나의 개념에서 나오므로, 그 개념부터 정확히 정의하고 시작한다.

신뢰 경계(trust boundary)의 정의

"여기서부터 들어오는 데이터와 요청은 그대로 믿을 수 없다"고 선언하는 선

이름 그대로 신뢰가 끝나는 자리에 긋는 경계다. 보안 설계 용어지만 뜻은 단순하다 — 경계 안쪽은 우리가 만들고 배포하고 고치는 코드가 있는 영역, 바깥쪽은 그렇지 않은 영역이다.

2. 내부 API가 느슨해도 되는 진짜 이유 · 통제 불가의 세 결과

여기가 이 문서 전체의 뼈대다. 내부 API에 인증이 간단하고 rate limit이 없어도 굴러가는 이유는 내부가 안전해서가 아니다. 사내 네트워크에도 버그 있는 코드가 있고, 잘못 배포된 배치가 초당 수천 번을 때릴 수 있다.

이 문서에서 딱 하나만 외운다면

내부 API는 "고칠 수 있어서" 느슨한 것이고, 외부 API는 "고칠 수 없어서" 빡빡한 것이다

내부의 느슨함은 "사후에 고칠 수 있다"는 능력으로 지불되고 있는 비용이다. 방어를 코드에 미리 심는 대신, 문제가 생기면 사람이 개입해 해결하는 쪽을 택한 것뿐이다. 파트너 API에서는 이 지불 수단이 사라지므로 방어를 사전에 시스템으로 심어야 한다.

인과를 뒤집으면 설명이 무너진다 "외부는 위험하고 내부는 안전하다"로 이해하면 사내에서 벌어지는 사고(잘못된 배치, 재시도 폭풍, 실수로 열린 조회 루프)를 설명하지 못한다. 위험도가 아니라 개입 가능성이 진짜 변수다.

2-1. 통제 불가가 낳는 세 가지 결과 — 예 · 악 · 계

예 — 호출 패턴을 예측할 수 없다
파트너가 언제 배포하는지, 새 기능이 트래픽을 몇 배로 늘릴지, 실패 시 몇 번 재시도하는지 우리는 모른다. 지수 백오프 없이 즉시 재시도를 무한 반복하는 클라이언트가 하나만 있어도 서비스가 흔들린다.
악 — 악의를 배제할 수 없다
파트너 회사가 나쁘다는 뜻이 아니라, 자격증명이 유출된 순간 그것을 쥔 쪽이 누구인지 우리는 알 수 없다는 뜻이다. 유출된 키로 들어오는 요청은 파트너의 정상 요청과 구별되지 않는다.
계 — 기술 문제가 곧 계약 문제다
내부 장애는 조직 안의 사고지만, 파트너 API 장애는 파트너사의 매출 손실이자 배상 조항의 발동 조건이다. 대응이 기술에서 끝나지 않고 고지·보상·정산까지 이어진다.
같은 기능을 제공하더라도 이 성격 차이 때문에 설계가 달라진다. 면접에서 값이 나가는 줄은 "잘못 호출할 때"와 "약속의 수준"이다.

장애의 성격우리 조직 내부 사고파트너 매출 손실 = 계약 분쟁기술 → 계약으로 번진다

한 문장 비유 — 구두 약속 vs 도장 찍은 계약서 내부 API는 사무실 안의 구두 회의 약속이고, 외부 파트너 API는 도장을 찍은 계약서다. 회의 약속은 사정이 생기면 슬랙 한 줄로 바꿀 수 있지만, 계약서는 바꾸려면 상대의 동의와 절차와 기간이 필요하다.

3. 축① 인증 — "누구인지"에서 "자격증명의 생명주기"로

내부 — 목적은 식별

  • 게이트웨이·서비스 메시 뒤의 네트워크 신뢰
  • 또는 서비스 간 토큰(mTLS, 내부 발급 JWT)
  • "이 요청이 주문 서비스에서 왔다"만 알면 된다

외부 — 식별만으로는 부족하다

  • 유출 — 새어 나간 키를 어떻게 무력화할 것인가
  • 위조·변조 — 이 본문이 그대로인지 어떻게 아는가
  • 권한 초과 — 계약에 없는 리소스를 어떻게 막는가
  • 회수·교체 — 끊거나 갈아 끼울 때 장애가 안 나는가

3-1. API 키 — 가장 단순하고, 가장 오래 유효한 자격증명

API 키는 서버가 파트너에게 발급한 긴 무작위 문자열로, 요청 헤더에 그대로 실어 보내는 자격증명이다. 구조적으로 비밀번호를 매 요청에 붙이는 것과 같다. 단순해서 파트너가 하루면 붙일 수 있다는 것이 최대 장점이고, 문제도 정확히 여기서 나온다.

API 키의 급소 — 피해 시간이 우리가 정한 값이 아니다

키는 폐기할 때까지 영원히 유효하다 → 유출과 폐기 사이의 시간이 곧 피해 시간

파트너의 로그 파일, 깃 저장소, CI 설정 어딘가에 키가 남아 유출되면 우리가 그 사실을 알아채고 폐기 버튼을 누르기 전까지 공격자는 계속 쓸 수 있다. 그 시간이 며칠일지 몇 달일지 우리는 통제할 수 없다.

3-2. OAuth2 client credentials 그랜트 — 사용자가 없는 서버-대-서버 인증

OAuth2를 처음 접하면 "사용자가 구글 로그인 버튼을 눌러 동의하는 그 화면"이 먼저 떠오른다. client credentials 그랜트는 그 사용자가 없는 경우를 위한 방식이다. 파트너 서버가 우리 API를 호출하는 데는 사람이 개입하지 않으므로 동의 화면도 리다이렉트도 없다. 파트너 시스템이 자기 자신의 자격으로 인증하기 때문에 이름이 "클라이언트(= 애플리케이션) 자격증명"이다.

"유출됐을 때" 행이 이 표의 핵심이고, "즉시 회수" 행이 반대 방향의 대가다. 이 두 줄을 같이 말해야 트레이드오프를 아는 답이 된다.

유출됐을 때우리가 폐기할 때까지 영원히 유효만료 시각(예: 1시간)에 저절로 무효화통제 불가능한 위험 → 우리가 정한 값
권한 범위표준에 없음 — 직접 만들어 붙여야 한다scope가 토큰 안에 담겨 표준으로 전달파트너가 늘 때 관리 방식이 표준화된다

파트너 쪽 구현 부담헤더 하나 추가토큰 발급·캐싱·만료 갱신 로직연동 착수 속도의 차이
우리 쪽 운영 부담키 저장소토큰 발급 서버가 운영 대상으로 추가파트너 수가 적으면 과한 투자일 수 있다
자체 검증(JWT)의 반대 방향 함정 — 여기까지 말해야 깊이가 드러난다 자체 검증 가능한 토큰은 발급된 뒤에는 서버가 조회 없이 서명만 보고 통과시키므로, 반대로 "지금 즉시 이 파트너를 끊어라"가 어렵다. 만료 시간을 짧게(15분~1시간) 잡거나, 폐기 목록을 별도로 조회하는 절충이 필요하다. 이 대가를 알고 만료 시간을 정했는지가 설계의 깊이를 가른다.

3-3. 권한 범위(scope) — 파트너마다 열어 주는 문이 다르다

파트너마다 계약이 다르다. "A사는 콘텐츠 조회만, B사는 등록까지, C사는 정산 데이터까지"처럼 키별로 접근 가능한 리소스를 처음부터 모델링해야 한다.

왜 "나중에 붙이면 된다"가 안 되는가 나중에 붙이려 하면 이미 모든 키가 모든 API를 호출할 수 있는 상태다. 그래서 ① 어느 파트너가 무엇을 쓰고 있는지부터 조사해야 하고 ② 조사 중에 잘못 잠그면 그대로 파트너 장애가 된다. 여기에 보조 수단으로 IP 허용 목록(파트너 서버의 고정 IP만 허용)과 TLS 필수를 겹쳐 어느 한 층이 뚫려도 다른 층이 남게 한다.

3-4. Before / After — 내부 감각으로 만든 외부 API

Before 키 하나로 전부 통과한다 — 파트너를 구분하지도, 한 곳만 끊지도 못한다

4. 키 로테이션 — "교체가 곧 장애"가 되지 않게

로테이션(rotation, 순환 교체)은 자격증명을 주기적으로 새것으로 바꾸는 절차다. 유출을 사후에 알아채기 어려우므로, 알아채지 못한 유출까지 시간이 지나면 무력화되도록 미리 갈아 끼우는 것이다.

문제는 파트너가 언제 새 키를 적용할지 우리가 정할 수 없다는 점이다(1절의 신뢰 경계 그대로다). 옛 키를 폐기하는 순간 새 키로 안 바꾼 파트너는 전부 401을 맞는다. 그래서 둘 다 유효한 겹침 기간(overlap window)을 반드시 둔다.

로테이션 4단계 — 발 · 겹 · 확 · 폐

① 발급
새 키 발급 + 파트너 공지
② 겹침
둘 다 유효 (예: 30일)
③ 확인
옛 키 호출 수 0을 지표로
④ 폐기
이때 비로소 비활성화
자격증명 설계에서 "동시에 유효한 값이 하나뿐"이라는 제약은 편의가 아니라 결함이다

5. HMAC 요청 서명 — 본문이 안 바뀌었고, 비밀키를 아는 쪽이 보냈다

키나 토큰은 "누구인가"만 증명한다. 그런데 그 요청이 중간에서 바뀌지 않았다는 것과 한 번 훔친 요청을 그대로 다시 보낸 것이 아니다는 것은 별개 문제다. 정산 금액이나 콘텐츠 전송 같은 API에서는 이 둘도 증명해야 한다.

HMAC이 한 값으로 증명하는 두 가지

HMAC(Hash-based Message Authentication Code)은 메시지와 비밀키를 함께 넣어 만든 해시값이다.

① 무결성 — 본문이 안 바뀌었다
해시는 입력이 1비트만 달라져도 완전히 다른 값이 나온다 → 본문이 바뀌면 값이 달라진다
② 인증 — 비밀키를 아는 쪽이 만들었다
비밀키를 모르면 그 값을 계산할 수 없다 → 발신자가 비밀키 보유자임이 함께 증명된다

서명 대상 문자열 5요소 — 메 · 경 · 타 · 논 · 본

메서드

재전송 유효 기간을 5분으로 좁힌다

정확히 알아 둘 성질 — HMAC은 제3자에게는 증명하지 못한다 시니어 변별 HMAC은 양쪽이 같은 비밀키를 공유하는 대칭 방식이므로, "파트너가 보냈다"를 우리에게 증명할 뿐 제3자에게 증명하지는 못한다 — 우리도 같은 서명을 만들 수 있기 때문이다. 법적 부인 방지까지 필요하면 파트너의 개인키로 서명하는 비대칭 방식을 써야 한다. 실무에서 HMAC이 표준처럼 쓰이는 이유는 이 정도 보증이면 충분한 경우가 대부분이고 구현·검증 비용이 훨씬 싸기 때문이다.

6. 축② Rate limit — 보호 장치이자 상품 조건

내부 — 없거나 느슨하다

  • 폭주하면 그 팀에 연락하면 된다
  • 그래도 서비스 보호용 전역 한도 하나는 두는 것이 좋다

외부 — 필수이고, 성격이 둘이다

  • 보호 — 파트너 사이의 격벽
  • 상품 조건 — 계약서에 적히는 요금제 항목
  • 이 이중성이 이 절의 핵심이다

6-1. 성격 하나 — 보호: 파트너 사이의 격벽

파트너 한 곳의 버그(재시도 폭풍, 잘못 배포된 배치)가 우리 서비스와 다른 파트너까지 죽이는 것을 막는 격벽이다. 그래서 한도는 반드시 파트너(키)별로 건다.

6-2. 성격 둘 — 상품 조건: 파트너가 소진량을 볼 수 없으면 한도는 상품이 아니다

"분당 몇 회, 일 몇 회"는 기술 파라미터가 아니라 요금제 항목이다. 무료 플랜은 분당 60회, 유료 플랜은 분당 600회처럼 계약서에 적힌다. 그리고 계약이 되려면 초과했을 때 무슨 일이 일어나는지도 계약이어야 한다.

이 절이 진짜로 말하는 것

파트너가 자기 소진량을 볼 수 없으면, 한도는 상품 조건이 될 수 없다

계약서에 "분당 600회"라고 적혀 있어도, 파트너의 클라이언트 코드는 지금 자기가 몇 번째 호출을 하고 있는지 알 방법이 없다. 여러 프로세스가 병렬로 호출하면 더욱 그렇다. 남은 여유를 알 수 없으면 파트너가 할 수 있는 일은 벽에 부딪혀 보는 것뿐이고, 그러면 한도는 "지킬 수 있는 조건"이 아니라 "가끔 얻어맞는 벌칙"이 된다. 그래서 응답 계약이 한도의 절반을 차지한다.

"성공 응답에도 매번"이 붙은 세 줄이 한도를 상품 조건으로 만드는 부분이다. 429가 난 뒤에야 알려 주면 파트너는 벽에 부딪히고 나서야 벽의 위치를 알게 된다.
응답 요소무엇을 알려 주는가언제 내려보내는가표준 지위
429 Too Many Requests"한도를 넘겼다" — 요청 내용이 아니라 타이밍의 문제라서 4xx인데도 재시도 대상이다한도 초과 시RFC 6585 확정
Retry-After: 12"12초 뒤에 다시 오라" — 이 값이 없으면 클라이언트가 할 수 있는 것은 즉시 재시도뿐이고, 거절이 새로운 부하가 된다429와 함께RFC 9110 확정
RateLimit-Limit: 600이 창(window)에 허용된 총 요청 수 = 계약된 한도성공 응답에도 매번IETF 초안
RateLimit-Remaining: 137지금 이 창에 남은 여유 — 파트너가 벽에 닿기 전에 스스로 감속할 수 있게 하는 값성공 응답에도 매번IETF 초안
RateLimit-Reset: 43카운터가 리셋되기까지 남은 시간(초) — "언제 다시 채워지는가"성공 응답에도 매번IETF 초안
헤더 이름의 현황 — 여기서 아는 척하면 감점, 정확히 말하면 가점 시니어 변별 RateLimit-* 계열은 IETF에서 표준화가 진행 중인 초안(draft-ietf-httpapi-ratelimit-headers)이고 아직 RFC로 확정되지 않았다. 초안 자체도 개정을 거치며 세 개의 개별 헤더에서 RateLimit이라는 구조화 필드 하나(+ 정책을 알리는 RateLimit-Policy)로 통합되는 방향으로 바뀌었다. 현장에서 가장 많이 보이는 것은 여전히 GitHub 등이 쓰는 X-RateLimit-Limit / X-RateLimit-Remaining / X-RateLimit-Reset 관행이다.
중요한 것은 이름이 아니라 "한도·잔량·리셋 세 정보를 매 응답에 실어 준다"는 계약이고, 어느 이름을 택하든 문서에 못 박는다
이 문서가 다루는 것과 다루지 않는 것 한도를 구현하는 알고리즘(token bucket, sliding window, 분산 환경의 카운터 원자성)은 07-traffic-performance/08-rate-limiting-algorithms-distributed.md가 다룬다. 여기서 다루는 것은 그 위에 얹히는 계약 면 — 누구 단위로 걸고, 무엇을 응답으로 약속하고, 어떻게 문서에 적을 것인가다.

7. 축③ 문서화 — 참고자료에서 계약서로

내부 — 문서의 오류를 사람이 메운다

  • 코드와 테스트가 문서 역할을 겸한다
  • 애매하면 소비자 팀에 물어보면 된다
  • 문서가 조금 낡아도 슬랙 한 번으로 해결

외부 — 문서가 구현의 유일한 근거다

  • 파트너 개발자는 문서만 보고 구현한다
  • 우리 코드를 볼 수 없고, 물어보려면 이메일과 미팅
  • 문서가 틀리면 연동 자체가 실패하고, 비용은 일정 지연과 반복 미팅으로 돌아온다

외부 문서에 갖춰야 할 것 셋

① 개발자 포털 수준의 레퍼런스
요청·응답 스키마, 에러 코드 표, rate limit 정책(6절의 헤더 계약 포함), 인증 방법, 호출 예제. 목표는 파트너가 "이 필드가 null일 수 있나요?"를 물어보지 않아도 되는 수준.
② 변경 로그 + 버전 정책
파트너는 "언제 무엇이 바뀌는지"를 문서로만 알 수 있다. 변경 로그가 없으면 파트너는 장애가 나고 나서야 변경을 알게 된다.
③ 샌드박스 + 테스트 키 가산점
파트너가 운영 데이터 없이 연동을 검증할 수 있어야 한다. 샌드박스가 없으면 파트너의 첫 통합 테스트가 우리 운영 환경에서 벌어진다.
문서가 계약서라면, 문서와 구현이 어긋나는 것은 계약 위반이다 사람의 성실함에 기대지 말고 체계로 보장해야 한다 — 코드에서 스펙을 뽑을 것인지(springdoc-openapi), 테스트가 통과해야만 문서가 나오게 할 것인지(Spring REST Docs), 스펙을 먼저 쓰고 구현을 검증할 것인지(contract-first)의 선택이 여기서 나온다. 상세는 15-api-docs-implementation-sync.md, 버전 전략은 03-api-versioning-strategies.md, 무엇이 파괴적 변경인지는 08-backward-compatible-api-changes.md가 다룬다.

8. 축④ SLI · SLO · SLA — 세 글자의 차이가 곧 책임의 차이

내부: 장애가 나면 같이 고친다. 공식 계약 없이 운영 목표(SLO) 수준으로 관리한다.  외부: 가용성·성능·지원이 계약 항목이 된다. 그런데 이 영역의 용어 셋이 자주 뒤섞이므로 먼저 구분부터 정확히 한다 — 셋은 같은 것의 다른 이름이 아니라 측정 → 목표 → 약속이라는 다른 층위다.

SLI — 측정→ SLO — 목표→ SLA — 약속(대가 있음) | SLI가 없으면 나머지 둘은 존재할 수 없다

SLOService Level Objective (목표)그 지표가 얼마여야 하는가에 대한 우리 내부의 목표월간 가용률 99.95% 이상내부 경보 — 아직 계약 위반은 아니다
SLAService Level Agreement (합의·계약)파트너와 맺은 약속. 어기면 대가가 따른다월간 가용률 99.9% 미만이면 이용료의 10% 크레딧환불 · 크레딧 · 해지 사유
SLI 정의가 다르면 같은 시스템이 다른 숫자를 낸다 5xx만 실패로 볼 것인가, 타임아웃도 포함할 것인가, 파트너 쪽 네트워크 문제로 도달하지 못한 요청은 어떻게 셀 것인가, 어느 지점(로드밸런서? 애플리케이션?)에서 잴 것인가. 이것을 정하는 것이 SLI다.

8-1. 왜 SLA를 SLO보다 반드시 느슨하게 잡는가 — 숫자로 본다

규칙과 그 두 가지 이유

SLA는 SLO보다 느슨하게 — 그 간격이 계측 오차를 흡수하고 개입할 시간을 만든다
이유 1 — 개입 시간
다운타임이 21.6분을 넘긴 시점에는 아직 계약 위반이 아니다. 우리는 여기서 경보를 받고 배포를 멈추고 원인을 찾을 21.6분을 더 갖는다.
이유 2 — 계측 오차
우리 대시보드 숫자와 파트너 숫자는 반드시 다르다. 측정 지점이 다르고(우리는 LB, 파트너는 자기 앱), 파트너 쪽 네트워크 실패가 우리 지표에 안 잡히고, 집계 창 경계도 어긋난다. 우리 99.92%가 파트너에겐 99.88%일 수 있다.
용어 하나 더 — 에러 예산(error budget) SLO가 허용하는 실패의 총량이다. 99.95%를 목표로 잡았다면 나머지 0.05%, 즉 월 21.6분이 우리가 써도 되는 예산이고, 이것을 다 쓰면 새 기능 배포를 멈추고 안정화에 집중하는 식으로 운영 판단에 쓴다.

8-2. SLA에 함께 들어가는 항목 — 가용률만이 아니다

장애 고지 채널과 시점
파트너가 장애를 우리 상태 페이지에서 아는 것과 자기 CS로 문의가 들어와서 아는 것은 신뢰의 차이가 크다. "탐지 후 30분 내"처럼 시점까지 계약에 적히는 경우가 많다.
점검 사전 고지 · 폐기 통보 기간
파괴적 변경·폐기의 사전 통보 기간(예: 6개월 전)이 들어가는 순간 API 폐기는 기술 결정이 아니라 계약 이행 문제가 된다.
지원 채널과 응답 시간
문의 접수 창구와 1차 응답까지의 시간 약속.
이 모든 것의 전제 — 파트너별 모니터링 가산점 "어느 파트너에게 몇 %의 에러를 줬는지"를 파트너 단위로 나눠 볼 수 없으면, 전체 에러율이 0.05%여도 특정 파트너에게만 3%를 주고 있었을 수 있다.
측정 단위가 계약 단위와 일치하지 않으면 SLA는 약속이 아니라 희망이다

9. 실무 사례 셋 — 격벽 · 로테이션 · 노출

사례 1 — 전역 한도만 있던 날: 파트너 A의 배치가 파트너 B를 죽였다

콘텐츠 연동 API에 전역 한도(전체 분당 5,000회)만 걸려 있었다. 어느 날 새벽, 파트너 A가 신간 30,000건을 동기화하는 배치를 돌렸다. 건당 1회 호출을 3분 안에 몰아 보내는 구현이었다. 파트너 A의 계약 한도는 분당 600회였다.

// 숫자를 계산해 보면 무슨 일이 벌어졌는지 바로 보인다
파트너 A의 실제 호출 속도 = 30,000건 ÷ 3분 = 10,000회/분
계약 한도                 = 600회/분
                            ─────────────────────
                            한도의 약 16.7배 (10,000 ÷ 600 = 16.67)

3분 동안 통과했어야 할 요청 = 600 × 3 = 1,800건
3분 동안 거절됐어야 할 요청 = 30,000 − 1,800 = 28,200건   ← 파트너별 한도가 있었다면
실제로는: A의 10,000회/분이 전역 한도 5,000회/분을 통째로 먹었다
          → 자기 한도의 1/10도 안 쓰던 파트너 B·C가 429를 맞았다

대응 — 기술 쪽

  • 한도를 파트너 키 단위로 재설계했다 (6-1의 격벽)
  • 성공 응답에도 RateLimit-Remaining을 싣기 시작했다 — 파트너 A의 배치가 남은 여유를 보고 스스로 감속할 수 있게 하려고
  • 이것이 없으면 파트너는 벽에 부딪히는 것 말고는 감속할 근거가 없다

대응 — 계약 쪽

  • 배치를 분산하도록 가이드: 30,000 ÷ 600 = 50분 — 최소 50분에 걸쳐 나눠 보내야 한다
  • "매시 정각에 시작"을 금지하고 시작 시각에 지터(무작위 지연)를 넣도록 요청 — 여러 파트너의 배치가 전부 정각에 시작하면 정각마다 트래픽 절벽이 생긴다
  • 백오프와 지터의 원리: 07-traffic-performance/11-retry-storm-backoff-jitter.md
교훈 — 한도의 단위는 곧 격리의 단위다. 전역 한도는 우리 서비스를 지키지만 파트너를 서로에게서 지키지 못한다

사례 2 — 키를 교체하려 했더니, 교체 자체가 장애였다

파트너 한 곳의 API 키가 공개 저장소의 설정 파일에 올라간 것이 발견됐다. 즉시 폐기해야 하는 상황인데, 여기서 초기 설계의 결함이 드러났다 — 파트너 테이블에 api_key 컬럼이 하나뿐이었다.

컬럼이 하나라는 것은 한 파트너에게 유효한 키가 언제나 정확히 하나라는 뜻이다. 새 키를 넣으려면 옛 키를 덮어써야 하고, 덮어쓰는 순간 파트너의 운영 시스템이 즉시 401을 맞는다. 파트너의 배포 주기가 주 1회였으므로 그동안 연동이 통째로 끊긴다. 유출 대응이 계획된 장애가 되는 상황이었고, 그래서 실제로는 "당장 폐기"를 못 하고 파트너 배포 일정에 맞추느라 며칠을 더 유출 상태로 두게 됐다.

Before 컬럼 하나 — 겹침이 구조적으로 불가능
CREATE TABLE partner (
    partner_id  bigint      PRIMARY KEY,
    name        varchar(100) NOT NULL,
    api_key     varchar(80)  NOT NULL   -- 하나뿐
);

-- 유효한 키가 언제나 정확히 하나 = 새 키를 넣으려면
-- 옛 키를 덮어써야 한다 = 그 순간 파트너는 401.
-- 로테이션이 곧 장애가 되는 구조다.
After 별도 행 — 한 파트너가 활성 자격증명을 둘 이상
CREATE TABLE partner_credential (
    key_id      varchar(40)  PRIMARY KEY,   -- 헤더로 오는 식별자
    partner_id  bigint       NOT NULL,
    secret_hash text         NOT NULL,      -- 원본 아닌 해시
    scopes      text[]       NOT NULL,
    status      varchar(10)  NOT NULL,      -- ACTIVE | DEPRECATED | REVOKED
    expires_at  timestamptz,                -- 겹침 기간의 종료 시각
    created_at  timestamptz  NOT NULL DEFAULT now()
);

-- 활성 자격증명만 빠르게 찾기 위한 부분 인덱스.
-- 폐기된 행이 쌓여도 인덱스 크기가 커지지 않는다.
CREATE INDEX idx_cred_active ON partner_credential (partner_id)
    WHERE status = 'ACTIVE';

status가 세 값인 이유 — DEPRECATED가 로테이션 절차를 성립시킨다

ACTIVE — 정상→ DEPRECATED — 아직 통과시키지만 곧 죽을 키 (호출 수를 센다)→ REVOKED — 차단

이 상태의 키로 들어오는 호출은 정상 처리하되 별도 지표로 카운트한다. 4절 로테이션 절차의 ③단계 — "옛 키 호출 수가 0인지 확인" — 이 이 지표로 이뤄진다. DEPRECATED 없이 ACTIVE/REVOKED 둘만 있으면, 폐기 버튼을 누르기 전에 안전한지 확인할 방법이 없다.

교체 가능성은 나중에 붙이는 기능이 아니라 처음의 데이터 모델에서 결정된다

사례 3 — 내부 모델을 그대로 내보낸 대가

연동을 빨리 열어야 해서 내부 콘텐츠 조회 API의 응답을 그대로 파트너에게 내줬다. 응답 객체는 내부 엔티티를 그대로 직렬화한 것이었고, 거기에는 내부 관리용 필드가 여럿 섞여 있었다 — 내부 등급 코드, 담당 MD의 사번, 다음 개편에서 없어질 예정이던 레거시 카테고리 ID.

여섯 달 뒤 카테고리 체계를 개편하려는데, 파트너 세 곳이 그 레거시 카테고리 ID로 자기 쪽 매핑 테이블을 만들어 놓은 상태였다. 그 필드는 우리에게는 삭제 예정 필드였지만, 파트너에게는 계약된 필드였다.

10. 공개는 한 방향 문 — 외부 계약 층을 어댑터로 얹는다

외부 공개 전에 반드시 하는 검토 셋 — 최소 · 멱등 · 분리

① 최소 공개 원칙
내부 모델을 그대로 노출하지 말고 외부 전용 응답 모델(DTO)을 별도로 두고 필요한 필드만 내보낸다. 판단 근거는 비대칭이다 — 필드 하나를 더 내보내는 비용은 지금 0이지만, 회수하는 비용은 몇 달이다.
② 쓰기 API엔 멱등성 키
파트너 클라이언트가 타임아웃 후 재시도하는지, 몇 번 하는지 우리는 모른다. "통제할 수 없는 재시도"라는 전제가 멱등성을 선택이 아니라 필수로 만든다. 설계는 06-idempotency-key-design.md.
③ 내부와 경로 분리
전용 엔드포인트나 전용 게이트웨이를 두면 인증·한도·감사 정책을 내부와 독립적으로 걸 수 있고, 파트너 트래픽만 따로 계측할 수 있다(8절 SLA 계측이 여기에 기댄다). 경계는 14-gateway-vs-service-responsibility-boundary.md.
셋을 한 문장으로 — 외부 계약 층을 내부 API 위에 어댑터로 얹어라

마무리 원칙 — 되돌릴 수 없는 결정은 느리게 한다

공개는 한 방향 문이다

되돌릴 수 있는 결정은 빠르게, 되돌릴 수 없는 결정은 느리게 — 외부 API 공개는 명백히 후자다. "일단 열고 나중에 정리하죠"가 통하지 않는 유일한 종류의 결정이라는 감각이 시니어의 답을 가른다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 인출 카드 — 답을 가리고 먼저 떠올려 본다

내부 API가 느슨해도 되는 진짜 이유?
안전해서가 아니라 호출자를 우리가 고칠 수 있어서. 느슨함은 "사후 개입"이라는 비용으로 지불되고 있다.
통제 불가가 낳는 세 결과?
예·악·계 — ①호출 패턴 예측 불가 ②악의 배제 불가(유출된 키 = 정상 요청과 구별 불가) ③기술 문제가 곧 계약 문제.
API 키 vs OAuth2 — 표에서 결정적인 두 줄?
유출됐을 때: "우리가 알아챌 때까지" vs "만료까지" — 통제 불가능한 값 → 우리가 정한 값. 반대로 즉시 회수: 키는 즉시, 자체 검증 토큰은 만료까지 못 끊는다.
로테이션 4단계?
발·겹·확·폐 — 발급 → 겹침 기간 → 옛 키 호출 수 0 확인 → 폐기. ③이 없으면 폐기가 도박이다.
HMAC 서명 대상 5요소?
메·경·타·논·본 — 메서드 · 경로 · 타임스탬프 · nonce · 본문 해시. 타임스탬프는 nonce 저장소를 5분치로 한정하고, nonce는 그 5분 안의 재전송을 막는다.
HMAC이 증명하지 못하는 것?
대칭 키라 제3자에게는 증명 못 한다 — 우리도 같은 서명을 만들 수 있으므로. 법적 부인 방지엔 비대칭 서명.
rate limit 응답 계약 5요소?
429 + Retry-After(확정 표준) + Limit·Remaining·Reset(초안). 뒤 셋은 성공 응답에도 매번 — 이게 한도를 상품 조건으로 만든다.
전역 한도만 두면?
noisy neighbor — 잘못한 쪽이 아니라 나중에 도착한 쪽이 429를 맞는다. 한도의 단위 = 격리의 단위.
SLI · SLO · SLA 한 줄씩?
측정 → 목표 → 약속(대가 있음). SLI가 없으면 나머지 둘은 존재할 수 없다.
SLA > SLO 완충의 숫자?
30일 = 43,200분. SLA 99.9% = 43.2분, SLO 99.95% = 21.6분(에러 예산) → 완충 21.6분. 이유 둘: 개입 시간 + 계측 오차 흡수.
외부 공개 전 검토 셋?
최소·멱등·분리 — 최소 공개(전용 DTO) · 쓰기엔 멱등성 키 · 내부와 경로 분리.
필드 공개의 비대칭?
더 내보내는 비용은 지금 0, 회수하는 비용은 몇 달. 공개는 한 방향 문이다.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

API 키와 OAuth2 client credentials 중 뭘 쓰나요? 필수힌트: 장단점 나열로 끝내지 말고 "판단 기준"과 "양쪽의 반대 방향 약점"까지 가야 완성된다

API 키는 발급받은 문자열을 매 요청 헤더에 그대로 싣는 방식이다. 연동이 단순해 파트너가 하루면 붙일 수 있다. 대신 장기 유효 자격증명이라 유출 시 피해 시간이 "우리가 알아채고 폐기할 때까지"로 무한정 열려 있고, 권한 범위와 만료 개념이 표준에 없어 전부 직접 만들어야 한다.

OAuth2 client credentials는 client id/secret으로 수명 짧은 액세스 토큰을 받아 그 토큰으로 호출하는 방식이다. 매 요청에 오가는 것이 한 시간 뒤 저절로 죽는 토큰이므로 유출 피해가 만료 시간으로 상한이 잡히고, scope와 만료가 표준에 내장돼 있어 파트너가 늘어날 때 관리 방식이 표준화된다. 대신 토큰 발급 서버가 운영 대상으로 늘어나고, 파트너 쪽에도 토큰 캐싱·갱신 구현이 필요하다.

판단 기준은 "파트너 수와 데이터 민감도"다

소수 파트너의 단순 조회 연동이면 서명(HMAC)을 동반한 API 키로 충분하고, 파트너가 늘고 쓰기 API나 민감 데이터가 걸리면 OAuth2로 표준화하는 쪽이 관리 비용이 낮다.

한 단계 더 나가려면 양쪽의 반대 방향 약점을 짚는다. API 키는 폐기가 즉시 반영되지만(다음 요청부터 차단) 유출 피해 시간이 길고, 자체 검증형 토큰은 유출 피해 시간이 짧지만 이미 발급된 토큰을 즉시 끊기는 어렵다. 그래서 OAuth2를 쓰더라도 "즉시 차단"이 필요한 도메인이면 만료를 짧게 잡거나 폐기 목록 조회를 얹는 절충이 따라온다.

rate limit에 걸린 파트너가 "우리는 정상 트래픽"이라고 항의하면? 필수힌트: 기술 답과 계약 답을 둘 다 내고, 마지막에 "우리 잘못일 가능성"까지 열어 둔다

측정 데이터로 대화한다. 파트너별 호출량·429 비율·시각별 분포 대시보드가 있어야 "새벽 3시에 3분간 10,000회/분을 보냈고 계약 한도는 600회/분"처럼 구체적으로 보여줄 수 있다. 이 대시보드가 없으면 대화가 "우리는 정상이다" 대 "아니다"의 말싸움이 된다.

원인 규명 다음의 해법은 기술과 계약 양면이다. 배치 폭주라면 배치를 분산하고 시작 시각에 지터를 넣도록 가이드하고(사례 1), 실제 트래픽 성장이라면 상위 쿼터로 계약을 조정한다.

여기에 두 가지를 덧붙이면 시야가 넓어 보인다.

하나 — 한도 상향은 용량 계획과 연동된 결정
파트너 한 곳의 한도를 올리려면 그만큼의 여유가 실제로 있어야 하므로 계약과 인프라가 함께 움직인다.
둘 — 우리 쪽 잘못일 가능성부터 본다
성공 응답에 잔량 헤더를 안 내려보내고 있었다면, 파트너가 감속할 수단을 우리가 안 준 것이다. 이 경우 항의의 절반은 정당하다.

문서에 한도와 헤더 계약이 명시돼 있었는지도 함께 확인한다 — 문서에 없던 한도로 차단했다면 그건 기술 문제가 아니라 계약 문제다.

내부 API를 그대로 파트너에게 열어주면 안 되나요? 시니어 변별힌트: "안 됩니다"가 아니라 "가장 빠르지만 가장 비싼 선택"으로 시작하고, 비용을 셋으로 쪼갠다

가장 빠르지만 가장 비싼 선택이라는 것부터 말한다. 이유를 셋으로 나눈다.

1
내부 모델과 내부 식별자가 노출된다. 정보 노출 자체도 문제지만 더 큰 것은 리팩터링의 족쇄다 — 사례 3에서 본 그대로, 우리에게는 삭제 예정 필드가 파트너에게는 계약된 필드가 된다.
2
변경 속도를 잃는다. 내부 API는 소비자와 합의만 하면 오늘 바꿀 수 있는 계약인데, 외부가 붙는 순간 같은 API가 몇 달짜리 폐기 절차의 대상이 된다. 특히 아픈 부분은 그 API를 쓰는 내부 서비스들의 변경 속도까지 함께 묶인다는 것이다.
3
인증·한도·감사가 내부 전제로 설계돼 있다. 파트너별 격리도, 서명 검증도, 파트너 단위 감사 로그도 없다. 이것들을 나중에 얹으려면 이미 붙어 있는 파트너를 깨지 않으면서 붙여야 한다.

올바른 형태는 외부 전용 계약 층(전용 DTO·전용 엔드포인트·전용 게이트웨이)을 내부 API 위에 어댑터로 얹는 것이다 — 내부는 계속 빠르게 바꾸고, 외부 계약은 안정적으로 유지하는 구조다(10절 도식).

마무리로 비가역성을 짚으면 시니어 관점이 드러난다 — 공개는 한 방향 문이다
파트너에게 데이터를 밀어줘야 하는 경우(웹훅)는 뭐가 달라지나요?힌트: 방향이 뒤집히면 역할도 뒤집힌다 — 이 대칭 한 줄이 이 질문의 정답이다

방향이 뒤집히면 역할도 뒤집힌다 — 이번엔 우리가 클라이언트이고 파트너가 서버다. 그래서 이 문서에서 파트너에게 요구했던 것들을 이번엔 우리가 지켜야 한다.

파트너 → 우리 (본문 1~10절)

  • 파트너가 서명을 만들고 우리가 검증한다
  • 파트너의 재시도가 통제 불가 → 우리가 멱등성 키를 요구
  • 우리가 한도를 걸고 잔량을 알려 준다

우리 → 파트너 (웹훅)

  • 우리가 서명을 만들어 실어 준다 — 파트너가 "이 요청이 진짜 우리한테서 왔는지" 검증할 수 있도록
  • 상대 서버가 다운돼 있을 수 있어 재시도가 전제, 재시도하면 중복 도착이 전제 → 파트너가 멱등하게 처리할 수 있도록 우리가 이벤트 ID를 실어 준다
  • 수신 실패분을 파트너가 스스로 복구할 재조회(pull) API를 함께 제공하면 운영 문의가 크게 준다 가산점

콜백의 재시도·중복·서명·유실 복구 설계 전체는 10-long-running-operations-202-polling-callback.md 3절이 다룬다. 이 질문이 나오면 그 문서 내용으로 답하되, "신뢰 경계를 우리가 넘어가는 쪽이 되면, 파트너에게 요구했던 방어를 우리가 제공하는 입장이 된다"는 대칭을 짚는 것이 이 문서의 몫이다.

SLA와 SLO는 뭐가 다른가요? 필수힌트: 두 개가 아니라 세 개(SLI 포함)로 답하고, "SLA를 느슨하게"의 이유 두 가지로 닫는다

SLI → SLO → SLA의 3단으로 답한다.

SLI
실제로 측정하는 지표. 성공 응답 수 ÷ 전체 요청 수 같은 계산식이고, 어디서 어떻게 재는지가 정의에 포함된다.
SLO
그 지표가 얼마여야 하는지에 대한 내부 목표. 어겨도 계약 위반은 아니고 내부 경보가 울린다.
SLA
파트너와 맺은 계약. 어기면 크레딧·환불 같은 대가가 따른다.

그리고 SLA를 SLO보다 느슨하게 잡는다는 실무 규칙과 그 두 가지 이유를 붙이면 정리가 완성된다. 첫째, 그 간격이 위반 전에 개입할 시간을 만든다 — SLA 99.9%는 월 43.2분까지 허용, SLO 99.95%는 월 21.6분에서 경보, 그 사이 21.6분이 완충 구간이다. 둘째, 우리 지표와 파트너 지표는 측정 지점과 집계 창이 달라 반드시 어긋나므로 그 오차를 흡수할 폭이 필요하다.

"내부 API는 SLO까지, 외부 API는 SLA까지 올라간다" — 신뢰 경계를 넘는 순간 약속의 층위 자체가 한 칸 올라간다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

파트너 자격증명이 유출된 것을 알았습니다. 순서대로 무엇을 하나요? 함정힌트: "즉시 폐기"라고 답하면 사례 2를 그대로 반복하게 된다

"즉시 폐기"는 반쪽 답이다. 폐기하는 순간 파트너 운영이 멈춘다면, 그 결정은 기술이 아니라 사업 판단이 된다. 순서를 이렇게 잡는다.

1
피해 범위부터 센다. 그 key_id로 들어온 호출을 감사 로그에서 뽑아 평소와 다른 IP·시간대·엔드포인트·볼륨이 있었는지 본다. 파트너별·키별 계측이 없으면 이 단계에서 이미 막힌다.
2
즉시 좁힐 수 있는 것부터 좁힌다. 전면 차단이 어렵다면 IP 허용 목록을 파트너의 실제 서버로 축소하거나, 그 키의 scope를 조회 전용으로 낮추거나, 한도를 평상시 수준으로 조여 대량 유출 시도를 막는다 — "끊거나 두거나" 사이에 중간 수단을 만들어 두는 것이 설계의 몫이다.
3
새 자격증명을 발급하고 겹침 기간을 시작한다. 이때 겹침 기간은 평시(30일)가 아니라 파트너가 긴급 배포로 감당할 수 있는 최소로 협의한다.
4
옛 키 호출 수 0을 지표로 확인한 뒤 REVOKED로 넘긴다(4절). 확인 없이 누르면 유출 대응이 파트너 장애로 바뀐다.

사후에 반드시 하는 것 하나 — 이번에 왜 즉시 끊지 못했는지를 데이터 모델과 정책의 문제로 기록한다. 사례 2에서 진짜 원인은 유출이 아니라 "컬럼이 하나였다"였다.

어차피 HTTPS(TLS)를 쓰는데 왜 HMAC 서명까지 필요한가요? 시니어 변별힌트: TLS가 보호하는 것은 "전송 구간"이고 서명이 보호하는 것은 "메시지"다 — 경계가 어디서 끝나는지를 말한다

보호하는 대상이 다르다. TLS는 전송 구간을 보호하고(도청·중간 변조 방지, 서버 신원 확인), HMAC 서명은 메시지 자체를 보호한다. 그래서 TLS가 끝나는 지점부터는 TLS가 아무것도 해 주지 않는다.

TLS 종료 이후의 구간
실무의 요청은 로드밸런서·WAF·게이트웨이에서 TLS가 한 번 풀린 뒤 내부를 지난다. 그 뒤 구간에서의 변조·오처리는 TLS의 관심사가 아니다.
"누가 만들었는가"가 앱에 안 남는다
서버 TLS만으로는 클라이언트 신원이 애플리케이션 층에 증명되지 않는다(mTLS를 쓰면 커넥션 단위로는 가능하지만, 요청 본문 단위의 무결성 증거는 여전히 남지 않는다).
재전송
TLS 세션 안에서의 재전송은 막히지만, 요청 내용이 어딘가(로그·프록시·파트너 내부 큐)에 남아 다시 보내지는 경우는 별개다. 이걸 막는 것이 타임스탬프 + nonce다.
사후 증거
서명은 요청과 함께 저장할 수 있는 증거다. 정산 분쟁에서 "이 본문 그대로 왔다"를 나중에 다시 검증할 수 있다 — TLS는 끝나면 아무것도 남기지 않는다.
TLS는 파이프를 지키고, 서명은 내용물을 지킨다 — 둘은 대체재가 아니라 층이 다른 방어다
파트너별 rate limit은 게이트웨이와 각 서비스 중 어디에 두나요?힌트: "게이트웨이요"로 끝내지 말고, 게이트웨이가 감당하지 못하는 종류의 한도를 하나 대라

기본은 게이트웨이(외부 전용 진입점)다. 이유는 셋이다 — ① 모든 엔드포인트에 일괄 적용되므로 새 API가 추가돼도 한도가 자동으로 따라붙고, ② 서비스에 도달하기 전에 차단하므로 폭주 시 뒷단 자원을 아끼고, ③ 인증·감사와 같은 자리에 있어 "누구인지" 판정 결과를 그대로 한도 키로 쓸 수 있다.

그런데 게이트웨이가 감당하지 못하는 한도가 있다. 요청 비용이 균일하지 않을 때다 — 목록 조회 1회와 대량 리포트 생성 1회를 같은 "1회"로 세면, 파트너는 한도 안에서도 우리 시스템을 무너뜨릴 수 있다. 이런 가중치 기반 한도(비싼 API는 여러 개 소모)나 동시 실행 수 제한은 비용을 아는 서비스 쪽이 판단해야 한다.

공통·거친 한도는 게이트웨이, 리소스 비용을 아는 세밀한 한도는 서비스 — 둘은 겹쳐 쓴다

어디에 두든 인스턴스가 여러 대면 카운터가 공유돼야 한다는 문제는 그대로 남는다(분산 카운터의 원자성: 07-traffic-performance/08-rate-limiting-algorithms-distributed.md). 책임 경계 일반론은 14-gateway-vs-service-responsibility-boundary.md.

파트너 API에서 401 · 403 · 429는 어떻게 구분해 내려주나요?힌트: "누군지 모른다 / 누군지는 알지만 안 된다 / 지금은 안 된다"의 세 문장
401 Unauthorized
누군지 모른다 — 키·토큰이 없거나, 만료됐거나, 서명이 안 맞는다. 파트너가 할 일: 자격증명을 고친다.
403 Forbidden
누군지는 알지만 권한이 없다 — 계약된 scope 밖, IP 허용 목록 밖. 파트너가 할 일: 계약을 확인한다. 재시도해도 소용없다.
429 Too Many Requests
지금은 안 된다 — 자격도 권한도 정상인데 타이밍의 문제다. 그래서 4xx인데도 재시도 대상이고, Retry-After로 언제를 알려 줘야 한다.

구분이 흐려지면 파트너의 대응이 틀어진다. scope 부족을 401로 내리면 파트너는 있지도 않은 자격증명 문제를 몇 시간 뒤진다. 반대로 만료된 토큰을 403으로 내리면 토큰 갱신 로직이 돌지 않는다.

다만 정보 노출과의 균형은 필요하다 — 존재하지 않는 리소스에 대해 403을 주면 "그 리소스가 존재한다"는 사실 자체가 새어 나가므로, 민감 리소스는 404로 감추는 선택도 있다. 어느 쪽을 택하든 에러 코드 표에 못 박아 문서화한다(05-error-response-body-standardization.md).

SLA에 "월간 가용률 99.9%"만 적으면 충분한가요?힌트: 가용률 100%인데도 파트너가 못 쓰는 상태를 하나 상상해 본다

부족하다. 가용률만 적힌 SLA는 "응답은 갔다"만 보장한다. 응답이 30초씩 걸려도 5xx가 아니면 가용률은 100%이고, 파트너 화면은 이미 멈춰 있다.

그래서 함께 적는 항목이 넷이다.

① 지연시간 SLO/SLA
예: p99 < 500ms. 백분위·측정 창·측정 지점까지 정의해야 의미가 생긴다(07-traffic-performance/01-throughput-latency-p99.md).
② 장애 고지 채널과 시점
상태 페이지 + "탐지 후 30분 내" 같은 시점.
③ 점검 사전 고지 · 폐기 통보 기간
이 조항이 들어가는 순간 API 폐기는 계약 이행 문제가 된다.
④ 지원 채널과 1차 응답 시간
장애 자체보다 연락이 안 되는 것이 신뢰를 더 깎는다.

그리고 가용률의 계산식(SLI) 자체를 계약서에 적어야 한다 — 어느 지점에서 재는지, 429는 실패로 세는지, 파트너 쪽 네트워크 실패는 어떻게 다루는지. 이걸 안 적으면 숫자는 합의했지만 세는 법은 합의하지 않은 계약이 된다.

샌드박스 환경까지 따로 만드는 건 과한 투자 아닌가요? 가산점힌트: 안 만들면 그 비용이 어디로 가는지를 따라가 본다

비용이 사라지는 게 아니라 옮겨 갈 뿐이다. 샌드박스가 없으면 파트너의 첫 통합 테스트가 우리 운영 환경에서 벌어진다. 그 결과는 셋이다 — ① 운영 데이터에 테스트 콘텐츠·테스트 정산 건이 섞인다, ② 파트너의 실수 루프가 운영 한도를 소진한다, ③ 실패할 때마다 우리 담당자에게 문의가 온다.

연동 초기가 문의가 가장 많은 구간이라는 점이 결정적이다. 샌드박스와 테스트 키·샘플 데이터·실패 케이스 재현 수단이 있으면 파트너가 혼자 시행착오를 끝낼 수 있고, 그만큼 우리 사람 시간이 절약된다.

다만 규모에 맞게 판단한다. 파트너가 한두 곳이면 운영과 분리된 테스트 계정 + 테스트 전용 파트너 ID로 시작해도 되고, 파트너가 늘면 독립 환경 + 자동 발급되는 테스트 키로 올라간다. 핵심은 환경의 규모가 아니라 "파트너가 우리 운영을 건드리지 않고 실패해 볼 수 있는 자리가 있는가"다.

한 줄 요약
내부 API와 외부 파트너 API의 차이는 기능이 아니라 신뢰 경계이고, 내부가 느슨해도 되는 이유는 안전해서가 아니라 호출자를 우리가 고칠 수 있어서다 — 고칠 수 없는 소비자를 전제로 인증은 자격증명 생명주기(파트너별 발급, 겹침 기간을 둔 무중단 로테이션, 타임스탬프·nonce를 포함한 HMAC 서명, scope, 즉시 회수)까지, rate limit은 파트너별 쿼터와 429+Retry-After+매 응답의 잔량 헤더라는 계약까지, 문서는 파트너가 그것만 보고 구현하는 계약서 수준으로, 약속은 SLI·SLO·SLA 3단으로(SLA는 계측 오차와 개입 시간을 위해 SLO보다 느슨하게) 명문화하고, 내부 모델을 직접 노출하지 않는 외부 전용 계약 층을 어댑터로 얹는 것이 핵심이다.
