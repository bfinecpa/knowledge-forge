API 날짜/시간 포맷 규약
타임존 없는 문자열이 만드는 조용한 사고

면접 질문: "API 응답의 날짜/시간 포맷은 어떻게 규약하나요? (ISO 8601, 타임존 표기, epoch) 규약이 없으면 어떤 사고가 나나요?"

핵심 관전 포인트 — 규약의 뼈대는 두 가지 구분이다. ① '시점(instant)'과 '달력상 날짜(date)'는 다른 타입이다 — 시점은 ISO 8601 + 오프셋 명시(2026-08-31T00:30:00Z)로, 달력상 날짜는 타임존 없는 date-only(2026-08-31)로 주고받는다. 생일에 타임존을 붙이면 오히려 하루가 밀린다. ② 값의 기준과 값의 표현은 책임이 다르다 — 저장·전송은 UTC로 통일하고, 사용자 타임존으로 바꿔 보여주는 일은 사용자의 타임존을 아는 유일한 주체인 클라이언트가 맡는다. 그리고 이 논의 전체를 떠받치는 선행 구분이 하나 더 있다 — 오프셋(+09:00)은 "그 순간 UTC와 몇 시간 차이인가"라는 숫자 하나이고, 타임존 ID(Asia/Seoul)는 "이 지역의 시차가 언제 어떻게 바뀌어 왔고 앞으로 어떤 규칙으로 바뀌는가"를 담은 규칙 묶음이다. 같은 America/New_York이 겨울엔 -05:00, 여름엔 -04:00인 것이 그 차이다. 규약이 없으면 타임존 없는 datetime 문자열을 클라이언트마다 다르게 해석해 — 브라우저 JS의 파싱 규칙조차 date-only는 UTC로, 오프셋 없는 date-time은 로컬로 갈린다 — 해외 사용자와 자정 경계에서만 터지는 버그가 난다. epoch은 초/밀리초 모호성과 가독성 때문에 외부 계약의 기본값으론 부적합하다. 이걸 팀 규약 문서로 명문화하고, 애플리케이션 타입·직렬화 설정·DB 컬럼 타입까지 잠가 두는 것까지가 답이다.
  • 1
    시점과 날짜는 타입이 다르다 — '어느 순간'을 가리키는 값(createdAt, paidAt)은 오프셋이 문자열 안에 박힌 ISO 8601로(2026-08-31T00:00:00Z), '달력의 칸'인 값(birthDate, 정산 기준일)은 타임존 없는 date-only로(1990-05-15) 준다. 모든 시간 값에 타임존을 붙이는 것이 정답이 아니다 — 생일에 붙이면 서쪽 타임존 사용자 화면에서 하루가 밀린다.
  • 2
    값의 기준은 서버가, 표현은 클라이언트가 — 저장·전송은 UTC 단일 기준으로 통일한다. 서버가 사용자 타임존을 추측해 변환해 주면 "누구 기준인가"라는 새 모호성이 생기고 같은 리소스가 사용자마다 다른 바디를 갖게 되어 캐시 공유도 깨진다. 다만 "일별 집계의 하루 경계는 어느 타임존의 자정인가"는 서버가 결정해야 하는 정책이다 — 표시는 클라이언트, 경계는 서버.
  • 3
    그 밑에 오프셋 vs 타임존 ID 구분이 깔려 있다 — 오프셋은 숫자 하나, 타임존 ID는 규칙 묶음(IANA tzdb)이다. 그래서 지나간 순간은 오프셋(UTC)으로 충분하지만, 미래의 벽시계 약속("2027년 3월 10일 서울 9시")은 규칙이 바뀌면 따라가야 하므로 현지 시각 + 타임존 ID로 저장한다. "UTC로 통일"의 유일한 예외가 여기다.

0. 질문 + 출제 의도

질문: "API 응답의 날짜/시간 포맷은 어떻게 규약하나요? (ISO 8601, 타임존 표기, epoch) 규약이 없으면 어떤 사고가 나나요?"

출제 의도: 타임존 없는 문자열, 서버 로컬 시각, epoch 밀리초가 뒤섞인 API는 클라이언트마다 다른 해석을 낳고, 그 버그는 해외 사용자에게서만 발견된다(22장 글로벌·i18n과 연결). 포맷 하나도 팀의 계약으로 명문화하는지 — API 설계의 엄밀함이 가장 사소해 보이는 지점에서 드러난다.

이 페이지가 겨냥하는 약점 세 가지 ① "타임존을 붙이면 된다"로 끝내는 것 → 1·7절에서 오프셋과 타임존 ID의 차이, 그리고 붙이면 오히려 틀리는 값(생일)을 갈라 놓는다.
② "사고가 난다"를 막연히 말하는 것 → 2·3절에서 9시간 밀림 · 1000배 · 하루 밀림 · 파싱 실패 네 종류를 실제 출력과 계산으로 보여준다.
③ 규약을 문서로만 아는 것 → 8·9·10절에서 타입 · JVM 설정 · DB 컬럼 세 겹으로 잠그는 방법과, 문서에 반드시 들어가야 할 7항목까지 내려간다.

1. 전제 — 오프셋과 타임존 ID는 다른 것이다

이 주제 전체가 이 구분 위에 서 있다. "타임존을 붙인다"는 말이 실제로는 서로 다른 두 가지를 가리키기 때문이다. 이걸 먼저 갈라 두지 않으면 4절의 "UTC로 통일"과 11절의 "미래 예약은 예외"가 서로 모순처럼 들린다.

한 문장으로 외우는 구분

오프셋은 영수증에 찍힌 환율 숫자, 타임존 ID는 환율을 정하는 규정집

영수증의 숫자는 그때 그 거래를 정확히 설명하지만 다음 달에도 같은 숫자일지는 말해 주지 않는다. 규정집은 날짜를 넣으면 그날의 숫자를 계산해 준다. 그래서 지나간 순간에는 숫자(오프셋)로 충분하고, 앞으로 올 약속에는 규정집(타임존 ID)이 필요하다.

이 표의 마지막 줄이 11절 마지막 꼬리질문(미래 예약 시각)의 답을 미리 담고 있다.
축오프셋 (+09:00 / Z)타임존 ID (Asia/Seoul)이 줄이 뜻하는 것
정체숫자 하나 (UTC와의 차이)규칙 묶음의 이름값 vs 함수

"규칙"의 실체 — IANA tzdb는 정기적으로 배포되는 데이터다 IANA tzdb(IANA Time Zone Database, tz database)는 전 세계 지역별 타임존 규칙 — 표준 오프셋, 서머타임 시작·종료 규칙, 그리고 과거의 변경 이력까지 — 을 모아 관리하는 공개 데이터베이스다. 각국 정부가 규칙을 바꾸면 갱신판이 발표되고(연 몇 차례), JDK·운영체제·브라우저가 그것을 받아 반영한다. ZoneId.of("Asia/Seoul")이 실제로 참조하는 것이 이 데이터이고, JDK에 어떤 판이 실려 있는지는 버전 문자열(2025b 같은)로 확인할 수 있다. 요점은 규칙 변경이 추상적인 가정이 아니라 "정기적으로 배포되는 데이터의 변경"이라는 것이다.

2. 규약이 없으면 나는 사고 4종

먼저 결론 — 사고는 이 네 가지 모양으로 나온다

① 9시간 밀림
타임존 없는 datetime
받는 쪽이 자기 로컬로 해석. 국내에서는 상쇄되어 재현되지 않는다.
② 1000배
epoch 초/밀리초
1970년 또는 서기 58,633년. 너무 이상해서 오히려 금방 잡힌다.
③ 하루 밀림
집계 경계 · date-only 오용
가장 위험하다. 매출이 몇 % 다르게 나오는 형태라 몇 달을 간다.
④ 파싱 실패
소수점 초 자릿수 · 공백 구분자
같은 필드인데 값에 따라 형태가 달라져 어느 날 갑자기 예외.

외우는 순서 — 밀림 · 1000배 · 하루 · 파싱. ①②는 눈에 띄게 틀리고, ③④는 그럴듯하게 조금 틀린다. 면접에서 값이 나가는 것은 ③을 먼저 말하는 것이다.

2-1. 한 JSON 안에 세 가지 유파가 공존한다

before 규약 없는 API의 전형 — 세 필드 모두 "언제인지 알 수 없는 값"
{
  "createdAt": "2026-08-31 09:00:00",   // 타임존 없음 — 어느 기준의 9시인가?
  "updatedAt": 1788134400,              // epoch — 초인가 밀리초인가?
  "expiredAt": "2026-09-01T00:00:00"    // T 는 있지만 오프셋이 없다
}

서버 개발자 머릿속에서는 전부 KST지만, 문자열 어디에도 그 정보가 없다. 받는 쪽은 각자 자기 로컬 타임존이나 UTC로 해석한다.

이 사고의 고약한 성질 — 개발자 자리에서는 100% 정상이다 국내에서 재현되지 않는다. 서버(KST)와 클라이언트(KST)가 같은 타임존이면 잘못된 해석끼리 상쇄되어 멀쩡해 보이기 때문이다. 해외 사용자, 해외 출장 중인 사용자, UTC로 도는 배치 서버에서만 9시간 밀림과 날짜 하루 밀림이 나타난다.

2-2. epoch 초/밀리초 1000배 사고

epoch은 기준 시점(1970-01-01T00:00:00Z)부터의 경과 시간을 나타내는 숫자다. 문제는 단위(초인지 밀리초인지)가 값 안에 적혀 있지 않다는 것이다. 그래서 한쪽이 초로 보내고 다른 쪽이 밀리초로 읽으면 1000배가 어긋난다.

2-3. 정산·통계의 하루 밀림 — 조금만 틀려서 더 위험하다

"8월 31일 주문"의 경계가 KST 자정이냐 UTC 자정이냐에 따라 집계 대상이 9시간어치 달라진다. 일별 정산·리포트가 시스템마다 다른 숫자를 내는 원인이 대개 여기다.

3. 브라우저 JS의 파싱 갈림길 함정

가장 결정적인 사례가 여기다. 자바스크립트의 new Date(문자열)은 같은 데이터라도 문자열이 어떤 모양이냐에 따라 UTC로 볼지 로컬로 볼지가 갈린다. ECMAScript 명세가 날짜/시간 문자열을 두 부류로 나눠 다르게 정의하기 때문이다 — 하나의 함수 안에 서로 반대되는 두 규칙이 들어 있는 셈이다.

실증 같은 "8월 31일 0시"인데 결과가 9시간 어긋나고, UTC 기준으로는 날짜까지 하루 다르다
$ TZ=Asia/Seoul node
> new Date("2026-08-31").toISOString()
'2026-08-31T00:00:00.000Z'        ← date-only 라서 UTC 자정으로 해석

> new Date("2026-08-31T00:00:00").toISOString()
'2026-08-30T15:00:00.000Z'        ← date-time 이라서 KST 자정으로 해석 → UTC 로는 전날 15시


$ TZ=America/New_York node
> new Date("2026-08-31").toLocaleString("en-US")
'8/30/2026, 8:00:00 PM'           ← 화면에는 8월 30일로 뜬다 (날짜 하루 밀림)

여기서 나오는 실무적 따름 결론 — 날짜 값은 애초에 Date로 파싱하지 않는다

date-only 문자열도 Date에 넣는 순간 UTC 시점이 되어 버린다. 위 세 번째 출력이 그 증거다 — "2026-08-31"이라는 달력의 칸을 Date에 넣었더니 시간선 위의 점이 되었고, 그 점을 뉴욕에서 표시하니 전날이 됐다.

그래서 날짜 값은 문자열 그대로 다루거나, 날짜 전용 타입(브라우저에 순차 도입되고 있는 Temporal API의 PlainDate 등)을 쓴다. 7절의 "날짜는 시점이 아니다"가 서버만의 이야기가 아니라는 뜻이다.

4. 시점의 표준형 — ISO 8601 + 오프셋 명시

4-1. 오프셋을 값 안에 넣는다

'어느 순간'을 가리키는 값(생성 시각, 결제 시각, 만료 시각)의 규약은 하나다.

after 오프셋이 문자열 안에 있어 해석의 여지가 없다
{
  "createdAt": "2026-08-30T15:00:00Z",        // UTC 표기 (권장 기본)
  "paidAt":    "2026-08-31T00:00:00+09:00"    // 오프셋 표기 — 같은 순간의 다른 표현
}
핵심은 포맷의 모양이 아니라 오프셋(Z 또는 ±hh:mm)이 값 안에 포함된다는 것

해석에 문맥이 필요 없어진다는 뜻이고, 그래서 "서버가 어느 타임존이더라"를 아는 사람만 값을 읽을 수 있는 상황이 사라진다.

덤으로 따라오는 실무 이점 두 가지 가산점 ① 사전순 정렬 = 시간순 정렬. 자릿수가 고정이라 문자 비교가 곧 크기 비교가 된다 — 로그 파일을 sort로 정렬하거나 문자열 컬럼을 ORDER BY 해도 시간순이 나온다. ② 사람이 눈으로 읽을 수 있다. 장애 대응 중 로그와 응답을 대조할 때 변환 단계가 사라진다.
단, ①에는 전제가 붙는다 — "같은 오프셋으로 통일했을 때"만 성립한다. 오프셋이 섞이면 깨진다: "2026-08-31T00:00:00+09:00"(= UTC 8/30 15:00)와 "2026-08-30T16:00:00Z"(그보다 1시간 뒤)를 문자열로 정렬하면 나중 순간이 앞에 온다. 정렬 이점을 쓰려면 UTC(Z) 통일 + 소수점 자릿수 고정이 함께 와야 한다(10절).

4-2. ISO 8601과 RFC 3339의 관계 — 같은 말이 아니다

4-3. 응답은 UTC 기본, 요청도 같은 규약으로

응답 — UTC(Z) 표기로 통일

  • 서버가 사용자 타임존을 추측해 변환해 주기 시작하면 "누구 기준으로 변환한 값인가"라는 새 모호성이 생긴다.
  • 같은 리소스가 사용자마다 다른 바디를 갖게 되어 캐시 공유가 깨진다.
  • 서버는 단일 기준의 값을 주고, 표시 변환은 사용자 타임존을 아는 클라이언트가 한다 — 책임 분리가 규약의 일부다.

예외 — 오프셋 자체가 도메인 정보일 때

  • "매장 현지 영업 시작 시각"처럼 "현지에서 몇 시였는가"가 의미를 갖는 값이라면 +09:00 표기를 유지한다.
  • UTC로 바꿔 버리면 정보가 사라지기 때문이다 — 순간은 보존되지만 "현지 9시였다"는 사실이 없어진다.
  • 자바 타입으로는 OffsetDateTime이 이 자리다(5절).
요청도 같은 규약을 적용한다 — 오프셋 없는 입력은 400 "관대하게 받아서 서버 타임존으로 추정하자"는 순간 2절의 사고가 입력 방향에서 그대로 재발한다. 그리고 입력 쪽 사고가 훨씬 나쁘다 — 응답은 잘못 보여주고 끝나지만, 입력은 잘못된 값이 DB에 저장되므로 원래 의도를 사후에 복원할 방법이 없다. "9시간 밀린 값"과 "원래 그 시각인 값"이 저장 후에는 구분되지 않는다.

5. Java 시간 타입 5종 — 무엇을 담는가

포맷 규약을 코드로 지키려면 타입을 골라야 하는데, java.time의 타입들은 이름이 비슷해서 자주 혼동된다. 각 타입이 무엇을 담고 무엇을 담지 않는지를 한 번에 놓고 보는 것이 가장 빠르다.

파란 줄이 기본값, 붉은 줄이 시점 필드에 쓰면 안 되는 타입이다.
타입무엇을 담는가타임존 정보어느 필드에 쓰나toString() 결과
Instant시간선 위의 한 점 (epoch부터의 경과 시간)없음 — 항상 UTC 기준이라 필요가 없다시점 필드의 기본값. 생성·결제·수정 시각2027-03-10T00:00:00Z
OffsetDateTime시점 + 그때의 UTC 오프셋오프셋(숫자)만현지 오프셋 자체가 정보인 값 (매장 현지 시각)2027-03-10T09:00+09:00
ZonedDateTime시점 + 타임존 ID(규칙)타임존 ID(규칙 묶음)미래 예약 — 규칙이 바뀌어도 따라가야 하는 값2027-03-10T09:00+09:00[Asia/Seoul]
LocalDateTime날짜 + 시각. 어느 타임존인지는 어디에도 없다없음시점 필드에 쓰면 안 된다2027-03-10T09:00
LocalDate달력의 칸없음 (있어서도 안 된다)생일·정산 기준일·휴무일 (7절)2027-03-10

LocalDateTime이 왜 위험한가 — 이름이 거짓말을 한다

이름에 Local이 붙어 있어 "로컬 타임존의 시각"처럼 읽히지만, 어느 타임존이 그 '로컬'인지는 값 어디에도 적혀 있지 않다. 담고 있는 것은 "2027년 3월 10일 9시"라는 달력·시계의 읽음값뿐이다.

LocalDateTime 필드→ 직렬화하면 오프셋 없는 문자열→ 3절의 파싱 갈림길→ 클라이언트마다 다른 순간

게다가 이 타입으로 현재 시각을 만들면(LocalDateTime.now()) JVM의 기본 타임존을 읽어 오므로, 로컬 개발 머신(KST)과 운영 컨테이너(UTC)에서 같은 코드가 다른 값을 만든다. "로컬에선 됐는데 서버에선 9시간 밀린다"의 정체가 대개 이것이다.

ZonedDateTime이 왜 미래 예약에 적합한가 오프셋 숫자가 아니라 타임존 ID를 들고 있기 때문이다. 2027-03-10T09:00[Asia/Seoul]은 "그때 서울의 규칙으로 계산했을 때의 오전 9시"라는 뜻이라, 그 사이 규칙이 바뀌면 계산 결과인 순간도 함께 바뀐다. 사용자가 의도한 것이 바로 그 "현지 9시"다(11절 마지막 꼬리질문).
단, API 계약에 쓸 때 함정이 하나 있다 — Jackson이 대괄호를 떼 버린다 Jackson은 기본 설정에서 직렬화 시 [Asia/Seoul] 부분을 떼고 오프셋만 내보낸다(WRITE_DATES_WITH_ZONE_ID가 기본 비활성). 즉 자바 안에서는 규칙을 들고 있어도 JSON으로 나가는 순간 오프셋 숫자로 납작해진다. 그래서 미래 예약을 API로 주고받을 때는 대괄호 표기에 기대지 말고 필드를 둘로 나누는 것이 안전하다.
계약 미래의 벽시계 약속 — 현지 시각과 타임존 ID를 각각 명시적인 필드로
{
  "startsAt": "2027-03-10T09:00:00",   // 오프셋 없는 현지 시각 (여기서는 이게 맞다)
  "timeZone": "Asia/Seoul"             // 규칙을 가리키는 ID
}

// 주의: 이 JSON 의 startsAt 은 "오프셋을 빠뜨린 것"이 아니라
//       "오프셋을 아직 확정하지 않은 것"이다. 확정은 실행 시점에
//       timeZone 의 그때 규칙으로 계산한다. 두 필드는 반드시 함께 다닌다.

6. epoch은 언제 쓰나 — 트레이드오프

epoch을 무조건 나쁘다고 하면 반쪽 답이다. 장단이 분명한 선택지이므로 나눠 보자.

장점

  • 타임존 해석의 여지가 원천적으로 없다 — 숫자 하나가 곧 시점이다.
  • 정렬·차이 계산이 그냥 산술 연산이다.
  • 페이로드가 작다 — 대량 이벤트 스트림에서 유의미하다.

단점

  • 단위(초/밀리초)가 값에 없다 → 계약이 없으면 2-2절의 1000배 사고.
  • 사람이 못 읽는다 → 디버깅·로그 대조 때마다 변환이 필요하다.
  • 달력 개념(date-only)을 표현할 수 없다 → API 전체를 한 포맷으로 통일하는 데 걸림돌.

판단 — "좋다/나쁘다"가 아니라 "어디에 쓰느냐"로 답한다

epoch이 합리적인 곳
내부 시스템 간 이벤트 스트림, 로그, 성능 민감 구간. 기계끼리 대량으로 주고받는 자리.
ISO 8601이 나은 곳
사람이 읽고 여러 클라이언트가 소비하는 외부 API 계약의 기본값. 파트너·문서·디버깅이 걸린 자리.
최악은 ISO와 epoch, 초와 밀리초가 한 API 안에 섞이는 것 — 2-1절의 before가 정확히 그 모습이다

epoch을 쓰기로 했다면 "밀리초 단위"임을 계약에 명시하고 전 필드에 일관 적용한다. 필드명에 단위를 넣는 것(createdAtMs)도 값싼 방어다.

7. 시점 vs 달력상 날짜 — 이 주제의 진짜 변별 지점 필수

모든 시간 값에 타임존을 붙이는 것이 정답이 아니다

둘을 가르는 판별 질문 — 이 한 문장만 외우면 된다

이 값이 뉴욕에서도 똑같은 글자로 보여야 하는가?
그렇다 → 달력의 칸
생일·기념일·정산 기준일·휴무일. 어느 타임존에서 봐도 5월 15일은 5월 15일이므로 애초에 타임존 변환의 대상이 아니다.
아니다 → 시간선 위의 점
결제·생성·만료 시각. 서울에서 9시에 결제한 그 순간은 뉴욕에서 전날 저녁으로 보이는 것이 맞다.

7-1. 날짜에 타임존을 붙이면 오히려 버그다

7-2. 날짜처럼 보이지만 사실은 시점인 값 함정

반대 방향의 함정도 있다. "쿠폰 만료일: 8월 31일"은 겉보기엔 날짜지만 실제로는 시점 결정이 숨어 있다.

"8월 31일까지 쓸 수 있다"는 말은 정확히 언제까지인가? KST 8월 31일 23:59:59까지인가, UTC 기준인가, 사용자가 있는 지역의 자정인가? 이건 포맷 문제가 아니라 도메인 결정이다. 그리고 결정하지 않으면 "분명 31일인데 못 쓴다"는 CS가 자정 무렵에만 들어온다.

"8월 31일까지"→ 도메인 결정: KST 기준 해당일 23:59:59→ 시점으로 환산해 계약에 명시 
KST 2026-08-31 23:59:59  =  UTC 로 환산하면 9시간을 뺀다
                         =  2026-08-31 14:59:59Z          ✓ 검산 완료

// 같은 방식으로 "KST 9월 1일 자정 직전까지"를 경계로 잡으면
//   2026-08-31T15:00:00Z 미만 이라는 조건이 된다.
// → 경계를 '이하'로 잡을지 '미만'으로 잡을지도 함께 정해야 한다.
//   (23:59:59 이하로 잡으면 그날 마지막 1초가 사라진다)

{ "expiresAt": "2026-08-31T14:59:59Z" }   // 도메인 결정의 결과를 시점으로 명시

정리하면 — 7절의 판별 질문에 "날짜"라고 답한 값이라도, 그 날짜에 경계가 걸려 있으면 결국 시점 결정이 필요하다. 생일에는 경계가 없지만 만료일에는 있다.

8. DB 타입도 같은 구분을 따른다 — PostgreSQL 기준

애플리케이션의 Instant / LocalDate 구분은 DB 컬럼 타입 선택에 그대로 이어진다. 여기서 PostgreSQL의 이름이 오해를 많이 사므로 정확히 짚어야 한다.

timestamptz(= timestamp with time zone)는 이름과 달리 타임존을 저장하지 않는다
PostgreSQL 타입저장하는 것세션 타임존의 영향짝이 되는 Java 타입
timestamptz시간선 위의 한 점 (UTC로 정규화)입력 해석과 출력 표시에만 영향. 저장된 값 자체는 무관Instant / OffsetDateTime
timestamp달력·시계의 읽음값 (기준 없음)없음 — 대신 어느 순간인지 알 수 없다LocalDateTime (시점 필드엔 쓰지 않는다)
date달력의 칸없음 (있어서도 안 된다)LocalDate

8-1. 2-3절의 "하루 밀림"이 SQL 레벨에서 나타나는 모습

before 세션 설정에 결과가 좌우되고, 인덱스도 못 탄다
-- created_at::date 는 "세션 타임존 기준의 날짜"라
-- 세션 설정에 따라 결과가 달라진다.
-- 게다가 컬럼에 함수를 씌우면 인덱스도 쓰지 못한다.
SELECT count(*) FROM orders
 WHERE created_at::date = DATE '2026-08-31';

-- 같은 쿼리를 UTC 세션에서 돌리면 KST 8/31 09:00 부터
-- 9/1 08:59 까지가 잡힌다 — 리포트 숫자가 달라진다.
after 하루의 경계를 쿼리에 명시하고 범위 조건으로
-- 하루의 경계를 어느 타임존의 자정으로 볼지 쿼리에 명시하고,
-- 범위 조건으로 쓴다. 범위 조건이라 created_at 인덱스를
-- 그대로 탈 수 있다.
SELECT count(*) FROM orders
 WHERE created_at >= TIMESTAMPTZ '2026-08-31 00:00:00+09'
   AND created_at <  TIMESTAMPTZ '2026-09-01 00:00:00+09';

-- 경계가 값 안에 적혀 있으므로 어느 세션에서 돌려도
-- 같은 숫자가 나온다. "하루"의 정의가 쿼리의 일부가 된 것.
이 before/after가 보여주는 것 — 포맷 규약은 성능 문제이기도 하다 컬럼에 함수를 씌우는 순간 인덱스를 못 탄다는 것은 SQL의 일반 원칙이지만, 날짜 경계를 명시하지 않은 규약이 개발자를 그 코드로 밀어 넣는다는 점이 중요하다. "하루의 경계"를 문서에 못박아 두면 정확성과 인덱스 사용이 동시에 따라온다.

9. 규약을 어길 수 없게 잠그는 세 겹

문서만으로는 규약이 지켜지지 않는다. 기본값을 규약대로 잠가 두어야 무심코 쓴 코드가 규약을 지키게 된다.

before 서버 타임존에 의존하는 타입
// 서버 TZ 가 바뀌면 값의 의미가 바뀐다.
public record OrderResponse(
        LocalDateTime createdAt
) {}

// 오프셋 정보가 애초에 없다
// → 직렬화하면 "2026-08-31T09:00:00"
// → 3절의 파싱 갈림길로 그대로 들어간다.
after 시점은 오프셋을 아는 타입으로
// 직렬화 결과에 Z 가 붙는다.
public record OrderResponse(
        Instant createdAt
) {}

// "2026-08-31T00:00:00Z"
// 타입이 기준을 값 안에 들고 있으므로
// 어떤 환경에서 직렬화해도 결과가 같다.

세 겹으로 잠근다 — 타입 · 설정 · 스키마

타
타입 선택이 첫 번째 방어선이다. Spring Boot + Jackson 조합은 기본으로 java.time 타입을 epoch 숫자가 아니라 ISO 8601 문자열로 직렬화한다(WRITE_DATES_AS_TIMESTAMPS를 비활성으로 설정해 둔다). 즉 문제는 라이브러리가 아니라 타입이다 — LocalDateTime은 애초에 오프셋 정보를 갖고 있지 않으니 어떤 설정을 해도 오프셋 없는 문자열이 나간다. 시점 필드를 Instant(또는 OffsetDateTime)로 선언하는 것 자체가 규약의 강제다.
설
JVM·컨테이너의 기본 타임존을 UTC로 통일한다. 다만 이것은 보조 수단이다. 더 근본적인 것은 기본 타임존을 읽는 API를 코드에서 쓰지 않는 것이다 — LocalDateTime.now(), 타임존 인자 없는 변환 같은 것들. 요지는 "설정을 잘 맞춘다"가 아니라 "설정이 뭐든 결과가 같도록 의존 자체를 없앤다"이다.
스
DB 컬럼 타입으로 스키마 차원에서 못박는다(8절). "UTC 기준 저장"이 운영 설정이 아니라 스키마의 성질이 되게 하는 것이다. 설정은 누군가 바꿀 수 있지만 컬럼 타입은 마이그레이션 없이는 바뀌지 않는다.
잠금의 강도 순서 — 스키마 > 타입 > 설정. 아래로 갈수록 "누군가 실수로 되돌릴 수 있는" 층이다.

10. 팀 규약 문서 체크리스트 7항목

마지막 한 겹은 문서다. 아래 항목이 정해져 있지 않으면 사람이 바뀔 때마다 같은 논쟁이 반복된다.

표현 3 · 처리 2 · 예외 2로 묶어 외운다. 붉은 줄은 포맷이 아니라 도메인 정책이라 특히 빠뜨리기 쉽다.
묶음항목정해야 할 것이 문서에서의 기본값
표현시점 포맷정확한 문자열 형태 (예시로 못박기)ISO 8601 + 오프셋 필수, UTC(Z) 기본 (4-1)
date-only 사용 기준어떤 값이 달력상 날짜인가생일·정산 기준일·휴무일 등 (7절)
필드 네이밍이름으로 타입 구분...At = 시점, ...Date = date-only (7절)
처리요청 입력 규칙오프셋 없는 입력을 어떻게 할 것인가400 거절 (4-3)
하루의 경계일별 집계의 자정 기준 타임존도메인 결정 — 반드시 명시 (2-3, 8-1)
예외epoch 사용 범위쓸 곳과 단위내부 이벤트·로그에 한정, 밀리초로 고정 (6절)
소수점 초 자릿수몇 자리로 고정할 것인가밀리초 3자리 고정 (아래)

마지막 항목이 사소해 보이지만 실제로 사고를 낸다 — Instant의 자릿수는 값에 따라 달라진다

Instant.parse("2026-08-31T00:00:00Z")   → "2026-08-31T00:00:00Z"          (0자리)
Instant.ofEpochMilli(1788134400123L)  → "2026-08-31T00:00:00.123Z"      (3자리)
Instant.now()                         → "2026-09-01T10:11:54.919910Z"   (6자리)
                                                            ↑
              같은 필드인데 값에 따라 소수점 자릿수가 0, 3, 6, 9 로 달라진다.

자바의 ISO 형식은 필요한 만큼만 출력하되 3자리 단위로 끊어 쓴다. 받는 쪽이 자릿수 고정 포맷(yyyy-MM-dd'T'HH:mm:ss.SSS'Z')으로 파싱하도록 구현해 두었다면, 0자리 값이나 6자리 값이 오는 순간 파싱 예외가 난다. 소수점 초를 아예 받지 않는 기본 설정을 가진 파서도 있다.

값에 따라 형태가 달라지는 필드는 계약이 아니다

그래서 "밀리초 3자리 고정"을 규약에 넣고 서버가 항상 그 형태로 내보내도록 포맷터를 지정한다. 이 사고가 특히 고약한 이유는 테스트 데이터로는 재현되지 않다가(Instant.parse로 만든 값은 0자리) 운영에서 Instant.now()가 들어가는 순간 터진다는 데 있다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

규약의 뼈대 두 가지?
① 시점과 달력상 날짜는 다른 타입(오프셋 붙인 ISO vs date-only) ② 값의 기준(UTC 저장·전송)과 표현(클라이언트 변환)은 책임이 다르다.
오프셋 vs 타임존 ID 한 문장?
오프셋은 숫자 하나(영수증의 환율), 타임존 ID는 규칙 묶음(환율 규정집). 지나간 순간은 오프셋, 앞으로 올 약속은 타임존 ID.
규약 없을 때의 사고 4종?
밀림 · 1000배 · 하루 · 파싱. ①②는 눈에 띄게 틀리고 ③④는 그럴듯하게 조금 틀려서 더 위험하다.
JS new Date의 두 규칙?
오프셋이 없을 때 date-only는 UTC, date-time은 로컬. 정반대다. 공백 구분자는 명세 밖 → 엔진 재량.
시점/날짜 판별 질문?
"이 값이 뉴욕에서도 같은 글자여야 하는가?" 그렇다 → date-only·LocalDate·date·...Date. 아니다 → ISO+Z·Instant·timestamptz·...At.
이름이 거짓말하는 타입 둘?
LocalDateTime(어느 '로컬'인지 값에 없다) · timestamptz(타임존을 저장하지 않는다. UTC로 정규화해 순간만 남긴다).
세 겹 잠금?
타·설·스 — 타입(Instant) · 설정(JVM UTC, 기본 타임존 의존 제거) · 스키마(timestamptz/date). 강도는 스키마 > 타입 > 설정.
규약 문서 7항목?
표현3(포맷·date-only 기준·네이밍) 처리2(입력 400·하루 경계) 예외2(epoch 범위·소수점 3자리 고정).

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

왜 저장·전송은 UTC로 하고, 표시 변환은 클라이언트가 하나요? 필수힌트: "클라이언트만 아는 정보"가 무엇인지 말하고, 마지막에 예외를 한 줄 덧붙이면 답이 커진다

시점의 '값'과 '표현'을 분리하기 위해서다. 같은 순간도 타임존마다 표현이 다른데, 사용자의 타임존을 아는 것은 클라이언트뿐이다(기기 설정·브라우저가 알려 준다).

서버가 표시까지 책임지려면 사용자별 타임존을 추측하거나 관리해야 하고, 같은 리소스가 사용자마다 다른 바디를 갖게 되어 캐시 공유도 깨진다. 반면 서버가 단일 기준(UTC)의 값을 주면 저장 쪽에서도(비교·정렬·집계가 단일 기준에서 성립한다) 전송 쪽에서도(해석 모호성이 없다) 단순해진다.

단, 예외를 함께 말하면 답이 한 칸 커진다

"일별 집계" 같은 서버 사이드 날짜 경계 연산은 어느 타임존의 자정인지를 서버가 결정해야 한다(2-3절, 8-1절). "전부 클라이언트 책임"이 아니라 "표시는 클라이언트, 경계 정책은 서버"가 정확한 분업이다. 그리고 오프셋 자체가 도메인 정보인 값(매장 현지 영업 시각)도 UTC로 납작하게 만들면 안 된다.

epoch 밀리초는 파싱 모호성이 없는데 왜 기본값으로 안 쓰나요?힌트: "모호성이 없다"는 전제가 이미 무엇에 기대고 있는지를 짚는다

모호성이 없다는 전제가 이미 계약("밀리초다")에 의존한다. 값 자체에 단위가 없어서, 계약이 부재하면 1000배 사고가 그 첫 희생자가 된다(2-2절). 즉 "포맷이 안전해서 계약이 필요 없다"가 아니라 "계약이 있어야만 안전한 포맷"이다.

그리고 외부 API의 소비자는 기계만이 아니다. 디버깅 중 로그와 응답을 눈으로 대조하는 개발자, 문서를 읽는 파트너에게 epoch은 매번 변환 비용이다. date-only 표현이 불가능해 API 전체를 한 포맷으로 통일할 수 없다는 것도 걸림돌이다.

정리하면 "어디에 쓰느냐"로 답한다 — 내부 이벤트 스트림·로그처럼 기계 간 대량 교환에는 epoch(단위 명시)이 합리적이고, 외부 계약의 기본값은 ISO 8601이다.

생일 같은 필드에 타임존을 붙이면 무슨 일이 생기나요? 함정힌트: 클라이언트가 "잘못 처리해서"가 아니라 "정상 처리해서" 망가진다는 점이 핵심이다

달력상 날짜를 시점(...T00:00:00Z)으로 인코딩하는 순간, 클라이언트의 표준 처리인 "로컬 변환 후 표시"가 그 값을 망가뜨린다. UTC 자정은 UTC보다 서쪽 타임존에서 전날 저녁이 되어 생일이 하루 밀려 보인다 — 7-1절에서 실제 출력('5/14/1990, 8:00:00 PM')으로 확인했다.

주목할 점은 클라이언트가 버그를 낸 것이 아니라는 것이다. 시점을 받으면 로컬로 변환해 보여주는 것이 맞는 동작이다. 잘못된 것은 날짜를 시점으로 인코딩한 서버의 계약이다.

날짜는 타임존 변환의 대상이 아니므로 date-only("1990-05-15")로 주고받는 것이 정확한 표현이다. 이 질문의 본질은 "모든 시간 값에 타임존을 붙이는 게 정답은 아니다 — 시점과 날짜는 타입이 다르다"는 구분을 하는지다.

미래의 예약 시각도 UTC로 변환해 저장하면 되나요? 시니어 변별힌트: "UTC로 통일"의 유일한 예외다. 왜 예외인지를 tzdb의 실제 변경 사례로 뒷받침한다

과거·현재의 시점은 UTC 저장이 정답이지만, 미래의 '벽시계 약속'은 예외다.

"2027년 3월 10일 오전 9시 서울 회의"를 지금 UTC로 환산해 2027-03-10T00:00:00Z로 고정한다고 하자. 그 사이 해당 지역의 타임존 규칙이 바뀌면 — 서머타임 도입·폐지, 표준 오프셋 변경 — 고정해 둔 UTC 값이 가리키는 현지 시각은 9시가 아니게 된다. 사용자가 약속한 것은 UTC의 어떤 순간이 아니라 "서울에서 9시"였는데도 그렇다.

이 "규칙이 바뀐다"가 추상적인 가정이 아니라는 것을 IANA tzdb(1절)로 뒷받침하면 답이 단단해진다. tzdb는 각국의 규칙 변경을 반영해 매년 여러 차례 갱신판이 나오는 살아 있는 데이터다. 실제로 멕시코는 2022년에 대부분 지역의 서머타임을 폐지했고, 이집트는 2023년에 서머타임을 다시 도입했다. 한국도 1987~1988년에 서머타임을 시행한 이력이 tzdb에 그대로 남아 있다.

미래의 약속은 현지 시각 + 타임존 ID로 저장하고, 실행 시점에 그때의 규칙으로 UTC를 계산한다

자바 타입으로는 ZonedDateTime이 이 역할을 하고(5절), API 계약으로는 startsAt + timeZone 두 필드로 나눠 표현하는 것이 안전하다 — Jackson이 직렬화 과정에서 [Asia/Seoul]을 떼 버리기 때문이다. "UTC로 통일"이라는 원칙의 예외 조건과 그 근거를 아는지가 이 질문의 변별점이다.

서버와 DB의 타임존 설정은 어떻게 관리하나요?힌트: "UTC로 맞춥니다"에서 멈추면 절반이다. 세 층으로 나눠 말한다

코드가 "기본 타임존"에 의존하는 지점을 없애는 방향으로 관리한다. 설정을 잘 맞추는 것은 보조 수단이고, 의존을 없애는 것이 본질이다.

애플리케이션
JVM·컨테이너 기본 타임존을 UTC로 통일해 환경 간 차이를 없애되, 애초에 기본 타임존을 읽는 타입·API(LocalDateTime.now(), 타임존 인자 없는 변환)를 쓰지 않는다. Instant처럼 기준이 값 안에 있는 타입을 쓰면 설정이 무엇이든 결과가 같다.
DB
시점 컬럼은 timestamptz, 달력상 날짜는 date로 못박는다(8절). timestamptz는 세션 타임존이 입력 해석과 출력 표시에만 영향을 주고 저장 값은 안 바뀌므로, 세션 설정이 어긋나도 비교·정렬·집계 결과가 달라지지 않는다. timestamp를 시점에 쓰면 이 안전장치가 통째로 없다.
커넥션·세션
그럼에도 표시 일관성을 위해 커넥션 풀 수준에서 세션 타임존을 UTC로 고정해 두면, 어느 인스턴스에서 조회해도 같은 문자열이 나와 로그 대조가 쉬워진다.
"설정을 잘 맞춘다"가 아니라 "설정이 뭐든 결과가 같도록 의존을 없앤다"

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

ISO 8601 문자열은 사전순 정렬 = 시간순 정렬이라던데, 항상 그런가요? 함정힌트: 반례를 하나 들 수 있으면 끝난다

아니다. "같은 오프셋으로 통일되어 있고 자릿수가 고정일 때"만 성립한다.

반례: "2026-08-31T00:00:00+09:00"은 UTC로 2026-08-30T15:00:00Z이고, "2026-08-30T16:00:00Z"는 그보다 1시간 뒤의 순간이다. 그런데 문자열로 비교하면 "2026-08-30..."이 "2026-08-31..."보다 앞서므로 나중 순간이 먼저 오도록 정렬된다.

자릿수도 같은 이유로 문제가 된다. "...T00:00:00Z"와 "...T00:00:00.123Z"가 섞이면 자리수가 달라 문자 비교가 시간 비교와 어긋날 수 있다.

그래서 이 이점을 쓰려면 UTC(Z) 통일 + 소수점 3자리 고정이 함께 와야 한다

면접에서는 "정렬 이점이 있다"로 끝내지 말고 "단, 오프셋이 섞이면 깨진다"까지 말하는 것이 변별점이다. 이 조건이 곧 규약 문서에 "UTC 기본"과 "소수점 3자리 고정"을 함께 적어야 하는 이유이기도 하다.

오프셋 없는 입력을 400으로 거절하면 클라이언트가 불편해하지 않나요? 관대하게 받으면 안 되나요?힌트: "관대함"의 대가를 누가 언제 치르는지를 따진다

관대함의 대가를 치르는 시점이 다르다는 것이 답의 뼈대다. 400은 클라이언트 개발자가 통합 테스트 중에 즉시 알아차리는 비용이고, 관대한 추정은 운영에서 해외 사용자가 자정 무렵에 치르는 비용이다. 같은 비용이 아니다.

게다가 입력 방향의 사고는 회복이 훨씬 어렵다. 응답은 잘못 보여주고 끝나지만, 입력은 잘못 해석된 값이 그대로 DB에 저장된다. 저장된 뒤에는 "9시간 밀려 들어온 값"과 "원래 그 시각인 값"이 구분되지 않으므로 사후 보정이 불가능하다.

실무적 절충은 있다 — 신규 API는 처음부터 엄격하게 시작하고, 이미 관대하게 받고 있던 기존 API는 ① 경고 로그와 응답 헤더로 알리는 기간을 두고 ② 사용 클라이언트를 식별해 마이그레이션한 뒤 ③ 버전을 올려 거절로 전환한다. 포맷 규칙을 조이는 것은 파괴적 변경이므로 하위 호환 절차를 그대로 따른다(08-backward-compatible-api-changes.md).

MySQL에는 timestamptz가 없는데 어떻게 하나요? 가산점힌트: "타입이 강제해 주던 것"을 무엇이 대신하는지 말한다

PostgreSQL의 timestamptz에 정확히 대응하는 타입이 없어서, 스키마가 해 주던 강제를 애플리케이션과 커넥션 설정이 나눠 진다.

TIMESTAMP
세션 타임존 기준으로 UTC로 정규화해 저장하고 조회 시 되돌린다 — 성격은 timestamptz에 가깝다. 다만 표현 범위가 좁아(2038년까지) 만료일·예약처럼 먼 미래를 담는 컬럼에는 쓰기 어렵다.
DATETIME
타임존 개념이 없다. 적힌 그대로 보관하므로 PostgreSQL의 timestamp·자바의 LocalDateTime과 같은 성격이다. 대신 먼 미래 날짜도 담을 수 있다.

그래서 흔한 실무 관행은 DATETIME(6) 컬럼에 애플리케이션이 항상 UTC 값만 넣는 규약 + 커넥션·세션 타임존 UTC 고정이다. 문제는 이 규약을 스키마가 강제해 주지 않는다는 것 — 누군가 KST 값을 한 번 넣어도 DB는 막지 않는다.

결론: 잠금 세 겹(9절) 중 스키마 층이 약해지므로 타입 층(Instant)과 설정 층에 더 의존하게 된다. 그래서 MySQL 환경에서는 "모든 시점 필드는 Instant로 선언한다"는 규칙과 커넥션 타임존 고정이 선택이 아니라 필수가 된다. 어떤 DB를 쓰든 "시점은 단일 기준으로 정규화, 날짜는 DATE"라는 원칙 자체는 그대로다.

표시는 클라이언트 책임이라면, 서버가 사용자 타임존을 알아야 하는 경우는 없나요? 시니어 변별힌트: "클라이언트가 없는 순간"에 서버가 무엇을 하는지 생각한다

있다. 그리고 그 경계를 아는 것이 "표시는 클라이언트" 원칙을 제대로 이해했다는 증거다. 원칙이 적용되는 전제는 "화면을 그리는 클라이언트가 그 순간 존재한다"는 것인데, 그 전제가 깨지는 자리가 있다.

서버가 사용자 타임존을 알아야 하는 자리
① 푸시·이메일 발송("현지 오전 9시에 보내기" — 발송 시점에 클라이언트는 꺼져 있다) ② 서버 렌더링 메일 본문·PDF ③ 사용자별 일별 리포트(어느 자정으로 자를지) ④ 배치 기반 알림(마감 하루 전 알림).
그때 무엇을 저장하나
오프셋이 아니라 타임존 ID를 사용자 프로필에 저장한다(Asia/Seoul). 오프셋으로 저장하면 서머타임 지역 사용자에게 계절마다 한 시간씩 틀린 시각에 발송된다 — 1절의 구분이 그대로 사고로 나타나는 자리다.

정리하면 분업은 세 갈래다 — 화면 표시는 클라이언트, 집계 경계는 서버 정책, 클라이언트가 없는 순간의 시각 계산은 사용자 프로필의 타임존 ID. 그리고 이 세 번째 때문에 "타임존은 사용자 설정 항목"이 필요해지는 서비스가 생긴다(22장 글로벌·i18n).

이미 date-only로 나가던 필드를 시점으로 바꿔야 한다면 어떻게 하나요?힌트: 타입이 바뀌는 변경은 값이 바뀌는 변경과 다르다

같은 필드명의 타입을 바꾸는 것은 파괴적 변경이다. "2026-08-31"을 받던 클라이언트가 "2026-08-31T14:59:59Z"를 받으면, 운이 좋으면 파싱 예외가 나고 운이 나쁘면 조용히 잘못 표시된다. 후자가 더 나쁘다.

그래서 필드를 바꾸지 말고 추가한다. 7-2절의 쿠폰 만료가 전형적인 사례다.

{
  "expiryDate": "2026-08-31",               // 기존 필드 — 당분간 유지 (deprecated 표시)
  "expiresAt":  "2026-08-31T14:59:59Z"     // 새 필드 — 경계 결정이 반영된 시점
}

순서는 ① 새 필드 추가 · 문서에 기존 필드 deprecated 표기 → ② 소비자 마이그레이션 확인 → ③ 다음 메이저 버전에서 제거다. 여기서 네이밍 규칙(...Date / ...At)이 값을 한다 — 이름이 다르므로 두 필드가 공존해도 혼동되지 않고, 클라이언트 개발자가 문서를 찾지 않고도 새 필드의 성격을 안다. (절차 상세: 08-backward-compatible-api-changes.md)

한 줄 요약
날짜/시간 규약의 요체는 포맷 암기가 아니라 두 가지 분리다 — 시점은 오프셋이 값 안에 박힌 ISO 8601(UTC 기본, 애플리케이션은 Instant, DB는 timestamptz)로, 달력상 날짜는 date-only(LocalDate, date)로 구분하고, 값의 기준(UTC 저장·전송)과 표현(클라이언트 변환)의 책임을 나눈 뒤, 이를 팀 문서와 타입·직렬화 기본값으로 강제하는 것 — 여기에 오프셋(숫자 하나)과 타임존 ID(규칙 묶음)의 차이를 얹으면 미래의 벽시계 약속만은 타임존 ID로 저장해야 한다는 예외까지 설명되고, 이 계약이 없으면 같은 문자열을 클라이언트마다 다르게 해석하는 버그가 해외 사용자와 자정 경계에서만 조용히 터진다.
