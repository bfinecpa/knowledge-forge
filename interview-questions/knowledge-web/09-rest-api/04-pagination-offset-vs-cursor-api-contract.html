페이지네이션 API 설계 — offset vs 커서
쿼리 기법이 아니라, 클라이언트와 맺는 계약이 다르다

면접 질문: "페이지네이션 API를 설계할 때 offset 기반과 커서 기반의 차이는?"

핵심 관전 포인트 — offset 기반은 "몇 번째부터 몇 건"(page/size)을, 커서 기반은 "이 항목 다음부터 몇 건"(cursor/size)을 계약으로 삼는다. 두 방식의 모든 차이는 하나에서 갈라져 나온다 — offset은 위치를 순번으로 가리키고, 커서는 값으로 가리킨다. 순번으로 가리키면 순번을 세어 봐야 하고(OFFSET 100000을 만난 DB는 앞의 10만 건을 건너뛰는 게 아니라 실제로 읽어 세고 버린 뒤 21번째부터 준다 — 비용이 깊이에 비례하는 이유), 앞쪽이 흔들리면 순번도 같이 흔들린다(글 하나가 추가되면 모든 행이 한 칸씩 밀려 페이지 경계에서 중복이, 삭제되면 누락이 난다). 값으로 가리키면 앞에서 무슨 일이 있든 "그 값보다 뒤"라는 조건이 가리키는 행 집합은 변하지 않고, 시작점을 인덱스 탐색 한 번으로 찾으므로 깊이와 무관하게 상수 비용이다. 대신 값에는 순번이 없으니 임의 페이지 점프와 total count를 포기한다. 커서 SQL의 실제 모양은 WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT 21이고, 여기서 id는 tie-breaker(동점 처리 키) — 없으면 데이터가 하나도 안 바뀌어도 경계에서 중복·누락이 난다 — 이며 21은 다음 페이지 존재 여부를 알기 위해 한 건 더 읽는 것이다. 이 값들을 불투명(opaque) 토큰으로 감싸는 이유는 "클라이언트가 해석할 수 있는 것은 전부 계약이 되기 때문"이고, Base64는 암호화가 아니라 인코딩이라 누구나 열어볼 수 있으므로 불투명은 기술적 은폐가 아니라 약속이다 — 위조 방지는 별개 문제라 서명이 따로 필요하다.
  • 1
    차이는 SQL이 아니라 계약이다 — offset은 "몇 번째부터"(page/size), 커서는 "이 항목 다음부터"(cursor/size)를 약속한다. 뿌리는 한 줄 — offset은 위치를 순번으로, 커서는 값으로 가리킨다. 나머지 차이는 전부 여기서 파생된다.
  • 2
    순번은 세어야 하고, 흔들린다 — OFFSET 100000은 앞의 10만 건을 읽고 버리므로 20건을 주려고 100,020건을 읽고(5,001배), 목록 앞쪽에 글이 하나 끼면 순번이 밀려 중복, 지워지면 누락이 난다. 커서는 값 비교라 인덱스 탐색 한 번으로 시작점에 착지하고(상수 비용), 앞쪽 변동에 흔들리지 않는다 — 대신 점프와 total count를 포기한다.
  • 3
    그래서 선택 기준은 성능이 아니라 UI다 — 페이지 번호 게시판·관리자 그리드는 offset + 깊이 상한, 무한 스크롤·피드는 커서. 커서를 고르면 토큰은 정렬 키 + tie-breaker를 담은 불투명 문자열로 설계해 내부 구조를 계약에서 빼고, 불투명은 은폐가 아니라 약속이므로 위조 방지는 HMAC 서명으로 따로 건다.

0. 질문 + 출제 의도

질문: "페이지네이션 API를 설계할 때 offset 기반과 커서 기반의 차이는?"

출제 의도: 성능(깊은 페이지네이션)에 더해, 실시간으로 데이터가 추가되는 목록에서 offset이 중복/누락을 만드는 정확성 문제까지 아는지 본다 — 피드형 서비스의 필수 지식. 쿼리 최적화가 아니라 "어떤 UI에 어떤 계약을 줄 것인가"라는 API 설계 결정을 할 수 있는지가 관전 포인트다.

이 페이지가 겨냥하는 약점 세 가지 ① "offset은 느리다"를 결론만 외운 상태 → 3절에서 Limit 노드가 세고 버리는 구조를 그림으로 열고, "20건을 주려고 100,020건"이라는 산술로 답한다. 메커니즘을 모르면 커서가 왜 빠른지도 설명할 수 없다.
② 성능만 말하고 정확성을 못 짚는 것 → 10절에서 삽입·삭제 타임라인으로 중복과 누락이 만들어지는 순간을 보여준다. 피드에서는 이게 성능보다 먼저 사용자 눈에 띈다.
③ 커서를 SQL 기법으로만 이해하는 것 → 7·8절에서 토큰이 곧 API 계약이라는 층으로 올라간다. "불투명하게 만든다"까지 말한 뒤 "그런데 Base64는 아무것도 감추지 못한다"를 스스로 덧붙일 수 있는지가 변별점이다.

범위 정리: offset이 DB에서 왜 느린지(read-and-discard, 힙 페치, 실행 계획 증명)는 04-rdb-sql/13-deep-pagination-offset-vs-cursor.md가 깊이 다룬다. 이 페이지는 API 계약 관점 — 요청/응답 스키마, 커서 토큰 설계, 클라이언트와의 약속 — 에 집중하고, 3절은 계약 설명에 필요한 만큼만 메커니즘을 연다.

1. 전제 — "어디부터"를 가리키는 방법은 논리적으로 둘뿐이다

페이지네이션이 하는 일은 하나다. 12,345건짜리 목록에서 지금 필요한 20건만 잘라 오는 것. 그러려면 "어디부터"를 표현해야 하는데, 표현하는 방법이 논리적으로 두 가지뿐이다. 순번으로 가리키거나, 값으로 가리키거나.

이 문서의 뿌리 한 줄 — 나머지는 전부 여기서 파생된다

offset은 위치를 순번으로 가리키고, 커서는 위치를 값으로 가리킨다
순번으로 가리키면
① 그 순번까지 세어 봐야 한다 → 비용이 깊이에 비례
② 앞쪽이 흔들리면 순번이 가리키는 대상도 같이 흔들린다 → 중복·누락
③ 대신 "몇 번째"라는 정보가 있으니 점프와 총 건수를 줄 수 있다
값으로 가리키면
① 세지 않고 인덱스로 바로 찾는다 → 비용이 상수
② 앞에서 무슨 일이 있어도 그 값은 그 값 → 안정
③ 대신 값에는 "몇 번째"가 없으니 점프도 총 건수도 못 준다

그러니까 이 질문은 성능 비교 문제가 아니라 "우리 UI에 순번이 필요한가"라는 설계 질문이다. 답변을 이 문장으로 열면 그다음 설명이 전부 여기에 매달린다.

비유 — 책갈피 vs 쪽수 친구에게 읽던 자리를 알려주는 방법은 두 가지다. "153쪽부터 읽어"(순번)와 "내가 책갈피 끼워 둔 그 문장 다음부터 읽어"(값). 평소엔 둘 다 된다. 그런데 누군가 앞쪽에 종이 한 장을 끼워 넣으면 153쪽이 가리키던 내용은 달라지고, 책갈피는 여전히 그 문장에 붙어 있다. 게다가 153쪽을 찾으려면 쪽을 세며 넘겨야 하지만 책갈피는 그냥 펼치면 된다. offset과 커서의 차이가 정확히 이것이다.

2. offset 기반의 계약 — "몇 번째부터"

계약이 다르다는 말을 추상적으로 두지 말고, 실제로 오가는 요청과 응답부터 보자. 두 방식은 파라미터 이름부터, 응답 필드 구성까지 다르다.

요청offset 기반
GET /posts?page=3&size=20
응답순번이 계약에 드러난다
{
  "content": [ { /* 20건 */ } ],
  "page": 3,
  "size": 20,
  "totalElements": 12345,
  "totalPages": 618
}

클라이언트에 주는 것: 전체 건수, 전체 페이지 수, 임의 페이지 점프(1페이지에서 500페이지로 바로). 페이지 번호가 붙은 게시판·관리자 그리드 UI가 요구하는 것들이다. 대신 서버는 매 요청 count 쿼리 비용과 깊은 페이지의 선형 비용을 지불하고, 10절의 정확성 문제를 안는다.

왜 618인가 — 숫자 하나가 count 쿼리를 부른다 totalPages는 totalElements를 size로 나눠 올림한 값이다. 12,345 ÷ 20 = 617.25이므로 마지막 5건을 담을 페이지가 하나 더 필요해 618이 된다. 이 숫자가 응답에 있으려면 서버가 매 요청 전체 건수를 세야 하고, 그 비용의 정체가 12절 두 번째 꼬리질문의 주제다. 응답 필드 하나가 쿼리 하나를 강제한다는 것 — 계약 설계에서 늘 따라오는 종류의 대가다.

3. offset의 비용은 왜 깊이에 비례하나 — 건너뛰기가 아니라 읽고 버리기다

"offset이 크면 느리다"는 결론만 외우면 커서가 왜 빠른지도 설명할 수 없다. 메커니즘 한 겹만 들어가자. 이 절은 계약 이야기가 아니지만, 계약을 고르는 근거가 여기서 나온다.

핵심은 이 한 줄 — B-tree 인덱스에는 "앞에서 10만 번째"로 가는 길이 없다

인덱스는 "값이 X인 곳"으로 가는 데는 트리 높이만큼(로그 시간)이면 된다. 그런데 각 노드가 자기 아래에 행이 몇 건 있는지를 세어 두지 않기 때문에 순번으로는 찾아갈 수 없다. 책 뒤의 색인이 "단어 → 쪽수"는 알려줘도 "앞에서 10만 번째 단어"는 못 알려주는 것과 같다.

그러니 10만 번째로 가려면 처음부터 세며 걷는 수밖에 없다. OFFSET이 "건너뛴다"는 말로 자주 번역되는 게 오해의 출발점이다 — DB는 건너뛰지 않는다. 읽고 버린다.

세는 주체가 누구인지가 그다음 포인트다. PostgreSQL의 실행계획은 위 노드가 아래 노드에게 "다음 행 하나 줘"라고 당기는 구조이고, OFFSET과 LIMIT은 맨 위의 Limit 노드가 처리한다. 아래 스캔 노드는 그 행이 결국 버려질 행인지 알 방법이 없으므로 행을 온전히 만들어서 위로 올린다.

면접에서 값이 나가는 한 문장 "OFFSET은 건너뛰는 게 아니라 읽고 버리는 겁니다." 여기에 "버릴 행인지 판정하려고 힙까지 읽어야 해서, 버리는 것조차 공짜가 아닙니다"를 얹으면 한 칸 더 간다. 그리고 이 문장이 곧바로 다음 문장을 부른다 — "커서는 이 세기를 아예 없앱니다."

4. 커서 기반의 계약 — "이 항목 다음부터"

요청커서 기반
# 첫 페이지 — 커서 없음
GET /posts?size=20

# 다음 페이지 — 받은 토큰을 그대로
GET /posts?size=20&cursor=eyJjcmVhdGVkQXQi...
응답순번이 계약에서 사라진다
{
  "items": [ { /* 20건 */ } ],
  "nextCursor": "eyJjcmVhdGVkQXQiOiIyMDI2...",
  "hasNext": true
}

클라이언트에 주는 것: 깊이와 무관한 일정한 응답 속도, 스크롤 중 삽입·삭제에도 흔들리지 않는 목록. 계약은 놀랍도록 단순하다.

"응답의 nextCursor를 다음 요청에 그대로 넣어라. hasNext가 false면 끝이다."

대신 totalElements도, "37페이지로 점프"도 없다.

4-1. 서버 쪽 SQL — 키셋 페이지네이션(keyset pagination)

이 계약을 받은 서버가 실제로 실행하는 쿼리가 아래다. 키셋이라는 이름은 위치를 순번이 아니라 정렬 키의 값(key set)으로 지정한다는 뜻이다.

-- 커서가 담고 있던 값을 그대로 조건에 꽂는다
SELECT id, title, created_at
  FROM posts
 WHERE (created_at, id) < ($1, $2)        -- ① 행 비교 / $1,$2 = 직전 페이지 마지막 행의 값
 ORDER BY created_at DESC, id DESC       -- ② tie-breaker 포함 전순서
 LIMIT 21;                                -- ③ 요청받은 20건 + 1건

커서 SQL 3요소 — 비 · 동 · 한

비 — 행 비교
(created_at, id) < ($1, $2)
두 컬럼을 사전순 한 덩어리로 비교. AND로 쪼개면 틀린다.
동 — 동점 처리 키
tie-breaker(보통 PK)를 정렬과 조건 양쪽에 넣어 전순서를 확정. 없으면 5절의 사고.
한 — 한 건 더
LIMIT size + 1로 hasNext를 count 없이 판정. 추가 비용은 인덱스 엔트리 하나.

① 행 비교(row comparison) — AND로 쪼개면 틀린다

두 컬럼을 각각 비교하는 것이 아니라 사전순으로 한 덩어리를 비교한다. 풀어 쓰면 created_at < $1 OR (created_at = $1 AND id < $2)다. 사전에서 "apple"과 "apply"를 비교할 때 앞 글자부터 보다가 같으면 다음 글자로 넘어가는 것과 같은 규칙이다.

Before흔한 실수 — 두 조건의 교집합이 된다
 WHERE created_at < $1 AND id < $2

-- created_at 은 더 과거인데 id 는 커서보다 큰 행이
-- 통째로 사라진다. 정렬 축이 두 개일 때 AND 는
-- 사전순 비교가 아니라 교집합이다.
After행 비교 — 사전순 한 덩어리
 WHERE (created_at, id) < ($1, $2)

-- 동치: created_at < $1
--    OR (created_at = $1 AND id < $2)
-- B-tree 범위 탐색으로 그대로 변환된다.

② PostgreSQL이 이 형태를 어떻게 실행하는가 — "비용이 상수"의 정체

행 비교는 (created_at, id) 복합 인덱스의 B-tree 범위 탐색으로 바로 변환된다. 즉 인덱스 트리를 뿌리에서 리프까지 한 번 내려가 시작 지점을 찍고, 거기서부터 리프를 21개만 순서대로 읽고 멈춘다. 1페이지든 5,001페이지든 하는 일이 똑같다.

필요한 인덱스 — 정렬 키와 tie-breaker를 순서대로 묶은 복합 인덱스 하나

CREATE INDEX idx_posts_created_id ON posts (created_at DESC, id DESC);

-- (created_at, id) 로 만들어도 된다. B-tree 는 양방향으로 읽을 수 있어서,
-- 두 컬럼의 방향이 "함께" 뒤집히는 ORDER BY created_at DESC, id DESC 는
-- 같은 인덱스를 역방향으로 훑어 처리할 수 있다.
-- 단 방향이 엇갈리면(created_at DESC, id ASC) 그 조합에 맞는 인덱스가 따로 필요하다.

③ LIMIT 21 — 왜 20이 아니라 21인가

응답에 hasNext를 담으려면 "뒤에 더 있는가"를 알아야 하는데, 이걸 COUNT(*)로 알아내면 커서 방식의 이점이 통째로 날아간다(count는 조건에 맞는 행을 전부 훑는다). 그래서 요청받은 것보다 한 건 더 읽는다.

읽어온 행 수로 hasNext를 판정한다 — 추가 비용은 인덱스 엔트리 하나를 더 읽는 것뿐이다.
읽어온 행 수hasNext응답에 담는 것
21건 (= size + 1)true앞의 20건만 — 21번째 행은 존재 확인용이므로 버린다
20건 (딱 떨어짐)false20건 전부 — 여기가 마지막 페이지다
7건false7건 전부 — 마지막 페이지
21번째 행을 응답에 흘리는 버그가 진짜 흔하다 LIMIT 21로 읽어 놓고 자르는 것을 잊으면 페이지 크기 계약(size=20)이 깨지고, 다음 페이지의 커서를 21번째 행에서 만들면 20번째 행이 통째로 누락된다. 순서를 규칙으로 못박아 두자 — ① 21건 읽기 → ② 21건이면 hasNext=true → ③ 앞 20건으로 자르기 → ④ 자른 결과의 마지막 행(20번째)으로 nextCursor 만들기.

5. tie-breaker — 정렬 키가 같은 행들의 순서를 확정하는 키

4절 SQL에서 id가 왜 붙어 있는지가 이 설계에서 가장 자주 빠뜨리는 부분이다.

tie-breaker는 정렬 키 값이 같은 행들 사이의 순서를 확정해 주는 보조 정렬 키다. 이름은 스포츠에서 왔다 — 동점(tie)인 두 팀의 순위를 가르는(break) 규칙이 tie-breaker다. 우리말로 옮기면 동점 처리 키쯤 된다. created_at이 같은 두 주문 사이의 순서를 id로 가른다는 뜻이다.

없으면 무슨 일이 생기는지가 중요하다. 데이터가 하나도 안 바뀌어도 페이지 경계에서 중복과 누락이 난다.

5-1. 커서에서는 이유가 하나 더 있다 — 커서가 행을 유일하게 지목해야 한다

위 예에서 1페이지 마지막이 R인데 커서에 created_at만 담아 WHERE created_at < '10:00:01'로 조회하면, 같은 시각의 Q가 통째로 건너뛰어진다. (created_at, id) < ('10:00:01', 503)이어야 Q가 정확히 포함된다.

tie-breaker의 조건 — 유일하고 불변인 값

유일해야 하는 이유
값이 겹치지 않아야 전순서(total order)가 완성된다. 하나라도 겹치면 그 지점에서 순서가 다시 미정이 된다.
불변이어야 하는 이유
나중에 바뀌면 그 값을 담아 둔 커서가 무효가 된다. 커서는 "과거에 본 값"을 들고 다니는 물건이다.
그래서 보통 PK를 쓴다 — 유일하고, 안 바뀌고, 이미 인덱스에 들어 있다

6. 두 계약을 나란히 놓으면

두 스키마를 나란히 놓으면 이 질문의 본질이 보인다 — 차이는 SQL이 아니라, 클라이언트에게 무엇을 약속하고 무엇을 약속하지 않는가다.

면접에서 값이 나가는 줄은 맨 아래 두 줄이다 — 위 다섯 줄은 사실 나열이고, 아래 두 줄이 "그래서 무엇을 고를 것인가"를 만든다.

비용페이지 깊이에 선형상수순번은 세어야 하고, 값은 인덱스로 찾는다 (3·4절)
어울리는 UI페이지 번호 게시판, 관리자 그리드무한 스크롤, 피드, "더 보기"UI가 순번을 요구하는가로 갈린다

암기 장치 — "점수를 주면 선중누를 문다"

점프(임의 페이지) + 총 수(total count)
offset이 무는 것 — 선 · 중 · 누

커서는 정확히 반대다 — 선중누를 안 물고, 점수를 못 준다. 이 대칭을 외워 두면 표를 통째로 복원할 수 있고, 면접에서 "둘 다 갖는 방법은 없나요?"라는 질문에도 "트레이드오프의 방향이 정해져 있어서, 둘 다 원하면 count를 따로 떼어내는 절충밖에 없습니다"로 바로 답할 수 있다.

7. 커서 토큰 설계 — 불투명해야 계약이 오래간다

7-1. 무엇을 담나 — 필수 2개 + 선택 2개

필수 — 이게 없으면 동작하지 않는다
① 정렬 키 값(createdAt) ② tie-breaker(id)
이 쌍이 서버에서 WHERE (created_at, id) < ($1, $2) 조건이 된다.
선택 — 이게 있으면 사고를 막는다
③ 정렬 기준 식별자(sort) — 8절의 일관성 검증용
④ 토큰 버전(v) — 구조를 바꿀 때 구버전 토큰을 식별
담지 말아야 할 것 디코드하면 다 보이므로 민감한 값은 애초에 넣지 않는다. 사용자 식별자, 내부 시스템 상태, 권한 정보 같은 것을 토큰에 실으면 "불투명하니까 괜찮다"가 성립하지 않는다. 이유는 바로 아래에서 본다.

7-2. 왜 불투명(opaque)이어야 하나 — 이름의 뜻부터

"불투명(opaque)"은 빛이 통과하지 않아 안이 안 보이는 물체를 가리키는 말이다. API에서는 "클라이언트가 안을 들여다볼 수 없는 값"이라는 뜻으로 쓴다. 반대는 투명한 값 — 클라이언트가 읽고 뜻을 이해할 수 있는 값이다. 왜 안이 안 보여야 하는지는 반례를 보면 즉시 이해된다.

7-3. 그런데 Base64는 아무것도 감추지 못한다 시니어 변별

여기서 반드시 짚어야 할 오해가 있다. Base64는 암호화가 아니라 인코딩이다. 암호화는 열쇠를 모르면 못 푸는 것이고, 인코딩은 바이트를 다른 문자 집합으로 옮겨 적는 것일 뿐이다. Base64를 쓰는 이유는 비밀 유지가 아니라, 임의의 바이트열을 URL에 안전하게 실을 수 있는 글자들로만 바꾸기 위해서다.

# 받은 커서
eyJjcmVhdGVkQXQiOiIyMDI2LTA4LTMwVDEyOjM0OjU2WiIsImlkIjoxMDIwMzR9

# 브라우저 콘솔에서 atob() 한 줄
atob("eyJjcmVhdGVkQXQiOiIyMDI2LTA4LTMwVDEyOjM0OjU2WiIsImlkIjoxMDIwMzR9")
// → {"createdAt":"2026-08-30T12:34:56Z","id":102034}   열쇠도, 도구 설치도 필요 없다

그러므로 "불투명하다"는 것은 기술적 은폐가 아니라 약속이다

"이 문자열의 내부 구조는 계약에 포함되지 않습니다. 열어 보고 그 결과에 의존하면 예고 없이 깨집니다."

약속만으로 충분한 것과 아닌 것을 반드시 구분해서 말해야 한다. 이 둘을 "불투명"이라는 한 단어로 뭉뚱그리면 바로 그 지점이 꼬리질문이 된다.

지키려는 것약속만으로 되나필요한 장치
토큰 구조를 나중에 바꿀 자유된다문서에 "해석 금지"를 명시 — 계약에 없는 것에 의존한 쪽 책임이다
내부 정보를 감추기안 된다디코드하면 다 보인다 → 애초에 민감한 값을 안 담는다
위조된 커서로 임의 조건 주입 막기안 된다값을 고쳐 다시 인코딩하면 그만이다 → HMAC 서명 (8절)
진화의 자유는 약속으로 지켜지지만, 위조 방지는 실제 장치가 있어야 한다

8. 서버는 토큰을 신뢰하지 않는다 — 검증과 방어

불투명하다고 해서 클라이언트가 위조하지 못하는 것은 아니다(바로 위에서 본 대로 Base64는 암호화가 아니다). 서버 측 방어 세 가지를 둔다 — 거 · 맞 · 서.

거
거절한다 — 파싱 실패·형식 위반은 400. 커서가 해석 불가능하면 조용히 첫 페이지를 주지 말고 명시적으로 거절한다. 조용한 폴백은 클라이언트 버그(토큰 유실)를 숨긴다 — 첫 페이지가 계속 돌아오면 클라이언트는 "목록이 짧구나"로 오해하고, 아무도 문제를 발견하지 못한 채 무한 스크롤이 같은 20건을 영원히 반복한다.
맞
맞춰 본다 — 정렬 파라미터와의 일관성 검증. sort=score로 만든 커서를 sort=createdAt 요청에 넣으면 조건과 정렬이 어긋나 엉뚱한 결과가 나온다 — WHERE (score, id) < (...) 조건을 걸어 놓고 ORDER BY created_at으로 정렬하는 꼴이기 때문이다. 토큰 안에 정렬 기준(또는 그 해시)을 함께 넣어 요청의 정렬과 다르면 400으로 거절한다.
서
서명한다 — HMAC 서명 또는 버전 필드. 가산점 토큰에 HMAC 서명을 붙이면 위조된 값으로 임의 조건을 주입하는 것을 차단할 수 있고, 버전 필드("v":1)를 넣어 두면 토큰 구조를 바꿀 때 구버전 토큰을 식별해 우아하게 만료시킬 수 있다("커서가 만료되었습니다. 목록을 새로고침하세요").
HMAC이 왜 위조를 막는가 — 한 줄만 보태면 답이 완성된다 HMAC은 서버만 아는 비밀 키로 내용에 대해 계산한 짧은 검증값이라, 클라이언트가 내용을 고치면 서명과 안 맞고, 비밀 키가 없으니 맞는 서명을 새로 만들 수도 없다. 중요한 것은 성격이다 — 서명은 내용을 감추지 않는다. 내용이 바뀌지 않았음을 증명할 뿐이다. 봉투를 봉인한 스티커와 같다: 안이 비쳐 보이든 말든, 뜯으면 티가 난다. 커서에 필요한 것도 딱 그것이다.
구현커서 토큰의 최소 구현 — 값 객체 + 불투명 직렬화
public record PostCursor(Instant createdAt, Long id) {

    public String encode() {
        String raw = createdAt + "|" + id;
        // URL 인코더를 쓰는 이유: 기본 Base64 의 '+' 와 '/' 는 쿼리 문자열에서
        // 다른 뜻으로 해석될 수 있어 '-' 와 '_' 로 바꿔 주는 변형이 필요하다.
        // 패딩('=') 도 URL 에서 지저분해지므로 뺀다.
        return Base64.getUrlEncoder().withoutPadding()
                     .encodeToString(raw.getBytes(UTF_8));
    }

    public static PostCursor decode(String token) {
        try {
            String[] parts = new String(Base64.getUrlDecoder().decode(token), UTF_8)
                                 .split("\\|");
            return new PostCursor(Instant.parse(parts[0]), Long.parseLong(parts[1]));
        } catch (Exception e) {
            // 첫 페이지로 조용히 폴백하지 않는다. 잘못된 커서는 클라이언트 버그이고,
            // 400 으로 돌려줘야 그쪽이 알아챌 수 있다.
            throw new InvalidCursorException(token);   // → @ControllerAdvice 에서 400
        }
    }
}

9. 응답 스키마의 디테일 — 여기서 갈린다

nextCursor는 서버가 만들어 내려준다
마지막 항목에서 클라이언트가 조립하게 하지 않는다 — 조립 규칙이 계약이 되는 걸 막는 것이 7절의 논리 그대로다. 다음 페이지가 없으면 nextCursor: null + hasNext: false.
hasNext 판정은 size + 1건 조회
21건을 읽어 21번째가 있으면 hasNext: true, 응답에는 20건만 담는다(4절의 LIMIT 21). count 쿼리가 필요 없다는 게 요점이다.
양방향이면 prevCursor도 함께
채팅 위로 스크롤 등. 서버는 부등호와 정렬 방향을 함께 뒤집어 조회한 뒤 결과 리스트를 다시 뒤집어 응답한다. 같은 인덱스를 역방향으로 읽을 뿐이라 인덱스 추가는 불필요.
size 상한은 서버가 강제한다
클라이언트가 보낸 값을 그대로 믿으면 size=100000이 들어온다. 최대치(예: 100)를 정하고, 초과 시 400인지 상한으로 자를지를 문서에 못박아 둔다. 0·음수는 400.

10. 정확성 — offset은 목록이 움직이면 창이 밀린다

출제 의도가 "성능에 더해"라고 짚은 지점이다. 피드형 서비스에서는 이게 성능보다 먼저 사용자 눈에 띈다.

원리는 1절에서 이미 나왔다. offset은 위치를 순번으로 가리키는데, 앞쪽에서 행이 추가되거나 삭제되면 뒤쪽 행들의 순번이 전부 이동한다. 1페이지를 요청한 시점과 2페이지를 요청한 시점 사이에 그 이동이 일어나면, "4번째부터"가 가리키는 대상이 내가 예상한 그 행이 아니게 된다.

중복과 누락은 무게가 다르다 — 이 한마디가 "운영해 본 사람"을 만든다

중복 — 시끄러운 버그
사용자가 보고 "같은 글이 두 번 나와요"라고 제보한다. 재현도 되고, 캡처도 온다.
누락 — 조용한 버그
아무도 모른 채 지나간다. 피드에서 특정 글이 특정 사용자에게만 안 보인 이유는 로그로도 못 찾는다. 제보 자체가 발생하지 않는다.
쓰기가 잦은 목록(피드·알림·댓글)에서 커서가 필수인 이유는 성능 이전에 이 정합성이다

11. 선택 기준은 성능이 아니라 UI다

"무조건 커서"가 아니라 UI 요구사항 → 계약 선택의 순서로 말해야 설계 답변이 된다. 하나의 서비스에 둘이 공존하는 게 보통이다.

커서를 고른다

  • 무한 스크롤 · 피드 · 타임라인 · "더 보기"
  • 사용자는 페이지 번호를 볼 일이 없고, 목록은 실시간으로 움직인다
  • 정렬 축이 고정돼 있다 (보통 최신순 하나)
  • 정렬 키가 변하지 않는 컬럼이다 (created_at ○ / updated_at ✗)

offset을 고른다 (+ 깊이 상한)

  • 페이지 번호 게시판, 관리자 그리드
  • 임의 점프 + total count가 요구사항에 명시돼 있다
  • 데이터 변동이 적어 중복·누락이 실질적 문제가 아니다
  • 정렬 축을 사용자가 바꾼다 (12절 마지막 질문)

offset을 골랐다면 반드시 붙이는 것 — 깊이 상한은 튜닝이 아니라 안전망이다

사람이 손으로 500페이지를 넘길 일은 거의 없다. 깊은 페이지 요청은 대부분 크롤러이거나 스크립트다. page가 상한을 넘으면 400으로 거절하는 인터셉터 한 장이면 사람이 기억하지 않아도 작동한다.

"성능 튜닝을 했다"가 아니라 "최악의 요청이 시스템을 흔들지 못하게 상한을 계약에 넣었다"로 설명하는 것이 정확하다. 상한을 넘는 조회가 정말 필요하면 그건 목록 API가 아니라 내보내기(export) 기능이라는 신호다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 면접 전날 이것만 — 질문을 먼저 읽고 답한 뒤 오른쪽을 본다

두 방식의 뿌리 한 줄?
offset은 순번으로, 커서는 값으로 위치를 가리킨다. 나머지 차이는 전부 파생.
OFFSET은 건너뛰나?
아니다 — 읽고 버린다. Limit 노드가 세고, 스캔 노드는 버릴 행도 온전히 만들어 올린다. 힙까지 읽어야 판정된다.
5,001페이지의 산술?
20건을 주려고 100,020건을 읽는다 = 5,001배. 실행계획에서 Limit 20 vs 스캔 100,020.
커서 SQL 3요소?
비·동·한 — 행 비교, 동점 처리 키, 한 건 더(LIMIT size+1).
행 비교를 AND로 쓰면?
틀린다. created_at < $1 AND id < $2는 교집합이라 "더 과거인데 id가 큰" 행이 통째로 사라진다.
tie-breaker가 없으면?
데이터가 하나도 안 바뀌어도 경계에서 중복·누락. 정렬 키가 같은 행들의 순서가 애초에 미정이라서.
tie-breaker의 조건?
유일 + 불변. 유일해야 전순서가 완성되고, 불변이어야 담아 둔 커서가 계속 유효하다 → PK.
왜 LIMIT 21인가?
hasNext를 count 없이 알려고. 21건이면 true + 앞 20건만 응답, 커서는 자른 뒤의 마지막 행으로 만든다.
"불투명"의 정확한 성격?
Base64는 암호화가 아니라 인코딩이라 누구나 atob()로 연다. 불투명은 은폐가 아니라 약속이고, 위조 방지는 HMAC 서명이 따로 필요하다.
서버 방어 3종?
거·맞·서 — 파싱 실패 거절(400), 정렬 기준 맞춤 검증, 서명(HMAC)+버전 필드.
count 요구의 절충 3종?
별·근·첫 — 별도 count 엔드포인트, 근사치("약 12,000건"), 첫 페이지에만 싣기.
트레이드오프 대칭?
"점수를 주면 선중누를 문다" — offset은 점프·총수를 주고 선형비용·중복·누락을 문다. 커서는 정확히 반대.
커서가 깨지는 전제?
커서의 안정성은 "정렬 키가 안 변한다"는 전제 위에 있다. updated_at 정렬에 커서를 쓰면 offset의 문제가 그대로 되살아난다.
중복과 누락의 무게?
중복은 제보가 온다. 누락은 아무도 모른 채 지나간다 — 로그로도 못 찾는다.
선택의 순서?
UI 요구사항 → 계약 선택. "무조건 커서"가 아니라 "우리 UI에 순번이 필요한가"가 먼저다.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

커서 토큰에는 무엇을 담고, 왜 불투명해야 하나요? 필수힌트: 담는 것 → 왜 tie-breaker가 필수인지 → 왜 불투명인지 → "그런데 Base64는" 순으로 쌓는다

정렬 키 + 유일한 tie-breaker(id)를 직렬화해 담는다. 여기에 선택적으로 정렬 기준 식별자와 토큰 버전을 더한다.

tie-breaker를 빠뜨리면 안 되는 이유부터 말하면 좋다 — 정렬 키 값이 같은 행들의 순서가 정의되지 않아, 데이터가 하나도 안 바뀌어도 페이지 경계에서 중복·누락이 난다. 게다가 커서 입장에서는 "마지막으로 본 행"을 유일하게 지목할 수 없다: created_at만 담으면 같은 시각의 행들이 통째로 건너뛰어진다.

불투명해야 하는 이유는 "클라이언트가 해석 가능한 것은 전부 계약이 되기 때문"이다. 값이 노출되면 클라이언트가 직접 조립해 호출하기 시작하고, 그 순간 정렬 키 변경·토큰 구조 변경이 파괴적 변경(breaking change)이 된다.

단, "불투명"의 성격을 정확히 말해야 한다. Base64는 암호화가 아니라 인코딩이라 누구나 열어볼 수 있으므로, 불투명은 기술적 은폐가 아니라 "이 안을 해석하지 마세요"라는 약속이다. 진화의 자유는 그 약속만으로 지켜지지만(계약에 없는 것에 의존한 쪽 책임), 위조 방지는 약속으로 안 되므로 HMAC 서명이 따로 필요하다.

담는 것 = 정렬 키 + tie-breaker (+ 정렬 기준, 버전) · 불투명 = 은폐가 아니라 약속 · 위조 방지 = 서명
기획이 "전체 12,345건" 표시와 무한 스크롤을 둘 다 원하면요? 필수힌트: "안 됩니다"가 아니다. 먼저 count의 비용이 무엇인지 설명하고, 절충안 세 개를 낸다

커서 응답에 total count가 없는 건 기술 한계가 아니라 비용 판단이므로, 먼저 그 비용이 무엇인지 설명할 수 있어야 한다.

PostgreSQL은 "이 테이블에 몇 행"이라는 숫자를 어디에도 확정해 두지 않는다. MVCC 때문에 같은 순간에도 트랜잭션마다 보이는 행 집합이 다르므로 단 하나의 정답이 존재하지 않는다. 그래서 COUNT(*)는 조건에 맞는 행을 매번 전부 훑어 세는 수밖에 없다.

인덱스를 태워도 완전히 해결되지 않는다. 인덱스 엔트리에는 그 행이 내 스냅샷에 보이는지가 없어서 원칙적으로 힙까지 확인해야 한다. PostgreSQL은 이걸 완화하려고 가시성 맵(visibility map) — 페이지 단위로 "이 페이지의 모든 행이 모두에게 보인다"를 표시해 둔 것 — 을 두고, 그 표시가 신선한 페이지에 한해 Index Only Scan이 힙을 건너뛴다(Heap Fetches: 0). 반대로 쓰기가 잦아 VACUUM이 따라가지 못하면 가시성 맵이 낡아 힙 페치가 붙는다. 어느 쪽이든 비용이 행 수 N에 비례한다는 성질은 그대로다.

이걸 설명한 뒤 절충안(별·근·첫)을 낸다.

별 — 별도 count 엔드포인트
목록과 분리 → 캐시 가능하고 목록 응답 속도와 독립
근 — 근사치 표기
"약 12,000건". 조건 없는 전체 건수면 pg_class.reltuples(VACUUM/ANALYZE가 갱신하는 추정치)가 상수 시간. 조건이 붙으면 카운터 테이블·주기적 집계.
첫 — 첫 페이지에만
첫 응답에만 count를 싣고 이후 페이지는 생략 — 스크롤 중 비용은 안 문다

핵심은 "정확한 실시간 count는 매 요청 전체 스캔 비용"임을 기획에 설명하고 요구사항의 진짜 의도(규모감 표시인지, 정확한 수치인지)를 확인해 계약을 정하는 것이다. "약 12,000개의 검색 결과"라고 쓰는 서비스가 많은 것은 게을러서가 아니라 이 계산을 이미 한 결과다.

그럼 커서 방식에는 total count를 "넣을 수 없는" 건가요? 함정힌트: 못 넣는 게 아니라 안 넣는 것이다. 두 결정은 직교한다

넣을 수 있다. 커서는 "어디부터 읽을지"를 정하는 방식이고 count는 별도 쿼리이므로, 두 결정은 직교한다. 커서 응답에 totalElements를 같이 실어도 문법적으로 아무 문제가 없다.

안 넣는 이유는 하나다 — 그 순간 "페이지가 깊어져도 비용이 상수"라는 커서의 유일한 성능 이점이 사라지기 때문이다. 목록 조회는 21건만 읽는데 count 쿼리가 N에 비례하는 스캔을 하면, 응답 시간을 지배하는 것은 count 쪽이 된다.

그래서 "커서 = count 없음"은 기술 규칙이 아니라 관례다. 이 구분을 말할 수 있으면 앞 질문의 절충안(첫 페이지에만 싣기)이 왜 성립하는지도 자연히 설명된다 — 무한 스크롤에서 count는 한 번만 필요하지 매 페이지 필요한 게 아니기 때문이다.

커서가 가리키던 행이 삭제되면 커서가 깨지나요? 함정힌트: 조건이 비교하는 대상이 "행"인지 "값"인지를 정확히 말한다

안 깨진다. 그대로 동작한다. 조건은 WHERE (created_at, id) < ($1, $2)이고, 여기서 $1, $2는 커서에 담겨 온 값이다. 그 값을 가진 행이 지금 존재하는지는 조건과 아무 상관이 없다.

이것이 커서 설계의 우아한 점이다 — 커서는 "행에 대한 참조"가 아니라 "정렬 축 위의 좌표"다. 좌표는 그 자리에 있던 물건이 치워져도 여전히 좌표다. (그래서 DB에 커서 상태를 저장할 필요도 없다 — 서버는 무상태로 남는다.)

진짜로 깨지는 경우는 따로 있다. 커서가 담은 값 자체가 변할 때다 — updated_at처럼 갱신되는 컬럼으로 정렬하면, 커서가 가리키는 좌표는 그대로인데 행들이 좌표축 위에서 움직여 중복·누락이 재발한다. 이 구분이 마지막 질문으로 이어진다.

잘못된 커서가 들어오면 그냥 첫 페이지를 주면 되지 않나요? 함정힌트: 그 폴백이 무한 스크롤에서 무엇을 만드는지 상상해 본다

안 된다. 400으로 명시적으로 거절한다. 조용한 폴백은 클라이언트 버그(토큰 유실·잘못된 인코딩)를 숨기기 때문이다.

구체적으로 무슨 일이 벌어지는지를 말하면 답이 선명해진다 — 클라이언트가 커서를 제대로 못 넘기는 버그가 있을 때, 서버가 매번 첫 페이지를 돌려주면 무한 스크롤이 같은 20건을 영원히 반복하거나, 목록이 "20건에서 끝난 것처럼" 보인다. 클라이언트 개발자는 "데이터가 원래 이만큼인가 보다"라고 오해하고, 서버 로그에는 정상 200만 남는다.

일반화하면: 입력이 계약을 위반했을 때 서버가 임의로 "선의의 해석"을 하면 오류가 관측 가능한 지점에서 사라진다. 잘못된 커서는 클라이언트 버그이고, 400은 그 버그를 그쪽에 돌려주는 유일한 통로다. 응답 본문에 INVALID_CURSOR 같은 식별 가능한 에러 코드를 함께 주면 더 좋다.

커서 방식에서 "이전 페이지"는 어떻게 지원하나요?힌트: 뒤집는 것이 두 개다. 그리고 인덱스가 하나 더 필요한지 아닌지까지 말한다

조건과 정렬을 반대로 뒤집어 조회한 뒤 결과 리스트를 다시 뒤집어 돌려주고, 응답에 prevCursor를 함께 내려준다.

-- 다음 페이지
 WHERE (created_at, id) < ($1, $2)  ORDER BY created_at DESC, id DESC  LIMIT 21

-- 이전 페이지: 부등호와 정렬 방향을 "함께" 뒤집고, 결과 리스트를 역순으로 뒤집어 응답
 WHERE (created_at, id) > ($1, $2)  ORDER BY created_at ASC,  id ASC   LIMIT 21

인덱스 추가는 필요 없다 — 같은 복합 인덱스를 반대 방향으로 읽을 뿐이기 때문이다(B-tree는 양방향으로 훑을 수 있다). 여기서 "부등호만 뒤집고 정렬은 그대로 두는 실수"가 흔한데, 그러면 이전 페이지가 아니라 목록의 맨 끝이 나온다.

한계는 그대로 남는다 — "이전"은 직전 페이지로의 이동이지 임의 점프가 아니다. 커서는 어느 방향으로든 한 칸씩만 움직인다.

무한 스크롤 화면에서 "새 글 3개" 같은 최신 방향 갱신은 어떻게 하나요?힌트: 앞 질문의 "뒤집기"를 그대로 쓴다. 그리고 이 count는 왜 싸도 되는지까지

이전 페이지와 같은 메커니즘이다. 화면 첫 번째 항목의 (created_at, id)를 기준으로 "그보다 앞선(최신) 행"을 조회한다 — WHERE (created_at, id) > ($1, $2) ORDER BY created_at ASC, id ASC. 즉 커서는 목록의 꼬리(nextCursor)뿐 아니라 머리(firstCursor)에서도 만들 수 있다.

"새 글 N개"의 N은 count 쿼리로 내도 괜찮다. 앞 질문에서 count를 피한 이유는 전체를 훑기 때문인데, 이 count는 "내가 마지막으로 본 지점보다 최신인 행"이라는 좁은 범위만 세므로 비용이 새로 생긴 행 수에 비례한다. 인덱스 범위 스캔 하나로 끝난다.

여기서 커서 설계의 성질 하나가 더 드러난다 — 커서는 목록의 절대 좌표계를 클라이언트에게 준 것이므로, "여기서부터 뒤로", "여기서부터 앞으로", "여기보다 새것이 몇 개" 같은 질문에 같은 조건식 하나로 전부 답할 수 있다. offset에는 이런 좌표가 없다.

hasNext 없이 nextCursor가 null인지만 보면 되지 않나요?힌트: 기능적으로는 맞다. 그래도 넣는 이유는 다른 층위에 있다

기능적으로는 그것만으로 충분하다. nextCursor: null이면 끝, 아니면 계속 — 정보량은 같다.

그럼에도 hasNext를 함께 두는 이유는 계약의 명료함이다. 클라이언트 코드에서 "null인지 검사"는 실수하기 쉽고(빈 문자열, "null" 문자열, 필드 누락 등 언어·직렬화기마다 다르게 나타난다), 불리언 필드는 의도를 문장으로 드러낸다. 무한 스크롤 컴포넌트의 조건문이 if (res.hasNext) loadMore()가 되는 것과 if (res.nextCursor != null)이 되는 것의 차이다.

둘 중 무엇을 고르든 규칙은 하나다 — 반드시 일관되게 채운다. hasNext: true인데 nextCursor: null인 응답이 나가면 클라이언트는 영원히 멈추지 않는 루프에 빠진다. 두 필드를 동시에 두기로 했다면 그 둘의 정합성이 곧 계약이다.

page/size 대신 offset/limit을 파라미터로 받으면 뭐가 달라지나요?힌트: 본질은 같다. 달라지는 건 "클라이언트가 무엇을 계산하게 되는가"다

본질은 같다 — 둘 다 순번 좌표이고, 3절의 읽고 버리기와 10절의 밀림을 똑같이 겪는다. offset = (page - 1) × size일 뿐이다.

계약으로서 달라지는 점은 두 가지다.

  • ① 임의 offset이 허용된다 — offset=37처럼 페이지 경계와 무관한 값이 들어올 수 있다. 무한 스크롤에 offset을 쓰는 흔한 형태가 이것인데, 클라이언트가 "지금까지 받은 개수"를 직접 누적해 보내는 구조라 화면 상태와 서버 요청이 어긋나기 더 쉽다. 상한 강제(offset 최대값)가 page 방식보다 더 중요해진다.
  • ② 0-based / 1-based 혼동이 사라진다 — page는 0부터인지 1부터인지가 계약에 반드시 명시돼야 하고(Spring Data는 page=0이 첫 페이지다), 이 혼동은 클라이언트가 한 페이지를 통째로 건너뛰거나 첫 페이지를 두 번 받는 사고로 나타난다. offset은 그 모호함이 없다.

정리하면 선택은 취향에 가깝지만, 어느 쪽이든 문서에 "첫 페이지는 무엇인가"와 "상한은 얼마인가"를 못박아야 한다는 결론은 같다.

운영 중인 offset API를 커서로 바꾸려면 어떻게 마이그레이션하나요?힌트: 하위 호환이 불가능한 변경이라는 진단이 먼저다. 그리고 "폐기는 계측 없이는 못 한다"까지

파라미터도 응답 구조도 바뀌므로 하위 호환이 불가능한 변경이다. page가 사라지고 cursor가 생기며, totalElements/totalPages도 사라진다 — 클라이언트의 페이지네이션 UI 자체를 다시 만들어야 하는 크기의 변경이다.

1
커서 기반 v2(또는 신규 파라미터 세트)를 병행 추가한다. 기존 API는 그대로 살려 둔다.
2
구 API에 깊이 상한을 걸어 피해를 차단한다 — 전환 기간에 크롤러가 5,000페이지를 긁는 것을 막는 게 먼저다.
3
전환 기간을 두고 사용량 메트릭으로 감시한다. 특히 강제 업데이트가 안 되는 모바일 구버전이 관건이다.
4
사용량이 0에 수렴하면 폐기 공지 후 제거한다.

이 절차 전체가 03-api-versioning-strategies.md의 폐기 타임라인과 같은 모양이라는 점을 짚으면 답이 커진다 — 계측 없이는 ④로 갈 수 없다는 것도 같다. "누가 아직 쓰고 있는지 모른다"면 폐기 결정은 영원히 내릴 수 없다.

이 질문의 진짜 무게: "처음부터 커서로 설계했으면 안 냈을 비용"이다 — 그래서 설계 시점의 선택을 묻는 것이다
정렬 키가 NULL일 수 있는 컬럼이면 커서를 어떻게 만드나요? 시니어 변별힌트: 비교 연산에 NULL이 들어가면 결과가 무엇이 되는지부터

그대로 쓰면 조용히 행이 사라진다. 행 비교 (sort_key, id) < ($1, $2)에서 어느 한쪽에 NULL이 끼면 비교 결과가 참도 거짓도 아닌 UNKNOWN이 되고, WHERE는 UNKNOWN인 행을 통과시키지 않는다 — 즉 NULL인 행들이 전부 누락된다.

정렬 위치도 헷갈린다. PostgreSQL의 기본값은 ASC일 때 NULLS LAST, DESC일 때 NULLS FIRST다. 즉 최신순(DESC) 목록에서 NULL인 행들이 맨 앞에 몰려 있고, 커서는 그 구간을 표현할 방법이 없다.

해법은 셋이고, 위에서부터 권한다.

  • ① 정렬 키를 NOT NULL로 만든다 — 가장 확실하다. created_at류는 대개 NOT NULL로 둘 수 있고, 둘 수 없다면 그 컬럼은 애초에 목록의 기본 정렬축으로 부적절하다는 신호다.
  • ② 대체값으로 정규화한다 — COALESCE(sort_key, '-infinity') 같은 식으로 NULL을 없앤 뒤 그 표현식과 동일한 표현식 인덱스를 만든다. 표현식이 인덱스와 정확히 일치해야 범위 탐색을 탄다는 점이 함정이다.
  • ③ NULL 구간을 커서에 표시한다 — 토큰에 "지금 NULL 구간인지" 플래그를 넣고 쿼리를 분기한다. 동작하지만 조건식이 복잡해져 버그가 잘 숨는다.

이 질문에서 변별되는 것은 "NULL 비교는 false가 아니라 UNKNOWN"이라는 SQL의 3값 논리를 실제 사고 경로로 연결할 수 있는가다.

정렬 기준을 사용자가 바꿀 수 있는 목록(관리자 그리드)에도 커서를 쓸 수 있나요? 시니어 변별힌트: "쓸 수는 있다"로 시작해, 정렬 축마다 무엇이 세 벌씩 필요한지 센다. 그리고 마지막에 전제 하나

쓸 수는 있지만 맞지 않는 경우가 많다. 정렬 축마다 ① 커서 구성 값 ② tie-breaker 포함 복합 인덱스 ③ 토큰 스키마가 따로 필요하다. 정렬 축이 다섯 개면 복합 인덱스도 다섯 벌이고, 인덱스는 조회를 빠르게 하는 만큼 쓰기를 느리게 하며 저장 공간도 먹는다.

그리고 결정적인 전제가 하나 있다 — 정렬 키는 불변 컬럼이어야 한다. updated_at 정렬에 커서를 쓰면 스크롤 중 갱신된 행이 위치를 옮겨 중복/누락이 재발한다. 커서가 "그 값보다 뒤"를 가리키는데 그 값 자체가 움직여 버리면, 10절에서 offset이 겪던 문제가 커서에서 그대로 되살아난다.

커서의 안정성은 "정렬 키가 안 변한다"는 전제 위에 있다 — 이걸 아는지가 이 질문의 변별 지점이다

결론은 요구사항별 비용 비교로 낸다. 정렬 축이 고정된 피드에는 커서가 정답이지만, 임의 컬럼 정렬 + 다중 필터 + total count까지 요구하는 관리자 그리드는 offset + 깊이 상한이 정직한 선택이고, 그마저 규모가 커지면 검색 엔진 위임(Elasticsearch의 search_after는 커서와 같은 발상이다)이 다음 단계다. "커서가 항상 우월하다"가 아니라 요구사항별 비용을 비교해 고르는 것이 설계 답변이다.

한 줄 요약
offset은 "몇 번째부터"라는 순번 좌표 계약이라 total count와 임의 점프를 주는 대신, DB가 앞의 행들을 실제로 읽고 버려야 해서 비용이 깊이에 비례하고(5,001페이지는 20건을 주려고 100,020건을 읽는다) 목록이 움직이면 순번이 밀려 중복·누락이 생긴다. 커서는 "이 항목 다음부터"라는 값 기반 계약이라 인덱스 탐색 한 번으로 시작점을 찾아 비용이 상수이고 앞쪽 변동에 흔들리지 않는 대신 점프와 count를 포기한다 — 커서 토큰은 정렬 키 + tie-breaker(동점 처리 키, 없으면 데이터가 안 바뀌어도 경계에서 중복·누락이 난다)를 담은 불투명 문자열로 설계해 내부 구조를 계약에서 빼고(불투명은 은폐가 아니라 약속이므로 위조 방지는 서명이 따로 필요하다), UI 요구사항(피드냐 페이지 번호 그리드냐)이 두 계약 중 무엇을 고를지 결정한다.
