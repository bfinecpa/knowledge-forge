API 게이트웨이 vs 서비스의 책임 경계
"도메인을 알아야 하는가"가 자르는 선

면접 질문: "API 게이트웨이에서 처리할 것과 각 서비스에서 처리할 것의 경계를 어떻게 나누나요?"

핵심 관전 포인트 — 경계 기준은 한 문장이다: "도메인 지식 없이, 모든 요청에 균일하게 적용되는가?" 그렇다면 게이트웨이(TLS 종료, 라우팅, 인증 토큰 검증, 전역 rate limit, 공통 로깅·트레이싱, CORS), 도메인 지식이 필요하면 서비스(리소스 소유권 기반 인가, 도메인 검증, 비즈니스 규칙). 대표 분할이 인증/인가다 — 게이트웨이는 "누구인가"(토큰 서명 검증)까지, "이 리소스에 이걸 해도 되는가"는 서비스가 한다. 그리고 이 경계를 지키지 못해 도메인 로직이 게이트웨이에 쌓이면, 모든 팀의 변경이 게이트웨이 배포에 줄을 서는 새로운 모놀리스가 된다 — MSA로 풀었던 결합을 게이트웨이에서 재조립하는 함정이다. 경계가 무너지는 것은 한 번의 큰 결정이 아니라 각각은 합리적이었던 작은 편의의 누적이라, 방어책도 "다이어그램을 잘 그리기"가 아니라 "게이트웨이에 넣자는 제안이 나올 때마다 적용하는 리뷰 기준을 팀이 공유하기"가 된다. 층은 셋으로 본다 — 게이트웨이는 도메인을 모른 채 얇게, BFF는 화면 요구에 맞춰 자주 바뀌게, 도메인은 서비스에.
  • 1
    기준은 한 문장이다 — "도메인 지식 없이, 모든 요청에 균일하게 적용되는가". 그렇다면 게이트웨이, 아니면 서비스다. 게이트웨이는 요청의 문법(HTTP 형식, 토큰 서명, 바이트 크기)만 보고, 서비스는 요청의 의미(이 주문이 누구 것인가, 이 상태 전이가 가능한가)를 본다.
  • 2
    대표 분할이 인증과 인가다 — 인증은 "요청에 딸려 온 증명서를 검사하는 일"이라 데이터가 필요 없고(게이트웨이), 인가는 "우리 DB의 상태와 대조하는 일"이라 데이터가 필요하다(서비스). 데이터가 있는 곳에 판정이 있어야 한다가 이 분할의 근거다.
  • 3
    경계가 무너지면 게이트웨이가 새로운 모놀리스가 된다 — 코드가 한 덩어리라는 뜻이 아니라 배포 단위가 한 덩어리로 되돌아왔다는 뜻이다. 그리고 그 붕괴는 각각은 합리적이었던 작은 결정 40개의 합으로 오므로, 방어도 큰 결정 한 번이 아니라 개별 결정마다 적용되는 리뷰 기준의 명문화여야 한다.

0. 질문 + 출제 의도

질문: "API 게이트웨이에서 처리할 것과 각 서비스에서 처리할 것의 경계를 어떻게 나누나요?"

출제 의도: 공통 관심사(인증, rate limit)의 위치 결정은 "게이트웨이가 비대해지면 그것이 새로운 모놀리스"라는 함정과의 균형이다. 시스템 전체의 책임 배치를 사고하는 아키텍처 감각을 잰다 — 기능 나열이 아니라, 배치 기준과 그 기준이 무너질 때의 조직적 비용까지 말할 수 있는지 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "게이트웨이가 하는 일"을 목록으로만 외운 상태 → 2절에서 각 항목이 왜 거기 있어도 되는지를 기준으로 되짚고, 4절에서 목록이 아니라 판정 절차를 만든다.
② 인증과 인가를 뭉뚱그려 "보안"이라 부르는 것 → 5절에서 "증명서 검사 vs DB 대조"로 갈라 놓고, 게이트웨이에 인가를 넣은 코드가 왜 성능이 아니라 조직 문제가 되는지 보여준다.
③ "게이트웨이를 얇게 유지한다"를 취향으로 말하는 것 → 8·9절에서 붕괴 타임라인과 배·폭·소(배포 병목·폭발 반경·소유권 실종)로 비용을 세고, 가용성 문제로 프레이밍해야 지켜진다는 데까지 간다.

1. 게이트웨이는 왜 있는가 — AOP를 네트워크 층으로 옮긴 것

경계를 나누려면 먼저 게이트웨이가 무엇을 위해 태어났는지를 알아야 한다. 존재 이유를 알면 "여기까지가 그 이유의 범위"라는 선도 같이 보인다.

1-1. 횡단 관심사 — 이미 알고 있는 개념이다

횡단 관심사(cross-cutting concern)는 특정 기능 하나에 속하지 않고, 모든 기능을 가로질러 똑같이 필요한 일이다. "횡단"은 기능들을 가로지른다는 뜻, "관심사"는 소프트웨어가 신경 써야 할 일이라는 뜻이다.

이 개념은 새로 배울 것이 아니다. Spring AOP가 정확히 이것을 위한 장치다. 로깅·트랜잭션·성능 측정은 주문에도 회원에도 결제에도 똑같이 필요한데, 메서드마다 손으로 넣으면 같은 코드가 수백 벌 복사되고 하나를 빠뜨려도 아무도 모른다.

Before 횡단 관심사를 손으로 넣으면
public Order createOrder(...) {
    tx.begin();                    // 모든 메서드에 똑같이
    log.info("createOrder start");  // 필요한 일
    try { /* 진짜 하려던 일 */ }
    finally { tx.commit(); log.info("end"); }
}
// 메서드 300개면 같은 코드가 300벌
// 한 곳을 빠뜨려도 아무도 모른다
After AOP로 한 곳에 한 번만 시공
@Transactional                     // 선언만 하면
public Order createOrder(...) {
    /* 진짜 하려던 일만 남는다 */
}
// 프레임워크가 모든 대상 메서드에
// 같은 처리를 끼워 넣는다
// → "전부에 적용됐는가"를 한 곳에서 보증
API 게이트웨이는 이 발상을 애플리케이션 안에서 네트워크 층으로 옮긴 것이다
AOP가 메서드 호출을 가로채 공통 처리를 하듯, 게이트웨이는 HTTP 요청을 가로채 공통 처리를 한다

1-2. 게이트웨이가 없으면 생기는 세 가지 비용

N개 서비스가 각자 TLS, 인증, rate limit, CORS, 접근 로그를 구현하는 상황을 생각해 보자.

① 중복 구현
같은 JWT 검증 코드가 N벌 존재한다. 공통 라이브러리로 뽑아도 버전이 갈리기 시작하면 사실상 N벌이다.
② 보안 구멍
N개 중 하나는 반드시 빠뜨린다. 새 서비스에 인증 필터를 안 걸고 배포하면 그 서비스만 뚫려 있는데 아무도 모른다. 본질은 "전부에 적용됐는지" 확인할 단일 지점이 없다는 것.
③ 변경 비용
"rate limit 한도를 조정하자"는 결정 하나에 N번 배포가 필요하다. 그러면 실무에서는 아무도 조정하지 않게 된다.

게이트웨이는 이 횡단 관심사를 트래픽이 반드시 지나는 단일 지점에서 한 번만 시공하려는 장치다. ②의 "단일 지점"이 특히 중요하다 — 게이트웨이의 진짜 값은 코드를 아끼는 것이 아니라 누락이 구조적으로 불가능해지는 것에 있다.

비유 — 건물의 정문 보안 게이트, 그리고 아파트 공동현관 출입증 검사(인증), 출입 기록(로깅), 혼잡 시 입장 제한(rate limit)은 정문에서 한다. 그러나 "이 방문자가 3층 회의실을 예약했는지"(도메인 인가)는 정문이 알 수 없고 알아서도 안 된다 — 그건 3층 부서(서비스)의 일이다. 정문 경비가 전 부서의 예약 현황을 실시간으로 알아야 한다면, 그건 정문이 회사 전체가 된 것이다.
더 짧게는 아파트다 — 공동현관 카드키가 인증(이 단지 주민인가), 세대 도어락이 인가(이 집에 들어갈 권한이 있는가). 공동현관이 각 세대의 도어락 비밀번호를 전부 들고 있으면, 편해지는 대신 그 문 하나가 뚫리면 단지 전체가 뚫린다.

2. 게이트웨이의 전형적 책임 8종 — 문·신·통·기

책임 목록을 외워서 나열하는 것과, 각각이 왜 게이트웨이에 있어도 되는지를 아는 것은 다르다. 면접에서 값이 나가는 것은 뒤쪽이다 — 후자를 말하면 4절의 기준이 자동으로 따라 나온다.

게이트웨이의 전형적 책임. 오른쪽 열이 전부 "도메인 지식이 필요 없다 + 모든 요청에 균일하다"의 변주라는 점을 확인하면서 읽는다.
책임무엇을 하는가왜 게이트웨이인가
TLS 종료HTTPS 암호를 여기서 풀고 내부로는 평문(또는 별도 mTLS)으로 보낸다인증서 관리와 암복호화 CPU 비용을 한 곳에 모은다
라우팅경로·호스트를 보고 어느 서비스로 보낼지 정한다클라이언트가 서비스 분할 구조를 몰라도 되게 만든다
인증 토큰 검증JWT 서명·만료 확인, 클레임 추출도메인 지식이 필요 없고 모든 요청에 균일하다
전역 rate limitIP당·클라이언트당 요청 수 상한서비스에 도달하기 전에 막아야 보호 효과가 있다
CORS와 프리플라이트브라우저의 교차 출처 요청 허용 여부를 헤더로 응답도메인 지식이 전혀 필요 없고 모든 요청에 규칙이 같다
접근 로그 · trace id요청마다 추적 ID를 만들어 하위로 전파, 공통 로그 기록모든 요청이 지나는 지점이라야 누락 없는 전수 기록이 된다
요청 크기 제한본문 최대 크기 초과 시 거절바이트만 세면 되고 내용을 해석할 필요가 없다
IP 차단 · 경계 보안알려진 공격 IP 차단, WAF 연동안쪽으로 들여보내기 전에 걸러야 의미가 있다

8종을 네 묶음으로 — 문 · 신 · 통 · 기

문 — 문 여닫기
TLS 종료 · 라우팅
요청을 받아 어디로 보낼지
신 — 신원
인증 토큰 검증 · CORS
누가 보냈고, 보내도 되는 출처인지
통 — 통제
전역 rate limit · 크기 제한 · IP 차단
얼마나 들여보낼지

지나간 흔적을 남긴다

네 묶음의 공통점을 한 문장으로: 전부 "요청 봉투"만 보고 처리할 수 있는 일이다. 봉투를 열어 내용을 읽어야 하는 순간부터는 게이트웨이의 일이 아니다.

용어 함정 — TLS "종료"는 연결을 끊는다는 뜻이 아니다 TLS 종료(TLS termination)에서 "종료"는 암호화 구간이 여기서 끝난다는 뜻이다. 클라이언트와 게이트웨이 사이는 HTTPS로 암호화되고, 게이트웨이가 그 암호를 풀어 평문 HTTP 요청을 얻은 뒤, 게이트웨이와 내부 서비스 사이는 평문으로(또는 내부용으로 다시 맺은 별개의 TLS로) 보낸다. 연결은 계속 살아 있고, 끝나는 것은 그 하나의 암호화 구간이다. 어느 계층에서 TLS를 종료할지의 트레이드오프는 08-network-http/17-tls-termination-lb-vs-app.md가 다룬다.

3. 층은 셋이다 — 게이트웨이 → BFF → 서비스

경계 논의가 어려워지는 이유는 대부분 층을 둘로만 보기 때문이다. "게이트웨이냐 서비스냐"로만 물으면 "화면용 응답 조합"처럼 어느 쪽에도 안 맞는 요구가 갈 곳이 없어져 게이트웨이로 흘러든다.

층을 셋으로 보면 각 요구가 갈 자리가 생긴다. 각 층이 무엇을 알아도 되고 무엇을 알면 안 되는지, 그리고 언제 바뀌는지를 함께 보는 것이 핵심이다.

이 그림을 면접에서 쓰는 방법 경계 질문을 받으면 목록을 나열하기 전에 층부터 세운다. "층을 셋으로 봅니다 — 게이트웨이는 도메인을 모른 채 얇게, BFF는 화면 요구에 맞춰 자주 바뀌게, 도메인 규칙은 서비스에." 이 한 문장이 있으면 뒤이어 나오는 모든 회색 지대 질문(조합은 어디서? 캐싱은 어디서?)에 갈 자리를 지정할 수 있다. 층이 둘뿐인 답에서는 애매한 요구가 전부 게이트웨이로 밀려간다.

4. 경계 기준 — 세 질문으로 자른다 (도 · 균 · 주)

어떤 처리를 어디에 둘지 애매할 때 이 순서로 묻는다. 순서가 중요하다 — 앞의 질문에서 결론이 나면 뒤는 안 봐도 된다.

경계 판정 3문 — 도 · 균 · 주

도
도메인 지식이 필요한가? 필요하면 무조건 서비스. 게이트웨이가 "주문", "쿠폰"의 의미를 알기 시작하는 순간 경계가 무너진다. 이 질문이 첫 번째인 이유 — 나머지 둘을 아무리 잘 통과해도 이것 하나가 걸리면 답이 뒤집힌다.
균
모든(대부분의) 요청에 균일하게 적용되는가? 균일하면 게이트웨이 후보. 특정 서비스에만 필요한 처리를 게이트웨이에 두면 그 서비스의 변경이 게이트웨이 배포를 요구하게 된다 — 3절 그림의 위층이 아래층의 주기로 끌려 내려온다.
주
바뀌는 주기와 주체가 누구인가? 서비스 팀의 기능 변경 때마다 함께 바뀌어야 하는 로직이면 서비스에 둔다. 변경의 주인과 코드의 위치를 일치시켜야 배포가 서로를 기다리지 않는다. 이 질문은 코드의 성질이 아니라 조직의 성질을 묻는 것이고, 그래서 앞의 둘로 애매한 회색 지대에서 결정적인 판정을 해 준다.

5. 대표 사례 — 인증(Authentication)과 인가(Authorization)의 분할

이 둘은 이름이 비슷해 자주 뭉뚱그려지는데, 세 질문에 대한 답이 정반대라 갈라지는 자리가 명확하다. 면접에서 경계를 묻는 질문에 가장 먼저 꺼낼 예시이기도 하다.

인증 = "누구인가" → 게이트웨이

  • JWT 서명 검증, 만료 확인, 사용자 ID·권한 클레임 추출
  • 판정에 필요한 것: 공개키와 서명 알고리즘뿐
  • 주문이 뭔지 쿠폰이 뭔지 몰라도 된다 → 도(道) 통과
  • 모든 요청에 균일 → 균 통과
  • 바뀌는 주체는 플랫폼·보안 → 주 통과
  • 검증 결과(사용자 ID 등)는 내부 헤더 또는 서명된 내부 토큰으로 서비스에 전달

인가 = "이 리소스에 이걸 해도 되는가" → 서비스

  • "이 주문은 이 사용자의 것인가", "이 문서의 편집 권한이 있는가"
  • 판정에 필요한 것: 주문 테이블의 owner_id
  • 그 데이터를 가진 쪽은 주문 서비스뿐 → 도(道)에서 즉시 탈락
  • 규칙이 바뀌는 주체는 도메인 팀·기획
  • 게이트웨이에 두면 게이트웨이가 도메인을 조회해야 한다

이 분할을 한 문장으로 외운다

인증은 "요청에 딸려 온 증명서를 검사하는 일"이라 데이터가 필요 없고,
인가는 "우리 DB의 상태와 대조하는 일"이라 데이터가 필요하다
→ 데이터가 있는 곳에 판정이 있어야 한다

5-1. 경계를 넘긴 코드는 무엇을 망가뜨리는가

Before 게이트웨이 라우트 필터에 도메인 인가
// gateway의 라우트 필터에서 —
if (path.matches("/orders/{id}")) {
    var order = orderServiceClient.getOrder(orderId);
    if (!order.ownerId().equals(userId)) {          
        return forbidden();                          
    }                                                 
}
// 문제 1: 게이트웨이가 주문 도메인을 조회·해석한다
// 문제 2: 인가 규칙이 바뀌면(예: '가족 계정도 조회 가능')
//         주문팀이 게이트웨이 배포를 기다린다
// 문제 3: 주문 조회가 2번 일어난다
After 게이트웨이는 신원까지, 인가는 서비스가
// [게이트웨이] JWT 검증 → 통과 시 내부로 신원 전달
//   X-User-Id: 42  (+ 위변조 방지 서명, 10절 Q1 참고)

// [주문 서비스] 도메인 데이터로 인가 판단
@GetMapping("/orders/{id}")
Order getOrder(@PathVariable long id,
               @RequestHeader("X-User-Id") long userId) {
    var order = orderRepository.findById(id);
    accessPolicy.checkReadable(order, userId);  // 소유권·
    return order;   // 가족계정 규칙은 주문팀 코드에,
}                   // 주문팀 배포 주기로

6. 회색 지대 넷 — 같은 이름, 반대 배치

기준을 외우는 것보다 기준을 애매한 사례에 적용해 보는 것이 실력이다. 자주 나오는 넷을 본다.

회색 지대 4종. 왼쪽과 오른쪽이 같은 이름을 쓴다는 점이 함정의 정체다 — 이름이 같다고 같은 자리에 두면 안 된다.
사례게이트웨이에 두는 경우서비스(또는 BFF)에 두는 경우가르는 근거
rate limitIP당·클라이언트당 전역 한도"포인트 전환은 사용자당 하루 3회"후자는 한도가 아니라 비즈니스 규칙이다. 같은 이름이라도 도메인 의미가 실리는 순간 넘어간다
응답 변환·조합헤더 추가 같은 무해한 수준여러 서비스 응답을 화면용으로 조합 → BFF조합에는 도메인 + 화면 지식이 둘 다 필요하다. 게이트웨이가 아니라 BFF로 분리한다
요청 검증JSON 문법이 맞는가, 크기 제한"배송지가 유효한 주소인가"전자는 바이트만 보면 되고, 후자는 주소 도메인을 알아야 한다
캐싱정적·공통 응답 캐시 (또는 그 앞 CDN)무효화 규칙이 도메인 이벤트에 묶인 캐시"주문이 취소되면 이 캐시를 비운다"는 규칙 자체가 도메인 지식이다

rate limit 행이 특히 좋은 훈련 재료다

두 항목은 이름이 같고, 구현 기술도 같고(카운터 + 시간 윈도우), 심지어 저장소도 같은 Redis일 수 있는데, 배치는 반대로 갈린다.

판단은 기술이 아니라 — "이 한도를 정한 사람이 보안팀인가 기획자인가"로 난다

보안팀이 정했으면 남용 방지이므로 전역·균일하고(게이트웨이), 기획자가 정했으면 제품 규칙이므로 도메인 상태(사용자 등급, 잔여 횟수, 이벤트 기간)에 묶인다(서비스). 같은 질문의 다른 형태 — "이 값이 바뀔 때 릴리즈 노트에 적히는가?" 적힌다면 제품 규칙이다.

한 줄 판정기 — 문법(syntax) vs 의미(semantics) 네 사례를 하나로 묶는 표현이 있다. 게이트웨이는 요청의 문법을 검사하고, 서비스는 요청의 의미를 검사한다. JSON 파싱이 되는가 · 크기가 얼마인가 · 서명이 유효한가는 문법이고, 이 주소가 배송 가능한가 · 이 사용자가 오늘 3회를 다 썼는가 · 이 주문이 취소 가능한 상태인가는 의미다. "봉투를 열지 않고 판정할 수 있는가"와 같은 말이다.

7. CORS 프리플라이트 — 기준에 정확히 들어맞는 예

CORS(Cross-Origin Resource Sharing, 교차 출처 자원 공유)는 브라우저가 지금 보고 있는 페이지의 출처(origin = 스킴 + 호스트 + 포트)와 다른 출처로 가는 요청의 응답을 기본적으로 못 읽게 막고, 서버가 응답 헤더로 "이 출처는 허용한다"고 명시적으로 동의해 줄 때만 풀어 주는 브라우저의 규칙이다. 집행자는 언제나 브라우저이므로 서버 간 호출이나 curl에는 아무 효력이 없다(상세는 08-network-http/08-cors-and-preflight.md).

여기서 이 문서와 이어지는 지점이 프리플라이트(preflight, 사전 확인)다. 브라우저는 PUT/DELETE, application/json 본문, 커스텀 헤더처럼 "예전 웹에는 없던 형태"의 교차 출처 요청을 보내기 전에, 먼저 OPTIONS 메서드로 "이런 메서드·헤더의 요청을 보내도 되나요?"를 물어본다. 서버가 허용 헤더로 답해야만 진짜 요청을 보낸다.

7-1. 세 질문으로 그대로 검사해 본다

① 도 — 도메인 지식?
필요 없다. 응답에 담을 것은 허용 출처 목록, 허용 메서드, 허용 헤더, 캐시 시간뿐. 주문이 뭔지 알 필요가 없다.
② 균 — 균일한가?
균일하다. /orders든 /coupons든 프리플라이트 응답 규칙이 같다.
③ 주 — 바뀌는 주체?
플랫폼·보안이다. 프론트 도메인이 추가될 때 바뀌고, 주문팀의 기능 변경과 무관하다.

세 질문을 모두 통과한다. 게다가 실무적 이득이 하나 더 있다.

덤 — OPTIONS는 가로채도 안전한 메서드다 가산점 OPTIONS는 HTTP 메서드 자체로도 safe(서버 상태를 바꾸지 않음)이면서 멱등(여러 번 보내도 결과가 같음)이라 게이트웨이가 대신 응답해도 부작용이 없다(01-restful-design-principles-resource-naming.md의 메서드 속성 표 참고). "가로채도 되는가"까지 메서드 속성으로 근거를 대면 한 칸 더 간다.

8. 함정 — 작은 편의 40개가 만드는 모놀리스

경계가 무너지는 것은 한 번의 큰 잘못된 결정이 아니다. 아무도 "게이트웨이에 도메인 로직을 넣자"고 결정하지 않는다. 무너짐은 각각은 합리적이었던 작은 결정들의 누적으로 온다.

9. 쌓이면 잃는 것 셋 + 방지 장치 셋

9-1. 세 가지 비용 — 배 · 폭 · 소

게이트웨이가 새로운 모놀리스가 될 때 잃는 것 — 배 · 폭 · 소

배 — 배포 병목
여러 팀의 변경이 단일 배포 파이프라인에 줄을 선다. 서비스는 하루 10번 배포하는데 게이트웨이는 조심스러워 주 1회가 되고, 게이트웨이에 로직을 둔 팀은 모두 그 주기에 묶인다.
폭 — 폭발 반경
게이트웨이는 전 트래픽의 단일 경로다. 특정 팀이 넣은 필터 하나의 버그가 전 서비스 장애가 된다. 서비스에 있었으면 그 도메인만 죽었을 문제다.
소 — 소유권 실종
게이트웨이 팀은 "그 도메인은 모른다", 도메인 팀은 "우리 저장소가 아니다". 결과는 아무도 테스트하지 않고 아무도 지우지 못하는 코드다.
"새로운 모놀리스"의 정확한 의미 — 코드가 한 덩어리라는 뜻이 아니라, 배포 단위가 한 덩어리로 되돌아왔다는 뜻이다

MSA로 분리했던 조직 결합이 게이트웨이에서 부활한다. 그리고 소가 배와 폭을 영구화한다 — 8절 타임라인의 6월 항목이 9월까지 살아남는 이유가 지울 소유자가 없기 때문이다.

9-2. 방지 장치 셋 가산점

1
"게이트웨이 변경은 설정이어야지 코드가 아니어야 한다"는 원칙. 라우트 추가, 한도 조정은 선언적 설정으로 하고, 도메인 조건문이 담긴 커스텀 필터가 PR에 등장하면 그것 자체를 경계 위반 신호로 리뷰에서 잡는다. 이 원칙의 값은 판정이 기계적이라는 데 있다 — 8절에서 본 것처럼 개별 결정의 합리성으로는 판단이 안 되므로, 형태로 거르는 규칙이 필요하다.
2
화면·클라이언트 맞춤 요구는 BFF로 배출한다. 조합·변환 요구를 게이트웨이가 아니라 클라이언트 팀이 소유하는 BFF 계층으로 보낸다. 3절의 3층 구조가 여기서 값을 한다 — 갈 곳이 있어야 배출이 된다. BFF가 없으면 "이 요구는 게이트웨이에 두면 안 된다"고 말해도 대안이 없어 결국 들어온다.
3
게이트웨이의 SLO와 변경 통계를 관리한다. 게이트웨이 배포 빈도가 올라가고 배포 사유가 특정 도메인 요구로 채워지면 경계가 새고 있다는 정량 신호다. "이번 분기 게이트웨이 배포 12건 중 9건이 특정 팀의 도메인 요구"라는 숫자는 리뷰에서 개별 PR을 막는 것보다 훨씬 강한 근거가 된다.
경계 위반 신호 도메인 조건문이 담긴 커스텀 필터
@Component
class LegacyCompatFilter implements GlobalFilter {
  public Mono<Void> filter(ServerWebExchange ex, GatewayFilterChain c) {
    if (grade.equals("VIP")) route("payment-v2");   // 도메인 개념
    if (path.startsWith("/orders")) renameField(...);  // 응답 해석
    if (partnerId == "P-77") return block();          // 사유 미상
    // ... 37줄 더
  }
}

리뷰에서 잡는 법: "이 조건문이 참조하는 것이 HTTP의 속성인가, 도메인의 속성인가?" 등급·주문·파트너는 전부 도메인의 속성이다.

허용 형태 선언적 설정 — 도메인 어휘가 등장하지 않는다
# 게이트웨이 라우트 정의 (형태는 제품마다 다르다)
routes:
  - id: order-service
    uri: lb://order-service       # 어디로 보낼지
    predicates: [ "Path=/orders/**" ]  # 경로 패턴만
    filters:
      - "RequestRateLimiter=200,400"   # 전역 한도
      - "RequestSize=1MB"              # 바이트만 센다
# 등급·주문상태·파트너 같은 도메인 어휘가 한 번도 안 나온다
# → 이것이 "게이트웨이가 얇다"의 관찰 가능한 정의

부수 효과: 설정이면 재배포 없이 반영할 수 있는 경로가 열리고, 변경 이력이 곧 감사 로그가 된다.

현실적인 균형 — "절대 안 된다"는 답은 오히려 약하다 장애 상황에서 게이트웨이에서 임시 차단하는 것이 정답인 순간은 실제로 있다. 서비스 배포에 이틀이 걸리는데 지금 어뷰징으로 서비스가 죽고 있다면, 가장 빨리 배포되는 곳에서 막는 것이 옳다. 8절 6월 항목이 함정인 이유는 임시 조치를 한 것이 아니라 임시가 영구가 된 것이다.
그래서 실무 답은 이렇게 말한다 — "긴급 조치는 게이트웨이에서 하되, 만료일과 소유자를 코드에 함께 남기고 제거 티켓을 같은 PR에서 만든다." "넣지 말자"보다 "넣되 반드시 나가게 하자"가 지켜지는 규칙이다.

10. 인출 카드 · 꼬리질문 셀프 테스트

면접 전날 이것만 — 인출 카드

경계 기준 (도·균·주)
① 도메인 지식이 필요한가 → 필요하면 무조건 서비스
② 모든 요청에 균일한가 → 아니면 그 서비스에
③ 바뀌는 주체가 도메인·화면 팀인가 → 맞으면 서비스/BFF
게이트웨이 책임 (문·신·통·기)
문 TLS 종료·라우팅 / 신 토큰 검증·CORS / 통 전역 rate limit·크기 제한·IP 차단 / 기 접근 로그·trace id

md의 꼬리질문 — 먼저 스스로 답해 보고 펼친다

게이트웨이가 인증했다는 걸 서비스는 어떻게 신뢰하나요? 내부에서 X-User-Id 헤더를 위조하면요? 함정힌트: "내부망이니까 믿는다"는 답은 감점이다. 공격자 시점 한 줄로 보여준 뒤 세 층으로 답한다

왜 위험한지를 공격자 시점으로 보면 즉시 이해된다.

# 공격자가 사내망의 아무 컨테이너(또는 침해된 다른 서비스)에서 이 한 줄을 실행하면
curl -H "X-User-Id: 1" http://order-service.internal:8080/orders/8471
#      ^^^^^^^^^^^^^^^^^^^ 게이트웨이가 붙여주기로 한 헤더를 직접 붙였을 뿐이다

# 주문 서비스는 "게이트웨이가 인증을 마친 사용자 1번의 요청"이라고 믿고 응답한다.
# 공격자는 로그인할 필요도, 토큰을 훔칠 필요도 없었다 —
# 인증을 통과한 것이 아니라 인증의 '결과'를 자칭했기 때문이다.
X-User-Id는 신원의 증명이 아니라 신원의 주장이다
증명(서명된 토큰)은 게이트웨이에서 소비되고 사라졌고, 서비스에는 주장만 도착한다

실무 답은 세 층이고, 보통 겹쳐서 쓴다.

1
서명된 내부 토큰으로 재발급한다. 게이트웨이가 외부 토큰을 검증한 뒤, 그 결과를 짧은 만료의 내부용 JWT로 새로 서명해 전달한다. 서비스는 게이트웨이의 공개키로 서명을 확인하므로 개인키 없이는 위조할 수 없다. 위 curl은 서명이 없어 즉시 거부된다.
2
네트워크 수준에서 호출자를 확인한다. 서비스가 게이트웨이 외의 직접 호출을 받지 않도록 격리하고, 서비스 간에는 mTLS를 쓴다. mTLS는 상호 TLS(mutual TLS)로, 평소 HTTPS가 서버만 인증서를 제시하는 것과 달리 클라이언트도 인증서를 제시해 서로를 확인한다. 그래서 "이 호출이 정말 게이트웨이에서 온 것인가"를 애플리케이션 코드가 아니라 네트워크 계층에서 보장할 수 있다. 서비스 메시(Istio 등)를 쓰면 애플리케이션 수정 없이 이 층을 깐다.
3
원본 토큰을 그대로 전파한다. 게이트웨이가 검증한 원본 토큰을 하위로도 넘겨 필요한 서비스가 재검증한다. 가장 단순하지만 검증이 N번 반복되고, 토큰 수명·스코프 관리가 복잡해진다.

이 세 대응을 관통하는 태도가 zero trust다. 이름 그대로 신뢰를 0으로 둔다는 뜻으로, "내부망이니까 믿는다"는 전제 자체를 버리고 모든 호출을 그때마다 검증하는 원칙이다. 방화벽 안쪽을 안전지대로 보던 과거 모델이 내부의 컨테이너 하나만 뚫려도 전부 무너진다는 경험으로 폐기된 결과다. "경계 안이라고 무조건 신뢰하지 않는다"는 태도를 보여주는 것이 이 질문의 포인트다.

그럼 인가를 위한 공통 권한 체크가 서비스마다 중복 구현되지 않나요? 시니어 변별힌트: 중복을 두 종류로 먼저 가른다. 그리고 "게이트웨이로 올리기"가 왜 답이 아닌지를 5절 근거로 다시 쓴다

먼저 중복을 두 종류로 갈라야 답이 정확해진다.

역할(role) 수준의 거친 체크

"ADMIN만 접근" 같은 것. 토큰 클레임만 보면 판정되므로 도메인 데이터가 필요 없다. 게이트웨이나 공통 라이브러리에서 균일 처리할 수 있고, 실제로 중복 문제가 크지 않다.

리소스 소유권 수준

"본인 것이거나, 같은 가족 계정이거나, ADMIN이면 조회 가능"이 주문·문서·결제 서비스에 각각 하드코딩되면, 규칙 하나 바뀔 때 세 곳을 고쳐야 하고 한 곳을 빠뜨리면 보안 사고다. 여기가 진짜 중복이다.

이걸 게이트웨이로 올리는 것은 답이 아니다(5절에서 본 이유 그대로 — 판정에 도메인 데이터가 필요하다). 대신 두 방향이 있다. (1) 공통 인가 라이브러리로 패턴을 표준화하거나, (2) 정책 결정을 별도 컴포넌트로 빼고 서비스는 질의만 하는 구조로 푼다. 후자를 PDP/PEP 분리라고 부른다.

PDP = Policy Decision Point
정책 결정 지점 — "이 사람이 이걸 해도 되나?"를 판단하는 곳. 인가 규칙이 여기 한 곳에만 존재한다.
PEP = Policy Enforcement Point
정책 집행 지점 — 그 판단을 받아 실제로 막거나 통과시키는 곳. 판단하지 않고 집행만 한다.

핵심은 "중복 제거의 방향이 게이트웨이 집중이 아니라 라이브러리화 또는 전담 컴포넌트화"라는 것이다. 실행 위치는 여전히 도메인 문맥이 있는 서비스 쪽이다.

한 가지 대가도 함께 말하면 좋다. PDP 질의가 요청마다 네트워크 왕복을 추가하므로, 실무에서는 PDP를 사이드카로 같은 파드에 붙이거나 정책을 각 서비스에 배포해 로컬에서 평가하는 방식(OPA 같은 도구가 이 형태를 지원한다)을 쓴다. 그리고 PDP 자체가 새로운 단일 장애점이 되지 않도록 가용성 설계가 필요하다.

BFF와 API 게이트웨이는 뭐가 다른가요? 필수힌트: "누구를 위한 것인가"와 "언제 바뀌는가"로 가른다. 표의 마지막 두 행이 결론을 만든다

같은 자리에 있는 것처럼 보이지만 소유권과 변경 주기가 다르다. 이 둘이 다르면 컴포넌트를 합칠 수 없다는 것이 답의 골격이다.

게이트웨이는 전 트래픽 공통의 인프라 경계(인증, rate limit, 라우팅)로 플랫폼 팀이 소유한다. 도메인을 모르는 채 얇게 유지되며, 보안·인프라 정책이 바뀔 때만 바뀐다.
BFF는 특정 프론트엔드 하나를 위한 전용 백엔드로, 그 클라이언트 팀이 소유한다. 07-chatty-api-call-explosion.md의 정의대로 재사용성을 대가로 왕복을 사는 거래이고, 화면 요구에 맞춰 자주 바뀌는 것이 정상이다.

그것이 9절의 배포 병목이고, 게이트웨이 모놀리스화의 시작이다. 그래서 분리한다. 답할 때는 "게이트웨이 → BFF → 서비스"로 층을 나눠 말하면 구조가 선명해진다(3절 그림).

게이트웨이 자체가 단일 장애점(SPOF)이자 병목이 되지 않나요? 필수힌트: "아니다"라고 답하면 안 된다. 맞다고 인정하고 세 가지 대응을 말한다 — 그리고 세 번째가 이 문서와 이어진다

SPOF(Single Point Of Failure, 단일 장애점)는 그것 하나가 죽으면 전체가 죽는 지점이다. 게이트웨이는 전 트래픽이 반드시 지나는 곳이므로 정의상 여기에 해당한다. "아니다"라고 답하면 안 된다 — 맞다고 인정하고, 그래서 어떻게 하는지를 말하는 것이 답이다.

1
무상태(stateless)로 설계해 수평 확장 가능하게 한다. 인스턴스가 요청 간에 기억하는 것이 없어야 아무 인스턴스나 아무 요청을 처리할 수 있고, 그래야 앞에 로드밸런서를 두고 대수를 늘릴 수 있다. 상태가 필요한 rate limit 카운터는 인스턴스 메모리가 아니라 외부 저장소(Redis 등)에 둔다 — 메모리에 두면 인스턴스가 늘어날수록 실제 한도가 인스턴스 수만큼 느슨해진다.
2
다중 인스턴스 + 헬스체크 기반 로드밸런싱으로 한 대가 죽어도 트래픽이 살아 있는 대수로 넘어가게 한다. 배포도 무중단(롤링·블루그린)으로 한다.
3
로직을 얇게 유지해 처리 지연과 장애 확률 자체를 낮춘다. 이 세 번째가 4·8·9절과 이어지는 지점이다. 도메인 조건문 40개가 쌓이면 요청당 처리 시간이 늘고(전 트래픽에 곱해진다), 버그가 들어갈 표면적이 넓어지며, 그 버그의 폭발 반경은 전 서비스다.
게이트웨이를 얇게 유지하는 것은 아키텍처 순수성 문제이기 전에 가용성 문제다

이 프레이밍이 실무에서 값을 한다 — 설계 취향으로 지키자고 하면 개별 요구 앞에서 밀리지만, 가용성 문제로 프레이밍하면 지킬 근거가 생긴다. 4절의 경계 기준과 같은 결론에 도달하는 다른 경로다.

지금 모놀리스에서 MSA로 전환 중이라면, 게이트웨이 도입 시점과 초기 책임 범위를 어떻게 잡겠어요? 시니어 변별힌트: 셋만 고른다. 그리고 "왜 그 셋인가"가 답의 절반이다 — 마지막에 리뷰 기준 명문화로 닫는다

처음부터 만능 게이트웨이를 만들지 않는다. 전환 초기의 게이트웨이는 라우팅 + 인증 + 공통 로깅의 최소 책임으로 시작한다.

이 셋을 고른 이유가 답의 절반이다. 모놀리스에서 서비스를 하나 떼어낼 때마다 즉시 필요해지는 것들이면서 — 라우팅이 없으면 클라이언트가 분할 구조를 알아야 하고, 인증이 없으면 새 서비스마다 재구현이고, 공통 로깅이 없으면 요청이 어디서 끊겼는지 못 찾는다 — 동시에 도메인 지식이 필요 없어 안전한 것들이다. 즉 "필요성은 최대, 경계 위험은 최소"인 교집합이다.

rate limit·IP 차단 같은 경계 보안은 그다음이다. 트래픽 특성과 공격 패턴이 파악되기 전에 한도를 정하면 정상 사용자를 막거나 아무것도 못 막는 값이 되므로, 데이터가 쌓이는 대로 추가한다.

반대로 응답 변환·조합 요구는 처음부터 BFF로 격리해 게이트웨이에 들어올 길을 막는다. 9절에서 말한 대로 갈 곳이 있어야 배출이 되고, 첫 사례가 게이트웨이로 들어가면 그것이 선례가 되어 두 번째부터는 막을 근거가 사라진다.

"게이트웨이에 넣자"는 제안이 나올 때마다 4절의 세 질문(도·균·주)을 리뷰 기준으로 명문화해 둔다

8절에서 본 것처럼 경계는 한 번의 큰 결정이 아니라 40개의 작은 결정으로 무너지므로, 방어도 큰 결정 한 번이 아니라 작은 결정마다 적용되는 기준이어야 한다. 경계는 아키텍처 다이어그램이 아니라 반복되는 개별 결정의 기준을 팀이 공유하는 것으로 지켜진다는 답이 시니어의 답이다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

게이트웨이가 매 요청 JWT를 검증하면 인증 서버에 매번 물어봐야 하나요? 그게 병목 아닌가요?힌트: "검증"과 "조회"를 구분한다. 그리고 이 방식이 사는 것과 잃는 것을 같이 말한다

비대칭 키로 서명된 토큰이면 매번 물어볼 필요가 없다. 게이트웨이는 인증 서버의 공개키만 갖고 있으면 로컬에서 서명을 검증할 수 있다. 공개키는 보통 JWKS 같은 공개키 목록 엔드포인트에서 한 번 받아 캐시하고, 키 회전(rotation) 시에만 다시 받는다. 즉 요청마다 네트워크 호출이 생기지 않는다.

이것이 토큰 기반 인증이 세션 조회 방식보다 게이트웨이에 잘 맞는 이유이기도 하다 — 세션 저장소를 조회해야 한다면 게이트웨이가 상태 저장소에 의존하게 되고, 그 저장소가 SPOF 하나를 더 만든다.

대신 잃는 것도 말해야 답이 완성된다 — 즉시 폐기(revocation)가 어렵다. 서버에 물어보지 않으므로 이미 발급된 토큰을 만료 전에 무효화할 방법이 기본적으로 없다. 그래서 실무에서는 액세스 토큰의 만료를 짧게 잡고 리프레시 토큰으로 갱신하거나, 즉시 차단이 필요한 경우에 한해 폐기 목록을 게이트웨이가 참조하는 절충을 쓴다. 후자는 조회가 다시 생기지만 "전체 검증"이 아니라 "예외 목록 확인"이라 비용이 다르다.

서비스 메시(사이드카)를 도입하면 API 게이트웨이는 필요 없어지나요? 시니어 변별힌트: 두 축이 다르다 — 트래픽의 방향으로 가른다

대체 관계가 아니라 담당하는 트래픽 방향이 다르다. 흔히 north-south(외부 ↔ 내부)와 east-west(내부 서비스 ↔ 내부 서비스)로 부른다.

API 게이트웨이 — north-south

외부 세계와의 경계다. 신뢰할 수 없는 클라이언트를 상대하므로 인증·CORS·전역 rate limit·요청 크기 제한·WAF처럼 외부에만 의미가 있는 일을 한다. 공개 API 계약의 얼굴이기도 하다.

서비스 메시 — east-west

내부 호출들 사이다. mTLS·재시도·타임아웃·서킷 브레이커·세밀한 트래픽 분할(카나리)·서비스 간 텔레메트리를 애플리케이션 코드 수정 없이 사이드카에서 처리한다.

겹치는 부분은 실제로 있다(재시도, 타임아웃, 관측). 그때의 판단은 이 문서의 기준과 같다 — "모든 내부 호출에 균일한가"면 메시로 내리는 게 맞다. 메시가 그 일을 가져가면 게이트웨이는 오히려 더 얇아진다.

그리고 메시가 게이트웨이의 인증을 대신하지는 못한다. mTLS가 보증하는 것은 "이 호출이 어느 워크로드에서 왔는가"(서비스 신원)이지 "어느 사용자의 요청인가"(최종 사용자 신원)가 아니다. 두 신원은 다른 층위라서, 앞 질문(X-User-Id 위조)의 답이 서명된 내부 토큰 + mTLS를 겹쳐 쓰는 형태가 되는 것이다.

이미 도메인 로직 40개가 쌓인 게이트웨이를 물려받았습니다. 어떻게 되돌리나요? 시니어 변별힌트: 큰 것부터 걷어내려 하면 실패한다. 순서가 답이다

순서가 답이다. 큰 것부터 걷어내려 하면 대개 실패한다 — 위험이 크고, 그러는 사이에도 새 조건문이 계속 들어오기 때문이다.

1
출혈부터 멈춘다. 기존 40개를 건드리기 전에 "신규 유입 차단" 규칙(9-2)을 먼저 세운다. 지금 이 순간부터 도메인 조건문이 담긴 필터 PR은 머지되지 않는다. 이 합의가 없으면 걷어내는 속도보다 쌓이는 속도가 빠르다.
2
목록화하고 소유자를 붙인다. 40개를 표로 만들고 각각에 "왜 넣었나 / 언제 넣었나 / 어느 팀 요구였나 / 지우면 누가 아픈가"를 채운다. 사유 미상 항목이 드러나는 것 자체가 성과다 — 그것들이 가장 먼저 지울 후보다.
3
네 갈래로 분류한다. ① 그냥 삭제 가능(이미 죽은 클라이언트용, 사유 소멸) ② 서비스로 이관(도메인 인가·검증) ③ BFF로 이관(응답 조합·변환) ④ 정당하게 남는 것(진짜 횡단 관심사). ①부터 처리한다 — 가장 싸고 가장 빨리 개수를 줄인다.
4
이관은 소유자가 있는 것부터. 트래픽이 큰 것부터가 아니다. 받아 줄 팀이 명확한 항목이 실제로 옮겨지는 항목이고, 사유 미상·소유자 없는 항목은 먼저 관측을 붙여(이 조건문이 최근 30일간 몇 번 발동했는가) "발동 0회"를 근거로 삭제한다.

그리고 진행 상황을 숫자로 공유한다 — "게이트웨이 도메인 조건문 40 → 12", "게이트웨이 배포 사유 중 도메인 요구 비율 75% → 20%". 9-2의 세 번째 장치(변경 통계)가 여기서는 진척 지표로 재사용된다.

서비스를 새로 추가할 때마다 게이트웨이를 배포해야 하나요?힌트: 이 질문 자체가 9-2의 "설정이지 코드가 아니다" 원칙의 실전 시험이다

배포해야 한다면 그것 자체가 경계가 잘못 잡혔다는 신호다. 라우트 추가는 게이트웨이의 정당한 책임이지만, 그 책임이 코드 변경 + 재배포를 요구하는 형태로 구현돼 있다면 서비스가 늘어날수록 게이트웨이 배포 빈도가 서비스 수에 비례해 올라간다.

두 가지로 푼다. ① 서비스 디스커버리 — 서비스 인스턴스 목록을 게이트웨이가 런타임에 조회하게 해서, 인스턴스가 뜨고 지는 것에 게이트웨이가 반응하지 않게 한다. ② 선언적 라우트 설정의 동적 반영 — 라우트 정의를 코드가 아니라 설정으로 두고 재배포 없이 갱신되게 한다(설정 저장소 감시, 쿠버네티스라면 리소스 선언 등 — 구체적 방식은 제품마다 다르다).

답을 한 단계 더 밀면 이렇게 된다 — "게이트웨이 배포 빈도"를 지표로 본다. 서비스 수가 늘 때 그 지표가 같이 늘면 ①②가 안 돼 있는 것이고, 서비스 수와 무관하게 보안·인프라 정책 변경 때만 오르면 정상이다. 3절 그림의 "바뀌는 때"가 실제로 지켜지고 있는지를 재는 방법이 이것이다.

게이트웨이에서 응답을 캐싱해도 되나요? 어디까지가 선인가요? 함정힌트: 캐싱 자체가 아니라 "무효화 규칙이 무엇에 묶여 있는가"를 본다

캐싱한다는 사실이 아니라 무효화 규칙이 무엇에 묶여 있는지가 선을 긋는다.

게이트웨이(또는 그 앞 CDN)에 둬도 되는 캐시

공통·정적 응답이고 무효화가 시간(TTL)이나 HTTP 캐시 헤더로 끝나는 것. 게이트웨이는 Cache-Control·ETag를 그대로 존중하기만 하면 되고 내용을 해석하지 않는다 — 4절 ①을 통과한다.

넘어가는 순간

"주문이 취소되면 이 캐시를 비운다"처럼 무효화가 도메인 이벤트에 묶이는 순간. 그러면 게이트웨이가 "주문 취소"가 무엇인지 알아야 하고, 도메인 팀이 상태 전이를 바꿀 때마다 게이트웨이의 무효화 규칙도 같이 바뀌어야 한다 — ①과 ③에서 동시에 걸린다.

사용자별 응답 캐싱은 특히 조심해야 한다. 인증된 사용자마다 다른 응답을 게이트웨이가 캐시하면 키 설계를 한 번만 틀려도 다른 사용자의 데이터가 새어 나간다 — 게이트웨이는 폭발 반경이 전 서비스이므로 이 사고의 규모도 전 서비스다. 개인화 응답의 캐시는 그 데이터를 소유한 서비스 쪽에 두는 편이 안전하다.

그냥 게이트웨이 없이, 공통 라이브러리를 서비스마다 넣으면 안 되나요?힌트: 1-2절의 세 비용 중 어느 것이 라이브러리로 풀리고 어느 것이 안 풀리는지 가른다

세 비용 중 하나만 풀린다. 공통 라이브러리는 ①중복 구현을 상당히 줄여 준다. 그러나 ②보안 구멍과 ③변경 비용은 남는다.

② 누락 — 라이브러리는 "넣어야 적용"된다. 새 서비스가 의존성을 빠뜨리거나 필터 등록을 잊으면 그 서비스만 무방비인데, 이를 전체에서 확인할 단일 지점이 없다. 게이트웨이는 트래픽이 반드시 지나는 물리적 경로라서 누락이 구조적으로 불가능하다 — 이 차이가 결정적이다.

③ 변경 — 라이브러리 버전을 올리려면 모든 서비스가 각자 올려 배포해야 한다. "한도를 조정하자"는 결정 하나에 N번의 배포와 N개 팀의 일정 조율이 붙는다. 게다가 언어·프레임워크가 섞여 있으면 라이브러리를 언어별로 N벌 유지해야 한다.

그래서 실무에서는 둘 다 쓴다. 게이트웨이가 경계에서 균일하게 강제하고, 라이브러리는 서비스 안에서 반복되는 패턴(인가 판정 헬퍼, 표준 에러 응답, 로깅 포맷)을 표준화한다. 앞 꼬리질문의 "인가 중복" 답이 바로 이 형태다 — 게이트웨이로 올리지 않고 라이브러리 또는 PDP로 푼다.

한 줄 요약
게이트웨이와 서비스의 경계는 "도메인 지식 없이 모든 요청에 균일하게 적용되는가"로 자른다 — 인증·라우팅·전역 rate limit·CORS 프리플라이트·공통 로깅은 게이트웨이, 리소스 소유권 인가·도메인 검증·비즈니스 규칙은 서비스, 화면 맞춤 조합은 BFF로 나누고(층이 셋이어야 각 요구가 갈 자리가 생긴다), 인가 중복은 게이트웨이 집중이 아니라 PDP/PEP 분리로 풀어 규칙은 한 곳에 모으되 집행은 도메인 문맥이 있는 서비스에 남긴다 — 이 기준이 무너져 도메인 로직이 게이트웨이에 쌓이면 모든 팀의 배포가 한 지점에 줄을 서는 새로운 모놀리스가 되는데, 그 붕괴는 각각 합리적이었던 작은 편의의 누적으로 오므로 경계 기준을 팀의 리뷰 기준으로 명문화해 개별 결정마다 적용하는 것까지가 설계다.
