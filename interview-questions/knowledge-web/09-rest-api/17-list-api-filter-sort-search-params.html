목록 API의 필터·정렬·검색 파라미터 설계
정렬 키 하나가 DB 인덱스와 맺는 계약이다

면접 질문: "목록 조회 API의 필터·정렬·검색 파라미터는 어떻게 설계하나요? 허용 정렬 키를 제한해야 하는 이유는?"

핵심 관전 포인트 — 목록 조회에 들어오는 조건은 성격이 다른 세 종류다. 정확히 일치시킬 조건(필터), 결과를 어떤 순서로 줄 것인가(정렬), 관련된 것을 찾아 달라(검색). 셋을 각각 다른 규약으로 받는다 — 필터는 의미가 드러나는 명시적 파라미터(status=SHIPPED&minAmount=10000), 정렬은 전사적으로 통일된 하나의 형식(sort=createdAt,desc), 검색은 q= 하나. 그리고 셋 다 서버가 화이트리스트(서버가 미리 열거해 둔 허용 값 목록, 목록에 없으면 거절)로 값을 제한한다. 특히 허용 정렬 키를 제한해야 하는 이유는 세 겹이다. ① 성능 — sort 파라미터는 그대로 ORDER BY가 되고, 인덱스가 받치지 않는 정렬은 PostgreSQL 실행계획에 Sort 노드를 만들어 조건에 맞는 행을 전부 읽어 정렬하며, 정렬 대상이 work_mem을 넘으면 메모리가 아니라 디스크 기반 외부 병합 정렬로 떨어진다. 즉 정렬 키를 열어 두는 것은 클라이언트가 쿼리스트링 하나로 대형 정렬 작업을 DB에 시킬 수 있는 문을 여는 것이다. ② 보안·캡슐화 — ORDER BY의 컬럼명 자리는 바인딩 파라미터가 원리적으로 불가능해서(프리페어드 스테이트먼트는 문장의 구조를 먼저 확정하고 값만 나중에 채우는데, 컬럼명은 값이 아니라 구조다) 동적 정렬은 문자열 조립일 수밖에 없고, 그래서 화이트리스트가 인젝션과 내부 컬럼명 노출을 막는 유일한 방어가 된다. ③ 계약 — 한 번 허용한 정렬 키는 클라이언트가 의존하는 공개 계약이 되고, 그 키를 받치는 인덱스를 영원히 유지해야 한다. 즉 정렬 키 목록은 "API 스펙이자 인덱스 목록"이며, 둘을 함께 관리하는 시야가 이 문항의 핵심이다.
  • 1
    조건을 세 종류로 갈라 각각 다른 규약으로 받는다 — 필터는 WHERE가 되고, 정렬은 ORDER BY가 되고, 검색은 LIKE·전문 검색이 된다. 만드는 SQL이 다르고 잘못 열었을 때 나는 사고도 다르므로 규약도 따로 세운다 — status=SHIPPED&minAmount=10000(명시적 파라미터), sort=createdAt,desc(전사 통일 형식), q=김철수(하나). 범용 문법 하나로 합치면 그 문법을 파싱하는 규칙 자체가 계약이 되어 문서화·검증·확장을 전부 잃는다.
  • 2
    셋 다 화이트리스트로 값을 제한하되, 정렬은 특히 강하게 막는다 — 성·보·계 세 겹이다. 성능(인덱스 없는 정렬 = Sort 노드 + 후보 전량 읽기, work_mem 넘으면 디스크 외부 병합 정렬), 보안·캡슐화(ORDER BY는 바인딩이 원리적으로 불가능 → 문자열 조립 → 인젝션·내부 컬럼명 노출), 계약(한 번 열면 그 인덱스를 평생 운영).
  • 3
    그래서 허용 정렬 키 목록은 곧 인덱스 목록이고, 좁게 시작해 넓힌다 — API 이름(createdAt)과 내부 컬럼(created_at)을 enum 매핑 한 겹으로 갈라 두면 인젝션·캡슐화·성능 문이 한 번에 막힌다. 허용 밖 키는 조용한 폴백이 아니라 400으로 거절한다. 방향이 비대칭이라 — 넓히기는 하위 호환, 좁히기는 파괴적 변경 — 되돌릴 수 있는 쪽은 "좁게 시작"뿐이다.

0. 질문 + 출제 의도

질문: "목록 조회 API의 필터·정렬·검색 파라미터는 어떻게 설계하나요? 허용 정렬 키를 제한해야 하는 이유는?"

출제 의도: 검색 조건은 요구사항이 끝없이 추가되는 영역이다. 파라미터 폭발을 계약으로 관리하고 허용 정렬 키를 인덱스와 연동해 제한하는지 — API 설계와 DB 설계를 함께 쥐는 시야를 본다. "파라미터를 어떻게 받느냐"는 표면이고, "그 파라미터가 DB에 어떤 쿼리를 만들 수 있는가"까지 내다보는지가 관전 포인트다.

이 페이지가 겨냥하는 약점 세 가지 ① 셋을 "조회 조건"으로 뭉뚱그리는 것 → 1절에서 만들어지는 SQL 절로 축을 갈라, 왜 규약이 셋이어야 하는지를 위험의 종류로 답한다.
② "인덱스 없으면 느려요"에서 멈추는 것 → 5~6절에서 전화번호부 한 장으로 B-tree의 두 성질을 세우고, EXPLAIN의 Sort Method 한 줄로 판정하는 법과 "LIMIT 20이니 20건만 아닌가"라는 반론을 숫자로 격파한다.
③ "화이트리스트 걸면 되죠"를 보안 이야기로만 하는 것 → 7절에서 왜 ORDER BY ?가 원리적으로 불가능한지를 프리페어드 스테이트먼트로 설명하고, 8절에서 정렬 키 = 인덱스 = 영구 운영 비용이라는 계약 관점까지 올린다.
이 문서의 각도 — 페이지네이션 문서와 무엇이 다른가 같은 카테고리의 04-pagination-offset-vs-cursor-api-contract.md는 "어디부터 몇 건을 줄 것인가"(offset/커서, tie-breaker, 커서 토큰)를 다룬다. 이 문서는 그 앞에 놓인 질문 — "어떤 행을, 어떤 순서로 고를 수 있게 허용할 것인가" — 를 다룬다. 두 문서가 만나는 지점은 하나다: 정렬 축을 하나 열 때마다 커서 설계도 인덱스도 한 벌씩 늘어난다(8절 끝).

1. 조건은 세 종류다 — 규약도 셋

GET /orders 하나에 붙는 쿼리 파라미터를 뭉뚱그려 "조회 조건"이라고 부르면 설계가 시작되지 않는다. 실제로는 성격이 완전히 다른 세 가지가 섞여 들어온다. 가르는 기준은 취향이 아니라 "서버가 이 파라미터로 SQL의 어느 절을 만드는가"다.

세 종류의 대비. 면접에서 값이 나가는 줄은 "만드는 SQL"과 "잘못 열면 생기는 일"이다 — 이 두 줄이 규약을 셋으로 나누는 근거다.
종류클라이언트가 요구하는 것서버가 만드는 SQL잘못 열면 생기는 일규약
필터"이 조건에 정확히 맞는 것만"WHERE 절조합이 폭발해 인덱스로 감당이 안 된다필드별 명시적 파라미터 + enum 값 검증 (2절)
정렬"이 순서로 줘"ORDER BY 절인덱스 없는 정렬이 DB를 태운다 + 바인딩 불가라 인젝션 통로전사 통일 하나의 형식 + 키 화이트리스트 (3·6·7·8절)
검색"이거랑 관련된 것 찾아 줘"LIKE / 전문 검색 / 검색 엔진중간 일치가 전체 스캔이 된다q 하나, 대상·방식은 서버 구현 (4절)

규약 한 줄 — 이 문서 전체의 뼈대

필터는 명시적 파라미터, 정렬은 통일된 형식, 검색은 q 하나 — 셋 다 서버 화이트리스트

면접에서 첫 문장으로 이 한 줄을 먼저 놓고, "특히 정렬을 강하게 막는 이유는 세 겹입니다"로 이어가면 답변의 뼈대가 그대로 선다.

1-1. 파라미터 폭발을 계약으로 관리하는 세 원칙

검색 조건은 요구사항이 끝없이 추가되는 영역이다. "이 상태도 걸러 주세요", "이 기간도요", "담당자별로도요" — 목록 API는 서비스가 성장하는 만큼 파라미터가 늘어난다. 관리 원칙은 셋이다.

① 추가는 자유, 의미 변경은 파괴적
새 필터를 하나 더 받는 것은 기존 클라이언트에 영향이 없다. 그러나 공개한 파라미터의 의미를 바꾸면(minAmount를 "상품 금액"→"결제 금액") 기존 클라이언트가 조용히 잘못된 결과를 받는다. 스키마는 그대로인데 뜻만 바뀌므로 타입 검증으로도 안 잡힌다 — 가장 위험한 파괴적 변경이다.
② 길이·중첩 한계는 POST 검색으로
조건 조합이 수십 개로 늘고 쿼리스트링이 길이 한계에 닿으면 POST /orders/search + 본문 조건 객체로 전환한다. 대가는 HTTP 캐시 상실과 시맨틱 절충 (11절 첫 꼬리질문).
③ 조합 폭발은 위임 신호
다중 필터 × 자유 정렬 × 전문 검색이 동시에 요구되는 화면(관리자 통합 검색)은 RDB 인덱스 설계로 감당할 조합 수를 넘어선다. 검색 엔진 위임을 검토할 신호다 (9절).

2. 필터 — 이름이 곧 문서다

Before 범용 문법 하나로 다 받기
GET /orders?filter=amount:gte:10000
           &filter=status:in:SHIPPED|DELIVERED
           &filter=orderedAt:between:2026-08-01..2026-08-31

// 이 요청을 이해하려면 다음이 전부 별도 문서로 필요하다
//  - 연산자 목록: gte / lte / in / between / like ...
//  - 구분자 규칙: 콜론은 몇 개까지? 값에 콜론이 있으면?
//  - between 의 .. 은 양끝 포함인가?
//  - in 의 구분자는 파이프? 콤마? URL 인코딩은?
// → 파싱 규칙 자체가 계약이 되어 버렸다
After 필드별 명시적 파라미터
GET /orders?minAmount=10000
           &status=SHIPPED&status=DELIVERED
           &orderedFrom=2026-08-01
           &orderedTo=2026-08-31

// 파라미터 이름 자체가 문서 역할을 한다
//  - minAmount : 설명 없이 뜻이 통한다
//  - from/to   : 이름에 경계의 방향이 들어 있다
//  - 반복 파라미터로 다중 값 (팀에서 하나로 통일)
// → 서버 검증도 필드별로 타입·범위를 그대로 건다
범위 조건은 쌍으로, 경계는 문서에
minAmount/maxAmount, orderedFrom/orderedTo처럼 이름에 경계의 방향을 담는다. 경계 포함 여부(이상/초과)는 반드시 문서에 명시한다 — 정하지 않으면 클라이언트마다 해석이 갈리고, 그 차이는 "합계가 1건씩 안 맞는다"는 형태로 뒤늦게 드러난다.
다중 값은 반복 또는 콤마 — 둘 중 하나로 통일
status=SHIPPED&status=DELIVERED 또는 status=SHIPPED,DELIVERED. 어느 쪽이든 좋지만 팀에서 하나로 정해 전 API에 같은 규칙을 쓴다. 목록 API 규약의 가치는 개별 설계의 우수함보다 전체 일관성 — 클라이언트 개발자가 "다음 API도 이렇게 생겼겠지"라고 예측할 수 있는 데서 나온다.

오타를 "빈 결과"로 응답하면 클라이언트 버그가 며칠 동안 위장된다

status=SHIPED(오타)가 들어왔을 때 허용 값 밖이면 400으로 명시적으로 거절한다. 조용히 빈 결과를 주면 클라이언트 개발자가 보는 것은 "데이터가 없네"뿐이라, 진짜 원인(오타)에 도달하는 데 며칠이 든다.

이 원칙은 정렬 키의 400 vs 폴백 논쟁(11절)과 정확히 같은 뿌리다 — 빨리 실패(fail-fast)해야 개발 단계에서 잡힌다. 에러 본문에 허용 값 목록을 담아 주면 문서를 다시 찾는 왕복까지 줄어든다.

3. 정렬 — 형식 통일과 "기본 정렬도 계약"

sort=createdAt,desc
Spring Data 관례
필드와 방향을 콤마로 나눈다. 다중 정렬은 sort 파라미터를 여러 번.
sort=-createdAt
부호 접두 관례 (JSON:API 등)
-가 내림차순. 다중 정렬은 sort=-createdAt,name처럼 콤마로 나열.

형식은 어느 쪽이든 좋다. 중요한 건 전사적으로 하나라는 것과, 정렬 가능한 필드를 서버가 열거해 제한한다는 것이다(제한 이유는 5~8절 전체). 다중 정렬(sort=status,asc&sort=createdAt,desc)을 지원한다면 우선순위가 파라미터 등장 순서라는 것까지 계약에 적는다.

기본 정렬도 계약이다 — ORDER BY 없는 SELECT의 순서는 표준적으로 보장이 없다

sort를 생략했을 때의 순서(보통 createdAt,desc)를 문서에 명시하고 암묵에 맡기지 않는다. 여기에는 SQL의 성질이 하나 깔려 있다 — DB는 그때그때 편한 순서로 준다. 어떤 실행계획을 골랐는지, 인덱스를 탔는지, 병렬 워커가 몇 개였는지에 따라 결과 순서가 달라질 수 있다.

"어제까지 최신순이었는데 오늘부터 순서가 튀어요" = 기본 정렬을 명시하지 않은 목록의 전형적 제보

우연히 원하는 순서로 나오던 것이 데이터 양이나 실행계획이 바뀌면서 깨진 것이다. 코드가 바뀐 적이 없으니 원인을 찾기도 어렵다.

한 칸 더 — 정렬 키 이름은 응답 필드 이름과 맞춰 둔다 응답이 {"createdAt": "..."}인데 정렬은 sort=created_date로 받는다면, 클라이언트는 두 개의 이름 체계를 외워야 한다. 정렬 키 = 응답 필드명으로 맞추면 그리드 컬럼 헤더와 정렬 파라미터가 1:1로 대응해 프론트가 매핑 테이블을 들고 있지 않아도 된다. 이것도 1절의 "일관성 = 예측 가능성"이 구체화된 형태다. (내부 컬럼명과의 분리는 7절 enum 매핑이 담당하므로, 외부 이름을 응답에 맞추는 것과 내부 컬럼을 감추는 것은 충돌하지 않는다.)

4. 검색 — q 하나가 사는 구현의 자유

전문 검색(여러 필드를 대상으로 한 부분 일치)은 필터와 성격이 다르다. 필터는 "정확한 조건"이고 검색은 "관련된 것 찾기"다. 정확한 조건은 참·거짓이 명확하지만, 관련성은 서버가 판단하는 것이라 판단 방식이 계속 진화한다. 그래서 q 하나로 받고, 대상 필드와 매칭 방식(전방 일치인지, 형태소 분석인지, 랭킹을 매기는지)은 서버 구현으로 감춘다.

트

5. 전제 — 인덱스는 "미리 정렬해 둔 목차"다

정렬 키와 인덱스의 관계를 이해하려면 인덱스가 어떻게 생겼는지부터 한 문단 필요하다. RDB의 기본 인덱스인 B-tree는 값을 크기 순으로 정렬해 계층적으로 담아 둔 자료구조다. 뿌리에서 시작해 "찾는 값이 이보다 큰가 작은가"를 몇 번 판단하며 내려가면 원하는 지점에 닿고, 리프(가장 아래층)는 정렬된 순서대로 옆으로 이어져 있다.

6. ① 성능 — 정렬 파라미터는 DB 부하로 통하는 문이다

sort 파라미터는 그대로 ORDER BY가 된다. 그리고 5절에서 본 대로, 그 정렬을 받쳐 주는 인덱스가 있느냐 없느냐에 따라 DB가 하는 일이 완전히 달라진다.

인덱스가 받치는 정렬 — 정렬이 통째로 생략된다

  • 인덱스를 순서대로 읽으면 끝이다.
  • 실행계획에 Index Scan(역방향이면 Index Scan Backward)만 나오고 Sort 노드가 아예 등장하지 않는다.
  • 필요한 만큼 읽고 멈춘다 — LIMIT 20이면 정말 20건 근처만 읽는다.

인덱스가 없는 컬럼 정렬 — 후보를 전부 읽어 정렬한다

  • 실행계획에 Sort 노드가 붙는다.
  • DB는 WHERE 조건에 맞는 행을 전부 읽어 올린 뒤 정렬한다.
  • 정렬 대상이 work_mem을 넘으면 디스크로 쏟아진다 — 아래 갈림길.
용어 — work_mem과 그 갈림길 work_mem은 정렬·해시 같은 연산 하나가 쓸 수 있는 메모리 상한이다(PostgreSQL 기본값은 4MB 수준). 정렬 대상이 그 안에 들어가면 메모리에서 퀵소트로 끝나지만, 넘어가면 임시 파일로 쏟아 내어 디스크에서 조각을 병합하는 외부 병합 정렬(external merge sort)로 떨어진다. 메모리 정렬과 디스크 정렬은 비용의 차원이 다르다. 그리고 이 갈림길은 추측이 아니라 관측할 수 있다 — 바로 아래.

LIMIT이 붙어 상위 N건만 들고 비교했다. 정렬용 메모리만 아꼈을 뿐 — 아래 함정 카드.
external merge Disk: 41008kB
디스크로 떨어졌다. 목록 API에서 반복 호출되면 그것만으로 DB CPU와 디스크 I/O가 함께 튄다.

가장 자주 나오는 반론 — "LIMIT 20이 붙어 있으니 20건만 처리하는 것 아닌가?"

아니다. 상위 20건이 무엇인지 알려면 후보 전체를 봐야 한다.

PostgreSQL은 LIMIT이 붙은 정렬에서 상위 N건만 들고 비교해 나가는 top-N heapsort를 고른다. 그래서 실행계획에 디스크 대신 Sort Method: top-N heapsort Memory: 30kB처럼 찍히기도 한다. 하지만 정렬용 메모리를 아꼈을 뿐, 그 아래 Seq Scan이 조건에 맞는 행을 전부 읽어 하나씩 비교하는 비용은 그대로다.

20건을 주려고 124만 행을 읽는 상황은 변하지 않는다

게다가 페이지가 깊어질수록 들고 있어야 할 N이 커진다 — OFFSET 20000이면 N이 20,020이다. 유지 대상이 커져 결국 work_mem을 넘고 디스크 정렬로 내려간다. 정렬 대상 전체를 내보내는 CSV 익스포트 같은 경로에서는 처음부터 디스크 정렬이다.

그래서 이 절의 결론 한 문장 정렬 키를 제한하지 않은 목록 API는, 클라이언트가 쿼리스트링 하나로 대형 정렬 작업을 DB에 시킬 수 있는 API다. 크롤러나 잘못 짠 클라이언트가 sort=memo(인덱스 없는 컬럼)로 연타하면 그게 그대로 DB CPU 스파이크가 된다. 그러므로 허용 목록은 "인덱스가 받치는 정렬 축"과 일치해야 한다 — 정렬 키 화이트리스트는 API 스펙이면서 동시에 인덱스 목록이다.

7. ② 보안·캡슐화 — 왜 ORDER BY ?는 안 되나

WHERE user_id = ?의 ? 자리에는 요청 값을 안전하게 꽂을 수 있는데, ORDER BY ?는 왜 안 될까. 이게 이 절 전체의 전제이므로 정확히 짚고 가야 한다.

프리페어드 스테이트먼트(prepared statement)는 SQL을 DB에 두 단계로 넘기는 방식이다. 먼저 문장의 뼈대를 보내면 DB가 그것을 구문 분석하고 실행 계획까지 세워 둔다. 그다음 값만 따로 보내면 DB가 준비된 계획에 값을 꽂아 실행한다. 핵심은 구조가 값보다 먼저 확정된다는 것이다.

8. ③ 계약 — 정렬 키 하나 = 인덱스 하나 평생 운영

허용 목록에 키를 하나 추가하는 순간 클라이언트들이 그것에 의존하기 시작한다. 그리고 하위 호환 원칙상 이미 공개한 기능의 제거는 파괴적 변경이다. 그런데 정렬 키의 경우, 제거하지 못하는 것이 API 스펙 한 줄만이 아니다.

가산점 — 커서 페이지네이션과의 연동 가산점 커서 기반 목록에서는 정렬 축 하나하나가 ① 커서에 담을 값 ② tie-breaker를 포함한 복합 인덱스 ③ 토큰 스키마를 각각 요구한다. 정렬 축이 다섯 개면 복합 인덱스도 다섯 벌이라는 뜻이다. 그래서 커서 기반 목록에서 정렬 키 화이트리스트는 선택이 아니라 구조적 전제다. 7절 코드처럼 정렬 키 enum에 tie-breaker까지 함께 매핑해 두면 "정렬 키 추가 = 커서 설계 + 인덱스 추가"라는 체크리스트가 코드 자체에 박힌다. (커서 계약의 상세는 04-pagination-offset-vs-cursor-api-contract.md)

정렬 키를 제한하는 이유 세 겹 — "성 · 보 · 계"

성 — 성능
sort는 그대로 ORDER BY. 인덱스가 안 받치면 Sort 노드 + 후보 전량 읽기, work_mem 넘으면 디스크 외부 병합 정렬. 쿼리스트링 하나로 DB에 대형 정렬을 시키는 문.
보 — 보안·캡슐화
ORDER BY 컬럼명은 바인딩이 원리적으로 불가능 → 문자열 조립 → 인젝션 + 내부 컬럼명이 공개 계약화. 화이트리스트가 유일한 방어.
계 — 계약
한 번 열면 그 인덱스를 평생 운영. 넓히기는 하위 호환, 좁히기는 파괴적 변경 — 비대칭이므로 좁게 시작한다.
허용 정렬 키 목록 = API 스펙이자 인덱스 목록

즉시 — 문을 닫고, 계약을 UI까지 전파한다. 정렬 키 화이트리스트(7절)를 걸고, 그리드 쪽에는 "정렬 가능 컬럼" 목록을 API 스펙으로 내려 줘서 허용된 컬럼에만 정렬 아이콘이 켜지게 한다. 그래야 사용자가 "왜 이 컬럼만 정렬이 안 되지?"라고 400 에러로 배우지 않는다.
2
협상 — "모든 컬럼 정렬"이 진짜 요구인지 확인한다. 접근 로그를 보면 대부분 실제로 쓰는 정렬 축은 두세 개다. 쓰는 축만 인덱스와 함께 허용 목록에 추가한다. 요구사항의 크기를 확인하지 않고 기술로만 받으면 인덱스가 컬럼 수만큼 늘어나고, 그만큼 쓰기가 느려진다(8절).
3
구조 전환 — 전부 진짜 요구라면 검색 엔진에 위임한다. 다중 필터 × 임의 정렬 × 전문 검색이 전부 필요하면 RDB 인덱스로는 조합 폭발을 감당할 수 없다. Elasticsearch에 색인해 그 화면만 위임한다. 대가는 색인 동기화 지연(RDB에 쓴 것이 검색 엔진에 반영되기까지의 시차)과 운영 컴포넌트 추가이므로, 화이트리스트로 버틸 수 있는 동안은 꺼내지 않는다.

10. 필터는 강도가 다르다 — 선택도(selectivity) 시니어 변별

"필터 조합마다 인덱스를 다 만들 수는 없는데, 필터 파라미터도 정렬처럼 막아야 하나요?" — 원칙은 같지만 강도를 다르게 적용한다. 그 이유를 말하려면 용어 하나가 필요하다.

선택도(selectivity)는 조건 하나가 전체 행 중 몇 퍼센트로 좁혀 주는가를 뜻한다. 100만 건 중 3건이 남는 조건은 선택도가 높고(0.0003%), 90만 건이 남는 조건은 선택도가 낮다(90%).

선택도가 낮은 조건은 인덱스를 타도 이득이 없다. 인덱스로 90만 건의 위치를 알아낸 뒤 그 90만 건을 다시 테이블에서 읽어 와야 하는데, 그럴 바에는 처음부터 테이블을 순차로 훑는 편이 빠르기 때문이다. PostgreSQL의 플래너가 선택도가 낮다고 판단하면 인덱스가 있어도 Seq Scan을 고르는 이유가 이것이다.

정렬 — 예외 없이 나빠진다

  • 인덱스가 없으면 조건에 맞는 행 전체를 읽어 정렬해야 한다.
  • 크면 디스크로 떨어진다(6절).
  • 다른 조건이 도와줄 여지가 구조적으로 없다 — 정렬은 후보 전체가 정해진 뒤에 하는 작업이기 때문.

필터 — 다른 조건과 결합하면 견딜 수 있다

  • 선택도 높은 다른 조건과 결합하면 인덱스 없이도 견딘다.
  • orderedFrom/To로 이미 3천 건까지 좁혀 놓았다면, 그 안에서 memo LIKE를 걸어도 3천 건만 훑으면 된다.
  • 그래서 화이트리스트의 대상이 "필드"가 아니라 "조합"이 된다.

필터 쪽 실무 기준 셋

  • 자주 쓰이는 필터 조합을 접근 로그로 확인하고, 그 조합에 복합 인덱스를 설계한다.
  • 선택도가 낮은 필터의 단독 호출(예: 전체의 90%가 SHIPPED인데 status만 걸고 조회)이 문제라면 "단독 사용 불가, 기간 필터 필수" 같은 조합 제약을 계약에 명시한다.
  • 조합이 통제 불능으로 늘면 검색 엔진 위임(9절)으로 넘어간다.
받을 수 있는 것과 빠르게 처리할 수 있는 것을 구분해, 후자만 약속하는 것이 설계다
비유 하나 — 화이트리스트는 식당 메뉴판이다 주방이 만들 수 있는 요리와 제시간에 낼 수 있는 요리는 다르다. 메뉴판에는 후자만 적는다. 손님이 "재료가 있으니 이것도 해 주세요"라고 하면 그날은 되지만 매일 주문이 들어오면 주방이 무너진다. "필터 파라미터 목록 = 지원을 약속한 조회 패턴", "정렬 키 목록 = 인덱스 목록"이라는 계약 관점이 정확히 이것이다 — 그리고 메뉴판에 한 번 올린 요리는 내리기가 어렵다(8절의 비대칭).

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

파라미터 규약 한 줄?
필터=명시적 파라미터(minAmount), 정렬=통일된 하나의 형식(sort=createdAt,desc), 검색=q 하나. 셋 다 서버 화이트리스트.
정렬 키를 제한하는 이유 셋?
성·보·계 — 성능(Sort 노드 + 후보 전량 + 디스크 정렬), 보안·캡슐화(바인딩 불가 → 문자열 조립), 계약(인덱스 평생 유지).
왜 ORDER BY ?는 안 되나?
프리페어드 스테이트먼트는 구조를 먼저 확정하고 값만 나중에 채운다. 컬럼명·ASC/DESC는 값이 아니라 구조라 파라미터가 될 수 없다 → 문자열 조립이 유일 → 화이트리스트가 유일한 방어.
EXPLAIN에서 판정하는 한 줄?
Sort Method. quicksort Memory(메모리) / top-N heapsort Memory(LIMIT — 메모리만 아낌) / external merge Disk(디스크로 떨어짐). 인덱스가 받치면 Sort 노드가 아예 없다.
"LIMIT 20이니 20건만" 반박?
상위 20건이 무엇인지 알려면 후보 전체를 봐야 한다. top-N heapsort는 정렬용 메모리만 아낀다 — 아래 Seq Scan이 124만 행을 읽는 비용은 그대로. OFFSET이 깊어지면 N이 커져 결국 디스크.
화이트리스트 구현 한 겹?
enum 매핑 — apiName(외부 계약) ↔ Sort(내부 컬럼 + tie-breaker). 요청 문자열은 equals 비교에만 쓰이므로 구문에 닿을 경로가 없다. 목록 밖은 400.
기본 정렬을 명시해야 하는 이유?
ORDER BY 없는 SELECT는 반환 순서가 표준적으로 보장되지 않는다. 실행계획·데이터 양이 바뀌면 순서가 튄다 → "어제까지 최신순이었는데" 제보.
검색 구현 사다리 4단계?
전·트·티·엔 — 전방 일치 → pg_trgm+GIN → tsvector+GIN → 검색 엔진. q 하나로 감춰 뒀기에 클라이언트 변경 없이 갈아탄다.
정렬 키 하나를 여는 결정의 정체?
"인덱스 하나를 평생 운영한다"는 결정. 넓히기=하위 호환 / 좁히기=파괴적 변경 → 비대칭 → 좁게 시작해서 요구가 확인될 때 넓힌다.
필터와 정렬의 강도 차이 근거?
선택도. 정렬은 후보 전체가 정해진 뒤 하는 작업이라 인덱스가 없으면 예외 없이 나빠지지만, 필터는 선택도 높은 다른 조건과 결합하면 견딘다 → 화이트리스트 대상이 "필드"가 아니라 "조합".

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

필터 조건이 계속 늘어 쿼리스트링이 감당이 안 되면 어떻게 하나요? 필수힌트: 전환 자체는 쉽다. 대가 두 가지와 "본문으로 옮겨도 그대로인 것" 하나를 붙여야 답이 완성된다

POST /orders/search(또는 /orders:search)로 전환해 조건 객체를 본문에 담는다. URL 길이 한계와 중첩 조건(AND/OR 조합) 표현 문제를 한 번에 해결한다.

대가는 두 가지다. POST라서 HTTP 캐시를 잃고(GET이 아니면 중간 캐시가 응답을 재사용하지 않는다), "조회인데 POST"라는 시맨틱 절충이 생긴다. 이 절충을 문서에 명시해 두어야 나중에 "왜 조회가 POST죠?"라는 리뷰 지적이 반복되지 않는다.

이때도 조건 객체의 필드와 연산자는 서버가 정의한 스키마로 제한한다

본문으로 옮겼다고 해서 "임의 필드 + 임의 연산자"를 열면 쿼리스트링 시절보다 더 넓은 문이 된다 — 위치가 바뀌었을 뿐 성·보·계 세 위험은 그대로다.

sort 파라미터 형식은 어떤 것을 쓰나요? 기준이 있나요? 필수힌트: 어느 쪽을 고르느냐로 답하면 절반이다. "진짜 기준"을 셋으로 세워야 한다

sort=createdAt,desc(Spring Data 관례)와 sort=-createdAt(JSON:API 등 부호 접두) 모두 실무에서 통용되고 우열은 크지 않다.

진짜 기준은 셋이다.

① 전사 일관성
서비스마다 형식이 다르면 클라이언트가 API마다 문서를 다시 읽어야 한다
② 다중 정렬 우선순위 명시
sort가 여러 개일 때 등장 순서가 우선순위라는 것까지 계약에 적는다
③ 기본 정렬 문서화
sort 생략 시의 순서. 안 적으면 순서가 튄다(3절)

"형식 선택보다 형식의 통일과 계약 명시가 본질"이라고 답하면 01-restful-design-principles-resource-naming.md의 '일관성이 예측 가능성을 만든다'는 관점과 정확히 정렬된다.

허용 목록 밖 정렬 키가 오면 400과 기본 정렬 폴백 중 무엇이 맞나요? 함정힌트: 답은 400이다. 그런데 "이미 폴백으로 돌고 있는 API"라는 조건이 붙으면 답이 한 겹 더 필요하다

400 거절이 맞다. 폴백은 당장의 장애는 없어 보이지만 클라이언트의 오타나 잘못된 연동을 "정렬이 이상하다"는 형태로 숨긴다. 빨리 실패(fail-fast)해야 개발 단계에서 잡힌다. 에러 응답 본문에 허용 키 목록을 담아 주면 문서를 다시 찾는 왕복도 줄어든다.

단, 이미 폴백으로 동작 중인 운영 API를 400으로 바꾸는 것은 그 자체가 파괴적 변경이다

지금까지 조용히 무시되던 요청이 갑자기 실패하기 시작하기 때문이다. 그래서 유예 기간을 둔다 — ① 먼저 로그로 위반 클라이언트를 파악하고 ② 공지한 뒤 ③ 전환한다. "측정 → 공지 → 전환"은 8절의 비대칭이 실무 절차로 번역된 형태다.

필터 조합마다 인덱스를 다 만들 수는 없는데, 필터 파라미터도 제한해야 하나요? 시니어 변별힌트: "원칙은 같지만 강도가 다르다"로 시작하고, 그 차이를 선택도라는 용어로 근거 짓는다

원칙은 같지만 강도를 다르게 적용한다. 근거는 선택도(selectivity) — 조건 하나가 전체 행 중 몇 퍼센트로 좁혀 주는가다. 선택도가 낮은 조건은 인덱스를 타도 이득이 없다(90만 건의 위치를 알아낸 뒤 그 90만 건을 다시 테이블에서 읽을 바에는 순차 스캔이 빠르다 — 플래너가 Seq Scan을 고르는 이유).

정렬과 필터의 차이가 여기서 나온다. 정렬은 인덱스가 없으면 예외 없이 비용이 급격히 나빠지지만(후보 전체를 읽어 정렬, 크면 디스크), 필터는 선택도 높은 다른 조건과 결합하면 인덱스 없이도 견딜 수 있다. orderedFrom/To로 이미 3천 건까지 좁혀 놓았다면 그 안에서 memo LIKE를 걸어도 3천 건만 훑으면 된다.

실무 기준 셋: ① 자주 쓰이는 필터 조합을 접근 로그로 확인해 복합 인덱스 설계 ② 선택도 낮은 필터의 단독 호출이 문제면 "단독 사용 불가, 기간 필터 필수" 같은 조합 제약을 계약에 명시(= 화이트리스트의 대상이 필드가 아니라 조합) ③ 조합이 통제 불능이면 검색 엔진 위임.

받을 수 있는 것과 빠르게 처리할 수 있는 것을 구분해, 후자만 약속하는 것이 설계다
검색(q)이 LIKE '%키워드%'로 구현돼 있으면 어떤 문제가 있나요? 필수힌트: "느립니다"로 끝내지 말고 왜부터. 그리고 "중간 일치는 무조건 전체 스캔"이라는 단정을 스스로 교정하면 한 칸 더 간다

먼저 왜 느린지부터. 5절에서 본 대로 B-tree 인덱스는 값을 정렬해 담아 두므로 "이렇게 시작하는 것"은 범위로 좁힐 수 있지만 "중간에 이게 들어간 것"은 어디에 있을지 알 수 없다. 그래서 LIKE '%키워드%'는 일반 B-tree 인덱스를 탈 수 없고, 조건에 맞는 후보 전체를 읽어 한 건씩 문자열을 대조하게 된다. 데이터가 늘면 검색 한 번이 목록 테이블 전체를 읽는 쿼리가 된다.

대응은 단계적이다 (전·트·티·엔).

① 전방 일치로 요구를 좁힐 수 있는지 확인한다. '키워드%'는 B-tree 범위 탐색이 되므로 인덱스가 그대로 듣는다. "이름 검색"이 실제로는 "이름 앞부분으로 찾기"면 충분한 경우가 의외로 많다. 가장 싼 해법이므로 먼저 물어본다.

② 중간 일치 자체를 인덱스로 살리려면 pg_trgm이 있다. PostgreSQL 확장 모듈로, 문자열을 3글자씩 겹쳐 자른 조각(트라이그램)으로 쪼개 GIN 인덱스에 담아 둔다. 검색어도 같은 방식으로 쪼갠 뒤 "이 조각들을 전부 가진 행"으로 후보를 좁히므로 LIKE '%키워드%'도 인덱스의 도움을 받을 수 있다. 그래서 "중간 일치는 무조건 전체 스캔"이라는 단정은 정확하지 않다.

CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX idx_orders_memo_trgm ON orders USING gin (memo gin_trgm_ops);
-- 이후 memo LIKE '%키워드%' 가 이 인덱스를 후보 축소에 쓸 수 있다

대가도 분명하다. 트라이그램 인덱스는 원문보다 커지기 쉬워 저장 공간과 쓰기 비용이 크고, 검색어가 3글자 미만이면 트라이그램을 만들 수 없어 인덱스가 도움이 안 된다.

③ 본격적인 전문 검색이면 tsvector + GIN이다. 두 가지가 각각 무엇인지 짚고 가자.

  • tsvector는 문서를 검색 가능한 단어 목록으로 미리 쪼개 정규화해 담아 두는 PostgreSQL 타입이다. to_tsvector('english', 'The cats are running')을 돌리면 'cat':2 'run':4 같은 형태가 나온다 — 불용어는 버리고, 어미를 떼어 어간으로 통일하고, 각 단어의 위치까지 기록한다. 검색할 때마다 문자열을 훑는 대신 미리 쪼개 둔 단어 목록끼리 비교하는 것이 전문 검색의 원리다.
  • GIN(Generalized Inverted Index, 일반화 역색인)은 그 tsvector에 맞는 인덱스다. B-tree는 "한 행에 키 하나"를 전제하는데 tsvector는 한 행이 수십 개의 단어를 갖는 다대다 구조라 그 전제가 성립하지 않는다. GIN은 방향을 뒤집어 "단어 → 그 단어를 가진 행 목록"을 저장한다 — 그래서 역(inverted)색인이다. 책 뒤의 찾아보기와 정확히 같은 구조다.
-- 생성 컬럼으로 tsvector 를 유지하고 GIN 인덱스를 건다
ALTER TABLE orders ADD COLUMN search_doc tsvector
    GENERATED ALWAYS AS (to_tsvector('simple', coalesce(customer_name,'') || ' ' || coalesce(memo,''))) STORED;
CREATE INDEX idx_orders_search ON orders USING gin (search_doc);

-- 조회
SELECT * FROM orders WHERE search_doc @@ plainto_tsquery('simple', '김철수');

한국어 주의점 하나. PostgreSQL 기본 파서는 한국어 형태소 분석을 하지 못해 공백 단위 분리에 가깝게 동작한다. "김철수의"를 "김철수"로 검색하면 안 걸릴 수 있다는 뜻이다. 본격적인 한국어 검색이 요구되면 별도 확장을 붙이거나 ④로 넘어가야 한다.

④ 검색 요구가 본격적이면(형태소 분석, 랭킹, 다중 필드, 오타 교정) 검색 엔진에 위임한다.

이 전환 전체가 가능한 이유는 q의 계약을 "어떻게 찾는지는 서버 구현"으로 감춰 뒀기 때문이다

반대로 searchOp=contains를 계약으로 노출했다면 구현을 바꿀 때마다 클라이언트를 함께 옮겨야 한다. 파라미터 설계가 구현 진화의 자유를 지켜 주는 사례다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

그럼 Spring에서 Pageable은 아예 쓰면 안 되나요? 어떻게 받아야 하나요?힌트: 금지가 아니라 "어디서 만드느냐"의 문제다. 경계를 한 줄로 그어 본다

쓰면 안 되는 게 아니라, 요청에서 직접 바인딩하지 않는다는 것이다. 경계를 한 줄로 그으면 이렇다 — Pageable은 요청이 만드는 것이 아니라 서버가 조립하는 것이다.

받는 모양: 컨트롤러는 sort를 문자열로 받고 → OrderSortKey.from(param)으로 enum 변환(여기서 400) → 서비스에서 PageRequest.of(page, size, key.getSort())로 Pageable을 조립한다. 요청 문자열은 enum 경계를 넘지 못하고, 실제 정렬은 우리가 코드에 적어 둔 Sort다.

같이 챙길 것 둘. ① 기본값 — sort·size 생략 시의 값을 서버가 정한다(@PageableDefault를 쓰든 직접 조립하든, 문서에 적는 것이 본질). ② size 상한 — 상한이 없으면 size=100000 하나로 6절의 문이 다시 열린다. 정렬 키만 막고 페이지 크기를 안 막으면 반쪽이다.

그리고 PropertyReferenceException을 @ControllerAdvice에서 잡아 400으로 바꾸는 것은 임시 방편일 뿐이라는 점도 짚어 두면 좋다 — 그건 "존재하지 않는 필드"만 걸러 낼 뿐, "존재하지만 인덱스가 없는 필드"는 그대로 통과시킨다. 세 위험 중 성능 문이 열린 채로 남는다.

허용 정렬 키 목록을 코드 대신 설정 파일이나 DB로 빼면 더 유연하지 않나요? 시니어 변별힌트: 이 목록이 무엇과 짝을 이뤄야 하는지를 생각한다

유연해지는 대신, 이 문서의 핵심 등식이 깨진다 — "정렬 키 목록 = 인덱스 목록".

정렬 키를 여는 결정은 반드시 인덱스와 함께여야 한다(8절). 목록이 코드와 마이그레이션 스크립트에 있으면 둘이 같은 릴리스에 묶여 리뷰·배포·롤백을 함께 받는다. 반대로 설정 파일이나 DB 테이블로 빼면 "재배포 없이 정렬 키를 켤 수 있게" 되는데, 그건 곧 인덱스 없는 정렬 축을 운영 중에 켤 수 있다는 뜻이다 — 9절 사례가 이번엔 코드 변경조차 없이 재현된다.

그래도 외부화가 필요한 경우(테넌트별로 노출 컬럼이 다른 SaaS 등)라면 안전장치를 함께 건다: 켤 수 있는 후보를 코드에 열거된 enum의 부분집합으로 제한하고(= 설정은 "켜기/끄기"만, "새 키 발명"은 불가), 기동 시점에 각 키의 인덱스 존재를 확인해 없으면 기동 실패나 경고로 드러낸다. 화이트리스트를 유연하게 만들더라도, 인덱스와의 짝은 자동으로 검사되게 만드는 것이 원칙이다.

화이트리스트에는 남아 있는데 인덱스가 사라진 경우는 어떻게 알아채나요?힌트: 사람이 기억하는 방식으로는 안 된다. 어디에 붙여야 자동으로 걸리는지

이 사고는 "정렬 키를 추가할 때"가 아니라 "인덱스를 정리할 때" 난다. 성능 개선 과제로 안 쓰는 것 같은 인덱스를 DROP 했는데, 사실 그것이 어떤 정렬 키를 받치고 있던 인덱스인 경우다. API는 그대로 200을 주므로 아무도 모르고, 어느 날 DB CPU만 올라간다(9절과 증상이 같다).

알아채는 장치 셋.

  • 대조 테스트 — 정렬 키 enum을 순회하며 각 키에 대응하는 인덱스가 실제로 존재하는지 확인하는 테스트를 둔다. "정렬 키 목록 = 인덱스 목록"을 사람의 기억이 아니라 CI가 지키게 하는 것이다.
  • 실행계획 회귀 확인 — 각 정렬 키의 대표 쿼리에 EXPLAIN을 걸어 Sort 노드가 등장하면 실패로 본다. 6절의 판정 기준을 그대로 자동화하는 방식이다.
  • 인덱스 삭제 절차에 체크 항목 — 마이그레이션에서 DROP INDEX를 할 때 "이 인덱스가 받치는 정렬 키가 있는가"를 리뷰 항목으로 둔다.

이 답의 핵심은 장치의 종류가 아니라 관점이다 — 화이트리스트와 인덱스는 "같이 만들어야 하는 것"이 아니라 "같이 유지되는지 계속 검사해야 하는 것"이다.

다중 정렬(sort를 두 개 이상)을 허용하면 인덱스는 몇 벌 필요한가요?힌트: B-tree 복합 인덱스에서 "컬럼 순서"가 무엇을 의미하는지가 답이다

정렬 축의 "조합과 순서"마다 필요하다. 복합 인덱스는 선언한 컬럼 순서대로 정렬해 둔 목차이므로, (status, created_at) 인덱스는 ORDER BY status, created_at은 받쳐 주지만 ORDER BY created_at, status는 받쳐 주지 못한다. 순서가 다르면 다른 인덱스다. 방향(ASC/DESC)이 축마다 엇갈리는 조합도 마찬가지로 따로 고려해야 한다.

그래서 "정렬 키 N개를 자유 조합"은 인덱스가 N개가 아니라 조합 수만큼 필요해진다. 정렬 키 다섯 개를 열어 두고 "두 개까지 조합 가능"이라고 하면 순서 있는 조합의 수만큼이 후보가 된다 — 8절의 "인덱스 하나 = 평생 운영"을 그 개수만큼 곱한 결정이다.

그래서 다중 정렬은 "자유 조합"이 아니라 "미리 정한 조합만"으로 여는 편이 안전하다

실무에서는 정렬 키 enum의 각 항목이 이미 "복합 정렬"인 경우가 많다는 점도 유효한 답이다 — 7절 코드의 Sort.by(DESC, "createdAt", "id")가 바로 그것이다. 클라이언트에게는 축 하나로 보이지만 내부적으로는 tie-breaker까지 포함한 복합 정렬이고, 그 조합에 딱 맞는 인덱스가 한 벌 존재한다.

빈 값(status=)이나 알 수 없는 파라미터(statuss=SHIPPED)가 오면 어떻게 하나요? 함정힌트: 둘의 답이 다르다. 그리고 "정답"보다 중요한 것이 하나 있다

둘은 성격이 다르므로 나눠서 답한다.

① 빈 값(status=) — "필터 미적용"인지 "빈 값과 일치"인지를 계약으로 정하고 문서에 적는다. 대부분은 미적용으로 두는 편이 프론트가 편하다(빈 입력창을 그대로 붙여 보내기 때문). 다만 정했다는 사실 자체가 중요하다 — 정하지 않으면 서버 구현체마다, 프레임워크 버전마다 다르게 동작할 수 있고 그 차이가 "결과 건수가 가끔 다르다"로 나타난다.

② 알 수 없는 파라미터(statuss=SHIPPED) — 무시하면 오타가 조용히 삼켜진다. 사용자가 보는 것은 "필터가 안 걸린 전체 목록"이고, 그것을 정상 응답으로 받는다. 2절의 status=SHIPED 사고와 정확히 같은 실패 방식이다.

다만 여기서는 절충이 필요하다. 알 수 없는 파라미터를 일괄 400으로 막으면 추적용 쿼리 파라미터(마케팅 유입 파라미터 등)나 미래에 추가될 파라미터를 먼저 보내는 클라이언트까지 막게 되어, 하위 호환을 좁히는 방향이 된다. 실무적 절충은 "알 수 없는 파라미터는 무시하되 로그로 남긴다" — 거절하지는 않지만 보이지 않게 두지도 않는 것이다. 무엇을 고르든 계약에 적어 두는 것이 이 질문의 진짜 답이다.

정렬 키 화이트리스트를 걸었는데도 특정 정렬만 계속 느립니다. 무엇을 의심하나요? 시니어 변별힌트: "인덱스가 있다"와 "이 쿼리에서 그 인덱스가 쓰인다"는 다른 말이다

"인덱스가 존재한다"와 "이 쿼리에서 그 인덱스가 정렬에 쓰인다"는 다른 말이라는 데서 출발한다. 확인은 EXPLAIN (ANALYZE, BUFFERS)에 Sort 노드가 있는지로 한다 — 있으면 인덱스가 정렬을 받치지 못한 것이다(6절).

대표적인 이유 셋.

  • 필터와 정렬이 한 인덱스에 함께 담기지 않았다. WHERE status = ? + ORDER BY created_at인데 인덱스가 (created_at)뿐이면, 플래너는 정렬을 살리려 인덱스를 타고 필터를 걸러 나가거나, 필터 인덱스를 타고 나서 따로 정렬하거나를 고른다. 필터 컬럼 + 정렬 컬럼을 함께 담은 복합 인덱스가 있어야 둘 다 받쳐진다.
  • 정렬 방향 조합이 인덱스와 다르다. 다중 정렬에서 축마다 방향이 엇갈리면(a ASC, b DESC) 단순 정방향/역방향 스캔으로 커버되지 않는다.
  • 선택도가 낮아 플래너가 Seq Scan을 골랐다(10절). 이 경우엔 인덱스가 있어도 안 쓰는 것이 맞는 판단일 수 있으므로, 고쳐야 할 것은 인덱스가 아니라 쿼리에 요구되는 조건이다.

그리고 진단의 순서를 함께 말하면 좋다 — 느린 쿼리를 먼저 특정하고(pg_stat_statements), 그 쿼리의 실행계획을 보고(Sort Method), 그다음에 인덱스를 손댄다. 인덱스부터 추가하는 것은 8절의 영구 비용을 근거 없이 늘리는 일이다.

한 줄 요약
필터는 명시적 파라미터, 정렬은 통일된 형식, 검색은 q 하나로 분리하되 셋 다 서버가 허용 값을 화이트리스트로 제한한다 — 특히 정렬 키는 ① 인덱스 없는 컬럼 정렬이 실행계획에 Sort 노드를 만들고 work_mem을 넘으면 디스크 외부 병합 정렬로 떨어지는 DB 부하의 문이자, ② ORDER BY의 컬럼명은 바인딩 파라미터가 원리적으로 불가능해 문자열 조립일 수밖에 없다는 점에서 인젝션·내부 컬럼명 노출의 통로이자, ③ 한 번 열면 그 인덱스를 평생 유지해야 하는 공개 계약이므로, 허용 정렬 키 목록 = 인덱스 목록으로 관리하며 좁게 시작해 요구가 확인될 때만 넓히는 것이 API와 DB를 함께 쥐는 설계다.
