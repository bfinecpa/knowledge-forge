PUT vs PATCH
전체 교체와 부분 수정, 그리고 "안 보낸 필드가 null로 덮이는" 사고

면접 질문: "PUT과 PATCH의 차이는?"

핵심 관전 포인트 — PUT은 "보낸 표현으로 자원 전체를 교체(replace)"하는 메서드고 PATCH는 "보낸 내용만 부분 수정(partial update)"하는 메서드다. 이때 '메서드의 의미'는 내가 정하는 것이 아니라 HTTP 명세가 미리 정해둔 것이고(이것을 시맨틱이라 부른다), 그 약속을 믿고 캐시·프록시·재시도 라이브러리·상대 팀 클라이언트가 움직이기 때문에 서버가 마음대로 어기면 사고는 내 코드 밖에서 난다. 가장 실질적인 차이는 멱등성이다 — PUT은 본문에 최종 상태가 통째로 담겨 있어 몇 번을 보내도 결과가 같으므로 "응답을 못 받았을 때 그냥 재시도해도 되는" 메서드지만, PATCH는 명세가 멱등을 약속하지 않으므로 자동 재시도 대상이 아니다. 이 구분이 흐려지면 실무에서 "클라이언트가 안 보낸 필드가 null로 덮여 데이터가 유실되는" 사고가 API 계약 수준에서 발생한다 — 부분 수정을 PUT으로 받거나, PATCH에서 '필드를 아예 안 보냄'과 '필드에 null을 보냄'을 구분하지 못하는 구현이 그 범인이다. 이 3-way 구분을 살리는 선택지가 JsonNullable 래퍼, JSON Merge Patch(RFC 7386), JSON Patch(RFC 6902) 셋이며, 어느 쪽을 고르든 팀 컨벤션으로 못박아 API 문서에 명시하는 것까지가 계약을 다루는 태도다.
  • 1
    차이는 "몇 개를 보내느냐"가 아니라 "안 보낸 필드를 무엇으로 해석하느냐"다 — PUT에서 빠진 필드는 "없애라", PATCH에서 빠진 필드는 "건드리지 마라". 같은 본문이라도 메서드가 바뀌면 뜻이 정반대가 된다.
  • 2
    가장 실질적인 차이는 멱등성 = "응답을 못 받았을 때 그냥 다시 보내도 되는가" — PUT은 본문에 최종 상태가 통째로 담겨 있어 예, PATCH는 명세가 약속하지 않았으므로 아니오다. 내 PATCH가 우연히 멱등이어도 바깥 인프라는 그 사실을 알 방법이 없다.
  • 3
    사고는 JSON의 3상태가 서버에서 2상태로 뭉개질 때 난다 — 값 / null / 키 없음을 구분하려면 JsonNullable·Merge Patch·JSON Patch 중 하나를 고르고 문서에 명시해야 한다. 그리고 동시 수정으로 인한 lost update는 메서드가 아니라 ETag/If-Match로 푼다.

0. 질문 + 출제 의도

질문: "PUT과 PATCH의 차이는?"

출제 의도: 전체 교체와 부분 수정의 구분이 흐리면 "안 보낸 필드가 null로 덮이는" 데이터 유실이 API 계약 수준에서 발생한다. HTTP 메서드의 시맨틱(의미 약속)을 지키는 규율이 있는지 보는 표본 검사다 — 이 구분을 아는 사람은 다른 계약(상태 코드, 멱등성)도 지킬 확률이 높다.

이 페이지가 겨냥하는 약점 세 가지 ① "PUT은 전체, PATCH는 부분"에서 멈추는 것 → 1·2절에서 "빠진 필드의 해석"이라는 축으로 다시 세우고, 이 약속을 믿고 움직이는 바깥 주체 셋을 도식으로 보여준다.
② 사고를 "실수"로 설명하는 것 → 4·5절에서 Jackson 역직렬화가 어디서 null을 만드는지를 파이프라인으로 분해해, 계약 위반이 코드 실수처럼 보이는 이유를 짚는다.
③ PATCH로 바꾸면 끝났다고 생각하는 것 → 8·9절에서 '안 보냄'과 'null 보냄'이 뭉개지는 3상태 문제와 그 선택지 넷·결정 트리까지 내려간다. 여기가 변별점이다.

1. 시맨틱 — 이 약속을 믿는 것들

이 문서 전체에서 "시맨틱"이라는 말이 계속 나오므로 먼저 정의하고 가자. 시맨틱(semantics)은 문법(syntax)의 반대말로 "의미"를 뜻한다. HTTP 메서드의 시맨틱이란, 그 메서드를 쓴 요청이 서버에게 무엇을 시키는 것인지를 HTTP 명세(RFC 9110)가 미리 정해둔 의미를 말한다. PUT이라는 세 글자가 문법이라면, "이 URI의 자원을 본문 내용으로 교체하라"가 시맨틱이다.

여기서 어긋나기 시작한다 — 의미는 내가 정하는 게 아니다

@PutMapping이 붙은 메서드 안에서 무슨 코드를 쓰든 프레임워크는 막지 않는다. 그렇다고 PUT의 의미가 내가 짠 코드로 바뀌지는 않는다. 세상은 여전히 명세에 적힌 의미로 그 요청을 해석한다.

그러면 "세상"은 구체적으로 누구인가. 이 약속을 참으로 믿고 동작하는 것들의 목록이 곧 답이다 — 아래 도식의 셋이다.

2. 빠진 필드의 해석이 정반대다

두 메서드의 차이는 "몇 개 필드를 보내느냐"가 아니라 서버가 요청 본문을 무엇으로 해석하겠다고 약속하느냐다. 같은 본문이라도 메서드가 무엇이냐에 따라 뜻이 정반대가 된다.

이 한 줄만 외우면 2절은 끝난다

빠진 필드를 PUT은 지우고, PATCH는 남긴다

면접에서 "몇 개를 보내느냐"로 설명하면 절반짜리 답이다. "안 보낸 필드를 무엇으로 해석하는가"로 답해야 4절의 사고 시나리오와 8절의 3상태 문제까지 자연스럽게 이어진다.

PUT 전체 교체 — 빠진 필드는 제거
# 현재: {"name":"김철수","email":"kim@ex.com","phone":"010-1111-2222"}

PUT /users/42
{"name":"김철수", "email":"new@ex.com"}

# phone을 안 보냈다 = "phone은 없다"고 선언한 것
# 결과: {"name":"김철수","email":"new@ex.com","phone":null}
PATCH 부분 수정 — 빠진 필드는 보존
# 현재: {"name":"김철수","email":"kim@ex.com","phone":"010-1111-2222"}

PATCH /users/42
{"email":"new@ex.com"}

# 보낸 email만 바뀐다
# 결과: {"name":"김철수","email":"new@ex.com","phone":"010-1111-2222"}

3. 멱등성 — 실무 질문은 "재시도해도 되는가"다

멱등(idempotent)은 "같은 요청을 1번 보내든 N번 보내든 서버의 최종 상태가 같다"는 성질이다. 낯선 한자어인 멱등(冪等)은 수학에서 왔다 — 거듭 적용해도 결과가 더 이상 변하지 않는 연산, 즉 f(f(x)) = f(x)를 뜻한다. 절댓값이 딱 그렇다. abs(-3)도 3이고 abs(abs(-3))도 3이라 몇 번을 씌워도 값이 그대로다.

여기까지는 정의일 뿐이고, 이 개념이 실무에서 왜 중요한지는 질문을 바꿔 던져야 드러난다.

"요청은 보냈는데 응답을 못 받았다. 다시 보내도 되는가?"

서버가 에러를 돌려주는 것은 오히려 다행이다 — 무엇이 잘못됐는지 알려주니까. 진짜 곤란한 것은 아무 응답도 못 받은 상태다. 이때 클라이언트가 아는 것은 "내가 요청을 보냈고 응답이 안 왔다"는 사실 하나뿐이고, 모르는 것은 "서버가 그 요청을 처리했는가"다.

가능한 세계 ①
요청이 서버에 도달조차 못 했다 → 미처리
가능한 세계 ②
도달해서 처리됐는데 응답이 유실됐다 → 처리됨
가능한 세계 ③
지금 서버가 처리하는 중이다 → 곧 처리됨
세 세계를 구분할 방법이 없다는 것이 문제의 본질 이 불확실성 앞에서 클라이언트가 할 수 있는 선택은 둘뿐이다 — 포기하거나, 다시 보내거나. 그런데 다시 보냈다가 실제로는 ②였다면 같은 작업이 두 번 실행된다. 멱등성이 정확히 이 갈림에서 답을 준다 — 요청이 멱등하면 ②였더라도 한 번 더 보낸 결과가 같으므로 "모르는 채로 그냥 다시 보내도" 안전하다. 즉 멱등성은 "재시도해도 되는가"라는 질문의 다른 이름이다.

PUT은 멱등하다 — 절대 좌표

  • 근거는 "본문에 최종 상태가 통째로 담겨 있기 때문"이다.
  • "42번 사용자를 이 내용으로 만들어라"는 명령은 목적지를 절대 좌표로 지정한 것과 같아서 몇 번을 실행해도 같은 자리에 도착한다.
  • 그래서 네트워크 오류로 응답을 못 받은 클라이언트가 안심하고 재시도할 수 있다.

PATCH는 멱등이 보장되지 않는다

  • PATCH는 "부분 수정"이라는 틀만 정하고 수정 내용의 성질은 정하지 않는다.
  • 본문에 절대값을 담으면 멱등이고, 상대 연산을 담으면 비멱등이다 — 같은 메서드인데 본문이 성질을 바꾼다.
  • 명세가 약속하지 않았으므로 인프라는 PATCH를 자동 재시도 대상으로 취급하지 않는다.
멱등 절대값을 지정하는 PATCH
PATCH /users/42   {"email": "new@ex.com"}

1회 후 new@ex.com
2회 후 new@ex.com
3회 후 new@ex.com   → 최종 상태 동일
비멱등 상대 연산을 지정하는 PATCH
PATCH /users/42   {"op":"increment", "field":"point", "by":100}

1회 후 +100
2회 후 +200
3회 후 +300   → 최종 상태가 달라진다

말을 정확히 골라야 하는 지점 감점 포인트

"PATCH는 절대 멱등이 아니다" — 틀린 설명
"구현이 멱등일 수는 있지만, 클라이언트와 인프라가 멱등이라고 가정해서는 안 되는 메서드" — 정확한 설명

메서드별 안전성·멱등성 전체 표와 재시도 판단(connection timeout vs read timeout), 멱등성 키 구현은 8장 04번·9장 06번 문서의 주제다. 이 문서는 PUT/PATCH 구현 선택에 집중한다.

4. 사고 재현 — "안 보낸 필드가 null로 덮였어요"

가장 흔한 사고는 부분 수정 화면을 PUT(또는 PUT처럼 동작하는 구현)으로 처리할 때 난다. 시나리오는 이렇다 — 회원 정보에 name, email, marketingAgreed(마케팅 수신 동의)가 있다. 앱의 "이메일 변경" 화면은 이메일 입력칸 하나뿐이라 email만 보낸다.

Before 부분 수정 요청을 전체 교체처럼 처리 — 데이터 유실
@PutMapping("/users/{id}")
public void update(@PathVariable Long id, @RequestBody UserUpdateRequest req) {
    User user = userRepository.findById(id).orElseThrow();

    // 요청 본문에 없던 필드는 DTO에서 null(또는 false)로 남아 있는데,
    // 아래 세 줄은 그 값을 그대로 엔티티에 덮어쓴다.
    user.setName(req.getName());                       // null로 덮임 이름 소멸
    user.setMarketingAgreed(req.getMarketingAgreed()); // null 또는 false로 덮임 동의 해제
    user.setEmail(req.getEmail());
}
이 버그가 위험한 이유 — 아무 신호도 남지 않는다 이메일만 바꿨는데 이름이 사라지고 마케팅 동의가 풀린다. 컴파일 에러도, 런타임 예외도 없이 조용히 데이터를 갉아먹다가 "동의한 적 있는데 왜 해제됐냐"는 CS로 발견된다. 그때는 이미 며칠치 데이터가 덮여 있고 원본이 없으니 복구도 어렵다.
원인은 코드가 아니라 계약 위반이다 — 클라이언트는 부분 수정(PATCH 시맨틱)을 기대했는데 서버는 전체 교체(PUT 시맨틱)로 처리했다.
After 부분 수정은 PATCH로 받고, 보낸 필드만 반영한다
@PatchMapping("/users/{id}") ① 이름을 동작에 맞춘다
public void patch(@PathVariable Long id, @RequestBody UserPatchRequest req) {
    User user = userRepository.findById(id).orElseThrow();

    // null 체크가 곧 "이 필드가 요청에 실려 왔는가"의 판정 역할을 한다.
    // 실려 오지 않은 필드는 건드리지 않으므로 기존 값이 보존된다.
    if (req.getName() != null)  user.setName(req.getName()); ② 동작을 이름에 맞춘다
    if (req.getEmail() != null) user.setEmail(req.getEmail());
    if (req.getMarketingAgreed() != null) {
        user.setMarketingAgreed(req.getMarketingAgreed());
    }
}
①과 ②는 한 세트다 메서드를 PATCH로 바꾼 것과 if (… != null)을 넣은 것은 반드시 같이 가야 한다. 둘 중 하나만 하면 여전히 이름과 동작이 어긋난다 — 6절과 10절의 "가짜 PATCH / 가짜 PUT"이 정확히 그 상태다. 그리고 이 구현에도 남은 구멍이 있다(8절).

5. 왜 null이 되는가 — 역직렬화가 하는 일

역직렬화(deserialization)는 네트워크로 도착한 JSON 문자열을 Java 객체로 되돌리는 과정이다. 반대 방향, 즉 Java 객체를 JSON 문자열로 바꾸는 것이 직렬화(serialization)다. Spring에서는 @RequestBody가 붙는 순간 Jackson 라이브러리가 이 일을 대신해 준다.

여기서 핵심은 Jackson이 "JSON에 없는 키"를 만났을 때 하는 일이 "아무것도 안 하는 것"이라는 점이다. 그 필드에는 값을 세팅하지 않고 지나가므로, 필드는 자바가 객체를 만들 때 넣어둔 기본값 그대로 남는다.

boolean과 Boolean — 같은 사고인데 한쪽은 흔적조차 없다

Boolean marketingAgreed
기본값 null. DB에 NOT NULL 제약이 있으면 제약 위반으로 터지기라도 한다 — 시끄럽지만 발견은 된다.
boolean marketingAgreed
기본값 false. NOT NULL에도 안 걸리고 정상적인 값처럼 보여서 조용히 "동의 해제"로 저장된다. 아무 신호도 남지 않는다.

그래서 요청 DTO의 필드는 원시 타입(boolean, int, long) 대신 래퍼 타입으로 선언한다. "값이 안 왔다"를 표현할 수 있는 타입이어야 구분 자체가 가능해지기 때문이다.

6. 반대 방향의 규율 — "친절한 PUT"이 계약을 무너뜨린다

여기까지 읽으면 "그럼 PUT에서도 null이면 건너뛰게 하면 되지 않나?"라는 생각이 든다. 안 된다. 그렇게 만든 PUT은 이름만 PUT인 PATCH다.

PUT을 제공한다면 지켜야 하는 두 문장

클라이언트는 항상 전체 표현을 보낸다  ·  서버는 빠진 필드를 "유지"가 아니라 "제거/초기화"로 처리한다

이 둘이 지켜질 때만 PUT이다. 빠진 필드를 적당히 유지해주는 "친절한 PUT"은 당장은 사고를 막아주는 것처럼 보이지만 더 나쁜 결과를 만든다.

1
클라이언트가 필드를 지울 방법이 사라진다. 사용자가 전화번호 입력칸을 비우고 저장했다고 하자. 클라이언트는 phone을 빼고 보내거나 null로 보낼 텐데, 친절한 PUT은 둘 다 "유지"로 처리해 버린다.
2
화면과 서버가 어긋난다. 사용자 화면에는 지워졌는데 서버에는 그대로 남는다. 다음 조회에서 되살아난 전화번호를 보고 사용자는 "저장이 안 됐다"고 판단한다.
3
클라이언트마다 해석이 갈라진다. 어떤 팀은 빈 문자열 ""을 보내 지우려 하고, 어떤 팀은 별도 삭제 API를 요구한다. 계약이 무너지는 것이 이 지점이다 — 같은 API를 쓰는 팀마다 다른 규칙을 각자 발명하기 시작한다.

7. PUT의 또 다른 대가 — lost update

전체 교체에는 사고 하나가 더 딸려 온다. lost update(갱신 유실)는 두 사람이 같은 자원을 각자 읽어 각자 수정한 뒤 저장했을 때, 나중에 저장한 쪽이 앞사람의 수정을 덮어써 앞사람의 변경이 흔적 없이 사라지는 현상이다. 이름 그대로 갱신이 유실된다. 에러도, 경고도, 로그도 남지 않는다는 것이 이 현상의 무서운 점이다.

8. 3상태 문제 — "안 보냄"과 "null로 지워라"의 구분

4절의 After 코드에도 남은 구멍이 있다. if (req.getX() != null) 방식은 "필드를 아예 안 보냈다"와 "필드를 null로 지워달라"를 구분하지 못한다. JSON 쪽에서는 이 셋이 분명히 다른 표현인데도 그렇다.

JSON이 말할 수 있는 세 가지 — 이 규칙이 이 절 전체의 축이다

값 = 바꿔  ·  널 = 지워  ·  무(키 없음) = 놔둬

그런데 5절에서 봤듯이 Jackson은 "키가 없으면 아무것도 안 한다". 그래서 평범한 DTO로 받으면 뒤의 두 경우가 똑같이 phone == null이 되어 구분이 사라진다.

그래서 설계 단계에서 먼저 던져야 할 질문은 하나다 "이 자원에 지울 수 있는(nullable) 필드가 있는가?" — 이 문제는 nullable 필드가 하나라도 있는 순간 생긴다. 반대로 모든 필드가 NOT NULL이고 "지우기"가 애초에 없는 API라면 평범한 DTO로도 충분하다. 없는 문제를 미리 풀 필요는 없다.

뒤로 갈수록 표현력이 커지고 클라이언트 비용도 커진다. 그리고 셋은 요청 본문의 모양부터 다르다 — 이것이 선택의 실질적 기준이 된다.

9-1. 선택지 ① JsonNullable 래퍼 필드

무엇인가. 필드 타입을 값 자체가 아니라 래퍼로 감싸서, "값이 실려 왔는가"와 "실려 온 값이 null인가"를 별개의 두 정보로 분리해 담는 방법이다. 대표적인 구현이 OpenAPI Generator가 쓰는 org.openapitools.jackson.nullable.JsonNullable이다. 요청 본문의 모양은 하나도 바뀌지 않고 서버 DTO의 타입만 바뀐다.

DTO 상태를 셋으로 구분하는 타입
public class UserPatchRequest {
    // JsonNullable은 상태를 셋으로 구분한다.
    //   undefined()   : 요청 본문에 이 키가 없었다      → 건드리지 마라
    //   of(null)      : 키가 있었고 값이 null이었다      → 지워라
    //   of("010-...") : 키가 있었고 값이 있었다          → 이 값으로 바꿔라
    private JsonNullable<String> phone = JsonNullable.undefined(); 초기값이 핵심

    public JsonNullable<String> getPhone() { return phone; }
}
적용 isPresent()가 묻는 것은 "키가 있었는가"다
// isPresent()는 "값이 null인가"가 아니라 "키가 본문에 있었는가"를 묻는다.
// 그래서 명시적으로 보낸 null도 통과하고, 아래 get()이 null을 돌려준다.
if (req.getPhone().isPresent()) {
    user.setPhone(req.getPhone().get());   // null이면 그대로 null로 설정 = 지우기
}
Optional로 대신하려는 시도는 권하지 않는다 함정 쓰려면 Jackson에 JsonNullableModule을 등록해야 한다. 그리고 Optional로 대신하면 기본 설정에서 명시적 null은 Optional.empty()가 되고 키가 없으면 필드 자체가 null로 남아서, "필드가 null이면 안 보낸 것, Optional.empty()면 null을 보낸 것"이라는 헷갈리는 3상태가 된다. 의도를 이름으로 드러내는 JsonNullable 쪽이 읽기 쉽다.

언제 고르나. 기존 JSON 계약(본문 모양)을 전혀 바꾸지 않고 3-way 구분만 살리고 싶을 때다. 클라이언트는 하던 대로 {"phone": null}을 보내면 되고 서버 DTO의 타입만 바뀌므로 도입 비용이 가장 낮다. 필드가 몇 개 안 되는 일반적인 CRUD API에서는 이 선택이 가장 현실적이다.

9-2. 선택지 ② JSON Merge Patch (RFC 7386)

무엇인가. "null = 제거, 키 없음 = 유지"라는 해석 규칙 자체를 표준 문서로 못박은 포맷이다. JsonNullable이 "우리 서버는 이렇게 해석하기로 했다"는 팀 내부의 약속이라면, Merge Patch는 RFC 번호가 붙은 공용 약속이다. 그래서 클라이언트에게 "우리는 RFC 7386을 따른다"는 한 줄로 해석 규칙 전체를 전달할 수 있다.

요청 본문 모양은 평범한 JSON, Content-Type이 다르다
PATCH /users/42
Content-Type: application/merge-patch+json

{"email": "new@ex.com", "phone": null}

# 해석: email은 이 값으로 바꾸고, phone은 제거하고, 나머지 필드는 그대로 둔다
구현 DTO 대신 JSON 트리로 받아 키의 존재 여부를 직접 다룬다
@PatchMapping(path = "/users/{id}", consumes = "application/merge-patch+json")
public void patch(@PathVariable Long id, @RequestBody JsonNode patch) throws IOException {
    User user = userRepository.findById(id).orElseThrow();

    // 엔티티에 직접 병합하지 않는다. 클라이언트가 role이나 balance처럼
    // 수정하면 안 되는 필드를 본문에 끼워 넣어도 그대로 반영되기 때문이다.
    UserPatchView view = mapper.convertValue(user, UserPatchView.class); 화이트리스트

    // readerForUpdating은 patch에 실제로 존재하는 키만 view에 덮어쓴다.
    // 없는 키는 건드리지 않고, null인 키는 null로 설정한다 — 곧 Merge Patch 시맨틱이다.
    mapper.readerForUpdating(view).readValue(patch);

    validator.validate(view);   // 병합 후에 검증해야 "최종 상태"를 검사하게 된다 순서 중요
    user.applyFrom(view);
}
한계도 알고 골라야 한다 null에 "제거"라는 의미를 부여했으므로 필드를 진짜 null 값으로 설정하는 것과 제거를 구분할 수 없다. 그리고 배열은 원소별 병합이 아니라 통째로 교체된다 — 태그 목록에서 한 개만 빼고 싶어도 전체 배열을 다시 보내야 한다.

언제 고르나. 자원이 문서에 가까운 형태(중첩 객체가 있고 부분 갱신이 잦은)이고, 해석 규칙을 표준으로 못박아 여러 클라이언트에 동일하게 전달하고 싶을 때다.

9-3. 선택지 ③ JSON Patch (RFC 6902)

무엇인가. 본문을 "바뀐 상태"가 아니라 "수행할 연산의 목록"으로 보내는 포맷이다. 앞의 둘이 "결과를 그려서 보내는" 방식이라면, 이쪽은 "수정 지시서를 명령문으로 적어 보내는" 방식이다. 본문이 객체가 아니라 연산 객체의 배열이라 모양부터 완전히 다르다.

요청 연산 객체의 배열
PATCH /users/42
Content-Type: application/json-patch+json

[
  {"op": "replace", "path": "/email",   "value": "new@ex.com"},
  {"op": "remove",  "path": "/phone"},
  {"op": "add",     "path": "/tags/-",  "value": "vip"},   // /tags/- 는 배열의 끝
  {"op": "test",    "path": "/version", "value": 7}       // 조건 검사
]
연산 여섯 가지
add · remove · replace · move · copy · test. path는 JSON Pointer(RFC 6901) 표기법으로 문서 안의 위치를 가리킨다.
요청 단위 원자성
연산은 적힌 순서대로 적용되고, 하나라도 실패하면 전체를 적용하지 않는 것이 규칙이다.
앞의 둘이 못 하던 일 ①
배열의 특정 원소만 추가·삭제·이동할 수 있다.
앞의 둘이 못 하던 일 ②
test 연산으로 "이 필드가 이 값일 때만 적용해라"는 조건을 요청 본문 안에 담을 수 있다.
test는 If-Match의 대체재가 아니다 test는 7절의 lost update 대응을 본문 수준에서 흉내 내는 셈인데, HTTP 계층의 표준 수단은 어디까지나 If-Match이므로 그쪽을 우선한다. 캐시·프록시·게이트웨이가 이해하는 것은 헤더이지 본문이 아니기 때문이다.
대가는 클라이언트 비용이다. 클라이언트가 "무엇을 바꿀지"가 아니라 "어떤 연산을 어떤 경로에 적용할지"를 조립해야 하고, 서버도 별도 라이브러리(jakarta.json의 Json.createPatch, 또는 com.github.java-json-tools:json-patch)를 물어야 한다. 사람이 눈으로 읽기도 앞의 둘보다 어렵다.

언제 고르나. 배열 원소 단위 편집이 필요하거나, 협업 편집·감사 로그처럼 "무엇을 어떻게 바꿨는지"를 연산 단위로 기록하고 재생해야 할 때다. 일반적인 회원 정보 수정에는 과하다.

9-4. 무엇을 고를 것인가

표현력이 커질수록 클라이언트 비용도 커진다. 표에서 값이 나가는 줄은 "요청 본문 모양"이다 — 계약을 바꾸는지 아닌지가 여기서 갈린다.
방식표현할 수 있는 것요청 본문 모양클라이언트 비용언제 고르나
평범한 DTO + null 체크값 설정만{"email":"..."}없음nullable 필드가 없고 "지우기"가 필요 없는 API
JsonNullable 래퍼값 설정 + 명시적 제거위와 동일 — 본문이 안 바뀐다없음기존 계약을 유지하며 3-way만 살릴 때 — 가장 현실적
JSON Merge Patch값 설정 + 제거 + 중첩 객체 병합{"phone": null} + 전용 Content-Type낮음문서형 자원, 해석 규칙을 표준으로 못박고 싶을 때
JSON Patch위 전부 + 배열 원소 조작·이동·조건부[{"op":"remove","path":"/phone"}]높음배열 편집, 연산 단위 기록·재생이 필요할 때

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

한 문장 차이?
빠진 필드를 PUT은 지우고, PATCH는 남긴다. 차이는 "몇 개를 보내느냐"가 아니라 "안 보낸 필드의 해석"이다.
멱등성의 실무 질문?
"응답을 못 받았을 때 그냥 다시 보내도 되는가." PUT은 예(본문에 최종 상태가 통째로), PATCH는 명세가 약속하지 않음.
PATCH 멱등, 정확한 표현?
"절대 멱등이 아니다"는 틀린 설명. "구현은 멱등일 수 있지만 클라이언트·인프라가 가정해서는 안 되는 메서드"가 정답.
null은 어디서 생기나?
Jackson이 없는 키를 건드리지 않아 자바 기본값이 남고, 그것이 엔티티로 복사된다. boolean이면 false라 신호조차 없다.
JSON 3상태 규칙?
값 = 바꿔 · 널 = 지워 · 무 = 놔둬. 평범한 DTO는 뒤의 둘을 하나로 뭉갠다.
3-way 선택지 넷?
무 · 래 · 병 · 연 — 평범 DTO / JsonNullable / Merge Patch(7386) / JSON Patch(6902).
"친절한 PUT"이 왜 나쁜가?
클라이언트가 필드를 지울 방법이 사라진다. 그러면 팀마다 ""·별도 삭제 API 등 규칙을 각자 발명하기 시작한다.
lost update 해결은?
메서드가 아니라 ETag + If-Match. 버전이 다르면 412 Precondition Failed. PATCH는 범위를 줄일 뿐이다.
설계할 때 첫 질문?
"이 자원에 지울 수 있는(nullable) 필드가 있는가?" 없으면 평범한 DTO로 충분하다.

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

PUT은 멱등한데 POST는 왜 멱등하지 않나요? 필수힌트: "누가 URI를 정하는가"로 답을 시작하면 한 번에 정리된다

차이는 "누가 URI를 정하는가"에서 온다.

POST /orders는 "컬렉션에 새 자원을 추가하라"는 요청이고, 만들어질 자원의 URI를 서버가 정한다. 그래서 호출할 때마다 서로 다른 새 자원이 생긴다 — 두 번 보내면 주문이 2건이다. 반면 PUT /orders/42는 URI가 이미 42로 못박혀 있고 "그 자리를 이 상태로 만들어라"는 요청이므로, 몇 번을 반복해도 최종 상태가 같다.

이 차이는 실무에서 재시도 정책으로 직결된다. 타임아웃이 났을 때 PUT은 그냥 재시도해도 되지만, POST 재시도는 곧 중복 생성이다.

결제·주문처럼 꼭 재시도가 필요한데 본질적으로 비멱등인 작업에는 서버가 멱등성을 직접 부여해야 한다

그 장치가 멱등성 키다 — 클라이언트가 시도마다가 아니라 "논리적 작업 1건마다" 고유 키를 만들어 보내고, 서버가 그 키로 중복을 흡수한다(06-idempotency-key-design.md).

값을 지정하는 PATCH는 사실상 멱등인데, 왜 "멱등이 아니다"라고 하나요? 필수힌트: 멱등성이 "요청의 성질"인지 "메서드의 계약"인지를 먼저 가른다

멱등성은 개별 요청의 우연한 성질이 아니라 메서드 단위의 계약이기 때문이다.

HTTP 명세가 PATCH에 멱등을 약속하지 않았으므로, 프록시·클라이언트 라이브러리·재시도 미들웨어는 "PATCH는 재시도하면 위험할 수 있다"를 전제로 동작한다. 이들은 내 PATCH 핸들러의 코드를 읽어볼 수 없다. 내 PATCH가 우연히 멱등이더라도 그건 명세가 아니라 구현 사정이므로 바깥에서는 알 방법이 없다(1절 도식의 붉은 점선).

그래서 "재시도해도 안전하다"를 계약으로 보장받고 싶다면 길은 둘뿐이다 — ① 전체 교체가 가능한 상황이면 PUT을 쓴다. ② 그럴 수 없으면 멱등성 키를 도입해 서버가 직접 중복을 흡수한다.

PUT으로 자원 생성도 가능한가요?힌트: 가능하다. 조건 하나와 응답 코드 구분까지 말하면 완성

가능하다 — 단, 클라이언트가 URI(식별자)를 결정할 수 있을 때다.

PUT /users/42/profile-image처럼 자원의 자리가 미리 정해져 있는 경우, 그 자리에 아직 아무것도 없으면 만들고 이미 있으면 갈아끼우면 된다. 이렇게 없으면 insert, 있으면 update로 동작하는 것을 upsert 시맨틱이라고 부른다(update + insert의 합성어다).

201 Created
그 자리에 새로 만들었을 때. Location 헤더로 자원 위치를 알려준다.
200 OK / 204 No Content
기존 것을 교체했을 때. 최종 표현을 함께 주면 200, 본문 없이 끝내면 204.

반면 서버가 ID를 발급하는 일반적인 생성(/orders에 새 주문 추가)은 클라이언트가 URI를 모르므로 PUT을 쓸 수 없고 POST를 쓴다. 굳이 PUT으로 하고 싶다면 클라이언트가 UUID를 만들어 PUT /orders/{uuid}로 보내는 설계도 가능한데, 이 경우 재시도가 안전해진다는 이점이 따라온다 — 같은 UUID로 다시 보내도 같은 자리를 덮어쓸 뿐이라 주문이 두 건 생기지 않는다.

그럼 수정 API는 무조건 PATCH로 만드는 게 좋은가요? 시니어 변별힌트: 판단 기준 한 줄을 먼저 제시하고, 마지막에 "메서드로 안 풀리는 것"을 얹는다

트레이드오프가 있다.

PUT의 강점

  • 시맨틱이 단순하다 — 보낸 것이 곧 최종 상태.
  • 멱등이라 재시도가 안전하다.
  • 서버 구현도 조건 분기 없이 통째로 덮어쓰면 끝이다.
  • "설정 저장"처럼 클라이언트가 항상 전체 상태를 들고 있는 화면에는 오히려 깔끔하다.

PATCH의 강점

  • 부분 수정 화면이 여러 개일 때 각 화면이 자기 필드만 보내면 된다.
  • 서로 다른 필드를 고치는 동시 요청끼리 덮어쓰지 않는다 — PUT 둘이 교차하면 한쪽 수정이 통째로 증발하지만(7절), PATCH는 그 경우가 줄어든다.
나의 기준: "클라이언트가 전체 표현을 신뢰성 있게 갖고 있는가" — 갖고 있으면 PUT, 화면이 쪼개져 있거나 필드가 많아 일부만 아는 상태면 PATCH

여기에 한 줄을 더 얹으면 판단이 완성된다. 어느 쪽이든 동시 수정이 진짜 문제라면 메서드 선택으로는 풀리지 않는다. PATCH는 lost update의 발생 범위를 줄일 뿐 없애지 못하므로, 같은 필드를 동시에 고치는 경우까지 막으려면 ETag/If-Match 기반의 낙관적 동시성 제어로 가야 한다(12-etag-if-match-optimistic-concurrency.md).

@PatchMapping만 붙이면 부분 수정이 되는 건가요? 함정힌트: 애너테이션이 하는 일의 범위를 정확히 말한다. 그리고 클라이언트 쪽 함정도 하나 있다

안 된다. 애너테이션은 라우팅만 담당하고, 부분 수정 시맨틱은 전적으로 구현 책임이다. @PatchMapping이 하는 일은 "PATCH 메서드로 이 경로에 들어온 요청을 이 자바 메서드로 보내라"가 전부다. 그 안에서 무슨 짓을 하는지는 검사하지 않는다.

가짜 PATCH 이름만 PATCH인 PUT
@PatchMapping("/users/{id}")
public void fakePatch(@PathVariable Long id,
                      @RequestBody UserRequest req) {
    User user = repo.findById(id).orElseThrow();
    user.setName(req.getName());   // null로 덮인다
    user.setEmail(req.getEmail());
}
// 4절의 null 덮어쓰기 사고가 그대로 재현된다
가짜 PUT 이름만 PUT인 PATCH
@PutMapping("/users/{id}")
public void fakePut(@PathVariable Long id,
                    @RequestBody UserRequest req) {
    User user = repo.findById(id).orElseThrow();
    if (req.getName() != null) user.setName(...);
    if (req.getEmail() != null) user.setEmail(...);
}
// 클라이언트가 필드를 지울 방법이 사라진다 (6절)
메서드 이름과 실제 동작이 어긋난 API가 계약 사고의 진원지다 — 클라이언트 개발자는 코드를 볼 수 없고 이름만 보고 자기 구현을 만든다

덧붙여 클라이언트 쪽에도 함정이 하나 있다. RestTemplate의 기본 요청 팩토리인 SimpleClientHttpRequestFactory는 JDK의 HttpURLConnection을 쓰는데, 이 클래스가 허용하는 메서드 목록에 PATCH가 없어 호출하면 ProtocolException이 난다. Apache HttpClient 기반 팩토리로 바꾸거나, java.net.http.HttpClient를 쓰는 RestClient·WebClient를 쓰면 해결된다. "PATCH를 붙였는데 안 된다"는 문의의 상당수가 서버가 아니라 여기서 나온다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

PATCH 요청 DTO에 @NotBlank·@NotNull을 그대로 걸면 어떻게 되나요? 함정힌트: 검증의 대상이 "요청 본문"인지 "병합 후 최종 상태"인지가 갈림길이다

안 보낸 필드가 전부 검증 실패로 400을 맞는다. 부분 수정 요청은 일부 필드만 담고 오는 것이 정상인데, 필드 단위 필수 제약을 요청 DTO에 그대로 걸면 "이름을 안 보냈다"는 정상 상황이 오류로 처리된다.

원인은 검증 대상을 잘못 잡은 것이다. PATCH에서 검증해야 하는 것은 요청 본문 자체가 아니라 "병합이 끝난 뒤의 최종 상태"다. 그래서 9-2의 Merge Patch 구현에서 validator.validate(view)를 병합 이후에 호출한 것이다 — 순서가 곧 의미다.

PATCH의 검증 순서: 현재 상태 로드 → 요청 병합 → 최종 상태 검증 → 저장

요청 DTO에 남겨도 되는 제약은 "값이 왔다면 지켜야 할 조건"뿐이다 — @Email, @Size, @Pattern처럼 값이 null이면 통과하는 제약은 그대로 둬도 안전하다. 반대로 필수 여부(@NotNull·@NotBlank)는 최종 상태 쪽으로 옮긴다.

PUT·PATCH의 응답으로는 무엇을 돌려줘야 하나요?힌트: PATCH에서 본문을 돌려주는 것이 특히 값을 하는 이유가 있다

선택지는 셋이다 — 200 OK + 최종 표현, 204 No Content, (PUT으로 새로 만들었다면) 201 Created + Location.

PATCH에서는 최종 표현을 돌려주는 쪽이 특히 유용하다. 이유가 둘 있다.

① 클라이언트 재동기화
클라이언트는 자기가 보낸 필드만 안다. 서버가 병합 결과 전체를 돌려주면 추가 GET 없이 화면을 정확히 맞출 수 있다 — 서버 계산값(수정시각, 파생 필드)까지 한 번에 온다.
② ETag 갱신
응답에 새 ETag를 같이 실어주면 클라이언트가 다음 수정에 쓸 버전을 바로 얻는다. 이게 없으면 수정할 때마다 GET을 한 번 더 해야 한다(7절).

주의할 점: 응답 본문에 수정 대상이 아닌 민감 필드까지 그대로 노출하지 않도록, 9-2의 UserPatchView처럼 노출 전용 표현을 통해 내보낸다.

JPA 더티 체킹을 쓰면 부분 수정이 자동으로 되는 것 아닌가요? 함정힌트: 더티 체킹이 비교하는 대상이 무엇인지 정확히 말한다

아니다. 더티 체킹은 이 문제에 대해 아무 방어도 해주지 않는다.

더티 체킹이 비교하는 것은 "요청 본문에 그 키가 있었는가"가 아니라 "엔티티 필드 값이 스냅샷과 달라졌는가"다. user.setName(null)을 호출해 기존 값이 null로 바뀌면 그것도 정상적인 변경으로 감지되어 UPDATE문에 그대로 포함된다. 즉 더티 체킹은 사고를 막는 게 아니라 사고를 성실히 DB에 반영한다.

더티 체킹이 실제로 해주는 일은 "바뀐 필드가 하나도 없으면 UPDATE를 아예 안 보내는 것"과 (설정에 따라) "바뀐 컬럼만 SET에 넣는 것"까지다. 무엇을 바꿀지 결정하는 책임은 여전히 애플리케이션 코드에 있다 — 그 결정 지점이 4절의 if (… != null)이고 8절의 3상태 판정이다.

필드가 서른 개인데 if (x != null)을 서른 번 쓰나요?힌트: 반복을 줄이는 것과 3상태를 살리는 것은 다른 문제다

반복 자체는 매퍼로 줄일 수 있다. MapStruct처럼 "소스 필드가 null이면 대상 필드를 건드리지 않는" 매핑 전략을 제공하는 도구를 쓰면 조건문이 사라진다. 스프링의 BeanUtils.copyProperties에 무시할 프로퍼티 목록을 넘기는 방식도 쓰인다.

그러나 이것은 "코드량 문제"만 푼 것이다 null을 무시하는 매퍼는 8절의 3상태 문제를 그대로 갖고 있다 — "지워라"를 여전히 "놔둬"로 해석한다. 오히려 조건문이 사라져 문제가 눈에 안 보이게 되므로 더 위험할 수 있다.

그래서 판단은 두 단계다 — ① 지울 수 있는 필드가 없다면 매퍼로 줄이면 되고, ② 지울 수 있는 필드가 있다면 필드가 몇 개든 JsonNullable이나 Merge Patch로 가야 한다. 특히 필드가 서른 개나 되는 자원이라면 Merge Patch처럼 JSON 트리 단위로 병합하는 쪽이 필드마다 코드를 쓰지 않아도 되므로 더 잘 맞는다.

주문을 취소할 때 PATCH로 status를 CANCELED로 바꾸면 되나요? 시니어 변별힌트: "필드 값 하나가 바뀌는 일"과 "부작용을 동반하는 상태 전이"는 다른 종류다

겉모습은 필드 하나 수정이지만, 실제로 벌어지는 일은 필드 수정이 아니다. 주문 취소에는 보통 환불, 재고 복원, 쿠폰 반환, 알림 발송 같은 부작용이 딸리고, "결제 완료 상태에서만 취소 가능" 같은 전이 규칙도 있다.

이것을 PATCH /orders/42 {"status":"CANCELED"}로 노출하면 문제가 생긴다.

허용되지 않는 전이가 열린다
클라이언트가 임의의 status 문자열을 보낼 수 있으므로, 서버는 결국 전이 규칙 분기를 status 값으로 다시 짜야 한다 — "부분 수정"이라는 겉모습만 남는다.
필요한 입력을 받을 곳이 없다
취소 사유·환불 계좌처럼 그 전이에만 필요한 파라미터를 자원 표현에 억지로 끼워 넣게 된다.
기준: "값이 바뀌는 것"이면 PATCH, "무슨 일이 일어나는 것"이면 별도 액션

그래서 이런 전이는 POST /orders/42/cancellation처럼 전이를 하나의 자원·액션으로 노출하는 쪽이 낫다. 이렇게 하면 허용된 전이만 API 표면에 존재하고, 필요한 입력을 그 요청 본문에서 받을 수 있으며, POST이므로 재시도 안전성은 멱등성 키로 따로 설계하면 된다. 자원 이름 짓기와 액션 표현은 01-restful-design-principles-resource-naming.md의 주제다.

한 줄 요약
PUT은 "본문이 곧 자원의 완전한 최종 상태"인 전체 교체(멱등 — 응답을 못 받아도 재시도 가능), PATCH는 "보낸 것만 바꾸는" 부분 수정(멱등 비보장 — 자동 재시도 대상이 아님)이며, 이 시맨틱이 흐려지는 순간 "안 보낸 필드가 null로 덮이는" 데이터 유실이 계약 수준에서 발생한다 — 그래서 부분 수정은 PATCH로 받고, nullable 필드가 있다면 '안 보냄'과 'null 보냄'을 구분하는 수단(JsonNullable · Merge Patch · JSON Patch)을 고른 뒤 그 선택을 문서에 명시하며, 동시 수정으로 인한 lost update는 메서드가 아니라 ETag/If-Match로 푸는 것까지가 이 질문의 완성형이다.
