API 에러 응답 바디 표준화
에러 스키마는 성공 응답과 동급의 계약이다

면접 질문: "API 에러 응답 바디는 어떻게 표준화하나요?"

핵심 관전 포인트 — 에러 응답은 "예외 상황의 부산물"이 아니라 소비자가 매일 받는 정상 트래픽이므로, 성공 응답과 똑같이 하나의 스키마로 고정된 계약이어야 한다. 스키마의 뼈대는 축을 둘로 나누는 것이다 — HTTP status는 게이트웨이·프록시·모니터링·재시도 로직처럼 바디를 파싱하지 않는 소비자가 읽는 축이고(그래서 "재시도해도 되나"를 여기서 판단한다), 에러 code는 "잔액 부족인지 한도 초과인지"처럼 status가 담을 수 없는 세부 구분을 클라이언트 분기에 전달하는 축이다. 어느 한 축만으로는 안 된다. 여기에 사람이 읽는 message, 검증 실패용 필드 상세 배열, 분산 추적의 진입점인 traceId를 더하면 뼈대가 완성된다. 에러 코드는 "클라이언트가 다르게 행동해야 할 때만" 분리하고, 한번 공개한 코드는 클라이언트의 분기문에 박히므로 필드명과 같은 급의 불변 계약이 된다 — 특히 앱 스토어에 나간 모바일 앱은 회수가 안 된다. 자체 포맷 대신 RFC 9457(구 7807) Problem Details라는 표준을 채택하는 선택지도 있고, 외부 공개 API일수록 표준이 계약 설명 비용을 줄인다. 마지막으로 "필드 추가는 안전, 모르는 코드는 status 기반 폴백"이라는 진화 규칙까지 문서화해 소비자와 공유하는 것이 설계의 끝이다.
  • 1
    에러 응답은 예외가 아니라 계약의 절반이다 — 검증 실패·만료 토큰·품절은 매일 수만 번 오는 정상 트래픽이고 클라이언트 코드의 절반이 그 분기다. 그래서 성공 DTO와 같은 급으로 스키마를 고정하고, 에러 종류가 늘어도 바디의 모양은 변하지 않게 한다.
  • 2
    축을 둘로 나눈다 — status는 부류(바디를 안 보는 게이트웨이·프록시·모니터링·재시도 로직이 읽는다), code는 세부(우리 API를 직접 쓰는 클라이언트 분기가 읽는다). 여기에 사람용 message, 검증 상세 errors[], 추적 진입점 traceId를 얹은 네 칸이 뼈대다.
  • 3
    코드 분리 기준과 진화 규칙까지가 설계다 — 코드는 "클라이언트가 다르게 행동해야 할 때만" 나누고, 한번 공개하면 필드명과 같은 급의 불변 계약(모바일 앱은 회수 불가)이다. 모르는 필드는 무시·모르는 코드는 status 폴백이라는 규약을 문서화하고, 외부 공개 API라면 RFC 9457 골격 + 확장 멤버로 자체 code를 검토한다.

0. 질문 + 출제 의도

질문: "API 에러 응답 바디는 어떻게 표준화하나요?"

출제 의도: 에러 스펙이 제각각이면 클라이언트마다 파싱 분기가 생기고, 장애 시 에러 원인 분류가 불가능하다. API를 "혼자 만드는 것"이 아니라 "여러 팀이 소비하는 제품"으로 보는지 확인한다. 스프링 구현 테크닉이 아니라, 에러 응답이라는 스키마를 소비자와의 계약으로 설계할 수 있는지를 보는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① "포맷 통일했습니다"에서 끝나는 답 → 2·3절에서 모양 불변과 이중 축이라는 두 개의 설계 판단을 분리해 세운다. 통일은 결과이고 판단이 내용이다.
② 바디만 보고 status를 잊는 것 → 3절에서 우리 응답을 읽는 소비자가 두 층이라는 사실을 그림 한 장으로 못 박는다. 200 + success:false가 왜 인프라 전체를 눈멀게 하는지가 여기서 나온다.
③ "코드는 잘게 나눌수록 좋다"는 오해와 변경 감각의 부재 → 5·8절에서 분리 기준(클라이언트의 행동)과 불변성(모바일은 회수 불가), 그리고 진화 규칙을 표와 타임라인으로 세운다.

범위 정리 — 스프링에서의 구현(@RestControllerAdvice, ErrorCode enum, 필터·비동기 구역의 포맷 통일)은 02-spring/19-global-exception-handling-error-response.md, 어떤 상태 코드를 고를지의 기준(4xx 6관문·5xx 제조 주체·재시도 판단)은 08-network-http/05-http-status-codes-usage-criteria.md에 있다. 이 페이지는 응답 스키마 설계 자체와 클라이언트 처리 계약만 다룬다.

1. 왜 에러 바디만 스키마 없이 자라는가

성공 응답에는 대개 DTO 클래스가 있다. 필드 이름을 정하고, 타입을 정하고, OpenAPI 문서에 올리고, 바꿀 때는 "이거 바꿔도 되나"를 묻는다. 그런데 같은 팀이 에러 응답은 Map.of("error", e.getMessage())로 그 자리에서 만들어 던진다.

서버 개발자의 감각

  • 에러는 "일어나면 안 되는 일"이다
  • 그러니 스펙 바깥의 예외 상황이다
  • 성공 경로만 계약, 실패 경로는 사고 처리
  • 그래서 그 자리에서 만들어 던진다

소비자(프론트·모바일·파트너)의 현실

  • 로그인 검증 실패, 만료 토큰, 품절, 한도 초과 —
  • 매일 수만 번 오는 정상 트래픽이다
  • 클라이언트 코드의 절반이 이 응답 처리 분기
  • "실패하면 무슨 모양이 오나요"는 성공 스펙만큼 자주 필요한 정보
에러 응답은 예외가 아니라 계약의 절반이다 — 이 인식이 없는 조직의 API는 아래처럼 자란다

1-1. 표준화하지 않은 API가 실제로 어떻게 생겼는가

before API마다 에러 바디 모양이 다르다
// 주문 API — A 개발자
{ "error": "재고가 없습니다" }

// 회원 API — B 개발자
{ "success": false, "errorMessage": "이미 가입된 이메일", "errCode": 1042 }

// 결제 API — 외부 SDK 스타일 흉내
{ "result": { "status": "FAIL", "reason": "LIMIT_EXCEEDED" } }

세 응답이 전부 다르다. 메시지가 든 키 이름이 error·errorMessage·result.reason으로 셋이고, 코드에 해당하는 것이 없거나(error), 숫자거나(1042), 문자열이다(LIMIT_EXCEEDED). 실패했다는 사실을 알리는 방법조차 success:false가 있는 쪽과 없는 쪽으로 갈린다.

소비자 비용
API마다 에러 파싱 코드를 따로 짠다. 그 지식은 코드에만 있으므로 물어볼 사람이 자리에 없으면 진행이 멈춘다. 그리고 물어봐서 얻은 답은 문서에 남지 않으므로 다음 사람이 또 물어본다.
운영 비용
장애 시 "어떤 종류의 실패가 늘고 있는지"를 집계할 공통 키가 없다. "5분 전부터 재고 소진 에러가 300배 늘었다" 같은 신호는 집계 키가 있어야만 알람이 된다.

2. "하나의 스키마" — 에러가 늘어도 모양은 안 변한다

표준화란 이 응답을 하나의 스키마로 통일하는 것이다. 그런데 "하나의 스키마"가 무슨 뜻인지 정확히 짚고 가야 한다. 여기서 미끄러지면 "포맷이 여러 개인 상태"에 이름만 붙이고 표준화했다고 부르게 된다.

after 어떤 API가 실패해도 이 모양 — 소비자는 파서를 한 번만 짠다
{
  "code": "ORDER-001",                   // 기계 판독용 — 분기·집계의 키
  "message": "재고가 소진된 상품입니다",      // 사람용
  "errors": [],                          // 검증 실패 시 필드별 상세
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"  // 장애 추적의 진입점
}

"하나의 스키마"의 정확한 뜻

에러의 종류가 늘어나도 바디의 모양은 변하지 않는다

검증 실패라고 해서 errors 배열이 갑자기 생기는 것이 아니라, 검증 실패가 아닐 때는 빈 배열로 나간다. 인증 에러라고 해서 code 대신 reason을 쓰지 않는다. 이 규칙이 있어야 소비자가 한 번 짠 파서를 모든 응답에 그대로 적용할 수 있다.

그럼 "재고 소진일 때 productId를 주고 싶다"는 요구는 어떻게 하나 세 갈래다. ① message에 값을 녹여 보낸다("상품 12345의 재고가…") — 가장 싸지만 기계가 못 읽는다. ② 모든 에러가 갖는 선택적 확장 칸(예: errors[]의 field·reason 또는 6절의 Problem Details 확장 멤버)을 미리 스키마에 넣어두고 필요할 때만 채운다. ③ 이 에러에서만 새 최상위 필드를 추가한다 — 이때도 "이 필드는 이 코드에서만 존재한다"가 문서에 있어야 하고, 소비자는 null 가능으로 다뤄야 한다. ①②는 스키마를 지키고 ③은 스키마를 무르게 만든다.

3. 이중 축 — 겉봉(status)과 속지(code)

표준 스키마를 설계할 때 던져야 하는 질문은 "무슨 정보를 담을까"가 아니라 "이 필드를 누가 읽는가"다. 읽는 주체가 다르면 필드를 나눠야 하고, 같으면 합쳐야 한다. 에러를 식별하는 수단은 둘 — HTTP status와 바디의 code다. 각각이 왜 혼자서는 모자란지를 순서대로 보면 이중 축이 필연이 된다.

3-1. status만으로는 왜 부족한가 — 종류가 너무 적다

status는 종류가 적다. 클라이언트 잘못을 뜻하는 4xx 계열이 전부 합쳐 스무 개 남짓이고, 실무에서 실제로 쓰는 것은 400 401 403 404 409 422 429 정도다. 반면 하나의 결제 API가 낼 수 있는 실패는 훨씬 많다.

POST /payments 가 400을 돌려줬다. 클라이언트가 아는 것:
  "요청이 잘못됐다"

클라이언트가 알아야 하는 것 — 화면 분기가 전부 달라진다:
  잔액이 부족한가?        -> 충전 화면으로 보낸다
  일일 한도를 넘었나?      -> 한도 안내 화면을 띄운다
  필수값이 빠졌나?        -> 입력 폼의 해당 칸에 표시한다
  카드가 만료됐나?        -> 카드 관리 화면으로 보낸다
status만 있으면 클라이언트가 message 문자열을 비교하게 된다 네 가지가 전부 같은 400이므로 구분할 방법이 문구 비교밖에 없다. 그 순간 서버가 문구를 다듬는 커밋이 프론트 장애가 되는 최악의 결합이 생긴다 — "잔액이 부족합니다"를 "잔액이 부족해요"로 바꾸는 카피 수정 하나에 앱이 충전 화면을 못 찾는다.

3-2. code만으로도 안 되는 이유 — 바디를 안 읽는 소비자가 있다

이쪽이 놓치기 쉬운 절반이다. 우리 응답을 읽는 소비자는 두 층인데, 위층은 JSON을 아예 열어보지 않는다.

비유 하나로 고정하기 — 겉봉과 속지

status = 봉투 겉면의 분류 도장 · code = 봉투 안 편지의 내용

우체국·분류기·배송 기사는 봉투를 뜯지 않는다. 겉면 도장만 보고 반송할지, 재배달할지, 창고에 둘지를 정한다. 편지 내용은 수신인만 읽는다. 겉봉에 "정상 배송"이라 찍고 안쪽에만 "반송해 주세요"라고 쓰면 — 그게 200 + {"success": false}다. 수신인 말고는 아무도 문제를 모른다.

두 축의 대비. 면접에서 값이 나가는 줄은 "누가 읽는가"다 — 나머지 줄은 전부 여기서 파생된다.
축HTTP status바디의 code이 줄이 뜻하는 것
누가 읽는가게이트웨이·프록시·모니터링·재시도 로직 (바디를 안 봄)우리 API를 직접 쓰는 클라이언트 코드읽는 주체가 다르므로 하나로 합칠 수 없다
무엇을 답하나"이 실패는 어떤 부류인가 — 재시도해도 되나, 캐시해도 되나""구체적으로 무엇이 잘못됐고 사용자를 어디로 보내야 하나"부류 ↔ 세부. 세부를 모르면 부류로 떨어지면 된다(8절 폴백)
값의 개수적다 — 수십 개, 표준이 정한 것많다 — 도메인이 자라면 늘어난다, 우리가 정한 것표준 값이라 인프라가 미리 알고 있다 / 우리 것이라 문서가 필요하다
바꿀 수 있나바꾸면 인프라 동작이 바뀐다 — 위험바꾸면 클라이언트 분기가 깨진다 — 위험둘 다 사실상 불변. 자유롭게 바꿀 수 있는 것은 message뿐

status를 고를 때의 실무 기준 한 줄

"이 실패를 그대로 재시도하면 결과가 달라질 수 있는가" — 아니면 4xx, 그럴 수 있으면 5xx

잔액 부족은 다시 보내도 여전히 부족하므로 4xx. DB 커넥션 고갈은 잠시 후엔 될 수도 있으므로 5xx. 이 기준으로 고르면 클라이언트 라이브러리의 자동 재시도가 우리가 의도한 대로 동작한다. (429처럼 4xx인데 재시도해야 하는 예외와 5xx인데 재시도하면 안 되는 경우는 08-network-http/05에서 다룬다.)

동시에 여러 개인 검증 실패를 담는 그릇(4-2)

CS·개발자

네 칸이 서로 다른 네 명의 독자를 향한다는 것이 이 뼈대의 근거다 — 3절에서 status와 code를 나눈 것과 같은 논리를 바디 안에서 한 번 더 적용한 결과다.

4-1. message — "보여줘도 되는가"를 계약에 명시한다

message에서 흔히 터지는 계약 불명확성이 있다. 클라이언트가 이 문구를 그대로 화면에 띄워도 되는가? 이 질문의 답이 문서 어디에도 없으면, 서버 개발자는 디버깅에 편한 문구를 넣고 프론트 개발자는 그걸 사용자에게 띄운다.

계약 공백이 만드는 대표 사고 "Cannot invoke \"Order.getItems()\" because \"order\" is null" — 이 문장이 사용자 결제 화면에 뜬다. 아무도 잘못한 사람이 없다는 것이 이 사고의 특징이다. 서버는 로그용으로 넣었고 클라이언트는 "서버가 준 안내 문구"로 알았을 뿐이다.

노선 A — message는 표시 가능

  • 서버가 사용자에게 보여도 안전한 문구만 담기로 계약
  • 클라이언트 구현이 단순하다 — 그냥 띄우면 된다
  • 대신 문구 품질과 다국어가 전부 서버 책임
  • "쿠폰 안내 문구 바꿔주세요" → 서버 배포가 필요

노선 B — message는 개발자용, 표시는 code 매핑

  • message는 로그·디버깅용, 사용자 문구는 클라이언트가 code → 자기 문구 테이블로 변환
  • 다국어와 A/B 문구 실험이 클라이언트의 자유
  • 대신 모든 code의 매핑을 웹·iOS·Android 각각 관리
  • 다국어 서비스이거나 클라이언트가 여럿이면 이쪽이 일반적

중요한 것은 어느 쪽이 옳으냐가 아니라 어느 쪽을 골랐는지가 문서에 있느냐다. 서버가 Accept-Language를 받아 문구를 번역해 내려주는 구조는 번역 리소스가 서버 배포에 묶이고, 클라이언트가 이미 갖고 있는 번역 파이프라인과 이중으로 관리된다.

노선과 무관하게 공통으로 지켜야 하는 금지

스택트레이스 · 예외 메시지 원문 · SQL · 내부 호스트명은 message에 절대 싣지 않는다

계약 문제이자 보안 문제다 — 예외 원문 하나로 프레임워크 버전과 테이블 이름이 공격자에게 넘어간다. 그런 정보가 필요한 사람(우리 개발자)은 traceId로 로그를 보면 된다(4-3). 내부 정보의 전달 통로는 응답이 아니라 로그다.

4-2. errors[] — 복수 오류를 담는 그릇, 그러나 포맷은 하나

검증 실패는 다른 에러와 성질이 다르다. 오류가 여러 개 동시에 존재한다. 회원가입 폼에서 이메일 형식이 틀리고 나이가 음수이고 비밀번호가 짧다면, 잘못된 것이 셋이다.

단일 message로 첫 오류만 알려줄 때

  • 첫 오류를 고치고 제출 → 다음 오류를 만남
  • 또 고치고 제출 → 또 다음 오류
  • 사용자는 자기가 세 군데를 틀렸다는 사실을 세 번 나눠 알게 된다

필드별 상세를 배열로 담을 때

  • 한 번의 응답으로 폼의 세 칸에 동시에 빨간 줄
  • 왕복이 3회 → 1회
  • 검증 실패가 아닐 때는 빈 배열로 나간다(2절 모양 불변)
shape 검증 실패일 때만 채워지는 칸 — 칸 자체는 언제나 있다
{
  "code": "COMMON-001",
  "message": "입력값이 올바르지 않습니다",
  "errors": [
    { "field": "email", "reason": "이메일 형식이 아닙니다" },
    { "field": "age",   "reason": "0 이상이어야 합니다" }
  ]
}
field에 무엇을 넣을지도 계약이다 — 폼의 빨간 줄이 이 문자열 하나에 달려 있다 중첩 객체와 배열이 섞이면 items[0].quantity 같은 경로 표기가 필요해진다. 이 표기법을 정해두지 않으면 서버는 items.0.quantity로 보내고 클라이언트는 items[0].quantity로 찾는 어긋남이 생긴다. 표기 후보는 대략 셋이다 — ① 점·대괄호 표기(items[0].quantity, 스프링 BindingResult가 내는 모양과 같다) ② JSON Pointer(/items/0/quantity, RFC 6901 표준이라 파서가 이미 있다) ③ 단순 필드명(중첩이 없는 단순 폼에서만). 무엇을 고르든 조직 전체에서 하나로 고정하는 것이 요점이다.

4-3. traceId — 에러 응답을 장애 추적의 진입점으로 가산점

traceId를 "장애 추적용 ID" 한 줄로 넘기면 왜 이게 스키마의 한 자리를 차지할 만한지가 안 보인다. 분산 추적이 무엇인지부터 쌓아야 한다.

1
전제 — 요청 하나가 여러 서비스를 지나간다. 주문 버튼을 누르면 요청은 게이트웨이를 거쳐 주문 서비스로 가고, 주문 서비스는 재고·결제 서비스를 부르고, 결제 서비스는 PG를 부른다. 각 서비스는 각자의 로그를 각자의 파일에 쌓는다.
2
문제 — 결제 서비스 로그에 NullPointerException이 하나 찍혔다. 이게 어느 사용자의 어느 주문에서 나온 것인지 알 방법이 없다. 같은 초에 다른 요청 200건이 함께 지나갔기 때문이다. 서비스 다섯 개의 로그를 시각으로 맞춰보는 것은 트래픽이 조금만 있어도 불가능하다.
3
해법 — 요청이 시작되는 지점에서 ID를 하나 만들어, 그 요청이 지나가는 모든 서비스에 같은 ID를 달고 다니게 한다. 그 ID가 trace ID다. 각 서비스가 로그를 쓸 때마다 이 ID를 함께 찍으면, ID 하나로 전 구간 로그를 시간순으로 꿰어 볼 수 있다.
4
한 단계 더 — span. 전 구간에 공통인 trace ID와 별개로, 각 구간(한 서비스 안에서 처리된 한 토막)을 span이라 부르고 span마다 span ID를 준다. trace ID는 "이 요청 전체", span ID는 "그 안의 이 구간"이다. 그래서 로그에는 보통 둘이 나란히 찍힌다.

여기까지가 준비고, 에러 응답 스키마에 traceId를 넣는다는 것은 이 ID를 사용자에게까지 노출한다는 뜻이다. 그러면 이런 흐름이 성립한다.

사용자 "결제하려는데 오류가 나요"→ CS "화면에 뜬 코드를 알려주세요"→ 개발자: 로그 검색창에 traceId 붙여넣기→ 전 구간 로그가 시간순으로 → 결제 서비스 NPE 한 줄 발견
이 고리가 있을 때
"어제 오후에 결제가 안 됐다"는 문의 하나가 검색 한 번이 된다. 에러 바디에 traceId를 넣는 것은 CS와 로그를 잇는 가장 싼 방법이다.
이 고리가 없을 때
같은 문의를 재현하는 데만 반나절이 든다. 재현이 안 되면 "확인 중"으로 남는다.

노출해도 되는 이유, 그리고 넣으면 안 되는 값

trace ID는 랜덤한 16진수 문자열일 뿐이라 그 자체로 아무 권한도, 내부 구조 정보도 담고 있지 않다. 그래서 사용자에게 보여도 된다.

반대로 순차 증가하는 요청 번호나 내부 서버 이름을 traceId 자리에 넣으면 안 된다

순번은 하루 트래픽량을, 호스트명은 인프라 구성을 공개하는 것이 된다. "값이 의미를 갖지 않는다"가 안전의 근거이므로, 의미를 넣는 순간 근거가 사라진다.

4-4. 네 칸의 계약 표면 — 무엇이 불변이고 무엇이 자유인가

스키마를 정하는 것과 "그중 무엇을 나중에 바꿀 수 있는지"를 정하는 것은 다른 작업이다. 후자를 안 정하면 8절의 진화 규칙을 세울 수 없다.

같은 바디 안에서도 칸마다 계약의 굳기가 다르다. 이 표가 5절(코드 불변성)과 8절(진화 규칙)의 밑그림이다.
칸굳기바꾸면 무엇이 깨지나그래서 실무에서는
HTTP status불변에 가까움재시도·캐시·서킷·에러율 알람이 한꺼번에 바뀐다바꾸려면 API 버전 단위로 다룬다
code불변클라이언트의 switch 분기가 조용히 default로 떨어진다필드명 삭제와 같은 급의 파괴적 변경(5절)
message자유아무것도 — 단, "message로 분기 금지"가 계약에 있을 때만이 자유를 지키려고 code를 따로 둔 것이다
errors[].field준불변폼의 빨간 줄 매핑이 어긋난다(경로 표기 포함)표기법을 조직 전체에서 하나로 고정
errors[].reason자유아무것도 — 사람이 읽는 문구다message와 같은 취급
traceId값은 매번 다름필드의 존재는 계약, 값은 계약이 아니다값에 의미를 부여하지 않는다(4-3)
이 표의 결론 한 줄 — "바뀌면 안 되는 기계용 식별자"와 "자유롭게 다듬는 사람용 문구"를 한 칸에 섞지 않는다"

5. 에러 코드 체계 — 필드명과 같은 급의 불변 계약

code 필드를 두기로 했다면, 코드 체계 자체가 설계 대상이 된다. 판단해야 하는 것이 세 가지다 — 형식(문자열 vs 숫자), 구조(접두사), 입도(얼마나 잘게 나눌 것인가). 그리고 그 위에 불변성이라는 결론이 얹힌다.

5-1. 형식과 구조 — 문자열 · 도메인 접두사

숫자 코드 errCode: 1042

  • 로그에 1042가 찍히면 매번 표를 찾아봐야 뜻을 안다
  • 대시보드에 숫자만 늘어서면 읽을 수가 없다
  • 채번 문제 — "다음 번호가 몇 번이지"를 관리해야 한다
  • 팀이 나뉘면 번호대가 겹친다
  • 장점은 짧다는 것뿐인데, 에러 응답의 바이트 수가 문제가 되는 상황은 실무에서 거의 없다

문자열 코드 MEMBER_EMAIL_DUPLICATED

  • 그 자체가 문서다 — 로그와 대시보드에서 바로 읽힌다
  • 채번이 필요 없다
  • 도메인 접두사(ORDER-, AUTH-)를 붙이면 ① 대시보드에서 접두사로 group by → "어느 도메인의 실패가 늘었나"가 바로 나오고 ② 코드만 보고 어느 팀에 물어볼지 안다
  • 마이크로서비스라면 접두사가 곧 소유 팀의 이름표
접두사 뒤는 일련번호인가 의미 있는 이름인가 ORDER-001이냐 ORDER_SOLD_OUT이냐는 취향이 갈리지만, 의미 있는 이름 쪽이 읽기 좋고 채번 문제도 없다. 어느 쪽이든 형식은 조직 전체에서 하나로 통일한다 — 어떤 API는 대문자 스네이크, 어떤 API는 하이픈이면 소비자가 다시 API마다 다른 파싱을 하게 된다(1절로 되돌아간다).

5-2. 입도 — 잘게 쪼갤수록 좋은 게 아니다

이 부분이 설계 감각이 드러나는 지점이다. 코드가 200개인데 클라이언트가 그중 8개만 분기하고 나머지 192개를 전부 "기타 오류"로 뭉갠다면, 그 192개는 만든 사람만 아는 코드다.

분리 기준 — 이 한 문장이 전부다

"클라이언트가 다르게 행동해야 하는 경우에만 코드를 분리한다"
분리해야 하는 경우클라이언트의 행동 — 이게 다르니까 코드가 필요하다
재고 소진재입고 알림 신청 버튼을 띄운다
인증 만료토큰을 갱신하고 원래 요청을 재시도한다
일일 한도 초과한도 안내 화면으로 보낸다
잔액 부족충전 화면으로 보낸다

반대로 "상품 ID 형식 오류"와 "쿠폰 ID 형식 오류"는 클라이언트가 둘 다 "입력을 확인하세요"로 처리한다면 코드를 나눌 이유가 없다. 나누고 싶다면 errors[]의 field로 구분하면 된다 — 축이 이미 하나 더 있다.

5-3. 불변성 — 여기서부터가 이 절의 결론

한번 공개한 코드는 바꿀 수 없다. 왜 그런지는 소비자 코드를 보면 즉시 납득된다.

consumer iOS 앱의 결제 실패 분기 — 서버가 내려준 code 문자열에 그대로 묶여 있다
switch error.code {
case "PAYMENT_INSUFFICIENT_BALANCE":      서버가 이 문자열을 바꾸는 순간 끊긴다
    navigate(to: .chargeScreen)      // 충전 화면으로 보낸다
case "PAYMENT_LIMIT_EXCEEDED":
    showLimitGuide()
default:                                모르는 코드는 status 기반 폴백 (8절)
    showGenericError(status: error.status)
}

서버가 PAYMENT_INSUFFICIENT_BALANCE를 INSUFFICIENT_BALANCE로 "정리"하는 순간, 이 앱은 잔액 부족을 만나도 default로 떨어져 "알 수 없는 오류"를 띄운다. 사용자는 충전 화면으로 못 간다. 예외도 안 나고, 서버 로그도 정상이고, 아무도 모른다.

가장 위험한 것은 삭제가 아니라 "의미 변경"이다

코드를 삭제하면 소비자는 default로 떨어지고, 최소한 "모르는 상황"이라는 사실은 안다. 그런데 코드의 의미를 바꾸면(예: ORDER-001을 재고 소진에서 주문 취소 불가로 재사용) 소비자는 그 코드를 안다고 믿고 재입고 알림 버튼을 띄운다.

예외도 안 나고, 로그도 깨끗하고, 조용히 틀린 화면으로 간다 — 그래서 삭제보다 나쁘다
카탈로그 문서화 — 코드 목록은 API 문서의 1급 시민이다 코드 목록을 네 칸(코드 · 의미 · HTTP status · 클라이언트 권장 행동)으로 관리하고 소비자와 공유한다. 마지막 칸이 특히 중요하다 — 5-2의 분리 기준("클라이언트가 다르게 행동할 때만")이 곧 이 칸이 비어 있으면 안 된다는 뜻이기 때문이다. 권장 행동을 못 쓰는 코드는 애초에 나눌 필요가 없었던 코드다. 성공 응답 스키마는 OpenAPI로 꼼꼼히 문서화하면서 에러 코드 표는 없는 API가 흔한데, 그 API의 에러 계약은 결국 "물어봐야 아는 것"이 되고, 물어봐서 얻은 답은 문서에 남지 않으므로 다음 사람이 또 물어본다.

6. RFC 9457 Problem Details — 이미 있는 국제 표준

2~5절에서 설계한 것을 IETF가 이미 표준으로 만들어 두었다. RFC 7807 "Problem Details for HTTP APIs"(2016년 3월)가 원본이고, 이를 폐지(obsolete)한 개정판이 RFC 9457(2023년 7월)이다.

"폐지"라는 말이 부르는 오해 7807이 틀려서 없어진 것이 아니라 9457이 그 자리를 물려받았다는 뜻이다. 다섯 개 표준 멤버로 이루어진 데이터 모델은 두 문서가 사실상 같고, 9457이 더한 것은 확장 멤버 사용 지침, 문제 유형을 IANA 레지스트리에 등록할 수 있게 한 것, 그리고 "유형 식별의 1차 키는 title이 아니라 type"이라는 명확화다. 바디 모양은 거의 같지만, 문서에 표기할 때는 현행 표준인 9457을 가리키는 것이 맞다.

6-1. 다섯 개 멤버 — "종류에 딸린 값"과 "이번 한 건에 딸린 값"

이름만 나열하면 type과 instance, title과 detail의 차이가 안 잡힌다. 각각이 무엇의 식별자인지로 나누면 한 번에 정리된다.

RFC 9457 전용 미디어 타입 application/problem+json과 함께 나가는 바디
// Content-Type: application/problem+json
{
  "type": "https://api.example.com/problems/sold-out", // 유형 식별 URI (문서 링크 겸용)
  "title": "재고 소진",                                 // 유형의 짧은 요약 — 유형마다 고정
  "status": 409,                                       // HTTP status 사본
  "detail": "상품 12345의 재고가 소진되었습니다",         // 이 발생 건의 상세
  "instance": "/orders/98765",                         // 이 발생 건의 식별 URI

  "code": "ORDER-001",                              확장 멤버 — 우리 체계를 그대로 얹는다
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "errors": []
}

6-2. type이 URI인 이유, 그리고 흔한 오해

에러 유형의 이름은 전 세계에서 충돌하지 않아야 하는데, 웹에는 이미 도메인이라는 네임스페이스 체계가 있다. sold-out이라는 이름은 우리 회사와 다른 회사가 서로 다른 뜻으로 쓸 수 있지만, https://api.example.com/problems/sold-out은 우리 것임이 분명하다. 그래서 URI를 쓴다.

반드시 짚어야 하는 오해 — 이 URI는 접속 가능한 주소가 아니어도 된다

RFC는 그 주소를 브라우저로 열었을 때 사람이 읽을 문서가 나오는 것을 권장할 뿐이고, 클라이언트가 이 URI를 자동으로 GET 하는 것은 오히려 하지 말라고 한다. 자동으로 열면 에러 하나당 HTTP 요청이 하나씩 더 늘고, 우리는 그 주소를 실제로 서비스해야 할 의무를 지게 된다.

클라이언트가 type으로 하는 일은 문자열 비교 하나다

5-3의 switch error.code와 정확히 같은 용법이고, 다만 값이 "ORDER-001" 대신 "https://api.example.com/problems/sold-out"인 것뿐이다. 즉 type은 사실상 우리 code 체계의 표준 버전이고, 5-3의 코드 카탈로그 문서화를 표준이 프로토콜 차원에서 흡수한 것이다.

6-3. application/problem+json이 왜 따로 있는가

내용물이 JSON인데 굳이 미디어 타입을 나눈 이유는, 바디를 열어보지 않고 헤더만으로 "이건 에러 설명 문서다"를 알 수 있게 하기 위해서다. 3절의 겉봉/속지 구분이 여기서 한 번 더 값을 한다 — 겉봉에 "안에 든 것은 표준 형식의 에러 문서"라고 적어두는 것이다.

이 구분이 값을 하는 장면
클라이언트 SDK는 응답을 받으면 성공 DTO 파서와 에러 파서 중 하나를 골라야 한다. Content-Type이 그냥 application/json이면 그 판단을 상태 코드에만 의존해야 하는데, 실무에서는 예외가 섞인다 — 게이트웨이가 대신 뱉은 HTML 에러 페이지가 502로 오기도 하고, 레거시 API가 에러를 200으로 내려주기도 한다.
+json이라는 접미사의 뜻
structured syntax suffix — "이 타입이 무엇이든 문법은 JSON을 따른다"는 표시다. 그래서 이 타입을 모르는 중간 도구도 최소한 JSON으로는 다룰 수 있다.
Spring에서의 지원 Spring Framework 6부터 ProblemDetail 타입이 들어와 있고, Spring Boot 3에서 spring.mvc.problemdetails.enabled=true를 켜면 프레임워크가 처리하는 예외들의 응답이 Problem Details 형식으로 바뀐다. (구현 상세: 02-spring/19-global-exception-handling-error-response.md)

7. 자체 포맷 vs 표준 포맷 — 판단 기준은 소비자다

두 선택지가 무엇인지 먼저 정리하자. 자체 포맷은 2~5절에서 설계한 {code, message, errors, traceId} 같은 우리 스키마이고, 표준 포맷은 6절의 Problem Details다. 둘 중 무엇이 우월하다는 답은 없고, "소비자가 누구인가"로 갈린다.

같은 질문에 대한 답이 소비자에 따라 뒤집힌다 — 이 표의 오른쪽 끝 칸이 판단의 실체다.
소비자자체 포맷RFC 9457무엇이 결정적인가
사내 프론트 팀 하나편하다 — 필드를 우리 마음대로 정하고, 스키마 변경도 슬랙 한 줄로 합의된다과하다 — 표준을 따르는 대가로 얻는 "설명 없이 통하는 계약"의 이득이 작다옆자리에 앉아 있는 팀에게는 설명 비용이 원래 낮다
외부 파트너 · 공개 API계약 설명서를 매번 읽히고 답해야 한다유리하다 — "RFC 9457입니다" 한 줄. 소비자 언어에 이미 이해하는 라이브러리가 있으면 파싱 코드를 아예 안 짜도 된다소비자 수가 늘수록 설명 비용이 선형으로 증가한다
이미 운영 중인 API—갈아타는 것 자체가 파괴적 변경 — 모든 소비자가 파서를 고쳐야 한다"표준이 더 좋으니 갈아타자"는 신규 API나 다음 메이저 버전에서 할 판단이다

실무적 절충 — 둘은 양자택일이 아니다

RFC 9457 골격 + 확장 멤버로 자체 code 체계

6절 예시에서 봤듯 표준은 확장 멤버를 허용하므로, 표준 도구가 이해하는 뼈대를 쓰면서 우리 도메인의 세부 분류도 유지할 수 있다. "표준을 채택한다고 우리 코드 체계를 버릴 필요가 없다"는 점을 정확히 아는지가 이 주제의 변별점이다.

8. 진화 규칙 — 계약은 "바꾸는 법"까지가 계약이다

성공 응답과 똑같이, 에러 스키마에도 변경 규칙이 필요하다. 규칙이 없으면 "이거 바꿔도 되나"를 매번 감으로 판단하게 되고, 그 판단은 언젠가 틀린다.

오른쪽 칸에 "~규약이 있을 때만"이 반복되는 것이 이 표의 핵심이다.
변경안전한가왜
새 필드 추가 (traceId 등)안전소비자가 모르는 필드를 무시한다는 규약이 있을 때만
새 code 추가조건부 안전모르는 코드 폴백 규약이 있을 때만. 없으면 소비자가 터진다
message 문구 수정안전message로 분기하지 말라는 계약이 있을 때만
code 의미 변경위험예외도 안 나고 조용히 틀린 화면으로 간다 — 삭제보다 나쁘다
code 삭제 · 재사용위험응답 필드 삭제와 같은 급
에러의 HTTP status 변경위험재시도·캐시·모니터링·서킷 브레이커 판단이 한꺼번에 바뀐다
안전한 변경이란 그 자체로 안전한 것이 아니라, 소비자가 특정 규약을 지킨다는 전제 위에서만 안전하다

그래서 그 전제를 계약 문서에 명시해야 한다. 명시해야 할 규약은 두 개뿐이다.

소비자에게 요구하는 두 규약 — "무시와 폴백"

규약 ① 모르는 필드는 무시한다
이것을 Tolerant Reader(관용적 파서)라고 부른다. 이 규약이 계약에 있어야 서버가 나중에 traceId 같은 필드를 추가할 수 있다. 없으면 필드 하나 추가에 모든 소비자가 깨진다. (08-backward-compatible-api-changes.md)
규약 ② 모르는 code는 status 기반 처리로 폴백
서버는 도메인이 자라면서 새 코드를 계속 추가하게 된다. 소비자가 "아는 코드만 분기하고 나머지는 status로" 약속돼 있어야 새 코드 추가가 하위 호환 변경으로 성립한다.

규약 ②가 3절의 이중 축이 값을 하는 지점이다 — 세부(code)를 모르면 부류(status)로 떨어지면 된다. 축이 하나였다면 폴백할 곳이 없다.

8-1. 규약 ②가 없을 때 실제로 터지는 형태

추상적으로 "깨진다"가 아니라 구체적인 실패 모드가 있다. 클라이언트가 code를 enum으로 역직렬화하는 경우, 서버가 새 코드를 추가하는 순간 그 값이 enum에 없어서 역직렬화 자체가 예외를 던진다. 응답을 읽지도 못하고 앱이 크래시한다.

before code를 enum으로 받는 소비자 — 서버의 정상적인 확장에 크래시한다
enum class ErrorCode {
    PAYMENT_INSUFFICIENT_BALANCE,
    PAYMENT_LIMIT_EXCEEDED
    // 서버가 새로 추가한 PAYMENT_CARD_EXPIRED가 없다
}

data class ApiError(
    val code: ErrorCode,   모르는 값 → 역직렬화 예외
    val message: String
)

// 응답을 객체로 만들지도 못한다.
// message도, traceId도, status 폴백도 못 쓴다 — 크래시.
after 문자열로 받고 알려진 값만 매핑한다 (Tolerant Reader)
data class ApiError(
    val code: String,      모르는 값도 일단 담긴다
    val message: String,
    val traceId: String? = null
)

fun handle(err: ApiError, status: Int) = when (err.code) {
    "PAYMENT_INSUFFICIENT_BALANCE" -> goCharge()
    "PAYMENT_LIMIT_EXCEEDED"       -> showLimitGuide()
    else -> fallbackBy(status)   부류로 떨어진다 — 앱은 살아 있다
}

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

표준화란 정확히 무엇을 고정하는 것?
에러 종류가 늘어도 바디의 모양이 안 변하는 것. 검증 실패가 아니면 errors는 빈 배열로 나가지, 사라지지 않는다.
네 칸과 각 칸의 독자?
코·메·에·트 — code(기계: 분기·집계) · message(사람) · errors[](폼 UI) · traceId(CS·개발자).
status만 / code만으로 안 되는 이유?
status만 → 종류가 적어 클라이언트가 message 문자열을 비교하게 된다(카피 수정이 프론트 장애). code만 → 바디를 안 여는 소비자가 눈을 감는다.
200 + success:false의 결과 넷?
재시도 ✕ · 서킷 ✕ · 캐시 판단 ✕ · 에러율 0%. 겉봉에 "정상 배송" 찍고 안에만 반송이라 쓴 것.
코드 분리 기준 한 문장?
"클라이언트가 다르게 행동해야 할 때만." 권장 행동을 못 쓰는 코드는 애초에 나눌 필요가 없던 코드다.
코드 불변성의 근거와 최악의 변경?
근거: 모바일 앱은 서버 배포로 회수 안 된다. 최악은 삭제가 아니라 의미 변경 — 예외도 안 나고 조용히 틀린 화면으로 간다.
RFC 9457 다섯 멤버 정리?
종류 둘(type·title) + 이번 건 둘(detail·instance) + 사본 하나(status). 미디어 타입은 application/problem+json.
진화 두 규약?
무시와 폴백 — ①모르는 필드는 무시(Tolerant Reader) ②모르는 코드는 status 기반 폴백. 이 둘이 있어야 "추가"가 하위 호환이 된다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

자체 에러 포맷과 RFC 9457 중 무엇을 선택하나요? 시니어 변별힌트: "표준이 좋다"로 끝내면 감점. 축 → 절충안 → 마이그레이션 비용 순으로 쌓는다

축은 "소비자가 누구인가"다. 사내 단일 프론트 팀이 소비자면 자체 포맷도 충분하고, 마이그레이션 비용이 없다면 굳이 갈아탈 이유가 약하다. 외부 파트너·공개 API·여러 조직이 소비자면 표준이 유리하다 — 설명 비용이 줄고, application/problem+json과 type URI라는 프로토콜 차원의 자기 문서화를 얻는다.

실무적 절충은 "RFC 9457 골격 + 확장 멤버로 자체 code 체계"다. 표준을 채택한다고 우리 코드 체계를 버릴 필요가 없다는 점을 정확히 아는지가 이 질문의 변별점이다.

마지막으로 이미 자체 포맷으로 운영 중인 API를 표준으로 바꾸는 것 자체가 파괴적 변경(모든 소비자의 파서 수정)이라는 점까지 언급하면, 표준의 우월함보다 계약의 무게를 먼저 보는 답이 된다. 그래서 전환은 신규 API나 다음 메이저 버전에서 한다.

에러 message를 클라이언트가 그대로 화면에 보여줘도 되나요? 필수힌트: "된다/안 된다"가 아니라 "계약에 뭐라고 썼나"가 답이다

"계약에 뭐라고 명시했는가"가 답이다. 명시가 없으면 서버는 개발자용 디버그 문구를 넣고 클라이언트는 그걸 사용자에게 띄우는 사고가 난다 — 아무도 잘못하지 않았는데 사고가 난다는 것이 이 문제의 성격이다.

표시 가능 노선이면 서버가 문구 품질과 다국어를 책임지고, 개발자용 노선이면 클라이언트가 code 기반 매핑을 책임진다. 어느 쪽이든 내부 정보(예외 원문, SQL, 내부 호스트명)는 금지다.

다국어 서비스라면 code 매핑 노선이 자연스럽다는 것까지 말하면 좋다. 서버가 Accept-Language를 받아 번역해 내려주면 번역 리소스가 서버 배포 주기에 묶이는데, 클라이언트는 이미 자기 번역 파이프라인을 갖고 있는 경우가 대부분이다.

이미 운영 중인 API의 에러 코드를 바꾸거나 없애도 되나요? 필수힌트: 근거는 "모바일은 회수 불가", 그리고 순서를 세 단계로 말한다

안 된다. 코드는 클라이언트 분기 로직에 박힌 불변 계약이라, 의미 변경·삭제·재사용은 응답 필드 삭제와 같은 파괴적 변경이다. 특히 모바일 앱은 배포로 회수가 안 된다는 점을 근거로 들면 무게가 실린다 — 웹 프론트는 같은 날 배포로 수습되지만, 앱 스토어의 구버전이 얼마나 오래 살아 있을지를 서버 팀이 통제할 수 없다.

잘못 만든 코드가 있다면 새 코드를 추가하고, 옛 코드는 지원 종료(deprecation) 공지 후 소비자 이전이 확인될 때까지 병행 유지한다. 순서가 "새것 추가 → 이전 → 옛것 제거"라는 것이 핵심이다.

여기에 대칭을 한 줄 붙이면 답이 완성된다

message는 반대로 언제든 고칠 수 있어야 하고, 그래서 "클라이언트가 message로 분기하는 것"을 계약으로 금지해두는 것이 중요하다. 이 금지가 없으면 message도 사실상 불변 계약이 되어버려 오타 하나 못 고치는 API가 된다.

클라이언트가 모르는 에러 코드를 받으면 어떻게 처리해야 하나요? 필수힌트: 폴백 동작 → 그게 왜 "계약"인지 → 구현상의 함정 순

HTTP status 기반 기본 처리로 폴백한다 — 4xx면 "요청을 확인하세요"류의 일반 안내, 5xx나 429면 재시도 또는 잠시 후 안내다. 3절의 "status는 부류, code는 세부"라는 이중 축이 여기서 값을 한다 — 세부를 모르면 부류로 떨어지면 되는 것이다.

그리고 이 폴백 규약이 계약에 명시돼 있어야 서버가 새 코드를 추가하는 것이 하위 호환 변경으로 성립한다는 점을 짚어야 한다. 규약 없이 코드를 추가하는 것은 사실상 소비자를 깨뜨리는 도박이다.

구현 관점의 함정도 덧붙이면 좋다. code를 enum으로 역직렬화하는 클라이언트는 모르는 값에서 응답을 읽지도 못하고 터진다. 그래서 "코드는 문자열로 받고 알려진 것만 매핑"이 관용적 파싱(Tolerant Reader)의 구체적 형태다. 같은 원리가 필드 추가에도 적용된다는 것까지 연결하면(08-backward-compatible-api-changes.md), 에러 스키마의 진화를 API 호환성이라는 더 큰 규칙의 한 사례로 보고 있다는 인상을 준다.

성공 응답도 {code, message, data} 래퍼로 감싸는 게 좋나요?힌트: 트레이드오프를 말한 뒤, "이 둘은 별개 주제"라고 분리하는 것이 진짜 답이다

성공까지 감싸는 공통 래퍼(envelope)는 트레이드오프다.

장점

  • 성공과 실패의 파싱 구조가 완전히 같아진다
  • 상태 코드를 읽기 어려운 일부 레거시 환경에서 유용

단점

  • HTTP status라는 표준 신호와 정보가 중복
  • 성공 응답마다 포장 비용
  • 표준 도구와 결이 어긋난다 — OpenAPI 스키마 생성, HTTP 캐시 의미론

REST를 제대로 쓴다면 "성공은 맨 바디, 실패만 표준 에러 스키마"가 일반적 권장이다.

그리고 답할 때 중요한 것은 "에러 응답 표준화는 성공 래퍼 없이도 성립한다"는 점을 분리해 말하는 것이다 — 이 둘을 한 덩어리로 묶어 생각하는 것이 흔한 혼동이다. "에러 포맷을 통일하려면 성공도 감싸야 한다"는 전제부터 틀렸다.

하나의 에러 code가 상황에 따라 다른 HTTP status로 나가도 되나요? 시니어 변별힌트: 두 축의 관계가 다대일인지 다대다인지의 문제다

code → status는 다대일로 고정하는 것이 원칙이다. 여러 code가 같은 400을 공유하는 것은 정상이지만(부류가 같으니까), 같은 code가 어떤 때는 409, 어떤 때는 422로 나가면 안 된다.

이유는 3절의 두 소비자로 설명된다. 같은 code인데 status가 흔들리면, 바디를 안 보는 소비자의 판단(재시도·캐시·서킷·에러율 분류)이 같은 실패에 대해 매번 달라진다. 재시도 로직이 어떤 날은 돌고 어떤 날은 안 도는 API가 되는 것이다. 소비자 입장에서 이것은 "간헐적으로 동작이 다른 API"로 보이고, 재현이 안 되는 버그 리포트가 된다.

그래서 코드 카탈로그의 "HTTP status" 칸이 필요하다. 카탈로그에 코드 · 의미 · status · 권장 행동을 함께 적는 순간, status가 code의 속성으로 고정되고 이 흔들림이 구조적으로 막힌다. 만약 정말로 상황에 따라 부류가 달라진다면 그것은 서로 다른 두 에러이므로 코드를 둘로 나누는 것이 맞다.

errors[]의 field 경로 표기는 어떻게 정하나요? 중첩 배열이면요?힌트: 후보 셋을 대고, 무엇을 고르든 "하나로 고정"이 결론이다

표기법 자체가 계약이다. 정해두지 않으면 서버는 items.0.quantity로 보내고 클라이언트는 items[0].quantity로 찾는 어긋남이 생기고, 그 결과 폼의 어느 칸에도 빨간 줄이 안 그어진다. 게다가 이 버그는 중첩 구조를 쓰는 화면에서만 나타나서 늦게 발견된다.

결론은 "무엇을 고르든 조직 전체에서 하나로 고정"이고, 문서에 중첩·배열 예시를 실제로 하나씩 실어두는 것이 가장 싼 방지책이다. 덧붙여 요청 바디에 없는 잘못(예: 쿼리 파라미터 오류, 두 필드의 조합이 모순인 경우)을 어떻게 표기할지도 정해야 한다 — field를 null로 두고 reason만 채우는 규칙을 흔히 쓴다.

RFC 9457은 왜 status를 헤더와 바디에 중복해서 담나요? 가산점힌트: 응답이 언제나 헤더와 함께 이동하지는 않는다

바디만 따로 떨어져 나가는 순간이 실제로 많기 때문이다. 로그에 응답 본문만 적재되거나, 이슈 트래커에 바디만 복붙되거나, 큐·파일로 에러 문서만 옮겨지는 경우 헤더는 사라지고 바디만 남는다. 그때 바디 안에 status가 있으면 부류(재시도 가능성·클라이언트 잘못인지 서버 잘못인지)를 여전히 알 수 있다.

대신 반드시 지켜야 할 제약이 붙는다 — 헤더의 상태 코드와 항상 같은 값이어야 한다. 둘이 어긋나면 바디를 보는 소비자와 헤더를 보는 소비자가 서로 다른 결론에 도달하고, 이것은 3절의 두 축이 모순되는 최악의 상태다. 그래서 이 값은 손으로 채우지 말고 응답을 만드는 한 곳에서 상태 코드로부터 파생시켜야 한다.

같은 이유로 자체 포맷을 쓰더라도 바디에 status 사본을 넣는 선택은 합리적이다. 다만 "클라이언트가 재시도 판단을 바디의 status로 하라"는 뜻은 아니다 — 그 판단은 여전히 실제 헤더로 한다.

에러 응답이 캐시되면 어떤 문제가 생기나요?힌트: 캐시 판단 축은 status이고, 바디에는 매번 달라야 하는 값이 들어 있다

캐시 여부를 정하는 축은 바디가 아니라 status와 캐시 헤더다(3절의 겉봉). 그런데 우리 에러 바디에는 매 발생 건마다 달라야 하는 값이 들어 있다 — traceId, 그리고 Problem Details의 detail·instance가 그렇다.

그래서 에러 응답이 캐시되면 두 가지가 동시에 망가진다. ① 사용자에게 남의 요청의 traceId가 표시되어 CS 흐름(4-3)이 엉뚱한 로그를 가리킨다. ② 이미 해결된 실패가 계속 재생되어 사용자가 재시도해도 같은 에러 화면을 본다.

실무 지침은 단순하다 — 에러 응답에는 캐시 금지를 명시적으로 지정한다. 특히 일부 상태 코드는 명시적 캐시 헤더가 없으면 캐시 가능으로 분류될 수 있다는 점을 알아야 한다(대표적으로 404). "에러니까 당연히 캐시 안 되겠지"라는 가정이 성립하지 않는 구간이 있다는 것이 요점이다. 반대로 의도적으로 캐시하고 싶은 에러(예: 영구 삭제된 리소스의 410)라면 그때는 traceId 같은 건별 값을 빼는 것까지 같이 결정해야 한다.

벌크 API처럼 일부만 실패하면 이 스키마로 표현할 수 있나요?힌트: 최상위 에러 스키마로는 못 담는다. 그런데 재사용할 수 있는 부분이 있다

최상위 에러 스키마로는 담을 수 없다. 지금까지의 스키마는 "요청 전체가 실패했다"를 전제로 하고, status도 그 전제 위에서 하나만 붙는다. 100건 중 3건만 실패한 요청에 단일 status와 단일 code를 붙이려는 순간 어느 쪽으로 붙여도 거짓말이 된다.

그래서 부분 실패는 별도의 계약이 필요하다 — 요청 자체는 처리에 성공했다고 보고, 항목별 결과 배열로 각 건의 성공/실패를 돌려주는 형태가 일반적이다.

여기서 재사용할 수 있는 것이 요점이다. 항목별 결과 요소 안에 같은 {code, message} 구조를 그대로 넣으면, 소비자는 이미 짜둔 에러 파서와 code 분기 테이블을 그대로 재활용한다. 바깥 껍데기는 달라도 안쪽 에러 표현은 같은 타입이라는 설계가 표준화의 이득을 부분 실패까지 확장한다. (상세: 16-bulk-api-partial-failure-response.md, 13-aggregation-api-partial-failure-contract.md)

GraphQL처럼 status 축이 사실상 없는 프로토콜에서는 어떻게 하나요? 가산점힌트: 축이 하나 사라지면 무엇이 대신 그 일을 해야 하는지 말한다

GraphQL은 관례적으로 전송 계층에서 200을 쓰고 바디의 errors 배열로 실패를 표현한다. 즉 3절의 겉봉 축이 사라진 상태다. 그래서 이 프로토콜에서는 두 가지가 강제된다.

① 세부 축(code)을 반드시 자체적으로 세워야 한다 — 폴백할 부류가 없기 때문이다. 관례적으로 errors[].extensions 안에 자체 코드를 넣고, 클라이언트는 이 값으로 분기한다. ② 모니터링과 재시도 로직이 바디를 파싱해야 한다 — 겉봉만 보는 인프라(게이트웨이·APM)는 전부 성공으로 집계하므로, 에러율 지표를 만들려면 바디를 여는 별도의 장치가 필요하다.

이 대비가 REST에서 두 축을 나눈 가치를 거꾸로 증명한다. "축을 하나 없앴더니 인프라가 하던 일을 전부 애플리케이션이 떠안게 됐다"가 정확한 요약이고, 이것이 REST API에서 에러를 200에 담으면 안 되는 이유와 같은 구조다.

코드 카탈로그가 코드베이스와 어긋나지 않게 하려면요?힌트: 사람이 두 곳을 손으로 맞추는 구조를 없애는 것이 답이다

문서와 구현을 사람이 손으로 동기화하는 구조면 반드시 어긋난다. 새 코드를 추가하는 커밋과 문서를 고치는 작업이 다른 시점·다른 사람에게 있기 때문이다. 그리고 어긋난 문서는 안 읽히는 문서가 되어 1절의 "슬랙으로 물어보기"로 되돌아간다.

방향은 하나다 — 원본(single source of truth)을 코드에 두고 문서를 파생시킨다. 에러 코드를 열거형 등 한 곳에서 정의하고, 각 항목에 의미 · HTTP status · 권장 행동을 속성으로 달아두면, 카탈로그 표는 그것으로부터 생성되고 status 고정(앞의 다대일 규칙)도 구조적으로 보장된다.

여기에 검증을 자동화하면 완성이다 — 권장 행동이 비어 있는 코드가 있으면 빌드에서 걸리게 하는 식이다. 5-2의 분리 기준("클라이언트가 다르게 행동할 때만")이 규칙에서 검사 가능한 조건으로 내려온 형태다. (문서-구현 동기화 일반론: 15-api-docs-implementation-sync.md)

한 줄 요약
에러 응답 표준화는 포맷 통일이 아니라 계약 설계다 — 바디를 안 보는 인프라가 읽는 축(HTTP status)과 클라이언트 분기가 읽는 축(불변 code)을 나눈 단일 스키마를 정하고, 여기에 사람용 message·검증 상세 errors[]·분산 추적의 진입점 traceId를 얹은 뒤, 코드 분리 기준("클라이언트가 다르게 행동할 때만")과 진화 규칙(필드 추가는 안전, 코드 삭제는 금지, 모르는 코드는 status로 폴백)까지 문서화해 소비자와 공유하며, 외부 공개 API라면 RFC 9457이라는 표준 골격 위에 자체 code를 확장 멤버로 얹는 것까지 검토하는 것이 "여러 팀이 소비하는 제품"으로서의 API 설계다.
