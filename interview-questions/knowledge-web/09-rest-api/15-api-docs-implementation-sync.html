API 문서-구현 동기화
문서가 거짓말하지 않게 만드는 체계

면접 질문: "API 문서와 실제 구현의 불일치를 어떻게 방지하나요? (Swagger 어노테이션 vs Spring REST Docs)"

핵심 관전 포인트 — 문서-구현 불일치의 근본 원인은 게으름이 아니라 구조다. 코드는 컴파일러와 테스트가 매일 검증하는데 문서는 아무도 검증하지 않으므로, 문서는 반드시 낡는다. 그래서 해법은 "부지런히 고치자"가 아니라 문서를 검증 루프 안에 집어넣는 것이고, 그 루프의 재료가 OpenAPI라는 규격이다. OpenAPI는 API의 경로·파라미터·응답 스키마를 사람의 문장이 아니라 기계가 읽는 YAML/JSON으로 적어 둔 규격이라, 그 파일 하나에서 문서 UI도 클라이언트 코드도 검증기도 스펙 diff도 나온다. 접근은 둘로 갈린다 — ① springdoc-openapi가 컨트롤러를 스캔해 규격을 뽑고 Swagger UI가 그것을 화면으로 그려주는 방식은 경로·메서드·타입 같은 구조적 사실은 코드에서 추출되므로 저절로 정확하지만 손으로 쓴 서술(에러 응답, 제약 조건, 예제 값)은 아무도 검증하지 않아 그대로 거짓말이 남고, ② Spring REST Docs는 테스트가 실제 요청을 보내고 응답을 검증해야만 문서 조각(snippet)을 뱉으므로 "문서에 적힌 것 = 검증된 것"이 강제된다. 정확성이 계약 수준이면 REST Docs 또는 스펙 우선 + CI 검증, 내부용 빠른 탐색이 목적이면 Swagger UI이며, 둘을 결합해 테스트에서 OpenAPI를 생성하는 절충도 있다. 마지막 층이 소비자 주도 계약 테스트(CDC)다 — 소비자가 "나는 이 요청에 이런 응답을 기대한다"를 계약 파일로 등록하고 제공자 빌드가 그것을 재생해 검증하므로, "문서와 다르다"를 넘어 "소비자가 실제로 쓰는 방식과 다르다"를 잡는다. 관통하는 원칙은 하나다 — 사람의 성실함이 아니라 빌드 파이프라인이 문서의 정확성을 보증하게 한다.
  • 1
    불일치는 성실함이 아니라 구조의 문제다 — 응답 DTO에서 필드를 지우면 코드는 컴파일에서 터지지만, 같은 필드를 문서에서 안 지워도 빌드는 초록불이다. 틀렸다는 신호가 존재하지 않는 산출물은 반드시 틀린 채로 남는다. 그래서 진짜 답은 "부지런히 고친다"가 아니라 "문서가 틀리면 빌드가 깨지게 만든다"이다.
  • 2
    두 도구의 차이는 "무엇이 검증되는가"에 있다 — springdoc은 경로·메서드·파라미터 타입·응답 DTO 필드 같은 구조적 사실을 코드에서 추출하므로 그 부분은 어긋날 수 없지만, 손으로 쓴 서술(특히 어느 에러가 실제로 나가는지)은 그냥 문자열이라 검증되지 않는다. REST Docs는 통과한 테스트가 실제로 주고받은 요청·응답으로 문서 조각을 만들어, 문서와 응답이 어긋나는 순간이 곧 테스트가 깨지는 순간이 된다.
  • 3
    정확성 요구 수준에 따라 방어선을 층으로 쌓는다 — 내부 탐색용이면 springdoc + Swagger UI, 계약 수준이면 REST Docs 또는 스펙 우선 + CI 스펙 diff, 그 위에 CDC를 얹는다. 세 층이 잡는 것이 다르다 — 스펙 diff는 "규칙 위반", CDC는 "실제 소비", REST Docs는 "문서와 구현의 일치"다.

0. 질문 + 출제 의도

출제 의도: 문서가 한 번 거짓말하면 아무도 안 믿게 되고, 그때부터 협업은 슬랙 질문으로 회귀한다. 테스트에서 문서를 생성(REST Docs)하거나 계약을 우선하는 접근을 아는지 — 문서를 신뢰 가능한 산출물로 관리하는 체계를 본다.

1. OpenAPI란 무엇인가 — 스펙 하나에서 여섯이 나온다

이 문서에 나오는 "스펙 우선", "스펙 diff", "스펙에서 코드 생성"이라는 말이 전부 이 개념 하나에 얹혀 있다. 여기부터 정확히 정의하고 시작한다.

한 문장 정의 OpenAPI는 API의 경로·HTTP 메서드·요청 파라미터·요청과 응답 바디의 필드와 타입·가능한 상태 코드를, 사람이 읽는 문장이 아니라 기계가 읽을 수 있는 형식(YAML 또는 JSON)으로 적어 두는 규격이다. 사람이 "이 API는 주문 하나를 조회하고, 없으면 404를 줍니다"라고 문장으로 적는 자리에, OpenAPI는 같은 내용을 구조화된 데이터로 적는다.
SPEC openapi.yaml — 사람이 읽어도 되지만, 애초에 기계가 읽으라고 만든 형식이다
openapi: 3.0.3
paths:
  /orders/{id}:                    # 경로
    get:                           # HTTP 메서드
      summary: 주문 조회
      parameters:
        - name: id
          in: path                 # 이 파라미터가 "경로에 박혀 있다"는 사실까지 데이터다
          required: true
          schema: { type: integer, format: int64 }
      responses:
        '200':
          content:
            application/json:
              schema:
                type: object
                properties:        # 응답 바디의 필드와 타입 — 이것이 기계 판독의 핵심
                  id:     { type: integer, format: int64 }
                  amount: { type: integer, description: 결제 금액(원) }
                  status: { type: string, enum: [PENDING, PAID, CANCELLED] }
        '404':
          description: 주문 없음

1-1. "기계가 읽을 수 있다"가 왜 중요한가

규격 파일 하나에서 여러 산출물을 자동으로 만들어낼 수 있기 때문이다. 문장으로 쓴 문서로는 아무것도 만들 수 없지만, 구조화된 데이터로는 만들 수 있다. 이것이 이 문서 전체가 "그냥 문서"가 아니라 "OpenAPI"에서 출발하는 이유다.

면접에서 "왜 그냥 위키가 아니라 OpenAPI인가"를 물으면 이 여섯을 대면 된다. 기계 판독 형식을 고르는 이유는 예쁜 화면이 아니라 이 여섯 가지 파생물이다.

2. Swagger · OpenAPI · springdoc · Swagger UI — 세 층으로 가르면 끝난다

현장에서 이 네 이름이 뒤섞여 쓰인다. "규격 / 규격을 만드는 도구 / 규격을 보여주는 도구"라는 세 층으로 갈라 보면 관계가 한 번에 정리된다.

네 이름의 정체. "설치하는 것"과 "형식인 것"을 구분하는 줄이 이 표의 핵심이다.

세 층 이름표 — "규 · 만 · 보"

규 = OpenAPI Spec (형식)←만듦― 만 = springdoc (라이브러리)―읽음→ 보 = Swagger UI (화면)

"우리는 Swagger 씁니다"의 정확한 뜻은 대개 "springdoc이 만들어 준 OpenAPI 문서를 Swagger UI로 본다"이다. 세 층이 전부 관여하는데 사람들은 화면에 보이는 UI의 이름으로 전체를 부른다. 면접에서 이 층 구분을 한 문장으로 정리하면 "도구를 써 본 사람"과 "구조를 아는 사람"이 갈린다.

3. source of truth — 어긋났을 때 어느 쪽이 정답인가

용어 하나를 더 깔고 간다. source of truth(유일한 진실 공급원)란, 같은 정보가 여러 곳에 존재할 때 서로 어긋나면 어느 쪽을 정답으로 볼지 미리 정해 둔 그 한 곳을 말한다.

API 정보는 최소한 두 곳에 있다 — 코드와 문서다. 코드 우선 방식(springdoc, REST Docs)에서는 코드가 정답이고 문서는 그 그림자다. 스펙 우선 방식에서는 스펙 파일이 정답이고 코드가 그것을 따라간다.

정답의 자리를 안 정해 둔 팀

  • 코드는 400을 주는데 문서에는 404라고 적혀 있다
  • 서버 개발자: "문서가 낡았어요"
  • 프론트 개발자: "구현이 잘못됐는데요"
  • 누구도 무엇이 버그인지 말할 수 없다

이 논쟁은 기술 문제가 아니라 조직 문제다 — 정답의 자리를 정해 두지 않았기 때문에 판정 자체가 불가능하다.

정답의 자리를 정해 둔 팀

  • 코드 우선이면: 문서가 낡은 것 → 문서 갱신이 과제
  • 스펙 우선이면: 구현이 스펙을 어긴 것 → 구현 수정이 과제
  • 어느 쪽이든 다음 행동이 즉시 정해진다

중요한 것은 어느 쪽을 고르느냐가 아니라, 고르지 않으면 판정이 불가능해진다는 점이다.

source of truth를 정하는 것은 "어느 도구가 좋은가"의 문제가 아니라 "누가 틀린 것인지 판정 가능하게 만드는가"의 문제다

4. 문서는 왜 반드시 낡는가 — "비 · 핫 · 신"

이제 본론이다. 불일치는 개인의 게으름이 아니라 구조에서 나온다. 문서와 코드가 별도 산출물일 때 무슨 일이 벌어지는지 세 단계로 본다. 면접에서 이 세 가지를 순서대로 대면 "문서 잘 씁시다"류의 답과 완전히 갈린다.

4-1. 첫째, 비대칭 — 검증자가 한쪽에만 있다

코드는 컴파일러와 테스트가 매일 검증하지만, 문서는 아무도 검증하지 않는다. 응답 DTO에서 필드 하나를 지우면 그것을 참조하던 코드가 컴파일에서 터진다. 그런데 같은 필드를 문서에서 지우지 않아도 아무 일도 일어나지 않는다. 빌드는 초록불이고 테스트는 전부 통과한다.

틀렸다는 신호가 존재하지 않는 산출물은 반드시 틀린 채로 남는다

4-2. 둘째, 가장 중요한 변경일수록 문서가 먼저 낡는다

급한 수정(hotfix)일수록 "일단 배포부터 하고 문서는 나중에"가 된다. 그런데 급한 수정은 대개 에러 처리나 예외 흐름을 건드리고, 그 부분이야말로 소비자가 문서를 가장 많이 찾아보는 대목이다.

그래서 낡는 순서가 최악이다 잘 안 바뀌는 정상 응답 스펙은 문서가 맞는 채로 남고, 자주 바뀌는 에러 응답·제약 조건이 먼저 낡는다. 소비자는 정상 흐름은 한 번 보고 외우지만 에러 처리는 볼 때마다 문서를 찾는다. 즉 가장 많이 조회되는 부분이 가장 먼저 거짓말이 된다.

4-3. 셋째, 문서의 신뢰는 0 아니면 1이다

이 비대칭이 이 문제를 특별하게 만든다. 한 번이라도 문서대로 했는데 400이 떨어진 경험을 하면, 소비자는 그 뒤로 문서를 안 보고 담당자에게 물어본다. 그리고 한 번 그렇게 된 팀은 문서를 고쳐도 신뢰가 돌아오지 않는다 — 고쳐졌는지 확인하려면 결국 문서를 믿어야 하는데, 그 믿음이 이미 없기 때문이다.

비유 — 양치기 소년 양치기 소년이 거짓말을 한 번 했다고 마을 사람들이 10%만 안 오는 것이 아니다. 다음부터는 아무도 안 온다. 문서도 똑같다. 90%가 정확한 문서는 90%의 가치가 있는 것이 아니라, 매번 검증해야 하므로 사실상 0에 가깝다. 문서의 가치는 "최신인가"가 아니라 "믿을 수 있는가"에 있다.

문서가 낡는 구조 3층 — "비 · 핫 · 신"

비
비대칭

핫

문서가 틀리면 빌드가 깨지게 만든다 — 문서를 검증 루프에 편입시킨다

5. springdoc — 코드에서 문서를 추출한다

springdoc은 애플리케이션이 뜰 때 컨트롤러를 스캔한다. 매핑 어노테이션에서 경로와 메서드를, 메서드 시그니처와 반환 타입에서 파라미터와 응답 스키마를, @NotNull 같은 Bean Validation 어노테이션에서 필수 여부와 제약을 읽어 OpenAPI 문서를 조립한다. 여기에 사람이 @Operation, @Schema 같은 서술 어노테이션으로 설명을 덧붙인다.

배경 — Bean Validation이 여기서 하는 일 @NotNull, @Min, @Size 같은 어노테이션은 원래 런타임 입력 검증용이다. 그런데 springdoc이 같은 어노테이션을 읽어 스펙의 required·minimum·maxLength로 옮긴다. 그래서 제약을 어노테이션으로 걸어 두면 "검증 코드"와 "문서"가 같은 한 줄에서 나온다 — 이 부분만큼은 어긋날 수 없다. 5-3의 완화책이 이 성질을 최대한 이용하는 방법이다.

5-1. 강점 — 구조적 사실은 저절로 정확하다

springdoc 컨트롤러에 서술 어노테이션을 붙인 전형적인 모습
@Operation(summary = "주문 조회", description = "주문 상세를 반환한다")
@ApiResponse(responseCode = "200", description = "조회 성공")
@GetMapping("/orders/{id}")
public OrderResponse getOrder(@PathVariable Long id) { ... }

진입 장벽이 낮고, 구조적 사실이 저절로 정확하다. 여기서 "구조적 사실"이 무엇인지 정확히 짚어야 한다 — 경로(/orders/{id}), HTTP 메서드(GET), 파라미터 이름과 타입(id, Long), 응답 DTO의 필드와 타입이다. 이것들은 사람이 문서에 옮겨 적는 것이 아니라 코드에서 추출되므로, 구현과 어긋날 방법이 없다. 필드 이름을 바꾸면 문서의 필드 이름도 자동으로 바뀐다. 여기에 Swagger UI의 try-it-out으로 브라우저에서 바로 호출해볼 수 있으니 탐색·QA·프론트 협업에는 확실히 편하다.

면접에서 감점되는 대답 — "Swagger는 부정확합니다" 이건 틀린 답이다. springdoc이 만든 문서에서 경로·메서드·파라미터 타입·응답 DTO 필드는 코드에서 추출되므로 절대 어긋나지 않는다. 부정확해지는 것은 딱 한 종류 — 사람이 손으로 쓴 서술이다. 이 구분을 못 하면 "두 도구의 차이를 모른다"로 읽힌다.

5-2. 약점 — 하필 "손으로 쓴 서술"이 자주 틀린다

약점은 정확히 강점의 반대편에 있다. 에러 응답, 제약 조건, 필드의 업무적 의미, 예제 값 — 이것들은 코드에서 추출할 수 없어서 어노테이션에 사람이 적어야 하고, 그 순간 4-1에서 말한 "아무도 검증하지 않는 산출물"이 코드 옆으로 자리만 옮겨 온 것이 된다.

BAD 어노테이션 기반 문서의 전형적 거짓말
@ApiResponse(responseCode = "404", description = "주문 없음")   // 문서에는 404라고 적혀 있다그냥 문자열
@GetMapping("/orders/{id}")
public OrderResponse getOrder(@PathVariable Long id) {
    return orderService.find(id);   // 그런데 예외 핸들러가 400을 반환하도록 바뀐 지 오래다
}
// 컴파일 통과 ✔  테스트 통과 ✔  문서는 거짓말 ✘ — 어긋났다는 신호가 어디에도 없다

이 예시가 보여주는 한 문장

@ApiResponse에 적은 404는 그저 문자열이다

컨트롤러가 실제로 어떤 상태 코드를 내보내는지와 아무 연결이 없다. 그래서 예외 핸들러를 고치는 커밋이 이 줄을 건드리지 않아도 되고, 아무도 이 줄이 낡았다는 것을 알 수 없다. 부수 문제로, 문서를 풍부하게 만들수록 프로덕션 코드가 문서 어노테이션으로 뒤덮여 비즈니스 로직의 가독성을 해친다 — 컨트롤러 메서드 하나에 어노테이션 열 줄이 붙고 실제 코드는 두 줄인 상황이 흔하다.

5-3. 그래도 Swagger를 써야 한다면 — 완화책 "줄 · 스 · 표"

구조는 못 바꿔도 거짓말할 표면적은 줄일 수 있다. 핵심 발상은 하나다 — 사람이 손으로 쓰는 서술의 양 자체를 줄이고, 그 자리를 코드에서 추출되는 것으로 대체한다.

BEFORE 서술 어노테이션에 전부 손으로 적었다
@Operation(summary = "주문 생성",
  description = "amount는 1 이상. 0을 보내면 400.")미검증
@ApiResponse(responseCode = "201", description = "생성 성공")
@ApiResponse(responseCode = "400", description = "amount가 0 이하")미검증
@ApiResponse(responseCode = "409", description = "중복 주문")미검증

public record OrderCreateRequest(Integer amount) {}
// 제약(1 이상)이 코드에 없고 문장에만 있다
// -> 검증 로직을 고쳐도 이 문장은 그대로 남는다
AFTER 제약은 코드로, 에러는 공통 모델 하나로

    @NotNull @Min(1)                       // 검증 = 문서

Swagger를 쓰면서 불일치를 줄이는 현실적 방법 — "줄 · 스 · 표"

줄

타입·필수 여부·제약은 타입 시스템과 Bean Validation에서 추출되게 하고, 손으로 쓰는 문장의 양 자체를 줄인다. 검증되지 않는 부분이 적을수록 거짓말할 표면적이 준다

6. Spring REST Docs — 테스트에서 문서를 생성한다

발상이 반대다. 문서를 코드 옆에 적는 대신, 통과한 테스트가 남긴 실제 요청과 실제 응답으로 문서를 만든다.

비유 — 레시피 카드 vs 완성 사진 어노테이션 문서는 "이렇게 만듭니다"라고 적어 둔 레시피 카드다. 실제로 그렇게 만들어졌는지 아무도 확인하지 않는다. REST Docs 문서는 실제로 만들어 낸 요리를 찍은 사진이다 — 사진이 존재한다는 것 자체가 요리가 만들어졌다는 증거이고, 요리가 바뀌면 사진도 바뀔 수밖에 없다. 이 한 문장 차이가 두 도구의 전부다.
GOOD REST Docs — 문서화 코드가 곧 단언(assertion)이다
@Test
void 주문_조회_문서화() throws Exception {
    mockMvc.perform(get("/orders/{id}", 1L))
        .andExpect(status().isOk())                       // ① 실제 동작을 먼저 검증하고
        .andDo(document("order-get",                      // ② 통과한 요청/응답으로 문서 조각 생성
            pathParameters(
                parameterWithName("id").description("주문 ID")),
            responseFields(                                // ★ 설명을 다는 자리이자 동시에 단언
                fieldWithPath("id").description("주문 ID"),
                fieldWithPath("amount").description("결제 금액(원)"),
                fieldWithPath("status").description("주문 상태"))));
}

responseFields는 문서에 쓸 설명을 다는 자리인 동시에 "응답에 정확히 이 필드들이 있다"는 단언(assertion)이기도 하다. 양방향으로 깨진다는 점이 중요하다.

방향 ① 문서에 있는데 응답에 없다

응답 DTO에서 amount를 지웠다 → responseFields에 선언한 필드가 응답에 없다 → 테스트 실패 → 빌드 실패

낡은 문서를 못 남기게 막는 방향이다.

방향 ② 응답에 있는데 문서에 없다

응답에 couponId를 추가하고 문서화를 잊었다 → 선언되지 않은 필드가 응답에 있다 → 테스트 실패 → 빌드 실패

문서화 누락까지 잡는 방향이다. 어노테이션 방식에는 이 방향의 방어가 아예 없다.

문서와 응답이 어긋나는 순간이 곧 빌드가 깨지는 순간이 된다 — 4-1의 오른쪽에 루프가 생겼다

6-1. 문서 조각(snippet)과 AsciiDoc — 2단 조립 구조

여기서 "문서 조각"이라는 말이 처음 나왔으므로 정의하고 간다. snippet은 REST Docs가 테스트 하나마다 만들어 내는 작은 문서 파일들이다. 하나의 완성된 문서가 아니라, 최종 문서에 끼워 넣을 부품이다.

그런데 이 조각들만으로는 문서가 되지 않는다. "이 API가 왜 있는지, 언제 쓰는지, 인증은 어떻게 하는지" 같은 서술은 테스트가 만들어낼 수 없기 때문이다. 그래서 사람이 뼈대 문서를 쓰고 거기에 조각을 끼워 넣는 2단 구조가 된다.

REST Docs의 분업 — 사실은 기계, 서술은 사람

기계가 만드는 것 (사실)
실제 요청 원문 · 실제 응답 원문 · curl 예시 · 파라미터 표 · 응답 필드 표 — 전부 통과한 테스트에서 나온다
사람이 쓰는 것 (서술)
이 API가 왜 있는지 · 언제 쓰는지 · 인증 방법 · 용어 설명 — 이 부분은 REST Docs에서도 검증되지 않는다

즉 REST Docs도 "전부 검증된다"가 아니다. 8절 비교표의 "무엇이 검증되지 않나" 줄에서 이 선을 정확히 그어야 한다.

6-2. 강점과 약점

강점 — 문서화가 곧 검증이다

  • 문서에 적힌 모든 필드는 테스트를 통과한 실제 응답에서 나온 것이므로 구조적으로 거짓말할 수 없다
  • 구현이 바뀌면 문서 테스트가 깨져서 문서 갱신을 잊는 것이 불가능해진다
  • 프로덕션 코드에 문서 어노테이션이 쌓이지 않는다 (문서화 코드가 테스트에 위치)
  • 예제 값이 실제 응답 원문이라 "예제가 옛날 값"이라는 문제가 없다

약점 — 비용이 크고 자유도가 낮다

  • 문서화할 필드를 테스트에 전부 선언해야 하므로 작성 비용이 만만치 않다
  • try-it-out 같은 인터랙티브 UI가 기본으로는 없다 (9-1의 결합형으로 보완)
  • 문서 서술의 자유도가 낮다
  • "테스트가 커버하는 케이스만" 문서화되므로, 테스트 문화가 약한 팀에서는 오히려 유지가 안 된다 — 문서를 만들려면 테스트를 먼저 써야 하는데 그 테스트를 안 쓰는 팀이라면 문서 자체가 안 생긴다

7. 무엇으로 요청을 보내는가 — MockMvc · WebTestClient · REST Assured 시니어 변별

REST Docs는 테스트에서 오간 요청과 응답을 받아 적는 도구일 뿐이고, 실제로 요청을 보내는 일은 별도의 테스트 클라이언트가 한다. 선택지가 셋이고, 셋의 차이는 무엇을 태우고 무엇을 태우지 않는가다. 이 차이가 11절 꼬리질문("mock으로 쓰면 그것도 거짓말 아닌가")의 답과 직결된다.

세 클라이언트의 범위. 꼬리질문에서는 이 표를 그대로 답으로 쓰면 된다.
도구서블릿 컨테이너(톰캣)를 띄우나실제 네트워크를 타나무엇까지 검증되는가
MockMvc아니오. MockHttpServletRequest라는 가짜 서블릿 객체를 만들어 DispatcherServlet에 직접 넘긴다아니오 — 같은 JVM 안에서의 메서드 호출이다컨트롤러 매핑, 인자 바인딩, 검증, 예외 핸들러, JSON 직렬화. 필터는 명시적으로 등록한 것만 (스프링 시큐리티 연동 시에는 자동 등록된다)
WebTestClient설정에 따라 다르다. 애플리케이션 컨텍스트에 바인딩하면 안 띄우고, @SpringBootTest(webEnvironment = RANDOM_PORT)와 함께 쓰면 실제로 뜬 서버의 포트에 붙는다모드에 따라 다르다mock 모드면 MockMvc와 비슷한 범위, 실제 서버 모드면 아래 REST Assured와 같은 범위
REST Assured예. 실제로 떠 있는 서버에 붙는다예 — 진짜 HTTP 요청이다서블릿 컨테이너, 전체 필터 체인, 보안 체인, 실제 직렬화까지 전부
함께 나오는 용어 — 슬라이스 테스트(slice test) 애플리케이션의 모든 빈을 올리는 대신 특정 층(slice)에 필요한 빈만 올리는 테스트를 말한다. @WebMvcTest가 대표적인데, 컨트롤러와 그 주변(메시지 컨버터, 예외 핸들러)만 올리고 @Service·@Repository는 올리지 않는다. 그래서 컨텍스트가 가볍고 빠른 대신, 서비스 계층은 @MockBean(Spring Boot 3.4부터는 @MockitoBean)으로 가짜를 채워 넣어야 한다. 이 "가짜를 채워 넣는다"가 11절 꼬리질문의 쟁점이 되는 지점이다.

8. 비교 — 검증되는 영역을 색으로 가른다

두 접근을 나란히 놓을 때, 값이 나가는 줄은 딱 두 개다 — 무엇이 저절로 맞고, 무엇이 검증되지 않는가. 이것을 구분해 말하는 것이 이 질문의 정확도를 가른다. "Swagger는 부정확하다"고 뭉뚱그리면 틀린 답이다.

두 접근 비교 요약. 위 두 줄이 이 표의 전부이고, 나머지는 그 결과다.

무엇이 검증되지 않나손으로 쓴 서술 전부 — description, 예제 값, 제약 조건 설명, 그리고 어느 에러 응답이 실제로 나가는지뼈대 문서에 사람이 쓴 산문(개요, 용어 설명, 인증 안내)

9. 방어선을 층으로 쌓는다 — 결합형 · 스펙 우선 · CDC

9-1. 결합형: 테스트에서 OpenAPI를 생성한다 가산점

두 접근의 장점이 서로 배타적이지 않다는 점이 이 절의 출발이다. REST Docs가 주는 것은 검증이고 Swagger UI가 주는 것은 화면인데, 이 둘은 다른 층의 이야기다.

REST Docs 테스트→ 통과한 요청·응답→ OpenAPI 스펙 생성 (restdocs-api-spec 등)→ Swagger UI 렌더링→ 검증된 스펙 + 인터랙티브 문서

그래서 REST Docs 테스트 결과에서 OpenAPI 스펙 파일을 생성하는 확장(restdocs-api-spec 같은 오픈소스)을 얹으면 둘 다 얻는다. 검증은 테스트가 하고, 생성된 스펙 파일을 Swagger UI가 읽어 화면을 그린다.

1절의 표를 다시 보면 이 조합의 값이 더 커진다 스펙 파일이 손에 들어오는 순간 클라이언트 코드 생성, 스펙 diff, 런타임 검증기까지 전부 붙일 수 있게 된다("문·클·서·검·목·디"). REST Docs 단독은 사람이 읽는 HTML에서 끝나지만, 스펙을 뽑아내면 기계가 쓸 수 있는 자산이 된다.

9-2. 스펙 우선(contract-first) — 정답의 자리를 스펙 파일로 옮긴다

지금까지의 두 방식은 모두 코드 우선이다. 코드가 먼저 있고 문서는 거기서 파생된다. 반대 방향도 있다. 스펙 우선은 OpenAPI 스펙을 먼저 쓰고 그것을 source of truth로 삼는 방법이다 — 3절에서 말한 "정답의 자리"를 코드가 아니라 스펙 파일에 두는 것이다.

① 구현이 스펙에서 벗어나기 어려워진다
스펙에서 서버 인터페이스와 DTO를 생성해 컨트롤러가 그 인터페이스를 구현하게 하면, 스펙에 없는 응답을 내보내는 코드가 애초에 컴파일되지 않는다.
② 병렬 개발이 가능해진다
실무에서 가장 크게 체감되는 이득이다. 스펙만 합의하면 프론트는 생성된 클라이언트나 mock 서버로 즉시 화면을 만들고 백엔드는 그동안 구현한다. 코드 우선에서는 백엔드가 만들 때까지 프론트가 기다린다.
③ 스펙이 저장소의 파일이라 PR 리뷰를 태울 수 있다
"말로 합의하고 코드는 딴판"이 구조적으로 어려워진다. 값은 파일 형식이 아니라 변경 이력과 리뷰 절차가 코드와 같은 수준으로 붙는다는 데 있다.

여기에 CI 검사를 얹으면 계약이 유지된다. 실제 응답을 스펙과 대조 검증하거나, 스펙 diff로 파괴적 변경을 감지해 빌드를 실패시키는 것이다. 이 스펙 diff가 08-backward-compatible-api-changes.md에서 말하는 호환성 방어선의 첫 층이다 — 필드 삭제, 타입 변경, 선택 파라미터의 필수화 같은 규칙 위반을 사람의 리뷰가 아니라 CI가 잡는다.

9-3. 소비자 주도 계약 테스트(CDC) — 문서가 아니라 실제 소비를 잡는다

스펙 diff에는 원리적인 한계가 하나 있다. 스펙 diff는 "규칙 위반"을 잡을 뿐, "실제로 누가 무엇을 쓰는지"는 모른다.

규칙상 안전한데 실제로 깨지는 경우

스펙상 optional로 선언해 둔 필드를 지우는 것은 규칙 위반이 아니다. 그런데 어느 소비자가 그 필드에 의존하고 있었다면 그 소비자는 깨진다.

규칙상 위반인데 실제 피해가 0인 경우

아무도 안 쓰는 필드를 지우는 것은 규칙상 파괴적 변경이라 CI가 막지만, 실제 피해는 0이다.

소비자 주도 계약 테스트(CDC, consumer-driven contract testing)는 이 빈틈을 메운다. 이름 그대로 계약을 제공자가 아니라 소비자가 주도해서 쓴다는 것이 이 방식의 정체다.

비유 — 열쇠 본을 떠서 맡겨 둔다 소비자가 자기 자물쇠의 본을 떠서 공용 보관함에 맡겨 둔다. 제공자는 열쇠 모양을 바꿀 때마다 보관함의 본에 실제로 꽂아 본다. 안 맞으면 열쇠를 배포하기 전에 알게 된다. "규격서상 이 열쇠가 표준에 맞는가"(스펙 diff)와 "이 열쇠가 실제로 저 집 문을 여는가"(CDC)는 다른 질문이다.

9-4. 세 방어선의 역할이 다르다 — "규 · 소 · 문"

방어선 3층 — "규 · 소 · 문"

규
스펙 diff
규칙 위반을 잡는다 — 필드 삭제 · 타입 변경 · 필수화
소
CDC
소비 실태를 잡는다 — "이 소비자가 이 필드를 읽고 있다"
문
REST Docs · 스펙 검증
문서-구현 일치를 잡는다

셋 다 사람의 성실함이 아니라 빌드가 판정한다는 공통점이 있다. 면접에서 "여러 겹을 쌓는다"고만 하지 말고 각 층이 무엇을 놓치는지까지 말하면 층 구분이 진짜라는 신호가 된다.

10. 선택 기준과 단계적 도입

도구를 고르는 기준은 취향이 아니라 "불일치가 났을 때 누가 얼마나 비싸게 다치는가"다.

A
소비자가 외부(파트너 · 공개)이고 문서가 계약이면 → 검증되는 문서가 필수다. REST Docs 또는 스펙 우선 + CI 검증.

09-partner-api-vs-internal-api.md에서 말하는 "문서가 참고자료에서 계약서로 바뀐다"가 이 선택의 근거다. 파트너 개발자는 우리 코드를 볼 수 없고 문서만 보고 구현하므로, 문서의 오류를 사람이 메워 줄 방법이 없다. 내부에서라면 슬랙 한 줄로 끝날 일이 외부에서는 연동 일정 지연과 반복 미팅이 된다.

B
소비자가 내부이고 속도 · 탐색이 우선이면 → springdoc + Swagger UI로 시작하되, 에러 응답처럼 거짓말이 잦은 부분만이라도 테스트로 고정한다.

전면 도입만이 선택지가 아니다. 8절 그림의 ④·⑤ 칸(실제 응답에 그 필드가 있는가 / 어떤 에러가 나가는가)만 REST Docs로 덮어도, 소비자가 가장 자주 데이는 곳은 막힌다.

10-1. 100개 API를 전부 옮길 수는 없다 — 위험 기반 분할

전면 전환이 아니라 위험 기반으로 나눈다. 기준은 "불일치가 났을 때의 비용"이다.

먼저 옮기는 것 — 사고 비용이 큰 API
외부 파트너에게 나가는 API, 결제 · 정산처럼 불일치 사고 비용이 큰 API → REST Docs 또는 계약 테스트
그대로 두는 것 — 내부 조회성 API
틀려도 슬랙 한 줄로 복구되는 내부 조회 API → springdoc 유지
전환 비용을 시간축으로 분산하는 한 문장 "신규 API부터 REST Docs를 기본으로 적용한다"는 전략을 얹으면 전환 비용이 시간축으로 분산된다 — 존재하는 100개를 한 번에 옮기는 대신, 앞으로 늘어나는 것만이라도 새 기준으로 만드는 것이다.
이 답에서 놓치면 안 되는 관점 도구 통일 자체가 목적이 아니라 "문서를 믿을 수 있는가"가 목적임을 놓치지 않는 답변이 좋다. 두 도구가 공존하는 상태는 어수선해 보이지만, 그 자체로 나쁜 것이 아니다.

어느 쪽을 고르든 관통하는 원칙 하나

사람의 성실함이 아니라 빌드 파이프라인이 문서의 정확성을 보증하게 한다

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

불일치의 근본 원인 한 문장?
게으름이 아니라 구조 — 코드에는 검증자가 있고 문서에는 없다. 틀렸다는 신호가 없는 산출물은 반드시 틀린 채로 남는다.
문서가 낡는 3층?
비 · 핫 · 신 — ①비대칭(검증자 없음) ②핫픽스가 하필 에러 흐름 ③신뢰는 0 아니면 1(고쳐도 안 돌아옴).
OpenAPI를 쓰는 이유 6종?
문 · 클 · 서 · 검 · 목 · 디 — 문서 UI · 클라이언트 코드 · 서버 인터페이스 · 검증기 · mock 서버 · 스펙 diff.
Swagger 관련 4개 이름의 층?
규 · 만 · 보 — 규격은 OpenAPI Spec(형식), 만드는 도구는 springdoc, 보여주는 도구는 Swagger UI. springfox는 Spring Boot 3에서 동작하지 않는다.
springdoc이 저절로 맞는 것?
경로 · HTTP 메서드 · 파라미터 이름과 타입 · 응답 DTO 필드와 타입. 코드에서 추출되므로 어긋날 수 없다 — "Swagger는 부정확하다"는 틀린 답.
springdoc이 끝까지 못 맞추는 것?
손으로 쓴 서술 전부 — 특히 어느 에러가 실제로 나가는지. @ApiResponse("404")는 그냥 문자열이고 실제 상태 코드와 아무 연결이 없다.
REST Docs가 깨지는 두 방향?
①문서에 있는데 응답에 없다 ②응답에 있는데 문서에 없다. 양방향이라 문서화 누락도 잡는다.
REST Docs 2단 조립?
[1단] 통과한 테스트 → snippet(기계 · 사실). [2단] 사람이 쓴 index.adoc이 include::로 조각을 끼움(사람 · 서술) → Asciidoctor 빌드.
테스트 클라이언트 3종 차이?
MockMvc(톰캣 X, 네트워크 X) · WebTestClient(설정에 따라) · REST Assured(전부 태움). 아래로 갈수록 실제와 같은 정도↑ 속도↓.
Swagger 유지하며 완화하는 3가지?
줄 · 스 · 표 — 서술 줄이기(Bean Validation으로 추출) · 스펙 스냅샷 diff를 CI에 · 에러 응답 표준화 후 그 모델만 문서화.
방어선 3층과 각자 놓치는 것?
규 · 소 · 문 — 스펙 diff는 규칙(실제 소비를 모름) · CDC는 실제 소비(미등록 소비자를 모름) · REST Docs는 문서-구현 일치(실제 사용과 다를 수 있음).
mock 테스트로 문서 만들 때 대응 3가지?
통 · 직 · 타 — 가능한 한 통합 테스트로 · 직렬화 경계(DTO)는 실제 객체로 · 타입을 실제 프로덕션 타입으로 고정.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

Swagger를 쓰면서 불일치를 줄이는 현실적인 방법은 없나요? 필수힌트: 셋을 대되, 마지막에 "이건 완화책일 뿐"이라는 선을 반드시 그어야 답이 닫힌다

있다. 셋을 든다.

① 서술 어노테이션을 최소화한다 — 문서의 구조적 부분(타입, 필수 여부)은 Bean Validation(@NotNull 등)과 타입 시스템에서 추출되게 하고, 손으로 쓰는 서술의 양 자체를 줄인다. 검증되지 않는 부분이 적을수록 거짓말할 표면적이 줄어든다.

② 생성된 OpenAPI 스펙을 CI에서 스냅샷으로 관리한다 — 스펙 파일을 저장소에 커밋해 두고 빌드마다 다시 생성해 비교하면, 의도치 않은 스펙 변화(필드 삭제 등)가 PR diff에 그대로 드러나 리뷰에 노출된다.

③ 에러 응답은 @ControllerAdvice 기반 공통 모델로 표준화하고 그 모델만 문서화한다 — API마다 제각각인 에러를 문서화하려니 거짓말이 나는 것이므로, 에러 스키마를 하나로 고정하면 문서화할 대상 자체가 하나가 된다(05-error-response-body-standardization.md).

다만 이 모두는 완화책이다 — "손으로 쓴 서술이 검증되지 않는다"는 구조 자체는 REST Docs나 계약 테스트로만 해결된다

MockMvc + 서비스 계층 mock 조합이면 문서는 컨트롤러 계층의 계약까지만 보증한다. mock이 실제 서비스와 다른 응답을 주도록 짜여 있다면 문서도 그 가짜 응답을 그대로 받아 적는다. 테스트는 통과하고 문서는 생성되는데 실제 서비스는 다른 값을 준다 — 검증의 형식만 남고 내용이 빈 상태다.

대응은 세 가지다 — "통 · 직 · 타".

통

타
타입 고정

"도구가 보증하는 범위가 어디까지인지"를 아는 것이 도구 이름을 아는 것보다 중요하다

한 줄로 닫으면 이렇다 — REST Docs가 보증하는 것은 "이 테스트가 실제로 주고받은 것"이고, 그 테스트가 얼마나 실제에 가까운지는 여전히 우리가 정한다.

문서화 대상이 100개 API인데 REST Docs 전환 비용이 너무 크면요? 필수힌트: "점진적으로"만 말하면 부족하다. 자르는 기준 한 줄과 시간축 분산 전략을 같이 댄다

전면 전환이 아니라 위험 기반으로 나눈다. 기준은 "불일치가 났을 때의 비용"이다.

외부 파트너에게 나가는 API, 결제 · 정산처럼 불일치 사고 비용이 큰 API부터 REST Docs나 계약 테스트로 옮기고, 내부 조회성 API는 springdoc으로 유지한다.

여기에 "신규 API부터 REST Docs를 기본으로 적용한다"는 전략을 얹으면 전환 비용이 시간축으로 분산된다 — 존재하는 100개를 한 번에 옮기는 대신, 앞으로 늘어나는 것만이라도 새 기준으로 만드는 것이다.

도구 통일 자체가 목적이 아니라 "문서를 믿을 수 있는가"가 목적임을 놓치지 않는 답변이 좋다. 두 도구가 공존하는 상태는 어수선해 보이지만, 그 자체로 나쁜 것이 아니다.

문서 불일치를 런타임에 감지할 수는 없나요? 가산점힌트: 1절의 "검증기" 파생물이 이 용법이다. 그리고 반드시 선을 하나 그어야 한다

가능하다. 게이트웨이나 필터에서 실제 요청 · 응답을 OpenAPI 스펙과 대조해 위반을 로깅하는 스펙 검증(validation) 계층을 둘 수 있다. 1절에서 본 "규격 파일에서 검증기를 만들 수 있다"가 이 용법이다.

값이 나오는 장면이 구체적이다. 운영 트래픽으로 "스펙에 없는 필드가 나가고 있다"나 "스펙에는 없는 400이 실제로는 자주 나간다"를 발견할 수 있어, 문서 체계를 전환하는 과도기나 감사(audit) 상황에 특히 유용하다. 테스트가 커버하지 못한 실제 경로를 트래픽이 대신 훑어 주는 셈이다.

이건 사후 감지이므로 빌드 시점 검증(테스트, 스펙 diff)의 보완이지 대체가 아니다

운영에 나간 뒤에 알게 되는 것과 배포 전에 막는 것은 다른 층의 방어다.

프론트엔드와의 협업에서는 뭐가 제일 효과적이었나요?힌트: 병렬 개발이 핵심이고, 여기에 절차 하나(PR 리뷰)를 더 붙여야 답이 완성된다

스펙 우선 + 코드 생성 조합이 협업 효과가 크다. 이유는 9-2에서 본 병렬 개발이다 — 스펙이 합의되면 프론트는 생성된 클라이언트나 mock 서버로 즉시 개발을 시작하고, 백엔드 구현은 그동안 병렬로 진행된다.

코드 우선에서는 백엔드가 API를 만들어 배포할 때까지 프론트가 기다리거나, 기다리기 싫어서 임의로 만든 가짜 데이터로 개발했다가 실제 응답과 어긋나 다시 고치게 된다.

여기에 절차 하나를 더 붙이면 답이 완성된다 — 스펙 변경은 반드시 PR 리뷰를 거치게 한다. 스펙 파일이 저장소에 있으므로 가능한 일이고, 이렇게 해야 "회의에서 말로 합의하고 코드는 딴판"이 되는 것을 막을 수 있다.

스펙을 저장소에 두는 것의 값은 파일 형식이 아니라 변경 이력과 리뷰 절차가 코드와 같은 수준으로 붙는다는 데 있다

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

자동 생성물인 OpenAPI 스펙을 저장소에 커밋한다는 게 이상하지 않나요? 빌드하면 나오는 건데요.힌트: 목적이 "산출물 보관"이 아니라는 데서 답이 갈린다

목적이 "산출물 보관"이 아니라 "변화를 눈에 띄게 만드는 것"이라서 커밋한다. 4절에서 본 문제의 핵심은 문서가 바뀌었는지(혹은 바뀌었어야 했는지) 아무도 모른다는 것이었다. 스펙을 커밋해 두면 그 변화가 PR diff라는, 팀이 이미 매일 보는 화면에 나타난다.

실제 동작은 이렇다 — 빌드가 스펙을 다시 생성해 커밋된 스냅샷과 비교하고, 다르면 실패시킨다. 개발자는 의도한 변경이면 스냅샷을 갱신해 PR에 포함시킨다. 그러면 리뷰어는 "응답에서 amount가 사라졌다"를 코드가 아니라 스펙 diff 한 줄로 본다.

부수 이득이 하나 더 있다 — 커밋된 스냅샷이 있으면 이전 버전과의 스펙 diff(파괴적 변경 검출)를 붙일 대상이 생긴다. 1절의 "디"가 여기서 가능해진다.

REST Docs로 가면 Swagger UI의 try-it-out은 포기해야 하나요?힌트: 검증과 화면은 같은 층의 이야기가 아니다

포기하지 않아도 된다. 9-1의 결합형이 정확히 이 문제를 푼다. REST Docs가 주는 것은 검증이고 Swagger UI가 주는 것은 화면인데, 이 둘은 다른 층이다.

REST Docs 테스트 결과에서 OpenAPI 스펙을 생성하는 확장(restdocs-api-spec 등)을 얹으면, 검증은 테스트가 하고 생성된 스펙을 Swagger UI가 읽어 화면을 그린다. 결과는 "테스트로 검증된 스펙 + 인터랙티브 문서"다.

이 조합의 값이 화면에서 끝나지 않는다는 점도 덧붙이면 좋다 — 스펙 파일이 손에 들어오는 순간 클라이언트 코드 생성 · 스펙 diff · 런타임 검증기가 전부 붙는다. REST Docs 단독은 사람이 읽는 HTML에서 끝나지만, 스펙을 뽑아내면 기계가 쓸 수 있는 자산이 된다.

스펙 우선으로 갔는데 구현이 스펙과 어긋나면 어떻게 막나요? 시니어 변별힌트: 컴파일 시점 · 빌드 시점 · 런타임의 세 지점을 나눠서 답한다

어긋남을 막는 지점을 세 곳에 둔다. 스펙 우선이 저절로 정합성을 보장하는 게 아니라, "스펙에서 무언가를 생성해 강제하는가"가 실제 방어력을 만든다.

컴파일 시점
스펙에서 서버 인터페이스와 DTO를 생성하고 컨트롤러가 그 인터페이스를 구현하게 한다 → 스펙에 없는 응답을 내보내는 코드가 애초에 컴파일되지 않는다
빌드 시점
CI에서 실제 응답을 스펙과 대조 검증하고, 이전 스펙과의 diff로 파괴적 변경을 검출해 빌드를 실패시킨다
런타임
게이트웨이·필터의 스펙 검증 계층으로 위반을 로깅한다. 단 사후 감지이므로 앞의 둘을 대체하지 않는다

여기에 절차 하나를 얹어야 완성된다 — 스펙 파일이 저장소에 있으니 스펙 변경에 PR 리뷰를 강제한다. 기술적 방어(생성 · 검증)와 절차적 방어(리뷰)가 같이 있어야 "스펙을 슬쩍 고쳐서 통과시키는" 경로까지 막힌다.

CDC를 도입하면 스펙 diff는 필요 없어지나요? 함정힌트: 9-4 그림에서 "각 층이 놓치는 것" 칸을 보면 바로 답이 나온다

아니다. 층이 다르다. CDC가 스펙 diff보다 "더 정확한 상위 호환"처럼 보이지만 각자 못 보는 곳이 다르다.

CDC가 놓치는 것은 "계약을 등록하지 않은 소비자"다 — 파트너사 앱, 외부 개발자, 사내 다른 조직의 배치 스크립트처럼 우리 CI에 계약을 올려주지 않는 소비자는 CDC의 시야 밖에 있다. 이들에게는 "규칙상 파괴적 변경을 하지 않는다"는 스펙 diff 기반의 방어가 유일한 보호막이다.

반대로 스펙 diff가 놓치는 것은 "규칙상 안전한데 실제로 깨지는 변경"과 "의미만 바뀐 변경"이다 — optional 필드 제거, 또는 필드 이름과 타입은 그대로인데 담기는 값의 의미가 바뀐 경우는 diff로 잡히지 않는다.

둘은 대체 관계가 아니라 보완 관계다 — 등록된 소비자는 CDC가, 등록되지 않은 소비자는 규칙(스펙 diff)이 지킨다
이미 문서를 아무도 안 믿게 된 팀입니다. 신뢰를 어떻게 되돌리나요?힌트: "다 고쳤습니다"가 왜 안 통하는지를 4-3에서 끌어오면 답의 방향이 정해진다

"전부 고쳤습니다"는 통하지 않는다. 4-3에서 본 대로 고쳐졌는지 확인하려면 결국 문서를 믿어야 하는데 그 믿음이 이미 없기 때문이다. 그래서 되돌리는 방법은 내용을 고쳤다는 주장이 아니라, 틀릴 수 없는 구조로 바뀌었다는 사실을 보여주는 것이어야 한다.

말할 수 있는 것이 셋이다. ① "이 문서는 테스트가 통과해야만 생성된다"(REST Docs) — 소비자가 문서를 믿는 근거가 사람의 약속이 아니라 빌드가 된다. ② "스펙이 바뀌면 PR diff에 뜨고 리뷰를 거친다"(스냅샷) — 몰래 바뀌는 경로가 없다. ③ "당신들이 등록한 계약을 우리 빌드가 재생한다"(CDC) — 소비자 입장에서 가장 강한 보증이다.

범위는 10절의 위험 기반 분할을 그대로 쓴다 — 전부를 한 번에 되돌리려 하지 말고 사고 비용이 큰 API부터 "검증되는 문서"로 바꾸고, 그 API에 한해 "이건 빌드가 보증한다"고 명시한다. 신뢰가 0/1이라는 성질은 범위를 좁히면 그 범위 안에서 다시 1로 만들 수 있다는 뜻이기도 하다.

@Schema(example = ...)로 예제 값을 잔뜩 달아 두면 그것도 거짓말이 되나요?힌트: 8절 그림의 ⑥ 칸이 무슨 색이었는지 떠올린다

된다. 예제 값은 8절 그림에서 ⑥ 칸(빨강)에 속하는, 손으로 쓴 서술이다. 코드에서 추출되는 것이 아니므로 필드의 의미가 바뀌거나 형식이 바뀌어도 예제는 그대로 남는다.

게다가 예제는 특히 위험하다 — 소비자가 문서를 읽을 때 스키마 정의보다 예제를 먼저 복사해 붙여 넣기 때문이다. 날짜 형식이나 enum 값처럼 예제 하나가 곧 소비자 구현이 되는 자리에서 낡은 예제는 곧바로 연동 실패로 이어진다.

REST Docs가 이 문제에 특히 강한 이유가 여기 있다 — REST Docs의 http-response.adoc은 실제로 받은 응답 원문이다. 즉 예제가 곧 실제라서 "예제만 옛날 값"이라는 상태가 성립하지 않는다. springdoc을 유지한다면 최소한 예제 값이 많이 붙는 API만이라도 문서화 테스트로 고정하는 것이 5-3의 "줄"과 같은 방향의 처방이다.

모놀리스라 소비자가 사내 팀 하나뿐입니다. 그래도 이 모든 게 필요한가요?힌트: 필요한 층과 필요 없는 층을 갈라 답한다. "다 하세요"도 "다 필요 없어요"도 답이 아니다

층을 갈라서 답하는 게 정확하다. 10절의 기준 — "불일치가 났을 때의 비용" — 을 그대로 적용하면 된다.

필요성이 낮은 것: 소비자가 옆자리 한 팀뿐이라면 CDC의 이득은 작다. 계약을 파일로 고정해 얻는 값보다 슬랙 한 줄로 확인하는 비용이 더 싸기 때문이다. 스펙 우선의 병렬 개발 이득도, 프론트와 백엔드가 같은 스프린트에서 붙어 일한다면 상대적으로 작다.

여전히 필요한 것: springdoc + Swagger UI는 비용이 거의 없으므로 기본으로 깔고 간다. 그리고 불일치 사고 비용이 큰 지점(결제 · 정산 · 외부로 나가는 웹훅)은 소비자가 사내여도 테스트로 고정할 값이 있다.

그리고 시간축을 언급하면 답이 좋아진다 — 지금 소비자가 하나라는 사실은 계속 유지되지 않는다. 앱이 붙고 파트너가 붙는 순간 문서가 참고자료에서 계약서로 바뀌는데(09-partner-api-vs-internal-api.md), 그때 100개를 한꺼번에 옮기는 것보다 신규 API부터 기본값을 바꿔 두는 편이 싸다.

한 줄 요약
문서-구현 불일치는 성실함의 문제가 아니라 "문서가 검증 루프 밖에 있다"는 구조의 문제이고, 그 루프의 재료가 API를 기계 판독 형식(YAML/JSON)으로 적어 문서 UI · 클라이언트 코드 · 검증기 · 스펙 diff를 전부 파생시킬 수 있게 하는 OpenAPI 규격이다 — springdoc이 코드를 스캔해 만든 규격을 Swagger UI로 보는 방식은 경로 · 메서드 · 타입 같은 구조적 사실은 저절로 정확하지만 손으로 쓴 서술은 아무도 검증하지 않아 거짓말이 남고, Spring REST Docs는 통과한 테스트가 남긴 실제 요청 · 응답으로 문서 조각을 만들어 사람이 쓴 뼈대에 끼워 넣으므로 문서와 구현이 어긋나는 순간이 곧 빌드가 깨지는 순간이 된다. 핵심 원칙은 문서가 틀리면 빌드가 깨지게 만드는 것이고, 외부 계약일수록(스펙 우선 + CI의 스펙 diff, 소비자가 계약을 등록하고 제공자 빌드가 재생하는 CDC) 그 강제 수준을 높이는 것이다.
