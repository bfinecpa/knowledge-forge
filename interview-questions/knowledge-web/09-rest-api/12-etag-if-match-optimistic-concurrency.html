ETag / If-Match 낙관적 동시성
lost update를 HTTP 계약으로 막는다

면접 질문: "낙관적 동시성 제어를 API 레벨에서 어떻게 표현하나요? (ETag, If-Match, 409 vs 412)"

핵심 관전 포인트 — 두 관리자가 같은 화면을 열어 편집하면 나중에 저장한 쪽이 먼저 저장한 쪽의 변경을 조용히 덮어쓴다(lost update). 이 구간을 DB 락으로 잡을 수 없는 이유는 GET과 PUT 사이에 몇 분짜리 "사람의 생각 시간"이 끼어 있기 때문이고, 그래서 답은 낙관적 방식 — 충돌이 드물 것이라 낙관하고 일단 잠그지 않은 채 진행하되, 저장하는 순간 "내가 본 그 버전이 아직 그대로인가"를 검사하는 것 — 이 된다. HTTP는 이 검사를 표현할 어휘를 표준으로 갖고 있다. 조건부 요청(conditional request), 즉 "이 조건이 참일 때만 이 요청을 실행하라"고 헤더로 전제를 거는 기능 묶음이다. 검사의 재료는 ETag(Entity Tag — 값이 같으면 표현이 같다는 뜻의 꼬리표)이고, 서버가 GET 응답에 실어 준 ETag를 클라이언트가 If-Match로 되돌려주면, 어긋날 때 서버는 요청을 실행하지 않고 412 Precondition Failed를 돌려준다. 상태 코드 구분이 채점 포인트다 — 412는 "네가 헤더로 건 전제가 거짓", 409는 전제 헤더와 무관한 자원 상태 충돌, 428 Precondition Required는 "전제를 걸어야 하는데 안 걸었다"로 낙관적 동시성을 선택이 아닌 계약으로 강제한다. 그리고 ETag의 원천은 결국 DB의 버전 컬럼이다 — WHERE id = ? AND version = ?의 영향 행 수가 0이면 충돌이라는 @Version의 검사를, 트랜잭션 경계 밖의 사람 시간까지 넓힌 것이 이 설계의 정체다.
  • 1
    문제는 트랜잭션이 못 덮는 구간이다 — GET과 PUT 사이에는 몇 분짜리 사람의 생각 시간이 있고, 커넥션 점유·HTTP 무상태·회수 불가라는 세 이유(커·무·유)로 DB 락이 이 구간을 건널 수 없다. 그래서 잠그지 않고 저장 시점에 검사하는 낙관적 방식을 택한다.
  • 2
    HTTP는 그 검사를 표현할 표준 어휘를 갖고 있다 — GET 응답의 ETag: "7"을 수정 요청의 If-Match: "7"로 되돌려주고, 어긋나면 서버가 요청을 실행하지 않고 412를 준다. "헤더로 건 전제가 깨짐 → 412 / 전제 헤더와 무관한 상태 충돌 → 409 / 전제를 안 걸었음 → 428"이고, 428이 있어야 낙관적 동시성이 옵션이 아니라 계약이 된다.
  • 3
    ETag의 원천은 @Version 컬럼이라 두 계층이 겹쳐진다 — API 레벨의 If-Match가 사람 시간을 덮고, UPDATE ... WHERE version = ?의 영향 행 수 0 판정이 밀리초 레이스를 덮는 이중 방어다. 다만 412를 자동 재시도로 뭉개면 결국 last write wins로 되돌아간다 — 412는 삼키는 에러가 아니라 사람에게 보여야 하는 신호다.

0. 질문 + 출제 의도

질문: "낙관적 동시성 제어를 API 레벨에서 어떻게 표현하나요? (ETag, If-Match, 409 vs 412)"

출제 의도: 두 관리자가 같은 데이터를 편집하는 lost update를 API 계약으로 막는 설계. DB 락 지식을 HTTP 계층으로 번역할 수 있는지 — 계층을 넘나드는 응용력을 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "ETag = 캐시용"으로만 알고 있는 것 → 3절에서 같은 ETag를 재료로 쓰는 정반대 방향의 두 헤더를 2×2로 갈라놓는다. If-Match는 같을 때 실행(쓰기 보호), If-None-Match는 다를 때 실행(읽기 절약)이다.
② 409와 412를 "둘 다 충돌이니까 아무거나"로 쓰는 것 → 8절에서 412·428은 If-Match라는 가지 위에 있고 409는 그 가지 바깥에 있다는 판정 순서를 트리로 고정한다.
③ DB 낙관적 락과 HTTP 계약을 별개로 외우는 것 → 6절에서 ETag는 @Version 컬럼을 헤더로 내보낸 것임을 보이고, 둘이 서로 다른 구간을 덮는 이중 필터임을 도식화한다.

경계 정리 — DB 계층의 낙관적 락 자체(@Version의 UPDATE SQL, 예외 타입, 재시도 전략)는 03-jpa-orm/10-optimistic-vs-pessimistic-lock.md, 캐시 재검증용 ETag(If-None-Match·304·검증자 종류)는 08-network-http/20-http-caching-headers-and-304.md, lost update의 정의와 PUT/PATCH 시맨틱은 02-put-vs-patch.md에 있다. 이 문서는 그 사이를 잇는 층 — 헤더 흐름과 상태 코드 선택 — 에만 집중한다.

1. GET과 PUT 사이의 "사람 시간"

lost update(갱신 유실)는 두 사람이 같은 자원을 각자 읽어 각자 수정한 뒤 저장했을 때, 나중에 저장한 쪽이 앞사람의 수정을 덮어써 앞사람의 변경이 흔적 없이 사라지는 현상이다. 무서운 점은 에러도 경고도 로그도 남지 않는다는 것이다 — 두 요청 모두 서버 입장에서는 완벽하게 정상적인 200 응답이었다.

이 사고를 부르는 다른 이름 — last write wins 여러 요청이 같은 데이터를 겹쳐 쓸 때 아무 검사도 하지 않으면 시간상 가장 나중에 도착한 쓰기가 앞의 것을 전부 덮어쓰고 최종 상태가 된다는 뜻이다. 이것은 어떤 알고리즘의 이름이 아니라 아무 대책도 세우지 않았을 때 자동으로 얻게 되는 기본 동작의 이름이다. 이 문서 전체가 "last write wins를 벗어나는 방법"에 관한 것이라고 봐도 된다 — 그리고 9절에서 대책을 세우고도 다시 여기로 되돌아가는 길이 있다는 것까지 확인한다.

1-1. DB 안에서라면 쉬운 문제다

DB 안에서라면 이 문제는 이미 풀려 있다. read-modify-write(읽고, 고치고, 쓰기)를 한 트랜잭션으로 묶고 조회 시점에 SELECT ... FOR UPDATE로 행을 잠가 버리면, 뒤에 온 트랜잭션은 앞 트랜잭션이 끝날 때까지 대기하므로 낡은 값을 읽을 기회 자체가 없다.

그런데 API 소비자의 편집 흐름은 트랜잭션 안에 들어가지 않는다. 그 사이에 사람이 있기 때문이다.

세 이유를 세 글자로 — 커 · 무 · 유

커넥션
트랜잭션이 열린 동안 커넥션 하나가 점유된다. 사람 시간만큼 붙들 수 없다.
무상태
HTTP는 stateless라 GET과 PUT이 같은 커넥션·같은 프로세스라는 보장이 없다.
유령 잠금
잠근 사람이 돌아오지 않으면 회수 신호가 없다. 자원은 영원히 잠긴다.

이 셋은 11절에서 그대로 재현된다 — 비관적 "편집 잠금 자원"을 도입하면 세 번째 이유가 TTL·하트비트·강제 해제라는 숙제로 돌아온다.

2. 낙관적 vs 비관적 — 이름의 뜻부터

이 대비를 세워 두지 않으면 8절의 상태 코드 논의도, 11절의 "편집 잠금과 어떻게 고르나"도 근거 없이 외우는 결론이 된다. 두 이름은 은유가 아니라 그대로 동작을 설명한다.

비관적 (pessimistic) — "충돌이 날 것이라고 비관하고 미리 잠근다"

  • 남이 건드리기 전에 내가 먼저 문을 잠그고 들어간다.
  • SELECT ... FOR UPDATE가 여기 속한다.
  • 충돌을 예방한다. 대신 잠근 동안 다른 사람은 기다린다.
  • 비유: 도서관에서 책을 대출해 가버린다. 반납 전까지 아무도 못 본다.

낙관적 (optimistic) — "충돌은 드물 것이라고 낙관하고 저장할 때 검사한다"

  • 아무도 안 건드렸을 것이라 믿고 작업하다가, 저장 직전에 "내가 본 그대로인가"를 확인한다.
  • 충돌을 예방하지 않고 감지하며, 감지되면 그 요청을 실패시킨다.
  • 비유: 복사본을 떠 가고, 제출할 때 원본의 판 번호를 대조한다.
  • 이 문서의 주제 — ETag + If-Match가 이 대조를 HTTP로 표현한 것.
두 방식의 대비. 면접에서 값이 나가는 줄은 "충돌이 났을 때"와 "실패 처리 책임"이다 — 낙관적 방식의 대가가 거기에 있다.
축비관적낙관적
전제충돌이 자주 날 것이다충돌은 드물 것이다
언제 개입하나읽는 시점에 미리 잠근다쓰는 시점에 검사한다
충돌이 없을 때의 비용잠금 획득·해제 비용을 매번 낸다사실상 0 (비교 한 번)
충돌이 났을 때뒤에 온 쪽이 기다린다뒤에 온 쪽이 실패한다
실패 처리 책임없음 (대기로 흡수)클라이언트가 재조회·재시도해야 한다

가장 자주 틀리는 한마디 — "낙관적 락은 사실 아무것도 잠그지 않는다"

이름에 "락"이 붙어 있어 오해하기 쉬운데, 하는 일은 잠금이 아니라 버전 비교다. 그래서 낙관적 방식에서는 뒤에 온 요청이 대기하는 일이 없고, 대신 실패한다. "그럼 락이 아닌데 왜 락이라고 부르나요?"라는 되물음까지 받으면 — "잠금과 같은 목적(상호 배제된 갱신)을 달성하지만 수단이 잠금이 아니라 검증이라서, 결과만 보고 붙은 이름"이라고 답하면 된다.

3. 조건부 요청 4형제 — HTTP가 이미 갖고 있는 어휘

낙관적 검사를 하려면 클라이언트가 "내가 본 버전"을 서버에 알려주고, 서버가 그 값과 현재 값을 비교해 실행 여부를 정해야 한다. 이 왕복을 표현할 어휘가 계약에 있어야 하는데, HTTP는 그것을 이미 표준으로 갖고 있다.

조건부 요청(conditional request)이란 "이 조건이 참일 때만 이 요청을 실행하라"고 헤더로 전제를 거는 HTTP의 기능 묶음이다. 이름 그대로 요청에 조건이 붙는다. 조건이 거짓이면 서버는 요청 본문을 실행하지 않고 거절 응답만 돌려준다. 이 범주를 먼저 세우는 것이 중요하다 — 8절에서 다룰 "412는 조건부 요청 전용 응답"이라는 주장이, 이 범주가 존재해야만 성립하기 때문이다.

가족은 넷이다. 두 축으로 갈린다 — 무엇으로 비교하는가(ETag냐 시각이냐), 그리고 같을 때 실행하는가 다를 때 실행하는가.

한 문장으로 외우는 방향 규칙

쓸 때는 같아야 실행(If-Match) · 읽을 때는 달라야 실행(If-None-Match)

쓰기는 "내가 본 그대로여야 덮어써도 안전"하니 같아야 하고, 읽기는 "달라졌을 때만 본문을 보내면 된다"니 달라야 한다. 목적이 방향을 정한다고 이해하면 헷갈리지 않는다.

3-1. ETag — 이름부터 풀자

ETag는 Entity Tag의 줄임말이다. "개체 태그", 즉 자원의 표현에 붙는 꼬리표다. 여기서 표현(Representation) 은 — 서버가 DB에 들고 있는 42번 주문 그 자체를 네트워크로 보낼 방법은 없고, 보낼 수 있는 것은 "42번 주문의 지금 상태를 JSON 같은 형식으로 찍어낸 스냅샷"뿐이며 그 스냅샷이 표현이다.

ETag가 뜻하는 것은 딱 하나다 값이 같으면 표현이 같고, 값이 다르면 표현이 달라졌다. 서버가 자원을 고칠 때마다 새 값을 붙여 주므로, 클라이언트가 들고 있는 ETag와 서버의 현재 ETag를 비교하면 "내가 본 뒤로 누가 고쳤는가"를 한 번의 문자열 비교로 알 수 있다. — 즉 ETag는 "무엇이 어떻게 바뀌었는지"는 전혀 알려주지 않는다. 오직 바뀌었는가 아닌가만 알려준다. 그래서 9절에서 병합은 결국 사람이나 클라이언트의 몫이 된다. 
# 값은 규격상 큰따옴표로 감싼다. 장식이 아니라 문법이고,
# 따옴표를 빼면 일부 클라이언트·프록시가 헤더를 해석하지 못한다.
ETag: "7"           # 버전 번호 기반
ETag: "a3f8c2e1"    # 내용 해시 기반
ETag: W/"7"         # 앞에 W/ 가 붙으면 "약한" ETag (7절) — If-Match 에서는 절대 일치하지 않는다
비유 — 결재판에 붙은 판 버전 스티커 결재판을 복사해 간 사람(GET + ETag)이 수정본을 제출할 때 "v3 기준으로 고쳤습니다"(If-Match)라고 명시하면, 접수 담당자는 원본이 이미 v4가 됐을 경우 접수를 거부한다(412). 담당자가 두 수정본을 말없이 겹쳐 붙이는 사고가 원천 차단된다. — 위키 편집에서 보는 "다른 사용자가 이 문서를 먼저 수정했습니다" 화면도 정확히 같은 메커니즘이다.

4. 왕복 전체 — t5에서 무슨 일이 일어나는가

4-1. 헤더 두 줄이 전부다

1 서버가 ETag를 발급한다
GET /orders/42 HTTP/1.1

HTTP/1.1 200 OK
ETag: "7"
Content-Type: application/json

{ "id": 42, "memo": "",
  "shippingAddress": "서울",
  "status": "PAID" }

// 클라이언트는 이 "7"을 보관한다.
2 클라이언트가 되돌려준다
PUT /orders/42 HTTP/1.1
If-Match: "7"
Content-Type: application/json

{ "id": 42, "memo": "선물포장",
  "shippingAddress": "서울",
  "status": "PAID" }

// "표현이 아직 7일 때만 실행하라"

버전이 그대로면 — 200 OK + 새 ETag

요청을 실행하고 ETag: "8"을 응답에 실어 준다. 새 ETag를 주는 것이 중요하다 — 클라이언트가 재조회 없이 연속 편집을 이어갈 수 있기 때문이다. 이것을 안 주면 사용자가 저장할 때마다 화면을 새로 불러와야 한다.

그 사이 누가 고쳤으면 — 412, 그리고 서버 상태는 그대로

HTTP/1.1 412 Precondition Failed

{ "code": "CONCURRENT_MODIFICATION",
  "message": "리소스가 다른 사용자에 의해
   수정되었습니다. 다시 조회 후 수정해주세요." }

4-2. 두 관리자의 타임라인 — 사고 상황에 If-Match만 얹으면

말로만 읽으면 와닿지 않으므로, lost update 사고 상황에 If-Match만 얹어 다시 돌려 보자. 관리자 A는 메모를, B는 배송지를 고치려 한다. 원래대로라면 t5에서 B의 낡은 메모가 A의 수정을 덮어썼을 것이다.

한 줄로 요약하면 — 성질이 바뀐다

lost update는 조용한 데이터 손실이었는데, If-Match는 그것을 시끄러운 실패로 바꾼다

시끄러운 실패는 클라이언트가 대응할 수 있지만, 조용한 손실은 대응할 기회조차 없다. 즉 If-Match가 충돌을 없애 주는 것이 아니다. 충돌을 눈에 보이게 만들어 개입할 기회를 만들어 줄 뿐이고, 그 기회를 쓰는 것은 9절에서 보듯 클라이언트의 몫이다.

5. 서버 구현 — Before / After

Before If-Match 없이 그대로 덮어쓰기 — last write wins
@PutMapping("/orders/{id}")
public OrderResponse update(@PathVariable Long id,
                            @RequestBody OrderRequest req) {
    return orderService.update(id, req);  // 늦게 온 쪽이 조용히 이긴다
}
After GET에서 ETag를 발급하고, PUT에서 If-Match를 검증한다
@GetMapping("/orders/{id}")
public ResponseEntity<OrderResponse> get(@PathVariable Long id) {
    Order o = orderService.find(id);
    return ResponseEntity.ok()
            // @Version 컬럼 값을 그대로 ETag 로 쓴다 (6절).
            // Spring 의 eTag() 는 따옴표가 없으면 붙여 주므로 "7" 형태로 나간다.
            .eTag(String.valueOf(o.getVersion()))
            .body(OrderResponse.of(o));
}

@PutMapping("/orders/{id}")
public ResponseEntity<OrderResponse> update(
        @PathVariable Long id,
        // required = false 로 받아야 "안 보냄"을 우리가 직접 판정할 수 있다.
        // required = true 면 Spring 이 400 을 내버려서 428 을 쓸 기회가 없다.
        @RequestHeader(value = "If-Match", required = false) String ifMatch,
        @RequestBody OrderRequest req) {

    if (ifMatch == null) {
        // 전제조건 없이 온 수정 요청. 이 자원에서 낙관적 동시성을 "강제"하기로
        // 했다면 여기서 거부해야 한다. 통과시키면 방어적인 클라이언트만
        // 손해 보는 구조가 된다 (8-2).
        return ResponseEntity.status(HttpStatus.PRECONDITION_REQUIRED).build();
    }

    Order updated = orderService.update(id, req, parseVersion(ifMatch));
    // 서비스 내부에서 하는 일:
    //   ① 엔티티를 조회해 현재 version 과 If-Match 값을 비교한다.
    //      다르면 PreconditionFailedException -> @ControllerAdvice 에서 412
    //   ② 같으면 필드를 반영한다. 커밋 시점의 @Version UPDATE 가
    //      최후의 안전망으로 한 번 더 검사한다 (6절).

    return ResponseEntity.ok()
            .eTag(String.valueOf(updated.getVersion()))  // 연속 편집을 위해 새 ETag
            .body(OrderResponse.of(updated));
}
required = false로 받는 이유 — 400과 428은 다른 말이다 true로 두면 헤더가 없을 때 Spring이 먼저 400 Bad Request를 내버리는데, 400은 "요청 문법이 틀렸다"는 뜻이라 "전제조건을 걸어야 하는데 안 걸었다"는 상황을 정확히 전달하지 못한다. 클라이언트 개발자는 400을 받으면 본문 JSON을 들여다보며 헤매게 된다. 428이라는 전용 코드가 있는 이유가 여기 있다(8-2).
놓치기 쉬운 구현 디테일 셋 ① 따옴표 처리 — If-Match 값은 "7"처럼 따옴표가 포함된 문자열로 들어온다. parseVersion에서 따옴표를 벗겨야 숫자로 비교된다. 벗기지 않고 비교하면 항상 불일치 → 항상 412다.
② 다중 값과 * — If-Match는 "7", "8"처럼 쉼표로 여러 개가 올 수 있고 *도 올 수 있다(8-3). 최소한 *는 처리해 두는 것이 안전하다.
③ 응답에도 ETag를 빠뜨리지 말 것 — PUT 응답에 새 ETag를 안 실어 주면 클라이언트는 매 저장마다 재조회해야 한다. 기능은 되지만 왕복이 두 배가 된다.

6. ETag의 원천은 @Version — 두 계층의 이중 방어

여기가 계층 번역의 그림이 완성되는 자리다. ETag는 하늘에서 떨어진 값이 아니라, DB가 이미 들고 있던 버전 컬럼을 HTTP 헤더로 내보낸 것이다.

6-1. @Version이 만드는 실제 SQL

없을 때 id만 보고 덮어쓴다
UPDATE orders
   SET memo = ?, shipping_address = ?
 WHERE id = ?;

-- 이것이 last write wins 그 자체다.
-- 늦게 도착한 UPDATE 가 무조건 이긴다.
있을 때 검사를 WHERE 안에 넣는다
UPDATE orders
   SET memo = ?, shipping_address = ?,
       version = version + 1
 WHERE id = ? AND version = ?;
--             └────────┘
-- "내가 읽었을 때의 버전 그대로일 때만 써라"

충돌 판정은 값을 다시 읽어 비교하는 것이 아니라 영향 행 수(affected rows)로 한다

UPDATE ... WHERE id = 42 AND version = 7

  → 영향 행 수 1 : WHERE 조건에 걸리는 행이 있었다.
                   아무도 안 건드렸다는 뜻. version 은 이제 8.

  → 영향 행 수 0 : WHERE 조건에 걸리는 행이 없다.
                   id 42 는 분명히 있는데 version 이 7이 아니다
                   = 누군가 이미 8 이상으로 올려놨다
                   = 충돌!  → ObjectOptimisticLockingFailureException

확인과 갱신이 하나의 SQL 문장 안에 들어 있다는 점이 핵심이다. "SELECT로 버전을 확인하고 → 같으면 UPDATE"로 나누면 그 사이에 다른 트랜잭션이 끼어들 틈이 생기지만, 검사를 WHERE절 안에 넣으면 DB가 원자적으로 판정한다.

정확한 디테일 하나를 덧붙이면 가산점 가산점 하이버네이트가 실제로 찍는 SQL은 version = version + 1이 아니라 version = ?이다. 새 버전 값을 메모리에서 계산해(읽은 값 + 1) 파라미터로 바인딩하기 때문이다. 개념적으로는 version + 1이 맞지만, 로그에서 보게 될 문자열은 update orders set memo=?, shipping_address=?, version=? where id=? and version=? 쪽이다. (상세: 03-jpa-orm/10-optimistic-vs-pessimistic-lock.md)

6-2. 두 계층을 나란히 놓으면 — 그리고 왜 둘 다 필요한가

이 표가 이 문서의 논지 전체다. 마지막 줄이 둘을 겹쳐 쓰는 이유이므로, 면접에서 값이 나가는 줄도 마지막 줄이다.

7. ETag 재료 선택과 강/약 검증자

7-1. 무엇으로 값을 만드나

버전 번호 — 권장
@Version 컬럼 값 그대로. 단조 증가라 비교가 명확하고, 이미 조회한 엔티티의 필드 하나이므로 생성 비용이 사실상 0이다. 동시성 제어 용도에는 대부분 이것이 최선.
내용 해시
응답 본문을 해시한 값. 버전 컬럼이 없는 자원이나 여러 테이블에서 조합해 만드는 파생·집계 표현에 유용하지만, 매 응답마다 직렬화 결과를 해시하는 비용이 든다.
수정 시각 — 함정
같은 초(또는 같은 밀리초)에 두 번 수정되면 두 표현이 같은 값을 갖는 정밀도 함정. Last-Modified/If-Unmodified-Since가 동시성 제어용으로 ETag보다 약한 이유와 같다.

7-2. 강한 ETag와 약한 ETag — If-Match에서는 이 구분이 치명적이다

ETag 값 앞에 W/가 붙으면 약한(weak) ETag이고, 없으면 강한(strong) ETag다. 둘은 "같다"의 기준이 다르다.

강한 ETag — "바이트까지 완전히 같다"

두 표현의 강한 ETag가 같다면 두 응답 본문은 1바이트도 다르지 않다.

ETag: "a3f8c2"

약한 ETag — "의미상 같다"

공백·필드 순서·응답에 박힌 생성 시각 주석 정도는 달라도 "같은 것"으로 친다. 사람이 보기에 같으면 같다고 보겠다는 선언.

ETag: W/"a3f8c2"

동시성 제어에서 반드시 알아야 할 한 줄

If-Match는 강한 비교를 쓴다 — 약한 ETag는 절대 일치하지 않는다

If-Match: W/"7"을 보내면 서버 ETag가 W/"7"이어도 불일치로 판정돼 언제나 412가 나간다. 반면 If-None-Match(캐시 재검증)는 약한 비교를 허용한다 — 읽기 절약이 목적이라 "의미상 같으면 본문을 생략해도 된다"가 성립하기 때문이다.

왜 쓰기만 엄격한가를 한마디로: 읽기에서 틀리면 본문을 한 번 더 받으면 그만이지만, 쓰기에서 틀리면 남의 데이터가 사라진다. 그래서 실패 비용이 큰 쪽에 엄격한 기준이 붙는다.

실무 함정 — "압축을 켰더니 If-Match가 항상 412를 냅니다" 응답 압축(gzip 등)을 켜면 본문 바이트가 바뀌므로 원본의 강한 ETag를 그대로 유지하는 것은 거짓말이 된다. 그래서 압축 계층을 통과한 응답의 ETag는 약한 것으로 낮아지거나 제거된다(Nginx는 약한 ETag로 낮춘다). 그러면 클라이언트가 받아 되돌려주는 값이 W/"7"이 되고, 위 규칙에 따라 항상 불일치 → 항상 412다. 버전 번호를 ETag로 쓰면서 압축·프록시 계층이 그것을 건드리지 않도록 확인해 두는 것이 안전하다.
같은 구분이 걸리는 다른 자리 — 범위 요청 이어받기(If-Range) 큰 파일을 받다 끊겨서 "이 파일의 5MB 지점부터 주세요"라고 이어받으려면, 서버가 지금 가진 파일이 내가 앞부분을 받아둔 그 파일과 바이트 단위로 완전히 같아야 한다. 1바이트라도 다르면 이어붙인 파일이 깨진다. 그래서 If-Range는 강한 ETag만 받아들인다. — If-Match와 If-Range가 강한 비교를 요구하는 이유는 같다: 둘 다 "틀리면 데이터가 깨지는" 연산이기 때문이다.
정리 — 동시성 제어용 ETag는 강한 ETag여야 하고, 버전 번호 기반이면 자연히 강한 ETag가 된다

8. 409 vs 412 vs 428 — 결정 트리

질문의 괄호가 굳이 "409 vs 412"를 짚는 이유는, 두 코드가 모두 "충돌"처럼 들리지만 메커니즘이 다르기 때문이다. 산문으로 읽기 전에 판정 순서를 그림으로 잡아 두자.

8-1. 세 코드를 각각 정확히

412 Precondition Failed
조건부 요청 전용 응답
클라이언트가 조건부 헤더(If-Match, If-Unmodified-Since 등)로 건 전제조건이 거짓으로 평가되어, 서버가 요청을 실행하지 않았다는 뜻. ETag/If-Match로 낙관적 동시성을 구현했다면 충돌의 정답은 412.
409 Conflict
전제 헤더와 무관한 상태 충돌
요청이 자원의 현재 상태와 충돌해 수행할 수 없다는 뜻. 상태 기계 위반(배송 시작된 주문 취소), 유니크 제약 충돌, CANCELLED 주문 수정 등. 버전을 본문 필드로 받는 설계라면 조건부 요청이 아니므로 여기(409)가 자연스럽다(10절).
428 Precondition Required
전제를 안 걸었다
이 자원의 수정에 전제조건이 필수인데 클라이언트가 If-Match 없이 요청했다는 뜻. 낙관적 동시성을 "옵션"에서 "계약"으로 승격시키는 장치.

8-2. 428이 왜 필요한가 — 설계 감각이 드러나는 지점

If-Match 없는 PUT을 그냥 통과시키면, 낙관적 동시성은 "보내는 클라이언트만 보호받는 옵션"이 된다. 그러면 어떻게 되는가.

428 없이 통과시킬 때 — 규칙을 지킨 쪽만 손해

  • 성실한 클라이언트 A: If-Match를 꼬박꼬박 보낸다 → 충돌 시 412를 받고 재조회한다
  • 게으른 클라이언트 B: If-Match를 안 보낸다 → 항상 성공한다. 남의 수정을 덮어쓴다
  • 결과: A가 애써 지킨 계약을 B가 무력화한다. 규칙을 지킨 쪽만 손해 보는 구조.

428로 거부할 때 — 모두 같은 계약 위에

  • B의 요청이 428로 막히므로 모든 소비자가 같은 계약 위에 서게 된다.
  • 클라이언트 입장에서도 "어디를 고쳐야 하는지"가 명확하다 — 400이었다면 본문을 뒤졌을 것이다.
  • 새로 붙는 소비자가 계약을 모른 채 조용히 데이터를 망가뜨리는 일이 원천 차단된다.

세 코드를 한 줄로 — 깨짐 · 상태 · 없음

클라이언트가 헤더로 건 전제가 깨졌다 → 412  ·  전제 헤더와 무관하게 상태가 안 맞는다 → 409  ·  전제를 걸어야 하는데 없다 → 428

덧붙일 한마디 — "412는 조건부 요청 메커니즘 전용 응답"이라는 문장을 말할 수 있으면 3절에서 세운 조건부 요청이라는 범주를 이해했다는 신호가 된다.

8-3. * — 존재 여부만 묻는 와일드카드

같은 ETag를 재료로 쓰지만 If-Match는 쓰기 안전, If-None-Match는 읽기 절약이다. 세 번째 줄은 덜 알려졌지만 생성 경쟁을 막는 데 유용하다.
헤더 조합용도조건이 참일 때조건이 거짓일 때
If-Match + PUT/PATCH/DELETE낙관적 동시성 (lost update 방지)실행하고 200412 — 실행하지 않음
If-None-Match + GET캐시 재검증 ("바뀐 것 없으면 본문 생략")본문과 함께 200304 Not Modified — 본문 생략
If-None-Match: * + PUT/POST"없을 때만 만들어라" (덮어쓰기 방지 생성)생성하고 201412 — 이미 존재함
If-Match: * + PUT/DELETE"존재하기만 하면 실행하라"실행412 — 자원이 없음
*는 "어떤 ETag든", 즉 "그 자원이 존재하기만 하면"을 뜻한다 그러므로 If-None-Match: *는 "그 자원이 존재하지 않을 때만 실행하라"가 되어, PUT으로 자원을 만들 때 남이 이미 만들어 둔 것을 실수로 덮어쓰는 일을 막는다. 반대로 If-Match: *는 "존재하기만 하면 실행하라"이므로 "없는 자원에는 실행하지 마라"라는 뜻이 된다. — 버전 없이도 걸 수 있는 가장 싼 전제조건이라, 클라이언트가 아직 ETag를 들고 있지 않은 생성 경로에서 쓸모가 있다.

9. 412를 받은 다음 — 자동 재시도의 함정

412는 "네 사본이 낡았다"는 신호이므로 복구 절차는 셋이다. 4-2 타임라인의 t6~t7이 바로 이 절차다.

조
다시 GET해서 최신 표현과 새 ETag를 받는다. — 서버가 알려줄 수 있는 것은 여기까지다.
판
자신의 변경을 최신본 위에 다시 적용할 수 있는지 판단한다. — 여기가 기술이 아니라 UX·제품 결정이다. 서버가 대신 정해 줄 수 없다.
재
새 ETag를 If-Match에 실어 재요청한다.
겹치는 필드가 없으면
A는 메모, B는 배송지처럼 충돌 필드가 없으면 자동 병합해 재시도할 수 있다.
같은 필드를 고쳤다면
"다른 사용자가 수정했습니다"를 보여주고 diff와 함께 사람에게 선택을 넘겨야 한다.
편집량이 큰 화면이라면
사용자의 입력을 잃지 않도록 로컬에 보관한 뒤 최신본과 나란히 보여주는 설계가 필요하다.

9-1. 반드시 붙여야 할 지적 — 자동 재시도는 last write wins로의 회귀다

1절에서 정의했듯 last write wins는 아무 검사도 하지 않을 때 나중 쓰기가 앞의 것을 전부 덮어써 최종 상태가 되는 기본 동작이다. 그런데 클라이언트가 412를 받고 "재조회 후 내 본문 그대로 재전송"을 자동으로 수행하면 어떻게 되는지 보자.

t5  B 의 PUT (If-Match: "7")  → 412
t6  B 의 클라이언트가 자동으로 GET → ETag "8" 획득
t7  B 의 클라이언트가 자동으로 PUT (If-Match: "8", 본문은 t3의 낡은 값 그대로)
    → 200. A 의 "선물포장"이 결국 덮여 사라진다.

    검사를 통과했을 뿐 결과는 아무 검사도 안 한 것과 같다.
    = last write wins 로 되돌아갔다

이 문서에서 가장 오해받는 문장

If-Match가 막아 주는 것은 "덮어쓰기"가 아니라 "덮어쓰는 줄 모르고 덮어쓰기"다

클라이언트가 그 신호를 받고도 사람에게 알리지 않은 채 같은 본문을 다시 밀어 넣으면, 프로토콜이 만들어 준 개입 기회를 스스로 버린 것이다.

정리하면 — 412는 자동 재시도 대상이 아니라 사용자에게 보여야 하는 에러다. 이 구분은 실무에서 아주 자주 어긋난다: 공통 HTTP 클라이언트에 "4xx 중 일부를 재시도" 같은 정책이 들어 있으면 412가 거기 휩쓸려 조용히 삼켜진다. 재시도 정책의 예외 목록에 412를 명시해 두는 것이 실무 대응이다.

헷갈리기 쉬운 대비 — DB의 낙관적 락 재시도는 왜 자동으로 해도 되나? ObjectOptimisticLockingFailureException을 잡아 트랜잭션 전체를 다시 실행하는 자동 재시도는 널리 쓰이는 정석이다. 차이는 "무엇을 다시 하는가"에 있다. DB 재시도는 읽기부터 다시 하므로 최신 값을 근거로 계산이 다시 이뤄진다. 반면 412 자동 재시도는 사람이 낡은 화면을 보고 만든 본문을 그대로 다시 보내므로 근거가 갱신되지 않는다. — 재실행해도 되는 것은 "계산"이고, 재실행하면 안 되는 것은 "사람의 낡은 판단"이다.

10. 헤더 방식 vs 본문 version 필드

기능적으로는 같은 낙관적 검사다. 이것을 먼저 인정하고 시작하는 편이 좋다 — 어느 쪽이든 "내가 본 버전"을 서버에 알려 주고 서버가 대조하는 구조는 동일하다. 차이는 계약이 어디에 놓이는가에서 나온다.

본문 방식이 나쁜 설계는 아니다. 다만 그 선택에 딸려 오는 것들이 있다.
축헤더 방식 (ETag / If-Match)본문 방식 ({"version": 7})
표준성HTTP 표준 시맨틱 — 중간 계층이 이해한다우리 팀의 자체 규약
충돌 응답 코드412 (표준이 정해 준다)팀 규약 (주로 409)
관심사 분리동시성 제어가 헤더에 있어 자원 표현이 깨끗하다자원 표현 안에 동시성 제어 필드가 섞인다

헤더 방식의 결정적 이점 한 문장 "우리 앱을 모르는 바깥의 것들이 이해한다." 표준 클라이언트 라이브러리, API 게이트웨이, 캐시가 If-Match와 412를 이미 알고 있다. 본문 방식은 우리 문서를 읽은 사람만 이해한다.
어느 쪽이든 팀 전체가 한 방식으로 일관되게 쓰고, 그 선택과 충돌 응답 코드를 API 문서에 명시하는 것이 정답이다

같은 회사 API인데 어떤 엔드포인트는 412를 주고 어떤 엔드포인트는 409를 주면, 클라이언트는 둘 다 처리하는 코드를 짜야 한다. 일관성의 가치가 방식 선택의 가치보다 크다.

11. 비관적 "편집 잠금"과 어떻게 고르나 시니어 변별

2절의 대비를 실제 선택으로 옮기는 질문이다. 기준은 충돌의 빈도와 실패했을 때 잃는 것의 크기다.

낙관적(ETag/If-Match)이 이기는 조건은 "충돌이 드물다"이다. 충돌이 없을 때의 비용이 0이므로, 평상시에는 아무 대가도 치르지 않고 드문 충돌만 412로 처리한다. 대부분의 어드민 CRUD가 여기 해당한다.

그런데 편집 세션이 길면 이 계산이 뒤집힌다. 30분짜리 긴 편집(대형 문서, 복잡한 설정 화면)에서 충돌이 잦다면, 사용자가 30분 작업을 마치고 저장을 눌렀을 때 412를 받는 경험은 재앙이다. 낙관적 방식의 대가인 "실패를 클라이언트가 감당한다"가 여기서는 30분의 작업 손실이라는 값으로 청구된다.

11-1. 비관적으로 간다면 — HTTP에서의 모습은 "잠금을 자원으로 만드는 것"

DB 락은 트랜잭션에 묶여 있어 사람 시간을 건널 수 없으므로(1절), 잠금을 애플리케이션 자원으로 승격시킨다.

POST   /documents/42/lock    -> 201 Created, { "lockId": "...", "expiresAt": "..." }
                                이미 남이 잠갔으면 409 Conflict + 누가 잠갔는지

PUT    /documents/42         -> 잠금 소유자만 실행 가능
DELETE /documents/42/lock    -> 편집 종료 시 해제

잠금을 도입하면 반드시 따라오는 비용 셋 — 만 · 뺏 · 보

만료 (TTL)
사용자가 탭을 닫으면 해제 요청이 안 온다(1절의 "유령"이 그대로 재현). 만료 시각을 두고 자동 회수해야 하고, 그러면 "편집 중인데 잠금이 만료되는" 반대 문제가 생겨 하트비트 갱신이 필요해진다.
뺏기 (강제 해제)
잠근 사람이 휴가를 갔을 때 관리자가 뺏을 수 있어야 하고, 뺏겼을 때 원래 사용자의 작업은 어떻게 되는지 정해야 한다.
보여주기 (소유권 UX)
"김철수님이 편집 중입니다"를 보여주고, 언제까지 기다려야 하는지 알려 줘야 한다.

이 셋을 함께 말하는 것이 채점 포인트다. "잠그면 되죠"에서 멈추면 잠금의 비용을 계산해 본 적 없는 사람으로 보인다.

세 번째 선택지 — 충돌 자체를 병합으로 흡수하는 실시간 협업 편집 OT나 CRDT 계열이다. 구글 독스처럼 두 사람의 편집을 동시에 반영해 애초에 "충돌"이라는 사건을 없애는 방식인데, 구현 난도가 한 자릿수 이상 높아지므로 그 자체가 제품의 핵심 가치일 때만 선택한다.
기본은 낙관적, 편집 세션이 길고 충돌 비용이 크면 잠금 자원 도입, 협업 편집이 제품의 본질이면 병합 모델

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

왜 DB 락으로 못 잡나?
커 · 무 · 유 — 커넥션을 몇 분 붙들 수 없고, HTTP 무상태라 GET/PUT이 같은 커넥션이 아니며, 잠근 사람이 안 돌아오면 회수 못 한다.
왕복을 두 줄로?
GET 응답 ETag: "7" → 수정 요청 If-Match: "7". 일치하면 200 + 새 ETag, 어긋나면 412 + 요청 미실행.
409 / 412 / 428 한 줄?
깨짐 · 상태 · 없음 — 헤더로 건 전제가 깨짐 412, 전제 헤더와 무관한 상태 충돌 409, 전제를 안 걸었음 428.
조건부 요청 방향 규칙?
쓸 때는 같아야 실행(If-Match) · 읽을 때는 달라야 실행(If-None-Match). 거짓일 때 각각 412 / 304.
ETag의 원천과 충돌 판정?
@Version 컬럼. UPDATE ... WHERE id=? AND version=?의 영향 행 수 0이면 충돌. 검사가 WHERE 안에 있어 원자적이다.
왜 이중 방어인가?
If-Match는 사람 시간(분·시간), @Version은 밀리초 레이스를 덮는다. 하나만 두면 각각의 구멍이 그대로 남는다.
약한 ETag 함정?
If-Match는 강한 비교라 W/"7"은 절대 일치하지 않는다. gzip 압축 계층이 ETag를 약하게 낮추면 항상 412가 난다.
412를 받으면 하면 안 되는 것?
자동 재시도. 낡은 본문 그대로 재전송하면 last write wins로 회귀한다. 절차는 조 · 판 · 재(재조회 → 병합 판단 → 재요청)이고, 판은 사람의 몫이다.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

412를 받은 클라이언트는 그다음에 뭘 해야 하나요? 필수힌트: 절차 셋을 말한 뒤, "가운데 단계는 기술이 아니다"를 반드시 덧붙인다

412는 "네 사본이 낡았다"는 신호이므로 복구 절차는 셋이다 — 조 · 판 · 재. ① 다시 GET해서 최신 표현과 새 ETag를 받는다. ② 자신의 변경을 최신본 위에 다시 적용할 수 있는지 판단한다. ③ 새 ETag를 If-Match에 실어 재요청한다.

여기서 ②는 기술이 아니라 UX·제품 결정이라는 점이 핵심이다. 서버가 대신 정해 줄 수 없다 — ETag는 "바뀌었다"만 알려줄 뿐 "무엇이 어떻게 바뀌었는지"는 알려주지 않기 때문이다. 겹치는 필드가 없으면 자동 병합이 가능하고, 같은 필드를 고쳤다면 diff와 함께 사람에게 선택을 넘겨야 한다.

그리고 반드시 붙일 지적 — 412를 자동 재시도로 뭉개면 결국 last write wins로 되돌아간다

재조회 후 낡은 본문을 그대로 다시 보내면 검사는 통과하지만 결과는 아무 검사도 안 한 것과 같다. If-Match가 막는 것은 "덮어쓰기"가 아니라 "덮어쓰는 줄 모르고 덮어쓰기"이므로, 412는 삼키는 에러가 아니라 사용자에게 보여야 하는 에러다. 실무 대응까지 말하면 좋다 — 공통 HTTP 클라이언트의 재시도 정책 예외 목록에 412를 명시해 둔다.

PATCH는 부분 수정인데도 If-Match가 필요한가요? 함정힌트: "겹치는 필드가 없으니 안전하다"는 착시를 깨는 예시 하나면 끝난다

필요하다. PATCH가 바꾸는 필드가 하나여도, 그 하나를 무엇으로 바꿀지 결정한 근거는 낡은 사본일 수 있기 때문이다.

예를 보면 분명해진다. 관리자가 화면에서 재고가 10인 것을 보고 "2개 출고했으니 8로"라고 판단해 PATCH {"stock": 8}을 보낸다. 그런데 그 사이 다른 곳에서 7개가 팔려 재고가 3이 됐다면, 올바른 값은 8이 아니라 1이다. PATCH가 보낸 값은 "절대값"이지만 그 절대값을 계산한 근거는 낡은 읽기였다.

오히려 PATCH가 더 위험한 면이 있다 — "겹치는 필드만 아니면 안전하다"는 착시 때문에 If-Match를 생략하기 쉽기 때문이다.

다만 예외가 있다. "조회 없이도 항상 유효한 연산"으로 설계된 엔드포인트라면 전제조건 없이도 안전하다. {"op": "increment", "field": "stock", "by": -2} 같은 상대 연산은 현재 값이 무엇이든 "2 줄인다"가 항상 의도한 바이므로 낡은 읽기에 의존하지 않는다.

전제조건의 필요 여부는 메서드 이름이 아니라 "이 연산이 낡은 읽기에 의존하는가"로 정한다

절대값을 보내면 필요하고, 상대 연산이면 대체로 불필요하다. 대신 상대 연산은 멱등하지 않아 재시도가 위험해진다 — 즉 "전제조건이 필요 없는 대신 재시도가 위험해지는" 맞교환이다. (02-put-vs-patch.md, 06-idempotency-key-design.md)

ETag 없이 요청 바디에 version 필드를 넣는 방식과 뭐가 다른가요? 필수힌트: "본문 방식은 틀렸다"고 말하면 감점이다. 먼저 같은 점을 인정하고 시작한다

기능적으로는 같은 낙관적 검사다. 이것을 먼저 인정하고 시작하는 편이 좋다 — 어느 쪽이든 "내가 본 버전"을 서버에 알려 주고 서버가 대조하는 구조는 동일하다. 차이는 계약이 어디에 놓이는가에서 나온다.

헤더 방식의 결정적 이점은 "우리 앱을 모르는 바깥의 것들이 이해한다"는 점이다. 표준 클라이언트 라이브러리·게이트웨이·캐시가 If-Match와 412를 이미 알고 있고, 같은 ETag를 캐시 재검증에 재사용할 수도 있다. 본문 방식은 우리 문서를 읽은 사람만 이해한다.

본문 방식이 나쁜 설계는 아니다. 구현이 직관적이고(DTO 필드 하나), 폼 전송이나 헤더 조작이 까다로운 클라이언트 환경에서 현실적이다. 다만 그 선택에는 "충돌 코드를 팀 규약으로 정해야 한다(주로 409)"와 "DELETE에는 적용하기 애매하다(본문을 싣기 어렵다)"가 딸려 온다. 자원 표현 안에 동시성 제어 필드가 섞이는 것도 비용이다.

어느 쪽이든 팀 전체가 한 방식으로 일관되게 쓰고, 그 선택과 충돌 응답 코드를 API 문서에 명시하는 것이 정답

같은 회사 API인데 어떤 엔드포인트는 412를 주고 어떤 엔드포인트는 409를 주면, 클라이언트는 둘 다 처리하는 코드를 짜야 한다.

GET마다 ETag를 만들려면 비용이 들지 않나요? 컬렉션 응답은요?힌트: "재료에 따라 다르다"로 시작하고, 컬렉션은 용도별로 갈라 답한다

재료에 따라 다르다는 것이 답의 출발점이다. 단건 자원이 버전 컬럼 기반이면 비용은 사실상 0이다 — 이미 조회한 엔티티의 필드 하나를 문자열로 바꿔 헤더에 넣을 뿐이다. 해시 기반이면 직렬화 결과에 해시 비용이 붙는데, 동시성 제어가 목적이라면 해시를 계산하는 대신 버전 컬럼을 두는 쪽으로 문제를 옮기는 게 낫다.

컬렉션(목록) 응답은 용도별로 판단이 갈린다.

동시성 제어 목적
목록에 ETag가 필요 없다. 편집 대상은 개별 자원이지 목록 자체가 아니다. PUT /orders처럼 목록 전체를 통째로 교체하는 API를 만들지 않는 한, 목록에 If-Match를 걸 일이 없다.
캐시 재검증 목적
별개의 판단이고 재료를 고르기가 까다롭다. 항목들의 최대 updated_at이나 전체 응답 해시가 되는데, 항목 하나만 바뀌어도 전체가 무효화되므로 적중률이 낮다. 페이지네이션 파라미터마다 캐시 키가 갈리는 것도 감안해야 한다.

답의 골자는 이것이다 — "ETag를 어디에 왜 붙이는가"를 용도별(쓰기 보호 vs 캐시 재검증)로 나눠 판단한다. 두 용도가 같은 값을 재사용할 수 있다는 것이 ETag의 매력이지만, 붙일지 말지의 판단 기준은 용도마다 다르다.

이 방식 대신 비관적으로 "편집 잠금"을 거는 설계와는 어떻게 고르나요? 시니어 변별힌트: 결론보다 "축"이 중요하고, 잠금에 딸려 오는 비용 셋을 반드시 계산에 넣는다

기준은 충돌의 빈도와 실패했을 때 잃는 것의 크기다. 낙관적이 이기는 조건은 "충돌이 드물다"이고 — 충돌이 없을 때의 비용이 0이므로 평상시엔 아무 대가도 치르지 않는다. 대부분의 어드민 CRUD가 여기다.

그런데 편집 세션이 길면 계산이 뒤집힌다. 30분짜리 편집에서 저장을 눌렀을 때 412를 받는 경험은 재앙이다 — "실패를 클라이언트가 감당한다"는 대가가 30분의 작업 손실로 청구된다.

비관적으로 가기로 했다면 HTTP에서의 모습은 "잠금 자체를 하나의 자원으로 만드는 것"이다 — POST /documents/42/lock(이미 남이 잠갔으면 409), DELETE /documents/42/lock. DB 락은 트랜잭션에 묶여 사람 시간을 건널 수 없으므로 잠금을 애플리케이션 자원으로 승격시키는 것이다.

그리고 잠금에 딸려 오는 비용 셋을 함께 말해야 한다 — 만 · 뺏 · 보. 만료(TTL): 탭을 닫으면 해제 신호가 안 오므로 자동 회수가 필요하고, 그러면 "편집 중인데 만료되는" 반대 문제로 하트비트가 필요해진다. 강제 해제: 잠근 사람이 휴가를 갔을 때 뺏을 수 있어야 하고 뺏긴 쪽의 작업 처리를 정해야 한다. 소유권 UX: "김철수님이 편집 중입니다"와 대기 시간을 보여줘야 한다.

세 번째 선택지도 언급하면 좋다 — OT/CRDT 계열의 실시간 협업 편집으로 충돌이라는 사건 자체를 없애는 방식인데, 난도가 한 자릿수 이상 높으므로 그것이 제품의 핵심 가치일 때만 고른다. 정리: 기본은 낙관적, 세션이 길고 충돌 비용이 크면 잠금 자원, 협업 편집이 본질이면 병합 모델.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

네트워크 재시도로 같은 PUT이 두 번 갔는데, 두 번째가 412를 받습니다. 버그인가요? 함정힌트: 첫 요청이 성공했는데 응답만 유실된 경우를 그려보라

버그가 아니라 If-Match의 구조적 성질이다. 순서를 그려 보면 분명하다 — 클라이언트가 If-Match: "7"로 PUT을 보냈고 서버는 정상 처리해 version 8이 됐는데 응답이 네트워크에서 유실됐다. 클라이언트는 실패로 판단하고 같은 요청(If-Match: "7")을 재전송한다. 서버는 이미 8이므로 412를 돌려준다.

결과적으로 "쓰기는 성공했는데 클라이언트는 실패로 안다"는 상태가 된다. 원래 PUT은 멱등해서 재시도가 안전한 메서드였는데, If-Match를 붙이는 순간 "같은 요청을 두 번 보내면 두 번째는 실패한다"가 되기 때문이다.

If-Match는 안전을 얻는 대신 재시도의 단순함을 내놓는 거래다

대응은 둘이다. ① 클라이언트가 412를 받으면 먼저 재조회해 "현재 상태가 이미 내가 의도한 그대로인지" 확인한다 — 그렇다면 내 요청이 성공한 것이므로 성공으로 처리한다. ② 더 확실한 방법은 멱등성 키(Idempotency-Key)를 함께 쓰는 것이다. 서버가 같은 키의 요청을 원래 응답 그대로 재생해 주면 재전송이 412가 아니라 원래의 200을 받는다.

두 장치는 목적이 다르므로 겹쳐 쓴다 — If-Match는 "다른 사람"의 개입을 막고, 멱등성 키는 "나 자신의 중복 전송"을 막는다. (06-idempotency-key-design.md)

서버 인스턴스가 여러 대인데 각자 ETag를 만들면 값이 갈리지 않나요? 시니어 변별힌트: 재료가 무엇이냐에 따라 답이 정반대다

재료에 따라 갈린다. 그리고 이것이 동시성 제어용 ETag로 버전 컬럼을 권하는 또 하나의 이유다.

버전 컬럼 기반이면 갈리지 않는다. 값의 출처가 모든 인스턴스가 공유하는 DB이므로, 어느 인스턴스가 응답하든 같은 자원에는 같은 ETag가 나간다. 인스턴스 독립적이라는 점이 구조적 이점이다.

내용 해시 기반이면 갈릴 수 있다. 같은 데이터를 직렬화해도 JSON 필드 순서, 소수점 표기, 라이브러리·JVM 버전 차이로 바이트가 달라지면 해시가 달라진다. 그러면 로드밸런서가 요청을 어느 인스턴스로 보내느냐에 따라 ETag가 흔들리고, If-Match가 무작위로 412를 낸다. 재현이 어려운 종류의 버그다.

중간 계층도 용의자다 — 7절의 gzip 사례처럼 프록시가 ETag를 약한 것으로 낮추거나 재작성하면 같은 증상이 난다. (캐시 재검증 쪽에서 같은 문제가 어떻게 나타나는지는 08-network-http/20-http-caching-headers-and-304.md에서 다룬다.)

If-Match를 DELETE에도 쓰나요?힌트: "lost update"의 삭제판을 떠올려 보라

쓴다. 오히려 헤더 방식의 이점이 가장 잘 드러나는 자리다. 의미는 "내가 본 그 상태의 자원만 삭제하라"이고, 막는 사고는 lost update의 삭제판이다 — 관리자가 목록에서 본 상태를 근거로 삭제를 눌렀는데, 그 사이 다른 사람이 그 자원의 상태를 바꿔 놓아 이제는 삭제하면 안 되는 자원이 됐을 수 있다. If-Match가 걸려 있으면 412로 막히고 사람이 다시 확인하게 된다.

본문 방식({"version": 7})이 여기서 불리하다 — DELETE에 본문을 싣는 것은 권장되지 않아서, 결국 쿼리 파라미터로 버전을 넘기는 어색한 우회를 하게 된다. 10절 표의 "DELETE에 적용" 줄이 이 이야기다.

두 가지를 덧붙이면 좋다. ① If-Match: *는 "존재할 때만 삭제하라"가 되어, 이미 지워진 자원에 대한 재전송을 412로 구분할 수 있다. ② DELETE 성공 응답에는 새 ETag가 없다 — 자원이 사라졌으므로 붙일 표현 자체가 없기 때문이다. PUT과 달리 "연속 편집을 위한 새 ETag" 개념이 성립하지 않는다.

412 응답 본문에 최신 표현을 같이 실어 주면 클라이언트가 재조회를 안 해도 되지 않나요? 가산점힌트: 좋은 아이디어다. 그런데 무엇과 충돌하는지를 같이 말해야 한다

실무적으로 좋은 아이디어이고 표준이 금지하지도 않는다. 4-2 타임라인의 t6(재조회 GET)을 통째로 없앨 수 있으므로 왕복이 하나 줄고, 클라이언트가 즉시 diff 화면을 띄울 수 있다.

다만 대가가 셋 있다. ① 에러 응답 포맷과 충돌한다 — 팀이 {code, message} 같은 표준 에러 본문을 쓰고 있다면 412만 자원 표현을 반환하는 예외가 생긴다. 절충은 에러 본문 안에 current 필드로 감싸 넣는 것이다. ② 권한 검사가 필요하다 — 그 사용자가 최신 표현을 볼 권한이 있는지 확인하지 않으면 에러 응답이 정보 유출 경로가 된다. ③ 응답 크기가 커진다 — 충돌이 잦은 대형 문서라면 무시할 수 없다.

그리고 반드시 문서화한다. "412 본문에 최신 표현을 싣는다"는 표준이 정해 주지 않는 우리 팀의 규약이므로, API 문서에 없으면 클라이언트가 활용하지 못한다. (05-error-response-body-standardization.md)

GET 없이 바로 PUT하는 배치·서버 간 연동은 428로 막으면 다 깨지는데요?힌트: 428을 걸지 말지는 자원이 아니라 "경로"의 성질로 정한다

좋은 지적이고, 여기서 판단 기준이 한 번 더 정교해진다. 428로 강제할지는 자원 단위가 아니라 "그 자원을 고치는 경로가 사람 시간을 낀 read-modify-write인가"로 정해야 한다.

외부 시스템을 원천으로 삼아 밀어 넣는 동기화 배치라면 이야기가 다르다. 이때 배치가 보내는 값은 화면에서 읽은 낡은 사본이 아니라 원천 시스템의 현재 값이므로 낡은 읽기에 의존하지 않는다. 이런 경로에서는 "마지막에 도착한 원천 값이 이긴다"가 오히려 의도된 동작이다.

그래서 실무 선택지는 셋이다. ① 사람이 쓰는 편집 엔드포인트와 배치용 동기화 엔드포인트를 분리하고 전자에만 428을 건다. ② 배치에는 If-Match: *만 요구해 "존재 확인"이라는 최소 전제만 건다. ③ 배치가 꼭 같은 엔드포인트를 써야 한다면, 서버가 한 트랜잭션 안에서 read-modify-write를 수행해 사람 시간이 끼지 않게 만든다 — 사람 시간이 없으면 @Version만으로 충분하기 때문이다(6절).

마무리 한 문장 — "낙관적 동시성은 사람이 읽고 사람이 고치는 경로를 위한 장치이므로, 그 전제가 없는 경로에까지 일률적으로 강제하면 계약이 아니라 방해물이 됩니다."

충돌을 아예 없애는 방향으로 자원을 설계할 수는 없나요? 시니어 변별힌트: 412가 자주 나는 것은 동시성 문제가 아니라 자원 경계 문제일 수 있다

있고, 412가 자주 난다면 먼저 의심해야 할 것이 자원 경계다. 4-2 타임라인에서 A와 B는 서로 다른 필드(메모 / 배송지)를 고쳤는데도 충돌했다. 이유는 둘이 같은 자원 /orders/42를 통째로 PUT했기 때문이다 — 충돌은 데이터가 겹쳐서가 아니라 "자원의 입자 크기(granularity)"가 커서 생겼다.

그래서 세 방향의 설계 개선이 가능하다. ① 자원을 쪼갠다 — PATCH /orders/42/memo, PATCH /orders/42/shipping-address처럼 독립적으로 편집되는 부분을 별도 자원(또는 별도 버전)으로 나누면 두 편집이 애초에 만나지 않는다. ② 상대 연산으로 바꾼다 — 재고처럼 "현재 값 + 델타"로 표현할 수 있는 것은 낡은 읽기에 의존하지 않으므로 충돌 자체가 성립하지 않는다. ③ 필드 단위 병합 — 서버가 변경된 필드만 받아(PATCH) 겹치지 않으면 자동 병합하고 겹칠 때만 412를 낸다.

다만 대가를 같이 말해야 한다. ①은 자원 수가 늘고 "주문 하나를 저장한다"는 원자성이 깨진다(두 자원을 각각 저장하다 하나만 성공할 수 있다). ②는 멱등하지 않아 재시도가 위험하다. ③은 서버가 필드 수준 충돌 판정 로직을 떠안는다.

그래서 실무 순서는 이렇다 — 먼저 If-Match로 안전을 확보하고, 412 발생률을 지표로 관찰한 뒤, 그 비율이 높은 자원에 한해 경계를 다시 그린다. 충돌률은 동시성 설계의 결과 지표이면서 자원 설계의 진단 지표이기도 하다.

한 줄 요약
GET과 PUT 사이의 사람 시간은 DB 락으로 잡을 수 없으므로 잠그지 않고 저장 시점에 검사하는 낙관적 방식을 택하고, 그 검사를 표현하는 HTTP의 어휘가 조건부 요청 — 서버가 GET 응답에 표현의 꼬리표인 ETag를 실어 주고 클라이언트가 수정 요청의 If-Match로 되돌려주면, 어긋날 때 서버가 요청을 실행하지 않고 412를 돌려주는 왕복 — 이다. 상태 코드는 "헤더로 건 전제가 깨졌다 → 412, 전제 헤더와 무관한 상태 충돌 → 409, 전제를 걸어야 하는데 안 걸었다 → 428"로 갈리며 428이 있어야 낙관적 동시성이 옵션이 아닌 계약이 되고, ETag의 원천은 결국 WHERE id = ? AND version = ?의 영향 행 수로 충돌을 판정하는 @Version 컬럼이라 API 레벨의 If-Match가 사람 시간을 덮고 DB의 @Version이 밀리초 레이스를 덮는 이중 방어가 된다 — 다만 412를 자동 재시도로 뭉개면 결국 last write wins로 되돌아가므로, 412는 삼키는 에러가 아니라 사람에게 보여 병합을 결정하게 하는 신호다.
