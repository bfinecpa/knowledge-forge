API 버저닝 전략 — URI vs 헤더
"미래의 변경"을 지금 설계하는 일

면접 질문: "API 버저닝 전략(URI, 헤더)의 장단점은?"

핵심 관전 포인트 — 버저닝을 말하려면 먼저 "언제 버전을 올리는가"의 기준인 파괴적 변경(breaking change) — 기존 클라이언트 코드를 한 줄도 고치지 않은 채로 새 서버와 통신했을 때 동작이 깨지는 변경 — 을 정의해야 한다. 응답에 필드를 더하는 것이 안전한 이유는 대부분의 JSON 역직렬화기가 모르는 필드를 그냥 무시하기 때문이고, 필드를 빼는 것이 위험한 이유는 있어야 할 값이 사라지면 그 자리에서 NPE나 파싱 실패로 죽기 때문이다 — 즉 안전/위험의 근거는 서버가 아니라 소비자 쪽 파서의 동작에 있다. 이 파괴적 변경을 흡수하는 방법이 "기존 계약(v1)은 그대로 두고 새 계약(v2)을 나란히 제공"하는 버저닝이고, 버전을 요청의 어디에 적느냐에 따라 경로·헤더·쿼리 세 방식으로 갈린다. URI 방식(/v1/orders)이 캐시·로그·라우팅에 유리한 이유는 명확하다 — HTTP 캐시의 기본 키가 메서드+URL이고 프록시·CDN·게이트웨이는 애초에 경로를 보고 판단하는 장비라서, 버전이 경로에 있으면 그 장비들이 우리 앱을 전혀 몰라도 버전을 구분할 수 있다. 헤더 방식(Accept: application/vnd.myapp.v2+json)은 HTTP의 콘텐츠 협상을 버전 선택에 재사용하는 것이라 URI가 순수하게 유지되지만, 브라우저 주소창으로 테스트할 수 없고 캐시가 Vary: Accept를 정확히 다뤄야 버전 섞임 사고를 피한다. 그리고 진짜 난도는 만드는 쪽이 아니라 없애는 쪽에 있다 — v2 출시 → Deprecation 고지 → 버전별 사용량 계측 → Sunset으로 종료 일시 확정 → brownout(짧게 일부러 끊어 남은 소비자를 깨우는 리허설) → 410 Gone 종료라는 폐기 타임라인과 그 근거가 되는 사전 계약이 v2를 낼 때 함께 준비돼 있어야 한다. 최고의 버저닝은 하위 호환 변경만으로 진화시켜 버전을 올릴 일 자체를 줄이는 것이다.
  • 1
    먼저 판단 기준을 정의한다 — 파괴적 변경은 "기존 클라이언트가 코드를 한 줄도 안 고치고 새 서버와 통신했을 때 깨지는 변경"이고, 깨지는 대상이 내 서버가 아니라 남의 클라이언트라는 점이 핵심이다. 추가는 안전하고 삭제는 위험한 근거도 서버가 아니라 소비자 쪽 파서에 있다 — 모르는 필드는 버릴 수 있지만, 없는 필드는 만들어 낼 수 없다.
  • 2
    버전을 요청의 어디에 적느냐가 세 방식이다 — URI 방식은 URL이 곧 캐시 키·라우팅 기준·로그 필드라서 우리 앱 바깥 장비까지 버전을 읽어 준다. 헤더 방식은 콘텐츠 협상을 재사용해 URI 순수성을 지키는 대신 Vary 관리와 가시성 부재를 비용으로 낸다. 소비자를 통제할 수 없을수록 URI 방식으로 기운다.
  • 3
    진짜 난도는 만드는 쪽이 아니라 없애는 쪽이다 — 공·계·고·깨·끊·지(공개+Deprecation → 계측 → Sunset 고지 → brownout → 410 Gone → 코드 제거)의 폐기 타임라인과 그 근거인 사전 계약을 v2를 낼 때 함께 준비한다. 그리고 최고의 버저닝은 하위 호환 변경만으로 진화시켜 버전을 올릴 일 자체를 줄이는 것이다.

0. 질문 + 출제 의도

질문: "API 버저닝 전략(URI, 헤더)의 장단점은?"

출제 의도: 버저닝은 "미래의 변경"을 지금 설계하는 일이다. 전략 없이 시작한 API가 v2를 내야 할 때 겪는 고통을 아는지 — 미래 비용을 앞당겨 사고하는 습관을 본다. 방식 비교 암기가 아니라, 왜 버전이 필요해지고 어떻게 하면 덜 필요해지는지까지 말하는 후보자가 변별된다.

이 페이지가 겨냥하는 약점 세 가지 ① "URI 방식은 캐시·로그·라우팅에 유리하다"를 근거 없이 외운 것 → 4·5절에서 캐시 기본 키가 메서드+URL이라는 사실 하나에서 세 장점이 전부 파생된다는 것을 보여준다.
② "필드 추가는 안전, 삭제는 위험"의 근거를 서버에서 찾는 것 → 3절에서 근거가 소비자 쪽 파서의 동작에 있음을 언어별로 갈라 보여준다.
③ 버전을 "만드는 법"만 말하고 "없애는 법"을 못 말하는 것 → 9·10절에서 계측 → 고지 → brownout → 410으로 이어지는 폐기 타임라인을 시간축에 놓는다.

1. 전제 — 서버는 한 벌인데 클라이언트는 여러 세대다

사내 서비스를 혼자 만들 때는 API를 바꾸는 일이 어렵지 않다. 서버를 고치고 클라이언트를 고쳐 같이 배포하면 끝이다. 버저닝이 문제가 되는 지점은 그 "같이"가 성립하지 않는 순간이다.

API는 배포하는 순간 소비자(모바일 앱, 파트너사, 타 팀)와의 계약이 된다. 문제는 소비자를 내가 통제할 수 없다는 것 — 특히 모바일 앱은 사용자가 업데이트를 안 하면 1년 전 버전이 여전히 살아서 내 API를 호출한다.

버저닝이 하는 일은 딱 하나 — 나란히 두기

파괴적 변경을 배포해야 하는데 소비자를 통제할 수 없다면, 남은 방법은 하나뿐이다. 기존 계약을 그대로 살려 둔 채 새 계약을 그 옆에 하나 더 세우는 것. v1은 어제와 똑같이 동작하고, 준비된 소비자만 v2로 옮겨 온다. 옮겨 오는 시점은 소비자가 자기 사정에 맞춰 정한다.

도로를 폐쇄하고 새로 까는 게 아니라, 새 도로를 옆에 놓고 기존 도로에는 안내판을 붙여 서서히 폐쇄하는 것

이 비유에서 "안내판"과 "서서히"에 해당하는 것이 9~10절의 폐기 정책이고, 실제로는 그쪽이 훨씬 어렵다.

2. 파괴적 변경 — "언제 버전을 올리는가"의 판단 기준

이 주제 전체가 "언제 버전을 올리는가"를 다루는데, 그 판단 기준을 먼저 정의하지 않으면 나머지가 전부 감으로 흐른다. 정의부터 못 박고 간다.

파괴적 변경(breaking change)의 정의 — 한 문장으로 외운다

기존 클라이언트가 자기 코드를 한 줄도 고치지 않은 채 새 서버와 통신했을 때 동작이 깨지는 변경

이름 그대로 "무언가를 깨뜨리는(breaking) 변경"인데, 깨지는 대상이 내 서버가 아니라 남의 클라이언트라는 점이 핵심이다. 반대로 소비자가 아무것도 모른 채 그대로 돌아가면 하위 호환 변경(non-breaking)이다.

하위 호환 (non-breaking) — 버전 없이 그냥 배포

  • 응답에 필드 추가
  • 새 엔드포인트 추가
  • 선택적(optional) 요청 파라미터 추가

기존 클라이언트는 모르는 필드를 무시하면 되므로 아무 일도 일어나지 않는다.

파괴적 (breaking) — 버저닝이 필요한 순간

  • 필드 삭제 / 이름 변경 / 타입 변경
  • 필수 파라미터 추가
  • URL 구조 변경
  • 에러 포맷 변경

기존 클라이언트가 즉시 깨진다. 이때가 버저닝이 필요한 순간이다.

파괴적 변경 6종 암기법 — 필드 3 + 계약 3

필드 3 — 응답 스키마가 바뀐다
삭제 · 이름 변경 · 타입 변경. 셋 다 "클라이언트가 읽던 자리에 기대한 값이 없다"는 같은 사고다. ("amount": 1000 → "amount": "1000" 같은 타입 변경이 가장 자주 실수로 나간다)
계약 3 — 요청/응답의 규약이 바뀐다
필수 파라미터 추가 · URL 구조 변경 · 에러 포맷 변경. 스키마는 그대로여도 부르는 법이나 실패했을 때의 모양이 달라지면 똑같이 깨진다.

여섯 개를 나열식으로 외우면 면접에서 두세 개가 빠진다. "필드 3 + 계약 3"으로 묶으면 두 덩어리만 기억하면 된다.

가장 자주 놓치는 파괴적 변경 — "에러 포맷"과 "열거값 추가" 에러 포맷 변경은 정상 경로 테스트를 아무리 돌려도 안 잡힌다. 소비자는 error.code를 문자열 비교로 분기하고 있는 경우가 많아서, 코드 체계를 정리하는 "리팩터링"이 그대로 파괴적 변경이 된다.
열거값(enum) 추가는 표에서는 "추가"처럼 보이지만 실제로는 위험할 수 있다 — 소비자가 switch에서 모르는 값을 만나 예외를 던지도록 짜 놓았다면 깨진다. 그래서 API 문서에 "열거값은 예고 없이 늘어날 수 있으니 모르는 값은 기본 분기로 처리하라"를 미리 적어 두는 것까지가 계약이다.

변경 종류별 판정표와 "깨야만 할 때"의 expand → migrate → contract 절차는 짝 문서 08-backward-compatible-api-changes.md가 본격적으로 다룬다. 이 문서는 그 판정에서 "파괴적"이 나왔을 때 어떤 장치로 흡수하는가에 집중한다.

3. 비대칭의 근거 — 서버가 아니라 소비자 쪽 파서에 있다

위 분류를 외우지 말고 근거를 이해해야 응용이 된다. 근거는 서버가 아니라 클라이언트의 JSON 파서가 "모르는 필드"와 "없는 필드"를 각각 어떻게 다루는가에 있다.

이 문서에서 하나만 외운다면 이 문장

모르는 필드는 버릴 수 있지만, 없는 필드는 만들어 낼 수 없다

"추가는 안전, 삭제는 위험"을 근거 없이 말하는 사람과, 이 한 문장으로 근거를 대는 사람이 갈리는 지점이다. 그리고 이 문장은 응용이 된다 — "타입 변경"이 왜 위험한지도 같은 논리로 설명된다(파서가 String이 온 자리에 Integer를 만들어 낼 수 없다).

3-1. 단서 하나 — "관대한 파싱"은 공짜가 아니라 규약이다

Jackson 자체의 기본값은 모르는 필드를 만나면 예외를 던지는 쪽(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES가 켜짐)이고, Spring Boot가 자동 구성하는 ObjectMapper에서 그 옵션을 꺼 주기 때문에 무시가 기본처럼 보이는 것이다. 즉 "추가는 안전"은 소비자가 관대한 파싱을 한다는 규약 위에서만 성립한다.

위험 엄격한 소비자 — 필드 추가만으로 깨진다
// 소비자가 ObjectMapper 를 직접 만들어 쓰는 경우
// (Spring Boot 자동 구성을 안 타는 배치 · SDK · 파트너사 코드에서 흔하다)
ObjectMapper om = new ObjectMapper();
om.enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);
// ↑ Jackson 자체의 기본값이 바로 이것이다.
//   서버가 "안전한 변경"이라고 믿고 tier 필드를 추가하는 순간
//   이 소비자는 UnrecognizedPropertyException 으로 죽는다.

OrderDto dto = om.readValue(json, OrderDto.class);
tolerant reader 관대한 소비자 — 계약이 성립한다
// Spring Boot 가 자동 구성하는 ObjectMapper 는 이 옵션을 꺼 준다.
// 직접 만들 때도 명시적으로 꺼서 "관대한 읽기"를 선언한다.
ObjectMapper om = new ObjectMapper();
om.disable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES);

// 그리고 이 규약은 코드가 아니라 API 문서에 적혀 있어야 한다:
//   "응답에는 문서에 없는 필드가 추가될 수 있습니다.
//    소비자는 모르는 필드를 무시해야 합니다."
// 이 한 문장이 있어야 "필드 추가"가 진짜로 안전해진다.
OrderDto dto = om.readValue(json, OrderDto.class);
tolerant reader — "관대한 독자" 모르는 단어가 한둘 나와도 문장을 계속 읽어 나가는 독자를 생각하면 된다. 반대는 모르는 단어가 나오는 순간 책을 덮는 독자다. HTTP API의 진화는 소비자가 전자이기를 전제로 설계되며, 그 전제를 말이 아니라 문서로 못 박아 두는 것이 계약의 일부다. 이 규약이 없으면 11절의 "버전을 안 올리고 진화시키기"가 통째로 불가능해진다.

4. 버전을 적을 수 있는 자리는 셋뿐이다

방식을 세 개 외우기 전에, 왜 선택지가 하필 그 셋인지를 먼저 보면 비교가 쉬워진다. HTTP 요청은 크게 요청 라인(메서드 + 경로 + 쿼리 문자열), 헤더, 본문 세 부분이다. 버전이라는 정보를 서버에 전달하려면 이 셋 중 어딘가에 적는 수밖에 없다.

세 방식을 가르는 한 줄

경로와 쿼리는 URL의 일부라서 중간 장비가 그냥 볼 수 있고, 헤더는 URL 바깥이라 중간 장비가 따로 읽어 줘야 한다

우편물 비유 — 우편 분류기는 봉투 겉면의 우편번호만 읽는다. URI 버저닝은 우편번호에 버전을 넣는 것이라 분류기가 알아서 갈라 준다. 헤더 버저닝은 봉투 안 편지 첫 줄에 버전을 적는 것이라, 봉투를 뜯어 읽을 수 있는 사람(=우리 애플리케이션)만 안다.

5. URI 경로 버저닝 — 바깥 장비가 읽어 준다

GET /v1/orders/42
GET /v2/orders/42

URI 방식의 장점 3 — 가·라·캐

가 — 가시성
URL만 봐도 어떤 계약인지 안다. 브라우저·curl로 바로 테스트되고, 접근 로그만으로 "v1을 아직 누가 쓰는지" 집계가 된다 → 폐기 운영이 쉬워진다.
라 — 라우팅
게이트웨이·LB가 경로 prefix만 보고 v1은 구서버, v2는 신서버로 보낼 수 있다 → 분리 배포가 간단하다.
캐 — 캐시
URL이 다르면 다른 캐시 키다. 중간 캐시(CDN 포함)가 버전을 섞어 응답할 위험이 구조적으로 없다.

세 장점을 나열만 하면 암기로 들린다. 셋이 전부 한 가지 사실에서 나온다는 것까지 말해야 근거가 된다 → 바로 아래.

세 장점의 공통 뿌리 — 이 한 문장이 근거다

URL은 우리 애플리케이션 바깥의 장비들도 이미 읽고 있는 값이다
캐시의 기본 키 = 메서드 + URL
URL이 다르면 캐시 입장에서 애초에 다른 물건이라, 별도 설정 없이 v1·v2 응답이 서로 다른 칸에 들어간다. 반대로 URL이 같으면 뒷사람에게 앞사람의 버전을 내줄 수 있다.
프록시·게이트웨이 = 원래 경로 보는 장비
버전이 경로에 있으면 이 장비들이 우리 애플리케이션 코드를 전혀 몰라도 버전을 구분한다.
액세스 로그 = 요청 라인을 남긴다
아무 설정도 안 한 상태에서 이미 버전별 호출량 집계가 가능하다 → 9절 "잔여 호출자 집계"가 공짜.

5-1. 라우팅 — 게이트웨이가 도메인 로직을 하나도 몰라도 된다

nginx 아는 것은 "경로 앞부분이 /v1 이냐 /v2 이냐" 뿐이다
# 게이트웨이가 우리 앱의 도메인 로직을 하나도 모른 채로 버전을 분리한다.
location /v1/ { proxy_pass http://orders-v1-pool; }   # 유지보수만 하는 구버전 풀
location /v2/ { proxy_pass http://orders-v2-pool; }   # 신규 배포가 나가는 신버전 풀

5-2. 로그 — 폐기 운영의 재료가 공짜로 생긴다

access log 어느 웹서버·CDN이든 기본 로그에 이미 들어 있는 값
10.0.3.11 - - [01/Sep/2026:10:22:03] "GET /v1/orders/42 HTTP/1.1" 200
10.0.3.42 - - [01/Sep/2026:10:22:04] "GET /v2/orders/42 HTTP/1.1" 200
                     ↑ 여기 v1/v2 가 이미 찍혀 있다
                       → 9절의 "v1 잔여 호출자 집계"가 공짜로 따라온다

URI 방식의 단점 — 값을 치르는 곳

  • "같은 자원인데 URI가 두 개" — REST 관점에서 URI는 자원의 식별자인데, 42번 주문이 /v1/orders/42와 /v2/orders/42 두 정체성을 갖게 된다. 자원을 가리켜 저장해둔 링크가 버전에 묶인다.
  • 버전이 계약 전체에 걸리므로, 한 리소스만 바뀌어도 v2로 전체 표면적이 복제되는 경향이 생긴다(코드·문서 유지 비용).

6. 헤더 버저닝 — 콘텐츠 협상을 버전 선택에 재사용한다

# ① 미디어 타입(콘텐츠 협상) 방식
GET /orders/42
Accept: application/vnd.myapp.v2+json

# ② 커스텀 헤더 방식
GET /orders/42
X-API-Version: 2

6-1. 먼저 콘텐츠 협상(content negotiation)이 무엇인가

이 방식을 "정석"이라고 부르는 근거가 콘텐츠 협상인데, 정작 그게 뭔지 모르면 근거가 근거로 들리지 않는다. 먼저 정의하고 간다.

콘텐츠 협상의 정의

클라이언트가 요청 헤더로 "나는 이런 형태의 표현을 원한다"고 말하고,
서버가 자기가 낼 수 있는 표현 중 하나를 골라 응답하는 HTTP의 기본 장치

"협상"이라는 이름은 한쪽이 일방적으로 정하는 게 아니라 클라이언트의 희망과 서버의 능력을 맞춰 본다는 뜻이다.

전제로 필요한 용어 — 자원(resource)과 표현(representation) 자원은 "42번 주문"이라는 대상 자체이고, 표현은 그 대상을 실제 바이트로 옮긴 결과다 — JSON일 수도, XML일 수도, 한국어일 수도, 영어일 수도 있다. 자원 하나에 표현은 여럿일 수 있다는 것이 콘텐츠 협상의 출발점이다.

이미 매일 쓰고 있는 장치이기도 하다.

콘텐츠 협상은 새로 배우는 것이 아니라 이미 쓰고 있던 것이다 — 버전은 그 목록에 한 줄 더 붙이는 것
요청 헤더클라이언트가 말하는 것서버가 고르는 것
Accept: application/json"JSON으로 주세요"표현의 형식
Accept-Language: ko-KR"한국어로 주세요"표현의 언어
Accept-Encoding: gzip"압축해서 보내도 됩니다"표현의 인코딩
Accept: application/vnd.myapp.v2+json"v2 형식으로 주세요"표현의 버전 ← 같은 장치의 재사용

미디어 타입 버저닝은 이 장치를 버전 선택에 그대로 재사용하는 것이다. "JSON 형식의 표현을 주세요"라고 말할 수 있다면 "v2 형식의 표현을 주세요"라고도 말할 수 있지 않겠느냐는 발상이다. 42번 주문이라는 자원은 하나이고, v1 응답과 v2 응답은 그 자원의 서로 다른 표현이라고 보면 개념이 딱 맞아떨어진다 — URI는 자원을 가리키고 헤더는 표현을 고른다. 이것이 "정석"이라고 불리는 이유다.

장점

  • URI가 순수하게 유지된다 — 자원의 식별자(URI)와 표현의 버전(헤더)이 분리된다. HTTP의 콘텐츠 협상을 정석대로 쓰는 방식.
  • 자원을 가리키는 링크가 버전과 무관하게 안정적이다. 채팅으로 공유한 /orders/42가 몇 년 뒤에도 유효하다.

단점

  • 눈에 안 보인다 — 브라우저 주소창으로 테스트 불가, curl에 헤더를 매번 붙여야 하고, 장애 조사 때 접근 로그의 URL만으로는 어떤 버전이 호출됐는지 모른다.
  • 캐시가 까다롭다 — 같은 URL에 버전별로 다른 응답이 나가므로 Vary: Accept를 정확히 줘야 하고, 이를 무시하는 캐시 계층이 있으면 버전 섞임 사고가 난다.
  • 파트너사 개발자 온보딩 비용이 크다 — "헤더 빼먹음"이 흔한 문의 유형이 된다.

6-2. Vary가 무엇이고 왜 여기서 필수인가

두 번째 단점이 이 방식의 실질적인 위험이므로 장치까지 짚어 두자. 앞에서 본 대로 캐시의 기본 키는 메서드 + URL이다. 그런데 헤더 버저닝에서는 URL이 /orders/42 하나뿐이고 응답만 v1·v2로 갈린다 — 캐시 입장에서는 같은 물건인데 내용이 두 가지인 상황이다.

Vary의 정의

서버가 캐시에게 "이 응답은 URL만으로 식별하지 마라.
다음 요청 헤더의 값도 캐시 키에 포함시켜라"라고 알려주는 응답 헤더

이름 그대로 "이 헤더 값에 따라 응답이 달라진다(vary)"는 선언이다. 헤더 버저닝을 택하는 순간 선택이 아니라 필수가 된다.

before Vary 없음 — 버전 섞임 사고의 조건
HTTP/1.1 200 OK
Content-Type: application/vnd.myapp.v2+json
(Vary 헤더가 없다)

# 캐시 키 = (GET, /orders/42)
#   → 버전이 키에 없다
#   → v1 을 요청한 사람과 v2 를 요청한 사람이
#      같은 칸을 공유한다
after Vary: Accept — 캐시 키에 버전이 들어간다
HTTP/1.1 200 OK
Content-Type: application/vnd.myapp.v2+json
Vary: Accept

# 캐시 키 = (GET, /orders/42, Accept 헤더 값)
#   → v1 을 요청한 사람과 v2 를 요청한 사람이
#      서로 다른 칸에 저장된다
before 헤더 버저닝인데 표현이 두 개인 걸 아무도 모른다
@GetMapping("/orders/{id}")
public OrderV2Response get(@PathVariable Long id) {
    return service.findV2(id);
}
// ① 같은 URL 에서 버전을 어떻게 고르는지 코드에 드러나지 않는다.
// ② 응답에 Vary 가 없어 중간 캐시가 v1/v2 를 한 칸에 섞는다.
// ③ 액세스 로그에는 "GET /orders/42" 만 남아
//    나중에 "누가 아직 v1 을 쓰는가"를 집계할 방법이 없다.
after produces 로 협상하고, Vary 와 로깅을 함께 건다
// produces 는 요청의 Accept 헤더와 매칭되는 조건이다.
// 즉 콘텐츠 협상이 프레임워크 수준에서 표현된다.
@GetMapping(value = "/orders/{id}", produces = "application/vnd.myapp.v1+json")
public OrderV1Response getV1(@PathVariable Long id) { ... }

@GetMapping(value = "/orders/{id}", produces = "application/vnd.myapp.v2+json")
public OrderV2Response getV2(@PathVariable Long id, HttpServletResponse res) {
    res.addHeader(HttpHeaders.VARY, HttpHeaders.ACCEPT); 캐시 섞임 방지
    return service.findV2(id);
}
// 그리고 액세스 로그 포맷에 Accept 헤더를 추가하는 인프라 작업이
// "선택"이 아니라 이 방식의 필수 준비물이 된다.
헤더 버저닝의 숨은 비용 — "사고 당시에는 못 하는 일" 헤더를 액세스 로그에 남기는 것은 인프라 설정 변경이다. 그런데 그 필요를 깨닫는 시점은 대개 사고 조사 중이고, 그때는 이미 지나간 요청의 헤더를 되살릴 수 없다. URI 방식이 공짜로 주는 것을 헤더 방식은 "미리 준비해 두어야만" 갖는다 — 그리고 미리 준비해야 하는 일은 자주 빠진다.

7. 쿼리 파라미터 버저닝 — 어느 쪽 장점도 온전히 갖지 못한다

GET /orders/42?version=2

URI 방식과 헤더 방식의 중간이다. URL의 일부라서 눈에 보이고 테스트가 쉽지만, "버전 파라미터를 빠뜨리면 어느 버전인가"라는 기본값 문제가 있고 자원 식별과 표현 선택이 뒤섞여 어느 쪽 장점도 온전히 갖지 못한다.

기본값 딜레마 — 어느 쪽을 골라도 손해다

?version= 없으면 → v1을 준다

무버전 URL /orders/42가 사실상 영구적인 v1 별칭이 된다. 12절 마지막 꼬리질문의 "무버전 API에 나중에 버전 붙이기"와 똑같은 상황으로 되돌아간다.

?version= 없으면 → 최신을 준다

파라미터를 빠뜨린 구버전 클라이언트가 어느 날 갑자기 깨진다. 그것도 우리가 v2를 배포한 날, 우리 대시보드에는 아무 이상 없이.

캐시 관점에서도 어중간하다 쿼리 문자열은 URL의 일부이므로 원칙적으로는 캐시 키에 포함되지만, 중간 장비에 따라 특정 쿼리 파라미터를 캐시 키에서 제외하도록 설정돼 있는 경우가 있다(추적용 파라미터를 제거하려는 흔한 설정). 그래서 URI 방식만큼 안심할 수 없다. 실무에서는 앞의 두 방식보다 드물다.

8. 비교 요약과 실무 선택 기준

세 방식 비교. 표의 각 줄은 4절 도식의 "중간 장비가 읽어 주는가"에서 파생된다 — 외우지 말고 그 한 줄에서 다시 유도할 수 있어야 한다.
기준URI 방식 /v1/orders헤더 방식 Accept: ...v2+json쿼리 방식 ?version=2
가시성 (테스트·로그·디버깅)좋음 — 액세스 로그에 이미 찍힘나쁨 — 별도 로깅 필요좋음 — URL에 보임
라우팅 / 배포 분리쉬움 — 경로 prefix로 풀 분리게이트웨이가 헤더 해석 필요가능하지만 경로보다 번거로움
캐시 안전성좋음 — URL = 캐시 키Vary 관리 필요 — 실패 시 버전 섞임원칙적으로 포함되나 장비 설정에 좌우
REST 순수성 (자원 식별)어색함 — 자원 URI가 버전에 묶임좋음 — 자원/표현 분리자원 식별과 표현 선택이 뒤섞임
소비자 사용 난이도낮음높음 — "헤더 누락" 문의낮음
기본값(생략 시) 문제없음 — 경로가 없으면 404있음 — 헤더 생략 시 기본 버전 지정 필요있음 — 어느 쪽을 골라도 손해

실무 선택 — 정답은 "URI"가 아니라 "소비자가 누구인가"다

외부에 공개하거나 파트너가 소비하는 API는 대부분 URI 방식을 택한다 — 이론적 순수성보다 가시성·운영 편의·소비자 접근성이 주는 이득이 크기 때문이다. 다만 면접에서 값이 나가는 문장은 결론이 아니라 판단 기준이다.

소비자를 통제할 수 없을수록 URI 방식으로 기운다

이유는 한 줄로 이어진다 — 소비자를 통제할 수 없다 = 폐기 운영이 어렵다 = "누가 아직 v1을 쓰는가"라는 재료가 반드시 필요하다. 그리고 그 재료를 URI 방식은 공짜로 준다.

소비자가 누구인가?→ 외부 공개 · 파트너 · 모바일 앱→ 통제 불가 · 폐기 어려움→ URI 방식
소비자가 누구인가?→ 내부 서비스 간 · 같은 조직→ 통제 가능 · 게이트웨이 헤더 라우팅 지원→ 헤더 방식도 유효한 선택지

9. 폐기 타임라인 — 종료는 이벤트가 아니라 절차다

전략 없이 시작한 API가 v2를 내야 할 때 겪는 고통은 대략 이렇다.

1
v2를 냈지만 v1 트래픽이 줄지 않는다 — 어떤 클라이언트가 v1을 쓰는지 집계 수단이 없다.
2
v1·v2 두 벌의 코드/문서/테스트를 무기한 유지한다 — 버그를 두 번 고친다.
3
v1을 내리자 업데이트 안 한 구버전 앱과 연락 안 되는 파트너사가 깨진다 — 장애 문의로 되돌아온다.

세 항목이 별개의 실패처럼 보이지만 원인은 하나다

v2를 낼 때 "언제 어떤 근거로 v1을 내릴 것인가"를 같이 정하지 않았다

그 순간부터 v1 종료는 기술 문제가 아니라 매번 새로 해야 하는 협상이 되고, 협상은 대체로 미뤄진다. 그래서 버저닝 전략에는 폐기 정책이 함께 설계되어야 한다.

① 버전별 사용량 계측
처음부터 버전 × 클라이언트 식별자별 호출량을 대시보드로 본다. "v1 잔여 호출자 톱10"을 뽑을 수 있어야 폐기가 가능하다.
② 폐기 공지 체계
문서·공지에 더해 응답 헤더로 기계가 읽을 수 있는 신호(Deprecation, Sunset)를 실어준다. 가산점
③ 지원 버전 수 상한
"동시 지원 최대 2개 버전, 신버전 공개 후 N개월 뒤 구버전 종료"를 계약(문서)에 미리 명시한다 — 폐기 근거를 사후 협상이 아니라 사전 계약으로.

말로만 하면 "공지하고 내린다"로 뭉개지므로 시간축에 놓고 보자. 아래는 신버전 공개 후 6개월 뒤 종료를 계약해 둔 경우의 표준 진행이다.

이 타임라인에서 눈여겨볼 설계 둘

① 종료를 두 단계로 쪼갰다
T+6의 "410 응답으로 전환"과 T+9의 "코드 제거"는 다른 일이다. 앞은 설정 한 줄로 되돌릴 수 있고 뒤는 되돌리려면 배포가 필요하다.
되돌리기 비용이 다른 두 작업을 같은 날 하지 않는 것이 운영의 기본기다.
② 404가 아니라 410을 쓴다
404 Not Found는 "그런 거 없다"라서 경로를 잘못 썼는지 API가 없어졌는지 구분이 안 된다.
410 Gone은 "여기 있었는데 의도적으로 없앴고 다시 안 돌아온다"는 뜻이라 받는 쪽이 즉시 원인을 안다. 본문에 대체 경로와 문서 링크를 담아 주면 더 좋다.

10. Deprecation · Sunset · brownout — 기계가 읽는 고지와 마지막 수단

블로그 공지와 이메일은 사람이 읽어야 도달한다. 그런데 9절의 세 번째 실패 — "연락 안 되는 파트너사" — 는 정확히 사람이 안 읽는 경로에서 터진다. 그래서 응답 자체에 폐기 정보를 실어 소비자의 코드나 모니터링이 읽을 수 있게 만드는 표준 헤더가 있다.

Deprecation
RFC 9745
"이 엔드포인트가 언제부로 폐기(deprecated)됐는가"를 담는다. 폐기됐다는 것은 아직 동작하지만 더는 권장되지 않고 곧 없어진다는 뜻이다. 값은 구조화 필드의 날짜 형식 — @ 뒤에 유닉스 초 타임스탬프. 값이 미래면 "그날부터 폐기 예정", 과거면 "그날부터 이미 폐기됨".
Sunset
RFC 8594
"이 엔드포인트가 언제 응답을 멈추는가"를 담는다. 이름은 해가 지는 시각이라는 뜻이고, 값은 HTTP 날짜 형식의 절대 시각이다.
응답 폐기 고지를 응답 헤더에 싣는다
HTTP/1.1 200 OK
Content-Type: application/json

Deprecation: @1798761599
# 2026-12-31 23:59:59 UTC 부터 폐기 상태.
# 구조화 필드의 날짜라 '@' 접두사가 붙는다.

Sunset: Wed, 31 Mar 2027 23:59:59 GMT
# 이 시각에 응답이 멈춘다. Deprecation 보다 반드시 뒤여야 한다.

Link: <https://api.example.com/docs/deprecations/orders-v1>; rel="deprecation"
# rel="deprecation" — 사람이 읽을 폐기 안내 문서 (RFC 9745)

Link: <https://api.example.com/v2/orders/42>; rel="successor-version"
# rel="successor-version" — 이 자원의 다음 버전이 어디인지 (RFC 5829)
현실적인 주의 — 표준 이전의 형태가 아직 많이 돌아다닌다 Deprecation은 표준이 되기 전 초안 단계에서 오래 쓰여 왔고, 그 시절 형태인 Deprecation: true나 HTTP 날짜 문자열을 그대로 내려주는 서비스가 아직 많다(GitHub이 그 예다). 받는 쪽을 만들 때는 여러 형태를 관대하게 해석하고, 내려주는 쪽은 현행 표준 형태를 쓰되 문서에 형식을 명시하는 것이 안전하다.
이 헤더들의 실질적인 가치 — 소비자 쪽 자동화 클라이언트가 응답에서 Sunset을 발견하면 로그에 경고를 남기거나 사내 알림을 쏘게 만들어 둘 수 있다. 그러면 "공지 메일을 아무도 안 읽었다"는 문제가 구조적으로 줄어든다. 즉 이 헤더는 우리를 위한 것이 아니라 소비자가 스스로를 지킬 수 있게 해 주는 장치이고, 그래서 파트너 API 문서에 "이 헤더를 감시하세요"까지 적어 주는 것이 한 칸 더 간 답변이다.

10-1. brownout — 짧게 일부러 끊어 남은 소비자를 깨운다

고지를 다 해도 트래픽이 안 빠지는 소비자가 반드시 남는다. 담당자가 바뀌었거나, 배치 스크립트를 아무도 안 보고 있거나, 그냥 안 읽은 경우다. 이들에게 도달하는 마지막 수단이 brownout이다.

brownout의 정의와 어원

종료 전에 짧은 시간 동안 일부러 해당 버전의 응답을 끊어,
남아 있는 소비자가 "장애"로 인지하게 만드는 기법

이름은 전력 용어에서 왔다. blackout(정전)이 완전히 꺼지는 것이라면 brownout은 전압이 떨어져 조명이 어두워지는 부분적 정전이다. 완전히 끄지 않고 잠깐만 어둡게 한다는 뉘앙스가 그대로 옮겨 왔다.

효과의 원리 — 공지는 안 읽어도 장애 알림은 읽는다

아무도 보지 않던 배치 스크립트도 실패하면 누군가에게 알림이 간다. 그때 비로소 "우리가 아직 v1을 쓰고 있었구나"가 발견된다. 화재 대피 훈련과 같은 발상이다 — 진짜 불이 나기 전에 짧게 경보를 울려 아무도 안 읽은 안내문을 몸으로 알게 하는 것.

brownout 실행 규칙 5 — 예·낮·짧·끄·빼

예 — 예고한다
기습이 아니다. "몇 월 며칠 몇 시부터 5분간 v1이 410을 반환합니다"를 미리 공지한다. 목적은 놀래키는 것이 아니라 연락 경로를 여는 것.
낮 — 업무 시간에
새벽에 하면 아무도 못 보고 지나간다. 상대 담당자가 깨어 있는 시간이어야 문의가 들어온다.
짧 — 짧게, 점점 길게
4주 전 5분 → 3일 전 1시간처럼 강도를 올린다.
끄 — 중단 스위치
예상보다 큰 영향이 나오면 즉시 되돌릴 수 있어야 한다. 설정 값 하나로 끄고 켜지도록 만든다.
빼 — 금전 경로는 제외
결제·정산처럼 실패가 곧 금전 손실인 경로는 제외하거나 별도 협의를 거친다. brownout은 압박 수단이지 사고 유발 장치가 아니다.
한 줄 요약
"예고된 · 낮 시간의 · 짧은 · 즉시 끌 수 있는 · 안전한 경로에서의" 리허설.

11. 시니어의 결론 — 최고의 버저닝은 버전을 안 올리는 것이다

9절부터 10절까지가 전부 버전 하나를 없애는 데 드는 비용이었다는 점을 다시 보자. 6개월의 타임라인, 계측 인프라, 개별 연락, brownout 리허설, 그동안의 이중 유지보수. 이 비용을 안 내는 유일한 방법은 애초에 버전을 안 올리는 것이다.

그래서 실제 실력은 "파괴적 변경을 피하는 설계"에서 드러난다 ① 응답 필드를 삭제하는 대신 새 필드를 병행 제공하고, 구 필드는 사용량이 0으로 수렴한 뒤에 뺀다 — 3절의 비대칭을 이용하는 것이다(추가는 공짜고 삭제만 비싸다).
② 클라이언트에게 tolerant reader 규약을 문서로 명시한다. "모르는 필드는 무시하라"가 계약에 있어야 필드 추가가 진짜로 안전해진다.
③ 버전 인상은 정말 계약을 갈아엎어야 하는 마지막 수단으로 아껴둔다.
before 필드 하나 고치려고 v2를 낸다
// 요구사항: discountAmount(원 단위 정수) 를
//           discount(금액 + 통화) 객체로 바꾸고 싶다.

// v1
record OrderV1(Long id, Integer discountAmount) {}

// v2 — 필드를 "교체"했다
record OrderV2(Long id, Money discount) {}

// 대가:
//  · /v2/orders 전체 표면적 복제 (코드·문서·테스트 두 벌)
//  · 6개월짜리 v1 폐기 타임라인 개시
//  · 계측 인프라 · 개별 연락 · brownout 리허설
// 필드 하나 때문에 이 값을 다 치른다.
after 병행 제공 → 사용량 0 수렴 후 제거
// 같은 버전 안에서, 추가만으로 진화시킨다.
record OrderV1(
        Long id,
        Integer discountAmount,   deprecated · 값은 계속 채운다
        Money discount             새 필드 · 신규 소비자는 이걸 읽는다
) {}

// · 기존 클라이언트: 모르는 필드 discount 를 무시 → 무사
// · 신규 클라이언트: discount 를 읽는다
// · 문서에 discountAmount 를 deprecated 로 표시
// · discountAmount 를 실제로 읽는 소비자가 0 이 될 때까지 기다렸다가
//   그때 비로소 제거한다 (그때는 폐기 절차가 훨씬 짧아진다)
//
// 버전을 올리지 않았으므로 9~10절의 비용이 통째로 발생하지 않는다.
단, 병행 제공도 공짜는 아니다 두 필드를 동시에 채우는 동안 "둘이 어긋나면 어느 쪽이 진실인가"라는 문제가 생기고, 응답 크기와 코드 복잡도가 늘어난다. 그래서 이 방식은 무기한 유지가 아니라 "구 필드 사용량이 0으로 수렴할 때까지의 한시적 상태"여야 하고, 언제 걷을지를 처음부터 정해 두어야 한다. (필드 단위의 expand → migrate → contract 절차는 08-backward-compatible-api-changes.md)

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

파괴적 변경의 정의 한 문장?
기존 클라이언트가 코드를 한 줄도 안 고치고 새 서버와 통신했을 때 깨지는 변경. 깨지는 대상이 내 서버가 아니라 남의 클라이언트.
추가는 안전, 삭제는 위험의 근거?
근거는 서버가 아니라 소비자 쪽 파서 — 모르는 필드는 버릴 수 있지만, 없는 필드는 만들어 낼 수 없다.
파괴적 변경 6종?
필드 3(삭제·이름 변경·타입 변경) + 계약 3(필수 파라미터 추가·URL 구조 변경·에러 포맷 변경).
삭제 시 언어별로 어떻게 죽나?
Java 참조 타입 null → 언박싱에서 NPE, Java 기본 타입 0 → 조용한 계산 오류(더 나쁨), Kotlin non-null·Swift 비옵셔널 역직렬화 자체 실패.
URI 방식 장점 3과 공통 뿌리?
가·라·캐(가시성·라우팅·캐시). 뿌리는 하나 — URL은 우리 앱 바깥 장비들도 이미 읽고 있는 값이다.
캐시의 기본 키는?
요청 메서드 + URL. 그래서 URI 방식은 설정 없이 버전이 갈리고, 헤더 방식은 Vary가 필수가 된다.
Vary가 하는 일 / 빠뜨리면?
캐시에게 "이 헤더 값도 캐시 키에 포함하라"고 알리는 응답 헤더. 빠뜨리면 v1 사본이 v2 요청자에게 나가 파싱 실패하고, 오리진에는 로그조차 안 남는다.
방식 선택 기준 한 줄?
소비자를 통제할 수 없을수록 URI 방식으로 기운다 — 통제 불가 = 폐기 어려움 = 계측이 반드시 필요, 그 계측을 URI가 공짜로 준다.
폐기 6단계?
공·계·고·깨·끊·지 — 공개(+Deprecation) → 계측 → Sunset 고지 → brownout → 410 Gone → 코드 제거.
Deprecation vs Sunset?
전자는 "언제부로 권장되지 않게 됐는가"(RFC 9745, @유닉스초), 후자는 "언제 응답이 멈추는가"(RFC 8594, HTTP 날짜). Sunset은 항상 Deprecation보다 뒤.
404가 아니라 410인 이유?
404는 "경로를 잘못 썼는지 없어진 건지 구분 불가". 410 Gone은 "의도적으로 없앴고 다시 안 돌아온다" — 받는 쪽이 즉시 원인을 안다.
brownout 정의와 규칙 5?
종료 전 짧게 일부러 끊어 남은 소비자를 "장애"로 깨우는 기법. 예·낮·짧·끄·빼(예고·업무시간·짧게 점점 길게·중단 스위치·금전 경로 제외).

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

필드 추가는 왜 안전하고, 삭제는 왜 위험한가요? 필수힌트: "클라이언트가 안 깨지니까"에서 멈추지 말고, 파서의 동작으로 근거를 대고 언어별로 갈라 보여준다

소비자 관점에서 보면 된다. 기존 클라이언트는 자기가 아는 필드만 읽으므로 모르는 필드가 추가돼도 무시하면 그만이다. 실제로 Jackson 같은 역직렬화기는 매핑할 자리가 없는 필드를 그냥 버린다.

단서를 붙이면 한 칸 더 간다 — 이 관대함은 클라이언트가 "모르는 필드가 오면 실패"하는 엄격 파싱을 하지 않는다는 규약 위에서만 성립한다. Jackson 자체의 기본값은 예외를 던지는 쪽(FAIL_ON_UNKNOWN_PROPERTIES)이고, Spring Boot가 그 옵션을 꺼 주기 때문에 무시가 기본처럼 보이는 것이다. 그래서 API 문서에 "모르는 필드는 무시하라"(tolerant reader)를 명시해 두는 것까지가 계약이다.

반대로 삭제·이름 변경은 그 필드를 읽던 코드가 즉시 깨진다 — 없는 값은 무시할 수 없기 때문이다.

Java 참조 타입
null이 들어오고 언박싱하는 줄에서 NPE
Java 기본 타입
0이 들어가 조용히 계산이 틀어진다 — 예외가 안 나서 가장 늦게 발견된다

핵심 한 문장부터. "내릴 수 있는 근거(사전 계약)와 수단(계측)을 v2를 낼 때 함께 준비한다"는 것이다. 이것이 없으면 v1 종료는 기술 문제가 아니라 매번 새로 해야 하는 협상이 되고, 협상은 대체로 미뤄진다.

절차는 셋으로 요약된다. ① 버전별 사용량을 계측해 잔여 호출자를 식별하고, ② 문서 공지 + Deprecation/Sunset 헤더로 기한을 알리고, ③ 사전에 계약된 지원 기간이 지나면 단계적으로 내린다(brownout → 410 Gone → 완전 제거).

한 단계 더 들어가면 원칙 하나를 덧붙일 수 있다 — 되돌리기 비용이 다른 작업을 분리한다. "410으로 전환"은 설정으로 즉시 되돌아가지만 "코드 제거"는 배포가 필요하므로, 둘을 같은 날 하지 않고 몇 달 간격을 둔다.

기간의 감을 물으면 공개 API의 실제 사례를 대면 된다. GitHub은 새 REST API 버전을 낸 뒤 이전 버전을 최소 24개월 더 지원한다고 문서에 못 박아 두고, 지원이 끝난 버전을 지정한 요청에는 400을 돌려준다. 사내 서비스라면 이보다 훨씬 짧아도 되지만, 기간을 사전에 문서화한다는 성질은 같다.

버전은 API 전체에 붙이나요, 리소스(엔드포인트)별로 붙이나요?힌트: 둘의 장단점을 말한 뒤, 그 둘보다 밑에 있는 기준 하나를 꺼내면 답이 완성된다

전역 버전(/v1/... 전체): 소비자가 이해하기 쉽고 문서가 단순하다. 대신 리소스 하나 바뀌어도 전체가 v2로 복제되는 비용.
리소스별 버전(/orders만 v2): 변경 범위가 작지만, "이 API는 지금 어떤 버전 조합이 유효한가"를 소비자가 추적해야 해서 혼란이 크다.
외부 공개 API는 전역 버전이 무난하고, 내부 API는 리소스별로 느슨하게 가져가기도 한다 — 소비자가 누구냐에 따라 갈리는 결정이다.

여기서 한 겹 더 들어가면 좋다. 실제로 큰 서비스들이 지키는 것은 "전역이냐 리소스별이냐"가 아니라 더 밑에 있는 기준 하나다.

소비자가 "지금 내가 어느 계약 위에 있는가"를 언제나 확실히 알 수 있어야 한다

이 기준으로 보면 서로 달라 보이는 사례들이 한 줄로 정리된다.

Kubernetes가 특히 좋은 반례다. 리소스 그룹마다 버전이 제각각인데도 혼란이 크지 않은 이유는, 버전이 경로에 항상 명시돼 있어 어느 요청을 보든 자기 버전이 눈에 보이기 때문이다. 반대로 리소스별 버전이 위험해지는 것은 "어떤 엔드포인트는 버전이 붙고 어떤 건 안 붙어서, 소비자가 조합표를 외워야 하는" 형태로 갈 때다.

그러니 답의 결론은 이렇게 맺는다 — "리소스별 버전을 쓰더라도, 버전이 요청마다 명시적으로 드러나 소비자가 추측하지 않아도 되는 형태여야 한다."

URI 버저닝이 REST 원칙 위반이라는 비판에 어떻게 답하시겠어요? 시니어 변별힌트: 비판을 먼저 정확히 인정하고, 그 다음 트레이드오프의 근거를 "한 가지 성질"로 압축한다

먼저 비판을 정확히 인정한다. 요지는 "URI는 자원의 식별자인데 버전이 끼면 같은 자원이 여러 식별자를 갖는다"는 것이고, 이론적으로 타당하다. 6절에서 본 자원/표현 구분으로 말하면 v1 응답과 v2 응답은 같은 자원의 다른 표현일 뿐인데, 표현의 차이를 자원의 식별자에 새겨 넣은 셈이다.

하지만 설계는 원칙 준수가 아니라 트레이드오프 선택이다 — 나는 운영 가시성(로그로 버전 사용량 집계), 폐기 운영 가능성, 소비자 접근성이 URI 순수성보다 실무 가치가 크다고 판단해 URI 방식을 고른다.

그 판단의 근거를 한 가지 성질로 압축할 수 있으면 좋다.

URI 방식이 주는 것은 전부 "우리 애플리케이션 바깥의 장비도 버전을 읽을 수 있다"는 한 가지 성질에서 나온다

액세스 로그가 그냥 남기는 URL이 곧 사용량 계측 데이터가 되고, 게이트웨이가 경로만 보고 버전별 풀을 분리하며, 캐시가 Vary 설정 없이도 버전을 섞지 않는다. 9절의 폐기 운영이 계측 위에 서 있는 이상 이 성질은 이론적 순수성과 맞바꿀 만하다.

대신 그 비용(자원 정체성 분열)을 알고 고르는 것과 모르고 고르는 것은 다르며, 내부 서비스 간 API처럼 소비자를 통제할 수 있고 게이트웨이가 헤더 라우팅을 잘 지원하는 환경이라면 헤더 방식도 유효한 선택지로 검토한다.

버저닝 없이 시작한 API에 나중에 버전을 붙일 수 있나요? 가산점힌트: "가능하지만 비용이 크다" 다음에, 진짜 문제가 코드가 아니라는 것을 말해야 한다

붙일 수 있지만 비용이 크다 — 무버전 URI(/orders) 자체가 이미 계약이라, /v2/orders를 내는 순간 기존 경로를 "암묵적 v1"으로 영구 유지하거나 마이그레이션을 강제해야 한다.

여기서 진짜 문제는 코드가 아니라 뒤엉킨 이름이다. /orders가 사실상 v1인데 이름에는 그 사실이 없으므로, 신규 소비자는 /orders와 /v2/orders 중 무엇이 최신인지 문서를 봐야만 알 수 있고, 나중에 v3이 나오면 /orders가 어느 세대인지 아무도 기억하지 못한다.

공개 시점에 버전 자리(/v1)를 미리 잡아두는 것이 정석이다

"지금은 v2 계획이 없어도 v1 prefix를 붙인다"는 결정 자체가 미래 비용을 앞당겨 사고하는 습관의 예시다. 비용은 경로에 세 글자를 더하는 것뿐인데, 안 붙였을 때 나중에 치르는 값은 위와 같다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

v1과 v2 코드를 한 코드베이스에서 어떻게 유지하나요? 컨트롤러를 통째로 복사해야 하나요?힌트: "버전은 어느 계층의 문제인가"를 먼저 정하면 답이 나온다

버전은 표현 계층의 문제다. 그래서 컨트롤러와 DTO만 버전별로 두고 도메인·서비스는 하나로 공유하는 것이 기본형이다. v1 컨트롤러는 v2 서비스의 결과를 v1 DTO 모양으로 되돌려 주는 얇은 어댑터가 된다.

이 구조가 유지되는 동안은 "두 벌의 실체"가 얇은 변환 계층뿐이라, 9절에서 말한 "버그를 두 번 고친다"는 비용이 거의 발생하지 않는다. 비즈니스 로직은 한 곳에만 있기 때문이다.

어댑터로 안 되는 순간이 있다 — v1과 v2의 시맨틱(도메인 규칙 자체)이 다른 경우다. 예를 들어 v1은 "부분 취소를 허용하지 않는다"는 규칙 위에 있고 v2는 허용한다면, 이건 표현 변환으로 흡수되지 않는다. 그때가 메이저 버전 인상이 진짜로 정당화되는 지점이다.

위험 신호 하나를 덧붙이면 좋다 — v1 어댑터에 도메인 규칙 수준의 if 분기가 쌓이기 시작하면, 그 v1은 이미 어댑터가 아니라 별개의 시스템이 되어 가는 중이다. 그 상태를 방치하는 것이 "두 벌 유지"의 실제 모습이므로, 그 시점에 v1 종료를 앞당길지 결정해야 한다.

무버전 /orders를 /v1/orders로 리다이렉트하면 깔끔하게 정리되지 않나요? 함정힌트: 리다이렉트가 옮기는 것은 무엇이고, 옮기지 못하는 것은 무엇인가

리다이렉트가 옮기는 것은 "이름"이지 "계약"이 아니다. /orders를 /v1/orders로 보내도, /orders를 호출하던 클라이언트는 여전히 v1 계약을 받게 되고 그 계약은 영구히 유지해야 한다. 앞 질문에서 말한 "암묵적 v1이 영원히 남는다"는 문제가 그대로다. 정리된 것은 우리 눈에 보이는 경로 이름뿐이다.

게다가 리다이렉트 자체의 비용이 붙는다.

  • 왕복이 한 번 더 생긴다 — 모든 호출에 레이턴시가 추가되고, 액세스 로그·캐시에 요청이 두 번 찍혀 계측이 지저분해진다.
  • 메서드 보존 문제 — 301/302는 역사적으로 POST를 GET으로 바꿔 버리는 구현이 흔했다. 메서드와 본문을 보존하려면 307/308을 써야 한다.
  • 클라이언트가 따라간다는 보장이 없다 — 모바일 SDK·배치 HTTP 클라이언트는 리다이렉트 자동 추적이 꺼져 있는 경우가 흔하다. 따라가지 않는 소비자에게는 그냥 장애다.
리다이렉트는 URL을 옮길 때 쓰는 도구지, 계약을 바꿀 때 쓰는 도구가 아니다

현실적인 처방은 "/orders를 v1의 영구 별칭으로 인정하고 문서에 그렇게 못 박는 것"이다. 없앨 수 없다면 최소한 모호하지 않게 만드는 것이 다음으로 좋은 선택이다.

왜 v1, v2 같은 정수 대신 날짜 버전을 쓰기도 하나요? 시니어 변별힌트: 버전 인상의 "단위 크기"가 무엇을 결정하는지 생각한다

정수 버전과 날짜 버전은 "한 번에 바꾸는 단위 크기"가 다르다.

정수 버전 /v1, /v2

  • 단위가 계약 전체다 — 올릴 때마다 표면적이 복제된다.
  • 그래서 자주 못 올린다. 작은 파괴적 변경은 계속 미뤄지고, 언젠가 한꺼번에 터진다.
  • 대신 소비자가 이해하기 쉽다 — "우리는 v1을 씁니다" 한 마디로 끝난다.

날짜 버전 2026-09-01

  • 단위가 작은 변경 하나다 — 파괴적 변경을 필요할 때마다 낼 수 있다.
  • 소비자는 특정 날짜에 고정(pinning)되고, 명시적으로 올리기 전에는 절대 바뀌지 않는다.
  • 대신 서버가 유지해야 하는 계약 수가 계속 늘어난다.

그래서 날짜 버전은 구조를 요구한다. 계약을 통째로 여러 벌 두는 것이 아니라, 코어는 최신 하나만 유지하고 날짜 사이의 차이를 요청/응답 변환 계층으로 흡수하는 형태여야 유지가 된다. 이 구조를 못 갖추면 날짜 버전은 정수 버전보다 훨씬 빨리 무너진다.

판단 기준: 파괴적 변경 빈도가 낮고 소비자 온보딩 편의가 중요한 조직은 URI + 정수 버전, 변경이 잦고 소비자를 정밀하게 고정해야 하는 플랫폼성 API는 날짜 버전이 어울린다. 앞 질문의 표에서 본 Stripe·GitHub이 후자의 사례다.

v1을 410으로 내렸는데 대형 파트너사 하나만 아직 못 옮겼습니다. 어떻게 하나요?힌트: "되돌린다/안 되돌린다"의 이분법이 아니다. 범위를 좁히는 선택지가 있다

먼저, 되돌릴 수 있는 상태인지가 이미 설계로 결정돼 있다. 9절대로 라우팅은 살려둔 채 응답만 410으로 바꿨다면 설정 하나로 즉시 복구된다. 코드를 이미 지웠다면 배포가 필요하다 — 두 작업을 같은 날 하지 않는 이유가 바로 이 순간을 위해서다.

그다음은 전체 복구가 아니라 범위를 좁히는 것이다. 해당 파트너의 API 키/클라이언트 식별자에 한해서만 v1을 허용하는 allowlist를 둔다. 다른 소비자에게는 종료가 유지되므로 "종료를 물린 것"이 되지 않고, 이미 v2로 옮긴 소비자들의 노력도 헛되지 않는다.

예외에는 반드시 기한과 조건을 붙여 문서화한다 — 새 종료일, 그 기간 동안의 지원 범위(예: 장애 시 우선순위를 부여하지 않음). 기한 없는 예외는 v1 종료를 영구히 미루는 장치가 된다.

마지막으로 재발 방지를 말하면 좋다. 이 사태의 원인은 대개 "계측은 있었지만 상위 호출자 개별 연락에서 그 파트너를 못 짚었다"거나 "brownout 시간대가 그 파트너의 배치 시간과 안 겹쳤다"이다. 다음 폐기 때는 brownout을 서로 다른 시간대에 나눠 실행해 배치성 소비자까지 걸리게 만드는 식으로 보완한다.

내부 마이크로서비스 간 API도 버저닝해야 하나요? 우리가 양쪽을 다 배포하는데요.힌트: "같이 배포한다"가 내부에서도 안 성립하는 순간이 있다

전체 버전 인상은 대개 불필요하지만, 하위 호환 규칙은 그대로 필요하다. 이유는 "같이 배포한다"가 내부에서도 완전히는 성립하지 않기 때문이다.

  • 롤링 배포 중에는 구·신 인스턴스가 동시에 떠 있다. 그 몇 분 동안 새 응답을 구 인스턴스가 받거나 그 반대가 된다.
  • 서로 다른 팀의 배포 순서를 완전히 통제할 수 없다. 배포 순서를 조율해야만 안 깨지는 변경은 언젠가 순서가 틀리는 날 깨진다.
  • 롤백도 마찬가지다 — 새 버전으로 되돌아갈 수 있으려면 구 버전이 새 데이터를 견뎌야 한다.

그래서 내부에서도 "추가만 하고, 삭제는 병행 제공 → 사용량 0 확인 → 제거의 2단계로"라는 규칙은 동일하게 적용되고, 대부분의 변경은 전체 버전 인상 없이 필드 단위 병행 제공으로 해결된다.

다만 착각 하나를 짚어야 한다 — "소비자를 통제할 수 있다"는 말은 "소비자 목록을 알고 있다"는 뜻이지, 자동으로 알게 된다는 뜻이 아니다. 내부 API도 "누가 이 엔드포인트를 부르는가"를 계측해 두지 않으면 정리할 때 똑같이 막힌다. 차이는 폐기 기간이 6개월이 아니라 2주여도 된다는 것뿐이다.

한 줄 요약
버저닝은 "기존 클라이언트 코드를 고치지 않으면 깨지는 변경"인 파괴적 변경으로부터 소비자를 지키는 장치이고(추가가 안전한 이유는 파서가 모르는 필드를 버리기 때문, 삭제가 위험한 이유는 없는 값을 만들어 낼 수 없기 때문), URI 방식은 URL이 곧 캐시 키·라우팅 기준·로그 필드라서 우리 앱 바깥의 장비까지 버전을 읽을 수 있어 폐기 운영에 강하고, 헤더 방식은 콘텐츠 협상을 재사용해 URI 순수성을 지키는 대신 Vary 관리와 가시성 부재라는 보이지 않는 비용을 낸다 — 그리고 진짜 실력은 하위 호환 변경만으로 API를 진화시켜 버전을 올릴 일 자체를 줄이고, 버전을 낼 때는 계측 · Deprecation/Sunset 고지 · brownout · 410 종료로 이어지는 폐기 타임라인까지 함께 설계하는 데 있다.
