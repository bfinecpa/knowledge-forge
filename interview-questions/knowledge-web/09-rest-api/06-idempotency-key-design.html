멱등성 키 설계 — 결제 API의 중복 요청 차단
네트워크는 반드시 실패하고, 클라이언트는 반드시 재시도한다

면접 질문: "결제 API에서 중복 요청(더블 클릭, 네트워크 재시도)을 어떻게 방지하나요? (멱등성 키 설계)"

핵심 관전 포인트 — 결제 API의 중복 요청은 "클라이언트가 조심하면 되는 문제"가 아니라 프로토콜의 본질적 한계다 — 타임아웃이 나면 클라이언트는 서버가 결제를 처리했는지 안 했는지 알 방법이 없고, 그래서 재시도할 수밖에 없다. 결국 서버가 API 계약 수준에서 중복을 흡수해야 한다. 클라이언트가 "결제 시도 1건"마다 고유한 멱등성 키(Idempotency-Key 헤더)를 만들어 보내고, 서버는 그 키를 유니크 제약이 걸린 행으로 먼저 꽂아 선점한 뒤(PostgreSQL의 INSERT ... ON CONFLICT DO NOTHING이 몇 행을 넣었는지로 승패를 가른다) 이긴 요청만 실제 처리하며, 같은 키의 재요청에는 저장해 둔 최초 응답을 상태 코드까지 통째로 재생(replay)한다. 이 설계의 심장은 "있나 검사하고 없으면 처리"가 아니라 "먼저 선점하고 이긴 쪽만 처리"라는 순서다 — 검사와 처리 사이의 간극이 곧 경쟁 조건이고, 그 간극을 없애는 방법이 원자성을 DB의 유니크 인덱스에 위임하는 것이기 때문이다. 여기에 같은 키로 다른 내용이 오는 클라이언트 버그를 잡는 요청 지문(fingerprint), 처리 중 크래시된 레코드를 회수하는 리스(lease), 그리고 "멱등성 키는 같은 시도의 재전송만 막고, 새 키로 온 새 시도는 도메인 유니크 제약이 막는다"는 계층 구분까지 얹어야 이중 결제가 실제로 막힌다.
  • 1
    중복은 막을 수 없는 전제다 — 타임아웃이 났을 때 "요청이 안 닿음 / 처리 중 / 이미 처리됨" 세 가지가 클라이언트 눈에 완전히 똑같이 보인다. 재시도 안 하면 "결제했는데 주문이 없는" 고객, 재시도하면 "한 번 샀는데 두 번 결제된" 고객이 생긴다 — 어느 쪽이든 사고이므로 출구는 재시도해도 안전한 API를 서버가 제공하는 것뿐이다.
  • 2
    핵심은 "검사 후 처리"가 아니라 "선점 후 처리"다 — exists()로 검사하고 없으면 처리하는 코드는 두 요청이 나란히 "없음"을 보는 check-then-act 간극에 뚫린다. INSERT ... ON CONFLICT DO NOTHING으로 키를 먼저 꽂고 삽입된 행 수(1/0)로 승패를 가른다 — 원자성의 출처는 내 if문이 아니라 DB의 유니크 인덱스다.
  • 3
    재요청에는 최초 응답을 상태 코드까지 재생한다 — "이미 처리됨" 에러를 주면 그 순간 멱등성이 깨진다. 그리고 지문·리스·계층 셋을 얹어야 완성이다: 같은 키·다른 내용은 422로 거절, 처리 중 크래시는 리스 만료 후 재선점 + PG 거래 조회로 회수, 새 키로 온 중복은 도메인 유니크 제약이 막는다.

0. 질문 + 출제 의도

질문: "결제 API에서 중복 요청(더블 클릭, 네트워크 재시도)을 어떻게 방지하나요? (멱등성 키 설계)"

출제 의도: 네트워크는 반드시 실패하고 클라이언트는 반드시 재시도한다는 전제에서, 중복 결제를 API 계약 수준에서 차단하는 설계를 할 수 있는지 본다. 이 개념 없이 결제 API를 만든 팀은 반드시 이중 결제 CS를 받는다 — 결제 포지션의 필수 검증이다.

이 페이지가 겨냥하는 약점 세 가지 ① "버튼 비활성화하면 되지 않나"에서 출발하는 것 → 1절에서 타임아웃 시 세 가지 세계가 구분 불가능하다는 것을 도식으로 보여주고, 클라이언트 대책이 원리적으로 왜 부족한지 못 박는다.
② 키를 저장했다는 사실만 말하고 "언제 저장하는가"를 못 말하는 것 → 4·5절에서 check-then-act 타임라인 vs 선점 타임라인을 나란히 펴서, 승부가 SQL 한 문장의 원자성에서 갈린다는 것을 보여준다.
③ 정상 경로만 그리는 것 → 9·11절에서 처리 도중 크래시(리스 회수 + PG 거래 조회)와 새 키로 온 중복(도메인 불변식)이라는 두 개의 구멍을 채운다.
이 문서의 자리 — 이미 다룬 것과 여기서 파고드는 것 HTTP 메서드별 멱등성의 정의와 멱등성 키 5원칙(선·중·재·범·저)의 개요는 08-network-http/04-http-method-idempotency-and-safety.md가, 메시지 컨슈머 쪽의 멱등 처리는 06-messaging/04-idempotent-consumer-implementation.md가 다룬다. 이 페이지는 HTTP API에서 멱등성 키를 실제로 설계할 때의 디테일에 집중한다 — 키 발급 주체와 시점, 저장 스키마의 각 칼럼이 왜 있는가, 동시 도착의 원자성, 리스와 TTL의 값 산정, 응답 재생의 규칙.

1. 중복은 왜 "막을 수 없는" 전제인가

이 질문에 대한 첫 반응은 대개 "버튼을 비활성화하면 되지 않나"다. 그 대책이 어디까지 유효한지는 중복이 생기는 경로를 늘어놓아 보면 바로 드러난다.

① 더블 클릭
버튼 비활성화로 줄일 수 있다. 가장 쉬운 경우다. 다만 두 번째 탭, 새로고침, 앱 강제 종료 후 재실행은 못 막는다 — 화면 하나는 다른 화면의 존재를 모르기 때문이다.
② 네트워크 재시도
여기가 진짜 문제다. 이 절의 나머지가 전부 이 이야기다. 클라이언트 코드로는 원리적으로 해결되지 않는다.
③ 중간 계층의 자동 재시도
HTTP 라이브러리·API 게이트웨이·리버스 프록시가 설정에 따라 알아서 재시도한다. 애플리케이션 코드는 한 번만 보냈는데 서버에는 두 번 도착한다.
④ 사용자 행동
"결제가 안 된 것 같은데?" 하고 새로고침 후 다시 결제. 사용자 입장에서는 합리적인 행동이라 교육으로 막을 수 없다.
③이 결정적인 이유 ①②④는 그래도 "우리 클라이언트 코드"의 이야기지만, ③은 우리가 짜지 않은 코드가 만드는 중복이다. 인프라 설정 한 줄이 바뀌면 중복이 생긴다는 뜻이고, 그래서 중복 방지의 책임은 클라이언트가 아니라 서버(API 계약)에 있어야 한다.

1-1. 타임아웃이 났을 때 클라이언트가 실제로 아는 것

결제 요청을 보냈는데 응답이 오기 전에 읽기 타임아웃이 났다. 이때 벌어졌을 수 있는 일은 셋이고, 셋 다 클라이언트 눈에는 완전히 똑같이 보인다.

그래서 클라이언트의 선택지는 둘뿐이고, 둘 다 사고다

재시도하지 않는다
①②였다면 "결제했다고 생각했는데 주문이 없는" 고객이 생긴다.
재시도한다
③이었다면 "한 번 샀는데 두 번 결제된" 고객이 생긴다.
"클라이언트가 재시도하지 않게 하자"는 해법이 될 수 없다 — 유일한 출구는 재시도해도 안전한 API를 서버가 제공하는 것이다

2. 멱등성 키 = 접수번호가 미리 적힌 신청서

멱등성(idempotency)
같은 요청을 1번 보내든 N번 보내든 결과(서버의 상태 + 클라이언트가 받는 응답)가 같은 성질. "멱등"은 거듭할 멱(冪)에 같을 등(等) — 몇 번을 거듭 적용해도 결과가 더 이상 변하지 않는다는 뜻이다. abs(-3)도 3이고 abs(abs(-3))도 3인 것과 같다.
그런데 결제 생성은 본질적으로 POST다
HTTP 명세는 GET·PUT·DELETE를 멱등한 메서드로 정의하지만 POST는 멱등하지 않다 — 부를 때마다 새 자원이 생기는 것이 POST의 의미이기 때문이다. 그래서 멱등성을 인위적으로 부여하는 장치가 필요하고, 그것이 멱등성 키다.

비유 — 접수번호가 미리 적힌 신청서

같은 접수번호의 신청서가 두 번 들어오면 창구 직원은 두 번 처리하지 않고 "이미 접수된 건입니다"라며 첫 번째 처리 결과를 보여준다. 접수번호가 없으면 직원은 두 신청서가 같은 건인지("아까 그분이 다시 내셨네") 다른 건인지("같은 상품을 하나 더 사시려나") 구분할 방법이 없다.

판정의 근거를 클라이언트가 미리 심어주는 것이 이 장치의 본질이다

메서드별 멱등성의 정확한 정의(왜 DELETE는 응답이 달라져도 멱등인가 등)는 08-network-http/04-http-method-idempotency-and-safety.md에서 다룬다. 이 페이지는 그 장치를 실제로 설계할 때 결정해야 하는 것들로 바로 들어간다.

3. 누가·언제 키를 만드는가 — 시도 1건에 키 1개

가장 많이 틀리는 지점이다. 키의 생명주기는 HTTP 요청 단위가 아니라 비즈니스 작업(결제 시도) 단위다.

키 발급 3규칙 — "시도 1건에 키 1개"

누가
클라이언트가 만든다. 응답을 못 받는 상황에서도 키를 이미 알고 있어야 하는 쪽이 만들어야 하기 때문 (12절 첫 꼬리질문).
언제
사용자가 결제 버튼을 누르는 순간 UUID를 하나 생성한다. 요청을 보낼 때가 아니라 시도가 시작될 때다.
언제 바꾸나
재전송(타임아웃 재시도)이면 유지, 사용자가 의도적으로 다시 시도하면 새 키.

전달은 관례적으로 Idempotency-Key HTTP 헤더를 쓴다. 주요 결제사 API들이 쓰는 이름이고, IETF에서 표준 헤더로 만들기 위한 논의가 진행돼 온 이름이기도 하다 — 아직 RFC로 확정된 헤더는 아니므로, 우리 API 문서에 헤더 이름과 의미를 직접 적어두는 것이 여전히 필요하다.

요청 클라이언트가 보내는 것
POST /payments HTTP/1.1
Idempotency-Key: 8f3c1e2a-4b7d-4a1e-9c22-a7f6b7d4e001   시도 1건에 하나
Content-Type: application/json

{ "orderId": "ORD-1001", "amount": 50000, "method": "CARD" }

4. check-then-act 간극 — 순진한 구현이 뚫리는 이유

키를 받았으니 이제 서버가 "이미 처리한 키인가"를 판단해야 한다. 가장 자연스러운 코드는 이렇게 생겼고, 이것이 틀렸다는 것이 이 문서의 핵심이다.

Before 검사하고 나서 행동하기 — 동시 요청에 뚫린다
@PostMapping("/payments")
public PaymentResponse pay(@RequestHeader("Idempotency-Key") String key,
                           @RequestBody PaymentRequest req) {
    if (idempotencyRepository.existsByKey(key)) {      // ① 검사여기서 알아낸 사실이
        return idempotencyRepository.findByKey(key).response();
    }
    PaymentResponse res = paymentService.process(req); // ② 처리 (PG 승인)
    idempotencyRepository.save(key, res);              // ③ 기록③까지 참으로 남아있지 않다
    return res;
}
경쟁 조건(race condition)
두 개 이상의 실행 흐름이 같은 데이터를 건드릴 때 어느 쪽이 먼저 도착하느냐에 따라 결과가 달라지는 상황. 이름 그대로 "경주" 상황이라 붙은 이름이다.
check-then-act 간극
검사(check)와 행동(act) 사이의 시간. 그 사이에 다른 요청이 끼어들면 검사 결과가 낡은 정보가 된다. 위 코드에서는 ①~③ 사이 전체가 간극이다.

더블 클릭으로 두 요청이 0.2초 간격으로 도착하는 장면과, 5절에서 만들 개선안을 같은 시간축에 나란히 펴면 승부가 어디서 갈리는지 보인다.

흔한 오답 — "트랜잭션으로 묶으면 되지 않나요" 답이 아니다. 일반적인 격리 수준(PostgreSQL 기본값인 Read Committed)에서 SELECT는 다른 트랜잭션이 아직 커밋하지 않은 행을 못 볼 뿐이고, "앞으로 생길 행"을 예약해 주지는 않는다. 존재하지 않는 행에는 잠글 대상 자체가 없기 때문이다. 트랜잭션은 이미 있는 행의 동시 수정은 막아주지만, "둘 다 없다고 봤다"는 이 상황은 막지 못한다.

5. 선점 후 처리 — 원자성을 유니크 인덱스에 위임한다

이 문서에서 딱 하나만 외운다면

"있나 물어보고 없으면 쓴다"가 아니라 "일단 써 보고, 써졌으면 내가 처음이다"

애플리케이션의 if문은 두 걸음이지만, 인덱스에 항목을 꽂는 일은 DB 안에서 나눌 수 없는 한 걸음이다. 유니크 인덱스가 걸린 컬럼에 두 세션이 같은 값을 동시에 INSERT하면 DB 엔진이 인덱스 항목 수준에서 한쪽을 대기시키고, 앞선 트랜잭션이 커밋되면 뒤에 온 쪽을 충돌로 판정한다. "둘 중 누가 이겼는가"의 판정을 애플리케이션이 아니라 DB 엔진에 맡기는 것이 이 설계의 전부다.

5-1. 테이블과 선점 SQL

DDL 멱등성 레코드 테이블 — 복합 기본키가 곧 유니크 제약이고, 그것이 심장이다
CREATE TABLE idempotency_record (
    user_id          bigint       NOT NULL,
    idempotency_key  varchar(64)  NOT NULL,
    fingerprint      char(64)     NOT NULL,  -- 요청 바디의 SHA-256 (16진수 64자) → 8절
    status           varchar(16)  NOT NULL,  -- IN_PROGRESS | COMPLETED
    response_status  int,                    -- 최초 응답의 HTTP 상태 코드 → 7절
    response_body    jsonb,                  -- 최초 응답 바디 원문
    locked_until     timestamptz  NOT NULL,  -- 리스 만료 시각 → 9절
    attempt          int          NOT NULL DEFAULT 0,  -- 재선점 횟수
    created_at       timestamptz  NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, idempotency_key)   -- 이 한 줄이 동시성 문제를 푼다키 스코프는 10절
);

-- TTL 정리 배치가 "오래된 레코드"를 훑는 경로 (10절)
CREATE INDEX idx_idem_created_at ON idempotency_record (created_at);
선점 충돌하면 예외를 던지는 대신 "0행"을 보고하게 한다
-- "몇 행이 삽입됐는가"가 곧 "내가 이겼는가"의 답이 된다.
INSERT INTO idempotency_record
       (user_id, idempotency_key, fingerprint, status, locked_until, created_at)
VALUES (:userId, :key, :fingerprint, 'IN_PROGRESS', now() + interval '30 seconds', now())
ON CONFLICT (user_id, idempotency_key) DO NOTHING;반환된 행 수 1 = 승, 0 = 패
왜 try { insert } catch (DuplicateKeyException)가 아니라 DO NOTHING인가 시니어 변별 PostgreSQL에서는 유니크 위반이 예외로 터지는 순간 그 트랜잭션 전체가 중단 상태(aborted)가 되어, 같은 트랜잭션 안에서 뒷 조회를 이어갈 수 없다. 그래서 catch 블록에서 findByKey를 호출하면 "현재 트랜잭션이 중단됨" 오류로 다시 터진다 — 정작 재생할 응답을 꺼내야 하는 그 자리에서. 예외 대신 영향받은 행 수로 승패를 가르는 형태가 훨씬 안전한 이유다.
굳이 예외를 잡아야 한다면 우회로는 둘이다 — 선점만 REQUIRES_NEW로 별도 트랜잭션에 태우거나, SAVEPOINT를 잡고 실패 시 그 지점까지만 롤백하는 것. 어느 쪽이든 ON CONFLICT DO NOTHING보다 복잡하다.

                             @AuthenticationPrincipal Long userId,
                             @RequestBody PaymentRequest req) {

    // ① 선점. 1 = 내가 최초. 0 = 이미 누가 이 키로 자리를 잡았다.

        if (!rec.fingerprint().equals(fingerprint)) {

        if (rec.status() == Status.IN_PROGRESS) {

                    .header("Retry-After", "1").build();           // 409
        }

        // ④ COMPLETED — 저장해 둔 최초 응답을 상태 코드까지 그대로 재생한다.
        return ResponseEntity.status(rec.responseStatus()).body(rec.responseBody());

    return ResponseEntity.ok(res);

이 코드에 @Transactional이 없다는 것이 핵심이다

선점 INSERT는 실제 결제 처리와 같은 트랜잭션에 있으면 안 된다. 같이 묶으면 두 가지가 동시에 망가진다.

① 표식이 안 보인다
선점한 행은 커밋되기 전에는 다른 요청에게 보이지 않는다. IN_PROGRESS 표식의 목적 자체가 "지금 누가 처리 중"임을 다른 요청에게 알리는 것인데, 결제가 끝나 커밋될 때까지 아무도 그 표식을 못 본다.
② 재시도가 붙잡힌다
PostgreSQL에서 뒤에 온 INSERT는 앞선 트랜잭션이 끝날 때까지 인덱스 항목에서 대기한다. 재시도 요청이 즉시 409를 받는 대신 PG 승인이 끝날 때까지 몇 초씩 커넥션을 붙잡고 있게 된다.
선점은 짧은 자기 트랜잭션으로 커밋하고 나서 실제 처리로 넘어간다

7. 재생(replay) — 왜 에러 대신 "같은 응답"인가

재생(replay)의 정의 같은 키로 두 번째 요청이 왔을 때 처리를 다시 하지 않고, 첫 번째 요청 때 만들어 저장해 둔 응답을 그대로 다시 내보내는 것. 녹음을 다시 트는 것과 같다고 해서 재생이라 부른다.

여기서 한 번 멈춰서 물어야 한다. 왜 그냥 "이미 처리된 요청입니다" 에러를 주면 안 되는가? 그게 더 정직해 보이는데.

"이미 처리됨" 에러(409)를 준다면

  • 재시도하는 클라이언트의 목표는 "중복이었다는 사실을 아는 것"이 아니라 "결제 결과를 아는 것"인데, 결제 ID를 못 받는다.
  • 결과를 알아내려고 조회 API를 또 불러야 한다 → 우리는 그 조회 경로를 따로 만들어야 한다.
  • 클라이언트 재시도 코드에 "성공 / 실패" 외에 "중복이니 다른 방법으로 결과를 알아내라"는 세 번째 갈래가 생긴다.
  • 무엇보다 그 순간 멱등성이 깨진다 — 1번 보낸 것과 N번 보낸 것이 구분 가능해지기 때문이다.

저장해 둔 최초 응답을 재생한다면

  • 클라이언트는 재시도했다는 사실조차 알 필요 없이 결제 결과를 받는다.
  • 재시도 코드가 "성공 / 실패" 두 갈래로 유지된다.
  • 별도 조회 경로가 필요 없다.
  • 멱등성의 정의 "1번과 N번을 구분할 수 없다"가 그대로 성립한다.

재생의 두 가지 규칙

① 통째로 저장한다 — 통째란 상태 코드까지 포함한다

바디만 저장하고 상태 코드를 매번 200으로 내보내면, 최초에 402(결제 실패)를 받았던 클라이언트가 재시도에서는 200을 받아 결제가 성공했다고 오해한다.

② 바디는 다시 만들지 말고 원문을 보관한다

나중에 응답 DTO에 필드가 추가되면, 재생 시점에 다시 조립한 바디는 최초 응답과 달라진다. "같은 응답"을 보장하려면 그때 실제로 나간 바이트를 들고 있는 것이 안전하다.

예외 — 재생임을 "헤더로만" 알리는 것은 무해하다 가산점 일부 결제사는 재생된 응답에 전용 헤더를 하나 덧붙인다(예: 재생 여부 표시). 관측과 디버깅에 쓰라는 것이고, 상태 코드와 바디는 건드리지 않으므로 멱등성이 깨지지 않는다. "그럼 재생인지 아닌지 아예 알 수 없나요?"라는 꼬리질문에 이 한 줄을 답하면 좋다.

8. 요청 지문(fingerprint) — 같은 키, 다른 내용을 거절한다

요청 지문은 요청 내용을 하나의 짧은 값으로 압축한 것이다. 보통 요청 바디의 SHA-256 해시를 쓴다. 사람의 지문처럼 "이게 아까 그것과 같은 것인가"를 판별하는 용도라서 지문이라 부른다.

8-1. 왜 필요한가 — 클라이언트는 키를 잘못 재사용한다

세션 단위 키
키를 결제 시도마다가 아니라 세션 단위로 만들어 두고 결제할 때마다 같은 키를 보내는 구현
재시도 래퍼의 객체 재사용
요청 객체를 재사용하면서 헤더는 그대로 두고 바디만 바뀐 경우
상수로 박힌 키
파트너사의 배치 스크립트나 테스트 코드가 키를 상수로 박아둔 경우
지문 검사가 없으면 아무도 에러를 보지 못하는 사고가 난다
1차:  Idempotency-Key: K   바디 {"amount": 50000}
      → 5만 원 승인. paymentId=P-771. 응답을 K에 저장.

2차:  Idempotency-Key: K   바디 {"amount": 30000}   클라이언트 버그로 키 재사용
      → 지문 검사가 없으면: 저장된 P-771(5만 원) 응답을 그대로 재생

클라이언트가 받는 것: "3만 원 결제를 요청했더니 성공 응답이 왔다"
실제로 존재하는 것:   5만 원 결제 하나뿐. 3만 원 결제는 어디에도 없다.
"조용한 사고"라서 더 위험하다 어느 쪽에서도 에러가 나지 않고, 로그도 정상이고, 클라이언트는 3만 원 결제가 끝났다고 믿는다. 불일치가 드러나는 것은 한참 뒤 대사(정산 대조) 단계다. 그래서 지문이 다르면 재생하지 말고 거절한다.

왜 400이 아니라 422인가

요청 문법 자체는 멀쩡하다 — JSON도 유효하고 필드도 다 맞다. 그래서 400(Bad Request)이 아니고, "의미상 처리할 수 없다"는 뜻의 422 Unprocessable Content가 맞다. Idempotency-Key 헤더에 대한 IETF 초안도 이 경우 422를 권고한다. 참고로 이 코드의 이름은 RFC 9110에서 Unprocessable Entity → Unprocessable Content로 바뀌었다.

8-2. 무엇을 해싱할 것인가 — 계약으로 정해야 하는 세부

함정 — JSON은 "같은 내용"이어도 바이트가 다를 수 있다 JSON은 키 순서나 공백이 달라도 같은 내용일 수 있어서, 클라이언트가 재시도할 때 객체를 다시 직렬화하면 같은 요청인데 지문이 달라진다. 그러면 정상적인 재시도가 422로 거절당한다 — 지문이 오히려 사고를 만드는 경우다.

선택지 A — 수신한 원문 바이트를 그대로 해싱

  • 서버 구현이 가장 단순하다.
  • 대신 "재시도는 처음 보낸 바이트를 그대로 다시 보낸다"를 계약에 명시해야 한다.
  • 대부분의 HTTP 재시도 래퍼가 바디를 버퍼에 담아두고 그대로 재전송하므로 현실적인 요구다.

선택지 B — 업무상 중요한 필드만 골라 해싱

  • 예: orderId + amount + method를 정해진 순서로 이어 붙여 해싱.
  • 직렬화 차이에 관대해진다.
  • 대신 해싱 대상에서 빠진 필드가 달라도 재생이 일어난다는 점을 감수한다.
어느 쪽이든 문서에 적어야 계약이 된다 — 지문 규칙은 구현 세부가 아니라 API 계약의 일부다

9. 상태 기계와 리스 — 처리 도중 죽으면 어떻게 되는가

지금까지 나온 상태 — 없음 · IN_PROGRESS · COMPLETED — 를 하나의 그림으로 모으면, 11절의 장애 시나리오를 읽을 수 있는 지도가 된다.

리스(lease) — 기한이 붙은 점유권

리스는 부동산의 임대차에서 온 말이다. 분산 시스템에서는 "지금부터 30초 동안은 내가 이 자원의 주인"이라는 시한부 표식을 뜻한다.

기한이 붙어 있으므로 점유자가 죽어버려도 시간이 지나면 저절로 풀린다 — "잠근 채로 죽는" 사고가 영구화되지 않는다

대신 살아 있는 점유자는 만료 전에 기한을 갱신해야 한다. 기한 없는 락을 쓰면 프로세스가 죽는 순간 그 자원은 사람이 손으로 풀어주기 전까지 영원히 잠긴다.

회수 만료된 IN_PROGRESS 레코드까지 재선점하는 SQL
INSERT INTO idempotency_record
       (user_id, idempotency_key, fingerprint, status, locked_until, created_at)
VALUES (:userId, :key, :fingerprint, 'IN_PROGRESS', now() + interval '30 seconds', now())
ON CONFLICT (user_id, idempotency_key) DO UPDATE
   SET locked_until = now() + interval '30 seconds',
       attempt      = idempotency_record.attempt + 1
 WHERE idempotency_record.status       = 'IN_PROGRESS'   -- 완료된 건은 건드리지 않는다
   AND idempotency_record.locked_until < now();          -- 만료된 것만 회수한다조건이 거짓이면 0행 → 남의 리스는 절대 못 뺏는다
리스 길이를 정하는 기준 — "최초 요청이 정상적으로 끝나는 데 걸리는 최대 시간" PG 승인의 읽기 타임아웃이 10초라면 리스를 30초쯤으로 잡는다.
너무 짧으면 — 정상 처리 중인 요청의 자리를 다른 재시도가 빼앗아 이중 승인이 난다.
너무 길면 — 크래시 후 사용자가 그만큼 오래 결제를 못 한다.

10. 저장소 · 키 스코프 · TTL

10-1. 저장소 — 판단 기준은 성능이 아니라 내구성

DB 테이블 (유니크 인덱스) — 결제의 기본

  • 선점·상태 전이·응답 저장이 한 트랜잭션 안에서 다뤄진다.
  • 내구성이 보장된다 — 이 도메인에서 "키가 사라진다" = "이중 결제"이기 때문이다.
  • 느리지만, 결제 한 건의 비용에 비하면 무시할 만한 비용이다.

Redis SET key value NX PX 30000 — 빠르지만 단독은 위험

  • NX = "키가 없을 때만 쓴다", PX = "밀리초 만료를 함께 건다" → 선점과 만료가 한 명령.
  • 별도 명령인 SETNX는 만료를 못 걸어 뒤에 EXPIRE를 따로 보내야 하는데, 그 사이에 죽으면 영구 락이 남는다.

10-2. 키 스코프 — 왜 (user_id, idempotency_key)인가

① 키가 UUID가 아닐 수 있다
우리는 UUID를 기대하지만 클라이언트가 order-1이나 타임스탬프를 보낼 수도 있다. 키를 전역으로 관리하면 서로 다른 사용자의 키가 실제로 충돌해서, 엉뚱한 사람의 결제 응답이 재생되거나 409로 막힌다.
② 악용을 막는다
키가 전역이면 공격자가 "다음에 쓰일 법한 키"를 미리 선점해 다른 사용자의 결제를 409로 막을 수 있다. 서비스 거부의 변종이다.
스코프의 실무 기준 — "키를 만든 주체가 곧 스코프" (사용자가 만들면 user_id, 파트너사 시스템이 만들면 가맹점 ID)

10-3. TTL — 성능 파라미터가 아니라 안전 파라미터

먼저 못 박을 것 TTL이 만료된 뒤 같은 키가 도착하면 서버는 그것을 "처음 보는 키"로 처리한다. 즉 너무 짧은 TTL은 그대로 이중 결제 경로다. TTL은 "얼마나 아낄까"가 아니라 "가장 늦게 도착할 수 있는 재시도가 언제인가"로 정한다.
상한을 정하는 것은 클라이언트의 성격이다.
재시도 주체최대 지연필요한 TTL
HTTP 클라이언트 라이브러리의 자동 재시도수 초 ~ 수십 초분 단위면 충분
모바일 앱이 오프라인 큐에 담아뒀다 앱 재실행 시 전송시간 ~ 일 단위24시간 이상
파트너사가 실패 건을 다음 날 배치로 재전송하루 이상7일

주요 결제사들이 쓰는 값이 대체로 24시간 안팎인 것은 두 번째 줄을 커버하기 때문이다. 파트너 연동이 일 단위 재전송을 한다면 7일까지 늘린다. 그리고 "만료 후 같은 키가 오면 새 요청으로 처리된다"는 것을 API 문서에 명시해야 한다 — 이건 구현 세부가 아니라 계약이다.

크기 감 — 저장 비용은 이중 결제 한 건보다 압도적으로 싸다

≈1KB

≈1GB

≈8GB

기본키 인덱스와 created_at 인덱스를 더해도 하루 1.1GB 남짓이고, 24시간 보관이면 테이블이 그 크기에서 평형을 이룬다. 이 정도 저장 비용은 이중 결제 한 건의 처리 비용(CS 응대, 환불, 정산 보정)보다 압도적으로 싸다.

10-4. 정리 방법 — PostgreSQL에는 행 단위 자동 만료가 없다

배치가 지워야 하는데, 하루치를 한 번에 DELETE하면 긴 트랜잭션과 대량의 죽은 튜플(dead tuple)이 생겨 VACUUM 부담이 커진다. 둘 중 하나를 택한다.

A 조금씩 나눠 지우기
-- 배치를 짧게 여러 번 돈다
DELETE FROM idempotency_record
 WHERE ctid IN (
   SELECT ctid FROM idempotency_record
    WHERE created_at < now() - interval '24 hours'
    LIMIT 5000
 );
B 파티션 통째로 드롭
-- created_at 기준 일자별 범위 파티션으로 나누고
-- 만료된 파티션을 통째로 없앤다
DROP TABLE idempotency_record_2026_08_28;

-- 파일을 통째로 없애므로 죽은 튜플이 남지 않고
-- VACUUM도 필요 없다 — 로그성 테이블의 정석

11. 멱등성 키가 있어도 뚫리는 구멍 셋

11-1. 사례 1 — 처리 도중 서버가 죽으면 키가 "영구 처리 중"이 된다

키를 선점(IN_PROGRESS)한 직후, PG 호출 전후 어딘가에서 서버 인스턴스가 죽었다. 배포로 컨테이너가 내려갔을 수도 있고 OOM으로 프로세스가 사라졌을 수도 있다.

리스가 없었다면 — 사용자는 영원히 결제를 못 한다 레코드는 IN_PROGRESS로 영원히 남고 이후 모든 재시도가 409를 받는다. 그리고 이 사용자는 다른 키로 다시 시도할 것이므로, 남는 것은 "결제가 자꾸 안 된다"는 CS뿐이다.
9절의 상태 기계 위에서 보면 죽은 지점에 따라 상황이 다르다는 것이 명확해진다.
서버가 죽은 지점레코드 상태PG 승인다음 재시도가 마주치는 것회수 방법
선점 INSERT 전없음안 됨키 없음 → 정상적으로 최초 처리필요 없음
선점 직후, PG 호출 전IN_PROGRESS안 됨리스 만료 전이면 409만료 후 재선점 → 처음부터 처리
PG 호출 도중·직후, 완료 기록 전IN_PROGRESS알 수 없음리스 만료 전이면 409만료 후 재선점 → PG 거래 조회로 판정
완료 기록 직후COMPLETED됨저장된 응답 재생필요 없음

세 번째 줄이 이 사례의 본체다. PG 호출 도중에 죽으면 승인이 났는지 안 났는지 우리도 모른다 — 1절에서 클라이언트가 겪은 것과 똑같은 불확실성이 이번엔 우리 서버 쪽에서 반복된 것이다. 그래서 회수는 두 단계다.

1
리스 만료로 자리를 되찾는다. 9절의 ON CONFLICT DO UPDATE ... WHERE locked_until < now()가 이 일을 한다. 만료된 레코드만 재선점되고, 정상 처리 중인 리스는 건드리지 않는다.
2
재처리 전에 PG에 물어본다. 재선점에 성공했다고 바로 승인을 다시 부르면 안 된다 — 죽기 전에 승인이 이미 났을 수 있기 때문이다. PG의 거래 조회 API로 "우리 주문번호에 대한 승인이 존재하는가"를 먼저 확인하고, 있으면 그 결과로 레코드를 COMPLETED로 마무리하고, 없으면 그때 처음부터 처리한다. (판정 절차 상세: 10-payment-consistency/04-pg-timeout-unknown-state.md)
"키 저장과 실제 처리 사이의 크래시"까지 시나리오에 넣는 것이 결제 시스템 설계의 기본기다 — 이 구간을 빼면 잘 동작하는 정상 경로만 그린 설계가 된다

11-2. 사례 2 — 멱등성 키는 "같은 시도"만 막는다 가산점

사용자가 결제 실패 화면에서 "다시 시도"를 눌렀다. 클라이언트는 3절의 규칙대로 새 키를 만들어 보낸다. 그런데 사실 첫 결제는 성공해 있었다 — 응답만 유실됐던 것이다. 키가 다르므로 서버는 이것을 정당한 신규 요청으로 보고 그대로 통과시킨다.

그리고 클라이언트가 새 키를 만든 것은 버그가 아니다 사용자가 새 시도를 했으니 새 키가 맞다. 같은 구멍이 다른 얼굴로도 나타난다 — 사용자가 주문서를 채우고 결제한 뒤 브라우저를 새로고침해서 같은 상품을 한 번 더 주문하는 경우다. 화면이 새로 그려지면서 새 키가 생기므로 멱등성 키는 이 중복을 아예 인식하지 못한다.
면접에서는 이 구분을 "전송 계층 중복 제거(transport-level dedup) vs 비즈니스 계층 중복 제거(business-level dedup)"로 명확히 나눠 말하면 좋다.
전송 계층 중복 제거비즈니스 계층 중복 제거
장치멱등성 키 (Idempotency-Key)도메인 유니크 제약
묻는 질문"이 요청이 아까 그 요청인가""이 업무가 이미 이뤄졌는가"
판정 근거클라이언트가 붙여 보낸 키도메인 데이터 자체 (주문번호, 장바구니 내용)
막는 것타임아웃 재시도, 게이트웨이 재전송, 더블 클릭새 키로 온 같은 업무의 재요청
못 막는 것새 키로 온 새 시도(막기는 하지만) 최초 응답을 재생해 주지는 못한다
2층 도메인 불변식을 DB가 지키게 한다 — PostgreSQL 부분 인덱스
-- "한 주문에 살아 있는 승인 결제는 1건뿐"이라는 도메인 불변식.
CREATE UNIQUE INDEX uq_payment_approved_per_order
    ON payment (order_id)
 WHERE status = 'APPROVED';부분 인덱스 — 취소된 결제는 조건에서 빠지므로 취소 후 재결제는 정상 허용
주문 생성처럼 아직 비즈니스 식별자가 없는 경우는 한 단계 더 생각해야 한다 결제는 order_id가 있으니 위 제약을 걸 수 있지만, 주문 자체를 만드는 API에는 걸 대상이 없다. 새로고침으로 같은 장바구니가 두 번 들어오는 것을 무엇으로 막을 것인가.

휴리스틱 — 장바구니 스냅샷 해시

  • "같은 사용자가 같은 장바구니 내용으로 5분 안에 만든 주문은 하나로 본다" — 해시에 유니크 제약을 건다.
  • 간단하지만 완전하지 않다. 정말로 같은 것을 두 개 사려는 사용자를 막아버릴 수 있다.

정공법 — 주문 초안(draft) ID를 먼저 발급

  • 주문서 화면에 진입할 때 서버가 초안을 만들어 ID를 내려주고, 결제는 그 초안 ID에 대해서만 이뤄지게 한다.
  • 새로고침해도 초안 ID가 같으므로 유니크 제약이 걸린다.
  • 즉 비즈니스 식별자를 결제보다 앞선 단계에서 미리 확보하는 것 — 12절의 "서버 생성 토큰"과 같은 발상이다.

11-3. 사례 3 — 우리 서버 → PG 호출에도 같은 문제가 재귀한다

우리 API가 완벽하게 멱등해도, 우리 서버가 PG를 호출하다 타임아웃 나면 1절의 딜레마가 서버 안에서 그대로 반복된다. 승인이 났는지 안 났는지 우리도 모르고, 재시도하면 이중 승인 위험이 있다.

1
PG가 멱등성 키를 지원하는가. 지원한다면 우리 쪽 재시도에 같은 키를 유지하면 된다. 이때 PG 쪽 키의 유효 기간도 함께 확인한다 — 우리 TTL보다 짧으면 늦은 재시도가 PG에서 새 승인이 된다.
2
지원하지 않는다면 가맹점 주문번호 기반 중복 방지가 있는가. 많은 PG가 "같은 가맹점 주문번호로는 승인이 한 번만"이라는 규칙을 갖고 있다. 그러면 주문번호가 사실상 멱등성 키 역할을 한다.
3
둘 다 없다면 재시도하지 않는다. 타임아웃 시 자동 재시도 대신 거래 조회로 실제 상태를 확인한 뒤 판단하는 것이 원칙이다. (10-payment-consistency/02-pg-integration-basics.md)

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

중복이 왜 "막을 수 없는 전제"인가?
타임아웃 시 안 됨 / 곧 됨 / 이미 됨이 클라이언트 눈에 전부 "응답 없음"으로 같다(두 장군 문제). 재시도해도 사고, 안 해도 사고 → 서버가 흡수해야 한다.
설계의 심장 한 문장?
검사 후 처리가 아니라 선점 후 처리. ON CONFLICT DO NOTHING이 넣은 행 수 1/0으로 승패를 가른다 — 원자성의 출처는 내 if문이 아니라 DB 유니크 인덱스.
선점 결과 네 갈래는?
1행 → 실제 처리. 0행 → ① 지문 다르면 422 ② IN_PROGRESS면 409 + Retry-After ③ COMPLETED면 재생. 지문 검사가 상태 검사보다 앞.
무엇을 저장하나 — 네 묶음?
식별(키+스코프) · 판정(지문+상태) · 재생(상태 코드+바디) · 수명(리스+생성시각).
왜 에러 대신 재생인가?
클라이언트가 원하는 건 "중복이었다"가 아니라 "결제 결과". 에러를 주면 그 순간 1번과 N번이 구분 가능해져 멱등성이 깨진다. 재생은 상태 코드까지 — 402를 200으로 바꾸면 성공으로 오해한다.
트랜잭션 경계 규칙?
선점은 짧은 자기 트랜잭션으로 커밋한 뒤 처리로 넘어간다. 같이 묶으면 ① IN_PROGRESS 표식이 안 보이고 ② 재시도가 인덱스 대기로 몇 초씩 붙잡힌다.
TTL과 리스, 값을 정하는 기준?
TTL = 가장 늦게 도착할 재시도(모바일 오프라인 큐 → 24시간, 파트너 배치 → 7일). 리스 = 최초 요청이 정상적으로 끝나는 최대 시간(PG 타임아웃 10초 → 30초).
두 층의 구분?
전송 계층(멱등성 키) = "이 요청이 아까 그 요청인가" / 비즈니스 계층(도메인 유니크 제약) = "이 업무가 이미 이뤄졌는가". 새 키로 온 중복은 1층이 못 막는다.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

멱등성 키는 누가 생성하나요? 서버가 만들어주면 안 되나요? 필수힌트: "키의 존재 이유"에서 답이 자동으로 나온다. 그리고 서버 생성이 가능한 경우 하나를 덧붙이면 완성

클라이언트가 만든다. 근거는 키의 존재 이유에 있다 — 키는 "응답을 못 받은 요청을 다시 보낼 때 그게 아까 그 요청임을 증명하는 것"이므로, 응답을 못 받는 상황에서도 키를 이미 알고 있어야 하는 쪽이 만들어야 한다.

서버가 응답 바디에 키를 담아 내려주는 방식은 여기서 자기모순이 된다. 정작 응답이 유실된 재시도 상황에서 클라이언트에게는 키가 없다. 문제를 풀어야 할 바로 그 순간에 도구가 없는 것이다.

서버 생성 토큰을 쓰고 싶다면 방법이 있다 — 결제 요청보다 앞선 별도 단계에서 미리 발급받는 것이다. "결제 화면 진입 시 토큰 발급 → 그 토큰을 결제 요청에 포함". 그러면 결제 요청이 실패해도 클라이언트 손에 토큰이 이미 있다.

이건 서버가 폼을 내려줄 때 일회용 토큰을 심어 중복 제출을 막던 고전적 패턴과 정확히 같은 구조이고, 11절의 "주문 초안 ID"와도 같은 발상이다
같은 키로 두 요청이 완전히 동시에 도착하면 어떻게 되나요? 필수힌트: 결론(한쪽만 INSERT 성공)만 말하면 절반이다. "원자성의 출처"와 PostgreSQL 디테일까지 가야 한다

유니크 제약 덕에 INSERT는 한쪽만 성공한다 — 이것이 이 설계의 심장이다. 성공한 쪽이 실제 처리를 진행하고, 실패한 쪽은 레코드를 조회해서 갈린다. COMPLETED면 저장된 응답을 재생하고, IN_PROGRESS면 409에 Retry-After를 실어 돌려준다.

이 답에서 반드시 짚어야 하는 것은 원자성의 출처다. 애플리케이션 레벨의 exists 검사로는 이 동시 도착을 못 막는다 — 두 요청이 나란히 "없음"을 보고 나란히 통과하는 check-then-act 간극이 있기 때문이다(4절 타임라인). 판정을 우리 if문이 아니라 DB의 유니크 인덱스에 위임했다는 것이 핵심이다.

PostgreSQL 구현 디테일을 하나 얹으면 깊이가 드러난다. 유니크 위반을 예외로 받으면 그 트랜잭션이 중단 상태가 되어 같은 트랜잭션에서 후속 조회를 이어갈 수 없으므로, ON CONFLICT DO NOTHING으로 받아 영향받은 행 수(1 또는 0)로 승패를 가르는 형태가 안전하다.

대안 하나와 그 트레이드오프까지 말하면 좋다. IN_PROGRESS에 409를 주는 대신 "최초 요청이 끝날 때까지 기다렸다가 같은 응답을 주는" 구현도 가능하다. 클라이언트 경험은 더 낫지만, 대기하는 동안 서버의 스레드와 커넥션을 붙잡고 있게 되어 부하 상황에서 위험하다.

재생할 때 최초 요청이 실패 응답이었다면요? 필수힌트: 실패를 한 덩어리로 다루면 틀린다. 세 종류로 쪼갠다

"확정된 실패"인가 "일시적 실패"인가로 갈린다. 이 분류가 실무 설계의 디테일이다.

확정 실패 → 그대로 재생
잔액 부족, 한도 초과, 카드 만료 같은 4xx 계열. 몇 번을 다시 시도해도 같은 결과이므로 COMPLETED로 저장해 두고 재요청에 그대로 돌려준다.
일시적 실패 → 확정 상태로 남기지 않는다
우리 서버 내부 오류로 처리 자체가 시작되지 못했거나 DB 커넥션이 없어 실패한 경우. COMPLETED로 박아두면 같은 키로는 영원히 저장된 500만 재생되어 사용자가 그 키로 결제할 방법이 없어진다. 레코드를 지우거나 리스를 만료시켜 "새로운 최초 처리"로 다시 갈 수 있게 남긴다.
경계 — PG 호출 타임아웃
실패가 아니라 "결과 불명"이다. 실패로 확정하면 실제로는 승인이 났는데 클라이언트에게 실패를 재생하게 되고, 성공으로 처리해도 마찬가지로 틀릴 수 있다. 거래 조회로 사실을 확인한 뒤에 확정한다(11절 사례 1).

이 세 번째 항목을 언급하면 답이 완성된다. "실패면 재생, 성공이면 재생"이라는 이분법에는 "모름"이 빠져 있고, 결제에서 사고는 대개 그 칸에서 난다.

Redis로 하면 되지 않나요? DB까지 써야 하나요? 시니어 변별힌트: 양쪽을 다 인정하고 "기준"을 제시한다. 기준 한 줄이 이 질문의 변별점이다

트레이드오프 판단 문제이므로 양쪽을 다 인정하고 기준을 제시하는 답이 좋다.

Redis의 SET key value NX PX는 원자적 선점을 제공하고 훨씬 빠르며 TTL도 공짜다. 단점은 둘이다. (1) 내구성 — Redis는 기본적으로 비동기 복제라, 페일오버 순간에 방금 쓴 키가 레플리카에 없을 수 있고 그러면 중복 요청이 그대로 통과한다. (2) 확장의 한계 — 응답 바디 저장과 IN_PROGRESS → COMPLETED 상태 전이까지 얹고 나면 결국 트랜잭션적 일관성이 필요해진다. 그 시점에는 Redis를 DB처럼 쓰고 있는 것이다.

판단 기준 한 줄 — "이 도메인에서 중복 한 건의 비용이 얼마인가"
결제
이중 결제 한 건의 비용(CS 응대, 환불, 정산 보정, 신뢰 하락)이 DB 쓰기 한 번의 비용보다 압도적으로 크다. → 내구성 있는 저장소(DB 유니크 제약)를 기본으로, Redis는 앞단의 빠른 차단에 보조로.
조회수 집계처럼 중복돼도 피해가 미미한 API
Redis 단독으로 충분하다. 여기에 DB 쓰기를 얹는 것이 오히려 과설계다.

"결제니까 DB"라고만 답하면 규칙을 외운 것이고, 비용 비교로 답하면 판단할 줄 아는 것이다.

PUT은 멱등하다는데, 그럼 결제를 PUT으로 만들면 해결되나요? 함정힌트: "절반만 맞다"로 시작해 시맨틱과 구현을 가른다

절반만 맞다. 이 질문은 시맨틱(계약)과 구현을 구분하는지를 본다.

맞는 절반. PUT /payments/{clientGeneratedId}처럼 클라이언트가 리소스 식별자를 정해서 올리면 "같은 식별자에 대한 반복 PUT"이라는 멱등 시맨틱을 자연스럽게 얻는다. 사실상 멱등성 키를 헤더가 아니라 URI에 녹인 것이라, 발상 자체는 같다.

틀린 절반. 멱등성은 계약이지 구현이 아니다. 메서드를 PUT으로 바꿨다고 프레임워크가 유니크 제약을 걸어주거나, 응답을 저장해 재생해주거나, 동시 도착을 정리해주지 않는다. 5절부터 9절까지의 설계를 그대로 다 해야 한다. PUT이라는 이름은 "이 API는 멱등합니다"라는 선언일 뿐이고, 그 선언을 참으로 만드는 것은 여전히 우리 코드와 DB 제약이다.

실무 관례까지 덧붙이면 좋다. 결제처럼 생성 + 외부 부수효과(PG 승인)가 함께 있는 작업에는 POST + 멱등성 키를 쓰는 쪽이 관례다. 처리 중(IN_PROGRESS) 상태를 409로 알리는 흐름이 "리소스를 이 상태로 만들어라"라는 PUT의 의미보다 POST 쪽에 더 자연스럽게 얹히기 때문이다. (메서드가 강제가 아니라 선언이라는 이야기: 08-network-http/04-http-method-idempotency-and-safety.md)

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

409를 받은 클라이언트는 정확히 어떻게 재시도해야 하나요?힌트: Retry-After만 말하면 절반이다. "많은 클라이언트가 동시에 409를 받는 상황"을 상상한다

서버가 준 Retry-After를 기준으로, 지수 백오프 + 지터(jitter)를 얹어, 상한 횟수까지만 재시도한다. 그리고 재시도할 때 키는 반드시 그대로 유지한다(3절).

지터가 필요한 이유가 이 답의 핵심이다. 더블 클릭이든 재시도 폭풍이든 여러 클라이언트가 거의 같은 시각에 409를 받는다. 모두가 정확히 1초 뒤에 다시 오면 같은 순간에 다시 몰려 서버 부하가 파도처럼 반복된다. 대기 시간에 무작위 폭을 섞어 도착 시각을 흩뜨리는 것이 지터다.

상한에 도달하면 어떻게 하는가까지 말하면 좋다 — 무한 재시도는 금지다. 상한을 넘으면 사용자에게 "처리 중"으로 안내하고 결제 상태 조회 API로 전환하는 것이 안전하다. 여기서 "결과를 못 받았으니 무조건 다시 결제"로 가면 11절 사례 2의 이중 결제 경로를 밟는다.

409 대신 202를 주면 어떠냐는 변형도 나올 수 있다. 202는 "요청을 접수했다"는 뜻이라 이번 요청이 새로 접수된 것처럼 읽힐 여지가 있다. 재요청이 기존 처리와 충돌해 지금은 결과를 줄 수 없다는 뜻이라면 409 + Retry-After가 의미에 더 맞고, 애초에 "접수 후 폴링"을 계약으로 삼는 API라면 202 + 상태 조회 URL 방식이 어울린다(09-rest-api/10-long-running-operations-202-polling-callback.md).

GET이나 DELETE 같은 멱등한 메서드에도 멱등성 키를 붙여야 하나요?힌트: "키가 필요한 조건"을 먼저 정의하면 답이 자동으로 나온다

필요 없다. 멱등성 키는 "메서드 자체로는 멱등성이 보장되지 않는데, 재시도는 반드시 일어나는" 요청에만 필요한 장치다.

GET은 서버 상태를 바꾸지 않으므로(안전, safe) 몇 번을 보내도 문제가 없다. DELETE는 "그 자원이 없는 상태로 만든다"는 의미라 반복해도 최종 상태가 같다 — 두 번째 호출이 404를 받더라도 서버의 최종 상태는 동일하므로 멱등성 정의를 만족한다. PUT도 마찬가지다.

그래서 실제로 키가 필요한 것은 POST(생성 + 외부 부수효과)와, 증감 연산처럼 멱등하지 않게 구현된 PATCH다 — {"balance": "+1000"} 같은 상대 변경은 반복하면 결과가 달라지므로 POST와 같은 취급을 해야 한다.

Idempotency-Key 헤더가 아예 안 오면 어떻게 처리하나요? 함정힌트: "필수로 한다"가 정답이지만, 운영 중인 API에 바로 적용하면 무슨 일이 나는지까지 생각한다

결제처럼 중복 비용이 큰 API에서는 헤더를 필수로 요구하고, 없으면 400으로 거절하는 것이 원칙이다. 헤더 없이 통과시키면 그 요청만 중복 방어가 통째로 빠진 경로가 되고, 사고는 정확히 그 경로에서 난다.

그런데 이미 운영 중인 API라면 곧장 400으로 바꿀 수 없다. 헤더를 안 보내던 기존 클라이언트가 전부 깨지기 때문이다. 그래서 단계적으로 간다.

① 계측
헤더 없는 요청을 통과시키되 경고 로그와 지표로 남긴다 — 어느 클라이언트가 아직 안 보내는지를 먼저 안다.
② 공지 · 마감일
API 문서에 헤더 이름·의미·TTL·422 조건을 명시하고 필수화 시점을 공지한다.
③ 필수화
지표에서 미사용이 사라지면 400으로 거절. 이때도 파트너별로 먼저 켤 수 있게 하면 위험이 줄어든다.

키 형식 검증도 같이 정한다 — 최대 길이(스키마의 varchar(64)와 맞춘다)와 허용 문자 정도. 형식이 어긋나면 400으로 거절하는 편이, 잘라 저장했다가 서로 다른 키가 같은 키로 뭉개지는 것보다 훨씬 안전하다.

서버가 여러 대인데(스케일 아웃) 멱등성 판정이 인스턴스마다 따로 놀지 않나요?힌트: 이 설계가 어디에 원자성을 위임했는지를 다시 떠올린다

따로 놀지 않는다 — 판정을 애플리케이션이 아니라 공유 저장소(DB 유니크 인덱스)에 위임했기 때문이다. 두 요청이 서로 다른 인스턴스에 도착해도 같은 인덱스 항목을 두고 경쟁하므로 승자는 여전히 한 명이다. 이 설계가 인스턴스 수와 무관하게 성립하는 이유가 바로 이것이다.

반대로 하면 안 되는 것을 말하면 이해가 분명해진다. JVM의 synchronized나 로컬 캐시로 중복을 막는 구현은 인스턴스가 한 대일 때만 동작한다. 서버가 두 대가 되는 순간 각 JVM이 자기 락만 보므로 두 요청이 나란히 통과한다. 중복 방어를 프로세스 메모리에 두면 스케일 아웃이 곧 장애다.

주의할 지점 하나: DB를 읽기 복제본까지 쓰는 구성이라면, 선점 후 조회를 복제본에서 하면 방금 쓴 행이 아직 안 보일 수 있다. 멱등성 레코드의 조회는 쓰기 노드(primary)에서 해야 한다.

멱등성 레코드는 결제 데이터와 같은 DB에 둬야 하나요? 시니어 변별힌트: 기준은 성능이 아니라 "무엇과 한 트랜잭션으로 묶을 수 있는가"다

기준은 "무엇과 원자적으로 묶여야 하는가"다. 5절에서 선점 INSERT는 결제 처리와 분리해야 한다고 했지만, 완료 기록(COMPLETED + 응답 저장)은 이야기가 다르다.

완료 기록이 결제 확정과 같은 DB에 있으면 두 쓰기를 한 트랜잭션으로 묶을 수 있다. 그러면 "결제는 확정됐는데 멱등성 레코드에는 COMPLETED가 안 남는" 창이 사라진다. 저장소가 다르면(예: 결제는 DB, 멱등성 키는 Redis) 그 창이 반드시 남고, 그 창에서 크래시가 나면 재시도가 "처리된 적 없다"고 판단하게 된다.

그 창이 남을 때의 보완책까지 말하면 좋다 — 9절의 리스 만료 + 재선점으로 회수하고, 재처리 전에 PG 거래 조회 또는 우리 결제 테이블 조회로 "이미 승인이 있는가"를 확인한 뒤 진행한다. 즉 저장소를 분리하는 대가는 "조회로 사실을 확인하는 단계"를 반드시 넣는 것이다.

선점은 따로 커밋, 완료 기록은 가능하면 결제와 한 트랜잭션 — 두 요구가 반대 방향이라는 것이 이 설계의 미묘한 지점이다
응답 바디를 통째로 저장하면 민감정보가 쌓이지 않나요?힌트: 저장하는 것이 "요청"이 아니라 "응답"이라는 점부터

저장 대상은 요청이 아니라 응답이라는 점이 출발점이다. 응답 바디는 이미 클라이언트에게 나간 값이므로, 카드번호 같은 것은 애초에 마스킹된 형태여야 한다 — 그렇지 않다면 그건 멱등성 레코드의 문제가 아니라 API 응답 설계 자체의 문제다.

그럼에도 이 테이블은 결제 응답이 모여 있는 곳이므로 다음을 함께 정한다.

보관 기간
TTL을 필요 이상으로 길게 잡지 않는다(10절). 다만 짧게 잡는 것이 곧 이중 결제 경로라는 제약이 있으므로, 안전 하한 아래로는 내리지 않는다.
접근 통제
운영 조회 경로를 제한하고 감사 로그를 남긴다.
저장 최소화
재생에 꼭 필요한 필드만 응답에 담는 설계를 하면, 저장되는 것도 자연히 줄어든다.

지문(fingerprint)이 요청 원문이 아니라 해시라는 점도 여기서 이점이 된다 — 요청 바디 자체는 저장하지 않고도 "같은 요청인가"를 판정할 수 있다.

한 줄 요약
타임아웃 난 클라이언트는 결제 성공/실패를 원리적으로 알 수 없어 반드시 재시도하므로, 서버가 클라이언트 생성 멱등성 키를 유니크 제약으로 원자적으로 선점하고(검사 후 처리가 아니라 선점 후 처리 — 원자성의 출처를 DB 인덱스에 위임해 check-then-act 간극을 없앤다) 최초 응답을 상태 코드까지 저장해 재생함으로써 "N번 보내도 1번 처리"를 API 계약으로 보장해야 한다 — 여기에 같은 키·다른 내용을 422로 거절하는 요청 지문, 처리 중 크래시를 회수하는 리스, 그리고 "멱등성 키는 같은 시도의 재전송만 막으므로 새 키로 온 중복은 주문당 결제 1건 같은 도메인 불변식이 막는다"는 계층 구분까지 겹쳐야 이중 결제가 실제로 막힌다.
