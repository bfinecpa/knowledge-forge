RESTful API 설계 원칙
리소스 중심 설계와 네이밍 — 일관성이 곧 협업 속도

면접 질문: "RESTful API의 설계 원칙을 설명해주세요. 리소스 네이밍 규칙은?"

핵심 관전 포인트 — REST는 "자원(리소스)을 URI로 식별하고, 그 자원에 무엇을 할지는 HTTP 메서드로, 결과는 상태 코드로 말한다"는 리소스 중심 설계 스타일이다. 이름의 뜻부터가 설계 지침이다 — 서버가 가진 자원 자체가 아니라 그 자원의 표현(Representation, 지금 상태를 JSON 같은 형식으로 찍어낸 스냅샷)을 주고받고, 그 표현을 받아 클라이언트의 상태가 다음 단계로 전이(State Transfer)한다는 뜻이다. 주고받는 것이 "명사(표현)"이므로 URI도 동사가 아닌 명사(복수형)가 되고, 동사는 이미 자리가 있는 HTTP 메서드가 맡는다. 그리고 메서드에는 안전성(safe, 서버 상태를 바꾸지 않는다)과 멱등성(idempotent, 몇 번 반복해도 최종 상태가 같다)이라는 계약이 붙어 있어 캐시·프록시·크롤러·자동 재시도 라이브러리가 그 계약만 믿고 동작한다 — 그래서 GET /orders/42/delete 같은 규약 위반은 내 코드가 아니라 인프라가 사고를 낸다. 그런데 원칙 암기보다 중요한 것은 일관성이다. API는 한번 공개되면 바꾸기 어려운 장기 계약이고, 일관된 규칙만이 클라이언트 개발자가 "다음 엔드포인트가 어떻게 생겼을지" 예측할 수 있게 해 협업 속도를 만든다. 원칙은 그 일관성을 지키기 위한 공용 언어다.
  • 1
    이름이 곧 설계 지침이다 — REST는 자원의 표현(Representation)을 주고받아 클라이언트의 상태를 전이(State Transfer)시키는 스타일이다. 오가는 것이 "명사(표현)"이므로 URI는 자원(명사·복수형), 행위는 HTTP 메서드, 결과는 상태 코드가 나눠 맡고, 서버는 요청 사이의 문맥을 기억하지 않는다(무상태).
  • 2
    메서드는 이름표가 아니라 계약이다 — HTTP 명세는 각 메서드에 안전성·멱등성을 못박아 두었고 캐시·프록시·크롤러·재시도 라이브러리가 그 계약만 믿고 움직인다. 그래서 GET으로 삭제를 만들면 내 코드가 아니라 내가 통제하지 못하는 인프라가 사고를 낸다.
  • 3
    그러나 원칙보다 일관성이 계약이다 — API는 배포하는 순간 소비자와의 장기 계약이 되고, 실무의 진짜 비용은 "원칙 위반"이 아니라 "엔드포인트마다 규칙이 다른 것"에서 나온다. 그래서 답은 "REST를 100% 지킨다"가 아니라 "팀 가이드를 만들어 전체 API의 일관성을 우선하고, 예외조차 문서화해 일관되게 만든다"이다.

0. 질문 + 출제 의도

질문: "RESTful API의 설계 원칙을 설명해주세요. 리소스 네이밍 규칙은?"

출제 의도: API는 한번 공개되면 바꾸기 어려운 장기 계약이다. 원칙의 준수 여부 자체보다, 일관성이 클라이언트 개발자의 예측 가능성(= 협업 속도)을 만든다는 이유를 아는지 본다. "왜 이렇게 짓는가"를 소비자 관점에서 설명하는 사람과 규칙만 외운 사람이 갈린다.

이 페이지가 겨냥하는 약점 세 가지 ① "REST(Representational State Transfer)"를 영문 병기만 하고 넘어가는 것 → 1절에서 세 단어를 각각 풀어, 왜 URI가 명사가 되는지와 왜 .json 확장자를 안 붙이는지를 이름에서 유도한다.
② 메서드를 "행위 이름표"로만 이해하는 것 → 3절에서 안전성·멱등성이 명세가 못박은 계약임을 보이고, 그 계약을 누가(브라우저·CDN·프록시·크롤러) 믿고 움직이는지를 도식으로 그린다.
③ 네이밍 규칙을 목록으로만 외우는 것 → 7·8절에서 규칙마다 "안 지키면 무엇이 비싸지는가"(URI 두 벌, 조상 검증, 캐시 키 분기)를 붙여, 규칙을 판단 기준 하나로 압축한다.

1. 이름부터 풀자 — Representational State Transfer

REST는 Roy Fielding이 2000년 박사 논문에서 정리한 아키텍처 스타일이고, 이름이 곧 설계 지침이다. 그런데 대부분의 설명이 REST(Representational State Transfer)라고 영문만 병기하고 넘어가서, 정작 이 세 단어가 무엇을 말하는지 모른 채 규칙만 외우게 된다. 이름부터 풀고 시작하자.

Representational — 표현
서버가 DB에 들고 있는 42번 주문 그 자체를 네트워크로 보낼 방법은 없다. 보낼 수 있는 것은 "지금 상태를 특정 형식으로 찍어낸 스냅샷"뿐이고, 그것이 표현이다. 같은 자원 하나가 JSON으로도 XML로도 표현된다.
State Transfer — 상태 전이
여기서 "상태"는 서버 데이터가 아니라 클라이언트가 지금 어느 화면·어느 단계에 있는가다. 목록에서 링크를 누르면 상세의 표현이 전송(Transfer)되고, 그 순간 사용자의 자리가 목록 → 상세로 옮겨간다.

첫 답변에 쓸 한 문장 — REST를 정의하라고 하면

자원을 URI로 지목하고, 그 자원의 표현을 주고받으며, 그 주고받음으로 클라이언트가 다음 단계로 이동하는 구조를 웹의 기존 인프라(HTTP) 위에서 그대로 쓰자는 제안

면접에서는 제약 조건 여섯 개를 나열하는 것보다 아래 ①~④를 "왜"와 함께 짚는 편이 낫다. 여섯 제약은 6절에서 한 문장씩 실체를 붙여 정리한다.

① 자원 = URI
무엇(what)
② 행위 = 메서드
어떻게(how)
③ 결과 = 상태 코드
어떻게 됐나
④ 무상태
기억하지 않는다
네 글자로 외운다 — 명(名) · 동(動) · 결(結) · 무(無)  :  명사는 URI, 동사는 메서드, 결과는 상태 코드, 문맥은 기억 안 함

2. ① 자원은 URI로, ② 행위는 HTTP 메서드로

2-1. 컬렉션도 하나의 자원이다

"무엇(what)"은 URI가 담당한다. 주문·회원·상품 같은 자원(명사)이 URI의 주인공이다.

/orders
주문들의 모음이라는 자원. 조회하면 목록 표현이 오고, 여기에 POST하면 새 항목이 추가된다.
/orders/42
42번 주문이라는 자원. 위 컬렉션의 원소 하나.

컬렉션과 단건이 같은 문법 위에 놓이는 이 구조가 뒤에 나올 네이밍 규칙(복수형)의 근거가 된다. /orders도 어엿한 하나의 자원이라는 점을 짚어두면 좋다.

2-2. URI에 동사를 넣지 않는 이유 — 자리가 이미 있기 때문

before URI에 동사 — 행위 표현 자리가 중복된다
POST /createOrder
POST /orders/42/delete
GET  /getOrderList

// 문제 ① 같은 "삭제"를 팀원마다 다르게 짓는다
//        /orders/42/delete · /deleteOrder?id=42 · /orders/42/remove
// 문제 ② 인프라가 메서드만 보고 판단하므로
//        위 GET 삭제는 캐시·프리페치·크롤러 사고로 이어진다 (3절)
// 문제 ③ 자원이 하나 늘 때마다 동사 조합만큼 엔드포인트가 는다
after 메서드가 행위, URI는 자원만
POST   /orders        // 생성
DELETE /orders/42     // 삭제
GET    /orders        // 목록 조회
GET    /orders/42     // 단건 조회

// URI = 명사(목적어), 메서드 = 동사
// "주문을 / 삭제한다" = DELETE /orders/42
// 문장 구조가 통일되면 처음 보는 API도 읽힌다.

3. 메서드의 두 계약 — 안전성(safe)과 멱등성(idempotent)

메서드를 "행위 이름표" 정도로만 이해하면 절반만 아는 것이다. HTTP 명세(RFC 9110)는 각 메서드에 두 가지 성질을 계약으로 못박아 두었고, 세상의 인프라 전체가 그 계약을 참으로 믿고 움직인다. 이 두 성질을 여기서 정의해 두어야 뒤의 상태 코드 이야기도, 꼬리질문도 근거를 갖는다.

안전(safe) — 서버 상태를 바꾸지 않는다
읽기 전용이라는 약속. 이름이 "안전"인 이유는 보내는 쪽 입장에서 부담이 없다는 데서 왔다 — 링크를 미리 눌러봐도, 크롤러가 사이트 전체를 훑어도 아무것도 망가지지 않으니 안전하다.
자문 질문: "이 요청이 크롤러에 의해 하루 만 번 호출돼도 괜찮은가?"
멱등(idempotent) — 반복해도 최종 상태가 같다
상태를 바꿔도 되지만 그 변화가 누적되지 않는다는 약속. 멱등(冪等)은 수학에서 왔다 — 거듭 적용해도 결과가 같은 연산, f(f(x)) = f(x).
절댓값을 떠올리면 된다. abs(-3)도 3이고 abs(abs(-3))도 3이라, 몇 번을 씌워도 더는 변하지 않는다.
멱등의 일상 비유 — 엘리베이터 호출 버튼
한 번 누르든 조급해서 열 번 누르든 엘리베이터의 상태는 "호출됨" 하나다.
멱등이 아닌 것 — 자판기 결제 버튼
열 번 누르면 열 번 결제된다. 변화가 누적된다. POST /orders가 이쪽이다.

여기서 가장 자주 틀리는 지점 — 멱등성의 기준은 "응답"이 아니라 "서버의 최종 상태"다

DELETE /orders/42를 두 번 보내면 첫 번째는 204, 두 번째는 404로 응답이 달라진다. 그래도 DELETE는 멱등이다 — 두 호출이 끝난 뒤 서버는 똑같이 "42번 주문이 없는 상태"이기 때문이다.

멱등 = 응답이 같다 (X)  /  멱등 = N번 보낸 뒤 서버의 최종 상태가 1번 보낸 뒤와 같다 (O)

그리고 안전한 메서드는 자동으로 멱등이다. 상태를 아예 안 바꾸는데 반복한다고 달라질 리가 없다. 반대는 성립하지 않는다 — DELETE는 안전하지 않지만 멱등이다.

메서드별 계약. 외울 것은 O/X 표가 아니라 맨 오른쪽 열의 이유다 — 이유를 알면 표를 복원할 수 있다.
메서드안전(safe)멱등(idempotent)그 칸에 들어가는 이유중간 계층이 이 계약으로 하는 일
GETOO"이 자원의 표현을 달라" — 조회만 요청하므로 상태를 안 바꾼다캐시 저장·재사용, 프리페치, 크롤링
HEADOOGET과 같되 본문 없이 헤더만 받는다 — 하는 일이 GET의 부분집합변경 여부·용량 확인(본문 없이)
OPTIONSOO"이 URI에 어떤 메서드를 쓸 수 있나"를 묻는다 — CORS 프리플라이트가 이것브라우저의 사전 확인 요청
PUTXO"이 자원을 이 상태로 만들어라" — 본문에 최종 상태가 통째로 담겨 반복해도 같은 자리타임아웃 시 자동 재시도 가능
DELETEXO"이 자원이 없는 상태로 만들어라" — 최종 상태는 언제나 "없음" 하나타임아웃 시 자동 재시도 가능
POSTXX"이 데이터를 처리해라" — 반복하면 새 자원이 하나씩 더 생겨 누적된다캐시·자동 재시도 모두 불가
PATCHXX (보장 안 함)수정 내용의 성질을 규약이 정하지 않는다 — 상대 연산(+100)이면 누적된다멱등이라고 가정할 수 없다
PATCH 칸을 오해하지 말자 "PATCH는 절대 멱등이 아니다"가 아니라, "구현이 멱등일 수는 있지만 클라이언트·인프라가 멱등이라고 가정해서는 안 된다"가 정확한 표현이다. {"status":"CANCELLED"}처럼 절대값을 지정하는 PATCH는 사실상 멱등이지만, {"point":"+100"}처럼 상대 연산이면 부를 때마다 누적된다. 규약이 이를 구분하지 않으므로 보장이 없는 것이다. (자세히: 02-put-vs-patch.md, ../08-network-http/04-http-method-idempotency-and-safety.md)

4. ③ 결과는 HTTP 상태 코드로 표현한다

성공과 실패를 본문에만 담지 말고 상태 코드로 먼저 말한다. 이유는 상태 코드가 본문을 파싱하지 않고도 읽히는 유일한 신호이기 때문이다. 로드밸런서, API 게이트웨이, 모니터링 에이전트, 클라이언트 라이브러리의 재시도 로직은 내 응답 JSON의 스키마를 모른다. 이들이 아는 것은 세 자리 숫자뿐이다.

before 무조건 200 + 본문으로만 성공 여부 전달
HTTP/1.1 200 OK
Content-Type: application/json

{"success": false, "message": "주문 없음"}

// 문제 ① 클라이언트·게이트웨이·모니터링이 모두
//        본문을 파싱해야 실패를 안다.
// 문제 ② 에러율 대시보드에 이 응답이 "성공"으로 집계된다
//        — 장애가 나도 그래프가 평온하다.
// 문제 ③ 재시도 라이브러리·서킷 브레이커가
//        실패를 인지하지 못해 아무 방어도 작동하지 않는다.
good 상태 코드가 먼저 말한다
HTTP/1.1 404 Not Found
Content-Type: application/json

{"code": "ORDER_NOT_FOUND", "message": "주문 없음"}

// 상태 코드 = 기계가 읽는 신호 (중간 계층까지 전달된다)
// 본문의 code = 사람과 클라이언트 코드가 분기하는 상세 사유
//   404 안에서도 "주문이 없다"인지 "회원이 없다"인지 구분
// 두 층이 각각 다른 소비자를 위해 존재한다.

실무에서 90%를 덮는 상태 코드 여섯 개 — "언제 쓰는가"를 붙여 외운다

코드뜻언제 쓰는가응답 본문
200 OK성공조회 성공, 또는 수정 후 바뀐 자원의 표현을 돌려줄 때있음
201 Created새 자원이 생겼다POST /orders로 자원을 만들었을 때. Location 헤더에 생성된 자원의 URI를 담는다보통 생성된 자원의 표현
204 No Content성공했고 돌려줄 표현이 없다삭제 성공, 또는 수정은 됐지만 클라이언트가 이미 결과를 아는 경우없음 (있으면 규약 위반)
400 Bad Request요청 자체가 잘못됐다필수 파라미터 누락, 타입 불일치처럼 요청을 고치기 전엔 몇 번을 보내도 같은 결과인 오류오류 표현
404 Not Found그 URI에 해당하는 자원이 없다존재하지 않는 ID 조회오류 표현
409 Conflict자원의 현재 상태와 충돌한다요청 자체는 멀쩡한데 지금 상태에서는 할 수 없는 경우 — 이미 취소된 주문을 또 취소, 중복 이메일 가입오류 표현

400과 409를 가르는 한 문장: 요청 내용을 고쳐야 통과하면 400, 요청은 그대로여도 자원의 상태가 달라지면 통과하면 409.

4-1. 201의 Location 헤더 — 클라이언트가 URI를 조립하지 않게 한다

클라이언트가 POST /orders를 보낼 때는 만들어질 주문의 URI를 모른다. ID를 서버가 발급하기 때문이다. 그래서 서버가 응답에 Location: /orders/42를 실어 "방금 만든 것은 여기에 있다"고 알려준다. 클라이언트는 이 값을 그대로 다음 요청의 주소로 쓸 수 있고, URI 조립 규칙을 자기 코드에 하드코딩하지 않아도 된다.

응답 생성 성공 — 상태 코드 · 위치 · 표현이 각자 한 가지씩 말한다
HTTP/1.1 201 Created
Location: /orders/42          // 생성된 자원의 주소 — 클라이언트가 URI를 만들지 않아도 된다
Content-Type: application/json

{"id": 42, "status": "PENDING", "total": 9900}   // 서버가 채운 값(id·status)을 바로 쓰게 해준다

4-2. 204를 언제 200 대신 쓰는가

기준은 하나 — "돌려줄 표현이 실제로 있는가"

  • DELETE /orders/42 성공 → 돌려줄 주문 표현이 이제 존재하지 않는다 → 204
  • PATCH로 수정 후 서버가 계산한 값(할인 적용 후 총액, 갱신된 updatedAt)이 필요하다 → 200 + 본문

판단이 애매할 때 던지는 질문

  • "이 응답 본문을 클라이언트가 실제로 읽고 쓰는가?"
  • 아무도 안 읽는 {"success": true}를 매번 만들어 보내는 것은 대역폭과 파싱 비용만 늘린다
  • 204에 본문을 담는 것은 규약 위반이다 — 일부 클라이언트는 본문을 아예 읽지 않는다
이어지는 문서 상태 코드 전반의 사용 기준(3xx 리다이렉트, 401과 403의 구분, 5xx 계열)은 ../08-network-http/05-http-status-codes-usage-criteria.md에서 별도로 다룬다.

5. ④ 무상태(Stateless) — 먼저 "상태를 들고 있으면 무엇이 곤란한가"

무상태의 이점을 "스케일 아웃과 장애 복구가 쉬워진다"로 먼저 말하면 결론만 남고 이유가 사라진다. 반대편, 즉 서버가 상태를 들고 있을 때 무슨 일이 벌어지는지부터 보자.

1
전통적인 서버 세션 방식에서는 로그인에 성공하면 서버가 자기 메모리에 세션 객체를 만들고 그 열쇠(세션 ID)를 쿠키로 내려준다.
2
문제는 그 세션이 그 서버 인스턴스의 메모리에만 있다는 것이다. 사용자의 다음 요청이 2번 서버로 가면 2번 서버는 그 세션 ID를 모르므로 "로그인 안 한 사람"으로 취급한다.
3
그래서 로드밸런서에 스티키 세션(sticky session) — 같은 사용자의 요청을 항상 같은 서버로 붙여 보내는 설정 — 을 걸게 된다. 이름 그대로 사용자가 특정 서버에 "붙어" 버리는 것이다. 여기서 두 가지 대가가 발생한다.

무상태에 대한 가장 흔한 오해

무상태 = "서버가 아무 데이터도 저장하지 않는다" (X)

주문 데이터는 당연히 DB에 남는다. 무상태가 금지하는 것은 "이 클라이언트가 지금 어느 단계까지 진행했는지"라는 대화의 문맥을 서버 메모리에 들고 다음 요청을 기다리는 것이다.

자원의 상태 (resource state)
서버가 저장한다. 주문·회원·상품 데이터 — DB에 남는 것.
애플리케이션 상태 (application state)
클라이언트가 들고 다닌다. "지금 3단계 결제 화면", "장바구니 편집 중" 같은 대화의 문맥.

6. 여섯 제약 조건 — 이름만 알고 넘어가면 안 되는 것들

Fielding이 정의한 REST의 아키텍처 제약은 여섯 개다. 앞의 ①~④는 그중 두 개(균일한 인터페이스, 무상태)를 실무 지침으로 풀어 쓴 것이므로, 나머지도 한 문장씩은 실체를 갖고 있어야 한다.

여섯 글자로 외운다 — 클 · 무 · 캐 · 계 · 균 · 코  (클라이언트-서버 · 무상태 · 캐시 가능 · 계층화 · 균일 인터페이스 · 코드 온 디맨드)

클라이언트-서버 (Client-Server)

UI를 다루는 쪽과 데이터를 저장하는 쪽의 관심사를 분리한다. 둘이 HTTP라는 계약으로만 이어져 있으면 앱을 새로 만들어도 서버를 건드릴 필요가 없고, 서버 DB를 갈아엎어도 앱이 그대로 돈다. 지금은 너무 당연해 보이지만, 화면과 데이터가 한 덩어리이던 시절에 대비해 명시된 제약이다.

무상태 (Stateless)

5절에서 본 그대로다. 요청은 자기 자신만으로 해석 가능해야 한다.

캐시 가능 (Cacheable)

응답은 자기 자신이 캐시 가능한지, 얼마나 유효한지를 스스로 밝혀야 한다(Cache-Control, ETag, Last-Modified). 그래야 브라우저와 CDN이 같은 요청을 서버까지 보내지 않고 저장해둔 응답을 재사용한다. 이 재사용이 성립하는 근거가 3절의 안전성 계약이다 — GET이 아무것도 바꾸지 않는다는 약속이 있어야 중간에서 응답을 가로채 재사용해도 되기 때문이다.

계층화 시스템 (Layered System)

클라이언트는 자기가 말을 거는 상대가 최종 서버인지 중간 계층인지 알 수 없어야 하고, 알 필요도 없어야 한다. 이 제약이 있어서 클라이언트와 서버 사이에 리버스 프록시(Nginx)·CDN·로드밸런서·API 게이트웨이를 얼마든지 끼워 넣어도 클라이언트 코드가 한 줄도 바뀌지 않는다.

반대로 말하면, 클라이언트가 "우리 서버는 8080 포트로 직접 붙어야 한다" 같은 배치 정보를 알고 있다면 그 API는 이 제약을 어긴 것이고, 나중에 앞단 인프라를 바꿀 때 클라이언트를 전부 고쳐야 한다.

6-1. 균일한 인터페이스 (Uniform Interface) — 하위 규칙 넷

REST를 다른 스타일과 구분 짓는 핵심 제약으로, "모든 자원을 똑같은 방식으로 다룬다"는 뜻이다. 하위 규칙이 넷인데, 앞의 ①②③이 바로 그중 셋이다.

하위 규칙뜻이 문서에서
자원의 식별모든 자원에 URI라는 고유 주소가 있다① (2절)
표현을 통한 자원 조작자원 자체가 아니라 표현(JSON 등)을 주고받아 변경한다①, 1절
자기 서술적 메시지메시지 하나만 보고 해석할 수 있어야 한다 — 메서드·Content-Type·상태 코드가 그 역할②③ (2·4절)
하이퍼미디어(HATEOAS)응답이 "다음에 할 수 있는 행동"의 링크를 담는다11절 꼬리질문
코드 온 디맨드 (Code-On-Demand) — 유일한 선택 사항 서버가 실행 가능한 코드(자바스크립트 등)를 내려보내 클라이언트의 기능을 확장하는 것. 여섯 제약 중 유일하게 선택 사항이며, 지키지 않아도 RESTful하다고 부른다. 여섯 개를 나열해야 할 때 "마지막 하나는 선택입니다"를 붙이면 외운 목록이 아니라 이해한 목록으로 들린다.

7. 리소스 네이밍 — 예측 가능성을 만드는 문법

규칙이 여러 개로 보이지만 목적은 하나로 수렴한다.

판단 기준은 하나 — 처음 보는 사람이 규칙만 알면 URI를 추측할 수 있는가
다섯 규칙. 외울 것은 왼쪽 열이 아니라 맨 오른쪽 "안 지키면 무엇이 비싸지는가"다.
규칙BeforeAfter안 지키면 비싸지는 것
동사 금지, 명사 사용/getUsers/users같은 행위의 이름이 팀원마다 갈리고, 메서드와 URI가 서로 모순될 수 있다
복수형 명사/user/42/users/42엔드포인트마다 "여긴 단수였나 복수였나"를 문서에서 확인해야 한다
소문자 + 하이픈(kebab-case)/orderItems, /order_items/order-items경로는 대소문자를 구분하므로 /orderitems로 잘못 적는 순간 404
계층 관계는 경로로/orderItemList?orderId=42/orders/42/items소유 관계가 URI에 안 드러나 구조를 문서로만 알 수 있다
파일 확장자 금지/users/42.json/users/42 + Accept 헤더표현 형식이 하나 늘 때마다 URI가 한 벌씩 늘어난다
다섯 글자로 외운다 — 동 · 복 · 케 · 계 · 확  (동사 금지 · 복수형 · kebab-case · 계층은 경로 · 확장자 금지)

7-1. 이유까지 알아야 하는 규칙 셋

복수형을 쓰는 이유 — 컬렉션과 단건이 하나의 문법으로 이어진다

/users(사용자들의 모음)와 /users/42(그 모음의 42번 원소)는 "컬렉션 / 컬렉션의 원소"라는 같은 문법을 공유한다. 단수와 복수를 섞으면 클라이언트는 엔드포인트마다 "여긴 /user였나 /users였나"를 문서에서 확인해야 한다.

규칙의 값어치는 문법적 정확성이 아니라 확인하러 가지 않아도 되는 데 있다.

kebab-case를 쓰는 이유 — 경로는 대소문자를 구분한다

/orderItems와 /orderitems는 서로 다른 URI이고, 어느 쪽으로 적었는지 헷갈리는 순간 404가 난다. 전부 소문자로 통일하면 이 실수 자체가 사라진다.

단어 구분자로 언더스코어(_) 대신 하이픈(-)을 고르는 것은 관례에 가깝지만, 밑줄이 링크의 밑줄 표시에 가려 안 보이는 문제와 검색엔진이 하이픈을 단어 구분자로 취급하는 관행이 근거로 꼽힌다.

파일 확장자를 쓰지 않는 이유 — 1절로 돌아간다

URI가 가리키는 것은 자원이지 파일이 아니고, 같은 자원이 JSON으로도 XML로도 표현될 수 있다. 어떤 표현을 원하는지는 Accept 헤더로 협상(content negotiation)하는 것이 HTTP가 이미 마련해둔 자리다. 확장자를 URI에 박으면 표현 형식이 자원의 주소에 섞여 들어가, 형식이 하나 늘 때마다 URI가 한 벌씩 늘어난다.

8. 중첩 깊이와 쿼리 파라미터의 경계

계층은 소유 관계일 때만 경로로 표현한다. /orders/42/items는 "42번 주문에 속한 항목들"이라는 소유가 명확할 때 쓴다. 그런데 여기서 반드시 따라오는 것이 깊이 제한이다.

경로와 쿼리의 경계 — 이 한 줄이면 필터·정렬·페이징 논쟁이 끝난다

자원의 식별은 경로, 자원을 "어떻게 보여줄지"는 쿼리
before 보여주는 방식을 경로에 박았다
GET /paid-orders
GET /pending-orders
GET /cancelled-orders

// 상태가 하나 늘 때마다 엔드포인트가 하나씩 는다.
// 정렬·페이징까지 조합하면 폭발한다.
after 자원은 하나, 걸러내는 방식은 쿼리
GET /orders?status=PAID&page=2&sort=createdAt,desc

// 자원은 어디까지나 "주문 컬렉션" 하나이고
// status · page · sort는 그 컬렉션을
// 걸러내고 잘라내는 "방식"일 뿐이다.
// 조건이 늘어도 엔드포인트는 그대로.

9. CRUD로 표현이 안 되는 동작 — 컨트롤 리소스

"주문 취소", "비밀번호 초기화"처럼 동사가 꼭 필요한 순간이 있다. 이런 동작은 생성·조회·수정·삭제 중 어디에도 깔끔하게 들어맞지 않는다. "주문 취소"는 주문을 지우는 것도 아니고 단순히 필드 하나를 바꾸는 것도 아니다 — 재고 복구, 결제 취소, 알림 발송이 딸린 하나의 업무 절차다.

컨트롤 리소스(control resource)란 이름 그대로 "제어(control)를 위해 만들어낸 자원", 즉 행위를 명사로 바꿔 자원인 척 만든 URI를 말한다. "취소한다(cancel)"라는 동사를 "취소(cancellation)"라는 명사로 바꿔 /orders/42/cancellation이라는 자원을 만들고, 거기에 POST하면 취소가 실행되는 식이다. 자원이 아닌 것을 자원의 문법 안으로 들여오는 우회이므로, REST 원칙의 예외가 아니라 "표현력이 모자란 지점을 메우는 규약"으로 이해하는 편이 정확하다.
방법 A 상태 전이를 자원의 부분 수정으로
PATCH /orders/42
{"status": "CANCELLED"}

// 언제 자연스러운가
//   상태 필드 하나만 바뀌는 단순한 전이
//   부수 효과가 거의 없다
//   이 전이에만 필요한 추가 입력이 없다
방법 B 행위를 명사화한 컨트롤 리소스로
POST /orders/42/cancellation
{"reason": "CUSTOMER_REQUEST"}

POST /users/42/password-reset

// 언제 자연스러운가
//   여러 시스템이 함께 움직이고 실패할 수 있는 절차
//   그 행위에만 필요한 입력(취소 사유)을 본문에 담기 좋다
//   나중에 GET /orders/42/cancellation 으로
//     취소 내역을 조회하는 확장이 자연스럽다

A와 B의 갈림 기준

그 전이에 딸린 부수 효과가 얼마나 되는가

상태 필드 하나만 바뀌면 A, 여러 시스템이 함께 움직이고 실패할 수 있는 절차라면 B가 "이것은 단순한 필드 수정이 아니라 하나의 작업"이라는 사실을 URI에 드러내 준다.

면접에서 값이 나가는 마무리 가산점 원칙을 억지로 우회하지 않고 "여기는 REST의 표현력이 부족한 지점이라, 팀 컨벤션으로 컨트롤 리소스를 정해 일관되게 씁니다"라고 말하면 실무 감각이 드러난다. 핵심은 예외를 만든다는 사실이 아니라, 예외에도 규칙이 있다는 것이다.

10. 실무 관점 — 원칙보다 일관성이 계약이다

API는 배포하는 순간 소비자(모바일 앱, 파트너사, 타 팀)와의 계약이 된다. 계약이라는 말이 무거운 이유는, 한번 나간 API는 내가 고치고 싶다고 고칠 수 없기 때문이다. 앱은 스토어 심사를 거쳐 배포되고 사용자가 업데이트해야 반영되며, 파트너사는 자기 일정으로 움직인다.

규칙이 제각각인 서비스에서 벌어지는 일

  • 어떤 API는 /users/42
  • 어떤 API는 /getUser?id=42
  • 또 어떤 API는 /api/v1/user/get/42
  • → 클라이언트 개발자는 화면 하나 붙일 때마다 문서를 뒤지고, 문서가 낡아 있으면 슬랙에 묻고, 답이 올 때까지 기다린다
  • → 이 커뮤니케이션 비용은 엔드포인트 수에 비례해 누적된다

규칙이 일관된 서비스에서 벌어지는 일

  • 문서 없이도 "상품 목록은 아마 GET /products겠지"라는 예측이 가능해진다
  • 그 예측이 맞는 경험이 서너 번 쌓이면 클라이언트 개발자는 문서를 확인하러 가지 않는다
  • → 이것이 협업 속도다
실무에서 진짜 문제를 일으키는 것은 "REST 원칙 위반"이 아니다 "엔드포인트마다 규칙이 다른 것"이다. 원칙을 80%만 지켜도 그 80%가 전 엔드포인트에서 똑같으면 소비자는 예측할 수 있다. 반대로 원칙을 완벽히 지킨 엔드포인트와 그렇지 않은 엔드포인트가 섞여 있으면 소비자는 매번 확인해야 한다.

시니어의 답 — 두 문장

"REST 원칙을 100% 지킨다"가 아니라 "팀의 API 설계 가이드(컨벤션 문서)를 만들어, 원칙 준수 여부보다 전체 API의 일관성을 우선한다"

여기에 하나를 더 얹으면 판단력이 드러난다. 이미 운영 중인 API가 규칙에서 벗어나 있다면, 그것을 고치는 것 자체가 계약 파기(breaking change)다. /getUser?id=42가 흉하다고 /users/42로 바꾸면 그 API를 쓰던 구버전 앱이 전부 깨진다.

현실적인 판단은 새로 만드는 API부터 규칙을 적용하고, 기존 것은 버전 정책이나 폐기(deprecation) 일정 위에서 다루는 것이다. (이어지는 문서: 08-backward-compatible-api-changes.md, 03-api-versioning-strategies.md)

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

REST 세 단어를 풀면?
자원 자체가 아니라 표현(Representation)을 주고받고, 그 전송이 곧 클라이언트 상태의 전이(State Transfer). 그래서 URI는 명사, 확장자 금지.
네 가지 원칙 축약어?
명·동·결·무 — 명사는 URI, 동사는 메서드, 결과는 상태 코드, 문맥은 기억 안 함(무상태).
멱등의 정확한 기준?
"응답이 같다"가 아니라 "N번 보낸 뒤 서버의 최종 상태가 1번과 같다". DELETE는 204→404여도 멱등.
안전과 멱등의 관계?
안전 ⊂ 멱등. 안전하면 자동으로 멱등, 역은 아니다(DELETE). 안전=GET·HEAD·OPTIONS, 멱등만=PUT·DELETE, 둘 다 아님=POST·PATCH.
상태 코드 여섯 개와 400 vs 409?
200·201·204·400·404·409. 요청을 고쳐야 통과=400, 요청은 그대로여도 상태가 바뀌면 통과=409.
201에 반드시 붙는 헤더?
Location: /orders/42 — 서버가 ID를 발급하므로 클라이언트가 URI를 조립하지 않게 한다.
네이밍 다섯 규칙?
동·복·케·계·확 — 동사 금지 / 복수형 / kebab-case / 계층은 경로 / 확장자 금지. 판단 기준은 "규칙만 알면 추측 가능한가".
깊은 중첩의 비용 셋?
① 필요 없는 조상 ID를 강요 ② 같은 자원에 URI가 두 벌(캐시 키·ETag·권한 코드 분기) ③ 조상 검증 누락 시 접근 제어 취약점.
경로와 쿼리의 경계?
자원의 식별은 경로, 보여주는 방식은 쿼리. /paid-orders가 아니라 /orders?status=PAID.
여섯 제약과 선택 사항?
클·무·캐·계·균·코. 마지막 코드 온 디맨드만 선택. 균일 인터페이스의 하위 규칙 넷 중 셋이 ①②③.
무상태 오해 방지 한 문장?
자원의 상태는 저장(DB), 애플리케이션 상태는 클라이언트가 소지. 저장 금지가 아니라 "대화의 문맥을 메모리에 들고 대기" 금지.
마지막에 반드시 붙일 한 문장?
"원칙 준수보다 전체 API의 일관성이 우선이고, 예외조차 가이드에 명문화해 일관되게 만듭니다."

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

GET으로 삭제하는 API(GET /orders/42/delete)는 뭐가 문제인가요? 필수힌트: "규약 위반이라서"로 끝내지 말고, 사고를 내는 주체가 누구인지 말한다

3절에서 정의한 안전성(safe) 계약을 근거로 답한다. GET은 "몇 번을 호출해도 서버 상태를 바꾸지 않는다"는 약속이고, 브라우저·프록시·CDN·검색엔진 크롤러·프리페치(미리 읽기) 기능이 전부 이 약속을 참으로 믿고 동작한다.

핵심은 "내 코드는 멀쩡한데 인프라가 사고를 낸다"는 구조다

이들은 내 서버 코드를 읽어보지 않았고, 오직 메서드 이름만 보고 판단한다.

마무리 한 문장: "GET 삭제는 문법이 틀린 문제가 아니라, 내가 서명한 계약을 인프라가 믿고 행동한다는 점에서 안전 문제입니다."

무상태(stateless)면 로그인 상태는 어떻게 유지하나요? 필수힌트: "기억하지 않는다"와 "인증하지 않는다"는 다르다
핵심은 "기억하지 않는다"이지 "인증하지 않는다"가 아니다

서버가 세션을 메모리에 들고 있는 대신, 매 요청에 인증 정보를 실어 보내면 된다. 토큰(JWT 등)을 Authorization: Bearer <token> 헤더로 전달하는 방식이 대표적이다.

이 방식이 무상태인 이유는, 토큰 자체에 "누구인지"가 서명과 함께 담겨 있어 서버가 그 요청 하나만 보고 검증을 끝낼 수 있기 때문이다. 이전 요청의 기억도, 다른 서버와의 공유도 필요 없다. 그래서 어느 인스턴스가 받아도 동일하게 처리된다.

절충안 — 세션 저장소를 외부(Redis 등)로 분리

  • 세션이라는 상태 자체는 남지만 애플리케이션 서버는 무상태가 된다
  • 5절의 두 문제(부하 편중, 인스턴스 사망 시 로그아웃)가 사라진다

그 대가

  • 요청마다 Redis 왕복이 추가된다
  • Redis가 새로운 단일 장애 지점이 된다

쿠키·세션·토큰 인증의 비교는 ../08-network-http/07-cookie-session-token-auth.md에서 더 다룬다.

PUT, POST, PATCH는 각각 언제 쓰나요? 필수힌트: 세 문장 뒤에 "선택 기준 한 줄"을 붙인다
POST
컬렉션에 새 자원을 생성(POST /orders). 서버가 ID를 발급하므로 클라이언트는 만들어질 URI를 미리 알 수 없다. 멱등하지 않다 — 두 번 호출하면 주문이 두 건.
PUT
지정한 URI의 자원을 본문 내용으로 전체 교체. 본문에 최종 상태가 통째로 담기므로 몇 번을 반복해도 결과가 같아 멱등.
PATCH
자원의 일부만 수정. 본문에는 바꿀 부분만 담긴다. 규약이 멱등을 보장하지 않는다.
새로 만드는데 주소를 서버가 정하면 POST, 주소가 정해진 자원을 통째로 갈아끼우면 PUT, 그중 일부만 손대면 PATCH

PUT과 PATCH의 자세한 차이와 "안 보낸 필드가 null로 덮이는" 사고는 02-put-vs-patch.md에서 다룬다. 다만 "행위의 의미가 메서드에 실려 있어야 클라이언트와 중간 계층(캐시·게이트웨이·재시도 라이브러리)이 안전하게 동작한다"는 한 줄은 여기서도 그대로 유효하다.

HATEOAS까지 지켜야 진짜 REST 아닌가요? 가산점힌트: "원론적으로는 그렇다"로 시작해 트레이드오프로 끝낸다

원론적으로는 그렇다. HATEOAS(Hypermedia As The Engine Of Application State, 애플리케이션 상태의 엔진으로서의 하이퍼미디어)는 응답에 "지금 이 상태에서 다음에 할 수 있는 행동"의 링크를 담아 클라이언트가 URI를 하드코딩하지 않게 하는 것이다.

응답 링크가 함께 오는 표현
{
  "id": 42, "status": "PAID", "total": 9900,
  "_links": {
    "self":   {"href": "/orders/42"},
    "cancel": {"href": "/orders/42/cancellation", "method": "POST"}
  }
}

핵심은 취소 가능 여부를 클라이언트가 판단하지 않는다는 데 있다. cancel 링크가 응답에 있으면 취소 버튼을 보여주고, 없으면 감춘다. 취소 정책이 바뀌어도(예: 배송 시작 후 취소 불가) 서버만 고치면 되고 앱을 재배포할 필요가 없다.

이 개념은 리처드슨 성숙도 모델(Richardson Maturity Model)의 마지막 단계다. "3단계"라는 말만 던지면 의미가 없으니 전체를 봐야 한다.

현실적인 답 — "소비자를 통제할 수 없는 공개 API처럼 클라이언트를 마음대로 고칠 수 없는 환경이 아니면 비용 대비 효익이 낮다"

반대로 결제 흐름처럼 "지금 어떤 행동이 가능한가"가 상태에 따라 자주 바뀌는 도메인에서는 부분적으로 도입할 값어치가 있다.

REST 원칙을 어겨도 되는 순간은 언제인가요? 시니어 변별힌트: "원칙은 목적을 위한 수단"에서 출발해, 마지막에 반드시 조건을 단다

원칙은 목적(예측 가능성, HTTP 인프라 활용)을 위한 수단이므로, 목적과 충돌하면 원칙이 양보한다. 대표 사례가 셋이다.

1
검색 조건이 너무 길거나 민감할 때. 조회는 GET이 원칙이지만 GET은 조건을 쿼리스트링에 실어야 한다. 그런데 쿼리스트링은 서버·프록시마다 길이 상한이 있어 조건이 수십 개가 되면 잘리고, 무엇보다 접근 로그와 브라우저 히스토리에 그대로 남는다. 그래서 POST /orders/search처럼 조건을 본문에 담는 설계를 택하기도 한다. 대신 POST는 캐시되지 않는다는 대가를 감수하는 것이므로, 그 손해를 알고 고르는 것과 모르고 고르는 것은 다르다.
2
복잡한 상태 전이. CRUD로 억지 매핑하지 말고 9절의 컨트롤 리소스(POST /orders/42/cancellation)를 컨벤션으로 정한다.
3
예외는 팀 가이드에 명문화해 예외조차 일관되게 만든다. 이것이 핵심이다.
"원칙을 아는 사람이 의도적으로, 근거와 함께 문서화하고 어기는 것"과 "몰라서 제각각인 것"은 결과물이 비슷해 보여도 완전히 다르다

전자는 소비자가 예외의 목록을 알 수 있지만, 후자는 소비자가 매번 부딪혀 보고 알아내야 한다.

추가 꼬리질문 — 한 칸씩 더 파고드는 것들

POST /orders를 보냈는데 응답이 안 와서 재시도했더니 주문이 두 건 생겼습니다. 어떻게 막나요? 시니어 변별힌트: POST를 멱등하게 만들 수는 없다. 대신 "중복을 알아볼 수 있게" 만든다

POST 자체를 멱등으로 바꿀 수는 없다 — 규약이 그렇게 정의돼 있고, 클라이언트도 인프라도 POST를 멱등이라고 믿지 않는다. 그래서 방향은 "메서드를 바꾸는 것"이 아니라 "서버가 같은 요청임을 알아볼 수 있게 만드는 것"이다.

널리 쓰이는 관례는 클라이언트가 요청마다 고유한 키를 만들어 헤더로 보내는 것이다(흔히 Idempotency-Key라 부른다). 서버는 그 키를 저장해두고, 같은 키로 다시 들어온 요청은 새로 처리하지 않고 처음 처리 결과를 그대로 돌려준다. 재시도해도 주문은 하나만 생기고, 클라이언트는 첫 응답과 같은 것을 받는다.

키를 만드는 주체가 클라이언트인 이유

  • 재시도는 클라이언트가 하는 행동이므로, "이 재시도가 어느 원래 요청의 반복인지"를 아는 것도 클라이언트뿐이다
  • 서버가 본문 해시로 판별하면 "진짜로 똑같은 주문을 두 번 하려는 경우"와 구분할 수 없다

REST 원칙과의 관계

  • 이것은 원칙 위반이 아니라 보완이다 — 메서드의 계약은 그대로 두고, 애플리케이션 층에서 중복 처리를 막는다
  • PUT·DELETE는 이런 장치가 필요 없다. 규약이 이미 멱등을 보장하기 때문이다 — 이것이 멱등성의 실용적 가치다

덧붙이면 좋은 한 줄: "멱등성이 왜 중요하냐"의 답이 바로 이 장면입니다 — 네트워크는 언제든 응답을 잃어버리므로, 멱등하지 않은 연산은 반드시 별도의 중복 방지 장치를 요구합니다."

복수형 대신 단수형(/user/42)을 쓰는 API도 많던데, 틀린 건가요?힌트: 이 문서 전체의 주제를 그대로 적용하면 된다

단수형 자체가 틀린 것은 아니다. 복수형이 널리 권장되는 이유는 "컬렉션 / 컬렉션의 원소"라는 하나의 문법으로 이어지기 때문이지, 문법적으로 단수가 오류이기 때문이 아니다.

진짜 문제는 단수냐 복수냐가 아니라 "섞여 있는 것"이다

/users/42와 /order/42가 한 서비스에 공존하면, 클라이언트는 엔드포인트마다 문서를 확인해야 한다. 반대로 전부 단수로 통일된 API는 어색해 보여도 예측 가능하다.

그래서 답은 이렇게 낸다 — "새로 설계한다면 컬렉션 문법이 이어지는 복수형을 택하겠습니다. 다만 이미 단수형으로 통일된 API가 있다면 그걸 바꾸는 것이 계약 파기이므로, 가이드에 단수형을 명문화하고 일관성을 유지하는 편이 낫습니다." (참고: 단수/복수 구분이 없는 명사 /settings나 단일 인스턴스 자원 /me처럼, 애초에 컬렉션이 아닌 자원은 예외로 다루고 그 예외 기준도 가이드에 적는다.)

남의 주문을 조회했습니다. 403을 줘야 하나요, 404를 줘야 하나요? 함정힌트: 상태 코드가 정보를 흘릴 수 있다

8절에서 본 조상 검증의 연장선이다. 검증 자체는 반드시 해야 하는데, 실패했을 때 무엇을 돌려주느냐가 갈린다.

403 Forbidden을 주면

  • 의미상 정확하다 — "자원은 있지만 당신은 권한이 없다"
  • 대신 "그 ID의 주문이 존재한다"는 사실을 알려준다
  • ID를 순회하며 403/404를 세면 주문 건수·ID 체계를 추측할 수 있다

404 Not Found를 주면

  • 존재 여부 자체를 감춘다 — 남의 자원은 "없는 것"으로 보인다
  • 민감한 도메인(주문·결제·의료)에서 흔히 택하는 쪽
  • 대신 디버깅이 어렵다 — 진짜 없는 건지 권한이 없는 건지 로그를 봐야 안다
정답이 하나로 정해지지 않는다 — "존재 여부가 노출돼도 되는 자원인가"로 팀이 정하고, 그 기준을 가이드에 적어 전 엔드포인트에 똑같이 적용한다

이 답변의 값은 "둘 중 하나를 고르는 것"이 아니라 "고르는 기준을 세우고 일관되게 적용한다"는 데 있다. 10절의 주제가 그대로 반복된다. (401/403의 구분은 ../08-network-http/05-http-status-codes-usage-criteria.md)

조회 조건이 복잡하면 GET에 요청 본문(body)을 실으면 되지 않나요?힌트: "금지"가 아니라 "의미가 정의되지 않았다"가 정확하다

권장되지 않는다. 이유는 "금지돼 있어서"가 아니라 GET 요청의 본문에 어떤 의미가 있는지를 명세가 정의하지 않기 때문이다. 의미가 정의되지 않으면 구현마다 처리가 갈린다 — 어떤 중간 계층은 본문을 그냥 버리고, 어떤 클라이언트 라이브러리는 GET에 본문을 실을 수단 자체를 제공하지 않는다.

더 실질적인 문제는 캐시다. HTTP 캐시는 메서드와 URI를 키로 저장하므로, 본문에 조건을 담으면 조건이 달라도 캐시 키가 같아진다. 즉 다른 조건의 검색에 남의 결과가 돌아올 수 있다.

그래서 실무의 선택은 둘 — ① 조건을 쿼리스트링에 담고 길이·민감도를 관리하거나, ② POST /orders/search로 명시적으로 내려간다

②를 고를 때 반드시 붙일 문장: "POST로 내려가면 캐시를 포기하는 것이므로, 조회 빈도가 높은 경로에는 쓰지 않고 검색 전용 엔드포인트로 격리합니다."

여러 자원에 걸친 작업(장바구니 담긴 상품을 한 번에 주문)은 URI를 어떻게 짓나요?힌트: "그 작업 자체를 하나의 자원으로 볼 수 있는가"를 먼저 묻는다

먼저 "이 작업의 결과로 무엇이 생기는가"를 묻는다. 대개 결과물이 곧 자원이다.

결과물이 자원인 경우
"장바구니를 주문으로 바꾼다"의 결과는 주문 한 건이다 → POST /orders에 장바구니 ID를 본문으로 넘긴다. 여러 자원을 건드리는 것은 서버 내부 사정일 뿐, 소비자가 보는 것은 "주문이 생겼다"이다.
결과물이 자원이 아닌 경우
"여러 항목을 한꺼번에 상태 변경"처럼 남는 것이 없다면, 9절의 컨트롤 리소스를 만든다 — 그 작업 자체를 명사로 만들어 POST /orders/bulk-cancellation 같은 자원으로 다룬다.

피해야 할 것은 POST /processCartToOrder처럼 동사 문장을 URI에 통째로 넣는 것이다. 그 순간 규칙이 깨지고, 비슷한 작업이 생길 때마다 이름 짓는 방식이 사람마다 달라진다.

한 줄 요약
REST는 자원의 표현(JSON 등)을 주고받아 클라이언트의 상태를 전이시키는 스타일이므로 URI에는 명사(복수형)를, 행위에는 안전성·멱등성 계약이 붙은 HTTP 메서드를, 결과에는 상태 코드를 쓰고 서버는 요청 사이의 문맥을 기억하지 않는다(무상태) — 그러나 원칙의 진짜 가치는 규칙 자체가 아니라 일관성이 만들어내는 예측 가능성에 있으므로, API가 장기 계약임을 전제로 "원칙 준수"보다 "팀 전체 API의 일관성"을 우선하고 예외조차 문서화해 일관되게 만드는 것이 소비자를 위한 설계다.
