AI 생성 이체 코드의 머지 전 검증
"테스트 전부 통과"는 행복 경로의 증명일 뿐이다

면접 질문: "AI가 생성한 '포인트 이체' 코드가 테스트를 전부 통과했습니다. 머지 전에 무엇을 어떤 순서로 검증하나요?"

핵심 관전 포인트 — "테스트 전부 통과"는 "작성자가 상상한 시나리오 안에서는 맞다"는 뜻이지 검증이 아니다. AI가 생성한 테스트는 행복 경로(happy path)에 편향돼 있고, 테스트까지 같은 AI가 짰다면 구현이 놓친 맹점을 테스트도 똑같이 놓친다. 돈이 움직이는 코드의 사고는 대부분 동시 실행 · 부분 실패 · 중복 요청에서 나는데, 이 셋은 단일 스레드로 도는 보통의 테스트에 구조적으로 담기지 않는다. 그래서 검증 순서는 (1) 동시성 — 같은 계좌 동시 이체 시 잔액 음수·갱신 유실 가능성, 락 또는 조건부 UPDATE 확인 (2) 트랜잭션 경계 — 차감과 지급이 한 트랜잭션인지, 외부 호출이 트랜잭션 안에 있는지 (3) 멱등성 — 재시도 시 이중 이체 (4) 예외 경로 — 부분 실패 시 상태 (5) 금액 타입과 도메인 검증(음수 이체, 자기 이체) 순이다. 피해가 크고 테스트로 안 잡히는 것부터 본다.
  • 1
    "통과"가 증명하는 범위부터 좁힌다 — 테스트 통과는 "테스트에 적힌 시나리오 안에서 맞다"는 뜻뿐이다. AI 테스트는 정상 이체·잔액 부족·계좌 없음 같은 행복 경로 변주에 몰리고, 더 나쁜 것은 구현과 테스트의 출처가 같으면 맹점까지 공유한다는 점이다. 답안지를 쓴 사람이 채점 기준표까지 쓴 시험이라 100점이 나와도 의미가 없다.
  • 2
    그래서 "테스트에 원천적으로 없는 축"을 찾는다 — 돈 사고는 기능이 틀려서가 아니라 조건이 겹쳐서 난다. 동시 실행 · 부분 실패 · 중복 요청 이 셋은 단일 스레드 · 1회 실행 · 정상 종료를 전제한 테스트에 구조적으로 담기지 않는다. 테스트를 아무리 늘려도 이 축의 커버리지는 영원히 0이다.
  • 3
    순서는 "피해 크기 × 테스트로 안 잡히는 정도"로 정렬한다 — 동시성 → 트랜잭션 경계 → 멱등성 → 예외 경로 → 금액 검증 순으로 본다. 그리고 발견한 결함은 리뷰 코멘트로 끝내지 않는다 — CountDownLatch 동시성 테스트와 DB 제약(CHECK·유니크)으로 재발이 불가능하게 박아 넣은 뒤 머지한다.

0. 질문 + 출제 의도

질문: "AI가 생성한 '포인트 이체' 코드가 테스트를 전부 통과했습니다. 머지 전에 무엇을 어떤 순서로 검증하나요?"

출제 의도: AI 산출물 검증 역량을 돈 도메인에서 시뮬레이션하는 질문이다. "테스트 통과"가 왜 검증이 아닌지(동시 실행·부분 실패·중복 요청은 보통 테스트에 없다)를 알고, 동시성 → 트랜잭션 경계 → 멱등성 → 예외 경로 순의 검증 우선순위를 갖고 있는지 — AI 시대 리뷰어의 실전 역량을 돈이 걸린 상황으로 압박해 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "테스트 초록불 = 검증 완료"라는 반사 → 2절에서 행복 경로 편향과 구현·테스트의 맹점 공유를 나눠 보이고, 커버리지 숫자가 왜 이 축에서 무의미한지까지 붙인다.
② "뭘 볼지"는 말해도 "왜 그 순서인지"를 못 대는 것 → 3절에서 피해 크기 × 테스트로 안 잡히는 정도라는 정렬 기준을 도식으로 세운다. 순서에 근거가 있으면 항목을 하나 잊어도 다시 유도할 수 있다.
③ 결함을 "코멘트"로만 지적하고 끝내는 것 → 10절에서 CountDownLatch + Testcontainers 재현 테스트, 마지막 꼬리질문에서 PR 템플릿 · ArchUnit · DB 제약으로 개인기를 절차로 바꾸는 답을 만든다.

1. 먼저 용어 셋 — 혼자 돌릴 때는 절대 안 보이는 개념들

이 문서 전체가 이 세 단어 위에 서 있다. 셋 다 "테스트를 한 번 돌려볼 때는 존재하지 않는 것처럼 보인다"는 공통점이 있어서, 정의를 정확히 잡고 시작해야 한다.

행복 경로 (happy path)
모든 것이 예상대로 흘러가는 실행 경로. 입력이 유효하고, 네트워크가 안 끊기고, 요청이 한 번만 오고, 다른 사용자가 같은 데이터를 안 건드리는 경우다. "행복"이라는 이름이 붙은 이유는 개발자가 기능을 만들 때 머릿속에 그리는 그림이 대개 이것뿐이기 때문이다. 그리고 장애는 여기서 나지 않는다.
인터리빙 (interleaving)
동시 실행은 두 요청이 "정확히 같은 순간"에 실행된다는 뜻이 아니다. 요청 A가 조회 → 계산 → 저장으로 이뤄져 있을 때 그 단계들 사이사이에 요청 B의 단계가 끼어드는 것 — 이 끼어듦이 인터리빙이다. 요청마다 스레드를 쓰는 서버에서 인터리빙은 예외가 아니라 기본 상태다.
원자적 (atomic)
"쪼갤 수 없다"는 뜻. 어떤 연산이 원자적이면 밖에서 볼 때 완전히 끝난 상태이거나 아예 시작도 안 한 상태 둘로만 관찰된다. 중간 상태가 안 보이니 그 한가운데로는 인터리빙이 끼어들 수 없다. 동시성 문제를 푸는 방법은 결국 하나 — 쪼개져 있어 끼어들 수 있던 것을 원자적으로 만드는 것이다.

세 단어를 한 줄로 잇는다

테스트는 행복 경로만 보고 → 사고는 인터리빙에서 나며 → 해법은 언제나 원자적으로 만들기 하나다

2. "테스트 통과"가 검증이 아닌 두 가지 이유

2-1. 이유 ① AI 테스트는 행복 경로에 편향된다

AI에게 "포인트 이체 기능을 만들고 테스트도 작성해줘"라고 하면 보통 이런 테스트가 나온다 — 정상 이체 성공, 잔액 부족 시 예외, 존재하지 않는 계좌 예외. 셋 다 훌륭한 테스트지만 공통점이 하나 있다. 전부 한 스레드에서, 한 번씩, 순서대로 실행되는 시나리오다. 즉 인터리빙이 하나도 없다.

2-2. 이유 ② 구현과 테스트가 같은 맹점을 공유한다

더 근본적인 문제는 검증의 독립성이다. 검증이란 "만든 것"을 "만든 것과 무관한 기준"에 비춰보는 행위인데, 구현과 테스트를 같은 모델이 같은 문맥에서 생성했다면 그 무관함이 사라진다. 구현이 요구사항을 잘못 이해했다면 같은 문맥에서 나온 테스트도 같은 오해를 기준으로 만들어진다.

리뷰어의 질문을 바꾸는 한 문장

"코드가 테스트를 통과했는가"가 아니라 "테스트에 없는 시나리오 중 돈이 새는 것이 있는가"

3. 검증 순서를 정렬하는 기준 — 순서 자체가 답이다

면접에서 항목 다섯 개를 나열하는 것보다 "왜 이 순서인가"를 한 문장으로 대는 쪽이 훨씬 강하다. 정렬 기준은 하나다 — 피해 크기 × 테스트로 안 잡히는 정도. 이 기준이 있으면 항목 하나를 잊어도 다시 유도해 낼 수 있다.

다섯 단계 두문자 — 동 · 경 · 멱 · 예 · 금

"동경에서 멱살 잡고 예금한다"
동시성→ 트랜잭션 경계→ 멱등성→ 예외 경로→ 금액 검증

순서를 외우는 것보다 정렬 기준(피해 × 안 잡힘)을 외우는 쪽이 안전하다. 기준만 있으면 항목을 잊어도 그 자리에서 다시 만들어낼 수 있다.

4. 1순위 동시성 — check-then-act를 찾아라

4-1. 결함의 이름부터

AI가 이체 코드에서 가장 흔히 내는 결함이 검사 후 실행(check-then-act) 패턴이다. 이름 그대로 "검사(check)한 결과를 믿고 실행(act)한다"는 구조다. 조회한 잔액으로 검사하고, 조회한 그 값으로 계산해서 저장한다.

위험한 것은 검사 자체가 아니라 검사와 실행 사이의 시간이다

그 사이에 다른 트랜잭션이 같은 데이터를 바꿔버리면, 검사 결과는 이미 과거의 사실이 되는데 실행은 그 과거를 근거로 진행된다.

before AI가 낸 전형적 결함 — 단일 실행에선 완벽해 보인다
@Transactional
public void transfer(Long fromId, Long toId, long amount) {
    Account from = accountRepository.findById(fromId).orElseThrow();
    Account to   = accountRepository.findById(toId).orElseThrow();

    // ① 검사: 이 시점의 balance는 "방금 읽어온 값"이지 "지금 DB의 값"이 아니다.
    //    평범한 SELECT는 행에 락을 걸지 않으므로, 읽은 직후부터 이 값은 낡을 수 있다.
    if (from.getBalance() < amount) {          check        throw new InsufficientBalanceException();
    }

    // ② 실행: DB에게 "빼라"가 아니라 "2,000으로 만들어라"라고 지시하는 것과 같다.
    //    최종 값을 자바가 미리 확정해버려서, DB는 그 사이 무슨 일이 있었는지 알 수 없다.
    from.setBalance(from.getBalance() - amount);   act    to.setBalance(to.getBalance() + amount);       act}

4-2. 시간축으로 펼쳐 보기 — 갱신 유실이 만들어지는 과정

말로는 잘 안 와닿으니, 잔액 10,000원 계좌 A에서 8,000원 이체 요청 두 건이 겹쳤을 때 실제로 무슨 일이 벌어지는지 시간 순서대로 늘어놓는다. T1과 T2는 각각 다른 요청을 처리하는 스레드이자 트랜잭션이다.

t8에서 T2가 "대기했다"는 사실이 함정이다

락 때문에 순서가 지켜졌으니 안전할 것 같지만, T2가 쓰려는 값 2000은 t6에 자바 메모리에서 이미 확정된 숫자다. T2는 깨어나서 다시 계산하지 않는다. 낡은 숫자를 그대로 덮어쓴다.

먼저 커밋된 갱신이 나중 갱신에 덮여 사라지는 현상 = 갱신 유실(lost update)

4-3. 얼마가 새는가 — 합계로 검산한다

돈 시스템의 검산은 항상 "시스템 전체 잔액의 합"으로 한다. 이체는 돈을 옮길 뿐 만들거나 없애지 않으므로, 이체 전후의 총합은 반드시 같아야 한다. 이것이 이 도메인의 불변식(invariant, 언제나 참이어야 하는 조건)이다.

같은 계좌 A에서 8,000원 이체 2건이 동시에 들어왔을 때
계좌이체 전정상 동작(1건만 성공)실제(갱신 유실)
A (출금)10,0002,0002,000
B (수취)08,0008,000
C (수취)008,000
합계10,00010,00018,000
이 8,000은 누구의 돈인가 총합이 10,000에서 18,000으로 늘었다. 8,000포인트가 무에서 생겼다. 회사 장부에서 이 8,000은 누구도 지불하지 않은 부채이고, 결국 회사가 물어낸다.
수취인이 같으면(더블 클릭) 증상이 반대로 나타난다 위 코드는 지급 쪽도 to.getBalance() + amount라는 똑같은 check-then-act다. 그래서 B의 잔액도 양쪽이 0을 읽고 둘 다 8,000을 써서 B는 8,000만 받는다. 합계는 우연히 맞지만 두 번째 이체가 통째로 증발한 것이고, 사용자에게는 "두 번 보냈는데 상대는 한 번만 받았다"로 나타난다. — 같은 결함이 계좌 조합에 따라 돈을 만들기도 하고 없애기도 한다.

4-4. @Transactional을 붙였는데 왜 안 막히나

주니어가 가장 많이 하는 오해가 여기다. @Transactional은 원자성(전부 커밋되거나 전부 롤백되거나)과 격리 수준에 따른 읽기 규칙을 주는 것이지, "내가 읽은 값이 커밋할 때까지 그대로일 것"을 보장하지 않는다.

오해 ① "격리 수준이 지켜주겠지"

  • PostgreSQL 기본 격리 수준은 READ COMMITTED
  • 이 수준의 약속은 딱 하나 — "커밋되지 않은 남의 변경은 안 보여준다"
  • t1·t2의 SELECT는 둘 다 커밋된 값 10,000을 읽었으니 규칙을 하나도 어기지 않았다
  • 즉 격리 수준은 읽기의 규칙이지 쓰기 순서의 보호가 아니다

오해 ② "어차피 락이 걸리잖아"

  • 평범한 SELECT는 행에 락을 걸지 않는다
  • 락은 UPDATE가 실행되는 t7·t8에 가서야 잡힌다
  • 그때는 이미 값이 정해진 뒤다
  • → 락이 필요한 구간과 락이 걸리는 구간이 어긋나 있다

리뷰어가 눈으로 찾는 시그니처 — 이것만 외우면 대부분 걸린다

① 조회 → if 검사 → 조회값 산술 → set
가장 전형적인 check-then-act. 이체·결제·정산 코드에서 제일 먼저 스캔한다.
② 공유되는 숫자를 읽어서 계산 후 쓰는 모든 지점
잔액 · 재고 · 쿠폰 수량 · 좌석 수. 이름만 다를 뿐 전부 같은 결함이다.
③ existsBy… 검사 후 save
유니크 제약 없는 중복 검사 — 멱등성 결함과 같은 뿌리(7절).
④ 두 자원을 잠그는데 순서 규칙이 없다
교착(deadlock) 후보. "잠그는 순서가 전역적으로 일정한가"를 묻는다(11절 사례 3).
이 지점마다 던지는 질문은 하나 — "이 두 줄 사이에 다른 트랜잭션이 끼면?" 코드가 답하지 못하면 결함이다

5. 해법 — 검사와 실행을 DB 안에서 한 문장으로 합친다

끼어들 틈을 없애는 방법은 "검사와 실행 사이의 시간"을 0으로 만드는 것이다. 자바에서 값을 계산해 내려보내는 대신, 조건과 연산을 통째로 DB에 넘겨 한 문장으로 실행시킨다.

after 검사·차감을 DB가 원자적으로 수행하는 조건부 UPDATE

이제 앞의 시간축을 다시 그려보면 t3~t6이 통째로 사라진다. 자바에서 값을 굳히는 단계가 아예 없기 때문이다.

t4에서 실제로 일어나는 일 PostgreSQL은 READ COMMITTED에서 UPDATE가 잠긴 행을 만나면, 락이 풀린 뒤 가장 최근 커밋된 버전으로 WHERE 조건을 다시 평가한다(내부적으로 EvaluatePlanQual이라 부르는 동작이다). 자바 변수에 박아둔 낡은 값과 달리, WHERE 절의 balance는 대기가 끝난 시점에 새로 읽힌다.

이 한 줄로 구조가 바뀐다

조건부 UPDATE는 "검사 후 실행(check-then-act)"이 아니라 "실행하면서 검사(act-and-check)"다

그래서 판단 근거도 바뀐다 — 조회한 잔액이 아니라 영향 행 수가 진실이다. 1 = 내가 차감했다, 0 = 조건이 거짓이었다.

5-1. 대안 두 가지와 마지막 방어선

같은 문제를 푸는 세 가지 방식 + 층이 다른 하나 — 서로 다른 가정 위에 서 있다
방식깔고 있는 가정검사가 일어나는 위치락을 쥐는 시간계좌 잔액에반드시 따라오는 주의점
조건부 UPDATE
기본기		충돌 여부와 무관하게 검사와 실행을 붙여버린다DB의 WHERE 절SQL 한 문장 실행 시간적합 — 기본으로 고른다도메인 로직이 SQL로 새어나가고 JPA 더티 체킹과 결이 안 맞는다 → 잔액 같은 핵심 불변식만 @Modifying으로 내리고 나머지는 평범한 엔티티로
비관적 락
pessimistic		"충돌이 날 것"이라 비관적으로 가정하고 미리 잠근다자바 코드 (락 안에서 안전)조회 시점부터 커밋까지여러 행을 함께 잠그고 복잡한 검증을 해야 할 때락 획득 순서를 계좌 id 오름차순으로 정렬하지 않으면 교착(deadlock). 락 구간에 외부 API 호출을 넣지 않는다
낙관적 락
optimistic		"충돌은 드물 것"이라 낙관적으로 가정하고 잠그지 않는다UPDATE의 WHERE version = ?사실상 없음부적합 — 3순위 꼬리질문 참고충돌 시 예외 → 호출자가 재시도. 충돌이 잦으면 재시도가 또 충돌해 처리량이 무너진다
DB CHECK 제약
층이 다르다		위 셋 중 무엇이든 뚫릴 수 있다고 가정한다DB 엔진(커밋 시점)—항상 함께 건다대안이 아니라 마지막 층. CHECK (balance >= 0)는 운영자가 콘솔에서 직접 UPDATE를 날려도 음수 커밋을 불가능하게 만든다

비관적 락을 쓴다면 반드시 붙는 규칙

두 자원을 잠글 때는 항상 계좌 id 오름차순으로 잠근다

A→B 이체와 B→A 이체가 동시에 오면 T1은 A를 잡고 B를 기다리고, T2는 B를 잡고 A를 기다려 영원히 서로를 기다린다(교착, deadlock). "항상 작은 id부터 잠근다"는 전역 규칙을 두면 두 트랜잭션 모두 A를 먼저 노리므로 순환이 생길 수 없다 — 한쪽은 그냥 기다리다 순서대로 진행된다.

어떤 방식을 고르든 마지막 한 줄 PostgreSQL에 CHECK (balance >= 0)를 걸어둔다. 애플리케이션의 어떤 경로가 뚫려도, 심지어 운영자가 콘솔에서 직접 UPDATE를 날려도 음수 잔액은 커밋 자체가 불가능해진다. 코드 리뷰가 실패했을 때를 위한 층이다.

6. 2순위 트랜잭션 경계 — 차감과 지급은 한 몸인가

트랜잭션 경계란 "어디서부터 어디까지가 전부 성공하거나 전부 실패하는 한 덩어리인가"를 가리키는 말이다. 이체에서 이 경계가 잘못 그어지면, 차감은 됐는데 지급은 안 된 상태가 정상 종료로 남는다.

6-1. 자기 호출(self-invocation) 함정 — 애노테이션이 있어도 트랜잭션이 안 열린다

스프링의 @Transactional은 원본 객체를 감싼 프록시(proxy, 대리 객체)가 메서드 진입 시 트랜잭션을 열어주는 방식으로 동작한다. 그런데 같은 클래스 안에서 this.withdraw()를 부르면 프록시를 거치지 않고 원본 객체의 메서드로 곧장 들어간다.

before 컴파일 오류도 경고도 없다 — 눈으로만 잡힌다
@Service
public class TransferService {

    // 트랜잭션이 없는 메서드

    @Transactional   // ← 내부 호출에서는 무시된다
    public void withdraw(Long id, long amount) { ... }

    @Transactional
    public void deposit(Long id, long amount) { ... }
}

트랜잭션 경계에서 던지는 세 가지 질문

① 한 몸인가
차감과 지급이 같은 @Transactional 안인가. REQUIRES_NEW·이벤트로 쪼개진 순간 부분 실패 창이 열린다.
② 프록시를 거치는가
this.메서드() 자기 호출은 애노테이션이 있어도 트랜잭션이 안 열린다. 조용히 실패하는 유형.
③ 안에 외부 호출이 있는가
HTTP·메시지 발행이 트랜잭션 안이면 커넥션·락 점유 + 유령 알림 두 피해가 동시에 난다.

7. 3순위 멱등성 — 같은 요청이 두 번 오면?

멱등성(idempotency)은 "같은 연산을 몇 번 반복해도 결과가 한 번 실행한 것과 같다"는 성질이다. 수학에서 온 말인데(1을 몇 번 곱해도 그대로다), 분산 시스템에서 중요한 이유는 네트워크가 "실패"와 "응답 유실"을 구분해주지 않기 때문이다.

앞의 조건부 UPDATE 코드도 여기서는 무력하다 클라이언트 타임아웃 후 재시도나 더블 클릭으로 같은 이체 요청이 두 번 도착하면, 5절의 코드는 두 번 다 정상적으로 성공한다. 잔액도 충분하고 검사도 통과하니 시스템 입장에서는 서로 다른 두 건의 정당한 이체다. 8,000원 이체가 16,000원 이체가 된다.
before 서버 생성 id + exists 검사

    Long id = idGenerator.next();                   매번 새 id

멱등성 리뷰에서 확인할 것은 딱 두 가지

① 키를 누가 만드는가
클라이언트가 만든 식별자(transferId / HTTP 헤더 Idempotency-Key)가 있는가. 서버가 만든 id는 요청마다 새로 생기므로 재시도를 구분할 수 없다. 재시도임을 아는 쪽은 클라이언트뿐이라 클라이언트가 만들어야 한다.
② 그 키에 유니크 제약이 있는가
if (exists(...)) return;은 4절과 같은 check-then-act라 동시에 오면 둘 다 통과한다. 유니크 제약을 걸고 INSERT를 먼저 시도하면 DB가 두 번째를 원자적으로 거부한다.
검사가 아니라 유니크 제약에 의한 원자적 선점 — 이 한 문장이 멱등성 설계의 전부다

상세 설계는 멱등성 키 문서(09-rest-api/06)와 같다.

8. 4순위 예외 경로 — 실패의 모양을 확인한다

지금까지가 "성공이 잘못되는" 경로였다면, 여기는 "실패가 잘못되는" 경로다.

8-1. 체크 예외에서는 롤백이 안 된다

자바 예외 두 종류와 스프링의 기본 롤백 규칙
구분정의@Transactional 기본 동작이체 코드에서의 결과
언체크 예외RuntimeException을 상속. 컴파일러가 처리를 강제하지 않는다롤백한다차감·지급 모두 되돌아간다 (정상)
체크 예외Exception을 직접 상속. throws나 try-catch를 강제한다롤백하지 않고 그대로 커밋한다차감만 커밋되고 지급은 안 된 상태가 정상 종료로 남는다

스프링은 체크 예외를 "예상된 업무 흐름"으로 간주하기 때문에 이런 기본값을 갖는다. AI 코드의 단골 함정이다.

10. 결함을 테스트로 박는다 — CountDownLatch

리뷰 코멘트로 끝내면 다음 사람이 같은 코드를 다시 쓴다. 결함은 재현하는 테스트를 머지 조건으로 걸어야 재발이 막힌다.

문제는 동시성 테스트가 잘 실패하지 않는다는 데 있다. 스레드 두 개를 그냥 띄우면 첫 번째가 시작해서 끝날 때까지 두 번째가 준비도 못 끝내는 일이 흔해서, 정작 겹쳐야 할 구간이 안 겹친다. 그래서 두 스레드를 출발선에 세워놓고 동시에 출발시키는 장치가 필요하다.

test 결함을 재현해 머지 조건으로 거는 동시성 테스트
@Test
void 잔액_1만원_계좌에_8천원_동시_이체_2건은_1건만_성공한다()
        throws Exception {
    int threads = 2;
    ExecutorService pool = Executors.newFixedThreadPool(threads);

    CountDownLatch ready = new CountDownLatch(threads); // 2가 0이 되면 전원 준비 완료
    CountDownLatch start = new CountDownLatch(1);       // 1이 0이 되면 출발 총성
    CountDownLatch done  = new CountDownLatch(threads); // 2가 0이 되면 전원 종료
    AtomicInteger success = new AtomicInteger();        // 여러 스레드가 함께 세므로 원자적 카운터

    for (int i = 0; i < threads; i++) {
        pool.submit(() -> {
            try {
                ready.countDown();   // "나 준비됐다"
                start.await();       이 줄이 겹침을 만든다                transferService.transfer(FROM, TO, 8_000L);
                success.incrementAndGet();
            } catch (InsufficientBalanceException expected) {
                // 잔액 부족 실패는 기대한 결과다. 성공 카운트만 올리지 않는다.
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();   // 인터럽트 상태 복원
            } finally {
                done.countDown();    // 성공이든 실패든 반드시 내려야 본 스레드가 안 멈춘다
            }
        });
    }
    ready.await();       // 두 스레드가 출발선에 설 때까지 기다린다
    start.countDown();   // 총성 — 여기서 두 스레드가 거의 같은 순간 transfer()에 진입한다
    done.await();        // 둘 다 끝날 때까지 기다린 뒤 검증한다

    assertThat(success.get()).isEqualTo(1);          두 건 중 정확히 한 건    assertThat(balanceOf(FROM)).isEqualTo(2_000L);   // 10,000 - 8,000
    assertThat(balanceOf(TO)).isEqualTo(8_000L);     16,000이면 갱신 유실}

이 테스트는 실제 PostgreSQL 위에서 돌려야 한다

H2 같은 인메모리 DB

  • 편하지만 락 동작과 격리 수준의 세부 구현이 PostgreSQL과 다르다
  • 결함이 재현되지 않은 채 초록불이 날 수 있다
  • 그러면 이 테스트는 안전하다는 착각만 늘린다 — 없느니만 못하다

Testcontainers

  • 테스트 실행 시 도커로 진짜 DB 컨테이너를 띄웠다가 끝나면 지우는 라이브러리
  • 운영과 같은 PostgreSQL 버전을 띄우는 것이 정석
  • 락·격리 수준 동작이 운영과 같아야 테스트가 증거가 된다
다섯 단계를 팀의 돈 코드 리뷰 체크리스트로 고정하면, AI 산출물 리뷰가 사람의 감이 아니라 재현 가능한 절차가 된다

11. 실무 사례 — 테스트 전부 통과 후에 터지는 방식

11-1. 사례 1 — 프로모션 트래픽에서 드러난 갱신 유실

포인트 선물하기 기능을 AI로 생성해 배포했다. 테스트 34건 전부 통과, 스테이징 QA도 통과했다. 스테이징이 통과한 이유는 명확했다 — 거기엔 동시 요청이 없었다. QA 담당자 한 명이 순서대로 눌러보는 환경에서 인터리빙은 발생하지 않는다.

이벤트 당일, 잔액 10,000포인트 계좌에서 더블 클릭으로 8,000포인트 선물 요청 2건이 30ms 간격으로 도착했다. 두 트랜잭션 모두 잔액 검사를 통과했다. 이 시스템은 차감만 check-then-act였고 지급은 balance = balance + :amount 증분 UPDATE였던 탓에, 지급 두 건은 모두 반영되고 차감 한 건만 사라졌다.

항목이벤트 전정상이었다면실제
보내는 계좌10,0002,0002,000
받는 계좌08,00016,000

11-2. 사례 2 — 트랜잭션 안의 알림 호출이 이체 전체를 세웠다

AI가 생성한 코드는 이체 커밋 전에 알림 API를 호출했다. 평소엔 응답이 50ms라 아무도 문제를 못 느꼈다.

피해 ① 외부사 장애가 코어 이체 장애로 전파

  • 알림사 장애로 응답이 5초로 늘어난 날
  • 각 이체 트랜잭션이 5초씩 DB 커넥션과 계좌 행 락을 붙잡았다
  • 트랜잭션이 열려 있는 동안 커넥션은 반납되지 않는다 → 기본 10개짜리 풀이 곧바로 고갈
  • 알림과 아무 관련 없는 이체 요청까지 전부 타임아웃

피해 ② 유령 알림

  • 타임아웃으로 롤백된 이체들에서도 알림은 이미 나간 뒤였다
  • 고객은 "8,000포인트 이체 완료" 알림을 받았는데 포인트는 안 들어왔다
  • CS가 함께 터졌다
알림을 AFTER_COMMIT 이벤트로 빼는 한 줄 리뷰로 둘 다 막을 수 있었던 장애다

11-3. 사례 3 — 맞이체 교착, PostgreSQL이 한쪽을 강제 롤백

동시성 결함을 고치면서 비관적 락으로 바꿨는데, 락 획득 순서를 정하지 않았다. A→B 8,000원 이체와 B→A 5,000원 이체가 동시에 실행됐다.

사례 3 이후 체크리스트에 추가된 항목

"두 자원을 잠그는 코드는 잠그는 순서가 전역적으로 일정한가"

두 트랜잭션 모두 작은 id를 먼저 노리므로 t1에서 한쪽이 이기고 다른 쪽은 처음부터 기다린다 — 순환이 만들어질 수 없으니 교착이 발생 자체를 안 한다. "탐지 후 재시도"가 아니라 "발생 불가능하게 설계"라는 점이 중요하다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 답을 먼저 떠올리고 오른쪽을 본다

"테스트 통과"가 증명하는 것은?
"작성자가 상상한 시나리오 안에서는 맞다"는 것뿐. 게다가 구현과 테스트의 출처가 같으면 맹점까지 공유한다 — 답안지를 쓴 사람이 채점 기준표까지 쓴 시험.
테스트에 원천적으로 없는 세 축은?
동시 실행 · 부분 실패 · 중복 요청. 단일 스레드 · 1회 실행 · 정상 종료를 전제하므로 이 축의 커버리지는 영원히 0이다.
검증 5단계와 정렬 기준은?
동 · 경 · 멱 · 예 · 금("동경에서 멱살 잡고 예금한다"). 기준은 피해 크기 × 테스트로 안 잡히는 정도.
check-then-act가 위험한 이유 한 줄?
검사 자체가 아니라 검사와 실행 사이의 시간이 위험하다. 검사 결과는 과거의 사실이 되는데 실행은 그 과거를 근거로 진행된다.
돈 시스템의 검산법은?
시스템 전체 잔액의 합. 이체는 옮길 뿐 만들거나 없애지 않으므로 전후 총합이 같아야 한다(불변식). 10,000 → 18,000이면 없는 돈이 발행된 것.
@Transactional이 못 막는 것은?
"내가 읽은 값이 커밋할 때까지 그대로일 것"은 보장하지 않는다. 격리 수준은 읽기의 규칙이지 쓰기 순서의 보호가 아니다.
조건부 UPDATE의 판단 근거는?
조회한 잔액이 아니라 영향 행 수. 1 = 내가 차감했다 / 0 = 조건이 거짓이었다(잔액 부족). "실행하면서 검사."
비관적 락에 반드시 붙는 규칙?
항상 계좌 id 오름차순으로 잠근다. 순환이 만들어질 수 없으니 교착이 발생 자체를 안 한다.
멱등성 두 조건?
① 클라이언트가 만든 키(재시도임을 아는 쪽은 클라이언트뿐) ② 그 키의 유니크 제약. 검사가 아니라 원자적 선점.
체크 예외의 함정?
스프링은 언체크 예외에서만 롤백한다. 체크 예외는 그대로 커밋 → 차감만 남은 상태가 정상 종료로 기록된다. rollbackFor = Exception.class.
음수 이체가 만드는 기능은?
WHERE balance >= -8000은 항상 참, 차감은 덧셈, 지급은 뺄셈 → 남의 돈을 빼앗아 오는 API. amount > 0은 보안 통제다.
동시성 테스트 3요소?
CountDownLatch 세 개(준비·총성·종료) + AtomicInteger 성공 카운트 + Testcontainers 진짜 PostgreSQL. H2로는 재현이 안 될 수 있다.

12-2. 꼬리질문 — 먼저 답해보고 펼친다

AI가 테스트도 잘 짜던데, 커버리지 90%면 부족한가요? 필수힌트: 커버리지가 세는 단위가 무엇인지 생각해본다

커버리지는 "테스트가 실행한 라인의 비율"이지 "검증된 시나리오의 비율"이 아니다. 이 둘의 차이가 동시성에서 극단적으로 드러난다.

4절의 check-then-act 코드는 라인 커버리지 100%에서도 초록불이다

결함이 특정 라인에 있는 게 아니라 라인들 사이의 실행 순서 겹침(인터리빙)에 있기 때문이다. 단일 스레드 테스트는 인터리빙을 하나도 만들지 않으므로, 아무리 여러 번 실행해도 이 축의 커버리지는 영원히 0이다.

숫자가 오히려 해가 되는 지점 구현과 테스트가 같은 출처면 맹점을 공유하므로, 커버리지가 높을수록 "충분히 검증됐다"는 착시만 강해진다. 그래서 숫자 대신 시나리오 목록(동시 2건 · 재시도 · 부분 실패 · 음수 금액)의 유무로 판단한다고 답한다.

전형적 check-then-act
② 공유 숫자를 읽어 계산 후 쓰는 모든 지점
잔액 · 재고 · 쿠폰 수량
③ existsBy… 검사 후 save
유니크 제약 없는 중복 검사 — 7절 멱등성과 같은 결함
④ 두 자원을 잠그는데 순서 규칙이 없음
교착 후보
이런 지점마다 던지는 질문은 하나 — "이 줄과 저 줄 사이에 똑같은 코드가 한 번 더 끼어들면 어떻게 되나?"

답이 "돈이 새거나 불변식이 깨진다"면, 원자적 연산(조건부 UPDATE · 유니크 제약 · 락)으로 바꾸게 한다.

비관적 락, 낙관적 락, 조건부 UPDATE 중 뭘 고르나요? 시니어 변별힌트: 세 가지가 서로 다른 "가정" 위에 서 있다. 선택 기준은 충돌 빈도와 실패 비용

세 가지가 서로 다른 가정 위에 서 있다는 것부터 정리하면 답이 나온다.

낙관적 락
"충돌이 드물다"
비관적 락
"충돌이 잦으니 미리 막는다"
조건부 UPDATE
"충돌 여부와 무관하게 검사와 실행을 붙여버린다"
그래서 선택 기준은 충돌 빈도 × 실패 비용이다

계좌 잔액은 인기 계좌(hot row, 쓰기가 몰리는 한 행)에 요청이 집중되고 실패 비용(음수 잔액)이 크다. 그래서 낙관적 락은 부적합하다 — 충돌할 때마다 예외를 던지고 재시도하는데, 충돌이 잦으면 재시도가 또 충돌해서 처리량이 오히려 무너진다. 낙관적 락은 충돌이 드물 때만 이득인 구조다.

기본기 — 조건부 UPDATE

  • 락 점유 시간이 SQL 한 문장 실행 시간으로 최소화된다
  • 검사와 갱신이 원자적
  • 단점: 도메인 로직이 SQL로 새고 JPA 더티 체킹과 결이 안 맞는다
  • 절충: 잔액 같은 핵심 불변식만 @Modifying 쿼리로 내리고 나머지는 평범한 엔티티로

여러 행 + 복잡한 검증 — 비관적 락

  • 여러 행을 함께 잠그고 그 위에서 검증해야 하면 이쪽
  • 반드시 id 오름차순 잠금과 함께
  • 락 구간 안에 외부 API 호출을 넣지 않는다
그리고 무엇을 고르든 CHECK (balance >= 0)까지 말하면 — 방어선을 하나가 아니라 층으로 설계한다는 인상을 준다
조건부 UPDATE가 0을 반환했을 때, 잔액 부족인지 계좌 없음인지 어떻게 구분하나요? 가산점힌트: 0은 "WHERE가 거짓"이라는 사실 하나만 알려준다. 그럼 사유는 어디서 얻나?

반환값만으로는 구분되지 않는다. 0은 "WHERE 조건을 만족한 행이 없었다"는 사실 하나만 알려주고, 그 원인이 잔액 부족인지 그런 계좌가 없음인지는 담고 있지 않다. 사용자에게 다른 메시지를 보여줘야 하므로 사유 분기는 필요하다.

원칙 — 변하는 값(잔액)은 원자적으로, 잘 변하지 않는 값(계좌 존재)은 사전 조회로

방법 ① 실패한 뒤에 사유를 조회한다

  • 0을 받은 다음에 계좌 존재 여부를 조회해 예외를 나눈다
  • 이미 실패가 확정된 뒤의 조회이므로 판단을 오염시키지 않는다 — check-then-act가 아니다
  • 정상 경로에는 추가 쿼리가 없다는 점이 장점

방법 ② 존재 검증만 앞에 둔다

  • 계좌 조회는 미리 하되 잔액 검사는 절대 자바에서 하지 않고 UPDATE에 맡긴다
  • 계좌 행은 이체 도중 사라지지 않으므로(하드 삭제를 하지 않는 한) 사전 검증이 낡을 위험이 낮다
  • 주의 — 이때 같이 읽어온 잔액으로 검사하고 싶은 유혹이 생긴다. 그 순간 4절 결함으로 되돌아간다

이 질문의 값은 "모든 검증을 원자적으로 만들 필요는 없다"는 판단력에 있다. 경합하는 값에만 원자성을 쓰고, 나머지는 읽기 쉬운 코드로 둔다.

차감과 지급을 다른 마이크로서비스가 담당하면요? 가산점힌트: "한 DB 트랜잭션"이라는 전제가 무너진다. 그다음 필요한 도구는 둘

"한 DB 트랜잭션"이라는 전제가 통째로 무너진다. 서로 다른 DB를 쓰는 두 서비스에 @Transactional을 걸어봐야 각자의 트랜잭션일 뿐, 한쪽 롤백이 다른 쪽을 되돌리지 못한다.

① 아웃박스(outbox) 패턴
"차감"과 "지급 요청 메시지 저장"을 같은 DB의 한 트랜잭션으로 묶어 커밋한 뒤, 별도 프로세스가 그 메시지 테이블을 읽어 실제로 발행한다. DB 커밋과 메시지 발행이 따로 놀아서 생기는 유실을 없애는 장치다.
② 보상 트랜잭션(사가, saga)
지급이 최종 실패하면 차감을 되돌리는 반대 방향 연산을 실행한다. 되돌리는 것이지 롤백이 아니므로, 이미 커밋된 차감 위에 "차감 취소"라는 새 기록이 쌓인다.
REQUESTED→ WITHDRAWN→ COMPLETED또는 COMPENSATED

그러면 이체는 위와 같은 상태 머신이 되고, 각 단계는 반드시 멱등해야 한다(메시지는 중복 전달될 수 있으므로).

핵심은 "@Transactional을 어디에 붙이나"가 아니라 "원자성 경계가 프로세스를 넘는 순간 설계가 통째로 달라진다"를 아는 것
프롬프트에 "동시성도 고려해줘"라고 쓰면 되지 않나요? 시니어 변별힌트: 생성 품질과 검증은 다른 축이다. 그리고 "형태만 갖춘 방어"라는 함정이 있다

산출물 품질은 확실히 좋아진다. 그러나 두 가지가 그대로 남는다.

남는 문제 ① 독립성은 회복되지 않는다

  • 방어 코드와 그 방어를 검증하는 테스트가 여전히 같은 문맥에서 나온다
  • 자기 채점 구조는 그대로다
  • 게다가 "무엇을 고려하라고 쓸지"의 목록 자체가 리뷰어의 지식에서 나온다 — 결국 사람이 그 목록을 갖고 있어야 한다

남는 문제 ② 형태만 갖춘 방어

  • @Version은 붙였는데 충돌 예외를 잡아 재시도하는 코드가 없다
  • 조건부 UPDATE로 바꿨는데 반환값을 확인하지 않는다 — 0이어도 그대로 지급한다
  • synchronized를 붙여놨는데 서버가 여러 대라 아무 효과가 없다
  • 전부 단일 실행 테스트는 통과한다
프롬프트는 생성 품질을 올리고, 리뷰는 재현 테스트로 확인한다 — 둘은 서로를 대체하지 않는다
금액 검증이 제일 쉬운데 왜 마지막에 보나요? 순서를 뒤집으면 안 되나요? 가산점힌트: "발견 개수"와 "남는 리스크"는 다른 지표다

쉬운 것부터 보면 발견 개수는 늘지만 남는 리스크는 줄지 않는다. 리뷰어의 집중력은 유한하고 앞에서 소진되므로, 가장 비싼 것을 가장 맑은 정신에 배치하는 것이 정렬의 목적이다.

정렬 기준은 피해 크기 × 테스트로 안 잡히는 정도 — "발견하기 쉬운 정도"가 아니다

게다가 5순위 항목들은 사람 손을 떠나보내기 가장 쉬운 것들이다.

타입 시스템
long·BigDecimal 시그니처면 double은 애초에 못 들어온다
ArchUnit
"money 패키지에서 double·float 금지"를 CI가 막는다
평범한 단위 테스트
음수·자기 이체는 단일 스레드 테스트로 충분히 잡힌다

즉 기계가 잡을 수 있는 것은 기계에게 내리고, 사람은 기계가 못 잡는 것부터 본다. 순서는 사람 리뷰라는 희소 자원의 배분 계획이다.

이 검증을 팀 프로세스로 만든다면 어떻게 하나요? 시니어 변별힌트: 사람의 집중력에 의존하는 리뷰는 바쁜 날 반드시 뚫린다

개인기를 절차로 바꾸는 것이 답이다.

1
PR 템플릿으로 체크리스트를 강제한다. 돈을 다루는 모듈의 PR에는 5단계(동시성·트랜잭션 경계·멱등성·예외 경로·금액 검증) 항목을 체크하지 않으면 리뷰 요청이 안 되게 한다.
2
동시성 테스트를 머지 조건으로 둔다. CountDownLatch + Testcontainers 테스트가 없는 잔액 변경 PR은 CI에서 막는다.
3
사람이 놓치는 것은 정적 규칙으로 내린다. ArchUnit(자바 코드의 구조 규칙을 테스트로 검증하는 라이브러리)으로 "트랜잭션 메서드 안에서 외부 HTTP 클라이언트 호출 금지", "money 패키지에서 double·float 타입 금지" 같은 규칙을 CI에 넣으면, 리뷰어의 기억력이 아니라 빌드가 막아준다.
4
DB 레벨 CHECK·유니크 제약을 항상 요구한다. 앞의 셋이 전부 실패했을 때의 마지막 방어선이다.

마무리 한 문장

AI가 코드 생산 속도를 높일수록, 리뷰는 사람의 눈이 아니라 자동화된 관문에 얹혀야 지속 가능하다

생산량이 10배가 되면 사람 리뷰는 10배가 될 수 없다는 것이 이 문제의 구조적 본질이다.

한 줄 요약
AI 이체 코드의 "테스트 전부 통과"는 행복 경로의 증명일 뿐이므로, 테스트에 원천적으로 없는 것 — 동시성(check-then-act, 잔액 음수) → 트랜잭션 경계(차감·지급 원자성, 트랜잭션 안 외부 호출) → 멱등성(재시도 이중 이체) → 예외 경로(부분 실패 상태) → 금액 검증(음수·자기 이체) — 순으로 리뷰하고, 결함은 코멘트가 아니라 CountDownLatch 동시성 테스트와 DB 제약으로 재발 불가능하게 박아 넣은 뒤에 머지한다.
