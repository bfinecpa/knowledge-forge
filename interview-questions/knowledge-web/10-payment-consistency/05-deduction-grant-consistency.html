차감과 지급의 정합성
순서를 정하는 기준은 "복구 가능성"이다

면접 질문: "포인트/캐시 차감과 콘텐츠 이용권 지급을 하나의 흐름에서 처리할 때 정합성을 어떻게 보장하나요?"

핵심 관전 포인트 — 포인트 차감(돈이 나감)과 이용권 지급(권리가 생김)이 같은 DB에 있다면 답은 단순하다 — 단일 트랜잭션으로 묶고, 잔액은 balance = balance - ? WHERE balance >= ? 조건부 UPDATE로 음수를 원천 차단한다. 서로 다른 시스템이라면 두 동작의 원자성은 포기하고 "실패해도 복구 가능한 순서"를 설계한다 — 차감을 먼저 하고 지급이 실패하면 환급(보상)한다. 환급은 더하기 연산이라 언제든 성공시킬 수 있지만, 지급을 먼저 하면 차감 실패를 메우려고 이미 소비됐을지 모르는 권리를 회수해야 한다. 여기에 트랜잭셔널 아웃박스(보낼 메시지를 같은 DB의 테이블에 INSERT해서 "커밋"과 "메시지 발행"을 한 몸으로 만드는 기법)로 발행 누락을 막고, 모든 돈의 이동을 append-only 원장에 남겨 어느 지점에서 죽어도 복구와 대사가 가능하게 만든다. 면접관이 보는 것은 "중간에서 죽는 지점을 몇 개나 열거하고, 각각의 복구를 말할 수 있는가"다.
  • 1
    같은 DB면 원자성은 공짜다 — 진짜 시험대는 동시성이다 — @Transactional 하나로 차감·원장·지급을 한 몸으로 묶고, 잔액 검사는 애플리케이션 if문이 아니라 UPDATE의 WHERE 절로 옮긴다. balance = balance - ? WHERE balance >= ?의 rowcount가 0이면 그것이 잔액 부족 신호다. 검사·잠금·갱신이 SQL 한 문장 안에서 원자적이라 lost update의 틈이 없다.
  • 2
    다른 시스템이면 원자성을 포기하고 순서를 설계한다 — 기준은 사용자 경험이 아니라 복구 가능성이다. 보상이 확실한 동작(차감)을 먼저, 보상이 불확실한 동작(지급)을 나중에 한다. 환급은 더하기라 논리적 실패 조건이 없고 우리 시스템 안에서 끝나지만, 권리 회수는 이미 소비됐으면 불가능하고 회수 API조차 없을 수 있다.
  • 3
    수렴을 실제로 굴리는 부품은 셋이다 — 트랜잭셔널 아웃박스(커밋과 발행을 한 트랜잭션으로 묶어 이중 쓰기를 제거), 멱등한 지급·환급(유니크 제약으로 중복 실행을 DB가 차단), append-only 원장(복구와 대사의 근거). 그리고 자동 복구가 실패한 사실은 반드시 사람 눈에 닿게 한다 — 돈이 붕 뜬 상태를 시스템이 "모르는 채" 두지 않는다.

0. 질문 + 출제 의도

질문: "포인트/캐시 차감과 콘텐츠 이용권 지급을 하나의 흐름에서 처리할 때 정합성을 어떻게 보장하나요?"

출제 의도: 돈이 나가는 동작과 권리가 생기는 동작 사이의 원자성을 설계할 수 있는지 본다. 한 DB면 트랜잭션으로 끝나지만, 서로 다른 시스템에 걸쳐 있으면 순서(차감 먼저? 지급 먼저?)를 정한 근거와 실패 시 복구까지 말해야 한다 — 정합성 설계를 구체적 실패 시나리오로 검증하는 습관이 있는지가 관전 포인트다.

이 페이지가 겨냥하는 약점 세 가지 ① "에러 나면 롤백하면 되죠"라는 반사적 답 → 2절에서 트랜잭션이 정확히 어디까지 되돌릴 수 있는지 경계선을 그리고, 커밋된 남의 트랜잭션은 롤백이 아니라 보상으로만 메울 수 있다는 출발점을 세운다.
② 순서를 사용자 경험으로 고르는 습관 → 5절에서 복구 가능성이라는 기준을 세우고, 두 순서의 최악의 결과를 나란히 놓고 비교한다.
③ 커밋과 발행 사이의 틈을 세지 않는 것 → 6절에서 이중 쓰기를 그림으로 드러내고 트랜잭셔널 아웃박스로 그 틈을 없앤다. 9절에서는 죽는 지점 3종을 각각의 복구와 함께 열거한다.

1. 왜 문제인가 — 실패가 만들 수 있는 네 가지 세계

5,000P짜리 웹툰 이용권을 구매하는 흐름을 보자. 해야 할 동작은 둘이다 — ① 포인트 5,000P 차감, ② 이용권 1장 지급. 이 둘 사이 어딘가에서 서버가 죽거나 네트워크가 끊기면, 시스템은 아래 네 가지 세계 중 하나에 놓인다.

"에러 나면 롤백하면 되죠"가 부족한 이유

그 답은 두 동작이 한 트랜잭션 안에 있을 때만 성립한다

면접관은 그 다음 — 트랜잭션이 닿지 않는 구간 — 을 묻고 있다. 그래서 먼저 "트랜잭션이 정확히 어디까지 보장해주는가"를 짚고 가야 한다. 그것이 바로 다음 절이다.

2. 전제 — @Transactional이 보장하는 것과 못 하는 것

트랜잭션(transaction)은 여러 개의 DB 작업을 "전부 성공 아니면 전부 없던 일"로 묶는 단위다. 이 성질을 원자성(atomicity)이라고 부른다 — 더 이상 쪼갤 수 없는 원자처럼 중간 상태로 남지 않는다는 뜻이다.

Spring에서 메서드에 @Transactional을 붙이면 메서드 시작 시 BEGIN, 정상 종료 시 COMMIT, 예외 발생 시 ROLLBACK이 자동으로 실행된다. 롤백이 가능한 이유는 DB가 변경 전 값을 별도 공간(PostgreSQL은 이전 버전 튜플, MySQL InnoDB는 언두 로그)에 남겨두기 때문이다. 즉 롤백은 DB 엔진이 자기 데이터에 대해 제공하는 기능이다. 여기서 경계가 드러난다.

보상은 회계의 "반대 분개"와 같은 사고방식이다 회계에서 잘못 적은 장부를 지우개로 지우지 않고 반대 방향의 분개를 새로 적는다. 왜냐하면 지우면 "무슨 일이 있었는지"가 사라지기 때문이다. 우리 설계도 똑같다 — 차감 기록을 지우는 대신 환급 기록을 새로 한 줄 더 쌓는다. 이 사고방식이 8절의 append-only 원장으로 그대로 이어진다.

3. 비유 — 자판기 한 대에 설계가 통째로 들어 있다

자판기는 반드시 동전을 먼저 받고(차감), 그다음 음료를 배출한다(지급). 배출이 실패하면 반환 레버가 있다 — 이게 보상(환급)이다. 반대로 음료를 먼저 주고 돈을 나중에 받는 자판기는 세상에 없다. 이미 딴 음료(소비된 권리)는 회수할 방법이 없기 때문이다. 그리고 자판기 안에는 동전 계수기가 있어 나중에 "판매된 재고 수 × 가격 = 수금액"이 맞는지 맞춰볼 수 있다 — 이게 원장과 대사다.

4. 같은 DB라면 — 단일 트랜잭션 + 조건부 UPDATE

포인트 지갑 테이블과 이용권 테이블이 같은 PostgreSQL 안에 있다면 원자성은 DB가 공짜로 준다. @Transactional 하나면 끝이다. 그런데 이때 진짜 시험대는 원자성이 아니라 동시성이다. 같은 사용자의 요청 두 개가 동시에 들어왔을 때 잔액이 어떻게 되는지가 문제다.

4-1. 먼저 짚고 갈 것 — lost update(갱신 유실)란 무엇인가

lost update는 두 트랜잭션이 같은 값을 읽어 각자 계산한 뒤 차례로 저장할 때, 나중 저장이 먼저 저장을 덮어써서 한쪽의 갱신이 사라지는 현상이다. 이름 그대로 "갱신이 유실된다". 잔액 5,000P인 사용자가 결제 버튼을 더블 클릭했다고 하자.

4-2. before / after — 검사와 차감을 UPDATE 한 문장으로 합친다

before 조회 후 갱신 — 두 가지 사고를 품고 있다
@Transactional
public void purchase(long userId, long orderId, long productId) {
    int balance = pointRepository.findBalance(userId);   // ① 조회
    if (balance < 5000) throw new InsufficientPointException();
    pointRepository.setBalance(userId, balance - 5000);  // ② 갱신
    ticketRepository.insert(orderId, userId, productId); // ③ 지급
}
// 사고 1(lost update): ①에서 두 요청이 모두 5000을 읽으면
//   둘 다 잔액 검사를 통과하고, ②의 덮어쓰기로 차감은 1번만 남는다.
// 사고 2: ①의 SELECT는 행을 잠그지 않는다. 트랜잭션으로 감쌌다고
//   동시성이 해결되는 게 아니라는 점이 이 코드의 교훈이다.
after 검사와 차감을 UPDATE 한 문장으로
@Transactional
public void purchase(long userId, long orderId, long productId) {
    int updated = pointRepository.deduct(userId, 5000);
    if (updated == 0) throw new InsufficientPointException();
    // 갱신된 행 수가 0이면 WHERE의 balance >= 5000이 거짓이었다는
    // 뜻 — 즉 잔액 부족이다. rowcount 확인이 곧 잔액 검사다.
    ledgerRepository.append(orderId, userId, -5000, EntryType.DEDUCT);
    ticketRepository.insert(orderId, userId, productId);
    // 같은 DB이므로 이 셋은 한 트랜잭션이다. 커밋되면 차감·원장·
    // 이용권이 전부 남고, 어디서든 예외가 나면 전부 사라진다.
}
repository 이 한 문장이 돈 도메인의 기본기다
@Modifying
@Query("""
    UPDATE PointWallet w
       SET w.balance = w.balance - :amount
     WHERE w.userId = :userId AND w.balance >= :amount
    """)
int deduct(@Param("userId") long userId, @Param("amount") int amount);

이 한 문장이 왜 안전한가 — 네 단계로 말한다

① DB가 읽어서 뺀다
balance = balance - :amount는 DB가 현재 값을 읽어 빼는 연산이다. 애플리케이션이 미리 읽어둔 옛날 값(5000)을 쓰지 않는다.
② UPDATE가 줄 세운다
UPDATE는 대상 행에 배타 잠금을 건다. 같은 행을 건드리려는 다른 UPDATE는 첫 번째가 커밋/롤백할 때까지 대기한다.
③ 조건이 거짓이 된다
대기에서 풀린 두 번째 요청이 보는 잔액은 이미 0이다. balance >= 5000이 거짓이 되어 0건 갱신으로 끝난다.
④ rowcount만 보면 된다
1 = 내가 차감했다 / 0 = 잔액 부족. 애플리케이션은 반환된 갱신 행 수만 확인한다.
검사·잠금·갱신이 SQL 한 문장 안에서 원자적이므로 틈이 원천적으로 없다
방어를 한 겹 더 — 잔액 음수는 애플리케이션 if문이 아니라 SQL이 막는다 컬럼에 CHECK (balance >= 0) 제약을 추가하면 어떤 경로(배치, 어드민 툴, 수동 SQL)로 들어오든 음수 잔액은 DB가 거부한다. 애플리케이션 코드는 바꿀 수 있는 사람이 많고 우회 경로가 생기지만, DB 제약은 모든 경로가 반드시 통과하는 마지막 관문이다.

5. 다른 시스템이라면 — 순서가 설계의 절반이다

포인트 서비스와 콘텐츠(이용권) 서비스가 DB를 따로 쓰는 순간, 2절에서 본 대로 두 동작을 한 트랜잭션에 넣을 방법은 없다. 이제 질문은 "어느 쪽을 먼저 실행하는가"로 바뀐다. 여기서 초보와 경험자가 갈린다.

초보의 기준 — 사용자 경험

  • "이용권부터 주면 사용자가 빨리 볼 수 있잖아요"
  • 정상 흐름만 상상하고 순서를 고른다
  • 실패했을 때 무엇이 남는지를 세어보지 않았다

경험자의 기준 — 복구 가능성

  • "실패했을 때 되돌리기 쉬운 쪽을 먼저 한다"
  • 두 순서의 최악의 결과를 나란히 놓고 비교한다
  • 순서는 취향이 아니라 근거가 있는 판단이 된다
두 순서를 최악의 결과까지 밀어붙여 비교한다
순서실패 시 보상보상의 성격최악의 결과
차감 → 지급환급(더하기)논리적 실패 없음, 내부 API잠시 돈이 빠졌다가 돌아옴
지급 → 차감권리 회수소비되면 불가능, 회수 API 부재 가능공짜 이용권 영구 확정

순서를 정할 때 던지는 세 질문 — "되 · 소 · 내"

되 — 되돌릴 수 있나?
이 동작의 반대 방향 연산이 존재하는가. 더하기의 반대는 빼기라 항상 있지만, "권리 발급"의 반대는 항상 있지는 않다.
소 — 소비될 수 있나?
보상하기 전에 사용자가 써버릴 수 있는 대상인가. 열람·다운로드·발송처럼 소비되면 회수해도 의미가 없는 것은 뒤로 미룬다.
내 — 내 시스템인가?
보상 API의 스펙과 배포 일정을 우리가 통제하는가. 외부 회사에 "취소 좀 해주세요"라고 부탁해야 한다면 보상은 불확실하다.
세 질문에 모두 "예"인 동작을 앞에 놓는다 — 포인트 차감이 정확히 그런 동작이다

6. 이중 쓰기 문제와 트랜잭셔널 아웃박스

순서를 정했다. 차감을 커밋하고, 콘텐츠 서비스에 지급을 요청한다. 그런데 여기 아직 구멍이 하나 남아 있다.

이중 쓰기(dual write)는 하나의 논리적 작업을 위해 서로 다른 두 저장소에 각각 써야 하는 상황을 말한다. 여기서는 ① 우리 DB에 차감을 커밋하고, ② Kafka(또는 HTTP)로 지급 요청을 보내는 것 — 두 개의 쓰기다. 두 쓰기는 원자적일 수 없다. 서로 다른 시스템이고, 둘을 묶어줄 공통 트랜잭션이 없기 때문이다.

비유 — 아웃박스는 집 앞 우체통이다 편지를 직접 우체국까지 들고 가는 것(코드에서 곧장 Kafka 발행)은, 가는 길에 내가 쓰러지면 편지도 함께 사라진다. 대신 집 앞 우체통에 넣어두면(같은 DB의 outbox 테이블에 INSERT) 내가 집을 비워도 집배원(릴레이)이 가져간다. 편지를 넣는 행위가 "집 안에서 끝나는 일"이라는 게 요점이다 — 우리가 통제하는 트랜잭션 안에서 완결된다.
DDL outbox 테이블과 부분 인덱스
CREATE TABLE outbox (
    id            bigserial   PRIMARY KEY,
    aggregate_id  bigint      NOT NULL,   -- 여기서는 order_id
    event_type    varchar(60) NOT NULL,   -- ticket.grant.requested
    payload       jsonb       NOT NULL,
    created_at    timestamptz NOT NULL DEFAULT now(),
    published_at  timestamptz              -- NULL이면 아직 미발행
);
-- 미발행 행만 빠르게 긁기 위한 부분 인덱스.
-- 발행이 끝난 수백만 행까지 매번 훑지 않게 해준다.
CREATE INDEX idx_outbox_unpublished
    ON outbox (id) WHERE published_at IS NULL;
service 커밋과 발행을 한 몸으로
@Transactional
public void deductAndRequestGrant(long userId, long orderId) {
    int updated = pointRepository.deduct(userId, 5000);
    if (updated == 0) throw new InsufficientPointException();

    ledgerRepository.append(orderId, userId, -5000, EntryType.DEDUCT);
    orderRepository.updateStatus(orderId, OrderStatus.DEDUCTED);

    // 카프카로 직접 보내지 않고 같은 DB의 테이블에 "예약"만 한다.
    // 이 INSERT는 위의 차감·원장·상태변경과 같은 트랜잭션이다.
    outboxRepository.save(OutboxMessage.of(
        "ticket.grant.requested", orderId, payload(userId, orderId)));

    // 커밋되면 차감·원장·주문상태·발행예약이 전부 남거나 전부 없다.
    // 커밋 직후 서버가 죽어도 outbox 행은 DB에 남아 있으므로
    // 되살아난 릴레이가 이어서 발행한다 — 흐름이 끊기지 않는다.
}

한 트랜잭션에 들어가는 네 줄 — "차 · 원 · 주 · 발"

차 — 차감
UPDATE point_wallet · 조건부 UPDATE로 음수 차단
원 — 원장
INSERT point_ledger · 왜 이 잔액이 됐는지의 근거
주 — 주문 상태
UPDATE orders · 어디까지 왔는지를 DB에 남긴다
발 — 발행 예약
INSERT outbox · 이 줄이 이중 쓰기를 없앤다
주문 상태를 남기는 이유 — 다른 주체(릴레이·배치·운영자)가 이어받으려면 "어디까지 왔는지"가 DB에 있어야 한다

7. at-least-once와 멱등성 — 반드시 세트다

릴레이는 발행에 성공할 때까지 재시도한다. 덕분에 메시지 유실은 없어진다. 대신 새로운 성질이 생긴다. 릴레이가 Kafka 발행에 성공했는데 published_at을 찍기 직전에 죽으면 어떻게 될까? 되살아난 릴레이는 그 행이 아직 미발행이라고 보고 한 번 더 발행한다.

at-least-once (최소 1회)

  • "적어도 한 번은 도착한다"는 보장이다
  • "정확히 한 번"이 아니다 — 2회 이상일 수 있다
  • 유실을 없애는 대가로 중복을 받아들인 것
  • 분산 시스템에서 가장 현실적인 타협점

그래서 따라붙는 규칙

  • at-least-once로 보내는 쪽이 있으면, 받는 쪽은 반드시 멱등해야 한다
  • 멱등성(idempotency) = 같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질
  • 비유: 전등의 "끄기" 버튼 — 이미 꺼진 전등에 끄기를 열 번 눌러도 결과는 꺼진 상태 하나

세트 규칙 — 어느 한쪽만 두면 반드시 뚫린다

재시도만 있고 멱등성이 없다
중복이 남는다 — 이용권 2장, 환급 2회. 9절 사례 3이 정확히 이 경우다.
멱등성만 있고 재시도가 없다
유실이 남는다 — 한 번 실패한 메시지를 아무도 다시 보내지 않는다.
둘 다 있다
유실도 중복도 없다. 이것이 실무에서 말하는 "실질적 exactly-once"의 정체다.
발신 쪽 재시도(at-least-once)와 수신 쪽 멱등성은 반드시 세트다

8. 원장(ledger) — 잔액은 "현재", 원장은 "역사"

잔액 컬럼만 갱신하면 사고가 났을 때 "왜 이 잔액이 됐는지"를 재구성할 수 없다. 3,200P라는 숫자만 남아 있을 뿐, 언제 무엇 때문에 얼마가 오갔는지는 어디에도 없다. 그래서 모든 증감을 원장(ledger)에 남긴다. 원장은 회계에서 빌려온 말로, 돈의 모든 이동을 시간 순으로 적어 두는 장부다. 그리고 그 장부는 append-only여야 한다 — 이미 적은 줄은 고치지도 지우지도 않고 새 줄만 추가한다.

DDL point_ledger
CREATE TABLE point_ledger (
    id         bigserial    PRIMARY KEY,
    order_id   bigint       NOT NULL,
    user_id    bigint       NOT NULL,
    amount     int          NOT NULL,  -- 차감은 음수, 환급은 양수
    entry_type varchar(20)  NOT NULL,  -- DEDUCT / REFUND
    created_at timestamptz  NOT NULL DEFAULT now(),
    UNIQUE (order_id, entry_type)  -- 주문당 차감 1번, 환급 1번
);
batch 대사 — 원장 합계와 잔액이 어긋난 사용자 찾기
SELECT w.user_id, w.balance, COALESCE(SUM(l.amount), 0) AS ledger_sum
  FROM point_wallet w
  LEFT JOIN point_ledger l ON l.user_id = w.user_id
 GROUP BY w.user_id, w.balance
HAVING w.balance <> COALESCE(SUM(l.amount), 0);
-- 이 쿼리가 한 건이라도 뱉으면 어딘가에서 사고가 났다는 뜻이다.
-- 보정은 항상 "원장 → 잔액" 방향으로만 한다.

멱등성을 if문으로 구현하면 안 되는 이유

애플리케이션 if문

  • if (이미 환급됐나?) return;
  • 이건 4절에서 본 check-then-act다
  • 동시 요청 두 건이 나란히 통과할 수 있다
  • 읽기와 쓰기 사이의 틈이 그대로 남는다

DB 유니크 제약

  • UNIQUE (order_id, entry_type)
  • DB 엔진이 쓰기 시점에 원자적으로 판정한다
  • 동시 요청 중 정확히 한 건만 성공한다
  • 틈이 없다 — 4절 조건부 UPDATE와 같은 원리
돈 도메인의 판정은 "읽고 판단"이 아니라 "쓰면서 판정"으로 만든다

9. 실무 사례 — 중간에서 죽는 지점별 시나리오

앞 절의 부품들이 실제로 어떤 사고를 막는지, 사고 순간의 타임라인과 함께 본다. 이 세 가지를 즉석에서 열거할 수 있으면 "실패 지점을 설계 단계에서 세어보는 사람"으로 보인다.

사례 1: 차감 성공 → 지급 호출 타임아웃 (결과 불명)

사례 2: 차감 커밋 직후 서버 크래시 — 아무도 모르는 미완결 흐름

차감을 커밋한 직후, 지급 요청을 보내기 직전에 파드가 재시작됐다. 아웃박스가 없는 구식 구현(커밋 후 코드에서 직접 HTTP 호출)이라면 주문은 DEDUCTED에서 영원히 멈춘다. 요청을 처리하던 스레드는 프로세스와 함께 사라졌고, 이 주문을 이어서 처리할 주체가 아무 데도 없다. 며칠 뒤 "5,000P 빠졌는데 이용권이 없다"는 CS로 발견된다.

(1) 아웃박스를 쓰면 이 시나리오 자체가 사라진다

  • 발행 예약이 차감과 같은 트랜잭션으로 DB에 남아 있다
  • 릴레이가 되살아나 발행을 이어간다
  • 요청 스레드의 생사와 무관하게 흐름이 전진한다

(2) 그래도 안전망으로 미완결 주문 스캔 배치를 둔다

  • 릴레이 자체가 장시간 죽어 있는 경우
  • 컨슈머 쪽에서 메시지가 처리되지 못하고 사라지는 경우
  • DEDUCTED로 N분 이상 머문 주문을 찾아 지급을 재개하거나 환급으로 종결
batch 안전망 배치가 찾아내는 대상 — 차감만 되고 5분 넘게 멈춘 주문
SELECT order_id, user_id, updated_at
  FROM orders
 WHERE status = 'DEDUCTED'
   AND updated_at < now() - interval '5 minutes'
 ORDER BY updated_at
 LIMIT 500;
-- LIMIT을 두는 이유: 장애 직후 수만 건이 쌓였을 때 배치 한 번이
-- 전부를 들고 가려다 자기가 타임아웃 나는 것을 막는다.

사례 2의 교훈 한 줄

요청 스레드가 죽어도 흐름을 이어갈 주체(릴레이 · 배치)가 설계 안에 존재해야 한다

그리고 그 주체가 "어디까지 진행됐는지" 판단할 근거가 주문 상태와 원장이다. 상태를 DB에 남기지 않으면 이어받을 방법 자체가 없다.

사례 3: 지급은 됐는데 응답 유실 → 재시도로 이용권 2장

콘텐츠 서비스가 지급을 끝내고 응답을 보내는 중에 커넥션이 끊겼다. 요청 쪽은 사례 1의 절차대로 재시도한다. 그런데 지급 로직이 멱등하지 않으면 — 즉 그냥 INSERT INTO ticket ...이면 — 이용권이 2장 발급된다. 1장에 5,000P니까 사용자에게 5,000P어치 이익이고, 이런 경로가 알려지면 프로모션 어뷰징 통로가 된다.

before 멱등하지 않은 지급
INSERT INTO ticket (order_id, user_id, product_id)
VALUES (:orderId, :userId, :productId);
-- 재시도가 오면 그냥 한 장 더 만든다.
-- 발신 쪽은 at-least-once인데 수신 쪽이 그 전제를
-- 모르고 있다 — 7절의 "세트 규칙"이 깨진 상태.
after 수신 쪽을 멱등하게 만든다
CREATE UNIQUE INDEX uq_ticket_order ON ticket (order_id);

INSERT INTO ticket (order_id, user_id, product_id)
VALUES (:orderId, :userId, :productId)
ON CONFLICT (order_id) DO NOTHING;  -- 이미 있으면 조용히 성공 취급
-- PostgreSQL 문법. 유니크 충돌이 나면 예외를 던지는 대신
-- 아무 일도 하지 않고 넘어간다. 두 번째 요청은 에러 없이
-- "성공"으로 응답되고, 이용권은 여전히 1장이다.
여기서 얻는 규칙 발신 쪽 재시도(at-least-once)와 수신 쪽 멱등성은 반드시 세트다. 어느 한쪽만 있으면 유실(재시도가 없어서)이나 중복(멱등성이 없어서)이 남는다. 그리고 멱등의 열쇠가 되는 비즈니스 키(order_id)는 발신 쪽이 만들어 넘겨야 한다 — 수신 쪽이 자기가 만든 ID로는 "같은 요청인지"를 판단할 수 없기 때문이다.

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 답을 먼저 떠올리고 오른쪽을 본다

네 가지 세계 중 사고는?
③ 차감만(CS 폭탄) · ④ 지급만(공짜 이용권). 정합성 설계 = ③④를 없애거나 ①②로 수렴시키는 일.
이 문서의 세 축은?
순 · 보 · 기 — 순서(차감 먼저) · 보상(환급) · 기록(원장·대사). 자판기 한 대에 셋 다 있다.
조건부 UPDATE 한 문장?
SET balance = balance - :amt WHERE user_id = :id AND balance >= :amt → rowcount 0 = 잔액 부족.
그게 왜 안전한가 4단?
① DB가 현재값을 읽어 뺀다 ② UPDATE가 배타 잠금으로 줄 세운다 ③ 두 번째는 조건이 거짓 ④ rowcount만 확인.
순서 판단 세 질문?
되 · 소 · 내 — 되돌릴 수 있나 / 소비될 수 있나 / 내 시스템인가. 셋 다 "예"인 쪽을 앞에.
한 트랜잭션 네 줄?
차 · 원 · 주 · 발 — 차감 · 원장 · 주문상태 · 발행예약(outbox).
트랜잭션 밖 4종은?
HTTP 호출 · Kafka 발행 · 파일/메일/외부승인 · Redis. @Transactional 안에 있어도 롤백되지 않는다.
세트 규칙 한 줄?
at-least-once 발신 ↔ 수신 멱등. 한쪽만 있으면 유실 또는 중복이 남는다.
멱등을 무엇으로 구현하나?
if문이 아니라 유니크 제약. UNIQUE(order_id, entry_type) · ON CONFLICT DO NOTHING. if문은 check-then-act라 동시 요청이 나란히 통과한다.
타임아웃은 실패인가?
아니다 — 결과 불명이다. ① 도착 못 함 ② 처리 중 ③ 처리 완료 후 응답 유실. ③에서 환급하면 공짜 세계.
잔액 vs 원장, 누가 진실?
원장이 진실, 잔액은 파생 캐시. 불일치는 항상 "원장 → 잔액" 방향으로만 보정한다.
자동 복구의 끝단은?
COMPENSATION_FAILED + 수동 개입 큐 + 알림. 돈이 붕 뜬 상태를 시스템이 "모르는 채" 두지 않는다.

10-2. 꼬리질문 — 먼저 답해보고 펼친다

왜 차감을 먼저 하나요? 지급 먼저가 사용자 경험엔 낫지 않나요? 필수힌트: 기준을 바꿔야 한다. 그리고 UX 관점으로 봐도 결론은 같다

순서의 기준은 사용자 경험이 아니라 보상의 확실성이다.

차감의 보상 = 환급

  • 잔액에 더하는 연산이라 논리적 실패 조건이 없다
  • 우리 시스템 안에서 끝난다 — 스펙과 배포를 우리가 통제
  • 일시 실패해도 재시도하면 언젠가 반드시 성공한다

지급의 보상 = 권리 회수

  • 이미 소비됐으면 불가능하다 (열람한 웹툰은 안 본 것이 되지 않는다)
  • 회수 API가 아예 없을 수도 있다 — 실무에서 흔하다
  • 지급과 회수 사이의 틈에 공짜 사용 창이 열린다
사용자 경험 관점에서 봐도 결론은 같다

"차감됐다가 환급된" 고객은 안내와 사과로 정리되지만, "공짜로 지급된" 건은 회사 손실이자 어뷰징 통로이고 회수하려면 고객과 다퉈야 한다. 즉 UX 기준으로 봐도 지급 먼저가 유리하지 않다.

여기에 한 문장 더 붙이면 좋다 잔액 부족이라는 최다 실패 사유를 첫 단계에서 걸러내므로 보상 빈도 자체가 줄어든다. 지급 단계까지 도달한 흐름은 이미 잔액 검증을 통과한 흐름이라 대부분 성공한다 — 순서를 잘 고르면 보상 로직이 돌 일이 적어진다.
잔액을 SELECT ... FOR UPDATE로 잠그고 검사하면 안 되나요? 필수힌트: "된다"로 시작하되, 아쉬운 점 둘과 정당한 경우 하나를 말한다

된다. SELECT ... FOR UPDATE는 조회하면서 그 행에 배타 잠금을 거는 문법이라, 행을 먼저 잠가두면 4절에서 본 check-then-act의 틈이 사라진다. 두 번째 요청은 첫 번째가 커밋할 때까지 SELECT 단계에서 대기하고, 깨어났을 때는 갱신된 잔액을 본다.

다만 조건부 UPDATE와 비교하면 두 가지가 아쉽다.

① 왕복이 2회다
SELECT로 잠그고 UPDATE로 갱신하므로 DB 왕복이 두 번이고, 그 사이 애플리케이션 로직이 도는 동안에도 잠금을 쥐고 있다. 잠금 보유 시간이 길어지면 같은 행에 몰리는 요청의 대기 시간도 같이 길어진다.
② 검사와 갱신이 코드에서 분리된다
나중에 누군가 UPDATE 앞에 다른 로직을 끼워 넣거나, 다른 경로에서 FOR UPDATE 없이 조회 후 갱신하는 코드를 짜면 다시 뚫린다. 조건부 UPDATE는 한 문장이라 쪼갤 여지가 없다.
정당한 경우 — 차감 전에 잔액 외 여러 값을 읽어 복잡한 판단을 해야 할 때

예를 들어 등급별 한도, 일일 사용 누적액, 보유 쿠폰을 함께 보고 차감액을 계산해야 한다면 한 문장의 UPDATE로 표현할 수 없으니 잠그고 읽는 편이 맞다. 단순 차감이라면 조건부 UPDATE가 기본기다. 즉 "뭐가 맞나요"가 아니라 "판단이 SQL 한 문장으로 표현되는가"가 갈림길이다.

외부 서비스 호출을 @Transactional 안에 두면 무슨 일이 생기나요? 함정힌트: 셋이다. 그리고 셋 다 같은 해법으로 사라진다
1
커넥션 풀 고갈 — 외부 호출이 3초 걸리는 동안 DB 커넥션과 행 잠금을 쥔 채 기다린다. 커넥션 풀이 20개인 서비스에 초당 30건이 들어오면 순식간에 풀이 마르고, 결제와 무관한 다른 API까지 같이 죽는다. 외부 장애가 우리 서비스 전체 장애로 번지는 전형적인 경로다.
2
외부 부수효과는 롤백되지 않는다 — 외부 호출(지급)은 성공했는데 그 뒤 커밋이 실패하면 DB는 롤백되지만 상대 시스템의 지급은 그대로 남는다. 즉 "차감 없이 지급된" 세계가 트랜잭션 안에서 만들어진다. @Transactional이 붙어 있어서 안전하다고 믿게 만드는 점이 오히려 위험하다.
3
커밋 전에 이벤트를 발행하면 수신 쪽이 못 본다 — 반대로 커밋 전에 Kafka로 먼저 쏘면, 컨슈머가 즉시 우리 DB를 조회했을 때 아직 커밋되지 않은 주문이 보이지 않아 "그런 주문 없음"으로 실패한다. 커밋보다 이벤트가 빠른 경합이다.
세 문제 모두 "커밋 후 발행"을 구조적으로 보장하면 사라진다 — 그것이 6절의 트랜잭셔널 아웃박스다
잔액 컬럼과 원장이 어긋나면 어느 쪽이 진실인가요? 시니어 변별힌트: 결론은 한 단어. 그런데 "그럼 잔액 컬럼을 없애면?"까지 답해야 변별력이 생긴다
원장이 진실이고, 잔액은 파생값(캐시)이다

근거를 말할 수 있어야 한다.

원장이 진실인 이유

  • append-only라 한 번 적힌 줄이 바뀌지 않는다 → 조작·유실의 흔적이 남는다
  • 모든 증감의 사유를 담고 있다 — order_id · entry_type · created_at
  • 처음부터 다시 합산하면 언제든 올바른 값을 재생성할 수 있다

잔액이 파생값인 이유

  • 원장의 합계를 미리 계산해 둔 성능용 값일 뿐이다
  • UPDATE 한 번으로 과거 흔적 없이 덮어써진다
  • 틀렸을 때 스스로를 근거로 고칠 수 없다

그래서 대사 배치는 SUM(amount)와 잔액 컬럼을 비교해 불일치를 찾고, 불일치가 나오면 원장 기준으로 잔액을 보정한다(8절 쿼리).

여기서 한 걸음 더 — "그럼 아예 잔액 컬럼을 없애고 매번 SUM 하면 되지 않나요?" 원장이 수백만 행으로 자라면 조회마다 전체 합산은 감당할 수 없다. 그래서 실무에서는 스냅샷 + 이후분 합산으로 절충한다 — 월말 시점의 잔액을 스냅샷 행으로 확정해 두고, 조회 시에는 "스냅샷 잔액 + 스냅샷 이후 원장 합계"만 계산한다.

구도를 한 문장으로: 원본과 파생을 구분하되, 파생은 성능을 위해 유지한다. 이 문장을 말하면 "캐시가 틀렸으면 원본에서 다시 계산한다"는 복구 전략이 자연스럽게 따라 나온다.

환급(보상)마저 실패하면 어떻게 하나요? 필수힌트: 3단으로 답한다. 마지막 단이 이 답의 핵심이다

환급은 더하기라 잔액 부족 같은 논리적 실패는 없지만, 포인트 서비스 장애나 네트워크 단절 같은 일시적 실패는 얼마든지 난다.

1
자동 재시도 — 환급 요청도 아웃박스나 재시도 큐에 태우고 지수 백오프(재시도 간격을 1초, 2초, 4초… 로 늘려 이미 힘든 상대 시스템에 부하를 더 주지 않는 방식)를 둔다.
2
한도를 넘기면 상태로 남긴다 — 재시도 한도(예: 5회)를 넘기면 주문을 COMPENSATION_FAILED로 전이시킨다. 이 상태의 의미는 "시스템이 자동으로 해결하지 못했고, 그 사실을 알고 있다"이다.
3
사람에게 넘긴다 — 수동 개입 큐(운영자가 보는 보정 대기 목록 테이블)에 orderId, 금액, 실패 사유, 마지막 시도 시각을 적재하고 알림을 쏜다.
돈이 붕 뜬 상태를 시스템이 "모르는 채" 두지 않는다

자동 복구가 실패하는 것 자체는 어쩔 수 없지만, 실패했다는 사실이 아무 데도 기록되지 않는 것은 설계 결함이다. 반드시 사람 눈에 닿는 경로를 만들어 두는 것 — 이것이 돈 도메인에서 재시도의 끝단이다.

2PC(XA 분산 트랜잭션)를 쓰면 두 시스템의 원자성을 얻을 수 있지 않나요? 시니어 변별힌트: "이론적으로는 된다"로 시작하고, 실무에서 피하는 이유 셋을 댄다

이론적으로는 된다. 2PC(two-phase commit, 2단계 커밋) 는 코디네이터가 참가자 전원에게 prepare를 보내 모두 "준비됐다"고 답하면 commit을 보내는 프로토콜이다. 전원이 준비된 뒤에만 커밋하므로 원자성이 성립한다. 그런데 실무의 마이크로서비스에서는 거의 쓰지 않는다.

① 블로킹 프로토콜이다
참가자는 prepare 응답 후 락을 쥔 채 코디네이터의 결정을 기다린다. 코디네이터가 그 사이 죽으면 참가자는 커밋해야 할지 롤백해야 할지 모르는 채 락을 놓지 못한다. 이 상태가 길어지면 해당 행을 쓰려는 모든 요청이 멈춘다.
② 참가할 수 없는 자원이 많다
DB 두 대는 참가시킬 수 있어도 HTTP로 부르는 콘텐츠 서비스, Kafka, Redis, 외부 결제사는 XA 참가자가 되지 못한다. 정작 우리가 묶고 싶은 대상이 대부분 밖에 있다.
③ 처리량이 떨어진다
한 번의 논리적 작업에 왕복이 두 배가 되고 락 보유 시간이 길어진다. 결제처럼 같은 행에 경합이 몰리는 도메인에서 특히 불리하다.
그래서 원자성을 포기하고 "결과적 일관성 + 보상"으로 간다 — 이 문서의 설계가 곧 그 형태다

이렇게 여러 로컬 트랜잭션을 순서대로 실행하고, 실패하면 앞선 것들을 보상 트랜잭션으로 되돌리는 패턴을 사가(saga)라고 부른다. "차감 → 지급, 실패 시 환급"이 가장 짧은 사가다. 2PC와의 차이를 한 문장으로 말하면 — 2PC는 중간 상태를 아예 안 만들려 하고, 사가는 중간 상태를 허용하되 반드시 수렴시킨다.

릴레이를 여러 인스턴스로 띄우면 같은 메시지를 중복 발행하지 않나요? 가산점힌트: "막는다"가 아니라 "무해하게 만든다"가 먼저다

중복 발행한다. 두 릴레이가 같은 미발행 행을 동시에 읽으면 같은 메시지가 두 번 나간다. 그런데 이것이 곧 사고는 아니다 — 애초에 릴레이는 at-least-once라 단일 인스턴스여도 중복은 발생한다(발행 성공 후 published_at을 찍기 전에 죽는 경우, 7절).

그래서 1순위 답은 "수신 쪽 멱등성으로 무해하게 만든다"이다

그 위에 중복의 양을 줄이는 운영 기법을 얹는다.

행 단위로 나눠 갖기
SELECT ... FOR UPDATE SKIP LOCKED로 미발행 행을 잠그고 가져오면, 다른 릴레이는 잠긴 행을 건너뛰고 다른 행을 집는다. 인스턴스를 늘려도 같은 행을 두고 다투지 않는다.
CDC로 전환
복제 로그를 구독하는 커넥터를 단일 활성 인스턴스로 운영하면 중복 발행 자체가 줄어든다. 대신 인프라가 하나 늘어난다.

답변의 순서가 곧 사고의 수준이다 — 중복을 막는 기법부터 말하면 "기법을 아는 사람", "어차피 at-least-once이므로 수신 멱등이 먼저다"부터 말하면 "보장 모델을 이해한 사람"으로 들린다.

outbox 테이블이 계속 커지는 문제는 어떻게 하나요? 가산점힌트: 이 테이블의 역할이 무엇인지 되물어본다

먼저 조회 성능과 테이블 크기를 나눠서 봐야 한다.

조회 성능은 이미 해결돼 있다

  • 6절의 부분 인덱스 WHERE published_at IS NULL 덕에
  • 인덱스에는 미발행 행만 들어간다
  • 발행 완료 행이 수백만 건이어도 릴레이의 조회는 느려지지 않는다

테이블 크기는 별개의 문제다

  • 디스크, 백업 시간, VACUUM/통계 갱신 부담이 계속 늘어난다
  • payload가 jsonb라 행 하나가 작지 않다
해법의 근거는 "outbox는 감사 기록이 아니라 전송 큐"라는 역할 정의다

무슨 일이 있었는지의 기록은 원장과 주문 이력이 담당한다. outbox는 "보냈는가"만 책임지는 임시 저장소이므로 발행 완료 행은 지워도 된다. 실무에서는 두 가지를 쓴다.

보관 기간 삭제
"발행 완료 후 N일 지난 행 삭제" 배치. 조사에 쓸 최소 기간(며칠)만 남긴다.
날짜 파티셔닝
일/월 단위 파티션으로 만들고 오래된 파티션을 통째로 드롭한다. 대량 DELETE보다 부하가 훨씬 작다.

주의 — 지우기 전에 반드시 published_at IS NOT NULL 조건을 건다. 미발행 행을 지우면 그 주문은 영원히 지급 요청을 받지 못한다.

"차감 먼저" 원칙에 예외는 없나요? 시니어 변별힌트: 원칙은 "순서"가 아니라 "기준"이다. 기준을 다시 적용해본다

원칙은 "차감을 먼저 한다"가 아니라 "보상이 확실한 쪽을 먼저 한다"이다. 순서는 그 기준을 우리 상황에 적용한 결과일 뿐이므로, 상황이 바뀌면 결과도 바뀔 수 있다. 5절의 되·소·내를 다시 적용해보면 결론이 뒤집히는 조건이 보인다.

지급 쪽이 확실히 회수 가능할 때
발급 직후에는 소비할 수 없는 형태(개시일이 미래인 이용권, 예약 상태의 좌석)이고 회수 API가 확실히 존재한다면 "소"와 "되"가 충족된다. 이때는 권리를 먼저 선점하는 편이 나을 수 있다 — 한정 수량 상품에서 "결제는 됐는데 재고가 없다"를 막아야 할 때가 대표적이다.
차감 쪽이 외부이고 되돌리기 비쌀 때
차감이 외부 결제사 승인이라 취소에 수수료·기간·정산 영향이 따른다면 "내"가 깨진다. 이때는 확실히 회수 가능한 내부 권리를 먼저 잡고, 결제 실패 시 그 선점을 푸는 편이 총비용이 낮을 수 있다.
단, 선점은 반드시 "소비 불가능한 상태"여야 한다 — 선점이 곧 사용 가능이면 예외가 성립하지 않는다

면접에서의 값은 예외를 아는 것 자체가 아니라 "원칙을 기준으로 환원해서 말할 수 있다"는 데 있다. "차감 먼저는 결론이고, 기준은 보상 가능성입니다. 지급 쪽 보상이 더 확실한 상황이라면 순서는 뒤집힙니다"가 완성된 답이다.

지급 결과가 확정되기 전에 사용자 화면에는 뭐라고 보여주나요? 가산점힌트: 화면 문구가 사용자의 다음 행동을 결정한다

내부 상태를 그대로 내려주면 안 된다. 화면 문구가 사용자의 행동을 결정하고, 그 행동이 곧 다음 요청이 되기 때문이다.

내부 주문 상태표시 문구사용자가 하게 되는 행동
DEDUCTED (지급 확정 전)"구매 처리 중입니다"기다린다 — 재구매하지 않는다
DEDUCTED (지급 확정 전)"구매 실패"다시 구매한다 → 이중 차감 · 이용권 2장
REFUNDED"구매에 실패해 포인트를 환급했습니다"안심하고 재시도 — 이때는 재시도가 옳다
COMPENSATION_FAILED"확인 중입니다. 곧 안내드립니다"기다린다 (뒤에서 운영자가 처리 중)
클라이언트에 내릴 것은 내부 열거형 이름이 아니라 "기다려야 하는가 / 다시 시도해도 되는가 / 끝났는가"라는 행동 지침이다
한 줄 요약
같은 DB면 단일 트랜잭션 + 조건부 UPDATE(balance = balance - ? WHERE balance >= ?)로 차감·지급을 한 몸으로 묶어 lost update까지 막고, 다른 시스템이면 보상이 확실한 차감을 먼저 실행한 뒤 지급 실패 시 환급으로 수렴시킨다 — 그 수렴을 실제로 굴리는 부품이 트랜잭셔널 아웃박스(같은 트랜잭션에 메시지를 예약해 커밋과 발행을 한 몸으로), 멱등한 지급·환급(유니크 제약으로 중복 실행 차단), append-only 원장(복구와 대사의 근거)이며, 설계의 완성도는 "중간에서 죽는 지점마다 복구 경로가 있는가"로 검증된다.
