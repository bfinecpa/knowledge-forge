웹훅 수신 처리
위조되고, 중복 오고, 순서가 뒤집힌다는 전제로 설계한다

면접 질문: "웹훅(callback) 수신 처리 시 주의할 점은 무엇인가요? (검증, 멱등성, 순서)"

핵심 관전 포인트 — 웹훅은 인터넷 어디서든 열려 있는 내 엔드포인트로 날아오는 HTTP 요청일 뿐이다. 그래서 세 가지를 전제해야 한다 — (1) 위조될 수 있다: HMAC 서명 검증으로 발신자를 확인하고, 그래도 페이로드의 금액·상태를 믿지 말고 거래 조회 API로 재확인한다. (2) 중복 온다: 발신측 재시도는 at-least-once이므로 이벤트 ID에 유니크 제약을 걸어 두 번째부터는 조용히 버린다. (3) 순서가 뒤집힌다: 취소 웹훅이 승인 웹훅보다 먼저 도착할 수 있으므로, 도착 순서가 아니라 상태 머신의 전이 규칙으로 반영 여부를 정한다. 여기에 운영 원칙 두 가지 — 검증·저장만 하고 빠르게 200을 준 뒤 처리는 비동기로 분리하고, 웹훅이 아예 유실될 경우를 대비해 보정 폴링(조회 API 기반 대사)을 깔아둔다. 셋 중 하나라도 빼먹으면 각각 보안 사고, 이중 지급, 상태 꼬임으로 직결된다.
  • 1
    위조를 전제한다 — 엔드포인트는 공개 인터넷에 열어둘 수밖에 없고 HTTP에는 출처를 증명하는 장치가 없다. 그래서 HMAC 서명 검증(원문 바이트로, 상수 시간 비교로, 타임스탬프를 포함해)이 필수 방어이고, IP 화이트리스트는 보조다. 금액·상태는 서명을 통과해도 믿지 않고 거래 조회 API로 확정한다.
  • 2
    중복을 전제한다 — 발신측은 응답을 못 받으면 재전송하는 at-least-once이고, "처리 성공"과 "응답 도달"은 다른 사건이라 이 간극은 원리적으로 없앨 수 없다. 그래서 중복 제거는 수신측 책임이다 — event_id에 유니크 제약을 걸고 ON CONFLICT DO NOTHING으로 검사와 선점을 한 문장에 합친다.
  • 3
    순서 역전을 전제한다 — 재시도가 있는 한 도착 순서는 사건의 순서에 대해 아무 정보도 주지 않는다. 그래서 "마지막에 온 게 최신"이 아니라 상태 머신의 전이 규칙으로 반영 여부를 정하고, 규칙에 없는 전이(CANCELLED → PAID)는 상태를 바꾸지 않고 200으로 버린다.
  • 4
    운영은 두 축이다 — 동기 구간은 검증 + 내구성 있는 저장까지만 하고 즉시 200을 준 뒤 실제 반영은 비동기 워커가 맡는다(안 그러면 타임아웃 → 재전송 루프를 스스로 만든다). 그리고 웹훅이 아예 안 올 경우를 위해 보정 폴링을 안전망으로 깐다 — 웹훅은 지연을 줄이는 최적화, 폴링이 정합성의 최후 보루.

0. 질문 + 출제 의도

질문: "웹훅(callback) 수신 처리 시 주의할 점은 무엇인가요? (검증, 멱등성, 순서)"

출제 의도: 웹훅은 위조 가능하고(검증), 중복으로 오고(멱등성), 순서가 뒤집힌다(상태 머신 검증). 셋 중 하나라도 빼먹으면 각각 보안 사고, 이중 지급, 상태 꼬임이 된다 — 결제 웹훅 수신부 설계의 필수 체크리스트를 갖췄는지 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "검증은 서명 확인이죠"에서 멈추는 것 → 4·5절에서 서명이 증명하는 범위가 어디까지인지를 명확히 긋고, 그 밖(구현 실수·시크릿 유출·발신측 버그)을 조회 API 재확인이 어떻게 덮는지 보인다.
② 중복·역전을 "드물게 생기는 예외"로 보는 것 → 2절에서 둘 다 메커니즘상 반드시 생기는 정상 현상임을 타임라인으로 그리고, 특히 장애 복구 시점에 몰려서 온다는 점을 사례로 확인한다.
③ "웹훅만 잘 처리하면 된다"는 전제 → 8·9절에서 동기 구간을 어디서 끊을지와 웹훅이 아예 안 왔을 때 누가 발견하는지까지 답할 수 있게 만든다. 여기까지 말하면 수신부 개발자가 아니라 결제 시스템 설계자로 들린다.

1. 전제 — 폴링과 웹훅은 "내가 물어보기" vs "상대가 알려주기"

웹훅 이야기를 하기 전에, 애초에 남의 시스템에서 벌어진 일을 알아내는 방법이 몇 가지나 되는지부터 정리하자. 근본적으로 두 가지뿐이다.

폴링(polling) — 내가 물어본다
주기적으로 상대에게 전화를 걸어 "그 결제 끝났어?"라고 묻는다. 영어 poll이 "물어보다"라는 뜻이라 붙은 이름이다. 구현이 단순하고, 전적으로 내 통제 아래 있다. 상대가 아무 연락을 안 해도 내가 물으면 되니까.
웹훅(webhook) — 상대가 알려준다
"이런 일이 생기면 이 URL로 알려줘"라고 미리 등록해두면 사건이 났을 때 상대가 내 URL로 HTTP 요청을 보낸다. 웹(HTTP)에 걸어두는 훅(hook, 갈고리 — 특정 사건이 났을 때 불려나갈 자리)에서 온 이름이다.

폴링의 대가는 "지연이냐 부하냐"의 맞바꿈이다. 1분에 한 번 물으면 최악의 경우 결제가 끝나고 59초 뒤에야 알게 되고, 1초에 한 번 물으면 지연은 줄지만 아무 일도 없는데 상대 서버를 초당 한 번씩 두드리게 된다. 결제 건수가 늘면 이 낭비가 그대로 곱해진다. 웹훅의 대가는 더 근본적이다 — 통제권이 상대에게 넘어간다.

폴링은 느리지만 스스로 복구되고 위조될 일이 없다. 웹훅은 빠르지만 유실되면 끝이고 위조가 가능하다. 그래서 결론을 미리 말하면 — 실무는 둘 중 하나를 고르는 게 아니라 웹훅을 1차 트리거로 쓰고 폴링을 안전망으로 까는 조합을 쓴다(9절).

가상계좌는 웹훅 없이는 사실상 성립하지 않는다 고객이 언제 입금할지 아무도 모르기 때문이다. 10분 뒤일 수도, 사흘 뒤일 수도 있다. "돈이 들어왔는지"를 폴링으로만 확인하려면 모든 미입금 주문을 며칠 동안 계속 조회해야 한다. 웹훅이 필요한 가장 선명한 사례다.

1-2. 비유 — 은행에서 걸려온 "입금됐습니다" 전화

웹훅을 한 문장으로 비유하면 은행이 전화로 "입금됐습니다"라고 알려주는 것이다. 편리하다. 내가 계좌를 계속 들여다볼 필요가 없으니까. 그런데 이 전화를 그대로 믿고 장부에 적으면 세 가지 사고가 난다.

① 위조 — 진짜 은행 직원인가

사기꾼이 "입금됐어요"라고 전화하면 물건을 공짜로 내주게 된다. 전화기에는 발신자가 진짜인지 확인해주는 장치가 없다.

② 중복 — 같은 내용을 두 번

"아까 전화가 잘 갔는지 확실치 않아서요" 하며 같은 통보가 또 온다. 두 번 다 처리하면 잔액이 이중으로 늘어난다.

③ 역전 — 취소가 먼저 도착

통신 사정으로 "입금 취소" 전화가 "입금 완료"보다 먼저 온다. 나중에 온 "완료"가 이미 취소된 거래를 되살린다.

세 글자로 압축한다 — 위 · 중 · 역

위조된다 · 중복 온다 · 역전된다  →  각각 보안 사고 · 이중 지급 · 상태 꼬임

면접에서 이 질문을 받으면 가장 먼저 이 세 단어를 던지고 하나씩 방어책을 붙여 나가면 된다. 순서도 이 순서가 자연스럽다 — 요청이 들어오는 순서(누구인가 → 처음인가 → 반영해도 되는가)와 같기 때문이다.

2. 세 가지는 "재수 없는 예외"가 아니라 정상 현상이다

여기가 이 주제의 갈림길이다. 셋을 드물게 터지는 버그로 보면 방어를 예외 처리로 짜게 되고, 메커니즘상 반드시 생기는 정상 현상으로 보면 방어가 설계의 뼈대가 된다. 왜 후자인지를 하나씩 짚는다.

2-1. 왜 위조가 가능한가 — 엔드포인트는 공개 인터넷에 열려 있다

웹훅 엔드포인트는 PG사 서버가 호출해야 한다. PG사 서버는 우리 사내망 안에 있지 않다. 따라서 이 URL은 공개 인터넷에서 접근 가능한 상태로 열어둘 수밖에 없다. 여기까지는 선택의 여지가 없는 구조적 사실이다.

2-2. 왜 중복이 오는가 — at-least-once가 무슨 뜻인가

발신측(PG사)은 우리에게 요청을 보내고 응답을 기다린다. 2xx를 받으면 "전달 성공"으로 표시하고, 못 받으면 실패로 보고 잠시 후 다시 보낸다. 여기까지는 상식적이다. 문제는 응답을 못 받은 것이 "처리가 안 됐다"는 뜻은 아니라는 점이다.

발신측이 취할 수 있는 태도는 원리적으로 둘뿐이다.

at-most-once (최대 1회)
응답을 못 받아도 재전송하지 않는다. 중복은 없지만 유실이 생긴다. 결제 승인 통보가 사라지는 것을 허용하는 셈이니 결제에서는 쓸 수 없다.
at-least-once (최소 1회)
확실해질 때까지 재전송한다. 유실은 없지만 중복이 생긴다. 결제 웹훅은 예외 없이 이쪽이다.

"정확히 한 번(exactly-once)"은 왜 없나

서로 다른 두 시스템 사이의 네트워크 위에서는 만들 수 없다. 마지막 메시지가 도착했는지를 확인하는 메시지 역시 도착 여부를 알 수 없어서, 확인의 확인이 무한히 필요해지기 때문이다.

실무의 exactly-once = at-least-once 전달 + 수신측 중복 제거

그래서 중복 제거는 수신측 책임이다. 이걸 발신측 탓으로 돌리면 설계 자체가 시작되지 않는다. 면접에서 "PG사가 중복을 안 보내게 해야죠"라고 답하면 이 대목을 모른다는 신호가 된다.

2-3. 왜 순서가 뒤집히는가 — 재시도가 순서를 흩뜨린다

이벤트가 발생한 순서와 도착한 순서가 다를 수 있는 이유는 여러 가지다. 발신측이 여러 워커로 병렬 발송하거나, 네트워크 경로가 달라지거나, 우리 쪽 여러 인스턴스가 각각 다른 속도로 처리하거나. 하지만 실무에서 압도적으로 흔한 원인은 재시도다. 한 이벤트가 재시도 대기열에서 몇 분을 기다리는 동안, 그 뒤에 발생한 이벤트는 한 번에 성공해 먼저 도착한다.

3. 수신부 설계 지도 — 관문 네 개 + 운영 원칙 둘

이제 방어를 세운다. 웹훅 하나가 도착해서 실제로 반영되기까지 네 개의 관문을 통과하고, 그 관문들을 두 개의 운영 원칙이 떠받친다. 아래 그림이 이 페이지 나머지 전체의 뼈대다.

비유로 묶어 외운다 — 건물 로비의 경비 데스크

① 신분증 확인
위조 사원증은 못 만든다 = HMAC 서명
② 본사에 전화
"이 사람 맞나요?" = 조회 API 재확인
③ 방명록 서명
이미 적혀 있으면 다시 안 적는다 = event_id 유니크
④ 출입 규칙표
퇴근 처리된 사람은 재입장 불가 = 상태 머신

신분증만 봐도, 방명록만 적어도 부족하다. 네 개가 서로 다른 종류의 잘못을 잡기 때문에 넷 다 필요하다는 점을 이 비유가 붙잡아 준다.

4. 1차 방어 — 발신자 검증: HMAC 서명이 본체, IP 화이트리스트는 보조

(a) 어디서 왔는지 본다
발신 IP를 확인한다.
(b) 아무나 못 만드는 증거물을 요구한다
서명을 검증한다.

상호 TLS(mTLS, 클라이언트도 인증서를 제시하는 방식)라는 세 번째 길도 있지만, PG사가 지원해야 쓸 수 있고 인증서 관리 부담이 커서 일반적인 웹훅 연동에서는 표준이 아니다. 실무에서 실제로 고르는 것은 (a)와 (b)이고, 정답은 "(b)가 본체, (a)는 보조"다.

4-1. 해시 → HMAC — "발신자만 만들 수 있는 지문"으로 가는 두 걸음

1
해시는 데이터의 지문이다. 임의 길이의 입력을 고정 길이 값으로 뭉개는 단방향 함수다. 같은 입력은 항상 같은 출력을 내지만 출력에서 입력을 되돌릴 수는 없다. 본문이 한 글자만 바뀌어도 지문이 완전히 달라지므로, 지문을 비교하면 변조 여부를 알 수 있다.
2
그런데 지문만 붙여 보내면 소용이 없다. 공격자도 같은 해시 함수를 돌릴 수 있어서, 본문을 위조한 뒤 그에 맞는 지문을 새로 계산해 붙이면 그만이기 때문이다. 지문을 발신자만 만들 수 있게 해야 한다.
3
여기서 비밀키가 등장한다 — HMAC은 "비밀키를 섞어 만든 지문"이다. (Hash-based Message Authentication Code) 발신자와 우리만 아는 시크릿을 본문과 함께 해싱하므로, 시크릿을 모르는 제3자는 본문을 위조해도 같은 지문을 만들 수 없다.
비유 — 인감도장 도장 자국(서명)은 누구나 볼 수 있지만, 도장 자체(시크릿)를 가진 사람만 같은 자국을 찍을 수 있다. 그래서 HMAC은 발신자가 누구인지(인증)와 본문이 변조되지 않았는지(무결성)를 한 번에 증명한다.

왜 equals로 비교하면 안 되나 — 타이밍 공격

자바의 문자열 비교는 앞에서부터 한 글자씩 보다가 다른 글자를 만나면 즉시 끝난다. 그래서 첫 글자부터 틀린 값은 빨리 실패하고, 앞 열 글자가 맞는 값은 조금 더 오래 걸린다. 이 미세한 시간 차이가 "몇 글자까지 맞췄는지"를 공격자에게 알려주는 통로가 된다.

공격자는 첫 글자를 0부터 f까지 바꿔가며 응답 시간이 미세하게 늘어나는 값을 찾고, 그 자리를 확정한 뒤 다음 글자로 넘어가는 식으로 서명을 한 글자씩 복원할 수 있다.

서명 비교는 길이와 무관하게 항상 같은 시간이 걸리는 상수 시간 비교로 — 자바는 MessageDigest.isEqual

이 함수는 중간에 끊지 않고 모든 바이트를 끝까지 훑어 차이를 누적한 뒤 마지막에 한 번 판정하기 때문에 실행 시간이 입력에 따라 달라지지 않는다.

구현 서명 검증기 — 세 가지(원문·상수 시간·타임스탬프)를 한자리에서
public boolean verify(String rawBody, String timestamp, String receivedSignature) {
    // ① 타임스탬프 허용 오차 검사 — 재전송 공격의 창을 좁힌다.
    long skewSeconds = Math.abs(Instant.now().getEpochSecond() - Long.parseLong(timestamp));
    if (skewSeconds > 300) return false;   // 5분

    // ② 서명 대상은 "타임스탬프 + 원문 바디" — 발신측과 조립 규칙이 한 글자도
    //    달라선 안 된다. 구분자·인코딩까지 연동 문서대로 맞춘다.
    byte[] message = (timestamp + "." + rawBody).getBytes(StandardCharsets.UTF_8);

    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
    byte[] expected = mac.doFinal(message);

    // ③ 상수 시간 비교. equals를 쓰면 "몇 글자까지 맞췄는지"가 시간으로 샌다.
    return MessageDigest.isEqual(expected, HexFormat.of().parseHex(receivedSignature));
}

  • 즉 IP 제한은 보안 장치이면서 동시에 장애 유발 장치다

그래도 IP 제한을 거는 이유

  • 무작위 스캐너가 엔드포인트에 닿는 것 자체를 막는다 — 서명 검증 연산조차 소모하지 않는다
  • 대량 위조 요청으로 인한 부하·로그 오염을 앞단에서 걷어낸다
  • 없는 것보다 낫다. 다만 그것만 믿어서는 안 된다.
서명 검증이 필수 방어, IP 제한은 공격 표면을 줄이는 보조 방어

5. 2차 방어 — 페이로드를 믿지 말고 거래 조회 API로 재확인한다

서명 검증까지 통과했으면 이제 본문을 믿어도 될까. 결제 도메인의 관례는 "아니오"다. 이유는 서명이 증명해주는 범위가 생각보다 좁기 때문이다.

서명이 증명하는 것

  • 이 바이트열은 시크릿을 가진 쪽이 만들었다
  • 전송 중 변조되지 않았다
  • (타임스탬프를 포함했다면) 최근에 만들어졌다

서명이 증명하지 않는 것

  • 우리 쪽 검증 구현에 실수가 없다는 것 — 재직렬화 본문으로 검증하고 있었다거나, 검증 실패를 로그만 남기고 통과시키고 있었다거나
  • 시크릿이 유출되지 않았다는 것 — 설정 파일이 git에 올라갔거나, 로그에 찍혔거나, 퇴사자가 들고 나갔거나
  • 발신측이 버그로 잘못된 값을 보내지 않았다는 것

돈이 걸린 값 — 금액과 상태 — 에 대해서는 이 정도 확률도 감당하기 어렵다. 그래서 신뢰 경계(trust boundary, 시스템이 "여기서부터는 믿지 않는다"라고 선을 긋는 지점)를 한 겹 더 둔다.

한 문장으로 외운다

웹훅은 초인종, 진실은 조회 API

웹훅의 역할을 "지금 조회해보라고 알려주는 신호"로 격하시키는 것이다. 초인종은 "누가 왔다"는 사실만 알려주지, 온 사람이 누구이며 무엇을 들고 왔는지는 말해주지 않는다 — 그건 문을 열어(조회해) 봐야 안다.

비용도 같이 말해야 완결된다 이벤트마다 외부 API 호출이 한 번씩 늘어난다. 이 호출은 수백 ms가 걸릴 수 있고 PG사 장애 시 실패할 수도 있다. 그래서 조회는 웹훅 응답을 돌려주는 동기 구간이 아니라 비동기 워커 안에서 한다(8절). 급한 것은 응답이고, 정확한 것은 나중에 해도 된다.

6. 3차 방어 — 멱등성: 이벤트 ID + 유니크 제약으로 중복을 제거한다

멱등(idempotent)은 "여러 번 해도 한 번 한 것과 결과가 같다"는 성질이다. 수학에서 온 말인데(같은 연산을 거듭 적용해도 값이 변하지 않는다는 뜻), 분산 시스템에서는 재시도를 안전하게 만드는 핵심 성질로 쓰인다.

멱등한 것 — 엘리베이터 버튼
열 번 눌러도 엘리베이터는 한 번 온다.
멱등하지 않은 것 — "잔액에 3,000원 더하기"
두 번 하면 6,000원이 늘어난다. 웹훅 처리가 이대로 짜여 있으면 재전송이 곧 사고다.

그럼 어떻게 멱등하게 만드는가. 방법은 "이미 처리한 이벤트인지 기억하고 두 번째부터는 건너뛴다"이다. 기억할 열쇠가 필요한데, 그게 발신측이 이벤트마다 부여하는 고유 ID(event_id)다. 재시도할 때도 같은 ID를 유지하는 것이 웹훅 발신측의 기본 계약이다.

6-1. 초보적인 구현이 뚫리는 지점 — check-then-act

스키마 수신한 웹훅 이벤트를 그대로 적어두는 원장 테이블 (PostgreSQL)
CREATE TABLE webhook_event (
    event_id     text PRIMARY KEY,           -- PG사가 준 이벤트 고유 ID.
                                             -- PK = 유니크 제약이므로 같은 ID의
                                             -- 두 번째 INSERT는 DB가 막아준다.
    event_type   text        NOT NULL,       -- APPROVED, CANCELLED …
    payment_key  text        NOT NULL,       -- 거래 식별자. 조회 API 호출용 키
    payload      jsonb       NOT NULL,       -- 원문 보관. "그때 뭐가 왔길래 이렇게
                                             -- 처리됐지"를 되짚거나 재처리할 때 필요
    status       text        NOT NULL DEFAULT 'RECEIVED',
                                             -- RECEIVED → PROCESSED | FAILED.
                                             -- 워커가 죽어도 여기 남아 있어야
                                             -- 재처리 배치가 다시 집는다
    received_at  timestamptz NOT NULL DEFAULT now()
);

상태 코드는 "잘 받았다"의 의미이지 "반영했다"의 의미가 아니다

409나 4xx를 주면 발신측이 "전달 실패"로 해석해 계속 재전송하거나, 재시도 한도를 소진하고 데드레터로 보내 상대 운영팀에 알람을 울린다. 중복은 우리 입장에서 "이미 반영이 끝난 정상 상황"이므로, 성공을 알려 재시도를 끝내주는 것이 맞다. 같은 원칙이 7절의 "역전 이벤트 무시"에도 그대로 적용된다 — 두 경우를 한 문장으로 묶어 설명하면 답이 단단해진다.

7. 4차 방어 — 순서 역전: 도착 순서가 아니라 상태 머신이 정한다

2-3절에서 봤듯 도착 순서는 믿을 수 없다. 그럼 무엇을 근거로 "이 이벤트를 반영할지 말지"를 정해야 할까. 선택지를 늘어놓고 보자.

(a) 도착 순서대로 덮어쓴다

last-write-wins. 늦게 온 승인이 취소를 덮어써서 사고가 난다. 탈락.

(b) 발생 시각을 비교한다

방향은 맞지만 — 발신측 서버의 시계를 우리가 검증할 수 없고(서버 간 시계는 늘 조금씩 어긋난다), 같은 초에 발생한 두 이벤트는 구분이 안 되며, 애초에 발생 시각을 안 주는 PG사도 있다.

(c) 전이가 허용되는지로 판단한다

외부 시계에 의존하지 않고, 우리 DB에 있는 현재 상태만으로 결정할 수 있다. 정답은 이쪽이고, (b)는 (c)를 보조하는 근거로만 쓴다.

(c)를 구현하는 장치가 상태 머신(state machine)이다. 상태 머신은 두 가지로 정의된다 — 가질 수 있는 상태의 목록과 어떤 상태에서 어떤 상태로 갈 수 있는지의 목록(전이 규칙). 여기 없는 전이는 일어날 수 없다고 선언하는 것이 핵심이다. 보드게임의 말과 같다 — 말이 놓일 수 있는 칸이 정해져 있고, 각 칸에서 갈 수 있는 다음 칸도 정해져 있다. 규칙에 없는 이동은 "그런 수는 없다"며 거부한다.

7-1. 반대 방향 — 승인보다 취소가 먼저 오면

READY 상태인 주문에 취소 웹훅이 왔다는 뜻인데, 여기는 조금 더 미묘하다. 두 가지 전략이 있고 어느 쪽을 택하든 근거를 말할 수 있어야 한다.

(가) READY → CANCELLED를 허용 전이로 정의하고 바로 종결

  • 단순하다. 규칙 한 줄이면 끝난다.
  • 이후 승인 웹훅이 와도 CANCELLED가 종결 상태라 자동으로 막힌다.
  • 대신 "실제로는 승인 후 취소된 건"과 "애초에 승인이 안 된 건"을 구분하지 않는다.

(나) 이상 신호로 보고 보류 큐에 넣은 뒤 조회 API로 확정

  • "아직 승인도 안 됐는데 취소가 왔다"를 판단을 미룰 사건으로 취급한다.
  • 잠시 후 PG사의 최종 상태를 조회해 확정한다. 느리지만 두 경우를 구분할 수 있다.
  • 정산·회계에서 취소 사유 구분이 필요한 도메인이라면 이쪽.
어느 쪽을 택하든 공통 원칙은 같다 — 도착 순서에 상태를 맡기지 않는다

발생 시각과 시퀀스 번호가 페이로드에 있으면 보조 판단 근거로는 쓰되, 그것만으로 결정하지는 않는다.

8. 운영 원칙 ① — 빠른 200 + 비동기 처리: 수신과 처리의 분리

발신측은 응답이 일정 시간(보통 5~10초) 안에 오지 않으면 타임아웃으로 간주하고 재전송한다. 그런데 수신 핸들러 안에서 조회 API 호출, 포인트 적립, 알림 발송, 정산 반영까지 다 하면 처리 시간이 쉽게 그 한계를 넘는다. 여기서 벌어지는 일이 고약하다.

동기와 비동기를 가르는 기준 질문 하나

"이 작업을 안 하면 이벤트가 영영 사라지는가?"
예 → 동기 구간
서명 검증(안 하면 위조가 들어온다) · 이벤트 DB 저장(안 하면 200을 준 뒤 증발한다)
아니오 → 비동기
조회 API 호출 · 상태 반영 · 적립 · 알림 — 이벤트가 DB에 남아 있으면 나중에 해도 된다
여기서 가장 자주 틀리는 지점 — "저장"은 반드시 내구성 있는 저장(DB)이어야 한다 인메모리 큐에 넣고 200을 주면 프로세스가 재시작될 때 이벤트가 통째로 사라지고, 발신측은 이미 200을 받았으니 재전송하지 않는다. "빠른 200"은 일을 미루는 것이지 일을 잊는 것이 아니다.
before 검증 없음 + 페이로드 신뢰 + 동기 처리 + 중복 무방비
@PostMapping("/webhooks/pg")
public ResponseEntity<Void> onWebhook(@RequestBody PgEvent e) {
    if ("APPROVED".equals(e.status())) {
        orderService.markPaid(e.orderId(), e.amount());
        // 위조된 요청이 보낸 금액을 그대로 결제 완료로 반영한다.
        // 공격자가 임의 주문번호로 이 요청을 만들면 무료 구매가 된다.

        pointService.accrue(e.orderId());
        // 같은 event_id가 재전송되면 이 줄이 다시 실행된다 = 이중 적립.

        notificationService.send(e.orderId());
        // 알림 발송이 3초 걸리면 응답이 3초 늦어지고,
        // 발신측 타임아웃을 넘기면 재전송이 온다 = 스스로 만든 중복.
    }
    return ResponseEntity.ok().build();
}
after 서명 검증 → 원자적 저장 → 즉시 200 → 처리는 비동기
@PostMapping("/webhooks/pg")
public ResponseEntity<Void> onWebhook(
        @RequestHeader("X-Signature") String sig,
        @RequestHeader("X-Timestamp") String ts,
        @RequestBody String rawBody) {   // DTO가 아니라 원문

    // ① 발신자 확인. 내부에서 상수 시간 비교와
    //    타임스탬프 허용 오차(5분) 검사를 함께 수행한다.
    if (!signatureVerifier.verify(rawBody, ts, sig)) {
        return ResponseEntity.status(401).build();
    }
    PgEvent e = parse(rawBody);

    // ② "검사 + 선점"을 한 문장에. true = 최초 도착.
    boolean firstArrival = eventRepository.insertIfAbsent(e);

    if (firstArrival) {
        // ③ 실제 반영은 워커에게. 이벤트 본문은 이미 ②에서
        //    DB에 남았으므로 큐가 유실돼도 배치가 집는다.
        eventQueue.enqueue(e.eventId());
    }
    // ④ 중복이어도 200. 4xx를 주면 영원히 재시도한다.
    return ResponseEntity.ok().build();
}
worker 비동기 워커 — 페이로드가 아니라 조회 API의 값으로 최종 확정한다
void process(String eventId) {
    WebhookEvent e = eventRepository.findById(eventId);

    // ⑤ 신뢰 경계. 웹훅 본문에서는 거래 키만 취했고,
    //    금액·상태는 PG사 원장을 직접 읽어 확정한다.
    //    이 호출이 수백 ms 걸려도 괜찮다 — 여기는 동기 응답 경로가 아니다.
    PgPayment truth = pgClient.getPayment(e.paymentKey());

    // ⑥ 전이 규칙 위반이면 상태를 바꾸지 않고 무시한다.
    //    (CANCELLED 상태에 뒤늦은 APPROVED가 도착한 경우 등)
    payment.transitionTo(truth.status(), truth.amount());

    // ⑦ 여기까지 왔을 때만 처리 완료로 표시한다.
    //    ⑥과 ⑦ 사이에 크래시가 나면 이벤트는 RECEIVED로 남아
    //    재처리된다 — 그래서 ⑥의 반영 로직 자체도 멱등해야 한다.
    eventRepository.markProcessed(eventId);
}

9. 운영 원칙 ② — 웹훅 유실 대비: 보정 폴링(대사)

지금까지의 방어는 전부 "웹훅이 오기는 온다"를 전제로 한다. 그런데 웹훅은 아예 안 올 수도 있다.

발신측 장애
PG사 발신 시스템 문제로 이벤트가 통째로 유실.
우리 쪽 장기 다운
배포·장애로 길게 죽어 재시도 한도를 모두 소진 → 발신측은 데드레터로 보내고 포기한다.
설정 사고
엔드포인트 URL 오설정, 방화벽 규칙 변경, 인증서 만료.
웹훅만 믿는 시스템의 최악은 "아무도 모른다"는 것 주문이 IN_PROGRESS에 영원히 머문다. 고객은 돈을 냈는데 주문은 미완료로 남고, 이 건은 아무도 발견하지 못한다 — 아무 이벤트도 오지 않았으니 트리거될 코드가 없기 때문이다. 에러 로그도, 알람도, 실패 카운터도 올라가지 않는다.
SQL 보정 대상 뽑기 — "진행 중인데 오래 멈춰 있는" 건만 (PostgreSQL)
SELECT payment_key
FROM payment
WHERE status IN ('READY', 'IN_PROGRESS')          -- 아직 종결되지 않았고
  AND updated_at < now() - interval '10 minutes'  -- 10분 넘게 그대로다
ORDER BY updated_at
LIMIT 500;
-- 조건 두 개가 모두 필요한 이유:
--   상태 조건이 없으면 이미 끝난 거래까지 매번 조회하게 되고,
--   시간 조건이 없으면 방금 시작한 정상 결제까지 붙잡아
--   PG사 조회 API에 불필요한 부하를 준다.
-- (status, updated_at) 복합 인덱스로 커버한다.

폴링 주기·범위를 정하는 두 가지 상한

위쪽 상한 — 조회 API 호출 한도
PG사가 정한 rate limit을 넘길 수 없다. LIMIT과 주기가 여기서 정해진다.
아래쪽 상한 — 방치 허용 시간
미결 건이 방치돼도 되는 최대 시간. 가상계좌 입금 확인이 30분 늦어도 되는지, 5분도 안 되는지가 도메인마다 다르다.

면접에서 이 두 상한을 함께 말하면 "배치 돌리면 됩니다"와는 다른 층위의 답이 된다.

10. 실무 사례 셋 — 하나씩 빼먹으면 정확히 무슨 일이 생기나

사례 1 — IP 화이트리스트만 믿다가 위조 웹훅으로 무료 구매 위조

1
서명 검증 없이 IP 제한만 걸어둔 가맹점. 처음에는 PG사 발신 IP가 몇 개뿐이라 잘 동작했다.
2
PG사가 발신 인프라를 클라우드로 옮기면서 IP 대역이 넓어졌다. 웹훅이 간헐적으로 차단되기 시작했고, 운영팀은 결제 누락 장애를 피하려 대역 전체를 허용해버렸다. 보안 장치가 가용성 사고를 일으켰고, 그걸 피하려다 보안 장치가 무력화됐다.
3
같은 클라우드를 쓰는 공격자가 이 구멍을 찾았다. 결제창에서 주문번호 채번 규칙을 관찰한 뒤, 89,000원짜리 주문에 status: "APPROVED"로 채운 위조 웹훅을 쏘았다. 요청은 허용된 대역에서 왔으므로 통과했고, 주문은 실제 결제 승인 없이 PAID가 되어 상품이 발송됐다.
두 방어 중 하나만 있었어도 막혔다 — 계층 방어의 뜻 HMAC 서명 검증이 있었다면 시크릿을 모르는 공격자의 요청은 401에서 끝났다. 서명이 없더라도 조회 API 재확인이 있었다면 PG사가 "그 거래는 READY(승인 전)입니다"라고 답했을 것이다.

사례 2 — 처리 후 응답 유실 → 재전송 → 적립금 이중 지급 중복

1
승인 웹훅을 받아 적립금 3,000원을 지급하고 200을 반환하는 순간 로드 밸런서 커넥션이 끊겼다. 우리 쪽 처리는 완료됐지만 발신측은 응답을 못 받았다.
2
PG사는 규정대로 실패로 판정하고 1분 뒤 같은 event_id로 재전송했다. 이벤트 ID 중복 제거가 없던 수신부는 적립 로직을 다시 실행했고, 고객 계정에 6,000원이 쌓였다.
3
건당 3,000원이라 사소해 보였고 팀도 초기에는 "드물게 생기는 일"로 넘겼다. 그런데 그날 밤 PG사 발신 서버 장애가 복구되면서 밀렸던 재전송이 한꺼번에 쏟아졌고, 수천 건의 이중 적립이 동시에 발생했다. 회수 공지와 CS 문의를 처리한 비용이 실제 지급액을 넘었다.
여기서 배울 것 — 분산 시스템의 중복은 고르게 오지 않는다 webhook_event(event_id PRIMARY KEY) 한 줄과 ON CONFLICT DO NOTHING 한 줄이 막아주는 사고다. 그리고 중복은 장애 복구 시점에 몰려서 온다 — 평소 빈도로 리스크를 계산하면 안 되는 이유다.

사례 3 — 순서 역전으로 취소된 주문이 다시 "결제 완료" 역전

1
고객이 120,000원을 결제한 직후 마음을 바꿔 곧바로 취소했다. PG사는 승인 이벤트와 취소 이벤트를 몇 초 간격으로 연달아 발신했다.
2
승인 웹훅의 첫 전송이 우리 서버의 순간적인 지연으로 타임아웃 나서 재시도 큐로 빠졌고, 그 사이 취소 웹훅이 먼저 도착해 정상 처리됐다. 1분 뒤 재시도된 승인 웹훅이 뒤늦게 도착했다.
3
수신부는 "마지막에 도착한 게 최신 상태"라는 전제로 상태를 덮어쓰는 구조였다. 뒤늦게 도착한 승인 웹훅이 CANCELLED였던 주문을 PAID로 되돌렸고, 출고 시스템은 PAID 주문을 정상 주문으로 보고 상품을 내보냈다. 고객은 환불을 받았는데 상품도 받았다 — 120,000원 손실에 회수 비용이 더해졌다.
코드로는 조건문 하나, 설계로는 전제의 차이 상태 머신이 CANCELLED를 종결 상태로 선언하고 CANCELLED → PAID 전이를 거부했다면, 늦게 온 승인 웹훅은 로그 한 줄만 남기고 200과 함께 버려졌을 것이다. 차이는 "도착 순서를 믿는가 아닌가"라는 설계 전제다.

가용성 리스크. 발신 IP는 PG사 인프라 변경으로 예고 없이 바뀌어 정상 트래픽을 차단한다 — 보안 장치가 장애 유발 장치가 된다. 그리고 그 장애를 피하려 대역을 넓히는 순간 보안 효과가 사라진다(10절 사례 1).
2
신원 보장 실패. 클라우드 NAT나 공유 프록시 뒤에서는 같은 IP 대역을 제3자도 쓴다. "이 IP = PG사"라는 등식이 성립하지 않는다.
3
무결성 무증명. IP는 발신 위치만 말해줄 뿐, 본문이 변조됐는지는 전혀 증명하지 못한다.

반면 HMAC 서명은 발신자 인증 + 본문 무결성 + (타임스탬프를 서명에 포함하면) 재전송 방지까지 준다.

서명이 필수 방어, IP는 공격 표면을 줄이는 보조 방어 — 둘은 대체재가 아니라 계층이다

덧붙이면 좋은 한 줄: "IP 제한은 무작위 스캐너가 엔드포인트에 닿는 것 자체를 막아주므로 없는 것보다는 낫습니다. 다만 그것만 믿으면 안 됩니다."

서명 검증까지 했는데 왜 조회 API로 또 확인하나요? 필수힌트: "서명이 증명하는 범위"를 정확히 긋는 것이 답의 핵심이다

서명은 "시크릿을 가진 쪽이 만든 바이트열이고 전송 중 변조되지 않았다"까지만 증명한다. 다음 세 가지는 서명으로 걸러지지 않는다.

웹훅은 초인종, 진실은 조회 API

비용도 함께 말하면 완결된다 — "이벤트마다 외부 호출이 한 번 늘어나므로, 이 호출은 동기 응답 경로가 아니라 비동기 워커 안에서 합니다."

중복 웹훅에는 어떤 상태 코드를 줘야 하나요? 필수힌트: 409를 떠올렸다면, 그 응답을 받은 발신측이 무엇을 할지 생각해본다
200이다

409나 4xx를 주면 발신측이 전달 실패로 간주해 계속 재전송하거나, 재시도 한도를 소진한 뒤 데드레터로 보내 상대 운영팀에 알람을 울린다. 중복은 우리 입장에서 "이미 반영이 끝난 정상 상황"이므로 성공으로 응답해 재시도를 종료시키는 것이 맞다.

같은 논리가 순서 역전으로 버리기로 판단한 이벤트에도 적용된다. 상태는 바꾸지 않고, 이벤트는 남기고, 로그를 찍고, 200을 준다.

상태 코드는 "잘 받았다"의 의미이지 "반영했다"의 의미가 아니다 — 이 한 문장으로 두 경우를 묶는다

거꾸로 정말로 재시도를 받아야 하는 상황(DB 다운으로 저장 자체를 못 했다 등)에는 5xx를 주는 것이 맞다. "무조건 200"이 아니라 "재시도가 도움이 되는가"로 나눈다고 말하면 한 단계 더 들어간 답이 된다.

비동기 처리 중에 워커가 실패하면 이벤트가 유실되지 않나요? 필수힌트: 답의 근거는 "언제 무엇을 저장했는가"에 있다

유실되지 않는다. 수신 시점에 이벤트를 DB에 RECEIVED 상태로 먼저 저장했기 때문이다. 워커는 처리에 성공했을 때만 PROCESSED로 바꾸므로, 실패하면 RECEIVED로 남아 재처리 배치가 다시 집는다.

여기서 짚어야 할 전제 "빠른 200"의 전제는 인메모리 큐가 아니라 내구성 있는 저장 후 응답이다. 메모리 큐에 넣고 200을 주면 프로세스 재시작 시 이벤트가 사라지고, 발신측은 이미 200을 받았으니 다시 보내주지도 않는다.

한 가지 더 덧붙이면 완결된다 — 처리 완료 표시 직전에 크래시가 나면 같은 이벤트가 재처리되므로 반영 로직 자체도 멱등해야 한다. 전송 계층에서 중복을 걸렀다고 도메인 로직의 멱등성이 면제되는 것은 아니다.

PG사가 이벤트 ID를 안 주면 중복 제거를 어떻게 하나요? 시니어 변별힌트: 대안을 하나 대는 것보다, "전송 계층과 도메인 계층을 구분"하는 것이 변별 포인트다

페이로드 안의 값들을 조합해 자연 키(natural key, 데이터 자체에 이미 들어 있는 식별 정보로 만든 키)를 만든다. 예를 들어 거래ID + 이벤트타입 + 상태 + 발생시각의 해시를 유니크 키로 쓴다.

단서 하나 — 재전송 시 발생시각이 갱신되는가 발신측이 재전송할 때 발생시각을 갱신해 보내는지 원본 그대로 보내는지에 따라 키 구성이 달라진다. 갱신해서 보낸다면 발생시각은 키에서 빼야 하고, 대신 다른 값으로 유일성을 만들어야 한다. 이건 연동 문서와 실측으로 확인할 일이지 추측할 일이 아니다.

어떤 조합으로도 유일성이 안 만들어지는 경우가 있다. 그때는 마지막 수단으로 상태 머신 자체의 멱등성에 기댄다 — 같은 거래의 같은 상태 전이는 상태 머신이 어차피 두 번 적용하지 않는다(이미 PAID인 주문에 PAID 전이가 또 와도 아무 변화가 없다).

그래도 남는 구멍 — 부수효과 적립·알림 같은 부수효과는 상태 전이와 별개로 실행되므로, 상태 머신 멱등성만으로는 못 막는다. 거래ID 기준 실행 이력 테이블로 따로 막아야 한다.
이 답의 변별 포인트 — 전송 계층의 중복 제거(event_id 유니크)와 도메인 계층의 멱등성(상태 머신 + 실행 이력)을 구분해 말하는 것

앞이 없으면 뒤가 대신할 수는 있어도 완전히 대체하지는 못한다.

웹훅으로 빠르게, 폴링으로 빠짐없이

여기에 폴링 대상을 좁히는 조건(진행 중 상태 + 경과 시간)과 주기 설정 기준(PG사 조회 API의 호출 한도, 미결 건이 방치돼도 되는 최대 시간)까지 말하면 운영 감각을 보여줄 수 있다.

웹훅을 여러 인스턴스가 나눠 받는데, 같은 거래의 이벤트가 동시에 처리되면요? 시니어 변별힌트: "멱등성 키가 있으니 괜찮다"고 답했다면 함정에 빠진 것이다

event_id 유니크 제약은 같은 이벤트의 중복만 막는다. 서로 다른 이벤트(승인과 취소)가 같은 거래에 대해 서로 다른 인스턴스에서 동시에 처리되는 것은 막지 못한다. 두 워커가 동시에 현재 상태를 읽고 각자 전이를 적용하면, 상태 머신 검증을 통과한 채로 마지막 쓰기가 이기는 상황이 다시 만들어진다.

해결은 거래 단위 직렬화다. 방법은 세 가지가 있고 각각 대가가 다르다.

① 비관적 락
처리 시작 시 해당 결제 행을 SELECT … FOR UPDATE로 잠근다. 가장 단순하지만 트랜잭션이 길어지면 경합이 생긴다.
② 낙관적 락
버전 컬럼을 두고 충돌 시 재시도. 경합이 드물면 효율적이다.
③ 파티션 키
큐를 쓴다면 거래 ID를 파티션 키로 삼아 같은 거래의 이벤트가 항상 같은 컨슈머로 가게 한다. 순서까지 함께 얻지만 큐 인프라가 필요하다.
변별 포인트 — "멱등성 키는 이벤트 중복을, 락은 동시성을 막는다. 둘은 다른 문제다"

서명 검증에 실패한 요청에는 무엇을 응답하고, 무엇을 남기나요? 함정힌트: 응답 코드보다 "5xx를 주면 안 되는 이유"와 "알람을 걸어야 하는 이유"가 핵심이다

4xx(보통 401)를 준다. 이유는 재시도가 도움이 되지 않기 때문이다 — 서명이 틀린 요청은 몇 번을 다시 보내도 틀린다. 여기서 5xx를 주면 발신측이 "우리 쪽 일시 장애"로 해석해 재시도 한도를 소진할 때까지 계속 두드린다.

응답 본문에 쓰지 말아야 할 것

  • "서명 불일치: 기대값 a3f9…" 같은 상세 — 공격자에게 힌트를 준다
  • 타임스탬프 오차 범위, 서명 알고리즘 세부 — 필요 이상으로 알려주지 않는다

대신 반드시 남길 것

  • 알람. 서명 실패는 둘 중 하나다 — 공격이거나, 시크릿이 어긋난 것(로테이션 사고·설정 오배포)
  • 후자라면 정상 웹훅이 전부 401로 떨어지고 있다는 뜻이므로 결제 누락 장애다. 조용히 넘기면 안 된다
  • 발신 IP·타임스탬프·요청 ID는 서버 로그에 (응답이 아니라)

한 줄로: "실패는 조용히 응답하고 시끄럽게 로깅한다."

웹훅 시크릿은 어떻게 교체(로테이션)하나요? 가산점힌트: 교체 순간에 "구 시크릿으로 서명된 요청"이 이미 날아오고 있다

핵심은 교체가 원자적일 수 없다는 것이다. 우리가 새 시크릿으로 바꾸는 그 순간에도 구 시크릿으로 서명된 요청이 이미 네트워크에 떠 있고, 재시도 큐에는 더 오래된 것도 남아 있다. 그래서 양쪽을 동시에 받아주는 기간을 둔다.

1
신규 시크릿을 발급받아 우리 쪽에 먼저 추가한다. 검증기가 구·신 두 개를 모두 시도하도록 만든다(둘 다 상수 시간 비교로).
2
PG사 콘솔에서 발신 시크릿을 신규로 전환한다. 이 시점부터 새 요청은 신규 서명으로 오고, 재시도 큐에 남은 옛 요청은 여전히 구 서명으로 온다 — 둘 다 통과한다.
3
발신측 최대 재시도 기간이 지나면 구 시크릿을 제거한다. 그 전까지는 "구 시크릿으로 검증 성공한 건수" 지표를 보고, 0이 된 것을 확인하고 내린다.

PG사가 키 식별자 헤더(어느 시크릿으로 서명했는지)를 제공하면 두 번 계산할 필요 없이 하나만 고르면 된다. 그리고 시크릿은 애플리케이션 설정 파일이 아니라 시크릿 매니저에 두고, 로그·에러 메시지에 절대 찍히지 않게 한다 — 5절에서 "시크릿 유출"을 신뢰 경계의 이유로 든 게 바로 이 지점이다.

webhook_event 테이블이 계속 커지는데, 오래된 행을 지워도 되나요? 함정힌트: 이 테이블은 로그가 아니라 "중복 제거의 근거"다

이벤트 저장과 큐 발행을 같은 트랜잭션에 넣으면 되지 않나요? 시니어 변별힌트: 큐는 DB 트랜잭션에 참여하지 않는다

넣을 수 없다. DB와 큐는 서로 다른 시스템이라 하나의 트랜잭션으로 묶이지 않는다. 그래서 어떻게 짜도 두 실패 모드 중 하나가 남는다 — 커밋 후 발행 실패(이벤트는 저장됐는데 워커가 안 깨어난다), 또는 발행 후 롤백(워커가 없는 이벤트를 찾아간다). 이것을 이중 쓰기(dual write) 문제라 한다.

우리 설계가 이미 답을 갖고 있다 webhook_event 테이블이 사실상 아웃박스(outbox) 역할을 한다. 진실은 DB에 있고 큐는 "빨리 깨우는 신호"일 뿐이므로, 큐 발행이 실패하거나 메시지가 유실돼도 RECEIVED 상태로 남은 이벤트를 재처리 배치가 집어간다. 큐를 정확성의 근거가 아니라 지연 단축 수단으로 격하시킨 것이 핵심이다.

정리하면 순서는 "DB 커밋 → 큐 발행"이다. 반대로 하면 워커가 아직 커밋되지 않은 이벤트를 조회해 못 찾는 경쟁이 생긴다(같은 이유로 @TransactionalEventListener(AFTER_COMMIT) 같은 장치를 쓴다).

여기서 "웹훅은 초인종, 진실은 조회 API"와 같은 구조가 내부에서 한 번 더 반복된다고 짚으면 좋다 — 빠른 경로와 정확한 경로를 분리하고, 빠른 경로가 실패해도 정확한 경로가 덮는다.

재처리 배치가 계속 실패하는 이벤트를 무한히 다시 집으면요?힌트: 하나의 나쁜 이벤트가 전체 처리를 막지 않게 해야 한다

이벤트 행에 시도 횟수와 다음 시도 시각을 둔다. 실패할 때마다 시도 횟수를 올리고 지수 백오프로 다음 시각을 미룬다. 그래야 일시적 장애(PG사 조회 API 다운)는 스스로 회복되고, 배치가 같은 건을 초당 수십 번 두드리는 일이 없다.

임계 초과 시
FAILED로 표시하고 자동 재시도 대상에서 제외한 뒤 알람. 사람이 원인을 보고 고친 뒤 수동으로 되돌린다.
왜 제외하나
코드 버그처럼 재시도로 낫지 않는 실패가 배치 슬롯을 계속 차지하면, 정상 이벤트의 처리까지 늦어진다(독약 메시지 문제).

여기에 하나 더 — RECEIVED로 오래 남아 있는 이벤트 수를 지표로 걸고 알람을 붙인다. 이 수치가 늘면 워커가 죽었거나 특정 유형이 계속 실패하고 있다는 뜻이고, 9절의 보정 폴링이 잡아내는 "웹훅이 안 온 건"과는 다른 종류의 사고다. 둘 다 감시해야 한다.

한 줄 요약
웹훅 수신부는 "위조·중복·역전"을 정상 상황으로 전제하고 — HMAC 서명(+ 조회 API 재확인)으로 위조를, 이벤트 ID 유니크 제약으로 중복을, 상태 머신 전이 검증으로 순서 역전을 각각 방어하며 — 동기 구간은 검증·저장 후 빠른 200까지로 줄이고 실제 반영은 비동기 워커가, 유실은 보정 폴링이 받치는 구조로 만들어야 보안 사고·이중 지급·상태 꼬임을 모두 막을 수 있다.
