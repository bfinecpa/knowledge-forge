분산 Saga와 보상 설계
롤백이 없는 세계에서 돈을 옮기는 법

면접 질문: "분산 환경에서 '잔액 차감 + 주문 생성 + 이용권 지급'이 서로 다른 서비스에 있을 때 트랜잭션을 어떻게 설계하나요? (Saga, 보상, 멱등성)"

핵심 관전 포인트 — 잔액 차감·주문 생성·이용권 지급이 서로 다른 서비스(각자의 DB)에 있으면 전역 롤백은 존재하지 않는다. 2PC는 잠금을 쥔 채 코디네이터를 기다리는 블로킹 구조라 실무에서 배제되고, 답은 Saga다 — 각 서비스의 로컬 트랜잭션을 순서대로 실행하고, 중간 실패 시 이미 커밋된 단계를 보상 트랜잭션(차감의 보상 = 환급)으로 되돌린다. 돈 도메인에서는 흐름의 현재 위치를 한곳에서 추적할 수 있는 오케스트레이션이 유리하고, 오케스트레이터의 상태 전이와 커맨드 발행은 트랜잭셔널 아웃박스로 한 몸이 되게 만든다. 모든 단계는 orderId 기반 멱등성 키를 전파받아 유니크 제약으로 중복 실행을 막고(재전송 안전), 보상도 실패한다는 전제로 재시도 + 수동 개입 큐를 끝단에 둔다. Saga에는 격리성(I)이 없으므로 중간 상태는 PENDING으로 감춘다 — 교과서의 Saga를 "보상 실패·중복 전달·중간 상태 노출"이라는 돈의 현실에 착지시키는 것이 이 질문의 본체다.
  • 1
    전역 롤백이 없으므로 "되돌리기"를 "반대 방향의 새 작업"으로 바꾼다 — 로컬 트랜잭션 T1→T2→T3을 순서대로 커밋하고, 실패하면 역순 보상 C2→C1을 태운다. 차감의 보상은 환급이라는 새 원장 기록이지 기록의 삭제가 아니다. 2PC는 블로킹·최저속 종속·XA 미지원 세 가지 이유로 배제한다.
  • 2
    돈 도메인은 오케스트레이션 + 상태 테이블 + 아웃박스 — 진행 위치를 saga_instance 한 테이블로 추적해야 CS 즉답·타임아웃 스캔·수동 재개가 성립한다. 그리고 상태 전이와 커맨드 발행을 같은 트랜잭션에 묶기 위해 메시지를 같은 DB의 outbox 테이블에 INSERT하고 릴레이가 발행한다(이중 쓰기 → 단일 쓰기).
  • 3
    멱등성은 Saga의 전제 조건이고, 끝단에는 사람이 있다 — orderId를 모든 커맨드에 전파해 유니크 제약 + ON CONFLICT DO NOTHING + "이미 처리됨 = 성공 응답"으로 재전송을 안전하게 만든다. 중간 상태는 PENDING·INACTIVE로 감추고(격리성 부재 대응), 보상 실패는 백오프 재시도 → COMPENSATION_FAILED → 수동 개입 큐로 받는다.

0. 질문 + 출제 의도

질문: "분산 환경에서 '잔액 차감 + 주문 생성 + 이용권 지급'이 서로 다른 서비스에 있을 때 트랜잭션을 어떻게 설계하나요? (Saga, 보상, 멱등성)"

출제 의도: Saga의 교과서 지식을 돈 도메인의 현실 — 보상 실패 시 수동 개입 큐, 멱등성 키 전파 — 에 착지시킬 수 있는지 본다. 아키텍처 패턴과 도메인 요구를 동시에 쥐고 설계하는 시니어급 종합 문제다.

이 페이지가 겨냥하는 약점 세 가지 ① "Saga = T1·T2·T3 하고 실패하면 보상" 까지만 말하는 것 → 6~8절에서 아웃박스·상태 머신 가드·멱등성 키 전파라는 실제로 동작하게 만드는 부품을 붙인다.
② "보상은 성공한다"는 암묵적 가정 → 11절 사례 1과 12절 꼬리질문에서 보상 실패 3단 대응(설계로 예방 → 백오프 재시도 → 수동 개입 큐)을 세운다. "보상은 실패하지 않는다고 가정한다"는 답은 탈락 신호다.
③ 격리성(I) 부재를 놓치는 것 → 9절에서 T1 커밋 순간부터 중간 상태가 세상에 공개된다는 사실과 PENDING·INACTIVE 의미적 잠금을 붙인다.

1. 먼저 등장인물 — 이 문서에 계속 나오는 여덟 단어

이 주제는 낯선 명사가 한꺼번에 쏟아진다. 설계를 보기 전에 용어를 한 문장씩 정리하고 가자. 이 여덟 개만 알면 이 문서 전체를 읽을 수 있다.

로컬 트랜잭션
한 DB 안에서 끝나는 트랜잭션. @Transactional이 보장해 주는 그것. 분산 환경에서 우리가 원자성을 확신할 수 있는 유일한 단위이고, Saga는 이 단위를 여러 개 이어 붙여 만든다.
2PC · 코디네이터 · XA
2단계 커밋은 중앙의 코디네이터가 "준비됐나?"(prepare) → "커밋하라"(commit) 두 단계로 전원을 묶는 방식. XA는 그 참여 자격을 정의한 표준 인터페이스로, prepare와 commit을 나눠 받을 수 있는 자원만 참여할 수 있다.
Saga
전체 작업을 로컬 트랜잭션 T1→T2→T3으로 쪼개 순서대로 실행하고, 중간 실패 시 이미 커밋된 앞 단계를 보상으로 되돌리는 패턴. 원자성을 시간축으로 풀어낸 방식이다.
보상 트랜잭션
앞 단계를 되돌리는 "반대 방향의 새 트랜잭션". 차감(-9,900P)의 보상은 환급(+9,900P)이라는 새 원장 기록이다. 기록이 지워지는 것이 아니라 한 줄 더 쌓인다.
오케스트레이터
Saga 상태를 자기 DB에 들고 각 서비스에 커맨드를 보내고 응답으로 상태를 전이시키는 지휘자. 반대 방식이 코레오그래피(각 서비스가 이벤트를 구독해 스스로 다음 단계를 수행).
아웃박스 · 릴레이 · CDC
아웃박스는 "보낼 편지함" 테이블. 메시지를 Kafka로 바로 쏘는 대신 같은 DB에 INSERT한다. 릴레이는 그 테이블을 읽어 실제로 발행하는 별도 프로세스이고, 읽는 방식이 폴링 또는 CDC(DB 복제 로그 구독, 예: Debezium)다.
at-least-once
"적어도 한 번은 도착한다"는 전달 보장. "정확히 한 번"이 아니다. 릴레이·Kafka·컨슈머 오프셋 커밋 어디서든 같은 메시지가 두 번 처리될 수 있다는 뜻이고, 이 문서의 멱등성 논의는 전부 여기서 출발한다.
멱등성 · 멱등성 키
멱등성은 같은 작업을 여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질. "같은 작업"인지 판단하는 기준 식별자가 멱등성 키이고, 여기서는 orderId(필요하면 orderId + 단계명)다.
한 문장으로 묶으면 Saga(무엇을) = 로컬 트랜잭션의 연쇄 + 역순 보상 · 오케스트레이션(누가 이끄나) = 상태 테이블을 쥔 지휘자 · 아웃박스(어떻게 새지 않게) = 전이와 발행을 한 트랜잭션으로 · 멱등성(중복을 어떻게) = at-least-once를 유니크 제약으로 흡수. 이 네 단어가 답변의 뼈대다.

2. 분산에는 롤백 버튼이 없다

@Transactional이 여러 SQL을 "전부 성공 아니면 전부 없던 일"로 묶어줄 수 있는 이유는 하나다. DB 엔진이 변경 전 값을 별도로 보관하고 있다가 ROLLBACK 신호를 받으면 되돌려 주기 때문이다. 즉 롤백은 하나의 DB가 자기 데이터에 대해 제공하는 기능이다.

포인트 서비스·주문 서비스·콘텐츠 서비스가 각자 자기 PostgreSQL을 쓰는 구조에서는 이 전제가 무너진다. 포인트 서비스가 COMMIT을 끝낸 순간, 그 차감은 그쪽 DB에서 이미 확정된 과거다. 나중에 지급이 실패했다고 해서 남의 DB를 향해 "아까 그거 롤백해"라고 보낼 수 있는 명령은 존재하지 않는다. 커밋된 트랜잭션을 취소하는 표준 SQL은 없다.

그래서 분산 환경의 실패 처리는 "되돌리기"가 아니라 "반대 방향의 새 작업으로 메우기"가 된다
before REST 3연쇄 — 실패 지점마다 다른 세계가 남는다
public void order(OrderRequest req) {
    pointClient.deduct(req.userId(), 9900);            // ① 차감 — 남의 DB에 COMMIT
    orderClient.create(req);                           // ② 주문 생성
    ticketClient.grant(req.userId(), req.productId()); // ③ 지급

    // ②에서 실패하면? ①은 남의 DB에 이미 커밋됐다.
    // catch에서 pointClient.refund()를 부르면? 그 refund가
    // 타임아웃 나면? 부르기 직전에 이 서버가 죽으면?
    // — "지금 어디까지 진행됐는지"가 어디에도 기록돼 있지 않다.
}

이 코드의 진짜 결함은 예외 처리가 없다는 것이 아니다. 진행 상태가 메모리(스레드의 스택)에만 있다는 것이다. 스레드가 죽으면 "①까지는 했고 ②에서 실패했다"는 사실이 이 세상에서 사라진다. 누구도 이어받을 수 없다.

이 절의 결론 한 문장

분산 트랜잭션 설계의 출발점은 "어떻게 롤백할까"가 아니라 "어디까지 갔는지를 어디에 적을까"다

3. 2PC는 왜 실무에서 배제되는가

"분산 트랜잭션"이라는 말을 들으면 먼저 떠오르는 것이 2단계 커밋(2PC, two-phase commit)이다. 코디네이터라는 중앙 심판이 있고, 절차는 두 단계다 — prepare("준비됐나?" → 참여자는 잠금을 쥔 채 "예"로 답한다)와 commit(전원 OK면 커밋 전파, 하나라도 NO면 중단 전파).

이론상 완벽하다. 전원이 커밋하거나 전원이 중단하므로 분산 원자성이 성립한다. 그런데 실무의 결제 시스템에서는 배제된다.

2PC 배제 3근거 — "블 · 느 · 엑"

블 — 블로킹
prepare 후 참여자가 행 잠금을 쥔 채 대기. 코디네이터 장애가 전 참여자의 잠금 정체로 전파된다.
느 — 최저속에 종속
전체 시간 = 가장 느린 참여자 + 코디네이터 왕복 2회. 하나가 200ms면 그동안 다른 참여자의 행도 전부 잠겨 있다.
엑 — XA 미지원
Kafka·외부 PG·타 팀 HTTP API는 XA를 지원하지 않는다. 참여 자격 자체가 없다.
그래서 답은 "원자성을 시간축으로 풀어낸" 방식 — Saga다
비유로 굳히기 — 2PC는 "다 같이 셋 세고 뛰어내리기" 전원이 준비 자세로 굳은 채 구령을 기다려야 하고(잠금 보유), 가장 느린 사람이 준비될 때까지 전원이 그대로이며(최저속 종속), 구령 담당이 쓰러지면 아무도 뛰지도 물러서지도 못한다(코디네이터 장애 = 잠금 정체). Saga는 반대로 한 명씩 순서대로 뛰고, 잘못되면 뛴 사람들이 역순으로 되돌아 나오는 방식이다.

4. Saga — 로컬 트랜잭션의 연쇄와 보상의 연쇄

Saga는 전체 작업을 각 서비스의 로컬 트랜잭션 T1 → T2 → T3으로 쪼개 순서대로 실행하고, 중간에 Ti가 실패하면 이미 커밋된 앞 단계들을 보상 트랜잭션 C(i−1) → … → C1으로 되돌리는 패턴이다.

Saga를 이해하는 열쇠 한 줄

보상은 롤백이 아니라 "반대 방향의 새 트랜잭션"이다

차감(−9,900P)의 보상은 환급(+9,900P)이라는 새로운 원장 기록이다. 차감 기록이 지워지는 게 아니라, 차감 기록 아래에 환급 기록이 한 줄 더 쌓인다. 회계에서 잘못된 분개를 지우개로 지우지 않고 반대 분개를 새로 적는 것과 같다.

4-1. 이것을 상태 머신으로 옮기면

Saga의 진행 위치는 곧 상태값 하나다. 이 상태 머신이 6절의 saga_instance.step 컬럼이 되고, 10절의 타임아웃 스캔과 11절의 수동 개입 큐가 전부 여기에 매달린다.

4-2. 비유 — 여행사 패키지 예약

구조가 그대로 대응된다

  • 항공권·호텔·렌터카는 서로 다른 회사 = 서로 다른 서비스·DB
  • 한 번에 묶어 예약할 수 없다 = 전역 트랜잭션 불가
  • 여행사 직원이 예약 대장을 펴놓고 순서대로 예약 = 오케스트레이터 + 상태 테이블
  • 호텔이 만실이면 이미 발권된 항공권을 취소 = 보상

비유가 알려주는 두 가지 통찰

  • 항공권 취소는 "예약이 없던 일이 되는 것"이 아니다 — 취소 수수료와 취소 기록이 남는 새로운 거래다. 보상 = 새 트랜잭션
  • 취소 전화가 불통이면(보상 실패) 직원은 대장에 "항공 취소 미처리"라고 적어두고 될 때까지 다시 건다. 대장에 적어두는 것이 핵심 — 직원이 퇴근해도 다음 직원이 대장을 보고 이어받는다
직원의 기억(메모리)이 아니라 대장(DB)에 적혀 있어야 교대가 가능하다 — 2절의 결론과 정확히 같은 말이다

5. 코레오그래피 vs 오케스트레이션 — 왜 선택지가 이 둘뿐인가

Saga를 구현하려면 반드시 답해야 하는 질문이 하나 있다. "T1이 끝났다는 것을 누가 알고, 누가 T2를 시작시키는가?" 이 질문의 답은 논리적으로 두 개뿐이다 — 다음 단계를 맡은 서비스가 스스로 알아채고 시작하거나, 중앙의 누군가가 알려주고 시작시키거나. 이 갈림이 그대로 두 방식이 된다.

두 방식의 차이 — 표의 마지막 두 줄이 돈 도메인의 판단 근거가 된다
코레오그래피오케스트레이션
흐름 지식각 서비스의 구독 관계에 분산오케스트레이터 한곳에 집중
결합도낮음 (서로를 직접 모름)높음 (오케스트레이터가 전부 앎)
단계 추가구독만 추가하면 됨오케스트레이터 수정 필요
"지금 어디서 멈췄나?"여러 서비스 로그를 모아야 앎테이블 한 번 조회로 앎
보상 경로이벤트로 얽혀 순환 구독이 생기기 쉬움상태 머신에 명시적으로 정의

이 선택을 한 문장으로 정당화하는 법

돈 도메인에서는 추적성·개입 가능성이 결합도 우려를 이긴다

결정적인 반론까지 준비해두면 좋다 — 코레오그래피에서 같은 것을 하려면 결국 모든 이벤트를 모아 흐름을 재구성하는 추적 저장소를 따로 지어야 하고, 그게 사실상의 오케스트레이터다. 결합도를 줄인 대신 관측 인프라를 하나 더 짓게 되는 셈이다.

절충안까지 말하면 설계 감각이 드러난다 "주변부 알림성 흐름은 코레오그래피, 돈이 걸린 핵심 경로는 오케스트레이션"이라는 분리 기준. 결제 완료 후 푸시 알림·마케팅 적립 이벤트 같은 것은 실패해도 보상이 필요 없으니 코레오그래피로 충분하다.

6. 상태 테이블과 트랜잭셔널 아웃박스

6-1. Saga 상태를 DB에 남긴다

Saga의 진행 상황은 반드시 영속화한다. 이유는 2절에서 본 그대로다 — 메모리에만 있으면 오케스트레이터 인스턴스가 죽는 순간 흐름이 사라진다. 상태가 DB에 있어야 다른 인스턴스나 배치가 테이블을 보고 이어받을 수 있다.

DDL 오케스트레이터의 심장 — saga_instance
CREATE TABLE saga_instance (
    saga_id     bigserial    PRIMARY KEY,
    order_id    bigint       NOT NULL UNIQUE,  -- 주문당 Saga 1개
    step        varchar(30)  NOT NULL,
    -- DEDUCT_REQUESTED -> ORDER_CREATED -> GRANT_REQUESTED
    -- -> COMPLETED | COMPENSATING -> COMPENSATED
    -- | COMPENSATION_FAILED (수동 개입 대기)
    retry_count int          NOT NULL DEFAULT 0,
    updated_at  timestamptz  NOT NULL DEFAULT now()
);
-- updated_at 인덱스: "오래 멈춰 있는 Saga" 스캔(10절)을 위한 것
CREATE INDEX idx_saga_stuck ON saga_instance (step, updated_at);
order_id UNIQUE
같은 주문에 Saga가 두 개 생기는 것을 DB가 막게 하기 위해서다. 애플리케이션의 "이미 있나?" 검사는 동시 요청 두 건이 나란히 통과할 수 있지만, 유니크 제약은 DB가 쓰기 시점에 원자적으로 판정한다.
retry_count
단순한 카운터처럼 보이지만 "몇 번까지 자동으로 해보고 사람을 부를 것인가"의 근거가 된다(11절 사례 1). 이 컬럼이 없으면 무한 재시도이거나 영영 사람을 못 부르거나 둘 중 하나다.

6-2. 이중 쓰기 문제 — 전이와 발행이 어긋나는 두 가지 경우

오케스트레이터가 하는 일은 매번 두 가지다 — ① 자기 DB의 Saga 상태를 전이시키고, ② 다음 서비스에 커맨드를 발행한다. 이 둘은 반드시 함께 일어나거나 함께 일어나지 않아야 한다. 그런데 DB 쓰기와 Kafka 발행은 서로 다른 시스템이라 한 트랜잭션으로 묶을 수 없다. 이것을 이중 쓰기(dual write) 문제라고 부른다.

비유 — 아웃박스는 "우체통"이다 편지를 직접 들고 우체국까지 뛰어가면(Kafka 직접 발행) 가는 길에 넘어졌을 때 장부에는 보냈다고 적혀 있는데 편지는 없는 상태가 된다. 대신 장부 기록과 우체통에 넣기를 같은 방 안에서 한 번에 끝내면(같은 트랜잭션), 집배원(릴레이)이 언제 오든 편지는 반드시 간다. 대신 집배원이 같은 편지를 두 번 가져갈 수는 있다 — 그것이 at-least-once이고, 7~8절 멱등성이 필요한 이유다.

아웃박스 3부품 — "테이블 · 릴레이 · 소비자 멱등"

① outbox 테이블
보낼 메시지를 같은 DB에 INSERT. 상태 전이와 한 트랜잭션.
② 릴레이
미발행 행을 읽어 실제 발행. 폴링(단순, 대부분 여기서 시작) 또는 CDC(WAL 구독, Debezium).
③ 소비자 멱등
릴레이가 발행 후 완료 표시 전에 죽으면 재발행한다. 중복 수신은 정상이므로 소비자가 흡수한다.

7. 상태 머신 가드 — 오케스트레이터 자신의 멱등성

릴레이와 Kafka는 모두 at-least-once(최소 1회) 전달이다. "적어도 한 번은 도착한다"는 보장이지 "정확히 한 번"이 아니다. 릴레이가 발행 성공 직후 발행 완료 표시 전에 죽으면 같은 메시지를 한 번 더 보낸다. 따라서 오케스트레이터도 같은 이벤트를 두 번 받을 각오를 해야 한다. 그 방어가 상태 머신 가드다.

before 가드도 잠금도 없고, 전이와 발행이 따로 논다
@Transactional
public void onDeductSucceeded(DeductSucceeded event) {
    Saga saga = sagaRepository.findByOrderId(event.orderId());
    // 잠금 없음 → 같은 주문 이벤트 2건이 동시에 들어오면
    //             둘 다 읽고 둘 다 전이시킨다.

    saga.moveTo(Step.ORDER_CREATED);
    saga.moveTo(Step.GRANT_REQUESTED);
    // 현재 상태를 안 본다 → 중복 배달이면 한 칸 더 전진하거나
    //                      이미 보상 중인 Saga를 되살린다.
}

// 게다가 발행이 트랜잭션 밖에 있다.
kafka.send("ticket.grant", event.orderId());
// 커밋과 묶이지 않으므로 6절의 두 어긋남이 그대로 재현된다.
after 전이 + 발행이 원자적이고, 중복 이벤트는 조용히 버린다
@Transactional
public void onDeductSucceeded(DeductSucceeded event) {
    // FOR UPDATE로 Saga 행을 잠근다. 같은 주문의 이벤트 두 개가
    // 동시에 도착해도 한 번에 하나씩만 상태를 전이시키기 위해서다.
    Saga saga = sagaRepository.findByOrderIdForUpdate(event.orderId());

    // 상태 머신 가드: "지금 상태에서 유효한 이벤트인가"만 받아들인다.
    // 이미 ORDER_CREATED로 넘어갔다면 이 이벤트는 중복 배달이므로
    // 조용히 버린다 — 이것이 오케스트레이터 자신의 멱등성이다.
    if (saga.step() != Step.DEDUCT_REQUESTED) return;

    saga.moveTo(Step.ORDER_CREATED);   // 주문은 이미 PENDING 생성됨
    saga.moveTo(Step.GRANT_REQUESTED);

    // 카프카로 직접 보내지 않는다. 위의 상태 전이와 같은 트랜잭션에
    // 남겨야 "전이만 되고 발행은 안 된" 상태가 생기지 않는다.
    outbox.save(Command.of("ticket.grant", event.orderId()));
}
after 실패 이벤트 핸들러 — 보상 커맨드도 똑같이 아웃박스로
@Transactional
public void onGrantFailed(GrantFailed event) {
    Saga saga = sagaRepository.findByOrderIdForUpdate(event.orderId());
    if (saga.step() != Step.GRANT_REQUESTED) return;   // 같은 가드

    saga.moveTo(Step.COMPENSATING);
    // 보상이야말로 유실되면 안 되는 메시지다.
    // "돈을 돌려주라"는 명령이 사라지면 되돌릴 방법이 없다.
    outbox.save(Command.of("point.refund", event.orderId()));
}

if (saga.step() != …) return; 이 한 줄이 하는 일

현재 상태에서 유효한 이벤트만 받아들이고 나머지는 조용히 버린다

왜 예외가 아니라 return인가

  • 중복 배달은 오류가 아니라 정상적으로 예상되는 상황이다 (at-least-once)
  • 예외를 던지면 컨슈머가 재시도를 반복하며 무한 루프에 빠진다
  • 알림을 걸어두면 정상 상황에 알림 폭탄이 되어 진짜 이상 징후가 묻힌다

가드가 막아주는 것들

  • 같은 성공 이벤트 2회 배달 → 두 번째는 상태가 이미 바뀌어 무시
  • 순서가 뒤집힌 이벤트 → 현재 단계와 안 맞으면 무시
  • 보상 중인 Saga에 뒤늦게 도착한 전진 이벤트 → 10절에서 이 케이스만은 무시가 아니라 별도 처리가 필요하다
FOR UPDATE와 가드는 역할이 다르다 — 둘 다 필요하다 FOR UPDATE(행 잠금)는 "동시에 두 이벤트가 처리되는 것"을 막고, 가드(상태 비교)는 "순차적으로 두 번 처리되는 것"을 막는다. 잠금만 있으면 순서대로 두 번 전진해 버리고, 가드만 있으면 둘 다 같은 상태를 읽고 통과한다. 동시성 방어와 중복 방어는 다른 층이라는 점을 말할 수 있어야 한다.

8. 멱등성 키 전파 — 참여자 전원이 멱등해야 한다

오케스트레이터만 멱등해서는 부족하다. 모든 참여 서비스의 쓰기가 멱등해야 한다. 커맨드도 at-least-once로 전달되기 때문이다.

키는 오케스트레이터가 만들어 모든 커맨드에 실어 보낸다. 자연스러운 선택은 orderId다. 한 주문에 성격이 다른 쓰기가 둘 이상이면(차감과 환급) orderId + 단계명으로 구분한다.

DDL 멱등성 키를 유니크 제약으로 못 박는다
-- 포인트 서비스: 주문당 차감 1건·환급 1건 (원장 유니크)
-- entry_type을 키에 포함하지 않으면, 차감이 이미 있다는 이유로
-- 환급(보상)이 거부되어 되돌릴 수 없게 된다.
ALTER TABLE point_ledger
    ADD CONSTRAINT uq_ledger UNIQUE (order_id, entry_type);

-- 콘텐츠 서비스: 주문당 이용권 1건
CREATE UNIQUE INDEX uq_ticket_order ON ticket (order_id);
before 조회 후 INSERT + "이미 처리됨"에 에러 응답
@Transactional
public GrantResult handle(GrantCommand cmd) {
    if (ticketRepository.existsByOrderId(cmd.orderId())) {
        throw new AlreadyGrantedException();  // ← 최악의 한 줄
    }
    // 문제 ①: 조회와 INSERT 사이에 틈이 있다.
    //         동시 배달 2건이 나란히 통과해 이용권 2장이 나간다.
    ticketRepository.insert(cmd.orderId(), cmd.userId(), cmd.productId());

    // 문제 ②: 에러를 응답하면 오케스트레이터가 "지급 실패"로 오판해
    //         불필요한 보상(환급)을 태운다 — 이용권은 그대로 둔 채
    //         돈만 돌려주는 최악의 결과.
    return GrantResult.success(cmd.orderId());
}
after INSERT-first + "이미 처리됨 = 성공 응답"
@Transactional
public GrantResult handle(GrantCommand cmd) {
    int inserted = ticketRepository.insertIfAbsent(
        cmd.orderId(), cmd.userId(), cmd.productId());
    // insertIfAbsent는 ON CONFLICT (order_id) DO NOTHING.
    // 확인과 선점이 DB 안에서 한 번에 원자적으로 일어난다.
    // inserted == 0 이면 이미 지급된 주문이라는 뜻이다.

    // 여기서 에러를 응답하면 오케스트레이터가 "지급 실패"로 오판해
    // 불필요한 보상(환급)을 태운다 — 이미 지급된 이용권을 그대로 둔 채
    // 돈만 돌려주는 최악의 결과가 된다. 그래서 성공으로 응답한다.
    return GrantResult.success(cmd.orderId());
}

INSERT-first가 핵심이다 — "이미 처리했나?"를 조회로 확인하지 않고, 일단 INSERT를 시도한다. 조회 후 INSERT는 그 사이 틈에 다른 요청이 끼어들 수 있지만, INSERT는 유니크 제약과 결합해 확인과 선점이 DB 안에서 한 번에 원자적으로 일어난다.

참여자 멱등성 3종 세트 — "유 · 온 · 성"

유 — 유니크 제약
UNIQUE (order_id) 또는 (order_id, entry_type). 중복 판정을 DB에 맡긴다.
온 — ON CONFLICT DO NOTHING
예외를 던지지 않고 흡수한다. 애플리케이션은 영향 행 수(0/1)로만 판단.
성 — 이미 처리됨 = 성공 응답
여기서 에러를 응답하면 잘못된 보상이 시작된다. 중복은 실패가 아니다.
멱등성이 전원에 깔려야 오케스트레이터가 "확신이 없으면 그냥 재전송한다"는 단순한 복구 전략을 쓸 수 있다

이 규칙이 왜 중요한지 한 번 더 짚자. 참여자 전원이 멱등하지 않으면 재전송할 때마다 "이미 했나 안 했나"를 확인하는 조회 API와 분기 로직이 필요해지고, 상태 공간이 폭발한다.

멱등성은 Saga의 전제 조건이지 부가 옵션이 아니다
비유 — 엘리베이터 버튼 버튼을 다섯 번 눌러도 엘리베이터는 한 번 온다. 그리고 이미 불이 켜져 있을 때 다시 누르면 "이미 눌렀습니다" 에러가 나는 게 아니라 그냥 아무 일도 안 일어나고 정상으로 취급된다. 참여자 핸들러가 정확히 이 동작이어야 한다 — 중복 입력을 흡수하고, 결과는 "요청대로 되어 있음"으로 응답한다.

담당 구간흡수하는 중복키를 만드는 주체
API 앞단의 Idempotency-Key클라이언트 ↔ 우리 API브라우저·게이트웨이의 재시도클라이언트
Saga 내부의 orderId 전파오케스트레이터 ↔ 참여 서비스커맨드 재전달, 이벤트 중복 배달오케스트레이터(흐름의 시작점)

가장 흔한 설계 실수

참여자가 각자 키를 만들면 안 된다 — 재전송마다 새 키가 붙어 중복 탐지가 원천적으로 불가능해진다

키는 흐름의 시작점에서 한 번 만들어 끝까지 같은 값으로 전파돼야 한다. "멱등성 키를 쓴다"는 말만으로는 부족하고, "누가 만들어 어디까지 실려 가는가"를 답할 수 있어야 한다.

9. 격리성 부재 — 중간 상태는 PENDING으로 감춘다

Saga는 ACID 중 격리성(I, Isolation)이 없다. 이것이 단일 트랜잭션과의 가장 큰 차이이고, 자주 놓치는 지점이다. 단일 트랜잭션에서는 커밋 전까지 다른 트랜잭션이 중간 상태를 볼 수 없다. Saga에서는 T1(차감)이 커밋된 순간부터 그 결과가 세상에 공개된다 — T2, T3이 아직 안 끝났는데도 말이다.

이용권을 INACTIVE로 넣는 것이 특히 중요한 이유

보상 불능 상황을 설계로 미리 제거한 것이다

지급 즉시 활성화한다면

  • 보상해야 할 때 이미 사용자가 열람해버린 이용권을 회수해야 한다
  • 소비된 권리는 회수가 불가능하다 — 보상 자체가 성립하지 않는다
  • 남는 선택지는 손실 처리 또는 고객 협의뿐

INACTIVE로 두면

  • 보상은 그냥 그 행을 삭제하거나 REVOKED로 바꾸는 일이 된다
  • 실패 확률이 거의 없는 보상이 된다 (12절 "보상 실패" 답변의 첫 번째 근거)
  • 10절의 "뒤늦게 도착한 지급 성공" 케이스도 회수 가능해진다

10. 타임아웃 — 무응답은 실패가 아니다

GRANT_REQUESTED에서 3분째 응답이 없다면 어떻게 하는가. 먼저 스케줄러가 오래 멈춘 Saga를 스캔한다.

SQL 멈춘 Saga 스캔 — idx_saga_stuck가 여기서 쓰인다
-- 3분 이상 같은 단계에 머물러 있는 Saga 찾기
SELECT saga_id, order_id, step, retry_count
  FROM saga_instance
 WHERE step IN ('DEDUCT_REQUESTED', 'GRANT_REQUESTED', 'COMPENSATING')
   AND updated_at < now() - interval '3 minutes'
 ORDER BY updated_at
 LIMIT 200;

찾은 Saga에는 커맨드를 재전송한다. 참여자가 8절의 규칙대로 멱등하므로 안전하다. 이미 처리됐다면 "처리됨" 성공 응답이 다시 오고, 미처리였다면 이번에 처리된다. 재전송 한도를 넘으면 실패로 간주하고 보상 경로로 전이시킨다. 단, 여기에 함정이 하나 있다.

이 절의 함정

"실패 응답"과 "무응답"은 다르다

명시적 실패 응답은 "확실히 안 됐다"는 사실이지만, 무응답은 결과 불명이다. 무응답 후 실패로 간주해 보상을 태웠는데, 뒤늦게 성공 응답이 도착할 수 있다.

타임아웃 처리 4단계

① 스캔
step + updated_at 인덱스로 오래 멈춘 Saga를 찾는다.
② 재전송
멱등하므로 그냥 다시 보낸다. "했는지 확인"이 필요 없다.
③ 한도 초과
retry_count가 한도를 넘으면 실패로 간주하고 보상 경로로.
④ 늦은 도착 대비
보상 후 도착한 성공에도 자리를 만든다 → 추가 보상.

11. 실무 사례 — 교과서가 말하지 않는 세 가지

사례 1. 보상도 실패한다 — 환급 커맨드가 죽은 컨슈머를 만났을 때

이용권 지급이 콘텐츠 서비스 배포와 겹쳐 5xx로 확정 실패했다. 오케스트레이터는 COMPENSATING으로 전이하고 환급(+9,900P) 커맨드를 발행했다. 그런데 포인트 서비스 컨슈머도 장애 중이다.

이 순간 사용자 돈 9,900P는 어느 쪽 권리로도 연결되지 않은 채 붕 떠 있다 — 이용권도 없고 포인트도 없다
1
환급 커맨드는 끝까지 살아남는다. 아웃박스에 커밋됐으므로 사라지지 않고, Kafka가 재전달을 계속하므로 컨슈머가 복구되면 처리된다. 멱등하므로 그 사이 중복 배달이 있어도 안전하다.
2
백오프를 두고 재시도한다. 지수 백오프(exponential backoff)는 재시도 간격을 1초 → 2초 → 4초 → 8초처럼 늘려가는 방식이다. 이미 힘들어하는 상대 시스템에 재시도 폭풍으로 부하를 더 얹지 않기 위한 것이다.
3
한도를 넘으면 사람을 부른다. 재시도 한도(예: 5회)를 넘기면 Saga를 COMPENSATION_FAILED로 전이시키고 수동 개입 큐 — 운영자가 보는 보정 대기 테이블 — 에 orderId·금액·실패 사유·마지막 시도 시각을 적재하고 알림을 쏜다.
DDL 끝단의 안전망 — manual_intervention_queue
CREATE TABLE manual_intervention_queue (
    id            bigserial   PRIMARY KEY,
    order_id      bigint      NOT NULL,
    saga_step     varchar(30) NOT NULL,
    amount        int         NOT NULL,
    reason        text        NOT NULL,
    last_tried_at timestamptz NOT NULL,
    resolved_at   timestamptz              -- NULL이면 미처리
);

돈 도메인 Saga의 끝단

언제나 "재시도 → 그래도 안 되면 사람"이다

자동 복구가 실패하는 것 자체는 막을 수 없다. 그러나 실패했다는 사실이 아무 데도 기록되지 않는 것은 설계 결함이다. 면접에서 이 문장 하나로 정리할 수 있어야 한다.

사례 2. 지급 커맨드 2회 배달 — 멱등성이 빠진 참여자

컨슈머가 지급을 끝내고 오프셋 커밋 전에 재시작됐다. Kafka 컨슈머는 "어디까지 읽었는지"를 오프셋(offset)이라는 숫자로 기록한다. 메시지를 처리한 뒤 오프셋을 커밋해야 다음부터 그 메시지를 안 받는데, 처리와 오프셋 커밋 사이에 죽으면 재시작 후 같은 메시지를 다시 받는다. 이것이 at-least-once 전달의 실체다.

대응은 8절의 3종 세트 그대로

① UNIQUE (order_id)+ ② ON CONFLICT DO NOTHING+ ③ 이미 처리됨 = 성공 응답
at-least-once를 쓰는 순간 참여자 멱등성은 전원 필수이고, 그것이 빠졌을 때 발견하는 수단이 대사다 — 예방과 탐지는 짝이다

사례 3. 오케스트레이터 크래시 — "차감했나 안 했나" 불명

차감 커맨드를 발행한 직후 오케스트레이터 인스턴스가 죽었다. 재기동 후 다른 인스턴스가 DEDUCT_REQUESTED에 멈춘 Saga를 타임아웃 스캔으로 발견했다. 그런데 차감이 실행됐는지 아닌지 알 수 없다. 가능한 상황이 셋이다.

아직 도달 안 함
커맨드가 컨슈머에 도달하지 않았다 → 미처리
응답 유실
처리는 됐는데 응답 이벤트가 유실됐다 → 처리됨
처리 중
지금 처리 중이다 → 곧 처리됨
대응 — 알 필요가 없게 만든다. 차감이 멱등하므로 그냥 커맨드를 재전송한다

어느 쪽이든 Saga는 전진한다

  • 이미 처리됐다면 포인트 서비스가 원장 유니크 위반을 만나 "처리됨" 성공 이벤트를 다시 내준다
  • 미처리였다면 이번에 처리되고 성공 이벤트가 온다

대안("조회 후 분기")이 나쁜 이유

  • 조회 API를 참여자마다 만들어야 한다
  • 조회 자체가 실패하는 경우를 또 다뤄야 한다
  • 조회와 재전송 사이에 상태가 바뀌는 경우까지 다뤄야 한다

이 사례가 증명하는 것

"멱등 재전송으로 수렴"은 "조회 후 분기"보다 상태 공간이 훨씬 작다

멱등성이 왜 Saga의 전제 조건인지를 이 사례가 증명한다. 멱등성은 중복을 막는 방어 장치이면서 동시에 복구 전략을 단순하게 만들어 주는 설계 자산이다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 답을 먼저 떠올리고 오른쪽을 본다

2PC 배제 3근거는?
블 · 느 · 엑 — 블로킹(잠금 쥔 채 대기, 코디네이터 장애가 전파), 가장 느린 참여자 + 왕복 2회에 종속, 엑스에이(XA) 미지원 자원은 참여 자격 없음.
보상이란?
롤백이 아니라 반대 방향의 새 트랜잭션. 차감의 보상 = 환급이라는 새 원장 한 줄. 되돌릴 때는 역순이고, 실패한 단계 자신은 보상하지 않는다.
Saga 필수 부품 6종?
상 · 아 · 릴 · 타 · 보 · 수 — 상태 테이블, 아웃박스, 릴레이, 타임아웃 스캐너, 보상 경로, 수동 개입 큐. "Saga는 이게 전부 딸려 오는 도구"라는 근거.
아웃박스가 푸는 문제는?
이중 쓰기(dual write). DB 커밋과 Kafka 발행을 한 트랜잭션에 못 묶으므로, 메시지를 같은 DB에 INSERT해 단일 쓰기로 바꾼다. 발행은 릴레이(폴링/CDC)가 맡는다.
참여자 멱등성 3종 세트?
유 · 온 · 성 — 유니크 제약, ON CONFLICT DO NOTHING, "이미 처리됨 = 성공 응답". 마지막이 빠지면 잘못된 보상이 시작된다.
멱등성 키 규칙 한 줄?
흐름의 시작점에서 한 번 만들어 끝까지 같은 값으로 전파. 단위는 orderId, 한 주문에 성격이 다른 쓰기가 둘이면 (order_id, entry_type).
Saga에 없는 ACID 글자는?
I(격리성). T1 커밋 순간부터 중간 상태가 공개된다 → 의미적 잠금: 주문 PENDING, 이용권 INACTIVE, PENDING 중 같은 상품 재주문 차단.
"실패 응답"과 "무응답"의 차이?
실패 응답 = 확실히 안 됐다. 무응답 = 결과 불명. 보상 후 뒤늦은 성공 이벤트가 올 수 있으므로 그 전이까지 상태 머신에 정의한다.
오케스트레이터 자신의 멱등성은?
상태 머신 가드 — if (saga.step() != 기대상태) return;. 예외가 아니라 return인 이유는 중복 배달이 오류가 아니라 정상이기 때문(예외 → 무한 재시도).
보상 실패 대응 3단?
① 실패할 수 없는 형태로 설계(환급은 더하기, 이용권은 INACTIVE) → ② 아웃박스 + 지수 백오프 재시도 → ③ COMPENSATION_FAILED + 수동 개입 큐 + 알림.

12-2. 꼬리질문 — 먼저 답해보고 펼친다

2PC를 쓰면 안 되는 이유를 다시 정리해주면요? Saga가 항상 답인가요? 필수힌트: 배제 근거 셋은 외워 두고, 진짜 변별은 "항상 Saga는 아니다" 다음에 나온다

2PC 배제 근거는 셋이다.

① 블로킹
prepare 후 참여자가 행 잠금을 쥔 채 대기 — 코디네이터 장애가 전 참여자의 잠금 정체로 전파.
② 최저속 종속
전체 시간 = 가장 느린 참여자 + 코디네이터 왕복 2회.
③ XA 미지원
Kafka·외부 PG·타 팀 HTTP API는 참여 자격 자체가 없다.

다만 "항상 Saga"도 아니다. 이 부분을 말할 수 있어야 설계 감각이 드러난다.

첫 번째 답은 "분산 트랜잭션이 필요 없게 서비스 경계를 다시 긋는 것"이다

차감과 주문이 한 서비스·한 DB로 묶일 수 있다면 로컬 트랜잭션 하나가 Saga보다 백 배 단순하다. Saga에는 상태 테이블·아웃박스·릴레이·타임아웃 스캐너·보상 경로·수동 개입 큐가 전부 딸려 온다(인출 카드의 "상·아·릴·타·보·수").

순서를 밝히면 좋다 Saga는 "경계를 합칠 수 없다는 결론이 난 뒤"의 도구다. 실제로 "마이크로서비스로 쪼갰더니 Saga가 필요해졌다"는 상황의 상당수는 경계를 잘못 그은 결과다 — 한 트랜잭션으로 묶여야 하는 데이터는 대체로 같은 서비스에 있어야 한다.
보상 트랜잭션이 실패하면 어떻게 하나요? 시니어 변별힌트: "재시도합니다"부터 말하면 절반만 맞다. 그 앞에 와야 할 답이 있다

3단 구조로 답한다. 순서가 중요하다 — 대응 절차보다 설계가 먼저다.

1
보상은 실패 확률이 낮게 설계한다. 이것이 첫 번째이자 가장 중요한 답이다.
  • 차감의 보상을 환급(더하기)으로 두면 "잔액이 모자라서 못 한다" 같은 논리적 실패가 없다. 남는 것은 일시적 장애뿐이다
  • 회수가 필요한 권리(이용권)는 Saga 완료 전 INACTIVE로 둬서 "이미 소비돼서 회수 불가"라는 보상 불능 상황을 구조적으로 없앤다
2
남는 실패는 일시 장애이므로 아웃박스 + 백오프 재시도로 흡수한다. 아웃박스에 커밋된 보상 커맨드는 유실되지 않고, 컨슈머가 복구되면 반드시 처리된다.
3
한도 초과 시 COMPENSATION_FAILED + 수동 개입 큐 + 알림. 돈이 붕 뜬 상태를 시스템이 모르는 채 두지 않는다.
보상 실패에 대한 최선의 대비는 대응 절차가 아니라, 보상이 실패할 수 없는 형태로 순서와 상태를 설계하는 것이다
탈락 신호 "보상은 실패하지 않는다고 가정한다"고 답하는 순간이다. 교과서의 Saga는 보상 성공을 가정하고 논의를 전개하지만, 돈의 현실은 정확히 그 가정의 바깥에서 터진다.
코레오그래피가 결합도는 더 낮지 않나요? 왜 오케스트레이션인가요? 시니어 변별힌트: 상대 말을 먼저 인정하고, 판단 기준이 "결합도"가 아니라는 것을 보여준다

맞다는 것부터 인정하고 시작한다. 코레오그래피는 서비스 간 직접 참조가 없어 단계 추가가 쉽고, 오케스트레이터라는 단일 지점에 지식이 몰리지 않는다.

그런데 돈 도메인의 지배적 요구는 결합도가 아니라 추적성·개입 가능성이다
CS 즉답
"이 주문 어디서 멈췄나"를 테이블 1회 조회로 답해야 한다.
타임아웃 스캔
멈춘 Saga를 찾을 수 있어야 재전송·보상 전이가 가능하다.
수동 재개
보상 실패 건을 사람이 이어받으려면 개입 지점이 있어야 한다.

이 셋은 전부 상태가 한 테이블에 있어야 성립한다. 그리고 결정적인 반론이 하나 있다.

코레오그래피에서 같은 것을 하려면 결국 모든 이벤트를 모아 흐름을 재구성하는 추적 저장소를 따로 지어야 하고, 그게 사실상의 오케스트레이터다

즉 결합도를 줄인 대신 관측 인프라를 하나 더 짓게 되는 셈이다. 마무리로 절충안까지 말하면 좋다 — "주변부 알림성 흐름은 코레오그래피, 돈이 걸린 핵심 경로는 오케스트레이션." 결제 완료 후 푸시 알림·적립 이벤트는 실패해도 보상이 필요 없으니 코레오그래피로 충분하다.

Saga 진행 중에 사용자가 잔액이나 주문을 조회하면요? 필수힌트: 이 질문은 ACID의 어느 글자를 묻고 있는가

격리성 부재 문제로 연결해 답한다(9절). T1(차감) 커밋 직후부터 잔액은 이미 줄어 있고 주문은 미확정이다. 이 중간 상태를 확정처럼 보여주면 안 된다.

주문
PENDING으로 두고 화면에는 "결제 처리 중"으로 노출.
이용권
Saga 완료까지 INACTIVE. 완료 커맨드에서 활성화.
재주문
PENDING 주문이 존재하는 동안 같은 상품 재주문 차단.

세 번째를 빼먹기 쉬운데, 이걸 안 하면 "처리 중인데 또 사기"로 인한 이중 차감·이중 지급 경합이 생긴다.

이런 기법을 의미적 잠금(semantic lock)이라 부른다 — DB 락이 아니라 데이터의 의미(상태값)로 접근을 제한한다는 뜻

용어까지 얹으면 정리가 깔끔하고, "격리성을 되찾는 게 아니라 중간 상태를 확정처럼 보이지 않게 만드는 것"이라는 한계 인식까지 보여주면 더 좋다.

멱등성 키는 어느 단위로 만들어 전파하나요? 필수힌트: 단위보다 "누가 만드는가"가 진짜 함정이다

오케스트레이터가 생성한 orderId(또는 sagaId)를 모든 커맨드에 실어 보내고, 각 참여자는 그것을 자기 테이블의 유니크 제약 컬럼으로 쓴다.

차감·환급처럼 한 주문에 성격이 다른 쓰기가 둘이면 (order_id, entry_type)으로 단계까지 키에 포함한다. 그러지 않으면 차감이 이미 있다는 이유로 환급이 거부된다 — 되돌릴 수 없게 되는 것이다.

중요한 것은 "참여자가 각자 키를 만들면 안 된다"는 점이다

재전송된 커맨드에 매번 새 키가 붙으면 중복 탐지가 원천적으로 불가능해진다. 키는 흐름의 시작점에서 한 번 만들어 끝까지 같은 값으로 전파돼야 한다.

마지막으로 두 개의 멱등성 장치를 구분해 말하면 정리가 완성된다.

담당 구간흡수하는 중복
API 앞단의 Idempotency-Key클라이언트 ↔ 우리 API브라우저·게이트웨이의 재시도
Saga 내부의 orderId 전파오케스트레이터 ↔ 참여 서비스커맨드 재전달, 이벤트 중복 배달

구간이 다른 별개의 장치이므로 하나가 다른 하나를 대체하지 않는다.

Saga의 단계 순서는 어떤 기준으로 정하나요? 시니어 변별힌트: "보상하기 쉬운 것"과 "보상이 불가능한 것"을 나눠 놓고 순서를 생각해본다

기준은 하나다 — 되돌리기 쉬운 단계를 앞에, 되돌리기 어렵거나 불가능한 단계를 뒤에 둔다.

앞에 두는 것 — 보상 가능한 단계

  • 포인트 차감(보상 = 환급, 논리적 실패 없음)
  • 주문 생성(보상 = CANCELLED 전이)
  • 즉 우리 시스템 안에서 반대 기록 한 줄로 끝나는 일

뒤로 미루는 것 — 보상이 어렵거나 불가능한 단계

  • 외부에 나가는 되돌릴 수 없는 행위 — 이메일·SMS 발송, 물리 배송 지시
  • 제3자에게 확정 통보가 되는 호출
  • 이런 단계를 앞에 두면 뒤에서 실패했을 때 보상할 방법이 없다

Saga 문헌에서는 되돌릴 수 없는 그 지점을 피벗(pivot) 단계라고 부른다. 피벗을 지나면 Saga는 뒤로 못 가고 앞으로만 간다 — 그래서 피벗 이후 단계들은 "실패하면 보상"이 아니라 "성공할 때까지 재시도"로 설계한다.

순서 설계의 목표 — "보상 불능 구간"을 만들지 않는 것

이 관점에서 보면 9절의 이용권 INACTIVE 결정도 같은 계열의 판단이다. "활성화"라는 되돌리기 어려운 행위를 Saga의 맨 끝(완료 시점)으로 미룬 것이기 때문이다.

아웃박스 테이블은 무한히 커지지 않나요? 릴레이가 같은 행을 두 번 발행하면요? 가산점힌트: 두 번째 질문의 답은 이미 이 문서 전체에 깔려 있다

운영 관점 두 가지를 나눠 답한다.

① 테이블 증가

아웃박스는 영구 보관용 테이블이 아니라 발행 대기열이다. 따라서 발행 완료 행은 일정 기간 뒤 정리한다 — 주기적인 삭제 배치, 또는 시간 기준 파티션을 만들어 통째로 드롭하는 방식이 흔하다. 감사 목적의 기록이 필요하다면 아웃박스가 아니라 별도의 이력 테이블이 그 역할을 맡는다.

주의 정리 기준은 "발행 완료 표시가 된 행"이어야 한다. 미발행 행을 시간만 보고 지우면 커맨드가 유실되고, 그 순간 아웃박스를 쓴 의미가 사라진다.

② 릴레이 중복 발행

여러 인스턴스가 동시에 폴링하면 같은 행을 두 인스턴스가 집어갈 수 있다. 실무적 해법은 두 층이다.

경합 줄이기
PostgreSQL의 SELECT … FOR UPDATE SKIP LOCKED로 이미 다른 인스턴스가 잡은 행을 건너뛰고 집어간다. 인스턴스 간 작업 분배가 자연스럽게 된다.
그래도 남는 중복은 흡수
발행 성공 직후 완료 표시 전에 죽으면 어차피 재발행된다. 이건 없앨 수 없다 — 그래서 at-least-once를 전제로 소비자를 멱등하게 만든 것이다.
답의 핵심 — 릴레이 중복은 "막을 문제"가 아니라 "이미 대비해 둔 상황"이다
Saga와 아웃박스까지 깔았으면 정합성 대사(reconciliation)는 필요 없지 않나요? 시니어 변별힌트: 사례 2에서 그 사고를 결국 누가 발견했는가

필요하다. 이유는 한 문장으로 정리된다.

Saga·아웃박스·멱등성은 예방 장치이고, 대사는 탐지 장치다 — 층이 다르다

예방이 뚫리는 경로는 실제로 존재한다.

제약 누락
참여자 한 곳에 유니크 제약을 빠뜨린 채 배포(사례 2). 시스템 어디에도 에러가 안 난다.
늦은 이벤트
보상 후 도착한 성공 이벤트(10절)를 처리하지 않고 버리면 조용히 어긋난다.
수동 개입 오류
사람이 보정하다 틀리는 경우는 어떤 자동 장치도 막지 못한다.

이 셋의 공통점은 "아무도 예외를 던지지 않는다"는 것이다. 에러 없이 어긋난 데이터는 대조해 보는 것 외에 발견 수단이 없다.

면접에서는 "예방과 탐지는 짝"이라고 말하고, 구체적으로 "차감 건수 : 이용권 건수 : 주문 건수가 맞는지"를 주기적으로 대조한다고 덧붙이면 좋다. 대사 배치의 설계는 08-reconciliation-batch-design.md에서 더 다룬다.

오케스트레이터는 별도 서비스로 두나요, 기존 서비스 안에 두나요? 가산점힌트: 진짜 질문은 "코드를 어디 두나"가 아니라 "상태 테이블이 어느 DB에 있나"다

먼저 질문을 바꿔 말하는 것이 좋은 답의 시작이다 — 중요한 것은 배포 단위가 아니라 saga_instance 테이블이 어느 DB에 있고, 그 전이가 아웃박스 INSERT와 같은 트랜잭션에 들어가는가이다.

이 둘이 같은 DB·같은 트랜잭션이기만 하면, 오케스트레이터가 별도 프로세스인지 아닌지는 부차적인 문제다

흐름의 소유 서비스 안에 두기 (흔한 출발점)

  • 주문 서비스가 흐름의 주인이면 그 안의 컴포넌트로 시작한다
  • 배포 단위가 하나 줄어 운영이 단순하다
  • 주문 상태와 Saga 상태를 같은 트랜잭션에서 다룰 수 있다

별도 서비스로 분리하기

  • Saga 종류가 여러 개로 늘고, 흐름의 주인이 애매해질 때
  • 타임아웃 스캐너·릴레이 같은 운영 컴포넌트가 독립적으로 스케일해야 할 때
  • 대신 주문 상태와 Saga 상태가 다른 DB로 갈라져 또 하나의 정합성 문제를 만든다는 비용을 안는다

"작게 시작해 필요가 증명되면 분리한다"는 순서를 밝히면 좋다. 처음부터 분리하면 Saga가 필요 없었을 수도 있는 흐름까지 분산 문제로 만들어 버린다(첫 번째 꼬리질문의 "경계를 다시 긋기"와 같은 이야기다).

한 줄 요약
분산된 차감·주문·지급에 전역 롤백은 없으므로, 로컬 트랜잭션의 연쇄(T1→T2→T3)를 오케스트레이터가 상태 테이블 + 아웃박스로 추적하며 이끌고 실패 시 역순 보상(C2→C1, 차감의 보상 = 환급)으로 되돌리는 Saga로 설계한다 — 단, orderId 멱등성 키를 전 단계에 전파해 재전송을 안전하게 만들고(멱등성은 Saga의 전제 조건), 중간 상태는 PENDING·INACTIVE로 감추며(격리성 부재 대응이자 보상 불능 예방), 보상도 실패한다는 전제로 재시도의 끝에 수동 개입 큐를 두는 것까지가 돈 도메인에서의 완성형이다.
