이중 지급 심층 방어
모든 방어선은 뚫린다는 전제로 쌓는다

면접 질문: "이중 지급/이중 차감을 막기 위한 방어선을 계층별로 나열해주세요. (UI → API → DB 제약)"

핵심 관전 포인트 — 이중 지급/이중 차감 방어는 한 층으로 끝나지 않는다. UI(버튼 비활성화)는 두 번째 탭을 모르고, API 멱등성 키는 "새 키로 온 새 시도"를 못 막고, 분산 락은 TTL 만료·페일오버로 새며, 애플리케이션의 exists 검사는 레이스 컨디션의 틈이 있다. 그래서 방어는 계층별로 쌓는다 — UI(빈도 감소) → API 멱등성 키(같은 시도의 재전송 흡수) → 분산 락(줄 세우기) → DB 유니크 제약 + 조건부 UPDATE(최후의 방어선) → 대사 배치(사후 탐지·보정). 최후의 방어선이 DB 제약이어야 하는 이유는, 상위 계층은 전부 배포 실수나 레이스로 뚫릴 수 있지만 DB 제약은 모든 쓰기 경로(API·배치·어드민)가 반드시 통과하는 단일 관문이고 원자성을 DB 엔진이 보장하기 때문이다. "주문당 승인 결제 1건" 같은 도메인 불변식(항상 참이어야 하는 업무 규칙)을 제약으로 새겨 넣는 것 — 그것이 이 질문의 정답 한 줄이다.
  • 1
    이중 결제는 성격이 다른 여섯 경로로 들어오므로 한 장치로는 못 막는다 — 더블 클릭·두 번째 탭·자동 재전송·사용자의 "다시 시도"·웹훅 중복·어드민 재처리. 그래서 UI(빈도 감소) → 멱등성 키(재전송 흡수) → 분산 락(줄 세우기) → DB 제약(최종 판정) → 대사(탐지·보정) 다섯 층으로 쌓는다. 스위스 치즈처럼 구멍의 위치가 서로 다른 판을 겹치는 것이 설계 목표다.
  • 2
    최후의 방어선은 반드시 DB여야 한다 — 상위 층은 전부 확률적 장치다. 락은 TTL 만료·페일오버·해제 순서 버그로 새고, 멱등성 키는 새 키 앞에서 무력하다. DB 제약은 모든 쓰기 경로가 통과하는 단일 관문이고 판정이 원자적이다. "주문당 살아있는 결제 1건"이라는 도메인 불변식을 부분 유니크 인덱스로 새긴다.
  • 3
    선점은 PG 승인 앞에 두고, 상태 전이는 조건부 UPDATE로 잠근다 — exists 검사 대신 INSERT-first로 자리를 먼저 잡으면 중복이 돈이 나가기 전에 걸러진다. 전이는 WHERE status='PENDING'을 달아 rowcount 1을 얻은 쪽만 승자가 되게 한다. 그래도 새어나간 PG와의 불일치는 대사 배치가 반드시 찾아낸다.

0. 질문 + 출제 의도

질문: "이중 지급/이중 차감을 막기 위한 방어선을 계층별로 나열해주세요. (UI → API → DB 제약)"

출제 의도: 단일 방어(프론트 버튼 비활성화)만 믿는 사람과, UI → API 멱등성 → DB 유니크 제약까지 다층으로 쌓는 사람의 차이를 본다. "각 방어선은 뚫린다"는 전제로 설계하는 심층 방어(defense in depth) 사고가 있는지가 관전 포인트다.

이 페이지가 겨냥하는 약점 세 가지 ① "프론트에서 버튼 막았는데요"로 끝나는 답 → 1절에서 여섯 개의 경로를 펼쳐 그 답이 1개만 막고 다섯에 무방비임을 보인다.
② "분산 락 걸면 되죠"라는 과신 → 7절에서 락이 새는 세 경로(TTL 만료·페일오버·해제 순서)를 GC 멈춤 타임라인으로 재현하고, 락은 원자성의 출처가 될 수 없다는 결론을 세운다.
③ "멱등성 키가 있으니 DB 제약은 중복 아닌가"라는 혼동 → 6·10절에서 전송 계층 중복 제거와 비즈니스 중복 제거가 서로 다른 질문에 답한다는 경계를 긋는다.

1. 이중 결제가 실제로 들어오는 여섯 경로

월 구독 9,900원이 두 번 결제되는 경로를 먼저 나열해 보자. 이 목록이 곧 방어 설계의 요구사항이다. 요구사항을 모르고 장치부터 고르면, 자기가 무엇을 못 막고 있는지도 모르게 된다.

① 더블 클릭 — 화면
사용자가 응답이 느리자 버튼을 두 번 누른다. 가장 빈도가 높고, 가장 막기 쉽다.
② 두 번째 브라우저 탭 — 화면
결제 페이지를 두 탭에 열고 각각 결제한다. 두 탭은 서로의 존재를 모른다.
③ 타임아웃 후 자동 재시도 — 네트워크
HTTP 라이브러리나 게이트웨이가 응답 없는 요청을 스스로 다시 보낸다. 사람은 아무것도 안 했다.
④ 실패 화면에서 "다시 시도" — 사람
사실은 성공했는데 응답만 유실됐고, 사용자는 실패한 줄 안다. 그래서 다시 누른다.
⑤ 웹훅 중복 수신 / 대사 배치의 재승인 — 서버 간
서버 대 서버 경로라 애초에 브라우저를 거치지 않는다. UI 방어가 존재조차 하지 않는 경로.
⑥ 어드민 툴에서 수동 재처리 — 사람
운영자가 별도 API를 통해 같은 주문을 다시 밀어 넣는다. 결제 API의 방어 코드를 통과하지 않는다.

여섯 경로를 통째로 외우는 법 — 2 · 1 · 2 · 1

화면 2(더블클릭·두 번째 탭) · 망 1(자동 재전송) · 사람 2(다시 시도·어드민 재처리) · 서버 간 1(웹훅/배치)

면접에서 여섯 개를 순서 없이 떠올리려 하면 두세 개에서 막힌다. 발생 주체별로 2-1-2-1로 묶어두면 "성격이 다른 문제를 한 장치로 못 막는다"는 결론까지 자동으로 따라 나온다.

여섯 경로의 성격이 전부 다르다는 점이 중요하다. ①은 한 화면 안의 문제이고, ③은 네트워크 계층의 문제이며, ④는 사용자 의도의 문제이고, ⑤·⑥은 아예 브라우저를 거치지 않는다. 성격이 다른 여섯 개의 문제를 한 가지 장치로 막을 수는 없다.

낙제 답변 — "프론트에서 버튼 막았는데요"

  • 막는 것: ①번 하나
  • 무방비: 나머지 다섯 개 전부
  • 특히 ⑤·⑥은 브라우저가 없는 경로라 이 방어가 존재하지도 않는다

절반의 답변 — "DB 제약 하나면 되죠"

  • 막히긴 한다 — 정합성은 지켜진다
  • 그러나 매 중복 요청이 PG 승인까지 갔다가 취소되는 비용이 남는다
  • 사용자에게 보이는 에러 화면도 누군가는 흡수해줘야 한다
각 층의 역할이 다르다 — 상위 층은 빈도를 줄이고, 최하층은 발생 자체를 0으로 만든다

아래 표가 이 문서 전체의 요약이다. 세로로 읽으면 각 층의 능력이 보이고, 가로로 읽으면 각 경로가 몇 겹을 통과해 내려오는지가 보인다. 4선 열이 전부 초록이라는 사실이 곧 "최후의 방어선은 DB"라는 결론이다.

2. 스위스 치즈 모델 — 심층 방어의 사고방식

항공 안전에서 쓰는 스위스 치즈 모델이 이 구조의 정확한 비유다. 스위스 치즈는 한 장 한 장에 구멍이 뚫려 있다. 구멍 없는 완벽한 한 장은 존재하지 않는다. 사고는 여러 장의 구멍이 일직선으로 겹치는 순간에만 관통한다.

이 사고방식을 심층 방어(defense in depth)라고 부른다. 원래 군사 용어로, 전선 하나에 모든 병력을 두지 않고 종심 깊게 여러 겹의 방어선을 두어 하나가 뚫려도 다음 선이 막게 하는 전술이다.

보조 비유 — 안내원과 개찰구 분산 락은 줄을 세우는 안내원이다. 대부분의 경우 질서를 지켜주지만, 잠깐 자리를 비우면(TTL 만료·페일오버) 두 사람이 동시에 들어간다.
DB 유니크 제약은 개찰구다. 안내원이 없어도, 안내원이 실수해도 표가 없으면 물리적으로 통과가 안 된다. 이 둘은 대체 관계가 아니라 같이 두는 것이다 — 개찰구만 있으면 사람들이 몰려 혼잡하고, 안내원만 있으면 결국 새는 사람이 나온다.

3. 전제 지식 — 레이스 컨디션과 check-then-act

아래에서 "레이스 컨디션 때문에 뚫린다"는 표현이 반복해서 나오므로 먼저 정의하고 간다.

레이스 컨디션 (race condition, 경쟁 상태)
두 개 이상의 실행 흐름이 같은 데이터를 동시에 건드릴 때, 누가 먼저 도착하느냐에 따라 결과가 달라지는 상황. 경주(race)에서 이름을 땄다.
check-then-act
먼저 확인하고(check), 그 결과에 따라 실행하는(act) 구조. 결제 코드에서 레이스가 생기는 가장 흔한 형태다.
문제의 원형 혼자 실행되면 완벽한 코드
if (!이미_결제됐나(orderId)) {   // check
    결제한다(orderId);            // act
}

이 문서를 관통하는 원칙 한 문장

틈을 없애는 방법은 둘뿐 — 독점하거나(락), 합치거나(원자적 연산). 그리고 독점은 새고, 합치기는 안 샌다.

4. 다섯 층의 지도 — 각 층이 막는 것과 새는 곳

전체 그림을 먼저 보자. 위쪽 층일수록 사용자에 가깝고 값이 싸며, 아래로 갈수록 확실해진다. 각 층을 볼 때 반드시 두 가지를 쌍으로 외운다 — 무엇을 막는가, 그리고 어디로 새는가. 새는 곳을 말할 수 있어야 그 층을 이해한 것이다.

다섯 층을 순서대로 인출하는 장치 — 빈 · 재 · 줄 · 판 · 탐

빈 — 빈도 감소
1선 UI
재 — 재전송 흡수
2선 멱등성 키
줄 — 줄 세우기
3선 분산 락
판 — 최종 판정
4선 DB 제약 (최후)
탐 — 탐지·보정
5선 대사 배치

면접에서는 장치 이름이 아니라 성격부터 말하는 편이 훨씬 좋게 들린다. "UI, 멱등성 키, 락, 제약, 대사요"보다 "빈도를 줄이는 층, 재전송을 흡수하는 층, 줄을 세우는 층, 최종 판정을 내리는 층, 사후에 탐지하는 층으로 나눕니다"가 설계 사고를 보여준다.

5. 1선 UI — 빈도를 줄이는 층 (정합성 보장이 아니다)

할 일은 세 가지다. 셋 다 "사용자가 물리적으로 두 번 보내는 상황"을 줄이는 데 초점이 있다.

1
결제 버튼 클릭 즉시 비활성화 + 로딩 오버레이 — 같은 화면에서의 연타를 끊는다. 오버레이까지 덮는 이유는, 버튼만 비활성화하면 그 아래 다른 경로(엔터 키, 폼 submit)가 남기 때문이다.
2
결제 진행 중 페이지 이탈 경고 — 사용자가 중간에 새로고침하는 것을 줄인다. 새로고침은 곧 "다시 시도"로 이어진다.
3
완료 후 결과 페이지로 redirect — 이를 PRG(Post/Redirect/Get) 패턴이라 부른다. POST 응답을 그대로 화면에 그리면 사용자가 새로고침했을 때 브라우저가 "양식을 다시 제출하시겠습니까?"를 띄우고 POST가 재전송된다. POST 처리 후 즉시 GET 페이지로 리다이렉트해 두면 새로고침해도 GET만 반복된다.

이 층의 가치 (분명히 있다)

  • 최다 빈도 경로(더블 클릭)를 끊는다
  • 하위 층의 부하와 CS 문의를 줄인다

새는 곳 (구조적 한계)

6. 2선 멱등성 키 — 같은 시도의 재전송을 흡수

6-1. 멱등성과 멱등성 키가 무엇인가

멱등성(idempotency)은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"이다. 전등의 끄기 버튼을 열 번 눌러도 결과는 꺼진 상태 하나인 것과 같다. HTTP에서 GET·PUT·DELETE는 멱등하고 POST는 멱등하지 않다고 말하는 것도 이 뜻이다 — POST는 부를 때마다 새 자원이 생긴다.

결제는 본질적으로 POST다. 그래서 인위적으로 멱등하게 만들어야 한다. 그 장치가 멱등성 키(idempotency key)다.

키를 만드는 주체
클라이언트가 결제 시도 1건마다 고유한 키를 하나 만든다(보통 UUID).
보내는 방법
Idempotency-Key 헤더에 실어 보낸다.
서버가 하는 일
유니크 제약이 걸린 저장소에 먼저 INSERT해서 자리를 선점(INSERT-first)하고, 선점에 성공한 최초 요청만 실제 결제를 수행한다. 같은 키가 다시 오면 저장해 둔 최초 응답을 재생한다.
여기서 INSERT-first가 무엇인지 — 이 문서의 핵심 단어다 "일을 하기 전에 먼저 DB에 자리를 잡는" 순서를 말한다. 검사부터 하지 않고 INSERT부터 하는 이유는, 3절에서 본 check-then-act의 틈을 없애기 위해서다. INSERT는 유니크 제약과 결합하면 "확인과 선점"이 DB 안에서 한 번에 원자적으로 일어난다 — 검사와 실행 사이에 끼어들 시간 자체가 존재하지 않는다.

6-2. 이 층이 흡수하는 것과 그냥 통과시키는 것

키의 상세 설계는 이 문서의 범위가 아니다 멱등성 키의 상세 설계(키 스코프, 응답 저장 형식, TTL, 동시 요청 처리)는 09-rest-api/06 문서가 다룬다. 여기서는 계층 구조 안에서의 위치와 한계만 짚는다.

6-3. 새는 곳 — 멱등성 키의 관할 밖

멱등성 키는 전송 계층의 중복만 막는다. 사용자가 실패 화면에서 의도적으로 "다시 시도"를 누르면 클라이언트는 새 키를 만든다. 그리고 그건 클라이언트 입장에서 올바른 동작이다 — 사용자가 새 시도를 했으니까. 문제는 첫 결제가 사실은 성공해 있었던 경우다. 키가 다르니 서버는 이걸 정당한 신규 요청으로 보고 그대로 통과시킨다.

키 스코프 버그
사용자별로 격리해야 할 키를 전역으로 쓰거나 그 반대.
TTL 만료
키 보관 기간이 지난 뒤 도착한 늦은 재시도.
헤더 전파 누락
API 게이트웨이 교체 배포에서 Idempotency-Key 헤더가 전달되지 않는다.
세 가지 모두 "버그 하나로 층 전체가 사라지는" 형태다 — 상위 층을 최후의 방어선으로 삼으면 안 되는 이유

7. 3선 분산 락 — 줄 세우기이지, 보장이 아니다

7-1. 왜 DB 락이 아니라 "분산" 락인가

한 프로세스 안이라면 synchronized로 줄을 세우면 된다. 그런데 결제 서버는 보통 여러 대다. 서버 A와 서버 B에 각각 요청이 들어오면 synchronized는 서로를 모른다. 그래서 모든 서버가 공유하는 외부 저장소에 "지금 이 주문은 내가 처리 중"이라는 표식을 두는데, 이것이 분산 락(distributed lock)이다. Redis가 흔히 쓰인다.

Redis 분산 락 획득 — 두 개의 옵션이 전부다
SET lock:payment:order:8471 <소유자ID> NX PX 3000
        │                        │  │
        │                        │  └─ PX 3000 : TTL(Time To Live) 3초 — 3초 뒤 자동 소멸
        │                        └──── NX       : 키가 없을 때만 설정 (먼저 잡은 쪽이 이긴다)
        └─────────────────────────────  잠글 대상은 "주문 단위"

TTL이 필요한 이유는, 락을 잡은 서버가 죽어버리면 아무도 락을 풀어주지 않아 그 주문이 영원히 처리 불가가 되기 때문이다. 그런데 바로 이 TTL이 다음 절에서 구멍의 원천이 된다.

이 층은 분명히 유효하다 — 무시하지 말 것 같은 주문의 동시 요청을 직렬화해 하위 층의 충돌 빈도와 불필요한 PG 호출을 줄인다. "락은 어차피 새니까 안 쓴다"가 아니라 "락은 확률을 낮추고, 제약이 판정한다"가 정확한 위치 설정이다.

7-2. 새는 곳 — 이것만 믿으면 안 되는 세 가지 이유

(1) TTL 만료

  • 락 TTL이 3초인데 소유자가 5초 걸리면?
  • TTL은 이미 만료됐고 두 번째 요청이 락을 새로 획득한다
  • 첫 번째 스레드는 자기가 락을 잃은 줄 모르고 계속 실행 → 둘이 동시에 실행

(2) 페일오버 시 락 유실

  • Redis 마스터가 죽어 레플리카로 승격될 때
  • 마스터에만 있고 아직 복제되지 않은 락 정보는 사라진다
  • 그 순간 같은 락을 두 요청이 동시에 쥔다 — 복제가 비동기이므로 이 창은 구조적으로 존재

(3) 해제와 커밋의 순서 버그

  • 락을 먼저 풀고 나중에 커밋하는 코드
  • 그 사이에 들어온 다음 요청은 아직 커밋되지 않아 보이지 않는 데이터를 검사하고 통과한다
  • 가장 흔하고 가장 눈에 안 띄는 버그

락이 새는 세 경로 — 즉석에서 열거할 수 있어야 한다

티 · 페 · 순 — 티TL 만료 · 페일오버 유실 · 해제/커밋 순서

"분산 락을 걸었는데 왜 유니크 제약이 또 필요한가요?"라는 꼬리질문의 변별 지점이 정확히 이 세 개를 말할 수 있는가다. 세 개를 못 대면 "책에서 읽었다"로 들리고, 대면 "겪어봤다"로 들린다.

여기서 "5초 걸릴 일이 있나?" — 있다

대표적인 것이 GC 멈춤(stop-the-world pause)이다. JVM이 가비지 컬렉션을 하는 동안 애플리케이션 스레드가 전부 멈추는데, 힙이 크고 full GC가 걸리면 수 초가 걸릴 수 있다. 멈춘 스레드는 자기가 멈춘 줄도 모른다. PG 응답 지연도 같은 결과를 만든다.

7-3. Before / After — 락 해제와 커밋의 순서

before 락 해제가 커밋보다 먼저 — 그 틈에 다음 요청이 통과한다
lock.acquire(key);
try {
    paymentService.pay(orderId);   // @Transactional 안에서 커밋
} finally {
    lock.release(key);             // 커밋 완료 전에 풀릴 수 있다
}

// 트랜잭션 경계가 이 메서드 "바깥"에 걸려 있으면
// pay()가 반환돼도 아직 커밋 전일 수 있다.
// 락은 이미 풀렸고, 다음 요청은 "아직 안 보이는 데이터"를
// 검사한 뒤 통과한다 → 3절의 레이스가 그대로 재현된다.
after 트랜잭션 커밋이 끝난 뒤에 푼다
lock.acquire(key);
try {
    paymentService.pay(orderId);
    // pay()가 반환된 시점 = 커밋 완료 시점이 되도록
    // 트랜잭션 경계를 pay() 내부에 두고,
    // 락 획득/해제는 그 바깥에 둔다.
} finally {
    lock.release(key);             // 커밋 이후에만 풀린다
}
순서 규칙 — 락의 생명은 트랜잭션의 생명을 완전히 감싸야 한다 (획득 → 트랜잭션 시작 → 커밋 → 해제)

3선의 결론 — 이 한 문장이 4선으로 넘어가는 다리다

락은 원자성의 출처가 될 수 없다. 락은 "대부분의 경우 줄을 잘 세워주는" 확률적 장치다.

결제 트래픽이 하루 수십만 건이면 0.01%도 매일 수십 건이다. "낮은 확률"은 돈 도메인에서 "반드시 일어난다"와 같은 말이다. 원자성의 출처는 다음 층이다.

8. 4선(최후) DB — 유니크 제약 + 조건부 UPDATE

8-1. 도메인 불변식을 DB에 새긴다

도메인 불변식(domain invariant)이란 그 업무에서 언제나 참이어야 하는 규칙이다. 여기서의 불변식은 이것이다.

이 문서에서 외워야 할 단 하나의 문장

"하나의 주문에는 살아있는(진행 중이거나 승인된) 결제가 1건만 존재한다"

이 규칙을 코드의 if문이 아니라 DB 제약으로 새기는 것이 4선의 전부다. 면접에서 이 문장을 그대로 말할 수 있으면 "계층을 나열한 사람"이 아니라 "최후의 방어선을 아는 사람"이 된다.

이유는 명확하다. 애플리케이션 코드는 경로마다 따로 짜여 있어서(결제 API, 웹훅 핸들러, 배치, 어드민 툴) 한 곳에서 빠뜨리면 뚫린다. DB 제약은 모든 쓰기가 반드시 통과하는 단일 관문이다.

8-2. 부분 유니크 인덱스 — 불변식을 그대로 SQL로 옮긴다

PostgreSQL은 이 불변식을 부분 유니크 인덱스(partial unique index)로 정확히 표현할 수 있다. 부분 인덱스란 WHERE 조건을 만족하는 행에 대해서만 만들어지는 인덱스를 말한다.

PostgreSQL 도메인 불변식이 그대로 SQL이 된다
-- 주문당 PENDING/APPROVED 결제는 1건만. FAILED는 여러 건 쌓여도
-- 되므로(재시도 이력을 남겨야 한다) 인덱스 대상에서 제외한다.
CREATE UNIQUE INDEX uq_payment_active_per_order
    ON payment (order_id)
 WHERE status IN ('PENDING', 'APPROVED');
왜 단순 UNIQUE (order_id)로는 안 되는가
단순 UNIQUE (order_id)부분 유니크 인덱스
살아있는 결제 중복막는다막는다
FAILED 이력 여러 건불가능 — 재시도 자체가 막힌다얼마든지 쌓인다
인덱스 크기전체 결제 행진행 중인 결제만 → 작게 유지
불변식과의 대응"주문당 결제 1건" (틀린 규칙)"주문당 살아있는 결제 1건" (맞는 규칙)

8-3. Before / After — exists 검사에서 INSERT-first로

before 애플리케이션 exists 검사 — 3절의 레이스에 그대로 뚫린다
public Payment start(long orderId, long amount) {
    if (paymentRepository.existsActiveByOrderId(orderId)) {  // ① 검사
        throw new DuplicatePaymentException(orderId);
    }
    Payment p = paymentRepository.save(
        Payment.pending(orderId, amount));                   // ② 생성
    pgClient.approve(p);                                     // ③ 승인
    return p;

    // 두 요청이 동시에 ①에서 "없음"을 보면 둘 다 ③까지 간다 —
    // 9,900원이 PG에서 두 번 승인된다.
    // ①과 ② 사이 틈이 곧 사고다.
}
after INSERT-first 선점 — 유니크 인덱스가 심판을 본다
public Payment start(long orderId, long amount) {
    Payment p;
    try {
        // PG 승인 "전"에 PENDING 행을 넣어 자리를 선점한다.
        // saveAndFlush로 즉시 INSERT를 날려야 여기서 제약 위반이 난다.
        // (save만 하면 트랜잭션 종료 시점까지 INSERT가 미뤄질 수 있다)
        p = paymentRepository.saveAndFlush(
                Payment.pending(orderId, amount));
    } catch (DataIntegrityViolationException e) {
        // 유니크 위반 = 누군가 먼저 선점했다는 뜻.
        // 중요한 건 "여기서 끝나면 PG에는 돈이 안 나갔다"는 점이다.
        throw new PaymentAlreadyInProgressException(orderId);
    }

    pgClient.approve(p);            // 최초 1건만 여기 도달한다

    int updated = paymentRepository.approve(p.getId());
    // rowcount 0 = 그 사이 누군가(웹훅/배치) 이미 상태를 바꿨다는 뜻.
    // 조용히 덮어쓰지 않고 예외로 드러내 조사 대상으로 만든다.
    if (updated == 0) throw new IllegalPaymentStateException(p.getId());
    return p;
}
after (2) 상태 전이도 조건부 UPDATE — PENDING일 때만 APPROVED가 된다
@Modifying
@Query("UPDATE Payment p SET p.status = 'APPROVED' " +
       "WHERE p.id = :id AND p.status = 'PENDING'")   // ← 검사 조건이 WHERE로 들어갔다
int approve(@Param("id") long id);

8-4. 포인트 두 가지 — 순서와 조건

첫째, 선점을 PG 승인 앞에 둔다

둘째, 상태 전이를 조건부 UPDATE로 잠근다

WHERE status = 'PENDING'이 붙어 있으면, 웹훅과 폴링이 동시에 같은 결제를 승인 확정하려 해도 rowcount 1을 얻는 쪽은 하나뿐이다. 늦게 온 쪽은 0건을 받고 자기가 졌다는 것을 안다.

05번 문서의 잔액 차감과 정확히 같은 원리 
UPDATE wallet SET balance = balance - 9900
 WHERE user_id = ? AND balance >= 9900   -- 검사가 WHERE 안으로 들어갔다

4선을 한 문장으로 — 이것이 3절 "틈"에 대한 답이다

검사 조건을 WHERE에 넣어, 검사와 실행 사이의 틈을 없앤다
INSERT-first + 유니크 제약
"존재하지 않을 때만 만든다"를 한 연산으로. 존재 확인과 선점이 DB 안에서 원자적으로 끝난다.
조건부 UPDATE
"아직 PENDING일 때만 APPROVED로"를 한 연산으로. rowcount가 승패 판정을 대신한다.

rowcount 규칙 — 1 = 내가 이겼다(후속 처리는 여기서만) · 0 = 누군가 먼저 바꿨다(덮어쓰지 말고 예외로 드러내 조사 대상으로). 0을 성공처럼 흘려보내는 것이 실무 최다 구멍이다.

9. 5선(사후) 대사 — 예방이 아니라 탐지·보정

4선까지 쌓아도 남는 것이 있다. 4선이 지키는 것은 "우리 DB의 상태"이지, PG 쪽 상태가 아니기 때문이다.

4선이 못 보는 상황

  • 우리 DB에는 결제가 1건인데 PG에는 2건이 승인돼 있다
  • 승인은 됐는데 우리 쪽 기록 직전에 죽었거나, 취소 API 호출이 유실된 채 잊힌 케이스
  • 우리 DB만 봐서는 아무 이상이 없어 보인다 — 이것이 가장 무서운 부분

대사(reconciliation)가 하는 일

  • 대사란 서로 다른 곳에 기록된 숫자를 맞춰 보고 어긋난 부분을 찾아내는 회계 작업
  • 매일 PG가 내려주는 거래 내역 파일과 우리 payment 테이블·원장을 orderId 기준으로 돌려 맞춘다
  • "우리 1건 : PG 2건" 같은 불일치를 찾아 자동 취소를 걸거나 운영자 보정 큐로 넘긴다
이것은 방어선이라기보다 그물 아래의 그물이다 — 막지는 못하지만, 뚫린 것을 며칠 안에 반드시 발견한다는 보장 장치

10. 실무 사례 — 방어선이 실제로 뚫리는 순간들

사례 1: 두 탭 결제 — UI가 막았다고 믿었던 팀

사용자가 결제 페이지를 두 탭에 열어두고 각각 결제 버튼을 눌렀다.

1선 UI 통과→ 2선 멱등성 키 통과→ 3선 락 — 동시면 대기, 순차면 통과→ 4선 DB 제약에서 차단
  • 각 탭의 버튼은 성실하게 비활성화됐다. 하지만 탭들은 서로의 존재를 모른다.
  • 멱등성 키도 탭마다 새로 생성돼 서로 다르다 — 1선·2선을 나란히 통과한다.
  • 3선 분산 락이 있었다면 둘 중 하나는 대기했겠지만, 첫 번째가 PG 승인을 마치고 락을 푼 뒤에는 두 번째가 그대로 진행한다. 락은 "동시"만 막지 "순차 중복"은 못 막는다.
  • 4선이 없었다면 9,900원이 2건 승인된다. 부분 유니크 인덱스가 있었다면 두 번째 INSERT가 PaymentAlreadyInProgressException으로 끝나고 PG 호출 자체가 발생하지 않는다.
교훈 — 상위 층의 방어는 "한 클라이언트 인스턴스" 스코프까지만 유효하다. 탭이 둘이면 클라이언트도 둘이다.

사례 2: "다시 시도" 새 키 — 멱등성 키의 관할 밖

첫 결제 요청이 PG 승인까지 정상적으로 끝났는데 응답이 유실됐다. 사용자는 실패 화면을 보고 "다시 시도"를 눌렀고, 클라이언트는 새 멱등성 키를 만들었다. 클라이언트 입장에서는 새 시도이므로 새 키가 올바른 동작이다.

그래서 2선은 이 요청을 설계대로 통과시킨다. 버그가 아니다. 이 요청을 멈출 수 있는 것은 "주문당 승인 결제 1건"이라는 도메인 불변식(4선)뿐이다.

전송 계층 중복 제거 (transport-level dedup)

  • 장치: 멱등성 키
  • 묻는 질문: "같은 메시지가 두 번 왔는가"
  • 알 수 있는 것: 요청의 동일성

비즈니스 중복 제거 (business-level dedup)

  • 장치: 도메인 불변식 = DB 제약
  • 묻는 질문: "이 업무가 이미 완료됐는가"
  • 알 수 있는 것: 업무의 기완료 여부
서로 다른 질문에 답하는 장치이므로 대체 관계가 아니다

사례 3: GC 멈춤 8초가 만든 이중 차감 — 락의 배신

포인트 30,000P 차감을 처리하던 중 애플리케이션이 full GC로 8초 멈췄다. 타임라인은 7-2절 도식에 그대로 그려져 있다.

30,000P가 두 번 빠져 합계 60,000P가 차감됐다. 원장에 UNIQUE (order_id, entry_type)이 있었다면 두 번째 INSERT가 유니크 위반으로 실패하며 그 차감 트랜잭션 전체가 롤백됐을 것이다.

락은 줄을 세울 뿐이고, 최종 심판은 DB 제약이라는 것을 돈으로 배운 사례

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 답을 먼저 떠올리고 오른쪽을 본다

이중 결제 여섯 경로는?
화면 2(더블클릭·두 번째 탭) · 망 1(자동 재전송) · 사람 2(다시 시도·어드민 재처리) · 서버 간 1(웹훅/배치). 성격이 다르므로 한 장치로 못 막는다.
다섯 층을 성격으로 말하면?
빈 · 재 · 줄 · 판 · 탐 — 빈도 감소(UI) · 재전송 흡수(멱등성 키) · 줄 세우기(분산 락) · 최종 판정(DB 제약) · 탐지·보정(대사).
락이 새는 세 경로는?
티 · 페 · 순 — TTL 만료(GC 멈춤·PG 지연) · 페일오버 시 락 유실 · 해제와 커밋의 순서 버그.
멱등성 키가 못 막는 것은?
새 키로 온 새 시도. 키는 "같은 메시지가 두 번 왔는가"만 알 뿐 "이 업무가 이미 완료됐는가"는 모른다.
최후의 방어선이 DB인 이유 두 가지?
① 모든 쓰기 경로가 반드시 통과하는 단일 관문 ② 판정의 원자성을 DB 엔진이 보장. (상위 층은 배포 실수·레이스로 뚫린다)
도메인 불변식 한 문장은?
"하나의 주문에는 살아있는(PENDING/APPROVED) 결제가 1건만 존재한다" → 부분 유니크 인덱스로 새긴다.
단순 UNIQUE(order_id)가 틀린 이유?
FAILED 이력을 2건 이상 못 남긴다 → 재시도 자체가 불가능해진다. 그래서 WHERE status IN ('PENDING','APPROVED')로 대상을 좁힌다.
선점(INSERT)은 어디에 두나?
PG 승인 "앞". 승인 뒤에 두면 위반 시 이미 돈이 나간 뒤라 취소·보정 큐·CS가 줄줄이 붙는다. 앞에 두면 돈이 아예 안 나간다.
조건부 UPDATE의 rowcount 규칙?
1 = 내가 이겼다(후속 처리는 여기서만) / 0 = 누가 먼저 바꿨다(덮어쓰지 말고 예외로 드러낸다). 0을 성공처럼 흘리는 게 최다 구멍.
대사의 성격 한 줄?
예방이 아니라 탐지·보정. 게다가 불일치 건수·금액을 지표로 쌓으면 상위 층의 조기 경보가 된다 — 평소 0이던 값이 오르면 어딘가에 구멍이 새로 생긴 것.

면접에서 이 질문을 받으면 — 30초 답변 골격

① "각 층은 반드시 뚫린다는 전제로 쌓습니다"로 연다 → ② 다섯 층을 성격과 함께 나열한다(빈·재·줄·판·탐) → ③ "최후의 방어선은 DB여야 합니다"와 그 이유 두 가지(단일 관문·원자성) → ④ 불변식 문장("주문당 살아있는 결제 1건")과 부분 유니크 인덱스 → ⑤ "선점은 PG 승인 앞에 둡니다"로 실무 감각을 붙이고 → ⑥ "그래도 새는 것은 대사가 잡습니다"로 닫는다.

11-2. 꼬리질문 — 먼저 답해보고 펼친다

분산 락을 걸었는데 왜 유니크 제약이 또 필요한가요? 시니어 변별힌트: 두 장치의 "역할"이 다르다. 그리고 락이 깨지는 경로 세 개를 즉석에서 댈 수 있는가?

락과 제약은 역할이 다르다는 것부터 말한다.

락 = 가용성·효율 장치

  • 동시 요청을 줄 세워 충돌 빈도와 불필요한 PG 호출을 줄인다
  • 사고를 "덜 일어나게" 만드는 확률적 장치
  • 보장은 TTL 만료 · 페일오버 유실 · 해제/커밋 순서 버그로 깨진다
  • 그리고 이 깨짐은 낮은 확률로 반드시 일어난다

제약 = 정합성 장치

  • DB 엔진이 쓰기 시점에 원자적으로 판정한다
  • 상위에서 무엇이 새어 들어와도 최종 상태의 불변식은 지켜진다
  • 코드 경로가 늘어나도 자동으로 적용된다
결제 트래픽이 하루 수십만 건이면 0.01%도 매일 수십 건이다 — "낮은 확률"은 돈 도메인에서 "반드시 일어난다"와 같은 말

이 꼬리질문의 변별 지점은 "락이 뚫리는 세 가지 경로를 즉석에서 열거할 수 있는가"다. 티·페·순을 구체적으로 말할 수 있어야 한다.

한 걸음 더 — fencing token 락을 줄 때 단조 증가하는 세대 번호를 함께 발급하고, 실제 쓰기에 그 번호를 실어 보내 저장소가 "지금까지 본 것보다 낮은 번호의 쓰기는 거부"하게 하는 기법이다. TTL 만료 시나리오에서 깨어난 옛 소유자의 쓰기를 거부할 수 있다. 다만 결론은 같다 — 최종 판정은 데이터 저장소에서 한다.
유니크 위반이 났을 때 이미 PG 승인이 떨어진 뒤라면요?힌트: 순서를 바꿔 대부분 예방한 뒤, 그래도 남는 경로가 무엇인지 생각해본다

선점(INSERT)을 승인 앞에 두면 대부분 예방된다. 하지만 웹훅 기반 확정처럼 승인 사실을 나중에 아는 경로에서는 "PG 승인 2건, 우리 DB 1건"이 여전히 생길 수 있다.

1
탐지 즉시 두 번째 승인 건을 PG 취소 API로 자동 취소한다.
2
취소 호출마저 실패하면 보정 큐에 적재해 재시도 + 운영자 알림으로 넘긴다.
3
고객 카드에 9,900원이 이중 청구된 상태는 분 단위로 해소돼야 하는 장애로 취급한다. 하루 뒤 배치로 처리하면 이미 카드사 청구가 나간다.
여기서 망취소(net cancellation)를 알면 실무 경험이 드러난다 승인 직후 같은 날 안에 취소하면 승인 자체를 없던 것으로 처리해 매입(청구)이 아예 발생하지 않게 해주는 PG가 있다. 이 경우 고객 명세서에 승인·취소 두 줄이 남지 않아 CS가 크게 줄어든다.
멱등성 키가 있는데 도메인 불변식이 왜 또 필요한가요? 필수힌트: 두 장치가 각각 "무엇을 묻는지"를 문장으로 만들어본다

멱등성 키의 관할은 "같은 키 = 같은 시도의 재전송"까지다.

새 키로 오는 새 시도 — 사용자의 의도적 재시도, 다른 탭, 어드민 재처리 — 는 키 입장에서 전부 정당한 신규 요청이다. 키는 "이 요청이 아까 그 요청과 같은 것인가"만 판단할 수 있고, "이 업무가 이미 완료됐는가"는 판단할 수 없다. 후자를 아는 것은 도메인 규칙뿐이다.

멱등성 키는 재시도 폭풍을 흡수하는 완충재, 도메인 불변식은 최종 관문 — 층이 다르므로 서로 대체가 안 된다

근거로 사례 2를 그대로 든다 — "승인은 났는데 응답이 유실돼 사용자가 다시 시도한 경우, 2선은 설계대로 통과시킵니다. 버그가 아닙니다. 그 요청을 멈출 수 있는 건 4선뿐입니다."

대사 배치도 방어선이라고 할 수 있나요?힌트: 예방과 탐지는 성격이 다르다. 그리고 대사 결과를 "지표"로 보면 용도가 하나 더 생긴다

성격이 다르다는 것을 먼저 짚는다. 1~4선은 예방이다 — 사고가 데이터에 기록되기 전에 차단한다. 대사는 탐지·보정이다 — 이미 벌어진 불일치를 찾아 되돌린다.

예방이 완벽할 수 없다는 전제를 받아들이면 탐지는 선택이 아니라 필수가 된다. 돈 도메인에서 최악은 사고가 나는 것이 아니라 "뚫렸는지조차 모르는 상태"이기 때문이다. 사고는 보상하면 되지만, 모르는 사고는 규모가 계속 자란다.

한 가지 더 붙이면 좋다 — 대사는 조기 경보이기도 하다 대사가 잡은 불일치는 금액·건수와 함께 지표로 쌓아야 한다. 이 지표가 평소 0인데 어느 날부터 0이 아니라면, 상위 방어선 어딘가에 구멍이 새로 생겼다는 뜻이다 — 대사 결과는 사후 보정 도구인 동시에 상위 층의 조기 경보로 쓰인다.
PostgreSQL에서 "주문당 승인 결제 1건"을 정확히 어떻게 표현하나요? MySQL이라면요? 가산점힌트: 단순 UNIQUE는 왜 틀리는가부터. MySQL에는 부분 인덱스가 없다

단순 UNIQUE (order_id)는 틀린다. 실패한 결제(FAILED)가 이력으로 여러 건 남아야 하는데 그것까지 막아버려 재시도가 불가능해진다. 부분 유니크 인덱스로 조건을 좁힌다.

CREATE UNIQUE INDEX uq_payment_active_per_order
    ON payment (order_id)
 WHERE status IN ('PENDING', 'APPROVED');

"살아있는 결제만 1건"이라는 불변식이 그대로 SQL이 된다. 부가 이점으로, 인덱스가 진행 중인 결제만 담으므로 크기가 작게 유지된다.

MySQL에는 부분 인덱스가 없다는 것까지 알면 DB별 차이를 아는 사람으로 보인다. 같은 요구를 MySQL에서 풀려면 "살아있으면 order_id, 아니면 NULL"을 담는 생성 칼럼(generated column)을 만들고 거기에 유니크를 건다 — MySQL의 유니크 인덱스는 NULL을 중복으로 치지 않기 때문에 FAILED 행은 얼마든지 쌓인다.

-- MySQL 우회: 살아있는 결제만 값을 갖는 생성 칼럼에 유니크를 건다
ALTER TABLE payment
  ADD COLUMN active_order_id BIGINT
      GENERATED ALWAYS AS (
        CASE WHEN status IN ('PENDING','APPROVED') THEN order_id END
      ) STORED,
  ADD UNIQUE KEY uq_payment_active (active_order_id);

핵심은 문법이 아니라 "불변식을 저장소가 이해하는 언어로 번역한다"는 태도다. 표현 수단은 DB마다 다르지만 목표 문장은 하나다.

PENDING 행이 좀비로 남으면 그 주문은 영영 결제 못 하는 것 아닌가요? 시니어 변별힌트: 인덱스 조건에 PENDING이 들어 있다는 사실을 뒤집어 생각해본다

정확한 지적이고, 실제로 일어난다. 부분 유니크 인덱스가 PENDING까지 포함하므로, 서버가 죽거나 PG 응답이 유실돼 PENDING인 채 남은 행이 있으면 그 주문의 새 결제 INSERT가 전부 막힌다. 사용자는 "결제를 시도할 수 없습니다"만 보게 된다. 안전장치가 서비스 장애로 바뀌는 순간이다.

불변식을 강하게 걸수록 "그 상태에서 빠져나오는 경로"를 반드시 함께 설계해야 한다

하면 안 되는 것

  • 오래된 PENDING을 무조건 FAILED로 일괄 정리 — 실제로는 승인됐을 수 있다. 돈이 나간 건을 시야에서 지우는 것이다
  • 인덱스에서 PENDING을 빼기 — 그러면 동시 요청 선점이 무력화된다(4선이 사라진다)

해야 하는 것

  • PENDING 행에 만료 시각을 두고, 정리 배치가 PG 거래조회로 진실을 확인한 뒤 APPROVED 또는 FAILED로 조건부 UPDATE
  • 확인이 안 되는 건은 UNKNOWN 계열로 두고 사람에게 알림 — 자동으로 못 끝내는 건이 있다는 것을 인정한다
  • 좀비 PENDING 건수를 지표화 — 늘어나면 상위 경로에 문제가 생긴 것

이 흐름은 01-payment-state-management의 고아 행 처리, 04-pg-timeout-unknown-state의 UNKNOWN 해소와 같은 장치다 — 새 로직을 만드는 게 아니라 기존 해소 배치로 흘려보낸다.

두 번째 INSERT는 유니크 위반이 즉시 나나요, 아니면 기다리나요? 시니어 변별힌트: 첫 트랜잭션이 아직 커밋 전이라면, DB는 그 행이 살아남을지 아직 모른다

즉시 실패하지 않고 기다린다. 첫 트랜잭션이 아직 커밋도 롤백도 하지 않았다면, DB는 그 선점 행이 최종적으로 존재하게 될지 아직 알 수 없다. 그래서 두 번째 INSERT는 첫 트랜잭션이 끝날 때까지 블록된다.

첫 트랜잭션이 커밋되면
두 번째는 유니크 위반 예외를 받는다 → PaymentAlreadyInProgressException.
첫 트랜잭션이 롤백되면
두 번째 INSERT가 성공한다 → 이 요청이 새 선점자가 된다. 선점이 자동으로 인계되는 셈이라 오히려 바람직하다.
여기서 나오는 실무 함정 선점 트랜잭션 안에 PG 호출을 넣으면 대기 시간이 그만큼 길어진다. PG 응답이 5초 걸리면 뒤에 온 요청은 5초 동안 DB 커넥션을 쥔 채 대기하고, 그런 요청이 몰리면 커넥션 풀이 고갈돼 결제와 무관한 API까지 함께 죽는다.
그래서 실무 경계는 "선점만 짧게 커밋 → 트랜잭션 밖에서 PG 호출 → 결과를 조건부 UPDATE로 반영" 세 토막이다

이 세 토막은 01-payment-state-management의 "선(선점) · 밖(트랜잭션 밖 PG 호출) · 조(조건부 UPDATE)"와 정확히 같은 구조다.

다섯 층 중 딱 하나만 만들 수 있다면 무엇을 고르겠습니까?힌트: "정합성"으로 답할 것인가 "비용 효율"로 답할 것인가 — 질문의 기준을 되짚어 말하는 게 정답이다

기준을 나눠 답하는 것이 이 질문의 정답 형태다. 하나만 고르라는 질문에 하나만 답하면 다른 기준을 못 본 사람이 된다.

정합성 기준이라면 → 4선 DB 제약

  • 다른 넷은 전부 "덜 일어나게" 하는 장치다
  • 발생 자체를 0으로 만드는 층은 4선뿐
  • 돈 도메인에서 포기할 수 없는 것은 "뚫려도 최종 상태는 옳다"

비용 효율 기준이라면 → 1선 UI

  • 실제 중복 요청의 대다수가 더블 클릭이다
  • 코드 몇 줄로 그 대부분이 사라진다
  • 단, 이건 "트래픽을 줄이는" 답이지 "사고를 막는" 답이 아니다
모범 답 — "하나만 고르면 4선입니다. 정합성을 책임지는 층은 거기뿐이기 때문입니다. 다만 실제로 가장 값싸게 효과를 내는 건 1선이라, 현실에서는 1선과 4선을 먼저 만들고 2·3선을 붙입니다."

덧붙일 한 줄 — 2선(멱등성 키)은 "자동 재전송"이라는, 다른 층이 값싸게 처리하지 못하는 고유 영역을 갖는다. 그래서 실무 우선순위는 보통 4선 → 1선 → 2선 → 3선 → 5선이 된다(5선은 규모가 커지면 필수가 된다).

멱등성 키 저장소를 Redis에 두면 안 되나요?힌트: 7절에서 Redis 락이 새는 이유를, 그대로 키 저장소에 대입해본다

"1차 필터"로는 좋고, "판정자"로는 위험하다. 이유는 7절에서 락이 샜던 이유와 완전히 같다.

TTL·축출
키가 사라지면 같은 키의 재전송이 신규 요청으로 통과한다.
페일오버 유실
복제가 비동기라 선점 기록이 사라지는 창이 구조적으로 존재한다.
응답 재생 불가
최초 응답 본문까지 잃으면 재전송에 무엇을 돌려줄지 알 수 없다.
원칙 — "빠르게 걸러내는 것"은 Redis, "최종적으로 판정하는 것"은 유니크 제약이 걸린 영속 저장소

이 답이 좋은 이유는 이 문서의 원칙을 다른 대상에 그대로 적용해 보였기 때문이다 — 휘발성 저장소는 확률을 낮추고, 영속 저장소의 제약이 판정한다. 락이든 멱등성 키든 구조는 같다.

실패한 결제를 다시 시도할 때, 새 행을 만드나요 기존 행을 되살리나요?힌트: 부분 유니크 인덱스가 FAILED를 제외한 이유를 떠올려본다

새 행을 만든다. FAILED 행은 이력으로 남기고 건드리지 않는다. 부분 유니크 인덱스가 WHERE status IN ('PENDING','APPROVED')로 FAILED를 제외한 이유가 바로 이것이다.

새 행을 만들 때 얻는 것

  • 시도마다 PG 거래 키·실패 사유·시각이 따로 보존된다
  • 대사 때 PG 쪽 시도 건수와 1:1로 맞춰볼 수 있다
  • "몇 번 실패한 뒤 성공했는가"가 데이터로 남아 어뷰징·카드 문제 분석이 가능해진다

기존 행을 되살릴 때 잃는 것

  • 이전 시도의 PG 거래 키가 덮여 사라진다 → 그 승인이 남아 있어도 추적 불가
  • 상태가 FAILED → PENDING으로 되돌아가는 전이가 생겨 상태 머신이 오염된다
  • 이력 테이블 없이는 "왜 이 상태인지" 재구성이 불가능해진다

단, 새 행을 만드는 설계에서는 "한 주문에 결제 행이 여러 개"가 정상이므로, 조회·정산 코드가 항상 "살아있는 1건"을 기준으로 동작하도록 맞춰야 한다. 불변식이 지켜주는 것이 정확히 그 지점이다.

한 줄 요약
이중 지급 방어는 스위스 치즈처럼 겹쳐 쌓는다 — UI는 빈도를 줄이고, 멱등성 키는 같은 시도의 재전송을 흡수하고, 분산 락은 줄을 세울 뿐이며, 최종 판정은 DB의 유니크 제약(주문당 살아있는 결제 1건)과 조건부 UPDATE가 내린다 — 상위 층은 레이스와 배포 실수로 반드시 뚫린다는 전제 아래 최후의 방어선을 데이터 저장소에 두고, 그래도 새어나간 불일치는 대사 배치가 반드시 찾아내도록 설계해야 완성이다.
