비동기 승인 결제 수단
가상계좌의 "완료"는 응답이 아니라 웹훅으로 온다

면접 질문: "가상계좌처럼 승인이 비동기로 완료되는 결제 수단은 상태 설계가 어떻게 달라지나요?"

핵심 관전 포인트 — 카드 결제는 요청-응답 한 사이클 안에 승인이 확정되는 동기 모델이지만, 가상계좌·계좌이체·후불 결제는 "결제 요청 성공"과 "돈이 실제로 들어옴" 사이가 몇 시간에서 며칠까지 벌어지는 비동기 모델이다. 그래서 상태 머신에 입금 대기(WAITING_DEPOSIT)와 기한 만료(EXPIRED)라는 새 상태가 필수로 추가되고, 승인의 유일한 완료 신호가 API 응답이 아니라 PG의 입금 통보 웹훅이 된다 — 웹훅은 중복되고, 유실되고, 만료 배치와 경합하므로 멱등 처리·조회 API 보완 대사·조건부 UPDATE가 설계의 중심이 된다. 여기에 금액 불일치 입금, 기한 후 입금, 부분 입금이라는 카드에는 없던 케이스와 "입금 대기 중 재고를 선점할 것인가"라는 주문 도메인과의 결합 문제까지 답할 수 있어야 한다.
  • 1
    상태 머신에 두 칸이 늘어난다 — 카드의 IN_PROGRESS는 수명이 몇 초지만, 가상계좌의 WAITING_DEPOSIT은 시간~일 단위로 체류하는 정상 상태다. 그리고 카드에는 사실상 없던 EXPIRED가 가장 흔한 종결 상태가 된다. 둘 다 예외가 아니라 정상 흐름이므로 조회·CS·지표·알림이 전부 이 상태를 정규로 다뤄야 한다.
  • 2
    완료 신호의 방향이 뒤집힌다 — 우리가 결과를 받아오는 게 아니라 PG가 걸어오는 입금 웹훅이 유일한 완료 신호다. 웹훅은 중복·위조·유실되고 만료 배치와 같은 행을 두고 경합하므로, 핸들러는 서명 검증 → 조회 API 재확인 → 금액 검증 → 조건부 UPDATE 네 관문으로 짜고, 유실 대비 조회 대사 배치(pull)를 항상 하나 더 둔다.
  • 3
    카드에 없던 예외가 전부 자동 환불로 수렴한다 — 기한 후 입금 · 금액 불일치 입금 · 취소 후 입금은 모두 "돈은 들어왔는데 주문이 없다"로 끝나므로, 로그가 아니라 예외 큐 → 전액 자동 환불 → 고객 안내 → 대사 잔량 0 확인까지가 한 설계 범위다. 그리고 입금 대기 동안 재고를 선점할지는 기술이 아니라 도메인 정책 결정이다.

0. 질문 + 출제 의도

질문: "가상계좌처럼 승인이 비동기로 완료되는 결제 수단은 상태 설계가 어떻게 달라지나요?"

출제 의도: "결제 = 즉시 승인"이라는 카드 중심 모델이 깨지는 지점이다. 입금 대기 · 기한 만료 · 금액 불일치 입금이라는 새로운 상태들을 기존 상태 머신에 수용할 수 있는지 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "결제 요청이 성공했으니 결제된 것"이라는 카드식 반사 → 1~3절에서 발급 응답은 돈에 관한 어떤 사실도 확정하지 않는다는 것을 시간축으로 보이고, WAITING_DEPOSIT을 정상 상태로 세운다.
② "웹훅 받아서 상태 바꾸면 끝"이라는 순진한 핸들러 → 4~5절에서 웹훅의 중복·위조·유실이라는 성질을 먼저 세우고, 그 성질 하나하나에 대응하는 네 관문으로 핸들러를 다시 짠다.
③ "처리 못 하는 건은 로그 남기고 넘어가면 됨" → 6·9·10절에서 "0건 갱신"을 조용히 삼킨 코드가 158,000원을 3주간 미아로 만든 사례를 붙이고, 예외의 수렴점을 설계 범위 안으로 끌어온다.

1. 무엇이 다른가 — 동기 승인과 비동기 승인

카드 결제의 시간 구조는 짧다. 우리 서버가 PG사(결제대행사)의 승인 API를 부르면 수 초 안에 카드사까지 다녀온 확정 결과가 HTTP 응답으로 돌아온다. 이걸 동기(synchronous) 라고 부른다 — 요청을 보낸 쪽이 결과가 나올 때까지 기다렸다가 같은 자리에서 결과를 받는 방식이다. 우리 코드로 보면 pgClient.approve(...)라는 메서드 호출 한 줄이 리턴될 때 결과가 손에 들어와 있다.

그래서 카드 결제에서 IN_PROGRESS의 수명은 몇 초다. 타임아웃 때문에 생기는 UNKNOWN은 어디까지나 예외 상황이지 정상 흐름이 아니다. 가상계좌는 여기가 통째로 다르다.

1-1. 가상계좌가 정확히 무엇인지부터

가상계좌(virtual account) 는 주문 1건을 위해 임시로 발급되는 1회용 입금 전용 계좌다. "가상"이라 부르는 이유는 실제 은행 계좌를 새로 개설하는 게 아니라, PG사가 가진 모계좌 아래에 주문마다 구분용 번호를 하나씩 찍어주는 구조이기 때문이다. 그 번호로 돈이 들어오면 PG는 "아, 이건 4211번 주문 건이구나"를 알 수 있다.

카드와 가상계좌 — 나란히 놓으면 차이가 선명해진다
카드가상계좌
승인을 결정하는 주체카드사 (우리 요청에 응답)고객의 손가락과 은행
완료 신호가 오는 방향우리가 보낸 요청의 응답저쪽에서 먼저 걸어오는 웹훅
"진행 중" 상태의 수명몇 초몇 시간 ~ 며칠
가장 흔한 종결 상태APPROVEDEXPIRED (입금 없이 만료)
돈이 안 들어올 수 있나거절되면 애초에 아무 일 없음고객이 그냥 안 보낼 수 있음
"취소"의 실체승인 자체를 없앰 (즉시)고객 계좌로 돈을 다시 보내는 이체 (며칠)

1-2. 비유 — 카운터 결제와 시장 도매상의 무통장 거래

카드 = 카운터 현장 결제

  • 카드를 긁고 그 자리에서 영수증을 받는다
  • 손님이 돌아설 때 이미 거래가 끝나 있다
  • "결제했나요?"라는 질문 자체가 성립하지 않는다

가상계좌 = 무통장 거래 주문서

  • "이 계좌로 보내주세요" 하고 주문서만 받아둔 상태
  • 사장님은 입금 문자가 올 때까지 물건을 부치지 않는다
  • 사흘 안에 입금이 없으면 주문서를 폐기한다
  • 입금 문자(웹훅)가 유일한 출고 신호다

카드 모델 그대로 가상계좌를 끼워 넣은 시스템이 저지르는 착각

"주문서 접수"를 "판매 완료"로 착각하는 순간 돈 없이 물건이 나간다

발급 응답이 성공했다고 상태를 APPROVED로 기록해서, 89,000원이 들어오지도 않았는데 주문을 완료 처리하는 것이다. 5절 before 코드가 정확히 이 코드다.

계좌이체(고객이 인증 후 이체하면 완료 통보가 오는 구조)와 후불 결제(한도 심사 후 확정 통보)도 정도만 다를 뿐 같은 비동기 구조다. 이 문서의 가상계좌 설계가 그대로 적용된다.

2. 무엇이 뒤집히는가 — 완료 신호의 방향

위 표에서 두 번째 줄이 설계를 가장 크게 바꾼다.

카드 — 우리는 결과를 기다리는 쪽

  • try { 결과 = 호출(); } catch { … } 구조에 모든 게 들어간다
  • 성공도 실패도 그 메서드 호출 한 줄의 결과다
  • 같은 스레드, 같은 요청, 같은 서버 인스턴스

가상계좌 — 우리는 창구를 열어두는 쪽

  • 결제 요청 API는 계좌번호만 받고 리턴한다
  • 진짜 결과는 완전히 다른 스레드, 다른 요청, 어쩌면 다른 서버 인스턴스에서 처리된다
  • 우리 코드는 결과를 받는 게 아니라 받을 창구(웹훅 엔드포인트)를 열어두고 기다린다

웹훅(webhook) 이 바로 그 창구다. 우리가 상대를 호출하는 게 아니라 상대가 우리 서버의 특정 URL로 먼저 HTTP 요청을 보내오는 방식이다. "결과 나오면 여기로 알려주세요" 하고 연락처를 남겨두는 것과 같다.

이 방향 전환에서 파생되는 문제 네 가지 — 이 문서의 나머지 전부다

공개 URL이다
누구나 요청을 보낼 수 있다 → 서명 검증이 필요하다 (4절)
응답 못 받으면 다시 보낸다
→ 중복 처리를 막아야 한다 (5절 조건부 UPDATE)
요청이 유실될 수 있다
→ 웹훅에만 의존하면 안 된다 (9절 사례 1, pull 대사 배치)
그동안 우리 배치는 계속 돈다
→ 같은 행을 두고 경합이 생긴다 (6절 레이스)

3. 상태 머신에 두 칸이 늘어난다 — WAITING_DEPOSIT · EXPIRED

새로 추가되는 상태 — "정상인가" 열이 가장 중요하다
상태뜻체류 시간정상인가이 상태를 만드는 주체
WAITING_DEPOSIT계좌 발급 완료, 입금 기다리는 중시간 ~ 일정상가상계좌 발급 API
EXPIRED기한까지 입금 없음 (종결)종결정상 — 가장 흔한 종결기한 만료 배치
APPROVED입금 확인 완료—정상입금 통보 웹훅 / 조회 대사 배치
REFUNDED이체로 돈을 돌려줌—정상환불 이체 (며칠 소요)

3-1. "정상 상태"라는 말이 왜 중요한가

WAITING_DEPOSIT은 카드의 IN_PROGRESS가 초 단위인 것과 달리 시간~일 단위로 체류하는 정상 상태다. 이 "정상"이라는 말이 코드 전체로 번진다.

지표가 망가진다
"결제 성공률"을 낼 때 입금 대기 건을 실패로 세면 지표가 통째로 왜곡된다. 아직 실패한 게 아니라 결과가 안 나온 것이다.
알림이 폭발한다
"10분 넘게 진행 중인 결제"를 장애 조건으로 잡으면 가상계좌 건이 전부 알림을 울린다. 정상 건이 경보를 울리기 시작하면 사람은 곧 경보를 무시하게 된다.
화면 문구가 거짓말한다
발급 직후 화면에 "결제 완료"가 뜨면 고객은 입금하지 않는다. 문구는 반드시 "입금 대기"여야 한다.

세 문장으로 압축

WAITING_DEPOSIT은 기다리는 게 정상이고, EXPIRED는 가장 흔한 결말이며, APPROVED는 웹훅이 만든다

가상계좌 주문의 상당수는 입금 없이 그냥 만료된다 — 고객이 마음을 바꾸거나, 잊어버리거나, 다른 수단으로 다시 결제하기 때문이다. EXPIRED를 "실패"로 분류하는 순간 대시보드가 새빨개진다.

4. 웹훅의 세 가지 성질 — 이걸 전제로 설계해야 한다

웹훅 핸들러를 짜기 전에, 웹훅이 어떤 물건인지부터 정확히 알아야 한다. 세 가지 성질이 있고 셋 다 설계에 직접 영향을 준다. 그리고 성질이라 부르기는 애매하지만 반드시 함께 다뤄야 할 네 번째 사실이 하나 더 있다.

1
중복 도착한다. PG는 웹훅을 보내고 우리 서버가 200을 돌려주면 "전달 성공"으로 간주한다. 200을 못 받으면 재발송한다. 그런데 200을 못 받는 이유가 "우리가 처리를 못 해서"만은 아니다 — 우리는 정상 처리하고 200을 보냈는데 그 응답이 네트워크에서 유실될 수도 있다. 그러면 PG 입장에서는 실패로 보이고, 우리는 이미 처리한 통보를 또 받는다.
at-least-once 전달 (최소 한 번은 전달) "정확히 한 번"은 분산 시스템에서 사실상 불가능하기 때문에, 보내는 쪽은 "최소 한 번"만 보장하고 중복 제거는 받는 쪽 책임으로 넘긴다. 즉 "중복이 온다"는 건 PG의 버그가 아니라 계약 조건이다.
2
위조될 수 있다. 웹훅 엔드포인트는 인터넷에 열린 공개 URL이다. 주소만 알면 누구나 "10만원 입금됐어요"라는 JSON을 POST할 수 있다. 그래서 서명 검증이 필수다.

서명 검증은 이렇게 동작한다 — PG와 우리만 아는 비밀키가 있고, PG는 보낼 본문에 그 키를 섞어 해시(HMAC)를 계산해 헤더에 담아 보낸다. 우리도 받은 본문에 같은 키로 같은 해시를 계산해 헤더 값과 비교한다. 일치하면 "비밀키를 아는 쪽이 보냈고, 본문이 중간에 변조되지 않았다"가 증명된다.

3
유실·지연될 수 있다. PG 장애, 우리 서버 배포 중 다운, 은행 점검 시간대의 지연 등으로 웹훅이 아예 안 오거나 몇 시간 뒤에 올 수 있다. 그래서 웹훅을 유일한 경로로 삼으면 안 된다 — 9절 사례 1의 주제다.

5-3. after — 네 개의 관문

after 서명 → 조회 재확인 → 금액 → 조건부 UPDATE
@PostMapping("/webhooks/deposit")
public ResponseEntity<Void> onDeposit(@RequestHeader("X-Signature") String sig,
                                      @RequestBody DepositNotification n) {

    // ① 서명 검증 — 이 요청이 정말 PG에서 왔는지 확인한다.
    //    공개 URL이므로 이 줄이 없으면 누구나 가짜 입금을 통보할 수 있다.
    webhookVerifier.verify(sig, n);

    // ② 통보 내용을 믿지 말고 PG 조회 API로 재확인한다.
    //    서명이 맞아도 키 유출이나 구현 실수의 여지는 남으므로,
    //    "얼마가 들어왔나" 같은 돈의 사실은 우리가 PG에 직접 물어서 확정한다.
    PgTransaction tx = pgClient.getTransaction(n.pgTxId());

    // ③ 금액 검증 — 주문 금액과 입금액이 다르면 승인하지 않는다. (7절)
    Payment p = paymentRepository.findByPgTxId(n.pgTxId());
    if (tx.amount().compareTo(p.getAmount()) != 0) {
        depositExceptionService.register(p, tx);   // 예외 큐 → 전액 자동 환불
        // 200을 준다. 우리가 접수해서 예외 처리로 보냈으므로,
        // PG가 같은 통보를 계속 재발송하게 둘 이유가 없다.
        return ResponseEntity.ok().build();
    }

    // ④ 조건부 UPDATE — 중복 웹훅과 만료 배치와의 경합을 한 번에 처리한다.
    //    "지금도 여전히 WAITING_DEPOSIT일 때만" APPROVED로 바꾼다.
    int updated = jdbc.update("""
        UPDATE payment SET status = 'APPROVED', approved_at = now()
         WHERE id = ? AND status = 'WAITING_DEPOSIT'
        """, p.getId());

    if (updated == 1) {
        // 갱신에 성공한 요청은 이 세상에 하나뿐이다.
        // 그러므로 이용권 지급도 정확히 한 번만 실행된다.
        // (지급 로직 자체도 결제 ID 유니크 제약으로 멱등하게 두면 이중 방어)
        benefitService.grant(p);
    } else if (reloadStatus(p.getId()) == EXPIRED) {
        // 만료 배치가 먼저 이겼다 = 기한 후 입금.
        // 돈은 이미 들어와 있으므로 버리면 안 되고 환불 파이프라인으로 보낸다. (6절)
        depositExceptionService.registerLateDeposit(p, tx);
    }
    // 그 외의 0건은 이미 APPROVED인 중복 웹훅이다. 조용히 200으로 끝낸다.
    return ResponseEntity.ok().build();
}

5-4. ④의 조건부 UPDATE가 이 설계의 심장이다

이 시점에 이 웹훅 요청이 처한 상황은 세 가지 중 하나다 — (a) 정상적인 첫 통보, (b) 이미 처리한 건의 중복 통보, (c) 만료 배치에 진 기한 후 입금. 그런데 애플리케이션 코드가 이 셋을 미리 구분할 방법은 없다. 지금 상태를 SELECT로 읽어본다 해도, 읽은 다음 UPDATE하기까지의 사이에 상태가 또 바뀔 수 있기 때문이다.

6. 기한 만료 배치 — 그리고 웹훅과의 레이스

만료 배치는 주기적으로(예: 5분) 기한 지난 입금 대기 건을 정리한다. 여기도 조건부 UPDATE다.

UPDATE payment
   SET status = 'EXPIRED'
 WHERE status = 'WAITING_DEPOSIT'
   AND deposit_deadline < now();
-- 만료 시각 직전에 웹훅이 먼저 APPROVED로 바꿔놨다면
-- status 조건에 안 걸려서 이 행을 건드리지 못한다.

6-1. 레이스 컨디션이 무엇인가

레이스 컨디션(race condition) 은 두 개 이상의 작업이 같은 자원을 두고 경쟁할 때, 어느 쪽이 먼저 도착하느냐에 따라 결과가 달라지는 상황이다. 경주(race)에 비유한 이름이다. 여기서 경쟁자는 만료 배치와 입금 웹훅이고, 자원은 결제 행 하나다. 그리고 이 경주에는 한쪽만 이겨야 한다 — 둘 다 성공하면 "만료된 승인 건"이라는 말이 안 되는 상태가 만들어진다.

기한 후 입금은 "혹시 생길 수도 있는 일"이 아니라 반드시 발생한다 고객이 23:59:59에 이체를 눌러도 은행 → PG → 우리로 통보가 오는 데 몇 분이 걸릴 수 있다. 두 시스템의 시계와 처리 순서를 우리가 맞출 방법이 없으므로, 이 케이스는 확률 문제가 아니라 시간 문제다.

6-2. 사후 처리보다 먼저 — 창 자체를 줄인다

EXPIRED 상태에 대한 입금은 예외 큐에 적재하고 자동 환불(계좌 이체 반환) 흐름으로 보낸다. 예외 큐란 정상 흐름으로 처리할 수 없는 건을 버리지 않고 모아두는 별도 테이블 또는 메시지 큐다. 핵심은 "처리 못 하는 건을 로그만 남기고 버리지 않는다"는 것이다.

그런데 사후 처리도 필요하지만, 애초에 이 창이 열리는 시간을 줄이는 게 더 낫다. PG에 따라 만료 시점에 가상계좌 자체를 닫아주는 옵션(계좌 만료 처리)이 있다. 계좌가 닫히면 그 뒤의 입금 시도는 은행 단에서 거절되므로, 애초에 우리 쪽으로 돈이 들어오지 않는다.

여기서 원칙 하나 — 7절에서도 똑같이 반복된다

예외 처리를 코드로 감당하기 전에, 예외가 발생할 수 있는 창 자체를 줄일 방법이 있는지 먼저 본다

7. 금액 불일치 입금 · 부분 입금 — 승인하지 말고 예외 큐로

고객이 49,000원 주문의 가상계좌에 40,000원을 보내거나 94,000원을 보내는 일이 실제로 일어난다. 이유는 단순하다 — 일부 은행 앱은 이체 화면에서 금액을 직접 입력하게 되어 있어서, 고객이 숫자를 잘못 치면 그대로 나간다.

주문 금액과 정확히 일치하지 않는 입금은 절대 APPROVED로 만들지 않는다

왜 그런지는 대안을 하나씩 검토해보면 알 수 있다.

대안 A — 부족해도 승인한다?

  • 40,000원 입금에 49,000원짜리 이용권 지급
  • 회사가 9,000원 손해를 본다
  • 이게 알려지면 악용된다
  • 명백히 안 된다

대안 B — "9,000원만 더 보내세요"라고 안내하고 합산한다?

  • 그럴듯해 보이지만 "부분 입금됨(누적 40,000 / 49,000)"이라는 상태가 필요해진다
  • 그리고 이 상태 하나가 시스템 전체로 번진다 (아래 표)
대안 B가 번지는 범위 — 상태 하나를 추가하면 네 군데가 같이 복잡해진다
영역새로 필요해지는 것
상태입금 횟수와 누적 금액을 추적해야 하고, 만료 시점의 처리 규칙이 새로 필요하다
대사PG 거래 내역과 맞출 때 1:1이 아니라 N:1 매칭이 된다
환불만료됐을 때 여러 건의 입금을 각각 되돌려야 한다
초과 입금94,000원이 들어오면 45,000원을 부분 환불해야 하는데, 이건 또 다른 흐름이다
채택 — 예외 큐 + 전액 자동 환불 이 복잡도 때문에 대부분의 커머스는 부분 입금 합산을 지원하지 않는다. 불일치 입금은 예외 큐에 적재해서 들어온 금액 전액을 자동으로 되돌려주고, 주문은 입금 대기를 유지하거나(고객이 정확한 금액으로 다시 보낼 수 있게) 만료시킨다.

예방책이 더 중요하다 — 6-2와 같은 발상

고정금액 가상계좌 옵션
지정한 금액과 다른 입금은 은행 단에서 거절된다. 고객은 이체 화면에서 애초에 다른 금액을 넣을 수 없거나, 넣어도 실패한다.
만료 시 계좌 닫기 옵션 (6-2)
기한이 지나면 계좌 자체를 닫아 기한 후 입금이 애초에 우리 쪽으로 오지 않게 한다.
예외 케이스를 코드가 아니라 입구에서 제거한다 — 처리해야 할 예외의 종류를 줄이는 게 예외 처리를 잘 짜는 것보다 낫다

8. 재고·주문 선점 — 입금 대기 동안 재고를 잡아둘 것인가

가상계좌는 결제 도메인 밖으로도 파문을 만든다. 카드 결제에서는 "결제 성공 = 즉시"이므로 재고 처리에 고민할 게 없었는데, 입금 대기가 48시간이면 그동안 재고를 어떻게 할지 결정해야 한다. 선택지는 둘뿐이고 둘 다 부작용이 있다.

선택지 A — 선점한다

발급 시점에 재고를 잡아둔다

  • 입금 없이 만료되는 다수의 주문이 그동안 재고를 잠근다
  • 한정 수량 상품이면 "품절인데 아무도 안 산" 상태가 되고, 진짜 살 고객이 못 산다
  • 악의적으로 가상계좌 주문을 대량 생성해 상품을 품절시키는 공격도 가능하다

선택지 B — 선점하지 않는다

입금이 확인될 때 재고를 잡는다

  • 고객이 이틀 뒤 입금했는데 그새 품절인 경우가 생긴다
  • 돈은 받았는데 물건이 없으니 자동 환불해야 한다
  • 고객은 "돈 보냈는데 왜 취소냐"고 화를 낸다 — CS 부담이 크다

정답은 도메인 정책이지 기술이 아니다. 다만 실무에서 자주 쓰는 기본 조합은 있다.

1
재고는 선점하되 입금 기한을 짧게 잡는다(48시간이 아니라 24시간). 재고가 잠기는 시간을 절반으로 줄인다.
2
만료 배치가 EXPIRED 전이와 함께 재고를 해제한다. 이때 재고 해제와 상태 전이가 항상 같이 일어나도록 같은 트랜잭션에 넣거나, 상태 전이 후 발행되는 이벤트로 묶는다. 둘이 따로 놀면 "만료됐는데 재고는 계속 잠긴" 건이 조용히 쌓인다.
3
한정판·타임세일 상품은 가상계좌 결제 수단 자체를 막는다. 재고 경쟁이 치열한 상품에서는 어느 선택지를 골라도 사고가 나므로, 애초에 비동기 수단을 허용하지 않는 게 낫다.

3번이 특히 실무적인 답이다

모든 상품에 같은 결제 수단을 열어줘야 할 이유가 없다

"기술로 해결할 수 없는 트레이드오프는 범위를 좁혀서 회피한다"는 판단이고, 이건 6-2·7절의 "창을 줄인다"와 같은 사고방식이다.

9. 실무 사례 — 비동기 승인이 뚫리는 구멍들

9-1. 사례 1 — 웹훅 유실: 입금했는데 3일째 "입금 대기" 함정

은행 점검 시간대에 걸친 입금 건들의 통보가 PG에서 지연·유실됐다. 고객은 137,000원을 입금했는데 주문은 WAITING_DEPOSIT에 머물렀다. 그리고 이틀 뒤 만료 배치가 정상적으로 동작해서 그 건을 EXPIRED로 넘기고 재고까지 풀어버렸다. 돈은 PG에 있고 주문은 만료된 최악의 CS다.

여기서 중요한 건 우리 코드에 버그가 없었다는 점이다 웹훅 핸들러도 만료 배치도 설계대로 정확히 동작했다. 문제는 설계가 웹훅 하나에만 의존했다는 것이다. "코드가 맞게 동작했는데도 사고가 났다"면 고쳐야 할 것은 코드가 아니라 구조다.

9-2. 사례 2 — 중복 웹훅으로 이용권 이중 지급 함정

이 시스템은 이용권 지급 로직이 무거워서 웹훅 핸들러의 처리 시간이 PG의 응답 타임아웃을 넘겼다. PG는 응답을 못 받았으니 실패로 간주해 같은 입금 통보를 세 번 보냈다. 상태 전이 검증이 없던 핸들러는 세 번 모두 지급을 실행했고, 59,000원 결제에 이용권 3개가 나갔다.

주목할 점 — 이건 "네트워크가 이상해서" 생긴 사고가 아니다 우리 핸들러가 느린 것 자체가 원인이었다. 느린 핸들러는 재발송을 유발하고, 재발송은 다시 느린 핸들러를 여러 개 띄운다. 부하가 커질수록 중복도 늘어나는 자기 증폭 구조다.
교훈 ① 조건부 UPDATE
최초 1회만 후속 처리를 실행한다. 5-3의 ④가 이것이다. 몇 번 오든 갱신에 성공하는 건 한 번뿐이다.
교훈 ② 무거운 작업은 응답과 분리
상태 전이만 동기로 처리하고 200을 빠르게 돌려준 뒤, 지급·알림은 비동기(메시지 큐, 이벤트 발행)로 넘긴다.
교훈 ③ 지급 로직도 멱등하게
지급 테이블에 결제 ID 유니크 제약을 걸면, 어떤 경로로 두 번 호출돼도 두 번째는 DB가 막는다.

두 문장으로 압축 — 하나는 목표, 하나는 사고방식

웹훅 핸들러의 목표는 빠른 접수이지 완전한 처리가 아니다

심층 방어(defense in depth) — 방어선 하나에 모든 걸 걸지 않고, 하나가 뚫려도 다음이 막도록 층을 쌓는 사고방식이다. 교훈 ③이 그것이다. 결제 시스템에서는 방어선 하나가 반드시 언젠가 뚫린다고 가정하는 편이 안전하다.

① 서명 검증→ ② 조회 재확인→ ③ 금액 검증→ ④ 조건부 UPDATE→ ⑤ 지급 테이블 유니크 제약

9-3. 사례 3 — 만료 5분 뒤 입금: 돈은 왔는데 주문이 없다 함정

23:58에 만료 배치가 158,000원 주문을 EXPIRED로 정리하고 재고를 해제했는데, 00:03에 입금 웹훅이 도착했다. 6절에서 본 "방향 2" 레이스가 실제로 일어난 것이다.

조건부 UPDATE는 있어서 이중 승인은 없었다. 그런데 0건일 때의 처리가 없었다. 핸들러는 "상태 전이 실패"라는 로그 한 줄만 남기고 요청을 버렸다.

before 0건을 조용히 삼킨다
int updated = jdbc.update("UPDATE … WHERE status='WAITING_DEPOSIT'", id);
if (updated == 0) {
    log.warn("상태 전이 실패: paymentId={}", id);   // 그리고 끝
    return ResponseEntity.ok().build();
}
// 이 warn 로그는 아무도 보지 않았다.
// 158,000원은 PG의 미매칭 잔액으로 3주간 방치되다가
// 월말 대사에서야 발견됐다. 고객은 그동안 아무 연락도 못 받았다.
after 0건의 이유를 갈라서 처리한다
int updated = jdbc.update("UPDATE … WHERE status='WAITING_DEPOSIT'", id);
if (updated == 0) {
    PaymentStatus now = reloadStatus(id);
    if (now == EXPIRED || now == CANCELED) {
        // 돈은 이미 들어와 있다. 버리면 미아가 된다.
        depositExceptionService.registerLateDeposit(p, tx);
    }
    // now == APPROVED 면 중복 웹훅. 이때만 조용히 넘어간다.
}
// "0건"은 하나의 사건이 아니라 서로 다른 두 사건이다.

세 사례를 관통하는 한 문장

"0건 갱신"을 조용히 삼키는 코드가 사고의 씨앗이다

갱신 행 수가 0이라는 건 "내가 예상한 세상과 실제 세상이 다르다"는 신호이고, 그 신호를 버리면 그 차이는 며칠 뒤 돈 문제로 돌아온다. 이건 01-payment-state-management에서도 같은 자리에서 터졌던 문제다.

여기까지 나온 카드에는 없던 예외들을 모아보면, 겉모습은 다르지만 결말이 전부 같다.

만료 배치가 이겨서 EXPIRED가 된 뒤 입금이 도착

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 답을 먼저 떠올리고 오른쪽을 본다

가상계좌 발급 응답이 확정하는 사실은?
아무것도 없다. "입금받을 준비가 됐다"뿐이다. 돈에 관한 사실은 0.
새로 추가되는 상태 2종은?
WAITING_DEPOSIT(시간~일 체류하는 정상 상태) · EXPIRED(가장 흔한 종결). 둘 다 예외가 아니다.
웹훅 4대 전제는?
중 · 위 · 유 + 경 — 중복 도착 / 위조 가능 / 유실·지연 / 만료 배치와 경합.
before 코드의 사고 원인 4종은?
발 · 서 · 금 · 상 — 발급을 승인으로 / 서명 검증 없음 / 금액 검증 없음 / 상태 전이 검증 없음.
웹훅 핸들러 네 관문 순서는?
① 서명 검증 → ② PG 조회 API 재확인 → ③ 금액 검증 → ④ 조건부 UPDATE.
조건부 UPDATE 3분기는?
1건 = 첫 통보(여기서만 지급) / 0건 & APPROVED = 중복(200) / 0건 & EXPIRED = 기한 후 입금(환불).
신뢰의 근거 한 줄은?
"누가 뭘 보냈는지"가 아니라 "우리가 누구에게 물어봤는지"를 신뢰의 근거로 삼는다.
"돈은 왔는데 주문이 없다" 3형제는?
기한 후 입금 · 금액 불일치 입금 · 취소 후 입금 → 전부 예외 큐 → 전액 자동 환불로 수렴.
레이스 해법 한 줄은?
레이스를 없애는 게 아니라 어느 승자든 안전한 결과가 되게 설계한다.
예외의 창을 줄이는 두 옵션은?
만료 시 계좌 닫기 · 고정금액 가상계좌. 둘 다 은행 단에서 거절시켜 애초에 돈이 안 들어오게 한다.
WAITING_DEPOSIT vs UNKNOWN?
전자는 결과가 아직 안 정해짐(정상), 후자는 이미 정해졌는데 우리가 모름(비정상).
웹훅 핸들러의 목표는?
빠른 접수이지 완전한 처리가 아니다. 무거운 후속 작업은 200 반환 뒤 비동기로.

11-2. 꼬리질문 — 먼저 답해보고 펼친다

만료 배치와 입금 웹훅이 같은 순간에 실행되면요? 시니어 변별힌트: "누가 이기게 만들까"를 고민하기 시작하면 이미 틀린 방향이다

양쪽 모두 WHERE status = 'WAITING_DEPOSIT' 조건부 UPDATE이므로, DB의 행 락 위에서 직렬화되어 정확히 한쪽만 성공한다.

"직렬화된다"는 말을 풀면 이렇다. PostgreSQL은 한 행을 UPDATE할 때 그 행에 락을 건다. 두 트랜잭션이 같은 행을 UPDATE하려 하면 나중에 온 쪽이 앞의 트랜잭션이 끝날 때까지 대기한다. 그리고 대기가 풀린 뒤 다시 조건을 확인한다. 그래서 앞 트랜잭션이 상태를 바꿔놨다면 뒤 트랜잭션의 WHERE 조건은 이제 맞지 않게 되어 0건이 된다.

승자패자에게 일어나는 일최종 결과
웹훅배치의 UPDATE가 0건정상 승인. 배치는 그냥 넘어감
배치웹훅의 UPDATE가 0건기한 후 입금 예외 경로 → 자동 환불
레이스를 없애는 게 아니라, 어느 승자든 안전한 결과가 되게 설계한다
주니어의 흔한 답변이 왜 안 되는가 "배치 실행 전에 상태를 한 번 더 확인한다"거나 "웹훅 처리 중에는 배치가 못 돌게 플래그를 둔다"처럼 애플리케이션 레벨 if문으로 순서를 조율하려는 방향인데, 이건 확인과 실행 사이의 틈을 없애지 못해서 결국 같은 문제가 남는다. 순서를 통제하려 들지 말고, 순서가 어떻게 되든 결과가 안전하도록 만드는 쪽이 맞다.
웹훅 내용을 왜 그대로 믿지 않고 조회 API로 재확인하나요? 필수힌트: 서명 검증은 1차 방어일 뿐이다. 신뢰의 "방향"을 생각해본다

웹훅 엔드포인트는 공개 URL이라 위조 요청이 가능하다. 서명 검증이 1차 방어인데, 서명이 있어도 완전하지 않다 — 비밀키가 유출될 수 있고, 검증 구현에 실수가 있을 수 있다(예: 서명 비교를 문자열 equals로 해서 타이밍 공격에 노출되거나, 특정 경로에서 검증을 건너뛰거나).

그래서 통보는 "입금이 있었을 수 있다"는 트리거로만 쓴다. 금액·상태 같은 돈에 관한 사실은 우리가 PG에 직접 발신하는 조회 API의 응답으로 확정한다.

핵심은 신뢰의 방향을 뒤집는 것이다
수신 (웹훅 본문)발신 (조회 API 응답)
누가 보냈나인터넷의 누군가 (서명으로 추정만 가능)우리가 PG 도메인으로 직접 물어봄
신뢰 근거서명이 맞더라. 아마도 PG겠지TLS로 PG 서버와 직접 연결해 받은 답
결론트리거로만 사용사실로 채택
"누가 뭘 보냈는지"가 아니라 "우리가 누구에게 물어봤는지"를 신뢰의 근거로 삼는다
일상의 비유로 한 번 더 입금 문자 알림은 스팸일 수도 있고 안 올 수도 있다. 그런데 내가 은행 앱을 열어 통장을 확인한 잔액은 내가 직접 확인한 사실이다. 문자는 "통장을 확인해봐야겠다"는 트리거로만 쓰고, 금액은 통장에서 읽는다. 주요 PG들이 공식 가이드에서 권장하는 패턴이기도 하다.
입금 대기 중 고객이 주문을 취소하면 어떻게 되나요? 시니어 변별힌트: 우리 DB 상태만 바꾸면 무엇이 남아 있는가? 그리고 그걸 닫는 API도 실패할 수 있다

WAITING_DEPOSIT → CANCELED 전이를 상태 머신에 추가한다. 여기까지는 쉽다.

핵심은 PG 쪽 가상계좌를 함께 만료(입금 불가) 처리하는 것이다. 우리 DB의 상태만 바꾸고 계좌를 열어둔 채로 두면, 고객이(또는 고객의 자동이체가) 그 계좌로 돈을 보낼 수 있다. 그러면 "취소된 주문에 입금"이라는, 6절의 기한 후 입금과 완전히 동일한 예외가 생긴다.

우리 상태와 PG 쪽 계좌 상태가 같이 움직여야 한다 — 한쪽만 닫으면 그 틈이 곧 사고다

그런데 여기서 한 걸음 더 나가야 시니어의 답이 된다. 계좌 만료 처리 자체가 실패하거나 타임아웃될 수 있다. PG API도 외부 호출이라 언제든 실패한다. 재시도를 걸어도 결국 안 되는 건이 생긴다.

예방 — 계좌 닫기

  • 취소 전이와 함께 PG 가상계좌 만료 API 호출
  • 실패하면 재시도 큐에 넣는다
  • 성공하면 이후 입금은 은행 단에서 거절

수습 — 예외 파이프라인

  • 그래도 도착하는 입금 통보는 자동 환불 경로로 수렴
  • 10절의 파이프라인을 그대로 재사용한다
  • 새 흐름을 만들 필요가 없다

예방과 수습을 둘 다 갖추는 것이지, 예방이 되니까 수습을 빼는 게 아니다. 이게 사례 2에서 말한 심층 방어의 또 다른 적용이다.

WAITING_DEPOSIT과 카드의 UNKNOWN은 뭐가 다른가요?힌트: 둘 다 "확정 전"이지만 성격이 정반대다. 운영 관점에서 가장 큰 차이는?

둘 다 "확정 전"이라는 점은 같지만 성격이 정반대다.

UNKNOWN (카드)WAITING_DEPOSIT (가상계좌)
결과가 정해졌나이미 정해졌다. 우리가 모를 뿐아직 안 정해졌다
정상인가비정상 (사고의 흔적)정상 (설계된 흐름)
적정 체류 시간수 분수 시간 ~ 수 일
쌓이면알림을 울려야 한다아무 문제 없다
담당 처리기분 단위 해소 배치 (PG 거래 조회)기한 만료 배치 + 입금 대사 배치
해소 수단조회로 확정, 안 되면 망취소웹훅 또는 조회로 입금 확인
같은 "중간 상태"라도 SLA와 처리기가 완전히 다르다

구체적으로: UNKNOWN이 10분 넘게 남아 있으면 담당자를 깨워야 하지만, WAITING_DEPOSIT이 30시간째 남아 있는 건 지극히 정상이다. 이 둘을 같은 "미확정 결제" 대시보드에 섞어놓으면 알림이 무의미해진다 — 정상 건이 경보를 계속 울리면 사람은 곧 경보를 무시하게 되고, 그때 진짜 UNKNOWN이 묻힌다.

카드/가상계좌 상태 머신을 하나의 enum으로 관리하나요, 분리하나요? 시니어 변별힌트: 양 극단을 먼저 검토하면 절충안의 근거가 생긴다. 그리고 "쪼개는 축"은 무엇인가?

먼저 양 극단을 보자.

완전 통합 — 하나의 enum + 하나의 전이 규칙

  • 의미 없는 조합을 걸러낼 수 없다
  • 카드 결제가 WAITING_DEPOSIT으로 전이하는 건 명백한 버그인데, 전이 규칙이 하나로 합쳐져 있으면 정상 전이로 통과한다
  • 컴파일 단계에서도 검증 단계에서도 못 잡고, 운영에서 이상한 데이터로 발견된다

완전 분리 — 수단마다 상태 enum을 따로

  • 공통 처리가 전부 중복된다
  • 취소·환불·대사·이력 기록은 수단과 무관하게 같은 로직인데, 타입이 다르면 코드를 수단 수만큼 복사하게 된다
공통 골격(READY, APPROVED, 취소·환불 계열, UNKNOWN)은 공유하되,
수단별 고유 상태를 포함한 허용 전이 테이블을 결제수단별로 분리한다
// 상태 값 자체는 하나의 enum으로 공유하고,
// "어떤 전이가 허용되는가"만 수단별로 다르게 둔다.
public interface PaymentStateMachine {
    boolean canTransition(PaymentStatus from, PaymentStatus to);
}

// 카드: WAITING_DEPOSIT으로 가는 전이 자체가 정의돼 있지 않다.
class CardStateMachine implements PaymentStateMachine { /* … */ }

// 가상계좌: IN_PROGRESS 대신 WAITING_DEPOSIT을 쓴다.
class VirtualAccountStateMachine implements PaymentStateMachine { /* … */ }
얻는 것 ①
카드 결제 경로에서 실수로 WAITING_DEPOSIT 전이를 시도해도 즉시 예외로 막힌다.
얻는 것 ②
수단이 더 늘면(에스크로, 후불, 해외 결제) 구현체를 하나 추가하는 것으로 끝난다.

이건 01-payment-state-management에서 말한 "상태 폭발은 상태 머신을 쪼개라는 신호" 의 실전 적용이다. 상태가 늘어난다고 enum에 값을 계속 더하는 게 아니라, 상태의 성격이 갈리는 축(여기서는 결제 수단)을 찾아서 그 축으로 쪼갠다.

웹훅 핸들러에서 200이 아니라 4xx·5xx를 돌려줘야 하는 경우는 언제인가요? 가산점힌트: 판단 기준은 딱 하나 — "다시 보내주면 결과가 달라질 수 있는가"

응답 코드는 PG에게 "재발송해줘 / 하지 마"를 지시하는 신호다. 그러니 기준도 하나뿐이다 — "다시 보내주면 결과가 달라질 수 있는가."

상황응답이유
정상 처리 완료200더 보낼 이유가 없다
중복 웹훅 (이미 APPROVED)200다시 보내도 결과가 같다. 중복은 에러가 아니다
금액 불일치 · 기한 후 입금 → 예외 큐 적재200우리가 접수해서 처리 중이므로 재발송은 소음일 뿐
DB 장애 · 일시적 오류로 처리 못 함5xx다시 보내주면 성공할 수 있다. 웹훅의 at-least-once를 우리 재시도 장치로 활용
서명 검증 실패4xx재발송해도 결과가 같다. 게다가 공격일 수 있으니 모니터링·알림 대상
응답 코드는 결과 보고가 아니라 "재발송 지시"다 — 이 관점으로 보면 분기가 저절로 정해진다
흔한 실수 두 가지 ① 예외가 나면 무조건 5xx → 절대 성공할 수 없는 건(예: 우리 DB에 없는 주문번호)에 대해 PG가 며칠간 재발송을 반복한다.
② 무조건 200 → 우리 DB 장애로 놓친 통보를 PG가 다시 보내주지 않는다. 그 건은 pull 대사 배치가 회수할 때까지 방치된다.
웹훅과 조회 대사 배치가 같은 입금을 동시에 발견하면 어떻게 되나요?힌트: 이미 답이 코드 안에 있다. 어디인가?

이미 처리되고 있다. 두 경로 모두 같은 조건부 UPDATE 관문을 통과하므로(9-1 도식), 한쪽만 1건이고 다른 쪽은 0건 & 현재 APPROVED가 된다. 진 쪽은 중복 웹훅과 완전히 같은 취급을 받는다 — 아무것도 하지 않고 조용히 끝낸다. 이용권은 이긴 쪽에서 정확히 한 번 나간다.

경로를 늘려도 승자 판정 지점이 하나면 멱등성은 깨지지 않는다
여기서 놓치기 쉬운 것 — 대사 배치의 로그 레벨 대사 배치가 "이미 APPROVED"를 발견했을 때 이걸 에러로 올리면 안 된다. 웹훅이 먼저 처리한 건은 대사 배치 입장에서 가장 흔한 정상 케이스다. 이걸 error로 찍으면 정상 동작이 매 주기마다 알림을 울리게 되고, 결국 그 알림 채널 전체가 무시된다.
가상계좌의 "결제 성공률" 지표는 어떻게 정의해야 하나요? 가산점힌트: 카드의 승인 성공률과 같은 칸에 놓으면 안 되는 이유가 있다

카드의 승인 성공률은 "시스템이 잘 동작하는가"를 재는 기술 지표다. 그런데 가상계좌에 같은 정의를 쓰면 고객이 입금을 안 한 것까지 시스템 실패로 잡힌다. 그래서 두 지표로 쪼개야 한다.

발급 성공률 — 기술 지표
가상계좌 발급 API 호출 중 성공한 비율. 이게 떨어지면 장애다. 카드의 승인 성공률과 같은 성격이므로 같은 알림 임계치를 걸어도 된다.
입금 전환율 — 비즈니스 지표
WAITING_DEPOSIT → APPROVED 비율. 이게 떨어지는 건 장애가 아니라 고객 이탈이다. 담당자를 깨울 게 아니라 기한·안내 문구·리마인드 알림을 손봐야 한다.
EXPIRED를 실패로 세는 순간, 정상 동작하는 시스템의 대시보드가 새빨개진다

알림도 마찬가지로 갈라야 한다 — "10분 이상 진행 중인 결제" 같은 조건에 WAITING_DEPOSIT이 들어가면 안 된다. 3-1에서 본 "상태 하나를 추가한다는 건 그 상태를 아는 코드를 전부 고친다는 뜻"이 지표와 알림에도 그대로 적용된다.

입금 기한(48시간 등)은 무엇을 기준으로 정하나요?힌트: 양쪽 끝에 각각 무슨 비용이 붙는지 생각해본다

기술 상수가 아니라 트레이드오프의 결과다. 양쪽 끝에 각각 비용이 붙는다.

기한을 길게 (예: 72시간)

  • 입금 전환율이 올라간다 — 고객이 입금할 시간이 넉넉하다
  • 대신 재고 잠금 시간이 길어진다 (8절 선택지 A의 부작용이 커진다)
  • 미확정 주문이 오래 쌓여 운영·CS 문의도 늘어난다

기한을 짧게 (예: 12시간)

  • 재고 회전이 빨라진다
  • 대신 기한 후 입금 케이스가 늘어난다 (6절 예외 파이프라인 부하)
  • 고객 불만도 늘어난다 — "저녁에 주문했는데 아침에 만료됐다"

여기에 달력의 사정도 얹어야 한다. 금요일 저녁에 발급된 건에 짧은 기한을 걸면 주말 중에 만료되고, 은행 점검 시간대에 걸치면 통보가 지연된다(9-1 사례가 그렇게 터졌다).

기한은 상품 특성별로 다르게 잡는다 — 한정 수량 상품은 짧게, 재고 여유가 있는 상품은 길게

그리고 어떤 기한을 잡든 기한 후 입금은 반드시 발생한다. 기한 조절은 빈도를 줄이는 수단이지 케이스를 없애는 수단이 아니다 — 예외 파이프라인은 항상 살아 있어야 한다.

한 줄 요약
가상계좌는 "발급 성공"과 "입금 완료" 사이가 며칠씩 벌어지는 비동기 승인 모델이므로 WAITING_DEPOSIT·EXPIRED라는 새 상태를 상태 머신에 추가하고, 완료의 유일한 신호인 입금 웹훅을 서명 검증 + 조회 API 재확인 + 조건부 UPDATE 멱등 처리로 받아내며, 기한 만료 배치와의 레이스·금액 불일치 입금·기한 후 입금은 전부 자동 환불 예외 파이프라인으로 수렴시켜야 한다 — 발급 응답을 승인으로 착각하는 순간 돈 없이 이용권이 나간다.
