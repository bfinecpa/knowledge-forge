취소·환불 상태 머신
취소는 결제의 되감기가 아니라 또 하나의 결제다

면접 질문: "결제 취소/부분 취소/환불의 상태 머신을 설계해보세요."

핵심 관전 포인트 — 취소를 결제 상태에 CANCELED 하나 얹는 것으로 모델링하면 부분 취소가 등장하는 순간 붕괴한다 — 취소는 여러 번 일어날 수 있고, 취소 자체가 실패하거나 타임아웃될 수 있으며, 같은 취소 요청이 중복 도착할 수 있기 때문이다. 그래서 취소 요청 1건을 별도 엔티티 1행으로 모델링하고, 취소 엔티티에 REQUESTED → IN_PROGRESS → APPROVED / FAILED / UNKNOWN이라는 자체 상태 머신을 준다. 결제 쪽에는 잔여 취소가능금액(cancelable_amount)을 두고 조건부 UPDATE로 원자적 차감해 "취소 합계 ≤ 결제 금액" 불변식을 DB가 지키게 하며, 중복 취소 요청은 클라이언트 생성 취소요청 키의 유니크 제약으로 멱등 처리한다. 시니어 변별점은 취소 실패 시의 금액 원복 — FAILED 확정이면 원복하고, UNKNOWN이면 절대 원복하지 않는다는 구분이다.
  • 1
    취소는 결제 1건에 대해 N건이다 — 부분 취소가 여러 번 오고, 각 취소가 독립적으로 실패·타임아웃한다. 그래서 취소 요청 1건 = 별도 엔티티 1행으로 두고 REQUESTED → IN_PROGRESS → APPROVED / FAILED / UNKNOWN이라는 자체 상태 머신을 준다. 결제의 CANCELED·PARTIAL_CANCELED는 취소 행을 집계한 파생값일 뿐이다.
  • 2
    합계 불변식은 검사가 아니라 차감으로 지킨다 — "취소 합계가 결제 금액을 넘지 않는다"를 애플리케이션 check-then-act로 지키면 동시 요청 두 건에 그대로 뚫린다. 결제 행에 cancelable_amount 카운터를 두고 WHERE cancelable_amount >= ?를 붙인 조건부 UPDATE로 먼저 선점한 뒤 트랜잭션 밖에서 PG를 부른다. 중복 요청은 cancel_request_id UNIQUE로 멱등 처리한다.
  • 3
    취소 실패에는 두 얼굴이 있다 — FAILED(거절 확정)는 안 나간 게 확실하므로 선점 금액을 원복하고, UNKNOWN(타임아웃)은 환불이 이미 나갔을 수 있으므로 절대 원복하지 않고 동결한다. 원복은 "한 번 더 취소해도 된다"는 허가증이라서, 첫 취소가 사실 성공이었다면 그 허가증이 곧 이중 환불이 된다. 원복은 배치가 PG에 조회해 FAILED를 확인한 뒤로 미뤄진다.

0. 질문 + 출제 의도

질문: "결제 취소/부분 취소/환불의 상태 머신을 설계해보세요."

출제 의도: 취소는 결제보다 경우의 수가 많다 — 부분 취소, 중복 취소 요청, 그리고 취소 자체의 실패까지. 상태 머신으로 불가능한 전이를 차단하는 설계를 하는지, 그리고 엣지 케이스를 스스로 열거하는 능력 자체를 평가한다.

이 페이지가 겨냥하는 약점 세 가지 ① 취소를 결제 상태 컬럼의 값 하나로 처리하려는 습관 → 3절에서 "진행 중·실패·결과 불명이 동시에 여러 개 존재한다"는 사실을 보이고, 4절에서 취소를 별도 엔티티로 세운다.
② "잔액 검사 코드를 짰으니 안전하다"는 착각 → 6절에서 check-then-act 타임라인을 그려 검사와 행동 사이의 시간이 곧 취약점임을 보이고, 조건부 UPDATE 차감으로 바꾼다.
③ 취소 타임아웃을 실패로 적고 금액을 되돌리는 반사행동 → 7절에서 원복이 이중 환불의 허가증이 되는 경로를 시간축으로 추적하고, 동결이라는 정답을 세운다.

1. 이어받는 세 개념 — 결제 상태 머신에서

이 문서는 결제 상태 머신(01번 문서)을 전제로 한다. 거기서 가져오는 개념 세 가지만 짧게 복습하고 시작하자.

상태 머신
"가질 수 있는 상태의 목록"과 "어느 상태에서 어느 상태로 갈 수 있는가의 목록"으로 시스템을 서술하는 방식. 목록에 없는 전이는 전부 금지다.
조건부 UPDATE
"기대하는 현재 값"을 WHERE 절에 넣어 UPDATE하는 기법. WHERE id=1 AND status='IN_PROGRESS'처럼 쓰면 그 사이 남이 상태를 바꿨을 때 갱신 행 수가 0이 되어 내가 졌다는 사실을 알 수 있다.
UNKNOWN
"결과를 모른다"를 담는 상태. PG에 요청을 보냈는데 타임아웃이 나면 됐는지 안 됐는지 알 수 없고, 이걸 FAILED(안 됐음이 확정)로 적는 순간 사고가 시작된다.

이 문서의 한 문장짜리 출발점

결제의 UNKNOWN을 잘못 다루면 고객이 두 번 결제하고,
취소의 UNKNOWN을 잘못 다루면 회사가 두 번 환불한다

같은 문제가 취소 쪽에서 훨씬 나쁜 형태로 반복된다. 이중 결제는 고객이 항의해서라도 발견되지만, 이중 환불은 아무도 항의하지 않아 대사 배치가 돌기 전까지 조용히 쌓인다.

2. 취소가 결제보다 어려운 이유 — 경우의 수부터 열거한다

결제는 "1건이 성공하거나 실패하거나"다. 취소는 다르다. 설계보다 열거가 먼저다 — 무엇이 다른지 전부 나열해보자. 면접에서도 이 열거 자체가 점수다.

① 부분 취소가 N번 온다
100,000원 결제에서 옵션 반품으로 30,000원, 다음 주에 또 20,000원. 즉 "결제 1 : 취소 N" 관계다. 이 한 가지만으로도 결제 테이블의 컬럼 하나로는 감당이 안 된다는 게 드러난다.
② 취소 자체가 실패한다
PG 취소 API도 타임아웃이 나고 거절당한다. 정산 마감으로 승인 취소가 불가능한 경우, 카드사 점검, 단순 5xx. 즉 "취소의 UNKNOWN"이 존재한다.
③ 중복 취소 요청이 온다
CS 담당자가 어드민 버튼을 두 번 누르거나 고객 앱이 응답이 느려 재시도한다. 30,000원 취소가 두 번 실행되면 60,000원이 환불된다.
④ 불가능한 요청이 온다
이미 전액 취소된 결제에 또 부분 취소, 잔여 70,000원인데 80,000원 취소, 아직 승인도 안 난 결제에 취소.

취소를 어렵게 만드는 네 가지 — 부 · 실 · 중 · 불

부분 취소 N번· 취소 자체의 실패· 중복 요청· 불가능한 요청

면접에서 "취소가 결제보다 어려운 이유"를 물으면 이 넷을 먼저 던지고 설계로 들어가면 된다. ①이 엔티티 분리를, ②가 UNKNOWN·동결을, ③이 멱등 키를, ④가 상태 머신 조건을 각각 요구한다 — 즉 이 네 개가 곧 설계 목차다.

3. 왜 payment.status에 값을 더하는 방식으로는 안 되는가

이 조합을 결제 상태 컬럼에 CANCELED, PARTIAL_CANCELED 같은 값을 추가하는 것만으로 감당하려 하면 즉시 막힌다. 구체적으로 어디서 막히는지 보자. 100,000원 결제에서 30,000원을 취소하고 payment.status = 'PARTIAL_CANCELED'로 바꿨다. 이제 다음 질문들에 답해보라.

상태 컬럼 하나로 대답할 수 있는가
질문상태 컬럼 하나로 답할 수 있나
얼마가 취소됐나?아니다 — PARTIAL_CANCELED는 금액을 모른다
몇 번에 걸쳐 취소됐나?아니다
각 취소의 사유는?아니다
지금 진행 중인 취소가 있나?아니다 — 결제 상태는 "확정된 결과"만 담는다
방금 그 취소가 타임아웃 났는데 어디에 적나?적을 곳이 없다

마지막 두 줄이 결정적이다. 결제 상태 컬럼은 값이 하나뿐이라 "확정된 결과"밖에 담지 못한다. 그런데 취소는 진행 중인 것, 실패한 것, 결과를 모르는 것이 동시에 여러 개 존재할 수 있다(2-1 도식). 값 하나로 여러 개를 표현할 방법은 없다.

모델링 실패의 정확한 지점

표현해야 할 대상이 여러 개면 행도 여러 개여야 한다

01번 문서에서 is_paid boolean이 무너진 이유가 "모른다를 적을 칸이 없어서"였다면, 여기서 payment.status가 무너지는 이유는 "동시에 여러 개인 것을 적을 칸이 하나뿐이라서"다. 칸이 모자라면 사람은 반드시 아무 칸에나 밀어 넣게 되고, 그 순간부터 그 데이터는 거짓말을 시작한다.

3-1. 비유 — 영수증에 줄을 긋지 말고 반품 전표를 끊어라

영수증에 볼펜으로 줄을 긋는 가게

  • 원본이 훼손된다 — 원래 얼마였는지가 사라진다
  • 반품이 두 번이면 줄을 두 번 긋는 수밖에 없다
  • 반품이 실패하면 그은 줄을 어떻게 지우나
  • "지금 확인 중인 반품"을 영수증에 적을 자리가 없다

반품 전표를 새로 끊는 가게

  • 언제 · 얼마를 · 왜 돌려줬는지가 적힌 별도 문서
  • 부분 반품이면 전표가 여러 장 쌓인다
  • 원 영수증 금액 − 전표 합계 = 잔여 금액
  • 반품이 실패해도 원 영수증은 멀쩡하다 — 전표 한 장이 잘못됐을 뿐
취소 엔티티 분리는 정확히 이 구조다 — 원 결제는 불변의 사실로 남기고, 취소는 각각 독립된 기록으로 쌓는다

4. 설계 ① 취소 요청 1건 = 1행, 자체 상태 머신을 가진다

스키마 PostgreSQL — 취소 엔티티
CREATE TABLE payment_cancellation (
    id                 bigserial   PRIMARY KEY,
    payment_id         bigint      NOT NULL REFERENCES payment(id),
    cancel_request_id  varchar(64) NOT NULL,  -- 멱등 키 (8절)
    -- 금액은 절대 float/double로 두지 않는다. 0.1+0.2가 0.3이 안 되는
    -- 부동소수점 오차가 돈에 섞이면 대사가 영원히 안 맞는다.
    amount             numeric(12) NOT NULL CHECK (amount > 0),
    reason             text        NOT NULL,
    status             varchar(20) NOT NULL,  -- REQUESTED/IN_PROGRESS
                                              -- /APPROVED/FAILED/UNKNOWN
    requested_by       varchar(50) NOT NULL,  -- 'user:1042', 'admin:kim'
    created_at         timestamptz NOT NULL DEFAULT now(),
    UNIQUE (cancel_request_id)                -- 중복 요청 차단 (8절)
);
이 스키마에서 놓치기 쉬운 두 컬럼 reason과 requested_by는 장식이 아니다. 취소는 사후에 "누가 왜 이 돈을 돌려줬나"를 반드시 추적당하는 행위다. 'admin:kim'처럼 주체의 종류까지 적어두면, 사고 조사에서 "고객이 한 취소인가 내부자가 한 취소인가"를 쿼리 한 줄로 가른다.

4-1. 취소의 상태 머신 — 결제 상태 머신의 축소판

맨 오른쪽 열이 이 문서에서 가장 중요한 부분이다 (7절에서 자세히)
상태뜻금액은 어떻게 되나
REQUESTED취소 요청을 접수만 함아직 아무 일 없음
IN_PROGRESSPG 취소 API를 부른 중잔여 금액에서 선점(차감)된 상태
APPROVED취소 성공 확정차감 확정
FAILED취소 실패 확정차감을 원복
UNKNOWN취소가 됐는지 모름차감된 채 동결

5. 설계 ② 원본과 파생 — 결제 상태는 취소 행들의 집계 결과다

취소를 별도 테이블로 뺐으면, 결제 쪽 상태(CANCELED / PARTIAL_CANCELED)는 어디서 오는가? 여기서 원본(source of truth)과 파생값(derived value)이라는 구분이 필요하다. 원본은 "사실이 기록된 유일한 자리"이고, 파생값은 "원본에서 계산해 낸 편의용 값"이다. 캐시와 비슷한 개념인데, 중요한 건 틀렸을 때 누가 맞는지가 미리 정해져 있다는 점이다.

합계 = 0
APPROVED — 취소 없음
0 < 합계 < 결제 금액
PARTIAL_CANCELED
합계 = 결제 금액
CANCELED
복구 수단 파생 상태를 원본에서 재계산하는 쿼리
-- 상태가 꼬였을 때 이 한 줄이 복구 수단이 된다. (10절 사례 3)
SELECT COALESCE(SUM(amount), 0)
  FROM payment_cancellation
 WHERE payment_id = 4211
   AND status = 'APPROVED';   -- 확정된 취소만 센다. IN_PROGRESS는 제외

6. 설계 ③ 잔여 취소가능금액 — 검사가 아니라 원자적 차감

"취소 합계가 결제 금액을 넘으면 안 된다"는 규칙을 어떻게 지킬 것인가. 이게 설계의 심장이다.

6-1. 전제 지식 — check-then-act가 왜 뚫리는가

가장 자연스러운 구현은 "먼저 검사하고, 통과하면 실행한다"이다. 영어로 check-then-act(검사 후 행동)라고 부르는 패턴이다.

Before check-then-act — 동시 취소 요청 두 건에 뚫린다
@Transactional
public void cancel(long paymentId, long amount, String reason) {
    Payment p = paymentRepository.findById(paymentId);
    long canceled = cancellationRepository
            .sumApprovedAmount(paymentId);          // ① 합계 조회
    if (canceled + amount > p.getAmount()) {        // ② 검사
        throw new ExceedsCancelableAmountException();
    }
    pgClient.cancel(p.getPgTransactionId(), amount); // ③ PG 취소  ← 트랜잭션 안!
    cancellationRepository.save(/* APPROVED 행 */);  // ④ 기록
}

6-2. 해법 — 검사를 없애고 차감으로 바꾼다

핵심 아이디어 — "검사한 뒤 실행한다"를 "실행 조건을 SQL에 넣어 한 번에 실행한다"로 바꾼다

이를 위해 결제 행에 cancelable_amount(잔여 취소가능금액) 컬럼을 둔다. 승인 시점에 결제 금액과 같은 값으로 시작해서, 취소가 일어날 때마다 줄어드는 카운터다.

"원자적(atomic)"이라는 말의 뜻 쪼개서 관찰될 수 없는 연산이라는 뜻이다. UPDATE ... SET x = x - 30000 WHERE x >= 30000은 DB가 그 행에 락을 걸고 읽기·비교·쓰기를 한 덩어리로 처리하므로 중간에 다른 트랜잭션이 끼어들 틈이 없다. 앞의 check-then-act에 있던 t1~t5 사이의 틈이 구조적으로 사라진다.
After 잔여 금액을 조건부 UPDATE로 선점한 뒤, 트랜잭션 밖에서 PG를 부른다
public CancelResult cancel(long paymentId, long amount,
                           String cancelRequestId, String reason) {
    // ① 짧은 트랜잭션 하나로 "선점"을 끝낸다.
    //    잔여 금액 차감 + 취소 행 INSERT가 함께 커밋되거나 함께 롤백된다.
    //    PG 호출은 여기 들어오지 않는다.
    Cancellation c = txTemplate.execute(tx -> {
        int updated = jdbc.update("""
            UPDATE payment
               SET cancelable_amount = cancelable_amount - ?
             WHERE id = ?
               AND status IN ('APPROVED', 'PARTIAL_CANCELED')   -- 상태 관문
               AND cancelable_amount >= ?                      -- 금액 관문
            """, amount, paymentId, amount);
        // 0건이 나오는 경우는 두 가지다.
        //  (a) 잔여 금액이 부족하다 (동시 요청에 밀렸거나 애초에 초과 요청)
        //  (b) 결제가 취소 가능한 상태가 아니다 (READY/FAILED/전액취소 완료)
        // 어느 쪽이든 "이 취소는 진행할 수 없다"이므로 여기서 끝낸다.
        if (updated == 0) {
            throw new ExceedsCancelableAmountException();
        }
        // 중복 cancel_request_id면 유니크 제약에 걸려
        // DuplicateKeyException이 나고, 위 차감도 함께 롤백된다.
        return cancellationRepository
                .insert(paymentId, cancelRequestId, amount,
                        reason, Status.IN_PROGRESS);
    });

    // ② 트랜잭션 밖에서 PG 취소 호출.
    //    수 초가 걸릴 수 있는 외부 호출을 트랜잭션에 넣지 않는다.
    try {
        pgClient.cancel(c.pgTransactionId(), amount, cancelRequestId);
        cancellationRepository.markApproved(c.id());
    } catch (PgDeclinedException e) {
        // PG가 "이 취소는 안 됐다"고 명시적으로 답한 경우.
        // 안 나간 게 확실하므로 선점했던 금액을 되돌려준다.
        cancellationRepository.markFailed(c.id(), e.getCode());
        restoreCancelableAmount(paymentId, amount);       원복
    } catch (PgTimeoutException e) {
        // 결과 불명. 환불이 나갔을 수도 있으므로 절대 원복하지 않는다.
        // 금액은 차감된 채 두고, 해소는 배치에 맡긴다. (7절)
        cancellationRepository.markUnknown(c.id());              동결
    }
    recalculatePaymentStatus(paymentId);  // 파생 상태 재계산 (5절)
    return CancelResult.of(c);
}

6-3. 이 코드의 설계 포인트 세 가지

① 불변식의 집행자는 DB다
cancelable_amount >= ?가 붙은 UPDATE는 원자적이므로 동시 취소 두 건 중 한 건은 반드시 0건 갱신으로 실패한다. 보험으로 CHECK (cancelable_amount >= 0)까지 걸어두면 어드민 스크립트·마이그레이션 등 어떤 경로로도 음수가 될 수 없다.
② 선점 후 호출
금액을 먼저 차감(선점)하고 나서 PG를 부른다. 순서를 뒤집으면 "PG에서는 취소가 됐는데 우리 DB에는 아무 기록이 없는" 구간이 생기고, 그 구간에서 서버가 죽으면 그 취소는 영원히 미아가 된다.
③ PG 호출은 트랜잭션 밖
외부 API를 트랜잭션 안에서 부르면 타임아웃 동안 커넥션과 락을 쥔 채 멈춘다. 취소가 몰리는 상황(이벤트 전체 환불 등)에서는 이것 하나로 커넥션 풀이 말라 서비스 전체가 죽는다.

일반화 — 다른 도메인에도 그대로 쓰이는 패턴

"여러 행의 합계 ≤ 상한"이라는 행 간 규칙을 → "이 한 행의 카운터가 음수가 되지 않는다"는 단일 행 규칙으로 번역한다

재고 차감, 쿠폰 발급 수량 제한, 포인트 잔액, 좌석 수 — 전부 같은 모양이다. 합계를 세지 말고 잔여 카운터를 하나 두고 조건부로 깎는다. 취소 설계에서 이 문장을 뽑아 말할 수 있으면, 이 문제가 결제에 국한된 게 아니라는 걸 아는 사람으로 보인다.

7. 설계 ④ 취소 실패의 두 얼굴 — FAILED는 원복, UNKNOWN은 동결 시니어 변별

위 코드에서 가장 중요한 분기가 catch 두 개의 차이다. 둘 다 "취소가 성공하지 못했다"인데 처리가 정반대다.

FAILED와 UNKNOWN — 이 표 한 장이 이 문서의 시니어 변별 지점이다
FAILED (거절 확정)UNKNOWN (타임아웃)
PG가 한 말"이 취소는 안 됐다"(아무 말도 못 들음)
실제로 환불이 나갔나확실히 안 나갔다나갔을 수도 있다
cancelable_amount원복한다동결한다 (그대로 둔다)
고객에게 보여줄 문구"취소 실패, 다시 시도해주세요""취소 확인 중입니다"
다음에 할 일없음 (고객이 재시도 가능)배치가 PG에 조회해 해소

7-1. 왜 UNKNOWN에서 원복하면 안 되는가 — 시간축으로 추적한다

이 문서에서 외울 문장 하나만 고른다면

돈 문제에서 결과 불명은 항상 "돈이 이미 움직였다"는 쪽으로 보수적으로 취급한다
결제의 UNKNOWN
"승인이 났을 수 있다"고 보고 → 재결제를 막는다
취소의 UNKNOWN
"환불이 나갔을 수 있다"고 보고 → 재취소를 막는다(동결)

방향은 같다. 모를 때는 돈이 이미 움직였다고 가정한다. 이 한 문장을 원칙으로 뽑아 말하면, 개별 케이스를 외운 사람이 아니라 기준을 가진 사람으로 보인다.

8. 설계 ⑤ 중복 취소 요청의 멱등 처리

8-1. 멱등성이 무엇이고 왜 서버의 책임인가

멱등성(idempotency)은 "같은 요청을 몇 번 보내도 결과가 한 번 보낸 것과 같은 성질"이다. 수학에서 f(f(x)) = f(x)인 함수를 멱등이라고 부르는 데서 온 말이다.

왜 필요한가 — 클라이언트는 재시도를 멈출 수 없다 응답을 못 받은 클라이언트는 요청이 서버에 도달했는지 아닌지 알 수 없다. 도달했을 수도 있다는 이유로 재시도를 포기하면 진짜 유실됐을 때 손해가 난다. 그래서 클라이언트는 재시도하게 되어 있고, 중복을 걸러내는 책임은 전적으로 서버에 있다.

8-2. 어떻게 구현하나 — 세 단계

1
클라이언트(또는 어드민 화면)가 "취소 시도 1건"마다 cancelRequestId를 생성한다. 서버가 만들면 안 된다 — 서버가 만들면 요청이 두 번 오면 키도 두 개가 되어 아무것도 못 막는다. UUID 같은 걸 클라이언트가 만들어 보내고, 재시도할 때는 같은 값을 다시 보낸다.
2
payment_cancellation.cancel_request_id에 UNIQUE 제약을 건다. 여기가 실제 방어선이다. 애플리케이션이 여러 대로 떠 있어도, 동시에 두 요청이 들어와도, DB의 유니크 인덱스는 둘 중 하나만 INSERT를 통과시킨다.
3
중복 키로 들어온 요청은 기존 행을 조회해서 그 결과를 재생한다. 새로 처리하지 않고, 첫 요청과 똑같은 응답을 돌려준다.
멱등 처리 중복 키는 예외가 아니라 "이미 접수됨"의 신호다
try {
    return doCancel(paymentId, amount, cancelRequestId, reason);
} catch (DuplicateKeyException e) {
    // 같은 취소 요청이 이미 접수돼 있다. 새로 처리하지 않고
    // 기존 행의 현재 상태에 맞는 응답을 돌려준다.
    Cancellation prev = cancellationRepository
            .findByRequestId(cancelRequestId);
    return switch (prev.status()) {
        // 이미 끝난 건 — 첫 요청과 똑같은 응답을 재생한다.
        // 클라이언트 입장에선 "한 번만 처리된" 것처럼 보인다.
        case APPROVED, FAILED -> CancelResult.of(prev);
        // 아직 진행 중이거나 결과 불명 — 결과를 지어내면 안 된다.
        // 409로 "처리 중"을 알리고 클라이언트가 나중에 조회하게 한다.
        case IN_PROGRESS, UNKNOWN -> throw new CancelInProgressException();
        default -> throw new IllegalStateException();
    };
}
이 switch에서 가장 자주 틀리는 칸 IN_PROGRESS·UNKNOWN을 "실패"로 응답하는 것이 최다 실수다. 그러면 클라이언트는 새 키를 발급해 진짜 새 취소를 걸어버린다. 7-1의 이중 환불 경로가 멱등 계층에서 다시 열리는 것이다. 모르는 것에 대해 결과를 지어내지 않는다는 원칙은 멱등 응답에도 똑같이 적용된다.

8-3. 멱등성은 한 구간만으로 부족하다

9. 설계 ⑥ 취소 가능 조건은 상태 머신 + 도메인 규칙 이중으로

취소 요청을 받으면 "이 취소가 가능한가"를 판단해야 한다. 이 판단은 두 층으로 나뉜다.

9-1. 1차 — 상태 머신이 막는 것

6절 조건부 UPDATE에 있던 status IN ('APPROVED', 'PARTIAL_CANCELED')가 이미 많은 것을 차단한다.

결제 상태결과이유
READY0건 → 거부아직 승인도 안 됐다
FAILED0건 → 거부애초에 돈이 안 나갔다
CANCELED0건 → 거부이미 전액 취소됐다
APPROVED / PARTIAL_CANCELED통과취소 가능

여기서 눈여겨볼 것 — 규칙이 저절로 따라온다

"전액 취소 후 부분 취소 불가"를 별도 if문으로 짜지 않았다

전액 취소되면 상태가 CANCELED가 되고 cancelable_amount도 0이 되므로, 조건 두 개가 자동으로 막는다. 상태 머신을 제대로 세우면 이렇게 규칙이 저절로 따라오는 경우가 많다 — 반대로 말하면, if문이 자꾸 늘어난다는 것은 상태 설계가 부족하다는 신호다.

9-2. 2차 — 도메인 정책이 막는 것

상태 머신으로 표현되지 않는, 업무 규칙 층의 조건들이다.

정산 마감 후
승인 취소가 불가능하므로 PG 취소가 아니라 별도 환불 이체 흐름으로 전환해야 한다.
이용권을 이미 소진
취소 불가로 막거나, 소진분을 차감한 나머지만 부분 취소한다.
프로모션 결제
할인이 여러 상품에 배분돼 있으면 배분을 역산해야 취소 금액이 나온다.
답변 형태 — "상태 머신이 1차, 도메인 정책이 2차" · 1차는 데이터 정합성을, 2차는 사업 규칙을 지킨다

1차를 도메인 정책으로 대신하려 들면(예: if문으로 잔액 검사) 6절에서 본 check-then-act 함정에 그대로 빠진다. 층을 섞지 않는 것 자체가 설계다.

10. 실무 사례 — 취소 설계가 뚫리는 구멍들

10-1. 사례 1 — 어드민 더블 클릭으로 이중 환불 함정

CS 담당자가 어드민에서 30,000원 취소 버튼을 눌렀는데 화면이 3초간 멈추자 한 번 더 눌렀다. 취소요청 멱등 키가 없어서 서버는 두 요청을 완전히 독립적인 취소로 처리했다. 원 결제 60,000원에서 30,000원 취소 두 건이 모두 성공했고, 고객에게 60,000원 전액이 환불됐다. 이용권은 절반만 회수됐다.

여기서 반드시 짚어야 할 점 — 잔여 검사 코드는 있었다 개발자는 "합계가 결제 금액을 넘으면 예외"를 분명히 짰다. 그런데 그게 6절의 check-then-act 형태라 동시 요청을 막지 못했다. 두 요청이 각각 "지금까지 취소 0원 + 이번 30,000원 = 30,000원 ≤ 60,000원"으로 계산해 둘 다 통과한 것이다.

교훈 ① 어드민도 클라이언트다

  • "내부 도구라서, 쓰는 사람이 몇 명 안 되니까 괜찮다"는 생각이 사고를 만든다
  • 사람이 두 번 누르는 것과 앱이 재시도하는 것은 서버 입장에서 구분되지 않는다
  • 취소 버튼을 누르는 순간 cancelRequestId를 발급해야 한다

교훈 ② 검사는 방어선이 아니다

  • 유니크 제약과 조건부 차감이 최종 방어선이어야 한다
  • 애플리케이션 검사는 좋은 에러 메시지를 주기 위한 앞단일 뿐이다
  • 앞단만 있고 최종 방어선이 없으면, 평소엔 잘 돌다가 동시성이 생기는 날 터진다

10-2. 사례 2 — 취소 타임아웃을 실패로 간주해 이중 환불 함정

취소 API 타임아웃을 FAILED로 기록하고 cancelable_amount를 즉시 원복하는 코드였다. 7절에서 본 실수를 그대로 저지른 것이다. 고객 화면에 "취소 실패, 다시 시도해주세요"가 떴고 고객이 재시도해 두 번째 취소가 성공했다. 그런데 첫 취소도 PG에서는 성공해 있었다 — 45,000원 결제에 45,000원 환불이 두 번 나갔다.

"PG가 막아줬어야 하는 것 아닌가" PG에도 잔액 검사가 있으니 첫 취소로 잔액이 0이 됐다면 두 번째는 거절됐어야 한다. 실제로는 거절되지 않았는데, 이유가 중요하다.
① 우리가 보낸 취소 요청 식별자가 매번 달랐다. 그래서 PG는 두 요청을 별개의 취소 건으로 접수했다.
② 이 결제는 부분취소가 가능한 건이라 PG의 검증은 "요청 금액이 남은 금액 이하인가" 수준의 금액 단위 검증만 했고, 그 시점에는 아직 첫 취소의 정산 반영이 끝나기 전이라 통과해버렸다.

사례 2의 교훈 — 코드만 고쳐서는 끝나지 않는다

취소의 타임아웃은 UNKNOWN이며 금액 동결이 원칙이다

그리고 이 사고는 화면 문구까지 함께 고쳐야 한다 — "취소 실패"는 고객에게 재시도를 시키는 문구다. "취소 확인 중"이어야 한다. 상태 설계의 정확성은 UI 문구까지 내려와야 완결된다 — 상태를 정확히 만들어놓고 화면에서 거짓말하면, 그 거짓말이 다음 요청을 만들어낸다.

10-3. 사례 3 — 파생 상태 재계산 누락으로 전액 취소 건이 부분 취소로 남음

취소 행은 APPROVED로 잘 쌓였는데, 결제 상태 재계산(recalculatePaymentStatus)이 특정 예외 경로에서 빠졌다. 100,000원 결제가 60,000원 + 40,000원 취소로 전액 환불됐는데 결제 상태는 PARTIAL_CANCELED로 남았다. 월말 정산 대사 배치가 "우리 장부상 잔여 0원인데 상태는 부분취소"인 건 200여 건을 찾아냈다.

돈은 새지 않았다

  • 취소 행이 원본이고 그건 정확했기 때문이다
  • 복구는 재집계 쿼리 한 번으로 끝났다(5절의 SELECT를 돌려 상태를 다시 써주면 된다)
  • 원본-파생 구조를 지켰기 때문에 가능했던 일이다
  • 만약 취소 정보가 결제 상태 컬럼에만 있었다면 복구할 근거 자체가 없었다

그런데 2차 피해가 있었다

  • 부분취소 상태를 조건으로 도는 CS 자동화가 이 건들에 "잔여 금액에 대한 안내" 메일을 보냈다
  • 이미 전액 환불받은 고객 200명이 이상한 메일을 받았다
  • 즉 파생값이 틀리면 돈이 안 새도 그 값을 읽는 모든 하류 시스템이 함께 틀린다
교훈 ① 파생은 반드시 원본에서 재계산 가능해야
"재계산 함수가 존재하는가"가 파생값 설계의 합격 기준이다. 재계산할 수 없는 파생값은 사실상 두 번째 원본이고, 그건 5절에서 말한 진짜 위험한 설계다.
교훈 ② 대사 배치에 정합성 검증 항목을 넣는다
"승인 취소 합계 vs 결제 상태"가 맞는지 정기적으로 확인하는 쿼리를 두면, 다음번에는 월말이 아니라 다음 날 아침에 발견된다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 답을 먼저 떠올리고 오른쪽을 본다

취소가 결제보다 어려운 이유 4종?
부 · 실 · 중 · 불 — 부분 취소 N번, 취소 자체의 실패, 중복 요청, 불가능한 요청.
취소 엔티티 상태 5종?
REQUESTED → IN_PROGRESS → APPROVED / FAILED / UNKNOWN. UNKNOWN만 다시 APPROVED·FAILED로 해소된다.
상태별 금액 처리 3원칙?
확 · 원 · 동 — APPROVED는 확정, FAILED는 원복, UNKNOWN은 동결. 동결분의 원복은 배치가 FAILED를 확인한 뒤로 미뤄진다.
돈 문제의 결과 불명 원칙 한 줄?
"모를 때는 돈이 이미 움직였다고 가정한다." 결제 UNKNOWN은 재결제를 막고, 취소 UNKNOWN은 재취소를 막는다.
원본과 파생의 방향은?
원본 = 취소 행들, 파생 = payment.status. 어긋나면 항상 원본이 맞고, 재집계해서 덮어쓴다.
합계 불변식을 지키는 방법?
검사(check-then-act)가 아니라 cancelable_amount 조건부 UPDATE 차감. 행 간 불변식을 단일 행 원자성 문제로 번역한 것.
차감 UPDATE가 0건일 때 두 가지 의미?
(a) 잔여 금액 부족(동시 요청에 밀림 또는 초과 요청), (b) 취소 가능한 상태가 아님(READY·FAILED·전액취소 완료). 어느 쪽이든 진행 불가.
방어 3겹은?
① 조건부 UPDATE >= ? — 실시간 집행 / ② CHECK (cancelable_amount >= 0) — 최후 보험 / ③ 대사 배치 SUM 재검증 — 사후 탐지.
멱등 2구간은?
클라이언트→서버는 cancel_request_id UNIQUE, 서버→PG는 같은 키 전달. 키는 클라이언트가 만든다(서버가 만들면 못 막는다).
취소 가능 판단 2층은?
1차 상태 머신(데이터 정합성) + 2차 도메인 정책(정산 마감·이용권 소진·프로모션 배분). 1차를 if문으로 대신하면 check-then-act에 빠진다.

11-2. 꼬리질문 — 먼저 답해보고 펼친다

취소가 UNKNOWN일 때 취소가능금액을 원복하나요? 시니어 변별힌트: 원복이 무엇을 가능하게 만드는지 생각해본다. 그리고 원복은 사라지는 게 아니라 어디로 가는가?

절대 원복하지 않는다.

UNKNOWN은 "PG에서 환불이 나갔을 수 있다"는 뜻이다. 원복한다는 것은 곧 "같은 금액의 취소가 한 번 더 통과할 수 있는 창을 연다"는 뜻이고, 첫 취소가 사실 성공이었다면 그 창으로 이중 환불이 나간다. 7-1의 t4~t7 시나리오가 정확히 그 경로다.

올바른 처리는 동결 — 금액은 차감된 채 두고 취소 행만 UNKNOWN으로 표시한다

그 뒤 배치가 PG 취소 조회 API로 결과를 확인해 APPROVED(동결 확정) 또는 FAILED(그때 원복)로 해소한다. 즉 원복은 사라지는 게 아니라 "확인된 뒤로 미뤄지는" 것이다.

여기서 원칙 하나를 뽑아 말하면 변별력이 생긴다

돈 문제에서 결과 불명은 항상 돈이 나간 쪽으로 보수적으로 취급한다

결제의 UNKNOWN에서는 "승인이 났을 수 있다"고 보고 재시도를 막았고, 취소의 UNKNOWN에서는 "환불이 나갔을 수 있다"고 보고 재취소를 막는다. 방향은 같다 — 모를 때는 돈이 이미 움직였다고 가정한다.

취소를 별도 엔티티로 빼면 결제 상태와 어긋날 수 있지 않나요? 필수힌트: "어긋나지 않게 한다"가 아니라 "어긋났을 때 무엇을 할지 미리 정한다"가 답이다

어긋날 수 있다. 사례 3(10-3)이 실제로 그랬다.

그래서 방향을 미리 정한다 — 취소 행이 원본(source of truth)이고, 결제의 CANCELED/PARTIAL_CANCELED는 파생값이다. 이 방향이 정해져 있으면 어긋났을 때 할 일이 명확하다. 원본에서 다시 계산해 파생을 덮어쓴다. 고민할 게 없다.

운영에서는 두 겹으로 관리한다

  • 즉시 — 파생값은 취소가 확정될 때마다 재계산한다
  • 정기 — 그래도 생기는 어긋남은 대사 배치가 "승인 취소 합계 vs 결제 상태" 검증으로 잡아 재계산으로 복구한다

진짜 위험한 설계

  • 원본과 파생을 구분하지 않고 양쪽을 각각 갱신하는 것
  • 어긋났을 때 어느 쪽이 맞는지 판단할 근거가 없다
  • 결국 사람이 건별로 PG 내역을 열어보며 손으로 맞춰야 한다

덧붙일 수 있는 한마디 — "파생값은 재계산 함수가 존재할 때만 파생값이다." 재계산할 수 없으면 그건 파생이 아니라 두 번째 원본이다.

부분 취소의 합계 제약을 DB CHECK만으로 걸 수는 없나요? 시니어 변별힌트: CHECK가 볼 수 있는 범위는 어디까지인가? 그리고 우리는 그 한계를 어떻게 우회했나?

걸 수 없다. CHECK 제약은 단일 행 안의 조건만 검사할 수 있기 때문이다. CHECK (amount > 0)처럼 그 행의 컬럼들만 보는 조건은 되지만, "이 payment_id를 가진 다른 행들의 amount 합계"처럼 다른 행을 봐야 하는 조건은 표현할 수 없다.

이걸 행 간 불변식(cross-row invariant)이라고 부른다. 여러 행에 걸쳐 성립해야 하는 규칙이고, 표준 SQL의 제약 문법으로는 직접 표현할 방법이 없다.

그래서 우리가 쓴 기법 — 행 간 불변식을 단일 행 갱신의 원자성 문제로 바꾼다

결제 행에 cancelable_amount라는 잔여 카운터를 하나 두면, "여러 취소 행의 합계 ≤ 결제 금액"이라는 행 간 규칙이 "이 한 행의 카운터가 음수가 되지 않는다"는 단일 행 규칙으로 번역된다. 단일 행 규칙은 조건부 UPDATE의 원자성으로 완벽하게 지킬 수 있다.

① 실시간 집행
조건부 UPDATE의 cancelable_amount >= ?
② 최후 보험
CHECK (cancelable_amount >= 0) — 어드민 스크립트·마이그레이션 등 모든 경로에 대해
③ 사후 탐지
대사 배치의 SUM(amount) 재검증

덧붙이면 좋은 한마디 — 이 번역 기법은 결제 전용이 아니다. 재고, 쿠폰 발급 수량, 포인트 잔액, 좌석 수가 전부 같은 모양의 문제다.

환불과 취소는 뭐가 다른가요? 필수힌트: 기준선은 "매입·정산"이다. 그리고 상태 머신에 무엇이 하나 더 붙는가?

말로는 섞어 쓰지만 실제 처리 경로가 다르다.

승인 취소(cancel)

  • 카드 승인 자체를 무효화하는 것
  • 보통 매입·정산 전에 가능하다
  • 고객에게는 승인 내역이 사라지는 형태로 반영 — 명세서에 애초에 안 찍히거나, 승인과 취소가 나란히 찍혔다가 상계된다
  • 처리가 빠르다

환불(refund)

  • 이미 매입·정산이 끝난 거래의 돈을 역방향 이체로 돌려주는 것
  • 이미 우리 계좌로 들어온 돈을 다시 내보내는 것이므로 별도 정산 주기를 탄다
  • 고객 계좌에 들어오기까지 며칠 걸릴 수 있다

상태 머신 관점에서는 같은 골격(요청 / 진행 / 확정 / 실패 / 불명)을 쓴다. 다만 두 가지가 추가된다.

① 비동기 확정 신호를 기다리는 상태
취소는 API 응답으로 끝나지만, 환불은 며칠 뒤 이체 결과가 별도로 온다 — "이체 완료"를 기다리는 상태가 하나 더 붙는다.
② 경로 자동 전환 분기
정산 마감 시각을 기준으로 취소 경로에서 환불 경로로 자동 전환한다. 같은 "취소해주세요" 요청이라도 마감 전이면 승인 취소, 마감 후면 환불 이체로 갈라진다.

9-2에서 "정산 마감 후"를 도메인 정책 층에 둔 이유가 이것이다 — 상태 머신으로는 표현되지 않고, 시각이라는 외부 조건이 경로를 가른다.

취소 요청이 몰리면(이벤트 종료 직후 등) 이 설계의 병목은 어디인가요? 시니어 변별힌트: 병목처럼 보이지만 병목이 아닌 것을 먼저 걷어내라

먼저 병목처럼 보이지만 병목이 아닌 것부터. UPDATE payment SET cancelable_amount = ...는 결제 행 단위로 행 락을 잡는다. 그래서 같은 결제에 대한 동시 취소는 줄을 서서 처리된다(직렬화된다).

이건 문제가 아니라 의도된 동작이다 — 애초에 같은 결제의 잔여 금액을 두 요청이 동시에 만지면 안 된다

그리고 서로 다른 결제끼리는 다른 행이라 아무 경합이 없으므로, 결제 건수가 늘어나는 방향으로는 얼마든지 확장된다.

진짜 병목 — PG 취소 API의 응답 시간과 호출량 제한 PG는 초당 호출 수를 제한하고, 취소 API는 보통 승인 API보다 느리다. 이벤트 전체 환불처럼 수만 건을 한꺼번에 취소해야 하는 상황에서 동기 API 호출을 반복하면, 우리 스레드가 PG 응답을 기다리며 전부 묶인다.

그래서 대량 취소는 구조를 바꾼다.

면접에서 마지막에 붙이면 좋은 한마디 — "엔티티 분리를 먼저 해둔 덕에 대량 처리 전환이 스키마 변경 없이 가능하다." 설계 결정 하나가 나중의 선택지를 열어둔다는 감각을 보여준다.

차감·INSERT는 한 트랜잭션인데 markApproved는 왜 밖에 있나요? 중간에 죽으면요? 시니어 변별힌트: "죽었을 때 남는 상태"를 적어보라. 그 상태가 이미 설계된 상태인가?

먼저 왜 나눴는지부터. markApproved는 PG 응답을 받은 뒤에야 할 수 있는 일이고, PG 호출은 수 초가 걸린다. 같은 트랜잭션에 묶으면 그 수 초 동안 결제 행 락과 DB 커넥션을 쥐고 있게 된다(6-3의 세 번째 포인트). 그래서 트랜잭션은 선점까지만이다.

그러면 PG 호출 직후, markApproved 직전에 서버가 죽으면 무엇이 남는가.

DB에 남는 것
취소 행이 IN_PROGRESS인 채로 남고, 금액은 차감된 상태다.
실제 세상
PG에서는 취소가 성공했을 수도 있다.
이 조합은 이미 우리가 이름 붙여둔 상황이다 — 사실상 UNKNOWN

그래서 처리도 새로 만들 필요가 없다. 일정 시간(예: PG 타임아웃 + 여유)을 넘긴 IN_PROGRESS 취소 행을 배치가 UNKNOWN으로 승격시키면, 그다음은 기존 UNKNOWN 해소 배치가 알아서 가져간다. 금액이 차감된 채 남아 있는 것도 동결과 같은 상태라 안전 방향으로 일관된다.

여기서 보여줄 감각

결과 불명 상황이 여러 갈래로 생겨도, 입구는 UNKNOWN 하나로 모으고 해소 장치는 하나만 유지한다

"타임아웃", "프로세스 유실", "웹훅 미도착"이 각각 다른 복구 로직을 갖게 되는 순간 그 코드는 관리되지 않는다. 승격(promote) → 단일 해소 경로가 유지 가능한 구조다.

cancelable_amount 컬럼 없이, 매번 SUM으로 계산하면서도 안전하게 할 수는 없나요?힌트: 방법은 있다. 그런데 무엇을 잠가야 하고, 그 비용은 얼마인가?

방법 자체는 있다. 결제 행을 비관적 락으로 먼저 잠그고(SELECT ... FROM payment WHERE id=? FOR UPDATE), 그 락을 쥔 상태에서 취소 합계를 SUM으로 구해 검사하면 check-then-act의 틈이 닫힌다. 같은 결제에 대한 두 번째 요청은 락 앞에서 대기하므로 낡은 합계를 들고 통과하는 일이 없다.

그래도 카운터 방식이 나은 이유

  • 락 구간이 길어진다 — 잠그고 → 집계하고 → 검사하고 → INSERT까지 붙잡고 있어야 한다. 카운터 방식은 UPDATE 한 문장이 전부다
  • 취소 행이 쌓일수록 SUM이 무거워진다 — 카운터는 행 수와 무관하다
  • "잠그는 것을 잊는" 실수가 가능하다 — 새로 합류한 개발자가 FOR UPDATE 없이 같은 로직을 짜면 조용히 뚫린다. 카운터는 조건이 SQL에 박혀 있어 빠뜨리기 어렵다

그럼에도 SUM은 계속 필요하다

  • 파생 상태 재계산(5절) — 결제 상태를 다시 쓰는 근거
  • 대사 배치의 사후 검증 — 카운터가 코드 버그로 어긋나지 않았는지 확인하는 독립된 두 번째 계산
  • 즉 SUM은 집행 수단이 아니라 검증 수단이다

정리하면 — 실시간 집행은 카운터 조건부 UPDATE, 사후 검증은 원본 SUM. 둘은 경쟁 관계가 아니라 역할이 다른 두 층이다.

UNKNOWN 취소가 남아 있는 결제에 다른 취소 요청이 오면 받아주나요?힌트: 기술적으로 통과되는 것과 통과시켜도 되는 것은 다르다

기술적으로는 통과된다. UNKNOWN 건의 금액은 동결(차감)돼 있으므로, 남은 cancelable_amount 범위 안의 새 취소 요청은 조건부 UPDATE를 통과한다. 돈이 초과로 나가지는 않는다 — 그게 동결의 목적이다.

그래도 운영 정책으로는 보류를 권한다 — 미해소 UNKNOWN이 있는 결제는 사람이 볼 때까지 새 취소를 막는 편이 안전하다
이유 ① 고객 혼란
앞 취소의 결과가 아직 확정되지 않았는데 새 취소가 겹치면, 고객에게 보여줄 잔여 금액과 안내 문구가 모두 애매해진다.
이유 ② 조사 난이도
나중에 대사에서 문제가 생겼을 때, UNKNOWN 한 건과 새 취소 여러 건이 얽혀 있으면 어느 환불이 어느 요청의 결과인지 가려내기 어렵다.

답변 형태로는 "정합성은 동결이 이미 지켜준다. 보류는 정합성이 아니라 운영·CS 관점의 판단이다"라고 층을 나눠 말하면 정확하다.

전액 취소와 부분 취소를 API로 나눠야 하나요? 가산점힌트: 두 경우의 내부 처리가 실제로 다른가?

나눌 필요가 없다. 전액 취소는 "금액 = 현재 cancelable_amount"인 부분 취소일 뿐이다. 내부 경로가 같으므로 하나의 취소 API에 금액을 받는 것이 단순하고 안전하다.

다만 클라이언트 편의를 위한 배려는 필요하다 전액 취소는 클라이언트가 금액을 직접 계산하게 하면 위험하다. 조회 시점과 취소 시점 사이에 다른 부분 취소가 끼면 금액이 어긋나 0건으로 거부된다. 그래서 "전액"이라는 의도를 명시적으로 표현할 수단(예: 금액 생략 = 잔여 전액)을 서버가 제공하고, 실제 금액은 서버가 cancelable_amount에서 읽어 채우는 편이 낫다.

이 답의 값은 "API를 나눌지"가 아니라 "금액 계산의 책임을 어디에 둘지"로 문제를 바꿔 말한 데 있다. 동시성이 있는 값의 계산 책임은 그 값을 소유한 쪽(서버·DB)에 둔다.

한 줄 요약
취소는 결제 1건에 여러 번, 그것도 실패·타임아웃·중복 요청을 동반하며 일어나므로 취소 요청 1건 = 별도 엔티티 1행으로 모델링해 자체 상태 머신(REQUESTED → IN_PROGRESS → APPROVED/FAILED/UNKNOWN)을 주고, 잔여 취소가능금액을 조건부 UPDATE로 원자적으로 선점·차감해 합계 불변식을 DB가 지키게 하며, 취소요청 키 유니크로 중복을 멱등 처리한다 — 그리고 취소의 UNKNOWN에서 금액을 원복하지 않는 것이 이중 환불을 막는 마지막 선이다.
