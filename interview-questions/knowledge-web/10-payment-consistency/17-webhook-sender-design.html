웹훅 발신 설계
내 이벤트의 소비자가 겪을 문제까지가 내 설계 범위다

면접 질문: "웹훅을 발신하는 쪽은 어떻게 설계하나요? (서명, 재시도와 백오프, 순서 역전, 수신측 장애 시 격리)"

핵심 관전 포인트 — 웹훅 발신은 "HTTP POST 한 번"이 아니라 배달 시스템 하나를 만드는 일이다. 비즈니스 트랜잭션과 같은 트랜잭션으로 발송 이벤트를 outbox 테이블에 먼저 기록하고(커밋됐으면 반드시 발송, 롤백됐으면 발송 안 함), 별도 디스패처가 비동기로 발송한다. 재시도는 지수 백오프 + 최대 횟수 + 데드레터로 관리하되, 재시도가 곧 수신측에 중복 도착을 의미하므로 이벤트 ID·발생 시각·HMAC 서명을 반드시 실어 수신측이 검증·중복 제거·순서 판단을 할 수 있게 해준다. 발송 큐는 수신사별로 격리해 한 수신사의 장애가 다른 수신사의 웹훅을 밀리게 하지 못하게 하고, 순서는 보장하지 않는다고 계약(문서)에 명시한 뒤 시퀀스로 판단 근거만 제공한다. 실패 이벤트 재발송 콘솔까지 있어야 운영이 성립한다 — 상대가 겪을 위조·중복·역전 문제를 발신자가 미리 준비해주는 시야를 본다.
  • 1
    발신은 배달 시스템이다 — 상태 변경과 같은 트랜잭션에서 outbox 테이블에 INSERT까지만 하고, 실제 HTTP 발송은 별도 디스패처가 맡는다. 커밋되면 반드시 남고 롤백되면 함께 사라지므로 유실과 유령 이벤트가 동시에 막힌다. 트랜잭션 안에서 외부를 호출하지 않으니 남의 지연이 내 커넥션 풀을 먹지도 않는다.
  • 2
    재시도는 곧 수신측의 중복이다 — 지수 백오프 + 지터 + 최대 횟수 + 데드레터로 재시도를 관리하되, 그 대가로 상대에게 넘어가는 부담을 재료로 갚는다. 이벤트 ID(재시도해도 불변)·발생 시각·시퀀스·HMAC 서명(키 ID 포함)을 실어 수신측이 위조 판별·중복 제거·역전 판단을 할 수 있게 한다.
  • 3
    격리하고, 못 지킬 약속은 하지 않는다 — 발송 큐를 수신사별로 나누고 서킷 브레이커를 걸어 한 곳의 장애를 그 레인 안에 가둔다(bulkhead). 순서는 보장하지 않는다고 문서로 계약하고 판단 근거만 제공하며, 데드레터 알림과 재발송 콘솔까지 갖춰야 파트너 연동 운영이 성립한다.

0. 질문 + 출제 의도

질문: "웹훅을 발신하는 쪽은 어떻게 설계하나요? (서명, 재시도와 백오프, 순서 역전, 수신측 장애 시 격리)"

출제 의도: 수신측 설계(기본 문항)의 거울상이다. 수신사 한 곳의 장애가 내 발송 큐 전체를 밀리게 하지 않도록 격리하고, 재시도가 상대에게 중복으로 도착함을 전제로 서명과 이벤트 ID를 실어주는지 — "내가 만든 API의 소비자가 겪을 문제"까지 설계하는 시야로, 파트너 연동 경험의 진위를 가른다.

이 페이지가 겨냥하는 약점 세 가지 ① "웹훅 발송 = 이벤트 생기면 그 자리에서 POST"라는 반사 → 1절에서 이중 쓰기(dual write) 타임라인으로 순서를 어떻게 바꿔도 사고가 난다는 것을 보이고, 3절에서 outbox로 접는다.
② "재시도 붙였으니 끝"이라는 착각 → 재시도는 문제를 푸는 동시에 수신측에 중복과 역전을 만들어 넘긴다. 4·5·7절에서 넘긴 부담을 재료(이벤트 ID·시퀀스·서명)로 갚는 구조를 세운다.
③ 발송 큐를 하나로 두는 것 → 6절에서 head-of-line blocking을 도식으로 보이고, 수신사별 레인·서킷 브레이커·수신사별 모니터링으로 격벽을 친다.

1. 발신자가 되는 순간 — 순진한 구현이 무너지는 네 방향

1-1. 언제 우리가 발신자가 되는가

웹훅 문항을 처음 만나면 대개 받는 쪽을 떠올린다. PG사가 우리에게 승인 결과를 쏴주는 그림 말이다. 이 문항은 입장이 반대다.

PG · 결제대행 플랫폼
우리가 PG사 쪽 시스템을 만드는 경우. 가맹점에게 승인·취소·정산 결과를 통지해야 한다.
파트너 · 가맹점 통지
"정산이 완료됐다", "결제가 승인됐다"를 외부 회사의 서버로 알리는 모든 경우.
사내 마이크로서비스
서비스 간 이벤트 통지도 구조는 완전히 같다. 상대가 사내라고 해서 유실·중복·역전이 사라지지 않는다.

이때 순진한 구현은 이렇다 — "이벤트가 생기면 그 자리에서 상대 URL로 POST 한다." 코드로는 세 줄이면 된다. 그런데 이 구조는 네 방향에서 무너진다.

무너지는 네 방향 — 이 절의 뼈대

못 묶고(원자성) · 옮고(전파) · 막고(간섭) · 떠넘긴다(전가)
① 원자성
우리 DB와 상대 서버는 하나의 트랜잭션으로 못 묶는다 → 유실 또는 유령 이벤트
② 장애 전파
동기 호출은 남의 응답 시간을 내 자원 점유 시간으로 번역한다 → 커넥션 고갈
③ 수신사 간섭
큐가 하나면 한 수신사의 재시도 물량이 다른 수신사를 막는다
④ 문제 전가
재시도가 만든 중복·역전을 상대가 방어할 재료를 안 주면 내 부실이 파트너의 사고가 된다

1-2. 방향 ① 원자성 — 두 시스템에 쓰는 순간 생기는 문제

먼저 전제를 하나 짚자. 우리 코드가 "결제 상태를 PAID로 바꾸고 웹훅을 보낸다"를 할 때, 이건 서로 다른 두 시스템에 쓰기를 하는 것이다. 하나는 우리 DB, 하나는 상대 서버다.

@Transactional은 우리 DB에 대해서만 작동한다. HTTP 호출은 트랜잭션의 관리 대상이 아니다. 롤백해도 이미 나간 HTTP 요청은 되돌아오지 않는다. 이렇게 트랜잭션이 하나로 묶지 못하는 두 곳에 써야 하는 상황을 이중 쓰기 문제(dual write problem) 라고 부른다.

1-3. 방향 ② 장애 전파 — 남의 장애가 내 장애가 된다

발송을 결제 트랜잭션 안에서 동기로 하면, 우리 스레드가 상대 서버의 응답을 기다리며 멈춰 선다. 상대가 30초 걸리면 우리 스레드도 30초 묶인다. 여기서 두 자원이 동시에 고갈된다.

수신사 응답 30초→ 우리 스레드 30초 점유→ 톰캣 스레드 풀 고갈+ 트랜잭션이 안 끝남 → DB 커넥션 미반납→ 커넥션 풀 고갈→ 무관한 조회 API까지 사망
후자가 특히 치명적인 이유 톰캣 스레드가 마르면 느려질 뿐이지만, DB 커넥션이 마르면 발송과 아무 관계 없는 조회 API까지 커넥션을 못 받아 함께 죽는다. 즉 남의 서버가 느려진 것이 내 결제 API 전체의 장애로 번역된다. 이건 상대를 신뢰할 수 있느냐의 문제가 아니라, 동기 호출이라는 구조가 장애를 전파하는 통로라는 문제다.

1-4. 방향 ③ 수신사 간 간섭 — 한 집이 온 동네를 막는다

발송을 비동기로 바꿔 큐에 넣었다고 해보자. 장애 전파는 막았다. 그런데 큐가 하나면 새로운 문제가 생긴다.

대형 수신사 하나가 점검에 들어가 5xx를 뿜기 시작하면, 그쪽으로 갈 이벤트가 계속 실패하고 재시도로 큐에 다시 쌓인다. 이 물량이 큐 앞머리를 점령하면 뒤에 있는 다른 수신사의 신규 이벤트가 앞으로 나오지 못한다.

head-of-line blocking — 줄 맨 앞이 막혀 뒤가 전부 대기하는 현상 계산대 맨 앞 손님이 가격 확인을 기다리는 동안 뒤에 열 명이 서 있는 상황과 같다. 뒤 사람들은 아무 문제가 없는데도 못 지나간다. 자세한 구조와 해법은 6절.

1-5. 방향 ④ 소비자 문제 전가 — 내 설계 부실이 파트너의 사고가 된다

여기가 이 문항의 출제 의도와 가장 맞닿은 지점이다. 재시도를 하는 순간 수신측에는 중복이 도착한다. 병렬로 발송하거나 재시도가 끼는 순간 순서가 뒤집힌다. 이건 우리가 재시도를 도입한 대가로 상대에게 넘기는 부담이다.

우리가 안 실어주면 → 상대는 원리적으로 방어가 불가능하다
우리가 만든 부담상대가 해야 하는 방어우리가 안 주면
재시도 → 중복 도착중복 제거(멱등 처리)이벤트 ID가 없으면 무엇이 같은 이벤트인지 판별할 열쇠가 없다
공개 엔드포인트 → 위조 가능발신자 진위 확인서명이 없으면 정말 우리에게서 온 것인지 확인할 수 없다
재시도·병렬 → 순서 역전신·구 판단 후 최신만 반영발생 시각·시퀀스가 없으면 어느 게 최신인지 판단할 근거가 없다
우리 발신 설계의 부실이 모든 파트너사의 사고가 된다 — 상대가 아무리 잘 만들어도 재료가 없으면 방어할 수가 없다

2. 우체국 — 이 문서 전체의 지도

지금까지의 네 문제를 한 그림으로 묶으면 우체국이다. 이 비유가 유용한 이유는 웹훅 발신 시스템의 구성 요소가 우체국의 장치와 하나씩 대응하기 때문이다. 아래 표가 이 문서의 나머지 전부다.

우체국의 장치 ↔ 웹훅 발신 시스템의 구성 요소 (오른쪽 열이 이 문서의 목차다)
우체국웹훅 발신왜 그 장치가 있는가절
편지를 받으면 먼저 접수 대장에 기록한다. 직원이 바로 뛰어나가지 않는다outbox 테이블직원이 중간에 사고를 당해도 편지가 사라지지 않는다. "보내야 한다"는 사실이 기록에 남아 있으므로 다른 직원이 이어서 배달한다3
모든 우편물에 등기번호와 소인이 찍혀 있다이벤트 ID · 서명 · 발생 시각받는 쪽이 "이거 아까 받은 그 편지네"(중복 제거), "이건 진짜 우체국 소인이네"(위조 판별)를 확인할 수 있다4
수취인이 부재중이면 정해진 일정으로 재방문한다 — 몇 시간 뒤, 다음 날, 사흘 뒤로 간격을 벌린다지수 백오프같은 문 앞을 1분마다 두드리는 것은 낭비다. 부재가 길수록 다음 방문도 늦춰야 전체 배달이 굴러간다5
계속 못 만나면 반송 보관소에 넣고 별도 처리한다데드레터 + 알림영원히 안 될 것에 자원을 쓰면 다른 편지가 밀린다. 대신 반드시 사람에게 알린다 — 조용히 버리면 유실과 같다5
한 동네 도로가 막혔다고 다른 동네 배달을 멈추지 않는다수신사별 큐 · 서킷 브레이커사고를 그 동네 안에 가둔다. 격벽(bulkhead)6
"이 편지가 저 편지보다 먼저 도착한다"는 약속은 하지 않는다. 대신 소인 날짜를 찍어준다순서 비보장 계약 + 시퀀스못 지킬 약속을 하면 상대가 그 약속을 믿고 방어를 생략한다. 판단 근거만 주는 편이 정직하고 안전하다7
반송된 편지를 다시 부칠 창구가 있다재발송 콘솔데드레터에 들어간 건은 결국 사람이 처리한다. 이건 예외 상황이 아니라 연동 운영의 일상이다8

3. Outbox 패턴 — 두 시스템 문제를 한 시스템 문제로 접는다

3-1. 선택지를 늘어놓고 하나씩 지운다

1-2절의 이중 쓰기 문제로 돌아가자. 두 시스템에 원자적으로 쓰고 싶은데 방법이 없었다. 가능한 접근은 셋이다.

전달 보장 선택지 비교 — 세로가 방식, 가로가 두 실패를 막는지 여부
방식유령 이벤트
롤백됐는데 발송됨		유실
커밋됐는데 미발송		실무 판단
(a) 분산 트랜잭션(2PC)
DB와 HTTP를 한 트랜잭션으로		막음막음쓰지 않는다 — HTTP API가 2PC를 지원해야 하는데 거의 없고, 코디네이터가 죽으면 참가자들이 락을 잡은 채 멈추며, 성능도 나쁘다
(b) 커밋 후 발송
AFTER_COMMIT에서 HTTP 호출		막음못 막음절반만 맞는 답. 커밋 직후 발송 코드가 실행되기 전에 프로세스가 죽으면 기록조차 남지 않아 재시도할 근거가 없다
(c) Outbox 패턴
발송 사실을 같은 트랜잭션에 INSERT		막음막음표준. 두 시스템에 원자적으로 쓰기를 포기하고, 한 시스템(우리 DB)에만 원자적으로 쓴 뒤 나머지를 나중에 따라오게 한다. 대가는 at-least-once(3-5절)

outbox는 "보낼 편지함"이라는 뜻이고, 발송할 이벤트를 우리 DB의 테이블에 적어두는 것이 전부다. 핵심은 이 INSERT가 비즈니스 상태 변경과 같은 트랜잭션 안에 있다는 점이다.

커밋됐다면

  • 상태 변경과 이벤트 기록이 둘 다 남는다 → 유실 없음
  • 크래시가 나도 기록이 남아 있으니 다른 프로세스가 이어서 보낸다

롤백됐다면

  • 둘 다 사라진다 → 유령 이벤트 없음
  • "보내야 한다"는 사실 자체가 없던 일이 된다

3-2. 전체 그림 — 기록 · 집기 · 보내기 · 되밀기

3-3. 테이블 설계 — 컬럼 하나하나가 뒤 절의 복선이다

SQL PostgreSQL — outbox 겸 발송 상태 추적 테이블
CREATE TABLE webhook_outbox (
    event_id      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
                                    -- 수신측이 중복 제거에 쓸 열쇠.
                                    -- 재시도해도 이 값은 절대 바뀌지 않는다  → 4-3절
    receiver_id   bigint      NOT NULL,  -- 수신사. 엔드포인트와 시크릿의 주인이자
                                         -- 격리의 기준 축              → 6절
    event_type    text        NOT NULL,  -- payment.approved 등
    resource_key  text        NOT NULL,  -- 거래 식별자. 같은 거래의 이벤트를 묶는 축
                                         -- (순서 판단·직렬 발송)        → 7절
    sequence_no   bigint      NOT NULL,  -- 그 거래 안에서 몇 번째 이벤트인지.
                                         -- 도착 순서가 뒤집혔을 때 수신측이
                                         -- 신·구를 판단할 근거         → 7절
    payload       jsonb       NOT NULL,
    occurred_at   timestamptz NOT NULL,  -- 발송 시각이 아니라 "사건이 일어난" 시각.
                                         -- 재시도로 늦게 도착해도 그대로다 → 4-4절
    status        text NOT NULL DEFAULT 'PENDING',
                                    -- PENDING → SENDING → DELIVERED | DEAD
    attempt_count int  NOT NULL DEFAULT 0,       -- 백오프 간격 계산과
                                                 -- 최대 횟수 판정에 쓴다      → 5절
    next_attempt_at timestamptz NOT NULL DEFAULT now()
                                    -- "이 시각 전에는 집지 마라". 백오프를
                                    -- 스케줄러 없이 컬럼 하나로 구현한다 → 5절
);

-- 발송 대상 조회 전용 인덱스
CREATE INDEX idx_outbox_due
    ON webhook_outbox (receiver_id, next_attempt_at)

3-5. 디스패처 — 여러 대를 띄워도 서로 밟지 않게

Java 수신사별로 도는 워커 — 발송 대상을 원자적으로 집어 보낸다
void dispatch(long receiverId) {
    List<WebhookOutbox> due = outboxRepository.claimDue(receiverId, 100);
    // 내부 쿼리:
    //   SELECT * FROM webhook_outbox
    //    WHERE receiver_id = :receiverId
    //      AND status = 'PENDING'
    //      AND next_attempt_at <= now()   ← 백오프 대기 중인 건은 제외
    //    ORDER BY next_attempt_at
    //    LIMIT 100
    //    FOR UPDATE SKIP LOCKED;

    for (WebhookOutbox e : due) {
        try {
            sender.send(e);        // 서명 헤더 포함, 연결 3초 / 응답 5초 타임아웃
            e.markDelivered();     // 2xx만 성공으로 인정한다
        } catch (Exception ex) {
            // 실패하면 다음 시도 시각을 뒤로 밀고 시도 횟수를 올린다.
            // 최대 횟수를 넘으면 내부에서 DEAD로 전환된다.
            e.scheduleRetry(backoff(e.attemptCount()));
        }
    }
}

FOR UPDATE SKIP LOCKED를 짚고 넘어가자. FOR UPDATE는 조회한 행에 락을 걸어 다른 트랜잭션이 손대지 못하게 하는 구문이다. 여기에 SKIP LOCKED를 붙이면 이미 다른 워커가 잡고 있는 행은 기다리지 않고 건너뛴다.

FOR UPDATE만 쓰면

  • 워커 2번이 워커 1번이 잡은 행 앞에서 대기한다
  • 워커를 늘려도 처리량이 안 늘어난다 — 줄만 길어진다
  • 사실상 워커 1대짜리 시스템에 비용만 더 쓰는 셈

FOR UPDATE SKIP LOCKED면

  • 서로 같은 이벤트를 집지 않으면서(락)
  • 서로를 기다리지도 않는다(SKIP)
  • 워커 수에 비례해 처리량이 는다 → 큐 테이블의 관용구

outbox의 한계도 정확히 알아야 한다

디스패처가 발송에 성공한 직후, DELIVERED로 표시하기 전에 죽으면 그 이벤트는 여전히 PENDING으로 남아 재발송된다.

발신도 결국 at-least-once — "정확히 한 번"은 만들 수 없다

그래서 이벤트 ID를 실어 수신측이 중복 제거할 수 있게 하는 것이 계약의 일부가 된다. 면접에서는 "정확히 한 번은 못 주니, 최소 한 번 + 중복 제거 재료를 준다"까지 말해야 답이 닫힌다.

4-1. HMAC 서명 — 무엇을 서명 대상에 넣느냐가 전부다

HMAC 서명은 서명 = HMAC-SHA256(시크릿, 타임스탬프 + "." + 원문 바디)로 계산한다. HMAC은 "비밀키를 섞어 만든 지문"으로, 시크릿을 모르는 제3자는 본문을 위조해도 같은 지문을 만들 수 없다.

Java 발신 측 서명 생성 — 서명 대상 문자열을 만드는 부분이 핵심이다
String sign(String secret, long timestamp, String rawBody) throws Exception {
    String signingInput = timestamp + "." + rawBody;   // 타임스탬프를 서명 대상에 포함

    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(secret.getBytes(UTF_8), "HmacSHA256"));
    byte[] digest = mac.doFinal(signingInput.getBytes(UTF_8));

    return "sha256=" + HexFormat.of().formatHex(digest);
}

// 발송 시 헤더로 함께 보낸다 — 수신측이 같은 계산을 재현할 수 있도록
//   X-Signature-Timestamp: 1772596800      ← 서명 대상에 들어간 그 값
//   X-Key-Id:              whk_2026a       ← 어느 시크릿으로 서명했는지
//   X-Signature:           sha256=8f3c1b…
//
// 주의: 수신측은 "역직렬화 후 다시 만든 JSON"이 아니라 원문 바이트로 검증해야 한다.
//       공백·키 순서가 한 글자만 달라져도 지문이 완전히 달라지기 때문.
//       그래서 발신 측도 outbox의 payload를 직렬화한 "그 문자열 그대로" 보낸다.
타임스탬프를 서명 대상에서 빼면 생기는 구멍 공격자가 정상 요청을 통째로 복사해 나중에 그대로 재전송하면 서명은 여전히 유효하다. 수신측은 이를 막을 방법이 없다 — 서명은 "우리가 만든 요청"임은 증명하지만 "지금 만든 요청"임은 증명하지 못하기 때문이다. 타임스탬프가 서명 대상에 들어 있어야 수신측이 "허용 시간 창을 벗어난 요청은 거절"이라는 방어를 걸 수 있다.

4-2. 키 ID와 시크릿 로테이션 — 교체는 반드시 하게 된다

시크릿은 반드시 바꾸게 된다. 유출 의심, 담당자 퇴사, 정기 교체 정책 등의 이유로. 문제는 교체 순간이다. 우리가 새 시크릿으로 서명하기 시작하는 시점과 수신사가 새 시크릿으로 검증하기 시작하는 시점은 절대 정확히 일치하지 않는다. 수신사가 열 곳이면 열 곳의 배포 일정이 다 다르다.

시크릿 교체는 언젠가 반드시 하게 되는 일이므로, 처음부터 교체 가능한 구조로 만든다

4-3. 이벤트 ID — 절대 어기면 안 되는 규칙 하나

재시도할 때도 같은 이벤트 ID를 유지한다

ID를 만드는 시점은 발송할 때가 아니라 outbox에 INSERT할 때, 딱 한 번

재시도마다 새 ID를 발급하면 수신측 입장에서는 서로 다른 이벤트 세 개가 온 것과 구별되지 않아, 중복 제거가 원리적으로 불가능해진다. 우리가 재시도라는 부담을 넘기면서 방어 재료까지 뺏는 셈이다.

Before 발송 시점에 ID 생성
void send(WebhookOutbox e) {
    String id = UUID.randomUUID().toString();  // 시도마다 새 값
    http.post(headers("X-Event-Id", id), e.payload());
}
// 3회 재시도 = 수신측에는 서로 다른 이벤트 3건.
// 상대가 아무리 잘 만들어도 중복 제거가 불가능하다.
After INSERT 시점에 한 번, 이후 불변

    String id = e.eventId();   // outbox PK — 재시도해도 동일
    http.post(headers("X-Event-Id", id), e.payload());
}
// 3회 재시도 = 수신측에는 같은 이벤트 3번.
// 상대는 이미 처리한 ID면 무시하면 된다(멱등 처리).

4-4. 발생 시각과 시퀀스 — 순서를 못 지키는 대신 주는 근거

occurred_at — 사건이 일어난 시각

  • 발송 시각이 아니라 사건이 실제로 일어난 시각이어야 한다
  • 재시도로 6시간 늦게 도착해도 이 값은 원래 시각 그대로
  • 그래야 수신측이 "이건 6시간 전의 사실"임을 알고 판단할 수 있다

sequence_no — 그 거래 안에서 몇 번째인가

  • 리소스(거래) 단위로 단조 증가하는 값으로 준다
  • 전역 시퀀스가 아닌 이유: 발급 지점이 병목이 되고, 여러 인스턴스에서 발급하면 순서가 어차피 깨진다
  • 수신측이 실제로 알고 싶은 것도 "이 거래 안에서 뭐가 먼저인가"이지 전체 이벤트의 절대 순서가 아니다
이벤트 타입과 스키마 버전도 같은 이유로 싣는다 페이로드 구조를 언젠가 바꾸게 되는데, 모든 수신사가 동시에 따라올 수는 없다. 버전 필드가 있으면 수신측이 분기할 수 있고, 우리도 구버전을 언제까지 지원할지 계약으로 명시할 수 있다. 키 로테이션과 완전히 같은 구조의 문제다 — "한 번에 바꾸기"를 포기하고 "겹치게 바꾸기"로 설계한다.

5. 재시도 정책 — 지수 백오프 · 지터 · 상한 · 데드레터

5-1. 왜 고정 간격이 나쁜가

"1분마다 재시도"는 단순해서 매력적이지만 두 가지로 무너진다.

① 장애의 지속 시간 분포와 안 맞는다

  • 수신측 장애는 크게 두 종류다 — 배포 실수나 재시작 같은 수 분짜리, 정기 점검이나 인프라 장애 같은 수 시간짜리
  • 1분 간격은 앞의 것에는 적절하지만 뒤의 것에는 재앙이다
  • 6시간 점검이면 이벤트 한 건당 360번을 시도한다

② 그 360번이 전부 부하로 쌓인다

  • 수신사에는 이미 죽어 있는 서버에 초당 요청을 퍼붓는 셈
  • 우리에게는 워커가 타임아웃 대기로 낭비되는 셈
  • 큐는 재적재되어 줄어들지 않고, 다른 수신사가 뒤에서 굶는다

그래서 지수 백오프(exponential backoff) 를 쓴다. 실패할 때마다 대기 시간을 배수로 늘리는 방식으로, "상대가 아직 안 고쳐졌다면 다음엔 더 오래 기다려도 된다"는 직관을 그대로 구현한 것이다.

1차즉시0(이벤트 발생 직후 첫 발송)

5-2. 지터 — 복구 직후가 두 번째 장애 지점이다

지터(jitter) 는 "흔들림"이라는 뜻으로, 계산된 대기 시간에 무작위 오차(예: ±20%) 를 더하는 것이다. 왜 필요한지는 수신사가 복구되는 순간을 그려보면 바로 보인다.

Java 백오프 계산 — 스케줄 배열 + 지터 + 상한을 한자리에
private static final Duration[] BACKOFF = {
    Duration.ofMinutes(1), Duration.ofMinutes(5), Duration.ofMinutes(30),
    Duration.ofHours(2),   Duration.ofHours(6),   Duration.ofHours(12),
};
private static final int MAX_ATTEMPTS = 7;   // 1차 즉시 + 재시도 6회

// attemptCount = 지금까지 실패한 횟수. 반환이 비어 있으면 DEAD로 보낸다.
Optional<Duration> backoff(int attemptCount) {
    if (attemptCount >= MAX_ATTEMPTS) return Optional.empty();   // 상한 → DEAD + 알림

    Duration base = BACKOFF[attemptCount - 1];
    double factor = 0.8 + ThreadLocalRandom.current().nextDouble() * 0.4;  // ±20% 지터
    return Optional.of(Duration.ofMillis((long) (base.toMillis() * factor)));
}

// 429를 받았고 Retry-After 헤더가 있으면 그 값을 우선한다 —
// 상대가 직접 알려준 대기 시간이 우리 추정보다 정확하다.
Duration nextDelay(HttpResponse res, int attemptCount) {
    return retryAfter(res).orElseGet(() -> backoff(attemptCount).orElseThrow(DeadLetter::new));
}

5-3. 성공 판정과 응답 코드별 분기

재시도의 전제는 "지금은 실패했지만 나중엔 될 수도 있다"인데, 이 전제가 성립하지 않는 실패가 있다. 그래서 응답 코드를 뭉뚱그리지 않고 갈라서 다룬다.

응답별 처리 — "나중엔 될 수도 있는가" 하나로 판단이 갈린다
응답우리 해석재시도이유와 추가 조치
2xx수신 확인—DELIVERED. 2xx만 성공으로 인정한다. 단 200은 "수신 확인"이지 "처리 완료"가 아니다 — 이 경계는 문서로 못박는다
3xx 리다이렉트설정 오류따라가지 않음서명된 요청을 리다이렉트 대상 URL로 그대로 재전송하면, 수신사 설정이 잘못됐거나 탈취당했을 때 우리 서명이 붙은 요청을 제3자 서버로 배달해주는 꼴이 된다. 실패 처리가 안전하다
5xx · 타임아웃 · 연결 실패일시적 문제지수 백오프로 재시도상대의 일시적 문제일 가능성이 높다 — 재시도의 전제가 성립하는 유일한 구간
400 · 401 · 403 · 404설정 문제빠르게 데드레터잘못된 URL, 시크릿 불일치, 페이로드 형식 오류 — 백 번 재시도해도 똑같이 실패한다. 빠르게 DEAD로 보내고 수신사에 알리는 편이 낫다
429 Too Many Requests"너무 빠르다"재시도하되 늦춘다Retry-After 헤더가 있으면 그 값을 존중해 대기 시간을 늘린다
410 Gone엔드포인트 폐기중단"이 엔드포인트는 폐기됐다"로 해석해 등록 자체를 비활성화하는 관례가 있다. 사라진 주소로 며칠간 재시도하는 낭비를 막는다

타임아웃은 짧게 — 이유가 직관과 반대다

연결 3초 / 응답 5초 수준 — 오래 기다려 성공률을 조금 올리는 것보다, 빨리 포기하고 나중에 다시 보내는 편이 전체 처리량에 유리하다

느린 수신사 하나가 워커를 오래 붙잡아 처리량을 갉아먹는 것을 막기 위해서다. 어차피 우리는 재시도를 한다 — 이 사실이 짧은 타임아웃을 정당화한다.

5-4. 데드레터 — 끝을 만들되, 조용히 끝내지 않는다

데드레터(dead letter) 는 우편에서 온 말로, 수취인 불명이라 배달도 반송도 못 하는 편지를 모아두는 곳을 뜻한다. 여기서는 최대 횟수를 소진한 이벤트를 DEAD 상태로 옮겨 재시도를 멈추는 것이다.

무한 재시도를 하지 않는 이유

  • 영원히 안 될 것에 자원을 쓰면 큐가 계속 부푼다
  • 그 사이 진짜 처리해야 할 이벤트가 밀린다
  • 즉 끝이 없는 재시도는 다른 수신사에게 세금이다

그런데 여기서 한 걸음 더

  • DEAD로 옮기는 순간 반드시 사람에게 알려야 한다
  • 수신사에게도 별도 채널(이메일·대시보드)로 통보한다
  • 알림 없는 DEAD는 "조용히 버림"이다

가장 흔한 마무리 실수

알림 없이 DEAD로 옮기는 것은 유실과 다를 게 없다 — 상태 컬럼만 다를 뿐이다

6. 수신사별 격리 — 한 집 장애가 온 동네를 못 막게

1-4절에서 본 head-of-line blocking을 실제로 어떻게 막는지 보자. 그림으로 먼저.

6-1. 구체적인 격리 수단 세 가지

① 수신사별 큐 · 파티션
receiver_id 기준으로 워커를 나누거나, 메시지 큐를 쓴다면 수신사를 파티션 키로 삼는다. 수신사가 많아 워커를 일대일로 둘 수 없다면 최소한 동시 발송 슬롯에 수신사별 상한을 둔다(예: 수신사당 동시 10건) — 그러면 한 수신사가 전체 워커 풀을 삼키지 못한다.
② 수신사별 서킷 브레이커
특정 수신사로의 연속 실패가 임계치를 넘으면 그쪽 발송을 잠시 완전히 끊는다. 죽은 서버에 타임아웃 비용을 계속 지불하지 않기 위한 장치다(아래 도식).
③ 모니터링 분리
발송 성공률과 지연을 반드시 수신사별로 집계한다. 전체 성공률만 보면 "99%"라 정상으로 보이지만, 실제로는 수신사 30곳 중 한 곳이 0%인 상황일 수 있다.
전체 성공률 하나만 보는 대시보드의 함정 수신사 한 곳이 완전히 죽어도 전체 성공률은 그 수신사의 물량 비중만큼만 떨어진다. 물량이 적은 수신사라면 전체 지표는 여전히 "99%"로 보이고, 대시보드는 초록색이고 알림은 울리지 않는다. 그러나 그 한 곳에게는 100% 장애다. 지표는 "평균이 감춘 최악"을 드러내도록 쪼개야 한다.

7. 순서 보장의 한계 — 못 지킬 약속은 하지 않는다

재시도와 병렬 발송이 있는 한 도착 순서 보장은 사실상 불가능하다. 승인 이벤트가 재시도 대기 중일 때 취소 이벤트가 한 번에 성공하면 순서가 뒤집힌다. 이건 버그가 아니라 재시도 메커니즘의 필연적 결과다.

7-1. 세 가지 선택지 — 정답은 (c) 하나뿐이다

(a) 순서를 보장한다고 문서에 쓴다

  • 지킬 수 없는 약속이다
  • 수신사가 그 약속을 믿고 순서 검증 없이 구현한다
  • 뒤집힘이 발생하면 사고의 원인이 우리 문서가 된다
  • 최악의 선택

(b) 아무 말도 안 한다

  • 수신사가 "당연히 순서대로 오겠지"라고 가정하고 구현한다
  • 결과는 (a)와 같고 발견이 더 늦어진다
  • 침묵은 중립이 아니라 암묵적 약속으로 읽힌다

(c) 비보장을 명시하고 근거를 실어준다

  • 정직하고, 수신사가 올바르게 방어할 수 있다
  • 우리는 처리량과 격리를 지킨다
  • 정답

(c)를 고른다는 것은 구체적으로 세 가지를 한다는 뜻이다

① 계약
연동 문서에 "이벤트 도착 순서는 보장되지 않습니다"를 명시
② 재료
페이로드에 occurred_at과 sequence_no를 실어준다
③ 가이드
수신측 가이드에 "상태 머신으로 전이를 검증하고, 페이로드 대신 조회 API로 최종 상태를 확정하라"를 적어준다

즉 수신측 문항에서 다룬 방어책을 발신자가 문서로 가르쳐주는 셈이다. 파트너사 개발자가 그 문서를 읽고 올바르게 구현하는 것까지가 우리 설계 범위라는 시각이 이 문항의 핵심이다.

8. 운영 도구 — 실패 이벤트 재발송 콘솔

데드레터에 들어간 이벤트는 결국 사람이 처리한다. 그리고 이 일은 예외적 상황이 아니라 연동 운영의 일상이다. 수신사가 "저희 어제 오후 2시부터 4시까지 장애였는데 그 시간대 웹훅 다시 쏴주실 수 있나요"라고 요청하는 일은 정기적으로 생긴다.

콘솔이 없으면 개발자가 운영 DB에 직접 쿼리를 날린다
-- 새벽에, 급하게, 손으로
UPDATE webhook_outbox
   SET status = 'PENDING', next_attempt_at = now()
 WHERE status = 'DEAD';   -- receiver_id 조건을 빠뜨렸다

-- 결과: 전 수신사에 수십만 건이 한꺼번에 재발송.
-- 복구하러 실행한 쿼리가 더 큰 장애를 만든다.
콘솔이 있으면 같은 일이 절차가 된다
[재발송] 수신사=B  기간=03-04 14:00~16:00  상태=DEAD
        이벤트 타입=payment.*

  → 대상: 1,284건   // 실행 전에 건수를 먼저 보여준다
  → 이벤트 ID 유지  // 원래 ID 그대로 (새 ID 발급 금지)
  → [확인] 버튼      // 감사 로그: 누가·언제·무엇을
콘솔은 편의 기능이 아니라 안전장치다 — 조건절 하나 잘못 쓰면 전 수신사에 수십만 건이 재발송된다

재발송 콘솔의 최소 요건 다섯

① 검색
수신사 · 기간 · 이벤트 타입 · 상태로 필터링
② 상세 조회
페이로드 원문과 발송 이력(각 시도의 시각, 응답 코드, 응답 본문 일부)
③ 재발송
선택 건 또는 기간 단위 일괄. 실행 전에 대상 건수를 보여주고 확인을 받는다
④ 동일 이벤트 ID 유지
재발송할 때도 원래 이벤트 ID를 그대로. 새 ID를 발급하면 수신사가 이미 처리한 건까지 다시 처리해버린다
⑤ 감사 로그
누가 · 언제 · 무엇을 재발송했는지 기록
+ 한 걸음 더
수신사가 스스로 기간을 지정해 재발송을 요청할 수 있는 API를 열어주면, 우리 운영팀에 요청 자체가 오지 않는다

9. 실무 사례 — 발신 설계 부재가 만드는 장애

1

동기 발송이 결제 API 전체를 멈추다

웹훅 발송을 결제 승인 트랜잭션 안에서 동기 호출로 구현한 팀이 있었다. 평소에는 수신사들이 100ms 안에 응답했고, 아무 문제가 없어 보였다.

대형 수신사 배포 실패 → 응답 30초→ 결제 스레드가 하나씩 발송 대기에 묶임→ 톰캣 스레드 풀 포화→ 트랜잭션이 안 끝나 DB 커넥션 풀도 고갈

그 결과 그 수신사와 아무 관계도 없는 모든 가맹점의 결제가 8분간 실패했다. 분당 결제액 기준으로 수천만원 규모의 기회 손실이었다.

배울 점 outbox + 비동기 디스패처였다면 결제는 정상 처리되고 해당 수신사의 웹훅만 지연됐을 일이다. 여기서 배울 점은 "외부 호출을 트랜잭션 안에 넣지 마라"라는 규칙 자체보다, 그 규칙이 왜 있는지 — 동기 호출은 남의 응답 시간을 내 자원 점유 시간으로 번역하는 장치라는 것 — 이다.
2

단일 큐 + 무한 재시도 — 한 수신사가 큐를 점령

발송을 단일 큐 + 고정 간격(1분) 재시도로 운영하던 플랫폼이 있었다. 수신사가 늘어나는 동안에도 이 구조를 바꾸지 않았다.

수신사 A가 반나절 정기 점검에 들어갔다. A로 갈 이벤트가 실패하고, 1분 뒤 큐에 다시 실리고, 또 실패하고를 반복했다. 재적재가 신규 유입보다 빨라지면서 큐 깊이가 수십만 건으로 불었다.

그 뒤에 서 있던 다른 수신사들의 승인 웹훅이 최대 4시간 지연됐다. 그중 수신사 B는 웹훅을 받아 출고를 트리거하는 구조였는데, 당일 출고 마감 시각을 넘겨 배상 이슈로 번졌다. 자기 시스템은 멀쩡했는데 남의 장애 때문에 손해를 본 것이다.

세 겹으로 막혔을 것

  • 파티션: A의 물량은 A의 레인 안에만 쌓인다
  • 지수 백오프: 시도 횟수가 반나절에 6회 이하로 줄어든다
  • 데드레터: 7회 실패 후 DEAD로 빠져 큐에서 사라진다

구조가 아니라 규모가 문제를 드러낸다

  • 수신사가 한두 곳일 때는 단일 큐도 아무 문제가 없다
  • 그래서 바꿀 이유를 못 느끼다가, 규모가 커진 뒤 한 번에 터진다
  • 격리는 사고가 난 뒤에 넣기 가장 어려운 구조다
3

시크릿 일괄 교체 — 모든 수신사의 검증이 깨지다

보안 점검에서 "웹훅 시크릿을 교체하라"는 지시가 내려왔다. 키 ID 체계가 없던 팀은 시크릿을 새로 만들어 일괄 교체하고, 수신사들에게 "새 시크릿으로 바꿔주세요"라고 공지했다.

문제는 교체가 원자적으로 일어날 수 없다는 것이다. 우리는 배포 즉시 새 시크릿으로 서명하기 시작했지만, 수신사들은 각자의 일정에 따라 며칠에 걸쳐 반영했다. 그 사이에 나간 웹훅은 전 수신사에서 서명 불일치로 401이 났다.

여기서 재시도 정책이 사고를 키운다 401은 4xx라 우리 정책상 "설정 오류"로 분류돼 빠르게 데드레터로 빠졌다. 결국 며칠간 발생한 이벤트 상당수가 DEAD로 쌓였고, 수신사별 반영 시점을 확인해가며 수동으로 재발송해야 했다. 좋은 정책(4xx는 빨리 포기)이 나쁜 계약(키 ID 없음)과 만나면 이렇게 증폭된다.
시크릿 교체는 언젠가 반드시 하게 되는 일이므로, 처음부터 교체 가능한 구조로 만들어야 한다

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 답을 먼저 떠올리고 오른쪽을 본다

순진한 발송이 무너지는 네 방향?
못 묶고(원자성) · 옮고(장애 전파) · 막고(수신사 간섭) · 떠넘긴다(문제 전가)
outbox를 한 문장으로?
두 시스템에 원자적으로 쓰기를 포기하고, 한 시스템(우리 DB)에만 원자적으로 쓴 뒤 나머지를 나중에 따라오게 한다
"커밋 후 발송"의 결함 한 줄?
유령 이벤트는 막고 유실은 못 막는다 — 커밋 직후 죽으면 "보내야 한다"는 기록이 없어 재시도할 근거 자체가 없다
큐 테이블 성능의 거의 전부?
미결 건만 담는 부분 인덱스 + FOR UPDATE SKIP LOCKED(락은 걸되 남이 잡은 행은 건너뛴다)
봉투 6칸은?
아까 그거냐(이벤트 ID) · 무슨 일(타입+버전) · 어느 거래(리소스 키) · 몇 번째(시퀀스) · 언제 일어났나(occurred_at) · 진짜 너·지금 거냐(서명+타임스탬프+키 ID)
절대 어기면 안 되는 규칙?
재시도해도 이벤트 ID는 바뀌지 않는다. ID 생성은 발송 시점이 아니라 outbox INSERT 시점에 한 번
백오프 스케줄 숫자?
1분 · 5분 · 30분 · 2시간 · 6시간 · 12시간, 최대 7회, 누적 20시간 36분 → 이후 DEAD. 여기에 ±20% 지터
간격과 총 창의 근거는 서로 다르다?
간격은 기술적 근거(수신측 장애 지속 시간 분포) · 총 재시도 창은 비즈니스 근거("N시간 늦게 도착해도 이 이벤트가 성립하는가")
재시도하면 안 되는 응답은?
3xx(따라가지도 않는다 — 서명된 요청을 제3자에게 배달할 위험) · 400/401/403/404(설정 문제) · 410(등록 비활성화). 429는 재시도하되 Retry-After 존중
격리 3종 세트?
수신사별 큐·파티션(최소한 수신사별 동시 발송 슬롯 상한) · 수신사별 서킷 브레이커 · 수신사별 모니터링(전체 성공률은 최악을 감춘다)
순서에 대한 답은?
비보장을 문서로 계약 + occurred_at·sequence_no 제공 + 상태 머신·조회 API 가이드. 전역 순서는 불가, 리소스 내 순서만 옵션
우리가 줄 수 있는 보장 수준?
at-least-once — "2xx를 받을 때까지 최소 1회 전달". 정확히 한 번은 못 주니, 최소 한 번 + 중복 제거 재료(이벤트 ID)를 준다

10-2. 꼬리질문 — 먼저 답해보고 펼친다

outbox 대신 트랜잭션 커밋 후 바로 발송하면 안 되나요? 필수힌트: 막는 것과 못 막는 것이 하나씩 있다. 그리고 outbox도 완벽하지 않다

"커밋 후 발송"(예: @TransactionalEventListener(AFTER_COMMIT)에서 HTTP 호출)은 절반만 맞는 답이다. 유령 이벤트는 막지만 유실은 못 막는다.

커밋 후 발송이 못 막는 것

  • 커밋 직후, 발송 코드가 실행되기 전에 프로세스가 죽으면
  • 그 이벤트는 어디에도 기록이 없다 — 재시도할 근거 자체가 없다
  • 배포 중 인스턴스 종료처럼 흔한 상황에서 조용히 사라진다

outbox가 다른 지점

  • "발송해야 한다는 사실" 자체를 커밋에 포함시킨다
  • 그래서 크래시가 나도 다른 프로세스의 디스패처가 이어서 보낸다
  • 기록이 남아 있다는 것이 복구 가능성의 전부다

대신 정직하게 한계도 말해야 한다. 디스패처가 발송 성공 직후 상태 갱신 전에 죽으면 중복 발송이 되므로, 전달 보장은 at-least-once다.

"정확히 한 번은 못 주니, 최소 한 번 + 중복 제거 재료(이벤트 ID)를 준다"로 정리하면 답이 닫힌다
재시도 간격과 횟수는 어떻게 정하나요? 필수힌트: 간격과 "총 창 길이"는 근거가 다르다

수신측 장애의 지속 시간 분포에 맞춘다가 원칙이다. 배포 실수나 재시작은 수 분, 정기 점검이나 인프라 장애는 수 시간 단위다. 그래서 앞은 촘촘히(1분, 5분), 뒤는 성기게(30분, 2시간, 6시간) 잡는 지수 백오프가 표준이고, 여기에 지터를 더해 복구 직후 재시도가 몰리는 것을 막는다.

총 재시도 창(마지막 시도까지의 누적 시간)은 다른 기준으로 정한다 — "이 이벤트가 N시간 늦게 도착해도 비즈니스가 성립하는가."

창을 짧게 잡을 이벤트

  • 웹훅이 출고를 트리거하는 용도라면 24시간 넘게 끌 이유가 없다
  • 그 시점엔 이미 배송 약속을 어겼으므로, 자동 재시도보다 사람이 개입하는 편이 낫다

창을 길게 잡아도 되는 이벤트

  • 정산 데이터 통지처럼 하루 이틀 늦어도 무방한 이벤트
  • 이런 건 재시도 창을 길게 잡아 사람 개입을 줄이는 편이 이득이다
간격은 기술적 근거로, 총 창 길이는 비즈니스 근거로 정한다 — 그 뒤는 데드레터 + 알림 + 콘솔 재발송으로 넘긴다
수신사가 200을 주고도 처리에 실패했다면 발신자 책임인가요?힌트: 경계를 긋는 것으로 끝내면 반쪽 답이다

전달 보장의 경계를 묻는 질문이다. 발신자의 계약은 "2xx 응답을 받을 때까지 최소 1회 전달" 이고, 200 이후의 처리 실패는 수신측 책임 영역이다.

다만 여기서 끝내면 반쪽이다. 성숙한 발신자는 두 가지를 더 한다.

① 경계를 문서로 명확히 한다

  • 연동 가이드에 "200은 수신 확인이지 처리 완료가 아닙니다"를 쓴다
  • 이게 없으면 수신사가 "우리 200 줬는데 왜 데이터가 없냐"고 물어올 때 대화가 시작되지 않는다

② 스스로 복구할 수단을 제공한다

  • 기간을 지정한 재발송 API, 이벤트 목록 조회 API
  • 그러면 수신사가 자기 장애를 스스로 메울 수 있고, 우리 운영팀에 요청이 오지 않는다
경계는 긋되 복구 수단은 제공한다 — 두 축으로 답한다
순서 보장을 요구하는 수신사가 있으면 어떻게 하나요? 시니어 변별힌트: 단칼에 "불가능합니다"라고 하지 않는다. 대가를 정확히 말하는 것이 변별 포인트다

기본 답은 "보장하지 않음 + 시퀀스 제공 + 수신측 상태 머신 가이드"다. 처리량과 격리를 지키는 선택이며, 대부분의 수신사는 상태 머신 검증만 제대로 하면 순서 보장이 필요 없다는 것을 설명하면 납득한다.

정말 필요한 경우를 위해서는 리소스(거래) 단위 직렬 발송을 옵션으로 제공할 수 있다. 같은 resource_key를 가진 이벤트는 앞 건이 DELIVERED가 되기 전에 다음 건을 보내지 않는 방식이다.

이때 대가를 정확히 말하는 것이 변별 포인트다

  • 한 이벤트의 실패가 그 거래의 후속 이벤트를 전부 막는다. 승인 이벤트가 재시도 중이면 취소 이벤트도 대기한다
  • 앞 건이 데드레터로 빠지면 결정을 해야 한다 — 후속 이벤트를 영원히 막을 것인가, 아니면 건너뛰고 보낼 것인가. 후자를 택하는 순간 순서 보장이라는 약속 자체가 깨진다
  • 발송 병렬도가 리소스 단위로 제한되므로 처리량이 떨어진다

못 박아야 할 것 ①

  • 전역 순서는 불가능하고, 리소스 내 순서만 가능하다

못 박아야 할 것 ②

  • 순서 보장은 가용성·처리량과 교환된다

이 둘을 짚으면 파트너 연동을 실제로 운영해본 티가 난다.

outbox 테이블이 계속 커지는데 어떻게 관리하나요?힌트: 완료된 행은 더 이상 무엇이 아닌가?

핵심 인식은 DELIVERED와 DEAD 상태의 행은 더 이상 큐가 아니라 이력이라는 것이다. 발송 대상 조회는 이 행들을 볼 필요가 없다.

① 조회가 미결 건만 보게 한다

  • WHERE status IN ('PENDING','SENDING') 조건이 붙은 부분 인덱스(partial index)
  • 테이블에 수억 건이 쌓여도 인덱스에는 미결 건만 들어 있어 폴링 쿼리가 느려지지 않는다

② 완료 건을 물리적으로 치운다

  • N일 보관 후 아카이브 테이블로 이동, 또는
  • occurred_at 기준 범위 파티셔닝 후 오래된 파티션을 통째로 드롭
왜 대량 DELETE가 아니라 파티션 드롭인가 PostgreSQL에서 대량 DELETE는 죽은 튜플을 남겨 VACUUM 부담과 테이블 팽창(bloat)을 만들지만, 파티션 드롭은 파일 단위 제거라 그런 비용이 없다.
"큐로 쓰는 테이블은 인덱스가 미결 건만 보게 하라"가 요지다
이벤트 페이로드에 어디까지 담아야 하나요? 시니어 변별힌트: 재시도로 6시간 뒤에 도착한 페이로드는 무엇인가?

웹훅 발신 설계에서 자주 놓치는 축인데, 선택지가 둘이다.

방식담는 것문제
전체 상태 전달
state transfer		결제 금액, 상태, 고객 정보까지 전부. 수신측이 추가 조회 없이 바로 처리할 수 있어 편하다(1) 페이로드가 커지고 스키마 변경 시 모든 수신사가 영향
(2) 재시도로 6시간 뒤 도착한 페이로드는 그 시점의 오래된 값 — 그대로 반영하면 최신 상태를 덮어쓴다
(3) 개인정보·민감 정보가 로그·프록시를 거쳐 유통된다
통지만
notification only		"결제 pay_123이 승인됐다"만 보내고, 상세는 수신측이 조회 API로수신측 조회 API 호출이 늘어난다. 이벤트 폭주 시 조회 API가 병목

실무의 절충은 "판단에 필요한 최소 정보 + 조회를 위한 키" 다. 이벤트 타입, 리소스 키, 발생 시각, 시퀀스, 그리고 수신측이 "이 이벤트를 처리할지 말지" 판단할 정도의 요약 필드만 담고, 금액·상태 같은 확정값은 조회 API로 가져가게 한다.

웹훅은 초인종, 진실은 조회 API

한 문장으로 말하면 — 페이로드에 무엇을 담을지는 발신자 편의가 아니라 "수신측이 뒤늦게 도착한 이벤트를 안전하게 처리할 수 있는가"로 정한다. 여기까지 말하면 발신과 수신을 한 시스템으로 보고 있다는 게 드러난다.

디스패처를 여러 대 띄우면 같은 이벤트를 두 번 보내지 않나요? 가산점힌트: 동시에 집는 것은 막을 수 있다. 그런데 막을 수 없는 창이 하나 남는다

두 가지를 분리해서 답해야 한다 — "동시에 집는 것"과 "죽었다 살아나서 다시 보내는 것"은 다른 문제다.

동시 집기 — 막을 수 있다

  • SELECT … FOR UPDATE SKIP LOCKED로 집으면 두 워커가 같은 행을 잡는 일이 없다
  • 집은 즉시 status = 'SENDING'으로 표시해 다음 폴링에서 다시 집히지 않게 한다

죽은 워커의 잔여물 — 못 막는다

  • 워커가 HTTP 성공 직후, 상태 갱신 전에 죽으면 그 행은 SENDING인 채 남는다
  • 그 행을 영원히 두면 유실이고, 회수해 재발송하면 중복이다
  • 둘 중 중복을 택하는 것이 표준 — 그래서 at-least-once

실무에서는 SENDING에 갇힌 행을 회수하는 스위퍼(sweeper) 를 둔다. "집은 시각(예: claimed_at)이 일정 시간 이상 지난 SENDING 행을 PENDING으로 되돌린다"는 규칙으로, 메시지 큐의 가시성 타임아웃(visibility timeout)과 같은 발상이다.

막을 수 있는 중복은 막고, 막을 수 없는 중복은 계약으로 넘긴다 — 그 계약의 이름이 이벤트 ID다
폴링 말고 CDC로 outbox를 읽는 방식은 뭐가 다른가요? 가산점힌트: 바뀌는 것은 "읽는 방법"뿐이고, 바뀌지 않는 것이 하나 있다

CDC(change data capture) 는 테이블을 주기적으로 조회하는 대신 DB의 트랜잭션 로그를 따라 읽어 변경을 스트림으로 뽑는 방식이다. outbox 테이블에 INSERT가 커밋되면 그 사실이 로그에서 곧바로 감지되어 발송 파이프라인으로 흘러간다.

얻는 것

  • 폴링 주기만큼의 지연이 사라진다 — 이벤트가 거의 즉시 나간다
  • 빈 폴링 쿼리로 DB를 계속 두드리지 않는다
  • 애플리케이션 코드는 여전히 outbox INSERT만 하면 된다(3-4절 After 코드 그대로)

치르는 것

  • 운영해야 할 인프라가 늘어난다(커넥터, 스트림 저장소, 오프셋 관리)
  • 커넥터 장애·재시작 시 재전송과 오프셋 되감기를 이해하고 다뤄야 한다
  • 수신사별 백오프·서킷 브레이커는 여전히 우리가 구현해야 한다 — CDC는 "집는 방법"만 바꾼다
바뀌지 않는 것: 전달 보장은 여전히 at-least-once다 — 읽는 방법을 바꿔도 중복 제거 재료는 그대로 필요하다

면접에서는 "수신사 수와 발송량이 폴링으로 감당되면 폴링으로 시작하고, 지연 요구가 빡빡해지거나 폴링 부하가 문제가 될 때 CDC를 검토한다"는 순서로 답하면 균형이 맞는다.

수신사가 웹훅 URL을 등록·변경할 때 발신자가 검증할 것은? 시니어 변별힌트: 상대가 알려준 주소로 우리 서버가 요청을 보낸다 — 이 문장 자체가 위험하다

웹훅 발신은 구조적으로 "외부에서 지정한 주소로 우리 서버가 HTTP 요청을 보내는 기능"이다. 이건 SSRF(server-side request forgery) 의 정의 그 자체다 — 그래서 URL 등록 지점이 보안 관문이 된다.

내부 주소 차단
사설 IP 대역·루프백·클라우드 메타데이터 주소로 해석되는 URL은 거부한다. 우리 서버가 남의 지시로 우리 내부망을 때리는 일을 막는다
발송 직전 재확인
등록 시점에만 검사하면 나중에 DNS 레코드를 내부 IP로 바꾸는 우회가 가능하다. 실제 연결하는 주소 기준으로 검사해야 한다
HTTPS 강제
서명이 있어도 페이로드 자체는 평문으로 노출된다. 결제 이벤트라면 더더욱
소유 확인
등록 시 검증용 이벤트를 한 번 보내고 정상 응답을 확인한다. 오타난 주소나 남의 서버를 등록하는 것을 거른다
리다이렉트 미추종
5절의 규칙이 여기서 보안 규칙으로 다시 쓰인다 — 3xx를 따라가면 위 검사들이 전부 우회된다
변경 이력 · 알림
엔드포인트와 시크릿 변경은 감사 로그와 통지 대상이다. 조용히 바뀌면 탈취와 구별되지 않는다

이 질문에 답할 수 있으면 발신 기능을 "기능"이 아니라 "우리 네트워크에서 나가는 트래픽"으로 보고 있다는 신호가 된다.

발송 시스템은 무엇을 모니터링해야 하나요? 가산점힌트: 큐 깊이보다 더 좋은 지표가 하나 있다

지표는 전부 수신사별로 쪼개서 본다(6절). 그 위에 네 가지를 얹는다.

① 발송 지연
occurred_at → 실제 전달 시각의 분포. "사건이 일어나고 상대가 알기까지 걸린 시간"이 우리가 파는 품질이다
② 최고령 미결 건의 나이
큐 깊이는 유입량에 따라 출렁여서 정체를 잘 못 보여준다. "가장 오래된 PENDING이 몇 분째인가"는 정체를 직접 가리킨다
③ DEAD 발생 건수
0이어야 정상인 지표. 1건이라도 나면 사람이 봐야 한다 — 알림 없는 DEAD는 유실이다
④ 재시도 비율 · 서킷 상태
성공률이 100%여도 재시도 비율이 높으면 수신사가 불안정하다는 신호. 서킷이 열린 수신사는 즉시 보여야 한다
"성공률 99%"는 수신사 한 곳의 100% 장애를 감출 수 있다 — 지표는 평균이 감춘 최악을 드러내도록 쪼갠다
한 줄 요약
웹훅 발신은 비즈니스 트랜잭션과 원자적으로 outbox에 기록한 뒤 비동기 디스패처가 지수 백오프·데드레터로 재시도하는 배달 시스템으로 만들고, 재시도는 곧 수신측 중복이므로 이벤트 ID·발생 시각·시퀀스·HMAC 서명(키 ID로 로테이션 지원)을 실어 수신측이 검증·중복 제거·역전 판단을 할 수 있게 하며 — 수신사별 큐·서킷 브레이커로 한 곳의 장애를 격리하고, 순서 비보장은 문서로 계약하고, 재발송 콘솔로 운영을 마감해야 파트너 연동이 성립한다.
