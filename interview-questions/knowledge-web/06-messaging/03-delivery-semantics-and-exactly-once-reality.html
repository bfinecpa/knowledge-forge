전달 의미론 — "정확히 한 번"은 어디까지가 진짜인가
at-most-once · at-least-once · exactly-once, 그리고 그 약속의 경계선

면접 질문: "at-least-once, at-most-once, exactly-once 전달 의미론을 설명해주세요. 실무에서 exactly-once는 현실적인가요?"

핵심 관전 포인트 — 전달 의미론은 "장애가 났을 때 메시지가 몇 번 처리되는가"에 대한 계약이다. 보내는 쪽은 응답이 안 왔을 때 "못 갔다"인지 "갔는데 응답만 유실됐다"인지 구별할 수 없고, 그래서 선택지는 재전송(중복 감수)과 포기(유실 감수) 둘뿐이다 — at-most-once는 유실을, at-least-once는 중복을 감수하고, exactly-once는 둘 다 없애겠다는 약속이지만 그 약속에는 경계가 있다. Kafka의 exactly-once는 멱등 프로듀서(프로듀서 ID + 시퀀스 번호로 재전송 중복을 브로커가 걸러냄)와 트랜잭션(여러 파티션 쓰기 + 컨슈머 오프셋 커밋을 한 원자 단위로 묶음)의 조합이라, "Kafka에서 읽어 Kafka에 쓰는" 파이프라인 안에서만 성립하고 컨슈머가 PostgreSQL에 쓰거나 외부 API를 부르는 순간 경계 밖이라 깨진다. 그래서 실무 정답은 exactly-once delivery를 좇는 게 아니라 at-least-once + 멱등 처리로 exactly-once "효과"를 만드는 것이다.
  • 1
    셋은 기술이 아니라 갈림길에 붙인 이름 — 응답이 안 오면 "안 갔다"와 "갔는데 응답만 유실"을 구별할 수 없다. 그래서 재전송하면 중복(at-least-once), 포기하면 유실(at-most-once). 정상 상황에선 셋이 똑같이 한 번 처리되고, 장애에서만 갈린다.
  • 2
    Kafka의 exactly-once는 두 장치의 조합이고 범위가 정해져 있다 — 멱등 프로듀서(재전송 중복 제거) + 트랜잭션(토픽 쓰기 + 오프셋 커밋의 원자적 묶음). 원자성이 닿는 곳은 Kafka의 것뿐이라, "Kafka에서 읽어 Kafka에 쓰는" 파이프라인 안에서만 성립한다.
  • 3
    컨슈머가 DB나 외부 API를 건드리는 순간 경계 밖 — "DB는 커밋됐는데 오프셋 커밋은 실패"라는 어긋남은 남는다. 그래서 현실의 정답은 at-least-once + 멱등 처리로 exactly-once "효과"를 만드는 것 — 인프라 설정이 아니라 처리 로직의 성질로 달성한다.

0. 질문 + 출제 의도

질문: "at-least-once, at-most-once, exactly-once 전달 의미론을 설명해주세요. 실무에서 exactly-once는 현실적인가요?"

출제 의도: "정확히 한 번"이 공짜가 아니며 대부분 at-least-once + 멱등 처리로 푼다는 실무 감각을 확인한다. 벤더 마케팅 용어("exactly-once 지원!")와 실제 보장 범위를 구분하는 비판적 시각 — 문서의 보장 문구를 그대로 믿지 않고 "어느 경계 안에서의 보장인가"를 따져 묻는 습관이 있는지를 본다.

이 페이지가 겨냥하는 약점 세 가지 ① 세 이름을 정의만 외우는 것 → 1절에서 "응답이 안 오면 구별할 수 없다"는 관측의 한계에서 셋을 유도한다. 유도해 본 사람은 절대 안 헷갈린다.
② "Kafka는 exactly-once를 지원한다"로 끝내는 것 → 6·7절에서 원자성이 닿는 범위에 실제로 선을 그어 보여준다. 그 선 밖에 DB·외부 API·Redis가 있다.
③ "전송 계층의 중복"과 "비즈니스 레벨의 중복"을 뭉뚱그리는 것 → 4절에서 enable.idempotence가 막는 것과 못 막는 것을 표로 가른다. 이 주제에서 가장 자주 나오는 변별 포인트다.

1. 왜 하필 셋뿐인가 — 갈림길의 정체

세 의미론을 외우기 전에 왜 애초에 "정확히 한 번"이 어려운가를 먼저 깔아야 한다. 이걸 건너뛰면 세 이름이 그냥 암기 대상이 된다.

메시지를 네트워크로 보냈는데 응답이 안 왔다. 이때 실제로 벌어진 일은 둘 중 하나다 — (가) 못 받았다, (나) 받아서 저장까지 했는데 응답만 유실됐다. 그런데 보내는 쪽이 손에 쥔 정보는 "응답이 안 왔다" 하나뿐이라 둘을 구별할 방법이 없다. 받는 쪽에 물어보는 것 자체가 또 하나의 네트워크 요청이고, 그 요청도 똑같이 유실될 수 있다.

인출용 연상 — 「재중 · 포유」

재전송 → 중복
재전송하면 중복이 남는다 = at-least-once. 유실은 없다.
포기 → 유실
포기하면 유실이 남는다 = at-most-once. 중복은 없다.
전송 계층에는 둘 다 피하는 제3의 길이 없다 — 유실과 중복 중 하나는 반드시 고른다

2. 세 이름의 정의와 등기우편 비유

at-most-once
최대 한 번 · 0 또는 1회
재전송하지 않는다. 중복은 절대 없고 유실은 있을 수 있다.
at-least-once
최소 한 번 · 1회 이상
확인될 때까지 재전송한다. 유실은 없고 중복은 있을 수 있다.
exactly-once
정확히 한 번 · 딱 1회
유실도 중복도 없다. 대신 비용과 범위 제약이 붙는다.
개발 환경에서는 셋이 구별되지 않는다 정상 상황에서는 세 의미론 모두 메시지가 한 번씩 처리된다. 차이는 장애와 재시도가 끼어들었을 때 비로소 드러난다. 그래서 로컬·스테이징에서는 아무 차이가 없고, 운영에서 처음 차이가 나타난다 — "테스트했는데 잘 되던데요"가 통하지 않는 영역이다.
세 번째 열이 이 표의 핵심이다 — 무엇을 감수하기로 했는가
의미론보장감수하는 것장애 시 실제로 벌어지는 일어울리는 데이터
at-most-once최대 한 번 (0 또는 1회)유실응답이 없으면 그냥 다음으로 넘어간다 — 사라진 것을 알아챌 방법조차 없다메트릭, 위치 업데이트
at-least-once최소 한 번 (1회 이상)중복재전송·재처리로 같은 이벤트가 두 번 이상 처리된다대부분의 비즈니스 이벤트
exactly-once정확히 한 번비용 · 범위 제약보장이 유효한 경계 안에서만 1회 — 경계를 넘으면 다시 at-least-once로 떨어진다Kafka 내 스트림 처리

비유 — 일반우편 · 등기우편 · 일련번호 확인

일반우편 = at-most-once

부치면 끝이고 도착 여부를 확인하지 않는다. 우체국에서 분실되면 그걸로 사라진다. 대신 싸고 빠르다.

등기우편 + "확인 안 오면 재발송" = at-least-once

편지는 반드시 도착한다. 그런데 도착 확인서가 오는 길에 분실되면 같은 편지를 한 번 더 부치게 된다 — 받는 사람은 같은 편지를 두 통 받는다.

봉투의 일련번호를 확인해 "이미 처리한 번호면 무시" = 멱등 처리

두 통이 와도 결과는 한 통 받은 것과 같아진다. 실무의 exactly-once는 사실상 이 형태다 — 우편 시스템을 완벽하게 만드는 것이 아니라, 받는 사람 쪽에서 중복을 흡수하는 것. 이 문장을 기억해 두면 7·8절이 전부 예고편처럼 들어온다.

3. 의미론은 한 곳에서 정해지지 않는다 — 구간 합성

"우리 시스템은 at-least-once입니다"라는 말은 사실 두 구간에 대한 주장이다. 메시지는 프로듀서에서 브로커로 한 번, 브로커에서 컨슈머로 한 번, 총 두 번의 네트워크 구간을 건넌다. 그리고 각 구간의 의미론은 서로 다른 설정이 정한다.

약한 고리 법칙

전달 의미론은 구간별로 정해지고, 전체는 가장 약한 구간을 따라간다

4. 구간 1 (프로듀서 → 브로커) — acks와 멱등 프로듀서

먼저 acks가 무엇을 정하는 값인지부터

acks는 "브로커의 몇 명이 받았다고 해야 성공으로 칠 것인가"를 정하는 값이다. Kafka의 파티션은 리더 한 대와 팔로워 여러 대로 복제되는데 — acks=0은 응답을 아예 기다리지 않고, acks=1은 리더만 받으면 성공, acks=all은 동기화 대상 복제본 전부가 받아야 성공이다. (내구성 관점의 상세는 27-producer-acks-durability.md에서 다룬다.)

같은 프로듀서라도 설정 조합에 따라 구간 1의 의미론이 달라진다
설정 조합유실브로커 내 중복 저장구간 1의 의미론
acks=0 + 재시도 없음있음없음at-most-once — 보내고 확인하지 않으니 유실을 알아챌 방법조차 없다
acks=all + retries없음있음at-least-once — "브로커는 썼는데 응답만 유실 → 재전송"이면 같은 메시지가 두 번 저장된다
acks=all + enable.idempotence=true없음없음구간 1에 한해 사실상 1회 — 아래에서 그 장치를 뜯어본다

enable.idempotence는 정확히 어떻게 중복을 지우는가

동작 원리는 단순하다. 프로듀서에 고유 ID(PID, producer id)를 부여하고, 파티션별로 보내는 메시지 묶음마다 1씩 증가하는 시퀀스 번호를 붙인다. 브로커는 파티션마다 "이 PID로부터 마지막으로 받은 시퀀스 번호"를 기억해 두고, 이미 받은 번호가 다시 오면 로그에 쓰지 않고 성공 응답만 돌려준다.

여기가 변별 포인트 — 막는 것과 못 막는 것

이 경계를 헷갈리면 "멱등 프로듀서를 켰으니 중복은 끝났다"는 잘못된 결론에 도달한다. 못 막는 두 경우를 코드 수준으로 보자.

✔ 막는 것 — 전송 계층의 중복

프로듀서 클라이언트가 자기 판단으로 재시도해서 같은 배치가 브로커에 두 번 저장되는 것. PID + 파티션별 시퀀스 번호로 브로커가 걸러낸다.

// 애플리케이션은 send()를 한 번만 불렀다.
// 재시도는 클라이언트 내부에서 일어난다.
producer.send(orderCreated);
//  └ 내부: seq=41 전송 → 응답 유실 → seq=41 재전송
//    브로커: 같은 seq → 저장 생략, 성공 응답만

✘ 못 막는 것 — 비즈니스 레벨의 중복

애플리케이션 코드가 같은 내용을 두 번 발행하는 것. 브로커는 내용이 같은지 알 바가 아니다.

// [경우 1] 코드가 두 번 발행한다
producer.send(orderCreated);  // seq=41 저장
producer.send(orderCreated);  // seq=42 저장 ← 다른 메시지 취급

// [경우 2] 프로세스가 재시작한다
// 구 프로세스: PID=7, seq=41 [주문 8471] → 저장
// 새 프로세스: PID=8, seq=0  [주문 8471] → 저장
//   PID가 다르면 비교 대상 자체가 아니다

면접에서 가장 자주 갈리는 한 문장

enable.idempotence가 막는 것은 "프로듀서 클라이언트가 자기 판단으로 재시도해서 생긴 브로커 측 중복 저장"이고, 막지 못하는 것은 "애플리케이션 코드가 같은 내용을 두 번 발행하는 것"이다.

전송 계층의 중복→설정으로 해결 비즈니스 레벨의 중복→멱등 키 설계로 해결

두 종류를 구분해서 이름 붙여 말하는 것만으로 답변의 급이 달라진다.

5. 구간 2 (브로커 → 컨슈머) — 오프셋 커밋 시점이 운명을 가른다

오프셋은 컨슈머가 "이 파티션을 어디까지 읽었는지"를 나타내는 숫자이고, 커밋은 그 숫자를 Kafka에 기록해 두는 행위다. 컨슈머가 죽었다가 살아나면 커밋된 오프셋부터 다시 읽기 시작한다. 그래서 "처리와 커밋 중 무엇을 먼저 하는가"가 이 구간의 운명을 가른다. (상세는 23-offset-commit-and-auto-commit-risk.md.)

문제 처리 전 커밋 — 유실 구조
// props: enable.auto.commit = true (기본값)
// → poll() 시점에 직전 배치까지를 백그라운드로 커밋한다.
//   "처리가 끝났는지"는 아무도 확인하지 않는다.
while (true) {
    ConsumerRecords<K, V> records = consumer.poll(ofMillis(200));

    consumer.commitSync();          // ← 처리보다 먼저 커밋

    for (var r : records) {
        handle(r);                  // ★ 여기서 죽으면
    }                               //   이 메시지는 영영 오지 않는다
}

수동 커밋으로 바꿔도 순서가 뒤집혀 있으면 똑같이 유실이다. 설정이 아니라 순서가 원인이다.

개선 처리 후 커밋 — 중복만 남긴다
// props: enable.auto.commit = false
// 커밋 시점을 애플리케이션이 직접 통제한다.

while (true) {
    ConsumerRecords<K, V> records = consumer.poll(ofMillis(200));

    for (var r : records) {
        handle(r);                  // 멱등하게 구현되어 있어야 한다
    }

    consumer.commitSync();          // ← 처리가 끝난 뒤에만 커밋
}

이제 남는 위험은 중복 수신뿐이고, 그건 8절의 멱등 처리로 흡수할 수 있다.

왜 "처리 후 커밋"이 정석인가 — 이유를 한 줄로

중복은 흡수할 방법이 있고, 유실은 흡수할 방법이 없다 — 없어진 데이터를 되살리는 코드는 쓸 수 없다

합성 결과 — 대부분의 Kafka 시스템이 실제로 서 있는 자리

구간 1 · 유실 없음 + 재전송 중복 없음 + 구간 2 · 유실 없음 + 중복 가능 → 전체 = at-least-once

흔한 실무 구성 — acks=all + 멱등 프로듀서 + 처리 후 커밋 — 의 최종 의미론이다. 유실은 없지만 컨슈머 입장에서 중복 수신은 언제든 가능하다. 그래서 "컨슈머는 멱등하게 만든다"가 기본기가 된다. exactly-once 이야기는 여기서부터 시작해야 의미가 있다.

6. Kafka exactly-once의 실체 — 두 장치, 그리고 LSO

Kafka가 제공하는 exactly-once(EOS, exactly-once semantics)는 두 장치의 조합이다. 하나는 이미 봤다.

① 멱등 프로듀서 (4절)

재시도로 인한 브로커 내 중복 저장을 제거한다. 단 보장 범위는 프로듀서 세션 · 파티션 단위 — 재기동 후 같은 메시지를 다시 send()하는 것까지 막아주지는 못한다.

② 트랜잭션 본론

여러 파티션에 대한 쓰기 + 컨슈머 오프셋 커밋을 하나의 원자 단위로 묶는다. DB의 @Transactional과 이름은 같지만 묶는 대상이 전혀 다르다.

transactional.id — 프로세스가 재시작해도 유지되는 이름표

4절의 PID는 세션마다 새로 발급되는 번호였다. 그래서 프로세스가 재시작하면 브로커 입장에서는 완전히 남남인 프로듀서가 된다. transactional.id는 이 문제를 푸는 사람 이름 같은 식별자다 — 새 세션이 시작될 때 Kafka가 "아, 예전의 그 프로듀서구나"를 알아본다. 덕분에 두 가지가 가능해진다.

미완결 트랜잭션 정리
재시작 전에 열려 있던 트랜잭션을 기동 시점에 정리한다.
좀비 차단
낡은 세션이 뒤늦게 쓰기를 시도하면 거절한다 — 죽은 줄 알았던 인스턴스가 살아 돌아와 이중 기록하는 사고를 막는다.
핵심 코드 읽기 → 처리 → 쓰기를 한 트랜잭션으로
// 애플리케이션 기동 시 한 번: transactional.id로 신원을 등록하고,
// 이전 세션이 남긴 미완결 트랜잭션을 정리한다.
producer.initTransactions();

while (true) {
    ConsumerRecords<K, V> records = consumer.poll(Duration.ofMillis(200));

    producer.beginTransaction();
    try {
        for (var record : records) {
            // 처리 결과를 출력 토픽에 쓴다. 여러 토픽·파티션에 써도
            // commitTransaction() 전까지는 아무도 못 본다.
            producer.send(new ProducerRecord<>("orders-aggregated", transform(record)));
        }

        // 핵심은 이 줄이다. 입력 오프셋 커밋을 컨슈머가 아니라
        // 프로듀서를 통해 트랜잭션 안에서 한다.
        producer.sendOffsetsToTransaction(offsetsOf(records), consumer.groupMetadata());

        producer.commitTransaction();
    } catch (Exception e) {
        // 중단하면 출력 쓰기도, 오프셋 커밋도 없던 일이 된다.
        // 재시작하면 같은 입력을 다시 읽어 처음부터 처리한다.
        producer.abortTransaction();
    }
}

sendOffsetsToTransaction이 이 구조의 심장이다. 오프셋 커밋까지 트랜잭션에 넣었기 때문에 "읽기-처리-쓰기"가 원자적이 된다. 만약 오프셋 커밋을 컨슈머가 따로 했다면 — "출력은 썼는데 오프셋 커밋은 실패" 또는 "오프셋은 커밋했는데 출력 쓰기는 실패"라는 어긋남이 다시 생긴다. 5절에서 본 그 문제가 형태만 바꿔 되돌아오는 것이다.

읽는 쪽도 설정이 필요하다 — isolation.level과 안정 오프셋(LSO)

커밋하면 브로커는 관련된 각 파티션 로그 끝에 트랜잭션 마커를 기록한다. 마커는 실제 데이터가 아니라 "여기까지의 이 트랜잭션은 커밋됨(또는 중단됨)"이라고 알리는 제어용 표식이다. 그런데 컨슈머 기본값은 isolation.level=read_uncommitted라 마커를 무시하고 로그에 있는 것을 전부 읽는다 — 중단될 트랜잭션의 메시지까지 읽어버린다. read_committed로 바꿔야 비로소 커밋되지 않은 트랜잭션의 메시지를 건너뛴다.

EOS 설정 인출 카드 — 네 줄이면 끝난다

위치설정역할
프로듀서enable.idempotence=true재전송 중복 저장 제거 (Kafka 3.0+ 기본값)
프로듀서transactional.id=<고정 식별자>재시작해도 유지되는 이름표 · 좀비 차단
처리 루프send() + sendOffsetsToTransaction() + commitTransaction()출력 쓰기와 오프셋 커밋을 한 원자 단위로
컨슈머isolation.level=read_committed미완결·중단 트랜잭션의 메시지를 건너뛴다
Kafka Streamsprocessing.guarantee=exactly_once_v2위 전부를 프레임워크가 대신 해준다

하나라도 빠지면 EOS가 아니다. 특히 isolation.level은 컨슈머 쪽 설정이라 프로듀서만 손보고 끝내는 실수가 잦다.

7. 경계 밖으로 나가는 순간 깨진다

6절의 무대는 "Kafka에서 읽어 → 처리하고 → Kafka에 쓰는" 파이프라인이었다. 그런데 현실의 컨슈머는 Kafka에만 쓰지 않는다. 대부분 DB에 쓴다. 그 순간 무슨 일이 벌어지는지 구체적으로 보자.

깨지는 지점 컨슈머가 PostgreSQL에 쓰는 순간
@KafkaListener(topics = "order-events")
public void handle(OrderEvent event) {
    // ① PostgreSQL에 INSERT하고 커밋한다. 이건 PostgreSQL의 트랜잭션이다.
    orderRepository.save(toOrder(event));

    // ② 리스너가 정상 리턴하면 그때 컨테이너가 오프셋을 커밋한다.
    //    이건 Kafka에 남기는 별개의 기록이다.
}

①과 ② 사이에서 크래시하면 어떻게 되는가.

t0
PostgreSQL: INSERT INTO orders ... ; COMMIT; — 주문 한 건이 DB에 확정됐다. 되돌릴 수 없다.
t1
★ 프로세스 크래시 (또는 리밸런싱으로 파티션을 빼앗김)
t2
오프셋 커밋은 일어나지 않았다. Kafka가 아는 마지막 커밋 지점은 이 메시지 이전이다.
t3
재시작 → 커밋된 오프셋부터 다시 읽음 → 같은 OrderEvent를 다시 수신
t4
① 다시 실행 → orders 테이블에 같은 주문이 두 건이 된다

여기서 "그럼 Kafka 트랜잭션으로 묶으면 되지 않나?"라는 생각이 자연스럽게 나온다. 안 된다. Kafka 트랜잭션이 감쌀 수 있는 것은 Kafka의 것뿐이다.

"exactly-once 지원"이라는 문구를 봤을 때 던져야 할 질문

"어느 경계 안에서?"

Kafka의 답은 "Kafka 토픽 쓰기와 컨슈머 오프셋 커밋까지"다. 이 한 줄을 정확히 말할 수 있으면, 벤더 문구를 그대로 믿지 않는 사람으로 읽힌다.

8. 정답 — 멱등 처리로 만드는 exactly-once "효과"

exactly-once delivery는 시스템 경계를 넘는 순간 불가능하고, 가능한 것은 exactly-once processing 효과다

전달은 at-least-once로 두되, 같은 메시지를 두 번 받아도 결과가 한 번 처리한 것과 같도록 처리 쪽을 멱등하게 만든다. 여기서 멱등성(idempotency)은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"을 말한다. 2절의 "봉투의 일련번호를 확인해 이미 처리한 번호면 무시"가 코드로 내려온 것이다.

문제 7절의 깨진 컨슈머
@KafkaListener(topics = "order-events")
public void handle(OrderEvent event) {

    orderRepository.save(toOrder(event));

    // 중복 수신에 대한 방어가 전혀 없다.
    // 같은 이벤트가 두 번 오면 주문도 두 건이 된다.
}
개선 멱등 컨슈머 — 처리 이력과 업무 쓰기를 한 DB 트랜잭션에
@KafkaListener(topics = "order-events")
@Transactional   // PostgreSQL 트랜잭션 (Kafka 트랜잭션 아님)
public void handle(OrderEvent event) {
    // 프로듀서가 발급한 고유 ID를 유니크 키로 삼는다.
    int inserted =
        processedEventRepository.insertIfAbsent(event.eventId());

    if (inserted == 0) return;   // 이미 처리됨 → 조용히 종료

    orderRepository.save(toOrder(event));
    // 이력 INSERT와 업무 쓰기가 같은 트랜잭션이라
    // "이력만 남고 주문은 없는" 어긋남이 생기지 않는다.
}

왜 "조회 후 INSERT"가 아니라 곧바로 INSERT인가

조회와 INSERT 사이의 틈에 같은 이벤트의 두 번째 처리가 끼어들 수 있다. 유니크 제약과 결합하면 "확인과 선점"이 DB 안에서 한 번에 원자적으로 일어난다.

왜 중복일 때 예외를 던지면 안 되는가

중복 수신은 오류가 아니라 at-least-once에서 정상적으로 예상되는 상황이다. 예외를 던지면 재시도 루프에 빠지고, 심하면 DLQ로 흘러가 정상 이벤트가 실패로 집계된다.

스키마 중복 판정의 기준이 되는 테이블
CREATE TABLE processed_event (
    event_id     uuid        PRIMARY KEY,   -- 중복 판정의 기준
    processed_at timestamptz NOT NULL DEFAULT now()
);
-- insertIfAbsent는 INSERT ... ON CONFLICT (event_id) DO NOTHING 이다.
-- 충돌 시 예외 없이 0행 삽입으로 끝나므로 분기가 단순해진다.

방향별로 패턴이 다르다 — 한 트랜잭션이 아니라 각 경계에서 각자

발행 측
DB 커밋과 이벤트 발행의 원자성
Transactional Outbox + CDC — 보낼 메시지를 같은 DB의 outbox 테이블에 INSERT해 업무 변경과 발행 예약을 한 트랜잭션으로 묶고, 별도 프로세스가 그 테이블을 읽어 Kafka로 발행한다. (28-transactional-outbox-cdc-kafka.md)
소비 측
이벤트 수신과 DB 반영의 중복 제거
멱등 컨슈머 — 위의 processed_event 방식. (04-idempotent-consumer-implementation.md)
"양쪽을 한 트랜잭션으로" 대신 "각 경계에서 각자의 패턴으로"가 분산 시스템의 표준 접근
방향 전환 한 줄 exactly-once는 인프라 설정이 아니라 처리 로직의 성질로 달성된다. 면접에서 이 문장이 나오면 "설정을 켤 줄 아는 사람"에서 "보장의 출처를 아는 사람"으로 넘어간다.

9. 실무 감각 — 데이터별로 의미론을 고른다

모든 데이터에 같은 보장을 걸 필요는 없다. 데이터의 가치에 보장 수준을 맞춘다.

보장을 올리는 것도 비용이고, 과설계도 비용이다
데이터 유형고르는 의미론왜주의할 점
로그 · 메트릭 · 실시간 위치at-most-once 성향
가벼운 커밋, 낮은 acks		초 단위 메트릭은 한 점이 빠져도 그래프가 유효하고, 차량 위치는 최신값만 의미가 있어 과거 값 재전송이 오히려 노이즈다. 유실 비용 < 중복·재처리 비용."싸다"는 이유로 비즈니스 이벤트까지 이 설정에 얹지 않는다
주문 · 결제 · 정산 등 비즈니스 이벤트at-least-once
+ 멱등 컨슈머
표준 조합		유실이 불가하다 — 돈이 사라지거나 생겨난다. 중복은 멱등 처리로 흡수한다.멱등 키를 프로듀서가 발급한 이벤트 ID로 잡는다 (오프셋·수신 시각 같은 것은 키가 못 된다)
Kafka 안에서 끝나는 스트림 집계EOS
exactly_once_v2		읽기·쓰기가 모두 Kafka라 트랜잭션이 전 구간을 감쌀 수 있는 유일한 영역이다. 집계 정확성이 곧 결과물의 가치다.트랜잭션 코디네이션 비용으로 지연·처리량 손해, LSO 때문에 read_committed 컨슈머의 체감 지연이 트랜잭션 주기만큼 늘어난다

우리 시스템이 지금 어떤 의미론인지 3분 만에 판정하기

1
프로듀서 설정 세 줄을 본다 — acks, retries, enable.idempotence. acks=0이면 여기서 이미 유실 구조다.
2
커밋 시점을 본다 — enable.auto.commit=true이거나 처리 전에 커밋하고 있으면 유실 가능. 처리 후 커밋이면 중복 가능.
3
처리 로직이 멱등한가를 본다 — 멱등 키로 중복을 걸러내지 않으면, 위에서 아무리 잘 설정해도 중복이 그대로 업무 데이터에 남는다.
세 칸을 채우면 답이 나온다 — "구간 1은 ○○, 구간 2는 ○○, 처리는 멱등/비멱등"

10. 인출 카드 · 꼬리질문 셀프 테스트

면접 전날 이것만 — 인출 카드 6장

① 왜 셋뿐인가
응답이 없으면 "안 갔다"와 "응답만 유실"을 구별 못 한다 → 재전송(중복) 또는 포기(유실). 재중 · 포유.
② 언제 갈리는가
정상 상황엔 셋 다 1회. 장애와 재시도가 끼어들 때만 차이가 난다 — 그래서 운영에서 처음 드러난다.
③ 어디서 정해지는가
구간 1은 acks·retries·enable.idempotence, 구간 2는 오프셋 커밋 시점. 전체는 약한 쪽을 따라간다.
④ 멱등 프로듀서의 사정거리
막는 것 = 클라이언트 재시도로 인한 브로커 측 중복 저장. 못 막는 것 = 앱이 두 번 발행 / 재기동 후 재발행(새 PID).
⑤ Kafka EOS의 경계
원자성 범위 = Kafka 토픽 쓰기 + 컨슈머 오프셋 커밋. 무대는 "Kafka → 처리 → Kafka" 파이프라인.
⑥ 실무 정답
at-least-once + 멱등 처리로 exactly-once 효과. 인프라 설정이 아니라 처리 로직의 성질로 달성한다.

꼬리질문 — 먼저 스스로 답한 뒤 펼친다

enable.idempotence는 무엇을 막고, 무엇을 못 막나요? 핵심힌트: 중복에는 두 종류가 있다. 이름을 붙여 나눠라

막는 것 — 프로듀서 클라이언트 내부의 재시도로 같은 배치가 브로커에 두 번 저장되는 것. 프로듀서 ID(PID) + 파티션별 시퀀스 번호로 브로커가 "이미 받은 시퀀스"를 감지해 저장 없이 성공 응답만 돌려준다.

못 막는 것 — 애플리케이션 레벨의 중복. 코드가 send()를 두 번 부르거나, 재기동한 프로세스가 같은 비즈니스 이벤트를 다시 발행하는 경우다. 새 프로세스는 새 프로듀서 세션이라 새 PID를 받으므로, 브로커 입장에선 아예 다른 프로듀서가 보낸 다른 메시지다.

답의 골격: "전송 계층의 중복은 설정으로, 비즈니스 레벨의 중복은 멱등 키 설계로"

한 걸음 더 — transactional.id를 주면 세션이 바뀌어도 신원이 유지되어 좀비 프로듀서를 차단할 수 있다. 다만 이것도 "같은 이벤트를 다시 send()하는 코드"를 막아주지는 않는다.

Kafka 트랜잭션으로 DB 쓰기까지 묶을 수는 없나요?힌트: 방향(발행/소비)에 따라 답이 다르다

없다. Kafka 트랜잭션의 원자성 범위는 Kafka 토픽 쓰기와 컨슈머 오프셋 커밋까지다. DB 커밋은 그 안에 들어올 수 없으므로 "DB는 커밋됐는데 오프셋 커밋은 실패"라는 어긋남은 그대로 남는다.

DB와 Kafka에 걸친 정합성은 방향별로 다른 패턴을 쓴다.

발행 측(DB 커밋과 이벤트 발행의 원자성) — Transactional Outbox + CDC. 보낼 메시지를 같은 DB의 outbox 테이블에 INSERT해 업무 데이터 변경과 발행 예약을 한 트랜잭션으로 묶고, 별도 프로세스가 그 테이블을 읽어 Kafka로 발행한다. (28-transactional-outbox-cdc-kafka.md)

소비 측(이벤트 수신과 DB 반영의 중복 제거) — 멱등 컨슈머. 8절의 processed_event 방식이다. (04-idempotent-consumer-implementation.md)

"양쪽을 한 트랜잭션으로" 대신 "각 경계에서 각자의 패턴으로"
결제 시스템에서 "정확히 한 번 결제"를 요구받으면 어떻게 설계하나요? 시니어 변별힌트: 요구사항을 다른 문제로 번역해야 한다

전달 계층에 exactly-once를 요구하지 않고, 도메인 계층에서 멱등성으로 달성한다.

결제 이벤트에 프로듀서가 발급한 고유 ID(멱등 키)를 싣고, 컨슈머는 처리 이력과 결제 반영을 같은 DB 트랜잭션으로 묶어 같은 키의 두 번째 처리를 무시한다. PG 같은 외부 결제사 호출에는 그쪽이 제공하는 idempotency key를 전달해 외부 경계에서도 중복을 흡수한다.

이벤트 생성 시 멱등 키 발급→컨슈머 중복 차단→외부 API idempotency key

즉 "정확히 한 번 결제"는 인프라 설정이 아니라 멱등 키가 이벤트 생성부터 외부 호출까지 관통하는 설계로 만든다.

요구사항을 "전달 보장 문제"가 아니라 "멱등성 설계 문제"로 번역하는 것이 시니어 답변이다
at-most-once를 일부러 선택하는 경우가 실제로 있나요?힌트: 비용 비교를 뒤집어 본다

있다. 유실 비용 < 중복·재처리 비용인 데이터가 그렇다.

  • 초 단위 메트릭 — 한 점이 빠져도 그래프는 유효하다.
  • 차량·배달원 위치 — 최신값만 의미가 있고, 과거 값 재전송은 오히려 노이즈다.
  • 대량 로그 샘플링 — 애초에 전수가 목적이 아니다.

이런 데이터에 at-least-once 인프라 비용(재시도, 멱등 처리, 커밋 관리)을 쓰는 건 과설계다.

답의 골격: "모든 데이터가 같은 보장을 받을 필요는 없다 — 데이터의 가치에 보장 수준을 맞춘다"
왜 시스템 경계를 넘는 exactly-once가 "어렵다"가 아니라 "원리적으로 불가능"한가요? 가산점힌트: 확인서의 확인서를 계속 요구해 보라

두 독립 시스템에 걸친 원자적 확정은 분산 합의 문제이고, 불확실한 채널 위에서 두 참여자가 완전한 합의에 도달할 수 없다는 두 장군 문제와 같은 구조다.

1절에서 본 "응답이 안 왔을 때 구별할 수 없다"가 바로 이 문제의 최소 형태다. 그래서 해법은 합의를 완성하는 것이 아니라, 합의가 어긋나도 결과가 같아지도록 만드는 것 — 멱등성이다.

면접에서는 여기까지 말하고 "그래서 실무는 at-least-once + 멱등 처리로 수렴합니다"로 착지하면 깔끔하다.

isolation.level=read_committed로 바꾸면 무엇이 느려지나요? 가산점힌트: 6절의 LSO 그림을 떠올려라

처리 속도가 느려지는 게 아니라 "보이기까지의 지연"이 늘어난다. read_committed 컨슈머는 안정 오프셋(LSO)을 넘어서 읽지 않는다 — LSO는 "그 앞에는 결말이 안 난 트랜잭션이 하나도 없는" 지점이다.

따라서 트랜잭션이 커밋(또는 중단)되어야 그 구간이 비로소 보인다. 결과적으로 체감 지연이 트랜잭션 주기만큼 늘어나고, 프로듀서가 트랜잭션을 열어둔 채 죽으면 transaction.timeout.ms로 강제 종료될 때까지 LSO가 멈춰 뒤 메시지 전체가 막힌다.

트랜잭션을 크게·오래 잡을수록 정확성은 그대로지만 소비 지연이 비례해서 커진다

운영 팁 — EOS를 켠 파이프라인에서 랙이 톱니처럼 오르내린다면 컨슈머 성능 문제가 아니라 트랜잭션 커밋 주기를 먼저 의심한다.

acks=all이면 유실이 절대 없나요? 함정힌트: "전부"가 몇 대인지는 고정값이 아니다

조건부다. acks=all은 "동기화 대상 복제본(ISR) 전부가 받으면 성공"인데, ISR의 크기는 고정이 아니다. 팔로워들이 지연되어 ISR에서 빠지고 리더 하나만 남은 상태라면, acks=all도 사실상 리더 한 대의 확인과 같아진다. 그 상태에서 리더가 죽으면 유실이다.

그래서 min.insync.replicas를 함께 건다 — "최소 이만큼은 동기화되어 있어야 쓰기를 받는다"는 하한선이다. 하한선에 못 미치면 브로커가 쓰기를 거절하므로, 조용한 유실 대신 명시적인 실패를 받게 된다.

acks=all은 혼자 쓰는 설정이 아니라 min.insync.replicas와 한 쌍이다

내구성 관점의 상세는 27-producer-acks-durability.md에서 다룬다. 이 질문의 요점은 "보장 문구의 전제 조건을 읽는 습관" — 이 페이지 전체의 주제와 같다.

멱등 프로듀서를 켜면 메시지 순서도 보장되나요?힌트: 재전송은 순서를 흔드는 대표 원인이다

파티션 단위로는 그렇다. 멱등성을 끄고 재시도를 켜면, 먼저 보낸 배치가 실패해 재전송되는 사이에 뒤 배치가 먼저 저장되어 순서가 뒤집힐 수 있다.

enable.idempotence=true면 브로커가 시퀀스 번호로 순서를 검증한다 — 기대하는 다음 번호가 아니면 받아들이지 않으므로 재정렬이 일어나지 않는다. 이 보장이 성립하려면 max.in.flight.requests.per.connection이 5 이하여야 하고, 멱등성을 켜면 이 제약이 함께 적용된다.

멱등 프로듀서 = 재전송 중복 제거 + 파티션 내 순서 유지 두 가지를 같이 준다

단, 이것은 한 파티션 안의 순서다. 토픽 전체 순서가 아니다 — 순서 보장의 단위 이야기는 24-message-ordering-partition-key.md.

EOS를 켜면 성능이 얼마나 떨어지나요?힌트: 숫자를 말하는 것보다 비용의 출처를 세는 게 낫다

숫자를 단정하지 말고 비용의 출처를 세는 편이 정확하다. 워크로드(메시지 크기, 배치 크기, 트랜잭션 주기)에 따라 크게 달라지기 때문에, "측정하겠다"가 맞는 답이다. 대신 어디서 비용이 나오는지는 세 가지로 지목할 수 있다.

① 트랜잭션 코디네이션 — beginTransaction/commitTransaction마다 코디네이터와의 왕복이 생긴다.
② 마커 기록 — 관련된 각 파티션 로그에 커밋/중단 마커를 쓴다. 트랜잭션이 잦고 작을수록 마커 비중이 커진다.
③ 소비 측 지연 — read_committed 컨슈머는 LSO에 막혀 트랜잭션이 닫힐 때까지 기다린다.

튜닝의 방향: 트랜잭션을 너무 잘게 쪼개면 ①②가, 너무 크게 잡으면 ③이 커진다

그래서 판단 기준은 "집계 정확성이 이 비용을 정당화하는가"다. 대부분의 업무 이벤트는 at-least-once + 멱등 처리가 더 싸고 더 튼튼하다.

멱등 키는 무엇으로 잡아야 하나요? 오프셋을 써도 되나요? 함정힌트: 같은 "사건"에 항상 같은 값이 붙어야 한다

이벤트를 만든 쪽이 생성 시점에 한 번 발급한 고유 ID가 정답이다. 조건은 하나 — 같은 비즈니스 사건에는 몇 번을 재발행해도 같은 값이 붙어야 한다.

오프셋은 부적절하다. 오프셋은 "그 메시지가 로그에 놓인 위치"일 뿐이라, 같은 사건을 다시 발행하면 다른 오프셋이 붙는다. 재발행·파티션 변경·다른 토픽으로의 복사 같은 상황에서 같은 사건이 다른 키로 보이게 되어 중복 차단이 무너진다.

업무 자연키(예: 주문 ID)만 쓰는 것도 위험하다. 같은 주문에 대해 생성·수정·취소 같은 서로 다른 이벤트가 오면 두 번째 이벤트가 중복으로 오인되어 통째로 버려진다. 자연키를 쓸 거면 "주문 ID + 이벤트 종류 + 버전"처럼 사건을 유일하게 지목하는 조합이어야 한다.

멱등 키의 조건: 사건마다 유일 + 재발행해도 불변 + 생성 측이 발급

저장·정리(오래된 이력 삭제) 전략을 포함한 구현 상세는 04-idempotent-consumer-implementation.md.

한 줄 요약
전달 의미론은 "응답이 안 왔을 때 재전송할 것인가"라는 갈림길에서 유실과 중복 중 무엇을 감수할지 고른 결과에 붙인 이름이고, Kafka의 exactly-once는 멱등 프로듀서(재전송 중복 제거)와 트랜잭션(파티션 쓰기 + 오프셋 커밋의 원자적 묶음)으로 Kafka 경계 안(읽기-처리-쓰기)에서만 성립하는 보장이므로 — PostgreSQL과 외부 API가 있는 현실 시스템의 정답은 exactly-once delivery를 좇는 것이 아니라 at-least-once + 멱등 처리로 exactly-once 효과를 만드는 것이다.
