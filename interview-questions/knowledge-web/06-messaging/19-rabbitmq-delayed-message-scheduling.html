지연 메시지와 스케줄링 — TTL+DLX, delayed message 플러그인, 그리고 Kafka로는 왜 어려운가
축은 하나다 — 타이머를 브로커가 들고 있는가, 애플리케이션이 들고 있는가. 여기서 "취소할 수 있는가"가 곧바로 따라 나온다

면접 질문: "RabbitMQ에서 지연 메시지·스케줄링을 어떻게 구현하나요? (TTL + DLX vs delayed message exchange 플러그인) 같은 요구를 Kafka로 풀면 왜 어려운가요?"

핵심 관전 포인트 — "30분 뒤 미결제 주문 자동 취소", "3일 뒤 만료 알림" 같은 요구는 큐로 푸는 것이 자연스러워 보이지만, 큐에는 원래 시간 개념이 없다. 큐는 들어온 순서대로 즉시 내보낸다. 그래서 RabbitMQ에서는 우회가 필요하고 방법이 셋이다 — ① 컨슈머 없는 큐에 TTL을 걸어 만료되면 DLX로 흘리는 대기 큐 방식(브로커 기본 기능만으로 되지만 지연 시간마다 큐를 따로 만들어야 한다), ② x-delayed-message 플러그인으로 메시지마다 지연을 지정하는 방식(유연하지만 대량·장기 지연에 약하다), ③ DB에 예약 행을 넣고 스케줄러가 시각이 되면 발행하는 방식(가장 무겁지만 취소·조회·변경이 가능한 유일한 방법). 그리고 결정적 판단 기준이 하나 있다 — 예약을 취소해야 하는가. 브로커에 넣은 지연 메시지는 되돌릴 수 없다. 사용자가 5분 만에 결제하면 30분 뒤 취소 메시지는 이미 날아가고 있고, 그때 할 수 있는 것은 소비 시점에 "아직 유효한가"를 다시 확인하는 것뿐이다.
  • 1
    전제부터 끊어 말한다. 큐에는 시간 개념이 없다. 큐의 기본 계약은 "넣으면 가능한 한 빨리 내보낸다"이므로 "이건 30분 뒤에 주세요"라는 지시를 받을 자리가 애초에 없다. 그래서 RabbitMQ의 지연 구현은 전부 정식 기능이 아니라 우회이고, 우회마다 잃는 것이 다르다는 것이 이 질문의 본질이다.
  • 2
    방법은 셋, 축은 하나다 — 타이머를 누가 드는가. ① TTL + DLX 대기 큐는 브로커가 든다(지연은 큐 단위 고정, 종류마다 큐를 판다). ② delayed message 플러그인도 브로커가 들지만 메시지마다 x-delay를 자유롭게 준다. ③ DB + 스케줄러는 애플리케이션이 든다 — 예약이 테이블의 한 행이 되므로 조회·변경·취소가 전부 SQL이다.
  • 3
    선택 기준과 한계로 닫는다. "취소·조회가 필요하거나 지연이 길거나 대량이면 DB"가 한 줄 답이고, 브로커 방식을 유지해야 한다면 지연 메시지를 "명령"이 아니라 "지금도 유효한지 확인하라는 요청"으로 설계해 소비 시점에 상태와 버전을 검증한다. Kafka는 오프셋이 "여기까지 처리했다"는 단일 숫자라 중간 하나만 미뤘다 돌아오는 것을 표현할 수 없어, 지연을 컨슈머가 pause/resume으로 직접 져야 한다.

0. 질문 + 출제 의도 · 먼저 깨야 할 오해

질문 — "RabbitMQ에서 지연 메시지·스케줄링을 어떻게 구현하나요? (TTL + DLX vs delayed message exchange 플러그인) 같은 요구를 Kafka로 풀면 왜 어려운가요?"

출제 의도 — "5분 뒤 재시도", "3일 뒤 만료 알림" 같은 흔한 요구를 브로커 기능으로 푸는 법을 아는지 본다. TTL+DLX의 head-of-line 함정까지 짚으면 실제로 구현해본 사람이다. 같은 요구가 Kafka에서 왜 어려운지 대비할 수 있으면 도구 선택의 근거를 갖춘 것이다.

먼저 깨야 할 오해 셋

오해 ①
"큐에 넣으면서 30분 뒤에 달라고 하면 되지 않나"
그런 필드가 없다. 큐의 계약은 즉시 배달이다. RabbitMQ의 모든 지연 구현은 "배달을 늦추는 기능"이 아니라 "다른 기능을 엮어 만든 타이머"다.
오해 ②
"플러그인만 깔면 스케줄러가 생긴다"
범용 스케줄러가 아니다. 대량 대기·장기 지연·고가용성은 이 플러그인이 상정한 사용처가 아니고, 매니지드 서비스에서는 설치 자체가 막혀 있을 수 있다.
오해 ③
"예약했으니 취소도 되겠지"
브로커에 넣은 예약은 되돌릴 수 없다. 취소 API가 없다. 취소가 요구사항이면 그것은 우회가 아니라 도구 선택 자체가 달라지는 문제다.
이 페이지를 읽는 방법 세 방법을 각각 외우려 하면 잘 안 붙는다. 2절의 축 하나(타이머를 누가 드는가)를 먼저 잡고, 그 위에 세 방법을 얹으면 표의 모든 행이 그 축에서 유도된다. 특히 "취소 가능 여부"는 외울 항목이 아니라 축에서 나오는 결과다.

1. 전제 — 큐에는 시간이 없다

메시지 큐의 기본 계약은 "넣으면 컨슈머가 곧 가져간다"이다. 큐는 가능한 한 빨리 메시지를 내보내려 한다. 지연이라는 개념은 이 계약과 정면으로 어긋난다.

비유 — 큐는 컨베이어 벨트다 벨트에 물건을 올리면 벨트는 최대한 빨리 반대편 끝으로 보낸다. 물건에 "30분 뒤에 내보내 주세요"라고 적을 칸이 없다. 그래서 지연을 만들려면 벨트 옆에 별도 장치를 붙여야 한다 — 타이머가 달린 대기실(TTL 대기 큐)을 하나 두거나, 물건을 붙들었다 놓아주는 문(플러그인 exchange)을 달거나, 아예 벨트 밖 수첩에 약속 시각을 적어두고(DB) 때가 되면 사람이 올려놓는 것이다. 세 방법의 차이는 여기서 다 나온다.

2. 축 하나 — 타이머를 누가 들고 있는가

세 방법을 하나씩 보기 전에 축을 하나 세워두면 나머지가 전부 그 위에 얹힌다. 축은 "시간을 재는 일을 브로커에 맡기는가, 애플리케이션이 직접 지는가"다.

축에서 곧바로 유도되는 결론

시간을 든 쪽이 예약의 소유자다. 브로커가 들면 예약은 내부 상태가 되어 우리 손이 닿지 않고, 애플리케이션이 들면 예약은 우리 데이터가 되어 마음대로 다룰 수 있다.
그래서 "취소 가능 여부"는 표에서 외울 항목이 아니라 축에서 계산되는 값이다. 면접에서 표를 통째로 외운 사람과 축 하나로 설명하는 사람은 여기서 갈린다.

3. 방법 ① — TTL + DLX 대기 큐

3-1. 원리 — 두 기능을 엮으면 타이머가 된다

이 방법은 지연 기능이 아니라 두 개의 평범한 기능을 조합한 것이다. 조합의 재료는 이렇다.

재료 1 — 메시지 TTL
RabbitMQ는 메시지 TTL이 만료되면 그 메시지를 dead letter로 처리한다. 그냥 지우는 것이 아니라 "죽은 편지"로 분류한다는 점이 핵심이다.
재료 2 — DLX(dead letter exchange)
큐에 x-dead-letter-exchange가 설정되어 있으면 dead letter가 버려지지 않고 그 exchange로 흘러간다.
컨슈머가 없는 큐 + TTL + DLX = 지연 배달

컨슈머가 없으므로 메시지는 아무에게도 배달되지 않고 그 자리에서 TTL이 다하기를 기다린다. 만료되는 순간 dead letter가 되고, DLX를 통해 진짜 목적지로 이동한다. 즉 "만료"라는 종료 이벤트를 "출발" 신호로 뒤집어 쓴 것이다.

3-2. 구현

선언 대기 큐 · 실행 큐 · 바인딩 (Spring AMQP)
// 대기 큐 — 컨슈머를 붙이지 않는다
@Bean Queue cancelWaitQueue() {
    return QueueBuilder.durable("order.cancel.wait")
            .ttl(30 * 60 * 1000)                       // 이 큐의 모든 메시지는 30분 뒤 만료
            .deadLetterExchange("order.exchange")      // 만료되면 여기로
            .deadLetterRoutingKey("order.cancel")      // 실행 큐로 라우팅
            .build();
}

// 실행 큐 — 여기에만 컨슈머를 붙인다
@Bean Queue cancelQueue() { return QueueBuilder.durable("order.cancel").build(); }

@Bean Binding cancelBinding(TopicExchange orderExchange) {
    return BindingBuilder.bind(cancelQueue()).to(orderExchange).with("order.cancel");
}

// 예약: 대기 큐에 직접 넣는다 (기본 exchange 사용 — 라우팅 키 = 큐 이름)
public void scheduleCancel(Long orderId) {
    rabbitTemplate.convertAndSend("", "order.cancel.wait", new CancelCommand(orderId));
}
놓치기 쉬운 인자 — x-dead-letter-routing-key 이 값을 지정하지 않으면 메시지의 원래 라우팅 키가 그대로 재사용된다. 위 코드처럼 기본 exchange로 넣었다면 원래 키는 order.cancel.wait이므로, DLX에서 매칭되는 바인딩이 없어 조용히 사라지거나 — 더 나쁘게는 대기 큐가 그 키로 바인딩되어 있으면 자기 자신으로 돌아가 무한 루프가 된다. 대기 큐를 만들 때 DLX 라우팅 키는 항상 명시한다.

3-3. 반드시 알아야 할 함정 — head-of-line blocking 함정

여기서 실무자와 책으로 배운 사람이 갈린다. 사실 한 줄은 이렇다 — RabbitMQ는 큐의 맨 앞 메시지만 만료 여부를 검사한다. 뒤쪽 메시지는 앞의 것이 나가야 검사 대상이 된다.

비유 — 차단봉이 하나뿐인 주차장 출구 출구 차단봉은 맨 앞 차 한 대만 확인한다. 앞차의 정산이 30분 걸리면, 뒤차가 이미 정산을 끝냈어도 나갈 수 없다. 큐의 만료 검사도 똑같다 — 준비된 것과 나갈 수 있는 것은 다르다.

큐 단위 TTL(x-message-ttl)이면 모든 메시지의 수명이 같으므로 앞의 것이 항상 먼저 만료되어 문제가 없다. 그런데 메시지 단위 TTL(expiration 속성)로 서로 다른 지연을 주면 무너진다.

문제 대기 큐 하나에 메시지별 TTL을 섞는다
// 대기 큐는 하나 — TTL을 큐에 박지 않았다
@Bean Queue waitQueue() {
    return QueueBuilder.durable("retry.wait")
            .deadLetterExchange("retry.exchange")
            .deadLetterRoutingKey("retry.run")
            .build();
}

// 호출부가 원하는 지연을 메시지마다 지정한다 — 편해 보인다
public void scheduleRetry(Object payload, Duration delay) {
    rabbitTemplate.convertAndSend("", "retry.wait", payload, m -> {
        m.getMessageProperties()
         .setExpiration(String.valueOf(delay.toMillis()));  // 메시지 단위 TTL
        return m;
    });
}

// 실제로 벌어지는 일
//   scheduleRetry(a, 30분)  ← 큐 맨 앞에 들어간다
//   scheduleRetry(b, 5초)   ← 뒤에 선다
//   scheduleRetry(c, 5초)   ← 뒤에 선다
// → b, c는 a가 만료되는 30분 뒤에야 흘러나간다
// → "재시도가 왜 안 되지?"로 며칠을 태운다
개선 지연 값마다 대기 큐를 따로 판다
// 큐에 TTL을 박는다 = 그 큐 안의 수명이 전부 같아진다
private Queue delayQueue(String name, int ttlMs) {
    return QueueBuilder.durable(name)
            .ttl(ttlMs)                          // 큐 단위 TTL
            .deadLetterExchange("retry.exchange")
            .deadLetterRoutingKey("retry.run")
            .build();
}

@Bean Queue wait5s()  { return delayQueue("wait.5s",  5_000); }
@Bean Queue wait30s() { return delayQueue("wait.30s", 30_000); }
@Bean Queue wait5m()  { return delayQueue("wait.5m",  300_000); }

// 호출부는 "가장 가까운 등급"의 큐를 고른다
public void scheduleRetry(Object payload, int attempt) {
    String q = switch (attempt) {          // 백오프 등급
        case 1 -> "wait.5s";
        case 2 -> "wait.30s";
        default -> "wait.5m";
    };
    rabbitTemplate.convertAndSend("", q, payload);
}

대기 큐의 절대 규칙

대기 큐 하나에는 같은 지연 시간만 담는다

5초·30초·5분이 필요하면 대기 큐를 세 개 만든다. 지연 값이 몇 종류로 고정되어 있으면(재시도 백오프처럼) 이 방식이 잘 맞는다.
반대로 사용자마다 임의의 시각을 예약해야 한다면 큐를 무한정 만들 수 없으므로 이 방식은 부적합하다. — 이 한 문장이 방법 ②와 ③으로 넘어가는 이유다.

3-4. 장단점 정리

장점

  • 플러그인 없이 기본 기능만으로 된다 — 매니지드 서비스에서도 항상 쓸 수 있다
  • 대기 큐도 그냥 큐이므로 대량으로 쌓여도 큐의 일반적 특성(디스크로 내려감)이 그대로 적용된다
  • durable + persistent면 브로커 재시작에도 살아남는다
  • 관리 UI에서 대기 건수가 그대로 보인다 (큐 depth로 관측 가능)

단점

  • 지연 종류마다 큐가 필요하다 — 임의 시각 예약에는 못 쓴다
  • 정확도가 높지 않다 — 만료 검사가 큐 앞머리에서만 일어나므로 부하 상황에서 늦어질 수 있다
  • 만료 후 DLX 라우팅 → 실행 큐 적재 → 배달의 단계에도 시간이 든다
  • 예약을 취소할 수 없다

4. 방법 ② — delayed message exchange 플러그인

4-1. 원리 — exchange가 메시지를 붙들고 있는다

rabbitmq_delayed_message_exchange 플러그인을 설치하면 x-delayed-message라는 새 exchange 타입을 쓸 수 있다. 이 exchange에 보낸 메시지는 바로 라우팅되지 않고 exchange가 붙들고 있다가, 지정한 지연이 지나면 그때 라우팅한다. 지연은 메시지 헤더 x-delay에 밀리초로 넣는다.

구현 exchange 선언과 메시지 단위 지연 발행
// exchange 선언 — 내부적으로 어떤 라우팅을 흉내 낼지도 지정한다
@Bean CustomExchange delayedExchange() {
    Map<String, Object> args = new HashMap<>();
    args.put("x-delayed-type", "topic");   // 지연 후에는 topic처럼 라우팅
    return new CustomExchange("order.delayed", "x-delayed-message", true, false, args);
}

// 발행 — 메시지마다 다른 지연을 줄 수 있다
public void scheduleCancel(Long orderId, Duration delay) {
    rabbitTemplate.convertAndSend("order.delayed", "order.cancel",
        new CancelCommand(orderId),
        message -> {
            message.getMessageProperties()
                   .setHeader("x-delay", delay.toMillis());  // 이 메시지만의 지연(ms)
            return message;
        });
}

4-2. 한계 — 언제 쓰면 안 되는가 함정

플러그인은 편하지만 범용 스케줄러가 아니다. 다음 네 경우에는 피해야 한다.

① 대량의 지연 메시지
지연 중인 메시지는 exchange가 자체 저장소에 들고 있다. 수십만~수백만 건이 동시에 대기하는 상황은 이 구조가 상정한 사용처가 아니다. 큐와 달리 일반적인 큐 관리 기능(디스크로 내리기, 길이 제한)이 그대로 적용되지 않는다.
② 아주 긴 지연
며칠~몇 달짜리 예약을 브로커에 쌓아두는 것은 좋은 설계가 아니다. 그동안 브로커를 업그레이드하거나 재구축하면 그 예약들의 운명이 불투명해진다.
③ 고가용성이 필요한 경우
지연 중인 메시지의 복제·이관이 일반 큐만큼 매끄럽지 않다. 클러스터 구성과 버전에 따라 동작이 다를 수 있으므로 쓰기 전에 반드시 자기 환경에서 노드 장애 시나리오를 시험해야 한다.
④ 운영 정책
커뮤니티 플러그인이므로 매니지드 서비스에서는 설치가 불가능할 수 있다. 클라우드 관리형 RabbitMQ를 쓴다면 지원 여부부터 확인해야 한다.

플러그인 금지 4상황 — "대 · 장 · 가 · 정"

대량 · 장기 · 가용성 · 정책. 넷 중 하나라도 걸리면 플러그인이 아니라 DB 스케줄러로 간다.
반대로 말하면 이 넷에 걸리지 않는 짧고 소량인 지연에서는 플러그인이 가장 손이 덜 간다.

적합한 자리 초~분 단위의 짧은 지연, 그리고 동시 대기 건수가 크지 않은 경우다. 재시도 백오프, 몇 분 뒤 리마인드, 짧은 유예 후 처리 같은 것들이다. 이 범위 안에서는 TTL 대기 큐보다 훨씬 쓰기 편하다 — 큐를 종류별로 만들 필요가 없고, 지연 값이 코드에서 그때그때 결정될 수 있다.

5. 방법 ③ — DB + 스케줄러, 그리고 조합

5-1. 언제 이것이 정답인가

앞의 두 방법에는 공통된 근본 한계가 있다. 브로커에 넣은 지연 메시지는 취소할 수도, 조회할 수도, 변경할 수도 없다. 그런데 실무 요구는 대개 이렇게 생겼다 — 그리고 셋 다 브로커로는 불가능하고, DB라면 전부 SQL 한 줄이다.

실무 요구 vs 브로커 예약 — 왼쪽 네 문장 중 하나라도 나오면 DB로 간다
요구브로커 예약(①②)DB 예약(③)
"결제하면 30분 뒤 취소 예약을 없애야 한다"불가능UPDATE ... SET status='CANCELLED'
"예약된 알림이 지금 몇 건인지 보고 싶다"사실상 불가SELECT count(*) WHERE status='PENDING'
"발송 시각을 바꿔야 한다"불가능UPDATE ... SET execute_at=?
"이 사용자의 예약을 전부 지워야 한다" (탈퇴)불가능DELETE ... WHERE user_id=?

5-2. 구조

스키마 예약 테이블 — 인덱스가 이 방식의 성패를 가른다
CREATE TABLE scheduled_task (
    id            BIGSERIAL PRIMARY KEY,
    task_type     VARCHAR(50)  NOT NULL,   -- ORDER_CANCEL, EXPIRY_NOTIFY ...
    payload       JSONB        NOT NULL,
    execute_at    TIMESTAMPTZ  NOT NULL,   -- 실행 예정 시각
    status        VARCHAR(20)  NOT NULL,   -- PENDING, PUBLISHED, CANCELLED
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now()
);

-- 스케줄러가 매번 때리는 쿼리이므로 인덱스가 필수다
CREATE INDEX idx_scheduled_task_due
    ON scheduled_task (execute_at)
    WHERE status = 'PENDING';            -- 부분 인덱스: 처리 끝난 행은 인덱스에서 빠진다
문제 단일 인스턴스 가정 + 상한 없음 + 직접 처리
@Scheduled(fixedDelay = 10_000)
@Transactional
public void publishDueTasks() {
    List<ScheduledTask> due = repository.findAllDue(Instant.now());
    // ① 상한이 없다 — 밀린 20만 건을 한 번에 집는다
    // ② 다른 인스턴스도 같은 행을 집는다 (중복 실행)

    for (ScheduledTask task : due) {
        notificationService.send(task);   // ③ 스케줄러가 직접 무거운 일을 한다
        task.markPublished();             //    한 건이 3초 걸리면 뒤가 전부 밀린다
    }
}

// 실제 사고 시나리오
//   배포로 스케줄러가 20분 멈춤 → 재개 순간 밀린 20만 건을 한 번에 집음
//   → 트랜잭션이 수 분간 열려 있고 (긴 트랜잭션)
//   → 인스턴스 3대가 같은 20만 건을 각각 처리하고
//   → 다운스트림(알림 API)이 그 순간 무너진다
개선 SKIP LOCKED + 배치 상한 + 큐에 위임
@Scheduled(fixedDelay = 10_000)   // 이 주기가 정확도의 상한이다
@Transactional
public void publishDueTasks() {
    List<ScheduledTask> due = repository.findDueTasks(
            Instant.now(), PageRequest.of(0, 500));   // 처리 상한

    for (ScheduledTask task : due) {
        rabbitTemplate.convertAndSend(                     // 실행은 큐에 넘긴다
                task.exchange(), task.routingKey(), task.payload());
        task.markPublished();
    }
}

// 여러 인스턴스가 같은 행을 집지 않게 한다
@Query(value = """
    SELECT * FROM scheduled_task
     WHERE status = 'PENDING' AND execute_at <= :now
     ORDER BY execute_at
     LIMIT :size
     FOR UPDATE SKIP LOCKED""", nativeQuery = true)
List<ScheduledTask> findDueTasks(Instant now, int size);

// 취소는 그냥 UPDATE 한 줄 — 브로커로는 불가능한 그 일
public void cancelScheduledCancel(Long orderId) {
    repository.cancelPending("ORDER_CANCEL", orderId);
}

컴포넌트 증가

5-4. 조합이 실전 답인 경우가 많다 가산점

셋 중 하나를 고르는 문제로 보기 쉽지만, 둘을 섞는 것이 실제로는 가장 흔하다. 각자 잘하는 일을 맡기는 구조다.

6. 취소할 수 없다는 문제 — 소비 시점 유효성 검사

여기까지가 구현 방법이다. 이제 세 방법을 모두 손에 쥔 상태에서 브로커에 시간을 맡기는 두 방법(①②)이 공통으로 못 하는 일을 본다. 2절에서 세운 축의 직접적인 결과이고, 사정상 DB 방식으로 갈 수 없을 때 그 제약을 어떻게 견디는지가 실무의 답이 된다.

6-1. 상황 — 25분 뒤에 도착하는 낡은 명령

30분 뒤 주문 취소를 예약했는데 사용자가 5분 만에 결제했다. 예약된 메시지는 이미 브로커 안에 있고 되돌릴 수 없다. 25분 뒤 그 메시지가 도착하면 워커는 이미 결제된 주문을 취소하려 든다.

6-2. 해법 — 실행할 때 다시 확인한다

문제 메시지가 왔으니 실행한다
@RabbitListener(queues = "order.cancel")
public void handle(CancelCommand cmd) {
    orderService.cancel(cmd.getOrderId());   // 이미 결제된 주문도 취소해버린다
}

// 이 코드가 전제하는 것
//   "메시지가 도착했다 = 지금도 그 일을 해야 한다"
// 지연 메시지에서는 이 전제가 깨진다.
// 예약과 실행 사이 30분 동안 세상이 바뀌기 때문이다.
개선 실행 직전에 현재 상태를 확인한다
@RabbitListener(queues = "order.cancel")
public void handle(CancelCommand cmd) {
    Order order = orderRepository.findById(cmd.getOrderId()).orElse(null);
    if (order == null) return;                  // 이미 삭제됨

    if (order.getStatus() != OrderStatus.PENDING_PAYMENT) {
        // 예약할 때는 미결제였지만 그 사이 상태가 바뀌었다.
        // 이 명령은 유효기간이 지난 것이므로 조용히 버린다.
        log.debug("취소 예약 무효화: orderId={}, 현재 상태={}",
                  cmd.getOrderId(), order.getStatus());
        return;
    }
    orderService.cancel(cmd.getOrderId());
}

이 패턴에는 이름이 있다

지연 메시지는 "명령"이 아니라 "확인 요청"으로 취급하라

메시지의 뜻이 "취소하라"가 아니라 "취소해야 하는지 확인하라"가 되면, 취소 불가라는 제약이 문제가 되지 않는다.
메시지 클래스 이름을 CancelOrderCommand가 아니라 CheckPaymentTimeoutCommand처럼 지으면 코드를 읽는 사람에게도 이 계약이 전달된다 — 이름 하나로 팀 전체의 오용을 줄일 수 있다.

6-3. 한 걸음 더 — 상태만으로 부족한 경우 시니어 변별

상태 값만 보면 "결제 → 취소 → 다시 주문"처럼 같은 상태로 돌아온 경우를 구분하지 못한다. 그래서 예약 시점의 상태 버전을 메시지에 담고, 소비 시점에 비교하면 완전해진다.

보강 예약 시점 버전을 함께 담아 비교한다
// 예약할 때의 버전을 함께 담는다
new CancelCommand(orderId, order.getVersion());

// 소비할 때 비교 — 그 사이 상태가 한 번이라도 바뀌었으면 무효
if (order.getVersion() != cmd.getVersionAtSchedule()) return;

// 왜 상태 비교만으로는 부족한가
//   10:00 예약 (상태 PENDING_PAYMENT, version 3)
//   10:05 결제 → PAID (version 4)
//   10:10 결제 취소 → PENDING_PAYMENT (version 5)  ← 상태가 원래대로 돌아왔다
//   10:30 낡은 취소 명령 도착 → 상태만 보면 "유효"로 판정된다
//   → version 3 != 5 이므로 버전 비교에서는 걸러진다
면접 답변으로 쓰는 한 문장 가산점 "브로커에서 취소가 안 되므로 소비 시점 검증으로 대체한다" — 이 설계는 지연 메시지를 실제로 운영해본 사람의 답이다. 여기에 "상태 값만으로는 왕복한 경우를 못 잡아서 버전을 함께 실어 보낸다"까지 붙이면 낙관적 락과 이벤트 순서 문제를 함께 이해하고 있다는 신호가 된다.

7. Kafka로는 왜 어려운가

앞의 것이 RabbitMQ 안에서 감수해야 할 한계였다면, 이쪽은 애초에 어느 브로커를 고를지의 근거다. 두 이야기를 나란히 두면 "이 방법들의 한계는 여기까지지만, 그럼에도 다른 도구보다는 낫다"는 판단이 한 줄로 이어진다.

7-1. 구조적 이유 — 오프셋은 단일 숫자다

Kafka의 파티션은 순서가 고정된 로그이고, 컨슈머는 오프셋을 순서대로 전진시키며 읽는다. 여기에 "이 레코드는 30분 뒤에 처리"라는 개념을 넣을 자리가 없다.

7-2. Kafka에서 쓰는 우회

1
단계별 지연 토픽. retry-5s, retry-1m, retry-10m 같은 토픽을 만들고, 각 토픽의 컨슈머가 레코드의 타임스탬프를 보고 아직 시간이 안 됐으면 처리를 멈춘다. 구체적으로는 컨슈머가 pause()로 파티션 소비를 일시 중지하고 정해진 시간이 지난 뒤 resume()한다. 지연 시간이 토픽마다 고정되어 있으므로 파티션 앞머리 레코드가 준비되면 그 뒤도 준비된 상태라는 성질을 이용한다.
RabbitMQ의 TTL 대기 큐와 발상은 같지만, 결정적으로 다른 점 지연을 브로커가 아니라 컨슈머가 직접 관리해야 한다. 그래서 두 가지가 따라붙는다 — ① 컨슈머가 재시작하면 pause 상태가 사라지고 처음부터 다시 판단해야 하며, ② max.poll.interval.ms를 넘기지 않도록 주의해야 한다(오래 멈춰 있으면 그룹에서 쫓겨나 리밸런싱이 일어난다). 지연 시간이 이 값보다 길면 그 구조 자체가 성립하지 않는다.
2
외부 스케줄러. 결국 DB나 별도 스케줄러를 두는 방식으로 가는 경우가 많다. 이 경우 Kafka는 "실행 시점의 전달 수단"일 뿐이고 지연 관리는 밖에서 한다. — RabbitMQ의 방법 ③과 정확히 같은 구조이고, 이것이 Kafka 환경에서 긴 지연을 다루는 사실상의 표준이다.

30초 답변 스크립트

"큐에는 시간 개념이 없어서 지연은 전부 우회로 만듭니다. RabbitMQ에서는 셋인데, 컨슈머 없는 큐에 TTL을 걸고 만료되면 DLX로 흘리는 대기 큐 방식, x-delayed-message 플러그인으로 메시지마다 x-delay를 주는 방식, DB에 예약 행을 넣고 스케줄러가 발행하는 방식입니다. 축은 타이머를 브로커가 드느냐 애플리케이션이 드느냐이고, 여기서 취소 가능 여부가 따라 나옵니다 — 브로커에 넣은 예약은 되돌릴 수 없어서, 취소·조회가 필요하면 DB 외에 답이 없습니다. TTL 방식은 브로커가 큐 앞머리만 만료 검사하기 때문에 한 대기 큐에 서로 다른 TTL을 섞으면 짧은 것이 긴 것 뒤에 갇힙니다. 그래서 지연 값마다 큐를 따로 팝니다. 브로커 방식을 유지해야 하면 지연 메시지를 '명령'이 아니라 '지금도 유효한지 확인하라는 요청'으로 설계해 소비 시점에 상태와 버전을 검증합니다. Kafka는 오프셋이 단일 숫자라 중간 하나만 미루는 표현이 안 돼서, 컨슈머가 pause/resume으로 직접 지연을 지고 max.poll.interval.ms까지 함께 신경 써야 합니다. 반대로 재처리가 필요하면 Kafka가 압도적입니다."

8-3. 꼬리질문 셀프 테스트

질문만 먼저 읽고 소리 내어 답해본 뒤 펼친다. 시니어 변별 표시가 붙은 것은 답의 깊이가 갈리는 지점이다.

TTL 대기 큐에서 지연 정확도는 얼마나 되나요?힌트: 검사가 일어나는 위치 하나, 만료 이후에 남은 단계 하나 — 이유가 둘이다

정확한 타이머가 아니다라고 답해야 한다. 이유는 둘이다.

① 만료 검사는 큐 앞머리에서 일어난다

  • 앞의 메시지가 나가야 뒤의 것이 검사된다
  • 큐 단위 TTL이면 순서가 맞아 문제가 적지만, 브로커가 바쁘면 검사가 늦어질 수 있다

② 만료 후 라우팅과 배달에도 시간이 든다

  • dead letter 처리 → DLX 라우팅 → 실행 큐 적재 → 컨슈머 배달
  • 실행 큐가 적체되어 있으면 그 대기 시간이 그대로 더해진다

그래서 초 단위 정확도를 요구하는 곳(경매 마감, 예약 발송 시각 준수)에는 부적합하다. 그런 요구에는 DB + 짧은 주기 스케줄러가 낫고, 정말 초 단위가 중요하면 실행 시각을 미리 계산해 여유를 두는 설계가 필요하다.

TTL은 "최소 이만큼은 기다린다"는 하한이지 "정확히 그때"라는 약속이 아니다
지연 메시지가 수십만 건 쌓이면 어떻게 되나요?힌트: 방식마다 "지연 중 메시지가 어디에 있는가"가 다르다 — 2절의 축을 다시 본다

방식마다 다르고, 그 차이는 "지연 중 메시지가 어디에 있는가"에서 나온다.

방식대량 시 거동판정
TTL 대기 큐그냥 큐이므로 일반적인 적체와 같은 문제를 겪는다 — 브로커 메모리를 쓰고, 임계치를 넘기면 alarm이 걸려 발행이 막힌다. 다만 큐의 저장 최적화(긴 큐를 디스크로 내리는 동작)가 적용되므로 어느 정도는 견딘다중간
플러그인exchange 자체가 지연 중인 메시지를 들고 있으므로, 대량 상황에 대한 대비가 큐만큼 되어 있지 않다쓰지 않는다
DB 스케줄러수백만 건도 인덱스만 맞으면 견딘다. 애초에 대량 데이터를 다루라고 만든 것이 DB다권장
대량이면 DB

한 걸음 더 나가면 좋은 답이 된다 — "대량이 예상되면 대기 큐에도 길이 상한(x-max-length)과 overflow 정책을 미리 정해둔다"는 관점이다. 상한이 없으면 지연 큐 적체가 브로커 전체의 발행 차단으로 번진다(한 큐의 문제가 전체 문제가 되는 경로).

예약을 취소해야 하는 요구가 있으면 어떻게 하나요? 시니어 변별힌트: 두 갈래로 답한다 — 도구를 바꾸는 답, 제약을 견디는 답. 그리고 지표 하나

두 갈래로 답한다.

1
취소가 자주 일어나고 정확해야 하면 DB 스케줄러를 쓴다. 브로커에는 애초에 취소 기능이 없으므로 우회가 아니라 도구 선택의 문제다.
2
브로커 방식을 유지해야 한다면 소비 시점 검증으로 대체한다. 6절에서 본 대로 메시지를 "명령"이 아니라 "확인 요청"으로 다루고, 상태와 버전을 비교해 무효한 것은 조용히 버린다.

여기에 한 가지 실무 관점을 덧붙이면 변별력이 생긴다. 무효 메시지가 쌓이면 자원 낭비라는 점이다.

취소율을 지표로 본다 취소율이 높은 업무(예: 미결제 취소 예약 중 90%가 결제로 무효화됨)라면, 브로커에 90%의 쓸모없는 메시지를 넣고 있는 셈이다. 이 비율이 높으면 DB 방식으로 옮기는 것이 자원 면에서도 유리하다. "취소율을 지표로 보고 판단한다"는 관점 자체가 답의 수준을 가른다.
취소가 기능 요구면 DB로 도구를 바꾸고, 취소가 예외 상황이면 소비 시점 검증으로 견딘다
그냥 스프링의 @Scheduled로 주기적으로 DB를 스캔하면 안 되나요?힌트: 된다. 다만 분산 환경에서 세 가지가 반드시 따라붙는다

되고, 오히려 많은 경우 그것이 정답이다. 다만 분산 환경에서 주의할 점이 셋 있다.

1
인스턴스가 여러 대면 중복 실행된다. 같은 스케줄러가 3대에서 동시에 돌면 같은 예약을 3번 처리한다. SELECT ... FOR UPDATE SKIP LOCKED로 행 단위 잠금을 걸거나, 분산 락(Redis 등)으로 한 대만 돌게 해야 한다.
2
한 번에 처리할 양에 상한을 둔다. 스케줄러가 한동안 멈췄다 재개되면 밀린 예약이 한꺼번에 쏟아진다. 상한 없이 처리하면 그 순간 다운스트림이 죽는다.
3
실행과 발행을 분리한다. 스케줄러는 "시각이 됐다"만 판단하고 실제 작업은 큐에 넘긴다. 스케줄러가 직접 무거운 작업을 하면 한 건이 오래 걸릴 때 뒤의 예약이 전부 밀린다.
스케줄러는 트리거, 큐는 실행

덧붙이면 좋은 운영 항목 — "마지막 성공 폴링 시각"과 "execute_at이 지났는데 아직 PENDING인 건수"를 지표로 내보내는 것이다. 스케줄러는 조용히 죽는 컴포넌트라서, 이 두 지표가 없으면 고장 사실을 사용자 문의로 알게 된다.

지연 메시지가 중복 실행되면 어떻게 되나요?힌트: 일반 메시지와 같은 해법 하나 + 지연 메시지에만 있는 위험 하나

일반 메시지와 같은 문제이고 같은 해법이다 — 멱등 처리. 다만 지연 메시지에는 고유한 위험이 하나 더 있다.

같은 예약이 여러 번 등록되는 경우 주문 생성 이벤트를 컨슈머가 두 번 처리하면 취소 예약이 두 건 걸린다. 30분 뒤 취소 명령이 두 번 오고, 두 번째는 이미 취소된 주문을 또 취소하려 한다. 소비 시점 멱등만으로는 "예약이 두 개 생긴 것" 자체를 막지 못한다.

그래서 예약 등록 자체도 멱등이어야 한다.

DB 방식

  • (task_type, reference_id)에 유니크 제약을 걸면 끝난다
  • 중복 INSERT가 DB 레벨에서 거부된다

브로커 방식

  • 예약 등록 시점에 중복을 막을 수단이 없다
  • 소비 시점 검증에 의존할 수밖에 없다

이것 역시 DB 방식의 이점이다. 6절의 "상태 + 버전 검증"이 여기서도 최후의 방어선이 되지만, 애초에 예약이 하나만 생기게 하는 것이 훨씬 싸다.

대기 큐에 컨슈머가 실수로 붙으면 어떻게 되나요?힌트: 오류가 나지 않는다는 것이 이 사고의 가장 나쁜 점이다

지연이 통째로 사라진다 — 그것도 조용히. 대기 큐의 지연은 "아무도 안 가져간다"는 사실에만 의존하므로, 컨슈머가 하나라도 붙으면 메시지는 TTL을 기다리지 않고 즉시 배달된다. "30분 뒤 취소"가 "즉시 취소"가 된다.

이 사고가 실제로 나는 경로 큐 이름 패턴으로 리스너를 등록하는 코드(order.*), 테스트 코드가 대기 큐를 소비하고 정리하지 않은 경우, 관리 UI에서 "Get message"로 꺼내 보고 requeue를 끄고 확인한 경우 — 셋 다 오류 없이 지연만 사라진다.

방어는 셋이다.

대기 큐는 배달 경로가 아니라 보관소다 — 컨슈머는 실행 큐에만 붙인다
x-dead-letter-routing-key를 지정하지 않으면 어떻게 되나요?힌트: 원래 라우팅 키가 어디로 갈지 따라가 본다 — 두 가지 나쁜 결말이 있다

메시지의 원래 라우팅 키가 그대로 재사용된다. 대기 큐에 넣을 때 기본 exchange + 큐 이름으로 발행했다면 원래 키는 order.cancel.wait이고, 이 키가 그대로 DLX에서 라우팅에 쓰인다. 결말은 둘 중 하나다.

결말 A — 조용한 소멸

  • DLX에 order.cancel.wait와 매칭되는 바인딩이 없다
  • 메시지는 어디에도 도착하지 않고 사라진다
  • 오류도 로그도 없다 — "예약한 취소가 안 돌았다"만 남는다

결말 B — 무한 루프

  • 대기 큐가 그 키로 DLX에 바인딩되어 있으면
  • 만료된 메시지가 자기 자신에게 돌아간다
  • 30분마다 영원히 순환하며 브로커 자원을 먹는다

그래서 대기 큐를 만들 때 DLX 라우팅 키는 항상 명시한다. 그리고 실행 큐와 대기 큐의 라우팅 키를 반드시 다르게 둔다 — 같으면 루프가 생길 여지가 열린다.

대기 큐 선언 체크리스트: TTL · DLX · DLX 라우팅 키 · 컨슈머 없음 — 넷 다 있어야 한다
메시지 단위 TTL(expiration)은 그럼 절대 쓰면 안 되나요?힌트: 위험한 것은 "메시지 단위 TTL" 자체가 아니라 특정 조합이다

금지가 아니라 조건부다. 위험한 것은 메시지 단위 TTL 자체가 아니라 "한 큐 안에서 서로 다른 값을 섞는 것"이다.

상황안전한가이유
한 큐 안의 모든 메시지가 같은 값안전큐 단위 TTL과 동일한 상태 — 앞이 먼저 만료된다
값이 단조 증가하도록 발행이 보장됨조건부이론상 앞이 먼저 만료되지만, 보장을 코드로 지키기 어렵다
값이 뒤섞여 들어옴위험짧은 것이 긴 것 뒤에 갇힌다 (head-of-line)
메시지 수명 제한 용도 (지연이 아님)안전"오래된 메시지는 버려라"는 의미로 쓰는 것은 원래 용도에 맞다

실무 판단은 이렇게 정리한다 — 지연 목적이면 큐 단위 TTL로 못 박고, 메시지 단위 TTL은 "유통기한" 용도로만 쓴다. 두 용도를 이름으로 구분해 두면 팀 안에서 오용이 줄어든다.

운영 중에 지연 시간을 30분에서 10분으로 바꿔야 합니다. 어떻게 하나요? 시니어 변별힌트: 이미 선언된 큐의 인자는 바꿀 수 없다 — 그럼 무엇으로 두었어야 했나

먼저 제약을 정확히 말해야 한다 — 이미 선언된 큐의 인자(x-message-ttl)는 나중에 바꿀 수 없다. 다른 값으로 다시 선언하려 하면 인자 불일치로 선언이 실패한다. 그래서 선택지는 셋이다.

1
새 큐를 만들어 전환한다. wait.10m을 새로 선언하고 발행 대상만 새 큐로 바꾼다. 기존 wait.30m에 남아 있는 메시지는 자연히 빠질 때까지 두었다가 비면 지운다. — 가장 안전하고, 진행 중인 예약의 지연 시간이 바뀌지 않는다는 점도 오히려 예측 가능하다.
2
애초에 policy로 두었으면 큐를 다시 만들지 않고 값을 바꿀 수 있다. TTL은 정책(policy)으로도 설정 가능하고 정책은 런타임에 변경된다. 인자와 정책을 동시에 쓰지 말고 한쪽으로 통일해 두는 것이 혼선을 막는다.
3
이런 변경이 잦다면 애초에 DB 스케줄러였어야 한다. UPDATE scheduled_task SET execute_at = execute_at - INTERVAL '20 minutes' 한 줄로 이미 걸린 예약까지 소급 변경된다. "지연 값이 정책적으로 자주 바뀌는가"는 도구 선택 질문 목록에 넣을 만한 항목이다.
함께 말하면 좋은 것 이미 대기 중인 메시지의 지연은 어떤 방법으로도 브로커에서 줄일 수 없다. "지금 대기 중인 것도 10분으로 바꿔달라"는 요구는 브로커 방식으로는 불가능하고, 이것이 2절 축의 또 다른 귀결이다.
스케줄러가 발행에는 성공했는데 상태 업데이트 전에 죽으면요? 시니어 변별힌트: 이 테이블은 사실 무엇과 같은 구조인가

같은 예약이 다시 발행된다 — 즉 at-least-once다. 그리고 이 구조를 알아보는 것이 핵심이다 — scheduled_task 테이블은 사실상 outbox와 같은 구조다. "DB에 기록 → 별도 프로세스가 폴링해 브로커로 발행 → 상태 표시"라는 형태가 동일하다.

피할 수 없는 것

  • 발행과 상태 UPDATE는 서로 다른 시스템이라 원자적으로 묶이지 않는다
  • 둘 사이에서 죽으면 재발행이 일어난다
  • 순서를 뒤집어 먼저 UPDATE 후 발행하면 이번엔 유실이 생긴다

그래서 하는 선택

  • 중복을 택하고 유실을 버린다 (발행 먼저, 표시 나중)
  • 컨슈머를 멱등하게 만든다 — 메시지에 고유 키(task id)를 실어 보낸다
  • 6절의 소비 시점 검증이 여기서도 두 번째 방어선이 된다

"지연 스케줄링을 DB로 하면 outbox와 같은 문제를 그대로 물려받는다"고 말할 수 있으면, 두 주제를 따로 외운 사람과 구조로 이해한 사람이 구분된다.

지연이 끝나는 시점에 컨슈머가 전부 죽어 있으면 어떻게 되나요?힌트: TTL 만료는 컨슈머 사정을 봐주지 않는다 — 복구 순간에 무슨 일이 생기는가

TTL 만료는 컨슈머 유무와 무관하게 진행된다. 만료된 메시지는 실행 큐에 계속 쌓이고, 컨슈머가 복구되는 순간 밀린 물량이 한꺼번에 몰린다(thundering herd).

지연 메시지에서 이 문제가 더 나쁜 이유 일반 큐의 적체는 발행 속도만큼 쌓이지만, 지연 큐는 "30분 전에 발행된 것들이 지금 한꺼번에 만료"되는 성질이 있다. 특히 이벤트성 트래픽(타임세일 등)으로 30분 전에 예약이 폭증했다면, 정확히 30분 뒤에 그만큼의 스파이크가 실행 큐에 생긴다. 부하의 모양이 그대로 복사되어 30분 뒤에 재생된다고 보면 된다.

대비는 셋이다.

prefetch 제한
워커가 한 번에 쥐는 양을 제한해 다운스트림으로 가는 동시성을 통제한다
실행 큐 감시
대기 큐가 아니라 실행 큐의 depth와 나이(age)를 본다 — 지연 설계가 무너졌는지가 여기서 보인다
지연 값 분산
동시 예약이 몰리면 지터(jitter)를 섞어 만료 시점을 흩는다 (예: 30분 ± 임의 0~60초)

지터를 섞는다는 답은 특히 좋다 — 스파이크를 만드는 원인이 "정확히 같은 지연"이라는 것을 이해했다는 신호이기 때문이다.

Redis의 sorted set이나 key 만료(keyspace notification)로 지연을 구현하는 건 어떤가요?힌트: 이 방식은 축 위의 어디에 놓이는가 — 그리고 무엇을 잃는가

2절의 축 위에서 "DB 스케줄러 쪽"에 가까운 방식이라고 자리매김부터 하면 좋은 답이 된다. 실행 시각을 score로 갖는 sorted set에 예약을 넣고, 워커가 주기적으로 "지금 시각 이하"를 꺼내 발행하는 형태다.

얻는 것

  • 취소·조회가 된다 — 멤버 삭제·조회가 O(log N) 수준
  • DB보다 가볍고 빠르다 — 짧은 주기 폴링에 유리
  • 지연 값이 완전히 자유롭다

잃는 것 · 주의

  • 내구성 — 영속화 설정에 따라 재시작 시 예약이 날아갈 수 있다
  • 예약이 업무 데이터와 다른 저장소에 있어 트랜잭션으로 묶이지 않는다
  • key 만료 알림 방식은 알림 유실 가능성이 있어 단독 신뢰는 위험하다
  • 여러 워커가 꺼낼 때 원자적 pop(스크립트 등)이 필요하다

정리하면 "짧고 대량이며 유실을 감내할 수 있는 지연"에는 좋고, "돈이 걸린 예약"에는 DB가 낫다. 면접에서는 선택지를 늘리되 판단 기준을 함께 제시하는 것이 중요하다 — "예약을 잃어도 되는가"가 그 기준이다.

한 줄 요약
큐에는 시간 개념이 없으므로 지연은 우회로 만든다 — 짧고 종류가 고정된 지연은 TTL+DLX 대기 큐, 짧지만 값이 자유로운 지연은 delayed message 플러그인, 길거나 취소·조회가 필요하면 DB 스케줄러이며, 브로커에 넣은 예약은 되돌릴 수 없으므로 지연 메시지는 항상 "명령"이 아니라 "지금도 유효한지 확인하라는 요청"으로 설계해야 한다.
