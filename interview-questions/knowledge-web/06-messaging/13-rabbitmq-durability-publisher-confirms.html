RabbitMQ 내구성 3종 — durable queue · persistent message · publisher confirms
셋은 같은 것을 세 번 켜는 스위치가 아니라, 서로 다른 구멍을 막는 세 개의 마개다 — 그리고 셋을 다 막아도 구멍은 둘 남는다

면접 질문: "RabbitMQ에서 메시지를 잃지 않으려면 무엇을 켜야 하나요? (durable queue, persistent message, publisher confirms) 각 설정이 막아주는 유실 지점은 어디인가요?"

핵심 관전 포인트 — "메시지 안 잃게 하려면 durable 켜면 되죠"는 반쪽 답이다. 유실 지점이 셋이고 각각을 막는 장치가 따로 있다. ① 큐 정의가 재시작 때 사라지는 것 → durable queue, ② 큐는 살아남았는데 안에 든 메시지가 메모리에만 있어 날아가는 것 → persistent message(delivery mode 2), ③ 프로듀서가 보냈는데 브로커에 도달했는지 자체를 모르는 것 → publisher confirms. 셋 중 하나만 켜면 나머지 구멍은 그대로 열려 있다. 그리고 셋을 다 켜도 남는 구멍이 있다 — confirm은 "브로커가 책임을 넘겨받았다"는 뜻이지 "어떤 큐에 들어갔다"는 뜻이 아니라서, 라우팅에 실패한 메시지도 정상 confirm을 받는다. 그래서 mandatory + return 콜백이 짝으로 따라붙어야 하고, 마지막으로 "DB는 커밋됐는데 발행이 실패한" 구간은 브로커 설정으로는 절대 못 막아 Outbox가 필요해진다.
  • 1
    설정을 나열하기 전에 유실 지점부터 쪼갠다. "메시지가 유실된다"를 뭉뚱그리면 대책도 뭉뚱그려진다. 발행 누락 → 도달 불명 → 라우팅 실패 → 메시지 소멸 → 큐 소멸 → 처리 중 사망으로 여섯 구간을 끊고, "어느 구간을 막고 싶으신가요"로 되묻는 것이 첫 문장이다. 셋의 역할은 그릇(durable) · 내용물(persistent) · 접수증(confirms)으로 갈린다.
  • 2
    셋을 다 켜도 라우팅 실패는 안 잡힌다. 라우팅 대상 큐가 0개여도 브로커는 정상 confirm(ack)을 돌려준다 — 브로커 입장에선 규칙을 적용했고 결과가 "대상 없음"이었을 뿐 오류가 아니기 때문이다. 그래서 아무도 못 받았는데 모든 지표가 정상인 상태가 만들어진다. 대책은 mandatory + return 콜백(프로듀서가 즉시 인지) 또는 alternate exchange(브로커에 남겨 사후 조사).
  • 3
    경계를 스스로 그어 보인다. "durable · persistent · confirms를 다 켜도 DB와 브로커 사이의 원자성은 남습니다" — DB 커밋과 발행 사이는 브로커 설정으로 절대 못 막고 Transactional Outbox가 표준 해법이다. 아래로는 하나 더 있다 — persistent도 fsync 직전 전원 차단은 못 막으므로, 그 이상은 복제(quorum queue)로 올라가야 한다. 설정 나열이 아니라 문제의 경계를 아는 답이 된다.

0. 질문 + 출제 의도 · 먼저 깨야 할 오해

질문: "RabbitMQ에서 메시지를 잃지 않으려면 무엇을 켜야 하나요? (durable queue, persistent message, publisher confirms) 각 설정이 막아주는 유실 지점은 어디인가요?"

출제 의도: 세 설정은 각각 다른 유실 지점을 막는다. 셋 중 하나만 켜고 "영속화했다"고 믿는 사고가 실무에서 매우 흔하다. 유실 경로를 단계별로 분해해 사고하는지, 그리고 "브로커 설정으로 막을 수 있는 구간"과 "애플리케이션 설계로만 막을 수 있는 구간"의 경계를 아는지 본다.

질문이 두 토막인 이유 — 배점은 뒤쪽에 있다 앞쪽 "무엇을 켜야 하나"는 이름 세 개를 대면 통과하는 구간이다. 진짜 질문은 뒤쪽 "각각이 막아주는 지점은 어디인가"다. 여기서 세 설정을 하나의 '영속화' 스위치로 뭉뚱그려 이해하고 있는 사람과 경로를 구간으로 끊어 사고하는 사람이 갈린다. 이 페이지는 1절에서 지도(여섯 구간)를 먼저 펴고, 2·3절에서 세 마개를 각 구멍에 끼우고, 4절에서 그러고도 남는 두 구멍으로 내려간다.
먼저 깨야 할 오해 4개 — 아래 절들이 각각 이것을 겨냥한다 ① "durable을 켰으니 메시지는 안 사라진다" → durable은 그릇에 대한 설정이다. 내용물이 메모리에만 있었다면 그릇은 빈 채로 복원된다 (2-1, 2-2).
② "persistent면 디스크에 확실히 적힌 것이다" → "적는다"와 "확실히 적혔다"는 다르다. 성능을 위해 여러 건을 모아 주기적으로 fsync하므로 그 사이 전원이 나가면 몇 건은 사라진다 (2-3).
③ "confirm ack을 받았으면 큐에 들어간 것이다" → 아니다. 라우팅 대상 큐가 0개여도 정상 ack이 온다. 가장 위험한 착각이다 (4-1).
④ "발행 메서드가 예외 없이 리턴했으면 성공이다" → "소켓에 썼다"는 뜻일 뿐이다. 그 시점에 브로커가 죽어 있었어도 예외가 안 날 수 있다 (3-1).

1. 유실 지도 — 여섯 구간과 각자의 마개

"메시지가 유실된다"고 뭉뚱그리면 대책도 뭉뚱그려진다. 발행부터 처리까지의 경로를 구간으로 끊고 각 구간에서 무엇이 죽을 수 있는지 나열하는 것이 출발점이다.

구간은 여섯이고 대책이 전부 다르다. 그리고 그 여섯 중 브로커 설정으로 막히는 것은 가운데 넷뿐이다 — 양 끝은 애플리케이션 설계로만 막힌다. 이 경계가 이 질문의 핵심이다.

같은 지도를 표로. 세 번째 열이 "이건 다른 문서의 주제"라고 선을 긋는 자리다 — 면접에서도 이렇게 범위를 정리해 주면 답이 깔끔해진다.
구간막는 장치어디서 다루나한 문장 설명
(A) 발행 자체가 안 됨Outbox 패턴 설정 불가20-rabbitmq-outbox-polling-publisher.mdDB와 브로커라는 두 시스템에 걸친 원자성 문제라 한쪽 설정으로 안 풀린다
(B) 도달 여부 모름publisher confirms이 문서 3절단방향이던 발행에 브로커의 응답을 만든다
(C) 라우팅 실패mandatory + return 또는 alternate exchange이 문서 4-1confirm으로는 절대 안 잡히는 유실 — 별도 장치가 필요하다
(D) 메시지 소멸persistent message이 문서 2-2내용물을 디스크에도 적으라는 지시
(E) 큐 소멸durable queue이 문서 2-1그릇을 재시작 후 복원하라는 지시
(F) 처리 중 사망manual ack + 멱등 컨슈머12-rabbitmq-ack-nack-prefetch.mdauto-ack은 보내는 즉시 삭제라 재전달 자체가 없다

세 마개 + 남는 두 구멍 — 다섯 개를 이 비유로 외운다

① 그릇
durable queue
그릇(큐 정의)이 재시작 후에도 다시 놓이는가
② 내용물
persistent message
담긴 것이 디스크에도 적혔는가
③ 접수증
publisher confirms
보낸 쪽이 접수됐다는 응답을 받았는가
④ 반송 스티커
mandatory + return / alternate exchange
받는 주소가 없을 때 되돌려받거나 따로 모은다 — 없으면 조용히 버려진다
⑤ 발송 대장
Transactional Outbox
부치기 전에 장부에 먼저 적는다 — 앱이 죽어도 장부는 DB에 남는다
①②③은 브로커에게 시키는 일, ④는 브로커에게 시키되 프로듀서가 받아야 하는 일,
⑤는 브로커가 아예 관여할 수 없는 일

1-1. 브로커가 죽는다는 것이 무슨 뜻인가

(D)와 (E)를 이해하려면 브로커가 메시지를 어디에 들고 있는지 알아야 한다.

RabbitMQ는 성능을 위해 메시지를 기본적으로 메모리에 들고 있다. 큐가 짧고 컨슈머가 빠르면 메시지는 디스크를 거치지 않고 메모리에서 메모리로 흘러간다. 이것이 RabbitMQ가 낮은 지연을 내는 이유다.

문제는 프로세스가 죽는 순간이다. 메모리에 있던 것은 전부 사라진다. 그래서 "디스크에도 적어라"라고 지시해야 하고, 그 지시가 persistent다.

그런데 디스크에 적어도 큐 정의가 재시작 후에 복원되지 않으면 그 안의 메시지도 의미가 없다. 그래서 큐 자체도 "재시작 후 복원하라"고 지시해야 하고, 그 지시가 durable이다.

둘은 층위가 다르다 — 이 한 문장이 2절 전체를 요약한다 durable은 그릇에 대한 설정이고, persistent는 내용물에 대한 설정이다. 그릇이 사라지면 내용물도 사라지고, 그릇만 남고 내용물이 메모리에만 있었다면 그릇은 빈 채로 복원된다.

2. 그릇과 내용물 — durable queue · persistent message

2-1. durable queue — 큐 정의를 살린다

큐를 선언할 때 durable=true를 주면 큐의 정의(이름, 속성, 바인딩)가 디스크에 기록되어 브로커 재시작 후 자동으로 복원된다.

durable=false인 큐는 재시작과 함께 사라진다. 큐가 사라지면 바인딩도 사라지고, 그 뒤에 도착한 메시지는 라우팅 대상이 없어 폐기된다.

비durable 큐의 진짜 무서운 점 — 유실이 "그때 그 몇 건"에서 끝나지 않는다 재시작 순간에 큐 안에 있던 메시지만 사라지는 것이 아니다. 큐가 없어졌으므로 그 뒤에 오는 메시지도 전부 갈 곳이 없다. 재시작 한 번에 "그 이후 모든 메시지"가 조용히 사라지는 형태의 장애가 되므로, 처음 몇 건이 아니라 지속적인 유실이 된다. 게다가 (C) 라우팅 실패와 겹쳐 프로듀서는 confirm ack을 계속 받으며 "정상"으로 보인다.
문제기본값에 맡긴 큐 선언
// 동작은 한다. 그런데 코드만 봐서는
// 이 큐가 재시작을 견디는지 알 수 없다
@Bean
Queue paymentQueue() {
    return new Queue("payment.done"); durable 여부가 안 보인다
}
개선업무 큐는 명시적으로 durable
@Bean
Queue paymentQueue() {
    return QueueBuilder.durable("payment.done") 재시작 후 복원
            .deadLetterExchange("payment.dlx")
            .build();
}

@Bean
TopicExchange orderEvents() {
    return ExchangeBuilder.topicExchange("order.events")
            .durable(true) exchange도 같이
            .build();
}

Queue 생성자의 기본값은 durable이지만, 명시하는 습관이 낫다. 리뷰어가 "이 큐는 재시작을 견디는가"를 코드에서 바로 확인할 수 있어야 하기 때문이다.

exchange도 잊지 말 것 — 실패 모습이 다르다 exchange에도 같은 설정이 있다. exchange가 durable이 아니면 재시작 시 exchange가 사라지고, 그러면 프로듀서의 발행이 "존재하지 않는 exchange" 오류로 실패한다. 큐 소멸이 조용한 유실이라면 exchange 소멸은 시끄러운 실패다 — 역설적으로 알아채기는 이쪽이 쉽다.

2-2. persistent message — 내용물을 디스크에 적는다

메시지를 발행할 때 delivery_mode = 2(persistent)로 표시하면 브로커가 그 메시지를 디스크에도 기록한다. delivery_mode = 1(transient)이면 메모리에만 둔다.

Spring AMQP의 기본값은 persistent이며(MessageDeliveryMode.PERSISTENT), 이것이 안전한 기본값이다. 명시적으로 지정하려면 이렇게 쓴다.

기본delivery mode를 직접 지정하는 형태
MessageProperties props = new MessageProperties();
props.setDeliveryMode(MessageDeliveryMode.PERSISTENT); // 디스크에도 기록
props.setMessageId(event.getId());  // 재발행 중복을 컨슈머가 걸러낼 열쇠 (6절)

Message message = new Message(body, props);
rabbitTemplate.send("order.events", "payment.done", message);

여기서 반드시 짚어야 할 조건이 있다. persistent 메시지라도 durable이 아닌 큐에 들어가면 재시작 후 사라진다. 큐 정의가 복원되지 않으므로 복원할 대상이 없기 때문이다.

둘 다 켜야 한다 — 하나만 켜고 안심하는 것이 가장 흔한 오해

durable 큐 + persistent 메시지→재시작 후에도 남는다 (유일한 안전 조합)
durable 큐 + transient 메시지→큐는 복원, 메시지는 소멸
비durable 큐 + persistent 메시지→큐가 없으므로 메시지도 소멸 (디스크 기록이 무의미)
비durable 큐 + transient 메시지→전부 소멸
그릇이 사라지면 내용물도 사라지고,
그릇만 남고 내용물이 메모리에만 있었다면 그릇은 빈 채로 복원된다

2-3. persistent를 켜도 남는 아주 작은 구멍 가산점

여기까지가 교과서고, 한 단계 더 들어가면 이런 사실이 있다. 디스크에 "적는다"와 "확실히 적혔다"는 다르다.

운영체제는 쓰기 요청을 곧바로 디스크에 밀어 넣지 않고 페이지 캐시에 모았다가 내보낸다. RabbitMQ도 성능을 위해 여러 메시지를 모아 주기적으로 fsync(캐시 내용을 물리 디스크에 강제로 내려쓰는 시스템 호출)한다. 매 건마다 fsync하면 디스크 성능에 묶여 처리량이 급락하기 때문이다.

막는 방법은 복제다. 여러 노드에 메시지를 복제해두면 한 노드가 죽어도 다른 노드에 남는다. 그리고 이 복제를 안전하게 하는 것이 quorum queue의 역할이다 — Raft라는 합의 알고리즘으로 과반 노드에 기록된 뒤에야 확정으로 처리한다. 이 이야기는 17-classic-vs-quorum-queue.md에서 이어간다.

3. 접수증 — publisher confirms

1절 지도에서 2절이 막은 것은 (D)와 (E) 둘이다. 브로커에 이미 도착한 메시지를 재시작 너머까지 살려두는 이야기였다. 남은 것은 도착 이전과 도착 이후다. 이 절은 그중 도착 이전 — 구간 (B)를 막는다.

3-1. 왜 필요한가 — 발행은 원래 단방향이다

여기까지의 설정은 전부 브로커에 도착한 뒤의 이야기다. 도착하지 못했다면 아무 의미가 없다.

기본적으로 AMQP의 발행은 단방향(fire-and-forget)이다. 프로듀서는 소켓에 바이트를 쓰고 끝낸다. 브로커가 받았는지, 큐에 넣었는지, 디스크에 적었는지 알 방법이 없다.

Publisher confirms(발행 확인)는 이 구간에 응답을 만든다. 채널을 confirm 모드로 전환하면, 브로커가 메시지를 처리한 뒤 해당 발행 번호에 대해 ack(성공) 또는 nack(실패)를 비동기로 돌려준다.

한 메시지가 여러 큐로 라우팅되면 confirm은 언제 오나 라우팅된 모든 큐가 그 메시지를 받아들인 뒤에 confirm이 온다. 큐가 셋이면 셋 다 적재(persistent+durable이면 셋 다 기록)된 뒤 하나의 ack이 온다. 그래서 fanout으로 넓게 퍼뜨리는 exchange일수록 confirm 지연이 길어진다 — confirm을 켠 뒤 지연이 늘었다면 바인딩 수부터 의심해 볼 만하다.

3-2. Spring에서 켜기 — correlated가 아니면 반쪽이다

설정application.yml
spring:
  rabbitmq:
    publisher-confirm-type: correlated  # 어떤 발행에 대한 응답인지 식별자로 연결
    publisher-returns: true             # 라우팅 실패 메시지를 되돌려받는다 (4-1)
개선RabbitTemplate — confirm + return을 짝으로 등록한다
@Bean
RabbitTemplate rabbitTemplate(ConnectionFactory cf) {
    RabbitTemplate t = new RabbitTemplate(cf);
    t.setMandatory(true); 라우팅 실패 시 폐기 말고 되돌려 달라

    t.setConfirmCallback((correlation, ack, cause) -> {
        if (ack) {
            // 브로커가 책임을 넘겨받았다. 여기서 outbox 행을 '발행됨'으로 표시한다
            outboxRepository.markPublished(correlation.getId());
        } else {
            // 브로커가 못 받았거나 내부 오류. 재발행 대상이다
            log.error("발행 실패: id={}, cause={}", correlation.getId(), cause);
        }
    });

    t.setReturnsCallback(returned ->
        // confirm은 성공인데 이쪽이 호출됐다면 = 브로커는 받았지만 갈 큐가 없었다
        log.error("라우팅 실패: rk={}", returned.getRoutingKey()));
    return t;
}

// 발행 시 식별자를 함께 넘겨야 콜백에서 어떤 메시지인지 알 수 있다
rabbitTemplate.convertAndSend("order.events", "payment.done", event,
        new CorrelationData(event.getId())); 이 줄이 없으면 콜백이 무력하다

왜 correlated인가 — 마지막 줄에 이유가 있다

콜백은 비동기로 오므로 "무엇에 대한 응답인지" 식별자가 없으면 아무 조치도 할 수 없다. 실패를 알아도 무엇을 재발행할지 모르기 때문이다.

식별자 없이 confirm만 켜두는 것은 사실상 로그만 찍는 것과 같다

면접에서 "confirm 켰습니다"라고만 답하면 "실패하면 무엇을 재발행하나요"가 바로 따라온다. CorrelationData까지 한 호흡에 말하는 것이 안전하다.

3-3. confirm은 비동기다 — 착각하기 쉬운 지점

confirm 콜백은 발행 호출과 다른 스레드에서, 나중에 온다. 그래서 이렇게 쓰면 안 된다.

문제발행 직후 성공했다고 간주
rabbitTemplate.convertAndSend(exchange, rk, event);

order.markEventPublished();  아직 confirm 안 왔다
orderRepository.save(order); 거짓 기록이 커밋된다

// 발행이 실패해도 DB에는 "발행 완료"로 남는다.
// 재발행 대상을 찾을 방법이 영영 사라진다 —
// 유실보다 나쁜 것은 '유실을 모르는 상태'다.
개선ack을 받은 뒤에 상태를 바꾼다
// 발행 시점 — '미발행'인 채로 식별자만 실어 보낸다
rabbitTemplate.convertAndSend(exchange, rk, event,
        new CorrelationData(event.getId()));

// 콜백 시점 (다른 스레드, 나중에)
t.setConfirmCallback((corr, ack, cause) -> {
    if (ack) outbox.markPublished(corr.getId());
    else     log.error("재발행 대상 id={}", corr.getId());
});

// confirm이 안 오거나 nack이면 그 행은 '미발행'으로 남아
// 다음 폴링에서 자동으로 재발행 대상이 된다.

올바른 흐름은 둘 중 하나다.

첫째 — 콜백에서 상태를 갱신한다 (표준)

  • confirm ack을 받은 시점에 "발행 완료"로 표시한다.
  • confirm이 안 오거나 nack이면 그 행은 미발행 상태로 남아 자연스럽게 재발행 대상이 된다.
  • 발행 스레드는 계속 다음 건을 밀어 넣을 수 있다 — 처리량 손실이 거의 없다.
  • 대가: 미확인(in-flight) 발행을 어딘가에 기록해 둬야 한다 — 그 자리가 보통 outbox 테이블이다.

둘째 — 동기적으로 기다린다

  • waitForConfirmsOrDie() 계열을 쓰면 confirm이 올 때까지 블로킹한다.
  • 구현이 단순하다 — 리턴했으면 성공이다.
  • 대가: 처리량이 급락한다 — 발행마다 왕복을 기다리기 때문이다.
  • 절충: 배치의 마지막에 한 번만 기다리는 식으로 쓴다.

3-4. AMQP 트랜잭션은 왜 안 쓰는가

AMQP에는 tx.select / tx.commit이라는 트랜잭션 기능도 있다. 발행을 트랜잭션으로 묶어 커밋하면 확실히 반영된다. 그런데 실무에서 거의 쓰지 않는다.

같은 목적, 다른 값. "확실성을 얻는 방법이 둘인데 동기 방식이 느려서 비동기 방식이 표준이 되었다"가 이 표의 요약이다.
AMQP 트랜잭션 (tx.select/tx.commit)publisher confirms
보장 내용커밋 성공 = 브로커에 반영됨ack 수신 = 브로커가 책임을 인수함
통신 방식발행(커밋)마다 동기 왕복비동기 응답 — 계속 밀어 넣을 수 있다
처리량크게 하락거의 그대로
구현 난이도낮음 (커밋하면 끝)콜백·식별자·미확인 추적이 필요
DB 트랜잭션과의 원자성여전히 없음여전히 없음 — 둘 다 (A) 구간은 못 막는다
실무거의 안 씀사실상 표준
이름 때문에 생기는 오해 — "AMQP 트랜잭션을 쓰면 DB와 묶이나요?" 아니다. AMQP 트랜잭션은 브로커 내부의 발행 원자성일 뿐이고, DB 트랜잭션과는 아무 관계가 없다. 마지막 행이 그 뜻이다 — tx를 써도 confirms를 써도 (A) 구간은 그대로 열려 있고, 그건 4-2의 Outbox 몫이다.

4. 셋을 다 켜도 남는 구멍 둘

이 절이 왜 여기 있는가 — 순서에 이유가 있다 셋 중 하나라도 꺼져 있으면 유실의 원인이 전부 그쪽으로 설명되어 버려서, 라우팅 실패 (C)나 DB 커밋과 발행 사이의 공백 (A) 같은 잔여 위험은 아예 시야에 들어오지 않는다. 잔여 위험은 기본을 다 켠 뒤에야 보인다 — 그래서 이 둘을 한 절에 묶었다.

4-1. confirm은 "라우팅됐다"는 뜻이 아니다 가장 위험한 함정

둘 중 첫째이자 가장 중요한 함정은 이것이다. 라우팅 대상 큐가 0개여도 브로커는 정상 confirm(ack)을 돌려준다.

브로커 입장에서는 라우팅 규칙을 적용했고 결과가 "대상 없음"이었을 뿐, 오류가 아니다. 그래서 프로듀서는 "성공적으로 발행했다"고 기록하지만 메시지는 어디에도 없다.

사고라우팅 키 오타 한 글자가 만드는 조용한 유실
프로듀서: publish(rk="payment.faild")   ← 오타 (failed)
브로커:   매칭 큐 0개 → 폐기 → confirm ack 회신
프로듀서: "발행 성공" 로그
결과:     아무도 못 받았는데 모든 지표가 정상

confirm ack이 보장하는 것 / 보장하지 않는 것

ack이 말해주는 것ack이 말해주지 않는 것
브로커가 메시지를 받았다어떤 큐에 들어갔는지 — 0개여도 ack
라우팅 규칙을 적용했다컨슈머가 받았는지 · 처리했는지
라우팅된 모든 큐가 받아들였다fsync까지 끝나 전원 차단을 견딘다는 것 (2-3)
persistent+durable이면 디스크에 기록했다DB의 상태와 일치한다는 것 (4-2)
confirm은 "내가 책임진다"는 브로커의 서명이지
"목적지에 도착했다"는 배달 완료 통지가 아니다
그래서 짝으로 붙인다 confirm에는 반드시 mandatory + return 콜백이 짝으로 따라붙어야 한다. mandatory를 켜면 라우팅 실패 메시지를 프로듀서가 되돌려받고, return 콜백에서 알람을 올릴 수 있다. 브로커 쪽 대안인 alternate exchange는 라우팅에 실패한 메시지를 지정한 대체 exchange로 흘려보내 별도 큐에 모으는 방식이며, 프로듀서 코드 없이 동작하고 프로듀서가 죽어도 메시지가 남는다는 장점이 있다. 자세한 내용은 10-rabbitmq-core-components.md에 있다.

4-2. DB 커밋과 발행 사이의 구간 — 설정으로는 절대 못 막는다

둘째이자 마지막 구멍은 브로커 설정으로 절대 못 막는다. 구간 (A) — 프로듀서 앱 안에서 DB 커밋과 발행 사이가 벌어지는 자리다.

문제트랜잭션 안에서 곧바로 발행
@Transactional
public void completePayment(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();                    // ① DB 상태 변경
    // ② 여기서 프로세스가 죽으면?
    rabbitTemplate.convertAndSend(...); 다른 시스템 — 같은 트랜잭션이 아니다
}

// ②에서 죽으면: DB는 커밋됐는데(또는 커밋될 예정인데) 이벤트가 없다
// ③을 먼저 하고 롤백되면: 일어나지 않은 일에 대한 이벤트가 나간다
개선같은 트랜잭션 · 같은 DB에 기록
@Transactional
public void completePayment(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();                             // ① 상태 변경
    outboxRepository.save(OutboxEvent.of(order)); 같은 DB
}   // ①②가 한 커밋으로 원자적으로 확정된다

// 별도 퍼블리셔가 outbox를 폴링해 발행하고,
// confirm ack을 받은 뒤에야 행을 '발행됨'으로 표시한다 (3-3)
// 발행이 실패하면 행이 남아 있으므로 다음 폴링에서 재시도된다
"@TransactionalEventListener(AFTER_COMMIT)로 옮기면 되지 않나요?" 시니어 변별 절반만 맞다. 커밋 이후로 발행을 미루면 롤백 시 유령 이벤트가 나가는 문제는 확실히 막힌다. 하지만 커밋 직후 · 발행 직전에 프로세스가 죽는 구간은 그대로 남는다 — 그림의 붉은 구간이 조금 좁아질 뿐 사라지지 않는다. "유령 이벤트"와 "유실"은 다른 문제이고, AFTER_COMMIT은 앞의 것만 푼다. 이 구분을 말할 수 있으면 Outbox가 왜 필요한지를 스스로 유도한 것이 된다.
면접에서 이 구간을 스스로 꺼내는 것이 중요하다 —
"durable, persistent, confirms를 다 켜도 DB와 브로커 사이의 원자성은 남습니다"

표준 해법은 Transactional Outbox — 이벤트를 같은 DB 트랜잭션 안에서 outbox 테이블에 저장하고, 별도 프로세스가 그 테이블을 읽어 발행하는 것이다. RabbitMQ 환경에서의 구현은 20-rabbitmq-outbox-polling-publisher.md에서 다룬다.

5. 운영 판단 — 성능 · Kafka 대응 · 유실 조사

5-1. persistent의 비용은 큐마다 다르게 판단한다

"persistent를 켜면 성능이 얼마나 떨어지나요"에 정확한 배수를 말하는 것은 위험하다. 디스크 종류, 메시지 크기, 큐 길이에 따라 크게 달라지기 때문이다. 대신 왜 떨어지는지를 말하면 된다.

왜 떨어지는가

  • 메모리 큐는 쓰기가 RAM 접근이지만 persistent는 디스크 I/O와 주기적 fsync가 끼어든다.
  • 큐가 짧게 유지될 때는 차이가 작다 — 메시지가 금방 소비되어 디스크 기록이 상쇄된다.
  • 큐가 길게 쌓일 때 차이가 커진다 — 적체된 메시지를 디스크에서 다시 읽어와야 한다.

그래서 판단 기준은 성능이 아니라 데이터 성격

  • 결제 · 주문처럼 유실이 곧 돈인 메시지는 예외 없이 persistent다.
  • 초당 수만 건의 지표 · 로그성 메시지는 transient가 정당할 수 있다.
  • 한 클러스터 안에서도 큐마다 다르게 가져가는 것이 정답이며, "전부 persistent" 또는 "전부 transient"라는 일괄 결정이 오히려 이상하다.
큐별 판단표. 면접에서는 "큐마다 다릅니다"에서 끝내지 말고 어떤 축으로 나누는지까지 말하는 것이 좋다 — 축은 "한 건을 잃었을 때 무슨 일이 벌어지는가"다.
메시지 성격예권장 조합이유
유실 = 돈 · 신뢰결제 완료, 주문 생성, 정산durable + persistent + confirms + mandatory + Outbox사후 복구 수단이 없다. 비용을 다 지불한다
유실 = 사용자 불편알림 메일 · 푸시, 쿠폰 지급durable + persistent + confirms재발송 경로가 따로 있으면 Outbox까지는 상황에 따라
유실 = 통계 오차클릭 지표, 사용량 집계, 감사 외 로그durable 큐 + transient 가능초당 수만 건 · 한 건의 가치가 낮다
지연이 곧 가치실시간 브로드캐스트 · 화면 갱신transient + 비durable(임시) 큐오래된 데이터는 되살려도 가치가 없다

5-2. Kafka의 acks와 대응시키면 — 목적은 같고 층위가 다르다

대응표. 외울 것은 표 자체보다 표 아래 한 문장이다.
보장KafkaRabbitMQ비고

Kafka는 애초에 로그 저장소로 설계되어 "안 적는다"는 선택지가 없지만, RabbitMQ는 메모리 큐가 기본이고 필요한 만큼 켜서 쓴다. 이 차이가 두 도구의 기본 성능 특성과 설정 실수의 위험도를 갈라놓는다 — RabbitMQ 쪽이 빠른 대신 실수하면 조용히 잃는다.

5-3. "메시지가 유실됐다"는 신고를 받았다 — 구간을 좁히는 순서

1절의 지도가 그대로 진단 순서가 된다. 다만 실전에서는 가장 흔한 오진부터 걷어내고 시작한다.

0
DLQ부터 본다. 유실이 아니라 실패 후 격리된 것일 수 있다. 실제로 "유실됐다"는 신고의 상당수가 DLQ에 얌전히 들어 있는 경우다. 이것을 먼저 확인하는 습관을 말하면 실전 감각이 드러난다.
1
발행 로그와 DB 상태를 대조한다. DB에는 주문이 완료로 남아 있는데 발행 로그가 없으면 (A) 구간 — Outbox 부재 문제다.
2
exchange의 in/out 지표를 본다. 들어온 수보다 나간 수가 적으면 (C) 라우팅 실패다. unroutable 큐가 있으면 거기 쌓여 있을 것이다.
3
큐의 durable 여부와 브로커 재시작 이력을 본다. 재시작 시각과 유실 구간이 겹치면 (D)(E)다.
4
컨슈머의 ack 모드를 본다. NONE(auto-ack)이면 컨슈머 재시작 · 크래시 시점과 대조한다 — (F)다.
순서가 이렇게 되는 이유 0번은 비용이 가장 싸고 적중률이 가장 높다. 1~4번은 지도의 왼쪽(프로듀서)부터 오른쪽(컨슈머)으로 훑는 순서인데, 이렇게 가면 "발행은 됐는가 → 라우팅은 됐는가 → 남아 있었는가 → 처리됐는가"로 범인이 있을 수 있는 구간이 한 단계씩 줄어든다. 아무 데나 찌르는 대신 이분 탐색처럼 구간을 좁히는 것이 이 답의 골격이다.

6. 인출 카드 · 꼬리질문 셀프 테스트

6-1. 면접 전날 이것만 — 60초 답변 스크립트

1
구간부터 쪼갠다. "유실은 한 곳에서 일어나지 않습니다. 발행 자체가 안 되는 구간, 도달 여부를 모르는 구간, 라우팅에 실패하는 구간, 메시지가 소멸하는 구간, 큐가 통째로 사라지는 구간, 처리 중 컨슈머가 죽는 구간 — 여섯이고 대책이 전부 다릅니다."
2
세 장치를 각 구간에 끼운다. "durable queue는 그릇을 살리고 — 큐 정의가 재시작 후 복원됩니다. persistent message(delivery mode 2)는 내용물을 살리고 — 메시지를 디스크에도 적습니다. publisher confirms는 접수증입니다 — 브로커가 책임을 넘겨받았다는 응답을 돌려줍니다."
3
가장 흔한 오해를 먼저 깬다. "셋은 서로를 대체하지 않습니다. durable 큐라도 transient 메시지면 그릇만 빈 채로 복원되고, persistent 메시지라도 비durable 큐면 복원할 그릇이 없어 디스크 기록이 무의미해집니다. 안전한 조합은 넷 중 하나뿐입니다."
4
셋을 다 켜도 남는 구멍을 스스로 꺼낸다. "다만 confirm은 '어떤 큐에 들어갔다'는 뜻이 아닙니다. 라우팅 대상이 0개여도 정상 ack이 오기 때문에, mandatory + return 콜백이나 alternate exchange를 짝으로 씁니다. 그리고 DB 커밋과 발행 사이의 원자성은 브로커 설정으로 못 막아 Outbox가 필요합니다."
5
한 층 더 내려가 마무리한다. 가산점 "persistent도 fsync 전 전원 차단은 못 막습니다. 단일 노드에서는 persistent가 최선이고, 그 이상은 복제(quorum queue)로 올라가야 합니다. 실무에서는 큐마다 다르게 가져갑니다 — 결제는 전부 켜고, 초당 수만 건 지표는 transient가 정당합니다."

6-2. 꼬리질문 셀프 테스트 답을 먼저 떠올린 뒤 펼친다

persistent를 켜면 성능이 얼마나 떨어지나요?힌트: 배수를 말하면 지는 질문이다 — 무엇을 말해야 하나

정확한 배수를 말하는 것은 위험하다. 디스크 종류, 메시지 크기, 큐 길이에 따라 크게 달라지기 때문이다. 대신 왜 떨어지는지를 말하면 된다.

메모리 큐는 쓰기가 RAM 접근이지만 persistent는 디스크 I/O와 주기적 fsync가 끼어든다. 특히 큐가 짧게 유지될 때는 차이가 작고(메시지가 금방 소비되어 디스크 기록이 상쇄됨), 큐가 길게 쌓일 때 차이가 커진다.

이어서 붙일 실무 판단 실무 판단은 데이터 성격으로 한다. 결제 · 주문처럼 유실이 곧 돈인 메시지는 예외 없이 persistent다. 초당 수만 건의 지표 · 로그성 메시지는 transient가 정당할 수 있다. 한 클러스터 안에서도 큐마다 다르게 가져가는 것이 정답이며, "전부 persistent" 또는 "전부 transient"라는 일괄 결정이 오히려 이상하다.
숫자를 답하는 질문이 아니라 "어떤 축으로 나누는가"를 답하는 질문이다
Kafka의 acks 설정과 대응시키면 어떻게 되나요?힌트: 목적은 같고 층위가 다르다 — 마지막 한 문장이 배점이다

목적은 같고 층위가 다르다. 4행짜리 표로 대응시킬 수 있다.

보장KafkaRabbitMQ
도달 여부 확인acks=1 (리더가 받음)publisher confirms
복제까지 확인acks=all + min.insync.replicasquorum queue + confirms (과반 복제 후 confirm)
디스크 기록기본적으로 로그 파일에 기록delivery_mode=2 (persistent)
정의 영속성토픽은 항상 영속durable=true (명시 필요)

핵심 차이는 Kafka는 디스크 기록과 복제가 기본 전제이고 RabbitMQ는 선택 사항이라는 점이다. Kafka는 애초에 로그 저장소로 설계되어 "안 적는다"는 선택지가 없지만, RabbitMQ는 메모리 큐가 기본이고 필요한 만큼 켜서 쓴다.

이 차이가 두 도구의 기본 성능 특성과
설정 실수의 위험도를 갈라놓는다
confirm을 받지 못하면 재발행해야 하는데, 그럼 중복이 생기지 않나요? 시니어 변별힌트: "생긴다"로 시작해야 하는 질문이다

생긴다. 그리고 피할 수 없다.

브로커가 메시지를 받고 confirm을 보내는 도중에 네트워크가 끊기면, 프로듀서는 "도달 못 함"과 "도달했지만 응답을 못 받음"을 구분할 방법이 없다. 재발행하면 중복이고, 안 하면 유실이다.

여기서 유실보다 중복이 낫다는 판단이 표준이다 —
중복은 컨슈머 쪽 멱등 처리로 흡수할 수 있지만 유실은 복구 수단이 없다

그래서 설계는 이렇게 간다.

1
프로듀서는 confirm을 못 받으면 재발행한다 (at-least-once 발행).
2
메시지에는 비즈니스 의미의 고유 ID를 넣는다 (message_id 속성 또는 페이로드 필드).
3
컨슈머는 그 ID로 처리 이력을 확인해 중복을 걸러낸다.
RabbitMQ에는 프로듀서 멱등성이 없다 — 이 한 줄이 변별점 Kafka에는 프로듀서 멱등성(enable.idempotence) 기능이 있어 브로커 수준에서 재전송 중복을 제거하지만, RabbitMQ에는 그에 해당하는 기능이 없다. 그래서 RabbitMQ 환경에서는 멱등 컨슈머가 선택이 아니라 필수라는 점을 짚으면 좋다.

구현 상세는 04-idempotent-consumer-implementation.md에서 다룬다.

구간을 좁히는 순서로 답하면 된다. 1절의 지도가 그대로 진단 순서가 된다.

0. DLQ
유실이 아니라 실패 후 격리일 수 있다. 신고의 상당수가 여기 얌전히 들어 있다.
1. 발행 로그 vs DB
DB는 완료인데 발행 로그가 없으면 (A) — Outbox 부재
2. exchange in/out
들어온 수 > 나간 수면 (C) 라우팅 실패. unroutable 큐를 본다
3. durable 여부 + 재시작 이력

유실 조사에서 가장 먼저 볼 곳은 DLQ다

0번을 먼저 확인하는 습관을 말하면 실전 감각이 드러난다. 나머지는 지도의 왼쪽에서 오른쪽으로 훑는 순서다.

durable 큐에 persistent 메시지를 넣었는데도 재시작 후 사라졌습니다. 무엇을 의심하나요?힌트: "둘 다 켰다"는 전제부터 의심한다 — 후보가 다섯이다

"둘 다 켰다"는 전제 자체를 먼저 검증하고, 그다음 애초에 큐에 있기는 했는지를 본다. 후보는 다섯이다.

1
메시지가 정말 persistent였는가. 큐는 durable인데 특정 프로듀서만 transient로 보내고 있는 경우가 흔하다 — 다른 언어 클라이언트나 스크립트는 기본값이 다를 수 있다. 관리 UI에서 큐의 persistent 메시지 수를 확인한다.
2
애초에 그 큐에 들어가 있었는가. 라우팅 키가 달라 다른 큐로 갔거나 어디에도 안 들어갔을 수 있다 (4-1). confirm ack을 받았다는 사실은 여기서 아무 증거가 되지 못한다.
3
큐 정책으로 폐기됐는가. 메시지 TTL이나 최대 길이(max-length) 초과 시 오래된 것부터 버리는 정책이 걸려 있으면 persistent 여부와 무관하게 사라진다. 재시작과 시점이 겹쳐 재시작 탓으로 오인되기 쉽다.
4
재시작 전에 이미 소비됐는가. 컨슈머가 auto-ack으로 받아가 처리에 실패했다면 브로커에는 이미 없다 — 이건 (F) 구간이지 (D)(E)가 아니다.
5
정상 종료가 아니라 전원 차단이었는가. fsync 직전에 서버 전원이 나갔다면 마지막 몇 건은 persistent라도 사라진다 (2-3). "몇 건만" 사라졌다면 이쪽, "전부" 사라졌다면 1~4번이다.
진단의 갈림길 한 줄 사라진 양이 "전부"인가 "마지막 몇 건"인가로 크게 갈린다. 전부라면 설정·라우팅 문제(구조적)이고, 마지막 몇 건이라면 fsync 창(물리적)이다. 이 질문을 먼저 던지면 후보 다섯 개가 즉시 둘로 줄어든다.
mandatory를 켰는데 그때 프로듀서가 죽어 있으면 return을 못 받지 않나요? 시니어 변별힌트: 맞다 — 그래서 무엇이 필요한가

맞다. 그것이 mandatory의 구조적 한계다. basic.return은 발행한 채널로 되돌아오는 프레임이라서 프로듀서 프로세스와 커넥션이 살아 있어야만 받을 수 있다. 프로듀서가 재시작 중이거나 이미 죽었다면 그 메시지는 그대로 사라진다.

mandatory + return

  • 장점: 프로듀서가 즉시 인지한다 — 어떤 라우팅 키가 틀렸는지 발행 코드 맥락에서 알 수 있다.
  • 단점: 프로듀서가 살아 있어야 하고, 메시지 실물은 어디에도 남지 않는다.

alternate exchange

  • 장점: 브로커에 실물이 남는다 — 사후 조사와 재처리가 가능하다. 프로듀서 코드가 필요 없다.
  • 단점: 프로듀서는 여전히 성공으로 안다 — unroutable 큐를 감시하지 않으면 아무도 모른다.
둘은 대체재가 아니라 보완재다 —
alternate exchange로 실물을 붙잡고, mandatory + return으로 즉시 알람을 올린다

덧붙일 한 줄: alternate exchange를 쓴다면 unroutable 큐의 메시지 수에 알람을 걸어야 한다. 그러지 않으면 "안전하게 모아두기만 하고 아무도 안 보는 큐"가 되어, 결국 유실과 같은 결과가 된다.

publisher confirms를 켜면 처리량이 떨어지나요?힌트: "비동기"라는 단어에 답의 절반이 있다 — 나머지 절반은 비용이 어디로 옮겨갔는가

쓰는 방식에 따라 완전히 달라진다. 그래서 "켜면 느려지나요"가 아니라 "기다리면 느려집니다"가 정확한 답이다.

콜백으로 받는 경우
발행 스레드는 계속 다음 건을 밀어 넣는다. 왕복을 기다리지 않으므로 처리량 손실이 거의 없다 — 이것이 confirms가 AMQP 트랜잭션을 밀어낸 이유다 (3-4).
매 건 동기로 기다리는 경우
waitForConfirms 계열을 발행마다 호출하면 왕복 지연이 그대로 처리량 상한이 된다. AMQP 트랜잭션과 비슷해진다.

다만 비용이 0이 되는 것은 아니고, 다른 곳으로 옮겨간다.

  • 미확인(in-flight) 발행을 어딘가에 들고 있어야 한다. 그 자리가 보통 outbox 테이블이고, 메모리에만 들고 있으면 프로듀서가 죽는 순간 재발행 대상 목록이 통째로 사라진다.
  • 브로커도 발행 번호별 상태를 추적해야 하므로 공짜는 아니다.
  • fanout처럼 여러 큐로 퍼지는 발행은 confirm이 늦게 온다 — 모든 대상 큐가 받아들인 뒤에 오기 때문이다 (3-1).
confirms의 비용은 지연이 아니라 "상태를 들고 있어야 한다"는 쪽에 있다
confirm 콜백 안에서 DB를 업데이트해도 되나요?힌트: 3-3의 정답 코드가 바로 그렇게 한다 — 그런데 조건이 있다

상태를 갱신하는 것 자체는 정답 패턴이다(3-3). 다만 콜백 안에서 오래 붙잡고 있으면 안 된다.

confirm 콜백은 클라이언트 라이브러리가 브로커와의 통신을 처리하는 스레드 계열에서 호출된다. 여기서 느린 쿼리, 외부 API 호출, 락 대기 같은 블로킹 작업을 하면 그 커넥션의 후속 프레임 처리 전체가 밀린다 — 발행 성능이 통째로 떨어지고, 심하면 confirm 처리가 적체된다.

콜백 안에서 해도 되는 일

  • PK 하나로 끝나는 짧은 UPDATE (outbox 행 상태 변경)
  • 메모리 자료구조에서 미확인 목록 제거
  • 지표 증가 · 짧은 로그

콜백 안에서 하면 안 되는 일

  • 여러 테이블을 건드리는 트랜잭션이나 느린 쿼리
  • 외부 HTTP 호출 · 알림 발송
  • 같은 스레드에서 다시 발행하며 기다리는 코드 (교착 위험)
무거운 일이 필요하면 콜백에서는 표시만 하고, 별도 스레드풀 · 별도 배치로 넘긴다

이 감각은 "콜백은 남의 스레드다"라는 한 문장으로 정리된다 — 리스너 스레드, 이벤트 루프, confirm 콜백 모두 같은 원칙이 적용된다.

publisher confirm과 컨슈머 ack은 같은 것인가요?힌트: 같은 단어인데 방향과 의미가 다르다

이름이 비슷하지만 방향도 의미도 다르다. 헷갈리면 답 전체가 흔들리므로 한 번 정리해 두는 것이 좋다.

publisher confirmconsumer ack
방향브로커 → 프로듀서컨슈머 → 브로커
의미"내가 책임을 넘겨받았다""내가 처리를 끝냈으니 지워도 된다"
막는 구간(B) 도달 여부 불명(F) 처리 중 컨슈머 사망
안 켰을 때유실을 인지하지 못한다auto-ack이면 유실 자체가 발생한다

confirm은 입구의 영수증, ack은 출구의 완료 서명 —
둘 다 있어야 파이프라인의 양 끝이 닫힌다
durable · persistent · confirms에 Outbox까지 다 하면 exactly-once인가요? 시니어 변별힌트: 아니다 — 무엇이 되고 무엇이 안 되는지 선을 그어야 한다

아니다. 전부 다 해도 at-least-once 발행이고, 중복 가능성은 남는다.

이유는 앞의 꼬리질문과 같다. confirm 응답이 유실되는 순간을 프로듀서가 구분할 수 없으므로, Outbox 퍼블리셔도 "확실하지 않으면 다시 보낸다"를 택할 수밖에 없다. Outbox는 (A) 구간의 유실을 없애는 장치이지 중복을 없애는 장치가 아니다.

전부 켰을 때 얻는 것
발행 유실 0에 수렴 — 여섯 구간이 모두 막힌다
그래도 남는 것
중복 전달 — 컨슈머 쪽 멱등 처리로만 흡수된다
"exactly-once를 달성했다"가 아니라
"at-least-once 발행 + 멱등 컨슈머로 exactly-once처럼 보이게 만들었다"가 정확한 표현이다

이 구분은 03-delivery-semantics-and-exactly-once-reality.md에서 본격적으로 다룬다. 면접에서 "exactly-once 됩니다"라고 단언하는 것은 위험하고, "효과적으로 한 번처럼 보이게 만든다"로 표현하는 것이 안전하다.

한 줄 요약
durable queue는 그릇을, persistent message는 내용물을, publisher confirms는 도달 여부를 지킨다 — 셋은 서로 다른 구간을 막으므로 전부 켜야 하고, 그러고도 남는 "라우팅 실패"는 mandatory / alternate exchange로, "DB 커밋과 발행 사이"는 Outbox로 따로 막아야 한다.
