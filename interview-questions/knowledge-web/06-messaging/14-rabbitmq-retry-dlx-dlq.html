RabbitMQ 재시도와 DLQ 설계 — DLX, TTL 지연 재시도, 그리고 requeue 무한 루프
「컨슈머 없는 큐 + TTL」이 곧 타이머다 — 시계는 브로커에게 맡기고, 지연 0ms 루프만 끊으면 된다

면접 질문: "RabbitMQ에서 재시도와 DLQ를 어떻게 설계하나요? (Dead Letter Exchange, TTL 기반 지연 재시도, requeue 무한 루프 함정)"

핵심 관전 포인트 — RabbitMQ에는 "실패한 메시지를 자동으로 보낼 곳"이 브로커 기능으로 있다. 큐에 x-dead-letter-exchange를 걸어두면 거부되거나(nack requeue=false), TTL이 만료되거나, 큐 길이 한도를 넘긴 메시지가 그 exchange로 넘어간다. 여기서 실무의 핵심 트릭이 나온다 — DLX가 다시 원래 큐를 가리키게 하면 "지연 재시도"가 공짜로 만들어진다. TTL 5초짜리 대기 큐에 넣었다가 만료되면 본 큐로 돌아오는 구조다. 반대로 절대 하면 안 되는 것이 basic.nack(requeue=true)의 무제한 반복이다. 지연이 전혀 없어 초당 수천 번 재시도하며 CPU를 태우고, 파싱 불가 메시지 하나가 워커 전체를 마비시킨다. 그리고 Spring AMQP의 기본값이 바로 requeue=true라서, 아무 설정도 안 한 컨슈머는 첫 번째 불량 메시지에서 이 루프에 빠진다.
  • 1
    실패를 먼저 두 갈래로 나눈다. "지금은 실패해도 나중엔 성공할 실패(일시적)"와 "몇 번을 해도 결과가 같은 실패(영구적)"를 예외 타입으로 구분하고, 영구 실패는 AmqpRejectAndDontRequeueException으로 재시도 없이 즉시 DLQ로 보냅니다. 이 분류가 없으면 전부 재시도해 무한 루프가 되거나 전부 격리해 DLQ가 범람합니다.
  • 2
    재시도의 시계는 브로커에게 맡깁니다. 큐에 x-dead-letter-exchange를 걸면 거부·TTL 만료·길이 초과 세 경우에 메시지가 옆길로 나가는데, 이 중 TTL 만료를 뒤집어 쓰면 지연 재시도가 됩니다 — 컨슈머를 붙이지 않은 TTL 대기 큐에 넣었다가 만료되는 순간 DLX를 통해 본 큐로 되돌리는 구조입니다. 백오프 단계마다 큐를 따로 둡니다(5초·30초·5분).
  • 3
    절대 금지는 지연 없는 requeue=true 반복입니다. 초당 수천 회 재시도로 CPU는 100%인데 처리량(ack rate)은 0이 되고, Spring AMQP 기본값이 default-requeue-rejected: true라 아무 설정도 안 한 컨슈머가 가장 위험합니다. 그래서 ① 기본값을 false로 바꾸고 ② 재시도 상한을 두고 ③ quorum queue의 x-delivery-limit으로 브로커 안전망까지 겁니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문: "RabbitMQ에서 재시도와 DLQ를 어떻게 설계하나요? (Dead Letter Exchange, TTL 기반 지연 재시도, requeue 무한 루프 함정)"

출제 의도: Kafka의 재시도 토픽에 대응하는 RabbitMQ의 표준 해법을 아는지 본다. 특히 basic.nack(requeue=true)가 만드는 무한 루프는 실무에서 CPU를 100%로 태우는 대표적 사고다. 실패 경로를 설계하지 않은 컨슈머가 치르는 대가를 겪어봤는지, 그리고 "재시도할 가치가 있는 실패"와 "몇 번을 해도 같은 실패"를 구분하는 감각이 있는지 확인한다.

괄호 안 세 단어가 곧 채점 기준이다 — 뒤로 갈수록 배점이 커진다 ① Dead Letter Exchange는 "발동 조건 세 가지를 말할 수 있는가"로 갈리는 정의 구간, ② TTL 기반 지연 재시도는 "컨슈머 없는 대기 큐가 타이머"라는 조립 원리와 큐를 왜 지연 단계별로 나누는가(head-of-line blocking)까지 가는 설계 구간, ③ requeue 무한 루프는 기본값이 위험하다는 사실과 3중 방어선을 아는 운영 구간이다. 이 페이지는 1절에서 실패를 분류하고, 2절에서 장치(DLX)를, 3절에서 그 장치로 조립한 패턴(지연 재시도)을, 4·5절에서 사고와 사후 운영을 다룬다.
먼저 깨야 할 오해 4개 — 아래 절들이 각각 이것을 겨냥한다 ① "실패하면 일단 재시도하면 된다" → 영구 실패에 재시도는 자원 낭비이자 무한 루프다. 분류가 코드에 없으면 둘 중 한쪽으로 반드시 무너진다 (1절).
② "requeue=true가 곧 재시도다" → 지연이 0ms라서 재시도가 아니라 장애다. 게다가 Spring 기본값이라 아무것도 안 한 상태가 가장 위험하다 (4절).
③ "RabbitMQ는 poison pill이 없으니 안전하다" → 구조적 이점은 맞지만 prefetch=1 · 컨슈머 1대에서 같은 건을 계속 requeue하면 결국 앞이 막힌다. 구조가 유리해도 설계를 안 하면 같은 곳에 도달한다 (1-2).
④ "DLQ에 넣었으니 끝" → 왜 실패했는지(진단 정보)와 어떻게 되돌릴지(재투입 절차)가 없으면 DLQ는 그냥 열어볼 수 없는 쓰레기통이다 (5절).

1. 실패는 두 종류다 — 분류가 설계의 출발점

컨슈머가 메시지 처리에 실패했다. 재시도해야 하는가?

답은 하나의 질문으로 갈린다. 실패의 원인이 시간에 따라 변하는가. 이 질문에 "예"면 기다렸다 다시 하면 되고, "아니오"면 백 번을 해도 같은 결과다.

판별식 — "시간이 지나면 결과가 달라지는가?" 이 한 문장이 재시도 경로 전체를 가른다

1-1. 예외 타입이 곧 실패 유형이다

분류를 주석이나 문서가 아니라 예외 타입으로 표현해야 하는 이유는 단순하다. 재시도 여부를 판단하는 것은 프레임워크이고, 프레임워크가 읽을 수 있는 것은 예외 타입뿐이기 때문이다.

문제 뭉뚱그린 컨슈머 — 모든 실패가 같은 취급을 받는다
@RabbitListener(queues = "payment.process")
public void handle(PaymentEvent event) {
    handler.handle(event);   // 예외가 그대로 올라간다
}

// application.yml — 아무것도 설정하지 않음
// default-requeue-rejected 기본값 = true
// → 파싱 불가 메시지 한 건이 무한 requeue 루프

파싱 실패든 DB 타임아웃이든 결과가 똑같다 — 지연 0ms로 되돌아온다. 영구 실패는 영원히 되돌아온다.

개선 예외 타입으로 두 갈래를 나눈다
@RabbitListener(queues = "payment.process")
public void handle(PaymentEvent event) {
    try {
        handler.handle(event);
    } catch (DataAccessResourceFailureException
             | ResourceAccessException e) {
        throw e;              // 일시적 → 재시도 대상
    } catch (JsonParseException | ValidationException e) {
        throw new AmqpRejectAndDontRequeueException(
                "복구 불가 메시지", e);   // 영구 → 즉시 DLQ
    }
}

AmqpRejectAndDontRequeueException은 Spring AMQP가 특별 취급하는 예외로, 재시도 없이 곧바로 거부하게 만든다. 영구 실패를 표현하는 표준 수단이다.

1-2. Kafka와 비교하면 RabbitMQ가 유리한 지점 — 그리고 그 이점이 사라지는 조건

이 문제에서 RabbitMQ는 구조적 이점이 있다. Kafka의 오프셋은 "여기까지 처리했다"는 숫자 하나라서, 5번 메시지가 계속 실패하면 6번 이후를 처리할 방법이 없다. 한 건이 파티션 전체를 막는다(poison pill). 그래서 Kafka는 재시도 토픽이라는 우회로를 반드시 설계해야 한다.

RabbitMQ는 메시지마다 상태를 추적하므로 실패한 한 건만 떼어내 DLQ로 보내고 나머지는 그대로 흘려보낼 수 있다. 뒤가 막히지 않는다.

이 이점에는 전제가 있다 "RabbitMQ는 뒤가 안 막힌다"는 말은 컨슈머가 여러 건을 동시에 처리할 수 있을 때의 이야기다. prefetch=1에 컨슈머 1대이고 그 한 건을 계속 requeue=true로 되돌리면, 그 메시지가 계속 큐 앞에 서 있어 결국 뒤가 막힌다. 면접에서 "RabbitMQ는 poison pill이 없습니다"라고만 답하면 바로 이 반례가 되돌아온다.

2. Dead Letter Exchange — 브로커가 깔아 둔 옆길

이 절은 장치를 깔고, 다음 절에서 그 장치로 패턴을 조립한다. 순서를 이렇게 잡은 이유는 지연 재시도가 별개의 기능이 아니라 DLX를 재료로 조립한 결과물이기 때문이다. DLX의 발동 조건 세 가지를 모른 채 지연 재시도 구성도부터 보면 화살표 몇 개가 왜 그렇게 이어지는지가 안 보인다.

비유 — dead letter는 우체국의 「사장 편지」다 Dead letter(사장 편지)는 우편에서 "배달도 반송도 못 하는 편지"를 뜻하는 말이다. 주소가 틀렸거나, 수취인이 거부했거나, 보관 기한이 지난 편지들이 모이는 별도 창구가 있다. RabbitMQ의 DLX는 정확히 그 창구이고, 큐마다 "우리 큐에서 처리 못 한 편지는 저기로 보내라"고 주소를 적어두는 것이 x-dead-letter-exchange 설정이다.

2-1. 무엇이 dead letter가 되는가 — 발동 조건 셋

DLX 발동 조건 세 가지 — 세 번째는 잘 안 쓰이지만, 두 번째가 이 문서의 핵심 도구다.
조건언제 발생하나x-death의 reason실무에서의 쓰임
basic.nack/basic.reject를 requeue=false로컨슈머가 "다시 주지 마라"며 거부rejected영구 실패·재시도 소진 건을 DLQ로 격리
메시지 TTL 만료큐(x-message-ttl)나 메시지(expiration)에 설정한 수명이 다 됨expired지연 재시도의 타이머 — 3절 전체가 이 한 줄에서 나온다
큐 길이 한도 초과x-max-length를 넘겨 오래된 것부터 밀려남maxlenDLQ 자체가 무한히 커지는 것을 막는 최후 방어

DLX 발동 3조건 암기 — 거 · 만 · 넘 셋을 못 대면 정의 구간에서 떨어진다

거 — 거부됐다
nack(requeue=false)
reason: rejected
만 — 만료됐다

넘 — 넘쳤다

"거부·만료·넘침" 세 글자만 붙잡으면 된다. 그리고 한마디 덧붙이면 좋다 — "컨슈머가 살아 있지 않아도 발동하는 조건이 둘(만료·넘침)이라, DLX는 애플리케이션과 무관하게 동작하는 브로커 기능입니다."

2-2. 기본 구성 — 그리고 라우팅 키를 빠뜨렸을 때의 순환 사고

기본형 본 큐 · DLX · DLQ · 바인딩 네 개면 끝난다
@Bean Queue paymentQueue() {
    return QueueBuilder.durable("payment.process")
            .deadLetterExchange("payment.dlx")        // 실패 시 갈 곳
            .deadLetterRoutingKey("payment.dead")     // 그때 붙일 라우팅 키
            .build();
}

@Bean DirectExchange paymentDlx() { return new DirectExchange("payment.dlx"); }

@Bean Queue paymentDlq() { return QueueBuilder.durable("payment.dlq").build(); }

@Bean Binding dlqBinding() {
    return BindingBuilder.bind(paymentDlq()).to(paymentDlx()).with("payment.dead");
}
함정 라우팅 키를 생략하면 — 원래 키가 그대로 유지된다
QueueBuilder.durable("payment.process")
        .deadLetterExchange("payment.dlx")
        // deadLetterRoutingKey 미지정
        // → 원래 라우팅 키(payment.process)가 그대로 붙는다
        .build();

// payment.dlx가 원본 exchange와 같은 바인딩 구조를 갖고 있으면
// 메시지가 「원래 큐」로 되돌아간다 → 지연 없는 순환
// 실패 → DLX → 본 큐 → 실패 → DLX → ... 무한
개선 DLX 전용 라우팅 키를 항상 명시한다
QueueBuilder.durable("payment.process")
        .deadLetterExchange("payment.dlx")
        .deadLetterRoutingKey("payment.dead")
        // 본 큐 라우팅 키와 「겹치지 않는」 이름
        .build();

// payment.dead는 DLQ에만 바인딩되어 있으므로
// 되돌아갈 경로 자체가 없다 → 순환 불가능
// 습관: dead letter용 키는 접미사(.dead)로 구분한다
이 함정이 위험한 이유 — 설정 오류가 아니라 「동작하는 오류」라서 라우팅 키를 빠뜨려도 선언은 성공하고 메시지도 흐른다. 다만 DLQ 대신 본 큐로 흘러갈 뿐이다. 개발 환경에서는 실패 메시지가 없어서 안 드러나고, 운영에서 첫 실패가 났을 때 순환이 시작된다. "DLX를 걸었는데 DLQ가 비어 있고 본 큐만 계속 도는" 증상이면 가장 먼저 이 설정을 본다.

2-3. x-death 헤더 — 몇 번 죽었는지 브로커가 세어 준다

메시지가 dead letter가 될 때마다 브로커는 x-death라는 헤더 배열을 붙이거나 갱신한다. 여기에는 원래 큐 이름, 이유, 시각, 그리고 몇 번째인지(count)가 들어 있다.

이 count가 실무에서 매우 유용하다. 애플리케이션이 재시도 횟수를 따로 저장하지 않아도, 브로커가 세어준 값으로 "이제 그만하고 DLQ로"를 판단할 수 있다.

읽는 법 x-death에서 재시도 횟수 꺼내기
@SuppressWarnings("unchecked")
private int deathCount(Message message) {
    List<Map<String, Object>> deaths =
            (List<Map<String, Object>>) message.getMessageProperties()
                    .getHeaders().get("x-death");
    if (deaths == null || deaths.isEmpty()) return 0;
    // count는 「같은 큐/이유 조합으로 몇 번 죽었는가」를 브로커가 누적한 값이다
    return ((Long) deaths.get(0).get("count")).intValue();
}

x-death는 「새로 발행하면」 초기화된다 무한 재시도의 흔한 원인

재시도 구현이 "원본을 그대로 되돌리는" 방식이면 count가 누적되지만, "새 메시지로 다시 발행하는" 방식이면 매번 0부터 시작해 무한 재시도가 된다. 후자를 쓴다면 재시도 횟수를 커스텀 헤더에 직접 담아 증가시켜야 한다.

원본 되돌리기→x-death.count 사용 가능 새로 발행→x-retry-count 같은 커스텀 헤더 필수

3. 지연 재시도 — 브로커를 타이머로 쓰는 표준 패턴

여기서부터가 2절의 장치를 재료로 쓰는 부분이다. 특히 발동 조건 두 번째 — TTL이 만료되면 메시지가 DLX로 넘어간다 — 하나만 뒤집어 쓰면 브로커가 타이머 역할을 하게 만들 수 있다.

3-1. 왜 「지연」이 반드시 필요한가

일시적 실패에 즉시 재시도하면 대개 또 실패한다. DB가 죽어 있는데 1ms 뒤에 살아날 리 없다. 그런데 즉시 재시도는 부하를 더한다. 다운스트림이 힘들어서 실패한 것인데 재시도가 트래픽을 증폭시켜 회복을 더 어렵게 만든다.

즉시 재시도의 자기 강화 고리 — 이것이 장애를 길게 만든다 다운스트림 지연 → 타임아웃 실패 → 즉시 재시도 → 다운스트림 요청량 2배 → 더 심한 지연 → 더 많은 실패 → 재시도 폭풍. 회복하려던 서비스를 재시도가 다시 눕힌다. 그래서 재시도에는 지연이 필요하고, 보통 점점 늘어나는 지연(exponential backoff)을 쓴다.
1차 실패→5초 뒤→30초 뒤→5분 뒤→DLQ (사람이 본다)

문제는 RabbitMQ의 큐에는 "N초 뒤에 배달" 기능이 없다는 것이다. 큐는 들어온 순서대로 즉시 내보낸다. 그래서 우회가 필요하다.

지연 재시도의 전부는 이 한 줄이다 이 문장을 먼저 말하고 그림을 설명한다

컨슈머 없는 큐 + TTL = 타이머

대기 큐에는 컨슈머를 붙이지 않는다. 아무도 가져가지 않으므로 메시지는 TTL이 다할 때까지 그 자리에 머물고, 만료되는 순간 dead letter가 되어 본 큐로 되돌아간다. 애플리케이션은 sleep도 스케줄러도 갖지 않는다 — 시간을 재는 일 전부가 브로커의 몫이 된다.

3-2. 대기 큐(wait queue) 패턴 — 전체 구성도

구현 대기 큐 선언과 단계 선택
// 5초, 30초, 5분 — 세 단계 대기 큐
@Bean Queue retry5s()  { return delayQueue("payment.retry.5s",  5_000); }
@Bean Queue retry30s() { return delayQueue("payment.retry.30s", 30_000); }
@Bean Queue retry5m()  { return delayQueue("payment.retry.5m",  300_000); }

private Queue delayQueue(String name, int ttlMillis) {
    return QueueBuilder.durable(name)
            .ttl(ttlMillis)                                // 이 큐의 모든 메시지 수명
            .deadLetterExchange("payment.exchange")        // 만료되면 본 exchange로
            .deadLetterRoutingKey("payment.process")       // 본 큐로 라우팅
            .build();
    // 이 큐에는 @RabbitListener를 「붙이지 않는다」 — 그것이 타이머가 되는 조건
}

// 컨슈머는 x-death count를 보고 다음 단계 대기 큐를 고른다
private String nextRetryQueue(int attempt) {
    return switch (attempt) {
        case 0 -> "payment.retry.5s";
        case 1 -> "payment.retry.30s";
        case 2 -> "payment.retry.5m";
        default -> "payment.dlq";   // 상한 초과 → 사람이 봐야 한다
    };
}

3-3. 반드시 알아야 할 함정 — head-of-line blocking 가산점 구간

여기서 실무자를 가르는 지점이 나온다. TTL을 큐 단위(x-message-ttl)가 아니라 메시지 단위(expiration 속성)로 주면 순서 문제가 생긴다.

RabbitMQ는 큐의 맨 앞 메시지만 만료 여부를 검사한다. 뒤쪽에 있는 메시지는 앞의 것이 나가야 검사 대상이 된다.

이 문장을 말할 수 있으면 실제로 구현해 본 사람이다 가산점 포인트

"메시지 단위 TTL은 큐 안의 지연 시간이 모두 같을 때만 안전하다"

뒤집어 말하면 — 메시지마다 다른 지연을 자유롭게 주고 싶다면 TTL 대기 큐가 아니라 다른 수단(delayed message 플러그인, DB + 스케줄러)을 봐야 한다. 재시도 백오프는 지연 값이 몇 종류로 고정되어 있어서 이 패턴이 잘 맞는 대표적 사례다.

3-4. 애플리케이션 내부 재시도와의 역할 분담

Spring AMQP는 리스너 컨테이너 수준의 재시도도 제공한다. 이것은 같은 스레드에서 sleep하며 재시도한다. 그래서 대기 큐 재시도와 성질이 다르다.

설정 인프로세스 재시도 — 짧은 흔들림 흡수용
spring:
  rabbitmq:
    listener:
      simple:
        default-requeue-rejected: false   # 무한 루프 방지 (4절)
        retry:
          enabled: true
          max-attempts: 3
          initial-interval: 200ms
          multiplier: 2
두 재시도는 경쟁 관계가 아니라 담당 구간이 다르다. 표의 첫 두 행이 성질 차이의 뿌리다.
인프로세스 재시도 (Spring retry)대기 큐 재시도 (TTL + DLX)그래서 무엇이 갈리는가
지연 동안스레드가 잡혀 있다스레드가 자유롭다동시에 처리 가능한 건수
적합한 지연밀리초 ~ 수 초수 초 ~ 수 시간다운스트림 회복 시간과 맞춰야 한다
컨슈머 재시작 시재시도 상태가 사라진다
(메시지는 unacked라 복구됨)		브로커에 남아 있어 무관배포 중 안정성
순서그 메시지가 앞을 막는다뒤로 빠지므로 안 막는다처리량 vs 순서 (6-2 꼬리질문)
가시성로그로만 보인다대기 큐 깊이로 눈에 보인다"지금 몇 건이 재시도 대기 중인가"를 답할 수 있는가
비용왕복 없음 (제자리)브로커 왕복 + 큐 선언 관리아주 짧은 흔들림에 쓰면 과하다
둘을 같이 쓰는 것이 정석이다 — 비유하면 「제자리에서 기다리기 vs 번호표 뽑고 자리 비우기」 창구에서 서류가 하나 빠졌을 때, 몇 초면 찾을 것 같으면 그 자리에서 기다린다(인프로세스 재시도). 발급받아 와야 하는 서류라면 번호표를 다시 뽑고 자리를 비운다(대기 큐). 짧은 흔들림은 인프로세스로 즉시 흡수하고(수백 ms), 그래도 실패하면 대기 큐로 넘겨 길게 기다린다(수 분). 인프로세스만 쓰면 긴 장애에서 스레드가 다 잠기고, 대기 큐만 쓰면 아주 짧은 흔들림에도 왕복 비용을 치른다.

4. requeue 무한 루프 — 기본값이 만드는 장애와 3중 방어선

3절이 "실패 경로를 제대로 설계했을 때"의 그림이라면 이 절은 그 반대편이다. 재시도 경로를 설계하지 않은 컨슈머에게 실제로 벌어지는 사고를 본다.

4-1. 무한 루프는 어떻게 만들어지는가

basic.nack(requeue=true)는 메시지를 지연 없이 즉시 큐로 되돌린다. 그 메시지가 다시 배달되고, 또 실패하고, 또 되돌아간다.

문제 설정 파일에 rabbitmq 항목이 아예 없는 상태
spring:
  rabbitmq:
    host: mq.internal
    # listener 설정 없음
    # default-requeue-rejected 기본값 true 적용
    # retry 비활성 → 상한도 없음

# 결과: 첫 불량 메시지에서 무한 루프.
# DLX를 걸어두었더라도 「거부되지 않으니」 DLQ로 가지 않는다.

DLX를 선언해 둔 것만으로는 안전해지지 않는다. DLX는 거부(requeue=false)될 때 작동하는데, requeue=true면 애초에 거부가 아니다.

개선 세 줄로 루프를 끊고 상한을 세운다
spring:
  rabbitmq:
    host: mq.internal
    listener:
      simple:
        default-requeue-rejected: false  # ① 루프 차단
        retry:
          enabled: true
          max-attempts: 3                # ② 상한
          initial-interval: 200ms
          multiplier: 2                  # 지수 백오프

이제 재시도 소진 시 거부되고, 거부되면 DLX로 넘어간다. 여기에 3절의 대기 큐를 얹으면 짧은 재시도 → 긴 재시도 → DLQ의 전체 경로가 완성된다.

4-2. 세 가지 방어선 — 층을 나눠 거는 것이 요령이다

3차 방어 quorum queue의 배달 횟수 상한
@Bean Queue paymentQueue() {
    return QueueBuilder.durable("payment.process")
            .quorum()                                 // quorum queue로 선언
            .deliveryLimit(5)                         // 5회 배달 후 자동 dead letter
            .deadLetterExchange("payment.dlx")
            .build();
}

3중 방어선 — 층과 담당을 짝지어 외운다 면접에서 셋을 순서대로 말한다

1차 · 앱 설정
default-requeue-rejected: false
담당: 루프의 존재 자체를 없앤다
2차 · 앱 상한
max-attempts / x-death count
담당: 정책 — 몇 번, 얼마나 기다려서
3차 · 브로커 상한
quorum queue x-delivery-limit
담당: 앱 버그에 대한 안전망

4-3. 진단 — 지표 두 개를 나란히 보면 즉시 판별된다

증상 ①
CPU는 높은데 처리량(ack rate)은 0에 가깝다. 일하지 않으면서 바쁘다.
증상 ②
큐의 Ready 수는 그대로인데 deliver rate만 비정상적으로 높다. 배달은 되는데 완료가 안 된다.
증상 ③
컨슈머 로그에 같은 메시지 ID의 같은 에러가 반복된다.

5. DLQ 운영 — 버리는 곳이 아니라 병원이다

무한 루프를 끊고 상한을 걸어두면 실패한 메시지는 결국 DLQ에 모인다. 여기서부터가 사고 이후의 국면이다.

비유 — DLQ는 쓰레기통이 아니라 병원이다 DLQ를 "실패한 메시지를 버리는 쓰레기통"으로 취급하면 앞에서 애써 격리한 의미가 없어진다. DLQ는 병원에 가깝다 — 환자를 눕혀 두는 곳이고, 무엇 때문에 쓰러졌는지 적힌 진단서가 함께 있어야 하며, 나을 수 있는 환자를 내보내는 퇴원 절차가 미리 마련되어 있어야 한다. 아래 셋이 그 진단서 · 감시 · 퇴원 절차에 각각 대응한다.
① 진단서
예외 메시지·스택트레이스·원본 라우팅 정보·추적 ID를 헤더에 함께 담는다
② 감시
깊이 > 0이면 알람. 큐마다 심각도를 다르게. 유입 속도도 함께 본다
③ 퇴원
재투입(redrive) 절차를 평상시에 만들어 둔다 — 장애 중에 만들면 늦는다

5-1. 진단 정보를 함께 담는다

DLQ에 메시지 본문만 들어 있으면 "왜 실패했는지" 알 수 없다. 원본 메시지는 실패 이유를 모른다. 며칠 뒤에 그 큐를 열어본 사람은 본문만 보고 원인을 추측해야 한다.

해법 RepublishMessageRecoverer — 거부 대신 「재발행」해 예외 정보를 붙인다
@Bean
MessageRecoverer messageRecoverer(RabbitTemplate template) {
    // 단순 거부 대신 재발행 → 스택트레이스와 원인 예외가 헤더로 붙는다
    // x-exception-message, x-exception-stacktrace, x-original-exchange,
    // x-original-routingKey 등이 자동 추가된다
    return new RepublishMessageRecoverer(template, "payment.dlx", "payment.dead");
}
자동으로 붙는 것
x-exception-message · x-exception-stacktrace · x-original-exchange · x-original-routingKey
직접 담으면 좋은 것
실패 시각 · 컨슈머 애플리케이션 버전 · 요청 추적 ID(trace id)
특히 추적 ID가 있으면 DLQ 메시지 하나에서 전체 호출 경로 로그로 바로 넘어갈 수 있다
단, 재발행은 x-death를 초기화한다 — 2-3의 함정과 정면으로 만난다 RepublishMessageRecoverer는 이름 그대로 새 메시지로 다시 발행한다. 진단 정보를 얻는 대신 x-death 누적을 잃는다. 재시도 횟수를 x-death로 세는 구조와 진단 정보를 붙이는 재발행을 함께 쓰려면, 재시도 횟수는 커스텀 헤더로 직접 관리하는 편이 안전하다. "둘 다 쓰되 카운터는 내가 든다"가 실무의 정리다.

5-2. 유입 자체를 알람으로 건다

DLQ는 정상 상태에서 비어 있어야 하는 큐다. 그래서 알람 조건이 단순하다.

DLQ 알람 3원칙 임계치 100건 같은 값을 잡으면 안 되는 이유까지

① 깊이 > 0이면 알람
100건 같은 임계치는 나쁘다. 결제 실패 1건은 그 자체로 사람이 봐야 하는 사건이기 때문이다.
② 큐마다 심각도를 다르게
결제 DLQ는 즉시 호출, 알림 DLQ는 근무 시간 내 확인. 임계치가 아니라 심각도로 조절한다.
③ 유입 「속도」도 본다
갑자기 초당 수십 건이면 개별 메시지 문제가 아니라 다운스트림 장애다. 메시지보다 다운스트림을 먼저 본다.

5-3. 재투입(redrive) 절차를 미리 만든다

DLQ에 쌓인 메시지는 원인을 고친 뒤 다시 처리해야 한다. 이 절차를 장애 상황에서 처음 만들면 늦는다.

RabbitMQ에는 rabbitmq_shovel이라는 플러그인이 있어 한 큐의 메시지를 다른 큐/exchange로 옮길 수 있다. DLQ → 본 exchange로 shovel을 임시로 걸었다가 비면 끄는 방식이 손이 가장 덜 간다.

직접 구현 평소에는 꺼져 있다가 운영자가 켜서 돌리는 재투입 컨슈머
@RabbitListener(queues = "payment.dlq", autoStartup = "false", id = "dlqRedrive")
public void redrive(Message message) {
    // 재투입 이력을 남긴다 — 몇 번 재투입됐는지 모르면 또 무한 루프다
    message.getMessageProperties().setHeader("x-redrive-count",
            redriveCount(message) + 1);
    rabbitTemplate.send("payment.exchange", "payment.process", message);
}
// 운영자가 rabbitListenerEndpointRegistry.getListenerContainer("dlqRedrive").start()

정상 운영이라면 DLQ에 들어온 건은 알람이 울리고 사람이 처리한다. 쌓여만 간다면 셋 중 하나다.

없다. 오히려 해롭다. 죽어 있는 서비스에 재시도 트래픽을 계속 보내면 회복을 방해하고, 그동안 DLQ가 정상 메시지로 가득 차 진짜 불량 메시지가 묻힌다.

이때 필요한 것은 서킷 브레이커와 소비 중단이다.

  • 다운스트림 실패율이 임계치를 넘으면 리스너 컨테이너를 아예 멈춘다. 메시지는 큐에 그대로 쌓이고, 브로커가 이미 저장소 역할을 하고 있으므로 유실되지 않는다.
  • 다운스트림이 회복되면 컨테이너를 다시 시작한다. 쌓인 메시지가 순서대로 처리된다.

장애 상황에서는 재시도보다 멈추는 것이 낫다 — 큐가 이미 버퍼 역할을 하고 있다

이 판단은 메시징 시스템을 운영해 본 사람의 답이다. 덧붙이면 좋은 한 줄 — "멈추면 큐가 쌓이는데 괜찮냐"는 반문에는 "큐 적체는 관측 가능하고 복구 가능한 상태지만, 재시도 폭풍은 다운스트림 복구 자체를 막습니다"로 답한다.

x-death의 count는 정확히 무엇을 세나요? 재발행하면 왜 0이 되나요?힌트: 헤더는 메시지에 붙어 다닌다 — 그럼 "새 메시지"에는?

x-death는 배열이고, 각 원소는 "어떤 큐에서 어떤 이유로 죽었는가"의 조합을 나타낸다. count는 그 조합으로 몇 번 죽었는지를 브로커가 누적한 값이다. 원소에는 큐 이름·reason·시각·라우팅 키 등이 함께 들어 있다.

초기화되는 이유는 단순하다. x-death는 메시지 헤더이고, 새 메시지를 발행하면 헤더도 새로 만들어지기 때문이다. 브로커는 "이 메시지가 예전 그 메시지의 후손인지" 알 방법이 없다.

count가 누적되는 경로

  • 컨슈머가 nack(requeue=false)로 거부
  • 대기 큐에서 TTL 만료
  • 큐 길이 초과로 밀려남

공통점 — 브로커가 원본 메시지를 옮기는 것이다.

count가 초기화되는 경로

  • 애플리케이션이 rabbitTemplate.send()로 다시 발행
  • RepublishMessageRecoverer 사용
  • 재투입(redrive) 컨슈머가 본 exchange로 재발행

공통점 — 애플리케이션이 새 메시지를 만드는 것이다.

그래서 실무의 정리는 이렇다 재발행을 한 번이라도 쓰는 구조라면, 재시도 횟수는 x-death가 아니라 커스텀 헤더(x-retry-count)로 직접 관리한다. 두 방식을 섞으면 "어떤 메시지는 세지고 어떤 메시지는 안 세지는" 가장 찾기 힘든 버그가 된다.
deadLetterRoutingKey를 지정하지 않으면 어떻게 되나요? 함정힌트: "아무 키도 안 붙는다"가 아니다

원래 라우팅 키가 그대로 유지된다. 이것이 뜻밖의 사고를 만든다 — DLX가 원본 exchange와 같은 바인딩 구조를 갖고 있으면 메시지가 원래 큐로 돌아가 순환한다.

위험한 이유는 설정 오류로 드러나지 않는다는 점이다. 선언은 성공하고, 메시지도 흐르고, 로그에도 아무 경고가 없다. 운영에서 첫 실패가 났을 때 비로소 순환이 시작된다.

증상 — DLX를 걸었는데 DLQ는 비어 있고 본 큐만 계속 돈다

대응은 습관 하나로 끝난다. DLX용 라우팅 키를 항상 명시하고, 본 큐 라우팅 키와 겹치지 않는 이름(접미사 .dead)을 쓴다. 그러면 되돌아갈 경로 자체가 존재하지 않으므로 순환이 구조적으로 불가능해진다.

대기 큐에 컨슈머를 붙이면 어떻게 되나요?힌트: TTL은 "큐에 머무는 동안" 흐른다

지연이 사라진다. 대기 큐가 타이머로 동작하는 이유는 아무도 가져가지 않아서 메시지가 TTL이 다할 때까지 큐에 머물기 때문이다. 컨슈머를 붙이면 만료되기 전에 바로 배달되므로, 그 큐는 그냥 또 하나의 처리 큐가 된다.

실수하기 쉬운 지점은 와일드카드 리스너다. payment.* 같은 패턴으로 큐를 잡거나, 자동 구성으로 선언된 모든 큐에 컨슈머를 붙이는 설정이 있으면 대기 큐까지 딸려 들어간다.

대기 큐의 정의는 "TTL이 걸려 있고 컨슈머가 없는 큐" — 둘 중 하나라도 빠지면 타이머가 아니다

점검 방법은 간단하다. 관리 콘솔에서 대기 큐의 Consumers 열이 0인지 확인한다. 0이 아니면 지연 재시도는 이미 동작하지 않고 있다.

재시도 상한은 몇 번이 적당한가요?힌트: 숫자를 답하면 근거를 묻는 반문이 온다

횟수가 아니라 총 지연 시간으로 역산하는 것이 정답의 형태다. 물어야 할 것은 "몇 번 할까"가 아니라 "다운스트림이 이 시간 안에 돌아오는가"다.

예를 들어 3절의 구성(인프로세스 0.6초 + 5초 + 30초 + 5분)은 총 예산 약 5분 36초다. 다운스트림의 평균 복구 시간이 3분이라면 이 예산은 충분하고, 10분이라면 마지막 단계를 늘리거나 한 단계를 더 둬야 한다.

입력값 ①
다운스트림 평균 복구 시간 — 배포 소요, 재시작 시간, 장애 대응 착수 시간
입력값 ②
이 메시지가 늦어져도 되는 한계 — 결제 승인은 분 단위, 야간 집계는 시간 단위
결과
둘 중 짧은 쪽이 총 예산. 백오프 단계는 그 예산을 채우도록 구성한다

덧붙이면 좋은 한 줄 — "상한을 넘긴 건은 실패가 아니라 '자동 처리를 포기하고 사람에게 넘긴 것'"이다. 그래서 상한을 늘리는 것과 DLQ 처리 인력을 늘리는 것은 같은 축의 선택이고, 무한정 늘리는 것은 사람이 볼 시점을 미루는 것일 뿐이다.

quorum queue의 x-delivery-limit이 있으면 애플리케이션 상한은 필요 없지 않나요? 시니어 변별힌트: 두 상한이 세는 대상이 다르다

층이 다르다. 하나로 다른 하나를 대체할 수 없다.

애플리케이션 상한브로커 x-delivery-limit
세는 대상비즈니스적 재시도 시도 횟수배달 횟수 (원인 불문)
백오프단계별 지연을 줄 수 있다없다 — 그냥 끊는다
실패 유형 구분일시적/영구적을 나눠 다르게 처리구분하지 않는다
앱 버그에 대한 내성코드가 틀리면 같이 틀린다앱과 무관하게 동작한다
역할정책안전망

즉 정책은 앱이 정하고, 그 정책이 무너졌을 때 브로커가 끊는다. 브로커 상한만 두면 백오프 없이 최대 속도로 N번 배달되고 끝이라 일시적 장애를 넘기지 못하고, 앱 상한만 두면 코드 버그·헤더 초기화 같은 사고에 방어가 없다.

앱 상한은 "어떻게 재시도할까", 브로커 상한은 "어떤 경우에도 여기서 멈춘다"

한 가지 더 짚으면 좋다 — x-delivery-limit은 quorum queue의 기능이므로, classic queue를 쓰고 있다면 이 층 자체가 없다. "우리는 3중 방어선 중 2개만 있다"는 사실을 아는 것도 답의 일부다.

DLQ 하나를 여러 큐가 공유해도 되나요?힌트: 알람과 재투입 두 가지를 상상해 본다

기술적으로는 된다. 여러 큐의 DLX를 같은 exchange로 두고 라우팅 키만 달리하거나, 아예 같은 DLQ로 모을 수 있다. 그런데 운영 두 지점에서 곤란해진다.

① 알람 심각도를 나눌 수 없다

결제 실패 1건은 즉시 호출, 알림 실패 1건은 근무 시간 확인인데 한 큐에 섞이면 둘 중 하나에 맞춰야 한다. 결제 기준으로 맞추면 알림 때문에 새벽에 깨고, 알림 기준으로 맞추면 결제 사고를 늦게 안다.

② 재투입 경로가 섞인다

재투입은 "어느 exchange로, 어느 라우팅 키로 되돌릴 것인가"가 필요하다. 섞여 있으면 메시지마다 헤더를 보고 분기해야 하고, 특정 유형만 골라 재투입하기도 어렵다.

기본은 본 큐 하나당 DLQ 하나 — 알람 심각도와 재투입 경로가 큐 단위로 정해지기 때문

다만 큐가 수십 개인 대규모 시스템에서는 DLQ가 그만큼 늘어나 관리 부담이 생긴다. 이때는 "심각도 등급별로 DLQ를 묶는" 절충이 현실적이다 — critical DLQ / normal DLQ 두세 개로 나누고, 원본 큐는 x-death와 x-original-routingKey로 구분한다.

delayed message 플러그인을 쓰면 대기 큐를 안 만들어도 되지 않나요?힌트: 편해지는 것과 잃는 것을 같이 말한다

맞다. 재시도 백오프 정도의 용도라면 플러그인 쪽이 쓰기 편하다. rabbitmq_delayed_message_exchange를 설치하면 x-delay 헤더에 밀리초를 넣어 메시지마다 자유롭게 지연을 줄 수 있고, 대기 큐를 종류별로 선언할 필요가 없다.

그래서 선택 기준은 "지연 값이 몇 종류로 고정되는가"다.

TTL + DLX 대기 큐delayed message 플러그인
추가 설치불필요 (기본 기능)플러그인 필요 — 매니지드 서비스에선 불가할 수 있다
지연 지정큐 단위 (고정값)메시지 단위 (자유)

대량 대기큐가 버퍼라 견딘다약하다 — 큐의 일반적 관리 기능이 그대로 적용되지 않는다

면접에서의 좋은 답은 "둘 다 알고 기준으로 고른다"는 형태다. "재시도 백오프는 지연 단계가 5초·30초·5분처럼 고정되므로 기본 기능만으로 되는 TTL 대기 큐를 우선 씁니다. 사용자마다 임의 시각을 예약하는 요구라면 플러그인이나 DB + 스케줄러로 갑니다."

6-3. 마지막 점검 — 이 조합이면 실패 경로가 완성된다

실무 기본형 체크리스트 그대로 외워도 되는 조합

① 실패 분류
일시적은 예외 그대로 던지고, 영구는 AmqpRejectAndDontRequeueException으로 즉시 거부.
② requeue 차단
default-requeue-rejected: false — 가장 먼저 확인할 한 줄.
③ 인프로세스 재시도
max-attempts: 3 · 200ms 지수 백오프 — 짧은 흔들림 흡수용.
④ 대기 큐 백오프
지연 단계마다 큐를 따로 (5초·30초·5분) · 컨슈머 0 · DLX는 본 exchange.
⑤ 상한과 안전망
x-death count 상한 초과 시 DLQ + quorum queue x-delivery-limit.
⑥ DLQ 운영
진단 헤더 + 깊이 > 0 알람 + 속도 제한 재투입 절차를 평상시에 준비.

순서에 의미가 있다. ②를 안 하면 나머지가 전부 무력화되고(거부가 일어나지 않으니 DLX가 작동하지 않는다), ⑥을 안 하면 ①~⑤로 격리한 메시지가 아무도 안 보는 곳에 쌓인다.

한 줄 요약
RabbitMQ의 재시도는 x-dead-letter-exchange와 TTL을 엮어 「컨슈머 없는 대기 큐」를 타이머로 쓰는 것이 표준이고, 절대 하면 안 되는 것은 지연 없는 requeue=true의 무제한 반복이다 — 실패를 일시적/영구적으로 나누고, 상한과 백오프를 두고, 넘어간 것은 진단 정보와 함께 DLQ에 격리해 사람이 보게 만들어야 한다.
