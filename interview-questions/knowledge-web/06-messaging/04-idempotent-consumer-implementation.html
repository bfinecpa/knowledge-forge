멱등 컨슈머 구현 — 중복은 예외가 아니라 정상 동작이다
키 선정 · 원자성 · 보관 기간, 이 세 디테일이 구현의 성패를 가른다

면접 질문: "멱등 컨슈머(idempotent consumer)를 어떻게 구현하나요?"

핵심 관전 포인트 — 멱등성은 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질"이고, at-least-once 세계에서 중복 수신은 버그가 아니라 스펙이다 — 커밋 전 크래시, 리밸런스, 프로듀서 재발행, 대량 재처리 어디서든 온다. 구현은 두 축이다: ① 연산 자체를 멱등하게 설계(절대값 세팅, UPSERT, 상태 기계 조건부 전이) — 가능하면 최선. ② 처리 이력 기반 중복 제거 — 프로듀서가 발급한 이벤트 ID를 멱등 키로, 이력 테이블(유니크 제약)과 비즈니스 변경을 같은 DB 트랜잭션으로 묶는다. 키는 메시지가 담고 있는 비즈니스적 사실에 붙어야지 파티션-오프셋 같은 위치에 붙으면 안 되고, 중복 판정은 애플리케이션의 SELECT가 아니라 DB의 유니크 제약 + ON CONFLICT DO NOTHING이 원자적으로 해야 하며, 이력은 최소한 토픽의 리텐션 기간보다 길게 보관해야 한다.
  • 1
    중복은 "혹시"가 아니라 "반드시" 온다 — at-least-once의 스펙이다. 커밋 전 크래시, 배포할 때마다 일어나는 리밸런스, 애플리케이션의 재발행, 운영상의 replay까지 경로가 넷이다. 그래서 "중복은 반드시 온다"를 전제로 컨슈머를 설계한다.
  • 2
    먼저 연산 자체를 멱등하게 바꿀 수 있는지 본다 — 상대 연산을 절대값 세팅으로, INSERT를 UPSERT로, 상태 전이는 출발 상태를 WHERE에 박아. 되면 이력 테이블도 정리 배치도 필요 없다. 가장 싼 해법이라 항상 먼저 검토한다.
  • 3
    안 되면 처리 이력 기반 중복 제거 — 그리고 세 디테일에서 승부가 난다 — 키는 프로듀서가 발급한 이벤트 ID(위치가 아니라 정체), 판정은 유니크 제약 + ON CONFLICT DO NOTHING으로 원자적으로, 이력과 업무 변경은 같은 DB · 같은 트랜잭션, 보관은 토픽 리텐션보다 길게.

0. 질문 + 출제 의도

질문: "멱등 컨슈머(idempotent consumer)를 어떻게 구현하나요?"

출제 의도: at-least-once 세계에서 중복은 예외가 아니라 정상 동작이다. 처리 이력 기반 중복 제거의 구현 디테일(키 선정, 저장소, 원자성)까지 들어가는지로 실전 경험을 가린다 — "중복 체크하면 된다" 수준과 "체크와 반영이 원자적이지 않으면 레이스에서 뚫린다"를 아는 수준의 차이를 보는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① "이력 테이블에 기록하고 다음에 확인한다"에서 멈추는 것 → 6절에서 SELECT 후 INSERT가 왜 레이스에서 뚫리는지를 타임라인으로 보여준다. 여기가 변별의 정중앙이다.
② 멱등 키를 아무거나 잡는 것 → 5절에서 파티션-오프셋 키가 유실과 중복 양쪽으로 뚫리는 세 시나리오를 그린다.
③ "이력은 적당히 지우면 되죠" → 7절에서 토픽 리텐션이 바닥선이라는 근거를 타임라인으로 세운다. 숫자가 아니라 도출 논리를 말하는 게 답이다.

1. 멱등성이란 — 엘리베이터 버튼과 은행 입금

용어부터 정확히 잡는다. 멱등성(idempotency)은 같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질이다.

수학에서 온 말이다. 어떤 함수 f에 대해 f(f(x)) = f(x)가 성립하면 그 함수를 멱등하다고 부른다. 한 번 적용한 결과에 또 적용해도 값이 안 바뀐다는 뜻이다. "멱(冪)"은 거듭제곱, "등(等)"은 같다 — 거듭 적용해도 같다는 뜻의 조어다.

한 줄로 외우는 멱등의 정의

멱등 = "몇 번 눌러도 결과가 같다" · 만드는 법 = 상대 연산 → 절대 상태 세팅

면접에서 정의를 물으면 "같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같은 성질" + 엘리베이터 버튼 한 문장이면 충분하다. 정의를 못 대면 그 뒤 구현 이야기가 전부 흐려진다.

2. 중복은 어디서 오는가 — 네 개의 경로

멱등 처리가 방어해야 할 중복은 한 곳에서 오지 않는다. 경로를 먼저 세어 두면 "왜 이렇게까지 하나"라는 의문이 사라진다.

흔한 오해 — "멱등 프로듀서를 켰으니 컨슈머는 안 해도 되지 않나?"

아니다. 멱등 프로듀서가 막는 것은 「전송 계층의 중복」(한 번의 send()가 네트워크 재시도로 브로커에 두 번 저장되는 것)뿐이다. 위 표의 네 경로 중 어느 것도 막지 못한다. 인프라 설정은 중복의 빈도를 줄이고, 멱등 컨슈머는 정확성을 보장한다 — 역할이 다른 두 층이다.

3. 두 전략 — 어느 쪽을 고를지 먼저 판정한다

구현은 두 축이다. 순서가 중요하다 — 전략 1이 되는지를 먼저 보고, 안 될 때만 전략 2로 간다.

두 전략의 성격 비교
전략 1 — 연산 자체를 멱등하게전략 2 — 처리 이력 기반 중복 제거
발상두 번 실행해도 결과가 같아지도록 연산을 바꾼다두 번째 실행을 기록으로 알아채고 건너뛴다
추가 저장소없음processed_event 테이블 + 유니크 제약 + 정리 배치
적용 범위제한적 — 덮어쓸 대상이 있어야 한다범용 — 사건 기록·부수효과에도 적용 가능
전제 조건절대값 방식은 파티션 내 순서 보장이 세트 (24-message-ordering-partition-key.md)프로듀서가 이벤트 ID를 발급해 줘야 한다
협의 대상이벤트 스키마가 바뀐다 → 프로듀서와 합의 필요ID 필드 추가만 합의하면 나머지는 컨슈머 내부 문제
선택 기준둘 중 하나가 아니라 순서다. 전략 1로 되는 부분은 전략 1로 처리하고, 남는 부분에만 전략 2를 얹는다. 실제 서비스에서는 한 컨슈머 안에서 둘이 공존하는 경우가 흔하다.

4. 전략 1 — 연산 자체를 멱등하게 (가능하면 최선)

별도 인프라 없이, 두 번 실행해도 결과가 같은 연산으로 바꿀 수 있는지 먼저 본다. 이 전략이 성립하면 이력 테이블도, 유니크 제약도, 정리 배치도 필요 없다. 가장 싼 해법이므로 항상 먼저 검토한다.

전략 1의 세 가지 기법 — 절 · 업 · 조

절대값 세팅
상대 연산 → 결과 상태
point += amount 대신 point = totalPoint
업서트(UPSERT)
분기를 DB에게
INSERT ... ON CONFLICT DO UPDATE 한 문장
조건부 전이
출발 상태를 WHERE에
UPDATE ... WHERE status = 'PAID'
셋 다 공통 원리는 하나 — "얼마만큼 바꿔라"를 "이 상태가 되게 하라"로

4-1. 상대 연산을 절대 상태 세팅으로 바꾼다

1절의 은행 비유가 그대로 코드가 된다.

문제 상대 연산 — 두 번 오면 두 번 적립된다
@KafkaListener(topics = "point-events")
public void handle(PointEvent event) {
    member.addPoint(event.amount());   // point = point + amount
    // 이벤트가 두 번 오면 포인트도 두 배로 쌓인다.
    // 「입금 +10,000」을 세 번 말한 것과 같다.
}
개선 절대값 세팅 — 몇 번 와도 최종 상태가 같다
@KafkaListener(topics = "point-events")
public void handle(PointEvent event) {
    member.setPoint(event.totalPoint());  // point = totalPoint
    // 같은 이벤트가 몇 번 와도 최종 상태가 같다
    // — 연산 자체가 멱등해졌다.
}

바뀐 것은 컨슈머 코드만이 아니다

이벤트의 스키마가 바뀌었다. 프로듀서가 amount(변화량)만 싣던 것을 totalPoint(결과 상태)까지 싣도록 바꿔야 한다. 즉 이 전략은 컨슈머 혼자 결정할 수 없고 이벤트 설계 단계에서 합의돼야 하는 것이다.

대가 — 순서가 지켜져야만 안전하다

100점 → 150점 → 200점 순으로 발행된 이벤트에서 150점이 마지막에 도착하면 최종 상태가 150점으로 잘못 굳는다. 그래서 이 전략은 같은 회원의 이벤트가 같은 파티션에 들어가도록 파티션 키를 설계하는 것과 세트다 — Kafka는 파티션 안에서만 순서를 보장한다. (24-message-ordering-partition-key.md)

4-2. INSERT를 UPSERT로 바꾼다

"없으면 삽입, 있으면 갱신"을 애플리케이션에서 분기하지 말고 DB가 한 문장으로 원자적으로 처리하게 한다.

SQL PostgreSQL UPSERT — 같은 키의 재수신은 같은 값으로 덮을 뿐이다
INSERT INTO order_summary (order_id, status, total_amount, updated_at)
VALUES (:orderId, :status, :amount, now())
ON CONFLICT (order_id)
DO UPDATE SET status       = EXCLUDED.status,
              total_amount = EXCLUDED.total_amount,
              updated_at   = now();

-- ON CONFLICT (order_id) : 「order_id의 유니크 제약에 걸리면」
-- EXCLUDED               : 「삽입하려다 막힌 그 행」을 가리키는 특수 별칭
-- 즉 이 한 문장이 「넣어 보고, 이미 있으면 새 값으로 갱신해라」를 뜻한다.
-- MySQL이라면 INSERT ... ON DUPLICATE KEY UPDATE 가 같은 역할을 한다.

4-3. 상태 기계 — 현재 상태를 조건에 박는다

도메인이 상태 전이로 모델링돼 있으면(주문, 정산, 구독) 가장 자연스러운 멱등 방식이 이것이다.

SQL 조건부 전이 — 출발 상태를 WHERE에 박는다
-- 「결제완료 -> 배송준비」 전이
UPDATE orders
   SET status = 'PREPARING'
 WHERE id = :orderId
   AND status = 'PAID';   -- 이 한 줄이 중복 방어 + 순서 방어를 동시에 한다

-- 첫 처리:   status가 PAID이므로 1행 갱신
-- 중복 처리: 이미 PREPARING이라 조건 불일치 -> 0행 갱신

0행 갱신일 때 예외를 던지면 안 된다

갱신된 행 수가 0이면 "이미 처리됨"으로 보고 예외 없이 조용히 넘어간 뒤 오프셋을 커밋한다.

중복은 오류가 아니라 정상적으로 예상되는 상황 — 예외를 던지면 컨슈머가 같은 메시지를 무한 재시도하며 파티션이 멈춘다

심하면 정상 이벤트가 DLQ로 흘러가 "실패"로 집계된다. 중복 skip은 에러 로그가 아니라 카운터 메트릭으로 남기는 것이 맞다 (9절 꼬리질문 참고).

4-4. 이 전략이 안 통하는 경우

전략 1은 언제나 최선이지만 언제나 가능하지는 않다. 아래 셋 중 하나에 해당하면 전략 2로 간다.

① 결과 상태를 실을 수 없다

프로듀서가 총액을 모르거나, 여러 이벤트가 합산돼야 최종 값이 나오는 경우.

② 행이 아니라 사건을 남긴다

포인트 원장, 감사 로그처럼 "한 줄 추가되는 것" 자체가 요구사항이면 덮어쓸 대상이 없다.

③ 부수효과가 있다

이메일·푸시·외부 결제 API는 DB 상태가 아니라 바깥 세계를 바꿔서 "덮어쓴다"는 개념이 없다. (→ 8절)

5. 전략 2 ① 키 선정 — 위치가 아니라 정체

전략 2의 발상은 단순하다. "이 이벤트 처리했음"을 어딘가에 기록해 두고, 다음에 같은 이벤트가 오면 기록을 보고 건너뛴다. 그런데 이 단순한 발상은 세 개의 디테일에서 전부 뚫릴 수 있다 — 키 선정(5절), 원자성(6절), 보관 기간(7절).

먼저 키다. 정석은 프로듀서가 이벤트를 만들 때 발급한 고유 ID(UUID 등, Outbox 패턴이라면 outbox 행의 PK)를 페이로드나 헤더에 실어 보내는 것이다. 소비 쪽에서 이것저것 조합해 만드는 것보다, 이벤트가 태어날 때 신분증을 쥐여주는 쪽이 확실하다.

자주 나오는 오답 — 토픽-파티션-오프셋 조합을 키로 쓰는 것 메시지마다 유일한 값처럼 보이니 그럴듯한데, 실제로는 세 방향으로 뚫린다. 더 나쁜 건 한쪽으로는 유실, 다른 쪽으로는 중복이라 어느 쪽으로 실패해도 알아채기 어렵다는 점이다.

이 절의 결론 — 원리 한 줄

멱등 키는 메시지가 담고 있는 비즈니스적 사실에 붙어야지, 그 메시지가 놓인 자리에 붙으면 안 된다
조건 ①
사건마다 유일하다
조건 ②
재발행·경로 변경에도 불변이다
조건 ③
생성 측(프로듀서)이 발급한다
업무 자연키(주문 ID)만 쓰는 것도 위험하다 같은 주문에 대해 생성 · 수정 · 취소 같은 서로 다른 이벤트가 오면, 두 번째 이벤트가 중복으로 오인되어 통째로 버려진다. 자연키를 쓸 거면 "주문 ID + 이벤트 종류 + 버전"처럼 사건을 유일하게 지목하는 조합이어야 한다. 그래서 결국 프로듀서가 발급한 이벤트 ID가 가장 안전한 기본값이다.

이력 테이블은 이렇게 잡는다

DDL processed_event — 중복 판정의 기준
CREATE TABLE processed_event (
    event_id       uuid         NOT NULL,
    consumer_group varchar(100) NOT NULL,
    processed_at   timestamptz  NOT NULL DEFAULT now(),
    PRIMARY KEY (event_id, consumer_group)   -- 이 유니크 제약이 최후 방어선이다
);

-- consumer_group을 키에 넣는 이유:
--   같은 토픽을 「정산 컨슈머」와 「알림 컨슈머」가 각자 소비하는데 이력 테이블을 공유하면,
--   정산이 먼저 처리한 이벤트를 알림 쪽이 「이미 처리됨」으로 오인해 건너뛴다.
--   소비 주체별로 이력이 따로여야 한다.

-- 오래된 이력 정리(7절)를 위한 인덱스
CREATE INDEX idx_processed_event_at ON processed_event (processed_at);

6. 전략 2 ② 원자성 — 두 겹이 필요하다

여기가 출제 의도의 심장부다. 이력 기반 중복 제거는 서로 다른 두 종류의 원자성을 동시에 요구하는데, 하나만 챙기고 다른 하나를 빠뜨리는 답이 흔하다.

(가) 확인과 선점의 원자성

"이미 처리됐는지 확인"과 "없으면 내가 자리를 차지"가 쪼갤 수 없는 한 동작이어야 한다. 안 그러면 동시성 레이스에서 뚫린다.

(나) 이력과 비즈니스 변경의 원자성

이력 기록과 업무 변경이 함께 커밋되거나 함께 롤백돼야 한다. 안 그러면 한쪽은 유실, 다른 쪽은 중복을 만든다.

6-1. (가) "SELECT 후 INSERT"는 왜 새는가 시니어 변별

가장 자연스러워 보이는 구현이 이것이다. 그리고 가장 자주 뚫리는 구현이기도 하다.

문제 check-then-act — 확인과 선점 사이에 틈이 있다
public void handle(OrderEvent event) {
    if (processedEventRepository.exists(event.eventId())) return;  // ① 확인
    orderRepository.save(toOrder(event));                          // ② 처리
    processedEventRepository.insert(event.eventId());              // ③ 기록
    // ①의 사실이 ③의 순간에는 이미 옛날 얘기가 되어 있을 수 있다.
}
개선 유니크 제약 + ON CONFLICT DO NOTHING
@Transactional
public void handle(OrderEvent event) {
    int inserted = processedEventRepository.insertIfAbsent(
            event.eventId(), consumerGroup);
    // 실행되는 SQL:
    //   INSERT INTO processed_event (event_id, consumer_group)
    //   VALUES (:eventId, :group)
    //   ON CONFLICT (event_id, consumer_group) DO NOTHING;
    // 반환값은 삽입된 행 수 — 1이면 내가 처음, 0이면 이미 누가 처리했다.

    if (inserted == 0) return;   // 중복 — 조용히 넘어가고 오프셋 커밋

    orderRepository.save(toOrder(event));
}

여기서 반드시 나오는 두 개의 반문

"@Transactional을 붙이면 해결되지 않나?"

안 된다. 기본 격리 수준인 READ COMMITTED에서 B의 SELECT는 A가 아직 커밋하지 않은 INSERT를 볼 수 없다. 트랜잭션이 하는 일은 "내 변경을 한 덩어리로 커밋/롤백하는 것"이지 "남이 끼어드는 것을 막는 것"이 아니다.
SERIALIZABLE까지 올리면 막히지만, 처리량이 크게 떨어지고 직렬화 실패 재시도 로직을 따로 짜야 한다.

"파티션 하나는 컨슈머 하나가 소비하는데 동시 처리가 되나?"

된다. 긴 GC나 외부 API 지연으로 max.poll.interval.ms를 넘기면 브로커가 그 인스턴스를 그룹에서 빼고 리밸런스로 파티션을 넘긴다. 그런데 쫓겨난 인스턴스는 자기가 쫓겨난 줄 모른 채 처리를 끝낸다 — 좀비 컨슈머(zombie consumer)다. 자세한 타임라인은 9절 꼬리질문에.

왜 ON CONFLICT DO NOTHING이 예외 캐치보다 나은가 (PostgreSQL) 그냥 INSERT를 날리고 DuplicateKeyException을 잡는 방식도 안전성은 같다. 다만 PostgreSQL에서는 제약 위반이 나면 그 트랜잭션 전체가 중단 상태(aborted)가 되어 이후 쿼리가 전부 거부되므로, 예외를 잡아서 같은 트랜잭션 안에서 뭔가를 더 하려면 세이브포인트가 필요하다. ON CONFLICT는 애초에 예외를 만들지 않으므로 이 문제가 없다.

6-2. (나) 이력과 비즈니스 변경은 반드시 같은 트랜잭션

두 번째 원자성은 다른 이야기다. 이력 기록과 비즈니스 변경이 함께 커밋되거나 함께 롤백돼야 한다. 왜 그런지는 어긋나는 두 경우를 보면 안다.

6-3. 그래서 Redis에 이력을 두면 안 되는가 — 이중 쓰기 문제

문제 체크와 반영이 서로 다른 시스템에 흩어져 있다 — 두 군데서 깨진다
public void handle(OrderEvent event) {
    if (redis.exists(event.eventId())) return;  // ① 체크 (Redis)
    orderRepository.save(toOrder(event));       // ② 반영 (PostgreSQL)
    redis.set(event.eventId(), "done");         // ③ 기록 (Redis)
}
// ②와 ③ 사이 크래시 -> 이력 없음 -> 재수신 시 ② 재실행 = 중복 (경우 2)
// ①을 통과한 두 요청이 동시에 ②로 진입하는 레이스도 그대로 열려 있다 (6-1)

이 코드가 고칠 수 없는 이유는 순서를 바꾸는 문제가 아니다. Redis와 PostgreSQL은 서로 다른 시스템이라 애초에 한 트랜잭션으로 묶을 수 없다. @Transactional은 하나의 DataSource가 관리하는 커넥션 안에서만 원자성을 만들어 준다. 다른 시스템에 대한 쓰기는 그 트랜잭션 바깥이므로, 롤백돼도 되돌아오지 않고 커밋 직전에 죽으면 남지 않는다.

이걸 "이중 쓰기(dual write) 문제"라고 부른다. 발행 측에서 이 문제를 푸는 것이 Outbox 패턴이고(28-transactional-outbox-cdc-kafka.md), 소비 측에서 이 문제를 회피하는 방법은 훨씬 간단하다 — 이력을 비즈니스 DB와 같은 DB에 두면 된다. 그러면 이중 쓰기가 아니라 한 트랜잭션 안의 두 쓰기가 된다.

이력 저장소 선택 — 역할이 다르다. Redis는 보조, DB는 최종 방어선
저장소업무 변경과 원자적인가확인·선점이 원자적인가역할
업무와 같은 DB의 테이블
유니크 제약 + ON CONFLICT		예 — 같은 트랜잭션예 — 인덱스 레벨에서 보장최종 방어선 (필수)
Redis SETNX아니오 — 이중 쓰기연산 하나로는 원자적이지만, DB 변경과는 어긋날 수 있다빠른 사전 차단(1차 필터)
replay로 수백만 건이 밀려올 때 DB까지 안 가고 걸러 부하를 줄인다. 단독 방어선이 될 수 없다
애플리케이션 메모리 캐시아니오아니오 — 인스턴스마다 따로 판단멱등 장치로는 사용 불가 (재기동하면 사라지고, 인스턴스 간 공유도 안 된다)
별도 DB의 이력 테이블아니오 — 이중 쓰기예확인은 원자적이지만 (나)의 원자성이 깨진다 — 같은 DB에 둘 수 있으면 굳이 나눌 이유가 없다

이 패턴의 핵심은 두 문장이다

① 같은 DB, 같은 트랜잭션 — 이력과 비즈니스 변경이 함께 커밋되거나 함께 롤백되게 한다
② 유니크 제약이 최후 방어선 — 중복 판정을 애플리케이션의 SELECT가 아니라 DB가 원자적으로 하게 한다

7. 전략 2 ③ 이력 보관 기간 — 근거 있는 숫자

processed_event는 처리한 이벤트 수만큼 계속 자란다. 언젠가는 지워야 하는데, "얼마나 보관하나"에는 근거가 있어야 한다. 면접에서 이 질문은 숫자를 맞히는 문제가 아니라 도출 논리를 보는 문제다.

바닥선은 명확하다 — 최소한 토픽의 리텐션 기간보다 길어야 한다

리텐션은 어디까지나 하한이고, 실제 기간은 "중복이 도달할 수 있는 최대 시간 창"을 기준으로 산정한다. 이 창을 이루는 요소가 셋이다.

보관 기간 산정 공식 — 「가장 긴 것 + 여유」

재시도 최대 지연
DLQ로 보내기 전 재시도를 며칠에 걸쳐 하는 설계라면 그만큼 늦게 같은 메시지가 온다
예상 컨슈머 랙
컨슈머가 며칠 밀렸다가 따라잡는 경우
운영 replay 범위
실제로 되감기를 하는 최대 폭
이 셋 중 가장 긴 값과 토픽 리텐션을 비교해 더 긴 쪽을 기준으로 잡고, 여기에 여유를 얹는다

정리 방법 — DELETE가 아니라 파티션 드롭

DDL 시간 기준 레인지 파티셔닝
-- 월별 레인지 파티셔닝: 오래된 이력을 DELETE가 아니라 파티션 통째로 버린다
CREATE TABLE processed_event (
    event_id       uuid         NOT NULL,
    consumer_group varchar(100) NOT NULL,
    processed_at   timestamptz  NOT NULL DEFAULT now(),
    PRIMARY KEY (event_id, consumer_group, processed_at)
) PARTITION BY RANGE (processed_at);

CREATE TABLE processed_event_2026_09 PARTITION OF processed_event
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

-- 정리는 이 한 줄이면 끝난다
DROP TABLE processed_event_2026_09;   -- 파일 자체가 사라진다

대량 DELETE의 함정 (PostgreSQL)

DELETE FROM processed_event WHERE processed_at < ...은 수천만 행에 죽은 튜플(dead tuple)을 만들고, 그 공간은 VACUUM이 돌기 전까지 회수되지 않는다. 지웠는데 테이블 크기는 그대로거나 오히려 부푼다.

파티션 드롭

DROP TABLE 한 줄이면 파일 자체가 사라진다 — 죽은 튜플도, VACUUM 부담도 없다. 이력 테이블처럼 "시간이 지나면 통째로 버리는" 데이터에는 압도적으로 싸다.

가산점 — 이 창을 넘어서는 대규모 replay는 별도 절차로 운영 감각 보관 창을 넘는 replay는 이력 정리와 정면으로 충돌한다. 이때는 임기응변으로 보관 기간을 늘리는 것이 아니라, 격리된 컨슈머 그룹으로 별도 환경에서 돌리거나 사전 공지 후 정리 배치를 멈추는 등의 별도 절차로 다룬다 (33-bulk-replay-isolation.md). 여기까지 말하면 운영을 해 본 티가 난다.

8. 트랜잭션 밖의 부수효과 — 멱등의 사각지대

이메일 발송, 푸시 알림, 외부 API 호출은 DB 트랜잭션으로 감쌀 수 없다. 6-3에서 본 이중 쓰기 문제가 여기서 다시 나타난다 — 트랜잭션을 롤백해도 이미 나간 이메일은 회수되지 않는다.

회색지대 순서를 어떻게 바꿔도 "보냈는지 안 보냈는지 모르는" 구간이 남는다
t0  트랜잭션 시작
t1  processed_event INSERT (성공)
t2  이메일 발송 API 호출 -> 메일 서버는 정상 접수했다
t3  ★ 응답을 받기 직전 컨슈머 프로세스가 죽는다 -> 트랜잭션 롤백
t4  재수신: 이력이 롤백됐으므로 통과 -> 이메일을 또 보낸다   <- 중복 발송

또는 t1과 t2의 순서를 바꾸면:
t1  이메일 발송 API 호출 (성공)
t2  ★ processed_event INSERT 직전 크래시
t3  재수신: 이력 없음 -> 또 보낸다                          <- 역시 중복 발송

트랜잭션의 원자성이 API 호출까지 미치지 못하기 때문이다. 대응은 이 한계를 인정하고 경계를 옮기는 것이고, 세 가지 방법이 있다.

(1) 수신 측에 멱등 키를 넘긴다

외부 API가 Idempotency-Key 헤더를 지원하면(결제 게이트웨이 대부분이 지원) 이벤트 ID를 그대로 넘긴다. 같은 키로 두 번 호출해도 상대 시스템이 한 번만 실행하고 두 번째는 첫 번째 결과를 그대로 돌려준다.

중복 흡수 책임을 상대 경계로 위임 — 가능하면 이게 제일 깔끔하다.

(2) 발송 이력을 먼저 기록하고 조건부 발송

상대가 멱등 키를 안 받으면 우리 쪽에서 기록을 남긴다. 트랜잭션 안에는 "발송 예약"만 넣고, 실제 발송은 밖에서 한다.

(3) 발송 자체를 별도 이벤트로 분리

컨슈머는 "주문 확정"만 하고 order.confirmed를 발행하며, 이메일 발송은 그 이벤트를 구독하는 별도 컨슈머가 맡는다. 그 컨슈머도 자기 이력 테이블로 멱등 처리하고, 발송 실패는 그쪽의 재시도·DLQ 정책으로 다룬다.

개선 (2) 기록만 트랜잭션 안에 — 실행은 밖으로
@Transactional
public void handle(OrderEvent event) {
    if (processedEventRepository.insertIfAbsent(event.eventId(), group) == 0) return;

    orderRepository.save(toOrder(event));

    // 발송 「예약」만 트랜잭션 안에 기록한다. 실제 발송은 하지 않는다.
    // 이 행이 커밋되면 「보내야 한다」는 사실이 확정되고,
    // 롤백되면 「보낼 일 자체가 없었다」가 된다 — 원자성이 성립한다.
    emailOutboxRepository.save(EmailOutbox.pending(event.eventId(), event.email()));
}

트랜잭션 안에는 「기록」만 — 「실행」은 밖으로. 그리고 한계를 정확히 말하는 것이 좋은 답이다
상대가 Idempotency-Key 지원?→예: 이벤트 ID 그대로 위임|아니오: 기록·실행 분리→더 밀면 별도 이벤트·별도 컨슈머

9. 인출 카드 · 꼬리질문 셀프 테스트

면접 전날 이것만 — 인출 카드 8장

① 중복의 네 경로
커밋 전 크래시 · 리밸런스(=배포) · 프로듀서 재발행 · 운영 replay. 넷 다 인프라 설정으로는 못 막는다.
② 두 전략의 순서
전략 1(연산 멱등) 먼저, 안 되면 전략 2(이력). 바로 이력 테이블부터 꺼내면 판단을 안 해 본 사람으로 보인다.
③ 전략 1의 세 기법
절대값 세팅 · 업서트 · 조건부 전이. 공통 원리 = "얼마만큼"을 "이 상태로".
④ 키의 원리 한 줄
키는 비즈니스적 사실(정체)에 붙인다. 파티션-오프셋(위치)은 유실·중복 양방향으로 뚫린다.
⑤ 원자성은 두 겹
(가) 확인+선점 = 유니크 제약 + ON CONFLICT DO NOTHING / (나) 이력+업무 = 같은 DB, 같은 트랜잭션.
⑥ 보관 기간의 바닥선
최소한 토픽 리텐션보다 길게. 정리는 DELETE가 아니라 파티션 드롭.
⑦ 부수효과
기록은 트랜잭션 안, 실행은 밖. 상대가 Idempotency-Key를 받으면 경계 밖으로 위임.
⑧ 중복일 때 예외 금지
중복은 정상 상황이다. 예외를 던지면 무한 재시도로 파티션이 멈춘다. 조용히 return + 오프셋 커밋.

내 컨슈머가 멱등한지 3분 만에 판정하기

1
이 핸들러를 두 번 연속 실행하면 결과가 달라지는가? 안 달라지면 이미 멱등하다 — 더 할 일이 없다. 달라진다면 어느 줄 때문인지 지목한다 (보통 +=, INSERT, 외부 호출).
2
그 줄을 절대값·UPSERT·조건부 전이로 바꿀 수 있는가? 되면 전략 1로 끝. 이벤트 스키마 변경이 필요하면 프로듀서와 합의한다.
3
안 된다면 이력 테이블 — 그리고 세 가지를 점검한다. ① 키가 이벤트 ID인가 (오프셋·수신 시각이 아니라) ② 판정이 유니크 제약인가 (SELECT가 아니라) ③ 이력과 업무 변경이 같은 트랜잭션인가.
4
부수효과가 있는가? 있으면 기록/실행 분리 또는 Idempotency-Key 위임으로 경계를 옮긴다.
네 칸을 채우면 답이 나온다 — "이 컨슈머는 ○○ 전략, 키는 ○○, 원자성은 ○○로 보장"

꼬리질문 — 먼저 스스로 답한 뒤 펼친다

멱등 키는 뭘로 잡나요? 파티션-오프셋을 쓰면 안 되나요? 핵심힌트: 같은 사건에 항상 같은 값이 붙어야 한다

프로듀서가 이벤트 생성 시점에 발급한 고유 ID가 정석이다.

파티션-오프셋은 브로커상의 "위치"일 뿐 "정체"가 아니다. 토픽 재생성으로 오프셋이 0부터 다시 매겨지면 같은 좌표가 전혀 다른 메시지에 재사용되어 새 메시지가 "이미 처리됨"으로 버려지고(유실), 파티션 증설이나 다른 토픽으로의 재발행·미러링·replay에서는 같은 비즈니스 이벤트에 다른 좌표가 붙어 중복 판별이 아예 안 걸린다(중복).

한쪽으로는 유실, 다른 쪽으로는 중복 — 양방향으로 뚫린다

반대로 이벤트 ID는 메시지가 어디를 거쳐 오든 불변이다. 원리로 말하면 키는 메시지가 담고 있는 비즈니스적 사실에 붙어야지 그 메시지가 놓인 위치에 붙으면 안 된다.

Outbox 패턴을 쓴다면 outbox 행의 PK가 자연스러운 이벤트 ID가 된다 — 발행 경로와 멱등 키 체계가 한 번에 정리되는 조합이다. 가산점

unique 제약 없이 SELECT로 존재 확인 후 INSERT 하면 안 되나요? 시니어 변별힌트: "파티션 하나에 컨슈머 하나"라는 반문을 미리 준비하라

동시성에서 깨진다. check-then-act 사이에 다른 처리가 끼어들 수 있기 때문이다 — 같은 이벤트를 든 두 스레드가 동시에 SELECT하면 둘 다 "없음"을 보고 둘 다 처리한다(6-1의 타임라인).

여기서 반드시 나오는 반문이 "파티션 하나는 컨슈머 하나가 소비하는데 동시 처리가 되나?"인데, 된다. 시나리오는 이렇다.

t0   인스턴스 A가 파티션 0의 메시지 E-1을 poll해서 처리를 시작한다
t1   A에서 긴 GC 또는 외부 API 지연이 발생해 처리가 길어진다
t2   A가 max.poll.interval.ms를 넘겨 poll을 못 하자,
     브로커는 A가 죽었다고 판단하고 그룹에서 제외한다
t3   리밸런스로 파티션 0이 인스턴스 B에게 넘어간다
t4   B가 (A가 오프셋을 커밋하지 못했으므로) E-1을 처음부터 다시 받아 처리한다
t5   ★ 이 순간 A는 자기가 쫓겨난 줄 모르고 t0에 시작한 처리를 계속 끝낸다
     -> 같은 메시지 E-1을 두 인스턴스가 동시에 처리 중이다

t5의 A를 좀비 컨슈머(zombie consumer)라고 부른다. 자기가 이미 그룹에서 쫓겨났다는 사실을 모른 채 살아 움직이기 때문이다 (35-max-poll-interval-vs-session-timeout.md).

유일하게 신뢰할 수 있는 심판은 두 요청이 반드시 거쳐 가는 단일 지점인 DB다

그래서 결론은 애플리케이션 레벨 체크로는 원리적으로 못 막는다는 것이다. 어느 인스턴스의 메모리에서 무슨 판단을 하든, 두 프로세스가 각자 판단하는 이상 틈은 생긴다. 그래서 유니크 제약 + ON CONFLICT DO NOTHING이 최후 방어선이어야 한다.

처리 이력 테이블이 무한히 커지는 문제는 어떻게 하나요?힌트: 정답 숫자가 아니라 도출 논리를 말한다

보관 기간을 근거를 갖고 정하고, 그보다 오래된 행을 정리한다.

바닥선은 토픽의 리텐션 기간이다. 되감아 다시 읽을 수 있는 구간 전체를 이력이 덮고 있어야 하고, 이력이 그보다 짧으면 replay 시 이미 지운 구간에서 중복 처리가 뚫린다. 그 위에 "중복이 도달 가능한 최대 창"(재시도 최대 지연 + 예상 컨슈머 랙 + 통상 replay 범위)을 얹어 산정한다.

정리는 시간 기준 레인지 파티셔닝으로 한다. PostgreSQL에서 대량 DELETE는 죽은 튜플을 만들어 VACUUM이 돌기 전까지 공간이 회수되지 않지만, 파티션 드롭은 파일이 통째로 사라져 비용이 거의 없다.

핵심은 "중복 도달 창과 토픽 리텐션이라는 근거에서 기간을 도출"하는 논리 구조를 보여주는 것

그리고 그 창을 넘는 replay는 별도 절차로 격리한다고 덧붙인다 (33-bulk-replay-isolation.md).

이메일 발송처럼 롤백 불가능한 부수효과는 어떻게 멱등하게 하나요?힌트: 한계를 인정하는 문장이 답의 일부다

DB 트랜잭션 안에 넣을 수 없다는 한계를 먼저 인정하고, 경계를 옮겨서 푼다.

첫째, 외부 시스템이 Idempotency-Key를 받으면 이벤트 ID를 그대로 전달해 중복 흡수를 그쪽 경계로 위임한다.

둘째, 그게 안 되면 기록과 실행을 분리한다 — 트랜잭션 안에서는 "발송 예약" 행만 남기고, 실제 발송은 그 행을 읽는 별도 워커가 수행한 뒤 상태를 SENT로 바꾼다. 소비 측에 다시 적용한 Outbox 구조다.

셋째, 한 걸음 더 나가면 발송 자체를 별도 이벤트로 떼어내 전용 컨슈머가 자기 이력 테이블로 멱등 처리하게 한다. 발송 실패의 재시도·DLQ 정책도 그쪽에 격리된다.

솔직하게 덧붙일 것: "보냈는지 모르는 상태"를 "중복 가능성만 남은 상태"로 줄이는 것이 최선이다

이 방법들도 완전한 exactly-once는 아니다 — 워커가 발송 후 상태 갱신 전에 죽으면 한 번 더 보낸다. 그 한계를 정확히 말하는 것이 좋은 답이다.

멱등 컨슈머를 만들었으면 exactly-once 설정은 필요 없나요?힌트: 대체 관계인지 층 관계인지

역할이 다르다. 대체 관계가 아니라 층이 다른 두 장치다.

인프라 층 — 빈도를 줄인다

멱등 프로듀서와 Kafka 트랜잭션은 Kafka 경계 안의 중복을 줄인다 — 프로듀서 재시도로 인한 중복, Kafka에서 읽어 Kafka로 쓰는 파이프라인의 중복이 대상이다.

애플리케이션 층 — 정확성을 보장한다

멱등 컨슈머는 그걸로 못 막는 비즈니스 레벨 중복까지 막는 최종 방어선이다 — 애플리케이션의 재발행, 운영상의 replay, 좀비 컨슈머가 여기 해당한다.

인프라 설정으로 중복 빈도를 낮추고, 애플리케이션 멱등으로 정확성을 보장하는 이중 구조

어느 하나만 있으면 부족하다 — 인프라 설정만 있으면 replay에서 뚫리고, 애플리케이션 멱등만 있으면 불필요한 중복 트래픽을 전부 DB로 받아내야 한다. (03-delivery-semantics-and-exactly-once-reality.md)

이력 테이블 PK에 consumer_group은 왜 넣나요? 빼면 무슨 일이 생기나요? 함정힌트: 같은 토픽을 구독하는 컨슈머가 하나뿐인가

같은 이벤트를 여러 컨슈머 그룹이 각자 처리하기 때문이다. 이력을 event_id만으로 잡고 테이블을 공유하면 이렇게 된다.

정산 컨슈머가 E-1 처리 → processed_event(E-1) INSERT
알림 컨슈머가 E-1 수신 → 이미 있다고 판단 → 알림을 보내지 않고 skip
// 알림은 한 번도 처리되지 않았는데 「처리됨」으로 취급된다 = 조용한 유실

멱등의 단위는 "이벤트"가 아니라 "이벤트 × 소비 주체"다. 같은 이벤트라도 정산과 알림은 서로 다른 작업이므로 이력도 따로 가져야 한다.

구현상 선택지는 둘이다 — PK를 (event_id, consumer_group)으로 잡아 한 테이블을 공유하거나, 컨슈머(서비스)마다 자기 DB에 자기 이력 테이블을 두거나. 서비스별로 DB가 갈려 있는 마이크로서비스 구조라면 후자가 자연스럽고, 그때는 consumer_group 컬럼이 필요 없어진다.

판단 기준: "이 이력 테이블을 누가 함께 쓰는가" — 공유한다면 반드시 소비 주체를 키에 넣는다
이력 INSERT가 모든 메시지마다 추가되는데 성능 부담은 없나요? 키 타입은 뭘 쓰는 게 좋나요? 가산점힌트: 비용의 출처를 세어 본다 — 왕복인가, 인덱스인가

비용의 출처를 나눠서 보는 게 정확하다.

① 왕복 비용은 거의 없다. 이력 INSERT는 업무 변경과 같은 커넥션·같은 트랜잭션에서 나가는 한 행 INSERT다. 다른 시스템을 부르는 것이 아니라서 네트워크 왕복이 새로 생기지 않는다. 대개 업무 쿼리 한 개를 더 날리는 정도의 비용이다.

② 진짜 비용은 인덱스와 테이블 크기다. 처리량이 초당 수천 건이면 이력도 같은 속도로 쌓이므로, 7절의 파티셔닝과 보관 기간 정책이 성능 대책이기도 하다. 오래된 파티션을 계속 떨어내면 활성 인덱스가 캐시에 들어오는 크기로 유지된다.

③ 키 타입의 트레이드오프. 완전 랜덤한 UUID(v4)는 B-tree 인덱스의 삽입 위치가 매번 흩어져 캐시 적중률이 떨어지고 페이지 분할이 잦다. 시간순으로 정렬되는 ID(UUIDv7, ULID 등)를 쓰면 삽입이 인덱스의 오른쪽 끝에 몰려 지역성이 좋아진다 — 대신 그 끝 페이지에 경합이 생긴다. 어느 쪽이든 사건마다 유일 + 불변이라는 조건만 만족하면 정확성에는 차이가 없고, 쓰기 처리량이 큰 시스템에서만 고민할 문제다.

④ replay처럼 중복이 폭주할 때는 Redis 1차 필터가 실제로 효과가 크다 — 이미 처리된 수백만 건을 DB까지 안 보내고 걸러낸다. 다만 6-3에서 본 대로 단독 방어선이 아니라 보조 수단이다.

배치로 100건씩 한 번에 처리할 때도 같은 방식이 되나요?힌트: 어떤 것이 새 이벤트인지 DB에게 물어볼 수 있다

된다. 오히려 한 번의 문장으로 처리할 수 있다. PostgreSQL이라면 RETURNING을 붙여 실제로 삽입된 행만 돌려받는다.

INSERT INTO processed_event (event_id, consumer_group)
VALUES (:id1, :g), (:id2, :g), (:id3, :g) /* ... 100건 */
ON CONFLICT (event_id, consumer_group) DO NOTHING
RETURNING event_id;   -- 돌아온 ID들 = 「내가 처음 처리하는」 이벤트

돌아온 ID 집합만 골라 비즈니스 처리를 수행하면 된다. 확인·선점의 원자성은 단건과 동일하게 유지된다.

두 가지만 주의한다.

  • 배치 전체를 한 트랜잭션으로 묶는다 — 일부만 커밋되면 6-2의 어긋남이 배치 단위로 생긴다. 전부 롤백되면 이력도 함께 사라지므로 재수신 시 안전하게 다시 처리된다.
  • 배치 안에 같은 키가 두 번 들어 있어도 DO NOTHING은 에러 없이 첫 행만 삽입한다. (DO UPDATE는 같은 행을 한 명령에서 두 번 건드리면 에러가 난다.)

배치를 크게 잡을수록 트랜잭션이 길어지고 락 보유 시간이 늘어난다 — 처리량과 트랜잭션 길이의 균형은 별개 주제다.

중복을 조용히 skip하면 문제가 있어도 모르지 않나요? 어떻게 관측하나요?힌트: 조용히 넘어가되, 세는 것은 별개다

"예외를 던지지 않는 것"과 "기록하지 않는 것"은 다르다. skip은 에러 로그가 아니라 카운터 메트릭으로 남긴다.

  • 중복 skip 카운터를 컨슈머 그룹·토픽 단위로 집계한다. 평상시에는 0에 가깝게 유지되는 것이 정상이다.
  • 급증은 신호다 — 리밸런스가 잦아졌거나(배포·max.poll.interval.ms 초과), 프로듀서가 재발행을 하고 있거나, 누군가 replay를 돌린 것이다. 중복률이 시스템 건강의 지표가 된다.
  • 로그로 남길 때는 DEBUG 레벨로 event_id만 남긴다. WARN·ERROR로 남기면 정상 동작이 알람을 울려 진짜 장애가 묻힌다.
중복은 막되 숨기지 않는다 — 조용히 넘어가고, 대신 센다
멱등하게 만들었으면 순서는 신경 안 써도 되나요? 함정힌트: "두 번 처리"와 "거꾸로 처리"는 다른 문제다

아니다. 멱등성은 "중복"을 푸는 장치이지 "순서"를 푸는 장치가 아니다. 둘은 별개 문제이고, 전략마다 순서에 대한 태도가 다르다.

방식중복 방어순서 역전 방어
절대값 세팅 (4-1)완전없음 — 오래된 값이 나중에 도착하면 그 값으로 굳는다
UPSERT (4-2)완전없음 — 마지막에 도착한 값이 이긴다
조건부 상태 전이 (4-3)완전있음 — 출발 상태가 안 맞으면 0행으로 튕긴다
이력 테이블 (5~7절)완전없음 — "두 번 처리"만 막고 "거꾸로 처리"는 통과시킨다

순서까지 지켜야 한다면 별도 장치가 필요하다 — ① 파티션 키를 엔티티 ID로 잡아 같은 엔티티의 이벤트를 한 파티션에 몰거나(24-message-ordering-partition-key.md), ② 이벤트에 버전·시퀀스를 실어 현재 저장된 버전보다 낮으면 무시하거나, ③ 조건부 전이로 상태 기계가 스스로 역행을 거부하게 한다.

멱등 ≠ 순서 안전 — "두 번 와도 같다"와 "거꾸로 와도 맞다"는 다른 보장
MySQL이면 무엇이 달라지나요?힌트: 문장은 다르지만 원리는 같다

문법과 정리 방법이 다를 뿐, 원리는 그대로다.

  • 확인+선점 — INSERT ... ON DUPLICATE KEY UPDATE 또는 INSERT IGNORE를 쓰고 영향받은 행 수로 판정한다. 다만 INSERT IGNORE는 유니크 위반 말고 다른 오류(형 변환 실패 등)까지 경고로 삼켜 버려서 조용히 잘못된 데이터가 들어갈 수 있다 — 제약 위반만 잡고 싶다면 ON DUPLICATE KEY UPDATE 쪽이 안전하다.
  • 동시성 — InnoDB에서도 유니크 인덱스에 같은 키로 두 트랜잭션이 INSERT하면 뒤에 온 쪽이 잠금 대기한다. 기본 격리 수준이 REPEATABLE READ라는 차이는 있지만, "유니크 제약이 원자적 심판"이라는 논리는 동일하다.
  • 정리 — 레인지 파티셔닝 후 ALTER TABLE ... DROP PARTITION으로 통째로 버린다. PostgreSQL의 죽은 튜플·VACUUM 이슈는 없지만, 대량 DELETE가 긴 트랜잭션과 언두 로그 증가를 부르는 것은 마찬가지라 파티션 드롭이 여전히 유리하다.
면접 답변 요령: "엔진마다 문장은 다르지만, 확인과 선점을 DB가 원자적으로 하게 만든다는 원리는 같습니다"
한 줄 요약
멱등 컨슈머는 "중복은 반드시 온다"는 at-least-once의 전제를 받아들이고, 가능하면 연산 자체를 멱등하게(절대값 · UPSERT · 조건부 전이) 바꾸고, 안 되면 프로듀서가 발급한 이벤트 ID를 — 파티션-오프셋 같은 위치가 아니라 비즈니스적 정체를 가리키는 키를 — 유니크 제약 걸린 이력 테이블에 ON CONFLICT DO NOTHING으로 넣어 확인과 선점을 원자적으로 만들고, 그 이력을 비즈니스 변경과 같은 트랜잭션으로 묶으며, 이력은 최소한 토픽 리텐션보다 길게 보관해 — 키 선정 · 원자성 · 보관 기간이라는 세 디테일로 exactly-once 효과를 애플리케이션 레벨에서 완성하는 패턴이다.
