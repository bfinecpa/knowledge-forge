RabbitMQ 큐 적체 진단과 해소 — 랙과 달리 "브로커가 먼저 무너진다"
Kafka의 랙은 오프셋이 뒤처진 것일 뿐이지만, RabbitMQ의 적체는 브로커의 메모리가 실제로 차오르는 것이다

면접 질문: "RabbitMQ 큐에 메시지가 계속 쌓일 때(적체) 원인 진단과 해소를 단계적으로 설명해주세요. (flow control, 메모리/디스크 alarm, lazy queue — Kafka 컨슈머 랙 대응과 비교)"

핵심 관전 포인트 — Kafka의 컨슈머 랙과 RabbitMQ의 큐 적체는 증상이 근본적으로 다르다. Kafka에서 컨슈머가 밀리는 것은 "오프셋이 뒤처진 것"일 뿐 브로커는 아무 부담도 지지 않는다 — 데이터는 어차피 디스크에 있었고 리텐션 기간까지 그대로 있다. RabbitMQ에서 큐가 쌓이는 것은 브로커의 메모리와 디스크가 실제로 차오르는 것이다. 그래서 임계치를 넘으면 브로커가 자기 보호를 위해 모든 프로듀서를 블로킹한다(메모리·디스크 alarm). 컨슈머가 느린 문제가 발행 API의 응답 지연으로 번지고, 결국 사용자 요청 처리까지 멈춘다. 컨슈머 장애가 서비스 전체 장애로 번지는 경로가 존재한다는 것이 RabbitMQ 적체의 본질이며, 진단은 항상 Ready/Unacked 두 숫자의 조합과 publish rate vs ack rate 비교에서 시작한다.
  • 1
    먼저 증상의 성격을 규정합니다. RabbitMQ의 적체는 브로커의 메모리·디스크를 실제로 먹는 일이라, 임계치를 넘으면 alarm이 켜지고 모든 발행 커넥션이 블로킹됩니다. 그 순간 API 스레드가 발행 호출에서 멈춰 서비스 전면 장애가 됩니다. 그래서 큐 깊이를 "컨슈머가 얼마나 밀렸는가"가 아니라 "브로커가 얼마나 위험한가"로 읽습니다.
  • 2
    진단은 두 숫자의 조합에서 시작합니다. consumers가 0이면 튜닝이 아니라 연결·기동 문제이고, Ready와 Unacked의 조합으로 배달이 안 되는 것 / 처리가 느린 것 / 컨슈머가 붙잡고 있는 것을 가릅니다. 깊이로 안 갈리면 deliver rate vs ack rate(재배달 루프)와 publish rate(유입 폭증)를 봅니다. 그리고 alarm이 이미 켜져 있다면 컨슈머 튜닝보다 alarm 해제가 먼저입니다.
  • 3
    해소는 시간축으로 셋을 나눠 말합니다. 분 단위로는 워커 증설·prefetch 조정·낮은 우선순위 큐의 유입 차단·디스크 확보, 며칠 안으로는 큐 분리와 길이 상한(x-max-length + x-overflow), 설계 수준에서는 컨슈머 처리량 개선과 프로듀서 배압(발행 타임아웃 + 대체 경로), 그리고 "소진 시간" 지표입니다. 앞의 둘은 시간을 벌 뿐이고, 원인을 없애는 것은 마지막 하나입니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문: "RabbitMQ 큐에 메시지가 계속 쌓일 때(적체) 원인 진단과 해소를 단계적으로 설명해주세요. (flow control, 메모리/디스크 alarm, lazy queue — Kafka 컨슈머 랙 대응과 비교)"

출제 의도: Kafka의 컨슈머 랙에 대응하는 문항이지만 증상이 다르다. RabbitMQ는 큐가 쌓이면 메모리·디스크 alarm과 flow control로 프로듀서를 막아 서비스 전체가 멈추는 방향으로 무너진다. "적체가 왜 발행 지연 장애로 번지는가"라는 인과를 설명할 수 있는지, 그리고 진행 중인 장애에서 단기 완화와 근본 대책을 분리해 말하는지를 본다.

질문에 답이 절반 들어 있다 — 괄호 안의 세 단어가 채점 기준이다 flow control · 메모리/디스크 alarm · lazy queue는 전부 "브로커가 자원 압박을 받는다"는 전제 위에서만 의미가 있는 개념이다. 즉 면접관은 "컨슈머를 늘리겠습니다"라는 처리량 답변이 아니라, "브로커가 지금 어떤 상태이고 그것이 프로듀서에 무엇을 하는가"를 듣고 싶어 한다. 이 축을 못 잡으면 16번(처리량 튜닝) 문서의 답을 그대로 반복하게 되고, 그 순간 이 문항의 변별 구간을 통째로 놓친다.
먼저 깨야 할 오해 4개 — 아래 절들이 각각 이것을 겨냥한다 ① "큐가 쌓이는 건 컨슈머가 좀 밀린 것뿐" → Kafka라면 맞다. RabbitMQ에서는 브로커 메모리가 실제로 차오르는 것이고, 끝에는 발행 차단 → 전면 장애가 있다 (1절).
② "큐 깊이만 보면 원인을 안다" → 깊이 하나로는 배달이 안 되는 것과 처리가 느린 것을 구분할 수 없다. 원인은 Ready·Unacked의 조합에서 갈린다 (2절).
③ "적체엔 일단 컨슈머 증설" → 병목이 다운스트림이면 증설은 그 다운스트림에 부하를 더 보내는 것이라 증상이 악화된다 (3절·6절).
④ "급한 불부터 끄면 된다" → 단기 완화는 시간을 벌 뿐 원인을 없애지 못한다. 두 층을 나눠 말하지 않으면 같은 사고가 반복된다 (3·4절).
이 페이지를 읽는 축 — 「어디까지 번지는가」와 「무엇으로 가르는가」 두 개면 된다 이 주제는 외울 항목이 많아 보이지만 축은 둘이다. 하나는 전파 경로 — 컨슈머 정지 → 큐 적체 → 메모리 alarm → 프로듀서 블로킹 → API 정지라는 한 줄짜리 인과이고, 진단·해소의 모든 판단이 "이 사슬의 어디쯤인가"로 결정된다. 다른 하나는 분기 기준 — Ready/Unacked 조합 + 두 rate 비교로 원인 다섯 가지가 갈린다. 1절이 첫 번째 축, 2절이 두 번째 축이고, 3~4절은 그 위에서 시간축으로 조치를 배치한 것이다.

1. 전제 — 적체가 왜 Kafka보다 위험한가

1-1. 저장 모델의 차이가 만드는 결과

Kafka는 처음부터 디스크 로그다. 메시지는 발행 시점에 파일에 append되고, 컨슈머가 읽든 안 읽든 리텐션 기간 동안 그대로 있다. 컨슈머가 하루 밀려도 브로커에게는 아무 변화가 없다 — 어차피 디스크에 있던 것을 컨슈머가 늦게 읽을 뿐이다.

RabbitMQ는 기본적으로 메모리 큐다. 큐가 짧으면 메시지가 디스크를 거의 거치지 않고 메모리에서 흘러간다. 이것이 낮은 지연의 비결이지만, 컨슈머가 멈추면 그 메시지들이 전부 브로커 메모리에 눌러앉는다.

그림으로 기억하기 — 창고 vs 컨베이어 벨트 Kafka는 창고다. 물건은 어차피 선반(디스크)에 올려져 있고, 수령이 늦으면 내 선반 번호(오프셋)가 뒤처질 뿐 창고는 평소와 똑같이 입고를 받는다. RabbitMQ는 컨베이어 벨트다. 물건은 벨트 위(메모리)에 얹혀 흘러가는 중이고, 하역이 멈추면 벨트 위에 물건이 그대로 쌓인다. 벨트가 넘치기 직전이 되면 관리자는 입구를 잠근다 — 그것이 메모리 alarm이다. "수령이 늦은 것"과 "벨트가 넘치는 것"은 급이 다른 사고라는 감각이 이 문서의 출발점이다.

1-2. 브로커의 자기 보호 — alarm과 flow control

RabbitMQ는 자기가 죽지 않기 위한 방어 장치를 갖고 있고, 그 방어가 프로듀서를 멈추는 방식으로 작동한다. "브로커를 살리기 위해 발행을 희생한다"는 이 설계 의도를 먼저 이해해야, 뒤에 나오는 모든 조치의 우선순위가 자연스럽게 정해진다.

메모리 alarm
브로커가 쓰는 메모리 > 임계치
alarm이 켜지면 모든 발행 커넥션이 블로킹된다. 클라이언트는 connection.blocked 알림을 받고, 이후 발행 호출이 응답 없이 멈춘다. 임계치는 보통 시스템 메모리의 일정 비율로 잡혀 있다.
디스크 여유 공간 alarm
디스크 여유 < 임계치
같은 일이 벌어진다. persistent 메시지를 더 쓸 수 없으니 발행을 막는 것이다. 원인이 큐가 아니라 로그 파일이 디스크를 채운 것인 경우도 흔하다.
flow control
브로커 내부의 크레딧 기반 제어
소비가 느린 경로로 메시지가 밀려들면 그 앞단(발행 채널)의 속도를 늦춘다. alarm처럼 완전히 막는 것은 아니지만 발행 지연이 눈에 띄게 늘어난다.
둘의 차이를 한 문장으로 구분해 두면 진단이 빨라진다 flow control은 "느려지는 것"이고 alarm은 "멈추는 것"이다. 발행 지연이 완만하게 늘고 있다면 flow control을 의심하고, 발행이 응답 없이 완전히 멈췄다면 alarm을 먼저 확인한다. 증상의 종류가 다르므로 "발행이 느리다"와 "발행이 안 된다"를 구분해서 보고받는 습관이 필요하다.

1-3. 그래서 무슨 일이 벌어지는가 — 이 문서의 핵심 인과

관점 전환 — 이 한 줄이 이 질문의 핵심이다

RabbitMQ의 큐 깊이는 "컨슈머가 얼마나 밀렸는가" 지표가 아니라 "브로커가 얼마나 위험한가" 지표다

Kafka의 랙은 컨슈머 팀의 문제지만, RabbitMQ의 적체는 브로커를 공유하는 모든 팀의 문제다. 그래서 같은 대시보드를 봐도 읽는 의미가 다르고, 에스컬레이션 기준도 다르다. 면접에서 이 문장을 먼저 말하고 들어가면 뒤의 설명이 전부 이 축에 정렬된다.

1-4. 미리 알아둘 방어 수단 — 무한 대기를 만들지 않는다

프로듀서 쪽에 타임아웃을 걸어 발행을 포기하고 요청을 빠르게 실패시키면 ⑤~⑦로 번지는 것을 막을 수 있다. 상한을 거는 자리는 둘이다.

자리 ① 채널 획득 대기

커넥션 팩토리의 채널 획득 대기 시간(channelCheckoutTimeout, Spring Boot 속성으로는 spring.rabbitmq.cache.channel.checkout-timeout)이다. 브로커가 막혀 채널이 반납되지 않으면 여기서 무한 대기가 시작된다.

자리 ② publisher confirm 대기

confirm을 기다리는 시간이다. CorrelationData가 돌려주는 future에 타임아웃을 걸어 확인한다. confirm을 무한정 기다리면 발행 스레드가 그대로 묶인다.

방어 발행 경로에 상한을 두고, blocked 신호를 직접 받아 즉시 실패시킨다
# application.yml — 무한 대기를 만들지 않는 최소 설정
spring:
  rabbitmq:
    publisher-confirm-type: correlated   # confirm을 받겠다고 선언
    cache:
      channel:
        checkout-timeout: 2000           # 채널을 2초 안에 못 얻으면 실패시킨다
// confirm을 무한정 기다리지 않는다
CorrelationData cd = new CorrelationData(event.getId());
rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, event, cd);
cd.getFuture().get(2, TimeUnit.SECONDS);   // 상한 — 넘으면 예외로 빠져나온다

// 브로커가 커넥션을 막았다는 사실 자체를 신호로 받는다
connection.addBlockedListener(new BlockedListener() {
    public void handleBlocked(String reason) { publishGate.set(false); }  // 이후 발행은 즉시 실패
    public void handleUnblocked() { publishGate.set(true); }
});
이름을 외우지 말고 원칙을 외운다 future의 타입(레거시 ListenableFuture / 최신 CompletableFuture)과 blocked 리스너의 등록 위치는 버전마다 다르다. 세부 설정 이름도 마찬가지다. 면접에서도 정확한 프로퍼티 이름보다 "발행 경로의 모든 대기에 상한을 둔다"는 원칙과 "어느 자리에 거는가(채널 획득 · confirm 대기)"를 말하는 편이 안전하고 점수가 높다.

2. 진단 — 두 숫자의 조합으로 원인이 갈린다

2-1. 봐야 할 지표

관리 콘솔이나 rabbitmqctl list_queues에서 얻는 값들이다. 여섯 개면 충분하고, 그중 앞의 셋은 큐의 상태, 뒤의 셋은 큐의 속도다.

상태 3개 + 속도 3개 — 이 조합이 진단의 전부다
지표의미이 값이 튈 때 의심할 것
messages_ready아직 아무에게도 배달 안 된 메시지 수이것만 크면 배달 자체가 막힌 것 — 컨슈머 부재 또는 처리 지연
messages_unacknowledged배달됐지만 ack을 못 받은 수prefetch × 컨슈머 수에 딱 붙어 있으면 컨슈머가 물고 놓지 못하는 중
consumers붙어 있는 컨슈머 수0이면 튜닝 대상이 아니다 — 애플리케이션·연결·리스너 기동 문제
publish rate초당 유입량평소 대비 급증이면 컨슈머가 아니라 트래픽이 원인
deliver rate초당 배달량ack rate와 나란히 봐야 의미가 생긴다
ack rate초당 처리 완료량실질 처리량. 소진 시간 계산의 분모가 되는 값
욕조로 기억하면 헷갈리지 않는다 Ready는 욕조에 고인 물, Unacked는 배수구에 걸려 빠지는 중인 물, publish rate는 수도꼭지, ack rate는 실제 배수 속도다. 물이 차오를 때 원인은 셋뿐이다 — 수도꼭지가 세졌거나(publish↑), 배수구가 막혔거나(ack↓), 배수구에 아무것도 안 걸려 있거나(consumers=0). 진단이란 이 셋 중 무엇인지 숫자로 확정하는 일이다.

2-2. Ready와 Unacked의 조합이 1차 분기를 만든다

원인 5종 인출 카드 — 「부 · 느 · 잡 · 돌 · 몰」

면접에서 진단을 물으면 이 다섯 개를 조건과 함께 뱉을 수 있어야 한다. 앞 글자만 이어 "부느잡돌몰"로 외운다.

부 — 컨슈머 부재
Ready↑ · Unacked = 0 · consumers = 0
연결·기동 문제. 튜닝은 무의미
느 — 처리 지연
Ready↑ · Unacked = prefetch 상한
다운스트림 의심. 스레드 덤프
잡 — 컨슈머가 붙잡음

2-3. 진단 순서 — 다섯 단계를 이 순서로 밟는다

1
컨슈머가 붙어 있는가. 
rabbitmqctl list_queues name messages_ready messages_unacknowledged consumers

consumers = 0이면 컨슈머 문제가 아니라 연결 문제다. 애플리케이션이 죽었거나, 큐 이름이 바뀌었거나, 배포 중 리스너가 시작되지 않았다. 이 경우 컨슈머를 튜닝해봐야 소용이 없다.

2
배달은 되는데 느린 것인가.

Unacked가 prefetch × 컨슈머 수에 딱 붙어 있다면, 컨슈머가 받을 만큼 받아놓고 처리를 못 끝내고 있다는 뜻이다. 원인은 컨슈머 안이 아니라 거의 항상 다운스트림이다.

DB 슬로우 쿼리 · 락 대기외부 API 지연 (타임아웃 없으면 무한정)GC 정지 시간 증가

컨슈머 애플리케이션의 스레드 덤프를 한 번 뜨면 대부분 즉시 보인다. "어디서 멈춰 있는가"를 추측하지 말고 덤프로 확인하는 것이 가장 빠르다.

3
처리 중인데 완료가 안 되는 것인가.

deliver rate는 높은데 ack rate가 낮으면 재배달 루프다. 실패한 메시지를 지연 없이 requeue하고 있다는 신호이며, CPU는 높은데 처리량이 0인 특징적 증상이 함께 나타난다. 대응은 14-rabbitmq-retry-dlx-dlq.md에 있다.

4
유입이 늘어난 것인가.

publish rate가 평소보다 크게 높으면 컨슈머는 정상이고 트래픽이 폭증한 것이다. 이때 컨슈머를 튜닝하는 것은 방향이 틀렸고, 컨슈머를 늘리거나 유입을 조절해야 한다.

5
브로커가 이미 방어에 들어갔는가. 
rabbitmqctl status | grep -A5 alarms       # 켜져 있는 alarm 확인
rabbitmqctl list_connections name state    # blocked / blocking 상태 확인

alarm이 켜져 있다면 이미 1-3의 ④단계에 도달한 것이다. 이 경우 최우선 조치는 컨슈머 튜닝이 아니라 alarm 해제다 — 프로듀서가 막혀 있는 동안 서비스 전체가 멈춰 있기 때문이다.

5단계는 마지막이지만 실제로는 「제일 먼저」 확인한다 설명 순서는 ①→⑤지만, 장애 대응에서는 ⑤를 가장 먼저 훑는다. alarm이 켜져 있으면 1~4번의 원인 분석은 그대로 유효하되 우선순위가 뒤로 밀리기 때문이다. "원인을 찾는 일"과 "출혈을 멈추는 일"은 동시에 진행하되, 출혈이 먼저다. 면접에서도 "alarm 여부부터 확인하고, 켜져 있으면 원인 분석과 병행해 압력부터 낮춥니다"라고 말하는 편이 낫다.
덧붙이면 좋은 한 줄 — 두 숫자는 「합」이 아니라 「비율」로 본다 Ready와 Unacked를 더해 "총 몇 건"으로 보고하는 습관은 정보를 버리는 것이다. 같은 1만 건이라도 Unacked 1만 건은 컨슈머가 물고 있는 상태(회복 시 재배달 폭탄이 되고, 채널이 끊기면 전부 Ready로 되돌아온다)이고, Ready 1만 건은 아직 아무도 손대지 않은 상태다. 대응도 회복 후 그림도 완전히 다르다.

3. 해소 — 단기 완화와 근본 대책을 나눈다

이 질문에서 가장 흔한 실패는 "지금 당장 할 일"과 "다시는 안 겪게 만들 일"을 섞어 답하는 것이다. 장애가 진행 중인데 큐 분리나 배압 설계를 말하면 그 순간에는 아무 소용이 없고, 반대로 급한 불만 끄고 덮으면 같은 사고가 반복된다.

그래서 시간축으로 셋을 나눈다. 분 단위의 응급 조치(3-1), 며칠 안의 구조 완화(3-2), 설계 수준의 근본 대책(3-3)이다. 세 층은 목적이 다르다 — 앞의 둘은 브로커의 압력을 낮춰 시간을 버는 것이고, 마지막 하나만이 원인을 없앤다.

3-1. 지금 당장 (분 단위)

목표는 브로커의 압력을 낮춰 프로듀서 블로킹을 푸는 것이다.

컨슈머를 늘린다 1순위
RabbitMQ는 Kafka와 달리 파티션 수 같은 상한이 없다. 큐 하나에 컨슈머를 몇 대든 더 붙일 수 있으므로 워커 파드 증설이 가장 즉효다. Kafka 대비 RabbitMQ의 명확한 운영상 이점이다.
prefetch를 조정한다
컨슈머를 늘렸는데도 안 빨라진다면 prefetch가 커서 기존 컨슈머가 메시지를 다 쥐고 있을 수 있다. 값을 낮추면 새로 붙은 컨슈머에게 일감이 분배된다.
급하지 않은 큐의 유입을 끊는다
브로커 전체가 위험할 때는 우선순위가 낮은 큐의 바인딩을 임시 제거해 유입을 막는 것이 합리적이다. 알림·통계성 이벤트를 잠시 포기하고 결제 흐름을 살리는 판단이다.
디스크 alarm이면 공간부터
로그 파일 정리나 볼륨 확장이 컨슈머 튜닝보다 훨씬 빠르다. 원인이 큐가 아니라 디스크를 채운 다른 파일인 경우도 많다.
3-1에서 하지 말아야 할 것 — 임계치를 올려 alarm을 끄는 것 가장 빠르게 alarm을 끄는 방법이라 손이 가지만, 브로커가 OOM으로 죽으면 훨씬 나빠진다. alarm은 "곧 죽는다"는 경고등이지 문제 자체가 아니다. 경고등을 끄는 것과 압력을 낮추는 것은 다르다. 굳이 손댄다면 여유가 실제로 있다는 근거를 확인한 뒤 아주 조금만 올린다.

3-2. 며칠 안 (구조 완화)

큐를 나눈다. 한 큐에 여러 종류의 작업이 섞여 있으면 느린 작업이 빠른 작업을 막는다. 무거운 작업을 별도 큐로 분리하고 워커도 따로 두면, 한쪽이 밀려도 다른 쪽은 정상 처리된다. 큐 분리는 성능 수단이 아니라 격리 수단이라는 관점이 중요하다.

큐 길이 상한을 건다. x-max-length 또는 x-max-length-bytes로 상한을 두면 적체가 브로커 전체를 위협하는 상황 자체를 막는다. 상한 초과 시 동작은 x-overflow로 정한다.

x-overflow 3종 — "상한을 넘으면 무엇을 희생할 것인가"의 선택지
x-overflow동작적합한 경우주의
drop-head가장 오래된 메시지를 버린다최신 값만 의미 있는 지표성 데이터유실이 조용히 일어난다 — 버린 건수를 지표로 남겨야 한다
reject-publish새 발행을 거부한다 (프로듀서가 오류를 받음)유실보다 발행 실패가 나은 경우프로듀서가 예외를 처리하지 않으면 그쪽이 터진다
reject-publish-dlx거부하면서 DLX로 보낸다거부된 것도 나중에 처리해야 하는 경우DLQ가 대신 쌓이므로 DLQ 소비 계획이 함께 있어야 한다
핵심은 "무한히 쌓이게 두지 않는 것" — 상한이 없으면 브로커가 죽는 방향으로 가고, 상한이 있으면 그 큐만 아프고 나머지는 산다

긴 큐를 디스크로 내린다. classic 큐에는 메시지를 가능한 한 디스크에 두는 lazy 모드가 있었다. 최신 버전에서는 classic 큐의 저장 방식이 개선되어 긴 큐를 자동으로 디스크로 내리는 동작이 기본에 가까워졌으므로, 쓰는 버전에서 이 설정이 여전히 의미가 있는지 확인해야 한다. 어느 쪽이든 원리는 같다 — 메모리 압력을 낮추는 대신 처리 지연을 감수한다.

3-3. 근본 대책 (설계)

컨슈머 처리량 자체를 올린다
배치 처리, 커넥션 풀 조정, 불필요한 동기 호출 제거. 자세한 내용은 16-rabbitmq-consumer-throughput-prefetch.md에서 다룬다.
프로듀서 쪽 배압(backpressure)
브로커가 막아서 API가 멈추는 것이 아니라, 애플리케이션이 스스로 판단해 빠르게 실패하게 만든다. 발행에 타임아웃을 두고, 실패하면 요청을 거절하거나 대체 경로(DB에 적재 후 나중에 발행)로 흘린다.
이벤트 발행 자체를 줄인다
같은 이벤트를 여러 큐에 복제하고 있다면 정말 그 소비자들이 다 필요한지 검토한다. RabbitMQ는 큐마다 실물 메시지가 쌓이므로 소비자 수가 곧 저장 부담이다.
감시 지표를 바꾼다 가산점
큐 깊이만 보지 말고 "현재 적체를 소진하는 데 걸리는 시간"을 지표로 만든다. 절대값보다 시간 환산이 훨씬 유용하다.

암기할 공식 하나 — 소진 시간

예상 소진 시간 = messages_ready ÷ ack rate

이 값이 SLA(업무상 허용 지연)를 넘기면 알람을 건다. 깊이 1만 건이 정상인 큐도 있고 100건이 비상인 큐도 있으므로, 절대값 임계치는 큐마다 다시 정해야 하고 트래픽이 변하면 무의미해진다.

개념 큐마다 다른 SLA를 같은 식으로 표현한다 — 지표 이름은 익스포터·버전마다 다르므로 이름을 외우지 말 것
# 알람 규칙 (의사 표현)
예상_소진_시간 = messages_ready / ack_rate

alert: NotifyBacklogTooSlow        expr: 예상_소진_시간 > 300     # 알림 큐 : 5분
alert: SettlementBacklogTooSlow    expr: 예상_소진_시간 > 3600    # 정산 큐 : 1시간

# 여기에 「추세」를 함께 본다 — 깊이가 일정하면 균형, 계속 증가하면 소진 시간이 발산 중
alert: BacklogGrowing              expr: publish_rate > ack_rate (지속)
추세가 절대값보다 먼저 알람을 울려야 한다 깊이가 일정하면 처리량과 유입량이 균형을 이룬 것이고, 계속 증가하면 소진 시간이 무한대로 발산하는 중이다. 발산 중인 큐는 지금 깊이가 작아도 시간문제다. 그래서 깊이 임계치 · 소진 시간 · 증가 추세 셋을 함께 걸어두고, 추세 알람을 가장 낮은 심각도로 가장 먼저 울리게 한다.

4. 실무 사례 — 알림 워커 하나가 주문 API를 멈춘 건

앞의 세 층이 왜 따로 필요한지를 한 건의 사고가 전부 보여준다. 이 사고에서 실제로 필요했던 조치는 전부 3-2·3-3에 있었고, 장애가 터진 뒤 3-1에서 꺼낼 수 있는 카드는 거의 없었다.

4-1. 상황 — 17분 만에 경계를 넘었다

외부 푸시 서비스가 응답 지연에 빠졌다. 알림 컨슈머는 타임아웃 설정 없이 그 API를 호출하고 있었다.

4-2. 무엇이 잘못됐나 — 기술적 원인은 하나, 설계 결함은 셋

「타임아웃 3부재」 — 이 사고의 정체

① 컨슈머 외부 호출에 타임아웃 없음
외부 호출에 타임아웃이 없으면 그 스레드는 영원히 잡힌다. 이것이 모든 것의 출발점이다.
② 큐에 길이 상한 없음
알림 큐가 무한정 쌓일 수 있었고, 그래서 브로커 전체를 위협하는 수준까지 갔다.
③ 프로듀서에 발행 타임아웃 없음
브로커가 블로킹했을 때 API 스레드가 무한 대기했다. 알림 발행이 실패해도 주문은 처리되어야 하는데, 그 구분이 코드에 없었다.
중요한 것은 "알림이 안 간 것"이 아니라 "알림 때문에 주문을 못 받은 것" — 중요도가 낮은 기능이 중요도가 높은 기능을 죽였다

        RestClient.create();   // 기본값에 맡김

after 3초 안에 반드시 스레드를 놓아준다
private final RestClient pushClient = RestClient.builder()
        .requestFactory(clientHttpRequestFactory(
                Duration.ofSeconds(2),    // 연결
                Duration.ofSeconds(3)))   // 응답
        .build();

@RabbitListener(queues = "notify.push")
public void handle(NotifyEvent e) {
    try {
        pushClient.post().uri("/push").body(e)
                  .retrieve().toBodilessEntity();
    } catch (ResourceAccessException timeout) {
        throw new AmqpRejectAndDontRequeueException(timeout);
    }   // 재시도는 지연 재시도 구조(14번)로 넘긴다
}
여기서 즉시 requeue하면 3절의 「돌(재배달 루프)」로 갈아탄다 타임아웃을 걸었다고 끝이 아니다. 실패한 메시지를 지연 없이 requeue하면 같은 메시지가 초당 수백 번 재배달되며 deliver rate ≫ ack rate 상태가 된다. CPU만 타고 처리량은 0인 그 증상이다. 그래서 타임아웃과 지연 재시도 + DLQ는 항상 짝으로 들어간다.

    log.warn("알림 발행 실패, outbox로 이월: {}", event.getId());
}
세 조치를 3절의 층에 대응시켜 보면, 이 사례가 왜 3절 안에 있어야 하는지가 분명해진다 컨슈머 타임아웃(①)과 프로듀서 격리(③)는 3-3의 근본 대책이고, 큐 길이 상한(②)은 3-2의 구조 완화다. 3-1의 응급 조치에 해당하는 것은 하나도 없다. 14:25에 alarm이 켜진 뒤 할 수 있었던 일은 알림 큐의 바인딩을 끊거나 큐를 비워 시간을 버는 것뿐이었고, 그것으로 원인이 사라지지는 않는다.
단기 완화는 시간을 벌 뿐 원인을 없애지 못한다 — 그래서 답변에서 두 층을 반드시 나눠 말해야 한다

4-4. 핵심 교훈 — 중요도가 다른 흐름은 격리한다

알림 큐와 결제 큐가 같은 브로커의 같은 메모리를 공유하는 한, 알림의 장애는 언제든 결제로 번질 수 있다. 정말 중요한 흐름이라면 브로커(또는 클러스터)를 분리하는 것까지 검토해야 한다.

vhost 분리로는 부족하다

vhost는 논리적 격리일 뿐이다 — 이름공간과 권한을 나눌 뿐, 메모리 alarm은 브로커 전역이다. 알림 vhost가 메모리를 채우면 결제 vhost의 프로듀서도 함께 블로킹된다.

격리의 강도는 계단식으로 올라간다

  • 같은 큐 안에서 분리 → 안 됨 (느린 작업이 빠른 작업을 막음)
  • 큐 분리 → 컨슈머 경합은 격리되지만 브로커 자원은 공유
  • vhost 분리 → 권한·이름 격리. alarm은 여전히 공유
  • 노드/클러스터 분리 → 자원까지 격리. 운영 비용이 대가

면접에서는 여기까지 말하면 충분하다 — "큐를 나누는 것은 컨슈머 경합의 격리이고, 브로커 자원의 격리는 노드를 나눠야 얻어집니다. vhost는 그 사이 어디에도 해당하지 않습니다."

6-2. 꼬리질문 셀프 테스트 — 먼저 스스로 답해 보고 펼친다

Kafka 컨슈머 랙 대응과 무엇이 다른가요?힌트: 진단 흐름이 아니라 「위험도」와 「쓸 수 있는 카드」가 다르다

진단 흐름은 비슷하고 위험도와 해소 수단이 다르다. Kafka의 랙은 오프셋 차이라 브로커에 부담이 없고 리텐션 기간만큼 시간이 있다. RabbitMQ의 적체는 브로커 메모리를 실제로 먹으므로 분 단위로 alarm에 도달한다.

확장은 RabbitMQ가 쉽다

Kafka는 파티션 수가 컨슈머 수의 상한이라 급할 때 늘릴 수 없고 컨슈머 내부 병렬화로 우회해야 한다. RabbitMQ는 큐 하나에 워커를 몇 대든 붙일 수 있어 증설이 즉시 효과다.

시간은 Kafka가 준다

Kafka는 밀려도 브로커가 버텨준다. RabbitMQ는 밀리는 동안 브로커 자체가 위험해지고, 임계치를 넘으면 프로듀서를 막아 서비스 전체를 세운다.

덧붙일 한 줄 — "Kafka는 되돌려 다시 읽을 수 있지만, RabbitMQ는 ack된 메시지가 사라집니다." 그래서 RabbitMQ에서는 「버리는 판단」이 곧 유실 결정이고, 그 결정을 장애 중에 즉흥으로 하지 않도록 사전에 등급을 정해 둔다.

메모리 alarm이 걸렸습니다. 지금 무엇부터 하나요?힌트: 프로듀서가 막혀 있다 = 시간이 없다

프로듀서가 막혀 있으므로 시간이 없다는 것을 전제로 답해야 한다. 순서는 「찾 · 보 · 끊 · 버 · 참」이다.

1
어느 큐가 메모리를 먹고 있는지 확인한다.
rabbitmqctl list_queues name messages memory --sort memory
2
그 큐의 컨슈머 상태를 본다. 컨슈머가 0이면 애플리케이션을 살리는 것이 최우선이다.
3
당장 살릴 수 없다면 유입을 끊는다. 그 큐의 바인딩을 임시 제거하면 새 메시지가 안 들어온다. 이미 쌓인 것은 남지만 더 나빠지지는 않는다.
4
중요도가 낮은 큐라면 비우는 것도 선택지다. rabbitmqctl purge_queue는 되돌릴 수 없으므로 마지막 수단이지만, 알림 큐 하나를 버려 결제를 살리는 판단이 필요한 순간이 실제로 있다.
5
임시로 임계치를 올리는 것은 신중해야 한다. 브로커가 OOM으로 죽으면 훨씬 나빠진다.
이 답의 핵심은 절차가 아니라 사전 준비다 "무엇을 버릴지 미리 정해두는 것"이 요점이다. 장애 중에 "이 큐 비워도 되나요?"를 물어볼 시간은 없다. 큐마다 중요도 등급을 사전에 문서화해두는 것이 운영 성숙도다.
적체가 반복되는데 컨슈머를 계속 늘리는 게 맞나요? 시니어 변별힌트: 증설이 효과가 있는 조건이 따로 있다

아니다. 컨슈머 증설은 컨슈머가 병목일 때만 효과가 있다.

병목이 다운스트림(DB, 외부 API)이라면 컨슈머를 늘리는 것은 그 다운스트림에 더 많은 부하를 보내는 것이다. DB 커넥션 풀이 20인데 컨슈머를 50대로 늘리면 30대는 커넥션을 기다리며 놀고, DB는 더 느려진다. 증상이 악화된다.

① 병목을 먼저 확정
컨슈머 스레드 덤프를 뜬다. 대부분 스레드가 DB 대기 중이면 병목은 DB다.
② 병목이 컨슈머 자신이면
증설한다. 이때만 증설이 제값을 한다.
③ 병목이 다운스트림이면
그쪽을 고친다 — 쿼리 튜닝, 인덱스, 배치화, 캐시.
④ 못 고치면
컨슈머 수를 오히려 제한하고 유입 쪽을 조절한다. 처리할 수 없는 속도로 받아봐야 큐만 쌓인다.
4번을 말할 수 있으면 좋다 — "처리량을 올릴 수 없으면 유입을 줄이는 것이 다음 선택지"

이 판단은 부하 제어를 이해한 사람의 답이다. 다만 유입을 줄이면 큐는 더 쌓이므로, 반드시 큐 길이 상한·소진 시간 알람과 함께 말해야 앞뒤가 맞는다.

큐 깊이 알람의 임계치는 어떻게 잡나요?힌트: 건수는 큐마다 다르지만 「분」은 기획과 합의할 수 있다

절대값으로 잡으면 큐마다 다시 정해야 하고 트래픽이 변하면 무의미해진다. 시간으로 환산하는 것이 낫다.

예상 소진 시간 = messages_ready / ack rate

이 값이 업무상 허용 지연(예: 알림은 5분, 정산은 1시간)을 넘으면 알람을 건다. 이점은 셋이다.

  • 트래픽이 늘어도 임계치를 다시 안 잡아도 된다.
  • 컨슈머가 느려지면 같은 깊이에서도 알람이 울린다.
  • 기획자와 "몇 분까지 허용되는가"를 협의한 결과를 그대로 지표로 옮길 수 있다.
여기에 「증가 추세」를 함께 본다 깊이가 일정하면 처리량과 유입량이 균형을 이룬 것이고, 계속 증가하면 소진 시간이 무한대로 발산하는 중이다. 추세가 절대값보다 먼저 알람을 울려야 한다.

"깊이가 평평한데 괜찮은가"라는 반문도 여기서 답이 나온다 — 평평하다는 것은 유입과 처리가 균형을 이뤘다는 뜻일 뿐, 그 상태의 소진 시간이 SLA 안인지는 별개다. 평평한 채로 소진 시간이 30분이면 그 큐는 상시 30분 지연 서비스다.

적체된 메시지가 이미 유효기간이 지난 경우는 어떻게 하나요?힌트: 30분 늦은 "결제 완료 알림"을 지금 보내는 게 맞을까

실무에서 자주 있는 상황이다. 30분 밀린 큐에 "결제 완료 알림"이 쌓여 있다면, 이제 와서 보내는 것이 오히려 이상할 수 있다.

이때 쓰는 것이 메시지 TTL이다. 큐에 x-message-ttl을 걸면 지정 시간이 지난 메시지가 자동으로 만료되어 사라지거나(DLX가 있으면 그쪽으로) 간다.

@Bean Queue realtimeNotifyQueue() {
    return QueueBuilder.durable("notify.realtime")
            .ttl(300_000)                              // 5분 지난 알림은 의미 없다
            .deadLetterExchange("notify.expired.dlx")  // 버리지 말고 집계는 한다
            .build();
}

이 설계의 이점은 적체가 자동으로 해소된다는 것이다. 컨슈머가 회복되면 유효한 메시지부터 처리하게 되고, 만료된 것들은 이미 빠져 있다.

다만 「어떤 메시지가 만료되어도 되는지」는 업무 판단이다 결제 원장 이벤트에 TTL을 걸면 정합성이 깨진다. 실시간성이 가치의 전부인 메시지에만 적용해야 한다. 그리고 만료도 유실이므로, DLX로 흘려 "몇 건이 만료됐는지"는 반드시 집계한다.
Ready는 0인데 Unacked만 잔뜩 쌓여 줄지 않습니다. 컨슈머가 회복되면 어떻게 되나요? 시니어 변별힌트: ack 안 된 메시지는 「사라지지 않고 되돌아온다」

먼저 상태 해석 — 「잡」 분기다. 컨슈머가 받아간 것을 끝내지 못하고 붙잡고 있는 중이며, 대개 타임아웃 없는 외부 호출·락 대기·데드락이다. 스레드 덤프가 즉답을 준다.

중요한 것은 회복 순간의 그림이다. ack 되지 않은 메시지는 채널·커넥션이 닫히는 순간 전부 큐로 되돌아간다(requeue). 그래서 이런 일이 벌어진다.

Ready 급증
Unacked에 있던 수만큼 Ready가 한 번에 튄다. 대시보드만 보면 "갑자기 적체가 폭증"한 것처럼 보인다
대량 중복 처리
이미 절반쯤 처리된 메시지도 되돌아온다. 멱등성이 없으면 그대로 사고다 (04번 문서)
재차 적체
되돌아온 것 + 그동안 유입된 것이 한꺼번에 몰린다. 회복 직후가 가장 위험한 구간
브로커가 먼저 끊어버리는 경우도 있다 브로커에 미ack 상한(consumer_timeout)이 설정돼 있으면, 그 시간을 넘긴 컨슈머의 채널이 닫히고 메시지가 requeue된다. 이 경우 같은 메시지가 계속 되돌아오며 「돌(재배달 루프)」로 증상이 바뀐다. 기본값과 존재 여부는 버전·설정에 따라 다르므로 쓰는 버전에서 확인해야 한다. 요점은 하나다 — 오래 붙잡는 컨슈머는 언젠가 강제로 끊긴다는 전제로 설계한다.

그래서 이 상황의 조치는 "컨슈머를 되살린다"가 아니라 "되살아났을 때 감당할 수 있게 만든다"까지 포함한다 — 멱등성 · prefetch 축소 · 유입 일시 차단 셋을 함께 준비한다.

적체가 심한 상태에서 컨슈머를 재배포해도 되나요?힌트: 배포는 「일시적으로 처리량을 0으로 만드는 행위」다

상황에 따라 다르고, 판단 기준은 "병목이 무엇인가"다.

해도 되는 경우

  • 컨슈머 코드의 버그·설정이 원인일 때 — 배포가 유일한 해결이다
  • 롤링으로 일부만 교체하면서 처리량을 0으로 만들지 않을 수 있을 때

미뤄야 하는 경우

  • 원인이 다운스트림일 때 — 배포해도 안 낫고 정지 시간만 손해
  • alarm이 이미 켜진 상태 — 처리량을 잠시라도 0으로 만들면 더 빨리 나빠진다
적체 중 배포에는 숨은 비용이 둘 있다 ① 정지 시간이 prefetch에 비례한다. graceful shutdown은 쥐고 있는 메시지를 다 처리하거나 반납할 때까지 기다리므로, prefetch × 건당 처리 시간만큼 멈춘다. ② 강제 종료(SIGKILL)하면 쥔 것이 전부 재배달된다 — 적체 중에는 그 양이 특히 크다. 멱등성이 없으면 배포가 곧 중복 사고가 된다.

정리 문장 — "적체 중 배포는 처리량을 잠시 0으로 만드는 행위입니다. 원인이 컨슈머 안에 있을 때만 이득이고, 그 외에는 alarm이 풀린 뒤로 미룹니다."

quorum queue를 쓰면 적체가 덜 위험해지나요?힌트: 압력의 「종류」가 바뀌는 것이지 사라지는 것이 아니다

메모리 압력은 줄어들 수 있지만, 위험이 사라지는 것은 아니다. quorum 큐는 메시지를 디스크에 기록하고 여러 노드에 복제하는 구조라, 긴 큐가 메모리에 눌러앉는 양상은 classic 큐보다 덜하다. 하지만 대가가 따라온다.

좋아지는 것
메모리 편중이 덜하다. 적체가 곧바로 메모리 alarm으로 직행하는 경로가 완화된다
나빠지는 것
디스크·네트워크 비용이 복제본 수만큼 늘어난다. 디스크 alarm 쪽 위험은 오히려 커진다
그대로인 것
alarm은 브로커 전역이라는 사실. 어떤 큐 타입을 쓰든 임계치를 넘기면 프로듀서가 막힌다
그래서 결론은 같다 — 큐 타입을 바꿔도 「길이 상한」과 「중요도별 격리」는 여전히 필요하다

선택 기준 자체는 17-classic-vs-quorum-queue.md에서 다룬다. 이 문항에서는 "큐 타입은 압력의 종류를 바꿀 뿐, 무한히 쌓이는 구조를 고쳐주지는 않는다"까지만 말하면 충분하다.

purge 말고 안전하게 큐를 비우는 방법은 없나요?힌트: 「버린다」와 「옮긴다」는 다르다

purge_queue는 되돌릴 수 없는 삭제다. 급할 때는 그것이 정답인 순간이 있지만, 옮기는 선택지를 먼저 검토할 가치가 있다.

다른 큐/브로커로 옮긴다
Shovel을 걸어 적체된 메시지를 다른 큐나 다른 브로커로 이동시킨다. 위험한 브로커의 압력은 즉시 내려가고, 데이터는 남는다.
임시 컨슈머로 덤프한다
아무 처리도 하지 않고 받아서 파일·오브젝트 스토리지에 적재만 하는 컨슈머를 붙인다. 빠르게 큐가 비고, 나중에 재발행할 수 있다.
사전 조치가 진짜 답
x-max-length + reject-publish-dlx를 미리 걸어두면, 초과분이 자동으로 DLQ로 흘러 애초에 "비울지 말지"를 고민할 일이 없다.
주의
옮기는 조치도 브로커 자원을 쓴다. 이미 alarm이 켜져 초 단위로 급한 상황이라면 중요도 낮은 큐는 그냥 버리는 편이 빠르다.

면접용 한 줄 — "버리기 전에 옮길 수 있는지 봅니다. 다만 옮기는 것도 시간을 쓰기 때문에, 무엇을 버려도 되는지는 장애 전에 정해 둡니다."

6-3. 마지막 점검 — 이 순서대로 말하면 답변이 닫힌다

답변 체크리스트 순서에 의미가 있다

① 증상의 성격 규정
"Kafka 랙과 달리 브로커 자원을 실제로 먹고, 끝에는 프로듀서 블로킹이 있습니다" — 이 한 줄로 시작한다
② alarm 여부 먼저
켜져 있으면 원인 분석과 병행해 압력부터 낮춘다. 순서를 바꾸면 그 동안 서비스가 멈춰 있다
③ 두 숫자로 분기
consumers → Ready/Unacked → rate. 「부·느·잡·돌·몰」 다섯을 조건과 함께 말한다
④ 병목 확정 후 증설
스레드 덤프로 확인. 다운스트림이 병목이면 증설은 악화라는 것을 반드시 덧붙인다
⑤ 단기와 근본을 분리
"분 단위 / 며칠 / 설계" 세 층으로 나눠 말한다. 앞의 둘은 시간을 벌 뿐이라는 문장을 넣는다
⑥ 마무리는 격리와 지표
큐 길이 상한 + 중요도별 격리, 그리고 소진 시간 지표(가산점). 여기까지 오면 답변이 닫힌다

①을 빠뜨리면 16번(처리량 튜닝) 답변과 구분되지 않고, ②를 빠뜨리면 장애 대응 경험이 없어 보이며, ⑤를 빠뜨리면 "급한 불만 끄는 사람"으로 읽힌다.

한 줄 요약
RabbitMQ의 적체는 Kafka의 랙과 달리 브로커의 메모리를 실제로 채워 프로듀서를 블로킹하고 서비스 전면 장애로 번지므로, Ready/Unacked 조합으로 원인을 빠르게 가르고(컨슈머 부재 / 처리 지연 / 재배달 루프 / 유입 폭증), 단기로는 워커 증설과 유입 차단으로 압력을 낮춘 뒤, 근본적으로는 큐 길이 상한과 중요도별 큐 격리로 "한 큐의 적체가 브로커 전체를 위협하지 않는" 구조를 만들어야 한다.
