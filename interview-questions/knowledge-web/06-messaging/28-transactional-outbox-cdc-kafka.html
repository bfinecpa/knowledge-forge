Outbox + CDC — DB 트랜잭션 로그를 이벤트 소스로
"커밋은 됐는데 발행이 안 됐다"를 코드가 아니라 구조로 없애는 법

면접 질문: "Kafka로 이벤트를 발행하는 서비스에서 'DB 커밋은 됐는데 발행이 실패'하는 문제를 어떻게 해결하나요? (Transactional Outbox + CDC)"

핵심 관전 포인트 — DB와 Kafka는 한 트랜잭션으로 묶을 수 없으므로(이중 쓰기 문제), 이벤트를 비즈니스 변경과 같은 트랜잭션으로 outbox 테이블에 기록하고 별도 경로로 발행한다. CDC는 그 발행 경로를 DB의 트랜잭션 로그 구독으로 구현한 것 — PostgreSQL이라면 WAL(Write-Ahead Log)을 논리적 디코딩으로 행 단위 변경으로 풀어내고, Debezium 커넥터가 복제 슬롯을 통해 그 스트림을 받아 outbox INSERT를 Kafka로 흘린다. 커밋이 WAL에 남는 순간 발행이 예약된 것과 같아서 유실이 없고, 폴링과 달리 DB 부하·지연이 거의 없다. 보장은 전 구간 at-least-once — 커넥터 재시작 시 중복 발행이 가능하므로 멱등 컨슈머가 세트이고, 순서는 논리적 디코딩이 커밋 순서대로 내보내는 성질 + aggregate ID 파티션 키로 지킨다. 운영의 급소는 복제 슬롯이다 — 슬롯은 아직 안 읽은 WAL을 서버가 지우지 못하게 붙잡으므로, 커넥터가 오래 죽어 있으면 데이터가 사라지는 게 아니라 디스크가 차서 DB 전체가 멈춘다.
  • 1
    문제를 "코드 버그"가 아니라 "구조 결함"으로 규정합니다. DB와 Kafka는 서로 다른 시스템이라 두 쓰기를 하나로 묶어 줄 공통의 트랜잭션이 없습니다(이중 쓰기 문제). 커밋→발행이면 유실, 발행→커밋이면 거짓 이벤트라 순서를 바꿔도 안 풀립니다. 그래서 방향은 하나 — 원자성의 단위를 DB 하나로 모읍니다.
  • 2
    Outbox로 모으고, CDC로 흘립니다. 이벤트를 비즈니스 변경과 같은 로컬 트랜잭션으로 outbox 테이블에 INSERT하면 "주문은 완료됐는데 이벤트는 없는" 상태가 구조적으로 불가능해집니다. 남은 일은 누가 그것을 Kafka로 옮기느냐(릴레이)인데, Debezium이 PostgreSQL의 WAL을 논리적 디코딩으로 읽어 밀리초 지연으로 흘립니다 — 폴링 SELECT가 사라지고 릴레이 코드가 인프라로 이동합니다.
  • 3
    보장의 한계와 운영 급소까지 말합니다. 전 구간 보장은 at-least-once라 커넥터 재시작 시 중복이 나오므로 outbox PK를 이벤트 ID로 쓰는 멱등 컨슈머가 세트입니다. 그리고 이 패턴을 떠받치는 복제 슬롯이 곧 최대 위험입니다 — 커넥터가 오래 죽으면 WAL이 안 지워져 DB 디스크가 차고 서비스 전체가 멈춥니다. 슬롯 지연 감시 + max_slot_wal_keep_size 상한까지가 답변의 완성입니다.

0. 질문 + 출제 의도 · 이 문서가 겨냥하는 약점

질문 — "Kafka로 이벤트를 발행하는 서비스에서 'DB 커밋은 됐는데 발행이 실패'하는 문제를 어떻게 해결하나요? (Transactional Outbox + CDC)"

출제 의도 — DB와 메시지 브로커라는 두 시스템에 걸친 원자성 문제의 표준 해법을 아는지 본다. 패턴 이름을 외웠는지가 아니라 이 패턴이 왜 필요한지를 스스로 유도할 수 있는지를 본다. 필요성을 설명할 수 있으면 분산 정합성의 핵심을 이해한 것이다.

이 문서의 사정거리 이중 쓰기 문제의 구조, AFTER_COMMIT의 한계, outbox 테이블·폴링 릴레이의 Spring 구현은 02-spring/23-transactional-outbox-pattern.md에 있다. 이 문서는 Kafka 관점 — CDC 연계, 발행 보장 체인, 순서와 중복 — 에 집중한다.

이렇게 답하면 반쪽이다

  • "재시도하면 됩니다" — 프로세스가 죽으면 재시도할 주체 자체가 사라진다. 재시도는 살아 있는 동안의 실패만 덮는다.
  • "발행을 먼저 하고 커밋합니다" — 유실이 거짓 이벤트로 바뀔 뿐이다. 일어나지 않은 일에 대한 이벤트가 떠돈다.
  • "Kafka 트랜잭션으로 묶습니다" — Kafka 트랜잭션은 Kafka 세계 안의 원자성이다. 외부 DB와는 묶이지 않는다.
  • "Outbox 쓰면 끝입니다" — Outbox는 "누가 옮기느냐"를 남긴다. 릴레이 이야기가 없으면 답이 절반이다.
  • "CDC를 쓰면 exactly-once가 됩니다" — 아니다. 전 구간 at-least-once이고, 중복 제거는 소비 측 몫이다.
  • "CDC는 DB에 부담이 없어서 무조건 좋습니다" — 부담의 종류가 바뀐 것이다. 복제 슬롯 감시라는 새 책임이 생긴다.

이 문서가 채워 주는 것

  • 왜 순서를 바꿔도 안 풀리는가 — 이중 쓰기 문제의 구조와, "묶을 방법을 찾지 말고 하나로 만든다"는 발상 전환.
  • CDC 부품 3종의 정의 — WAL / 논리적 디코딩 / 복제 슬롯이 각각 무엇이고 왜 필요한지.
  • 보장 체인 4구간 — 구간마다 유실 방지 수단과 중복이 생기는 지점이 다르다.
  • 순서를 지키는 4겹 사슬 — 어느 한 고리가 끊기면 무엇이 깨지는지.
  • "outbox를 비워도 된다"의 진실 — 그리고 PostgreSQL MVCC에서 남는 죽은 튜플.
  • 슬롯이 DB를 멈추는 인과 6단계 — MySQL과 문제의 방향이 정반대인 이유까지.

이 문서를 관통하는 한 문장

두 시스템을 묶을 방법을 찾지 말고 — 묶어야 할 두 시스템을 하나로 만든다

2PC도, Kafka 트랜잭션도 "DB와 브로커를 어떻게 묶을까"라는 질문에 대한 답을 찾으려는 시도다. Outbox는 질문 자체를 바꾼다 — Kafka로 나갈 메시지를 DB에 쓰는 행위로 치환해서, 두 시스템에 대한 쓰기를 한 시스템에 대한 두 쓰기로 만들어 버린다. 그러면 이미 가진 로컬 트랜잭션이 문제를 푼다.

1. 이중 쓰기 — 커밋과 발행 사이엔 항상 틈이 있다

가장 흔한 코드부터 본다. 누구나 처음에는 이렇게 쓴다.

before 커밋 후 발행 — 이 두 줄 사이 어디서든 죽을 수 있다
// before: 커밋 후 발행
@Transactional
public void completeOrder(Long id) { ... }   // ① DB 커밋

kafkaTemplate.send("order-completed", event); // ② 발행①과 ② 사이 = 무방비 구간
//                                            크래시 / 브로커 장애 / 네트워크 단절
//                                            → 주문은 완료됐는데 이벤트는 세상에 없다

여기서 대부분 "그럼 순서를 바꾸면?"을 떠올린다. 바꿔도 안 풀린다. 문제가 옮겨 갈 뿐이다.

1-1. 원인은 순서가 아니라 구조다

DB와 Kafka는 서로 다른 시스템이고, 두 시스템에 대한 쓰기를 하나의 원자적 단위로 묶어 줄 공통의 트랜잭션이 없다. 이것을 이중 쓰기(dual write) 문제라고 부른다. 그림으로 보면 원인이 한눈에 보인다 — 두 쓰기를 감싸는 상자가 없다.

이중 쓰기의 두 얼굴 — 이름을 붙여서 외운다

커밋 → 발행 = 유실
DB에는 있는데 이벤트가 없다
후속 처리(정산·알림·배송)가 영원히 일어나지 않는다. 조용하고, 사후 발견이 어렵다.
발행 → 커밋 = 거짓 이벤트
이벤트는 있는데 DB에는 없다
컨슈머가 일어나지 않은 일을 처리한다. 없는 주문을 정산하고 없는 배송을 시작한다.

면접에서 이 두 방향을 모두 말해야 "순서를 바꿔도 안 된다"는 결론에 설득력이 생긴다. 한쪽만 말하면 "그럼 반대로 하면 되잖아요?"라는 되물음에 막힌다.

"재시도하면 되지 않나요?"가 안 통하는 이유 재시도는 프로세스가 살아 있을 때의 실패만 덮는다. 커밋 직후 프로세스 자체가 죽으면 재시도할 주체와 재시도에 필요한 정보(이벤트 내용)가 메모리와 함께 사라진다. 재시도 큐를 메모리에 두는 순간 같은 문제가 한 층 아래에서 반복된다 — "재시도할 일이 있다"는 사실 자체를 어딘가 내구성 있는 곳에 남겨야 하고, 그 "어딘가"가 바로 outbox다.

그렇다면 방향은 하나다. 원자성의 단위를 DB 하나로 모아야 한다. Kafka로 나갈 메시지 자체를 DB에 쓰는 것으로 바꾸면, 두 시스템에 대한 쓰기가 한 시스템에 대한 두 쓰기가 되고 로컬 트랜잭션이 그것을 묶어 준다.

2. Outbox — 보낼 편지함을 DB 안에 둔다

아웃박스(outbox)는 말 그대로 "보낼 편지함"이다. 편지를 우체통에 넣는 순간 "보낸 것"이 아니라 "보낼 것으로 확정된 것"이 된다. 실제 배달은 집배원이 나중에 한다. 이 비유가 패턴의 전부다 — 발행을 "즉시 실행"에서 "예약"으로 바꾼다.

2-1. outbox 테이블 — 컬럼 하나하나가 역할을 가진다

CREATE TABLE outbox (
    id             bigserial    PRIMARY KEY,   -- 이 값이 곧 이벤트 고유 ID가 된다
    aggregate_type varchar(50)  NOT NULL,      -- 예: 'ORDER' — 목적지 토픽 라우팅에 쓴다
    aggregate_id   varchar(50)  NOT NULL,      -- 예: 주문 ID — 메시지 키(파티션 키)가 된다
    event_type     varchar(50)  NOT NULL,      -- 예: 'OrderCompleted'
    payload        jsonb        NOT NULL,      -- 이벤트 본문. jsonb라 컬럼 추가 없이 스키마가 진화한다
    created_at     timestamptz  NOT NULL DEFAULT now()
);

outbox 컬럼 = 메시징 요소와 1:1로 대응한다 (이 매핑을 외운다)

컬럼Kafka에서 무엇이 되는가왜 그 자리에 필요한가
id (bigserial PK)이벤트 고유 ID컨슈머의 멱등 키. DB가 유일성을 보장해 주므로 별도 UUID 생성기가 필요 없다.
aggregate_type목적지 토픽ORDER → order-events. 라우팅을 데이터로 표현해 커넥터 설정을 단순하게 유지한다.
aggregate_id메시지 키 = 파티션 키같은 주문의 이벤트를 같은 파티션에 몰아 순서를 지킨다. 9절 사슬의 마지막 고리.
event_type헤더 / 타입 식별자컨슈머가 역직렬화 대상과 분기를 정한다.
payload (jsonb)메시지 본문스키마가 컬럼에 묶이지 않아 DDL 없이 진화한다. 커넥터 재설정도 불필요.
created_at(발행 안 함)보존 기간·파티셔닝 기준. 10절의 파티션 드롭 전략에서 쓰인다.

암기 포인트 — "PK는 멱등 키, aggregate_type은 토픽, aggregate_id는 파티션 키". 이 세 개만 말해도 설계를 이해했다는 신호가 된다.

after 발행을 "예약"으로 바꿔 한 트랜잭션 안에 넣는다
@Transactional
public void completeOrder(Long id) {
    Order order = orderRepository.findById(id).orElseThrow();
    order.complete();                     // ① 비즈니스 변경

    outboxRepository.save(Outbox.of(      // ② 발행 예약같은 DB · 같은 TX
            "ORDER", id.toString(), "OrderCompleted", toPayload(order)));
    // ①과 ②는 함께 커밋되거나 함께 롤백된다.
    // "주문은 완료됐는데 이벤트는 없는" 상태가 구조적으로 불가능해졌다.
}
코드에서 사라진 것에 주목한다 kafkaTemplate.send()가 비즈니스 메서드에서 통째로 사라졌다. 도메인 서비스는 이제 "무슨 일이 일어났는지 DB에 기록"만 한다 — 브로커 주소도, 직렬화도, 재시도도 모르는 코드가 된다. 나중에 Kafka를 다른 브로커로 바꿔도 이 메서드는 한 글자도 안 바뀐다.

2-2. 남은 문제는 하나 — 누가 옮기는가

여기까지가 Outbox다. 그런데 outbox에 행이 쌓여 있을 뿐 아직 Kafka에는 아무것도 안 갔다. "outbox에 쌓인 레코드를 누가, 어떻게 Kafka로 옮기느냐" — 이 옮기는 역할을 릴레이(relay)라고 부르고, 구현이 두 가지다.

① 폴링 릴레이 — 내가 물어본다

스케줄러가 짧은 주기로 미발행 행을 집어 발행하고 발행 완료를 마킹한다.

SELECT * FROM outbox
 WHERE published_at IS NULL
 ORDER BY id
 LIMIT 100
   FOR UPDATE SKIP LOCKED;
  • 스케줄러 + DB만 있으면 되어 도입이 쉽다
  • 이벤트가 없어도 조회는 계속 돈다
  • 발행 지연 = 폴링 주기

② CDC 릴레이 — DB가 알려 준다

DB가 이미 쓰고 있는 트랜잭션 로그를 구독해 INSERT를 실시간으로 감지한다.

# 애플리케이션 코드 없음
# 인프라 설정만 존재한다
plugin.name=pgoutput
slot.name=outbox_slot
table.include.list=public.outbox
  • 주기적 SELECT가 아예 없다
  • 지연이 로그 전파 속도로 줄어든다
  • 대신 운영할 인프라가 하나 늘어난다

이 문서의 본론은 후자다. 그런데 "CDC가 더 좋다"가 아니라 "무엇을 내주고 무엇을 얻는가"를 먼저 정리하고 들어가야 한다.

3. 릴레이 두 갈래 — 폴링 vs CDC

3-1. 축을 세워 놓고 비교한다

같은 Outbox 테이블, 다른 릴레이 — 무엇이 실제로 달라지는가
축폴링 릴레이CDC (Debezium)면접에서 붙일 한마디

3-2. CDC 전체 그림 — 이 다음 세 절은 이 그림의 확대다

CDC(Change Data Capture, 변경 데이터 캡처)는 DB에 SELECT를 날려 "뭐 바뀐 거 있어?"를 물어보는 대신, DB가 자기 내구성을 위해 이미 쓰고 있는 트랜잭션 로그를 읽어 변경을 감지하는 방식이다. 대표 구현이 Debezium이고 Kafka Connect의 소스 커넥터로 동작한다.

PostgreSQL CDC 부품 3종 — 이름과 한 줄 역할을 세트로 외운다

WAL
Write-Ahead Log
데이터를 고치기 전에 변경 내용을 먼저 적는 로그. 크래시 복구와 복제의 원천이자 CDC의 데이터 소스.
논리적 디코딩
logical decoding
WAL의 물리적 기록을 시스템 카탈로그와 대조해 행 단위 변경으로 풀어 주는 기능. wal_level=logical 필요.
복제 슬롯
replication slot
"이 구독자가 어디까지 읽었나"를 서버 쪽에 남기는 표식. 안 읽은 WAL을 지우지 못하게 붙잡는다.

세 부품이 각각 하나의 질문에 답한다 — WAL: "데이터는 어디에 있나?" / 논리적 디코딩: "그걸 어떻게 읽나?" / 복제 슬롯: "어디까지 읽었는지 누가 기억하나?"

4. WAL — 왜 있고, 왜 그대로는 못 읽는가

PostgreSQL은 테이블 데이터 파일을 곧바로 고치지 않는다. "무엇을 어떻게 바꿀 것인지"를 먼저 로그 파일에 순차로 기록하고, 실제 데이터 페이지는 그 뒤에 바꾼다. 이 로그가 WAL(Write-Ahead Log, 미리 쓰는 로그)이다. 이름 그대로 데이터 변경보다 로그를 "먼저(ahead) 쓴다(write)".

4-1. 그런데 WAL을 그대로는 못 읽는다

"그럼 WAL을 읽으면 되겠네"인데, 그대로는 안 된다. WAL에 담긴 것은 물리적 변경 기록이기 때문이다. "테이블 orders의 몇 번째 파일 블록의 몇 번째 바이트부터를 이런 값으로 바꿔라" 같은 형태다.

면접에서 이 한 줄이 깊이를 만든다 "Debezium이 WAL을 읽습니다"까지는 누구나 말한다. "WAL은 물리 로그라 그대로는 못 읽고, 논리적 디코딩이 행 단위로 풀어 준 것을 읽습니다"까지 가면 왜 wal_level=logical이 필요한지가 자연스럽게 설명된다 — 다음 절이 그 이야기다.

5. 논리적 디코딩 — 물리 로그를 행 단위로 푼다

그 간극을 메우는 PostgreSQL의 기능이 논리적 디코딩(logical decoding)이다. WAL의 물리적 기록을 읽어 시스템 카탈로그와 대조해 가며 행 단위 변경(INSERT / UPDATE / DELETE)으로 풀어 주는(decode) 기능이다. "물리적으로 기록된 것을 논리적 의미로 디코딩한다"는 뜻에서 붙은 이름이다.

설정 켜는 방법은 한 줄이다 — 다만 재시작이 필요하다
# postgresql.conf — 서버 재시작이 필요하다
wal_level = logical        # 기본값은 replicaWAL 볼륨이 늘어난다

wal_level을 logical로 올리면 PostgreSQL이 WAL에 논리적 디코딩에 필요한 추가 정보를 더 실어 쓴다. 즉 공짜가 아니라 WAL 볼륨이 늘어나는 대가가 있다. 11절에서 볼 디스크 문제와도 직결되므로 기억해 둔다.

wal_level = minimal
복구에 꼭 필요한 최소 기록. 복제도 CDC도 불가.
wal_level = replica
기본값
물리 복제·PITR 가능. 논리적 디코딩은 불가.
wal_level = logical
CDC에 필요
디코딩용 추가 정보까지 기록. WAL 볼륨 증가가 대가.

5-1. 출력 플러그인 — 디코딩 결과를 어떤 형식으로 내보낼까

디코딩 결과를 어떤 형식으로 내보낼지는 출력 플러그인(output plugin)이 정한다. PostgreSQL 10부터 pgoutput이 서버에 기본 내장돼 있고, Debezium PostgreSQL 커넥터도 이걸 기본으로 쓴다. 예전에는 wal2json 같은 확장을 서버에 따로 설치해야 했는데, 지금은 그럴 필요가 없다.

5-2. 이 문서에서 두 번 이상 값을 하는 성질 — 커밋된 것만, 커밋 순서대로

논리적 디코딩의 성질 중 이 문서에서 두 번 이상 값을 하는 것이 하나 있다. 커밋된 트랜잭션만, 커밋 순서대로 내보낸다. 진행 중인 트랜잭션의 변경은 커밋될 때까지 모아 뒀다가 커밋 시점에 한꺼번에 흘리고, 롤백된 트랜잭션의 변경은 아예 나오지 않는다.

논리적 디코딩의 두 성질 — 이 문서 후반부의 근거가 된다

① 커밋된 것만 나온다
롤백된 트랜잭션의 변경은 스트림에 존재하지 않는다. → "거짓 이벤트"가 구조적으로 불가능(1절 오른쪽 실패 모드가 사라진다).
② 커밋 순서대로 나온다
동시 진행 트랜잭션도 스트림에서는 한 줄로 늘어선다. → 9절 순서 보장 사슬의 첫 번째 고리.

면접에서 "CDC를 쓰면 발행→커밋 롤백 문제는 어떻게 되나요?"를 물으면 이 ①을 꺼내면 된다 — "애초에 커밋 안 된 것은 스트림에 나오지 않습니다."

6. 복제 슬롯 — 보장의 근거이자 위험의 근원

논리적 디코딩을 쓰려면 복제 슬롯(replication slot)이 반드시 있어야 한다. 복제 슬롯은 "이 구독자가 WAL을 어디까지 읽고 확인했는지"를 PostgreSQL 서버 쪽에 남겨 두는 표식이다. 슬롯 하나가 구독자 하나에 대응하고, 구독자가 접속을 끊었다가 다시 붙으면 슬롯에 적힌 위치부터 이어서 받는다. Debezium이 재시작해도 처음부터 다시 읽지 않는 것이 이 덕분이다.

왜 "서버 쪽"에 남기는 것이 중요한가 읽은 위치를 클라이언트가 기억한다면, 클라이언트가 죽어 있는 동안 서버는 그 사실을 모르고 WAL을 지워 버린다. 위치를 서버가 들고 있어야 서버가 "아직 이 구독자가 안 읽었으니 보존해야겠다"고 판단할 수 있다. 슬롯은 "위치 기억"과 "보존 강제"라는 두 일을 한꺼번에 한다 — 그리고 두 번째가 이 절의 주제다.

6-1. 이 문서 전체에서 가장 중요한 성질

슬롯이 존재하는 한, PostgreSQL은 그 슬롯이 아직 확인하지 않은 WAL을 절대 지우지 않는다

원래 PostgreSQL은 체크포인트가 끝나면 더 이상 필요 없어진 WAL 파일을 재활용하거나 삭제한다. 그런데 슬롯이 "나는 아직 여기까지밖에 못 읽었다"고 잡고 있으면, 그 지점 이후의 WAL은 전부 보존 대상이 된다.

슬롯의 양면성 — 한 문장이 두 얼굴을 갖는다

보장 측면

"안 읽은 WAL은 안 지운다" → 커넥터가 죽어도 데이터는 기다린다 → 유실 없음

위험 측면

"안 읽은 WAL은 안 지운다" → 커넥터가 안 살아나면 영원히 안 지운다 → 디스크 소진 → DB 정지

같은 문장이다. 앞부분만 말하면 "CDC 좋네요"로 끝나고, 뒷부분까지 말하면 "이 사람은 운영해 봤구나"가 된다.

6-2. 슬롯 상태 감시 — 운영에서 반드시 봐야 할 뷰

감시 pg_replication_slots — CDC를 도입했다면 이 쿼리에 알람을 건다
SELECT slot_name,
       active,        -- false면 커넥터가 지금 붙어 있지 않다는 뜻
       wal_status,    -- reserved / extended / unreserved / lost
       pg_size_pretty(
           pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)
       ) AS unconsumed_wal   -- 슬롯이 아직 소비하지 못하고 붙잡고 있는 WAL의 양
  FROM pg_replication_slots;
confirmed_flush_lsn
구독자가 여기까지 확실히 받았다고 확인해 준 지점. 이 지점 이전의 WAL만 삭제 가능해진다.
pg_current_wal_lsn()
서버가 지금 WAL을 쓰고 있는 지점.
두 값의 차이
슬롯 지연(lag). 이 값이 계속 커지면 곧 디스크가 찬다는 신호다.
active = false
커넥터가 붙어 있지 않다. 이 상태가 지속되면 그것만으로 즉시 알람 대상.
wal_status = lost
상한을 넘겨 슬롯이 무효화된 상태. 그 슬롯은 더 이상 쓸 수 없다(11절).
LSN이 뭔가요 LSN(Log Sequence Number)은 WAL 안의 위치를 가리키는 좌표다. "파일 몇 번의 몇 바이트째"를 하나의 단조 증가하는 값으로 표현한 것이라고 보면 된다. Debezium이 저장하는 오프셋도 이 LSN이고, 8절에서 중복 발행이 생기는 이유가 바로 이 LSN 저장 시점 문제다.

7. Debezium 설정과 Outbox Event Router

이제 조각을 맞춘다. pgoutput을 쓰려면 퍼블리케이션(publication) — 어떤 테이블의 변경을 논리 복제 스트림에 실을지 정하는 정의 — 이 필요하다.

-- outbox 테이블의 변경만 스트림에 싣는다
CREATE PUBLICATION outbox_pub FOR TABLE outbox;
connector Debezium PostgreSQL 커넥터 설정 — 한 줄 한 줄이 앞 절의 개념과 대응한다
connector.class=io.debezium.connector.postgresql.PostgresConnector
plugin.name=pgoutput                     # PostgreSQL 10+ 내장 출력 플러그인 (5절)
slot.name=outbox_slot                    # 커넥터 전용 복제 슬롯 이름 (6절)
publication.name=outbox_pub
table.include.list=public.outbox         # outbox 테이블만 캡처한다
skipped.operations=u,d                   # outbox는 INSERT만 의미가 있다. UPDATE/DELETE는 무시
heartbeat.interval.ms=10000              # 슬롯 위치를 주기적으로 전진시킨다저트래픽 함정 방지

transforms=outbox
transforms.outbox.type=io.debezium.transforms.outbox.EventRouter
부수 효과 하나 — REPLICA IDENTITY를 안 건드려도 된다 skipped.operations로 DELETE를 무시하므로 outbox 테이블의 REPLICA IDENTITY(DELETE·UPDATE 시 어떤 옛 값을 WAL에 실을지 정하는 설정)를 건드릴 필요가 없다. 기본값인 기본 키 기준으로 충분하다. 일반 테이블을 CDC할 때는 이 설정 때문에 골치를 앓는데, outbox 패턴은 INSERT만 쓰므로 그 문제를 통째로 피해 간다 — outbox를 CDC 대상으로 삼는 숨은 장점이다.

7-1. Outbox Event Router — 테이블 변경을 "이벤트"로 바꾸는 조각

Debezium이 기본으로 내보내는 것은 "outbox 테이블의 행이 이렇게 바뀌었다"는 테이블 변경 메시지다. before/after/source/op 같은 CDC 고유의 봉투에 싸여 나온다. 그대로 쓰면 컨슈머가 CDC 내부 포맷에 결합된다.

Debezium의 outbox event router를 걸면 이 봉투를 벗겨 준다. Kafka Connect에서 메시지를 중간에 변형하는 장치를 SMT(Single Message Transform)라고 부르는데, 그중 하나다.

라우터가 하는 일 3줄 — 이 순서대로 말한다

  • outbox 행의 payload 컬럼만 꺼내 이벤트 본문으로 만들고,
  • aggregate_type으로 목적지 토픽을 라우팅하고 (예: ORDER → order-events),
  • aggregate_id를 메시지 키로 실어 파티션 키가 되게 한다.

결과적으로 컨슈머는 CDC의 존재를 모른 채 평범한 도메인 이벤트를 받는다. 세 번째 줄은 특히 중요하다 — 순서 보장 사슬의 마지막 고리가 여기서 걸린다(9절).

7-2. CDC의 성질과 대가 — 한 관점으로 전부 유도된다

DB 입장에서 Debezium은 복제 클라이언트 하나가 더 붙은 것과 같다. 스탠바이 서버가 WAL을 받아 자기 데이터를 갱신하듯, Debezium은 WAL을 받아 Kafka로 흘린다. 이 관점이 서면 CDC의 성질이 자연스럽게 따라온다.

유실 없음

커밋이 WAL에 기록되는 것 자체가 PostgreSQL 내구성의 일부다. WAL에 남았고 슬롯이 그 지점을 붙잡고 있는 이상, 커넥터는 (지금이든 재시작 후든) 반드시 읽는다.

DB 부하·지연 최소

폴링처럼 주기적 SELECT가 없다. WAL 읽기는 순차 접근이라 부담이 적고, 커밋→발행 지연이 폴링 주기가 아니라 로그 전파 속도(보통 밀리초 단위)로 줄어든다.

릴레이 코드 소멸

스케줄러, FOR UPDATE SKIP LOCKED, 발행 마킹 코드가 전부 인프라(커넥터)로 이동한다. 애플리케이션은 outbox INSERT만 안다.

대가는 운영 부담이다 — 이 문장을 빼먹지 않는다 Kafka Connect 클러스터와 Debezium 커넥터라는 새 구성요소의 배포·모니터링·장애 대응이 생기고, 여기에 PostgreSQL 쪽의 wal_level 변경(서버 재시작 필요)과 복제 슬롯 감시라는 DB 운영 책임까지 추가된다. 이벤트가 적고 몇 초 지연이 허용되면 폴링으로 시작하고, 규모가 커지면 CDC로 진화시키는 경로가 일반적이다.

8. 발행 보장 체인 — 어디까지가 보장이고 어디부터가 내 몫인가

"Outbox + CDC를 쓰면 끝"이 아니다. 메시지가 지나는 구간마다 보장 수단이 다르다는 것을 체인으로 설명할 수 있어야 한다.

구간별 보장 수단 — 면접에서 이 표를 머릿속에서 읽어 내려가면 된다
구간유실 방지 수단중복 발생 지점
앱 → DB(outbox)로컬 트랜잭션 원자성없음 (롤백되면 이벤트도 없음)
DB → DebeziumWAL 내구성 + 복제 슬롯이 미확인 WAL을 보존커넥터 재시작 시 재발행
Debezium → KafkaConnect 내부 프로듀서 acks=allack 유실 시 재전송
Kafka → 컨슈머처리 후 오프셋 커밋커밋 전 리밸런싱/장애 시 재처리

8-1. 두 번째 줄을 정확히 이해해야 한다

Debezium은 "WAL의 어디까지 읽어 Kafka에 넘겼는지"를 LSN으로 저장하는데, Kafka로의 발행과 이 오프셋 저장이 원자적이지 않다. 발행은 했는데 오프셋 저장 전에 커넥터가 죽으면, 재시작 후 같은 구간을 다시 읽어 같은 이벤트가 한 번 더 발행된다.

이 한 줄이 대부분의 오답을 만든다

Outbox + CDC의 보장은 exactly-once가 아니라 at-least-once

"CDC를 쓰면 정확히 한 번 발행됩니다"는 틀린 답이다. 그리고 이것은 Debezium의 결함이 아니라 분산 시스템의 일반적 한계다 — 두 시스템에 걸친 "발행"과 "발행 기록"을 원자적으로 묶을 방법이 없다는 점에서, 1절의 이중 쓰기 문제가 한 층 위에서 다시 나타난 것이다.

8-2. 그래서 결론은 언제나 같다 — 멱등 컨슈머

필수 outbox 이벤트 ID 기반 멱등 처리 — CDC를 써도 이건 생략 불가
@KafkaListener(topics = "order-events")
@Transactional
public void consume(OutboxMessage msg) {
    if (!processedEventRepository.tryInsert(msg.eventId())) return; // 중복 스킵
    settlementService.settle(msg.payload());
    // 처리 이력 INSERT와 비즈니스 처리를 같은 TX로 -> 소비 측 원자성
}

여기서 msg.eventId()가 무엇인지가 깔끔하다. outbox 테이블의 id(bigserial PK)가 그대로 이벤트 고유 ID가 된다. 발행 경로와 멱등 키 체계가 한 번에 정리되는 조합이다.

역할 분담 — 이 한 줄까지 말해야 답변이 완결된다

생산 측 (Outbox + CDC)

유실 방지 — "커밋된 것은 반드시 나간다"를 책임진다. 중복은 못 막는다.

소비 측 (멱등 컨슈머)

중복 제거 — "여러 번 와도 결과는 한 번"을 책임진다. 유실은 못 막는다.

한쪽만으로는 절대 완성되지 않는다

9. 순서 — 커밋 순서가 파티션 순서가 되는 4겹 사슬

폴링 릴레이를 멀티 인스턴스로 띄우면 같은 aggregate의 이벤트를 서로 다른 인스턴스가 집어 발행 순서가 흔들릴 수 있었다. SKIP LOCKED로 서로 다른 행을 집게 만들어도, 먼저 집은 쪽이 늦게 발행하면 순서가 뒤집힌다.

9-1. 사슬 4개 고리 — 하나라도 끊기면 순서가 깨진다

사슬 암기 — 4단계를 이 문장으로 외운다

DB 커밋 순서
   → (논리적 디코딩) 커밋 순서 그대로의 단일 스트림
   → (커넥터 태스크 1개) 순차 발행
   → (aggregate_id 메시지 키) 같은 주문은 같은 파티션
   → (Kafka 파티션 내 순서 보장) 컨슈머가 커밋 순서대로 받는다

"DB가 정한 순서를 → 스트림이 유지하고 → 단일 태스크가 유지하고 → 키가 같은 파티션에 묶고 → Kafka가 지킨다." 다섯 마디로 줄여서 외우면 면접에서 통째로 나온다.

10. outbox 테이블 정리 — 비워도 되지만, VACUUM을 생각해야 한다

폴링 방식은 발행 여부를 published_at 같은 컬럼으로 마킹하고 발행 완료된 행을 주기적으로 지워야 했다. 릴레이가 테이블을 읽어야 하니 행이 남아 있어야 하기 때문이다.

CDC는 다르다. 커넥터는 테이블이 아니라 WAL에서 읽으므로, 테이블에 행이 남아 있을 필요가 없다.

가산점 INSERT 직후 같은 트랜잭션에서 DELETE — 그래도 이벤트는 정상 발행된다
@Transactional
public void completeOrder(Long id) {
    order.complete();
    Outbox row = outboxRepository.save(Outbox.of("ORDER", ...));
    outboxRepository.delete(row);   // 같은 트랜잭션에서 바로 지운다
    // INSERT 기록은 이미 WAL에 남았으므로 이벤트는 정상 발행된다.
    // 커넥터는 skipped.operations=d 설정으로 DELETE를 무시한다.
}

10-1. PostgreSQL에서는 DELETE가 즉시 지우는 게 아니다

PostgreSQL은 MVCC(다중 버전 동시성 제어)로 동작하기 때문에, DELETE는 행을 즉시 지우지 않는다. "이 행 버전은 죽었다"고 표시할 뿐이고, 실제 공간 회수는 VACUUM(보통 백그라운드의 autovacuum)이 나중에 돌면서 한다.

대응 A — 테이블 단위 autovacuum 조정

ALTER TABLE outbox SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_vacuum_threshold    = 100
);
  • 이 테이블만 훨씬 자주 청소하게 만든다
  • 설정 두 줄로 끝나 도입이 가볍다
  • 트래픽이 더 커지면 또 따라잡지 못할 수 있다

대응 B — 즉시 DELETE 대신 짧은 보존 + 파티션 드롭

-- created_at 기준 레인지 파티셔닝
DROP TABLE outbox_2026_08_29;  -- 통째로
  • 죽은 튜플도 VACUUM 부담도 없다
  • 며칠치 이벤트 원장이 남는다 → 11절 복구용
  • 파티션 관리라는 운영 작업이 생긴다

이 절의 인출 문장

"CDC를 쓰면 outbox를 비워도 된다" + "그래도 PostgreSQL에서는 죽은 튜플이 남는다"

두 문장을 함께 말할 수 있으면 DB 운영까지 아는 사람으로 읽힌다. 앞 문장만 말하면 "그럼 테이블 크기는 왜 계속 늘어나죠?"라는 되물음에 막힌다.

11. 최악 시나리오 — 슬롯이 DB를 멈춘다 시니어 변별

여기가 PostgreSQL CDC 운영의 급소다. 그리고 MySQL을 쓰던 사람이 가장 크게 헷갈리는 지점이기도 하다 — 문제의 방향이 정반대이기 때문이다.

11-1. 인과 6단계 — 이걸 말할 수 있느냐가 이 질문의 핵심이다

11-2. 대응은 세 단계다

1

예방 — 슬롯 지연 감시가 최우선이다

pg_replication_slots에서 active와 미소비량을 주기적으로 확인하고 알람을 건다.

SELECT slot_name, active, wal_status,
       pg_size_pretty(
           pg_wal_lsn_diff(pg_current_wal_lsn(), confirmed_flush_lsn)
       ) AS unconsumed_wal
  FROM pg_replication_slots;
  • active = false가 지속 → 커넥터가 안 붙어 있다
  • 미소비량이 우상향 → 디스크가 차고 있다
  • 여기에 더해 하트비트 설정으로 "트래픽이 없어서 슬롯이 안 움직이는" 함정도 함께 막는다(11-3)
2

상한 — max_slot_wal_keep_size로 안전장치를 건다

PostgreSQL 13부터 있는 설정으로, 슬롯이 붙잡을 수 있는 WAL 양의 상한이다. 기본값은 -1(무제한)이라 아무것도 안 걸려 있다.

max_slot_wal_keep_size = 100GB

이 값을 넘어서면 PostgreSQL은 슬롯을 지키는 대신 WAL을 지우고 그 슬롯을 무효화(invalidate)한다. pg_replication_slots.wal_status가 lost로 바뀌고, 그 슬롯은 더 이상 쓸 수 없다.

3

트레이드오프를 정확히 말한다

상한을 걸지 않으면 커넥터 장애가 DB 전면 장애로 번지고, 상한을 걸면 그 한도를 넘긴 순간 슬롯이 죽어 그 구간 이벤트의 연속성이 끊긴다.

DB 전체를 지킬 것인가, 이벤트 스트림의 연속성을 지킬 것인가

11-3. 낮은 트래픽 테이블의 함정 — 하트비트

슬롯의 confirmed_flush_lsn은 커넥터가 자기가 관심 있는 변경을 받아 처리했을 때 전진한다. 그런데 outbox 테이블에는 하루 종일 아무 변경이 없고 다른 테이블에만 대량 쓰기가 일어나는 상황을 생각해 보자.

11-4. 슬롯이 무효화됐다면 — 복구 경로

커넥터를 새 슬롯으로 다시 시작하면 Debezium은 초기 스냅샷을 다시 뜬다 — 대상 테이블의 현재 내용 전체를 읽어 이벤트로 내보내는 동작이다. 그런데 여기서 10절의 선택이 결과를 가른다.

이 절 전체를 한 문장으로

보장의 전제 조건이 무엇이고, 그 전제가 깨졌을 때 무슨 일이 벌어지며,
어느 쪽 손실을 택할 것인지까지 말하는 것이 시니어 답변이다
  • 전제: 복제 슬롯이 미확인 WAL을 붙잡아 준다
  • 깨졌을 때: 커넥터가 오래 죽으면 WAL이 디스크를 채우고 DB 전체가 멈춘다
  • 선택: max_slot_wal_keep_size로 DB를 지키고 이벤트 연속성을 내준다 — 그리고 그 한계에 닿기 전에 알람으로 개입한다

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 챙겨야 할 운영 포인트 4가지

커넥터 생존 모니터링
커넥터가 죽으면 발행이 조용히 멈춘다 — 애플리케이션 로그에는 아무 에러도 안 나오는 장애다. Kafka Connect의 태스크 상태(RUNNING / FAILED)와 슬롯 지연에 알람을 건다. 특히 pg_replication_slots.active가 false인 상태가 지속되면 그것만으로도 즉시 알람 대상이다.
슬롯 지연 감시 (최우선)
이유가 둘이다. ① 지연이 커진다는 것은 발행이 밀리고 있다는 뜻이다. ② 더 중요한 이유 — 그 지연이 곧 DB 서버 디스크를 갉아먹고 있다는 뜻이다(11절). 두 번째 이유를 말하는 것이 핵심이다.
하트비트 설정
outbox에 트래픽이 없고 다른 테이블에만 쓰기가 몰리는 상황에서 슬롯이 전진하지 않는 함정을 막는다. heartbeat.interval.ms를 켜 둔다. 알람이 안 울리는 유형의 사고라 예방 설정이 유일한 방어다.
스키마 변경 주의
outbox 테이블의 컬럼 구조는 커넥터 설정(event router가 읽는 컬럼 이름)과 결합돼 있다. 이벤트 본문 자체는 payload jsonb 안에서 버전 필드를 두고 진화시키고, 테이블 DDL은 커넥터 영향 검토 후 진행한다.

12-2. 인출 카드 — 답을 가리고 스스로 말해 본다

Q. 이중 쓰기 문제란?
DB와 Kafka는 서로 다른 시스템이라 두 쓰기를 묶어 줄 공통 트랜잭션이 없다. 커밋→발행은 유실, 발행→커밋은 거짓 이벤트. 순서로는 못 푼다.
Q. Outbox의 발상 전환 한 줄은?
두 시스템을 묶을 방법을 찾는 대신, 메시지를 DB에 씀으로써 묶어야 할 두 시스템을 하나로 만든다.
Q. CDC 부품 3종과 역할은?
WAL(변경의 원본 기록) · 논리적 디코딩(물리→행 단위 변환, wal_level=logical) · 복제 슬롯(읽은 위치 기억 + WAL 보존 강제).
Q. 왜 WAL을 그대로 못 읽나?
WAL은 물리적 블록 변경 기록이라 "어떤 테이블의 어떤 행이 어떻게 바뀌었는지" 알 수 없다. 논리적 디코딩이 시스템 카탈로그와 대조해 풀어 준다.
Q. 논리적 디코딩의 두 성질은?
① 커밋된 것만 나온다(롤백은 스트림에 없음 → 거짓 이벤트 불가). ② 커밋 순서대로 나온다(순서 사슬 1번 고리).
Q. 복제 슬롯의 한 문장 성질은?
"슬롯이 존재하는 한 아직 확인 안 한 WAL을 절대 지우지 않는다." 유실 방지의 근거이자 디스크 소진의 원인이다.
Q. 전 구간 보장 수준은?
at-least-once. 커넥터가 발행과 LSN 오프셋 저장을 원자적으로 못 해서 재시작 시 재발행이 생긴다. 중복 제거는 소비 측.
Q. 멱등 키는 무엇으로 쓰나?
outbox 테이블의 id(bigserial PK). 재발행돼도 같은 값이라, 처리 이력 테이블의 유니크 제약 한 줄로 흡수된다.
Q. 순서 보장 4겹 사슬은?
커밋 순서 → 논리적 디코딩 단일 스트림 → 커넥터 태스크 1개 → aggregate_id 메시지 키 → 파티션 내 순서 보장.
Q. 가장 잘 끊기는 고리는?
메시지 키(3번). 안 실으면 라운드로빈으로 파티션이 흩어져 앞의 두 고리가 무의미해진다.
Q. outbox를 비워도 되는 이유와 단서는?
커넥터는 테이블이 아니라 WAL에서 읽으므로 비워도 된다. 단 MVCC라 죽은 튜플이 남아 autovacuum 조정이나 파티션 드롭이 필요하다.
Q. 커넥터가 며칠 죽으면?
MySQL은 데이터가 사라져서 문제, PostgreSQL은 안 지워져서 문제. WAL이 쌓여 디스크가 차면 DB 전체가 멈춘다.
Q. 그 최악을 막는 설정은?
max_slot_wal_keep_size(기본 -1 무제한). 상한을 넘으면 슬롯이 lost로 무효화된다 — DB를 지키고 이벤트 연속성을 내주는 맞바꿈.
Q. 감시 알람 3종은?
① Connect 태스크 FAILED ② pg_replication_slots.active = false 지속 ③ 미소비 WAL 우상향. 여기에 하트비트로 저트래픽 함정까지.

12-3. 꼬리질문 셀프 테스트 — 질문을 보고 먼저 소리 내어 답한 뒤 펼친다

폴링 릴레이 대신 CDC를 선택하는 기준은 무엇입니까?힌트: 축은 셋인데, 세 번째가 실무의 기준이다

트레이드오프 축은 셋이다 — 지연, DB 부하, 운영 복잡도.

  • 폴링은 스케줄러와 DB만으로 끝나 도입이 쉽지만, 발행이 폴링 주기만큼 지연되고 주기적 SELECT가 DB를 계속 때린다. 이벤트가 없어도 조회는 계속 돌아간다.
  • CDC는 지연이 밀리초급이고 DB 부하가 거의 없지만, Kafka Connect + Debezium이라는 인프라 운영이 새로 생긴다. PostgreSQL이라면 여기에 wal_level=logical로 인한 WAL 볼륨 증가와 복제 슬롯 감시 책임까지 얹힌다.

이벤트 빈도가 낮고 몇 초 지연이 허용되면 폴링, 이벤트가 많고 지연 요구가 빡빡하며 커넥터를 운영할 역량(모니터링 체계 포함)이 있으면 CDC다.

"우리 팀이 그 인프라를 감시하고 복구할 수 있는가"까지 판단 기준에 넣는 것이 실무적인 답이다. 감시하지 못할 CDC는 폴링보다 위험하다 — 조용히 멈추고, 멈춘 채로 DB 디스크를 채우기 때문이다.

Debezium이 재시작하면 이벤트가 중복 발행되지 않나요?힌트: 된다. 문제는 그 다음에 무엇을 말하느냐다

된다 — 그리고 그게 정상 동작이다.

커넥터는 Kafka로의 발행과 자신의 LSN 오프셋 저장을 원자적으로 할 수 없으므로, 발행 후 오프셋 저장 전에 죽으면 재시작 시 같은 구간을 다시 읽어 재발행한다. Outbox + CDC의 보장은 exactly-once가 아니라 at-least-once이고, 중복 제거는 소비 측 몫이다.

구체적으로는 outbox 행의 PK를 이벤트 고유 ID로 삼아, 컨슈머가 처리 이력 테이블에 유니크 제약으로 ON CONFLICT DO NOTHING INSERT를 시도하고 0행이면 스킵하는 멱등 컨슈머를 세트로 구현한다.

한 가지 덧붙이면 좋다. CDC가 exactly-once를 못 만든다는 것은 결함이 아니라 분산 시스템의 일반적 한계다. 두 시스템에 걸친 "발행"과 "발행 기록"을 원자적으로 묶을 방법이 없다는 점에서, 이건 1절의 이중 쓰기 문제가 한 층 위에서 다시 나타난 것이다.

이벤트 순서는 어떻게 보장되나요? 폴링 릴레이와의 차이는?힌트: 고리 4개를 끝까지 이어 본다

논리적 디코딩이 커밋된 트랜잭션만 커밋 순서대로 단일 스트림으로 내보내고, 복제 슬롯 하나는 연결 하나만 소비할 수 있어 커넥터 태스크가 하나로 강제되므로, 발행 순서가 커밋 순서와 일치한다. 여기에 outbox router가 aggregate_id를 메시지 키로 실으면 같은 aggregate의 이벤트가 같은 파티션에 순서대로 쌓인다.

폴링 릴레이는 멀티 인스턴스일 때 같은 aggregate의 이벤트를 다른 인스턴스가 나눠 집으면 발행 순서가 흔들릴 수 있어, FOR UPDATE SKIP LOCKED나 단일 릴레이 같은 추가 장치가 필요했다.

CDC는 이 문제를 설정이 아니라 구조로 없앤다. 다만 마지막 고리(메시지 키)는 여전히 내가 챙겨야 한다 — 라우터를 안 걸거나 aggregate_id가 비면 앞의 세 고리를 잘 지켜도 파티션이 흩어져 순서가 깨진다.

커넥터가 며칠 죽어 있으면 어떻게 되나요? WAL이 계속 쌓이는 건 아닌가요?힌트: MySQL을 떠올리면 방향을 반대로 틀린다 시니어 변별

여기가 PostgreSQL CDC 운영의 급소다. 그리고 MySQL을 쓰던 사람이 가장 크게 헷갈리는 지점이기도 하다 — 문제의 방향이 정반대이기 때문이다.

  • MySQL이라면 "데이터가 사라지는" 문제다. binlog는 보존 기간이 지나면 서버가 알아서 지운다. 커넥터가 보존 기간보다 오래 죽어 있으면 읽을 로그가 없어져 그 구간의 이벤트는 CDC 경로로 복구 불가다.
  • PostgreSQL은 정반대로 "지워지지 않아서" 문제가 된다. 복제 슬롯이 아직 안 읽은 WAL을 붙잡고 있으면 PostgreSQL은 그것을 절대 지우지 않는다. 커넥터가 죽어 있는 동안 데이터는 안전하게 보존되지만, 그 대가로 WAL이 무한정 쌓인다.

그리고 WAL은 pg_wal 디렉터리, 즉 DB 서버의 데이터 디스크에 쌓인다.

커넥터 다운
   → 슬롯의 confirmed_flush_lsn이 멈춘다
   → 그 지점 이후의 WAL이 삭제 대상에서 제외된다
   → pg_wal 디렉터리가 계속 커진다
   → 디스크가 가득 찬다
   → PostgreSQL은 WAL을 더 쓸 수 없으면 쓰기를 중단한다
   → ★ DB 전체가 멈춘다

이벤트 파이프라인 하나가 죽었을 뿐인데 서비스 전체 장애가 된다. 이 인과를 말할 수 있느냐가 이 질문의 핵심이다.

여기에 하나를 더 얹으면 이해가 완성된다. WAL은 데이터베이스 클러스터 전체가 공유한다. outbox 테이블에 트래픽이 하나도 없어도 다른 테이블의 쓰기가 WAL을 채운다. 즉 슬롯이 붙잡는 양은 outbox 트래픽이 아니라 DB 전체 쓰기량에 비례한다 — 하루 50GB의 WAL을 만드는 DB에서 커넥터가 3일 죽어 있으면 150GB가 붙잡히는 식이다.

대응은 세 단계다. ① 예방 — pg_replication_slots의 active와 미소비량에 알람. ② 상한 — max_slot_wal_keep_size(PostgreSQL 13+, 기본 -1 무제한)로 안전장치. ③ 트레이드오프 명시 — 상한을 안 걸면 커넥터 장애가 DB 전면 장애로 번지고, 걸면 넘긴 순간 슬롯이 lost가 되어 이벤트 연속성이 끊긴다. 대부분의 팀은 상한을 거는 쪽을 택한다 — DB가 멈추면 이벤트고 뭐고 없기 때문이다.

그냥 Kafka 트랜잭션(transactional producer)으로 DB 커밋과 묶으면 안 되나요?힌트: 그 트랜잭션의 경계가 어디까지인지 되짚는다

Kafka 트랜잭션은 "여러 파티션·토픽에 걸친 발행 + 컨슈머 오프셋 커밋"을 원자적으로 묶는 기능, 즉 Kafka 세계 안의 원자성이다.

외부 DB의 트랜잭션과는 묶이지 않으므로 이중 쓰기 문제를 못 푼다. "Kafka 트랜잭션을 커밋했는데 DB 커밋이 롤백되는" 조합은 여전히 가능하다.

DB와 브로커를 아우르는 분산 트랜잭션(2PC, 2단계 커밋)이 이론적 대안이지만, Kafka는 XA(분산 트랜잭션 표준 인터페이스)를 지원하지 않고, 지원한다 해도 참여자가 잠금을 쥔 채 코디네이터를 기다리는 블로킹 구조라 가용성·성능 비용이 크다.

그래서 실무 표준은 원자성을 로컬 트랜잭션 하나로 모으는 Outbox다. "두 시스템을 묶을 방법을 찾는" 대신 "묶어야 할 두 시스템을 하나로 만드는" 발상의 전환이 이 패턴의 본질이다.

outbox 행을 같은 트랜잭션에서 바로 DELETE해도 이벤트가 발행되나요? 부작용은요?힌트: 발행의 근거가 어디에 있는지 + MVCC 가산점

발행된다. 커넥터는 테이블이 아니라 WAL에서 읽기 때문이다. INSERT와 DELETE를 같은 트랜잭션에서 해도 INSERT의 WAL 기록은 이미 쓰였으므로 이벤트는 정상적으로 나가고, 커넥터는 skipped.operations=d로 DELETE를 무시한다. 결과적으로 테이블은 논리적으로 항상 비어 있게 되어 폴링 방식의 고질병인 outbox 테이블 비대화가 사라진다.

다만 PostgreSQL에서는 여기에 한 가지를 더 얹어야 한다. PostgreSQL은 MVCC로 동작하므로 DELETE는 행을 즉시 지우지 않는다. "이 행 버전은 죽었다"고 표시할 뿐이고, 실제 공간 회수는 VACUUM(보통 autovacuum)이 나중에 한다.

논리적으로:  SELECT count(*) FROM outbox;  →  0

물리적으로:  테이블 파일에는 죽은 튜플(dead tuple)이 계속 쌓인다.
             인덱스에도 그 튜플들을 가리키는 항목이 남는다.
             autovacuum이 따라잡지 못하면 → 테이블·인덱스 비대화(bloat)

초당 수백 건의 INSERT + DELETE가 일어나는 outbox 테이블은 기본 설정으로는 버거울 수 있다. 대응은 둘 — ① 테이블 단위로 autovacuum을 공격적으로 조정(autovacuum_vacuum_scale_factor 등을 이 테이블만 낮춘다), ② 즉시 DELETE 대신 짧은 보존 + 파티션 드롭(created_at 레인지 파티셔닝 후 오래된 파티션을 DROP TABLE — 파일이 통째로 사라지므로 죽은 튜플도 VACUUM 부담도 없다).

wal_level=logical로 바꾸는 데 드는 비용은 무엇입니까?힌트: 설정 한 줄이지만 공짜가 아니다 — 그리고 11절과 곱해진다

세 가지를 말한다.

  • 서버 재시작이 필요하다. 운영 중인 DB라면 점검 시간 확보가 전제다. "설정 한 줄"이라고 가볍게 말하면 안 되는 이유다.
  • WAL 볼륨이 늘어난다. PostgreSQL이 논리적 디코딩에 필요한 추가 정보를 WAL에 더 실어 쓰기 때문이다. 같은 트래픽이어도 하루에 생성되는 WAL의 양이 커지고, WAL 아카이브·백업 용량도 함께 늘어난다.
  • 그리고 이 증가가 11절의 문제와 곱해진다. 슬롯이 붙잡는 양은 "DB 전체 쓰기량 × 커넥터가 죽어 있던 시간"인데, logical로 올리면 그 곱셈의 앞항이 커진다. 즉 디스크가 차는 속도가 더 빨라진다.

그래서 도입 전에 "현재 하루 WAL 생성량이 얼마이고, 디스크 여유가 며칠치인가"를 재 보는 것이 순서다. 이 숫자가 있어야 max_slot_wal_keep_size를 근거 있게 정할 수 있다.

outbox 테이블에는 하루 종일 이벤트가 거의 없는데 DB 디스크가 계속 차고 있습니다. 커넥터는 RUNNING입니다. 원인은?힌트: 슬롯 위치는 무엇을 처리했을 때 전진하는가 시니어 변별

하트비트를 안 켠 저트래픽 함정이다.

슬롯의 confirmed_flush_lsn은 커넥터가 자기가 관심 있는 변경을 받아 처리했을 때 전진한다. 그런데 table.include.list가 public.outbox 하나뿐이고 그 테이블에 변경이 없으면, 커넥터에게 넘길 것이 없으니 슬롯 위치가 그대로다.

문제는 WAL은 데이터베이스 클러스터 전체가 공유한다는 점이다. 다른 테이블의 대량 쓰기로 WAL은 계속 쌓이는데, 슬롯이 옛 위치를 붙잡고 있으니 그 WAL이 전부 삭제 대상에서 제외된다. 아무 문제가 없어 보이는데 디스크만 차는 상황이다.

이 사고가 특히 위험한 이유 커넥터는 RUNNING이고, 컨슈머 랙도 0이고, 애플리케이션 에러도 없다. 일반적인 알람은 하나도 울리지 않는다. 오직 pg_replication_slots의 미소비 WAL 지표만이 이상을 보여 준다.

해결은 Debezium의 heartbeat.interval.ms를 켜는 것이다. 커넥터가 주기적으로 하트비트를 주고받으며 슬롯 위치를 전진시켜 이 함정을 막는다. "관심 있는 변경이 없어도 여기까지 읽었다"고 말해 주는 장치라고 설명하면 정확하다. 저트래픽 outbox를 CDC로 잡을 때는 선택이 아니라 필수 설정으로 취급한다.

Outbox Event Router(SMT)를 안 쓰고 Debezium 기본 메시지를 그대로 쓰면 안 되나요?힌트: 세 가지가 동시에 나빠진다 — 그중 하나는 순서다

동작은 한다. 하지만 세 가지가 동시에 나빠진다.

  • 컨슈머가 CDC 포맷에 결합된다. before/after/source/op라는 CDC 고유의 봉투를 컨슈머가 벗겨야 한다. 나중에 폴링 릴레이로 되돌리면 컨슈머를 전부 고쳐야 한다 — 인프라 선택이 소비자 계약으로 새어나간 것이다.
  • 토픽이 테이블 단위로 묶인다. 기본 토픽 이름은 <서버>.<스키마>.<테이블> 형태라 모든 도메인 이벤트가 outbox 토픽 하나에 섞인다. 컨슈머가 event_type으로 필터링하며 관심 없는 메시지까지 전부 읽게 된다.
  • 순서 보장이 깨진다. 이게 가장 실질적인 피해다. 라우터가 없으면 메시지 키가 outbox 테이블의 PK가 되는데, PK는 행마다 다르므로 같은 주문의 이벤트가 서로 다른 파티션으로 흩어진다. 9절 사슬의 3번 고리가 끊긴다.

즉 라우터는 편의 기능이 아니라 설계의 일부다. 특히 세 번째 이유를 말할 수 있으면 "순서 보장 사슬을 실제로 이해했다"는 신호가 된다.

슬롯이 lost가 됐습니다. 복구 절차는 어떻게 됩니까?힌트: 초기 스냅샷이 무엇을 읽는지 생각해 본다

슬롯은 되살릴 수 없으므로 커넥터를 새 슬롯으로 다시 시작한다. 그러면 Debezium은 초기 스냅샷을 다시 뜬다 — 대상 테이블의 현재 내용 전체를 읽어 이벤트로 내보내는 동작이다.

그런데 여기서 10절의 선택이 결과를 가른다.

  • "INSERT 직후 DELETE" 전략이었다면 — 테이블이 비어 있으므로 스냅샷으로 복구할 것이 없다. 그 구간의 이벤트는 원본 도메인 테이블(orders 등)을 기준으로 재구성하는 별도 배치를 짜야 한다. 사고 당일에 이 배치를 처음 짜기 시작하면 복구가 몇 배로 길어진다.
  • "며칠치 보존 + 파티션 드롭" 전략이었다면 — outbox 테이블 자체가 복구용 원장 역할을 한다. 스냅샷이 실제로 데이터를 읽어 내보내므로 누락 구간을 outbox에서 그대로 재발행할 수 있다.

어느 쪽이든 재발행분은 컨슈머에게 중복으로 도착한다 — 그래서 여기서도 멱등 컨슈머가 복구를 가능하게 만드는 전제가 된다. 멱등하지 않으면 "복구하려다 이중 정산"이 난다.

복구 후에는 반드시 원인 제거까지 간다 — 알람 임계값을 max_slot_wal_keep_size보다 충분히 낮게 다시 잡고, 하트비트 설정을 점검하고, 커넥터 자동 재시작 정책을 확인한다.

Debezium PostgreSQL 커넥터는 왜 태스크를 하나만 씁니까? 처리량이 부족하면 어떻게 하나요?힌트: 제약의 출처는 커넥터가 아니라 PostgreSQL이다

제약의 출처는 Debezium이 아니라 PostgreSQL이다. 하나의 복제 슬롯은 하나의 연결만 소비할 수 있으므로, 커넥터가 스트림을 여러 태스크로 나눠 읽는 일이 애초에 불가능하다. 그 결과로 순차 읽기가 강제되고, 이것이 9절 순서 사슬의 2번 고리가 된다 — 제약이 곧 보장을 만드는 구조다.

처리량이 부족하다면 순서대로 검토한다.

  • 먼저 진짜 병목을 찾는다. 단일 태스크가 병목인 경우보다, Connect 워커의 자원 부족이나 프로듀서 배치 설정, 또는 다운스트림 컨슈머 랙이 원인인 경우가 흔하다.
  • outbox 행을 가볍게 만든다. payload가 크면 그만큼 WAL과 전송량이 커진다 — 큰 본문은 참조로 바꾸는 편이 낫다(claim check 계열 접근).
  • 도메인별로 커넥터를 분리한다. outbox 테이블을 도메인별로 나누고 각각 별도 퍼블리케이션·슬롯·커넥터를 둔다. 이러면 병렬도가 올라가지만 서로 다른 슬롯 사이의 순서는 보장되지 않고, 무엇보다 감시해야 할 슬롯이 늘어난다(11절 위험이 슬롯 개수만큼 늘어난다).

Kafka 이후의 병렬 처리는 이 제약과 무관하다는 점도 짚어 두면 좋다 — 발행은 단일 태스크여도 소비는 파티션 수만큼 병렬이다. 대부분의 시스템에서 outbox 발행이 병목이 되는 일은 드물다.

outbox 테이블 없이 orders 같은 도메인 테이블을 직접 CDC하면 안 되나요?힌트: 그때 Kafka로 나가는 것은 "이벤트"인가 "행 변경"인가 시니어 변별

기술적으로는 된다. 실제로 레거시 DB에서 데이터를 뽑아내는 용도로는 그렇게 쓴다. 하지만 도메인 이벤트를 발행하는 용도로는 네 가지가 문제가 된다.

  • 나가는 것이 "이벤트"가 아니라 "행 변경"이다. status가 PAID에서 SHIPPED로 바뀌었다는 사실은 알 수 있어도, 그것이 "정상 배송 시작"인지 "관리자 강제 조정"인지는 알 수 없다. 의도(intent)가 표현되지 않는다.
  • DB 스키마가 곧 공개 계약이 된다. 컬럼 이름을 바꾸거나 테이블을 정규화하면 모든 컨슈머가 깨진다. 리팩터링할 때마다 외부 계약 협상을 해야 하는 구조가 된다.
  • 여러 테이블에 걸친 하나의 비즈니스 이벤트를 조립할 수 없다. 주문·결제·배송지가 세 테이블이면 세 개의 행 변경 메시지가 따로 나간다. 컨슈머가 그것을 다시 조립해야 하고, 조립 시점의 정합성도 스스로 챙겨야 한다.
  • 운영 부담이 늘어난다. UPDATE·DELETE를 캡처해야 하므로 REPLICA IDENTITY를 조정해야 하고(옛 값을 WAL에 더 싣게 되어 WAL이 더 커진다), 대량 배치 UPDATE 한 번이 수백만 건의 이벤트 폭풍을 만든다.

outbox는 이 문제를 "무엇을 이벤트로 내보낼지 명시적으로 설계하게 만드는" 방식으로 푼다. 발행할 이벤트를 코드에서 의도적으로 쓴 것만 나가고, 테이블 구조를 바꿔도 payload만 그대로면 계약은 유지된다. "CDC를 쓰는 것"과 "테이블을 그대로 노출하는 것"은 다른 이야기라는 구분이 이 질문의 핵심이다.

RabbitMQ에서의 대응 Debezium CDC 같은 정석 경로가 없어 FOR UPDATE SKIP LOCKED 폴링 퍼블리셔 + publisher confirm 콜백이 실무 기본형이다. 20-rabbitmq-outbox-polling-publisher.md에서 다룬다. 브로커가 바뀌어도 "원자성을 로컬 트랜잭션 하나로 모은다"는 뼈대는 동일하고, 릴레이 구현만 달라진다는 점을 말하면 좋다.
한 줄 요약
커밋과 발행 사이의 틈은 코드로 못 막는다 — 이벤트를 같은 트랜잭션으로 outbox에 남기고, Debezium이 PostgreSQL의 WAL을 논리적 디코딩으로 풀어 복제 슬롯을 통해 읽어 Kafka로 흘리면 "WAL에 남은 커밋은 반드시 발행된다"가 성립하며, 남는 중복(at-least-once)은 outbox PK를 키로 한 멱등 컨슈머로, 순서는 논리적 디코딩의 커밋 순서 + aggregate ID 파티션 키로 지킨다 — 다만 그 보장을 떠받치는 복제 슬롯이 곧 최대 위험이므로, 슬롯 지연을 감시하고 max_slot_wal_keep_size로 상한을 걸어 "커넥터 장애가 DB 디스크를 채워 서비스 전체를 멈추는" 최악을 막는 것까지가 운영의 완성이다.
