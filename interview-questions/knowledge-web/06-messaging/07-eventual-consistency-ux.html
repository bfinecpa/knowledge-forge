최종 일관성과 UX — "결제했는데 왜 안 보여요"를 다루는 법
지연은 없앨 대상이 아니라, 사용자가 실패로 오인하지 않게 설계할 대상이다

면접 질문: "이벤트 기반 아키텍처에서 최종 일관성(eventual consistency)으로 인한 UX 문제를 어떻게 다루나요?"

핵심 관전 포인트 — 이벤트 기반 아키텍처에서 쓰기와 그 결과가 조회에 반영되는 시점 사이의 지연은 버그가 아니라 설계의 속성이다. 따라서 대응도 두 축으로 간다. 기술 축 — 사용자가 자기 행동의 결과는 즉시 보게 만드는 read-your-own-writes(응답에 결과 포함, 쓰기 경로 조회 라우팅, 버전 토큰)와, "처리중"이라는 정직한 중간 상태를 도메인과 화면에 도입하는 것. 제품 축 — "몇 초까지 허용 가능한가"를 기획과 협상해 SLA로 못 박고, 컨슈머 랙을 그 SLA 기준으로 모니터링하는 것. 그리고 돈·권한처럼 즉시성이 필수인 구간은 애초에 동기 범위에 남긴다.
  • 1
    전제부터 깐다 — 지연은 우리가 산 물건의 값이다. 서비스를 쪼개고 사이를 이벤트로 이어 가용성·처리량·낮은 결합을 샀고, 그 대가가 지연이다. 그래서 목표는 "지연 제거"가 아니라 "지연을 실패로 오인하지 않게 만들기"다.
  • 2
    기술 축은 둘. read-your-own-writes로 자기가 쓴 것은 자기에게 즉시 보이게 하고(보장 범위를 한 사람으로 좁히는 절충), RYOW로도 안 되는 구간은 PENDING이라는 정식 도메인 상태로 정직하게 표현한다. "처리중"은 프런트 문구가 아니라 enum 값이다.
  • 3
    제품 축이 시니어 변별점이다. "몇 초까지 늦어도 되는가"를 흐름별로 기획·CS와 합의하고, 그 숫자가 랙 알람 임계값 · RYOW TTL · PENDING 타임아웃 세 자리에 그대로 들어간다. 허용치를 정의한 적 없는 시스템은 지연이 장애인지조차 판단할 수 없다.

0. 질문 + 출제 의도

질문: "이벤트 기반 아키텍처에서 최종 일관성(eventual consistency)으로 인한 UX 문제를 어떻게 다루나요?"

출제 의도: "구매했는데 이용권이 아직 안 보여요"를 기술 문제이자 제품 문제로 다루는지 본다. 기획자와 "몇 초까지 허용 가능한가"를 협상하는 역할까지 백엔드의 일임을 아는 사람인지 — 즉 아키텍처 선택의 대가가 사용자 화면에 어떻게 나타나는지를 끝까지 추적하는 시야를 확인한다.

이 페이지가 겨냥하는 약점 세 가지 ① "최종 일관성 = 어쩔 수 없는 것"에서 멈추는 것 → 1·2절에서 지연이 어느 구간에 얼마씩 붙는지를 분해하고, 그것이 사용자의 어떤 행동으로 되돌아오는지까지 잇는다.
② "처리 중입니다라고 띄우면 되죠"로 답하는 것 → 5절에서 그것이 프런트엔드 문구 작업이 아니라 도메인 모델에 상태를 하나 추가하는 일임을 enum before/after로 못 박는다. 상태가 없으면 화면은 그것을 그릴 수 없다.
③ 기술 처방만 나열하고 끝내는 것 → 8·9절이 시니어 변별의 정중앙이다. 허용 지연은 협상해서 정하는 제품 값이고, 그 숫자가 알람 임계값과 코드 상수로 동시에 들어간다.

1. 지연은 버그가 아니라 청구서다

1-1. 용어부터 — "일관성"이 뜻하는 두 가지

이 문서의 모든 논의가 두 단어의 차이 위에 서 있다. 먼저 이것부터 정확히 갈라놓고 들어간다.

강한 일관성 (strong consistency)

"쓰기가 완료된 직후, 누가 어디서 읽어도 그 새 값이 보인다"

  • 단일 DB에 COMMIT하고 바로 SELECT하면 방금 쓴 값이 나온다
  • 우리가 익숙한 세계 — 그래서 이것을 기본값이라고 착각한다

최종 일관성 (eventual consistency)

"언젠가는 모든 읽기 경로가 같은 값으로 수렴한다"

  • eventual = 결국. 수렴은 약속하지만 언제 수렴하는지는 약속하지 않는다
  • 이름 자체가 시간 보장의 부재를 드러내고 있다

가장 먼저 잡아야 할 프레임 — 최종 일관성은 사고가 아니라 구매다

결제 서비스와 이용권 서비스를 분리하고 그 사이를 Kafka로 이었을 때, 우리는 세 가지를 샀다. 지연은 그 물건값이다.

산 것 ① 가용성
한쪽이 죽어도 다른 쪽은 산다
산 것 ② 처리량
각자 자기 속도로 처리한다
산 것 ③ 낮은 결합
서로의 API를 직접 부르지 않는다
낸 값 = 지연 — 그래서 "지연을 없애자"는 방향은 산 것을 도로 반납하자는 말이다
과제는 지연을 없애는 것이 아니라, 지연을 사용자가 「실패」로 오인하지 않게 만드는 것

1-2. 지연은 어디서 쌓이는가 — 네 구간으로 분해한다

"느리다"를 한 덩어리로 두면 손댈 곳이 안 보인다. 전형적인 흐름을 단계별로 펼치면 지연이 네 조각으로 나뉘어 붙어 있다는 것이 보이고, 그중 어느 한 칸만 폭발한다는 것도 보인다.

2. 사용자는 지연을 「실패」로 읽는다

사용자는 아키텍처를 모른다. Kafka도 컨슈머도 랙도 모른다. 사용자가 아는 것은 하나다 — "돈을 냈는데 화면에 아무것도 없다."

이 문서 전체를 관통하는 비유 — 주문은 받았는데 「조리 중」 표시가 없는 식당

주문서는 이미 주방으로 넘어갔다. 그런데 손님 테이블의 화면에는 아무것도 없다. 손님이 하는 행동은 정해져 있다 — 화면을 두드리고, 다시 주문하고, 직원을 부른다. 이 비유의 각 조각이 이 문서의 각 절에 그대로 대응한다.

결제는 성공했고 이벤트도 발행됐다. 실패한 게 아니라 진행 중이다.

3. RYOW — 보장 범위를 「한 사람」으로 좁힌 절충

3-1. 무엇을 보장하고, 무엇을 보장하지 않는가

read-your-own-writes(RYOW)는 "한 사용자가 방금 쓴 데이터는, 그 사용자 자신이 곧바로 읽었을 때 반드시 보인다"는 보장이다. 우리말로 옮기면 "자기가 쓴 것은 자기가 읽는다"다.

주의해서 볼 것은 보장하지 않는 것 쪽이다. 여기에 이 기법의 값어치 전부가 들어 있다.

보장한다

  • 내가 방금 산 이용권은 내 화면에 즉시 보인다
  • 내가 방금 쓴 리뷰는 내 목록에 즉시 보인다

보장하지 않는다

  • 그 값이 다른 사용자에게 언제 보이는지 — 전혀 약속하지 않는다
  • 옆 사람의 통계 대시보드에 30초 뒤 반영돼도 RYOW는 지켜진 것이다
RYOW = 최종 일관성 전체를 포기하지 않으면서, 사용자 한 명의 체감만 즉시 일관되게 만드는 절충

3-2. 왜 이 절충이 훨씬 싼가 — 숫자로 본다

강한 일관성과 나란히 놓으면 값 차이가 분명해진다. 강한 일관성을 만들려면 모든 조회 경로가 항상 최신을 봐야 한다. 실무에서 이 말은 둘 중 하나다 — 조회 모델(캐시, 읽기 전용 레플리카, CQRS read model)을 못 쓴다, 또는 쓰되 동기 복제로 묶어 쓰기 응답이 복제 완료까지 기다린다. 어느 쪽이든 조회 모델을 둔 이유 자체가 사라진다.

4. RYOW 구현 3종 — 화면 · 사람 · 토큰

암기 — 보장 범위가 넓어지는 순서 = 비용이 커지는 순서

① 화면 — 응답에 결과 포함▶ ② 사람 — 쓰기 경로로 라우팅▶ ③ 토큰 — 버전으로 요구
외우는 말: "화면 → 사람 → 토큰" — 뒤로 갈수록 어디서든 성립하지만 계약과 인프라를 더 건드린다

4-1. 구현 ① 쓰기 응답에 결과를 담는다 — 가장 싸다

가장 싸고, 그래서 가장 먼저 시도할 방법이다.

Before 쓰기는 명령만 던지고, 화면은 뒤처진 조회 모델만 본다
POST /purchases  -> 202 Accepted  (본문 없음)
GET  /my/passes  -> 200 []  // 아직 컨슈머가 처리 전이라 빈 목록 → "안 보여요"
After ① 응답에 결과를 담아 클라이언트가 화면을 직접 갱신한다 (낙관적 UI)
POST /purchases  -> 200 { "passId": 7, "status": "ACTIVE", ... }
// 클라이언트는 응답으로 받은 이용권을 목록에 즉시 추가한다.
// 조회 모델이 따라잡기 전까지의 공백을 「클라이언트 상태」가 메운다.
이 방식의 정체를 정확히 이해할 것 서버가 일관성을 보장하는 것이 아니다. 클라이언트가 자기 메모리에 들고 있는 값으로 공백을 메우는 것이다. 조회 모델은 여전히 뒤처져 있고 화면만 앞서 있다. 그래서 통하는 곳과 안 통하는 곳이 칼같이 갈린다.

통하는 상황

  • 쓰기 직후 같은 화면에서 결과를 보여줄 때
  • 구매 버튼을 누른 그 화면에 "이용권 1장 추가됨"을 그리는 경우

안 통하는 상황 — 그 화면을 벗어나는 순간 전부

  • 다른 탭 갔다 돌아오면 서버에서 목록을 다시 받아온다 → 없다
  • 새로고침해도 없다. 폰으로 열어도 없다
  • 클라이언트 메모리에만 있던 보장이라 메모리가 날아가면 같이 날아간다

비유로 기억하기 — 손에 쥔 영수증

응답에 담긴 결과는 손에 쥔 영수증이다. 그 자리에서는 증명이 되지만, 영수증을 놓고 나오면 끝이다. 가게 장부(조회 모델)에는 아직 안 올라가 있기 때문이다. 그래서 구현 ①은 "그 순간 그 화면"만 덮는다.

4-2. 구현 ② 쓰기 경로로 조회를 라우팅한다 — 서버가 보장한다

방금 쓴 사용자의 조회만 조회 모델이 아니라 원본(쓰기) 저장소로 보낸다. 서버가 보장하므로 화면을 이동하든 새로고침하든 성립한다 — 구현 ①의 한계가 여기서 사라진다.

판단 근거를 어디에 둘 것인가 — 두 선택지

(가) 쿠키에 둔다

쓰기 응답에서 Set-Cookie: lastWriteAt=...을 내려주면 클라이언트가 이후 요청에 자동으로 실어 보낸다.

  • 서버 무상태 유지, 추가 저장소 불필요
  • 클라이언트가 조작할 수 있다 — 누구나 쿠키를 심어 모든 조회를 원본으로 보낼 수 있고, 그것은 곧 조회 모델을 우회해 원본 DB에 부하를 거는 통로다
  • 쿠키를 안 쓰는 진입 경로(서버 간 호출, 일부 네이티브 앱)에서는 아예 안 통한다

(나) 서버 쪽 세션 저장소(예: Redis)에 둔다

쓰기가 끝나면 ryow:{userId}에 TTL을 걸어 기록하고, 조회 때 그 키의 존재 여부로 판단한다.

  • 조작이 불가능하다
  • TTL 만료가 자동으로 특별 취급을 해제해 준다 — 별도 정리 로직이 필요 없다
  • 조회마다 Redis 조회가 한 번 더 붙는다
After ② 쓰기 직후 그 사용자의 조회만 원본으로 보낸다
@PostMapping("/purchases")
public PurchaseResponse purchase(@AuthenticationPrincipal Long userId, ...) {
    PurchaseResponse res = purchaseService.purchase(userId, ...);
    // TTL = 허용 지연 SLA와 같은 값으로 잡는다(8·9절).
    // SLA가 5초라면 "5초 뒤에는 조회 모델이 따라잡았을 것"이라고 보는 것이다.
    redis.setex("ryow:" + userId, Duration.ofSeconds(5), "1");
    return res;
}

@GetMapping("/my/passes")
public List<PassView> myPasses(@AuthenticationPrincipal Long userId) {
    // 이 사용자가 최근에 썼는가? 그렇다면 뒤처진 조회 모델 대신
    // 반드시 최신인 원본을 읽게 한다.
    boolean recentlyWrote = redis.hasKey("ryow:" + userId);
    return recentlyWrote
        ? passQuery.fromPrimary(userId)    // 원본(쓰기) 저장소
        : passQuery.fromReplica(userId);   // 조회 모델
}

TTL은 아무 숫자가 아니다

TTL = 우리가 약속한 허용 지연 — 8절에서 기획과 합의할 그 숫자가 여기 그대로 들어간다

TTL을 길게 잡을수록 보장은 두터워지지만 원본으로 새는 트래픽이 늘어난다. 조회 부하를 원본에서 떼어내려고 조회 모델을 만들었는데 그것을 도로 붙이는 것이므로 — 원칙은 "필요한 만큼만 짧게"다.

구현 ②가 안 통하는 상황 사용자를 식별할 수 없는 비로그인 경로에서는 "누가 방금 썼는지"를 특정할 수 없다. 그리고 원본 저장소가 그 추가 부하를 감당할 수 있다는 전제가 필요하다.

4-3. 구현 ③ 버전 토큰으로 "이 버전 이상"을 요구한다 가산점

가장 정확하고 가장 비싸다. 발상은 이렇다. 쓰기 응답에 "이 쓰기가 만들어낸 버전"을 담아 클라이언트에 준다. 클라이언트는 이후 조회 요청에 그 토큰을 실어 보내면서 사실상 이렇게 요구한다 — "나는 이 버전 이상이 반영된 결과만 받겠다."

값어치 — 어떤 진입 경로에서도 성립한다

  • 토큰이 클라이언트 손에 있으므로 새로고침해도, 앱을 껐다 켜도 보장이 따라간다
  • 구현 ①처럼 화면 하나에 묶이지 않는다
  • 구현 ②처럼 서버가 사용자를 식별해야만 하는 것도 아니다

비용 — 세 군데서 발생한다

  • 조회 API 계약이 바뀐다 — 모든 조회가 토큰 파라미터를 받아야 한다
  • 조회 서비스가 자기 진행 지점을 노출해야 한다 — 내부 구현이던 것이 API 계약의 일부가 된다
  • 대기 방식은 요청 스레드를 점유한다 — 대기 상한을 반드시 두고, 넘으면 원본 우회나 "처리중" 응답으로 빠져야 한다
구현 ③이 안 통하는 상황 토큰을 전달할 수 없는 진입 경로다. 메일 링크를 눌러 바로 들어온 화면, 서버 사이드 렌더링의 첫 진입에는 토큰이 없다. 그때는 토큰 없는 요청을 그냥 조회 모델로 보내고, 대신 "처리중" 상태(5절)가 화면을 지키게 한다.

4-4. 세 방식 한눈에 — 그리고 셋은 배타적이지 않다

보장 범위 · 비용 · 깨지는 지점
보장 범위보장 주체구현 비용깨지는 지점먼저 쓸 상황
① 응답에 결과 포함
화면		그 화면, 그 순간클라이언트 메모리가장 낮음화면 이동 · 새로고침 · 다른 기기거의 언제나 기본으로 깐다
② 쓰기 경로 라우팅
사람		그 사용자의 모든 조회서버중간 — 판단 근거 저장소 필요비로그인 경로 · 원본 부하①로 부족한 흐름에 얹는다
③ 버전 토큰
토큰		토큰을 든 모든 요청서버 + 토큰가장 높음 — 조회 API 계약 변경토큰 없는 진입 경로정확성이 정말 필요한 소수 흐름
현실적인 조합: ①을 기본으로 깔고 → 부족한 흐름에만 ②를 얹고 → 정확성이 꼭 필요한 소수 흐름에 ③

5. "처리중"은 화면 문구가 아니라 도메인 상태다

RYOW로 안 되는 경우가 있다. 처리 자체가 비동기 저편에서 끝나야 결과가 「존재」하는 경우다 — 외부 결제망의 승인 확정, 배송 접수, 외부 정산 API 응답 같은 것들. 이때는 서버가 원본을 읽어도 보여줄 것이 없다. 결과가 아직 만들어지지 않았기 때문이다.

여기서 흔히 나오는 대응이 "화면에 '처리 중입니다'라고 띄우자"인데, 이것은 프런트엔드 문구 작업이 아니다. 왜 그런지는 화면이 아니라 도메인 모델 쪽에서 봐야 보인다.

5-1. 상태가 모델에 없으면 화면은 그것을 그릴 수 없다

Before 주문 상태에 중간 상태가 없다
public enum OrderStatus {
    COMPLETED,   // 완료
    CANCELLED    // 취소
}

// 이 모델이 표현할 수 있는 세계는 두 가지뿐이다
//   ① "그런 주문은 없다"
//   ② "완료된 주문이다"
//
// 결제는 승인됐지만 후속 처리가 아직인 그 몇 초 동안
// 서버가 정직하게 답할 수 있는 말이 이 둘 중에는 없다.
결과 조회 API 응답
GET /my/orders/1024
404 Not Found   // 또는 200 []
// 화면: "구매 내역이 없습니다"
After 중간 상태를 정식 도메인 상태로 승격한다
public enum OrderStatus {
    PENDING,     // 결제 승인됨 + 후속 처리(지급) 진행 중
    COMPLETED,   // 후속 처리까지 끝나 확정됨
    FAILED       // 후속 처리 확정 실패 — 재시도를 안내
}

// 이제 서버는 「세 번째 답」을 갖게 됐다.
// enum 한 줄의 추가가 아래 것들을 전부 가능하게 만든다:
//   · 화면의 "처리중" 표시     · 완료 통지(6절)
//   · 중복 구매 가드            · CS 상담 근거
//   · 타임아웃 감지와 강등 UX(10절)
결과 조회 API 응답
GET /my/orders/1024
200 { "status": "PENDING", "elapsedSec": 3 }
// 화면: "구매 처리 중입니다 (3초 경과)"

이 절의 한 문장

"결제했는데 왜 안 보여요"는 UI 버그가 아니라 — 도메인 모델에 중간 상태가 없다는 사실의 표면화다

그래서 대응도 프런트가 아니라 enum에 값을 하나 추가하는 것에서 시작한다. 상태가 모델에 없으면 API도 그것을 담을 수 없고, 화면도 그것을 그릴 수 없고, 상담원도 그것을 볼 수 없다.

5-2. 상태 전이 — 세 갈래와 「그날의 화면」

5-3. 거짓 완료가 왜 최악인가 — "늦는 것"과 "사라지는 것"은 무게가 다르다

PENDING이 없으면 화면은 COMPLETED를 미리 그릴 수밖에 없다. 그리고 그 뒤에 실패하면 사용자는 완료라고 봤던 것이 사라지는 경험을 한다.

5-4. 같은 처방이 다른 문서에서도 나온다 — 의미적 잠금

이 처방에는 이름이 있다. 의미적 잠금(semantic lock) — DB 락처럼 물리적으로 접근을 막는 것이 아니라, 데이터에 "아직 확정 아님"이라는 표식을 붙여 확정처럼 취급되지 않게 하는 기법이라 "의미적"이라고 부른다.

같은 발상이 세 자리에서 나온다 — 대상만 다르다

① 다른 서비스의 로직

③ 사용자의 눈

셋 다 하나의 처방이다 — "확정 전 데이터를 상태값으로 표시해 둔다"

5-5. PENDING이 있어야 비로소 중복 구매 가드가 성립한다

2절에서 본 "다시 산다"는 가장 위험한 행동이 여기서 차단된다. "이 사용자에게 이 상품의 PENDING 주문이 있으면 새 구매를 막는다"는 규칙은 — PENDING이라는 상태가 모델에 존재해야만 쓸 수 있는 문장이다.

가드 서버에서 막는다 — 클라이언트 버튼 비활성화만으로는 부족하다
@Transactional
public PurchaseResponse purchase(Long userId, Long productId, String requestKey) {
    // ① 진행 중인 같은 상품 주문이 있으면 새로 만들지 않는다
    orderRepository.findByUserAndProductAndStatus(userId, productId, PENDING)
        .ifPresent(o -> { throw new DuplicateInFlightException(o.getId()); });
    // → 화면은 이 예외를 "이미 처리 중인 주문이 있습니다"로 그린다.
    //   "실패"가 아니라 "진행 중"이라고 말하는 것이 핵심이다.

    // ② 그래도 남는 틈: 동시 요청 두 개는 ①을 둘 다 통과할 수 있다.
    //   최종 방어선은 멱등키의 유니크 제약이다.
    return orderService.createIdempotent(userId, productId, requestKey);
}
가드 두 겹을 함께 말해야 한다 PENDING 조회 가드는 대부분의 재구매를 막지만 동시 요청은 못 막는다 — 두 요청이 같은 순간에 조회하면 둘 다 "없음"을 본다. 그래서 최종 방어선은 멱등키(요청 키)에 건 DB 유니크 제약이다. 자세한 것은 같은 장의 04-idempotent-consumer-implementation.md. 면접에서는 "UX 가드 + 데이터 제약, 두 겹"이라고 답하는 것이 안전하다.

6. 완료를 어떻게 알릴 것인가 — 네 방법의 대가

PENDING을 만들었으면 이제 "언제 끝났는지"를 사용자에게 전해야 한다. 방법은 넷이고, 각각 다른 종류의 대가를 낸다. 여기서 답이 갈리는 지점은 기법 이름이 아니라 "대가가 어디로 옮겨 가는가"를 말할 수 있느냐다.

6-1. 폴링 — 대가는 조회량이고, 반드시 숫자로 계산한다

먼저 계산부터 — 폴링 비용 공식

대기 사용자 수 × (1 / 폴링 주기) = 초당 추가 조회수
10,000명
대기자
÷ 2초
폴링 주기
= 5,000 QPS
1분이면 30만 회

진짜 무서운 대목은 크기가 아니라 타이밍이다. 대기자가 1만 명까지 쌓이는 상황은 곧 컨슈머 랙이 커진 상황이고, 그것은 시스템이 이미 힘들어하는 상황이다. 즉 가장 아플 때 조회가 최대가 되는 구조다 — 2절에서 본 "새로고침 연타"를 우리가 코드로 자동화해 준 셈이다.

그래서 폴링을 쓴다면 최소한 이 셋을 건다.

1
지수 백오프 — 1, 2, 4, 8, 16, 32초로 간격을 늘린다. 6회로 63초를 덮으면서 조회는 6번뿐이다. 고정 2초로 63초를 덮으려면 약 31회다.
2
최대 횟수 상한 — 무한 폴링을 클라이언트가 못 하게 강제하고, 상한을 넘으면 "완료되면 알림을 보내드립니다"로 전환한다.
3
경량 상태 확인 API 분리 — 이용권 목록 전체를 다시 내려주지 말고 { "status": "PENDING" } 한 줄만 답하는 전용 엔드포인트를 만들고 짧은 TTL 캐시를 붙인다. 같은 5,000 QPS라도 비용이 자릿수 단위로 달라진다.
Before 고정 간격 + 무한 + 무거운 조회
setInterval(async () => {
  // 목록 전체를 매번 다시 받아온다
  const list = await fetch('/my/passes');
  render(list);
}, 2000);   // 끝날 때까지 영원히 2초마다

// 대기 1만 명 → 5,000 QPS, 그것도 목록 전체 조회.
// 게다가 랙이 길어질수록 대기자가 늘어 부하가 더 커진다.
After 지수 백오프 + 상한 + 경량 상태 API
const delays = [1000, 2000, 4000, 8000, 16000, 32000]; // 합 63초
for (const d of delays) {
  await sleep(d);
  // 한 줄짜리 상태 전용 엔드포인트 (짧은 TTL 캐시)
  const { status } = await fetch('/my/orders/1024/status');
  if (status !== 'PENDING') return refresh(status);
}
// 상한 초과 → 폴링을 끊고 통지 방식으로 넘긴다
showNotifyLater();   // "완료되면 알려드릴게요"

6-2. SSE · 웹소켓 · 푸시 — 대가가 「연결」과 「도달」로 옮겨 간다

SSE (Server-Sent Events) — 서버가 밀어준다

HTTP 연결을 열어둔 채 서버 → 클라이언트 한 방향으로 이벤트를 흘려보낸다. 완료 통지에 정확히 맞는 모양이다 — 클라이언트는 받기만 하면 되니까.

  • 대가 = 연결 유지 비용. 대기 1만 명이면 동시 연결 1만 개가 서버·LB·프록시의 커넥션 슬롯을 점유한다
  • 프록시 idle timeout에 끊기지 않도록 주기적 keep-alive 이벤트가 필요하다
  • 덜 알려진 대가: 여러 인스턴스로 뜬 서버에서는 그 사용자의 연결을 들고 있는 인스턴스에만 알림이 닿아야 한다 → 완료 이벤트를 전 인스턴스에 퍼뜨리는 장치(예: Redis pub/sub)가 하나 더 필요하다. 폴링에는 없던 문제다

웹소켓 — 완료 통지 용도로는 과하다

양방향 상시 연결. 클라이언트가 서버로 보낼 것이 없는데 양방향 채널을 여는 것이다.

  • SSE의 대가를 전부 그대로 내면서
  • 프로토콜 업그레이드, 연결 중 인증 갱신, 재연결 처리 등 운영 부담이 더 붙는다
  • 채팅처럼 원래 양방향이 필요한 기능이 이미 웹소켓을 쓰고 있다면 거기에 얹는 것은 합리적 — 완료 통지 하나 때문에 새로 도입할 이유는 없다
푸시 알림은 성격이 다르다 — 대체가 아니라 보완 앱을 떠난 사용자에게 닿는 유일한 수단이다. 대신 도달이 보장되지 않고(OS 권한, 네트워크, 지연) 즉시성도 약하다. 그래서 화면 갱신을 대체하는 것이 아니라 보완한다 — 화면에 있는 동안은 폴링이나 SSE가, 떠난 뒤에는 푸시가 맡는 식이다.
완료 통지 네 방법 — 대가가 어디로 가는가
조회 부하연결 자원앱 떠난 뒤추가로 필요한 장치적합한 규모
폴링대기자 수에 비례해 증가없음안 됨백오프 · 상한 · 경량 상태 API대기자가 적을 때
SSE없음동시 연결 수만큼안 됨keep-alive · 인스턴스 간 브로드캐스트대기자가 많고 실시간이 중요할 때
웹소켓없음동시 연결 + 운영 부담안 됨SSE의 것 + 재연결 · 인증 갱신이미 웹소켓을 쓰고 있을 때
푸시 알림없음없음됨디바이스 토큰 관리 · 권한지연이 길어질 수 있을 때

암기 — 통지 방식을 바꾸면 「비용의 종류」가 바뀐다

폴링 = 조회량▶ SSE · 웹소켓 = 연결 수▶ 푸시 = 도달 불확실
공짜로 좋아지는 것이 아니다 — 비용의 종류가 옮겨 갈 뿐이고, 어느 쪽이 우리 인프라에서 싼지가 선택 기준이다

그리고 넷 모두의 전제는 하나로 같다 — PENDING 상태가 존재해야 한다. 상태가 없으면 클라이언트는 무엇을 폴링할지도, 서버는 무엇의 완료를 통지할지도 정할 수 없다.

7. 선긋기 — 애초에 무엇을 비동기로 뺄 것인가

지금까지가 "비동기로 뺀 것을 어떻게 감당하는가"였다면, 그 앞에 던져야 할 질문이 있다. 애초에 무엇을 비동기로 뺄 것인가. 기준은 하나다.

8. 제품 축 — 허용 지연을 협상한다 시니어 변별

시니어가 갈리는 지점은 여기다. 최종 일관성의 지연 허용치는 엔지니어가 혼자 정하는 값이 아니라 제품 결정이다.

8-1. 던져야 할 질문은 한 문장 — 그리고 던지는 시점이 중요하다

"이용권 지급이 결제 후 몇 초까지 늦어도 되는가?"

답이 "3초"라면

RYOW로 충분하다 — 그 사용자 화면만 즉시 채워주고 조회 모델은 뒤에서 따라잡게 두면 된다.

답이 "0초여야 한다"면

그 구간은 비동기로 뺄 수 없다는 뜻이다. 동기 커밋 범위에 남겨야 한다(7절).

여기가 변별 지점 — 순서를 말할 수 있는가

✗ 아키텍처를 다 만든 뒤 확인 삼아 묻는다
✓ 아키텍처를 정하기 전에 백엔드가 먼저 던진다
이 질문의 답이 7절의 경계선을 긋는다 — 그러니 경계선을 긋기 전에 물어야 한다

8-2. 하나의 숫자가 아니라 흐름별로 협상한다

협상은 서비스 전체에 하나의 숫자를 정하는 방식이 아니라 흐름별로 한다. 판단 근거는 딱 하나 — "결과가 안 보이면 사용자가 무엇을 하는가"다.

흐름별 허용 지연 — 근거는 "사용자의 다음 행동"이다
흐름안 보이면 사용자가 하는 행동그 행동의 비용허용 지연필요한 처방
결제 → 이용권 지급재구매 시도, CS 문의중복 결제 · 환불 · 신뢰 손실초 단위 이하RYOW + PENDING + 중복 가드 + 강등 배너
주문 → 배송 상태 갱신새로고침, 잠시 후 다시 봄불편 정도수십 초PENDING 표시 정도면 충분
구매 → 추천 목록 반영아무것도 안 함 (인지조차 못 함)없음분 단위없음
활동 → 통계 대시보드아무것도 안 함없음시간 단위"○시 기준" 표기 정도
이 표가 말하는 것 지연의 비용이 흐름마다 다르다. 중복 결제로 이어지는 지연과 아무도 모르는 지연에 같은 기준을 적용할 이유가 없다. 그래서 "우리 시스템의 허용 지연은 N초입니다"라는 단일 숫자 답변은 오히려 감점이다 — 흐름별 차등을 말해야 한다.

9. 같은 숫자가 세 자리에 들어간다 시니어 변별

여기가 이 문서에서 가장 실질적인 연결이다. 기획과 합의한 SLA 숫자는 문서에 적히고 끝나는 것이 아니라 — 컨슈머 랙 알람의 임계값으로, 그리고 코드의 상수로 그대로 들어간다.

9-1. 그러려면 랙을 「개수」가 아니라 「시간」으로 봐야 한다

규칙 — 랙은 개수가 아니라 나이로 잰다

랙 지표 = 가장 오래된 미처리 메시지의 나이 (적재 시각 → 지금)

이렇게 재야 SLA와 같은 단위가 되고, 그래야 합의한 숫자를 그대로 임계값으로 쓸 수 있다. 개수와 시간은 단위가 달라서 애초에 비교가 안 된다.

9-2. 협상 결과가 알람 임계값이 되고, 동시에 코드의 상수가 된다

암기 — SLA 5초가 들어가는 세 자리

① 알람
랙 나이 > 5초 → 경고
> 15초 → 강등 배너
② TTL
RYOW 라우팅 판단 키의
Redis TTL = 5초
③ 타임아웃
PENDING 경과 > 5초
→ 강등 · 운영 알림
한 문장으로: "같은 숫자가 협상 테이블 · 알람 설정 · 코드 상수에 동시에 들어간다"

10. 지연은 반드시 오므로, 그날의 UX를 미리 만든다

마지막 한 조각은 강등(degradation) UX다. 랙이 SLA를 크게 넘는 상황이 오면 보여줄 것들을 미리 준비해 두는 것이다.

① 배너
"현재 이용권 지급이 지연되고 있습니다.
결제는 정상 처리되었습니다."
두 번째 문장이 특히 중요하다 — 2절의 "다시 산다"를 막는 문장이 이것이다.
② CS 대응 문구
상담원이 볼 수 있는 주문 상태(PENDING + 경과 시간)와 안내 스크립트.
상태가 화면에 노출돼 있어야 상담이 성립한다.
③ 중복 구매 가드
PENDING인 동안 같은 상품의 구매 버튼을 비활성화하고 서버에서도 차단한다.
클라이언트 비활성화만으로는 부족하다 — API를 직접 부르는 경로가 남는다.

순서가 핵심이다 — 강등 UX는 「장애 대응 절차」가 아니다

이 배너를 장애가 터진 날 급하게 만들면 늦다
강등 UX는 기능 개발 시점에 함께 만드는 산출물이다

지연은 반드시 온다. 그날의 화면까지 설계해 두는 것이 이벤트 기반 아키텍처의 운영이다. 그리고 이 세 가지가 발동되는 조건이 바로 9절의 임계값이다 — SLA×3을 넘으면 배너가 자동으로 뜬다처럼 조건을 코드에 걸어둔다.

11. 인출 카드 · 꼬리질문 셀프 테스트

면접 전날 이것만 — 인출 카드 8장

① 프레임 한 줄
지연은 버그가 아니라 청구서다. 가용성·처리량·낮은 결합을 사고 낸 값. 그래서 목표는 "지연 제거"가 아니라 "실패로 오인시키지 않기".
② 4처방 — 즉·정·협·감
즉시(RYOW) · 정직(PENDING) · 협상(SLA) · 감시(랙 나이). 기술 둘만 말하면 절반이다.
③ RYOW의 정의
보장 범위를 한 사람으로 좁힌 절충. 남에게 언제 보이는지는 전혀 약속하지 않는다 — 그래서 싸다.
④ 구현 3종 순서
화면 → 사람 → 토큰. ①응답에 결과 ②쓰기 경로 라우팅 ③버전 토큰. 뒤로 갈수록 넓게 보장, 비싸게.
⑤ 핵심 문장
"결제했는데 왜 안 보여요"는 UI 버그가 아니라 도메인 모델에 중간 상태가 없다는 사실의 표면화다.
⑥ 폴링 산수
1만 명 ÷ 2초 = 5,000 QPS(1분 30만). 무서운 건 크기가 아니라 가장 아플 때 최대가 된다는 타이밍.
⑦ 랙은 나이로
"랙 1만 건"은 판단 불가, "지급 지연 40초"는 즉시 판단. SLA와 단위를 맞춰야 임계값으로 쓸 수 있다.
⑧ 마무리 문장
"허용치를 정의한 적 없는 시스템은 지연이 나도 그것이 장애인지 아닌지조차 판단할 수 없다."

이 질문을 받으면 3분 안에 이 순서로 답한다

1
프레임을 깐다 — "지연은 아키텍처를 고른 대가입니다. 그래서 없애는 게 아니라 실패로 오인되지 않게 설계합니다."
2
요구를 분해한다 — "불만의 대부분은 남의 데이터가 아니라 자기 행동의 결과가 안 보일 때입니다. 그래서 본인 것만 즉시 보이게 하면 대부분 해결됩니다." → RYOW 3종 중 상황에 맞는 것.
3
RYOW로 안 되는 구간을 짚는다 — "결과가 비동기 저편에서 만들어지는 구간은 보여줄 게 없습니다. 그래서 PENDING을 enum에 추가합니다. 프런트 문구가 아니라 도메인 상태입니다." → 완료 통지 방식과 그 대가.
4
제품 축으로 넘어간다 — "허용 지연은 제가 혼자 정할 값이 아니라 흐름별로 기획·CS와 협상합니다. 결제는 초 단위 이하, 통계는 시간 단위처럼요."
5
운영으로 닫는다 — "그 숫자가 랙 나이 알람 임계값 · RYOW TTL · PENDING 타임아웃 세 자리에 그대로 들어갑니다. 그리고 강등 UX는 기능 개발 시점에 함께 만듭니다."
빠뜨리면 감점되는 것: 동기로 남길 구간을 먼저 긋는다는 말 (7절) — 모든 것을 비동기로 빼지 않는다

꼬리질문 — 먼저 스스로 답한 뒤 펼친다

read-your-own-writes를 구체적으로 어떻게 구현했나요 / 하겠나요? 핵심힌트: 기법 나열보다 "요구의 분해"를 먼저 말해야 점수가 난다

답의 핵심은 기법 나열이 아니라 요구의 분해다. 먼저 이 문장을 던진다 — "본인 것만 즉시 보이면 되고, 남의 화면은 몇 초 늦어도 됩니다." 이 분해를 말하면 이어지는 세 기법이 왜 전부 "한 사용자만 특별 취급"이라는 같은 모양인지가 저절로 설명된다.

  1. 쓰기 응답에 결과를 담아 클라이언트가 화면 상태를 직접 갱신 — 가장 싸고 대부분 충분하다. 단 "화면을 벗어나면 보장이 사라진다"는 한계를 함께 말해야 한다. 보장 주체가 서버가 아니라 클라이언트 메모리이기 때문이다.
  2. 쓰기 직후 그 사용자의 조회를 원본 저장소로 라우팅 — 서버가 보장하므로 클라이언트 수정이 필요 없다. 관건은 "최근에 썼다"는 판단 근거를 어디에 두느냐다.
    • 쿠키: 무상태 · 추가 저장소 불필요 / 조작 가능(원본 DB 부하 통로가 된다) · 쿠키 없는 경로에서 무력
    • 서버 세션(Redis): 조작 불가 · TTL이 자동 해제 / 조회마다 1회 추가
    그리고 TTL은 SLA와 같은 값으로 잡는다는 말까지 붙인다.
  3. 버전 토큰으로 조회 모델의 따라잡음을 확인 — 파티션·오프셋을 토큰으로 주고, 조회 서비스가 자기 진행 지점과 비교해 대기하거나 원본 우회한다. 어떤 진입 경로에서도 성립하지만 조회 API 계약이 바뀌고 조회 서비스가 자기 진행 지점을 노출해야 한다.
마무리: "①을 기본으로 깔고, 부족한 흐름에만 ②, 정확성이 꼭 필요한 소수 흐름에 ③" — 셋은 배타적이지 않다
그럴 거면 그냥 동기로 하면 되지 않나요?힌트: 부분적으로 맞는 지적이다. 반박이 아니라 「선긋기」로 답한다

부분적으로 맞는 지적이라 반박하지 않고 선긋기로 답한다.

  • 결과에 다음 행동이 의존하는 핵심 경로(결제 확정, 권한 부여)는 동기로 남긴다. 여기를 비동기로 빼면 RYOW·PENDING·완료 통지·강등 UX를 전부 만들고도 사용자는 여전히 기다린다.
  • 지연이 허용되는 부가 경로(알림·통계·추천)만 비동기로 뺀다.

양 극단의 비용을 대칭으로 말하는 것이 이 답의 요령이다 — 전부 동기로 묶으면 가용성·처리량·서비스 간 결합의 비용을 도로 내고, 전부 비동기로 빼면 UX 비용을 낸다.

경계를 어디에 긋느냐가 설계 판단이고, 그 기준이 바로 "이 결과는 몇 초까지 늦어도 되는가"다

즉 이 꼬리질문의 답은 다음 질문의 답과 같은 뿌리에서 나온다. 그 연결을 말로 이어주면 더 좋다.

허용 지연 시간은 누가 어떻게 정하나요? 시니어 변별힌트: 답의 진짜 무게는 "정한 다음 그 숫자가 어디로 가는가"에 있다

백엔드가 단독으로 정하는 값이 아니다. 흐름별로 "안 보이면 사용자가 무엇을 하는가"(재구매? 이탈? 무시?)를 기획·CS와 함께 따져 도메인별로 차등을 둔다 — 결제·권한은 초 단위 이하, 알림·통계는 분 단위 허용, 같은 식이다.

그리고 이 답의 진짜 무게는 뒷부분에 있다. 정한 숫자는 문서로 끝나는 게 아니라 세 자리로 동시에 들어가야 산다.

그리고 순서를 짚으면 한 단계 더 올라간다 — 이 질문은 아키텍처를 다 만든 뒤 확인 삼아 묻는 게 아니라, 아키텍처를 정하기 전에 백엔드가 먼저 던져야 한다. 답이 "0초"면 애초에 비동기로 뺄 수 없는 구간이기 때문이다.

마무리 문장: "허용치를 정의한 적이 없는 시스템은 지연이 나도 그것이 장애인지 아닌지조차 판단할 수 없다."
완료를 폴링으로 확인시키면 조회가 폭주하지 않나요?힌트: "폭주한다"고 인정하고 숫자로 시작하는 게 가장 좋은 답이다

폭주한다. 그러니 숫자로 인정하고 시작하는 것이 좋다 — 대기 1만 명이 2초마다 폴링하면 초당 5,000 조회, 1분이면 30만 회다. 더 나쁜 것은 그 부하가 시스템이 가장 아플 때(랙이 쌓여 대기자가 많은 때) 최대가 된다는 점이다.

그래서 폴링을 쓴다면 세 가지를 건다.

  • 지수 백오프 + 최대 횟수를 클라이언트에 강제 — 1, 2, 4, 8, 16, 32초면 6회로 63초를 덮는다(고정 2초로 같은 시간을 덮으면 약 31회).
  • 경량 상태 확인 API로 분리하고 짧은 TTL 캐시 — 목록 전체를 내려주는 조회와 { "status": "PENDING" } 한 줄은 비용이 자릿수 단위로 다르다.
  • 상한을 넘으면 통지 방식으로 전환 — "완료되면 알려드릴게요"로 바꾸고 푸시로 넘긴다.

규모가 더 커지면 SSE나 웹소켓 push로 바꾸는데, 여기서 대가가 사라지는 게 아니라 옮겨 간다는 점을 짚으면 좋다 — 조회량 대신 동시 연결 1만 개, 프록시 idle timeout 대응, 그리고 여러 인스턴스 중 그 사용자의 연결을 들고 있는 인스턴스에만 이벤트를 보내기 위한 브로드캐스트 장치가 필요해진다.

공짜로 좋아지는 게 아니라 비용의 종류가 바뀌는 것 — 그리고 어느 쪽이든 PENDING 상태의 존재가 전제다
쓰기 직후 조회를 원본으로 보내면, 조회 모델을 둔 의미가 없어지는 것 아닌가요? 함정힌트: "얼마나 새는가"를 비율로 계산해서 답한다

비율로 답하는 질문이다. "일부는 새지만 그 일부가 얼마나 작은지"를 계산해서 보여주면 된다.

  • 특별 취급 대상자는 쓰기 QPS × TTL이다. 쓰기 100건/s에 TTL 5초면 어느 순간에도 최대 500명. 전체 조회 트래픽에 비하면 극히 일부이고, 나머지는 그대로 조회 모델이 받는다.
  • 그래서 TTL이 이 답의 핵심 변수다. TTL을 늘리면 보장은 두터워지지만 원본으로 새는 몫이 선형으로 늘어난다. 원칙은 "필요한 만큼만 짧게" — 그리고 그 "필요한 만큼"이 곧 SLA다.
  • 범위를 더 좁힐 수도 있다: 사용자 전체 조회가 아니라 방금 쓴 그 엔티티를 포함하는 조회에만 라우팅을 건다. 예를 들어 "내 이용권 목록"만 원본으로 보내고 "상품 목록"은 그대로 둔다.
반드시 함께 말할 것 — 원본이 감당 가능한가 이 방식은 원본 저장소에 추가 부하를 되돌려 주는 방식이다. 그래서 "쓰기 QPS × TTL 만큼의 조회를 원본이 받아낼 수 있는가"를 먼저 확인하는 것이 순서다. 못 받아내면 TTL을 줄이거나 구현 ①(응답에 결과 포함)으로 후퇴하는 게 맞다.
PENDING 상태가 끝나지 않고 영원히 남으면 어떻게 하나요? 가산점힌트: "누가 PENDING을 깨우는가"라는 질문이다. 이벤트는 유실될 수 있다

반드시 생긴다고 보고 설계해야 하는 상황이다. 완료 이벤트가 유실되거나, 컨슈머가 DLQ로 보내버렸거나, 다운스트림이 응답하지 않으면 PENDING은 영원히 PENDING이다. 그리고 PENDING이 남아 있으면 중복 구매 가드 때문에 사용자는 재구매도 못 한다 — 가드가 오히려 사용자를 가둔다.

처방은 "아무도 안 깨우면 스스로 깨어난다"는 장치를 두는 것이다.

// PENDING 스위퍼 — 주기적으로 늙은 PENDING을 찾아 처리한다
@Scheduled(fixedDelay = 10_000)
public void sweepStalePending() {
    // ① SLA를 넘긴 것 — 아직 희망은 있다. 화면만 강등한다
    orders.findPendingOlderThan(SLA)
          .forEach(o -> { o.markDegraded(); alert.warn(o); });

    // ② 확정 시한을 넘긴 것 — 실패로 확정하고 보상한다
    orders.findPendingOlderThan(HARD_TIMEOUT)
          .forEach(o -> { o.markFailed(); refund.compensate(o); });
}
  • 두 개의 시한을 둔다 — SLA 초과(화면 강등 + 경고 알람)와 하드 타임아웃(FAILED 확정 + 보상). 전자는 아직 성공할 수 있는 상태이고, 후자는 포기하는 지점이다.
  • 확정 전이는 멱등해야 한다 — 스위퍼가 FAILED로 넘긴 직후 늦은 완료 이벤트가 도착할 수 있다. 상태 전이 규칙(FAILED에서 COMPLETED로 갈 수 있는가)을 미리 정해 둬야 한다.
  • 보상은 Saga의 영역이다 — 같은 장의 08-saga-choreography-orchestration-compensation.md로 이어진다.

면접에서는 "PENDING을 만들었으면 PENDING을 끝내는 책임자도 함께 만든다"는 한 문장으로 정리하면 좋다.

낙관적 UI로 화면에 먼저 "완료"를 그렸는데 뒤에서 실패하면요? 함정힌트: "늦게 나오는 것"과 "있다가 없어지는 것"의 무게 차이

이것이 정확히 「거짓 완료」이고, 이 문서가 최악이라고 부르는 상황이다. 사용자는 완료라고 봤던 것이 사라지는 경험을 한다. "늦게 나오는 것"은 기다림이지만 "있다가 없어지는 것"은 신뢰 붕괴이고, 둘의 무게는 전혀 다르다.

그래서 낙관적 UI에는 적용 기준이 붙는다.

써도 되는 곳

  • 실패 확률이 낮고, 실패해도 되돌림이 싼 것
  • 좋아요, 북마크, 목록 순서 변경 같은 것

쓰면 안 되는 곳

  • 돈 · 권한 · 재고처럼 되돌림이 비싼 것
  • 여기서는 낙관적 "완료" 대신 PENDING을 정직하게 그린다

정리하면 이렇게 답한다 — 응답에 결과를 담아 화면을 채우는 것(구현 ①) 자체는 좋지만, 그때 그리는 상태가 COMPLETED가 아니라 PENDING이어야 한다. 즉 "결과를 미리 보여주되, 확정이라고 말하지는 않는다."

낙관적으로 보여줄 것은 결과이지 확정이 아니다
본인이 아니라 다른 사용자에게도 즉시 보여야 하는 화면은 어떻게 하나요? 가산점힌트: RYOW의 정의상 여기는 원래 커버 범위가 아니다

먼저 RYOW의 한계를 정확히 인정하고 시작한다 — RYOW는 "내가 쓴 것이 나에게"만 보장한다. 남에게 언제 보이는지는 정의상 약속하지 않는다. 그러니 이 요구는 RYOW로 풀 문제가 아니다.

실제로 이런 요구가 나오는 자리는 정해져 있다.

  • 운영자/상담원 화면 — 사용자가 방금 한 결제를 상담원이 즉시 봐야 한다
  • 협업 화면 — 같은 문서·같은 예약 슬롯을 여러 명이 동시에 본다
  • 재고·좌석처럼 경쟁이 있는 자원 — 남의 쓰기가 나에게 즉시 보여야 한다

선택지는 셋이고, 비용 순서대로 검토한다.

  1. 그 화면만 원본을 읽게 한다 — 상담원 화면처럼 트래픽이 작은 화면이면 이게 가장 싸고 확실하다. "소수 화면만 강한 일관성 경로"라는 예외 취급.
  2. 그 구간을 애초에 동기로 남긴다(7절) — 재고·좌석처럼 경쟁이 정확성을 좌우하면 이벤트로 빼면 안 된다.
  3. 실시간 push로 밀어준다 — 협업 화면은 애초에 변경을 구독하는 구조(SSE/웹소켓)로 만들고, 일관성이 아니라 갱신 지연으로 문제를 재정의한다.

덧붙이면 좋은 말: "RYOW로 안 되는 요구가 나오면, 그것은 대체로 7절의 경계선을 다시 그으라는 신호"다.

랙을 "나이"로 잰다고 했는데, 실제로 어떻게 측정하나요? 가산점힌트: 컨슈머가 메시지를 처리하는 순간에 무엇을 알고 있는지 생각해 보라

가장 단순한 방법은 컨슈머 쪽에서 직접 재는 것이다. 컨슈머는 메시지를 처리하는 순간 그 메시지가 브로커에 적재된 시각을 함께 갖고 있다. 그 값과 현재 시각의 차가 곧 "이 메시지가 얼마나 늙었는가"다.

@KafkaListener(topics = "purchase-completed")
public void handle(ConsumerRecord<String, Payload> record) {
    long ageMs = System.currentTimeMillis() - record.timestamp();
    meter.record("consumer.record.age", ageMs);   // 이 값이 곧 "지급 지연"
    grantPass(record.value());
}

그리고 이 방식의 함정 두 가지를 함께 말해야 답이 완성된다.

  • 유입이 멈추면 지표가 갱신되지 않는다. 처리할 메시지가 없으면 이 값은 더 이상 올라오지 않는다 — "정상"으로 보이는 게 아니라 아무 값도 안 나온다. 그래서 개수 기반 랙과 함께 봐야 하고, 지표가 끊긴 것 자체도 알람 대상이다.
  • 이미 처리한 메시지의 나이다. 컨슈머가 아예 멈춰 있으면(리밸런싱 중, 스레드 블로킹) 이 값도 같이 멈춘다. 그래서 "마지막으로 관측된 나이 + 그 관측이 얼마나 오래됐는가"를 같이 봐야 한다.

브로커 쪽에서 재는 방법도 있다 — 커밋된 오프셋의 메시지 적재 시각과 로그 끝(latest) 메시지의 적재 시각을 비교하면, 컨슈머가 살아 있지 않아도 외부에서 지연을 관측할 수 있다. 운영에서는 컨슈머 내부 지표 + 외부 관측을 함께 두는 쪽이 안전하다.

진단과 해소 방법 전체는 같은 장의 31-consumer-lag-diagnosis-and-resolution.md에서 다룬다. 이 문서에서 확실히 해야 할 것은 "임계값을 SLA에서 가져온다"는 연결이다.

중복 결제는 PENDING 가드만 있으면 막히나요? 함정힌트: 동시에 두 번 누르면 두 요청이 같은 순간에 조회한다

대부분은 막히지만 전부는 아니다. PENDING 조회 가드는 "조회 → 판단 → 생성" 사이에 틈이 있다. 두 요청이 같은 순간에 조회하면 둘 다 "진행 중인 주문 없음"을 본다. 더블 클릭, 앱의 재시도, 네트워크 타임아웃 후 사용자 재요청이 정확히 이 상황을 만든다.

그래서 가드는 두 겹이다.

1겹 — UX 가드
PENDING 조회로 막고, 화면에는 "실패"가 아니라 "이미 처리 중"이라고 말한다. 사용자가 다시 누를 이유 자체를 없애는 것이 목적이다.
2겹 — 데이터 제약
요청 멱등키(또는 사용자+상품+기간 조합)에 DB 유니크 제약. 경쟁 상태에서 DB가 최종 심판을 본다. 제약 위반은 예외가 아니라 "이미 처리됨"으로 해석한다.

덧붙이면 좋은 것: 컨슈머 쪽에도 같은 문제가 있다. 완료 이벤트가 재전달되면 이용권이 두 번 지급될 수 있으므로 컨슈머 자체가 멱등해야 한다 — 같은 장의 04-idempotent-consumer-implementation.md.

UX 가드는 확률을 줄이고, 데이터 제약이 정확성을 보장한다 — 둘은 대체 관계가 아니다
한 줄 요약
최종 일관성의 UX 문제는 지연을 없애는 게 아니라 — 자기 행동의 결과는 즉시 보이게 하고(read-your-own-writes), 나머지는 "처리중"이라는 정직한 도메인 상태로 보여주고, "몇 초까지 괜찮은가"를 제품 결정으로 합의해 그 숫자를 그대로 랙 알람 임계값과 코드 상수로 쓰는 것 — 즉 지연을 사용자가 실패로 오인하지 않게 설계하는 일이다.
