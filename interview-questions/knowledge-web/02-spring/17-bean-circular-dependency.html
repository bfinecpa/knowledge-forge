Bean 순환 참조
@Lazy로 덮기 전에 설계를 고쳐라 — 기동 실패는 버그가 아니라 조기 경보다

면접 질문: "Bean 순환 참조가 발생하는 원인과 해결 방법은?"

핵심 관전 포인트 — 순환 참조는 A가 B를, B가 다시 A를 주입받아 의존 그래프가 고리를 이루는 상태다. 컨테이너가 기동을 실패시키는 것은 버그가 아니라 조기 경보이므로, 답의 1순위는 경보를 끄는 우회(@Lazy, 필드 주입 전환)가 아니라 의존을 단방향으로 되돌리는 설계 수정이다 — 공통 책임을 제3의 컴포넌트로 추출하거나, 사후 알림 성격의 역방향 호출을 이벤트로 끊거나, 인터페이스를 호출하는 쪽에 두어 의존 방향을 뒤집는다. @Lazy·ObjectProvider는 순환을 없애는 것이 아니라 첫 호출 시점으로 미루는 것이라 "부팅에서 잡히던 문제가 트래픽에서 터진다"는 대가가 붙고, 그래서 진단을 끝낸 뒤 부채로 기록하고 쓰는 차선책이다.
  • 1
    현상이 아니라 구조로 정의한다 — 의존을 화살표로 그렸을 때 출발한 자리로 돌아오는 고리가 생긴 상태이고, 생성자 주입에서는 어느 쪽도 먼저 완성될 수 없어 기동이 실패한다. 이 실패는 컨테이너의 한계가 아니라 "하나의 책임이 두 클래스에 찢어져 있다"는 설계 경보다.
  • 2
    해결의 1순위는 설계 수정 네 갈래다 — 부트가 그려 주는 사이클 메시지로 문제의 빈 쌍을 특정한 뒤, ①공통 책임 추출 · ②이벤트로 역방향 절단 · ③인터페이스 소유를 옮겨 의존 역전 · ④병합 후 재분할 중 하나로 고리를 열어 화살표가 한 방향으로만 흐르게 만든다.
  • 3
    우회 수단은 대가까지 함께 말한다 — @Lazy·ObjectProvider는 순환을 없애지 않고 해소 시점만 뒤로 민다. 잃는 것은 기동 시점 검증이라 배포는 초록불인데 몇 시간 뒤 특정 트래픽에서 터지고, 코드에서 순환이 보이지 않아 고리가 조용히 자란다. 그래서 부채로 기록하고 쓰는 임시 조치다.

0. 질문 + 출제 의도

질문: "Bean 순환 참조가 발생하는 원인과 해결 방법은?"

출제 의도: 순환 참조는 대부분 잘못된 책임 분배의 증상이다. @Lazy로 덮는 답과 설계를 고치는 답 중 무엇이 먼저 나오는지로 설계 감각을 본다. 에러를 없애는 법만 아는 사람과 에러가 가리키는 구조 문제를 읽는 사람을 가르는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① "필드 주입으로 바꾸면 된다"는 옛 정답 → 4절에서 Spring Boot 2.6부터 기본값이 false라 그 경로도 기동에 실패한다는 것을, 스위치의 소유자(코어 vs 부트)까지 구분해 못 박는다.
② "필드 주입은 왜 되는데"를 설명 못 하는 것 → 3절에서 3단계 캐시 11단계를 도식으로 따라가, ③에서 공개하고 ⑨에서 꺼낸다는 한 문장으로 압축한다.
③ 해결책을 나열만 하고 고르지 못하는 것 → 6절의 진단 결정 트리로 "두 빈이 서로에게 원하는 것"에 따라 처방이 갈리게 만든다. 나열이 아니라 선택이 답이다.
한 문장 비유 — 결재 교착, 그리고 화재경보기 결재 교착: 두 부서가 서로 "당신 부서장 서명이 먼저 있어야 우리가 서명한다"고 버티면 어느 쪽도 먼저 서명할 수 없다. 생성자 주입 순환이 정확히 이 상태다 — 게을러서가 아니라 시작점이 논리적으로 존재하지 않는다.  /  화재경보기: @Lazy는 불을 끄는 것이 아니라 경보기를 떼는 것에 가깝다. 소리는 멎지만 불은 그대로 있고, 다음에 발견되는 시점은 훨씬 늦다.
면접에서 순서를 뒤집으면 감점 @Lazy를 첫 번째 해결책으로 말하는 순간, 면접관이 듣는 것은 "해결책을 안다"가 아니라 "에러 메시지를 지우는 것을 해결이라고 부르는 사람"이다. 진단 → 설계 수정 → (그래도 안 되면) 우회 + 부채 기록 순서를 지키는 것 자체가 답의 절반이다.

1. 순환 참조란 무엇인가 — 고리의 모양부터 본다

순환 참조(circular dependency)는 빈들의 의존 관계를 화살표로 그렸을 때 출발한 자리로 돌아오는 고리가 생긴 상태다. A → B → A처럼 둘일 수도 있고, A → B → C → A처럼 셋 이상이 돌아 만드는 큰 고리일 수도 있다. 셋 이상짜리는 각 클래스만 따로 보면 아무 이상이 없어 보여서 눈으로 찾기가 훨씬 어렵다 — 그래서 5절의 로그 읽는 법이 실무에서는 더 중요해진다.

문제 가장 흔한 두 개짜리 형태 — 이 두 줄이 고리의 전부다
@Service
@RequiredArgsConstructor
public class OrderService {
    private final PaymentService paymentService;   // A는 B가 있어야 만들어진다화살표 A→B
}

@Service
@RequiredArgsConstructor
public class PaymentService {
    private final OrderService orderService;       // B는 A가 있어야 만들어진다화살표 B→A · 여기서 고리가 닫힌다
}

2. 생성자 주입은 왜 시작조차 못 하나

위 코드는 생성자 주입에서 애플리케이션이 시작조차 못 한다. 이유는 신비롭지 않고 논리적이다 — new OrderService(paymentService)를 호출하려면 인자로 넘길 "완성된 PaymentService"가 손에 있어야 하는데, 그것을 만들려면 다시 "완성된 OrderService"가 필요하다. 어느 쪽도 먼저 완성될 수 없다.

한 문장으로 봉인 — 실패의 성격을 바꿔 말한다

생성자 주입에서 순환이 기동 시점에 터져 주는 것은 단점이 아니라 조기 발견이라는 장점이다

면접에서 이 한 줄을 먼저 깔면, 뒤에 나오는 @Lazy 이야기가 "경보를 끄는 조치"로 자연스럽게 자리를 잡는다. 순서가 뒤집히면 같은 지식도 다르게 들린다.

3. 3단계 캐시 — 필드 주입 순환이 성립하는 진짜 메커니즘

"필드 주입은 되고 생성자 주입은 안 된다"의 진짜 답은 스프링이 싱글턴 빈을 담아 두는 세 개의 맵에 있다. DefaultSingletonBeanRegistry가 들고 있는 이 셋을 흔히 3단계 캐시라고 부른다.

암기 장치 — 3단계 캐시는 "완 · 조 · 팩", 조회는 내려가고 승격은 올라간다

1차 완성품(singletonObjects) · 2차 조기 참조(earlySingletonObjects) · 3차 팩토리(singletonFactories)

조회는 1 → 2 → 3으로 내려가고, 3차에서 만든 결과는 2차로 올라간다(승격). 이 두 방향만 정확히 말해도 "메커니즘을 안다"는 인상이 선다.

비유하자면 완공 전 아파트의 입주권이다. 건물(빈)은 아직 미완성인데, "이 자리에 들어설 그 건물"을 가리키는 권리증은 먼저 넘겨줄 수 있다. 나중에 건물이 완공되면 권리증이 가리키던 그 자리에 진짜 건물이 서 있으므로 결과적으로 아무 문제가 없다. 3단계 캐시가 하는 일이 정확히 이것이다.

3-1. 왜 굳이 3단계인가 — 미완성 객체를 2차에 바로 넣으면 안 되나

자연스럽게 따라오는 질문이고, 가산점이 붙는 지점이다. 3차 캐시가 보관하는 것이 객체가 아니라 팩토리인 이유는 AOP 프록시 때문이다.

객체를 그대로 2차에 넣는다면

  • 남에게 건네는 것은 원본 객체가 된다.
  • 그 빈이 @Transactional 대상이라면 최종 빈은 프록시인데, 남들이 붙든 것은 원본이다.
  • 같은 이름의 빈이 두 얼굴로 돌아다닌다 — 어떤 경로는 트랜잭션이 걸리고 어떤 경로는 안 걸린다.

팩토리를 넣으면 무엇이 달라지나

  • 팩토리는 실행되는 순간 "이 빈이 프록시 대상이면 프록시를 지금 미리 만들어 내보내라"를 수행한다.
  • 그래서 조기 참조도 최종 빈과 같은 정체(프록시)로 나간다.
  • 아무도 조기 참조를 요구하지 않으면 팩토리는 실행되지 않는다 — 프록시를 앞당겨 만드는 비용을 순환이 실제로 있는 경우에만 치른다.

그래도 실패하는 경우가 있다 — "순환 허용 = 안전"이 아니라는 근거 가산점

조기 참조를 넘겨준 뒤 초기화 과정에서 그 빈이 예상 밖의 후처리로 다른 객체에 감싸지면, 남들이 붙들고 있는 참조와 최종 빈이 서로 다른 객체가 된다. 스프링은 이 상황을 감지해 아래 메시지로 기동을 실패시킨다.

Bean with name '...' has been injected into other beans [...] in its raw version
as part of a circular reference, but has eventually been wrapped.

면접에서 "순환을 허용해도 안전이 보장되는 것은 아니다"의 구체적 근거로 쓸 수 있다. 허용은 성공을 보장하지 않는다 — 이 문장 하나가 allow-circular-references=true를 켜자는 주장의 근거를 무너뜨린다.

4. Spring Boot 2.6부터는 필드 주입 순환도 기본 금지다

여기가 옛 자료를 그대로 믿으면 안 되는 지점이다. 인터넷에는 아직도 "생성자 주입에서 순환이 나면 필드 주입으로 바꾸면 된다"는 글이 남아 있는데, 지금 기본 설정에서는 그렇게 해도 기동이 실패한다.

사실 관계를 정확히 나눠 두자. 순환 허용 여부를 정하는 스위치는 AbstractAutowireCapableBeanFactory.allowCircularReferences이고, Spring Framework 자체의 기본값은 true다. 그런데 Spring Boot는 2.6부터 이 값을 false로 뒤집어 놓는다. 즉 순환을 금지한 것은 프레임워크 코어가 아니라 부트의 판단이고, Boot 3.x도 이 기본값을 유지한다.

임시 우회 이 설정이 없으면(=기본값 false) 세터·필드 주입 순환도 기동에 실패한다
# application.yml
spring:
  main:
    allow-circular-references: true   # 임시 우회. 켰다는 사실 자체가 부채다켤 거면 이슈 번호와 만료일을 같이 남긴다

버전 사실 세 줄 — 이대로 말하면 "옛 자료를 보고 온 답"이 되지 않는다

스위치 이름
AbstractAutowireCapableBeanFactory
.allowCircularReferences
Framework 코어 기본값
true — 허용. 금지한 주체가 코어가 아니다
Boot 2.6+ 기본값
false — 부트가 뒤집었고 3.x도 유지

이 문서의 버전 의존 서술은 Spring Boot 3.x / Spring Framework 6.x 기준이며, 내부 구현 인용은 Spring Framework 6.2 소스를 확인한 것이다.

5. 에러 메시지를 읽어 문제의 클래스 쌍을 특정한다

기동 실패 로그는 길지만, 순환 참조일 때는 부트가 사이클을 그림으로 그려 준다. BeanCurrentlyInCreationFailureAnalyzer가 예외의 cause 사슬을 거슬러 올라가며 같은 빈 이름이 두 번 나오는 지점을 찾아 아래 형태로 출력한다.

***************************
APPLICATION FAILED TO START
***************************

Description:

The dependencies of some of the beans in the application context form a cycle:

┌─────┐
|  orderService defined in file [/app/classes/com/example/order/OrderService.class]
↑     ↓
|  paymentService defined in file [/app/classes/com/example/payment/PaymentService.class]
└─────┘

Action:

Relying upon circular references is discouraged and they are prohibited by default.
Update your application to remove the dependency cycle between beans. As a last resort,
it may be possible to break the cycle automatically by setting
spring.main.allow-circular-references to true.

로그 읽는 법 — 세 가지만 기억한다

① 고리의 구성원
┌와 └ 사이에 나열된 빈 이름이 전부다. 두 줄이면 두 개짜리, 다섯 줄이면 다섯 개가 도는 큰 고리. 화살표는 위→아래로 "이 빈이 아래 빈을 필요로 한다"이고 마지막 줄에서 첫 줄로 돌아온다.
② 걸린 자리
괄호가 알려준다. 클래스 파일 경로면 그 클래스 정의 자체, (field private ... OrderService.paymentService) 형태로 필드가 찍히면 그 필드가 문제의 주입 지점이다. 필드가 명시된 줄부터 보면 된다.
③ 끊을 화살표
셋 이상이면 "도메인 상식에 비추어 가장 어색한 화살표" 하나를 고른다. 보통 하위 개념이 상위 개념을 되부르는 역방향(알림이 주문을 부르는 식)이다. 고리의 화살표를 전부 손볼 필요는 없다.

6절의 처방은 이 "끊을 화살표"를 정한 뒤에 고르는 것이다. 순서가 반대면 "무엇을 고칠지"가 아니라 "무엇을 아는지"만 말하게 된다.

6. 1순위 해결 — 설계를 고쳐 의존을 단방향으로 만든다

순환을 발견하면 코드를 고치기 전에 질문 하나를 던진다. "A가 B에게 시키는 일과, B가 A에게 시키는 일이 각각 무엇인가?" 이 답에 따라 처방이 갈린다. 해결책을 네 개 나열하는 것과 진단 결과에 따라 하나를 고르는 것은 완전히 다른 답이다.

암기 장치 — 설계 처방 4종은 "추 · 이 · 역 · 병"

추출(제3의 컴포넌트) · 이벤트(사후 통지 절단) · 역전(인터페이스 소유 이동) · 병합(경계 다시 긋기)

순서에도 의미가 있다 — 앞쪽일수록 흔하고 앞쪽일수록 먼저 검토한다. 실무에서 부딪히는 순환의 상당수는 ①에서 끝난다.

6-1. ① 공통 책임을 제3의 컴포넌트로 추출한다

가장 흔한 원인이자 가장 자주 정답인 처방이다. A와 B가 서로에게 요구하는 기능을 들여다보면, 그것이 양쪽 어느 쪽의 고유 책임도 아닌 공통 하위 작업인 경우가 많다.

before 결제가 주문 상태를 바꾸려고 주문을 다시 부른다
@Service @RequiredArgsConstructor
public class OrderService {
    private final PaymentService paymentService;

    public void order(Long orderId) {
        paymentService.pay(orderId);
    }

    // 이 메서드 하나 때문에
    // PaymentService 가 OrderService 를 알아야 한다
    public void markPaid(Long orderId) { /* PAID 로 */ }
}

@Service @RequiredArgsConstructor
public class PaymentService {
    private final OrderService orderService;여기서 고리가 닫힌다

    public void pay(Long orderId) {
        // ... 결제 처리 ...
        orderService.markPaid(orderId);
    }
}
after "주문 상태 전이"에 자기 집을 만들어 준다
@Component @RequiredArgsConstructor
public class OrderStatusUpdater {양쪽 어디에도 의존하지 않는다
    // OrderService 도 PaymentService 도 모른다
    // → 고리에 참여할 수가 없다
    private final OrderRepository orderRepository;

    @Transactional
    public void markPaid(Long orderId) { /* PAID 로 */ }
}

@Service @RequiredArgsConstructor
public class OrderService {
    private final PaymentService paymentService;
    public void order(Long id) { paymentService.pay(id); }
}

@Service @RequiredArgsConstructor
public class PaymentService {
    private final OrderStatusUpdater orderStatusUpdater;제3의 빈에만 의존

    public void pay(Long orderId) {
        // ... 결제 처리 ...
        orderStatusUpdater.markPaid(orderId);
    }
}
언제 쓰나두 빈이 서로에게 요구하는 일이 도메인적으로 어느 한쪽의 고유 책임이 아닐 때. 순환의 가장 흔한 원인이므로 이것부터 검토한다.

6-2. ② 이벤트로 역방향 의존을 끊는다

markPaid 같은 상태 전이가 아니라 "결제가 끝났으니 알림도 보내고 포인트도 적립하라"처럼 뒤에 따라붙는 후속 작업이라면, 추출보다 이벤트가 맞다. 후속 작업은 앞으로 계속 늘어나는데, 늘어날 때마다 PaymentService의 의존성이 하나씩 늘어나는 구조를 만들고 싶지 않기 때문이다.

이벤트 발행은 "이런 일이 일어났다"는 사실만 컨테이너에 던지고, 누가 그것을 받아 무엇을 하는지는 신경 쓰지 않는 방식이다. 발행하는 쪽이 구독하는 쪽의 존재를 모른다는 점이 핵심이고, 그래서 컴파일 의존이 한 방향으로 끊긴다.

after PaymentService는 OrderService를 모른다 — 사실만 발행한다
@Service @RequiredArgsConstructor
public class PaymentService {
    private final ApplicationEventPublisher eventPublisher;받는 쪽을 모른다

    @Transactional
    public void pay(Long orderId) {
        // ... 결제 처리 ...
        // "결제가 완료됐다"는 사실만 던진다. 받는 쪽이 몇 개든 여기 코드는 안 바뀐다.
        eventPublisher.publishEvent(new PaymentCompletedEvent(orderId));
    }
}

@Component @RequiredArgsConstructor
public class PaymentCompletedListener {
    private final OrderRepository orderRepository;

    // AFTER_COMMIT: 결제 트랜잭션이 커밋된 뒤에만 실행하라는 뜻이다.
    // 커밋 전에 실행하면 "롤백됐는데 알림은 이미 나간" 사고가 난다.
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void on(PaymentCompletedEvent event) { /* 주문 상태 변경, 알림 등 */ }
}

이벤트로 갈아탈 때 반드시 짚어야 할 함정 둘 함정

① 스프링 이벤트는 기본이 동기다
publishEvent는 리스너를 같은 스레드에서 곧바로 호출하고 끝날 때까지 기다린다. "이벤트로 바꿨으니 비동기가 됐다"고 생각하면 느린 리스너가 그대로 응답 시간을 붙잡는다.
② AFTER_COMMIT 안의 DB 쓰기
조용히 반영되지 않을 수 있다. 이미 커밋이 끝난 트랜잭션에 얹혀 실행되기 때문이다. 순환을 없애려다 정합성 사고를 새로 만드는 대표적인 경로다.

그래서 이벤트로 갈아탈 때는 실행 시점과 실패 경로를 함께 설계해야 한다. 두 함정의 자세한 동작과 대응은 16-spring-event-transactional-event-listener.md가 다룬다.

언제 쓰나역방향 호출이 사후 통지 성격이고, 본 흐름이 그 결과값을 쓰지 않을 때. 반대로 결과를 받아 다음 분기를 해야 한다면 이벤트는 맞지 않는다 — 그때는 6-3으로 간다.

6-3. ③ 인터페이스를 호출하는 쪽에 두어 의존 방향을 뒤집는다

본 흐름 안에서 동기로 결과를 받아 써야 해서 이벤트가 맞지 않고, 그렇다고 공통 하위 작업으로 떼어낼 것도 아닌 경우가 있다. 이때 쓰는 것이 의존성 역전이다.

먼저 용어를 풀어 두자. 의존성 역전(Dependency Inversion)은 "구체적인 구현이 아니라 추상(인터페이스)에 의존하게 만든다"는 원칙이고, 핵심은 그 인터페이스를 누가 소유하느냐에 있다. 인터페이스를 호출하는 쪽 패키지에 두면, 호출하는 쪽은 자기 패키지 안의 인터페이스만 알면 되고 구현체가 사는 패키지를 몰라도 된다. 그러면 화살표가 뒤집힌다 — 원래 "호출하는 쪽 → 구현체"였던 컴파일 의존이 "구현체 → 호출하는 쪽의 인터페이스"가 된다. 이름의 "역전"은 이 화살표 방향이 뒤집힌다는 뜻이다.

비유 — 콘센트 규격은 전자제품 회사가 아니라 건물이 정한다건물이 "여기 꽂을 거면 이 모양이어야 한다"는 규격(인터페이스)을 자기 벽에 박아 두면, 건물은 어느 회사 제품이 꽂힐지 몰라도 되고 제품 쪽이 규격에 맞춰 온다. 인터페이스를 쓰는 쪽이 소유한다는 것이 이 처방의 전부다.
before 결제가 주문 정보를 조회해야 해서 OrderService를 직접 부른다
package com.example.payment;

@Service @RequiredArgsConstructor
public class PaymentService {
    private final OrderService orderService;   // com.example.order 를 직접 안다 — 순환

    public PaymentResult pay(Long orderId) {
        int amount = orderService.getPayableAmount(orderId);   // 결과가 바로 필요하다
        return charge(amount);
    }
}
after ① 필요한 능력을 결제 쪽이 정의한 인터페이스로 선언
package com.example.payment;

// 이 인터페이스는 결제 패키지가 소유한다.
// "결제가 남에게 요구하는 최소한의 능력"만 담는다
// — 주문 도메인 전체가 아니다.
public interface PayableAmountProvider {소유자 = 호출하는 쪽
    int getPayableAmount(Long orderId);
}

@Service @RequiredArgsConstructor
public class PaymentService {
    private final PayableAmountProvider amountProvider;
    // 자기 패키지의 인터페이스만 안다

    public PaymentResult pay(Long orderId) {
        return charge(amountProvider.getPayableAmount(orderId));
    }
}
after ② 구현체는 주문 쪽에 둔다 — 화살표가 order → payment
package com.example.order;

@Component @RequiredArgsConstructor
public class OrderPayableAmountProvider
        implements PayableAmountProvider {구현이 규격을 따라간다

    // ★ OrderService 가 아니라 저장소에 의존한다
    private final OrderRepository orderRepository;

    @Override
    public int getPayableAmount(Long orderId) {
        return orderRepository.findAmount(orderId);
    }
}

// 빈 그래프:
// OrderService → PaymentService
//              → OrderPayableAmountProvider → OrderRepository
// 고리 없이 흐른다.

흔한 실수 — 구현체가 다시 OrderService를 주입받으면 고리가 그대로 돌아온다 함정

OrderPayableAmountProvider는 OrderRepository 같은 하위 계층에만 의존해야 한다

인터페이스를 옮겨 놓고 구현체 안에서 원래 서비스를 주입받으면 빈 그래프에는 payment → order 화살표가 그대로 남는다. 구현체를 얇게 유지하는 것이 이 처방의 전제다.

언제 쓰나동기 호출이 필요하고 결과값을 본 흐름에서 써야 할 때. 모듈 경계를 유지하면서 순환만 끊고 싶을 때. 대가는 인터페이스와 구현체가 서로 다른 패키지에 흩어져 "구현을 찾아가기가 조금 번거로워진다"는 것 정도다.

6-4. ④ 애초에 한 책임이면 합친다

추출도 이벤트도 역전도 전부 어색하게 느껴진다면, 마지막 가능성을 봐야 한다. 두 클래스가 사실은 한 책임을 억지로 나눠 가진 것일 수 있다. 서로를 계속 부르면서 한 시나리오를 완성하고 있다면 그건 이미 한 덩어리다.

"쪼개져 있다 = 좋은 설계"가 아니다

응집도는 관련된 것이 함께 있는 정도를 말한다. 서로를 끊임없이 부르는 두 클래스는 응집도가 높은 하나를 억지로 둘로 자른 결과인 경우가 많다.

이때는 메서드를 한쪽으로 옮겨 병합하는 것이 정답이고, 그 결과 클래스가 너무 커진다면 원래 나눴던 선이 아니라 다른 선으로 다시 나눠야 한다는 뜻이다.

6-5. 처방 선택표

표는 고른 뒤 확인용이다. 고르는 과정은 위 결정 트리(6절 첫 도식)에 있다.
두 빈의 관계 (진단)처방남는 의존 방향주의할 점
양쪽이 같은 하위 작업을 서로에게 부탁① 제3의 컴포넌트 추출A → C ← BC가 A·B 어느 쪽도 몰라야 고리에 참여하지 않는다
B의 완료를 A에게 통지, 결과값은 불필요② 이벤트 발행/구독B → (이벤트) ← 리스너기본 동기 · AFTER_COMMIT DB 쓰기 미반영
B가 A의 정보를 동기로 받아 써야 함③ 인터페이스를 B 패키지에 두고 역전A → B (구현체가 따라감)구현체가 다시 A를 주입받으면 원위치
둘이 계속 왕복하며 한 시나리오를 완성④ 병합 후 다른 선으로 재분할고리 자체가 소멸합친 뒤 커지면 다른 기준으로 다시 나눈다

7. 차선책 — 우회 수단과 각각이 치르는 대가

설계 수정이 당장 불가능한 상황은 실제로 있다. 대규모 레거시라 파급이 크거나, 릴리즈 직전이거나, 순환의 한쪽이 우리가 못 고치는 라이브러리 빈일 수 있다. 그때 쓰는 수단들인데, 전부 "순환을 없애는 것이 아니라 해소 시점을 뒤로 미루는 것"이라는 공통점과 그에 따르는 대가가 있다.

7-1. @Lazy — 프록시를 끼워 넣어 시점을 미룬다

먼저 무엇이 주입되는지부터 정확히 하자. @Lazy가 붙은 주입 지점에는 진짜 빈이 아니라 프록시가 들어간다. 프록시는 원본인 척하는 대리인 객체로, 메서드 호출을 먼저 받아 그때 컨테이너에서 진짜 빈을 조회한 뒤 그 호출을 넘긴다.

차선책 프록시를 만드는 데는 진짜 상대 빈이 필요 없다 — 그래서 교착이 풀린다
@Service
public class PaymentService {
    private final OrderService orderService;

    public PaymentService(@Lazy OrderService orderService) {여기 들어오는 건 프록시
        // 프록시를 만드는 데는 진짜 OrderService 가 필요 없으므로
        // "완성된 상대가 있어야 나를 만들 수 있다"는 교착이 풀린다.
        this.orderService = orderService;
    }

    public void pay(Long orderId) {
        orderService.markPaid(orderId);   // 이 줄이 처음 실행되는 순간에야 진짜 빈을 찾는다문제는 여기서 처음 드러난다
    }
}

7-2. ObjectProvider — 지연 조회를 코드에 드러낸다

@Lazy와 원리는 같지만 지연이 타입에 드러난다는 점이 다르다.

차선책 숨지 않는다는 것 하나가 @Lazy보다 나은 점이다
@Service @RequiredArgsConstructor
public class PaymentService {
    // 타입 자체가 "지금 꺼내는 게 아니라 나중에 꺼내는 의존"이라고 말한다
    private final ObjectProvider<OrderService> orderServiceProvider;리뷰에서 바로 보인다

    public void pay(Long orderId) {
        orderServiceProvider.getObject().markPaid(orderId);
    }
}

나은 점

  • 코드 리뷰에서 ObjectProvider가 보이면 "여기 순환이 있구나"를 바로 안다.
  • 지연이 타입 시그니처에 드러나 다음 사람이 오해하지 않는다.

같은 점 / 나쁜 점

  • 사용하는 자리마다 getObject()가 붙어 코드가 조금 지저분해진다.
  • 순환은 여전히 그대로 있다 — @Lazy와 똑같이 시점만 미룬 것이다.

7-3. ApplicationContext를 직접 주입받아 조회 — 마지막 수단

지양 컨테이너 자체를 의존성으로 들고 다니게 된다
@Service @RequiredArgsConstructor
public class PaymentService {
    private final ApplicationContext context;이 클래스가 뭘 쓰는지 시그니처에서 사라진다

    public void pay(Long orderId) {
        context.getBean(OrderService.class).markPaid(orderId);   // 서비스 로케이터
    }
}

이 방식은 앞의 둘보다 확실히 나쁘다. 이유가 셋이다.

① 의존성이 사라진다
생성자 시그니처에서 무엇이 필요한지 알 수 없다. 메서드 본문을 다 읽어야 하고, "의존성을 공개 계약으로 드러낸다"는 이득이 통째로 없어진다.
② 테스트가 무거워진다
목을 넣으려면 ApplicationContext를 모킹해 getBean 호출까지 스텁해야 한다.
③ 호출 시점에 터진다
빈이 없으면 기동이 아니라 호출 시점에 실패한다. @Lazy와 같은 문제인데 타입 안전성까지 더 잃는다.
이 패턴에는 이름이 있다 — 서비스 로케이터(service locator)필요한 것을 주입받는 대신 "찾아 주는 창구"에 매번 물어보는 방식이라 그렇게 부른다. 의존성 주입이 해결한 문제로 되돌아가는 것이라 안티패턴으로 취급된다.

8. 우선순위 — 그리고 하지 말아야 할 것

8-1. 하지 말아야 할 것 — 필드 주입 전환으로 "해결"

spring.main.allow-circular-references=true를 켜고 필드 주입으로 바꾸면 에러 메시지는 사라진다. 하지만 이것은 경보기를 끄는 것이지 해결이 아니다.

손해를 세어 보면 거래가 얼마나 나쁜지 보인다

순환 구조는 그대로 남고, 여기에 더해 생성자 주입이 주던 것들을 한꺼번에 버린다.

불변성
final로 보장되던 것이 사라진다
완결성
컨테이너 밖에서 반제품 객체가 만들어질 수 있다
테스트
컨테이너 없이 도는 단위 테스트가 어려워진다
설계 신호
의존성이 늘어나는 것이 눈에 안 보인다

순환 하나를 덮으려고 코드베이스 전체의 주입 정책을 후퇴시키는 거래다. 면접에서 이것을 첫 번째 해결책으로 말하면 설계 감각을 의심받는다.

8-2. 우선순위를 한 줄로

설계 수정 (추 · 이 · 역 · 병)> ObjectProvider ≈ @Lazy (부채로 기록)> ApplicationContext 직접 조회> 필드 주입 전환 (사실상 금지)

우회를 쓰기로 했다면, 여기까지가 조치다

왜 순환이 있고 언제 걷어낼지를 주석과 이슈로 남기는 것까지가 조치다

기록이 없으면 다음 사람은 그것을 정상적인 구조로 오해한다. "임시"라고 쓰지 않은 임시 조치는 영구 구조가 된다.

예방책 — 기동 실패보다 한 단계 더 앞에서 막는다패키지 간 의존 방향을 테스트로 못 박아 두는 것이다. ArchUnit 같은 도구로 "payment 패키지는 order 패키지를 참조하지 않는다"는 규칙을 테스트로 만들어 두면, 순환이 만들어진 순간이 아니라 만들어지려는 순간에 CI가 잡는다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 면접 전날 이것만 — 질문을 보고 답을 먼저 떠올린 뒤 카드를 읽는다

순환 참조의 정의는?
의존을 화살표로 그렸을 때 출발한 자리로 돌아오는 고리. 둘일 수도, 셋 이상일 수도 있고 후자는 각 클래스만 보면 정상이라 로그 없이는 못 찾는다.
생성자 주입은 왜 실패하나?
인자로 넘길 완성본이 서로 필요해 시작점이 존재하지 않는다. BeanCurrentlyInCreationException — 버그가 아니라 조기 경보.
3단계 캐시는?
완 · 조 · 팩 — 1차 singletonObjects(완성품) · 2차 earlySingletonObjects(조기 참조) · 3차 singletonFactories(팩토리). 조회 1→2→3, 승격 3→2.
한 문장 메커니즘은?
③에서 공개하고 ⑨에서 꺼낸다 — 껍데기를 만든 직후 3차에 팩토리를 등록해 완성 전에 참조를 미리 공개하고, 상대가 요구할 때 그것을 꺼내 준다.
왜 3차가 객체가 아니라 팩토리인가?
AOP 프록시 때문. 조기 참조도 프록시여야 최종 빈과 같은 정체가 된다. 팩토리는 요구가 있을 때만 실행되므로 순환이 있을 때만 비용을 치른다.
Boot 버전 사실은?
스위치는 allowCircularReferences. Framework 코어 기본 true, Boot 2.6+ 기본 false(3.x 유지) — 그래서 필드 주입으로 바꿔도 기동 실패.
설계 처방 4종은?
추 · 이 · 역 · 병 — 추출(A→C←B) · 이벤트(사후 통지) · 역전(인터페이스를 호출하는 쪽에) · 병합(경계 재설정).
처방은 무엇으로 고르나?
"A가 B에게, B가 A에게 시키는 일이 각각 무엇인가." 사후 통지면 이벤트, 결과를 동기로 받아야 하면 역전, 공통 하위 작업이면 추출.
@Lazy의 대가는?
순환은 그대로, 시점만 이동. 잃는 것은 기동 시점 검증 — 배포는 초록불, 장애는 트래픽 시점. 더해서 코드에서 안 보여 고리가 자란다.
우선순위 한 줄은?
설계 수정 > ObjectProvider ≈ @Lazy(부채 기록) > ApplicationContext 조회 > 필드 주입 전환(사실상 금지).
셋 이상은 어디를 끊나?
도메인 상식에 비추어 가장 어색한 화살표 하나. 보통 하위가 상위를 되부르는 역방향. 전부 손볼 필요 없다.
예방은?
ArchUnit으로 패키지 의존 방향을 테스트로 못 박는다 — 기동 실패보다 한 단계 앞에서 CI가 잡는다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

필드 주입으로 바꾸면 에러가 사라지는데, 그럼 해결된 것 아닌가요? 함정힌트: "에러"와 "문제"를 분리하고, 버전 사실로 못을 박은 뒤, 관점 전환으로 마무리한다

에러가 사라진 것이지 문제가 사라진 것이 아니다. 순환이라는 구조는 그대로고, 컨테이너가 3단계 캐시로 미완성 참조를 미리 꺼내 억지로 이어붙여 준 것뿐이다.

그리고 지금은 그마저도 안 된다. Spring Boot 2.6부터 spring.main.allow-circular-references의 기본값이 false라서 필드 주입이어도 기동이 실패한다. 옛 자료를 보고 온 답이라는 인상을 주지 않으려면 이 버전 사실을 정확히 말하는 것이 좋다 — 덧붙여 금지한 주체는 프레임워크 코어가 아니라 부트이고(코어 기본값은 여전히 true), 프레임워크 스스로 "이 꼼수는 기본으로 켜 두지 말라"고 판단했다는 사실 자체가 근거가 된다.

마무리는 관점 전환으로 한다. "생성자 주입에서 순환이 기동 시점에 터져 주는 것은 단점이 아니라 조기 발견이라는 장점"이고, 그것을 끄는 방향의 조치는 진단이 끝난 뒤에 부채로 기록하고 쓰는 것이다.

필드 주입 순환을 스프링이 내부적으로 어떻게 조립해 주나요? 가산점힌트: 맵 세 개의 이름과 내용 → 조회·승격 방향 → "왜 팩토리인가" → 생성자 주입이 안 되는 이유

싱글턴 3단계 캐시로 답한다. 1차 singletonObjects는 완성된 빈, 2차 earlySingletonObjects는 이미 남에게 건네준 미완성 참조, 3차 singletonFactories는 그 미완성 참조를 만들어 낼 팩토리를 보관한다. 조회는 1차 → 2차 → 3차 순이고, 3차에서 만들어진 참조는 2차로 승격되면서 3차에서 제거된다(같은 미완성 참조를 두 번 만들어 서로 다른 객체가 돌아다니는 것을 막기 위해).

흐름은 A를 만드는 도중 B가 A를 요구하면 3차 캐시의 팩토리로 A의 조기 참조를 꺼내 B에 주입하고, B가 완성된 뒤 그 B를 A의 필드에 넣어 A도 완성시킨다.

3차가 객체가 아니라 팩토리인 이유까지 말하면 깊이가 드러난다. 그 빈이 AOP 대상이면 남에게 건넬 참조는 프록시여야 하는데, 프록시는 원래 초기화 후에 만들어진다. 팩토리는 실행되는 순간 프록시를 앞당겨 만들어 내보내고, 아무도 조기 참조를 요구하지 않으면 실행되지 않으므로 그 비용을 순환이 있는 경우에만 치른다.

그리고 생성자 주입은 이 메커니즘으로도 못 푼다. 조기 참조를 3차 캐시에 등록하려면 인스턴스가 일단 존재해야 하는데, 생성자 주입은 그 인스턴스를 만드는 것부터가 상대를 요구하기 때문이다.

@Lazy는 내부적으로 어떻게 순환을 끊나요? 대가는 없나요?힌트: 무엇이 주입되는지부터 말하고, "의존의 시점이 바뀐 것"으로 압축한 뒤 대가를 셋 댄다

진짜 빈 대신 프록시를 주입한다. 프록시를 만드는 데는 상대 빈이 필요 없으므로 생성 교착이 풀리고, 프록시의 메서드가 처음 호출되는 순간 컨테이너에서 실제 빈을 조회해 위임한다. 즉 "주입 시점의 의존"을 "사용 시점의 의존"으로 바꾼 것이다.

대가는 명확히 말해야 한다. 순환은 없어지지 않았고 해소 시점만 뒤로 밀렸다. 부팅에서 잡히던 문제가 특정 트래픽이 그 경로를 밟는 시점으로 옮겨가므로, 배포와 장애 사이에 시간 간격이 생겨 원인 추적이 어려워진다. 코드에서 순환이 보이지 않게 되어 사이클이 조용히 자라는 것도 대가이고, 프록시로 감쌀 수 없는 형태(final 클래스 등)면 그마저도 실패한다.

같은 원리를 타입에 드러내는 것이 ObjectProvider다. 순환이 그대로 남는다는 점은 똑같지만, 리뷰에서 "여기 순환이 있다"가 보인다는 이유로 @Lazy보다 조금 낫다.

순환 참조 에러를 만나면 설계에서 무엇부터 의심하나요? 시니어 변별힌트: 처방을 나열하지 말고, "무엇을 보고 고르는지"를 먼저 말한다

두 빈이 서로에게 원하는 것이 각각 무엇인지부터 적어 본다. 그 내용에 따라 처방이 갈리기 때문이다.

① 양쪽이 공유하는 하위 작업이 각자 안에 박혀 있다 → 제3의 컴포넌트로 추출한다. 가장 흔하고 대개 정답이다. "주문 상태 변경"처럼 어느 쪽의 고유 책임도 아닌 것이 한쪽 클래스에 얹혀 있는 경우다.

② "B가 끝나면 A가 반응해야 한다"는 사후 통지가 직접 호출로 구현돼 있다 → 이벤트로 역전한다. 단, 스프링 이벤트는 기본이 동기이고 AFTER_COMMIT 리스너의 DB 쓰기는 반영되지 않을 수 있다는 함정을 함께 알고 있어야 한다.

③ 동기로 결과를 받아 써야 해서 이벤트가 안 맞는다 → 인터페이스를 호출하는 쪽 패키지에 두어 의존 방향을 뒤집는다. 이때 구현체가 다시 원래 서비스를 주입받으면 고리가 그대로 돌아오므로, 구현체는 저장소 같은 하위 계층에만 의존하게 얇게 만든다.

④ 두 클래스가 계속 왕복하며 한 시나리오를 완성한다 → 애초에 경계를 잘못 그은 것이므로 병합한 뒤 다른 선으로 다시 나눈다.

마무리는 순서를 밝히는 것이다. @Lazy는 이 진단을 끝낸 뒤에도 당장 못 고칠 때 부채로 기록하고 쓰는 임시 조치이고, 우회를 먼저 말하고 설계를 나중에 말하면 순서가 뒤집힌 것이다.

셋 이상이 도는 순환은 어떻게 찾고 끊나요?힌트: 코드를 뒤지지 말고 로그를 읽는다 → 끊을 화살표를 고르는 기준 → 예방책

두 개짜리는 눈에 보이지만 A → B → C → A는 각 클래스만 보면 아무 이상이 없다. 그래서 부트의 실패 메시지를 읽는 것이 출발점이다. The dependencies of some of the beans in the application context form a cycle: 아래에 ┌와 └ 사이로 고리 구성원 전부가 순서대로 나열되고, 필드 주입이면 문제의 필드까지 괄호에 찍힌다.

끊을 지점을 고르는 기준은 "도메인 상식에 비추어 가장 부자연스러운 화살표"다. 보통 하위 개념이 상위 개념을 되부르는 화살표(알림이 주문을 부르고, 결제가 주문을 부르는 식)가 그렇다. 그 하나를 설계 처방 중 하나로 끊으면 고리가 열린다 — 고리를 이루는 모든 화살표를 다 손볼 필요는 없다.

여기에 예방책을 덧붙이면 좋다. 패키지 간 의존 방향을 테스트로 못 박아 두는 것이다. ArchUnit 같은 도구로 "payment 패키지는 order 패키지를 참조하지 않는다"는 규칙을 테스트로 만들어 두면, 순환이 만들어지는 순간이 아니라 만들어지려는 순간에 CI가 잡는다. 기동 실패보다 한 단계 더 앞에서 막는 셈이다.

@Lazy로 풀어 둔 순환은 운영에서 어떤 식으로 문제가 되나요? 시니어 변별힌트: 세 가지가 "순서대로" 온다 — 시점 이동 → 조용한 성장 → 초기화 순서 의존

첫째, 장애 시점이 배포에서 트래픽으로 옮겨간다. 부팅과 헬스체크는 통과하지만 실제 호출 경로에서 프록시가 처음 풀리는 순간 문제가 드러난다. 배포 직후가 아니라 몇 시간 뒤 특정 요청에서 터지므로 "방금 배포한 것과 관계있나"를 판단하기 어려워진다.

둘째, 사이클이 조용히 자란다. 코드 리뷰에서 순환의 존재가 보이지 않으므로 그 위에 의존이 계속 쌓여 두 개짜리였던 고리가 넷·다섯짜리가 된다. 그때는 끊을 지점을 고르는 것부터 어려워진다.

셋째, 초기화 순서에 암묵적으로 기대는 코드가 섞이면 "어쩌다 되는" 코드가 된다. @PostConstruct에서 상대 빈을 건드리는 로직이 대표적이다. 프록시가 아직 안 풀린 상태에서 호출되면 빈 조회가 그 자리에서 일어나며 예상치 못한 순서 문제를 만든다.

그래서 @Lazy를 쓸 때는 왜 순환이 있고 언제 걷어낼지를 주석과 이슈로 남기는 것까지가 조치라고 답한다.

클래스에 붙이는 @Lazy와 주입 지점에 붙이는 @Lazy는 같은 건가요? 함정힌트: 하나는 "언제 만들까"이고 다른 하나는 "무엇을 꽂을까"다

다른 이야기다. 빈 정의 쪽(@Component·@Bean)에 붙인 @Lazy는 "이 빈을 기동 때 미리 만들지 말고 처음 필요해질 때 만들어라"는 지연 초기화 지시다. 주입 지점(생성자 파라미터·필드)에 붙인 @Lazy는 "그 자리에 진짜 빈 대신 지연 프록시를 꽂아라"는 지시이고, 순환을 끊는 데 쓰는 것은 이쪽이다.

차이가 중요한 이유는, 빈 정의에 @Lazy를 붙여 두어도 다른 빈이 그 빈을 주입해 달라고 요구하는 순간 결국 만들어지기 때문이다. 즉 "미리 만들지 말라"만으로는 교착이 풀리지 않는다. 교착을 푸는 것은 "그 자리에 프록시를 꽂는다" 쪽이고, 대가(기동 시점 검증 상실)도 거기에 붙는다.

프로토타입 스코프 빈끼리 순환이면 어떻게 되나요? 가산점힌트: 3단계 캐시는 무엇을 위한 캐시였는지 되짚는다

스프링이 풀어 주지 못하고 BeanCurrentlyInCreationException으로 끝난다. 이유가 구조적이다 — 3단계 캐시는 싱글턴 레지스트리의 장치이고, 프로토타입 빈은 요청할 때마다 새로 만들어 컨테이너가 보관하지 않는다. 보관하지 않으니 "완성 전 참조를 공개해 둔다"는 수법 자체가 성립하지 않는다.

그래서 이 경우는 allow-circular-references를 켜는 것으로도 해결되지 않는다. 답은 하나뿐 — 설계를 고쳐 고리를 없애거나, 지연 조회(ObjectProvider)로 사용 시점에 꺼내 쓰는 것이다. "우회 스위치가 만능이 아니다"의 또 다른 근거로 쓸 수 있다.

순환을 정말 끊었는지는 무엇으로 확인하나요?힌트: "기동이 됐다"만으로는 부족하다 — 무엇이 켜져 있는지부터 본다

세 가지를 함께 본다.

① allow-circular-references가 꺼진 상태에서 기동이 되는가. 이 값이 true로 켜져 있으면 기동 성공은 아무것도 증명하지 않는다. 검증의 출발점은 스위치를 기본값(false)으로 되돌리는 것이다.

② 코드에 @Lazy·ObjectProvider·getBean()이 남아 있지 않은가. 셋 중 하나라도 그 고리 위에 남아 있으면 순환은 끊긴 것이 아니라 미뤄진 것이다.

③ 의존 방향이 테스트로 고정돼 있는가. ArchUnit 규칙으로 "payment는 order를 참조하지 않는다"를 못 박아 두면, 다음 사람이 같은 고리를 다시 만들려는 순간 CI가 막는다. 여기까지 해야 "고쳤다"가 "다시 안 생긴다"로 바뀐다.

한 줄 요약
순환 참조는 컨테이너의 버그가 아니라 "하나의 책임이 두 클래스에 찢어져 있다"는 설계 경보이며 — 세터·필드 주입에서 성립하던 것은 스프링이 3단계 캐시로 완성 전의 미완성 참조를 미리 노출해 서로를 이어붙여 준 덕분이지 문제가 없어서가 아니고, Spring Boot 2.6부터는 spring.main.allow-circular-references가 기본 false라 그 경로마저 기동에 실패한다 — 그러니 답은 부트가 그려 주는 사이클 메시지로 문제의 빈 쌍을 특정한 뒤 공통 책임 추출 · 이벤트 역전 · 인터페이스 소유 역전 · 병합 중 하나로 의존을 단방향으로 되돌리는 것이고, @Lazy와 ObjectProvider는 순환을 없애는 것이 아니라 첫 호출 시점으로 미루는 것이므로 진단을 끝낸 뒤 부채로 기록하고 쓰는 차선책이다.
