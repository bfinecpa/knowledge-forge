트랜잭션 동기화와 커넥션 바인딩 원리
한 트랜잭션의 쿼리는 어떻게 같은 커넥션을 타는가 — TransactionSynchronizationManager

면접 질문: "Spring의 트랜잭션 동기화(TransactionSynchronizationManager)와 커넥션 바인딩 원리를 설명해주세요."

핵심 관전 포인트 — @Transactional이 시작되면 트랜잭션 매니저가 풀에서 커넥션을 하나 얻어 TransactionSynchronizationManager의 ThreadLocal 리소스 맵(키가 DataSource 객체, 값이 ConnectionHolder)에 바인딩한다. 이후 JdbcTemplate·JPA·MyBatis 등 모든 데이터 접근 코드는 커넥션을 풀에서 직접 꺼내지 않고 DataSourceUtils를 경유해 "내 스레드에 바인딩된 커넥션이 있으면 그것을 재사용"한다 — 그래서 한 트랜잭션의 모든 쿼리가 같은 커넥션을 타고, 쿼리마다 close()를 불러도 안전하다. 반대로 이 규칙을 우회해 dataSource.getConnection()을 직접 부르면 트랜잭션 밖의 별개 커넥션이 나와 방금 쓴 데이터가 안 보이고 커넥션도 두 개를 점유한다. 저장소가 ThreadLocal이라는 사실에서 나머지 전부가 따라 나온다 — @Async로 스레드가 바뀌면 새 스레드의 리소스 맵이 비어 있어 트랜잭션이 전파되지 않고, 그렇다고 리소스 맵을 복사해 물려주면 JDBC 커넥션이 스레드세이프하지 않은 데다 원 트랜잭션 종료 시 풀로 반환된 커넥션을 제3의 요청과 나눠 쓰는 참사가 난다. 같은 저장소의 짝인 synchronizations에는 beforeCommit → beforeCompletion → 커밋 → afterCommit → afterCompletion 순서로 불리는 콜백이 등록되며, @TransactionalEventListener와 OSIV는 전부 이 기계 위에 얹힌 것이다.
  • 1
    구조부터 말한다 — @Transactional 진입 시 매니저가 풀에서 커넥션을 얻어 TSM의 ThreadLocal 리소스 맵에 DataSource 객체를 키로 바인딩하고, 이후 모든 데이터 접근은 DataSourceUtils.getConnection()을 경유해 "내 스레드에 바인딩된 것이 있으면 재사용"한다. 반납도 대칭이라 트랜잭션 소속 커넥션은 참조 카운트만 줄고 닫히지 않는다.
  • 2
    규칙을 우회하면 무슨 일이 생기는지로 이해도를 증명한다 — dataSource.getConnection()을 직접 부르면 별개 커넥션 = 별개 트랜잭션이라 ① 커밋 전이라 방금 쓴 데이터가 안 보이고 ② 커넥션을 두 개 점유해 풀이 절반의 트래픽에서 마르고 ③ 심하면 자기 자신과 락 대기에 걸린다.
  • 3
    저장소가 ThreadLocal이라는 한 문장에서 나머지를 연역한다 — @Async 경계에서는 새 스레드의 맵이 비어 있어 참여가 아니라 분리이고, 리소스를 물려주는 것은 비스레드세이프 + 풀 재대여 오염 때문에 금지다. 짝인 synchronizations의 콜백 5단계 + 마지막 언바인딩 순서가 @TransactionalEventListener와 OSIV를 떠받치는 하부 기계다.

1. 전제 지식 — ThreadLocal이라는 사물함

이 문서 전체가 ThreadLocal이라는 저장소 하나 위에 서 있다. 여기부터 정확히 잡고 가야 뒤의 모든 현상이 "외울 것"이 아니라 "따라 나오는 것"이 된다.

ThreadLocal은 스레드마다 각자 자기 값을 갖는 저장소다. 같은 변수 이름으로 읽어도 스레드마다 다른 값이 나온다.

private static final ThreadLocal<String> currentUser = new ThreadLocal<>();

// 스레드 A에서
currentUser.set("alice");
currentUser.get();   // "alice"

// 스레드 B에서 — 같은 static 필드를 읽는데
currentUser.get();   // null. A가 넣은 값이 안 보인다.여기서 모든 것이 시작된다

static 필드인데 스레드마다 값이 다르다는 것이 처음에는 이상하게 보인다. 이름이 오해를 부르는데, 값은 ThreadLocal 객체 안에 있는 것이 아니라 Thread 객체 안에 있다. 각 Thread는 ThreadLocalMap이라는 자기만의 맵을 들고 있고, ThreadLocal 인스턴스는 그 맵의 키로 쓰일 뿐이다.

1-1. 왜 하필 ThreadLocal에 두는가 — 대안을 그려보면 안다

스프링이 이 저장소를 고른 이유는 "요청 하나 = 스레드 하나 = 트랜잭션 하나"라는 전제 때문이다. 블로킹 방식의 Spring MVC에서 요청 하나는 톰캣 워커 스레드 하나가 처음부터 끝까지 처리한다. 컨트롤러 → 서비스 → 리포지토리로 내려가는 호출 스택 전체가 같은 스레드 위에 있다. 그러므로 "현재 스레드"는 곧 "현재 요청"이다.

대안을 그려 보면 이 선택의 값이 분명해진다.

대안 만약 스프링이 ThreadLocal을 안 썼다면 — 커넥션이 모든 시그니처를 오염시킨다
public Order placeOrder(Connection con, OrderRequest request) {
    orderRepository.save(con, order);
    couponRepository.use(con, couponId);
    pointRepository.deduct(con, userId, amount);
}
// 비즈니스 로직과 아무 상관 없는 Connection이 모든 메서드에 따라다닌다.
// 게다가 중간에 한 군데라도 다른 커넥션을 넘기면 트랜잭션이 조용히 쪼개진다.

용어 봉인 — "동기화(synchronization)"의 뜻부터 정확히

여러 스레드를 맞추는 동기화가 아니라, 트랜잭션 리소스를 스레드에 맞춰(동기화해) 두고 어디서든 꺼내 쓰게 하는 것

자바의 synchronized가 떠올라 "락 이야기인가?"로 오해하기 쉬운 지점이다. 면접에서 이 뜻을 먼저 정확히 짚고 들어가면, 뒤의 설명이 전부 같은 축 위에 정렬된다.

2. TransactionSynchronizationManager — 저장소의 실물

이름이 길어서 위압적이지만, 실제 클래스를 열어 보면 필드가 전부 static + ThreadLocal인 저장소 한 벌이다. 인스턴스를 만들 필요도 없는 abstract 클래스이고, 하는 일은 "현재 스레드에 무엇이 걸려 있는가"를 넣고 빼는 것뿐이다.

실물 필드가 전부 ThreadLocal이다 — 이것이 전부다
public abstract class TransactionSynchronizationManager {

    // ① 리소스 맵: 이 문서의 주인공. 키 = DataSource / EntityManagerFactory 객체
    private static final ThreadLocal<Map<Object, Object>> resources
            = new NamedThreadLocal<>("Transactional resources");커넥션이 여기 걸린다

    // ② 동기화 콜백 집합: 커밋 전후에 불릴 훅들 (9절)
    private static final ThreadLocal<Set<TransactionSynchronization>> synchronizations
            = new NamedThreadLocal<>("Transaction synchronizations");이벤트·OSIV의 하부

    // ③ 현재 트랜잭션의 메타 정보 — @Transactional의 속성이 여기 실려 다닌다
    private static final ThreadLocal<String>  currentTransactionName            = ...;
    private static final ThreadLocal<Boolean> currentTransactionReadOnly        = ...;
    private static final ThreadLocal<Integer> currentTransactionIsolationLevel  = ...;
    private static final ThreadLocal<Boolean> actualTransactionActive           = ...;
}

저장소는 두 칸이다 — 이 구분이 문서 전체의 뼈대

resources
"지금 무엇을 쓰고 있는가"
키 = DataSource/EntityManagerFactory 객체, 값 = ConnectionHolder/EntityManagerHolder. 5·6·7절의 주제.
synchronizations
"끝날 때 무엇을 할 것인가"
커밋 전후에 불릴 콜백 집합. @TransactionalEventListener가 여기 얹힌다. 9절의 주제.

면접 답변을 이 두 칸으로 나눠 시작하면 "구조를 눈으로 본 사람"처럼 들린다. 반대로 둘을 뭉뚱그리면 이벤트 리스너 얘기가 나올 때 연결이 끊긴다.

2-1. 리소스 맵은 상황마다 이렇게 생겼다

ConnectionHolder는 왜 커넥션을 한 겹 감싸는가 — 참조 카운트 홀더는 참조 카운트를 들고 있어서, 같은 트랜잭션 안에서 여러 번 getConnection()이 불려도 "몇 명이 이 커넥션을 쓰고 있는지"를 센다. 이 카운트가 있어야 5-2절의 "쿼리마다 close()를 불러도 실제로 닫히지 않는" 동작이 가능해진다. 즉 홀더는 커넥션의 소유권 관리자다.

3. 커넥션의 일생 — @Transactional 진입과 종료

@Transactional이 붙은 메서드에 프록시를 통해 들어가면(프록시를 통하지 않으면 아무 일도 안 일어난다 — 11-transactional-self-invocation.md), 트랜잭션 매니저의 doBegin()이 순서대로 네 가지 일을 한다. 그리고 끝날 때는 정확히 역순으로 정리된다.

암기 장치 — 진입 4단계는 "획 · 준 · 바 · 메"

획득(풀에서 커넥션) → 준비(setAutoCommit(false)) → 바인딩(bindResource) → 메타(플래그 + initSynchronization)

이 네 글자를 쥐고 있으면 "어느 단계가 안 일어났는가"로 문제를 나눌 수 있다 — 프록시를 안 타면 1단계부터 아예 없고, 스레드가 바뀌면 3단계의 결과가 안 보이며, 매니저가 다른 DataSource를 보고 있으면 3단계가 엉뚱한 키로 들어간다(4절).

4. 왜 키가 DataSource 객체인가 — 멀티 데이터소스

리소스 맵의 키를 문자열이나 상수로 두지 않고 DataSource 객체 자체로 둔 이유는 하나다. 데이터소스가 여러 개인 환경에서 각각 따로 바인딩하기 위해서다. 주 DB와 통계 DB를 함께 쓰는 구성을 보자.

설정 트랜잭션 매니저는 DataSource 하나에 하나씩 붙는다
@Configuration
public class DataSourceConfig {

    @Bean @Primary
    public DataSource mainDataSource() { /* 주문·회원 DB */ }

    @Bean
    public DataSource statsDataSource() { /* 통계 DB */ }

    // 매니저는 자기가 아는 DataSource "하나만" 트랜잭션으로 관리한다.
    @Bean @Primary
    public PlatformTransactionManager mainTxManager(DataSource mainDataSource) {
        return new DataSourceTransactionManager(mainDataSource);
    }

    @Bean
    public PlatformTransactionManager statsTxManager(DataSource statsDataSource) {
        return new DataSourceTransactionManager(statsDataSource);
    }
}
before 롤백해도 audit_log는 남는다 — 원인은 "키가 없다"는 사실 하나
@Service @RequiredArgsConstructor
public class StatsService {

    // @Transactional의 value는 "어느 트랜잭션 매니저를 쓸 것인가"다.
    // 생략하면 @Primary 매니저(= mainTxManager)가 선택되므로,
    // 통계 DB에 쓰면서 이 값을 빼먹으면 트랜잭션이 엉뚱한 DB에 열린다.
    @Transactional("statsTxManager")
    public void writeDailyStats(DailyStats stats) {
        statsJdbcTemplate.update("INSERT INTO daily_stats ...", ...);   // 바인딩된 #12 재사용 ✓

        mainJdbcTemplate.update("INSERT INTO audit_log ...", ...);main 키가 맵에 없다
        // → 풀에서 새 커넥션을 꺼내 auto-commit으로 즉시 확정된다.
        //   이 메서드가 아래에서 예외로 롤백돼도 이 INSERT는 남는다.
    }
}

멀티 DS의 단일 규칙 — "매니저가 모르는 DataSource는 트랜잭션 밖이다"

@Transactional이 관리하는 것은 지정된 매니저의 DataSource 하나뿐이다

나머지 데이터소스로 나가는 쿼리는 바인딩이 없으므로 auto-commit으로 즉시 확정된다. 여기에 매니저 이름을 빼먹으면 @Primary가 선택되어 "엉뚱한 DB에 트랜잭션이 열리는" 두 번째 사고가 겹친다.

두 DB를 하나의 원자적 단위로 묶으려면 선택지는 둘뿐이고 둘 다 대가가 있다.

ChainedTransactionManager — 원자성이 없다

  • 여러 매니저를 순서대로 커밋한다.
  • 첫 번째가 커밋된 뒤 두 번째가 실패하면 첫 번째는 이미 확정이라 되돌릴 수 없다.
  • 즉 최선 노력(best-effort) 순차 커밋일 뿐이고, 그래서 Spring Data에서 deprecated 됐다.

JTA / XA — 진짜 2단계 커밋, 대신 비싸다

  • prepare → commit의 2단계 커밋으로 진짜 원자성을 얻는다.
  • 대신 가용성이 두 시스템의 곱으로 떨어지고, prepare 이후 잠금 블로킹이 생긴다.
  • 상세는 23-transactional-outbox-pattern.md 1-5.
실무의 현실적인 답 — "묶지 않는 설계" 감사 로그처럼 정확성 요구가 다른 쓰기는 애초에 원자적으로 묶을 필요가 없는 경우가 많고, 정말 묶여야 하는 데이터라면 같은 DB에 있어야 한다는 신호로 읽는 편이 낫다. 면접에서는 "기술적으로 묶는 두 방법 + 각각의 대가 + 그래서 대개는 설계로 푼다" 순서로 답하면 균형이 잡힌다.

5. DataSourceUtils — 분기 하나가 전부다

3절에서 커넥션을 스레드에 걸어 뒀다. 이제 JdbcTemplate이 그것을 어떻게 찾아 쓰는지가 이 문서의 본론이다. 결론부터 말하면 JdbcTemplate은 dataSource.getConnection()을 부르지 않는다. 대신 DataSourceUtils.getConnection(dataSource)를 부르고, 그 안에는 분기가 딱 하나 있다.

5-1. 의사코드로 펼쳐 보기

얻을 때 getConnection
Connection getConnection(DataSource dataSource) {

    // ① "내 스레드에 이 DataSource로 바인딩된 커넥션이 있나?"
    ConnectionHolder holder = (ConnectionHolder)
        TransactionSynchronizationManager.getResource(dataSource);

    if (holder != null && holder.hasConnection()) {
        holder.requested();              // 참조 카운트 +1
        return holder.getConnection();   // ★ 그대로 재사용
    }여기가 답의 전부

    // ② 바인딩이 없다 = 트랜잭션 밖이다 → 풀에서 새로
    Connection con = dataSource.getConnection();

    // ③ 트랜잭션은 없고 "동기화만" 활성이면(OSIV 등)
    //    이 커넥션도 걸어 두고 정리 콜백을 등록한다
    if (TSM.isSynchronizationActive()) {
        holder = new ConnectionHolder(con);
        TSM.bindResource(dataSource, holder);
        TSM.registerSynchronization(
            new ConnectionSynchronization(holder, dataSource));
    }
    return con;
}

7. JPA와 JdbcTemplate을 한 트랜잭션에서 섞어 쓸 수 있는 이유

9. 동기화 콜백 — synchronizations 저장소가 하는 일

2절에서 본 두 번째 저장소가 이제 등장한다. 여기에는 트랜잭션의 특정 시점에 불릴 콜백이 등록된다.

직접 등록 등록만 하고 지금 실행되지는 않는다
@Transactional
public void placeOrder(OrderRequest request) {
    Order order = orderRepository.save(Order.of(request));

    // isSynchronizationActive()가 false면(= 트랜잭션 밖이면) IllegalStateException이 난다.
    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {

            @Override public void beforeCommit(boolean readOnly) {
                // 아직 커밋 전이다. 여기서 하는 DB 쓰기는 원 트랜잭션에 그대로 포함된다.
                // "커밋 직전에 마지막으로 검증하거나 파생 데이터를 남기는" 자리다.
            }

            @Override public void afterCommit() {
                // 커밋이 성공했을 때만 불린다. 캐시 무효화·알림 발송처럼
                // "확정된 뒤에만 해야 하는" 일의 자리다.
                // 여기서 예외를 던져도 커밋은 이미 끝나서 롤백되지 않는다.
                cacheManager.evict("orders", order.getId());
            }

            @Override public void afterCompletion(int status) {
                // 커밋이든 롤백이든 항상 불린다. try-finally의 finally에 해당한다.
                if (status == STATUS_ROLLED_BACK) metrics.increment("order.rollback");
            }
        });
}

앞뒤가 커밋을 기준으로 대칭이고, 맨 끝의 언바인딩만 콜백 바깥에 있다

가장 잘 나오는 함정 — afterCommit에서의 DB 쓰기는 조용히 사라진다

afterCommit이 실행되는 시점에도 커넥션은 아직 스레드에 바인딩된 채다(언바인딩은 콜백이 전부 끝난 뒤). 그래서 여기서 JPA로 엔티티를 수정하면 5절의 분기가 여전히 리소스를 찾아 주므로 코드는 에러 없이 잘 돈다.

그런데 트랜잭션은 이미 커밋이 끝났으므로 그 변경은 flush될 기회를 얻지 못하고 사라진다 — 에러가 안 나는 것이 이 버그의 가장 나쁜 점

확실히 저장하려면 @Transactional(propagation = REQUIRES_NEW)로 새 트랜잭션을 열어야 한다(12-transaction-propagation-required-vs-requires-new.md). 다만 REQUIRES_NEW는 기존 트랜잭션을 보류하고 새로 여는 것이라 그동안 커넥션을 2개 점유한다는 대가가 따른다.

9-1. @TransactionalEventListener는 이 기계 위에 얹힌 것이다

콜백을 직접 등록하는 코드를 실무에서 자주 쓰지는 않는다. @TransactionalEventListener가 그것을 감싼 편의 장치이기 때문이다.

@Transactional
public void complete(Long orderId) {
    ...
    eventPublisher.publishEvent(new OrderCompletedEvent(orderId));즉시 전달되지 않는다
    // 스프링은 이 이벤트를 즉시 리스너에 전달하지 않고,
    // registerSynchronization()으로 콜백에 등록해 뒀다가 지정된 phase에 실행한다.
}

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(OrderCompletedEvent event) { ... }
phase와 콜백의 대응은 그대로 1:1이다 — 편의 장치의 아래에 무엇이 있는지 보여주는 표
TransactionPhase실제로 불리는 콜백그 자리의 성격
BEFORE_COMMITbeforeCommit()아직 커밋 전 — 여기서의 DB 쓰기는 원 트랜잭션에 포함된다
AFTER_COMMIT 기본값afterCommit()확정 후 — DB 쓰기는 조용히 사라진다. 캐시 무효화·알림 발송의 자리
AFTER_ROLLBACKafterCompletion(STATUS_ROLLED_BACK)롤백된 경우에만
AFTER_COMPLETIONafterCompletion(...)커밋·롤백 공통의 finally 자리
그래서 앞의 함정이 @TransactionalEventListener에도 그대로 적용된다 AFTER_COMMIT 리스너에서의 DB 쓰기가 조용히 사라지는 현상, @Async를 붙이면 새 스레드라 바인딩이 없어져 일반 @Transactional로도 저장되는 차이 — 전부 이 절의 구조에서 나온다. 사용법·phase 선택·실패 경로 설계는 16-spring-event-transactional-event-listener.md가 본론이고, 여기서 기억할 것은 "그 편의 장치의 아래에 synchronizations 저장소와 네 개의 콜백이 있다"는 연결이다.

10. OSIV — 같은 바인딩 구조의 수명을 늘려 놓은 것 가산점

이 구조를 알면 OSIV(Open Session In View)가 무엇을 하는 장치인지도 한 문장으로 설명된다.

OSIV는 트랜잭션이 끝나도 EntityManagerHolder의 바인딩을 풀지 않고 HTTP 응답이 끝날 때까지 유지하는 장치다

스프링 부트의 spring.jpa.open-in-view 기본값이 true라 기본으로 켜져 있고, 구현은 OpenEntityManagerInViewInterceptor가 요청 시작 시 EntityManager를 만들어 2절에서 본 바로 그 리소스 맵에 바인딩하고 응답 완료 시 언바인딩하는 것이다. 즉 트랜잭션 경계와 영속성 컨텍스트 경계를 일부러 어긋나게 만든다.

이 문서에서 얻을 것 — OSIV는 별도의 마법이 아니다 지금까지 본 바인딩 구조의 수명을 늘린 것뿐이다. 면접에서 이렇게 연결해 말하면 "OSIV를 따로 외운 사람"이 아니라 "구조에서 연역한 사람"으로 읽힌다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

무엇이 어디에 바인딩되나?
TransactionSynchronizationManager의 ThreadLocal 리소스 맵에 키 = DataSource 객체, 값 = ConnectionHolder(참조 카운트 보유).
"한 트랜잭션 = 한 커넥션"의 실체는?
DataSourceUtils.getConnection()의 분기 한 줄 — 바인딩된 홀더가 있으면 그대로 재사용, 없으면 풀에서 새로.
쿼리마다 close()해도 안전한 이유?
반납도 대칭이라, 트랜잭션 소속 커넥션이면 released()로 카운트만 -1하고 닫지 않는다.
진입 4단계는?
획 · 준 · 바 · 메 — 획득 → 준비(setAutoCommit(false)) → 바인딩 → 메타·initSynchronization.
직접 getConnection()의 증상 3종은?
안 · 둘 · 락 — 방금 쓴 게 안 보인다 / 커넥션 둘을 점유(자기 교착) / 락 대기.
콜백 순서는?
beforeCommit → beforeCompletion → ★커밋 → afterCommit → afterCompletion → 언바인딩.
롤백 경로에서 빠지는 것은?
이름에 Commit이 든 둘(beforeCommit·afterCommit). Completion이 든 둘은 언제나 불린다.
afterCommit에서 JPA 쓰기를 하면?
에러 없이 돌지만 조용히 사라진다. 언바인딩이 콜백 뒤라 리소스는 찾아지는데, 커밋할 트랜잭션이 없다.
@Async + @Transactional은?
참여가 아니라 분리. 새 스레드의 맵이 비어 있어 완전히 별개인 새 트랜잭션이 열린다.
리소스를 물려주면 안 되는 이유 2종?
① JDBC 커넥션은 스레드세이프하지 않다 ② 풀 재대여 오염 — 반환된 커넥션을 제3의 요청과 나눠 쓴다.
멀티 DS에서 매니저가 모르는 DS는?
키가 없으니 풀에서 새 커넥션 + auto-commit. 롤백돼도 그 쓰기는 남는다.
OSIV를 한 줄로?
같은 바인딩의 수명을 응답 끝까지 늘린 것. 대가는 커넥션 반환 지연.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

멀티 데이터소스 환경에서는 어떻게 동작하나요? 필수힌트: "키가 무엇인가"에서 출발하면 "문제가 없다 → 그런데 이 경우엔 있다"로 자연스럽게 이어진다

리소스 맵의 키가 DataSource 객체이므로 데이터소스마다 따로 바인딩된다. 그래서 두 DB를 동시에 쓰는 것 자체는 아무 문제가 없다.

문제는 @Transactional이 관리하는 것은 지정된 트랜잭션 매니저의 DataSource 하나뿐이라는 점이다. @Transactional("statsTxManager") 안에서 main 데이터소스에 쿼리를 날리면 main 쪽에는 바인딩이 없으므로 풀에서 새 커넥션을 꺼내 auto-commit으로 즉시 확정된다 — 트랜잭션이 롤백돼도 그 쓰기는 남는다. 여기에 매니저 이름을 빼먹으면 @Primary 매니저가 선택되므로 엉뚱한 DB에 트랜잭션이 열리는 사고도 흔하다.

둘을 원자적으로 묶으려면 ChainedTransactionManager(순차 커밋일 뿐 원자성이 없어 deprecated)나 JTA/XA인데, 실무의 답은 대개 "묶어야 한다면 같은 DB에 있어야 한다"는 설계 신호로 읽는 것이다.

트랜잭션 없이 JdbcTemplate만 쓰면 어떻게 되나요? 필수힌트: 5절 분기의 ②로 간다. 나쁜 점만 말하지 말고 "그래서 좋은 경우"까지

5절 ①에서 바인딩을 못 찾으므로 ②로 간다. 쿼리마다 풀에서 커넥션을 꺼내 auto-commit으로 실행하고 즉시 반납한다.

함의가 둘이다. 첫째, 쿼리 하나하나가 각각의 트랜잭션이므로 여러 쿼리 사이의 원자성이 없다. 둘째, 커넥션 점유 시간이 최소라 읽기 전용 단순 조회에서는 오히려 효율적이다.

그래서 조회만 하는 메서드에 습관적으로 @Transactional을 붙이면 점유 구간만 길어지는 경우가 있다. "여러 쿼리가 하나의 일관된 스냅샷을 봐야 하는가"를 따져 보고 붙이는 것이 맞다.

@Async 메서드에 @Transactional을 붙이면 어떻게 되나요? 함정힌트: "참여 / 분리" 중 하나를 먼저 못 박고, 자기 호출 함정을 겹쳐 말한다

참여가 아니라 분리다. 새 스레드의 리소스 맵이 비어 있으므로 원 트랜잭션에 합류할 방법이 없고, 풀에서 새 커넥션을 꺼내 완전히 별개인 새 트랜잭션이 열린다. 원 트랜잭션이 롤백돼도 이쪽은 이미 커밋됐을 수 있다.

여기에 별개의 함정이 하나 더 겹친다. 같은 클래스 안에서 this.asyncMethod()처럼 자기 자신을 호출하면 프록시를 타지 않아 @Async와 @Transactional이 둘 다 무시된다. @Async가 무시되면 동기 실행이 되어 원 스레드에서 도는데, 이 경우엔 오히려 트랜잭션에 참여하게 되므로 "어떤 날은 되고 어떤 날은 안 되는" 것처럼 보이는 혼란이 생긴다.

진단의 첫걸음은 호출 경로가 프록시를 지나는지 확인하는 것이다(11-transactional-self-invocation.md). 그 다음이 "스레드가 바뀌었는가"다.

AFTER_COMMIT인데 롤백일 때도 남아야 하는 기록(감사 로그, 시도 이력)은 어떻게 하나요? 시니어 변별힌트: 선택지는 둘이고, 둘 다 "새 트랜잭션"이라는 같은 결론으로 수렴한다

AFTER_COMMIT은 롤백 시 아예 실행되지 않으므로 그 자리에 둘 수 없다. 선택지는 둘이다.

① AFTER_COMPLETION으로 옮긴다. 커밋이든 롤백이든 실행되고 status 인자로 어느 쪽인지 알 수 있다. 다만 이 시점은 원 트랜잭션이 이미 끝난 뒤라 여기서의 DB 쓰기는 9절의 함정에 걸린다 — REQUIRES_NEW로 새 트랜잭션을 열어야 실제로 저장된다.

② REQUIRES_NEW로 선커밋(write-ahead)한다. 작업을 시작하기 전에 별도 트랜잭션으로 "시도했다"는 기록을 먼저 커밋해 두는 방식이다. 본 트랜잭션이 롤백돼도 그 기록은 남는다. 시도 이력이나 외부 호출 로그처럼 실패 자체를 남겨야 하는 데이터에는 이쪽이 정석이다.

주의할 점은 REQUIRES_NEW가 기존 트랜잭션을 끝내는 것이 아니라 잠시 보류하고 새 트랜잭션을 여는 것이라, 그동안 커넥션을 2개 점유한다는 사실이다. 풀 크기가 동시 요청 수보다 작으면 자기 교착이 생길 수 있다.

TransactionSynchronization을 직접 등록해 본 적이 있나요? 콜백 순서를 말해주세요. 시니어 변별힌트: 순서만 읊으면 절반이다. 각 자리의 "성격"과 마지막 언바인딩까지 붙여야 한다

순서는 beforeCommit → beforeCompletion → 실제 커밋 → afterCommit → afterCompletion → 리소스 언바인딩이고, 롤백 경로에서는 beforeCommit과 afterCommit이 빠진다(이름에 Commit이 든 것들).

각 자리의 성격을 함께 말하면 좋다. beforeCommit은 아직 커밋 전이라 여기서의 DB 쓰기가 같은 트랜잭션에 포함되고, afterCommit은 확정 후라 여기서 예외를 던져도 되돌릴 수 없으며, afterCompletion은 커밋·롤백 공통의 finally 자리다.

가장 중요한 디테일은 언바인딩이 콜백 전부가 끝난 뒤에 일어난다는 것이다. 그래서 afterCommit에서 JPA 쓰기를 하면 리소스가 아직 붙어 있어 에러 없이 실행되지만, 커밋할 트랜잭션이 없어 조용히 사라진다. 이 함정을 설명할 수 있으면 구조를 실제로 이해한 것으로 읽힌다.

실무에서 직접 등록이 필요한 경우도 짚어 두면 좋다. @TransactionalEventListener는 이벤트 객체를 만들어 발행해야 하는데, 한 메서드 안에서 로컬 변수를 붙잡아 커밋 후에 쓰고 싶은 정도의 일이라면 익명 클래스로 registerSynchronization을 부르는 편이 짧다. 파일 업로드 후 커밋 실패 시 업로드된 파일을 지우는 정리 작업이 전형적인 예다 — afterCompletion에서 status를 보고 롤백이면 지운다.

OSIV는 이 구조와 어떤 관계인가요? 가산점힌트: "별도의 장치가 아니라 같은 구조의 수명 연장"이라는 한 문장으로 시작한다

OSIV는 같은 바인딩 구조의 수명을 요청 끝까지 늘려 놓은 것이다. OpenEntityManagerInViewInterceptor가 요청 시작 시 EntityManager를 만들어 리소스 맵에 바인딩하고 응답 완료 시 언바인딩하므로, 서비스 트랜잭션이 끝난 뒤에도 영속성 컨텍스트는 살아 있다. 그래서 컨트롤러와 JSON 직렬화 단계의 지연 로딩이 통과한다.

여기서 정확히 말해야 하는 것은 트랜잭션 경계와 영속성 컨텍스트 경계가 별개라는 점이다. OSIV는 둘을 일부러 어긋나게 만드는 장치다.

대가는 커넥션 반환 시점이다. 컨트롤러·응답 단계의 지연 로딩이 커넥션을 다시 요구하고, 그 커넥션이 요청 끝까지 붙잡힌다. 그 구간에 외부 API 호출 같은 느린 I/O가 있으면 아무 일도 하지 않는 커넥션을 그 시간만큼 점유하게 되어 풀이 마른다. 트레이드오프와 안전한 전환 절차는 03-jpa-orm/09-osiv-tradeoff-and-migration.md에 있다.

isActualTransactionActive()와 isSynchronizationActive()는 뭐가 다른가요? 가산점힌트: 2절의 저장소 두 칸이 각각 켜지는 조건이 다르다

두 플래그는 서로 다른 것을 묻는다. isActualTransactionActive()는 "진짜 트랜잭션이 열려 있는가"(커넥션이 잡히고 setAutoCommit(false)가 된 상태인가)이고, isSynchronizationActive()는 "동기화 기계가 켜져 있는가"(리소스 바인딩과 콜백 등록이 가능한 상태인가)다.

둘이 어긋나는 경우가 실제로 있다. propagation = SUPPORTS처럼 "트랜잭션이 있으면 참여하고 없으면 없는 대로 진행"하는 설정에서 바깥에 트랜잭션이 없으면, 스프링은 실제 트랜잭션 없이 동기화만 활성인 상태로 진행할 수 있다. 5절 의사코드의 ③번 분기(트랜잭션은 없는데 바인딩과 정리 콜백을 등록하는 자리)와 OSIV가 이 상태를 쓴다.

실무적 함의는 이렇다 — registerSynchronization()은 동기화가 활성이어야 부를 수 있고(아니면 IllegalStateException), 같은 이유로 @TransactionalEventListener는 트랜잭션 밖에서 발행된 이벤트를 기본적으로 처리하지 않는다(fallbackExecution 기본값이 꺼져 있어 조용히 건너뛴다). "이벤트가 안 왔어요"의 첫 번째 확인 지점이 여기다.

커넥션은 @Transactional 진입 즉시 잡히나요? 그 시점을 미룰 수는 없나요? 시니어 변별힌트: 3절 타임라인의 ①을 오른쪽으로 밀 수 있는가

기본 구성(DataSourceTransactionManager + 평범한 DataSource)에서는 진입 즉시 잡힌다. 3절 타임라인의 ①이 doBegin()의 첫 줄이고, 그 순간부터 점유 막대가 시작된다. 그래서 메서드 앞부분에 느린 계산이나 외부 호출이 있으면 그 시간만큼 아무 일도 안 하는 커넥션이 잡혀 있다(22번 문서의 주제).

미루는 장치가 있다. LazyConnectionDataSourceProxy는 DataSource를 한 겹 감싸서 바인딩 시점에는 실제 커넥션을 잡지 않고, 첫 쿼리가 실제로 나갈 때 비로소 풀에서 꺼내오게 한다. 점유 구간을 "메서드 전 구간"에서 "첫 쿼리 이후"로 줄일 수 있고, 읽기/쓰기 라우팅 데이터소스와 함께 쓸 때 트랜잭션 속성이 정해진 뒤에 실제 커넥션을 고르게 하려는 목적으로도 쓴다.

다만 도입 전에 정확히 알아야 할 것이 있다 — 이건 구조를 바꾸는 최적화라 커넥션 획득 실패가 메서드 진입이 아니라 첫 쿼리 시점으로 밀리는 등 실패 지점이 달라진다. 먼저 시도할 것은 "트랜잭션 경계 안에서 느린 일을 빼는" 설계 수정이고, 이 프록시는 그 다음이다.

스레드풀은 스레드를 재사용하는데, 이전 요청의 바인딩이 남아 있을 위험은 없나요? 함정힌트: 정상 경로에서는 왜 안전한가 → 그럼 언제 위험해지는가

정상 경로에서는 안전하다. 트랜잭션 매니저가 finally에 해당하는 정리 단계에서 반드시 unbindResource와 플래그 초기화를 수행하기 때문이다(3절 종료 ③·④). 예외로 끝나도 이 정리는 실행된다.

위험해지는 것은 이 대칭을 사람이 깨뜨렸을 때다. TransactionSynchronizationManager.bindResource()를 직접 호출해 놓고 unbindResource()를 빠뜨리면, 그 값은 스레드가 풀로 돌아간 뒤에도 남아 다음 요청이 "내 것이 아닌 커넥션"을 재사용하게 된다. 같은 이유로 커스텀 ThreadLocal(사용자 컨텍스트 등)도 반드시 finally에서 remove() 해야 한다.

이 계열의 위험(메모리 누수와 이전 요청 정보 유출) 전체는 01-java-kotlin/16-threadlocal-thread-pool-risks.md가 본론이다. 요약하면 "스레드풀에서 ThreadLocal은 반드시 짝을 맞춰 지운다"가 규칙이다.

같은 트랜잭션·같은 커넥션인데 JPA로 저장한 데이터가 JdbcTemplate 조회에서 안 나옵니다. 왜죠? 함정힌트: "같은 커넥션"과 "이미 DB로 보냈다"는 다른 말이다

커넥션은 같지만 SQL이 아직 DB로 전송되지 않았기 때문이다. JPA는 쓰기 지연으로 변경을 영속성 컨텍스트에 모아 뒀다가 flush 시점에 한꺼번에 보낸다. save()만 부른 상태에서는 DB 입장에서 그 행이 아직 존재하지 않는다.

해법은 entityManager.flush()로 "지금 SQL을 보내라"고 지시하는 것이다. flush()는 커밋이 아니다 — 트랜잭션은 여전히 열려 있고 롤백하면 함께 사라진다.

한 걸음 더 나가면 좋다. 이 함정은 "이중 바인딩 덕분에 두 기술을 섞을 수 있다"는 사실의 이면이다 — 커넥션 공유는 프레임워크가 보장하지만, 무엇이 이미 DB에 갔는지는 보장하지 않는다. 그래서 두 기술을 섞는 코드에서는 flush 시점을 의식적으로 관리해야 한다(03-jpa-orm/15-flush-timing-and-sql-ordering.md).

REQUIRES_NEW가 커넥션을 2개 쓴다면, 풀 크기를 키우면 해결되나요? 시니어 변별힌트: 완화책과 근본 해결을 나눠 말한다

완화는 되지만 해결은 아니다. 문제의 본질은 "한 요청이 동시에 몇 개의 커넥션을 쥐는가"이고, 그 값이 1보다 크면 동시 요청 수가 늘어날 때 서로가 서로를 막는 구간이 반드시 생긴다.

널리 인용되는 교착 회피 하한식이 이 관계를 잘 보여준다 — 풀 크기 ≥ 동시 스레드 수 × (한 스레드가 동시에 쥐는 커넥션 수 − 1) + 1. 한 스레드가 커넥션을 하나만 쥔다면 이 식은 1이 되어 교착 자체가 성립하지 않는다. 즉 근본 해결은 "동시에 쥐는 수를 1로 되돌리는 것"이다.

실무 순서는 이렇다 — ① REQUIRES_NEW가 정말 필요한지 재검토(대개는 "실패해도 남아야 하는 기록"이라는 요구에서 나온다) ② 필요하면 그 구간을 최대한 짧게 ③ 풀 크기는 그 다음. 풀만 키우면 DB 쪽 커넥션 상한과 컨텍스트 스위칭 비용으로 문제가 옮겨갈 뿐이다.

WebFlux(리액티브)나 가상 스레드에서도 이 구조가 그대로 성립하나요? 가산점힌트: 두 경우의 답이 다르다 — "스레드가 유지되는가"가 갈림길이다

가상 스레드(virtual thread)에서는 그대로 성립한다. 가상 스레드도 각자 자기 ThreadLocal 저장소를 갖기 때문에, 1절 그림의 구조가 바뀌지 않는다. 다만 "스레드가 싸졌다고 커넥션도 싸지는 것은 아니다"가 중요한 단서다 — 동시 처리량의 상한은 여전히 커넥션 풀 크기이고, 오히려 스레드가 많아진 만큼 커넥션 대기가 병목으로 드러나기 쉽다.

리액티브에서는 성립하지 않는다. 하나의 요청 처리가 여러 스레드를 옮겨 다니므로 "현재 스레드 = 현재 요청"이라는 전제 자체가 깨진다. 그래서 스프링은 리액티브 트랜잭션에서 ThreadLocal 대신 리액티브 스트림을 따라 흐르는 컨텍스트(Reactor Context)에 트랜잭션 컨텍스트를 실어 나르는 별도의 동기화 매니저를 쓴다.

면접에서 이 대비를 한 문장으로 정리하면 강하다 — "바인딩의 매체가 스레드냐 구독 컨텍스트냐가 다를 뿐, '트랜잭션 리소스를 어딘가에 걸어 두고 데이터 접근 코드가 그것을 찾아 쓴다'는 설계는 같다."

한 줄 요약
Spring 트랜잭션은 "풀에서 얻은 커넥션을 TransactionSynchronizationManager의 ThreadLocal 리소스 맵에 DataSource를 키로 바인딩해 두고, 모든 데이터 접근이 DataSourceUtils를 경유해 그것을 재사용"하는 구조라서 한 트랜잭션의 쿼리가 같은 커넥션을 타고 쿼리마다 close()를 불러도 안전하며, 이 규칙을 우회한 dataSource.getConnection()은 별개 커넥션·별개 트랜잭션을 만들어 방금 쓴 데이터가 안 보이고 커넥션도 두 개를 점유하게 만든다 — 저장소가 ThreadLocal이므로 스레드가 바뀌는 @Async 경계에서는 트랜잭션이 전파되지 않고 커넥션을 물려주는 것은 비스레드세이프와 풀 재대여 오염 때문에 금지이니 새 트랜잭션으로 분리해야 하며, 짝인 synchronizations 저장소의 beforeCommit → beforeCompletion → 커밋 → afterCommit → afterCompletion → 언바인딩 콜백 순서가 @TransactionalEventListener와 OSIV를 떠받치는 하부 기계다.
