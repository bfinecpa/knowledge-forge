@Async의 동작 원리와 주의점
"동시 처리가 8개에서 안 늘어나는" 스레드풀 함정과 조용히 묻히는 예외

면접 질문: "@Async의 동작 원리와 주의점(스레드풀 설정, 예외 처리, 프록시)은?"

핵심 관전 포인트 — @Async는 프록시가 메서드 호출을 가로채 톰캣 요청 스레드풀과는 별개인 TaskExecutor에 작업으로 던지고 호출자는 즉시 리턴하는 구조다. 여기서 실무 사고 네 가지가 전부 파생된다 — ① 스레드풀은 "바쁘면 스레드를 늘리는" 것이 아니라 "큐에 먼저 쌓고 큐가 넘칠 때만 늘리는" 순서라, 스프링 부트 기본 큐 용량이 Integer.MAX_VALUE인 채로 max-size만 올리면 동시 처리가 core-size(기본 8)에 영영 고정된다. ② void 리턴이면 예외가 호출자에게 전달될 길이 원천적으로 없어 로그 한 줄만 남고 묻힌다. ③ 트랜잭션·SecurityContext·MDC는 셋 다 ThreadLocal에 들어 있고 새 스레드는 자기만의 ThreadLocal을 갖기 때문에 하나도 넘어가지 않는다. ④ 큐가 JVM 힙 위에 있으므로 배포·크래시로 프로세스가 내려가면 대기 중이던 작업이 통째로 사라진다. 그래서 @Async는 "빨라 보이게 하는 도구"이지 "반드시 실행됨을 보장하는 도구"가 아니며, 내구성이 필요하면 RabbitMQ·Kafka 같은 브로커나 아웃박스 패턴으로 도구 자체를 바꿔야 한다.
  • 1
    구조부터 말한다 — @EnableAsync가 만든 프록시가 호출을 가로채 톰캣 요청 스레드풀과 완전히 별개인 TaskExecutor에 작업을 제출하고 기다리지 않고 즉시 리턴한다. 응답이 빨라지는 건 일이 줄어서가 아니라 점유하는 풀이 바뀌어서이고, 프록시 기반이므로 this.asyncMethod() 자기 호출은 조용히 동기로 돈다.
  • 2
    스레드풀은 "큐 먼저, 스레드 나중"이다 — core가 차면 스레드를 늘리는 게 아니라 큐에 넣고, 큐가 가득 차야 max까지 늘린다. 부트 기본 queue-capacity가 Integer.MAX_VALUE라 큐가 영원히 안 차므로 max-size는 도달 불가능한 설정이 되고 동시 처리는 core 8에 고정된다. 그래서 core · max · queue-capacity · 거부 정책은 넷이 한 세트다.
  • 3
    조용한 실패 3종을 짚는다 — void 예외는 AsyncUncaughtExceptionHandler 기본 구현이 로그 한 줄만 남기고 끝나고, ThreadLocal이라 트랜잭션·SecurityContext·MDC가 안 넘어가며, 큐가 JVM 힙 위라 재시작하면 대기 작업이 사라진다. 결론은 도구를 성능이 아니라 내구성 요구사항 기준으로 고른다는 것.

0. 질문 + 출제 의도

질문: "@Async의 동작 원리와 주의점(스레드풀 설정, 예외 처리, 프록시)은?"

출제 의도: 기본 스레드풀 방치(무제한 큐), 조용히 사라지는 예외, 프록시 제약 — 셋 다 운영에서만 터지는 유형이다. 비동기를 "빠르게 하는 마법"이 아니라 "관리해야 할 자원"으로 보는지 확인한다.

이 페이지가 겨냥하는 약점 세 가지 ① "별도 스레드에서 돈다"에서 멈추는 것 → 1·2절에서 그 스레드가 어느 풀 소속인지를 타임라인으로 못 박는다. 여기서 컨텍스트 미전파·용량 산정·CallerRunsPolicy가 전부 파생된다.
② 설정 세 숫자를 "그냥 크게 잡으면 되는 값"으로 아는 것 → 3·4절에서 분기 순서를 흐름도로 그려 "큐가 무한이면 max는 존재하지 않는 숫자"임을 눈으로 확인한다.
③ "CompletableFuture를 쓰면 안전하다"에서 끝내는 것 → 6절에서 리턴값을 버리면 void와 똑같이 묻힌다는 지점까지 밀어붙인다.
한 문장 비유 — 우편함, 그리고 은행 창구 우편함: @Async 호출은 편지를 사무실 우편함에 넣고 자리로 돌아오는 것이다. 내 손은 자유로워졌지만 편지는 아직 안 갔고(지연), 우체부가 언제 올지는 내가 모르며(순서 보장 없음), 그 우편함은 사무실 안 종이 상자라 불이 나면 통째로 탄다(8절 유실).  /  은행 창구: 창구 8개가 다 차면 창구를 더 여는 게 아니라 대기 번호표를 뽑게 하고, 대기 의자가 전부 차야 비로소 예비 창구를 연다 — 이것이 3절의 분기 순서다.
이 문서의 범위 — 형제 문서와의 경계 이 문서는 스레드풀 자체의 설정에 지면을 집중한다. 커밋 시점에 맞춰 비동기 작업을 태우는 이야기는 16-spring-event-transactional-event-listener.md, 스케줄러 스레드를 여러 작업이 공유해서 생기는 지연 전파는 34-scheduled-tasks-threading.md, 자기 호출 문제의 대안별 대가는 11-transactional-self-invocation.md에 있다. 셋 다 "요청 스레드가 아닌 다른 스레드에서 일이 돈다"는 같은 뿌리에서 나온 문제다.

1. 동작 원리 — 프록시가 호출을 가로채 "다른 풀"에 던진다

1-1. 전제 지식 — 프록시가 무엇인가

@Async를 이해하려면 프록시부터 알아야 한다. 프록시는 원본 객체인 척하면서 호출을 먼저 받아 부가 작업을 한 뒤 원본에 넘기는 대리인 객체다. 원본과 똑같은 타입이라 호출하는 쪽은 대리인인지 원본인지 구분하지 못한다.

@EnableAsync를 켜면 스프링은 @Async가 붙은 메서드를 가진 빈을 찾아 그 빈을 감싸는 프록시를 만들고, 컨테이너에 원본 대신 프록시를 등록한다. 다른 빈이 @Autowired로 주입받는 것은 원본이 아니라 이 프록시다. @Transactional이 트랜잭션을 열고 닫는 것과 완전히 같은 메커니즘이고, 프록시가 끼워 넣는 부가 작업만 다르다.

개념 @Async 프록시가 하는 일 (의사코드)
public void sendWelcomeMail(Long memberId) {
    // 원본 메서드를 지금 부르지 않는다. "나중에 부를 일감" 형태로 포장해 풀에 맡긴다.
    executor.submit(() -> target.sendWelcomeMail(memberId));여기가 전부다
    // 맡긴 일이 끝나기를 기다리지 않고 곧바로 호출자에게 돌아간다.
    // @Async가 응답을 빠르게 만드는 이유의 전부가 이 두 줄이다.
    return;
}

핵심은 진짜 메서드가 다른 스레드에서, 나중에(그 풀의 스레드가 비면) 실행된다는 것이다. 호출자는 제출만 하고 다음 줄로 넘어간다. 메일 발송·알림·이력 적재처럼 "응답을 늦출 이유가 없는 부가 작업"을 응답 경로에서 떼어내는 것이 @Async의 용도다.

1-2. 프록시 기반이라 자기 호출에는 무력하다

before 에러 없이 조용히 동기 실행
@Service
public class OrderService {

    public Order order(OrderRequest request) {
        Order order = save(request);
        this.sendWelcomeMail(order.memberId());프록시 통과 X
        // this는 프록시가 아니라 "원본 자신"이다.
        // 비동기 전환 코드는 프록시에만 있으므로
        // 이 호출은 그냥 같은 스레드에서 동기로 돈다.
        return order;
    }

    @Async
    public void sendWelcomeMail(Long memberId) { ... }
}
after 별도 빈으로 분리 — 정석
@Service
@RequiredArgsConstructor
public class OrderService {

    private final MailService mailService;주입 = 프록시

    public Order order(OrderRequest request) {
        Order order = save(request);
        // 주입받은 것은 원본이 아니라 프록시다 → 비동기로 돈다
        mailService.sendWelcomeMail(order.memberId());
        return order;
    }
}

@Service
public class MailService {
    @Async("mailExecutor")
    public void sendWelcomeMail(Long memberId) { ... }
}
함정의 성질 — 실패가 시끄럽지 않다 에러도 경고도 없이 조용히 동기로 실행되어 "비동기로 뺐는데 왜 응답이 여전히 느리지?"로만 드러난다. 원인과 해법(별도 빈 분리가 정석, 자기 주입·TransactionTemplate·AopContext 등 대안의 대가)은 @Transactional의 자기 호출 문제와 한 글자도 다르지 않으므로 11-transactional-self-invocation.md에 맡긴다.

@Async가 "안 먹는" 경우 체크리스트 — 전부 원인이 하나다

공통 원인은 단 하나, "프록시를 거쳐 들어오지 않았다"이다. 아래 넷 중 하나라도 걸리면 애너테이션은 예외도 로그도 없이 무시된다.

① @EnableAsync 누락
애초에 프록시를 만들지 않는다. 스프링 부트에서도 자동으로 켜지지 않는다.
② 자기 호출 (this.method())
프록시를 우회해 원본을 직접 부른다. → 별도 빈으로 분리.
③ private · final 메서드
프록시가 오버라이드할 수 없는 메서드는 가로챌 수 없다. public으로 연다.
④ 빈이 아닌 객체
new로 만든 인스턴스에는 컨테이너가 프록시를 씌울 기회 자체가 없다.

2. 두 개의 풀 — 톰캣 요청 스레드풀과 @Async 스레드풀은 완전히 별개다

의사코드의 executor가 정확히 무엇인지가 뒤에 나올 함정들의 출발점이다. 이 풀은 톰캣이 요청을 받아 처리하는 스레드풀과 아무 관계가 없다. 관리 주체부터 다른, 서로를 모르는 두 개의 풀이다.

2-1. 이 분리에서 파생되는 실무 포인트 셋

① 용량 산정은 따로
톰캣이 200개여도 비동기 작업의 동시 처리 상한은 async 풀의 core 8개다. 톰캣 스레드는 멀쩡한데 async 큐만 무한히 쌓이는 그림이 4절의 내용이다.
② CallerRunsPolicy는 이 경계를 뚫는다
큐가 넘쳐 거부가 발생하는 순간 호출자 — 즉 톰캣 요청 스레드 — 가 그 작업을 떠맡는다. 백프레셔는 공짜가 아니라 톰캣 풀을 담보로 잡는 거래다(5절).
③ 컨텍스트 미전파의 근본 원인
SecurityContext·MDC·트랜잭션 커넥션은 http-nio-…-exec-3의 ThreadLocal에 있고 task-1은 그 저장소에 접근할 방법이 없다(7절).

2-2. 스레드풀은 갈라져도 DB 커넥션풀은 공유한다 시니어 변별

풀이 둘로 갈렸다고 해서 자원이 전부 갈린 것은 아니다. async 워커가 DB를 쓰면 톰캣 스레드와 같은 HikariCP 인스턴스에서 커넥션을 가져간다.

암기 카드 — 스프링 부트가 관리하는 스레드풀은 셋이고, 기본값이 전부 다르다

2-3. 가상 스레드를 켜면 이 절의 전제가 바뀐다 가산점

Spring Boot 3.2부터 spring.threads.virtual.enabled=true를 주면 양쪽 다 가상 스레드로 바뀐다. 톰캣은 요청마다 가상 스레드를 만들어 쓰고, @Async는 풀링이 없는 SimpleAsyncTaskExecutor 계열로 대체된다.

정확한 표현은 "튜닝이 사라진다"가 아니라 "튜닝 지점이 이동한다" 논리적으로는 여전히 별개의 실행 경로지만 "고정 크기 풀"이라는 전제가 사라지므로 3·4절의 core/max/queue 튜닝 논의 자체가 무의미해진다. 대신 동시성 상한이 없어지니 병목은 그다음 자원 — 대개 커넥션풀이나 외부 API의 처리량 — 으로 이동한다. 이전에는 core 8이 자연스러운 동시성 제한 역할을 해줬다는 사실을 짚으면 이해도가 드러난다.

3. ★ 분기 순서 — 큐가 가득 차야 스레드가 늘어난다

실제 면접에서 "max-size를 100으로 올렸는데 동시 처리가 8개에서 안 늘어난다, 왜냐" 시나리오로 출제되는 파트다. 이 절의 흐름도 하나가 이 문서에서 가장 자주 인출되는 그림이다.

3-1. 전제 지식 — 세 개의 숫자가 각각 무엇인가

임시 인력까지 포함한 스레드 개수의 절대 상한.

여기까지는 이름만 봐도 짐작이 간다. 함정은 이 셋이 어떤 순서로 쓰이는가에 있다.

3-2. 판단 순서를 그대로 그리면 — 직관과 반대다

암기 장치 — 분기 순서는 "코 · 큐 · 맥 · 리"

코어(빈 자리 있으면 스레드 생성) → 큐(자리 있으면 적재, 스레드 안 늘림) → 맥스(큐가 찼을 때만 증설) → 리젝트(정책 호출)

이 네 글자를 쥐고 있으면 "max를 올렸는데 왜 안 늘어나죠?"에 "큐가 두 번째 관문이라 큐가 무한이면 세 번째 관문에 도달하지 못한다"고 즉답할 수 있다. 순서를 바꿔 말하면 답이 통째로 틀린다.

왜 이런 순서로 설계했나 — 근거까지 말하면 한 칸 올라간다 스레드를 새로 만드는 비용(스택 메모리 할당, OS 스케줄링 대상 추가)이 큐에 객체 하나를 넣는 비용보다 훨씬 크기 때문이다. 순간적인 부하 급증이라면 줄을 세워 흡수하는 편이 낫고, 줄이 넘칠 만큼 지속되는 부하일 때만 스레드를 늘리자는 판단이다. 은행 창구 비유가 그대로 들어맞는다 — 창구 8개가 다 차면 창구를 더 여는 게 아니라 번호표를 뽑게 하고, 대기 의자가 전부 차야 예비 창구를 연다.

4-1. 큐 용량은 무엇을 보고 정하는가 시니어 변별

100이라는 숫자는 어디서 나오는가. 큐 길이는 곧 "최악의 대기 시간"을 정하는 손잡이라는 관점으로 잡는다.

암기 공식 — 큐 길이를 대기 시간으로 환산한다

// 메일 발송 1건 = 평균 200ms 라고 하자
초당 처리 건수 = 스레드 수 ÷ 1건 처리 시간
              = 8 ÷ 0.2초  = 40건/초     (core 8개일 때)
              = 32 ÷ 0.2초 = 160건/초    (max 32개까지 늘어났을 때)

최악의 대기 시간 = 큐 길이 ÷ 초당 처리 건수
                = 100 ÷ 40 = 2.5초큐 100의 의미
즉 큐 100 = "메일이 최대 2.5초 늦게 나가는 것까지는 허용한다"는 선언이다

큐를 길게 잡으면

  • 거부가 거의 없어진다
  • 대신 대기 시간이 그만큼 길어진다
  • 스레드 증설이 늦게 시작된다
  • 힙 사용량이 커진다
  • 극단이 기본값 21억이고 그 결과가 이 절 앞부분

큐를 짧게 잡으면

  • 스레드가 빨리 늘어나 지연이 짧아진다
  • 대신 거부가 잦아진다
  • 극단은 SynchronousQueue(용량 0)
  • → 남는 스레드가 없으면 즉시 max까지 증설, 그마저 없으면 바로 거부
판단 기준은 작업의 성격이다 지연이 곧 사용자 불만인 작업(알림·인증 메일 발송)은 큐를 짧게 잡아 스레드를 빨리 늘리고, 지연이 아무래도 상관없는 작업(통계 집계, 캐시 워밍)은 큐를 넉넉히 잡아 스레드 수를 아낀다. 그래서 용도별로 풀을 분리(@Async("mailExecutor"))하는 것이 크기 튜닝의 전제가 된다 — 성격이 다른 작업을 한 풀에 섞으면 어느 쪽 기준으로도 못 잡는다.

5. 거부 정책 4종 — 그 순간 실제로 무슨 일이 벌어지는가

큐도 차고 max도 찬 순간 RejectedExecutionHandler가 호출된다. 네 가지 기본 구현이 각각 무엇을 하는지 정확히 알아야 한다 — 이름만 외우면 "유실을 아무도 모르게 만드는 정책"을 골라놓고 모를 수 있다.

정책그 순간 실제로 벌어지는 일작업의 운명
AbortPolicy 기본제출한 스레드에 RejectedExecutionException을 던진다실행 안 됨 — 단, 호출자가 실패를 인지한다
CallerRunsPolicy제출한 스레드가 그 자리에서 run()을 직접 호출한다실행됨 — 단, 호출자 스레드가 그동안 묶인다
DiscardPolicy아무것도 하지 않고 조용히 반환한다실행 안 됨 — 아무도 모른다
DiscardOldestPolicy큐 맨 앞(가장 오래된) 작업을 버리고 새 작업을 큐에 넣는다새 작업은 실행됨 — 가장 오래 기다린 작업이 희생

함정 — Discard 계열은 "유실을 아무도 모르게" 만든다

AbortPolicy가 기본인 이유는 "모르는 것보다 아는 것이 낫다"는 원칙 때문이다. 예외가 올라오면 최소한 로그와 지표에 남는다.

DiscardPolicy·DiscardOldestPolicy는 명시적인 근거 — 예를 들어 "1초마다 갱신되는 시세 스냅샷이라 오래된 건 버리는 게 맞다" 같은 — 없이는 쓰지 않는다. 특히 DiscardOldestPolicy는 가장 먼저 들어온 요청이 가장 먼저 버려지는 불공평한 특성이 있다.

5-1. CallerRunsPolicy의 양면 — 실무에서 가장 자주 고르는 정책

밝은 면 — 백프레셔가 공짜로 생긴다

  • 백프레셔(backpressure) = 하류가 소화하지 못할 때 상류의 유입 속도를 강제로 늦추는 장치
  • 풀이 포화되면 호출자가 직접 일하느라 다음 요청을 받지 못하니, 유입 속도가 처리 속도에 자동으로 맞춰진다
  • 작업을 버리지도 않는다 — 유실 0

어두운 면 — 그 호출자가 톰캣 요청 스레드다

  • 2절에서 두 풀이 별개라고 했는데, 이 정책은 그 경계를 의도적으로 허문다
  • 메일 발송이 2초 걸리면 그 요청 스레드는 2초 동안 새 요청을 못 받는다
  • async 풀의 포화가 톰캣 풀의 고갈로 번진다
  • 그 순간만큼은 비동기가 아니게 된다

한 문장으로 봉인 — CallerRunsPolicy의 정확한 설명

"버리지 않는 대신 톰캣 풀을 담보로 잡는" 거래이며, 그 순간만큼은 비동기가 아니게 된다

6. 조용한 실패 ① — 리턴 타입이 예외의 운명을 가른다

여기서부터는 설정이 아니라 "다른 스레드에서 나중에 실행된다"는 사실 자체가 만드는 문제다. 이 절부터 8절까지 셋은 예외도 경고도 없이 조용히 일어난다는 공통점이 있다.

@Async 메서드에서 던진 예외는 다른 스레드에서 터진다. 호출자는 이미 리턴받고 떠난 뒤이므로 예외가 호출자의 try-catch에 잡힐 방법이 원천적으로 없다. 그다음 예외가 어디로 가는지는 리턴 타입이 결정한다.

6-1. void — 담아 돌려줄 그릇 자체가 없다

6-2. CompletableFuture — 예외가 결과 객체에 담긴다

리턴 타입을 CompletableFuture로 바꾸면 예외의 행선지가 달라진다. 스프링이 작업을 CompletableFuture로 감싸 제출하기 때문에, 메서드 안에서 터진 예외는 사라지지 않고 그 Future 안에 "예외로 완료됨" 상태로 저장된다.

@Async
public CompletableFuture<MailResult> sendWelcomeMail(Long memberId) {
    // 여기서 예외가 나면 스프링이 그 예외를 잡아 반환될 Future에 담는다.
    // 스레드가 조용히 죽는 것이 아니라 "실패라는 결과"가 남는다.
    return CompletableFuture.completedFuture(doSend(memberId));
}

호출자가 그 예외를 수령하는 방법은 셋이고, 각각 예외가 다른 껍데기에 싸여 나온다.

CompletableFuture<MailResult> future = mailService.sendWelcomeMail(id);

// ① get(): ExecutionException으로 감싸여 나온다. 원인은 getCause()에 들어 있다.
try { future.get(); }
catch (ExecutionException e) { log.error("발송 실패", e.getCause()); }

// ② join(): CompletionException으로 감싸여 나온다. 체크 예외 선언이 필요 없다.
try { future.join(); }
catch (CompletionException e) { log.error("발송 실패", e.getCause()); }

//    ①②는 결과가 나올 때까지 호출자 스레드를 블로킹하므로,
//    "비동기로 뺀 이득"을 그 자리에서 반납하게 된다는 점에 주의한다.
future.exceptionally(ex -> { log.error("발송 실패", ex); return MailResult.failed(); });블로킹 없음

get()

7. 조용한 실패 ② — 컨텍스트 미전파, 원인은 셋이 아니라 하나다

@Async 메서드 안에서 트랜잭션도 안 이어지고, SecurityContext도 비어 있고, MDC의 trace id도 사라진다. 셋을 따로 외울 필요는 없다 — 원인이 하나이기 때문이다.

셋 다 ThreadLocal에 저장된다. ThreadLocal은 이름 그대로 스레드마다 별도의 저장 칸을 갖는 변수로, 같은 객체를 참조해도 스레드가 다르면 다른 값을 본다. 스프링이 요청 스코프의 정보를 메서드 인자로 일일이 넘기지 않고도 어디서든 꺼내 쓸 수 있게 만든 장치다.

7-1. 하나의 원인, 세 가지 증상

트랜잭션
스레드가 바뀌면 커넥션 바인딩이 없으므로 @Async+@Transactional은 호출자와 완전히 별개인 새 트랜잭션을 연다. 호출자가 롤백돼도 이쪽은 커밋될 수 있다.
SecurityContext
기본 전략 MODE_THREADLOCAL에서는 getAuthentication()이 null이 되어, @PreAuthorize가 붙은 메서드 호출이 권한 없음으로 실패한다.
MDC
요청마다 부여한 trace id가 비어 있어 비동기 구간부터 로그 추적이 뚝 끊긴다. "이 발송 실패 로그가 어느 요청 건인지 못 찾는" 형태로 대가를 치른다.
트랜잭션 쪽에는 타이밍 문제가 하나 더 붙는다 스프링의 트랜잭션은 커넥션(JPA라면 EntityManager)을 ThreadLocal에 묶어두고 같은 스레드의 쿼리들이 그것을 공유하게 하는 구조다(원리는 24-transaction-synchronization-connection-binding.md). 그래서 호출자가 커밋하기 전에 @Async 쪽이 먼저 실행될 수 있어, 방금 저장한 데이터를 조회했는데 안 보이는 문제까지 생긴다. 커밋 이후를 보장해야 한다면 이 조합이 아니라 16-spring-event-transactional-event-listener.md의 AFTER_COMMIT으로 시점을 고정해야 한다.

7-2. 해법 ① TaskDecorator — 제출 시점에 캡처해 실행 시점에 복원

TaskDecorator는 풀에 제출되는 모든 Runnable을 한 번 감쌀 수 있게 해주는 확장점이다. 감싸는 코드는 호출자 스레드에서 실행되므로, 그 시점에 컨텍스트를 복사해 두었다가 워커 스레드에서 되살릴 수 있다.

public class ContextCopyingDecorator implements TaskDecorator {

    @Override
    public Runnable decorate(Runnable task) {
        // ① 이 두 줄은 decorate()를 호출한 스레드 = 호출자(톰캣) 스레드에서 실행된다.
        //    그래서 아직 컨텍스트가 살아 있고, 지금이 복사할 수 있는 유일한 시점이다.
        Map<String, String> mdc = MDC.getCopyOfContextMap();
        SecurityContext security = SecurityContextHolder.getContext();캡처 = 호출자 스레드

        return () -> {
            // ② 이 람다 안은 워커 스레드에서 실행된다. 캡처해 둔 값을 자기 ThreadLocal에 심는다.
            try {
                if (mdc != null) MDC.setContextMap(mdc);
                SecurityContextHolder.setContext(security);
                task.run();
            } finally {
                // ③ 풀 스레드는 재사용된다 — 이 작업이 끝나면 같은 스레드가 다른 사용자의
                //    작업을 받는다. 안 지우면 A의 인증 정보로 B의 작업이 도는 보안 사고가 된다.
                MDC.clear();
                SecurityContextHolder.clearContext();이 청소가 핵심
            }
        };
    }
}

// 등록
executor.setTaskDecorator(new ContextCopyingDecorator());

가장 자주 빠뜨리는 것 — ③의 청소

톰캣도 스프링도 요청이 끝나면 자기 ThreadLocal을 청소해주지만, 내가 직접 심은 값은 내가 지워야 한다

풀 스레드는 재사용된다. 안 지우면 다음 작업에 앞 사용자의 인증 정보와 trace id가 묻어 들어간다 — 이건 버그가 아니라 보안 사고다. finally에서 지운다는 것까지가 이 코드의 요점이다.

7-3. 해법 ② 기성품 데코레이터를 쓴다

@Bean
public AsyncTaskExecutor mailExecutor() {
    ThreadPoolTaskExecutor delegate = new ThreadPoolTaskExecutor();
    // ... core / max / queue / 거부 정책 설정 (4절) ...
    delegate.initialize();
    // 이 래퍼가 제출 시점의 SecurityContext를 캡처해 워커 스레드에 심고,
    // 작업이 끝나면 원래 상태로 되돌려 놓는 일까지 대신한다.
    return new DelegatingSecurityContextAsyncTaskExecutor(delegate);청소까지 검증됨
}

SecurityContext만 필요하다면 Spring Security가 제공하는 DelegatingSecurityContextAsyncTaskExecutor로 기존 실행기를 감싸면 된다. 직접 짠 데코레이터와 달리 청소 로직까지 검증돼 있다. MDC까지 함께 옮겨야 하면 두 방식을 합치거나, 관측 라이브러리(Micrometer Context Propagation 등)가 제공하는 전파 장치를 쓴다. 어느 쪽이든 "제출 시점에 캡처해서 실행 시점에 복원하고 끝나면 청소한다"는 뼈대는 동일하다.

트랜잭션은 이 방식으로 옮기지 않는다 시니어 변별 커넥션은 복사할 수 있는 값이 아니라 한 번에 한 스레드만 써야 하는 자원이라, 두 스레드가 같은 커넥션을 동시에 쓰면 그때부터는 정합성 문제가 아니라 커넥션 상태 손상 문제가 된다. "컨텍스트 전파"라는 같은 이름 아래 두 종류가 섞여 있다는 점을 구분해야 한다 — 값(MDC·인증 정보)은 복사할 수 있고, 자원(커넥션)은 복사할 수 없다.

8. 조용한 실패 ③ — 인메모리 큐, 재시작하면 대기 작업이 통째로 사라진다

@Async의 큐는 JVM 힙 위에 있는 자바 객체다(LinkedBlockingQueue). 이 한 문장에서 판단 기준이 전부 나온다.

① 프로세스가 내려가면 큐도 사라진다
배포로 인한 재시작이든 크래시든 마찬가지다. 대기 중이던 작업은 흔적도 없이 없어지고, 실행 중이던 작업은 중간에 끊긴다.
② 다른 서버가 나눠 처리할 수 없다
큐가 그 서버 안에 있으므로 한 서버의 async 풀이 포화돼도 옆 서버는 그 사실조차 모른다. 처리량 상한이 그 서버의 스레드풀 하나로 고정된다.
그레이스풀 셧다운은 절반만 해결한다 server.shutdown=graceful을 켜면 진행 중인 요청은 기다려주지만, 그것은 톰캣 스레드의 이야기다. async 풀까지 안전하게 비우려면 setWaitForTasksToCompleteOnShutdown(true)와 setAwaitTerminationSeconds(...)를 별도로 줘야 하고, 그마저 대기 시간을 넘긴 작업은 결국 버려진다. 그리고 크래시에는 아무 대비도 되지 않는다.

8-1. 그래서 언제 메시지 큐로 갈아타는가

판단 기준@Async로 충분메시지 큐(RabbitMQ, Kafka)로
유실 허용유실돼도 재시도하거나 무시 가능 (캐시 워밍, 조회수 집계)유실 불가 (결제 후처리, 포인트 적립, 정산)
재시도·실패 추적불필요필요 — 재시도 큐와 DLQ로 실패 건을 붙잡아 둔다
처리 주체같은 프로세스 안에서 처리해도 됨별도 컨슈머로 분리·확장해야 함
부하 분산그 서버 한 대로 충분컨슈머를 늘려 여러 대가 나눠 처리
한 단계 더 — "DB 커밋과 메시지 발행이 원자적이어야 한다"면 주문은 저장됐는데 발행만 실패하는 사고를 막아야 하는 경우다. DB와 브로커는 서로 다른 시스템이라 하나의 트랜잭션으로 묶을 수 없으므로, 발행할 메시지를 같은 DB의 outbox 테이블에 INSERT해 비즈니스 변경과 한 트랜잭션으로 커밋하고, 별도 릴레이 프로세스가 그 테이블을 읽어 발행한다. 이것이 트랜잭셔널 아웃박스 패턴이고 23-transactional-outbox-pattern.md에서 다룬다.

이 절의 결론 — 도구 선택의 기준

@Async는 "빨라 보이게 하는 도구"이지 "반드시 실행됨을 보장하는 도구"가 아니다

도구를 성능이 아니라 내구성 요구사항을 기준으로 고르는 것이 이 파트의 핵심이다. 유실 허용 → @Async / 유실 불가 → 브로커 / DB와의 원자성까지 → 아웃박스 세 단계로 외운다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

@Async의 동작 원리 한 줄은?
프록시가 호출을 가로채 톰캣 풀과 별개인 TaskExecutor에 submit하고 즉시 리턴. 응답이 빨라지는 건 점유하는 풀이 바뀌어서다.
스레드풀 분기 순서는?
코 · 큐 · 맥 · 리 — core → 큐 → max → reject. "큐 먼저, 스레드 나중"이 전부다.
max를 올려도 안 늘어나는 이유는?
부트 기본 queue-capacity가 21억이라 큐가 영원히 안 차서 max 분기에 도달하지 못한다 → core 8 고정.
기본값 숫자 셋은?
톰캣 200 / @Async core 8 / @Scheduled 풀 1. (@Async max·queue는 둘 다 Integer.MAX_VALUE)
설정은 몇 개가 한 세트?
넷 — core · max · queue-capacity · 거부 정책. 큐를 제한하면 거부가 생기므로 정책 없는 제한은 미완성.
큐 길이는 어떻게 정하나?
최악 대기 시간 = 큐 길이 ÷ 초당 처리 건수. 큐 100 · 40건/초 → 2.5초를 허용하겠다는 선언.
거부 정책 4종은?
Abort(예외로 알림·기본) · CallerRuns(호출자가 실행) · Discard(조용히 버림) · DiscardOldest(가장 오래된 것 버림).
CallerRunsPolicy 한 줄 평은?
버리지 않는 대신 톰캣 풀을 담보로 잡는 거래이며, 그 순간만큼은 비동기가 아니게 된다.
void 예외는 어디로 가나?
AsyncUncaughtExceptionHandler. 기본 구현은 에러 로그 한 줄이라 사실상 묻힌다 → AsyncConfigurer로 지표·알림 연결.
get()과 join()의 차이는?
get()→ExecutionException, join()→CompletionException. 둘 다 getCause()에 원래 예외. 블로킹 없이는 exceptionally().
CompletableFuture면 안전한가?
아니다. 리턴값을 버리면 void와 똑같이 묻힌다 — 예외는 보관될 뿐 알려주지 않는다.
컨텍스트 3종이 안 넘어가는 원인은?
하나 — ThreadLocal. 트랜잭션·SecurityContext·MDC 전부 거기 있고 넘어가는 건 Runnable뿐.
재시작하면 큐는?
전부 유실. 큐가 JVM 힙 위의 객체라서다. 유실 불가면 브로커, DB 원자성까지면 아웃박스.
@Async가 안 먹는 4경우는?
@EnableAsync 누락 · 자기 호출 · private/final 메서드 · 빈이 아닌 객체. 공통 원인은 프록시 미통과.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

void @Async 메서드에서 예외가 나면 어디로 가나요? 어떻게 관측하나요? 필수힌트: "호출자에게 안 간다"의 이유를 두 겹으로 — 이미 떠났고, 그릇도 없다

호출자에게는 절대 전달되지 않는다. 호출자는 작업을 제출하고 이미 리턴받아 떠났고, void라 예외를 담아 돌려줄 그릇도 없기 때문이다.

예외는 AsyncUncaughtExceptionHandler가 받는데 기본 구현(SimpleAsyncUncaughtExceptionHandler)은 에러 로그 한 줄이라 사실상 조용히 묻힌다. 관측하려면 AsyncConfigurer를 구현해 커스텀 핸들러를 등록하고 로그와 함께 지표·알림을 태우거나, 애초에 CompletableFuture를 리턴하고 호출자가 exceptionally 등으로 결과를 소비하게 설계한다.

후자도 리턴값을 버리면 똑같이 묻힌다는 점까지 말해야 완결이다.

@Async가 쓰는 스레드풀은 톰캣 요청 스레드풀과 같은 건가요? 필수힌트: 다르다고만 하지 말고 여기서 파생되는 것 셋까지 — 용량·CallerRuns·ThreadLocal

완전히 별개다. 톰캣 풀은 서블릿 컨테이너가 관리하고(server.tomcat.threads.*, 기본 max 200, 이름 http-nio-…-exec-N), @Async 풀은 스프링 빈 applicationTaskExecutor다(spring.task.execution.*, 기본 core 8, 이름 task-N).

요청 스레드는 작업을 제출한 뒤 응답을 내보내고 풀로 반납되며, 실제 실행은 그 뒤에 워커 스레드에서 일어난다 — 응답이 빨라지는 건 일이 줄어서가 아니라 점유하는 풀이 바뀌어서다.

여기서 세 가지가 따라온다. ① 톰캣이 200개여도 비동기 동시 처리 상한은 core 8개라 용량 산정을 따로 해야 하고, ② CallerRunsPolicy는 그 경계를 뚫어 톰캣 스레드가 작업을 떠맡게 만들며, ③ ThreadLocal(SecurityContext·MDC·트랜잭션)이 안 넘어가는 이유도 결국 이 분리다.

단, 스레드풀은 갈라져도 HikariCP 커넥션풀은 공유하므로 async 풀만 키우면 병목이 커넥션풀로 옮겨간다는 점까지 말하면 완결이다.

max-size를 늘렸는데 동시 처리가 core 개수에서 안 늘어납니다 — 왜죠? 시니어 변별힌트: 분기 순서를 말로 그린 뒤, 기본값을 대입하고, 해결책에 거부 정책을 붙인다

ThreadPoolExecutor의 분기 순서 때문이다. core가 다 바쁘면 스레드를 늘리는 게 아니라 큐에 먼저 넣고, 큐가 가득 차야 max까지 스레드를 추가한다.

스프링 부트 기본 queue-capacity가 Integer.MAX_VALUE(사실상 무제한)라 큐가 영원히 안 차고, 따라서 max-size는 값이 얼마든 도달 불가능한 설정이 된다. 동시 처리는 core=8에 고정되고 나머지는 큐에서 무한 대기하며, 큐에 쌓인 객체가 힙을 잠식해 OOM까지 갈 수 있다.

해결은 queue-capacity를 유한하게 제한하는 것이고, 그 순간 거부 상황이 생기므로 거부 정책까지 한 세트로 설계해야 한다. 큐 길이는 "최악의 대기 시간 = 큐 길이 ÷ 초당 처리 건수"로 역산해 잡는다고 말하면 근거까지 갖춘 답이 된다.

큐까지 가득 차면 어떻게 되나요?힌트: 4종을 나열하되 각각 "작업의 운명"과 "누가 아는가"를 붙인다

RejectedExecutionHandler가 호출된다.

기본인 AbortPolicy는 RejectedExecutionException을 던져 호출자가 실패를 인지하게 한다. CallerRunsPolicy는 호출자 스레드가 그 작업을 직접 실행해 유입 속도가 자연히 줄어드는 백프레셔 효과를 내지만, 그 호출자가 톰캣 요청 스레드라면 async 풀의 포화가 톰캣 풀 고갈로 번진다는 대가가 있고 그 순간은 동기 실행이 된다.

DiscardPolicy는 조용히 버리고 DiscardOldestPolicy는 큐에서 가장 오래된 것을 버린다 — 유실을 아무도 모르게 되므로 명시적 근거 없이는 쓰지 않는다.

@Async와 @Transactional을 한 메서드에 같이 붙이면 어떻게 되나요? 함정힌트: "안 된다"가 아니라 "된다, 그런데 남남인 트랜잭션이 열린다"에서 시작

동작은 하지만 호출자 트랜잭션과는 완전히 별개다. 트랜잭션은 커넥션을 ThreadLocal에 묶는 구조라 스레드가 바뀌는 순간 남남이 되고, @Async 쪽은 자기 스레드에서 새 트랜잭션을 연다.

그래서 호출자가 롤백돼도 @Async 쪽은 커밋될 수 있고(역도 성립), 호출자 커밋 전에 @Async가 먼저 돌아 "방금 저장한 데이터가 안 보이는" 타이밍 문제도 난다.

커밋 이후를 보장해야 하면 @TransactionalEventListener(phase = AFTER_COMMIT)로 시점을 고정하고, 그 위에 @Async를 얹어 실행 스레드까지 분리한다(16-spring-event-transactional-event-listener.md). 유실까지 막아야 하면 아웃박스 패턴으로 설계를 바꾼다.

@Async 작업이 큐에 쌓인 채 서버가 재시작되면요? 필수힌트: "유실된다"에서 끝내지 말고 도구를 바꾸는 기준까지

전부 유실된다. @Async의 큐는 JVM 힙 위의 자바 객체라 프로세스가 내려가면 같이 사라지고, 실행 중이던 작업도 중간에 끊긴다. 재시도도 유실 감지도 없다.

setWaitForTasksToCompleteOnShutdown(true)로 정상 종료 시 큐를 비울 시간을 벌 수는 있지만, 대기 시간을 넘긴 작업은 결국 버려지고 크래시에는 아무 대비가 안 된다.

그래서 유실돼도 되는 작업(캐시 워밍, 통계 집계)에만 @Async를 쓰고, 유실 불가한 작업(결제 후처리, 포인트 적립)은 브로커가 디스크에 보존하고 ack 기반으로 재전달해주는 메시지 큐로, DB 커밋과의 원자성까지 필요하면 아웃박스 패턴으로 간다. 도구를 성능이 아니라 내구성 요구사항 기준으로 고르는 것이 답의 핵심이다.

같은 클래스 안에서 this.asyncMethod()를 부르면요? 함정힌트: @Transactional 자기 호출과 완전히 같은 원리라고 연결하면 한 번에 정리된다

비동기가 아니라 조용히 동기 실행된다. 비동기 전환 코드는 프록시에 있는데 this 호출은 프록시를 거치지 않고 원본을 직접 부르기 때문이다 — @Transactional의 자기 호출 미적용과 완전히 같은 원리다.

에러가 없어서 "비동기로 뺐는데 응답이 안 빨라진다"로만 드러난다. 해결은 해당 메서드를 별도 빈으로 분리하는 것이 정석이며, 대안들의 대가는 11-transactional-self-invocation.md에 정리돼 있다.

@Async를 붙였는데 아무 일도 안 일어납니다 — 무엇부터 점검하나요? 함정힌트: 원인 넷을 나열하되, 공통 원인 하나로 묶어서 말한다

넷을 순서대로 본다. 공통 원인은 하나 — "프록시를 거쳐 들어오지 않았다"이다.

① @EnableAsync 누락 — 애초에 프록시를 만들지 않는다. 스프링 부트에서도 자동으로 켜지지 않으므로 설정 클래스에 명시해야 한다.
② 자기 호출 — this.method()는 프록시를 우회한다. 별도 빈으로 분리한다.
③ private·final 메서드 — 프록시가 오버라이드할 수 없는 메서드는 가로챌 수 없다. public으로 연다.
④ 빈이 아닌 객체 — new로 만든 인스턴스에는 컨테이너가 프록시를 씌울 기회 자체가 없다.

확인 방법도 한 줄 붙이면 좋다 — 메서드 안에서 Thread.currentThread().getName()을 찍어보면 http-nio-…-exec-N이면 동기, task-N/mail-N이면 비동기다. 추측 대신 스레드 이름으로 판정한다.

@Async 메서드의 리턴 타입은 아무거나 써도 되나요? 함정힌트: "호출 즉시 리턴한다"는 사실에서 가능한 리턴 타입이 논리적으로 결정된다

사실상 void와 Future 계열(CompletableFuture 포함) 둘뿐이다. 호출자는 작업이 시작되기도 전에 리턴받으므로, 그 시점에 실제 값이 존재할 수가 없다. 값을 돌려주려면 "나중에 채워질 그릇"을 리턴하는 수밖에 없고 그 그릇이 Future다.

그래서 String이나 도메인 객체를 리턴 타입으로 선언하면 컴파일은 되지만 호출자는 실제 결과를 받을 수 없다. 결과가 필요 없으면 void, 결과나 실패를 받아야 하면 CompletableFuture — 선택지는 이 둘이라고 정리하면 된다.

큐가 함정이라면 core-size를 아주 크게 잡아버리면 되지 않나요? 시니어 변별힌트: "그러면 큐 분기 전에 스레드가 만들어지긴 한다"를 인정한 뒤, 대가를 센다

효과는 있다 — core가 크면 큐 분기에 가기 전에 스레드를 만들므로 동시 처리는 실제로 늘어난다. 문제는 대가다.

① core 스레드는 일이 없어도 유지된다(원하면 allowCoreThreadTimeOut(true)로 회수 가능하게 만들 수 있다). 스레드마다 스택 메모리를 잡고 있으므로 평시에 놀고 있는 인력이 그대로 비용이 된다.
② 스레드가 많아지면 컨텍스트 스위칭 비용이 늘어 오히려 처리량이 떨어질 수 있다.
③ 결정적으로 다음 자원이 못 버틴다 — 워커 200개가 동시에 DB를 치면 HikariCP 10개 앞에 줄을 서고, 그 대기가 요청 처리 쪽 커넥션까지 잠식한다(2-2절).

그래서 올바른 순서는 "core를 키운다"가 아니라 "하류 자원이 감당할 수 있는 동시성을 먼저 정하고, 그 값에 맞춰 max를 잡은 뒤, 큐로 버스트를 흡수한다"이다. 스레드풀 크기는 스레드의 사정이 아니라 하류 자원의 사정으로 정한다.

비동기 작업이 밀리고 있다는 걸 어떻게 알아채나요? 가산점힌트: 에러율·응답 시간에는 안 잡힌다는 것부터 말한다

일반적인 지표에는 안 잡힌다는 점이 출발점이다. 큐가 무제한이면 거부도 예외도 없고 응답 시간은 오히려 좋아 보인다. 그래서 전용 지표를 내가 만들어야 한다.

① 큐 길이와 활성 스레드 수 — ThreadPoolTaskExecutor에서 직접 꺼내(getThreadPoolExecutor().getQueue().size(), getActiveCount()) 지표로 내보낸다. Micrometer가 실행기를 계측하도록 붙여두면 큐 적재량·활성 수·완료 건수를 대시보드에 올릴 수 있다.
② 제출 시각과 실행 시작 시각의 차이(큐 대기 시간)를 작업 안에서 직접 기록한다 — "몇 건 쌓였나"보다 "몇 초 늦게 시작했나"가 사용자 체감에 직결된다.
③ 스레드 덤프 — setThreadNamePrefix를 용도별로 지정해 두면 덤프 한 장으로 막힌 것이 요청 스레드인지 메일 워커인지 즉시 구분된다.
④ 실패 카운터 — AsyncUncaughtExceptionHandler에서 올리는 async.failure 지표(6절).

알림 임계치는 "큐 길이 > 큐 용량의 50%가 N분 지속"처럼 추세로 잡는다. 순간 피크는 정상 동작이고, 줄지 않는 것이 사고 신호다.

TaskDecorator로 SecurityContext를 옮겼는데, 트랜잭션도 같은 방법으로 옮길 수 있나요? 함정힌트: 넘기려는 것이 값인가 자원인가

옮기지 않는다. MDC 맵이나 SecurityContext는 복사해도 되는 값이지만, 커넥션(또는 EntityManager)은 한 번에 한 스레드만 써야 하는 자원이다.

두 스레드가 같은 커넥션을 동시에 쓰면 그때부터는 정합성 문제가 아니라 커넥션 상태가 손상되는 문제가 된다 — 한쪽이 커밋/롤백을 하는 동안 다른 쪽이 쿼리를 날리는 식이라 결과를 예측할 수 없다.

그래서 비동기 구간에서 DB를 써야 하면 그 스레드에서 자기 트랜잭션을 새로 여는 것이 정답이고, 호출자 트랜잭션의 커밋 이후를 보장해야 한다면 전파가 아니라 @TransactionalEventListener(AFTER_COMMIT)로 시점을 고정하는 방향으로 푼다.

비동기 작업 안에서 다른 비동기 작업의 결과를 기다리면(get()) 어떻게 되나요? 시니어 변별힌트: 두 작업이 같은 풀을 쓰고 있다면?

같은 풀을 공유하면 스레드 고갈로 인한 교착이 생길 수 있다. 워커 스레드가 하위 작업을 제출한 뒤 그 결과를 기다리며 블로킹하는데, 하위 작업은 같은 풀의 빈 스레드를 기다린다. 부모 작업들이 풀을 전부 점유하고 있으면 아무도 진행하지 못한다.

core 8짜리 풀에서 부모 작업 8개가 각각 자식 작업의 결과를 기다리면, 자식 8개는 영원히 큐에서 대기한다 — 큐가 무한이라 거부조차 나지 않고 조용히 멈춘다.

해법은 셋이다. ① 부모와 자식을 다른 풀로 분리한다(가장 확실하다). ② 블로킹 대기 대신 thenCompose·thenCombine 같은 논블로킹 조합을 쓴다. ③ 굳이 기다려야 한다면 get(timeout)으로 무한 대기를 막는다. 원칙은 "풀 안에서 그 풀을 기다리지 않는다"이다.

가상 스레드를 켜면 이 튜닝은 다 필요 없어지나요? 가산점힌트: "필요 없어진다"가 아니라 "이동한다" — 어디로 이동하는지 지목한다

Spring Boot 3.2 이상에서 spring.threads.virtual.enabled=true를 주면 @Async가 풀링 없는 실행기로 바뀌므로 core/max/queue라는 손잡이 자체가 사라진다.

하지만 "튜닝이 필요 없어진다"가 아니라 "튜닝할 지점이 이동한다"가 맞다. 스레드가 사실상 무제한이 되면 동시 실행 수를 막아주던 방벽이 없어지므로, 병목은 그다음 유한한 자원 — HikariCP 커넥션풀, 외부 API의 처리량, DB의 동시 처리 능력 — 으로 옮겨간다.

이전에는 core 8이 자연스러운 동시성 제한 역할을 해줬다는 사실을 짚으면 이해도가 드러난다. 그래서 가상 스레드 환경에서는 세마포어나 레이트 리미터처럼 명시적인 동시성 제한 장치를 따로 두는 판단이 필요해진다.

한 줄 요약
@Async는 프록시가 호출을 가로채 톰캣 요청 스레드풀과는 별개인 인메모리 큐에 작업을 던지고 즉시 리턴하는 구조이며, 자기 호출 미적용 · "큐가 차야 max가 는다"는 분기 순서와 무제한 기본 큐가 만드는 동시 처리 8개 고정 · void 예외의 조용한 증발 · ThreadLocal이라 넘어가지 않는 트랜잭션과 SecurityContext와 MDC · 재시작 시 작업 유실이 전부 그 한 문장에서 파생되므로, 이 파생 관계를 아는 사람은 설정 네 개(core · max · queue · 거부 정책)를 한 세트로 설계하고 내구성이 필요한 순간에는 도구 자체를 브로커나 아웃박스로 바꾼다.
