@Transactional 자기 호출 미적용
조용히 트랜잭션 없이 도는 코드, 그리고 4가지 해법

면접 질문: "같은 클래스 내부 메서드 호출 시 @Transactional이 적용되지 않는 이유는? 해결 방법은?"

핵심 관전 포인트 — 트랜잭션을 열고 닫는 코드는 원본 객체가 아니라 그 앞에 세워진 프록시에 있다. 그런데 같은 클래스 안에서 this.method()로 부르면 호출이 프록시를 거치지 않고 원본으로 직행하므로 @Transactional이 아예 적용되지 않는다. 이 함정이 위험한 이유는 동작이 틀리기 때문이 아니라 틀렸다는 신호가 하나도 없기 때문이다 — 컴파일도 기동도 실행도 멀쩡하고, 예외가 나지 않는 정상 경로에서는 결과까지 같아서 테스트도 통과한다. 트랜잭션이 없으면 Spring Data JPA 리포지토리 호출이 건건이 자기 트랜잭션을 열고 즉시 커밋하므로 실패 시 앞부분만 남은 부분 커밋이 되고, 엔티티 변경 감지는 flush될 트랜잭션이 없어 UPDATE가 아예 나가지 않는다. 그래서 배포 직후가 아니라 몇 주 뒤 정산 불일치로 발견된다. 확인은 추측이 아니라 절차로 한다 — 주입받은 참조에 AopUtils.isAopProxy(), 의심 지점에 isActualTransactionActive()와 getCurrentTransactionName(), 그리고 org.springframework.transaction.interceptor 로거를 TRACE로 올려 어느 메서드에 트랜잭션이 실제로 열렸는지 눈으로 본다. 해법은 넷이고 각각 대가가 다르다 — 별도 빈 분리(클래스가 늘지만 유일하게 구조적 해결), 자기 주입(순환 참조를 만들고 @Lazy가 필요하며 설계 신호를 가린다), TransactionTemplate(선언적 트랜잭션의 이점을 포기), AopContext.currentProxy()(exposeProxy=true 전역 설정이 필요하고 코드가 스프링에 묶인다). 정석이 빈 분리인 이유는 프록시 때문이 아니다 — 트랜잭션 경계는 곧 설계 경계이고, 자기 호출로 트랜잭션을 나누고 싶다는 욕구 자체가 "이 메서드는 다른 책임이다"라는 신호이기 때문이다.
  • 1
    원인은 한 문장 — this는 프록시가 아니다. 트랜잭션 코드는 프록시에만 있고 원본에는 한 줄도 없는데, 프록시가 원본에 위임한 순간 프록시는 호출 스택에서 빠진다. 그 뒤 원본 안에서 일어나는 this.processOne()은 프록시와 무관하다. 그래서 판단 기준은 "애너테이션이 붙었는가"가 아니라 "이 호출이 프록시를 통과했는가"다.
  • 2
    위험한 건 결과가 아니라 침묵이다. 리포지토리 호출은 건건이 커밋되어 실패 시 부분 커밋이 남고, 엔티티 변경 감지는 flush될 트랜잭션이 없어 UPDATE가 사라지며, readOnly·propagation 같은 속성이 전부 무시된다. 그런데 정상 경로에서는 최종 데이터가 같아 테스트가 통과한다 — 그래서 리뷰를 뚫고 배포된 뒤 몇 주 뒤 정산 불일치로 발견된다.
  • 3
    해법은 넷(분·자·템·노)이고 정석은 빈 분리인데, 이유를 프록시에서 찾으면 절반이다. @Transactional이 긋는 것은 원자성 단위의 경계이고 원자성 단위는 도메인 판단에서 나오므로 트랜잭션 경계 = 설계 경계다. 자기 호출로 트랜잭션을 나누고 싶다는 욕구는 한 클래스에 원자성 단위가 다른 두 책임이 들어 있다는 신호이고, 빈 분리만이 프록시 문제와 설계 문제를 동시에 고친다.

0. 질문 + 출제 의도

질문: "같은 클래스 내부 메서드 호출 시 @Transactional이 적용되지 않는 이유는? 해결 방법은?"

출제 의도: AOP 프록시 원리의 실전 검증이다. 이 함정은 런타임에 조용히 트랜잭션 없이 실행되므로 코드 리뷰에서 눈으로 잡아야 하고, AI가 생성한 서비스 코드에도 흔히 들어 있다. 원리를 "설명"하는 것을 넘어 사고를 "예방·수습"할 수 있는 사람인지를 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "프록시를 안 거쳐서요"에서 멈추는 것 → 1·2절에서 호출이 어느 객체로 넘어가는지를 단계별 도식으로 못 박고, "CGLIB은 상속인데 왜?"라는 반문까지 미리 막는다.
② "트랜잭션이 안 걸린다"를 추상적으로만 말하는 것 → 3절에서 구체적으로 무엇이 망가지는지 5가지로 쪼갠다. 부분 커밋과 UPDATE 실종은 증상이 완전히 다르다.
③ "조심하겠습니다"로 끝내는 것 → 5절에서 확인 수단 4종 + 회귀 방지 테스트를 절차로 갖춘다. 이 질문의 진짜 관전 포인트는 검증 수단을 손에 쥐고 있는가다.
이 문서의 자리 — 스프링 프록시 3부작의 "함정 편" 프록시가 어떻게 만들어지는지(JDK 동적 프록시 vs CGLIB, final 함정)는 10번 문서가, @Transactional의 기본 동작과 롤백 규칙은 07번 문서가 본론이다. 여기서는 자기 호출 함정 하나만 끝까지 판다 — 증상을 어떻게 알아채고, 네 해법이 각각 무엇을 대가로 치르는지. 버전 의존 서술은 스프링 프레임워크 6.x / 스프링 부트 3.x 기준이다.

1. 왜 안 걸리나 — this는 프록시가 아니다

1-1. 전제 — 메모리에 객체가 두 개 있다

@Transactional이 붙은 빈에 대해 스프링은 원본 객체(target)와 그것을 감싼 프록시 객체 두 개를 만든다. 그리고 컨테이너에 등록해 다른 빈에 주입하는 것은 프록시 쪽이다. 트랜잭션을 시작·커밋·롤백하는 코드는 프록시에만 있고 원본에는 한 줄도 없다.

여기서 조건이 뒤바뀐다 — 이 페이지 전체의 열쇠

부가 기능이 도는 조건은 "이 메서드에 애너테이션이 붙어 있는가"가 아니라
"이 호출이 프록시 객체를 통과했는가"다

애너테이션은 표식(메타데이터)일 뿐 스스로 아무 일도 하지 않는다. 그 표식을 읽고 실행하는 주체는 프록시이므로, 프록시를 안 거친 호출에는 표식을 읽어줄 사람이 아무도 없다.

1-2. 문제의 코드 — 문법적으로는 흠잡을 데가 없다

문제 리뷰어 두 명이 통과시켜도 이상하지 않은 코드
@Service
public class OrderService {

    public void processAll(List<OrderRequest> requests) {
        for (OrderRequest request : requests) {
            this.processOne(request);this = 원본 객체 → 프록시를 우회한다
        }
    }

    @Transactional
    public void processOne(OrderRequest request) {
        // 트랜잭션 없이 실행된다. 컴파일도 기동도 실행도 멀쩡하다.
    }
}

가장 안 보이는 형태 — this.는 생략할 수 있다

자바에서 this.processOne(request)와 processOne(request)는 완전히 같은 자기 호출이다. 실무 코드에는 this.가 생략된 형태가 압도적으로 많고, 그래서 "수신자 없는 메서드 호출"이 눈에 안 띈다. 리뷰 때 찾아야 할 패턴은 this.가 아니라 "같은 클래스 안의 @Transactional 메서드를 수신자 없이 부르는 자리"다. 메서드 참조 requests.forEach(this::processOne)도 같은 함정이다.

1-3. 호출 경로를 한 단계씩 따라가면

비유 ① — 회사 대표번호와 안내원 대표번호(프록시)로 걸려온 전화는 안내원이 통화 기록을 남기고 담당자에게 연결한다. 그런데 담당자가 옆자리 동료에게 직접 말을 걸면 대표번호를 거치지 않았으니 기록이 남지 않는다. 안내원이 모든 직원의 전화를 받을 수 있다는 사실과는 무관하다 — 그 경로로 들어오지 않은 대화는 잡을 수 없다.
비유 ② — 공항 보안검색대 (해법이 왜 "분리"인지까지 설명해준다) 프록시는 게이트 안으로 들어가는 유일한 검색대다. 밖에서 들어오는 사람은 반드시 통과하지만, 이미 게이트 안에 있는 사람이 옆 사무실로 걸어가는 것은 검색대를 다시 지나지 않는다 — 자기 호출이 이것이다. 그래서 해법은 하나로 모인다: 그 방을 게이트 밖의 다른 건물로 옮겨서(= 별도 빈으로 분리해서) 다시 정문을 통과하게 만드는 것이다.

2. "CGLIB은 상속인데요?" — super가 아니라 위임이다

날카로운 반문이고 면접에서 자주 나온다. 자바의 동적 디스패치 규칙대로라면 자식(프록시)이 오버라이드한 메서드가 불려야 맞기 때문이다. 실제로 이 반문에 막히면 "외웠구나"로 읽힌다.

답은 한 문장이다. 스프링의 CGLIB 프록시는 super 호출 방식으로 동작하지 않는다. 상속은 "같은 타입인 척"하기 위한 수단일 뿐이고, 실제 동작은 별도 인스턴스에 대한 위임이다.

오해 상속이니까 이럴 것 같지만
// 이 방식이라면 자기 호출도 걸린다
public void processAll(List<OrderRequest> requests) {
    부가기능();
    super.processAll(requests);스프링은 이 방식이 아니다
}

// 실행 주체가 프록시 인스턴스 하나뿐이므로
// this == 프록시 가 되어, 내부 호출도
// 오버라이드된 프록시 메서드로 디스패치된다
실제 별도의 원본 인스턴스에 위임한다
// 완전히 다른 객체의 메서드를 부른다
public void processAll(List<OrderRequest> requests) {
    부가기능();
    target.processAll(requests);다른 인스턴스로 넘어간다
}

// 넘어간 뒤의 this 는 순수한 원본이라
// 동적 디스패치가 개입할 여지가 없다

이 반문에 답하는 순서 — 3단

① 사실 정정
스프링 CGLIB 프록시는 super 호출이 아니라 별도 인스턴스에 위임한다.
② 상속의 역할 재정의
상속은 "같은 타입인 척"하기 위한 것 — 타입 호환용이지 실행 흐름용이 아니다.
③ 방증 제시
프록시 객체의 필드가 null인 것 — 주입은 원본에 일어난다. 두 객체가 별개라는 증거.

3. 증상 — 에러가 아니라 침묵이라서 악질이다

"트랜잭션이 안 걸린다"는 문장은 추상적이다. 구체적으로 무엇이 달라지는지를 알아야 증상을 알아볼 수 있다. 다섯 갈래로 쪼개면 이렇다.

① 리포지토리 호출이 건건이 커밋된다
SimpleJpaRepository의 메서드에는 @Transactional이 걸려 있다. 바깥에 트랜잭션이 없으면 호출 하나마다 자기 트랜잭션을 열고 즉시 커밋한다. 반복문 중간에 예외가 나면 그 전까지 저장된 것만 남는 부분 커밋이 된다.
② 변경 감지 UPDATE가 아예 안 나간다 최악
부트의 OSIV 기본값 때문에 영속성 컨텍스트는 요청 끝까지 열려 있지만, 변경 감지 flush는 트랜잭션 커밋 시점에 일어난다. 트랜잭션이 없으면 flush 시점 자체가 오지 않아 order.markPaid() 같은 수정이 조용히 사라진다.
③ JdbcTemplate은 문장 단위 커밋
커넥션의 autoCommit이 켜진 상태(HikariCP 기본값)로 실행되므로 SQL 한 문장마다 커밋된다. 역시 부분 커밋이 남는다.
④ @Transactional 속성이 전부 무시된다
readOnly·propagation·isolation·timeout·rollbackFor 전부 프록시가 읽어서 적용하는 값이다. REQUIRES_NEW로 건별 커밋을 의도했는데 트랜잭션 자체가 없는 상황이 여기서 나온다.

⑤ 그런데 정상 경로에서는 결과가 똑같다 — 이 함정이 배포되는 진짜 이유

예외가 나지 않으면 "건건이 커밋"이든 "한 번에 커밋"이든 최종 데이터가 같다 → 테스트가 통과한다

그래서 기능 테스트·스모크 테스트·QA 시나리오는 이 버그를 절대 잡지 못한다. 차이는 오직 실패 경로에서만 드러난다. 5절의 회귀 방지 테스트를 "실패 경로"로 짜야 하는 이유가 이것이다.

암기 장치 — 증상 4종은 "리 · 변 · J · 속", 그리고 안 잡히는 이유는 "같"

리포지토리 건건 커밋 · 변경 감지 실종 · JdbcTemplate 문장 커밋 · 속성 전부 무시
— 그런데 정상 경로 결과가 같아서 테스트가 통과한다

면접에서 "트랜잭션이 안 걸립니다"로 끝내면 절반이다. "무엇이 어떻게 망가지는지"를 두 갈래(부분 커밋 / UPDATE 실종)로 나눠 말하는 순간, 겪어본 사람으로 들린다.

비유 — 화재가 아니라 누수다
불(예외)이 나면 연기 감지기가 즉시 울린다 — 에러율 알람, 스택 트레이스, 롤백. 그러나 이 함정은 천장 안쪽의 미세한 누수에 가깝다. 아무 소리도 나지 않고, 몇 주 뒤 천장이 내려앉고 나서야 원인을 거슬러 올라간다. 그때는 이미 젖은 자재를 전부 찾아 교체(= 데이터 수동 보정)해야 한다.

4. 타임라인 — 배포에서 발견까지 11일

침묵이 왜 악질인지는 시간축으로 봐야 실감이 난다. 주문 처리 배치에 이 버그가 들어간 경우를 따라가 보자. 어느 팀에나 있을 법한 전개다.

AI가 생성한 서비스 코드에 이 패턴이 흔한 이유 가산점 같은 맥락이다. 문법과 가독성 기준으로는 흠잡을 데 없는 코드라서 "동작하는 코드"만 검증하는 리뷰로는 그대로 통과한다. 면접에서는 여기에 한 줄 더 붙이면 좋다 — "AI 코드 리뷰 체크리스트에 '자기 호출 + @Transactional 조합'을 명시적 항목으로 둔다."

5. 확인 절차 — 정적 · 동적 · 회귀

이 질문의 진짜 관전 포인트

"조심하겠습니다"는 답이 아니다 — 확인 수단을 손에 쥐고 있는가를 본다

붙였으니 되겠지가 아니라 적용 여부를 검증하는 절차를 갖추는 것. 정적 확인(코드에서 패턴 찾기)과 동적 확인(실행 중에 물어보기), 그리고 회귀 방지(테스트로 못 박기)로 나눠서 갖춰 둔다.

5-1. 진단 순서도 — 네 수단을 어떤 순서로 쓰는가

5-2. 정적 확인 — 코드에서 패턴을 찾는다

같은 클래스 안에서 @Transactional이 붙은 메서드를 부르는 자리를 찾는다. 앞서 봤듯 this.를 생략해도 자기 호출이라는 점이 함정이다.

# @Transactional 이 붙은 public 메서드 이름을 뽑아두고,
# 같은 파일 안에서 그 이름이 "수신자 없이" 호출되는 자리를 찾는다.
grep -rn -B2 "@Transactional" --include=*.java src/main/java | grep "public\|protected"
사람 눈은 이 패턴을 놓친다 — 팀 차원에서는 규칙으로 고정한다 ArchUnit 같은 아키텍처 테스트나 정적 분석 규칙으로 "같은 클래스 내부에서 @Transactional 메서드 호출 금지"를 못 박아 두는 편이 낫다. 리뷰에 의존하는 방어는 사람이 바뀌면 사라지고, 테스트에 넣은 방어는 남는다.

5-3. 동적 확인 ① — 주입받은 참조가 프록시가 맞는지

@Autowired OrderService orderService;

@Test
void 프록시가_적용됐는지_확인() {
    // 반드시 "주입받은 참조"에 대해 검사해야 의미가 있다
    assertThat(AopUtils.isAopProxy(orderService)).isTrue();
    assertThat(AopUtils.isCglibProxy(orderService)).isTrue();   // 부트 기본값은 CGLIB
}

주의 — 원본 메서드 안에서 isAopProxy(this)는 언제나 false다

1절에서 봤듯 그 자리의 this는 원본이기 때문이다. 이것은 버그 탐지가 아니라 "this는 프록시가 아니다"라는 사실의 실증으로 쓸 수 있다 — 신입 교육 때 한 번 찍어보게 하면 설명이 필요 없어진다. 반대로 이 사실을 모르면 "프록시가 안 만들어졌다"고 오진하고 엉뚱한 곳을 파게 된다.

5-4. 동적 확인 ② — 그 지점에 트랜잭션이 실제로 열려 있는지

@Transactional
public void processOne(OrderRequest request) {
    // 지금 이 실행이 트랜잭션 안인가? 자기 호출로 들어왔다면 false
    log.info("tx active = {}", TransactionSynchronizationManager.isActualTransactionActive());

    // 한 걸음 더 — "어느 메서드가 이 트랜잭션을 열었는가"
    // 선언적 트랜잭션이면 "com.example.OrderService.processOne" 형태로 나온다.
    // 여기에 processAll 이 찍히면 processOne 의 @Transactional 은 무시된 것이다.
    log.info("tx name   = {}", TransactionSynchronizationManager.getCurrentTransactionName());
}
getCurrentTransactionName()이 결정적인 이유 "트랜잭션이 있다/없다"가 아니라 "누가 열었는가"까지 알려주기 때문이다. 바깥에도 @Transactional이 있는 경우 isActualTransactionActive()는 true를 돌려주므로 문제를 그대로 놓친다. 이름을 보면 연 사람이 processAll이라는 사실이 곧바로 드러난다.

5-5. 동적 확인 ③ — 트랜잭션 로그를 켠다 (코드 무수정)

설정 application.yml
logging:
  level:
    org.springframework.transaction.interceptor: TRACE
출력 열리고 닫힐 때마다 메서드 이름이 찍힌다
TRACE ... Getting transaction for
          [com.example.OrderService.processAll]
TRACE ... Completing transaction for
          [com.example.OrderService.processAll]
// processOne 이 목록에 없다 → 적용되지 않은 것

기대한 메서드 이름이 목록에 없으면 그 메서드의 @Transactional은 적용되지 않은 것이다. 4절 타임라인의 D+11에서 원인을 확정한 수단이 바로 이것이다 — 코드를 건드리지 않고 운영 이슈를 재현할 때 쓴다.

5-6. 회귀 방지 — 실패 경로 테스트로 못 박는다

@Test
void 중간에_실패하면_그_건은_통째로_롤백된다() {
    // 두 번째 저장에서 예외가 나도록 준비한 뒤,
    assertThatThrownBy(() -> orderService.processOne(실패하는_요청))
        .isInstanceOf(OrderException.class);

    // 앞부분 저장도 남아 있지 않아야 한다. 트랜잭션이 없으면 이 단언이 깨진다.
    assertThat(orderRepository.count()).isZero();
}

암기 장치 — 진단 4수단은 "프 · 활 · 이 · 로", 방어는 "실패 경로"

프록시인가(isAopProxy) → 활성인가(isActualTransactionActive) → 이름은 누구인가(getCurrentTransactionName) → 로그(TRACE)

정상 경로 테스트로는 이 버그가 절대 잡히지 않는다(3절 ⑤). 실패 경로 테스트가 유일한 자동 방어선이라는 문장까지 붙이면 답이 완성된다.

6. 해법 넷과 각각의 대가

네 방법 모두 "프록시를 다시 통과하게 하거나, 프록시에 의존하지 않게 한다"는 같은 목표를 갖는다. 차이는 무엇을 대가로 치르느냐다. 먼저 네 경로를 한 장으로 보면 이렇다.

암기 장치 — 해법 4종은 "분 · 자 · 템 · 노"

분리(별도 빈) · 자기 주입 · 템플릿(TransactionTemplate) · 노출 프록시(AopContext)

면접에서는 넷을 나열한 뒤 각각의 대가를 한 문장씩 붙이고, "기본은 분리, 예외적으로 템플릿"이라는 선택 기준으로 닫는 것이 가장 좋은 구성이다.

6-1. 별도 빈으로 분리 정석

트랜잭션 메서드를 다른 빈으로 옮긴다. 호출이 프록시라는 문을 다시 통과하게 되므로 구조적으로 해결된다.

before 자기 호출 — 트랜잭션 미적용
@Service
public class OrderService {

    public void processAll(List<OrderRequest> requests) {
        for (OrderRequest request : requests) {
            this.processOne(request);프록시 우회
        }
    }

    @Transactional
    public void processOne(OrderRequest request) { /* ... */ }
}
after 별도 빈 — 프록시를 경유
@Service
@RequiredArgsConstructor
public class OrderService {

    // 주입받는 것은 원본이 아니라 프록시다 — 여기가 전부다
    private final OrderProcessor orderProcessor;

    public void processAll(List<OrderRequest> requests) {
        for (OrderRequest request : requests) {
            orderProcessor.processOne(request);프록시 경유
        }
    }
}

@Service
@RequiredArgsConstructor
public class OrderProcessor {

    @Transactional
    public void processOne(OrderRequest request) { /* 건별 커밋 */ }
}

대가

  • 클래스 파일이 하나 는다.
  • 두 클래스 사이에 의존성과 필드를 나눠 배치해야 한다.
  • 나누는 기준을 잘못 잡으면 OrderProcessor처럼 아무 의미 없는 이름의 빈이 생겨 오히려 응집도가 떨어진다.

그런데 이 대가는 대체로 이득으로 돌아온다

  • "여러 건을 순회하며 오케스트레이션하는 책임"과 "한 건을 원자적으로 처리하는 책임"은 원래 다른 책임이다.
  • 분리하면 단위 테스트 대상이 명확해진다.
  • 건별 트랜잭션이라는 의도가 클래스 구조에 드러난다. → 7절의 결론으로 이어진다.

6-2. 자기 주입(self-injection) 대가 3종

자기 자신의 프록시를 주입받아 this 대신 그것으로 호출한다.

@Service
public class OrderService {

    // @Lazy 가 필요한 이유: 자기가 자기를 주입받는 순환 구조라
    // 실제 해석을 "첫 사용 시점"까지 미뤄야 안전하다.
    @Autowired @Lazy
    private OrderService self;

    public void processAll(List<OrderRequest> requests) {
        for (OrderRequest request : requests) {
            self.processOne(request);self 는 프록시다 (this 가 아니다)
        }
    }

    @Transactional
    public void processOne(OrderRequest request) { /* ... */ }
}
① 순환 참조를 만든다
생성자 주입 형태는 "자기를 만들려면 자기가 필요한" 진짜 순환이라 BeanCurrentlyInCreationException으로 확실히 실패한다. 필드·세터 주입은 동작하지만, 부트 2.6부터 순환 참조가 기본 금지(spring.main.allow-circular-references=false)로 바뀌어 기동 단계에서 막힐 수 있다. @Lazy·ObjectProvider 관용구가 굳은 것도 이 때문이다.
② 설계 신호를 가린다
자기 호출이 필요해졌다는 것은 대개 "한 클래스에 트랜잭션 단위가 다른 두 책임이 있다"는 신호인데(7절), 자기 주입은 프록시 문제만 가리고 그 신호는 무시한다.
③ 읽는 사람이 이유를 모른다
self.processOne()은 this.processOne()과 동작이 다른데 코드만 봐서는 왜 다른지 알 수 없다. 프록시 구조를 아는 사람에게만 읽히는 코드가 된다.
쓸 자리 분리할 만한 응집된 책임이 정말 안 보일 때, 그리고 그 이유를 주석으로 남길 때의 차선책이다. 면접에서는 "필요한 우회 장치(@Lazy)가 있다는 것 자체가 구조가 자연스럽지 않다는 신호"라는 해석까지 붙이면 좋다.

6-3. TransactionTemplate — 프로그래밍 방식

애너테이션(선언적 방식)을 포기하고 트랜잭션 경계를 코드로 직접 긋는다. 프록시에 의존하지 않으므로 자기 호출 문제가 원천적으로 존재하지 않는다.

@Service
@RequiredArgsConstructor
public class OrderService {

    private final TransactionTemplate transactionTemplate;

    public void processAll(List<OrderRequest> requests) {
        for (OrderRequest request : requests) {
            // 이 람다의 시작과 끝이 곧 트랜잭션 경계다. 프록시가 개입하지 않는다.
            transactionTemplate.executeWithoutResult(status -> processOne(request));
        }
    }

    // 더 이상 @Transactional 이 필요 없고, private 이어도 된다.
    private void processOne(OrderRequest request) { /* ... */ }
}
① 선언적 방식의 이점을 포기
선언적 방식의 값은 "비즈니스 코드에 인프라 코드가 섞이지 않는다"는 것이었다. TransactionTemplate은 그 이점을 되돌린다 — 트랜잭션 관리 코드가 다시 서비스 안으로 들어온다.
② 속성을 바꾸려면 인스턴스가 는다
스레드 안전하지만 속성(격리 수준·timeout·전파·readOnly)이 인스턴스에 고정된다. 읽기 전용과 쓰기, 서로 다른 timeout이 필요하면 템플릿 빈을 여러 개 만들어 주입받아야 한다.
③ 롤백 제어 방식이 달라진다
람다 안에서 unchecked 예외를 던지면 롤백되지만, checked 예외는 Consumer 시그니처상 던질 수 없다. 예외를 잡아 처리하면서 롤백시키려면 status.setRollbackOnly()를 직접 호출해야 한다 — 잊기 쉬운 지점이다.
쓸 자리 — 여기서는 오히려 이쪽이 정답이다 "반복문 안에서 건별 트랜잭션"처럼 경계를 세밀하게 제어하는 것이 목적 그 자체일 때는 의도를 가장 정확히 드러낸다. 트랜잭션이 어디서 시작해 어디서 끝나는지가 코드에 그대로 보이기 때문이다. 면접에서 "무조건 빈 분리"로만 답하면 도구를 모르는 것처럼 보이는데, 이 예외를 붙이면 상황별 기준을 가진 사람으로 보인다.

6-4. AopContext.currentProxy() 마지막 수단

현재 스레드에 노출된 프록시를 꺼내 호출한다.

전제 이게 없으면 런타임에 죽는다
// 애플리케이션 전역 설정
@EnableAspectJAutoProxy(exposeProxy = true)

// 빠뜨리면 컴파일은 통과하고
// 실행 시점에 IllegalStateException
사용 프록시를 꺼내 호출한다
public void processAll(List<OrderRequest> requests) {
    OrderService proxy = (OrderService) AopContext.currentProxy();캐스팅도 검증되지 않는다
    for (OrderRequest request : requests) {
        proxy.processOne(request);
    }
}
① 전역 설정을 켜야 한다
exposeProxy = true는 이 클래스만이 아니라 애플리케이션의 모든 프록시 호출에 적용된다. 프록시를 통과할 때마다 ThreadLocal에 프록시를 넣고 빼는 작업이 추가되므로, 메서드 하나를 구제하려고 전체에 비용을 얹는 구조다.
② 코드가 스프링 AOP에 묶인다
비즈니스 로직이 "나는 프록시로 감싸져 있다"는 인프라 사실을 알게 된다. 침투성이 네 방법 중 가장 나쁘고, 순수 단위 테스트에서는 AopContext가 비어 있어 그대로 실패한다.
③ 실패가 런타임에만 드러난다
exposeProxy 설정을 누군가 지우면 컴파일은 통과하고 실행 시점에 IllegalStateException이 난다. 캐스팅 대상 타입도 컴파일러가 검증해주지 않는다.
면접에서의 정답 — "방법은 알지만 권장하지 않는다" 쓸 자리는 레거시라 클래스 분리가 당장 불가능한 경우의 응급 처치뿐이다. 알고는 있되 고르지 않는다는 태도를 보여주는 것이 이 항목의 용도다.
한 걸음 더 — AspectJ 위빙 가산점 AspectJ 위빙으로 전환하면 프록시 자체가 사라져 자기 호출 제약이 없어진다. 다만 전용 컴파일러나 로드 타임 위빙 에이전트가 필요해 빌드·실행 파이프라인 복잡도가 크게 올라가므로, 이 문제 하나를 풀자고 도입하는 것은 명백한 과잉이라는 판단까지 함께 붙여야 한다. "해결책을 아는 것"과 "그 비용을 아는 것"은 다른 신호다.

해법프록시 경유주된 대가어울리는 자리코드 침투성

7. 왜 빈 분리가 정석인가 — 경계의 정체 시니어 변별

여기서 한 걸음 더 나가면 이 질문의 진짜 답이 나온다. 빈 분리가 정석인 이유는 "프록시를 다시 통과하니까"가 아니다.

① @Transactional이 선언하는 것
"여기부터 여기까지가 전부 성공하거나 전부 없던 일이 된다" — 즉 원자성 단위의 선언이다.
② 원자성 단위는 어디서 오나
아무렇게나 정해지지 않는다. "이 작업은 하나의 의미 있는 행위인가"라는 도메인 판단에서 나온다.
③ 따라서
트랜잭션 경계는 곧 설계 경계다. 트랜잭션을 어디서 끊을지 정하는 일은 책임을 어디서 끊을지 정하는 일과 같다.

이 페이지에서 딱 하나만 외운다면

트랜잭션 경계 = 설계 경계
자기 호출로 트랜잭션을 나누고 싶다는 욕구 = "이 메서드는 다른 책임이다"라는 신호

8. 같은 구조의 함정들 — @Async · @Cacheable · 메서드 보안

이 함정은 @Transactional만의 문제가 아니다. 프록시 기반 부가 기능 전부가 같은 구조다. 개별 애너테이션의 버그가 아니라 프록시 방식의 공통 제약으로 묶어 설명하면 원리를 이해하고 있다는 신호가 된다.

자기 호출 시 어떻게 조용히 실패하는가 — 증상이 각기 다른 팀의 문제로 보인다는 점이 공통점이다
애너테이션자기 호출 시 실제 동작결과값은?어느 팀 문제로 보이나왜 안 잡히나

그래서 한 번 자기 호출을 발견했다면 그 클래스의 다른 프록시 애너테이션도 함께 훑는 것이 실무적인 대응이다. 원인이 같으므로 같은 자리에 몰려 있을 가능성이 높다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

왜 적용이 안 되나?
트랜잭션 코드는 프록시에만 있는데 this는 원본이라 프록시를 우회한다. 조건은 "애너테이션이 붙었나"가 아니라 "프록시를 통과했나".
CGLIB은 상속인데 왜?
스프링 프록시는 super 호출이 아니라 별도 인스턴스에 위임한다. 상속은 타입 호환용. 방증: 프록시 필드가 null.
증상 4종은?
리·변·J·속 — 리포지토리 건건 커밋 · 변경 감지 UPDATE 실종 · JdbcTemplate 문장 커밋 · 속성 전부 무시. 안 잡히는 이유는 정상 경로 결과가 같아서.
진단 4수단은?
프·활·이·로 — isAopProxy · isActualTransactionActive · getCurrentTransactionName · 인터셉터 TRACE 로그.
②만 보면 놓치는 경우는?
바깥에도 @Transactional이 있을 때. isActualTransactionActive()가 true라서 통과된다 — 이름을 봐야 연 사람이 processAll임이 드러난다.
해법 4종은?
분·자·템·노 — 빈 분리 · 자기 주입 · TransactionTemplate · AopContext(노출 프록시).
빈 분리가 정석인 이유는?
프록시 때문이 아니다. 트랜잭션 경계 = 설계 경계이므로, 자기 호출 욕구는 "두 책임이 섞여 있다"는 신호다.
예외적으로 템플릿이 나은 자리는?
경계 제어 자체가 목적일 때 — "반복문 안 건별 트랜잭션". 시작·끝이 코드에 그대로 보인다.
자동 방어선은?
실패 경로 테스트뿐. 중간에 실패시키고 앞부분까지 롤백됐는지 단언한다. 정상 경로 테스트로는 절대 안 잡힌다.
@Transactional만의 문제인가?
아니다. @Async는 동기 실행, @Cacheable은 적중률 0%, 메서드 보안은 권한 검사 생략. 전부 조용히 실패한다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

왜 CGLIB은 상속인데 this.method() 호출이 프록시 쪽으로 안 가나요? 필수힌트: "상속이 무엇을 위한 것인가"를 먼저 정정하고, 마지막에 눈으로 확인 가능한 방증을 붙인다

스프링의 CGLIB 프록시가 super 호출 방식이 아니라 별도 원본 인스턴스에 위임하는 구조이기 때문이다.

상속은 "같은 타입인 척"하기 위한 수단일 뿐이다. 만약 프록시가 super.method()를 부르는 구조였다면 실행 주체가 프록시 인스턴스 하나뿐이라 this가 곧 프록시가 되고 자기 호출도 걸렸을 것이다. 하지만 스프링은 프록시와 원본을 메모리에 따로 존재하는 두 인스턴스로 두고, 프록시가 원본에 위임한 순간부터 실행 주체가 원본이 되므로 동적 디스패치가 개입할 여지가 없다.

방증을 하나 붙이면 좋다 — 디버거로 프록시 객체의 필드를 보면 전부 null인 경우가 있다. 의존성 주입은 원본에 일어나기 때문이고, 이것 자체가 두 객체가 별개라는 증거다. 프록시 생성 원리 상세는 10-aop-jdk-dynamic-proxy-vs-cglib.md에 있다.

별도 빈 분리와 자기 주입 중 무엇을 택하겠나요? 기준은? 시니어 변별힌트: 근거를 프록시가 아니라 설계에서 가져오고, 마지막에 "무조건 분리"가 아닌 예외를 하나 댄다

기본은 빈 분리이고, 근거를 프록시가 아니라 설계에서 가져와야 한다.

@Transactional이 긋는 것은 원자성 단위의 경계이고, 원자성 단위는 "이 작업이 하나의 의미 있는 행위인가"라는 도메인 판단에서 나온다. 즉 트랜잭션 경계는 곧 설계 경계다. 그러므로 "자기 호출로 트랜잭션을 나누고 싶다"는 욕구가 생겼다는 것은 한 클래스에 트랜잭션 단위가 다른 두 책임이 들어 있다는 신호다. 빈 분리는 프록시 문제와 설계 문제를 동시에 고친다.

자기 주입은 프록시 문제만 가리고 설계 신호는 무시하는 방법이고, 대가도 실재한다 — 생성자 주입으로는 순환 참조라 아예 실패하고, 필드 주입은 부트 2.6 이후 순환 참조 기본 금지 때문에 @Lazy 같은 우회가 필요하다. 우회 장치가 필요하다는 것 자체가 구조가 부자연스럽다는 신호로 읽는 것이 맞다.

다만 "무조건 분리"로 답하면 도구를 모르는 것처럼 보인다. "반복문 안 건별 트랜잭션"처럼 경계 제어 자체가 목적이면 TransactionTemplate이 의도를 가장 잘 드러낸다는 예외까지 말하면, 상황별로 도구를 고르는 기준을 가진 사람으로 보인다.

processAll에도 @Transactional이 붙어 있었다면 어떻게 되나요? 함정힌트: "트랜잭션이 없다"와 "속성만 무시된다"는 전혀 다른 상황이다 — 진단 수단도 달라진다

"트랜잭션이 아예 없는 것"과 "속성이 무시된 채 바깥에 합류하는 것"을 구분해서 답해야 정확하다.

processAll()이 프록시를 통해 호출됐다면 트랜잭션은 존재한다. 내부의 this.processOne()은 여전히 프록시를 안 거치므로, processOne()의 @Transactional 속성만 전부 무시되고 그냥 바깥 트랜잭션 안에서 평범한 메서드로 실행된다.

이 상황이 특히 위험한 이유가 있다. 건별 커밋을 의도해 processOne()에 REQUIRES_NEW를 붙였는데 전체가 한 트랜잭션으로 묶이는 사고가 이 유형이다. 1,000건을 처리하는 배치라면 999번째에서 실패했을 때 앞의 998건이 전부 함께 롤백된다.

진단할 때도 함정이 하나 더 있다. isActualTransactionActive()는 이 경우 true를 돌려주므로 문제를 놓친다. getCurrentTransactionName()을 봐야 트랜잭션을 연 것이 processAll이라는 사실이 드러난다(5절 순서도의 노란 칸). 전파 옵션 자체는 12-transaction-propagation-required-vs-requires-new.md에서 다룬다.

이 함정은 @Transactional만의 문제인가요? 필수힌트: 세 사례를 나열한 뒤, 세 사례를 관통하는 한 문장으로 닫는다

아니다. 프록시 기반 부가 기능 전부가 같은 구조다. 개별 애너테이션의 버그가 아니라 프록시 방식의 공통 제약으로 묶어 설명하면 원리를 이해하고 있다는 신호가 된다.

@Async: 자기 호출 시 별도 스레드로 넘어가지 않고 호출한 스레드에서 동기로 실행된다. Future를 받아 쓰고 있었다면 결과는 정상이고 응답 시간만 느려지므로, 성능 문제로만 보여 원인을 찾기 어렵다.

@Cacheable: 자기 호출 시 캐시를 조회하지도 저장하지도 않고 매번 원본 메서드를 실행한다. 결과값은 언제나 정확하므로 기능 테스트는 전부 통과하고, 캐시 적중률이 0%인 채로 DB 부하만 늘어난다.

@PreAuthorize 등 메서드 보안: 자기 호출 시 권한 검사가 건너뛰어진다. 이쪽은 성격이 정합성이 아니라 보안 취약점이다.

닫는 문장이 중요하다 — 전부 예외 없이 조용히 실패하고, 증상이 각기 다른 팀(정합성 / 성능 / 보안)의 문제로 보여 원인이 하나라는 사실이 잘 드러나지 않는다.

트랜잭션이 실제로 적용됐는지 런타임에 어떻게 확인하나요? 필수힌트: 도구 나열이 아니라 좁혀 들어가는 순서로 답한다. 마지막은 회귀 방지

수단을 갖고 있는지를 보는 질문이므로, 절차로 답한다.

① 그 지점에 트랜잭션이 있는가: TransactionSynchronizationManager.isActualTransactionActive()가 가장 직접적이다.

② 누가 그 트랜잭션을 열었는가: getCurrentTransactionName()이 com.example.OrderService.processOne 형태로 알려준다. 바깥에도 @Transactional이 있는 경우 ①만으로는 문제를 놓치므로 이쪽이 결정적이다.

③ 코드를 안 건드리고 보려면: org.springframework.transaction.interceptor 로거를 TRACE로 올린다. Getting transaction for [...] / Completing transaction for [...] 로그로 어느 메서드에 트랜잭션이 열렸는지가 그대로 찍힌다. 기대한 메서드 이름이 없으면 적용되지 않은 것이다.

④ 프록시 자체가 만들어졌는가: 주입받은 참조에 AopUtils.isAopProxy()를 건다. final 클래스 때문에 프록시 생성이 실패한 경우까지 걸러낸다. 단, 원본 메서드 안에서 AopUtils.isAopProxy(this)는 언제나 false라는 점에 주의한다 — 그 자리의 this는 원본이기 때문이고, 이건 버그가 아니라 이 문서의 주제 그 자체다.

⑤ 회귀 방지: 실패 경로에서 롤백되는지를 검증하는 테스트로 못 박는다. 정상 경로 테스트로는 이 버그가 절대 안 잡힌다. "붙였으니 되겠지"가 아니라 적용 여부를 검증하는 절차를 갖고 있는가를 보는 질문이라는 점을 의식하고 답하면 좋다.

private 메서드에 @Transactional을 붙이면 어떻게 되나요? 함정힌트: "왜 안 되는가"를 두 겹으로 — 프록시가 가로챌 수 있는가, 그리고 호출 경로가 애초에 무엇인가

적용되지 않는다. 그리고 역시 아무 에러도 나지 않는다. 이유가 두 겹이라는 점까지 말하면 좋다.

① 프록시가 가로챌 수 없다. CGLIB 프록시는 상속으로 메서드를 오버라이드해 호출을 가로채는데, private 메서드는 오버라이드 대상이 아니다. 같은 이유로 final 메서드도 가로챌 수 없다. 스프링 AOP의 프록시 모드에서 선언적 트랜잭션은 public 메서드에만 적용되며, private·protected·package-private에 붙이면 조용히 무시된다.

② 호출 경로가 애초에 자기 호출뿐이다. private 메서드는 정의상 같은 클래스 안에서만 부를 수 있으므로, 설령 가로챌 수 있었더라도 모든 호출이 이 문서가 다루는 자기 호출이 된다. 즉 두 이유가 겹쳐 있어 어느 쪽으로도 빠져나갈 수 없다.

실무 대응은 자기 호출과 같다 — 그 로직이 별도 트랜잭션 단위라면 별도 빈으로 분리하고, 경계 제어가 목적이면 TransactionTemplate으로 감싼다. TransactionTemplate 방식에서는 오히려 private이어도 아무 문제가 없다(6-3절)는 대비를 짚으면 이해도가 드러난다.

requests.forEach(this::processOne)처럼 메서드 참조로 넘기면 어떻게 되나요? 함정힌트: 메서드 참조는 "어느 인스턴스에 묶인 참조"인가

여전히 자기 호출이다 — 트랜잭션이 걸리지 않는다.

this::processOne은 this, 즉 원본 인스턴스에 바인딩된 메서드 참조다. 나중에 forEach 안에서 호출되든 다른 스레드에서 호출되든 도착지는 원본 객체이므로 프록시를 통과하지 않는다. 호출 시점이 미뤄질 뿐 경로는 this.processOne()과 완전히 같다.

반대로 orderProcessor::processOne처럼 다른 빈(=프록시)에 바인딩된 메서드 참조는 정상적으로 걸린다. 판단 기준은 언제나 하나다 — "이 참조가 가리키는 수신 객체가 프록시인가, 원본인가".

리뷰 관점에서 이 형태가 특히 위험한 이유는 this가 눈에 보이지 않는 형태로도 쓸 수 있기 때문이다 — forEach(this::processOne)에서 this::를 지운 형태는 없지만, 람다 r -> processOne(r)는 수신자가 아예 안 보인다. 정적 분석 규칙이 사람 눈보다 나은 이유가 여기 있다(5-2절).

별도 빈으로 분리했는데도 여전히 트랜잭션이 안 걸립니다. 무엇부터 보나요? 가산점힌트: "프록시가 있는가 → 가로챌 수 있는 메서드인가 → 정말 외부 호출인가 → 롤백 조건은 맞는가" 순서

원인을 네 층으로 나눠 위에서부터 배제한다. 순서가 곧 답이다.

① 프록시가 만들어졌는가. 새로 만든 클래스가 @Service 등으로 빈 등록이 됐는지, 컴포넌트 스캔 범위 안에 있는지 확인한다. AopUtils.isAopProxy(주입받은 참조)가 false면 여기서 끝난다.

② 가로챌 수 있는 메서드인가. final 클래스·final 메서드면 CGLIB이 오버라이드할 수 없고, public이 아니면 프록시 모드에서 적용 대상이 아니다. 코틀린이라면 클래스·메서드가 기본으로 final이라는 점이 특히 자주 걸린다.

③ 정말 외부 호출이 됐는가. 분리해 놓고도 새 빈 안에서 다시 자기 호출을 하고 있거나, 옮긴 메서드를 여전히 옛 경로로 부르고 있는 경우가 있다. getCurrentTransactionName()으로 연 사람의 이름을 확인하면 즉시 갈린다.

④ 트랜잭션은 열렸는데 롤백이 안 되는 것 아닌가. 이건 다른 문제다 — checked 예외는 기본적으로 롤백 대상이 아니고, try-catch로 예외를 삼키면 프록시는 정상 리턴으로 보고 커밋한다. "트랜잭션이 없다"와 "트랜잭션은 있는데 커밋됐다"를 섞지 않는 것이 진단의 핵심이고, 갈라내는 수단이 5절의 TRACE 로그다. 롤백 규칙 자체는 07-transactional-default-behavior-rollback.md에서 다룬다.

이 함정을 팀 차원에서 재발 방지하려면 무엇을 하겠습니까? 시니어 변별힌트: "리뷰 잘하겠습니다"는 답이 아니다 — 사람이 바뀌어도 남는 장치를 댄다

"리뷰에서 잡겠다"는 답은 약하다. 이 함정은 문법적으로 자연스러운 코드라서 사람 눈이 놓치는 것이 정상이고, 실제로 4절 타임라인에서도 리뷰어 2명을 통과했다. 사람이 바뀌어도 남는 장치로 답해야 한다.

① 자동 검출. ArchUnit 같은 아키텍처 테스트나 정적 분석 규칙으로 "같은 클래스 안의 @Transactional 메서드를 내부에서 호출 금지"를 빌드에 넣는다. 리뷰는 통과할 수 있어도 빌드는 통과할 수 없게 만드는 것이 핵심이다.

② 실패 경로 테스트를 관례로. 트랜잭션이 걸린 메서드에는 "중간에 실패시켰을 때 앞부분까지 롤백되는가" 테스트를 짝으로 요구한다. 정상 경로 테스트는 이 버그에 대해 아무 정보도 주지 않는다.

③ 진단 런북. "트랜잭션이 의심되면 org.springframework.transaction.interceptor를 TRACE로 올리고 메서드 이름 목록을 본다"를 문서로 남긴다. 4절에서 원인 규명에 이틀이 걸린 이유는 수단을 그 자리에서 떠올리지 못했기 때문이다.

④ AI 코드 리뷰 체크리스트. AI가 생성한 서비스 코드에 이 패턴이 흔하므로 "자기 호출 + @Transactional 조합"을 명시적 항목으로 둔다. ③④는 "겪어본 팀"에서만 나오는 답이라 인상에 남는다.

AspectJ 위빙으로 바꾸면 해결된다던데, 도입하시겠습니까? 가산점힌트: "된다"와 "한다"는 다르다 — 비용을 말하고 판단으로 닫는다

해결은 된다. 그러나 이 문제 하나 때문에 도입하는 것은 명백한 과잉이다.

원리상 그렇다 — AspectJ 위빙은 프록시를 세우는 대신 바이트코드 자체에 부가 기능을 짜 넣는다. 프록시라는 "통과해야 할 문"이 존재하지 않으므로, 자기 호출이든 private 메서드든 제약이 사라진다. 자기 호출 함정이 스프링 AOP의 본질적 한계가 아니라 프록시 방식이라는 구현 선택의 결과라는 점을 보여주는 좋은 대비이기도 하다.

대가가 크다는 것이 답의 무게중심이다 — 전용 컴파일러(컴파일 타임 위빙)나 로드 타임 위빙 에이전트가 필요해 빌드·실행 파이프라인 복잡도가 크게 올라가고, 팀 전체가 디버깅·트러블슈팅 방식을 새로 배워야 한다. 메서드 하나를 위해 프로젝트 전체의 빌드 방식을 바꾸는 셈이므로, 판단은 "빈 분리로 해결하고, AspectJ는 선택지로만 알고 있는다"가 맞다. 이 판단까지 붙는 것이 "방법을 아는 사람"과 "선택할 줄 아는 사람"의 차이다.

한 줄 요약
트랜잭션 코드는 프록시에만 있는데 this.method()는 프록시를 우회해 원본을 직접 부르므로 @Transactional이 에러 없이 조용히 무시되고 — 리포지토리 호출이 건건이 커밋되거나 변경 감지 UPDATE가 아예 나가지 않아 몇 주 뒤 정산 불일치로 발견되는 유형이라 isActualTransactionActive() · getCurrentTransactionName() · 트랜잭션 TRACE 로그로 적용 여부를 검증하는 절차를 갖춰야 하고, 해법 넷(분·자·템·노) 중 별도 빈 분리가 정석인 이유는 프록시를 다시 통과해서가 아니라 트랜잭션 경계가 곧 설계 경계이며 자기 호출로 트랜잭션을 나누고 싶다는 욕구 자체가 "이 메서드는 다른 책임이다"라는 신호이기 때문이다.
