2. Spring / Spring Boot

톰캣 스레드풀 / HikariCP 크기 산정 — 코어 수가 아니라 "점유 시간"으로 계산한다

📖 약 7분 🧩 8개 섹션 0/8 섹션 이해
🎯 핵심 관전 포인트

풀 크기는 감이 아니라 Little's law(동시수 L = 처리량 λ × 체류시간 W)로 계산하는 공학적 결정이다. 요청이 그 자원을 점유하는 시간을 기준으로 — 톰캣 스레드는 전체 응답시간 동안, DB 커넥션은 커넥션 점유 시간 동안만 붙잡히므로 — 각각 따로 계산한다. 코어 수는 스레드 수의 기준이 아니라 CPU 연산 총량의 상한일 뿐이다(블로킹 I/O 바운드 서버는 스레드 ≫ 코어). 계산값은 출발점이고, 최종 숫자는 부하 테스트와 메트릭으로 검증한다.

0

질문 + 의도

▾
면접 질문

"톰캣 스레드풀(max-threads), DB 커넥션풀(HikariCP) 크기는 어떤 기준으로 산정하나요?"

출제 의도"기본값 그대로" 또는 "많을수록 좋다"는 답을 거르는 질문이다. 풀 크기는 계산 가능한 공학적 결정(동시 요청 수 × 요청당 점유 시간)이고, 이 계산을 해본 사람만 용량 산정 회의에서 근거 있는 숫자를 낼 수 있다.
1

산정 골격 — Little's law

▾
text
동시에 자원을 점유 중인 요청 수 = TPS × 그 자원의 점유 시간

예제: 4코어 장비, 평균 응답 100ms(그중 DB 커넥션 점유 50ms), 목표 500 TPS

자원점유 시간계산필요 개수
톰캣 스레드요청 전체 응답시간 100ms (블로킹 MVC에선 처음부터 끝까지 묶임)500 × 0.1s50 (+여유)
Hikari 커넥션트랜잭션/쿼리 구간 50ms만500 × 0.05s25
  • 같은 요청이라도 자원마다 점유 시간이 다르므로 풀 크기도 달라진다 — "스레드 수 = 커넥션 수"로 맞추는 건 근거 없는 낭비(또는 부족)다.
  • 커넥션 점유 시간을 줄이면(트랜잭션 밖으로 외부 호출 빼기, 쿼리 튜닝) 같은 TPS를 더 작은 풀로 감당한다 — 풀 늘리기 전에 점유 시간부터 의심.
2

오개념 교정 1 — "스레드 수 = 코어 수"가 아니다

▾
  • 코어 수 = 어느 한 순간에 CPU 위에서 실제로 실행(RUNNING) 중일 수 있는 스레드의 최대 개수이지, 존재할 수 있는 스레드 수의 제한이 아니다.

  • 4코어에서 스레드 50개가 돌아가는 방식(OS 시분할 다중화):

    • BLOCKED/WAITING (대부분) — DB 소켓 응답 대기 중. 스케줄링 대상에서 아예 빠져 CPU 0%, 스택 메모리(~1MB)만 점유. 응답이 도착하면 OS가 깨워 run queue에 넣는다.
    • RUNNABLE (소수) — 코어가 비기를 대기. 스케줄러가 수 ms 타임 슬라이스로 4개 코어에 번갈아 태운다.
  • 어느 순간의 스냅샷: 50개 중 ~25개는 DB 대기, 다수는 클라이언트 네트워크 I/O 대기, 실제 CPU가 필요한 스레드는 몇 개뿐 → 4코어로 충분.
3

오개념 교정 2 — 블로킹 MVC에서 대기 중 스레드는 다른 요청을 처리하지 못한다

▾
java
// 블로킹 서블릿 MVC + JDBC — 스레드는 요청에 100ms 내내 묶인다
public OrderResponse getOrder(Long id) {
    Order order = orderRepository.findById(id);  // DB 응답 50ms 대기
    // ← 이 50ms 동안 이 스레드는 '블로킹'되어 아무것도 못 한다.
    //    CPU만 놓아줄 뿐, 다른 요청을 처리하는 게 아니다.
    return toResponse(order);
}
  • "대기하는 동안 스레드가 다른 요청을 처리한다"는 WebFlux 같은 논블로킹 모델의 이야기다(적은 이벤트 루프 스레드가 콜백으로 여러 요청을 오간다).
  • 블로킹 모델에서 대기 시간을 흡수하는 수단은 스레드 개수뿐 → 그래서 I/O 바운드 서버는 코어 수보다 훨씬 많은 스레드가 필요하다.
4

코어 수의 실제 역할 — CPU 연산 총량의 상한

▾
  • 요청당 실제 CPU 연산이 8ms라면: 4코어 = 초당 4,000ms의 CPU 예산 → 최대 500 TPS가 CPU 한계. 이 한계는 스레드를 아무리 늘려도 안 올라간다.

  • 정리:

    • I/O 바운드 (일반적인 웹 API): 스레드 ≫ 코어. 스레드 수는 Little's law로.
    • CPU 바운드 (암호화, 인코딩, 대량 연산): 스레드 ≈ 코어(±1~2). 그 이상은 컨텍스트 스위칭·캐시 오염 비용만 늘어 오히려 처리량이 떨어진다.
  • 과도한 스레드의 비용: 스택 메모리(스레드당 ~1MB), 컨텍스트 스위칭, GC 루트 증가. "많을수록 좋다"는 답은 이 비용을 모른다는 자백이다.
5

HikariCP 공식 권장 — "풀은 작을수록 좋다"

▾
  • HikariCP 위키의 출발점 공식: connections = (core_count × 2) + effective_spindle_count — 단, 이때 core_count는 DB 서버의 코어다. 커넥션이 많아도 DB가 동시에 실행할 수 있는 양은 DB의 CPU·디스크가 상한이기 때문.
  • 애플리케이션 쪽 계산(Little's law, 25개)과 DB 쪽 한계(공식) 중 작은 쪽이 실질 상한 — 커넥션을 늘려도 DB가 못 받으면 대기 줄만 DB 앞으로 옮겨질 뿐이다. 앱 인스턴스가 N대면 DB에는 N × pool 커넥션이 꽂힌다는 것도 함께 계산.
  • 풀이 작을수록 커넥션 캐시 적중·DB 부하 안정에 유리 — "고갈 나니 늘리자"가 아니라 점유 시간 단축이 먼저.
6

계산은 출발점 — 실측으로 검증

▾

  • 부하 테스트로 목표 TPS를 걸고 확인할 메트릭:

    • tomcat.threads.busy (active threads) — max에 붙어 있으면 스레드 부족 또는 응답시간 악화
    • hikaricp.connections.active / hikaricp.connections.pending / connection acquire wait time — 대기 시간이 생기기 시작하면 커넥션 부족(또는 점유 시간 증가)
    • CPU 사용률 — 스레드를 늘렸는데 TPS가 안 오르고 CPU가 포화면 CPU 바운드 한계
  • 응답시간 분포(p99)가 평균과 크게 다르면 평균 기반 계산이 깨진다 — 느린 쿼리 하나가 점유 시간을 끌어올려 풀을 잠식.
7

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

산술적으로 스레드 100/커넥션 50이지만, 먼저 CPU 예산(요청당 CPU × 1000 ≤ 코어 수 × 1000ms?)과 DB 쪽 한계를 재검토. 한 대의 수직 확장이 아니라 인스턴스 증설(수평)로 나누는 게 일반적.

체류시간 W가 늘면 같은 TPS에서 필요 동시수 L이 비례 증가 → 풀이 먼저 마르고, 대기가 응답시간을 더 늘리는 악순환(고갈 연쇄). 풀 크기 문제가 아니라 W 악화(느린 쿼리, 외부 API 지연)가 근본 원인인 경우가 많다.

대기 요청까지 다 받아들여 메모리·컨텍스트 스위칭 비용 증가 + 뒷단(DB)에 과부하 전달. 처리 못 할 요청은 빨리 거절(큐 제한)하는 게 전체 시스템에 낫다 — backpressure 관점.

스레드 점유 비용이 사라져 톰캣 스레드 산정 문제는 완화되지만, DB 커넥션은 여전히 물리 자원이라 Hikari 산정(점유 시간 기준)은 그대로 유효. 병목이 스레드에서 커넥션으로 이동할 뿐.

✅ 한 줄 요약

풀 크기는 "동시수 = TPS × 점유시간"(Little's law)으로 자원별 점유 시간 기준 계산한다 — 블로킹 MVC에서 스레드는 응답시간 내내 묶이므로 톰캣 = TPS×응답시간(예제: 50), 커넥션은 트랜잭션 구간만이므로 Hikari = TPS×점유시간(25) — 코어 수는 스레드 수 기준이 아니라 CPU 연산 총량과 CPU 바운드 작업의 상한이며, 최종 숫자는 부하 테스트의 active/pending 메트릭으로 검증한다.
