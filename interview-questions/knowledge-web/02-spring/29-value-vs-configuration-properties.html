@Value vs @ConfigurationProperties
설정 주입 두 방식의 차이와 선택 기준 — 설정도 코드처럼 검증한다

면접 질문: "@Value와 @ConfigurationProperties의 차이와 선택 기준은?"

핵심 관전 포인트 — @Value는 프로퍼티 한 개를 문자열 키로 찍어 필드에 꽂는 도구이고, @ConfigurationProperties는 프리픽스로 묶인 설정 그룹을 통째로 타입 세이프 객체에 붓는 도구다. 후자의 실무적 결정타는 @Validated + Bean Validation으로 잘못된 설정(오타·누락·범위 위반)을 기동 시점 실패(fail-fast)로 잡아낸다는 것 — Binding to target ... failed: Property: payment.retryCount / Value: "0" / Reason: must be greater than or equal to 1처럼 어느 프로퍼티가 어느 파일 몇 번째 줄에서 왜 틀렸는지를 찍고 앱이 뜨지 않는다. @Value는 기본값(${x:3000})이 붙은 키가 누락되면 조용히 그 기본값으로 흘러가 한참 뒤 런타임 오동작으로 발각된다. 여기에 relaxed binding(max-retry-count/maxRetryCount/MAX_RETRY_COUNT를 같은 프로퍼티로 인식 → 환경변수로 운영 설정을 덮어쓸 수 있다), 생성자 바인딩 기반 불변 설정(부트 3에서는 생성자가 하나면 @ConstructorBinding도 생략 가능, record가 가장 깔끔), 스프링 없이 new로 만들어 쓰는 테스트 용이성까지가 후자 쪽 이점이다. 반대로 @Value만 할 수 있는 것은 SpEL(#{...})인데, 설정 로직이 문자열 안에 숨어 IDE·컴파일러의 사정권 밖으로 나간다는 대가를 안다는 것까지 말해야 균형이 잡힌다. 결론: 묶인 설정이 2개 이상이면 @ConfigurationProperties, SpEL이 꼭 필요한 단발 값만 @Value.
  • 1
    다루는 단위가 다르다 — @Value는 키 하나를 문자열로 지목해 필드에 꽂고, @ConfigurationProperties는 프리픽스 아래 전체를 하나의 타입 세이프 객체에 바인딩한다. 그래서 전자는 설정 키 문자열이 코드 전체에 흩어지고, 후자는 프로퍼티 클래스 한 곳에만 남는다.
  • 2
    실무적 결정타는 실패 시점과 실패 메시지다 — @Validated를 붙이면 잘못된 설정이 기동 시점에 Property · Value · Origin(파일:줄) · Reason 네 줄과 함께 앱을 죽인다. @Value는 기본값이 붙은 키가 누락·오타 나면 로그 한 줄 없이 그 기본값으로 흘러가, 장애가 난 뒤에야 발각된다.
  • 3
    선택 기준은 한 줄로 말한다 — 묶인 설정이 2개 이상이면 @ConfigurationProperties(검증·불변·relaxed binding·자동완성·테스트 용이성이 전부 따라온다), SpEL이 꼭 필요한 단발 값만 @Value. 단 SpEL은 설정 로직을 문자열 안에 숨겨 컴파일러·IDE의 사정권 밖으로 빼는 대가가 있다는 것까지 붙인다.

0. 질문 + 출제 의도

질문: "@Value와 @ConfigurationProperties의 차이와 선택 기준은?"

출제 의도: 설정 오타가 런타임에 조용히 기본값으로 도는 사고를 타입 안전 바인딩·검증으로 막는지 본다. 설정도 코드처럼 검증 대상으로 보는 규율의 표본이 되는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① "하나 vs 여러 개"에서 멈추는 것 → 4·5절에서 그 차이가 어떤 장애로, 얼마나 늦게 드러나는지를 타임라인과 실패 로그로 못 박는다.
② "@Value도 없으면 기동 실패하지 않나"라는 반문에 무너지는 것 → 5절에서 "값의 부재"와 "값의 부적절함"을 갈라, @Value가 잡는 것이 앞의 하나뿐임을 보인다.
③ @Value를 싸잡아 부정하는 것 → 9·10절에서 SpEL이라는 유일한 우위와 그 대가, 그리고 @Value가 여전히 옳은 자리 세 곳을 남겨 균형을 잡는다.

이 문서의 버전 의존 서술은 스프링 부트 3.x 기준이며, 2.x와 달라지는 지점은 그때마다 표시한다(8절).

한 문장 비유 — 벽에 붙인 포스트잇 vs 입국 심사대 @Value는 포스트잇이다. 아무 벽(아무 클래스의 아무 필드)에나 붙일 수 있고, 적힌 것은 손글씨 문자열이라 철자가 틀려도 종이는 아무 말이 없다.  /  @ConfigurationProperties는 입국 심사대다. 모든 값이 창구 하나를 통과하며 여권(타입)과 비자 요건(@Min·@NotBlank)을 검사받고, 요건에 안 맞으면 그 자리에서 입국이 거부된다 — 나중에 시내 한복판에서 문제가 터지는 대신에.

1. 전제 — yml에 적은 값이 자바 객체에 닿는 마지막 한 걸음

두 애너테이션을 비교하기 전에 그 밑에 깔린 구조를 한 문단으로 정리하고 가자. 이걸 세워두면 뒤에 나오는 모든 차이가 "같은 사전을 다르게 조회하는 방식의 차이"로 정리된다.

스프링은 기동할 때 여러 출처(커맨드라인 인자, 환경변수, application.yml, 기본값 등)에서 프로퍼티를 읽어 Environment라는 하나의 커다란 키-값 사전을 만든다. 이 사전 안에서 값은 전부 문자열이다. timeout: 3000이라고 썼어도 사전에는 "3000"이라는 글자로 들어간다.

그러면 int timeout = 3000을 얻으려면 두 가지 일이 필요하다. ① 어느 키를 볼지 정하기, ② 문자열을 원하는 타입으로 바꾸기. @Value와 @ConfigurationProperties는 이 두 가지를 처리하는 서로 다른 방식이고, 둘의 모든 차이는 여기서 갈라져 나온다.

2. 두 도구의 정체 — 값 하나를 찍어 오기 vs 그룹을 통째로 붓기

2-1. @Value — 값 하나를 문자열 키로 찍어 가져온다

@Value는 필드나 파라미터에 붙여 "이 자리에 이 키의 값을 넣어라"라고 지시하는 애너테이션이다. 키는 ${...} 안에 문자열로 적는다.

@Value 키 하나에 필드 하나 — 그 관계를 잇는 것은 오직 문자열이다
@Component
public class PaymentClient {

    // "payment.api-url 이라는 키의 값을 이 필드에 넣어라"
    @Value("${payment.api-url}")
    private String apiUrl;

    // 콜론 뒤는 기본값이다. 키가 없으면 3000이 들어간다.
    @Value("${payment.timeout-ms:3000}")이 콜론이 4절 사고의 씨앗
    private int timeoutMs;
}

동작 방식은 단순하다. 빈을 만든 뒤 ${...} 안의 키로 Environment를 조회하고, 얻은 문자열을 필드 타입으로 변환해 리플렉션으로 꽂는다. 이름이 @Value인 이유도 여기 있다 — 다루는 단위가 값(value) 하나다.

2-2. @ConfigurationProperties — 프리픽스 아래를 통째로 객체에 붓는다

접근이 정반대다. 키를 하나씩 지목하지 않고, 접두어(prefix)를 하나 정한 다음 그 아래의 모든 키를 클래스의 필드 이름과 짝지어 한꺼번에 채운다.

yml 설정은 원래 이렇게 묶여 있다
# application.yml
payment:
  api-url: https://pg.example.com
  timeout: 3s
  retry-count: 3
클래스 묶인 모양 그대로 받는다
@ConfigurationProperties(prefix = "payment")
public class PaymentProperties {
    private String apiUrl;      // ← payment.api-url
    private Duration timeout;   // ← payment.timeout
    private int retryCount;     // ← payment.retry-count
    // getter/setter 생략
}

여기서 api-url이라는 yml 키가 apiUrl이라는 자바 필드와 어떻게 짝지어지는지가 궁금할 텐데, 그것이 6절에서 다룰 relaxed binding이다.

이 방식을 바인딩(binding)이라고 부른다. 원래 웹 요청 파라미터를 객체에 채워 넣는 것을 가리키던 말인데, 설정에서도 같은 일 — 바깥에서 온 이름-값 쌍들을 객체의 필드에 묶어 채우는 일 — 이라 같은 단어를 쓴다. 이름이 @ConfigurationProperties인 이유도 분명하다 — 다루는 단위가 설정 프로퍼티들(복수)의 묶음이다.

이름이 곧 정의다 — 여기서 헷갈리면 뒤가 전부 흔들린다

@Value
value = 값 하나
"이 키의 값을 이 필드에" — 1:1, 연결 고리는 문자열. 그래서 컴파일러가 볼 수 없다.
@ConfigurationProperties
properties = 프로퍼티들(복수)
"이 프리픽스 아래를 이 클래스에" — N:1, 연결 고리는 클래스 구조. 그래서 타입·제약·자동완성이 붙는다.

3. 한눈에 비교 — 그리고 이 표가 말해주지 않는 것

8개 축 비교. 표는 "무엇이 다른가"만 알려준다 — "그래서 왜 문제가 되는가"는 4~7절이 담당한다.
축@Value@ConfigurationProperties이 차이가 터지는 자리
단위프로퍼티 1개씩 필드에 주입프리픽스 하위 전체를 객체로 바인딩7절 (산탄총)
표현식${...} 플레이스홀더 + SpEL #{...} 지원${...}만 지원, SpEL 불가9절
키 매칭키를 정확히 일치시켜야 함relaxed binding (표기법 4종을 같은 것으로)6절
타입단순 변환만중첩 객체, List/Map, Duration("10s")·DataSize("10MB")8절
검증불가 (개별 값의 존재 여부뿐)@Validated + Bean Validation → 기동 시점 검증4·5절 (핵심)
불변성필드 주입이라 final 불가생성자 바인딩으로 불변 객체 가능7절
IDE 지원없음configuration-processor로 자동완성 메타데이터 생성7절
테스트스프링 컨텍스트가 있어야 값이 채워짐new로 직접 만들어 쓸 수 있음10절 꼬리질문

표는 여기까지다. 표만 보면 "무엇이 다른가"는 알겠지만 "그래서 왜 문제가 되는가"는 안 보인다. 면접에서도 이 표를 읊는 데서 끝나면 암기한 사람으로 들리고, 아래 다섯 사고 중 하나라도 시나리오로 말하면 겪어본 사람으로 들린다.

암기 장치 — @Value가 만드는 사고 5종은 "침 · 무 · 불 · 산 · 가"

침묵하는 기본값 · 무검증(있기만 하면 통과) · 불일치(키 표기) · 산탄총(흩어진 문자열) · 가변(누가 바꾼다)

면접에서 "차이가 뭐냐"를 물으면 표를 읊는 대신 이 다섯 중 두세 개를 사고 시나리오로 말하는 편이 훨씬 강하다. 4~7절이 각각 하나씩이다.

4. 사고 ① — 기본값이 붙은 키의 누락은 침묵한다

@Value의 동작을 정확히 알아야 이 사고가 보인다. 키가 없을 때의 행동이 기본값 유무에 따라 완전히 다르다.

선언키가 없거나 오타가 났다면
@Value("${payment.api-url}")기동 실패 — Could not resolve placeholder 'payment.api-url'
@Value("${payment.timeout-ms:3000}")조용히 3000 — 아무 로그도 없다
이 문서에서 가장 반직관적인 한 줄 기본값을 붙이는 건 보통 좋은 습관처럼 느껴진다. "값이 없어도 합리적인 값으로 돌게 하자"는 의도니까. 그런데 그 순간 그 키는 오타를 검출할 수 없는 키가 된다. 기본값은 사실상 "결원을 알리지 않고 대신 뛰는 대타"다 — 경기는 계속되지만 아무도 결원을 모른다.
before @Value 산탄총 — 오타·누락이 조용히 기본값으로 흘러간다
@Component
public class PaymentClient {

    @Value("${payment.api-url}")
    private String apiUrl;

    // 운영 yml에는 payment.timeout-ms 가 아니라 payment.timeoutMs 로 적혀 있었다.
    @Value("${payment.timeout-ms:3000}")키가 안 맞으니 3000. 로그도 경고도 없다
    private int timeoutMs;              // 의도했던 값은 10000

    // 운영 yml에서 이 키를 통째로 빠뜨렸다. 기본값 0이 들어간다.
    @Value("${payment.retry-count:0}")"재시도 0회"는 문법적으로 완벽히 유효한 값이다
    private int retryCount;
}
after 그룹 바인딩 + 검증 — 잘못된 설정이면 앱이 아예 뜨지 않는다
@Validated                                ① 이게 있어야 아래 제약이 실제로 검사된다
@ConfigurationProperties(prefix = "payment")
public record PaymentProperties(
        @NotBlank String apiUrl,          // ② 비어 있으면 안 된다
        @NotNull Duration timeout,        // ③ yml에 timeout: 3s 로 적는다
        @Min(1) @Max(5) int retryCount     // ④ "값이 있음"이 아니라 "값이 유효함"을 본다
) {}

payment.timeout을 오타 냈다면 timeout이 null이 되고, @NotNull 위반으로 기동이 실패한다. 배포 파이프라인이 그 자리에서 빨간불이 되므로 운영에 나가지 못한다.

같은 사상의 반복 — 프로파일 문서와 한 몸이다 이것은 09-application-yml-profile.md에서 본 것과 정확히 같은 설계 결정이다 — "안전하지 않으면 조용히 도는 대신 아예 뜨지 않게 한다." 프로파일 누락을 기동 실패로 바꾼 것과, 설정 오타를 기동 실패로 바꾸는 것은 같은 종류의 선택이다.

붙였다고 안심하면 안 되는 것 — @Validated의 세 가지 전제

① 클래스에 붙여야 한다
@Validated를 클래스(레코드)에 붙여야 검증이 켜진다. 필드에 제약만 달아두면 아무 일도 일어나지 않는다.
② 구현체가 있어야 한다
jakarta.validation 구현체가 클래스패스에 있어야 한다. 실무에서는 spring-boot-starter-validation을 추가한다.
③ 중첩은 @Valid
중첩 객체는 그 필드에 @Valid를 추가로 붙여야 안쪽까지 검사한다. 안 붙이면 바깥 껍데기만 본다.
확인 방법: 일부러 틀린 값을 넣고 기동이 죽는지 한 번 본다 — 이 한 번이 "검증한다고 믿었는데 안 하고 있었다"를 막는다

5. 사고 ② — "값이 있음"과 "값이 유효함"은 다르다 반문 대비

4절의 표에서 본 것처럼 @Value도 기본값 없는 키가 빠지면 기동에 실패하기는 한다. 그래서 "@Value도 fail-fast 되는 것 아니냐"는 반문이 자주 나온다. 두 실패 메시지를 나란히 놓으면 차이가 분명해진다.

@Value 알려주는 것은 "이 키가 없다" 하나뿐
***************************
APPLICATION FAILED TO START
***************************

Description:

Failed to bind properties under '' to java.lang.String:

... (실제로는 대개 아래 예외가 원인으로 찍힌다)
java.lang.IllegalArgumentException: Could not resolve
placeholder 'payment.api-url' in value "${payment.api-url}"
@ConfigurationProperties + @Validated 네 줄이 전부 말해준다
***************************
APPLICATION FAILED TO START
***************************

Description:

Binding to target com.example.payment.PaymentProperties failed:

    Property: payment.retryCount
    Value: "0"
    Origin: class path resource [application.yml] - 12:20
    Reason: must be greater than or equal to 1

Action:
    Update your application's configuration

왼쪽이 알려주는 것은 "이 키가 없다" 하나뿐이다. 값이 존재하기만 하면 그 값이 말이 되는지는 전혀 보지 않는다. retry-count: -5도, retry-count: 9999도 통과한다. 오른쪽 네 줄이 각각 무엇을 알려주는지 짚어 보면 값어치가 드러난다.

오른쪽 네 줄이 없다면 각각을 사람이 손으로 알아내야 한다 — 그것도 장애 중에.
글자줄알려주는 것이 줄이 없으면 뭘 해야 하나
PProperty: payment.retryCount어느 프로퍼티가 문제인지전체 설정을 눈으로 훑어야 한다
VValue: "0"실제로 바인딩된 값이 무엇인지로그를 찍어 재배포하고 확인해야 한다
OOrigin: application.yml - 12:20어느 파일 몇 번째 줄 몇 번째 칸에서 온 값인지어느 프로파일 파일이 이겼는지를 우선순위 규칙으로 역추적해야 한다
RReason: must be greater than or equal to 1어떤 규칙을 어겼는지코드를 읽어 의도를 역추적해야 한다

암기 장치 — 기동 실패 메시지 네 줄은 P · V · O · R

Property(어느 키) · Value(무슨 값) · Origin(어느 파일 몇 줄) · Reason(왜 틀렸나)

면접에서 "검증이 된다"보다 "P·V·O·R 네 줄이 찍히고 앱이 안 뜬다"가 압도적으로 구체적이다. 특히 Origin을 언급하는 사람은 드물다.

왜 Origin이 실무에서 가장 크게 느껴지나 설정값은 여러 층에서 덮어써진다(커맨드라인 > 환경변수 > 프로파일 yml > 기본 yml). 그래서 장애 중에 늘 따라붙는 의심이 "내가 고친 파일이 실제로 이긴 파일이 맞나"인데, Origin이 그 답을 직접 준다. Origin이 application-prod.yml이 아니라 application.yml을 가리키고 있다면 — 프로파일 파일에 그 키가 아예 없다는 뜻이다.

Reason에 찍히는 문구는 Bean Validation 제약의 기본 메시지다. @Min(1) → must be greater than or equal to 1, @NotBlank → must not be blank, @NotNull → must not be null. 직접 지정하면 그 문구가 그대로 찍히므로, 팀에서 자주 실수하는 설정에는 한국어 안내를 넣어 두는 것도 좋다.

@Min(value = 1, message = "재시도는 1회 이상이어야 합니다") int retryCountReason 줄에 이 문구가 그대로 찍힌다

이 절을 한 문장으로 봉인

@Value가 잡는 것은 "값의 부재"뿐이고, @ConfigurationProperties + @Validated가 잡는 것은 "값의 부적절함"이다

그리고 실무의 설정 사고는 대부분 후자다 — 값이 없어서 나는 사고보다, 값이 있는데 틀려서 나는 사고가 훨씬 많고 훨씬 늦게 발견된다.

6. 사고 ③ — 키 표기가 안 맞아 값이 안 들어간다: relaxed binding

relaxed binding은 "느슨한 바인딩"이라는 뜻으로, 같은 프로퍼티를 여러 표기법으로 써도 전부 같은 것으로 인식해 주는 규칙이다. 이름에 "느슨한"이 붙은 이유는, 키를 글자 그대로 대조하는 엄격한 방식과 대비되기 때문이다.

암기 장치 — 표기 4종은 "케 · 카 · 스 · 대"

케밥(retry-count) · 카멜(retryCount) · 스네이크(retry_count) · 대문자 스네이크(RETRY_COUNT)

yml에는 케밥이 권장 표기이고, 대문자 스네이크는 환경변수 자리다 — 이 두 개만 정확히 말해도 충분하다.

6-1. @Value에는 이 깔때기가 없다 — 다만 흔한 오해 하나

@Value에는 relaxed binding이 없다. ${...} 안에 적은 문자열로 사전을 조회할 뿐이다.

@Value("${payment.retryCount}")   // yml에는 retry-count 로 적혀 있다
private int retryCount;           // → Could not resolve placeholder. 기동 실패.
여기서 정확히 갈라야 할 오해 — "그럼 @Value는 환경변수로 못 덮나?" 덮을 수 있다. 다만 relaxed binding과는 다른 경로다. 환경변수를 담는 프로퍼티 소스 자체가 조회할 때 이름을 한 번 정규화해 주기 때문이다 — 점과 하이픈을 밑줄로 바꾸고 대문자로 올려 다시 찾아본다. 그래서 @Value("${payment.retry-count}")는 환경변수 PAYMENT_RETRY_COUNT로 덮인다.
@Value에 없는 것은 "yml 키 표기 사이의 유연함"이다. yml에 retry-count로 적어 놓고 @Value("${payment.retryCount}")로 읽으려 하면 못 찾는다. 그리고 이 실수는 위험한 방향으로 조용하다 — 기본값을 붙여 뒀다면(4절) 기동조차 실패하지 않는다.
틀린 요약
"@Value는 환경변수로 못 덮는다" — 사실이 아니다. 이렇게 답하면 반례 하나로 무너진다.
정확한 요약
"환경변수 오버라이드는 둘 다 된다. @Value에 없는 것은 yml 안에서의 표기 유연함이다."

7. 사고 ④⑤ — 흩어진 설정은 회수할 수 없고, 가변 설정은 언젠가 누가 바꾼다

7-1. 사고 ④ — 산탄총 수술(shotgun surgery)

@Value는 붙이는 자리가 자유롭다. 아무 빈의 아무 필드에나 붙일 수 있다. 편해 보이지만, 프로젝트가 커지면 이 자유가 문제가 된다.

before 같은 payment 설정이 세 클래스에 흩어져 있다
@Component class PaymentClient   { @Value("${payment.api-url}")       String url; }
@Component class PaymentRetrier  { @Value("${payment.retry-count:0}") int retry; }
@Component class PaymentMetrics  { @Value("${payment.api-url}")       String url; }같은 키가 두 곳에 중복

payment.api-url을 payment.gateway.url로 이름을 바꿔야 한다고 하자. 무엇을 해야 하나. 문자열 전체 검색이 유일한 수단이다. 컴파일러는 도와주지 않는다 — @Value 안의 문자열은 컴파일러 입장에서 그냥 문자열 상수이므로, 하나를 빠뜨려도 빌드가 성공한다. 빠뜨린 그 하나는 기동 시점(기본값이 없다면)이나 런타임(기본값이 있다면)에야 드러난다.

after 설정이 타입으로 흐른다 — 문자열 키는 PaymentProperties 안에만 있다
@Component
public class PaymentClient {

    private final PaymentProperties props;

    public PaymentClient(PaymentProperties props) { this.props = props; }

    public void call() {
        // props.apiUrl() 은 컴파일러가 아는 이름이다.
        restClient.get().uri(props.apiUrl()).retrieve();이름을 바꾸면 이 줄에서 컴파일 에러
    }
}
부수적으로 따라오는 것 — IDE 자동완성 spring-boot-configuration-processor 의존성을 추가하면 컴파일 시점에 프로퍼티 클래스를 읽어 메타데이터 파일(META-INF/spring-configuration-metadata.json)을 생성한다. 그러면 IDE가 application.yml에서 payment.까지만 쳐도 자동완성과 타입 힌트, 자바독 설명까지 보여준다. 오타를 애초에 안 내게 만드는 예방책이다 — 4·5절이 "오타를 빨리 잡는" 장치라면 이것은 "오타를 덜 내게 하는" 장치다.

7-2. 사고 ⑤ — 설정 객체가 가변이면 언젠가 누가 바꾼다

@Value 필드 주입은 final을 쓸 수 없다. 객체를 먼저 만들고 나중에 리플렉션으로 값을 꽂는 순서라서, final 필드에는 넣을 자리가 없기 때문이다. @ConfigurationProperties의 setter 기반 바인딩도 마찬가지로 setter가 있어야 하므로 가변이다. 가변이라는 것은 곧 기동 후에 누군가 값을 바꿀 수 있다는 뜻이다.

가변 설정 빈이 만드는 사고

@Service
public class BatchService {
    private final PaymentProperties props;

    public void runBulk() {
        props.setTimeout(Duration.ofMinutes(5));"배치니까 늘리자"
        // ... 그리고 되돌리지 않는다.
    }
}
  • @ConfigurationProperties 빈은 싱글턴이다 — 한 곳에서 바꾸면 그 빈을 주입받은 모든 곳의 값이 함께 바뀐다.
  • 온라인 결제 경로의 타임아웃까지 5분이 된다.
  • 스레드 안전하지도 않다 — 어떤 요청은 3초를, 어떤 요청은 5분을 본다. 재현 불가능한 산발 오류가 된다.
  • 이런 코드는 리뷰를 통과해 버린다 — 문법적으로 아무 문제가 없기 때문이다.

생성자 바인딩이면 이 사고가 구조적으로 불가능

@Validated
@ConfigurationProperties(prefix = "payment")
public record PaymentProperties(
        @NotNull Duration timeout, ...
) {}
// setter가 없다 → 바꿀 방법이 없다
// props.setTimeout(...) 은 컴파일조차 안 된다
  • 객체가 완성되는 순간 이미 모든 값이 들어가 있다 → 필드를 final로 둘 수 있고, 곧 불변이다.
  • "조심하자"는 규율이 아니라 컴파일러가 막는다.
  • 배치에서 타임아웃을 다르게 쓰고 싶다면 설정 키를 따로 두는 것이 옳은 해법이다(payment.batch.timeout).

두 사고를 한 줄로

문자열로 흩어놓으면 회수할 수 없고, 가변으로 두면 언젠가 누가 바꾼다

둘 다 "사람이 조심하면 되는 문제"처럼 보이지만, 실제로는 구조로만 막히는 문제다. 이 관점이 이 질문의 출제 의도(설정도 코드처럼 취급하는 규율)와 정확히 맞닿는다.

8. 실무 표준형 — 생성자 바인딩 · record · 등록 방법

8-1. 생성자 바인딩과 record

생성자 바인딩(constructor binding)은 setter로 하나씩 채우는 대신 생성자 파라미터로 한 번에 채우는 바인딩 방식이다. 객체가 완성되는 순간 이미 모든 값이 들어가 있으므로 필드를 final로 둘 수 있고, 곧 불변 객체가 된다.

버전에 따라 문법이 다르므로 정확히 짚는다. 면접에서 이 구분을 말하면 "최근에 써본 사람"으로 들린다.
부트 버전필요한 선언비고
2.2 ~ 2.x클래스 또는 생성자에 @ConstructorBinding 필수패키지: ...context.properties.ConstructorBinding
3.0 ~생성자가 하나면 생략 가능. 생성자가 여럿일 때만 그중 하나에 붙인다패키지 이동: ...context.properties.bind.ConstructorBinding, 그리고 생성자에만 붙일 수 있다

부트 3에서 record를 쓰면 생성자가 자동으로 하나뿐이므로 애너테이션이 아예 필요 없다. 이것이 요즘 가장 깔끔한 형태다.

after 부트 3.x — 애너테이션 두 개로 끝난다
@Validated
@ConfigurationProperties(prefix = "payment")
public record PaymentProperties(
        @NotBlank String apiUrl,
        @NotNull Duration timeout,
        @Min(1) @Max(5) int retryCount,
        Retry retry           // 중첩 설정도 record로
) {
    // payment.retry.* 아래가 여기로 들어온다
    public record Retry(@NotNull Duration backoff,
                        boolean jitter) {}
}
yml 타입이 단위를 강제한다
payment:
  api-url: https://pg.example.com
  timeout: 3s              # Duration으로 변환된다 (3초)
  retry-count: 3
  retry:
    backoff: 500ms
    jitter: true

timeout: 3s가 Duration이 되는 것은 부트의 ApplicationConversionService가 Duration·DataSize 전용 컨버터를 제공하기 때문이다. s, ms, m, h 접미어를 알아듣고, 단위 없이 숫자만 쓰고 싶으면 @DurationUnit(ChronoUnit.SECONDS)로 기본 단위를 지정할 수 있다. DataSize도 같은 방식으로 10MB를 파싱한다.

함정 — 생성자 바인딩이 조용히 안 먹는 조건

생성자 바인딩은 @EnableConfigurationProperties나 @ConfigurationPropertiesScan으로 등록한 경우에만 동작한다. 프로퍼티 클래스에 @Component를 붙여 컴포넌트 스캔으로 올리면 스프링의 일반 빈 생성 경로를 타므로 setter 기반 JavaBean 바인딩만 적용되고, record처럼 setter가 없는 타입은 값이 채워지지 않는다.

증상: "record로 만들었더니 값이 전부 null/0이다" → 가장 먼저 등록 경로(@Component를 붙이지 않았는지)를 본다

8-2. 등록 방법 두 가지

방법 1 패키지 스캔 — 애플리케이션 코드에 편하다
// 메인 클래스에 한 번만 붙이면
// @ConfigurationProperties 붙은 클래스를 전부 찾는다
@SpringBootApplication
@ConfigurationPropertiesScan
public class MyApplication { ... }
방법 2 명시 등록 — 라이브러리·자동 구성에 쓴다
// 필요한 것만 하나씩 올린다
@Configuration
@EnableConfigurationProperties(PaymentProperties.class)
public class PaymentConfig { ... }

라이브러리나 자동 구성 모듈을 만들 때는 방법 2를 쓴다. 컴포넌트 스캔 범위에 의존하지 않고 "이 설정 클래스가 필요하다"를 코드로 명시하기 때문이다. 애플리케이션 코드에서는 방법 1이 편하다.

9. @Value만 할 수 있는 것 — SpEL, 그리고 그 대가 균형 잡기

@Value가 여전히 살아남는 이유는 하나다. SpEL(Spring Expression Language) — 문자열 안에 작은 표현식을 써서 값을 계산할 수 있는 문법이다. ${...}가 "사전에서 값을 꺼내라"라면, #{...}는 "이 식을 평가해라"다.

SpEL 실제 용도 세 가지
public class TimeConfig {

    // ① JVM 시스템 프로퍼티 읽기 — Environment의 프로퍼티 키로는 안 잡히는 값
    @Value("#{systemProperties['user.timezone']}")
    private String jvmTimezone;

    // ② 다른 빈의 값 참조 — 설정 파일에 없는, 런타임에 계산되는 값
    @Value("#{schedulerConfig.poolSize * 2}")
    private int workerCount;

    // ③ 문자열을 리스트로 쪼개기 (프로퍼티 값 + 표현식 조합)
    @Value("#{'${payment.allowed-methods}'.split(',')}")
    private List<String> allowedMethods;
}

여기까지가 장점이다. 그런데 이 유연함이 왜 오히려 위험한지를 함께 말할 수 있어야 균형이 잡힌다.

1
설정 로직이 문자열 안에 숨는다. #{schedulerConfig.poolSize * 2}는 명백히 로직이다 — "워커 수는 풀 크기의 두 배"라는 정책이 문자열 안에 들어가 있다. 자바 코드로 썼다면 메서드 하나에 이름이 붙고 테스트가 붙었을 규칙이, 애너테이션 인자 안에 갇힌다.
2
컴파일러와 IDE의 사정권 밖이다. schedulerConfig라는 빈 이름을 바꾸거나 poolSize 게터를 getCorePoolSize()로 리팩터링해도 컴파일은 성공한다. IDE의 "이름 바꾸기(rename)" 리팩터링도 이 문자열은 건드리지 않는다. 깨진 사실은 기동할 때 SpelEvaluationException으로 처음 드러난다.
3
표현식이 커지면 아무도 못 읽는다. 위 ③번만 해도 #{'${...}'.split(',')}처럼 따옴표와 두 종류의 괄호가 섞여 있다. 여기에 조건식이나 ?:가 붙기 시작하면 리뷰가 불가능해진다.
before 설정 로직을 SpEL 문자열에
@Value("#{'${payment.allowed-methods}'.split(',')}")
private List<String> allowedMethods;

// 리팩터링에 취약하고, 이 규칙만 따로 테스트할 방법이 없다
after 리스트 바인딩은 기본 제공된다
// yml: payment.allowed-methods: CARD,BANK
@ConfigurationProperties(prefix = "payment")
public record PaymentProperties(List<String> allowedMethods) {}

// 쉼표 구분 문자열도, yml 리스트 표기도 그대로 들어온다

SpEL 사용 기준 한 줄

SpEL은 "설정 파일로는 표현할 수 없는 런타임 값"에만 쓴다

값을 쪼개거나 계산하는 정도의 일은 대부분 @ConfigurationProperties의 타입 변환이 이미 해준다. "SpEL이 되니까 @Value가 낫다"가 아니라 "SpEL이 필요한 자리에만 @Value"가 정확한 표현이다.

10. 선택 기준 · 인출 카드 · 꼬리질문 셀프 테스트

10-1. 선택 기준 — 이 세 줄이 답의 마지막 문단이다

고민 없이 판단하는 기준

묶인 설정이 2개 이상
→ 고민 없이 @ConfigurationProperties. 검증·불변·테스트 용이성·자동완성이 전부 따라온다.
SpEL이 꼭 필요한 단발 값
→ @Value. #{systemProperties[...]}, 다른 빈의 값 참조처럼 설정 파일로 표현할 수 없는 런타임 값.
애매하면
→ @ConfigurationProperties. 설정은 늘어나기 마련이고, 흩어진 @Value를 나중에 회수하는 비용이 처음부터 클래스 하나 만드는 비용보다 훨씬 크다(7절).
한 줄: "묶이면 클래스로, SpEL이 필요한 단발만 @Value"

덧붙이면 인상이 달라지는 한 문장 — 기본값을 함부로 붙이지 않는다

@Value를 쓰더라도 기본값(:default)은 함부로 붙이지 않는다. 기본값은 "이 값이 없어도 이 앱은 올바르게 동작한다"는 선언인데, 대부분의 설정은 그렇지 않다. 없으면 기동이 실패하도록 두는 편이 4절의 사고를 막는다.

10-2. 3초 인출 카드 — 보기 전에 먼저 답해보기

한 문장 차이는?
@Value는 키 하나를 문자열로 찍어 필드에, @ConfigurationProperties는 프리픽스 그룹을 타입 세이프 객체에 통째로.
사고 5종은?
침·무·불·산·가 — 침묵하는 기본값 · 무검증 · 표기 불일치 · 산탄총 · 가변.
기동 실패 메시지 네 줄은?
P·V·O·R — Property · Value · Origin(파일:줄) · Reason. Origin이 "어느 파일이 이겼나"를 직접 답해준다.
@Value가 잡는 것 / 못 잡는 것은?
잡는 것은 "값의 부재"뿐. "값의 부적절함"(retry-count: -5)은 그대로 통과시킨다.
relaxed binding 표기 4종은?
케·카·스·대 — retry-count · retryCount · retry_count · RETRY_COUNT. 마지막이 환경변수 자리.
"@Value는 환경변수로 못 덮는다"?
틀렸다. 덮인다(환경변수 소스가 이름을 정규화한다). @Value에 없는 것은 yml 안에서의 표기 유연함이다.
부트 3의 표준형은?
@Validated + @ConfigurationProperties + record. 생성자가 하나라 @ConstructorBinding도 생략.
record인데 값이 전부 null이면?
등록 경로를 본다. @Component로 올리면 setter 바인딩만 적용돼 record는 안 채워진다. @ConfigurationPropertiesScan/@EnableConfigurationProperties로.
@Value가 여전히 옳은 자리는?
스·단·라 — 스펠(SpEL) 필요 · 진짜 단발 값 · 라이브러리에서 프로퍼티 클래스를 노출하기 싫을 때.
이 질문의 본질은?
애너테이션 선택이 아니라 "설정을 코드와 같은 급으로 취급하는가" — 타입 · 컴파일러 검사 · 테스트 · 안전한 리팩터링.

10-3. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

@Value도 키 오타면 기동에 실패하지 않나요? 필수힌트: "절반만 맞다"로 시작한다. 갈라야 할 축은 두 개 — 기본값 유무, 그리고 "있음 vs 유효함"

절반만 맞다. 기본값(:default)이 없는 키는 Could not resolve placeholder로 기동에 실패한다. 하지만 기본값이 붙은 키는 누락되거나 오타가 나도 조용히 그 기본값으로 흘러간다 — 로그도 경고도 없다.

그리고 더 중요한 차이가 있다. @Value가 검사하는 것은 "값이 있는가"뿐이고, "값이 유효한가"는 보지 않는다. retry-count: -5도, timeout: 0도 통과한다. @Min(1) 같은 제약으로 유효성까지 기동 시점에 잡는 것은 @ConfigurationProperties + @Validated만 할 수 있다.

실무의 설정 사고는 대부분 후자 쪽이다 — 값이 없어서 나는 사고보다, 값이 있는데 틀려서 나는 사고가 훨씬 늦게 발견된다.

기동 시점 검증이 된다는 걸 구체적으로 말해보세요. 로그에 뭐가 찍히나요? 필수힌트: 네 글자 — P · V · O · R. 이 중 하나는 남들이 잘 언급하지 않는다

Binding to target ... failed: 아래에 네 줄이 찍히고 앱이 뜨지 않는다.

    Property: payment.retryCount
    Value: "0"
    Origin: class path resource [application.yml] - 12:20
    Reason: must be greater than or equal to 1

어느 프로퍼티가(P), 어떤 값으로(V), 어느 파일 몇 번째 줄에서 와서(O), 어떤 규칙을 어겼는지(R)가 전부 나온다. 특히 Origin이 실무에서 크다 — 설정은 커맨드라인 > 환경변수 > 프로파일 yml > 기본 yml 순으로 덮어써지므로 "내가 고친 파일이 실제로 이긴 파일이 맞나"가 늘 의심스러운데, Origin이 그 답을 직접 준다.

Reason은 Bean Validation 제약의 기본 메시지다(@Min(1) → must be greater than or equal to 1). @Min(value = 1, message = "재시도는 1회 이상이어야 합니다")처럼 지정하면 그 문구가 그대로 찍히므로, 팀에서 자주 틀리는 설정에는 한국어 안내를 넣어 두면 좋다.

@Validated를 붙였는데 검증이 안 도는 것 같습니다. 어디부터 보나요? 함정힌트: 세 가지 전제 — 붙인 위치, 구현체 존재, 중첩

세 가지를 순서대로 본다.

① 붙인 위치 — @Validated는 클래스(레코드)에 붙어야 한다. 필드에 @Min만 달아두면 아무 일도 일어나지 않는다.

② 구현체 존재 — jakarta.validation 구현체가 클래스패스에 있어야 한다. 실무에서는 spring-boot-starter-validation을 추가하면 된다. 이게 없으면 제약 애너테이션은 붙어만 있고 아무 일도 하지 않는다.

③ 중첩 객체 — 안쪽까지 검사하려면 그 필드에 @Valid를 추가로 붙여야 한다. 안 붙이면 바깥 껍데기만 본다.

그리고 확인 방법을 함께 말하면 좋다 — 일부러 틀린 값을 넣고 기동이 죽는지 한 번 본다. "검증한다고 믿었는데 안 하고 있었다"가 이 영역에서 가장 흔한 사고이고, 검증 장치를 도입한 사람의 책임은 그것이 실제로 도는지 한 번 확인하는 데까지다.

record로 만들었는데 값이 전부 null·0입니다. 왜죠? 함정힌트: 문법 문제가 아니라 "어떤 경로로 빈이 되었는가" 문제다

등록 경로를 가장 먼저 의심한다. 생성자 바인딩은 @EnableConfigurationProperties나 @ConfigurationPropertiesScan으로 등록한 경우에만 동작한다. 프로퍼티 클래스에 @Component를 붙여 컴포넌트 스캔으로 올리면 스프링의 일반 빈 생성 경로를 타므로 setter 기반 JavaBean 바인딩만 적용되고, record처럼 setter가 없는 타입은 값이 채워지지 않는다.

그 다음으로 볼 것은 prefix 값과 yml의 들여쓰기다. 부트 3.x라면 @ConstructorBinding은 생성자가 하나뿐이면 필요 없다는 점도 함께 기억해 둔다 — 부트 2.x에서 넘어온 코드에는 이 애너테이션이 클래스에 붙어 있는 경우가 있는데, 부트 3에서는 생성자에만 붙일 수 있다.

record로 만들면 값을 못 바꾸는데, 운영 중에 설정을 바꿔야 하면요? 가산점힌트: "못 바꾸는 것이 목적이다"로 시작하고, 동적 갱신의 새 결합까지 말한다

못 바꾸는 것이 목적이다. 싱글턴 설정 빈을 아무나 바꿀 수 있으면 한 곳의 변경이 전체에 새는 사고가 난다(7-2절). 게다가 그 변경은 스레드 안전하지도 않아 어떤 요청은 3초를, 어떤 요청은 5분을 보는 재현 불가능한 상태가 된다.

런타임 동적 갱신이 정말 필요하다면 그건 별도 장치의 영역이다. Spring Cloud Config Server + @RefreshScope 조합이 대표적으로, 설정 서버의 값이 바뀌면 해당 빈을 새로 만들어 교체한다. 값을 수정하는 게 아니라 객체를 통째로 갈아 끼우는 방식이므로 불변성과 충돌하지 않는다.

여기서 트레이드오프를 함께 말하면 좋다. 동적 갱신은 "설정 서버가 죽으면 전 서비스가 영향을 받는" 새 결합을 만든다. 서비스 몇 개 규모에서는 재배포로 설정을 바꾸는 편이 단순하고 안전하다.

Duration은 어떻게 3s를 파싱하나요? 가산점힌트: 컨버터 이름을 대고 끝내면 절반이다. "이 변환 자체가 검증"이라는 데까지 간다

부트의 ApplicationConversionService가 Duration·DataSize 등에 대한 전용 컨버터를 등록해 두기 때문이다. 3s, 500ms, 10m, 2h 같은 접미어를 알아듣는다. 단위 없이 숫자만 쓰고 싶으면 필드에 @DurationUnit(ChronoUnit.SECONDS)을 붙여 기본 단위를 지정한다. DataSize도 같은 구조로 @DataSizeUnit이 있고 10MB 같은 표기를 파싱한다.

여기서 한 걸음 더 들어가면 변별이 된다 — 이 변환은 그 자체로 검증 역할을 한다. timeout: 3초처럼 파싱할 수 없는 값을 쓰면 바인딩 단계에서 실패해 앱이 뜨지 않는다. 반대로 @Value("${payment.timeout-ms}") int로 받았다면 밀리초 단위라는 사실이 필드 이름에만 적혀 있어 yml에 10(10ms를 의도했는지 10초를 의도했는지 모를 값)을 써도 아무도 못 잡는다. 타입이 단위를 강제하는 것이 Duration의 진짜 값어치다.

프로퍼티 클래스에 정의하지 않은 키를 yml에 적어두면 어떻게 되나요? 함정힌트: 바인딩은 "클래스 → yml" 방향으로만 본다. 그래서 무엇이 안 잡히는지

기본적으로 조용히 무시된다. 바인딩은 "클래스에 있는 필드를 채우는" 방향으로 동작하므로, 클래스에 없는 키가 yml에 남아 있어도 아무 일도 일어나지 않는다.

여기서 중요한 결론이 나온다 — 키 이름을 틀리게 적는 실수 자체를 스프링이 잡아주는 것은 아니다. payment.retry-count를 payment.retrycount로 적으면 그 줄은 무시되고, 클래스 쪽 필드는 바인딩되지 않은 채 남는다.

그래서 두 장치가 짝으로 필요하다. ① @NotNull·@Min 같은 제약 — 안 채워진 필드를 기동 시점 실패로 바꾼다(4·5절). ② spring-boot-configuration-processor — IDE 자동완성으로 오타를 애초에 덜 내게 한다(7-1절). 전자는 사후 탐지, 후자는 사전 예방이고 둘은 대체재가 아니다.

@ConfigurationProperties 빈을 다른 빈에서 어떻게 쓰나요? 필수힌트: "생성자 주입"으로 끝내지 말고, 그래서 테스트가 어떻게 가벼워지는지까지

일반 빈처럼 생성자 주입으로 받으면 된다. @Autowired도 필요 없다(생성자가 하나면 생략 가능).

@Service
public class PaymentService {
    private final PaymentProperties props;
    public PaymentService(PaymentProperties props) { this.props = props; }
}

효과는 "편하다"에 그치지 않는다. 설정이 문자열 키가 아니라 타입으로 흐르므로, 어떤 설정이 어디서 쓰이는지를 IDE의 "사용처 찾기"로 정확히 알 수 있고, 이름을 바꾸면 컴파일러가 모든 사용처를 짚어 준다(7-1절).

테스트도 쉬워진다. 스프링 컨텍스트 없이 그냥 만들면 된다.

// 스프링을 띄우지 않는 순수 단위 테스트
var props = new PaymentProperties("https://stub", Duration.ofSeconds(3), 3, null);
var service = new PaymentService(props);

@Value 필드 주입은 이게 안 된다. new PaymentClient()로 만들면 @Value 필드가 전부 null·0이라, 값을 넣으려면 리플렉션(ReflectionTestUtils.setField)을 쓰거나 스프링 컨텍스트를 통째로 띄워야 한다. 테스트가 무거워지는 원인이 사실은 설정 주입 방식에 있는 경우가 흔하다.

한 클래스에서 @Value와 @ConfigurationProperties를 섞어 써도 되나요?힌트: "동작은 한다"에서 출발해, 무엇이 나빠지는지로 넘어간다

동작은 한다. 서로 배타적인 장치가 아니다. 다만 같은 설정 그룹을 두 경로로 읽는 상태가 문제다 — payment.timeout은 프로퍼티 클래스에서 오고 payment.retry-count는 어느 서비스의 @Value에서 온다면, "이 그룹의 설정이 어디까지인지"를 아는 사람이 없어진다. 7-1절의 산탄총 상태가 절반만 해소된 채로 굳는다.

그래서 실무 기준은 "그룹 단위로 옮기고, 옮긴 그룹의 @Value는 남기지 않는다"다. 레거시를 마이그레이션할 때는 프리픽스 하나씩 끊어서 옮기고, 옮긴 프리픽스에 대해 grep "${payment."가 0건이 되는 것을 완료 조건으로 삼으면 깔끔하다.

세 층으로 나눠 답한다.

① 예방(오타를 덜 내게) — spring-boot-configuration-processor로 IDE 자동완성을 켠다. yml 표기는 케밥 케이스로 통일한다.

② 탐지(오타를 기동 실패로) — 운영에 영향을 주는 값은 전부 @ConfigurationProperties + @Validated로 옮기고, @Value의 기본값(:default)을 함부로 붙이지 않는다. 기본값을 붙이는 순간 그 키는 오타를 검출할 수 없는 키가 된다.

③ 게이트(실패를 배포 전에) — 탐지 장치가 있어도 그 프로파일로 한 번 떠보지 않으면 소용이 없다. 운영과 같은 프로파일·환경변수 조합으로 컨텍스트를 띄우는 테스트를 CI에 넣거나, 배포 파이프라인에 스테이징 기동 확인 단계를 둔다. 기동 실패는 그 자리에서 빨간불이 되어야 의미가 있다.

정리하면 "발각 시점을 왼쪽으로 당긴다"는 3절의 시간 축이 그대로 파이프라인 설계가 된다.

그럼 @Value는 이제 안 쓰는 게 맞나요? 시니어 변별힌트: 단정하면 감점이다. "경계를 그어" 답하고, 마지막에 층위를 한 칸 올린다

"안 쓴다"고 단정하면 오히려 감점이다. 경계를 그어 답하는 것이 이 질문의 의도다.

@Value가 여전히 옳은 자리는 셋이다(스·단·라). ① SpEL이 필요한 값(다른 빈 참조, 시스템 프로퍼티), ② 프로퍼티 클래스를 만들 만큼 묶이지 않은 진짜 단발 값 하나, ③ 라이브러리 코드에서 프로퍼티 클래스를 노출하고 싶지 않을 때.

@ConfigurationProperties로 가야 하는 자리는 그 외 전부다. 특히 운영에 영향을 주는 값(타임아웃, 재시도, 풀 크기, 외부 연동 주소)은 예외 없이 이쪽이어야 한다. 이유는 4~7절 전체다 — 이 값들이야말로 틀렸을 때 늦게, 그리고 장애 중에 발견되는 값들이다.

한 걸음 더 나아가면 이렇게 정리할 수 있다. 이 질문의 본질은 애너테이션 선택이 아니라 "설정을 코드와 같은 급으로 취급하는가"다. 코드에는 타입이 있고, 컴파일러가 검사하고, 테스트가 있고, 리팩터링이 안전하다. @ConfigurationProperties는 설정에 그 넷을 전부 붙여 주는 장치이고, @Value 산탄총은 설정을 "문자열 키로 아무 데서나 꺼내 쓰는 전역 변수" 상태로 두는 것이다.

설정 오타는 코드 버그와 똑같은 무게의 사고인데, 코드 버그는 컴파일러와 테스트가 잡아 주고 설정 오타는 아무도 안 잡아 준다면 — 그 비대칭을 메우는 것이 @Validated + 기동 시점 실패다.

한 줄 요약
@Value는 문자열 키로 값 하나를 찍어 오는 도구라 SpEL이 필요한 단발 값에만 쓰고, 그 외에는 @ConfigurationProperties로 프리픽스 그룹을 불변·타입 세이프 객체(부트 3에서는 record 하나로 충분)에 바인딩한 뒤 @Validated로 잘못된 설정을 Property · Value · Origin · Reason이 찍히는 기동 시점 실패로 드러내는 것이 정석이다 — relaxed binding 덕에 환경변수로 운영 값을 덮어쓰는 길까지 열리므로, 묶인 설정이 2개 이상이면 고민 없이 후자다.
