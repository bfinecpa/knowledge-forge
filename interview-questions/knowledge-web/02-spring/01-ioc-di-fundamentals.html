IoC와 DI
제어의 역전과 의존성 주입 — 무엇이고, 왜 쓰는가

면접 질문: "IoC와 DI란 무엇이고, 왜 사용하나요?"

핵심 관전 포인트 — IoC(제어의 역전)는 "객체를 언제 만들고, 누구와 연결하고, 언제 없앨지"를 결정하는 주도권을 내 코드에서 스프링 컨테이너로 넘기는 설계 원칙이고, DI(의존성 주입)는 그 원칙을 실현하는 구체적 수단이다 — 필요한 협력 객체를 클래스 안에서 new로 직접 만들지 않고 밖에서 넣어받는 것. 이렇게 하면 클래스가 구현체 이름이 아니라 인터페이스에만 의존하게 되어, 결제사를 Toss에서 Kakao로 바꿀 때 고쳐야 하는 곳이 new가 흩어진 파일 전부에서 빈 설정 한 곳으로 줄고, 테스트에서는 컨테이너를 띄우지 않고 new OrderService(가짜 게이트웨이) 한 줄로 진짜 결제 API를 차단할 수 있다. 여기에 컨테이너가 객체를 손에 쥐고 있기에 가능해지는 것이 하나 더 있다 — @Transactional·@Cacheable 같은 프록시 기반 AOP다. 내가 new로 만든 객체에는 스프링이 프록시를 씌울 기회가 없으므로 그 애너테이션들이 조용히 무효가 된다.
  • 1
    IoC는 원칙(what), DI는 그 원칙을 실현하는 방식(how)이다 — 객체의 생성·조립·생명주기 주도권을 내 코드가 아니라 컨테이너가 갖게 하고(IoC), 그 결과로 클래스는 필요한 협력 객체를 인터페이스 타입으로 밖에서 넣어받는다(DI). 내 코드는 프레임워크를 부르는 쪽이 아니라 호출당하는 쪽이 된다.
  • 2
    "왜"의 답은 두 가지 수치로 말한다 — ① 결합도: PG사를 바꿀 때 열어야 하는 파일이 new가 흩어진 7개에서 설정 1개로 줄어든다. ② 테스트 가능성: new OrderService(mock) 한 줄이면 컨테이너도 네트워크도 없이 "PG 타임아웃 시 주문이 어떻게 되는가" 같은 예외 경로까지 검증할 수 있다.
  • 3
    세 번째 실익은 컨테이너가 객체를 쥐고 있어야만 생긴다 — @PostConstruct·싱글턴 보장, 그리고 프록시 기반 AOP가 그것이다. 뒤집어 말하면 "DI가 안 되면 @Transactional도 안 먹는다" — 내가 new로 만든 객체는 컨테이너가 존재조차 모르므로 프록시를 씌울 기회가 없고, 예외도 로그도 없이 트랜잭션 없이 돈다.

0. 질문 + 출제 의도

질문: "IoC와 DI란 무엇이고, 왜 사용하나요?"

출제 의도: "왜"를 묻는 이유는 테스트 가능성과 결합도 관점에서 설명할 수 있는지 보기 위해서다. 이걸 설명 못 하는 사람은 DI를 쓰면서도 static 유틸과 new를 남발해 테스트 불가능한 코드를 만든다.

이 페이지가 겨냥하는 약점 세 가지 ① "컨테이너가 관리해준다"에서 멈추는 것 → 1절에서 컨테이너의 정체(사실상 Map 한 벌)와 기동 4단계를 도식으로 못 박아, "넘긴다"의 대상이 무엇인지부터 세운다.
② "결합도가 낮아진다"를 형용사로만 말하는 것 → 3절에서 같은 요구사항에 대해 고쳐야 할 파일이 7개 → 1개로 줄어드는 것을 grep 결과로 보여준다. 결합도는 셀 수 있는 수치다.
③ DI = 인터페이스 = DIP를 뭉뚱그리는 것 → 5·8절의 2×2 사분면과 구분표로 "주입은 했지만 DIP는 위반"인 구간을 분리해 낸다.
한 문장 비유 — 뷔페, 그리고 콘센트 뷔페: 무엇을 먹을지(비즈니스 로직)는 여전히 내가 정하지만, 장보기와 조리와 배식(객체 생성·조립)은 주방이 한다.  /  콘센트: 노트북은 "한국전력"이나 "이 건물 발전기"에 의존하지 않는다. 220V 콘센트 규격(인터페이스)에만 맞추면 벽에 무엇이 연결돼 있든 상관없다 — 그래서 배터리 시뮬레이터(목 객체)를 꽂아 실험할 수도 있다.

1. 전제 지식 — 컨테이너와 빈이 도대체 무엇인가

@Autowired나 @Service를 써 본 사람도 "컨테이너에게 넘긴다"는 문장에서 막힌다. 넘기는 대상이 무엇인지를 한 번도 정의받지 못했기 때문이다. IoC를 말하기 전에 이 둘부터 세우고 간다.

1-1. 컨테이너 — 완성된 객체들을 이름표 붙여 보관하는 창고

스프링 컨테이너는 애플리케이션이 쓸 객체들을 대신 만들어 서로 연결해 놓고, 이름표를 붙여 보관하다가 필요할 때 꺼내주는 저장소다. 자바 코드로서의 정체는 ApplicationContext라는 인터페이스의 구현체이고, 그 안에는 대단한 마법이 아니라 사실상 Map<빈 이름, 완성된 객체> 한 벌과 그 객체들을 어떻게 만들지 적어둔 설계도 목록이 들어 있다.

"컨테이너(container, 담는 그릇)"라는 이름은 정확히 그 역할에서 왔다. 객체들을 담아두는 그릇이라는 뜻이다.

암기 장치 — 컨테이너 기동 4단계는 "스 · 인 · 주 · 보"

스캔(설계도 등록) → 인스턴스화(객체 생성) → 주입(연결) → 보관(이름표 붙여 Map에)

이 네 글자를 쥐고 있으면 "빈 등록은 됐는데 주입이 안 된다", "기동은 됐는데 프록시가 안 씌워졌다" 같은 문제를 몇 번 단계의 문제인지로 나눠 말할 수 있다.

1-2. 빈(bean) — 컨테이너가 관리하는 객체

빈은 "컨테이너가 만들고, 연결하고, 생명주기를 책임지는 객체"다. 같은 클래스라도 내가 new로 만든 인스턴스는 빈이 아니다. 컨테이너의 Map 안에 들어 있어야 빈이다. 이 구분이 뒤에서 계속 되돌아온다 — 빈이 아니면 @Transactional도 안 먹는다(7절).

이름의 유래도 알아두면 기억에 남는다. 자바에서 재사용 가능한 부품 객체를 부르는 옛 규격 이름이 JavaBeans였고, 자바(Java)가 커피 산지 이름이라 그 부품들을 커피콩(bean)에 빗댄 것이다. 스프링은 이 관례를 그대로 물려받아 자기가 관리하는 객체를 빈이라 부른다. 즉 "콩"에 기술적 의미는 없고 "컨테이너에 담긴 부품 하나"로 읽으면 된다.

같은 클래스, 두 개의 객체 — 무엇이 다른가

클래스가 @Service로 등록돼 있어도, 그 클래스를 내가 new로 만들면 그 인스턴스는 빈이 아니다. 빈 여부를 가르는 것은 클래스에 붙은 애너테이션이 아니라 "이 객체를 누가 만들었는가"다.

컨테이너가 만든 OrderService내가 new로 만든 OrderService
의존성 자동 주입된다안 된다 (내가 인자로 넘겨야 함)
@PostConstruct / @PreDestroy호출된다호출되지 않는다
싱글턴 보장컨테이너가 보장new할 때마다 새 객체
@Transactional · @Cacheable · @Async프록시가 씌워져 동작조용히 무시된다 (예외도 로그도 없음)

2. IoC — 제어의 주도권이 뒤집힌다

이제 IoC를 말할 수 있다. 전통적인 코드에서는 내 코드가 주도권을 갖는다. 필요한 객체를 내가 만들고, 내가 호출한다.

전통 생성 시점도 대상도 전부 내가 결정한다
public class OrderService {
    private final PaymentGateway gateway = new TossPaymentGateway();이 한 줄에 세 가지가 박혀 있다
    // 무엇을 : TossPaymentGateway
    // 언제   : OrderService 가 만들어지는 바로 그 순간
    // 어떻게 : 인자 없는 기본 생성자로
}

IoC(Inversion of Control, 제어의 역전)는 이 주도권을 컨테이너로 넘기는 것이다. 무엇을 만들고 누구와 연결하고 언제 없앨지는 컨테이너가 결정하고, 내 코드는 호출당하는 입장이 된다. "역전"이라는 말은 호출의 방향이 뒤집혔다는 뜻이다 — 내가 프레임워크를 부르던 것에서, 프레임워크가 나를 부르는 쪽으로.

2-1. IoC는 DI보다 넓은 개념이다

여기서 미리 못 박아둘 것이 하나 있다. IoC ⊃ DI다. 주입 없이도 성립하는 IoC가 여럿 있고, DI는 그중 스프링이 주력으로 택한 하나일 뿐이다.

한 문장으로 봉인 — 층위를 섞지 않는다

IoC는 "제어를 넘긴다"는 원칙(what)이고, DI는 그것을 "의존성을 밖에서 주입받는 방식으로" 실현하는 패턴(how)이다

3. DI — new 한 줄이 왜 나쁜가

3-1. 결합도부터 정의하자

"결합도가 낮아진다"는 결론을 먼저 외우면 아무 쓸모가 없다. 정의부터 세운다.

결합도(coupling)의 정의 — 형용사가 아니라 관계

B가 바뀌었을 때 A도 같이 고쳐야 하는 정도

A를 고칠 이유가 A 자신의 요구가 아니라 B의 변경 때문에 생긴다면, A는 B에 결합돼 있다. 그래서 결합도는 "고쳐야 하는 파일 수"라는 셀 수 있는 값으로 드러난다(3-2절).

new TossPaymentGateway() 한 줄이 만드는 결합은 두 겹이다.

① 컴파일 타임 의존
OrderService.class 안에 TossPaymentGateway라는 클래스 이름이 상수 풀에 박힌다. 그 클래스가 사라지면 OrderService는 컴파일조차 안 된다.
② 생성 방법에 대한 의존
new TossPaymentGateway()는 "인자 없는 생성자로 만들 수 있다"는 사실에 기대고 있다. Toss가 API 키·타임아웃을 생성자로 받게 바뀌면 아무 상관없는 OrderService가 깨진다.

3-2. "PG사를 바꿔주세요" — 실제로 열어야 하는 파일의 개수

3-3. before / after — 사라진 것은 new가 아니라 "책임"이다

Before 직접 생성 — 강한 결합
public class OrderService {
    private final PaymentGateway gateway = new TossPaymentGateway();

    // 문제 1: Toss -> Kakao 로 바꾸려면 이 파일을 열어야 한다
    //         (그리고 같은 짓을 하는 다른 6개 파일도 함께)
    // 문제 2: 테스트를 돌리면 진짜 결제 API 로 HTTP 요청이 나간다
    //         가짜로 바꿔 끼울 자리가 코드 어디에도 없다
    // 문제 3: TossPaymentGateway 의 생성자 시그니처가 바뀌면
    //         이 클래스가 같이 깨진다
}
After 생성자 주입 — 느슨한 결합
public class OrderService {
    private final PaymentGateway gateway;인터페이스 타입 — 구현체 이름이 없다

    // "나를 만들려면 PaymentGateway 하나가 필요하다"만 선언하고,
    // 그것을 누가 어떻게 구해오는지는 알지도 못하고 알 필요도 없다
    public OrderService(PaymentGateway gateway) {주입 통로
        this.gateway = gateway;
    }
}

after 코드에서 사라진 것은 new 한 줄이 아니라 "어떤 구현체를 쓸지 결정하는 책임" 자체다. 그 책임이 OrderService 밖으로 나가 설정(@Configuration 또는 컴포넌트 스캔)으로 옮겨졌다.

3-4. 의존 방향이 뒤집힌다 — DIP와 OCP

4. 주입 통로는 세 가지가 있다

의존성을 밖에서 넣어주는 통로는 셋이다.

방식값이 들어가는 자리한 줄 특징
생성자 주입 기본값생성자 파라미터의존성이 다 갖춰지지 않으면 객체 자체가 만들어지지 않는다 — final 불변, 순환 참조 조기 발견, 컨테이너 없는 단위 테스트가 전부 여기서 파생된다
수정자(setter) 주입setXxx() 메서드객체를 먼저 만들고 나중에 넣는다 — 선택적 의존성에나 쓴다
필드 주입@Autowired가 붙은 필드에 직접가장 짧지만 주입 통로가 외부에 없어 컨테이너 없이는 값을 채울 수 없다
여기서는 "통로가 셋 있고, 기본은 생성자 주입"까지만 셋 중 무엇을 왜 골라야 하는지, 필드 주입이 구체적으로 어떤 사고를 부르는지는 03-constructor-injection-over-field-injection.md에서 통째로 다룬다. 이 문서에서 알아둘 것은 생성자 주입이 "컨테이너 없이 new로 조립 가능"이라는 성질을 유일하게 보장한다는 점이다 — 6절 테스트 이야기가 전부 그 성질 위에 서 있다.

5. 실익 ① 구현 교체 — 코드 문제를 설정 문제로 축소한다

교체는 전부-아니면-전무로 오지 않는다. 실제로 오는 요구는 이런 모양이다.

"장애 나면 5분 안에 예전 PG로 되돌릴 수 있어야 합니다"
환경별 분기
"스테이징에서는 PG를 태우지 말고 항상 성공하는 가짜로 두세요"

new가 흩어져 있으면 이 셋 다 코드 수정과 재배포를 요구한다. DI 구조에서는 "어떤 구현체를 빈으로 올릴지"만 바꾸면 되므로 설정 문제로 축소된다.

After 교체 지점이 한 파일에 모인다
@Configuration
public class PaymentConfig {

    // 프로필로 갈아 끼운다. prod 에서는 Kakao, local/staging 에서는 가짜.
    // 되돌리기가 필요하면 프로필이나 설정값만 바꿔 재기동하면 되고,
    // OrderService · RefundService · SettlementBatch 는 손대지 않는다.
    @Bean
    @Profile("prod")
    public PaymentGateway paymentGateway(PgProperties props) {
        return new KakaoPaymentGateway(props.apiKey(), props.timeout());
    }

    @Bean
    @Profile("!prod")
    public PaymentGateway fakePaymentGateway() {
        return new AlwaysSuccessPaymentGateway();스테이징에서 진짜 결제 차단
    }
}

가장 흔한 착각 — "주입받으면 결합이 풀린다"

DI를 쓴다고 자동으로 이 이점이 생기지는 않는다. OrderService(TossPaymentGateway gateway)처럼 구현체 타입을 주입받으면 주입은 했지만 결합은 그대로다 — OrderService.class에는 여전히 TossPaymentGateway라는 이름이 박히고, 3-2절의 grep 결과도 줄어들지 않는다.

이점은 "주입받는다"가 아니라 "인터페이스 타입으로 받는다"에서 나온다

6. 실익 ② 테스트 — 목을 끼워 넣을 "자리"가 있는가

출제 의도가 테스트 가능성을 짚는 이유가 여기 있다. new로 직접 만드는 구조에서는 테스트가 물리적으로 불가능해진다.

용어 하나 — 목(mock) 진짜 협력 객체 대신 세워두는 가짜 객체로, 미리 정해둔 값을 돌려주고 "몇 번 어떤 인자로 호출됐는지"를 기록해준다. 진짜 결제 API를 부르지 않고도 "결제가 성공하면 주문이 PAID로 바뀌는가"를 검증하기 위한 도구다.
Before 내부에서 new — 테스트가 성립하지 않는다
public class OrderService {
    private final PaymentGateway gateway = new TossPaymentGateway();
}

// 테스트에서 할 수 있는 일이 없다
OrderService service = new OrderService();
service.placeOrder(order);진짜 Toss 서버로 HTTP 요청

// - CI 서버에 결제사 API 키가 있어야 한다
// - 네트워크가 끊기면 내 주문 로직과 무관하게 빨간불
// - "결제 실패 시 주문이 CANCELLED 로 가는가"는
//   검증할 방법이 아예 없다. 실패를 일으키려면
//   진짜로 결제를 실패시켜야 하기 때문이다.
After 생성자 주입 — 컨테이너도 네트워크도 없이 끝난다
PaymentGateway fake = mock(PaymentGateway.class);
when(fake.pay(any())).thenReturn(PaymentResult.success());

OrderService service = new OrderService(fake);가짜를 그냥 넣는다
service.placeOrder(order);
assertThat(order.status()).isEqualTo(PAID);

// 실패 경로도 한 줄로 만들어낸다
// — 진짜 API 로는 재현조차 어려운 상황이다
when(fake.pay(any())).thenThrow(new PgTimeoutException());
assertThatThrownBy(() -> service.placeOrder(order))
        .isInstanceOf(OrderFailedException.class);

핵심은 속도가 아니라 검증 가능한 상황의 범위다

new가 박힌 구조에서는 "PG 타임아웃", "잔액 부족", "중복 결제 응답" 같은 예외 경로를 테스트할 수단이 없다. 그런데 장애는 정확히 그 경로에서 난다. "테스트가 빨라진다"만 말하면 절반이고, "진짜로는 재현할 수 없는 실패 상황을 마음대로 만들어낼 수 있다"까지 말해야 답이 완성된다.

테스트 가능성의 분기점 = "컨테이너 없이 new로 인스턴스화할 수 있는가"
여기서 한 걸음 더 — new OrderService(fake)는 그 자체가 DI다 이 테스트 코드에는 스프링이 한 글자도 없다. 그런데도 의존성은 밖에서 주입됐다. 즉 DI는 패턴이고, 컨테이너는 그 패턴을 자동화하는 도구일 뿐이다 — 손으로 조립해도 DI다. "DI = 스프링 기능"이 아니라 "DI = 설계 방식"이라는 구분을 이 한 줄로 증명할 수 있다.

7. 실익 ③ 컨테이너가 객체를 쥐고 있어야 가능한 것 — 생명주기와 AOP

세 번째 실익은 앞의 둘과 성격이 다르다. 컨테이너가 객체를 직접 만들었기 때문에 비로소 할 수 있는 일들이다. 컨테이너는 자기가 만든 객체에 초기화 콜백(@PostConstruct)과 소멸 콜백(@PreDestroy)을 불러줄 수 있고, 싱글턴 보장도 해줄 수 있다. (생명주기 전체는 02-bean-lifecycle-singleton-scope.md에서 다룬다.)

그중 실무에서 가장 자주 사고로 이어지는 것이 프록시 기반 AOP다. 프록시는 원본 객체인 척하면서 호출을 먼저 받아 부가 작업을 한 뒤 원본에 넘기는 대리인 객체다. @Transactional이 하는 일이 정확히 이것이다.

한 문장으로 봉인 — "DI가 안 되면 @Transactional도 안 먹는다"

컨테이너 밖에서 new로 만든 객체는 스프링이 존재조차 모르므로 프록시를 씌울 기회가 없고, 애너테이션은 조용히 무시된다. 예외도 로그도 없이 그냥 트랜잭션 없이 돈다는 점이 특히 위험하다. 가산점

주의할 확장: 빈으로 등록됐다고 항상 도는 것도 아니다. 같은 클래스 안에서 this.내부메서드()로 부르면 프록시를 거치지 않아 역시 무효가 된다(자기 호출 문제, 11-transactional-self-invocation.md). 프록시를 거쳐 들어왔는가가 유일한 판단 기준이다.

암기 장치 — DI의 실익 3종은 "교 · 테 · 프"

교체(고칠 파일 7 → 1)  ·  테스트(new OrderService(mock), 예외 경로까지)  ·  프록시(@Transactional·@Cacheable이 걸릴 자리)

앞의 둘은 "인터페이스 타입으로 받았기 때문에" 생기고, 마지막 하나는 "컨테이너가 만들었기 때문에" 생긴다 — 원인이 다르다는 것까지 말하면 답이 정돈된다.

8. 헷갈리는 셋 — DI · DIP · 서비스 로케이터

층위가 다른 것을 같은 줄에 놓고 비교하면 답이 흐려진다. 먼저 "이건 원칙이고 저건 기법"이라고 층위를 나눈 뒤 관계를 말한다.
층위한 줄 정의관계
IoC설계 원칙제어(생성·조립·호출)의 주도권을 내 코드 밖으로 넘긴다가장 넓은 개념. DI는 그 부분집합
DI구현 기법필요한 협력 객체를 밖에서 넣어받는다IoC의 구현 수단이자 DIP를 지키기 위한 도구
DIP설계 원칙 (SOLID)고수준 모듈은 저수준 모듈이 아니라 추상화에 의존하라지향점이지 문법이 아니다 — DI를 써도 위반할 수 있다(5절 사분면)
서비스 로케이터구현 기법필요한 객체를 중앙 등록소에 요청해 꺼내 쓴다IoC의 한 형태지만 의존성을 감춘다 — 그래서 지양

8-1. DI vs 서비스 로케이터 — 차이는 "의존성이 밖에서 보이는가" 가산점

Locator 의존성이 메서드 본문 안에 숨는다
public class OrderService {

    public void placeOrder(Order order) {
        PaymentGateway gateway = Locator.get(PaymentGateway.class);
        gateway.pay(order);
    }

    // - 생성자 시그니처만 봐서는 이 클래스가 무엇을
    //   필요로 하는지 알 수 없다
    // - 테스트하려면 Locator 라는 전역 상태를
    //   테스트마다 세팅하고 되돌려야 한다
    // - 등록을 빠뜨리면 기동이 아니라
    //   그 메서드가 호출되는 순간에 터진다
}
DI 의존성이 생성자라는 공개 계약에 드러난다
public class OrderService {

    private final PaymentGateway gateway;

    public OrderService(PaymentGateway gateway) {필요한 것이 전부 여기 적혀 있다
        this.gateway = gateway;
    }

    // - 이 클래스가 무엇에 의존하는지 한눈에 보인다
    // - 테스트는 인자로 목을 넘기면 끝, 전역 상태 없음
    // - 짝이 없으면 기동 시점에 즉시 실패한다
}
비유 — 배달받는 요리사 vs 창고에 몰래 다녀오는 요리사 DI는 레시피 첫 줄에 "재료: 밀가루, 계란, 버터"가 적혀 있고 그것을 배달받아 시작하는 요리사다. 서비스 로케이터는 레시피에 재료 목록이 없고, 조리 도중에 필요할 때마다 창고에 다녀오는 요리사다. 둘 다 재료를 직접 재배하진 않지만(= 둘 다 IoC), 레시피만 보고 무엇이 필요한지 알 수 있는 쪽은 하나뿐이다.

결론 한 줄과, 놓치기 쉬운 뒷문장

DI는 의존성을 드러내고, 서비스 로케이터는 감춘다

뒷문장까지 붙여야 답이 완성된다 — 로케이터를 쓰는 클래스는 로케이터 자체에 결합되므로, 결합 대상이 결제사에서 로케이터로 바뀌었을 뿐 없어지지 않았다.

그리고 실무 연결: 스프링에서도 ApplicationContext를 주입받아 getBean()을 호출하는 코드는 사실상 서비스 로케이터이며, 같은 이유로 지양한다. 실패 시점도 밀린다 — DI는 기동 시점에 터지지만 로케이터는 그 메서드가 실제로 호출되는 순간에 터지므로, 드물게 타는 경로라면 운영 중에 발견된다.

9. 비용과 한계 — "단점은 없나요?"에 균형 있게 답하기 시니어 변별

1
흐름 추적이 어려워진다. gateway.pay()를 IDE에서 따라가면 인터페이스로 간다. 실제로 어떤 구현체가 도는지는 코드가 아니라 빈 설정과 활성 프로필을 봐야 알 수 있다. 구현체가 여럿이고 @Profile·@ConditionalOnProperty까지 얽히면 "지금 운영에서 뭐가 뜬 거지"가 곧바로 안 나온다.
완화책 — 기동 로그에 선택된 구현체를 남기거나, 액추에이터의 빈 목록 엔드포인트를 열어둔다.
2
기동 비용과 러닝 커브. 컨테이너가 모든 빈을 미리 만들고 연결하므로 기동 시간이 붙는다. 빈이 수천 개인 모놀리식에서는 로컬 개발의 재기동 시간이 체감상 문제가 된다.
뒤집어 보면 이것은 1절의 이점과 같은 성질의 대가다 — 기동 때 그래프를 다 세우기 때문에 오류도 기동 때 드러난다.
3
과도한 추상화 — 실무에서 가장 흔한 실수. 구현체가 하나뿐이고 바뀔 일도 없는데 인터페이스부터 만들면, 파일 수와 점프 횟수만 늘고 얻는 게 없다. OrderService / OrderServiceImpl 짝이 프로젝트 전체에 기계적으로 깔린 경우가 전형이다.

세 번째에 덧붙이면 인상이 달라지는 판단 기준

인터페이스를 두는 쪽
외부 시스템과 맞닿는 경계 — PG, 메일, 외부 API, 파일 스토리지. 이유는 교체 가능성보다 테스트에서 그 경계를 끊어야 하기 때문이다.
구체 클래스로 두는 쪽
순수한 도메인 계산 로직 — 외부에 나가지 않고 입력만으로 결과가 정해지는 코드는 그냥 new해서 테스트하면 되므로 인터페이스가 얻는 게 없다.
기준 한 줄: "교체 가능성이 있거나, 테스트에서 가짜로 바꿔 끼워야 하는 지점에 선별 적용한다"

암기 장치 — 단점 3종은 "흐 · 기 · 추"

흐름 추적 난이도  ·  기동 비용과 러닝 커브  ·  추상화 과잉

"단점 없나요?"에 "딱히 없습니다"로 답하는 것이 가장 나쁜 답이다. 세 개를 대고 각각의 완화책·판단 기준까지 붙이는 것이 시니어 변별 지점이다.

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

IoC와 DI의 관계는?
IoC = 원칙(what), DI = 그 원칙을 실현하는 패턴(how). IoC ⊃ DI — 템플릿 메서드·서블릿 생명주기·콜백은 주입 없는 IoC다.
컨테이너의 정체는?
ApplicationContext 구현체 = 사실상 Map<빈 이름, 완성된 객체> + 설계도 목록. 기동 4단계는 스·인·주·보.
빈과 그냥 객체의 차이는?
누가 만들었는가. 내가 new한 인스턴스는 @Service가 붙은 클래스여도 빈이 아니다.
결합도의 정의는?
B가 바뀌었을 때 A도 고쳐야 하는 정도. 형용사가 아니라 고칠 파일 수로 드러난다.
DI의 실익 3종은?
교·테·프 — 교체(7→1) · 테스트(new OrderService(mock)) · 프록시(@Transactional).
DI했는데 결합이 안 풀렸다면?
구현체 타입으로 주입받은 것. 이점은 "주입받는다"가 아니라 "인터페이스 타입으로 받는다"에서 나온다.
@Transactional이 안 먹는 두 경우는?
① 빈이 아닌 객체(new로 생성) ② 같은 클래스 내부 호출. 공통 원인은 프록시를 거치지 않았다는 것.
테스트 가능성의 분기점은?
컨테이너 없이 인스턴스화할 수 있는가. 되면 밀리초 단위 단위 테스트, 안 되면 통합 테스트뿐.
DI vs 서비스 로케이터?
DI는 드러내고 로케이터는 감춘다. 로케이터는 결합 대상이 로케이터로 바뀐 것일 뿐이고, 실패도 호출 시점으로 밀린다.
단점 3종은?
흐·기·추 — 흐름 추적 난이도 · 기동 비용 · 추상화 과잉. 기준: 외부 경계는 인터페이스, 순수 계산은 구체 클래스.

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

IoC와 DI의 관계를 한 문장으로 정리하면요? 필수힌트: 층위를 나눈 뒤, "DI 없이 성립하는 IoC"의 예를 하나 대면 한 칸 올라간다

IoC는 "제어를 넘긴다"는 원칙(what)이고, DI는 그것을 "의존성을 밖에서 주입받는 방식으로" 실현하는 패턴(how)이다.

관계를 분명히 하려면 DI 없이 성립하는 IoC의 예를 들 수 있어야 한다. 템플릿 메서드 패턴(뼈대는 상위 클래스가 갖고 세부 단계만 내가 구현하면 상위 클래스가 그것을 불러준다), 서블릿 컨테이너가 서블릿의 init·service·destroy를 알아서 부르는 것, JdbcTemplate이 내가 넘긴 콜백을 대신 호출해주는 것 — 전부 주입 없이도 제어가 역전돼 있다.

그러므로 스프링은 "IoC 컨테이너"이면서 동시에 그 넓은 IoC 중 DI를 주된 구현 수단으로 택한 컨테이너다. "IoC = DI"라고 답하면 이 구분을 놓친 것으로 들린다.

DI를 왜 쓰나요? 이점을 실무 언어로 설명해보세요. 필수힌트: 형용사 대신 숫자와 시나리오. "고칠 파일 개수"와 "재현 못 하는 실패 상황"

세 가지를 원인이 다른 두 묶음으로 나눠 말한다.

① 교체 비용 — 결제사를 Toss에서 Kakao로 바꿀 때, new가 흩어진 구조에서는 프로덕션 5개 + 테스트 2개 = 7개 파일을 열어 고치고 전부 다시 검증해야 하고, 한 곳을 빠뜨리면 "환불만 아직 Toss로 나가는" 부분 장애가 난다. DI 구조에서는 PaymentConfig 1개 파일이고, 빠뜨릴 곳이 하나뿐이라 부분 교체 상태가 존재할 수 없다.

② 테스트 가능성 — new OrderService(mock) 한 줄로 컨테이너도 네트워크도 없이 테스트가 끝난다. 더 중요한 것은 속도가 아니라 검증 가능한 상황의 범위다. PG 타임아웃·잔액 부족·중복 결제 응답 같은 예외 경로는 진짜 API로는 재현조차 어려운데, 목이 있으면 thenThrow 한 줄이다. 장애는 정확히 그 경로에서 난다.

③ 프록시 AOP — 앞의 둘이 "인터페이스 타입으로 받았기 때문에" 생기는 이점이라면, 이것은 "컨테이너가 그 객체를 직접 만들었기 때문에" 생기는 이점이다. @Transactional·@Cacheable·@Async는 전부 컨테이너가 씌운 프록시가 하는 일이다.

주입 방식은 어떤 게 있고, 무엇을 쓰나요? 필수힌트: 세 개를 나열한 뒤 근거를 "한 줄"로 압축하고, 파생 효과를 거기서 뽑아낸다

생성자 주입 · 수정자(setter) 주입 · 필드 주입 셋이 있고 기본값은 생성자 주입이다.

근거를 한 줄로 압축하면 "의존성이 다 갖춰지지 않으면 객체 자체가 만들어지지 않게 만드는 유일한 방식"이기 때문이다. 나머지는 전부 여기서 파생된다 — final 불변 보장, 순환 참조 조기 발견(서로를 필요로 하면 어느 쪽도 먼저 만들 수 없으므로 기동에서 드러난다), 컨테이너 없는 단위 테스트, 책임 비대화의 가시화(생성자 파라미터가 8개면 그 클래스가 너무 많은 일을 한다는 뜻이 눈에 보인다).

각각이 없으면 실제로 어떤 사고가 나는지는 03-constructor-injection-over-field-injection.md에서 하나씩 전개한다.

DIP(의존관계 역전 원칙)와는 다른 건가요? 함정힌트: "층위가 다르다"로 시작하고, 마지막에 "DI를 써도 DIP를 위반할 수 있다"를 코드로 든다

층위가 다르다. DIP는 "고수준 모듈은 저수준 모듈이 아니라 추상화에 의존하라"는 SOLID의 설계 원칙이다 — 지향점이지 문법이 아니다. DI는 그 원칙을 지킬 수 있도록 의존성을 밖에서 넣어주는 구현 기법이다.

결정적인 것은 DI를 쓴다고 DIP가 자동으로 지켜지지는 않는다는 점이다.

public OrderService(TossPaymentGateway gateway) { ... }DI ✓ / DIP ✗
public OrderService(PaymentGateway gateway)     { ... }DI ✓ / DIP ✓

위쪽은 주입은 했지만 OrderService가 여전히 Toss라는 저수준 세부에 컴파일 타임으로 묶여 있고, 3-2절의 grep 결과도 줄어들지 않는다. DI는 통로일 뿐이고, DIP를 지키는 것은 그 통로로 무엇을 흘려보내느냐(인터페이스냐 구현체냐)다.

서비스 로케이터와는 뭐가 다른가요? 가산점힌트: "둘 다 IoC다"에서 출발해, 차이를 "의존성이 밖에서 보이는가" 한 축으로 좁힌다

서비스 로케이터는 필요한 객체를 중앙 등록소에 이름이나 타입으로 요청해 꺼내 쓰는 방식이다. 제어가 넘어가 있다는 점에서 이것도 IoC의 한 형태다 — 그래서 "IoC냐 아니냐"로는 구분되지 않는다.

차이는 "의존성이 밖에서 보이는가" 한 축이다. 로케이터를 쓰면 Locator.get(...) 호출이 메서드 본문 안에 숨어 있어 생성자 시그니처만 봐서는 이 클래스가 무엇을 필요로 하는지 알 수 없다. 테스트하려면 전역 상태인 로케이터를 테스트마다 세팅하고 되돌려야 하고, 등록을 빠뜨리면 기동이 아니라 그 메서드가 호출되는 순간에 터진다.

그리고 결합이 사라진 것도 아니다 — 로케이터를 쓰는 클래스는 로케이터 자체에 결합되므로 결합 대상이 결제사에서 로케이터로 옮겨갔을 뿐이다. 스프링에서도 ApplicationContext를 주입받아 getBean()을 호출하는 코드는 사실상 서비스 로케이터이며, 같은 이유로 지양한다.

단점이나 비용은 없나요? 시니어 변별힌트: 세 개를 대고, 각각에 완화책이나 판단 기준을 붙인다

(1) 흐름 추적이 어려워진다. gateway.pay()를 따라가면 인터페이스로 간다. 실제 구현체는 빈 설정과 활성 프로필을 봐야 알 수 있고, @Profile·@ConditionalOnProperty가 얽히면 "지금 운영에 뭐가 떠 있나"가 즉답이 안 된다. 완화책은 기동 로그에 선택된 구현체를 남기거나 액추에이터 빈 목록을 열어두는 것.

(2) 기동 비용과 러닝 커브. 컨테이너가 모든 빈을 미리 만들고 연결하므로 기동 시간이 붙는다. 빈이 수천 개인 모놀리식에서는 로컬 재기동 시간이 체감 문제가 된다.

(3) 과도한 추상화 — 가장 흔한 실수. 구현체가 하나뿐이고 바뀔 일도 없는데 인터페이스부터 만들면 파일 수와 점프 횟수만 늘고 얻는 게 없다.

여기에 판단 기준을 붙이면 균형 잡힌 인상을 준다 — "교체 가능성이 있거나, 테스트에서 가짜로 바꿔 끼워야 하는 지점에 선별 적용한다." 구체적으로 외부 시스템(PG·메일·외부 API·파일 스토리지)과 맞닿는 지점은 거의 항상 인터페이스로 두는 값이 있고(교체보다 테스트에서 경계를 끊기 위해), 반대로 순수한 도메인 계산 로직은 구체 클래스로 두는 편이 대개 낫다.

빈이 아닌 객체에서 @Transactional이 무시된다면, 왜 예외조차 안 나나요? 함정힌트: 애너테이션 자체는 무엇을 하는가 — 그 질문에 답이 있다

애너테이션은 그 자체로 아무 동작도 하지 않는 표식(메타데이터)이기 때문이다. 동작을 만들어내는 주체는 그 표식을 읽고 프록시를 씌우는 컨테이너다. 내가 new로 만든 객체는 컨테이너의 관리 대상이 아니므로 아무도 그 표식을 읽지 않고, 읽지 않았으니 "무시했다"는 사실을 알릴 주체도 없다. 컴파일러 역시 애너테이션이 실제로 효력을 갖는지까지는 검증하지 않는다.

그래서 이 실패는 가장 나쁜 형태의 실패 — 조용한 실패다. 컴파일도 되고 기동도 되고 기능 테스트도 통과할 수 있으며, 롤백돼야 할 상황에서 롤백이 안 될 뿐이다. 그 사실은 데이터가 깨진 뒤에 발견된다. 같은 이유로 @Async가 안 걸려 동기로 도는 것, @Cacheable이 안 걸려 매번 DB를 치는 것도 조용히 일어난다.

그럼 빈으로 등록만 되면 @Transactional은 항상 도나요? 함정힌트: 판단 기준은 "빈인가"가 아니라 "무엇을 통해 호출됐는가"다

아니다. 빈이라도 같은 클래스 안에서 this.내부메서드()로 호출하면 그 호출은 프록시를 거치지 않고 원본 객체 안에서 곧바로 일어나므로 트랜잭션이 걸리지 않는다(자기 호출, self-invocation).

즉 판단 기준은 "빈인가"가 아니라 "이 호출이 프록시를 거쳐 들어왔는가"다. new로 만든 객체는 프록시가 아예 없어서, 자기 호출은 프록시가 있어도 우회해서 같은 결과가 된다. 상세는 10-aop-jdk-dynamic-proxy-vs-cglib.md와 11-transactional-self-invocation.md에서 다룬다.

스프링 없이도 DI를 할 수 있나요? 그럼 컨테이너는 왜 쓰나요?힌트: 이 문서 6절의 테스트 코드가 이미 답이다

할 수 있다. main에서 new OrderService(new TossPaymentGateway(...))처럼 객체 그래프를 손으로 조립하는 것도 완전한 DI다. 6절의 new OrderService(fake)가 바로 그 예이고, 거기엔 스프링이 한 글자도 없다. DI는 패턴이고 컨테이너는 그 패턴을 자동화하는 도구라는 구분이 여기서 드러난다.

그럼 컨테이너를 왜 쓰냐면, 조립 대상이 수백 개로 늘어나는 순간 수동 조립이 감당되지 않기 때문이다. 컨테이너는 ① 조립 코드를 대신 써주고(스캔·자동 주입) ② 싱글턴·스코프를 관리하고 ③ 생명주기 콜백을 불러주고 ④ 프록시를 씌워 AOP를 걸어준다. 특히 ④는 수동 조립으로는 얻기 힘든 부분이라, "컨테이너 없이도 DI는 되지만 @Transactional은 안 된다"가 실무적인 답이 된다.

구현체가 둘 이상이면 스프링은 어떤 걸 주입하나요? 가산점힌트: 후보를 좁히는 순서와, 못 좁혔을 때 "언제" 터지는지까지

기본은 타입으로 찾는다. PaymentGateway 타입 빈이 하나면 그것을 넣는다. 후보가 여럿이면 스프링은 좁히기를 시도한다 — @Primary가 붙은 것이 있으면 그것, @Qualifier("bean이름")로 지목했으면 그것, 그래도 안 되면 주입받는 쪽의 변수/파라미터 이름과 빈 이름이 일치하는지를 본다.

끝내 하나로 좁혀지지 않으면 기동이 실패한다(후보가 여럿이면 NoUniqueBeanDefinitionException, 아예 없으면 NoSuchBeanDefinitionException 계열). 이 "기동 시점 실패"가 서비스 로케이터 대비 DI의 이점이라는 점을 함께 말하면 좋다 — 로케이터였다면 같은 실수가 그 메서드를 실제로 타는 날 운영에서 터졌을 것이다.

인터페이스 없이 구체 클래스를 주입받으면 테스트가 아예 불가능한가요?힌트: "불가능하진 않다"에서 출발해, 그래도 남는 것이 무엇인지로 넘어간다

불가능하진 않다. 목 프레임워크는 구체 클래스도 대역으로 만들 수 있고(상속으로 하위 타입을 만들어 메서드를 가로채는 방식), 그래서 OrderService(TossPaymentGateway gateway)여도 가짜를 넣는 것 자체는 된다. 다만 클래스나 메서드가 final이면 그 방식이 막힐 수 있다는 제약이 따라온다.

중요한 건 테스트가 되더라도 남는 것이다 — 컴파일 타임 결합은 그대로이므로 OrderService는 여전히 Toss가 없으면 컴파일되지 않고, 교체 요구가 오면 3-2절의 grep 목록이 다시 나타난다. 그래서 답은 "테스트는 되지만 DIP 위반은 남는다"(5절 사분면의 노란 칸)가 정확하다.

DI 구조에서 순환 참조는 왜 기동 때 드러나나요? 가산점힌트: 생성자 주입에서 A와 B가 서로를 필요로 하면 "누가 먼저 만들어질 수 있는가"

생성자 주입은 "짝이 없으면 객체가 만들어지지 않는" 방식이기 때문이다. A를 만들려면 B가 먼저 있어야 하고 B를 만들려면 A가 먼저 있어야 하면 어느 쪽도 먼저 만들어질 수 없다. 컨테이너는 1절의 ②·③단계(인스턴스화·연결)에서 이 막다른 길을 만나 기동을 중단한다.

반대로 필드·세터 주입은 객체를 먼저 만들어 놓고 나중에 값을 넣기 때문에 순환이 있어도 일단 기동이 되어버릴 수 있다 — 설계 문제가 숨는다. "기동 때 시끄럽게 실패하는 것이 운영 중 조용히 도는 것보다 낫다"가 생성자 주입을 기본으로 두는 이유 중 하나다. 상세는 17-bean-circular-dependency.md.

DI가 결합도를 낮춘다면, 결합도가 0이 되는 건가요? 시니어 변별힌트: 결합은 사라지는 게 아니라 옮겨간다 — 어디로 옮겨갔는지 지목한다

0이 되지 않는다. OrderService는 여전히 PaymentGateway라는 인터페이스에 결합돼 있다. 달라진 것은 결합 대상의 성질이다 — 자주 바뀌는 구체적 세부(Toss의 생성자·API 키·엔드포인트)에서 거의 안 바뀌는 추상(pay 한다는 계약)으로 옮겨간 것이다.

그리고 결합의 총량이 사라진 것도 아니다 — "어떤 구현체를 쓸지 결정하는 책임"은 PaymentConfig로 이동했다. DI의 효과는 "결합을 없앤다"가 아니라 "결합을 한 곳에 모아 관리 가능하게 만든다"로 말하는 편이 정확하다.

이렇게 답하면 인터페이스 설계가 나쁘면 이점도 사라진다는 데까지 자연스럽게 이어진다 — 예컨대 PaymentGateway에 getTossSpecificToken() 같은 메서드가 있으면 추상이 특정 구현에 오염된 것이라, 인터페이스를 뒀어도 Kakao로 교체할 때 다시 여러 파일이 깨진다.

한 줄 요약
IoC는 객체의 생성·조립·생명주기 주도권을 내 코드에서 컨테이너(빈들을 만들어 연결해 보관하는 저장소)로 넘기는 원칙이고, DI는 그것을 "필요한 협력 객체를 인터페이스 타입으로 밖에서 주입받는다"는 방식으로 실현하는 패턴이다 — 그 대가로 얻는 것은 결제사 교체 시 고칠 파일이 7개에서 1개로 줄어드는 낮은 결합도, 진짜 API 없이 타임아웃·실패 경로까지 검증할 수 있는 new OrderService(mock) 테스트, 그리고 컨테이너가 객체를 쥐고 있어야만 가능한 @Transactional 같은 프록시 AOP다.
