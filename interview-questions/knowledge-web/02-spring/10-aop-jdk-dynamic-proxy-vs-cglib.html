AOP 동작 원리 — JDK Dynamic Proxy vs CGLIB
"붙였는데 동작 안 함"의 뿌리 하나

면접 질문: "AOP의 동작 원리(JDK Dynamic Proxy vs CGLIB)를 설명해주세요."

핵심 관전 포인트 — 스프링 AOP는 대상 빈을 그대로 등록하지 않고, 그 빈을 감싼 프록시 객체를 대신 등록한다. 그래서 다른 빈이 주입받는 것은 원본이 아니라 전부 프록시다. 프록시가 "원본인 척"할 수 있는 방법은 자바에 정확히 두 가지뿐이다 — 원본의 인터페이스를 구현하거나(JDK 동적 프록시), 원본 클래스를 상속하거나(CGLIB). 이 한 문장에서 실무 함정이 기계적으로 따라 나온다. JDK 방식은 인터페이스 목록으로 클래스를 찍어내므로 인터페이스가 없으면 만들 수가 없고, 만들어진 프록시는 구현 클래스의 자식이 아니라서 구현 클래스 타입으로 주입받으면 BeanNotOfRequiredTypeException이 난다 — 스프링 부트가 인터페이스가 있어도 CGLIB을 기본값(proxyTargetClass=true)으로 쓰는 이유가 이것이다. 반대로 CGLIB은 상속이라서 final 클래스는 프록시 생성 자체가 실패해 기동이 죽고(시끄럽다), final 메서드는 프록시는 만들어지되 그 메서드만 조용히 부가 기능이 빠진다(조용하다) — 장애의 악질성은 에러의 크기가 아니라 발견되기까지의 침묵으로 결정된다. 그리고 양쪽 공통으로, 호출이 프록시를 통과하지 않으면 부가 기능은 걸리지 않는다. @Transactional·@Async·@Cacheable이 "붙였는데 동작 안 하는" 상황은 전부 이 프록시 구조 하나로 설명된다.
  • 1
    구조부터 말한다 — 스프링 AOP는 런타임 프록시 방식이다. 컨테이너는 원본 빈을 만든 뒤 그것을 감싼 별개의 객체(프록시)를 만들어 그쪽을 등록하고, 다른 빈은 전부 프록시를 주입받는다. 결정적으로 부가 기능 코드는 프록시에만 있고 원본에는 없다 — 그래서 실행 조건은 "애너테이션이 붙었는가"가 아니라 "이 호출이 프록시를 통과했는가"다.
  • 2
    선택지가 둘인 이유는 스프링이 아니라 자바가 정했다 — 프록시가 원본 타입 변수에 담기려면 인터페이스를 구현했거나 클래스를 상속했거나 둘 중 하나여야 한다. 전자가 JDK 동적 프록시(java.lang.reflect.Proxy가 인터페이스 배열을 받아 클래스를 생성), 후자가 CGLIB(대상 클래스를 상속한 자식을 바이트코드로 생성)다. 스프링 부트의 기본값은 CGLIB(spring.aop.proxy-target-class=true)이고, 그 이유는 JDK 프록시가 구현 클래스 타입으로 주입되지 않아 BeanNotOfRequiredTypeException을 내기 때문이다.
  • 3
    함정은 이 구조에서 기계적으로 따라 나온다 — final 클래스는 상속이 안 돼 기동이 실패하고(fail-fast), final·private 메서드는 프록시는 만들어지되 그 메서드만 조용히 새고, 자기 호출(this.method())은 프록시를 우회해 역시 조용히 샌다. 그래서 진단은 두 질문으로 끝난다 — ① 프록시가 이 메서드를 오버라이드할 수 있었는가, ② 이 호출이 프록시를 통과했는가.

0. 질문 + 출제 의도

질문: "AOP의 동작 원리(JDK Dynamic Proxy vs CGLIB)를 설명해주세요."

출제 의도: 프록시 기반이라는 사실을 모르면 @Transactional·@Async·@Cacheable이 "붙였는데 동작 안 하는" 상황을 이해할 수 없다. 스프링의 마법 대부분이 이 하나의 원리로 설명되므로, 이걸 아는지가 스프링을 "쓰는" 사람과 "이해하는" 사람의 분기점이다.

이 페이지가 겨냥하는 약점 세 가지 ① "프록시가 감싼다"를 비유로만 말하는 것 → 2절에서 메모리에 객체가 두 개라는 사실을 도식으로 못 박는다. "감싸는 코드"가 아니라 별개의 인스턴스다.
② "JDK는 인터페이스, CGLIB은 상속"을 암기로만 아는 것 → 5절에서 왜 인터페이스가 필수인지를 newProxyInstance의 파라미터에서, 4절에서 왜 선택지가 둘뿐인지를 자바 타입 시스템에서 유도한다.
③ 함정을 나열만 하고 등급을 못 매기는 것 → 8절에서 기동에서 죽는 실패와 운영에서야 드러나는 침묵을 타임라인으로 갈라 "어느 쪽이 더 악질인가"에 답할 수 있게 한다.

1. 전제 — AOP가 풀려는 문제는 무엇인가

AOP를 "관점 지향 프로그래밍"이라고 번역해 놓으면 아무것도 설명되지 않는다. 무엇을 풀려는 기법인지부터 본다.

서비스 코드에는 두 종류의 관심사가 섞여 있다. 하나는 그 메서드가 존재하는 이유인 비즈니스 로직(주문을 만든다, 재고를 깎는다)이고, 다른 하나는 그 로직이 무엇이든 상관없이 똑같이 필요한 부가 관심사(트랜잭션을 열고 닫는다, 실행 시간을 로그로 남긴다, 권한을 확인한다, 결과를 캐시에 넣는다)다.

문제는 부가 관심사가 여러 클래스에 똑같은 모양으로 흩어진다는 것이다. 서비스가 50개면 트랜잭션 시작·커밋·롤백 코드가 50벌 복제된다. 한 곳을 고치면 49곳을 놓친다.

before 부가 관심사가 비즈니스 로직에 얽혀 모든 메서드에 복제된다
public Order order(OrderRequest request) {
    Connection conn = dataSource.getConnection();
    conn.setAutoCommit(false);          // 트랜잭션 시작 — 이 서비스와 아무 상관 없는 코드
    long start = System.nanoTime();     // 로깅 — 역시 상관 없다
    try {
        Order result = doOrder(request, conn);   // 이 한 줄만이 이 메서드의 존재 이유다
        conn.commit();
        return result;
    } catch (Exception e) {
        conn.rollback();
        throw e;
    } finally {
        log.info("order took {}ms", (System.nanoTime() - start) / 1_000_000);
        conn.close();
    }
}붉은 줄 전부가 이 서비스 50개에 똑같이 복제된다

이렇게 여러 모듈을 가로질러(cross-cutting) 반복되는 부가 관심사를 횡단 관심사(cross-cutting concern)라 부른다. AOP는 이 횡단 관심사를 한 곳에 모아 정의해 두고, 대상 코드를 한 글자도 건드리지 않은 채 실행 시점에 끼워 넣는 기법이다.

after 부가 관심사는 사라지고 "존재 이유"만 남는다
@Transactional
public Order order(OrderRequest request) {
    return doOrder(request);
}
왜 하필 "관점(aspect)"인가 — 이름의 유래 기존의 객체 지향은 시스템을 "주문"·"재고"·"회원" 같은 명사(객체) 단위로 자른다. 그런데 "트랜잭션"이나 "감사 로깅"은 그 어느 명사에도 속하지 않고 전부를 가로지른다 — 시스템을 자르는 또 다른 관점(측면)인 것이다. 그 관점 하나를 독립된 모듈로 떼어낸 것이 aspect이고, 그렇게 자르는 프로그래밍이 aspect-oriented programming이다.

2. 스프링의 구현 방식 — 런타임 프록시

그렇다면 @Transactional 한 줄이 어떻게 위의 try-catch-finally를 대신하는가. 스프링이 고른 방법은 런타임 프록시다.

프록시의 정의 — 영문 병기가 아니라 이 문장을 외운다

프록시는 원본 객체인 척하면서 호출을 먼저 받아 부가 작업을 한 뒤 원본에 넘기는 대리인 객체다

여기서 놓치면 안 되는 단어가 "객체"다. 프록시는 "감싸는 코드"가 아니라 메모리에 따로 존재하는 별개의 인스턴스다. 이 한 단어가 8절 자기 호출 함정의 전부를 설명한다.

2-1. 프록시 안에서 벌어지는 일 (의사코드)

// 프록시 객체 안에서 개념적으로 벌어지는 일
public Order order(OrderRequest request) {
    // ① 전작업 — 트랜잭션 시작 / 캐시 조회 / 시작 시각 기록 / 권한 검사
    Order result = target.order(request);   // ② target은 원본 인스턴스 #1을 가리키는 필드다
    // ③ 후작업 — 커밋 / 캐시 저장 / 소요 시간 로깅
    return result;                          // ④ 리턴값은 손대지 않고 그대로 돌려준다
}

이 문서 전체를 지탱하는 한 문장

부가 기능이 실행될 조건은 "그 메서드에 애너테이션이 붙어 있는가"가 아니라 "이 호출이 프록시 객체를 통과했는가"다

8절의 함정 다섯 개가 전부 이 문장의 따름정리다. 면접에서 함정을 나열하기 전에 이 문장을 먼저 말하면, 나열이 아니라 유도로 들린다.

비유 — 사무실 앞 안내데스크 프록시는 담당자 앞에 앉힌 안내원이다. 방문객이 데스크를 통과해 들어가면 방명록에 기록이 남는다(부가 기능). 그런데 담당자가 옆방 동료에게 직접 걸어가면 데스크를 지나지 않으므로 아무 기록도 남지 않는다 — 담당자가 규칙을 어긴 것도, 방명록이 고장 난 것도 아니다. 동선이 데스크를 비껴갔을 뿐이다. 스프링에서 @Transactional이 "조용히 안 먹는" 상황은 거의 전부 이 동선 문제다.

3. 지도 — AOP 구현 방법은 프록시만이 아니다

AOP를 구현하는 방법이 프록시뿐인 것은 아니다. 전체 지형을 한 번 그려두면 이 문서가 다루는 범위가 분명해지고, 앞으로 볼 함정들의 정확한 원인도 지목할 수 있다.

비유 — 안내원 vs 담당자 교육 프록시는 담당자 앞에 안내원을 앉히는 방식이고, AspectJ는 담당자 본인을 교육시켜 스스로 기록하게 만드는 방식이다. 안내원 방식의 약점(담당자에게 직접 말을 걸면 기록이 안 남는다)이 후자에는 애초에 존재하지 않는다.
가장 자주 나오는 혼동 — @Aspect를 쓰면 AspectJ를 쓰는 것인가 아니다. 스프링 AOP는 AspectJ의 애너테이션과 포인트컷 표현식 문법만 빌려왔다. @Aspect, @Around("execution(...)")를 쓰고 있어도 실제 엔진은 여전히 런타임 프록시다 — 문법은 AspectJ, 동작은 프록시라는 조합이다. 그래서 @Aspect를 쓰는 코드에도 자기 호출·final·private 함정이 그대로 적용된다.

4. "원본인 척"하는 방법 — 자바에는 둘뿐이다

프록시가 성립하려면 반드시 만족해야 하는 조건이 하나 있다. 원본과 같은 타입으로 취급될 수 있어야 한다. 이유는 단순하다 — 주입받는 쪽 코드가 이렇게 생겼기 때문이다.

public class OrderController {
    private final OrderService orderService;   // 이 변수에 "프록시"가 담겨야 한다
}

컨테이너가 프록시를 이 필드에 넣으려면 프록시가 OrderService로 대입 가능해야 한다. 자바에서 어떤 객체가 다른 타입으로 대입될 수 있는 경우는 정확히 둘뿐이다.

암기 장치 — "척하는 법은 둘뿐: 구현 아니면 상속"

구현 → JDK 동적 프록시 (인터페이스 필요)  ·  상속 → CGLIB (final 금지)

면접에서 이 문장으로 시작하면 그다음 질문(왜 인터페이스가 필수인가 / 왜 final이 문제인가)에 암기가 아니라 유도로 답하게 된다.

5. JDK 동적 프록시 — 인터페이스가 유일한 타입 통로

JDK 동적 프록시는 JDK에 내장된 java.lang.reflect.Proxy를 쓴다. 핵심 메서드는 이것 하나다.

OrderService proxy = (OrderService) Proxy.newProxyInstance(
    classLoader,                       // ① 만들어낸 클래스를 어디에 적재할지
    new Class[]{OrderService.class},   // ② "이 인터페이스들을 구현한 클래스를 만들어라"타입 정보는 여기서만 온다
    invocationHandler                  // ③ 가로챈 호출을 어떻게 처리할지
);

newProxyInstance는 런타임에 새 클래스를 바이트코드로 찍어내는 메서드다. 그리고 그 클래스가 무슨 타입인지를 결정하는 정보는 ②번 인터페이스 배열이 유일하다. 그러니 인과가 명확해진다.

"인터페이스가 필수"의 진짜 이유 — 규칙이 아니라 인과

인터페이스가 없다 → 배열이 빈다 → 아무 타입도 아닌 클래스가 만들어진다 → OrderService 자리에 담길 수 없다

"스프링이 그렇게 정해서"가 아니라, 타입 정보를 얻을 통로가 그것뿐이기 때문이다. 이 차이를 말할 수 있으면 암기한 사람과 구분된다.

생성 결과 Proxy.newProxyInstance가 런타임에 만들어내는 클래스 (개념적 형태)
public final class $Proxy0 extends java.lang.reflect.Proxy implements OrderService {이미 Proxy를 상속했다

    @Override
    public Order order(OrderRequest request) {
        // 모든 메서드가 이 한 줄로 수렴한다 — 어떤 메서드가 불렸는지를
        // Method 객체로 넘겨주고, 실제 처리는 핸들러에 위임한다.
        return (Order) h.invoke(this, ORDER_METHOD, new Object[]{request});
    }
}
여기서 7절의 함정이 이미 결정된다 — 단일 상속의 벽 생성된 클래스는 이미 java.lang.reflect.Proxy를 상속하고 있다. 자바는 단일 상속이므로, 이 클래스가 OrderServiceImpl을 추가로 상속할 자리는 구조적으로 남아 있지 않다. 즉 JDK 프록시는 인터페이스의 형제일 뿐, 구현 클래스와는 아무 혈연이 없는 남남이다.

6. CGLIB — 원본을 상속한 자식 클래스를 찍어낸다

CGLIB은 바이트코드 조작 라이브러리다. 원래는 별도 의존성이었지만, 스프링이 이것을 자기 안에 재패키징해 넣었으므로 따로 추가할 필요가 없다. CGLIB이 만드는 것은 원본 클래스를 상속한 자식 클래스다.

생성 결과 CGLIB이 런타임에 생성하는 클래스 (개념적 형태)
// 실제 이름은 OrderService$$SpringCGLIB$$0 처럼 붙는다 (스프링 6 기준).
public class OrderService$$SpringCGLIB$$0 extends OrderService {대상 클래스를 그대로 extends

    private final Object target;   // 원본 인스턴스 — super가 아니라 별도 객체다

    @Override
    public Order order(OrderRequest request) {
        // 전작업 → 원본 호출 → 후작업
        return (Order) interceptor.intercept(target, ORDER_METHOD, new Object[]{request});
    }
}

오해 방지 — 상속은 "타입을 맞추기 위한 수단"일 뿐이다

CGLIB 프록시가 extends를 쓴다고 해서 실제 실행이 super.order()인 것이 아니다. 실행은 별도로 존재하는 원본 인스턴스(target)에 대한 위임이다. 상속은 "같은 타입인 척"하기 위한 수단일 뿐이라는 이 구분이, "CGLIB은 상속이니 자기 호출도 잡히지 않나?"라는 재반문을 끊는 결정적 근거가 된다(8-5절 · 11번 문서).

6-1. 생성자는 몇 번 호출되나 가산점

CGLIB이 자식 클래스를 만든다는 사실에서 자연스럽게 나오는 의문이 있다. 자식 인스턴스를 만들려면 부모 생성자가 먼저 돌아야 하는데, 그러면 원본 생성자가 두 번 실행되는 것 아닌가? 원본 인스턴스 #1을 만들 때 한 번, 프록시 인스턴스 #2를 만들 때 또 한 번.

스프링 4.0 이전 — 실제로 그랬다

  • 프록시 대상 클래스에 기본 생성자가 반드시 있어야 했다
  • 생성자에 로깅·카운터 증가 같은 부수 효과를 넣어두면 그것이 두 번 실행됐다

스프링 4.0부터 — Objenesis로 우회

  • Objenesis(역시 스프링에 재패키징돼 내장)는 생성자를 거치지 않고 인스턴스만 확보하는 JVM별 우회 기법 모음이다
  • 덕분에 프록시를 만들 때 생성자가 아예 한 번도 호출되지 않고, 기본 생성자 요구도 사라졌다
단서를 함께 말해야 답이 완성된다 공식 문서는 "JVM이 생성자 우회를 허용하지 않는 환경에서는 여전히 두 번 호출될 수 있고, 그 경우 스프링 AOP가 디버그 로그를 남긴다"는 단서를 달아둔다. 그래서 결론은 "생성자는 절대 두 번 안 불린다"가 아니라 "생성자에 부수 효과를 두지 않는 것이 안전하다"가 된다.

7. 대조표 · 선택 규칙 · 부트가 CGLIB으로 갈아탄 이유

7-1. 한눈에 보는 대조표

모든 행이 "구현이냐 상속이냐" 한 갈래에서 파생된다. 표를 외우는 것이 아니라 1행에서 나머지를 유도할 수 있어야 한다.
JDK 동적 프록시CGLIB
같은 타입인 척하는 방법대상의 인터페이스를 구현대상 클래스를 상속한 자식 생성
타입 정보를 어디서 얻나newProxyInstance에 넘긴 인터페이스 배열대상 클래스 그 자체
필요한 것인터페이스가 반드시 있어야 함클래스만 있으면 됨
구현 수단JDK 내장 (java.lang.reflect.Proxy)바이트코드 생성 (스프링이 재패키징해 내장)
캐스팅 가능한 타입인터페이스 타입으로만인터페이스 + 구체 클래스 타입
못 만드는 경우인터페이스가 없을 때final 클래스일 때
부가 기능이 빠지는 메서드인터페이스에 선언되지 않은 메서드final · private 메서드
런타임 클래스 이름 (진단용)jdk.proxy2.$Proxy123 형태OrderService$$SpringCGLIB$$0 형태

7-2. 선택 규칙과 스프링 부트의 기본값

스프링 프레임워크의 원래 규칙

  • 대상 빈이 인터페이스를 하나라도 구현하면 → JDK 동적 프록시
  • 하나도 구현하지 않으면 → CGLIB
  • proxyTargetClass = true를 주면 인터페이스가 있어도 CGLIB 강제

스프링 부트 — 이 값을 처음부터 true로 켜둔다

  • 설정 키: spring.aop.proxy-target-class=true (부트 기본값)
  • 즉 부트 애플리케이션에서 만나는 프록시는 인터페이스가 있든 없든 거의 전부 CGLIB이다
@EnableAspectJAutoProxy(proxyTargetClass = true)      // AOP 전반
@EnableTransactionManagement(proxyTargetClass = true)  // 트랜잭션

7-3. 부트가 프레임워크 기본값을 뒤집은 이유 — 타입 관계 하나 때문이다

함정 주니어가 반드시 한 번은 밟는다 — 코드는 멀쩡한데 기동이 실패한다
@RestController
@RequiredArgsConstructor
public class OrderController {

    // "구현체가 하나뿐이니 구체 타입이 더 명확하지 않나?"는 자연스러운 판단이고,
    // 프록시가 없다면 실제로 아무 문제가 없다.
    private final OrderServiceImpl orderService;   // 인터페이스가 아니라 구현 클래스 타입JDK 프록시면 여기서 터진다
}
org.springframework.beans.factory.BeanNotOfRequiredTypeException:
  Bean named 'orderServiceImpl' is expected to be of type
  'com.example.OrderServiceImpl' but was actually of type 'jdk.proxy2.$Proxy123'

부트가 proxyTargetClass=true를 기본값으로 삼은 근거는 둘이다

① 타입 주입 사고를 원천 차단
CGLIB 프록시는 OrderServiceImpl의 자식이므로 인터페이스 타입으로도, 구현 클래스 타입으로도 주입된다.
② 인터페이스 없는 빈도 프록시해야 한다
요즘 실무는 구현체가 하나뿐인 서비스에 인터페이스를 억지로 만들지 않는 쪽으로 기울었다. JDK 방식만 쓴다면 그런 빈에는 @Transactional을 아예 걸 수 없다.

함정을 아는 것과, 그 함정이 프레임워크 기본값을 바꿔놓은 역사를 아는 것은 다르다. 후자까지 말하면 답이 한 칸 올라간다.

8. 함정 지도 — 시끄러운 실패와 조용한 실패

부트가 CGLIB으로 갈아탄 대가는 분명하다. 상속으로 동작하니, 상속을 막는 키워드가 곧 함정이 된다. 다만 함정을 나열하는 것과 유도하는 것은 다르다 — 아래 플로우차트는 2절의 한 문장에서 모든 함정을 기계적으로 뽑아낸 것이다.

8-1. 상속의 대가 ① — final 클래스는 시끄럽게 죽는다

자바에서 상속을 금지하는 키워드가 final이다. CGLIB이 상속으로 동작하므로, final 클래스는 자식 클래스를 만들 수 없어 프록시 생성 자체가 실패한다.

문제 클래스에 final — CGLIB이 상속할 수 없다
@Service
public final class SettlementService {여기 final 하나로 기동이 죽는다

    @Transactional
    public void settle(Long orderId) { /* ... */ }
}
// 기동 시점에 프록시 생성이 실패하며 애플리케이션이 뜨지 않는다.

이 실패는 기동 중에 즉시 드러난다. 로컬에서 한 번 실행하면 바로 알 수 있고, CI에서도 컨텍스트 로딩 테스트에 걸린다. 고치는 방법도 final을 떼는 것 하나뿐이라 고민할 여지가 없다.

8-2. 상속의 대가 ② — final 메서드는 조용히 샌다

같은 final인데 붙는 위치가 메서드로 바뀌면 증상이 완전히 달라진다. 클래스는 상속 가능하므로 프록시는 정상적으로 만들어진다. 다만 그 메서드만 오버라이드할 수 없다.

문제 프록시는 만들어지는데 이 메서드만 샌다
@Service
public class SettlementService {

    @Transactional
    public final void settle(Long orderId) {오버라이드 불가
        // 컴파일도 되고 기동도 되고 실행도 된다.
        // 트랜잭션만 없다.
    }
}
고침 final을 뗀다 — 그것뿐이다
@Service
public class SettlementService {

    @Transactional
    public void settle(Long orderId) { /* ... */ }프록시가 오버라이드할 수 있다
}
// 프록시가 오버라이드할 수 있어야
// 부가 기능이 걸린다.
같은 키워드, 붙는 위치만 다른데 증상·발견 시점·위험도가 전부 갈린다.
붙은 위치프록시 생성부가 기능발견 시점증상
final 클래스실패—기동 즉시애플리케이션이 아예 안 뜬다
final 메서드성공그 메서드만 미적용정합성 사고가 난 뒤아무 신호 없이 트랜잭션만 없다

8-3. private·패키지 프라이빗, 그리고 코틀린

오버라이드가 안 되는 메서드는 final만이 아니다. 스프링 공식 문서가 CGLIB의 제약으로 명시하는 목록은 다음과 같다.

CGLIB 제약 4종 — 암기법 "클 · 메 · 프 · 패"

클래스 final · 메서드 final · 프라이빗 메서드 · 패키지 프라이빗(다른 패키지의 부모 메서드)
제약프록시 생성왜 안 되나
final 클래스실패상속 자체가 금지되어 자식 클래스를 만들 수 없다
final 메서드성공오버라이드할 수 없어 그 메서드만 부가 기능이 빠진다
private 메서드(프라이빗)성공오버라이드 대상이 아니므로 가로챌 수 없다
다른 패키지의 패키지 프라이빗성공사실상 private처럼 취급되어 적용되지 않는다
private은 어느 프록시 방식으로도 구제되지 않는다 private은 JDK 방식에서도 당연히 불가능하다 — 인터페이스에 private 메서드를 선언할 수 없으니 프록시가 가로챌 통로 자체가 없다. 그래서 @Transactional을 private 메서드에 붙이는 것은 어떤 설정으로도 살릴 수 없는 유일한 케이스다.
코틀린에서 이 함정이 유난히 자주 터지는 이유 코틀린은 클래스와 메서드가 기본적으로 final이다. 자바에서 final을 붙이는 것은 의식적인 행위지만, 코틀린에서는 아무것도 안 쓰면 final이 된다. 그래서 open 키워드를 붙이거나, 스프링 애너테이션이 달린 클래스를 자동으로 열어주는 kotlin-spring(allopen) 컴파일러 플러그인을 반드시 쓴다. 스프링 이니셜라이저가 코틀린 프로젝트에 이 플러그인을 기본 포함시키는 것도 이 때문이다.

8-4. 양쪽 공통의 대가 — 프록시를 통과하지 않은 호출

지금까지의 함정은 "프록시가 그 메서드를 감쌀 수 있는가"의 문제였다. 마지막 함정은 성격이 다르다. 프록시가 멀쩡히 그 메서드를 감쌌는데도 부가 기능이 안 걸리는 경우가 있다.

여기서 붙잡고 넘어갈 것 하나

원인은 애너테이션이 아니라 프록시 구조다. "@Transactional이 자기 호출에서 안 되는 버그가 있다"가 아니라 "프록시 방식이라서 자기 호출에는 구조적으로 걸릴 수 없다"가 정확한 진술이고, 같은 이유로 @Async·@Cacheable도 전부 똑같이 샌다.

8-5. 실무 진단 팁 — 지금 이 빈이 어느 프록시인지 3초에 확인하기

// ① 클래스 이름으로 즉시 구분된다 (디버거·로그 어디서나)
System.out.println(orderService.getClass().getName());
//  jdk.proxy2.$Proxy123            → JDK 동적 프록시
//  ...OrderService$$SpringCGLIB$$0 → CGLIB 프록시
//  com.example.OrderService        → 프록시가 아예 없다 (AOP 대상이 아니었다)

// ② 스프링이 제공하는 판별 유틸 (org.springframework.aop.support.AopUtils)
AopUtils.isAopProxy(orderService);          // 프록시이긴 한가
AopUtils.isJdkDynamicProxy(orderService);   // JDK 방식인가
AopUtils.isCglibProxy(orderService);        // CGLIB 방식인가
이 확인이 왜 중요한가 세 번째 출력(프록시가 아예 없음)이 나왔다면 플로우차트의 ①에서 이미 실패한 것이므로, final이나 자기 호출을 뒤질 필요가 없다 — 애초에 AOP 대상으로 잡히지 않은 것이다. 진단의 첫 삽을 어디에 뜰지가 이 한 줄로 갈린다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

스프링 AOP의 한 문장은?
컨테이너에 등록되는 것은 원본이 아니라 원본을 감싼 프록시이고, 부가 기능 코드는 프록시에만 있다.
"원본인 척"하는 방법은?
구현(JDK 동적 프록시) 아니면 상속(CGLIB) 둘뿐. 스프링이 아니라 자바 타입 시스템이 정한 것.
JDK에 인터페이스가 필수인 이유?
newProxyInstance에 넘기는 인터페이스 배열이 타입 정보의 유일한 통로라서. 배열이 비면 아무 타입도 아닌 클래스가 나온다.
스프링 부트의 기본값은?
CGLIB — spring.aop.proxy-target-class=true. 자바 설정으론 @EnableAspectJAutoProxy(proxyTargetClass = true).
JDK 프록시 + 구현 클래스 주입?
BeanNotOfRequiredTypeException(기동 실패) · 캐스팅하면 ClassCastException. 원인은 부모-자식이 아니라 형제.
CGLIB 제약 4종은?
클·메·프·패 — final 클래스 · final 메서드 · 프라이빗 메서드 · 다른 패키지의 패키지 프라이빗.
final 클래스 vs final 메서드?
클래스는 기동이 죽는 좋은 실패, 메서드는 운영에서야 드러나는 나쁜 실패. 악질성은 침묵의 길이로 결정된다.
부가 기능의 실행 조건은?
"애너테이션이 붙었는가"가 아니라 "이 호출이 프록시를 통과했는가".
진단 3질문은?
① 프록시가 만들어졌나 ② 그 메서드를 오버라이드했나 ③ 호출이 프록시를 통과했나.
CGLIB이면 생성자가 두 번?
4.0 이전엔 그랬고 지금은 아니다(Objenesis로 0회). 단, JVM 환경 단서가 있으니 생성자에 부수 효과를 두지 않는다.
@Aspect를 쓰면 AspectJ인가?
아니다. 문법은 AspectJ, 동작은 프록시 — 그래서 final·private·자기 호출 함정이 그대로 있다.
어느 프록시인지 확인하려면?
getClass().getName() — $Proxy123이면 JDK, $$SpringCGLIB$$면 CGLIB, 둘 다 아니면 프록시가 없는 것. AopUtils도 있다.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

프록시는 원본과 '같은 타입인 척'해야 한다 — 자바에서 같은 타입인 척하는 방법은 몇 가지인가요? 필수힌트: 개수를 먼저 말하고, "누가 정했는가"를 덧붙이면 한 칸 올라간다

두 가지다. 인터페이스 구현과 상속. 그리고 이것이 스프링이 정한 것이 아니라 자바 타입 시스템이 정한 것이라는 점을 짚으면 좋다 — 어떤 객체가 다른 타입 변수에 대입될 수 있는 경우가 그 둘뿐이므로, 프록시 기술도 그 둘뿐일 수밖에 없다.

각각이 JDK 동적 프록시(java.lang.reflect.Proxy가 인터페이스 배열을 받아 런타임에 클래스를 생성)와 CGLIB(대상 클래스를 상속한 자식 클래스를 바이트코드로 생성)이다.

주의할 표현이 하나 있다. CGLIB이 상속하는 것은 추상 클래스가 아니라 평범한 구체 클래스 그 자체다. "인터페이스 대신 추상 클래스를 쓴다"가 아니라 "대상 클래스를 그대로 extends 한다"가 정확한 설명이다.

JDK 동적 프록시는 왜 인터페이스가 반드시 필요한가요? 필수힌트: "규칙이라서"가 아니라 메서드 시그니처에서 인과를 끌어낸다

Proxy.newProxyInstance(classLoader, interfaces, handler)가 인터페이스 배열만을 타입 정보로 받아 런타임에 클래스를 찍어내기 때문이다. 이 배열이 비면 아무 타입도 구현하지 않은 클래스가 만들어지고, 그것은 OrderService 타입 변수에 담길 수 없다. 타입 정보를 얻을 통로가 인터페이스밖에 없다는 것이 인과의 전부다.

여기서 한 걸음 더 나가면 가산점이다. 생성된 클래스는 java.lang.reflect.Proxy를 이미 상속하고 있고, 자바는 단일 상속이므로 대상 구현 클래스를 추가로 상속할 자리가 구조적으로 없다. 그래서 JDK 프록시는 구현 클래스 타입으로 절대 캐스팅되지 않는다.

JDK 프록시일 때 @Autowired로 구현 클래스 타입을 주입받으면 어떻게 되나요? 실무 함정힌트: 예외 이름 → 원인 한 문장 → 그 함정이 바꿔놓은 프레임워크 기본값

BeanNotOfRequiredTypeException이 나며 기동이 실패한다. 메시지는 "빈 orderServiceImpl은 OrderServiceImpl 타입이어야 하는데 실제로는 $Proxy123이었다"는 형태이고, 스프링 부트는 여기에 "이 빈은 OrderService만 구현한 JDK 동적 프록시라서 그렇다. 인터페이스로 주입받거나 proxyTargetClass=true를 켜라"는 진단을 덧붙여 준다.

원인을 한 문장으로 답하면 이렇다 — 프록시는 인터페이스를 구현했을 뿐 구현 클래스를 상속한 적이 없어서, 둘은 부모-자식이 아니라 형제 관계다.

그리고 이 답의 진짜 값은 다음 연결에 있다. 스프링 부트가 proxyTargetClass=true를 기본값으로 삼은 이유가 바로 이 사고를 없애기 위해서다. 함정을 아는 것과, 그 함정이 프레임워크 기본값을 바꿔놓은 역사를 아는 것은 다르다.

스프링 부트는 왜 CGLIB을 기본값으로 골랐나요? 필수힌트: 근거 둘 + 설정 키까지

① 타입 주입 사고 차단. JDK 프록시는 구현 클래스 타입으로 주입·캐스팅되지 않아 BeanNotOfRequiredTypeException과 ClassCastException을 만든다. CGLIB 프록시는 대상 클래스의 자식이라 인터페이스로도 구체 클래스로도 받을 수 있다.

② 인터페이스 없는 빈도 프록시해야 한다. 구현체가 하나뿐인 서비스에 인터페이스를 강제하지 않는 요즘 실무에서, JDK 방식만으로는 @Transactional을 걸 수 없는 빈이 대량으로 생긴다.

설정 키는 spring.aop.proxy-target-class=true(부트 기본값)이고, 자바 설정으로는 @EnableAspectJAutoProxy(proxyTargetClass = true), @EnableTransactionManagement(proxyTargetClass = true)다.

final이 클래스에 붙었을 때와 메서드에 붙었을 때, 어느 쪽이 더 악질적인 장애인가요? 시니어 변별힌트: 직관과 반대다. 판단 기준을 먼저 세우고 그 기준으로 답한다

final 메서드 쪽이다.

final 클래스는 상속이 불가능해 프록시 생성 자체가 실패하고 애플리케이션이 뜨지 않는다. 시끄럽게 즉시 죽으므로 배포될 기회조차 없다 — fail-fast의 교과서적 사례다.

final 메서드는 클래스가 상속 가능하니 프록시는 정상적으로 만들어진다. 다만 그 메서드만 오버라이드되지 않아 부가 기능이 빠진다. 컴파일도 기동도 실행도 멀쩡하고, 예외가 나지 않는 정상 경로에서는 결과도 동일하므로 테스트까지 통과한다. @Transactional이었다면 트랜잭션 없이 돌다가 실패 경로에서 데이터가 반쯤 커밋된 뒤에야 발견된다.

여기서 관점 하나를 얹으면 답이 완성된다 — 장애의 악질성은 에러의 크기가 아니라 발견되기까지의 침묵으로 결정된다. 같은 논리로 자기 호출도 final 메서드와 같은 등급의 위험이다.

그럼 대상 클래스가 이미 다른 클래스를 상속하고 있으면 CGLIB이 안 되나요? 함정힌트: 상속하는 쪽과 상속당하는 쪽을 구분한다

함정이 아니다. 상속하는 쪽은 프록시이고 상속당하는 쪽이 대상 클래스이므로, 대상이 이미 부모를 갖고 있어도 프록시 → 대상 → 대상의 부모로 체인이 한 칸 늘어날 뿐이다.

문제가 되는 것은 어디까지나 대상 자신이 final이라 상속당할 수 없는 경우다. "상속을 쓴다"는 말에서 "다중 상속이 안 되니 문제 아닌가"로 넘어가는 오해를 정확히 끊어주면 이해도가 드러난다.

CGLIB 프록시를 만들면 원본 생성자가 두 번 호출되나요? 가산점힌트: "예전엔 그랬다"로 시작해 버전과 라이브러리 이름까지, 그리고 단서 한 줄

스프링 4.0 이전에는 그랬고, 지금은 아니다. 스프링 4.0부터 CGLIB 프록시 인스턴스를 Objenesis로 생성한다. Objenesis는 생성자를 거치지 않고 인스턴스만 확보하는 기법을 모아둔 라이브러리이고, 그래서 프록시 생성 시 대상 생성자가 한 번도 호출되지 않는다. 기본 생성자가 반드시 있어야 한다는 옛 제약도 이때 함께 사라졌다.

다만 공식 문서는 "JVM이 생성자 우회를 허용하지 않는 환경에서는 여전히 두 번 호출되고 디버그 로그가 남을 수 있다"는 단서를 남겨두었다. 그래서 실무 결론은 "절대 안 불린다"가 아니라 "생성자에 부수 효과(로깅, 카운터 증가, 외부 호출)를 두지 않는다"가 된다.

스프링 AOP와 AspectJ의 차이는 무엇인가요?힌트: 적용 "시점"과 "방식"으로 가른 뒤, 마지막에 판단을 얹는다

적용 시점과 적용 방식이 다르다.

스프링 AOP는 런타임에 프록시 객체를 세우는 방식이라 제약이 셋이다 — (1) 스프링 빈에만, (2) 메서드 실행 지점에만, (3) 프록시를 통과한 호출에만 적용된다.

AspectJ는 컴파일 타임이나 클래스 로딩 시점에 바이트코드를 직접 수정(위빙)하는 방식이라 프록시가 아예 존재하지 않는다. 그래서 자기 호출·final·private·생성자·필드 접근까지 전부 잡을 수 있다. 대가는 전용 컴파일러(ajc)나 로드 타임 위빙 에이전트가 필요해 빌드·실행 파이프라인이 복잡해진다는 것이다.

여기에 판단을 얹으면 좋다 — "제약을 만나면 AspectJ로 도망가는 것이 아니라, 대부분은 빈 분리 같은 설계로 푸는 것이 실무 관례"다. 자기 호출 문제 하나를 풀자고 AspectJ를 도입하는 것은 명백한 과잉이다.

@Aspect, @Around를 쓰고 있으면 AspectJ를 쓰고 있는 것 아닌가요? 함정힌트: "문법"과 "엔진"을 분리한다

아니다. 가장 자주 혼동되는 지점이다.

스프링 AOP는 AspectJ의 애너테이션과 포인트컷 표현식 문법만 빌려왔다. @Aspect, @Around("execution(...)")를 쓰고 있어도 실제 엔진은 여전히 런타임 프록시다. 문법은 AspectJ, 동작은 프록시라는 조합인 것이다.

그래서 @Aspect를 쓰는 코드에도 자기 호출·final·private 함정이 그대로 적용된다. 진짜 AspectJ 위빙을 쓰려면 컴파일 타임 위빙(ajc)이나 로드 타임 위빙(LTW)을 별도로 설정해야 한다.

프록시는 모든 public 메서드를 감싸는데, 왜 자기 호출만 부가 기능이 빠지나요?힌트: "감쌌는가"와 "지나갔는가"는 다른 질문이다

부가 기능의 실행 조건이 "메서드가 감싸져 있는가"가 아니라 "호출이 프록시 객체를 통과했는가"이기 때문이다. 프록시는 실제로 모든 대상 메서드를 감싸고 있다 — 다만 그 경로로 호출이 들어오지 않았을 뿐이다.

"CGLIB은 상속이니 오버라이드된 프록시 메서드가 동적 디스패치로 불려야 하지 않나"라는 재반문이 따라올 수 있다. 답은 스프링의 CGLIB 프록시가 super 호출 방식이 아니라 별도 원본 인스턴스에 위임하는 구조라는 것이다. 상속은 타입을 맞추기 위한 수단일 뿐이고, 실행 주체가 원본 인스턴스로 넘어간 순간 프록시는 호출 경로에서 빠지므로 동적 디스패치가 개입할 여지가 없다.

디버거로 프록시 객체를 열어보니 필드가 전부 null이던데, 주입이 안 된 건가요? 가산점힌트: 주입은 누구에게 일어났는가

정상이다. 의존성 주입은 원본 객체(target)에 일어나고, 프록시는 호출을 넘기는 껍데기라서 자기 필드를 채울 이유가 없다. 실제 일은 필드가 채워진 원본이 하므로 동작에는 문제가 없다.

이 현상 자체가 "프록시와 원본은 메모리에 존재하는 서로 다른 두 객체"라는 사실의 직접적인 증거이기도 하다. 자기 호출 함정을 설명할 때 이 관찰을 근거로 쓰면 설명이 훨씬 구체적이 된다.

실행 중에 지금 이 빈이 어느 프록시인지 어떻게 확인하나요? 가산점힌트: 클래스 이름 하나로 세 가지 경우가 갈린다

bean.getClass().getName()을 찍어보는 것이 가장 빠르다. jdk.proxy2.$Proxy123 형태면 JDK 동적 프록시, 이름에 $$SpringCGLIB$$가 들어 있으면 CGLIB 프록시, 원본 클래스 이름 그대로면 프록시가 아예 씌워지지 않은 것이다.

스프링이 제공하는 판별 유틸도 있다 — AopUtils.isAopProxy(...), AopUtils.isJdkDynamicProxy(...), AopUtils.isCglibProxy(...).

이 확인이 진단의 첫 삽이 되는 이유는, 세 번째 경우(프록시 없음)라면 final이나 자기 호출을 뒤질 필요가 없기 때문이다 — 애초에 AOP 대상으로 잡히지 않은 것이므로 문제는 빈 등록·포인트컷·설정 쪽에 있다.

JDK 프록시일 때, 인터페이스에 선언되지 않은 public 메서드는 어떻게 되나요? 함정힌트: "부가 기능이 빠진다"보다 한 단계 앞의 문제가 있다

프록시가 그 메서드를 아예 갖고 있지 않다. JDK 프록시는 넘겨받은 인터페이스에 선언된 메서드만 구현한 클래스이기 때문이다. 그래서 인터페이스 타입으로 주입받은 참조로는 그 메서드를 호출할 방법 자체가 없고(컴파일이 안 된다), 부가 기능 적용 여부를 따지기 이전의 문제가 된다.

반대로 CGLIB은 대상 클래스를 통째로 상속하므로 인터페이스에 없는 public 메서드까지 그대로 오버라이드해 감싼다. 표의 "부가 기능이 빠지는 메서드" 행이 두 기술에서 다른 이유가 이것이다 — JDK는 "인터페이스 밖", CGLIB은 "final·private"가 사각지대다.

@Transactional을 인터페이스 쪽에 붙여도 되나요? 함정힌트: 부트 기본값이 무엇인지 떠올리면 답이 나온다

스프링 공식 권장은 "구체 클래스(와 그 메서드)에 붙이라"다. 이유가 정확히 이 문서의 주제와 맞물린다 — 클래스 기반 프록시(CGLIB)를 쓰면 인터페이스에 붙은 애너테이션이 인식되지 않기 때문이다.

그래서 인터페이스에만 붙여둔 코드는 JDK 프록시 환경에서는 동작하다가, proxyTargetClass=true(부트 기본값)로 넘어가는 순간 조용히 무효가 될 수 있다. 설정 값 하나에 따라 트랜잭션이 붙었다 떨어졌다 하는 코드는 그 자체로 위험하므로, 구현 클래스에 붙이는 것을 규칙으로 삼는다.

프록시는 빈 생명주기의 어느 시점에 만들어지나요? 가산점힌트: 그 답에서 "@PostConstruct 안에서는 왜 트랜잭션이 안 걸리나"가 따라 나온다

빈 후처리기(BeanPostProcessor)가 초기화 이후 단계에서 원본 대신 프록시를 돌려주는 방식이다. 즉 원본 생성 → 의존성 주입 → 초기화 콜백 → (그다음) 프록시로 교체의 순서이고, 컨테이너에 최종적으로 남는 것이 교체된 프록시다.

여기서 따름정리 하나가 나온다 — @PostConstruct 같은 초기화 콜백은 원본 객체에서 실행되고, 그 안에서 this로 부르는 호출에는 부가 기능이 걸리지 않는다. 원리는 자기 호출과 완전히 같다(프록시를 통과하지 않았다). "초기화 때 캐시를 데워두려고 @PostConstruct에서 @Cacheable 메서드를 불렀는데 캐시가 안 차더라"는 사고가 여기서 나온다.

private 메서드에 @Transactional을 붙이면 왜 컴파일 에러도 경고도 없나요? 함정힌트: 애너테이션은 그 자체로 무엇을 하는가

애너테이션은 그 자체로 아무 동작도 하지 않는 표식(메타데이터)이기 때문이다. 동작을 만들어내는 주체는 그 표식을 읽고 프록시를 씌우는 컨테이너이고, 컴파일러는 그 표식이 실제로 효력을 갖는지까지 검증하지 않는다.

private은 CGLIB에서는 오버라이드 대상이 아니고, JDK에서는 인터페이스에 선언조차 할 수 없어 어느 방식으로도 구제되지 않는 유일한 케이스다. 그래서 결과는 가장 나쁜 형태의 실패 — 조용한 실패가 된다. 정적 분석 도구나 코드 리뷰 체크리스트로 잡는 수밖에 없다는 것이 실무 결론이다.

한 줄 요약
스프링 AOP는 원본 대신 "원본인 척하는 대리인"을 컨테이너에 등록하는 구조이고, 척하는 방법이 인터페이스 구현(JDK 동적 프록시)이냐 상속(CGLIB, 부트 기본값)이냐의 차이일 뿐이라서 — JDK 방식은 인터페이스가 없으면 만들 수 없고 구현 클래스 타입으로 주입받으면 BeanNotOfRequiredTypeException을 내며(부트가 CGLIB으로 갈아탄 이유), CGLIB 방식은 final 클래스면 기동이 죽고 final·private 메서드면 조용히 새고, 양쪽 모두 프록시를 통과하지 않은 자기 호출에는 걸리지 않는다 — "붙였는데 동작 안 함" 계열 장애는 전부 "프록시가 이 메서드를 오버라이드할 수 있었는가"와 "이 호출이 프록시를 통과했는가" 두 질문으로 진단된다.
