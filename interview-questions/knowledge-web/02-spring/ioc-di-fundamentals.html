IoC와 DI — 제어의 역전과 의존성 주입, 왜 쓰는가

📖 약 5분 🧩 5개 섹션 0/5 섹션 이해
🎯 핵심 관전 포인트

IoC(제어의 역전)는 객체의 생성·생명주기 관리·의존관계 연결의 주도권을 개발자 코드에서 프레임워크(컨테이너)로 넘기는 설계 원칙이고, DI(의존성 주입)는 그 원칙을 구현하는 구체적인 방법이다 — 객체가 필요한 의존성을 직접 new로 만들지 않고 외부에서 넣어받는 것. 이렇게 하면 클래스가 구현체가 아닌 인터페이스(추상화)에만 의존하게 되어 결합도가 낮아지고, 구현 교체가 쉬워지고, 테스트 시 가짜 객체를 끼워 넣을 수 있게 된다.

0

질문 + 의도

▾
면접 질문

"IoC와 DI란 무엇이고, 왜 사용하나요?"

출제 의도"왜"를 묻는 이유는 테스트 가능성과 결합도 관점에서 설명할 수 있는지 보기 위해서다. 이걸 설명 못 하는 사람은 DI를 쓰면서도 static 유틸과 new를 남발해 테스트 불가능한 코드를 만든다.
1

IoC — "제어의 주도권이 뒤집힌다"

▾

전통적인 코드에서는 내 코드가 주도권을 갖는다. 필요한 객체를 내가 만들고, 내가 호출한다.

java
// 전통적 방식: 내가 만들고 내가 제어
public class OrderService {
    private final PaymentGateway gateway = new TossPaymentGateway();  // 내가 직접 생성
}

IoC는 이 주도권을 컨테이너에게 넘기는 것이다. "객체를 언제 만들고, 누구와 연결하고, 언제 소멸시킬지"를 스프링 컨테이너가 결정하고, 내 코드는 호출당하는 입장이 된다.

  • 비유: 직접 재료를 사서 요리하는 것(전통) vs 뷔페에서 차려진 음식을 받는 것(IoC). 무엇을 먹을지(비즈니스 로직)는 내가 정하지만, 조리(객체 생성·조립)는 주방이 한다.
  • 이런 특성을 할리우드 원칙이라고도 한다 — "Don't call us, we'll call you." (프레임워크가 내 코드를 호출한다)

꼬리질문 대비: IoC는 DI보다 넓은 개념이다. 템플릿 메서드 패턴, 서블릿 컨테이너가 서블릿 생명주기를 관리하는 것, JdbcTemplate이 콜백을 호출해주는 것도 모두 IoC의 한 형태다.

2

DI — IoC를 실현하는 구체적 수단

▾

DI는 "필요한 의존성을 외부에서 주입받는다"는 패턴이다.

✕ BEFORE직접 생성 — 강한 결합
public class OrderService {
    private final PaymentGateway gateway = new TossPaymentGateway();
    // 문제 1: Toss → Kakao로 바꾸려면 이 클래스를 수정해야 함
    // 문제 2: 테스트할 때 진짜 결제 API가 호출됨 (가짜로 바꿀 방법이 없음)
    // 문제 3: TossPaymentGateway의 생성 방법이 바뀌면 여기도 깨짐
}
✓ AFTER생성자 주입 — 느슨한 결합
public class OrderService {
    private final PaymentGateway gateway;   // 인터페이스에만 의존

    public OrderService(PaymentGateway gateway) {   // 외부에서 넣어줌
        this.gateway = gateway;
    }
}

핵심 효과는 의존 방향이 추상화를 향하게 된다는 것이다. OrderService는 이제 "어떤 구현체가 오는지" 전혀 모른다. 이것이 DIP(의존관계 역전 원칙)와 OCP(개방-폐쇄 원칙)를 코드 수준에서 실현하는 방법이다.

3

왜 사용하는가 — 세 가지 실익

▾

① 결합도 감소와 구현 교체

결제사를 교체할 때 OrderService는 한 줄도 수정하지 않는다. 빈 등록(설정)만 바꾸면 된다.

java
@Configuration
public class PaymentConfig {
    @Bean
    public PaymentGateway paymentGateway() {
        return new KakaoPaymentGateway();   // 여기만 변경
    }
}

② 테스트 용이성 (실무에서 가장 체감이 큰 이점)

java
// 진짜 결제 API 없이 OrderService의 로직만 검증
PaymentGateway fake = mock(PaymentGateway.class);
when(fake.pay(any())).thenReturn(PaymentResult.success());

OrderService service = new OrderService(fake);   // 가짜를 주입
service.placeOrder(order);                        // 순수 로직만 테스트

직접 new 하는 구조였다면 mock을 끼워 넣을 자리 자체가 없다.

③ 객체 생명주기와 횡단 관심사의 위임

컨테이너가 생성을 관리하기 때문에 싱글톤 보장, 초기화/소멸 콜백, 그리고 프록시 기반 AOP(@Transactional, @Cacheable 등)가 가능해진다. 내가 new로 만든 객체에는 스프링이 프록시를 씌울 기회가 없다 — "DI가 안 되면 @Transactional도 안 먹는다"는 점을 언급하면 가산점.

4

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

방식특징
생성자 주입권장. 필수 의존성 보장
수정자(setter) 주입선택적/변경 가능한 의존성용
필드 주입 (@Autowired 필드)테스트·불변성에 불리, 지양

생성자 주입을 권장하는 이유:

  1. final 선언 가능 → 불변 보장, 주입 누락 시 컴파일/기동 시점에 즉시 실패
  2. 순환 참조를 기동 시점에 감지 — 필드 주입은 실제 호출 시점까지 숨어 있을 수 있음
  3. 컨테이너 없이 순수 자바로 테스트 가능 — new OrderService(fake) 처럼
  4. 생성자 파라미터가 비대해지면 "이 클래스가 책임이 너무 많다"는 설계 신호가 됨 (필드 주입은 이 신호를 숨김)
💡

"IoC는 '제어를 넘긴다'는 원칙(what), DI는 그것을 '의존성을 주입받는 방식으로' 실현하는 패턴(how)이다. DI 없이도 IoC는 존재하고(템플릿 메서드, 서비스 로케이터), 스프링은 IoC를 주로 DI로 구현한 것이다."

  • DIP: "고수준 모듈은 저수준 모듈이 아닌 추상화에 의존하라"는 SOLID의 설계 원칙
  • DI: 그 원칙을 지키도록 의존성을 밖에서 넣어주는 구현 기법
  • DI를 쓴다고 자동으로 DIP가 지켜지는 건 아니다 — OrderService(TossPaymentGateway gateway)처럼 구현체 타입을 주입받으면 DI는 했지만 DIP는 위반이다.
  • 객체 그래프가 설정/애너테이션 뒤로 숨어 흐름 추적이 어려워짐 (어떤 구현체가 주입되는지 코드만 봐서는 모름)
  • 컨테이너 기동 비용, 러닝 커브
  • 과도한 추상화 — 구현체가 하나뿐이고 바뀔 일도 없는데 인터페이스부터 만드는 것은 비용. "교체 가능성과 테스트 필요성이 있는 지점에 선별 적용한다"고 답하면 균형 잡힌 인상을 준다.
✅ 한 줄 요약

IoC는 객체의 생성·조립·생명주기의 주도권을 컨테이너로 넘기는 원칙이고, DI는 이를 "의존성을 외부에서 주입"하는 방식으로 실현하는 패턴이다. 그 대가로 얻는 것이 낮은 결합도, 쉬운 구현 교체, 그리고 mock 주입이 가능한 테스트 구조다.
