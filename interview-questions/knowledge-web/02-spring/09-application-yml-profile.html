application.yml Profile 활용
환경 분리는 "운영이 로컬 DB에 붙는" 사고를 막는 기본 방어선

면접 질문: "application.yml의 profile은 어떻게 활용하나요?"

핵심 관전 포인트 — 프로파일은 하나의 빌드 산출물을 로컬·개발·스테이징·운영에서 각기 다른 설정으로 띄우기 위한 스프링의 환경 분리 장치다. 관례는 application.yml에 환경 무관 공통 설정만 두고, DB 접속 정보처럼 환경마다 달라지는 값은 전부 application-{profile}.yml로 분리한 뒤 배포 환경에서 SPRING_PROFILES_ACTIVE 환경변수로 활성화하는 것이다. 다만 인과를 정확히 말해야 한다 — 프로파일을 썼기 때문에 안전해지는 것이 아니다. 안전을 만드는 것은 "기동에 반드시 필요한 설정(DataSource URL)을 공통 yml에서 비워 두는 설계 결정"이고, 프로파일은 그 비워 둔 자리를 환경별로 채워 넣는 수단일 뿐이다. 이 설계를 택하는 순간 프로파일 지정을 깜빡하면 Failed to configure a DataSource … (no profiles are currently active)로 기동 자체가 죽으므로 — 조용히 엉뚱한 DB에 붙는 대신 시끄럽게 죽는(fail-fast) — 환경 오연결 사고가 구조적으로 불가능해진다. 여기에 활성화 경로의 우선순위, 부트 2.4의 문법 변경(spring.profiles → spring.config.activate.on-profile), 그리고 yml에 남는 것이 시크릿만이 아니라 토폴로지라는 한계까지 이어 말할 수 있으면 완성이다.
  • 1
    프로파일은 "하나의 jar를 환경별 설정으로 갈아 끼우는 스위치"다 — 활성 프로파일 이름에 맞는 설정 파일을 추가로 읽고, 그 이름이 붙은 빈만 등록한다. 그래서 공통은 application.yml, 환경 의존 값은 application-{profile}.yml로 나누고, 배포 환경에서는 SPRING_PROFILES_ACTIVE=prod 환경변수로 켠다.
  • 2
    다만 인과를 정확히 말하면 — 프로파일을 써서 안전해지는 것이 아니다. 안전을 만드는 것은 "기동에 필수인 DataSource URL을 공통 yml에서 비워 두겠다"는 설계 결정이고, 프로파일은 그 빈자리를 채우는 수단이다. 같은 프로파일을 쓰면서 공통 yml에 로컬 DB URL을 남겨두면 방어선은 존재하지 않는다.
  • 3
    그 결정이 만드는 결과가 이 질문의 핵심이다 — 프로파일 누락이라는 흔한 휴먼 에러가 "며칠 뒤 발견되는 조용한 오연결"이 아니라 "배포 즉시의 기동 실패"로 격하된다. (no profiles are currently active)가 그 자리에서 찍히므로 데이터는 단 한 건도 잘못 흐르지 않는다. 이것이 안전한 기본값(secure by default) 설계다.

0. 질문 + 출제 의도

질문: "application.yml의 profile은 어떻게 활용하나요?"

출제 의도: 로컬/스테이징/운영의 설정 분리는 "운영 DB에 로컬 설정으로 붙는" 류의 사고를 막는 기본 방어선이다. 환경 분리를 대충 하는 사람은 언젠가 반드시 사고를 낸다는 관점에서, 환경 구성의 기본기를 확인한다.

이 페이지가 겨냥하는 약점 세 가지 ① "파일 나눠서 씁니다"에서 멈추는 것 → 2절에서 프로파일이 하는 일을 "설정 파일 선택 + 빈 선택" 딱 둘로 좁히고, 하지 않는 일(검증·강제·경고)을 못 박는다. 7절 사고가 가능한 이유가 정확히 여기다.
② "프로파일 쓰면 안전하다"는 인과 착각 → 8절에서 원인(설계 결정)과 수단(프로파일)을 분리한다. 안티패턴 구성도 프로파일을 쓰고 있는데 사고가 났다.
③ 우선순위와 버전을 얼버무리는 것 → 4절의 7층 우선순위 스택과 3절의 부트 2.4 문법 변경을 숫자·키 이름 수준으로 붙잡는다.
두 문장 비유 — 멀티탭 라벨, 그리고 누전차단기 멀티탭 라벨: 기계(코드)는 하나인데 어느 콘센트(환경)에 꽂느냐에 따라 연결되는 전원(DB·외부 시스템)이 달라진다. 프로파일은 그 콘센트에 붙은 라벨이다.  /  누전차단기: 배선에 이상이 생겼을 때 좋은 설계는 "조용히 감전시키는 것"이 아니라 "전기를 끊어버리는 것"이다. 8절의 fail-fast가 정확히 이것 — 설정이 비어 있으면 앱은 뜨지 않는다.

1. 왜 프로파일인가 — 선택지 셋 중 나머지 둘이 왜 안 되는지

같은 코드인데 환경마다 달라져야 하는 값이 있다. 로컬은 내 PC의 DB·상세 로그·목(mock) 외부 연동, 개발/스테이징은 개발용 DB·테스트 계정·검증용 외부 시스템, 운영은 운영 DB·최소 로그·실 결제와 알림 연동이다.

문제는 이 차이를 어디에 담느냐다. 선택지는 크게 셋이고, 프로파일이 왜 답인지는 나머지 둘이 왜 안 되는지를 보면 드러난다.

원칙 한 줄 — 프로파일이 구현하는 것

설정은 코드가 아니라 환경에 둔다  /  빌드 산출물은 하나, 바뀌는 것은 기동 시점의 스위치뿐

12-factor app의 config 원칙을 스프링이 구현한 것이 프로파일이라고 보면 정확하다. 그래서 "환경별로 jar를 따로 빌드한다"는 말이 나오는 순간 이미 프로파일의 이점을 버린 것이다.

2. 프로파일이 실제로 하는 일 — 딱 두 가지, 그리고 하지 않는 일

"프로파일"이라는 말을 처음 만나면 "환경별 설정을 알아서 관리해 주는 기능"처럼 크게 들린다. 실제로 하는 일은 훨씬 작고 단순하다. 활성 프로파일 이름의 목록을 들고 있으면서, 그 이름에 해당하는 설정 파일과 빈만 골라 적용하는 것이 전부다.

암기 장치 — 프로파일이 하는 일은 "파일 고르기 · 빈 고르기" 둘뿐

활성 프로파일 = 이름 목록  →  ① 설정 파일 선택(덮어쓰기)  +  ② 빈 선택(등록 여부)

뒤집어 외울 것: "검증 · 강제 · 경고는 안 한다." 프로파일은 메커니즘이지 정책이 아니다 — 정책은 8절처럼 내가 설계로 만들어야 한다.

3. 파일 구조와 문법 — 어디에 쓰고, 부트 2.4에서 무엇이 바뀌었나

3-1. 파일 분리 방식 (가장 일반적)

src/main/resources/
├── application.yml          # 공통: 환경과 무관한 설정만
├── application-local.yml    # 로컬 개발자 PC
├── application-dev.yml      # 개발 서버
├── application-stg.yml      # 스테이징
└── application-prod.yml     # 운영

파일명 규칙은 application-{프로파일 이름}.yml이다. 활성 프로파일이 prod면 부트가 application-prod.yml을 찾아 읽는다.

공통 application.yml — 환경 무관 설정만
spring:
  application:
    name: order-service
  jpa:
    open-in-view: false   # 어느 환경이든 동일해야 하는 정책성 설정

server:
  port: 8080

# datasource 는 여기 없다 — 8절의 방어선이 바로 이 "없음"이다
환경 application-local.yml / application-prod.yml
# application-local.yml — 로컬에서만 쓰는 값
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/order
    username: local_user
    password: local_pw      # 로컬 한정이므로 파일에 있어도 무방
logging:
  level:
    org.hibernate.SQL: debug

# application-prod.yml — 시크릿은 자리표시자로
spring:
  datasource:
    url: jdbc:postgresql://prod-db.internal:5432/order
    username: ${DB_USERNAME}   # 실제 값은 환경변수·시크릿 저장소에서
    password: ${DB_PASSWORD}
logging:
  level:
    root: warn

3-2. 멀티 도큐먼트 방식 — 한 파일 안에서 ---로 나누기

파일을 나누는 대신 한 파일 안에서 ---로 문서를 나눠 구분할 수도 있다. YAML에서 ---는 "여기부터 새 문서"라는 표준 구분자다.

# application.yml 하나에서 프로파일별 블록 분리
spring:
  application:
    name: order-service

---
spring:
  config:
    activate:
      on-profile: local      # 이 블록은 local 프로파일일 때만 적용된다
  datasource:
    url: jdbc:postgresql://localhost:5432/order

---
spring:
  config:
    activate:
      on-profile: prod
  datasource:
    url: jdbc:postgresql://prod-db.internal:5432/order

설정 양이 적을 때는 한 파일이 편하지만, 환경이 늘고 설정이 커지면 파일 분리가 가독성과 코드 리뷰의 diff 확인에 유리하다.

3-3. 부트 2.4의 문법 변경 — 옛 키를 그대로 두면 기동이 죽는다 함정

이 문서의 서술은 스프링 부트 2.4 이상 기준이다. 2.4에서 설정 데이터 처리가 개편되며 "이 문서가 언제 적용되는가"를 지정하는 키가 바뀌었다.

멀티 도큐먼트에서 블록의 활성화 조건을 지정하는 키
부트 버전문서 활성화 조건 키옛 키(spring.profiles)를 쓰면
~ 2.3spring.profiles: local정상 동작
2.4 ~spring.config.activate.on-profile: local기동 시 예외로 죽는다

2.4 이상에서 옛 문법을 그대로 두면 어떻게 되는지가 중요하다. 조용히 무시되는 것이 아니라, 명시적인 예외로 기동이 실패한다. 부트는 설정 데이터를 처리하면서 spring.profiles 키를 발견하면 InvalidConfigDataPropertyException을 던지고, 메시지에 대체 키까지 알려준다.

Property 'spring.profiles' imported from location 'class path resource [application.yml]'
is invalid and should be replaced with 'spring.config.activate.on-profile'
[origin: class path resource [application.yml] - 8:3]   ← 파일명 + 줄:칸까지 찍힌다

origin에 파일명과 줄·칸 번호까지 찍히므로 고칠 자리가 바로 나온다. 부트를 2.3에서 2.4 이상으로 올릴 때 만나는 대표적인 기동 실패이고, 조용한 오동작이 아니라 시끄러운 실패로 처리한 것 자체가 부트의 의도다 — 프로파일 조건이 조용히 무시되면 모든 블록이 적용되는 상태가 되어, 7절에서 볼 오연결 사고와 똑같은 결과가 나기 때문이다.

4. 프로파일을 켜는 네 경로, 그리고 같은 키가 겹치면 누가 이기나

4-1. 네 가지 경로

# 1. 커맨드라인 인자 — 가장 강하다
java -jar app.jar --spring.profiles.active=prod

# 2. JVM 시스템 프로퍼티 (-D)
java -Dspring.profiles.active=prod -jar app.jar

# 3. 환경변수 — 배포 환경의 사실상 표준 관례
#    (k8s Deployment env, systemd unit, Docker -e 등에서 지정)
export SPRING_PROFILES_ACTIVE=prod

# 4. yml 안에 지정 — 로컬 기본값 용도 정도로만
#    application.yml:  spring.profiles.active: local

왜 SPRING_PROFILES_ACTIVE는 대문자에 밑줄인가 — 완화된 바인딩(relaxed binding)

SPRING_PROFILES_ACTIVE→밑줄을 점으로→전부 소문자로→spring.profiles.active

셸의 환경변수 이름에는 점(.)을 쓸 수 없다. 스프링이 이름을 변환해 주기 때문에 같은 프로퍼티를 환경변수로도 줄 수 있는 것이다. 이 규칙은 프로파일뿐 아니라 모든 설정 키에 적용된다 — SPRING_DATASOURCE_URL → spring.datasource.url.

테스트에는 별도의 경로가 하나 더 있다.

// 테스트 전용 — 이 테스트 컨텍스트의 활성 프로파일을 직접 지정한다
@SpringBootTest
@ActiveProfiles("test")
class OrderServiceTest { ... }

@ActiveProfiles는 프로퍼티를 통하지 않고 테스트 컨텍스트의 Environment에 활성 프로파일을 직접 심는다. 부트는 이렇게 프로그래밍 방식으로 지정된 프로파일을 프로퍼티로 바인딩된 값보다 우선하므로, application.yml에 spring.profiles.active: local이 들어 있어도 테스트는 test 프로파일로 뜬다.

4-2. 외부화 설정 우선순위 — 프로파일만이 아니라 모든 설정값에 적용된다

스프링 부트는 여러 곳에서 프로퍼티를 읽어 층층이 쌓고, 위층이 아래층을 덮는다.

암기 장치 — 실전에서 부딪히는 네 층만: "커 · 시 · 환 · 파"

커맨드라인 인자 > 시스템 프로퍼티(-D) > 환경변수 > 파일(yml)

7층 전체를 못 외워도 이 네 개면 실무 질문의 대부분이 커버된다. 그리고 파일들 사이의 순서는 "jar 안 → jar 밖", "공통 → 프로파일별" 두 축으로 기억한다.

jar 밖 파일이 jar 안을 이긴다 — 탈출구이자 사고 원인 부트는 클래스패스뿐 아니라 실행 디렉토리(./, ./config/)에서도 같은 이름의 파일을 찾는다. 그래서 재빌드 없이 jar 옆에 application-prod.yml을 놓아 값을 덮을 수 있다. 장애 중에 커넥션 풀만 급히 올리는 긴급 탈출구가 되지만, 동시에 "이 서버만 설정이 다른데 아무도 모르는" 사고의 원인이기도 하다 — 저장소의 yml을 아무리 읽어도 실제 값이 안 나온다. 이 방식을 쓴다면 반드시 형상 관리 대상으로 잡아야 한다.

5. @Profile — 값이 아니라 빈 자체를 갈아 끼우기

지금까지는 값을 바꾸는 이야기였다. 그런데 환경에 따라 바뀌어야 하는 것이 값이 아니라 동작 자체인 경우가 있다. 로컬에서 실제 결제를 긁거나 실제 문자를 보내면 안 되는 상황이 대표적이다. 이럴 때는 값이 아니라 빈 구현체 자체를 환경별로 바꾼다.

before 값으로 풀려다 실패하는 형태 — 분기가 코드에 남는다
@Component
public class PaymentGateway {

    @Value("${payment.mock-enabled:false}")
    private boolean mockEnabled;

    public PaymentResult pay(Order order) {
        // 운영 코드 안에 "가짜로 처리하는 경로"가
        // 영구히 살아 있다.
        if (mockEnabled) {프로퍼티 하나만 잘못 켜지면
            return PaymentResult.success("MOCK-" + order.id());운영에서 결제가 통과된 척한다
        }
        return pgClient.charge(order);
    }
}
after 구현체를 통째로 교체 — 운영 바이너리엔 목이 "등록조차" 안 된다
public interface PaymentGateway {

@Component

핵심은 주입받는 쪽 코드에 분기가 하나도 없다는 것이다. PaymentGateway를 생성자 주입으로 받아 쓰는 서비스는 자기가 목을 쓰는지 실물을 쓰는지 모른다. 활성 프로파일에 해당하는 빈만 컨테이너에 등록되므로 실행 중에 결정할 것이 아무것도 남지 않는다.

@Profile("prod")
해당 프로파일일 때만 등록
@Profile({"local","dev"})
여러 개 나열 = OR
@Profile("!prod")

어느 프로파일에도 걸리지 않으면 — 빈이 0개가 되어 기동이 죽는다

위 예에서 stg 프로파일로 띄우면 PaymentGateway 구현이 하나도 등록되지 않아, 주입받는 쪽에서 NoSuchBeanDefinitionException으로 기동이 실패한다.

언뜻 불편해 보이지만 이것도 8절과 같은 종류의 fail-fast다 — "빈이 없다"가 기동 시점에 드러나는 편이, 운영에서 결제 호출이 아무 일도 안 하는 것보다 훨씬 낫다. 조용히 도는 것보다 시끄럽게 죽는 편이 낫다는 원칙이 값(8절)에서든 빈(5절)에서든 동일하게 적용된다.

6. 프로파일 그룹 — 나열 실수를 구조적으로 없앤다 가산점

프로파일이 "환경"만이 아니라 "기능 스위치"로도 늘어나면 개수가 빠르게 불어난다. 부트 2.4부터는 여러 프로파일을 이름 하나로 묶을 수 있다.

spring:
  profiles:
    group:
      prod: "prod-db, prod-mq, monitoring"   # prod 하나 켜면 세 개가 같이 켜진다

그룹이 없을 때

  • 배포 스크립트가 prod,prod-db,prod-mq,monitoring을 정확히 나열해야 한다.
  • 하나만 빠뜨려도 그 프로파일의 yml이 통째로 안 읽힌다.
  • 나열 순서가 바뀌면 겹치는 키의 승자가 달라진다 — 그런데 아무도 리뷰하지 않는다.

그룹이 있을 때

  • 배포 스크립트는 SPRING_PROFILES_ACTIVE=prod 하나만 지정한다.
  • 세부 구성과 순서가 설정 파일 안에 고정되어 코드 리뷰를 탄다.
  • 빠뜨릴 것이 없는 구조로 바꾼 것 — 휴먼 에러 지점 자체를 제거.

함정 — 프로파일 2개 이상을 켤 때의 "순서 의존 오버라이드"

--spring.profiles.active=prod,monitoring처럼 쉼표로 여러 개를 켤 수 있고 각 프로파일의 yml이 모두 적용된다. 같은 키가 겹치면 나중에 처리된(목록에서 뒤에 선언된) 프로파일 값이 이긴다.

prod,monitoring 과 monitoring,prod 는 다른 결과를 낸다

대응은 둘이다. ① 여러 프로파일이 같은 키를 정의하지 않도록 역할을 나눈다(환경 프로파일 1개 + 기능 스위치 프로파일들). ② 조합이 필요하면 spring.profiles.group으로 묶어 이름 하나로 켠다.

7. 실무 사고 시나리오 — 프로파일 지정을 깜빡하면 출제 의도의 정중앙

환경 분리를 "그냥 파일 나누기"로만 아는 사람과, 사고를 구조적으로 막는 방어선으로 이해하는 사람이 여기서 갈린다.

프로파일을 지정하지 않고 기동하면 스프링 부트는 default 프로파일로 뜬다. 에러도 경고도 없다. 이때 읽히는 것은 기본 application.yml뿐이고 application-{profile}.yml은 아무것도 적용되지 않는다. 문제는 흔한 안티패턴 구성에서 터진다.

안티패턴 기본 application.yml에 로컬 접속 정보가 들어 있다
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/order   # "로컬 기본값이니 편하겠지"이 한 줄이 방어선을 지운다
    username: local_user
    password: local_pw

용어 한 개 — 조용한 오연결(silent misconnection)

앱은 정상 기동하고 헬스체크도 통과하는데, 붙은 DB만 엉뚱한 곳인 상태

운영 장비에 우연히 DB가 떠 있거나 기본값이 개발 DB를 가리키고 있으면 운영 트래픽이 엉뚱한 DB에 쓰는 최악의 시나리오가 된다. 모니터링 지표는 전부 초록이므로 탐지 수단이 사람의 신고밖에 없다.

8. 인과를 바로잡기 — 안전을 만드는 것은 프로파일이 아니다 변별 지점

가장 흔한 오해를 정면으로 짚어야 한다. "프로파일을 쓰면 이런 사고가 안 난다"는 말은 틀렸다. 7절의 안티패턴도 프로파일을 쓰고 있다. application-prod.yml도 있고 application-local.yml도 있다. 그런데 사고가 났다.

8-1. 그래서 이렇게 고친다 — fail-fast 설계

핵심 아이디어 한 문장: "실수했을 때 조용히 잘못 도는 것"보다 "시끄럽게 죽는 것"이 안전하다
before application.yml에 로컬 DB가 남아 있다
spring:
  application:
    name: order-service
  datasource:프로파일이 없어도 채워진다 = 방어선 없음
    url: jdbc:postgresql://localhost:5432/order
    username: local_user
    password: local_pw

# 프로파일 누락 → 정상 기동 → 조용한 오연결
after 공통에는 환경 무관 설정만, DB 정보는 프로파일로
spring:
  application:
    name: order-service
  jpa:
    open-in-view: false
# datasource 항목 자체가 없다.이 "없음"이 방어선이다
# 프로파일 없이 뜨면 채울 값이 없어 기동이 죽는다.

# application-local.yml — 로컬 접속 정보는 여기로 이동
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/order
    username: local_user
    password: local_pw

이제 같은 실수를 하면 앱은 기동 도중 죽고, 이런 메시지를 남긴다.

***************************
APPLICATION FAILED TO START
***************************

Description:

Failed to configure a DataSource: 'url' attribute is not specified and
no embedded datasource could be configured.

Reason: Failed to determine a suitable driver class

Action:

Consider the following:
	If you want an embedded database (H2, HSQL or Derby), please put it on the classpath.
	If you have database settings to be loaded from a particular profile you may need to
	activate it (no profiles are currently active).

이 메시지를 한 줄씩 읽어 보면 부트가 정확히 이 상황을 예상하고 만들어 둔 안내라는 것을 알 수 있다.

1
'url' attribute is not specified — 무엇이 없는지를 지목한다.
2
If you have database settings to be loaded from a particular profile you may need to activate it — "프로파일에서 읽어야 할 DB 설정이 있다면 프로파일을 활성화해야 할 수 있다"고 원인을 직접 지목한다.
3
(no profiles are currently active) — 지금 활성 프로파일이 하나도 없다는 사실까지 괄호로 붙여 준다. 프로파일이 있었다면 (the profiles prod are currently active)처럼 이름이 찍힌다.

배포 담당자는 이 세 줄을 읽고 그 자리에서 "아, 프로파일을 안 줬구나"를 알아챈다. 데이터는 단 한 건도 잘못 흐르지 않는다. 같은 실수(프로파일 누락)가 "며칠 뒤 발견되는 데이터 사고"에서 "배포 순간 발견되는 기동 실패"로 격하된 것이다.

암기 카드 — 이 문서에서 반드시 인출해야 할 개념 이름 둘

fail-fast
잘못된 상태로 계속 도는 대신 즉시 실패시킨다. 실수의 발견 시점을 배포 순간으로 끌어당기는 설계.
secure by default (안전한 기본값)
시스템의 기본 상태가 "위험하게 동작"이 아니라 "동작 거부"가 되도록 설계한다.

로컬 개발 편의는 IDE Run Configuration에 local 프로파일을 박아 두면 되므로 잃는 것이 없다. "편해서"는 방어선을 지불할 이유가 되지 못한다.

8-2. 무엇을 어디에 둘 것인가 — 기준은 단 하나

배치 기준 — "환경마다 값이 달라지는가"

성격예둘 자리
환경 의존DB URL·계정, 외부 API 엔드포인트와 키, 브로커 주소, 로그 레벨application-{profile}.yml
환경 무관애플리케이션 이름, JPA 정책(open-in-view), 직렬화 포맷, 잭슨 설정기본 application.yml

특히 DataSource처럼 "없으면 기동이 실패하는" 필수 설정을 프로파일 쪽에 두는 것이 핵심이다. 그것이 프로파일 누락을 기동 실패로 바꿔 주는 트리거이기 때문이다.

그러면 DB를 안 쓰는 서비스는? — 트리거가 없다 8-1의 방어선은 "DB를 쓰는 앱"에서만 통한다. DataSource가 없어야만 죽는 구조이기 때문이다. DB를 쓰지 않는 서비스에는 같은 fail-fast를 명시적 검증 코드로 만들어 줘야 한다 — 기동 시 활성 프로파일을 검사해 기대 목록 밖이면 직접 예외를 던진다.
가산점 방어선 추가 — 알 수 없는 프로파일이거나 없으면 기동 거부
@Component
public class ProfileGuard implements InitializingBean {

    private static final Set<String> ALLOWED = Set.of("local", "dev", "stg", "prod");
    private final Environment env;

    public ProfileGuard(Environment env) { this.env = env; }

    @Override
    public void afterPropertiesSet() {
        // DataSource가 없어야만 죽는 8-1의 방어선은 "DB를 쓰는 앱"에서만 통한다.
        // 이 가드는 DB를 안 쓰는 앱에도 같은 fail-fast를 적용하기 위한 것이다.
        List<String> active = List.of(env.getActiveProfiles());
        if (active.stream().noneMatch(ALLOWED::contains)) {
            throw new IllegalStateException(
                    "환경 프로파일이 지정되지 않았습니다. 활성 프로파일=" + active);
        }
    }
}

9. 시크릿은 프로파일 파일에도 넣지 않는다 — 그리고 빼도 남는 것

9-1. 왜 application-prod.yml에도 평문 비밀번호를 두면 안 되나

이유 ① 저장소 권한 = 운영 DB 권한

yml은 git에 커밋되므로 저장소 접근 권한이 곧 운영 DB 접근 권한이 된다. 신입이 온보딩하려고 클론하는 순간 운영 DB 비밀번호를 받아 가는 구조다.

이유 ② 히스토리는 지워지지 않는다

한 번 들어간 비밀번호는 파일을 지워도 남는다. git rm 후 커밋해도 과거 커밋에는 그대로 있고, 이미 클론한 사람들의 로컬에도 남는다 — 사실상 회수가 불가능하다.

관례는 자리표시자 + 외부 주입이다.

# application-prod.yml — 구조만 정의, 실제 값은 바깥에서
spring:
  datasource:
    password: ${DB_PASSWORD}   # 환경변수, k8s Secret, Vault 등에서 주입
이 문법은 새 기능이 아니다 ${DB_PASSWORD}는 4-2의 우선순위 표에서 4층(OS 환경변수)에 있는 값을 끌어다 쓰는 것이다. 즉 이미 있는 우선순위 체계를 명시적으로 참조하는 것뿐이며, 시크릿 전용 기능이 따로 있는 게 아니다.
주입 수단은 환경 성숙도에 따라 단계가 있다 — 얻는 것과 남는 한계를 짝으로 말하면 균형 잡힌 답이 된다
단계수단얻는 것남는 한계
1OS 환경변수저장소에서 시크릿 제거배포 스크립트·프로세스 환경에 평문으로 남음
2Kubernetes Secret배포 매니페스트와 분리, RBAC 적용기본값이 base64 인코딩일 뿐 암호화가 아님
3Vault / AWS Secrets Manager암호화 저장, 감사 로그, 자동 로테이션별도 인프라와 장애점이 늘어남
4Spring Cloud Config + 시크릿 저장소설정과 시크릿을 서비스 전체에 중앙 관리설정 서버가 죽으면 전 서비스 기동 실패

3단계의 값어치는 "암호화"가 아니다 — 여기서 한 칸 올라간다

Vault급 도구의 진짜 이점 = 감사 로그 + 자동 로테이션

누가 언제 이 비밀번호를 읽어 갔는지 기록이 남고, 주기적으로 자동 교체되므로 유출됐더라도 유효 기간이 짧다. 환경변수는 이 둘을 제공하지 못한다 — "환경변수도 결국 평문 아니냐"에 대한 답이 여기 있다.

9-2. 시크릿을 빼도 남는 것 — 토폴로지 노출 시니어 변별

토폴로지는 원래 "도형·배치의 구조"를 뜻하는 말인데, 인프라 문맥에서는 구성원들이 어떻게 배치되고 서로 연결되어 있는지의 지도를 가리킨다. 서버·서비스가 몇 개이고 이름이 무엇인지, 어떤 호스트·포트로 접속하는지, 누가 누구를 호출하는지, DB가 마스터·레플리카로 나뉘어 있는지 — 한마디로 비밀번호가 아니라 "우리 시스템의 지도"다.

앞 절의 자리표시자 처리로 비밀번호는 저장소에서 사라진다. 하지만 주소와 구성 형태는 yml에 그대로 남아 git에 커밋된다.

before 시크릿은 빠졌지만 내부 주소·구조가 그대로
spring:
  datasource:
    url: jdbc:postgresql://prod-db-master.internal.corp:5432/iam
  rabbitmq:
    addresses: rabbit-1.internal.corp:5672,rabbit-2.internal.corp:5672
after 주소도 자리표시자 — 실제 값은 ConfigMap/Config Server
spring:
  datasource:
    url: ${DB_URL}"무엇이 필요한가"만 남는다
  rabbitmq:
    addresses: ${RABBIT_ADDRESSES}"어디에 있는가"는 배포 환경이 안다
단, "그래서 항상 외부화하라"는 결론이 아니다 — 여기서 균형을 잡아야 한다 외부화는 "설정 저장소가 죽으면 전 서비스가 기동 실패"라는 새 단일 장애점을 만든다. 서비스 몇 개 규모에서는 프로파일 yml + 시크릿만 외부화가 오히려 단순하고 안전하다. 토폴로지 노출은 규모가 커질 때 외부화 쪽으로 저울을 기울게 만드는 무게 하나로 이해하는 편이 정확하다.

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

프로파일이 하는 일 두 가지는?
① 설정 파일 선택(application-{p}.yml을 덮어쓰기) ② 빈 선택(@Profile). 검증·강제·경고는 안 한다.
왜 코드 분기·빌드 치환이 아닌가?
코드 분기 = 운영 분기가 운영 전까지 실행되지 않음. 빌드 치환 = 검증한 jar와 배포한 jar가 다른 파일.
프로파일 미지정으로 뜨면?
default 프로파일. 에러도 경고도 없이 기본 application.yml만 읽는다.
안전을 만드는 것은 무엇인가?
프로파일이 아니라 "필수 설정을 공통 yml에서 비워 두는 설계 결정". 프로파일은 채우는 수단일 뿐.
설정 우선순위 실전 네 층은?
커·시·환·파 — 커맨드라인 > 시스템 프로퍼티(-D) > 환경변수 > yml. 바깥·늦은 것이 이긴다.
yml 파일들 사이의 순서는?

부트 2.4에서 바뀐 키는?

배치 기준 한 줄은?

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

운영 장비에 배포하는데 담당자가 프로파일 지정을 깜빡했다. 부트는 어떤 설정으로 뜨나? 이 사고를 구조적으로 막으려면? 필수힌트: "무엇으로 뜨는가" → "그래서 무엇이 위험한가" → "인과를 어디에 두는가" 세 박자

프로파일 미지정 시 default 프로파일로 뜨고, 기본 application.yml만 적용된다. 기본 yml에 로컬 DB 접속 정보가 들어 있는 구성이라면 운영 장비가 에러 없이 기동해 로컬·개발 설정의 DB에 붙는 조용한 오연결 사고가 난다. 가장 나쁜 지점은 정상 기동한다는 것 — 헬스체크도 통과하고 모니터링도 초록불이라 발견 수단이 사람의 신고밖에 없다.

구조적 방어는 기본 yml에서 환경 의존 설정을 전부 제거하는 것이다. DB 접속 정보가 프로파일 yml에만 있으면 프로파일 누락 시 DataSource 구성이 실패해 기동 자체가 죽는다. 실수가 데이터 사고가 아니라 즉시 눈에 보이는 기동 실패로 드러나는 fail-fast 구조다.

여기서 인과를 정확히 말하면 한 단계 더 올라간다. 프로파일을 썼기 때문에 안전한 것이 아니라, 필수 설정을 공통 자리에 두지 않기로 한 설계 결정 때문에 안전한 것이다. 프로파일은 비워 둔 자리를 채우는 수단이고, 방어선은 "비워 둔다"는 결정 쪽에 있다.

기본 yml에서 무엇을 빼고 어디로 옮기면 원천 차단되나? 필수힌트: 기준은 딱 하나. 그리고 "왜 하필 DataSource가 중요한가"까지

기준은 딱 하나, "환경마다 값이 달라지는가"다.

성격예둘 자리
환경 의존DB URL·계정, 외부 API 엔드포인트와 키, 브로커 주소, 로그 레벨application-{profile}.yml
환경 무관애플리케이션 이름, JPA 정책(open-in-view), 직렬화 포맷, 잭슨 설정기본 application.yml

특히 DataSource처럼 "없으면 기동이 실패하는" 필수 설정을 프로파일 쪽에 두는 것이 핵심이다. 그것이 프로파일 누락을 기동 실패로 바꿔 주는 트리거이기 때문이다.

반대로 말하면 DB를 안 쓰는 서비스에는 이 트리거가 없으므로, 8-2의 ProfileGuard처럼 활성 프로파일을 직접 검사해 예외를 던지는 명시적 검증을 따로 둬야 한다.

프로파일을 2개 이상 동시에 활성화하면? 충돌하는 키는 누가 이기나? 함정힌트: 승자 규칙을 말한 뒤, 그 규칙이 왜 사고 원인이 되는지까지

--spring.profiles.active=prod,monitoring처럼 쉼표로 여러 개를 켤 수 있고, 각 프로파일의 yml이 모두 적용된다. 같은 키가 겹치면 나중에 처리된(목록에서 뒤에 선언된) 프로파일 값이 이긴다.

이 "순서 의존 오버라이드"는 암묵적이라 사고 원인이 되기 쉽다. prod,monitoring과 monitoring,prod가 다른 결과를 내는데, 배포 스크립트에서 순서가 바뀌는 것을 아무도 리뷰하지 않는다.

실무 대응은 둘이다. ① 여러 프로파일이 같은 키를 정의하지 않도록 역할을 나눈다 — 환경 프로파일 1개 + 기능 스위치 프로파일들. ② 조합이 필요하면 spring.profiles.group으로 묶어 이름 하나로 켠다. 그러면 순서가 설정 파일 안에 고정되고 배포 스크립트에서 실수할 여지가 사라진다.

부트 2.4에서 spring.profiles가 spring.config.activate.on-profile로 바뀐 배경은? 가산점힌트: "키 하나가 두 역할을 겸했다"에서 출발한다. 마지막에 "옛 키를 쓰면 어떻게 되는가"를 정확히

2.4 이전의 spring.profiles 키는 역할이 두 개 섞여 있었다. 멀티 도큐먼트에서 "이 블록은 어느 프로파일용인가"라는 조건 지정과, spring.profiles.active/include의 프로파일 활성화가 같은 접두어를 공유했다.

특히 프로파일 문서 안에서 또 다른 프로파일을 활성화하는 것이 가능해, 설정 적용 순서가 직관과 어긋나는 케이스가 생겼다. "A 프로파일 블록이 B를 켜고, B 블록이 다시 C를 켜는" 식의 연쇄가 성립하면 최종 설정이 무엇인지 읽어서 알기 어렵다.

2.4의 설정 처리 개편에서 "이 문서가 언제 적용되는가"라는 조건은 spring.config.activate.on-profile로 분리하고, 프로파일 문서 내부에서 spring.profiles.active로 추가 활성화하는 것은 금지(예외 발생)했다. 대신 프로파일 조합 요구는 spring.profiles.group이라는 명시적 수단으로 흡수했다. 요컨대 "조건"과 "활성화"의 책임 분리다.

정확히 알아 둘 것 하나 — 2.4 이상에서 옛 키를 그대로 쓰면 조용히 무시되는 게 아니라 InvalidConfigDataPropertyException으로 기동이 실패한다. 부트가 굳이 예외로 처리한 이유는, 프로파일 조건이 조용히 무시되면 결국 "모든 블록이 적용되는" 상태가 되어 이 문서 전체가 경계하는 오연결 사고로 이어지기 때문이다.

시크릿을 전부 환경변수로 뺐는데도 yml을 저장소에 두는 게 문제라는 건 무슨 뜻인가? 시니어 변별힌트: 남는 것의 이름을 대고, 마지막에 "비대칭"으로 마무리

남는 것이 토폴로지, 즉 내부 주소와 구성 형태이기 때문이다. 비밀번호는 사라져도 prod-db-master.internal.corp, Redis 클러스터 노드의 사설 IP 대역, RabbitMQ·Kafka 브로커 대수, 인증·결제 서비스의 내부 URL과 API 버전은 yml에 그대로 남는다.

이것만으로 공격자는 정찰(reconnaissance)을 끝낼 수 있고, 내부망에 발 하나를 들여놓은 뒤의 횡적 이동(lateral movement)이 크게 빨라진다. 저장소는 퇴사자의 로컬 clone, public 전환 실수, 협력사 공유, git 히스토리로 유출 경로가 넓다.

핵심은 비대칭이다. 시크릿은 교체(rotate)하면 되지만 내부 호스트명과 네트워크 대역은 바꾸는 비용이 훨씬 크다 — DNS 레코드, 방화벽 규칙, 다른 서비스의 설정이 전부 얽혀 있기 때문이다. 해소하려면 주소까지 자리표시자로 두고 실제 값은 k8s ConfigMap이나 설정 서버에서 주입한다 — 다만 그건 새 단일 장애점을 만드는 트레이드오프다.

환경이 늘어날 때 프로파일 yml 방식의 한계는? 설정을 아예 코드 저장소 밖으로 빼는 선택은 언제 하나? 시니어 변별힌트: 한계 셋 → 그래서 외부화 → 그런데 외부화의 대가 → 원칙은 동일

(1) 설정 변경 = 재빌드·재배포. yml이 jar 안에 들어가므로 운영 설정 하나 바꾸려 해도 배포 파이프라인을 한 바퀴 돌려야 한다. 장애 중에 커넥션 풀 크기를 올리고 싶어도 빌드부터 기다려야 한다는 뜻이다.

(2) 저장소 노출. 운영 인프라의 내부 주소와 구조가 코드 저장소에 드러난다. 시크릿을 외부화해도 토폴로지는 남는다.

(3) 다건 서비스 일관성. 마이크로서비스가 늘면 공통 설정 변경을 서비스 수만큼 반복해야 한다. 로그 포맷 하나 바꾸는 데 서른 개 저장소에 PR을 올리는 상황이 된다.

그래서 규모가 커지면 Spring Cloud Config, k8s ConfigMap/Secret, 외부 설정 저장소로 설정을 코드 밖으로 뺀다.

다만 여기서 균형을 잡는 것이 변별 포인트다. 외부화는 "설정 저장소 장애가 전 서비스 기동 실패로 번지는" 새 결합을 만든다. 서비스 몇 개 수준에서는 프로파일 yml + 시크릿만 외부화가 오히려 단순하고 안전하다. 규모에 따른 트레이드오프 판단이라는 점을 말하면 좋다. 그리고 어느 쪽을 택하든 "기본 상태가 안전한가(fail-fast)"라는 원칙은 동일하게 적용된다 — 설정 서버를 쓰더라도 "설정을 못 받으면 이전 값으로 그냥 뜬다"가 아니라 "못 받으면 뜨지 않는다"가 기본이어야 한다.

공통 yml을 비우는 대신, 로컬 기본값을 application-default.yml에 넣으면 되지 않나요? 함정힌트: 방어선은 "파일 이름"에 있지 않다. 무엇에 있었는지 되돌아본다

결과가 같아진다. 부트는 활성 프로파일이 하나도 없을 때 default라는 이름의 프로파일이 활성인 것으로 취급하므로, 그 이름의 설정도 함께 적용된다. 즉 프로파일을 깜빡한 운영 장비가 그 값으로 정상 기동한다 — 7절 안티패턴과 정확히 같은 결말이고, 파일 이름만 바뀐 것이다.

이 질문이 함정인 이유는 "프로파일 파일로 옮겼으니 안전하다"는 착각을 건드리기 때문이다. 8절의 인과를 다시 붙이면 답이 자동으로 나온다 — 방어선은 "값이 어느 파일에 있느냐"가 아니라 "프로파일 미지정 상태에서 그 값이 채워지느냐"에 있다.

판단 기준을 한 문장으로: "아무 프로파일도 주지 않고 띄웠을 때 앱이 뜨면, 방어선이 없는 것이다." 로컬 편의가 목적이라면 파일이 아니라 IDE Run Configuration이나 실행 스크립트에 local을 박아 두는 것이 옳은 자리다 — 그건 내 PC에만 존재하고 운영 장비로 따라가지 않기 때문이다.

"로컬에서 매번 프로파일 주는 게 번거롭다"는 팀원을 어떻게 설득하나요?힌트: 반박이 아니라 "거래"를 보여준다 — 얻는 것과 지불하는 것

먼저 불편이 진짜라는 것을 인정하고, 그 불편이 어디로 옮겨갈 수 있는지를 보여주는 편이 설득력 있다.

① 거래를 명시한다. "공통 yml에 로컬 DB를 두자"는 제안은 개발자 각자의 5초짜리 편의를 얻고 운영 오연결 방어선 전체를 지불하는 거래다. 지불하는 쪽의 최악값이 "며칠간 엉뚱한 DB에 쓰인 운영 데이터"라는 점을 숫자로 말한다.

② 대체 수단이 있어 잃는 것이 없음을 보인다. IDE의 Run Configuration에 local을 박아두면 실행 버튼 한 번으로 끝이고, 실행 스크립트나 bootRun 설정에 넣어 두면 팀 전체가 한 번만 세팅하면 된다. 중요한 것은 그 설정이 내 PC에만 있고 운영 장비로 따라가지 않는다는 점이다.

③ 실패 비용을 비교한다. 프로파일을 깜빡했을 때 로컬에서는 기동 실패 로그를 보고 3초 만에 고친다. 같은 실수가 운영에서 나면 데이터 복구가 필요하다. 같은 방어선이 로컬에서는 싸게, 운영에서는 비싸게 작동하는 것뿐이다.

테스트에서 @ActiveProfiles("test")가 yml의 spring.profiles.active: local을 이기는 이유는? 가산점힌트: 같은 층에서 겨루는 것이 아니다 — 어느 경로로 들어가는지가 다르다

둘이 같은 방식으로 겨루는 게 아니기 때문이다. spring.profiles.active: local은 프로퍼티로 바인딩되는 값(4-2 우선순위 표의 5층)인 반면, @ActiveProfiles는 테스트 컨텍스트의 Environment에 활성 프로파일을 직접 심는다. 부트는 이렇게 프로그래밍 방식으로 지정된 프로파일을 프로퍼티로 바인딩된 값보다 우선한다.

실무적으로 중요한 함의는 "테스트는 로컬 설정에 오염되지 않는다"는 것이다. 개발자마다 application.yml의 기본 프로파일을 다르게 만져 놓아도 테스트는 항상 test 프로파일로 뜨므로 CI와 로컬의 결과가 갈리지 않는다. 반대로 @ActiveProfiles를 안 붙인 테스트는 사람마다 다른 프로파일로 도는 위험이 있다.

spring.profiles.include와 spring.profiles.group은 어떻게 다른가요? 가산점힌트: "항상 붙는가" vs "그 프로파일이 켜졌을 때만 붙는가"

include는 무조건 덧붙이기다 — 어떤 프로파일이 활성이든 상관없이 지정한 프로파일을 활성 목록에 항상 추가한다. 그래서 "모든 환경에서 공통으로 켜져야 하는 프로파일"에 어울린다.

group은 조건부 묶음이다 — 특정 프로파일이 활성화될 때만 딸린 프로파일들이 함께 켜진다. group.prod: "prod-db, prod-mq, monitoring"이면 prod가 켜질 때만 세 개가 따라 켜지고, local로 띄우면 아무것도 따라오지 않는다.

그래서 "환경별 구성 조합"에는 거의 항상 group이 맞다. 6절에서 본 목적 — 배포 스크립트에서 여러 개를 정확히 나열해야 하는 휴먼 에러 지점을 없애는 것 — 을 만족시키는 쪽도 group이다. 참고로 2.4 이상에서는 프로파일 문서(on-profile이 걸린 블록) 안에서 프로파일을 추가 활성화하는 것 자체가 금지되므로, "prod 블록 안에서 include로 더 켜기" 같은 옛 패턴은 group으로 옮겨야 한다.

jar 밖에 application-prod.yml을 두면 jar 안을 덮는다는데, 실무에서 어떻게 쓰고 어떤 사고가 나나요? 함정힌트: 같은 성질이 탈출구도 되고 사고도 된다 — 차이를 만드는 건 형상 관리

탈출구로서: 부트는 클래스패스뿐 아니라 실행 디렉토리(./, ./config/)에서도 같은 이름의 파일을 찾고, 그쪽이 더 강하다. 그래서 장애 중에 재빌드 없이 커넥션 풀 크기나 타임아웃만 급히 올릴 수 있다. 빌드 파이프라인을 한 바퀴 도는 시간을 아끼는 유일한 현실적 수단일 때가 있다.

사고로서: 그 파일은 저장소에 없다. 누군가 임시로 얹어 두고 잊으면 "저장소의 yml을 아무리 읽어도 실제 값이 안 나오는" 서버가 생긴다. 스케일 아웃으로 새 인스턴스가 뜨면 그 서버만 설정이 다르고, 원인을 찾는 데 몇 시간이 든다.

그래서 답은 "쓰지 마라"가 아니라 "쓰되 흔적을 남겨라"다 — 배포 스크립트나 IaC(ConfigMap 등)에 포함시켜 형상 관리 대상으로 잡고, 손으로 얹은 파일은 반드시 회수 시한을 정한다. 판단 기준 한 줄: "이 값을 어디서 왔는지 나중에 누가 추적할 수 있는가."

@Profile("prod")·@Profile("local")만 있는데 stg로 띄우니 기동이 실패한다. 버그인가요? 함정힌트: 실패의 종류를 구분한다 — 잘못된 실패인가, 의도된 실패인가

버그가 아니라 의도된 fail-fast다. stg에는 어느 @Profile도 걸리지 않으므로 PaymentGateway 구현이 하나도 등록되지 않고, 주입받는 쪽에서 NoSuchBeanDefinitionException이 나며 기동이 멈춘다.

여기서 대안을 비교해 보면 왜 이게 나은지가 분명해진다 — 만약 스프링이 "구현이 없으면 null을 넣고 그냥 뜬다"였다면, 스테이징에서 결제 호출이 조용히 아무 일도 안 하다가 그 사실을 테스터가 "결제가 됐는데 돈이 안 빠졌다"고 신고할 때 알게 된다. 기동 실패가 훨씬 싼 실패다.

고치는 방법은 셋 중 하나다. ① stg도 실물을 쓸 것이면 @Profile({"stg","prod"})로 명시적으로 포함시킨다. ② 목을 쓸 것이면 @Profile("!prod")처럼 부정 조건으로 뒤집는다. ③ 기본 구현을 두고 특정 환경만 덮어쓰는 구성(@ConditionalOnMissingBean 계열)을 쓴다. 어느 쪽이든 "어느 환경에서 무엇이 뜨는지"를 명시적으로 적어 두는 것이 핵심이다.

한 줄 요약
프로파일은 하나의 빌드를 환경별 설정으로 갈아 끼우는 스위치이고, 공통은 application.yml·환경 의존 설정은 application-{profile}.yml로 나누되 — 안전을 실제로 만드는 것은 프로파일 자체가 아니라 "기동에 필수인 DataSource URL을 공통 yml에서 비워 두는 설계 결정"이며, 그 결정 덕분에 프로파일 누락이라는 흔한 휴먼 에러가 "운영이 로컬 DB에 붙는 조용한 사고"가 아니라 "(no profiles are currently active)라고 찍히는 배포 즉시의 기동 실패"로 격하되는, 안전한 기본값 설계가 완성된다.
