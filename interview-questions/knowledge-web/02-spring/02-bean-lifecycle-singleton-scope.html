Bean 생명주기와 싱글턴 스코프
컨테이너의 기본 계약, 그리고 싱글턴에 상태를 두면 안 되는 이유

면접 질문: "Bean의 생명주기와 기본 스코프(singleton)를 설명해주세요. 싱글턴 빈에 상태를 두면 왜 위험한가요?"

핵심 관전 포인트 — 스프링 빈의 기본 스코프는 싱글턴이다. 컨테이너당 인스턴스를 하나만 만들어 모든 요청 스레드가 그 하나를 공유한다. 생명주기는 인스턴스화 → 의존성 주입 → 초기화 전 후처리 → 초기화 콜백(@PostConstruct) → 초기화 후 후처리(여기서 AOP 프록시가 씌워진다) → 사용 → 소멸 콜백(@PreDestroy) 순서로 흐른다. 이 계약에서 곧바로 따라 나오는 결론이 있다 — 싱글턴 빈의 인스턴스 필드는 사실상 전역 변수이므로, 거기에 요청별 상태를 담으면 여러 스레드가 같은 칸을 덮어쓰며 사용자 간 데이터가 섞인다. 단일 사용자 테스트는 전부 통과하고 동시 접속에서만 터지는, 테스트로 못 잡는 버그의 전형이다. 그래서 싱글턴 빈이 필드로 가질 수 있는 것은 주입받은 불변 의존성과 설정값뿐이고, 요청마다 달라지는 데이터는 지역 변수와 메서드 파라미터로만 다룬다.
  • 1
    생명주기는 컨테이너가 지키는 순서 계약이다 — 인스턴스화 → 주입 → 초기화 전 후처리 → @PostConstruct → 초기화 후 후처리 → 사용 → @PreDestroy. 이 중 초기화 후 후처리(6단계)에서 AOP 프록시가 씌워지고, 그래서 @PostConstruct(5단계) 안에서는 @Transactional이 아직 작동하지 않는다.
  • 2
    기본 스코프가 싱글턴이라는 말은 "인스턴스는 하나, 스레드는 여럿"이라는 뜻이다 — 톰캣은 요청마다 스레드를 붙이고 그 풀은 기본 200개다. 즉 최대 200개 스레드가 같은 인스턴스 하나의 필드를 동시에 밟는다. 싱글턴 빈의 인스턴스 필드는 모든 동시 요청이 공유하는 전역 변수다.
  • 3
    그래서 원칙은 무상태(stateless)다 — 필드에는 불변 의존성과 설정값만 두고, 요청별 데이터는 스레드 전용 공간인 스택(지역 변수·파라미터)으로만 흘린다. 이 계약을 어긴 코드는 단위·통합·QA 테스트를 전부 통과한 뒤 운영의 동시 접속에서만 데이터가 섞이므로, 코드 리뷰 말고는 잡을 수단이 없다.

0. 질문 + 출제 의도

질문: "Bean의 생명주기와 기본 스코프(singleton)를 설명해주세요. 싱글턴 빈에 상태를 두면 왜 위험한가요?"

출제 의도: 싱글턴 빈의 인스턴스 필드에 요청별 상태를 둔 코드는 단일 사용자 테스트를 전부 통과하고 동시 접속에서만 데이터가 섞인다. 프레임워크의 기본 계약(빈 하나를 모든 스레드가 공유한다)을 아는지가 이런 "테스트로 못 잡는 버그"의 예방선이다.

이 페이지가 겨냥하는 약점 세 가지 ① 생명주기를 순서만 외운 것 → 1·3절에서 6단계(프록시 생성)와 5단계(@PostConstruct)의 전후 관계를 실무 사고(@Transactional이 안 먹는 상황)와 묶는다.
② "싱글턴이니까 빠르다" 정도로 끝내는 것 → 6절에서 왜 싱글턴이 기본값인지를 비용·기동 시점 검증·프록시 3가지 근거로 세우고, GoF 패턴과의 차이까지 붙인다.
③ "상태를 두면 위험하다"를 결론만 아는 것 → 8절에서 두 스레드가 같은 필드를 밟는 타임라인을 시각으로 재현해, "왜 테스트로 못 잡는가"까지 설명할 수 있게 만든다.
이 문서의 기준 버전 서술은 Spring Boot 3.x / Spring Framework 6.x 기준이다. 애너테이션 패키지가 javax.annotation에서 jakarta.annotation으로 바뀐 것이 Boot 2.x와의 대표적 차이다 — @PostConstruct·@PreDestroy의 import 경로가 달라진다.
한 문장 비유 — 은행 창구의 직원 한 명 싱글턴 빈은 창구 직원이고 요청은 손님이다. 직원은 한 명인데 손님은 계속 바뀐다. 직원이 업무 절차(로직)만 기억하고 있으면 아무 문제가 없다. 그런데 "방금 손님의 계좌번호"를 자기 수첩(인스턴스 필드)에 적어두고 다음 손님 응대에 그대로 쓰면 사고가 난다. 8절 전체가 이 비유의 각주다.

1. Bean 생명주기 — 컨테이너가 대신 해주는 일의 순서

IoC의 요지가 "객체의 생성·소멸 주도권을 컨테이너에 넘긴다"였다면, 생명주기는 컨테이너가 그 일을 정확히 어떤 순서로 해주는지에 대한 계약이다. 순서를 아는 것이 왜 실무 문제인지는 3절에서 드러난다 — @Transactional이 안 먹는 대표적 상황이 이 순서에서 나오기 때문이다.

암기 장치 — 7단계는 "정·인·주 / 전·초·후 / 소"

정의 → 인스턴스화 → 주입  |  전처리 → 초기화 콜백 → 후처리  |  소멸

세 덩어리로 끊어 외운다 — 만들고(정·인·주) · 손보고(전·초·후) · 치운다(소). 그리고 숫자 두 개만 붙여 기억하면 실무 문제가 전부 풀린다: @PostConstruct는 5, 프록시는 6. 5 < 6이라는 부등호 하나가 3절의 답이다.

단계별로 "컨테이너가 무엇을 하는가"와 "그래서 내 코드에 무엇이 강제되는가"를 짝지어 본다.
단계이름컨테이너가 하는 일이 단계가 만드는 실무 결과
1빈 정의 읽기컴포넌트 스캔, @Configuration 파싱아직 설계도만 있고 객체는 없다. BeanFactoryPostProcessor가 이 설계도를 손본다(${...} 치환).
2인스턴스화생성자를 호출해 실제 객체를 만든다생성자 주입은 이 시점에 의존성이 함께 들어온다. 필드·세터 주입이면 아직 비어 있다.
3의존성 주입필드 주입·세터 주입의 값을 채운다2와 3 사이 = 필드가 null인 구간. 생성자에서 주입 빈을 쓰면 NPE.
4초기화 전 후처리BeanPostProcessor.postProcessBeforeInitialization@PostConstruct를 실제로 찾아서 호출하는 주체가 여기 있는 후처리기다.
5초기화 콜백@PostConstruct → afterPropertiesSet() → @Bean(initMethod)주입 완료가 보장된 첫 지점. 주입받은 빈을 쓰는 초기화는 여기에 둔다.
6초기화 후 후처리BeanPostProcessor.postProcessAfterInitialization
★ AOP 프록시가 여기서 씌워진다		@Transactional·@Async·@Cacheable은 이 단계부터 작동한다. 5단계에서는 아직 없다.
7소멸 콜백@PreDestroy → destroy() → @Bean(destroyMethod)자원 반납 자리. 프로토타입 스코프 빈에는 불리지 않는다(7절).

정확히 하자면 4번과 5번은 완전히 별개의 단계가 아니다. @PostConstruct를 실제로 호출하는 주체가 InitDestroyAnnotationBeanPostProcessor라는 후처리기이고, 그것이 4단계(초기화 전 후처리) 안에서 애너테이션 붙은 메서드를 찾아 불러준다. 즉 스프링의 초기화 콜백 자체가 후처리기 메커니즘 위에 올라가 있다. 이 사실이 바로 다음 절과 이어진다.

2. BeanPostProcessor가 무엇인가 — 바꿔치기가 가능한 확장 지점

도식에 갑자기 등장한 이 이름부터 정의하고 간다.

BeanPostProcessor = 빈이 만들어진 뒤 초기화 전후에 끼어들어, 그 빈을 손보거나 아예 다른 객체로 바꿔치기할 수 있는 확장 지점

메서드가 두 개뿐인 인터페이스이고, 컨테이너는 모든 빈 하나하나에 대해 등록된 모든 후처리기의 두 메서드를 불러준다.

인터페이스 이름은 길지만 실체는 메서드 두 개다
public interface BeanPostProcessor {
    // 5단계(초기화 콜백) 직전에 불린다
    Object postProcessBeforeInitialization(Object bean, String beanName);

    // 5단계(초기화 콜백) 직후에 불린다
    Object postProcessAfterInitialization(Object bean, String beanName);
}
//  ↑ 결정적인 것은 반환 타입이 void 가 아니라 Object 라는 점이다.
//    후처리기는 받은 빈을 그대로 돌려줄 수도 있지만, 전혀 다른 객체를 돌려줄 수도 있고
//    컨테이너는 그 반환값을 최종 빈으로 채택한다.
비유 — 서류를 바꿔서 돌려주는 창구 창구에 제출한 서류를 담당자가 검토만 하고 그대로 돌려주는 구조가 아니다. 다른 서류로 바꿔서 돌려줄 수 있는 구조다. 그리고 다음 사람은 바뀐 서류만 보게 된다 — 원본이 어디 갔는지 알 방법도 없다. 이 "바꿔치기 가능"이 AOP의 작동 원리 전부다.

여기서 얻는 한 줄 — AOP는 마법이 아니라 "반환값 바꿔치기"다

스프링 AOP의 후처리기(AbstractAutoProxyCreator)는 postProcessAfterInitialization에서 원본 빈을 감싼 프록시를 만들어 원본 대신 반환한다. 그래서 6단계가 "AOP 프록시가 씌워지는 지점"이 된다. @Transactional·@Async·@Cacheable이 전부 이 한 지점에 얹혀 있다.

3. 6단계가 왜 중요한가 — @PostConstruct 안에서는 @Transactional이 안 먹는다 가산점

이제 순서가 실무 사고로 이어지는 지점을 본다. 먼저 프록시가 무엇인지부터 세운다.

프록시 = 원본 객체인 척하면서 호출을 먼저 받아 부가 작업을 한 뒤 원본에 넘기는 대리인 객체

@Transactional이 붙은 서비스에 대해 컨테이너는 원본을 감싼 프록시를 만들고, 다른 빈에게 원본이 아니라 프록시를 주입한다. 그래서 "트랜잭션이 걸린다"는 말은 정확히는 "프록시를 거쳐 호출됐다"는 뜻이다. 여기서 두 가지가 동시에 어긋나면 트랜잭션이 사라진다.

before 기동 중 워밍업 — 자연스러워 보이지만 트랜잭션이 걸리지 않는다
@Service
public class ReportService {

    private final ReportRepository repository;

    public ReportService(ReportRepository repository) {
        this.repository = repository;
    }

    @PostConstruct
    void warmUp() {
        // 문제 ① 이 시점은 5단계다. 프록시는 6단계에서야 만들어지므로 아직 없다.
        // 문제 ② this 로 부르는 순간 프록시를 거치지 않는다 — 있었더라도 못 가로챈다.
        loadAll();   // == this.loadAll() → 트랜잭션 없이 실행된다
        // 결과: 영속성 컨텍스트가 없으니 지연 로딩 접근에서 LazyInitializationException 이 나거나,
        //       쿼리마다 커넥션을 따로 잡았다 놓는 형태가 된다.
    }

    @Transactional
    public void loadAll() { /* ... */ }
}
고침 1 기동이 "완료된 뒤"로 미룬다 — ApplicationReadyEvent
// ApplicationReadyEvent 는 모든 빈이 만들어지고 프록시까지 씌워진 뒤 발행된다.
// 이 시점에는 주입받은 참조가 전부 프록시다.
@Component
public class ReportWarmUpRunner {

    private final ReportService reportService;   // 주입받은 것 = 프록시

    public ReportWarmUpRunner(ReportService reportService) {
        this.reportService = reportService;
    }

    @EventListener(ApplicationReadyEvent.class)
    void warmUp() {
        reportService.loadAll();   // 프록시를 거치므로 트랜잭션이 정상 적용된다
    }
}

// 고침 2: 초기화 로직을 별도 빈으로 분리해 그 빈을 주입받아 호출한다.
// 핵심은 같다 — "자기 자신을 부르지 말고, 주입받은 프록시를 통해 부른다".

면접에서 이렇게 연결하면 "외운 것"이 아니라 "이해한 것"으로 읽힌다

@PostConstruct(5단계) < AOP 프록시 생성(6단계)  +  this는 언제나 원본  =  트랜잭션이 두 겹으로 빠진다

둘 중 하나만 말해도 답은 되지만, 두 이유를 나눠 말하고 "그래서 프록시를 만들어 놓고 미루는 것만이 해법"까지 가면 한 칸 더 간다. 같은 원리가 @Async·@Cacheable에도 그대로 적용된다 — 전부 6단계의 프록시에 얹혀 있기 때문이다.

4. 초기화 로직은 어디에 두는가 — 생성자 vs @PostConstruct vs 기동 완료 후

순서가 알려주는 두 번째 실무 지침이다. 필드 주입이나 세터 주입을 쓰는 클래스는 생성자 실행 시점(2단계)에 의존성이 아직 비어 있다. 주입은 3단계에서 일어나기 때문이다.

before 필드 주입 + 생성자에서 사용
@Service
public class CacheService {

    @Autowired
    private RedisTemplate<String, String> redis;
    // ↑ 3단계에서 채워진다

    public CacheService() {
        redis.opsForValue().set("warm", "1");
        // 2단계 — redis 는 아직 null. NPE.
    }
}
after 주입 완료가 보장된 콜백으로 이동
@Service
public class CacheService {

    @Autowired
    private RedisTemplate<String, String> redis;

    @PostConstruct
    void warmUp() {
        redis.opsForValue().set("warm", "1");
        // 5단계 — 주입이 끝났음이 보장된다
    }
}

다만 생성자 주입을 쓰면 2단계에서 이미 의존성이 손에 들어와 있으므로 이 함정 자체가 사라진다. 그래서 판단은 아래 세 갈래로 정리된다.

5. 소멸 콜백 — 자원을 반납하는 자리, 그리고 graceful shutdown

@PreDestroy는 컨테이너가 그 빈의 관리를 끝내는 시점에 불린다. 커넥션 풀 반납, 직접 만든 스레드 풀의 shutdown(), 열어둔 파일 핸들 정리 같은 것을 여기에 둔다. 실무에서 함께 짚어야 하는 것이 graceful shutdown이다.

여기서 미리 박아둘 예외 하나 — 프로토타입 빈에는 소멸 콜백이 불리지 않는다

컨테이너는 프로토타입 빈을 만들어 건네준 뒤 그 인스턴스를 추적하지 않는다. 몇 개를 만들었는지, 지금 누가 들고 있는지, 언제 버려지는지를 기록하지 않는다는 뜻이다. 추적하지 않으니 @PreDestroy를 불러줄 대상 목록도 없다. 자세한 실무 함의는 7절에서 다룬다.

6. 스코프 — 기본은 싱글턴, 그런데 왜 싱글턴인가

스코프 = "빈 인스턴스를 몇 개 만들고 언제까지 살려둘 것인가"의 규칙
스코프인스턴스 수특징
singleton컨테이너당 1개기본값. 기동 시 미리 만들어 둔다(eager) — 그래서 의존성 문제가 기동 시점에 드러난다
prototype주입·조회할 때마다 새로소멸 콜백을 컨테이너가 안 불러준다. "사용할 때마다 새로"가 아니다(7절)
requestHTTP 요청당 1개웹 환경 전용. 싱글턴에 주입하려면 스코프 프록시가 필요하다
sessionHTTP 세션당 1개웹 환경 전용

6-1. 기본이 싱글턴인 이유 세 가지

서비스·리포지토리 같은 빈은 로직(코드)만 담고 데이터를 담지 않는 것이 전제다. 그렇다면 요청마다 새로 만들 이유가 없다. 같은 코드를 담은 객체를 초당 수천 개씩 새로 만들고 버리는 것은 순수한 낭비이기 때문이다. 인스턴스를 하나만 두면 세 가지가 따라온다.

① 생성 비용과 GC 부담이 사라진다
초당 1,000 요청 × 요청당 빈 10개라면 프로토타입에서는 초당 10,000개의 객체가 만들어졌다 버려진다. 싱글턴에서는 0개다.
② 문제가 기동 시점에 드러난다
싱글턴은 기동 중에 미리 만들어지므로, 주입할 빈이 없거나 순환 참조가 있으면 애플리케이션이 아예 뜨지 않는다. 배포 후 특정 요청에서 터지는 것보다 훨씬 싼 실패다.
③ 프록시를 한 번만 씌우면 된다
AOP 프록시 생성은 클래스 단위로 바이트코드를 만들어내는 비싼 작업이라 요청마다 반복할 일이 아니다. 6단계가 빈당 한 번만 도는 이유다.

6-2. 스프링의 싱글턴은 GoF 싱글턴 패턴이 아니다 가산점

한 문장 구분 — 무엇이 "하나"를 강제하는가

GoF = 클래스가 스스로 강제한다   |   스프링 = 컨테이너가 하나만 만들어 재사용한다 (클래스는 아무것도 모른다)

7. "상태가 필요하면 프로토타입을 쓰면 되나?" — 가장 자주 빠지는 함정

8절을 읽고 나면 자연스럽게 드는 의문이다. "요청마다 새 인스턴스면 상태를 필드에 둬도 안전한 것 아닌가?" 대부분의 경우 이 답은 함정이고, 이유가 둘이다. 첫째가 결정적이다.

프로토타입은 "주입할 때마다 새로"이지 "사용할 때마다 새로"가 아니다 — 그리고 싱글턴에 대한 주입은 기동 시 한 번뿐이다
before 프로토타입 빈을 싱글턴 빈의 필드로 주입받았다
@Component
@Scope("prototype")
public class OrderContext {          // 요청별 상태를 담으려고 프로토타입으로 만들었다
    private Order order;
    public void setOrder(Order o) { this.order = o; }
    public Order getOrder() { return order; }
}

@Service                              // 이 빈은 싱글턴이다
public class OrderService {

    private final OrderContext context;   // 주입은 "기동 시 딱 한 번" 일어난다

    public OrderService(OrderContext context) {
        this.context = context;           // 여기서 받은 그 인스턴스를 영원히 들고 있는다
    }

    public void process(OrderRequest request) {
        context.setOrder(createOrder(request));   // 모든 스레드가 같은 인스턴스를 덮어쓴다
        pay(context.getOrder());
    }
}

7-1. 정말 "사용 시점마다" 새 인스턴스가 필요하다면

방법 1 ObjectProvider — 가장 흔하고 읽기 쉬운 선택
@Service
public class OrderService {
    private final ObjectProvider<OrderContext> contextProvider;

    public OrderService(ObjectProvider<OrderContext> contextProvider) {
        this.contextProvider = contextProvider;   // 주입되는 것은 "꺼내는 도구"다
    }

    public void process(OrderRequest request) {
        OrderContext context = contextProvider.getObject();   // 호출할 때마다 새 인스턴스
        // 게다가 이 참조는 지역 변수이므로 스레드마다 독립이다 — 섞일 수가 없다
    }
}
@Lookup 메서드 주입
추상 메서드에 @Lookup을 붙이면 스프링이 그 메서드 구현을 대신 만들어 매 호출마다 새 빈을 돌려준다.
스코프 프록시
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS) — 주입되는 것이 프록시이고, 그 프록시가 호출 시점에 실제 빈을 찾아 위임한다.

둘째 이유가 더 근본적이다 — 애초에 필드에 둘 필요가 없다

위 예시의 OrderContext도 그냥 메서드 파라미터로 넘기면 그만이다. 프로토타입은 "상태를 필드에 두고 싶다"는 요구의 해법이 아니다.

프로토타입의 진짜 용도 = 생성 비용이 있고 재사용하면 안 되는 객체(예: 상태를 가진 빌더)를 컨테이너가 만들어 주기를 바라는 드문 요구

7-2. 프로토타입 빈에 소멸 콜백이 안 불리는 이유와 실무 주의점

컨테이너는 프로토타입 빈을 만들어 건네준 뒤 그 인스턴스를 추적하지 않는다. 몇 개를 만들었는지, 지금 누가 들고 있는지, 언제 버려지는지를 기록하지 않으므로 @PreDestroy를 불러줄 대상 목록 자체가 없다.

그래서 자원을 쥔 프로토타입 빈은 새어 나간다 파일 핸들이나 커넥션을 열어두는 객체를 프로토타입으로 만들어 놓고 컨테이너가 닫아줄 것이라 기대하면 자원이 그대로 샌다. 정리 책임은 그것을 받아 쓴 쪽에 있으므로 try-with-resources로 감싸거나 명시적으로 닫는 코드를 직접 넣어야 한다.

8. 싱글턴에 상태를 두면 왜 위험한가 — 요청은 여럿, 빈은 하나

8-1. 전제 — 요청마다 스레드가 붙는다

톰캣 같은 서블릿 컨테이너는 요청 하나에 스레드 하나를 배정해 처리한다. 스레드는 매번 새로 만드는 게 아니라 미리 만들어 둔 풀에서 꺼내 쓰고 돌려준다. Spring Boot의 내장 톰캣은 이 풀 크기가 기본 200(server.tomcat.threads.max)이다.

8-2. before — 요청별 상태를 필드에 담은 코드

before 한 줄씩 읽으면 논리에 아무 잘못이 없어 보인다
@Service
public class OrderService {

    private Order currentOrder;   // 모든 스레드가 공유하는 단 한 칸

    public void process(OrderRequest request) {
        this.currentOrder = createOrder(request);   // ① 자기 주문을 이 칸에 넣는다
        validate();                                 // ② 이 사이에 다른 스레드가 칸을 덮어쓴다
        pay(this.currentOrder);                     // ③ 다시 읽으면 남의 주문이 나온다
    }
}
이 버그의 성질 — 코드에는 아무 단서가 없다 문제는 "이 메서드가 동시에 여러 번 실행된다"는 사실이 코드 어디에도 적혀 있지 않다는 것이다. 컴파일러도 경고하지 않고, 정적 분석도 대부분 잡지 못하며, 한 줄씩 따라 읽으면 완벽하게 논리적이다.

8-3. 두 스레드가 같은 칸을 밟는 타임라인 이 문서의 핵심 그림

사용자 1의 요청(스레드 A)과 사용자 2의 요청(스레드 B)이 거의 동시에 들어왔다고 하자. 힙에 있는 OrderService 인스턴스는 단 하나이고, 그 안의 currentOrder 필드도 단 한 칸이다.

금전 사고
사용자 1은 결제되지 않았는데 성공 화면을 보고, 사용자 2는 두 번 결제된다.
개인정보 사고
응답에 남의 주문 정보(수령인 이름·주소·연락처)가 실려 나간다. "내 주문 내역에 모르는 사람 정보가 보인다"는 유형의 사고가 정확히 이것이다.
재현 불가 장애
t1~t4 사이에 다른 스레드가 끼어들어야만 발생하므로, 같은 코드가 대부분의 요청에서는 멀쩡히 돈다.

8-4. 왜 테스트로 못 잡는가

이 버그가 특별히 위험한 이유는 우리가 가진 모든 검증 수단이 단일 스레드라는 데 있다.

검증 수단실행 형태이 버그를 잡는가
단위 테스트스레드 1개가 순차 실행못 잡음
@SpringBootTest 통합 테스트대개 스레드 1개가 순차 호출못 잡음
QA 수동 테스트사람 한 명이 클릭못 잡음
코드 리뷰사람이 읽음여기서만 잡힌다
운영동시 접속간헐적으로 터짐 — 그때는 이미 사고다

그래서 이 유형은 "발견해서 고치는" 버그가 아니다

t1~t4 사이의 아주 좁은 창에 다른 스레드가 정확히 끼어들어야 재현되므로 부하 테스트를 돌려도 안 나올 수 있다. 그리고 터졌을 때조차 원인 추적이 어렵다 — 로그에는 "사용자 1의 요청이 주문#2를 결제했다"는 결과만 남고 그렇게 된 경위는 어디에도 기록되지 않기 때문이다.

"발견해서 고치는" 버그가 아니라 "구조적으로 발생 불가능하게 만드는" 버그 — 그래서 프레임워크의 기본 계약을 아는 것이 곧 예방선이다

8-5. after — 상태를 스택으로 옮긴다

after 상태를 필드가 아니라 지역 변수·파라미터로 — 무상태(stateless) 설계
@Service
public class OrderService {

    private final PaymentGateway gateway;   // 불변 의존성 — 모두가 읽기만 하므로 공유해도 안전

    public OrderService(PaymentGateway gateway) {
        this.gateway = gateway;
    }

    public void process(OrderRequest request) {
        Order order = createOrder(request);   // 지역 변수 = 스레드마다 자기 스택에 따로 생긴다
        validate(order);                      // 상태는 필드에 두지 말고 파라미터로 흘려보낸다
        gateway.pay(order);                   // 다른 스레드가 이 order 를 볼 방법이 아예 없다
    }
}

이 문서에서 반드시 인출해야 할 한 문장

싱글턴 빈이 가질 수 있는 필드는 불변인 것(주입받은 의존성·설정값)뿐이고,
요청마다 달라지는 데이터는 지역 변수와 메서드 파라미터로만 다룬다

9. 고전 사례 — SimpleDateFormat을 필드로 둔 코드 가산점

직접 상태를 넣지 않았는데도 같은 사고가 나는 경우가 있다. 내부에 상태를 가진 객체를 필드로 뒀을 때다.

before final인데도 안전하지 않다
@Service
public class SettlementService {

    // 매번 new 하기 아까워서 필드로 뺐다
    // — 흔하고 자연스러운 최적화처럼 보인다
    private final SimpleDateFormat format
        = new SimpleDateFormat("yyyy-MM-dd");

    public Date parse(String text) throws ParseException {
        return format.parse(text);
        // 내부 Calendar 를 두 스레드가 함께 밟는다
    }
}
after 불변 포맷터로 교체
@Service
public class SettlementService {

    private final DateTimeFormatter format
        = DateTimeFormatter.ofPattern("yyyy-MM-dd");
    // DateTimeFormatter 는 불변이라 공유해도 안전하다

    public LocalDate parse(String text) {
        return LocalDate.parse(text, format);
        // 파싱 중간 상태를 포맷터에 담지 않는다
    }
}

여기서 얻을 일반 규칙 — 필드로 두기 전에 던질 질문 하나

"이 객체가 내부에 변경되는 상태를 갖는가?"  —  final은 이 질문에 답해주지 않는다
공유하면 위험한 부류
SimpleDateFormat, Calendar, Matcher, 가변 컬렉션 필드(ArrayList·HashMap), 직접 만든 "빌더" 성격의 객체
공유해도 안전한 부류
DateTimeFormatter, Pattern, String, 주입받은 스프링 빈(무상태라는 전제), 설정값(int·String 등 불변)

10. 정말 상태가 필요하면 무엇을 쓰나

먼저 짚을 것 — "스프링은 synchronized 하나 없이 어떻게 안전한가요?" 스프링이 안전하게 만들어주는 것이 아니다. 빈을 무상태로 설계하는 것이 개발자와 프레임워크 사이의 계약이고, 스프링은 그 계약이 지켜졌다는 전제 위에서 인스턴스를 하나만 만들어 공유하는 것이다. 구조로 보면 공유되는 것은 불변 의존성뿐이고 변하는 데이터는 각 스레드의 스택에만 있으므로, 경합할 대상 자체가 존재하지 않는다.

그리고 synchronized는 답이 아니다

만약 상태를 공유해야만 했다면 서비스 메서드에 락을 걸어 해결하는 것이 해법처럼 보이지만, 메서드 전체에 락을 걸면 동시 처리량이 사실상 1로 떨어져 200개 스레드가 줄을 선다. 동기화가 필요 없는 것이 아니라, 동기화가 필요 없는 구조를 강제하는 것이 싱글턴 + 무상태 조합의 설계 의도다.

요구사항의 단위에 따라 도구가 다르고, 각각 대가가 있다. 순서대로 검토하는 것이 실무 판단이다.
순위선택지상태의 단위언제 쓰나대가 · 주의점
1지역 변수·파라미터로 재구성호출 1회첫 번째 답은 언제나 이것이다. 값을 파라미터로 넘기거나, 값들을 묶은 컨텍스트 객체를 만들어 메서드 인자로 흘려보낸다대가 없음. "상태가 꼭 필요하다"고 느껴지는 경우의 대부분은 메서드를 쪼개다가 값 넘기기가 귀찮아진 상황이지 진짜 요구가 아니다
2request 스코프 빈HTTP 요청 1건요청 하나가 여러 계층을 거치며 공유해야 하는 컨텍스트싱글턴이 그냥 주입받으면 기동 시점에 처리 중인 요청이 없어 문제가 된다 → proxyMode = ScopedProxyMode.TARGET_CLASS로 프록시를 주입받아야 한다
3ThreadLocal스레드 1개스프링 시큐리티의 SecurityContextHolder가 이 방식으로 현재 인증 정보를 들고 있다① 톰캣은 스레드를 풀에서 재사용하므로 요청이 끝날 때 remove()를 안 하면 다음 요청에 이전 사용자의 값이 남는다 — 인증 정보에서 이 실수는 곧 계정 도용급 사고다
② @Async나 별도 스레드 풀 경계에서는 전파되지 않는다
4진짜 공유 상태
(AtomicLong, ConcurrentHashMap)		인스턴스(서버) 1대카운터, 로컬 캐시 — 여기서만 동시성 도구를 의도적으로 쓴다서버를 여러 대로 늘리는 순간 인스턴스마다 값이 갈라진다. 서버별 합이 전체 카운트가 아니게 되므로, 정확한 값이 필요하면 Redis 같은 외부 저장소로 빼는 것까지 검토한다
덧붙이면 좋은 최신 맥락 — 가상 스레드 가산점 Spring Boot 3.2부터 spring.threads.virtual.enabled=true로 요청을 가상 스레드에서 처리할 수 있다. 가상 스레드는 요청마다 새로 만들어지고 풀에서 재사용되지 않으므로 ThreadLocal의 "지우는 것을 잊어 다음 요청에 새어 나가는" 위험은 줄어든다. 반면 싱글턴 빈 필드 공유 문제는 조금도 달라지지 않는다 — 스레드가 무엇이든 인스턴스는 여전히 하나이기 때문이다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

생명주기 7단계?
정·인·주 / 전·초·후 / 소 — 정의 · 인스턴스화 · 주입 / 초기화 전 후처리 · 초기화 콜백 · 초기화 후 후처리 / 소멸.
프록시는 몇 단계에서 생기나?
6단계(초기화 후 후처리). @PostConstruct는 5단계. 5 < 6 — 이 부등호가 3절 전체의 답이다.
@PostConstruct에서 @Transactional은?
안 먹는다. 이유가 둘이다 — ① 그 시점(5)엔 프록시가 아직 없고 ② this 호출은 프록시를 거치지 않는다. 해법은 ApplicationReadyEvent로 미루기.
기본 스코프와 인스턴스 수?
싱글턴 · 컨테이너당 1개. "JVM당 1개"라고 말하면 틀린다 — 컨텍스트가 2개면 인스턴스도 2개.
싱글턴에 상태를 두면?
인스턴스 필드 = 모든 동시 요청이 공유하는 전역 변수. 스레드가 서로의 값을 덮어쓰며 사용자 데이터가 섞인다.
왜 테스트로 못 잡나?
검증 수단이 전부 단일 스레드(단위·통합·QA)라서. 코드 리뷰에서만 잡힌다.
프로토타입의 함정?
"주입할 때마다 새로"이지 "사용할 때마다 새로"가 아니다. 싱글턴에 주입되면 기동 시 받은 인스턴스 하나로 고정된다.
사용 시점마다 새로 받으려면?
ObjectProvider · @Lookup · 스코프 프록시 셋 중 하나.
프로토타입에 @PreDestroy는?
안 불린다. 컨테이너가 건네준 뒤 추적하지 않으므로 호출 대상 목록 자체가 없다. 정리는 받아 쓴 쪽의 책임.
final이면 안전한가?
아니다. final은 참조를 고정할 뿐 객체 내부 상태 변경은 막지 못한다 — SimpleDateFormat이 반례.
초기화 로직은 어디에?
주입 빈을 안 쓰면 생성자 / 쓰면 @PostConstruct / 트랜잭션이 필요하면 ApplicationReadyEvent.
상태가 정말 필요하면?
지역 변수 → request 스코프(+프록시) → ThreadLocal(+remove()) → Atomic·Concurrent(서버 늘면 갈라짐) 순으로 검토.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

그럼 스프링은 synchronized 하나 없이 어떻게 안전한가요? 필수힌트: "스프링이 안전하게 해준다"로 시작하면 틀린 답이다. 누가 무엇을 보장하는지부터 나눈다

스프링이 안전하게 만들어주는 것이 아니다. 빈을 무상태로 설계하는 것이 개발자와 프레임워크 사이의 계약이고, 스프링은 그 계약이 지켜졌다는 전제 위에서 인스턴스를 하나만 만들어 공유한다. 계약을 어기면 8절의 사고가 그대로 난다.

구조로 보면 이렇다. 공유되는 것은 불변 의존성뿐이고 변하는 데이터는 각 스레드의 스택에만 있으므로, 경합할 대상 자체가 존재하지 않는다. 동기화 장치가 없는 게 아니라 필요한 상황이 만들어지지 않는 것이다.

한 걸음 더 — 만약 상태를 공유해야만 했다면 synchronized로 해결하는 것은 답이 아니다. 서비스 메서드 전체에 락을 걸면 동시 처리량이 1로 떨어져 200개 스레드가 줄을 선다. 동기화가 필요 없는 것이 아니라, 동기화가 필요 없는 구조를 강제하는 것이 싱글턴 + 무상태 조합의 설계 의도다.

정말 상태가 필요하면 어떤 선택지가 있나요? 시니어 변별힌트: 도구 이름을 나열하지 말고 "상태의 단위"와 "각각의 대가"로 묶어 답한다

① 지역 변수·파라미터로 재구성 — 첫 번째 답은 언제나 이것이다. 실무에서 "상태가 꼭 필요하다"고 느껴지는 경우의 대부분은 메서드를 쪼개다가 값을 넘기기 귀찮아진 상황이지 진짜 요구가 아니다. 값을 파라미터로 넘기거나, 값들을 묶은 컨텍스트 객체를 만들어 인자로 흘려보내면 해결된다.

② request 스코프 빈 — 요청 단위 상태. 요청 하나가 여러 계층을 거치며 공유해야 하는 컨텍스트에 쓴다. 주의점은 싱글턴이 요청 스코프 빈을 그냥 주입받으면 7절과 같은 문제가 생긴다는 것 — 기동 시점에는 처리 중인 HTTP 요청이 없으므로 주입할 대상 자체가 없다. 그래서 proxyMode = ScopedProxyMode.TARGET_CLASS로 프록시를 주입받고, 그 프록시가 호출 시점에 현재 요청에 묶인 실제 빈을 찾아 위임하게 한다.

③ ThreadLocal — 스레드 단위 상태. 스프링 시큐리티의 SecurityContextHolder가 이 방식이다. 대가가 둘이다 — 첫째, 톰캣은 스레드를 풀에서 재사용하므로 요청이 끝날 때 remove()를 안 하면 다음 요청에 이전 사용자의 값이 그대로 남는다. 인증 정보에서 이 실수가 나면 곧바로 계정 도용 수준의 사고다. 둘째, @Async나 별도 스레드 풀로 넘어가는 경계에서는 값이 전파되지 않아 그쪽에서는 비어 있다.

④ 진짜 공유 상태(카운터, 로컬 캐시). 여기서만 동시성 도구를 의도적으로 쓴다 — AtomicLong, ConcurrentHashMap. 다만 서버를 여러 대로 늘리는 순간 인스턴스마다 값이 갈라진다는 한계를 함께 말해야 한다. 정확한 값이 필요하면 Redis 같은 외부 저장소로 빼는 것까지 검토한다.

프로토타입 빈은 왜 소멸 콜백이 안 불리나요? 실무에서 뭘 조심해야 하죠? 함정힌트: "추적하지 않는다"가 핵심어. 그리고 2-3절의 주입 시점 이야기를 얹어야 답이 완성된다

컨테이너는 프로토타입 인스턴스를 만들어 넘겨준 시점에 관리를 끝낸다. 몇 개를 만들었고 누가 들고 있는지 추적하지 않으므로 @PreDestroy를 호출할 대상 목록 자체가 없다.

실무에서 조심할 것은 자원을 쥔 프로토타입 빈이다. 파일 핸들이나 커넥션을 열어두는 객체를 프로토타입으로 만들어 놓고 컨테이너가 닫아줄 것이라 기대하면 자원이 그대로 샌다. 정리 책임은 그것을 받아 쓴 코드에 있으므로 try-with-resources나 명시적 close()를 직접 넣어야 한다.

여기에 7절을 얹으면 답이 완성된다 — 프로토타입은 "주입할 때마다 새로"이지 "사용할 때마다 새로"가 아니므로, 싱글턴에 주입하면 인스턴스가 하나로 고정된다. 사용 시점마다 새로 받으려면 ObjectProvider, @Lookup, 스코프 프록시 중 하나를 써야 한다.

@PostConstruct와 생성자의 차이는 뭐고, 초기화 로직은 어디에 두나요? 필수힌트: 답을 단계 번호로 말한다. 그리고 세 번째 갈래(트랜잭션)를 빠뜨리지 않는다

시점이 다르다. 생성자는 2단계(인스턴스화), @PostConstruct는 5단계(초기화 콜백)에서 실행된다. 그래서 판단 기준이 셋으로 갈린다.

  • 필드/세터 주입을 쓰는 클래스라면 생성자 시점에 의존성이 아직 비어 있으므로(3단계 전), 주입받은 빈을 사용하는 초기화는 반드시 @PostConstruct에 둔다.
  • 생성자 주입을 쓰는 클래스라면 생성자 시점에 이미 의존성이 들어와 있으므로, 값 검증이나 방어적 복사 같은 가벼운 작업은 생성자에서 해도 된다.
  • 트랜잭션이 필요한 초기화라면 둘 다 안 된다. @PostConstruct 시점(5단계)에도 AOP 프록시는 아직 없고(6단계), this로 부르면 프록시를 거치지도 않는다. ApplicationReadyEvent 리스너로 미뤄 기동이 완전히 끝난 뒤 주입받은 프록시를 통해 호출한다.

마지막 항목을 생명주기 단계 번호와 함께 설명할 수 있으면, 순서를 외운 것이 아니라 이해한 것으로 읽힌다.

@PostConstruct, InitializingBean, @Bean(initMethod)이 다 있으면 실행 순서는요?힌트: 표준 애너테이션이 가장 먼저다

초기화는 @PostConstruct → afterPropertiesSet()(InitializingBean) → @Bean(initMethod) 순이고, 소멸은 대칭으로 @PreDestroy → destroy()(DisposableBean) → @Bean(destroyMethod) 순이다.

실무 선택 기준까지 붙이면 좋다 — 내가 만든 클래스면 @PostConstruct(표준 애너테이션이라 스프링에 의존하지 않는다), 인터페이스 구현은 스프링 API에 코드가 묶이므로 권장되지 않고, 수정할 수 없는 외부 라이브러리 클래스는 @Bean(initMethod = "...")로 지정한다.

싱글턴 빈에 @Lazy를 붙이면 무엇이 달라지나요? 함정힌트: 인스턴스 개수는 그대로다. 달라지는 것은 "언제 만드는가"와 "언제 실패하는가"다

인스턴스가 여러 개가 되는 것이 아니다. 여전히 컨테이너당 1개이고, 달라지는 것은 생성 시점뿐이다 — 기동 중이 아니라 처음 사용되는 순간에 만들어진다.

그래서 대가가 명확하다. 6-1절의 두 번째 이점(문제가 기동 시점에 드러난다)을 포기하는 것이다. 주입할 빈이 없거나 초기화가 실패하는 문제가 기동 로그가 아니라 운영 중 첫 호출에서 터진다. 기동 시간이 문제가 되는 특정 무거운 빈에 국소적으로 쓰는 것은 합리적이지만, 기본값으로 깔면 "배포는 성공했는데 트래픽이 오자 죽는" 구조를 만든다.

컨트롤러도 싱글턴인데, @RequestBody로 받은 값은 왜 안전한가요? 필수힌트: 필드인가 파라미터인가만 보면 된다

컨트롤러도 싱글턴이 맞다. 그런데 @RequestBody·@RequestParam·@PathVariable로 받은 값은 메서드 파라미터이고, 파라미터는 호출할 때마다 그 스레드의 스택 프레임에 새로 생긴다. 8-5절의 그림 그대로 다른 스레드가 접근할 수 없는 공간이므로 섞일 여지가 없다.

위험해지는 순간은 그 값을 필드에 담을 때다. private OrderRequest currentRequest; 같은 필드를 만들어 파라미터를 옮겨 담으면 즉시 8-3절의 타임라인이 재현된다. 즉 안전의 근거는 "스프링이 컨트롤러를 특별 취급해서"가 아니라 "값이 스택에 있어서"다.

필드가 List나 Map이면요? 그것도 위험한가요? 함정힌트: 9절의 규칙 그대로 — "내부에 변경되는 상태를 갖는가"

요청 처리 중에 원소를 넣거나 빼면 위험하다. private final List<Order> buffer = new ArrayList<>(); 같은 필드는 final이어도 내부 상태가 계속 바뀌므로 9절의 SimpleDateFormat과 정확히 같은 부류다. 증상은 원소 유실, 크기 불일치, 순회 중 ConcurrentModificationException 등으로 나타난다.

반대로 기동 시 한 번 채우고 이후 읽기만 하는 컬렉션(설정값 목록, 코드 매핑 테이블)은 안전하다. 더 확실히 하려면 List.of(...)나 Map.of(...) 같은 불변 컬렉션으로 만들어 "쓰기 자체가 불가능"하게 못 박는다 — 규칙을 주석이 아니라 타입으로 표현하는 것이 리뷰 비용을 줄인다.

이 버그를 코드 리뷰에서 기계적으로 잡으려면 무엇을 보나요? 시니어 변별힌트: "조심하자"가 아니라 체크 가능한 규칙으로 바꾼다

리뷰어의 눈에 의존하는 대신 세 가지를 기계적으로 훑는다.

  • ① 빈 클래스에 final이 아닌 인스턴스 필드가 있는가 — 대부분 여기서 걸린다. 주입 의존성과 설정값은 전부 final이어도 문제가 없기 때문에, final이 아닌 필드는 그 자체로 "왜?"를 물어야 하는 신호다.
  • ② final이지만 내부가 가변인 타입인가 — SimpleDateFormat, Calendar, Matcher, 가변 컬렉션. 9절의 질문("내부에 변경되는 상태를 갖는가")을 타입별로 적용한다.
  • ③ 세터가 있는 빈인가 — 요청 처리 중에 호출되는 세터는 곧 공유 상태 변경이다.

여기서 한 칸 더 가려면 규칙을 테스트로 고정한다고 말하면 좋다. ArchUnit 같은 도구로 "@Service·@Component가 붙은 클래스의 인스턴스 필드는 모두 final이어야 한다"는 아키텍처 테스트를 CI에 걸면, 사람이 매번 기억하지 않아도 되는 구조가 된다. 8-4절의 결론("발견이 아니라 예방")을 실행으로 옮기는 방법이다.

동시성 테스트를 짜면 잡히지 않나요?힌트: "잡을 수도 있다"에서 시작하되, 왜 신뢰할 수 없는지를 말한다

운이 좋으면 잡힌다. ExecutorService와 CountDownLatch로 스레드 수십 개를 동시에 출발시켜 결과를 검증하면 재현되는 경우가 있다.

문제는 그 테스트를 신뢰할 수 없다는 것이다. 재현은 t1~t4 사이의 좁은 창에 다른 스레드가 정확히 끼어드는 타이밍에 달려 있어, 같은 코드가 어떤 날은 통과하고 어떤 날은 실패한다. 통과했다고 안전을 보증하지 못하는 테스트는 안전하다는 착각만 만든다. 그래서 결론은 8-4절과 같다 — 이 유형은 테스트로 발견하는 대상이 아니라 구조로 발생 불가능하게 만드는 대상이다.

가상 스레드를 켜면 이 문제가 사라지나요? 가산점힌트: 무엇이 달라지고 무엇이 그대로인지를 나눠 답한다

싱글턴 빈 필드 공유 문제는 조금도 달라지지 않는다. Spring Boot 3.2부터 spring.threads.virtual.enabled=true로 요청을 가상 스레드에서 처리할 수 있지만, 스레드가 무엇이든 인스턴스는 여전히 하나이기 때문이다. 오히려 스레드를 값싸게 많이 만들 수 있으므로 동시 실행 수가 늘어 사고 확률이 올라갈 수도 있다.

달라지는 것은 ThreadLocal 쪽이다. 가상 스레드는 요청마다 새로 만들어지고 풀에서 재사용되지 않으므로, "remove()를 잊어 다음 요청에 이전 값이 새어 나가는" 위험은 줄어든다. 이 두 가지를 구분해서 말하는 것이 답의 핵심이다.

같은 클래스인데 인스턴스가 2개인 상황도 있나요?힌트: 싱글턴의 범위를 정확히 말하면 답이 나온다

있다. 싱글턴의 범위는 "컨테이너당 1개"이지 "JVM당 1개"가 아니기 때문이다. 테스트에서 설정이 다른 컨텍스트가 여러 개 뜨면(다른 @MockBean 조합, 다른 프로퍼티) 컨텍스트마다 별도의 인스턴스가 만들어진다. 물론 테스트 코드에서 new로 직접 만든 것도 컨테이너와 무관한 또 하나의 인스턴스다.

이 사실이 실무에서 의미를 갖는 지점은 static 필드나 프로세스 전역 상태를 빈에 섞어 쓸 때다. 빈 인스턴스는 컨텍스트별로 갈라지는데 static은 JVM 전체가 공유하므로, 테스트 간에 값이 새어 나가 실행 순서에 따라 결과가 달라지는 테스트가 만들어진다. 6-2절에서 GoF 싱글턴의 단점으로 꼽은 것이 정확히 이 현상이다.

한 줄 요약
스프링 빈은 "컨테이너가 인스턴스화 → 주입 → 초기화 콜백 → 프록시 씌우기 → 소멸까지 대신 관리하고, 기본은 컨테이너당 1개(싱글턴)를 모든 스레드가 공유한다"는 계약 위에 있다 — 그래서 싱글턴 빈은 불변 의존성만 필드로 갖고 요청별 상태는 지역 변수와 파라미터(스레드 전용 스택)로만 다루는 무상태 설계가 원칙이며, 이를 어긴 코드는 단위·통합·QA 테스트를 전부 통과한 뒤 운영의 동시 접속에서만 사용자 데이터가 섞이는, 코드 리뷰 말고는 잡을 수단이 없는 사고를 낸다.
