톰캣 스레드풀 / HikariCP 크기 산정
코어 수가 아니라 "점유 시간"으로 계산한다

면접 질문: "톰캣 스레드풀(max-threads), DB 커넥션풀(HikariCP) 크기는 어떤 기준으로 산정하나요?"

핵심 관전 포인트 — 풀 크기는 감이 아니라 Little's law(동시 점유 수 L = 처리량 λ × 점유 시간 W)로 계산하는 공학적 결정이다. 핵심은 같은 요청이라도 자원마다 W가 다르다는 것 — 블로킹 MVC에서 톰캣 스레드는 응답을 다 쓸 때까지 전체 응답시간 동안 묶이지만, DB 커넥션은 트랜잭션·쿼리 구간에만 묶인다. 그래서 500 TPS·응답 100ms·커넥션 점유 50ms인 서버는 톰캣 50, Hikari 25라는 서로 다른 숫자가 나오고, "스레드 수 = 커넥션 수"로 맞추는 것은 근거가 없다. 코어 수는 스레드 수의 기준이 아니라 CPU 연산 총량의 상한일 뿐이라(요청당 CPU 5ms면 4코어 = 800 TPS가 천장), I/O 바운드 서버는 스레드가 코어보다 훨씬 많은 것이 정상이다. 계산값 L은 이용률 100%에 해당하는 값이라 그대로 쓰면 안 되고, 목표 이용률 ρ로 나눠 c = L/ρ로 여유를 만든다 — "×1.5"는 주술이 아니라 ρ=0.67의 역수다. 반대편에는 DB 쪽 상한이 있어서 HikariCP 위키는 connections = (core_count × 2) + effective_spindle_count를 권하는데 여기서 core_count는 앱 서버가 아니라 DB 서버의 코어 수이고, 앱 계산값과 DB 상한 중 작은 쪽이 실질 상한이다. 마지막으로 자원은 연쇄로 묶이므로(톰캣 200에 Hikari 10이면 실질 처리량은 10/0.05s = 200 TPS에서 막힌다) 풀 크기는 따로 정하는 것이 아니라 병목 지점을 의식하고 정한다. 그리고 계산은 출발점일 뿐, 최종 숫자는 hikaricp.connections.pending과 tomcat.threads.busy로 검증한다.
  • 1
    계산으로 시작한다 — L = λ × W로 자원별 필요 개수를 뽑는다. 500 TPS · 응답 100ms · 커넥션 점유 50ms면 톰캣 50, Hikari 25. 두 숫자가 다른 이유는 W가 다르기 때문이고, 그래서 "스레드 수 = 커넥션 수"는 근거가 없다.
  • 2
    계산값은 설정값이 아니다 — L은 이용률 100%에 해당하므로 목표 이용률로 나눈다(c = L/ρ, ρ=0.7이면 1.43배). 그리고 커넥션은 반대편의 DB 상한 (DB 코어 × 2) + spindle과 인스턴스 수를 곱한 총합에 다시 묶인다 — 작은 쪽이 실질 상한이다.
  • 3
    풀 크기는 성능 설정이 아니라 용량 선언이다 — λ_max = c/W이므로 c를 정하는 순간 처리량 상한이 정해진다. 톰캣 200 · Hikari 10이면 그 서버는 200 TPS 서버다. 그리고 막혔을 때 손댈 것은 c가 아니라 W(점유 시간)이며, 최종 확인은 hikaricp.connections.pending과 usage 실측이다.

질문: "톰캣 스레드풀(max-threads), DB 커넥션풀(HikariCP) 크기는 어떤 기준으로 산정하나요?"

출제 의도: "기본값 그대로" 또는 "많을수록 좋다"는 답을 거르는 질문이다. 풀 크기는 계산 가능한 공학적 결정(동시 요청 수 × 요청당 점유 시간)이고, 이 계산을 해본 사람만 용량 산정 회의에서 근거 있는 숫자를 낼 수 있다.

기준 버전: Spring Boot 3.x + 톰캣 10.1 + HikariCP 5.x. 기본값을 언급할 때는 그 자리에서 어느 컴포넌트의 기본값인지 밝힌다.

이 페이지가 겨냥하는 약점 네 가지 ① "코어 수 × N"으로 답하는 것 → 4·6절에서 코어는 스레드 수의 기준이 아니라 CPU 연산 총량의 상한임을 스레드 상태와 CPU 예산 계산으로 분리한다.
② "스레드 수 = 커넥션 수"로 맞추는 것 → 2절의 요청 타임라인 도식에서 두 자원의 점유 구간이 다르다는 것을 눈으로 못 박는다.
③ "계산값 × 1.5"를 근거 없이 던지는 것 → 7절에서 1.5의 정체가 ρ≈0.67의 역수임을, 대기가 1/(1-ρ)로 폭발한다는 대기행렬 관점으로 세운다.
④ 앱 쪽만 보고 끝내는 것 → 8·9절에서 DB 상한 · 인스턴스 수 곱 · 연쇄 병목을 붙여 "이 숫자가 시스템 전체에서 무엇을 뜻하는가"까지 간다.

1. 산정의 뼈대 — Little's law를 직관에서 식으로

1-1. 법칙 이름을 꺼내기 전에 — 가게에 몇 명이 있는가

식을 먼저 보면 무슨 소리인지 모른다. 그래서 식 없이 답할 수 있는 문제부터 시작한다.

어떤 가게에 손님이 초당 10명씩 들어온다. 한 손님은 들어와서 평균 3초 머물다 나간다.
아무 순간에나 가게 안을 들여다보면 평균 몇 명이 있겠는가?

1-2. 식으로 옮기기

방금 한 계산이 Little's law다. MIT의 John Little이 1961년에 증명해 그의 이름이 붙었다.

L  =  λ  ×  W L 동시 점유 수(어느 순간 시스템 안에 있는 것의 평균 개수)  =  λ 도착률·처리량(초당 몇 건)  ×  W 체류 시간(하나가 안에 머무는 평균 시간)

성립 조건은 하나뿐

  • 안정 상태(steady state) — 들어오는 속도와 나가는 속도가 장기적으로 같아야 한다.
  • 유입이 처리보다 계속 빠르면 L은 수렴하지 않고 무한정 늘어난다.
  • 그래서 이 법칙은 "감당 가능한 부하 안에서" 쓰는 도구다.

조건에 없는 것들이 더 중요하다

  • 도착이 균일하든 몰리든 상관없다.
  • 처리 순서가 선착순이든 아니든 상관없다.
  • 처리 시간 분포가 어떻든 상관없다.
  • → 그래서 어떤 자원에도 그대로 대입할 수 있다.

암기 장치 — 세 글자를 문장으로 붙여 외운다

"초당 몇 건(λ)이 몇 초씩 머무는가(W) → 그 곱이 지금 안에 있는 개수(L)"

면접에서 식을 쓰기 전에 이 문장을 먼저 말하면 상대가 "이 사람은 외운 게 아니라 이해했다"로 듣는다. 그리고 단위가 곧 검산이다 — 건/초 × 초/건 = 건. 결과 단위가 "건"이 아니면 어딘가 틀린 것이다.

2. 서버에 대입한다 — 같은 요청인데 자원마다 W가 다르다 이 문서의 핵심

가게를 서버로 바꾼다. "가게 안의 손님 수"가 "그 자원을 동시에 점유 중인 요청 수"가 되고, 그 숫자가 곧 필요한 풀 크기다. 예제 조건은 이렇다.

결정적인 지점은 톰캣 스레드와 DB 커넥션의 W가 다르다는 것이다. 아래 타임라인이 이 문서에서 가장 중요한 그림이다.

비유로 한 번 더 — 식당의 테이블과 화구 1-1의 가게로 돌아가자. 손님 한 명은 테이블을 입장부터 퇴장까지 내내 점유하지만, 주방의 화구는 조리하는 동안만 점유한다. 그래서 같은 손님 유입에도 필요한 테이블 수와 필요한 화구 수는 다르다. 테이블 = 톰캣 스레드(전체 체류), 화구 = DB 커넥션(작업 구간만). "테이블 수와 화구 수를 똑같이 맞춘다"는 말이 이상하게 들린다면, "스레드 수 = 커넥션 수"도 똑같이 이상한 말이다.

2-1. 단위 환산 — 왜 굳이 초로 바꾸는가

λ는 "초당", W는 "밀리초"로 되어 있으니 먼저 초로 맞춘다. 환산하지 않고 계산해 보면 이 식이 무엇을 세고 있는지가 오히려 더 선명해진다.

[단위를 맞춰서]
  톰캣   W = 100ms = 100/1000 초 = 0.1초    →  L = 500건/초 × 0.1초/건 = 50건
  Hikari W =  50ms =  50/1000 초 = 0.05초   →  L = 500건/초 × 0.05초/건 = 25건

[환산하지 않고 그대로 곱하면 — 뜻이 더 잘 보인다]
  500건/초 × 100ms/건 = 50,000 ms/초 = 50초/초

  읽는 법: "실제 시간 1초가 흐를 때마다 스레드-시간 50초어치가 필요하다."
  스레드 하나는 1초에 1초어치밖에 못 대므로  →  스레드 50개가 필요하다.
같은 요청, 같은 처리량 — 자원별 점유 구간이 다르므로 필요 개수가 다르다
자원점유 구간W계산계산값 L
톰캣 스레드요청 수신 ~ 응답 완료100ms500 × 0.150
Hikari 커넥션트랜잭션 시작 ~ 반환50ms500 × 0.0525

"스레드 수 = 커넥션 수"로 맞추면 무슨 일이 생기나

커넥션을 50으로 올려 맞추면

  • 필요한 것은 25개인데 50개를 잡아뒀으므로 25개는 평생 논다.
  • 그러면서 DB 쪽 자원(프로세스·메모리·락 경합)은 실제로 잡아먹는다(8절).

스레드를 25로 내려 맞추면

  • λ_max = 25/0.1 = 250 TPS — 목표의 절반에서 막힌다.
  • 나머지 250 TPS는 accept 큐에 쌓이다가 거절된다.
두 자원의 W가 2배 다르면 필요한 개수도 2배 다른 것이 정상이다

여기서 나오는 가장 값진 따름정리 — c를 늘리기 전에 W를 의심한다

W를 줄이면 같은 λ를 더 작은 풀로 감당한다

커넥션 점유 시간 50ms → 25ms로 줄이면 필요 커넥션은 25개 → 12.5개가 된다. 풀을 늘리는 것은 DB라는 남의 자원을 더 쓰겠다는 요청이지만, W를 줄이는 것은 내 코드를 고쳐 자원 소비를 줄이는 것이다. 후자가 거의 항상 낫다(줄이는 방법은 10절과 22-external-api-call-inside-transaction.md).

2-2. W를 줄인다는 것이 코드에서는 이런 뜻이다

말로만 "점유 시간을 줄여라"라고 하면 손에 안 잡힌다. 트랜잭션 안에서 외부 API를 호출하는 코드가 가장 흔한 W 증폭기다.

before 커넥션을 쥔 채 외부 API를 기다린다 — W = 50 + 300 = 350ms
@Transactional
public void placeOrder(OrderCommand cmd) {
    Order order = orderRepository.save(Order.of(cmd));   // 10ms

    PayResult r = pgClient.pay(cmd.card(), cmd.amount());외부 PG 300ms
    // 이 300ms 동안에도 DB 커넥션은 반납되지 않는다.
    // 트랜잭션이 열려 있는 한 커넥션은 이 스레드에 묶여 있다.

    order.markPaid(r.approvalNo());                      // 10ms
}
// 필요 커넥션 = 500 × 0.35 = 175개  ← DB 상한(8절)으로는 불가능
after 외부 호출을 트랜잭션 밖으로 — W = 50ms 유지
public void placeOrder(OrderCommand cmd) {
    Long id = orderService.createPending(cmd);짧은 트랜잭션 ①

    PayResult r = pgClient.pay(cmd.card(), cmd.amount());
    // 커넥션을 반납한 상태로 300ms를 기다린다

    orderService.markPaid(id, r.approvalNo());짧은 트랜잭션 ②
}
// 톰캣 스레드의 W는 여전히 350ms지만(→ 스레드는 더 필요),
// 커넥션의 W는 50ms 그대로 → 필요 커넥션 25개.
// 대신 ①과 ② 사이에 원자성이 깨지므로 보상/상태 전이 설계가 필요하다.
이 대비에서 진짜로 배워야 할 것 같은 리팩터링이 두 자원에 다르게 작용한다. 외부 호출을 트랜잭션 밖으로 빼면 커넥션의 W는 줄지만 톰캣 스레드의 W는 그대로다(스레드는 여전히 응답이 끝날 때까지 붙잡혀 있다 — 5절). 즉 "W를 줄였다"는 말은 항상 "어느 자원의 W인가"와 함께 해야 한다. 이것이 자원별로 따로 계산해야 하는 이유이기도 하다.

3. 식을 거꾸로 쓰면 — 풀 크기는 성능 설정이 아니라 용량 선언이다

L = λW는 등식이므로 λ = L / W로 돌려 쓸 수 있다. 그러면 "풀 크기 c를 정하는 순간 그 자원을 지나는 최대 처리량이 정해진다"는 뜻이 된다.

λmax  =  c  /  W 풀 크기를 정한다 = 그 자원을 통과할 수 있는 초당 건수의 천장을 선언한다
커넥션 10개
10 / 0.05 = 200 TPS
HikariCP 기본값이 만드는 천장
커넥션 25개
25 / 0.05 = 500 TPS
목표에 딱 맞는 계산값
커넥션 50개
50 / 0.05 = 1,000 TPS
단, DB가 받아준다는 전제에서만

면접에서 이 방향으로 말해야 답이 완성된다

"풀 크기를 왜 그렇게 잡았나"에 대한 답에는
"그 값이 우리 서비스의 처리량 상한을 얼마로 선언한 것인지"가 함께 있어야 한다

예: "Hikari 25는 점유 50ms 기준 500 TPS 상한을 뜻하고, 그 위로는 커넥션 대기가 시작됩니다" — 이렇게 말하면 숫자가 설정값이 아니라 계약으로 들린다.

4. 오개념 ① — "스레드 수는 코어 수만큼"이 아니다 함정

"4코어니까 스레드도 4개쯤"이 자연스럽게 들리는 이유는 코어 수를 동시에 존재할 수 있는 스레드 수의 제한으로 오해하기 때문이다. 정확히는 이렇다.

코어 수의 정확한 정의

코어 수 = 어느 한 순간에 CPU 위에서 실제로 명령어를 실행 중일 수 있는 스레드의 최대 개수

존재할 수 있는 스레드 수와는 아무 상관이 없다. 스레드 50개를 만들어 두고 그중 4개만 실행 중이고 46개는 자고 있어도 아무 문제가 없다.

주니어가 거의 반드시 틀리는 지점

JDBC로 DB 응답을 기다리는 스레드는 BLOCKED가 아니라 RUNNABLE로 보인다

왜 그런가. 소켓 read는 JVM 입장에서는 네이티브 메서드 호출이다. JVM이 네이티브 코드에 진입하는 순간, 그 안에서 OS가 스레드를 재웠는지 어쨌는지 JVM은 알 수 없다. 그래서 "네이티브 안에 있다 = 실행 중일 수도 있다"로 보고 RUNNABLE로 표시한다. 자바가 보는 상태와 OS가 보는 상태가 어긋나는 지점이다.

BLOCKED는 오직 synchronized 락 경쟁을 뜻하는 상태 이름이라는 것만 기억하면 이 함정은 안 밟는다.

스레드 덤프 DB 응답을 기다리는 톰캣 스레드는 실제로 이렇게 찍힌다

5. 오개념 ② — 대기 중인 스레드가 다른 요청을 처리해주지는 않는다 함정

4절에서 "대기 중인 스레드는 CPU를 안 쓴다"고 했다. 여기서 "그럼 그동안 다른 요청을 처리하면 되지 않나"로 넘어가는 것이 두 번째 오개념이다. 못 한다.

오해 "DB 기다리는 동안 이 스레드가 다른 요청을 처리한다"
public OrderResponse getOrder(Long id) {
    Order order = orderRepository.findById(id);여기서 멈춘다
    // 위 한 줄에서 소켓 read가 반환될 때까지 이 메서드는 이 줄에 멈춰 있다.
    // 이 스레드의 콜 스택에는 getOrder 호출 프레임이 그대로 쌓여 있고,
    // 그 프레임을 치우지 않는 한 다른 요청의 코드를 실행할 수 없다.
    //
    // CPU를 놓아준 것과 스레드를 놓아준 것은 전혀 다른 이야기다.
    return toResponse(order);
}

한 문장 원리 — 스레드가 곧 콜 스택이다

스레드 하나에는 콜 스택이 하나뿐이고, 그 스택에는 지금 진행 중인 요청의 호출 프레임이 쌓여 있다

다른 요청을 처리하려면 그 스택을 어딘가에 치워두고 새 스택을 올려야 하는데, 플랫폼 스레드에는 그런 기능이 없다. 그래서 블로킹 MVC에서 대기 시간을 흡수하는 수단은 스레드 개수뿐이다.

6. 그럼 코어 수는 무엇을 정하는가 — CPU 연산 총량의 상한

코어 수가 스레드 수의 기준이 아니라면 아무 의미가 없는 것인가. 아니다. 코어 수는 초당 처리 가능한 CPU 연산의 총량을 정한다. 이것을 "CPU 예산"이라 부르고 계산으로 확인한다.

[CPU 예산 계산]

4코어 = 초당 4 × 1,000ms = 4,000ms 의 CPU 시간을 제공한다.
요청 하나가 실제로 쓰는 CPU 시간이 5ms 라면,

  CPU 상한 = 4,000ms / 5ms = 800 TPS

즉 스레드를 50개로 잡든 500개로 잡든 이 서버는 800 TPS를 넘을 수 없다.
목표 500 TPS일 때의 CPU 이용률 = 500 / 800 = 62.5%
요청당 CPU 시간이 늘어나면 천장이 이렇게 내려앉는다 (4코어 = 초당 4,000ms 예산)

5ms4,000 / 5 = 800 TPS62.5%여유 있음

요청당 CPU 8ms 행이 함정이다 CPU 상한이 정확히 목표와 같아진다. 숫자상으로는 "딱 맞는다"처럼 보이지만 이용률 100%는 "쉴 틈이 하나도 없다"는 뜻이고, 그 지점에서 큐가 어떻게 폭발하는지는 7-2절에서 다룬다. 이용률 100%로 계획하는 것은 계획이 아니라 도박이다.

6-1. 워크로드 성격에 따라 산정 방식이 완전히 갈린다

I/O 바운드 — 일반적인 웹 API

  • DB · 캐시 · 외부 API를 기다리는 시간이 대부분
  • 스레드 ≫ 코어가 정상
  • 스레드 수는 Little's law로 계산한다
  • 스레드를 늘리면 실제로 처리량이 올라간다 (대기를 더 많이 겹쳐 놓을 수 있으므로)

CPU 바운드 — 암호화 · 이미지 인코딩 · 대량 집계

  • 기다림 없이 계속 연산한다
  • 스레드 ≈ 코어(±1~2)
  • 스레드를 늘려도 아무 효과가 없다 — 코어 4개면 초당 4,000ms 예산은 그대로다
  • 오히려 컨텍스트 스위칭과 캐시 오염 비용이 붙어 처리량이 떨어진다

두 오개념을 한 장으로 봉인 — 코어와 스레드의 역할 분담

코어 수는 "얼마나 빨리 계산하는가"의 상한,   스레드 수는 "얼마나 많이 동시에 기다릴 수 있는가"의 상한

그래서 두 숫자는 서로 다른 질문에 답한다. "코어가 4개인데 스레드 50개가 말이 되나요?"라는 질문에는 "그 50개 중 실제로 계산 중인 것은 최대 4개고, 나머지는 기다리는 중이라 코어를 쓰지 않습니다"라고 답하면 된다.

6-2. 그래서 "많을수록 좋다"가 왜 틀린가 — 비용 3종

1
스택 메모리. 플랫폼 스레드는 만들 때 전용 콜 스택을 네이티브 메모리에 예약한다. 크기는 플랫폼마다 달라 수백 KB~2MB 수준이다(리눅스 x86-64 기본 1MB, macOS/AArch64 OpenJDK 21은 2MB). 예약이지 즉시 소모는 아니지만, 주소 공간과 커널 자료구조는 스레드 수에 정직하게 비례한다.
2
컨텍스트 스위칭. 실행 가능한 스레드가 코어보다 훨씬 많으면 스케줄러가 계속 갈아 끼운다. 레지스터 저장·복원 비용도 있지만 더 아픈 것은 CPU 캐시 오염이다 — 새로 올라온 스레드는 자기 데이터가 캐시에 없어 메모리에서 다시 읽어야 한다.
3
뒷단으로 과부하를 그대로 흘려보낸다. 실무 핵심 max-threads를 2,000으로 잡으면 그 2,000개가 전부 DB 커넥션을 요구하러 몰려간다. 처리 못 할 요청을 앞에서 받아들이는 것은 문제를 뒤로 미루는 것이 아니라 더 나쁜 곳에서 터지게 만드는 것이다.

암기 장치 — 스레드를 늘리는 비용 3종은 "스 · 컨 · 뒷"

스택 메모리  ·  컨텍스트 스위칭  ·  뒷단 과부하 전달

앞의 둘은 내 서버 안의 비용이고, 세 번째는 남의 자원(DB)으로 번지는 비용이다. 면접에서는 세 번째를 반드시 말해야 "설정값 외운 사람"과 갈린다.

7. 계산값에서 운영 설정값으로 — 피크로 계산하고, 이용률만큼 여유를 둔다

먼저 못 박을 것 2절에서 나온 50과 25는 계산값이지 설정값이 아니다. 그대로 application.yml에 넣으면 안 된다. 그 사이를 메우는 고려가 네 가지(피크 · 이용률 · DB 상한 · 인스턴스 수)이고, 이 절과 다음 절에서 차례로 붙인다.

7-2. 여유는 주술이 아니라 "목표 이용률의 역수"다 시니어 변별

"계산값 × 1.5" 같은 숫자를 근거 없이 던지면 안 된다. 여유가 필요한 이유부터 짚자.

L = λW로 나온 50은 "평균적으로 50개가 동시에 점유 중"이라는 뜻이다. 여기서 풀 크기를 정확히 50으로 잡으면 이용률 ρ = L/c = 50/50 = 100%가 된다. 이건 "딱 맞게 썼다"가 아니라 "쉴 틈이 하나도 없다"는 뜻이다.

문제는 도착이 평균값대로 균일하게 오지 않는다는 것이다. 어떤 순간에는 55개가 몰리고 어떤 순간에는 45개다. 이용률이 100%라면 55개가 몰린 순간의 5개는 대기해야 하고, 그 대기가 응답시간을 늘려 W가 커지고, W가 커지면 L이 커지고, L이 커지면 대기가 더 늘어난다.

7-3. 그래서 여유는 이렇게 정한다

c  =  L  /  ρtarget 배수를 외우는 것이 아니라 "이 자원을 몇 %까지 쓸 작정인가"를 정하는 것이다 
톰캣   L=50, ρ=0.7  ->  c = 50/0.7  = 71.4  ->  72 (또는 여유 있게 80)
Hikari L=25, ρ=0.7  ->  c = 25/0.7  = 35.7  ->  36
톰캣   L=50, ρ=0.8  ->  c = 50/0.8  = 62.5  ->  64
Hikari L=25, ρ=0.8  ->  c = 25/0.8  = 31.2  ->  32

"계산값 × 1.5"의 정체를 한 줄로 말할 수 있으면 이 질문은 이긴다

×1.5 = ρ_target ≈ 0.67의 역수  ·  ×1.43 = ρ 0.7  ·  ×1.25 = ρ 0.8

판단 기준은 위 대기 확률 표와 서비스의 지연 목표(SLO)다. "1.5배 곱합니다"가 아니라 "이 자원은 이용률 70%를 목표로 잡아서 1.43배를 곱했습니다"라고 말한다.

모델의 한계도 같이 말하면 신뢰가 올라간다 위 모델들은 도착이 무작위(포아송)라고 가정한다. 실제 트래픽은 그보다 더 몰려서 오므로, 모델이 말하는 대기보다 실제 대기가 나쁘다. 그래서 이 계산은 하한선을 주는 것이고, 최종 확인은 10절의 실측이다.

8. 반대편의 상한 — 커넥션은 DB가 허락하는 만큼만이다

7절까지는 앱 쪽 사정만 봤다. 커넥션은 반대편에 DB가 있다는 점이 다르다. HikariCP 공식 위키의 "About Pool Sizing" 문서는 반직관적인 주장을 한다 — 풀을 키우면 처리량이 오히려 떨어진다.

8-1. 왜 커넥션을 늘리면 DB가 느려지는가

커넥션 하나는 DB 쪽에서 실행 주체 하나를 뜻한다. PostgreSQL은 커넥션마다 백엔드 프로세스를 하나씩 띄운다(MySQL은 스레드 하나). 그러니 커넥션 1,000개는 DB 서버에 프로세스 1,000개다. 그 DB 서버의 코어가 8개라면, 8개 코어가 1,000개 프로세스를 시분할해야 한다. 여기서 세 가지가 나빠진다.

① 컨텍스트 스위칭
6-2에서 본 비용이 이번엔 DB 서버에서 발생한다. 코어 8개 위에 1,000개를 번갈아 태우면 실제 쿼리 실행보다 갈아 끼우는 데 쓰는 시간이 늘어난다.
② 락 경합
동시 실행 트랜잭션이 많을수록 같은 행·같은 인덱스 페이지·같은 내부 자료구조를 건드릴 확률이 오른다. 경합 = 대기 = W 증가 = 커넥션이 더 오래 잡힘이라는 되먹임이 생긴다.
③ 디스크 시크 · 캐시 오염
회전 디스크에서는 동시 요청이 많을수록 헤드가 이리저리 움직여 순차성이 깨진다. SSD에서는 이 효과가 훨씬 작지만 0은 아니고, 대신 공유 버퍼 오염(서로의 캐시된 페이지를 밀어냄)이 그 자리를 대신한다.
위키가 인용하는 실험 — 숫자가 반직관적이라 오히려 기억에 남는다 Oracle Real-World Performance 그룹의 실험에서 커넥션 풀을 2,048개에서 96개로 줄였더니 응답시간과 처리량이 모두 개선됐다. 줄였는데 좋아졌다는 것이 요점이다 — 커넥션은 "많이 확보할수록 유리한 자원"이 아니라 DB의 동시 실행 능력을 초과하면 순수한 손해가 되는 자원이다.

8-2. 위키의 출발점 공식과, 여기 박힌 함정

connections = (core_count × 2) + effective_spindle_count DB가 동시에 의미 있게 진행시킬 수 있는 작업의 개수를 추정하는 식

주니어가 반드시 틀리는 지점

core_count는 DB 서버의 코어 수다 — 앱 서버의 코어 수가 아니다

이 공식이 말하는 것은 "DB가 동시에 얼마나 진행시킬 수 있는가"이지 "앱이 몇 개를 요청할 수 있는가"가 아니다. 앱 서버 스펙을 넣어 계산했다면 식은 맞게 썼는데 답은 무의미하다.

core_count × 2 — 왜 2배인가

커넥션 하나가 항상 CPU를 쓰는 게 아니라 중간중간 디스크·네트워크를 기다리기 때문이다. 그 대기 동안 다른 커넥션이 코어를 쓰라고 여유분을 둔 것이다. (구조적으로는 4절에서 본 "대기 중 스레드는 CPU를 안 쓴다"와 같은 논리다.)

effective_spindle_count — 실무에서는 어떻게 하나

동시에 독립적으로 탐색(seek)할 수 있는 디스크의 개수다. 회전 디스크 시절의 어휘라 SSD·클라우드 스토리지에서는 그대로 대입하기 어렵다. 실무에서는 이 항을 작게(1~2) 두거나 사실상 무시하고, 대신 실측으로 보정한다.

DB 서버가 8코어라면 (8 × 2) + 1 = 17개 정도가 출발점이 된다. 7-3에서 앱 계산으로 나온 36과 이 17이 충돌한다.

충돌했을 때의 규칙 — 이 문서에서 가장 자주 인출할 한 줄

앱 계산값과 DB 상한 중 작은 쪽이 실질 상한이다

앱이 36개를 꽂아도 DB가 17개어치의 일밖에 못 하면, 나머지 19개는 대기 줄을 앱 쪽에서 DB 쪽으로 옮겨 놓은 것에 불과하다. 오히려 DB 안에서의 경합을 늘려 W를 더 나쁘게 만든다.

그럼 어떻게 하는가 — c를 늘리는 대신 W를 줄인다. L = λW에서 c가 17로 묶여 있고 λ가 500이라면, W는 17/500 = 34ms 이하여야 한다. "50ms를 34ms로 줄이는 것"이 진짜 과제가 된다(2-2의 리팩터링이 여기서 쓰인다).

8-3. 앱 인스턴스 수를 곱하는 것을 잊지 않는다 함정

풀 크기는 인스턴스 하나당 값이다. 그런데 DB가 보는 것은 전체 합계다.

오토스케일링과 만나면 더 고약해진다 트래픽이 늘어 인스턴스가 6대에서 12대로 늘면 DB 커넥션 요구가 360개로 자동으로 두 배가 된다. 앱을 수평 확장했는데 DB가 먼저 죽는 전형적인 패턴이고, 하필 트래픽이 가장 많을 때 발생한다.

대응 3종

총합 기준으로 역산
인스턴스 수를 곱한 총합을 기준으로 인스턴스당 풀 크기를 정한다. (DB 허용치 ÷ 최대 인스턴스 수)
PgBouncer 같은 풀러
DB 앞에 커넥션 풀러를 둬서, 앱들의 커넥션을 받아 DB에는 훨씬 적은 수의 실제 커넥션으로 다중화해 준다.
워크로드 분리
배치 · 관리 도구 · 읽기 전용 조회처럼 성격이 다른 워크로드는 별도 데이터소스로 분리해 서로의 풀을 잠식하지 않게 한다.

9. 자원은 연쇄로 묶인다 — 문만 넓히면 건물 전체가 마비된다 시니어 변별

지금까지 스레드와 커넥션을 따로 계산했지만, 실제 요청은 두 자원을 순서대로 통과한다. 그래서 하나만 잘 잡아도 소용이 없다. 톰캣 200 · Hikari 10이라는 흔한 조합(둘 다 각각의 기본값에 가깝다)에서 500 TPS가 들어오면 무슨 일이 생기는지 따라가 보자.

9-1. 여기서 나오는 산정 원칙 3가지

1
연쇄 자원의 처리량 상한은 가장 좁은 자원이 정한다. 톰캣을 200으로 잡아둔 것이 200 TPS 서버를 만들지 않는다. Hikari 10이 그렇게 만든다. "우리 서버 몇 TPS 받나요"의 답은 가장 좁은 자원의 λ_max다.
2
풀 크기는 따로 정하는 것이 아니라, 어디를 병목으로 삼을지 정하고 나머지를 거기에 맞춘다. 병목을 DB에 두기로 했다면(대개 그렇다 — DB가 가장 늘리기 어려운 자원이므로), 톰캣 스레드는 커넥션 대기 요청을 잔뜩 쌓아두지 않을 만큼만 두는 것이 낫다.
3
좁은 지점 앞에서는 오래 기다리게 두지 말고 빨리 거절한다. HikariCP connection-timeout을 기본 30초에서 2~3초로 낮추면, 대기 줄이 톰캣 스레드풀로 전이되는 시간이 10배 짧아진다.
이 대응은 26-hikaricp-connection-pool-exhaustion.md에서 처방으로 다시 다룬다.

10. 계산은 출발점이다 — 무엇을 보고 검증하는가

계산이 끝나면 부하 테스트로 목표 λ를 걸고 아래 지표를 본다. 각 지표를 "어떤 값이면 무슨 뜻인지"까지 정해두고 봐야 검증이 된다.

검증 지표 — 값 자체가 아니라 "이 값이면 무슨 뜻인가"를 미리 정해둔다
지표이 값이면뜻
hikaricp.connections.pending0보다 크다커넥션을 못 받고 기다리는 스레드가 있다 = 풀 부족 또는 W 증가. 이 지표가 0이 아니면 이미 사용자 응답시간에 대기가 더해지고 있다.
hikaricp.connections.activemax에 붙어 있다풀이 포화. pending과 함께 봐야 원인이 갈린다 — active만 높고 pending이 0이면 "잘 쓰고 있는 것"일 수도 있다.
hikaricp.connections.usage계산에 쓴 W보다 크다점유 시간 가정이 틀렸다. 이 값이 실측 W다. 산정의 입력을 교정해 주는 유일한 지표.
hikaricp.connections.acquire0에서 벗어난다커넥션을 얻는 데 걸리는 시간. 여기가 늘면 이미 대기 중이라는 뜻이다.
tomcat.threads.busytomcat.threads.config.max에 붙는다스레드 포화. 단 원인일 수도 결과일 수도 있다 — 응답시간 악화(W 증가)의 결과로도 이렇게 된다.
CPU 사용률포화인데 TPS가 안 오른다6절의 CPU 상한에 걸린 것. 스레드를 늘려도 소용없다. 장비를 키우거나 요청당 CPU를 줄여야 한다.

가장 중요한 지표 하나만 고른다면 — hikaricp.connections.usage

이것이 Little's law의 W를 실측해 주는 값이기 때문이다

계산할 때 W=50ms로 가정했는데 실측이 120ms로 나온다면, 필요 커넥션은 25가 아니라 500 × 0.12 = 60개다. 계산이 틀린 게 아니라 입력 가정이 틀렸던 것이다.

pending > 0  +  usage가 가정치와 같다

진짜 풀 부족이다. 계산은 맞았고 c가 작았던 것 → c를 올리거나(DB 상한 안에서) 인스턴스를 늘린다.

pending > 0  +  usage가 늘었다

풀 부족이 아니라 점유 시간 문제다. 느린 쿼리·인덱스 누락·트랜잭션 안 외부 호출·락 경합을 찾는다 → c가 아니라 W를 고친다.

이 두 갈래가 26-hikaricp-connection-pool-exhaustion.md의 진단 프레임으로 그대로 이어진다.

메트릭이 안 보인다면 — 톰캣 쪽은 스위치를 켜야 한다 Spring Boot에서 Hikari 메트릭은 Micrometer가 붙어 있으면 자동으로 나오지만, 톰캣 메트릭(tomcat.*)은 server.tomcat.mbeanregistry.enabled=true를 켜야 노출된다. 이걸 몰라서 "톰캣 지표가 안 보인다"고 하는 경우가 흔하다.
마지막 함정 — 평균만 보면 계산 자체가 깨진다 p99가 평균과 크게 벌어지면 평균 기반 계산 자체가 무너진다(7-1). 분포를 보지 않고 평균만으로 산정하면 느린 요청 1%가 풀을 잠식하는 상황을 계산에서 아예 놓친다.

10-1. 산정 절차 한 장 요약 — 계산 → 보정 → 상한 → 검증

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

풀 크기 산정의 기본식은?
L = λ × W. "초당 몇 건(λ)이 몇 초씩 머무는가(W) → 그 곱이 지금 안에 있는 개수(L)". 단위 검산: 건/초 × 초/건 = 건.
톰캣과 Hikari의 숫자가 왜 다른가?
W(점유 구간)가 다르다. 스레드는 응답 전체(100ms), 커넥션은 트랜잭션 구간(50ms) → 50 vs 25.
"스레드 수 = 커넥션 수"가 틀린 이유는?
W가 2배 다르면 필요 개수도 2배 다르다. 맞춰버리면 커넥션이 놀거나 처리량이 잘린다.
코어 수는 무엇을 정하나?
CPU 연산 총량의 상한. 4코어 = 초당 4,000ms → 요청당 5ms면 800 TPS가 천장. 스레드 수의 기준이 아니다.
DB 응답 대기 중인 스레드의 상태는?
RUNNABLE. BLOCKED는 synchronized 락 대기만이다. 상태 이름 말고 스택 최상단을 봐라.
"계산값 × 1.5"의 정체는?
ρ_target ≈ 0.67의 역수. c = L/ρ. ρ 0.7 → ×1.43, ρ 0.8 → ×1.25.
이용률을 왜 100%로 두면 안 되나?
대기가 1/(1−ρ)로 폭발한다. ρ 0.5 → 총 체류 2배, ρ 0.9 → 10배, ρ 0.99 → 100배.
커넥션의 DB 쪽 상한 공식은?
(core_count × 2) + effective_spindle_count. core_count는 DB 서버 코어 수(앱 아님). 8코어 → 17.
풀 크기 계산에서 마지막에 빼먹는 것은?
앱 인스턴스 수를 곱하는 것. 6대 × 30 = 180 > PostgreSQL max_connections 기본 100.
연쇄 자원의 처리량 상한은?
가장 좁은 자원이 정한다. 톰캣 200 · Hikari 10 = 10/0.05 = 200 TPS 서버.
검증의 두 갈래는?
pending>0 + usage 그대로 = 진짜 풀 부족 / pending>0 + usage 증가 = W 문제.
풀을 늘리기 전에 손댈 것은?
W(점유 시간). W를 절반으로 줄이면 필요 개수도 절반. c는 남의 자원(DB)을 더 쓰는 것, W는 내 코드를 고치는 것.

          L_hikari = 500 × 0.05 = 25
② 여유    ρ_target = 0.7  ->  tomcat 72, hikari 36
③ DB 상한 DB 8코어 -> (8×2)+1 = 17  ->  hikari는 17이 상한
④ 인스턴스 6대 × 17 = 102  ->  PostgreSQL max_connections 100 초과, 재조정 필요
⑤ 결론    hikari는 계산값(36)이 아니라 DB 상한에 묶인다.
          -> 풀을 늘리는 대신 점유 시간 W를 50ms -> 34ms 이하로 줄이는 것이 과제
⑥ 검증    부하 테스트에서 pending > 0 여부와 usage 실측치로 가정을 확인

"앱 계산값과 DB 상한 중 작은 쪽이 실질 상한이고, 거기서 막히면 c가 아니라 W를 손대야 한다"까지 말하면 이 질문은 끝난다. ⑤에서 "계산대로 못 잡는다"를 스스로 인정하고 방향을 트는 것이 핵심이다 — 계산만 잘하는 사람과 갈리는 지점이 여기다.

트래픽이 2배(1,000 TPS)가 되면 풀도 2배로 잡으면 되나요? 필수힌트: 산술적으로는 맞다. 그 전에 확인할 두 가지가 있고, 결론은 수직이 아니라 수평이다

산술적으로는 스레드 100, 커넥션 50이 맞다. 하지만 그 전에 확인할 것이 둘 있다.

(1) CPU 예산이 버티는가. 요청당 CPU 5ms면 4코어의 상한은 800 TPS다(6절). 1,000 TPS는 애초에 이 장비에서 불가능하다 — 풀을 아무리 늘려도 안 된다.

(2) DB가 버티는가. 커넥션 50개는 DB 쪽 공식이 말하는 17개를 크게 넘는다. 늘려도 DB 안에서 경합만 늘어난다(8절).

그래서 답은 한 대의 수직 확장이 아니라 인스턴스 증설(수평 확장)이다. 단 8-3의 함정이 여기서 튀어나온다 — 인스턴스를 2배로 늘리면 DB 커넥션 요구도 2배가 되므로, 인스턴스당 풀 크기를 함께 줄이거나 PgBouncer를 넣어야 한다. "수평 확장하면 DB 쪽 총 커넥션이 같이 늘어난다"를 짚는 것이 이 질문의 변별점이다.

응답시간이 갑자기 늘어나면 무슨 일이 벌어지나요? 시니어 변별힌트: L = λW를 그대로 읽는다. 그리고 거기서 멈추면 절반이다 — 되먹임

λ는 그대로인데 W가 늘면 L이 비례해서 늘어난다.

평상시  500 TPS × 0.05s = 25개 필요, 풀 36개  -> 이용률 69%, 여유 있음
느린 쿼리로 점유 시간이 300ms가 되면
        500 TPS × 0.30s = 150개 필요, 풀은 36개  -> 즉시 고갈

여기서 멈추면 절반이다. 진짜 무서운 것은 되먹임이다.

W 증가 -> 필요 L 증가 -> 풀 고갈 -> 커넥션 대기 발생
      -> 대기 시간이 응답시간에 더해져 W가 더 증가 -> ...

7-2의 곡선이 말하는 그대로다 — 이용률이 1에 가까워지면 대기가 폭발하고, 그 대기가 다시 W를 밀어 올린다. 그래서 풀 크기 문제로 보이는 장애의 상당수가 실제로는 W 악화(느린 쿼리, 인덱스 누락, 외부 API 지연, 락 경합)가 원인이다.

그리고 W 악화는 풀 크기로 못 메운다. 위 예에서 300ms를 감당하려면 커넥션 150개가 필요한데, DB 상한이 17이라면 어떤 풀 크기로도 불가능하다. 진단 절차는 26-hikaricp-connection-pool-exhaustion.md가 다룬다.

톰캣 max-threads를 그냥 크게(예: 2,000) 잡으면 안 되나요? 필수힌트: 세 층위 — 자원 비용, 뒷단 전달, 그리고 "빨리 거절하는 것이 낫다"

(1) 자원 비용. 스레드당 스택이 수백 KB~2MB 예약되므로 2,000개면 수 GB의 주소 공간이다. 컨텍스트 스위칭 비용도 붙는다(6-2).

(2) 뒷단으로 과부하가 그대로 전달된다 — 이게 핵심이다. 9절에서 봤듯이 스레드를 넓게 열면 그 스레드들이 전부 커넥션을 요구하러 몰려간다. 처리 못 할 요청을 받아들이는 것은 문제를 뒤로 미루는 것이 아니라 더 나쁜 곳에서 터지게 하는 것이다.

(3) 그래서 빨리 거절하는 것이 낫다. 감당 가능한 만큼만 받고 나머지는 accept 큐 상한에서 거절해 503을 주는 편이, 전부 받아들여 30초 뒤 전면 타임아웃되는 것보다 낫다. 이것이 백프레셔의 관점이다 — 풀 크기의 상한은 제약이 아니라 신호 장치다(07-traffic-performance/16-backpressure-and-application-points.md).

여기서 한 걸음 더 나가면 가산점이다. 톰캣의 max-threads 200은 그 자체가 유입 제어(admission control) 장치였다. 아무도 그걸 백프레셔라고 부르지 않았지만, 시스템을 지켜주던 것은 그 숫자다. 다음 질문이 바로 이 지점을 건드린다.

가상 스레드(Java 21)를 켜면 이 산정 문제가 사라지나요? 시니어 변별힌트: 절반은 사라지고 절반은 그대로인데, 한 부분은 오히려 나빠진다

절반만 사라지고, 나머지 절반은 오히려 나빠진다. 세 칸으로 나눠 답한다.

사라지는 쪽 — 가상 스레드는 블로킹 시 캐리어 스레드를 반납하므로 스레드 개수가 사실상 제약이 아니게 된다. 톰캣 요청 스레드 산정 문제는 의미가 옅어진다. Spring Boot 3.2+에서 spring.threads.virtual.enabled=true 한 줄이면 켜진다.

그대로인 쪽 — DB 커넥션은 여전히 물리 자원이다. 한 줄 원리로 말하면 "가상 스레드는 기다리는 주체를 싸게 만들 뿐, 기다리는 대상의 개수를 늘리지 않는다." 스레드를 1만 개 띄워도 Hikari 커넥션 17개는 17개다. Little's law는 자원별로 성립하므로 스레드 계산식만 무의미해지고 커넥션 계산식은 그대로 남는다.

나빠지는 쪽 — 스레드풀이 암묵적으로 하던 유입 제어가 사라진다. 동시 요청 상한이 max-threads 200에서 max-connections 8,192로 뛰므로, 예전엔 문 앞에서 거절되던 요청이 전부 들어와 커넥션 풀 앞에서 30초를 기다린다. 빠른 실패가 느린 전멸로 바뀐다.

대응은 세마포어·Resilience4j Bulkhead로 문지기를 명시적으로 복원하고 connection-timeout을 짧게 잡는 것이다. 자세한 논의는 27-webflux-vs-mvc-threading-model.md(모델 비교와 유입 제어)와 01-java-kotlin/28-virtual-threads-pinning.md(동작 원리와 핀닝)에 있다.

Hikari의 minimumIdle은 어떻게 잡나요? 가산점힌트: 기본 동작이 무엇인지부터. 그리고 "커넥션을 새로 여는 비용"이 언제 청구되는지

HikariCP는 minimumIdle의 기본값을 maximumPoolSize와 같게 둔다. 즉 기본 동작은 고정 크기 풀이고, 이것이 공식 권장이기도 하다.

이유를 말할 수 있으면 좋다. 커넥션을 새로 여는 것은 TCP 핸드셰이크 + TLS + DB 인증이라 수십 ms가 드는 비싼 작업이다. 트래픽이 잠깐 줄었다고 커넥션을 닫아버리면, 다시 늘었을 때 가장 바쁜 순간에 커넥션을 새로 여느라 응답시간이 튄다. 풀을 고정 크기로 두면 그 지연이 애초에 발생하지 않는다.

minimumIdle을 낮추는 것이 의미 있는 경우는 8-3의 상황 — 인스턴스가 많아 DB의 max_connections가 빠듯할 때, 유휴 인스턴스가 커넥션을 붙들고 있지 않게 하려는 목적뿐이다. "메모리 아끼려고" 낮추는 것은 얻는 것 없이 지연만 사는 선택이다.

스레드 덤프에 RUNNABLE이 200개면 CPU가 포화된 건가요? 함정힌트: 상태 이름이 아니라 스택 최상단

아니다. 오히려 CPU 사용률이 0%에 가까울 수 있다. RUNNABLE은 "실행 중"과 "실행 가능"과 "네이티브 안에 들어가 있음"을 구분하지 않는 상태이고, 소켓 read 대기가 바로 그 네이티브 안이다. JVM은 네이티브 코드 안에서 OS가 스레드를 재웠는지 알 수 없으므로 RUNNABLE로 표시한다.

그래서 판단은 스택 최상단으로 한다. sun.nio.ch.Net.poll·SocketInputStream.read·PgStatement.executeQuery가 최상단이면 그건 대기이고, 애플리케이션 코드나 직렬화·암호화 루틴이 최상단이면 그때 비로소 연산이다.

교차 확인도 함께 말하면 좋다 — 스레드 덤프만 보지 말고 CPU 사용률 지표를 같이 본다. RUNNABLE 다수 + CPU 낮음 = I/O 대기(뒷단이 느리다), RUNNABLE 다수 + CPU 포화 = 진짜 CPU 바운드(6절의 상한). 이 두 갈래는 처방이 정반대다 — 전자는 스레드/커넥션과 뒷단 지연 문제, 후자는 스레드를 늘려도 소용없는 문제다.

connection-timeout을 30초에서 3초로 낮추면 실패가 오히려 늘어나는 것 아닌가요? 가산점힌트: "실패가 늘어난다"가 맞다. 그것이 목적이라는 것을 설명할 수 있는가

실패 건수는 늘어난다. 그리고 그것이 목적이다. 30초를 기다리는 동안 그 요청은 톰캣 스레드 하나를 30초간 점유한다(5절). 즉 기다림 자체가 자원 소모이고, 커넥션이 부족한 상황에서 오래 기다리는 것은 부족을 더 악화시킨다.

같은 사건을 두 가지로 세어보면 분명해진다. 30초 타임아웃에서는 사용자는 30초를 기다린 끝에 에러를 받고, 그 30초 동안 스레드가 묶여 다른 정상 요청까지 못 받는다. 3초 타임아웃에서는 실패를 3초 만에 돌려주고 스레드를 즉시 회수하므로, 같은 시간에 정상 처리되는 요청이 더 많아진다.

단, 함께 정해야 할 것이 있다. ① 타임아웃 값은 위쪽(클라이언트·게이트웨이) 타임아웃보다 짧아야 한다 — 그래야 우리 쪽이 먼저 포기하고 자원을 회수한다. ② 거절을 사용자에게 어떻게 보여줄지(재시도 안내·503)와 ③ 재시도가 몰려 2차 폭주를 만들지 않도록 백오프를 함께 설계한다. 이 관점 전체가 백프레셔다.

톰캣의 max-threads · max-connections · accept-count는 각각 무엇이 다른가요? 가산점힌트: "받아들이는 문 / 처리하는 일꾼 / 문 앞의 줄"로 나눠 그린다

세 값은 서로 다른 단계의 상한이고, 산정에서 헷갈리면 엉뚱한 값을 만진다.

  • max-connections — 동시에 받아들여 관리하는 연결(소켓)의 최대 개수. NIO 커넥터에서는 이 값이 크다(기본 8,192). "문의 폭"에 해당한다.
  • max-threads — 요청을 실제로 처리하는 워커 스레드의 최대 개수(기본 200). "일꾼 수"이고, 이 문서의 산정 대상이다.
  • accept-count — 일꾼이 전부 바쁠 때 OS 수준에서 대기시킬 연결 요청의 큐 길이. "문 앞에 세워둘 줄의 길이"이고, 이 줄까지 차면 새 연결은 거절된다.

산정 관점에서의 결론: Little's law로 계산하는 것은 max-threads다. max-connections는 "얼마나 많은 요청을 일단 붙잡아 둘 것인가"를, accept-count는 "넘치면 얼마나 줄을 세우고 언제 거절할 것인가"를 정한다.

여기서 가상 스레드 이야기와 연결된다 — 가상 스레드를 켜면 실질 동시 처리 상한이 max-threads에서 max-connections로 옮겨간다. 유입 제어를 하던 숫자가 200에서 8,192로 바뀌는 것이고, 그래서 문지기를 다른 수단으로 복원해야 한다.

W에 평균 대신 p99를 넣으면 풀이 과하게 커지지 않나요? 시니어 변별힌트: 두 값으로 각각 계산해 보고, 그 간격 자체를 정보로 읽는다

커진다. 그래서 하나만 쓰지 않고 둘 다 계산해 간격을 읽는다.

Little's law는 평균 W로 평균 L을 준다. 그러니 평균 기반 계산은 "평상시 필요한 개수"의 기준선이 되고, p95·p99 기반 계산은 "느린 요청까지 감당하려면 필요한 개수"의 상한선이 된다. 최종 c는 그 사이에서 ρ와 SLO로 정한다.

더 중요한 것은 두 값의 간격 자체가 진단 정보라는 점이다. 평균 100ms · p99 800ms처럼 8배 벌어져 있으면, 그것은 "풀을 8배로 잡아라"가 아니라 "꼬리 지연을 만드는 원인이 있다"는 신호다 — 느린 쿼리, 인덱스 누락, 특정 파라미터에서만 터지는 풀스캔, 커넥션 획득 대기 그 자체. 이 경우 올바른 처방은 c 확대가 아니라 꼬리 자르기(W 개선)다.

실무 절충안: λ는 피크 시간대 값으로, W는 같은 시간대의 평균으로 계산해 L을 뽑고, 꼬리의 두께를 ρ_target에 반영한다(p99/평균 비율이 크면 ρ를 0.5~0.6으로 더 보수적으로). 그리고 hikaricp.connections.usage 실측 분포로 이 가정을 다시 확인한다(10절).

풀을 늘렸는데 처리량이 그대로입니다. 어디를 봐야 하나요? 시니어 변별힌트: 이 문서에 나온 천장이 네 개다 — 차례로 지운다

"늘렸는데 안 오른다"는 것은 그 자원이 병목이 아니었다는 뜻이다. 이 문서에 나온 천장을 순서대로 지워나간다.

  • ① 다른 자원이 병목이다(9절). 톰캣을 늘렸는데 Hikari가 10이면 여전히 200 TPS다. 가장 좁은 자원의 λ_max를 다시 계산한다.
  • ② CPU 상한에 걸렸다(6절). CPU 사용률이 포화인데 TPS가 안 오른다면 스레드를 늘려도 소용없다. 요청당 CPU를 줄이거나 장비를 키운다.
  • ③ DB 안에서 막혔다(8절). 커넥션을 늘렸는데 usage(점유 시간)가 같이 늘었다면, DB가 경합으로 느려진 것이다 — 늘린 만큼 W가 늘어 λ = c/W가 제자리다. 이때는 줄이는 것이 답일 수 있다.
  • ④ 애초에 부하 생성기가 못 밀고 있다. 클라이언트 쪽 커넥션 수·스레드 수·keep-alive 설정 때문에 목표 λ가 실제로 걸리지 않은 경우가 의외로 흔하다. 서버 지표 이전에 부하 도구의 실제 전송 TPS부터 확인한다.

판별의 축은 하나다 — λ = c / W에서 c를 올렸는데 λ가 그대로면 W가 같이 올랐거나, 애초에 다른 곳에 더 낮은 천장이 있는 것이다. 이 한 줄로 네 갈래를 정리할 수 있다.

그럼 톰캣 스레드와 커넥션 수를 같게 맞춘 설정은 전부 틀린 건가요? 함정힌트: "같아지는 경우"가 있긴 하다 — 어떤 조건에서인가

"같게 맞춘다"가 목표가 되는 것이 틀렸다는 것이지, 결과적으로 두 숫자가 비슷해지는 상황 자체가 틀린 것은 아니다.

두 값이 실제로 가까워지는 조건은 W가 서로 비슷할 때다. 예컨대 응답시간의 거의 전부가 DB 구간인 단순 조회 API(역직렬화·직렬화 비용이 미미하고 외부 호출도 없는)라면 톰캣 W ≈ Hikari W가 되어 계산값도 가까워진다. 이 경우 "같은 숫자"는 우연이 아니라 계산 결과다.

그래서 답의 형식은 이렇게 된다 — "두 값을 맞추는 규칙은 없고, 각각 계산한 결과가 가까울 수는 있다." 반대로 외부 API 호출이 끼거나 응답 페이로드가 커서 전송 시간이 길면 두 W가 크게 벌어지고, 그때 같게 맞춘 설정은 반드시 한쪽을 낭비하거나 한쪽을 병목으로 만든다.

한 줄 요약
풀 크기는 Little's law(L = λ × W)로 자원별 점유 시간을 기준으로 계산한다 — 블로킹 MVC에서 톰캣 스레드는 전체 응답시간(100ms) 동안, Hikari 커넥션은 트랜잭션 구간(50ms) 동안만 묶이므로 500 TPS 서버에서 톰캣 50 · 커넥션 25라는 서로 다른 숫자가 나오고, 코어 수는 스레드 수의 기준이 아니라 CPU 연산 총량의 상한(요청당 5ms면 4코어 = 800 TPS)일 뿐이다. 계산값 L은 이용률 100%에 해당하므로 목표 이용률로 나눠 c = L/ρ로 여유를 만들되(ρ=0.7이면 1.43배 — 대기는 1/(1−ρ)로 폭발한다), 커넥션은 DB 쪽 상한 (DB 코어 × 2) + spindle과 앱 인스턴스 수를 곱한 총합에 다시 묶이며 둘 중 작은 쪽이 실질 상한이다. 그리고 자원은 연쇄로 묶여 있어 톰캣 200에 Hikari 10이면 서버 전체가 10/0.05 = 200 TPS에서 막히므로 풀 크기는 병목을 정하고 거기에 맞추는 것이고, 최종 숫자는 hikaricp.connections.pending(0 초과면 부족)과 hikaricp.connections.usage(실측 W)로 검증한다.
