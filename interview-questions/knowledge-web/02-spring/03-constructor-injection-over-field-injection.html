생성자 주입을 권장하는 이유
필드 주입 대비 — 컨벤션이 아니라 근거로

면접 질문: "생성자 주입을 권장하는 이유는 무엇인가요? (필드 주입 대비)"

핵심 관전 포인트 — 생성자 주입은 "의존성이 다 갖춰지지 않으면 객체 자체를 만들 수 없다"는 불변식을 자바 컴파일러가 강제하게 만드는 유일한 방식이다. 필드 주입은 스프링이 생성자가 끝난 뒤 리플렉션으로 private 필드에 값을 꽂아 넣는 방식이라 그 불변식이 없다 — 그래서 final을 붙일 수 없고, 컨테이너 밖에서는 필드가 전부 null인 반제품 객체가 만들어지며, 순환 참조가 껍데기끼리 이어붙어 조용히 성립하고, 의존성이 몇 개로 불어나든 겉으로 드러나지 않는다. 즉 권장 근거 네 가지(불변성 · 순환 참조 조기 발견 · 컨테이너 없는 단위 테스트 · 책임 비대화의 가시화)는 서로 다른 장점 넷이 아니라 "객체가 불완전한 상태로 존재할 수 있는가"라는 한 가지 질문에서 전부 파생된 결과다.
  • 1
    근거는 원래 하나다 — 생성자 주입은 의존성을 생성자 시그니처라는 공개 계약으로 선언해, 불완전한 객체가 존재할 수 있는 경로 자체를 컴파일러가 막게 만든다. 필드 주입은 그 계약을 클래스 안에 감추고 생성자가 끝난 뒤 리플렉션으로 채워지길 기대한다.
  • 2
    그 하나에서 네 가지가 파생된다 — 불·순·테·설: 불변(final 가능 → 싱글턴 빈이 공유해도 안전) · 순환 참조가 기동에서 즉시 드러남(껍데기를 못 만드니 BeanCurrentlyInCreationException) · 테스트에서 new OrderService(mock) 한 줄(컨테이너도 리플렉션도 불필요) · 설계 신호(파라미터 8개가 되면 보는 순간 불편해서 리팩터링 압력이 생김).
  • 3
    "길어서 못 쓴다"는 반론은 이미 해소됐다 — Spring 4.3부터 생성자가 하나면 @Autowired를 생략할 수 있고, Lombok @RequiredArgsConstructor나 Kotlin 주 생성자로 보일러플레이트가 사라진다. 단 Lombok을 쓰면 필드의 @Qualifier·@Value가 생성자 파라미터로 복사되지 않는 함정이 있어 lombok.config에 copyableAnnotations를 등록해 둔다.

0. 질문 + 출제 의도

질문: "생성자 주입을 권장하는 이유는 무엇인가요? (필드 주입 대비)"

출제 의도: 순환 참조의 조기 발견, 불변성, 테스트 시 목 주입 용이성까지 연결해 말하는지 본다. 컨벤션을 "팀 규칙이라서"가 아니라 근거로 이해하는 사람은 새로운 상황에서도 올바른 선택을 한다.

이 페이지가 겨냥하는 약점 세 가지 ① 장점을 네 개의 목록으로 외우는 것 → 1절에서 "불완전한 객체가 존재할 수 있는가"라는 한 뿌리에서 네 갈래가 갈라지는 도식을 먼저 세운다. 뿌리를 쥐면 하나를 잊어도 다시 유도할 수 있다.
② "필드 주입은 주입이 누락돼도 조용히 넘어간다"고 잘못 말하는 것 → 5절에서 정정한다. @Autowired는 기본이 required = true라 컨테이너 안에서는 둘 다 기동이 실패한다. 진짜 차이는 컨테이너 밖에서 난다.
③ "final을 못 붙인다"를 스프링의 제약으로 설명하는 것 → 4절에서 자바 언어 규칙(생성자 종료 시한)임을 시점 도식과 실제 컴파일 에러 메시지로 못 박는다.
한 문장 비유 — 엔진 없이 출고되는 자동차 생성자 주입은 엔진을 넣어야만 차가 조립 라인 밖으로 나오는 공장이다. "엔진 없는 완성차"라는 물건은 세상에 존재할 수 없다.  /  필드 주입은 빈 차체를 먼저 출고해 놓고, 정비공이 나중에 보닛을 강제로 열어(setAccessible(true)) 엔진을 밀어 넣는 공장이다. 그래서 ① 엔진 없는 차가 도로에 굴러다닐 수 있고(컨테이너 밖의 new), ② 두 대가 서로의 부품을 나눠 갖는 이상한 조립도 성립하며(순환 참조), ③ 보닛을 열 도구가 없는 사람은 그 차를 완성할 방법이 아예 없다(단위 테스트).

1. 한 뿌리에서 갈라진 네 근거 — 목록이 아니라 유도다

이 질문의 흔한 실패는 "불변성, 순환 참조, 테스트, 설계 신호" 네 단어를 순서 없이 나열하는 것이다. 외운 티가 나고, 하나를 잊으면 복구가 안 된다. 실제로는 네 개가 서로 독립적인 장점이 아니라 같은 뿌리에서 갈라진 가지다. 뿌리는 이 한 문장이다.

뿌리 문장 — 이것 하나만 쥐면 네 개가 유도된다

필드 주입에는 "의존성이 비어 있는 객체가 실제로 존재하는 구간"이 있고, 생성자 주입에는 없다

암기 장치 — 근거 4종은 "불 · 순 · 테 · 설"

불변(final)  ·  순환 조기 발견  ·  테스트 용이  ·  설계 신호

문장으로 이으면 이렇게 된다 — "불완전한 객체를 막으니, 순환이 드러나고, 테스트가 쉬워지고, 설계 냄새가 보인다." 네 단어가 인과로 이어져 있다는 점이 이 문장의 핵심이다.

2. 리플렉션 — 필드 주입이 실제로 하는 일

필드 주입 설명에 반드시 나오는 단어인데, 정의 없이 넘어가는 경우가 많다. 이 단어를 정의하지 못하면 뒤의 테스트 이야기(7절)가 통째로 설득력을 잃는다.

리플렉션(reflection)이란 실행 중에 클래스의 내부 정보(필드 목록, 메서드 목록, 애너테이션)를 뒤져 보고, 심지어 private 필드에도 값을 강제로 집어넣을 수 있게 해주는 자바 기능이다. 이름은 프로그램이 실행 도중 자기 자신을 거울에 비춰 들여다본다는 뜻에서 왔다.

스프링이 필드 주입을 처리할 때 실제로 하는 일이 이것이다. 스프링 내부의 AutowiredAnnotationBeanPostProcessor가 하는 일을 풀어 쓰면 대략 다음과 같다.

내부 동작 스프링이 @Autowired 필드에 값을 넣는 방법
Field field = OrderService.class.getDeclaredField("gateway");
field.setAccessible(true);          // private 접근 제한을 강제로 연다언어의 접근 제어를 우회하는 한 줄
field.set(orderServiceInstance, gateway);   // 값을 직접 꽂아 넣는다

setAccessible(true) 한 줄이 핵심이다. 자바 문법상 접근할 수 없는 곳에 값을 넣기 위해 언어의 접근 제어를 우회한다. 편리하지만, 이 우회가 없으면 그 객체를 완성할 방법이 없다는 뜻이기도 하다.

여기서 나오는 한 문장이 7절(테스트)까지 그대로 간다

필드 주입으로 짜인 클래스는 리플렉션 없이는 완성될 수 없는 클래스다

스프링 컨테이너 안에서는 이 사실이 보이지 않는다 — 컨테이너가 대신 리플렉션을 써 주기 때문이다. 컨테이너 밖으로 나가는 순간(테스트·수동 등록) 이 성질이 곧바로 비용으로 청구된다.

3. 시점 도식 — 값이 생성자 "안"에서 정해지는가, "밖"에서 꽂히는가

세 방식의 차이는 문법이 아니라 "객체가 만들어지는 시점 대비 값이 언제 들어가는가"에 있다. 이 시점 차이 하나에서 뒤의 모든 결론이 나온다.

3-1. 코드로 보는 대비 — 계약을 드러내는가, 감추는가

before 필드 주입 — 세 줄로 짧아 보이지만 계약을 숨긴다
@Service
public class OrderService {
    @Autowired
    private PaymentGateway gateway;final 불가

    // 이 클래스의 생성자 시그니처는 OrderService() 다.
    // 겉보기 계약은 "아무것도 없어도 만들 수 있다" 인데,
    // 실제로는 거짓이다 — 스프링이 몰래 채워주기를
    // 기대하고 있을 뿐이다.
}
after 생성자 주입 — 의존성이 공개 계약에 드러난다
@Service
public class OrderService {
    private final PaymentGateway gateway;불변 확정

    // "나를 만들려면 PaymentGateway 가 반드시 있어야 한다"
    // 를 시그니처로 선언한다. 이 선언은 문서가 아니라
    // 컴파일러가 검사하는 규칙이다.
    public OrderService(PaymentGateway gateway) {
        this.gateway = gateway;
    }
}

핵심 차이는 의존성이 어디에 드러나는가다. 생성자 주입은 "이 객체를 만들려면 이것들이 반드시 필요하다"를 생성자 시그니처라는 공개 계약으로 선언한다. 필드 주입은 그 계약을 클래스 내부에 감추고, 스프링이 리플렉션으로 몰래 채워주기를 기대한다.

4. 근거 ① 불변 — 왜 필드 주입은 final을 못 붙이는가

먼저 사실 확인부터. 필드 주입에 final을 붙이면 스프링이 실패하는 게 아니라 컴파일 자체가 안 된다. 이 구분을 못 하면 "스프링이 그렇게 만들어놔서요"라는 부정확한 답이 나온다.

컴파일 실패 스프링이 뜨기도 전에 javac가 거부한다
@Service
public class OrderService {
    @Autowired
    private final PaymentGateway gateway;   // 컴파일 에러스프링과 무관한 자바 규칙
}
javac 21 실제 확인한 에러 메시지
error: variable gateway not initialized in the default constructor
    private final PaymentGateway gateway;
                                 ^

(생성자를 명시적으로 쓰고 거기서 대입하지 않은 경우에는 메시지가 이렇게 나온다)
error: variable gateway might not have been initialized
    public OrderService() { }
                          ^

이유는 스프링과 무관한 자바 언어 규칙이다. final 필드는 생성자가 끝나는 순간까지 값이 정해져 있어야 한다. 컴파일러는 모든 생성자를 훑어 "이 경로로 나가면 final 필드가 아직 비어 있다"는 경우가 하나라도 있으면 컴파일을 거부한다.

비유 — 시험 종료 종 생성자 종료가 시험 종료 종이고, final 필드는 종이 울리기 전에 반드시 채워야 하는 답안이다. 생성자 주입은 종이 울리기 전에 답을 적는다. 필드 주입은 종이 울린 뒤에 감독관(스프링)이 답안지를 걷어가 대신 적어준다 — 결과가 맞고 틀리고를 떠나 규칙상 자격 미달이라, 채점(컴파일)조차 되지 않는다.

한 문장으로 봉인

final을 못 쓰는 것은 스프링의 제약이 아니라 순서의 필연이다

필드 주입이 값을 꽂는 시점이 생성자가 끝난 뒤이기 때문에, 컴파일러가 요구하는 마감 시한을 원천적으로 지킬 수 없다(3절 도식의 "선 오른쪽").

4-1. 그럼 final이 없으면 무슨 사고가 나는가 — 두 가지

1
나중에 누가 바꿔 끼울 수 있다. final이 아닌 필드는 클래스 안 어디서든 재대입할 수 있고, 밖에서도 리플렉션으로 바꿀 수 있다. 실제로 다음 같은 코드가 만들어진다.
실패 패턴 "테스트에서만 잠깐 바꾸려고" 열어둔 통로가 프로덕션에 남는다
@Service
public class OrderService {
    @Autowired
    private PaymentGateway gateway;

    // 처음에는 테스트 편의로 추가됐지만, 일단 열리면 프로덕션 코드에서도 불린다.
    public void setGateway(PaymentGateway gateway) { this.gateway = gateway; }싱글턴 빈의 상태가 런타임에 바뀐다
    // 그러면 "지금 이 싱글턴 빈의 gateway 가 무엇인지"를 시점마다 따져야 한다.
}

여기서 02번 문서의 싱글턴 이야기와 만난다. 서비스 빈은 싱글턴이라 모든 요청 스레드가 그 인스턴스 하나를 공유한다. 어떤 요청 처리 중에 이 필드가 바뀌면 그 순간 다른 스레드들의 동작이 함께 바뀐다. final은 "이 필드는 만들어진 뒤 절대 안 바뀐다"를 컴파일러가 보증하게 만들어, 싱글턴 빈이 공유해도 안전한 유일한 형태를 강제한다.

2
안전한 발행(safe publication) 보장을 잃는다. 가산점 자바 메모리 모델은 final 필드에 특별한 보장을 준다 — 생성자 안에서 final 필드에 쓴 값은, 생성자가 끝난 뒤 그 객체 참조를 받은 다른 스레드에게 반드시 올바르게 보인다. 별도 동기화가 없어도 그렇다. final이 아닌 필드에는 이 보장이 없어서, 이론적으로는 다른 스레드가 초기화 이전의 null을 볼 수도 있다.
실제 스프링 애플리케이션에서 이것이 드러나는 일은 드물다 — 컨테이너 기동이 끝난 뒤에 요청이 들어오므로 기동 자체가 사실상 하나의 큰 동기화 지점 역할을 하기 때문이다. 그래도 final이 왜 동시성 관점에서도 이득인지를 말할 수 있으면 깊이가 드러난다.

5. 오해 정정 — 실패 시점은 같다, 진짜 차이는 컨테이너 "밖"이다 함정

흔히 하는 부정확한 설명

"필드 주입은 주입이 빠져도 조용히 넘어가서 나중에 NPE가 난다"

정확하지 않다. @Autowired는 기본값이 required = true이므로, 주입할 빈을 못 찾으면 필드 주입이든 생성자 주입이든 똑같이 기동이 실패한다. 둘 다 UnsatisfiedDependencyException으로 애플리케이션이 안 뜬다. 컨테이너 안에서는 이 점에 차이가 없다.

면접에서 이 문장을 그대로 말하면 "실제로 겪어보지 않고 블로그를 외웠다"는 인상을 준다. 진짜 차이는 컨테이너 밖에서 드러난다.

필드 주입 컴파일러가 이것을 막지 못한다
OrderService service = new OrderService();컴파일 통과
// 객체도 만들어진다. 그런데 gateway 는 null 이다.

service.placeOrder(order);
// -> 첫 호출에서 NullPointerException
//    스택트레이스는 placeOrder 안쪽을 가리키므로,
//    진짜 원인("주입을 안 했다")이 한 겹 가려진다.
생성자 주입 애초에 이 코드가 컴파일되지 않는다
OrderService service = new OrderService();컴파일 에러
// error: constructor OrderService in class OrderService
//        cannot be applied to given types;
//   required: PaymentGateway
//   found:    no arguments

// -> 불완전한 객체를 만들려는 시도 자체가
//    컴파일 단계에서 차단된다.

5-1. 이 차이가 실무에서 나타나는 자리 셋

① 테스트 코드
new OrderService()로 만들어 놓고 필드 채우는 것을 잊으면, 테스트가 NPE로 실패하며 진짜 원인이 가려진다.
② @Configuration 수동 등록
new로 빈을 만들어 등록하는 코드에서 세팅을 빠뜨리면 그대로 반제품이 빈으로 올라간다.
③ 선택적 의존성
@Autowired(required = false)는 빈이 없어도 기동된다. 정말로 null인 필드를 들고 운영에 나간다.

이 절의 결론 — 답변에서 이 문장으로 바꿔 말한다

생성자 주입의 진짜 값은 "기동 시점에 실패한다"가 아니라
"불완전한 객체가 존재할 수 있는 경로를 컴파일러가 전부 막는다"는 것

실패 시점을 앞당기는 정도가 아니라, 잘못된 상태 자체를 표현 불가능(unrepresentable)하게 만든다. 이 표현을 쓰면 "실패를 빨리 발견한다"만 말하는 답변과 확실히 갈린다.

6. 근거 ② 순환 참조 — 왜 생성자 주입에서만 조기에 드러나는가

A가 B를 필요로 하고 B가 A를 필요로 하는 구조를 순환 참조라고 한다. 두 방식에서 컨테이너가 무엇을 할 수 있는지가 갈린다.

여기서 반드시 붙여야 하는 판단 한 줄 기동이 되는 쪽이 좋은 게 아니다. 순환 참조는 대부분 책임 분배가 잘못됐다는 증상이므로, 조용히 굴러가는 것보다 기동 실패로 드러나는 편이 낫다. 숨은 채로 굴러가면 나중에 호출 순서에 따라 null을 보거나, 리팩터링 중에 정체 모를 초기화 순서 버그로 되돌아온다.

버전 사실 — 프레임워크가 이미 생성자 주입의 관점을 채택했다

Spring Boot 2.6부터 순환 참조가 기본적으로 금지
필드 주입이라도 기동이 실패하며, spring.main.allow-circular-references=true를 명시해야 예전처럼 동작한다

Boot 3.x도 이 기본값을 유지한다. 즉 프레임워크 스스로 "순환은 허용할 상태가 아니라 오류다"라는 생성자 주입의 관점을 채택한 것이다. 이 사실을 덧붙이면 단순한 취향 논쟁이 아님을 보일 수 있다.

7. 근거 ③ 테스트 — mock을 넣을 "자리"가 있는가

실무에서 체감이 가장 큰 차이다. 2절에서 본 "리플렉션 없이는 완성될 수 없는 클래스"라는 성질이 여기서 곧바로 비용으로 돌아온다. 필드 주입된 클래스를 단위 테스트하려면 정상적인 자바 문법으로는 방법이 없고, 남는 선택지는 둘뿐이다.

선택지 ① 테스트도 리플렉션을 쓴다

OrderService service = new OrderService();
ReflectionTestUtils.setField(service, "gateway", mock(...));문자열 결합
  • 필드명을 문자열 "gateway"로 지정한다는 점이 문제다.
  • 나중에 필드명을 paymentGateway로 바꾸면 컴파일은 멀쩡히 통과하고, 테스트는 런타임에 IllegalArgumentException으로 깨진다.
  • IDE의 리네임 리팩터링도 이 문자열은 따라오지 못한다.

선택지 ② 스프링 컨테이너를 띄운다

@SpringBootTest
class OrderServiceTest {
    @Autowired OrderService service;
    @MockitoBean PaymentGateway gateway;전체 기동
}
  • 메서드 하나 검증하려고 애플리케이션 전체를 기동한다.
  • 수 초 걸리는 기동이 테스트 스위트마다 반복되며 피드백 루프가 무너진다.
  • 결국 아무도 로컬에서 테스트를 돌리지 않게 된다.
after 생성자 주입 — 컨테이너도 리플렉션도 없이 끝난다
PaymentGateway fake = mock(PaymentGateway.class);
when(fake.pay(any())).thenReturn(PaymentResult.success());

OrderService service = new OrderService(fake);   // 그냥 new공개 계약만 사용
service.placeOrder(order);                        // 밀리초 단위로 끝나는 단위 테스트

테스트 가능성의 분기점 — 한 줄로 압축

"컨테이너 없이 인스턴스화할 수 있는가"가 테스트 가능성의 분기점이다

생성자 주입은 테스트 코드가 프로덕션 코드와 똑같은 공개 계약(생성자)만 사용하게 만든다. 테스트가 클래스 내부 구현(필드명)이나 프레임워크(컨테이너 기동)에 기대지 않으므로, 리팩터링에 깨지지 않고 빠르다.

한 걸음 더 — 주입 방식 하나가 팀의 테스트 문화를 끌고 간다 필드 주입이 퍼진 코드베이스는 필연적으로 통합 테스트 위주가 된다(선택지 ②밖에 남지 않으므로). 그러면 전체 테스트 시간이 늘어 아무도 로컬에서 테스트를 돌리지 않게 되고, 결국 CI에서만 늦게 발견되는 구조가 굳는다. 그래서 필드 주입을 없애야 할 이유를 "@SpringBootTest 없이 테스트를 짤 수 있게 하기 위함"이라고 말하면 설득력이 크다.

8. 근거 ④ 설계 신호 — 나쁜 냄새를 숨기지 못하게 한다

의존성이 8개인 클래스를 두 방식으로 써 보면 차이가 눈에 보인다.

필드 주입 8줄이 조용히 늘어난다 — 아무도 불편하지 않다
@Service
public class OrderService {
    @Autowired private PaymentGateway gateway;
    @Autowired private OrderRepository orderRepository;
    @Autowired private CouponService couponService;
    @Autowired private PointService pointService;
    @Autowired private StockService stockService;
    @Autowired private NotificationService notificationService;
    @Autowired private AuditLogger auditLogger;
    @Autowired private ShippingClient shippingClient;한 줄 추가에 아무 저항이 없다
}
생성자 주입 파라미터 8개짜리 생성자 — 보는 순간 불편하다
public OrderService(PaymentGateway gateway,
                    OrderRepository orderRepository,
                    CouponService couponService,
                    PointService pointService,
                    StockService stockService,
                    NotificationService notificationService,
                    AuditLogger auditLogger,
                    ShippingClient shippingClient) { ... }이 불편함이 곧 설계 경보다

이 눈에 보이는 고통이 "이 클래스가 책임을 너무 많이 진 것 아닌가(SRP 위반)"를 묻게 만들고, 리팩터링을 촉발하는 압력으로 작동한다. 필드 주입은 그 신호를 무음 처리한다 — @Autowired 한 줄을 더 붙이는 데는 아무 저항이 없기 때문이다.

이 절의 한 문장 — 뒤집어 말하는 것이 포인트

생성자 주입의 "불편함"은 결함이 아니라 의도된 기능(feature)이다

설계가 나빠지고 있다는 사실을 코드가 스스로 드러내게 만드는 장치다. 그래서 "롬복으로 가려서 계속 간다"는 답은 감점이다 — 네 번째 장점을 스스로 무력화하는 선택이기 때문이다.

8-1. 그래서 파라미터가 10개가 되면 — 묶어서 뽑아낸다

9. 실무 작성법 — 보일러플레이트는 도구로 지우되, 함정은 알고 지운다

9-1. @Autowired는 생략할 수 있다

버전 규칙

Spring 4.3부터는 클래스에 생성자가 하나뿐이면 그 생성자에 @Autowired를 붙이지 않아도
스프링이 주입 대상으로 인식한다

생성자가 둘 이상이면 어느 것을 쓸지 알 수 없으므로, 그때는 사용할 생성자에 @Autowired를 명시해야 한다.

권장 애너테이션 없이도 주입된다
@Service
public class OrderService {
    private final PaymentGateway gateway;

    // @Autowired 없음. 생성자가 하나뿐이므로 스프링이 알아서 이 생성자를 쓴다.
    public OrderService(PaymentGateway gateway) { this.gateway = gateway; }스프링 애너테이션 0개
}

부수 효과가 하나 있다. 이 규칙 덕분에 프로덕션 코드에서 스프링 애너테이션이 하나 줄어든다. 클래스가 프레임워크에 덜 묶일수록 순수 자바로 테스트하기도, 나중에 다른 곳에서 재사용하기도 쉬워진다.

9-2. Lombok / Kotlin으로 생성자를 지운다

"생성자 코드가 길어진다"는 반론은 도구로 해소된다.

Java Lombok
// @RequiredArgsConstructor 는 final 필드(그리고
// @NonNull 필드)를 파라미터로 받는 생성자를
// 컴파일 시점에 만들어준다. 생성자가 하나뿐이므로
// @Autowired 도 불필요하다.
@Service
@RequiredArgsConstructor
public class OrderService {
    private final PaymentGateway gateway;
    private final OrderRepository orderRepository;
}
Kotlin 주 생성자
// 주 생성자 문법이라 애초에 보일러플레이트가 없다.
// val 이 곧 final 이므로 불변도 기본값이다.
@Service
class OrderService(
    private val gateway: PaymentGateway,
    private val orderRepository: OrderRepository,
)

반론 봉인

결과적으로 필드 주입보다 코드가 길지 않다 — "짧아서 필드 주입을 쓴다"는 이유는 성립하지 않는다

9-3. @RequiredArgsConstructor의 함정 — @Qualifier가 사라진다 함정

Lombok을 쓸 때 반드시 알아야 하는 함정이 하나 있다. Lombok이 생성한 생성자의 파라미터에는 필드에 붙은 @Qualifier가 기본적으로 복사되지 않는다.

먼저 @Qualifier가 무엇인지 같은 타입의 빈이 둘 이상일 때 "이 중 어느 것을 주입할지"를 이름으로 지정하는 애너테이션이다. 타입만으로는 후보가 좁혀지지 않으니 이름표를 하나 더 다는 것이다.
고침 ② 이 클래스만 Lombok을 포기하고 생성자를 직접 쓴다
@Service
public class OrderService {
    private final PaymentGateway gateway;

    public OrderService(@Qualifier("tossGateway") PaymentGateway gateway) {
        this.gateway = gateway;   // 파라미터에 직접 붙였으므로 의도가 그대로 전달된다
    }
}

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

한 축으로 압축하면?
값이 생성자 "안"에서 정해지는가, "밖"에서 꽂히는가. 네 결론이 전부 여기서 유도된다.
근거 4종은?
불·순·테·설 — 불완전한 객체를 막으니 순환이 드러나고 테스트가 쉬워지고 설계 냄새가 보인다.
왜 final을 못 붙이나?
자바 규칙이다 — final은 생성자 종료 시한까지 채워져야 하는데 필드 주입은 그 뒤에 꽂는다. 스프링이 아니라 컴파일이 거부.
주입 누락 시 실패 시점 차이는?
컨테이너 안에서는 차이가 없다 — required = true라 둘 다 기동 실패. 진짜 차이는 컨테이너 밖(new).
생성자 주입의 진짜 값은?
실패를 앞당기는 게 아니라 잘못된 상태를 표현 불가능하게 만드는 것.
필드 주입에서 순환이 성립하는 이유는?
껍데기를 먼저 만들 수 있어서. 스프링이 3단계 캐시로 미완성 참조를 반대편에 빌려준다.
순환 참조와 Boot 버전 사실은?
Boot 2.6부터 기본 금지(3.x 유지). 되살리려면 spring.main.allow-circular-references=true.
테스트 가능성의 분기점은?
컨테이너 없이 인스턴스화할 수 있는가. 되면 밀리초 단위 단위 테스트, 안 되면 리플렉션 or @SpringBootTest.
@Autowired 생략 조건은?
Spring 4.3+ & 생성자가 하나뿐일 때. 둘 이상이면 쓸 생성자에 명시.
Lombok 함정은?
@RequiredArgsConstructor가 @Qualifier·@Value를 파라미터로 복사하지 않는다 → lombok.config의 copyableAnnotations.
파라미터 10개면?
주입 방식이 아니라 클래스 분리 신호. 검증 묶음은 Validator로, 사후 효과는 이벤트로.
final의 동시성 이득은?
안전한 발행(safe publication) — 생성자에서 쓴 final 값은 동기화 없이도 다른 스레드에 올바르게 보인다.
필드 주입이 허용되는 자리는?
테스트 클래스. 프레임워크가 인스턴스를 만들어주고, new로 재사용할 대상도 아니다. 프로덕션은 예외 없음.
순환이 났을 때 첫 답은?
@Lazy가 아니다. ① 제3의 빈 추출 ② 이벤트로 방향 끊기 ③ 경계 재검토 → 그래도 불가피하면 @Lazy.

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

생성자 주입을 권장하는 이유를 말해보세요. 필수힌트: 네 개를 나열하지 말고, 하나의 불변식에서 넷을 유도한다

먼저 뿌리 문장부터 놓는다 — 생성자 주입은 "의존성이 다 갖춰지지 않으면 객체 자체를 만들 수 없다"는 불변식을 자바 컴파일러가 강제하게 만드는 유일한 방식입니다. 필드 주입은 스프링이 생성자가 끝난 뒤 리플렉션으로 private 필드에 값을 꽂아 넣는 방식이라 그 불변식이 없습니다.

그 하나에서 네 가지가 파생됩니다(불·순·테·설). ① 불변 — final을 붙일 수 있어 싱글턴 빈이 공유해도 안전한 형태가 강제됩니다. ② 순환 참조 — 어느 쪽도 먼저 만들 수 없으므로 BeanCurrentlyInCreationException으로 기동에서 즉시 드러납니다. ③ 테스트 — new OrderService(mock) 한 줄로 컨테이너도 리플렉션도 없이 끝납니다. ④ 설계 신호 — 파라미터가 8개가 되면 보는 순간 불편해서 리팩터링 압력이 생깁니다.

마무리로 정확도를 한 칸 올리는 문장을 붙입니다 — "생성자 주입의 값은 실패 시점을 앞당기는 게 아니라, 불완전한 객체가 존재할 수 있는 경로를 컴파일러가 전부 막는 것"입니다.

"필드 주입은 주입이 누락돼도 조용히 넘어가서 나중에 NPE가 난다" — 맞는 설명인가요? 함정힌트: @Autowired의 기본값부터 확인한다. 그리고 "안"과 "밖"을 나눈다

정확하지 않습니다. @Autowired는 기본값이 required = true이므로, 주입할 빈을 못 찾으면 필드 주입이든 생성자 주입이든 똑같이 UnsatisfiedDependencyException으로 기동이 실패합니다. 컨테이너 안에서는 차이가 없습니다.

진짜 차이는 컨테이너 밖에서 납니다. 필드 주입된 클래스는 new OrderService()가 컴파일도 되고 객체도 만들어지지만 gateway는 null이라, 첫 호출에서 NPE가 나고 스택트레이스가 진짜 원인을 가립니다. 생성자 주입이면 그 코드가 아예 컴파일되지 않습니다(required: PaymentGateway / found: no arguments).

실무에서 이게 나타나는 자리는 셋입니다 — 테스트 코드, @Configuration에서 new로 수동 등록, 그리고 @Autowired(required = false) 같은 선택적 의존성(이 경우는 빈이 없어도 기동되므로 정말로 null인 필드를 들고 운영에 나갑니다).

그럼 setter 주입은 언제 쓰나요? 필수힌트: 원칙을 말한 뒤 "그런데 그 자리가 실무에선 거의 비어 있다"까지

원칙은 "필수 의존성은 생성자, 선택적 의존성은 setter"입니다. 없어도 객체가 성립하는 의존성이나 런타임에 교체될 수 있는 의존성에 씁니다.

다만 실무에서 이 자리는 거의 비어 있다는 점을 함께 말하는 게 좋습니다. 선택적 의존성 자체가 드물고, 그마저도 대안이 있기 때문입니다.

  • 있으면 쓰고 없으면 넘어가는 의존성은 ObjectProvider<T>를 생성자로 받아 getIfAvailable()로 처리하면 됩니다. 그러면 "없을 수도 있다"는 사실이 타입에 드러납니다.
  • 기본 구현이 있는 경우라면 기본값을 넣은 생성자를 두는 편이 낫습니다.

setter 주입이 실제로 필요한 경우는 프레임워크가 객체를 만든 뒤에 값을 넣어줘야 하는 레거시 연동 정도입니다.

필드 주입을 써도 되는 자리는 정말 하나도 없나요?힌트: 예외를 하나 인정하되, 그 예외가 왜 안전한지 근거를 댄다

테스트 클래스 안은 예외로 볼 수 있습니다. JUnit 5와 스프링 테스트 컨텍스트가 테스트 인스턴스를 직접 만들어주므로, 테스트 클래스에서 @Autowired 필드를 쓰는 것은 관행이고 문제가 되지 않습니다. 테스트 클래스는 new로 만들어 재사용할 대상이 아니고, 순환 참조나 불변성 이슈도 없기 때문입니다.

프로덕션 코드에서는 예외를 두지 않는 편이 낫습니다. "이 클래스만은 괜찮다"는 판단이 쌓이면 결국 컨벤션이 무너지기 때문입니다. 그리고 근거를 하나 더 붙이면 좋습니다 — 필드 주입이 퍼진 코드베이스는 필연적으로 @SpringBootTest 위주의 통합 테스트가 되고, 그러면 전체 테스트 시간이 늘어 아무도 로컬에서 테스트를 돌리지 않게 됩니다. 주입 방식 하나가 팀의 테스트 문화까지 끌고 갑니다.

생성자 주입인데 순환 참조가 발생하면 어떻게 해결하나요? 시니어 변별힌트: 첫 답으로 @Lazy를 꺼내면 감점이다. 설계 수정 세 가지를 먼저

@Lazy를 한쪽에 붙이면 그 자리에 프록시가 주입되어 기동은 통과합니다. 하지만 이것은 증상을 덮는 임시방편입니다. 순환은 대부분 책임 분배가 잘못됐다는 신호이므로, 설계를 고치는 답이 먼저 나와야 합니다.

1. 공통 로직을 제3의 빈으로 추출한다. A와 B가 서로 부르는 부분을 C로 빼면 A → C ← B의 단방향이 됩니다. 순환의 원인이 "두 클래스가 같은 일을 서로에게 부탁하고 있었다"인 경우가 가장 많고, 이 방법이 대개 정답입니다.

2. 이벤트로 방향을 끊는다. B가 A를 직접 호출하는 대신 ApplicationEventPublisher로 이벤트를 발행하고 A가 그것을 구독하게 하면, B는 A를 알 필요가 없어져 컴파일 의존이 한쪽으로만 남습니다. "주문이 완료되면 알림을 보낸다" 같은 부수 효과 성격의 호출에 특히 잘 맞습니다.

3. 경계 자체를 재검토한다. 두 클래스가 사실은 한 책임을 억지로 나눠 가진 것은 아닌지 봅니다. 이 경우 답은 합치는 것입니다.

"@Lazy로 돌리겠다"가 첫 답으로 나오면 설계 감각을 의심받습니다. 순서를 "설계 수정 → 그래도 불가피하면 @Lazy"로 두어야 합니다.

@Lazy는 어떤 원리로 순환을 통과시키나요? 가산점힌트: 그 자리에 들어가는 것이 "진짜 빈"이 아니다

실제 빈 대신 프록시(대역 객체)가 먼저 주입되기 때문입니다. 생성자 파라미터에 @Lazy를 붙이면 스프링은 그 자리에 같은 타입인 척하는 프록시를 넣어 일단 객체 생성을 완료시키고, 그 의존성의 메서드가 처음 호출되는 순간에 진짜 빈을 컨테이너에서 찾아 위임합니다.

즉 "객체를 만드는 시점"과 "진짜 의존성이 필요한 시점"을 분리해서 사이클을 끊는 것입니다. 6절 도식으로 말하면 "B 없이는 new A(...)를 못 한다"는 막다른 길을, 가짜 B를 하나 끼워 넣어 우회하는 셈입니다.

그래서 한계도 분명합니다 — 순환이라는 설계 사실은 그대로 남고, 호출 흐름에 프록시 한 겹이 끼어 디버깅이 어려워집니다. 도구가 있다는 것과 그것을 첫 답으로 꺼내는 것은 다릅니다.

생성자 파라미터가 10개가 됐습니다. 어떻게 하시겠어요? 필수힌트: "주입 방식을 바꾼다"가 아니다. 신호에 응답한다

주입 방식을 바꿀 문제가 아니라 클래스 분리 신호로 읽습니다. 8절에서 말한 "눈에 보이는 고통"이 제 역할을 하고 있는 상황이므로, 그 신호에 응답하는 것이 맞습니다.

구체적으로는 파라미터들을 용도별로 묶어봅니다. 보통 2~3개의 응집된 덩어리가 나옵니다 — 예컨대 [주문 검증] couponService·pointService·stockService → OrderValidator로 추출, [결제] gateway·orderRepo → OrderService에 남김, [사후 처리] notificationService·auditLogger·shippingClient → 이벤트 리스너로 분리. 결과는 OrderService(gateway, orderRepo, orderValidator)로 파라미터 3개입니다.

특히 세 번째 덩어리는 대개 "주문 완료 이후에 일어나는 부수 효과"라서 ApplicationEventPublisher로 밀어내기 좋습니다. "롬복으로 가려서 계속 간다"는 답은 감점 요인입니다 — 생성자 주입의 네 번째 장점을 스스로 무력화하는 선택이기 때문입니다.

그런데 @RequiredArgsConstructor를 쓰면 파라미터가 안 보이는데, 설계 신호가 사라진 것 아닌가요? 시니어 변별힌트: 신호가 "사라진다"와 "약해진다"는 다르다. 그리고 무엇으로 보완할지

신호가 완전히 사라지지는 않습니다. Lombok이 만드는 생성자의 파라미터 목록은 정확히 final 필드 목록이므로, 필드가 10줄이면 파라미터도 10개라는 사실이 클래스 상단에 그대로 남습니다. 다만 "긴 생성자를 직접 타이핑하는 고통"이 사라지므로 체감 압력이 약해지는 것은 사실입니다.

그래서 답은 "둘 다 취한다"가 됩니다 — 보일러플레이트는 도구로 지우되, 압력은 다른 장치로 복원합니다. 코드 리뷰에서 필드 수 상한을 보는 것, 정적 분석 규칙으로 의존성 개수 임계값을 두는 것이 그 장치입니다.

핵심은 Lombok을 쓰느냐가 아니라, 늘어난 의존성을 보고 "이 클래스가 책임을 너무 많이 지고 있다"고 판단하느냐입니다. 도구가 고통을 줄여준 만큼, 판단을 사람이 채워야 합니다.

Spring Boot 2.6부터는 필드 주입이어도 순환 참조가 기동 실패하는데, 그럼 생성자 주입의 이점 하나가 사라진 것 아닌가요? 가산점힌트: "프레임워크가 왜 그 기본값을 택했는가"로 되돌린다

부분적으로 맞지만, 결론은 반대입니다. Boot 2.6부터 순환 참조가 기본 금지되고 3.x도 이 기본값을 유지하는 것은, 프레임워크 스스로 "순환은 허용할 상태가 아니라 오류다"라는 생성자 주입의 관점을 채택했다는 뜻입니다. 생성자 주입의 판단이 표준이 된 것이지 이점이 사라진 게 아닙니다.

또한 탐지 방식이 다릅니다. 필드 주입에서의 차단은 컨테이너가 사후에 검사해서 막아주는 것이라 spring.main.allow-circular-references=true 한 줄로 되살릴 수 있습니다. 생성자 주입에서는 그 플래그를 켜도 여전히 실패합니다 — 컨테이너가 관대해지고 말고를 떠나 객체를 만드는 것 자체가 논리적으로 불가능하기 때문입니다.

그리고 나머지 세 이점(불변 · 테스트 · 설계 신호)은 버전과 무관하게 그대로입니다. 특히 컨테이너 밖에서 new로 반제품이 만들어지는 문제는 어떤 설정으로도 막을 수 없습니다.

생성자가 두 개 이상이면 스프링은 어느 것으로 주입하나요?힌트: 4.3 규칙의 전제 조건을 다시 읽는다

Spring 4.3부터 @Autowired를 생략할 수 있는 것은 "생성자가 하나뿐일 때"입니다. 후보가 둘 이상이면 스프링은 어느 것을 써야 할지 알 수 없으므로, 사용할 생성자에 @Autowired를 명시해야 합니다.

실무적으로는 애초에 생성자를 여러 개 두지 않는 편이 낫습니다. 생성자가 여러 개라는 것은 대개 "이 객체가 여러 가지 다른 상태로 만들어질 수 있다"는 뜻인데, 스프링 빈은 기동 시 한 번 만들어져 고정되는 객체이므로 그런 유연성이 필요할 이유가 거의 없습니다. 생성자를 하나로 유지하면 @Autowired도 지울 수 있어 프로덕션 코드에서 스프링 애너테이션이 하나 더 줄어듭니다.

Kotlin에서 @Autowired lateinit var는 어떤가요? 함정힌트: 자바 필드 주입의 문제 중 무엇이 그대로 남는지 하나씩 대응시켜 본다

Kotlin판 필드 주입이라 같은 문제를 그대로 안습니다. lateinit은 var에만 붙일 수 있으므로 val(자바의 final에 해당)을 포기해야 하고, 그 결과 불변 보장과 안전한 발행 이점이 사라집니다. 컨테이너 밖에서 OrderService()로 만들면 초기화 전 접근 예외(UninitializedPropertyAccessException)가 나므로, "반제품 객체가 실재하는 구간"도 그대로 있습니다.

Kotlin은 오히려 주 생성자 문법 덕분에 생성자 주입의 보일러플레이트가 애초에 없습니다 — class OrderService(private val gateway: PaymentGateway) 한 줄이면 끝이라, 필드 주입을 택할 이유가 자바보다도 적습니다.

final을 붙이는 게 동시성에도 도움이 되나요? 가산점힌트: 자바 메모리 모델이 final에만 주는 보장이 있다

됩니다. 자바 메모리 모델은 생성자 안에서 final 필드에 쓴 값은, 생성자가 끝난 뒤 그 객체 참조를 받은 다른 스레드에게 반드시 올바르게 보인다고 보장합니다. 이를 안전한 발행(safe publication)이라 부르고, 별도의 synchronized나 volatile 없이도 성립합니다.

이 보장은 final이 아닌 필드에는 없습니다. 이론적으로는 다른 스레드가 초기화되기 전의 null을 볼 수 있는 여지가 남습니다.

스프링 애플리케이션에서 이 차이가 실제 버그로 나타나는 일은 드뭅니다 — 컨테이너가 모든 빈을 만들고 연결한 뒤에야 요청 처리가 시작되므로, 사실상 기동이 하나의 큰 동기화 지점 역할을 하기 때문입니다. 그래도 이 사실을 알고 있으면 final이 "실수로 재대입하는 것을 막는 스타일 규칙"이 아니라 언어 차원의 보장을 끌어오는 장치임을 설명할 수 있습니다. 02번 문서의 "싱글턴 빈이 공유해도 안전한 필드는 불변인 것뿐"이라는 원칙과 정확히 같은 지점에서 만납니다.

필드 주입이 이렇게 문제가 많은데, 스프링은 왜 아직도 지원하나요? 시니어 변별힌트: 역사적 맥락 + 여전히 정당한 사용처 + 프레임워크의 태도 변화

역사와 호환성 때문입니다. 애너테이션 기반 주입이 퍼지던 시기에 가장 짧게 쓸 수 있는 방식이었고, 이미 그렇게 작성된 코드가 방대하므로 기능을 없애면 기존 애플리케이션이 깨집니다. 그리고 테스트 클래스처럼 여전히 정당한 사용처도 있습니다.

다만 프레임워크의 태도는 이미 기울어 있습니다. ① Spring 4.3에서 단일 생성자면 @Autowired를 생략할 수 있게 해 생성자 주입의 마찰을 없앴고, ② Spring Boot 2.6부터는 순환 참조를 기본 금지해 필드 주입만 누리던 관용을 거둬들였습니다. ③ 스프링 공식 문서에서도 생성자 주입을 권장합니다.

그래서 답은 "지원한다 = 권장한다"가 아니다로 정리합니다. 지원은 호환성의 문제고, 권장은 설계의 문제입니다.

한 줄 요약
생성자 주입은 의존성을 생성자 시그니처라는 공개 계약으로 드러내어 "불완전한 객체는 아예 만들 수 없다"는 불변식을 컴파일러가 강제하게 만드는 방식이고, 필드 주입은 생성자가 끝난 뒤 리플렉션으로 private 필드에 값을 꽂아 넣기에 그 불변식이 없다 — final을 붙일 수 없고(생성자 종료 시한을 못 지키므로), 컨테이너 밖에서는 new로 반제품이 만들어지며, 껍데기끼리 이어붙어 순환 참조가 성립하고, 의존성이 몇 개로 불어나든 겉으로 드러나지 않는다. "팀 규칙이라서"가 아니라 잘못된 상태를 표현 불가능하게 만들고 나쁜 설계를 숨기지 못하게 하는 구조적 근거가 있는 선택이다.
