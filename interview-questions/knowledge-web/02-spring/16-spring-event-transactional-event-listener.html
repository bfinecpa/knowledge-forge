Spring Event와 @TransactionalEventListener
"커밋도 안 됐는데 알림부터 나간" 사고를 막는 도구

면접 질문: "Spring Event를 활용해본 경험이 있나요? @TransactionalEventListener는 언제 유용한가요?" / "DB 커밋 후에 이벤트를 발행해야 하는 요구사항을 어떻게 구현하나요?"

핵심 관전 포인트 — ApplicationEventPublisher로 발행한 이벤트는 기본이 동기·같은 스레드·같은 트랜잭션이다. "이벤트니까 비동기겠지"는 오해이고, 리스너가 던진 예외는 발행자에게 그대로 튀어 발행자의 트랜잭션을 롤백시킨다. @EventListener가 발행 즉시 실행이라면 @TransactionalEventListener는 실행을 트랜잭션 phase(기본 AFTER_COMMIT)까지 미루는 장치다. Redis·메일·MQ 같은 외부 시스템은 DB 트랜잭션에 참여하지 않아 롤백으로 되돌릴 수 없으므로, 커밋이 확정되기 전에 건드리면 "DB는 안 바뀌었는데 외부만 바뀐" 거짓 알림·거짓 캐시가 남는다. AFTER_COMMIT은 그 방향의 사고를 원천 차단하는 대신 반대 방향의 문제를 만든다 — 커밋은 이미 끝났으므로 리스너가 실패해도 롤백할 트랜잭션이 없고, 스프링은 그 예외를 로그 한 줄로 삼켜 호출자에게 알려주지도 않는다. 게다가 이미 커밋이 끝난 트랜잭션에 얹혀 도는 자리라 리스너 안의 DB 쓰기는 조용히 증발하고(해법은 REQUIRES_NEW), 트랜잭션이 없는 곳에서 발행하면 리스너 자체가 조용히 스킵된다. 그래서 이 질문의 본체는 phase 암기가 아니라, 커밋 뒤 실패 경로를 수용·재시도·보상·아웃박스 중 무엇으로 막을지 요구사항의 심각도로 고르는 판단이다.
  • 1
    기본값부터 못 박는다 — 동기·같은 스레드·같은 트랜잭션이다. publishEvent()는 리스너를 전부 실행한 뒤에야 리턴하므로 실행 흐름은 직접 호출과 완전히 같고, 리스너의 예외는 발행자에게 튀어 발행자의 트랜잭션을 롤백시킨다. 이벤트가 낮추는 것은 결합도뿐이지 실행 흐름이 아니다.
  • 2
    @TransactionalEventListener는 실행 "시점"을 트랜잭션 타임라인에 묶는 장치다. 기본값 AFTER_COMMIT은 커밋이 확정된 뒤에만 리스너를 부르고 롤백 시에는 아예 부르지 않는다 — 되돌릴 수 없는 외부 반영(알림·캐시 무효화·MQ 발행)을 "실행하고 되돌리기"가 아니라 "애초에 실행하지 않기"로 해결한다.
  • 3
    대신 문제가 반대 방향으로 옮겨간다 — 커밋 뒤의 실패에는 롤백도 없고 신호도 없다. 스프링이 그 예외를 삼켜 컨트롤러는 200 OK를 내려보내므로, 첫 대책은 실패를 지표·알림으로 승격시켜 관측 가능하게 만드는 것이고, 그다음 수용 · 재시도 · 보상 · 아웃박스 중 요구사항이 감당할 불일치의 크기로 방어선을 고른다.

0. 질문 + 출제 의도

질문: "Spring Event(ApplicationEventPublisher)를 활용해본 경험이 있나요? @TransactionalEventListener는 언제 유용한가요?" / "DB 커밋 후에 이벤트를 발행해야 하는 요구사항을 어떻게 구현하나요? (AFTER_COMMIT, Transactional Outbox)"

출제 의도: 결합도를 낮추면서 "커밋 후에만 알림 발송" 같은 정합성 요구를 지키는 실무 패턴을 아는지 본다. 이벤트를 써봤다는 사람에게 커밋 전/후 실행 시점을 물으면 진짜 이해도가 드러난다. 고난이도 버전에서는 "커밋됐는데 발행 실패" / "발행됐는데 롤백"의 양쪽 실패를 다 짚는지를 본다 — 분산 시스템 정합성의 축소판이라, 이 문제를 이해한 사람은 Kafka·MSA 정합성 문제 전반을 이해할 준비가 된 것이다.

이 페이지가 겨냥하는 약점 세 가지 ① "이벤트는 비동기"라는 오해 → 1절에서 스레드 이름 로그와 예외 역류 도식으로 "직접 호출과 같다"를 못 박는다.
② phase를 표로만 외우는 것 → 2절에서 트랜잭션 종료 타임라인 위에 4개 phase를 올려 AFTER_COMMIT과 AFTER_COMPLETION의 차이, 그리고 리소스 정리보다 먼저 돈다는 사실을 시각화한다. 4절의 함정 전부가 이 한 장에서 파생된다.
③ AFTER_COMMIT을 만능으로 아는 것 → 5·6절에서 "롤백도 없고 신호도 없다"는 문제의 정확한 모양을 그리고, 방어선 4단계 사다리로 선택 기준을 만든다.
한 문장 비유 — 도장 찍기 전에 돌린 청첩장 계약이 확정되기 전에 축하 문자를 먼저 돌리면, 계약이 깨졌을 때 문자를 회수할 방법이 없다. @EventListener는 도장을 찍는 손이 아직 움직이는 중에 문자를 돌리는 것이고, @TransactionalEventListener(AFTER_COMMIT)은 도장이 찍힌 것을 확인하고 나서 돌리는 것이다.  /  뒤집으면 이 비유가 5절의 문제도 그대로 설명한다 — 도장은 찍혔는데 문자 발송이 실패하면? 계약을 무를 수는 없다. 그때부터는 "다시 보낼 것인가, 늦어도 괜찮다고 볼 것인가, 계약을 취소할 것인가"의 문제가 된다.

1. Spring Event 기본 — 발행·구독, 그리고 "동기"라는 증거

1-1. 무엇을 해결하려고 만든 도구인가

이벤트는 한 컴포넌트가 "무슨 일이 일어났다"고 외치면 관심 있는 컴포넌트들이 각자 알아서 반응하는 구조다. 발행자는 구독자가 누구인지, 몇 명인지 몰라도 된다. 결합도를 낮추는 것이 유일한 목적이다.

기본 발행자는 구독자를 컴파일 타임에도 모른다
// 발행: "주문이 완료됐다"고 외치기만 한다
@Service
@RequiredArgsConstructor
public class OrderService {
    private final ApplicationEventPublisher eventPublisher;

    @Transactional
    public Order complete(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.complete();
        // 누가 이 이벤트를 받는지 이 클래스는 모른다. 컴파일 시점에도 모른다.
        eventPublisher.publishEvent(new OrderCompletedEvent(order.getId()));
        return order;
    }
}

// 구독: 알림과 통계가 각자의 리스너로 반응한다 — 서로의 존재도 모른다
@Component
public class NotificationListener {
    @EventListener
    public void on(OrderCompletedEvent event) { /* 알림 발송 */ }
}

@Component
public class StatisticsListener {
    @EventListener
    public void on(OrderCompletedEvent event) { /* 통계 집계 */ }
}

이벤트가 없었다면 OrderService가 알림·통계·캐시 서비스를 전부 주입받아 순서대로 호출해야 한다. 이벤트를 쓰면 "주문 완료 후 할 일"이 하나 늘어도 OrderService는 한 줄도 바뀌지 않는다 — 리스너 클래스를 하나 추가하면 끝이다.

1-2. 가장 흔한 오해 — "이벤트니까 비동기겠지"

아니다. 기본은 동기, 같은 스레드, 같은 트랜잭션이다. 말로만 하면 잘 안 믿기니 증거를 보자. 스레드 이름을 찍어보면 한 번에 끝난다.

실험 스레드 이름과 로그 순서를 찍는다
@Transactional
public Order complete(Long orderId) {
    log.info("발행 직전 thread={}", threadName());
    eventPublisher.publishEvent(new OrderCompletedEvent(orderId));
    log.info("발행 직후 thread={}", threadName());
    return order;
}

@EventListener
public void on(OrderCompletedEvent event) {
    log.info("리스너 안 thread={}", threadName());
}
결과 두 가지를 동시에 증명한다
발행 직전 thread=http-nio-8080-exec-3
리스너 안 thread=http-nio-8080-exec-3   ① 같은 스레드
발행 직후 thread=http-nio-8080-exec-3   ② 리스너 뒤에 찍힘

① 발행자와 리스너가 같은 요청 스레드다.
② "발행 직후"가 리스너보다 뒤에 찍힌다
   = publishEvent()가 리스너를 전부 실행한
     뒤에야 리턴한다.
   -> 리스너가 3초 걸리면
      publishEvent()도 3초 걸린다.

즉 실행 흐름만 놓고 보면 발행자가 리스너 메서드를 직접 호출한 것과 완전히 같다. 다른 점은 발행자가 리스너의 존재를 컴파일 타임에 모른다는 것뿐이다.

암기 장치 — Spring Event의 기본값은 "동 · 스 · 트"

동기(리스너가 끝나야 리턴)  ·  같은 스레드(요청 스레드 그대로)  ·  같은 트랜잭션(리스너의 DB 작업도 합류)

이 세 글자에서 모든 함정이 파생된다 — 동기라서 응답이 느려지고, 같은 스레드라서 예외가 역류하고, 같은 트랜잭션이라서 리스너가 쓴 데이터도 함께 롤백된다.

1-3. 그래서 리스너의 예외가 발행자의 트랜잭션을 롤백시킨다

같은 스레드·같은 호출 스택이라는 말은, 리스너에서 던진 예외가 publishEvent() 호출 지점으로 그대로 튀어 오른다는 뜻이다.

실무 결론 ①
부가 작업의 실패가 본체를 무너뜨리는 구조가 기본값이다. 알림 실패로 주문이 취소되는 게 맞는지는 요구사항의 문제이지 프레임워크가 정해줄 문제가 아니다. 아니라면 리스너 안에서 try-catch로 삼키거나 실행 시점을 커밋 뒤로 미뤄야 한다.
실무 결론 ②
리스너 안의 DB 작업은 발행자와 같은 트랜잭션에서 실행된다. 리스너가 무엇을 저장하든 아직 커밋 전이며, 발행자가 나중에 롤백하면 리스너가 쓴 것도 함께 사라진다.

2. @TransactionalEventListener — 실행 시점을 트랜잭션 타임라인에 묶는다

@EventListener가 "발행 즉시 실행"이라면 @TransactionalEventListener는 "발행은 해두되 실행은 트랜잭션이 특정 단계에 도달할 때까지 미룬다"이다. 발행 시점에 이벤트를 곧바로 처리하지 않고 현재 트랜잭션에 콜백을 등록해 두었다가, 트랜잭션이 그 단계에 이르면 그때 리스너를 부른다.

2-1. phase 4종을 타임라인 위에 올려놓기

표로만 외우면 AFTER_COMMIT과 AFTER_COMPLETION의 차이가 잘 안 잡힌다. 트랜잭션이 끝나는 과정을 시간축으로 그려놓고 각 phase가 어느 지점인지 표시하면 한 번에 정리된다. 이 그림 한 장이 4절 함정 전부의 근거다.

phase 4종 — "무엇을 넣는 자리인가"까지 같이 외워야 실전에서 고를 수 있다.
phase실행 시점무엇을 넣는 자리인가
BEFORE_COMMIT커밋 직전, 같은 트랜잭션 안커밋 전 마지막 검증, 파생 데이터의 추가 저장 — 여기 쓴 DB 변경은 본 트랜잭션과 함께 커밋되고, 여기서 예외가 나면 커밋이 취소되고 롤백된다
AFTER_COMMIT 기본값커밋 성공 후외부 시스템 반영 — 알림, 캐시 무효화, MQ 발행 — 롤백된 경우 호출조차 되지 않는다
AFTER_ROLLBACK롤백 후실패 알림, 실패 지표 적재
AFTER_COMPLETION커밋이든 롤백이든 완료 후결과와 무관한 정리 작업
기본 phase를 생략하면 AFTER_COMMIT이다
@Component
public class NotificationListener {
    // phase를 생략하면 AFTER_COMMIT — 커밋이 확정된 뒤에만 실행된다
    @TransactionalEventListener
    public void on(OrderCompletedEvent event) { /* 알림 발송 */ }
}

암기 장치 — phase 4종은 시간 순서로 "전 · 후 · 롤 · 완"

커밋 전(BEFORE_COMMIT) → 커밋 후(AFTER_COMMIT) → 롤백 후(AFTER_ROLLBACK) → 무조건 완료 후(AFTER_COMPLETION)

이름에 이미 답이 있다 — BEFORE/AFTER는 커밋 기준의 앞뒤, COMMIT/ROLLBACK/COMPLETION은 어떤 결말에 반응할지다. COMPLETION만 결말을 가리지 않는다(= 커밋+롤백 둘 다)고 기억하면 AFTER_COMMIT과 헷갈리지 않는다.

@EventListener vs @TransactionalEventListener — 실행 "시점"만 다르다. 스레드도 동기 여부도 같다.
@EventListener@TransactionalEventListener (AFTER_COMMIT)
실행 시점publishEvent() 즉시 그 자리트랜잭션이 커밋을 마친 뒤
실행 스레드발행자와 같은 스레드발행자와 같은 스레드 (@Async를 겹치기 전까지)
롤백되면이미 실행된 뒤 — 되돌릴 수 없다아예 실행되지 않는다
리스너 예외의 행방발행자에게 전파 → 발행자 트랜잭션 롤백스프링이 삼킨다 → 로그 한 줄, 호출자는 모름 5절
리스너 안의 DB 쓰기발행자 트랜잭션에 합류 — 같이 커밋/롤백이미 끝난 트랜잭션에 합류해 증발 (REQUIRES_NEW 필요)
트랜잭션이 없으면그냥 실행된다조용히 스킵된다 4-2

3. AFTER_COMMIT이 존재하는 이유 — 외부 시스템은 트랜잭션에 참여하지 않는다

이 질문의 핵심이다. 먼저 전제 하나를 깔아야 한다. DB 트랜잭션의 롤백은 그 DB 안의 변경만 되돌린다. DB 엔진이 변경 전 값을 보관하고 있다가 ROLLBACK 신호에 되돌려주는 기능이기 때문이다. Redis 쓰기, 메일 발송, 푸시 알림, 메시지 발행은 그 DB 바깥의 세계다 — 한번 나가면 되돌릴 수단이 없다.

before 커밋 전에 알림이 나간다
@Service
public class OrderService {
    @Transactional
    public Order complete(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.complete();
        eventPublisher.publishEvent(new OrderCompletedEvent(order.getId()));@EventListener면 이 줄에서 푸시 발송 완료
        // 아직 커밋 전인데 고객 휴대폰에는 이미 알림이 떴다
        applyCoupon(order);   // 여기서 예외 -> 트랜잭션 전체 롤백
        return order;
    }
}
// 결과: DB의 주문은 "완료 안 됨"으로 되돌아갔는데
//       고객 휴대폰에는 "주문이 완료되었습니다" 푸시가 남았다
//       -> 거짓 알림. CS 문의가 들어와도 DB엔 흔적이 없다.
after 커밋이 확정된 뒤에만 나간다
@Component
public class NotificationListener {

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    public void on(OrderCompletedEvent event) {
        // 롤백된 경우 이 메서드는 호출조차 되지 않는다.
        // "실행하고 되돌리기"가 아니라
        // "애초에 실행하지 않기"로 문제를 없앤 것이다.
        pushService.send(event.orderId(), "주문이 완료되었습니다");
    }
}

// 발행하는 쪽(OrderService)은 한 글자도 바뀌지 않는다.
// 바뀐 것은 "언제 실행되는가" 하나뿐이다.

규칙 — 되돌릴 수 없는 작업을 다루는 정석

되돌리는 방법을 마련하는 것이 아니라, 되돌릴 일이 없게 순서를 잡는다

AFTER_COMMIT은 그 원칙을 애너테이션 한 줄로 강제하는 장치다. 면접에서는 이 문장을 먼저 말하고 phase 이름을 대는 편이 순서가 좋다.

3-1. 실전 사례 — 보안 설정 변경 후 Redis 토큰 차단

보안 설정(예: 특정 앱의 접근 차단)이 변경되면 Redis에 살아 있는 해당 사용자들의 토큰을 차단해야 하는 요구사항이 있었다.

같은 트랜잭션 안에서(또는 BEFORE_COMMIT에서) 차단하면

  • 이후 로직에서 예외가 나 설정 저장이 롤백됐을 때
  • 설정은 그대로인데 사용자 토큰만 차단된 상태가 남는다
  • 사용자는 아무 이유 없이 강제 로그아웃당한다
  • 운영자는 "설정을 안 바꿨는데 왜 로그아웃됐냐"는 문의를 받는다
  • DB만 보면 아무 흔적이 없어 원인 추적도 어렵다

@TransactionalEventListener(AFTER_COMMIT)로 옮기면

  • 설정 변경이 DB에 확정된 경우에만 토큰이 차단된다
  • 롤백 시나리오에서 Redis는 손도 대지 않는다
  • 발행 지점(SettingService)의 코드는 그대로다
  • 남는 위험은 반대 방향 하나로 좁혀진다 — "커밋은 됐는데 차단이 실패" (5절)
"외부 시스템 반영은 커밋이라는 사실이 확정된 뒤에" — 이 한 문장이 AFTER_COMMIT의 존재 이유 전부다

4. 함정 3종 — 증발 · 스킵 · 지연

먼저 세 글자로 잡아둔다 — "증 · 스 · 지"

증발(리스너의 DB 쓰기가 사라진다)  ·  스킵(트랜잭션이 없으면 리스너가 안 돈다)  ·  지연(여전히 동기라 응답이 늦어진다)

앞의 둘은 예외도 로그도 없이 조용히 일어난다는 공통점이 있다. "왜 안 되지"를 며칠 헤매게 만드는 유형이라, 증상 → 원인을 외워두면 실무에서 바로 값을 한다.

4-1. 함정 ① — AFTER_COMMIT 리스너 안의 DB 쓰기가 조용히 사라진다 주니어 필수

before 예외도 로그도 없는데 DB에 데이터가 없다
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(OrderCompletedEvent event) {
    historyRepository.save(new OrderHistory(event.orderId()));정상 리턴하는데 테이블엔 행이 없다
}

왜 그런지는 2-1 타임라인의 ★ 지점을 다시 보면 나온다. AFTER_COMMIT 리스너는 커밋이 이미 끝났지만 리소스 정리는 아직 안 된 틈에서 실행된다.

after 자기 손으로 커밋하는 새 트랜잭션을 연다
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW)이 한 줄이 핵심
public void on(OrderCompletedEvent event) {
    // REQUIRES_NEW는 묶여 있던 (이미 끝난) 트랜잭션을 잠시 밀어두고
    // 새 커넥션으로 트랜잭션을 열기 때문에, 이 save()는 이 메서드가 끝날 때
    // 자기 힘으로 커밋된다.
    historyRepository.save(new OrderHistory(event.orderId()));
}
대가를 반드시 함께 말한다 — 커넥션을 하나 더 쓴다 REQUIRES_NEW는 새 커넥션을 하나 더 잡는다. 리스너가 오래 걸리면 그동안 커넥션 두 개를 동시에 점유하는 셈이라, 트래픽이 몰리면 커넥션 풀 고갈로 이어질 수 있다. REQUIRED와 REQUIRES_NEW의 차이 자체는 12-transaction-propagation-required-vs-requires-new.md에서 다룬다.

4-2. 함정 ② — 트랜잭션이 없으면 리스너가 조용히 스킵된다 디버깅 지옥

@TransactionalEventListener는 "진행 중인 트랜잭션에 콜백을 걸어두는" 장치다. 그렇다면 걸어둘 트랜잭션이 없으면 어떻게 되는가?

답: 아무 일도 일어나지 않는다 예외도, 경고도 없다. 스프링은 DEBUG 레벨로 "No transaction is active - skipping ..." 한 줄만 남기고 이벤트를 버린다. 기본 로그 레벨이 INFO이므로 그 줄조차 보이지 않는다. 이것이 "테스트에서 리스너가 안 불려 몇 시간을 헤매는" 전형적인 원인이다.
원인 ①
발행하는 메서드에 @Transactional을 안 붙였다.
원인 ②
붙였지만 같은 클래스 안에서 this.method()로 호출해 프록시를 타지 않았다. (11-transactional-self-invocation.md)
원인 ③
테스트가 서비스 메서드를 거치지 않고 publishEvent()를 직접 호출했다.
우회 트랜잭션이 없어도 실행되게 하려면 — 다만 습관적으로 쓰지 말 것
// 트랜잭션이 없을 때는 @EventListener처럼 즉시 실행하고,
// 있을 때는 AFTER_COMMIT까지 미룬다.
@TransactionalEventListener(fallbackExecution = true)
public void on(OrderCompletedEvent event) { ... }
fallbackExecution = true를 습관적으로 붙이지 않는 이유 "트랜잭션이 없다"는 사실 자체가 대개는 발행 지점의 버그 신호인데, 이 옵션은 그 신호를 지워버린다. 원인을 찾을 때 잠깐 켜보고, 정말로 트랜잭션 밖 발행이 정상 경로인 경우에만 남긴다.

4-3. 함정 ③ — 여전히 동기다, 느린 리스너가 응답을 붙잡는다

@TransactionalEventListener는 실행 시점만 미룰 뿐 여전히 요청 스레드에서 동기로 돈다. 커밋 직후, 응답이 나가기 전에 실행되므로 리스너의 메일 발송이 3초 걸리면 사용자 응답도 3초 늦어진다.

조합 응답과 무관한 부수 작업이라면 실행 스레드까지 분리한다
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(OrderCompletedEvent event) { mailService.send(...); }

이때 무슨 일이 일어나는지 정확히 알고 써야 한다. 커밋 후 요청 스레드가 작업을 async 풀에 제출하고 곧바로 응답을 내보내며, 실제 실행은 그 뒤에 워커 스레드에서 일어난다. 그래서 15-async-annotation.md의 이슈 세트가 그대로 따라붙는다.

스레드풀 설정
기본 큐가 무제한이라 동시 처리가 core 8개에 고정되고, 리스너가 느리면 큐만 무한히 쌓인다.
예외 처리
void 리턴이면 예외가 AsyncUncaughtExceptionHandler의 로그 한 줄로 끝난다.
컨텍스트 미전파
워커 스레드에는 트랜잭션도, SecurityContext도, MDC의 trace id도 없다. 커밋 후 별도 스레드이므로 트랜잭션 전파는 애초에 존재하지 않고, DB를 쓰려면 자기 트랜잭션을 열어야 한다.
유실 구간이 넓어진다
async 큐는 JVM 힙 위에 있다. 제출은 됐는데 실행 전에 배포로 프로세스가 내려가면 사라진다. 동기라면 최소한 응답 전에 시도라도 했겠지만, @Async는 시도조차 못 한 채 사라질 수 있다.

교환 관계를 한 문장으로

@Async는 응답 지연을 줄이는 대가로 유실 위험을 키운다

"느리니까 @Async 붙이면 되지"가 아니라 이 교환을 인지하고 선택했다고 말해야 한다. 유실이 허용 안 되는 작업이라면 답은 @Async가 아니라 아웃박스(6-4)다.

5. 커밋 뒤의 실패에는 롤백이 없다 — 문제의 정확한 모양 시니어 변별

AFTER_COMMIT은 "롤백됐는데 외부만 바뀐" 문제를 막지만 반대 방향의 문제를 새로 만든다. 커밋은 이미 확정됐는데 리스너가 실패하면? DB는 바뀌었는데 Redis 토큰 차단은 안 된 상태다. 이번엔 되돌릴 트랜잭션이 없다.

5-1. 여기에 많은 사람이 모르는 사실이 하나 더 붙는다 — 예외조차 안 올라온다

@TransactionalEventListener의 AFTER_COMMIT은 내부적으로 트랜잭션 완료 콜백으로 실행되는데, 스프링은 그 콜백들을 하나씩 부르면서 Throwable을 통째로 잡아 "TransactionSynchronization.afterCompletion threw exception" 이라는 에러 로그만 남기고 다음 콜백으로 넘어간다. 나머지 콜백을 지키기 위한 설계지만, 결과적으로 컨트롤러는 아무 일도 없었던 것처럼 200 OK를 내려보낸다.

이 절의 인출 문장 — 순서를 바꾸지 말 것

롤백은 불가능하다 → 그 예외는 호출자에게 전파되지도 않는다 → 그래서 가장 먼저 할 일은 실패를 관측 가능하게 만드는 것

"재시도하면 됩니다"부터 말하면 한 칸을 건너뛴 답이 된다. 관측되지 않는 실패에는 재시도도 보상도 발동하지 않는다는 것이 이 절의 요지다.

6. 방어선 4단계 — 관측된 실패를 무엇으로 막는가

실패를 관측 가능하게 만들었다면, 이제 어떻게 다룰지를 정한다. 요구사항의 심각도에 따라 네 갈래가 있고, 뒤로 갈수록 신뢰성과 복잡도가 함께 올라간다.

6-1. ① 불일치를 유계(bounded)로 만들고 수용

불일치가 "영원히"가 아니라 "최대 N분"이라면 수용 가능한 경우가 많다. 토큰 차단 사례가 정확히 그렇다 — 토큰의 TTL이 30분이라면, 차단에 실패해도 그 토큰은 30분 뒤 만료된다. TTL이 곧 불일치 지속 시간의 상한이 되는 것이다.

무한한 위험→TTL이라는 상한 발견→유한한 위험→스펙 레벨 의사결정

그러면 이것은 기술 문제가 아니라 "우리 보안 스펙상 최대 30분의 지연은 허용되는가"라는 스펙 레벨 의사결정이 된다. 기술로 다 막으려 하지 않고 비즈니스와 합의해 답을 얻는 것도 설계다. 다만 "어쩔 수 없다"와 "상한이 30분임을 확인하고 합의했다"는 완전히 다른 답변이라는 점이 중요하다.

6-2. ② 재시도

실패 원인이 Redis 순단이나 메일 서버의 일시 장애처럼 몇 초 뒤면 낫는 종류라면 재시도로 흡수하는 것이 가장 값싼 해법이다.

상한
무한 재시도는 금물. 재시도 상한과 초과 시 알림이 세트로 따라와야 한다.
지수 백오프
1초 → 2초 → 4초로 늘려간다. 이미 힘들어하는 상대 시스템에 재시도 폭풍으로 부하를 더 얹지 않기 위해서다.
그다음
재시도로도 안 되는 실패는 결국 ①(수용)이나 ③(보상)으로 넘어간다.
재시도는 문제를 없애는 대책이 아니라 — 일시 장애를 걸러내 진짜 실패의 빈도를 낮추는 필터다

6-3. ③ 보상 트랜잭션

보상 트랜잭션은 이미 커밋된 변경을 새 트랜잭션으로 역연산해 되돌리는 것이다. "완료 처리"의 보상은 "완료 취소"다. 커밋 기록을 지우는 것이 아니라 반대 방향의 변경을 한 번 더 쌓는다는 점에서 롤백과 다르다.

허점 ① — 그 사이에 남이 읽고 행동했다

원 커밋과 보상 커밋 사이의 시간 동안 다른 요청이 이미 변경된 상태를 읽고 행동했을 수 있다. 주문이 완료로 바뀐 것을 보고 배송 준비가 시작됐다면, 주문 상태를 되돌려도 그 행동은 되돌아오지 않는다.

허점 ② — 보상 자체가 실패한다

실패 처리의 실패라는 무한 후퇴에 빠진다. 실무에서는 보상도 재시도하고, 그마저 실패하면 수동 개입 큐에 적재해 사람을 부르는 것으로 끝을 맺는다.

그래서 선택 기준은 하나다 "안 되면 원래 변경을 취소하는 것이 사용자에게 더 나은 경우"에만 고른다. 예약을 확정했는데 좌석 배정이 실패했다면 예약을 취소하는 편이 낫다. 반대로 알림 발송이 실패했다고 주문을 취소하는 것은 명백히 과하다.

6-4. ④ 아웃박스 패턴 — 신뢰성이 요구사항일 때

"커밋됐으면 반드시, 언젠가는, 외부 반영도 된다"가 요구사항이라면 위의 셋으로는 부족하다. 이벤트가 메모리에만 있는 한 프로세스가 죽는 순간 사라지기 때문이다. 해법은 이벤트를 메모리가 아니라 DB에 남기는 것이다.

outbox 발행할 이벤트를 같은 트랜잭션 안에서 DB에 적는다
@Transactional
public void changeSecuritySetting(SettingRequest request) {
    settingRepository.save(setting);
    // 발행할 이벤트를 같은 DB의 outbox 테이블에 INSERT한다.
    // 설정 변경과 발행 예약이 '같은 트랜잭션의 두 쓰기'가 되므로
    // 둘 다 커밋되거나 둘 다 롤백된다 — 어긋날 방법이 없다.
    outboxRepository.save(OutboxEvent.of("TOKEN_BLOCK", payload));
}

// 별도 릴레이(스케줄러 폴링 또는 CDC)가 outbox 테이블의 미발행 행을 읽어
// 실제 발행을 수행하고, 성공한 것만 발행 완료로 표시한다.
// 실패하면 다음 주기에 다시 시도한다 — 행이 DB에 있으므로 사라지지 않는다.

구현 상세 — 폴링과 CDC의 선택, FOR UPDATE SKIP LOCKED를 쓴 릴레이의 동시 실행, at-least-once 전달과 멱등 소비자 — 는 23-transactional-outbox-pattern.md가 이 문서의 후속편으로 다룬다.

6-5. 그래서 무엇을 고르는가 — 후속 작업의 성격으로 가른다

네 갈래를 "신뢰성 순서"로만 외우면 실전에서 못 고른다. 후속 작업이 어떤 성격인가로 매핑해두면 바로 답이 나온다.

면접에서는 이 표의 왼쪽 칸을 먼저 말하고 오른쪽을 붙인다 — "이 작업은 늦어도 되는 종류라서 ①을 골랐습니다"의 어순이다.
후속 작업의 성격맞는 방어선예시
늦어도 되고, 다른 장치가 결국 정리해준다① 유계 불일치 수용TTL 있는 캐시 무효화, 토큰 차단
실패 원인이 대개 일시적이라 곧 낫는다② 재시도 + 상한 + 알림Redis 순단, 메일 서버 일시 장애
안 되면 원래 변경을 취소하는 편이 낫다③ 보상 트랜잭션예약 확정 후 좌석 배정 실패
절대 유실되면 안 되고 언젠가는 반드시 반영돼야 한다④ 아웃박스결제 후처리, 정산, 타 서비스 통지

암기 장치 — 방어선은 "수 · 재 · 보 · 아", 고르는 기준은 한 문장

수용 → 재시도 → 보상 → 아웃박스  /  기준: 요구사항이 감당할 수 있는 불일치의 크기

그 앞에 0단계 — 실패를 관측 가능하게 만들기가 있다는 것까지 붙이면 5절과 6절이 하나로 이어진다. 0 → 수 → 재 → 보 → 아.

7. Spring Event를 계속 쓸까, 브로커로 갈아탈까

Spring Event는 한 프로세스 안의 결합도를 낮추는 도구다. 이벤트가 애플리케이션 메모리에만 존재하므로 서버가 죽으면 유실되고, 다른 서비스(프로세스)에는 전달할 수 없다.

브로커(Kafka · RabbitMQ)로 갈아타는 신호 4가지

  • 소비자가 다른 프로세스나 다른 서비스일 때
  • 이벤트 유실이 허용되지 않을 때 — 브로커는 디스크에 보존하고 ack를 받아야 지운다
  • 소비 속도를 발행 속도와 분리해 버퍼링해야 할 때
  • 재처리나 리플레이가 필요할 때

반대로 Spring Event로 충분한 경우

  • 같은 프로세스 안에서 부수 작업을 떼어내는 것이 목적이라면 브로커는 과투자다
  • 목적이 결합도 낮추기일 때 — 리스너 클래스 추가만으로 확장된다
  • 아웃박스 + 브로커 조합은 "커밋과 발행의 원자성"이 실제 요구사항일 때 꺼내는 카드이지 기본값이 아니다

8. 인출 카드 · 꼬리질문 셀프 테스트

8-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

Spring Event의 기본값은?
동 · 스 · 트 — 동기 · 같은 스레드 · 같은 트랜잭션. "이벤트니까 비동기"는 바로 감점.
리스너가 예외를 던지면?
@EventListener면 발행자에게 역류해 발행자 트랜잭션이 롤백. AFTER_COMMIT이면 스프링이 삼켜 200 OK.
phase 4종은?
전 · 후 · 롤 · 완 — BEFORE_COMMIT / AFTER_COMMIT(기본값) / AFTER_ROLLBACK / AFTER_COMPLETION.
AFTER_COMMIT의 존재 이유는?
외부 시스템은 DB 트랜잭션에 참여하지 않아 롤백으로 되돌릴 수 없다. "실행하고 되돌리기"가 아니라 "애초에 실행하지 않기".
함정 3종은?
증 · 스 · 지 — 증발(리스너 DB 쓰기) · 스킵(트랜잭션 없음) · 지연(여전히 동기).
리스너의 save()가 증발하는 이유는?
커밋은 끝났는데 커넥션은 아직 묶여 있는 틈이라 REQUIRED가 이미 끝난 트랜잭션에 합류한다. 해법 REQUIRES_NEW, 대가 커넥션 하나 더.
리스너가 아예 안 불린다면?
발행 시점에 트랜잭션이 없다. ① @Transactional 누락 ② this 자기 호출 ③ 테스트에서 publishEvent() 직접 호출.
@Async를 겹치면?
응답 지연을 줄이는 대가로 유실 위험을 키운다. 워커 스레드엔 트랜잭션도 SecurityContext도 MDC도 없다.
커밋 뒤 실패의 0단계는?
관측 가능하게 만들기. 예외가 삼켜지므로, try-catch로 지표·알림으로 승격시키지 않으면 어떤 대책도 발동하지 않는다.
방어선 4단계와 선택 기준은?
수 · 재 · 보 · 아 — 수용 · 재시도 · 보상 · 아웃박스. 기준은 요구사항이 감당할 불일치의 크기.

8-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

@EventListener와 @TransactionalEventListener의 차이는? 필수힌트: "시점이 다르다"로 시작하고, 마지막에 "트랜잭션이 없을 때"의 차이를 한 칸 더 붙인다

실행 시점이 다르다. @EventListener는 publishEvent() 호출 즉시 그 자리에서 실행된다 — 발행자의 트랜잭션 안, 커밋 전이다. @TransactionalEventListener는 이벤트 처리를 트랜잭션 콜백으로 예약해 두었다가 지정한 phase에 실행한다.

기본값인 AFTER_COMMIT이면 커밋이 확정된 뒤에만 실행되고, 롤백되면 실행 자체가 안 된다. "커밋이라는 사실이 확정된 뒤에만 해야 하는 일", 즉 되돌릴 수 없는 외부 시스템 반영이 후자의 존재 이유다.

한 가지 더 붙이면 좋다 — 트랜잭션이 아예 없으면 @TransactionalEventListener는 조용히 스킵된다. @EventListener와 갈리는 또 하나의 지점이다.

이벤트 발행-리스너는 기본이 비동기인가요? 함정힌트: "아니다"부터. 그리고 세 가지 결과(스레드·예외·트랜잭션)를 한 묶음으로 말한다

아니다. 동기, 같은 스레드, 같은 트랜잭션이다.

publishEvent()가 리턴하기 전에 리스너들이 전부 실행되므로 스레드 이름을 찍어보면 발행자와 동일하고, 리스너의 예외는 발행자에게 그대로 전파되어 발행자의 트랜잭션을 롤백시킨다. 리스너 안의 DB 작업도 발행자와 같은 트랜잭션에 합류한다.

비동기로 만들려면 @Async를 명시적으로 조합해야 하고, 그 순간 15-async-annotation.md의 이슈 세트가 전부 따라온다. "이벤트니까 당연히 비동기"라고 답하면 바로 감점되는 지점이다.

AFTER_COMMIT 리스너에서 repository.save()가 조용히 안 먹는 이유는? 함정힌트: "커밋은 끝났는데 아직 안 끝난 것"이 무엇인지 지목한다

AFTER_COMMIT 리스너는 커밋은 끝났지만 리소스 정리는 아직 안 된 틈에서 실행되기 때문이다. 커넥션과 EntityManager가 여전히 스레드에 묶여 있으므로, 기본 전파 속성 REQUIRED인 save()는 "진행 중인 트랜잭션이 있다"고 판단해 이미 커밋이 끝난 그 트랜잭션에 참여자로 합류한다.

참여자는 스스로 커밋하지 않고 바깥쪽이 커밋해줄 것을 기대하는데, 그 바깥쪽은 이미 커밋을 끝냈다. 결국 리소스 정리 단계에서 커밋 없이 버려진다. 예외가 안 나서 운영에서 한참 뒤에 발견되는 유형이다.

해결은 리스너 메서드에 @Transactional(propagation = REQUIRES_NEW)를 붙여 기존 트랜잭션을 밀어두고 새 커넥션으로 자기 트랜잭션을 열게 하는 것이다. 커넥션을 하나 더 점유한다는 대가까지 언급하면 완결이다.

AFTER_COMMIT 리스너가 실패하면? 커밋은 이미 됐는데 — 정합성은 어떻게 지키나요? 시니어 변별힌트: "롤백은 불가능"을 인정하고 시작 → 예외조차 안 올라온다는 사실 추가 → 그다음에야 방어선

롤백은 불가능하다는 사실부터 인정하고 시작한다. 그리고 한 가지를 덧붙이면 깊이가 드러난다 — 그 예외는 호출자에게 전파되지도 않는다. 스프링이 트랜잭션 완료 콜백의 예외를 잡아 에러 로그만 남기므로 컨트롤러는 정상 응답을 내려보낸다. 그래서 첫 번째 대책은 리스너 안에서 실패를 잡아 지표와 알림으로 승격시켜 관측 가능하게 만드는 것이다.

그다음 방어선을 요구사항의 심각도로 고른다.

① 불일치를 유계로 만들고 수용한다 — 토큰 TTL 30분이 불일치 상한이 되므로 스펙 레벨 의사결정으로 격상시킨다. ② 일시 장애라면 지수 백오프 재시도 + 상한 + 실패 알림. ③ 원래 변경을 취소하는 편이 나은 작업이라면 보상 트랜잭션 — 단 원 커밋과 보상 사이에 상태를 읽고 행동한 다른 요청은 되돌릴 수 없고, 보상 자체도 실패할 수 있다는 허점을 짚는다. ④ 유실이 절대 안 되면 아웃박스 패턴으로 이벤트를 같은 트랜잭션에 저장하고 별도 릴레이가 발행한다.

"요구사항이 감당할 불일치의 크기로 단계를 고른다"고 답하면 시니어 답변이다.

@TransactionalEventListener를 붙였는데 리스너가 아예 안 불립니다. 왜죠? 함정힌트: 이 애너테이션이 "무엇에 등록하는" 장치인지를 떠올리면 원인이 하나로 좁혀진다

가장 흔한 원인은 발행 시점에 트랜잭션이 없는 것이다. 이 애너테이션은 진행 중인 트랜잭션에 콜백을 등록하는 방식이라 등록할 트랜잭션이 없으면 이벤트를 그냥 버리고, DEBUG 레벨 로그 한 줄만 남긴다. 기본 로그 레벨(INFO)에서는 그 줄조차 안 보인다.

점검 순서는 이렇다. ① 발행 메서드에 @Transactional이 붙어 있는가, ② 붙어 있다면 그 메서드가 프록시를 거쳐 호출됐는가(같은 클래스 안의 this 호출이면 트랜잭션이 안 열린다), ③ 테스트가 서비스 메서드를 거치지 않고 publishEvent()를 직접 부르고 있지는 않은가.

fallbackExecution = true로 트랜잭션 없이도 즉시 실행되게 할 수 있지만, "트랜잭션이 없다"는 사실 자체가 대개 발행 지점의 버그 신호이므로 원인을 먼저 확인하는 편이 낫다.

Spring Event로 계속 갈지, Kafka나 RabbitMQ 같은 브로커로 갈아탈지 — 기준은? 시니어 변별힌트: "메모리에만 있다"는 한 가지 사실에서 신호 네 개를 뽑아낸다

Spring Event는 한 프로세스 안의 결합도를 낮추는 도구다. 이벤트가 애플리케이션 메모리에만 존재하므로 서버가 죽으면 유실되고, 다른 서비스(프로세스)에는 전달할 수 없다.

갈아타는 신호는 넷이다. ① 소비자가 다른 프로세스나 다른 서비스일 때, ② 이벤트 유실이 허용되지 않을 때(브로커는 디스크에 보존하고 ack를 받아야 지운다), ③ 소비 속도를 발행 속도와 분리해 버퍼링해야 할 때, ④ 재처리나 리플레이가 필요할 때.

반대로 같은 프로세스 안에서 부수 작업을 떼어내는 것이 목적이라면 브로커는 과투자다. 그리고 아웃박스 + 브로커 조합은 "커밋과 발행의 원자성"이 실제 요구사항일 때 꺼내는 카드이지 기본값이 아니다.

BEFORE_COMMIT은 언제 쓰나요? AFTER_COMMIT과 결정적으로 뭐가 다르죠? 가산점힌트: "아직 같은 트랜잭션 안"이라는 한 가지 사실에서 두 결과가 파생된다

결정적 차이는 "아직 같은 트랜잭션 안"이라는 것 하나이고, 여기서 두 결과가 파생된다. ① 여기서 한 DB 쓰기는 본 트랜잭션과 함께 커밋된다 — 그래서 REQUIRES_NEW 같은 장치 없이도 정상 저장되고, 본 작업이 롤백되면 같이 롤백된다. ② 여기서 예외가 나면 커밋이 취소되고 롤백된다 — 즉 본 작업을 막을 수 있는 마지막 지점이다.

그래서 용도가 갈린다. BEFORE_COMMIT은 "이 트랜잭션의 일부로 취급되어야 하는 것"(커밋 전 마지막 검증, 파생 데이터의 추가 저장)이고, AFTER_COMMIT은 "이 트랜잭션이 성공했다는 사실에 반응하는 것"(외부 시스템 반영)이다.

뒤집어 말하면 BEFORE_COMMIT에 외부 시스템 호출을 넣으면 3절의 거짓 알림 문제가 그대로 재현된다 — 아직 커밋 전이므로 그 뒤에 롤백될 수 있기 때문이다. "DB 안의 일이면 BEFORE, DB 밖의 일이면 AFTER"로 외우면 헷갈리지 않는다.

같은 이벤트를 듣는 리스너가 3개인데 첫 번째가 예외를 던지면 나머지는 실행되나요? 가산점힌트: 답이 두 개다 — 애너테이션에 따라 갈린다

어느 애너테이션이냐에 따라 갈린다.

@EventListener라면 나머지는 실행되지 않는다. 리스너들은 발행자와 같은 호출 스택에서 차례로 불리는데, 첫 번째에서 던진 예외가 그대로 publishEvent() 밖으로 튀어나가 뒤의 리스너에 도달할 기회 자체가 사라지고, 발행자의 트랜잭션까지 롤백된다. 즉 알림 리스너 하나가 통계 리스너와 주문 커밋을 동시에 죽인다.

AFTER_COMMIT이라면 나머지는 정상 실행된다. 스프링이 트랜잭션 완료 콜백을 하나씩 부르면서 Throwable을 잡아 로그만 남기고 다음으로 넘어가기 때문이다. 나머지 콜백을 지키기 위한 설계이고, 그 부작용이 5절의 "예외가 삼켜진다"이다.

그래서 실무 결론은 같다 — 리스너 안에서 자기 실패는 자기가 처리한다. 부가 작업이 본체나 형제 리스너를 무너뜨리지 않게 try-catch로 경계를 긋고, 삼킨 실패는 반드시 지표·알림으로 올린다.

이벤트 객체에 엔티티를 통째로 담아 보내도 되나요? 함정힌트: 리스너가 도는 시점에 영속성 컨텍스트는 어떤 상태인가

ID와 값만 담는 편이 안전하다. 이유는 리스너가 도는 시점에 있다. AFTER_COMMIT은 커밋이 끝나고 리소스 정리로 향하는 자리이고, @Async까지 겹치면 영속성 컨텍스트가 아예 없는 다른 스레드다. 이 상태에서 엔티티의 아직 로딩되지 않은 연관을 건드리면 지연 로딩이 실패할 수 있다.

또 하나 — 리스너에서 엔티티의 필드를 바꿔도 반영되지 않는다. 변경 감지(dirty checking)로 UPDATE가 나가려면 커밋될 트랜잭션이 있어야 하는데, 그 트랜잭션은 이미 끝났기 때문이다(4-1의 증발과 같은 원인).

그래서 이 문서의 예제도 new OrderCompletedEvent(order.getId())처럼 식별자만 담는다. 리스너에서 더 많은 정보가 필요하면 REQUIRES_NEW로 자기 트랜잭션을 열어 다시 조회하는 편이 명확하다 — 커밋된 최신 상태를 읽는다는 장점도 따라온다.

@Async와 @TransactionalEventListener를 같이 붙이면 트랜잭션은 어떻게 되나요? 함정힌트: "전파"라는 단어를 쓰기 전에, 그 스레드에 원래 트랜잭션이 있기는 한지 묻는다

전파될 트랜잭션이 애초에 없다. 두 가지 이유가 겹친다 — ① AFTER_COMMIT은 커밋이 끝난 뒤라 되살릴 트랜잭션이 없고, ② @Async는 다른 스레드에서 도는데 트랜잭션은 스레드에 묶여 있으므로 워커 스레드로 따라가지 않는다. 같은 이유로 SecurityContext와 MDC의 trace id도 없다(별도 전파 설정을 하지 않았다면).

그래서 4-1의 증발 함정은 여기선 일어나지 않는다 — 워커 스레드에는 묶여 있는 커넥션 자체가 없어 잘못 합류할 대상이 없기 때문이다. 대신 트랜잭션 없이 도는 것이 기본이므로, DB를 쓰려면 리스너에 @Transactional을 명시적으로 붙여 자기 트랜잭션을 열어야 한다.

그리고 진짜 대가는 따로 있다 — 유실 구간이 넓어진다. async 큐는 JVM 힙 위에 있어서, 제출은 됐는데 실행 전에 배포로 프로세스가 내려가면 그 작업은 사라진다. 유실이 허용되지 않는 작업이라면 답은 @Async가 아니라 아웃박스다.

아웃박스를 쓰면 AFTER_COMMIT 리스너는 필요 없어지나요? 시니어 변별힌트: 아웃박스에서 "발행 예약"이 일어나는 시점이 언제인지 다시 본다

발행 경로로서는 필요 없어진다. 아웃박스의 요점은 "발행 예약"을 본 변경과 같은 트랜잭션 안의 INSERT로 만드는 것이므로, 예약은 커밋 전에 끝나고 실제 발행은 별도 릴레이가 맡는다. 커밋 이후를 노리는 리스너에 의존하지 않는 것 자체가 목적인 셈이다.

그래서 둘의 관계는 "상위 호환"이 아니라 "접근이 다르다"로 말하는 편이 정확하다. AFTER_COMMIT은 "커밋됐다는 사실을 확인하고 지금 시도한다"이고, 아웃박스는 "시도해야 한다는 사실을 커밋과 함께 기록해 두고 나중에 반드시 처리한다"이다. 전자는 지금 실패하면 끝이고, 후자는 기록이 남아 있어 다시 시도된다.

다만 Spring Event를 아웃박스와 함께 쓰는 것은 여전히 자연스럽다 — 아웃박스 행을 본 트랜잭션과 함께 커밋되는 자리, 즉 서비스 코드 안이나 BEFORE_COMMIT 리스너에서 INSERT하면 결합도는 낮추면서 원자성도 지킬 수 있다. 대가는 테이블·릴레이·멱등 소비자라는 운영 복잡도이고, 재시도가 있는 한 전달은 at-least-once가 되므로 소비자 멱등성은 선택이 아니라 필수다.

한 줄 요약
Spring Event는 기본이 동기·같은 스레드·같은 트랜잭션이라 결합도만 낮출 뿐 실행 흐름은 직접 호출과 같고(리스너의 예외가 발행자를 롤백시킨다), @TransactionalEventListener(AFTER_COMMIT)는 "트랜잭션에 참여하지 못하는 외부 시스템은 커밋이 확정된 뒤에만 건드린다"는 원칙을 코드로 강제해 거짓 알림·거짓 캐시를 막는다 — 대신 커밋이 끝난 자리라 리스너의 DB 쓰기는 REQUIRES_NEW 없이는 조용히 증발하고 트랜잭션이 없으면 리스너 자체가 스킵되며 실패해도 롤백은커녕 예외조차 올라오지 않으므로, 실패를 먼저 관측 가능하게 만든 뒤 수용·재시도·보상·아웃박스 중 요구사항이 감당할 불일치의 크기에 맞는 방어선을 고르는 것까지가 설계다.
