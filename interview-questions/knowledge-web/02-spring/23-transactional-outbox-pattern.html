Transactional Outbox 패턴
스프링에서 "커밋됐는데 발행 실패"를 코드가 아니라 구조로 없애는 법

면접 질문: "DB 커밋 후에 이벤트를 발행해야 하는 요구사항을 어떻게 구현하나요? (AFTER_COMMIT, Transactional Outbox)"

핵심 관전 포인트 — DB와 메시지 브로커는 서로 다른 시스템이라 하나의 트랜잭션으로 묶을 수 없다(이중 쓰기 문제). 커밋을 먼저 하면 발행 직전 크래시에서 이벤트가 유실되고, 발행을 먼저 하면 롤백 시 존재하지 않는 데이터의 거짓 이벤트가 나간다 — 순서를 어떻게 바꿔도 깨지고 try-catch로도 못 막는다(프로세스가 죽으면 catch도 안 돈다). XA/2PC로 묶는 길은 이론상 존재하나 가용성이 두 시스템의 곱으로 떨어지고 Kafka·RabbitMQ 모두 XA를 지원하지 않아 실무에서 배제된다. 스프링에서의 출발점은 @TransactionalEventListener(AFTER_COMMIT)인데, 이것은 "발행 먼저" 방향의 거짓 이벤트만 막을 뿐 이벤트가 JVM 메모리에만 있어 유실을 못 막는다(at-most-once). 그래서 "보낼 이벤트"를 비즈니스 변경과 같은 트랜잭션으로 같은 DB의 outbox 테이블에 INSERT해 이중 쓰기를 단일 쓰기로 바꾸고, 별도 릴레이가 그 행을 읽어 발행한다 — 폴링 릴레이는 PostgreSQL의 FOR UPDATE SKIP LOCKED로 여러 인스턴스가 같은 행을 집지 않게 하고, RabbitMQ라면 비동기 publisher confirm 콜백에서, Kafka라면 ack 확인 후에 발행 완료를 표시한다. 결과 보장은 at-least-once이므로 소비자 멱등성이 반드시 짝으로 따라온다.
  • 1
    먼저 문제의 정체를 이중 쓰기로 규정한다 — DB 쓰기와 브로커 발행은 서로 다른 시스템에 대한 쓰기 두 번이라 원자성이 없다. 커밋 먼저면 유실(조용히 한 건이 빠져 며칠 뒤 대사에서 발견), 발행 먼저면 거짓 이벤트(없는 주문을 정산·차감). try-catch나 보상 코드로는 못 막는데, 그 코드들도 전부 프로세스 안에 있기 때문이다. 그래서 코드가 아니라 구조로 푸는 문제다.
  • 2
    스프링의 1차 답이 어디까지인지 정확히 선을 긋는다 — @TransactionalEventListener(AFTER_COMMIT)은 롤백 시 리스너가 아예 안 돌아 거짓 이벤트를 원천 제거하지만, 이벤트 객체가 JVM 힙에만 있어 크래시하면 재시도할 대상 자체가 사라진다 — 보장은 at-most-once. 판단 기준은 하나다: "이 이벤트가 한 건 빠지면 무슨 일이 생기는가." 푸시 알림이면 이걸로 충분하고, 정산·재고·상태 동기화면 아웃박스로 간다.
  • 3
    아웃박스는 이중 쓰기를 단일 쓰기로 바꾼다 — 브로커에 보내는 대신 같은 DB의 outbox_event 테이블에 같은 트랜잭션으로 INSERT하면 원자성이 공짜로 성립한다. 별도 릴레이가 processed_at IS NULL 행을 FOR UPDATE SKIP LOCKED로 나눠 집어 발행하고, 브로커의 확인 응답(confirm/ack)을 받은 뒤에만 발행 완료를 표시한다. 남는 성질은 at-least-once이므로 "생산 측은 유실 방지, 소비 측은 중복 제거(멱등 소비자)"까지 말해야 답이 완성된다.

0. 질문 + 출제 의도

질문: "DB 커밋 후에 이벤트를 발행해야 하는 요구사항을 어떻게 구현하나요? (AFTER_COMMIT, Transactional Outbox)"

출제 의도: "커밋됐는데 발행 실패" / "발행됐는데 롤백"의 양쪽 실패를 다 짚는지 본다. 분산 시스템 정합성의 축소판이라, 이 문제를 이해한 사람은 Kafka·MSA 정합성 문제 전반을 이해할 준비가 된 것이다.

이 페이지가 겨냥하는 약점 세 가지 ① 한쪽 실패만 보는 것 → 1절에서 두 순서를 같은 시퀀스 도식에 나란히 놓고, 유실과 거짓 이벤트가 서로 다른 실패임을 못 박는다.
② "아웃박스를 씁니다"로 끝내는 것 → 4~7절에서 테이블 컬럼 하나하나의 이유, SKIP LOCKED가 푸는 정확한 지점, confirm 콜백에서 표시해야 하는 이유까지 내려간다.
③ 소비자 멱등성을 빠뜨리는 것 → 10절에서 릴레이 안에서 이중 쓰기가 축소판으로 재현되는 그림을 보여, at-least-once가 결함이 아니라 의도적 교환임을 세운다.
한 문장 비유 — 편지함, 그리고 등기우편 편지함: 편지를 직접 우체국까지 들고 뛰는 대신 집 앞 편지함(outbox)에 넣어 두면 집배원(릴레이)이 와서 가져간다. 넣는 행위와 가져가는 행위가 분리되므로 내가 넣자마자 쓰러져도 편지는 편지함에 남아 있다.  /  등기우편: 우체통에 넣었다(convertAndSend())와 상대가 받았다(publisher confirm)는 다른 사건이다. 접수증 없이 "보냈다"고 장부에 적으면, 중간에 사라진 편지를 영영 못 찾는다(7절).

1. 이중 쓰기 — 어느 순서로 놓아도 깨진다

1-1. 한 문장의 요구사항이, 실행 시점에는 두 시스템에 대한 쓰기 2번

"주문을 완료 처리하고, 주문 완료 이벤트를 브로커에 발행한다." 한 문장이지만 실행 시점에는 서로 다른 두 저장소에 쓰기 2번이다.

문제 하나의 @Transactional 안에 두 시스템이 들어와 있다
@Transactional
public void complete(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();                                        // ① PostgreSQL에 쓰기
    rabbitTemplate.convertAndSend("order.events",
            "order.completed", new OrderCompleted(order));   // ② RabbitMQ에 쓰기여기엔 롤백이 없다
}

우리가 원하는 것은 둘 다 되거나 둘 다 안 되는 것이다. 그런데 @Transactional이 관리하는 것은 ①의 DB 커넥션뿐이고, ②는 완전히 다른 프로토콜로 다른 서버에 나가는 네트워크 호출이다. 롤백 신호는 브로커에 도달하지 않는다.

용어 봉인 — 이중 쓰기(dual write)

한 논리적 작업이 원자성 보장 없이 두 시스템에 쓰기를 하는 상황

이름 그대로 "쓰기가 두 번"이라는 사실 자체가 문제의 이름이 된 것이다. 그래서 해법의 방향도 이름에 이미 들어 있다 — 쓰기를 한 번으로 만드는 것(4절).

1-2. 두 순서를 나란히 놓고 본다

두 순서를 한 표로. 실패의 성질이 다르다는 것까지 말해야 답이 선명해진다.
순서실패 지점결과발견 난이도
커밋 → 발행커밋 성공 후, 발행 전 크래시 / 발행 실패이벤트 유실 — 주문은 있는데 후속 처리가 없음어렵다 (조용히 빠짐)
발행 → 커밋발행 성공 후 커밋 실패거짓 이벤트 — 없는 주문의 이벤트가 소비됨쉽다 (소비자에서 예외)

"try-catch로 잘 감싸면 되지 않나요?" — 가장 흔한 반론이 막히는 이유

catch 블록은 프로세스가 살아 있어야 실행된다
catch가 안 도는 상황
kill -9 · OOM Killer · 쿠버네티스 파드 축출 · 노드 장애 · 그냥 배포로 인한 재시작
"보상으로 DB를 되돌리면?"
그 보상 코드도 프로세스 안에 있다. 같은 벽에 부딪힌다.
"재시도 큐에 넣으면?"
인메모리 큐라면 재시작 시 통째로 사라진다. 영속적 기록이 아니면 의미가 없다.

이 인식이 이 질문의 절반이다. 면접에서 "예외 처리를 잘 하면 된다"로 답하면 문제의 층위를 못 본 것으로 들린다.

2. 왜 XA/2PC로 묶지 않는가 시니어 변별

"두 시스템을 한 트랜잭션으로 묶을 수 없다"고 했지만, 이론적으로는 방법이 있다. 2단계 커밋(2PC, two-phase commit)이다. 배제하는 이유를 말할 수 있어야 "선택지가 왜 아웃박스로 좁혀지는가"의 설명이 완성된다.

비유 — 결혼식 주례 2PC의 코디네이터(coordinator, 조정자)는 주례와 같다. "이 결혼에 동의합니까?"를 양쪽에 각각 묻고(prepare), 둘 다 "예"라고 답해야 성립을 선언한다(commit). 문제는 세 가지다 — 둘 중 하나만 못 와도 식이 안 열리고(가용성), "예"라고 답한 쪽은 선언이 올 때까지 자리를 뜰 수 없으며(잠금 블로킹), 결정적으로 브로커는 이 예식에 참석할 자격 자체가 없다(XA 미지원).

암기 장치 — 2PC 배제 3종은 "가 · 잠 · 자"

가용성이 곱으로 떨어진다  ·  잠금을 쥔 채 블로킹(in-doubt)  ·  자격이 없다(XA 미지원)

여기에 한 문장을 덧붙이면 인상이 달라진다 — "아웃박스는 분산 원자성을 포기하고, 로컬 원자성 + 비동기 전달 + 소비자 멱등성으로 같은 효과를 재구성한 것"이다. 문제를 푼 것이 아니라 문제가 성립하지 않는 형태로 바꾼 것에 가깝다.

그래서 선택지는 하나로 좁혀진다 두 시스템을 원자적으로 묶을 수 없다면, 남은 길은 하나다 — 원자성이 필요한 두 쓰기를 같은 시스템 안으로 끌어들이는 것. 브로커에 보내야 할 것은 결국 "이런 이벤트를 발행해야 한다"는 사실이고, 그 사실을 브로커가 아니라 같은 DB의 테이블에 적으면 비즈니스 변경과 이벤트 기록이 한 트랜잭션 안의 DB 쓰기 두 번이 되어 원자성이 자동으로 성립한다. 다만 스프링을 쓰고 있다면 그 앞에 한 정거장이 더 있다.

3. AFTER_COMMIT — 막아주는 것과, 끝내 못 막는 것

많은 팀이 여기서 출발한다. 여기서 왜 막히는지를 알아야 아웃박스가 필요한 이유가 몸에 붙는다.

3-1. 막아주는 것 — "발행 먼저"의 거짓 이벤트

ApplicationEventPublisher로 발행한 이벤트는 기본이 동기 · 같은 스레드 · 같은 트랜잭션이다. @EventListener를 붙이면 publishEvent() 호출 즉시 리스너가 실행되므로 아직 커밋 전이다 — 1절의 "발행 먼저"와 똑같은 상황이 된다. @TransactionalEventListener는 실행 시점을 트랜잭션의 phase에 묶는다. 기본값인 AFTER_COMMIT이면 커밋이 확정된 뒤에만 리스너가 돈다.

1차 답 롤백되면 리스너가 아예 실행되지 않는다 → 거짓 이벤트 원천 제거
@Transactional
public void complete(Long orderId) {
    Order order = orderRepository.findById(orderId).orElseThrow();
    order.complete();
    // 이 시점에는 아직 아무것도 발행되지 않는다. 이벤트는 커밋 후 실행될
    // 콜백으로 "등록만" 된다 — 등록 메커니즘은 24번 문서의 동기화 콜백이다.
    eventPublisher.publishEvent(new OrderCompletedEvent(order.getId()));
}

@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(OrderCompletedEvent event) {
    rabbitTemplate.convertAndSend("order.events", "order.completed", event);커밋 확정 뒤에만 실행
}

@Async까지 얹으면 발행이 원래 트랜잭션 스레드 밖으로 나가므로 응답 지연에도 영향을 주지 않는다. 여기까지는 좋다. 문제는 우리가 1절 표의 첫 줄, "커밋 → 발행" 순서로 옮겨 탔을 뿐이라는 점이다.

3-2. 못 막는 것 — 이벤트가 JVM 메모리에만 있다

한계 같은 코드에 주석으로 실패 경로를 세 개 달면 이렇게 된다
@Async
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(OrderCompletedEvent event) {
    rabbitTemplate.convertAndSend("order.events", "order.completed", event);
    // ① 브로커 순단으로 여기서 예외가 나면? 커밋은 이미 확정, 이벤트만 증발한다.
    // ② 커밋 직후 이 메서드에 도달하기 전에 서버가 재시작되면?
    //    이벤트 객체는 힙에만 있었으므로 흔적도 없이 사라진다.
    // ③ @Async 큐(인메모리)에 대기 중이던 이벤트들도 재시작 시 통째로 사라진다.
}
이벤트가 휘발성이다
publishEvent()가 만든 객체는 JVM 힙에만 존재한다. 디스크에도, DB에도 없다. 프로세스가 사라지면 같이 사라진다.
재시도할 근거가 없다
재시도하려 해도 "무엇을 못 보냈는지"의 기록이 어디에도 없다. 재시도 로직 자체도 프로세스 생존을 전제로 한다.
그래서 at-most-once다
"커밋됐으면 반드시 언젠가는 발행된다"가 요구사항이라면 이 도구로는 도달할 수 없다.

전달 보장 3종 — 용어를 정확히 쥐고 답한다

보장뜻어긋났을 때이 문서에서의 위치
at-most-once (최대 1회)중복은 없지만 유실될 수 있다이벤트가 한 건 빠진다AFTER_COMMIT 리스너 발행
at-least-once (최소 1회)유실은 없지만 중복될 수 있다같은 이벤트가 두 번 처리된다아웃박스 + 릴레이
exactly-once (정확히 1회)유실도 중복도 없다—분산 환경에서 단독으로는 실질적으로 불가능

3-3. 그럼 언제까지 이벤트로 충분한가 — 판단 기준

무조건 아웃박스로 가는 것이 정답은 아니다. 아웃박스에는 테이블, 릴레이 프로세스, 정리 배치, 적체 모니터링이 전부 딸려 온다. 요구사항이 그 비용을 정당화하는지 판단하는 것이 설계다.

판단 기준은 질문 하나로 기계화된다

"이 이벤트가 한 건 빠지면 무슨 일이 생기는가"

빠져도 되는 것 → AFTER_COMMIT + @Async + 실패 로그

  • 마케팅 푸시 알림
  • 최근 본 상품 기록
  • 대시보드 집계 갱신

한 건 유실이 데이터 불일치를 만들지 않는다.

빠지면 안 되는 것 → 아웃박스

  • 정산 원장 기록
  • 재고 차감
  • 타 서비스의 상태 동기화, 포인트 적립

유실이 곧 정합성 깨짐이고, 나중에 대사로 찾아내 수동 보정해야 한다.

이 구분을 요구사항에서 스스로 끌어내는 것이 답변의 설계 감각 부분이다. "무조건 아웃박스"라고 답하면 비용을 계산하지 않은 사람으로 들린다.

4. 아웃박스 — 발상과 테이블 설계

4-1. 발상 — 브로커를 트랜잭션에 넣지 말고, "보낼 사실"을 DB에 넣는다

브로커 발행을 트랜잭션에 묶으려 애쓰지 말고, "발행해야 한다는 사실"을 같은 DB에 같은 트랜잭션으로 기록한다

아웃박스(outbox)는 말 그대로 "보낼 편지함"이다. 편지를 직접 우체국까지 들고 뛰는 대신 집 앞 편지함에 넣어 두면 집배원(릴레이)이 와서 가져간다. 내가 넣는 행위와 집배원이 가져가는 행위가 분리되므로, 내가 넣자마자 쓰러져도 편지는 편지함에 남아 있다.

DB 쓰기 2번은 한 로컬 트랜잭션으로 묶을 수 있으므로 이중 쓰기가 단일 쓰기로 바뀐다. 이것이 패턴의 전부다.

4-2. 테이블 스키마 — 컬럼마다 이유가 있다

DDL PostgreSQL 기준 — 주석이 곧 면접 답변이다
CREATE TABLE outbox_event (
    id             bigserial     PRIMARY KEY,
    -- 이벤트 고유 ID. 소비자가 중복 제거의 멱등 키로 쓸 값이므로
    -- 반드시 메시지에 실어 보낸다. (UUID를 쓰면 릴레이가 여러 대여도
    -- 충돌 걱정이 없지만, bigserial은 대략의 생성 순서를 준다.)

    aggregate_type varchar(50)   NOT NULL,   -- 예: 'ORDER'. 토픽/라우팅 키 결정에 쓴다
    aggregate_id   varchar(64)   NOT NULL,
    -- 이 이벤트가 어느 애그리거트(하나로 묶여 변경되는 데이터 단위, 여기선 주문 1건)의
    -- 것인지. Kafka 파티션 키 / RabbitMQ 라우팅에 쓰이며 순서 보장의 단위가 된다.

    event_type     varchar(100)  NOT NULL,   -- 예: 'ORDER_COMPLETED'
    payload        jsonb         NOT NULL,   -- 이벤트 본문
    schema_version int           NOT NULL DEFAULT 1,
    -- 스키마 버전을 처음부터 넣어 둔다. 아웃박스에는 코드 배포 전에 쌓인
    -- 과거 이벤트가 남아 있을 수 있어, 소비자가 버전을 보고 분기해야 하는
    -- 순간이 반드시 온다. 나중에 추가하면 그때 쌓인 행에는 값이 없다.

    created_at     timestamptz   NOT NULL DEFAULT now(),
    processed_at   timestamptz,NULL = 미발행. 상태와 시각을 한 컬럼으로
    -- 상태를 별도 varchar 컬럼 대신 이 타임스탬프의 NULL 여부로 표현하면
    -- "언제 발행됐는가"까지 한 컬럼으로 얻는다.

    attempts       int           NOT NULL DEFAULT 0,
    last_error     text
    -- 실패가 반복되는 독성 이벤트(poison event)를 골라내기 위한 운영 컬럼.
    -- 이 값이 임계치를 넘으면 알람을 걸고 별도 처리한다.
);

-- 부분 인덱스: 조건에 맞는 행만 인덱스에 넣는 PostgreSQL 기능이다.
-- 폴링 쿼리는 항상 "미발행 행"만 찾으므로, 발행 완료된 행까지 인덱스에
-- 담을 이유가 없다. 발행 완료 행이 수천만 건 쌓여도 이 인덱스는
-- "아직 안 보낸 몇 건" 크기로 유지된다.
CREATE INDEX idx_outbox_unprocessed
    ON outbox_event (id)
    WHERE processed_at IS NULL;테이블 크기와 무관하게 일정한 폴링 비용
왜 jsonb인가 — 그리고 언제 text인가
jsonb는 운영 중 조회·필터가 쉬워서 쓴다. 다만 입력 JSON을 파싱해 내부 표현으로 저장하므로 키 순서와 공백이 보존되지 않는다. 발행 바이트를 그대로 지켜야 하는 경우(예: 서명 검증)에는 text로 둬야 한다.
왜 schema_version을 처음부터 넣나
아웃박스에는 배포 전에 쌓인 과거 이벤트가 남아 있을 수 있다. 나중에 컬럼을 추가하면 그때 쌓인 행에는 값이 없다 — 그 순간 소비자가 분기할 근거를 잃는다.
aggregate_id가 순서의 단위다
Kafka 파티션 키, RabbitMQ 라우팅에 쓰인다. "같은 주문의 이벤트 순서"는 이 값을 기준으로만 말할 수 있다(9-2절).
attempts·last_error는 장식이 아니다
이 두 컬럼이 없으면 영원히 실패하는 독성 이벤트를 찾아낼 방법이 없다. 릴레이는 조용히 계속 재시도만 하게 된다(9-3절).

여기서 미리 짚는 함정 — "마지막 처리 id 이후"로 읽으면 이벤트를 건너뛴다

릴레이를 만들 때 "마지막으로 처리한 id 이후"라는 고수위 표시(high-water mark) 방식을 쓰고 싶어진다. 커서 하나만 들고 있으면 되니 단순해 보인다. PostgreSQL에서 이건 이벤트를 건너뛴다. 시퀀스 값은 INSERT 시점에 할당되지만, 커밋 순서는 그와 다를 수 있기 때문이다.

폴링 기준은 커서(id)가 아니라 미처리 플래그다 — WHERE processed_at IS NULL

5. 쓰기 경로 — 스프링 이벤트에서 아웃박스로 넘어가는 지점

3절의 코드를 어떻게 바꾸는지가 이 문서의 실질적 출발점이다. 바뀌는 것은 딱 한 줄의 방향이다 — 브로커로 나가던 화살표가 DB로 돌아온다.

before 커밋 후 브로커로 직접 발행 — 이벤트가 메모리에만 있어 유실된다
@Async
@TransactionalEventListener(
        phase = TransactionPhase.AFTER_COMMIT)
public void on(OrderCompletedEvent event) {
    rabbitTemplate.convertAndSend(
        "order.events", "order.completed", event);
}

// 트랜잭션 밖 · 힙 위 · 기록 없음
// → 크래시하면 재시도할 대상 자체가 없다
// → 보장: at-most-once
after 같은 트랜잭션 안에서 outbox 테이블에 INSERT한다
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional
    public void complete(Long orderId) {
        Order order = orderRepository
                .findById(orderId).orElseThrow();
        order.complete();
        // 브로커는 이 메서드에 등장하지 않는다.
        // 트랜잭션 안에는 DB 작업만 남는다.
        outboxRepository.save(OutboxEvent.of(
            "ORDER", order.getId().toString(),
            "ORDER_COMPLETED", toJson(order)));
    }   // 주문 변경과 outbox INSERT가 함께 커밋/롤백
}
덤으로 따라오는 이득 — 트랜잭션 안에서 외부 호출이 사라진다 after 코드의 트랜잭션 안에는 DB 작업만 남는다. 브로커가 3초 느려져도 커넥션을 물고 기다리는 코드가 없다 — 22-external-api-call-inside-transaction.md의 "트랜잭션 안 외부 호출" 문제를 같은 리팩터링 한 번으로 동시에 피하는 셈이다. 면접에서 이 한 문장을 덧붙이면 패턴의 부수 효과까지 본 사람으로 들린다.

5-1. 도메인이 아웃박스를 모르게 하는 변형 — phase만 바꾼다

스프링 이벤트를 쓰던 코드라면 리스너를 지우지 말고 phase만 바꾸는 방법도 있다. 도메인 레이어는 계속 publishEvent()로 이벤트를 던지고, 리스너(어댑터)가 그것을 outbox 행으로 바꿔 넣는 형태다.

변형 도메인은 그대로 이벤트를 발행하고, 어댑터가 아웃박스에 적는다
// phase가 BEFORE_COMMIT인 것이 핵심이다 — 아직 커밋 전이므로 이 INSERT가
// 원래 트랜잭션에 그대로 포함된다.
@TransactionalEventListener(phase = TransactionPhase.BEFORE_COMMIT)AFTER_COMMIT이면 안 된다
public void toOutbox(OrderCompletedEvent event) {
    outboxRepository.save(OutboxEvent.from(event));
}

가장 잘 나오는 함정 — 같은 애너테이션, phase 하나로 정반대가 된다

phase그 안에서 해야 할 일반대로 하면
BEFORE_COMMIToutbox 테이블에 INSERT
아직 커밋 전이라 원래 트랜잭션에 포함된다		커밋 이후에 INSERT하면 그 쓰기는 flush될 기회를 얻지 못하고 조용히 사라진다 — 아웃박스 행이 아예 안 생긴다
AFTER_COMMIT브로커로의 직접 발행(유실을 감수하는 경우)
커밋 확정 뒤라 거짓 이벤트가 없다		커밋 전에 발행하면 1절의 "발행 먼저" = 거짓 이벤트로 되돌아간다
DB에 적는 일은 커밋 전에(BEFORE_COMMIT), 밖으로 내보내는 일은 커밋 후에(AFTER_COMMIT)

이 형태의 값은 도메인 코드가 아웃박스의 존재를 모른다는 점이다 — 발행 인프라를 나중에 바꿔도 도메인은 그대로다. 대가는 "이 이벤트가 어디서 outbox 행이 되는지"가 코드에서 한 단계 멀어진다는 것이라, 팀이 이벤트 흐름을 추적하는 방식과 함께 고르면 된다.

6. 폴링 릴레이 — FOR UPDATE SKIP LOCKED가 핵심이다

outbox 테이블에 쌓인 행을 읽어 브로커로 보내는 별도 프로세스를 릴레이(relay, 중계기)라고 부른다. 만드는 방법은 크게 둘 — 폴링 퍼블리셔와 CDC다(8절에서 비교). 대부분의 팀이 폴링에서 시작하고, 이 문서에서 가장 실무적인 대목도 여기다.

6-1. 문제부터 — 릴레이를 두 대 띄우면 같은 행을 동시에 집는다

릴레이 1대 = 단일 장애점→ 그래서 보통 여러 대를 띄운다→ 두 인스턴스가 같은 미발행 행을 동시에 집는다→ 둘 다 발행 = 중복 · 둘 다 표시 = 아무도 눈치 못 챔

SELECT ... FOR UPDATE로 잠그면 어떨까. 중복은 막지만 이번엔 두 번째 인스턴스가 첫 번째의 잠금이 풀릴 때까지 그냥 대기한다. 릴레이를 두 대 띄운 의미가 없어진다 — 처리량이 한 대 몫으로 고정된다.

6-2. 구현 — 선점(claim)과 발행(publish)을 나눈다

구현은 두 단계로 나눈다. 여기에 22번 문서에서 배운 원칙이 그대로 적용된다 — DB 트랜잭션을 쥔 채 브로커로 네트워크 호출을 하지 않는다.

1단계 "내가 이 행들을 맡는다"를 짧은 트랜잭션으로 선점만 한다
@Repository
@RequiredArgsConstructor
public class OutboxClaimRepository {

    private final JdbcTemplate jdbcTemplate;

    @Transactional
    public List<OutboxEvent> claim(String workerId, int size) {
        return jdbcTemplate.query("""
            WITH picked AS (
                SELECT id
                  FROM outbox_event
                 WHERE processed_at IS NULL
                   AND (claimed_at IS NULL OR claimed_at < now() - interval '5 minutes')
                 ORDER BY id
                 LIMIT ?
                 FOR UPDATE SKIP LOCKED
            )
            UPDATE outbox_event o
               SET claimed_at = now(), claimed_by = ?, attempts = attempts + 1
              FROM picked
             WHERE o.id = picked.id
         RETURNING o.*
            """, rowMapper, size, workerId);
        // SKIP LOCKED : 다른 릴레이가 이미 잠근 행은 기다리지 않고 건너뛴다.
        // ORDER BY id : 같은 애그리거트의 이벤트가 생성 순서대로 나가게 한다.
        // claimed_at 만료(5분) : 발행 중 릴레이가 죽으면 그 행은 선점된 채 영영
        //   남는다. 시간이 지나면 다른 릴레이가 다시 주워 가게 한다.
        //   → 그래서 이 구조는 필연적으로 at-least-once다.
    }

    @Transactional
    public void markPublished(long id) {
        jdbcTemplate.update(
            "UPDATE outbox_event SET processed_at = now() WHERE id = ?", id);
    }
}
2단계 발행은 트랜잭션 밖에서 — 브로커가 느려도 커넥션을 물지 않는다
@Component
@RequiredArgsConstructor
public class OutboxRelay {

    private final OutboxClaimRepository repository;
    private final EventPublishPort publisher;   // RabbitMQ / Kafka 구현체
    private final String workerId = UUID.randomUUID().toString();

    // fixedDelay: 이전 실행이 "끝난 뒤" 1초를 센다. fixedRate로 두면 발행이
    // 느려질 때 실행이 겹쳐 쌓이므로, 릴레이에는 fixedDelay가 맞다.
    @Scheduled(fixedDelay = 1000)fixedRate가 아니다
    public void relay() {
        List<OutboxEvent> events = repository.claim(workerId, 100);
        for (OutboxEvent event : events) {
            // 이 호출은 DB 트랜잭션 밖이다. 브로커가 3초 걸려도 커넥션은 풀에 있다.
            publisher.publish(event);
        }
    }
}
정직하게 짚을 것 — 더 짧은 구현도 실무에서 통한다 선점과 발행을 나누지 않고 트랜잭션 안에서 그대로 발행하는 구현도 흔하다(코드가 훨씬 짧다). 배치 100건에 브로커 응답이 빠르다면 대체로 견딘다. 다만 그 구조는 브로커 지연이 릴레이의 DB 커넥션 점유로 번역되는 경로를 그대로 남기므로, 릴레이에 전용 커넥션풀을 주고 배치 크기를 작게 잡는 등의 제한을 함께 둬야 한다. 판단 근거를 말할 수 있으면 어느 쪽을 골라도 된다 — 면접에서 점수가 갈리는 지점은 선택이 아니라 근거의 유무다.

7. 발행 확인 — "보냈다"와 "브로커가 받았다"는 다른 사건이다

여기가 RabbitMQ 특유의 함정 — 아웃박스를 만든 이유가 통째로 무너지는 지점

rabbitTemplate.convertAndSend()는 메시지를 소켓에 밀어 넣고 바로 리턴한다. 브로커가 그 메시지를 받아 디스크에 안전하게 넣었는지는 아직 모른다. 이 상태에서 processed_at을 찍으면 "발행했다고 표시했지만 실제로는 브로커에 안 들어간" 유실이 생긴다.

발행 완료 표시는 브로커의 확인 응답(confirm/ack)을 받은 뒤에만 — send() 직후가 아니다

등기우편 비유: 우체통에 넣었다(convertAndSend())와 접수증을 받았다(publisher confirm)는 다른 사건이다. 접수증 없이 장부에 "보냄"이라고 적으면, 중간에 사라진 편지를 영영 못 찾는다 — 아웃박스 테이블에는 발행됐다고 적혀 있으니 재시도 대상에서도 빠진다.

7-1. RabbitMQ — publisher confirms

설정 CORRELATED + returns — 두 가지 실패를 각각 잡는다
@Configuration
public class RabbitConfig {
    @Bean
    public CachingConnectionFactory connectionFactory() {
        CachingConnectionFactory factory = new CachingConnectionFactory(host);
        // CORRELATED: 확인 응답에 우리가 붙인 식별자를 함께 돌려준다.
        // 이게 있어야 "어느 메시지에 대한 ack인지" 알 수 있다.
        factory.setPublisherConfirmType(CachingConnectionFactory.ConfirmType.CORRELATED);
        // 라우팅될 큐가 하나도 없으면 되돌려 받기 위한 설정.
        // confirm만으로는 "브로커는 받았지만 아무 큐에도 안 들어간" 상황을 못 잡는다.
        factory.setPublisherReturns(true);
        return factory;
    }
}
발행자 "발행 완료" 표시는 반드시 콜백 안에서
@Component
@RequiredArgsConstructor
public class RabbitOutboxPublisher implements EventPublishPort {

    private final RabbitTemplate rabbitTemplate;
    private final OutboxClaimRepository repository;

    @PostConstruct
    void registerCallback() {
        // 확인 응답은 비동기로 온다. 그래서 "발행 완료" 표시는 반드시
        // 이 콜백 안에서 해야 한다 — convertAndSend() 직후가 아니다.
        rabbitTemplate.setConfirmCallback((correlation, ack, cause) -> {
            long outboxId = Long.parseLong(correlation.getId());
            if (ack) {
                repository.markPublished(outboxId);여기서만 표시한다
            } else {
                // nack: 브로커가 책임질 수 없다고 답한 것. 표시하지 않고 두면
                // claimed_at 만료 후 다른 주기에 다시 집어 재시도된다.
                log.warn("outbox nack id={} cause={}", outboxId, cause);
            }
        });
        rabbitTemplate.setMandatory(true);
        rabbitTemplate.setReturnsCallback(returned ->
            log.error("라우팅 실패 — 바인딩 설정 오류 가능: {}", returned.getMessage()));
    }

    @Override
    public void publish(OutboxEvent event) {
        // CorrelationData에 outbox의 PK를 실어 보낸다. 콜백에서 이 값으로
        // 어느 행을 발행 완료로 표시할지 찾는다.
        rabbitTemplate.convertAndSend(
                exchangeOf(event), routingKeyOf(event), event.payload(),
                new CorrelationData(String.valueOf(event.id())));
    }
}

암기 카드 — RabbitMQ에서 메시지가 살아남으려면 셋이 동시에 필요하다

메시지 persistent  +  큐 durable  +  브로커 확인(confirm)

셋 중 하나라도 빠지면 브로커 재시작 시 메시지가 사라진다. 아웃박스를 아무리 잘 만들어도 브로커 쪽 세 조건이 안 맞으면 유실은 그대로라는 점이 요지다. (상세는 06-messaging/13-rabbitmq-durability-publisher-confirms.md, 아웃박스와의 결합 전체는 06-messaging/20-rabbitmq-outbox-polling-publisher.md.)

7-2. Kafka — CompletableFuture와 acks=all

Kafka는 확인 응답을 CompletableFuture로 돌려주므로 형태가 조금 다르다. 원칙은 동일하다 — ack 확인 후에만 표시한다.

Kafka 키를 aggregate_id로 주는 것이 순서 보장의 열쇠다
@Override
public void publish(OutboxEvent event) {
    // 키를 aggregate_id로 준다. Kafka는 같은 키를 같은 파티션에 보내고
    // 파티션 안에서는 순서가 보장되므로, "같은 주문의 이벤트 순서"가 지켜진다.
    kafkaTemplate.send(topicOf(event), event.aggregateId(), event.payload())
        .whenComplete((result, ex) -> {
            if (ex == null) {
                repository.markPublished(event.id());   // ack 확인 후에만 표시
            } else {
                log.warn("kafka 발행 실패 id={}", event.id(), ex);
            }
        });
}
acks=1이면 아웃박스가 거짓말을 하게 된다 프로듀서 설정에서 acks=all(모든 in-sync 복제본이 받아야 ack)을 함께 잡아야 브로커 한 대가 죽어도 유실되지 않는다. acks=1이면 리더만 받고 ack가 오므로, 리더가 복제 전에 죽으면 아웃박스에는 발행 완료로 표시됐는데 메시지는 사라진 상태가 된다 — 7절 상단의 잘못된 구현과 결과가 같아진다.

9-2. 순서 — SKIP LOCKED가 처리량을 준 대가

"같은 주문의 CREATED → PAID → SHIPPED가 순서대로 소비돼야 한다"는 요구가 있다면 주의할 지점이 브로커 쪽과 릴레이 쪽 둘인데, 진짜 문제는 릴레이 쪽이다.

대응은 셋 중 하나. 무엇을 포기할지가 각각 다르다.
대응방법포기하는 것 / 조건
단일 릴레이로 운영가장 단순하다. ShedLock 같은 분산 락으로 "여러 인스턴스 중 한 번에 하나만 실행"을 강제하면 가용성은 유지하면서 순서를 지킬 수 있다처리량이 한 대 몫. 이벤트량이 적으면 이걸로 충분하다
애그리거트 단위로 분할hash(aggregate_id) % 릴레이수로 담당을 고정한다. 같은 주문의 이벤트는 항상 같은 릴레이가 처리순서 유지 + 처리량은 릴레이 수만큼. 대신 릴레이 수 변경 시 재배치를 다뤄야 한다
소비자가 흡수이벤트에 시퀀스 번호를 넣고 소비자가 "이미 더 나중 상태면 무시"하도록 만든다 — 상태 기계 가드와 같은 발상소비자 구현이 복잡해진다. 대신 생산 측 제약이 사라진다
답변에 꼭 넣을 한 문장 "순서 요구가 실제로 있는지부터 따진다." 상당수의 이벤트는 순서와 무관하고, 순서 보장은 공짜가 아니다 — 위 표의 세 대응이 모두 처리량·복잡도·유연성 중 하나를 지불한다. 요구를 확인하지 않고 순서 보장부터 설계하면 필요 없는 비용을 낸다.

9-3. 조용한 죽음 — 지표에 알람을 거는 것이 구현의 일부다

아웃박스 운영에서 가장 위험한 장애 — 릴레이가 멈추는 것

애플리케이션 정상+ 주문도 잘 저장됨+ 에러 로그 없음→ 다만 outbox 테이블에 행만 쌓인다

며칠 뒤 다른 팀이 "우리 쪽에 이벤트가 안 들어온다"고 알려주기 전까지 아무도 모른다. 1절의 "유실은 소리를 내지 않는다"가 운영 단계에서 그대로 재현되는 것이다. 그래서 지표에 알람을 거는 것이 구현의 일부다.

모니터링 이 두 쿼리를 대시보드와 알람에 건다
-- 발행 적체: 미처리인 채 N분 넘은 건수. 이 값이 0보다 크게 유지되면 릴레이 이상.
SELECT count(*) AS backlog,
       max(now() - created_at) AS oldest_age이게 특히 좋은 지표다
  FROM outbox_event
 WHERE processed_at IS NULL
   AND created_at < now() - interval '5 minutes';

-- 독성 이벤트(poison event): 반복 실패로 attempts만 올라가는 행
SELECT id, event_type, attempts, last_error
  FROM outbox_event
 WHERE processed_at IS NULL AND attempts > 10;

backlog — 건수

트래픽에 따라 출렁인다. 피크 시간에는 정상적으로도 커지므로 절대값 임계치를 잡기 어렵다.

oldest_age — 가장 오래된 미처리 행의 나이

"발행이 얼마나 밀렸는가"를 직접 말해준다. 트래픽과 거의 무관하므로 "5분 넘으면 알람" 같은 임계치를 그대로 쓸 수 있다.

10. 결론 — 보장은 at-least-once, 그래서 멱등 소비자가 짝이다

릴레이는 "발행 → 표시" 순서로 일한다. 발행은 성공했는데 processed_at을 찍기 전에 릴레이가 죽으면, 그 행은 미처리로 남아 다음 주기에 한 번 더 발행된다.

이벤트 고유 ID(outbox의 PK). 그래서 반드시 메시지에 실어 보내야 한다 — 4-2 스키마의 첫 컬럼이 여기서 회수된다.
원자성
조회 후 INSERT가 아니라 INSERT 먼저. 유니크 제약은 DB가 쓰기 시점에 원자적으로 판정한다.
같은 트랜잭션
이력 기록과 비즈니스 처리를 따로 커밋하면 "이력은 남았는데 처리는 롤백된" 이벤트가 영영 재처리되지 않는다.

여기서의 exactly-once는 전달 보장이 아니라 "효과의 일회성"이라는 점까지 짚으면 정확하다. 키 선정·이력 보관 기간 같은 구현 디테일은 06-messaging/04-idempotent-consumer-implementation.md에 있다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 면접 전날 30초 인출 카드

이중 쓰기의 두 실패는?
커밋 먼저 = 유실(조용하다, 대사로 발견) / 발행 먼저 = 거짓 이벤트(시끄럽다, 소비자 예외). 순서 조정으로는 못 푼다.
try-catch로 안 되는 이유는?
catch는 프로세스가 살아 있어야 실행된다. kill -9·OOM·파드 축출·배포 재시작에서는 안 돈다. 코드가 아니라 구조 문제.
2PC 배제 3종은?
가·잠·자 — 가용성 곱(99.9%²=99.8%) · 잠금 블로킹(in-doubt) · 자격 없음(Kafka·RabbitMQ 모두 XA ✗).
AFTER_COMMIT의 보장은?
at-most-once. 거짓 이벤트는 막지만 이벤트가 힙에만 있어 유실을 못 막고, 재시도할 대상 자체가 없다.
아웃박스 한 줄 정의는?
"보낼 사실"을 비즈니스 변경과 같은 트랜잭션으로 같은 DB에 INSERT해 이중 쓰기를 단일 쓰기로 바꾼 것.
파이프라인 4단계는?
적고(INSERT) · 집고(claim) · 보내고(publish) · 표시한다(mark). 표시는 confirm/ack 뒤에만.
폴링 기준 컬럼은?
WHERE processed_at IS NULL. "마지막 처리 id 이후"는 금지 — 시퀀스 순서 ≠ 커밋 순서라 뒤늦게 커밋된 행을 건너뛴다.
릴레이 여러 대의 열쇠는?
FOR UPDATE SKIP LOCKED(PostgreSQL 9.5+). FOR UPDATE만 쓰면 줄을 서서 처리량이 한 대 몫이 된다.
phase를 어떻게 나누나?
DB에 적는 일은 BEFORE_COMMIT(트랜잭션에 포함), 밖으로 내보내는 일은 AFTER_COMMIT. 반대로 하면 둘 다 조용히 실패.
발행 완료 표시 시점은?
RabbitMQ: confirm 콜백 안 / Kafka: ack 후. send() 직후에 찍으면 아웃박스가 거짓말을 한다. Kafka는 acks=all까지.
폴링 vs CDC 축은?
지연 · DB 부하 · 운영 복잡도. RabbitMQ면 사실상 폴링. 급소는 각각 조용한 죽음과 복제 슬롯 적체(디스크 고갈).
운영 리스크 3종은?
비·순·죽 — 비대화(파티션 드롭) · 순서(릴레이 분할/ShedLock) · 죽음(oldest_age 알람).
최종 보장과 짝은?
at-least-once → 멱등 소비자 필수. 생산 측 유실 방지 + 소비 측 중복 제거 = 효과의 exactly-once.
패턴이 깨지는 전제는?
outbox가 비즈니스 테이블과 같은 DB여야 한다. 전용 DB로 분리하는 순간 이중 쓰기가 부활한다.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

AFTER_COMMIT 리스너에서 발행하고, 실패하면 재시도하면 아웃박스 없이도 되지 않나요? 필수힌트: "재시도가 안 된다"가 아니라 "재시도할 대상이 없다"로 답한다

재시도 로직은 프로세스가 살아 있어야 실행된다. 커밋 직후 서버가 크래시되거나 재배포로 재시작되면 이벤트 객체는 힙에만 있었으므로 재시도할 대상 자체가 사라진다. @Async를 썼다면 실행 대기 중이던 인메모리 큐도 통째로 사라진다.

더 근본적인 문제는 "무엇을 못 보냈는지"의 영속적 기록이 없다는 것이다. 장애 복구 후 어떤 이벤트를 다시 보내야 하는지 알아낼 방법이 없어, 결국 비즈니스 테이블을 뒤져 "이벤트가 나갔어야 할 것 같은" 행을 추정해야 한다.

아웃박스의 본질은 재시도가 아니라 "보내야 할 것"의 내구성 있는 기록이고, 그 기록을 비즈니스 변경과 원자적으로 남긴다는 점이다. 재시도는 그 기록이 있어서 가능해진 부수 효과에 가깝다.

그럼 브로커에 먼저 발행하고 나서 DB를 커밋하면 안 되나요? 함정힌트: "방향만 바뀔 뿐"에서 시작해, 그래도 남는 차이(발견 난이도)까지 정직하게 말한다

방향만 바뀔 뿐 똑같이 깨진다. 발행 후 커밋이 실패하면(유니크 제약 위반, 데드락 롤백, 크래시) 존재하지 않는 데이터에 대한 거짓 이벤트가 이미 소비자에게 전달된 뒤다. 브로커 발행에는 롤백이 없다 — 메시지가 브로커에 들어가는 순간 그것은 이미 소비자에게 전달됐을 수도 있는 과거이고, 우리 트랜잭션이 롤백된다고 해서 소비자의 머릿속에서 그 이벤트가 지워지지 않는다.

굳이 비교하면 유실보다 거짓 이벤트가 발견은 쉽다 — 소비자가 없는 주문을 조회하다 예외를 던지므로 로그에 남는다. 하지만 그 사이 재고가 깎이거나 정산이 잡혔다면 이미 오염이 발생한 뒤다.

핵심은 순서 조정으로는 못 푼다는 것이다. 원자성이 필요한 두 쓰기가 서로 다른 시스템에 있는 한, 어느 순서로 놓아도 그 사이에 틈이 있다. 두 쓰기를 같은 시스템(DB) 안으로 모으는 구조 변경만이 답이다.

왜 XA/2PC로 DB와 브로커를 묶지 않나요? 시니어 변별힌트: 세 가지를 "판단 두 개 → 사실 하나" 순서로. 마지막에 아웃박스의 정체를 한 문장으로 재정의한다

첫째, 가용성이 곱으로 떨어진다. 2PC는 두 참여자가 동시에 살아 있어야 성립하므로 99.9% × 99.9% = 99.8%, 연간 다운타임이 8.76시간에서 17.5시간으로 두 배가 된다. 그리고 그 영향이 "이벤트 발행 실패"에 그치지 않고 주문 저장 자체의 실패로 나타난다 — 부수적인 기능 때문에 핵심 기능의 가용성을 깎는 셈이다.

둘째, prepare 이후 참여자가 잠금을 쥔 채 블로킹된다. 코디네이터가 죽으면 결정을 못 받은 in-doubt 트랜잭션이 잠금을 쥔 채 남아 운영자의 수동 판정이 필요해진다. 한 지점의 장애가 DB 전체의 잠금 정체로 번진다.

셋째, 애초에 브로커가 XA를 지원하지 않는다. Kafka 트랜잭션은 Kafka 내부(프로듀서 → 토픽 → 컨슈머 오프셋)의 원자성이지 외부 DB와 묶이는 XA가 아니고, RabbitMQ의 채널 트랜잭션(txSelect/txCommit)도 마찬가지다. 참여 자격이 없으므로 논의가 성립하지 않는다.

여기에 한 문장을 덧붙이면 좋다. 아웃박스는 "분산 원자성을 포기하고, 로컬 원자성 + 비동기 전달 + 소비자 멱등성으로 같은 효과를 재구성한 것"이다. 문제를 푼 것이 아니라, 문제가 성립하지 않는 형태로 바꾼 것에 가깝다.

아웃박스는 중복 발행이 가능하다는데, 그러면 정합성이 깨지는 것 아닌가요? 필수힌트: "결함이 아니라 의도적 교환"으로 규정한 뒤, 중복 제거의 책임 소재와 원자성 조건까지

아웃박스가 제공하는 것은 at-least-once다. 유실은 없지만 중복은 있다. 그리고 그것은 결함이 아니라 의도적 교환이다 — 유실된 이벤트는 되돌릴 수 없지만 중복된 이벤트는 소비자가 걸러낼 수 있으므로, 둘 중 하나를 골라야 한다면 중복이 훨씬 다루기 쉽다.

중복 제거는 소비 측에서 한다. 이벤트 고유 ID를 처리 이력 테이블에 유니크 제약으로 INSERT하고, 이미 있으면 조용히 스킵한다. 이때 처리 이력 기록과 비즈니스 처리를 같은 트랜잭션으로 묶는 것이 핵심이다 — 따로 커밋하면 "이력은 남았는데 처리는 롤백된" 이벤트가 영영 재처리되지 않는다.

정리하면 "생산 측은 유실 방지, 소비 측은 중복 제거"로 역할을 나눠 결과적으로 exactly-once에 상응하는 효과에 도달하는 구조다. 이때의 exactly-once는 전달 보장이 아니라 효과의 일회성이라는 점까지 짚으면 정확하다.

폴링 릴레이와 CDC 중 무엇을 선택하나요? 필수힌트: 축 세 개를 먼저 세우고, 마지막에 "되돌릴 수 있는 결정"이라는 점을 붙인다

트레이드오프 축은 지연 · DB 부하 · 운영 복잡도 셋이다.

폴링은 추가 인프라 없이 스케줄러로 끝나지만 주기만큼 지연되고 주기적 쿼리가 DB를 때린다. 이벤트 빈도가 낮고 몇 초 지연이 허용되면 이걸로 충분하다. 특히 RabbitMQ 환경에서는 Debezium 같은 표준 CDC 경로가 없으므로 폴링이 사실상 기본 선택이다.

CDC는 WAL 구독이라 지연과 부하 면에서 우수하지만 Debezium/Kafka Connect 운영이라는 새 부담이 생기고, 복제 슬롯이 적체되면 WAL이 쌓여 DB 디스크가 차는 종류의 장애를 새로 떠안는다.

판단 기준에 "우리 팀이 그 인프라를 운영할 수 있는가"를 넣어 답하면 좋다. 그리고 아웃박스 테이블 스키마와 쓰기 경로가 동일하므로 폴링으로 시작해 나중에 CDC로 갈아타는 경로가 열려 있다는 점을 덧붙이면, 되돌릴 수 있는 결정과 아닌 결정을 구분하는 감각을 보여줄 수 있다.

릴레이를 여러 인스턴스로 띄우면 같은 이벤트를 동시에 발행하지 않나요? 가산점힌트: FOR UPDATE만으로는 왜 부족한지 → SKIP LOCKED → 그래도 남는 것(순서·at-least-once)

폴링 쿼리에 SELECT ... FOR UPDATE SKIP LOCKED를 쓴다. FOR UPDATE만 쓰면 두 번째 인스턴스가 잠금이 풀릴 때까지 기다리므로 릴레이를 늘린 의미가 없어지는데, SKIP LOCKED는 잠긴 행을 건너뛰고 다음 행을 집게 해서 인스턴스 수만큼 처리량이 늘어난다. PostgreSQL 9.5부터 쓸 수 있다.

더 단순하게 가려면 ShedLock 같은 분산 락으로 릴레이 자체가 한 번에 하나만 돌게 만든다. 순서 보장이 필요한 도메인에서는 오히려 이쪽이 맞다 — SKIP LOCKED는 처리량을 주는 대신 같은 애그리거트 이벤트의 발행 순서를 흔든다.

어느 쪽이든 at-least-once 특성은 남는다. 발행 후 표시 전에 죽으면 재발행되므로 멱등 소비자는 여전히 필수다.

아웃박스 테이블이 병목이 되지는 않나요? 가산점힌트: 쓰기·읽기·공간 세 방향으로 쪼개고, 마지막에 "전용 DB 분리"라는 유혹을 스스로 차단한다

쓰기 부하 — 아웃박스 INSERT는 비즈니스 트랜잭션에 쓰기 한 건을 더한다. append-only INSERT라 인덱스 갱신도 가볍지만, 트랜잭션 지속 시간이 조금 길어지는 것은 사실이다. 커넥션 점유 시간이 늘어나므로 22번 문서의 계산이 그대로 적용된다.

읽기 부하 — 4-2의 부분 인덱스(WHERE processed_at IS NULL)로 해결한다. 발행 완료 행이 아무리 쌓여도 인덱스 크기는 미처리 건수에 비례하므로, 폴링 쿼리는 테이블 크기와 무관하게 일정한 비용을 유지한다.

공간과 부풀림 — 9-1의 정리 배치 또는 파티셔닝이다. PostgreSQL에서는 DELETE가 죽은 튜플을 남긴다는 점 때문에 대량 삭제보다 파티션 드롭이 우월하다 — VACUUM 없이 파일 삭제로 끝난다.

정말로 병목이 된다면 그다음 선택지는 아웃박스 전용 DB 분리인데, 그 순간 비즈니스 변경과 outbox INSERT가 다시 다른 시스템이 되어 이중 쓰기 문제가 부활한다. 아웃박스는 "같은 DB"라는 전제 위에서만 성립하는 패턴이라는 점을 짚으면 패턴을 이해했다는 신호가 된다.

스프링 이벤트를 유지하고 싶어서 AFTER_COMMIT 리스너 안에서 outbox 행을 INSERT했습니다. 왜 행이 안 생기나요? 함정힌트: 그 시점에 트랜잭션은 이미 어떤 상태인가

커밋이 이미 끝난 뒤이기 때문이다. AFTER_COMMIT 콜백은 이름 그대로 커밋 이후에 실행되므로, 그 안에서 하는 INSERT는 원래 트랜잭션에 포함되지 않는다. 별도의 트랜잭션 처리를 명시하지 않으면 그 쓰기는 flush될 기회를 얻지 못하고 조용히 사라진다 — 예외도 로그도 없이 outbox 행만 안 생긴다.

아웃박스가 성립하는 조건을 다시 보면 답이 명확하다. 비즈니스 변경과 outbox INSERT가 하나의 트랜잭션 안에서 함께 커밋돼야 한다. 그러려면 INSERT는 커밋 전에 일어나야 한다.

그래서 어댑터 리스너를 둘 때는 phase = TransactionPhase.BEFORE_COMMIT이다. 규칙으로 압축하면 — DB에 적는 일은 커밋 전에, 밖으로 내보내는 일은 커밋 후에. 반대로 하면 양쪽 다 조용히 실패한다(전자는 행이 안 생기고, 후자는 거짓 이벤트가 나간다).

폴링할 때 "마지막으로 처리한 id 이후"만 읽으면 커서 하나로 끝나는데, 왜 안 쓰나요? 함정힌트: 시퀀스 값이 할당되는 시점과 커밋되는 시점은 같지 않다

이벤트를 건너뛴다. PostgreSQL에서 시퀀스 값은 INSERT 시점에 할당되지만 커밋 순서는 그와 다를 수 있기 때문이다.

트랜잭션 A가 id=100을 받아 놓고 처리가 길어져 나중에 커밋하고, 트랜잭션 B가 id=101을 받아 먼저 커밋했다고 하자. 릴레이가 그 사이에 조회하면 101만 보인다. 여기서 "마지막 처리 id = 101"을 기록해 두면, 뒤늦게 커밋된 100은 영영 조회되지 않는다.

그래서 기준은 반드시 미처리 플래그여야 한다 — WHERE processed_at IS NULL. 커밋되지 않은 행은 애초에 보이지 않고, 뒤늦게 커밋되면 그때 보이기 시작한다. 이 조건은 커밋 순서에 의존하지 않으므로 안전하다. 성능이 걱정된다면 커서가 아니라 부분 인덱스로 푼다.

convertAndSend()가 예외 없이 리턴했으면 발행에 성공한 것 아닌가요? 함정힌트: 그 호출이 보장하는 범위가 어디까지인지 — 소켓인가, 브로커 디스크인가

아니다. rabbitTemplate.convertAndSend()는 메시지를 소켓에 밀어 넣고 바로 리턴한다. 브로커가 그 메시지를 받아 안전하게 보관했는지는 아직 모른다. 이 상태에서 processed_at을 찍으면 "발행했다고 표시했지만 실제로는 브로커에 안 들어간" 유실이 생기고, 그 행은 재시도 대상에서도 빠진다 — 아웃박스를 만든 이유가 마지막 한 줄에서 통째로 무너진다.

그래서 publisher confirms를 켜고(ConfirmType.CORRELATED), CorrelationData에 outbox의 PK를 실어 보낸 뒤 confirm 콜백 안에서만 발행 완료를 표시한다. 확인 응답은 비동기로 오므로 어느 메시지에 대한 ack인지 식별할 수단이 반드시 필요하다.

한 가지 더 — confirm만으로는 "브로커는 받았지만 아무 큐에도 라우팅되지 않은" 상황을 못 잡는다. 그래서 setPublisherReturns(true) + setMandatory(true) + returns 콜백으로 라우팅 실패를 따로 잡아야 한다(대개 바인딩 설정 오류다). Kafka라면 같은 자리에 acks=all이 온다.

별도 outbox 테이블 없이 비즈니스 테이블에 event_sent 플래그를 두고 폴링하면 안 되나요? 가산점힌트: "상태"와 "사건"의 차이. 그리고 그 테이블을 나중에 지울 수 있는가

작은 규모에서는 실제로 통하는 변형이다. 테이블을 하나 덜 만들고, 원자성도 그대로 성립한다(같은 트랜잭션 안의 같은 행 UPDATE니까). 다만 네 가지를 포기하게 된다.

① 사건이 아니라 상태만 남는다. 아웃박스 행은 "이때 이런 일이 일어났다"는 사건의 기록이지만, 플래그는 "지금 이 행의 상태"일 뿐이다. 한 폴링 주기 안에 상태가 두 번 바뀌면 중간 전이 이벤트는 발행되지 않는다. 같은 이유로 한 애그리거트에 여러 종류의 이벤트를 실을 수도 없다.

② 페이로드 스냅샷이 없다. 릴레이가 발행할 때 읽는 것은 "그때의 값"이 아니라 "지금 값"이라, 발행이 밀린 사이 값이 바뀌면 사실과 다른 페이로드가 나간다. outbox의 payload는 커밋 시점의 스냅샷을 얼려 둔 것이다.

③ 발행 관심사가 비즈니스 테이블에 침투한다. 발행용 컬럼·인덱스·재시도 카운터가 가장 뜨거운 테이블에 붙고, 발행 완료 UPDATE가 비즈니스 행을 계속 갱신한다.

④ 정리를 못 한다. outbox는 발행 후 삭제하거나 파티션을 드롭할 수 있지만, 비즈니스 데이터는 지울 수 없다. 발행 이력이 영구히 따라다닌다. — 정리하면 이벤트 종류가 하나뿐이고 빈도가 낮으면 선택지지만, 이벤트가 늘어나는 순간 별도 테이블로 가는 것이 정석이다.

아웃박스를 도입했는데도 이벤트가 유실될 수 있는 경로가 남아 있나요? 시니어 변별힌트: 아웃박스가 보장하는 구간은 "커밋까지"다. 그 오른쪽의 각 경계를 하나씩 짚는다

남는다. 아웃박스가 원자적으로 보장하는 것은 "커밋됐으면 outbox 행이 반드시 있다"까지이고, 그 오른쪽은 각각 따로 지켜야 한다. 실무에서 나오는 경로는 다섯이다.

① 확인 전에 표시하는 구현 — send() 직후 processed_at을 찍으면 브로커에 안 들어간 메시지가 재시도 대상에서 빠진다. 가장 흔한 실수다.

② Kafka acks=1 + 리더 장애 — 리더만 받고 ack가 오므로 복제 전에 리더가 죽으면 아웃박스에는 발행 완료인데 메시지는 사라진다. acks=all로 막는다.

③ RabbitMQ의 세 조건 중 하나 누락 — 메시지 persistent + 큐 durable + confirm이 동시에 필요하다. 하나라도 빠지면 브로커 재시작 시 메시지가 사라진다.

④ 라우팅 실패 — 브로커는 받았지만 바인딩이 없어 아무 큐에도 안 들어간 경우. confirm은 ack로 오므로 표시까지 정상적으로 되고 메시지만 없다. mandatory + returns 콜백으로 잡는다.

⑤ 정리 배치의 조건 누락 — DELETE ... WHERE created_at < ...처럼 processed_at 조건 없이 오래된 행을 지우면 아직 발행 못 한 행까지 지워진다. 이건 복구 불가능한 유실이다. 정리 조건은 반드시 processed_at < now() - interval '...'이어야 한다 — 미발행 행(NULL)은 이 조건에 걸리지 않는다. 여기에 소비 측의 처리 전 ack(auto-ack)까지 더하면, "아웃박스를 썼는데 왜 유실이 나느냐"의 원인 목록이 완성된다.

그럼 모든 이벤트를 아웃박스로 보내면 되지 않나요? 필수힌트: 딸려 오는 운영 대상을 먼저 세고, 판단 질문 하나로 기준을 만든다

무조건 아웃박스가 정답은 아니다. 아웃박스에는 테이블, 릴레이 프로세스, 정리 배치(또는 파티션 관리), 적체 모니터링이 전부 딸려 온다. 요구사항이 그 비용을 정당화하는지 판단하는 것이 설계다.

기준은 질문 하나다 — "이 이벤트가 한 건 빠지면 무슨 일이 생기는가."

빠져도 되는 것(마케팅 푸시, 최근 본 상품, 대시보드 집계): 한 건 유실이 데이터 불일치를 만들지 않는다 → AFTER_COMMIT + @Async + 실패 로그로 충분하다.

빠지면 안 되는 것(정산 원장, 재고 차감, 타 서비스 상태 동기화, 포인트 적립): 유실이 곧 정합성 깨짐이고 나중에 대사로 찾아내 수동 보정해야 한다 → 아웃박스로 간다. 이 구분을 요구사항에서 스스로 끌어내는 것이 답변의 설계 감각 부분이고, 반대로 "전부 아웃박스"라고 답하면 비용을 계산하지 않은 사람으로 들린다.

한 줄 요약
DB와 브로커는 서로 다른 시스템이라 한 트랜잭션으로 묶을 수 없어 커밋 먼저면 유실, 발행 먼저면 거짓 이벤트라는 이중 쓰기 딜레마가 생기고, 프로세스가 죽으면 catch도 안 돌기에 코드가 아니라 구조로 풀어야 하며, XA/2PC는 가용성이 곱으로 떨어지고 Kafka·RabbitMQ 모두 참여 자격이 없어 배제된다 — 스프링의 @TransactionalEventListener(AFTER_COMMIT)은 거짓 이벤트만 막을 뿐 메모리 이벤트의 유실(at-most-once)을 못 막으므로, "보낼 이벤트"를 비즈니스 변경과 같은 트랜잭션으로 같은 DB의 outbox 테이블에 INSERT해 이중 쓰기를 단일 쓰기로 바꾸고, 폴링 릴레이가 FOR UPDATE SKIP LOCKED로 행을 나눠 집어 RabbitMQ publisher confirm(또는 Kafka ack) 콜백에서 발행 완료를 표시하며, 테이블 비대화는 파티션 드롭으로, 순서는 릴레이 분할로, 남는 at-least-once 중복은 멱등 소비자로 마감하는 것이 완성형이다.
