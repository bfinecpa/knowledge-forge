반복되는 인증 사용자 조회 제거
인터셉터 + 커스텀 ArgumentResolver — "빠뜨릴 자리"를 없애는 구조

면접 질문: "컨트롤러마다 반복되는 인증 사용자 조회/검증 코드를 어떻게 제거하나요? (커스텀 ArgumentResolver, 인터셉터)"

핵심 관전 포인트 — 컨트롤러마다 반복되는 "토큰 추출 → 사용자 조회 → 검증" 코드는 역할을 둘로 쪼개 제거한다. 검증하고 차단하는 일은 요청 앞단(필터 또는 인터셉터)이 맡고, 컨트롤러 파라미터에 사용자 객체를 채워 넣는 일은 커스텀 HandlerMethodArgumentResolver가 맡는다. 이 분리가 취향이 아니라 필수인 이유는, 검증까지 리졸버에 넣으면 @AuthUser 파라미터가 없는 컨트롤러 메서드는 리졸버가 호출조차 되지 않아 검증을 통째로 건너뛰기 때문이다 — 인증이 "붙이면 되는 것"이 아니라 "빠뜨릴 수 없는 것"이 되게 만드는 구조가 출제 의도의 본체다. 앞단을 필터로 할지 인터셉터로 할지는 예외 처리 일관성 · 커버리지 · 경로 매칭 세 축으로 갈리고, 전달 통로로 ThreadLocal을 쓴다면 톰캣 스레드가 재사용되므로 afterCompletion에서 반드시 remove()해야 다음 요청이 이전 사용자 정보를 보는 사고를 막는다. 스프링 시큐리티를 쓰고 있다면 @AuthenticationPrincipal이 이미 같은 구조를 제공한다는 것도 정직하게 짚어야 한다.
  • 1
    역할을 둘로 쪼갠다 — 검증·차단은 앞단(인터셉터 preHandle 또는 필터), 주입은 커스텀 HandlerMethodArgumentResolver. 앞단이 통과시킨 요청에 사용자 정보를 실어 두면, 리졸버는 그것을 꺼내 파라미터로 넘기기만 한다. 결과적으로 컨트롤러에는 myOrders(@AuthUser LoginUser user) 한 줄만 남는다.
  • 2
    이 분리가 필수인 이유를 말해야 답이 완성된다 — 리졸버는 "파라미터를 채우려고" 불리는 부품이라 채울 파라미터가 없으면 호출되지 않는다. 검증까지 리졸버에 넣으면 인증 조건이 "그 메서드에 @AuthUser를 적었는가"로 바뀌어, 안 적은 메서드가 무인증으로 열리고 그 구멍이 정상처럼 보인다. 원리로는 "차단은 모든 요청이 반드시 지나가는 자리에, 주입은 값이 필요한 곳에"다.
  • 3
    남는 축은 셋이고 전부 짚을 수 있어야 한다 — ① 앞단을 필터/인터셉터 중 무엇으로 할지는 예외 처리 일관성 · 커버리지 · 경로 매칭으로 갈린다. ② 전달 통로를 ThreadLocal로 쓰면 톰캣 스레드 재사용 때문에 afterCompletion에서 remove()가 필수다(기본값은 request attribute). ③ 스프링 시큐리티를 쓴다면 @AuthenticationPrincipal이 이미 같은 구조이므로, 커스텀은 시큐리티 미도입이거나 도메인 객체 변환이 필요할 때의 선택지다.

0. 질문 + 출제 의도

질문: "컨트롤러마다 반복되는 인증 사용자 조회/검증 코드를 어떻게 제거하나요? (커스텀 ArgumentResolver, 인터셉터)"

출제 의도: 컨트롤러마다 토큰 파싱·사용자 조회가 복붙되면 검증 누락 한 곳이 곧 보안 구멍이다. 횡단 관심사를 프레임워크 확장점으로 옮겨 "실수할 수 없는 구조"를 만드는지 — 프레임워크를 쓰는 수준을 넘어 확장하는 수준인지 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "중복 제거"에서 멈추는 것 → 1절에서 진짜 문제가 "빠뜨려도 아무 일도 안 일어난다"임을 도식으로 못 박는다. 목표는 코드를 줄이는 것이 아니라 빠뜨릴 자리를 없애는 것이다.
② 커스텀 리졸버를 "무겁고 특수한 마법"으로 보는 것 → 2절에서 @RequestBody·@PathVariable도 같은 인터페이스의 구현체임을 표와 파이프라인 위치로 보인다. 여기에 supportsParameter의 판정이 캐싱된다는 시니어 변별 지점을 얹는다.
③ "리졸버가 검증까지 다 하면 되지 않나"에서 무너지는 것 → 3절의 대비 도식이 이 문서의 설계 논점 본체다. 같은 컨트롤러 안에서도 메서드마다 인증이 걸렸다 안 걸렸다 하는 그림을 그린다.
한 문장 비유 — 공항 보안검색대와 좌석 배정 보안검색대(앞단: 필터·인터셉터)는 모든 승객이 반드시 지나가는 통로에 있다. 목적지가 어디든, 티켓에 무엇이 적혔든 상관없이 걸린다. 좌석 배정(리졸버)은 탑승권에 좌석 칸이 있는 사람에게만 해 주면 된다 — 값을 필요로 하는 곳에서 하는 일이기 때문이다. 검색을 좌석 배정 창구로 옮기면? 좌석 칸이 없는 탑승권을 든 사람은 검색 없이 비행기에 탄다. 3절이 정확히 이 이야기다.

1. 문제 — "중복이 있다"가 아니라 "구멍이 정상처럼 보인다"

Before 모든 컨트롤러 메서드마다 반복되는 네 줄
@GetMapping("/orders")
public List<Order> myOrders(@RequestHeader("Authorization") String token) {
    String userId = tokenParser.parse(token);          // ① 헤더에서 토큰을 꺼내 파싱
    LoginUser user = userService.findById(userId);     // ② 사용자 조회
    if (user == null || user.isLocked()) {             // ③ 검증
        throw new UnauthorizedException();
    }
    return orderService.findByUser(user);              // ④ 여기서부터가 진짜 로직
}

이 코드의 문제를 "중복이 있다"로만 보면 해결책도 얕아진다. 위험은 두 층이다.

층 1 — 변경 비용이 곱해진다

"잠긴 계정도 조회는 허용"처럼 정책이 하나 바뀌면 수십 곳을 고쳐야 한다. 이건 아프지만 눈에 보이는 비용이다 — 고치다 빠뜨리면 테스트가 잡아줄 여지라도 있다.

층 2 — 빠뜨려도 아무 일이 없다 본체

새 엔드포인트에서 ①~③을 안 붙이면 컴파일 에러도, 테스트 실패도, 런타임 예외도 없다. 그냥 인증 없이 잘 동작하는 API가 하나 생긴다. 아무도 모르는 채로.

이 문서 전체를 관통하는 목표 문장

목표는 중복 제거가 아니라 "빠뜨릴 자리를 없애는 것"

이 문장을 쥐고 있어야 3절(왜 리졸버 혼자 하면 안 되는가)과 7절(경로 설정의 방향)이 같은 원리의 두 사례로 읽힌다. 면접에서도 이 한 문장을 먼저 깔고 구현을 설명하면 "기술을 아는 사람"이 아니라 "구조를 설계하는 사람"으로 들린다.

After 컨트롤러에는 비즈니스 로직만 남는다 — 이것이 목표 지점
@GetMapping("/orders")
public List<Order> myOrders(@AuthUser LoginUser user) {토큰·조회·검증이 전부 사라졌다
    return orderService.findByUser(user);
}

2. 확장점의 정체 — HandlerMethodArgumentResolver는 우리가 발명하는 물건이 아니다

@AuthUser LoginUser user라는 파라미터에 값이 어떻게 들어가는지를 이해하려면, 컨트롤러 메서드의 파라미터를 원래 누가 채우는가를 먼저 알아야 한다. 이걸 모르면 커스텀 리졸버가 "마법 같은 특수 기능"으로 보이는데, 실제로는 정반대다.

2-1. 컨트롤러 파라미터는 누가 채우는가

컨트롤러 메서드는 평범한 자바 메서드다. 누군가 인자를 만들어서 넘겨줘야 실행된다.

관찰 이 네 개의 값은 성격이 전부 다르다
@GetMapping("/orders/{id}")
public Order get(@PathVariable Long id,          // URL 경로에서 뽑는다
                 @RequestParam String sort,       // 쿼리 스트링에서 뽑는다
                 @RequestBody OrderFilter filter,  // 본문 JSON을 Jackson으로 역직렬화한다
                 HttpServletRequest request) { ... } // 서블릿 객체를 그대로 넘긴다

스프링은 이 "파라미터 하나를 무엇으로 채울지"를 판단하고 실제로 채우는 일을 HandlerMethodArgumentResolver라는 인터페이스에 위임한다.

정의 — 이름을 뜯으면 그대로다

HandlerMethodArgumentResolver = 컨트롤러 메서드의 파라미터 하나하나를 무엇으로 채울지 결정하고 실제 값을 만들어 내는 부품

핸들러 메서드(handler method)의 인자(argument)를 풀어내는(resolve) 자. 이름이 곧 정의다.

중요한 것은 이것이 우리를 위한 특별 확장 슬롯이 아니라, 스프링 MVC가 이미 자기 기능을 전부 이 인터페이스로 구현하고 있다는 점이다.

매일 쓰는 애너테이션들의 뒤편 — 전부 같은 인터페이스의 구현체다
애너테이션 · 타입담당 구현체하는 일
@PathVariablePathVariableMethodArgumentResolverURL 경로 조각을 꺼내 타입 변환
@RequestParamRequestParamMethodArgumentResolver쿼리 스트링·폼 값을 꺼내 타입 변환
@RequestBodyRequestResponseBodyMethodProcessor본문을 메시지 컨버터로 역직렬화
@ModelAttributeServletModelAttributeMethodProcessor요청 파라미터로 객체를 조립·바인딩
HttpServletRequest 등ServletRequestMethodArgumentResolver서블릿 객체를 그대로 전달
@AuthenticationPrincipal (Security)AuthenticationPrincipalArgumentResolverSecurityContext에서 인증 주체를 꺼냄
@AuthUser (우리가 만들 것)AuthUserArgumentResolver앞단이 실어 둔 사용자 객체를 꺼냄
이 표에서 가져갈 문장 우리는 새로운 메커니즘을 만드는 것이 아니라, 스프링이 이미 쓰고 있는 확장점에 구현체를 하나 더 얹는 것이다. @RequestBody가 동작하는 것과 @AuthUser가 동작하는 것은 완전히 같은 원리다. 이 관점이 서면 "커스텀 리졸버는 무겁고 위험한 기술"이라는 오해가 사라진다.

2-2. 파이프라인에서의 위치 — 인자 바인딩은 컨트롤러 진입 "전"에 끝난다

2-3. 두 메서드는 각각 언제 불리는가 — supportsParameter의 결과는 캐싱된다 시니어 변별

인터페이스에는 메서드가 딱 둘이다.

인터페이스 전부다. 이게 확장점의 총량이다
public interface HandlerMethodArgumentResolver {

    boolean supportsParameter(MethodParameter parameter);          // "이 파라미터를 내가 담당하는가"

    Object resolveArgument(MethodParameter parameter,               // "실제 값을 만들어 내라"
                           ModelAndViewContainer mavContainer,
                           NativeWebRequest webRequest,
                           WebDataBinderFactory binderFactory) throws Exception;
}
supportsParameter
스프링이 등록된 리졸버를 순서대로 돌며 물어보고, true를 답한 첫 번째 리졸버에게 그 파라미터를 맡긴다. 순서가 이르면 이긴다.
resolveArgument
실제 값을 만들어 반환한다. 여기서 반환한 객체가 그대로 컨트롤러 메서드의 인자로 들어간다.

여기서 정확히 알아 둬야 답이 한 칸 올라가는 동작이 하나 있다.

Before 요청 내용에 따라 판정을 바꾸려 한다

// 관리자 요청이 먼저 들어왔다면 이후 모든 요청이
// "관리자용 리졸버" 담당으로 굳어진다.

        && p.getParameterType().equals(LoginUser.class);타입까지

규칙 — 두 메서드의 역할 분담을 한 줄로

supportsParameter는 파라미터의 정적 생김새만 본다  /  요청마다 달라지는 것은 전부 resolveArgument에서

정적 생김새 = 애너테이션 + 타입. 둘 다 검사하는 습관을 들이면, @AuthUser String userId처럼 잘못 선언한 자리를 우리가 담당하지 않겠다고 답해 오류가 명확해진다.

2-4. 등록 위치와 순서 — 앞은 못 뺏고, 뒤는 우리가 먼저 잡는다

    @Override

3. 설계 논점 — 왜 검증을 리졸버에 두면 안 되는가 시니어 변별

리졸버가 사용자 객체를 만들 수 있다면, 굳이 인터셉터를 따로 두지 말고 리졸버 안에서 검증까지 끝내면 되지 않나? 코드가 한 곳으로 모이니 더 단순해 보인다. 이 반문에 정확히 답하는 것이 이 질문의 본체다.

Before 검증까지 리졸버가 한다 — 동작은 한다
public class AuthUserArgumentResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter p) {
        return p.hasParameterAnnotation(AuthUser.class);
    }

    @Override
    public Object resolveArgument(MethodParameter p, ModelAndViewContainer mav,
                                  NativeWebRequest req, WebDataBinderFactory bf) {
        String token = req.getHeader("Authorization");
        LoginUser user = authService.verify(token);   // 검증도 여기서문제의 한 줄
        if (user == null) throw new UnauthorizedException();
        return user;
    }
}

동작은 한다. 그런데 인증이 걸리는 조건이 "그 컨트롤러 메서드에 @AuthUser 파라미터가 있는가"로 바뀌어 버린다. 2-2에서 확인했듯 리졸버는 파라미터를 채우기 위해 호출되는 부품이므로, 채울 파라미터가 없으면 애초에 호출되지 않는다.

결과 같은 컨트롤러 안에서 인증이 걸렸다 안 걸렸다 한다
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    @GetMapping                      // @AuthUser 있음 → 리졸버 호출됨 → 검증됨
    public List<Order> myOrders(@AuthUser LoginUser user) {
        return orderService.findByUser(user);
    }

    @DeleteMapping("/{id}")          // @AuthUser 없음 → 리졸버가 호출조차 안 됨
    public void cancel(@PathVariable Long id) {
        orderService.cancel(id);     // 토큰 없이도 남의 주문이 취소된다무인증 통과
    }
}

여기서 뽑아내야 할 원리 — 이 문장 하나가 답의 척추다

차단은 "모든 요청이 반드시 지나가는 자리"에 있어야 하고,
주입은 "값이 필요한 곳"에 있으면 된다

리졸버는 후자의 자리다. 앞단(필터·인터셉터)은 경로 패턴으로 적용 범위가 정해지므로 컨트롤러 메서드의 시그니처와 무관하게 모든 요청을 통과시킨다. 이 원리는 7절(경로 설정의 방향)과 6절(필터+인터셉터 3단 분리)에서 계속 재사용된다.

그래서 역할은 이렇게 갈린다 — 표의 "이유" 칸이 면접 답변의 실제 문장이다
역할담당이유
토큰 검증 · 차단 (401)인터셉터 preHandle 또는 필터컨트롤러 진입 전에 한 번만, 경로 패턴으로 적용 범위를 제어한다. 메서드 시그니처와 무관하게 걸린다
사용자 객체를 파라미터로 주입HandlerMethodArgumentResolver인터셉터는 컨트롤러 메서드에 값을 직접 넘길 수 없다 — 파라미터 바인딩은 리졸버의 소관이다

3-1. 그래도 어긋났을 때 — 조용한 null 대신 시끄러운 실패

분리를 하고 나면 리졸버는 "사용자 정보가 이미 있다"를 전제로 꺼내기만 하면 된다. 다만 전제가 깨졌을 때의 처리는 남겨 둔다. 앞단 경로 패턴에서 빠진 URL이 있으면 리졸버가 null을 만나는데, 이때 조용히 null을 넘기면 컨트롤러 깊은 곳에서 NullPointerException이 나서 원인 추적이 어렵다.

방어 원인을 "이름으로 말해 주는" 예외로 즉시 실패시킨다
@Override
public Object resolveArgument(MethodParameter p, ModelAndViewContainer mav,
                              NativeWebRequest req, WebDataBinderFactory bf) {
    Object user = req.getAttribute(LOGIN_USER, RequestAttributes.SCOPE_REQUEST);
    if (user == null) {
        // 여기 도달했다는 것은 "인증 앞단을 안 거친 경로에 @AuthUser를 붙였다"는
        // 설정 실수라는 뜻이다. null을 넘겨 컨트롤러에서 NPE가 나게 두는 대신
        // 원인을 이름으로 말해 주는 예외로 즉시 실패시킨다.
        throw new IllegalStateException(
                "인증 앞단을 거치지 않은 요청에 @AuthUser가 사용됐다: " + p.getMethod());
    }
    return user;
}

"실수할 수 없는 구조"의 실제 모습은 두 겹이다

겹 1 — 빠뜨릴 자리를 없앤다
차단을 모든 요청이 지나가는 앞단에 두어, 새 엔드포인트를 추가해도 자동으로 인증이 걸리게 한다.
겹 2 — 그래도 어긋나면 시끄럽게 실패한다
설정이 어긋나면 조용한 NPE가 아니라 원인을 말하는 예외로 즉시 터뜨린다. 실패가 보이게 만드는 것이 목적.

4. 구현 — 네 조각이 전부다

1
마커 애너테이션 — 이 파라미터가 인증 사용자 자리임을 표시한다. RUNTIME 유지가 필수다 — 리플렉션으로 런타임에 읽어야 하기 때문이다. CLASS나 SOURCE로 두면 hasParameterAnnotation이 영영 false다.

@Retention(RetentionPolicy.RUNTIME)이게 빠지면 아무것도 동작하지 않는다

2
인터셉터 — 검증하고, 통과한 요청에 사용자 정보를 실어 둔다. 검증 실패는 여기서 예외로 끝나므로 컨트롤러는 시작조차 되지 않는다.

리졸버 — 실어 둔 것을 꺼내 파라미터로 넘긴다. 검증 로직이 여기 없다는 것이 3절의 결론이 코드에 반영된 모습이다.
public class AuthUserArgumentResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter p) {

        return p.hasParameterAnnotation(AuthUser.class)
            && p.getParameterType().equals(LoginUser.class);
    }

    @Override
    public Object resolveArgument(MethodParameter p, ModelAndViewContainer mav,
                                  NativeWebRequest req, WebDataBinderFactory bf) {
        Object user = req.getAttribute(AuthInterceptor.LOGIN_USER, RequestAttributes.SCOPE_REQUEST);
        if (user == null) {
            throw new IllegalStateException(
                    "인증 앞단을 거치지 않은 요청에 @AuthUser가 사용됐다: " + p.getMethod());
        }
        return user;
    }
}

5. 전달 통로 — request attribute vs ThreadLocal

앞단에서 만든 사용자 정보를 리졸버까지 어떻게 전달하는가. 두 가지 통로가 있고 성질이 정반대다.

request.setAttributeThreadLocal
수명요청 객체와 함께 사라진다 — 뒤처리 불요직접 정리해야 한다
꺼내는 곳리졸버의 NativeWebRequest에서 바로어디서든 static 접근
도달 범위요청 객체를 들고 있는 곳까지같은 스레드라면 서비스 깊은 곳까지
대표 사례4절의 구현스프링 시큐리티의 SecurityContextHolder
권장기본값으로 권장컨트롤러 밖에서도 사용자 정보가 꼭 필요할 때

request attribute를 기본값으로 두는 이유는 "수명 관리가 필요 없다" 하나로 충분하다. 요청이 끝나면 요청 객체가 버려지고 그 안의 attribute도 함께 사라진다. 개발자가 지울 일이 없으니 지우는 것을 잊을 일도 없다.

ThreadLocal은 편의를 주는 대신 정리 책임을 떠넘긴다. 파라미터로 넘기지 않아도 어느 계층에서든 AuthContext.currentUser()로 꺼낼 수 있어서, 서비스 열 겹 아래에서 사용자 정보가 필요할 때 메서드 시그니처를 전부 고치지 않아도 된다. 그런데 여기에 치명적인 함정이 있다.

함정의 뿌리 — 톰캣 스레드는 요청이 끝나도 죽지 않는다 요청이 끝나면 스레드는 풀로 돌아가 재사용된다. ThreadLocal에 담긴 값은 스레드에 붙어 있으므로, 지우지 않으면 다음 요청이 그 값을 그대로 본다.
고침 요청이 어떻게 끝나든 반드시 지운다
public class AuthInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        AuthContext.set(authService.verify(req.getHeader("Authorization")));
        return true;
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        // postHandle이 아니라 afterCompletion인 이유:
        // postHandle은 핸들러에서 예외가 나면 건너뛴다. 그러면 예외가 난 요청의
        // 값이 스레드에 남아 다음 요청으로 새어 나간다.
        // afterCompletion은 예외 발생 시에도, 뷰 렌더링 후에도 반드시 실행된다.
        AuthContext.clear();   // 내부적으로 threadLocal.remove()set(null)이 아니다
    }
}

ThreadLocal 통로를 쓴다면 반드시 붙는 세 문장

① 정리 훅은 afterCompletion
postHandle은 핸들러에서 예외가 나면 건너뛴다. 예외가 난 요청의 값이 그대로 남는다. afterCompletion은 예외에도, 뷰 렌더링 후에도 반드시 실행된다.
② set(null)이 아니라 remove()
set(null)은 스레드의 맵에 "null이라는 값"을 남길 뿐 엔트리 자체는 살아 있다. 스레드 풀이 오래 유지되면 누적돼 메모리 누수가 된다. remove()는 엔트리를 제거한다.
③ @Async에는 전파되지 않는다
비동기 메서드는 별도 스레드 풀에서 돌므로 요청 스레드의 ThreadLocal을 볼 수 없다. 값을 파라미터로 명시 전달하거나 TaskDecorator로 복사해 넘겨야 한다.
한 원리로 묶으면 — "요청 스레드에 묶인 것은 스레드를 벗어나면 사라진다"

트랜잭션과 DB 커넥션도 같은 방식으로 요청 스레드에 묶여 있어서 @Async 경계를 넘으면 함께 사라진다. 특별한 함정이 아니라 하나의 원리라는 점을 말하면 답이 넓어진다.

6. 앞단을 필터로 할까 인터셉터로 할까

"인터셉터 또는 필터"라는 병렬 표현은 "필터 = 시큐리티 전용"이라는 오해를 부르기 쉽다. 순수 서블릿 필터로 JWT를 검증하는 구현은 흔하고 정당하다. 둘 다 가능하고, 실제로 갈리는 지점은 셋뿐이다.

세 축 — 이 표가 "왜 그걸 골랐나요"에 대한 근거의 전부다
필터인터셉터
예외 → 에러 응답@ControllerAdvice가 못 잡는다 (DispatcherServlet 바깥)잡힌다 — 기존 예외 처리 체계 그대로
커버리지정적 리소스·404·다른 서블릿까지 전부 지나간다DispatcherServlet이 핸들러를 찾은 요청만
경로 매칭서블릿 스펙(/api/*, *.json) — 제외라는 개념이 없다addPathPatterns / excludePathPatterns

암기 장치 — 세 축은 "예 · 커 · 경"

예외 처리 일관성  ·  커버리지  ·  경로 매칭

선택 근거 교정: "인터셉터는 스프링 빈을 쓸 수 있어서"는 약한 근거다 — 필터도 빈으로 등록하면 주입받을 수 있다. 진짜 근거는 이 세 축이고, 이 교정을 스스로 말하면 인상이 크게 달라진다.

6-1. 필터 인증의 최대 불편 — 에러 포맷이 깨진다

필터에서 throw new UnauthorizedException()을 해도 @RestControllerAdvice의 핸들러를 타지 않는다. 부트 기본 /error 응답이 나가 버려서 팀이 정한 {"code":"AUTH_001", ...} 포맷을 못 맞춘다. 클라이언트 입장에서는 인증 실패만 응답 모양이 다른 셈이다.

응답을 손으로 조립할 수도 있지만, 더 나은 우회법은 HandlerExceptionResolver를 주입받아 직접 호출하는 것이다. 필터에서 던진 예외를 기존 @ExceptionHandler 체계에 그대로 얹을 수 있다.

우회 필터의 예외를 기존 예외 처리 체계에 태운다
public class JwtAuthFilter extends OncePerRequestFilter {

    private final HandlerExceptionResolver resolver;   // 부트가 등록한 것을 빌려 쓴다

    public JwtAuthFilter(@Qualifier("handlerExceptionResolver") HandlerExceptionResolver resolver) {
        // 이름을 지정해야 정확히 그 빈이 주입된다.
        // HandlerExceptionResolver 타입 빈이 여러 개라 타입만으로는 특정되지 않는다.
        this.resolver = resolver;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        try {
            req.setAttribute(AuthInterceptor.LOGIN_USER,
                    authService.verify(req.getHeader("Authorization")));
            chain.doFilter(req, res);
        } catch (AuthException e) {
            resolver.resolveException(req, res, null, e);   // @ExceptionHandler를 태운다
        }
    }
}

6-2. 반대로 필터가 유리한 지점 — 엔드포인트 존재 노출

인터셉터는 핸들러 매핑이 성공한 요청만 탄다. 존재하지 않는 URL은 preHandle이 불리지 않고 곧장 404가 나간다.

6-3. 인터셉터만 할 수 있는 것 — 핸들러 정보 접근

필터는 URL 문자열밖에 못 본다. 그래서 "이 URL은 ADMIN만" 같은 규칙을 URL → 권한 매핑 테이블로 필터 안에 따로 들고 있어야 한다.

Before 필터 — 정책이 컨트롤러에서 멀리 떨어져 산다
private static final Map<String, String> URL_ROLES = Map.of(

인터셉터 핸들러에서 애너테이션을 직접 읽는다
@Override
public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
    // 정적 리소스 등은 HandlerMethod가 아니다 — 여기서 걸러야 아래에서 캐스팅 오류가 안 난다.
    if (!(handler instanceof HandlerMethod hm)) return true;

    RequiresRole ann = hm.getMethodAnnotation(RequiresRole.class);
    if (ann == null) ann = hm.getBeanType().getAnnotation(RequiresRole.class);  // 클래스 단위도 지원
    if (ann != null && !currentUser(req).hasRole(ann.value())) {
        throw new ForbiddenException();   // @ControllerAdvice가 받아 준다
    }
    return true;
}

6-4. 필터만 할 수 있는 것 — 요청/응답 객체 교체

var wrapped = new ContentCachingRequestWrapper(req);
chain.doFilter(wrapped, res);다음 단계에 넘기는 객체 자체를 바꾼다
log.info("body={}", new String(wrapped.getContentAsByteArray()));

7. 경로 설정의 "방향"이 안전을 결정한다

서블릿 필터의 url-pattern은 세 형태만 지원한다 — 완전 일치(/api/login), 경로 접두(/api/*), 확장자(*.json). 제외(exclude)라는 개념 자체가 없다. 그런데 실무의 인증 설정은 거의 항상 "전부 막고 몇 개만 연다" 모양이다.

registry.addInterceptor(authInterceptor)
        .addPathPatterns("/api/**")                       // 기본은 전부 차단
        .excludePathPatterns(
            "/api/auth/login", "/api/auth/signup",        // 공개 엔드포인트만 예외
            "/api/health", "/api/docs/**")
        .order(1);

필터로 하면 이 화이트리스트를 필터 코드 안에서 AntPathMatcher로 직접 굴려야 한다. 스프링 시큐리티의 permitAll()이 제공하는 게 정확히 이 기능이다. 시큐리티 없이 필터로 인증하겠다면 결국 이 경로 매칭 로직을 손으로 만들게 된다.

그런데 문법보다 중요한 것은 방향이다 같은 인터셉터, 같은 문법으로도 정반대의 안전성이 나온다. 아래 두 방향의 차이는 코드 품질이 아니라 "실패했을 때 무슨 일이 일어나는가"다.

규칙 — 인증 경로 설정의 기본값

전부 막고, 공개할 것만 예외로 판다 (deny by default)

패턴 문법 자체도 인터셉터 쪽이 훨씬 세다 — /api/v1/orders/*(한 세그먼트), /api/**(나머지 전부), /api/{version}/users/**(변수). 단 부트 3부터 PathPatternParser가 기본이라 **는 패턴 맨 끝에만 올 수 있다.

(1) 스프링 시큐리티를 쓰지 않는 경우

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

역할을 어떻게 쪼개나?
검증·차단은 앞단(필터/인터셉터), 주입은 리졸버. 통로는 request attribute가 기본.
왜 리졸버가 검증하면 안 되나?
리졸버는 채울 파라미터가 없으면 호출조차 안 된다. 인증이 "@AuthUser를 적었는가"에 달리게 되고, 안 적은 메서드가 무인증으로 열린다.
한 줄 원리는?
차단은 "모든 요청이 반드시 지나가는 자리"에, 주입은 "값이 필요한 곳"에.
HandlerMethodArgumentResolver

supportsParameter
판정이 캐싱된다(MethodParameter 키). 그래서 정적 생김새(애너테이션+타입)만 봐야 한다. resolveArgument는 매 요청 호출.
등록 순서에서의 위치는?

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

HandlerMethodArgumentResolver가 정확히 뭔가요? 필수힌트: 정의 한 줄 → "특별 슬롯이 아니다"라는 관점 → 파이프라인 위치 순으로 쌓는다

컨트롤러 메서드의 파라미터 하나하나를 무엇으로 채울지 결정하고 실제 값을 만들어 내는 부품이다. 컨트롤러 메서드도 평범한 자바 메서드라 누군가 인자를 만들어 넘겨야 실행되는데, 그 일을 스프링이 이 인터페이스에 위임한다.

여기서 관점 하나를 반드시 얹어야 한다. 이건 우리를 위한 특별 확장 슬롯이 아니라 스프링 MVC가 자기 기능을 구현하는 데 이미 쓰고 있는 인터페이스다. @PathVariable은 PathVariableMethodArgumentResolver, @RequestParam은 RequestParamMethodArgumentResolver, @RequestBody는 RequestResponseBodyMethodProcessor가 담당한다. 즉 우리는 새 메커니즘을 만드는 것이 아니라 이미 돌아가는 확장점에 구현체를 하나 더 얹는 것이다.

파이프라인 위치까지 말하면 완성된다. HandlerAdapter가 핸들러 실행 절차를 총괄하고, 그 안의 인자 바인딩 단계가 리졸버의 자리다. 인자 바인딩은 컨트롤러 진입 전에 끝난다 — 컨트롤러가 시작될 때 파라미터는 이미 완성돼 있다.

supportsParameter와 resolveArgument는 각각 언제 불리나요? 시니어 변별힌트: 역할 설명은 절반이다. 나머지 절반은 "호출 빈도"에 있다

supportsParameter는 "이 파라미터를 내가 담당하는가"를 답하고, 스프링은 등록된 리졸버를 순서대로 물어 true를 답한 첫 번째 리졸버에게 그 파라미터를 맡긴다. resolveArgument는 실제 값을 만들어 반환하고, 그 반환값이 컨트롤러 인자로 들어간다.

정확히 답해야 하는 지점은 호출 빈도다. supportsParameter의 결과는 캐싱된다. 여러 리졸버를 묶는 HandlerMethodArgumentResolverComposite가 MethodParameter를 키로 "이 파라미터는 이 리졸버 담당"을 기억하기 때문에, 같은 (메서드, 인자 번호) 조합에 대해서는 사실상 첫 요청에만 호출된다. resolveArgument는 매 요청 호출된다.

여기서 실무 규칙이 나온다. supportsParameter는 파라미터의 정적 생김새(애너테이션·타입)만 보는 순수 판정이어야 한다. 요청 내용을 보고 판정을 바꾸려 하면 첫 요청의 결과가 굳어져 "가끔만 동작하는" 재현 불가 버그가 된다.

타입까지 함께 검사하라는 것도 덧붙이면 좋다. 애너테이션만 보면 @AuthUser String userId 같은 오용에서 엉뚱한 타입을 넣으려다 런타임에 터진다.

인터셉터 없이 리졸버 혼자 검증까지 다 하면 안 되나요? 시니어 변별힌트: "안 된다"로 시작하고, 이유를 "리졸버는 언제 호출되는가"에서 끌어낸다

안 된다. 그리고 그 이유가 이 질문의 핵심이다.

리졸버는 파라미터를 채우기 위해 호출되는 부품이다. 채울 파라미터가 없으면 애초에 호출되지 않는다. 그래서 검증을 리졸버에 넣으면 인증이 걸리는 조건이 "그 컨트롤러 메서드에 @AuthUser 파라미터가 있는가"로 바뀐다.

@GetMapping    myOrders(@AuthUser LoginUser user)   → 리졸버 호출 → 검증됨   ✓
@DeleteMapping cancel(@PathVariable Long id)        → 리졸버 미호출 → 무검증  ✗

같은 컨트롤러 안에서도 메서드마다 인증이 걸렸다 안 걸렸다 하고, 빠진 쪽은 예외도 경고도 없이 정상 동작한다. 결국 "각 메서드에서 챙기는 구조"를 "각 메서드가 파라미터를 선언했는지에 달린 구조"로 바꾼 것일 뿐, 빠뜨릴 자리를 없애지 못했다.

원리로 정리하면 이렇다. 차단은 "모든 요청이 반드시 지나가는 자리"에 있어야 하고, 주입은 "값이 필요한 곳"에 있으면 된다. 앞단(필터·인터셉터)은 경로 패턴으로 범위가 정해지므로 컨트롤러 시그니처와 무관하게 모든 요청을 통과시킨다.

여기에 "그럼에도 리졸버가 null을 만나면 예외로 즉시 실패시킨다"는 두 번째 겹까지 말하면 완성된다 — 앞단 경로 패턴에서 빠진 URL이 있을 때 조용한 NPE 대신 원인을 이름으로 말하는 예외가 나야 한다.

@RequestAttribute로 충분하지 않나요? 커스텀 리졸버까지 만들 필요가 있나요?힌트: "된다"를 인정하고 시작한다. 이득 셋을 대고, 마지막에 결정타 하나를 남긴다

@RequestAttribute("loginUser") LoginUser user로도 꺼낼 수는 있다. 스프링이 기본 제공하는 리졸버로 처리되므로 커스텀 리졸버 없이 동작한다.

커스텀 리졸버의 이득은 셋이다. ① 문자열 키 은닉 — "loginUser"라는 문자열이 컨트롤러 수십 곳에 흩어지지 않는다. 오타가 나도 컴파일 에러가 없는 문자열을 노출하지 않는 것 자체가 값이다. ② 타입 검사 — supportsParameter에서 타입을 함께 확인하므로 잘못된 타입 선언이 걸러진다. ③ 미인증·null 처리 정책의 한 곳 집중 — "없으면 예외인가, Optional인가, 익명 사용자 객체인가"를 리졸버 한 곳에서 결정한다.

그리고 통로를 바꿀 수 있다는 점이 결정적이다. @RequestAttribute는 "request attribute에서 꺼낸다"는 구현을 컨트롤러 시그니처에 박아 넣는다. 나중에 ThreadLocal이나 SecurityContextHolder로 통로를 바꾸면 컨트롤러를 전부 고쳐야 한다. 커스텀 리졸버는 그 지식을 리졸버 하나에 가둬 둔다.

ThreadLocal 정리를 왜 afterCompletion에서 하나요? 함정힌트: postHandle이 언제 건너뛰는지, 그리고 "왜 반드시 지워야 하는지"를 함께

요청이 어떻게 끝나든 반드시 실행되는 훅이기 때문이다. afterCompletion은 핸들러에서 예외가 났을 때도, 뷰 렌더링이 끝난 뒤에도 호출된다. 반면 postHandle은 핸들러에서 예외가 나면 건너뛴다 — 그러면 예외가 난 요청의 값이 스레드에 그대로 남는다.

왜 반드시 지워야 하는지를 함께 말해야 한다. 톰캣 스레드는 요청이 끝나도 죽지 않고 풀로 돌아가 재사용된다. ThreadLocal 값은 스레드에 붙어 있으므로, 안 지우면 다음 요청 — 다른 사용자 — 이 이전 사용자 정보를 본다. 앞단이 값을 덮어쓰기 전에 누군가 읽으면 그대로 유출이다. 개발 환경에서는 스레드 재사용이 드물어 재현되지 않고 트래픽이 있는 운영에서만 터진다는 점도 악질이다.

set(null)이 아니라 remove()를 부르는 이유까지 말하면 정확한 답이 된다. set(null)은 "null이라는 값"을 남길 뿐 엔트리 자체는 스레드의 맵에 남아 있어, 스레드 풀이 오래 유지되는 환경에서 누적되면 메모리 누수가 된다.

@Async 서비스에서 그 사용자 정보가 필요하면요? 가산점힌트: 대응 두 가지를 대고, 마지막에 "특별한 함정이 아니라 하나의 원리"로 넓힌다

ThreadLocal은 새 스레드에 전파되지 않는다. @Async 메서드는 별도 스레드 풀에서 실행되므로 요청 스레드의 ThreadLocal을 볼 수 없다.

대응은 둘이다. 값을 파라미터로 명시 전달하거나, TaskDecorator로 요청 스레드의 컨텍스트를 복사해 비동기 스레드에 넘긴다. 후자를 쓸 때는 읽기용 컨텍스트만 복사하고, 비동기 작업이 끝날 때 그쪽에서도 정리해야 한다는 조건이 붙는다.

이게 특별한 함정이 아니라 하나의 원리라는 점을 말하면 좋다 — "요청 스레드에 묶인 것은 스레드를 벗어나면 사라진다." 트랜잭션과 DB 커넥션도 같은 방식으로 요청 스레드에 묶여 있어서 @Async 경계를 넘으면 함께 사라진다.

인증을 필터에서 하면 안 되나요? 시큐리티가 없어도? 필수힌트: "된다"로 시작한다. "필터 = 시큐리티 전용"이라는 오해를 먼저 깬 뒤 세 축을 댄다

된다. 순수 서블릿 필터로 JWT를 검증하는 것은 흔한 구현이고 "필터 = 시큐리티 전용"이 아니다. 갈리는 축은 셋이다 — 예·커·경.

① 예외 처리 일관성. 필터에서 던진 예외는 @ControllerAdvice가 못 잡아 부트 기본 /error 응답이 나가고 팀의 에러 포맷이 깨진다. @Qualifier("handlerExceptionResolver")로 HandlerExceptionResolver를 주입받아 직접 호출하면 우회할 수 있다.

② 커버리지. 인터셉터는 핸들러 매핑이 성공한 요청만 타므로, 없는 URL은 401이 아니라 404가 나간다 — 토큰 없이도 경로 존재 여부를 알아낼 수 있다(엔드포인트 열거). 필터로 막으면 존재 여부와 무관하게 401이다.

③ 경로 매칭. 서블릿 필터에는 excludePathPatterns가 없어 공개 엔드포인트 화이트리스트를 AntPathMatcher로 직접 구현해야 한다. 시큐리티의 permitAll()이 제공하는 게 정확히 그 기능이다.

실무에서는 인증은 필터, 애너테이션 기반 인가는 인터셉터로 나누는 조합도 흔하다는 것까지 붙이면 좋다.

인터셉터로는 못 하고 필터로만 되는 게 있나요? 가산점힌트: 한 가지로 좁힌다 — "무엇을 다음 단계에 넘길 수 있는가"

요청/응답 객체 자체의 교체다. 필터는 chain.doFilter(감싼요청, 감싼응답)으로 래퍼를 다음 단계에 넘길 수 있고, 인터셉터는 이미 만들어진 요청을 받아 boolean만 반환하므로 구조적으로 불가능하다.

대표적인 것이 요청 본문 로깅이다. InputStream은 한 번만 읽히므로 ContentCachingRequestWrapper로 감싸서 교체하지 않으면, 로깅한 순간 컨트롤러의 @RequestBody가 빈 본문을 받는다. XSS 파라미터 치환, 응답 압축도 전부 이 범주다.

스프링 시큐리티를 쓰는데도 커스텀 리졸버를 만들 이유가 있나요? 시니어 변별힌트: 먼저 "이미 있다"를 인정한다. 그 다음 예외 두 가지, 마지막에 비용까지

먼저 @AuthenticationPrincipal이 이미 같은 일을 한다는 것을 인정하는 것이 정직한 시작이다. 시큐리티는 인증 필터 체인(검증·차단), SecurityContextHolder(전달 통로), AuthenticationPrincipalArgumentResolver(주입)로 이 문서의 구조를 그대로 갖고 있다. 시큐리티를 쓰면서 같은 것을 다시 만드는 것은 중복이다.

그럼에도 만드는 경우는 둘이다. (1) 시큐리티를 안 쓰는 경우 — 사내 게이트웨이가 인증을 끝내고 헤더로 사용자 ID만 넘겨주는 구조나 자체 토큰 체계라면 시큐리티 전체를 들이는 것이 과할 수 있다. (2) 도메인 사용자 객체로 변환이 필요한 경우 — SecurityContextHolder에 있는 것은 UserDetails나 JWT 클레임이지 우리 도메인의 Member 엔티티가 아니다. 컨트롤러가 도메인 객체를 받게 하려면 변환 지점이 필요하고, 그 자리가 리졸버다. 이때도 검증은 시큐리티가 하고 리졸버는 변환만 한다 — 3절의 원칙은 그대로다.

커스텀 조합을 고를 때의 비용까지 말하면 시니어다운 답이 된다 — 경로 화이트리스트, CSRF, 세션 고정 공격 방어, @PreAuthorize 같은 인가 애너테이션, 익명 사용자 처리를 전부 직접 만들게 된다는 것이다.

인터셉터 안에서 주입받은 서비스가 null입니다. 왜죠? 함정힌트: new로 만든 객체는 무엇이 아닌가

WebConfig에서 new AuthInterceptor()로 만들었기 때문이다. 그렇게 만든 인스턴스는 스프링 빈이 아니므로 의존성 주입 대상이 아니다. 필드 주입을 걸어 뒀다면 그 필드는 영영 null이고, 첫 요청에서 NullPointerException이 난다. 애너테이션은 표식일 뿐, 그것을 읽고 값을 넣어 주는 주체는 컨테이너이기 때문이다.

해결은 인터셉터를 빈으로 만들고 그 빈을 등록에 넘기는 것이다 — 인터셉터에 @Component를 붙이거나 @Bean으로 등록한 뒤, WebConfig가 생성자 주입으로 받아 registry.addInterceptor(authInterceptor)에 넘긴다. 리졸버도 정확히 같다 — 사용자 조회 리포지토리를 쓰는 리졸버라면 반드시 빈으로 만들어야 한다.

공개 엔드포인트에서도 "로그인했으면 사용자, 아니면 익명"으로 받고 싶다면요? 가산점힌트: 두 층 모두 손봐야 한다 — 앞단의 통과 정책과 리졸버의 null 정책

"선택적 인증(optional authentication)" 구간이라 부르는 요구다. 비로그인도 볼 수 있지만 로그인했으면 개인화해서 보여주는 상품 목록 같은 화면이 전형이다. 두 층을 함께 손봐야 한다.

① 앞단 — 이 경로들은 "토큰이 있으면 파싱해서 실어 두고, 없으면 그냥 통과"하는 정책이 필요하다. 기존의 강제 인증 인터셉터에서 excludePathPatterns로 빼내고, 선택적 인증 전용 인터셉터를 그 경로에만 따로 건다. 토큰이 있는데 유효하지 않은 경우는 통과가 아니라 401로 막는 편이 안전하다 — "깨진 토큰이 조용히 무시되는" 상태를 만들지 않기 위해서다.

② 리졸버 — null일 때의 정책을 여기 한 곳에서 정한다. supportsParameter가 타입까지 검사하고 있으므로, 예컨대 Optional<LoginUser>나 별도의 @AuthUser(required = false) 속성을 지원하도록 판정 조건을 넓히고, resolveArgument에서 비어 있음 / 익명 사용자 객체 / 예외 중 무엇을 돌려줄지 결정한다. 여기가 커스텀 리졸버의 이득 ③(미인증 처리 정책의 한 곳 집중)이 실제로 값을 하는 지점이다.

이 구조를 테스트로는 어떻게 지키나요? 시니어 변별힌트: 부품 테스트와 "구조가 유지되는지" 테스트는 다른 이야기다

층을 나눠 말하면 정리가 된다.

① 리졸버 단위 테스트. supportsParameter는 테스트용 메서드의 MethodParameter를 만들어 true/false를 검증한다 — @AuthUser가 없을 때, 타입이 다를 때(@AuthUser String) false가 나오는지가 핵심 케이스다. resolveArgument는 가짜 요청에 attribute를 심어 두고 그 객체가 그대로 반환되는지, 없을 때 예외가 나는지를 본다.

② 슬라이스 테스트. MockMvc의 standalone 설정에 커스텀 리졸버와 인터셉터를 직접 등록하면, 컨트롤러 한 개만 띄운 채 "토큰 없으면 401, 있으면 200 + 사용자 주입"을 확인할 수 있다.

③ 그리고 진짜 중요한 것 — "구조가 유지되는지"의 회귀 테스트. 1절의 문제는 새 엔드포인트에서 인증이 빠지는 것이었다. 이것을 사람이 지키는 대신 테스트로 지킬 수 있다 — 애플리케이션에 등록된 핸들러 매핑을 전부 열거해, 공개 화이트리스트에 없는 경로에 토큰 없이 요청했을 때 401이 나오는지를 도는 테스트를 하나 둔다. 새 API를 추가하면서 설정을 어긋나게 하면 배포 전에 빨간불이 켜진다. "빠뜨릴 자리를 없애고, 그래도 어긋나면 시끄럽게 실패시킨다"는 이 문서의 원칙을 CI 층위까지 밀어 올린 형태다.

preHandle에서 false를 반환하는 것과 예외를 던지는 것 중 무엇이 낫나요?힌트: 둘 다 요청을 멈춘다. 차이는 "그 다음에 누가 응답을 만드는가"에 있다

둘 다 이후 단계를 실행하지 않는다는 점은 같다. 차이는 응답을 누가 만드느냐다.

false 반환은 "여기서 끝났다"는 신호일 뿐이라 응답 본문과 상태 코드를 내가 직접 써야 한다. 그러면 에러 바디를 인터셉터 안에서 손으로 조립하게 되고, @RestControllerAdvice가 만드는 팀 표준 에러 포맷과 어긋날 위험이 생긴다. 리다이렉트처럼 정말 응답을 직접 제어해야 하는 경우에 어울린다.

예외를 던지는 쪽은 인터셉터가 DispatcherServlet 안쪽에 있다는 이점을 그대로 쓴다 — UnauthorizedException을 던지면 기존 @ExceptionHandler 체계가 받아 다른 모든 에러와 같은 포맷의 401을 만들어 준다. 인증 실패만 응답 모양이 다른 사태를 막을 수 있으므로, REST API의 인증 인터셉터에서는 예외 쪽이 기본값이다. 이게 6절 "예외 처리 일관성" 축이 인터셉터의 이득이 되는 이유이기도 하다.

한 줄 요약
반복되는 인증 코드는 "검증·차단은 모든 요청이 반드시 지나가는 앞단(필터 또는 인터셉터), 주입은 커스텀 HandlerMethodArgumentResolver"로 역할을 나눠 제거하는데 — 이 분리가 필수인 이유는 검증까지 리졸버에 넣으면 @AuthUser 파라미터가 없는 메서드는 리졸버가 호출조차 되지 않아 인증이 통째로 빠지고 그 구멍이 정상처럼 보이기 때문이고, 리졸버는 @RequestBody·@PathVariable도 쓰고 있는 기존 확장점이라 우리는 구현체를 하나 얹을 뿐이며(supportsParameter의 판정은 캐싱되므로 정적 생김새만 봐야 한다), 앞단을 필터로 할지 인터셉터로 할지는 예외 처리 일관성·커버리지·경로 매칭 세 축으로 갈리고, ThreadLocal을 통로로 쓴다면 톰캣 스레드 재사용 때문에 afterCompletion에서 반드시 remove()해야 하며, 스프링 시큐리티를 쓰고 있다면 @AuthenticationPrincipal이 이미 같은 구조를 제공하므로 커스텀은 시큐리티 미도입이거나 도메인 객체 변환이 필요할 때의 선택지다.
