RestTemplate vs WebClient vs RestClient
"최신이니까 WebClient"가 왜 틀린 판단인가

면접 질문: "RestTemplate, WebClient, RestClient의 차이와 선택 기준은?"

핵심 관전 포인트 — 세 클라이언트의 스펙 차이는 표 한 장이면 끝나고, 질문의 본체는 선택 기준이다. HTTP 클라이언트는 "최신순"이 아니라 "우리 앱이 서 있는 스레드 모델과 맞는가"로 고른다. 톰캣 MVC 앱에서 WebClient를 .block()으로 쓰면 요청 스레드는 여전히 묶여 있고 리액터 스레드만 하나 더 늘어나므로, 논블로킹의 이점은 0인 채로 의존성과 디버깅 난도만 떠안는다. 그래서 평범한 MVC 신규 개발이면 RestClient가 기본값이고, WebClient는 .block() 없이 끝까지 논블로킹으로 흘려보낼 수 있을 때만 정당하며, 잘 돌고 있는 RestTemplate 코드는 굳이 갈아엎지 않는다 — RestTemplate은 deprecated가 아니라 유지보수 모드다. 그리고 무엇을 고르든 연결 타임아웃·읽기 타임아웃·커넥션 풀 상한을 명시하지 않으면 외부 API의 지연 하나가 톰캣 스레드풀 고갈로 번져 남의 장애가 내 장애가 된다 — 이 지점이 출제 의도의 본체다.
  • 1
    스펙은 한 줄씩 — RestTemplate은 스프링 3.0의 동기 클라이언트로 지금은 유지보수 모드(deprecated 아님), WebClient는 스프링 5.0의 논블로킹·리액티브 클라이언트로 Mono/Flux를 반환, RestClient는 스프링 6.1·부트 3.2에 들어온 "WebClient의 fluent API + 동기 실행 모델"로 RestTemplate의 실질적 후계자다.
  • 2
    선택은 실행 모델 정합성으로 한다 — WebFlux 스택이면 WebClient, 톰캣 MVC 신규 코드면 RestClient, 이미 잘 도는 RestTemplate은 손댈 일이 생겼을 때 함께 이전. MVC에서 WebClient + .block()은 최악의 조합이다 — 톰캣 200스레드 × 응답 200ms면 어느 쪽이든 상한은 똑같이 1,000 rps인데, 리액터 의존성과 스택트레이스 오염만 추가로 낸다.
  • 3
    무엇을 고르든 진짜 답은 타임아웃과 풀이다 — 연결·읽기·풀 대기 세 타임아웃과 커넥션 풀 상한을 명시하지 않으면, 외부 API가 5초로 느려질 때 리틀의 법칙대로 200건/초 × 5초 = 1,000개의 스레드가 필요해져 1초 만에 톰캣 스레드가 전부 묶인다. 값은 "외부가 보통 얼마나 걸리나"가 아니라 "우리가 몇 개의 스레드를 내줄 수 있나"에서 역산한다.

0. 질문 + 출제 의도

질문: "RestTemplate, WebClient, RestClient의 차이와 선택 기준은?"

출제 의도: 단순 API 선택 같지만 실제로는 타임아웃·커넥션풀 설정이 어디 있는지 아는가의 질문이다. 외부 호출 클라이언트의 기본 설정을 방치한 채 운영에 가는 것이 연쇄 장애의 고전적 시작점이다.

이 페이지가 겨냥하는 약점 세 가지 ① 스펙 나열로 끝내는 것 → 2절의 표는 30초에 끝내고, 4·5절에서 "우리 앱의 스레드 모델과 맞는가"라는 단 하나의 선택축을 스레드 타임라인으로 못 박는다.
② "RestTemplate은 deprecated"라는 잘못된 전제 → 3절에서 deprecated와 유지보수 모드를 4개 축으로 분리한다. 이 전제가 틀리면 그 위의 마이그레이션 결정이 통째로 틀린다.
③ "타임아웃 5초 걸었습니다"에서 멈추는 것 → 6절에서 타임아웃이 세 종류라는 것을, 7절에서 값을 자원 예산에서 역산하는 법을 숫자로 보여준다.
한 문장 비유 — 식당 종업원, 그리고 세 개의 시계 종업원(스레드): 블로킹은 주문을 넣고 주방 앞에 서서 기다리는 것, 논블로킹은 주문만 넣고 홀로 돌아가 다른 테이블을 받다가 벨이 울리면 가지러 가는 것이다. 종업원 수가 같아도 후자가 훨씬 많은 테이블을 본다.  /  세 개의 시계(6절): 가게 문이 안 열린다(연결 타임아웃) · 주문은 받았는데 음식이 안 나온다(읽기 타임아웃) · 빈 테이블이 없어 밖에서 기다린다(풀 대기 타임아웃) — 셋은 전혀 다른 사건이고, 마지막 하나만 상대가 아니라 우리 문제다.

1. 전제 지식 — "블로킹"과 "논블로킹"은 스레드가 묶여 있는가의 차이다

비교표에 들어가기 전에 표에서 쓸 두 단어를 먼저 정의하고 간다. 이 두 단어를 정의 없이 표에 던지면 표를 읽어도 아무것도 못 고른다.

블로킹(blocking)

요청을 보낸 스레드가 응답이 올 때까지 그 자리에 멈춰 서 있는 것. 스레드는 CPU를 쓰지 않고 잠들어 있지만, 다른 요청을 처리하러 갈 수 없다. 즉 기다리는 동안에도 스레드 한 개를 계속 점유한다.

논블로킹(non-blocking)

요청만 던져놓고 스레드는 곧바로 다른 일을 하러 가는 것. 응답이 도착하면 OS가 알려주고 그때 아무 스레드나 하나가 이어서 처리한다. 대기 시간이 스레드를 잡아먹지 않으므로 스레드 몇 개로 수천 개의 동시 대기를 감당한다.

이 문서에서 다루는 범위 서버 쪽 스레딩 모델 자체(톰캣 vs 네티, WebFlux가 왜 적은 스레드로 버티는가)의 본론은 27-webflux-vs-mvc-threading-model.md에 있다. 여기서는 클라이언트를 고르는 데 필요한 만큼만 다룬다.

②의 Mono는 "미래에 값이 하나 올 것"이라는 계획서일 뿐이고, 누군가 구독(subscribe)해야 그때 실제로 실행된다. MVC 컨트롤러에서 당장 Member 객체가 필요하면 .block()으로 기다리는 수밖에 없다 — 함정의 시작이다(4절).

②와 ③을 나란히 놓고 보면 RestClient의 정체가 드러난다. WebClient의 좋은 API 디자인만 가져오고, 실행 모델은 MVC에 맞는 동기·블로킹으로 되돌린 것이다. "RestTemplate은 낡았는데 WebClient는 우리 스택에 안 맞는다"는 오랜 어정쩡함을 해소하려고 스프링 팀이 만든 물건이다.

3. 사실 확인 — RestTemplate은 deprecated가 아니다

이 질문에서 가장 자주 나오는 오답이 "RestTemplate은 deprecated라서 못 쓴다"다. 정확한 사실은 이렇다. RestTemplate은 스프링 5.0부터 유지보수 모드(maintenance mode)다. 유지보수 모드는 "버그와 보안 취약점은 계속 고치지만 새 기능은 넣지 않는다"는 뜻이다. @Deprecated 애너테이션은 붙어 있지 않고, 컴파일 경고도 나지 않으며, 제거 일정도 공지된 바 없다.

두 상태를 구분해 두면 뒷 판단이 달라진다 — 특히 마지막 줄

틀린 전제 위에 세워진 결정은 통째로 틀린다

"deprecated니까 지금 다 갈아엎어야 한다"는 전제 자체가 틀렸고, 그 잘못된 전제 위에서 내려진 결정이 바로 다음 절에서 볼 "톰캣 MVC 앱에 WebClient를 넣고 .block()으로 쓰는" 최악의 조합이다. 사실관계를 바로잡는 것이 답의 절반이다.

4. 최악의 조합 — MVC 앱에서 .block()을 부르면 스레드에 무슨 일이 생기는가

한동안 "RestTemplate은 유지보수 모드니까 WebClient로 가야 한다"는 말이 퍼졌고, 실제로 톰캣 기반 MVC 앱에 WebClient를 넣고 .block()으로 쓰는 코드가 대량으로 생산됐다.

문제 톰캣 MVC 앱에서 흔히 보이는 코드
Member member = webClient.get()
        .uri("/members/{id}", id)
        .retrieve()
        .bodyToMono(Member.class)
        .block();여기서 톰캣 요청 스레드가 멈춰 선다

"논블로킹 클라이언트를 썼으니 조금이라도 낫지 않나"라고 생각하기 쉬운데, 스레드 단위로 그려 보면 정확히 반대다.

논블로킹의 이점은 "대기가 스레드를 점유하지 않는 것"인데, .block()은 그 대기를 다시 스레드 점유로 되돌린다

그러니 이점이 줄어드는 게 아니라 정확히 0이 된다. 이점이 0이면 손해가 없는 게 아니라, 지불한 비용만큼 순손실이다.

4-2. 그런데 비용은 전부 그대로 청구된다

1
의존성이 늘어난다. spring-boot-starter-webflux를 통해 reactor-core, reactor-netty가 들어온다. 클래스패스에 리액티브 스택이 얹히면서 자동 설정 판단이 바뀌기도 한다 — 부트는 클래스패스에 WebFlux만 있고 spring-webmvc가 없으면 아예 리액티브 웹 애플리케이션으로 기동한다.
2
스택트레이스가 리액터 프레임으로 덮인다. 실무에서 가장 뼈아픈 비용이다. 리액티브 코드에서는 콜백이 실행되는 스레드가 호출한 스레드와 달라 자바가 원래의 호출 경로를 스택에 남겨주지 못한다. Hooks.onOperatorDebug()나 reactor-tools의 ReactorDebugAgent 같은 별도 장치를 켜야 겨우 조립 지점을 복원할 수 있다.
3
새로운 장애 유형이 생긴다. .block()을 리액터의 논블로킹 스레드(reactor-http-nio-*) 위에서 호출하면 IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-3가 터진다. 이벤트 루프 스레드가 멈추면 그 스레드가 담당하던 수백 개의 다른 커넥션까지 함께 멈추기 때문에 리액터가 아예 막아 둔 것이다. MVC 코드에서만 쓰다가 나중에 필터·핸들러 일부를 리액티브로 옮기는 순간 이 예외를 만난다.

정리 — 판단 기준은 도구의 최신 여부가 아니다

HTTP 클라이언트의 실행 모델은 앱이 서 있는 스레드 모델과 맞아야 한다

5. 판단 순서도 — 이 질문의 본체

말로 늘어놓으면 헷갈리니 순서대로 물어 내려가면 된다. 위에서부터 하나씩 답하면 끝난다.

①이 결정적인 이유
WebFlux 스택에서는 요청 처리 자체가 이벤트 루프 위에서 돈다. 그 위에서 블로킹 클라이언트를 부르면 4-2의 (3)과 같은 사고가 난다. 이때만큼은 선택지가 하나뿐이다.
②에서 RestClient가 기본값인 이유
실행 모델이 앱과 일치하고(동기), API는 WebClient와 같은 모던 fluent 스타일이며, 새 코드이므로 마이그레이션 비용이 아예 없다.
③에서 "그대로 둔다"가 답인 이유
잘 돌아가는 코드를 트렌드 때문에 바꾸는 것 자체가 리스크다. 회귀 테스트 비용과 장애 확률을 지불하고 얻는 것이 "최신 API"뿐이라면 남는 장사가 아니다.

5-1. 그래도 MVC에서 WebClient가 정당화되는 경우

"MVC면 무조건 RestClient"로 외우면 반대편 함정에 빠진다. 정당성은 도구가 아니라 사용 패턴에서 나오고, 기준은 하나다.

기준은 단 하나 — .block()으로 값을 즉시 뽑아내지 않는 사용인가
SSE · 스트리밍 응답
응답이 끝나기 전에 도착한 조각부터 처리해야 하므로, "다 받아서 객체 하나로 반환"하는 동기 클라이언트로는 자연스럽게 다룰 수 없다.
스레드를 반납하는 비동기 조합
여러 외부 API를 동시 호출해 조합하되 결과를 DeferredResult·CompletableFuture로 반환해 톰캣 스레드를 반납하는 경우. 이때는 4절의 도식이 성립하지 않는다.
WebFlux 이전 과도기
조직이 WebFlux로 이전하는 중이라 클라이언트를 먼저 통일하는 전략. 목적이 "지금의 성능"이 아니라 "이전 비용의 분할 납부"라면 합리적일 수 있다.
반대로 이것은 어떤 근거로도 정당화되지 않는다 "단건 호출하고 바로 .block()"이 코드의 전부인 경우.

5-2. 선택을 한 지점에 가두기 — HTTP Interface (@HttpExchange)

스프링 6부터는 세 클라이언트 위에 얹는 선언적 추상화가 하나 더 있다. 인터페이스에 애너테이션만 달면 스프링이 구현체를 만들어 준다. OpenFeign과 같은 발상의 스프링 내장판이다.

선언 인터페이스 + 애너테이션만
public interface MemberApi {

    @GetExchange("/members/{id}")
    Member getMember(@PathVariable Long id);
}
조립 어댑터만 갈아끼우면 하부 클라이언트가 바뀐다 — 호출부는 그대로다

AI 시대 관점 — 스펙 나열은 AI의 몫, 스택 판단은 리뷰어의 몫 세 클라이언트의 스펙 비교표는 AI에게 물으면 몇 초 만에 나온다. 그러나 AI는 우리 앱이 톰캣 위 MVC인지 WebFlux인지, 스레드풀 사정이 어떤지라는 문맥을 모른 채 제안한다. 실제로 AI가 생성한 코드에는 "비동기 처리가 필요해 보여서" WebClient + .block() 조합이 자주 들어 있다 — 4절에서 본 최악의 조합이다. 리뷰어가 할 일은 스펙 지식이 아니라 판단이다. "이 코드베이스는 톰캣 MVC다. .block()으로 쓸 거면 WebClient를 들일 이유가 없다. RestClient로 바꾸고 읽기 타임아웃을 명시하라." — 실행 모델이라는 근거로 AI의 제안을 걸러내는 것이 사람이 유지해야 할 역량이고, 이 질문이 여전히 면접에 나오는 이유다.

6. 어느 클라이언트를 고르든 반드시 챙기는 것 — 타임아웃은 세 종류다

면접에서 "선택"만 답하고 끝내면 반쪽이다. 출제 의도가 지목한 곳은 여기다. 무엇을 고르든 타임아웃과 커넥션 풀을 명시하지 않으면 사고가 난다.

그리고 "타임아웃 5초 걸었습니다"라고만 답하면 반은 틀린 답이다. HTTP 호출 한 번에는 성격이 다른 시계가 최소 둘, 커넥션 풀을 쓰면 셋 붙는다. 각각 어느 구간을 재는지를 요청의 생애 위에 그려 보자.

암기 장치 — 타임아웃 3종은 "연 · 읽 · 풀", 진단 문장도 셋

연결(상대가 안 받는다) · 읽기(상대가 받고 안 준다) · 풀 대기(우리 풀이 말랐다)

면접에서 "타임아웃 걸었습니다"로 끝내지 말고 이 세 글자를 나열하고 각각 무엇을 재는지 한 줄씩 붙이면, 그 자체가 "설정 화면을 실제로 열어 본 사람"이라는 신호가 된다.

7-1. 리틀의 법칙 — 동시에 몇 개의 스레드가 묶이는지 세는 도구

리틀의 법칙 (Little's Law)

L (시스템 안에 머무는 개수) = λ (도착률) × W (머무는 시간)

큐 이론의 결과지만 직관적으로도 맞는 관계다 — 계산대에 1분에 10명이 오고 한 명당 2분이 걸리면 매장 안에는 평균 20명이 있다. 외부 호출에 대입하면 L = 동시에 묶여 있는 스레드 수가 된다.

전제 — 톰캣 최대 스레드 200개(부트 기본값) · 해당 엔드포인트 유입 초당 200건 · 평소 외부 API 응답 100ms
상황필요한 스레드 L = λ × W결과
평상시 (100ms)200건/초 × 0.1초 = 20개200개 중 20개만 쓴다 — 여유 있다
외부 API가 5초로 느려짐
죽은 게 아니라 느려진 것 — 더 위험하다		200건/초 × 5초 = 1,000개가진 것은 200개 — 800개 부족
스레드가 전부 묶이기까지 200 ÷ 200 = 1초

7-2. 타임아웃을 걸었다고 자동으로 살아남는 것이 아니다

같은 조건(톰캣 200, 유입 초당 200건)에서 타임아웃 값만 바꿔 보자.

읽기 타임아웃필요한 스레드 L = 200 × W보유 200개와 비교
3초200 × 3 = 600개✗ 여전히 고갈된다
1초200 × 1 = 200개✗ 아슬아슬하다 (여유 0)
0.5초200 × 0.5 = 100개✓ 버틴다

규칙 — 타임아웃 값은 우리 쪽 자원 예산에서 역산한다 시니어 변별

W (읽기 타임아웃 상한) = Lbudget (내줄 수 있는 스레드) ÷ λ (유입)

"외부 API가 보통 얼마나 걸리나"가 아니라 "최악일 때 우리가 몇 개의 스레드를 내줄 수 있나"가 출발점이다. 톰캣 200개 중 절반인 100개만 이 API에 내주기로 하고 유입이 초당 200건이면 100 ÷ 200 = 0.5초가 상한이다.

외부 API의 p99가 800ms라서 1초를 잡고 싶어도, 우리 예산이 0.5초라면 1초는 못 준다. 그 경우 답은 타임아웃을 늘리는 게 아니라 스레드 예산을 늘리거나(스레드풀 확대) 호출 자체를 줄이는 것(캐싱, 비동기화)이다.

8. 재시도는 점유 시간을 곱한다 — 그리고 멱등성과 짝이다

타임아웃을 걸고 나면 자연스럽게 "그럼 실패했을 때 재시도하면 되겠네"로 넘어가는데, 여기에 두 개의 함정이 있다.

8-1. 첫 번째 함정 — 재시도는 자원 예산을 곱셈으로 갉아먹는다

7절에서 어렵게 0.5초로 맞춘 예산이 재시도 3회를 붙이는 순간 이렇게 된다.

재시도 설정실제 점유 시간필요한 스레드 L = 200 × W결과
1회 시도 (재시도 없음)0.5초200 × 0.5 = 100개✓ 예산 안
3회까지 시도0.5 × 3 = 1.5초200 × 1.5 = 300개✗ 고갈 (보유 200개)

게다가 외부가 느려진 상황이란 곧 모든 요청이 재시도를 하는 상황이므로, 상대에게 가는 부하도 3배가 된다. 이미 힘들어하는 시스템에 재시도 폭풍을 얹어 회복을 방해하는 것이다.

지수 백오프 (exponential backoff)
재시도 간격을 1초 → 2초 → 4초처럼 늘려 가는 방식. 상대에게 회복할 틈을 준다.
지터 (jitter)
간격에 무작위 오차를 섞어 모두가 동시에 재시도하지 않게 하는 장치. 없으면 재시도가 박자를 맞춰 몰려간다.
자원 계산은 재시도 횟수를 곱한 총 점유 시간으로 한다 — W총 = 타임아웃 × 시도 횟수

8-2. 두 번째 함정이 더 위험하다 — 타임아웃 ≠ 미처리

읽기 타임아웃이 터졌다는 것은 "응답을 못 받았다"이지 "처리가 안 됐다"가 아니다. 이 한 줄을 놓치면 이중 결제가 난다.

9. 커넥션 풀 — 왜 필요하고, 왜 상한이 필요한가

9-1. 오해 먼저 — 연결과 요청은 1:1이 아니다

"요청할 때마다 TCP 핸드셰이크를 하는 것 아닌가?"는 흔한 오해다. 연결은 관(pipe)이고 요청은 그 관으로 흘리는 물이다. 관을 뚫는 데만 비용이 들고, 이미 뚫린 관에는 그냥 흘려보내면 된다.

TCP 3-way 핸드셰이크
1 RTT
TLS 핸드셰이크
+ 2 RTT (TLS 1.3이면 + 1 RTT)
합계
2~3 RTT — 요청 첫 바이트를 보내기도 전에 든 비용
숫자로 RTT가 30ms인 외부 API라면 호출마다 60~90ms를 그냥 버린다. 여기에 TLS 키 교환의 비대칭 암호 연산 CPU 비용이 양쪽 모두에 붙는다. 재사용된 연결이면 이 비용이 전부 0이다.

9-2. keep-alive만으로는 왜 부족한가

keep-alive는 "연결 하나를 계속 쓰자"는 프로토콜 차원의 약속일 뿐이다. 실제 앱에서는 스레드 수백 개가 동시에 같은 API를 부른다. 이때 누가 지금 어떤 연결을 쓰는지 추적하고, 다 쓴 연결을 버리지 않고 회수하고, 남는 연결이 없을 때 새로 열지 기다릴지 판단하고, 오래 논 연결을 정리하는 관리자가 필요하다.

풀 = keep-alive 연결들을 여러 스레드가 안전하게 나눠 쓰게 하는 관리자

9-3. 무한정 열면 안 되는 세 가지 이유

이유 ① — fd(파일 디스크립터) 고갈

fd는 커널이 열어 둔 무언가를 가리키는, 프로세스가 들고 있는 작은 정수다. 물품보관소 번호표와 같다 — 실물(소켓·파일)은 커널이 보관하고 프로세스는 번호만 들고 다닌다. 유닉스의 "everything is a file" 원칙에 따라 파일·소켓·파이프·터미널이 전부 fd로 표현되고, 그래서 read()/write()/close()로 똑같이 다뤄진다. 자바의 Socket, FileInputStream도 내부에 FileDescriptor를 하나씩 안고 있다.

외부 API 호출로 fd 소진→ 새 인바운드 연결 accept 불가→ 로그 파일 쓰기·설정 읽기 실패→ 전부 Too many open files

현재 사용량은 ls /proc/<PID>/fd | wc -l로 볼 수 있다.

이유 ② — TIME_WAIT과 로컬 포트 고갈

"소켓 하나당 포트 하나"가 아니다. TCP 연결의 신분증은 4-튜플이고, 이 묶음만 유일하면 된다. 응답 패킷이 도착했을 때 커널이 "이걸 어느 소켓에 넣지?"를 판단할 근거가 이 튜플뿐이라서 연결마다 달라야 한다.

이유 ③ — 상한은 제약이 아니라 백프레셔다

설계 관점에서 가장 중요한 이유다. 외부 API가 느려졌을 때 두 경우를 비교해 보자.

풀 없음 / 무제한

  • 응답이 5초로 지연 → 연결이 계속 증가 → 500개 … 2,000개 … 5,000개
  • fd·포트 고갈 → 서버 전체 사망
  • 느리게 죽고, 원인이 불명확하고, 복구도 느리다

풀 있음 / 최대 50

  • 응답이 5초로 지연 → 50개에서 멈춘다
  • 51번째 스레드는 풀에서 대기 → ③ 커넥션 요청 타임아웃 내에 못 얻으면 즉시 실패
  • 빠른 실패 + 지표에 "pool timeout"으로 명확히 기록

암기 카드 — 풀에 상한을 두는 이유 "fd · 포트 · 백프레셔"

① fd
프로세스당 한 통장 — 아웃바운드가 다 쓰면 인바운드 accept와 로그 쓰기까지 실패
② 포트
같은 대상으로는 로컬 포트만이 구분자 + TIME_WAIT 60초 → 초당 약 470개가 물리적 상한
③ 백프레셔
상한은 압력을 눈에 보이는 형태로 바꿔 조용한 자원 고갈사를 빠르고 진단 가능한 실패로 전환

③은 6절의 타임아웃과 짝을 이루고, 11절의 서킷 브레이커·벌크헤드와 같은 계열의 발상이다. 면접에서는 ③을 가장 마지막에, 가장 힘주어 말하는 것이 좋다 — 앞의 둘은 지식이고 ③은 설계 감각이다.

10. 설정은 어디에 하는가 — 출제 의도가 정면으로 묻는 지점

"타임아웃과 커넥션 풀을 어디에 설정하나"에 즉답할 수 있어야 한다. 핵심 구조부터 잡으면 이렇다. RestTemplate과 RestClient는 HTTP를 직접 말하지 않고 ClientHttpRequestFactory라는 부품에 위임한다. 그래서 타임아웃과 풀은 클라이언트가 아니라 이 팩토리(그리고 그 아래 실제 HTTP 라이브러리)에 설정한다. WebClient는 대신 ClientHttpConnector를 통해 리액터 네티에 위임한다.

RestClient / RestTemplate Apache HttpClient 5로 갈아끼우고 세 타임아웃 + 풀을 다 준다

        .setMaxConnTotal(100)전체 상한 — fd·포트 예산의 방어선
        .setMaxConnPerRoute(50)호스트당 상한 — 느려진 한 대상이 풀을 독점하지 못하게
        .setDefaultConnectionConfig(ConnectionConfig.custom()
                .setConnectTimeout(Timeout.ofSeconds(2))① 연결 타임아웃
                .setValidateAfterInactivity(TimeValue.ofSeconds(5))  // 10-2 참고 — 오래 논 연결 검사
                .build())
        .build();

CloseableHttpClient httpClient = HttpClients.custom()
        .setConnectionManager(cm)
        .setDefaultRequestConfig(RequestConfig.custom()
                .setResponseTimeout(Timeout.ofMillis(500))② 읽기 타임아웃
                .setConnectionRequestTimeout(Timeout.ofSeconds(1))③ 풀 대기 타임아웃
                .build())
        .build();

RestClient restClient = RestClient.builder()
        .baseUrl("https://api.example.com")
        .requestFactory(new HttpComponentsClientHttpRequestFactory(httpClient))
        .build();

10-2. 유휴 커넥션 정리 — 간헐적 오류의 단골 원인

풀에 넣어 둔 연결은 내가 안 쓰는 동안 상대가 끊을 수 있다. 서버의 keep-alive 타임아웃, 중간 로드밸런서나 NAT의 유휴 타임아웃 때문이다. 문제는 상대가 끊었다는 사실을 내가 즉시 알 수 없다는 것이다.

① 내 쪽 유휴 정리를 상대보다 짧게

상대 서버의 keep-alive 타임아웃이 60초면 나는 20초로 잡는다. 죽은 연결을 잡기 전에 내가 먼저 버리는 것이다. 위 예제의 maxIdleTime이 그 값이다.

② 꺼내 쓰기 직전에 검사

Apache HttpClient 5의 validateAfterInactivity가 "이만큼 놀았던 연결은 꺼낼 때 살아 있는지 확인하라"는 설정이다.

11. 에러 핸들링 · 서킷 브레이커 · 방어 3단

11-1. 4xx/5xx를 다루는 방식이 셋 다 다르다

RestTemplate / RestClient

4xx/5xx 응답이면 기본적으로 HttpClientErrorException / HttpServerErrorException을 던진다 — 즉 try-catch로 잡는다. RestClient는 onStatus()로 상태별 핸들러를 fluent하게 등록할 수 있다.

WebClient

retrieve()는 4xx/5xx에서 예외를 던지는 게 아니라 WebClientResponseException을 담은 에러 시그널을 Mono에 흘린다. try-catch가 아니라 onErrorResume 같은 리액티브 연산자로 처리해야 하고, 상태 코드와 무관하게 응답을 직접 다루려면 exchangeToMono()를 쓴다.

RestClient 외부의 HTTP 세부사항을 우리 도메인 예외로 번역한다
Member member = restClient.get()
        .uri("/members/{id}", id)
        .retrieve()
        .onStatus(HttpStatusCode::is4xxClientError, (request, response) -> {
            // 여기서 번역하지 않으면 HttpClientErrorException이 서비스 계층까지 올라간다.
            // 그러면 상위 코드가 "외부 API를 HTTP로 부른다"는 사실을 알게 되어
            // 나중에 그 API를 gRPC나 내부 호출로 바꿀 때 상위 코드까지 함께 바뀐다.
            throw new MemberNotFoundException(id);
        })
        .body(Member.class);

"외부 API의 404를 우리 도메인 예외로 번역해 경계 안쪽에 HTTP 세부사항이 새지 않게 한다"는 관점까지 붙이면 설계 감각을 보여줄 수 있다.

11-2. 가산점 — 서킷 브레이커로 한 층 더 가산점

7절에서 확인한 것이 있다. 타임아웃과 풀 상한을 잘 잡아도, 외부가 계속 느린 동안은 매 요청이 그 타임아웃만큼 기다렸다 실패한다. 초당 200건이 전부 0.5초씩 헛되이 기다리는 셈이고, 상대에게도 계속 부하를 주므로 회복을 방해한다.

서킷 브레이커(circuit breaker, 회로 차단기)는 "실패율이 임계치를 넘으면 아예 호출을 시도조차 하지 않고 즉시 실패시키는" 장치다. 두꺼비집이 과전류를 감지하면 회로를 끊어 집 전체를 지키는 것과 같아서 이 이름이 붙었다.

암기 카드 — 방어는 3단이고, 셋은 서로 다른 축을 자른다

① 타임아웃
한 건의 점유 시간을 자른다
리틀의 법칙의 W
② 풀 상한
동시 점유 개수를 자른다
리틀의 법칙의 L
③ 서킷 브레이커
아예 시도하지 않는다
W를 0으로 만든다
시간 → 개수 → 시도 순으로 자른다. 셋이 각각 다른 축이므로 하나가 다른 하나를 대체하지 않는다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 면접 전날 3분 인출 카드

세 클라이언트를 한 줄씩?
RestTemplate 동기+옛 API(유지보수 모드) · WebClient 논블로킹+모던 API(Mono/Flux) · RestClient 동기+모던 API(후계자).
선택 기준 한 문장?
최신순이 아니라 앱의 스레드 모델과 맞는 실행 모델로 고른다. WebFlux→WebClient / MVC 신규→RestClient / 도는 RestTemplate→그대로.
MVC + .block()의 처리량은?
RestTemplate과 완전히 동일(200스레드 × 200ms = 1,000 rps). 스레드만 2개로 늘고 이점은 정확히 0.
RestTemplate은 deprecated?
아니다 — 유지보수 모드. 컴파일 경고 없음 · 버그/보안 수정 계속 · 제거 예고 없음 · 마이그레이션 시한 없음.
타임아웃 3종은?
연·읽·풀 — 연결("상대가 안 받는다") · 읽기("상대가 받고 안 준다") · 풀 대기("우리 풀이 말랐다").
타임아웃 값은 어떻게 정하나?
자원 예산에서 역산 — W = L_budget ÷ λ. 예: 100개 ÷ 200건/초 = 0.5초. 재시도 횟수를 곱해서 계산한다.
타임아웃 없으면 몇 초 만에 죽나?
외부가 5초로 느려지면 200×5=1,000개 필요 → 1초 만에 톰캣 고갈. 트랜잭션 안이면 0.05초에 DB 풀이 먼저.
풀 상한이 필요한 3이유?
fd · 포트 · 백프레셔 — 한 통장인 fd, TIME_WAIT 60초로 초당 약 470개인 포트, 그리고 조용한 죽음을 빠른 실패로 바꾸는 것.
기본 팩토리의 함정은?
new RestTemplate()·RestClient.create()는 SimpleClientHttpRequestFactory → 풀 없음 + 타임아웃 0(무한).
설정은 어디에 하나?
클라이언트가 아니라 ClientHttpRequestFactory(RestTemplate·RestClient) / ClientHttpConnector → reactor-netty ConnectionProvider(WebClient).
재시도의 두 함정은?
① 점유 시간을 곱한다(0.5×3=1.5초→300개) ② 멱등하지 않으면 이중 처리. 타임아웃 = "응답 못 받음"이지 "처리 안 됨"이 아니다.
방어 3단은?
타임아웃(시간) → 풀 상한(개수) → 서킷 브레이커(시도 자체). 세트로 "트랜잭션 안에서 외부 호출 금지"까지 말한다.

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

MVC 앱에서 WebClient를 .block()으로 쓰면 구체적으로 뭐가 문제인가요? 필수힌트: "느려진다"가 아니라 스레드 관점으로 답한다 — 누가 묶이고 몇 개가 동원되는가

스레드 관점으로 답하는 것이 정답 골격이다. .block()을 부르는 순간 톰캣 요청 스레드는 내부 래치에서 잠들어 응답을 기다린다. 즉 실행 모델이 RestTemplate과 완전히 같아진다. 오히려 리액터 nio 스레드가 실제 I/O를 처리하느라 하나 더 동원되므로 스레드는 늘고 처리량 상한은 그대로다. 200 스레드 × 200ms 응답이면 어느 쪽이든 1,000 rps로 동일하다.

이점이 0인데 비용은 다 낸다 — ① 리액터 의존성 추가, ② 리액터 프레임으로 도배돼 우리 코드를 찾기 어려워진 스택트레이스, ③ 나중에 코드 일부가 리액티브 스레드 위로 올라가면 터지는 IllegalStateException: block() ... are blocking이라는 새로운 장애 유형. "얻는 것 없이 복잡도만 산 것"으로 요약하면 된다.

RestTemplate은 deprecated인가요? 기존 코드를 다 갈아타야 하나요? 함정힌트: 사실관계 정정이 답의 절반이고, 나머지 절반은 비용-편익이다

deprecated가 아니라 유지보수 모드다. 버그와 보안 수정은 계속되지만 새 기능은 안 들어간다는 뜻이고, 컴파일 경고도 없고 제거 예고도 없다. 이 구분을 정확히 말하는 것부터가 답의 절반이다.

따라서 잘 돌아가는 코드를 갈아타는 것 자체가 목적이 되면 안 된다. "신규 코드는 RestClient, 기존 코드는 어차피 손댈 일이 생겼을 때 함께 이전"이 현실적 판단이고, RestClient가 RestTemplate과 같은 기반(메시지 컨버터, ClientHttpRequestFactory)을 공유하므로 점진 이전 비용이 낮다는 점을 덧붙이면 좋다.

여기에 "돌아가는 코드를 트렌드 때문에 바꾸는 것도 리스크"라는 비용-편익 관점까지 얹으면 시니어다운 답이 된다. 교체가 만드는 것은 회귀 테스트 비용과 장애 확률이고, 얻는 것이 "최신 API"뿐이라면 남는 장사가 아니다.

외부 API 호출에 타임아웃을 안 정하면 무슨 일이 벌어지나요? 필수힌트: 숫자로 답하는 것이 이 질문의 정답 형태다 — 리틀의 법칙과 두 개의 시각

톰캣 200 스레드, 초당 200건 유입, 외부 API가 죽지 않고 5초로 느려진 상황을 가정하자. 리틀의 법칙으로 필요한 스레드는 200건/초 × 5초 = 1,000개인데 가진 것은 200개다. 아무도 반납하지 않으므로 200 ÷ 200 = 1초 만에 톰캣 스레드가 전부 묶이고, 그 시점부터 그 API와 무관한 /health, /products 요청까지 전부 죽는다. 타임아웃이 없으면 5초가 아니라 무한이므로 스레드는 영영 안 돌아온다.

한 단계 더 들어가면 시니어 답변이 된다. 그 외부 호출이 @Transactional 안에 있으면 스레드만이 아니라 DB 커넥션까지 쥔 채 대기한다. HikariCP 기본 풀은 10개이므로 10 ÷ 200 = 0.05초 만에 DB 커넥션이 먼저 마른다 — 톰캣이 마르기 1초 전에, 그것도 DB를 쓰는 모든 기능을 함께 죽이면서. 그래서 결론은 언제나 세트다 — 타임아웃 명시 + 트랜잭션 안에서 외부 호출 금지.

그럼 타임아웃 값은 몇 초로 잡나요? 시니어 변별힌트: "3초쯤"은 근거 없음, "p99가 800ms니까 1초"는 절반. 나머지 절반은 우리 쪽 예산이다

정답은 우리 쪽 자원 예산에서 역산하는 것이다. 리틀의 법칙을 뒤집는다. 이 API에 내줄 수 있는 스레드 예산을 L_budget, 유입을 λ라 하면 허용 가능한 점유 시간은 W = L_budget ÷ λ다. 톰캣 200개 중 절반인 100개까지만 내주기로 하고 유입이 초당 200건이면 100 ÷ 200 = 0.5초가 상한이다.

외부 API의 p99가 800ms라서 1초를 잡고 싶어도 우리 예산이 0.5초라면 1초는 못 준다 — 그 경우 답은 타임아웃을 늘리는 게 아니라 스레드 예산을 늘리거나(스레드풀 확대) 호출 자체를 줄이는 것(캐싱, 비동기화)이다.

세 가지를 함께 말하면 완성된다. ① 재시도까지 포함해 계산한다 — 0.5초 × 3회면 실제 점유는 1.5초, 필요한 스레드는 300개로 뛴다. ② 연결 타임아웃과 읽기 타임아웃은 다른 근거로 정한다 — 연결은 네트워크 왕복 특성(1~3초면 충분), 읽기는 위의 자원 예산. ③ 타임아웃만으로는 못 막는 구간이 있다 — 외부가 계속 느린 동안은 매 요청이 0.5초씩 헛되이 대기하므로, 그 위에 서킷 브레이커를 얹어야 점유 시간이 0으로 떨어진다.

RestClient에서 타임아웃과 커넥션 풀은 어디에 설정하나요? 필수힌트: 클라이언트 객체에는 그 설정이 없다 — 한 층 아래를 지목한다

클라이언트가 아니라 ClientHttpRequestFactory와 그 아래 실제 HTTP 라이브러리에 설정한다. RestTemplate과 RestClient는 HTTP를 직접 말하지 않고 이 팩토리에 위임하기 때문이다. WebClient는 대신 ClientHttpConnector → reactor-netty HttpClient → ConnectionProvider(풀) 경로다.

여기서 결정적인 사실 하나를 반드시 붙인다 — 아무 설정 없이 new RestTemplate()이나 RestClient.create()를 쓰면 SimpleClientHttpRequestFactory가 붙는데, 이건 JDK HttpURLConnection 기반이라 커넥션 풀을 관리하는 주체가 없고 타임아웃 기본값은 0, 즉 무한이다. 재사용 이득도 상한도 없는 상태다.

실무 답은 Apache HttpClient 5로 갈아끼우고 setMaxConnTotal·setMaxConnPerRoute·세 타임아웃을 명시하는 것이고, 부트를 쓴다면 RestClient.Builder를 빈으로 주입받아 자동 설정(관측 지표 등)을 함께 얻는 편이 낫다.

커넥션 풀은 왜 상한을 두나요? 크게 잡으면 좋은 것 아닌가요? 필수힌트: 세 가지를 층위별로 — 두 개는 자원 고갈, 마지막 하나는 설계 이야기다

(1) fd 고갈. 소켓은 fd를 하나씩 소비하고, fd 테이블은 프로세스당 하나뿐이라 아웃바운드와 인바운드가 같은 통장을 쓴다. 외부 호출로 fd를 다 쓰면 새 인바운드 연결 수락도, 로그 파일 쓰기도 실패한다 — 전부 Too many open files다.

(2) TIME_WAIT과 로컬 포트 고갈. 같은 대상 서버로 나가는 연결은 4-튜플 중 로컬 포트만 다르므로 연결 하나가 포트 하나를 잡는다. 연결을 닫아도 그 튜플은 60초간(리눅스) 예약되므로, 임시 포트 28,000개 기준 초당 약 470개가 새 연결의 물리적 상한이다. 초과하면 BindException: Cannot assign requested address — CPU도 메모리도 멀쩡한데 연결만 실패해 원인 파악이 어렵다.

(3) 상한은 제약이 아니라 백프레셔다 — 이게 설계상 가장 중요한 답이다. 상한이 없으면 외부 지연이 곧 무한한 연결 증가로 이어져 서버가 조용히 죽는다. 상한이 있으면 51번째 요청이 커넥션 요청 타임아웃으로 빠르게, 그리고 "pool timeout"이라는 명확한 이름으로 실패한다. 상한은 압력을 눈에 보이는 형태로 바꾸는 장치다.

여기에 maxConnPerRoute까지 언급하면 좋다. 전체 상한만 있으면 느려진 대상 하나가 풀 전체를 독점해 정상적인 다른 API 호출까지 굶긴다. 호스트당 상한이 그 격벽(bulkhead) 역할을 한다.

재시도를 넣으면 안정성이 올라가는 것 아닌가요? 시니어 변별힌트: 조건부로만 맞다 — 하나는 자원 계산, 하나는 부작용 이야기다

첫째, 재시도는 안정성과 함께 부하도 곱한다. 3회 재시도는 우리 쪽 스레드 점유 시간을 3배로, 상대에게 가는 요청도 3배로 만든다. 그런데 재시도가 발동하는 상황이란 곧 외부가 힘들어하는 상황이므로, 재시도 폭풍이 상대의 회복을 방해한다. 그래서 지수 백오프와 지터가 필수이고, 자원 계산은 재시도 횟수를 곱한 총 점유 시간으로 해야 한다.

둘째, 멱등하지 않은 요청은 재시도하면 안 된다. 읽기 타임아웃이 터졌다는 것은 "응답을 못 받았다"이지 "처리가 안 됐다"가 아니다. 결제 승인 POST를 재시도하면 결제사 입장에서는 승인 요청이 두 번 온 것이고, 그대로 이중 결제가 된다.

원칙은 "재시도와 멱등성은 짝"이다. GET·PUT·DELETE는 정의상 멱등하니 그냥 재시도해도 되고, POST는 Idempotency-Key 같은 멱등성 키를 상대가 지원할 때만 재시도할 수 있다. 지원하지 않는다면 재시도하지 않고 실패로 처리한 뒤 상태를 남겨 대사(reconciliation)하는 것이 정답이다.

외부 API를 대량으로 동시에 호출해야 하면 어떻게 하나요? 가산점힌트: 전통적 답(WebClient 병렬) 뒤에 자바 21 이후 판도 변화를 덧붙인다

전통적인 답은 이렇다. 동기 클라이언트로 100개를 순차 호출하면 지연이 합산되므로(100 × 응답시간), WebClient로 논블로킹 병렬 호출한다 — Flux.fromIterable(ids).flatMap(id -> webClient.get()...) 식으로 적은 스레드로 동시에 흘려보내고 결과를 조합한다. 이때 flatMap의 동시성 인자로 상대에게 가는 부하에 상한을 거는 것까지 말하면 좋다.

다만 자바 21의 가상 스레드 이후 판도가 바뀌었다는 점을 덧붙여야 최신 지형을 아는 답이 된다. 가상 스레드는 블로킹 호출에서 대기할 때 OS 스레드를 반납하고 JVM 힙으로 물러나므로 대기 비용이 사실상 0이다. 그래서 RestClient 같은 동기 클라이언트를 가상 스레드 기반 ExecutorService로 병렬 실행해도 같은 동시성 목표를 달성할 수 있다.

// 자바 21 — 코드는 순차 코드처럼 읽히는데 동시성은 확보된다
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Member>> futures = ids.stream()
            .map(id -> executor.submit(() -> memberApi.getMember(id)))블로킹 호출 그대로
            .toList();
    // 각 가상 스레드는 응답을 기다리는 동안 OS 스레드를 점유하지 않는다
}

"대량 동시 호출 = 무조건 WebClient"라는 공식이 약해졌다는 것, 그리고 가상 스레드에서도 커넥션 풀 상한은 여전히 필요하다는 것(스레드는 싸졌지만 fd와 포트는 그대로 유한하다)까지 말하면 정확한 답이 된다.

그럼 MVC에서 WebClient를 쓰는 게 정당화되는 경우는 없나요? 가산점힌트: 기준은 도구가 아니라 사용 패턴 — 한 줄로 압축할 수 있다

있다. 판단 기준은 도구가 아니라 사용 패턴이고, 한 줄로는 ".block()으로 값을 즉시 뽑아내지 않는 사용인가"다.

세 가지가 대표적이다. (1) SSE·스트리밍 응답을 받아 흘려보내는 경우 — 응답이 끝나기 전에 도착한 조각부터 처리해야 하므로 동기 클라이언트로는 자연스럽게 다룰 수 없다. (2) 여러 외부 API를 동시 호출해 조합하되 결과를 DeferredResult나 CompletableFuture로 이어 톰캣 스레드를 반납하는 경우 — 이때는 요청 스레드가 대기하지 않으므로 논블로킹이 실제로 값을 한다. (3) 조직이 WebFlux로 이전 중이라 클라이언트를 먼저 통일하는 과도기 전략.

반대로 "단건 호출하고 바로 .block()"이 코드의 전부라면 정당화되지 않는다.

RestClient와 WebClient는 API가 거의 같은데, 왜 굳이 별도 클래스를 만들었나요? 가산점힌트: 같은 것은 표면(API), 다른 것은 실행 모델과 소속 모듈이다

같은 것은 API 스타일뿐이고, 다른 것은 실행 모델과 소속 모듈이다. WebClient는 spring-webflux 소속이라 쓰려면 리액티브 스택을 클래스패스에 들여야 하고, 반환도 Mono/Flux여서 MVC 컨트롤러에서 값을 얻으려면 결국 .block()을 부르게 된다. RestClient는 spring-web 소속이고 반환이 일반 객체다.

즉 RestClient는 "WebClient의 좋은 API 디자인만 가져오고 실행 모델은 MVC에 맞는 동기·블로킹으로 되돌린 것"이고, "RestTemplate은 낡았는데 WebClient는 우리 스택에 안 맞는다"는 오랜 어정쩡함을 해소하려고 만든 물건이다.

실무적으로 하나 더 붙이면 좋다 — RestClient는 RestTemplate과 메시지 컨버터·ClientHttpRequestFactory를 공유하므로 기존 설정 자산을 그대로 재사용할 수 있다. 이것이 "손대는 김에 옮기기"의 비용을 낮춘다.

읽기 타임아웃을 1초로 걸었는데 총 소요가 10초여도 안 걸릴 수 있나요? 함정힌트: 그 시계가 재는 것이 "총 시간"인지 "무소식인 시간"인지

있다. 읽기 타임아웃은 대개 "바이트가 하나도 안 도착한 채 흐른 시간"을 잰다. 그래서 응답이 조금씩이라도 계속 흘러오면 총 소요가 값을 넘어도 걸리지 않는다. 느린 대용량 다운로드나 스트리밍 응답, 상대가 청크를 찔끔찔끔 보내는 경우가 여기 해당한다.

그러므로 "읽기 타임아웃 = 이 호출의 최대 소요 시간"이라고 생각하면 자원 계산이 통째로 어긋난다. 총 소요를 잘라야 한다면 읽기 타임아웃과는 다른 축이 필요하다 — 호출 전체에 상한을 거는 장치를 얹거나, 11절의 서킷 브레이커·벌크헤드처럼 "동시 점유 개수"를 자르는 방향으로 방어한다. 어느 쪽이든 "세 개의 시계가 각각 다른 구간을 잰다"는 6절의 그림을 정확히 알고 있어야 나오는 판단이다.

트래픽이 뜸한 새벽에만 connection reset이 간헐적으로 납니다. 왜일까요? 가산점힌트: "뜸한 시간"이 힌트다 — 풀에 놀고 있던 연결에 무슨 일이 있었나

풀에 놀고 있던 연결을 상대가 이미 끊었는데 우리는 모른 채 꺼내 쓴 것이다. 서버의 keep-alive 타임아웃이나 중간 로드밸런서·NAT의 유휴 타임아웃 때문에 상대가 조용히 끊는다. FIN이 오더라도 풀에서 놀고 있는 소켓이라 아무도 읽지 않으므로 우리 쪽 풀은 그 연결을 여전히 "살아 있다"고 여긴다. 그리고 첫 write에서 connection reset / NoHttpResponseException이 터진다.

대응은 두 가지를 함께 쓴다. ① 내 쪽 유휴 정리 시간을 상대의 keep-alive 타임아웃보다 짧게 잡는다(상대가 60초면 나는 20초) — 죽은 연결을 잡기 전에 내가 먼저 버리는 것이다. ② 꺼내 쓰기 직전에 검사한다 — Apache HttpClient 5의 validateAfterInactivity가 그 설정이다. "트래픽이 뜸할수록 연결이 오래 놀아서 더 잘 난다"는 관찰까지 말하면 원인을 정확히 짚은 답이 된다.

타임아웃을 걸었는데도 스레드풀이 고갈됐습니다. 어디부터 의심하나요? 시니어 변별힌트: "걸었다"와 "충분히 짧다"는 다르다. 그리고 곱셈으로 늘어나는 것이 둘 있다

다섯 가지를 순서대로 확인한다.

① 값이 예산보다 큰가. 3초를 걸었다면 200 × 3 = 600개로 여전히 고갈이다. 타임아웃을 걸었다는 사실이 아니라 L = λ × W가 보유 스레드보다 작은지가 기준이다.

② 재시도가 곱하고 있는가. 0.5초 × 3회 = 1.5초 → 300개. 재시도는 점유 시간을 곱한다.

③ 트랜잭션 안에서 부르는가. 그렇다면 톰캣보다 DB 커넥션 풀(기본 10)이 0.05초 만에 먼저 마른다 — 증상은 "스레드풀 고갈"이 아니라 DB 관련 전면 장애로 먼저 나타난다.

④ 커넥션 요청 타임아웃(③번 시계)을 안 걸었는가. 풀 상한만 있고 대기 타임아웃이 없으면 풀 앞에서 무한 대기가 된다 — 읽기 타임아웃은 연결을 얻은 뒤부터 재므로 이 구간을 못 자른다.

⑤ 외부가 계속 느린가. 그렇다면 매 요청이 타임아웃만큼 헛되이 기다리므로, 서킷 브레이커로 시도 자체를 끊어야 W가 0으로 떨어진다. — 이 다섯 개가 곧 "시간 → 개수 → 시도"라는 방어 3단의 점검표다.

한 줄 요약
RestTemplate(동기·유지보수 모드, deprecated 아님), WebClient(논블로킹·리액티브), RestClient(동기 + 모던 API, 스프링 6.1/부트 3.2 등장, RestTemplate의 후계자)의 스펙 차이보다 중요한 것은 선택 기준이다 — HTTP 클라이언트는 최신순이 아니라 앱의 스레드 모델과 맞는 실행 모델로 고르는 것이고, 톰캣 MVC에서 .block()을 부르면 요청 스레드는 그대로 묶인 채 리액터 스레드만 하나 늘어 처리량 상한(200 스레드 × 200ms = 1,000 rps)이 RestTemplate과 완전히 같아지므로 이점 0에 비용만 남는다. 그래서 MVC 신규 개발은 RestClient가 기본값이고, 무엇을 고르든 연결·읽기·풀 대기 타임아웃과 커넥션 풀 상한을 "우리가 내줄 수 있는 스레드 예산"에서 역산해 명시해야 외부 API의 지연 하나가 1초 만에 톰캣 스레드풀 고갈로 번지는 연쇄를 끊을 수 있다.
