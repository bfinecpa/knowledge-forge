Graceful Shutdown과 무중단 배포 — 배포할 때마다 에러가 소량 나는 이유

📖 약 11분 🧩 8개 섹션 0/8 섹션 이해
🎯 핵심 관전 포인트

배포 시 에러의 실패 모드는 두 가지다 — (a) 구버전 프로세스가 죽으면서 진행 중이던 요청이 끊기는 것, (b) LB가 아직 트래픽을 보내는데 앱이 새 요청을 거부하는 순서 레이스. (a)는 앱의 server.shutdown=graceful이 막고, (b)는 인프라가 트래픽 차단 → 전파 대기 → SIGTERM 순서를 보장해야 막는다. 역할 분담: 앱 graceful = 이미 들어온 요청 보호, 인프라 = 새 요청 차단, 배포 절차 = 둘의 순서 보장. 한쪽만 하면 배포 때마다 에러가 "소량" 계속 난다.

0

질문 + 의도

▾
면접 질문

"배포 중 무중단(graceful shutdown)을 위해 Spring Boot에서 어떤 설정과 인프라 구성이 필요한가요?"

출제 의도배포할 때마다 에러가 소량 발생하는데 아무도 신경 안 쓰는 팀이 많다. 이를 문제로 인식하고 인프라(LB 제외)와 앱(진행 중 요청 완료)의 협업으로 풀어본 사람인지 — 운영 품질에 대한 기준선을 본다.
1

문제 정의 — 두 가지 실패 모드를 구분하라

▾

배포 스크립트가 구버전 프로세스를 내리는 순간:

실패 모드증상책임 주체
(a) 진행 중 요청 끊김처리하다 만 요청이 커넥션 리셋/502 — 트랜잭션은 롤백되지만 클라이언트는 실패 응답앱 (server.shutdown=graceful)
(b) 순서 레이스앱은 이미 종료 절차에 들어갔는데 LB가 계속 새 요청을 보냄 → connection refused/502인프라 + 배포 절차

많은 팀이 (a)만 고치고 "graceful 켰는데 왜 아직도 에러가 나지?"에서 멈춘다 — 남은 건 전부 (b)다.

2

앱 쪽: server.shutdown=graceful

▾
yaml
server:
  shutdown: graceful          # 기본값은 immediate
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s   # 기본 30초

SIGTERM 수신 시 동작 순서:

  1. 신규 요청 수용 중단 — 톰캣이 새 커넥션/요청을 더 받지 않는다.
  2. 진행 중(in-flight) 요청 완료 대기 — 처리 중이던 요청은 응답까지 마저 처리.
  3. 타임아웃 초과 시 강제 진행 — timeout-per-shutdown-phase(기본 30s)를 넘기면 남은 요청을 포기하고 종료 단계를 계속한다. 무한정 기다리지 않는다.

주의: 이 설정은 이미 들어온 요청만 보호한다. 1번 단계 때문에 "새 요청 거부"는 오히려 즉시 시작되므로, LB가 계속 트래픽을 보내고 있으면 (b) 레이스가 그대로 터진다.

3

핵심 원리 — LB 제외는 비동기로 전파된다

▾

LB에서 인스턴스를 빼는 것은 API 호출 한 번으로 끝나지 않는다. 헬스체크 주기, 엔드포인트 목록 전파, 프록시 갱신까지 수 초의 전파 지연이 있다. 그래서 순서 보장 패턴은 항상 3단계다:

text
① 트래픽 차단 신호 (LB 디레지스터 / readiness DOWN / 엔드포인트 제거)
② 전파 대기 (LB가 실제로 안 보낼 때까지 — sleep 또는 draining 대기)
③ SIGTERM (이제 graceful shutdown이 in-flight만 처리하면 됨)

②를 생략하면 ①과 ③ 사이에 도착한 요청이 전부 에러가 된다 — "graceful 켰는데도 배포 에러"의 정체.

3-1. 애초에 "전파"가 왜 필요한가 — 라우팅 판단은 한 곳에서 안 한다

"목록에서 뺐다"는 건 원본 하나를 고친 것이고, 실제로 트래픽을 흘리는 건 그 목록의 사본을 들고 있는 여러 대의 프록시다. 노드가 50대면 각 노드의 kube-proxy 50개가 각자 사본을 들고 각자 판단한다. 인그레스 파드도, 클라우드 LB 노드도 마찬가지다.

💡

중앙 스위치 한 번 내리면 끝나는 구조가 아니라, 복제된 데이터가 모든 사본에 퍼져야 끝나는 구조다. 그래서 "제거"가 "전파"를 필요로 한다.

3-2. 전파 지연의 세 가지 원인

앞 문단의 "헬스체크 주기, 엔드포인트 목록 전파, 프록시 갱신"은 전파가 왜 느린지의 세 원인을 나열한 것이다.

원인무엇에 걸리는 시간인가실제 크기
① 헬스체크 주기상대가 "쟤 죽었네"를 알아채는 시간. LB는 통보받는 게 아니라 주기적으로 찔러보고 판단한다ALB 기본 30초 주기 × 2회 연속 실패 = 최악 60초+
② 엔드포인트 목록 전파알아낸 사실이 모든 사본에 도달하는 시간. watch 이벤트가 노드 수만큼 각각 날아가고 도착 시각도 제각각수백 ms ~ 수 초
③ 프록시 갱신사본을 받은 뒤 실제 규칙을 다시 쓰는 시간. kube-proxy는 iptables 규칙 전체 재작성, nginx는 upstream 리로드, 클라우드 LB는 반영까지 별도 지연서비스가 많은 클러스터에서 수 초

합치면 인지(①) + 배포(②) + 적용(③) = 수 초 ~ 수십 초. readiness DOWN 방식이 특히 느린 이유는 ①이 통째로 붙기 때문이다 — 내가 DOWN을 응답해도 상대가 물어보러 오는 건 최대 한 주기 뒤다.

3-3. "트래픽 차단 신호" 세 가지는 같은 목적, 다른 주체

①에 병기된 세 가지는 선택지다. 환경에 따라 쓸 수 있는 게 달라서 나란히 적었을 뿐 목적은 같다.

방법실행 주체방식쓰는 환경
LB 디레지스터배포 스크립트(내가 능동적으로)LB API를 직접 호출해 "이 인스턴스 빼"VM + 클라우드 LB, LB API 권한이 있을 때
readiness DOWN앱(수동적으로 당함)헬스체크에 실패로 응답 → 상대가 알아서 뺌LB API 권한이 없을 때. 대신 위 ① 주기만큼 느림
엔드포인트 제거k8s 컨트롤러(자동으로 일어남)파드의 삭제 표시를 보고 컨트롤러가 목록에서 뺌쿠버네티스. 내가 시키는 게 아니라 저절로 일어난다

셋의 공통점이 이 장의 핵심: 전부 "신호"일 뿐 "완료"가 아니다.

  • 디레지스터 API가 200을 반환해도 → LB 노드들에 반영은 아직.
  • readiness가 DOWN을 응답해도 → 상대가 아직 안 물어봤을 수 있음.
  • 엔드포인트 목록에서 빠져도 → 노드 50대의 iptables는 아직 옛날 것.

그래서 ①에서 ③으로 바로 넘어가면 안 되고, 가운데 ②가 반드시 들어가야 한다.

4

Kubernetes — preStop sleep이 필요한 이유

▾

함정: 파드 종료 시 "엔드포인트 목록에서 제거"와 "컨테이너에 SIGTERM 전송"이 동시에, 서로 비동기로 진행된다. kube-proxy/인그레스가 엔드포인트 갱신을 반영하기 전에 SIGTERM이 먼저 도착할 수 있다.

4-1. 등장인물 — 누가 무엇을 하는가

주체어디서 도나하는 일
API 서버(etcd)마스터모든 상태의 원본. "이 파드 죽는 중"이라는 사실이 여기 기록된다
kubelet노드마다 1개자기 노드의 컨테이너 관리. preStop 훅 실행 → SIGTERM 전송이 이쪽 담당
EndpointSlice 컨트롤러마스터(kube-controller-manager)"이 서비스의 살아있는 파드 IP 목록" 관리. 목록에서 제거가 이쪽 담당
kube-proxy노드마다 1개위 목록을 보고 자기 노드의 iptables/IPVS 규칙을 다시 쓴다
인그레스 컨트롤러(nginx 등)파드로 여러 개위 목록을 보고 자기 upstream 설정을 다시 쓴다
클라우드 LB(ALB 등)클라우드 쪽자체 타겟 목록 보유. 컨트롤러가 API로 디레지스터해줘야 빠진다

핵심: SIGTERM을 보내는 주체(kubelet)와 목록에서 빼는 주체(EndpointSlice 컨트롤러)는 서로 다른 프로세스이고, 서로에게 보고하지 않는다.

4-2. 파드 하나가 죽을 때 실제로 벌어지는 일

kubectl delete pod나 롤링 업데이트가 하는 일은 딱 하나 — API 서버에 있는 파드 객체에 삭제 표시(deletionTimestamp)를 찍는 것뿐이다. 그 순간 이걸 지켜보던 두 부류가 동시에, 각자 움직인다.

text
            [API 서버] 파드에 "삭제중" 표시
                  │
        ┌─────────┴───────────────────────────────┐
   (경로 A: 죽이는 쪽)                    (경로 B: 트래픽 끊는 쪽)
        ▼                                         ▼
   그 노드의 kubelet                     EndpointSlice 컨트롤러
        │                                         │
    preStop 훅 실행                        목록에서 파드 IP 제거
        │                                         │
    SIGTERM 전송                      ┌───────────┼────────────┐
        │                             ▼           ▼            ▼
   앱: 새 요청 거부 시작        노드1 kube-proxy  노드2...  nginx 인그레스
                                iptables 재작성           upstream 리로드
                                                                │
                                                                ▼
                                                     클라우드 LB 디레지스터
  • 경로 A는 짧다 — 마스터 → 그 노드의 kubelet → 컨테이너. 한두 홉이면 끝.
  • 경로 B는 길다 — 마스터 → 목록 갱신 → 클러스터의 모든 노드가 각자 감지 → 각자 iptables 재작성 → 인그레스도 각자 리로드 → 클라우드 LB는 API 호출까지.

그래서 A가 먼저 끝난다. 앱은 이미 "새 요청 안 받음" 모드인데 아직 규칙을 못 고친 노드의 kube-proxy는 그 파드로 요청을 계속 보낸다 → connection refused / 502. 누가 버그를 낸 게 아니라 둘의 순서를 맞춰줄 조정자가 애초에 없는 설계다.

preStop sleep은 여기에 개입한다 — 짧은 쪽(A)에 일부러 브레이크를 걸어 긴 쪽(B)이 따라잡을 시간을 준다.

4-3. 설정

yaml
spec:
  terminationGracePeriodSeconds: 60   # > preStop(15s) + graceful timeout(30s)
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 15"]   # ② 전파 대기를 sleep으로 확보
      readinessProbe:
        httpGet: { path: /actuator/health/readiness, port: 8080 }
  • preStop sleep 10~15초 = SIGTERM을 늦춰서 엔드포인트 제거가 전파될 시간을 버는 것. 이 sleep 동안 앱은 정상 서빙 중이므로 새 요청을 받아도 안전하다.
  • terminationGracePeriodSeconds는 preStop + graceful timeout의 합보다 커야 한다. 넘기면 SIGKILL이 날아와 graceful이고 뭐고 없다.
  • readiness probe는 롤링 업데이트에서 신버전이 준비된 뒤에만 트래픽을 받게 하는 반대 방향 보호막.
5

VM + LB — 배포 스크립트가 순서를 책임진다

▾
bash
# ① LB에서 제외 (디레지스터 API 또는 헬스체크 엔드포인트를 DOWN으로 전환)
aws elbv2 deregister-targets --targets Id=$INSTANCE
# ② connection draining / deregistration delay 대기 (LB가 in-flight를 흘려보내는 시간)
sleep $DRAIN_SECONDS
# ③ 이제 SIGTERM
kill -TERM $PID   # graceful shutdown이 잔여 요청 마무리

헬스체크 DOWN 전환 방식(예: actuator readiness를 내리는 관리 엔드포인트 호출)을 쓰면 LB API 권한 없이도 ①을 수행할 수 있다 — 단 헬스체크 실패 판정 횟수 × 주기만큼 ②를 길게 잡아야 한다.

6

놓치기 쉬운 것

▾
  • SIGKILL(kill -9)은 graceful 무효 — 훅 자체가 실행되지 않는다. 배포 스크립트가 TERM 후 대기 없이 곧바로 -9를 쏘는지 점검.
  • 백그라운드 작업도 shutdown phase에 물린다 — @Scheduled/@Async 실행 중 작업, 커넥션풀 정리(HikariCP close)도 컨텍스트 종료 단계에서 순서대로 내려간다. 오래 걸리는 배치성 작업이 있으면 timeout 안에 못 끝나 강제 종료될 수 있다.
  • 롤링 배포는 신구 버전이 동시에 살아 있는 시간을 만든다 — DB 스키마·이벤트 포맷이 양쪽 버전과 호환(하위호환)돼야 무중단이 완성된다. 프로세스 종료만 곱게 해서는 부족하다.
7

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

(b) 레이스. LB 제외 전파가 끝나기 전에 SIGTERM이 도착. 해법 = preStop sleep / 디레지스터 후 대기.

timeout-per-shutdown-phase 초과 시 끊긴다. 장시간 작업은 요청-응답이 아니라 비동기 작업(큐 + 워커)으로 분리하는 게 설계 정답.

종료 시퀀스에서는 readiness 실패 반영도 결국 엔드포인트 전파를 기다려야 하므로 같은 문제. sleep이 가장 단순·확실한 전파 대기 수단.

좀비 배포가 된다(롤링이 안 끝남). 상한을 두고, 초과분은 끊는 대신 장시간 작업 자체를 없애는 방향으로.

✅ 한 줄 요약

무중단 배포 = 앱의 server.shutdown=graceful(들어온 요청은 끝까지, 기본 30s 상한) + 인프라의 트래픽 차단 → 전파 대기 → SIGTERM 순서 보장(k8s는 preStop sleep, VM은 디레지스터 후 draining 대기) — 앱은 이미 들어온 요청을 보호하고, 인프라는 새 요청을 차단하며, 배포 절차가 그 둘의 순서를 보장한다.
