Spring MVC 요청 처리 흐름
DispatcherServlet이 지휘하는 프론트 컨트롤러 파이프라인

면접 질문: "Spring MVC의 요청 처리 흐름(DispatcherServlet → HandlerMapping → ...)을 설명해주세요."

핵심 관전 포인트 — 모든 HTTP 요청은 단 하나의 프론트 컨트롤러인 DispatcherServlet으로 모이고, 그 앞뒤로 정해진 파이프라인을 통과한다. 순서는 Filter(서블릿 컨테이너) → DispatcherServlet → HandlerMapping(누가 처리할지 탐색) → HandlerAdapter(인터셉터 preHandle → 인자 바인딩 → 컨트롤러 실행 → 반환값 처리) → 예외가 났다면 HandlerExceptionResolver → 뷰 렌더링 또는 메시지 컨버터 직렬화 → 응답이다. 탐색과 실행이 HandlerMapping과 HandlerAdapter로 갈라져 있다는 점, 그리고 인자 바인딩이 컨트롤러 진입 전에 끝난다는 점이 이 파이프라인을 이해하는 두 축이다. 이 순서를 쥐고 있으면 스택트레이스에 어떤 프레임이 보이고 어떤 프레임이 없는지만으로 요청이 어느 단계에서 죽었는지 특정할 수 있어서, 인증·바인딩·비즈니스 로직 중 어디를 열어봐야 할지가 즉시 정해진다.
  • 1
    순서를 통째로 말한다 — Filter → DispatcherServlet → HandlerMapping(누가 처리할지 탐색) → HandlerAdapter(실행: 인터셉터 preHandle → 인자 바인딩·검증 → 컨트롤러 메서드 → 반환값 처리 → postHandle) → 예외 시 HandlerExceptionResolver → ViewResolver+렌더링 또는 HttpMessageConverter 직렬화 → afterCompletion → 응답은 필터 체인을 역순으로 되돌아 나간다.
  • 2
    이 파이프라인을 이해하는 축은 둘이다 — ① 탐색과 실행이 갈라져 있다: Mapping은 누가(which), Adapter는 어떻게(how)에 답한다. 핸들러의 형태가 하나가 아니어서, 실행 방법을 DispatcherServlet이 직접 알면 OCP가 깨지기 때문이다. ② 바인딩은 컨트롤러 진입 "전"에 끝난다: invokeForRequest()가 getMethodArgumentValues()를 먼저 부르고 그다음에 doInvoke()를 부른다.
  • 3
    그래서 이 지식은 곧 디버깅 속도다 — 스택에 DispatcherServlet.doDispatch가 없으면 요청은 필터에서 죽은 것이고, 있는데 doInvoke가 없으면 컨트롤러는 한 줄도 실행된 적이 없다. "400인데 서비스 로그가 없다"에서 흐름을 모르는 사람은 실행된 적도 없는 OrderService를 뒤지고, 아는 사람은 DTO의 검증 애너테이션을 먼저 연다.

0. 질문 + 출제 의도

질문: "Spring MVC의 요청 처리 흐름(DispatcherServlet → HandlerMapping → ...)을 설명해주세요."

출제 의도: 필터에서 죽었는지, 인터셉터에서 죽었는지, 컨트롤러 전 바인딩에서 죽었는지 — 에러 로그의 스택트레이스를 보고 "어느 단계"인지 즉시 아는 사람과 모르는 사람의 디버깅 속도 차이가 크다. 파이프라인의 순서를 아는 것이 곧 디버깅 방향을 잡는 능력임을 확인하는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① 이름만 순서대로 읊고 끝나는 것 → 2절의 한 장 도식으로 각 단계가 "무엇을 알고 있는 시점"인지까지 붙여서 외운다. 순서 암송은 배점의 절반이다.
② "Mapping이 찾고 Adapter가 실행한다"를 외우기만 하는 것 → 6절에서 왜 굳이 둘로 쪼갰는지를 핸들러 4종과 OCP로 설명한다. "왜"를 답하면 한 칸 올라간다.
③ 바인딩 예외를 컨트롤러 문제로 착각하는 것 → 7·10절에서 getMethodArgumentValues와 doInvoke의 선후 관계를 못 박고, 실제 스택트레이스 세 개로 판별 절차를 만든다.
두 문장 비유 — 원무과 접수 창구, 그리고 공항 원무과 접수 창구: 환자는 무조건 창구로 오고, 창구가 증상을 보고 어느 진료과로 보낼지 정한다. 접수·보험 확인 같은 공통 절차는 창구가 처리하므로 진료과 의사(컨트롤러)는 진료에만 집중한다.  /  공항: 보안 검색대(Filter)는 어느 항공편 승객이든 무조건 통과시키지만 당신이 어느 비행기를 탈지는 모른다. 탑승 게이트(Interceptor)는 항공편이 정해진 뒤에야 존재하므로 편별로 다르게 대할 수 있지만, 보안 검색에서 걸러진 사람은 게이트를 구경도 못 한다.

1. 왜 "프론트 컨트롤러" 구조인가

1-1. 전제 지식 — 스프링 이전에 요청을 받던 물건

HTTP 요청을 받아 자바 객체로 바꿔주는 일은 스프링이 발명한 것이 아니다. 서블릿 컨테이너(톰캣 같은 것)가 소켓을 열고 HTTP 텍스트를 파싱해 HttpServletRequest 객체로 만들어 주면, 개발자는 서블릿이라는 자바 클래스로 그 요청을 처리했다. 여기서는 "DispatcherServlet도 결국 서블릿 하나이며, 그 앞에는 스프링이 아닌 컨테이너의 세계가 있다"는 사실만 쥐고 가면 된다.

문제는 URL마다 서블릿을 하나씩 만들던 구조에 있었다. 인코딩 설정, 인증 확인, 파라미터 파싱, 뷰 이동 같은 공통 작업이 모든 서블릿에 그대로 복사된다.

before URL마다 서블릿 하나 — 공통 로직이 전부 중복된다
public class OrderServlet extends HttpServlet {
    protected void doPost(HttpServletRequest req, HttpServletResponse res) {
        req.setCharacterEncoding("UTF-8");중복 1 · 인코딩
        // 빠뜨리면 이 URL만 한글이 깨진다
        if (!isAuthenticated(req)) { ... }중복 2 · 인증
        // 서블릿 하나만 빠뜨려도 그게 보안 구멍이다
        String itemId = req.getParameter("itemId");중복 3 · 파싱
        // 문자열을 손으로 꺼내 타입 변환까지 직접

        // ... 비즈니스 로직 (진짜 하고 싶었던 일은 여기뿐) ...

        req.getRequestDispatcher("/order.jsp")중복 4 · 뷰 경로
           .forward(req, res);
    }
}
after 개발자는 핸들러 메서드만 쓴다 — 공통 처리는 파이프라인이 대신한다
@RestController
public class OrderController {

    @PostMapping("/orders")
    public OrderResponse create(@RequestBody OrderRequest request) {
        // 인코딩 · 인증 · JSON 역직렬화 · 검증 · 직렬화가

        return orderService.create(request);
    }
    // ↑ 그래서 이 메서드에 도달하지 못한 요청은
    //   여기 로그가 한 줄도 안 남는다 — 10절의 주제다.
}

1-2. 프론트 컨트롤러 — 관문 하나로 모은다

프론트 컨트롤러 패턴은 모든 요청이 반드시 지나가는 관문을 하나 두고, 공통 처리를 그 관문에 모으고, 관문이 "이 요청은 누가 처리할지"를 찾아 위임하는 구조다. "프론트"는 앞단이라는 뜻이고, 이름 그대로 모든 컨트롤러의 앞에 서 있다. Spring MVC에서 그 관문이 DispatcherServlet이다 — dispatch는 "적임자에게 배정해 보낸다"는 뜻으로, 이 서블릿이 하는 일 자체가 이름이 됐다.

편해진 대가 — 이 문서 전체의 존재 이유

내 코드가 실행되기 전에 벌어지는 일이 프레임워크 뒤로 숨는다

공통 처리를 파이프라인에 넘긴 순간, 인코딩·인증·역직렬화·검증이 내가 볼 수 없는 곳에서 일어난다. 그래서 이 파이프라인의 단계를 아는 것이 그대로 디버깅 능력이 된다. 흐름을 모르면 "내 코드가 실행되기 전에 벌어진 일"을 아예 추적할 수 없다.

2. 전체 파이프라인 — 이 한 장이 답의 뼈대다

아래 도식이 이 문서의 전부다. 왼쪽 두 개의 세로 띠(영역 경계)와 ④ 안의 다섯 줄만 정확히 기억하면, 뒤의 모든 절은 이 그림의 각 칸을 확대한 것에 지나지 않는다.

암기 장치 — 큰 순서는 "필 · 디 · 매 · 어 · 예 · 뷰 · 후", 어댑터 속은 "전 · 바 · 실 · 반 · 후"

필터 → 디스패처서블릿 → 매핑(누가) → 어댑터(어떻게) → 예외 리졸버 → 뷰 렌더링 → 후처리(afterCompletion)
④ 어댑터 속 5단계 — 전(preHandle) → 바인딩·검증 → 실행(컨트롤러) → 반환값 처리 → 후(postHandle)

면접에서는 첫 줄을 먼저 통으로 말하고, "이 중 ④가 다시 다섯 단계로 나뉩니다"라고 깊이를 한 겹 더 내려가는 순서로 답하면 구조가 있는 답으로 들린다.

단계별로 "그 시점에 무엇을 알고 있는가"가 다르다 — 이 차이가 11절의 배치 판단을 그대로 결정한다.
단계관리 주체그 시점에 아는 것 / 모르는 것여기서 죽으면 나타나는 증상
① Filter서블릿 컨테이너요청/응답 객체 자체는 교체 가능. 하지만 어느 핸들러가 처리할지는 모른다애플리케이션 로그에 흔적 없이 401·403
② DispatcherServletSpring MVC전략 객체 목록을 안다. 처리 자체는 전부 위임—
③ HandlerMappingSpring MVCURL·메서드·헤더 → 핸들러 + 인터셉터 목록404 (컨트롤러 코드는 멀쩡)
④-b ArgumentResolverSpring MVC핸들러 시그니처와 요청 본문. 컨트롤러는 아직 실행 전400 + 컨트롤러 로그 없음
④-c 컨트롤러내 코드완성된 인자 객체. 여기부터 내 책임500 + 내 패키지 스택트레이스
⑤ ExceptionResolverSpring MVCDispatcherServlet 안에서 난 예외만 안다에러 응답 포맷이 팀 표준과 다름

3. ① Filter — 스프링에 들어오기 전

톰캣 같은 서블릿 컨테이너가 관리하며 DispatcherServlet보다 먼저 실행된다. Spring Security의 인증·인가도 사실은 이 필터 체인(FilterChainProxy)에서 동작한다. 이름이 "Spring" Security라서 스프링 MVC 안에 있을 것 같지만, 실행 위치는 스프링 MVC 바깥이다.

디버깅 단서 — 가장 자주 헛수고하는 지점 컨트롤러에 브레이크포인트를 걸었는데 아예 안 걸리고 401이나 403이 떨어진다면, 요청은 여기서 이미 끝난 것이다. 컨트롤러 코드를 아무리 들여다봐도 답이 없다. 봐야 할 것은 필터 체인의 구성과 순서이지 컨트롤러가 아니다.

Filter와 Interceptor를 어떻게 나눠 쓰는지, 이 계층에서 터진 예외가 왜 @ControllerAdvice에 안 잡히는지는 06-filter-vs-interceptor에서 다룬다. 이 문서에서는 "필터는 파이프라인의 ①, 즉 스프링 밖"이라는 위치만 확실히 쥐면 된다.

4. ② DispatcherServlet — 직접 일하지 않는 지휘자

DispatcherServlet은 스스로 요청을 처리하지 않는다. 각 단계를 교체 가능한 전략 객체에게 위임한다. 여기서 "전략 객체"란 같은 역할을 하는 여러 구현 중 하나를 골라 끼울 수 있게 인터페이스로 분리해 둔 부품을 말한다.

HandlerMapping
누가 처리하는가
URL·메서드·헤더를 보고 핸들러를 찾는다
HandlerAdapter
어떻게 실행하는가
찾은 핸들러의 실행 절차를 안다
HandlerExceptionResolver
예외를 어떻게 응답으로
@ControllerAdvice가 여기서 실행된다
ViewResolver
뷰를 어떻게 찾는가
논리 이름 → 실제 View 객체

Spring MVC의 확장성은 전부 이 위임 구조에서 나온다. 새로운 방식의 핸들러나 새로운 뷰 기술을 붙일 때 DispatcherServlet을 고칠 필요가 없다 — 다음 절이 정확히 그 이야기다.

한 걸음 더 — "서블릿 하나가 병목이 되지 않나요?" DispatcherServlet은 인스턴스가 하나지만, 서블릿 컨테이너는 요청마다 스레드를 배정해 같은 인스턴스의 메서드를 동시에 실행한다. 병목이 되지 않는 전제는 이 서블릿이 요청별 상태를 필드에 갖지 않는다는 것이다. 같은 이유로 싱글턴 빈인 컨트롤러·서비스에 요청별 상태를 필드로 두면 그 순간 스레드 안전성이 깨진다.

5. ③ HandlerMapping — "누가 처리할지" 찾기

요청 URL, HTTP 메서드, 헤더 등을 보고 실행할 핸들러(대개는 컨트롤러 메서드)를 찾는다. @RequestMapping 계열 애너테이션을 담당하는 구현이 RequestMappingHandlerMapping이다.

이때 해당 핸들러에 적용될 인터셉터 목록도 함께 묶어서 반환한다. 이 사실 하나가 인터셉터의 성격 전체를 결정한다.

인터셉터의 성격은 여기서 결정된다

인터셉터는 "어떤 핸들러가 처리하는지 정해진 뒤"에야 존재할 수 있는 부품이다

그래서 인터셉터는 핸들러별로 선별 적용할 수 있는 대신, 필터처럼 모든 요청을 무조건 덮을 수는 없다. 공항 비유로 돌아가면 — 탑승 게이트는 항공편이 정해진 뒤에만 존재하고, 보안 검색에서 걸러진 사람은 게이트를 지나가지 않는다.

디버깅 단서 — 404인데 컨트롤러 코드는 멀쩡해 보인다면 매핑 자체가 안 된 것이고, 원인은 URL 오타 · 컴포넌트 스캔 누락 · @Controller 미부착 같은 것들이다. 매핑이 없을 때 스프링은 보통 예외 없이 404를 만들지만, 설정과 버전에 따라 NoHandlerFoundException·NoResourceFoundException 같은 예외로 만들어 ⑤로 보내기도 한다. "404가 @ControllerAdvice에 안 잡힌다"는 문의의 뿌리가 이 차이다 — 예외가 애초에 안 만들어졌으면 잡을 것도 없다.

6. ④ HandlerAdapter — 왜 "찾기"와 "실행하기"가 둘로 갈라져 있는가 단골

여기가 주니어가 가장 많이 헷갈리는 지점이고, 그래서 꼬리질문 1순위다. "핸들러를 찾았으면 그냥 호출하면 되지, 왜 어댑터가 또 필요한가?"

답은 핸들러의 형태가 하나가 아니기 때문이다. 우리가 매일 쓰는 @RequestMapping 메서드 말고도, Spring MVC가 실행할 수 있는 핸들러는 여러 종류다.

역할을 이렇게 쪼갰다 — 면접에서는 이 두 줄이 답의 핵심이다.
부품답하는 질문아는 것
HandlerMapping누가(which) 처리하는가URL · HTTP 메서드 · 헤더 → 핸들러 객체 (+ 적용될 인터셉터 목록)
HandlerAdapter어떻게(how) 실행하는가이 핸들러 종류의 실행 절차 — 인자를 어떻게 만들고 어떻게 호출하는지
비유 — 콘센트 어댑터 나라마다 플러그 모양(핸들러 형태)이 다른데, 벽면 콘센트(DispatcherServlet)를 나라마다 새로 뚫는 대신 어댑터를 끼운다. 콘센트는 "어댑터"라는 하나의 규격만 알면 되고, 새 나라가 생겨도 벽을 부수지 않는다.

암기 장치 — 두 글자로 봉인

Mapping = which(누가)  ·  Adapter = how(어떻게)

꼬리질문이 오면 ① 역할이 다르다(which/how) → ② 핸들러 형태가 4종이라 실행 절차가 제각각 → ③ 직접 알면 if-else가 늘어 OCP 위반 → ④ 그래서 supports()로 담당을 고른다 순서로 답한다. ③과 ④를 붙이면 "프레임워크가 OCP를 지키는 대표적 설계"라는 말이 자연스럽게 나온다.

7. ④-b ArgumentResolver — 컨트롤러 진입 "전"에 벌어지는 일 함정

@RequestParam, @PathVariable, @RequestBody 같은 애너테이션을 보고 HTTP 요청을 자바 객체로 바꾸는 부품이 ArgumentResolver다. 애너테이션 종류마다 담당 구현이 하나씩 있고, @RequestBody를 맡는 것은 RequestResponseBodyMethodProcessor다. @RequestBody의 JSON 역직렬화는 여기서 HttpMessageConverter(기본 구현은 Jackson)를 호출해 이뤄지고, @Valid 검증도 값이 채워진 직후 같은 자리에서 실행된다.

이 문서에서 반드시 기억해야 할 사실이 하나 있다.

암기 장치 — 컨트롤러 진입 전에 터지는 예외 3종은 "읽 · 검 · 형"

읽기 실패
HttpMessageNotReadableException
JSON을 읽지 못했다 — 문법 오류, 타입 불일치
검증 실패
MethodArgumentNotValidException
읽긴 읽었는데 @Valid 제약에 걸렸다
형변환 실패
MethodArgumentTypeMismatchException
Long id 자리에 abc — 변환이 안 됐다

이 셋 중 하나가 로그에 보이는데 컨트롤러 첫 줄의 로그가 안 찍혔다면, 그건 로거 설정이 잘못된 것이 아니라 애초에 그 줄이 실행된 적이 없는 것이다. 이 인과를 모르면 비즈니스 로직을 몇 시간 뒤진다.

현장 400이 났는데 "주문 생성 시작" 로그가 안 찍힌다 — 로거 문제가 아니다
@PostMapping("/orders")
public OrderResponse create(@Valid @RequestBody OrderRequest request) {
    log.info("주문 생성 시작 {}", request);이 줄에 도달한 적이 없다
    return orderService.create(request);
}

// @Valid 가 붙은 인자를 만드는 일은 ④-b(getMethodArgumentValues)의 몫이고,
// 그 단계에서 던져진 예외는 ④-c(doInvoke)로 내려가지 않는다.
// → 볼 곳은 "요청 스펙과 DTO의 검증 애너테이션"이지 OrderService 가 아니다.

8. ④-d ReturnValueHandler — 응답이 두 갈래로 갈리는 지점

컨트롤러가 값을 반환하면 ReturnValueHandler가 "이 반환값을 어떻게 다룰지" 결정한다. 여기서 응답 경로가 두 갈래로 갈리고, 갈림의 기준은 오직 @ResponseBody의 유무다.

같은 컨트롤러 메서드에 @ResponseBody를 붙였다 뗐다 하면 응답이 어떻게 달라지는지를 코드로 보면 이렇다. 반환 문자열은 똑같은데 의미가 정반대가 된다.

A @ResponseBody 없음 — 반환 문자열은 "뷰 이름"으로 해석된다
@Controller
public class OrderPageController {

    @GetMapping("/orders/{id}")
    public String detail(@PathVariable Long id, Model model) {
        model.addAttribute("order", orderService.find(id));
        return "order/detail";논리 뷰 이름
    }
}
// ⑥ ViewResolver → templates/order/detail.html 렌더링
// 응답 바디: 렌더링된 HTML 문서
B @ResponseBody 있음 — 같은 문자열이 "응답 본문 그 자체"가 된다
@Controller
public class OrderApiController {

    @GetMapping("/orders/{id}")
    @ResponseBody
    public String detail(@PathVariable Long id) {
        return "order/detail";본문에 그대로 기록
    }
}
// ④-d에서 끝. 뷰 렌더링은 일어나지 않는다.
// 응답 바디: order/detail  (Content-Type: text/plain)

가장 흔한 사고 — @Controller에서 JSON을 반환하려다 "뷰를 찾을 수 없다"

@ResponseBody가 없으면 반환값은 응답 본문 후보가 아니라 "뷰 결정에 쓰일 값"으로 해석된다. 객체를 반환한 경우에는 뷰 이름이 없으니 요청 URL에서 뷰 이름을 추측해 찾다가 실패한다. 에러 메시지가 "뷰가 없다"여서 사람들이 템플릿 설정을 뒤지지만, 진짜 원인은 애너테이션 한 개다.

@RestController는 이 실수를 구조적으로 막으려고 @Controller와 @ResponseBody를 미리 합쳐 놓은 것이다 — 즉 이 두 조각은 파이프라인의 서로 다른 단계에 작용한다.

조각작용하는 단계하는 일
@Controller③ HandlerMappingRequestMappingHandlerMapping이 핸들러 후보로 고르는 조건이 된다 (타입에 @Controller 또는 @RequestMapping이 있는가)
@ResponseBody④-d ReturnValueHandler반환값을 뷰 이름으로 해석하는 대신 HttpMessageConverter로 직렬화해 본문에 쓰고, ⑥을 건너뛰게 만든다

9. ⑤ 예외 · ⑥ 뷰 · ⑦ 뒷정리

9-1. ⑤ HandlerExceptionResolver — 예외를 응답으로 바꾸는 자리

컨트롤러에서(또는 인터셉터의 preHandle, 바인딩 단계에서) 예외가 던져지면 DispatcherServlet이 그것을 잡아 등록된 리졸버들에게 넘긴다. 우리가 쓰는 @ControllerAdvice + @ExceptionHandler는 그중 ExceptionHandlerExceptionResolver가 실행해 주는 것이다.

9-2. ⑥ 뷰 렌더링 — 조건부 단계

뷰 이름을 반환하는 전통 MVC라면 ViewResolver가 논리 뷰 이름을 실제 View 객체로 바꿔 렌더링한다. @ResponseBody 경로라면 8절에서 본 대로 이 단계 자체가 생략된다. 파이프라인 도식에서 ⑥만 점선으로 그린 이유가 이것이다.

9-3. ⑦ afterCompletion — 반드시 해야 하는 뒷정리의 자리

마지막으로 Interceptor.afterCompletion이 실행된다. 예외가 났든 안 났든 항상 호출된다는 점이 postHandle과의 결정적 차이이고, 그래서 자원 정리나 MDC 해제처럼 "반드시 해야 하는 뒷정리"의 자리다.

before 정리를 postHandle에 뒀다 — 예외 경로에서 조용히 누수된다
public class TraceInterceptor implements HandlerInterceptor {

    public boolean preHandle(...) {
        MDC.put("traceId", UUID.randomUUID().toString());
        return true;
    }

    public void postHandle(...) {   // 예외가 나면 호출되지 않는다누수 지점
        MDC.clear();
    }
}
// 결과: 예외가 난 요청의 traceId 가 스레드에 남는다.
// 톰캣은 스레드를 재사용하므로, 다음 요청 로그에
// 남의 traceId 가 찍힌다 — 추적이 통째로 뒤엉킨다.
after afterCompletion — 예외가 나도 실행되는 유일한 자리
public class TraceInterceptor implements HandlerInterceptor {

    public boolean preHandle(...) {
        MDC.put("traceId", UUID.randomUUID().toString());
        return true;
    }

    public void afterCompletion(..., Exception ex) {항상 호출
        MDC.clear();
    }
}
// 정상·예외 어느 경로로 끝나든 반드시 정리된다.
// 시그니처에 Exception ex 가 있는 것 자체가
// "예외 상황에도 불린다"는 설계 의도의 증거다.

규칙 — 인터셉터 세 메서드의 실행 조건

메서드언제 불리는가예외가 났다면여기 둘 것 / 두면 안 되는 것
preHandle컨트롤러 실행 전—인증·인가 확인, 값 심기. false 반환 시 파이프라인이 여기서 끝난다
postHandle컨트롤러 실행 후, 뷰 렌더링 전건너뛴다정상 결과에 대한 후처리. 정리 로직은 두면 안 된다
afterCompletion요청 처리가 끝난 뒤그래도 실행된다자원 해제 · MDC clear · 응답 시간 기록

인터셉터가 여러 개면 preHandle은 등록 순서대로, postHandle·afterCompletion은 역순으로 실행된다 — 자원을 스택처럼 쌓았다가 반대로 푸는 구조다.

이 표의 값어치 — 뒤져야 할 코드 범위가 한 단계로 줄어든다

흐름을 모르는 사람

"POST /orders가 400인데 서비스 로그가 없다"
→ 로그 설정을 의심하고
→ 실행된 적도 없는 OrderService부터 읽는다
→ 몇 시간 뒤 "DTO에 @NotNull이 있었네"

흐름을 아는 사람

"로그가 없다 = 컨트롤러 도달 전"
→ 한 줄 추론으로 ④-b로 좁히고
→ 요청 바디와 DTO 검증 애너테이션을 편다
→ 몇 분

면접에서 이 대비를 한 문장으로 말하면 "순서를 외웠다"가 아니라 "써 봤다"로 들린다.

11. 같은 지식이 공통 관심사의 "배치"를 결정한다

파이프라인의 각 단계는 그 시점에 무엇을 알고 있느냐가 다르다. 그래서 "이 공통 처리를 어디에 둘 것인가"의 답도 파이프라인이 정해 준다. 흐름을 아는 것은 디버깅뿐 아니라 설계 판단에도 그대로 쓰인다.

before 핸들러 정보가 필요한 감사 로깅을 필터에 뒀다
public class AuditFilter implements Filter {

    public void doFilter(...) {
        // 어느 컨트롤러가 처리할지 알아야 하는데...알 방법이 없다
        // 문제: 필터는 ③ HandlerMapping "보다 앞"이다.
        //       "어느 핸들러가 처리할지"가 아직 정해지지
        //       않은 시점이라 핸들러 정보에 접근할 방법이 없다.
        // → URL 문자열을 정규식으로 파싱하는 임시방편으로
        //   흘러가고, 매핑이 바뀔 때마다 조용히 깨진다.
    }
}
after 핸들러 정보가 필요하면 ③ 이후인 Interceptor가 맞는 자리
public class AuditInterceptor implements HandlerInterceptor {

    public boolean preHandle(HttpServletRequest req,
                             HttpServletResponse res, Object handler) {
        HandlerMethod method = (HandlerMethod) handler;어느 메서드인지 안다
        // ③에서 핸들러가 이미 정해졌기 때문에 가능하다.
        // 덕분에 @AuditLog 같은 커스텀 애너테이션이 붙은
        // 핸들러만 골라 처리할 수 있다.
        return true;
    }
}
반대 방향의 실수도 있다 인증 실패한 요청까지 포함해 "모든" 요청을 세거나 기록해야 한다면 Interceptor는 너무 안쪽이다. 인터셉터는 ③ 이후에만 존재하므로, ①에서 걸러진 요청은 인터셉터의 관측 사각지대가 된다. trace id 심기를 인터셉터에 두면 정확히 문제가 되는 요청(인증 실패·차단된 요청)의 로그만 추적 불가가 된다.

배치 판단 한 줄 — "무엇을 알아야 하는가"로 결정한다

핸들러를 알아야 하면 Interceptor(③ 이후) · 모든 요청을 덮어야 하거나 요청/응답 객체 자체를 손봐야 하면 Filter(①)

전체 판단 기준과 근거는 06-filter-vs-interceptor에서 다룬다. 이 문서에서 챙길 것은 "배치 문제는 결국 파이프라인 위치 문제"라는 사고 방식이다.

12. 한계와 트레이드오프 시니어 변별

"이 구조의 한계나 트레이드오프는 없나요?"에는 세 가지를 말할 수 있다. 각각에 완화책이나 판단 기준을 붙이는 것이 균형 잡힌 답의 조건이다.

1
요청당 스레드 하나(thread-per-request) 모델이다. 서블릿 스택 위에 있어 기본적으로 블로킹이고, 요청 하나가 외부 API 응답을 기다리는 동안 그 스레드는 아무 일도 못 하면서 점유된다. 외부 호출이 잦고 응답이 느린 트래픽에서는 스레드 풀이 먼저 고갈된다. 이 지점이 WebFlux(이벤트 루프 기반)나 가상 스레드를 검토하는 이유다.
붙일 판단 기준"대부분의 사내 API는 MVC로 충분하고, 팀의 디버깅 역량과 라이브러리 생태계 호환성까지 포함해 선택한다."
2
흐름이 프레임워크 뒤로 숨는다. 편리함의 대가로, 파이프라인을 모르면 "내 코드가 실행되기 전에 벌어진 일"을 전혀 추적할 수 없다. 1-2절의 대가가 여기서 청구된다.
붙일 완화책10절의 스택트레이스 판별이 그 비용을 상쇄하는 지식이고, 필터 순서 · 인터셉터 등록 · 커스텀 ArgumentResolver 같은 확장 지점을 아는 것도 같은 맥락이다.
3
DispatcherServlet 바깥은 별개의 세계다. 예외 처리와 로깅 정책을 @ControllerAdvice 안에만 세우면 필터 단계에서 만들어진 응답이 그 정책 밖으로 새어 나간다.
붙일 결론에러 포맷과 관측의 일관성은 필터 계층까지 포함해서 설계해야 한다 — 9-1절의 두 레인 도식이 그 근거다.

13. 인출 카드 · 꼬리질문 셀프 테스트

13-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

큰 순서 7단계는?
필 · 디 · 매 · 어 · 예 · 뷰 · 후 — Filter → DispatcherServlet → HandlerMapping → HandlerAdapter → ExceptionResolver → View → afterCompletion.
④ 어댑터 속 5단계는?
전 · 바 · 실 · 반 · 후 — preHandle → 바인딩·검증 → 컨트롤러 실행 → 반환값 처리 → postHandle.
Mapping과 Adapter의 차이는?
which vs how. Mapping은 누가 처리하는가, Adapter는 어떻게 실행하는가.
왜 굳이 둘로 쪼갰나?
핸들러 형태가 4종이라 실행 절차가 제각각. 직접 알면 if-else가 늘어 OCP 위반 → supports()로 담당을 고른다.
바인딩은 언제 끝나나?
컨트롤러 진입 전. invokeForRequest가 getMethodArgumentValues → doInvoke 순으로 부른다.
진입 전에 터지는 예외 3종은?
읽 · 검 · 형 — HttpMessageNotReadable / MethodArgumentNotValid / MethodArgumentTypeMismatch.
응답이 갈리는 기준은?
오직 @ResponseBody의 유무. 있으면 메시지 컨버터로 본문 직행 + ⑥ 생략, 없으면 반환값 = 뷰 이름.
@RestController의 두 조각은 어디에?
@Controller는 ③ 매핑 후보 선정, @ResponseBody는 ④-d 반환값 처리. 단계가 다르다.
postHandle vs afterCompletion?
예외가 나면 postHandle은 건너뛴다. afterCompletion은 항상 → 정리 로직의 자리.
스택트레이스 판별 두 프레임은?
DispatcherServlet.doDispatch(없으면 ①) · InvocableHandlerMethod.doInvoke(없으면 ④-c 전).
인터셉터 여러 개면 순서는?
preHandle은 등록 순, postHandle·afterCompletion은 역순.
인터셉터가 모든 요청을 못 덮는 이유?
③ HandlerMapping이 핸들러와 함께 인터셉터 목록을 반환하므로, 핸들러가 정해진 뒤에만 존재한다.

13-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

Spring MVC의 요청 처리 흐름을 설명해주세요. 필수힌트: 이름만 나열하지 말고 "큰 순서 → ④의 내부 → 그래서 얻는 것" 3층으로 답한다

① 큰 순서를 통으로 — Filter(서블릿 컨테이너) → DispatcherServlet → HandlerMapping(누가 처리할지 탐색) → HandlerAdapter(실행) → 예외가 났다면 HandlerExceptionResolver → 뷰 렌더링 또는 메시지 컨버터 직렬화 → afterCompletion → 응답은 필터 체인을 역순으로 되돌아 나갑니다.

② 한 겹 내려가서 ④의 내부 — HandlerAdapter 안에서 인터셉터 preHandle → ArgumentResolver의 인자 바인딩·@Valid 검증 → 컨트롤러 메서드 실행 → ReturnValueHandler의 반환값 처리 → postHandle 순으로 진행됩니다. 여기서 컨트롤러 메서드는 다섯 단계 중 세 번째라는 게 핵심입니다.

③ 그래서 얻는 것 — 이 순서를 알면 스택트레이스만으로 요청이 죽은 단계를 특정할 수 있습니다. DispatcherServlet.doDispatch가 없으면 필터에서 죽은 것이라 컨트롤러를 볼 필요가 없고, 있는데 doInvoke가 없으면 컨트롤러는 한 줄도 실행되지 않은 것이라 볼 곳은 DTO와 요청 스펙입니다.

HandlerMapping이 있는데 HandlerAdapter는 왜 또 필요한가요? 필수힌트: which/how로 시작해서, "핸들러 형태가 하나가 아니다"를 근거로 대고, OCP로 마무리

역할이 다릅니다. Mapping은 "누가(which)", Adapter는 "어떻게(how)"에 답합니다.

근거는 핸들러의 형태가 하나로 고정돼 있지 않다는 것입니다. @RequestMapping 메서드, 함수형 라우팅 핸들러, 정적 리소스 핸들러, 레거시 Controller 인터페이스는 실행 절차가 전부 다릅니다 — 어떤 것은 애너테이션을 읽어 인자를 만들고 리플렉션으로 호출해야 하고, 어떤 것은 메서드를 한 번 부르면 끝입니다.

실행 방법을 DispatcherServlet이 직접 알면 핸들러 형태가 늘 때마다 DispatcherServlet을 수정해야 하므로 개방-폐쇄 원칙이 깨집니다. 어댑터로 분리했기 때문에 새 형태는 어댑터 하나를 추가해 등록하는 것으로 끝납니다.

"프레임워크가 OCP를 지키는 대표적 설계"라고 짚으면 가산점이고, supports(handler)로 담당 어댑터를 고르는 구조까지 말하면 더 좋습니다.

@Controller와 @RestController의 차이는 이 흐름에서 어디에 해당하나요? 필수힌트: "합쳐진 것"이라고만 하면 절반. 두 조각이 서로 다른 단계에 작용한다

@RestController = @Controller + @ResponseBody이고, 두 조각이 파이프라인의 서로 다른 단계에 작용합니다.

@Controller 쪽은 ③ HandlerMapping에 작용합니다. RequestMappingHandlerMapping이 핸들러 후보를 고르는 조건이 "타입에 @Controller 또는 @RequestMapping이 있는가"이기 때문입니다.

@ResponseBody 쪽은 ④-d ReturnValueHandler에 작용합니다. 반환값을 뷰 이름으로 해석하는 대신 HttpMessageConverter로 직렬화해 응답 본문에 쓰고, ⑥ 뷰 렌더링을 건너뛰게 만듭니다.

@Controller에서 JSON을 응답하려다 "뷰를 찾을 수 없음"이 나는 이유가 후자입니다 — 반환값이 응답 본문 후보가 아니라 뷰 결정에 쓰일 값으로 해석되기 때문입니다.

@RequestBody의 JSON은 정확히 어느 시점에 객체로 바뀌나요? 함정힌트: "컨트롤러에서요"가 아니다. 두 메서드의 선후 관계로 답한다

컨트롤러 메서드를 호출하기 직전, ④-b 단계입니다. RequestResponseBodyMethodProcessor라는 ArgumentResolver가 HttpMessageConverter(Jackson)를 호출해 요청 본문을 역직렬화합니다.

그래서 JSON 문법 오류(HttpMessageNotReadableException)나 @Valid 실패(MethodArgumentNotValidException)는 컨트롤러 코드가 한 줄도 실행되기 전에 터집니다. invokeForRequest가 getMethodArgumentValues를 먼저 부르고 그다음에 doInvoke를 부르기 때문입니다.

이 예외들의 스택트레이스에 내 컨트롤러 프레임이 없는 이유가 이것이고, 컨트롤러 첫 줄의 로그가 안 찍히는 이유도 같습니다. 10-2의 스택트레이스를 예로 들면 설명이 확실해집니다.

Filter와 Interceptor의 차이는? 각각 언제 쓰나요? 필수힌트: 차이의 뿌리는 "파이프라인에서의 위치" 하나다

이 파이프라인에서의 위치 차이가 전부입니다.

Filter는 ① — DispatcherServlet 바깥이라 어떤 핸들러가 처리할지 모르지만, 요청/응답 객체 자체를 교체할 수 있고 모든 요청을 덮습니다.
Interceptor는 ③ 이후 — HandlerMethod를 알고 있어 핸들러별 선별 처리가 가능하지만, 스프링에 들어온 요청만 볼 수 있습니다.

여기서 파생되는 실무 결론이 셋입니다 — ① 예외가 @ControllerAdvice에 잡히는지가 갈리고, ② 요청 본문 로깅은 Filter에서만 안전하며, ③ trace id를 Interceptor에 두면 인증 실패 요청이 관측 사각지대가 됩니다. 각각의 근거는 06-filter-vs-interceptor에서 다루므로, 면접에서는 위치 두 문장으로 답하고 필요하면 근거를 이어가면 됩니다.

왜 요청 본문 로깅은 Filter에서만 "안전하게" 되나요? 가산점힌트: 요청 본문은 객체가 아니라 스트림이다

요청 본문은 스트림이라 원칙적으로 한 번만 읽을 수 있기 때문입니다. 어딘가에서 본문을 읽어버리면 그 뒤의 ④-b ArgumentResolver가 @RequestBody를 역직렬화할 때 읽을 것이 남아 있지 않습니다.

그래서 본문을 로깅하려면 읽은 내용을 캐싱해 두었다가 다시 읽을 수 있게 해주는 래퍼로 요청 객체를 감싸야 하고(ContentCachingRequestWrapper 같은 것), 요청 객체 자체를 바꿔치기해 다음 단계로 넘길 수 있는 것은 Filter뿐입니다. 인터셉터는 이미 정해진 요청 객체를 건네받는 위치라 이 교체를 할 수 없습니다.

인터셉터의 preHandle이 false를 반환하면 그 뒤는 어떻게 되나요? afterCompletion은 불리나요? 함정힌트: "항상 불린다"를 그대로 적용하면 틀린다. 기준은 "이미 통과한 인터셉터인가"

false를 반환하면 그 뒤 단계는 전부 진행되지 않습니다 — 바인딩도, 컨트롤러도, 뷰 렌더링도 없습니다. 그래서 preHandle이 인증·인가 확인의 자리인 것입니다. 이때 응답은 그 인터셉터가 직접 써야 합니다.

afterCompletion은 "이미 preHandle을 통과한 인터셉터들"에 한해 역순으로 호출되고, false를 반환한 인터셉터 자신의 afterCompletion은 호출되지 않습니다. 논리가 일관됩니다 — 시작하지 않은 것은 정리할 것도 없다. 그래서 "afterCompletion은 항상 불린다"는 "정상적으로 시작된 인터셉터에 한해"라는 단서를 붙여야 정확합니다.

정적 리소스(/css/app.css) 요청도 이 파이프라인을 타나요? 가산점힌트: 6절의 핸들러 4종 표에 답이 이미 있다

탑니다. 정적 리소스도 핸들러의 한 종류여서, 리소스를 담당하는 HandlerMapping이 ResourceHttpRequestHandler를 찾아주고 HttpRequestHandlerAdapter가 그것을 실행합니다 — "찾기와 실행이 갈라져 있다"는 설계가 실제로 쓰이는 대표 사례입니다.

실무적 함의도 있습니다. 인터셉터를 /**로 등록하면 정적 리소스 요청까지 잡습니다. 인증 인터셉터라면 CSS·이미지 요청이 로그인 페이지로 튕기고, 로깅 인터셉터라면 페이지 한 번에 로그가 수십 줄 쌓입니다 — excludePathPatterns로 제외 경로를 명시해야 하는 이유입니다.

404가 @ControllerAdvice에 잡히지 않는 이유는? 함정힌트: ⑤는 "예외를" 응답으로 바꾸는 자리다 — 그럼 예외가 없다면?

애초에 예외가 만들어지지 않았기 때문입니다. ③ HandlerMapping에서 매핑을 못 찾으면 스프링은 보통 예외를 던지지 않고 곧장 404 응답을 만듭니다. ⑤ HandlerExceptionResolver는 "예외를 응답으로 바꾸는" 자리이므로, 예외가 없으면 실행될 일도 없습니다.

다만 설정과 버전에 따라 NoHandlerFoundException·NoResourceFoundException 같은 예외로 만들어 ⑤로 보내기도 합니다. 그래서 답은 "기본적으로는 예외가 없어서 안 잡히고, 예외로 만들도록 설정하면 잡을 수 있다"가 정확합니다. 이 구분을 모르면 "핸들러를 붙였는데 왜 안 타지"를 몇 번이고 반복하게 됩니다.

DispatcherServlet은 하나인데 동시 요청은 어떻게 처리하나요? 병목이 아닌가요? 가산점힌트: 인스턴스가 하나인 것과 동시에 못 도는 것은 다르다

인스턴스가 하나인 것과 동시 실행이 안 되는 것은 다릅니다. 서블릿 컨테이너는 요청마다 스레드를 배정해 같은 인스턴스의 메서드를 동시에 실행합니다. 요청별 데이터는 전부 메서드 인자와 지역 변수로 흐르므로 서로 섞이지 않습니다.

전제는 이 서블릿이 요청별 상태를 필드에 갖지 않는다는 것이고, 같은 전제가 싱글턴 빈인 컨트롤러·서비스에도 그대로 적용됩니다 — 요청별 값을 필드에 담는 순간 스레드 안전성이 깨집니다. 진짜 병목은 서블릿 개수가 아니라 스레드 풀 크기와 각 요청의 점유 시간이고, 이것이 12절의 thread-per-request 이야기로 이어집니다.

컨트롤러가 CompletableFuture나 DeferredResult를 반환하면 이 흐름이 어떻게 달라지나요? 시니어 변별힌트: 파이프라인이 "한 번에" 끝나지 않고 둘로 쪼개진다

파이프라인이 두 번에 나눠 진행됩니다. 컨트롤러가 결과 대신 "나중에 채워질 그릇"을 반환하면, 그 시점에 요청을 처리하던 컨테이너 스레드는 응답을 완성하지 않은 채 반환되고 요청은 비동기 처리 모드로 들어갑니다. 그래서 ④-d 이후 단계가 그 자리에서 이어지지 않습니다.

나중에 결과가 채워지면 컨테이너가 그 요청을 다시 디스패치하고, 남은 단계(반환값 처리 → 뷰 또는 직렬화 → 응답 완료)가 그때 진행됩니다. 이때 컨트롤러 메서드가 다시 호출되지는 않습니다 — 이미 만들어진 결과를 쓰기 때문입니다.

인터셉터도 이 구조에 맞춰져 있습니다. 비동기 처리가 시작되는 시점에는 postHandle·afterCompletion 대신 AsyncHandlerInterceptor의 afterConcurrentHandlingStarted가 불립니다. ThreadLocal에 무언가 담아 두는 인터셉터·필터가 비동기에서 깨지는 이유가 여기 있습니다 — 시작한 스레드와 끝내는 스레드가 다를 수 있습니다.

이 구조의 한계나 트레이드오프는 없나요? 시니어 변별힌트: 세 개를 대되 각각에 완화책이나 판단 기준을 붙인다

(1) 요청당 스레드 하나 모델입니다. 서블릿 스택 위라 기본적으로 블로킹이고, 외부 API를 기다리는 동안 스레드가 점유됩니다. 외부 호출이 잦고 느린 트래픽에서는 스레드 풀이 먼저 고갈되며, 이 지점이 WebFlux나 가상 스레드를 검토하는 이유입니다. 다만 "대부분의 사내 API는 MVC로 충분하고, 팀의 디버깅 역량과 라이브러리 생태계 호환성까지 포함해 선택한다"는 기준을 붙이는 편이 좋습니다.

(2) 흐름이 프레임워크 뒤로 숨습니다. 편리함의 대가로 내 코드가 실행되기 전에 벌어진 일을 추적하기 어렵습니다. 완화책은 스택트레이스 판별 절차를 알고, 필터 순서·인터셉터 등록·커스텀 ArgumentResolver 같은 확장 지점을 파악해 두는 것입니다.

(3) DispatcherServlet 바깥은 별개의 세계입니다. 예외 처리와 로깅 정책을 @ControllerAdvice 안에만 세우면 필터 단계에서 만들어진 응답이 정책 밖으로 새어 나갑니다. 에러 포맷과 관측의 일관성은 필터 계층까지 포함해 설계해야 합니다.

커스텀 ArgumentResolver는 이 흐름의 어디에 끼어드나요? 가산점힌트: 자리를 알면 "그래서 무엇을 할 수 있고 무엇은 못 하는지"가 따라 나온다

④-b, 즉 컨트롤러 진입 직전입니다. 스프링은 등록된 리졸버들에게 "이 파라미터를 네가 만들 수 있냐"고 물어 담당을 고르므로, @RequestParam 같은 기본 애너테이션 옆에 내 애너테이션을 하나 더 얹는 것이 됩니다 — 6절의 supports() 구조와 같은 확장 방식입니다.

전형적인 용도는 인증된 사용자 정보를 컨트롤러 파라미터로 바로 받는 것입니다. 필터·인터셉터가 심어 둔 인증 정보를 리졸버가 꺼내 도메인 객체로 만들어 넣어주면, 컨트롤러마다 반복되던 "요청에서 꺼내 캐스팅하고 널 체크하는" 코드가 사라집니다. 반대로 이 리졸버에서 던진 예외 역시 컨트롤러 진입 전에 발생하므로, 7절의 규칙이 그대로 적용됩니다.

한 줄 요약
Spring MVC는 모든 요청을 DispatcherServlet 하나로 모아 HandlerMapping(누가) → HandlerAdapter(어떻게: 인터셉터·바인딩·실행·반환값 처리) → ExceptionResolver 또는 뷰 렌더링이라는 교체 가능한 전략 객체들에게 위임하는 프론트 컨트롤러 파이프라인이며, 탐색과 실행이 왜 둘로 갈라져 있는지와 바인딩이 컨트롤러 진입 전에 끝난다는 두 사실을 쥐고 있으면 스택트레이스에 어떤 프레임이 있고 없는지만으로 요청이 죽은 단계를 즉시 특정할 수 있다.
