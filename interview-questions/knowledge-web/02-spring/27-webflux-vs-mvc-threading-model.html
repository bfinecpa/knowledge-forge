WebFlux vs MVC 스레딩 모델
대기를 "스레드 개수"로 흡수하나, "이벤트 통지"로 흡수하나

면접 질문: "Spring WebFlux와 MVC의 스레딩 모델 차이를 설명해주세요. WebFlux 도입이 오히려 독이 되는 경우는?"

핵심 관전 포인트 — 두 모델의 차이는 "I/O를 기다리는 동안 무엇을 낭비하는가"로 갈린다. MVC는 thread-per-request — 요청 하나에 톰캣 스레드 하나가 응답을 다 쓸 때까지 전속되고, 대기 시간을 스레드 개수로 흡수한다(기본 200개가 곧 동시 요청 상한). WebFlux(Netty)는 이벤트 루프 — 커널에 "이 소켓에 데이터가 오면 알려달라"고 등록해 두고 스레드를 즉시 반납해 다음 이벤트로 넘어가므로, 코어 수만큼의 스레드로 수만 동시 연결을 감당한다. 그래서 WebFlux의 전제는 전 구간 논블로킹이고, 이 전제가 깨지는 순간의 폭발 반경이 결정적이다 — 50ms짜리 블로킹 호출 감당량이 톰캣 200스레드는 4,000 TPS인데 이벤트 루프 4개는 80 TPS로 50배 차이라, JDBC 한 줄이 서버 전체를 세운다. 우회로인 boundedElastic(코어×10 = 40스레드)조차 800 TPS라 MVC보다 5배 좁으니, 그 우회가 코드의 주류가 되면 WebFlux를 쓸 이유가 없다. 그리고 Java 21 가상 스레드가 "블로킹 코드 그대로" 이벤트 루프급 동시성을 주면서 "동시 연결 때문에 WebFlux"라는 근거는 상당 부분 무너졌다 — 남는 자리는 request(n)으로 수요를 상류에 전파해야 하는 스트리밍과 유휴 연결이 극단적으로 많은 경우뿐이다. 대신 가상 스레드는 스레드풀이 암묵적으로 해주던 유입 제어를 없애(동시 요청 상한 200 → max-connections 8,192, 40배) 커넥션 풀 앞에서 빠른 실패를 느린 전멸로 바꾸므로, 그 문지기를 세마포어·Bulkhead로 명시 복원해야 한다.
  • 1
    차이는 속도가 아니라 "대기를 무엇으로 흡수하는가"다 — MVC는 요청 하나에 스레드 하나가 응답까지 전속돼 대기를 스레드 개수로 사고(동시 요청 상한 = 풀 크기 200), WebFlux는 소켓을 커널의 epoll에 등록하고 스레드를 반납해 대기를 이벤트 통지로 흡수한다(스레드 ≈ 코어 수). 요청 100개 × DB 50ms에서 묶이는 스레드가 100개 대 4개가 이 차이의 전부다 — 50ms 자체는 어느 쪽도 줄지 않는다.
  • 2
    독이 되는 경우는 "전 구간 논블로킹"이라는 전제가 깨질 때이고, 피해가 질적으로 다르다 — 50ms 블로킹 호출 감당량이 톰캣 4,000 TPS 대 이벤트 루프 80 TPS로 50배 차이라, MVC에서는 "느려짐"인 것이 WebFlux에서는 "정지"다(헬스체크까지 포함). 우회로 boundedElastic도 800 TPS라 MVC보다 5배 좁고, 여기에 리액티브 학습 곡선·끊긴 스택트레이스·ThreadLocal(MDC·Security·@Transactional) 전면 재작업 비용이 얹힌다.
  • 3
    지금 기준의 판단은 "가상 스레드로 충분하지 않은가"를 먼저 묻는 것이다 — Java 21 가상 스레드는 블로킹 코드 그대로 런타임이 캐리어를 반납해 같은 이득을 훨씬 싸게 준다. WebFlux에 남는 자리는 request(n) 수요 전파가 필요한 스트리밍과 유휴 연결 100만 개급뿐이다. 단 가상 스레드는 스레드풀이 하던 유입 제어를 없애므로(200 → 8,192) 세마포어·Bulkhead와 짧은 connection-timeout으로 문지기를 명시 복원해야 한다.

0. 질문 + 출제 의도

질문: "Spring WebFlux와 MVC의 스레딩 모델 차이를 설명해주세요. WebFlux 도입이 오히려 독이 되는 경우는?"

출제 의도: 기술 선택에서 "우리 팀의 학습 비용, 디버깅 난이도, 블로킹 라이브러리 의존성"까지 넣어 판단하는지 본다. 이력서에 WebFlux를 쓴 지원자의 이해가 튜토리얼 수준인지 운영 수준인지 가르는 질문이기도 하다.

기준 버전: Spring Boot 3.x(WebFlux는 Reactor Netty), Java 21. 가상 스레드 서술은 Java 21 정식 기능 기준이고, Spring Boot의 가상 스레드 통합은 3.2 이상이다.

이 페이지가 겨냥하는 약점 세 가지 ① "논블로킹이라 빠르다"로 답하는 것 → 2절에서 같은 상황 하나를 두 모델에 넣어, 50ms는 양쪽 다 똑같이 기다리고 묶이는 스레드만 100 대 4라는 것을 타임라인으로 못 박는다.
② "블로킹 라이브러리를 쓰면 이점이 사라진다"는 순한 표현 → 4절에서 80 TPS 대 4,000 TPS라는 산술로 바꾼다. 사라지는 정도가 아니라 서버가 선다.
③ 2019년의 정답을 그대로 말하는 것 → 7·8절에서 가상 스레드가 무너뜨린 근거와, 그 대가로 새로 생긴 유입 제어 소실(200 → 8,192) 문제까지 붙인다.
한 문장 비유 — 진료실과 진동벨 MVC = 진료실: 환자 한 명이 들어오면 검사 결과가 나올 때까지 의사와 방을 통째로 점유한다. 의사가 그동안 아무것도 안 하고 앉아 있어도(CPU 0%) 그 방은 다른 환자가 못 쓴다 — 그래서 동시 진료 수 = 방 개수(200).  /  WebFlux = 진동벨: 주문을 받아 주방에 넣고 벨을 쥐여 보낸 뒤 즉시 다음 손님을 받는다. 음식이 나오면 주방이 벨을 울려(epoll 통지) 그때 이어서 처리한다 — 그래서 카운터 4개로 손님 수만 명을 받는다. 단, 카운터 직원이 한 명이라도 "주문 하나를 직접 요리하기 시작하면"(블로킹) 그 줄 전체가 선다.

1. 전제 지식 — "스레드를 반납한다"가 OS 수준에서 무슨 뜻인가

WebFlux 설명에는 "논블로킹", "이벤트 루프", "스레드를 반납한다" 같은 말이 정의 없이 등장한다. 그런데 이 말들은 프레임워크의 어휘가 아니라 운영체제의 어휘다. 아래를 먼저 깔지 않으면 그다음이 전부 주문처럼 들린다.

1-1. 블로킹 I/O — 커널이 스레드를 재운다

DB에서 데이터를 읽는 코드는 결국 소켓에서 읽는 코드다. 자바로는 inputStream.read(buf) 한 줄이지만, 그 아래에서는 read(fd, buf, n)이라는 시스템 콜이 일어난다. 시스템 콜은 애플리케이션이 직접 할 수 없는 일(하드웨어 접근, 네트워크 송수신)을 커널에 대신 해달라고 요청하는 호출이다.

이때 읽을 데이터가 아직 도착하지 않았으면 커널은 그 스레드를 대기 큐로 옮기고 재운다.

블로킹 read→ 논블로킹 소켓만 — 폴링 지옥, CPU 100%+ I/O 다중화(epoll)→ 스레드 1개로 소켓 N개

이 문서 전체가 서 있는 한 문장

"CPU를 놓아준 것"과 "스레드를 놓아준 것"은 전혀 다른 이야기다

DB 응답을 기다리며 잠든 스레드는 CPU를 1%도 쓰지 않는다(스케줄링 대상에서 빠졌으므로). 그런데 스레드 자체는 놓여나지 않았다 — 콜 스택에 그 요청의 프레임이 그대로 쌓여 있고, 그 스택을 치우기 전에는 다른 요청의 코드를 실행할 수 없다. "반납한다"는 스택을 비우고 돌아온다는 뜻이고, 그 대신 "나중에 이어서 할 일"을 콜백으로 적어 둬야 한다. 그 적어 두는 방식을 선언적으로 만든 것이 Reactor의 Mono/Flux다.

"스레드를 반납한다"의 정확한 의미 — 대기 중 스택이 비어 있는가
블로킹논블로킹 + 다중화
기다리는 방식스레드가 소켓 하나에 매달려 잠든다소켓들을 커널에 위탁하고 준비된 것만 처리
소켓 1만 개를 기다리려면스레드 1만 개스레드 1개
대기 중 스레드의 스택그 요청의 프레임이 쌓인 채 묶여 있다비어 있다 — 다른 일을 할 수 있다

1-2. 이벤트 루프 — 그 위에 올린 프로그래밍 모델

이벤트 루프(event loop)는 위의 epoll_wait 호출을 무한 루프로 돌리는 스레드다. 이름 그대로 "이벤트를 받아 처리하는 것을 반복하는 고리"다.

개념 이벤트 루프의 뼈대 — 별표 한 줄이 4·5절 전체의 씨앗이다
while (running) {
    List<Event> ready = selector.select();   // epoll_wait — 준비된 게 없으면 여기서 잠든다
    for (Event e : ready) {
        e.handler().run();                   // 준비된 이벤트의 콜백을 실행한다
        // ★ 이 handler 안에서 절대로 블로킹하면 안 된다.여기가 전부다
        //    블로킹하는 순간 이 루프가 멈추고, 이 루프가 담당하는
        //    나머지 모든 연결의 이벤트 처리도 함께 멈춘다.
    }
}
여기서 미리 각인할 것 루프 하나가 수천 개 연결을 담당하므로, 그 루프를 한 번 막으면 수천 개가 함께 멈춘다. MVC의 "스레드 200개 중 1개가 잠긴다"와 구조적으로 다른 사건이다.

2. 두 모델 — 같은 상황 하나로 겹쳐 보기

2-1. MVC — thread-per-request

thread-per-request(요청당 스레드)는 이름 그대로다. 요청 하나가 도착하면 톰캣이 워커 스레드 하나를 배정하고, 그 스레드가 응답 바이트를 다 쓸 때까지 그 요청에 전속된다.

MVC 블로킹 서블릿 + JDBC — 스레드가 요청에 묶이는 지점
public OrderResponse getOrder(Long id) {
    Order order = orderRepository.findById(id);이 안에서 블로킹 read
    // 스레드는 커널의 대기 큐로 들어가 CPU 를 쓰지 않지만,
    // getOrder 호출 프레임이 스택에 그대로 남아 다른 요청을 못 받는다.
    return toResponse(order);
}

그래서 동시 요청 상한 = 스레드풀 크기가 된다. 톰캣 기본값은 max-threads 200이다. 필요한 스레드 수는 Little's law로 계산한다 — 500 TPS × 응답 100ms = 동시 50개(25-thread-pool-connection-pool-sizing.md).

이 모델의 성질 한 줄

대기 시간을 스레드 개수로 산다

대기가 길어지면(외부 API 지연 등) 같은 처리량을 내는 데 더 많은 스레드가 필요하다. 그런데 스레드는 스택 메모리(플랫폼에 따라 수백 KB~2MB 예약)와 컨텍스트 스위칭 비용이 있어서, 수천~수만 동시 연결로 가면 이 방식이 물리적으로 감당이 안 된다.

여기서 자주 나오는 오해 — 대기 중인 스레드는 BLOCKED가 아니다 스레드 덤프에서 DB 응답을 기다리는 스레드는 BLOCKED가 아니라 RUNNABLE로 표시된다. BLOCKED는 오직 synchronized 락 경쟁을 뜻하는 상태 이름이고, 소켓 대기는 네이티브 메서드 안에서 일어나 JVM이 상태를 알 수 없기 때문에 RUNNABLE로 남는다. 자세한 것은 25-thread-pool-connection-pool-sizing.md 2-1.

2-2. WebFlux(Netty) — 이벤트 루프

WebFlux는 서블릿 컨테이너 대신 Netty를 기본 서버로 쓴다. Netty는 1-2의 이벤트 루프를 자바로 구현한 네트워크 프레임워크다. 이벤트 루프 스레드는 코어 수만큼만 뜬다 — Reactor Netty의 기본값은 max(가용 코어 수, 4)이고 reactor.netty.ioWorkerCount로 바꿀 수 있다. 4코어 장비면 4개다.

1
요청 도착 — 이벤트 루프 스레드가 핸들러 체인을 실행한다.
2
DB·외부 API 호출을 논블로킹으로 걸어놓는다 — 쿼리를 소켓에 쓰고, "이 소켓에 응답이 오면 알려달라"고 epoll에 등록한 뒤, 이어서 할 일(리액티브 체인의 다음 단계)을 콜백으로 등록해 둔다. 그리고 스레드는 즉시 다음 이벤트 처리로 넘어간다 — ★ 여기가 "반납"이다.
3
50ms 뒤 응답이 소켓에 도착 — 커널(epoll/kqueue)이 이벤트 루프에 통지하고, 루프가 ②에서 등록해 둔 콜백을 이어서 실행한다.

스레드가 "무언가를 기다리는" 일이 없고 항상 실행할 이벤트만 처리한다. 그래서 대기 시간이 스레드를 소모하지 않고, 4~8개 스레드로 수만 동시 연결을 감당한다. Mono/Flux는 이 "걸어놓고 나중에 이어 하기"를 사람이 읽을 수 있는 체인으로 표현한 것이다 — 콜백을 손으로 중첩하면(콜백 지옥) 관리가 안 되므로, 그것을 선언적 연산자 체인으로 바꾼 것이 리액티브 라이브러리의 존재 이유다.

2-3. 같은 상황 하나로 겹쳐 보기 — 이 그림 하나가 답의 뼈대다

상황 요청 100개가 동시에 도착한다. 각 요청은 DB 쿼리 하나를 보내고 응답을 50ms 기다린 뒤 결과를 돌려준다. 장비는 4코어다.

면접에서 이 한 문장을 먼저 못 박는다

대기 50ms는 어느 모델에서도 50ms다. 줄어드는 것은 그 50ms 동안 묶이는 스레드 수(100 → 4)뿐이다

"WebFlux가 빠르다"로 시작하면 그다음 질문("그럼 응답시간이 얼마나 빨라지죠?")에서 바로 무너진다. 먼저 부정하고, 그다음에 진짜 이득(동시 연결 수·자원 효율)을 말하는 순서가 안전하다.

3. 백프레셔 — MVC에도 있다, 이름이 다를 뿐

2-4의 표에서 "백프레셔"라는 칸을 넘겼다. 이 개념은 8절(가상 스레드가 무엇을 없애는가)의 전제가 되므로 여기서 제대로 정의하고 간다.

백프레셔(backpressure)의 정의 — 배관에서 온 말이다

받는 쪽이 감당할 수 있는 속도로만 보내게 만드는 장치

하류가 좁으면 압력이 거꾸로 밀려 올라와 펌프를 막는다. 흐름은 아래로 가고, "그만 보내"라는 신호는 위로 간다.

3-1. 없으면 어떻게 되는가 — 절벽에서 떨어진다

before 백프레셔 없음 — 생산자가 소비자 사정을 모른다
BlockingQueue<Log> queue =

// 초당 9,000건씩 쌓이는데
// 생산자는 "아무 문제 없다"고 느낀다.
// 지연이 서서히 늘다가 힙이 차는 순간 OOM 급사.
after 백프레셔 있음 — 상한이 곧 신호 장치다
BlockingQueue<Log> queue =

// 생산 속도가 소비 속도에 자동으로 맞춰진다.

// offer → put, 무제한 → 상한. 이 차이가 전부다.
이 실패 모양을 기억한다 백프레셔가 없는 시스템은 서서히 느려지다 멈추는 것이 아니라, 멀쩡해 보이다 절벽에서 떨어진다. 큐의 상한은 제약이 아니라 신호 장치다 — 상한이 없으면 시스템은 자기가 과부하라는 사실을 알 방법이 없다.

3-2. 포화 시 선택지는 셋뿐이고, 블로킹 세계에도 그대로 있다

막기 (block)

버리기 (drop)

생산자에게 에러를 반환한다. 호출자가 재시도·백오프 가능할 때 — HTTP 429.

"막기"만 쓰면 정체가 상류로 계속 전파되므로, 실무에서는 막기 + 타임아웃 후 거절 조합이 일반적이다. 적용 지점별 정리는 07-traffic-performance/16-backpressure-and-application-points.md.

3-3. 그럼 Reactive Streams는 무엇이 다른가

4. WebFlux가 독이 되는 경우 ① — 폭발 반경을 숫자로

여기가 이 질문의 본체다. WebFlux의 이점은 전 구간 논블로킹이라는 전제 위에서만 성립하고, 그 전제가 깨졌을 때의 피해가 MVC와 질적으로 다르다.

"블로킹 라이브러리를 쓰면 WebFlux의 이점이 사라진다"는 흔한 설명은 너무 순한 표현이다. 이점이 사라지는 정도가 아니라 서버가 멈춘다. 1-2의 이벤트 루프 코드를 다시 보면 이유가 자명하다 — 핸들러 안에서 블로킹하면 그 while 루프가 그 자리에 서고, 그 루프가 담당하는 모든 연결의 이벤트 처리가 함께 멈춘다.

5. WebFlux가 독이 되는 경우 ② — CPU 바운드와 팀·운영 비용

5-1. CPU 바운드 작업 — 반납할 대기가 없다

이벤트 루프의 이점은 "기다리는 시간을 다른 일에 쓴다"는 것이다. 그렇다면 기다리는 시간이 없는 작업에는 아무 이점이 없다.

I/O 바운드 — 이벤트 루프가 이기는 자리

  • DB 조회, 외부 API 중계, 파일 전송
  • 요청 시간의 대부분이 남을 기다리는 시간
  • 그 대기를 반납할 수 있으므로 스레드가 적어도 된다

CPU 바운드 — 이득 0, 위험만 도입

  • 이미지 리사이징, 암호화, 대량 집계
  • 반납할 대기가 없다 — 루프가 연산에 잡혀 있는 동안 그 루프의 모든 연결이 지연된다
  • 4-1과 정확히 같은 피해. 블로킹 I/O가 아니라 계산이 루프를 막는다는 점만 다르다
그리고 근본적으로 CPU 바운드는 모델과 무관하게 코어 수가 상한이다. 4코어는 초당 4,000ms의 CPU 시간을 제공하고, 그 이상은 어떤 스레딩 모델로도 만들어낼 수 없다(25-thread-pool-connection-pool-sizing.md 2-3).

5-2. 팀·운영 비용 — 가장 자주 과소평가되는 항목

출제 의도가 명시적으로 짚는 항목이다. 기술적 우열이 아니라 조직의 감당 능력을 판단에 넣는지를 본다.

1
학습 곡선 — 리액티브는 명령형과 사고 방식이 다르다. map과 flatMap의 구분, subscribeOn과 publishOn의 차이, 구독하지 않으면 아무 일도 일어나지 않는다(cold publisher)는 성질. 한 명이라도 모르면 그 사람이 짠 코드에 block()이 들어간다.
2
디버깅 난이도 — 스택트레이스가 체인 곳곳에서 끊긴다. 예외 발생 시점의 스택에는 원래 요청이 어디서 시작됐는지가 없다 — 그 요청을 시작한 스레드는 이미 다른 일을 하고 있기 때문이다. Hooks.onOperatorDebug()나 checkpoint()로 보완할 수 있지만 전자는 오버헤드가 커서 운영에서 상시 켜기 어렵다.
3
ThreadLocal 전제가 깨진다 — 실무에서 가장 크게 물리는 항목. 자바 생태계의 많은 것들이 "한 요청은 한 스레드에서 처리된다"를 전제로 ThreadLocal에 컨텍스트를 담아 왔다.
4
의존성 전수 조사 — 도입 전에 모든 의존 라이브러리의 논블로킹 여부를 점검해야 한다. 하나라도 블로킹이면 4-1의 피해를 본다. 라이브러리 목록을 훑는 정도로 끝나지 않고 그것들이 내부에서 뭘 쓰는지까지 봐야 한다.
"한 요청 = 한 스레드"를 깔고 만들어진 것들이 전부 재작업 대상이 된다

@Transactional이 안 되는 이유는 구조로 답해야 한다

Spring의 트랜잭션 동기화는 커넥션을 TransactionSynchronizationManager의 ThreadLocal에 묶어 같은 스레드의 후속 DB 접근이 그 커넥션을 재사용하게 하는 구조다(24-transaction-synchronization-connection-binding.md). 리액티브 체인은 단계마다 스레드가 바뀔 수 있으므로 이 연결고리 자체가 성립하지 않는다.

출제 의도에 정면으로 답하는 한 문장 튜토리얼 수준의 이해로 도입한 WebFlux는 같은 하드웨어의 MVC보다 느리고 장애만 어렵게 만든다.

우회로는 MVC보다 5배 좁다. 이벤트 루프를 지키는 데는 성공했지만, 그 구간은 결국 thread-per-request로 회귀한 것이고 그 풀이 톰캣 기본값보다 작기 때문이다. 회귀했으므로 풀 크기 산정 문제(Little's law)도 그대로 되살아난다 — 800 TPS를 넘기려면 boundedElastic 크기를 조정해야 하는데, 그 순간 "우리는 왜 WebFlux를 쓰고 있는가"라는 질문이 돌아온다.

거기에 스레드 간 전환 비용도 얹힌다. 이벤트 루프 → 워커 → 이벤트 루프로 두 번 넘어가므로 요청당 컨텍스트 스위칭이 늘고 지연이 조금 붙는다.

이벤트 루프→ boundedElastic 워커 (블로킹 격리)→ 이벤트 루프 전환 2회 · 지연 가산

판단 기준은 하나 — 이 우회가 몇 군데에 쓰이는가

소수 (레거시 한두 개)

  • 합리적인 절충이다
  • 나머지 구간은 이벤트 루프의 이득을 그대로 누린다

코드의 주류가 됐다면

  • WebFlux를 쓸 이유가 남지 않는다
  • MVC로 돌아가는 것이 더 빠르고 더 단순하다

7. 제3의 선택지 — Java 21 가상 스레드

여기까지의 논의는 "블로킹 코드를 쓰려면 스레드가 많아야 하고, 스레드는 비싸다"는 전제 위에 있었다. Java 21의 가상 스레드가 그 전제를 무너뜨린다. 가상 스레드는 OS 스레드에 1:1로 대응하지 않는, JVM이 스케줄링하는 경량 스레드다.

가상 스레드 블로킹 두 줄에서 캐리어가 반납된다 — 코드는 MVC 스타일 그대로
public OrderResponse getOrder(Long id) {
    Member member = memberClient.get(id);        // 300ms 대기 — 여기서 캐리어 반납
    Order order = orderRepository.findById(id);  // 50ms 대기 — 여기서도 반납
    return toResponse(order, member);
}
Spring Boot 3.2+ 설정 한 줄이면 켜진다
spring:
  threads:
    virtual:
      enabled: true    # 톰캣 요청 처리를 가상 스레드로 — MVC 스타일 코드를 그대로 둔다
공짜는 아니다 — 핀닝(pinning) JVM이 시스템 콜 경로를 소유하지 못하는 지점(synchronized 블록 안에서의 블로킹, 네이티브 호출)에서는 캐리어를 반납하지 못하고 못박힌다. 동작 원리와 JDK 버전별 차이는 01-java-kotlin/28-virtual-threads-pinning.md.

7-1. 그 플래그가 실제로 바꾸는 것 / 안 바꾸는 것

spring.threads.virtual.enabled=true는 톰캣 요청 스레드만 바꾸는 것이 아니다. "고정 크기 풀"이라는 전제가 통째로 사라지는 변화다.

바뀌는 것

  • 톰캣 요청 처리 스레드
  • @Async의 기본 executor → 풀링 없는 SimpleAsyncTaskExecutor
  • @Scheduled의 스케줄러 → SimpleAsyncTaskScheduler
  • 이들은 작업마다 새 가상 스레드를 띄우므로 core/max/queue 튜닝 논의 자체가 무의미해진다(15-async-annotation.md)

안 바뀌는 것

  • 직접 만들어 등록한 ExecutorService 빈
  • HikariCP 풀 크기
  • parallelStream이 쓰는 공용 ForkJoinPool(01-java-kotlin/17-parallelstream-pitfalls.md)
  • → 플래그 하나로 시스템의 절반만 바뀌면 나머지 절반이 병목이 된다. 그게 8절이다

8. 가상 스레드가 걷어낸 문지기 시니어 변별

8-1. "무한정"의 실제 상한 — 200이 아니라 8,192

가상 스레드를 켜면 스레드 개수 제한은 사라진다. 그런데 동시 요청 상한이 사라지는 것은 아니다. 톰캣에는 스레드 수와 별개로 max-connections라는 설정이 있다 — 동시에 열어 둘 수 있는 연결의 최대 개수이고, NIO 커넥터의 기본값은 8,192다. 가상 스레드를 켜면 max-threads가 실질적 제한을 못 하게 되므로 이 값이 새로운 실질 상한이 된다.

이 40배가 8-2·8-3의 문제를 전부 만든다

200
기본 MVC — max-threads
8,192
가상 스레드 — max-connections
"무한정"은 스레드 얘기이지 요청 얘기가 아니다 — 동시 요청 상한이 40배가 된다

8-2. 사라지는 것은 백프레셔가 아니라 유입 제어다

3-2에서 "블로킹 모델에도 백프레셔가 있다"고 했다. 그 목록에 있던 항목 하나가 가상 스레드로 사라진다. 톰캣 스레드풀 200개는 그 자체가 유입 제어(admission control) 장치였다. 유입 제어란 "시스템에 들어오는 요청의 수 자체를 문 앞에서 제한하는 것"이다. 201번째 요청은 스레드를 못 잡아 accept 큐에서 대기하다 거절된다. 아무도 그것을 백프레셔라고 부르지 않았지만, 시스템을 지켜주던 것은 그 숫자였다.

정확히 짚어야 할 것 상한이 없어진 것이 아니라 개발자 책임으로 옮겨진 것이다. 물리 자원(DB 커넥션, 파일 디스크립터, 외부 API rate limit)의 상한은 그대로 있고, 다만 그 앞에서 요청을 걸러 주던 장치가 없어졌을 뿐이다. 그러니 명시적으로 다시 넣어야 한다.

8-3. 빠른 실패가 느린 전멸로 바뀐다

한 줄 원리 — 물리 자원 산정은 어느 모델에서도 면제되지 않는다

가상 스레드는 "기다리는 주체"를 싸게 만들 뿐, "기다리는 대상"의 개수를 늘리지 않는다

가상 스레드를 1만 개 띄워도 Hikari 커넥션 10개는 10개다. Little's law는 자원별로 성립하므로(25-thread-pool-connection-pool-sizing.md 1-3) 스레드 계산식만 무의미해지고 커넥션 계산식은 그대로 남는다.

안티패턴 커넥션을 쥔 채 외부 API를 기다린다 — 가상 스레드가 이 결함을 40배로 증폭시킨다
@Transactional
public Order place(Long id) {
    Order o = orderRepository.save(...);   // 여기서 커넥션을 잡는다 — 커밋까지가 점유 구간
    paymentClient.charge(o);               // 외부 API 300ms — 커넥션을 쥔 채로 기다린다
    return o;                              // 커밋 시점에 커넥션 반환
}
즉시 대응 스레드풀이 암묵적으로 하던 유입 제어를 명시적으로 복원한다
// 커넥션을 쥐는 구간 자체를 세마포어로 제한한다 — 풀 크기에 맞춘 문지기
private final Semaphore dbGate = new Semaphore(10);

public Order place(Long id) {
    if (!dbGate.tryAcquire(200, TimeUnit.MILLISECONDS)) {문지기 복원
        // 200ms 안에 자리를 못 잡으면 즉시 거절한다.
        // 30초를 기다리다 죽는 것보다, 지금 429/503 을 주는 편이 호출자에게도 낫다.
        throw new TooManyRequestsException();
    }
    try { return orderService.placeInTx(id); }
    finally { dbGate.release(); }
}

대응은 두 층이고, 마지막 문장이 답의 핵심이다

즉시 대응 (증상 처리)

  • 세마포어 또는 Resilience4j Bulkhead·RateLimiter로 문지기 복원
  • Hikari connection-timeout을 30초 → 1~2초로 낮춰 빠른 실패를 되살린다(26-hikaricp-connection-pool-exhaustion.md 3-3)

근본 대응

  • 트랜잭션 밖으로 외부 API 호출을 뺀다(22-external-api-call-inside-transaction.md)
  • 올바른 설계는 가상 스레드가 있든 없든 동일하다
가상 스레드가 장애를 만든 것이 아니라, 원래 있던 설계 결함의 안전 마진을 걷어낸 것이다

9. 그래서 WebFlux에 남는 자리 · 도입 판단

가상 스레드가 나온 뒤 WebFlux의 위치를 정직하게 정리하면 이렇다. 일반적인 요청/응답 워크로드에서는 근거가 상당 부분 약해졌다 — 홉이 하나뿐이라 3-2의 블로킹 백프레셔로 충분하고, 동시 연결 문제는 가상 스레드가 훨씬 싼 값에 해결해 준다. 남는 자리는 둘이다.

9-1. ① 수요 신호를 상류로 전파해야 하는 스트리밍

SSE, WebSocket, chunked 응답, 메시지 소비처럼 오래 사는 스트림이다. 블로킹으로도 자연 백프레셔는 걸리지만, 선택지가 "막히거나 터지거나" 둘뿐이라 drop·buffer·sample 같은 중간 전략(3-3)을 표현할 방법이 없다.

한계 가상 스레드 + 블로킹 — 생산 10,000/s, 소비(브라우저) 100/s
Thread.ofVirtual().start(() -> {
    for (Event e : eventSource) emitter.send(e);
    // send 가 막히면 이 가상 스레드는 얌전히 멈춘다. 여기까진 백프레셔가 작동한 것이다.
    // 문제는 그 사이 eventSource 뒤에 이벤트가 쌓인다는 것이고,표현할 자리가 없다
    // "쌓지 말고 버려라" 나 "100ms 마다 최신값만" 을 표현할 자리가 없다.
});

9-2. ② 유휴 연결이 극단적으로 많은 경우

가상 스레드는 싸지만 공짜는 아니다. 스택이 힙에 상주하므로 연결당 수 KB가 든다. 100만 유휴 연결급에서는 이벤트 루프 몇 개 + 연결당 작은 상태 객체가 여전히 메모리로 이긴다. 푸시 알림 게이트웨이, 대규모 SSE 팬아웃이 여기 해당한다.

10. 인출 카드 · 꼬리질문 셀프 테스트

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

두 모델의 한 줄 차이는?
대기를 스레드 개수로 흡수(MVC, 상한 200) vs 이벤트 통지로 흡수(WebFlux, 스레드 ≈ 코어 수).
"스레드를 반납한다"의 정확한 뜻은?
스택을 비우고 돌아온다. CPU를 놓아준 것과 스레드를 놓아준 것은 다른 이야기다.
논블로킹만으로 되는가?
안 된다. EAGAIN 폴링으로 CPU 100%. 반드시 I/O 다중화(epoll/kqueue)가 짝으로 필요하다.
요청 100개 × DB 50ms면?
대기 50ms는 동일. 묶이는 스레드가 100개 대 4개. 응답시간은 안 빨라진다.
50ms 블로킹 감당량 3종은?
80 / 800 / 4,000 TPS — 이벤트 루프 4개 · boundedElastic 40개 · 톰캣 200개.
이벤트 루프 1개가 막히면?
Netty는 채널을 루프에 고정 배정 → 다른 루프가 대신 안 해준다. 그 루프 담당 연결 전면 정지.
DB 대기 스레드의 상태는?
BLOCKED가 아니라 RUNNABLE. BLOCKED는 synchronized 락 경쟁만 뜻한다.
백프레셔가 MVC엔 없나?
있다 — TCP 수신 윈도 · 유한 큐 · CallerRunsPolicy · 스레드풀 · 커넥션 풀. 이름이 다를 뿐.
Reactive Streams만의 것은?
홉을 건너 전파되는 request(n)과 drop/buffer/sample 정책 선택지.
가상 스레드가 없앤 것은?
백프레셔가 아니라 유입 제어. 동시 요청 상한 200 → 8,192 (40배).
그 결과 실패 양상은?
빠른 실패 → 느린 전멸. 8,192 : 10 경쟁 후 connection-timeout 30초 채우고 전면 실패.
WebFlux에 남는 자리는?
① request(n) 전파가 필요한 스트리밍 ② 유휴 연결 100만 개급. 그 외엔 가상 스레드.

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

이벤트 루프 스레드가 하나 블로킹되면 정확히 무슨 일이 벌어지나요? 필수힌트: "느려진다"가 아니라 "정지한다"로 답하고, 그 이유를 Netty의 배정 구조로 설명한 뒤 숫자를 붙인다

그 루프에 배정된 모든 채널(연결)의 이벤트 처리가 멈춘다.

이유를 구조로 답한다. Netty는 채널 하나를 이벤트 루프 하나에 고정 배정하고, 그 배정은 연결이 닫힐 때까지 바뀌지 않는다. 그래서 다른 루프가 대신 처리해 주지 않는다 — "전체의 1/N이 느려진다"가 아니라 "그 루프가 담당하는 연결들의 전면 정지"다.

숫자를 붙이면 강해진다. 4코어면 루프가 4개이고, 50ms 블로킹 호출을 감당하는 능력은 4 ÷ 0.05 = 80 TPS다. 톰캣 200스레드의 4,000 TPS와 50배 차이다. 그 이상이 들어오면 루프 4개가 전부 잠기고 서버가 어떤 요청도 받지 못한다 — 헬스체크까지 포함해서.

WebFlux를 쓰면 성능이 좋아지나요? 함정힌트: 먼저 부정하고 시작한다. 그다음 진짜 좋아지는 축을 지목하고, 판단 기준 한 줄로 닫는다

단일 요청의 응답시간은 빨라지지 않는다. DB 50ms는 어느 모델에서든 50ms다(2-3의 타임라인). 이걸 먼저 못 박는 것이 중요하다.

좋아지는 것은 같은 하드웨어로 감당하는 동시 연결 수와 자원 효율이다. 요청 100개가 각각 50ms를 기다릴 때, MVC는 스레드 100개를 묶어 두고 WebFlux는 4개로 처리한다.

그래서 판단 기준이 나온다 — "처리량 병목이 스레드인가." 대부분의 사내 API는 병목이 DB이거나 외부 API이지 스레드가 아니다. 그런 경우 WebFlux로 바꿔도 처리량이 그대로이거나 오히려 떨어진다 — 병목은 그대로인데 5-2의 비용만 추가되기 때문이다.

MVC를 쓰면서 WebClient만 쓰는 건 어떤가요? 필수힌트: "가능하다"로 시작하되, block() 한 줄에서 무슨 일이 일어나는지를 인지하고 있음을 보여야 한다

가능하고 실제로 흔한 절충이다. 외부 API를 여러 개 병렬로 호출하는 구간만 논블로킹으로 얻고, 나머지는 서블릿 모델을 유지한다.

// 외부 3곳을 병렬 호출 — 순차면 300ms, 병렬이면 가장 느린 하나(120ms)로 끝난다
Mono<A> a = webClient.get()...retrieve().bodyToMono(A.class);   // 100ms
Mono<B> b = webClient.get()...retrieve().bodyToMono(B.class);   // 120ms
Mono<C> c = webClient.get()...retrieve().bodyToMono(C.class);   //  80ms

Result r = Mono.zip(a, b, c).map(this::merge).block();여기서 톰캣 스레드가 다시 묶인다

block() 하는 순간 그 스레드는 여전히 묶인다는 것을 인지하고 쓰는지가 이 답의 변별점이다. 다만 "묶인 시간"이 300ms에서 120ms로 줄었으므로 Little's law 상 이득은 명확하다. 논블로킹의 이득은 "스레드가 안 묶인다"가 아니라 "묶이는 시간이 짧아진다"에서 온다. 클라이언트 3종 비교는 18-resttemplate-webclient-restclient.md.

@Transactional이 WebFlux에서 동작하나요? 필수힌트: "안 된다"로 끝내지 말고, 무엇이 어디에 묶여 있어서 성립하지 않는지를 지목한다

동작하지 않는다. 이유를 구조로 답해야 한다.

Spring의 트랜잭션 동기화는 커넥션을 TransactionSynchronizationManager의 ThreadLocal에 묶어 같은 스레드의 후속 DB 접근이 그 커넥션을 재사용하게 만드는 구조다(24-transaction-synchronization-connection-binding.md). 리액티브 체인은 단계마다 실행 스레드가 바뀔 수 있으므로 "같은 스레드"라는 연결고리 자체가 성립하지 않는다.

대안은 R2DBC + Reactor Context 기반의 리액티브 트랜잭션 관리다. ThreadLocal 대신 구독마다 따라다니는 Reactor Context에 트랜잭션 자원을 담는다. @Transactional을 리액티브 리포지토리와 함께 쓰면 Spring이 ReactiveTransactionManager를 통해 처리하지만, JDBC 리포지토리에 붙인 @Transactional은 리액티브 체인 안에서 그냥 안 먹는다. 같은 이유로 MDC와 SecurityContextHolder도 재작업 대상이다.

백프레셔가 MVC엔 정말 없나요? 시니어 변별힌트: "없다"가 아니라 "이름이 다르다"로 시작하고, 없는 것 둘을 정확히 지목한다

있다. TCP 수신 윈도, 유한 큐, CallerRunsPolicy, 스레드풀 크기, 커넥션 풀 크기 형태의 암묵적 백프레셔가 이미 곳곳에서 작동한다(3-2). 백프레셔는 프레임워크 기능이 아니라 유한한 자원을 다루는 시스템의 일반 원리다.

없는 것은 둘이다.

  • 홉을 건너 전파되는 명시적 수요 신호(request(n)). 블로킹 세계의 백프레셔는 각 홉에서 국소적으로 막힐 뿐 서로를 모른다.
  • drop / buffer / sample 같은 정책 선택지. 블로킹에서는 "막히거나 터지거나"가 사실상 전부이고, 중간 전략을 쓰려면 큐와 정책 코드를 직접 짜야 한다.

"없다"가 아니라 "이름이 다르고, 전파 범위와 정책 선택지가 다르다"로 답하면 이 질문은 통과다.

가상 스레드를 켰더니 오히려 장애가 늘었습니다. 왜죠? 시니어 변별힌트: 숫자 두 개(200 → 8,192)와 표현 한 줄("빠른 실패 → 느린 전멸")로 압축한다

스레드풀이 암묵적으로 하던 유입 제어가 사라졌기 때문이다(8-2).

경로를 숫자로 설명한다. 동시 요청 상한이 max-threads 200에서 max-connections 8,192로 40배가 되면서, 예전에는 문 앞에서 거절되던 요청이 전부 진입한다. 그런데 Hikari 커넥션 10개는 그대로다. 8,192개가 10개를 두고 경쟁하다 connection-timeout 기본값 30초를 채우고 전면 타임아웃된다.

빠른 실패가 느린 전멸로 바뀐 것이고, 이 표현으로 요약하면 좋다. 대응은 두 층이다.

  • 즉시 대응: 세마포어나 Resilience4j Bulkhead로 문지기를 명시적으로 복원하고, connection-timeout을 1~2초로 낮춰 빠른 실패를 되살린다.
  • 근본 대응: 트랜잭션 안의 외부 호출을 밖으로 뺀다.

마지막 문장이 이 답의 핵심이다 — 가상 스레드가 장애를 만든 것이 아니라, 원래 있던 설계 결함의 안전 마진을 걷어낸 것이다. 올바른 설계는 가상 스레드가 있든 없든 같다.

어떤 기준으로 도입을 판단하시겠어요? 필수힌트: 관문 넷을 순서대로 대되, ④를 먼저 언급하는 것이 지금 기준이다

넷을 전부 통과해야 도입한다는 식으로 답한다(9-3의 도식).

  1. 동시 연결이 실제로 스레드 한계에 부딪히고 있는가? — tomcat.threads.busy가 max에 붙는지 메트릭으로 확인. 근거 없이 시작하지 않는다.
  2. 전 의존성이 논블로킹으로 갈 수 있는가? — DB 드라이버(R2DBC), HTTP 클라이언트, 로깅, 서드파티 SDK까지 전수 조사. 하나라도 블로킹이면 4개 스레드 중 하나가 잠긴다.
  3. 팀이 리액티브 디버깅을 감당하는가? — 끊긴 스택트레이스, ThreadLocal 재작업(MDC/Security/트랜잭션).
  4. 가상 스레드로 충분하지 않은가? — 스트리밍 백프레셔나 극단적 유휴 연결 요건이 있는가. 없다면 가상 스레드가 같은 이득을 훨씬 싸게 준다.

④를 먼저 묻는 것이 요즘 기준의 시니어다. 2019년의 정답과 지금의 정답이 다르고, 그 변화의 이유(가상 스레드가 "블로킹 코드 그대로" 동시성을 준다)를 설명할 수 있어야 한다.

R2DBC로 바꾸면 다 해결되나요? 가산점힌트: 해결되는 것 하나와 남는 것 하나를 나눈 뒤, 생태계 비용을 덧붙인다

이벤트 루프 블로킹 문제는 해결되지만 커넥션 풀 문제는 그대로 남는다.

R2DBC도 커넥션 풀(ConnectionPool)을 쓰고, DB 쪽 커넥션은 여전히 물리 자원이다. 8-3의 한 줄 원리가 여기서도 그대로다 — 논블로킹은 기다리는 주체를 싸게 만들 뿐, 기다리는 대상의 개수를 늘리지 않는다. 커넥션 10개짜리 풀은 R2DBC에서도 10개이고, Little's law 산정은 그대로 필요하다.

그리고 생태계 비용을 짚으면 좋다. R2DBC를 쓰면 JPA/Hibernate를 쓸 수 없다 — JPA 명세 자체가 블로킹 API로 정의돼 있기 때문이다. 지연 로딩, 영속성 컨텍스트, 더티 체킹을 전부 포기하고 Spring Data R2DBC의 얇은 매핑으로 가야 한다. "WebFlux 도입"이 실제로는 "데이터 접근 계층 전면 재작성"인 경우가 많다는 사실이 5-2의 비용 항목에서 가장 크게 물리는 부분이다.

블로킹 코드를 boundedElastic으로 감싸면 해결된 것 아닌가요? 함정힌트: "이벤트 루프는 지켰다"를 인정한 뒤, 그 구간이 무엇으로 회귀했는지와 숫자를 댄다

이벤트 루프를 지키는 데는 성공한다. 하지만 그 구간은 결국 thread-per-request로 회귀한 것이고, 그 풀이 톰캣 기본값보다 작다.

숫자로 답한다 — boundedElastic의 기본 상한은 가용 코어 수 × 10(4코어면 40개)이므로 50ms 블로킹 감당량이 40 ÷ 0.05 = 800 TPS다. 톰캣 200스레드의 4,000 TPS보다 5배 좁다. 그리고 회귀했으므로 풀 크기 산정 문제(Little's law)가 그대로 되살아난다 — 800 TPS를 넘기려면 풀 크기를 조정해야 하는데, 그 순간 "우리는 왜 WebFlux를 쓰고 있는가"라는 질문이 돌아온다.

그래서 판단 기준은 "이 우회가 몇 군데에 쓰이는가"다. 전체 엔드포인트의 소수(레거시 한두 개)라면 합리적인 절충이지만, 이 우회가 코드의 주류가 되면 WebFlux를 쓸 이유가 남지 않는다. 덧붙여 publishOn이 아니라 subscribeOn이어야 한다는 것도 짚으면 좋다 — publishOn은 그 지점 이후 단계의 스레드만 바꾸므로 소스 자체가 이벤트 루프에서 실행되는 것을 막지 못한다.

숨은 블로킹은 어떻게 찾나요? 가산점힌트: 도구 이름 하나와, 그 도구를 어느 단계에서 켜는지까지

BlockHound를 쓴다. JVM 에이전트로 붙어서 논블로킹으로 지정된 스레드(이벤트 루프)에서 블로킹 호출이 일어나면 BlockingOperationError를 던진다.

필요한 이유는 블로킹이 눈에 잘 안 띄기 때문이다. JDBC처럼 명백한 것만이 아니라 동기 HTTP 클라이언트(RestTemplate), 파일 I/O, 동기 로깅 어펜더(디스크가 느려지면 로그 한 줄이 루프를 막는다), 서드파티 내부의 synchronized·Thread.sleep, 무심코 부른 Mono.block()까지 있다. 전부 컴파일도 되고 기능 테스트도 통과하고 부하가 걸려야 드러난다.

켜는 자리가 중요하다 — 테스트 단계다. 운영에서 켜면 블로킹이 발견될 때마다 에러가 나므로 오히려 위험하다. CI에서 통합 테스트를 BlockHound와 함께 돌려 "이번 커밋에서 블로킹이 들어왔는지"를 자동으로 막는 것이 제대로 된 사용법이다.

CPU 바운드 작업이 많은 서비스에 WebFlux를 쓰면 어떻게 되나요? 함정힌트: 이벤트 루프의 이점이 무엇이었는지로 되돌아가면 답이 나온다

이득이 0인데 위험만 도입하는 선택이다. 이벤트 루프의 이점은 "기다리는 시간을 다른 일에 쓴다"는 것인데, 이미지 리사이징·암호화·대량 집계 같은 CPU 바운드 작업에는 반납할 대기가 없다.

피해는 4-1과 정확히 같다. 이벤트 루프가 연산에 잡혀 있는 동안 그 루프에 배정된 모든 연결이 지연된다 — 블로킹 I/O가 아니라 계산이 루프를 막는다는 점만 다르다.

그리고 근본적으로 CPU 바운드는 모델과 무관하게 코어 수가 상한이다. 4코어는 초당 4,000ms의 CPU 시간을 제공하고, 그 이상은 어떤 스레딩 모델로도 만들어낼 수 없다(25-thread-pool-connection-pool-sizing.md 2-3). 굳이 리액티브 스택에서 처리해야 한다면 별도 워커 풀로 격리해야 하고, 그러면 6절의 대가 논의로 되돌아간다.

이벤트 루프 스레드 수를 4개 말고 200개로 늘리면 되지 않나요? 함정힌트: 그렇게 하면 무엇이 되는지를 이름으로 답한다

늘릴 수는 있다(reactor.netty.ioWorkerCount). 하지만 그렇게 하는 순간 이 아키텍처는 사실상 thread-per-request로 되돌아간다 — 대기를 다시 스레드 개수로 사기 시작한 것이고, 이벤트 루프 모델을 택한 이유(코어 수만큼의 스레드로 수만 연결)를 스스로 버린 것이다.

게다가 이벤트 루프는 "CPU를 쉬지 않고 쓰는 스레드"를 전제로 설계된 것이라 코어 수를 크게 넘겨 띄우면 컨텍스트 스위칭 비용만 늘고, 논블로킹 구간에서는 얻는 처리량이 없다(대기가 없으므로 스레드를 늘려도 병렬성이 늘지 않는다).

정리하면 "블로킹이 있으니 루프를 늘리자"는 진단이 잘못된 것이다. 선택지는 둘뿐이다 — 그 블로킹을 없애거나(R2DBC·논블로킹 클라이언트), 격리하거나(6절 boundedElastic). 격리가 주류가 되면 MVC(또는 가상 스레드)로 돌아가는 것이 정답이다.

그럼 가상 스레드를 켜면 max-threads는 이제 신경 안 써도 되나요? 시니어 변별힌트: 무의미해진 계산식과 그대로 남는 계산식을 나눈다

max-threads 계산식만 무의미해지고, 나머지 산정은 전부 그대로 남는다.

Little's law는 자원별로 성립한다. 가상 스레드가 싸게 만든 것은 "기다리는 주체"뿐이고, "기다리는 대상"인 DB 커넥션·파일 디스크립터·외부 API rate limit은 물리적으로 고정돼 있다. 가상 스레드를 1만 개 띄워도 Hikari 커넥션 10개는 10개다.

오히려 새로 신경 쓸 것이 생긴다. 첫째, 실질 상한이 max-connections 8,192로 옮겨갔다는 것. 둘째, 플래그가 시스템의 절반만 바꾼다는 것이다 — 톰캣 요청 스레드와 @Async·@Scheduled의 기본 executor는 바뀌지만, 직접 등록한 ExecutorService 빈, HikariCP 풀 크기, parallelStream의 공용 ForkJoinPool은 그대로다. 절반만 바뀌면 나머지 절반이 병목이 된다.

스트리밍이 아니라면 정말 WebFlux를 쓸 이유가 없나요? 시니어 변별힌트: "없다"로 단정하지 말고, 남는 두 자리를 정확히 대고 그 경계 조건을 말한다

일반적인 요청/응답 워크로드에서는 근거가 상당 부분 약해졌다는 것이 정직한 답이다. 홉이 하나뿐이라 3-2의 블로킹 백프레셔로 충분하고, 동시 연결 문제는 가상 스레드가 훨씬 싼 값에 해결한다.

남는 자리는 둘이다.

  • 수요 신호를 상류로 전파해야 하는 스트리밍 — SSE, WebSocket, chunked 응답, 메시지 소비 같은 오래 사는 스트림. 블로킹으로도 자연 백프레셔는 걸리지만 선택지가 "막히거나 터지거나" 둘뿐이라 onBackpressureDrop·sample 같은 중간 전략을 표현할 자리가 없다.
  • 유휴 연결이 극단적으로 많은 경우 — 가상 스레드는 싸지만 스택이 힙에 상주해 연결당 수 KB가 든다. 100만 유휴 연결급에서는 이벤트 루프 몇 개 + 작은 상태 객체가 메모리로 이긴다. 푸시 알림 게이트웨이, 대규모 SSE 팬아웃이 여기다.

그리고 이미 WebFlux로 돌고 있는 시스템을 되돌리라는 뜻은 아니다. 전 구간 논블로킹이 이미 갖춰져 있고 팀이 감당하고 있다면 그 자체로 잘 도는 선택지다. 이 논의는 "새로 시작할 때 무엇을 기본값으로 두는가"에 대한 것이다.

한 줄 요약
MVC는 요청당 스레드 하나가 응답까지 묶여 대기를 "스레드 개수"로 흡수하고(상한 = 풀 크기 200), WebFlux는 코어 수만큼의 이벤트 루프가 커널의 epoll에 "이 소켓에 데이터가 오면 알려달라"를 등록해 두고 스레드를 반납해 대기를 "이벤트 통지"로 흡수한다(요청 100개 × DB 50ms에서 묶이는 스레드가 100개 대 4개) — 대신 전 구간 논블로킹이 전제라 이벤트 루프 위 블로킹 한 번의 폭발 반경이 질적으로 다르며, 50ms 블로킹 감당량이 톰캣 200스레드는 4,000 TPS인데 이벤트 루프 4개는 80 TPS로 50배 차이라 JDBC 한 줄이 서버를 세운다. 우회로인 boundedElastic(코어×10)조차 800 TPS라 MVC보다 5배 좁으니 우회가 주류가 되면 WebFlux를 쓸 이유가 없고, 여기에 리액티브 학습 곡선·끊긴 스택트레이스·ThreadLocal(MDC·Security·@Transactional) 전면 재작업 비용이 얹힌다. Java 21 가상 스레드는 코드를 블로킹 스타일로 둔 채 런타임이 대기 시 캐리어를 반납해 같은 이득을 훨씬 싸게 주므로 "동시 연결 때문에 WebFlux"라는 근거를 대부분 무너뜨렸고, 남는 자리는 request(n)으로 수요를 상류에 전파해야 하는 스트리밍과 유휴 연결 100만 개급 워크로드뿐이다 — 단 가상 스레드는 스레드풀이 암묵적으로 하던 유입 제어를 없애(200 → max-connections 8,192, 40배) 커넥션 풀 앞의 빠른 실패를 느린 전멸로 바꾸므로, 세마포어·Bulkhead와 짧은 connection-timeout으로 문지기를 명시 복원해야 한다(물리 자원 산정은 어느 모델에서도 면제되지 않는다).
