Spring Boot Auto Configuration
"알아서 해주는 마법"의 실체는 조건부 빈 등록

면접 질문: "Spring Boot의 Auto Configuration은 어떻게 동작하나요?"

핵심 관전 포인트 — 여기서 자동화되는 "설정"은 application.yml이 아니라 빈을 만들어 컨테이너에 등록하는 자바 코드(@Configuration + @Bean)다. @SpringBootApplication 안의 @EnableAutoConfiguration이 시작점이고, 부트는 클래스패스의 각 jar에 들어 있는 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 파일에서 자동 구성 후보 클래스 목록을 읽은 뒤, 후보마다 @ConditionalOnClass(클래스패스에 있나) · @ConditionalOnMissingBean(사용자가 직접 등록 안 했나) 같은 조건을 평가해 통과한 것만 빈 정의로 등록한다. 이 조건 평가는 런타임이 아니라 빈 정의를 등록하는 단계에서 일어나고, 자동 구성은 DeferredImportSelector라서 사용자 설정이 전부 처리된 뒤에 맨 마지막으로 평가된다 — 내가 만든 DataSource 빈이 부트의 기본 DataSource를 이기는 메커니즘은 이 "순서"가 전부다. 마법이 아니라 "조건 붙은 @Configuration의 대량 자동 import"이며, 안 먹을 때는 --debug의 CONDITIONS EVALUATION REPORT에서 탈락 사유를 읽는 것이 추적의 정석이다.
  • 1
    자동화 대상은 yml이 아니라 "빈 조립 코드"다 — @SpringBootApplication 안의 @EnableAutoConfiguration이 시작점이고, 부트는 클래스패스의 모든 jar에서 AutoConfiguration.imports 파일을 긁어 자동 구성 후보 목록(부트 3.5 기준 약 156개)을 만든다. spring.datasource.url 같은 값은 여전히 내가 쓰고, 부트는 그 값을 읽어 DataSource를 만드는 코드를 대신 실행한다.
  • 2
    후보 전부가 적용되는 게 아니라 "조건 평가"를 통과한 것만 남는다 — @ConditionalOnClass(그 jar가 있나) · @ConditionalOnMissingBean(사용자가 이미 만들었나) · @ConditionalOnProperty(그 값이 켜져 있나)가 문지기다. 평가는 런타임이 아니라 빈 정의(설계도)를 등록하는 단계에서 끝나고, 웹+JPA 정도면 통과는 대개 20~30개다.
  • 3
    "내 빈이 이긴다"의 정체는 우선순위가 아니라 순서다 — 자동 구성은 DeferredImportSelector라 사용자 설정이 전부 처리된 뒤 맨 마지막에 평가된다. 그래서 내 DataSource 빈 정의가 이미 등록돼 있고, 자동 구성은 그걸 보고 스스로 물러난다(back-off) — 둘 만들어졌다 하나가 이기는 게 아니라 애초에 하나만 만들어진다. 안 먹을 땐 --debug의 Did not match 사유를 읽는다.

0. 질문 + 출제 의도

질문: "Spring Boot의 Auto Configuration은 어떻게 동작하나요?"

출제 의도: "스프링부트가 알아서 해줬는데 왜 안 되지"라는 상황 — 빈 충돌, 의존성 추가만으로 바뀐 동작 — 에서 원인을 추적하려면 자동 설정의 조건부 로딩을 이해해야 한다. 마법을 마법으로 두는 사람은 이 유형의 문제에서 항상 막히므로, 프레임워크의 동작을 원리로 이해하는지를 확인하는 질문이다.

이 페이지가 겨냥하는 약점 세 가지 ① "설정"을 yml로 오해하는 것 → 1절에서 설정값(properties) vs 설정 클래스(configuration)를 분리해, 자동화되는 쪽이 빈 조립 코드임을 먼저 못 박는다.
② "조건 보고 등록한다"에서 멈추는 것 → 6·7절에서 평가 시점(빈 정의 등록 단계)과 평가 순서(자동 구성이 맨 마지막)를 도식으로 분리한다. back-off가 성립하는 이유는 순서 하나다.
③ 안 먹을 때 추적 수단이 없는 것 → 8절에서 CONDITIONS EVALUATION REPORT의 4덩어리를 원인 3종에 매핑하고, Did not match 줄에서 범인 빈 이름을 뽑는 법까지 다룬다.
한 문장 비유 — 이사 온 집의 가전 설치 기사 @ComponentScan은 내 집 안 물건 정리다. 내가 사 온 물건(@Service, @Repository)을 제자리에 놓는 일이라 대상이 전부 내 것이다.  /  자동 구성은 가전 설치 기사다. 내가 세탁기(의존성)를 들여놓으면 기사가 와서 수도와 배수를 연결해 준다. 단 기사는 조건을 본다 — 세탁기가 실제로 배달돼 있는지(@ConditionalOnClass), 내가 이미 직접 배관을 연결해 뒀는지(@ConditionalOnMissingBean)를 확인하고, 이미 해뒀으면 손대지 않고 물러난다.

1. 오해부터 걷어내자 — 여기서 "설정"은 yml이 아니다

"자동 설정(auto configuration)"이라는 이름 때문에 가장 흔하게 생기는 오해가 application.yml을 채우는 일을 부트가 대신해 준다는 것이다. 이 오해를 안고 읽으면 뒤에 나오는 조건 평가나 back-off가 전부 엉뚱하게 들리므로 여기서부터 바로잡고 시작한다.

스프링 세계에서 "설정(configuration)"이라는 단어는 완전히 다른 두 가지를 가리킨다. 이 둘을 구분하는 것이 이 질문 전체의 출발점이다.

부르는 말실체파일 예자동 구성의 대상인가
설정값(properties)문자열·숫자 같은 값application.yml, 환경변수아니다 — 내가 직접 쓴다
설정 클래스(configuration)빈을 만들어 등록하는 자바 코드@Configuration + @Bean이것이 자동화된다

1-1. 부트 이전에는 이 조립 코드를 사람이 직접 썼다

왜 이런 게 필요했는지는 부트 이전 코드를 보면 바로 납득된다. 값(URL·계정)만 다르고 조립 절차는 프로젝트마다 늘 같았다.

before 부트 없던 시절 — 프로젝트마다 직접 쓰던 조립 코드
@Configuration
public class MyDbConfig {

    @Bean
    public DataSource dataSource() {프로젝트가 100개면 100번 똑같이
        // 구현체를 고르고 · 접속 정보를 넣고 · 빈으로 등록한다
        // 이 세 가지가 "설정 클래스"가 하는 일 전부다.
        HikariDataSource ds = new HikariDataSource();
        ds.setJdbcUrl("jdbc:postgresql://localhost:5432/order");
        ds.setUsername("order_app");
        return ds;
    }

    @Bean
    public JdbcTemplate jdbcTemplate(DataSource ds) {
        // DataSource 빈이 있어야만 만들 수 있다
        // — 조립에는 순서와 의존이 있다.
        return new JdbcTemplate(ds);
    }
}
after 부트를 쓰면 위 클래스가 통째로 사라진다

//
// application.yml
//   spring.datasource.url: jdbc:postgresql://.../order

// 그리고 이렇게 바로 주입받아 쓴다.
@Service
public class OrderQuery {

    private final JdbcTemplate jdbc;내가 만든 적 없는 빈인데 주입된다

    public OrderQuery(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }
}

1-2. 대표적으로 무엇이 자동 구성되나

공통 패턴: "의존성(jar)을 추가했다 = 그걸 쓰겠다는 의사표시"로 간주하고, 그 라이브러리를 쓰는 데 필요한 기반 빈들을 프로퍼티 값을 반영해 만들어 준다.
의존성을 추가하면자동으로 생기는 빈
spring-boot-starter-web내장 톰캣, DispatcherServlet, JSON 변환기(MappingJackson2HttpMessageConverter)
spring-boot-starter-data-jpaDataSource(HikariCP 커넥션 풀), EntityManagerFactory, TransactionManager
spring-boot-starter-security시큐리티 필터 체인 — 의존성만 넣어도 모든 요청에 인증이 걸리는 이유
jackson (web에 포함)ObjectMapper
spring-boot-starter-data-redisRedisConnectionFactory, RedisTemplate
spring-boot-starter-amqpConnectionFactory, RabbitTemplate, RabbitAdmin

세 번째 줄이 이 성질을 가장 극적으로 보여준다

build.gradle에 시큐리티 한 줄을 추가했을 뿐인데 모든 엔드포인트가 로그인 화면으로 리다이렉트된다. 코드 어디에도 그런 지시는 없다. 의존성 추가가 곧 설정 변경이라는 사실을 몸으로 알려주는 사례이고, 이것이 뒤(11절)에서 다룰 "암묵성이라는 비용"의 원형이다.

2. 전체 그림 — 모으고 · 거르고 · 등록한다

세부로 들어가기 전에 전체 파이프라인을 한 장으로 잡아 두자. 자동 구성이 하는 일은 결국 세 단계뿐이고, 나머지 절은 전부 이 세 단계의 확대다.

암기 장치 — 자동 구성 3단계는 "모 · 거 · 등"

모은다(imports 파일에서 후보 156개) → 거른다(@Conditional 조건 평가) → 등록한다(통과한 20~30개를 빈 정의로)

면접에서 "어떻게 동작하나요"를 들으면 이 세 글자부터 뱉고 각 단계를 확대해 나가면 된다. 그리고 세 단계 전부가 "빈 정의 등록 단계" 안에서 끝난다는 것과, 이 파이프라인이 사용자 설정 처리 뒤에 실행된다는 것 두 가지를 덧붙이면 답의 뼈대가 완성된다.

3. 시작점 — @SpringBootApplication을 펼쳐 보면

@SpringBootApplication
// = 아래 세 개를 합친 것
// @SpringBootConfiguration    → 이 클래스 자체가 설정 클래스
// @ComponentScan              → 내 패키지 하위의 @Component 들을 스캔
// @EnableAutoConfiguration    → ★ 자동 구성의 시작점
public class MyApplication { ... }

역할 분담이 핵심이다. @ComponentScan은 내가 짠 코드를 빈으로 등록하고, @EnableAutoConfiguration은 내가 안 짠 코드 — 라이브러리 쪽에서 미리 만들어 둔 설정 클래스들 — 을 조건에 맞춰 등록한다.

4. 후보 목록은 어디서 오나 — imports 파일

AutoConfigurationImportSelector는 클래스패스의 모든 jar를 뒤져 다음 경로의 파일을 전부 읽어 합친다.

META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

# 파일 내용: 자동 구성 클래스의 FQCN(패키지까지 포함한 전체 이름)이 한 줄에 하나씩
org.springframework.boot.autoconfigure.admin.SpringApplicationAdminJmxAutoConfiguration
org.springframework.boot.autoconfigure.amqp.RabbitAutoConfiguration
org.springframework.boot.autoconfigure.aop.AopAutoConfiguration
org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
...

파일명이 저렇게 긴 이유는 규칙이 META-INF/spring/{애너테이션 FQCN}.imports이기 때문이다. @AutoConfiguration 애너테이션의 전체 이름이 org.springframework.boot.autoconfigure.AutoConfiguration이라 그대로 파일명이 됐다. 외울 필요는 없지만 "왜 이렇게 긴가"를 알면 오타를 덜 낸다.

5. 조건 평가 — @Conditional 계열이 문지기다

각 자동 구성 클래스에는 "이 조건일 때만 활성화"라는 문지기 애너테이션이 붙어 있다. 클럽 입구에서 신분증을 확인하고 통과 여부를 판정하는 사람처럼, 후보 하나하나에 질문을 던져 통과·탈락을 가른다.

암기 장치 — 조건 3종은 "클 · 빈 · 값"

@ConditionalOnClass
클래스패스를 본다
지정한 클래스가 클래스패스에 있을 때만 통과. "HikariCP jar가 있어야 커넥션 풀 설정을 하지"
@ConditionalOnMissingBean
빈 정의를 본다
같은 타입 빈이 아직 등록돼 있지 않을 때만 통과. 사용자 빈 우선의 핵심 장치다.
@ConditionalOnProperty
yml 값을 본다
지정한 프로퍼티가 특정 값일 때만 통과. yml로 자동 구성을 켜고 끄는 스위치다.

클래스패스에 있나 · 빈이 이미 있나 · 값이 켜져 있나 — 세 글자면 조건 평가의 실무 케이스 대부분이 설명된다.

5-1. 실제 DataSourceAutoConfiguration의 구조

@AutoConfiguration
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })① jdbc 관련 클래스가 있어야
public class DataSourceAutoConfiguration {

    @Configuration(proxyBeanMethods = false)
    @ConditionalOnMissingBean({ DataSource.class, XADataSource.class })② 사용자가 직접 안 만들었을 때만
    protected static class PooledDataSourceConfiguration {

        @Bean
        public DataSource dataSource(DataSourceProperties props) {
            // props 가 yml의 spring.datasource.* 값을 들고 온다
            // — 1절에서 말한 "입력값"이 여기로 들어온다.
            return props.initializeDataSourceBuilder().build();
        }
    }
}

이 두 조건의 합작이 부트의 사용 경험 전체를 설명한다.

① @ConditionalOnClass가 참이 되는 순간

spring-boot-starter-data-jpa를 추가하면 → DataSource·EntityManagerFactory·TransactionManager가 "알아서" 생긴다.

내가 한 일은 build.gradle 한 줄 추가뿐이다.

② @ConditionalOnMissingBean이 거짓이 되는 순간

내가 @Bean DataSource를 직접 등록하면 → 부트의 기본 DataSource는 조용히 물러난다(back-off).

같은 원리로 ObjectMapper, RestTemplateBuilder, TaskExecutor, RabbitTemplate도 전부 "의존성 추가 → 기본 빈 제공, 직접 정의 → 기본 빈 후퇴"로 동작한다.

사용자 설정이 항상 이긴다 그런데 "이긴다"는 표현부터가 부정확하다
@Configuration
public class MyDataSourceConfig {

    @Bean
    public DataSource dataSource() {이 빈 정의가 등록되는 순간
        // 자동 구성의 @ConditionalOnMissingBean 이 "이미 있다"고 판정해
        // 부트의 기본 DataSource 는 생성 자체가 안 된다.
        //
        // 두 개 생겼다가 하나가 이기는 게 아니라 → 애초에 하나만 만들어진다.
        return new HikariDataSource(myCustomConfig());
    }
}

정확한 표현으로 교정하기 — 면접 답변의 한 칸 차이

✗ "내 빈이 자동 구성 빈을 덮어쓴다 / 우선순위가 높다"
✓ "내 빈 정의가 먼저 등록돼 있어서, 나중에 온 자동 구성이 스스로 물러난다"

덮어쓰기라면 두 개가 만들어졌다가 하나가 지워지는 그림인데, 실제로는 부트 쪽 @Bean 메서드가 빈 정의로 등록되지도 않는다. 이 차이를 말할 수 있으면 다음 절(순서)로 자연스럽게 넘어간다.

6. 조건은 언제 평가되나 — 런타임이 아니라 "빈 정의 등록" 단계다

여기가 이 질문에서 가장 자주 흐려지는 지점이다. 결론부터 말하면 조건 평가는 애플리케이션이 요청을 받는 런타임의 일이 아니고, 심지어 빈 인스턴스가 하나도 만들어지기 전에 끝난다.

그래서 @ConditionalOnMissingBean을 내 @Configuration에 붙이면 안 된다 내 설정 클래스끼리는 처리 순서가 보장되지 않는다. 조건을 평가하는 시점에 상대 빈이 아직 등록 전일 수 있고, 그러면 결과가 실행할 때마다 달라질 수 있다. "여태까지 처리한 것만 볼 수 있다"는 성질은 순서가 보장된 자리에서만 안전하다 — 그 자리가 바로 자동 구성이다.

7. 순서가 메커니즘의 전부다 — 자동 구성은 맨 마지막에 처리된다

그러면 그 순서는 누가 보장하는가. AutoConfigurationImportSelector의 선언 한 줄에 답이 있다.

public class AutoConfigurationImportSelector implements DeferredImportSelector, ... { }
//                                                     ↑
//                                       "미뤄진(deferred) import 선택기"

스프링의 설정 클래스 파서는 일반 import를 전부 처리한 뒤, 맨 마지막에 이 종류의 선택기를 실행한다. 자동 구성이 이 인터페이스를 구현했다는 것은 곧 "내 설정을 다 처리한 다음에 오라"고 스스로 줄 맨 뒤에 선 것이다.

규칙 — 이 한 줄이 이 문서에서 가장 자주 인출된다

사용자 설정이 전부 먼저, 자동 구성은 언제나 맨 마지막 — 그래서 내 빈을 보고 물러날 수 있다

7-1. 이 순서를 이해하면 부수적인 사실들도 자동으로 설명된다

왜 @ConditionalOnMissingBean을 내 설정에 붙이면 안 되나

내 설정끼리는 처리 순서가 보장되지 않아서, 조건을 평가하는 시점에 상대 빈이 아직 등록 전일 수 있다. 결과가 실행할 때마다 달라질 수 있다는 뜻이다.

왜 자동 구성끼리는 @AutoConfigureAfter가 필요하나

자동 구성 A가 자동 구성 B의 빈 유무를 조건으로 본다면, A가 B보다 나중에 평가되도록 명시해야 판정이 성립한다. 예: JPA 자동 구성은 DataSource 빈을 조건으로 보므로 DataSourceAutoConfiguration 이후여야 한다.

8. 실무 — 자동 구성이 안 먹을 때 추적하는 법

출제 의도가 정확히 여기다. "부트가 알아서 해줬는데 왜 안 되지?" 상황에서 마법을 마법으로 두는 사람은 막히고, 조건 평가를 이해하는 사람은 추적한다.

암기 장치 — 안 먹는 원인 3종은 "조 · 충 · 제"

(1) 조건 불충족
필요한 클래스가 클래스패스에 없거나(의존성 누락), @ConditionalOnProperty가 보는 프로퍼티가 꺼져 있다. 4-1의 imports 파일 누락도 사실상 이 부류다.
(2) 충돌 / back-off
어딘가에서 같은 타입 빈을 이미 등록해 자동 구성이 물러났다. 특히 사내 공통 라이브러리가 몰래 등록한 빈 — 내 코드에는 흔적이 없어 코드만 읽어서는 절대 안 보인다.
(3) 제외(exclude)
누군가 exclude로 꺼 뒀다. 테스트 슬라이스 애너테이션이나 상속받은 부모 설정 클래스에 숨어 있을 수 있다.

셋을 구분하는 방법이 다행히 하나로 통일돼 있다 — 부트가 후보 하나하나의 판정 결과와 사유를 전부 기록해 두기 때문이다.

8-1. --debug — 리포트 4덩어리가 원인 3종에 그대로 대응한다

9. 반대로, 자동 구성을 일부러 끄는 법

추적의 반대편에는 "필요 없는 자동 구성을 끄는" 작업이 있다. 방법은 두 가지다.

방법 1 애너테이션 속성
// 컴파일 타임에 타입으로 지정하므로 오타가 잡힌다
@SpringBootApplication(exclude = DataSourceAutoConfiguration.class)
public class MyApplication { ... }
방법 2 프로퍼티
# 코드 수정 없이 환경별로 제어할 수 있다.
# 값이 FQCN 문자열이라 오타가 나면 기동 시
# "존재하지 않는 클래스" 에러로 알려준다.
spring:
  autoconfigure:
    exclude: org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration

문제는 언제 이게 필요하냐인데, 실무에서 마주치는 상황은 대체로 아래 네 가지다.

1
테스트에서 DB 없이 컨텍스트를 띄우고 싶을 때 — 가장 흔하다.

순수한 도메인 서비스 단위 테스트인데 spring-boot-starter-data-jpa가 클래스패스에 있다는 이유만으로 DataSourceAutoConfiguration이 켜지고, 접속 정보가 없으니 Failed to configure a DataSource로 컨텍스트 로딩이 실패한다.

before DB를 전혀 안 쓰는데 컨텍스트가 안 뜬다
@SpringBootTestDataSource가 없어서 로딩 실패
class OrderPolicyTest { ... }
after DB 계층 자동 구성만 걷어내고 띄운다
@SpringBootTest(properties =
   "spring.autoconfigure.exclude="
 + "org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration")
class OrderPolicyTest { ... }
다만 이런 상황이 잦다면 — 반대 방향의 접근이 낫다 exclude를 반복하기보다 @DataJpaTest·@WebMvcTest 같은 테스트 슬라이스를 쓴다. 슬라이스는 "필요한 자동 구성만 켠다"는 화이트리스트 방식이라, 블랙리스트(exclude)처럼 새 의존성이 추가될 때마다 목록을 늘려야 하는 문제가 없다.
2
커넥션 풀이나 클라이언트를 완전히 직접 조립해야 할 때. 부트의 기본 조립으로는 표현이 안 되는 요구(멀티 데이터소스, 라우팅 데이터소스 등)가 있으면 자동 구성을 끄고 전부 손으로 쓴다.
3
의존성을 뺄 수 없는데 기능은 꺼야 할 때. 다른 모듈이 끌고 오는 전이 의존성이라 build 파일에서 제거할 수 없는 경우다. 클래스패스에는 있으니 @ConditionalOnClass는 통과해 버리므로, exclude로 명시적으로 끈다.
4
시큐리티 자동 구성을 걷어낼 때 — 여기엔 단서가 붙는다. 게이트웨이가 인증을 전담하는 내부 서비스인데 spring-boot-starter-security가 전이 의존성으로 딸려 와 모든 요청이 401이 되는 경우다. 다만 이 경우 exclude보다 SecurityFilterChain 빈을 직접 정의해 "허용" 정책을 명시하는 쪽이 안전하다 — 자동 구성을 끄면 나중에 인증이 필요해졌을 때 아무도 그 사실을 모르는 상태가 되기 때문이다.

10. 심화 — 없는 클래스를 실명으로 지목했는데 왜 안 터지나 시니어 변별

꼬리질문 중 가장 어려운 것이고, 어려운 이유는 "애초에 뭐가 문제인데?"라는 전제가 통째로 생략되어 있어서다. 전제를 세 계단으로 나눠 채워야 질문이 보인다.

10-1. 전제 ① — 자동 구성 클래스는 안 써도 항상 클래스패스에 있다

build.gradle에 spring-boot-starter-web 하나만 넣어도, 실제로 받아지는 jar 안은 이렇다.

spring-boot-autoconfigure-3.x.jar
 └─ org/springframework/boot/autoconfigure/
     ├─ web/     ServletWebServerFactoryAutoConfiguration.class
     ├─ jdbc/    DataSourceAutoConfiguration.class
     ├─ amqp/    RabbitAutoConfiguration.class      ← RabbitMQ 안 썼는데도 있음
     ├─ kafka/   KafkaAutoConfiguration.class       ← 있음
     └─ ... 156개

부트는 기술별로 jar를 쪼개지 않았다. 모든 기술의 자동 구성 클래스를 하나의 거대한 jar에 전부 담아 두고, 어떤 스타터를 쓰든 이 jar가 통째로 딸려온다.

여기서 오해 하나를 뒤집어야 한다

✗ "RabbitMQ 스타터를 넣어야 RabbitAutoConfiguration이 생긴다"
✓ "RabbitAutoConfiguration은 처음부터 항상 있다. 안 쓰면 조건에서 탈락할 뿐"

10-2. 전제 ② · ③ — 비대칭이 만드는 닭-달걀

10-3. 정확히 어디서 터지는가 — 로딩이 아니라 리플렉션이다 흔한 오해

"클래스를 로딩하면 참조 클래스가 없어서 터진다"는 설명은 사실이 아니다 JVM의 심볼 해석(resolution)은 게을러서(lazy), 로딩만으로는 상수 풀의 참조를 해석하지 않는다. 터지는 건 로딩한 클래스를 리플렉션으로 들여다볼 때다. 그리고 조건을 평가하려면 반드시 들여다봐야 한다. 
Class<?> c = Class.forName("...RabbitAutoConfiguration");   // ① 안 터진다 — 잘 출력됨
System.out.println(c.getName());

ConditionalOnClass ann = c.getAnnotation(ConditionalOnClass.class);  // ② OK
Class<?>[] required = ann.value();                          // ③ 여기서 터진다TypeNotPresentException

③이 왜 터지나: value()의 반환 타입이 Class[]다. 즉 나에게 값을 돌려주려면 RabbitTemplate의 Class 객체를 실제로 만들어서 배열에 담아 줘야 한다. jar가 없으니 실패하고, JDK는 TypeNotPresentException을 던진다. 같은 이유로 c.getDeclaredMethods()도 터진다 — Method 객체를 만들려면 반환 타입 RabbitTemplate을 해석해야 하기 때문이다.

10-4. 답 — 자바 코드로 읽지 않고, 파일로 읽는다

전화를 걸지 않고 문패를 본다. RabbitAutoConfiguration.class는 결국 디스크의 파일이고, 그 안에서 애너테이션은 이렇게 저장돼 있다.

RuntimeVisibleAnnotations:
  ConditionalOnClass(
    value = [ "Lorg/springframework/amqp/rabbit/core/RabbitTemplate;" ]
                            ↑ 이건 그냥 글자다. 클래스가 아니다.
  )

종이에 적힌 "김철수"라는 글씨를 읽는 데 김철수 씨가 실존할 필요는 없다. 그래서 스프링은 ASM이라는 바이트코드 리더로 .class 파일의 바이트를 직접 읽어 이름 문자열만 뽑아낸다.

before 리플렉션 — 터진다
Class<?>[] v = clazz.getAnnotation(ConditionalOnClass.class).value();
//   → Class 객체를 돌려주려면 RabbitTemplate을 실제로 로딩해야 한다
//   → TypeNotPresentException
after ASM(MetadataReader) — 안 터진다
String[] v = (String[]) asmMetadata
        .getAnnotationAttributes(ConditionalOnClass.class.getName()).get("value");
//   → ["org.springframework.amqp.rabbit.core.RabbitTemplate"]  그냥 문자열
부수 효과도 크다 — 이걸 덧붙이면 답이 완성된다 후보 156개 중 탈락할 120여 개가 JVM에 아예 안 올라가므로 기동 속도와 메타스페이스를 아낀다. 뒤집어 말하면 "후보가 156개나 되는데 기동이 느리지 않나요?"라는 질문의 답이 여기 있다 — 대부분은 파일만 읽고 탈락시키므로 "156개 클래스를 로딩하는 비용"이 아니다.

10-5. 곁가지 — "그럼 스프링은 그 소스를 어떻게 컴파일했나?" 가산점

@ConditionalOnClass(RabbitTemplate.class)라는 소스를 컴파일하려면 컴파일 시점에는 RabbitTemplate이 반드시 있어야 한다. 스프링 팀은 spring-boot-autoconfigure를 빌드할 때 RabbitMQ·Kafka·Redis를 전부 optional 의존성으로 걸어 놓고 컴파일한다. optional은 "컴파일엔 필요하지만 이 jar를 쓰는 사람에게 전파하지는 마라"는 뜻이다.

스프링 팀의 빌드 시점

RabbitTemplate 있음 → 컴파일 성공

내 프로젝트의 실행 시점

RabbitTemplate 없음 → 그래서 ASM이 필요

이 두 시점의 간극이 문제의 근원이고, ASM이 그 간극을 메운다.

자동 구성 모듈을 직접 만들 때 이어지는 실천 규칙 가산점

없을 수 있는 타입이 @Bean 메서드의 시그니처(반환 타입·파라미터)에 등장하면 위험하다 — 바깥 클래스가 조건을 통과하는 순간 리플렉션 대상이 되어 NoClassDefFoundError가 난다.

그런 @Bean은 자체 @ConditionalOnClass를 단 중첩 static 설정 클래스로 격리한다

중첩 클래스의 조건도 ASM으로 먼저 평가되므로 안전하게 통째로 건너뛴다. 5-1에서 본 DataSourceAutoConfiguration.PooledDataSourceConfiguration이 바로 그 관례를 따른 구조다 — 그 중첩 구조가 스타일이 아니라 안전장치였다는 것을 여기서 알게 된다.

11. 스타터 직접 만들기 · 비용과 한계

11-1. 사내 공통 라이브러리를 만들 때 쓰는 레시피

1
@AutoConfiguration 클래스를 작성하고 @ConditionalOnClass, @ConditionalOnMissingBean 등 조건을 건다 — 사용자가 재정의하면 물러나도록 설계하는 게 관례다.
2
META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 파일에 그 클래스의 FQCN을 등록한다. 컴포넌트 스캔 대상 패키지에 두는 것이 아니다 — 스캔에 걸리면 조건 평가 체계 밖에서 무조건 등록돼 버리고, 무엇보다 사용자 설정과 같은 타이밍에 처리되어 7절의 순서 보장이 깨진다.
3
설정값은 @ConfigurationProperties로 노출해 yml로 제어 가능하게 한다.
4
관례상 자동 구성 모듈(xxx-spring-boot-autoconfigure)과 의존성 묶음 모듈(xxx-spring-boot-starter)을 분리한다.
2번이 함정이다 — 부트 2.x용 사내 라이브러리를 3.x로 올린다면 spring.factories의 EnableAutoConfiguration 키는 3.0에서 제거됐으므로, imports 파일로 옮기지 않으면 에러 하나 없이 조용히 아무 일도 일어나지 않는다(4-1절 표).

11-2. 자동 구성의 단점이나 비용은? 시니어 변별

① 암묵성 — 첫 번째 비용

어떤 빈이 왜 생겼는지 코드만 봐서는 안 보인다. 팀원이 의존성 하나 추가했을 뿐인데 시큐리티 필터 체인이나 기본 동작이 통째로 바뀌는 "원거리 부수효과"가 생긴다.

대응 원칙: 의존성 추가는 설정 변경과 같은 무게로 리뷰한다.

② 기동 비용 — 정확히 말해야 한다

후보 156개 전체에 대한 조건 평가가 기동 시간에 더해진다.

다만 ASM으로 파일만 읽고 대부분을 탈락시키므로(10절), 실제 비용은 "150개 클래스를 로딩하는 것"보다 훨씬 작다는 점까지 짚으면 정확하다.

③ 암묵적 기본값 리스크 — 세 번째이자 가장 위험하다

커넥션 풀 크기, 타임아웃 같은 기본값을 "부트가 알아서"에 맡기고 운영에 나가면, 평시에는 멀쩡하다가 트래픽이 오르는 순간 기본값이 병목이 된다. HikariCP의 기본 풀 크기 10이 대표적이다 — 로컬과 스테이징에서는 절대 드러나지 않는다.

결론은 균형 있게 — "기본값에 의존하되, 운영 크리티컬한 값은 명시적으로 고정한다"

자동 구성을 끄자는 것도, 전부 맡기자는 것도 아니다. 그리고 문제가 생기면 --debug나 /actuator/conditions로 조건 평가 결과를 읽어 추적한다는 대응까지 이어지면 원리와 운영이 모두 잡힌 인상을 준다.

12. 인출 카드 · 꼬리질문 셀프 테스트

12-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

자동화되는 "설정"은 무엇인가?
yml이 아니라 빈 조립 코드(@Configuration + @Bean). yml은 그 코드가 읽어 가는 입력값이다.
동작 3단계는?
모·거·등 — 모은다(imports 156) · 거른다(@Conditional) · 등록한다(통과 20~30개를 빈 정의로).
후보 목록은 어디서 오나?
각 jar의 META-INF/spring/…AutoConfiguration.imports. 3.0부터 spring.factories의 자동 구성 키는 제거됐다.
조건 3종은?
클·빈·값 — OnClass(클래스패스) · OnMissingBean(빈 정의) · OnProperty(yml 값).
조건은 언제 평가되나?
런타임이 아니다. 빈 정의(설계도) 등록 단계에서, 인스턴스가 하나도 만들어지기 전에 끝난다.
내 빈이 "이기는" 이유는?
우선순위가 아니라 순서. 자동 구성은 DeferredImportSelector라 사용자 설정 뒤 맨 마지막에 평가되어 스스로 물러난다.
back-off를 정확히 표현하면?
"덮어쓴다"가 아니라 "부트 쪽 @Bean이 빈 정의로 등록되지도 않는다" — 애초에 하나만 만들어진다.
안 먹는 원인 3종은?
조·충·제 — 조건 불충족 · 빈 충돌(back-off) · 명시적 제외. 리포트 4덩어리에 그대로 대응한다.
리포트에서 건지는 단어는?
found beans of type '…' dataSource — 끝의 빈 이름이 범인. 그 이름으로 검색하면 몰래 등록한 라이브러리가 나온다.
리포트 어디에도 안 보이면?
탈락이 아니라 후보 목록에 없다는 뜻 — imports 파일 누락·FQCN 오타·2.x용 spring.factories만 있는 라이브러리.
없는 클래스를 지목했는데 왜 안 터지나?
ASM으로 .class 파일을 읽어 String[]으로 조건 값을 얻기 때문. 조건 평가가 로딩보다 먼저 일어난다.
단점 3종은?
암묵성(의존성=설정 변경) · 기동 비용(단, ASM이라 작다) · 암묵적 기본값(HikariCP 풀 10).

12-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

Spring Boot의 Auto Configuration은 어떻게 동작하나요? 필수힌트: "설정"의 정의부터 교정하고, 3단계를 대고, 평가 시점과 순서를 덧붙인다

먼저 용어를 교정하며 시작하는 것이 이 질문의 첫 관문이다. 여기서 자동화되는 "설정"은 application.yml이 아니라 빈을 만들어 컨테이너에 등록하는 자바 코드(@Configuration + @Bean)다. spring.datasource.url 같은 값은 여전히 내가 쓰고, 부트는 그 값을 읽어 DataSource를 만드는 코드를 대신 실행한다.

동작은 세 단계다(모·거·등). ① @SpringBootApplication 안의 @EnableAutoConfiguration이 AutoConfigurationImportSelector를 import하고, 이것이 클래스패스 모든 jar에서 META-INF/spring/…AutoConfiguration.imports를 읽어 후보 목록(부트 3.5 기준 156줄)을 만든다. ② 후보마다 @ConditionalOnClass·@ConditionalOnMissingBean·@ConditionalOnProperty를 평가한다. ③ 통과한 20~30개만 빈 정의로 등록한다.

여기에 두 가지를 덧붙이면 답이 완성된다 — 평가 시점은 런타임이 아니라 빈 정의 등록 단계이고, 평가 순서는 DeferredImportSelector라서 사용자 설정이 전부 처리된 뒤 맨 마지막이다. 그래서 내 빈을 보고 물러날 수 있다.

내가 DataSource 빈을 직접 등록하면 부트의 자동 구성 DataSource는 어떻게 되나요? 필수힌트: "덮어쓴다"라고 답하면 반 칸 손해다. 무엇이 안 일어나는지로 말한다

생성 자체가 안 된다. 자동 구성의 DataSource 쪽에 @ConditionalOnMissingBean이 붙어 있어서, 컨테이너에 이미 사용자 정의 DataSource 빈 정의가 있으면 조건 불충족으로 그 @Bean 메서드가 빈 정의로도 등록되지 않는다. "두 개 생겼다가 하나가 이기는" 게 아니라 애초에 하나만 만들어진다.

여기서 한 걸음 더 들어가면 변별이 된다 — 이것이 성립하는 이유는 순서 때문이다. 자동 구성은 DeferredImportSelector라서 사용자 설정이 전부 처리된 뒤에 마지막으로 평가된다(7절). 그래서 조건을 평가하는 시점에는 내 빈 정의가 이미 등록돼 있고, 자동 구성은 그것을 보고 물러날 수 있다. 순서가 반대였다면 이 메커니즘은 아예 성립하지 않는다.

그 조건 평가는 언제 일어나나요? 애플리케이션이 도는 중인가요? 함정힌트: 컨테이너 기동을 두 단계로 쪼갠 뒤, 어느 쪽인지 지목한다

런타임이 아니다. 컨테이너 기동은 크게 [1단계] 빈 정의(설계도) 등록 → [2단계] 빈 인스턴스화 두 단계인데, @Conditional 계열은 전부 1단계에서 평가된다. ConfigurationClassPostProcessor가 설정 클래스를 파싱하면서 조건을 통과한 클래스의 @Bean 메서드만 설계도로 등록하고 탈락한 것은 아예 등록하지 않는다. 이 시점엔 new가 한 번도 일어나지 않았다.

여기서 결론 두 개가 따라 나온다. ① @ConditionalOnMissingBean이 보는 것은 "이미 생성된 빈"이 아니라 "지금까지 등록된 빈 정의"다. ② 그래서 순서에 극도로 민감하다 — 내 빈 정의가 먼저 등록돼 있어야만 자동 구성이 물러난다.

@ConditionalOnMissingBean을 제 @Configuration에도 붙여서 써도 되나요? 함정힌트: "여태까지 처리한 것만 본다"는 성질이 어떤 전제 위에서만 안전한가

권장되지 않는다. 이 조건은 "여태까지 처리된 빈 정의"만 볼 수 있는데, 내 설정 클래스들끼리는 처리 순서가 보장되지 않는다. 그래서 조건을 평가하는 시점에 상대 빈이 아직 등록 전일 수 있고, 그러면 같은 코드가 실행할 때마다 다른 결과를 낼 수 있다. 스프링 부트의 자바독도 "자동 구성 클래스에만 쓰기를 강력히 권장한다"고 명시한다.

왜 자동 구성에서는 안전한가를 붙이면 답이 닫힌다 — 자동 구성은 사용자 설정이 전부 끝난 뒤 맨 마지막에 평가된다는 순서 보장이 있기 때문이다. 조건의 안전성은 애너테이션이 아니라 그 애너테이션이 놓인 자리의 순서 보장에서 나온다.

@ConditionalOnClass는 그 클래스가 없어도 왜 자동 구성 클래스 로딩이 안 터지나요? 시니어 변별힌트: 먼저 "무엇이 문제인지"를 세워야 한다 — 없는 클래스를 실명으로 지목한 애너테이션

질문의 전제부터 세워야 한다. spring-boot-autoconfigure.jar에는 내가 안 쓰는 기술의 자동 구성까지 전부 들어 있다. 그래서 RabbitAutoConfiguration(설정하는 쪽)은 항상 있는데 RabbitTemplate(설정당하는 쪽, spring-rabbit.jar)은 없는 비대칭이 생긴다. 그런데 @ConditionalOnClass(RabbitTemplate.class)는 없을지도 모르는 클래스를 클래스 리터럴로 지목하고 있다 — 김철수 씨가 집에 있는지 확인하려고 김철수 씨한테 전화를 거는 꼴이다.

정확히 어디서 터지는지도 짚어야 한다. 흔한 오해와 달리 클래스 로딩만으로는 안 터진다(JVM의 심볼 해석은 lazy하다). 터지는 곳은 리플렉션이다 — annotation.value()의 반환 타입이 Class[]라서, 값을 돌려주려면 RabbitTemplate의 Class 객체를 실제로 만들어야 하고 그래서 TypeNotPresentException이 난다.

답: 스프링은 자바 코드로 읽지 않고 파일로 읽는다. ASM 바이트코드 리더로 .class 파일의 바이트를 직접 파싱해 조건 값을 String[](이름 문자열)로 뽑아낸다. Class[] → String[], 이 반환 타입 하나가 해결의 핵심이다. 그 문자열을 ClassUtils.isPresent()에 넘겨 try-catch로 감싼 통제된 로딩으로 존재를 확인한다.

부수 효과까지 말하면 완성이다 — 후보 156개 중 탈락할 120여 개가 JVM에 아예 안 올라가므로 기동 속도와 메타스페이스를 아낀다. 즉 답의 핵심은 "조건 평가가 클래스 로딩보다 먼저, 로딩 없이 일어난다는 순서"다.

그럼 스프링 팀은 그 소스를 어떻게 컴파일했나요? 가산점힌트: 컴파일 시점과 실행 시점을 분리한다

@ConditionalOnClass(RabbitTemplate.class)라는 소스를 컴파일하려면 컴파일 시점에는 RabbitTemplate이 반드시 있어야 한다. 스프링 팀은 spring-boot-autoconfigure를 빌드할 때 RabbitMQ·Kafka·Redis 등을 전부 optional 의존성으로 걸고 컴파일한다. optional은 "컴파일엔 필요하지만 이 jar를 쓰는 사람에게 전파하지는 마라"는 뜻이다.

스프링 팀의 빌드 시점엔 있고, 내 프로젝트의 실행 시점엔 없다 — 이 두 시점의 간극이 문제의 근원이고, ASM이 그 간극을 메운다.

자동 구성 클래스끼리 순서는 어떻게 정해지나요? 가산점힌트: 애너테이션 이름만 대지 말고, 왜 필요한지를 조건의 성질로 설명한다

@AutoConfigureBefore / @AutoConfigureAfter / @AutoConfigureOrder로 자동 구성 클래스 간의 상대 순서를 선언한다.

왜 필요한지는 조건의 성질로 설명된다. @ConditionalOnMissingBean은 "여태까지 등록된 빈 정의"만 볼 수 있으므로, A가 B의 빈 유무를 조건으로 본다면 A는 반드시 B보다 나중에 평가돼야 한다. 예를 들어 JPA 자동 구성은 DataSource 빈의 존재를 조건으로 보므로 DataSourceAutoConfiguration 이후에 평가되어야 한다.

주의 둘을 덧붙이면 좋다. ① 이 애너테이션들은 자동 구성 클래스에만 적용되고 일반 사용자 @Configuration의 순서 제어 수단이 아니다. ② 사용자 설정 전체는 언제나 자동 구성보다 먼저 처리되므로(7절), 사용자 설정과 자동 구성 사이의 순서를 이 애너테이션으로 조정할 일은 없다.

@ConditionalOnBean은요? 이건 편하게 써도 되나요? 함정힌트: OnMissingBean과 같은 것을 본다 — 그러면 같은 제약을 받는다

같은 이유로 순서에 민감하고, 같은 이유로 자동 구성 안에서만 안전하다. @ConditionalOnBean도 @ConditionalOnMissingBean과 마찬가지로 "여태까지 처리된 빈 정의"를 보기 때문에, 평가 시점에 대상 빈이 아직 등록 전이면 "없다"로 판정되어 조용히 탈락한다.

그래서 어떤 자동 구성이 다른 자동 구성의 빈을 전제로 한다면 @AutoConfigureAfter로 순서를 명시해야 판정 자체가 성립한다. 순서 선언 없이 @ConditionalOnBean만 걸어두면 "됐다 안 됐다 하는" 가장 디버깅하기 힘든 형태가 된다.

부트 2.x용 사내 라이브러리를 3.x에 올렸더니 자동 구성이 통째로 안 먹습니다. 함정힌트: 리포트 어디에도 안 나온다는 것 자체가 결정적 단서다

후보 목록을 담는 파일이 3.0에서 바뀐 것이 1순위 원인이다. 2.6 이하는 META-INF/spring.factories의 EnableAutoConfiguration= 키, 2.7은 둘 다 동작(imports 도입, spring.factories는 폐기 예정), 3.0부터는 META-INF/spring/…AutoConfiguration.imports만 읽는다. spring.factories의 자동 구성 항목은 제거됐다.

이 실패는 시끄럽지 않다 — 에러 없이 조용히 무시된다. 진단은 --debug 리포트로 한다: 해당 클래스가 Negative matches에 탈락 사유와 함께 나오면 조건 문제이고, Positive·Negative·Exclusions 어디에도 안 보이면 조건에서 탈락한 게 아니라 후보 목록에 애초에 없다는 뜻이다 → imports 파일 누락 또는 FQCN 오타.

자동 구성이 안 먹을 때 실무에서 어떻게 추적하나요? 필수힌트: 원인을 셋으로 분류하고, 그 셋이 리포트의 어느 덩어리에 대응하는지로 답한다

원인은 보통 셋 중 하나다(조·충·제). ① 조건 불충족 — 필요한 클래스가 클래스패스에 없거나 @ConditionalOnProperty가 꺼져 있다. ② 빈 충돌/back-off — 어딘가에서 같은 타입 빈을 이미 등록했다. ③ 명시적 exclude — 누군가 꺼 뒀다.

셋을 구분하는 방법은 하나로 통일돼 있다. --debug로 기동하면 CONDITIONS EVALUATION REPORT가 나오고, 네 덩어리가 원인에 그대로 대응한다 — Positive matches(적용됨) / Negative matches(탈락 사유, ①②를 여기서 구분) / Exclusions(③) / Unconditional classes(진단엔 거의 안 씀).

가장 값어치 있는 것은 Did not match 밑의 줄이다. did not find required class 'com.rabbitmq.client.Channel'이면 의존성 누락이고, found beans of type 'javax.sql.DataSource' dataSource면 back-off인데 끝에 붙은 dataSource가 범인의 빈 이름이다. 그 이름으로 코드베이스와 의존 라이브러리를 검색하면 사내 라이브러리가 몰래 등록한 빈을 찾아낼 수 있다.

이미 떠 있는 앱이라면 재기동 없이 /actuator/conditions로 같은 리포트를 JSON으로 받는다(기동 때 만들어진 ConditionEvaluationReport를 다시 꺼내 주는 것뿐이다). 다만 내부 구성이 그대로 드러나므로 외부에 열어 두면 안 된다.

자동 구성 결과를 조금만 바꾸고 싶습니다. 바로 exclude하면 되나요? 가산점힌트: 개입 강도를 낮은 것부터 네 단계로 세운다

exclude는 가장 마지막 수단이다. 개입 강도가 약한 순서로 네 단계를 두고 위에서부터 시도하는 것이 실무 순서다.

① yml 프로퍼티로 조정 — 자동 구성 대부분은 @ConfigurationProperties로 값을 노출하므로, 풀 크기·타임아웃 같은 것은 값만 바꾸면 끝난다.
② 부트가 제공하는 커스터마이저/Configurer 빈 등록 — 예컨대 MVC 설정은 WebMvcConfigurer, Jackson은 Jackson2ObjectMapperBuilderCustomizer처럼 "기본 조립은 유지하고 일부만 손대는" 훅이 마련돼 있다. 부트의 기본값 갱신을 계속 따라갈 수 있다는 것이 최대 장점이다.
③ 같은 타입 빈을 직접 정의 — @ConditionalOnMissingBean 덕분에 자동 구성이 그 빈만 back-off한다. 조립을 통째로 내가 책임진다는 뜻이므로 부트가 기본으로 깔아주던 설정도 함께 사라질 수 있다는 점을 감수해야 한다.
④ exclude — 그 자동 구성 전체가 필요 없을 때만.

왜 이 순서인가: 아래로 갈수록 내가 떠안는 책임이 커지고, 부트 버전 업그레이드 때 깨질 여지도 커진다. ①②는 부트의 기본 조립 위에 얹는 것이고 ③④는 그 조립을 내가 대체하는 것이다.

테스트 슬라이스(@WebMvcTest 등)는 자동 구성과 어떤 관계인가요?힌트: 블랙리스트와 화이트리스트

방향이 반대다. @SpringBootTest + spring.autoconfigure.exclude는 "전부 켜고 필요 없는 걸 뺀다"(블랙리스트)인 반면, 슬라이스 애너테이션은 "그 계층에 필요한 자동 구성만 켠다"(화이트리스트)다. 슬라이스마다 켤 자동 구성 목록이 따로 정의돼 있고, 컴포넌트 스캔 대상도 좁혀진다 — 예컨대 @WebMvcTest는 웹 계층 빈만 올리고 @Service·@Repository는 올리지 않는다.

실무적 함의: 블랙리스트는 새 의존성이 추가될 때마다 exclude 목록을 늘려야 하지만, 화이트리스트는 목록을 건드릴 일이 없다. "DB 없이 뜨게 하려고 exclude를 매번 붙이고 있다"면 슬라이스로 갈아탈 신호다. 대신 슬라이스는 협력 빈을 목으로 채워야 하므로 그 비용은 감수한다.

직접 스타터/자동 구성 모듈을 만들려면 어떻게 하나요? 가산점힌트: 4단계 레시피 + "컴포넌트 스캔에 두면 안 되는 이유"

① @AutoConfiguration 클래스를 작성하고 @ConditionalOnClass·@ConditionalOnMissingBean 등 조건을 건다 — 사용자가 재정의하면 물러나도록 설계하는 게 관례다. ② META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports에 FQCN을 등록한다. ③ 설정값은 @ConfigurationProperties로 노출해 yml로 제어 가능하게 한다. ④ 자동 구성 모듈(xxx-spring-boot-autoconfigure)과 의존성 묶음 모듈(xxx-spring-boot-starter)을 분리한다.

2번에 두 개의 함정이 있다. 첫째, 컴포넌트 스캔 대상 패키지에 두면 안 된다 — 스캔에 걸리면 조건 평가 체계 밖에서 무조건 등록되고, 무엇보다 사용자 설정과 같은 타이밍에 처리되어 "자동 구성은 맨 마지막"이라는 순서 보장이 깨진다. 그러면 사용자가 같은 타입 빈을 정의했을 때 back-off가 안정적으로 동작하지 않는다. 둘째, 부트 2.x에서 올려온 라이브러리라면 spring.factories에서 imports 파일로 옮겨야 한다 — 안 옮기면 에러 없이 조용히 무시된다.

자동 구성 모듈을 만들 때, 없을 수도 있는 타입을 @Bean에 쓰면 어떻게 되나요? 시니어 변별힌트: ASM은 조건까지만 지켜준다 — 조건을 통과한 뒤에는?

바깥 클래스가 조건을 통과하는 순간 위험해진다. 조건 평가까지는 ASM이 로딩 없이 처리해 주지만, 통과한 클래스는 그때부터 진짜로 로딩되고 리플렉션 대상이 된다. 이때 @Bean 메서드의 시그니처(반환 타입·파라미터)에 없는 타입이 있으면 Method 객체를 만들 수 없어 NoClassDefFoundError 계열의 실패가 난다.

부트가 실제로 쓰는 관례는 그런 @Bean을 자체 @ConditionalOnClass를 단 중첩 static 설정 클래스로 격리하는 것이다. 중첩 클래스의 조건도 ASM으로 먼저 평가되므로 안전하게 통째로 건너뛴다. 5-1에서 본 DataSourceAutoConfiguration.PooledDataSourceConfiguration이 바로 그 관례를 따른 구조다 — 중첩 구조가 스타일이 아니라 안전장치였다는 점을 짚으면 확실히 변별된다.

자동 구성의 단점이나 비용은 없나요? 시니어 변별힌트: 셋을 대되, 두 번째는 "생각보다 작다"로 정확히 교정하고, 마지막에 균형 잡힌 결론

① 암묵성이 첫 번째 비용이다. 어떤 빈이 왜 생겼는지 코드만 봐서는 안 보인다. 팀원이 의존성 하나 추가했을 뿐인데 시큐리티 필터 체인이나 기본 동작이 통째로 바뀌는 "원거리 부수효과"가 생긴다. 그래서 의존성 추가는 설정 변경과 같은 무게로 리뷰해야 한다는 원칙을 함께 말하면 좋다.

② 기동 비용이 두 번째다. 후보 156개 전체에 대한 조건 평가가 기동 시간에 더해진다. 다만 ASM으로 파일만 읽고 대부분을 탈락시키므로, 실제 비용은 "150개 클래스를 로딩하는 것"보다 훨씬 작다는 점까지 짚으면 정확하다.

③ 암묵적 기본값 리스크가 세 번째이자 가장 위험하다. 커넥션 풀 크기·타임아웃 같은 기본값을 "부트가 알아서"에 맡기고 운영에 나가면, 평시에는 멀쩡하다가 트래픽이 오르는 순간 기본값이 병목이 된다. HikariCP의 기본 풀 크기 10이 대표적이다 — 로컬과 스테이징에서는 절대 드러나지 않는다.

결론을 균형 있게 내는 것이 변별 포인트다. "기본값에 의존하되, 운영 크리티컬한 값은 명시적으로 고정한다" — 자동 구성을 끄자는 것도, 전부 맡기자는 것도 아니다. 그리고 문제가 생기면 --debug나 /actuator/conditions로 조건 평가 결과를 읽어 추적한다는 대응까지 이어지면 원리와 운영이 모두 잡힌 인상을 준다.

"의존성만 추가했는데 동작이 바뀌는" 사고를 팀에서 어떻게 막을 수 있을까요? 시니어 변별힌트: 앞 절들의 도구(리포트 · 명시적 고정 · 의존성 트리)를 실천으로 옮긴다

원리에서 대응이 곧바로 나온다. "의존성 추가 = @ConditionalOnClass 통과 = 설정 변경"이므로, 의존성 변경 PR은 설정 변경과 동일한 리뷰 강도로 다룬다. 특히 전이 의존성으로 딸려오는 것이 위험하므로, 의존성 트리로 "내가 직접 넣지 않았는데 들어온 스타터"가 있는지 확인한다 — 시큐리티가 전형적인 예다.

두 번째는 가시화다. 기동 시 조건 평가 리포트를 확인할 수 있게 해 두고(로컬 --debug, 운영은 인증 뒤의 /actuator/conditions), "무엇이 켜져 있는지"를 사람이 눈으로 볼 수 있는 상태로 만든다. 코드 리딩으로는 절대 안 보이는 것이 자동 구성이기 때문이다.

세 번째는 고정이다. 운영에서 사고로 이어지는 값(커넥션 풀 크기, 각종 타임아웃)은 기본값에 맡기지 않고 yml에 명시해 둔다. 그러면 부트 버전이 올라가며 기본값이 바뀌어도 내 서비스의 동작은 바뀌지 않는다 — 이것이 "기본값에 의존하되 크리티컬한 값은 고정한다"는 원칙의 실천 형태다.

한 줄 요약
Auto Configuration이 자동화하는 것은 yml이 아니라 빈 조립 코드이며, 실체는 "imports 파일로 모은 후보 156개를 @Conditional 조건 평가로 걸러 빈 정의로 등록하는 메커니즘"이다 — 이 평가가 런타임이 아니라 빈 정의 등록 단계에서, 그것도 DeferredImportSelector 덕분에 사용자 설정이 전부 끝난 뒤 맨 마지막에 일어나기 때문에 @ConditionalOnMissingBean이 내 빈을 보고 물러날 수 있고, 안 먹을 때는 --debug의 CONDITIONS EVALUATION REPORT에서 Did not match 사유를 읽는 것이 추적의 정석이다.
