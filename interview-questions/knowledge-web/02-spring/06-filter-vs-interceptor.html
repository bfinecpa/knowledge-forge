Filter vs Interceptor
소속이 다르면, 아는 것과 할 수 있는 것이 다르다

면접 질문: "Filter와 Interceptor의 차이, 각각 어떤 용도에 적합한가요?"

핵심 관전 포인트 — Filter는 서블릿 컨테이너(톰캣) 소속으로 DispatcherServlet 바깥에서 돌고, Interceptor는 Spring MVC 소속으로 HandlerMapping이 핸들러를 찾은 뒤에 돈다. 이 소속 차이 하나에서 실질적인 차이 셋이 파생된다. Filter는 요청/응답 객체 자체를 다른 것으로 갈아끼워 체인에 넘길 수 있지만 어떤 컨트롤러가 처리할지는 모르고, Interceptor는 HandlerMethod를 손에 쥐고 있어 핸들러별로 선별 처리할 수 있으며, Filter에서 터진 예외는 DispatcherServlet에 도달한 적이 없으므로 @ControllerAdvice가 구조적으로 잡을 수 없다. 그래서 배치 기준은 "모든 요청을, 스프링 밖에서 덮어야 하는 일은 Filter(인코딩·CORS·인증·본문 캐싱·trace id), 어떤 핸들러가 처리하는지 알아야 하는 일은 Interceptor(애너테이션 기반 인가·핸들러별 감사 로깅)"가 된다. 잘못 놓으면 인증 실패 응답에만 trace id가 빠지는 관측 사각지대가 생긴다.
  • 1
    차이의 뿌리는 하나 — 소속이다. Filter는 서블릿 스펙의 표준 부품이라 톰캣이 직접 호출하고 DispatcherServlet 바깥에 있다. Interceptor는 Spring MVC의 확장점이라 DispatcherServlet이 자기 처리 과정 중간에 불러주며, HandlerMapping이 핸들러를 확정한 뒤에 실행된다. 컨테이너는 인터셉터라는 개념 자체를 모른다.
  • 2
    거기서 실질 차이 셋이 파생된다 — 교체 · 문맥 · 예외. ① Filter만 chain.doFilter()에 다른 객체를 넘겨 요청/응답을 갈아끼울 수 있다(본문 캐싱이 Filter의 일인 이유). ② Interceptor만 HandlerMethod를 알아 애너테이션 기반 선별이 된다. ③ @ControllerAdvice는 DispatcherServlet이 자기 try 안에서 잡은 예외만 처리하므로, Filter의 예외는 원천적으로 못 잡는다.
  • 3
    그래서 배치 기준은 "무엇을 알아야 하고 무엇을 만져야 하는가"다. 스트림을 만지거나 스프링에 못 들어온 요청까지 덮어야 하면 Filter(인코딩·CORS·인증·본문 캐싱·trace id), 어떤 핸들러가 처리하는지 알아야 하면 Interceptor(애너테이션 인가·핸들러별 감사 로깅)다. 이걸 뒤집으면 인증 실패 요청에만 trace id가 없는, 즉 장애가 난 요청일수록 추적이 안 되는 최악의 사각지대가 생긴다.

0. 질문 + 출제 의도

질문: "Filter와 Interceptor의 차이, 각각 어떤 용도에 적합한가요?"

출제 의도: 인증·로깅·트레이싱을 어느 계층에 넣을지의 실무 결정을 할 수 있는지 본다. 잘못 놓으면 "인증 실패 응답에는 trace id가 안 찍히는" 류의 관측 사각지대가 생긴다 — 차이를 암기했는지가 아니라, 차이로부터 배치 결정을 도출할 수 있는지가 관전 포인트다.

이 페이지가 겨냥하는 약점 세 가지 ① "Filter는 스프링 밖, Interceptor는 안"에서 멈추는 것 → 2절의 소속 지도로 경계선을 눈에 박고, 4·5·6절에서 그 한 줄이 만드는 실질 차이 셋을 각각 코드로 끌어낸다.
② "Filter 예외는 @ControllerAdvice가 못 잡는다"를 문장으로만 외운 것 → 6절에서 doDispatch()의 try 블록을 경계선으로 그려 왜 못 잡는지, 그리고 아무 대응도 안 하면 실제로 어떤 응답이 나가는지까지 밀어붙인다.
③ 차이는 아는데 배치는 감으로 하는 것 → 9절의 관심사별 배치표와 trace id 사고 타임라인으로 "잘못 놓으면 무엇이 안 보이는가"를 구체적 장애로 보여준다.
두 문장 비유 — 정문 보안 게이트 vs 부서 안내 데스크 Filter는 건물 정문의 보안 게이트다. 방문자가 어느 부서에 가는지 몰라도 출입증 검사와 소지품 검사는 할 수 있고, 가방 안의 물건을 바꿔 담아 들여보낼 수도 있다. Interceptor는 부서 입구의 안내 데스크다. 방문자가 만날 담당자가 누구인지 이미 알고 있어서 그 담당자에 맞는 절차를 밟게 할 수 있다. — 공항으로 바꿔도 같다. 보안검색대는 모든 승객을 통과시키지만 어느 항공편인지 모르고, 탑승 게이트 직원은 편명과 좌석 등급을 알기에 선별 처리가 된다. 그리고 보안검색대에서 벌어진 사고는 게이트 직원이 알지 못한다 — 6절 예외 경계 이야기가 이 문장이다.

요청이 지나가는 전체 파이프라인의 단계별 흐름은 05 Spring MVC 요청 처리 흐름에서 다룬다. 이 문서는 그중 Filter와 Interceptor 두 계층의 비교와, 공통 관심사를 어느 쪽에 둘 것인가의 결정에 집중한다.

1. 전제 지식 — 서블릿 컨테이너와 서블릿 스펙

두 부품의 차이를 말하려면 "서블릿 컨테이너"와 "서블릿 스펙"이 무엇인지부터 정해 두어야 한다. 이 두 단어를 정의 없이 쓰면 나머지 설명이 전부 공중에 뜬다.

서블릿 컨테이너
HTTP를 자바 객체로 바꿔 우리 코드에 넘겨주는 서버. 톰캣이 대표. ① TCP 소켓을 열고 접속 대기 → ② 도착한 바이트를 HTTP 규격으로 파싱해 HttpServletRequest 생성 → ③ 스레드 풀에서 스레드를 꺼내 우리 코드 호출 → ④ HttpServletResponse에 쓴 내용을 HTTP 텍스트로 조립해 송신.
"컨테이너"라는 이름
이 서버가 우리가 만든 부품(서블릿)을 담아 두고 그 생명주기를 대신 관리해 주는 그릇이기 때문에 붙었다. 담는 그릇 = container.
서블릿 스펙
그릇과 부품 사이의 계약서. 정식 명칭은 Jakarta Servlet Specification. 부품이 구현할 인터페이스(Servlet, Filter, HttpServletRequest…)와 컨테이너가 언제 어떤 순서로 호출하는지가 문서로 못 박혀 있다. 계약이 표준이라 톰캣을 제티·언더토우로 바꿔도 같은 코드가 돈다.

이 문서 전체의 열쇠 — 한 문장

컨테이너 입장에서 보면 스프링 MVC 전체가 DispatcherServlet이라는 "서블릿 한 개"일 뿐이다

컨테이너는 스프링이라는 것이 존재하는지도 모르고, 그저 계약대로 서블릿 하나를 호출할 뿐이다. 그래서 Filter는 서블릿 스펙에 있는 단어이고, Interceptor는 없는 단어다. 이 비대칭이 모든 차이의 출발점이다.

2. 소속 지도 — 모든 차이의 뿌리

Filter — 서블릿 스펙이 정의한 부품

  • 서블릿에 도달하기 전과 응답이 나간 뒤에 끼어든다.
  • 여러 개가 사슬처럼 연결돼 체인이라 부르고, 각 필터가 chain.doFilter(req, res)로 다음 차례에 넘긴다.
  • 이 호출을 하지 않으면 요청은 거기서 끝난다 — 뒤의 필터도 DispatcherServlet도 실행되지 않는다. 이렇게 흐름을 끊는 것이 단락(short-circuit)이다.

Interceptor — Spring MVC가 정의한 부품

  • HandlerMapping이 "이 요청은 누가 처리할지"를 찾아낸 뒤에 실행된다.
  • 그래서 처음부터 핸들러 정보를 손에 쥐고 시작한다.
  • preHandle이 false를 반환하면 컨트롤러로 가지 않는다 — Filter의 "doFilter를 안 부른다"에 대응하는 차단 수단.

암기 장치 — 소속 하나에서 파생되는 차이 셋: 교 · 문 · 예

교체(요청/응답 객체)  ·  문맥(핸들러 정보)  ·  예외(@ControllerAdvice 도달 여부)

면접에서 표를 통째로 나열하는 대신 "소속이 다르다 → 그래서 교·문·예 세 가지가 갈린다"로 답하면, 암기가 아니라 인과로 설명하는 사람으로 들린다. 4·5·6절이 각각 하나씩이다.

3. 한 요청의 타임라인 — 언제 무엇을 알고 있는가

4. 차이 ① 요청/응답 객체를 교체할 수 있는가 — Filter만 가능

Filter는 chain.doFilter(req, res)를 부를 때 자기가 받은 객체가 아니라 다른 객체를 넘길 수 있다. 반면 Interceptor는 preHandle의 인자로 요청 객체를 받아 볼 뿐이고, 뒤 단계에 전달될 객체를 바꿔치기할 수단 자체가 없다.

이 차이가 실무에서 가장 아프게 드러나는 곳이 요청 본문 로깅이다.

전제 — HTTP 요청 본문은 한 번만 읽을 수 있다

HttpServletRequest.getInputStream()은 소켓에서 흘러들어오는 스트림이고, 스트림은 한 번 소비하면 되감을 수 없다. 그래서 로깅 코드가 본문을 먼저 읽어버리면, 뒤에서 @RequestBody를 바인딩하려던 HttpMessageConverter는 이미 비어버린 스트림을 만난다. — 수도관에 비유하면, 수도꼭지에서 흘러나온 물은 다시 관으로 밀어 넣을 수 없다. 두 사람이 마시려면 먼저 컵(버퍼)에 받아 두는 수밖에 없다.

before Interceptor에서 본문을 로깅하려 했다
public class BodyLoggingInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req,
                             HttpServletResponse res, Object handler)
            throws IOException {

        String body = StreamUtils.copyToString(req.getInputStream(), UTF_8);스트림 소비
        log.info("req body: {}", body);

        // 문제 1 : 스트림을 여기서 소비해 버렸다.
        //          뒤이어 ④-b 바인딩 단계에서 Jackson 이 읽으려 하면
        //          본문이 비어 있어 HttpMessageNotReadableException
        //          ("Required request body is missing") 이 난다.
        //
        // 문제 2 : "읽은 내용을 되돌려 놓은 새 request" 를 만들어
        //          넘기고 싶어도, Interceptor 에는
        //          뒤 단계로 전달될 객체를 교체할 방법이 없다.
        return true;
    }
}
after Filter에서 캐싱 래퍼로 교체해 체인에 넘긴다
@Component
public class BodyLoggingFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {

        var wrappedReq = new ContentCachingRequestWrapper(req);
        var wrappedRes = new ContentCachingResponseWrapper(res);

        chain.doFilter(wrappedReq, wrappedRes);원본이 아니라 래퍼를 넘긴다

        // 로깅은 반드시 doFilter '뒤' 에 온다. 래퍼는 본문을 미리
        // 읽어 두는 물건이 아니라, 아래 단계가 읽어 갈 때 곁에서
        // 받아 적는 물건이라 아래가 읽기 전에는 버퍼가 비어 있다.
        log.info("req body: {}", new String(wrappedReq.getContentAsByteArray(), UTF_8));
        log.info("res body: {}", new String(wrappedRes.getContentAsByteArray(), UTF_8));

        wrappedRes.copyBodyToResponse();빠뜨리면 빈 본문이 나간다
    }
}

해법은 읽은 바이트를 따로 보관해 두는 래퍼로 갈아끼운 뒤 체인에 넘기는 것이고, 그 래퍼가 스프링이 제공하는 ContentCachingRequestWrapper다. 이름 그대로 "내용을 캐싱하는 요청 래퍼"이며, 아래 단계가 스트림을 읽을 때마다 그 바이트를 내부 버퍼에도 복사해 둔다.

이 코드에 숨은 함정 두 개 — 실제로 자주 터진다

① copyBodyToResponse() 누락
응답 래퍼는 본문을 자기 버퍼에 붙들고 있다. 이 줄이 없으면 클라이언트에게 빈 본문이 나간다. 로깅을 붙였더니 응답이 사라지는, 원인 찾기 고약한 사고.
② 아래가 안 읽으면 캐시도 빈다
래퍼는 받아 적는 물건이라, 인증 실패로 요청이 컨트롤러에 닿지 못하면 getContentAsByteArray()는 빈 배열을 돌려준다. 본문을 무조건 남겨야 한다면 필터에서 직접 전부 읽어 보관하는 커스텀 래퍼가 필요하다.

②는 6절·9절의 "차단된 요청은 안쪽 계층이 못 본다"와 정확히 같은 구조의 문제다 — 이 페이지에서 세 번 반복되는 패턴이니 한 번에 묶어 기억한다.

결론 — 추상적 서술의 실체

인코딩 설정 · 응답 압축 · 본문 캐싱처럼 요청/응답 스트림 자체를 다루는 일은 구조적으로 Filter의 영역

"Filter는 요청/응답 객체를 교체할 수 있다"는 추상적인 서술의 실체가 바로 이 chain.doFilter(wrappedReq, wrappedRes) 한 줄이다. 면접에서는 이 한 줄을 말할 수 있느냐가 암기와 이해를 가른다.

5. 차이 ② 핸들러 문맥을 아는가 — Interceptor만 가능

Interceptor의 preHandle은 세 번째 인자로 핸들러 객체를 받는다. HandlerMethod로 캐스팅하면 어떤 컨트롤러의 어떤 메서드가, 어떤 애너테이션을 달고 이 요청을 처리할 예정인지 알 수 있다.

Interceptor 핸들러에 붙은 애너테이션으로 분기한다
public class AdminAuthInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {

        if (!(handler instanceof HandlerMethod method)) return true;이 줄이 없으면 ClassCastException
        // 정적 리소스 요청 등은 HandlerMethod 가 아니다. 캐스팅 전에 반드시 걸러야 한다.

        if (method.hasMethodAnnotation(AdminOnly.class) && !isAdmin(req)) {Filter 로는 불가능한 판단
            res.setStatus(HttpServletResponse.SC_FORBIDDEN);
            return false;   // false 를 반환하면 컨트롤러는 실행되지 않는다
        }
        return true;
    }
}

Interceptor로 하면 얻는 것

  • 애너테이션은 메서드를 따라다닌다 — 컨트롤러를 리팩터링해 경로가 바뀌어도 어긋나지 않는다.
  • addPathPatterns / excludePathPatterns로 경로 기반 선별도 된다. 서블릿의 URL 패턴 문법보다 표현력이 좋다(/api/** 같은 다중 와일드카드, 경로 변수 패턴 등).
  • "이 애너테이션이 붙은 핸들러에만", "이 URL 그룹에만" 같은 선별적 공통 처리가 자연스럽다.

Filter로 같은 일을 하면 생기는 것

  • URL 문자열을 직접 비교해야 한다 — 3절 타임라인의 왼쪽 구간에서는 누가 처리할지 아직 정해지지도 않았다.
  • 컨트롤러가 리팩터링되어 경로가 바뀌면 조용히 어긋난다. 컴파일 에러도, 테스트 실패도 나지 않는다 — 보안 구멍이 침묵 속에 생긴다.
  • URL 목록이 늘어날수록 필터 안의 문자열 배열이 진실의 원천이 되어 관리가 어긋난다.

함정 — instanceof HandlerMethod 체크를 빠뜨리면

정적 리소스 요청 등은 핸들러가 HandlerMethod가 아니다(예: 리소스 핸들러). 바로 캐스팅하면 평소엔 잘 돌다가 특정 요청에서만 ClassCastException이 나는 형태로 터진다. 캐스팅 전 instanceof 확인은 인터셉터 작성의 기본 관례로 외워 둔다.

6. 차이 ③ 예외가 어디까지 올라가는가 — 에러 응답 일관성의 분기점

셋 중 가장 실무적인 차이다. 그리고 "Filter의 예외는 @ControllerAdvice가 못 잡는다"는 문장을 외우는 것과, 왜 못 잡는지를 아는 것은 전혀 다르다.

6-1. 왜 못 잡는가 — 인과

@ControllerAdvice + @ExceptionHandler는 스스로 동작하는 장치가 아니다. DispatcherServlet이 자기 처리 과정에서 예외를 잡은 뒤 HandlerExceptionResolver에게 넘겨야 비로소 실행된다. 그중 ExceptionHandlerExceptionResolver가 @ControllerAdvice에 등록된 핸들러를 찾아 호출하는 구현이다.

뼈대 DispatcherServlet.doDispatch() — 경계선이 여기 있다
try {이 울타리 안에서 난 예외만 @ControllerAdvice 에 도달한다
    mappedHandler = getHandler(request);                  // ③ HandlerMapping
    if (!mappedHandler.applyPreHandle(req, res)) return;   // ④-a Interceptor.preHandle
    mv = ha.handle(req, res, mappedHandler.getHandler());  // ④-b 바인딩 + ④-c 컨트롤러
    mappedHandler.applyPostHandle(req, res, mv);          // ④-e postHandle
}
catch (Exception ex) {
    dispatchException = ex;     // 이 try 안에서 난 예외만 여기로 들어온다
}
// 잡은 예외를 HandlerExceptionResolver 들에게 넘긴다 → @ControllerAdvice 실행
processDispatchResult(req, res, mappedHandler, mv, dispatchException);

여기서 결론이 그대로 따라 나온다. 이 try 블록 안에서 난 예외만 @ControllerAdvice에 도달한다. 그런데 Filter는 이 코드가 실행되기도 전, doDispatch를 부른 적조차 없는 바깥에서 돈다. Filter의 예외는 DispatcherServlet에 도달한 적이 없는 예외이므로 잡힐 방법이 원천적으로 없다.

6-2. 그래서 실제로 무슨 응답이 나가는가 가산점

이 부분을 구체적으로 말할 수 있느냐가 아는 사람과 외운 사람을 가른다. (Spring Boot 3.x · 내장 톰캣 기준)

예외가 필터 체인을 뚫고 톰캣까지 올라가면, 톰캣은 에러 페이지 처리를 시작한다. 스프링 부트는 기동할 때 컨테이너에 /error 경로를 에러 페이지로 등록해 두므로, 톰캣은 같은 스레드에서 /error로 ERROR 디스패치라는 새 요청 처리를 한 번 더 일으킨다. 그 요청을 받는 것이 스프링 부트의 BasicErrorController다.

가산점 포인트 — ERROR 디스패치에는 필터가 다시 타지 않는다 OncePerRequestFilter는 기본적으로 이 ERROR 디스패치에서는 실행되지 않는다(shouldNotFilterErrorDispatch()가 true). 그래서 필터에서 MDC에 심어 둔 trace id를 finally에서 지웠다면, 에러 페이지 처리 과정의 로그에는 trace id가 없다. 9절의 사각지대 이야기와 이어지는 지점이다.

7. 대응책 — 에러 응답 표준화는 필터 계층까지 포함해 설계한다

암기 장치 — 대응책 4종은 "직 · 재 · 그 · 위"

직접 쓴다  ·  재사용한다  ·  그물을 친다  ·  위임한다

실무에서는 (4) 위임으로 인증·인가를 덮고, 그 밖의 필터 예외를 (1) 직접 또는 (2) 재사용으로 받고, (3) 그물을 최후에 두는 조합이 흔하다.

1
직접 — 예외 처리 전용 Filter를 체인 맨 앞에 둔다. 뒤에서 올라온 예외를 잡아 표준 포맷 JSON을 직접 써서 응답한다. 가장 직관적이고 의존성이 없다.
(1) 직접 체인 맨 앞의 예외 처리 필터
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)다른 필터보다 바깥에 있어야 그들의 예외를 잡는다
public class ErrorResponseFilter extends OncePerRequestFilter {
    private final ObjectMapper objectMapper;

    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        try {
            chain.doFilter(req, res);
        } catch (Exception e) {
            log.error("filter chain error", e);
            // 여기서 직접 쓰지 않으면 톰캣의 에러 페이지 처리로 넘어가 버린다.
            res.setStatus(HttpServletResponse.SC_INTERNAL_SERVER_ERROR);
            res.setContentType(MediaType.APPLICATION_JSON_VALUE);
            res.setCharacterEncoding("UTF-8");빠뜨리면 한글 메시지가 깨진다
            objectMapper.writeValue(res.getWriter(),
                    ErrorResponse.of("INTERNAL_ERROR", "일시적인 오류가 발생했습니다"));
        }
    }
}
2
재사용 — HandlerExceptionResolver를 필터에 주입해 직접 호출한다. MVC의 예외 처리 로직, 즉 @ControllerAdvice에 이미 써 놓은 것을 필터 계층에서 재사용하는 방법이다. 포맷 정의가 한 곳에만 남는다는 것이 장점.
private final HandlerExceptionResolver resolver;   // "handlerExceptionResolver" 빈을 주입

// catch 블록에서
resolver.resolveException(req, res, null, e);handler 자리는 null — 핸들러가 없는 예외다
3
그물 — /error를 우리 컨트롤러로 받는다. ErrorController 인터페이스를 구현한 컨트롤러로 BasicErrorController를 대체하면, 필터에서 올라온 예외든 다른 경로든 결국 /error로 모이므로 마지막 그물이 된다. 다만 이때는 원래 예외가 요청 속성(jakarta.servlet.error.exception)에 담겨 오므로 그것을 꺼내 써야 한다.
4
위임 — 인증·인가 실패는 Spring Security의 표준 확장점에서 처리한다. Spring Security는 이 문제를 이미 알고 있어서, 필터 체인 안에 ExceptionTranslationFilter를 두고 인증 예외는 AuthenticationEntryPoint(401), 인가 예외는 AccessDeniedHandler(403)로 넘긴다. 이 둘을 구현해 팀 표준 JSON을 쓰면 된다.
인과를 한 문장으로 — 이 문장이 4절 전체를 봉인한다 Spring Security가 굳이 자체 예외 처리기(AuthenticationEntryPoint · AccessDeniedHandler)를 갖고 있는 이유가 바로 "필터 안에서는 @ControllerAdvice를 쓸 수 없기 때문"이다. 이 한 문장을 말하면 "외운 사람"에서 "구조를 아는 사람"으로 넘어간다.
(4) 위임 인증 실패도 팀 표준 JSON으로
@Bean
public AuthenticationEntryPoint authenticationEntryPoint(ObjectMapper om) {
    return (request, response, authException) -> {
        response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
        response.setContentType(MediaType.APPLICATION_JSON_VALUE);
        response.setCharacterEncoding("UTF-8");
        om.writeValue(response.getWriter(), ErrorResponse.of("UNAUTHORIZED", "인증이 필요합니다"));
    };
}

핵심 인식 — 면접에서 이 문장으로 마무리한다

에러 응답의 일관성은 @ControllerAdvice만으로 완성되지 않고, 필터 계층까지 포함해 설계해야 한다

8. 차이가 아닌 것 — 의존성 주입 낡은 지식

오래된 자료에 남아 있는 설명

  • "Filter는 스프링 빈이 아니라 컨테이너 관할이라 DI를 못 받는다."
  • "그래서 Filter에서는 서비스나 ObjectMapper를 쓸 수 없다."

지금은 차이가 아니다

  • 스프링 부트에서는 Filter를 @Component로 등록하거나 FilterRegistrationBean으로 감싸 등록하면 그대로 스프링 빈이고 생성자 주입도 된다.
  • 7절 예제들이 ObjectMapper·HandlerExceptionResolver를 주입받는 것이 그 증거다.

원래 문제였던 것 — 컨테이너가 관리하는 필터가 스프링 빈을 쓰지 못하는 상황 — 은 DelegatingFilterProxy로 해결됐다. 컨테이너에 등록된 껍데기 필터가 실제 처리를 스프링 빈에게 위임하는 구조이고, Spring Security의 필터 체인이 바로 이 방식으로 꽂힌다.

9-4. 사고 사례 — trace id를 Interceptor에 심었을 때

trace id는 요청 하나에 부여하는 고유 식별자로, 그 요청이 남긴 모든 로그에 같은 값을 찍어 흩어진 로그를 한 줄기로 잇는 데 쓴다. 보통 MDC(Mapped Diagnostic Context, 로깅 라이브러리가 스레드마다 들고 있는 작은 키-값 저장소)에 넣어 두면 로그 패턴이 자동으로 찍어 준다.

before Interceptor에서 MDC에 심는다
public class TraceInterceptor implements HandlerInterceptor {
    public boolean preHandle(HttpServletRequest req,
                             HttpServletResponse res, Object handler) {
        MDC.put("traceId", UUID.randomUUID().toString());여기까지 오지 못하는 요청이 있다
        return true;
    }
}

// 정상 요청에는 trace id 가 있고 실패 요청에만 없다.
// "특정 사용자가 계속 401 을 받는다" 는 문의가 들어와도
// 그 사용자의 요청 로그를 하나의 흐름으로 이어붙일 수가 없다.
after 필터 체인 맨 앞에 Filter로 심는다
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)Security 필터(기본 -100)보다 앞
public class TraceIdFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {

        // 앞단 게이트웨이가 헤더로 넘겨준 값이 있으면 이어받고, 없으면 새로 만든다.
        // 이어받아야 서비스 경계를 넘는 요청도 하나의 흐름으로 추적된다.
        MDC.put("traceId", resolveOrGenerate(req));
        res.setHeader("X-Trace-Id", MDC.get("traceId"));
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear();톰캣은 스레드를 재사용한다
        }
    }
}

컨트롤러에 닿지 못하면 아무도 스트림을 읽지 않아 getContentAsByteArray()가 빈 배열(4절)
예외가 안 잡힌다
doDispatch에 닿은 적이 없으므로 @ControllerAdvice가 볼 기회가 없다(6절)
지표가 조용해진다
차단된 요청은 Interceptor의 카운터를 지나지 않아 공격 시 오히려 트래픽이 줄어 보인다(9-3절)

10. 세 훅과 실행 순서 — 양파 껍질 구조

10-1. Interceptor의 세 훅 — try-catch-finally에 대응시킨다

훅호출 시점예외가 나면반환값자리
preHandle컨트롤러 실행 전 (핸들러는 이미 확정)—false면 차단인가와 선행 검증의 자리. 여기서 던진 예외는 @ControllerAdvice에 도달한다.
postHandle컨트롤러가 정상 완료된 뒤, 뷰 렌더링 전아예 호출되지 않는다voidModelAndView를 손보는 용도라 REST API에서는 쓸 일이 거의 없다.
afterCompletion요청 처리가 끝난 뒤예외가 나도 항상 호출void자원 정리·소요 시간 기록처럼 반드시 실행돼야 하는 일의 자리.

암기 장치 — 세 훅은 try-finally에 얹으면 안 헷갈린다

preHandle = try 진입 전 검문  ·  postHandle = try 블록의 마지막 줄  ·  afterCompletion = finally

"정리 로직을 postHandle에 두면 예외 경로에서 조용히 누수된다"까지 말하면 가산점이다. finally에 해당하는 것이 afterCompletion이라고 대응시켜 두면 시점을 외울 필요가 없다.

10-2. 실행 순서 — 먼저 들어간 것이 나중에 나온다

Filter

  • FilterRegistrationBean.setOrder() 또는 빈에 붙인 @Order로 정한다.
  • 숫자가 작을수록 바깥쪽(먼저 실행)이다.
  • Spring Security의 필터 체인도 이 순서 체계 안의 한 자리(스프링 부트 기본값 -100)를 차지한다 → "Security보다 앞이어야 하나 뒤여야 하나"를 명시적으로 설계해야 한다. 9-4절의 trace id 필터가 그 예다.

Interceptor

  • WebMvcConfigurer.addInterceptors에서 등록한 순서대로 preHandle이 실행된다.
  • postHandle과 afterCompletion은 역순으로 실행된다.
  • 즉 먼저 들어간 것이 나중에 나오는 양파 껍질 구조이고, Filter 체인도 같은 모양이다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

차이의 뿌리 한 줄은?
소속. Filter = 서블릿 컨테이너(DispatcherServlet 바깥), Interceptor = Spring MVC(HandlerMapping 뒤).
파생 차이 3종은?
교 · 문 · 예 — 객체 교체 / 핸들러 문맥 / 예외 도달.
Filter만 되는 것은?
chain.doFilter(wrappedReq, wrappedRes) — 객체를 갈아끼워 넘긴다. 본문 캐싱·압축·인코딩이 Filter인 이유.
Interceptor만 되는 것은?
HandlerMethod로 애너테이션 기반 선별. 경로가 바뀌어도 애너테이션은 메서드를 따라다닌다.
예외 경계는 어디인가?
DispatcherServlet.doDispatch()의 try 블록. 안이면 @ControllerAdvice 도달, 밖이면 톰캣 에러 페이지.
아무 대응 없으면 뭐가 나가나?
/error ERROR 디스패치 → 부트 기본 JSON 또는 Whitelabel HTML. 그마저 없으면 톰캣 HTML → Unexpected token '<'.
대응책 4종은?
직 · 재 · 그 · 위 — 필터에서 직접 쓰기 / HandlerExceptionResolver 재사용 / /error 그물 / Security에 위임.
배치 기준 한 문장은?
"모든 요청을 스프링 밖에서 덮어야 하면 Filter, 핸들러를 알고서 처리해야 하면 Interceptor."
trace id를 Interceptor에 두면?
인증 실패 요청에는 안 찍힌다. 인증은 Filter 계층에서 끝나므로 preHandle까지 오지 않는다 → 장애 요청일수록 추적 불가.
세 훅 대응은?
preHandle=검문, postHandle=정상 경로 전용, afterCompletion=finally.
순서 규칙은?
Filter는 @Order 작을수록 바깥(Security는 -100). Interceptor는 등록 순서대로 pre, 역순으로 post·after — 양파.
차이가 아닌 것은?
DI. 부트에서는 Filter도 빈으로 등록해 생성자 주입이 된다. 옛 제약은 DelegatingFilterProxy로 해소.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

Filter와 Interceptor의 차이, 각각 어떤 용도에 적합한가요? 필수힌트: 표를 나열하지 말고 "소속 → 파생 차이 셋 → 배치 기준" 순서로 인과를 만든다

차이의 뿌리는 소속 하나다. Filter는 서블릿 컨테이너(톰캣) 소속으로 DispatcherServlet 바깥에서 돌고, Interceptor는 Spring MVC 소속으로 HandlerMapping이 핸들러를 찾은 뒤에 돈다.

여기서 실질 차이 셋이 파생된다. ① Filter는 chain.doFilter()에 다른 객체를 넘겨 요청/응답을 교체할 수 있다 — 본문은 한 번만 읽을 수 있어서 캐싱 래퍼로 갈아끼워야 하고, 그건 Filter만 가능하다. ② Interceptor는 HandlerMethod를 손에 쥐고 있어 어떤 컨트롤러의 어떤 메서드가, 어떤 애너테이션을 달고 처리할지 알고 선별 처리할 수 있다. ③ Filter의 예외는 DispatcherServlet에 도달한 적이 없어 @ControllerAdvice가 구조적으로 잡을 수 없다.

그래서 배치 기준은 "무엇을 알아야 하고 무엇을 만져야 하는가"다. 스트림을 만지거나 스프링에 못 들어온 요청까지 덮어야 하면 Filter(인코딩·CORS·인증·본문 캐싱·trace id), 핸들러를 알아야 하면 Interceptor(애너테이션 인가·핸들러별 감사 로깅)다. 잘못 놓으면 인증 실패 응답에만 trace id가 빠지는 관측 사각지대가 생긴다.

Spring Security는 왜 Interceptor가 아니라 Filter 체인으로 구현돼 있나요? 필수힌트: 이유 셋 — 차단 위치 / 보호 범위 / 표준. 그리고 예상되는 반문 하나를 미리 막는다

이유가 셋이다.

① 차단이 목적이라 바깥 경계에서 끝나야 한다. 인증과 인가는 들여보낸 뒤 막는 것보다 들어오기 전에 막는 편이 공격 표면이 작다. 스프링 MVC 안까지 들어오면 그만큼 코드가 더 실행된 뒤 막는 셈이다.

② 보호 대상이 컨트롤러만이 아니다. 정적 리소스를 포함해 서블릿 컨테이너로 들어오는 모든 요청을 덮어야 하는데, Interceptor는 DispatcherServlet 안쪽이라 그 범위를 커버하지 못한다.

③ Filter는 서블릿 스펙 표준이라 특정 웹 프레임워크에 묶이지 않는다. Spring MVC가 아닌 환경에도 같은 보안 계층을 얹을 수 있다.

예상 반문 대비 — "스프링 빈이 아닌 컨테이너 관할이라 DI를 못 받지 않느냐"는 물음에는 DelegatingFilterProxy로 답한다. 컨테이너에 등록되는 것은 껍데기 프록시 필터이고, 실제 처리는 스프링 빈인 FilterChainProxy에게 위임한다. "필터인데 스프링 빈의 DI를 온전히 쓴다"는 구조까지 말하면 가산점이다.

Filter에서 발생한 예외를 @ControllerAdvice가 못 잡는다면, 에러 응답 표준화는 어떻게 하나요? 필수힌트: ① 왜 못 잡는지 한 문장 ② 대응책 4종 ③ 아무 대응도 안 하면 실제로 뭐가 나가는지

먼저 왜 못 잡는지를 한 문장으로 말한다. @ControllerAdvice는 DispatcherServlet이 자기 try 안에서 잡은 예외를 HandlerExceptionResolver에게 넘겨야 실행되는 장치인데, Filter의 예외는 DispatcherServlet에 도달한 적이 없다.

그다음 대응책 넷(직·재·그·위)을 든다. ① 체인 맨 앞의 예외 처리 전용 Filter에서 표준 JSON을 직접 쓰거나, ② HandlerExceptionResolver 빈을 필터에 주입해 호출함으로써 MVC의 예외 처리 로직을 재사용하거나, ③ /error를 우리 ErrorController로 받아 마지막 그물을 치거나, ④ 인증·인가 실패는 AuthenticationEntryPoint·AccessDeniedHandler에 위임한다.

여기에 아무 대응도 하지 않으면 실제로 무엇이 나가는지까지 말하면 확실해진다. 스프링 부트라면 톰캣이 /error로 ERROR 디스패치를 걸어 BasicErrorController가 부트 기본 JSON이나 Whitelabel HTML을 내고, 그 처리마저 없으면 톰캣의 HTML 에러 페이지가 나가 프런트의 JSON 파서가 Unexpected token '<'로 터진다.

핵심 인식은 "에러 응답의 일관성은 @ControllerAdvice만으로 완성되지 않고, 필터 계층까지 포함해 설계해야 한다"는 것이다.

그럼 Interceptor에서 던진 예외는 @ControllerAdvice가 잡나요? 함정힌트: 기준은 "Filter냐 Interceptor냐"가 아니라 "울타리 안이냐 밖이냐"다

preHandle에서 던진 예외는 잡힌다. doDispatch()의 try 블록 안에서 applyPreHandle이 호출되기 때문이다. 같은 이유로 바인딩(ArgumentResolver) 단계와 컨트롤러 메서드의 예외도 잡힌다.

그래서 기준을 "Filter는 못 잡고 Interceptor는 잡는다"로 외우면 반쪽짜리다. 진짜 기준은 "DispatcherServlet의 try 울타리 안에서 났는가" 하나이고, Filter는 그 울타리 밖, Interceptor는 안이라서 결과가 갈린 것뿐이다.

실무적 함의: 인가 실패를 Interceptor에서 예외로 던지면 팀 표준 에러 포맷을 그대로 재사용할 수 있다. 반대로 preHandle에서 response.setStatus(403)만 하고 false를 반환하면 본문이 빈 응답이 나가므로, 그 경우엔 본문을 직접 써 주거나 예외를 던지는 쪽을 택해야 한다.

Interceptor의 세 훅은 각각 언제 쓰나요? 필수힌트: 시점 + "예외가 나면 어떻게 되는가"를 반드시 붙인다

preHandle은 컨트롤러 실행 전이고, false를 반환해 요청을 차단할 수 있다. 인가와 선행 검증의 자리다.

postHandle은 컨트롤러가 정상 완료된 뒤, 뷰 렌더링 전이다. 예외가 나면 아예 호출되지 않는다. ModelAndView를 손보는 용도라 REST API에서는 쓸 일이 거의 없다.

afterCompletion은 요청 처리가 끝난 뒤 예외가 나도 항상 호출된다. 자원 정리, 소요 시간 기록처럼 반드시 실행돼야 하는 일의 자리다.

"정리 로직을 postHandle에 두면 예외 경로에서 조용히 누수된다"까지 말하면 가산점이다. try-finally의 finally에 해당하는 것이 afterCompletion이라고 대응시키면 기억하기 쉽다.

Filter와 Interceptor 각각 실행 순서는 어떻게 제어하나요? 가산점힌트: 두 계층의 규칙을 말한 뒤, "Security 기준으로 앞/뒤를 설계한다"까지 나아간다

Filter는 FilterRegistrationBean.setOrder() 또는 빈에 붙인 @Order로 정하며, 숫자가 작을수록 바깥쪽(먼저 실행)이다. Spring Security의 필터 체인도 이 순서 체계 안의 한 자리(스프링 부트 기본값 -100)를 차지하므로, "Security보다 앞이어야 하나 뒤여야 하나"를 명시적으로 설계해야 한다 — trace id 필터를 HIGHEST_PRECEDENCE로 두는 것이 그 예다.

Interceptor는 WebMvcConfigurer.addInterceptors에서 등록한 순서대로 preHandle이 실행되고, postHandle과 afterCompletion은 역순으로 실행된다. 먼저 들어간 것이 나중에 나오는 양파 껍질 구조이고, Filter 체인도 같은 모양이다.

Interceptor에서도 요청 본문을 읽을 수 있게 하려면요? 함정힌트: 가능하지만 "언제 읽느냐"가 함정이다

앞단 Filter에서 ContentCachingRequestWrapper로 감싸 두면, 그 뒤 단계는 모두 래퍼를 보므로 Interceptor에서도 캐시에 접근할 수 있다. 요청 객체를 교체하는 일 자체는 Filter가 대신 해 준 것이다.

다만 시점이 함정이다. 래퍼는 아래 단계가 읽어 갈 때 곁에서 받아 적는 물건이라, preHandle 시점에는 아직 아무도 본문을 읽지 않아 버퍼가 비어 있다. 바인딩(@RequestBody)이 끝난 뒤인 afterCompletion에서야 내용이 차 있다.

그래서 "요청 진입 시점에 본문을 반드시 남겨야 한다"면 필터에서 직접 전부 읽어 보관하는 커스텀 래퍼가 필요하다. 이 경우 대용량 업로드 본문까지 메모리에 올리지 않도록 크기 상한을 두는 것이 실무 관례다.

OncePerRequestFilter는 왜 쓰나요? 그냥 Filter를 구현하면 안 되나요? 가산점힌트: 이름 그대로 "요청당 한 번" — 그럼 언제 두 번 돌 뻔했는가

서블릿 컨테이너는 하나의 HTTP 요청 안에서도 디스패치를 여러 번 일으킬 수 있다 — forward·include·ERROR·ASYNC가 그것이다. 설정에 따라 그때마다 필터 체인이 다시 타면 같은 필터가 한 요청에 두 번 이상 실행될 수 있고, 그러면 로그가 두 번 찍히거나 카운터가 두 번 올라가거나 MDC가 덮어써지는 문제가 생긴다.

OncePerRequestFilter는 이미 수행했다는 표시를 요청 속성에 남겨 같은 요청 안에서 본문 로직이 한 번만 돌도록 보장한다. 그래서 스프링 진영의 필터는 대부분 이 클래스를 상속한다.

여기서 6절과 이어지는 포인트: OncePerRequestFilter는 ERROR 디스패치에서는 기본적으로 실행되지 않는다(shouldNotFilterErrorDispatch()가 true). 그래서 필터에서 finally로 MDC를 지워 두었다면 에러 페이지 처리 과정의 로그에는 trace id가 없다 — 관측 설계 시 알고 있어야 할 사각지대다.

CORS 처리를 Interceptor에 두면 왜 문제가 되나요? 가산점힌트: 브라우저가 진짜 요청 전에 보내는 그 요청은 무엇을 달고 오는가

브라우저는 교차 출처 요청 전에 preflight(OPTIONS) 요청을 먼저 보내는데, 이 요청에는 Authorization 헤더나 쿠키 같은 인증 정보가 실리지 않는다. 그래서 인증 필터가 먼저 만나면 401로 막아버리고, 응답에 CORS 헤더가 없으니 브라우저에는 인증 오류가 아니라 CORS 오류로 표시된다 — 원인과 증상이 어긋나 디버깅이 오래 걸리는 전형적인 사고다.

즉 CORS 응답 헤더는 인증보다 앞 계층에서 붙어야 하고, Interceptor는 인증 필터보다 한참 안쪽이라 구조적으로 늦다. "모든 요청을, 인증보다 먼저 덮어야 하는 일"이므로 9-2절 기준에 따라 Filter가 답이다.

Filter에서 인증한 사용자 정보를 컨트롤러까지 어떻게 넘기나요?힌트: 통로는 둘 — 요청 속성과 ThreadLocal. 그리고 둘 다 "정리"가 따라붙는다

통로는 둘이다. ① 요청 속성(request.setAttribute(...))에 담아 뒤 단계에서 꺼내거나, ② ThreadLocal 기반 보관소(Spring Security의 SecurityContextHolder가 그 방식)에 담아 어디서든 꺼낸다.

컨트롤러에서 파라미터로 바로 받고 싶다면 HandlerMethodArgumentResolver를 만들어 @LoginUser User user 같은 형태로 주입하는 것이 스프링다운 방법이다(33-custom-argument-resolver-auth-user.md).

공통 주의점은 정리다. ThreadLocal에 담았으면 요청이 끝날 때 반드시 비워야 한다 — 톰캣은 스레드를 재사용하므로, 안 지우면 다음 요청이 남의 인증 정보를 물려받는 심각한 사고가 된다. 9-4절의 MDC.clear()가 정확히 같은 이유다.

AOP까지 포함하면 셋 중 무엇을 언제 쓰나요? 시니어 변별힌트: "무엇을 알아야 하는가"를 기준으로 세 계층을 나누고, 마지막에 중복 배치 금지 원칙을 붙인다

"무엇을 알아야 하는가"를 기준으로 세 계층을 나눈다.

Filter는 HTTP 요청/응답 객체 자체가 대상이고 스프링 진입 전이어야 할 때다. 인코딩, 인증, 본문 캐싱, trace id가 여기 속한다.

Interceptor는 HTTP 문맥에 더해 핸들러 정보가 필요할 때다. 애너테이션 기반 인가, 핸들러별 감사 로깅이 여기 속한다.

AOP는 HTTP와 무관하게 메서드 단위로 걸어야 할 때다. 서비스 계층 메서드의 인자와 반환값에 접근할 수 있고, 웹이 아닌 진입점 — 스케줄러, 배치, 메시지 컨슈머 — 에도 그대로 적용된다. 반대로 Filter와 Interceptor는 웹 요청에만 걸린다. 트랜잭션과 캐시가 AOP로 구현돼 있는 이유가 이것이다.

트레이드오프도 짚는다. AOP는 프록시 기반이라 같은 클래스 안의 자기 호출에 무력하고, 포인트컷이 넓으면 영향 범위를 파악하기 어렵다. Interceptor는 웹 계층에 묶인다. Filter는 핸들러 문맥이 없어 세밀한 선별이 힘들다.

마무리 원칙 — "트랜잭션·캐시처럼 도메인 메서드에 붙는 관심사는 AOP, HTTP 경계의 관심사는 Filter/Interceptor로 나누되, 같은 관심사를 두 계층에 중복해 두지 않는다." 중복해서 걸어 두면 나중에 "왜 로그가 두 번 찍히지"를 추적하는 데 시간을 쓰게 된다.

비동기 컨트롤러(Callable·DeferredResult)에서는 훅과 trace id가 어떻게 되나요? 시니어 변별힌트: 요청 처리 스레드가 먼저 반환된다 — 그럼 ThreadLocal에 담긴 것은?

컨트롤러가 Callable이나 DeferredResult를 반환하면 서블릿 요청 처리 스레드는 결과를 기다리지 않고 먼저 반환된다. 이때 postHandle·afterCompletion 대신 AsyncHandlerInterceptor의 afterConcurrentHandlingStarted가 호출되고, 결과가 준비되면 ASYNC 디스패치로 다시 들어와 나머지 처리가 이어진다.

여기서 관측이 깨진다. MDC는 스레드마다 따로 있는 저장소이므로, 실제 작업이 도는 다른 스레드에는 trace id가 따라가지 않는다. 그래서 비동기 구간의 로그만 trace id가 비어 흐름이 끊긴다.

대응은 스레드 풀에 컨텍스트 복사 로직(TaskDecorator 등)을 걸어 MDC를 넘겨주는 것이다. 원리는 9-4절과 같다 — "trace id는 요청이 지나가는 모든 실행 경로에 심어야 하고, 경로가 갈라지는 지점마다 명시적으로 옮겨야 한다."

한 줄 요약
Filter는 서블릿 컨테이너 소속이라 DispatcherServlet 바깥에서 모든 요청을 덮고 요청/응답 객체 자체를 교체할 수 있으며(인코딩·인증·본문 캐싱·trace id), Interceptor는 Spring MVC 소속이라 HandlerMethod를 알고 있어 핸들러별 선별 처리에 적합하다(애너테이션 기반 인가·감사 로깅) — 배치 기준은 "모든 요청을 스프링 밖에서 덮어야 하면 Filter, 핸들러를 알고서 처리해야 하면 Interceptor"이고, 이 경계는 예외에도 그대로 적용되어 Filter의 예외는 DispatcherServlet에 닿은 적이 없으므로 @ControllerAdvice가 아니라 톰캣의 에러 페이지 처리로 넘어가며, 잘못 놓으면 인증 실패 응답에만 trace id가 빠지는 관측 사각지대가 생긴다.
