HikariCP 커넥션 고갈 진단
증상은 하나, 원인은 넷 — "오래 점유"와 "미반환(누수)"을 구분하라

면접 질문: "HikariCP에서 커넥션 고갈(connection pool exhaustion)이 발생했습니다. 원인 후보와 진단 방법은?"

핵심 관전 포인트 — Connection is not available, request timed out after 30000ms는 증상이 하나인데 원인은 여럿인 전형적 상황이라, 이 질문이 보는 것은 지식이 아니라 진단 방법론이다. 고갈의 물리는 하나뿐이다 — 필요 동시 점유 수 L = λ × W가 풀 크기 c를 넘으면 나머지는 대기한다. 그래서 원인은 λ가 커졌거나(① 풀 크기 부족), W가 커졌거나(② 느린 쿼리·락 대기, ③ 트랜잭션 안 외부 호출·CPU 작업), W가 아예 무한대이거나(④ 커넥션 누수) 넷뿐이다. 진단의 결정적 갈림은 "오래 점유"와 "미반환"의 구분이고, 이건 시계열 모양으로 가른다 — 트래픽이 빠졌는데도 hikaricp.connections.active가 max에 붙어 안 내려오면 누수, 트래픽과 함께 오르내리면 점유다. 앱 메트릭으로 계열을 좁힌 뒤 PostgreSQL의 pg_stat_activity로 교차 확인하는데, 가장 자주 나오는 범인이 state = 'idle in transaction' — 커넥션과 락을 쥐는 것에 더해 VACUUM까지 막아 테이블 블로트를 만든다. 누수 지점은 leakDetectionThreshold가 대여 시점 스택트레이스로 코드 라인까지 잡아주고, 스레드 덤프로 "기다리는 스레드(피해자)"와 "쥐고 있는 스레드(용의자)"를 갈라 읽어 교차 확인한다. 그리고 처방까지 가야 답이 완성된다 — 풀 확대는 ①일 때만 정답이고, W가 원인이면 대기 줄이 DB 앞으로 옮겨질 뿐이며(점유가 50ms → 3초가 되면 500 TPS에 커넥션 1,500개가 필요하다), 누수면 마르는 시각만 미룬다.
  • 1
    원인을 외워서 나열하지 않고 식에서 유도한다 — 고갈의 물리는 하나다. L = λ × W > c. 그러므로 원인은 λ가 커졌나(①), W가 DB 안에서 커졌나(②), W가 DB 밖에서 커졌나(③), W가 무한대인가(④) 넷뿐이고, 계열이 정해지면 처방도 자동으로 갈린다.
  • 2
    진단은 코드가 아니라 관측에서 시작한다 — ① 예외 로그의 괄호(total/active/idle/waiting) → ② Hikari 메트릭 시계열(active·usage) → ③ PostgreSQL pg_stat_activity로 교차 확인 → ④ 그다음에야 코드. 결정적 갈림은 하나의 질문이다 — "트래픽이 빠졌을 때 active가 따라 내려오는가." 안 내려오면 누수다.
  • 3
    처방은 계열마다 다르고, 풀 확대는 ①일 때만 정답이다 — ②③이면 산술적으로 감당이 안 되고(W가 3초면 500 TPS에 1,500개 필요, max_connections 기본값은 100) DB 경합이 늘어 W가 더 나빠지는 양의 되먹임이 생긴다. ④면 죽는 시각만 뒤로 밀린다. 남는 답은 W를 줄이는 것이고, 그동안 전면 장애로 번지지 않게 connection-timeout을 짧게 잡아 연쇄를 끊는다.

0. 질문 + 출제 의도

질문: "HikariCP에서 커넥션 고갈(connection pool exhaustion)이 발생했습니다. 원인 후보와 진단 방법은?"

출제 의도: 증상(timeout 로그)은 하나인데 원인은 여럿(누수, 느린 쿼리, 트랜잭션 내 외부 호출, 풀 크기)인 전형적 상황이다. 원인 후보를 나열하고 각각의 배제 방법을 말할 수 있는지 — 진단 방법론 자체를 평가한다.

이 페이지가 겨냥하는 약점 세 가지 ① 원인을 목록으로 외워 나열하는 것 → 2절에서 L = λ × W > c 하나로 원인 넷을 유도한다. 외운 목록과 유도한 목록은 면접에서 완전히 다르게 들린다.
② "누수 같습니다"를 근거 없이 말하는 것 → 5절에서 "오래 점유"와 "미반환"을 시계열 모양으로 가르고, 6·8절에서 DB 뷰·스택트레이스·스레드 덤프로 교차 확인하는 절차를 만든다.
③ 진단 없이 "풀을 늘리자"로 직행하는 것 → 9절에서 계열별로 계산해 반박한다. 풀 확대는 진단의 결과여야지 진단의 대체물이면 안 된다.

이 문서의 기준: Spring Boot 3.x + HikariCP 5.x + PostgreSQL 14 이상. DB 진단 어휘는 PostgreSQL 기준이고 MySQL과 갈리는 지점만 한 줄로 대비한다.  /  이 문서의 자리: 여기는 "이미 잡아놨는데 왜 고갈됐는가"(진단)다. "애초에 얼마로 잡을 것인가"(산정)는 25-thread-pool-connection-pool-sizing.md가 앞에 있다.

한 문장 비유 — 매장 컵 10개짜리 카페 매장용 컵이 10개(= maximumPoolSize c)뿐인 카페를 떠올리면 네 계열이 그대로 대응된다. ① 손님이 갑자기 몰린다(λ↑ — 컵 회전은 정상인데 개수가 모자람)  ·  ② 설거지가 느려진다(W↑ — 컵이 늦게 돌아온다)  ·  ③ 손님이 컵을 든 채 밖에 전화하러 나간다(W↑ — 컵은 안 쓰면서 점유만 한다)  ·  ④ 손님이 컵을 들고 집에 간다(W = ∞ — 영영 안 돌아온다). 컵을 더 사는 것(풀 확대)이 해결하는 건 ①뿐이고, ④에서는 재고가 마르는 시각만 미룰 뿐 반드시 마른다.

1. 먼저 로그 한 줄을 끝까지 읽는다

장애 채널에 올라오는 것은 보통 이 예외다. 대부분 앞부분만 읽고 넘어가는데, 괄호 안이 진단의 절반이다. HikariCP는 타임아웃 예외를 던질 때 그 순간의 풀 통계를 함께 찍어 준다.

LOG 이 한 줄에 이미 네 개의 사실이 들어 있다
java.sql.SQLTransientConnectionException:
  HikariPool-1 - Connection is not available, request timed out after 30001ms
  (total=10, active=10, idle=0, waiting=27)
평상시 통계도 남길 수 있다 — 장애 "전후 추이"를 보려면 이게 있어야 한다 com.zaxxer.hikari.pool.HikariPool 로거를 DEBUG로 켜 두면 HikariCP가 30초마다 같은 형식의 통계를 평상시에도 찍는다. 장애 시점의 스냅샷 하나만으로는 "원래 그랬는지 갑자기 그렇게 된 것인지"를 알 수 없다.

      (total=10, active=3, idle=7, waiting=0)   ← 평상시 모습. idle이 있고 waiting이 0이다

2. 고갈의 물리는 하나뿐이다 — L = λ × W

원인이 넷이라고 하지만, 고갈이 일어나는 메커니즘 자체는 하나다. 25번 문서의 Little's law를 그대로 가져오면 이렇게 된다.

모든 것이 여기서 나온다 — 이 식 하나만 쥐고 있으면 된다

필요한 동시 점유 수   L = λ × W    vs    풀 크기 c
λ (람다)
초당 요청 수
들어오는 속도
W
커넥션 점유 시간
하나가 커넥션을 잡고 있는 시간 (대여 → 반환)
c
maximumPoolSize
동시에 내줄 수 있는 개수
L ≤ c
대기 없음. waiting = 0
L > c
나머지 (L − c)개가 getConnection()에서 대기 → connectionTimeout을 넘기면 SQLTransientConnectionException

이 틀이 왜 유용한가. 어떤 현상을 보든 "이건 λ 얘기인가, W 얘기인가, c 얘기인가"로 분류할 수 있고, 그러면 처방도 자동으로 갈리기 때문이다. 원인 목록을 외우는 것과 이 식에서 유도하는 것은 면접에서 완전히 다르게 들린다.

암기 장치 — 원인 4계열은 "람 · 안 · 밖 · 무한"

람다가 커졌나(①)  ·  W가 안에서 커졌나(②)  ·  W가 밖에서 커졌나(③)  ·  W가 무한인가(④)

면접에서 "누수, 느린 쿼리, 외부 호출, 풀 크기요"라고 목록으로 답하는 것과, "고갈은 L = λW > c일 때만 일어나므로 후보는 λ·W·c 셋에 W = ∞를 더해 넷입니다"라고 유도해서 답하는 것은 완전히 다르게 들린다.

3. 원인 4계열 — 각각의 전형적인 모양

3-1. ① 풀 크기 부족 — 정상 동작이 용량을 넘어선 경우

가장 단순한 계열이다. 코드에 아무 문제가 없고 커넥션도 제때 반환되는데, 동시에 필요한 개수가 풀 크기를 넘었을 뿐이다.

풀 크기 c = 10, 커넥션 점유 W = 50ms
  이 풀이 감당하는 최대 처리량  λ_max = c / W = 10 / 0.05s = 200 TPS

  트래픽 150 TPS  ->  L = 150 × 0.05 = 7.5개   (여유 있음)
  트래픽 300 TPS  ->  L = 300 × 0.05 = 15개    (10개를 넘음 -> 고갈)

전형적인 모양은 이렇다. 프로모션·푸시 발송·배치와 겹친 시각에 트래픽이 평소의 2~3배로 뛰고, 그 시간대에만 고갈이 나며, 트래픽이 빠지면 저절로 정상으로 돌아온다. 쿼리는 여전히 빠르고 DB CPU도 한가하다.

이 계열의 결정적 특징 어떤 커넥션도 오래 붙들려 있지 않다. 그래서 hikaricp.connections.usage(점유 시간)가 평소와 같은데 active만 max에 붙어 있다면 ①일 가능성이 높다. 4절에서 이 지표 하나가 계열을 어떻게 가르는지 본다.

3-2. ② 느린 쿼리·락 대기 — DB "안"에서 W가 늘어난 경우

같은 트래픽인데 쿼리 한 건이 오래 걸려 커넥션이 오래 잡히는 경우다. W가 늘면 L이 비례해 늘고, c는 그대로이므로 고갈이 난다.

평소  500 TPS × 0.05s =  25개 필요
느린 쿼리로 점유가 300ms가 되면
      500 TPS × 0.30s = 150개 필요   <- 풀이 36개여도 즉시 마른다

원인은 대개 셋 중 하나다.

인덱스 누락 · 실행 계획 변경
데이터가 쌓이면서 옵티마이저가 인덱스 스캔에서 순차 스캔으로 계획을 바꾸는 일이 실제로 일어난다. 어제까지 5ms였던 쿼리가 오늘 800ms가 된다.
락 대기
다른 트랜잭션이 같은 행에 UPDATE나 SELECT ... FOR UPDATE를 걸고 있으면 내 쿼리는 시작조차 못 하고 서 있다. 쿼리 자체는 빠른데 대기만 긴 상태라 슬로우 쿼리 로그로는 원인이 안 보인다.
DB 자체의 포화
커넥션이 많아 DB 안에서 경합이 나는 상황. 풀을 늘린 것이 원인이 되어 W가 늘어난 경우다 — 9절의 되먹임이 여기서 시작된다.
락 대기가 슬로우 쿼리 로그로 잘 안 잡히는 이유 로그는 보통 실행 시간을 기준으로 하는데, 대기 시간도 실행 시간에 포함되어 찍힌다. 그래서 "8초 걸린 UPDATE"라는 사실은 남지만 "그중 7.9초는 남을 기다린 시간"이라는 것은 로그만으로 안 보인다. 그래서 ②의 진단은 6절의 wait_event_type과 pg_blocking_pids()로 넘어간다.

3-3. ③ 트랜잭션 내 외부 호출·CPU 작업 — DB "밖"에서 W가 늘어난 경우

②와 결과는 같지만 원인 위치가 정반대다. 쿼리는 5ms에 끝났는데 커넥션은 3초 동안 잡혀 있는 경우다.

before 트랜잭션 경계 안에 외부 API 호출이 들어와 있다
@Transactional
public Order place(OrderRequest req) {
    Order order = orderRepository.save(Order.of(req));여기서 커넥션이 잡힌다
    // 이 save 로 트랜잭션이 시작되며 커넥션이 잡혔고,
    // 메서드가 끝날 때까지 그 커넥션은 반환되지 않는다.
    // 트랜잭션 경계 = 커넥션 점유 구간이기 때문이다.

    PaymentResult result = paymentClient.charge(order);평소 300ms
    // 이 300ms 동안 커넥션은 아무 쿼리도 보내지 않으면서
    // 대여 상태로 남아 있다. DB 입장에서는
    // 'idle in transaction' 으로 보인다 (7절).
    // PG사가 느려져 3초가 되면? 점유도 그대로 3초가 된다.

    order.markPaid(result);
    return order;
}
after 커넥션을 쥐는 구간과 남을 기다리는 구간을 분리한다
// @Transactional 이 없다 — 경계를 안쪽으로 옮겼다
public Order place(OrderRequest req) {
    // ① 짧은 트랜잭션 — PENDING 저장 후 즉시 커밋
    Order order = orderService.createPending(req);약 5ms 점유 후 반납

    // ② 트랜잭션 밖 — 3초가 걸려도 커넥션 0개
    PaymentResult result = paymentClient.charge(order);

    // ③ 다시 짧은 트랜잭션 — 결과 반영 후 커밋
    return orderService.applyResult(order.getId(), result);
}
// 점유 3,000ms -> 5ms 두 번 = 1/300
// 같은 500 TPS 에서 필요 커넥션 1,500개 -> 5개
// 풀 크기를 손대지 않고 W 만으로 문제를 없앤 것이다.

반드시 알아야 하는 전제 — 트랜잭션 경계 = 커넥션 점유 구간

Spring에서 트랜잭션 경계와 커넥션 점유 구간은 같다. @Transactional 메서드에 진입해 첫 DB 접근이 일어나는 순간 커넥션이 잡혀 TransactionSynchronizationManager의 ThreadLocal에 묶이고, 메서드가 끝나 커밋/롤백될 때까지 그 스레드에 붙어 있다. 중간에 DB를 안 쓰는 구간이 있어도 반환되지 않는다(24-transaction-synchronization-connection-binding.md).

그래서 트랜잭션 안에 들어간 모든 것이 커넥션 점유 시간에 그대로 더해진다 — 외부 API 호출, 파일 I/O, 무거운 연산, 심지어 Thread.sleep까지

이 계열의 위험은 평소에는 안 터진다는 데 있다. 300ms면 500 TPS에서 150개가 필요해 이미 아슬아슬하지만, 트래픽이 낮은 서비스에서는 몇 달 동안 아무 일 없이 돌아간다. 그러다 외부 PG사가 느려지는 날 한 번에 터진다. 상세한 장애 시뮬레이션은 22-external-api-call-inside-transaction.md에 있다.

3-4. ④ 커넥션 누수 — 반환 자체가 없는 경우

앞의 셋은 커넥션이 결국은 돌아온다. 누수는 영영 안 돌아온다.

before 수동으로 얻고, 정상 경로에서만 닫는다

오해 하나 걷어내기 — Connection.close()는 커넥션을 끊는 것이 아니다

HikariCP가 돌려주는 것은 진짜 커넥션이 아니라 그것을 감싼 프록시(HikariProxyConnection)이고, 그 프록시의 close()는 "풀에 반납한다"는 뜻이다. 그래서 close를 빠뜨리면 커넥션이 끊기는 게 아니라 대여 상태로 영원히 남는다 — 이것이 누수라는 이름의 정확한 의미다.

비유하자면 close()는 책을 폐기하는 것이 아니라 도서관에 반납하는 것이다. 반납을 안 하면 책이 사라지는 게 아니라 영원히 내 이름으로 대출 중이고, 도서관 재고만 한 권씩 줄어든다.

누수가 무서운 이유는 누적된다는 점이다. 점유 시간 문제는 트래픽이 빠지면 저절로 회복되지만, 누수는 요청이 들어올 때마다 남은 커넥션이 하나씩 줄어들 뿐 절대 회복되지 않는다.

4. 관측 ① 앱 — Hikari 메트릭 네 개면 대부분 갈린다

진단 순서의 대원칙 — "로 · 메 · 디 · 코"

로그 괄호 → 메트릭 시계열 → DB 뷰(pg_stat_activity) → 그다음에야 코드

코드부터 뒤지지 말고, 장애 중인 장비에서 관측 데이터를 먼저 본다. 코드 리뷰는 후보를 좁힌 다음에 하는 일이다. 면접에서 "일단 코드를 보겠습니다"로 시작하면 그 순간 감점이다.

가장 자주 놓치는 지점 — "지표에 안 나타난다"는 것 자체가 지표다

usage는 반환 시점에 기록되는 타이머다. 대여할 때 시작하고 반납할 때 멈춰서 값을 남긴다. 누수된 커넥션은 반납이 없으므로 이 타이머에 아무것도 남기지 않는다.

"누수는 지표에 안 나타난다"가 아니라 "안 나타난다는 것 자체가 누수의 지표"다

같은 논리가 APM 트레이스에도 적용된다 — 오래 점유(②③)는 긴 스팬으로 보이지만, 누수(④)는 스팬이 닫히지 않아 아예 안 잡힌다.

6. 관측 ② DB — pg_stat_activity로 교차 확인한다

앱 메트릭으로 계열을 좁혔으면 DB에서 확인한다. PostgreSQL에서 지금 무슨 일이 벌어지는지 보는 창은 pg_stat_activity 뷰 하나다. 백엔드 프로세스(= 커넥션) 하나가 한 행이다. 먼저 전체 그림부터 본다.

SQL 1단계 — 상태별로 몇 개씩 있는가 (여기서 이미 계열이 갈린다)
-- 이 DB에 붙은 커넥션이 어떤 상태로 몇 개씩 있는가
SELECT state, count(*)
  FROM pg_stat_activity
 WHERE datname = current_database()
 GROUP BY state
 ORDER BY 2 DESC;

state뜻고갈과의 관계
active지금 쿼리를 실행 중많고 오래 지속되면 ②
idle트랜잭션 없이 놀고 있음정상. 풀에 반납된 커넥션이 여기 있다

idle in transaction (aborted)위와 같은데 이미 오류가 나서 롤백만 남은 상태예외 처리 누락 의심
SQL 2단계 — 오래 도는 쿼리를 찾되, "무엇을 기다리는지"까지 본다
-- 1초 넘게 돌고 있는 쿼리
SELECT pid,
       now() - query_start        AS running_for,
       wait_event_type, wait_event,   -- 무엇을 기다리는가 (CPU면 NULL)
       left(query, 120)           AS query
  FROM pg_stat_activity
 WHERE state = 'active'
   AND now() - query_start > interval '1 second'

한 컬럼이 "느리다"의 정체를 가른다 — wait_event_type

다른 트랜잭션을 기다리는 중 → 6-1절의 pg_blocking_pids()로 범인을 지목한다

"느리다"의 원인이 계산인지 대기인지를 이 한 컬럼이 갈라 준다. 슬로우 쿼리 로그로는 이 구분이 안 된다(3-2절).

6-1. 락 대기 추적 — pg_blocking_pids()로 "누가 누구를 막는가" 가산점

②의 하위 유형인 락 대기는 "누가 누구를 막고 있는가"를 알아야 진단이 끝난다. PostgreSQL 9.6부터 이걸 한 함수로 해결할 수 있다.

SQL 피해자 쪽 — 지금 잠금 때문에 서 있는 세션
SELECT a.pid,
       now() - a.query_start        AS waiting_for,
       a.wait_event_type, a.wait_event,
       pg_blocking_pids(a.pid)      AS blocked_by,   -- 나를 막고 있는 pid 배열
       left(a.query, 100)           AS my_query
  FROM pg_stat_activity a
 WHERE cardinality(pg_blocking_pids(a.pid)) > 0
 ORDER BY waiting_for DESC;
SQL 용의자 쪽 — 막고 있는 세션을 되짚어 조회한다
-- 여기서 state 가 'idle in transaction' 으로 나오면 원인은 ③이다
SELECT pid, state, now() - state_change AS in_state_for, left(query, 120)
  FROM pg_stat_activity
 WHERE pid = ANY (
        SELECT unnest(pg_blocking_pids(pid))
          FROM pg_stat_activity
         WHERE cardinality(pg_blocking_pids(pid)) > 0);
이 한 갈래를 짚으면 이 질문은 사실상 통과다 막는 쪽이 idle in transaction으로 나오는 순간 진단이 끝난다. "쿼리도 안 하면서 락을 쥐고 있는 트랜잭션"이므로 원인은 ③이고, 코드에서 트랜잭션 안에 들어간 외부 호출을 찾으면 된다. ②로 보이던 락 대기의 진짜 원인이 ③이었다는 것 — 계열이 서로를 만들어낸다는 사실이 여기서 드러난다.
MySQL이라면 가산점 대응되는 것이 SHOW PROCESSLIST 또는 information_schema.processlist이고, idle in transaction에 해당하는 상태는 Sleep이면서 트랜잭션이 열려 있는 세션이라 information_schema.innodb_trx를 함께 봐야 한다. PostgreSQL 쪽이 한 뷰에서 다 보인다는 점이 진단상 유리하다.

7. idle in transaction이 왜 특별히 위험한가 시니어 변별

idle in transaction은 BEGIN은 했는데 아직 COMMIT도 ROLLBACK도 안 했고, 지금 이 순간 실행 중인 쿼리도 없는 상태다. 3-3절의 코드가 외부 API를 호출하는 300ms 동안 DB에서 보이는 모습이 정확히 이것이다.

"쿼리를 안 보내고 있으니 DB는 놀고 있는 것 아닌가"라고 생각하기 쉽지만 정반대다. 세 가지를 동시에 붙잡고 있다.

(1) 커넥션을 붙잡는다
앱 쪽에서는 Hikari 커넥션 하나가 대여 중이고, DB 쪽에서는 백엔드 프로세스 하나가 살아 있다. 이게 고갈로 직결된다.
(2) 획득한 락을 붙잡는다
트랜잭션이 끝나야 락이 풀린다. UPDATE를 한 번이라도 했다면 그 행의 배타 락을 계속 쥐고 있고, 다른 트랜잭션들이 그 뒤에 줄을 선다. 하나의 느린 외부 API 호출이 무관한 요청 수십 개를 세우는 경로가 여기다.
(3) VACUUM을 방해한다
PostgreSQL 특유의 문제이고 가장 늦게 발견되는 피해다. 결과는 테이블 블로트 — 즉 ③이 방치되면 결국 ②를 유발한다.

7-1. 세 번째 피해를 정확히 — MVCC와 VACUUM

먼저 전제를 깔자. PostgreSQL은 MVCC(다중 버전 동시성 제어)를 쓴다. UPDATE는 기존 행을 덮어쓰지 않고 새 버전의 튜플을 추가하며, 옛 버전은 그것을 아직 봐야 하는 트랜잭션이 있을 수 있으므로 그대로 남겨 둔다. 이렇게 남은 옛 버전을 죽은 튜플(dead tuple)이라 하고, 아무도 안 보게 되면 VACUUM이 회수해 공간을 재사용한다.

여기서 "아무도 안 본다"의 기준이 문제다. 기준은 현재 살아 있는 트랜잭션 중 가장 오래된 것의 스냅샷이다. 그보다 나중에 죽은 튜플은 그 오래된 트랜잭션이 볼 수도 있으므로 회수할 수 없다.

정확히 말하면 가산점 — BEGIN만 한 트랜잭션은 VACUUM을 막지 않는다

BEGIN만 하고 쿼리를 한 번도 실행하지 않은 트랜잭션은 아직 스냅샷을 잡지 않아 VACUUM을 막지 않는다

문제가 되는 것은 이미 쿼리를 실행한 뒤 열린 채로 방치된 트랜잭션이고, 3-3절 같은 실무 코드는 전부 여기 해당한다(save를 먼저 하고 외부 API를 부른다). 그래서 실무에서는 이 예외 조항이 위안이 되지 않는다.

SQL 방치된 세션을 찾는다 — state_change가 핵심 컬럼
-- 10초 넘게 idle in transaction 인 세션
SELECT pid,
       usename, application_name, client_addr,
       now() - state_change AS idle_in_tx_for,   -- 이 상태로 얼마나 있었나
       now() - xact_start   AS tx_age,           -- 트랜잭션 전체 나이
       left(query, 120)     AS last_query        -- 마지막으로 실행한 쿼리
  FROM pg_stat_activity
 WHERE state = 'idle in transaction'
   AND state_change < now() - interval '10 seconds'
 ORDER BY state_change;
state_change
현재 상태로 전환된 시각이므로 now() - state_change가 곧 "이 상태로 얼마나 방치됐는가"다.
query
지금 실행 중인 쿼리가 아니라 마지막으로 실행한 쿼리다. 트랜잭션이 어디까지 진행하다 멈췄는지를 알려주므로 코드의 어느 지점인지 특정하는 데 결정적이다.

VACUUM 방해 여부까지 확인하려면 가장 오래된 스냅샷을 본다.

SQL backend_xmin이 오래될수록 회수하지 못하는 튜플이 많다
SELECT pid, state, backend_xmin, age(backend_xmin) AS xmin_age,
       now() - xact_start AS tx_age
  FROM pg_stat_activity
 WHERE backend_xmin IS NOT NULL
 ORDER BY age(backend_xmin) DESC
 LIMIT 10;

idle_in_transaction_session_timeout = '30s'
  -- idle in transaction 이 이 시간을 넘으면 그 세션을 종료시킨다.
  -- 기본값 0(비활성). PostgreSQL 9.6 이상.

statement_timeout = '5s'    -- 쿼리 하나가 이 시간을 넘으면 취소. 기본 0.
lock_timeout      = '2s'    -- 락을 이 시간 안에 못 얻으면 실패. 기본 0.
idle_in_transaction_session_timeout을 켜면 ③의 피해가 무한정 번지는 것을 DB 쪽에서 끊을 수 있다. 대신 애플리케이션은 커넥션이 끊긴 것으로 보이므로 예외 처리가 필요하다. 근본 대책이 아니라 방화벽이라는 점을 분명히 하고 쓴다.

8-1. leakDetectionThreshold — 코드의 어느 줄이 새는가

계열이 ④로 좁혀졌으면 코드의 어느 줄이 새는지를 찾아야 한다. HikariCP가 이를 위한 기능을 내장하고 있다.

YAML 상시 설정을 권장한다 (8-2에서 비용을 따진다)
spring:
  datasource:
    hikari:

      # 최소 2000ms 이며 maxLifetime 보다 크면 HikariCP 가 무시한다. 0 이면 비활성(기본).

동작 원리를 알아야 값을 제대로 잡을 수 있다. HikariCP는 커넥션이 대여될 때마다 다음 두 가지를 한다.

1
그 순간의 스택트레이스를 담은 예외 객체를 하나 만들어 둔다. 던지지 않고 보관만 한다. 이게 나중에 "어디서 빌려갔는지"를 알려줄 증거다.
2
임계 시간 뒤에 실행될 태스크를 내부 스케줄러에 등록한다. 커넥션이 제때 반환되면 이 태스크는 취소된다. 반환 전에 태스크가 먼저 실행되면 → 보관해 둔 스택트레이스를 WARN으로 찍는다.

8-2. 운영에 상시 켜도 되는가 가산점

결론 — 켜도 된다

  • 비용은 대여마다 예외 객체 1개(스택트레이스 채우기) + 스케줄 태스크 1개다.
  • 그런데 커넥션 대여 자체가 이미 그보다 훨씬 비싼 작업이고, getConnection() 뒤에는 대개 수 ms 이상 걸리는 쿼리가 따라온다. 상대적으로 무시할 만한 비율.
  • 실무에서 상시 켜 두는 것이 일반적이다.

다만 "공짜"라고 말하면 안 된다

  • 스택트레이스를 채우는 것은 공짜가 아니다.
  • 비활성(0)일 때는 이 경로 자체를 타지 않아 정말로 비용이 0이다.
  • 그래서 정확한 표현은 "끄면 빨라진다"가 아니라 "켜도 거의 안 느려진다"다.
오탐 주의 — 그런데 오탐도 정보 가치가 있다 이 로그는 "누수 확정"이 아니라 "이 획득 지점이 임계 시간 이상 커넥션을 물고 있었다"는 사실만 말한다. 배치의 정상적인 장기 점유도 걸린다. 다만 오탐이라도 버릴 정보가 아니다 — 커넥션을 오래 물고 있다는 사실 자체가 ③의 신호이기 때문이다. 대응은 임계값을 올리는 것보다 애초에 그 작업의 점유를 줄이는 것(청크 단위 커밋)이 낫다.

9. 처방 — 계열별 대응과 "풀을 늘린다"가 대개 오답인 이유

진단만 하고 끝나면 절반이다. 계열을 좁혔으면 처방이 달라져야 하고, 계열마다 처방이 다르다는 사실 자체가 진단을 하는 이유다.

계열별 처방 — 오른쪽 열이 식의 어느 항을 건드리는가를 말한다
계열처방처방의 성격
① 풀 크기 부족풀 확대 (단 DB 상한 확인) 또는 인스턴스 증설c를 키운다
② 느린 쿼리·락 대기인덱스·실행 계획 교정, 락 범위 축소, statement_timeout·lock_timeoutW를 줄인다
③ 트랜잭션 내 외부 호출트랜잭션 경계 밖으로 빼기, 상태 기반 재설계(PENDING), 아웃박스W를 줄인다
④ 커넥션 누수try-with-resources, 수동 getConnection() 제거 — 우회로 없음W = ∞를 없앤다
②의 처방에서 자주 빠뜨리는 것 — 타임아웃은 성능 설정이 아니다 statement_timeout과 lock_timeout을 설정하면 최악의 W에 상한이 생긴다. 이게 중요한 이유는 L = λ × W 때문이다 — W에 상한이 없으면 L에도 상한이 없고, 그러면 어떤 c로도 방어가 안 된다. 타임아웃은 성능 설정이 아니라 W의 상한을 선언하는 안전장치다.

9-1. ②③일 때 — 산술적으로 감당이 안 된다

인출 대상 — 목표 500 TPS 에서 필요한 커넥션 수 = 500 × W

25개
W = 50ms (정상)
150개
W = 300ms
500개
W = 1초
1,500개
W = 3초
W가 60배 나빠지면 필요 커넥션도 60배 — 1,500개를 꽂을 수 있는 PostgreSQL은 실무에 없다

max_connections 기본값이 100이고, 늘린다 해도 커넥션마다 백엔드 프로세스가 하나씩 붙으므로 DB 서버가 먼저 무너진다. 앱 인스턴스가 6대면 6 × 500 = 3,000개가 되어 PostgreSQL이 접속 자체를 거부한다(FATAL: sorry, too many clients already).

그리고 늘리면 더 나빠진다. 25번 문서 3-3에서 본 그대로다.

9-2. ④일 때 — 죽는 시각만 미룬다

계산은 이미 3-4절에서 끝났다

  • 누수 속도 분당 5개 → 풀 10이면 2분, 50이면 10분, 100이면 20분.
  • 누수 속도는 풀 크기와 무관하다. 새는 코드가 그대로면 새는 속도도 그대로다.

더 큰 손해는 따로 있다

  • "재시작하니 괜찮아졌다", "풀 늘렸더니 며칠 갔다"는 경험이 쌓이면서 진짜 원인을 영영 안 찾게 된다.
  • 그사이 재발 주기라는 가장 좋은 단서도 흐려진다.

이 절의 결론 한 줄

풀 확대는 진단의 결과여야지, 진단의 대체물이면 안 된다

"고갈 났으니 늘리자"는 ①이라는 진단을 이미 내렸다는 뜻인데, 대개는 그 진단을 하지 않은 채로 나온 말이다. 그리고 ①이 맞더라도 그냥 늘리면 안 된다 — 앱 쪽 계산값과 DB 쪽 상한 중 작은 쪽이 실질 상한이고, 앱 인스턴스 수를 곱한 총합이 PostgreSQL max_connections를 넘지 않아야 한다(25-thread-pool-connection-pool-sizing.md).

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

고갈의 물리를 한 줄로?
L = λ × W > c. 필요 동시 점유 수가 풀 크기를 넘으면 나머지가 대기하고, connectionTimeout을 넘기면 예외가 난다.
원인 4계열은?
람 · 안 · 밖 · 무한 — λ↑(①) / W↑ DB 안(②) / W↑ DB 밖(③) / W = ∞(④).
로그 괄호 네 개는?
total · active · idle · waiting. total=10이면 풀 크기를 한 번도 안 건드렸다는 뜻(기본값).
누수와 점유를 가르는 질문은?
"트래픽이 빠졌을 때 active가 따라 내려오는가." 안 내려오면 누수.
usage에 기록이 없다는 것은?
반환 시점에 기록되는 타이머이므로, 기록이 없다는 것은 반환이 없다는 뜻 = 누수. "안 나타나는 것 자체가 지표."
pending의 정상값은?
0. 그래서 알람 임계를 정하기 가장 쉬운 지표다. 0보다 크면 이미 고갈 중.
idle in transaction의 3중 피해는?
커넥션을 쥔다 · 락을 쥔다 · VACUUM을 막는다(→ 블로트 → ②를 유발).
풀 확대가 정답인 경우는?
①일 때만. ②③은 산술적으로 감당 불가 + 되먹임, ④는 죽는 시각만 미룸.
500 TPS 에 W = 3초면?
커넥션 1,500개 필요. PostgreSQL max_connections 기본값은 100.
상한 4종은?
statement_timeout · lock_timeout · idle_in_transaction_session_timeout · connection-timeout. 앞 셋은 기본 0(무제한), 마지막은 30초.
누수 탐지 임계값 잡는 규칙은?
usage p99보다 넉넉히 위, 최소 2,000ms, maxLifetime(기본 30분)보다 크면 무시된다.
스레드 덤프 두 부류는?
피해자(ConcurrentBag.borrow에서 대기) / 용의자(스택 최상단이 계열을 알려줌). ④면 용의자가 아예 없다.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

장애 상황입니다. 지금 무엇부터 보시겠어요? 필수힌트: 순서 자체가 답이다. "코드를 보겠습니다"로 시작하면 그 순간 감점

관측 → 계열 축소 → 그다음에야 코드 순서로 말한다.

① 예외 로그의 괄호(total, active, idle, waiting)를 읽는다(1절). 풀 크기가 기본값 10인지, 대기 줄이 얼마나 긴지가 즉시 나온다.

② Hikari 메트릭 시계열에서 active와 usage를 본다(4·5절). 트래픽이 빠졌는데 active가 안 내려오면 누수(④)로 직행하고, usage가 평소와 같으면 ①, 늘었으면 ②③이다.

③ pg_stat_activity를 state별로 집계한다(6절). 오래 도는 active가 많으면 ②, idle in transaction이 쌓여 있으면 ③, DB가 한가한데 앱은 고갈이면 ④ 확정이다.

④ 계열이 좁혀진 뒤에야 코드를 본다. ③이면 @Transactional 안의 외부 호출, ④면 leakDetectionThreshold 로그의 스택트레이스부터 본다.

"앱과 DB 양쪽에서 교차 확인한다"는 원칙을 명시적으로 말하면 좋다 — 앱 지표만 보면 ②와 ③이 안 갈리고, DB만 보면 ④를 영영 못 찾는다.

쿼리도 빠르고 DB도 한가한데 커넥션이 계속 마릅니다. 왜죠? 시니어 변별힌트: 이 조합 자체가 지문이다. 결론을 먼저 말하고 근거를 식으로 댄다

이 조합이 나오는 순간 누수(④)로 좁혀야 한다.

근거를 논리로 말할 수 있어야 한다. 고갈은 L = λW > c일 때 일어나는데, DB가 한가하다는 것은 λ도 W도 크지 않다는 뜻이다. 그런데도 c를 다 썼다면, 남은 가능성은 대여된 커넥션이 계산에 잡히지 않는 것 — 즉 반환되지 않는 것뿐이다.

확인 순서는 이렇다.

1. active의 시계열 모양을 본다. 트래픽이 빠졌는데도 max에 붙어 있으면 누수다(5절).
2. usage 타이머에 기록이 없는지 본다. 반환 시점에 기록되는 지표이므로 누수 커넥션은 흔적을 남기지 않는다.
3. leak-detection-threshold를 켜고 대여 지점 스택트레이스를 받는다(8-1).
4. 스레드 덤프에서 "기다리는 스레드는 많은데 쥐고 있는 스레드가 없다"를 확인한다(8-3).
5. 재시작 후 재발 주기를 잰다. 일정한 주기로 정확히 재발하면 누수 속도가 일정하다는 뜻이다.

그리고 누수는 대개 @Transactional 밖에 있다는 것까지 말하면 좋다. Spring이 관리하는 트랜잭션은 반환을 보장하므로, 범인은 dataSource.getConnection()을 직접 부르는 코드나 레거시 JDBC 코드다. 코드를 뒤질 때 어디부터 볼지를 아는 것이 진단 속도를 가른다.

idle in transaction은 왜 위험한가요? 필수힌트: 세 층위로 답하고, 마지막에 "BEGIN만 한 트랜잭션은 예외"를 붙이면 가산점

(1) 커넥션을 쥔다. 트랜잭션이 열려 있는 동안 Hikari 커넥션 하나가 계속 대여 상태다. 이게 고갈로 직결된다.

(2) 락을 쥔다. 이미 UPDATE를 했다면 그 행의 배타 락을 트랜잭션이 끝날 때까지 붙들고 있다. 무관한 요청들이 그 뒤에 줄을 서므로, 하나의 느린 외부 호출이 서비스 전반의 지연으로 번진다.

(3) VACUUM을 막아 테이블 블로트를 만든다. PostgreSQL의 MVCC에서 죽은 튜플은 "가장 오래된 활성 트랜잭션의 스냅샷"보다 최신이면 회수되지 않는다. 30분째 열려 있는 트랜잭션 하나가 그 30분 동안 생긴 모든 죽은 튜플의 회수를 막는다. 결과는 테이블·인덱스 비대화와 스캔 성능 저하 — ③이 결국 ②를 만들어낸다.

정확히 하면 가산점이다. BEGIN만 하고 쿼리를 한 번도 안 한 트랜잭션은 스냅샷이 없어 VACUUM을 막지 않는다. 문제가 되는 것은 쿼리를 한 뒤 열린 채로 방치된 트랜잭션이고, 실무 코드는 대개 여기 해당한다.

대응은 코드 수정(트랜잭션 밖으로 외부 호출 빼기)이 근본이고, idle_in_transaction_session_timeout은 피해 확산을 막는 방화벽이다. 이 구분을 붙여야 답이 완성된다.

고갈 났으니 풀을 늘리면 되지 않나요? 시니어 변별힌트: "①일 때만 정답"이라고 못 박고, 나머지를 계산으로 반박한 뒤 올바른 방향까지

①일 때만 정답이라고 못 박고 나머지를 계산으로 반박한다.

②③이면 산술적으로 감당이 안 된다. 점유 시간이 50ms에서 3초로 늘면 500 TPS를 감당하는 데 커넥션이 1,500개 필요하다. PostgreSQL의 max_connections 기본값은 100이고, 앱 인스턴스가 6대면 총합이 그 몇 배가 된다. 그리고 늘리면 DB 안 경합이 늘어 W가 더 나빠지는 양의 되먹임이 생긴다(9-1). 대기 줄이 사라지는 게 아니라 앱 앞에서 DB 앞으로 옮겨 가는 것이고, DB 앞의 줄이 더 비싸다.

④면 마르는 시간만 미룬다. 분당 5개씩 새는 코드에서 풀을 10에서 100으로 늘리면 2분이 20분이 될 뿐이다. 오히려 진짜 원인을 영영 안 찾게 되는 것이 더 큰 손해다.

그리고 올바른 방향을 함께 제시해야 답이 완성된다. L = λW ≤ c에서 c를 못 늘리면 남는 것은 W를 줄이는 것이다 — 트랜잭션 밖으로 외부 호출 빼기, 인덱스·실행 계획 교정, 락 범위 축소. hikaricp.connections.usage가 그 개선을 직접 측정해 준다.

그럼 maximumPoolSize를 아주 크게 잡아두면 최소한 고갈은 안 나지 않나요? 함정힌트: 커넥션 풀은 병목이면서 동시에 "문지기"다

고갈이 다른 곳으로 옮겨 갈 뿐이다. 커넥션 풀은 병목이면서 동시에 문지기이기도 하다.

풀 크기 10이 하던 일은 "DB에 동시에 10개까지만 보낸다"는 유입 제어다. 이걸 500으로 열면 DB가 500개의 동시 요청을 받게 되고, DB 쪽 경합이 폭증해 모든 쿼리가 같이 느려진다. 일부가 실패하던 것이 전부가 느려지는 것으로 바뀐다.

여기에 총량 계산이 붙는다. 앱 인스턴스가 6대면 6 × 500 = 3,000개다. PostgreSQL은 접속 자체를 거부한다(FATAL: sorry, too many clients already).

"상한은 제약이 아니라 신호 장치"라는 표현까지 쓰면 좋다. 상한이 없으면 시스템은 자기가 과부하라는 사실을 알 방법이 없다(07-traffic-performance/16-backpressure-and-application-points.md).

leakDetectionThreshold를 운영에 상시 켜도 되나요? 가산점힌트: "켜도 된다"로 시작하되, 비용이 정확히 무엇인지 말한다. "공짜"라고 하면 감점

켜도 된다. 다만 공짜라고 말하면 안 된다.

비용은 대여마다 예외 객체 1개(스택트레이스 채우기) + 스케줄 태스크 1개다. 커넥션 대여와 그 뒤에 따라오는 쿼리에 비하면 무시할 만한 비율이라 실무에서는 상시 켜 두는 것이 일반적이다. 비활성(0)일 때는 이 경로를 아예 타지 않으므로 그때의 비용은 정말로 0이다 — 그래서 정확한 표현은 "끄면 빨라진다"가 아니라 "켜도 거의 안 느려진다"다.

값은 hikaricp.connections.usage의 p99보다 넉넉히 위로 잡고, maxLifetime(기본 30분)보다 크면 HikariCP가 무시한다는 점, 최솟값이 2,000ms라는 점을 함께 알아 두면 좋다.

로그가 찍혔는데 누수가 아닌 경우도 답할 수 있어야 한다. 배치나 대량 처리의 정상적인 장기 점유가 걸린 것이다. 대응은 ① 임계값을 그 작업보다 크게 잡거나 ② 그 작업을 별도 데이터소스로 분리하거나 ③ 애초에 그 작업의 점유 자체를 줄이는 것(청크 단위 커밋)이다. 마지막 선택지가 가장 낫다 — 그런 장기 점유는 오탐이기 이전에 이미 ③의 신호이기 때문이다.

active가 max인데 pending은 0입니다. 고갈인가요? 함정힌트: 부등식의 어느 쪽인지로 답한다 — L > c 인가, L ≈ c 인가

아직 실패는 아니다. 하지만 여유가 0인 상태다.

식으로 말하면 L ≈ c인 지점이다. 대여 요청이 곧바로 커넥션을 받고 있으므로 대기 줄은 없고(pending = 0), 실패도 아직 없다. 그러나 λ가 조금만 커지거나 W가 조금만 늘어나면 즉시 pending이 생긴다.

그래서 지표를 이렇게 나눠 쓴다 — pending > 0은 "이미 벌어진 일"을 알리는 확정 알람이고, active / max 비율이 지속적으로 1에 가까운 것은 "곧 벌어질 일"을 알리는 선행 신호다. 선행 신호에서 usage를 함께 보면 여유가 사라진 이유가 λ 때문인지 W 때문인지까지 갈린다.

반대로 pending > 0인데 active가 max가 아닌 상황도 있는지 물으면, 그건 커넥션을 새로 만드는 중이거나 순간적인 경합으로 잠깐 나타날 수 있는 모습이다 — 지속된다면 커넥션 생성 자체가 느린 것(DB 접속 지연)을 의심하고 acquire 시간을 본다.

슬로우 쿼리 로그에는 아무것도 없는데 커넥션은 오래 잡혀 있습니다. 가산점힌트: "DB 밖 시간은 DB 로그에 남지 않는다"에서 출발한다

③(트랜잭션 안 외부 호출·CPU 작업)의 전형적인 모습이다. 쿼리는 5ms에 끝났으니 슬로우 쿼리 로그에 남을 이유가 없고, 그 뒤 3초는 DB 밖에서 흐른 시간이라 DB는 그 시간의 존재조차 모른다.

확인은 두 값의 차이로 한다. 앱의 hikaricp.connections.usage(점유 시간)에서 그 요청이 실제로 실행한 쿼리 시간의 합을 빼면, 남는 것이 커넥션을 쥔 채 DB 밖에서 보낸 시간이다. 이 값이 크면 ③이다.

교차 확인은 두 곳에서 한다. ① DB에서는 pg_stat_activity의 state = 'idle in transaction'으로 보이고(query 컬럼에 마지막으로 실행한 쿼리가 남아 있어 코드 지점을 특정할 수 있다), ② 스레드 덤프에서는 부류 B의 스택이 @Transactional 메서드 → HTTP 클라이언트 → 소켓 read로 이어진다(8-3).

또 하나의 가능성은 락 대기다. 이 경우는 쿼리가 실행 시간으로는 길게 찍힐 수 있지만 "왜 길었는지"가 안 보인다. wait_event_type = Lock과 pg_blocking_pids()로 막고 있는 세션을 지목하면 갈린다 — 그리고 막는 쪽이 idle in transaction이면 결국 원인은 또 ③이다.

connection-timeout을 30초에서 2초로 줄이면 실패가 늘어나지 않나요? 함정힌트: 실패의 "총량"과 "방식"을 나눠서 답한다

바뀌는 것은 주로 실패의 방식이지 총량이 아니다. 풀이 고갈된 상태에서 30초를 기다린 요청들도 결국 대부분 실패한다. 달라지는 것은 그 30초 동안 톰캣 스레드를 하나씩 물고 있었다는 사실이다.

2초로 줄이면 같은 시간에 대기로 잠기는 스레드 양이 15분의 1이 된다. 그러면 DB를 안 쓰는 API와 헬스체크가 살아남고, LB가 인스턴스를 빼지 않으며, 장애가 그 기능 안에 갇힌다. 스레드가 빨리 풀리므로 회복도 빠르다.

대가도 정직하게 말해야 한다. 아주 짧은 스파이크에서라면 30초 안에는 커넥션을 얻어 성공했을 요청이 2초에서 실패로 바뀔 수 있다. 그래서 값은 정상 상황의 hikaricp.connections.acquire보다는 넉넉히 위, 그러나 톰캣 스레드를 오래 잠그지 않는 선에서 잡는다.

그리고 반드시 붙여야 하는 문장 — 이것은 증상 처리다. 근본 원인은 여전히 ①~④ 중 하나이고, 짧은 타임아웃은 그것이 전면 장애로 번지지 않게 막는 격벽일 뿐이다.

지금 당장 서비스를 살려야 합니다. 재시작 말고 할 수 있는 게 있나요? 시니어 변별힌트: 조치 전에 "증거 보전"을 먼저 말하면 인상이 달라진다

먼저 증거를 보전한다. 재시작이든 세션 종료든 지금 상태를 지우는 조치이므로, ① 스레드 덤프 1~2회(간격을 두고) ② pg_stat_activity 스냅샷 ③ 최근 Hikari 메트릭 구간을 먼저 확보한다. 이걸 안 하면 복구 후에 원인을 못 찾아 같은 장애가 반복된다.

그다음 조치는 계열에 따라 다르다.

③이 보이면(idle in transaction이 쌓임) 오래된 세션을 끊어 커넥션과 락을 회수한다. idle_in_transaction_session_timeout을 켜거나 해당 세션을 종료하는 방식이고, 애플리케이션에는 커넥션이 끊긴 것으로 보이므로 예외가 발생한다는 점을 감수하고 하는 조치다.

②가 보이면 문제 쿼리를 취소하고 statement_timeout·lock_timeout을 걸어 최악의 W에 상한을 만든다.

④가 보이면 아쉽지만 재시작 외에 회수 수단이 없다. 대신 재시작 시각을 기록해 재발 주기를 재는 것이 다음 진단의 결정적 자료가 된다.

공통으로 할 수 있는 것은 유입을 줄이는 쪽이다 — 무거운 배치·리포트 기능을 잠시 끄거나, 해당 엔드포인트에 제한을 걸어 λ를 낮춘다. c를 못 늘리고 W도 당장 못 줄이면 남는 항은 λ뿐이라는 것도 식에서 그대로 나온다.

MySQL이라면 무엇을 봐야 하나요? 가산점힌트: 대응되는 뷰 이름과, "한 뷰로 안 끝난다"는 차이

pg_stat_activity에 대응되는 것은 SHOW PROCESSLIST 또는 information_schema.processlist다. 여기서 오래 도는 쿼리는 같은 방식으로 찾을 수 있다.

다만 idle in transaction에 해당하는 상태를 한 눈에 보기 어렵다. MySQL에서 그 상태는 Sleep이면서 트랜잭션이 열려 있는 세션으로 나타나는데, Sleep만으로는 "그냥 노는 커넥션"과 구분되지 않는다. 그래서 information_schema.innodb_trx를 함께 봐서 그 세션에 열린 트랜잭션이 있는지를 확인해야 한다.

진단 절차 자체는 그대로다 — 앱 메트릭으로 계열을 좁히고 DB에서 교차 확인한다. 다른 것은 어휘와 도구뿐이고, PostgreSQL이 한 뷰에서 다 보인다는 점이 진단상 유리하다는 차이를 말할 수 있으면 충분하다.

한 줄 요약
커넥션 고갈은 증상 하나에 원인 넷이지만 물리는 하나다 — L = λ × W가 풀 크기 c를 넘으면 대기가 생기므로, 원인은 λ·c 문제(① 풀 크기 부족)이거나 W 문제(② 느린 쿼리·락 대기, ③ 트랜잭션 안 외부 호출)이거나 W가 무한대인 경우(④ 누수)뿐이다. 진단은 앱 메트릭으로 계열을 좁히고(pending > 0이면 고갈, usage가 W의 실측치, active가 트래픽과 함께 안 내려오면 누수) PostgreSQL의 pg_stat_activity로 교차 확인하되(오래 도는 active는 ②, 쌓인 idle in transaction은 ③ — 이건 커넥션·락에 더해 VACUUM까지 막아 블로트를 만든다), 누수 지점은 leakDetectionThreshold의 대여 시점 스택트레이스로 특정하고 스레드 덤프에서 "기다리는 스레드(피해자)"와 "쥐고 있는 스레드(용의자)"를 갈라 읽어 확정한다. 그리고 처방은 계열마다 달라서 풀 확대는 ①일 때만 정답이다 — W가 원인이면 점유가 3초일 때 500 TPS에 커넥션 1,500개가 필요해 산술적으로 감당이 안 되고 DB 경합만 키우며, 누수면 마르는 시각만 뒤로 밀린다. 남는 답은 W를 줄이는 것이고, 그동안 전면 장애로 번지지 않게 connection-timeout을 짧게 잡아 연쇄를 끊는다.
