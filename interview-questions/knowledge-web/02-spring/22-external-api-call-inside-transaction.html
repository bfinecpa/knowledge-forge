트랜잭션 안의 외부 API 호출
외부사 지연 하나가 전 서비스 마비로 번지는 연쇄

면접 질문: "트랜잭션 안에서 외부 API를 호출하면 어떤 문제가 생기나요? 어떻게 설계를 바꾸겠습니까?"

핵심 관전 포인트 — 트랜잭션은 시작부터 커밋까지 DB 커넥션 1개를 독점하는 구간이다. 그 안에서 외부 API를 호출하면 커넥션 점유 시간이 "우리가 통제할 수 없는 외부사의 응답 속도"에 종속된다 — 외부가 200ms에서 3초로 느려지는 순간 필요 커넥션이 11개에서 151개로 뛰고, 풀 30개는 0.6초 만에 바닥나며, 커넥션을 기다리는 톰캣 스레드 200개까지 5초 안에 전부 묶여 외부 API와 무관한 조회·헬스체크마저 응답하지 못한다. 헬스체크가 죽으면 로드밸런서가 인스턴스를 빼고 남은 인스턴스가 같은 경로로 무너져 전면 장애가 된다. 정합성도 함께 깨진다 — 롤백은 우리 DB 안만 되돌리므로 "외부 결제는 승인됐는데 주문은 롤백"이 남고, 특히 타임아웃은 "실패"가 아니라 "결과 불명"이라 가장 위험하다. 설계의 답은 트랜잭션 경계를 DB 작업만으로 좁혀 외부 호출을 밖으로 빼고, PENDING → CONFIRMED / FAILED 상태 기계로 중간 실패를 관측 가능하게 만든 뒤, 남은 구멍(외부 호출 후 두 번째 트랜잭션 직전 크래시)은 조회 API와 멱등키를 쓰는 복구 배치로 수렴시키는 것이다.
  • 1
    성능 — 트랜잭션 구간 = 커넥션 독점 구간이므로, 점유 시간의 주도권이 외부사에게 넘어간다. 외부가 200ms → 3초가 되면 Little's law로 필요 커넥션이 11개 → 151개가 되고, 풀 30개는 0.6초, 톰캣 스레드 200개는 약 4.9초에 마른다. 그 시점의 서버는 CPU도 놀고 DB도 한가한데 헬스체크까지 무응답이다.
  • 2
    정합성 — 롤백은 우리 DB 안의 세계만 되돌린다. "외부 승인 성공 + 우리 DB 롤백"이면 고객 돈만 나간 상태가 남고, 더 나쁜 것은 타임아웃이다. 타임아웃은 실패가 아니라 결과 불명이라 롤백·커밋·재시도 어느 쪽을 골라도 틀릴 수 있다.
  • 3
    설계 — 경계를 DB 작업만으로 좁힌다. tx1(PENDING 커밋) → 커넥션 없이 외부 호출 → tx2(CONFIRMED/FAILED). 쪼갠 대가로 생기는 "외부 호출 후 tx2 직전 크래시" 구멍은 UNKNOWN 상태와 조회 API·멱등키 기반 복구 배치로 메우고, 외부 호출 자체에는 타임아웃·재시도·서킷 브레이커를 짝으로 건다.

0. 질문 + 출제 의도

질문: "트랜잭션 안에서 외부 API를 호출하면 어떤 문제가 생기나요? 어떻게 설계를 바꾸겠습니까?"

출제 의도: DB 커넥션을 문 채로 3초짜리 외부 호출을 기다리면, 외부사 지연 하나가 커넥션풀 고갈 → 전 서비스 마비로 번진다. 이 연쇄를 머리로 시뮬레이션할 수 있는 사람만 장애가 나기 전에 구조를 바꾼다. 대용량 서비스 면접의 핵심 변별 문항이다.

이 페이지가 겨냥하는 약점 세 가지 ① "커넥션을 오래 잡아서 안 좋다"에서 멈추는 것 → 2절에서 Little's law로 필요 커넥션 11 → 151, 풀 고갈 0.6초, 스레드 고갈 4.9초까지 초 단위로 계산한다. 그리고 커넥션풀에서 멈추지 않고 톰캣 스레드풀·헬스체크·LB까지 연쇄를 끝까지 끌고 간다.
② 성능만 말하고 정합성을 빠뜨리는 것 → 3절에서 외부 성공 × DB 롤백의 2×2 조합표와 "타임아웃 = 결과 불명"을 분리해 둔다. 한쪽만 말하면 절반 답변이다.
③ "트랜잭션 밖으로 빼면 된다"로 끝내는 것 → 5절에서 쪼갠 대가로 새로 생기는 구멍(외부 호출 후 tx2 직전 크래시)과 그것을 메우는 상태 기계 + 복구 배치까지 간다. 여기까지 가야 시니어 답변이다.

이 문서는 Spring Boot 3.x / Spring Framework 6.x, HikariCP 기본 설정, 내장 톰캣 기준으로 쓴다.

한 문장 비유 — 친구를 기다리며 계산 안 하는 손님, 그리고 이미 보낸 편지 성능: 식당에 테이블(커넥션)이 30개다. 손님이 먹는 데 걸리는 시간은 짧은데 "친구(외부 API)가 올 때까지 계산 안 하고 앉아 있을게요" 라고 한다. 테이블이 언제 비는지를 식당이 아니라 손님의 친구가 정한다.  /  정합성: 롤백은 내 노트에 쓴 글씨를 지우개로 지우는 것이지, 이미 부친 편지를 우체통에서 도로 꺼내는 능력이 아니다. 편지(외부 승인)는 이미 상대 손에 있다.

1. 전제 — 트랜잭션이 독점하는 것: 커넥션 1개, 시작부터 커밋까지

1-1. 커넥션풀이 무엇이고, 왜 개수가 적은가

먼저 깔아야 할 사실이 하나 있다. DB 커넥션은 요청마다 새로 만드는 것이 아니라, 미리 몇 개만 만들어 두고 돌려 쓰는 자원이다. 이 "미리 만들어 둔 커넥션 보관함"이 커넥션풀이고, 스프링 부트의 기본 구현체가 HikariCP다.

왜 미리 만들어 두는가. 커넥션 하나를 새로 여는 데는 TCP 연결, 인증, 세션 초기화가 필요해서 보통 수십 ms가 든다. 실제 쿼리가 2ms인데 연결에 50ms를 쓰는 것은 낭비다. 그래서 애플리케이션이 뜰 때 몇 개를 열어 두고, 요청이 오면 빌려주고, 끝나면 돌려받는다.

그러면 왜 넉넉히 만들지 않는가. 커넥션 하나는 DB 서버 쪽에서도 프로세스나 스레드 하나를 잡아먹기 때문이다. PostgreSQL은 커넥션마다 백엔드 프로세스를 하나씩 띄우므로, 커넥션 1,000개는 DB 서버에 프로세스 1,000개다. 그래서 풀 크기는 수십 개 수준으로 잡는 것이 정상이고, HikariCP의 기본 maximumPoolSize도 10이다.

이 문서 전체의 전제 — 딱 한 문장

커넥션은 수십 개짜리 한정 자원이다 — 그래서 "누가 얼마나 오래 쥐고 있는가"가 곧 처리량이다

풀 크기를 어떤 근거로 정하는지는 25-thread-pool-connection-pool-sizing.md에 따로 있다.

1-2. @Transactional은 그 한정 자원을 통째로 붙잡는 구간이다

@Transactional 메서드에 진입하면 스프링의 트랜잭션 매니저는 풀에서 커넥션 하나를 꺼내 setAutoCommit(false)로 바꾼 뒤 현재 스레드에 바인딩한다. 그리고 그 커넥션은 메서드가 끝나 커밋 또는 롤백될 때까지 풀로 돌아가지 않는다.

돌아가지 않는 이유는 트랜잭션의 정의 자체에 있다. 트랜잭션은 "여러 쿼리를 하나의 원자적 단위로 묶는" 것인데, 그 묶음은 한 커넥션 안에서만 성립한다. 중간에 커넥션을 반납했다가 다른 커넥션으로 이어 붙일 수 있다면 애초에 롤백할 대상이 어디에 있는지도 알 수 없다.

이 등식 하나가 문제의 전부다

트랜잭션 구간 = 커넥션 독점 구간

스레드에 바인딩한다는 것이 정확히 무슨 뜻이고 이후 쿼리들이 그 커넥션을 어떻게 찾아 쓰는지는 24-transaction-synchronization-connection-binding.md에 있다.

before DB 작업 사이에 외부 호출이 끼어 있다
@Transactional
public Order placeOrder(OrderRequest request) {
    // 이 줄에 도달하기 전에 이미 커넥션을 꺼내 왔다 — 여기부터가 점유 구간이다
    Order order = orderRepository.save(Order.of(request));  // 실제 DB 작업: 약 5ms

1-3. 여기서 문제가 두 갈래로 갈린다

트랜잭션 안에 외부 호출을 두면 두 종류의 사고가 각각 따로 발생한다. 서로 원인이 다르므로 나눠서 봐야 한다. 면접에서 한쪽만 말하면 절반 답변이다.

① 성능 — 자원이 마른다 (2절)

  • 점유 시간이 늘어 커넥션풀 → 톰캣 스레드풀 순서로 자원이 마른다.
  • 범위가 결제 기능 → 인스턴스 전체 → 서비스 전체로 번진다.
  • 원인은 "오래 잡고 있다".

② 정합성 — 되돌릴 수 없다 (3절)

  • 외부 호출은 롤백되지 않아 "외부는 됐는데 우리 DB는 없던 일"이 남는다.
  • 타임아웃은 실패가 아니라 결과 불명이라 더 나쁘다.
  • 원인은 "원자성 범위 안에 되돌릴 수 없는 것이 들어와 있다".

그리고 4절의 설계 변경은 두 문제를 동시에 푼다. 그래서 답변은 "문제 두 갈래 → 해법 하나"의 구조로 짜면 깔끔하다.

2. 성능 붕괴 — 장애 연쇄를 숫자로 따라간다

2-1. 계산 도구 — Little's law

동시에 몇 개의 커넥션이 필요한지는 감이 아니라 계산으로 나온다. 쓰는 공식은 Little's law 하나다.

이 문항의 유일한 공식

동시에 자원을 점유 중인 개수 L = 도착률 λ × 하나당 점유 시간 W

말로 풀면 이렇다. 초당 50건이 들어오고 한 건이 자원을 0.2초 쥔다면, 어느 순간을 잘라 봐도 평균 50 × 0.2 = 10건이 그 자원을 쥔 채로 있다. 식당으로 치면 "초당 손님 수 × 손님 한 명의 체류 시간 = 지금 앉아 있는 손님 수"다.

여기서 결정적인 사실 — 점유 시간 W가 두 배가 되면 필요 개수 L도 두 배가 된다. 트래픽이 하나도 안 늘었는데 외부사가 느려졌다는 이유만으로 필요 커넥션이 폭증하는 이유가 이 비례 관계다.

2-3. 1단계 — 평시에는 몇 개가 필요한가

요청 하나당 커넥션 점유 시간은 DB 작업 10ms + 외부 호출 200ms = 210ms = 0.21초다.

L = λ × W = 50건/초 × 0.21초 = 10.5개
이 장애가 배포 시점에 잡히지 않는 이유 필요 커넥션 약 11개, 풀은 30개. 사용률 35%로 여유롭다. 평시 지표만 보면 이 코드는 아무 문제가 없어 보인다. 코드 리뷰에서도, 부하 테스트에서도(외부사가 정상인 한) 통과한다. 문제는 우리 쪽 변경이 아니라 남의 집 사정으로 시작된다.

2-4. 2단계 — 외부가 3초로 느려지면 필요량이 얼마가 되는가

외부 응답만 200ms → 3,000ms로 바뀐다. 우리 트래픽도, 우리 쿼리도 그대로다.

W = 10ms + 3,000ms = 3,010ms = 3.01초
L = 50건/초 × 3.01초 = 150.5개       // 풀은 30개 → 121개가 모자란다

필요 커넥션 11개 → 151개. 외부 응답이 15배(200ms → 3,000ms) 느려지자 필요량도 약 15배로 뛰었다. 반대로 읽으면 이렇다 — 풀 30개로 감당 가능한 처리량은 L / W = 30 / 3.01 ≈ 9.97, 즉 초당 10건이다. 들어오는 50건 중 10건만 처리되고 초당 40건이 갈 곳을 잃는다.

2-5. 3단계 — 풀이 바닥나기까지 0.6초

"언젠가 고갈된다"가 아니라 몇 초 만인지를 계산할 수 있다. 지연이 시작된 순간을 t=0이라 하자. 이때부터 들어온 요청은 3.01초가 지나야 커넥션을 반납한다. 즉 첫 3.01초 동안은 반납이 한 건도 없다. 그동안 점유된 커넥션 수는 그냥 도착한 건수와 같다.

점유 커넥션 수 = 50 × t
             30 = 50 × t
              t = 0.6초      // 사람이 알림을 보고 대시보드를 여는 시간보다 훨씬 짧다

이 순간부터 새 요청은 커넥션을 기다린다. 기다림의 한도는 HikariCP의 connection-timeout 기본값 30초이고, 그 시간이 지나면 이런 예외가 난다.

java.sql.SQLTransientConnectionException:
    HikariPool-1 - Connection is not available, request timed out after 30000ms

2-6. 4단계 — 두 번째 고갈: 톰캣 스레드가 대기로 말라붙는다 시니어 변별

여기가 이 문제의 핵심이고, 커넥션풀 이야기만 하고 멈추면 놓치는 지점이다.

블로킹 방식의 Spring MVC에서는 요청 하나가 톰캣 워커 스레드 하나를 처음부터 끝까지 점유한다. 커넥션을 기다리는 동안에도 그 스레드는 다른 요청을 처리하러 가지 않는다. 그냥 getConnection() 호출에 멈춰 서 있다.

t = 0.6초  : 커넥션 30개 전부 사용 중 = 톰캣 스레드 30개가 일하는 중
             남은 톰캣 스레드 슬롯 = 200 - 30 = 170개

이후 초당 순증 = 유입 50건 - 처리 완료 약 10건 = 40건/초

170개 ÷ 40개/초 = 약 4.3초   →   t ≈ 4.9초에 톰캣 스레드 200개 전부 대기 상태

이 시점의 서버 상태를 정확히 짚어야 한다 — "지표는 멀쩡한데 서버는 죽었다"

에러 로그

스레드 200개가 전부 getConnection()에서 park된 채 30초를 기다리고 있을 뿐이다. 그래서 확인 수단은 지표가 아니라 스레드 덤프다 — 스택 최상단이 전부 HikariCP의 대기 지점을 가리킨다.

결정적 결과: 톰캣 스레드가 하나도 안 남았으므로 서버는 어떤 요청도 받지 못한다. 결제와 아무 상관 없는 상품 조회, 캐시에서만 읽는 API, DB를 건드리지도 않는 헬스체크까지 전부 응답이 없다.

2-7. 5단계 — 마지막 고리: 헬스체크 실패가 전면 장애를 만든다

암기 장치 — 연쇄 5단계는 "점 · 커 · 스 · 헬 · 전"

점유 시간 증가 → 커넥션풀 고갈(0.6초) → 스레드풀 고갈(4.9초) → 헬스체크 실패 → 전면 장애
W 0.21초 → 3.01초→ L 11개 → 151개 (풀 30)→ 스레드 200개 소진→ LB 제외 · 재시작→ 전면 장애

면접에서 이 다섯 글자를 뼈대로 두고 각 단계에 숫자를 하나씩 붙이면 그대로 완성된 답변이 된다.

2-8. 덧 — 커넥션만 잡고 기다리는 게 아니다: 행 락도 같이 잡는다 가산점

한 겹 더 있다. 트랜잭션 안에서 SELECT ... FOR UPDATE나 UPDATE로 특정 행을 이미 건드린 상태라면, 그 트랜잭션은 행 락을 쥔 채로 외부 응답을 기다린다.

before 커넥션 + 행 락을 동시에 3초 동안 붙잡는다
@Transactional
public void useCoupon(Long couponId) {
    Coupon c = couponRepository.findByIdForUpdate(couponId); // 이 행에 락이 걸린다
    paymentClient.approve(...);                              // 락을 쥔 채 3초 대기
    c.markUsed();
}

같은 쿠폰(또는 같은 재고 행, 같은 계좌 행)을 갱신하려는 다른 트랜잭션들은 커넥션을 얻는 데 성공하더라도 DB 안에서 락을 기다리며 다시 멈춘다. 인기 상품처럼 경합이 집중되는 행이 있으면 커넥션 고갈과 락 대기가 겹쳐 붕괴가 더 빨라진다.

DB 쪽에서 보이는 그림자 — idle in transaction PostgreSQL이라면 pg_stat_activity에서 state = 'idle in transaction'인 세션이 쌓이는 모습으로 보인다. 트랜잭션은 열려 있는데 쿼리는 안 돌고 있는 상태 — 정확히 "외부 응답을 기다리는 중"의 DB 쪽 그림자다. 애플리케이션 스레드 덤프와 이 지표를 짝으로 말할 수 있으면 실제로 겪어본 사람의 답이 된다.

3. 정합성 붕괴 — 롤백은 우리 DB 안에서만 유효하다

3-1. 롤백이 되돌리지 못하는 것

성능만의 문제가 아니다. 트랜잭션의 롤백은 DB가 자기 데이터에 대해 제공하는 기능이다. 변경 전 값을 DB가 보관하고 있다가 ROLLBACK 신호에 되돌려 주는 것이지, 세상의 모든 변화를 되감는 마법이 아니다.

외부 API 호출은 이미 상대 시스템에 도달했고, 상대는 자기 DB에 커밋을 끝냈다. 우리 쪽 롤백은 거기에 아무 영향도 주지 못한다.

before 롤백이 정합성을 지켜준다는 믿음이 깨지는 코드
@Transactional
public Order placeOrder(OrderRequest request) {
    Order order = orderRepository.save(Order.of(request));
    paymentClient.approve(order);           // ① 성공 — PG사 원장에 승인이 확정된다
    couponService.use(request.couponId());  // ② 쿠폰이 이미 사용됨 → 예외 → 전체 롤백여기서 터진다
    return order;
}
// 롤백이 지운 것    : 우리 DB의 주문 행
// 롤백이 못 지운 것 : PG사의 승인 기록, 고객 카드의 승인 문자
// 결과              : 고객은 결제됐는데 우리에겐 주문이 없다. 돈이 붕 뜬다.

3-2. 네 가지 실패 조합 — 무엇이 정상이고 무엇이 사고인가

"외부 호출 결과"와 "DB 트랜잭션 결과"를 곱하면 조합이 넷이다. 이 표를 그릴 수 있어야 어떤 케이스를 설계로 막아야 하는지 정리된다.

#외부 호출DB 트랜잭션최종 상태판정
①성공커밋결제됨 + 주문 있음정상
②성공롤백결제됨 + 주문 없음사고 — 고객 돈이 나갔는데 우리에겐 기록이 없다
③실패(명시적 거절)롤백결제 안 됨 + 주문 없음정상
④응답 불명(타임아웃)롤백모름 + 주문 없음최악 — ①인지 ③인지 알 수 없다

② 는 "무엇이 잘못됐는지 아는" 사고

  • PG 승인 번호가 우리 로그에는 남아 있으니, 취소 API를 부르거나 수동 환불로 수습이 된다.
  • 문제는 그 수습 코드가 롤백 이후에 실행돼야 한다는 점이다 — 롤백은 자동이고 수습은 우리가 짜 넣어야 하므로 대개 빠져 있다.

④ 는 "무엇이 잘못됐는지도 모르는" 사고

  • 승인이 났는지 안 났는지를 우리 데이터로는 판정할 수 없다.
  • 그래서 다음 절 전체를 이것 하나에 쓴다. 이 구분을 하는 답변이 드물기 때문에 그대로 변별점이 된다.

3-3. 타임아웃이 가장 위험한 이유 — 실패가 아니라 "결과 불명"이다 함정

타임아웃을 실패로 취급하는 것이 가장 흔한 오해다. 타임아웃은 "상대가 처리하지 않았다"가 아니라 "정해진 시간 안에 답을 못 들었다"는 뜻이고, 그 안에는 서로 다른 세 가지 세계가 섞여 있다.

여기서 잘못된 선택을 하면 이렇게 된다 — 세 갈래가 전부 함정이다

실패로 간주 → 롤백
(C)였다면 표의 ②가 된다. 고객 돈만 나갔다.
성공으로 간주 → 커밋
(A)였다면 결제도 안 됐는데 주문이 확정된다. 이번엔 우리가 손해다.
그냥 재시도
(C)였다면 이중 결제다. 멱등키 없이 재시도하면 안 되는 이유가 이것이다.
정답은 "지금 정하지 않는 것" — 결과가 불명이면 불명이라고 데이터에 적어두고, 진실을 아는 쪽(PG)에게 나중에 물어본다

장비 ① 조회 API (reconcile)

  • PG사는 대개 "우리 주문번호로 승인 내역을 조회하는" API를 제공한다.
  • 이 API가 있어야 ④를 ①이나 ③으로 확정할 수 있다.
  • 그래서 외부사 연동 스펙을 검토할 때 조회 API의 유무를 반드시 확인해야 한다 — 없다면 그 자체가 설계 리스크다.

장비 ② 멱등키 (idempotency key)

  • "이 요청은 아까 그 요청과 같은 요청"임을 상대가 알아볼 수 있게 하는 식별자.
  • 우리 주문 ID를 키로 실어 보내면, (C) 상태에서 재시도해도 PG는 새 승인을 만들지 않고 기존 결과를 그대로 돌려준다.
  • 재시도를 안전하게 만드는 유일한 수단이라 결과 불명 상황의 필수 장비다.

4. 설계 변경 — 트랜잭션 경계를 DB 작업만으로 좁힌다

고치는 방향은 하나다. 커넥션을 쥐는 구간에서 외부 호출을 몰아낸다. 구조적으로는 트랜잭션이 없는 조율자(퍼사드) 하나를 위에 두고, 그 아래에 짧은 트랜잭션 메서드 둘을 두는 모양이 된다.

before 하나의 트랜잭션에 DB 쓰기 · 외부 호출 · DB 쓰기가 섞여 있다
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional                                점유 구간이 하나뿐이다
    public Order placeOrder(OrderRequest request) {

        Order order = orderRepository
                .save(Order.of(request));         // DB 쓰기 5ms

        PaymentResult result =
            paymentClient.approve(order);       // 외부 200ms~3초

        order.confirm(result);                  // DB 쓰기 5ms
        return order;
    }   // 커밋 + 커넥션 반환
}

// 문제 1) 점유 구간이 하나뿐이라
//         그 안의 가장 느린 것이 전체를 지배한다 (2절)
// 문제 2) 원자성의 범위 안에
//         되돌릴 수 없는 것이 들어와 있다 (3절)
after [tx1 커밋] → [커넥션 없이 외부 호출] → [tx2 커밋]
@Service
@RequiredArgsConstructor
public class OrderFacade {   // @Transactional 없음!
    private final OrderService orderService;
    private final PaymentClient paymentClient;

    public Order placeOrder(OrderRequest request) {
        // tx1: 이 메서드가 리턴되는 순간 커밋이 끝나고
        //      커넥션은 이미 풀로 돌아가 있다
        Order order = orderService.createPending(request);

        // 이 구간에는 커넥션이 없다 — 외부가 3초를 쓰든핵심
        // 30초를 쓰든 풀의 여유는 줄지 않는다
        PaymentResult result = paymentClient
                .approve(order.getId(), order.getAmount());

        // tx2: DB 작업만 있으므로 수 ms짜리 짧은 점유
        return orderService.confirm(order.getId(), result);
    }
}

@Service @RequiredArgsConstructor
public class OrderService {

    @Transactional
    public Order createPending(OrderRequest request) {
        return orderRepository.save(Order.pending(request));
    }

    @Transactional
    public Order confirm(Long orderId, PaymentResult result) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.confirm(result);   // PENDING -> CONFIRMED
        return order;
    }
}

반드시 짚어야 할 함정 — 클래스를 나누지 않으면 아무 일도 일어나지 않는다

OrderFacade와 OrderService는 반드시 서로 다른 빈이어야 한다. 같은 클래스 안에서 this.createPending(...)처럼 자기 자신을 호출하면 프록시를 거치지 않아 @Transactional이 아예 적용되지 않는다(11-transactional-self-invocation.md).

트랜잭션을 쪼개려고 메서드만 나누고 클래스는 그대로 두는 실수가 흔하다. 그리고 이 실수는 조용히 일어난다 — 예외도 로그도 없이 트랜잭션 없이 도는 코드가 되고, 쪼갠 효과도 없다.

함정 하나 더 — 퍼사드에 @Transactional을 붙이면 원점이다 구조를 잘 나눠 놓고 습관적으로 OrderFacade에 @Transactional을 붙이면, 바깥 트랜잭션이 전체를 다시 감싸므로 커넥션 점유 구간이 원래대로 되돌아간다. 이 클래스에 트랜잭션이 없다는 것이 설계의 핵심이므로 주석으로 남겨 두는 편이 안전하다.

4-1. 효과를 2절의 숫자로 되짚는다

외부가 3초로 느려져도 커넥션 점유 시간 W는 여전히 10ms 수준이다.

개선 후 필요 커넥션 = 50건/초 × 0.01초 = 0.5개       // 151개 → 1개 미만
해결된 것 — 커넥션풀
필요량 151개 → 0.5개. 커넥션풀은 외부 지연의 영향을 전혀 받지 않는다. 2절 연쇄의 첫 고리가 끊긴다.
남은 것 — 톰캣 스레드
스레드는 여전히 외부 응답을 기다린다. 50 × 3.01 = 151개가 필요하므로 200개 안이라 버티지만 여유는 크지 않다. 그래서 7절이 짝으로 따라와야 한다.

이 문장을 빠뜨리면 과장이 된다

경계를 좁히는 것은 "커넥션풀로의 전파를 끊는" 조치이지 외부 지연 자체를 없애는 조치가 아니다

면접에서 "트랜잭션 밖으로 빼면 해결됩니다"로 끝내면 스레드풀은 어떻게 되나요?라는 반문을 맞는다. 먼저 스스로 그 한계를 말하고 7절(타임아웃·서킷 브레이커)로 넘어가는 것이 안전하다.

5. after에도 남는 구멍 — 상태 기계와 복구 배치 시니어 변별

트랜잭션을 쪼갠 대가로 틈이 생긴다. before에는 없던 새로운 실패 지점이다. 여기까지 스스로 말하는 것이 이 문항의 마지막 관문이다.

5-1. 상태를 넷으로 두는 이유 — UNKNOWN을 아끼면 돈이 샌다

PENDING과 CONFIRMED만으로는 부족하다. 3-3에서 본 "결과 불명"을 담을 자리가 필요하기 때문이다.

5-2. 복구 배치 — 추측하지 않고 진실을 아는 쪽에 물어본다

after 오래 PENDING인 주문을 주워 외부에 진실을 물어본다
@Scheduled(fixedDelay = 60_000)
public void reconcilePendingOrders() {
    // 5분 기준을 두는 이유: 방금 만들어져 정상 진행 중인 PENDING까지 건드리면
    // 아직 처리 중인 결제를 취소해 버릴 수 있다.
    // 정상 흐름의 최대 소요보다 넉넉히 긴 값을 잡는다.
    List<Order> stuck = orderRepository.findPendingOlderThan(Duration.ofMinutes(5));

    for (Order order : stuck) {
        // 우리가 모르는 사실(진짜 승인됐는가)을 아는 쪽은 PG뿐이다.
        // 그래서 추측하지 않고 조회 API로 물어본다.이 한 줄이 설계의 핵심
        PaymentStatus status = paymentClient.inquire(order.getId());

        switch (status) {
            // PG에 승인이 있다 → 우리 쪽 tx2만 유실된 것이므로 이어서 확정한다
            case APPROVED    -> orderService.confirm(order.getId(), status.toResult());
            // PG에 아무것도 없다 → 승인 전에 끊긴 것이므로 실패로 닫는다
            case NOT_FOUND   -> orderService.fail(order.getId(), "PG 승인 기록 없음");
            // PG도 아직 확정 못 한 상태 → 다음 주기에 다시 물어본다
            case IN_PROGRESS -> { }
        }
    }
}

배치가 여러 번 돌아도 안전해야 한다 — 상태 기계 가드

confirm은 "현재 상태가 PENDING일 때만" CONFIRMED로 바꾼다

이 조건부 전이(가드)로 만들면 같은 주문에 배치가 두 번 돌아도 두 번째는 조용히 아무 일도 하지 않는다. 외부 호출의 멱등성은 멱등키로, 우리 쪽 전이의 멱등성은 상태 가드로 — 양쪽 다 필요하다.

잃은 것

  • "큰 트랜잭션 하나의 즉시 원자성".
  • 중간 상태가 사용자에게 보일 수 있다(주문 목록에 "처리 중").
  • 복구 배치라는 운영해야 할 부품이 하나 늘었다.

얻은 것

  • 관측 가능성 — 어디까지 진행됐는지가 데이터로 남는다. 메모리에만 있던 진행 상황이 DB로 나왔으므로 다른 인스턴스나 배치가 이어받을 수 있다.
  • 최종 일관성 — 언젠가 수렴한다.
  • 장애 격리 — 외부 지연이 커넥션풀로 전파되지 않는다.
답변의 마무리로 쓰는 한 문장 원래 그 원자성은 외부 세계까지 덮어주지 못했으므로 애초에 반쪽짜리였다. 그러므로 실제 선택지는 "즉시 일관성 vs 최종 일관성"이 아니라 "관측 가능한 최종 일관성 vs 관측조차 안 되는 불일치"다.
운영 지표도 여기서 나온다 "PENDING/UNKNOWN인 채 N분 넘은 건수"에 알람을 걸면, 복구 배치가 조용히 죽어 있는 장애를 발견할 수 있다. 상태를 데이터로 남긴 설계의 부수 이득이다.

6. 외부 호출이 "결과를 결정하지 않는" 경우 — 이벤트와 아웃박스

지금까지는 외부 호출 결과가 주문의 확정 여부를 결정하는 경우였다. 그런데 알림 발송, 캐시 갱신, 통계 집계처럼 주문 성공 여부와 무관한 부수 작업이라면 더 간단한 길이 있다. 이 경우 필요한 것은 "커밋이 확정된 뒤에만 실행되게 하는 것" 하나뿐이다.

7. 외부 호출 자체의 방어선 가산점

경계를 옮겨도 외부는 여전히 느려지고 실패한다. 4-1에서 봤듯 톰캣 스레드는 여전히 외부 응답을 기다리므로, 다음 세 가지가 짝으로 따라와야 한다.

타
타임아웃은 선택이 아니라 필수다. connect 타임아웃(연결 수립까지)과 read 타임아웃(응답 수신까지)을 둘 다 명시한다. 클라이언트 기본값이 무제한인 경우가 많은데, 그러면 "느린 실패"가 "영원한 대기"가 되어 스레드가 영영 안 돌아온다.
값의 기준 — 외부사 응답 시간의 99분위 × 여유 배수로 잡고, 그보다 오래 걸리는 건은 애초에 성공해도 사용자에게 의미가 없다고 판단한다.
멱
재시도는 멱등키와 세트다. 3-3에서 본 대로 멱등키 없는 재시도는 이중 결제를 만든다. 그리고 재시도 간격은 지수 백오프(1초, 2초, 4초처럼 늘려 가는 방식)로 둔다 — 이미 힘들어하는 상대에게 재시도 폭풍을 얹지 않기 위해서다.
서
서킷 브레이커는 연쇄 차단의 마지막 방어선이다. 최근 실패율이 임계치를 넘으면 한동안 아예 호출을 시도하지 않고 즉시 실패시키는 장치다(전기 회로의 차단기에서 온 이름). 이것이 하는 일은 스레드를 기다림에서 해방하는 것이다 — 2-6에서 스레드를 마르게 한 것은 실패가 아니라 대기였으므로, "빨리 실패시키는" 것만으로 스레드풀 고갈을 막을 수 있다.

암기 장치 — 방어선 3종은 "타 · 멱 · 서"

타임아웃(connect + read)  ·  멱등키 + 지수 백오프 재시도  ·  서킷 브레이커

4절(경계 좁히기)이 커넥션풀을 지키는 조치라면, 이 셋은 톰캣 스레드풀을 지키는 조치다. 두 묶음을 짝으로 말해야 답변이 닫힌다.

8. 통하지 않는 우회로 3종 — 먼저 알고 있어야 반박당하지 않는다

우회로 ① @Transactional(propagation = REQUIRES_NEW)로 쪼갠다

안 된다. 오히려 나빠진다. REQUIRES_NEW는 기존 트랜잭션을 끝내는 것이 아니라 잠시 보류(suspend)하고 새 트랜잭션을 여는 전파 옵션이다. 보류된 트랜잭션의 커넥션은 풀로 돌아가지 않고 그대로 붙잡혀 있다. 그래서 안쪽 트랜잭션이 도는 동안 커넥션을 2개 쥔다.

결과적으로 요청당 점유량이 2배가 되어 풀이 절반의 시간에 고갈되고, 풀 크기가 동시 요청 수보다 작으면 "바깥 커넥션을 쥔 채 안쪽 커넥션을 기다리는" 요청들이 서로를 막는 자기 교착에 빠질 수 있다. 필요한 것은 중첩이 아니라 종료다 — 4절처럼 트랜잭션이 없는 조율자를 두고 커밋을 실제로 끝낸 뒤 외부를 호출해야 한다. (12-transaction-propagation-required-vs-requires-new.md)

우회로 ② 커넥션풀을 200개로 늘린다

구조를 그대로 두고 숫자만 키우는 것은 문제를 뒤로 미룰 뿐이다. 세 가지 이유로 통하지 않는다.

ⓐ 계산이 안 맞는다 — 외부가 3초면 필요량이 151개이고, 지연이 6초가 되면 301개다. 필요량은 우리가 통제하지 못하는 값에 비례하므로 어떤 숫자로도 안전하지 않다.
ⓑ DB가 먼저 무너진다 — 1-1에서 봤듯 커넥션 하나는 DB 서버 쪽 프로세스/스레드 하나다. 커넥션을 늘리면 이번엔 DB의 컨텍스트 스위칭과 메모리가 병목이 되어 전체가 느려진다.
ⓒ 스레드풀 고갈은 그대로다 — 커넥션이 넉넉해져도 요청 하나가 톰캣 스레드를 3초씩 붙잡는 사실은 변하지 않는다.

고쳐야 할 것은 L(개수)이 아니라 W(점유 시간)라는 것이 Little's law가 알려주는 결론이다. (25-thread-pool-connection-pool-sizing.md)

우회로 ③ @Transactional(timeout = 3)으로 잘라낸다

스레드를 구해주지 못한다. 트랜잭션 타임아웃은 남은 시간을 검사하는 시점이 정해져 있다 — 스프링은 트랜잭션 만료 여부를 DB 리소스를 획득하거나 쿼리를 실행하는 시점에 확인하고, JDBC 쿼리에는 남은 시간을 제한으로 넘긴다.

그런데 지금 멈춰 있는 곳은 DB가 아니라 HTTP 소켓이다. 아무도 그 대기를 끊어주지 않으므로 스레드는 외부 응답이 오거나 HTTP 클라이언트 자신의 타임아웃이 걸릴 때까지 그대로 있고, 만료는 그 뒤 다음 DB 접근에서야 드러난다. 게다가 만료돼 롤백되더라도 이미 나간 외부 호출은 되돌아오지 않는다(3절 ②). 외부 호출을 끊는 것은 트랜잭션 타임아웃이 아니라 HTTP 클라이언트의 read 타임아웃이다.

8-1. AI가 생성한 서비스 코드를 리뷰할 때 보는 것 가산점

생성 도구는 "서비스 메서드에는 @Transactional"이라는 관성이 강해서, 트랜잭션 경계 안에 RestTemplate/WebClient/FeignClient 호출이 들어간 코드를 자주 만든다. 눈에 띄는 오류가 없고 테스트도 통과하므로 리뷰에서 걸러야 한다.

1. 경계 안의 블로킹 외부 호출
@Transactional 메서드 안에 HTTP 클라이언트 호출, 메시지 발행, 파일/S3 IO가 있는가.
2. 타임아웃 명시
있다면 그 호출에 connect/read 타임아웃이 명시돼 있는가. 기본값 무제한이면 스레드가 영영 안 돌아온다.
3. 실패 처리의 전제
실패 처리 로직이 "외부는 롤백되지 않는다"를 간과하고 있지 않은가 — catch 후 그냥 예외를 다시 던져 롤백에 맡기는 코드가 전형이다.
4. 쪼갠 뒤의 복구 경로
경계를 쪼갠 코드라면 중간 상태(PENDING)와 복구 경로가 함께 설계돼 있는가 — 쪼개기만 하고 복구가 없으면 5절의 구멍이 그대로 남는다.

공통점은 "완료 시점을 우리가 정하지 못한다"는 것이다. 그런 것이 트랜잭션 안에 있으면 커넥션 점유 시간의 주도권도 함께 넘어간다. (35-ai-code-transaction-review-checklist.md)

9-2. 3초 인출 카드 — 보기 전에 먼저 답해보기

왜 트랜잭션 안이 문제인가?
트랜잭션 구간 = 커넥션 독점 구간이라서. 점유 시간 W의 주도권이 외부사에게 넘어간다.
유일한 공식은?
L = λ × W. W가 2배면 L도 2배 — 트래픽이 그대로여도 필요 자원이 폭증하는 이유.
연쇄 5단계는?
점·커·스·헬·전 — 점유 시간 ↑ → 커넥션풀(0.6초) → 스레드풀(4.9초) → 헬스체크 실패 → 전면 장애.
고갈 시점의 서버 증상은?
CPU 유휴 · DB 한가 · 에러 로그 없음 · 응답만 없음. 확인은 지표가 아니라 스레드 덤프(스택 최상단이 HikariCP 대기).
왜 전면 장애가 되나?
헬스체크 실패 → LB 제외 · 파드 재시작 → 남은 인스턴스 λ 증가 → 같은 연쇄 반복. 자동 복구 장치가 가속기가 된다.
정합성 사고 두 가지는?
② 외부 성공 + DB 롤백(돈만 나감), ④ 타임아웃(결과 불명). ①③은 정상.
타임아웃이 왜 최악인가?
실패가 아니라 "결과 불명"이라서. (A)미도달 (B)처리중 (C)승인완료가 우리 눈에는 똑같이 보인다.
결과 불명의 필수 장비 2종은?
조회 API(reconcile)와 멱등키. 멱등키는 재시도를 안전하게 만드는 유일한 수단.
설계 변경의 형태는?
트랜잭션 없는 퍼사드 + tx1(PENDING) → 외부 호출 → tx2. 반드시 다른 빈이어야 한다(자기 호출 함정).
쪼갠 뒤 새로 생기는 구멍은?
외부 호출 성공 후 tx2 직전 크래시. try/catch로 못 막고 복구 배치로 메운다.
상태 4종과 그 이유는?
PENDING · CONFIRMED · FAILED · UNKNOWN. UNKNOWN을 아끼면 "PG는 승인, 우리는 실패"를 영영 못 찾는다.
외부 호출 방어선 3종은?
타·멱·서 — 타임아웃(connect+read) · 멱등키+지수 백오프 · 서킷 브레이커. 스레드를 대기에서 해방하는 조치.
통하지 않는 우회로는?
REQUIRES_NEW(커넥션 2개 점유) · 풀 키우기(W가 그대로) · 트랜잭션 timeout(HTTP 대기를 못 끊는다).
한 줄 결론은?
"롤백은 우리 DB 안의 세계만 되돌린다" + "고쳐야 할 것은 L이 아니라 W다".

9-3. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

외부 API 호출이 실패하면 트랜잭션을 롤백하면 되는 것 아닌가요? 필수힌트: 두 갈래로 답한다 — ① 타임아웃은 실패 확정이 아니다 ② 롤백해도 성능 문제는 그대로다

두 가지 이유로 불충분하다.

첫째, 타임아웃은 실패 확정이 아니다. 상대는 성공했고 응답만 유실됐을 수 있어서, 롤백하면 3-2 표의 ② — 외부는 성공했는데 우리 DB는 없던 일 — 이 된다. 확정하려면 조회 API로 실제 결과를 물어봐야 하고, 그 조회는 트랜잭션 롤백 이후에 일어나야 하므로 애초에 트랜잭션 안에서 해결될 문제가 아니다.

둘째, 롤백으로 정합성을 지킬 수 있는 경우라 해도 성능 문제는 그대로 남는다. 실패를 기다리는 동안(타임아웃이 30초라면 30초 내내) 커넥션을 문 채이므로 2절의 연쇄는 똑같이 일어난다. 롤백은 성능 문제를 하나도 해결하지 못한다.

한 줄로 정리하면 "롤백은 우리 DB 안의 세계만 되돌린다"가 답의 뼈대다.

커넥션풀 고갈이 전 서비스 장애로 번지는 경로를 구체적으로 설명해주세요 필수힌트: 숫자를 붙여 단계로. 커넥션풀에서 멈추지 말고 스레드풀 → 헬스체크 → LB까지
외부 응답 200ms -> 3초
  -> 점유 시간 W: 0.21초 -> 3.01초
  -> 필요 커넥션 L = 50 × W: 11개 -> 151개 (풀은 30개)
  -> 반납이 없는 첫 3초 동안 50t = 30 -> t=0.6초에 풀 고갈
  -> 커넥션 대기 요청이 톰캣 스레드를 점유한 채 멈춤 (블로킹 MVC)
  -> 순증 40건/초, 남은 슬롯 170개 -> 약 4.3초 뒤 스레드 200개 소진
  -> DB가 필요 없는 조회·헬스체크까지 무응답
  -> LB 제외 / k8s 재시작 -> 남은 인스턴스의 λ 증가 -> 같은 연쇄 반복
  -> 전면 장애

핵심 문장은 "커넥션풀과 톰캣 스레드풀이라는 두 겹의 공유 자원이 차례로 마르는 연쇄"이고, 마지막 고리인 "헬스체크 실패가 자동 복구 장치를 붕괴 가속기로 바꾼다"까지 말하면 완성이다.

여기에 이 시점의 서버가 CPU도 놀고 DB도 한가한데 응답만 없다는 점, 그래서 스레드 덤프로 확인해야 한다는 점을 덧붙이면 실제 겪어본 사람의 답이 된다.

결제와 아무 상관 없는 상품 조회 API는 왜 같이 죽나요? 필수힌트: 두 자원 중 어느 쪽을 공유하고 있는지 짚는다

커넥션풀은 안 쓰더라도 톰캣 스레드풀은 공유하기 때문이다. 블로킹 MVC에서 요청 하나 = 스레드 하나인데, 결제 요청들이 getConnection()에서 멈춘 채 스레드 200개를 전부 점유해 버리면, 새로 들어온 조회 요청은 처리해 줄 스레드 자체를 배정받지 못한다.

그래서 캐시에서만 읽는 API도, DB를 아예 건드리지 않는 /actuator/health도 똑같이 무응답이 된다. 자원 하나(커넥션)의 고갈이 자원 둘(스레드)의 고갈로 번역되는 순간 장애 범위가 "결제 기능"에서 "이 인스턴스 전체"로 확대되는 것이다.

한 걸음 더 나가면 격리 설계 이야기가 된다 — 느린 외부 연동 경로와 핵심 조회 경로가 같은 스레드풀·같은 커넥션풀을 공유하고 있다면, 한쪽의 지연이 다른 쪽을 반드시 끌고 들어간다.

트랜잭션을 쪼개면 중간 실패 시 정합성은 어떻게 지키나요? 시니어 변별힌트: "원자성이 사라진다"가 아니라 "원자성의 단위를 줄이고 단위 사이를 상태로 잇는다"

원자성이 사라지는 것이 아니라 원자성의 단위를 줄이고 단위 사이를 상태로 잇는 것이라고 답한다.

PENDING을 커밋해 두면 "어디까지 진행됐는지"가 데이터로 남는다. 메모리에만 있던 진행 상황이 DB로 나왔다는 것이 핵심이다 — 프로세스가 죽어도 다른 인스턴스나 배치가 그 행을 보고 이어받을 수 있다.

그 위에 복구 배치를 얹는다. 오래 PENDING/UNKNOWN인 건을 주워 외부 조회 API로 진실을 확인하고 CONFIRMED나 FAILED로 수렴시킨다. 재시도가 안전하려면 외부 호출에 멱등키가 실려 있어야 하고, 우리 쪽 전이도 "현재 상태가 PENDING일 때만"이라는 가드로 멱등하게 만든다.

마지막으로 트레이드오프를 명시한다. "큰 트랜잭션의 즉시 일관성"과 "쪼갠 구조의 최종 일관성 + 장애 격리" 중 무엇을 택할지는 요구사항이 정한다 — 다만 외부 호출이 끼어 있는 순간 전자는 원래 불가능했으므로, 실제 선택지는 "관측 가능한 최종 일관성"과 "관측조차 안 되는 불일치" 사이라고 답하면 시니어 답변이다.

결제 승인 결과가 있어야 주문을 확정할 수 있는데, 그래도 트랜잭션 밖으로 뺄 수 있나요? 필수힌트: "외부 결과에 의존한다"와 "같은 트랜잭션이어야 한다"는 서로 다른 명제다

뺄 수 있고, 빼야 한다. "외부 결과에 의존한다"와 "같은 트랜잭션이어야 한다"는 서로 다른 명제다.

진행 순서는 그대로 유지된다. tx1(PENDING 저장) → 외부 승인 → tx2(결과 반영)이므로 "승인 결과를 보고 확정한다"는 요구는 조금도 훼손되지 않는다. 바뀐 것은 그 사이에 커넥션을 쥐고 있느냐뿐이다.

잃는 것은 "실패 시 자동 롤백" 하나인데, 그 자동 롤백은 어차피 PG사의 승인을 되돌리지 못하므로 애초에 환상이었다. 결제처럼 진실의 원천이 외부에 있는 도메인은 조회 API와 멱등키로 정합성을 맞추는 것이 정석이고, DB 트랜잭션은 우리 쪽 기록을 짧고 확실하게 남기는 역할만 맡는다.

그럼 @Transactional(propagation = REQUIRES_NEW)로 쪼개면 되지 않나요? 함정힌트: suspend는 "끝내는 것"이 아니다 — 보류된 커넥션은 어디에 있나

안 된다. 오히려 나빠진다.

REQUIRES_NEW는 기존 트랜잭션을 끝내는 것이 아니라 잠시 보류(suspend)하고 새 트랜잭션을 여는 전파 옵션이다. 보류된 트랜잭션의 커넥션은 풀로 돌아가지 않고 그대로 붙잡혀 있다. 그래서 안쪽 트랜잭션이 도는 동안 커넥션을 2개 쥔다.

바깥 트랜잭션 안에 외부 호출이 있고 그 안에서 REQUIRES_NEW를 쓰면, 커넥션 점유량이 요청당 2개가 되어 풀이 절반의 시간에 고갈된다. 게다가 풀 크기가 동시 요청 수보다 작으면 "바깥 커넥션을 쥔 채 안쪽 커넥션을 기다리는" 요청들이 서로를 막는 자기 교착에 빠질 수 있다.

필요한 것은 트랜잭션의 중첩이 아니라 종료다. 즉 4절처럼 트랜잭션이 없는 조율자를 두고 커밋을 실제로 끝낸 뒤 외부를 호출해야 한다. (12-transaction-propagation-required-vs-requires-new.md)

커넥션풀을 넉넉하게 200개로 늘리면 되지 않나요? 함정힌트: L = λ × W에서 우리가 손댈 수 있는 값이 무엇인지 짚는다

구조를 그대로 두고 숫자만 키우는 것은 문제를 뒤로 미룰 뿐이다. 세 갈래로 답한다.

① 계산이 안 맞는다. 외부가 3초면 151개, 6초면 301개가 필요하다. 필요량이 우리가 통제하지 못하는 값에 비례하므로 어떤 숫자를 골라도 안전이 보장되지 않는다.

② DB가 먼저 무너진다. 커넥션 하나는 DB 서버 쪽에서도 프로세스나 스레드 하나다(PostgreSQL은 커넥션마다 백엔드 프로세스). 커넥션을 늘리면 DB의 컨텍스트 스위칭과 메모리가 병목이 되어 전체가 오히려 느려진다.

③ 스레드풀 고갈은 그대로다. 커넥션이 넉넉해져도 요청 하나가 톰캣 스레드를 3초씩 붙잡는다는 사실은 변하지 않아서, 결국 2-6의 두 번째 고갈은 똑같이 온다.

정리하면 고쳐야 할 것은 L(개수)이 아니라 W(점유 시간)다. Little's law는 "풀을 얼마나 키울까"가 아니라 "점유 시간을 줄이지 않으면 답이 없다"를 알려주는 도구로 쓰는 것이 맞다.

@Transactional(timeout = 3)을 걸면 3초 만에 끊기지 않나요? 함정힌트: 트랜잭션 타임아웃은 "언제" 검사되는가 — 지금 스레드가 멈춰 있는 곳은 어디인가

스레드를 구해주지 못한다. 트랜잭션 타임아웃은 남은 시간을 검사하는 시점이 정해져 있다 — 스프링은 만료 여부를 DB 리소스를 획득하거나 쿼리를 실행하는 시점에 확인하고, JDBC 쿼리에는 남은 시간을 제한으로 넘긴다.

그런데 지금 스레드가 멈춰 있는 곳은 DB가 아니라 HTTP 소켓이다. 아무도 그 대기를 인터럽트해 주지 않으므로 스레드는 외부 응답이 오거나 HTTP 클라이언트 자신의 타임아웃이 걸릴 때까지 그대로 있고, 트랜잭션 만료는 그 뒤 다음 DB 접근에서야 드러난다. 즉 커넥션 점유 시간은 전혀 줄지 않는다.

게다가 만료돼서 롤백되더라도 이미 나간 외부 호출은 되돌아오지 않는다(3절의 ②). 외부 호출을 끊는 장치는 트랜잭션 타임아웃이 아니라 HTTP 클라이언트의 connect/read 타임아웃이고, 트랜잭션 타임아웃은 "이 트랜잭션이 비정상적으로 길다"를 잡는 보조 안전장치로 이해하는 것이 맞다.

WebFlux 같은 논블로킹으로 바꾸면 해결되나요? 가산점힌트: 두 자원 중 어느 쪽이 구제되고 어느 쪽이 그대로인지 나눠서 답한다

고갈되는 두 자원 중 한쪽만 구제된다.

구제되는 쪽 — 스레드. 논블로킹 모델에서는 외부 응답을 기다리는 동안 스레드가 다른 일을 하러 갈 수 있으므로, 2-6의 "스레드 200개가 대기로 말라붙는" 현상은 크게 완화된다.

그대로인 쪽 — 커넥션. JDBC는 블로킹 API라서 WebFlux 위에서도 DB 접근은 결국 별도의 블로킹 스레드에서 처리되고, 무엇보다 "트랜잭션이 열려 있는 동안 커넥션 하나를 붙잡는다"는 성질 자체는 바뀌지 않는다. 트랜잭션 안에 외부 호출이 남아 있으면 W는 여전히 3.01초이고 L = 151개도 그대로다.

그래서 답은 "기술 스택을 바꾸는 것은 이 문제의 해법이 아니다"가 된다. 경계를 좁히는 설계는 MVC든 WebFlux든 똑같이 필요하고, 그 설계를 먼저 한 뒤에야 스택 논의가 의미를 갖는다. (27-webflux-vs-mvc-threading-model.md)

외부사가 조회 API를 제공하지 않으면 복구 배치를 어떻게 만드나요? 시니어 변별힌트: 기술 문제가 아니라 "연동 계약"의 문제로 끌고 간다

먼저 그것을 연동 스펙 검토 단계에서 잡아야 할 리스크로 규정한다. "결과 불명 상황에서 진실을 확인할 수단이 없다"는 것은 구현 난이도의 문제가 아니라 그 연동으로는 정합성을 보장할 수 없다는 뜻이기 때문이다. 그래서 조회 API의 유무는 성능 요구사항만큼이나 먼저 확인해야 할 항목이다.

그럼에도 없는 상태로 가야 한다면 차선책을 겹쳐 쌓는다.

① 멱등키로 재시도를 안전하게 만든다 — 조회는 못 해도 같은 키로 다시 요청했을 때 중복 승인이 생기지 않는다면 재시도로 상태를 확정할 수 있다. ② 정산 파일·대사 데이터로 사후 확인한다 — 많은 외부사가 일별 거래 내역을 파일이나 별도 채널로 제공하므로, 주기가 느릴 뿐 진실을 확인하는 경로는 남는다. ③ 그것도 없으면 UNKNOWN 건을 사람이 처리할 수 있게 만든다 — 운영 화면과 알림을 붙여 수동 확인·수동 마감을 정식 절차로 설계한다.

핵심은 "자동으로 못 하니 포기한다"가 아니라 "불일치가 데이터로 남고 누군가에게 도달하게 만든다"는 것이다. 3-2 표의 ④가 조용히 묻히는 것과 목록에 쌓여 보이는 것 사이의 차이가 곧 설계의 값어치다.

지표는 다 정상인데 서비스가 응답하지 않습니다. 어떻게 진단하나요? 가산점힌트: CPU·DB가 한가하다는 것 자체가 단서다 — 무엇을 떠야 보이는가

"CPU도 한가하고 DB도 한가한데 응답이 없다"는 조합 자체가 강한 단서다. 일을 못 해서가 아니라 기다리느라 멈춘 것이므로, 봐야 할 것은 사용률이 아니라 대기다.

① 스레드 덤프를 뜬다. 톰캣 워커 스레드들의 스택 최상단이 전부 HikariCP의 커넥션 대기 지점을 가리키면 진단이 끝난다 — 커넥션풀 고갈이고, 그 원인은 커넥션을 오래 쥐는 무언가다.

② DB 쪽에서 교차 확인한다. PostgreSQL이라면 pg_stat_activity에 state = 'idle in transaction' 세션이 쌓여 있는지 본다. 트랜잭션은 열려 있는데 쿼리는 안 돌고 있는 상태가 바로 "외부 응답을 기다리는 중"의 DB 쪽 그림자다.

③ 그다음이 구조 확인이다. 커넥션풀 지표(active/idle/pending)와 외부 API 응답 시간 지표를 같은 시간축에 겹쳐 보면, 외부 지연이 먼저 오르고 그 뒤 풀이 마르는 인과 순서가 보인다. 이 순서를 보여주는 것이 "PG사 탓"과 "우리 설계 탓"을 구분하는 근거가 된다.

AI가 생성한 서비스 코드에서 이 문제를 리뷰할 때 무엇을 보나요? 가산점힌트: 체크리스트 넷 — 경계 안의 외부 호출 / 타임아웃 / 실패 처리의 전제 / 복구 경로

생성 도구는 "서비스 메서드에는 @Transactional"이라는 관성이 강해서, 트랜잭션 경계 안에 RestTemplate/WebClient/FeignClient 호출이 들어간 코드를 자주 만든다. 눈에 띄는 오류가 없고 테스트도 통과하므로 리뷰에서 걸러야 한다.

1. @Transactional 메서드 안에 HTTP 클라이언트 호출, 메시지 발행, 파일/S3 IO 같은 블로킹 외부 호출이 있는가.
2. 있다면 그 호출에 connect/read 타임아웃이 명시돼 있는가 (기본값 무제한이면 스레드가 영영 안 돌아온다).
3. 실패 처리 로직이 "외부는 롤백되지 않는다"를 간과하고 있지 않은가 — catch 후 그냥 예외를 다시 던져 롤백에 맡기는 코드가 전형적이다.
4. 경계를 쪼갠 코드라면 중간 상태(PENDING)와 복구 경로가 함께 설계돼 있는가 — 쪼개기만 하고 복구가 없으면 5절의 구멍이 그대로 남는다.

한 줄 요약
트랜잭션은 커넥션이라는 수십 개짜리 한정 자원의 독점 구간이므로 그 안에 외부 API 호출을 넣으면 점유 시간이 외부사 손에 넘어가고, 외부가 200ms에서 3초로 느려지는 것만으로 필요 커넥션이 11개에서 151개로 뛰어 풀은 0.6초 만에, 톰캣 스레드 200개는 5초 안에 마르며 헬스체크 실패 → 인스턴스 제외 → 남은 인스턴스 붕괴의 전면 장애로 번진다 — 게다가 롤백은 우리 DB 안만 되돌리므로 "외부 성공 + DB 롤백"과 "타임아웃 = 결과 불명"이라는 정합성 사고까지 함께 생기니, 트랜잭션 경계를 DB 작업만으로 좁혀 외부 호출을 밖으로 빼고 PENDING → CONFIRMED / FAILED / UNKNOWN 상태 기계와 조회 API·멱등키 기반 복구 배치로 남은 구멍까지 수렴시키는 것이 정석 설계다.
