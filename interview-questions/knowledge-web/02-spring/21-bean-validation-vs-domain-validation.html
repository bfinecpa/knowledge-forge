Bean Validation(@Valid)과 도메인 검증의 역할 분담
"이 검증은 누구의 책임인가"를 계층 설계로 답하기 — 그리고 "중복"을 정리하는 올바른 방향

면접 질문: "Bean Validation(@Valid)과 도메인 검증의 역할 분담은 어떻게 하나요? 같은 검증이 계층마다 중복되는 문제는 어떻게 정리하나요?"

핵심 관전 포인트 — 분담 기준은 하나다: "이 검증을 하는 데 요청 값 말고 다른 정보가 필요한가?" 요청 값만 보고 판정 가능한 형식 검증은 컨트롤러 진입 시점에 Bean Validation으로 걸러 400으로 끝내고, DB 상태가 필요하면 애플리케이션 서비스가, 객체 자신이 항상 지켜야 할 조건(불변식)이면 도메인 객체가 맡는다. 계층 간 "중복"은 목적이 다르면 중복이 아니다 — @Valid는 웹이라는 하나의 입구만 지키고 도메인 불변식은 배치·컨슈머·테스트까지 모든 경로를 지키므로, 이 이중 방어는 낭비가 아니라 설계다. 정리해야 할 진짜 중복은 같은 규칙이 여러 DTO와 서비스에 복붙된 것이고, 답은 검증을 지우는 방향이 아니라 커스텀 제약 애너테이션과 값 객체로 한곳에 봉인해 "검증을 잊을 수 없는 구조"를 만드는 방향이다.
  • 1
    기준은 질문 하나로 기계화된다 — "요청 값 말고 무엇이 더 필요한가?" 아무것도 필요 없으면(형식·길이·범위·패턴) 컨트롤러 DTO의 Bean Validation이 400 + 필드별 에러로 끝내고, DB·외부 시스템 상태가 필요하면 애플리케이션 서비스가, 그 객체 자신의 상태만 있으면 되면 도메인 객체가 맡는다. 계층별로 감으로 나누지 않는다.
  • 2
    "DTO에서 했는데 도메인에서 또 하면 낭비 아닌가"에는 목적으로 답한다 — DTO 검증은 사용자에게 친절한 400을 주기 위한 것이고, 도메인 불변식은 유효하지 않은 객체가 만들어지는 것 자체를 막기 위한 것이다. @Valid는 웹 입구 하나만 지키고, 도메인은 배치·메시지 컨슈머·내부 호출·테스트까지 전부 지킨다 — 그리고 컨트롤러를 안 거치는 경로는 시간이 지날수록 늘어난다.
  • 3
    진짜 중복은 "복붙된 규칙"이고, 답은 지우기가 아니라 봉인이다 — 형식 규칙은 커스텀 제약 애너테이션(@PhoneNumber)으로, 계층을 떠도는 값은 값 객체(Email)로, 상태 전이 규칙은 도메인 메서드(order.cancel())로 모은다. 핵심은 검증 횟수를 줄인 게 아니라 "검증되지 않은 값"을 타입 수준에서 표현 불가능하게 만든 것이다.

0. 질문 + 출제 의도

질문: "Bean Validation(@Valid)과 도메인 검증의 역할 분담은 어떻게 하나요? 같은 검증이 계층마다 중복되는 문제는 어떻게 정리하나요?"

출제 의도: 형식 검증(컨트롤러)과 비즈니스 규칙 검증(도메인)의 경계가 없으면 검증이 중복되거나, 더 나쁘게는 "저쪽에서 하겠지"로 누락된다. "이 검증은 누구의 책임인가"를 계층 설계로 답할 수 있는지 — 검증을 애너테이션 장식이 아니라 설계 요소로 다루는지 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "컨트롤러는 형식, 도메인은 비즈니스"에서 멈추는 것 → 4절에서 질문 하나짜리 순서도로 세 계층을 기계적으로 가른다. 감으로 나누면 사람마다 팀마다 달라진다.
② 중복을 "지워서" 정리하려는 것 → 6·7절에서 겉보기 중복(유지)과 진짜 중복(봉인)을 분리한다. 도메인 방어를 지우면 "컨트롤러를 거칠 때만 안전한" 시스템이 된다.
③ @Valid·@Validated·실패 예외를 뭉뚱그리는 것 → 2·3절에서 둘의 정확한 차이 3가지와 예외 3종 분기를 도식으로 못 박는다. 애너테이션 하나로 예외 타입이 바뀌는 자리가 실제로 있다.
한 문장 비유 — 정문 검색대와 금고 자물쇠 정문 검색대(@Valid)는 방문객의 신분증 형식이 맞는지 서류만 보고 판정한다 — 빠르고 친절하며, 문제가 있으면 건물에 들여보내지 않는다. 하지만 검색대는 정문 하나만 지킨다. 지하 주차장·비상계단(배치 잡·메시지 컨슈머·내부 호출·테스트)으로 들어온 사람은 검색대를 지나지 않는다. 그래서 금고 자체에 자물쇠(도메인 불변식)가 필요하다 — 자물쇠는 누가 어떤 통로로 왔든 열쇠 없이는 열리지 않는다. 검색대와 자물쇠는 중복이 아니라 역할 분담이고, 검색대가 있다고 자물쇠를 떼는 것이 이 질문에서 가장 흔한 오답이다.

1. Bean Validation이 도는 정확한 자리

Bean Validation은 "객체의 필드가 지켜야 할 제약을 애너테이션으로 선언하면 그것을 검사해 주는" 자바 표준 스펙이다. 패키지 이름이 jakarta.validation이고, 스펙은 규격만 정의할 뿐 실제 검사를 수행하는 구현체는 따로 있다. 스프링 부트가 기본으로 끌고 오는 구현체는 Hibernate Validator다.

먼저 확인할 전제 — 의존성이 없으면 애너테이션은 장식일 뿐이다 spring-boot-starter-validation을 넣어야 구현체가 들어온다. 그게 없으면 @NotBlank가 붙어 있어도 아무 일도 일어나지 않는다 — 오류도 경고도 없이, 그냥 검증이 없는 것처럼 동작한다. "@Valid를 붙였는데 검증이 안 돕니다"의 1순위 원인이다.

스프링 MVC는 컨트롤러 파라미터에 @Valid나 @Validated가 붙어 있으면 컨트롤러 메서드 본문에 들어가기 전에 검증을 실행한다. 정확히 어느 지점인지, 그리고 그 자리에서 걸러야 이득이 무엇인지를 파이프라인 위에 찍으면 이렇다.

기준 코드 이 페이지 전체가 이 예제 위에서 돈다
public record SignUpRequest(
        @NotBlank @Email String email,
        @NotBlank @Size(min = 8, max = 64) String password,
        @NotNull @Past LocalDate birthDate
) {}

@PostMapping("/members")
public MemberResponse signUp(@RequestBody @Valid SignUpRequest request) {
    // 여기 도달했다는 것은 위 제약을 전부 통과했다는 뜻이다.그래서 재확인이 필요 없다
    // 그래서 이 메서드 안에서 email 이 null 인지 다시 확인할 필요가 없다.
    return memberService.signUp(request.toCommand());
}

이 계층이 거르는 것의 공통 성질 — 4절 분담 기준의 출발점

여기서 거르는 것은 전부 "요청 값 자체만 보고 판정 가능한 것"이다

null · 공백 여부, 길이, 숫자 범위, 날짜의 과거/미래, 정규식 패턴. DB를 볼 필요도, 다른 객체를 볼 필요도 없다. 이 한 문장이 4절 순서도의 첫 질문이 된다.

2. @Valid vs @Validated — 헷갈리기 전에 소속부터

주니어가 가장 많이 헷갈리는 지점이다. 둘은 서로 다른 물건이고, 소속부터 다르다.

@Valid — 자바 표준

jakarta.validation.Valid
Bean Validation 스펙이 정의한 애너테이션. 스프링이 아니라 자바 진영의 규격이다.

@Validated — 스프링

org.springframework.validation.annotation.Validated
스프링이 표준에 없는 두 가지를 채우려고 직접 만든 애너테이션이다.

차이는 셋이고, 각각이 실무에서 대응하는 상황이 다르다. "컨트롤러냐 서비스냐"로 외운 답은 절반만 맞다 — 첫 줄을 보라.
@Valid (표준)@Validated (스프링)
컨트롤러 파라미터에서 검증 트리거된다된다
차이 ① 검증 그룹(groups) 지정불가능가능
차이 ② 클래스에 붙여 메서드 파라미터 검증(AOP) 켜기불가능가능
차이 ③ 필드에 붙여 중첩 객체로 검증 전파(cascade)가능불가능

2-1. 차이 ① 검증 그룹 — 같은 DTO, 다른 규칙

같은 DTO를 등록과 수정에서 다른 규칙으로 검증하고 싶을 때 쓴다. 예를 들어 id는 수정 요청에는 필수지만 등록 요청에는 없어야 한다. 제약마다 어느 그룹에 속하는지 표시해 두고, 파라미터에서 그룹을 골라 지정한다.

public interface OnCreate {}
public interface OnUpdate {}   // 그룹은 "표지"일 뿐이라 빈 인터페이스면 충분하다

public record ProductRequest(
        @Null(groups = OnCreate.class)      // 등록 때는 id 가 없어야 한다
        @NotNull(groups = OnUpdate.class)   // 수정 때는 id 가 있어야 한다
        Long id,
        @NotBlank(groups = {OnCreate.class, OnUpdate.class}) String name
) {}

// @Validated 의 괄호 안에 그룹을 지정한다. @Valid 에는 이 자리가 없다.
@PostMapping("/products")
public void create(@RequestBody @Validated(OnCreate.class) ProductRequest req) { ... }

@PutMapping("/products/{id}")
public void update(@RequestBody @Validated(OnUpdate.class) ProductRequest req) { ... }

2-2. 차이 ② 클래스에 붙이면 메서드 파라미터 검증이 켜진다

컨트롤러가 아닌 일반 스프링 빈(서비스 등)의 메서드 파라미터에 제약을 걸고 싶을 때 쓴다. 이때 동작 방식은 컨트롤러 파라미터 검증과 완전히 다르다 — AOP 프록시가 메서드 호출을 가로채 검사한다. 이 사실이 9절의 자기 호출 함정으로 이어진다.

@Service
@Validated   // 클래스에 붙여야 이 빈의 메서드 파라미터 검증이 활성화된다
public class PointService {

    // 컨트롤러가 아닌 서비스 메서드인데도 제약이 검사된다
    public void charge(@NotNull Long memberId, @Min(1000) int amount) { ... }
}

2-3. 차이 ③ 중첩 객체로 파고드는 것은 @Valid만 한다

DTO 안에 또 다른 객체가 있을 때, 그 필드에 @Valid를 붙여야 안쪽까지 검증한다. 이건 Bean Validation 스펙이 @Valid를 "여기서부터 안으로 들어가라"는 표시(cascade 마커)로 정해 놓았기 때문이고, 스프링 애너테이션인 @Validated를 필드에 붙여 봐야 아무 일도 일어나지 않는다.

public record OrderRequest(
        @NotNull Long itemId,
        // @Valid 가 없으면 shipping 이 null 인지만 보고, 그 안의 제약은 검사하지 않는다.
        @Valid @NotNull ShippingInfo shipping,겉만 검증되고 속은 통과하는 대표 함정

        // 컬렉션은 요소 하나하나까지 파고들어야 한다.
        // 타입 인자 자리의 @Valid 표기(Bean Validation 2.0 의 컨테이너 요소 검증)를 쓰거나,
        // 필드 자체에 @Valid 를 붙여도 요소로 전파된다.
        @NotEmpty List<@Valid OrderLine> lines
) {}

한 문장으로 봉인 — "컨트롤러냐 서비스냐"가 아니다

그룹이 필요하면 @Validated, 중첩 전파가 필요하면 @Valid

컨트롤러 @RequestBody 파라미터에는 둘 다 쓸 수 있고 검증도 둘 다 돈다. 실제로 스프링 내부에서 두 애너테이션을 함께 인식하는 곳이 있고(ValidationAnnotationUtils), @Validated는 거기서 그룹까지 함께 넘긴다. 실무에서는 파라미터에 @Valid, 그룹이 필요한 자리에만 @Validated를 쓰는 것이 일반적이다.

이 문서의 버전 기준 버전 의존 서술은 Spring Boot 3.2 이상 / Spring Framework 6.1 이상 기준이며, 예외 타입은 Spring Framework 6.1과 6.2 소스에서 직접 확인한 것이다. 6.0 이하에서 달라지는 부분은 그때마다 표시한다.

3. 검증 실패 예외는 세 종류다

이걸 모르면 "MethodArgumentNotValidException 핸들러를 만들어 뒀는데 어떤 요청은 응답 포맷이 깨져 나간다"는 상황을 만난다. 검증이 어디서 어떻게 돌았느냐에 따라 예외가 갈린다.

같은 내용을 표로 — 기본 상태 코드 열의 마지막 줄이 이 표의 핵심이다.
검증이 걸린 자리던져지는 예외기본 상태 코드
@RequestBody + @Valid (JSON 본문 DTO)MethodArgumentNotValidException400
@ModelAttribute (쿼리 파라미터·폼 바인딩)MethodArgumentNotValidException (6.1 이상)400
컨트롤러 메서드 파라미터에 직접 붙은 제약
@RequestParam @Min(1) int page		HandlerMethodValidationException (6.1 이상)400
@Validated 클래스의 메서드 파라미터 검증 (서비스 빈 등)ConstraintViolationException없음 → 그대로 두면 500

3-1. 버전에 따라 달라지는 두 가지 — 오래된 자료를 그대로 믿으면 틀린다

① @ModelAttribute 실패는 지금 BindException이 아니다

오래된 자료에는 "@RequestBody면 MethodArgumentNotValidException, @ModelAttribute면 BindException"이라고 적혀 있다. Spring Framework 6.x의 ModelAttributeMethodProcessor는 MethodArgumentNotValidException을 던진다.

다만 MethodArgumentNotValidException이 BindException을 상속하도록 바뀌었기 때문에 @ExceptionHandler(BindException.class)를 등록해 두면 양쪽 다 잡힌다. 옛 방식으로 짠 핸들러가 여전히 동작하는 이유가 이것이다.

② 단일 파라미터 제약은 6.1부터 @Validated 없이도 검증된다

예전에는 @RequestParam @Min(1) int page 같은 제약을 검사하려면 컨트롤러 클래스에 @Validated를 붙여야 했고, 실패하면 ConstraintViolationException이 나왔다.

6.1부터는 컨트롤러 메서드 파라미터에 제약 애너테이션이 있으면 프레임워크가 내장 메서드 검증을 수행하고 HandlerMethodValidationException(입력 검증 실패는 400)을 던진다. @Validated가 필요 없어진 것이다.

그런데 여기에 함정이 붙는다 — 붙였느냐 안 붙였느냐로 예외가 갈린다

클래스에 @Validated가 붙어 있으면 내장 검증이 꺼지고 AOP 프록시 쪽으로 넘어간다. 스프링이 그렇게 만들어 둔 이유는 같은 검증이 두 번 돌지 않게 하기 위해서인데, 결과적으로 같은 코드에서 예외 타입이 달라진다.

컨트롤러 메서드에 @Min(1) 직접 → 클래스에 @Validated 없음 → HandlerMethodValidationException (400)
컨트롤러 메서드에 @Min(1) 직접 → 클래스에 @Validated 있음 → ConstraintViolationException (핸들러 없으면 500)

3-2. 세 종류를 하나의 포맷으로 수렴시키는 핸들러

// 세 종류를 같은 포맷으로 수렴시킨다. 하나라도 빠지면 그 경로만 응답 모양이 다르다.
@RestControllerAdvice
public class ValidationExceptionHandler {

    // ① @RequestBody / @ModelAttribute 실패.
    //    BindException 으로 받으면 MethodArgumentNotValidException 도 함께 잡힌다(상속 관계).
    @ExceptionHandler(BindException.class)
    public ResponseEntity<ErrorResponse> handleBind(BindException e) {
        List<ErrorResponse.FieldError> errors = e.getBindingResult().getFieldErrors().stream()
                .map(f -> new ErrorResponse.FieldError(f.getField(), f.getDefaultMessage()))
                .toList();
        return ResponseEntity.badRequest()
                .body(ErrorResponse.of(ErrorCode.INVALID_INPUT, errors));
    }

    // ② @Validated 빈의 메서드 파라미터 검증 실패.
    //    스프링이 기본 처리해 주지 않으므로 직접 등록해야 500 이 안 나간다.
    @ExceptionHandler(ConstraintViolationException.class)이걸 빼면 그 경로만 500
    public ResponseEntity<ErrorResponse> handleConstraint(ConstraintViolationException e) {
        List<ErrorResponse.FieldError> errors = e.getConstraintViolations().stream()
                // propertyPath 는 "charge.amount" 같은 메서드.파라미터 형태다.
                // 클라이언트에게는 마지막 마디(파라미터명)만 주는 편이 쓸모 있다.
                .map(v -> new ErrorResponse.FieldError(
                        lastNode(v.getPropertyPath()), v.getMessage()))
                .toList();
        return ResponseEntity.badRequest()
                .body(ErrorResponse.of(ErrorCode.INVALID_INPUT, errors));
    }
}

5. 불변식 — 웹 입구 하나를 지키는 것과 모든 경로를 지키는 것

불변식(invariant)은 "그 객체가 살아 있는 동안 언제나 참이어야 하는 조건"이다. 생성자에서 그것을 보장하고, 이후 어떤 메서드도 그것을 깨뜨리지 않는다. "금액은 음수일 수 없다", "주문에는 최소 한 개의 주문 항목이 있다", "계좌 잔액은 0 이상이다" 같은 것들이다.

이름의 "불변"은 값이 안 바뀐다는 뜻이 아니라 조건이 항상 참으로 유지된다는 뜻이다.

검증과 불변식의 관계 — 한 문장

검증은 "지금 이 값이 맞는지 확인하는 행위"이고,
불변식은 "틀린 상태가 애초에 존재할 수 없게 만드는 성질"이다

후자가 훨씬 강하다. 잘못된 상태를 만들 방법이 없으면 그 상태를 검사할 필요도 없어지기 때문이다.

6. "중복" 문제 — 겉보기 중복과 진짜 중복을 먼저 가른다

DTO에서 @Size(min = 8)을 검증했는데 도메인 생성자에서도 길이를 확인한다. 이건 중복인가?

DTO 검증의 목적

사용자에게 친절한 400 응답

  • 필드별 메시지 — 어느 칸을 고쳐야 하는지
  • 다국어 메시지
  • 여러 오류를 한 번에 알려주기

도메인 검증의 목적

유효하지 않은 객체의 존재 자체를 차단

  • 개발자 실수 방어
  • 웹 아닌 경로 방어 (배치·컨슈머·테스트)
  • 메시지 품질은 신경 쓸 필요가 없다
목적이 다르니 만듦새도 달라야 한다 도메인 쪽은 사용자 응답용 메시지를 다듬을 필요 없이 IllegalArgumentException으로 단순하게 던지면 된다. 정상 운영에서는 DTO 검증이 먼저 걸러 주므로 도메인 예외가 실제로 터진다는 것은 앞 계층이 뚫렸다는 뜻이고, 그래서 도메인 예외는 사용자 안내가 아니라 버그 감지기로 동작한다. 이 이중 방어는 비용이 거의 없고 이득이 커서 "의도된 중복"으로 받아들이는 것이 일반적인 결론이다.

6-1. 그럼 정리해야 할 진짜 중복은 무엇인가

① 같은 형식 규칙이 여러 DTO에 복붙
전화번호 정규식이 가입·수정·관리자 등록 DTO에 각각 박혀 있고, 정책이 바뀌면 하나를 빼먹는다.
→ 처방: 커스텀 제약 애너테이션 (7-1) · 값 객체 (7-2)
② 같은 비즈니스 검증이 서비스 여기저기에 복붙
"취소 가능한 상태인가"를 여러 서비스 메서드가 각자 if문으로 검사한다.
→ 처방: 도메인 메서드로 봉인 (7-3)

계층 간 중복은 목적이 다르면 중복이 아니고, 진짜 중복은 같은 목적의 같은 규칙이 여러 파일에 복사된 것이다

7-2. 값 객체로 봉인 — "검증되지 않은 값"을 타입 수준에서 없앤다

애너테이션으로 규칙을 모으는 것은 DTO 계층 안에서만 통한다. 그 값이 DTO를 떠나 서비스와 도메인을 떠돌기 시작하면 다시 "이 문자열은 검증된 것인가?"를 매번 물어야 한다.

값 객체(Value Object)는 형식과 의미가 있는 값을 원시 타입 대신 전용 타입으로 감싸, 그 타입이 존재한다는 사실 자체가 유효성의 증거가 되게 만드는 기법이다. "값"이라는 이름은 식별자(id)로 구분되는 엔티티와 달리 값이 같으면 같은 것으로 취급된다는 성질에서 왔다.

    // 취소하려면 cancel() 을 부를 수밖에 없고, cancel() 은 검증을 건너뛸 수 없다.
    // "검증을 잊을 수 없는 구조" 가 중복 제거의 종착점이다.
}

8. 계층별 실패를 에러 응답으로 옮기기

역할 분담의 마무리는 예외 매핑이다. 각 계층의 실패가 서로 다른 뜻을 가지므로 응답도 달라야 한다.

세 번째 줄이 이 표의 핵심이다 — 그리고 실무에서 가장 자주 틀리는 줄이기도 하다.
어디서 실패했나예외응답왜

"정상 흐름에서는 나올 수 없는" 예외를 400으로 내려보내면 사용자에게 "입력을 확인하세요"라고 거짓말을 하면서 우리 버그는 알람도 없이 묻힌다.

그 선언이 정확해야 로그와 알람이 제 역할을 한다. 상태 코드 선택 기준과 로그 정책은 19-global-exception-handling-error-response.md의 2-4절과 3-1절이 다룬다.

가로축은 실제로 들어오는 값이다. 파란 칸(통과)이 문제가 되는 자리다.
애너테이션적용 대상null"" (빈 문자열)" " (공백만)
@NotNull모든 타입거부통과통과
@NotEmpty문자열, 컬렉션, 맵, 배열거부거부통과
@NotBlank문자열만거부거부거부

타입별로 무엇을 쓸지는 고민할 필요가 없다

함정 ② 중첩 객체와 컬렉션 요소에 @Valid를 빠뜨린다

2-3절에서 본 그대로다. 필드에 @Valid가 없으면 그 안쪽 제약은 검사되지 않고, 겉만 통과한 요청이 서비스로 들어온다. 컬렉션도 List<@Valid OrderLine>처럼 요소까지 챙긴다.

가장 흔하면서 가장 조용한 함정 에러도 로그도 나지 않고 "검증이 도는 것처럼 보이면서 안 돈다." 그래서 코드 리뷰 체크리스트에 넣을 값어치가 있다 — "중첩 객체 필드에 @Valid 있는가", "컬렉션 요소에 @Valid 있는가" 두 줄이면 된다.

함정 ③ @Validated 메서드 검증은 프록시 기반이라 자기 호출에 무력하다

2-2절에서 본 대로 이 검증은 AOP 프록시가 호출을 가로채 수행한다. 그런데 같은 클래스 안에서 this.charge(...)로 부르면 그 호출은 프록시를 거치지 않고 원본 객체 안에서 곧바로 일어나므로, 가로챌 기회 자체가 없어 검증이 통째로 건너뛰어진다.

@Service
@Validated
public class PointService {

    public void chargeAll(List<Long> memberIds) {
        for (Long id : memberIds) {
            // 문제: 이 호출은 프록시를 거치지 않는다.
            //       amount 가 0 이어도 @Min(1000) 이 검사되지 않는다.
            this.charge(id, 0);에러가 아니라 "조용히 검증 없이" 통과한다
        }
    }

    public void charge(@NotNull Long memberId, @Min(1000) int amount) { ... }
}
일반화까지 말하면 한 칸 올라간다 @Transactional 자기 호출 함정과 정확히 같은 뿌리다. 원인(메모리에 원본과 프록시 두 객체가 있고 this는 프록시가 아니다)과 해법 네 가지의 트레이드오프는 11-transactional-self-invocation.md가 다룬다. 여기서 가져갈 것은 "프록시 기반 부가 기능은 전부 이 함정을 공유한다"는 일반화다 — @Transactional · @Cacheable · @Async · @Validated.

함정 ④ DB 조회가 필요한 검증을 ConstraintValidator 안에 숨긴다

커스텀 Validator는 스프링 빈이라 Repository를 주입받을 수 있고, 그래서 "이메일 중복 검사"를 @UniqueEmail 같은 애너테이션으로 만들고 싶어진다. 기술적으로 되는데 권하지 않는 이유 셋은 10절 꼬리질문에서 전개한다 — 요약하면 트랜잭션 경계 · TOCTOU · 테스트 무게다.

함정 ⑤ AI 생성 코드의 검증 배치

AI가 만든 코드는 두 극단으로 치우치는 패턴이 흔하다 — 검증을 서비스 메서드 첫머리의 if문 뭉치로 몰아넣거나, 반대로 DTO 애너테이션만 붙이고 도메인을 무방비로 두거나.

리뷰 체크리스트 셋 — 그대로 옮겨 쓸 수 있는 형태

①
형식 검증이 DTO에 있는가
서비스 첫머리 if문 뭉치로 내려와 있지 않은가
②
도메인 객체가 불변식을 스스로 지키는가
setter로 상태를 바꾸고 있지 않은가
③
DB가 필요한 검증이 Validator 안에 숨어 있지 않은가
Repository를 주입받은 ConstraintValidator가 있는가

암기 장치 — 함정 5종은 "낫 · 중 · 자 · 숨 · 쏠"

낫(@Not* 3종 혼동) · 중(중첩 @Valid 누락) · 자(자기 호출) · 숨(Validator에 DB 숨기기) · 쏠(AI 코드의 한쪽 쏠림)

이 중 ②(중)와 ③(자)은 예외도 로그도 없이 조용히 통과한다는 공통점이 있다. "실패가 시끄럽지 않은 함정"이 가장 위험하다는 점까지 말하면 답이 정돈된다.

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

분담 기준 한 줄은?
"이 검증에 요청 값 말고 무엇이 더 필요한가" — 없다 → DTO(400) / DB → 서비스(409) / 자기 상태 → 도메인(불변식).
@Valid vs @Validated?
그룹이면 @Validated, 중첩 전파면 @Valid. 소속도 다르다(표준 vs 스프링). 컨트롤러 @RequestBody엔 둘 다 된다.
검증 실패 예외 3종은?
본·파·빈 — 본문 MethodArgumentNotValid(=Bind) · 파라미터 HandlerMethodValidation · 빈 ConstraintViolation. 막내만 스프링이 안 챙긴다.
같은 코드인데 예외가 갈리는 자리는?
컨트롤러 클래스에 @Validated가 붙으면 내장 검증이 꺼지고 AOP로 넘어가 ConstraintViolationException이 된다.
불변식의 정의는?
객체가 살아 있는 동안 언제나 참이어야 하는 조건. "불변"은 값이 아니라 조건이 유지된다는 뜻.
"중복 아니냐"의 답은?
@Valid는 웹 입구 하나, 도메인은 모든 경로(배치·컨슈머·테스트). 목적이 다르면 중복이 아니다.
진짜 중복 2종과 처방은?
형식 규칙 복붙 → 커스텀 제약 애너테이션 · 값 객체 / 상태 규칙 복붙 → 도메인 메서드.
값 객체의 핵심 효과는?
검증 횟수 감소가 아니라 "검증되지 않은 상태"를 타입 수준에서 표현 불가능하게 만든 것.
불변식 위반은 몇 번으로 응답?
500 + 알람. 400으로 내리면 사용자에게 거짓말하면서 우리 버그가 4xx에 묻힌다.
함정 5종은?
낫·중·자·숨·쏠 — @Not* 혼동 · 중첩 @Valid 누락 · 자기 호출 · Validator에 DB 숨기기 · AI 코드 쏠림.
문자열엔 어떤 @Not*?
@NotBlank(공백만도 거부). 컬렉션엔 @NotEmpty, 숫자·날짜엔 @NotNull.
중복 정리의 방향은?
지우기가 아니라 봉인 — 한곳에 모으고 나머지는 타입과 메서드를 믿는다. 종착점은 "검증을 잊을 수 없는 구조".

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

@Valid와 @Validated의 차이는 무엇인가요? 필수힌트: 소속부터 말하고 → 차이 셋 → "둘 다 컨트롤러에서 돈다"를 정확히 짚는다

소속이 다르다는 것부터 말한다. @Valid는 jakarta.validation의 자바 표준이고, @Validated는 스프링이 만든 것이다.

차이는 셋이다. ① @Validated는 검증 그룹을 지정할 수 있다 — 같은 DTO를 등록과 수정에서 다른 규칙으로 검증할 때 쓴다. ② @Validated를 클래스에 붙이면 컨트롤러 밖 스프링 빈의 메서드 파라미터 검증이 AOP 프록시로 켜진다. ③ 반대로 중첩 객체로 검증을 전파하는 것은 @Valid만 한다 — cascade 마커는 Bean Validation 스펙이 @Valid로 정해 놓았기 때문이다.

컨트롤러 @RequestBody 파라미터에는 둘 다 쓸 수 있고 검증도 둘 다 돈다는 점을 정확히 말하는 것이 중요하다. "@Valid는 컨트롤러, @Validated는 서비스"라는 식으로 외운 답은 절반만 맞다. 그룹이 필요하면 @Validated, 중첩 전파가 필요하면 @Valid가 정확한 기준이다.

여기에 ②의 대가를 덧붙이면 좋다. 프록시 기반이라 자기 호출에는 적용되지 않고, 실패 예외도 달라서 전역 예외 처리에서 따로 매핑해야 한다.

검증 실패 시 어떤 예외가 던져지나요? 함정힌트: "한 종류가 아니다"로 시작한다. 그리고 셋 중 하나만 스프링이 안 챙긴다

한 종류가 아니라는 것이 이 질문의 답이다. Spring Framework 6.1 이상 기준으로 셋을 구분한다.

① @RequestBody나 @ModelAttribute 바인딩 검증 실패 → MethodArgumentNotValidException. 이 예외가 BindException을 상속하므로 @ExceptionHandler(BindException.class) 하나로 둘 다 잡힌다. (오래된 자료의 "@ModelAttribute는 BindException"은 6.x에서는 정확하지 않다.)

② 컨트롤러 메서드 파라미터에 직접 붙은 제약 → HandlerMethodValidationException. 6.1부터는 @Validated 없이도 프레임워크가 내장 검증을 수행한다. 다만 클래스에 @Validated를 붙이면 내장 검증이 꺼지고 AOP 쪽으로 넘어가 ConstraintViolationException이 나온다 — 애너테이션 하나로 예외 타입이 바뀐다는 것이 핵심이다.

③ @Validated 클래스의 메서드 파라미터 검증 → ConstraintViolationException.

마무리로 실무 결론을 낸다. ③만 스프링이 챙겨 주지 않는다. ResponseEntityExceptionHandler의 기본 처리 목록에 ①과 ②는 있지만 ConstraintViolationException은 없어서, 매핑을 빠뜨리면 사용자 입력 문제인데 500이 나가고 5xx 알람까지 울린다.

DTO에서 검증했는데 도메인에서 또 검증하는 건 낭비 아닌가요? 시니어 변별힌트: "목적이 다르다"로 시작하고, "웹을 안 거치는 경로"를 구체적으로 나열한다

목적이 달라서 낭비가 아니다. DTO 검증은 웹 입구에서 사용자에게 친절한 400을 주기 위한 것이고, 도메인 검증(불변식)은 웹을 거치지 않는 모든 경로 — 배치, 메시지 컨슈머, 다른 서비스 메서드, 테스트 — 에서 유효하지 않은 객체가 만들어지는 것 자체를 막기 위한 것이다.

도메인 방어를 지우고 DTO만 믿으면 "컨트롤러를 거칠 때만 안전한" 시스템이 된다. 그리고 컨트롤러를 안 거치는 경로는 시간이 지날수록 늘어난다.

다만 비용을 줄이는 방향은 분명히 있다는 것도 말한다. 도메인 쪽은 메시지 국제화 같은 응답 품질을 신경 쓸 필요 없이 IllegalArgumentException만 던지면 되고, 값 객체를 쓰면 검증 코드 자체는 한곳에만 존재한다.

한 문장으로 압축하면 "중복처럼 보이는 이중 방어는 유지하되, 검증 로직의 소스는 하나로"다.

이메일 중복 검사처럼 DB 조회가 필요한 검증은 어느 계층에서 하나요? 커스텀 Validator에서 Repository를 주입받으면 안 되나요? 시니어 변별힌트: "기술적으로는 되지만"으로 시작한다. 이유 셋 + 정석은 이중 구조

애플리케이션/도메인 계층이 정답이다. 기술적으로는 ConstraintValidator가 스프링 빈이라 Repository 주입이 가능하지만 권하지 않고, 이유가 셋이다.

① 트랜잭션 경계가 어긋난다. 검증은 바인딩 직후, 즉 서비스의 트랜잭션이 열리기 전에 돈다. 그래서 검증 조회와 본 로직이 서로 다른 트랜잭션에서 일어나고, 그 사이에 데이터가 바뀔 수 있다.

② 어차피 시점 문제를 못 막는다. "중복 없음" 판정 직후 다른 요청이 끼어들어 같은 이메일을 넣으면 판정은 무의미해진다. 이렇게 검사한 시점과 사용하는 시점 사이에 상태가 바뀔 수 있는 문제를 TOCTOU(time-of-check to time-of-use)라고 부른다. 그래서 DB 유니크 제약이라는 최종 방어가 반드시 필요하다.

③ DTO 단위 테스트가 무거워진다. 형식 검증기에 DB 의존이 생기면 그 DTO를 검증하는 테스트마다 Repository를 준비해야 한다.

정석은 이중 구조다. 사전 중복 검사는 서비스에서 UX용으로 하고(사용자에게 친절한 메시지를 주기 위해), 최종 보장은 유니크 제약 + DataIntegrityViolationException 처리로 한다. 앞의 것은 편의이고 뒤의 것이 진짜 방어라는 역할 구분을 말하면 정확한 답이 된다.

값 객체로 검증을 옮기면 구체적으로 무엇이 좋아지나요? 가산점힌트: 셋을 들고, 마지막에 비용과 선별 기준까지 붙여야 균형이 잡힌다

셋을 든다.

① 검증 로직이 타입 하나에 봉인되어 중복이 사라진다. 규칙 변경이 한 파일 수정으로 끝난다.

② 시그니처가 문서가 된다. String email은 "검증됐는지 알 수 없는 문자열"이지만 Email은 존재 자체가 유효성 증명이라, 받는 쪽에서 재검증할 필요가 없어진다. 핵심은 검증 횟수를 줄인 것이 아니라 "검증되지 않은 이메일"이라는 상태를 타입 수준에서 표현 불가능하게 만든 것이다.

③ 같은 타입의 값이 여러 개일 때 순서 실수를 컴파일러가 잡는다. transfer(from, to)에 계좌번호 문자열 두 개를 바꿔 넣는 류의 버그다.

비용도 함께 말한다. 클래스 수가 늘고 JPA 매핑(@Embeddable, AttributeConverter) 손질이 필요하다. 그래서 모든 원시 타입을 감싸는 것이 아니라 규칙이 있고 여러 계층을 떠도는 핵심 도메인 값부터 선별 적용한다는 판단 기준까지 말하면 균형이 잡힌다.

검증 실패 응답은 어떻게 표준화하나요? 필수힌트: 세 예외를 하나의 스키마로 수렴시키되, "하나는 분리한다"가 마지막 문장

세 종류의 예외를 하나의 형식(에러 코드, 메시지, 필드별 상세 목록)으로 수렴시킨다. BindException으로 ①과 ②를 받고(상속 관계 덕분에 MethodArgumentNotValidException도 함께 잡힌다), ConstraintViolationException을 따로 받고, 비즈니스 예외는 도메인별 에러 코드와 4xx로 매핑한다.

포인트는 클라이언트 입장에서 "어느 계층에서 실패했는지"가 아니라 "무엇을 고쳐 보내야 하는지"가 보이는 일관된 스키마를 유지하는 것이다. 검증이 컨트롤러에서 걸렸든 서비스 메서드에서 걸렸든 클라이언트에게는 같은 모양이 가야 한다.

여기에 하나를 분리해 말하면 답이 완성된다. 도메인 불변식 위반은 400이 아니라 500 + 알람으로 분리한다. 앞단 검증이 뚫렸다는 버그 신호이므로 사용자에게 "입력을 확인하세요"라고 안내하는 것 자체가 틀렸고, 그렇게 처리하면 우리 버그가 4xx 통계에 섞여 영영 안 보인다.

@Validated를 서비스에 붙여 파라미터를 검증하려는데 안 걸립니다. 무엇을 확인하나요? 함정힌트: 순서대로 셋. 마지막에 "프록시 기반 부가 기능은 전부 같은 조건"으로 일반화

세 가지를 순서대로 확인한다.

① 클래스에 @Validated가 붙어 있는가. 파라미터에만 제약을 붙이고 클래스 애너테이션을 빼먹으면 AOP가 꽂히지 않아 아무 검증도 돌지 않는다. 컨트롤러가 아닌 일반 빈에서는 이것이 가장 흔한 원인이다.

② 자기 호출이 아닌가. 같은 클래스 안에서 this.method(...)로 부르면 프록시를 거치지 않아 검증이 통째로 건너뛰어진다. @Transactional 자기 호출과 같은 뿌리이고, 에러가 나는 것이 아니라 조용히 통과한다는 점이 악질이다. 별도 빈으로 분리하는 것이 정석 해법이다.

③ 호출자가 프록시를 통해 부르고 있는가. 다른 빈에서 주입받아 부른 것이라면 프록시를 거치므로 정상이다. new로 직접 만든 인스턴스나, final 메서드라 CGLIB이 오버라이드하지 못하는 경우는 걸리지 않는다.

"프록시 기반 부가 기능은 전부 같은 조건을 공유한다"는 일반화까지 말하면 좋다. @Transactional, @Cacheable, @Async, @Validated가 안 먹는다는 신고는 대체로 이 셋 중 하나다.

@Valid를 붙였는데 검증이 아예 안 돕니다. 무엇부터 확인하나요? 함정힌트: "일부만 안 도는" 것과 "아예 안 도는" 것은 원인이 다르다

"아예 안 돈다"와 "일부만 안 돈다"를 먼저 구분하는 것이 진단의 출발점이다.

아예 안 돈다면 1순위는 의존성이다. Bean Validation은 스펙일 뿐이고 실제 검사는 구현체(Hibernate Validator)가 한다. spring-boot-starter-validation이 없으면 애너테이션은 붙어 있어도 오류도 경고도 없이 아무 일이 일어나지 않는다. 다음으로 파라미터에 @Valid(또는 @Validated) 자체를 안 붙였는지, 커스텀 애너테이션이라면 @Constraint와 @Retention(RUNTIME)이 빠지지 않았는지를 본다.

일부만 안 돈다면 원인이 다르다. 중첩 객체·컬렉션 요소에 @Valid가 없어서 안쪽만 안 도는 것(9절 함정 ②)이거나, 서비스 빈이라면 클래스에 @Validated가 없거나 자기 호출(함정 ③)이다. "전부 안 되는가, 일부만 안 되는가"가 두 원인 묶음을 가르는 첫 질문이다.

컨트롤러 파라미터에 BindingResult를 같이 받으면 어떻게 되나요? 가산점힌트: 예외가 안 던져진다 — 그게 편의이자 함정이다

검증에 실패해도 예외가 던져지지 않고 컨트롤러 메서드가 그대로 실행된다. 실패 정보는 BindingResult 안에 담겨 들어오고, 처리 책임이 프레임워크에서 개발자에게 넘어온다. (BindingResult는 검증 대상 파라미터 바로 뒤에 와야 그 대상과 짝지어진다.)

화면 렌더링형 컨트롤러에서 입력값을 유지한 채 폼을 다시 보여줘야 할 때는 유용하다. 하지만 REST API에서는 대체로 함정이다 — 3절에서 만든 전역 핸들러가 타지 않으므로 그 API만 응답 포맷이 갈라지고, if (result.hasErrors()) 분기를 빼먹으면 검증 실패한 요청이 그대로 서비스로 들어간다.

판단 기준은 "실패 응답을 이 메서드가 직접 만들어야 할 이유가 있는가"다. 없으면 BindingResult를 받지 않고 예외가 던져지게 두는 편이 포맷 일관성 면에서 낫다.

값 객체가 좋다면 요청 DTO 필드를 처음부터 Email 타입으로 받으면 안 되나요? 시니어 변별힌트: 실패가 "언제" 일어나는지를 따져 본다 — 바인딩 전인가 후인가

경계(DTO)에서는 원시 타입으로 받고, 서비스로 넘길 때 값 객체로 바꾸는 편이 낫다. 이유는 실패가 일어나는 시점에 있다.

DTO 필드가 Email이면 형식이 틀린 값은 Bean Validation이 돌기도 전에 역직렬화 단계에서 생성자 예외로 터진다. 그러면 필드별 에러 목록을 담은 400이 아니라 본문을 못 읽었다는 형태의 실패가 되고, "어느 필드가 왜 틀렸는지"와 "여러 오류를 한 번에" 알려주는 DTO 검증의 장점이 통째로 사라진다.

그래서 실무 패턴은 이중 구조다 — DTO는 String + @Email로 받아 사용자에게 친절한 400을 보장하고, toCommand() 같은 변환 지점에서 new Email(...)로 승격시켜 그 안쪽 계층부터는 값 객체만 떠돌게 한다. 1절 예제의 request.toCommand()가 바로 그 경계다. 두 검증의 목적이 다르다는 6절 논지가 여기서도 그대로 적용된다.

커스텀 제약 애너테이션의 @Constraint(validatedBy = {})에서 빈 배열은 무슨 뜻인가요? 가산점힌트: Validator를 "직접 만드는 경우"와 "기존 제약을 합성하는 경우"를 나눈다

"이 애너테이션 전용 검사 클래스는 없고, 위에 붙여 둔 제약들을 그대로 물려준다(합성한다)"는 뜻이다. @PhoneNumber가 하는 일은 @Pattern 하나를 이름 있는 규칙으로 포장하는 것뿐이라 별도 ConstraintValidator가 필요 없다.

반대로 기존 제약의 조합으로 표현되지 않는 규칙(예: 체크섬 계산, 특정 코드 체계 검사)이라면 ConstraintValidator 구현 클래스를 만들어 validatedBy에 지정한다. 이때 그 Validator는 스프링 빈이라 의존성 주입이 가능한데, 그렇다고 Repository를 주입해 DB 조회를 넣으면 안 된다는 것이 9절 함정 ④다.

@ReportAsSingleViolation도 함께 알아두면 좋다. 내부 제약이 여러 개일 때 위반 메시지가 여러 줄로 튀어나오는 것을 막고, @PhoneNumber가 정의한 메시지 하나로 묶어 응답한다 — 규칙의 내부 구현을 클라이언트에게 노출하지 않는다는 점에서도 값이 있다.

한 줄 요약
역할 분담의 기준은 "이 검증에 요청 값 말고 무엇이 더 필요한가" 하나이고 — 요청 값만으로 판정되는 형식 검증은 컨트롤러의 Bean Validation이 400으로 걸러 내고(그때 @Valid는 중첩 전파, @Validated는 그룹과 메서드 검증이라는 서로 다른 물건이며 실패 시 던져지는 예외도 셋으로 갈린다), DB 상태가 필요하면 애플리케이션 서비스가, 객체가 살아 있는 동안 언제나 참이어야 할 불변식이면 도메인 객체가 스스로 지킨다 — 목적이 다른 이중 방어는 중복이 아니라 "웹 입구만 지키는 것"과 "모든 경로를 지키는 것"의 역할 분담이고, 정리해야 할 진짜 중복(복붙된 규칙)은 검증을 지워서가 아니라 커스텀 제약 애너테이션과 값 객체로 한곳에 봉인해 "검증되지 않은 값이 타입 수준에서 존재할 수 없는 구조"로 만드는 것이 답이다.
