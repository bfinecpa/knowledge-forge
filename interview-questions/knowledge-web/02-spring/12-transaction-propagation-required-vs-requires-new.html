트랜잭션 전파 REQUIRED vs REQUIRES_NEW
바깥 트랜잭션을 물려받을 것인가, 새로 열 것인가

면접 질문: "@Transactional의 전파(propagation) 옵션 중 REQUIRED와 REQUIRES_NEW의 차이와 실무 활용 사례는?"

핵심 관전 포인트 — 전파는 트랜잭션 경계를 가진 메서드가 또 다른 트랜잭션 메서드를 호출했을 때 "바깥에 이미 열려 있는 트랜잭션을 물려받을 것인가"를 정하는 규칙이다. REQUIRED(기본값)는 물려받는다 — 새 BEGIN이 아예 나가지 않고 같은 커넥션·같은 물리 트랜잭션을 그대로 쓰며, 안쪽 메서드가 정상 종료할 때의 "커밋"은 실제 COMMIT이 아니라 아무 일도 하지 않는 것이다. 그래서 둘은 한 몸이 되고, 그 운명 공동체의 실체는 안쪽 실패가 공유 트랜잭션에 찍는 rollback-only 플래그다. REQUIRES_NEW는 물려받지 않는다 — 바깥을 유보(suspend)하고 커넥션을 하나 더 얻어 독립된 물리 트랜잭션을 열기 때문에 본 처리가 롤백돼도 이력은 남지만, 대가로 스레드 하나가 커넥션 2개를 동시에 점유한다. 풀 크기 10에 이 경로를 타는 요청 10개가 동시에 들어오면 전원이 첫 커넥션을 쥔 채 두 번째를 기다려 connectionTimeout까지 API 전체가 멈춘다. 교착을 원천 차단하는 풀 크기는 스레드 수 x (스레드당 최대 커넥션 - 1) + 1인데 톰캣 기본 스레드 200을 대입하면 201이라는 비현실적인 수가 나온다 — 그래서 답은 풀을 키우는 것이 아니라 스레드당 커넥션 수를 1로 되돌리는 것이다.
  • 1
    전파는 "안쪽이 바깥 트랜잭션을 물려받을지"의 규칙이고, 갈림길은 물리 트랜잭션을 공유하느냐다 — REQUIRED는 진행 중인 트랜잭션에 합류한다. 새 BEGIN도, 새 커넥션도 없다. 안쪽이 정상 리턴해도 COMMIT은 나가지 않고, 실제 커밋은 트랜잭션을 시작한 가장 바깥에서 단 한 번 일어난다.
  • 2
    REQUIRES_NEW는 바깥을 유보하고 커넥션을 하나 더 빌려 독립 물리 트랜잭션을 연다 — 그래서 본 처리가 롤백돼도 실패 이력은 남는다. 넣을지 판별하는 기준은 하나다. "본 처리가 롤백된 세상에 이 데이터만 남아 있어도 되는가" — 감사 로그·시도 이력은 예, 재고·잔액은 아니오(부분 커밋을 설계로 못 박는 실수).
  • 3
    그 독립에는 청구서가 붙는다 — 스레드당 커넥션 2개 동시 점유. 풀 10 + 동시 요청 10이면 서로가 서로를 기다리는 풀 자기 데드락이고 connectionTimeout(HikariCP 기본 30초)까지 API가 멈춘다. 원천 차단 풀 크기 Tn x (Cm - 1) + 1은 톰캣 스레드 200 기준 201이라 비현실적이므로, 처방은 풀 확대가 아니라 Cm을 1로 되돌리는 것 — 아웃박스 · 커밋 후 이벤트 · 큐 위임이다.

0. 질문 + 출제 의도

질문: "@Transactional의 전파(propagation) 옵션 중 REQUIRED와 REQUIRES_NEW의 차이와 실무 활용 사례는?"

출제 의도: "본 처리는 롤백돼도 감사 로그는 남아야 한다" 같은 요구사항을 구현하는 도구를 아는지, 그리고 반대로 REQUIRES_NEW 남용이 커넥션 2개 점유로 데드락과 풀 고갈을 만드는 것까지 아는지 — 도구의 비용을 아는 사람인지 본다.

이 페이지가 겨냥하는 약점 세 가지 ① "안쪽 메서드가 끝나면 거기까지는 커밋된다"는 오해 → 3절에서 커밋 권한 판정 도식으로 "합류한 논리 트랜잭션은 COMMIT을 보내지 않는다"를 못 박는다.
② "REQUIRES_NEW를 붙였으니 독립이다"에서 멈추는 것 → 5·6절에서 예외 전파는 별개(catch까지가 한 세트)이고 자기 호출이면 통째로 무효라는 두 함정을 분리해 낸다.
③ 비용을 숫자로 말하지 못하는 것 → 8·9절에서 풀 10 + 요청 10 = 전원 교착, 원천 차단 풀 크기 11 vs 201까지 계산으로 끌고 간다. "쓰면 위험합니다"는 답이 아니다.
한 문장 비유 — 회의실, 그리고 무효 도장 회의실: 바깥 메서드가 회의실 하나(커넥션)를 잡고 회의를 연다. REQUIRED는 합석이다 — 방을 새로 잡지 않고 들어가 앉으며, "회의 종료" 선언 권한은 방을 잡은 사람에게만 있다. REQUIRES_NEW는 옆 방을 하나 더 잡는 것인데, 원래 방을 비워두지 않고 잡아둔 채다.  /  무효 도장: 합석한 사람이 사고를 치면 공동 서류에 "이 회의 결과는 무효" 도장(rollback-only)이 찍힌다. 사고 친 사람은 붙잡을 수 있어도(try-catch), 이미 찍힌 도장은 지울 수 없다.

1. 전파란 무엇인가 — 결정되는 단 하나의 순간

전파(propagation)는 "퍼져 나감"이라는 뜻이다. 무엇이 무엇에게 퍼진다는 걸까. 답은 트랜잭션 경계가 호출 체인을 따라 안쪽으로 퍼져 나간다는 것이다.

상황을 구체적으로 그려 보자. order()에 @Transactional이 붙어 있어서 이 메서드가 시작될 때 트랜잭션이 하나 열린다. 그런데 order()가 호출하는 decrease()에도 @Transactional이 붙어 있다. 이 순간 스프링은 반드시 하나를 결정해야 한다.

"바깥에서 이미 열려 있는 그 트랜잭션을 안쪽도 그대로 물려받을 것인가, 아니면 안쪽 몫의 트랜잭션을 따로 열 것인가"

전파 옵션은 정확히 이 질문 하나에 대한 답이다. 그래서 정의는 한 문장으로 세울 수 있다 — 전파란 트랜잭션 경계를 가진 메서드가 다른 트랜잭션 메서드를 호출했을 때, 바깥의 트랜잭션을 안쪽이 어떻게 물려받을지 정하는 규칙이다.

배경 — 전파 옵션 7종을 "물려받는가 / 없으면 어떻게 하는가" 두 축으로 정리

면접에서 물어보는 건 대개 위의 둘이지만, 나머지를 같은 두 축으로 배치할 수 있으면 답이 정돈돼 보인다.

2. 전제 — 트랜잭션은 커넥션 위에 열린다

전파를 이해하려면 트랜잭션이 어디에 존재하는지부터 짚어야 한다. 트랜잭션은 자바 객체가 아니라 DB 커넥션 위에서 열리고 닫히는 상태다. JDBC로 벗겨 보면 이런 모양이다.

JDBC 트랜잭션의 실체 — 커넥션 점유 구간이 곧 트랜잭션 수명이다
Connection con = dataSource.getConnection();  // 풀에서 커넥션 한 개를 빌린다 — 여기부터 점유 구간
con.setAutoCommit(false);                     // 이 순간부터가 트랜잭션 안이다 (사실상의 BEGIN)
// ... 여러 SQL ...
con.commit();                                 // 또는 con.rollback()
con.close();                                  // 풀에 반납 — 여기서 점유 구간이 끝난다

여기서 나오는 사실 두 개가 이 문서 전체를 지배한다

① 트랜잭션 하나 = 커넥션 하나
커넥션 A에서 시작한 트랜잭션을 커넥션 B에서 커밋할 방법은 없다. 그래서 독립 트랜잭션을 연다 = 커넥션을 하나 더 빌린다가 된다.
② 커넥션은 트랜잭션이 끝나야 반납된다
트랜잭션이 길면 점유도 그만큼 길다. 그래서 유보(suspend)는 반납이 아니다 — 나중에 커밋해야 하니 놓을 수가 없다.
같은 트랜잭션에 합류한다 = 같은 커넥션을 쓴다  /  독립 트랜잭션을 연다 = 커넥션을 하나 더 빌린다

2-1. 스프링은 그 커넥션을 "스레드 창고"에 올려둔다

스프링은 진행 중인 트랜잭션의 커넥션을 TransactionSynchronizationManager라는 창고의 ThreadLocal에 담아 둔다. 같은 스레드에서 도는 리포지토리 코드는 이 창고를 뒤져 "지금 진행 중인 트랜잭션의 커넥션"을 찾아 쓴다. 그래서 서로 다른 클래스의 메서드들이 자연스럽게 같은 트랜잭션에 참여한다.

합류와 유보의 정체도 전부 이 창고에서 벌어지는 일이다. 그림 한 장으로 세워두면 뒤의 모든 동작이 여기서 파생된다.

2-2. 물리 트랜잭션과 논리 트랜잭션

물리 트랜잭션
커넥션 위에서 실제로 BEGIN부터 COMMIT/ROLLBACK까지 진행되는 진짜 트랜잭션. DB가 인식하는 단위이고 커밋·롤백의 실제 단위다.
논리 트랜잭션
@Transactional이 붙은 메서드 하나하나에 대응하는 스프링의 관리 단위. "이 메서드가 트랜잭션 경계다"라고 세어 두는 회계 장부에 가깝다.

논리 트랜잭션 여러 개가 물리 트랜잭션 하나를 공유할 수 있다는 것이 핵심이다. order()와 decrease()는 논리적으로는 둘이지만 물리적으로는 하나일 수 있다. 그리고 REQUIRED와 REQUIRES_NEW의 차이는 결국 한 줄로 압축된다.

물리 트랜잭션을 공유하느냐, 새로 만드느냐
두 옵션의 전체 대비 — 이 표의 3행(커넥션)과 4행(안쪽의 커밋)이 나머지 전부를 만든다.
REQUIRED (기본값)REQUIRES_NEW
바깥 트랜잭션이 있으면물려받아 합류 (물리 트랜잭션 공유)바깥을 유보하고 새로 시작
바깥 트랜잭션이 없으면새로 시작새로 시작
DB 커넥션1개를 공유별도 커넥션을 추가 획득 (동시 2개)
안쪽 메서드가 정상 종료할 때COMMIT을 보내지 않는다 (아무 일도 안 함)즉시 실제 COMMIT
커밋/롤백 운명공동체 — 한쪽 실패 시 전체 롤백독립 — 각자 커밋/롤백
안쪽 실패의 파급공유 트랜잭션에 rollback-only 플래그바깥 플래그는 무사 (단, 예외는 그대로 전파)

3. REQUIRED — "합류"의 물리적 의미

기본값이 REQUIRED인 이유는 대부분의 비즈니스 로직이 원하는 것이 "전부 성공하거나 전부 실패하거나"이기 때문이다. 주문 저장과 재고 차감이 서로 다른 서비스 메서드에 흩어져 있어도 하나의 물리 트랜잭션으로 묶여 원자성이 지켜진다.

문제는 "합류"라는 단어가 마치 두 트랜잭션이 손을 잡는 그림처럼 들린다는 것이다. 실제로 일어나는 일은 훨씬 밋밋하다 — 안쪽에서는 아무 트랜잭션도 시작되지 않는다. 스프링은 창고를 뒤져 "이미 진행 중인 트랜잭션이 있네"를 확인하고, 그냥 그것을 계속 쓴다.

코드 커밋 권한이 어디에 있는지를 주석으로 못 박은 형태
@Service
public class OrderService {

    @Transactional   // 진행 중인 트랜잭션이 없으므로 여기가 물리 트랜잭션의 시작점주인
    public void order(OrderRequest request) {
        orderRepository.save(order);
        stockService.decrease(request.itemId());
    }
}

@Service
public class StockService {

    @Transactional   // REQUIRED(기본값) — order()의 트랜잭션을 물려받는다참여자
    public void decrease(Long itemId) {
        // 이 메서드가 리턴해도 DB에는 COMMIT이 나가지 않는다.
        // 커밋 권한은 트랜잭션을 시작한 order() 쪽에만 있다.
    }
}

3-1. 안쪽의 "커밋"은 실제 커밋이 아니다

여기가 주니어가 가장 자주 오해하는 지점이다. decrease()에도 @Transactional이 붙어 있으니 "이 메서드가 끝나면 여기까지는 커밋되겠지"라고 읽기 쉽다. 아니다. 스프링은 트랜잭션을 시작한 쪽과 합류한 쪽을 구분해 기억하고, 커밋 처리 시점에 이렇게 갈린다.

암기 장치 — REQUIRED는 "하나, 하나, 하나"

커넥션 하나  ·  실제 COMMIT 한 번(가장 바깥)  ·  운명 하나(공동체)

거꾸로 REQUIRES_NEW는 전부 "둘"이 된다 — 커넥션 둘, 커밋 둘, 운명 둘. 이 대칭 하나로 두 옵션의 표를 통째로 복원할 수 있다.

4. rollback-only — "운명 공동체"의 실체

물리 트랜잭션이 하나이므로 한쪽이 롤백되면 다른 쪽도 롤백된다. 여기까지는 당연하다. 그런데 이 "운명 공동체"에는 눈에 잘 안 보이는 장치가 하나 딸려 있다.

합류한 안쪽에서 예외가 났다고 하자. 안쪽은 트랜잭션의 주인이 아니라서 직접 롤백할 수 없다 — 롤백해 버리면 바깥이 지금까지 한 작업까지 함께 날아가는데, 그럴 권한이 없기 때문이다. 그래서 스프링은 대신 공유 중인 트랜잭션에 "이건 커밋하면 안 됨"이라는 표식을 찍는다. 이것이 rollback-only 플래그다.

함정 — try-catch가 통하는 경우와 통하지 않는 경우

통하지 않는다 — 안쪽이 REQUIRED

  • 안쪽 실패가 공유 물리 트랜잭션에 마크를 찍는다
  • 바깥이 예외를 삼켜도 커밋 시점에 터진다
  • 증상: UnexpectedRollbackException

통한다 — 안쪽이 REQUIRES_NEW

  • 마크가 찍히는 대상이 다른 물리 트랜잭션
  • 바깥이 catch로 막아야만 바깥이 산다
  • 독립성과 예외 차단은 별개의 두 가지 일

시나리오 전문과 해법 비교는 07-transactional-default-behavior-rollback.md 4절에 있다.

5. REQUIRES_NEW — 유보하고 커넥션을 하나 더 빌린다

REQUIRES_NEW는 진행 중이던 트랜잭션을 잠시 유보(suspend)한다. 유보란 "창고에 올려둔 트랜잭션 정보를 통째로 꺼내 옆에 치워 두고, 창고를 빈 상태로 만드는 것"이다(2-1절 그림 ③). 창고가 비었으니 스프링은 "진행 중인 트랜잭션이 없다"고 판단하고, 풀에서 커넥션을 하나 더 빌려 완전히 새 물리 트랜잭션을 연다.

유보는 반납이 아니다 치워 둔 바깥 트랜잭션의 커넥션은 여전히 이 스레드가 쥐고 있다. 나중에 재개해서 커밋해야 하니 놓을 수가 없다. 이 한 문장이 8절 전체의 원인이다.

암기 장치 — REQUIRES_NEW의 세 글자는 "유 · 둘 · 비"

유보(반납 아님)  ·  커넥션 둘(동시 점유)  ·  비가역(이미 COMMIT)

이 세 글자가 각각 장점 1개와 리스크 2개로 갈린다 — 비가 이력이 남는 이유(장점)이자 재고·잔액에 쓰면 안 되는 이유(리스크)이고, 둘이 8절 풀 데드락의 원인이다.

5-1. 독립이 만드는 두 가지 성질

성질 ① 안쪽이 롤백돼도 바깥은 무사할 수 있다

4절의 rollback-only 플래그가 서로 다른 물리 트랜잭션에 찍히기 때문이다.

단, 조건이 붙는다 — 바깥이 그 예외를 try-catch로 막아 줘야 한다. 전파 옵션을 바꿨다고 예외 객체가 사라지는 게 아니다. 예외는 그대로 콜 스택을 타고 올라가고, 바깥은 자기 롤백 규칙(런타임 예외면 롤백)에 따라 자기 트랜잭션을 롤백한다.

"안쪽을 독립시키기"와 "예외 전파를 끊기"는 서로 다른 일이고, 둘 다 해야 의도한 그림이 된다

성질 ② 안쪽이 커밋되면 되돌릴 수 없다

이미 DB에 COMMIT이 나갔기 때문이다. 커밋된 트랜잭션을 취소하는 표준 SQL은 존재하지 않는다.

이 비가역성이 REQUIRES_NEW의 존재 이유이자 위험의 근원이다. 그래서 넣을 데이터인지 판별하는 기준도 여기서 곧장 도출된다.

"본 처리가 롤백된 세상에 이 데이터만 남아 있어도 괜찮은가, 혹은 남아 있어야 하는가?"

판별 기준을 데이터 종류로 펼치면

적합 — 남아야 하는 것
감사 로그 · 실패 이력 · 외부 연동 시도/응답 기록 · 배치 건별 처리 결과 · 알림 발송 이력
공통점: 본 처리와 운명을 같이하면 안 되는 데이터
부적합 — 남으면 안 되는 것
재고 · 잔액 · 포인트처럼 본 처리와 정합성이 묶인 데이터
롤백된 주문의 재고만 차감된 채로 남는 상태를 코드가 스스로 만들어낸다 — 부분 커밋을 설계로 못 박는 실수

6. 실무 사례 — "본 처리가 실패해도 이건 남아야 한다"

대표 사례는 실패 이력·감사 로그다. "주문 처리가 실패하면 주문은 롤백돼야 하지만, 실패했다는 기록 자체는 남아야 한다"는 요구는 REQUIRED로는 원천적으로 불가능하다. 기록도 같은 물리 트랜잭션에 실려 있어 본 처리와 함께 증발하기 때문이다.

before 실패 이력까지 함께 롤백 — "왜 실패했는지가 어디에도 없다"
@Service
public class OrderService {

    @Transactional
    public void order(OrderRequest request) {
        try {
            process(request);
        } catch (Exception e) {
            historyService.saveFailure(request, e);같은 물리 트랜잭션
            throw e;방금 남긴 기록도 함께 증발
        }
    }
}

// 결과: 장애 분석에 가장 필요한 순간에
//       history 테이블이 비어 있다.
after 이력 저장만 독립 물리 트랜잭션으로 떼어낸다
@Service
public class HistoryService {   // 반드시 별도 빈

    @Transactional(propagation = Propagation.REQUIRES_NEW)커넥션 B
    public void saveFailure(OrderRequest req, Exception e) {
        // 이 메서드가 끝나는 순간 COMMIT이 나간다.
        // 바깥이 그 뒤에 롤백돼도 이 한 줄은 남는다.
        historyRepository.save(FailureHistory.of(req, e));
    }
}

// 호출부 — 이력 저장 실패가 본 처리를 죽이면 안 된다면
try {
    historyService.saveFailure(request, e);
} catch (Exception ignore) {
    log.warn("실패 이력 저장 실패", ignore);방향을 막는 catch
}

세트로 따라오는 함정 두 개 — 둘 다 "에러가 안 나서" 악질이다

① 자기 호출이면 통째로 무효

  • REQUIRES_NEW도 프록시가 적용하는 속성이라, 같은 클래스 안에서 this.saveFailure()로 부르면 프록시를 거치지 않아 전파 옵션이 없는 것과 똑같이 동작한다
  • 위 예시에서 HistoryService를 굳이 별도 빈으로 둔 이유가 이것
  • 컴파일도 되고 실행도 되고 평소에는 이력이 잘 쌓인다 — 정작 롤백되는 장애 순간에만 함께 사라진다
  • 11-transactional-self-invocation.md 참고

② 반대 방향도 막아야 한다

  • 이력은 남기되 이력 저장 실패가 본 처리를 죽이면 안 된다면, 호출부에서 saveFailure()를 try-catch로 감싸야 한다
  • 독립성과 예외 차단은 별개다 (5-1 성질 ①)
  • 즉 어느 방향이든 호출부의 예외 처리는 설계의 일부다

7. 그럼에도 REQUIRES_NEW가 답이 아닌 경우 — "아 · 이 · 큐"

"본 처리가 실패해도 남아야 한다"는 요구가 나왔다고 해서 반사적으로 REQUIRES_NEW를 꺼내면 안 된다. 남길 대상이 무엇이냐에 따라 더 나은 도구가 있고, 그 도구들의 공통점은 커넥션 2개를 동시에 쥐는 구간이 아예 없다는 것이다.

암기 장치 — 대안 3종은 "아 · 이 · 큐" (커넥션 2개 문제를 푸는 IQ)

아웃박스
남길 것이 외부 호출·메시지 발행일 때
보낼 메시지를 같은 DB의 outbox 테이블에 INSERT해 본 트랜잭션과 한 몸으로 커밋하고, 별도 릴레이가 읽어 발행한다.
이벤트
본 트랜잭션과 동기일 필요가 없을 때
@TransactionalEventListener로 커밋/롤백이 끝난 뒤 실행. 바깥이 커넥션을 반납한 다음에 새로 빌린다.
큐 위임
처리 자체를 떼어내도 될 때
할 일을 메시지로 넘겨 다른 소비자가 처리. 원 요청 스레드는 커넥션을 하나만 쥐고 끝난다.
셋 다 같은 방향의 처방이다 — 스레드당 동시 커넥션 수(Cm)를 1로 되돌린다 (9절)

7-1. 남길 것이 메시지 발행이라면 — 애초에 문제 정의가 틀렸다

"주문이 커밋되면 Kafka로 이벤트를 쏜다"를 REQUIRES_NEW로 풀려는 시도가 있는데, 이건 전파 옵션으로 풀 수 있는 문제가 아니다. DB 쓰기와 브로커 발행은 서로 다른 시스템이라 어떤 전파 옵션으로도 한 트랜잭션에 묶이지 않는다(이중 쓰기 문제). 답은 아웃박스다 — 23-transactional-outbox-pattern.md를 그대로 따르면 된다.

7-2. 동기일 필요가 없다면 — 트랜잭션 바깥으로 뺀다

대안 커밋/롤백이 끝난 뒤에 실행되는 리스너 — 점유 구간이 겹치지 않는다
@TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)원 트랜잭션 종료 후
// AFTER_ROLLBACK 시점에는 원래 트랜잭션이 이미 끝나 있다.
// 그래서 여기서 DB에 쓰려면 리스너 자신이 새 트랜잭션을 열어야 한다.
@Transactional(propagation = Propagation.REQUIRES_NEW)이번엔 겹치지 않는다
public void onOrderFailed(OrderFailedEvent event) {
    historyRepository.save(FailureHistory.of(event));
}
최악의 조합 — 외부 API 호출을 REQUIRES_NEW로 감싸기 트랜잭션 안에서 외부 API를 부르면 안 되는 이유는 응답 대기 시간 내내 커넥션을 붙잡기 때문인데, REQUIRES_NEW로 감싸면 그 대기 시간 동안 커넥션을 2개 붙잡는다. 문제를 두 배로 키운 셈이다. (22-external-api-call-inside-transaction.md 참고)

8. 청구서 — 커넥션 2개 점유와 커넥션 풀 자기 데드락

REQUIRES_NEW의 독립성은 공짜가 아니다. 5절 그림이 보여주듯 스레드 하나가 커넥션 2개를 동시에 점유한다. 이것이 만드는 최악의 시나리오가 커넥션 풀 자기 데드락이다 — 다른 서비스도, 락 경합도, 느린 쿼리도 없이 순전히 자기들끼리 물려서 멈추는 교착이다.

정확히 짚을 것 — 이 교착은 "영원히"가 아니다

HikariCP는 connectionTimeout(기본값 30,000ms)만큼 기다린 뒤 SQLTransientConnectionException을 던지고 포기한다. 즉 30초 동안 전원이 멈춰 있다가 한꺼번에 실패하고, 실패한 스레드들이 커넥션을 반납하면서 다시 풀린다.

트래픽이 계속 들어오면 이 사이클이 반복 → 실제로는 "간헐적으로 30초씩 멈추는 API"로 관측된다

원인을 짐작하기 가장 어려운 형태의 장애다 — 느린 쿼리도 없고, 에러 로그는 커넥션 타임아웃 하나뿐이며, 평상시 지표는 멀쩡하다.

9. 그래서 풀 크기는 얼마여야 하는가 — 11 vs 201

교착을 원천적으로 불가능하게 만들려면 어떤 조건이 필요한지 계산해 보자. 조건은 하나다 — 어떤 순간에도 적어도 한 스레드는 필요한 커넥션을 전부 모을 수 있어야 한다. 그 한 명이 완주하고 반납하면 다음 사람이 완주하고, 연쇄적으로 전부 풀린다.

공식 유도 — 최악의 배분에서 딱 1개를 더한다

Tn
동시에 이 경로를 탈 수 있는 스레드 수
Cm
스레드 하나가 동시에 쥐어야 하는 최대 커넥션 수
1
최악의 배분을 상상한다 — 모든 스레드에 Cm - 1개씩 나눠준 상태. 전원이 딱 1개씩 모자라 아무도 완주하지 못한다 = 교착. 이때 쥐여 있는 커넥션 수는 Tn x (Cm - 1).
2
여기에 딱 1개만 더 있으면 한 명이 완주하고, 그가 반납한 Cm개가 다음 사람에게 흘러가 연쇄적으로 해소된다.
필요한 풀 크기 = Tn x (Cm - 1) + 1

9-1. 실제 서버에 대입하면 — 공식이 알려주는 진짜 결론

문제는 실제 서버 값을 넣을 때 드러난다. 톰캣의 기본 max-threads는 200이고, 그 스레드 전부가 이 경로를 탈 수 있다면 Tn = 200이다.

이 문서의 사례 (Tn=10, Cm=2)
11
10 x (2 - 1) + 1 — 현실적
톰캣 기본값 (Tn=200, Cm=2)
201
200 x (2 - 1) + 1 — 비현실적

커넥션 201개짜리 풀은 현실적이지 않다. DB 쪽 max_connections도 문제지만, 애초에 커넥션 풀은 작을수록 좋다는 것이 정설이다(컨텍스트 스위칭과 디스크 경합 때문에 커넥션을 늘려도 처리량은 어느 지점부터 오히려 떨어진다). 그래서 풀 크기를 키워서 이 식을 만족시키겠다는 접근 자체가 틀렸다.

공식이 알려주는 진짜 결론 — 분모가 아니라 Cm을 건드린다

해법은 Cm을 1로 되돌리는 것 — 그러면 Tn x 0 + 1 = 1이 되어 교착 조건 자체가 소멸한다

7절의 대안 셋 — 아웃박스 · 커밋/롤백 후 이벤트 · 큐 위임(아 · 이 · 큐) — 이 전부 이 방향의 처방이다. "풀을 늘릴까요"가 아니라 "왜 한 스레드가 2개를 쥐어야 하는가"를 되묻는 것이 답이다.

9-2. 평균은 0.25개인데 왜 위험한가 시니어 변별

흥미로운 대비가 하나 있다. 처리량 관점에서 REQUIRES_NEW의 추가 비용은 사실 거의 없다. 풀 크기 산정의 기본식(Little's law: 동시 점유 수 = TPS × 점유 시간)으로 계산해 보면 그렇다.

평균으로 계산한 추가 비용

  • 목표 500 TPS, 요청당 커넥션 점유 50ms
  • 기본 필요 커넥션 = 500 x 0.05s = 25개
  • 그중 10%가 REQUIRES_NEW 경로, 안쪽 INSERT가 5ms
  • 추가 동시 커넥션 = (500 x 0.1) x 0.005s = 0.25개
평균적으로는 커넥션 0.25개어치만 더 있으면 된다

그런데 이 경로가 서비스를 30초씩 멈춰 세운다

이유는 하나다 — 교착은 평균이 아니라 동시 도착의 꼬리에서 터지기 때문이다.

평상시 지표로는 아무 문제가 없어 보이다가, 트래픽이 몰려 그 경로를 탄 요청이 풀 크기만큼 겹치는 순간 한 번에 터진다.

"평소에 멀쩡하니 괜찮다"가 근거가 될 수 없는 종류의 위험이고, 이 구분을 말할 수 있는지가 변별점이다
완화 요인 하나 — 다만 요행에 기대는 것이다 Spring Boot 3.x의 기본 구성에서 하이버네이트는 커넥션을 트랜잭션 시작 시점이 아니라 첫 쿼리 시점에 가져와 트랜잭션이 끝날 때까지 쥔다(hibernate.connection.handling_mode가 DELAYED_ACQUISITION_AND_HOLD). 그래서 바깥 메서드가 DB를 건드리기 전에 REQUIRES_NEW를 호출한다면 그 순간 바깥은 아직 커넥션을 안 쥐고 있을 수도 있다.
다만 이것은 우연한 코드 배치에 기대는 것이지 설계가 아니다. 게다가 readOnly나 isolation을 지정한 트랜잭션은 그 값을 커넥션에 설정해야 하므로 시작 시점에 커넥션을 미리 잡는다. 요행에 기대지 말고 Cm을 1로 만드는 것이 정답이다.

10. NESTED — 세이브포인트, 그리고 JPA에서 안 쓰이는 이유

전파 옵션 중 세 번째로 자주 언급되는 것이 NESTED다. REQUIRES_NEW와 헷갈리기 쉬우니 정확히 구분해 두자.

NESTED는 새 물리 트랜잭션을 열지 않는다. 대신 진행 중인 트랜잭션 안에 세이브포인트(savepoint)를 찍는다. 세이브포인트는 트랜잭션 중간에 꽂아 두는 되감기 지점으로, 롤백할 때 트랜잭션 전체가 아니라 그 지점까지만 되감을 수 있게 해 준다. 게임의 중간 저장과 같은 개념이다.

REQUIRES_NEWNESTED
커넥션2개 (동시 점유)1개 (세이브포인트만 추가)
안쪽의 커밋독립적으로 즉시 COMMIT안쪽 성공분은 바깥 커밋에 함께 실린다
바깥이 롤백되면안쪽은 남는다안쪽도 함께 사라진다
안쪽이 실패하면바깥에 영향 없음 (예외만 전파)세이브포인트까지만 부분 롤백
JPA에서사용 가능사실상 사용 불가 (아래 두 겹)

JPA에서 NESTED가 막히는 두 겹

1
JpaTransactionManager는 중첩 트랜잭션을 기본적으로 허용하지 않는다. nestedTransactionAllowed 값이 꺼져 있어서 NESTED를 선언하면 NestedTransactionNotSupportedException이 난다. (JDBC/MyBatis에서 쓰는 DataSourceTransactionManager는 이 값이 켜져 있어 정상 동작한다.)
2
설령 그 값을 켠다 해도 세이브포인트는 JDBC 커넥션 수준의 되감기일 뿐 영속성 컨텍스트를 되돌려 주지 않는다. DB에서는 UPDATE가 취소됐는데 1차 캐시 안의 엔티티는 여전히 변경된 상태로 남아 있고, 그 상태가 다음 플러시에 다시 UPDATE로 나갈 수 있다 — DB와 메모리가 어긋난다.
그래서 JPA 실무에서 "부분적으로 독립된 커밋"이 필요하면 선택지는 REQUIRES_NEW로 좁혀지고, 8절의 커넥션 비용을 피할 수 없다

이 인과가 곧 REQUIRES_NEW의 대안을 7절처럼 트랜잭션 바깥에서 찾아야 하는 이유다.

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

전파의 정의 한 줄은?
트랜잭션 메서드가 다른 트랜잭션 메서드를 부를 때 바깥 트랜잭션을 안쪽이 어떻게 물려받을지 정하는 규칙. 결정하는 것은 안쪽 애너테이션.
REQUIRED를 세 단어로
하나 · 하나 · 하나 — 커넥션 하나, 실제 COMMIT 한 번(가장 바깥), 운명 하나.
REQUIRES_NEW를 세 글자로
유 · 둘 · 비 — 유보(반납 아님) · 커넥션 둘(동시) · 비가역(이미 COMMIT).
합류한 안쪽이 정상 리턴하면?
COMMIT을 보내지 않는다. 커밋 권한은 트랜잭션을 시작한 주인에게만 있다.
"try-catch 했는데 왜 롤백?"
합류한 안쪽이 rollback-only 플래그를 찍었기 때문. 예외는 잡아도 마크는 못 잡는다 → UnexpectedRollbackException.
REQUIRES_NEW 판별 기준은?
"본 처리가 롤백된 세상에 이 데이터만 남아 있어도 되는가" — 감사 로그·이력은 예, 재고·잔액은 아니오.
독립시키면 끝인가?
아니다. 예외 전파는 별개 — 바깥이 catch까지 해야 한 세트다.
교착 시나리오 숫자는?
풀 10 + 동시 요청 10 → 전원 1개 부족 → connectionTimeout 30초 뒤 전원 실패.
Tn x (Cm - 1) + 1
Tn=10·Cm=2 → 11 / 톰캣 200 → 201(비현실). 결론: 풀이 아니라 Cm을 1로.
대안 3종은?
아 · 이 · 큐 — 아웃박스 · (커밋 후) 이벤트 · 큐 위임. 공통점: 점유 구간이 겹치지 않는다.
NESTED와의 결정적 차이는?
바깥이 롤백될 때 — REQUIRES_NEW는 남고 NESTED는 사라진다. JPA에선 두 겹으로 막힌다.
가장 조용한 사고는?
자기 호출(this.saveFailure()) — 전파 옵션이 통째로 무시되고, 장애 순간에만 이력이 함께 사라진다.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

REQUIRED로 합류한 안쪽 메서드가 정상 리턴하면 그 시점에 커밋되나요? 필수힌트: "커밋 권한"이라는 말을 쓰고, 이어질 "그럼 안쪽 애너테이션은 무의미한가요?"까지 미리 막는다

안 된다. 합류한 논리 트랜잭션은 커밋 권한이 없다. 스프링은 커밋 처리에서 "내가 이 트랜잭션을 시작한 주인인가"를 먼저 확인하고, 주인이 아니면 COMMIT을 보내지 않고 그냥 리턴한다. 실제 COMMIT은 트랜잭션을 시작한 가장 바깥에서 단 한 번 나간다.

이어서 "그럼 안쪽 메서드에 붙은 @Transactional은 아무 일도 안 하나요?"라고 물어오면, 경계 선언으로서는 여전히 의미가 있다고 답한다. 그 메서드가 단독으로 호출될 때는 자기가 주인이 되어 트랜잭션을 열고, 합류할 때는 rollback-only를 찍는 주체가 된다. "커밋만 안 할 뿐 아무것도 안 하는 것은 아니다"가 정확한 표현이다.

REQUIRED 구조에서 안쪽 예외를 try-catch로 잡았는데 UnexpectedRollbackException이 났습니다. 왜죠? 함정힌트: 잡은 것과 찍힌 것은 다르다 — 찍히는 대상이 무엇인지 지목한다

예외는 잡았지만 이미 찍힌 rollback-only 마크는 잡을 수 없기 때문이다. 합류한 안쪽은 트랜잭션의 주인이 아니라 직접 롤백할 권한이 없으므로, 대신 공유 중인 물리 트랜잭션에 "커밋 금지" 표식을 찍고 예외를 던진다.

바깥이 그 예외를 삼키고 정상 리턴하면, 바깥 프록시는 커밋을 시도하다가 마크를 발견하고 전체를 ROLLBACK한 뒤 UnexpectedRollbackException을 던진다. 마크가 찍힌 시점(안쪽)과 터지는 시점(바깥 커밋)이 다르다는 것이 이 함정의 본질이고, 그 사이에는 아무 로그도 남지 않는다.

해법은 세 방향이다 — ① 애초에 바깥에서 예외를 삼키지 않는다, ② 안쪽 실패를 무시해도 되는 성격이라면 안쪽을 트랜잭션 밖으로 빼거나 REQUIRES_NEW로 분리한다, ③ 안쪽에서 롤백 대상이 아닌 예외로 바꿔 던진다(체크 예외 등 롤백 규칙에 걸리지 않는 형태). "잡으면 되겠지"가 통하지 않는 구조라는 것을 아는지가 포인트다.

REQUIRES_NEW 안에서 예외가 났고 바깥이 catch하지 않았다면, 바깥 트랜잭션은 어떻게 되나요? 필수힌트: 독립된 것은 "플래그"이지 "예외 객체"가 아니다

바깥도 롤백된다. REQUIRES_NEW의 독립성은 "안쪽 롤백이 바깥 물리 트랜잭션에 rollback-only를 찍지 않는다"는 뜻이지, 예외 객체가 콜 스택을 타고 올라가는 것까지 막아 주지 않는다. 바깥으로 전파된 런타임 예외는 바깥 트랜잭션의 평범한 롤백 규칙에 그대로 걸린다.

"독립시키고 싶으면 catch까지가 한 세트"라고 답하면 정확하다. 반대로 이력 저장 실패가 본 처리를 죽이면 안 되는 경우에도 같은 catch가 필요하므로, 어느 방향이든 호출부의 예외 처리는 설계의 일부다.

바깥이 롤백되면 REQUIRES_NEW로 이미 커밋된 데이터는 어떻게 되나요? 시니어 변별힌트: "되돌릴 수 없다"에서 끝내지 말고, 그 비가역성에서 판별 기준을 도출한다

되돌릴 수 없다. 이미 DB에 COMMIT이 나갔기 때문이고, 커밋된 트랜잭션을 취소하는 표준 SQL은 존재하지 않는다.

그래서 판별 기준을 비가역성에서 도출해 답하는 것이 포인트다 — "본 처리가 롤백된 세상에 이 데이터만 남아 있어도 되는가?" 감사 로그·시도 이력은 남아야 하니 적합하다.

반면 재고·잔액처럼 본 처리와 정합성이 묶인 데이터를 REQUIRES_NEW로 빼는 것은 부분 커밋을 설계로 못 박아 넣는 실수다. 롤백된 주문의 재고만 차감된 채로 남는 상태를 코드가 스스로 만들어내는 셈이다.

REQUIRES_NEW가 커넥션 풀을 고갈시키는 시나리오를 숫자로 설명해보세요. 시니어 변별힌트: 왜 2개인지 → 교착의 계산 → 처방, 세 단계로 끊어 말한다

① 왜 2개인가 — 바깥 트랜잭션은 유보돼도 커넥션을 반납하지 않고(나중에 커밋해야 하므로) 쥐고 있는데, 안쪽이 별도 커넥션을 추가로 요구하므로 스레드당 동시 2개 점유가 된다.

② 교착의 계산 — 풀 크기 10에 이 경로를 타는 동시 요청 10개면, 전원이 첫 커넥션을 쥔 채 두 번째를 기다리는데 반납할 주체가 자기들뿐이라 아무도 진행하지 못한다. 영원히는 아니고 connectionTimeout(HikariCP 기본 30초)까지 멈췄다가 전원 실패한다 — 관측되는 모습은 "간헐적으로 30초씩 멈추는 API"다.

③ 처방 — 교착을 원천 차단하는 풀 크기는 Tn x (Cm - 1) + 1인데, 톰캣 기본 스레드 200을 넣으면 201이 나와 현실성이 없다. 그러니 풀을 키우는 방향이 아니라 Cm을 1로 되돌리는 방향 — 아웃박스 · 커밋/롤백 후 이벤트 · 큐 위임 — 이 정답이다.

여기에 "처리량 관점의 추가 비용은 평균 0.25개 수준으로 미미한데도 위험한 이유는, 교착이 평균이 아니라 동시 도착의 꼬리에서 터지기 때문"이라는 대비까지 붙이면 계산과 감각을 동시에 보여줄 수 있다.

NESTED와 REQUIRES_NEW의 차이는 무엇인가요? 필수힌트: 세이브포인트에서 시작해 "바깥이 롤백될 때"로 승부를 내고, JPA 제약으로 마무리한다

NESTED는 새 물리 트랜잭션이 아니라 같은 트랜잭션 안에 세이브포인트를 찍는 방식이다. 안쪽이 실패하면 세이브포인트까지만 부분 롤백하고 바깥은 계속 갈 수 있다. 커넥션이 1개라 8절의 풀 비용도 없다.

결정적 차이는 바깥이 롤백될 때다. 물리 트랜잭션이 하나이므로 바깥이 롤백되면 안쪽 작업도 함께 사라진다. REQUIRES_NEW는 남는다. 그래서 "본 처리가 실패해도 이력은 남아야 한다"는 요구는 NESTED로 풀 수 없다.

JPA에서는 두 겹으로 막힌다 — JpaTransactionManager가 중첩 트랜잭션을 기본적으로 허용하지 않아 NestedTransactionNotSupportedException이 나고, 설령 허용해도 세이브포인트는 JDBC 커넥션만 되감을 뿐 영속성 컨텍스트의 엔티티 상태는 그대로 남아 DB와 어긋난다. "그래서 JPA 실무의 선택지는 REQUIRES_NEW로 좁혀지고, 그 비용을 피하려면 전파 옵션이 아니라 트랜잭션 바깥의 도구를 봐야 한다"로 마무리하면 좋다.

같은 클래스 안의 메서드에 REQUIRES_NEW를 붙여 호출하면 어떻게 되나요? 함정힌트: 무효가 된다는 사실보다 "왜 이 함정이 특히 악질인가"가 점수 구간이다

자기 호출은 프록시를 거치지 않으므로 전파 옵션이 통째로 무시되고, 그냥 바깥 트랜잭션 안에서 실행된다. "독립 트랜잭션으로 분리했다고 믿었는데 실제로는 운명 공동체"라는, 이 주제와 자기 호출 함정이 교차하는 지점이다.

특히 악질인 이유는 에러가 안 나기 때문이다. 컴파일도 되고 실행도 되고 평소에는 이력이 잘 쌓인다. 정작 본 처리가 롤백되는 장애 순간에만 이력이 함께 사라져서, 원인 분석에 가장 필요한 순간에 데이터가 없다.

답은 별도 빈으로 분리하는 것이다. (11-transactional-self-invocation.md 참고)

REQUIRES_NEW 안에서, 바깥이 방금 저장한 데이터를 조회하면 보이나요? 시니어 변별힌트: 커넥션이 다르다는 사실에서 격리 수준 이야기로 자연스럽게 넘어간다

보이지 않는다. 안쪽은 별도 커넥션의 별도 물리 트랜잭션이고, 바깥이 아직 커밋하지 않은 변경은 다른 트랜잭션에서 보이지 않는 것이 정상이기 때문이다(더티 리드를 허용하지 않는 일반적인 격리 수준 기준).

그래서 "바깥에서 방금 저장한 주문을 REQUIRES_NEW 안에서 ID로 조회했더니 없다"는 현상이 나온다. 안쪽에 필요한 값이 있다면 조회하지 말고 파라미터로 넘겨야 한다는 실무 규칙이 여기서 나온다.

한 걸음 더 나가면 같은 행을 건드릴 때의 위험으로 이어진다 — 바깥이 이미 잠근 행을 안쪽이 수정하려 하면, 안쪽은 바깥의 락을 기다리고 바깥은 안쪽이 끝나기를 기다리는 교착이 된다. 커넥션 풀 데드락과는 별개로 행 락 수준에서도 자기 자신과 물릴 수 있다는 것까지 말하면 이해도가 분명해진다.

합류한 안쪽 메서드에 지정한 timeout·isolation·readOnly는 어떻게 되나요? 가산점힌트: 물리 트랜잭션의 속성을 정하는 주체가 누구인지로 답한다

무시된다. 이 속성들은 물리 트랜잭션 단위로 커넥션에 설정되는 값이고, 물리 트랜잭션을 시작한 것은 바깥이다. 합류한 안쪽은 새로 시작하는 것이 아니므로 자기 값을 반영할 자리가 없다.

실무에서 자주 나오는 사고가 "바깥이 readOnly = false인데 안쪽에 readOnly = true를 붙여 놓고 읽기 전용이라 믿는 것", 그리고 "안쪽에만 timeout을 걸어 두고 제한이 걸렸다고 믿는 것"이다. 실제로 그 속성이 필요하면 물리 트랜잭션을 새로 여는 경계(가장 바깥, 또는 REQUIRES_NEW)에 걸어야 한다.

그럼 REQUIRES_NEW는 언제 써도 되는 건가요? 판단 순서를 말해보세요. 시니어 변별힌트: "쓴다/안 쓴다"가 아니라 체크리스트 순서로 답한다

네 개의 질문을 이 순서로 통과시킨다.

① 남길 대상이 무엇인가 — 외부 시스템 호출·메시지 발행이면 애초에 전파 옵션 문제가 아니다(아웃박스). DB에 남길 이력성 데이터일 때만 후보가 된다.

② 본 트랜잭션과 동기여야 하는가 — 아니라면 커밋/롤백 후 이벤트가 더 낫다. 같은 REQUIRES_NEW라도 점유 구간이 겹치지 않기 때문이다.

③ 남아도 되는 데이터인가 — "본 처리가 롤백된 세상에 이것만 남아도 괜찮은가"에 예여야 한다. 재고·잔액이면 여기서 탈락이다.

④ 그래도 써야 한다면 비용을 관리한다 — 별도 빈으로 분리(자기 호출 방지), 호출부 try-catch, 안쪽 구간을 최대한 짧게(외부 API 호출 금지), 그리고 그 경로가 동시에 몇 개까지 겹칠 수 있는지를 풀 크기와 비교해 둔다. "쓰지 마세요"가 아니라 "이 순서로 걸러내고, 남으면 이렇게 비용을 관리한다"가 실무의 답이다.

한 줄 요약
전파는 "바깥에 이미 열린 트랜잭션을 안쪽이 물려받을 것인가"의 규칙이고, REQUIRED는 물려받아 새 BEGIN 없이 같은 커넥션을 쓰며 안쪽의 커밋이 실제로는 아무 일도 하지 않는 운명 공동체(그 실체는 rollback-only 플래그)를 만드는 반면, REQUIRES_NEW는 바깥을 유보하고 커넥션을 하나 더 빌려 독립 커밋을 만들어 "본 처리가 롤백돼도 남아야 할 이력"을 가능하게 하지만 스레드당 커넥션 2개 점유라는 청구서가 따라온다 — 풀 10에 동시 요청 10이면 connectionTimeout까지 전원 교착이고 이를 원천 차단하는 풀 크기 Tn x (Cm - 1) + 1은 톰캣 스레드 200 기준 201이라 현실성이 없으므로, 답은 풀을 키우는 것이 아니라 아웃박스 · 커밋 후 이벤트 · 큐 위임으로 스레드당 커넥션 수를 1로 되돌리는 것이다.
