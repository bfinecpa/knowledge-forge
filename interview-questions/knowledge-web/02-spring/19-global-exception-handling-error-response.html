전역 예외 처리와 에러 응답 표준화
에러 응답도 API 계약이다

면접 질문: "예외를 전역으로 처리하는 방법(@ControllerAdvice)과 에러 응답 표준화를 어떻게 설계하나요?"

핵심 관전 포인트 — @RestControllerAdvice + @ExceptionHandler는 "예외를 HTTP 응답으로 바꾸는 일"을 한곳에 모으는 장치이고, 핵심은 애너테이션이 아니라 그 한곳에서 정하는 계약이다 — ErrorCode enum이 코드·메시지·HTTP status의 단일 진실 공급원이 되고, 모든 실패가 같은 ErrorResponse 모양으로 나가야 프론트엔드가 파서를 한 번만 짜고 운영이 코드별 에러율을 집계할 수 있다. 여기에 4xx는 warn · 5xx는 error+알람이라는 로그 정책(4xx를 error로 찍으면 알람 피로로 진짜 장애를 놓친다)과 내부 정보 비노출을 얹고, 마지막으로 @ControllerAdvice가 구조적으로 닿지 못하는 구역 — 필터 · /error · 비동기 — 까지 같은 포맷으로 맞추는 것이 마무리다. 그 통일의 방법은 핸들러마다 JSON을 따로 쓰는 것이 아니라 공통 ErrorResponse 생성기를 만들어 세 구역이 함께 쓰게 만드는 것이다.
  • 1
    장치가 아니라 계약을 먼저 말한다 — @RestControllerAdvice는 예외를 응답으로 바꾸는 코드를 한곳에 모으는 수단일 뿐이고, 설계의 실체는 ErrorCode enum이 코드·메시지·status를 한 줄에 묶어 단일 진실 공급원이 되는 것과 모든 실패가 같은 ErrorResponse 모양으로 나가는 것이다.
  • 2
    실익은 두 소비자로 말한다 — 프론트엔드는 HTTP 클라이언트에 에러 인터셉터 하나만 두면 되고(포맷이 하나여야 성립한다), 운영은 code 필드로 group by해 "어떤 실패가 얼마나 나는지"를 초 단위로 센다. 여기에 status는 바디를 열지 않는 게이트웨이·LB·APM·재시도 로직이 읽는 유일한 신호라는 이중 축을 붙인다.
  • 3
    마무리는 운영과 사각지대다 — 4xx는 warn(스택트레이스 없이) · 5xx는 error+스택트레이스+알람, 응답에는 trace id는 담고 예외 원문은 담지 않는다. 그리고 Advice가 못 닿는 필터 · 매핑 없는 경로 · 비동기는 각자 JSON을 쓰는 게 아니라 공통 생성기 하나를 주입받아 함께 쓴다.

0. 질문 + 출제 의도

질문: "예외를 전역으로 처리하는 방법(@ControllerAdvice)과 에러 응답 표준화를 어떻게 설계하나요?"

출제 의도: 에러 응답의 일관성은 프론트엔드·모바일 팀과의 협업 비용, 그리고 장애 시 에러율 집계 가능성을 결정한다. "혼자 잘 짜는" 것 너머 "시스템의 계약을 설계"해본 사람인지 본다. 애너테이션 사용법을 아는지가 아니라, 에러 응답을 시스템 간 인터페이스로 다루는지를 보는 질문이다.

이 페이지가 겨냥하는 약점 네 가지 ① "@ControllerAdvice 붙이면 됩니다"에서 끝나는 것 → 2절에서 이 장치가 파이프라인의 어느 단계에 매달려 있는지를 도식으로 못 박는다. 위치를 알면 9절의 "못 잡는 구역"이 저절로 따라 나온다.
② 핸들러가 여럿일 때의 우선순위를 모르는 것 → 3절의 3단계 규칙(컨·순·촌)과, 실무에서 실제로 터지는 "전용 핸들러가 있는데 안 불린다" 함정.
③ "표준화했습니다"가 포맷 얘기에서 멈추는 것 → 4~6절에서 코드 체계·status 선택·분리 기준까지 내려간다. status와 code는 서로 다른 소비자를 위한 두 축이다.
④ 운영 관점이 빠지는 것 → 8절의 로그 정책을 알람 피로라는 숫자 근거 위에 세우고, 응답에 trace id는 담되 예외 원문은 담지 않는 이유를 보안 문제로 다룬다.
한 문장 비유 — 응급실 트리아지 색깔과 진단 코드 응급실은 환자에게 두 가지 표시를 붙인다. 문 앞 분류 담당이 즉시 읽는 색깔(빨강·노랑·초록)과, 담당 의사가 치료를 정하는 진단 코드다. HTTP status가 색깔이고 — 게이트웨이·로드밸런서·APM·재시도 로직은 바디를 열어보지 않고 이 숫자만 읽는다 — 바디의 code가 진단 코드다. 색깔만 있으면 무엇을 치료할지 모르고, 코드만 있으면 문 앞에서 줄이 갈리지 않는다. 그래서 표준화의 결론은 늘 둘 다, 그리고 한 곳에서 정한다가 된다.

이 문서의 버전 의존 서술은 Spring Boot 3.x / Spring Framework 6.x 기준이며, 내부 동작 인용은 Spring Framework 6.2 소스를 확인한 것이다. 응답 스키마 자체의 설계(status와 code의 이중 축, 코드의 불변 계약성, RFC 9457 채택 판단)는 09-rest-api/05-error-response-body-standardization.md가, 상태 코드 각각의 의미는 08-network-http/05-http-status-codes-usage-criteria.md가 다룬다. 이 페이지는 그것을 스프링에서 어디에 어떻게 구현하느냐에 집중한다.

1. 전제 — 전역 처리가 없으면 무엇이 흩어지는가

표준화의 이점을 말하려면 표준화가 없는 상태의 비용부터 눈으로 봐야 한다. 아래는 전역 처리가 없을 때 실제로 쌓이는 코드다.

before 컨트롤러마다 제각각 — 포맷도, 상태 코드도, 로그도 다르다
@PostMapping("/orders")
public ResponseEntity<?> order(@RequestBody OrderRequest request) {
    try {
        return ResponseEntity.ok(orderService.order(request));
    } catch (SoldOutException e) {
        // A 개발자: Map 으로 즉석에서 만든다. 키 이름이 "error" 다.
        return ResponseEntity.badRequest().body(Map.of("error", e.getMessage()));포맷 ①
    } catch (Exception e) {
        // B 개발자: 문자열 한 줄. 500 인데 로그조차 안 남는다 —
        // 나중에 이 장애를 조사할 단서가 아무 데도 없다.
        return ResponseEntity.status(500).body("서버 오류");포맷 ② + 로그 없음
    }
}

비용 ① 프론트엔드 — 공통 처리가 성립하지 않는다

HTTP 클라이언트에 에러 인터셉터를 하나 두고 전부 거기서 처리하는 흔한 패턴이 깨진다. 인터셉터가 바디를 열어도 어떤 키를 읽어야 할지 API마다 다르기 때문이다. 결국 API마다 에러 파싱 코드를 따로 짠다.

비용 ② 운영 — 셀 공통 키가 없다

"어떤 실패가 얼마나 나는지"를 세려면 code 필드로 group by하면 몇 초다. 그 키가 없으면 로그 문자열을 눈으로 세는 작업이 그 자리를 대신한다. 장애 중에 이걸 하고 있게 된다.

그래서 목표를 한 문장으로 고정한다

모든 실패가 하나의 계약된 모양으로 나가고, 그 모양을 정하는 자리가 코드베이스에 단 한 곳만 존재한다

이 문장을 쥐고 있으면 뒤의 모든 결정(ErrorCode enum, 공통 ErrorResponse, 공통 생성기)이 같은 목표의 반복으로 보인다. 반대로 이 문장이 없으면 @ControllerAdvice 사용법만 남는다.

2. @ControllerAdvice는 파이프라인의 어디에 놓인 장치인가

@ControllerAdvice는 스스로 도는 물건이 아니다. Spring MVC 요청 파이프라인의 한 단계에서 불려야 실행된다. 이 위치를 정확히 알아두면 두 가지가 공짜로 따라온다 — 스프링 기본 처리보다 왜 우리 핸들러가 먼저 이기는지(이 절), 그리고 필터 예외를 왜 구조적으로 못 잡는지(9절).

Spring MVC 기본 리졸버 3종 — 등록 순서대로
순서리졸버담당
1ExceptionHandlerExceptionResolver@ExceptionHandler 메서드를 찾아 실행한다 — 우리가 쓰는 것
2ResponseStatusExceptionResolver예외에 붙은 @ResponseStatus나 ResponseStatusException을 상태 코드로 바꾼다
3DefaultHandlerExceptionResolver스프링 MVC 표준 예외를 규격에 맞는 상태 코드로 바꾼다(예: 지원하지 않는 메서드 → 405)
@RestControllerAdvice = @ControllerAdvice + @ResponseBody 리턴 객체가 JSON으로 직렬화되므로 REST API에서는 이쪽을 쓴다. @ControllerAdvice만 쓰면 리턴 문자열이 뷰 이름으로 해석되어 "왜 404 뷰를 찾지?"가 된다.

3. 여러 핸들러 중 무엇이 실행되는가 — 3단계 규칙

실무에서 자주 헷갈리는 지점이다. RuntimeException 핸들러와 IllegalArgumentException 핸들러가 둘 다 있으면 어느 쪽이 이기는가? 답은 세 단계로 순서가 정해져 있다.

암기 장치 — 3단계는 "컨 · 순 · 촌"

컨트롤러 안이 최우선 → 없으면 Advice 순서 → 그 안에서 촌수

면접에서 이 질문을 받으면 세 글자를 순서대로 펼치면 답이 완성된다. 특히 1단계와 2단계 사이에는 "조회조차 안 한다", 2단계 안에서는 "첫 Advice에서 멈춘다"는 두 단정이 핵심이다.

3-1. 진짜 함정은 2단계에 있다

매칭은 Advice 빈 단위로 먼저 끊긴다. @Order(1)인 Advice에 Exception 핸들러만 있고 @Order(2)인 Advice에 SoldOutException 전용 핸들러가 있다면, SoldOutException이 던져져도 1번 Advice에서 매칭에 성공해 버리므로 2번은 조회되지 않는다. "전용 핸들러가 있는데도 안 불린다"는 현상의 정체가 이것이다.

문제 순서가 앞선 Advice의 넓은 핸들러가 뒤를 가린다
@Order(1) @RestControllerAdvice앞에 있는데 넓다
class CommonAdvice {
    @ExceptionHandler(Exception.class) ...여기서 매칭 종료
}

@Order(2) @RestControllerAdvice
class OrderAdvice {
    @ExceptionHandler(SoldOutException.class) ...실행되지 않는다
}
고침 안전망은 항상 가장 낮은 우선순위로
@Order(Ordered.HIGHEST_PRECEDENCE) @RestControllerAdvice
class OrderAdvice {
    @ExceptionHandler(SoldOutException.class) ...구체 = 앞
}

@Order(Ordered.LOWEST_PRECEDENCE) @RestControllerAdvice
class CommonAdvice {
    @ExceptionHandler(Exception.class) ...넓음 = 뒤
}

규칙 하나로 정리

넓게 잡는 Advice일수록 뒤에 둔다

실무에서는 Advice를 여러 개로 쪼갤 때만 문제가 되므로, 하나로 시작해 필요할 때 쪼개면서 순서를 명시하는 편이 안전하다. 쪼개는 시점의 신호는 대개 "도메인 팀별로 예외가 늘어 한 파일이 300줄을 넘을 때"다.

4. 응답 계약 설계 — ErrorCode를 단일 진실 공급원으로

표준화의 목표를 정확히 잡자. "코드 · 사용자 메시지 · HTTP status"라는 세 값의 조합이 코드베이스 전체에서 딱 한 곳에만 존재하게 만드는 것이다. 그 한 곳이 enum이다.

암기 장치 — ErrorCode 한 줄에 들어가는 세 칸은 "코 · 메 · 상"

코드(기계 판독용)  ·  메시지(사람이 읽는 문구)  ·  상태 코드(HTTP status)

이 세 칸이 한 줄에 붙어 있다는 사실 자체가 설계다. 흩어져 있으면 같은 실패가 어떤 API에서는 400, 어떤 API에서는 409로 나가고, 메시지도 조금씩 달라진다.

4-1. 뼈대는 세 조각이다

뼈대 ① ErrorCode enum · ② BusinessException · ③ ErrorResponse
// ① 에러 코드 enum — 코드·메시지·status 의 단일 진실 공급원
public enum ErrorCode {

    ORDER_SOLD_OUT("ORDER-001", "재고가 소진된 상품입니다", HttpStatus.CONFLICT),
    ORDER_NOT_FOUND("ORDER-002", "주문을 찾을 수 없습니다", HttpStatus.NOT_FOUND),
    INVALID_INPUT("COMMON-001", "입력값이 올바르지 않습니다", HttpStatus.BAD_REQUEST),
    INTERNAL_ERROR("COMMON-999", "일시적인 오류가 발생했습니다", HttpStatus.INTERNAL_SERVER_ERROR);

    private final String code;
    private final String message;
    private final HttpStatus status;
    // 생성자·게터 생략
}

// ② 비즈니스 예외 — ErrorCode 를 품는 단일 베이스
// 예외 클래스를 에러마다 만들지 않고 하나로 두는 이유는 핸들러를 하나만 쓰기 위해서다.
// 예외 종류가 늘 때마다 핸들러가 늘면 그건 표준화가 아니다.
public class BusinessException extends RuntimeException {
    private final ErrorCode errorCode;

    public BusinessException(ErrorCode errorCode) {
        super(errorCode.getMessage());
        this.errorCode = errorCode;
    }
}

// ③ 공통 응답 포맷 — 모든 실패가 이 모양으로만 나간다
public record ErrorResponse(
        String code,                    // "ORDER-001" — 프론트 분기·에러율 집계의 키
        String message,                 // 사용자에게 보여도 되는 문구만
        List<FieldError> errors,        // 검증 실패 시 필드별 상세.아니면 빈 리스트
        String traceId                  // 로그 검색의 진입점 (8절)
) {
    public record FieldError(String field, String reason) {}
}

놓치기 쉬운 규칙 — errors는 사라지지 않는다

검증 실패가 아닐 때도 errors는 빈 배열 []로 나간다

에러 종류에 따라 필드가 생겼다 없어졌다 하면 소비자는 파서를 다시 분기해야 하고, 그러면 "포맷이 여러 개인 상태"에 표준화라는 이름만 붙인 것이 된다. 키의 존재 여부가 아니라 값의 길이로 구분하게 만드는 것이 계약이다.

4-2. 전역 핸들러 — 컨트롤러에서 try-catch가 사라진다

@RestControllerAdvice
@RequiredArgsConstructor
public class GlobalExceptionHandler {

        log.warn("business error: code={}, message={}", code.getCode(), e.getMessage());4xx = warn, 스택 없이 (8절)

        // 실패한 필드를 전부 담는 이유: 하나만 알려주면 사용자가 고치고 제출할 때마다
        // 다음 오류를 새로 만나는 UX 가 된다.
        return ResponseEntity.badRequest()
                .body(ErrorResponse.of(ErrorCode.INVALID_INPUT, errors));
    }

    // 최후의 안전망. 여기 걸린다는 것은 "우리가 예상하지 못한 실패" 라는 뜻이다.
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleUnexpected(Exception e) {
        log.error("unexpected error", e);5xx = error + 스택트레이스 전체 + 알람
        return ResponseEntity.internalServerError()
                .body(ErrorResponse.of(ErrorCode.INTERNAL_ERROR));
        // e.getMessage() 를 그대로 내보내면 SQL 문·테이블명·내부 클래스명이 새어 나간다.8-2 참고
        // 사용자에게는 고정 문구를, 원인은 위의 error 로그에 남긴다.
    }
}
검증 실패 예외는 MethodArgumentNotValidException 하나가 아니다 @RequestParam·@PathVariable에 붙은 제약, @Validated 클래스의 메서드 파라미터 검증 등은 다른 예외 타입으로 올라온다. 그래서 핸들러를 따로 등록해야 응답 형식이 통일된다. 예외 종류별 발생 조건은 21-bean-validation-vs-domain-validation.md가 정리하고, 스프링이 던지는 표준 예외를 한 번에 흡수하는 방법은 7절에서 다룬다.

5. 에러 코드 체계를 어떻게 짜는가

enum의 첫 칸에 들어갈 문자열의 형식을 정하는 문제다. 실무에서 갈리는 축이 둘이다.

5-1. 축 ① 도메인 접두사를 붙일 것인가 → 붙인다

이유 ① 장애 대시보드에서 group by가 된다

ORDER-*, PAY-*로 묶어 세면 "어느 도메인의 실패가 늘었나"가 바로 나온다. 접두사가 없으면 코드 목록을 사람이 분류해가며 세야 한다.

이유 ② 코드만 보고 담당을 안다

장애 중에 "이건 어느 팀에 물어봐야 하나"가 즉답된다. 마이크로서비스라면 접두사가 곧 소유 팀의 이름표다.

5-2. 축 ② 일련번호인가, 의미 있는 이름인가

ORDER-001 대 ORDER_SOLD_OUT — 트레이드오프
ORDER-001 (번호)ORDER_SOLD_OUT (의미)
로그·대시보드 가독성표를 찾아봐야 뜻을 안다그 자체가 문서다
프론트 분기 코드오타가 나도 눈에 안 띈다오타가 나면 읽는 순간 보인다
채번 관리"다음 번호가 몇 번이지"를 관리해야 하고, 팀이 나뉘면 번호대가 겹친다관리할 것이 없다
응답 크기짧다조금 길다

어느 쪽이든 프론트가 문자열 비교로 분기한다는 사실은 같다. 번호 쪽이 오타에 강해 보이지만 실제로는 반대다 — "ORDER-001"을 "ORDER-01"로 잘못 쓰면 눈으로 못 잡고, 조건문이 조용히 안 걸려 "알 수 없는 오류" 화면으로 떨어진다. "ORDER_SOLD_OUT"은 오타가 나면 읽을 때 티가 난다. 응답 크기 이득은 실무에서 문제가 되는 경우가 거의 없다.

결론 두 줄 — 순서가 중요하다

① 의미 있는 이름을 권한다  ·  ② 그보다 더 중요한 것은 조직 전체에서 형식 하나로 통일하는 것

어떤 API는 하이픈, 어떤 API는 대문자 스네이크면 소비자가 다시 API마다 다른 파싱을 하게 된다. 개별 선택보다 일관성이 앞선다는 이 순서를 뒤집어 말하면 "취향 논쟁"으로 들린다.

클라이언트가 다르게 행동해야 하는 경우에만 코드를 분리한다

코드가 200개인데 클라이언트가 8개만 분기하고 나머지를 "기타 오류"로 뭉갠다면, 그 192개는 만든 사람만 아는 코드다. "상품 ID 형식 오류"와 "쿠폰 ID 형식 오류"를 나눌 이유가 없다면 errors[]의 field로 구분하면 된다.

그리고 한번 공개한 코드는 클라이언트 분기문에 박히므로 응답 필드명과 같은 급의 불변 계약이 된다 — 의미 변경·삭제는 파괴적 변경이고, 앱 스토어에 나간 모바일 앱은 서버 배포로 회수되지 않는다. 자세한 논점은 09-rest-api/05-error-response-body-standardization.md 2-6절.

6. 각 ErrorCode의 HTTP status를 어떻게 고르는가

enum의 세 번째 칸이다. 코드 체계는 우리가 만드는 것이지만 status는 이미 표준이 뜻을 정해 놓은 값이고, 게이트웨이·로드밸런서·APM·클라이언트 라이브러리의 재시도 로직이 바디를 열어 보지 않고 이 숫자만 읽는다. 그래서 아무 값이나 넣으면 안 된다.

암기 장치 — 질문 순서는 "우 · 인 · 자 · 형 · 상"

우리 잘못? → 누구인지? → 자원 있나? → 형태 맞나? → 상태와 맞나?

순서가 중요한 이유는 앞의 질문이 뒤를 가리기 때문이다. 예를 들어 인증이 안 된 사용자의 잘못된 입력은 400이 아니라 401이다 — 애초에 그 입력을 검증해줄 이유가 없다.

6-1. 팀 규칙으로 정할 때의 실용적 출발점

"비즈니스 규칙 위반에 400을 줄지 409나 422를 줄지"는 실무에서 늘 논쟁이 된다. 이 논쟁의 결론을 개인이 그때그때 내리게 두는 것이 진짜 문제다. ErrorCode enum이 있으면 판단이 코드 리뷰 대상이 되고, 새 코드를 추가할 때 옆줄의 기존 항목이 곧 기준선이 된다.

나눈다 — 400 vs 409

클라이언트에게 주는 지시가 다르다. 400은 "입력을 고쳐서 다시 보내라", 409는 "입력은 멀쩡하니 최신 상태를 다시 조회한 뒤 판단하라". 실익이 분명하므로 반드시 나눈다.

안 나눠도 된다 — 400 vs 422

클라이언트가 어차피 바디의 code를 보고 필드별 메시지를 띄우므로 구분의 실익이 작다. 검증 실패는 전부 400으로 통일하는 팀이 많고 그것도 합리적이다.

반대로 컨트롤러마다 ResponseEntity.status(...)를 직접 쓰면 같은 성격의 실패가 API마다 다른 status로 나가고, 클라이언트는 결국 status를 믿지 못해 바디만 보게 된다. status가 장식이 되는 순간 앞서 말한 인프라 계층 전부가 눈을 잃는다.

반드시 붙일 규칙 — 도메인 불변식 위반은 4xx가 아니라 5xx

IllegalArgumentException처럼 "정상 흐름에서는 나올 수 없는" 예외가 API 경계까지 올라왔다면 → 5xx

그것은 사용자 입력 문제가 아니라 앞 계층 검증이 뚫렸다는 버그 신호다. 이걸 400으로 내려보내면 사용자에게 "입력을 확인하세요"라고 거짓말을 하면서 우리 버그는 알람도 없이 묻힌다. 400은 사용자가 고칠 수 있는 것에만 준다.

7. 스프링 표준 예외까지 한 번에 흡수 · ProblemDetail

7-1. ResponseEntityExceptionHandler — 남는 구멍을 메운다

우리가 정의한 예외만 잡아서는 포맷이 통일되지 않는다. 바인딩 실패, 본문 파싱 실패, 지원하지 않는 메서드, 매핑되지 않은 경로 같은 스프링 MVC 자신이 던지는 예외가 남기 때문이다. 그대로 두면 이들은 스프링 기본 응답으로 나가고, 프론트는 "어떤 에러는 우리 포맷, 어떤 에러는 스프링 포맷"을 만난다.

ResponseEntityExceptionHandler는 무엇인가 스프링 표준 예외들을 한 클래스에 몰아 등록해 둔 추상 클래스다. Spring Framework 6.2 기준으로 여기에 걸려 있는 예외는 HttpRequestMethodNotSupportedException, HttpMediaTypeNotSupportedException, MissingServletRequestParameterException, MethodArgumentNotValidException, HandlerMethodValidationException, NoResourceFoundException, HttpMessageNotReadableException, TypeMismatchException, MaxUploadSizeExceededException 등 스무 개 가까이 된다. 상속만 하면 이 전부가 우리 Advice의 관할로 들어온다.
흡수 상속 + handleExceptionInternal 한 곳에서 포맷을 갈아 끼운다
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {이 한 줄이 스무 개를 데려온다

    // 상속한 표준 예외들의 응답은 이 한 곳을 거쳐 나간다.
    // 예외 종류별로 메서드를 따로 오버라이드하지 않아도 포맷이 통일되는 이유다.
    @Override
    protected ResponseEntity<Object> handleExceptionInternal(
            Exception ex, Object body, HttpHeaders headers,
            HttpStatusCode statusCode, WebRequest request) {

        ErrorCode code = mapToErrorCode(statusCode);   // status → 우리 ErrorCode 로 환산
        log.warn("spring standard exception: {}", ex.getClass().getSimpleName());
        return ResponseEntity.status(statusCode)
                .body(ErrorResponse.of(code));         // 우리 포맷으로 갈아 끼운다
    }

    // 검증 실패만은 필드별 상세가 필요하므로 따로 오버라이드한다
    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex, HttpHeaders headers,
            HttpStatusCode status, WebRequest request) {
        List<ErrorResponse.FieldError> errors = ex.getBindingResult().getFieldErrors().stream()
                .map(f -> new ErrorResponse.FieldError(f.getField(), f.getDefaultMessage()))
                .toList();
        return ResponseEntity.badRequest()
                .body(ErrorResponse.of(ErrorCode.INVALID_INPUT, errors));
    }
}

상속하면 따라오는 함정 — 중복 등록으로 기동이 실패한다

MethodArgumentNotValidException은 이미 부모의 @ExceptionHandler에 등록돼 있다. 자식 클래스에 같은 예외의 @ExceptionHandler를 또 선언하면 중복 등록으로 애플리케이션 기동이 실패한다.

기동 실패 새 메서드를 만들면
class GlobalExceptionHandler
        extends ResponseEntityExceptionHandler {
  @ExceptionHandler(MethodArgumentNotValidException.class)
  public ResponseEntity<?> handle(...) { ... }부모와 중복
}
정상 부모 메서드를 오버라이드한다
class GlobalExceptionHandler
        extends ResponseEntityExceptionHandler {
  @Override
  protected ResponseEntity<Object> handleMethodArgumentNotValid(...)
}

7-2. ProblemDetail과 RFC 9457 가산점

에러 응답 포맷에는 이미 국제 표준이 있다. RFC 9457 "Problem Details for HTTP APIs"이고, 2016년의 RFC 7807을 2023년에 개정해 그 자리를 물려받은 문서다. type(문제 유형 식별 URI), title(유형의 짧은 요약), status, detail(이번 한 건의 설명), instance(이번 한 건의 식별 URI) 다섯 멤버로 이루어지고, application/problem+json이라는 전용 미디어 타입을 쓴다.

Spring Framework 6부터 ProblemDetail 타입이 프레임워크에 들어와 있다. 스프링 표준 예외들은 ErrorResponse 인터페이스를 구현하며 이미 ProblemDetail 본문을 들고 다니고, 우리 예외도 ErrorResponseException을 던지거나 ProblemDetail을 직접 반환하면 표준 형식으로 나간다.

표준 ProblemDetail 반환 — 표준 다섯 멤버 위에 자체 필드를 얹을 수 있다
@ExceptionHandler(SoldOutException.class)
public ProblemDetail handleSoldOut(SoldOutException e) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(
            HttpStatus.CONFLICT, "상품 " + e.getProductId() + "의 재고가 소진되었습니다");
    pd.setType(URI.create("https://api.example.com/problems/sold-out"));  // 유형 식별자
    pd.setTitle("재고 소진");
    pd.setProperty("code", "ORDER_SOLD_OUT");확장 필드 — 우리 코드 체계를 얹는다
    return pd;
}
스위치와 자체 Advice를 같이 켜면 생기는 혼란 Spring Boot 3에는 이것을 자동으로 켜는 스위치가 있다 — spring.mvc.problemdetails.enabled=true(기본값 false). 켜면 부트가 ResponseEntityExceptionHandler를 상속한 Advice를 하나 등록해, 스프링이 처리하는 예외들의 응답을 Problem Details 형식으로 내보낸다.
여기서 함정 — 자체 Advice에서 이미 같은 예외들을 처리하고 있는데 이 스위치까지 켜면, 어느 쪽이 이기는지는 3절의 Advice 순서 규칙에 달린다. 둘을 동시에 켜 놓고 "왜 내 포맷이 안 나오지"를 뒤지는 상황이 생기므로, 표준을 쓸지 자체 포맷을 쓸지 하나로 정하는 편이 낫다.

"RFC 9457입니다" 한 줄이 포맷 설명서보다 훨씬 싸다. 상대도 이미 파서를 갖고 있을 수 있다.

여기에 전환 비용까지가 판단 재료다 — 이미 자체 포맷으로 운영 중인 API를 표준으로 바꾸는 것 자체가 모든 소비자의 파서를 고치게 만드는 파괴적 변경이다. 전체 논의는 09-rest-api/05-error-response-body-standardization.md 3절.

8. 운영 설계 — 로그 정책과 비노출

8-1. 4xx와 5xx를 다르게 다뤄야 하는 이유 — 숫자로 확인한다

"4xx는 warn, 5xx는 error"라는 규칙은 자주 인용되지만 근거를 대지 못하면 그냥 관습이다. 근거는 알람 피로(alert fatigue) — 알람이 너무 자주 울려 사람이 그것을 무시하게 되고, 그래서 진짜 장애의 알람도 함께 무시되는 현상이다.

비유 — 토스트 연기에 매일 울리는 화재경보기 경보기가 토스트 굽는 연기에 매일 울리면 사람들은 결국 배터리를 빼버린다. 그 순간 경보기는 진짜 불이 났을 때도 울리지 않는 물건이 된다. 4xx를 error로 찍는 것은 알람 시스템에 매일 토스트 연기를 주입하는 일이다.

감시 방법코드별 발생률의 급변이라는 집계 지표발생 자체가 신호

4xx에서 스택트레이스를 빼는 이유는 심각도 때문만이 아니다. 예외 하나당 수십 줄이 쌓여 로그 저장 비용과 검색 속도에 직접 영향을 준다. 게다가 원인이 요청 안에 있으므로 스택을 봐도 새로 알 것이 없다.

균형 — "4xx를 무시하라"는 뜻이 아니다

개별 발생은 warn으로 조용히 남기되, 감시는 "코드별 발생률의 급변"이라는 집계 지표로 건다

401이 평소의 100배로 튀면 그것은 크리덴셜 스터핑 시도이고, 특정 API의 400이 급증하면 클라이언트가 잘못 배포된 것이다. 개별 이벤트로 울리는 알람과 비율 변화로 울리는 알람은 다른 물건이라는 구분을 말하면 운영 감각이 드러난다.

10-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

전역 예외 처리의 본질은?
애너테이션이 아니라 "모든 실패가 하나의 계약된 모양으로 나간다"는 시스템 간 약속. 포맷을 정하는 자리가 딱 한 곳만 존재해야 한다.
Advice는 어느 단계에서 불리나?
DispatcherServlet이 잡은 예외 → HandlerExceptionResolver 체인의 1순위(ExceptionHandlerExceptionResolver). 그래서 스프링 기본 처리보다 우선한다.
핸들러 선택 3단계는?
컨 · 순 · 촌 — 컨트롤러 안 최우선 → Advice 순서(첫 매칭에서 멈춤, 함정) → 예외 상속 촌수.
전용 핸들러가 안 불린다면?
넓은 Advice가 앞 순서에 있다. 규칙: 넓게 잡는 Advice일수록 뒤에. 안전망은 LOWEST_PRECEDENCE.
ErrorCode enum의 세 칸은?
코 · 메 · 상 — code · message · HttpStatus. 이 셋이 한 줄에 붙어 있는 것이 단일 진실 공급원의 실체.
status와 code의 역할 분담은?
status = 바디를 안 여는 기계(게이트웨이·LB·APM·재시도)가 읽고, code = 클라이언트 화면 분기와 대시보드 group by가 읽는다.
status 고르는 질문 순서는?
우 · 인 · 자 · 형 · 상 — 우리 잘못(5xx) → 인증(401)/인가(403) → 자원(404) → 형태(400) → 상태 충돌(409).
도메인 불변식 위반의 status는?
4xx가 아니라 5xx. 앞 계층 검증이 뚫렸다는 버그 신호다. 400으로 내리면 사용자에게 거짓말하고 버그는 묻힌다.
코드 분리 기준은?
클라이언트가 다르게 행동해야 하는 경우에만. 아니면 errors[].field로 구분한다.
4xx를 error로 찍으면?
2만 20건 중 20건 = 0.1%. 알람이 4xx 변동에 계속 울려 며칠이면 아무도 안 본다. 로그 레벨은 알람 규칙이 읽는 입력값.
응답에 담을 것 / 담지 말 것?
담을 것 trace id(CS ↔ 로그 진입점) · 담지 말 것 스택트레이스 · e.getMessage()(SQL·테이블명 유출 = 보안 문제).
Advice가 못 잡는 세 구역은?
필 · 경 · 비 = 필터(앞) · 매핑 없는 경로(밖) · 비동기(딴 스레드). 통일 방법은 공통 ErrorResponseWriter를 함께 쓰는 것.
스프링 표준 예외 흡수는?
ResponseEntityExceptionHandler 상속 + handleExceptionInternal 오버라이드. 같은 예외에 @ExceptionHandler를 또 선언하면 기동 실패.
표준 포맷을 쓸지 판단 기준은?
소비자가 누구인가. 사내 프론트 하나면 자체 포맷, 외부 파트너·공개 API면 RFC 9457. 전환은 파괴적 변경.

10-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

@ControllerAdvice가 못 잡는 예외는 어떤 게 있나요? 필수힌트: 구역을 나열하기 전에 "왜"를 한 문장으로. 위치 문제지 설정 문제가 아니다

먼저 왜 못 잡는지를 한 문장으로 말한다. @ControllerAdvice는 DispatcherServlet이 자기 try 안에서 잡은 예외를 HandlerExceptionResolver에 넘겨야 실행되는 장치인데, 필터의 예외는 DispatcherServlet에 도달한 적이 없다. 위치 때문이지 설정 문제가 아니라는 것이 핵심이다.

그다음 구역을 든다 — 필터 계층(Spring Security의 인증·인가 실패가 대표), 매핑되지 않은 경로, 그리고 HTTP 요청 스레드 밖(@Async, @Scheduled). 필 · 경 · 비다.

대응은 앞의 둘과 마지막을 나눠 말한다. 앞의 둘은 응답을 직접 써야 하므로 AuthenticationEntryPoint·AccessDeniedHandler·예외 처리 필터·ErrorController에서 처리하되, 핵심은 각자 JSON을 만드는 것이 아니라 공통 ErrorResponse 생성기를 주입받아 함께 쓰는 것이다. 그래야 포맷 정의가 한 곳에만 남는다. 마지막은 돌려줄 응답이 없으므로 비동기 예외 핸들러에서 로깅·알람으로 다룬다.

아무 대응도 안 하면 실제로 무엇이 나가는지까지 말하면 확실해진다. 스프링 부트라면 톰캣이 /error로 재진입시켜 부트 기본 JSON이나 Whitelabel HTML이 나가고, 그 처리마저 없으면 톰캣의 HTML 에러 페이지가 나가 프론트의 JSON 파서가 터진다.

같은 예외의 핸들러가 여러 곳에 있으면 무엇이 실행되나요? 필수힌트: 세 단계로 답하고, 2단계의 함정과 3단계의 안심을 함께 말한다

세 단계로 답한다. ① 컨트롤러 클래스 안의 @ExceptionHandler가 최우선이고, 있으면 전역 Advice는 조회조차 되지 않는다. ② 없으면 Advice 빈들을 @Order 순으로 훑어 매칭되는 메서드를 가진 첫 Advice에서 멈춘다. ③ 그 Advice 안에서 여러 메서드가 매칭되면 예외 상속 계층에서 거리가 가장 가까운 것을 고른다.

③ 덕분에 Exception 안전망을 깔아 둬도 구체 핸들러가 있으면 그쪽이 이긴다는 점, 그리고 ② 때문에 순서가 앞선 Advice의 넓은 핸들러가 뒤쪽 Advice의 구체 핸들러를 통째로 가려 버리는 함정이 있다는 점을 함께 말하면 실제로 겪어 본 답이 된다.

규칙은 하나다 — 넓게 잡는 Advice일수록 뒤에 둔다. 안전망은 @Order(Ordered.LOWEST_PRECEDENCE)에 두는 것이 기본이다.

왜 예외를 catch해서 200 OK에 에러 바디로 주면 안 되나요? 함정힌트: "바디를 파싱하지 않는 소비자"가 누구인지부터. 세 가지가 동시에 망가진다

HTTP status는 바디를 파싱하지 않는 소비자들이 읽는 유일한 신호이기 때문이다. 200으로 감싸면 세 가지가 한꺼번에 망가진다.

① 관측이 죽는다. 게이트웨이·로드밸런서·APM의 에러율 지표가 전부 0이 되어, 결제가 전부 실패하는 중에도 대시보드는 초록색이다. 장애를 사용자 문의로 처음 알게 된다.

② 캐시와 재시도가 오동작한다. 프록시·CDN이 에러 응답을 정상 응답으로 캐싱할 수 있고, 클라이언트 라이브러리의 자동 재시도가 "성공했다"고 판단해 돌지 않는다.

③ 클라이언트가 매번 바디를 열어야 한다. HTTP 클라이언트에 에러 인터셉터 하나를 두는 공통 처리가 불가능해진다.

정리는 이중 축으로 한다 — status로 기계가 읽는 부류를, 바디의 code로 클라이언트가 읽는 세부 구분을 담당시킨다. 어느 한쪽만으로는 안 된다.

에러 코드 체계는 어떻게 설계하나요? HTTP status만으로는 왜 부족한가요? 시니어 변별힌트: "status는 종류가 적다"를 결제 사례로 구체화한 뒤, 분리 기준과 계약성으로 마무리

status는 종류가 적어 비즈니스 구분을 담지 못한다. 실무에서 쓰는 4xx는 400·401·403·404·409·422·429 정도인데, 결제 하나가 낼 수 있는 실패는 잔액 부족·한도 초과·카드 만료·필수값 누락처럼 훨씬 많고 각각 클라이언트가 사용자를 보내야 할 화면이 다르다. status만 있으면 넷이 전부 같은 400이고, 클라이언트가 구분할 방법은 message 문자열 비교뿐이다. 그 순간 서버가 문구를 다듬는 커밋이 프론트 장애가 된다.

그래서 기계 판독용 코드를 별도 축으로 둔다. 도메인 접두사를 붙이는 이유는 장애 대시보드에서 접두사로 group by 하면 어느 도메인의 실패가 늘었는지 바로 나오고, 코드만 보고 어느 팀에 물어볼지 알기 때문이다. 접두사 뒤는 일련번호보다 의미 있는 이름을 권하는데, 번호는 로그에서 뜻을 알려면 표를 찾아야 하고, 채번 관리 부담이 생기며, 오타가 나도 눈에 안 띄기 때문이다.

여기서 시니어답게 보이는 지점은 분리 기준이다. "클라이언트가 다르게 행동해야 하는 경우에만 코드를 분리한다." 코드가 200개인데 클라이언트가 8개만 분기하고 나머지를 "기타 오류"로 뭉갠다면 그 192개는 만든 사람만 아는 코드다. "상품 ID 형식 오류"와 "쿠폰 ID 형식 오류"를 나눌 이유가 없다면 errors[]의 field로 구분하면 된다.

마지막으로 코드 목록을 문서화해 프론트와 공유하는 것까지가 설계라고 말한다. 에러 코드는 성공 응답 스키마와 동급의 API 계약이고, 한번 공개한 코드의 의미 변경·삭제는 응답 필드 삭제와 같은 파괴적 변경이다. 특히 앱 스토어에 나간 모바일 앱은 서버 배포로 회수되지 않는다.

비즈니스 규칙 위반에는 400과 409·422 중 무엇을 주나요?힌트: 코드 하나를 고르기 전에 "이건 팀 규칙의 대상"이라고 못 박는다

먼저 이 판단이 개인이 아니라 팀 규칙의 대상이라는 점을 말한다. 같은 성격의 실패가 API마다 다른 status로 나가면 클라이언트는 결국 status를 믿지 못하고 바디만 보게 되고, 그러면 status는 장식이 된다. 코드 하나를 정확히 고르는 것보다 일관성이 중요하다.

그다음 실용적 기준을 든다. 400과 409의 차이는 클라이언트에게 주는 지시가 다르므로 반드시 나눈다 — 400은 "입력을 고쳐서 다시 보내라"이고, 409는 "입력은 멀쩡하니 최신 상태를 다시 조회한 뒤 판단하라"다. 이미 취소된 주문을 또 취소하거나, 재고가 소진됐거나, 낙관적 락이 충돌한 경우가 409다.

반면 400과 422는 굳이 나누지 않는 팀이 많고 그것도 합리적이다. 클라이언트가 어차피 바디의 코드를 보고 필드별 메시지를 띄우므로 구분의 실익이 작기 때문이다.

여기에 한 가지를 더 붙이면 답이 완성된다. 도메인 불변식 위반은 4xx가 아니라 5xx로 분리한다. "정상 흐름에서는 나올 수 없는" 예외가 API 경계까지 올라온 것은 사용자 입력 문제가 아니라 앞 계층 검증이 뚫렸다는 버그 신호이므로, 400으로 내려보내면 사용자에게 거짓말을 하면서 우리 버그를 알람 없이 묻는 셈이 된다.

4xx를 error 로그로 남기면 안 되는 이유가 뭔가요? 필수힌트: 단어 하나(알람 피로)로 시작해 숫자로 뒷받침하고, 마지막에 균형을 잡는다

알람 피로 때문이라고 답하고 숫자로 뒷받침한다. 하루 100만 요청에 4xx가 2%면 2만 건인데, 이걸 error로 찍으면 하루 error 로그 2만 20건 중 실제 조사 대상인 5xx 20건은 0.1%가 된다. "error 급증 시 알람" 규칙은 4xx 변동에 계속 울려 며칠이면 아무도 안 보게 되고, 5xx 20건은 검색으로도 안 찾아진다.

로그 레벨은 심각도 표시가 아니라 알람 규칙이 읽는 입력값이라는 것이 핵심이다. 여기에 스택트레이스를 4xx에서 빼는 이유(예외당 수십 줄이 쌓여 저장 비용과 검색 속도에 직접 영향, 원인이 요청 안에 있어 스택을 봐도 새로 알 것이 없음)를 덧붙이면 좋다.

마무리는 균형이다. 4xx를 무시하라는 뜻은 아니다. 401이 평소의 100배로 튀면 크리덴셜 스터핑이고, 특정 API의 400 급증은 클라이언트 오배포 신호다. 개별 발생은 warn으로 조용히 남기되 감시는 코드별 발생률의 급변이라는 집계 지표로 건다 — 개별 이벤트 알람과 비율 변화 알람은 다른 물건이라는 구분을 말하면 운영 감각이 드러난다.

검증 실패처럼 에러가 여러 개인 경우는 응답을 어떻게 설계하나요?힌트: UX 시나리오 → 배열 필드 → "빈 배열로도 나간다" → field 문자열도 계약

단일 message로 첫 오류만 알려주면 "고치고 제출 → 다음 오류 → 또 고치고 제출"이라는 최악의 UX가 된다. 사용자는 자기가 세 군데를 틀렸다는 사실을 세 번 나눠 알게 된다.

그래서 공통 포맷에 필드별 상세 배열(errors: [{field, reason}])을 두고, MethodArgumentNotValidException의 BindingResult에서 전체 필드 오류를 변환해 담는다.

포인트는 이 배열이 검증 실패가 아닌 에러에서도 사라지지 않고 빈 배열로 나간다는 것이다. 에러 종류마다 응답 모양이 달라지면 소비자가 파서를 다시 분기해야 하고, 그건 표준화가 아니라 "포맷이 여러 개인 상태"에 이름만 붙인 것이다.

한 걸음 더 들어가면 field에 무엇을 넣을지도 계약이다. 중첩 객체와 배열이 섞이면 경로 표기가 필요한데, 서버는 items.0.quantity로 보내고 클라이언트는 items[0].quantity로 찾는 어긋남이 실제로 생긴다. 폼의 어느 칸에 빨간 줄을 그을지가 이 문자열 하나에 달려 있다.

@ExceptionHandler 메서드 자체가 예외를 던지면 어떻게 되나요? 함정힌트: "그 예외가 다시 Advice로 간다"고 답하면 무한 루프가 된다 — 그럴 리 없다

그 예외가 다시 @ExceptionHandler의 대상이 되지는 않는다. 그렇게 되면 핸들러가 자기 예외를 자기가 다시 처리하는 무한 루프가 되기 때문이다. 스프링은 이 경우를 "이 리졸버가 처리하지 못한 것"으로 보고 남은 리졸버로 넘기며, 아무도 못 잡으면 예외가 서블릿 컨테이너까지 올라가 결국 /error 응답(부트 기본 JSON 또는 Whitelabel HTML)이 나간다.

실무적 교훈은 하나다 — 핸들러 안에서는 실패할 수 있는 일을 하지 않는다. 흔한 사고가 핸들러 안에서 DB를 조회해 안내 문구를 만들거나, 외부 알림을 동기로 호출하거나, null일 수 있는 값을 꺼내 쓰는 것이다. 그 순간 사용자는 우리 포맷이 아닌 응답을 받고, 원래 예외의 정보까지 함께 잃는다.

방어책은 두 가지다 — ① 핸들러는 ErrorCode를 읽어 응답을 만드는 일만 한다(부가 작업은 비동기로 밀어낸다), ② 그래도 남는 위험에 대비해 /error 컨트롤러를 우리 포맷으로 대체해 둔다(9절의 소비자 ④). 마지막 그물이 있어야 최악의 경우에도 HTML이 나가지 않는다.

@RestControllerAdvice의 적용 범위를 좁힐 수 있나요? 가산점힌트: 속성 세 가지와, 실무에서 그게 필요해지는 상황 하나

좁힐 수 있다. @ControllerAdvice에는 대상 컨트롤러를 한정하는 속성이 있다 — basePackages·basePackageClasses(특정 패키지 하위 컨트롤러만), assignableTypes(특정 클래스·인터페이스를 구현한 컨트롤러만), annotations(특정 애너테이션이 붙은 컨트롤러만). 지정하지 않으면 모든 컨트롤러가 대상이다.

실무에서 이게 필요해지는 대표 상황은 "한 애플리케이션에 성격이 다른 API가 공존할 때"다. 예컨대 외부 공개 API는 RFC 9457 형식으로, 사내 어드민 API는 자체 포맷으로 내보내야 한다면 Advice를 둘로 나누고 각각 범위를 지정한다. 또는 레거시 v1과 신규 v2의 응답 포맷이 다를 때도 같은 방법을 쓴다.

다만 범위를 나누는 순간 3절의 순서 규칙이 다시 살아난다 — 범위가 넓은 Advice일수록 뒤(LOWEST_PRECEDENCE)로 보내야 좁은 Advice가 먼저 기회를 얻는다. 그리고 나누더라도 ErrorResponse 생성 로직은 공유해야 한다. 포맷이 둘로 갈리는 것과, 포맷 정의가 네 곳에 복사되는 것은 다른 문제다.

에러 문구는 서버가 정하나요, 클라이언트가 정하나요? 시니어 변별힌트: 다국어와 톤을 떠올리면 "code가 계약의 핵심"인 이유가 한 겹 더 드러난다

둘 다 필요하고 역할이 다르다. 서버의 message는 기본값이자 폴백이고, 최종 문구 결정권은 클라이언트에 두는 조합이 실무에서 잘 작동한다.

이유는 셋이다. ① 다국어 — 사용자의 언어는 클라이언트가 알고 있고, 서버가 모든 언어의 문구를 들고 있는 것보다 클라이언트가 code로 자기 언어 문구를 고르는 편이 단순하다. ② 톤과 맥락 — 같은 ORDER_SOLD_OUT이라도 상세 페이지에서는 "품절된 상품입니다", 결제 화면에서는 "결제 중 재고가 소진되었습니다. 장바구니를 확인해 주세요"처럼 화면마다 다른 문구가 맞다. ③ 배포 주기 — 문구 수정 하나에 서버 배포가 필요한 구조는 느리다.

그래서 서버 message는 "클라이언트가 아직 모르는 코드를 만났을 때 그대로 보여줘도 안전한 문장"이어야 한다. 이 기준이 곧 내부 정보를 담지 않는다(8-2)와 같은 규칙으로 이어진다.

이 답의 진짜 결론은 "그래서 code가 계약의 핵심"이라는 것이다. 문구는 양쪽이 자유롭게 바꿀 수 있지만 code는 클라이언트 분기문에 박혀 있어 바꿀 수 없다. 문구를 다듬는 커밋이 프론트를 깨뜨리지 않게 만드는 것이 코드 축을 따로 두는 이유였다.

전역 예외 처리는 어떻게 테스트하나요?힌트: "예외가 잘 잡히나"만 보면 절반이다 — 계약이 지켜지는지를 본다

테스트의 대상을 두 층으로 나눠 말한다.

① 매핑이 맞는가 — MockMvc로 예외를 던지는 요청을 보내고 status와 바디의 code를 함께 검증한다. Advice만 떼어 빠르게 보고 싶으면 MockMvcBuilders.standaloneSetup(controller).setControllerAdvice(new GlobalExceptionHandler())로 컨테이너 없이 조립할 수 있고, 필터·Security까지 얽힌 경로는 전체 컨텍스트를 띄워야 실제와 같아진다(9절의 구역 ①은 standaloneSetup으로는 재현되지 않는다).

② 계약이 지켜지는가 — 이쪽이 자주 빠진다. 모든 응답에 code·message·errors·traceId 네 필드가 항상 존재하는지, 검증 실패가 아닐 때 errors가 빈 배열로 나가는지, ErrorCode의 코드 문자열에 중복이 없는지는 enum 전체를 순회하는 테스트로 한 번에 잡을 수 있다. 새 ErrorCode를 추가하는 사람이 규칙을 어기면 빌드가 깨지게 만드는 것이 목적이다.

여기에 하나 더 붙이면 좋다 — 안전망 핸들러가 e.getMessage()를 노출하지 않는지를 테스트로 고정해 두는 것. 이 습관은 리팩터링 중에 조용히 되살아나기 쉬운 종류의 실수다.

한 줄 요약
전역 예외 처리의 본질은 @ControllerAdvice라는 애너테이션이 아니라 "모든 실패가 하나의 계약된 모양으로 나간다"는 시스템 간 약속이다 — ExceptionHandlerExceptionResolver가 예외 타입이 가장 가까운 핸들러를 골라 준다는 동작을 알고(그래서 넓게 잡는 Advice는 뒤에 둔다), ErrorCode enum을 코드·메시지·status의 단일 진실 공급원으로 삼아 "비즈니스 규칙 위반에 400인가 409인가" 같은 판단을 개인이 아니라 코드 리뷰의 대상으로 만들며, 4xx는 warn·5xx는 error+알람이라는 로그 정책을 알람 피로라는 근거 위에 세우고, 스프링 표준 예외는 ResponseEntityExceptionHandler 상속으로 흡수하고, 마지막으로 Advice가 구조적으로 닿지 못하는 필터·/error·비동기 구역까지 공통 ErrorResponse 생성기 하나를 함께 쓰게 만들어야 프론트엔드 협업 비용과 장애 시 에러 집계라는 실익이 완성된다.
