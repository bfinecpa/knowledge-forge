Spring WebFlux vs MVC 스레딩 모델 — "대기를 스레드 개수로 흡수하나, 이벤트로 흡수하나"

📖 약 9분 🧩 8개 섹션 0/8 섹션 이해
🎯 핵심 관전 포인트

MVC는 thread-per-request — 요청당 스레드 1개가 응답까지 묶이고, 대기 시간을 스레드 개수로 흡수한다(톰캣 기본 200개 = 동시 요청 상한). WebFlux(Netty)는 이벤트 루프 — 스레드를 코어 수만큼만 띄우고, I/O를 걸어놓은 뒤 스레드를 즉시 반납해 다음 이벤트를 처리한다(대기를 이벤트 통지로 흡수 → 적은 스레드로 수만 동시 연결). 그래서 WebFlux의 전제는 전 구간 논블로킹이다 — 이벤트 루프 위에서 블로킹(JDBC 등) 한 번이면 코어 수만큼뿐인 스레드가 잠겨 전체가 마비되므로, 블로킹 스택·CPU 바운드·팀 역량에 따라 오히려 독이 된다.

0

질문 + 의도

▾
면접 질문

"Spring WebFlux와 MVC의 스레딩 모델 차이를 설명해주세요. WebFlux 도입이 오히려 독이 되는 경우는?"

출제 의도기술 선택에서 "우리 팀의 학습 비용, 디버깅 난이도, 블로킹 라이브러리 의존성"까지 넣어 판단하는지 본다. 이력서에 WebFlux를 쓴 지원자의 이해가 튜토리얼 수준인지 운영 수준인지 가르는 질문이기도 하다.
1

MVC — thread-per-request (대기 = 스레드 점유)

▾
  • 요청 1개 = 톰캣 스레드 1개가 응답을 쓸 때까지 전담. DB 50ms 대기 중에도 스레드는 BLOCKED로 묶여 있다(다른 요청을 처리하지 못한다 — thread-pool-connection-pool-sizing.md 오개념 교정 2).
  • 동시 요청 상한 = 스레드풀 크기(기본 200). 필요 스레드 수는 Little's law로: 500 TPS × 응답 100ms = 동시 50개.
  • 대기가 길어질수록(외부 API 지연 등) 같은 TPS에 더 많은 스레드가 필요 — 대기 시간을 스레드 개수로 사는 모델. 스레드는 스택 ~1MB·컨텍스트 스위칭 비용이 있어 수천~수만 동시 연결에는 한계.
2

WebFlux(Netty) — 이벤트 루프 (대기 = 스레드 반납)

▾
  • 이벤트 루프 스레드는 코어 수만큼만(Netty 기본 = 가용 코어 수, 최소 4). 스레드가 요청에 전속되지 않는다.

  • 동작 방식:

    1. 요청 도착 → 이벤트 루프 스레드가 핸들러 체인 실행
    2. DB/외부 API 호출을 논블로킹으로 걸어놓고(콜백 등록) 스레드는 즉시 다음 이벤트 처리로 이동
    3. 50ms 뒤 응답이 소켓에 도착하면 → OS(epoll/kqueue)가 이벤트로 통지 → 이벤트 루프가 등록된 콜백(리액티브 체인의 다음 단계)을 이어서 실행
  • 스레드는 "요청을 기다리는" 일이 없고 항상 실행할 이벤트만 처리 → 대기 시간이 스레드를 소모하지 않아, 4~8개 스레드로 수만 동시 연결 감당.
  • Reactor의 Mono/Flux는 이 "걸어놓고 나중에 이어 하기"를 선언적 체인으로 표현한 것. 백프레셔(소비 측이 감당할 만큼만 당겨 받기)도 스펙에 내장.

4

WebFlux가 독이 되는 경우

▾
  1. 이벤트 루프 위 블로킹 호출 — JDBC, 블로킹 HTTP 클라이언트, 파일 I/O, 심지어 느린 로깅까지. MVC에서 블로킹은 "200개 중 1개"의 국소 피해지만, WebFlux에서는 "4개 중 1개"라 폭발 반경이 정반대로 크다. DB가 JDBC(R2DBC 아님)면 결국 어딘가에서 블로킹 — WebFlux의 이득이 사라지고 위험만 남는다. 한 구간이라도 블로킹이면 전 구간 논블로킹이라는 전제가 깨진다.
  2. CPU 바운드 작업 — 대기가 없으면 반납할 것도 없다. 이벤트 루프가 연산에 잡혀 있는 동안 그 루프에 배정된 모든 연결이 지연. CPU 바운드는 모델과 무관하게 코어 수가 상한(thread-pool-connection-pool-sizing.md §4).
  3. 팀·운영 비용 — 리액티브 학습 곡선, 체인 곳곳에서 끊기는 스택트레이스로 디버깅 난이도 급상승, ThreadLocal 전제(MDC, SecurityContext, @Transactional의 트랜잭션 동기화 — transaction-synchronization-connection-binding.md) 전부 재작업. 의존 라이브러리 중 하나라도 블로킹이면 도루묵이므로 전체 의존성의 논블로킹 여부 점검이 도입 전 필수. "튜토리얼 수준 이해로 도입한 WebFlux"는 같은 하드웨어의 MVC보다 느리고 장애만 어렵게 만든다.
5

블로킹이 불가피할 때의 우회 — 그리고 그 대가

▾
java
// 이벤트 루프에서 블로킹 JDBC를 직접 호출하면 안 되므로 별도 스레드풀로 격리
Mono.fromCallable(() -> jdbcRepository.findById(id))   // 블로킹 호출
    .subscribeOn(Schedulers.boundedElastic())          // 전용 워커 풀에서 실행
  • boundedElastic은 블로킹 작업용 워커 풀(기본 상한 = 코어 × 10) — 이벤트 루프는 지키지만, 그 구간은 결국 thread-per-request로 회귀한 것이라 워커 풀 크기 산정 문제(Little's law)가 그대로 되살아난다. 이 우회가 코드의 주류가 되면 WebFlux를 쓸 이유가 없다.
  • publishOn은 체인의 이후 단계 실행 스레드를 바꾸고, subscribeOn은 구독(소스 실행) 스레드를 바꾼다 — 블로킹 소스 격리는 subscribeOn.
  • BlockHound: 이벤트 루프 스레드에서 블로킹 호출이 일어나면 예외를 던져주는 감지 도구 — 테스트 단계에서 "숨은 블로킹"을 잡는 안전망.
6

제3의 선택지 — Java 21 가상 스레드(Loom)

▾
  • 가상 스레드는 블로킹 시 캐리어 스레드에서 자동으로 마운트 해제 — "블로킹 코드를 그대로 두고" 스레드를 사실상 무한정 띄우는 모델. thread-per-request의 프로그래밍 단순함 + 이벤트 루프급 동시성.
  • Spring Boot 3.2+에서 spring.threads.virtual.enabled=true로 톰캣 요청 처리에 적용 가능 — 리액티브 재작성 없이 MVC 스타일 유지. "동시 연결 때문에 WebFlux"라는 근거는 상당 부분 약화됐다(단, 백프레셔·스트리밍 조합은 여전히 WebFlux 영역이고, DB 커넥션 등 물리 자원 산정은 그대로 유효).
7

꼬리질문 대비 포인트

▾

질문을 눌러 답을 펼쳐보세요 — 먼저 스스로 답해본 뒤 확인하면 훨씬 오래 남습니다.

그 루프에 배정된 모든 채널(연결)의 이벤트 처리가 멈춘다. Netty는 채널을 루프에 고정 배정하므로 다른 루프가 대신 처리해주지 않는다 — 1/N 마비가 아니라 해당 연결들 전면 정지.

단일 요청 응답시간은 빨라지지 않는다(DB 50ms는 그대로 50ms). 좋아지는 건 같은 하드웨어로 감당하는 동시 연결 수와 자원 효율. 처리량 병목이 스레드가 아니라면(대부분의 사내 API가 그렇다) 이득이 없다.

가능하고 흔한 절충. 외부 API 병렬 호출 구간만 논블로킹으로 얻고 서블릿 모델은 유지 — 단 block() 하는 순간 그 스레드는 여전히 묶인다는 것을 인지할 것.

ThreadLocal 기반 트랜잭션 동기화는 스레드가 바뀌는 리액티브 체인에서 무의미 — R2DBC + Reactor Context 기반의 리액티브 트랜잭션 관리로 대체해야 한다.

① 동시 연결이 실제로 스레드 한계에 부딪히는가(메트릭 근거) ② 전 의존성이 논블로킹 가능한가(DB 드라이버 포함) ③ 팀이 리액티브 디버깅을 감당하는가 ④ 가상 스레드로 충분하지 않은가 — 넷 다 통과해야 도입.

✅ 한 줄 요약

MVC는 요청당 스레드 1개가 응답까지 묶여 대기를 "스레드 개수"로 흡수하고(상한 = 풀 크기), WebFlux는 코어 수만큼의 이벤트 루프가 I/O를 걸어놓고 스레드를 반납해 대기를 "이벤트 통지"로 흡수한다(적은 스레드로 수만 연결) — 대신 전 구간 논블로킹이 전제라 이벤트 루프 위 블로킹 한 번(JDBC 등)의 폭발 반경이 MVC와 정반대로 크며, 블로킹 스택·CPU 바운드·팀 역량 부족이면 독이 되고, Java 21 가상 스레드가 "블로킹 코드 그대로"라는 제3의 선택지다.
