Spring Cache 추상화(@Cacheable)
프록시가 대신하는 read-through와 네 가지 함정 — "TTL 속성을 애너테이션에서 찾다가 못 찾는" 이유까지

면접 질문: "@Cacheable의 동작 원리와 함정은? (자기 호출 미적용, 캐시 키 설계, null 캐싱, TTL은 어디서 설정하나)"

핵심 관전 포인트 — @Cacheable은 프록시가 메서드 호출을 가로채 캐시를 먼저 조회하고, 히트면 메서드를 아예 실행하지 않고 캐시값을 돌려주며, 미스일 때만 실행 후 결과를 저장하는 read-through 구조다. 그래서 프록시 기반 애너테이션의 공통 제약(자기 호출 미적용)을 그대로 물려받고, 실무 사고는 대부분 두 곳에서 난다 — 기본 키 생성기는 파라미터 값만으로 키를 만들 뿐 클래스도 메서드도 키에 넣지 않아 같은 캐시 이름을 쓰는 두 메서드가 서로의 값을 받아 가고, 키에 사용자·테넌트 식별자가 빠지면 성능 버그가 아니라 남의 데이터가 보이는 보안 사고가 된다. null 캐싱은 "없는 데이터를 계속 조회하는 캐시 관통"과 "생겼는데도 없다고 나오는 지연" 사이의 선택이고, TTL은 애너테이션에 없다 — 만료의 의미와 단위가 구현체마다 달라 추상화 대상에서 빠졌기 때문이며 CacheManager 설정에서 캐시 이름별로 준다. 즉 이 질문은 애너테이션 한 줄 뒤의 동작과 "추상화의 경계가 어디까지인가"를 확인하고 쓰는지를 본다.
  • 1
    동작은 한 문장이다 — 프록시가 메서드 앞에서 키를 만들어 캐시를 조회하고, 히트면 원본 메서드를 아예 실행하지 않고 캐시값을 반환하며, 미스일 때만 실행하고 그 결과를 저장한다(read-through). @Transactional·@Async와 완전히 같은 Spring AOP 메커니즘이고, 가로채서 무엇을 하는지만 다르다.
  • 2
    함정은 네 가지 — "자 · 키 · 널 · 티". 자기 호출은 프록시를 우회해 예외도 로그도 없이 캐시가 통째로 무시되고, 키는 기본 생성기가 클래스도 메서드도 넣지 않고 파라미터 값만 쓰기 때문에 같은 캐시 이름의 두 메서드가 같은 칸을 공유한다 — 여기에 테넌트 ID가 빠지면 타사 데이터 유출이다.
  • 3
    나머지 둘은 "정답이 없다"가 정답이다. 널(null) 캐싱은 캐시 관통 ↔ 반영 지연의 트레이드오프라 짧은 TTL로 절충하고, 티(TTL)는 애너테이션에 존재하지 않는다 — Cache 인터페이스가 get·put·evict 셋뿐이라 만료가 공통 분모가 아니었기 때문이고, 그래서 CacheManager 설정에서 캐시 이름별로 준다.

0. 질문 + 출제 의도

질문: "Spring Cache 추상화(@Cacheable)의 동작 원리와 함정은? (자기 호출 미적용, 캐시 키 설계, null 캐싱, TTL은 어디서 설정하나)"

출제 의도: 캐시 추상화도 AOP 프록시 위에 있어 자기 호출에 무력하고, 캐시 키 설계 실수는 "다른 사용자의 데이터가 보이는" 사고로 직결된다. 애너테이션 한 줄의 편의 뒤에 있는 동작(키 생성 규칙, null 처리, TTL은 캐시 매니저 설정임)을 확인하고 쓰는지 — Redis/캐싱 지식이 스프링 계층에 착지하는 지점을 검증하는 질문이다.

이 페이지가 겨냥하는 약점 네 가지 ① "캐시를 붙여준다"에서 멈추는 것 → 1절에서 프록시가 실제로 실행하는 다섯 단계를 도식으로 못 박고, "히트면 원본이 안 돈다"는 한 줄에 밑줄을 긋는다.
② @Cacheable을 "캐시에 넣어준다"로 읽는 것 → 2절에서 갱신 메서드에 붙였을 때 save()가 아예 호출되지 않아 저장이 조용히 사라지는 과정을 호출 순서로 따라간다.
③ 키를 "알아서 잘 만들어 주겠지"로 넘기는 것 → 4절에서 엔트리 좌표가 (캐시 이름, 키) 둘뿐임을 격자로 보여주고, 같은 칸을 공유하는 사고 3형태를 분리한다.
④ "TTL은 CacheManager에서요"까지만 답하는 것 → 8절에서 왜 거기로 내려갔는지(Cache 인터페이스에 만료를 말할 자리가 없다)를 계층 도식으로 세운다.

암기 장치 — 이 질문의 함정 네 개는 "자 · 키 · 널 · 티"

자기 호출  ·  키 설계  ·  널(null) 캐싱  ·  티(TTL)의 위치

질문 자체가 괄호 안에 이 네 개를 나열해 준다. 네 글자를 쥐고 들어가면 답변에서 하나를 빠뜨릴 일이 없고, 각각이 "왜 그렇게 되는가"를 하나의 원인(프록시와 추상화의 경계)으로 묶어 말하면 암기한 것이 아니라 이해한 것으로 들린다.

한 문장 비유 — 비서, 그리고 사물함 비서: 사장 앞으로 온 전화를 비서(프록시)가 먼저 받아 "저번에 답해 드린 그 건"이면 사장을 부르지 않고 자기가 답한다. 처음 듣는 용건일 때만 사장(원본 메서드)에게 연결하고, 그 답변을 적어 둔다.  /  사물함: 캐시 엔트리의 주소는 구역 이름(캐시 이름) + 사물함 번호(키) 딱 두 개다. 누가 넣었는지(클래스·메서드)는 주소에 없다 — 그래서 번호만 같으면 남의 물건을 그대로 꺼내 간다. 4절의 사고 전부가 이 한 문장에서 나온다.

1. 동작 원리 — 프록시가 "조회 → 없으면 실행하고 저장"을 대신한다

1-1. 전제 지식 — 여기서 말하는 프록시가 무엇인가

@Cacheable을 붙이면 스프링은 그 빈을 그대로 등록하지 않고 한 겹 감싼 대리인 객체를 만들어 등록한다. 이 대리인이 프록시다.

프록시는 원본 객체인 척하면서 호출을 먼저 받아 부가 작업을 한 뒤 원본에 넘기는 대리인 객체다. 같은 인터페이스(또는 같은 클래스를 상속한 타입)를 구현하고 있어서 호출하는 쪽은 원본인지 대리인인지 구별하지 못한다. @Transactional, @Async와 완전히 같은 메커니즘(Spring AOP)이고, 가로채서 무엇을 하는지만 다르다 — 트랜잭션은 앞에서 BEGIN을 걸고 뒤에서 COMMIT을 하고, 캐시는 앞에서 조회하고 뒤에서 저장한다.

1-2. 프록시가 실제로 실행하는 다섯 단계

개념 프록시가 대신 실행하는 로직을 자바로 옮기면
public Member findMember(Long memberId) {
    Object key = keyGenerator.generate(target, method, memberId); // ① 캐시 키를 만든다
    Cache.ValueWrapper hit = cache.get(key);                      // ② 그 키로 캐시를 조회한다

    if (hit != null) {
        return (Member) hit.get();   // ③ 히트 — 원본 메서드를 아예 호출하지 않는다모든 사고의 뿌리
    }

    Member result = target.findMember(memberId);  // ④ 미스일 때만 진짜 메서드를 실행한다
    cache.put(key, result);                       // ⑤ 그 결과를 캐시에 남긴다
    return result;
}

1-3. 추상화 계층 — 구현체를 갈아끼울 수 있는 이유, 그리고 TTL이 없는 이유

분업 한 줄 — 8절까지 이 문장 하나로 간다

캐시 이름은 코드가 정하고, 그 캐시의 물리적 성질(저장소 · TTL · 크기 상한)은 설정이 정한다

2. 세 애너테이션 — 기준은 오직 "원본 메서드를 실행하는가"

@Cacheable, @CachePut, @CacheEvict를 "캐시 관련 애너테이션 3종"으로 뭉뚱그려 외우면 반드시 사고가 난다. 셋은 하는 일이 겹치지 않고, 원본 메서드를 실행하는가라는 기준 하나로 정확히 갈린다.

갈림길은 하나 — 실행 여부가 나머지를 전부 결정한다
원본 메서드 실행캐시에 하는 일한 줄 정의
@Cacheable히트면 안 한다미스일 때만 저장"있으면 안 부른다" — 읽기 전용 조회에만 쓴다
@CachePut항상 한다결과로 항상 덮어쓴다"항상 부르고 결과를 덮어쓴다" — 갱신 결과를 캐시에 반영
@CacheEvict항상 한다지운다"지운다" — 삭제, 또는 최종 값을 이 메서드가 모를 때

2-1. 지뢰 — 이름 때문에 갱신 메서드에 @Cacheable을 붙인다

@Cacheable이라는 이름이 "캐시 가능" 혹은 "캐시에 넣는다"로 읽히기 때문에, 결과를 캐시에 반영하고 싶은 갱신 메서드에 @Cacheable을 붙이는 실수가 흔하다.

문제 이름만 보고 갱신 메서드에 붙였다
@Cacheable(cacheNames = "members", key = "#member.id")조회용이다
public Member updateMember(Member member) {
    return memberRepository.save(member);
}
// 2차 호출부터 캐시 히트 → save()가 아예 안 불린다
고침 갱신에는 @CachePut
@CachePut(cacheNames = "members", key = "#member.id")항상 실행
public Member updateMember(Member member) {
    return memberRepository.save(member);
}
// 항상 실행하고, 그 결과로 캐시를 덮어쓴다

암기 장치 — 세 애너테이션은 "안 · 덮 · 지"

@Cacheable
있으면 안 부른다
조회 전용. 부작용 있는 메서드에 붙이면 그 부작용이 사라진다
@CachePut
항상 부르고 덮는다
갱신 후 곧바로 다시 읽을 가능성이 높을 때 — 미리 채워 둔다
@CacheEvict
그냥 지운다
삭제, 또는 최종 값을 이 메서드가 모를 때. 확신이 없으면 이쪽

@CachePut과 @CacheEvict의 선택 기준: "이 메서드가 캐시에 넣을 정확한 최종 값을 알고 있는가?" 갱신 경로가 여러 개라 확신이 없으면 evict가 안전하다 — 틀린 값을 넣는 것보다 다음 읽기에서 한 번 더 읽는 편이 낫다.

2-2. @CacheEvict의 두 옵션 — allEntries와 beforeInvocation

// 단건 무효화
@CacheEvict(cacheNames = "members", key = "#memberId")
public void deleteMember(Long memberId) { ... }

// allEntries = true      : 해당 캐시 이름의 전체 엔트리 삭제
// beforeInvocation = true: 메서드 실행 "전에" 삭제한다.
//   기본값은 실행 "후"라서, 메서드가 예외를 던지면 삭제가 아예 일어나지 않는다.
//   "실패하더라도 캐시는 무조건 비워야 한다"면 before로 뒤집는다.
@CacheEvict(cacheNames = "orgChart", allEntries = true, beforeInvocation = true)
public void rebuildOrgChart(Long companyId) { ... }
함정 — beforeInvocation의 기본값은 false다 재구축 도중 예외가 나면 캐시에는 낡은 값이 그대로 남는다. 이 상태가 오히려 더 위험한 도메인(권한, 가격)이라면 true로 뒤집어 "실패해도 일단 비운다"를 택한다. 반대로 true의 대가는 메서드가 실패했는데도 캐시가 비어 원본 부하가 튄다는 것이다 — allEntries = true와 함께 쓸 때 특히 그렇다(7절의 스탬피드를 스스로 만들 수 있다).

3. 함정 ① 자기 호출 — 프록시 기반 애너테이션의 공통 제약

캐시 로직은 프록시에 있는데, 같은 클래스 안에서 this.method()로 부르면 프록시를 거치지 않고 원본 객체를 직접 호출한다. 그래서 캐시가 아예 적용되지 않는다.

문제 같은 클래스 안에서 this로 호출
@Service
public class MemberService {

    public MemberSummary summarize(Long memberId) {
        Member m = this.findMember(memberId);캐시 통째로 무시
        return MemberSummary.from(m);
    }

    @Cacheable(cacheNames = "members", key = "#memberId")
    public Member findMember(Long memberId) { ... }
}
고침 별도 빈으로 분리 — 반드시 프록시를 통과
@Service
public class MemberService {
    private final MemberQueryService query; // 다른 빈

    public MemberSummary summarize(Long memberId) {
        Member m = query.findMember(memberId); // 프록시 경유
        return MemberSummary.from(m);
    }
}

@Service
public class MemberQueryService {
    @Cacheable(cacheNames = "members", key = "#memberId")
    public Member findMember(Long memberId) { ... }
}
면접에서의 답변 전략 — 원리로 묶어라 네 가지 해법(별도 빈 분리 · 자기 자신 주입 · AopContext.currentProxy() · AspectJ)의 본론은 11-transactional-self-invocation.md에 있다. 여기서는 "프록시 기반 애너테이션은 전부 같은 제약을 공유한다"고 원리로 묶어 답하고 그 문서의 내용으로 이어 가면 된다. 정석은 캐시 대상 메서드를 별도 빈으로 분리하는 것이고, 그 이유는 "반드시 프록시를 통해 호출되게 만드는 유일하게 깔끔한 방법"이기 때문이다.

4. 함정 ② 캐시 키 — 사고가 가장 많이 나는 대목

4-1. 기본 키 생성기의 실제 규칙, 그리고 규칙에 없는 것

key를 지정하지 않으면 SimpleKeyGenerator가 키를 만든다. 규칙은 딱 세 줄이다.

SimpleKeyGenerator의 세 규칙 — 정확히 외워 둘 값이 있다
파라미터 개수만들어지는 키
0개SimpleKey.EMPTY — 모든 무인자 호출이 같은 키를 공유한다
1개그 파라미터 값 자체 (단, null이거나 배열이면 아래 규칙으로 넘어간다)
2개 이상전부 묶은 SimpleKey 객체 (내부적으로 파라미터 배열의 equals/hashCode로 비교한다)

가장 중요한 사실은 표에 없다

기본 키에는 클래스 이름도, 메서드 이름도 들어가지 않는다. 파라미터 값만으로 키가 만들어진다.

캐시 안에서 엔트리를 구분하는 것은 (캐시 이름, 키) 두 값뿐이므로, 같은 캐시 이름을 쓰는 서로 다른 두 메서드가 같은 값의 파라미터를 받으면 완전히 같은 자리에 쓰고 읽는다.

4-2. 같은 칸을 공유하는 사고 세 가지 모양

모양 ① 같은 클래스, 이름만 다른 두 메서드

@Cacheable(cacheNames = "products")
public Product findProduct(Long productId) { ... }

@Cacheable(cacheNames = "products")
public ProductStock findStock(Long productId) { ... }
  • findProduct(1L) 먼저 → 캐시["products"][1L] = Product
  • findStock(1L) 나중 → 히트 → Product를 반환 → 호출부에서 ClassCastException
  • 반환 타입이 같으면(findPriceBy… / findCostBy…가 둘 다 Money) 예외조차 안 난다.

모양 ② 다른 클래스, 같은 이름 메서드 보안

// MemberService
@Cacheable(cacheNames = "members")

  • 관리자가 먼저 조회하면 마스킹이 풀린 값이 캐시에 올라가고, 그다음 일반 사용자 조회가 그 값을 받아 간다.
  • 성능 버그가 아니라 개인정보 유출이다.
모양 ③ 박싱만 다른 오버로드 — 가장 눈에 안 띄는 형태 오버로드된 두 메서드는 파라미터 목록이 달라야 하므로 대개 키도 달라지지만, 박싱만 다른 오버로드는 값이 같아진다.

// 두 메서드가 완전히 같은 캐시 엔트리를 공유한다.

캐시 이름은 "이 캐시에 무엇이 들어 있는가"를 말해야 하고, 그 이름 아래에는 한 종류만 들어가야 한다

4-3. 파라미터가 객체면 equals/hashCode가 없을 때 히트율이 0이 된다

문제 조건 객체에 equals/hashCode가 없다
@Cacheable(cacheNames = "search")
public List<Member> search(MemberSearchCondition condition) { ... }

public class MemberSearchCondition {   // equals/hashCode 없음
    private final String city;
    private final int minAge;
}
고침 record는 값 기반 equals/hashCode를 자동 생성
public record MemberSearchCondition(String city, int minAge) {}

// 내용이 같으면 키도 같아진다 → 비로소 캐시가 일을 시작한다
// (record를 못 쓰면 equals/hashCode를 직접 구현한다)

Object의 기본 equals는 참조 동일성이다. 요청마다 새로 만들어지는 조건 객체는 내용이 완전히 같아도 서로 다른 객체이므로 키가 매번 달라진다.

무서운 것은 "동작이 정상처럼 보인다"는 점이다 1번 요청: new MemberSearchCondition("서울", 20) → 키 A → 미스 → 저장
2번 요청: new MemberSearchCondition("서울", 20) → 키 B → 미스 → 저장  ← 내용은 같은데 다른 키

결과는 다 맞고 응답도 나온다. 다만 캐시가 아무 일도 안 하고 있을 뿐이다. 히트율 0%에 더해 사실상 같은 값이 무한히 쌓여 메모리 누수처럼 보이기까지 한다.

여기서 얻을 교훈 — 캐시는 "붙였는지"가 아니라 "히트율"로 확인한다

CacheMetricsRegistrar나 Actuator의 캐시 지표로 히트/미스 비율을 대시보드에 올려 두지 않으면 이런 종류의 실패는 발견 자체가 되지 않는다. 자기 호출(3절)도, equals 누락(4-3)도 증상이 "아무 일도 안 일어남"이라 지표 없이는 보이지 않는다.

@Cacheable(cacheNames = "orders", key = "#p0")                                // 인덱스로 (이름 정보가 없을 때)
@Cacheable(cacheNames = "orders", key = "#req.userId + ':' + #req.status")    // 객체 속성 조합
@Cacheable(cacheNames = "orders", key = "#root.methodName + ':' + #userId")   // 메서드 이름을 직접 넣기

구분자가 값 안에 나타날 수 있는가 #a + ':' + #b에서 a="1:2", b="3"과 a="1", b="2:3"은 둘 다 "1:2:3"이 되어 충돌한다. 값에 구분자가 섞일 수 있는 도메인이라면 구분자를 값에 안 나오는 문자로 바꾸거나 길이를 함께 넣는다.

5. condition과 unless — 평가 시점이 정반대다

주니어가 거의 구분하지 못하는 지점이고, 그래서 면접에서 잘 물어보는 지점이다. 둘 다 "조건부 캐싱"이지만 언제 평가되는지가 다르고, 그 차이에서 나머지가 전부 따라 나온다.

public Member findMemberOrNull(Long memberId) { ... }

6. 함정 ③ null 캐싱 — "없음"을 기억할 것인가

스프링 캐시 추상화의 기본은 null도 캐시 가능이다. 구현체별로 조금씩 다르다.

Redis
null을 그대로 직렬화할 수 없어 NullValue라는 마커 객체로 바꿔 저장한다(allowNullValues 기본값 true).
Caffeine
null을 허용한다.
allowNullValues = false
null 저장 시 예외가 난다.

문제는 "null을 캐시하는 게 맞느냐"인데, 양쪽 모두 대가가 있다. 어느 쪽이 정답이 아니라 트레이드오프라는 것을 아는지가 이 질문의 핵심이다.

선택얻는 것잃는 것
null을 캐시함없는 키 조회가 DB에 안 간다 (관통 차단)"없음"이 TTL 동안 고정 — 새로 생긴 데이터가 안 보인다
null을 캐시 안 함새 데이터가 즉시 보인다없는 키 조회가 매번 DB 관통 — 공격에 취약
한 층 더 — 블룸 필터 아예 존재할 수 없는 키를 DB에 가기 전에 걸러 내는 방법이다. 블룸 필터는 "확실히 없음" 또는 "아마 있음"만 답하는 확률적 자료구조라서, "확실히 없음"으로 판정된 요청은 캐시도 DB도 건드리지 않고 즉시 반환할 수 있다. 캐싱 쪽의 본론은 05-redis-caching/06-cache-stampede.md와 05-redis-caching/05-look-aside-cache-aside-pattern.md에 있다.

면접 답변 형태 — 판단 기준을 한 줄로

"데이터가 새로 생기는 빈도 vs 없는 키를 조회하는 빈도"라는 요구사항으로 고르는 문제이고, 대개는 짧은 TTL의 null 캐싱이 두 위험을 모두 줄인다

7. 동시에 미스가 몰리면 원본이 여러 번 실행된다 — sync = true

1-2의 의사코드를 다시 보면 "조회 → 미스 → 실행 → 저장" 사이에 아무 잠금이 없다. 그래서 같은 키에 대한 미스가 동시에 몰리면 전부가 각자 메서드를 실행한다. 이것이 캐시 스탬피드(cache stampede)다 — 평소에는 1초에 한 번도 안 나가던 무거운 쿼리가 만료 순간에 수백 번 동시에 나가 DB를 무너뜨린다.

@Cacheable(cacheNames = "orgChart", key = "#companyId", sync = true)
public OrgChart loadOrgChart(Long companyId) { ... }   // 수 초짜리 무거운 연산

스탬피드 완화책을 계층별로 — 이 순서로 답한다

① sync = true
같은 JVM 안에서 한 스레드만 실행. 단일 인스턴스면 이걸로 충분한 경우가 많다.
② 분산 락
"전체에서 딱 한 번만 재계산"이 필요하면 Redis 분산 락. 다만 4번이 견딜 만하면 복잡도를 지불하지 않는 것도 정당한 판단이다.
③ TTL 지터
같은 시각에 대량 적재된 캐시가 같은 시각에 일제히 만료되는 것 자체를 막기 위해 TTL에 무작위 오차를 섞는다.
④ refresh-ahead
만료 전에 백그라운드로 미리 갱신한다(Caffeine refreshAfterWrite). 값이 아예 없어지는 구간을 만들지 않는다.

본론은 05-redis-caching/06-cache-stampede.md, 분산 락의 함정은 05-redis-caching/16-distributed-lock-pitfalls-redlock.md.

8. 함정 ④ TTL은 애너테이션에 없다 시니어 변별

@Cacheable에는 TTL(만료 시간) 속성이 존재하지 않는다

애너테이션에서 ttl = ...을 찾으면 못 찾는다 — 빠뜨린 것이 아니라 의도된 설계다

"CacheManager 설정에서 합니다"까지는 절반이고, 왜 거기로 내려갔는지를 말해야 이 질문의 의도에 답한 것이 된다.

이유는 1-3에서 미리 본 계층 구조에 있다. 스프링 캐시 추상화가 정의한 Cache 인터페이스에는 get·put·evict 세 동작밖에 없다. 왜 그것만인가 — 모든 캐시 구현체가 공통으로 가진 개념이 그것뿐이기 때문이다. 만료는 사정이 완전히 다르다. 구현체마다 개념 자체가 갈린다.

공통 분모가 없는 것을 억지로 추상화하면 구현체마다 의미가 달라지는 애너테이션이 된다
구현체만료 · 퇴출 개념
Redis키 단위 TTL. 만료 시각이 되면 서버가 지운다
CaffeineexpireAfterWrite(쓴 뒤 경과), expireAfterAccess(마지막 접근 뒤 경과), maximumSize(크기 초과 시 퇴출), refreshAfterWrite(만료가 아니라 갱신)

추상화가 답할 수 없는 질문들 — 그래서 빠졌다 maximumSize로 밀려나는 것은 "만료"인가 아닌가?  /  refreshAfterWrite는 TTL인가 아닌가?  /  ConcurrentMapCache에 ttl = 10m을 주면 어떻게 동작해야 하는가?

8-1. Redis — RedisCacheConfiguration.entryTtl()

@Bean
public CacheManager cacheManager(RedisConnectionFactory factory) {
    RedisCacheConfiguration defaults = RedisCacheConfiguration.defaultCacheConfig()
            .entryTtl(Duration.ofMinutes(10));   // 이름을 따로 지정하지 않은 캐시의 기본 TTL

    // 캐시 이름별로 다른 TTL — 실무에서는 거의 필수다.
    // TTL의 근거는 "데이터가 얼마나 자주 바뀌는가"와 "얼마나 낡아도 괜찮은가"다.
    Map<String, RedisCacheConfiguration> perCache = Map.of(
            "members",  defaults.entryTtl(Duration.ofHours(1)),    // 잘 안 변한다 → 길게
            "orgChart", defaults.entryTtl(Duration.ofMinutes(5)),  // 자주 변한다 → 짧게
            "notFound", defaults.entryTtl(Duration.ofSeconds(30))  // 6절의 null 캐싱용 → 아주 짧게
    );

    return RedisCacheManager.builder(factory)
            .cacheDefaults(defaults)
            .withInitialCacheConfigurations(perCache)
            .build();
}

부트를 쓰면 전역 기본값만은 프로퍼티로도 줄 수 있다. 다만 캐시 이름별 TTL은 프로퍼티로 표현할 수 없으므로 위의 CacheManager 빈이 필요하다.

spring:
  cache:
    type: redis
    redis:
      time-to-live: 10m
      cache-null-values: true   # 6절의 allowNullValues

}
// 또는 yml 한 줄로: spring.cache.caffeine.spec=expireAfterWrite=10m,maximumSize=10000

// 캐시 이름별로 다른 TTL을 주려면 이름마다 별도 빌더로 등록한다
manager.registerCustomCache("orgChart",
        Caffeine.newBuilder()
                .expireAfterWrite(Duration.ofMinutes(5))
                .maximumSize(1_000)
                .build());
로컬 캐시에는 maximumSize를 반드시 준다 Redis는 별도 프로세스라 메모리가 넘치면 Redis가 죽지만, Caffeine은 우리 애플리케이션의 힙을 쓴다. 상한이 없으면 캐시가 커지다가 GC를 압박하고 결국 OutOfMemoryError로 애플리케이션 자체를 죽인다.

8-3. 캐시 이름별 TTL을 정하는 기준

① 이 데이터가 바뀌는 주기는?

그보다 짧게 잡으면 낡은 값을 볼 일이 거의 없다.

② 낡은 값이 보이면 얼마나 곤란한가?

  • 권한 · 가격 → 매우 곤란 → 짧게 + 변경 시 즉시 evict
  • 회원 프로필 → 조금 곤란 → 중간
  • 공지 목록 → 별로 → 길게

관점 한 줄 — TTL은 무효화의 대체재가 아니라 안전망이다

변경 시 @CacheEvict가 1차 방어, TTL은 "무효화를 빠뜨렸을 때 최대 이만큼만 틀리겠다"는 상한선

무효화를 완벽하게 하는 것은 매우 어렵기 때문에 둘을 언제나 함께 둔다. 이 문장을 덧붙이면 "TTL을 감으로 정하지 않는 사람"으로 들린다.

9. 인출 카드 · 꼬리질문 셀프 테스트

9-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

동작을 한 문장으로?
프록시가 키 생성 → 캐시 조회 → 히트면 원본 실행 없이 반환 / 미스면 실행 후 저장하는 read-through.
함정 네 개는?
자 · 키 · 널 · 티 — 자기 호출 · 키 설계 · 널 캐싱 · TTL의 위치.
세 애너테이션의 기준은?
원본 메서드를 실행하는가 하나. 안(Cacheable) · 덮(CachePut) · 지(CacheEvict).
갱신에 @Cacheable을 붙이면?
2차 호출부터 히트 → save()가 아예 안 불린다. 예외 없이 저장이 조용히 사라진다.
기본 키 생성 3규칙은?
0개 → SimpleKey.EMPTY / 1개 → 그 값 자체(null·배열 제외) / 2개 이상 → SimpleKey.
키에 없는 것은?
클래스 이름도 메서드 이름도 없다. 엔트리 좌표는 (캐시 이름, 키) 둘뿐.
같은 칸 사고 3형태는?
① 이름만 다른 두 메서드 ② 클래스만 다른 같은 이름 ③ 박싱만 다른 오버로드(long/Long).
키에 꼭 넣을 것은?
누 · 무 · 관 — 누구의 데이터(테넌트·사용자) · 무엇(도메인 식별자) · 어느 관점(뷰·마스킹·언어).
condition vs unless?
전/후. condition은 참일 때 캐싱·조회+저장 둘 다, unless는 참일 때 캐싱 안 함·저장만.
null 캐싱은?
관통 ↔ 반영 지연 트레이드오프. 절충은 짧은 TTL의 null 캐싱, 한 층 더는 블룸 필터.
TTL이 애너테이션에 없는 이유?
Cache에 get·put·evict뿐 — 만료는 구현체마다 개념이 달라 공통 분모가 아니었다.
분업 한 줄은?
캐시 이름은 코드가, 물리적 성질(저장소·TTL·크기)은 설정이 정한다.
히트율이 0%라면?
① 자기 호출 ② 파라미터 객체 equals/hashCode 없음 ③ 키에 매번 달라지는 값 ④ TTL 과소 ⑤ condition이 늘 거짓.
sync = true의 한계는?
JVM 범위(4대면 4번) + unless 불가 · 캐시 이름 1개 · 다른 캐시 연산과 겹치기 불가.

9-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

@Cacheable, @CachePut, @CacheEvict는 각각 언제 쓰나요? 필수힌트: 기준을 "원본 메서드를 실행하는가" 하나로 잡고, 마지막에 "이름 때문에 생기는 실수"를 덧붙인다

@Cacheable은 "있으면 안 부른다" — 히트면 메서드를 실행하지 않으므로 읽기 전용 조회에만 쓴다. @CachePut은 "항상 부르고 결과를 덮어쓴다" — 갱신 메서드에서 결과를 캐시에 반영할 때. @CacheEvict는 "지운다" — 삭제, 또는 갱신 후의 정확한 최종 값을 이 메서드가 알지 못할 때.

여기서 반드시 짚어야 할 실수가 있다. 이름 때문에 @Cacheable을 갱신 메서드에 붙이는 경우가 흔하다 — "캐시 가능"이 "캐시에 넣어 준다"로 읽히기 때문이다. 그러면 두 번째 호출부터 캐시 히트가 나서 save()가 아예 실행되지 않고 저장이 조용히 사라진다. 예외도 안 나고 옛 값이 리턴되므로 성공한 것처럼 보인다.

@CachePut과 @CacheEvict 중 고를 때는 "이 메서드가 캐시에 넣을 정확한 값을 알고 있는가"로 판단한다. 확신이 없으면 evict가 안전하다 — 틀린 값을 넣는 것보다 다음 읽기에서 한 번 더 읽는 편이 낫다.

기본 키 생성 규칙을 정확히 설명해 주시겠어요? 시니어 변별힌트: 규칙 세 줄을 말한 뒤, "규칙에 없는 것"으로 넘어가는 것이 진짜 답이다

SimpleKeyGenerator의 규칙은 셋이다. 파라미터가 0개면 SimpleKey.EMPTY, 1개면 그 값 자체(단 null이거나 배열이면 제외), 2개 이상이면 전부 묶은 SimpleKey.

그런데 진짜 답은 규칙에 없는 것이다. 키에는 클래스 이름도 메서드 이름도 들어가지 않는다. 캐시 엔트리를 구분하는 것은 (캐시 이름, 키)뿐이므로, 같은 캐시 이름을 쓰는 두 메서드가 같은 값의 파라미터를 받으면 완전히 같은 자리에 읽고 쓴다.

사고 모양을 세 가지로 들면 좋다. ① 같은 클래스의 이름만 다른 두 메서드(findProduct(1L) / findStock(1L)) — 반환 타입이 다르면 ClassCastException이고, 같으면 예외조차 없이 엉뚱한 값이 나간다. ② 다른 클래스의 같은 이름 메서드 — 관리자용 조회가 캐시를 채우면 일반 사용자가 마스킹 안 된 값을 받아 간다. ③ 박싱만 다른 오버로드(find(long) / find(Long)) — 프록시에 도달할 때 둘 다 Long이라 키가 같아진다.

해법은 두 층이다. 캐시 이름을 "저장하는 데이터의 의미" 단위로 분리해 한 이름 아래 한 종류만 두고, 그래도 겹칠 여지가 있으면 key를 명시하거나 #root.methodName을 키에 포함한다.

멀티테넌트 서비스에서 캐시 키 설계 시 반드시 넣어야 할 것은 무엇인가요? 보안힌트: "테넌트 ID요"는 절반. 이 사고의 성질(코드가 멀쩡해 보이고 테스트로 안 잡힌다)까지 말해야 완성된다

테넌트 식별자(회사 ID 등), 사용자별 데이터라면 사용자 ID다. 빠뜨리면 A사가 채운 캐시를 B사가 받아 가는 타사 데이터 유출 — 성능 버그가 아니라 보안 사고다.

이 사고의 성질까지 말해야 답이 완성된다. 메서드는 companyId를 정확히 받아 DB를 제대로 조회하는데 키에만 그 값이 빠져 있는 형태라서 코드를 봐도 이상해 보이지 않는다. 그리고 테스트로 잡히지 않는다 — 단일 테넌트 테스트는 전부 통과하고, 두 테넌트가 같은 인스턴스에서 같은 대상을 연달아 조회할 때만 재현된다.

그래서 대책은 "키에 꼭 넣읍시다"가 아니라 구조로 강제하는 것이다. 커스텀 KeyGenerator에서 현재 테넌트 컨텍스트를 읽어 모든 키에 자동으로 붙이거나, CacheManager 레벨에서 캐시 이름에 테넌트 prefix를 붙인다. "사람이 기억해서 지키는 규칙"을 "빠뜨릴 자리가 없는 구조"로 바꾸는 것이 시니어의 답이다.

condition과 unless의 차이가 뭔가요? 필수힌트: "평가 시점"에서 출발하면 나머지(참조 가능 변수·영향 범위·의미 반전)가 전부 따라 나온다

평가 시점이 다르고, 거기서 나머지가 전부 따라 나온다.

condition은 메서드 실행 전에 평가된다. 아직 결과가 없으니 파라미터만 볼 수 있고 #result는 못 쓴다. 거짓이면 캐시 조회와 저장을 통째로 건너뛴다.

unless는 메서드 실행 후에 평가된다. 그래서 #result로 결과를 볼 수 있고, 참이면 저장만 거부한다. 조회는 이미 끝난 뒤라 unless로는 캐시 히트를 막을 수 없다.

의미도 뒤집혀 있다. condition은 참일 때 캐싱하고, unless는 참일 때 캐싱하지 않는다. 이름이 각각 "이 조건이면"과 "이 조건이 아닌 한"이라서다.

가산점으로 예외 하나를 덧붙이면 좋다. @CachePut은 항상 메서드를 실행하므로 그 condition은 실행 후에 평가되고 #result를 참조할 수 있다 — "condition은 언제나 실행 전"이라고 외우면 여기서 틀린다.

null을 캐시해야 하나요, 하지 말아야 하나요? 필수힌트: 어느 한쪽을 고르면 반쪽 답이다. 두 실패 시나리오를 각각 그린 뒤 절충안으로 착지한다

둘 다 대가가 있는 트레이드오프라고 답하는 것이 정답 형태다.

unless = "#result == null"로 null을 캐시하지 않으면, 존재하지 않는 키를 반복 조회할 때 매번 캐시를 그냥 통과해 DB를 때린다. 이것이 캐시 관통(cache penetration)이다 — 캐시가 방패 역할을 전혀 못 하고 요청이 관통한다는 뜻이고, 없는 id를 무작위로 던지는 공격에 캐시가 통째로 무력해진다.

반대로 null을 캐시하면 "없음"이 TTL 동안 고정된다. 그 사이에 데이터가 실제로 생겨도 만료 전까지는 계속 "없음"이 나간다. 신규 가입자가 한 시간 동안 404를 받는 문의가 이 모양이다.

실무 절충은 "null도 캐시하되 아주 짧은 TTL을 준다"이다. "없음"을 수십 초만 기억해 관통은 막고 반영 지연은 그 수십 초로 제한한다. null 전용 캐시 이름을 따로 만들어 TTL을 다르게 주는 구성이 자연스럽다. 한 층 더 얹으면 블룸 필터로 존재할 수 없는 키를 캐시·DB에 가기 전에 걸러 내는 방법이 있다. 판단 기준을 한 줄로 말하면 "데이터가 새로 생기는 빈도 vs 없는 키를 조회하는 빈도"다.

TTL은 왜 애너테이션에 없나요? 어디서 설정하나요? 시니어 변별힌트: "CacheManager에서요"는 절반. Cache 인터페이스에 무엇이 있는지부터 말한다

"CacheManager 설정에서 합니다"까지는 절반이고, 왜 거기로 내려갔는지를 말해야 이 질문의 의도에 답한 것이 된다.

스프링 캐시 추상화가 정의한 Cache 인터페이스에는 get·put·evict 세 동작밖에 없다. 모든 캐시 구현체가 공통으로 가진 개념이 그것뿐이기 때문이다. 만료는 그렇지 않다 — Redis는 키 단위 TTL, Caffeine은 expireAfterWrite/expireAfterAccess/maximumSize/refreshAfterWrite, Ehcache는 TTL과 TTI를 따로 두고, ConcurrentMapCache에는 만료 개념이 아예 없다. 공통 분모가 없는 것을 억지로 추상화하면 구현체마다 의미가 달라지는 애너테이션이 된다.

그래서 분업이 이렇게 됐다. 애너테이션은 "어느 이름의 캐시에 넣을지"만 말하고, 그 캐시의 물리적 성질(저장소, TTL, 크기 상한)은 CacheManager 설정이 정한다.

구체적으로는 Redis면 RedisCacheConfiguration.entryTtl(), Caffeine이면 Caffeine.newBuilder().expireAfterWrite(...)다. 여기에 캐시 이름별로 다른 TTL을 주는 법(Redis는 withInitialCacheConfigurations, Caffeine은 registerCustomCache)까지 붙이고, TTL 값의 근거는 "데이터 변경 주기"와 "낡은 값이 보였을 때의 곤란함"이라고 말하면 실무 경험이 드러난다. 마지막으로 TTL은 무효화의 대체재가 아니라 안전망이라는 관점을 덧붙이면 좋다.

캐시가 만료된 순간 같은 키로 요청 1,000개가 동시에 들어오면 어떻게 되나요? 가산점힌트: 이름을 대고, 완화책을 "로컬 → 분산 → 만료 시각 분산 → 만료 전 갱신" 계층으로 답한다

캐시 스탬피드다. 기본 동작은 1,000개 스레드가 전부 미스를 보고 전부 메서드를 실행한다 — 평소 잘 안 나가던 무거운 쿼리가 1,000번 동시에 DB를 때린다. 완화책을 계층별로 답한다.

① sync = true — 같은 JVM 안에서는 한 스레드만 실행하고 나머지는 그 결과를 기다린다. 단일 인스턴스면 이걸로 충분한 경우가 많다. ② 분산 락 — 서버가 4대면 sync = true로도 4번의 동시 실행이 남는다. "전체에서 딱 한 번만 재계산"이 필요하면 Redis 분산 락을 쓴다. 다만 4번이 견딜 만한 숫자라면 분산 락의 복잡도는 지불하지 않는 것도 정당한 판단이다. ③ TTL 지터 — 같은 시각에 대량 적재된 캐시가 일제히 만료되는 것 자체를 막기 위해 TTL에 무작위 오차를 섞는다. ④ refresh-ahead — 만료 전에 백그라운드로 미리 갱신한다(Caffeine refreshAfterWrite).

sync = true의 제약도 함께 말하면 정확한 답이 된다 — unless와 함께 쓸 수 없고, 캐시 이름을 하나만 지정할 수 있으며, 같은 메서드에 다른 캐시 연산을 겹칠 수 없다.

@Cacheable과 @Transactional을 같은 메서드에 쓰면 순서는 어떻게 되나요? 가산점힌트: 둘 다 프록시 어드바이스다 — "누가 바깥인가"의 문제로 바꿔 말한다

둘 다 프록시 어드바이스이므로 프록시 체인에서 누가 바깥인가의 문제다. 기본 순서에서는 캐시 인터셉터가 트랜잭션 인터셉터보다 바깥에 있다.

요청 ─▶ [캐시 인터셉터] ─▶ [트랜잭션 인터셉터] ─▶ 원본 메서드
         히트면 여기서 반환 ✗ (트랜잭션은 시작조차 안 된다)

조회 캐시에서는 이게 오히려 이득이다 — 히트하면 DB 커넥션을 아예 잡지 않는다.

주의할 것은 반대 상황이다. 캐시 저장(put)이 트랜잭션 커밋 전에 일어나므로, 저장 후 트랜잭션이 롤백되면 DB에는 없는 값이 캐시에는 남는 불일치가 생긴다. 대응은 캐시 조작을 커밋 이후로 미루는 것이다 — TransactionAwareCacheManagerProxy로 CacheManager를 감싸면 put/evict가 커밋 후에 반영되고, 더 명시적으로는 @TransactionalEventListener(AFTER_COMMIT)에서 무효화를 실행한다.

서버 2대가 각자 로컬 캐시(Caffeine)를 쓰면 무슨 문제가 생기나요? 가산점힌트: 증상을 "사용자 눈에 어떻게 보이는지"로 먼저 말하면 설득력이 붙는다

인스턴스 간 불일치다. A 서버에서 데이터를 수정하고 @CacheEvict로 무효화해도 그건 A의 로컬 캐시만 지운 것이고, B 서버는 TTL이 다할 때까지 옛 값을 계속 서빙한다.

사용자 눈에는 "수정했는데 새로고침하면 값이 왔다 갔다 한다"로 보인다 — 로드밸런서가 어느 서버로 보내느냐에 따라 다른 답이 나오기 때문이다. 재현이 안 되는 문의의 전형적 모양이다.

해법을 네 가지로 답한다. ① 분산 캐시(Redis)로 전환 — 모두가 같은 캐시를 본다. 대신 매 조회에 네트워크 왕복이 붙는다. ② 무효화 브로드캐스트 — 로컬 캐시는 유지하되 변경 이벤트를 Redis pub/sub 등으로 전 인스턴스에 뿌려 각자 evict하게 한다. ③ 2단 캐시(near cache) — 로컬(빠름) + Redis(일관성)를 겹치고 무효화는 pub/sub으로. ④ 짧은 TTL로 감수 — "이 데이터가 몇 초의 불일치를 견딜 수 있나"가 판단 기준이고, 견딜 수 있다면 가장 단순한 답이다.

@CacheEvict만으로 무효화가 부족해지는 경우는 언제인가요? 시니어 변별힌트: "@CacheEvict가 잡을 수 있는 변경의 범위"를 먼저 한정한다

@CacheEvict는 캐시를 쓰는 그 애플리케이션의, 그 메서드를 거친 변경만 잡는다. 그래서 두 경우에 무너진다.

① 다른 서비스·배치·DBA가 DB를 직접 바꾸는 경우. 그 경로는 @CacheEvict를 지나가지 않으므로 캐시는 낡은 채로 남는다. ② 변경 메서드가 여러 곳이라 evict를 빠뜨리는 경우. 새 갱신 경로를 추가하면서 evict를 안 붙이면 조용히 낡은 값이 남는다.

해법은 무효화를 애너테이션이 아니라 이벤트 기반으로 옮기는 것이다. 데이터 변경 시 도메인 이벤트나 메시지(Kafka, Redis pub/sub)를 발행하고 캐시 보유자들이 구독해 evict한다. 더 근본적으로는 CDC(Debezium 등)로 DB 변경 자체를 구독하면 "어떤 경로로 바뀌었든" 무효화를 걸 수 있다.

그럼에도 완벽한 무효화는 어렵기 때문에 TTL을 최후의 안전망으로 항상 함께 둔다. "캐시 무효화는 컴퓨터 과학의 두 가지 어려운 문제 중 하나"라는 농담이 괜히 있는 게 아니다.

같은 클래스 안에서 @Cacheable 메서드를 호출하면 어떻게 되나요? 함정힌트: @Transactional 자기 호출과 "완전히 같은 원리"라고 묶어서 답한다

적용되지 않는다. 캐시 로직은 프록시에 있는데 this.method()는 프록시를 거치지 않고 원본 객체를 직접 부르기 때문이다. @Transactional 자기 호출 문제와 완전히 같은 원리이고, CGLIB 프록시가 private·final 메서드를 못 가로채는 것도 같은 뿌리에서 나온다.

가장 무서운 점은 에러도 경고도 없이 조용히 캐시 없이 실행된다는 것이다. 히트율 모니터링이 없으면 "캐시를 붙였는데 DB 부하가 안 줄어든다"는 증상으로 한참 뒤에 발견된다. 해결은 캐시 대상 메서드를 별도 빈으로 분리해 반드시 프록시를 통해 호출되게 하는 것이 정석이고, 자세한 대안 비교는 11-transactional-self-invocation.md에 있다.

캐시를 붙였는데 히트율이 0%에 가깝습니다. 원인 후보를 순서대로 대보세요. 시니어 변별힌트: 이 문서에 흩어진 "조용한 실패" 다섯 개를 한 줄로 꿰면 그대로 체크리스트가 된다

① 자기 호출 — 같은 클래스 안 this. 호출이면 캐시 로직이 통째로 실행되지 않는다(3절). 로그도 예외도 없으니 가장 먼저 의심한다.

② 파라미터 객체에 equals/hashCode가 없다 — 내용이 같아도 매 요청 다른 키가 만들어져 미스만 쌓인다(4-3). 캐시 엔트리 수가 요청 수만큼 늘어나는지 보면 바로 판별된다.

③ 키에 매 호출 달라지는 값이 섞였다 — 타임스탬프, 요청 ID, LocalDateTime.now()가 들어간 DTO를 통째로 키로 쓰는 경우다. ②와 증상이 같지만 원인이 다르다.

④ TTL이 과도하게 짧거나 maximumSize가 작다 — 넣자마자 만료되거나 곧바로 밀려난다. 이건 코드가 아니라 CacheManager 설정을 봐야 보인다(8절).

⑤ condition이 사실상 늘 거짓이거나, ⑥ 프록시가 애초에 안 씌워졌다(빈이 아니거나 final/private 메서드). 진단 순서의 원칙은 "프록시를 탔는가 → 키가 안정적인가 → 엔트리가 살아 있는가" 세 단계이고, 그 전제로 히트/미스 지표를 먼저 노출해 두는 것이 답의 출발점이다.

캐시에 넣는 객체는 어떤 조건을 갖춰야 하나요? 가산점힌트: 로컬 캐시와 원격 캐시에서 "돌려받는 객체의 정체"가 다르다

저장소에 따라 요구 조건이 갈린다. Redis 같은 원격 캐시는 값을 직렬화해서 보내고 역직렬화해서 돌려주므로, 직렬화 가능한 형태여야 하고 역직렬화 시 타입을 복원할 수 있어야 한다. 그래서 캐시 전용 DTO를 두고 직렬화 방식을 명시적으로 설정하는 편이 안전하다.

로컬 캐시(Caffeine)는 반대의 함정이 있다. 직렬화가 없는 대신 같은 힙의 같은 객체 참조를 그대로 여러 호출자에게 나눠 준다. 그래서 돌려받은 객체를 호출부에서 수정하면 캐시 안의 값도 함께 바뀐다. 대응은 불변 객체(record)로 만들거나 방어적 복사다.

공통으로 피할 것은 JPA 엔티티를 그대로 캐싱하는 것이다. 영속성 컨텍스트 밖으로 나간 엔티티가 여러 요청에 공유되고, 지연 로딩 필드에 접근하는 순간 세션이 없어 실패할 수 있다. 캐시에는 필요한 값만 담은 불변 DTO를 넣는다가 실무 원칙이다.

@Cacheable 메서드가 예외를 던지면 캐시에는 무엇이 저장되나요? 함정힌트: 1-2의 의사코드에서 put이 어느 줄에 있는지 보면 답이 나온다

아무것도 저장되지 않고 예외가 그대로 호출자에게 전파된다. 1-2의 의사코드에서 cache.put은 메서드가 정상적으로 값을 반환한 뒤에 실행되므로, 예외로 빠져나가면 put 줄에 도달하지 못한다. 즉 "실패는 캐시되지 않는다"가 기본 동작이다.

여기서 파생되는 함정이 두 개 있다. ① 실패가 캐시되지 않는다는 것은 곧 "실패하는 호출은 매번 원본까지 간다"는 뜻이다. 원본이 계속 실패하는 상황이라면 캐시가 부하를 전혀 막아 주지 못하므로, 이때 필요한 것은 캐시가 아니라 서킷 브레이커다.

② @CacheEvict는 방향이 반대다. 기본값 beforeInvocation = false에서는 메서드가 예외를 던지면 삭제 자체가 일어나지 않아 캐시에 낡은 값이 그대로 남는다(2-2). 이 상태가 더 위험한 도메인이라면 beforeInvocation = true로 뒤집는다.

@CacheEvict(allEntries = true)를 자주 호출하면 무슨 문제가 있나요?힌트: 지운 다음 순간 무슨 일이 벌어지는지 — 7절과 연결된다

스스로 스탬피드를 만든다. 캐시 이름 아래 전체 엔트리가 한꺼번에 사라지므로, 그 직후 들어오는 요청이 전부 미스가 되어 원본으로 몰린다. 7절에서 본 "만료 순간 1,000개 요청"을 변경이 일어날 때마다 인위적으로 재현하는 셈이다. 변경이 잦은 도메인에서 allEntries = true를 쓰면 캐시 히트율이 구조적으로 낮게 유지된다.

비용도 있다. 로컬 캐시는 맵을 비우면 끝이지만, Redis에서는 그 캐시 이름의 prefix에 해당하는 키들을 찾아서 지워야 하므로 엔트리가 많을수록 부담이 커진다.

그래서 가능하면 key를 지정한 단건 evict가 기본이고, allEntries는 "무엇이 바뀌었는지 특정할 수 없는 재구축"에만 쓴다. 굳이 써야 한다면 그 캐시 이름을 잘게 쪼개 영향 범위를 줄이거나, evict 대신 @CachePut으로 갱신해 빈 구간 자체를 만들지 않는 방법을 검토한다.

한 줄 요약
@Cacheable은 프록시가 메서드 앞에서 키로 캐시를 조회해 히트면 원본 실행을 건너뛰고 미스일 때만 실행 결과를 저장하는 read-through 추상화이고 — 그래서 "히트면 메서드가 안 돌아간다"는 성질이 갱신 메서드에 @Cacheable을 붙이는 순간 저장이 조용히 사라지는 사고가 되며(갱신은 @CachePut, 확신 없으면 @CacheEvict), 기본 키 생성기가 클래스도 메서드도 키에 넣지 않고 파라미터 값만 쓴다는 사실이 같은 캐시 이름을 공유하는 두 메서드의 값 뒤바뀜과 테넌트 식별자 누락에 의한 타사 데이터 유출로 이어지고(사람의 기억 대신 커스텀 KeyGenerator로 구조가 강제하게 만든다), null 캐싱은 캐시 관통과 반영 지연 사이의 트레이드오프라 짧은 TTL로 절충하며, TTL이 애너테이션에 없는 것은 만료의 의미가 구현체마다 달라 추상화 대상에서 빠졌기 때문이므로 CacheManager 설정에서 캐시 이름별로 준다 — 이 네 가지가 "추상화의 경계가 어디까지인가"를 아는 답변의 전부다.
