Actuator 운영 엔드포인트와 외부 노출 보안
관측 도구가 공격 표면이 되지 않게

면접 질문: "Actuator에서 운영에 실제로 활용하는 엔드포인트는? 외부 노출 시 보안 주의점은?"

핵심 관전 포인트 — Actuator는 앱이 자기 내부 상태를 HTTP로 알려주는 스프링 부트의 관측·관리 창구다. 운영에서 실제로 손이 가는 것은 넷이다 — health(LB 헬스체크와 k8s probe의 판정 근거), metrics/prometheus(커넥션 풀·톰캣 스레드·JVM 지표의 원천), loggers(재기동 없이 로그 레벨을 바꾸는 유일한 수단), threaddump/heapdump(SSH 없이 뜨는 진단 덤프). 문제는 같은 창구가 공격자에게도 열린다는 것이다. /env가 열리면 설정의 키 이름과 프로퍼티 소스 구조가 통째로 드러나고, /heapdump는 GET 한 번에 그 순간 메모리 전체 — 세션 토큰, 복호화된 시크릿, 처리 중이던 개인정보 — 를 수백 MB 파일로 내려준다. 부트 3.x는 기본 노출이 health 하나뿐이고 /env·/configprops의 값은 전부 마스킹되므로 기본값 자체는 안전한데, 사고는 개발 편의로 켜 둔 exposure.include=*가 운영에 그대로 나가면서 난다. 그래서 방어는 3중이다 — 필요한 것만 여는 최소 노출, management.server.port로 관리 포트를 분리해 방화벽으로 내부망만 허용, 그리고 인증. 여기에 함정이 셋 붙는다: 포트를 분리하면 관리 포트가 별도 자식 컨텍스트에서 떠서 메인 컨텍스트의 시큐리티 필터 체인이 자동 적용되지 않고, 내가 SecurityFilterChain을 하나라도 정의하는 순간 부트의 기본 보안 자동 설정이 물러나며, loggers는 POST로 상태를 바꾸는 쓰기 엔드포인트라 읽기 전용과 위험도가 다르다.
  • 1
    운영에서 실제로 쓰는 것은 넷이다 — health는 모니터링이 아니라 트래픽을 보낼지 말지를 정하는 라우팅 제어 장치, prometheus는 커넥션 풀·톰캣 스레드·GC 지표의 원천, loggers는 재기동 없이 로그 레벨을 바꾸는 유일한 수단, threaddump/heapdump는 SSH 없이 뜨는 진단 덤프다.
  • 2
    같은 창구가 공격자에게도 열린다 — /env는 부트 3.x에서 값이 전부 마스킹돼도 프로퍼티 이름과 소스 구조라는 정찰 정보를 흘리고, /heapdump는 마스킹이라는 개념 자체가 없어 GET 한 번에 세션 토큰·복호화된 시크릿·개인정보를 통째로 내주며, /loggers는 POST로 앱 동작까지 바꾼다. 부트 3.x 기본 노출은 health 하나이므로, 사고는 대부분 개발 편의로 넣은 include: "*"가 운영에 나가서 난다.
  • 3
    방어는 계층이 다른 세 겹이고, 함정 둘까지 말해야 완성이다 — ① 최소 노출(이름으로 열거) ② 관리 포트 분리 + 망 제한 ③ 인증. 그런데 포트를 분리하면 관리 포트가 자식 컨텍스트라 시큐리티 필터가 따라오지 않고, 내 SecurityFilterChain을 정의하면 부트의 기본 보호가 물러난다. 그래서 인증 없이 curl로 찔러 401이 나오는지 확인하는 것까지가 답이다.

0. 질문 + 출제 의도

질문: "Actuator에서 운영에 실제로 활용하는 엔드포인트는? 외부 노출 시 보안 주의점은?"

출제 의도: 헬스체크·메트릭·스레드덤프를 운영의 표준 도구로 쓰고 있는지, 동시에 /heapdump·/env 무방비 노출이 곧 정보 유출 사고임을 아는지 확인한다. 편의 기능의 보안 면적을 함께 보는 습관이 있는지를 본다.

이 페이지가 겨냥하는 약점 세 가지 ① 엔드포인트 이름만 나열하는 것 → 2·3절에서 각각이 어떤 운영 상황을 푸는 도구인지(트래픽 라우팅 판정 / 고갈 원인 특정 / 재현 상태를 죽이지 않는 디버깅)로 바꿔 세운다.
② "마스킹되니 괜찮다"에서 멈추는 것 → 5·6절에서 부트 2.x/3.x를 갈라 마스킹이 안전망이지 방어선이 아님을 보이고, /heapdump에는 마스킹이라는 단계 자체가 없다는 결정타를 붙인다.
③ "시큐리티 걸었으니 안전하다"는 착각 → 8절의 두 함정(관리 포트 = 자식 컨텍스트, 내 체인 정의 시 기본 보호 후퇴)을 도식으로 못 박고, curl로 401 확인이라는 검증 습관까지 붙인다.
한 문장 비유 — 공장 관제실, 그리고 셔터가 내려진 창구 관제실: Actuator는 공장 벽에 붙은 계기판과 조작 레버다. health는 "이 라인에 물량을 넣어도 되는가"를 알리는 신호등, metrics는 계기판, loggers는 보기만 하는 게 아니라 돌릴 수 있는 레버, heapdump는 공장 안을 통째로 사진 찍어 가져가는 것이다.  /  셔터: 기계는 전부 켜져 있고(활성화) 창구 셔터만 하나 열려 있는 상태(노출)가 부트의 기본값이다. include에 이름을 한 줄 추가하는 것은 셔터를 올리는 일이고, 기계는 이미 돌고 있으므로 올리는 즉시 동작한다.

1. 전제 — Actuator가 무엇이고, 스위치가 왜 둘인가

Actuator(액추에이터)는 "구동 장치"라는 뜻으로, 앱이 자기 내부 상태를 밖에서 들여다보고 일부는 조작까지 할 수 있게 열어주는 스프링 부트의 부가 모듈이다. 의존성 하나(spring-boot-starter-actuator)를 넣으면 /actuator/** 경로에 미리 만들어진 관리용 HTTP 엔드포인트들이 붙는다.

여기서 두 가지를 구분해야 뒤의 보안 이야기가 정확해진다. 이 구분을 모르면 "왜 /actuator/env가 404가 나지"에서 헤매고, 반대로 include: "*"가 왜 위험한지도 체감하지 못한다.

활성화 (enabled)
그 엔드포인트가 존재하는가
대부분 기본 활성이고, shutdown 하나만 기본 비활성이다.
노출 (exposure)
존재하는 것을 HTTP/JMX로 내보이는가
부트 3.x 기준 HTTP와 JMX 양쪽 모두 기본값은 health 하나뿐이다.
기본 상태를 한 문장으로: "기능은 다 켜져 있는데 창구만 하나 열려 있다"

2. 운영에서 실제로 손이 가는 엔드포인트

엔드포인트는 수십 개지만, 운영에서 반복적으로 손이 가는 것은 몇 개 되지 않는다. 이름을 나열하는 대신 각각이 어떤 상황을 푸는 도구인지로 외우는 편이 면접에서도 실무에서도 낫다.

2-1. health — 모니터링이 아니라 라우팅 제어 장치다

/actuator/health는 LB의 헬스체크와 쿠버네티스 probe가 찔러보는 대상이다. 여기서 나오는 UP/DOWN 하나로 이 인스턴스에 트래픽을 보낼지 말지가 결정된다.

인식 전환 — "모니터링용"이 아니다 이 엔드포인트는 지표를 보여주는 창이 아니라 트래픽 스위치다. 무중단 배포에서 "트래픽 차단 신호"를 보내는 방법 중 하나가 바로 이 응답을 DOWN으로 바꾸는 것이다(28-graceful-shutdown-zero-downtime-deploy.md).

부트는 이 하나의 엔드포인트를 목적별로 쪼갤 수 있게 health group 기능을 제공한다. /actuator/health/liveness(프로세스가 살아 있는가)와 /actuator/health/readiness(지금 트래픽을 받을 수 있는가)가 그것이다. 둘의 역할 차이와 "DB 체크를 어디에 넣을 것인가"는 별도 문서에서 다룬다(15-container-infra/liveness-readiness-probe-db-check.md). 이 페이지에서는 그 group을 잘 나눠 놔도 show-details는 별개의 축이라는 점만 9절에서 짚는다.

2-2. metrics / prometheus — 판단의 근거가 되는 숫자

/actuator/prometheus는 Prometheus가 주기적으로 긁어가는 지표 노출 창구다. 실제로 장애 때 보는 것은 이런 값들이다.

hikaricp.connections.active
지금 사용 중인 DB 커넥션 수
hikaricp.connections.pending
커넥션을 못 얻어 기다리고 있는 요청 수 — 고갈의 직접 신호
tomcat.threads.busy
요청을 처리 중인 톰캣 스레드 수
jvm.memory.used · jvm.gc.pause
힙 사용량과 GC 정지 시간

이 숫자들이 없으면 풀 크기 산정이 감으로 떨어지고, 고갈 장애가 났을 때 "무엇이 고갈됐는지"조차 특정할 수 없다. 풀 산정 근거는 25-thread-pool-connection-pool-sizing.md, 고갈 진단은 26-hikaricp-connection-pool-exhaustion.md에 있다.

실전 포인트 — "풀 고갈인가, 스레드 고갈인가"를 가르는 두 계열

풀 = DB 커넥션 풀
hikaricp.connections.active / ...pending
관용적으로 "풀 지표"라 하면 이쪽을 먼저 뜻한다
스레드 = 톰캣 · JVM
tomcat.threads.busy / jvm.threads.live
톰캣 스레드도 구조상 풀이지만 부르는 이름이 다르다

장애 때 이 두 계열을 갈라 보는 것이 원인 특정의 첫 단계다 — 둘 다 포화면 DB 대기가 스레드를 잡아먹은 것인지, 스레드만 포화면 느린 외부 호출 쪽인지로 갈린다.

2-3. threaddump / heapdump — SSH 없이 뜨는 진단 덤프

원래 이 둘은 서버에 직접 붙어서 JDK 도구로 뜨는 것이다. jstack <pid>(스레드 덤프), jmap -dump:...(힙 덤프). Actuator는 같은 일을 HTTP로 대신해 준다.

GET /actuator/threaddump

  • 그 순간 모든 스레드의 상태와 스택을 JSON으로 반환
  • 커넥션 풀 고갈·데드락 진단의 1차 자료
  • 어느 스레드가 무엇을 기다리고 있는지가 그대로 보인다

GET /actuator/heapdump

  • 힙 전체를 hprof 파일로 다운로드
  • 메모리 릭을 MAT 같은 도구로 파헤칠 때
  • 편리한 만큼 노출 사고의 최우선 경계 대상 (6절)
경계 하나 — 이 둘은 앱이 이미 떠 있어야 쓸 수 있다 기동이 안 끝나 웹 서버가 아직 안 뜬 상태에서는 HTTP 엔드포인트 자체가 없다. 그때는 jstack·jmap으로 직접 떠야 한다. 기동 지연 진단에서 이 구분이 중요하다(32-slow-application-startup-diagnosis.md). 같은 이유로, 운영에서 이 둘을 평시에 닫아둬도 진단 수단이 사라지는 것은 아니다 — JDK 도구라는 대체 경로가 남는다.

/actuator/startup은 기동 단계별 소요 시간을 JSON으로 준다. 어느 빈이 몇 ms를 먹었는지 정렬해 볼 수 있어 기동 지연 진단의 정밀 도구다. 다만 BufferingApplicationStartup을 코드에서 미리 설정해 둬야 동작한다. /actuator/info는 빌드 버전과 git 커밋 해시를 보여준다 — "지금 떠 있는 게 정말 방금 배포한 그 버전인가"를 확인하는 용도다. 부트 3.x부터는 이것도 기본 노출에서 빠졌으므로 쓰려면 명시적으로 열어야 한다.

3. loggers — 재기동 없이 로그 레벨을 바꾸는 유일한 수단

여기가 이 문서에서 가장 중요한 하나다. 읽기 전용이 아니라 쓰기 가능한 엔드포인트이기 때문이다.

3-1. 이게 없으면 생기는 딜레마

운영 조회 → 변경 → 원복, 세 줄이 전부다
# 현재 레벨 조회 (GET)
curl http://localhost:9292/actuator/loggers/com.daou.security

# security 패키지만 DEBUG로 — 재기동 없이 즉시 반영 (POST)
curl -X POST http://localhost:9292/actuator/loggers/com.daou.security \
  -H 'Content-Type: application/json' -d '{"configuredLevel": "DEBUG"}'여기서 상태가 바뀐다

# 조사가 끝나면 원복. configuredLevel을 null로 보내면 설정 파일 값으로 돌아간다.
curl -X POST http://localhost:9292/actuator/loggers/com.daou.security \
  -H 'Content-Type: application/json' -d '{"configuredLevel": null}'
1
간헐적 오류가 관측된다 → 원인 패키지를 좁힌다. 루트 로거를 올리면 디스크가 찬다 — 범위를 좁게 잡는 것이 첫 규율이다.
2
그 패키지만 DEBUG로 POST한다 → 재현될 때까지 로그를 확보한다.
3
configuredLevel: null로 원복한다. 원복을 잊으면 그 자체가 디스크·비용 사고가 된다.

3-2. POST라는 사실이 위험도를 바꾼다 함정

이 엔드포인트는 앱의 상태를 실제로 바꾼다. 그래서 노출됐을 때의 위험이 읽기 전용 엔드포인트와 성격이 다르다. 공격자 관점에서 보면 이렇다.

① 서비스 거부 (DoS)

  • 루트 로거를 TRACE로 올리면 초당 수만 줄이 쏟아진다
  • 디스크가 차고 I/O가 포화되며, 로그 수집 파이프라인까지 함께 무너진다
  • 인증 없이 요청 한 번이면 된다

② 민감 정보를 로그로 유도

  • 보안·인증 패키지를 DEBUG로 올리면 이후 로그에 토큰·요청 파라미터가 평문으로 찍힌다
  • 그 로그는 수집 시스템에 그대로 흘러간다
  • 로그 조회 권한만 있는 낮은 권한 내부자에게도 도달한다

한 줄로 봉인 — 위험의 성격이 다르다

env·heapdump는 정보가 샌다  /  loggers·shutdown은 공격자가 앱의 동작을 바꾼다

그래서 노출 위험도를 나눌 때 상태를 바꾸는 엔드포인트를 정보 유출 엔드포인트보다 위에 둬야 한다(7절). 같은 계열인 /actuator/shutdown을 부트가 유일하게 기본 비활성으로 뒀다는 사실 자체가 설계 의도를 말해준다.

4. 기본값은 안전한데, 왜 사고가 나는가

먼저 사실관계를 정확히 하자. 부트 3.x의 기본 노출은 health 하나뿐이다. 공식 문서가 "기본적으로 HTTP와 JMX 양쪽에서 health 엔드포인트만 노출된다"고 명시한다. (부트 2.x에서는 info도 함께 열려 있었다.)

그러면 왜 사고가 나는가. 개발자가 열기 때문이다. 전형적인 경로는 이렇다.

5. /env·/configprops — 버전에 따라 위험의 성격이 다르다

이 두 엔드포인트는 앱이 읽어들인 모든 설정값을 보여준다. /env는 환경변수·시스템 프로퍼티·yml을 포함한 전체 프로퍼티 소스를, /configprops는 @ConfigurationProperties로 바인딩된 설정 객체들을 덤프한다.

여기서 부트 2.x와 3.x의 동작이 완전히 다르므로 반드시 구분해서 말해야 한다.

부트 2.x부트 3.0 이상
값 마스킹 방식키 이름 패턴 기반 — password, secret, key, token, credentials 등이 이름에 들어가면 ******로 가림전부 마스킹 — 값은 기본적으로 모두 ******
제어 프로퍼티management.endpoint.env.keys-to-sanitize (패턴 목록)management.endpoint.env.show-values / ...configprops.show-values, 기본 never
커스텀 이름 키
규약 밖 이름		db-auth, token-value 같은 이름은 그대로 노출마스킹됨

부트 3.0의 변경은 릴리스 노트에 명시돼 있다. env, configprops, quartz 세 엔드포인트의 show-values 프로퍼티가 도입됐고 기본값이 never(항상 전부 마스킹)이며, always 또는 when-authorized로 바꿔야 값이 보인다. 그래서 위험의 성격이 이렇게 갈린다.

부트 2.x의 위험 — 마스킹 규칙을 빠져나가는 키

마스킹은 키 이름을 보고 판단하는 안전망이지 방어선이 아니다.

  • spring.datasource.password → 가려진다
  • payment.gateway.merchant-auth-string → 평문 그대로 나온다

이름 규약을 지켰는지에 보안이 걸려 있는 구조 자체가 불안정하다.

부트 3.x의 위험 — 값이 아니라 구조가 샌다

값이 전부 가려져도 /env는 프로퍼티 이름과 프로퍼티 소스 목록을 그대로 보여준다.

  • 내부 관리 API가 존재한다는 사실
  • 어떤 외부 결제사를 쓰는지
  • 자격증명을 환경변수로 주입한다는 사실
  • 지금 어떤 프로파일이 활성인지
부트 3.x 값은 전부 가려졌는데, 그래서 안전한가
{
  "systemEnvironment": {
    "PAYMENT_PG_ENDPOINT":      { "value": "******" },값은 가려짐
    "INTERNAL_ADMIN_API_HOST":  { "value": "******" },이런 게 있다는 사실은 노출
    "AWS_SECRET_ACCESS_KEY":    { "value": "******" }주입 방식까지 드러남
  }
}
비유 — 검게 칠한 서류, 그러나 라벨은 그대로인 서류철 값 마스킹은 서류 본문을 검은 펜으로 칠한 것이다. 그런데 서류철 등에 붙은 라벨("결제사 계약", "내부 관리 API 접속") 은 그대로 남아 있다. 무엇을 쓰는 조직인지, 무엇이 어디에 있는지는 라벨만으로 충분히 읽힌다 — 이것이 정찰(reconnaissance) 정보이고, 다음 단계 공격의 표적을 정하는 재료가 된다.

가장 위험한 조합 — 2.x → 3.x 마이그레이션

3.x로 올린 뒤 "/env에서 값이 안 보인다"는 불편을 해결하려고 show-values: always를 넣는 경우가 실제로 있다. 그 순간 3.x의 안전한 기본값을 버리고 2.x보다 더 위험한 상태(패턴 마스킹조차 없이 전부 평문)가 된다.

기본 never · 전부 마스킹→ when-authorized · 최소한의 타협→ always · 2.x보다 더 위험
운영에서는 애초에 /env를 노출하지 않는 것이 정답이다

6. /heapdump — GET 한 번에 메모리 전체

/env가 조심스럽게 가려진 설정이라면, /heapdump는 아예 가릴 개념이 없다. 힙 덤프는 그 순간 JVM 힙에 있던 모든 객체를 있는 그대로 담은 바이너리 파일이고, 마스킹이라는 단계가 존재하지 않는다.

그 파일 안에 들어 있는 것

복호화된 시크릿

7. 노출 위험도는 3단계로 나뉜다

암기 장치 — 3단계는 동사로 외운다

바꾼다(loggers · shutdown)  >  퍼간다(heapdump · env)  >  엿본다(beans · mappings)

8. 3중 방어 — 그리고 각각의 함정

방어는 서로 다른 계층에서 세 겹으로 건다. 한 겹이 뚫려도 다음 겹이 남게 하는 것이 목적이다. 세 겹이 같은 계층에 있으면 한 번의 실수로 전부 무너지지만, 계층이 다르면 설정 실수(앱)와 방화벽 오설정(망)이 동시에 나야 뚫린다.

암기 장치 — 3중 방어는 "적게 열고 · 멀리 두고 · 잠근다"

적게 열고(최소 노출)  ·  멀리 두고(관리 포트 분리 + 망 제한)  ·  잠근다(인증)
겹 ① 최소 노출
애플리케이션 설정 계층
애초에 창구를 만들지 않는다. 가장 싸고 가장 확실하지만, 열어야 하는 것에는 무력하다.
겹 ② 망 제한
네트워크 계층
앱 취약점과 무관하게 패킷을 차단. 대신 SSRF와 내부망 침해에는 뚫린다.
겹 ③ 인증
애플리케이션 보안 계층
호출자를 확인한다. 대신 두 함정(자식 컨텍스트 · 기본 보호 후퇴) 때문에 실제로 걸렸는지 확인이 필요하다.

8-1. 첫 번째 겹: 최소 노출 — 이름으로 열거한다

before 개발 편의로 넣었다가 그대로 운영에 나간 설정
management:
  endpoints:
    web:
      exposure:
        include: "*"env · heapdump · loggers · beans 전부

# 문제는 이 한 줄이 "무엇을 여는지"를
# 코드에 남기지 않는다는 것이다.
# 부트가 새 엔드포인트를 추가하면
# 그것도 자동으로 열린다.
after 필요한 것만 이름으로 (화이트리스트)
management:
  endpoints:
    web:
      exposure:
        # health: LB/probe용
        # prometheus: 지표 수집용
        # info: 배포 버전 확인용
        include: health, info, prometheus열린 것이 목록으로 남는다
함정 — "*" + exclude 조합은 왜 차선인가 굳이 "*"를 써야 한다면 exclude를 반드시 짝으로 붙인다. exclude는 include보다 우선한다는 규칙 자체는 맞다. 다만 이것은 블랙리스트라, 새 부트 버전에서 위험한 엔드포인트가 추가되면 그대로 열린다. 화이트리스트(include 열거)가 안전한 이유는 모르는 것이 자동으로 열리지 않기 때문이다.
heapdump와 env를 아예 빼는 것이 기본이다 — 필요할 때만 임시로 열고, 조사가 끝나면 닫는다

8-2. 두 번째 겹: 관리 포트 분리 + 망 제한

yaml 이 한 줄이 방어의 계층을 하나 늘린다
management:
  server:
    port: 9292        # 서비스는 8080, 관리는 9292

8-3. 함정 ① — 관리 포트는 별도 자식 컨텍스트에서 뜬다 함정

management.server.port가 메인 포트와 다르면, 부트는 관리 엔드포인트를 위해 별도의 웹 서버와 별도의 자식 애플리케이션 컨텍스트를 만든다. 그런데 메인 컨텍스트에 등록한 서블릿 필터는 이 자식 컨텍스트에 자동으로 등록되지 않는다. 스프링 시큐리티의 필터 체인도 서블릿 필터이므로 마찬가지다.

검증 설정을 믿지 말고 확인한다 — 이 한 줄이 함정 ①·②를 동시에 잡는다
# 인증 없이 호출했을 때 401/403이 나와야 정상이다.
# 200이 나온다면 시큐리티가 관리 포트에 적용되지 않은 것이다.
curl -i http://localhost:9292/actuator/env배포 체크리스트에 넣을 항목
선택의 문제 — 포트 분리가 항상 정답은 아니다 관리 컨텍스트에 필터를 직접 등록하려면 @ManagementContextConfiguration으로 관리 컨텍스트 전용 설정을 만드는 방법이 있지만, 손이 많이 가고 버전에 민감하다. 포트를 분리하지 않고 같은 포트에서 시큐리티로 막는 쪽이 오히려 단순할 때가 많다 — 어느 쪽이 낫다기보다, 두 방식의 방어 지점이 다르다는 것을 알고 고르는 것이 중요하다.

8-4. 세 번째 겹: 인증 — 망 제한이 뚫리는 경로가 실재한다

SSRF(Server-Side Request Forgery, 서버가 공격자가 지정한 주소로 대신 요청을 보내게 만드는 취약점)가 대표적이다. 외부에 열린 앱에 SSRF 구멍이 있으면, 공격자는 그 앱을 발판 삼아 http://localhost:9292/actuator/heapdump를 호출시킬 수 있다. 요청이 내부에서 나가므로 방화벽은 아무것도 막지 못한다. 이미지 URL 미리보기, 웹훅 등록, 외부 문서 가져오기 같은 흔한 기능이 전부 후보다(16-security/14-ssrf-server-side-request-forgery.md).

after actuator 전용 체인을 앞세운다

        .authorizeHttpRequests(auth -> auth

            // 나머지는 전부 ACTUATOR 권한 보유자만. 모니터링 수집 계정에 부여한다.
            .anyRequest().hasRole("ACTUATOR"))수집 계정에 부여
        // 브라우저 로그인 폼이 아니라 도구가 호출하므로 HTTP Basic이 적합하다.
        .httpBasic(Customizer.withDefaults())
        // actuator 호출은 세션을 쓰지 않으므로 CSRF 대상이 아니다.
        .csrf(csrf -> csrf.disable());
    return http.build();
}

8-5. 함정 ② — 내 SecurityFilterChain을 정의하는 순간 부트의 기본 보호가 사라진다 함정

스프링 시큐리티가 클래스패스에 있으면 부트는 ManagementWebSecurityAutoConfiguration으로 actuator를 자동 보호한다 — health만 열고 나머지는 인증을 요구하는 체인을 만들어 준다. 그런데 이 자동 설정에는 @ConditionalOnDefaultWebSecurity 조건이 붙어 있어, 사용자가 SecurityFilterChain 빈을 하나라도 정의하면 물러난다.

시큐리티 의존성 추가→ 부트가 actuator 자동 보호→ 내가 SecurityFilterChain 정의→ 자동 보호 후퇴 — 내 규칙이 전부
문제 actuator가 "나머지"에 휩쓸린다
// /api/** 만 인증을 걸고 나머지를 permitAll 했다.
// actuator 경로는 "나머지"에 해당해 그대로 열린다.
http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/**").authenticated()
        .anyRequest().permitAll());/actuator/heapdump 포함
고침 별도 체인으로 먼저 판정한다
// actuator 전용 체인을 @Order(1)로 앞세워
// 별도로 판정한다 (8-4의 actuatorSecurity 빈).
@Bean @Order(1) SecurityFilterChain actuatorSecurity(...)
@Bean @Order(2) SecurityFilterChain apiSecurity(...)순서가 곧 우선순위

가장 위험한 믿음 한 문장

"시큐리티를 붙였으니 actuator는 알아서 보호된다" — 실무의 앱 대부분에서 이 문장은 틀렸다

실무의 앱은 거의 전부 자기 시큐리티 설정을 갖고 있다. 즉 자동 보호는 이미 물러나 있고, 물러난 자리를 내 체인이 어떻게 처리하느냐가 전부다. permitAll()을 넓게 걸어놨다면 그대로 열린다. 그래서 결론은 다시 curl로 401 확인이다.

9. health 하나만 열어도 새는 것 — show-details

방어 3중선과 별개의 축이 하나 있다. health 하나만 열어 둔 상태에서도, management.endpoint.health.show-details 설정에 따라 정찰 정보가 인증 없이 나간다.

10. 자주 헷갈리는 지점

loggers는 로그 "수집"이 아니다
로그를 모아 검색하게 해주는 것은 Loki·ELK 같은 별도 시스템의 일이다. /actuator/loggers는 떠 있는 프로세스의 로그 레벨 설정을 바꾸는 관리 기능이다 — "무엇을 찍을지"를 정하는 쪽이고, 수집은 "찍힌 것을 어디로 보낼지"의 문제다.
덤프는 그 자리에서 뜬다
어딘가에 저장돼 있던 파일을 서빙하는 게 아니라, 요청을 받은 순간 JVM에서 새로 뜬다. 그래서 호출할 때마다 내용이 다르고, heapdump는 호출 자체가 무거운 작업이다(그래서 DoS 수단이 된다).
"기본 비활성" ≠ "기본 미노출"
shutdown은 기능 자체가 꺼져 있어(enabled=false) 노출을 열어도 동작하지 않는다. env·heapdump는 기능은 켜져 있고 창구만 닫혀 있어서, include에 이름을 넣는 순간 즉시 동작한다. 한 줄 설정으로 위험이 열리는 쪽은 후자다.
"풀·스레드 지표"의 풀은 DB 커넥션 풀
관용적으로 "풀 지표"는 DB 커넥션 풀(hikaricp.*)을 먼저 뜻하고, "스레드"는 톰캣·JVM 스레드다. 장애 때 "커넥션 풀 고갈인가, 스레드 풀 고갈인가"를 이 두 계열로 갈라내는 것이 실전 포인트다(2-2절).

11. 인출 카드 · 꼬리질문 셀프 테스트

11-1. 3초 인출 카드 — 보기 전에 먼저 답해보기

운영 4대 엔드포인트는?
헬·메·로·덤 — health(라우팅 판정) · metrics/prometheus(고갈 원인 특정) · loggers(무재기동 레벨 변경) · thread/heapdump(SSH 없는 진단).
부트 3.x 기본 노출은?
health 하나뿐이다 — HTTP와 JMX 양쪽 모두. (2.x에서는 info도 함께 열려 있었다.)
활성화와 노출의 차이는?
존재하는가 vs 창구로 내보이는가. 기본 비활성은 shutdown 하나뿐이고, 나머지는 기능은 켜져 있고 창구만 닫혀 있다.
사고는 어디서 나는가?
기본값이 아니라 개발 편의로 넣은 include: "*"가 공통 application.yml에 들어가 운영에 배포되면서.
3.x에서도 /env가 위험한 이유는?
값은 전부 마스킹돼도 프로퍼티 이름과 프로퍼티 소스 구조가 그대로 나간다 — 정찰 정보로 충분하다.
/heapdump가 최우선 경계인 이유는?
마스킹이라는 개념 자체가 없다. GET 한 번에 DB 접속정보·복호화된 시크릿·세션 토큰·개인정보. 게다가 반복 호출은 그 자체로 DoS.
/loggers가 특별한 이유는?
유일하게 상태를 바꾸는(POST) 상시 활성 엔드포인트. 루트 TRACE로 디스크 포화 DoS, 보안 패키지 DEBUG로 토큰을 로그에 유도.
3중 방어는?
적·멀·잠 — 적게 열고(최소 노출) · 멀리 두고(관리 포트 분리 + 망 제한) · 잠근다(인증).
두 함정은?
① 포트를 나누면 관리 포트가 자식 컨텍스트라 필터가 따라가지 않는다 ② 내 SecurityFilterChain을 정의하면 부트의 기본 보호가 물러난다.
확인 방법 한 줄은?
curl -i http://localhost:9292/actuator/env → 401/403이어야 정상. 200이면 인증이 안 걸린 것이다.
health의 show-details 기본값은?
never. always면 DB 종류·버전, Redis 버전, 디스크 경로·잔량이 인증 없이 나간다. 절충안은 when-authorized.
EndpointRequest를 쓰는 이유는?
"/actuator/**" 문자열로 매칭하면 base-path를 바꿨을 때 조용히 깨진다. EndpointRequest는 타입으로 매칭해 따라온다.
노출 위험도 3단계는?
바꾼다(loggers·shutdown) > 퍼간다(heapdump·env) > 엿본다(beans·mappings).
화이트리스트가 나은 이유는?
exclude(블랙리스트)는 새 부트 버전에서 추가된 엔드포인트가 그대로 열린다. include 열거는 모르는 것이 자동으로 열리지 않는다.

11-2. 꼬리질문 — 스스로 답한 뒤 펼쳐서 확인

/env에 마스킹이 있는데 왜 위험한가요? 함정힌트: "마스킹되니 괜찮다"로 끝내면 함정에 빠진다. 부트 버전부터 가른다

부트 버전을 먼저 갈라서 답해야 정확하다.

부트 2.x — 마스킹은 password, secret, key 같은 키 이름 패턴을 보고 판단한다. 사내 관례로 붙인 merchant-auth-string 같은 규약 밖 이름은 그대로 노출된다. 이름을 잘 지었는지에 보안이 걸려 있는 구조다.

부트 3.x — show-values가 도입돼 기본값 never, 즉 값은 전부 마스킹된다. 여기까지는 안전하다.

그래도 남는 것 — 값이 가려져도 프로퍼티 이름과 프로퍼티 소스 구조는 그대로 보인다. 내부 관리 API의 존재, 어떤 외부 서비스를 쓰는지, 자격증명을 어떤 방식으로 주입하는지가 드러난다. 정찰 정보로는 충분하다.

가장 위험한 것 — 3.x로 올린 뒤 "값이 안 보인다"는 이유로 show-values: always를 넣는 경우다. 2.x의 패턴 마스킹조차 없는, 전부 평문 상태가 된다.

그리고 결정타를 덧붙인다. /heapdump에는 마스킹이라는 개념 자체가 없다. /env를 아무리 잘 가려도 /heapdump가 열려 있으면 힙 안의 같은 값이 평문으로 나간다. 마스킹은 안전망이지 방어선이 아니다 — 방어선은 노출 자체를 막는 것이다.

관리 포트를 분리하고 방화벽으로 막았는데도 인증이 필요한가요? 시니어 변별힌트: 망 제한이 뚫리는 경로를 구체적으로 하나 대고, 8-3의 함정까지 이어 붙인다

필요하다. 망 제한이 뚫리는 경로가 실재하기 때문이다.

가장 현실적인 경로가 SSRF다. 외부에 열린 앱에 "URL을 받아 대신 호출해 주는" 기능이 있고 대상 검증이 허술하면, 공격자는 그 기능에 http://localhost:9292/actuator/heapdump를 넣는다. 요청이 서버 내부에서 출발하므로 방화벽 규칙은 전혀 적용되지 않는다. 이미지 URL 미리보기, 웹훅 등록, 외부 문서 가져오기 같은 흔한 기능이 전부 후보다.

경로가 하나 더 있다. 내부망은 생각보다 넓다. 같은 VPC의 다른 서비스, 침해당한 사내 PC, 잘못 설정된 VPN이 전부 "내부"다. 내부망 신뢰를 전제로 인증을 생략하는 것은 제로 트러스트 원칙과 정면으로 어긋난다.

여기서 8-3의 함정을 이어 말하면 깊이가 드러난다. 포트를 분리하면 관리 포트가 별도 자식 컨텍스트에서 뜨기 때문에 메인 컨텍스트의 시큐리티 필터 체인이 자동으로 적용되지 않는다. 즉 "포트도 분리했고 시큐리티도 걸었으니 두 겹"이라고 믿었는데 실제로는 방화벽 한 겹뿐인 상태가 될 수 있다. 그래서 설정을 넣은 뒤 인증 없이 curl로 찔러 401이 나오는지 반드시 확인해야 한다.

스프링 시큐리티를 쓰고 있으면 actuator는 자동으로 보호되지 않나요? 함정힌트: 자동 설정에 붙은 조건이 무엇인지, 그 조건이 실무에서 성립하는지

대부분의 실제 앱에서는 보호되지 않는다. 이 질문은 정확히 그 착각을 노린 것이다.

부트에는 ManagementWebSecurityAutoConfiguration이 있어서 actuator를 자동 보호해 준다 — health만 열고 나머지는 인증을 요구하는 체인을 만든다. 그런데 여기에는 @ConditionalOnDefaultWebSecurity 조건이 붙어 있고, 이 조건은 사용자가 SecurityFilterChain 빈을 정의하지 않았을 때만 성립한다.

실무의 앱은 거의 전부 자기 시큐리티 설정을 갖고 있다. 그 순간 자동 보호는 물러나고, actuator 경로는 내 체인의 규칙을 그대로 따른다. .anyRequest().permitAll()이 걸려 있으면 그대로 열린다.

그래서 처방은 actuator 전용 체인을 별도로 두고 @Order로 앞세우는 것이다. 경로 매칭은 "/actuator/**" 문자열 대신 EndpointRequest.toAnyEndpoint()를 쓴다 — management.endpoints.web.base-path를 바꾸면 문자열 매칭은 조용히 깨지지만 EndpointRequest는 따라오기 때문이다.

/actuator/loggers가 왜 특별히 위험한가요? 필수힌트: 지금까지의 위험과 "성격"이 다르다는 데서 출발한다

읽기 전용이 아니라 쓰기 가능한 엔드포인트이기 때문이다. env·heapdump는 "정보가 샌다"는 위험이었지만, loggers는 공격자가 앱의 동작을 바꿀 수 있다.

① 서비스 거부. 루트 로거를 TRACE로 POST하면 초당 수만 줄이 쏟아진다. 디스크가 차고, I/O가 포화되고, 로그 수집 파이프라인까지 함께 무너진다. 인증 없이 요청 한 번으로 된다.

② 민감 정보를 로그로 유도. 인증·보안 관련 패키지를 DEBUG로 올리면 이후 로그에 토큰과 요청 파라미터가 평문으로 찍힌다. 로그 조회 권한만 있는 낮은 권한의 내부자에게도 그것이 흘러간다.

그래서 노출 위험도를 나눌 때 상태를 바꾸는 엔드포인트를 정보 유출 엔드포인트보다 위에 둬야 한다. 같은 계열로 /actuator/shutdown이 있는데, 이것 하나만 부트가 기본 비활성으로 두고 있다는 사실 자체가 설계 의도를 말해준다.

loggers를 운영에서 실제로 어떻게 쓰나요? 필수힌트: 도구 설명이 아니라 "어떤 문제를 푸는가"로 시작한다

"재기동하면 증상이 사라진다"는 문제를 푸는 도구라고 답하는 것이 핵심이다.

절차는 이렇다. 간헐적 오류가 관측된다 → 원인 패키지를 좁힌다 → 그 패키지만 DEBUG로 POST한다 → 재현될 때까지 로그를 확보한다 → configuredLevel: null로 원복한다.

가치의 핵심은 "재기동 없이"에 있다. 재기동하면 커넥션 풀도, 캐시도, 문제를 만들던 상태도 전부 초기화된다. 즉 관찰하려던 대상 자체가 사라진다. 로그 레벨을 바꾸려고 재배포한다는 것은 증상을 없앤 뒤 증상을 조사하겠다는 말이 된다.

주의점도 함께 말하면 완성된다. 범위를 좁게 잡을 것(루트 로거를 올리면 디스크가 찬다), 원복을 잊지 말 것, 그리고 이 강력한 기능이 곧 위험이므로 인증 뒤에 두고 호출을 감사 로그로 남길 것.

health에 DB 체크를 넣어야 하나요? 필수힌트: 두 probe의 "실패 시 대응"이 정반대라는 데서 갈린다

readiness에는 넣고 liveness에는 빼는 것이 정석이다.

이유는 두 probe의 실패 시 대응이 정반대이기 때문이다. liveness 실패는 컨테이너 재시작을 부르고, readiness 실패는 트래픽만 차단한다. DB가 잠깐 끊겼을 때 앱을 재시작해봐야 DB는 여전히 안 붙는다 — 재기동으로 고칠 수 없는 문제에 재기동을 처방하면 전 파드가 동시에 재시작하는 재시작 폭풍이 난다.

DB 순단 시 원하는 동작은 트래픽만 빼고(readiness fail) 프로세스는 살려두는 것(liveness ok)이다. 그러면 DB가 회복될 때 파드가 스스로 돌아온다.

여기에 이 문서의 관점 하나를 덧붙이면 좋다. health group을 나눠 쓰더라도 show-details는 별개의 축이다. liveness/readiness를 잘 갈라 놨어도 show-details: always면 두 응답 모두에 DB 종류·버전과 디스크 경로가 붙어 나간다. probe는 상태 코드만 보므로 상세는 불필요하다.

include: "*"를 쓰되 위험한 것만 exclude로 빼면 되지 않나요? 함정힌트: 규칙 자체는 맞다. 문제는 "내가 모르는 것"이 어느 쪽으로 떨어지는가다

차선은 되지만 기본값으로 삼을 수는 없다. exclude가 include보다 우선한다는 규칙 자체는 맞다 — 그래서 당장은 동작한다.

문제는 구조가 블랙리스트라는 것이다. 블랙리스트는 "내가 아는 위험"만 막는다. 새 부트 버전에서 새로운 엔드포인트가 추가되면 그것은 자동으로 열린다 — 내가 그 존재를 알기도 전에 노출된다. 반대로 화이트리스트(include 열거)는 모르는 것이 자동으로 열리지 않는다. 실수의 방향이 "닫히는 쪽"으로 기울어져 있다.

부수적인 이점도 있다. include: health, info, prometheus는 "이 서비스가 무엇을 노출하는지"가 코드로 남는 문서가 된다. 리뷰어가 그 한 줄만 보고 판단할 수 있고, 변경이 diff에 드러난다. "*"는 아무것도 남기지 않는다.

heapdump·threaddump를 닫아두면 정작 장애 때는 어떻게 진단하나요? 가산점힌트: 이 둘은 원래 무엇으로 뜨던 것인가

진단 수단이 사라지는 것이 아니다. 이 둘은 원래 서버에 붙어 JDK 도구로 뜨던 것이다 — jstack <pid>(스레드 덤프), jmap -dump:...(힙 덤프). Actuator는 같은 일을 HTTP로 대신해 주는 편의일 뿐이므로, 닫아둬도 대체 경로가 남는다.

운영 방식은 "평시 닫고, 필요할 때 임시로 열고, 조사가 끝나면 닫는다"가 기본이다. 특히 heapdump는 뜨는 동안 JVM이 사실상 멈추고(stop-the-world) 수백 MB~수 GB를 디스크에 쓰므로, 상시 열어둘 이유가 애초에 없다.

한 가지 경계를 덧붙이면 좋다. HTTP 엔드포인트는 앱이 이미 떠 있어야 쓸 수 있다. 기동이 안 끝나 웹 서버가 아직 안 뜬 상태라면 엔드포인트 자체가 없으므로, 그때는 어차피 JDK 도구로 직접 떠야 한다. 기동 지연 진단에서 이 구분이 중요하다.

actuator를 인증 뒤에 두면 Prometheus 수집과 k8s probe는 어떻게 하나요? 가산점힌트: 전부 잠그는 게 아니라 "무엇을 열고 무엇을 잠그는지"를 갈라 말한다

전부 잠그는 것이 아니라 갈라서 잠근다. 8-4의 체인이 정확히 그 모양이다.

열어두는 쪽 — health와 info는 LB와 k8s probe가 인증 없이 찔러야 하므로 permitAll()로 둔다. probe에 인증 정보를 넣는 것도 불가능하진 않지만 운영이 복잡해지고 실익이 적다. 대신 show-details를 never(또는 when-authorized)로 두어 응답에서 새는 정보를 최소화한다.

잠그는 쪽 — prometheus를 포함한 나머지는 hasRole("ACTUATOR")로 두고, 모니터링 수집 계정에 그 권한을 부여한다. 도구가 호출하므로 브라우저 로그인 폼이 아니라 HTTP Basic이 적합하고, 수집기 쪽에는 그 자격증명을 설정해 둔다.

여기에 망 제한이 겹치면 더 안전해진다 — prometheus 수집은 어차피 내부망에서 오는 트래픽이므로, 관리 포트를 내부 대역으로 한정해도 수집에는 아무 지장이 없다. 인증과 망 제한이 서로를 방해하지 않는 대표적인 구간이다.

관리 포트를 분리하는 것과, 같은 포트에서 시큐리티로 막는 것 중 무엇을 고르나요? 시니어 변별힌트: "어느 쪽이 낫다"가 아니라 "방어 지점이 다르다"로 답한다

어느 쪽이 낫다기보다, 두 방식의 방어 지점이 다르다는 것을 알고 고르는 문제다.

포트 분리의 강점은 네트워크 계층에서 막는다는 것이다. 앱에 취약점이 있든 없든, 시큐리티를 잘못 걸었든 아니든 패킷 자체가 도달하지 못한다. 애플리케이션 보안과 독립된 겹이라는 점이 값어치다.

대신 대가가 있다. 관리 포트는 별도 자식 컨텍스트에서 뜨므로 메인 컨텍스트의 시큐리티 필터 체인이 자동으로 적용되지 않는다. 관리 컨텍스트에 필터를 직접 붙이려면 @ManagementContextConfiguration 같은 수단이 있지만 손이 많이 가고 버전에 민감하다. 그래서 같은 포트에서 시큐리티로 막는 쪽이 오히려 단순할 때가 많다.

실무적으로는 "가능하면 둘 다, 못 고르면 검증 가능한 쪽"이 답이 된다. 어느 쪽을 택하든 결론은 같다 — 설정을 믿지 말고 curl -i로 찔러 401이 나오는지 확인하는 것까지가 방어의 일부다.

한 줄 요약
Actuator는 health(라우팅 판정)·prometheus(지표)·loggers(무재기동 레벨 변경)·threaddump/heapdump(진단)로 운영을 떠받치는 창구지만 같은 창구가 공격자에게도 열려서 — /env는 부트 3.x에서 값이 전부 마스킹돼도 설정의 이름과 구조를 흘리고, /heapdump는 GET 한 번에 메모리 전체를 내주며, /loggers는 POST로 앱 동작까지 바꾸므로 — 부트 3.x의 기본값이 health 하나뿐이라는 설계 의도를 존중해 최소 노출로 열고, 관리 포트를 분리해 내부망만 허용하고, 그 위에 인증을 한 겹 더 얹되, 포트를 분리하면 시큐리티 필터 체인이 자동 적용되지 않고 내 SecurityFilterChain을 정의하면 부트의 기본 보호가 물러난다는 두 함정을 알고 실제로 401이 나오는지 확인하는 것까지가 완성이다.
