# 면접 질문별 출제 의도 — "면접관은 왜 이걸 묻는가"

> 짝 문서: `interview-questions-backend.md`
> 이 문서는 각 질문에 대해 "지식을 아는지 확인한다"가 아닌, **현업의 어떤 순간에 이 지식이 없으면 일이 막히는지 / 답변이 후보자의 무엇을 드러내는지**를 설명한다.

## 먼저: 면접관이 지식 질문을 던지는 진짜 이유

AI가 모든 지식 질문에 답할 수 있는 시대에 면접관이 여전히 기술 질문을 하는 이유는 크게 6가지다. 아래 개별 질문 설명은 모두 이 중 하나 이상에 뿌리를 둔다.

1. **상황 인지(trigger recognition)** — 지식은 검색하면 나오지만, "지금이 그 지식이 필요한 순간"임을 알아채는 건 검색이 안 된다. 캐시 스탬피드를 몰라도 코드는 짤 수 있지만, 아는
   사람만 배포 전에 "이 코드, 만료 순간에 DB 뚫리는데요"라고 말할 수 있다.
2. **장애 상황의 실시간 판단** — 새벽 3시에 서비스가 죽었을 때 증상을 보고 원인 후보를 좁히는 건 내재화된 모델로만 가능하다. 무엇을 검색해야 할지 모르면 AI도 못 쓴다.
3. **비가역 결정의 품질** — 샤드 키, 스키마, 아키텍처, 이벤트 스키마 같은 결정은 나중에 바꾸는 비용이 수십 배다. 함정을 미리 아는 사람만 설계 시점에 회피할 수 있다.
4. **AI 산출물 검증 능력** — AI가 짜준 코드의 동시성 버그, 잘못된 트랜잭션 경계를 잡아내려면 리뷰어의 머릿속에 정확한 동작 모델이 있어야 한다. 모델이 없으면 AI의 그럴듯한 오답을 그대로 배포한다.
5. **경험의 진위 판별** — 같은 개념도 "겪어본 사람"과 "외운 사람"의 답이 다르다. 겪어본 사람은 증상, 삽질 과정, 트레이드오프의 아픈 쪽을 말한다. 면접관은 이력서의 "대용량 트래픽 경험"이 진짜인지
   이 질문들로 교차 검증한다.
6. **꼬리 질문의 발판** — 기본 질문 자체가 목적이 아니라, 답변에서 나온 키워드를 파고들어 이해의 깊이(어디까지 진짜 자기 것인지)를 측정하는 시작점이다.

## 1. Java / Kotlin 언어

### 기본 ⭐

- **JVM 메모리 구조 / 객체 생성 위치** — 운영 중 메모리 지표(heap 사용률, Metaspace 증가)를 읽고 "정상인지 누수인지"를 판단하는 첫 관문. 이 지도가 없으면 모니터링 대시보드의 그래프가
  그냥 그림이고, OOM 알람이 왔을 때 어느 영역 덤프를 떠야 할지조차 정할 수 없다.
- **GC 동작 원리 / Young·Old 분리 이유** — GC 로그와 pause 그래프를 읽는 능력의 기초. "왜 트래픽 피크마다 응답이 200ms 튀는가"의 범인이 GC인지 아닌지를 가려내려면 세대별 수집의
  동작을 알아야 한다. 또한 "객체를 오래 들고 있는 코드가 왜 비싼지"를 체감하는 사람만 캐시 크기 같은 결정을 제대로 한다.
- **equals/hashCode 동시 재정의** — HashMap/Set에 넣은 객체가 "분명 넣었는데 못 찾는" 버그는 재현이 어렵고 증상이 엉뚱한 곳(중복 처리 실패, 캐시 미스 폭증)에서 나타난다. 이
  규약을 모르면 그 버그를 몇 시간씩 엉뚱한 데서 찾는다. AI가 생성한 엔티티/VO 코드에서 이 실수를 리뷰로 잡아낼 수 있는지도 본다.
- **String 불변성 / StringBuilder** — 불변 객체가 왜 스레드 안전과 캐싱(String pool)을 공짜로 주는지 이해하는지를 본다. 이 감각이 있는 사람은 도메인 객체 설계에서도 불변을
  기본값으로 두어 동시성 버그의 반을 원천 차단한다.
- **Checked vs Unchecked 예외 선택 기준** — 팀의 예외 처리 컨벤션(어디서 잡고, 어디서 변환하고, 무엇을 롤백시키는가)을 설계하거나 따를 때 필요한 판단. 실무에서
  `catch (Exception e) {}`로 삼켜진 예외가 장애 원인 은폐의 단골이라, 예외를 "설계의 일부"로 보는 사람인지 확인한다.
- **인터페이스 vs 추상 클래스** — 실제로는 "확장 지점을 어떻게 설계하는가"의 질문. 외부 연동(PG사가 3곳)처럼 구현이 여럿인 지점에서 추상화 경계를 어디에 둘지 결정해본 사람인지를 본다.
- **final의 의미** — 사소해 보이지만, "변경 가능 지점을 의도적으로 줄이는 습관"이 있는지를 드러낸다. 코드 리뷰에서 동료의 가변 상태를 지적할 수 있는 최소 어휘.
- **Java 8+ 기능 실무 활용** — 버전별 문법 암기가 아니라, "팀 코드베이스의 관용구를 읽고 쓸 수 있는가"와 Stream 남용(가독성 해치는 체이닝, 스트림 안 사이드이펙트)을 분별하는 감각을 본다.
- **Kotlin null safety / 플랫폼 타입** — Java 라이브러리와 섞인 실무 코드베이스에서 NPE는 대부분 플랫폼 타입 경계에서 터진다. `!!`를 아무데나 쓰는 사람과 경계에서 검증하는 사람은
  운영 장애 빈도가 다르다.
- **data class / sealed class** — sealed + when의 조합이 "새 상태 추가 시 컴파일러가 누락을 잡아주는 설계"임을 아는지. 결제 상태 같은 상태 머신을 안전하게 확장하는 실무
  패턴과 직결된다.
- **enum의 활용 폭** — enum을 상수 나열로만 쓰는 사람과 동작(전략 메서드)·허용 전이(상태 머신)를 타입에 싣는 사람은 코드 전반의 분기문 산탄(if-else 산재) 양이 다르다. "타입 시스템에
  규칙을 실어 컴파일러가 지키게 한다"는 sealed class 문항과 같은 사고의 Java 판이다.

### 중급 ⭐⭐

- **G1 vs ZGC, latency 민감 서비스의 선택** — GC 선택은 서비스 특성(처리량형 배치 vs p99 민감 API)에 따른 의사결정이고, 잘못 고르면 하드웨어를 늘려도 해결이 안 된다. "선택의
  근거를 말할 수 있는가"로 인프라 결정에 참여할 수 있는 연차인지 가늠한다.
- **Full GC 빈발 시 추적 순서** — 전형적인 "AI에 물어볼 수 없는" 상황: 원인이 코드 어딘가에 있고, 로그·덤프·최근 배포 이력을 조합해 좁혀야 한다. 추적의 '순서'를 묻는 이유는 방법론 없이
  찍는 사람과 체계적으로 배제해가는 사람을 구분하기 위해서다.
- **HashMap 내부 동작** — 자료구조 하나를 끝까지 파본 적 있는지의 표본 검사. 리사이징 비용을 아는 사람은 초기 용량 지정 같은 사소하지만 대량 처리에서 유의미한 최적화를 자연스럽게 한다.
- **ConcurrentHashMap의 동시성 보장 방식** — "thread-safe 컬렉션을 쓰면 안전하다"는 착각(복합 연산은 여전히 원자적이지 않음)을 갖고 있는지 검사한다. 이 착각은 부하가 걸려야만
  드러나는 최악의 버그를 만든다.
- **volatile: 가시성 vs 원자성** — `volatile int counter++` 같은 코드가 왜 틀렸는지 즉시 보이는가. 동시성 버그는 테스트를 통과하고 운영에서만 터지므로, 코드 리뷰 단계에서 잡을
  수 있는 사람의 가치가 특히 크다.
- **happens-before** — 동시성 코드의 정확성을 "돌려보니 되던데요"가 아니라 규칙으로 논증할 수 있는지. 이게 되는 사람만 lock-free 코드나 AI가 생성한 동시성 코드를 검증할 수 있다.
- **ThreadLocal과 스레드풀의 위험** — 톰캣은 스레드를 재사용하므로 정리 안 한 ThreadLocal은 "다른 사용자의 인증 정보가 섞여 보이는" 류의 보안 사고로 직결된다. 프레임워크가 숨겨준 실행
  모델을 이해하고 쓰는지 확인하는 질문.
- **parallelStream의 함정** — 공용 ForkJoinPool을 웹 요청 처리에서 나눠 쓰면 한 기능의 부하가 전체 서비스를 굶긴다. "편해 보이는 API의 숨은 공유 자원"을 의식하는 습관이 있는지
  본다.
- **Coroutine 동작 원리 / 스레드와의 차이** — 코루틴을 "가벼운 스레드"라고만 아는 사람은 블로킹 호출을 코루틴 안에 넣어 이점을 전부 없앤다. 원리를 알아야 "어디서 이득이고 어디서 무의미한지"를
  판단한다.
- **Dispatchers.IO vs Default** — I/O bound와 CPU bound 작업의 구분은 스레드풀 설계 전반(비동기 처리, 배치 병렬화)에 반복 등장하는 판단이다. 이 구분이 안 되면 풀 크기
  설정이 전부 감으로 이뤄진다.
- **타입 소거와 와일드카드(PECS)** — 제네릭이 컴파일 타임 전용 장치임을 알아야 런타임 타입 분기가 안 되는 이유, 직렬화 라이브러리가 TypeReference 같은 우회를 쓰는 이유가 이해된다.
  PECS는 공통 모듈·라이브러리의 API 시그니처를 설계하는 사람과 소비만 하는 사람을 가르는 표지다.
- **Optional의 사용 범위** — Optional을 필드·파라미터·컬렉션 원소에 쓰는 코드는 "null 안전"이 아니라 관용구 위반이다. 도구의 설계 의도(반환 타입으로 부재를 표현)를 이해하고 쓰는지 —
  편리해 보이는 API를 원래 목적 밖으로 확장할 때 멈출 수 있는 절제를 본다.
- **try-with-resources와 자원 누수** — 커넥션·스트림 누수는 평소엔 멀쩡하다가 트래픽이 몰리는 날 풀 고갈로 터진다. finally 수동 정리의 실수 가능성(예외 중첩, 반환 누락)을 언어
  기능으로 제거하는 습관 — 자원의 생명주기를 의식하며 코드를 쓰는지의 표본이다.
- **방어적 복사와 컬렉션 노출** — getter로 내부 List를 그대로 반환하면 외부가 도메인 객체의 불변식을 우회해 상태를 바꿀 수 있다 — 캡슐화가 메서드 시그니처가 아니라 참조 공유 수준에서 깨지는
  지점. 불변을 기본값으로 두는 설계 습관(String 문항)의 실전 검증이다.
- **static SimpleDateFormat (공유 가변 상태 리뷰)** — 서두의 의도 1(상황 인지)·4(AI 검증)를 정면으로 묻는 형식. 스레드 안전하지 않은 객체의 공유는 테스트를 전부 통과하고 동시
  요청에서만 값이 섞이는 유형이라, 리뷰어의 머릿속 모델만이 방어선이다. 한 사례를 같은 패턴(가변 static, 싱글턴 빈의 상태 필드)으로 일반화해 찾는지 — 함정을 "목록"이 아니라 "유형"으로 아는지 본다.

### 고난이도 ⭐⭐⭐

- **OOM 힙 덤프 분석 과정** — 실제 해본 사람과 아닌 사람의 답이 극명하게 갈리는 질문. 도구 이름(MAT, dominator tree)이 아니라 "덤프를 뜨면 서비스가 멈추는데 운영 중에 어떻게 뜰
  건가" 같은 현실 제약을 언급하는지로 경험의 진위를 가린다.
- **스레드 덤프에서 데드락 찾기** — 데드락은 서비스가 "죽지 않고 멈추는" 형태라 재시작으로 덮기 쉽고, 근본 원인을 못 찾으면 반복된다. 덤프를 읽어 락 순환을 찾는 능력은 반복 장애를 끊는 능력이다.
- **JIT 동작이 성능에 미치는 영향** — 배포 직후 latency 상승, 부하 테스트의 워밍업 필요성 같은 "측정을 오염시키는 요인"을 아는지. 이걸 모르면 성능 측정 자체를 잘못해서 잘못된 결론으로
  튜닝한다.
- **synchronized/ReentrantLock/StampedLock/CAS 선택 기준** — 동기화 도구 선택은 경합 정도와 읽기/쓰기 비율에 따른 트레이드오프 판단이다. 항상 synchronized만 쓰는
  사람은 고경합 지점에서 병목을 만들고, 항상 lock-free를 쓰는 사람은 검증 불가능한 코드를 만든다.
- **False sharing** — 극한 성능 최적화가 필요한 순간(집계 카운터, 고빈도 이벤트 처리)에 프로파일러에도 잘 안 잡히는 병목의 정체를 아는지. 하드웨어까지 내려가본 깊이의 표본 검사에 가깝다.
- **Virtual Thread와 pinning** — 새 기술 도입 판단의 시금석. "가상 스레드 쓰면 다 해결"이 아니라 pinning(synchronized 블록 내 블로킹) 같은 제약과 기존 코드베이스의
  궁합을 먼저 따지는 사람인지 — 즉 하이프와 실제를 구분하는 습관을 본다.
- **structured concurrency / GlobalScope의 위험** — 비동기 작업의 생명주기 관리(요청이 취소되면 하위 작업도 취소되어야 함)를 놓치면 유령 작업이 자원을 먹고 에러는 아무도 못
  본다. 비동기 코드의 "실패와 취소"까지 설계하는 사람인지 확인한다.

### 알면 좋은 +α

- **record vs data class** — 불변 데이터 캐리어를 언어가 직접 지원하는 흐름(Java 16+)을 따라오고 있는지, DTO 보일러플레이트를 어떻게 줄이는지 — 언어 버전 업의 이점을 실무에
  수용하는 속도를 본다.
- **오토박싱 캐시와 == (127은 true, 128은 false)** — `==`와 `equals` 혼동이 만드는 "작은 값 테스트는 전부 통과하고 운영 데이터에서만 틀리는" 버그의 대표 사례. 언어의 미묘한
  규칙이 재현 안 되는 버그로 나타나는 전형을 아는지 본다.
- **Strong/Soft/Weak 참조** — 로컬 캐시·리스너 보관 자료구조에서 메모리 누수를 만들지 않는 도구(WeakHashMap 등)의 기반. GC와 참조의 상호작용까지 아는 깊이의 표본.
- **Kotlin inline / reified** — 제네릭 타입 소거라는 JVM 제약을 언어가 어떻게 우회하는지 아는가 — 라이브러리 코드(`filterIsInstance` 등)를 읽고 쓰는 수준과 API
  시그니처를 설계하는 수준의 분기점.
- **BigDecimal의 equals vs compareTo** — 1.0과 1.00이 equals로는 다르고 compareTo로는 같다는 스케일 함정은 "금액 일치 검증이 간헐적으로 실패하는" 재현 어려운
  버그를 만든다. 금액을 다루는 타입의 미묘한 규약까지 확인해봤는지 — 10장 부동소수점 금지의 다음 단계 디테일이다.

## 2. Spring / Spring Boot

### 기본 ⭐

- **IoC/DI의 이유** — "왜"를 묻는 이유는 테스트 가능성과 결합도 관점에서 설명할 수 있는지 보기 위해서다. 이걸 설명 못 하는 사람은 DI를 쓰면서도 static 유틸과 new를 남발해 테스트 불가능한
  코드를 만든다.
- **Bean 생명주기 / 싱글턴에 상태를 두는 위험** — 싱글턴 빈의 인스턴스 필드에 요청별 상태를 둔 코드는 단일 사용자 테스트를 전부 통과하고 동시 접속에서만 데이터가 섞인다. 프레임워크의 기본 계약을
  아는지가 이런 "테스트로 못 잡는 버그"의 예방선이다.
- **생성자 주입 권장 이유** — 순환 참조의 조기 발견, 불변성, 테스트 시 목 주입 용이성까지 연결해 말하는지. 컨벤션을 "팀 규칙이라서"가 아니라 근거로 이해하는 사람은 새로운 상황에서도 올바른 선택을
  한다.
- **스테레오타입 애너테이션 차이** — 사소하지만 `@Repository`의 예외 변환처럼 애너테이션이 실제 동작을 바꾸는 지점을 아는지. "장식"과 "기능"을 구분하는 정밀함의 표본.
- **Spring MVC 요청 처리 흐름** — 필터에서 죽었는지, 인터셉터에서 죽었는지, 컨트롤러 전 바인딩에서 죽었는지 — 에러 로그의 스택트레이스를 보고 "어느 단계"인지 즉시 아는 사람과 모르는 사람의
  디버깅 속도 차이가 크다.
- **Filter vs Interceptor** — 인증, 로깅, 트레이싱을 어느 계층에 넣을지의 실무 결정. 잘못 놓으면 "인증 실패 응답에는 trace id가 안 찍히는" 류의 관측 사각지대가 생긴다.
- **@Transactional 기본 동작 / 롤백 조건** — checked exception에서 롤백 안 되는 기본값을 모르면 "예외는 났는데 데이터는 반쯤 커밋된" 정합성 사고를 낸다. 결제 도메인에서는 이
  한 줄이 돈 사고다.
- **Auto Configuration 동작** — "스프링부트가 알아서 해줬는데 왜 안 되지"라는 상황(빈 충돌, 의존성 추가만으로 바뀐 동작)에서 원인을 추적하려면 자동 설정의 조건부 로딩을 이해해야 한다.
  마법을 마법으로 두는 사람은 이 유형의 문제에서 항상 막힌다.
- **Profile 활용** — 로컬/스테이징/운영의 설정 분리는 "운영 DB에 로컬 설정으로 붙는" 류의 사고를 막는 기본 방어선. 환경 분리를 대충 하는 사람은 언젠가 반드시 사고를 낸다.

### 중급 ⭐⭐

- **AOP 프록시 원리 (JDK vs CGLIB)** — 프록시 기반이라는 사실을 모르면 `@Transactional`, `@Async`, `@Cacheable`이 "붙였는데 동작 안 하는" 상황을 이해할 수
  없다. 스프링의 마법 대부분이 이 하나의 원리로 설명되므로, 이걸 아는지가 스프링을 "쓰는" 사람과 "이해하는" 사람의 분기점이다.
- **자기 호출 시 @Transactional 미적용** — 위 원리의 실전 검증. 이 함정은 코드 리뷰에서 눈으로 잡아야 하고(런타임에 조용히 트랜잭션 없이 실행됨), AI가 생성한 서비스 코드에도 흔히 들어
  있다.
- **REQUIRED vs REQUIRES_NEW 실무 사례** — "본 처리는 롤백돼도 감사 로그는 남아야 한다" 같은 요구사항을 구현하는 도구. 반대로 REQUIRES_NEW 남용이 커넥션 2개 점유로 데드락과
  풀 고갈을 만드는 것까지 아는지 — 도구의 비용을 아는 사람인지 본다.
- **readOnly=true의 실제 효과** — 플러시 생략, replica 라우팅 힌트 등 실효를 아는지. "붙이면 좋다더라"식 카고컬트 습관인지, 효과를 알고 쓰는지를 가리는 질문.
- **격리 수준과 이상 현상** — 격리 수준은 "정합성 버그가 재현 안 되는 이유"의 단골 원인이다. non-repeatable read를 모르면 "같은 트랜잭션에서 두 번 읽었는데 값이 달라요"라는 버그 리포트
  앞에서 코드만 백날 들여다본다.
- **@Async의 주의점** — 기본 스레드풀 방치(무제한 큐), 예외가 조용히 사라지는 문제, 프록시 제약 — 셋 다 운영에서만 터지는 유형이다. 비동기를 "빠르게 하는 마법"이 아니라 "관리해야 할 자원"으로
  보는지 확인한다.
- **Spring Event / @TransactionalEventListener** — 결합도를 낮추면서 "커밋 후에만 알림 발송" 같은 정합성 요구를 지키는 실무 패턴. 이벤트를 써봤다는 사람에게 커밋 전/후
  실행 시점을 물으면 진짜 이해도가 드러난다.
- **순환 참조 해결** — 순환 참조는 대부분 잘못된 책임 분배의 증상이다. `@Lazy`로 덮는 답과 설계를 고치는 답 중 무엇이 먼저 나오는지로 설계 감각을 본다.
- **RestTemplate/WebClient/RestClient 선택** — 단순 API 선택 같지만 실제로는 타임아웃·커넥션풀 설정이 어디 있는지 아는가의 질문. 외부 호출 클라이언트의 기본 설정을 방치한 채
  운영에 가는 것이 연쇄 장애의 고전적 시작점이다.
- **전역 예외 처리와 에러 응답 표준화** — 에러 응답의 일관성은 프론트엔드·모바일 팀과의 협업 비용, 그리고 장애 시 에러율 집계 가능성을 결정한다. "혼자 잘 짜는" 것 너머 "시스템의 계약을 설계"해본
  사람인지 본다.
- **@Cacheable의 함정** — 캐시 추상화도 AOP 프록시 위에 있어 자기 호출에 무력하고, 캐시 키 설계 실수는 "다른 사용자의 데이터가 보이는" 사고로 직결된다. 애너테이션 한 줄의 편의 뒤에 있는
  동작(키 생성 규칙, null 처리, TTL은 캐시 매니저 설정임)을 확인하고 쓰는지 — 5장 Redis 지식이 스프링 계층에 착지하는 지점이다.
- **@Valid와 도메인 검증의 역할 분담** — 형식 검증(컨트롤러)과 비즈니스 규칙 검증(도메인)의 경계가 없으면 검증이 중복되거나, 더 나쁘게는 "저쪽에서 하겠지"로 누락된다. "이 검증은 누구의 책임인가"
  를 계층 설계로 답할 수 있는지 — 검증을 애너테이션 장식이 아니라 설계 요소로 다루는지 본다.

### 고난이도 ⭐⭐⭐

- **트랜잭션 안의 외부 API 호출** — DB 커넥션을 문 채로 3초짜리 외부 호출을 기다리면, 외부사 지연 하나가 커넥션풀 고갈 → 전 서비스 마비로 번진다. 이 연쇄를 머리로 시뮬레이션할 수 있는 사람만
  장애가 나기 전에 구조를 바꾼다. 대용량 서비스 면접의 핵심 변별 문항.
- **커밋 후 이벤트 발행 (Outbox)** — "커밋됐는데 발행 실패" / "발행됐는데 롤백"의 양쪽 실패를 다 짚는지 본다. 분산 시스템 정합성의 축소판이라, 이 문제를 이해한 사람은 Kafka·MSA 정합성
  문제 전반을 이해할 준비가 된 것이다.
- **트랜잭션 동기화와 커넥션 바인딩 원리** — 멀티 데이터소스, 배치+API 혼재, 비동기 경계에서 트랜잭션이 "왜 안 타는지"를 추적하려면 이 내부 구조까지 알아야 한다. 프레임워크의 추상화가 새는(
  leaky) 지점에서 일할 수 있는 깊이인지 확인한다.
- **스레드풀·커넥션풀 크기 산정** — "기본값 그대로" 또는 "많을수록 좋다"는 답을 거르는 질문. 풀 크기는 계산 가능한 공학적 결정(동시 요청 수 × 요청당 점유 시간)이고, 이 계산을 해본 사람만 용량
  산정 회의에서 근거 있는 숫자를 낼 수 있다.
- **HikariCP 커넥션 고갈 진단** — 증상(timeout 로그)은 하나인데 원인은 여럿(누수, 느린 쿼리, 트랜잭션 내 외부 호출, 풀 크기)인 전형적 상황. 원인 후보를 나열하고 각각의 배제 방법을 말할
  수 있는지 — 진단 방법론 자체를 평가한다.
- **WebFlux vs MVC, 독이 되는 경우** — 기술 선택에서 "우리 팀의 학습 비용, 디버깅 난이도, 블로킹 라이브러리 의존성"까지 넣어 판단하는지. 이력서에 WebFlux를 쓴 지원자의 이해가 튜토리얼
  수준인지 운영 수준인지 가르는 질문이기도 하다.
- **Graceful shutdown 구성** — 배포할 때마다 에러가 소량 발생하는데 아무도 신경 안 쓰는 팀이 많다. 이를 문제로 인식하고 인프라(LB 제외)와 앱(진행 중 요청 완료)의 협업으로 풀어본
  사람인지 — 운영 품질에 대한 기준선을 본다.

### 알면 좋은 +α

- **@Value vs @ConfigurationProperties** — 설정 오타가 런타임에 조용히 기본값으로 도는 사고를 타입 안전 바인딩·검증으로 막는지 — 설정도 코드처럼 검증 대상으로 보는 규율의 표본.
- **Actuator 운영 활용과 노출 보안** — 헬스체크·메트릭·스레드덤프를 표준 도구로 쓰는지, 그리고 `/heapdump`·`/env` 무방비 노출이 곧 정보 유출 사고임을 아는지 — 편의 기능의 보안
  면적을 함께 보는 습관.
- **Spring Security 필터 체인** — "401이 어디서 나왔는가"를 추적하려면 인증이 컨트롤러 훨씬 앞의 필터에서 일어남을 알아야 한다. 인증/인가 실무의 디버깅 기초 체력.
- **애플리케이션 시작 시간 추적** — 시작이 느리면 스케일 아웃 반응과 배포 속도가 함께 느려진다. 빈 초기화 비용을 측정·지연(lazy)하는 방법을 아는지 — 잘 안 보는 지표에서 운영 품질을 찾는 시야.
- **반복 인증 코드 제거 (ArgumentResolver)** — 컨트롤러마다 토큰 파싱·사용자 조회가 복붙되면 검증 누락 한 곳이 곧 보안 구멍이다. 횡단 관심사를 프레임워크 확장점으로 옮겨 "실수할 수 없는
  구조"를 만드는지 — 프레임워크를 쓰는 수준을 넘어 확장하는 수준인지 본다.
- **@Scheduled의 스레드 모델** — 기본이 단일 스레드 풀이라 느린 작업 하나가 다른 모든 스케줄을 밀리게 하는데, 증상(특정 작업이 제때 안 돎)에서 원인(스레드 공유)으로 가는 연결이 어렵다.
  18장의 주기 작업 침묵 중단과 짝을 이루는, "프레임워크 기본값을 확인하고 쓰는" 습관의 표본이다.
- **AI 코드의 트랜잭션 체크리스트** — 의도 4(AI 산출물 검증)의 스프링 판. AI가 짠 서비스 코드의 결함은 문법이 아니라 트랜잭션 경계(자기 호출로 미적용, 경계 안 외부 호출, 삼켜진 예외로 인한
  롤백 누락)에 숨는다. 검증 항목을 체크리스트로 언어화해둔 사람인지 — 리뷰가 감이 아니라 절차인지 확인한다.

## 3. JPA / ORM

### 기본 ⭐

- **JPA vs MyBatis** — 도구 선택의 근거를 말할 수 있는지. 팀마다 둘 다 쓰이므로 "왜 이 프로젝트엔 이게 맞는가"를 논할 수 있어야 기술 스택 논의에 참여할 수 있다.
- **영속성 컨텍스트 / dirty checking** — JPA의 거의 모든 미스터리("save 안 했는데 UPDATE가 나감", "조회했는데 쿼리가 안 나감")가 이 개념 하나로 설명된다. 이걸 모르고 JPA를
  쓰는 건 자동변속기 원리를 모르고 견인차를 모는 것과 같다 — 평소엔 되지만 이상 동작 시 속수무책이다.
- **EAGER vs LAZY 기본 전략** — 기본값을 잘못 두면 스키마가 커질수록 조회 하나가 조인 폭탄이 된다. 초기 설계 결정이 1년 뒤 성능을 결정하는 대표 사례라, 기본 전략의 근거를 묻는다.
- **N+1 문제와 해결** — JPA 성능 문제의 8할. 중요한 건 해결책 암기가 아니라 "운영 전에 어떻게 발견하는가"(쿼리 로그 확인 습관, 테스트에서 쿼리 수 검증)까지 말하는지다.
- **merge vs dirty checking** — merge의 오해(detached 엔티티 전체 덮어쓰기)는 "안 바꾼 필드가 null로 덮이는" 데이터 유실 사고를 만든다. 미묘하지만 사고 유형이 명확한
  지식.
- **연관관계의 주인** — FK 갱신이 "왜 안 되는지" 헤매는 신입 단골 이슈. 이걸 명확히 설명하면 JPA 매핑을 눈감고도 다루는 수준임을 시사한다.
- **LazyInitializationException** — JPA 입문자가 가장 먼저 부딪히는 예외이고, 해결책의 선택(트랜잭션 연장? fetch join? DTO 변환 시점 이동?)이 곧 계층 설계 이해를
  드러낸다. "무조건 EAGER로" 또는 "OSIV 켜서" 같은 답은 증상 은폐임을 아는지 — 예외 하나로 영속성 컨텍스트의 생명주기 전체를 검증하는 효율 높은 질문이다.

### 중급 ⭐⭐

- **fetch join + 페이징** — limit이 쿼리에 안 붙고 전체를 메모리에 올리는 이 함정은 데이터가 적을 땐 멀쩡하다가 데이터 증가와 함께 OOM으로 터진다. "지금은 되는데 나중에 터지는" 코드를
  미리 알아보는 눈을 검사한다.
- **OSIV 트레이드오프** — 기본값(켜짐)이 커넥션을 뷰 렌더링까지 물고 있게 한다는 사실은 대용량 트래픽에서 커넥션 고갈의 숨은 원인이다. 프레임워크 기본값을 의심해본 적 있는지를 본다.
- **낙관적 vs 비관적 락** — 동시 수정 시나리오(같은 회차를 두 관리자가 편집)에서 충돌 빈도와 재시도 비용을 따져 선택하는 판단력. "락이 필요하다"까지는 다 알지만 "어떤 락인지"의 근거를 대는 사람은
  적다.
- **벌크 연산 후 영속성 컨텍스트** — 벌크 UPDATE가 1차 캐시를 우회해 "DB는 바뀌었는데 조회 결과는 옛날 값"인 상황은 증상이 괴상해서 원인을 모르면 며칠을 헤맨다. 겪었거나 원리를 아는 사람만
  즉답한다.
- **엔티티 직접 노출 금지** — API 스펙이 DB 스키마에 종속되는 문제, 지연 로딩 직렬화 폭탄, 순환 참조 — "계층 간 경계"를 지키는 규율이 있는지의 리트머스.
- **QueryDSL 동적 쿼리** — 검색 필터 조합 같은 실무 요구를 문자열 조립 없이 타입 안전하게 푸는 경험. "실무 CRUD 너머의 조회 요구"를 다뤄봤는지 확인한다.
- **유니크 제약 + 동시 INSERT** — 중복 체크 후 저장(check-then-act) 패턴이 동시성에서 깨지는 것을 아는지. 회원가입, 쿠폰 발급 등에서 반복 출제되는 실전 상황으로, DB 제약을 최후
  방어선으로 쓰는 설계 습관을 본다.
- **flush 시점과 SQL 실행 순서** — flush가 커밋·JPQL 실행 직전에 일어나고 쓰기 지연 SQL이 코드 순서와 다르게 나갈 수 있음을 모르면, "코드상 삭제 후 삽입인데 유니크 제약 위반" 같은
  미스터리를 못 푼다. 영속성 컨텍스트 이해가 진짜인지 검증하는 실전 문항.
- **findById vs getReferenceById** — 연관관계 설정만 필요한데 SELECT를 날리는 낭비를 프록시로 없앨 수 있는지 — JPA를 "동작하게" 쓰는 수준과 "쿼리를 통제하며" 쓰는 수준을
  가르는 디테일이다.
- **상속 매핑 전략** — 상속 구조를 테이블로 내리는 결정은 조회 성능(조인 비용), 무결성(nullable 컬럼), 확장성(타입 추가)의 트레이드오프이고 한번 정하면 바꾸기 매우 비싸다. 객체 모델과 관계
  모델의 임피던스 불일치를 실제로 다뤄봤는지 본다.
- **조회 전용 DTO 프로젝션** — 목록 조회에 엔티티를 쓰면 필요 없는 컬럼까지 읽고 영속성 컨텍스트 관리 비용(스냅샷 유지)까지 지불한다. "변경이 목적인 조회"와 "표시가 목적인 조회"를 구분해 도구를
  달리 쓰는지 — 조회 성능 최적화의 첫 단추이자 CQRS(12장)로 이어지는 사고의 출발점이다.
- **루프 건별 조회 PR 리뷰** — 의도 1(상황 인지)의 검사 형식. N+1 개념을 아는 것과, 지금 잘 돌아가는 코드에서 "데이터가 늘면 터진다"를 배포 전에 말할 수 있는 것은 다르다. 리뷰 코멘트라는
  형식은 지적의 정확성뿐 아니라 대안 제시(IN 절 일괄 조회)와 전달 방식까지 함께 드러낸다.

### 고난이도 ⭐⭐⭐

- **재고/포인트 차감 동시성 4가지 접근 비교** — 정답이 없는 문제에서 트레이드오프(충돌률, 처리량, 데드락 위험, 인프라 의존)를 정리해 말하는 능력 자체를 평가한다. 실무의 기술 선택 회의를 15분으로
  압축한 질문이며, 결제 도메인 채용에서는 사실상 필수 검증 항목.
- **대량 INSERT와 JDBC batch / IDENTITY 문제** — "JPA로 짰더니 100만 건에 2시간"인 상황에서 원인(건별 INSERT, IDENTITY의 batch 무력화)을 알고 우회로를 설계할
  수 있는지. ORM의 한계를 인정하고 내려갈 줄 아는 유연함을 본다.
- **여러 Aggregate 동시 수정의 문제** — 트랜잭션 경계 = 정합성 경계 = 락 경합 범위라는 연결을 이해하는지. 큰 트랜잭션이 데드락과 경합의 온상임을 알고 도메인 이벤트로 쪼개는 설계는, 모놀리스에서
  MSA로 가는 사고의 전 단계다.
- **replica 라우팅과 replication lag** — "쓰고 바로 읽었는데 없어요"라는, 코드에는 버그가 없는 버그. 인프라 구조가 애플리케이션 로직에 스며드는 지점을 다뤄본 경험을 확인하며, 대용량
  서비스는 replica 없이 운영이 불가능하므로 사실상 필수 경험 검증이다.

### 알면 좋은 +α

- **CascadeType.REMOVE / orphanRemoval** — 편의 설정 하나가 "부모를 지웠더니 공유되던 자식까지 사라지는" 연쇄 삭제 사고를 만든다. 파급 범위를 모르는 편의 기능은 쓰지 않는
  신중함을 본다.
- **엔티티의 equals/hashCode** — 프록시 클래스 비교, id가 저장 전엔 null인 시점 문제로 Set/Map에서 엔티티가 사라지는 미묘한 버그. 1장의 equals 규약이 JPA라는 구체 환경에서
  어떻게 꼬이는지 아는 응용 깊이.
- **Soft delete와 유니크 제약** — 삭제된 행이 유니크 제약을 계속 점유해 "탈퇴했는데 재가입이 안 돼요"가 되는 실무 함정. 삭제를 "행 제거"가 아닌 도메인 상태로 다룰 때의 대가를 설계에
  반영하는지 본다.
- **JPA Auditing의 동작과 한계** — 생성/수정 이력이 리스너(영속성 컨텍스트 이벤트) 기반이라 벌크 연산·네이티브 쿼리에서는 조용히 빠진다는 것을 아는지 — "자동으로 되는 것"의 동작 경로를 알아야
  안 되는 경우도 예측할 수 있다. 감사 요구(16장)가 있는 데이터라면 이 구멍이 곧 컴플라이언스 이슈다.

## 4. RDB / SQL / 데이터 모델링

### 기본 ⭐

- **인덱스와 B+Tree** — "인덱스 걸면 빨라진다"는 다 알지만, 구조를 알아야 "왜 이 쿼리는 인덱스를 못 타는지", "인덱스가 쓰기를 얼마나 느리게 하는지"를 추론할 수 있다. 인덱스 설계는 백엔드가
  매주 하는 일이라 추론 능력이 곧 생산성이다.
- **인덱스가 있는데 풀스캔** — 함수 적용, 타입 불일치, 낮은 선택도 등 원인이 다양한데, 이 목록이 머리에 있는 사람은 슬로 쿼리를 5분 만에 고치고 없는 사람은 "인덱스 있는데 왜 느리지"에서 멈춘다.
- **클러스터드 vs 세컨더리 인덱스** — InnoDB에서 PK 선택이 왜 성능 결정인지(세컨더리 인덱스가 PK를 품는 구조), UUID PK가 왜 문제인지가 여기서 나온다. 테이블 설계 첫 단추의 근거를
  확인한다.
- **정규화/반정규화 기준** — 교과서 정규화만 아는 사람과 "조회 패턴에 맞춰 의도적으로 중복을 허용하고 그 대가(갱신 정합성)를 관리"해본 사람을 구분한다. 대용량 조회 시스템은 반정규화 없이 성립하지
  않는다.
- **ACID** — 개념 암기가 아니라, 이후 꼬리 질문("그럼 커밋 순간 서버가 죽으면 D는 어떻게 보장되나요")의 발판. 각 글자를 실제 메커니즘(redo log, undo, 락/MVCC)과 연결하는지로
  깊이를 잰다.
- **JOIN 종류와 실행 방식** — LEFT JOIN을 써야 할 곳에 INNER를 써서 데이터가 조용히 누락되는 버그는 리뷰에서 잡아야 한다. 실행 방식(NL/Hash)은 "조인이 왜 느린가"를 실행 계획에서
  읽는 기초.
- **WHERE vs HAVING** — 집계 전/후 필터의 구분이 안 되면 통계 쿼리에서 틀린 숫자를 만들고, 틀린 숫자는 틀린 비즈니스 판단으로 이어진다.

### 중급 ⭐⭐

- **복합 인덱스 컬럼 순서** — 인덱스를 "거는" 것과 "설계하는" 것의 차이가 여기서 갈린다. 등호 조건 먼저·범위 조건 뒤 같은 원칙을 쿼리 패턴에서 도출할 수 있어야, 테이블당 인덱스 수를 늘리지 않으면서
  여러 쿼리를 커버하는 설계가 가능하다.
- **커버링 인덱스** — 랭킹·목록 조회 같은 고빈도 쿼리를 디스크 접근 없이 처리하는 핵심 기법. 아는 사람은 같은 하드웨어에서 몇 배의 처리량을 뽑는다.
- **EXPLAIN 읽기와 개선 프로세스** — 느린 쿼리 개선을 "인덱스 추가해봄 → 빨라짐"이 아니라 측정→가설→검증의 사이클로 수행하는지. 프로세스를 묻는 이유는 이 능력이 쿼리를 넘어 모든 성능 문제에
  이식되기 때문이다.
- **MVCC** — "읽기는 왜 락을 안 잡는가"를 이해해야 격리 수준, 락 경합, undo 폭증(긴 트랜잭션의 해악) 같은 운영 이슈가 전부 연결된다. RDB 내부 이해의 허리에 해당하는 개념.
- **갭 락과 데드락** — "INSERT만 하는데 데드락"이라는, 원리를 모르면 이해 불가능한 운영 현상의 정체. 데드락 로그를 읽고 원인 트랜잭션 쌍을 특정하는 실무 능력과 직결된다.
- **깊은 페이지네이션** — 관리자 페이지나 크롤러가 유발하는 고전적 부하 패턴. offset의 비용 구조를 알아야 커서 기반으로 재설계할 수 있고, 이는 API 스펙 변경까지 수반하므로 미리 아는 것의 가치가
  크다.
- **무중단 DDL** — "컬럼 하나 추가"가 수억 건 테이블에서는 서비스 중단 리스크임을 아는지. 이 감각이 없는 사람은 운영 DB에 습관처럼 ALTER를 날려 사고를 낸다. 스키마 변경 절차를 갖춘 팀에서
  일해봤는지도 드러난다.
- **커넥션 수와 처리량** — "느리니까 커넥션을 늘리자"는 직관이 왜 역효과인지(경합 증가)를 아는지. 병목의 위치를 확인하지 않은 처방이 얼마나 위험한지에 대한 감각을 검사한다.
- **긴 트랜잭션의 해악** — undo 누적으로 인한 조회 성능 저하, 락 점유 시간, 복제 지연까지 — "트랜잭션은 짧게"라는 격언의 실제 근거를 메커니즘으로 아는지. 트랜잭션 범위 안에 파일 처리·외부 호출을
  넣은 코드를 리뷰에서 잡는 눈이기도 하다(2장 고난이도와 같은 뿌리).
- **total count의 비용** — COUNT는 조건에 맞는 전체를 세야 해서 목록 조회 본체보다 비싼 경우가 많다. "전체 몇 건 중 몇 페이지" UI가 기술적으로 얼마나 비싼 요구인지 알고 근사치·카운트
  캐싱·무한 스크롤 같은 대안을 기획과 협상해봤는지 — 요구사항의 비용을 알려주는 것까지가 백엔드의 일임을 아는지 본다.
- **JSON 컬럼의 사용 기준** — 스키마 유연성의 편의와 그 대가(인덱싱 제약, 타입 안전 상실, 조회 최적화 어려움)를 아는지. "정규화가 귀찮아서 JSON"과 "진짜 비정형 속성이라 JSON"을 구분하는
  설계 규율의 표본.
- **SELECT FOR UPDATE의 락 범위** — 조건이 인덱스를 못 타면 스캔한 행 전부에 락이 걸려 "한 건 잠그려다 테이블을 세우는" 사고가 난다. 락을 "무엇을 잠그는가"가 아니라 "어떻게 찾은 행을
  잠그는가"로 이해하는지 — 실행 계획과 락이 결합되는 한 단계 깊은 이해를 확인한다.
- **LIKE '%…%'와 검색 전환 기준** — 중간 일치 검색이 인덱스 구조상 불가능함을 알고, 풀텍스트 인덱스로 버틸 수 있는 규모와 검색 엔진 도입(운영 비용, 동기화 문제 — 12장)의 문턱을
  판단하는지 — "검색 기능 추가해주세요"라는 흔한 요구의 숨은 비용을 산정하는 능력이다.
- **통계 조회의 분리** — 무거운 집계 쿼리 하나가 운영 트랜잭션의 락·버퍼·CPU를 잠식하는 것은 "기능은 다른데 자원은 공유"하는 문제의 전형이다. 실시간 요구를 되물어(하루 지연 허용 가능?) 사전
  계산으로 내리는 협상까지 — OLTP와 OLAP를 분리하는 감각(12장 CQRS의 실용 판)을 확인한다.
- **"변경 없음"의 검증** — 의도 2(장애 상황 판단)의 대표 형식. "배포 안 했는데요"는 코드 변경만 본 말이고, 시스템은 데이터 증가·통계 갱신·인접 배치·외부사 변경·인프라 작업으로 매일 변한다. "
  변경 없음"이라는 전제 자체를 의심하고 변경의 정의를 넓혀 조사하는지 — 진단의 첫 갈림길에서 방향을 잡는 능력을 본다.

### 고난이도 ⭐⭐⭐

- **초고빈도 카운터 갱신** — 같은 행 UPDATE의 락 직렬화라는 병목을 인식하고, 버퍼링·배치 반영·근사치 허용 같은 완화책과 그 대가(실시간성, 유실 가능성)를 비즈니스와 협상하는 능력. 웹툰 조회수는
  정확히 이 문제라 도메인 적합성 검증이기도 하다.
- **샤딩 시점과 샤드 키** — 샤드 키는 한번 정하면 되돌리는 비용이 거의 재구축급인 비가역 결정. "무엇으로 나눌 것인가"에 조회 패턴, 분포 균형, 리샤딩 계획까지 넣어 사고하는지 — 아키텍트로 성장할
  재목인지 본다.
- **수억 건 삭제/아카이빙** — DELETE 한 방이 undo 폭증·복제 지연·락으로 장애가 되는 것을 아는지. "작업을 운영에 안전하게 수행하는 방법"(청크 분할, 파티션 드랍) 자체가 시니어의 기술임을
  확인한다.
- **유니크 채번 설계** — Auto Increment의 한계(샤딩, 노출 위험)에서 출발해 Snowflake/UUID v7의 트레이드오프(정렬성, 인덱스 지역성)까지 — 작은 주제 하나에 분산 시스템 지식이
  압축돼 있어 깊이 측정에 효율적이다.
- **"결제됐는데 주문이 없다" 정합성 사고** — 실제 장애 시나리오를 그대로 던져 원인 가설 수립(트랜잭션 경계, 웹훅 유실, 부분 실패)과 재발 방지 설계를 동시에 시키는 질문. 사고 대응의 전체 사이클을
  수행할 수 있는지 본다.
- **DB failover 중 애플리케이션 동작** — 인프라가 복구를 해줘도 애플리케이션이 커넥션을 못 갈아타면 장애는 계속된다. "내 코드 밖에서 벌어지는 일"까지 책임 범위로 보는 시야를 확인한다.

### 알면 좋은 +α

- **ORDER BY의 인덱스 활용과 filesort** — 목록 조회의 기본형(WHERE+ORDER BY+LIMIT)에서 정렬이 인덱스를 못 타면 매 요청이 정렬 작업이 된다. WHERE 조건만 보고 인덱스를
  설계하는 반쪽 습관을 가리는 질문.
- **DATETIME vs TIMESTAMP** — 타임존 처리·범위(2038년 문제)·기본값 동작의 차이는 22장의 시간 원칙이 스키마 레벨에 착지하는 지점이다. 컬럼 타입 선택 하나가 글로벌 확장의 발목을 잡는
  사례를 아는지 본다.
- **실행 계획의 갑작스러운 변경** — "코드도 쿼리도 안 바꿨는데 느려졌다"의 단골 원인(통계 정보 갱신, 데이터 분포 변화). DB를 정적인 계산기가 아니라 상태에 따라 판단이 바뀌는 시스템으로 이해하는지 —
  힌트로 고정하는 것의 트레이드오프까지 가면 상급이다.
- **대량 UPSERT의 부작용** — 편리한 한 방 쿼리가 AUTO_INCREMENT를 갱신에도 소모해 ID 고갈을 앞당기고, 갭 락과 얽혀 데드락을 만드는 것을 아는지 — 동기화·적재 배치의 단골 도구가 갖는
  숨은 비용까지 확인하고 쓰는 습관을 본다.
- **백업과 복구의 거리** — 복구를 한 번도 연습 안 한 백업은 없는 것과 같다(백업 파일 손상, 복구 절차 미숙, RTO 초과). PITR로 "삭제 사고 직전 시점"까지 돌아가는 시나리오를 그려봤는지 —
  데이터를 지키는 마지막 방어선의 실효성을 검증해본 운영 성숙도다.
- **FK 제약 실무 논쟁** — 대용량 환경에서 FK가 만드는 비용(락 전파, 마이그레이션 제약, 샤딩 불가)과 FK를 포기했을 때 잃는 최후 방어선을 양쪽 다 말할 수 있는지 — 교과서 규범과 실무 관행이
  충돌하는 지점에서 "우리 서비스의 조건"으로 결론을 내는 사고를 본다. 앱 레벨 검증 + 배치 정합성 점검으로 대체하는 체계까지 말하면 상급이다.

## 5. Redis / 캐싱

### 기본 ⭐

- **싱글 스레드인데 왜 빠른가** — 메모리 접근·이벤트 루프라는 구조적 이유를 알아야 "Redis에 O(N) 명령 하나가 전체를 블로킹한다"는 운영상 함정까지 연결된다. 빠른 이유와 느려지는 이유가 동전의
  양면임을 아는지 본다.
- **자료구조별 사용 사례** — Redis를 "빠른 Map"으로만 쓰는 사람과 Sorted Set으로 랭킹을, Set으로 중복 방지를 설계하는 사람의 활용 폭 차이. 도구의 표현력을 아는 만큼 설계 선택지가
  넓어진다.
- **캐시해도 되는 데이터의 기준** — 캐시 도입은 "정합성 완화"라는 비용을 지불하는 결정이다. 잔액을 캐시하면 안 되는 이유를 즉답 못 하는 사람에게 결제 시스템을 맡길 수 없다.
- **TTL과 eviction 정책** — maxmemory 도달 시 무슨 일이 벌어지는지(eviction? 쓰기 거부?) 모르고 운영하면, 메모리가 차는 날 캐시가 아니라 장애 발생기가 된다.
- **Look-aside 패턴** — 기본 패턴의 흐름을 알아야 그 패턴의 빈틈(미스 폭주, 갱신 경합)을 논할 수 있다. 이후 고난이도 질문들의 공통 기반.

### 중급 ⭐⭐

- **캐시 스탬피드** — 인기 키 하나의 만료가 DB를 뚫는 이 현상은 "트래픽이 많아야만 존재하는 문제"의 대표라, 대용량 경험의 진위를 가리는 데 효과적이다. 해결책을 여러 개 아는지보다 문제의 발생 조건을
  정확히 그리는지를 본다.
- **캐시-DB 정합성, 갱신 vs 삭제** — 순서 역전(늦게 도착한 옛 값이 캐시를 덮는)까지 언급하는지로 분산 환경의 타이밍 문제를 사고할 수 있는지 잰다. "삭제가 안전한 이유"를 논증하는 과정이 곧 동시성
  사고력 시연이다.
- **RDB vs AOF** — "Redis 재시작하면 데이터 어떻게 되나요"라는 운영 질문에 답할 수 있는지. 캐시 용도면 유실 허용, 대기열이면 불가 — 용도별로 다른 답을 내는지 본다.
- **Sentinel vs Cluster / 해시 슬롯 제약** — Cluster 전환 시 멀티 키 연산(MGET, 트랜잭션)이 깨지는 것은 "인프라 확장이 애플리케이션 코드를 바꾸는" 사례다. 확장 계획을 세울
  때 이 제약을 미리 아는 사람과 전환 후에 아는 사람의 차이는 크다.
- **Sorted Set 랭킹 설계와 한계** — 실시간 인기 웹툰은 이 회사의 실제 기능이다. 기본 설계에 더해 "시간 윈도우는 어떻게? 수억 멤버면?"의 한계 인식까지 가는지 — 도구 적용과 규모 검증을 함께
  하는 습관을 본다.
- **세션 저장소로서의 Redis** — stateless 확장의 전제 조건. Redis 장애 = 전 사용자 로그아웃이라는 폭발 반경을 인식하고 가용성 대책과 함께 말하는지 확인한다.
- **KEYS 금지와 SCAN** — 운영 Redis에 KEYS 한 방으로 전 서비스가 수 초 멈춘 사고는 업계 단골이다. "편한 명령의 시간 복잡도"를 확인하는 습관 — 사고를 안 쳐본 티가 나는지 본다.
- **Hot key** — 클러스터로 분산해도 인기 키 하나는 한 노드에 몰린다는, "분산 = 해결"이라는 착각을 깨는 질문. 감지 방법(모니터링)까지 답하는지로 운영 감각을 잰다.
- **캐시 키 설계와 버저닝** — 배포로 캐시 객체 구조가 바뀌면 구버전 데이터의 역직렬화 실패가 배포 직후 장애로 나타난다. 키에 버전을 넣어 신구가 공존하게 하는지 — 캐시를 "저장소"가 아니라 "배포와 함께
  움직이는 계약"으로 다루는지 본다. 롤링 배포 중 신구 코드가 같은 캐시를 읽는 순간까지 상상하면 상급.
- **TTL 캐시 PR 리뷰** — 캐시 스탬피드 개념 문항과 짝을 이루는 의도 1(상황 인지)의 검사. "지금 잘 동작하는 코드"에서 트래픽 조건이 바뀌었을 때의 붕괴 지점(동시 만료, 미스 폭주)을 배포 전에
  말할 수 있는지 — 지식이 리뷰 코멘트라는 실행 가능한 형태로 나오는지 본다.

### 고난이도 ⭐⭐⭐

- **분산 락의 함정** — TTL 만료 후에도 자기가 락 주인인 줄 아는 프로세스, 남의 락 해제 — 이 함정들은 "락을 얻었다"는 착각 속에 정합성을 조용히 깬다. Redlock 논쟁에 견해를 묻는 건 정답이
  아니라 "안전성과 실용성의 트레이드오프에 자기 기준이 있는지"를 보기 위해서다.
- **선착순 쿠폰 10만 건** — 정확성(원자적 카운트), 내구성(Redis 유실 시), 공정성, DB 반영의 비동기화까지 — 한 문제에 이 섹션 전체 지식을 조합해야 한다. 지식의 보유가 아니라 조합 능력을
  보는 설계 질문.
- **Redis OOM 시나리오** — "캐시가 죽으면 서비스가 어떻게 되는가"를 미리 그려보고 방어(메모리 알람, eviction 정책, 키 TTL 규율)를 깔아두는 운영 성숙도를 확인한다.
- **캐시 무력화 시 DB 보호** — 캐시는 언젠가 죽는다는 전제에서 출발하는지. 캐시 장애가 곧 DB 장애가 되는 구조라면 캐시는 가용성을 높인 게 아니라 장애 지점을 추가한 것 — 이 역설을 이해하는지 본다.
- **2단 캐시와 무효화 전파** — 로컬 캐시의 노드 간 불일치라는 새 문제를 감수할 만큼 이득이 큰 상황(초고빈도 읽기)을 판별하고, pub/sub 무효화 같은 해법의 불완전함(유실 시 불일치 지속)까지
  짚는지 — 복잡도를 추가하는 결정의 신중함을 잰다.

### 알면 좋은 +α

- **Pipeline / MGET / MULTI 구분** — Redis 성능의 실제 지배 요인이 명령 처리 속도가 아니라 네트워크 왕복임을 아는지. 루프 안에서 GET을 N번 치는 코드를 리뷰에서 잡는 눈이다.
- **Lua 스크립트의 원자성** — check-then-act(조회 후 조건부 갱신)를 원자화하는 실무 도구(쿠폰 발급, 락 소유자 검증 해제). 동시에 긴 스크립트가 싱글 스레드 전체를 세우는 양날임을 아는지
  본다.
- **Big key와 UNLINK** — 수백만 멤버 컬렉션은 조회·삭제·마이그레이션 전부를 블로킹 폭탄으로 만든다. big key는 지우는 법(UNLINK, 점진 삭제)보다 만들어지기 전에 키 설계로 막는 것임을
  아는지.
- **Streams vs Pub/Sub** — pub/sub은 구독자가 없던 순간의 메시지가 그냥 사라진다는 유실 특성을 아는지 — "유실 허용 여부"라는 요구사항 축으로 기능을 고르는 판단력이고, 6장
  Kafka와의 선긋기이기도 하다.
- **HyperLogLog / Bitmap** — 수천만 UV를 12KB로 세는 확률 자료구조의 존재를 아는지 — "정확한 답이 꼭 필요한가"를 되물어 비용을 수백 배 줄이는 발상이다. 정확도(±0.8%)를
  비즈니스와 협상 가능한 파라미터로 다루는 감각을 본다.
- **Cold cache와 캐시 워밍** — 캐시 히트율을 전제로 용량이 설계된 시스템은 캐시가 빈 순간 DB가 원래 트래픽을 그대로 맞는다. 배포·장애 복구 절차에 "캐시 상태"라는 축이 들어 있는지 — 캐시
  무력화 방어(고난이도 문항)와 같은 뿌리의 운영 감각이다.
- **MULTI/EXEC와 WATCH vs Lua** — MULTI는 원자적 일괄 실행일 뿐 중간 조회 결과로 분기할 수 없다는 제약(그래서 check-then-act는 WATCH나 Lua가 필요)을 아는지 — "
  트랜잭션"이라는 같은 단어가 RDB와 Redis에서 전혀 다른 보장임을 구분하는 정밀함을 본다.

## 6. Kafka / 메시징 / 이벤트 기반 아키텍처

### 기본 ⭐

- **MQ 도입 이유와 동기 호출 대비 트레이드오프** — "비동기로 하면 좋다"가 아니라 잃는 것(즉시 정합성, 흐름 추적 난이도, 실패 처리 복잡도)을 함께 말하는지. 도입 결정의 양면을 보는 습관은 모든
  아키텍처 논의의 입장권이다.
- **Kafka 기본 구성요소** — 이후 모든 논의(순서, 병렬성, 재처리)의 어휘. 특히 파티션이 "순서 보장 단위이자 병렬성 단위"라는 이중성을 짚는지가 이해도의 척도다.
- **파티션과 컨슈머 수의 관계** — "컨슈머를 늘렸는데 처리량이 안 늘어요"라는 실제 상황의 원인. 스케일 아웃의 상한이 설계 시점(파티션 수)에 결정된다는 것을 알아야 처음부터 맞게 잡는다.
- **Kafka vs RabbitMQ** — 로그 기반(재소비 가능) vs 큐 기반(소비 후 삭제)의 구조 차이가 "재처리가 필요한가"라는 요구사항과 어떻게 연결되는지 — 요구사항→기술 매핑 능력을 본다.
- **오프셋 커밋과 자동 커밋의 위험** — 처리 전 커밋(유실) vs 처리 후 커밋(중복)이라는 선택이 존재함 자체를 아는지. 이 선택을 의식하지 않고 기본값으로 운영하는 시스템은 유실이 나도 원인을 모른다.

### 중급 ⭐⭐

- **순서 보장 단위와 키 설계** — "사용자별 이벤트 순서"라는 흔한 요구를 파티션 키로 푸는 것, 그리고 그 대가(키 편중 시 특정 파티션 병목)까지 — 요구사항을 인프라 메커니즘으로 번역하는 능력을
  확인한다.
- **전달 의미론과 exactly-once의 현실성** — "정확히 한 번"이 공짜가 아니며 대부분 at-least-once + 멱등 처리로 푼다는 실무 감각. 벤더 마케팅 용어와 실제 보장 범위를 구분하는 비판적
  시각을 본다.
- **재시도/DLQ 설계** — 실패 메시지 하나가 파티션 전체를 막는 poison pill 문제를 아는지. "실패하면 어떻게 되나"를 설계하지 않은 컨슈머는 반드시 운영에서 그 대가를 치른다 — 실패 경로 설계
  습관의 검증.
- **리밸런싱과 처리 중 메시지** — 배포할 때마다 중복 처리가 발생하는 이유의 정체. 리밸런싱을 모르면 "가끔 알림이 두 번 가요"라는 버그 리포트를 영원히 미제로 남긴다.
- **acks 설정과 내구성** — 처리량과 유실 위험의 다이얼이 프로듀서 설정 하나에 있다는 것. 결제 이벤트와 로그 이벤트에 다른 값을 쓰는 근거를 말할 수 있는지 — 데이터 중요도별 차등 설계 감각을 본다.
- **멱등 컨슈머 구현** — at-least-once 세계에서 중복은 예외가 아니라 정상 동작이다. 처리 이력 기반 중복 제거의 구현 디테일(키 선정, 저장소, 원자성)까지 들어가는지로 실전 경험을 가린다.
- **Outbox + CDC** — DB와 메시지 브로커라는 두 시스템에 걸친 원자성 문제의 표준 해법을 아는지. 이 패턴의 필요성을 스스로 설명할 수 있으면 분산 정합성의 핵심을 이해한 것이다.
- **파티션 수 산정** — 파티션은 나중에 늘리면 키 순서가 깨지고(고난이도 문항), 처음부터 과하게 잡으면 브로커 메타데이터·복제 부담이 커진다. "목표 처리량 ÷ 컨슈머 단일 처리량 + 성장 여유"라는 산정
  논리를 갖고 있는지 — 비가역에 가까운 설정을 설계 시점에 계산하는 습관을 본다.
- **컨슈머 단일 처리량 향상과 오프셋 커밋** — 배치 폴링·내부 병렬화로 처리량을 올릴 때 커밋 시점이 어긋나면 유실이나 중복이 생긴다. "병렬화가 전달 보장을 깨는 지점"을 인식하는지 — 처리량과 정확성의
  트레이드오프를 컨슈머 구현 레벨에서 다뤄봤는지 확인한다.
- **Fat vs thin 이벤트** — 의도 3(비가역 결정)의 이벤트 설계 판. 페이로드 형태는 모든 컨슈머가 의존하는 계약이라 나중에 바꾸면 전 소비자가 흔들린다. fat은 소비자 자립(역조회 불필요) 대신
  스키마 결합·개인정보 전파, thin은 느슨함 대신 조회 부하·시점 불일치 — 초기 결정 하나가 1년 뒤의 결합도와 장애 모드를 결정함을 아는지 본다.

### 고난이도 ⭐⭐⭐

- **컨슈머 랙 증가 대응** — 랙은 "지금 사용자에게 알림이 30분 늦게 가고 있다"는 뜻이다. 원인(처리 속도, 파티션 편중, 다운스트림 지연)의 분기 진단과 단기/장기 대응 분리 — 진행 중인 성능 저하를
  다루는 실전 능력을 본다.
- **파티션 증설의 부작용** — "늘리면 되지"가 키 재배치로 순서 보장을 깨는 것을 아는지. 쉬워 보이는 운영 작업의 숨은 파급을 확인하는 습관 — 이게 없으면 확장 작업이 정합성 사고가 된다.
- **스키마 진화** — 이벤트는 발행자와 소비자가 다른 팀·다른 배포 주기라서, 스키마 변경 하나가 남의 서비스를 깬다. API 하위 호환성 개념을 비동기 세계로 확장해 사고할 수 있는지 본다.
- **대량 재처리와 실시간 격리** — 장애 복구로 100만 건을 replay할 때 실시간 트래픽까지 밀리게 하면 2차 장애다. 복구 작업 자체의 안전성을 설계하는, 한 단계 위의 운영 사고를 확인한다.
- **최종 일관성의 UX 문제** — "구매했는데 이용권이 아직 안 보여요"를 기술 문제이자 제품 문제로 다루는지. 기획자와 "몇 초까지 허용 가능한가"를 협상하는 역할까지 백엔드의 일임을 아는 사람인지 본다.
- **Saga와 보상 트랜잭션** — 분산 트랜잭션의 실무 대안을 아는 것에 더해, 보상의 함정(보상 자체의 실패, 보상 불가능한 동작 — 이미 발송된 알림)까지 짚는지 — 해법의 한계를 아는 것이 진짜 이해의
  증거다.

### 알면 좋은 +α

- **max.poll.interval.ms vs session.timeout.ms** — "컨슈머가 자꾸 쫓겨나며 리밸런싱이 반복되는" 실무 단골 장애의 원인 분기(처리가 느림 vs 하트비트 끊김). 두 타임아웃의
  구분이 곧 진단 능력이다.
- **Log compaction** — 리텐션(시간 기반 삭제)과 다른 "키별 최신값 보존" 모델을 아는지 — 상태 스냅샷·CDC 토픽의 기반으로, Kafka를 큐가 아니라 로그 저장소로 이해하는 깊이의 표본.
- **대용량 페이로드 (claim check)** — 브로커는 대형 바이너리 운반용이 아니다. 본문은 오브젝트 스토리지에 두고 참조만 이벤트로 흘리는 패턴을 아는지 — 도구의 설계 전제를 벗어나는 요구를 패턴으로
  우회하는 능력을 본다.

## 7. 대용량 트래픽 / 성능 최적화

### 기본 ⭐

- **처리량 vs 지연시간, p99를 보는 이유** — 평균만 보는 사람은 "평균 50ms인데 왜 유저가 느리대요?"에서 막힌다. 상위 백분위가 실제 사용자 경험이고 장애의 전조라는 것 — 성능을 "측정하는 언어"
  를 공유할 수 있는지가 성능 업무 참여의 전제다.
- **scale-out vs scale-up의 한계** — "서버 늘리면 되죠"가 통하지 않는 지점(DB, 상태 공유)을 아는지. 확장의 병목이 결국 상태 있는 계층으로 수렴한다는 인식이 아키텍처 논의의
  출발점이다.
- **로드밸런서 역할과 알고리즘** — least connection이 필요한 상황(요청별 처리 시간 편차)을 아는지 — LB를 블랙박스로 두면 "특정 서버만 부하가 몰리는" 현상을 영원히 못 푼다.
- **Stateless 설계와 세션 처리** — 오토스케일링의 전제 조건. 로컬 상태(메모리 세션, 로컬 파일)가 하나라도 있으면 스케일 아웃이 버그 발생기가 된다는 것을 배포 전에 아는 사람인지 확인한다.
- **CDN과 웹툰 이미지 서빙** — 이 도메인에서 트래픽의 대부분은 이미지다. 오리진까지 오는 트래픽을 구조적으로 줄이는 계층을 이해해야 "서버 최적화보다 캐시 히트율 1% 올리는 게 크다" 같은 우선순위
  판단이 가능하다.

### 중급 ⭐⭐

- **API가 느려졌을 때 병목 추적 전 과정** — 이 질문의 진짜 목적은 방법론이다: 어디부터 보는지(지표 → 구간 분해 → 프로파일링), 추측인지 측정인지. 체계 없이 "코드를 봤어요"로 시작하는 사람은
  실전에서 몇 시간을 낭비한다.
- **부하 테스트 설계** — 목표 TPS를 어디서 얻는지(실측 피크 × 성장 계수), 시나리오가 실제 트래픽 패턴을 닮았는지 — 형식적 부하 테스트와 의미 있는 부하 테스트를 구분해본 사람인지 가린다.
- **Rate limiting 알고리즘과 분산 구현** — 알고리즘 비교보다, 분산 환경에서 "서버별 로컬 카운트의 합이 전체 한도를 넘는" 문제를 인지하는지가 핵심. 단일 서버 지식을 분산으로 확장할 때 무엇이
  깨지는지 보는 사고 실험이다.
- **서킷 브레이커 상태 전이와 튜닝** — 도입은 쉽지만 임계값을 잘못 잡으면 정상 트래픽을 차단하거나(과민) 장애 전파를 못 막는다(둔감). "패턴 적용"과 "패턴 튜닝"의 차이 — 운영까지 해봤는지를 가린다.
- **타임아웃 설정 기준** — 타임아웃 없는 외부 호출은 시한폭탄이고, 너무 긴 타임아웃은 스레드를 인질로 잡는다. 전 구간(connection/read/전체)의 타임아웃 예산을 계산해본 사람인지 — 연쇄 장애
  방어의 첫 번째 나사다.
- **재시도가 장애를 증폭시키는 메커니즘** — 장애 중인 서버에 재시도 폭탄이 떨어져 복구를 막는 retry storm은 "선의의 코드가 장애를 키우는" 대표 사례다. backoff+jitter를 아는지보다 이
  역설을 인식하는지가 중요하다.
- **대량 푸시/알림 발송 설계** — 발송 자체보다 발송이 유발하는 2차 트래픽(알림 받은 수백만 명이 동시 접속)까지 그리는지 — 시스템 바깥의 피드백 루프를 보는 시야를 확인한다.
- **정시 트래픽 스파이크 대비** — 예측 가능한 스파이크는 준비 안 하면 그냥 태만이다. 계층별(CDN, 캐시 사전 워밍, 사전 스케일 아웃) 대비를 시간 축까지 넣어 말하는지 — 이 회사의 매일 밤 실제
  상황이므로 도메인 적합성 검증이기도 하다.

### 고난이도 ⭐⭐⭐

- **대기열 시스템 설계** — 수요가 공급을 초과할 때 "전원 수용 불가"를 인정하고 실패를 공정하고 우아하게 배분하는 설계. 시스템 한계를 인정하는 데서 출발하는 사고 — 무한 확장 환상이 없는지 본다.
- **Graceful degradation** — "추천이 죽으면 인기순이라도 보여준다"처럼 기능별 중요도를 나누고 비핵심의 실패를 격리하는 설계는, 장애 시 "전체 다운"과 "일부 기능 저하"의 차이를 만든다.
  장애를 이분법(정상/다운)이 아닌 스펙트럼으로 사고하는지 확인한다.
- **백프레셔** — 유입 속도 > 처리 속도가 지속되면 큐가 어딘가에서 터진다는 보존 법칙. 이를 아는 사람은 "큐를 키우자"가 해결이 아니라 지연임을 알고, 유입 제한이나 처리 확장 중에서 답을 찾는다.
- **자원 한계와 Little's Law** — 풀 크기·큐 크기를 감이 아니라 산수(L = λW)로 정하는지. 용량 계획 회의에서 "그냥 넉넉하게요"가 아니라 계산된 숫자를 내는 능력의 유무.
- **Cascading failure 메커니즘과 방어** — 대형 장애의 대부분은 단일 원인이 아니라 전파다. 전파 경로(스레드 고갈 → 상류 적체)를 그릴 수 있어야 방어벽(bulkhead, 타임아웃, 서킷)을
  어디에 세울지 정할 수 있다 — 대규모 시스템 운영자의 핵심 심성 모델.
- **조회수 집계 파이프라인** — 정확성·실시간성·부하의 3자 트레이드오프를 비즈니스 요구("조회수가 1 정도 틀려도 되는가")와 협상하며 설계하는지. 기술 선택 이전에 요구사항의 완화 가능 지점을 찾는 습관을
  본다.
- **멀티 리전 트레이드오프** — 글로벌 서비스 포지션의 실무 그 자체. 물리 법칙(빛의 속도)이 만드는 하드 제약 안에서 데이터 배치를 결정해본, 혹은 사고할 수 있는 수준인지 확인한다.

### 알면 좋은 +α

- **Load shedding** — "모두에게 느린 서비스보다 일부를 빨리 거절하는 서비스가 낫다"는 반직관을 수용하는지. 무엇부터 버릴지(비핵심 API, 비로그인 트래픽)의 우선순위 결정이 곧 비즈니스
  이해도다.
- **오토스케일링 지표 선택** — I/O bound 서비스는 CPU가 낮은 채로 죽는다. HPA가 CPU 기준이면 스케일 아웃이 영원히 안 일어나는 상황 — 병목 자원과 스케일링 지표가 일치해야 함을 아는지
  본다.
- **부하 테스트와 운영의 괴리** — 작은 데이터셋, 워밍업된 캐시, 단순화된 시나리오가 만드는 거짓 합격. 측정 환경의 대표성을 의심하는 습관 — "테스트는 통과했는데 운영에서 터졌다"의 예방선이다.

## 8. 네트워크 / HTTP / 웹

### 기본 ⭐

- **URL 입력 후 일어나는 일** — 요청이 지나는 전체 경로의 지도를 갖고 있는지 보는 질문. 이 지도가 있어야 "어느 구간에서" 실패했는지 분해할 수 있다 — 모든 네트워크 디버깅의 밑그림.
- **TCP handshake / 종료** — 커넥션 수립 비용을 알아야 keep-alive와 커넥션 풀의 존재 이유가 이해되고, TIME_WAIT 같은 운영 현상이 종료 절차의 산물임을 안다. 외운 지식이 아니라
  뒤 개념들의 지반인지 확인한다.
- **TCP vs UDP** — 신뢰성의 비용(재전송, 순서 보장으로 인한 지연)을 이해하는지. "왜 실시간 스트리밍은 UDP 계열인가"에 답할 수 있으면 프로토콜을 요구사항에 맞춰 고르는 사고가 있는 것이다.
- **HTTP 메서드 멱등성** — 멱등성은 "네트워크 실패 시 재시도해도 되는가"라는 실무 질문의 근거다. GET을 상태 변경에 쓴 API가 프록시 프리페치로 데이터를 바꾸는 사고 — 규약 위반의 실제 대가를
  아는지 본다.
- **상태 코드 사용 기준** — 상태 코드는 클라이언트·모니터링·재시도 로직이 모두 의존하는 계약이다. 401/403 구분, 409의 활용을 정확히 하는 사람의 API는 장애 시 에러율 분류가 가능하고, 대충
  200에 에러 바디를 넣는 사람의 API는 모니터링이 눈뜬장님이 된다.
- **TLS handshake / 대칭·비대칭 키** — HTTPS 인증서 만료, 핸드셰이크 지연 같은 운영 이슈를 다룰 때의 기초. 비대칭으로 키 교환, 대칭으로 본문 암호화라는 구조를 알면 "TLS가 왜 첫
  요청만 느린가"류의 성능 질문도 풀린다.
- **쿠키/세션/토큰 인증 차이** — 인증 방식 선택은 확장성(서버 상태), 보안(탈취 대응), 클라이언트 종류(웹/앱)가 얽힌 실무 결정이다. IAM·인증 기능을 다루는 백엔드의 상시 업무.
- **CORS와 preflight** — 프론트엔드와 협업하는 백엔드가 가장 자주 받는 질문("CORS 에러 나요")에 원리로 답할 수 있는지. 원리를 모르면 스택오버플로 복붙 설정(`*` 허용)으로 보안 구멍을
  만든다.

### 중급 ⭐⭐

- **HTTP/1.1 → 2 → 3와 HOL blocking** — 프로토콜 버전이 이미지 수십 장을 싣는 웹툰 페이지의 로딩 특성을 바꾼다. 각 버전이 "무슨 문제를 풀었는지"의 흐름으로 이해하는 사람은 새
  프로토콜 도입 판단도 할 수 있다.
- **keep-alive / TIME_WAIT 대량 발생** — 커넥션을 재사용하지 않는 클라이언트 코드가 포트 고갈로 이어지는 실제 장애 패턴. netstat 출력에서 이상을 읽어내는 운영 능력과 직결된다.
- **502 vs 504 구분** — 상태 코드 하나가 "백엔드가 죽었다"와 "백엔드가 느리다"를 갈라준다. 장애 첫 1분에 보는 방향을 정해주는 지식 — 초동 대응 속도의 차이를 만든다.
- **Nginx의 역할과 이벤트 기반 구조** — 요청이 앱에 도달하기 전 계층에서 무슨 일이 벌어지는지 모르면, 앱 로그에 아무것도 없는 장애(Nginx에서 반려된 요청) 앞에서 속수무책이다.
- **Nginx-Tomcat 타임아웃 불일치** — 계층 간 설정 불일치가 만드는 유령 현상(업로드가 특정 크기에서만 실패, 간헐적 502)의 정체. 시스템을 계층 스택 전체로 보는 시야를 확인한다.
- **웹소켓/SSE/폴링 선택** — 실시간성 요구(댓글, 알림)를 구현 비용·인프라 제약(LB의 장수 커넥션 처리)과 함께 판단하는지 — "요구사항의 실시간이 진짜 몇 초 수준인지"를 되묻는 사람인지 본다.
- **대용량 파일 업로드/다운로드** — 파일을 서버 메모리에 통째로 올리는 코드는 파일이 크면 OOM이다. 스트리밍과 presigned URL(서버를 우회시키는 설계)을 아는지 — 데이터가 흐르는 경로 자체를
  설계하는 능력.

### 고난이도 ⭐⭐⭐

- **L4 vs L7 LB** — 어느 계층에서 라우팅하느냐가 가능한 기능(경로 기반 분기, 쿠키 스티키니스)과 성능을 결정한다. 인프라 팀과 트래픽 구성을 논의할 때 필요한 공용어.
- **TLS termination 위치** — 보안(내부 구간 평문)과 성능(암복호화 오프로드), 운영(인증서 관리 지점)의 3자 트레이드오프. 정답이 없는 구성 결정을 근거로 논할 수 있는지 본다.
- **간헐적 timeout의 네트워크 계층 추적** — 애플리케이션 로그에 안 남는 문제를 tcpdump까지 내려가 잡는 능력은 흔치 않고, 이게 되는 사람은 팀에서 "미제 사건 해결사"가 된다. 스택 아래로
  내려가길 두려워하지 않는지 확인한다.
- **DNS TTL과 failover의 함정** — "DNS 바꿨는데 왜 아직 옛 서버로 오지?"라는, 전환 작업 때마다 등장하는 현상. 캐싱 계층이 곳곳에 있는 인터넷의 실제 동작을 아는지 — 재해 복구 계획의
  현실성을 검증한다.

### 알면 좋은 +α

- **HTTP 캐싱 헤더와 304** — CDN·브라우저 캐시는 백엔드가 내려주는 헤더로 조종된다. 콘텐츠 서비스에서 Cache-Control 설계는 성능 도구이자, 잘못 쓰면 개인화 응답이 공유 캐시에 남는 보안
  사고의 원인 — 양면을 다 아는지 본다.
- **응답 압축의 트레이드오프** — CPU와 대역폭의 교환이며, 이미 압축된 포맷(이미지)엔 낭비임을 아는지 — "켜면 좋은 옵션"에도 비용 계산을 하는 습관의 표본.
- **X-Forwarded-For와 실제 클라이언트 IP** — 스푸핑 가능한 헤더를 그대로 믿으면 rate limit·차단·감사 로그가 전부 우회된다. "신뢰 경계 밖에서 온 값"이라는 감각을 네트워크 헤더에도
  적용하는지 본다.

## 9. REST API 설계

### 기본 ⭐

- **RESTful 설계 원칙과 리소스 네이밍** — API는 한번 공개되면 바꾸기 어려운 장기 계약이다. 원칙의 준수 여부보다, 일관성이 클라이언트 개발자의 예측 가능성(= 협업 속도)을 만든다는 이유를 아는지
  본다.
- **PUT vs PATCH** — 전체 교체와 부분 수정의 구분이 흐리면 "안 보낸 필드가 null로 덮이는" 데이터 유실이 API 계약 수준에서 발생한다. 시맨틱을 지키는 규율의 표본 검사.
- **API 버저닝 전략** — 버저닝은 "미래의 변경"을 지금 설계하는 일이다. 전략 없이 시작한 API가 v2를 내야 할 때 겪는 고통을 아는지 — 미래 비용을 앞당겨 사고하는 습관을 본다.
- **offset vs 커서 페이지네이션** — 성능(4장)에 더해, 실시간으로 데이터가 추가되는 목록에서 offset이 중복/누락을 만드는 정확성 문제까지 아는지 — 피드형 서비스의 필수 지식.
- **에러 응답 표준화** — 에러 스펙이 제각각이면 클라이언트마다 파싱 분기가 생기고, 장애 시 에러 원인 분류가 불가능하다. API를 "혼자 만드는 것"이 아니라 "여러 팀이 소비하는 제품"으로 보는지
  확인한다.

### 중급 ⭐⭐

- **결제 API 멱등성 키** — 네트워크는 반드시 실패하고 클라이언트는 반드시 재시도한다는 전제에서, 중복 결제를 API 계약 수준에서 차단하는 설계. 이 개념 없이 결제 API를 만든 팀은 반드시 이중 결제
  CS를 받는다 — 결제 포지션의 필수 검증.
- **Chatty API 개선** — 모바일 환경(높은 왕복 지연)에서 API 호출 수가 곧 체감 속도다. 백엔드 편의(리소스별 단순 API)와 클라이언트 효율의 긴장을 인식하고 조율해본 경험을 본다.
- **하위 호환 변경 원칙** — 내 배포가 남의 앱을 깨는 구조(특히 강제 업데이트 불가능한 모바일)에서 일해봤는지. "필드 삭제는 왜 위험하고 추가는 왜 안전한가"를 소비자 관점에서 설명하는지 확인한다.
- **외부 파트너 API vs 내부 API** — 신뢰 경계가 바뀌면 설계가 바뀐다(인증 강화, rate limit, 문서가 곧 계약). 콘텐츠 연동 업무의 실제 형태라, 외부와의 기술 계약을 다뤄본 경험을
  검증한다.
- **긴 작업의 REST 표현** — HTTP 타임아웃 안에 못 끝나는 작업을 동기 API로 만들면 타임아웃과 재시도 중복 실행이 뒤엉킨다. 프로토콜의 제약을 설계로 수용하는(202 + 상태 조회) 능력을 본다.
- **REST vs GraphQL vs gRPC** — 유행이 아니라 소비자 특성(외부 공개냐, 내부 서비스 간이냐, 클라이언트 주도 조회냐)으로 선택하는지 — 기술 선택의 축이 "누가 쓰는가"에 있음을 아는지
  확인한다.

### 고난이도 ⭐⭐⭐

- **ETag/If-Match 낙관적 동시성** — 두 관리자가 같은 데이터를 편집하는 lost update를 API 계약으로 막는 설계. DB 락 지식을 HTTP 계층으로 번역할 수 있는지 — 계층을 넘나드는
  응용력을 본다.
- **Aggregation API의 부분 실패** — 5개 서비스 중 1개가 죽었을 때 전체 실패냐 부분 응답이냐는 기술이 아니라 제품 결정이며, 이를 프론트·기획과 협의해 스펙에 명시해본 경험을 확인한다.
- **게이트웨이 vs 서비스의 책임 경계** — 공통 관심사(인증, rate limit)의 위치 결정은 "게이트웨이가 비대해지면 그것이 새로운 모놀리스"라는 함정과의 균형이다. 시스템 전체의 책임 배치를 사고하는
  아키텍처 감각을 잰다.

### 알면 좋은 +α

- **API 문서-구현 동기화** — 문서가 한 번 거짓말하면 아무도 안 믿게 되고, 그때부터 협업은 슬랙 질문으로 회귀한다. 테스트에서 문서를 생성(REST Docs)하거나 계약을 우선하는 접근을 아는지 —
  문서를 신뢰 가능한 산출물로 관리하는 체계를 본다.
- **벌크 API의 부분 실패 응답** — 100건 중 3건 실패 시 전체 롤백인지 부분 성공인지는 클라이언트의 재시도 설계까지 바꾸는 계약 결정이다. 성공/실패 이분법을 넘어 응답 모델을 설계하는지 확인한다.
- **목록 조회의 필터·정렬 파라미터 설계** — 검색 조건은 요구사항이 끝없이 추가되는 영역이다. 파라미터 폭발을 계약으로 관리하고 허용 정렬 키를 인덱스와 연동해 제한하는지 — API 설계와 DB 설계를 함께
  쥐는 시야를 본다.
- **날짜/시간 포맷 규약** — 타임존 없는 문자열, 서버 로컬 시각, epoch 밀리초가 뒤섞인 API는 클라이언트마다 다른 해석을 낳고, 그 버그는 해외 사용자에게서만 발견된다(22장). 포맷 하나도 팀의
  계약으로 명문화하는지 — API 설계의 엄밀함이 가장 사소해 보이는 지점에서 드러난다.

## 10. 결제 / 정합성 (도메인 심화)

### 기본 ⭐

- **결제 상태 관리 설계** — 결제는 "요청과 완료 사이"의 중간 상태가 본질이다. 상태를 이진(성공/실패)으로 모델링한 시스템은 타임아웃·지연 승인 앞에서 반드시 무너진다 — 돈을 다루는 시스템 설계의 첫
  관문.
- **PG 연동 기본 고려사항** — 외부사는 느려지고, 중복 응답하고, 스펙과 다르게 동작한다는 전제를 갖고 있는지. "행복 경로만 구현한 연동"과 "방어적 연동"의 차이는 CS 건수와 정산 차액으로 드러난다.
- **웹훅 수신 처리 주의점** — 웹훅은 위조 가능하고(검증), 중복 오고(멱등), 순서가 뒤집힌다(상태 머신 검증). 셋 중 하나라도 빼먹으면 각각 보안 사고, 이중 지급, 상태 꼬임이 된다 — 수신부 설계의
  필수 체크리스트를 갖췄는지 본다.

### 중급 ⭐⭐

- **PG 타임아웃 — 결제됐는지 모르는 상태** — "성공도 실패도 아닌 상태"를 다루는 능력이 결제 개발자의 핵심 역량이다. 임의로 실패 처리(고객 돈만 나감)도 성공 처리(미수금)도 못 하며, 상태 조회
  API·보류 상태·후속 확인 배치로 푸는 과정을 설계할 수 있는지 — 이 질문 하나로 결제 경험의 진위가 갈린다.
- **차감 + 지급의 정합성** — 돈이 나가는 동작과 권리가 생기는 동작 사이의 원자성. 한 DB면 트랜잭션, 다른 시스템이면 순서(차감 먼저? 지급 먼저?)와 실패 시 복구까지 — 정합성 설계를 구체적 실패
  시나리오로 검증하는 습관을 본다.
- **취소/부분 취소/환불 상태 머신** — 취소는 결제보다 경우의 수가 많다(부분, 중복 취소 요청, 취소의 실패). 상태 머신으로 불가능한 전이를 차단하는 설계를 하는지 — 엣지 케이스를 열거하는 능력 자체를
  평가한다.
- **이중 지급 방어선 계층화** — 단일 방어(프론트 버튼 비활성화)만 믿는 사람과 UI→API 멱등성→DB 유니크 제약까지 다층으로 쌓는 사람의 차이. "각 방어선은 뚫린다"는 전제로 설계하는 심층 방어 사고를
  확인한다.
- **정산/대사 배치의 필요성** — 실시간 정합성 장치가 완벽해도 대사는 필요하다 — "우리 기록과 PG 기록은 반드시 어긋난다"는 현실 인정에서 출발하는지. 사후 검증 체계까지 갖춘 시스템을 만들어봤는지 본다.
- **AI 이체 코드의 머지 전 검증** — 의도 4(AI 산출물 검증)를 돈 도메인에서 시뮬레이션하는 질문. "테스트 통과"가 검증이 아닌 이유(동시 실행, 부분 실패, 중복 요청은 보통 테스트에 없다)를 알고,
  동시성→트랜잭션 경계→멱등성→예외 경로 순의 검증 우선순위를 갖고 있는지 — AI 시대 리뷰어의 실전 역량을 돈이 걸린 상황으로 압박해 본다.

### 고난이도 ⭐⭐⭐

- **분산 서비스 간 잔액 차감+주문+지급** — Saga의 교과서 지식을 돈 도메인의 현실(보상 실패 시 수동 개입 큐, 멱등성 키 전파)에 착지시킬 수 있는지. 아키텍처 패턴과 도메인 요구를 동시에 쥐고
  설계하는 시니어급 종합 문제.
- **부동소수점 금지와 통화/환율** — 0.1+0.2≠0.3이 실제 정산 차액이 되는 도메인. 글로벌 서비스의 통화별 소수점 자리, 환율 적용 시점 고정 같은 규칙이 "코드가 아니라 도메인 지식"임을 아는지 —
  글로벌 결제 포지션의 실무 검증.
- **복합 할인 배분과 부분 환불 역산** — 할인 3종이 섞인 주문의 부분 환불 금액 계산은 순수 로직 문제 같지만, 배분 규칙을 처음에 안 정하면 환불 때마다 1원 차이 CS가 난다. 정책 미결정이 기술 부채가
  되는 지점을 미리 보는 눈을 확인한다.
- **결제 감사와 append-only** — "지금 상태"만 저장하면 "어떻게 이 상태가 됐는가"라는 감사·CS·분쟁 대응 질문에 답할 수 없다. 데이터 모델링에 규제·감사 요구를 반영하는 시야 — 컴플라이언스가
  명시된 포지션과 직결된다.

### 알면 좋은 +α

- **망취소** — 타임아웃으로 "우리는 실패로 기록했는데 PG엔 승인된" 거래를 정리하는 절차의 존재 자체를 아는지 — 결제 연동을 실제로 해본 사람만 아는 디테일이라 경험 진위 판별력이 높다.
- **비동기 승인 결제 수단(가상계좌 등)** — "결제=즉시 승인"이라는 카드 중심 모델이 깨지는 지점. 입금 대기·기한 만료·금액 불일치 입금이라는 새 상태들을 상태 머신에 수용할 수 있는지 본다.
- **부정 결제 탐지** — 탐지 규칙과 오탐(정상 고객 차단)의 긴장, 사전 차단과 사후 취소의 비용 차이 — 보안·UX·매출이 얽힌 다목적 최적화를 다뤄봤는지, 16장 봇 차단 질문의 결제 도메인 판이다.
- **웹훅 발신측 설계** — 수신측 설계(기본 문항)의 거울상. 수신사 한 곳의 장애가 내 발송 큐 전체를 밀리게 하지 않도록 격리하고, 재시도가 상대에게 중복으로 도착함을 전제로 서명·이벤트 ID를
  실어주는지 — "내가 만든 API의 소비자가 겪을 문제"까지 설계하는 시야로, 파트너 연동(9장) 경험의 진위를 가른다.
- **대사가 잡아낸 실제 불일치** — 의도 5(경험의 진위)의 직격 질문. 대사를 "만들어봤다"는 사람은 많지만 실제 불일치의 원인(웹훅 유실, 타임아웃 후 뒤늦은 성공, 부분 취소 누락)과 그 후의 개선까지
  말하는 사람은 겪은 사람뿐이다 — 정산 시스템 경험의 진위가 이 한 사례에서 갈린다.

## 11. Spring Batch / 배치 처리

### 기본 ⭐

- **Job/Step/Chunk 구조** — 프레임워크 구조 자체보다 "왜 청크 단위로 커밋하는가"(전체 롤백 비용, 재시작 지점)를 이해하는지 — 대량 처리의 실패를 전제한 설계 감각의 입구.
- **Commit interval의 의미** — 이 숫자 하나가 실패 시 재처리 범위, 메모리 사용량, DB 부하를 동시에 조절한다는 것을 아는지. 설정값을 "성능 다이얼"로 이해하는 사람만 튜닝을 할 수 있다.
- **Tasklet vs Chunk** — 도구 선택의 소형 사례. 건별 처리가 필요 없는 작업에 Chunk를 강요하거나, 수백만 건을 Tasklet 안 반복문으로 도는 실수를 하지 않는지 본다.

### 중급 ⭐⭐

- **실패 후 재시작 지점과 멱등성** — 배치의 실패는 일상이고, "다시 돌려도 안전한가"가 설계되지 않은 배치는 실패할 때마다 수동 데이터 정리를 부른다. 새벽 배치 실패 알람 후 "그냥 재실행"이 가능한
  시스템과 아닌 시스템의 운영 비용 차이는 크다.
- **JpaPagingItemReader 페이지 밀림** — 읽으면서 데이터가 바뀌면 페이징이 밀려 일부를 건너뛰는, "배치는 성공했는데 일부 데이터가 처리 안 된" 조용한 결함. 성공 로그가 처리 완전성을
  보장하지 않음을 아는지 — 정산 배치라면 돈 문제다.
- **skip/retry 정책** — 100만 건 중 3건의 불량 데이터 때문에 전체를 실패시킬 것인가? skip 한도, 실패 건 별도 적재, 사후 처리까지 — "부분 실패의 처리 방침"을 사전에 정의하는 성숙도를
  본다.
- **배치 시간 증가와 스케줄 겹침** — 데이터 증가에 따라 배치는 반드시 느려진다는 시간 축 사고. 겹침 감지(중복 실행 방지 락)와 근본 대응(증분 처리 전환)을 구분해 말하는지 확인한다.

### 고난이도 ⭐⭐⭐

- **배치 병렬화 방식 비교** — 병렬화는 공짜가 아니다(순서 의존성, 청크 간 경합, 재시작 복잡도). "느려서 병렬화했다"가 아니라 병목 지점에 맞는 방식을 골랐는지 — 병렬성 설계의 일반 역량을 배치라는
  구체 상황에서 검증한다.
- **배치의 운영 DB 부하 격리** — 새벽 배치가 새벽 트래픽의 응답 지연을 만드는, "배치와 서비스가 자원을 공유한다"는 사실을 의식하는지. 자기 작업의 이웃 영향(blast radius)을 계산하는 습관을
  본다.
- **배치 vs 스트림 전환 기준** — "일 1회 집계"가 "준실시간 요구"로 바뀔 때의 아키텍처 판단. 지연 요구·재처리 필요성·운영 복잡도를 축으로 결정하는지 — 요구사항 변화를 아키텍처 변화로 번역하는
  능력.
- **정산 배치의 실행 중 데이터 변경** — 집계 도중 원본이 바뀌면 합계가 안 맞는 문제는 "마감"이라는 도메인 개념(스냅샷, 기준 시점 고정)으로 푸는 것임을 아는지 — 기술 문제를 도메인 규칙으로 승화시키는
  사고를 확인한다.

### 알면 좋은 +α

- **JobInstance와 동일 파라미터 재실행 제약** — "같은 파라미터로는 완료된 Job이 다시 안 도는" 프레임워크 계약을 알고, run.id 추가 같은 우회를 의도적으로 쓰는지 — 프레임워크의 안전장치를
  이해하고 다루는 수준을 본다.
- **다중 인스턴스의 스케줄 중복 실행 방지** — 서버를 스케일 아웃한 날부터 크론이 N번 돌기 시작하는 함정. 분산 락(ShedLock 등)의 필요성을 배포 구조에서 도출하는지 확인한다.
- **"성공했는데 0건 처리" 감지** — 성공 로그는 처리 완전성을 보장하지 않는다(페이지 밀림 문제와 같은 뿌리). 처리 건수 추이를 지표로 감시하는 데까지 가는지 — 배치의 관측성을 설계하는 성숙도.

## 12. NoSQL / 데이터 다양성

### 기본 ⭐

- **NoSQL 종류와 적합 사례** — "MongoDB 써봤어요"가 아니라 데이터 형태·접근 패턴→저장소 유형의 매핑 표를 갖고 있는지. 저장소 선택은 프로젝트 초기에 한 번 하고 오래 사는 결정이라, 선택의
  어휘를 갖췄는지 본다.
- **RDB 대신 NoSQL을 고르는 기준** — 유행 따라 고르는 사람을 거르는 질문. "스키마가 자주 바뀌어서"가 아니라 트랜잭션 요구·조회 패턴·규모라는 축으로 판단하는지, 그리고 "기본값은 RDB"라는
  보수성이 있는지 확인한다.
- **CAP 정리의 실무적 의미** — 정리 암기가 아니라 "네트워크 분단 시 이 시스템은 에러를 낼 것인가, 옛 데이터를 줄 것인가"라는 구체적 질문으로 번역할 수 있는지 — 분산 저장소의 장애 모드를 예측하는
  언어다.

### 중급 ⭐⭐

- **MongoDB 임베딩 vs 참조** — RDB 정규화 본능을 그대로 가져오면 NoSQL의 이점이 사라지고, 무조건 임베딩하면 도큐먼트 비대화로 무너진다. "함께 조회되는 데이터는 함께 저장"이라는 접근 패턴
  중심 사고로 전환했는지 본다.
- **조인 없는 세계의 연관 데이터** — 비정규화의 대가(갱신 시 여러 곳 수정)를 관리하는 방법까지 말하는지. 편익만 알고 비용을 모르면 그 비용은 운영에서 데이터 불일치로 청구된다.
- **CQRS가 유효한 상황** — 패턴 지식보다 "복잡도를 추가할 만큼 읽기/쓰기 요구가 비대칭인가"라는 도입 문턱 판단을 본다. 패턴을 이력서용으로 도입하는 사람을 거르는 질문.
- **Elasticsearch 동기화와 색인 지연** — 검색 기능의 실제 어려움은 검색이 아니라 원본과의 동기화다. "방금 올린 작품이 검색 안 돼요"를 버그가 아닌 설계된 지연으로 관리(SLA 정의, 지연
  모니터링)하는지 확인한다.

### 고난이도 ⭐⭐⭐

- **수십억 건 열람 기록 스토리지 설계** — 쓰기 폭주·단순 키 조회·거대 볼륨이라는 특성에서 저장소를 역산하는 설계 문제. 요구사항 수치화(일 쓰기량, 조회 패턴)를 먼저 하는지 — 규모 추정 없이 기술명부터
  나오는 사람을 가린다.
- **Hot partition 회피** — 파티션 키 설계 실수는 배포 후 특정 파티션만 불타는 형태로 나타나고, 키 변경은 데이터 전체 재적재다. 비가역 결정의 함정을 사전에 아는지 — 샤드 키 질문의 NoSQL
  판.
- **Read-your-writes** — 최종 일관성 시스템에서 "내 글이 안 보여요"는 버그 리포트로 반드시 들어온다. 이를 기술 결함이 아니라 일관성 모델의 속성으로 인식하고 우회(세션 일관성, 자기 쓰기
  캐시)를 설계하는지 본다.

### 알면 좋은 +α

- **MongoDB 멀티 도큐먼트 트랜잭션의 남용** — 트랜잭션이 자꾸 필요하다는 건 모델링(임베딩 경계)이 접근 패턴과 어긋났다는 신호일 수 있다. 기능의 존재와 기능의 남용 신호를 구분하는지 본다.
- **TTL 인덱스와 데이터 수명 위임** — 세션·이력 데이터의 만료를 앱의 삭제 배치가 아니라 저장소 기능에 위임하는 설계 — 4장의 대량 삭제 문제를 원천 회피하는 선택지를 아는지.
- **폴리글랏 저장소의 source of truth** — RDB·Redis·ES가 공존할 때 "어디가 진실이고 나머지는 파생인가"를 명시하지 않으면 불일치가 났을 때 어느 쪽을 고칠지조차 정할 수 없다. 저장소가
  늘어날수록 필요해지는 정합성 거버넌스 감각을 본다.

## 13. 아키텍처 / 설계

### 기본 ⭐

- **레이어드 아키텍처의 책임과 의존 방향** — 계층 위반(컨트롤러에서 리포지토리 직접 호출, 서비스에 HTTP 개념 유입)을 리뷰에서 지적할 수 있는 최소 공용어. 규칙보다 "왜 의존 방향이 한쪽이어야
  하는가"(변경 파급 차단)를 설명하는지 본다.
- **모놀리스 vs MSA, 무조건 MSA인가** — "MSA가 좋대요"를 거르는 질문. 분산의 비용(네트워크 실패, 정합성, 운영 복잡도, 조직 성숙도)을 열거하고 "지금 우리 규모에는"이라는 조건부 답을
  하는지 — 아키텍처를 상황의 함수로 보는지 확인한다.
- **SOLID 실무 예시** — 원칙 암송이 아니라 자기 코드에서의 사례(OCP: PG사 추가 시 기존 코드 무수정)를 대는지로, 원칙이 체화됐는지 장식인지 가린다.
- **DTO/Entity/Domain 분리 이유** — 계층 간 데이터 계약을 분리하지 않으면 DB 컬럼 하나 바꾸는 일이 API 스펙 변경이 된다. 변경의 파급 범위를 격리하는 설계 본능이 있는지 본다.

### 중급 ⭐⭐

- **헥사고날 아키텍처** — 핵심은 용어가 아니라 "도메인 로직이 인프라(DB, 외부 API)를 모르게 한다"는 의존성 역전의 실익 — 인프라 교체와 테스트 용이성 — 을 실감해봤는지다. 유행 아키텍처를 형식만
  따라한 사람을 가리는 질문.
- **DDD Aggregate / Bounded Context** — MSA의 서비스 경계를 "팀 구조 따라" 또는 "테이블 따라" 자르면 분산 모놀리스가 된다. 경계 도출의 근거(불변식의 범위, 언어의 경계)를
  갖고 있는지 — 서비스 분리 논의에 기여할 수 있는 수준인지 본다.
- **Strangler fig 점진 전환** — 빅뱅 재작성의 실패 확률을 알고, 병행 운영·단계적 트래픽 전환·롤백 가능성을 갖춘 전환을 설계하는지 — "레거시와 함께 일하는 기술"은 신규 개발 기술보다 실무에서
  더 자주 필요하다.
- **동기 vs 비동기 통신 선택** — "응답이 즉시 필요한가"와 "실패 시 함께 실패해야 하는가"라는 두 질문으로 통신 방식을 도출하는지 — 서비스 간 결합의 형태를 요구사항에서 끌어내는 사고를 확인한다.
- **공유 라이브러리 지옥** — 공통 모듈의 버전 업이 전 서비스 동시 배포를 강요하는 역설 — 재사용이 결합이 되는 지점을 겪어봤는지. DRY 원칙의 한계를 아는 성숙도를 본다.
- **멀티모듈 경계 기준** — 모듈 경계는 팀의 빌드 시간, 코드 소유권, 순환 의존과 직결되는 일상적 결정이다. "기술 계층으로 vs 도메인으로" 나눈 근거를 말할 수 있는지 확인한다.
- **트랜잭션 스크립트 vs 도메인 모델** — 서비스 클래스가 수천 줄로 비대해지는 익숙한 결말의 근원. 단순 CRUD에 도메인 모델은 과잉이고 복잡한 불변식에 스크립트는 분기 산탄이라는, 복잡도에 따른 선택
  기준을 갖고 있는지 — "설계 패턴을 아는가"가 아니라 "코드가 썩는 방향을 예측하는가"를 본다.

### 고난이도 ⭐⭐⭐

- **부분 실패를 전제로 한 설계 원칙** — 분산 시스템 설계 철학의 총론. 타임아웃·멱등성·재시도가 개별 기법이 아니라 "부분 실패"라는 하나의 전제에서 도출됨을 꿰고 있는지 — 지식이 체계인지 파편인지
  드러난다.
- **서비스 간 데이터 소유권 패턴** — MSA 실무의 최대 난제. 동기 조회(결합)·복제(정합성 관리)·이벤트 구독(지연) 각각의 대가를 알고 상황별로 고르는지 — "조인이 안 되는 세계"에서 일해본 경험의
  검증.
- **Dual write / shadow read 검증** — 점진 전환의 성패는 전환 로직이 아니라 검증 체계(신구 결과 비교, 불일치 알람)에 달렸음을 아는지 — "전환했다"와 "전환이 옳았음을 증명했다"를
  구분하는 엄밀함을 본다.
- **웹툰 플랫폼 Bounded Context 분해** — 열람권의 소속(구매? 열람? 정책?)처럼 정답 없는 경계 문제에서 근거를 세우고 반론에 대응하는 과정 자체가 평가 대상. 도메인 모델링 실전
  시뮬레이션이다.
- **ADR과 설계 합의 프로세스** — 설계 결정의 "왜"가 기록되지 않은 조직은 2년 뒤 같은 논쟁을 반복한다. 설계를 개인기가 아니라 조직의 자산으로 만드는 습관 — 시니어로 성장할 사람인지의 지표다.
- **가역/비가역 결정의 구분 기준** — 의도 3(비가역 결정)의 메타 질문. 모든 결정에 같은 신중함을 쓰면 속도가 죽고, 비가역 결정을 가볍게 지나치면 시스템이 죽는다. 되돌림 비용을 축으로 결정을 분류하고,
  어려운 결정에만 검증(프로토타입, ADR, 리뷰 확대)을 집중하는지 — 설계 리소스의 배분 감각 자체를 본다.

### 알면 좋은 +α

- **BFF 패턴** — 웹/앱/파트너가 같은 API를 쓰며 생기는 요구 충돌을 흡수하는 계층 vs 클라이언트 수만큼 늘어나는 중복 — 계층 추가의 편익과 비용을 함께 논하는지, 9장 aggregation 설계와
  연결되는 시야다.
- **설정 중앙화·서비스 디스커버리의 역설** — 편의를 위한 공통 인프라가 전 서비스의 새 SPOF가 된다. "그것이 죽으면 무슨 일이 벌어지는가"를 도입 결정에 포함하는지 본다.
- **이벤트 스토밍 등 협업 설계 기법** — 도메인 경계는 혼자 그리는 게 아니라 도메인 전문가와 언어를 맞추며 도출하는 것 — 설계를 협업 활동으로 다뤄봤는지, Bounded Context 도출의 방법론
  판이다.
- **모듈러 모놀리스** — "MSA 아니면 모놀리스"라는 이분법을 벗어나 배포 단위와 코드 경계를 분리해 사고하는지. 경계를 컨벤션이 아니라 도구(멀티모듈 의존 방향, ArchUnit)로 강제해야 유지된다는
  것까지 — 분산의 비용 없이 경계의 이득을 취하는 중간 해를 아는 성숙도를 본다.

## 14. 운영 / 장애 대응 / 관측성

### 기본 ⭐

- **로그 레벨 기준과 좋은 로그** — 로그는 미래의 장애 대응자(대부분 미래의 자신)에게 보내는 편지다. ERROR 남발로 알람이 무의미해진 팀, 컨텍스트 없는 로그("처리 실패")로 원인 추적이 불가능한 팀을
  겪어봤는지 — 로그를 쓰는 시점에 읽는 시점을 상상하는 습관을 본다.
- **4 golden signals** — 대시보드에 지표가 100개 있어도 "무엇부터 보는가"의 우선순위가 없으면 장애 시 눈만 바쁘다. 관측의 프레임워크를 갖고 있는지 — 신규 서비스에 모니터링을 "설계"할 수
  있는지의 기초다.
- **liveness vs readiness** — 이 구분을 모르면 "시작 중인 서버에 트래픽이 가서 에러" 또는 "일시 과부하 서버가 재시작 무한 루프"가 된다. 오케스트레이터와 애플리케이션 간 계약을 정확히
  맺을 수 있는지 확인한다.
- **배포 전략 비교** — 배포는 장애의 최대 원인이다. "새 버전이 잘못됐을 때 얼마나 빨리, 좁은 피해로 되돌리는가"를 축으로 전략을 비교하는지 — 배포를 릴리즈가 아니라 리스크 관리로 보는 시각을 본다.
- **로그/메트릭/트레이스의 역할 구분** — 메트릭은 "무엇이 이상한가", 트레이스는 "어디가 느린가", 로그는 "왜 그랬는가"에 답한다는 역할 분담이 없으면 장애 때 로그부터 grep하며 시간을 태운다. 세
  신호를 넘나드는 조사 동선(지표로 범위 좁히기 → 트레이스로 구간 특정 → 로그로 원인 확인)이 있는지 — 관측 도구를 "많이 아는가"가 아니라 "순서 있게 쓰는가"를 본다.

### 중급 ⭐⭐

- **분산 추적과 trace id 전파** — MSA에서 "이 요청이 어디서 느려졌나"는 추적 없이는 서비스 수만큼의 로그 그렙이다. 전파 메커니즘(헤더, 비동기 경계에서의 유실)까지 아는지 — 관측 인프라를 쓰는
  사람인지 이해하는 사람인지 가린다.
- **새벽 에러율 급증, 첫 10분** — 장애 대응의 우선순위 감각을 통째로 검증하는 질문: 영향 파악 → 전파 → 최근 변경 확인 → 완화(롤백) 먼저, 원인 규명은 나중. "코드부터 판다"는 답은 사용자가 피
  흘리는 동안 수술 대신 부검을 하는 것 — 이 순서 감각은 겪어야만 생긴다.
- **배포 직후 latency 상승** — 배포마다 반복되는 현상의 원인 목록(JIT, 캐시, 커넥션 워밍업)을 갖고 있으면 "정상 현상"과 "이번 배포의 결함"을 빠르게 구분한다. 오탐에 롤백을 낭비하지 않는
  판단력.
- **Blameless postmortem** — 비난 문화에서는 장애 정보가 은폐되고 같은 장애가 반복된다. 회고를 개인 추궁이 아닌 시스템 개선으로 끌고 가본 경험 — 팀의 학습 능력에 기여할 사람인지 본다.
- **알람 피로** — 알람이 100개 오면 0개 오는 것과 같다. 알람을 "받을 사람이 즉시 행동할 수 있는 것"으로 큐레이션해본 경험 — 온콜 체계를 소비만 했는지 개선까지 했는지 가린다.
- **기능 플래그 릴리즈** — 배포와 릴리즈를 분리하면 문제 시 재배포 없이 끌 수 있다. 릴리즈 리스크를 코드 수준에서 관리하는 도구를 다뤄봤는지 — 대규모 사용자 대상 기능 오픈의 실무 방식이다.
- **readiness에 외부 의존 포함 논쟁** — DB 체크를 넣으면 DB 장애 시 전 인스턴스가 일제히 트래픽에서 빠져 "부분 장애를 전체 장애로 승격"시킨다. 헬스체크가 감지 장치이자 장애 증폭 장치가 될
  수 있다는 양면을 아는지 — 정답 없는 트레이드오프에서 서비스 특성 기반의 판단을 하는지 본다.
- **롤백 vs 핫픽스** — 원칙은 검증된 이전 버전으로의 롤백이지만, 롤백이 불가능한 조건(스키마 변경 동반 — 23장, 신 버전이 이미 만든 데이터)을 식별할 수 있는지가 진짜 질문이다. 장애 중의 의사결정을
  사전 규칙(배포 전에 롤백 가능성 확인)으로 만들어봤는지 — "빠른 복구 우선" 원칙(20장)의 배포 사고 판이다.
- **재시작 후 재발하는 성능 저하** — 의도 2(장애 판단)의 누수 계열 진단. "재시작하면 낫는다"는 증상이 누적형 원인(메모리/커넥션/FD 누수, 무한 증가 캐시)을 가리킨다는 패턴 인식과, 지표(힙 추이,
  커넥션 수, FD 수)로 후보를 배제하는 순서를 갖고 있는지 — 재시작을 해결책으로 아는 사람과 증상 은폐로 아는 사람을 가른다.
- **정시 에러율 스파이크** — 의도 2(장애 판단)의 주기성 진단. "같은 시각 반복"이 크론·배치·인접 시스템 스케줄·외부사 갱신·인증서/캐시 만료를 가리킨다는 것 — 시간 축 상관관계에서 원인 후보를 뽑는
  사고를 본다. 자기 시스템의 시간표(무엇이 언제 도는지)를 알고 있는지도 함께 드러난다.

### 고난이도 ⭐⭐⭐

- **재현 불가 간헐 500 추적 방법론** — 재현이 안 되면 "관측을 늘려 다음 발생을 잡는" 전략(상세 로깅 조건부 활성화, 발생 패턴 상관 분석)으로 전환해야 한다. 미제 사건을 포기하지 않고 체계적으로
  좁혀가는 끈기와 방법 — 시니어 디버깅의 정수를 본다.
- **운영 중 무중단 메모리 누수 진단** — "재시작하면 되죠"와 "재시작은 증상 은폐고 언젠가 더 크게 터진다" 사이의 성숙도 차이. 운영 제약(덤프의 STW, 트래픽 배제 후 관찰) 하에서 진단을 설계하는
  능력을 확인한다.
- **대규모 장애 커뮤니케이션** — 큰 장애에서 기술만큼 중요한 것이 정보 흐름(상황실, 주기적 공유, 복구 우선순위 결정권)임을 아는지 — 장애를 혼자 고치는 사람이 아니라 대응을 조직화할 사람인지 본다.
- **SLI/SLO/에러 버짓** — "안정성이냐 속도냐"라는 소모적 논쟁을 숫자 기반 의사결정(버짓 소진 시 기능 개발 중단)으로 바꾸는 도구. 안정성을 감정이 아니라 계약으로 다루는 조직에서 일할 준비가 됐는지
  확인한다.

### 알면 좋은 +α

- **로그 중앙화 파이프라인과 비용** — 서버 접속 grep에서 중앙 검색으로의 전환은 장애 대응 속도를 바꾼다. 동시에 로그는 실제 청구서가 되는 비용(보존 기간, 샘플링, 레벨 정책)임을 아는지 — 관측성을
  운영 가능한 예산으로 다루는 시야.
- **메트릭 카디널리티 폭발** — userId를 라벨로 넣는 순간 시계열이 사용자 수만큼 생겨 모니터링 시스템이 먼저 죽는다. 관측 도구 자체의 용량 설계라는, 한 겹 위의 운영 감각을 본다.
- **Synthetic monitoring** — 트래픽이 없는 새벽의 장애는 사용자 지표로는 아침에야 보인다. 능동적으로 호출해 확인하는 감시 계층의 필요성 — "지표가 조용함"과 "정상"을 구분하는지 확인한다.

## 15. 컨테이너 / 인프라 (Docker, Kubernetes)

### 기본 ⭐

- **컨테이너 vs VM / 이미지와 컨테이너** — "내 로컬에선 되는데요"를 없애는 도구의 원리. 격리 수준의 차이(커널 공유)를 알아야 컨테이너의 한계(보안 경계, 커널 의존 문제)도 안다.
- **이미지 최적화** — 이미지 크기는 배포 속도·스케일 아웃 반응 속도·레지스트리 비용으로 직결된다. 빌드 캐시를 이해하는 사람의 CI는 2분, 모르는 사람은 20분 — 팀 전체의 반복 비용을 줄일 수 있는
  사람인지 본다.
- **Pod/Deployment/Service** — 쿠버네티스 위에 배포되는 앱의 개발자로서, 자기 앱이 어떻게 스케줄되고 트래픽을 받는지 모르면 인프라 팀과의 대화가 통역 없이 불가능하다.

### 중급 ⭐⭐

- **컨테이너 환경 JVM 힙 설정** — 컨테이너 메모리 limit과 JVM 힙의 관계를 모르면 OOMKilled가 반복되는데 앱 로그에는 아무 흔적이 없다. "JVM과 컨테이너, 두 세계의 경계"에서 발생하는
  문제를 다룰 수 있는지 — Java+K8s 조합의 필수 실무 지식.
- **requests/limits와 OOMKilled/throttling** — limit 설정이 곧 앱의 성능 상한이다. CPU throttling은 에러 없이 조용히 latency만 올리는, 원인을 모르면 못
  잡는 유형 — 인프라 설정과 앱 성능의 연결 고리를 아는지 본다.
- **HPA와 스파이크 대응 한계** — 오토스케일링은 만능이 아니다(지표 감지→기동까지의 지연). 스파이크가 예측 가능하면 사전 스케일, 불가능하면 여유 용량이라는 판단 — 자동화의 반응 속도 한계를 아는지
  확인한다.
- **무손실 롤링 업데이트** — readiness, preStop, graceful shutdown, LB 연동이 전부 맞물려야 한다는 것 — 어느 하나만 빠져도 배포마다 소량 에러가 난다. "배포 시 에러 0"
  이 여러 계층의 협주임을 아는 사람인지 본다.

### 고난이도 ⭐⭐⭐

- **특정 Pod만 느린 현상** — 같은 코드가 노드에 따라 다르게 동작하는 문제(noisy neighbor, throttling)는 앱 관점만으로는 미제가 된다. 조사 범위를 노드·cgroup까지 넓힐 수
  있는지 — 인프라 추상화 아래를 볼 수 있는 깊이.
- **Stateful 워크로드의 K8s 운영 견해** — 정답 없는 논쟁적 주제로 판단력을 본다: "가능하다"와 "우리 팀 역량으로 감당 가능하다"를 구분하고, 운영 부담을 근거로 매니지드 서비스와 비교하는지.
- **서비스 메시 도입 판단** — 해결하는 문제(mTLS, 트래픽 제어)가 실재하는지, 사이드카의 비용(지연, 운영 복잡도)을 감당할 규모인지 — 인프라 유행 기술에 대한 비용-편익 사고의 표본 검사.

### 알면 좋은 +α

- **stdout 로깅 원칙** — 컨테이너는 언제든 교체된다는 전제에서 로그 파일 소유를 포기하고 플랫폼에 위임하는 12-factor 원칙 — 컨테이너 환경으로의 사고방식 전환을 체화했는지의 표본.
- **ConfigMap/Secret 변경 반영** — "설정 바꿨는데 왜 그대로예요"의 정체(env 주입은 재시작 필요, 마운트는 지연 갱신). 선언과 반영 사이의 간극을 아는지 — K8s 위 앱 운영의 흔한 혼란
  지점이다.
- **PodDisruptionBudget** — 노드 점검(drain)이 서비스 장애가 되지 않게 하는 앱-인프라 간 계약. 인프라 팀의 작업으로부터 내 서비스를 지키는 선언을 앱 개발자의 책임으로 아는지 본다.

## 16. 보안

### 기본 ⭐

- **SQL Injection / XSS / CSRF** — 3대 고전 취약점은 "프레임워크가 막아주는" 것 같지만, 동적 쿼리 문자열 조립이나 innerHTML 한 줄로 부활한다. 원리를 알아야 프레임워크 보호가
  안 닿는 코드를 리뷰에서 잡는다 — 보안은 전담 팀이 아니라 코드 작성자의 첫 방어선이다.
- **비밀번호 저장** — 평문·양방향 암호화·빠른 해시(MD5) 저장은 유출 시 피해가 회사 존폐급이 된다. bcrypt의 "느림이 곧 방어"라는 역설을 이해하는지 — 잘못하면 되돌릴 수 없는 유형의 결정을
  확인한다.
- **JWT 구조와 탈취 대응의 어려움** — JWT의 본질적 트레이드오프(서버 상태 제거 ↔ 즉시 무효화 불가)를 아는지. "로그아웃했는데 토큰이 살아있는" 문제를 설계 시점에 인지하고 만료 전략을 세우는지 —
  인증 시스템 담당의 기본기.
- **인증 vs 인가** — 구분이 흐리면 "로그인은 했는데 남의 리소스에 접근되는" 인가 누락이 나온다. 모든 API에서 "누구인가"와 "해도 되는가"를 별도로 검증하는 습관의 언어적 기초.
- **인코딩 vs 해싱 vs 암호화** — Base64를 암호화로 알고 민감 정보를 "인코딩해서 저장"하는 사고는 실제로 반복된다. 가역성과 키의 유무라는 축으로 셋을 구분하고 용도(전송 표현, 무결성·비밀번호,
  기밀성)에 매핑하는지 — 보안 어휘의 기초가 잡혔는지 거르는 필터 질문이다.

### 중급 ⭐⭐

- **Refresh token 저장과 회전** — access token 수명 단축의 실효는 refresh token 관리에 달렸다. 회전(재사용 감지 시 전체 무효화)까지 아는지 — 토큰 인증을 "붙여본"
  수준과 "위협 모델까지 설계한" 수준을 가린다.
- **OAuth 2.0과 PKCE** — 소셜 로그인은 거의 모든 서비스의 요구사항이고, 흐름을 모르고 라이브러리만 쓰면 리다이렉트 검증 누락 같은 구멍이 생긴다. PKCE의 필요성(코드 탈취 시나리오)을 설명할
  수 있으면 흐름을 공격자 관점에서 이해한 것이다.
- **시크릿 관리** — 깃에 커밋된 API 키는 삭제해도 히스토리에 남고, 유출 봇은 수 분 안에 찾아낸다. 시크릿의 저장·주입·순환 체계를 갖춘 팀에서 일해봤는지 — 한 번의 실수가 곧 사고인 영역의 규율을
  본다.
- **PII 암호화와 마스킹 계층** — 개인정보가 로그로 새는 사고는 개발자의 무의식적 로깅 한 줄에서 나온다. 데이터 분류→계층별 처리(저장 암호화, 로그 마스킹)를 체계로 아는지 — 규제 준수가 명시된
  포지션의 실무 요구.
- **IDOR 방지** — "URL의 ID만 바꾸면 남의 주문이 보이는" 취약점은 스캐너가 못 잡고 코드 리뷰로만 잡힌다. 모든 리소스 접근에 소유권 검증을 넣는 설계 습관 — 자동화가 못 막는 취약점을 사람이
  막을 수 있는지 본다.
- **서비스 간 내부 인증** — "내부망이니까 인증 생략"은 침투 한 번에 전체가 뚫리는 수평 이동 경로를 만든다. 제로 트러스트 관점에서 내부 호출에도 신원과 권한을 요구하는지 — 신뢰 경계를 네트워크 위치가
  아니라 워크로드 단위로 긋는 시야를 본다.
- **세션 고정 공격** — 로그인 성공 시 세션 ID 재발급이라는 한 줄이 빠지면 공격자가 미리 심어둔 세션이 인증된 세션으로 승격된다. 인증 구현의 "아는 사람만 챙기는" 디테일 — 프레임워크가 기본 제공하는
  방어(스프링 시큐리티의 세션 마이그레이션)를 인지하고 쓰는지 확인한다.
- **파일 업로드 보안** — 확장자만 믿으면 콘텐츠 위장(이미지로 위장한 스크립트)에 뚫리고, 업로드 파일이 웹 루트에서 실행 가능하면 곧 원격 코드 실행이다. 검증·저장 위치 분리·서빙 경로 격리라는 다층
  방어를 아는지 — 사용자 입력 중 가장 위험한 형태(파일)를 다루는 체크리스트의 보유를 확인한다.
- **SSRF** — 사용자가 준 URL을 서버가 대신 호출하는 순간, 서버의 네트워크 위치(내부망, 클라우드 메타데이터 엔드포인트)가 공격자에게 넘어간다. 웹훅 등록·이미지 수집 같은 흔한 기능이 공격면임을
  인지하는지 — "서버가 클라이언트가 되는" 지점의 위험을 아는, 클라우드 시대에 중요도가 급상승한 취약점이다.

### 고난이도 ⭐⭐⭐

- **국가별 규제가 아키텍처에 미치는 영향** — GDPR 삭제권은 "백업과 이벤트 로그 속 개인정보까지 어떻게 지우나"라는 아키텍처 문제다. 법무 요구를 기술 설계로 번역하는 능력 — 이 공고의 "
  법령·컴플라이언스 반영" 업무 그 자체다.
- **콘텐츠 서빙 보안의 현실적 수준** — 클라이언트에 보여준 이상 완벽한 복제 방지는 불가능하다는 한계를 인정하고, "방어 수준과 비용·UX의 균형점"을 정하는 판단 — 완벽이 불가능한 문제에서 멈출 지점을
  정하는 성숙도를 본다.
- **크리덴셜 스터핑/봇 차단** — 정상 로그인과 구분이 어려운 공격을 계층별(네트워크 rate limit, 행동 패턴, 캡차)로 다층 대응하는 설계. 보안과 UX(정상 사용자 불편)의 긴장을 다뤄봤는지
  확인한다.

### 알면 좋은 +α

- **의존성 취약점 대응 (Log4Shell류)** — 내가 안 짠 코드의 구멍이 내 사고가 되는 시대. 공개 후 첫 하루의 대응 순서(영향 파악→완화→패치)와 평소 대비(의존성 스캔, SBOM)를 갖췄는지 —
  대응 속도가 곧 노출 시간이다.
- **감사 로그 설계** — "누가 언제 무엇을"은 일반 로그와 요구 수준이 다르다(변조 방지, 보존 기간, 접근 통제). 로그를 용도별로 다른 데이터 등급으로 다루는지 — 규제 대응 포지션의 실무 감각.
- **보안 응답 헤더** — HSTS 같은 헤더 한 줄이 다운그레이드 공격을 막는다. 프레임워크 기본값 너머에 명시적으로 챙겨야 할 방어 계층이 있음을 아는지 본다.
- **암호화 키 관리와 로테이션** — 암호화의 실무 난제는 알고리즘이 아니라 키의 수명주기다. 키를 코드·DB에 두는 순간 암호화가 무의미해지는 것, envelope encryption으로 대량 데이터의 키
  로테이션을 전체 재암호화 없이 푸는 구조까지 — "암호화했다"와 "키가 안전하다"를 구분하는지 본다.

## 17. 테스트 / 코드 품질

### 기본 ⭐

- **단위/통합 구분과 테스트 피라미드** — 피라미드가 역전된(E2E만 잔뜩) 팀은 테스트가 느리고 깨지기 쉬워 결국 아무도 안 돌린다. 테스트 포트폴리오를 비용 구조로 이해하는지 — 테스트를 "짜는" 것과 "
  전략을 갖는" 것의 차이.
- **좋은 단위 테스트의 조건** — 느리고 순서 의존적인 테스트는 자산이 아니라 부채다. 테스트 코드도 유지보수 대상임을 아는지 — "테스트가 있다"와 "테스트가 신뢰된다"를 구분하는 기준을 본다.
- **Mock의 남용 경계** — 전부 mocking한 테스트는 구현을 복창할 뿐 아무것도 검증하지 않는다. "무엇을 검증하려는가"에서 mock 대상을 역산하는지 — 테스트가 형식인지 검증인지 가리는 질문.
- **테스트하기 어려운 코드 개선** — 시각·랜덤·외부 의존을 주입으로 분리하는 능력은 곧 설계 능력이다. "테스트하기 어렵다"를 "설계가 잘못됐다"는 신호로 읽는지 — 테스트와 설계의 연결을 이해하는 수준을
  본다.

### 중급 ⭐⭐

- **외부 PG API 의존 테스트** — 외부사 샌드박스에 의존한 테스트는 그쪽 사정으로 CI가 깨진다. 계약 테스트·스텁 서버로 "우리가 통제하는 경계"를 만드는지 — 통제 불가능한 의존과 함께 일하는 기술을
  확인한다.
- **@SpringBootTest 비용과 슬라이스** — 전체 컨텍스트 테스트만 쓰는 팀은 테스트 10분 → 개발자가 안 돌림 → 품질 하락의 악순환에 빠진다. 테스트 실행 시간을 팀 생산성 문제로 다뤄봤는지
  본다.
- **동시성 버그의 테스트 재현** — "가끔만 실패하는" 버그를 결정적으로 재현하는 기법(래치로 인터리빙 강제, 반복 실행)을 아는지 — 가장 잡기 어려운 버그 유형에 대한 공략법 보유 여부.
- **Testcontainers vs H2** — H2로 통과한 쿼리가 운영 MySQL에서 다르게 동작하는 함정(방언, 락 동작 차이). "테스트 환경과 운영 환경의 괴리"가 만드는 거짓 안심을 경계하는지
  확인한다.
- **코드 리뷰에서 보는 것** — 리뷰 관점의 우선순위(정합성·동시성·경계 조건 > 스타일)가 잡혀 있는지. 팀의 코드 품질은 리뷰어의 눈높이가 결정하므로, 리뷰어로서의 기여 가능성을 직접 측정한다.

### 고난이도 ⭐⭐⭐

- **테스트 0% 레거시에 기능 추가** — 실무에서 가장 흔하면서 가장 어려운 상황. "일단 리팩토링"이 아니라 현재 동작 고정(characterization test) → 안전망 위에서 변경이라는 순서를
  아는지 — 레거시를 다루는 전문 기술의 유무.
- **파이프라인 테스트 전략과 flaky 관리** — flaky test를 방치하면 "빨간불인데 머지"가 습관이 되어 테스트 체계 전체가 무너진다. 테스트 인프라의 신뢰도를 운영하는 관점 — 개인 기술을 넘어 팀
  시스템을 관리할 수 있는지 본다.
- **카오스 엔지니어링** — "장애 대응을 장애가 났을 때 처음 해보는" 팀과 미리 연습한 팀의 차이. 무엇부터(스테이징에서 의존성 하나 차단) 시작할지 답하는지로, 개념 소비자인지 실행 가능한 수준인지 가린다.

### 알면 좋은 +α

- **픽스처 관리와 테스트 간 간섭** — 테스트 데이터 준비가 테스트 코드의 실제 유지보수 비용이고, 간섭(공유 상태, 실행 순서 의존)이 flaky의 주범이다. 테스트 격리를 설계 문제로 다루는지 본다.
- **아키텍처 테스트 (ArchUnit)** — 리뷰어의 눈에만 의존하던 계층 규칙을 CI가 강제하게 만드는 도구 — 규율을 사람에서 시스템으로 옮기는 사고를 갖췄는지, 13장의 계층 원칙과 연결된다.
- **커버리지 지표의 함정** — 숫자가 목표가 되면 assert 없는 테스트가 양산된다(굿하트의 법칙). 지표를 신호로 쓰되 목표로 삼지 않는 분별 — 측정 문화의 성숙도를 잰다.

## 18. 비동기 / Non-blocking 프로그래밍

### 기본 ⭐

- **동기/비동기 × 블로킹/논블로킹 4분면** — 이 구분이 흐리면 "비동기로 바꿨는데 왜 안 빨라져요"(내부는 여전히 블로킹)라는 상황을 이해할 수 없다. 이후 모든 비동기 논의의 좌표계.
- **CompletableFuture 예외 처리** — 비동기 예외는 조용히 사라진다 — get() 안 하면 아무도 모른다. "에러가 로그에도 안 남는" 최악의 실패 모드를 인지하고 있는지 확인한다.
- **이벤트 루프 모델** — 적은 스레드로 많은 연결을 처리하는 원리를 알아야 그 대가(루프 위에서 블로킹 금지)도 안다. Netty 기반 도구(WebClient, Redis 클라이언트)를 안전하게 쓰기 위한
  전제 지식.

### 중급 ⭐⭐

- **thenApply vs thenApplyAsync 실행 스레드** — "어느 스레드에서 실행되는가"를 모르고 쓴 비동기 체인은 느린 작업을 이벤트 루프에서 실행해 전체를 마비시킨다. 비동기 코드의 스레드
  흐름을 추적할 수 있는지 — 눈에 안 보이는 실행 컨텍스트를 보는 능력.
- **스레드풀 분리 이유** — 외부 API 지연이 내부 처리까지 굶기는 것을 풀 격리로 막는 bulkhead 개념. 자원 격리를 코드 수준에서 실천하는지 — 연쇄 장애 방어가 아키텍처만의 일이 아님을 아는지
  본다.
- **Mono/Flux와 backpressure** — 리액티브의 핵심이 "빠름"이 아니라 "생산-소비 속도 협상"임을 아는지 — 리액티브를 유행어로 아는 사람과 문제 해결 도구로 아는 사람을 가린다.
- **WebClient 병렬 조합** — 순차 3회 호출(300ms)을 병렬(100ms)로 바꾸는, 비동기의 실질 이득이 나오는 대표 지점. 개념을 실제 latency 개선으로 연결해본 경험을 확인한다.
- **비동기에서 MDC/트랜잭션 유실** — 스레드 경계를 넘으면 ThreadLocal 기반의 모든 것(로그 컨텍스트, 트랜잭션, 인증 정보)이 사라진다. "비동기 도입 후 trace id가 끊겨요"는 반드시 겪는
  문제 — 겪고 해결해봤는지가 비동기 실전 경험의 척도다.

### 고난이도 ⭐⭐⭐

- **리액티브 스택의 블로킹 혼입** — 이벤트 루프 스레드 몇 개가 전부인 구조에서 블로킹 하나가 전체 서비스를 세운다 — 리액티브의 이점과 취약점이 동전의 양면임을 아는지. 감지 도구(BlockHound)까지
  아는지로 운영 수준을 가린다.
- **R2DBC의 실익 판단** — "전 구간이 논블로킹이어야 의미 있다"는 병목 이동의 원리와, DB 커넥션이 병목이면 리액티브가 무의미한 경우를 아는지 — 기술의 이득이 나오는 조건을 특정하는 사고를 본다.
- **Virtual Thread 시대의 WebFlux** — 정답 없는 최신 논쟁으로 기술 판단력을 본다: 각 접근의 남는 가치(backpressure, 스트리밍)와 사라지는 가치(스레드 절약)를 분리해
  논하는지 — 기술 지형 변화를 자기 언어로 소화하고 있는지 확인한다.
- **Coroutine-Reactor 혼용과 컨텍스트 전파** — 실제 코드베이스는 패러다임이 섞여 있고, 경계에서 컨텍스트(MDC, 트랜잭션)가 끊긴다. 이질적 기술의 접합부에서 일할 수 있는지 — 교과서 밖
  실무의 지저분함을 다루는 능력.

### 알면 좋은 +α

- **비동기 수단의 선택 스펙트럼** — 스레드풀+CompletableFuture(재시작 시 유실), Spring Event(프로세스 경계 내), 메시지큐(내구성·재시도) — "유실돼도 되는가, 재시도가 필요한가"
  라는 요구 축으로 고르는지. "일단 @Async"가 왜 위험한지의 종합 판단이다.
- **CompletableFuture의 타임아웃·취소** — 비동기의 실패·중단 경로까지 설계하는지, cancel이 실행 중인 스레드를 멈추지 않는다는 오해 포인트를 아는지 — 행복 경로만 아는 비동기 사용자를
  가린다.
- **주기 작업의 침묵 중단** — scheduleAtFixedRate는 예외 한 번에 이후 실행이 영원히 멈춘다는 유명 함정. "주기 작업의 마지막 성공 시각"을 감시하는 데까지 가는지 — 스케줄러의 실패 모드를
  아는 운영 감각.

## 19. CS 기초 (운영체제 / 자료구조)

### 기본 ⭐

- **프로세스 vs 스레드, 컨텍스트 스위칭 비용** — "스레드를 늘리면 빨라진다"의 한계(스위칭 오버헤드)를 아는지 — 스레드풀 크기, 가상 스레드의 존재 이유 등 상위 개념 전부가 이 기초 위에 선다.
- **뮤텍스 vs 세마포어** — 상호 배제와 개수 제한(동시 실행 N개 허용)의 구분은 "외부 API 동시 호출 10개 제한" 같은 실무 요구를 올바른 도구로 푸는 기초다.
- **가상 메모리와 페이지 폴트** — 메모리 지표(RSS vs 가상 메모리)를 올바르게 읽고, 스왑 발생이 왜 성능 절벽인지 아는지 — 서버 메모리 이슈 진단의 최소 소양.
- **HashMap O(1)의 조건과 최악** — "평균과 최악의 구분"이라는 성능 사고의 기본기. 해시 충돌 편중이 실제 서비스에서 특정 키 패턴으로 발생할 수 있음을 아는지 본다.
- **배열 vs 연결 리스트와 캐시 지역성** — Big-O가 같아도 실측이 다른 이유(메모리 접근 패턴)를 아는지 — 이론 복잡도와 실제 성능의 간극을 이해하는 사람만 올바른 최적화를 한다.
- **정렬과 TimSort** — 알고리즘 하나를 설명시키는 건 "설명 능력" 자체의 검사이기도 하다. 실무 라이브러리가 교과서 알고리즘이 아닌 이유(실데이터의 부분 정렬성 활용)까지 알면 이론-실무 연결이 된
  것이다.

### 중급 ⭐⭐

- **I/O 멀티플렉싱** — Nginx·Netty·Redis가 전부 이 원리 위에 있다. 이걸 알면 세 도구의 성능 특성과 금기 사항(블로킹 금지)이 하나의 원리로 통합 이해된다 — 개별 도구 지식을 원리로
  압축하고 있는지 본다.
- **파일 디스크립터 고갈** — "Too many open files"는 커넥션 누수의 대표 증상인데, FD 개념이 없으면 에러 메시지 자체를 해석 못 한다. OS 자원과 애플리케이션 버그의 연결을 아는지
  확인한다.
- **Zero-copy** — Kafka가 빠른 이유, 대용량 파일 서빙 최적화의 원리. 도구의 성능 주장("빠릅니다")을 메커니즘으로 검증할 수 있는 깊이의 표본.
- **CPU는 낮은데 처리량이 안 나옴** — 대기(락, I/O, 커넥션풀)가 병목일 때의 전형적 증상 — "CPU 낮음 = 여유 있음"이라는 오독을 하는지 검사한다. 이 오독은 스케일 아웃이라는 비싼 오답으로
  이어진다.
- **페이지 캐시와 DB/Kafka 성능** — "메모리 여유가 없어 보이는데 정상"(페이지 캐시)을 읽어내고, 재시작 직후 디스크 읽기 폭증의 이유를 아는지 — OS와 미들웨어 성능의 접점을 보는 시야.

### 고난이도 ⭐⭐⭐

- **NUMA** — 하드웨어 토폴로지가 대형 인스턴스의 성능 편차를 만드는 지점. 극한 튜닝 경험 또는 그 수준까지 파본 호기심의 표지 — 대부분 몰라도 되지만, 아는 사람은 깊이가 증명된다.
- **fsync와 내구성의 비용** — "커밋이 왜 느린가"의 물리적 근원. DB 설정(innodb_flush_log_at_trx_commit)의 내구성-성능 트레이드오프를 판단할 때 필요한 바닥 지식 — 추상화의
  최하층까지 내려가본 깊이를 잰다.
- **cgroup 환경의 CPU 지표 왜곡** — 컨테이너 시대에 "보이는 지표가 실제와 다른" 대표 사례. 지표를 무조건 믿지 않고 수집 메커니즘까지 의심하는 관측 성숙도를 본다.

### 알면 좋은 +α

- **시스템 콜과 모드 전환 비용** — 버퍼링·배치 write·zero-copy 같은 I/O 최적화 전부의 공통 근거. "왜 잘게 쓰면 느린가"를 원리로 답할 수 있는지 본다.
- **JVM OOM vs 리눅스 OOM Killer** — 힙 OOM은 자바 로그에, OOM Killer는 dmesg에 흔적을 남긴다. "로그도 없이 죽었어요"의 진단 경로가 완전히 다름을 아는지 — 15장
  OOMKilled와 연결되는 컨테이너 시대의 필수 구분.
- **ulimit 등 OS 리소스 제한** — 파일 디스크립터·프로세스 수 상한은 코드에 안 보이는 서버의 벽이다. 애플리케이션 증상(간헐적 accept 실패)을 OS 설정까지 내려가 확인하는 시야를 본다.

## 20. 경험 기반 / 시나리오 질문 (기술 태도)

> 이 섹션의 공통 의도: 기술 지식이 아니라 **일하는 방식의 재현 가능성**을 본다. 과거 행동은 미래 행동의 최선의 예측 변수이므로, 구체적 일화(상황·수치·본인의 판단 지점)가 없는 일반론은 전부 감점이다.

- **가장 자랑스러운 설계 + 다시 만든다면** — 후반부가 진짜 질문이다: 자기 설계의 한계를 스스로 말할 수 있는가. 완벽했다고 답하는 사람은 회고 능력이 없거나 설계 경험이 얕은 것 — 성장 곡선의 기울기를
  예측하는 질문.
- **기술 부채 vs 신규 기능 판단과 설득** — 엔지니어의 일은 코드가 아니라 우선순위 협상까지다. 부채의 비용을 비즈니스 언어(장애 위험, 개발 속도 저하)로 번역해 비개발자를 설득해봤는지 — 시니어로 갈수록
  이 능력이 코딩보다 희소해진다.
- **가장 기억에 남는 자기 장애** — 사고를 숨기지 않고 말하는 solidity, 원인의 구조적 이해(내 실수 → 시스템이 못 막은 이유), 재발 방지의 실행 여부까지 — 장애를 학습으로 전환하는 사이클이 있는
  사람인지 본다. 수치를 요구하는 건 일화의 진위 검증이다.
- **10배 성능 개선의 가설과 측정** — "튜닝했더니 빨라졌어요"와 "측정 → 병목 가설 → 검증"의 차이. 측정 없는 개선담은 우연이거나 과장 — 성능 업무의 과학적 방법론 보유 여부를 가린다.
- **기술 의견 대립의 해소** — 목소리 크기나 연차가 아니라 실험·데이터·트레이드오프 정리로 결론에 도달했는지, 그리고 자기 의견이 기각됐을 때의 행동 — 팀에 들어왔을 때의 협업 마찰 비용을 예측한다.
- **신기술 도입 근거 / 도입 안 한 경험** — "도입하지 않기로 한 경험"을 묻는 쪽이 핵심이다: 유행 기술의 문제 적합성을 검증하고 기각할 수 있는 절제 — 기술 선택의 비용을 조직이 치른다는 것을 아는
  사람인지 본다.
- **모호한 요구사항에서의 시작** — 실무 요구사항은 늘 불완전하다. 가정을 명시하고, 되돌리기 쉬운 부분부터 만들고, 빨리 보여줘서 피드백을 당기는지 — 불확실성 앞에서 멈추는 사람인지 움직이는 사람인지
  가린다.
- **리팩토링의 원칙과 멈추는 기준** — "멈추는 기준"이 진짜 질문이다. 리팩토링 범위가 계속 번지는 사람은 일정과 리뷰 가능성을 해친다 — 완벽주의와 실용주의의 균형점을 스스로 정할 수 있는지 본다.
- **운영 DB 스키마 변경 프로세스** — 지식(무중단 DDL)이 아니라 절차 감각을 본다: 영향 분석 → 하위 호환 순서(컬럼 추가 → 코드 배포 → 마이그레이션 → 정리) → 롤백 계획. 위험한 작업을 의식(
  ritual)으로 만드는 사람인지 — 운영 사고의 대부분은 절차 생략에서 나온다.
- **리뷰에서 크게 지적받은 경험** — 피드백을 방어하지 않고 흡수해 행동을 바꾼 구체적 사례가 있는지 — 코칭 가능성(coachability)은 2~4년차 채용에서 현재 실력보다 중요한 변수다.
- **트래픽 100배 시 첫 붕괴 지점** — 자기 시스템의 병목 지도를 머리에 갖고 있는지 — 이것이 없는 사람은 시스템을 "돌아가는 상태"로만 알고 "왜 돌아가는지"는 모르는 것이다. 용량 한계에 대한 상시적
  의식을 검사한다.
- **API 스펙 협의 갈등** — 프론트·기획과의 스펙 갈등은 주간 단위로 발생하는 일상이다. 기술 근거와 상대 제약(앱 심사 일정 등)을 함께 놓고 조율하는지 — 협업 인터페이스의 품질을 본다.
- **빠른 복구 vs 원인 규명** — 원칙(복구 우선)과 예외(증거 보존이 필요한 경우, 복구 시도가 상황을 악화시킬 경우)를 함께 말하는지 — 장애 상황의 의사결정 프레임이 있는지 확인한다.
- **문서화 수준에 대한 견해** — "코드로 표현 가능한 것(무엇을)"과 "코드로 표현 불가능한 것(왜, 기각된 대안)"을 구분해 후자만 문서화한다는 기준이 있는지 — 문서화를 신앙이 아니라 비용-편익으로
  다루는지 본다.
- **온콜과 반복 알람 개선** — 알람을 받기만 한 사람과 알람의 근본 원인을 줄여간 사람의 차이 — 운영 부담을 "견디는" 사람이 아니라 "갚아나가는" 사람인지, 온콜 체계에 대한 주인의식을 확인한다.
- **운영 설정값 변경 경험** — 의도 5(경험의 진위)의 정밀 검증. 기본값을 한 번도 바꿔본 적 없다는 것은 시스템을 한계까지 운영해본 적 없다는 뜻이기 쉽다. 변경의 근거(측정), 절차(단계 적용), 결과(
  수치)를 말하는지 — "써봤다"와 "운영했다"의 차이가 설정값 하나의 이야기에서 드러난다.
- **매일 보는 지표 3개** — 의도 5(경험의 진위). 자기 서비스를 실제로 돌보는 사람은 지표에 우선순위와 이유(이 지표가 무엇의 전조인지)가 있다. 모니터링이 "있다"고 말하는 사람과 매일 "읽는다"는
  사람을 가르는 질문.
- **이력서 기술의 4연쇄 자가 점검** — 의도 6(꼬리 질문의 발판)을 역이용하는 준비법이자 질문. 면접관은 이력서의 키워드마다 "왜 → 대안 → 트레이드오프 → 회고"로 파고들고, 이 체인이 끊기는 지점이 곧
  지식의 경계다. 스스로 먼저 파보게 하는 것 — 답변의 깊이만이 아니라 자기 깊이의 "위치"를 아는지(메타 인지)를 본다.

### 알면 좋은 +α

- **일정 지연의 조기 공유** — 지연 자체보다 늦은 보고가 신뢰를 깬다. 나쁜 소식을 빨리, 대안과 함께 전하는 사람인지 — 협업 리스크 관리의 핵심 습관을 본다.
- **새 팀/도메인 파악 순서** — 코드보다 먼저 볼 것(도메인 용어, 배포 방식, 최근 장애 이력)의 우선순위가 있는지 — 학습 능력의 재현 가능성을 온보딩이라는 구체 상황으로 검증한다.
- **자동화 판단** — 반복 작업을 갚아나가는 주인의식과, 발생 빈도 대비 자동화 비용을 따져 "안 하기로 한" 절제 — 양쪽이 다 있는지로 판단력의 균형을 본다.

## 21. 시스템 설계 (화이트보드 대비)

> 이 섹션의 공통 의도: 설계 질문에 정답은 없다. 면접관이 보는 것은 (1) **요구사항을 수치화하는 습관**(규모 추정 없이 기술명부터 나오면 감점), (2) **트레이드오프의 명시적 선택**(모든 걸 다
> 잘하는 설계는 아무것도 결정 안 한 설계), (3) **실패 시나리오 자문**("이게 죽으면?"을 스스로 묻는지), (4) **면접관과의 대화 능력**(요구사항을 되묻고, 피드백에 설계를 수정하는지)이다. 각
> 문제는
> 이 4가지를 특정 각도에서 자극한다.

- **회차 열람 시스템** — 이 회사의 핵심 트랜잭션 그 자체. 권한 검증의 위치(매 이미지 요청마다? 열람 시작 시 토큰 발급?), 이미지 서빙과 권한의 분리, 열람 기록의 쓰기 폭주 — 도메인의 실제 난점을
  얼마나 빨리 짚어내는지로 적합성을 본다.
- **실시간 인기 랭킹** — "실시간"의 정의를 되묻는지(1초? 1분?)가 첫 관문. 정확한 실시간의 비용과 근사치의 저렴함 사이에서 요구를 협상하는 능력 — 비기능 요구의 완화 지점을 찾는 설계 감각을 잰다.
- **댓글 시스템** — 쓰기보다 조회 패턴(베스트 정렬, 페이징)이 어려운 문제. 좋아요 수 정렬의 캐싱과 정합성, 신고/블라인드의 상태 관리 — 평범해 보이는 기능의 숨은 복잡도를 발견하는 눈을 본다.
- **선착순 쿠폰** — 정합성(초과 발급 0건)과 처리량(초당 수만)이 정면 충돌하는 문제. 어디서 원자성을 지키고 어디를 비동기로 미루는지의 절단면 — 일관성 요구의 계층화 능력을 정밀 측정한다.
- **수백만 명 알림 발송** — 발송 자체(팬아웃 전략)와 발송 후 유입 스파이크까지 — 시스템 경계 밖의 2차 효과를 설계에 포함하는지. 대량 작업의 시간 분산, 실패 재시도의 중복 방지까지 가면 상급.
- **URL 단축** — 설계 면접의 고전이라 준비 여부가 드러나는 문제. 그래서 면접관은 표준 답을 넘어 변형(커스텀 키 충돌, 통계 집계의 쓰기 부하, 리다이렉트 latency 예산)으로 파고든다 — 암기한
  설계인지 이해한 설계인지 가린다.
- **정기 구독 결제** — 시간 기반 트리거(수백만 건 갱신의 시간 분산), 실패의 단계적 처리(재시도 → 유예 → 해지), 결제 수단 만료 — 실패 경로가 본체인 시스템을 설계할 수 있는지. 유료 콘텐츠
  도메인의 실제 업무와 직결된다.
- **검색 자동완성** — latency 예산이 밀리초 단위인 문제(타이핑마다 호출). 전용 자료구조(trie), 프리컴퓨트, 클라이언트 디바운스까지 — 극단적 응답 속도 요구에서 계층 전체를 동원하는 설계를
  본다.
- **글로벌 콘텐츠 배포 파이프라인** — 국가별 노출 정책·번역본이라는 도메인 규칙과 멀티 리전 데이터 배치의 결합 — 이 공고의 "글로벌 서비스 + 규제 반영" 업무의 축소판. 기술과 정책이 얽힌 문제의 분해
  능력을 확인한다.
- **A/B 테스트 플랫폼** — 버킷팅의 일관성(같은 유저는 항상 같은 그룹), 지표 수집의 대량 쓰기, 실험 간 간섭 — 인프라성 플랫폼 설계로, "기능 개발"을 넘어 "개발자를 위한 시스템"을 설계하는
  시야까지 있는지 본다.
- **SNS 피드/타임라인** — push(쓰기 시 팬아웃)와 pull(읽기 시 집계)의 선택이 팔로워 분포에 따라 갈리고, 유명인(팔로워 수백만)은 하이브리드로 푸는 고전 문제. 같은 기능도 데이터 분포에 따라
  설계가 달라진다는 것 — "평균이 아니라 꼬리(스큐)가 설계를 결정한다"는 대용량 설계의 핵심 감각을 정면으로 검사한다.
- **실시간 채팅** — 장수 커넥션 관리(8장 웹소켓), 메시지 순서와 ID 채번(4장), 읽음 상태의 쓰기 폭주, 오프라인 푸시 폴백까지 여러 장의 지식이 한 문제에 조합되는 종합 설계. "전송 중 유실과
  중복"이라는 메시징의 본질 문제(6장)를 사용자 향 기능에서 다시 푸는지 — "실시간"의 실제 요구 수준을 되묻는 습관도 함께 본다.

### 알면 좋은 +α

- **이미지 업로드·썸네일 파이프라인** — 콘텐츠 플랫폼의 일상 업무 그 자체. 동기 처리 범위(업로드 응답)와 비동기 범위(파생본 생성)의 절단, 원본·파생본 관리, CDN 무효화까지 — 미디어 처리의 전
  경로를 그릴 수 있는지 본다.
- **다중 기기 동시 이용 제한** — 세션 상태·실시간성·동시 로그인 경합이 얽힌 문제로, 계정 공유 제한이라는 콘텐츠 비즈니스 요구와 직결된다. 정확성(즉시 차단)과 구현 비용의 절충점을 스스로 정하는지 본다.
- **무중단 대용량 데이터 이전** — dual write→백필→검증→컷오버라는 순서와 각 단계의 롤백 지점 — 13장 점진 전환 원칙의 실전 종합판으로, "되돌릴 수 있는 상태를 유지하며 전진"하는 능력을
  검증한다.

## 22. 글로벌 서비스 / 국제화 (시간, 인코딩, 규제)

> 공고의 "다양한 국가의 법령, 규제 및 컴플라이언스 요구사항 검토 및 서비스 반영"이 이 섹션의 존재 이유다. 글로벌 서비스의 버그는 한국 서버·한국 개발자·한국 테스트를 전부 통과하고 해외 사용자에게만
> 터진다 — 즉 "테스트로 못 잡는 버그"의 밀집 지대라서, 미리 아는 사람과 겪고 아는 사람의 차이가 유난히 크다.

### 기본 ⭐

- **시간 저장·처리 원칙 (Instant vs LocalDateTime vs ZonedDateTime)** — 타임존 버그는 로컬에서도 CI에서도 재현되지 않고 해외 사용자의 "공개 시각이 이상해요" CS로만
  나타난다. "저장·연산은 UTC(Instant), 표시 시점에만 사용자 타임존 변환"이라는 규율이 없으면 국가가 추가될 때마다 기존 데이터가 오염된다. 글로벌 포지션에서 가장 싸게 물어서 가장 확실하게 실무
  준비도를 가리는 질문.
- **utf8mb4와 이모지** — 댓글에 이모지 하나가 들어오는 순간 MySQL utf8(실제 3바이트) 테이블은 INSERT가 깨지거나 데이터가 잘린다. 인코딩이 "어딘가의 설정"이 아니라 클라이언트→서버→DB
  전 구간의 데이터 계약임을 아는지 — 댓글·닉네임을 받는 콘텐츠 서비스가 반드시 한 번은 겪는 사고 유형이다.
- **i18n 메시지 처리 계층** — 에러 메시지를 서버가 번역해 내려줄지, 에러 코드만 주고 클라이언트가 번역할지는 API 계약 설계 문제다. 전자는 언어 추가마다 서버 배포, 후자는 코드 체계 관리 비용 —
  언어 추가라는 확실한 미래 변경이 어느 계층에 파급되는지를 미리 사고하는지 본다.

### 중급 ⭐⭐

- **국가별 공개 시각과 DST** — "매일 밤 11시 공개"가 국가마다 다른 절대 시각이고, DST 전환일에는 하루가 23시간 또는 25시간이라 "존재하지 않는 시각"과 "두 번 오는 시각"이 생긴다. 크론
  표현식 하나로 끝난다고 믿는 사람은 3월과 11월에 두 번 사고를 낸다 — 시간이라는 익숙한 개념의 숨은 복잡도를 존중하는지, 이 회사의 "정시 신작 공개"라는 실제 업무에 바로 연결되는 감각인지 본다.
- **Geo-blocking의 판정과 정책 분리** — 국가 판정 수단(IP, 계정 설정, 스토어 지역)이 각각 불완전함(VPN, 여행자, 이사)을 알고, "판정"과 "노출 정책"을 분리해 정책 변경이 배포 없이
  가능하게 설계하는지 — "법령 준수"라는 추상적 요구가 코드 구조로 착지하는 지점의 실무 능력을 확인한다.
- **국가별 집계의 '하루' 기준** — 일 단위 랭킹·정산에서 "하루"가 어느 타임존의 하루인지 정의하지 않으면 국가별 숫자가 미묘하게 어긋나고, 그 어긋남은 파트너 정산 분쟁으로 청구된다. 기술 이전에 도메인
  규칙을 시간 축에서 명시하는 습관 — 정산 배치의 "마감" 개념(11장)의 글로벌 판이다.
- **국가별 가격/통화 데이터 모델** — 통화마다 소수점 자리(원화 0, 달러 2, 디나르 3)와 반올림 규칙이 다르다는 사실을 모델에 반영하는지. "금액은 통화와 함께여야만 의미 있는 값"이라는 도메인 모델링
  감각 — 10장의 부동소수점 금지와 짝을 이루는 글로벌 결제의 기초다.

### 고난이도 ⭐⭐⭐

- **국가별 연령 규제의 설계 격리** — 성인 인증 방식·연령 기준이 국가마다 다를 때 `if (country == ...)` 분기가 코드 전체에 퍼지면 국가 추가마다 전체 회귀 테스트가 필요해진다. 정책을
  데이터/전략 객체로 격리해 변경을 국소화하는 설계 — "규제는 반드시 또 바뀐다"는 전제로 아키텍처를 세우는지, 공고의 컴플라이언스 업무를 감당할 설계 역량이 있는지 본다.
- **데이터 국외 이전 제한과 데이터 토폴로지** — 특정 국가 데이터는 그 리전 밖으로 나갈 수 없다는 법적 하드 제약이 "글로벌 통합 통계"라는 비즈니스 요구와 정면 충돌한다. 원본은 리전에 고정하고
  집계·가명화 결과만 이동시키는 식의 절충을 설계할 수 있는지 — 법이 만드는 제약 조건 안에서 시스템을 최적화하는, 이 포지션 고유의 문제 해결을 시뮬레이션한다.
- **보존 의무 vs 삭제권 충돌** — "전자상거래 기록 5년 보관"과 "개인정보 즉시 삭제 요구"가 같은 데이터에 동시에 걸리는 모순을 분리 보관·가명화·접근 통제 조합으로 푸는지 — 법무 요구를 그대로
  구현하는 게 아니라 기술 해법으로 번역해 역제안하는, 규제 대응 실무의 최고 난도 지점이다.

### 알면 좋은 +α

- **번역 폴백 전략** — 미번역 키가 빈 문자열이나 코드 그대로 사용자에게 노출되는 사고. 폴백 체인(요청 언어→기본 언어→키)을 명시적으로 설계하는지 — 국제화의 실패 경로까지 설계하는 습관을 본다.
- **국가별 회원 데이터 모델** — 수집 가능 항목·동의 방식이 국가의 함수일 때 필수/선택 필드를 어떻게 모델링하는지 — 규제가 스키마를 바꾸는 실무 사례로, 컴플라이언스 업무의 데이터 설계 판이다.
- **tzdata 업데이트의 영향** — 타임존 규칙은 "법으로 바뀌는 데이터"다(국가의 DST 폐지 등). 저장된 미래 시각(예약 공개)이 규칙 변경 시 재해석되는 문제까지 아는지 — 시간을 정적 상식이 아니라
  관리 대상 데이터로 보는 깊이.

## 23. 빌드 / CI·CD / 형상관리

> 배포는 장애의 최대 원인이고, 빌드·파이프라인은 팀 전체가 매일 지불하는 고정 비용이다. 이 섹션은 "코드를 잘 짜는가" 너머 "코드가 운영에 도달하는 경로를 신뢰할 수 있게 만드는가"를 본다 — 2~4년차가
> 팀에 기여할 수 있는 가성비 높은 영역이기도 하다.

### 기본 ⭐

- **브랜치 전략 선택 기준** — 전략 이름 암기가 아니라 배포 주기·팀 규모·릴리즈 형태(상시 배포 vs 버전 릴리즈)에서 전략을 도출하는지. "브랜치가 오래 살수록 머지 비용이 복리로 커진다"는 비용 구조를
  아는 사람은 작은 PR·짧은 브랜치라는 일상 습관도 갖고 있다 — 협업 규율의 표본 검사.
- **CI 파이프라인 단계 구성** — "테스트를 돌린다" 이상으로 무엇을(컴파일→단위→통합→정적 분석) 어떤 순서로(싼 검증 먼저, 빠른 실패) 배치하는지 — 파이프라인을 팀의 품질 게이트로 설계하는 관점이
  있는지, 피드백 루프 속도가 곧 개발 속도임을 아는지 본다.
- **Gradle api vs implementation** — 의존성 노출 범위가 변경 전파 범위(= 증분 빌드 속도)와 모듈 경계 누수를 결정한다. 멀티모듈에서 이 구분을 대충 하면 한 줄 수정이 전체 재빌드가
  되고, 하위 모듈의 내부 구현이 상위에 새어나간다 — 빌드 도구를 "돌아가게 하는" 수준과 "설계하는" 수준의 분기점.

### 중급 ⭐⭐

- **빌드 시간 개선** — 빌드 20분은 개발자당 하루 수 시간의 대기이자 "CI 통과 전에 퇴근" 같은 우회 행동의 원인이다. 측정(어느 단계가 느린가)→캐시·병렬화·테스트 계층 분리의 순서로 접근하는지 — 팀
  생산성을 인프라 문제로 다뤄본 경험, 17장의 테스트 전략과 연결되는 시야를 확인한다.
- **DB 마이그레이션과 코드 롤백 호환** — "코드는 롤백했는데 스키마는 이미 바뀐" 상황에서 구버전 코드가 신스키마 위에서 도는 순간을 상정해봤는지. 롤백 가능한 배포가 expand-contract(
  추가→전환→정리) 같은 스키마 변경 규율을 전제함을 아는지 — 20장의 "스키마 변경 프로세스"를 배포 안전성 관점에서 재검증하는 질문이다.
- **프레임워크 메이저 업그레이드 절차** — Spring Boot 2→3 같은 업그레이드를 "브랜치 하나에서 한 방"이 아니라 사전 호환 작업(deprecated 제거)→의존성 단계 상향→환경별 검증 게이트로
  쪼개는지 — 크고 위험한 변경을 작고 되돌릴 수 있는 단계로 분해하는 능력은 리팩토링·전환 작업 전반에 이식되는 핵심 역량이다.

### 고난이도 ⭐⭐⭐

- **한 번 빌드, 여러 환경 배포(artifact promotion)** — 스테이징에서 검증한 바이너리와 운영에 가는 바이너리가 다르면(환경별 재빌드) 스테이징 검증은 무효라는 원칙을 아는지. 이 원칙이 설정
  외부화·환경 독립적 아티팩트라는 전제를 요구함까지 연결하는지 — "검증했다"는 말의 엄밀한 의미를 따지는 사고를 본다.
- **모노레포 vs 멀티레포** — 정답 없는 조직·도구 설계 문제로 판단력을 잰다: 원자적 크로스 모듈 변경·코드 공유(모노레포)와 소유권 명확성·빌드 격리(멀티레포)의 트레이드오프를 팀 규모·도구 성숙도의
  함수로 논하는지 — 기술 선택이 조직 구조의 함수임을 아는 시야까지 있으면 상급이다.

### 알면 좋은 +α

- **파이프라인 시크릿 관리** — CI 로그는 의외로 많은 눈에 노출되고, 포크 PR로 시크릿이 흘러가는 구조적 위험도 있다. 마스킹·주입 방식·접근 범위를 챙기는지 — 16장 시크릿 관리의 파이프라인 판이다.
- **카나리 자동 롤백** — 사람이 지켜보는 카나리는 새벽 배포에서 무용지물이다. 판단 지표(에러율, p99)와 임계값을 사전에 정의해 자동화하는지 — 배포 안전을 사람의 주의력에서 시스템으로 옮기는 성숙도.
- **의존성 자동 업데이트 운영** — Dependabot PR이 쌓이기만 하는 팀과 꾸준히 머지되는 팀의 차이는 테스트 신뢰도다. 보안 패치 속도(16장)가 결국 테스트 체계(17장)에 달려 있다는 연결을 보는지
  확인한다.

## 24. AI 도구 활용 / 성장 방식

> 문서 서두에서 밝힌 "AI 산출물 검증 능력"을 정면으로 묻는 섹션이다. AI 도구 사용이 기본값이 된 시대에 면접관이 확인하려는 것은 사용 여부가 아니라 **검증의 기준과 책임의 소재** — 그리고 자동화
> 시대에도 깊이가 계속 쌓이는 사람인지다. 2~4년차 채용에서는 "이 사람의 5년 뒤"를 예측하는 질문이기도 하다.

- **AI 코딩 도구 활용 방식과 검증 기준** — 쓰는지가 아니라 어떻게 검증하는지를 본다. "동작하니 통과"인 사람과 "트랜잭션 경계·동시성·엣지 케이스·기존 컨벤션 부합을 리뷰 기준으로 검증"하는 사람의
  차이가 앞으로 팀 코드베이스의 품질 차이가 된다. AI가 짠 코드도 커밋한 사람의 책임이라는 소유 의식이 있는지 — 이것이 없는 사람의 생산성 향상은 부채 생산 속도의 향상이다.
- **AI 생성 코드에서 잡아낸 버그 사례** — 검증 능력의 실증 질문. "그럴듯했지만 틀렸던 지점"(존재하지 않는 API, 미묘하게 어긋난 동시성 처리, 프로젝트 컨벤션 위반)을 구체적으로 말하는 사람은 AI를
  도구로 부리는 사람이고, 사례가 전혀 없는 사람은 AI 출력을 검증 없이 소비해왔을 가능성이 높다 — 5번 의도(경험의 진위 판별)의 AI 시대 버전이다.
- **AI에 맡기는 것과 직접 하는 것의 경계** — 위임 경계의 기준은 곧 "무엇이 내가 검증 가능한 범위이고 무엇이 책임의 핵심인지"에 대한 자기 인식이다. 경계가 없는 사람은 검증할 수 없는 것까지 맡기고,
  경계가 지나친 사람은 도구 시대의 생산성을 잃는다 — 판단 기준을 언어화할 수 있는지 자체가 메타 인지의 증거다.
- **AI 시대의 깊이 쌓기** — 보일러플레이트를 직접 짜며 배우던 경로가 좁아진 시대에 내재화(장애 대응 복기, 원리 역추적, 생성된 코드 리뷰를 학습 기회로 전환)를 어떻게 유지하는지 — 자기 성장을 스스로
  설계하는 메타 능력을 본다. 이 질문에 답을 갖고 있는 사람만이 "AI로 10배 생산"과 "10년차에도 주니어 깊이" 사이의 갈림길에서 전자의 길로 간다. 이 문서를 먼저 쓰고 질문을 도출하는 공부법 자체가 그
  답의 한 예다.
- **사람도 놓치는 AI 결함 유형** — 의도 4(AI 검증)의 한 단계 위 메타 질문. AI 결함 중 사람 리뷰가 잘 잡는 것(네이밍, 명백한 로직 오류)과 함께 놓치는 것(그럴듯한 동시성 처리, 미묘한 경계
  조건, 존재하지 않는 API의 자연스러운 사용)을 구분하고, 그 빈틈을 사람의 주의력이 아니라 장치(테스트 강제, 정적 분석, CI 게이트)로 메우는지 — 25장 재발 방지 체계화와 연결되는 AI 시대의 품질
  설계 감각이다.

### 알면 좋은 +α

- **AI 도구와 데이터 경계** — 생산성 도구가 코드·고객 데이터의 유출 경로가 될 수 있다는 인식과, 무엇을 넣어도 되는지의 판단 기준(사내 정책, 민감도 분류)을 갖췄는지 — AI 시대의 기본 보안 소양.
- **AI 생성 테스트의 함정** — 구현을 그대로 복창해 항상 통과하는 테스트는 검증이 아니라 동어반복이다. 테스트가 명세(의도)를 검증하는지 구현을 재확인할 뿐인지 분별하는 눈 — 17장 mock 남용 문제의
  AI 판이다.
- **팀 차원의 AI 활용 규칙** — 개인의 활용 노하우를 팀의 리뷰 기준·책임 규칙으로 승격시키는 사고 — 연차와 무관하게 프로세스 개선에 기여할 수 있는 지점이고, 그런 제안을 해본 사람인지 본다.

## 25. 시니어 잣대 대응 — 같은 질문, 다른 기대치

> 공고가 2~4년차여도 지원자가 몰리는 회사는 면접을 "연차 대비 뛰어난 사람"을 거르는 상향 필터로 운영한다. 중요한 사실: 시니어 잣대는 대부분 새로운 질문이 아니라 **같은 질문에 대한 답의 고도**로
> 적용된다. 면접관은 답변을 3단계로 등급화한다:
>
> 1. **안다** — 개념을 정확히 설명한다. 책과 AI로 얻을 수 있는 수준. 최소 합격선.
> 2. **겪었다** — 증상, 삽질 과정, 트레이드오프의 아픈 쪽을 말한다. 경험의 증거. 좋은 2~4년차.
> 3. **체계를 만들었다** — 그 문제가 다시 나올 수 없게 만든 장치와, 그것을 팀에 전파한 이야기를 한다. 6~8년차의 답.
>
> 3단계 답이 한두 개만 나와도 면접관은 "연차 대비 뛰어남"으로 기록한다. 예를 들어 N+1 질문에서 1단계는 "fetch join으로 해결합니다", 2단계는 "쿼리 로그로 배포 전에 잡습니다", 3단계는 "
> 테스트에서 쿼리 수를 검증하는 규칙을 CI에 넣어 팀 전체의 재발을 막았습니다"다. 장애 질문에서 1단계는 원인 설명, 2단계는 복구 경험, 3단계는 재발 방지 장치와 다른 팀 전파다. 공통 패턴: **지식 →
경험 → 팀의 자산**.
>
> 아래 질문들은 3단계 답이 존재하는지를 직접 캐는, 시니어 변별 전용 질문이다.

- **팀 전체가 따라야 했던 기술 결정** — 내 코드가 아니라 남들이 따라야 하는 결정(컨벤션, 공통 모듈, 기술 선택)을 내리고, 반대 의견과 결정 이후의 결과(반발, 실패, 정착)까지 책임져봤는지 — 개인
  기여자와 기술 리더의 분기점이다. 결과가 실패였더라도 복기가 정확하면 오히려 가점.
- **재발 방지의 체계화** — 같은 유형의 버그·장애가 구조적으로 다시 나올 수 없게 만든 장치(린트 규칙, 아키텍처 테스트, CI 게이트, 코드 템플릿)가 있는지 — "고쳤다"와 "다시는 안 나게 했다"의
  차이가 연차 잣대의 핵심이다.
- **비용 의식** — 인프라 비용을 줄인 경험, 또는 성능 개선의 비용 대비 효과를 계산해 "하지 않기로" 한 판단 — 시니어는 기술을 돈의 언어로 번역해 비개발 의사결정자와 대화할 수 있어야 한다. 최적화를
  멈춘 이야기가 최적화를 한 이야기보다 시니어함을 더 증명한다.
- **주니어 성장 지원** — 리뷰·페어링·문서로 다른 사람을 성장시킨 구체적 방법과 그 사람의 변화 — "팀의 총 처리량을 늘리는 사람"인지의 증거로, 혼자 잘하는 사람의 상한을 넘는지 본다.
- **크로스팀 기술 협상** — 다른 팀이 소유한 시스템의 변경을 이끌어내거나 공유 자원의 계약(SLA, 스키마, API 스펙)을 협상한 경험 — 조직 경계를 넘는 영향력은 연차가 올라갈수록 코딩보다 희소하고 비싼
  능력이다.
- **1년 뒤를 내다본 부채 관리** — "지금은 문제없지만 6개월 뒤 터진다"를 데이터로 예측하고 미리 갚도록 설득한 경험 — 사고의 시간 축이 스프린트 단위인지 분기·연 단위인지가 주니어와 시니어의 조용한
  차이다.

## 26. 인증 / 인가 / 세션 (이력 기반 심화)

> 면접관은 이력서의 주력 도메인을 반드시 파고든다 — 여기서 답이 얕으면 다른 모든 답변의 신뢰도가 함께 떨어지고, 깊으면 "자기 도메인을 완전히 소유한 사람"으로 각인된다. IAM 경력자에게 이 섹션은 선택이
> 아니라 본진 방어전이다. 동시에 콘텐츠 플랫폼도 계정·세션·기기 제한이 핵심 기능이므로, 본인 경험을 지원 회사의 문제로 번역해 보이는 연결 능력까지 평가된다. 25장의 3단계 잣대(안다→겪었다→체계를 만들었다)
> 가
> 가장 엄격하게 적용되는 곳 — 이 장의 질문만큼은 3단계 답을 준비해야 한다.

### 기본 ⭐

- **세션 저장소 설계** — 7장의 stateless 원칙이 인증이라는 구체 도메인에 착지하는 지점. 스티키 세션의 함정(스케일 인 시 세션 소실), Redis 중앙화의 폭발 반경(장애 = 전 사용자 로그아웃,
  5장), 토큰의 무효화 문제(16장)를 하나의 결정 안에서 종합하는지 — 본인 도메인이므로 각 방식의 아픈 지점을 일반론이 아니라 실증으로 말할 수 있어야 한다.
- **SSO / SAML vs OIDC** — 프로토콜 스펙 암기가 아니라 "신뢰를 어떻게 위임하는가"라는 구조(IdP-SP 관계, 클레임 전달, 서명 검증)를 그릴 수 있는지. B2B는 SAML 레거시가 현실이고
  신규는 OIDC라는 지형, 그리고 연동에서 실제로 터지는 지점(시계 오차, 인증서 만료, 리다이렉트 URI 검증)을 겪어봤는지 — IAM 경력의 진위를 가장 직접적으로 검증하는 질문이다.
- **RBAC vs ABAC / 조직 계층 권한** — 역할 폭발(예외 케이스마다 역할이 늘어나는 것)과 속성 기반의 유연성-복잡성 트레이드오프를 아는지. 조직 트리 상속, 겸직, 권한 위임 같은 현실 요구가
  교과서 모델을 어떻게 비트는지 겪어본 사람의 답은 다르다 — 권한 모델은 한번 잘못 잡으면 전 기능에 파급되는 비가역 결정이다.

### 중급 ⭐⭐

- **동시 로그인 제한** — 21장 +α(다중 기기 제한)의 본진 판. 로그인 경합(두 기기가 동시에 로그인), 강제 로그아웃의 전파 지연, "먼저 로그인한 쪽과 나중 쪽 중 누구를 끊는가"라는 정책 결정까지 —
  상태 관리·실시간성·UX가 얽힌 문제를 자기 도메인에서 풀어봤는지 확인한다.
- **JWT 즉시 무효화** — 16장 JWT 트레이드오프의 실전 심화. 블랙리스트를 두는 순간 "상태 없는 토큰"이라는 존재 이유가 무너지는 역설을 인식하고, 그럼에도 취할 절충(짧은 만료 + 리프레시 시점
  검증, 중요 작업만 서버 확인)을 설계하는지 — 아키텍처 선택의 대가를 끝까지 따라가는 사고를 본다.
- **멀티테넌시 격리** — 격리 수준(DB/스키마/로우 레벨)이 비용, 운영 복잡도, 유출 리스크, 테넌트별 커스터마이징 요구와 맞물리는 다차원 결정임을 아는지. "WHERE tenant_id 한 줄 누락이 곧
  타사 정보 유출 사고"라는 로우 레벨 격리의 아픈 지점을 방어 장치(쿼리 인터셉터, 테스트 게이트)와 함께 말하면 실무자다.
- **전 기기 로그아웃** — 세션이 여러 저장소·기기·토큰에 흩어져 있을 때 "전부 무효화"가 얼마나 어려운 요구인지 아는지. 토큰 버전/세대(generation) 비교 같은 설계 패턴으로 푸는지 — 계정
  탈취라는 보안 사건 대응 절차의 기술적 뒷받침을 설계해봤는지 본다.
- **외부 IdP 장애 시 로그인 흐름** — 인증이 외부 의존을 갖는 순간 7장의 타임아웃·서킷·폴백 문제가 로그인이라는 최전선에서 재현된다. "고객사 AD가 죽으면 우리 서비스도 로그인 불가인가"에 대해 캐시된
  인증 정보·유예 정책 같은 절충을 설계해봤는지 — 자기 시스템의 장애 모드를 파악하고 있는지 확인한다.
- **토큰 저장 위치** — localStorage는 XSS 한 방에 토큰이 통째로 유출되고, httpOnly 쿠키는 CSRF 방어가 다시 필요해진다는 "무엇을 막으면 무엇이 열리는" 트레이드오프의 전형. 쿠키
  속성(SameSite, Secure) 설계는 백엔드의 몫이라 프론트엔드 협업에서 백엔드가 답을 갖고 있어야 하는 질문이다 — 인증 도메인 경력자라면 즉답이 기대되는 지점.

### 고난이도 ⭐⭐⭐

- **대규모 조직 동기화(SCIM)** — B2B IAM의 최난제 중 하나. 대량 변경의 중간 상태(조직 개편 도중의 반영 순서), 순서 의존(부서 생성 전 사원 배치 불가), 부분 실패 복구, 원천(HR 시스템)
  과의 정합성 검증까지 — 11장 배치 설계와 6장 이벤트 설계가 도메인 위에서 종합되는 문제다. 본인의 실제 업무와 가장 가까운 질문이므로 3단계(체계화) 답이 나와야 하는 지점.
- **인증 시스템의 SPOF 완화** — "인증이 죽으면 전부 죽는" 구조를 토큰 서명 검증의 로컬화(각 서비스가 공개키로 자체 검증), 공개키 캐싱, 만료 유예 같은 설계로 완화하는지 — 가용성과 보안(무효화
  즉시성)이 정면 충돌하는 지점에서 절충안을 만드는 능력을 본다. 7장 cascading failure 방어를 자기 도메인에서 증명할 기회다.
- **권한 변경 전파 지연** — 발급된 토큰, 캐시된 권한, 세션에 이미 실린 정보라는 3중의 지연 축적을 인식하는지. "퇴사자가 몇 분간 접근 가능해도 되는가"를 보안 요구와 성능 비용의 협상으로 다루고,
  즉시성이 필요한 소수 지점(결제, 관리자 기능)만 실시간 확인하는 차등 설계를 하는지 — 최종 일관성(6장)의 인가 판이다.

### 알면 좋은 +α

- **다양한 OAuth grant** — authorization code 외의 흐름(서버 간 통신, 입력 제약 기기)이 각각 어떤 신뢰 모델을 전제하는지 — OAuth를 "소셜 로그인 라이브러리"가 아니라 위임
  프레임워크로 이해하는 깊이의 표본.
- **계정 잠금의 DoS 역이용** — 방어 장치가 공격 도구가 되는 역설(아이디만 알면 남의 계정을 잠글 수 있음)을 아는지 — 보안 정책의 2차 효과까지 사고하는지, 점진적 지연·CAPTCHA·IP 기반 차등
  같은 대안의 트레이드오프를 논할 수 있는지 본다.
- **인증 감사 로그** — 16장 감사 로그의 IAM 판. 인증·인가 이벤트는 보안 사고 조사에서 유일한 진실 소스라 변조 방지·완전성(실패 시도 포함)·검색 가능성의 요구 수준이 다르다 — 규제 대응과 사고
  대응을 모두 지원하는 데이터 설계를 해봤는지 확인한다.
- **패스키(WebAuthn)** — 비밀번호가 사라지면 유출·스터핑 위협도 사라지지만, 공개키 등록·기기 분실 시 복구·크로스 디바이스 동기화라는 새 관리 대상이 생긴다. "비밀번호 제거"가 인증 책임의 제거가
  아니라 이동임을 아는지 — 인증 기술의 다음 세대를 백엔드 관점에서 소화하고 있는지 본다.

## 맺음: 이 문서를 활용하는 법

각 질문의 출제 의도를 알면 답변의 방향이 바뀐다:

1. **지식 나열이 아니라 상황 연결로 답하라** — "N+1은 ~입니다"보다 "N+1을 방치하면 데이터가 쌓일수록 조회가 느려지는데, 저는 쿼리 로그로 배포 전에 잡습니다"가 출제 의도에 명중하는 답이다.
2. **트레이드오프 질문은 한쪽 편을 들되 조건을 달아라** — 면접관은 결정 못 하는 사람보다 근거 있는 결정을 하는 사람을 찾는다.
3. **경험 질문에서 실패담을 아껴두지 마라** — 실패 + 구조적 원인 분석 + 재발 방지가 성공담보다 높게 평가되는 이유가 위 의도에 다 나와 있다.
4. **모든 답의 끝에 "그래서 실무에서 나는 ~한다"를 붙일 수 있는지 자문하라** — 그 문장이 안 나오는 지식은 아직 면접용으로 준비가 안 된 것이다.
